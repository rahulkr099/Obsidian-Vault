# Lesson 0.3 — System Architecture

Now we're going to design the **brain and skeleton** of the AI LMS.

The goal of this lesson is not to memorize technologies. You should understand:

> **When a user performs an action, where does that request go, what happens to it, and where does the data live?**

# 2. Why Modular Monolith?

You may hear:

> "Real companies use microservices."

Don't blindly follow that.

For your project, microservices would introduce unnecessary complexity:

```text
Service A
Service B
Service C
Service D
     ↓
Network communication
     ↓
Docker
     ↓
Service discovery
     ↓
Monitoring
     ↓
Deployment
```

Instead:

```text
                    Backend
                       │
        ┌──────────────┼──────────────┐
        │              │              │
       Auth          Courses          AI
        │              │              │
     Progress        Quiz         Resources
```

Everything runs as one application, but modules are logically separated.

This gives you:

**simplicity + good architecture + room to scale.**

# 3. Frontend Architecture

Our frontend is:

```text
React
   +
TypeScript
   +
Vite
```

Its main responsibility is:

> **Display UI and communicate with the backend.**

It should NOT contain business-critical logic.

For example:

```text
Student clicks "Enroll"
        ↓
React
        ↓
POST /api/v1/courses/:id/enroll
        ↓
Backend
```

React shouldn't decide:

```text
"Is this student actually allowed to enroll?"
```

The backend decides that.

# 5. Backend Architecture

Our backend follows:

```text
Request
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Prisma
   ↓
PostgreSQL
```

This is one of the most important parts of this project.

---

# 6. Route Layer

Example:

```http
POST /api/v1/courses
```

The route connects the URL to the appropriate controller.

Conceptually:

```text
POST /courses
      ↓
authMiddleware
      ↓
roleMiddleware
      ↓
courseController.create
```

Routes shouldn't contain business logic.

---

# 7. Middleware Layer

Middleware handles things that should happen **before the controller**.

Examples:

```text
Authentication
Authorization
Validation
Rate limiting
Logging
```

For example:

```text
Request
  ↓
Is user logged in?
  ↓
Does user have instructor role?
  ↓
Is request valid?
  ↓
Controller
```

---

# 8. Controller Layer

The controller should be **thin**.

Its job is basically:

```text
Request
   ↓
extract data
   ↓
call service
   ↓
send response
```

For example:

```text
courseController
       ↓
courseService.createCourse()
       ↓
response
```

Don't put 100 lines of business logic inside the controller.

---

# 9. Service Layer

This is where our **business logic** lives.

Example:

```text
courseService.createCourse()
```

might perform:

```text
Validate instructor
        ↓
Validate category
        ↓
Generate slug
        ↓
Create course
        ↓
Return course
```

The controller shouldn't know all those details.

---

# 10. Repository Layer

The repository handles database access.

Example:

```text
courseRepository.create()
courseRepository.findById()
courseRepository.findBySlug()
courseRepository.update()
courseRepository.delete()
```

So:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Prisma
    ↓
PostgreSQL
```

This separation will be especially useful when you write tests.

# 12. Prisma

Prisma sits between our application and PostgreSQL.

```text
Node.js
   ↓
Prisma
   ↓
PostgreSQL
```

Why use Prisma?

You get:

- Type-safe database queries
    
- migrations
    
- schema management
    
- relationships
    
- good TypeScript integration
    

But remember:

> **Prisma is not the database.**

PostgreSQL is the database.

# 14. Background Workers

Here's where our system becomes more interesting.

Imagine an instructor uploads:

```text
nodejs-course.pdf
```

We need to:

```text
Extract text
      ↓
Clean text
      ↓
Split into chunks
      ↓
Generate embeddings
      ↓
Store vectors
```

That could take time.

Don't make the user's HTTP request wait for all of this.

Instead:

```text
Instructor
    │
    ▼
Upload PDF
    │
    ▼
API Server
    │
    ├──────────────► Object Storage
    │
    ▼
Create Job
    │
    ▼
Redis / BullMQ
    │
    ▼
Worker
    │
    ├── Extract text
    ├── Chunk
    ├── Generate embeddings
    └── Store vectors
```

The API can immediately respond:

```json
{
  "status": "PROCESSING"
}
```

That's a real backend engineering pattern.

---

# 15. Object Storage

Large files should not live directly inside our backend server.

We'll eventually use object storage for:

```text
PDFs
Videos
Images
Course resources
Certificates
```

Architecture:

```text
Browser
   ↓
Upload
   ↓
Object Storage
   ↓
File URL
   ↓
PostgreSQL
```

PostgreSQL stores metadata such as:

```text
filename
url
size
mimeType
courseId
uploadedBy
```

Not the actual large file.

# 18. Vector Database

PostgreSQL handles normal structured information.

A vector database handles **semantic search**.

For example:

```text
Student:
"How does authentication work?"
```

The system doesn't necessarily search for exact words.

Instead:

```text
Question
   ↓
Embedding
   ↓
Vector similarity
   ↓
Relevant course content
```

Possible choices later include:

- pgvector with PostgreSQL
    
- Qdrant
    
- another vector database
    

For your project, I'd strongly consider **pgvector with PostgreSQL** initially.

That lets you keep the architecture simpler.

```text
   ↓

```

Notice something important:

**Never blindly trust AI output.**

The AI might return malformed data.


# 20. Complete Request Example

Let's follow one request from beginning to end.

Suppose a student clicks:

> Enroll in Node.js Course

### Step 1 — React

```text
Student clicks Enroll
```

### Step 2 — Axios

```http
POST /api/v1/courses/123/enroll
```

### Step 3 — Express

```text
Router
```

### Step 4 — Authentication

```text
Is JWT/session valid?
```

### Step 5 — Authorization

```text
Is user a STUDENT?
```

### Step 6 — Controller

```text
enrollmentController.create()
```

### Step 7 — Service

```text
enrollmentService.enroll()
```

Business logic:

```text
Does course exist?
       ↓
Is course published?
       ↓
Already enrolled?
       ↓
Create enrollment
```

### Step 8 — Repository

```text
enrollmentRepository.create()
```

### Step 9 — Prisma

```text
Prisma
   ↓
INSERT
```

### Step 10 — PostgreSQL

Enrollment is stored.

### Step 11 — Response

```json
{
  "success": true,
  "message": "Successfully enrolled"
}
```

### Step 12 — React

UI updates:

```text
✓ Enrolled
Continue Learning →
```

That's the kind of flow you should be able to explain during your viva.

# 23. Our Architecture Principles

I want you to follow these throughout the project.

### Principle 1 — Frontend is not trusted

```text
Frontend validation ≠ Security
```

Backend validates everything important.

---

### Principle 2 — Controllers stay thin

```text
Controller
    ↓
Service
```

Business logic belongs in services.

---

### Principle 3 — Database access is isolated

```text
Service
    ↓
Repository
    ↓
Prisma
```

---

### Principle 4 — AI stays behind our backend

```text
React
 ↓
Backend
 ↓
AI Service
 ↓
LLM
```

Never expose your AI provider API key to React.

---

### Principle 5 — Heavy work is asynchronous

```text
HTTP request
     ↓
Quick response
     ↓
Background job
```

Use this for things like document processing and embeddings.

---

### Principle 6 — PostgreSQL is the source of truth

Redis can disappear.

Cache can disappear.

AI provider can change.

But our core LMS data remains in PostgreSQL.
