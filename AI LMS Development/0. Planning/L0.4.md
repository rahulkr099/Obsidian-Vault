# Lesson 0.4 — Database & ER Design

Now we are going to design the **database of our AI LMS**.

This is one of the most important planning steps because almost every backend feature will eventually interact with PostgreSQL.

Our goal is to answer:

> **What data do we need, how is it related, and what rules must the database enforce?**

---

# 1. Our Database Philosophy

We'll use:

```text
PostgreSQL
    ↓
Prisma ORM
    ↓
Node.js / Express
```

The database should be responsible for **data integrity**, while the service layer handles most business rules.

We'll use:

- Primary keys
    
- Foreign keys
    
- Unique constraints
    
- Indexes
    
- Enums
    
- Timestamps
    
- Transactions where necessary

# 8. Course Status

A course shouldn't immediately become public.

We'll use:

```text
DRAFT
PUBLISHED
ARCHIVED
```

Workflow:

```text
Instructor creates
       ↓
     DRAFT
       ↓
Instructor publishes
       ↓
   PUBLISHED
       ↓
Instructor/Admin archives
       ↓
   ARCHIVED
```

This is much better than a simple:

```text
isPublished = true
```

because later we can add more states.

# 14. `enrollments`

Here's an important database relationship.

A student can enroll in many courses.

A course can have many students.

That's a:

**Many-to-Many relationship.**

We solve it using an intermediate table.

```text
STUDENT
   │
   │
   ▼
ENROLLMENTS
   ▲
   │
   │
COURSE
```

Table:

```text
enrollments
────────────────────
id
student_id
course_id
enrolled_at
completed_at
```

Important constraint:

```text
UNIQUE(student_id, course_id)
```

Why?

Without it:

```text
Rahul → Node Course
Rahul → Node Course
Rahul → Node Course
```

could accidentally happen.

We want:

```text
Rahul → Node Course
```

only once.

# 16. Important Constraint

A student should have only **one progress record per lesson**.

Therefore:

```text
UNIQUE(student_id, lesson_id)
```

This prevents:

```text
Rahul → Lesson 5 → progress record 1
Rahul → Lesson 5 → progress record 2
Rahul → Lesson 5 → progress record 3
```

Instead:

```text
Rahul → Lesson 5 → one progress record
```

which we update.

# 20. Security Consideration

Here's something important.

The frontend should **not receive `is_correct`** when displaying a quiz.

Otherwise a student could inspect the API response and immediately see:

```json
{
  "option": "A",
  "isCorrect": true
}
```

😂

Instead:

```text
Database
   ↓
Backend
   ↓
Remove correct answer
   ↓
Frontend
```

When the student submits:

```text
selectedOption
```

the backend checks the actual answer.

# 31. Database Rules We Should Enforce

These are important.

|Rule|Database enforcement|
|---|---|
|Email must be unique|`UNIQUE`|
|Course slug must be unique|`UNIQUE`|
|Category slug unique|`UNIQUE`|
|Student cannot enroll twice|Composite `UNIQUE`|
|Student has one progress record/lesson|Composite `UNIQUE`|
|Student has one review/course|Composite `UNIQUE`|
|Certificate number unique|`UNIQUE`|
|Rating 1–5|Check constraint|
|Position positive|Check constraint|
|Foreign relationships valid|Foreign keys|

This is what I mean by:

> **Let the database protect data integrity.**

Don't rely only on JavaScript checks.

# 32. Indexes

Indexes are important for performance.

We'll eventually index things like:

```text
users.email
courses.slug
courses.instructor_id
courses.category_id
courses.status
modules.course_id
lessons.module_id
enrollments.student_id
enrollments.course_id
lesson_progress.student_id
lesson_progress.lesson_id
quiz_attempts.student_id
ai_conversations.student_id
```

For example, we frequently ask:

```sql
SELECT *
FROM courses
WHERE instructor_id = ?;
```

An index on:

```text
instructor_id
```

makes this query much more efficient as the database grows.

---

# 33. Soft Delete vs Hard Delete

Another architectural decision.

Suppose an instructor deletes a course.

Should we actually execute:

```sql
DELETE FROM courses;
```

?

For some entities, I'd prefer soft deletion/archive.

For courses:

```text
status = ARCHIVED
```

rather than immediately destroying the data.

This is useful because:

```text
Analytics
Historical enrollments
Certificates
Audit history
```

may depend on the course.

---

# 34. Timestamps


Don't add timestamps blindly to every table; use them where they provide value.

# 🎯 The Most Important Concept From 0.4

Notice how we're **not** putting everything into `courses`.

Bad design:

```text
courses
────────────────────
title
lesson1
lesson2
lesson3
quiz1
quiz2
student1
student2
...
```

Instead, we're normalizing the data:

```text
Course
 ↓
Modules
 ↓
Lessons
 ↓
Quizzes
 ↓
Questions
 ↓
Options
```

and:

```text
Student
 ↓
Enrollments
 ↓
Courses
```

This makes the system much easier to query, maintain, and scale.

# 🧩 A Real Example

Suppose we create:

**Course: Node.js Backend Engineering**

```text
Course
│
├── Module 1: Express Fundamentals
│   ├── Lesson 1: Express Introduction
│   ├── Lesson 2: Middleware
│   └── Lesson 3: Routing
│
├── Module 2: Authentication
│   ├── Lesson 1: JWT
│   ├── Lesson 2: Refresh Tokens
│   └── Lesson 3: RBAC
│
└── Module 3: Database
    ├── Lesson 1: PostgreSQL
    ├── Lesson 2: Prisma
    └── Lesson 3: Transactions
```

A student enrolls:

```text
Rahul
  ↓
Enrollment
  ↓
Node.js Backend Engineering
```

Then:

```text
Rahul
 ↓
Lesson Progress
 ↓
Middleware → completed
JWT → completed
RBAC → 70%
```

Then Rahul asks:

> "Explain RBAC according to this course."

Our future AI system can do:

```text
Question
   ↓
AI Conversation
   ↓
Retrieve relevant document chunks
   ↓

   ↓
LLM
   ↓
Course-aware answer
```

Now you can see why the database design and AI architecture are connected.
