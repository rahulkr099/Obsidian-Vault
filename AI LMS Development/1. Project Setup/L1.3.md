# 4. Why `tsx`?

Normally Node.js doesn't directly execute TypeScript.

We could compile:

```text
TypeScript
    ↓
JavaScript
    ↓
Node.js
```

But during development, `tsx` gives us a convenient workflow:

```text
TypeScript
    ↓
tsx
    ↓
Node.js
```

So we can run:

```bash
pnpm dev
```

and get fast development feedback.

```json
    "moduleResolution": "NodeNext",
    "strict": true,
    "esModuleInterop": true,

```

The important options are:

```text

```

and:

```text

```

These make TypeScript more helpful at catching bugs.

# 7. `app.ts` vs `server.ts`

We're going to make an important architectural distinction.

## `app.ts`

Responsible for:

```text
Express application
Middleware
Routes
Error handler
```

## `server.ts`

Responsible for:

```text
Starting the HTTP server
```

So:

```text
app.ts
  ↓
Express application

server.ts
  ↓
app.listen()
```

Why separate them?

Because later testing becomes easier.

You can import:

```text
app
```

without automatically starting a server.

# 9. Create `server.ts`

```bash
touch src/server.ts
```

Add:

```ts
import app from "./app.js";

const PORT = process.env.PORT || 4000;

app.listen(PORT, () => {
  console.log(`API running on port ${PORT}`);
});
```

Notice:

```ts
"./app.js"
```

Even though the source file is:

```text
app.ts
```

we're using Node's ESM-style module resolution.

This is a common TypeScript + modern Node setup.

# 16. Add CORS

Eventually our React frontend runs on:

```text
http://localhost:5173
```

and backend:

```text
http://localhost:4000
```

Different origins mean we need CORS.

Install:

```bash
pnpm add cors
pnpm add -D @types/cors
```

Then:

```ts
import cors from "cors";
```

and:

```ts
app.use(
  cors({
    origin: "http://localhost:5173",
  }),
);
```

So our `app.ts` becomes approximately:

```ts
import cors from "cors";
import express from "express";
import apiRouter from "./routes/index.js";

const app = express();

app.use(
  cors({
    origin: "http://localhost:5173",
  }),
);

app.use(express.json());

app.use("/api/v1", apiRouter);

export default app;
```

Later we'll move the origin into environment configuration.

Don't hardcode production URLs.

# 18. Request Body Parsing

We already added:

```ts
app.use(express.json());
```

This lets Express understand:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

Without the middleware, `req.body` won't behave as expected for JSON requests.

We'll later add limits:

```text

  limit: "1mb"
})
```

because accepting unlimited request bodies is not a good idea.


That's fine.

But later, don't write something like this inside a course route:

```text

  // 100 lines of validation
  // database queries
  // ownership checks
  // slug generation
  // business logic
  // etc.

});
```

Instead:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
```

That's the architecture we've committed to.

# 21. Create a Simple Error Handler

We don't want Express errors scattered around the application.

Create:

```bash
touch src/middlewares/error.middleware.ts
```

Initially:

```ts
import type { ErrorRequestHandler } from "express";

export const errorHandler: ErrorRequestHandler = (
  err,
  _req,
  res,
  _next,
) => {
  console.error(err);

  res.status(500).json({
    success: false,
    error: {
      code: "INTERNAL_SERVER_ERROR",
      message: "Something went wrong",
    },
  });
};
```

Then add it **after your routes**:

```ts
app.use(errorHandler);
```

Order matters.

```text
middleware
   ↓
routes
   ↓
error handler
```

The error handler needs to be registered after the routes it handles.

We'll improve this considerably in Phase 2.
