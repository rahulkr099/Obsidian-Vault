---

# 1. Why Docker for PostgreSQL?

We could install PostgreSQL directly:

```bash
sudo apt install postgresql
```

But for this project, Docker is cleaner.

Without Docker:

```text
Linux Mint
 └── PostgreSQL installed globally
```

With Docker:

```text
Linux Mint
 └── Docker
      └── PostgreSQL container
```

This gives us:

- easy setup
    
- isolated environment
    
- reproducibility
    
- easy reset
    
- easier deployment knowledge
    
- no system-wide PostgreSQL configuration
    

And later, if you delete the project:

```bash
docker compose down
```

your Linux system doesn't have a bunch of project-specific database configuration left behind.

# 4. Create Docker Compose

From the project root:

```bash
cd ~/Projects/ai-lms
```

Create:

```bash
touch docker-compose.yml
```

Our initial file:

```yaml
services:
  postgres:
    image: postgres:17-alpine
    container_name: ai-lms-postgres
    restart: unless-stopped

    environment:
      POSTGRES_USER: ai_lms
      POSTGRES_PASSWORD: ai_lms_dev_password
      POSTGRES_DB: ai_lms

    ports:
      - "5432:5432"

    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

---

# 5. Understand This File

Don't just copy it.

Let's understand every important part.

---

## `services`

```yaml
services:
```

A Docker Compose file defines services.

Currently we have:

```text
services
   │
   └── postgres
```

Later we'll potentially have:

```text
services
```

---

# 6. PostgreSQL Image

```yaml
image: postgres:17-alpine
```

This tells Docker:

> Use the PostgreSQL 17 Alpine image.

`alpine` is a small Linux-based image.

For development, this keeps the container relatively lightweight.

---

# 7. Container Name

```yaml
container_name: ai-lms-postgres
```

So instead of an automatically generated container name, we get:

```text
ai-lms-postgres
```

Check it later with:

```bash
docker ps
```

---

# 8. Restart Policy

```yaml
restart: unless-stopped
```

This means Docker can restart the container after things like a Docker daemon restart.

But if you explicitly stop it, Docker won't keep starting it automatically.

---

# 9. PostgreSQL Environment Variables

We have:

```yaml
environment:
  POSTGRES_USER: ai_lms
  POSTGRES_PASSWORD: ai_lms_dev_password
  POSTGRES_DB: ai_lms
```

These initialize PostgreSQL.

So:

```text

ai_lms
```

# 10. Port Mapping

This:

```yaml
ports:
  - "5432:5432"
```

means:

```text
Your computer             Docker
localhost:5432  ────────► PostgreSQL:5432
```

The format is:

```text
HOST:CONTAINER
```

So:

```text
5432:5432
```

means:

```text
host port 5432
      ↓
container port 5432
```

---

# 11. Why Port 5432?

PostgreSQL's default port is:

```text
5432
```

So our connection will eventually be:

```text
localhost:5432
```

---

# 12. Volumes

This part is extremely important:

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data
```

PostgreSQL stores its database files inside:

```text
/var/lib/postgresql/data
```

inside the container.

But containers can be removed.

So we create a Docker volume:

```text
postgres_data
```

Conceptually:

```text
PostgreSQL container
        │
        ▼
/var/lib/postgresql/data
        │
        ▼
postgres_data volume
```

This means your database survives:

```bash
docker compose down
```

# 21. Important Docker Commands

You should memorize these.

### Start

```bash
docker compose up -d
```

### Stop

```bash
docker compose stop
```

### Start again

```bash
docker compose start
```

### View running containers

```bash
docker ps
```

### View logs

```bash
docker compose logs -f postgres
```

### Stop and remove containers

```bash
docker compose down
```

### Stop and remove containers + database volume

```bash
docker compose down -v
```

⚠️ Be careful with:

```bash
docker compose down -v
```

because it deletes the PostgreSQL Docker volume.

That means your local database data is gone.

---

# 22. `stop` vs `down`

This distinction is important.

### `docker compose stop`

```text
Container
   ↓
Stopped
```

Data remains.

---

### `docker compose down`

```text
Container
   ↓
Removed
```

Named volumes remain unless you use:

```bash
docker compose down -v
```

---

### `docker compose down -v`

```text
Container
   ↓
Removed

Volume
   ↓
Removed

Database data
   ↓
💀 Gone
```

Remember this.

# 23. Database Connection URL

Now we need a connection string.

Our database information is:

```text

port:     5432

```

So:

```text
postgresql://ai_lms:ai_lms_dev_password@localhost:5432/ai_lms
```

Break it down:

```text
postgresql://
        │
        ├── user
        │     ↓
        │   ai_lms
        │
        ├── password
        │     ↓
        │   ai_lms_dev_password
        │
        ├── host
        │     ↓
        │   localhost
        │
        ├── port
        │     ↓
        │   5432
        │
        └── database
              ↓
            ai_lms
```

# 25. Docker Network Concept

Here's an important concept you'll need later.

If your backend runs directly on your Linux machine:

```text
Express
localhost
    │
    ▼
localhost:5432
    │
    ▼
PostgreSQL container
```

So:

```text
DATABASE_URL
```

uses:

```text
localhost
```

But if we eventually put Express **inside Docker**, then:

```text
api container
      │
      ▼
postgres container
```

The API should use the Compose service name:

```text
postgres
```

rather than:

```text
localhost
```

So inside Docker, it becomes conceptually:

```text
postgresql://ai_lms:password@postgres:5432/ai_lms
```

This distinction is extremely important.

> Inside a container, `localhost` means **that container**, not your PostgreSQL container.

# 27. Add a Healthcheck to Compose

Let's improve our Docker setup.

Modify:

```yaml
services:
  postgres:
    image: postgres:17-alpine
    container_name: ai-lms-postgres
    restart: unless-stopped

    environment:
      POSTGRES_USER: ai_lms
      POSTGRES_PASSWORD: ai_lms_dev_password
      POSTGRES_DB: ai_lms

    ports:
      - "5432:5432"

    volumes:
      - postgres_data:/var/lib/postgresql/data

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ai_lms -d ai_lms"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

Now Docker can determine whether PostgreSQL is actually ready.

# 30. Security Improvement We'll Make Later

Currently:

```yaml
POSTGRES_PASSWORD: ai_lms_dev_password
```

is visible in:

```text
docker-compose.yml
```

For a real project, we'll move credentials to environment variables:

```text
.env
   ↓
Docker Compose
   ↓
PostgreSQL
```

For example:

```yaml
environment:
  POSTGRES_USER: ${POSTGRES_USER}
  POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
  POSTGRES_DB: ${POSTGRES_DB}
```

Then:

```env
POSTGRES_USER=ai_lms
POSTGRES_PASSWORD=...
POSTGRES_DB=ai_lms
```

We'll properly set this up in **Lesson 1.7 — Environment Configuration**.

For this lesson, understanding the database/container relationship is the priority.

# 31. Why PostgreSQL Instead of MongoDB?

For this AI LMS, PostgreSQL gives us several advantages.

Our data has many relationships:

```text
User
 ↓
Enrollment
 ↓
Course
 ↓
Module
 ↓
Lesson
 ↓
Quiz
 ↓
Question
 ↓
Attempt
```

PostgreSQL is excellent for this kind of relational data.

And later:

```text
PostgreSQL
    +
pgvector
```

allows us to store vector embeddings for our RAG system.

So we don't need to immediately introduce:

```text
PostgreSQL
+
MongoDB
+
Separate Vector DB
```

We're keeping the architecture simpler.
