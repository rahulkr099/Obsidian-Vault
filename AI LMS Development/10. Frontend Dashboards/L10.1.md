# Lesson 10.1 — React + TypeScript Frontend Architecture

This lesson starts **Phase 10**.

Our goal is not just to convert JavaScript files to `.tsx`. We are going to design the frontend so that it can handle the full AI LMS without becoming messy.

The source project you provided already separates areas such as common components, authentication, courses, dashboards, course building, and course viewing. We'll use that organization as inspiration, but build a cleaner **React + TypeScript** architecture for our LMS.

# 2. The Main Problem With a Beginner React Project

A small project can start like this:

```text
src/
├── App.jsx
├── components/
├── pages/
└── utils/
```

At first this feels great.

But imagine our LMS eventually contains:

```text
50+ pages
100+ components
20+ API services
multiple user roles
AI features
RAG
quizzes
analytics
course builder
```

If we continue throwing files into:

```text
components/
pages/
utils/
```

we'll eventually get:

```text
components/
├── Button.tsx
├── CourseCard.tsx
├── StudentCard.tsx
├── AdminCard.tsx
├── AIChat.tsx
├── ...
```

and it becomes difficult to understand:

> "Which files belong to which feature?"

So we're going to design the architecture **before** building all the pages.

```text

             │                           │
             └─────────────┬─────────────┘
                           │
                         Hooks
                           │
                      API Services
                           │
                    State / Query Cache
                           │

                           │
```

For example:


# 5. `app/` — Application-Level Configuration

```text
app/
├── App.tsx
├── router.tsx
└── providers/
```

This folder contains things that configure the entire application.

For example:

```text
App
 │
 ├── QueryProvider
 ├── AuthProvider
 ├── Router
 └── ToastProvider
```

A simplified `App.tsx` might eventually look like:

```tsx
function App() {
  return (
    <QueryProvider>
      <AuthProvider>
        <RouterProvider router={router} />
      </AuthProvider>
    </QueryProvider>
  );
}

export default App;
```

The important idea:

> `App.tsx` should configure the application, not become the application's business-logic dumping ground.

# 10. Page vs Component

This is a very important distinction.

### Page

```text
/student/dashboard
```

is a route.

Therefore:

```tsx
StudentDashboard.tsx
```

is a page.

### Component

Inside it:

```text
LearningStats
ContinueLearning
RecentCourses
UpcomingQuiz
```

are components.

Think:

```text
URL
 ↓
Page
 ↓
Components
 ↓
UI components
```

# 12. `services/`

This is where API communication lives.

For example:

```text
services/
├── api.ts
├── auth.service.ts
├── course.service.ts
├── student.service.ts
├── instructor.service.ts
├── admin.service.ts
├── quiz.service.ts
└── ai.service.ts
```

Instead of doing this inside a component:

```tsx
axios.get("/api/v1/student/courses");
```

we do:

```tsx
studentService.getCourses();
```

Example:

```ts
export const studentService = {
  async getCourses() {
    const response = await api.get("/student/courses");

    return response.data;
  },
};
```

Then:

```tsx
const courses = await studentService.getCourses();
```

This separation becomes extremely valuable later.

# 16. `stores/`

Not every piece of state should go into global state.

We'll eventually have things such as:

```text
stores/
├── auth.store.ts
├── ui.store.ts
└── learning.store.ts
```

For example:

```text
Auth state
   ↓
currentUser
isAuthenticated
```

But we'll be careful not to put everything into a global store.

A useful rule:

```text
Server data
    ↓
TanStack Query

UI state
    ↓
local state / Zustand

Form state
    ↓
React Hook Form
```

This prevents the classic:

```text
Redux stores EVERYTHING
```

problem.

# 19. The Most Important Architecture Rule

Remember this:

```text
Pages
  ↓
Components
  ↓
Hooks
  ↓
Services
  ↓
API
```

For example:

```text
StudentDashboard
      ↓
LearningStats
      ↓
useStudentStats()
      ↓
studentService.getStats()
      ↓
GET /api/v1/student/stats
```

Not:

```text
StudentDashboard
      ↓
axios
      ↓
random endpoint
      ↓
business logic
      ↓
UI
```

That second architecture becomes difficult to maintain.

# 20. TypeScript's Role

TypeScript should flow through the entire frontend.

Imagine the backend returns:

```json
{
  "id": "course_123",
  "title": "React Fundamentals",
  "price": 499
}
```

We define:

```ts
interface Course {
  id: string;
  title: string;
  price: number;
}
```

Then:

```tsx
function CourseCard({
  course,
}: {
  course: Course;
}) {
  return (
    <article>
      <h2>{course.title}</h2>
      <p>₹{course.price}</p>
    </article>
  );
}
```

Now if you accidentally write:

```tsx
course.prcie
```

TypeScript catches it.

That's the main benefit we're looking for.

---

# 21. TypeScript + React Props

Suppose we have:

```tsx
interface CourseCardProps {
  course: Course;
  onEnroll: (courseId: string) => void;
}
```

Then:

```tsx
function CourseCard({
  course,
  onEnroll,
}: CourseCardProps) {
  return (
    <div>
      <h2>{course.title}</h2>

      <button
        onClick={() => onEnroll(course.id)}
      >
        Enroll
      </button>
    </div>
  );
}
```

Now the component contract is explicit.

---

# 22. Avoid `any`

One of our rules for Phase 10:

```tsx
❌ any
```

unless there is a genuinely unavoidable external boundary.

Instead of:

```ts
const user: any = response.data;
```

we want:

```ts
const user: User = response.data;
```

Even better, we'll eventually type our API functions so the type flows automatically.

# 🧠 Lesson 10.1 Takeaways

The most important things to remember:

```text
1. React + TypeScript is our frontend stack.

2. Pages represent routes.

3. Components represent reusable UI/features.

4. Layouts provide common page structure.

5. Services communicate with the backend.

6. Hooks contain reusable React behavior.

7. Types describe our data contracts.

8. Server state and UI state should be treated differently.

9. Don't put API/business logic directly inside UI components.

10. Organize around responsibilities/features, not random files.
```

And the architecture to keep in your head is:

```text
                 PAGE
                  ↓
             COMPONENT
                  ↓
                HOOK
                  ↓
               SERVICE
                  ↓
                 API
                  ↓
              BACKEND
                  ↓
              DATABASE
```
