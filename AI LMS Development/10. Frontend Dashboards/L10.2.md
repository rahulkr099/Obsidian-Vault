# 4. Why We Need Layouts

Imagine every dashboard page contains:

```tsx
<Sidebar />

<Navbar />

<main>
  ...
</main>
```

Then:

```text
StudentDashboard.tsx
InstructorDashboard.tsx
MyCourses.tsx
Progress.tsx
Settings.tsx
```

would all repeat the same structure.

That's bad.

Instead:

```text
DashboardLayout
       ↓
    Sidebar
       +
    Header
       +
   <Outlet />
```

The child page goes into `<Outlet />`.

Your uploaded source already uses this idea with a dashboard wrapper and `Outlet`, so we're keeping that useful pattern.

# 5. Understanding `<Outlet />`

Suppose we have:

```tsx
function DashboardLayout() {
  return (
    <div>
      <Sidebar />

      <main>
        <Outlet />
      </main>
    </div>
  );
}
```

And:

```text
/dashboard
/dashboard/profile
/dashboard/settings
```

The router decides which component appears inside:

```tsx
<Outlet />
```

So:

```text
DashboardLayout
│
├── Sidebar
├── Header
└── Outlet
      │
      ├── Dashboard
      ├── Profile
      └── Settings
```

This is one of the most important React Router concepts for this project.

# 6. Create Our First Router

Create:

```text
src/app/router.tsx
```

Basic version:

```tsx
import {
  createBrowserRouter,
} from "react-router-dom";

import Home from "../pages/public/Home";
import Courses from "../pages/public/Courses";
import Login from "../pages/auth/Login";

export const router = createBrowserRouter([
  {
    path: "/",
    element: <Home />,
  },
  {
    path: "/courses",
    element: <Courses />,
  },
  {
    path: "/login",
    element: <Login />,
  },
]);
```

Then:

```tsx
import { RouterProvider } from "react-router-dom";
import { router } from "./router";

function App() {
  return <RouterProvider router={router} />;
}

export default App;
```

Now React knows:

```text
/          → Home
/courses   → Courses
/login     → Login
```

# 12. ProtectedRoute

Create:

```text
src/components/auth/ProtectedRoute.tsx
```

Basic version:

```tsx
import { Navigate, Outlet } from "react-router-dom";

interface ProtectedRouteProps {
  isAuthenticated: boolean;
}

export default function ProtectedRoute({
  isAuthenticated,
}: ProtectedRouteProps) {
  if (!isAuthenticated) {
    return <Navigate to="/login" replace />;
  }

  return <Outlet />;
}
```

Conceptually:

```text
Request /student/dashboard
          ↓
   Is authenticated?
       /       \
     No         Yes
     ↓           ↓
 /login       Dashboard
```

---

# 13. Why `replace`?

We use:

```tsx
<Navigate
  to="/login"
  replace
/>
```

because we don't want the browser history to become:

```text
/dashboard
    ↓
/login
```

and then the user presses Back and returns to the protected page.

`replace` replaces the current history entry.

# 15. Don't Trust Local UI State for Security

Very important:

```text
ProtectedRoute
```

protects the **frontend experience**.

It is NOT the real security boundary.

A malicious user can still call:

```text
GET /api/v1/admin/users
```

directly.

Therefore:

```text
Frontend protection
       +
Backend authorization
```

are both required.

Our real security chain is:

```text
React Route Guard
       ↓
Express Authentication
       ↓
Authorization Middleware
       ↓
Service-level permission checks
```

This is especially important because our Phase 14 security work will revisit these boundaries.

# 18. RoleRoute

```tsx
import {
  Navigate,
  Outlet,
} from "react-router-dom";

import type { UserRole } from "../../types/user";

interface RoleRouteProps {
  userRole: UserRole | null;
  allowedRoles: UserRole[];
}

export default function RoleRoute({
  userRole,
  allowedRoles,
}: RoleRouteProps) {
  if (!userRole) {
    return <Navigate to="/login" replace />;
  }

  if (!allowedRoles.includes(userRole)) {
    return <Navigate to="/unauthorized" replace />;
  }

  return <Outlet />;
}
```

Now:

```text
Student
   ↓
/admin/dashboard
   ↓
RoleRoute
   ↓
❌ Not allowed
   ↓
/unauthorized
```

---

# 19. Why Have `/unauthorized`?

Because these are two different situations:

### Not authenticated

```text
"I haven't logged in."
```

→ `/login`

### Not authorized

```text
"I am logged in, but I don't have permission."
```

→ `/unauthorized`

This distinction is important.

We'll create:

```text
pages/public/Unauthorized.tsx
```

Eventually it can show:

```text
403

You don't have permission
to access this page.

[Go to Dashboard]
```

# 27. Navigation

For internal navigation, don't use:

```html
<a href="/student/dashboard">
```

Use React Router:

```tsx
import { Link } from "react-router-dom";

<Link to="/student/dashboard">
  Dashboard
</Link>
```

Why?

Because normal `<a>` navigation causes a full browser request.

React Router navigation allows the SPA to transition between pages without reloading the entire application.

# 32. Route Security Flow

Our final frontend authentication flow will look like:

```text
User opens URL
       ↓

       ↓

       ↓
Auth state loading?
    /        \
  yes         no
```

# 33. Frontend Route Protection ≠ Backend Security

This deserves another warning.

Never assume:

```tsx
<RoleRoute allowedRoles={["admin"]} />
```

means your API is secure.

A user can bypass your React UI entirely.

For example:

```bash
curl https://api.example.com/api/v1/admin/users
```

The backend must still check:

```text
Authentication
      ↓
Authorization
      ↓
Resource ownership / permissions
```

So our architecture is:

```text
                Frontend
                   │
             Route Guards
                   │
                   ↓
                 API
                   │
          Authentication
                   │
          Authorization
                   │
                   ↓
               Database
```

This is one of the most important full-stack concepts in this project.

# 36. What We Should NOT Do

### ❌ Giant App.tsx

```tsx
function App() {
  // 500 lines of routes
}
```

Avoid it.

### ❌ API calls in router

Don't do:

```tsx
router → axios → API
```

Authentication state belongs in the auth layer.

### ❌ Role logic everywhere

Don't write:

```tsx
if (user.role === "admin") ...
```

in 50 components.

Centralize route and permission logic.

### ❌ Frontend-only authorization

Never rely on React for backend security.

### ❌ One giant Dashboard component

We'll separate:

```text
Student
Instructor
Admin
```

because their responsibilities are different.
