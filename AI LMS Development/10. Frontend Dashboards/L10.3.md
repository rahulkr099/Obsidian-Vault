# 2. First: Understand Authentication vs Authorization

These two words are easy to mix up.

## Authentication

> "Who are you?"

Example:

```text
Email + Password
        ↓
Backend
        ↓
User verified
        ↓
Authenticated
```

## Authorization

> "What are you allowed to do?"

Example:

```text
User = Rahul
Role = student

/student/dashboard
      ↓
Allowed ✅

/admin/users
      ↓
Not allowed ❌
```

So:

```text
Authentication
      ↓
Identity

Authorization
      ↓
Permissions
```

Our previous lesson's:

```text
ProtectedRoute
RoleRoute
```

deal with the frontend side of this.

# 6. Authentication State

We need one central place that answers:

```text
Who is currently logged in?
```

Our state looks like:

```ts
interface AuthState {
  user: User | null;
  isAuthenticated: boolean;
  isLoading: boolean;
}
```

Conceptually:

```text
AuthState
│
├── user
├── isAuthenticated
└── isLoading
```

Example when logged out:

```ts
{
  user: null,
  isAuthenticated: false,
  isLoading: false
}
```

Logged in:

```ts
{
  user: {
    id: "123",
    name: "Rahul",
    email: "rahul@example.com",
    role: "student"
  },
  isAuthenticated: true,
  isLoading: false
}
```

During session restoration:

```ts
{
  user: null,
  isAuthenticated: false,
  isLoading: true
}
```

That last state is extremely important.

# 7. Why `isLoading` Matters

Imagine the user already has a valid session.

Browser opens:

```text
/student/dashboard
```

React initially doesn't know who the user is.

If we immediately check:

```ts
if (!user) {
  navigate("/login");
}
```

we could incorrectly redirect the user before the session check finishes.

So we need:

```text
Application starts
       ↓
Checking session
       ↓
Loading...
       ↓
Session found?
    /       \
  yes       no
   ↓         ↓
Dashboard   Login
```

Never confuse:

```text
user === null
```

with:

```text
authentication check finished
```

That's why we have:

```text
isLoading
```

# 8. Auth Service

Create:

```text
src/services/auth.service.ts
```

The service is responsible for talking to the backend.

For example:

```ts
import { api } from "./api";
import type {
  LoginInput,
  RegisterInput,
} from "../types/auth";

export const authService = {
  async login(input: LoginInput) {
    const response = await api.post(
      "/auth/login",
      input
    );

    return response.data;
  },

  async register(input: RegisterInput) {
    const response = await api.post(
      "/auth/register",
      input
    );

    return response.data;
  },

  async getCurrentUser() {
    const response = await api.get(
      "/auth/me"
    );

    return response.data;
  },

  async logout() {
    await api.post("/auth/logout");
  },
};
```

The exact endpoints should match the backend we built.

The important separation is:

```text
Component
❌ axios

Component
 ↓
authService
 ↓
axios
```

export const api = axios.create({

Don't blindly copy this into every project. It depends on how the backend stores and transports authentication credentials.

For our LMS, we'll keep the frontend authentication layer compatible with the backend's refresh/session architecture.

# 10. Authentication Tokens

Our system needs to distinguish between:

```text
Access credential
Refresh credential
```

Conceptually:

```text
Login
 ↓
Access Token
+
Refresh Token
```

The access credential is used for normal API requests.

The refresh credential is used to obtain a new access credential when the current one expires.

A safer production architecture generally avoids exposing long-lived refresh credentials to JavaScript when secure HTTP-only cookies can be used.

So our frontend should **not casually do this**:

```ts
localStorage.setItem(
  "refreshToken",
  refreshToken
);
```

That creates unnecessary exposure to JavaScript-accessible token theft.

We'll keep the token-storage decision aligned with the backend security design.

# 11. Auth Store

We need somewhere to store frontend authentication state.

We could use:

```text
Context
```

or:

```text
Zustand
```

For this LMS, we'll keep the state small.

A conceptual Zustand store could look like:

```ts
interface AuthStore {
  user: User | null;
  isLoading: boolean;

  setUser: (user: User | null) => void;
  setLoading: (value: boolean) => void;
  clearAuth: () => void;
}
```

The important point isn't the library.

The important point is:

> Authentication state should have one clear owner.

Don't have:

```text
Navbar → one user state
Dashboard → another user state
Sidebar → another user state
Profile → another user state
```

That creates synchronization problems.

# 12. `useAuth()`

Components shouldn't directly manipulate the store everywhere.

Instead:

```ts
const {
  user,
  isAuthenticated,
  isLoading,
  login,
  logout,
} = useAuth();
```

Then:

```tsx
function Navbar() {
  const { user, logout } = useAuth();

  return (
    <nav>
      <span>{user?.name}</span>

      <button onClick={logout}>
        Logout
      </button>
    </nav>
  );
}
```

This creates a clean interface for the rest of the application.

# 14. Login Form

A basic version:

```tsx
interface LoginFormProps {
  onSuccess?: () => void;
}

function LoginForm({
  onSuccess,
}: LoginFormProps) {
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");

  const {
    login,
    isLoading,
  } = useAuth();

  async function handleSubmit(
    event: React.FormEvent
  ) {
    event.preventDefault();

    await login({
      email,
      password,
    });

    onSuccess?.();
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}
        onChange={(event) =>
          setEmail(event.target.value)
        }
      />

      <input
        type="password"
        value={password}
        onChange={(event) =>
          setPassword(event.target.value)
        }
      />

      <button disabled={isLoading}>
        {isLoading ? "Logging in..." : "Login"}
      </button>
    </form>
  );
}
```

This is intentionally simple.

We'll improve the form architecture using **React Hook Form + Zod** when we build our reusable forms.

# 17. Don't Automatically Trust Registration Response

A common beginner mistake is:

```ts
const response = await register(data);

setUser(response.user);
```

without thinking about the backend's actual authentication policy.

The backend might return:

```json
{
  "message": "Account created. Please verify your email."
}
```

rather than authenticating the user.

So frontend behavior should follow the API contract.

# 19. Auth Initialization

A provider or root-level auth hook can perform:

```tsx
useEffect(() => {
  async function initializeAuth() {
    try {
      setLoading(true);

      const user =
        await authService.getCurrentUser();

      setUser(user);
    } catch {
      setUser(null);
    } finally {
      setLoading(false);
    }
  }

  initializeAuth();
}, []);
```

Conceptually:

```text
start
 ↓
loading = true
 ↓
check session
 ↓
set user
 ↓
loading = false
```

# 20. ProtectedRoute With Real Auth State

Now our previous `ProtectedRoute` becomes more realistic:

```tsx
function ProtectedRoute() {
  const {
    user,
    isLoading,
  } = useAuth();

  if (isLoading) {
    return <FullPageLoader />;
  }

  if (!user) {
    return (
      <Navigate
        to="/login"
        replace
      />
    );
  }

  return <Outlet />;
}
```

This is much better than:

```tsx
if (!user) {
  return <Navigate to="/login" />;
}
```

because it respects the session initialization phase.

# 21. RoleRoute With Real User

Our `RoleRoute` can now become:

```tsx
interface RoleRouteProps {
  allowedRoles: UserRole[];
}

function RoleRoute({
  allowedRoles,
}: RoleRouteProps) {
  const { user, isLoading } = useAuth();

  if (isLoading) {
    return <FullPageLoader />;
  }

  if (!user) {
    return (
      <Navigate
        to="/login"
        replace
      />
    );
  }

  if (!allowedRoles.includes(user.role)) {
    return (
      <Navigate
        to="/unauthorized"
        replace
      />
    );
  }

  return <Outlet />;
}
```

Now our route system is actually connected to authentication state.

# 22. Role-Based Redirect After Login

Suppose:

```text
student
```

logs in.

We want:

```text
/student/dashboard
```

Instructor:

```text
/instructor/dashboard
```

Admin:

```text
/admin/dashboard
```

Create a helper:

```ts
function getDashboardRoute(
  role: UserRole
): string {
  switch (role) {
    case "student":
      return "/student/dashboard";

    case "instructor":
      return "/instructor/dashboard";

    case "admin":
      return "/admin/dashboard";
  }
}
```

Then:

```tsx
const navigate = useNavigate();

const user = await login(credentials);

navigate(
  getDashboardRoute(user.role)
);
```

Now the login flow is role-aware.

# 24. Logout

Logout should not simply mean:

```ts
localStorage.clear();
```

It should be an actual authentication operation.

Flow:

```text
Click Logout
     ↓
authService.logout()
     ↓
Backend invalidates session/refresh credential
     ↓
Frontend clears user state
     ↓
Navigate to login/home
```

Example:

```ts
async function logout() {
  try {
    await authService.logout();
  } finally {
    clearAuth();
    navigate("/login");
  }
}
```

The `finally` is useful because the local UI should not remain logged in just because the network request failed.

---

# 25. Why Logout Should Be Server-Aware

Imagine:

```text
User clicks Logout
```

but the backend refresh session remains valid.

Then the old session could potentially still be used.

Therefore:

```text
Frontend logout
       +
Backend session invalidation
```

is the correct model.

# 26. Session Expiration

What happens when the access credential expires?

```text
React
 ↓
API request
 ↓
Backend
 ↓
401 Unauthorized
```

We don't want the user to suddenly see errors everywhere.

Our Axios layer can eventually handle:

```text
401
 ↓
Attempt refresh
 ↓
Retry original request
```

If refresh fails:

```text
Refresh failed
 ↓
Clear auth
 ↓
Redirect to login
```

Conceptually:

```text
API Request
    ↓
   401?
  /    \
No      Yes
↓        ↓
Return   Refresh
         /    \
      success  failure
        ↓        ↓
      retry    logout
```

This is an important piece of the frontend/backend authentication integration.

---

# 27. Avoid Infinite Refresh Loops

A dangerous interceptor design is:

```text
Request
 ↓
401
 ↓
Refresh
 ↓
401
 ↓
Refresh
 ↓
401
 ↓
Refresh
...
```

We must make sure the refresh request itself isn't endlessly intercepted.

We'll implement the proper Axios interceptor pattern when we build the API layer more completely.

The important lesson:

> Token refresh is a state machine, not simply "if 401, call refresh forever."

# 33. The Authentication State Machine

I want you to understand this model:

```text
                 START
                   │
                   ↓
              CHECKING
                   │
          ┌────────┴────────┐
          ↓                 ↓
    AUTHENTICATED       UNAUTHENTICATED
          │                 │
          ↓                 ↓
       APP UI             LOGIN
          │
          ↓
       EXPIRED
          │
          ↓
      REFRESH
       /    \
    success failure
      ↓       ↓
     APP     LOGIN
```

This is much easier to reason about than scattered boolean checks.

# 39. Important Security Rules

Keep these rules throughout the project:

```text
1. Never trust frontend authorization.

2. Never put long-lived secrets in localStorage casually.

3. Backend must validate authentication.

4. Backend must validate roles/permissions.

5. Handle token/session expiration.

6. Don't expose sensitive authentication errors.

7. Don't store passwords in frontend state longer than necessary.

8. Clear sensitive client-side state on logout.

9. Don't put tokens into URLs.

10. Don't log tokens/passwords.
```

And remember:

```text
React Route Guard
        ≠
Real Security
```

The real security boundary remains the backend.
