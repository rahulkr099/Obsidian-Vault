# 1. What Is the Student Dashboard?

The dashboard is the student's central workspace.

After login:

```text
Student
   ↓
/student/dashboard
```

They should immediately understand:

```text

How much have I completed?
What should I continue?
What assessments are coming?
What did I recently do?
What have I bookmarked?
```

Our dashboard should therefore be **action-oriented**, not just a collection of statistics.


# 21. Why Use a Union Type?

This:

```ts
type ActivityType =
  | "lesson_completed"
  | "lesson_started"
  | "quiz_completed"
  | "certificate_earned";
```

means TypeScript knows the only valid activity types.

Then:

```ts
if (activity.type === "quiz_completed") {
  // ...
}
```

Your editor can provide autocomplete.

This is one of the places where TypeScript becomes genuinely useful rather than simply adding types to JavaScript.

# 29. Student Dashboard API

Instead of making the dashboard send 10 separate requests:

```text

GET /student/courses
GET /student/progress
GET /student/activity
GET /student/certificates
...
```

we can have a dashboard-specific aggregation endpoint if the backend architecture supports it:

```text
GET /api/v1/student/dashboard
```

Response conceptually:

```json
{
  "stats": {},
  "continueLearning": [],
  "recentCourses": [],
  "upcomingAssessments": [],
  "recentActivity": []

```

This can make the dashboard much easier to load.

However, don't blindly create an enormous "dashboard API" that becomes a dumping ground. It should contain data specifically required by the dashboard.

# 31. Dashboard Hook

Create:

```text

```

Conceptually:

```ts
export function useStudentDashboard() {
  return useQuery({
    queryKey: ["student", "dashboard"],
    queryFn: studentService.getDashboard,
  });
}
```

This assumes TanStack Query, which we'll use for server state.

The flow becomes:

```text

       ↓

       ↓
TanStack Query
       ↓
studentService
       ↓
API
```

---

# 32. Why TanStack Query Is Useful Here

Dashboard data is **server state**.

It comes from:

```text
Backend
```

not from the browser itself.

TanStack Query gives us:

```text
Caching
Loading state
Error state
Refetching
Request deduplication
Stale data management
Mutation invalidation
```

So instead of manually writing:

```text
loading
error
data
useEffect
fetch
setState
```

for every API request, we get a consistent model.

# 40. Important: Don't Duplicate Backend Logic

Suppose backend gives:

```json
{
  "progress": 68
}
```

Don't make frontend somehow recalculate:

```text
completedLessons / totalLessons × 100
```

unless that calculation is intentionally a presentation-only calculation.

Why?

Because backend might have rules involving:

```text
video completion
lesson completion
quiz completion
required lessons
weighted content
```

The backend should own the business definition of "course progress."

The frontend should display it.

# 🧠 Lesson 10.6 Takeaways

The biggest things to remember:

```text
1. The student dashboard is an overview and action center.

2. Don't put every feature inside StudentDashboard.tsx.

3. Use small feature components.

4. Use authenticated user state from useAuth().

5. Treat dashboard data as server state.

6. Use TanStack Query for server-state fetching/caching.

7. Backend owns learning-progress business rules.

8. Frontend displays and interacts with that data.

9. Always design loading, error, empty, and success states.

10. Continue Learning should be the primary student action.

11. Keep dashboard, course player, quiz, and AI Tutor as
    separate experiences.

12. Build the UI with mock data first, then connect APIs.
```

The student experience now has a clear path:

