# 1. What Is a Course Builder?

A course builder is basically an instructor's **content management workspace**.

Instead of creating one huge form, we divide the course into logical pieces:

```text
Course Builder
│
├── Course Information
├── Course Structure
│   ├── Section 1
│   │   ├── Lesson 1
│   │   ├── Lesson 2
│   │   └── Quiz
│   │
│   └── Section 2
│       ├── Lesson 3
│       └── Lesson 4
│
├── Pricing
├── Settings
├── Preview
└── Publish
```

# 20. Video Upload

Video is one of the heavier parts of the LMS.

Don't upload a huge video directly through your React application server unless the architecture explicitly calls for it.

A better production architecture is generally:

```text
Browser
   ↓
Request upload authorization
   ↓
Backend
   ↓
Storage provider / signed upload
   ↓
Browser uploads video
   ↓
Storage
   ↓
Asset URL / ID
   ↓
Backend records metadata
```

This keeps your application server from becoming a giant file-transfer bottleneck.

# 37. Important State Architecture

The builder has **two types of state**.

### Local draft state

```text
Current title
Current description
Expanded section
Selected lesson
Unsaved changes
```

### Server state

```text
Saved course
Course ID
Published status
Server response
```

So:

```text
                 Course Builder
                       │
              ┌────────┴────────┐
              ↓                 ↓
        Local Draft         Server State
              │                 │
          useState /         TanStack
          useReducer          Query
```

For a complex builder, `useReducer` can be a very good choice.

---

# 38. Why `useReducer`?

Imagine these actions:

```text
ADD_SECTION
UPDATE_SECTION
DELETE_SECTION
ADD_LESSON
UPDATE_LESSON
DELETE_LESSON
MOVE_SECTION
MOVE_LESSON
UPDATE_COURSE
```

Using many individual `useState`s becomes messy.

A reducer gives us:

```ts
dispatch({
  type: "ADD_SECTION",
});
```

or:

```ts
dispatch({
  type: "UPDATE_LESSON",
  payload: {
    sectionId,
    lessonId,
    changes,
  },
});
```

This is a very good use case for `useReducer`.

---

# 39. Course Builder Reducer

Conceptually:

```ts
type CourseBuilderAction =
  | {
      type: "UPDATE_COURSE";
      payload: Partial<CourseDraft>;
    }
  | {
      type: "ADD_SECTION";
    }
  | {
      type: "UPDATE_SECTION";
      payload: {
        sectionId: string;
        changes: Partial<CourseSectionDraft>;
      };
    }
  | {
      type: "DELETE_SECTION";
      payload: {
        sectionId: string;
      };
    };
```

Then:

```text
UI
 ↓
dispatch(action)
 ↓
Reducer
 ↓
New CourseDraft
 ↓
UI re-renders
```

This is a much cleaner architecture for complex form builders.

Whether we use React Context or keep the state in the page/hook depends on complexity.

For this builder, a provider can become useful once multiple deeply nested components need the same draft state.

But don't introduce Context merely because it exists.

---

# 46. Provider vs Props

Without Context:

```text
CourseBuilder
 ↓
CourseCurriculum
 ↓
CourseSection
 ↓
LessonItem
```

Passing many props can become annoying.

With Context:

```text
CourseBuilderProvider
        ↓
CourseCurriculum
        ↓
CourseSection
        ↓
LessonItem
```

Any child can access:

```ts
useCourseBuilder()
```

This can be useful for a deeply nested builder.

---

# 47. Don't Put Everything in Context

Context should contain things such as:

```text
draft
selected lesson
builder actions
```

But don't put:

```text
all server data
all application state
all authentication
all UI state
```

into one giant provider.

Otherwise you'll create:

```text
AppContext
```

with 500 lines of unrelated state.

Keep contexts focused.

---

# 48. Course Builder Error Handling

Imagine:

```text
Save Draft
```

fails.

Don't lose the draft.

Show:

```text
⚠ Unable to save changes.

Your local changes are still available.

[ Retry ]
```

This is especially important for content creation.

# 🧠 Lesson 10.8 Takeaways

The most important concepts:

```text
1. Course Builder is a complex editor, not one giant form.

2. Keep one central CourseDraft state.

3. useReducer is a good fit for complex builder operations.

4. Separate course information, curriculum, lessons,
   resources, pricing, and settings.

5. Use composition:
   Course → Section → Lesson.

6. Support draft → preview → publish.

7. Track unsaved changes.

8. Eventually add autosave, but first make manual saving reliable.

9. Backend must validate publishing rules.

10. Backend owns course ownership and authorization.

11. Reuse public course components for preview where possible.

12. AI should assist instructors, not silently publish content.

13. Keep server state and local builder state separate.

14. Design the builder so drag-and-drop ordering can be added later.
```
