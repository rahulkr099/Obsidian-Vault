# 1. What Is the Course Player?

The course player is the student's dedicated learning workspace.

A typical desktop layout:

```text
┌────────────────────────────────────────────────────────────┐
│ AI LMS     React + TypeScript        Progress: 68%        │
├──────────────────────────┬─────────────────────────────────┤
│                          │                                 │
│ Course Curriculum        │                                 │
│                          │        Video / Content          │
│ Section 1                │                                 │
│ ✓ Introduction           │                                 │
│ ✓ JSX                    │                                 │
│ → Components             │                                 │
│ 🔒 Props                 │                                 │
│                          │                                 │
│ Section 2                │                                 │
│ ○ State                  │                                 │
│ ○ Hooks                  │                                 │
│                          │                                 │
│                          │                                 │
│                          ├─────────────────────────────────┤
│                          │ Lesson Title                    │

│                          │                                 │
│                          │ [ Previous ] [ Complete ] [Next]│
└──────────────────────────┴─────────────────────────────────┘
```

The source project already contains the basic idea of a learning page with a video/content area, course content navigation, and lesson progression.

We'll make the architecture much more explicit.

# 2. Course Player Route

We'll use:

```text
/learn/:courseId
```

For a specific lesson:

```text
/learn/:courseId/lesson/:lessonId
```

For example:

```text
/learn/react-typescript/lesson/react-hooks
```

This is better than keeping the selected lesson only in React state.

If the user refreshes:

```text
Browser refresh
     ↓
URL still contains lesson ID
     ↓
Course Player restores
```

---

# 3. Course Player Route Protection

This page must be protected.

The flow:

```text
User
 ↓
ProtectedRoute
 ↓
Student/authorized user
 ↓
CoursePlayer
```

But there's another important check.

Being logged in doesn't automatically mean:

> "This student can access this course."

We need:

```text
Authentication
+
Enrollment / Access Authorization
```

So the backend must verify:

```text
Current User
      ↓
Enrollment
      ↓
Course Access
```

The frontend should never rely on:

```tsx
if (user) {
  showCourse();
}
```

That is only a UI convenience.

```ts
export interface LearningCourse {
```

# 7. Why `completed` and `isLocked`?

The curriculum needs to know the student's current state.

For example:

```text
✓ Introduction
✓ JSX
→ Components
🔒 Props
○ State
```

These states are different:

```text
completed
current
locked
available
```

Don't represent everything using one property such as:

```ts
status: string;
```

Prefer explicit state where it makes the UI clearer.

# 12. Don't Load the Entire Course Content Blindly

There are two reasonable strategies.

### Strategy A — Load curriculum once

```text
Course Player
 ↓
Course structure
 ↓
All lesson metadata
```

Then load actual lesson content separately.

This is often a good approach.

### Strategy B — Load everything

```text
Course
 ↓
All lessons
 ↓
All content
```

This can become inefficient for large courses.

I recommend:

```text
Course metadata/curriculum
        ↓
Lesson metadata
        ↓
Current lesson content
```

This gives us a good balance.

# 15. Video Progress

This is very important for the LMS.

Suppose the student watches:

```text
18:20 video
```

and reaches:

```text
12:34
```

We should remember it.

Then:

```text
Student returns later
        ↓
Video resumes around 12:34
```

This means the frontend needs to periodically report playback progress.

---

# 16. Don't Send an API Request Every Second

Bad:

```text
0:01 → API
0:02 → API
0:03 → API
...
```

That's terrible.

Instead:

```text
Video playback
     ↓
Track locally
     ↓
Throttle/debounce
     ↓
Send progress periodically
```

For example:

```text
Every 10–30 seconds
```

or at meaningful events:

```text
Pause
Seek
Video ended
Lesson exited
```

The exact interval should be chosen based on the backend/storage design.

# 42. Multiple Queries vs One Query

We could request:

```text
Course
Lesson
Progress
```

separately.

Or backend could provide:

```text
GET /learning/courses/:courseId/lessons/:lessonId
```

with:

```json
{
  "course": {},
  "lesson": {},
  "progress": {},
  "navigation": {}
}
```

Either can work.

For the course player, an aggregated response can sometimes make sense because these pieces are required to render the same screen.

But don't make one massive endpoint that returns every course lesson's entire content.

# 49. Error States

Course player needs more specific errors than a normal page.

### Course inaccessible

```text
You don't have access to this course.
```

### Lesson not found

```text
Lesson not found.
```

### Video unavailable

```text
Unable to load this video.

[ Try Again ]
```

### Progress update failed

```text
Progress could not be saved.
We'll retry automatically.
```

Don't make a tiny progress-saving failure destroy the entire learning experience.

---


This is especially useful for learners with unstable connections.

But this is an advanced improvement, not something you need to fully implement now.

# 🧠 Lesson 10.9 Takeaways

Remember these principles:

```text
1. Course Player is the actual learning environment.

2. The URL should identify the current course and lesson.

3. Authentication and course enrollment are separate checks.

4. Backend owns access control and completion rules.

5. Keep curriculum navigation separate from lesson content.

6. Video, article, and quiz lessons should use separate viewers.

7. Track video progress efficiently — never send a request every second.

8. Progress, bookmarks, notes, and completion should be server-backed.

9. Use loading, error, locked, completed, and empty states.

10. Reuse course/curriculum components from public pages where appropriate.

11. Course Player should connect naturally to the Assessment system.

12. Course Player should provide contextual entry into the AI Tutor.

13. Keep server state separate from UI state.

14. Build with mock data first, then connect APIs.

15. Make "Continue Learning" fast and obvious.
```
