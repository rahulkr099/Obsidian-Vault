# Lesson 11.10 — Retry Strategies

This is **Lesson 11.10 of Phase 11**.

So far, we have:

```text
11.5 → Job Queues
11.6 → Background Workers
11.7 → AI Generation Jobs
11.8 → Email Jobs
11.9 → Notification Jobs
11.10 → Retry Strategies  ← Today
11.11 → Job Monitoring
11.12 → Idempotency
```

The problem we're solving today is simple:

> **What should happen when a background job fails?**

A production system should not immediately give up because an AI provider, email provider, network, or temporary database problem failed once.

---

# 1. Why Do Jobs Fail?

Background jobs depend on many things:

```text
Worker
  ↓
Redis
  ↓
PostgreSQL
  ↓
AI Provider
  ↓
Email Provider
  ↓
Network
```

Any of them can temporarily fail.

For example:

```text
AI Worker
   ↓
OpenAI/API provider
   ↓
❌ Timeout
```

If we simply mark the job as permanently failed:

```text
Job
 ↓
Error
 ↓
Failed forever
```

we may be throwing away work that could have succeeded a few seconds later.

---

# 2. Retry Means "Try Again"

A retry is simply:

```text
Job
 ↓
Attempt 1
 ↓
Failure
 ↓
Attempt 2
 ↓
Failure
 ↓
Attempt 3
 ↓
Success
```

For example:

```text
AI generation
Attempt 1 → timeout ❌
Attempt 2 → timeout ❌
Attempt 3 → success ✅
```

This is extremely useful for temporary failures.

---

# 3. But Don't Retry Everything

This is the most important lesson.

Some errors are temporary:

```text
Network timeout
Provider temporarily unavailable
HTTP 429
Temporary database connection failure
```

These may be retryable.

Other errors are permanent:

```text
Invalid email address
Course doesn't exist
Unauthorized user
Invalid AI output
Malformed job data
```

Retrying these 10 times doesn't fix anything.

For example:

```text
Course doesn't exist
      ↓
Retry
      ↓
Course doesn't exist
      ↓
Retry
      ↓
Course doesn't exist
```

That's pointless.

So:

> **Retry transient failures, not permanent failures.**

---

# 4. Two Categories of Errors

Think of errors as:

```text
                    Error
                      │
              ┌───────┴───────┐
              ↓               ↓
          Transient        Permanent
              │               │
              ↓               ↓
           Retry           Don't retry
```

### Transient

Something might work later.

### Permanent

Trying again with the same input won't solve the problem.

---

# 5. Examples for Your AI LMS

### AI Generation

```text
Provider timeout
→ retry

HTTP 429
→ retry

Provider 503
→ retry
```

But:

```text
Course not found
→ don't retry

Invalid job data
→ don't retry

User not authorized
→ don't retry
```

---

# 6. Email Examples

Retry:

```text
Provider timeout
Provider temporarily unavailable
HTTP 429
HTTP 500

```

Don't blindly retry:

```text
Invalid email address
Permanent rejection
Malformed request
```

---

# 7. Notification Examples

Retry:

```text
Temporary database connection problem
Redis/network issue
```

Probably don't retry:

```text
Invalid user ID
Invalid notification type
Malformed job payload
```

---

# 8. BullMQ Attempts

BullMQ lets you configure how many attempts a job can have.

For example:

```ts
await emailQueue.add(
  "verification-email",
  {
    userId,
    verificationId,
  },
  {
    attempts: 3,
  }
);
```

That means conceptually:

```text
Attempt 1
Attempt 2
Attempt 3
```

If all fail:

```text
Job → Failed
```

---

# 9. Why Have a Maximum?

Never retry forever.

Imagine:

```text
attempt 1
attempt 2
attempt 3
...
attempt 999999
```

You could create:

```text
Infinite API calls
Infinite cost
Infinite queue processing
Provider abuse
Database load
```

Instead:

```text
attempts: 3
```

or:

```text
attempts: 5
```

depending on the job.

---

# 10. Retry Without Delay

Imagine:

```text
Attempt 1 → failure
Attempt 2 → immediately
Attempt 3 → immediately
```

This is usually not ideal.

Suppose the AI provider is temporarily down.

You would create:

```text
Request
 ↓
Failure
 ↓
Immediately retry
 ↓
Failure
 ↓
Immediately retry
```

You may make the problem worse.

Instead, use **backoff**.

---

# 11. What Is Backoff?

Backoff means:

> **Wait before trying again.**

For example:

```text
Attempt 1
   ↓
failure
   ↓
wait 1 second
   ↓
Attempt 2
   ↓
failure
   ↓
wait 2 seconds
   ↓
Attempt 3
```

This gives the external system time to recover.

---

# 12. Exponential Backoff

A common strategy is:

```text
1s
2s
4s
8s
16s
```

This is called **exponential backoff**.

Conceptually:

```text
delay = base × 2^(attempt - 1)
```

For example, with base `1000ms`:

```text
Attempt 1 → 1s
Attempt 2 → 2s
Attempt 3 → 4s
Attempt 4 → 8s
```

This is widely used in distributed systems.

---

# 13. BullMQ Backoff

You can configure a backoff strategy.

For example:

```ts
await emailQueue.add(
  "verification-email",
  data,
  {
    attempts: 3,
    backoff: {
      type: "exponential",
      delay: 1000,
    },
  }
);
```

Conceptually:

```text
Maximum attempts = 3
Initial delay = 1 second
Backoff = exponential
```

So a temporary failure gets another chance without immediately hammering the provider.

---

# 14. Fixed Backoff

You can also use a fixed delay.

For example:

```text
Attempt 1
 ↓
wait 5 seconds
 ↓
Attempt 2
 ↓
wait 5 seconds
 ↓
Attempt 3
```

Conceptually:

```ts
backoff: {
  type: "fixed",
  delay: 5000,
}
```

Fixed backoff is useful when you want predictable spacing.

---

# 15. Exponential vs Fixed

### Fixed

```text
5s
5s
5s
5s
```

Simple and predictable.

### Exponential

```text
1s
2s
4s
8s
```

Better when a service may need increasing recovery time.

For your AI/Email workloads, exponential backoff will often be a useful default for transient external-service failures.

---

# 16. Add Jitter

Imagine you have:

```text
10,000 failed jobs
```

and all of them retry exactly after:

```text
10 seconds
```

Then at exactly 10 seconds:

```text
10,000 requests
       ↓
Provider
       ↓
🔥
```

This can create a **thundering herd**.

A common solution is **jitter**:

```text
Retry around 10 seconds
but with some randomness
```

For example:

```text
Job A → 9.4s
Job B → 10.2s
Job C → 11.1s
Job D → 9.8s
```

Now the load is spread out.

---

# 17. Why Jitter Matters for Your LMS

Imagine your AI provider has a temporary outage.

You have:

```text
5,000 AI jobs
```

They all fail around the same time.

Without jitter:

```text
Provider recovers
      ↓
5,000 retries
      ↓
Provider overloaded again
      ↓
Failures
```

With backoff + jitter:

```text
Provider recovers
      ↓
Retries spread over time
      ↓
More stable recovery
```

This is an important production concept.

---

# 18. Retry Strategy for AI Jobs

A reasonable conceptual strategy might be:

```text
AI generation
├── attempts: 3
├── exponential backoff
└── jitter
```

Possible flow:

```text
Attempt 1
   ↓
timeout
   ↓
wait
   ↓
Attempt 2
   ↓
429
   ↓
wait longer
   ↓
Attempt 3
   ↓
success
```

---

# 19. But What About HTTP 429?

HTTP `429` means:

```text
Too Many Requests
```

This is a classic retry candidate.

However, if the provider sends a `Retry-After` value, that can be more useful than blindly applying your own delay.

Conceptually:

```text
Provider
 ↓
429
 ↓
Retry-After: 10s
 ↓
Wait
 ↓
Retry
```

Your provider abstraction should ideally preserve useful rate-limit information.

---

# 20. Retry-After

Suppose:

```text
AI provider → 429
Retry-After → 20 seconds
```

Don't necessarily do:

```text
retry after 1 second
```

Instead:

```text
wait approximately 20 seconds
```

This respects the provider's guidance.

The exact implementation depends on the SDK/provider you're using.

---

# 21. Permanent AI Failure

Suppose your worker receives:

```text
courseId = "does-not-exist"
```

Worker:

```text
Fetch course
 ↓
Not found
```

Don't do:

```text
retry
retry
retry
```

because the course won't magically appear because you retried.

Instead:

```text
Job
 ↓
Permanent error
 ↓
Failed
```

And update the LMS generation record:

```text
status = failed
```

---

# 22. Validation Errors Should Usually Not Retry

Suppose AI returns:

```json
{
  "questions": "invalid"
}
```

Your schema validation fails:

```text
Zod
 ↓
❌ invalid structure
```

Retrying the exact same output doesn't help.

However, there's a subtle point:

If your worker can **regenerate** the AI output with a modified prompt, that is a different operation from blindly retrying the failed job.

For example:

```text
Invalid AI output
 ↓
Regeneration strategy
 ↓
New AI request
```

That should be an explicit AI-generation strategy, not an accidental infinite retry loop.

---

# 23. Retry vs Regeneration

This distinction is useful.

### Retry

```text
Same operation again
```

Example:

```text
LLM request timed out
→ send the same logical request again
```

### Regeneration

```text
Generate a new AI response
```

Example:

```text
AI returned invalid quiz structure
→ modify prompt / ask model again
```

Both consume AI resources.

Therefore, put limits on both.

---

# 24. Email Retry Strategy

For email:

```text
Provider timeout
       ↓
Retry
```

Potentially:

```text
attempts = 3
backoff = exponential
```

But:

```text
Invalid recipient
       ↓
Don't keep retrying
```

Otherwise you waste resources on an email address that will never work.

---

# 25. Notification Retry Strategy

For notification creation:

```text
PostgreSQL connection temporarily fails
       ↓
Retry
```

But:

```text
Unknown notification type
       ↓
Don't retry
```

This is why the worker needs to distinguish error categories.

---

# 26. Create Typed Errors

Your backend already has an `AppError` concept.

You can build more specific categories.

For example:

```ts
class RetryableError extends Error {
  retryable = true;
}
```

And:

```ts
class NonRetryableError extends Error {
  retryable = false;
}
```

Then:

```ts
throw new RetryableError(
  "AI provider temporarily unavailable"
);
```

versus:

```ts
throw new NonRetryableError(
  "Course not found"
);
```

This makes your retry policy explicit.

---

# 27. Better Error Classification

You could eventually have:

```ts
type ErrorCategory =
  | "TRANSIENT"
  | "PERMANENT"
  | "RATE_LIMITED"
  | "VALIDATION"
  | "AUTHORIZATION";
```

Then:

```text
TRANSIENT
→ retry

RATE_LIMITED
→ retry after delay

PERMANENT
→ don't retry

VALIDATION
→ don't retry

AUTHORIZATION
→ don't retry
```

This is much better than:

```text
if (error) retry
```

---

# 28. Don't Retry Authorization Errors

Imagine:

```text
Worker
 ↓
User not authorized
```

Retrying:

```text
1 second later
 ↓
same user
 ↓
same authorization
 ↓
failure
```

doesn't make sense.

Authorization should normally be resolved before creating the job anyway.

That's another reason to perform authorization in the API before queueing.

---

# 29. Don't Retry Invalid Job Data

Suppose the job contains:

```json
{
  "courseId": null
}
```

The worker should detect this immediately.

```text
Job data invalid
 ↓
Permanent failure
```

not:

```text
retry 5 times
```

This also indicates a bug in your producer.

---

# 30. Queue-Level Retry vs Application-Level Retry

This distinction is important.

### Queue-level retry

BullMQ retries the job:

```text
Job
 ↓
failure
 ↓
BullMQ
 ↓
try again
```

### Application-level retry

Your code deliberately performs another operation:

```ts
for (...) {
  try {
    await callProvider();
  }
}
```

Don't casually combine both.

You could accidentally create:

```text
Application retry × Queue retry
```

For example:

```text
Queue attempts = 3
Application retries = 3
```

Potentially:

```text
3 × 3 = 9 provider calls
```

That's easy to overlook.

---

# 31. Keep Retry Ownership Clear

For your architecture, I'd recommend:

```text
Worker
 ↓
Call provider once
 ↓
Error
 ↓
Throw
 ↓
BullMQ retry policy
```

rather than having every handler implement its own retry loop.

Then special cases can be handled explicitly when necessary.

---

# 32. Retry Configuration

You can centralize defaults.

For example:

```ts
export const retryDefaults = {
  attempts: 3,

  backoff: {
    type: "exponential",
    delay: 1000,
  },
};
```

Then:

```ts
await emailQueue.add(
  "verification-email",
  data,
  retryDefaults
);
```

This prevents every developer from inventing different retry policies.

---

# 33. But Different Jobs Need Different Policies

Don't force one strategy everywhere.

For example:

```text
AI generation
→ 3 attempts

Email
→ 5 attempts

Notification
→ 3 attempts
```

Maybe:

```text
Security email
→ higher priority

Marketing email
→ lower priority
```

The correct values depend on your system.

# 35. Failed Jobs

After all attempts are exhausted:

```text
Job
 ↓
Attempt 1 ❌
 ↓
Attempt 2 ❌
 ↓
Attempt 3 ❌
 ↓
FAILED
```

At this point, don't just forget about it.

Later, Lesson 11.11 will cover:

```text
Failed jobs
 ↓
Monitoring
 ↓
Metrics
 ↓
Alerts
 ↓
Investigation
```

---

# 36. Dead-Letter Thinking

A failed job that has exhausted its retries can be considered a candidate for a **dead-letter** workflow.

Conceptually:

```text
Main Queue
    ↓
Job
    ↓
Retries exhausted
    ↓
Failed / Dead-letter storage
```

This allows developers/operators to investigate and potentially replay jobs.

BullMQ has its own failed-job handling mechanisms; you don't necessarily need to build a separate queue called `dead-letter` immediately.

The important concept is:

> **Don't lose permanently failed jobs without visibility.**

---

# 37. Job Retention

You also need to think about how long completed and failed jobs remain available.

If you process:

```text
1 million jobs/day
```

and keep every job forever:

```text
Redis
 ↓
Huge amount of historical job data
```

That's unnecessary.

You can configure retention for completed/failed jobs.

Conceptually:

```ts
removeOnComplete: true
```

or retain a limited number.

For debugging, you may want to retain some failed jobs.

For production, choose retention based on your operational needs.

---

# 38. Retry and Cost

This is especially important for AI jobs.

Suppose one AI request costs:

```text
₹1
```

and you have:

```text
10,000 jobs
```

If every job retries twice:

```text
10,000 × 3 attempts
= 30,000 AI calls
```

Potentially:

```text
₹30,000
```

instead of:

```text
₹10,000
```

So retry policy isn't just a reliability feature.

It's also a **cost-control feature**.

# 48. Don't Catch and Hide Errors

Bad:

```ts
async (job) => {
  try {
    await processJob(job);
  } catch (error) {
    console.error(error);
  }
}
```

Why?

Because the processor resolves successfully.

BullMQ may interpret:

```text
Promise resolved
 ↓
Job completed
```

even though your operation failed.

Better:

```ts
async (job) => {
  try {
    return await processJob(job);
  } catch (error) {
    console.error(error);
    throw error;
  }
}
```

Now:

```text
throw
 ↓
job failed
 ↓
retry policy
```

# 49. One Important Warning: Retries Can Create Side Effects

Imagine:

```text
Worker
 ↓
Create quiz
 ↓
Send email
 ↓
Crash
```

The job retries:

```text
Create quiz again
 ↓
Duplicate quiz
```

or:

```text
Send email again
 ↓
Duplicate email
```

This is exactly why retry strategies and idempotency are connected.

Retries make your system more reliable, but they can also repeat side effects.

That's why the next lesson after monitoring is:

```text
11.12 — Idempotency
```

---

# 50. Retry vs Idempotency

Think:

```text
Retry
→ "Do the operation again."

Idempotency
→ "Doing it again won't create an unwanted duplicate."
```

Example:

```text
Job
 ↓
Create notification
 ↓
Crash
 ↓
Retry
 ↓
Create notification
```

Without idempotency:

```text
2 notifications ❌
```

With idempotency:

```text
1 notification ✅
```

We'll solve this properly in 11.12.

# 🧠 Interview Questions

### What is retry?

Retry means attempting a failed job again.

### Why use backoff?

To avoid immediately sending repeated requests to a service that may be temporarily unavailable.

### What is exponential backoff?

Increasing the delay between retries:

```text
1s
2s
4s
8s
```

### Why use jitter?

To spread retries over time and avoid many jobs retrying simultaneously.

### Should every error be retried?

No. Only errors that are likely to be temporary should generally be retried.

### What is HTTP 429?

It indicates that the client has sent too many requests. It is often retryable, preferably respecting a provider's `Retry-After` guidance.

### Why limit attempts?

To prevent infinite retries, resource exhaustion, provider overload, and unexpected costs.

### What is the danger of retries?

They can repeat side effects such as:

```text
duplicate emails
duplicate notifications
duplicate database records
```

which is why idempotency is important.

```text
           Backoff        Failed
              │
              ↓
           Retry
              │
              ↓
          ATTEMPT 2
```

And the core rule:

> **Retry transient failures, not permanent failures.**

For your AI LMS specifically:

```text
AI timeout       → retry
AI 429           → retry/backoff
AI 503           → retry
Email timeout    → retry
DB temporary     → retry

Course missing   → don't retry
Invalid payload  → don't retry
Unauthorized     → don't retry
Invalid AI data  → usually don't blindly retry
```
