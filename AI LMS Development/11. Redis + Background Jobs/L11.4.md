# Lesson 11.4 — Redis Rate Limiting

The Phase 11 roadmap defines **11.4 as Redis Rate Limiting**, after Redis fundamentals, caching, and temporary data.

You've already learned basic rate limiting in the backend foundation. Now we're going to understand **why Redis makes rate limiting work properly when your application has multiple API servers**.

---

## 1. What is Rate Limiting?

Rate limiting means:

> **Restricting how many requests a client can make within a certain amount of time.**

For example:

```text
Login API

5 requests / minute
```

A user can do:

```text
Request 1 ✅
Request 2 ✅
Request 3 ✅
Request 4 ✅
Request 5 ✅
Request 6 ❌
```

This protects your application from:

- brute-force attacks
    
- credential stuffing
    
- API abuse
    
- accidental request floods
    
- excessive AI API usage
    
- denial-of-service style traffic
    

---

# 2. Why Do We Need Redis for Rate Limiting?

You may already know something like:

```ts
express-rate-limit
```

which can keep counters in application memory.

For example:

```text
API Server
   ↓
Memory
   ↓
request counter
```

That works reasonably well for a **single server**.

But imagine production:

```text
              Load Balancer
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
    Server A   Server B   Server C
```

Each server has its own memory.

Suppose the limit is:

```text
5 requests / minute
```

The attacker sends:

```text
Server A → 5 requests
Server B → 5 requests
Server C → 5 requests
```

The application may effectively allow:

```text
15 requests
```

instead of:

```text
5 requests
```

because the counters aren't shared.

---

# 3. Redis Solves the Shared Counter Problem

Instead:

```text
              Load Balancer
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
    Server A    Server B    Server C
        │          │          │
        └──────────┼──────────┘
                   ↓
                 Redis
                   │
                   ↓
             Shared Counter
```

Now all servers use the same counter.

For example:

```text
rate-limit:login:user:123
```

or:

```text
rate-limit:login:ip:192.168.x.x
```

The counter is centralized.

---

# 4. Basic Redis Counter

Redis has an extremely useful command:

```redis
INCR key
```

Example:

```redis
INCR rate-limit:test
```

First request:

```text
1
```

Second:

```text
2
```

Third:

```text
3
```

and so on.

So Redis can act as our request counter.

---

# 5. Adding TTL

A counter without expiration isn't useful for normal time-window rate limiting.

We want:

```text
5 requests
within
60 seconds
```

So conceptually:

```text
Request
   ↓
INCR counter
   ↓
Set TTL = 60 seconds
```

Example:

```redis
INCR rate-limit:login:user:123
EXPIRE rate-limit:login:user:123 60
```

Now:

```text
rate-limit:login:user:123
        ↓
       1
        ↓
      TTL 60s
```

After 60 seconds:

```text
key disappears
```

and the user gets a fresh window.

---

# 6. The Basic Algorithm

Let's say:

```text
Limit = 5 requests
Window = 60 seconds
```

For every request:

```text
1. Identify client
2. Build Redis key
3. Increment counter
4. Check count
5. Reject if limit exceeded
6. Set expiration
```

Conceptually:

```text
Request
   ↓
Identify client
   ↓
Redis INCR
   ↓
count
   ↓
count > 5 ?
 ┌─────┴─────┐
 No          Yes
 ↓            ↓
Allow       Reject
```

---

# 7. Identifying the Client

This is one of the most important design decisions.

You need to decide:

> **What exactly are we limiting?**

Possible identifiers:

```text
IP address
User ID
API key
Session
Endpoint + IP
Endpoint + User ID
```

For a login endpoint, you might consider:

```text
IP-based
```

and possibly:

```text
Account-based
```

For an authenticated AI endpoint:

```text
userId
```

is usually much more useful than only IP.

# 8. Example: Login Rate Limit

Suppose:

```http
POST /api/v1/auth/login
```

Limit:

```text
5 attempts / minute
```

Redis key:

```text
rate-limit:login:ip:192.168.1.10
```

Flow:

```text
Login request
     ↓
Find IP
     ↓
Redis INCR
     ↓
Count = 3
     ↓
3 <= 5
     ↓
Allow
```

Sixth request:

```text
Count = 6
     ↓
6 > 5
     ↓
Reject
```

# 9. What Response Should We Return?

Usually:

```http
429 Too Many Requests
```

This HTTP status means the client has sent too many requests within a given time.

Example:

```json
{
  "success": false,
  "message": "Too many requests. Please try again later."
}
```

This fits nicely with the standardized API response architecture you built earlier.

---

# 10. Returning Retry Information

It is useful to tell the client when they can try again.

For example:

```http
Retry-After: 42
```

Meaning:

```text
Try again after approximately 42 seconds.
```

Your API can therefore communicate:

```text
429 Too Many Requests
Retry-After: 42
```

This is better than simply saying:

```text
"Blocked."
```

---

# 11. Different Endpoints Need Different Limits

Don't use one global limit for everything.

For example:

```text
/login
5 / minute
```

while:

```text
/course
100 / minute
```

and:

```text
/ai/chat
20 / minute
```

and:

```text
/ai/generate-quiz
5 / minute
```

This is especially important in your AI LMS.

Why?

Because an AI request may cost money.

# 12. AI Rate Limiting

Imagine a malicious student sends:

```text
POST /api/v1/ai/chat
```

10,000 times.

Without protection:

```text
10,000 requests
      ↓
LLM API
      ↓
💰 huge API bill
```

With Redis rate limiting:

```text
10,000 requests
      ↓

      ↓

```

This protects:

```text

+

+
```

# 13. Rate Limiting vs Caching

Don't confuse these.

### Caching

Answers:

> Can we avoid doing the same expensive work again?

```text
Request
 ↓
Redis
 ↓
Cached result
```

### Rate limiting

Answers:

> How many requests is this client allowed to make?

```text
Request
 ↓
Redis counter
 ↓
Allowed?
```

So:

```text
Caching
→ optimize performance

Rate limiting
→ control traffic
```

Redis happens to be useful for both.

---

# 14. Fixed Window Rate Limiting

The simple approach we've discussed is called a **fixed window**.

Example:

```text
12:00:00 → 12:01:00
```

Limit:

```text
5 requests
```

At:

```text
12:00:00
```

the counter starts.

At:

```text
12:01:00
```

it expires.

Then a new window begins.

Conceptually:

```text
12:00 ─────────── 12:01
      max 5 requests

12:01 ─────────── 12:02
      max 5 requests
```

It's easy to implement, but it has a weakness.

---

# 15. Fixed Window Boundary Problem

Suppose:

```text
Limit = 5 / minute
```

User sends:

```text
12:00:58
→ 5 requests
```

Then:

```text
12:01:01
→ 5 more requests
```

The user made:

```text
10 requests
```

within about:

```text
3 seconds
```

That's possible because the requests crossed the window boundary.

This is called a **boundary burst**.

For many basic APIs, fixed windows are still acceptable.

But more advanced systems can use:

```text
Sliding window
Token bucket
Leaky bucket
```

We'll focus on the concepts you actually need rather than implementing every algorithm.

---

# 16. Atomic Operations Matter

This is extremely important.

Imagine two requests arrive at exactly the same time:

```text
Request A → read count
Request B → read count
```

If both read:

```text
4
```

then both might think:

```text
4 < 5
```

and both allow themselves.

This creates a race condition.

Redis provides atomic operations such as:

```redis
INCR
```

which helps with this.

Instead of:

```text
GET
calculate
SET
```

use atomic Redis operations wherever possible.

---

# 17. Why GET + SET Is Dangerous

Avoid:

```text
GET counter
↓
counter + 1
↓
SET counter
```

under concurrent traffic.

Two requests can interfere with each other.

Prefer:

```redis
INCR counter
```

because Redis handles the increment atomically.

This is an important backend engineering concept.

---

# 18. Setting TTL Correctly

Here's a subtle issue.

Suppose every request does:

```redis
INCR rate-limit:user:123
EXPIRE rate-limit:user:123 60
```

Then the expiration may keep getting pushed forward.

For example:

```text
Request 1
TTL = 60

Request 2
TTL = 60 again

Request 3
TTL = 60 again
```

The window effectively becomes a rolling expiration.

For a fixed-window implementation, you generally want to set the expiration **when the counter is first created**, not reset it on every request.

Conceptually:

```text
INCR
 ↓
Was this the first request?
 ↓
Yes → EXPIRE 60
No  → don't reset TTL
```

This small detail matters.

---

# 19. Simple TypeScript Example

A conceptual implementation:

```ts
async function checkRateLimit(
  key: string,
  limit: number,
  windowSeconds: number
) {
  const count = await redis.incr(key);

  if (count === 1) {
    await redis.expire(
      key,
      windowSeconds
    );
  }

  const ttl = await redis.ttl(key);

  return {
    allowed: count <= limit,
    count,
    remaining: Math.max(
      0,
      limit - count
    ),
    retryAfter: ttl,
  };
}
```

Then:

```ts
const result = await checkRateLimit(
  `rate-limit:login:ip:${ip}`,
  5,
  60
);
```

If:

```text
count = 3
```

we get roughly:

```json
{
  "allowed": true,
  "count": 3,
  "remaining": 2
}
```

If:

```text
count = 6
```

we get:

```json
{
  "allowed": false,
  "count": 6,
  "remaining": 0
}
```

# 20. Middleware Architecture

Don't put this logic directly inside every controller.

Bad:

```text
Login Controller
   ↓
Redis rate limiting
   ↓
Authentication logic
   ↓
Database
```

Better:

```text
Request
   ↓
Rate Limit Middleware
   ↓
Authentication Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
```

For example:

```ts
router.post(
  "/login",
  loginRateLimiter,
  authController.login
);
```

Now the controller doesn't need to know anything about rate limiting.

That's consistent with the **thin-controller architecture** you've been following.

# 22. IP-Based vs User-Based Limits

Let's compare.

### IP-based

```text
rate-limit:ai:ip:192.168.1.10
```

Good for:

```text
Unauthenticated endpoints
Login
Registration
Password reset
```

But it has problems.

Imagine:

```text
College Wi-Fi
     ↓
500 students
     ↓
same public IP
```

If you aggressively limit by IP:

```text
Student A
Student B
Student C
...
```

they may all share the same limit.

### User-based

```text
rate-limit:ai:user:123
```

Better for:

```text
Authenticated AI APIs
Course operations
User-specific expensive operations
```

Best systems often combine multiple controls.

# 24. Rate Limiting Expensive AI Operations

Not every AI operation should have the same limit.

For example:

### AI chat

```text
20 requests/minute
```

### Quiz generation

```text
5 requests/10 minutes
```

### Course summarization

```text
3 requests/10 minutes
```

Why?

Because their cost may differ.

For example:

```text
AI chat
→ relatively small request

Generate full course quiz
→ potentially large LLM request
```

So rate limits should reflect **resource cost**, not just endpoint popularity.

# 25. Rate Limiting and User Quotas

There's another concept that is related but different.

### Rate limit

Controls:

```text
How fast can you make requests?
```

Example:

```text
20 requests/minute
```

### Usage quota

Controls:

```text
How much can you use over a larger period?
```

Example:

```text
100 AI generations/day
```

You might eventually have:

```text
Rate limit:
20/minute

Daily quota:
100/day
```

Redis can help track both.

However, your permanent usage/billing records may belong in PostgreSQL.

# 26. Rate Limiting and Authentication

Rate limiting should happen at the right stage.

For login:

```text
Request
 ↓
Rate limit
 ↓
Validate credentials
```

You don't want an attacker to repeatedly hammer password verification.

For authenticated AI requests:

```text
Request
 ↓
Authenticate user
 ↓
Rate limit user
 ↓
AI service
```

Because you need:

```text
userId
```

to build:

```text
rate-limit:ai:user:123
```

So the placement depends on what identity information the limiter needs.

# 27. Redis Key Structure

Good keys:

```text
rate-limit:login:ip:192.168.1.10
rate-limit:ai:user:123
rate-limit:quiz-generation:user:123
rate-limit:password-reset:ip:192.168.1.10
```

The pattern:

```text
rate-limit:<resource>:<identity-type>:<identity>
```

makes debugging easier.

---

# 28. Don't Trust Client-Supplied Identity

Never do something like:

```http
X-User-Id: 123
```

and blindly use that for rate limiting.

A malicious client could send:

```http
X-User-Id: 999
```

Use identity established by your server-side authentication system.

For example:

```text
JWT
 ↓
Authentication middleware
 ↓
req.user.userId
```

Then:

```ts
const userId = req.user.userId;
```

That's the trusted identity.

# 29. Handling Redis Failure

This is an important production decision.

Suppose:

```text
API
 ↓
Redis ❌
```

What should happen?

For a cache:

```text
Redis failure
 ↓
Maybe fallback
```

For a security-sensitive rate limiter:

```text
Redis failure
 ↓
Should we allow?
Should we reject?
```

There is no universal answer.

For a login endpoint, you may choose to **fail closed** for strict protection:

```text
Cannot verify rate limit
        ↓
Reject temporarily
```

Or for less sensitive endpoints, you might choose **fail open**:

```text
Redis unavailable
        ↓
Allow request
```

The correct choice depends on the endpoint and threat model.

This is exactly why security engineering isn't simply "add middleware."

# 30. Rate Limit Headers

A useful API can return headers such as:

```http
X-RateLimit-Limit: 20
X-RateLimit-Remaining: 17
X-RateLimit-Reset: 1723636800
```

Then the client knows:

```text
Limit = 20
Remaining = 17
Reset = ...
```

When exceeded:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 42
```

This makes your API easier to consume.

# 🧠 Interview Questions

### What problem does Redis solve for distributed rate limiting?

It provides a **shared counter/state store** that multiple API instances can access.

### Why is in-memory rate limiting problematic with multiple servers?

Each server maintains its own counter, so the rate limit isn't globally shared.

### Why use `INCR` instead of `GET` + `SET`?

`INCR` is atomic, which helps avoid race conditions when concurrent requests update the same counter.

### What status code should rate-limited requests receive?

```text
429 Too Many Requests
```

### What is a fixed-window limiter?

A limiter that allows a fixed number of requests during a defined time window, such as:

```text
5 requests / 60 seconds
```

### What is the boundary problem?

A client can potentially make bursts at the end of one window and the beginning of another, exceeding the intended rate over a short period.

### Should every endpoint have the same rate limit?

No. Limits should reflect the endpoint's sensitivity, expected traffic, and resource cost.
