# Lesson 11.6 — Background Workers

According to your Phase 11 roadmap, **11.6 is Background Workers**, immediately after Job Queues.

In **11.5**, we created the pipeline:

```text
API
 ↓
Queue
 ↓
Job waiting
```

But nothing was actually processing the job.

Today we add the missing piece:

```text
API
 ↓
Queue
 ↓
Worker
 ↓
Job Handler
 ↓
Actual Work
```

This is one of the most important backend concepts in the whole LMS.

---

# 1. What is a Background Worker?

A **background worker** is a separate process that continuously waits for jobs and processes them.

Think of it like a worker at a restaurant:

```text
Customer
   ↓
Order
   ↓
Order Queue
   ↓
Kitchen Worker
   ↓
Prepare Food
   ↓
Completed
```

In your application:

```text
Client
   ↓
API
   ↓
Job Queue
   ↓
Background Worker
   ↓
Process Job
```

The API doesn't have to perform the long-running work itself.

---

# 2. Why Do We Need a Separate Worker?

Consider:

```text
POST /api/v1/ai/generate-quiz
```

Without a worker:

```text
HTTP Request
    ↓
Express
    ↓
LLM
    ↓
Generate quiz
    ↓
Save database
    ↓
HTTP Response
```

The API process is busy.

With a worker:

```text
HTTP Request
    ↓
Express
    ↓
Create Job
    ↓
HTTP Response
```

Then separately:

```text
Queue
 ↓
Worker
 ↓
LLM
 ↓
PostgreSQL
```

Now your API is free to handle other requests.

---

# 3. API Server vs Worker

This distinction is extremely important.

### API server

Responsible for:

```text
HTTP requests
Authentication
Authorization
Validation
Responses
```

### Worker

Responsible for:

```text
Background jobs
AI generation
Emails
Notifications
Document processing
Long-running tasks
```

So:

```text
             Application
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
    API Server           Worker
       │                   │
       ↓                   ↓
    HTTP                Jobs
       │                   │
       └─────────┬─────────┘
                 ↓
               Redis
```

They have different responsibilities.

# 5. Worker Is a Separate Process

This is important.

Don't think:

```text
Express
 ├── API
 └── Worker
```

inside the same request-processing flow.

Instead, conceptually:

```text
Node Process 1
└── API Server

Node Process 2
└── Worker
```

For example:

```text
Terminal 1:

npm run dev:api
```

and:

```text
Terminal 2:

npm run dev:worker
```

Both connect to the same Redis instance.

```text
API ──────┐
          ↓
        Redis
          ↑
Worker ───┘
```

This separation becomes very useful in production.

---

# 6. Why Separate Processes?

Suppose your worker gets stuck processing a huge AI job.

If API and worker are the same process:

```text
Worker becomes overloaded
       ↓
API becomes affected
       ↓
Users experience slow requests
```

With separate processes:

```text
Worker overloaded
       ↓
API remains available
```

That's one of the biggest reasons to separate them.

# 7. Creating a BullMQ Worker

In 11.5, we created:

```ts
import { Queue } from "bullmq";

const aiQueue = new Queue(
  "ai-generation",
  {
    connection: {
      host: "localhost",
      port: 6379,
    },
  }
);
```

Now we create a worker:

```ts
import { Worker } from "bullmq";

const worker = new Worker(
  "ai-generation",
  async (job) => {
    console.log(
      "Processing:",
      job.name,
      job.data
    );
  },
  {
    connection: {
      host: "localhost",
      port: 6379,
    },
  }
);
```

The important part:

```text
Worker(
    "ai-generation",
    processor
)
```

The worker listens to the same queue:

```text
Queue name:
ai-generation
```

---

# 8. The Processor Function

This part:

```ts
async (job) => {
   // work
}
```

is the **processor**.

For example:

```ts
const worker = new Worker(
  "ai-generation",
  async (job) => {
    console.log(job.name);
    console.log(job.data);
  },
  {
    connection,
  }
);
```

When a job arrives:

```text
Queue
 ↓
Worker
 ↓
processor(job)
```

The processor performs the actual work.

# 10. Return Value of a Job

A worker can return a result:

```ts
return {
  quizId: "quiz-123",
};
```

BullMQ can store job completion information.

Conceptually:

```text
Job
 ↓
Worker
 ↓
return result
 ↓
Completed
```

This becomes useful when we later want to inspect job results.

However, don't use the queue as your primary database.

For important LMS data:

```text
Quiz
Course
Certificate
Progress
```

save it to PostgreSQL.

The queue is for **processing**, not permanent business storage.

# 11. Job States

A job can move through states such as:

```text
WAITING
   ↓
ACTIVE
   ↓
COMPLETED
```

or:

```text
WAITING
   ↓
ACTIVE
   ↓
FAILED
```

The worker controls the transition through processing.

Conceptually:

```text
Queue
 │
 ├── Waiting
 │
 ↓
Worker
 │
 ├── Success → Completed
 │
 └── Error   → Failed
```

This will become very important in the later monitoring lesson.

---

# 12. Handling Errors

Never let an error silently disappear.

For example:

```ts
const worker = new Worker(
  "ai-generation",
  async (job) => {
    try {
      await processJob(job);
    } catch (error) {
      console.error(error);
      throw error;
    }
  },
  { connection }
);
```

Why throw the error again?

Because the queue needs to know:

```text
The job failed.
```

If you catch the error and don't rethrow it:

```ts
try {
  await processJob(job);
} catch (error) {
  console.error(error);

  // ❌ no throw
}
```

the queue may think the job succeeded.

That's dangerous.

---

# 13. Correct Error Flow

Use:

```text
Job
 ↓
Worker
 ↓
process
 ↓
Error?
 ┌───────┴───────┐
No              Yes
 ↓                ↓
Complete        throw
                  ↓
                Failed
```

This is especially important when:

```text
AI API
Database
Email provider
External service
```

fails.

---

# 14. Example Worker With Error Handling

```ts
const worker = new Worker(
  "ai-generation",
  async (job) => {
    try {
      const result = await generateQuiz(
        job.data.courseId
      );

      return result;
    } catch (error) {
      console.error(
        `Job ${job.id} failed`,
        error
      );

      throw error;
    }
  },
  {
    connection,
  }
);
```

Now BullMQ knows the job failed.

Later, retry configuration can decide what happens next.

# 16. Concurrency

Suppose the queue has:

```text
100 jobs
```

You could process them:

```text
Job 1
 ↓
complete
 ↓
Job 2
 ↓
complete
```

That's sequential processing.

But sometimes you want:

```text
Job 1 ──┐
Job 2 ──┤
Job 3 ──┼──→ Worker
Job 4 ──┤
Job 5 ──┘
```

This is **concurrency**.

BullMQ allows you to configure worker concurrency.

Conceptually:

```ts
const worker = new Worker(
  "ai-generation",
  processor,
  {
    connection,
    concurrency: 4,
  }
);
```

This means the worker can process up to approximately four jobs concurrently.

---

# 17. Why Concurrency Matters for AI

Suppose:

```text
100 AI jobs
```

If you process all 100 simultaneously:

```text
100 LLM requests
      ↓
Rate limits
Cost
CPU
Memory
Database load
```

could become a problem.

Instead:

```text
100 jobs
   ↓
Queue
   ↓
4 at a time
   ↓
4
4
4
4
...
```

This creates controlled throughput.

For AI workloads, concurrency is a very important production consideration.

---

# 18. Don't Pick Concurrency Randomly

For example:

```text
concurrency: 100
```

is not automatically better than:

```text
concurrency: 5
```

The correct value depends on:

```text
LLM provider limits
CPU
RAM
Database capacity
Network
Job duration
Cost
Expected traffic
```

Start conservatively and measure.

This is an important production engineering habit:

> **Tune based on evidence, not guesses.**

# 22. Different Job Types

Suppose our queue contains:

```text
generate-quiz
generate-summary
generate-explanation
```

We can route them:

```ts
async function processor(job: Job) {
  switch (job.name) {
    case "generate-quiz":
      return generateQuizHandler(job);

    case "generate-summary":
      return generateSummaryHandler(job);

    default:
      throw new Error(
        `Unknown job: ${job.name}`
      );
  }
}
```

But as the project grows, you may want separate queues/workers for very different workloads.

We'll make that decision based on workload rather than creating unnecessary complexity.

# 23. One Worker vs Multiple Workers

You can have:

```text
             Redis
               │
       ┌───────┼────────┐
       ↓       ↓        ↓
     Worker  Worker   Worker
       │       │        │
       AI     Email   Notification
```

Or:

```text
Redis
 ↓
One Worker
 ↓
Everything
```

For a small project, one worker may be enough.

For production, separating workloads can make sense.

For example:

```text
AI Worker
Email Worker
Notification Worker
Document Worker
```

Why?

Because AI jobs may be slow while notification jobs may be tiny.

You don't want a huge AI backlog to prevent urgent notifications from processing.

---

# 24. Queue Isolation

Imagine:

```text
100 AI jobs
```

and:

```text
1 password-reset email
```

If everything shares one queue and one worker:

```text
AI job
AI job
AI job
...
AI job
Password reset email
```

The password reset email could wait behind expensive AI tasks.

Instead:

```text
AI Queue
   ↓
AI Worker

Email Queue
   ↓
Email Worker
```

Now email can proceed independently.

This is a strong real-world architecture concept.

---

# 25. Worker Scaling

Suppose traffic grows.

You don't necessarily need to make one worker bigger.

You can run multiple worker processes:

```text
                 Redis
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
   Worker 1    Worker 2    Worker 3
```

All consume from the same queue.

BullMQ coordinates job distribution through Redis.

So:

```text
More traffic
    ↓
More workers
    ↓
More processing capacity
```

This is **horizontal scaling**.

---

# 26. API Scaling and Worker Scaling Are Independent

This is a very useful insight.

You might have:

```text
API servers = 3
Workers = 5
```

or:

```text
API servers = 10
Workers = 2
```

depending on the workload.

For example:

```text
Heavy read traffic
    ↓
More API servers
```

while:

```text
Heavy AI generation
    ↓
More AI workers
```

The queue decouples the two systems.

# 27. Graceful Shutdown

Workers should shut down properly.

Imagine you deploy a new version:

```text
Worker
 ↓
processing job
```

If you immediately kill the process:

```text
Worker ❌
```

you risk interrupting work.

A proper worker should respond to:

```text
SIGTERM
SIGINT
```

and gracefully stop accepting new work while allowing active processing to finish when possible.

Conceptually:

```ts
process.on("SIGTERM", async () => {
  await worker.close();
  await prisma.$disconnect();
  process.exit(0);
});
```

The exact shutdown design will depend on your deployment environment.

This becomes particularly important in Phase 13 when we deploy with Docker.

# 28. Worker Health

A worker doesn't expose HTTP requests in the same way your API does.

So how do we know it's alive?

Later, we'll use:

```text
heartbeat
logs
queue metrics
job processing metrics
process monitoring
```

For now, understand that:

```text
Worker running
≠
Worker healthy
```

A worker could technically be alive but unable to process jobs.

Example:

```text
Worker process: running
Redis connection: broken
AI provider: failing
Jobs: increasing
```

That's why monitoring becomes its own lesson.

# 29. Worker Logging

Good worker logs should identify the job.

Instead of:

```text
Error occurred
```

use something like:

```text
[AI Worker]
jobId=abc123
jobName=generate-quiz
courseId=456
status=started
```

Then:

```text
[AI Worker]
jobId=abc123
status=completed
duration=8420ms
```

Or on failure:

```text
[AI Worker]
jobId=abc123
status=failed
error="AI provider timeout"
```

This will be very useful when debugging production jobs.

---

# 30. Never Log Sensitive Job Data

Don't log:

```text
password
access token
refresh token
OTP
API key
full private user information
```

For example, avoid:

```ts
console.log(job.data);
```

if `job.data` might contain sensitive information.

Prefer:

```ts
console.log({
  jobId: job.id,
  jobName: job.name,
  courseId: job.data.courseId,
});
```

This is another small but important security habit.

Let's build a simple worker for the queue from 11.5.

# 🧠 Interview Questions

### What is a background worker?

A separate process that consumes jobs from a queue and performs asynchronous work outside the API request lifecycle.

### Why separate workers from API servers?

To isolate long-running/background workloads from HTTP traffic and allow them to scale independently.

### What is the difference between a queue and a worker?

```text
Queue
→ stores/schedules jobs

Worker
→ processes jobs
```

### Can multiple workers process the same queue?

Yes. Multiple workers can consume jobs from the same queue, allowing horizontal scaling and increased processing capacity.

### What is concurrency?

The number of jobs a worker can process at the same time.

### Why shouldn't AI workers have unlimited concurrency?

Because external API limits, cost, CPU, memory, and downstream database capacity can all become bottlenecks.

### What happens if a worker throws an error?

The job can be marked as failed, allowing the queue system to handle failure according to its configuration.
