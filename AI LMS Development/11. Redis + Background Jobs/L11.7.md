# Lesson 11.7 — AI Generation Jobs

According to your Phase 11 roadmap, **11.7 is AI Generation Jobs**, after Job Queues and Background Workers.

This is where we connect everything we've learned:

```text
Redis
  ↓
Queue
  ↓
Worker
  ↓
AI Provider
  ↓
PostgreSQL
```

The goal is to move **slow/expensive AI operations out of the normal HTTP request**.

---

# 1. Why AI Generation Should Be a Background Job

Imagine your instructor clicks:

> Generate a 30-question quiz from this course.

Without a queue:

```text
Browser
   ↓
POST /api/ai/quiz/generate
   ↓
Express
   ↓
Fetch course
   ↓
Build prompt
   ↓
LLM API
   ↓
Generate 30 questions
   ↓
Validate response
   ↓
Save quiz
   ↓
HTTP response
```

The instructor may wait several seconds.

Worse, if the AI provider takes 20 seconds:

```text
HTTP request
    │
    ├────────────── 20 seconds ──────────────┐
    │                                        │
    ↓                                        ↓
API process                              Response
```

That's not a good user experience.

---

# 2. The Better Architecture

Instead:

```text
Instructor
    ↓
POST /api/ai/quiz/generate
    ↓
API
    ↓
Create AI job
    ↓
Redis / BullMQ
    ↓
Return job ID
```

Then:

```text
AI Queue
    ↓
AI Worker
    ↓
Fetch course
    ↓
Build prompt
    ↓
LLM
    ↓
Validate result
    ↓
PostgreSQL
```

The user gets a quick response:

```json
{
  "success": true,
  "jobId": "job_123",
  "status": "queued"
}
```

Instead of waiting for the AI.

---

# 3. What Kind of AI Tasks Should Become Jobs?

For your AI LMS, good candidates include:

```text
AI quiz generation
AI question generation
Course summarization
Lesson summarization
AI explanations
Embedding generation
Document processing
RAG ingestion
Certificate generation
Large content analysis
```

Especially expensive operations:

```text
Large prompt
      ↓
LLM
      ↓
Large response
```

are good candidates for background processing.

---

# 4. What Should Stay Synchronous?

Not every AI request needs a queue.

For example:

```text
Student:
"Explain recursion in simple words."
```

If the expected response is fast, you might keep:

```text
POST /api/ai/chat
      ↓
LLM
      ↓
Response
```

synchronous.

But:

```text
Generate 50 quiz questions
Analyze a 200-page document
Generate embeddings for 1,000 chunks
Summarize an entire course
```

are much better candidates for background jobs.

A useful question is:

> **Does the user need the final result before the HTTP request can finish?**

If not, consider a background job.

# 6. Important Rule: The Queue Is Not the Database

Suppose we generate:

```json
{
  "questions": [
    "...",
    "...",
    "..."
  ]
}
```

Don't think:

```text
AI result
 ↓
Redis
 ↓
Permanent storage
```

Instead:

```text
AI result
 ↓
Validate
 ↓
PostgreSQL
 ↓
Permanent quiz
```

Redis/BullMQ handles:

```text
job processing
```

PostgreSQL handles:

```text
business data
```

So:

```text
BullMQ
→ "Please generate this."

PostgreSQL
→ "This quiz now exists."
```

That's an important architectural separation.

---

# 7. What Data Should the AI Job Contain?

Don't put the entire course into the job.

Avoid:

```json
{
  "course": {
    "id": "...",
    "title": "...",
    "lessons": [...],
    "content": "huge content..."
  }
}
```

Instead:

```json
{
  "userId": "user_123",
  "courseId": "course_456",
  "numberOfQuestions": 20,
  "difficulty": "medium"
}
```

The worker can retrieve the authoritative course data from PostgreSQL.

This gives us:

```text
Small job
   ↓
courseId
   ↓
PostgreSQL
   ↓
Current course data
```

That's much cleaner.

---

# 8. Why Fetch Data Inside the Worker?

Imagine:

```text
12:00
Instructor creates job
```

At:

```text
12:01
Course content changes
```

Worker starts at:

```text
12:02
```

If the job contains an old copy of the entire course, the worker may process stale data.

If the job contains:

```text
courseId
```

the worker can fetch the latest permitted data.

So:

```text
Job
 ↓
Identifier
 ↓
Repository
 ↓
Current data
```

is usually a better design.

# 9. AI Job Structure

We can define a TypeScript type:

```ts
export type GenerateQuizJobData = {
  userId: string;
  courseId: string;
  numberOfQuestions: number;
  difficulty: "easy" | "medium" | "hard";
};
```

Now the job becomes strongly typed.

Example:

```ts
const job = await aiQueue.add(
  "generate-quiz",
  {
    userId: "user_123",
    courseId: "course_456",
    numberOfQuestions: 20,
    difficulty: "medium",
  }
);
```

This is much better than passing an unstructured object everywhere.

# 10. API Layer

Your controller should remain thin.

Something like:

```ts
async generateQuiz(req, res) {
  const job = await aiService.queueQuizGeneration(
    req.user.userId,
    req.body
  );

  return res.status(202).json({
    success: true,
    data: {
      jobId: job.id,
      status: "queued",
    },
  });
}
```

Notice:

The controller doesn't:

```text
❌ call LLM
❌ fetch course
❌ generate questions
❌ save questions
```

It simply asks the service to create a job.

---

# 11. Why HTTP 202?

For asynchronous processing, HTTP `202 Accepted` is a natural choice.

It communicates:

> The request was accepted for processing, but the final operation hasn't completed yet.

So:

```http
POST /api/v1/ai/quizzes/generate
```

could return:

```http
202 Accepted
```

with:

```json
{
  "success": true,
  "data": {
    "jobId": "job_123",
    "status": "queued"
  }
}
```

This is more semantically accurate than pretending the quiz has already been generated.

---

# 12. Service Layer

Your service might conceptually do:

```ts
async function queueQuizGeneration(
  userId: string,
  input: GenerateQuizInput
) {
  // authorization / business checks

  const job = await aiQueue.add(
    "generate-quiz",
    {
      userId,
      courseId: input.courseId,
      numberOfQuestions:
        input.numberOfQuestions,
      difficulty: input.difficulty,
    }
  );

  return job;
}
```

The service is responsible for the business decision:

```text
Should this job be created?
```

The queue infrastructure handles:

```text
How should the job be queued?
```

---

# 13. Authorization Before Queueing

This is extremely important.

Suppose:

```text
Instructor A
```

tries:

```http
POST /ai/quizzes/generate
```

with:

```json
{
  "courseId": "course-owned-by-instructor-B"
}
```

Don't queue the job and check permission later.

Do:

```text
Request
 ↓
Authenticate
 ↓
Authorize
 ↓
Check course ownership/access
 ↓
Create job
```

Not:

```text
Request
 ↓
Create job ❌
 ↓
Worker discovers unauthorized request
```

Why?

Because unauthorized jobs shouldn't enter your expensive AI pipeline.

---

# 14. Validate Before Queueing

Similarly:

```json
{
  "numberOfQuestions": -1000
}
```

should never become an AI job.

Validate:

```text
numberOfQuestions
difficulty
courseId
```

before queueing.

Example:

```text
Request
 ↓
Zod validation
 ↓
Authorization
 ↓
Queue
```

This saves:

```text
AI cost
Redis resources
Worker resources
Database resources
```

# 15. AI Worker

Now the interesting part.

Our worker receives:

```ts
job.data
```

For example:

```json
{
  "userId": "user_123",
  "courseId": "course_456",
  "numberOfQuestions": 20,
  "difficulty": "medium"
}
```

The worker can call a handler:

```ts
const worker = new Worker(
  "ai-generation",
  generateQuizHandler,
  {
    connection,
  }
);
```

Then:

```ts
async function generateQuizHandler(job) {
  const {
    userId,
    courseId,
    numberOfQuestions,
    difficulty,
  } = job.data;

  // process AI generation
}
```

---

# 16. Worker Processing Pipeline

The handler should not simply do:

```text
LLM → Save
```

A safer pipeline is:

```text

 ↓

 ↓
Fetch course
 ↓
Check required data
 ↓
Build prompt
 ↓
Call LLM
 ↓

 ↓

 ↓

 ↓

 ↓

```

Each step matters.

The worker can use your existing repository:

const course =

if (!course) {

# 19. AI Provider Abstraction

Don't tightly couple your worker to one provider.

Instead of:

```ts
await openai.chat.completions.create(...)
```

everywhere, prefer an abstraction such as:

```ts
const result =
  await aiProvider.generateQuiz({
    context,
    numberOfQuestions,
    difficulty,
  });
```

Then:

```text
AI Service
    ↓
AI Provider Interface
    ↓
Provider implementation
```

This makes it easier to change providers later.

# 20. AI Output Must Be Validated

This is one of the most important parts.

Never assume:

```text
LLM response = valid database data
```

Even if you ask the model for JSON, it can return:

```json
{
  "questions": [
    {
      "question": "...",
      "options": "wrong shape"
    }
  ]
}
```

Your worker should validate the result.

For example, using Zod:

```ts
const QuestionSchema = z.object({
  question: z.string(),
  options: z.array(z.string()).length(4),
  correctAnswer: z.string(),
  explanation: z.string(),
});
```

Then:

```ts
const result =
  QuestionSchema.array().safeParse(
    aiResponse
  );
```

If invalid:

```text
AI output
 ↓
Validation ❌
 ↓
Job failure
```

Don't save invalid AI output into PostgreSQL.

---

# 21. Why AI Validation Is So Important

Your AI system is an **untrusted external-output boundary**.

Think:

```text
Your application
       ↓
External AI
       ↓
Untrusted output
       ↓
Validation
       ↓
Trusted internal structure
```

This is similar to:

```text
HTTP request
 ↓
Validation
```

You already learned this principle with Zod.

Now apply the same idea to AI.

---

# 22. Save to PostgreSQL

After validation:

```text
AI result
 ↓
Validated structure
 ↓
Quiz repository
 ↓
PostgreSQL
```

For example:

```ts
const quiz =
  await quizRepository.create({
    courseId,
    createdBy: userId,
    difficulty,
  });
```

Then questions:

```ts
for (const question of questions) {
  await questionRepository.create({
    quizId: quiz.id,
    ...question,
  });
}
```

In a real implementation, you'd likely use a **transaction** so you don't end up with a half-created quiz.

For example:

```text
Create quiz
 ↓
Create questions
 ↓
Everything succeeds
```

or:

```text
Something fails
 ↓
Rollback
```

Your earlier Prisma/database lessons are important here.

---

# 23. Use a Database Transaction

Imagine:

```text
Quiz created
Question 1 created
Question 2 created
Question 3 ❌
```

Now your database has an incomplete quiz.

Better:

```text
Transaction
 ├── Create quiz
 ├── Create question 1
 ├── Create question 2
 ├── Create question 3
 └── Commit
```

If question 3 fails:

```text
Rollback
```

This keeps the database consistent.

# 24. Job Status vs Business Status

Don't confuse:

```text
Job status
```

with:

```text
Quiz status
```

For example:

### Job

```text
queued
processing
completed
failed
```

### Quiz generation

```text
generating
ready
failed
```

They may be related, but they are not necessarily the same thing.

A good system can explicitly model business state in PostgreSQL.

For example:

```text
AI Generation Request
---------------------
id
userId
courseId
status
quizId
errorMessage
createdAt
completedAt
```

Then:

```text
BullMQ
→ processing mechanism

PostgreSQL
→ durable business status
```

This is an important architecture improvement.

# 27. Why Have Both `generationId` and `jobId`?

They have different purposes.

### `jobId`

Belongs to the queue system:

```text

```

Used for:

```text

queue debugging

```

### `generationId`

Belongs to your LMS:

```text

```

Used for:

```text

business state
history
audit

```

So:

```text
BullMQ job
     ↓
technical processing

Generation record
     ↓
business/application state
```

This separation is very useful.

# 38. AI Output Pipeline

A safe pipeline is:

```text
                 LLM
                  ↓
             Raw Output
                  ↓
             Parse JSON
                  ↓
            Schema Validate
                  ↓
            Business Validate
                  ↓
            Normalize Data
                  ↓
             PostgreSQL
```

For example:

```text
"correctAnswer"
```

must actually match one of:

```text
options
```

That's a **business validation** rule beyond basic schema validation.

---

# 39. Example Business Validation

Suppose AI returns:

```json
{
  "question": "What is TypeScript?",
  "options": [
    "A",
    "B",
    "C",
    "D"
  ],
  "correctAnswer": "E"
}
```

Schema might be valid:

```text
correctAnswer = string
```

but business validation fails:

```text
"E" isn't one of the options.
```

So:

```text
Schema validation
      ↓
passes

Business validation
      ↓
fails
```

Don't save it.

# 40. Worker Should Be Deterministic Where Possible

AI itself is probabilistic.

Your surrounding processing should be predictable:

```text
Fetch data
 ↓
Build prompt
 ↓
Call AI
 ↓
Validate
 ↓
Save
```

Avoid hidden side effects like:

```text
worker
 ↓
random database updates
 ↓
external API calls
 ↓
another queue
 ↓
more side effects
```

unless they're explicitly part of the job design.

Predictability makes retries and debugging much easier.

# 44. Practical Implementation Plan

Don't try to build the entire system in one file.

Build it in layers.

### Step 1 — Queue

```text
ai-generation
```

### Step 2 — API

```text
POST /ai/generations
```

### Step 3 — Generation record

```text
status = queued
```

### Step 4 — Queue job

```json
{
  "generationId": "...",
  "userId": "...",
  "courseId": "..."
}
```

### Step 5 — Worker

```text
consume job
```

### Step 6 — Fetch course

```text
courseRepository
```

### Step 7 — AI provider

```text
generateQuiz()
```

### Step 8 — Validate

```text
Zod + business rules
```

### Step 9 — Transaction

```text
Quiz
+
Questions
```

### Step 10 — Update generation

```text
completed
```

This is a much better implementation strategy than trying to build everything simultaneously.

# 🧠 Interview Questions

### Why should AI generation be asynchronous?

Because AI generation can be slow, expensive, and unpredictable. Moving it to a background worker keeps normal API requests responsive.

### Why shouldn't the entire course be stored inside the job?

It makes jobs unnecessarily large and can cause stale data. Passing identifiers and loading authoritative data in the worker is usually cleaner.

### Why validate AI output?

LLM output is not guaranteed to follow your expected structure. Validation prevents malformed or unsafe data from entering your database.

### Why use a generation record in PostgreSQL?

It provides durable business-level status that the frontend and users can query independently of the queue system.

### What is the difference between `jobId` and `generationId`?

```text
jobId
→ queue infrastructure

generationId
→ LMS business/application state
```

### What happens if AI generation fails?

The worker should surface the failure so the job can be marked failed and the generation record can be updated appropriately. Retry behavior will be handled later.

# 🎯 The Core Mental Model

This is the architecture I want you to remember:

```text
             USER
               │
               ↓
        ┌─────────────┐
        │     API     │
        └──────┬──────┘
               │
         Create Job
               │
               ↓
        ┌─────────────┐
        │    Redis    │
        │   BullMQ    │
        └──────┬──────┘
               │
               ↓
        ┌─────────────┐
        │ AI Worker   │
        └──────┬──────┘
               │
       ┌───────┼────────┐
       ↓       ↓        ↓
   PostgreSQL  AI      Validation
       │       API        │
       └───────┴──────────┘
               ↓
          Quiz Created
```

The most important principle is:

> **The API schedules the AI work; the worker performs the AI work; PostgreSQL stores the final business result.**

And one more:

> **Never trust raw AI output just because it came from an LLM. Validate it before it reaches your database.**
