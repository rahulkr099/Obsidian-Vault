# Lesson 11.8 — Email Jobs

According to your Phase 11 roadmap, **11.8 is Email Jobs**.

In the previous lessons, we built:

```text
11.4 → Redis Rate Limiting
11.5 → Job Queues
11.6 → Background Workers
11.7 → AI Generation Jobs
```

Now we'll apply the same queue + worker architecture to **email sending**.

The core idea is:

> **Don't make the user's HTTP request wait for an email provider. Put email work into a queue and let a background worker send it.**

---

# 1. The Problem With Sending Email Directly

Suppose a student registers:

```http
POST /api/v1/auth/register
```

A simple implementation might do:

```text
Request
  ↓
Validate user
  ↓
Create user
  ↓
Send verification email
  ↓
Wait for email provider
  ↓
Response
```

The email provider could take:

```text
500 ms
2 seconds
5 seconds
```

or fail temporarily.

That means your registration API is unnecessarily dependent on the email provider.

---

# 2. Better Architecture

Instead:

```text
POST /register
      ↓
Validate
      ↓
Create user
      ↓
Create email job
      ↓
Return response
```

Then:

```text
Email Queue
      ↓
Email Worker
      ↓
Email Provider
      ↓
Student receives email
```

Complete flow:

```text
                   Student
                      │
                      ↓
                  API Server
                      │
                      ├──────────────→ PostgreSQL
                      │
                      ↓
                  Email Queue
                      │
                      ↓
                    Redis
                      │
                      ↓
                  Email Worker
                      │
                      ↓
                Email Provider
                      │
                      ↓
                 Student Email
```

---

# 3. Why Email Is a Great Background Job

Email has several characteristics that make it suitable for background processing:

```text
External network dependency
Potentially slow
Can temporarily fail
Usually doesn't need to block the request
Can be retried
```

Examples:

```text
Email verification
Password reset
Welcome email
Course enrollment
Certificate delivery
Assignment reminder
Payment receipt
Notification email
```

# 5. Important: Don't Queue Before Creating the User

Consider this:

```text
Queue email
    ↓
Create user
```

If user creation fails:

```text
Email queued ❌
User doesn't exist
```

That's wrong.

Better:

```text
Create user
    ↓
Success
    ↓
Create email job
```

So the basic flow is:

```text
Database operation
       ↓
Successful?
    ┌──┴──┐
   Yes    No
    ↓      ↓
 Queue    Error
```

# 6. Email Queue

Create a dedicated queue:

```ts
import { Queue } from "bullmq";

export const emailQueue =
  new Queue("email", {
    connection: {
      host: "localhost",
      port: 6379,
    },
  });
```

Notice that this is separate from:

```text
ai-generation
```

We now have:

```text
Redis
 ├── ai-generation
 └── email
```

---

# 7. Why Separate AI and Email Queues?

Imagine:

```text
100 AI jobs
```

and:

```text
1 password-reset email
```

If they share one queue:

```text
AI
AI
AI
AI
...
Password Reset
```

The password-reset email could be delayed.

Instead:

```text
AI Queue
   ↓
AI Workers

Email Queue
   ↓
Email Workers
```

Now they can scale independently.

---

# 8. Email Job Data

Don't put an entire user object into the queue.

Bad:

```ts
await emailQueue.add("verification", {
  user: entireUserObject,
});
```

Better:

```ts
await emailQueue.add(
  "verification-email",
  {
    userId: user.id,
    email: user.email,
    verificationTokenId:
      verification.id,
  }
);
```

Even better, depending on your design:

```ts
{
  userId,
  verificationId
}
```

and let the worker fetch authoritative information.

# 11. Email Worker

The worker looks like:

```ts

const worker = new Worker(
  "email",

    console.log(
      `Processing email job ${job.id}`
    );

    // Send email
  },
  {
    connection: {
      host: "localhost",
      port: 6379,
    },
  }
);
```

Now:

```text
Email Queue
    ↓
Email Worker
    ↓
Email Provider
```

# 12. Don't Put Email Provider Logic Everywhere

Avoid this:

```text
Registration Service
    ↓
Email Provider

Password Reset Service
    ↓
Email Provider

Certificate Service
    ↓
Email Provider
```

You don't want every module knowing provider-specific details.

Instead:

```text
Registration Service
       ↓
Email Queue
       ↓
Email Worker
       ↓
Email Service
       ↓
Email Provider
```

This gives you a clean boundary.

---

# 13. Email Provider Abstraction

Create something like:

```ts
interface EmailProvider {
  send(
    options: SendEmailOptions
  ): Promise<void>;
}
```

Then:

```ts
class SomeEmailProvider
  implements EmailProvider {
  
  async send(
    options: SendEmailOptions
  ) {
    // provider-specific implementation
  }
}
```

Your worker doesn't need to know the provider's internal API.

It simply says:

```ts
await emailProvider.send({
  to,
  subject,
  html,
});
```

---

# 14. Why Provider Abstraction Matters

Suppose you initially use:

```text
Provider A
```

Later you want:

```text
Provider B
```

Without abstraction:

```text
50 files
 ↓
provider-specific code
```

With abstraction:

```text
Application
    ↓
EmailProvider interface
    ↓
Provider A

or

Provider B
```

Much easier to change.

# 15. Email Templates

Don't generate email HTML directly inside your worker.

Avoid:

```ts
await emailProvider.send({
  html: `
    <html>
      ...
    </html>
  `,
});
```

inside every handler.

Instead:

```text
Email Worker
     ↓
Email Handler
     ↓
Email Template
     ↓
Email Provider
```

For example:

```text
templates/
├── verification.ts
├── password-reset.ts
├── welcome.ts
└── certificate.ts
```

# 16. Template Function

Conceptually:

```ts
function verificationEmailTemplate(

  return {
    subject: "Verify your email",

      <p>
        Please verify your email.
      </p>
```

```ts

  to,
```

# 18. Verification Token Security

Don't put a raw sensitive verification token into logs.

For example, avoid:

```ts

  "Verification token:",
  token
);
```

Instead log:

```ts
console.log({
  jobId: job.id,
  type: "verification-email",
  userId,
});
```

Tokens should be treated as sensitive.

# 20. Email Job Data Should Not Contain Passwords

```ts

  newPassword,
  passwordHash

```

into an email job.

Obviously:

```text

❌ access token
```

# 25. Email Worker Concurrency

Email sending can usually have higher concurrency than AI generation, but don't assume an unlimited value.

For example:

```ts
const worker = new Worker(
  "email",
  processEmailJob,
  {
    connection,
    concurrency: 10,
  }
);
```

That means:

```text
10 email jobs
```

can be processed concurrently by that worker process.

The correct number depends on:

```text
Email provider limits
Your server
Expected traffic
Provider throughput
```

---

# 26. Email Provider Rate Limits

Suppose your provider allows:

```text
100 emails/minute
```

but you configure:

```text
500 concurrent jobs
```

You can overwhelm the provider.

So:

```text
Queue concurrency
+
Provider rate limits
```

need to be designed together.

This is another example of why queues aren't just about speed.

They also help with **controlled throughput**.

For example:

```text

- network timeout
- provider unavailable
- temporary server error
```

These may be retryable.

But:

```text
Permanent:
- malformed email address
- invalid recipient
```

may not be useful to retry repeatedly.

# 28. Email Worker Error Handling

A basic handler:

```ts
async function processEmailJob(
  job: Job
) {
  try {
    const result =
      await handleEmail(job);

    return result;
  } catch (error) {
    console.error({
      jobId: job.id,
      error,
    });

    throw error;
  }
}
```

The important part:

```ts
throw error;
```

This tells BullMQ:

```text
The job failed.
```

Don't silently swallow the error.

---

# 29. Email Delivery Is Not the Same as Email Job Completion

This is an important distinction.

Suppose:

```text
Worker
 ↓
Email provider
 ↓
accepted
```

The provider may have accepted the message, but that doesn't always mean:

```text
The recipient definitely received it.
```

Your application can know:

```text
email submission succeeded
```

but final delivery may depend on the email provider and recipient mail system.

So your business status might distinguish:

```text
queued
sending
sent
failed
```

and potentially later:

```text
delivered
bounced
complained
```

if your provider gives webhook events.

We don't need to build webhooks yet.

# 36. Email Handler Example

For verification:

```ts
async function handleVerificationEmail(
  job: Job<VerificationEmailJob>
) {
  const {
    userId,
    verificationId,
  } = job.data;

  const user =
    await userRepository.findById(userId);

  const verification =
    await verificationRepository
      .findById(verificationId);

  if (!user || !verification) {
    throw new Error(
      "Required email data not found"
    );
  }

  const url =
    buildVerificationUrl(
      verification.token
    );

  const email =
    verificationEmailTemplate(url);

  await emailProvider.send({
    to: user.email,
    subject: email.subject,
    html: email.html,
  });
}
```

Again, don't copy this blindly. Adapt it to your actual auth/token design.

# 42. What Should the API Response Say?

Suppose registration succeeded but the email job failed to enqueue.

You shouldn't simply say:

```text
"Registration and email sent successfully."
```

if the email hasn't been queued.

The API should accurately represent what happened.

For example:

```json
{
  "success": true,
  "data": {
    "userId": "user_123",
    "verificationEmailQueued": true
  }
}
```

or whatever response structure matches your API conventions.

Accuracy in API responses matters.

# 43. Registration Transaction vs Email Queue

There's a subtle design question.

Suppose:

```text
Create user
 ↓
Create verification record
 ↓
Queue email
```

What if queue creation fails?

```text
Database success
Queue failure
```

Now:

```text
User exists
Verification exists
Email wasn't queued
```

This is a distributed consistency problem.

You have several possible strategies:

```text
Retry queue creation
Outbox pattern
Transactional event/outbox system
Scheduled recovery
```

For your current project, we'll keep the design understandable first.

But remember:

> **Database transactions cannot automatically make Redis queue operations atomic with PostgreSQL.**

This becomes a more advanced architecture topic later.

# 49. Important Architecture Principle

You now have three separate responsibilities:

```text
Queue
→ "This work needs to happen."

Worker
→ "I'll perform the work."

Provider
→ "I'll communicate with the external service."
```

For email:

```text
Email Queue
     ↓
Email Worker
     ↓
Email Provider
```

For AI:

```text
AI Queue
     ↓
AI Worker
     ↓
AI Provider
```

This pattern can be reused for many external services.

# 50. Compare AI Jobs and Email Jobs

||AI Job|Email Job|
|---|---|---|
|Queue|`ai-generation`|`email`|
|Worker|AI Worker|Email Worker|
|External service|LLM|Email provider|
|Typical duration|Seconds+|Usually shorter|
|Cost sensitivity|High|Medium|
|Retry need|High|High|
|Concurrency|Usually lower|Usually higher|
|Output|AI-generated data|Message delivery|

Both follow the same basic pattern:

```text
Producer
   ↓
Queue
   ↓
Worker
   ↓
External Service
```

# 🧠 Interview Questions

### Why should email sending be asynchronous?

Because email providers are external services that can be slow or temporarily unavailable. Sending email in a background job keeps API responses fast and isolates failures.

### Why use a separate email queue?

It allows email processing to scale and fail independently from AI jobs and normal API requests.

### Should the entire user object be placed in the job?

Usually no. Prefer small, serializable data such as IDs and necessary parameters.

### What should happen when an email provider temporarily fails?

The job should fail in a way that allows an appropriate retry strategy.

### Should you retry every email failure?

No. Temporary failures may be retryable, while permanent failures such as an invalid recipient may not be.

### Why use an email provider abstraction?

It prevents your business logic from becoming tightly coupled to a particular email provider.

### Why shouldn't passwords or access tokens be included in email jobs?

They are sensitive credentials and should never be unnecessarily copied into queue payloads or logs.

### Why isn't a successful email API call necessarily proof of delivery?

The provider may only confirm that it accepted the message. Final delivery can happen later and may fail.
