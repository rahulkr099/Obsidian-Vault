# Lesson 11.9 — Notification Jobs

According to your Phase 11 roadmap, **Lesson 11.9 is Notification Jobs**.

So far we've built:

```text
11.5 → Job Queues
11.6 → Background Workers
11.7 → AI Generation Jobs
11.8 → Email Jobs
```

Now we'll use the same architecture for **notifications inside your LMS**.

The main idea:

> **When an important event happens, create a notification job instead of making the original request perform all notification work.**

---

# 1. What Is a Notification?

A notification tells a user that something happened or needs their attention.

For your LMS, examples include:

```text
Course published
New course assigned
Assignment due soon
Assignment graded
Quiz completed
Certificate generated
New announcement
Instructor replied
AI generation completed
Course enrollment
Password/security alert
```

For example:

```text
Student
   ↓
Assignment graded
   ↓
Notification
   ↓
"Your assignment has been graded."
```

---

# 2. Why Use a Job?

Suppose an instructor grades an assignment.

The API might need to:

```text
Update submission
Create notification
Send email
Update unread count
Create activity record
```

If everything happens synchronously:

```text
POST /assignments/:id/grade
        ↓
Update database
        ↓
Create notification
        ↓
Send email
        ↓
More work
        ↓
Response
```

Instead:

```text
POST /assignments/:id/grade
        ↓
Update submission
        ↓
Create notification job
        ↓
Response
```

Then:

```text
Notification Queue
        ↓
Notification Worker
        ↓
Create notification
        ↓
Optional email job
        ↓
Optional realtime event
```

---

# 3. Notification Types in Your LMS

Let's define some useful types.

```ts
type NotificationType =
  | "COURSE_PUBLISHED"
  | "COURSE_ENROLLED"
  | "ASSIGNMENT_ASSIGNED"
  | "ASSIGNMENT_GRADED"
  | "QUIZ_COMPLETED"
  | "CERTIFICATE_READY"
  | "AI_GENERATION_COMPLETED"
  | "NEW_ANNOUNCEMENT";
```

This is better than arbitrary strings.

For example:

```text
"assignment_graded"
```

and:

```text
"ASSIGNMENT_GRADED"
```

shouldn't randomly appear throughout your codebase.

Use one consistent convention.

---

# 4. Notification Channels

A notification doesn't have to mean only an in-app notification.

You can have:

```text
             Notification Event
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
    In-App        Email       Push
```

For example:

```text
Assignment graded
       │
       ├── In-app notification
       ├── Email
       └── Push notification
```

For your first implementation, I'd recommend:

```text
1. In-app notification
2. Email as an optional channel
3. Push later
```

Keep the architecture simple first.

---

# 5. In-App Notification

An in-app notification is stored in PostgreSQL.

For example:

```text
┌──────────────────────────────────────┐
│ 🔔 Assignment graded                 │
│                                      │
│ Your React assignment was graded.   │
│                                      │
│ 2 minutes ago                        │
└──────────────────────────────────────┘
```

The important thing is that the notification remains available even if the user wasn't online when it was created.

---

# 6. Notification Database Model

A basic Prisma model could look like:

```prisma
model Notification {
  id        String   @id @default(cuid())

  userId    String
  type      String

  title     String
  message   String

  isRead    Boolean  @default(false)

  createdAt DateTime @default(now())
  readAt    DateTime?

  user      User     @relation(
    fields: [userId],
    references: [id]
  )

  @@index([userId, isRead])
  @@index([userId, createdAt])
}
```

Adapt this to your existing schema rather than copying it blindly.

The important fields are:

```text
userId
type
title
message
isRead
createdAt
readAt
```

---

# 7. Why Store Notifications in PostgreSQL?

Because notifications are business data.

Suppose the student was offline:

```text
10:00 AM
Assignment graded
```

They open the LMS at:

```text
2:00 PM
```

The notification should still exist.

Therefore:

```text
Notification
     ↓
PostgreSQL
     ↓
Persistent
```

Redis is useful for temporary/fast coordination, but PostgreSQL should hold durable notification records.

# 9. Notification Job Data

Don't pass the entire user object.

Use something like:

```ts
export type NotificationJobData = {
  userId: string;

  type: NotificationType;

  entityId?: string;

  metadata?: Record<string, unknown>;
};
```

For assignment grading:

```ts
await notificationQueue.add(
  "assignment-graded",
  {
    userId: studentId,
    type: "ASSIGNMENT_GRADED",
    entityId: assignmentId,
  }
);
```

The `entityId` tells the worker what business object the notification relates to.

---

# 10. Why `entityId`?

Imagine:

```text
ASSIGNMENT_GRADED
entityId = assignment_123
```

The notification can link the student to:

```text
/courses/course-123/assignments/assignment-123
```

Similarly:

```text
COURSE_ENROLLED
entityId = course_456
```

can link to:

```text
/courses/course-456
```

This gives your frontend useful navigation information.

# 12. Notification Worker

Now create:

```text
src/workers/notification/
└── notification.worker.ts
```

Basic worker:

```ts
import { Worker } from "bullmq";

const worker = new Worker(
  "notification",
  async (job) => {
    console.log(
      "Processing notification:",
      job.id
    );

    console.log(job.data);
  },
  {
    connection: {
      host: "localhost",
      port: 6379,
    },
  }
);
```

Architecture:

```text
Event
 ↓
Queue
 ↓
Notification Worker
 ↓
PostgreSQL
```

# 13. Notification Handler

Keep the worker clean by moving business logic into a handler.

```ts
async function processNotification(
  job: Job<NotificationJobData>
) {
  const {
    userId,
    type,
    entityId,
  } = job.data;

  // create notification
}
```

Then:

```ts
const worker = new Worker(
  "notification",
  processNotification,
  {
    connection,
  }
);
```

This follows the same architecture we used for AI and email jobs.

---

# 14. Notification Factory

Don't build notification text randomly inside every worker.

Create a notification factory.

For example:

```ts
function buildNotification(
  type: NotificationType,
  data: {
    entityId?: string;
  }
) {
  switch (type) {
    case "ASSIGNMENT_GRADED":
      return {
        title: "Assignment graded",
        message:
          "Your assignment has been graded.",
      };

    case "COURSE_PUBLISHED":
      return {
        title: "New course available",
        message:
          "A new course has been published.",
      };

    default:
      throw new Error(
        `Unsupported notification type: ${type}`
      );
  }
}
```

Now notification content is centralized.

---

# 15. Why Centralize Notification Content?

Without a factory:

```text
Course Service
 → notification text

Assignment Service
 → notification text

Quiz Service
 → notification text

Certificate Service
 → notification text
```

You may end up with inconsistent messages.

Instead:

```text
Business Event
     ↓
Notification Factory
     ↓
Title + Message + Metadata
```

This is much easier to maintain.

# 22. Database Indexing

This query will happen often:

```sql
SELECT *
FROM notifications
WHERE user_id = ?
  AND is_read = false;
```

So an index like:

```prisma
@@index([userId, isRead])
```

is useful.

For recent notifications:

```sql
ORDER BY created_at DESC
```

you may also want an index based on your query patterns.

Don't add indexes blindly—design them around actual queries.

# 28. Don't Make Notification Worker Call the Email Provider Directly

Avoid:

```text

       ↓
Create notification
       ↓
Send email
```

Instead:

```text
Notification Worker
       ↓

       ↓
Email Queue
       ↓
Email Worker
       ↓
Email Provider
```

Why?

Because email has its own:

```text
retry
rate limiting
provider failures
templates
delivery tracking
```

Keep those responsibilities inside the email system.

# 35. But Be Careful With Delayed Jobs

Suppose the student submits the assignment before the reminder time.

You don't want:

```text
Assignment submitted
       ↓
Student receives:
"Your assignment is due tomorrow."
```

So the worker should verify current state:

```text
Reminder job starts
       ↓
Check assignment
       ↓
Already submitted?
   ┌───┴───┐
  Yes      No
   ↓        ↓
Don't      Send
notify
```

This is another example of:

> **Don't blindly trust the state from the moment the job was created.**

Fetch current authoritative state when processing.

# 36. Notification Worker Concurrency

Notifications are usually lightweight:

```text
Queue
 ↓
Worker
```

You could use:

```ts
concurrency: 10
```

or another value based on your workload.

But again:

> **Tune concurrency based on actual workload and database capacity.**

If the worker creates many database writes at once, excessive concurrency can overwhelm PostgreSQL.

# 37. Worker Error Handling

Use the same pattern:

```ts
async function processNotification(
  job: Job<NotificationJobData>
) {
  try {
    // process

  } catch (error) {
    console.error({
      jobId: job.id,
      type: job.data.type,
      error,
    });

    throw error;
  }
}
```

Don't do:

```ts
catch (error) {
  console.error(error);
}
```

without throwing again.

Otherwise BullMQ may think:

```text
Job succeeded
```

even though notification creation failed.

# 42. Security: User Ownership

This is extremely important.

Suppose:

```http
PATCH /notifications/notif-123/read
```

The server must check:

```text
notification.userId === req.user.userId
```

Never assume that knowing a notification ID means the user owns it.

Bad:

```ts
await notificationRepository.markAsRead(
  notificationId
);
```

Better:

```ts
await notificationRepository.markAsRead(
  notificationId,
  req.user.userId
);
```

Then the repository query can enforce ownership.

---

# 43. Notification Content Security

Don't blindly render arbitrary user-generated HTML inside notifications.

For example, don't allow:

```text
User-generated content
      ↓
raw HTML
      ↓
notification
```

Use escaped/plain text content or a controlled rendering system.

This becomes particularly important in your dedicated security phase.

---

# 44. Notification Worker and Database Transactions

Suppose the notification worker does:

```text
Create notification
Create activity record
Update unread count
```

You might be tempted to store an explicit unread count.

But often you don't need to.

You can simply query:

```sql
COUNT(*)
WHERE user_id = ?
AND is_read = false
```

and let PostgreSQL calculate it.

For high-scale systems, caching counters can become useful, but don't prematurely introduce extra state.

Start with the source of truth.

---

# 45. Should We Cache Unread Count?

Initially:

```text
Frontend
 ↓
GET /notifications/unread-count
 ↓
PostgreSQL
```

is perfectly reasonable.

Later, if traffic becomes huge:

```text
PostgreSQL
      ↓
Redis counter
```

could improve performance.

But then you have synchronization complexity.

My recommendation for your LMS:

> **Start with PostgreSQL. Optimize the unread count only after measuring a real bottleneck.**

# 49. Notification + Email Together

For important events:

```text
Assignment graded
       │
       ├───────────────┐
       ↓               ↓
Notification Queue   Email Queue
       ↓               ↓
Notification Worker  Email Worker
       ↓               ↓
PostgreSQL          Email Provider
```

This architecture gives you independent processing.

If email is down:

```text
Email Worker ❌
```

the in-app notification can still work:

```text
Notification Worker ✅
```

That's excellent failure isolation.

# 50. Event-Driven Thinking

You're starting to move toward an event-driven architecture.

Instead of thinking:

```text
AssignmentService
   ↓
do everything
```

think:

```text
Assignment graded
       ↓
Event
       ↓
Multiple reactions
```

For example:

```text
Assignment graded
       │
       ├── Update grade
       ├── Notification
       ├── Email
       ├── Activity log
       └── Analytics
```

Queues allow those side effects to be processed asynchronously.

This is a major backend engineering concept.

---

# 51. Don't Overdo Event-Driven Architecture

However, don't turn every simple operation into:

```text
20 events
15 queues
8 workers
```

That creates unnecessary complexity.

Use background jobs when:

```text
Work is slow
Work can happen later
Work can fail independently
Work needs retries
Work can be processed asynchronously
```

For a simple:

```text
GET /course/:id
```

you don't need a queue.

# 53. Interview Questions

### What is a notification job?

A background job that processes notification-related work asynchronously.

### Why store notifications in PostgreSQL?

Because in-app notifications are durable business data that users may need to see later.

### Why have a separate notification queue?

To isolate notification processing from AI, email, and API workloads.

### Should notification and email use the same worker?

Usually not. They have different failure modes, scaling needs, and processing characteristics.

### What happens if a notification worker fails?

The job should fail properly so the queue can handle it according to the configured retry strategy.

### Why use `entityId`?

It connects a notification to the underlying LMS resource, such as an assignment, course, quiz, or certificate.

### Should you put the entire user object in the job?

Usually no. Prefer small, serializable identifiers.

### How can duplicate notifications happen?

A worker may process the same job more than once after a crash or retry. Idempotency is needed to prevent duplicate side effects.

> **A business event can trigger multiple independent background jobs.**

That's the foundation for building a scalable LMS notification system.
