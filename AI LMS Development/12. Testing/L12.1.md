# 🧪 Lesson 12.1 — Unit Testing

Phase 12 is officially **Testing & Quality Engineering**, and according to the roadmap, the first lesson is **Unit Testing**.

This lesson is important because before testing your complete API, database, authentication, AI, and RAG system, you need to understand how to test the **smallest pieces of your code independently**.

---

## 1. What is Unit Testing?

A **unit** is a small, isolated piece of code.

Usually:

```text
function
method
utility
business rule
small module
```

For example:

```ts
function add(a: number, b: number) {
  return a + b;
}
```

A unit test asks:

```text
Given:
a = 2
b = 3

When:
add(2, 3)

Then:
5
```

So:

```text
        Input
          ↓
     ┌─────────┐
     │ Function│
     └─────────┘
          ↓
        Output
          ↓
      Assertion
```

---

# 2. Why Do We Need Unit Tests?

Imagine your AI LMS has:

```text
50 services
100 controllers
80 utilities
40 repositories
```

You change one function.

Without tests:

```text
Change code
   ↓
Run application
   ↓
Manually test everything
   ↓
😵
```

With unit tests:

```text
Change code
   ↓
Run tests
   ↓
❌ Test failed
   ↓
Find the problem
```

This gives you confidence when modifying existing code.

---

# 3. Unit Test vs Manual Testing

Suppose you have:

```ts
function calculateProgress(completed: number, total: number) {
  return (completed / total) * 100;
}
```

Manual testing:

```text
Open application
Login
Open course
Complete lessons
Check progress
```

Unit testing:

```ts
expect(calculateProgress(5, 10)).toBe(50);
```

The second approach is:

- faster
    
- repeatable
    
- automated
    
- easier to run in CI/CD
    
- useful when refactoring
    

---

# 4. The AAA Pattern

A very common structure for unit tests is:

```text
Arrange
   ↓
Act
   ↓
Assert
```

### Arrange

Prepare the test data.

### Act

Call the function.

### Assert

Check the result.

Example:

```ts
const result = calculateProgress(5, 10);

expect(result).toBe(50);
```

Conceptually:

```text
Arrange
   ↓
completed = 5
total = 10

Act
   ↓
calculateProgress(5, 10)

Assert
   ↓
result === 50
```

Remember:

> **AAA = Arrange → Act → Assert**

This pattern will appear throughout the rest of our testing phase.


# 6. Example: LMS Progress Calculation

Suppose:

```ts
function calculateProgress(
  completedLessons: number,
  totalLessons: number
): number {
  return Math.round((completedLessons / totalLessons) * 100);
}
```

We want to test:

```text
10 / 10 → 100
5 / 10  → 50
1 / 4   → 25
0 / 10  → 0
```

A test suite could conceptually look like:

```ts
describe("calculateProgress", () => {
  it("returns 100 when all lessons are completed", () => {
    expect(calculateProgress(10, 10)).toBe(100);
  });

  it("returns 50 when half the lessons are completed", () => {
    expect(calculateProgress(5, 10)).toBe(50);
  });

  it("returns 0 when no lessons are completed", () => {
    expect(calculateProgress(0, 10)).toBe(0);
  });
});
```

Notice something important.

We're not testing the entire LMS.

We're testing **one small piece of business logic**.

---

# 7. `describe()` and `it()`

Most modern JavaScript/TypeScript testing frameworks provide concepts like:

```ts
describe()
it()
expect()
```

### `describe()`

Groups related tests.

```ts
describe("calculateProgress", () => {
   // tests
});
```

Think:

```text
Test Suite
    ↓
calculateProgress
```

### `it()`

Defines one behavior.

```ts
it("returns 50 when half the lessons are completed", () => {
   // test
});
```

Think:

```text
Test Case
    ↓
Expected behavior
```

### `expect()`

Defines what you expect.

```ts
expect(result).toBe(50);
```

---

# 8. Test Behavior, Not Implementation

This is a **very important professional habit**.

Bad mindset:

> "I need to test every internal line."

Better mindset:

> "I need to verify that this function behaves correctly."

For example:

```ts
function calculateProgress(completed: number, total: number) {
  return Math.round((completed / total) * 100);
}
```

Your test should care about:

```text
Input → Output
```

not:

```text
Did Math.round() execute?
Did this variable have this name?
Did the developer use this exact implementation?
```

Why?

Because later you might rewrite the implementation:

```ts
return Math.floor(...)
```

or optimize it.

The behavior should remain the contract.

---

# 9. Happy Path vs Edge Cases

A beginner mistake is testing only the happy path.

For:

```ts
calculateProgress(5, 10)
```

you might test:

```text
50%
```

But what about:

```text
0 lessons
0 completed
total = 0
completed > total
negative values
```

For example:

```ts
calculateProgress(0, 10)
```

should probably be:

```text
0%
```

But:

```ts
calculateProgress(10, 0)
```

creates a problem.

You need to decide what your business rule should be.

Perhaps:

```ts
if (totalLessons === 0) {
  return 0;
}
```

Now your test can protect that decision.

---

# 10. Unit Tests Are Also Documentation

Consider this:

```ts
it("returns 0 when a course has no lessons", () => {
  expect(calculateProgress(0, 0)).toBe(0);
});
```

A developer reading this immediately learns:

> The LMS considers a course with zero lessons to have 0% progress.

So tests don't only detect bugs.

They also document expected behavior.

# 11. Testing Business Rules

This is where unit testing becomes especially valuable for backend development.

Imagine:

```ts
function canPublishCourse(course: Course): boolean {
  return (
    course.title.length > 0 &&
    course.lessons.length > 0 &&
    course.instructorId !== null
  );
}
```

We can test:

```text
No title
      ↓
Cannot publish

Title + no lessons
      ↓
Cannot publish

Title + lessons + instructor
      ↓
Can publish
```

This is much more valuable than testing simple getters/setters.

# 14. Testing Pyramid

Think of testing like this:

```text
              /\
             /  \
            / E2E\
           /------\
          /  API   \
         /----------\
        / Integration\
       /--------------\
      /   Unit Tests   \
     /------------------\
```

At the bottom:

```text
Many unit tests
```

Then:

```text
Fewer integration tests
```

Then:

```text
Fewer API/E2E tests
```

Why?

Because unit tests are generally:

```text
Fast
Cheap
Isolated
Easy to debug
```

# 15. Unit Testing in TypeScript

Since your project is TypeScript-based, your tests should also be TypeScript.

Example structure:

```text
src/
├── services/
│   └── course.service.ts
│
└── utils/
    └── progress.ts

tests/
└── unit/
    ├── course.service.test.ts
    └── progress.test.ts
```

Or you may keep tests close to the source:

```text
src/
└── utils/
    ├── progress.ts
    └── progress.test.ts
```

Both approaches are valid.

For your larger AI LMS, we'll choose a structure that works well with the monorepo and CI setup later.

# 17. A Better Example: Quiz Scoring

Your LMS will eventually have quizzes.

Suppose:

```ts
function calculateQuizScore(
  correctAnswers: number,
  totalQuestions: number
): number {
  if (totalQuestions === 0) {
    return 0;
  }

  return Math.round(
    (correctAnswers / totalQuestions) * 100
  );
}
```

Potential tests:

```text
5 / 5 → 100
4 / 5 → 80
3 / 5 → 60
0 / 5 → 0
0 / 0 → 0
```

But we should also ask:

```text
6 / 5 ?
-1 / 5 ?
5 / -2 ?
```

Should those be allowed?

That's where **business rules** come into play.

A good developer doesn't blindly write tests.

They first ask:

> "What behavior do we actually want?"

Then the test protects that behavior.

# 18. Tests Help You Refactor

Imagine you initially write:

```ts
function calculateQuizScore(correct: number, total: number) {
  return (correct / total) * 100;
}
```

Later you realize:

```text
Division by zero
Floating-point values
Invalid input
```

You improve it.

Your tests should still pass.

```text
Old implementation
       ↓
Tests
       ↓
Refactor
       ↓
Tests
       ↓
Still passing
```

This gives you confidence to improve the architecture.

That's one of the biggest benefits of testing.

# 19. What Makes a Good Unit Test?

A good unit test is generally:

### Fast

It should execute quickly.

### Isolated

It shouldn't depend on unrelated systems.

### Deterministic

Same input should produce the same expected result.

### Small

One behavior per test.

### Readable

Someone should understand why it exists.

### Reliable

It shouldn't randomly fail.

### Meaningful

It should protect useful behavior.

---

# 20. What Makes a Bad Unit Test?

Avoid tests that:

```text
❌ Depend on production database
❌ Call real AI APIs
❌ Depend on network
❌ Depend on current time without control
❌ Depend on random values
❌ Test implementation details
❌ Are extremely large
❌ Test multiple unrelated behaviors
```

For example:

```text
Test
 ↓
Real OpenAI API
 ↓
Network
 ↓
Database
 ↓
Redis
```

That's not a good unit test.

We'll learn how to isolate those dependencies later.

# 🧠 The Most Important Mental Model

Whenever you see a function, think:

```text
What is its contract?
```

For example:

```ts
calculateProgress(5, 10)
```

Contract:

```text
Input:
completed = 5
total = 10

Expected:
50
```

Then ask:

```text
What happens with 0?
What happens with invalid input?
What happens at boundaries?
What happens when dependencies fail?
```

This mindset will make you much better at testing.
