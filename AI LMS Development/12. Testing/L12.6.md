# 🔐 Lesson 12.6 — Authorization Testing

In **12.5**, we tested authentication:

> **“Who are you?”**

Now we test authorization:

> **“What are you allowed to do?”**

For your AI LMS, this is extremely important because we have different users:

```text
Student
Instructor
Admin
```

and they should not all have the same permissions.

The core flow is:

```text
Request
   ↓
Authentication
   ↓
Identify User
   ↓
Authorization
   ↓
Check Permission
   ↓
Allow / Deny
```

---

# 1. Authentication vs Authorization

Keep this distinction very clear.

### Authentication

```text
Who are you?
```

Example:

```text
Rahul
   ↓
Valid access token
   ↓
Authenticated
```

### Authorization

```text
What can Rahul do?
```

Example:

```text
Rahul = STUDENT
   ↓
Create Course?
   ↓
❌ No
```

So:

```text
Authentication
      ↓
Identity

Authorization
      ↓
Permissions
```

A user can be **authenticated but not authorized**.

---

# 2. Why Authorization Testing Matters

Imagine this endpoint:

```http
DELETE /api/v1/courses/:courseId
```

Suppose an instructor owns Course A.

A student somehow gets a valid token and calls:

```http
DELETE /api/v1/courses/course-a
```

If your API responds:

```text
200 OK
```

you have a serious authorization vulnerability.

The user is authenticated.

But they are **not authorized**.

Authorization testing catches this.

---

# 3. Your LMS Roles

Our simplified LMS has:

```text
STUDENT
INSTRUCTOR
ADMIN
```

Think about their permissions.

### Student

Usually:

```text
View courses
Enroll
Learn lessons
Submit quizzes
View own progress
Use AI tutor
```

### Instructor

Usually:

```text
Create courses
Update own courses
Manage lessons
View student progress for own courses
Create quizzes
```

### Admin

Usually:

```text
Manage users
Manage courses
Manage system settings
Moderate content
```

The exact permission matrix should follow the application's defined rules.

---

# 4. RBAC

One common authorization model is:

**RBAC = Role-Based Access Control**

Conceptually:

```text
User
  ↓
Role
  ↓
Permissions
```

For example:

```text
Student
   ↓
course.read
course.enroll
lesson.read

Instructor
   ↓
course.create
course.update
lesson.create
lesson.update

Admin
   ↓
user.manage
course.manage
system.manage
```

Authorization tests verify that these rules actually work.

---

# 5. Basic Authorization Test

Suppose:

```http
POST /api/v1/courses
```

is an instructor-only endpoint.

Test:

```text
Student
   ↓
POST /courses
   ↓
403 Forbidden
```

Then:

```text
Instructor
   ↓
POST /courses
   ↓
201 Created
```

This is the simplest authorization test.

---

# 6. Build a Permission Matrix

Before writing tests, create a matrix.

For example:

|Operation|Student|Instructor|Admin|
|---|--:|--:|--:|
|View published course|✅|✅|✅|
|Enroll|✅|Maybe|Admin policy|
|Create course|❌|✅|✅|
|Update own course|❌|✅|✅|
|Update another instructor's course|❌|❌|✅|
|Delete course|❌|Own only|✅|
|Manage users|❌|❌|✅|

The exact rules should come from your application design.

The important lesson is:

> **Write down authorization rules before writing authorization tests.**

Otherwise, tests can accidentally encode inconsistent permissions.

---

# 7. Authorization Test Structure

A useful test pattern is:

```text
Arrange
   ↓
Create user with role
   ↓
Create target resource
   ↓
Authenticate
   ↓
Act
   ↓
Call protected endpoint
   ↓
Assert
   ↓
Allowed / Forbidden
```

For example:

```text
Create Student
     ↓
Login
     ↓
POST /courses
     ↓
403
```

---

# 8. 401 vs 403

This distinction is extremely important.

### `401 Unauthorized`

Usually means:

> The request is not successfully authenticated.

Examples:

```text
No token
Invalid token
Expired token
```

```text
Request
   ↓
No valid identity
   ↓
401
```

### `403 Forbidden`

Usually means:

> The user is authenticated but doesn't have permission.

Example:

```text
Student
   ↓
Valid token
   ↓
POST /courses
   ↓
403
```

So:

```text
No valid identity
      ↓
401

Valid identity
+
Insufficient permission
      ↓
403
```

Your tests should protect this distinction.

---

# 9. Role-Based Testing

For every important protected endpoint, think:

```text
Anonymous
Student
Instructor
Admin
```

For example:

```http
POST /api/v1/courses
```

Test:

```text
Anonymous   → 401
Student     → 403
Instructor  → 201
Admin       → depends on policy
```

This creates a clear authorization test matrix.

---

# 10. Don't Test Only Roles

Authorization isn't only about roles.

Consider:

```text
Instructor A
Instructor B
```

Both have:

```text
role = INSTRUCTOR
```

But they don't necessarily have access to each other's courses.

This introduces:

> **Resource ownership.**

---

# 11. Resource Ownership

Imagine:

```text
Instructor A
   ↓
Course A

Instructor B
   ↓
Course B
```

Instructor A sends:

```http
PATCH /api/v1/courses/B
```

Even though:

```text
Instructor A = INSTRUCTOR
```

they should not automatically be allowed to modify Course B.

Expected:

```text
403 Forbidden
```

or another deliberately chosen response.

This is a very important authorization test.

---

# 12. IDOR / BOLA

This kind of vulnerability is often discussed as:

**IDOR — Insecure Direct Object Reference**

and in API security:

**BOLA — Broken Object Level Authorization**

The basic attack looks like:

```text
GET /api/v1/courses/course-A
```

works for the legitimate owner.

The attacker changes:

```text
course-A
```

to:

```text
course-B
```

and suddenly gets access to another user's resource.

Authorization tests should deliberately try this.

---

# 13. Example: Student Progress

Suppose:

```http
GET /api/v1/students/:studentId/progress
```

Student A should be able to see:

```text
/student-A/progress
```

but not:

```text
/student-B/progress
```

Test:

```text
Student A
   ↓
GET /student-B/progress
   ↓
❌
```

This is a classic object-level authorization test.

---

# 14. Never Trust IDs From the Client

A dangerous pattern is:

```ts
const { studentId } = req.params;

const progress = await progressService
  .getProgress(studentId);
```

If the server only checks:

```text
"Is this user logged in?"
```

then a user could potentially change:

```text
/student-A
```

to:

```text
/student-B
```

and access someone else's information.

Authorization should verify the relationship between:

```text
Authenticated user
       +
Requested resource
```

---

# 15. Ownership Authorization

Conceptually:

```text
Authenticated User
        ↓
        ID
        ↓
Resource
        ↓
ownerId
```

Then:

```text
user.id === resource.ownerId
```

might be part of the authorization decision.

For example:

```text
Instructor A
id = 101

Course
instructorId = 101
```

Allowed.

But:

```text
Instructor A
id = 101

Course
instructorId = 202
```

Denied.

---

# 16. Role + Ownership

Real applications often need both.

For example:

```text
Instructor
   +
Owns Course
   ↓
Can update
```

Whereas:

```text
Instructor
   +
Doesn't own Course
   ↓
Cannot update
```

And:

```text
Admin
   +
Any Course
   ↓
Can update
```

So authorization can become:

```text
Role
 +
Permission
 +
Resource ownership
```

This is why authorization testing is more complex than simply checking a role string.

---

# 17. Testing Admin Privileges

Admins have powerful permissions, so test them carefully.

For example:

```http
DELETE /api/v1/users/:id
```

Test:

```text
Student
   ↓
403

Instructor
   ↓
403

Admin
   ↓
Allowed
```

Also test:

```text
Admin token invalid
   ↓
401
```

A user shouldn't become an admin merely because they manipulate client-side data.

---

# 18. Never Trust the Frontend

This is a crucial backend security principle.

Suppose your React app hides a button:

```tsx
{user.role === "ADMIN" && (
  <DeleteUserButton />
)}
```

That is useful for UI.

But it is **not authorization**.

An attacker can directly call:

```http
DELETE /api/v1/users/123
```

without using your UI.

Therefore:

```text
Frontend
   ↓
UX restriction

Backend
   ↓
Actual authorization
```

Your tests should call the API directly.

---

# 19. Testing Client-Side Role Manipulation

Suppose a student changes:

```json
{
  "role": "ADMIN"
}
```

in browser state.

That should not change their actual backend permissions.

Test:

```text
Student token
   ↓
Modify client state
   ↓
Call admin API
   ↓
403
```

Why?

Because the server should derive authorization from trusted server-side identity data.

---

# 20. JWT Role Claims

You might eventually put something like:

```json
{
  "sub": "user-id",
  "role": "STUDENT"
}
```

inside a token.

Tests should ensure that the server validates the token properly.

An attacker should not be able to simply modify:

```text
role = STUDENT
```

to:

```text
role = ADMIN
```

and get access.

That connects authorization testing with the token-integrity testing from **12.5**.

---

# 21. Permission-Based Authorization

Instead of directly checking roles everywhere:

```ts
if (user.role === "ADMIN") {
  ...
}
```

larger systems often use permissions.

For example:

```text
course:create
course:update
course:delete
user:manage
```

Then:

```text
Instructor
   ↓
course:create
course:update

Admin
   ↓
course:create
course:update
course:delete
user:manage
```

This can make authorization more flexible.

---

# 22. Testing Permissions

Suppose:

```text
course:update
```

is required for updating a course.

Tests should verify:

```text
User with permission
       ↓
Allowed
```

and:

```text
User without permission
       ↓
403
```

This is especially useful if your system later grows beyond only three roles.

---

# 23. Testing Least Privilege

A good authorization system gives users only the permissions they need.

For example:

```text
Student
```

shouldn't automatically have:

```text
user:delete
course:delete
system:configure
```

Tests should verify that unnecessary privileges aren't accidentally granted.

Think:

```text
Minimum permissions
       ↓
Minimum attack surface
```

---

# 24. Privilege Escalation Testing

Privilege escalation means a user somehow obtains more permissions than they should have.

For example:

```text
Student
   ↓
Attempts instructor endpoint
   ↓
403
```

or:

```text
Instructor
   ↓
Attempts admin endpoint
   ↓
403
```

You should test both **vertical** and **horizontal** privilege escalation.

---

# 25. Vertical Privilege Escalation

Moving upward in privilege:

```text
Student
   ↓
Instructor
   ↓
Admin
```

Example:

```text
Student
   ↓
DELETE /admin/users
   ↓
403
```

That's vertical privilege escalation protection.

---

# 26. Horizontal Privilege Escalation

Same role, different resource.

```text
Instructor A
      ↓
Course B owned by Instructor B
      ↓
403
```

or:

```text
Student A
      ↓
Progress belonging to Student B
      ↓
403
```

This is often where BOLA/IDOR bugs appear.

---

# 27. Nested Resource Authorization

LMS APIs can have nested resources.

For example:

```http
PATCH /api/v1/courses/:courseId/lessons/:lessonId
```

Authorization must verify:

```text
User
 ↓
Course ownership
 ↓
Lesson belongs to Course
 ↓
Permission to modify
```

You shouldn't only check:

```text
lessonId
```

because an attacker might supply a valid lesson belonging to another course.

---

# 28. Example: Lesson Authorization

Suppose:

```text
Instructor A
   ↓
Course A
   ↓
Lesson A
```

Instructor B requests:

```http
PATCH /courses/A/lessons/A
```

The server should check:

```text
Is Instructor B authorized for Course A?
        ↓
No
        ↓
403
```

This prevents nested-resource authorization bugs.

---

# 29. Testing Delete Permissions

Deletion is especially dangerous.

Test:

```text
Student → DELETE Course
Instructor → DELETE another instructor's Course
Instructor → DELETE own Course
Admin → DELETE Course
```

Expected behavior should follow your authorization policy.

Also verify the **side effect**:

```text
Unauthorized request
       ↓
403
       ↓
Database unchanged
```

This is important.

It isn't enough to return `403`; the resource must actually remain untouched.

---

# 30. Testing Read Permissions

Authorization applies to reads too.

Developers sometimes protect:

```text
POST
PATCH
DELETE
```

but forget:

```text
GET
```

Example:

```http
GET /api/v1/users/:id/private-profile
```

A user shouldn't necessarily be able to retrieve another user's private information.

Test:

```text
User A
   ↓
GET User B private data
   ↓
403 / 404
```

according to the application's intended behavior.

---

# 31. Testing Update Permissions

Suppose:

```http
PATCH /api/v1/users/:id
```

A student should potentially be able to update:

```text
their own profile
```

but not:

```text
another user's role
```

So test:

```text
Student A
   ↓
PATCH Student A profile
   ↓
Allowed
```

but:

```text
Student A
   ↓
PATCH Student B role = ADMIN
   ↓
Rejected
```

This is a very important authorization boundary.

---

# 32. Testing Mass Assignment

Suppose the client sends:

```json
{
  "name": "Rahul",
  "role": "ADMIN"
}
```

The backend should not blindly update every provided field.

Authorization and input handling should ensure that a student can't promote themselves.

Test:

```text
Student
   ↓
PATCH /me
role = ADMIN
   ↓
Rejected / ignored
```

depending on the API design.

This is a great example of why validation and authorization work together.

---

# 33. Authorization and Database Queries

Sometimes the safest authorization check can happen directly in the database query.

Instead of:

```text
Find course
    ↓
Check owner
    ↓
Update
```

you may design a query equivalent to:

```text
Update course
WHERE
course.id = requestedCourse
AND
course.instructorId = authenticatedUser
```

Then:

```text
Rows affected = 0
```

can mean:

```text
Not found
or
Not authorized
```

depending on the API design.

This approach can reduce race conditions and accidental authorization gaps.

---

# 34. Authorization and Race Conditions

Consider:

```text
Request A
   ↓
Check ownership
   ↓
Allowed

Request B
   ↓
Resource ownership changes

Request A
   ↓
Update resource
```

Authorization checks should be designed carefully so that there isn't a gap between:

```text
Check
```

and:

```text
Action
```

Database-level conditions and transactions can help.

This connects authorization testing to the database and transaction testing from **12.4**.

---

# 35. Testing Authorization Middleware

You may have middleware such as:

```text
requireAuth()
requireRole()
requirePermission()
```

You can unit-test these individually:

```text
Student
   ↓
requireRole(INSTRUCTOR)
   ↓
403
```

But you should also API-test them:

```text
Student token
   ↓
POST /courses
   ↓
403
```

Both layers are useful.

---

# 36. Authorization Test Matrix

For an instructor-only endpoint:

```text
POST /courses
```

you might have:

|Identity|Expected|
|---|--:|
|No token|401|
|Invalid token|401|
|Student|403|
|Instructor|201|
|Admin|Depends on policy|

For:

```text
PATCH /courses/:id
```

you could have:

|User|Resource|Expected|
|---|---|--:|
|Student A|Course A|403|
|Instructor A|Course A|Allowed|
|Instructor B|Course A|403|
|Admin|Course A|Allowed|

This is exactly the kind of matrix we want in automated tests.

---

# 37. Authorization Test Naming

Make test names describe the security rule.

Good:

```text
allows instructors to update their own courses
```

```text
rejects students from creating courses
```

```text
rejects instructors from updating another instructor's course
```

```text
prevents students from viewing another student's private progress
```

Bad:

```text
test role
test permissions
test course
```

The first style becomes living security documentation.

In **12.3**, we tested:


Now we ask:

```text

```

So:



# 39. Authorization Testing and Authentication

Remember:

```text
Authentication
      ↓
Who is this?
```

Then:

```text
Authorization
      ↓
What can they do?
```

The complete security chain becomes:

```text
HTTP Request
      ↓
Authentication
      ↓
User Identity
      ↓
Authorization
      ↓
Permission
      ↓
Resource Ownership
      ↓
Business Operation
      ↓
Database
```

A failure at any authorization stage should prevent the operation.

# 40. Example: Complete Course Update Test

Let's design one.

### Scenario

Instructor A owns Course A.

```text

      ↓

```

Test:

```text

  ↓
Create Instructor A
Create Instructor B
Create Course A owned by A
Generate tokens

Act
  ↓
Instructor B
PATCH /courses/A

Assert
  ↓
403

Verify
  ↓

```

This is an excellent authorization test because it checks:

```text

+
Ownership
+
API behavior
+
Database side effect
```

```text
   ↓
```

But perhaps:


# 42. Authorization Testing for Instructor Analytics

Suppose:

```http
GET /api/v1/instructor/courses/:courseId/students
```

Instructor A should see students enrolled in:

```text
Course A
```

but not:

```text
Course B
```

owned by Instructor B.

Test:

```text
Instructor A
    ↓
Course B analytics
    ↓
403 / 404
```

This is particularly important because analytics may contain sensitive student information.

---

# 43. Authorization Testing for Admin APIs

Admin APIs are especially sensitive.

For example:

```text
GET /admin/users
DELETE /admin/users/:id
PATCH /admin/users/:id/role
```

Test all non-admin roles.

```text
Student
   ↓
❌

Instructor
   ↓
❌

Admin
   ↓
✅
```

Also test that a normal user cannot modify their own role to become admin.

---

# 44. Don't Depend on UI Authorization

Remember this rule:

```text
UI authorization
      ≠
Backend authorization
```

Your frontend might display:

```text
Admin Dashboard
```

only for admins.

But the backend must still protect:

```text
/api/v1/admin/*
```

because users can directly call the endpoint.

Your automated tests should bypass the UI and directly attack the API.

---

# 45. Common Authorization Testing Mistakes

### ❌ Testing only role-based permissions

You must also test ownership.

### ❌ Testing only write operations

Read operations can leak sensitive information.

### ❌ Trusting frontend role checks

Frontend checks are not security boundaries.

### ❌ Returning 200 for denied operations

Use your defined authorization error contract.

### ❌ Returning 403 but still changing the database

Always verify side effects.

### ❌ Checking authorization only once

Nested resources and related objects may need additional checks.

### ❌ Trusting client-provided user IDs

Derive identity from authenticated server-side context.

---

# 46. Authorization Test Pyramid

You can think about authorization testing like:

```text
                  Authorization
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
        Roles       Ownership    Permissions
          │            │            │
          └────────────┼────────────┘
                       ↓
                Protected APIs
                       ↓
                 Database state
```

The strongest tests verify both:

```text
Response
+
Side effect
```

---

# 🧠 Most Important Mental Model

Whenever you test a protected resource, ask **four questions**:

```text
1. Who is making the request?
            ↓
2. What role/permissions do they have?
            ↓
3. What resource are they trying to access?
            ↓
4. Are they allowed to perform this action on that resource?
```

For example:

```text
Instructor B
     ↓
INSTRUCTOR
     ↓
Course A
     ↓
Course A belongs to Instructor A
     ↓
❌ DENY
```

This mental model will prevent a huge number of authorization mistakes.
