# 🤖 Lesson 12.7 — AI Service Testing

Now we enter the **AI-specific part of Phase 12**.

So far, we've tested:

```text
12.1  Unit Testing
12.2  Integration Testing
12.3  API Testing
12.4  Database Testing
12.5  Authentication Testing
12.6  Authorization Testing
12.7  AI Service Testing  ← YOU ARE HERE
```

Your AI LMS has a special problem:

> Traditional software usually expects the same input to produce the same output. LLMs don't always behave that way.

For example:

```text
Question:
"What is a binary search?"

LLM response A:
"Binary search is an algorithm..."

LLM response B:
"Binary search is a searching technique..."

LLM response C:
"Imagine a sorted dictionary..."
```

All three could be correct.

Therefore, we **cannot test AI systems exactly like ordinary deterministic functions**.

---

# 1. What Is AI Service Testing?

Your application may have an AI service like:

```text
Student
   ↓
AI Tutor API
   ↓
AI Service
   ↓
Prompt Builder
   ↓
LLM Provider
   ↓
AI Response
```

We need to verify that **our AI integration behaves correctly**.

We're not trying to prove:

> "The LLM will always produce this exact sentence."

Instead, we're testing things such as:

```text
Input handling
Prompt construction
Provider communication
Output structure
Error handling
Timeouts
Retries
Token limits
Usage limits
Fallback behavior
```

---

# 2. Why AI Testing Is Different

Consider a normal function:

```ts
function add(a: number, b: number) {
  return a + b;
}
```

We can confidently test:

```text
2 + 3 → 5
```

But with an LLM:

```text
"What is React?"
```

there can be many valid answers.

Therefore:

```text
Traditional Testing
       ↓
Exact expected output

AI Testing
       ↓
Expected behavior / properties
```

This is one of the most important concepts in AI testing.

# 5. The Biggest Rule: Don't Call a Real LLM in Every Unit Test

Imagine you have:

```text
500 AI tests
```

and every test calls:

```text
Your API
   ↓
OpenAI / another provider
   ↓
Internet
   ↓
LLM
```

This creates problems:

```text
Slow
Expensive
Non-deterministic
Rate-limited
Hard to debug
Dependent on network
```

Instead:

```text
Test
 ↓
AI Service
 ↓
Mock AI Provider
 ↓
Fake Response
```

This gives us fast and deterministic tests.

---

# 6. Mock the Provider, Not Your AI Logic

This distinction is extremely important.

Suppose your service does:

```text
AI Service
   ↓
Build prompt
   ↓
Call provider
   ↓
Parse response
   ↓
Return result
```

We don't want to mock the entire AI service.

Instead:

```text
AI Service
   ↓
Real logic
   ↓
Mock provider
```

Then we're actually testing **our code**.

For example:

```text
Real:
Prompt Builder
Response Parser
Error Handling
Retry Logic

Mock:
External LLM API
```

# 11. Don't Test the LLM's Exact Wording

Suppose the model returns:

```text
"Binary search works on sorted data because..."
```

Don't write:

```ts
expect(response).toBe(
  "Binary search works on sorted data because..."
);
```

That is fragile.

Instead test properties such as:

```text
Response exists
Response is a string
Response is not empty
Response contains required structured fields
```

And where appropriate:

```text
Response satisfies expected constraints
```

# 12. Structured AI Output

Structured output makes AI testing much easier.

Suppose your quiz generator should return:

```json
{
  "question": "What is binary search?",
  "options": [
    "A searching algorithm",
    "A sorting algorithm",
    "A database",
    "A programming language"
  ],
  "answer": 0,
  "explanation": "..."
}
```

Instead of accepting arbitrary text, your service can validate the response.

Conceptually:

```text
LLM
 ↓
JSON
 ↓
Schema validation
 ↓
Valid?
 ├── Yes → Continue
 └── No  → Reject / Retry
```

This is much easier to test than completely free-form output.

# 13. AI Response Schema Testing

Suppose the expected structure is:


Test:

```text
All required fields exist
Correct data types
Answer is valid
```

For example:

```text

```

The AI service should not blindly trust model output.

# 14. Test Invalid AI Responses

LLMs can sometimes produce malformed output.

For example:

```json
{
  "question": "What is React?"
}
```

but:

```text

answer missing
```

Your application should handle this safely.

Test:

```text
LLM returns invalid structure
       ↓
Schema validation fails
       ↓
Controlled error / retry
```

Not:

```text
LLM returns invalid structure
       ↓
Application crashes
       ↓
500
```

unless that is explicitly your chosen behavior.

# 16. Testing Timeouts

Imagine:

```text
Student
   ↓
AI Tutor
   ↓
Provider
   ↓
... waiting ...
```

You don't want your API hanging indefinitely.

You might define:

```text
Provider timeout = 10 seconds
```

Then:

```text
Provider doesn't respond
       ↓
Timeout
       ↓
AI service handles error
```

A test should simulate the timeout.

You should **not actually wait ten seconds** for every test.

Use a fake/mocked provider that immediately behaves as if it timed out.

# 18. Don't Retry Everything

Some errors shouldn't be retried.

For example:

```text
Invalid API key
Invalid request
Invalid prompt format
```

Retrying these repeatedly won't help.

Whereas:

```text
Temporary network failure
503
429
```

might be retryable.

Your tests should protect this distinction.

Conceptually:

```text
Error
 │
 ├── Retryable
 │      ↓
 │    Retry
 │
 └── Non-retryable
        ↓
      Fail
```

---

# 19. Exponential Backoff

When retrying, you may eventually use:

```text
Attempt 1 → 100ms
Attempt 2 → 200ms
Attempt 3 → 400ms
Attempt 4 → 800ms
```

or another appropriate strategy.

The exact numbers depend on your system.

For unit tests, don't actually wait.

Instead, test that:

```text
Retry count is correct
Backoff strategy is invoked correctly
Retries stop after maximum attempts
```

Use controlled/fake time where appropriate.

# 48. Common AI Testing Mistakes

### ❌ Calling the real LLM in every test

Expensive and unreliable.

### ❌ Comparing exact AI text

Too fragile.

### ❌ Trusting model output

Always validate important structured output.

### ❌ Ignoring provider failures

External services fail.

### ❌ Infinite retries

Can cause huge costs.

### ❌ Ignoring token limits

Large inputs can break requests or increase costs.

### ❌ Testing only successful responses

Failure behavior is critical.

### ❌ Mixing RAG evaluation with basic service tests

Keep concerns separated.

# 🧠 Most Important Mental Model

For normal software:

```text
Input
 ↓
Function
 ↓
Exact Output
```

For AI services:

```text
Input
 ↓
Our AI Service
 ↓
External Model
 ↓
Variable Output
```

Therefore:

```text
Test what WE control.
```

We control:

```text
Validation
Prompt construction
Provider invocation
Configuration
Parsing
Schema validation
Retries
Timeouts
Usage limits
Error mapping

```

We don't completely control:

```text

```

That's the key difference.

# 🎯 Lesson 12.7 Summary

AI service testing is mainly about testing **your AI engineering**, not trying to make an LLM deterministic.

You should now understand:

```text
✅ AI service testing
✅ Mocking AI providers
✅ Fake providers
✅ Prompt construction testing
✅ Structured output validation
✅ Invalid AI responses
✅ Provider error handling
✅ Timeout testing
✅ Retry testing
✅ Rate-limit handling
✅ Token/context limits
✅ AI usage limits
✅ Provider fallback
✅ Conversation context testing
✅ Sensitive-data protection
```

The core architecture should eventually look like:

```text
                    AI SERVICE
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
      Validation     Prompt        Parsing
          │          Builder          │
          └─────────────┬─────────────┘
                        ↓
                  AI Provider
                        ↓
                   Fake in Tests
                        ↓
               Controlled Response
```

And remember:

> **Don't test whether the LLM says the exact sentence you expected. Test whether your application handles the LLM correctly.**

For your AI LMS, that's a much more robust approach.
