# Lesson 13.10 — Production Docker Image 🐳

In **13.9**, we made testing part of CI.

Now we move to the next important step:

> **How do we turn our TypeScript/Node.js backend into a clean production Docker image?**

Our target is:

```text
Source Code
    ↓
npm ci
    ↓
TypeScript Build
    ↓
Production Dependencies
    ↓
Small Docker Image
    ↓
Run as non-root user
    ↓
Production Container
```

For your AI LMS backend, we want to avoid carrying unnecessary development tools into production.

---

# 1. Development Image vs Production Image

A development container might contain:

```text
TypeScript
tsx
ESLint
Vitest
Source code
Hot reload
Development dependencies
```

That's useful while building.

But production doesn't need most of that.

Production should ideally contain:

```text
Compiled JavaScript
Production dependencies
Prisma runtime files
Required configuration
Node.js runtime
```

Think:

```text
Development
   ↓
Everything needed to develop

Production
   ↓
Only what's needed to run
```

---

# 2. Why Production Images Should Be Smaller

Suppose your development environment contains:

```text
TypeScript
ESLint
Vitest
Testing libraries
Source maps
Source code
Development tooling
```

There's no reason to ship all of that to production.

A smaller image generally means:

```text
Smaller image
     ↓
Faster pull
     ↓
Faster deployment
     ↓
Less storage
     ↓
Smaller attack surface
```

This is one reason multi-stage Docker builds are so useful.

---

# 3. Multi-Stage Docker Builds

The main concept:

```text
Stage 1: Build
        ↓
Compile TypeScript

Stage 2: Production
        ↓
Copy only required output
```

Architecture:

```text
┌─────────────────────┐
│    Builder Stage    │
│                     │
│ Node.js             │
│ npm                 │
│ TypeScript          │
│ Dev dependencies    │
│ Source code         │
│                     │
│ npm run build       │
└──────────┬──────────┘
           │
           │ compiled output
           ↓
┌─────────────────────┐
│   Production Stage  │
│                     │
│ Node.js             │
│ Production deps     │
│ Compiled JS         │
│ Prisma              │
└─────────────────────┘
```

The first stage doesn't become the final image.

---

# 4. Why Not Just Use One Stage?

You could do:

```dockerfile
FROM node:22
WORKDIR /app

COPY . .
RUN npm install
RUN npm run build

CMD ["npm", "start"]
```

It may work.

But now your production image may contain:

```text
TypeScript source
Development dependencies
Tests
ESLint
Git metadata
Other unnecessary files
```

That's not ideal.

Multi-stage builds let us separate:

```text
Build environment
```

from:

```text
Runtime environment
```

---

# 5. Our Production Dockerfile

A basic multi-stage Dockerfile:

```dockerfile
FROM node:22-bookworm-slim AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM node:22-bookworm-slim AS production

WORKDIR /app

ENV NODE_ENV=production

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist

CMD ["node", "dist/server.js"]
```

This is our starting point.

We'll improve it further.

---

# 6. Understand the Builder Stage

The first line:

```dockerfile
FROM node:22-bookworm-slim AS builder
```

creates the build stage.

We name it:

```text
builder
```

So later we can say:

```dockerfile
COPY --from=builder
```

---

# 7. Why `bookworm-slim`?

We're using:

```text
node:22-bookworm-slim
```

instead of a full Debian-based image.

The `slim` image contains fewer unnecessary packages.

Conceptually:

```text
node:22
   ↓
Larger

node:22-bookworm-slim
   ↓
Smaller
```

For production, smaller is often preferable.

---

# 8. `WORKDIR`

```dockerfile
WORKDIR /app
```

Everything now happens inside:

```text
/app
```

So:

```dockerfile
COPY package*.json ./
```

means:

```text
Host
 ↓
/app/package.json
/app/package-lock.json
```

---

# 9. Copy Package Files First

This is important:

```dockerfile
COPY package*.json ./
RUN npm ci
```

instead of:

```dockerfile
COPY . .
RUN npm ci
```

Why?

Docker caching.

Suppose you change:

```text
src/course.service.ts
```

but don't change:

```text
package.json
package-lock.json
```

Docker can reuse the dependency installation layer.

Conceptually:

```text
package.json unchanged
       ↓
npm ci layer cached
       ↓
Build faster
```

---

# 10. Docker Layer Caching

Think of:

```dockerfile
COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build
```

as:

```text
Layer 1
package files

Layer 2
npm dependencies

Layer 3
source code

Layer 4
build output
```

If source code changes:

```text
Layer 1 → cached
Layer 2 → cached
Layer 3 → changed
Layer 4 → rebuild
```

This can significantly speed up builds.

---

# 11. `npm ci`

The builder uses:

```dockerfile
RUN npm ci
```

This installs the complete dependency tree:

```text
Production dependencies
+
Development dependencies
```

Why?

Because we need development tools to compile TypeScript:

```text
TypeScript
Prisma CLI
ESLint
etc.
```

depending on your project.

---

# 12. Copy Source Code

Then:

```dockerfile
COPY . .
```

Now the builder contains:

```text
/app
├── package.json
├── package-lock.json
├── src/
├── prisma/
├── tsconfig.json
└── ...
```

---

# 13. Build TypeScript

Then:

```dockerfile
RUN npm run build
```

Assuming:

```json
{
  "scripts": {
    "build": "tsc"
  }
}
```

TypeScript compiles:

```text
src/
 ↓
dist/
```

For example:

```text
src/server.ts
      ↓
dist/server.js
```

---

# 14. Production Stage

Now:

```dockerfile
FROM node:22-bookworm-slim AS production
```

This starts a completely new image stage.

It does **not** inherit all the files from the builder automatically.

That's the key advantage.

---

# 15. Production Environment

We set:

```dockerfile
ENV NODE_ENV=production
```

This tells Node/npm and your application:

```text
Production mode
```

Remember:

```text
Development
Test
Production
```

are separate environments.

---

# 16. Production Dependencies

Then:

```dockerfile
COPY package*.json ./

RUN npm ci --omit=dev
```

This installs only production dependencies.

Conceptually:

```text
Builder
 ├── dependencies
 └── devDependencies

Production
 └── dependencies
```

So things like:

```text
Vitest
ESLint
TypeScript
```

don't need to be included if they're only development dependencies.

---

# 17. Copy Compiled Application

Now:

```dockerfile
COPY --from=builder /app/dist ./dist
```

This is the important multi-stage operation.

We're saying:

> Take `/app/dist` from the builder stage and copy it into the production stage.

The final image might look like:

```text
/app
├── node_modules/
├── package.json
├── package-lock.json
└── dist/
    ├── server.js
    ├── controllers/
    ├── services/
    └── ...
```

---

# 18. Why Don't We Copy `src/`?

Because production runs compiled JavaScript.

Instead of:

```text
src/
 ↓
TypeScript
 ↓
runtime compilation
```

we want:

```text
dist/
 ↓
JavaScript
 ↓
Node.js
```

Production doesn't need TypeScript compilation.

---

# 19. Start Command

Finally:

```dockerfile
CMD ["node", "dist/server.js"]
```

Docker starts:

```text
node
 ↓
dist/server.js
```

This is preferable to running:

```text
tsx
```

in production.

---

# 20. Why Not `npm run dev`?

Never use:

```dockerfile
CMD ["npm", "run", "dev"]
```

for production.

Development usually means:

```text
Watch files
Hot reload
tsx
Verbose debugging
```

Production should be:

```text
Compiled JS
Stable process
Production configuration
```

---

# 21. `.dockerignore`

We also need:

```text
.dockerignore
```

Example:

```text
node_modules
npm-debug.log
.git
.gitignore
.env
.env.*
!.env.example
coverage
tests
Dockerfile*
compose*.yaml
README.md
```

The exact list should match what your application actually needs.

---

# 22. Why `.dockerignore` Matters

Without `.dockerignore`:

```dockerfile
COPY . .
```

could send:

```text
node_modules/
.git/
coverage/
.env
tests/
```

into the Docker build context.

That's wasteful.

With `.dockerignore`:

```text
Source
 ↓
Filtered
 ↓
Docker build context
```

This improves:

```text
Build speed
Image hygiene
Security
```

---

# 23. Important: `.dockerignore` and Secrets

You should ensure:

```text
.env
```

is not copied into the image.

Remember our earlier principle:

```text
Secrets
   ↓
Runtime configuration
```

not:

```text
Secrets
   ↓
Docker image
```

So:

```text
.env
```

should normally be excluded.

---

# 24. Runtime Environment Variables

Your application can still receive:

```text
DATABASE_URL
REDIS_URL
JWT_SECRET
AI_API_KEY
```

at runtime.

For example:

```bash
docker run \
  -e DATABASE_URL="..." \
  -e REDIS_URL="..." \
  -e JWT_SECRET="..." \
  ai-lms-api:1.0.0
```

The image doesn't contain the actual secret values.

---

# 25. Build-Time vs Runtime Configuration

This distinction is extremely important.

### Build time

```text
docker build
```

creates:

```text
Image
```

### Runtime

```text
docker run
```

provides:

```text
Environment
Secrets
Configuration
```

Think:

```text
Build
  ↓
Immutable image

Run
  ↓
Environment-specific configuration
```

---

# 26. Don't Do This

Avoid:

```dockerfile
ENV DATABASE_URL=postgresql://...
ENV JWT_SECRET=super-secret
```

That bakes values into the image.

Instead:

```dockerfile
ENV NODE_ENV=production
```

is okay because it's not a secret.

Sensitive configuration should come from runtime.

---

# 27. Prisma and Docker

Your AI LMS uses Prisma.

This introduces an important issue.

The production container needs the Prisma runtime generated for your application.

Typically your project has:

```text
prisma/
├── schema.prisma
└── migrations/
```

and Prisma Client generated during installation/build.

Your project should have a suitable:

```json
{
  "scripts": {
    "build": "prisma generate && tsc"
  }
}
```

or an equivalent generation step.

The exact setup depends on your Prisma version and schema.

---

# 28. Prisma Client Generation

Conceptually:

```text
schema.prisma
      ↓
prisma generate
      ↓
Prisma Client
      ↓
Application
```

If Prisma Client hasn't been generated, your application may fail at runtime.

So verify that your build process generates it.

For example:

```bash
npx prisma generate
npm run build
```

or:

```json
{
  "scripts": {
    "build": "prisma generate && tsc"
  }
}
```

---

# 29. Should `prisma/` Be Copied to Production?

This depends on how you handle migrations.

For runtime:

```text
Prisma Client
```

is required.

For deployment:

```text
prisma/migrations
```

is often needed when you run:

```bash
npx prisma migrate deploy
```

Therefore, don't blindly exclude the entire `prisma/` directory from the production image if your deployment strategy expects migrations to run from the container.

A common approach is:

```dockerfile
COPY prisma ./prisma
```

in the production stage.

---

# 30. Production Dockerfile With Prisma

A more realistic version:

```dockerfile
FROM node:22-bookworm-slim AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY prisma ./prisma
COPY tsconfig.json ./
COPY src ./src

RUN npx prisma generate
RUN npm run build


FROM node:22-bookworm-slim AS production

WORKDIR /app

ENV NODE_ENV=production

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules/.prisma ./node_modules/.prisma
COPY --from=builder /app/node_modules/@prisma ./node_modules/@prisma
COPY --from=builder /app/prisma ./prisma

CMD ["node", "dist/server.js"]
```

However, whether the explicit Prisma generated directories are needed depends on your Prisma setup and package installation behavior.

In many setups, running the appropriate Prisma generation step in the production dependency installation stage can make the Dockerfile cleaner.

So treat the above as a learning example, not a universal copy-paste.

---

# 31. Better Prisma Installation Strategy

You can structure the production stage like:

```dockerfile
FROM node:22-bookworm-slim AS production

WORKDIR /app

ENV NODE_ENV=production

COPY package*.json ./
COPY prisma ./prisma

RUN npm ci --omit=dev
RUN npx prisma generate

COPY --from=builder /app/dist ./dist

CMD ["node", "dist/server.js"]
```

This can be easier to reason about.

The production stage now has:

```text
package.json
package-lock.json
prisma/
production dependencies
generated Prisma Client
dist/
```

---

# 32. Why Run Prisma Generate in Production?

Because the production container needs the generated client.

The flow:

```text
schema.prisma
    ↓
prisma generate
    ↓
Prisma Client
    ↓
Node.js application
```

This is different from:

```text
prisma migrate deploy
```

Remember:

### Generate

```text
Create Prisma Client
```

### Migrate deploy

```text
Apply database migrations
```

They're different operations.

---

# 33. Production Container User

Now we reach an important security improvement.

By default, some containers may run as:

```text
root
```

We don't want our application process to unnecessarily run as root.

Instead:

```text
Node.js
 ↓
non-root user
```

This reduces the impact if the application is compromised.

---

# 34. Node Official Image User

The Node official images provide a `node` user.

We can use:

```dockerfile
USER node
```

Then:

```dockerfile
CMD ["node", "dist/server.js"]
```

runs as the non-root user.

---

# 35. Ownership Problem

If we copy files as root and then switch:

```dockerfile
USER node
```

the `node` user may not have permission to access certain files.

That's why ownership matters.

A useful pattern is:

```dockerfile
COPY --chown=node:node ...
```

For example:

```dockerfile
COPY --chown=node:node --from=builder /app/dist ./dist
```

---

# 36. Production Dockerfile With Non-Root User

A cleaner example:

```dockerfile
FROM node:22-bookworm-slim AS builder

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY prisma ./prisma
COPY tsconfig.json ./
COPY src ./src

RUN npx prisma generate
RUN npm run build


FROM node:22-bookworm-slim AS production

WORKDIR /app

ENV NODE_ENV=production

COPY package*.json ./
COPY prisma ./prisma

RUN npm ci --omit=dev
RUN npx prisma generate

COPY --chown=node:node --from=builder /app/dist ./dist

USER node

CMD ["node", "dist/server.js"]
```

This is much closer to a production-oriented image.

---

# 37. Why Run `npm ci` Before `USER node`?

Because installing packages may require filesystem permissions.

We can perform installation as root during image construction:

```text
Build stage
    ↓
Install

Production stage
    ↓
Install

Then:
USER node
```

The application process itself runs as:

```text
node
```

not root.

# 40. Health Checks

A production service should ideally expose a health endpoint.

For example:

```text
GET /health
```

Response:

```json
{
  "status": "ok"
}
```

Then the container/orchestrator can determine whether the application is responding.

---

# 41. Liveness vs Readiness

These concepts become important later.

### Liveness

> Is the application process alive?

```text
GET /health/live
```

### Readiness

> Is the application ready to serve traffic?

```text
GET /health/ready
```

Readiness might check:

```text
Database
Redis
Required dependencies
```

For example:

```text
Application
   ↓
Database available?
   ↓
Redis available?
   ↓
Ready
```

Don't make liveness checks unnecessarily dependent on every external service.

---

# 42. Docker `HEALTHCHECK`

Docker supports:

```dockerfile
HEALTHCHECK
```

For example:

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/health').then(r => { if (!r.ok) process.exit(1) }).catch(() => process.exit(1))"
```

This can work if your Node version supports the required `fetch` behavior.

But don't blindly add health checks before your `/health` endpoint exists.

```ts
app.get("/health", (_req, res) => {
  res.status(200).json({
    status: "ok",
  });
```

Then:


# 44. Graceful Shutdown

Production containers also need graceful shutdown.

When Docker stops the container:

```text
SIGTERM
   ↓
Application
   ↓
Stop accepting new requests
   ↓
Finish existing work
   ↓
Close Redis
   ↓
Close database
   ↓
Exit
```

Your Node server should handle shutdown signals.

Conceptually:

```ts
process.on("SIGTERM", async () => {
  await server.close();
  await redis.quit();
  await prisma.$disconnect();

  process.exit(0);
});
```

The exact implementation depends on your server architecture.

---

# 45. Why Graceful Shutdown Matters

Without it:

```text
Container stopping
      ↓
Request interrupted
      ↓
Job interrupted
      ↓
Connection abruptly closed
```

With graceful shutdown:

```text
SIGTERM
 ↓
Cleanup
 ↓
Finish
 ↓
Exit
```

This becomes important when deploying new versions.

---

# 46. One Process Per Container

A common container principle is:

```text
One main application process
```

For our backend:

```text
Container
   ↓
Node.js API
```

Don't put:

```text
Node API
+
PostgreSQL
+
Redis
```

inside one production container.

Instead:

```text
API Container
PostgreSQL
Redis
```

are separate services.

---

# 47. Why Separate Services?

Because each service has a different responsibility:

```text
API
 ↓
Application logic

PostgreSQL
 ↓
Persistent data

Redis
 ↓
Cache / temporary data
```

They can be:

```text
Scaled separately
Restarted separately
Monitored separately
Updated separately
```

This is one of the fundamental container architecture principles.

---

# 48. Production Image Should Be Immutable

Once built:

```text
ai-lms-api:abc1234
```

we ideally don't modify it.

Instead:

```text
Build image
   ↓
Test image
   ↓
Deploy same image
```

Don't:

```text
Build
 ↓
Deploy
 ↓
SSH into container
 ↓
Modify files manually
```

That's not reproducible.

---

# 49. Immutable Deployment

Think:

```text
Git Commit
    ↓
Docker Image
    ↓
Registry
    ↓
Production
```

If something goes wrong:

```text
Production
 ↓
Previous image
 ↓
Rollback
```

This becomes extremely powerful.

---

# 50. Image Tags

You might eventually use:

```text
ai-lms-api:latest
```

but don't rely only on `latest`.

Better:

```text
ai-lms-api:a84f21c
```

where:

```text
a84f21c
```

is the Git commit SHA.

You could also use release tags:

```text
ai-lms-api:v1.0.0
```

This makes deployments traceable.

---

# 51. Why `latest` Can Be Dangerous

Imagine:

```text
Production
 ↓
ai-lms-api:latest
```

Then a new image replaces `latest`.

Now:

```text
What exactly is production running?
```

It's less explicit.

With:

```text
ai-lms-api:a84f21c
```

you know exactly which commit is deployed.

Think:


# 🧠 Lesson 13.10 Summary

Remember these concepts.

### 1. Multi-stage builds

```text
Builder
  ↓
Compile
  ↓
Production image
```

### 2. Production image should be minimal

```text
No unnecessary dev tools
No tests
No source TypeScript
No secrets
```

### 3. Build dependencies and runtime dependencies are different

```text
Builder
→ dev + production dependencies

Production
→ production dependencies
```

### 4. Use `.dockerignore`

```text
.env
node_modules
.git
coverage
tests
```

when they aren't needed in the build context.

### 5. Secrets belong at runtime

```text
Image
 +
Runtime configuration
 =
Container
```

### 6. Don't run production as root

```text
USER node
```

is a useful security improvement.

### 7. Prisma needs special attention

```text
prisma generate
```

creates Prisma Client.

```text
prisma migrate deploy
```

applies migrations.

They are different.

### 8. Docker image should be immutable

```text
Commit
 ↓
Image
 ↓
Deploy
```

Don't manually modify running containers.

### 9. Tag images meaningfully

Prefer:

```text
ai-lms-api:a84f21c
```

or:

```text
ai-lms-api:v1.0.0
```

over relying only on:

```text
ai-lms-api:latest
```
