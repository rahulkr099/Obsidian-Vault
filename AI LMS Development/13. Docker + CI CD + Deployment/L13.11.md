# Lesson 13.11 — Container Registry & Deployment 🚀

In **13.10**, we created a production-ready Docker image.

Now we need to answer:

> **How does that Docker image get from GitHub Actions onto a production server?**

The production flow becomes:

```text
Developer
    ↓
git push
    ↓
GitHub
    ↓
GitHub Actions
    ↓
Test
    ↓
Build Docker Image
    ↓
Push Image to Registry
    ↓
Production Server
    ↓
Pull Image
    ↓
Run Container
```

This is one of the most important DevOps concepts in Phase 13.

---

# 1. What Is a Container Registry?

A container registry is a place where Docker images are stored.

Think of it like:

```text
GitHub
   ↓
stores source code

Container Registry
   ↓
stores Docker images
```

For example:

```text
Source:
github.com/your-user/ai-lms

Image:
registry.example.com/your-user/ai-lms-api
```

The registry becomes the bridge between:

```text
CI
```

and:

```text
Production
```

---

# 2. Why Do We Need a Registry?

Suppose GitHub Actions builds:

```text
ai-lms-api:abc123
```

Where does the production server get it from?

We don't want:

```text
Developer laptop
      ↓
SSH
      ↓
Copy Docker image manually
```

Instead:

```text
GitHub Actions
      ↓
Container Registry
      ↓
Production Server
```

The registry becomes the central image store.

---

# 3. Common Container Registries

Some popular options are:

- GitHub Container Registry — GHCR
    
- Docker Hub
    
- Amazon Elastic Container Registry — ECR
    
- Google Artifact Registry
    
- Azure Container Registry
    

For learning our AI LMS deployment pipeline, **GitHub Container Registry (GHCR)** is a convenient choice because the source repository and container images can live within the GitHub ecosystem.

# 5. Image Naming

A container image has several important pieces.

For example:

```text
ghcr.io/username/ai-lms-api:abc1234
```

Break it down:

```text
ghcr.io
   ↓
Registry

username
   ↓
Owner / namespace

ai-lms-api
   ↓
Image name

abc1234
   ↓
Tag
```

---

# 6. What Is a Tag?

A tag identifies a particular version of an image.

Examples:

```text
ai-lms-api:latest
ai-lms-api:v1.0.0
ai-lms-api:v1.2.0
ai-lms-api:abc1234
```

The most useful tag for CI/CD is often a commit SHA.

For example:

```text
ai-lms-api:8f42a91
```

This tells us:

> This image was created from Git commit `8f42a91`.

---

# 7. Why Commit SHA Tags Are Powerful

Imagine:

```text
Commit A
 ↓
Image A

Commit B
 ↓
Image B

Commit C
 ↓
Image C
```

Production can run:

```text
ai-lms-api:C
```

If C has a problem:

```text
Production
 ↓
Rollback
 ↓
Image B
```

You don't need to rebuild the application.

That's the power of:

> **Build once, deploy the same artifact.**

---

# 8. Why `latest` Alone Isn't Enough

Suppose production runs:

```text
ai-lms-api:latest
```

Today:

```text
latest → version A
```

Tomorrow:

```text
latest → version B
```

Now it becomes harder to answer:

> Exactly which version is production running?

With:

```text
ai-lms-api:8f42a91
```

the answer is explicit.

---

# 9. Image Digest

There is an even stronger identifier:

```text
sha256:...
```

Docker images have immutable content digests.

Conceptually:

```text
Tag
 ↓
Image
 ↓
Digest
```

A tag can move:

```text
latest
```

but a digest identifies a specific image content.

In highly controlled production environments, deployment by digest is even more deterministic.

For now, commit-SHA tags are an excellent learning step.

---

# 10. Build Once, Deploy Many

This is one of the most important principles of this lesson.

Bad workflow:

```text
Developer
 ↓
Build image
 ↓
Deploy

Production
 ↓
Build image again
 ↓
Deploy
```

Now you have potentially different builds.

Better:

```text
Source
 ↓
CI
 ↓
Build image ONCE
 ↓
Test image
 ↓
Push image
 ↓
Production pulls SAME image
```

So:

```text
Build
  ↓
Artifact
  ↓
Deploy
```

not:

```text
Deploy
  ↓
Build something new
```

# 12. Authentication to the Registry

GitHub Actions needs permission to push an image.

For GHCR, GitHub provides a workflow token:

```text
GITHUB_TOKEN
```

The workflow can use it to authenticate to GitHub's container registry.

Conceptually:

```text
GitHub Actions
      ↓
GITHUB_TOKEN
      ↓
GHCR
```

Don't manually create and hard-code a password into the workflow.

---

# 13. Workflow Permissions

The workflow needs permission to write packages.

For example:

```yaml
permissions:
  contents: read
  packages: write
```

This means:

```text
contents: read
    ↓
Read repository

packages: write
    ↓
Push container image
```

This is better than giving the workflow broad permissions it doesn't need.

---

# 14. Login to GHCR

GitHub provides Docker login actions.

Conceptually:

```yaml
- name: Log in to GHCR
  uses: docker/login-action@v3
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

Now Docker can authenticate to:

```text
ghcr.io
```

---

# 15. Why Use `github.actor`?

This:

```yaml
${{ github.actor }}
```

identifies the GitHub user or actor that triggered the workflow.

So:

```text
username
   ↓
GitHub actor
```

while:

```text
password
   ↓
GITHUB_TOKEN
```

is supplied securely.

---

# 16. Don't Print the Token

Never do:

```yaml
run: echo "${{ secrets.GITHUB_TOKEN }}"
```

Even if GitHub attempts to mask secrets, you should never intentionally print them.

Treat tokens like passwords.

---

# 17. Build the Image

After login:

```yaml
- name: Build Docker image
  run: |
    docker build \
      -t ghcr.io/${{ github.repository_owner }}/ai-lms-api:${{ github.sha }} \
      .
```

Now:

```text
github.sha
```

represents the current commit.

So the image might become:

```text
ghcr.io/rahul/ai-lms-api:8f42a91...
```

---

# 18. Why `${{ github.sha }}`?

GitHub automatically provides the commit SHA.

Conceptually:

```text
Git commit
    ↓
8f42a91...
    ↓
Docker tag
    ↓
ai-lms-api:8f42a91...
```

Now every image can be traced back to its source commit.

---

# 19. Push the Image

After building:

```yaml
- name: Push Docker image
  run: |
    docker push \
      ghcr.io/${{ github.repository_owner }}/ai-lms-api:${{ github.sha }}
```

Now:

```text
Local CI runner
      ↓
Docker image
      ↓
GHCR
```

# 21. Use Docker Metadata Action

For a more professional workflow, use:

```yaml
docker/metadata-action
```

This can generate useful tags automatically.

For example:

```yaml
- name: Extract Docker metadata
  id: meta
  uses: docker/metadata-action@v5
  with:
    images: ghcr.io/${{ github.repository_owner }}/ai-lms-api
```

Then:

```yaml
- name: Build and push Docker image
  uses: docker/build-push-action@v6
  with:
    context: .
    push: true
    tags: ${{ steps.meta.outputs.tags }}
    labels: ${{ steps.meta.outputs.labels }}
```

This becomes useful when we want:

```text
SHA tags
Version tags
Branch tags
```

without manually constructing all of them.

# 22. Buildx

You may notice:

```text
docker/build-push-action
```

rather than:

```bash

```

This uses Docker Buildx functionality.

It provides a more powerful build system suitable for CI/CD.

Conceptually:

```text
docker build
     ↓
Basic build

     ↓
Advanced build/push/cache/multi-platform workflows
```

For our learning pipeline, understanding the distinction is enough for now.

# 23. Why Build and Push Together?

You can use:

```yaml
docker/build-push-action
```

with:

```yaml
push: true
```

This performs:

```text
Build
 ↓
Push
```

as one CI operation.

That's often cleaner than:

```text
docker build
docker push
```

# 36. Reverse Proxy

We don't want users accessing:

```text
http://server-ip:3000
```

directly.

Instead:

```text
https://api.yourdomain.com
```

A reverse proxy such as Nginx can sit in front:

```text
Internet
   ↓
HTTPS :443
   ↓
Nginx
   ↓
localhost:3000
   ↓
AI LMS container
```

This will become important in the next deployment steps.

---

# 37. Why Use a Reverse Proxy?

It can handle:

```text
TLS/HTTPS
Domain routing
Request forwarding
Security headers
Compression
Connection handling
```

Instead of making your Node application directly responsible for every public-facing concern.

Suppose the Node app listens on:

```text
3000
```

inside the container.

Docker maps:

```bash
-p 3000:3000
```

meaning:

```text

      ↓
Container port 3000
```

But with Nginx:

```text
Internet
 ↓
443
 ↓
Nginx
 ↓
3000
 ↓
Container
```

The public user doesn't need to know the internal application port.

# 39. Deployment Process

A manual deployment initially looks like:

```text
1. Build image
2. Push image
3. SSH into server
4. Pull image
5. Stop old container
6. Start new container
7. Check health
```

For example:

```bash
docker pull ghcr.io/example/ai-lms-api:NEW_TAG
```

Then:

```bash
docker stop ai-lms-api
```

Then:

```bash
docker rm ai-lms-api
```

Then:

```bash
docker run ...
```

This works, but we'll automate it.

---

# 40. Why Manual Deployment Isn't Ideal

Imagine doing this every day:

```text
SSH
 ↓
docker pull
 ↓
docker stop
 ↓
docker rm
 ↓
docker run
```

Easy to make mistakes.

We want:

```text
Git push
 ↓
CI
 ↓
Image
 ↓
Deploy
```

That is CD.

---

# 41. Deployment Safety

Before replacing the running container:

```text
Old version
    ↓
Healthy
```

We should build:

```text
New version
    ↓
Test
```

and ideally:

```text
New version
    ↓
Health check
    ↓
Healthy
```

Only then should traffic be switched.

For simple deployments we'll initially do a controlled replacement.

Later, more advanced strategies include:

```text
Rolling deployment
Blue-green deployment
Canary deployment
```

---

# 42. Rollback

Suppose:

```text
Production
 ↓
v1.4.0
```

Then we deploy:

```text
v1.5.0
```

and discover:

```text
❌ Broken enrollment
```

Because our images are tagged:

```text
ai-lms-api:v1.4.0
ai-lms-api:v1.5.0
```

we can roll back:

```text
v1.5.0
 ↓
v1.4.0
```

No rebuild required.

---

# 43. Rollback Is Why Immutable Images Matter

Without immutable artifacts:

```text
"Let's rebuild the old version."
```

But the build environment might have changed.

With immutable images:

```text
Old image
   ↓
Still exists
   ↓
Deploy it
```

This is much safer.

---

# 44. Database Rollbacks Are Different

Be careful.

Rolling back:

```text
Application image
```

is relatively straightforward.

Rolling back:

```text
Database schema
```

can be much harder.

For example:

```text
v2 application
 ↓
adds column
```

then:

```text
rollback application to v1
```

but database still contains:

```text
new column
```

That's why database migrations need backward-compatible deployment strategies.

We'll revisit this when discussing production deployment.

---

# 45. Migration Deployment Strategy

A safer pattern is often:

```text
1. Deploy backward-compatible database migration
2. Deploy new application
3. Verify
4. Remove old database structures later
```

rather than:

```text
Delete database column
 ↓
Deploy old application
```

which could break the old version.

This is commonly called an **expand-and-contract** migration strategy.

# 46. GHCR Package Visibility

When using GitHub Container Registry, packages can have visibility/access controls.

You should understand:

```text
Public image
```

means anyone can potentially pull it.

For a private backend:

```text
Private image
```

is usually preferable.

Then production needs authentication to pull it.

# 47. Production Registry Authentication

The production server may need credentials to pull a private image.

Conceptually:

```text
Production Server
      ↓
docker login ghcr.io
      ↓
Private registry
      ↓

```

Do not use a personal account password.

Use an appropriate token/credential with the minimum permissions needed.

---

# 48. Principle of Least Privilege

For registry access:

```text

      ↓
Give pull permission
```

Don't give:

```text

```

if the server only needs:

```text

```

This is a security principle we'll revisit heavily in Phase 14.

# 59. Container Restart Policy

For a basic Docker deployment:

```bash
docker run -d \
  --restart unless-stopped \
  ...
```

This tells Docker to restart the container if it stops unexpectedly, subject to Docker's restart-policy behavior.

Conceptually:

```text
API crashes
   ↓
Docker notices
   ↓
Restart
```

But remember:

> Restart policies are not a replacement for fixing application crashes.

---

# 60. Health Check After Deployment

After starting the new container:

```bash
curl http://localhost:3000/health
```

We expect:

```text
200 OK
```

If the health check fails:

```text
New container
   ↓
❌
```

we should not blindly declare deployment successful.

---

# 61. Basic Deployment Verification

After deployment:

```text
1. Container running?
2. Health endpoint returns 200?
3. Database connection works?
4. Redis connection works?
5. Logs look normal?
6. API responds through domain?
```

This is called **smoke testing**.

A smoke test is a quick check that the application is fundamentally working.

---

# 62. Smoke Test Example

After deployment:

```bash
curl -f https://api.example.com/health
```

The `-f` option causes curl to return a failure status for HTTP errors.

So:

```text
200
 ↓
Success
```

but:

```text
500
 ↓
Failure
```

This can be used in automated deployment verification.

```text

```

# 64. Deployment Strategies

There are several approaches.

### Recreate

```text
Stop old
 ↓
Start new
```

Simple.

### Rolling

```text
Old A
Old B
 ↓
New A
 ↓
New B
```

Less downtime.

### Blue-Green

```text
Blue = current
Green = new
```

Switch traffic:

```text
Blue
 ↓
Green
```

### Canary

```text
95% → old
5% → new
```

Then gradually increase.

For our current VPS deployment, start with **recreate/controlled replacement**.

We don't need Kubernetes complexity yet.

# 67. A Simple GHCR Workflow

Here's the important portion of a deployment-ready image workflow:

```yaml
permissions:
  contents: read
  packages: write

steps:
  - name: Checkout repository
    uses: actions/checkout@v4

  - name: Log in to GHCR
    uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}

  - name: Build and push image
    uses: docker/build-push-action@v6
    with:
      context: .
      push: true
      tags: ghcr.io/${{ github.repository_owner }}/ai-lms-api:${{ github.sha }}
```

This is the conceptual bridge from CI to CD.

# 72. Container Registry Is Not a Database

Don't confuse:

```text
PostgreSQL
```

with:

```text
Container Registry
```

PostgreSQL stores:

```text
Users
Courses
Enrollments
Progress
```

Registry stores:

```text
Docker images
```

So:

```text
Application data
     ↓
PostgreSQL

Application artifact
     ↓
Container registry
```

Different responsibilities.

# 73. Container Registry Is Also Not Git

Git stores:

```text
Source code
History
Branches
Commits
```

Registry stores:

```text
Built container images
```

So:

```text
Git
 ↓
Source

Registry
 ↓
Artifact
```

The relationship is:

```text
Git commit
   ↓
Docker build
   ↓
Container image
```

# 74. One More Important Principle: Artifact Promotion

A mature deployment process often looks like:

```text
Build image once
       ↓
Test image
       ↓
Development
       ↓
Staging
       ↓
Production
```

The same image can move through environments.

You don't rebuild at every stage.

This avoids:

```text
Staging image ≠ Production image
```

Instead:

```text
Same artifact
```

This is a powerful DevOps principle.

# 79. Common Mistakes

### Mistake 1

```text

```

Avoid it.

```text
Use latest only
```

Prefer immutable/versioned tags.

### Mistake 3

```text
Put secrets in Docker image
```

Never.

### Mistake 4

```text
Use production DB for CI
```

Never.

### Mistake 5

```text
Deploy before tests finish
```

Don't.

### Mistake 6

```text
No health check
```

Add one.

### Mistake 7

```text
No rollback plan
```

Always know the previous working image.
