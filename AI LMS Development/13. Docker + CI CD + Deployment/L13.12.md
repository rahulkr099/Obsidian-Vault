# 4. Health Checks

The first question is simple:

> Is my application alive?

Create an endpoint such as:

```http
GET /health
```

Response:

```json
{
  "status": "ok"
}
```

Then:

```text
Monitoring
    ↓
GET /health
    ↓
200 OK
    ↓
Application alive
```

---

# 5. Liveness vs Readiness

These are slightly different.

## Liveness

Answers:

> Is the application process alive?

```http
GET /health/live
```

Example:

```json
{
  "status": "alive"
}
```

This should be very lightweight.

---

## Readiness

Answers:

> Is the application ready to receive traffic?

```http
GET /health/ready
```

It may check:

```text
PostgreSQL
Redis
Required dependencies
```

For example:

```text
API
 ↓
Database available?
 ↓
Redis available?
 ↓
Ready
```

---

# 6. Don't Make Liveness Too Strict

Suppose Redis temporarily goes down.

If:

```text
/health
```

always requires Redis:

```text
Redis unavailable
 ↓
Health endpoint fails
 ↓
Container considered dead
```

But the Node process itself might still be perfectly alive.

That's why separating:

```text
liveness
```

and:

```text
readiness
```

is useful.

---

# 7. Example Health Routes

Conceptually:

```ts
app.get("/health/live", (_req, res) => {
  res.status(200).json({
    status: "alive",
  });
});
```

Readiness:

```ts
app.get("/health/ready", async (_req, res) => {
  const databaseReady = await checkDatabase();
  const redisReady = await checkRedis();

  if (!databaseReady || !redisReady) {
    return res.status(503).json({
      status: "not_ready",
    });
  }

  return res.status(200).json({
    status: "ready",
  });
});
```

The exact implementation depends on your infrastructure.

---

# 8. Why `503`?

If the service isn't ready:

```http
503 Service Unavailable
```

is a useful HTTP status.

It communicates:

> The server is currently unable to serve this request normally.

So:

```text
Healthy
 ↓
200
```

and:

```text
Not ready
 ↓
503
```

# 9. Docker Health Check

Docker can periodically check your application.

Conceptually:

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=5s \
  --retries=3 \
  CMD ...
```

The flow becomes:

```text
Docker
 ↓
/health/live
 ↓
200
 ↓
Healthy
```

If it repeatedly fails:

```text
Docker
 ↓
Health check
 ↓
Failure
 ↓
Unhealthy
```

---

# 10. Health Check Isn't Monitoring

This distinction is important.

A health check answers:

```text
"Is it healthy right now?"
```

Monitoring answers:

```text
"How has the system behaved over time?"
```

For example:

```text
Health check
 ↓
200 OK
```

but monitoring might show:

```text
Error rate ↑
Response time ↑
CPU ↑
Memory ↑
```

The application may technically be alive while users are already experiencing problems.

# 11. Application Logs

Your Node application should produce useful logs.

For example:

```text
INFO  Server started on port 3000
INFO  Database connected
INFO  Redis connected
INFO  HTTP request
ERROR Failed to create enrollment
```

Logs help answer:

> What happened?

---

# 12. Don't Use Random `console.log`

This:

```ts
console.log("hello");
```

is fine while learning.

But production applications need structured logging.

Instead of:

```text
User failed
```

we want something like:

```json
{
  "level": "error",
  "message": "Failed to create enrollment",
  "requestId": "req_123",
  "userId": "user_456"
}
```

Structured logs are much easier to search and analyze.

---

# 13. Log Levels

Common levels:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

Think:

### DEBUG

Detailed development information.

```text
Cache lookup started
```

### INFO

Normal application events.

```text
Server started
```

### WARN

Something unusual happened but the system can continue.

```text
AI provider response slow
```

### ERROR

An operation failed.

```text
Database query failed
```

### FATAL

The application cannot continue safely.

```text
Required configuration missing
```

---

# 14. Don't Log Secrets

Never log:

```text
JWT
Passwords
API keys
Refresh tokens
Database passwords
Authorization headers
```

Bad:

```ts
logger.info({
  token: req.headers.authorization,
});
```

Don't do that.

---

# 15. Be Careful With User Data

The AI LMS may process:

```text
Student questions
Course content
AI conversations
Uploaded documents
```

You should avoid dumping sensitive user content into logs unnecessarily.

For example, don't automatically log:

```text
Entire AI conversation
Entire uploaded PDF
Full request body
```

unless there is a strong operational reason and appropriate privacy controls.

# 16. Request IDs

A request ID is extremely useful.

Imagine:

```text
Request
 ↓
API
 ↓
Service
 ↓
Database
 ↓
Error
```

Without a request ID, finding the related logs can be difficult.

With:

```text
requestId=req_8f92a
```

you can search:

```text
req_8f92a
```

and find all related logs.

---

# 17. Request ID Flow

```text

   ↓
requestId
   ↓

   ↓

   ↓
Service
   ↓
Repository
```

Every relevant log can include:

```json
{
  "requestId": "req_8f92a",
  "message": "Course lookup failed"
}
```

This makes debugging much easier.

# 19. Don't Log Everything

Logging every tiny internal operation can create:

```text
Millions of logs
 ↓
Higher storage
 ↓

```

A good production logging strategy focuses on useful events.

Log:

```text

Important state changes
Errors
Security events
Slow requests
Critical infrastructure events
```

Don't blindly log everything.

# 21. Four Golden Signals

A very useful monitoring model is:

```text
Latency
Traffic
Errors
Saturation
```

### Latency

How long requests take.

```text
GET /courses
 ↓
120 ms
```

### Traffic

How much traffic you're receiving.

```text
100 requests/sec
```

### Errors

How many requests fail.

```text
2% error rate
```

### Saturation

How close the system is to its limits.

```text
CPU: 85%
Memory: 90%
Database connections: 95%
```

These four signals provide a strong operational starting point.

# 32. Alerting

Monitoring without alerts can still leave you checking dashboards manually.

An alert tells you:

> Something needs attention.

Examples:

```text
Error rate > 5%
```

or:

```text
API unavailable for 2 minutes
```

or:

```text
Disk usage > 85%
```

or:

```text
Database connections > 90%
```

---

# 33. Good Alerts vs Bad Alerts

Bad:

```text
CPU > 50%
```

This might happen normally.

You'll receive too many alerts.

Better:

```text
CPU > 90%
for 10 minutes
```

The idea is:

> Alert when the condition is meaningful enough to require action.

So alerts should be:

```text
Relevant
Actionable
Specific
```


# 48. RPO and RTO

Two useful production concepts.

### RPO

**Recovery Point Objective**

> How much data can we afford to lose?

Example:

```text
RPO = 1 hour
```

means you might accept losing up to one hour of data.

### RTO

**Recovery Time Objective**

> How quickly must the service be restored?

Example:

```text
RTO = 30 minutes
```

means the target is to restore service within 30 minutes.


# 56. Don't Automatically Roll Back Everything

Some failures should trigger investigation rather than an immediate rollback.

For example:

```text
AI provider outage
```

Rolling back your application won't necessarily fix it.

Instead:

```text
Application healthy
+
AI provider unavailable
```

requires:

```text
Retry
Fallback
Graceful degradation
Provider status check
```

This is why diagnosis matters.

# 57. Graceful Degradation

Your AI LMS should ideally remain partially usable if an external AI provider fails.

For example:

```text
AI unavailable
 ↓
Course browsing still works
 ↓
Progress tracking still works
 ↓
Quiz history still works
 ↓
AI tutor temporarily unavailable
```

This is much better than:

```text
AI provider down
 ↓
Entire LMS down ❌
```

---

# 58. AI Timeout

Never let an AI request hang forever.

Conceptually:

```text
AI request
 ↓
Timeout: 30 seconds
 ↓
No response
 ↓
Return controlled error
```

Rather than:

```text
Request
 ↓
Waiting forever
```

This protects your application resources.

---

# 59. AI Retry

Retries should be used carefully.

For transient failures:

```text
Request
 ↓
Temporary failure
 ↓
Retry
```

But don't do:

```text
Failure
 ↓
Retry
 ↓
Retry
 ↓
Retry
 ↓
Retry
 ↓
...
```

because this can increase:

```text
Cost
Load
Latency
```

Use bounded retries and appropriate backoff.

# 68. Incident Documentation

After a serious incident, record:

```text
What happened?
When?
Impact?
Root cause?
How was it detected?
What fixed it?
How long did recovery take?
What will prevent it next time?
```

This is called a **postmortem**.

The goal isn't:

```text
"Who caused it?"
```

The goal is:

> **"How can we make the system safer so this doesn't happen again?"**

### 1. Containers make environments reproducible.

```text
"My machine works"
```

becomes:

```text

```

### 2. CI catches problems before deployment.

```text

 ↓

 ↓

```

```text

 ↓
Image
 ↓
Production
```

Don't rebuild differently for every environment.

### 5. Keep secrets outside images.

```text
Image ≠ Secrets
```

### 6. Production containers should be minimal and non-root.

### 7. Container registries bridge CI and production.

```text
CI → Registry → Production
```

### 8. Monitoring is part of production, not an optional extra.

### 9. Backups must be restorable.
