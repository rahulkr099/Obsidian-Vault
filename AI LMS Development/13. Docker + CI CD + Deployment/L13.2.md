# Lesson 13.2 — Dockerfile 🐳

In **13.1**, we learned:

```text
Dockerfile
    ↓
Docker Image
    ↓
Docker Container
```

Today we'll focus on the first part:

> **How do we create our own Docker image?**

The answer is a **Dockerfile**.

For your AI LMS, we're going to eventually create a Docker image for the **Node.js + TypeScript backend**.

---

# 1. What Is a Dockerfile?

A `Dockerfile` is a text file containing instructions that tell Docker how to build an image.

Think of it as a recipe:

```text
Dockerfile
    ↓
"Start with Node"
    ↓
"Create application directory"
    ↓
"Copy package files"
    ↓
"Install dependencies"
    ↓
"Copy source code"
    ↓
"Build TypeScript"
    ↓
"Start application"
```

Then Docker converts those instructions into:

```text
Dockerfile
    ↓
docker build
    ↓
Docker Image
```

---

# 2. Basic Dockerfile

Let's start with a tiny Node.js application.

Project:

```text
docker-demo/
├── package.json
├── package-lock.json
└── index.js
```

`index.js`:

```js
console.log("Hello from Docker!");
```

Now create:

```text
Dockerfile
```

with:

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

CMD ["node", "index.js"]
```

Don't worry if this looks unfamiliar.

We'll understand every line.

---

# 3. `FROM`

```dockerfile
FROM node:22
```

`FROM` tells Docker which base image to use.

Here:

```text
node:22
```

means:

```text
Node.js version 22
```

Conceptually:

```text
Node 22 Image
      ↓
Our Docker Image
```

We don't need to install Node manually.

The base image already provides it.

---

# 4. What Is a Base Image?

Imagine building a house.

You don't start by manufacturing bricks.

You start with a foundation.

Similarly:

```text
node:22
    ↓
Base Image
    ↓
Your Application
```

Docker Hub contains many official images.

For example:

```text
node
postgres
redis
nginx
```

We'll use official images whenever possible.

---

# 5. `WORKDIR`

Next:

```dockerfile
WORKDIR /app
```

This tells Docker:

> Use `/app` as the working directory inside the container.

So instead of:

```text
/
├── bin
├── etc
├── usr
└── ...
```

our application lives conceptually at:

```text
/app
```

Commands after this point operate from `/app`.

For example:

```dockerfile
WORKDIR /app

RUN npm install
```

is effectively running:

```bash
cd /app
npm install
```

inside the image-building environment.

---

# 6. `COPY`

Now:

```dockerfile
COPY package*.json ./
```

This copies:

```text
package.json
package-lock.json
```

into the container's working directory.

The `*` is a wildcard.

So:

```text
package*.json
```

matches:

```text
package.json
package-lock.json
```

The destination:

```text
./
```

means the current working directory.

Because we already have:

```dockerfile
WORKDIR /app
```

the files go into:

```text
/app
```

---

# 7. Why Copy package Files First?

This is a very important Docker optimization.

We could write:

```dockerfile
COPY . .
RUN npm install
```

but that's not ideal.

Instead:

```dockerfile
COPY package*.json ./
RUN npm install

COPY . .
```

Why?

Because Docker uses **layers**.

Suppose your source code changes:

```text
index.js
```

but your dependencies don't change.

Docker can reuse the dependency-installation layer.

Conceptually:

```text
package.json
      ↓
npm install
      ↓
Cached Layer ✅
      ↓
Source Code
```

Next build:

```text
package.json unchanged
      ↓
Reuse npm install layer ⚡
      ↓
Copy new source
```

This makes builds faster.

---

# 8. `RUN`

```dockerfile
RUN npm install
```

`RUN` executes a command while building the image.

So:

```dockerfile
RUN npm install
```

means:

```text
During image building
        ↓
Run npm install
        ↓
Dependencies become part of image
```

Other examples:

```dockerfile
RUN npm run build
```

or:

```dockerfile
RUN apt-get update
```

We'll use `RUN` frequently.

---

# 9. `COPY . .`

Next:

```dockerfile
COPY . .
```

This copies the project files into `/app`.

So our image now roughly contains:

```text
/app
├── package.json
├── package-lock.json
├── index.js
└── node_modules
```

---

# 10. `CMD`

Finally:

```dockerfile
CMD ["node", "index.js"]
```

This tells Docker what command to run when the container starts.

So:

```text
Container starts
      ↓
node index.js
      ↓
Hello from Docker!
```

An important distinction:

```text
RUN
```

happens during **image building**.

```text
CMD
```

is the default command when the **container starts**.

Remember this.

---

# 11. RUN vs CMD

|Instruction|When?|Example|
|---|---|---|
|`RUN`|Image build|`RUN npm install`|
|`CMD`|Container start|`CMD ["node", "index.js"]`|

Think:

```text
docker build
     ↓
RUN
     ↓
Image created
     ↓
docker run
     ↓
CMD
     ↓
Container starts
```

---

# 12. Build Your First Image

From your project directory:

```bash
docker build -t docker-demo .
```

Let's break it down.

### `docker build`

Build a Docker image.

### `-t`

Give the image a name/tag.

### `docker-demo`

Our image name.

### `.`

Use the current directory as the build context.

So:

```bash
docker build -t docker-demo .
```

means:

> Build an image using the Dockerfile in this directory and call the image `docker-demo`.

---

# 13. Check the Image

Run:

```bash
docker images
```

You should see something similar to:

```text
REPOSITORY    TAG       IMAGE ID
docker-demo   latest    abc123...
```

The default tag is:

```text
latest
```

So:

```text
docker-demo
```

is effectively:

```text
docker-demo:latest
```

# 14. Run Your Image

Now:

```bash
docker run --name docker-demo-container docker-demo
```

Docker will:

```text
docker-demo image
       ↓
Create container
       ↓
Start container
       ↓
CMD
       ↓
node index.js
```

Output:

```text
Hello from Docker!
```

---

# 15. See the Container

Run:

```bash
docker ps -a
```

You'll see something similar to:

```text
CONTAINER ID   IMAGE         STATUS
abc123         docker-demo   Exited
```

Why `Exited`?

Because:

```js
console.log("Hello from Docker!");
```

finishes immediately.

There's no server keeping the process alive.

# 16. Dockerfile for a Node.js Server

Now let's make something closer to your actual backend.

Suppose:

```text
server/
├── package.json
├── package-lock.json
└── src/
    └── server.js
```

`server.js`:

```js
const express = require("express");

const app = express();

app.get("/", (req, res) => {
  res.json({
    message: "AI LMS API is running",
  });
});

app.listen(3000, () => {
  console.log("Server running on port 3000");
});
```

Dockerfile:

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

EXPOSE 3000

CMD ["node", "src/server.js"]
```

Notice the new instruction:

```dockerfile
EXPOSE 3000
```

---

# 17. What Does `EXPOSE` Do?

This is commonly misunderstood.

```dockerfile
EXPOSE 3000
```

does **not** actually publish the port to your host.

It documents that the application inside the container listens on:

```text
3000
```

You still need:

```bash
docker run -p 3000:3000 ...
```

to access it from your computer.

So:

```text
EXPOSE
```

and:

```text
-p
```

are different.

---

# 18. `EXPOSE` vs `-p`

### Dockerfile

```dockerfile
EXPOSE 3000
```

means:

> This application expects to use port 3000 inside the container.

### Docker command

```bash
docker run -p 3000:3000 my-api
```

means:

```text
Host 3000
    ↓
Container 3000
```

# 22. Example TypeScript Dockerfile

A simple version:

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build

EXPOSE 3000

CMD ["node", "dist/server.js"]
```

This assumes:

```json
{
  "scripts": {
    "build": "tsc"
  }
}
```

and:

```text
tsconfig.json
```

outputs compiled JavaScript into:

```text
dist/
```

# 23. Why `npm ci` Instead of `npm install`?

For production/CI environments, you'll commonly see:

```bash
npm ci
```

instead of:

```bash
npm install
```

`npm ci` is designed for clean, reproducible installs based on the lockfile.

It expects:

```text
package.json
+
package-lock.json
```

This is particularly useful in:

```text
Docker
CI/CD
Production
Automated builds
```

We'll discuss this more when we build our CI pipeline.

---

# 24. `.dockerignore`

This is another extremely important file.

Create:

```text
.dockerignore
```

For a Node.js application:

```text
node_modules
npm-debug.log
.git
.gitignore
.env
.env.*
dist
coverage
Dockerfile
.dockerignore
```

Why?

Suppose your project contains:

```text
node_modules/
```

It might be hundreds of megabytes.

We don't want to copy your local dependencies into the image.

Docker should install them itself:

```text
package-lock.json
       ↓
npm ci
       ↓
Container's node_modules
```

---

# 25. Never Copy `.env` Into the Image

Notice:

```text
.env
.env.*
```

inside `.dockerignore`.

This is very important.

Your `.env` might contain:

```text
DATABASE_URL=...
JWT_SECRET=...
OPENAI_API_KEY=...
```

We don't want these secrets baked into the Docker image.

Later we'll learn proper production secret management.

# 26. Docker Build Context

When you run:

```bash
docker build -t ai-lms-api .
```

the:

```text
.
```

means the current directory is sent as the **build context**.

Docker can access files from that context.

That's why:

```dockerfile
COPY . .
```

works.

But `.dockerignore` tells Docker:

> Don't send these files as part of the build context.

---

# 27. Docker Layers

This is one of the most valuable concepts to understand.

Consider:

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build

CMD ["node", "dist/server.js"]
```

Docker creates layers roughly corresponding to instructions.

```text
FROM node:22
      ↓
Layer
      ↓
WORKDIR
      ↓
Layer
      ↓
COPY package*.json
      ↓
Layer
      ↓
npm ci
      ↓
Layer
      ↓
COPY source
      ↓
Layer
      ↓
npm run build
```

If your source code changes but:

```text
package.json
package-lock.json
```

don't change, Docker can reuse earlier layers.

That's why Dockerfile ordering matters.

---

# 28. Bad Ordering

Avoid:

```dockerfile
COPY . .

RUN npm ci
```

as your first application-copy step.

If one source file changes:

```text
src/controllers/user.controller.ts
```

Docker may have to invalidate the following dependency-installation layer.

---

# 29. Better Ordering

Prefer:

```dockerfile
COPY package*.json ./

RUN npm ci

COPY . .
```

Now:

```text
package.json unchanged
        ↓
npm ci layer cached
        ↓
Only application layers rebuild
```

This can make Docker builds significantly faster.

---

# 30. Multi-Stage Builds

Now we reach an important production concept.

A TypeScript application needs build tools:

```text
typescript
ts-node
development dependencies
```

But production may only need:

```text
Node.js
compiled JavaScript
production dependencies
```

Why ship all build tools into production?

We don't need to.

That's why we use **multi-stage builds**.

Conceptually:

```text
Stage 1 — Builder
       ↓
Install dependencies
       ↓
Compile TypeScript
       ↓
dist/

Stage 2 — Production
       ↓
Copy dist/
       ↓
Production dependencies
       ↓
Run application
```

---

# 31. Example Multi-Stage Dockerfile

A simplified version:

```dockerfile
FROM node:22 AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM node:22 AS production

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist

EXPOSE 3000

CMD ["node", "dist/server.js"]
```

This is much closer to what we'll eventually want for your production backend.

---

# 32. Understanding `AS builder`

Here:

```dockerfile
FROM node:22 AS builder
```

we give the first stage a name:

```text
builder
```

Then:

```dockerfile
COPY --from=builder /app/dist ./dist
```

means:

> Copy the compiled `dist` directory from the builder stage into the production stage.

So:

```text
Builder
/app/dist
    ↓
Production
/app/dist
```

---

# 33. Why Multi-Stage Builds?

Without multi-stage:

```text
Production Image
├── source code
├── TypeScript
├── build tools
├── dev dependencies
├── compiled JS
└── production dependencies
```

With multi-stage:

```text
Production Image
├── compiled JS
├── production dependencies
└── required runtime files
```

Benefits:

```text
Smaller image
Less unnecessary software
Reduced attack surface
Cleaner production environment
Faster deployment
```

This connects directly with our **Phase 14 security work** later.

---

# 36. Common Beginner Mistakes

### ❌ Mistake 1 — Using `localhost` for another container

Inside a container:

```text
localhost
```

means:

> This same container.

It does **not** mean your PostgreSQL container.

We'll fix this properly in Docker Compose.

---

### ❌ Mistake 2 — Putting secrets in Dockerfile

Never do:

```dockerfile
ENV JWT_SECRET=my-secret
```

for real secrets.

---

### ❌ Mistake 3 — Copying `node_modules`

Don't do:

```dockerfile
COPY node_modules .
```

Use:

```dockerfile
COPY package*.json ./
RUN npm ci
```

---

### ❌ Mistake 4 — Running development mode in production

Avoid:

```dockerfile
CMD ["npm", "run", "dev"]
```

for the production image.

Production should run the compiled application.

---

### ❌ Mistake 5 — Installing everything in the final image

For production, eventually we'll use:

```bash
npm ci --omit=dev
```

and multi-stage builds.
