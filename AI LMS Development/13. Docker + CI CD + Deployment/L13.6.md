# Lesson 13.6 — Production Environment 🌍

So far we've built:

```text
13.1 → Docker fundamentals
13.2 → Dockerfile
13.3 → Docker Compose
13.4 → PostgreSQL container
13.5 → Redis container
```

Now we need to solve an important production problem:

> **How do we manage configuration and secrets differently in development, testing, and production?**

For your AI LMS, this is especially important because we'll eventually have:

```text
DATABASE_URL
REDIS_URL
JWT secrets
AI API keys
Email credentials
CORS configuration
Storage credentials
```

We should **never treat all environments the same**.

---

# 1. What Is an Environment?

An environment is a specific setup in which your application runs.

For our project, think about three main environments:

```text
Development
     ↓
Testing
     ↓
Production
```

They may run the same application code, but their configuration is different.

---

# 2. Development Environment

This is where you're building the LMS.

Example:

```text
Developer
   ↓
Linux Mint
   ↓
Docker Compose
   ↓
API + PostgreSQL + Redis
```

Development may use:

```text
localhost
debug logging
development database
test API keys
frequent database resets
```

Example:

```env
NODE_ENV=development
```

---

# 3. Testing Environment

Testing should be isolated from your normal development data.

Conceptually:

```text
Tests
  ↓
Test API
  ↓
Test PostgreSQL
```

You don't want:

```text
Automated test
    ↓
DELETE production student data ❌
```

So testing should use separate configuration.

For example:

```env
NODE_ENV=test
```

and potentially:

```text
ai_lms_test
```

instead of:

```text
ai_lms
```

---

# 4. Production Environment

Production is where real users access your application.

```text
Students
    ↓
Production API
    ↓
Production PostgreSQL
    ↓
Production Redis
```

Production configuration needs much more care:

```text
Real database
Real secrets
HTTPS
Restricted CORS
Production logging
Monitoring
Security controls
```

Example:

```env
NODE_ENV=production
```

---

# 5. Same Code, Different Configuration

This is the core idea.

We want:

```text
Same Application Code
        │
   ┌────┼────┐
   ↓    ↓    ↓
 Dev   Test  Prod
   │    │     │
   ↓    ↓     ↓
Config Config Config
```

For example, the application might always do:

```ts
process.env.DATABASE_URL
```

but the value changes depending on the environment.

---

# 6. What Is Configuration?

Configuration tells the application **how it should run**.

Examples:

```text
PORT
NODE_ENV
DATABASE_URL
REDIS_URL
CORS_ORIGIN
LOG_LEVEL
JWT_EXPIRATION
AI_MODEL
```

These aren't necessarily all secrets.

For example:

```env
PORT=3000
```

isn't secret.

But:

```env
DATABASE_URL=postgresql://user:password@...
```

may contain credentials and must be protected.

---

# 7. What Is a Secret?

A secret is sensitive information that should not be exposed publicly.

Examples:

```text
Database passwords
JWT signing secrets
AI provider API keys
SMTP passwords
Cloud credentials
Encryption keys
```

For your AI LMS:

```text
JWT_SECRET
AI_API_KEY
DATABASE_PASSWORD
REDIS_PASSWORD
EMAIL_PASSWORD
```

should be treated as secrets.

---

# 8. The `.env` File

During development, you'll commonly use:

```text
.env
```

For example:

```env
NODE_ENV=development
PORT=3000

DATABASE_URL=postgresql://lms_user:lms_password@localhost:5432/ai_lms

REDIS_URL=redis://localhost:6379

JWT_SECRET=development-secret
```

Your Node.js application can load these values.

But:

> **`.env` should generally not be committed to Git.**

---

# 9. `.gitignore`

Your `.gitignore` should include:

```text
.env
.env.*
!.env.example
```

This means:

```text
.env
    ↓
Don't commit

.env.production
    ↓
Don't commit

.env.example
    ↓
Can commit
```

The exact pattern can vary based on your project structure, but the principle is important.

---

# 10. `.env.example`

Instead of committing your real secrets, commit a template:

```env
NODE_ENV=
PORT=

DATABASE_URL=

REDIS_URL=

JWT_SECRET=

AI_API_KEY=

CORS_ORIGIN=
```

This tells another developer:

> These environment variables are required.

But it doesn't reveal the real values.

---

# 11. Example Project Structure

Your backend could eventually look like:

```text
backend/
├── src/
├── prisma/
├── Dockerfile
├── compose.yaml
├── .dockerignore
├── .gitignore
├── .env
├── .env.example
├── package.json
└── tsconfig.json
```

The important distinction:

```text
.env
   ↓
Private

.env.example
   ↓
Public template
```

---

# 12. Never Put Secrets in Source Code

Don't do this:

```ts
const jwtSecret = "my-super-secret-key";
```

Don't do this:

```ts
const apiKey = "sk-xxxxxxxx";
```

And don't do this:

```dockerfile
ENV JWT_SECRET=my-super-secret
```

Instead:

```ts
const jwtSecret = process.env.JWT_SECRET;
```

Then inject the value through the environment.

---

# 13. Never Put Secrets in Dockerfile

This is especially important now that we're learning Docker.

❌ Don't:

```dockerfile
ENV DATABASE_PASSWORD=secret123
```

Why?

Because the Dockerfile is source code.

It can be:

```text
GitHub
Docker build logs
Image history
Developer machines
CI systems
```

You don't want secrets baked into your image.

---

# 14. Docker Image vs Runtime Configuration

A very useful production principle is:

```text
Docker Image
    ↓
Application
    ↓
Configuration injected at runtime
```

Not:

```text
Docker Image
    ↓
Application + production secrets
```

Think:

```text
             Same Image
          ┌───────┼───────┐
          ↓       ↓       ↓
         Dev     Test    Prod
          │       │       │
       Config   Config   Config
```

This means we can build one application image and provide different configuration when it runs.

---

# 15. Development `.env`

For local development:

```env
NODE_ENV=development
PORT=3000

DATABASE_URL=postgresql://lms_user:lms_password@postgres:5432/ai_lms

REDIS_URL=redis://redis:6379

CORS_ORIGIN=http://localhost:5173

JWT_SECRET=local-development-secret
```

Notice:

```text
postgres
redis
```

rather than:

```text
localhost
```

when the API itself runs inside Docker Compose.

---

# 16. Why `localhost` Depends on Where the Application Runs

This is one of the easiest things to get wrong.

### API running directly on Linux:

```text
Node.js
   ↓
localhost:5432
   ↓
PostgreSQL Docker container
```

### API running inside Docker:

```text
API container
   ↓
postgres:5432
   ↓
PostgreSQL container
```

So your `DATABASE_URL` depends on **where the API process runs**.

---

# 17. Production Configuration

Production might use:

```env
NODE_ENV=production
PORT=3000

DATABASE_URL=postgresql://production-user:...@private-db:5432/ai_lms

REDIS_URL=redis://private-redis:6379

CORS_ORIGIN=https://your-frontend-domain.com
```

The values are different.

But your application code doesn't need to change.

It still reads:

```ts
process.env.DATABASE_URL
process.env.REDIS_URL
```

---

# 18. Configuration Validation

One problem with environment variables is that everything is a string.

For example:

```env
PORT=3000
```

Node receives:

```text
"3000"
```

not:

```text
3000
```

And this:

```env
ENABLE_AI=true
```

is:

```text
"true"
```

not:

```ts
true
```

So environment variables should be validated.

---

# 19. Using Zod for Environment Validation

Since we've already chosen **Zod** for backend validation, we can use it for environment configuration too.

Example:

```ts
import { z } from "zod";

const envSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().min(1),
  REDIS_URL: z.string().min(1),
  JWT_SECRET: z.string().min(32),
});

export const env = envSchema.parse(process.env);
```

Now:

```ts
env.PORT
env.DATABASE_URL
env.REDIS_URL
env.JWT_SECRET
```

are validated.

---

# 20. Why Validate Environment Variables?

Without validation:

```text
Application starts
      ↓
DATABASE_URL missing
      ↓
Prisma connection fails
      ↓
Application crashes later
```

With validation:

```text
Application starts
      ↓
Validate environment
      ↓
DATABASE_URL missing
      ↓
Fail immediately
      ↓
Clear configuration error
```

This is called **fail fast**.

It's much easier to debug.

---

# 21. Configuration Module

Instead of accessing:

```ts
process.env.DATABASE_URL
```

everywhere, create one configuration module.

For example:

```text
src/
└── config/
    └── env.ts
```

Then:

```ts
import { z } from "zod";

const schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().min(1),
  REDIS_URL: z.string().min(1),
  JWT_SECRET: z.string().min(32),
});

export const env = schema.parse(process.env);
```

Then elsewhere:

```ts
import { env } from "./config/env";

console.log(env.PORT);
```

This gives you one centralized configuration boundary.

---

# 22. Don't Log Secrets

This is a common mistake.

Don't do:

```ts
console.log(process.env);
```

because your logs could contain:

```text
DATABASE_URL
JWT_SECRET
AI_API_KEY
```

Instead log safe configuration:

```ts
console.log({
  environment: env.NODE_ENV,
  port: env.PORT,
});
```

Not:

```text
JWT_SECRET=...
```

---

# 23. Production Secrets

In real production, secrets should come from a secure mechanism.

Depending on the deployment environment, that could be:

```text
Platform secrets
Secret manager
Encrypted CI/CD secrets
Cloud secret service
Container orchestration secrets
```

The exact service isn't the main point yet.

The important principle is:

```text
Source code
    ❌
GitHub
    ❌
Docker image
    ❌

Secure runtime configuration
    ✅
```

# 24. GitHub Secrets

When we reach **13.7 — GitHub Actions**, we'll need CI/CD secrets.

GitHub Actions can provide secrets to workflows.

Conceptually:

```text
GitHub
   ↓
Encrypted Secret
   ↓
GitHub Actions
   ↓
Deployment
```

For example:

```text
DOCKER_USERNAME
DOCKER_TOKEN
DEPLOY_TOKEN
```

But don't put:

```text

```

inside your repository.

# 25. Frontend vs Backend Environment Variables

This is extremely important for your React/TypeScript frontend.

Some frontend environment variables are sent to the browser.

Therefore:

```text
Frontend environment variable
   ↓
Potentially public
```

So never put:

```text
DATABASE_PASSWORD
JWT_SECRET
AI_API_KEY
```

in frontend environment variables.

Architecture:

```text
Browser
   ↓
Public configuration

Backend
   ↓
Private secrets
```

---

# 26. AI API Keys

This is especially important for your AI LMS.

Wrong:

```text
React frontend
   ↓
AI API key
   ↓
Direct AI provider request
```

A user could inspect the browser and potentially extract the key.

Better:

```text
React
   ↓
Your API
   ↓
AI provider
```

The AI API key stays on the backend.

```text
AI_API_KEY
   ↓
Backend environment
   ↓
AI service
```

---

# 27. CORS by Environment

Your frontend URL will differ between environments.

Development:

```text
http://localhost:5173
```

Production:

```text
https://your-lms-domain.com
```

So don't hard-code one value into your backend.

Use:

```env
CORS_ORIGIN=http://localhost:5173
```

in development.

Production:

```env
CORS_ORIGIN=https://your-lms-domain.com
```

Then:

```ts
app.use(
  cors({
    origin: env.CORS_ORIGIN,
    credentials: true,
  })
);
```

The exact CORS setup depends on your authentication strategy, but the configuration principle remains.

For example:

# 30. Prisma Migrations in Production

This is an important distinction.

Development:

```bash
npx prisma migrate dev
```

Production generally should use:

```bash
npx prisma migrate deploy
```

Why?

`migrate dev` is designed for development workflows.

`migrate deploy` applies already-created migrations in a deployment environment.

Conceptually:

```text
Developer
   ↓
Create migration
   ↓
Git
   ↓
CI/CD
   ↓
Production
   ↓
prisma migrate deploy
```

We'll integrate this into our deployment workflow later.

# 31. Docker Compose Environment Variables

You can use:

```yaml
services:
  api:
    environment:
      NODE_ENV: ${NODE_ENV}
      DATABASE_URL: ${DATABASE_URL}
      REDIS_URL: ${REDIS_URL}
```

Then Compose reads values from the environment or `.env` mechanisms.

This is useful because your Compose file doesn't need to contain actual secrets.

---

# 32. Better Compose Pattern

Instead of:

```yaml
environment:
  DATABASE_URL: postgresql://lms_user:lms_password@postgres:5432/ai_lms
```

you can use:

```yaml
environment:
  DATABASE_URL: ${DATABASE_URL}
```

Then:

```env
DATABASE_URL=postgresql://lms_user:lms_password@postgres:5432/ai_lms
```

The Compose file stays cleaner.

Check:

```bash
git status
```

If you see:

```text
.env
```

and it contains secrets, stop.

Your `.gitignore` should protect it.

Example:

```gitignore

.env
.env.*
!.env.example
```

Then:

```bash
git status
```

should not show your `.env`.

# 35. What If You Already Committed a Secret?

This is important.

If you accidentally commit:

```text
AI_API_KEY=secret
```

deleting the line later isn't enough.

Git history may still contain it.

The safe approach is:

```text
1. Revoke/rotate the secret
2. Remove it from the repository
3. Clean Git history if necessary
4. Store the new secret securely
```

The most important first action is usually:

> **Rotate the compromised secret.**

We'll revisit secret handling in Phase 14.

---

# 36. Production Docker Principle

Remember:

```text
Build
   ↓
Image
```

should not depend on your production secret values.

Instead:

```text
Production Image
       +
Runtime Secrets
       ↓
Production Container
```

This gives us a reusable image.

For example:

```text
ai-lms-api:1.0.0
```

could potentially run in:

```text
Development
Testing
Production
```

with different configuration.

# 37. Development Compose

You might eventually have:

```text
compose.yaml
```

for common configuration.

And perhaps:

```text
compose.dev.yaml
```

for development-specific behavior.

For example:

```text
Development
 ├── hot reload
 ├── source mounts
 └── verbose logs
```

while production:

```text
Production
 ├── compiled application
 ├── no source mounts
 ├── production dependencies
 └── stricter configuration
```

We don't need to create all of this yet.

The important thing is understanding the separation.

---

# 38. Bind Mounts vs Production Containers

Development often benefits from:

```text
Source code
   ↓
Bind mount
   ↓
Container
```

so changes appear immediately.

Production generally shouldn't work like:

```text
Host source directory
      ↓
Production container
```

Instead:

```text
Source
  ↓
Build
  ↓
Docker image
  ↓
Production container
```

This creates a much more reproducible deployment.

---

# 39. Environment Matrix

Here's a useful way to think about your LMS:

|Setting|Development|Testing|Production|
|---|---|---|---|
|`NODE_ENV`|`development`|`test`|`production`|
|Database|Dev DB|Test DB|Prod DB|
|Redis|Dev Redis|Test Redis|Prod Redis|
|Logging|Verbose|Useful|Controlled|
|CORS|Local frontend|Test frontend|Real domain|
|AI keys|Dev/test|Mock/test|Production secret|
|Debug mode|Enabled|Controlled|Disabled|
|Secrets|Local `.env`|CI secrets|Secure secret store|

The exact values will change, but this separation is what matters.
