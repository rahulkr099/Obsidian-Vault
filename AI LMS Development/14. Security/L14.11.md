# 🔐 Lesson 14.11 — Dependency & Supply-Chain Security

Your application is no longer just **your code**.

A modern MERN/TypeScript AI LMS may depend on:

```text
React
Express
Prisma
PostgreSQL
Axios
Zod
JWT libraries
Redis libraries
AI SDKs
PDF parsers
File upload libraries
Docker images
GitHub Actions
npm packages
```

So your real application is:

```text
Your Code
    +
Dependencies
    +
Build Tools
    +
Docker Images
    +
CI/CD Actions
    +
External Services
```

This creates a new attack surface:

> **The software supply chain.**

---

# 1. What Is Supply-Chain Security?

Supply-chain security means protecting the software and components that your application depends on.

Imagine:

```text
Your LMS
   ↓
npm package
   ↓
another npm package
   ↓
another package
   ↓
another package
```

Your project might directly install:

```text
20 packages
```

but those packages can bring hundreds of transitive dependencies.

So:

```text
Your Code
   ↓
Direct Dependencies
   ↓
Transitive Dependencies
   ↓
Huge Dependency Tree
```

If one dependency becomes malicious or vulnerable, your application can be affected.

---

# 2. Why This Matters for Your AI LMS

Your AI LMS will probably use packages for:

```text
Authentication
Validation
Database
File uploads
PDF parsing
AI integration
Vector search
Queues
Redis
Logging
Testing
Docker
```

Some libraries will process highly sensitive input.

For example:

```text
User
 ↓
Upload PDF
 ↓
PDF parser
 ↓
Text extraction
```

If the parser has a serious vulnerability, your application's security can be affected even if your own code is perfect.

---

# 3. Direct vs Transitive Dependencies

Suppose your `package.json` contains:

```json
{
  "dependencies": {
    "express": "...",
    "zod": "...",
    "jsonwebtoken": "..."
  }
}
```

These are **direct dependencies**.

But Express itself depends on other packages.

Those are:

> **Transitive dependencies.**

Think:

```text
Your App
   │
   ├── Express
   │     ├── Package A
   │     └── Package B
   │
   ├── Zod
   │
   └── JWT
         └── Package C
```

You may not even know Package C exists.

That's why dependency security needs automated tooling.

---

# 4. Dependency Tree

You can inspect your npm dependency tree with:

```bash
npm ls
```

For example:

```text
ai-lms
├── express
├── prisma
├── zod
├── jsonwebtoken
└── ...
```

For a particular package:

```bash
npm ls express
```

This helps answer:

> "Why is this package installed?"

---

# 5. `package.json` vs `package-lock.json`

You should understand both.

### `package.json`

Defines your intended dependencies.

```json
{
  "dependencies": {
    "express": "^5.1.0"
  }
}
```

### `package-lock.json`

Records the resolved dependency tree and versions.

Think:

```text
package.json
    ↓
What I want

package-lock.json
    ↓
What was actually resolved
```

The lockfile is extremely important for reproducible builds.

---

# 6. Why Lockfiles Matter

Suppose today:

```text
express
 ↓
dependency A v1.2.3
```

Tomorrow:

```text
dependency A
 ↓
new version
```

If your dependency range permits it, different installations might resolve differently.

A lockfile helps ensure:

```text
Developer machine
       ↓
CI
       ↓
Docker
       ↓
Production
```

use the same resolved versions.

---

# 7. `npm install` vs `npm ci`

This is an important production concept.

### `npm install`

Used commonly during development.

It can update dependency resolution/lockfile depending on the situation.

### `npm ci`

Designed for clean, reproducible installs in CI environments.

Conceptually:

```text
package-lock.json
      ↓
npm ci
      ↓
Exact locked dependency tree
```

For production CI/CD pipelines, `npm ci` is generally preferable when you have a committed lockfile.

---

# 8. Never Randomly Delete the Lockfile

You may have seen advice like:

```bash
rm package-lock.json
rm -rf node_modules
npm install
```

This can sometimes resolve dependency problems during development.

But don't make it your normal security strategy.

Deleting the lockfile means:

```text
Old resolution
     ↓
Discarded
     ↓
New resolution
```

which can unexpectedly change many dependencies.

Before doing this, understand why you're changing dependency resolution.

---

# 9. Vulnerable Dependencies

A package may have:

```text
CVE
```

or another published security advisory.

For example:

```text
Package
Version 1.2.0
     ↓
Security vulnerability
     ↓
Fixed in 1.2.3
```

Your job is to identify:

```text
Do we use the vulnerable version?
Is the vulnerable code reachable?
Is a fixed version available?
Does upgrading introduce breaking changes?
```

---

# 10. `npm audit`

A basic first check:

```bash
npm audit
```

This checks your dependency tree against known vulnerability information.

You can also run:

```bash
npm audit --json
```

which is useful for automation.

---

# 11. Don't Blindly Run `npm audit fix`

You may see:

```bash
npm audit fix
```

This can be useful.

But don't treat it as:

> "Security is fixed now."

Dependency upgrades can introduce:

```text
Breaking changes
Behavior changes
New bugs
Compatibility problems
```

Especially when a major version changes.

Security work still requires testing.

---

# 12. The Correct Dependency Update Flow

A good process:

```text
Vulnerability detected
        ↓
Identify affected package
        ↓
Understand severity
        ↓
Check fixed versions
        ↓
Update dependency
        ↓
Run tests
        ↓
Build application
        ↓
Security scan
        ↓
Deploy
```

This is much better than:

```text
npm audit fix
 ↓
Done
```

---

# 13. Severity Matters

Not every vulnerability has the same impact.

Common severity categories:

```text
Low
Moderate
High
Critical
```

But don't blindly ignore a "low" vulnerability either.

Ask:

```text
Is the vulnerable feature used?
Is it reachable from user input?
Does it affect production?
Is exploitation realistic?
Is there a fix?
```

---

# 14. Reachability

This is an important security concept.

Suppose a dependency has a vulnerability in:

```text
optional-feature-X
```

but your application never uses that feature.

The practical risk may be different from a vulnerability directly reachable through:

```text
POST /api/upload
```

So vulnerability assessment should consider:

```text
Severity
+
Reachability
+
Exposure
+
Impact
```

---

# 15. npm Package Typosquatting

Imagine the real package is:

```text
jsonwebtoken
```

An attacker publishes:

```text
jsonwebt0ken
```

or:

```text
jsonwebtoken-helper
```

with a malicious payload.

A developer accidentally installs the wrong package.

This is:

> **Typosquatting.**

---

# 16. Always Verify Package Names

Before installing:

```bash
npm install some-package
```

check:

```text
Package name
Publisher
Repository
Documentation
Download history
Version history
Known reputation
```

Don't blindly copy random commands from blog posts.

Especially avoid:

```bash
npm install mysterious-package
```

just because a Stack Overflow answer mentions it.

---

# 17. Dependency Confusion

This is a different attack.

Imagine your organization has an internal package:

```text
@company/auth-utils
```

and an attacker publishes a similarly named public package.

If package resolution is misconfigured, your build system could potentially pull the attacker's package instead.

This is:

> **Dependency confusion.**

For your personal AI LMS, the risk may be lower if you don't have private package names, but it's important to understand for professional development.

---

# 18. Package Installation Scripts

npm packages can define lifecycle scripts.

For example:

```json
{
  "scripts": {
    "postinstall": "..."
  }
}
```

When installed, code may execute.

That means:

```text
npm install
```

is not always simply:

```text
Download files
```

It can potentially execute package-provided scripts.

This is why dependency trust matters.

---

# 19. `npm install` Is Code Execution

Think about this:

```bash
npm install
```

You're effectively saying:

> "Download code from external publishers and potentially execute installation scripts on my machine."

Therefore:

```text
Developer machine
CI runner
Production build environment
```

all need to be treated as security boundaries.

---

# 20. `--ignore-scripts`

npm provides mechanisms to disable lifecycle scripts when appropriate.

For example:

```bash
npm install --ignore-scripts
```

However, don't blindly use this everywhere.

Some legitimate packages rely on installation scripts to:

```text
Build native modules
Generate files
Download required components
```

The important lesson is:

> **Understand what install scripts do before trusting dependencies.**

---

# 21. Native Dependencies

Some packages use native code.

For example:

```text
Node.js
 ↓
Native addon
 ↓
C/C++
```

These packages can increase complexity because you're no longer dealing only with JavaScript.

Examples of concerns:

```text
Compilation
Binary compatibility
Native vulnerabilities
Platform-specific behavior
```

Prefer well-maintained libraries with strong security histories when native components are required.

---

# 22. Dependency Maintenance

Don't wait until:

```text
npm audit
```

shows 200 vulnerabilities.

Instead:

```text
Weekly/monthly dependency review
```

can keep your project healthy.

Track:

```text
Outdated packages
Security advisories
Deprecated packages
Abandoned packages
Breaking changes
```

---

# 23. Outdated ≠ Vulnerable

Important distinction.

A package can be:

```text
Old
```

without having a known vulnerability.

And a package can be:

```text
Current
```

but still have a newly discovered vulnerability.

Therefore:

```text
Outdated
      ≠
Vulnerable
```

You should monitor both.

---

# 24. Abandoned Packages

Suppose you find:

```text
Package X
Last update: 5 years ago
Issues unanswered
No maintainers
```

Even if:

```text
npm audit
```

reports no vulnerabilities, the package may still be risky.

Why?

```text
No maintenance
 ↓
Security bugs may remain undiscovered/unfixed
```

Prefer actively maintained dependencies for security-sensitive functionality.

---

# 25. Dependency Count

More dependencies mean:

```text
More code
More attack surface
More updates
More vulnerabilities
More maintenance
```

Don't install a package for a 5-line utility.

For example:

```js
const isEven = (n) => n % 2 === 0;
```

doesn't require:

```text
some-is-even-package
```

Dependency minimization is a security strategy.

---

# 26. The "Tiny Package" Problem

Historically, the JavaScript ecosystem has had incidents where very small packages caused huge dependency problems.

The lesson isn't:

> "Never use npm."

It's:

> **Every dependency is a trust decision.**

Before adding one, ask:

```text
Do I need it?
Can I implement this safely myself?
Is it maintained?
Is it widely used?
Does it have a good security record?
```

---

# 27. Don't Reinvent Cryptography

There's an important exception.

Don't think:

> "I'll remove dependencies by writing my own encryption library."

Bad idea.

For security-sensitive primitives:

```text
Hashing
Password hashing
Cryptography
TLS
JWT handling
```

use mature, well-reviewed libraries.

Dependency minimization doesn't mean reinventing security primitives.

# 31. Docker Base Images

Supply-chain security isn't just npm.

Your Dockerfile might contain:

```dockerfile
FROM node:22
```

That base image is also a dependency.

Think:

```text
Dockerfile
   ↓
Node image
   ↓
Linux packages
   ↓
System libraries
```

Vulnerabilities can exist at any level.

---

# 32. Pin Docker Versions

Instead of loosely using:

```dockerfile
FROM node:22
```

you can use a more controlled tag or, for stronger reproducibility, pin by digest.

Conceptually:

```text
Image tag
    ↓
May change over time

Image digest
    ↓
Specific immutable image
```

This improves reproducibility.

You need to balance this with maintenance, because pinned images still need regular updates when security fixes are released.

---

# 33. Scan Docker Images

Your CI pipeline should eventually scan:

```text
Docker image
   ↓
Known vulnerabilities
```

It can identify vulnerabilities in:

```text
OS packages
Node runtime
Libraries
Other installed components
```

Common tools in this space include:

```text
Trivy
Grype
Docker Scout
```

You don't need all of them.

Choose an appropriate scanner and integrate it into CI.

---

# 34. GitHub Actions Are Dependencies Too

Suppose your CI contains:

```yaml
- uses: actions/checkout@v4
```

That action is external code.

So:

```text
GitHub Actions
=
Supply-chain dependency
```

You should:

```text
Use trusted actions
Keep actions updated
Limit permissions
Review third-party actions
```

---

# 35. GitHub Actions Permissions

Avoid giving workflows unnecessary permissions.

Conceptually:

```yaml
permissions:
  contents: read
```

is safer than:

```text
Everything:
write
```

if the workflow only needs to read repository contents.

This follows:

> **Least privilege.**

---

# 36. Third-Party GitHub Actions

Imagine:

```yaml
- uses: random-user/some-action@main
```

You're trusting:

```text
random-user
```

with code execution in your CI environment.

That action may potentially access:

```text
Repository
CI secrets
Build environment
Cloud credentials
```

Be very careful with third-party actions.

---

# 37. Pinning Actions

A floating reference such as:

```yaml
uses: some/action@main
```

can change over time.

A stronger approach is to pin to a specific release or commit SHA where practical.

Conceptually:

```text
@main
 ↓
Can change

@v4
 ↓
Version-controlled reference

@commit-sha
 ↓
Specific immutable revision
```

Again, pinning doesn't eliminate maintenance—you must intentionally update the pinned reference when security fixes arrive.

# 38. Software Bill of Materials

Now we reach an important professional concept:

> **SBOM — Software Bill of Materials**

It answers:

> "What software components are inside this application?"

Conceptually:

```text
AI LMS
├── Node.js
├── Express
├── Prisma
├── Zod
├── Axios
├── PDF parser
├── PostgreSQL client
└── ...
```

This becomes extremely useful during security incidents.

---

# 39. Why SBOM Matters

Imagine a critical vulnerability is announced:

```text
Critical vulnerability
in package XYZ
```

You need to answer:

> "Do we use XYZ?"

Without an SBOM:

```text
Search manually
      ↓
Maybe
      ↓
Hours of work
```

With an SBOM:

```text
Search inventory
      ↓
XYZ found
      ↓
Affected services identified
```

Much faster.

# 41. Don't Make CI Impossible to Use

Security gates need sensible policies.

For example:

```text
Critical → Block
High → Review/block depending on context
Moderate → Track
Low → Monitor
```

Don't blindly fail every build because:

```text
Some dependency has an irrelevant low-severity advisory
```

Otherwise developers may start bypassing security checks.

---

# 44. Dependency Update Strategy

A practical strategy:

### Patch update

```text
1.2.3 → 1.2.4
```

Usually lower risk.

### Minor update

```text
1.2.3 → 1.3.0
```

Potentially moderate risk.

### Major update

```text
1.x → 2.x
```

Potentially breaking.

Security fixes sometimes require major upgrades, so you can't simply avoid major updates.

---

# 45. Lockfile Review

When a dependency changes:

```text
package.json
package-lock.json
```

both may change.

Review the lockfile diff.

You don't necessarily need to manually understand every line, but watch for:

```text
Unexpected package additions
Unexpected registry URLs
Unexpected dependency changes
Unexpected version jumps
```

This can catch suspicious changes.

---

# 46. Package Registry Security

npm packages normally come from:

```text
npm registry
```

Be careful when using custom registries.

Your CI should have a clear understanding of:

```text
Which registry?
Which scope?
Which authentication?
Which packages?
```

Misconfigured registries can contribute to dependency confusion.

# 47. Package Provenance

# 51. CI Environment Isolation

Your CI runner should have only what it needs.

For example:

```text
Pull Request
 ↓
Run tests
 ↓
No production deployment secrets
```

Whereas:

```text
Main branch
 ↓
Deploy
 ↓
Production credentials available
```

This reduces the impact of malicious code introduced through a pull request.

---

# 52. Never Give Forked PRs Production Secrets

This is a major CI security concept.

Imagine an external contributor opens:

```text
Pull Request
```

If your workflow automatically exposes:

```text
PRODUCTION_DEPLOY_TOKEN
AI_API_KEY
CLOUD_SECRET
```

to untrusted code, you're creating a serious risk.

A safer architecture is:

```text
Untrusted PR
   ↓
Limited CI
   ↓
No production secrets
```

Then trusted workflows handle deployment separately.

```text

       ↓

       ↓

       ↓
```

Reproducibility is a security property as well as an engineering property.

# 54. Immutable Artifacts

```text

 ↓

 ↓

```

```text

 ↓
```

> **4. Verify packages before installing them, especially security-sensitive parsers.**

> **5. Treat Docker images and CI/CD actions as dependencies too.**

> **6. Keep CI permissions and secrets to the minimum required.**

> **7. Scan dependencies and container images continuously.**

> **8. Build and scan artifacts before production rather than installing random packages directly on production servers.**

> **9. Remove unnecessary dependencies.**

> **10. Keep a clear inventory of what software is actually inside your application.**
