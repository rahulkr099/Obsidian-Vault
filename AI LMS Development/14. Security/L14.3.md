# 🔐 Lesson 14.3 — API Security

Now we move from general OWASP concepts to something you will use **every day as a backend developer**:

> **How do we design and protect APIs so that users cannot abuse, bypass, or manipulate them?**

For your AI LMS, almost everything important eventually passes through an API:

```text
React Frontend
      ↓
     API
      ↓
 ┌────┼─────────────┐
 ↓    ↓             ↓
Auth LMS           AI
 ↓    ↓             ↓
       PostgreSQL
          │
        Redis
```

So if the API is weak, the whole application is weak.

---

# 1. What Is API Security?

API security means protecting your API against:

```text
Unauthorized access
Data exposure
Malicious input
Abuse
Brute force
Injection
Privilege escalation
Resource exhaustion
Information leakage
```

A secure API should answer:

```text
Who are you?
     ↓
Are you allowed?
     ↓
Is your input valid?
     ↓
Can you access this resource?
     ↓
Can you perform this operation?
     ↓
Are you abusing the API?
     ↓
What should we return?
     ↓
What should we log?
```

---

# 2. Start With the Request

Every request should be treated as **untrusted**.

Example:

```http
POST /api/v1/courses
Authorization: Bearer <token>
Content-Type: application/json

{
  "title": "JavaScript Course",
  "description": "Learn JavaScript"
}
```

Don't immediately think:

> "The frontend sent valid data."

Instead think:

```text
Request
  ↓
UNTRUSTED
  ↓
Validate
  ↓
Authenticate
  ↓
Authorize
  ↓
Process
```

---

# 4. Authentication

First question:

> **Who is making this request?**

Example:

```http
GET /api/v1/profile
Authorization: Bearer <access-token>
```

Your authentication middleware should:

```text
Token
 ↓
Verify
 ↓
Decode
 ↓
Identify user
 ↓
req.user
```

For example:

```ts
req.user = {
  userId: "123",
  role: "student"
};
```

But remember:

> The client should never be trusted to tell us its own role.

Bad:

```json
{
  "role": "admin"
}
```

Good:

```text
Token
 ↓
User ID
 ↓
Database
 ↓
Trusted role
```

---

# 5. Authorization

Authentication answers:

> Who are you?

Authorization answers:

> Are you allowed to do this?

Example:

```http
POST /api/v1/courses
```

Maybe:

```text
Student     ❌
Instructor  ✅
Admin       ✅
```

Middleware could conceptually look like:

```ts
authorize("instructor", "admin")
```

But role checking alone isn't always enough.

---

# 6. Role ≠ Resource Ownership

Suppose:

```text
Instructor A
   ↓
Course A

Instructor B
   ↓
Course B
```

Instructor A is allowed to edit courses.

But that doesn't mean Instructor A can edit **every** course.

You need:

```text
Role check
    +
Ownership check
```

Example:

```ts
if (course.instructorId !== req.user.userId) {
  throw new ForbiddenError("Not your course");
}
```

This is one of the most important API-security concepts for your LMS.

---

# 7. Never Trust IDs From the Client

Consider:

```http
GET /api/v1/users/123/progress
```

The client controls:

```text
123
```

Therefore ask:

> Is user `123` actually allowed to see this resource?

A vulnerable implementation:

```ts
const progress = await getProgress(req.params.userId);
```

A safer design may use the authenticated identity:

```ts
const progress = await getProgress(req.user.userId);
```

Or, for admin/instructor cases, explicitly authorize access to the requested user.

---

# 8. Input Validation

Every API accepts input.

Examples:

```text
req.body
req.params
req.query
headers
cookies
```

These should be validated.

Your project already uses **Zod**, so continue that pattern.

Example:

```ts
const createCourseSchema = z.object({
  title: z.string().trim().min(3).max(100),
  description: z.string().trim().max(5000),
});
```

Then:

```text
Request
   ↓
Zod
   ↓
Valid?
 ┌─┴─┐
No  Yes
↓     ↓
400   Controller
```

---

# 9. Why Validation Is Security

Suppose your endpoint expects:

```json
{
  "title": "React Course"
}
```

An attacker sends:

```json
{
  "title": "A",
  "unexpectedField": "...",
  "hugeField": "..."
}
```

Without validation, unexpected data may enter your application.

Validation gives you:

```text
Type safety
Business constraints
Size limits
Format restrictions
Unexpected-input protection
```

---

# 10. Validate Every Input Location

Don't validate only `req.body`.

Also consider:

### Params

```http
GET /courses/:courseId
```

Validate:

```text
courseId
```

### Query

```http
GET /courses?page=1&limit=20
```

Validate:

```text
page
limit
sort
filter
```

### Headers

Some headers influence security-sensitive behavior.

### Cookies

Authentication/session cookies must be handled carefully.

---

# 11. Request Size Limits

Imagine your endpoint accepts JSON.

An attacker sends:

```text
100 MB JSON payload
```

Why should your API accept that?

You can configure request-body limits.

Conceptually:

```ts
express.json({
  limit: "1mb"
});
```

The exact limit should depend on your application's requirements.

For file uploads, use separate and appropriate limits.

---

# 12. Rate Limiting

One of the most important API security controls.

Imagine:

```text
POST /auth/login
```

Attacker:

```text
Request 1
Request 2
Request 3
...
Request 100,000
```

Without protection, your API can be abused.

Rate limiting creates a boundary:

```text
User/IP
   ↓
Requests
   ↓
Rate limiter
   ↓
Allowed / blocked
```

---

# 13. Different Endpoints Need Different Limits

Don't necessarily use one global rate limit for everything.

For example:

```text
Login
   ↓
Strict

Password reset
   ↓
Strict

AI generation
   ↓
Strict + usage quota

Course browsing
   ↓
More relaxed

Health check
   ↓
Different policy
```

This is especially important for your AI LMS because AI requests can have a real monetary cost.

---

# 14. Rate Limit ≠ Usage Quota

These are related but different.

### Rate limit

Controls **how frequently** requests can be made.

```text
100 requests / minute
```

### Usage quota

Controls **how much a user can consume**.

For example:

```text
Student
   ↓
50 AI messages / day
```

You may eventually need both:

```text
Rate limiting
     +
AI usage quota
```

---

# 15. AI Endpoint Security

Consider:

```http
POST /api/v1/ai/chat
```

Potential abuse:

```text
Huge prompt
    ↓
Huge token usage
    ↓
Expensive API call
```

Or:

```text
Attacker
 ↓
Thousands of requests
 ↓
AI provider
 ↓
Huge bill
```

Therefore:

```text
Authentication
     ↓
Authorization
     ↓
Input size limit
     ↓
Rate limit
     ↓
Usage quota
     ↓
AI request
```

This is **application security + financial security**.

---

# 16. CORS

CORS stands for:

> Cross-Origin Resource Sharing

Suppose:

```text
Frontend
https://app.example.com

Backend
https://api.example.com
```

The browser needs permission to make certain cross-origin requests.

Your API should define which origins are allowed.

Conceptually:

```ts
cors({
  origin: "https://app.example.com"
});
```

Don't blindly use:

```ts
origin: "*"
```

especially when your architecture involves credentials.

---

# 17. CORS Is Not Authentication

This is a common misunderstanding.

CORS does **not** mean:

> "Only authorized users can access my API."

CORS is primarily a browser cross-origin policy.

An attacker can still make requests using tools such as:

```text
curl
Postman
custom scripts
server-side requests
```

Therefore:

```text
CORS
  ≠
Authentication
```

You need both where appropriate.

---

# 18. Security Headers

Security headers tell browsers how your application should behave.

Your Express application can use a security-header middleware such as Helmet.

Conceptually:

```ts
app.use(helmet());
```

Security headers can help with things such as:

```text
Clickjacking
MIME sniffing
Content security
Referrer behavior
Browser security policies
```

But don't think:

> "Helmet = secure application."

It is one layer of defense.

---

# 19. Content Security Policy

CSP stands for:

> Content Security Policy

It can restrict where browsers are allowed to load resources from.

Conceptually:

```text
script-src
style-src
img-src
connect-src
```

For your LMS, CSP becomes particularly interesting because you may have:

```text
React
AI interface
Videos
Images
Course content
External services
```

A strict policy can reduce the impact of some XSS attacks.

---

# 20. Error Handling

Your API should not expose internal implementation details.

Bad:

```json
{
  "error": "PrismaClientKnownRequestError...",
  "stack": "..."
}
```

Potentially exposed:

```text
Database details
File paths
Internal architecture
Stack traces
Library information
```

Better:

```json
{
  "success": false,
  "message": "Something went wrong"
}
```

And internally:

```text
Application
   ↓
Logger
   ↓
Detailed error
```

while the client receives:

```text
Safe error
```

---

# 21. Don't Leak Sensitive Data in Errors

Never accidentally return:

```text
Passwords
Tokens
API keys
Database URLs
Internal secrets
Stack traces
```

Even this can be dangerous:

```ts
res.json({
  user
});
```

if `user` contains:

```text
passwordHash
refreshToken
resetToken
```

Use explicit response DTOs.

---

# 22. Secure Response Design

Think about what the client actually needs.

Database object:

```text
User
├── id
├── name
├── email
├── passwordHash
├── refreshToken
├── resetToken
└── role
```

Public response:

```json
{
  "id": "123",
  "name": "Rahul",
  "email": "example@email.com",
  "role": "student"
}
```

This is **data minimization**.

---

# 23. HTTP Methods

Use HTTP methods intentionally.

```text
GET
POST
PATCH
PUT
DELETE
```

Example:

```text
GET    /courses
POST   /courses
PATCH  /courses/:id
DELETE /courses/:id
```

Don't use:

```text
GET /delete-course?id=123
```

for destructive operations.

Why?

Because GET is generally expected to be safe/read-oriented, and accidental triggering can become dangerous.

---

# 24. API Versioning

You've already covered API versioning earlier.

Continue using:

```text
/api/v1/...
```

Why does this help security?

Because you can eventually:

```text
v1 → old behavior
v2 → hardened behavior
```

and migrate clients safely.

It also makes security changes easier to manage.

---

# 25. Pagination Is Also Security

Suppose you have:

```http
GET /api/v1/users
```

and someone requests:

```text
?limit=10000000
```

That's potentially a resource-exhaustion problem.

Never allow unlimited queries.

Use something like:

```text
default limit = 20
maximum limit = 100
```

Conceptually:

```ts
const limit = Math.min(requestedLimit, 100);
```

Better still, validate it with your schema.

---

# 26. Filtering and Sorting

Consider:

```http
GET /courses?sort=createdAt
```

Don't blindly inject arbitrary client values into database queries.

Prefer an allowlist:

```text
Allowed sort fields:

createdAt
updatedAt
title
rating
```

Then:

```text
Unknown field
     ↓
Reject
```

This is another example of **never trusting client input**.

---

# 27. Prevent Mass Assignment

Imagine:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

and you do:

```ts
await prisma.user.update({
  where: { id },
  data: req.body,
});
```

🚨 Dangerous.

The client may modify fields it shouldn't.

Instead explicitly select allowed fields:

```ts
const updateData = {
  name: req.body.name,
  bio: req.body.bio,
};
```

This is an extremely useful backend security pattern.

# 28. API Security and Your Service/Repository Architecture

Your architecture:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

is actually helpful for security.

### Controller

Handles:

```text
Request
Validation
Response
```

### Service

Handles:

```text
Business rules
Authorization decisions
Resource ownership
```

### Repository

Handles:

```text
Database access
```

For example:

```text
Controller
   ↓
createLesson()
   ↓
Service
   ├── verify user
   ├── verify instructor role
   ├── verify course ownership
   └── create lesson
          ↓
      Repository
          ↓
      PostgreSQL
```

This keeps security logic organized.

---

# 29. Don't Put All Security in Middleware

You might have:

```ts
authenticate
authorize("instructor")
```

but that's not always enough.

Why?

Because:

```text
Instructor A
```

and:

```text
Instructor B
```

may have the same role but different resources.

Therefore:

```text
Middleware
    ↓
Role check

Service
    ↓
Ownership check
```

This is a very useful pattern.

---

# 30. API Security and Database Security

Never assume:

```text
API authorization
     ↓
Database automatically safe
```

Suppose:

```ts
await prisma.course.findUnique({
  where: {
    id: courseId,
  },
});
```

You may need:

```ts
await prisma.course.findFirst({
  where: {
    id: courseId,
    instructorId: userId,
  },
});
```

Now the database query itself reinforces ownership.

That's **defense in depth**.

# 31. Secure API Flow — LMS Example

Suppose an instructor wants to update a course:

```http

Authorization: Bearer <token>
```

A secure flow:

```text
Request
   ↓
CORS / security middleware
   ↓
Rate limit
   ↓
Authentication
   ↓
Validate courseId
   ↓
Validate request body
   ↓
Check instructor role
   ↓
Load course
   ↓
Check ownership
   ↓
Update allowed fields
   ↓
Database
   ↓
Audit important action
   ↓
Safe response
```

That's what API security looks like in practice.

# 🧠 36. The Most Important API Security Rules

If you remember only these, you're already making good progress:

### Rule 1

> **Never trust the client.**

### Rule 2

> **Authentication does not mean authorization.**

### Rule 3

> **Role checks are not enough; check resource ownership.**

### Rule 4

> **Validate every external input.**

### Rule 5

> **Limit how much work a request can cause.**

### Rule 6

> **Return only the data the client needs.**

### Rule 7

> **Don't expose internal errors.**

### Rule 8

> **Protect expensive endpoints differently from cheap endpoints.**

### Rule 9

> **Security should exist at multiple layers.**

### Rule 10

> **Log important security events, but never log secrets.**
