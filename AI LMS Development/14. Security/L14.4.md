# 🔐 Lesson 14.4 — Authentication Hardening

In Lesson 14.3, we secured the **API layer**.

Now we're going deeper into one of the most sensitive parts of your AI LMS:

> **Authentication — making sure an attacker cannot easily become another user.**

Your authentication system is the gateway to everything:

```text
                    User
                      │
                      ↓
                   Login
                      │
                      ↓
              Authentication
                      │
                      ↓
              ┌───────┴───────┐
              ↓               ↓
        Access Token     Refresh Token
              │               │
              ↓               ↓
          API Access      New Access Token
                              │
                              ↓
                         Protected APIs
```

If authentication is compromised:

```text
Student account
      ↓
Attacker
      ↓
Private courses
AI conversations
Progress
Personal data
```

So authentication deserves strong protection.

---

# 1. Authentication vs Authorization

First, keep this distinction clear.

### Authentication

> **Who are you?**

```text
Email + Password
       ↓
Verify identity
       ↓
User authenticated
```

### Authorization

> **What are you allowed to do?**

```text
Authenticated User
       ↓
Student?
Instructor?
Admin?
       ↓
Permissions
```

The flow is:

```text
Authentication
      ↓
Authorization
```

Not the other way around.

---

# 2. What Does Authentication Need to Protect?

Your LMS authentication system contains several sensitive assets:

```text
Passwords
Password hashes
Access tokens
Refresh tokens
Reset tokens
Email verification tokens
Sessions
User identities
Authentication cookies
```

A security mistake involving any of these can lead to **account takeover**.

---

# 3. Password Security

Never store passwords directly.

Bad:

```text
email: user@example.com
password: Rahul123
```

❌ Never.

Instead:

```text
User password
     ↓
Password hashing
     ↓
Password hash
     ↓
PostgreSQL
```

When the user logs in:

```text
Entered password
       ↓
Password verification
       ↓
Stored hash
       ↓
Match?
```

You don't decrypt the stored password.

---

# 4. Password Hashing ≠ Encryption

This is important.

### Encryption

```text
Plaintext
   ↓
Encryption
   ↓
Ciphertext
   ↓
Decryption
   ↓
Plaintext
```

### Password hashing

```text
Password
   ↓
Hash
   ↓
Stored hash
```

The application verifies the password against the hash rather than decrypting a stored password.

Use a password-hashing algorithm designed for passwords, such as:

```text
Argon2id
bcrypt
```

For a new system, **Argon2id is an excellent modern choice** when supported by your stack.

---

# 5. Why Fast Hashing Is Bad for Passwords

Developers normally want fast algorithms.

For passwords, that's not ideal.

Imagine an attacker has:

```text
10 billion password guesses
```

If password hashing is extremely fast:

```text
10 billion
    ↓
Very quickly
```

That's dangerous.

Password hashing should deliberately be expensive enough to make large-scale guessing harder.

---

# 6. Password Policy

Don't rely only on:

```text
At least 8 characters
```

A better approach is to encourage:

```text
Long passwords
Unique passwords
No commonly breached passwords
```

Also avoid unnecessarily strange rules like:

```text
Must contain:
1 uppercase
1 lowercase
1 number
1 symbol
```

if they cause users to choose predictable patterns.

The goal is:

> **Strong and hard-to-guess passwords, without making authentication unnecessarily frustrating.**

---

# 7. Login Flow

A secure login flow conceptually looks like:

```text
POST /auth/login
       ↓
Validate input
       ↓
Find user
       ↓
Verify password
       ↓
Check account state
       ↓
Create authentication session/tokens
       ↓
Return safe response
```

Never do:

```text
Find user
   ↓
Password incorrect
   ↓
"Email doesn't exist"
```

and:

```text
Find user
   ↓
Password incorrect
   ↓
"Wrong password"
```

This can reveal whether an account exists.

---

# 8. Prevent User Enumeration

Consider:

```http
POST /auth/login
```

Attacker tries:

```text
v@example.com
admin@example.com
rahul@example.com
...
```

If your API responds:

```text
"User does not exist"
```

for unknown users and:

```text
"Wrong password"
```

for existing users, attackers can discover registered accounts.

Prefer a generic message such as:

```text
"Invalid email or password."
```

---

# 9. Brute-Force Attacks

An attacker can repeatedly try passwords:

```text
login attempt
login attempt
login attempt
login attempt
...
```

Controls include:

```text
Rate limiting
Progressive delays
Account protection
Monitoring
Strong password hashing
MFA where appropriate
```

For example:

```text
5 failed attempts
       ↓
Temporarily slow authentication
```

Be careful with permanent account lockouts because attackers can intentionally lock other users out.

---

# 10. Credential Stuffing

Credential stuffing is different from brute force.

The attacker may already have:

```text
email + password
```

from another website breach.

They try the same credentials on your LMS.

```text
Old Website
    ↓
Leaked credentials
    ↓
Your LMS
```

This is why:

```text
Unique passwords
+
Rate limiting
+
MFA
+
Login monitoring
```

are useful.

---

# 11. Access Tokens

After successful authentication, your application needs a way to recognize the user on subsequent requests.

One approach is an access token.

```text
Login
  ↓
Access Token
  ↓
API requests
```

Example:

```http
Authorization: Bearer <access-token>
```

The server verifies it and identifies the user.

---

# 12. Access Tokens Should Be Short-Lived

Suppose an attacker steals an access token.

If it lasts:

```text
30 days
```

the attacker may have a long time to use it.

Instead, access tokens are generally better kept relatively short-lived.

Conceptually:

```text
Access Token
    ↓
Short lifetime
    ↓
Expires
    ↓
Refresh process
```

The exact duration depends on your application's threat model and session requirements.

---

# 13. Refresh Tokens

This solves an important usability problem.

If access tokens expire frequently, users shouldn't have to log in again constantly.

So:

```text
Access Token
    ↓
Short-lived

Refresh Token
    ↓
Longer-lived
```

When the access token expires:

```text
Client
  ↓
Refresh token
  ↓
/auth/refresh
  ↓
New access token
```

---

# 14. The Danger of Refresh Tokens

Refresh tokens are powerful.

Whoever possesses a valid refresh token may be able to obtain new access tokens.

Therefore:

> **Treat refresh tokens like highly sensitive credentials.**

If an attacker steals one:

```text
Refresh Token
      ↓
New Access Token
      ↓
Protected APIs
```

So refresh-token protection is extremely important.

---

# 15. Refresh Token Rotation

A strong strategy is **refresh-token rotation**.

Conceptually:

```text
Refresh Token A
      ↓
Refresh
      ↓
Refresh Token B
      ↓
Refresh
      ↓
Refresh Token C
```

The previous token becomes invalid.

If an old refresh token is reused:

```text
Old Refresh Token
       ↓
Reuse detected
       ↓
Possible token theft
       ↓
Invalidate session/family
```

This makes stolen refresh tokens harder to abuse.

---

# 16. Refresh Token Storage

You previously used refresh-token storage in your backend architecture.

A better production pattern is to avoid storing a raw refresh token directly when possible.

Instead:

```text
Refresh Token
      ↓
Hash
      ↓
Database
```

Then when a refresh request arrives:

```text
Presented token
      ↓
Hash / verify
      ↓
Compare with stored value
```

If your database is compromised, storing only token hashes reduces the value of the stolen database data.

---

# 17. Refresh Token Database Model

A dedicated session/token table can be useful.

For example:

```text
RefreshSession

id
userId
tokenHash
expiresAt
createdAt
revokedAt
deviceInfo
ipAddress
```

Then:

```text
User
 │
 ├── Session A
 ├── Session B
 └── Session C
```

This lets you manage sessions individually.

---

# 18. Session Management

Imagine Rahul logs in from:

```text
Laptop
Phone
College computer
```

You might have:

```text
Session A → Laptop
Session B → Phone
Session C → College PC
```

A good security design can allow:

```text
Revoke one session
Revoke all sessions
```

This is extremely useful if a device is lost.

---

# 19. Logout

Logout should do more than:

```text
delete token from frontend
```

The server should invalidate the appropriate session/refresh token.

Conceptually:

```text
Logout
  ↓
Refresh session revoked
  ↓
Client clears authentication state
```

Otherwise, a previously issued refresh token may remain usable.

---

# 20. Password Change

Suppose a user changes their password.

What should happen to existing sessions?

A strong security policy is:

```text
Password changed
      ↓
Invalidate existing sessions
      ↓
Require re-authentication
```

This is especially important if the password was changed because the user suspected account compromise.

---

# 21. "Logout Everywhere"

A useful LMS security feature:

```text
Settings
   ↓
Security
   ↓
Logout all devices
```

Backend:

```text
UPDATE sessions
SET revokedAt = NOW()
WHERE userId = ?
```

Then all refresh sessions become invalid.

---

# 22. Secure Cookies

If you use cookies for authentication/session information, important attributes include:

```text
HttpOnly
Secure
SameSite
```

### HttpOnly

JavaScript cannot directly read the cookie.

This can reduce token theft through some XSS scenarios.

### Secure

Cookie is sent only over HTTPS.

### SameSite

Controls cross-site cookie behavior and can help reduce CSRF risk.

---

# 23. Cookie Example

Conceptually:

```ts
res.cookie("refreshToken", token, {
  httpOnly: true,
  secure: true,
  sameSite: "lax",
});
```

The exact `SameSite` policy depends on your frontend/backend deployment architecture.

For example, if your application requires cross-site cookie behavior, the configuration becomes more complex and CSRF protection becomes especially important.

---

# 24. localStorage vs HttpOnly Cookie

This is a common discussion.

### localStorage

```text
JavaScript
   ↓
localStorage
   ↓
Access token
```

Advantages:

```text
Easy to use
Simple SPA integration
```

Risk:

```text
XSS can potentially access the token.
```

### HttpOnly cookie

```text
Browser
   ↓
HttpOnly cookie
```

JavaScript cannot directly read it.

But cookie-based authentication requires careful consideration of:

```text
CSRF
SameSite
CORS
Cross-origin architecture
```

There is no universal one-line answer.

For a production application, choose based on the whole architecture rather than copying a popular tutorial.

---

# 25. CSRF

If authentication uses cookies, the browser automatically sends cookies with applicable requests.

That creates a CSRF concern.

Conceptually:

```text
Victim logged into LMS
       ↓
Visits malicious website
       ↓
Browser sends authenticated request
       ↓
LMS
```

CSRF defenses can include:

```text
SameSite cookies
CSRF tokens
Origin/Referer validation where appropriate
Careful CORS configuration
```

We'll study web security in greater depth in **14.6**.

---

# 26. Password Reset

Password reset is one of the most security-sensitive endpoints.

Typical flow:

```text
Forgot Password
      ↓
Email
      ↓
Random reset token
      ↓
User clicks link
      ↓
Verify token
      ↓
Set new password
```

The reset token should generally be:

```text
Random
Unpredictable
Short-lived
Single-use
```

---

# 27. Never Put Passwords in Reset URLs

Don't do:

```text
https://example.com/reset?password=...
```

Obviously, that would be disastrous.

Instead:

```text
https://example.com/reset?token=<random-token>
```

Then the backend verifies the token.

---

# 28. Reset Token Storage

Similar to refresh tokens, you can store a hash:

```text
Reset Token
     ↓
Hash
     ↓
Database
```

Your database might contain:

```text
userId
tokenHash
expiresAt
usedAt
```

Once used:

```text
usedAt = current time
```

The token cannot be reused.

---

# 29. Email Verification

A typical flow:

```text
Registration
     ↓
Create user
     ↓
emailVerified = false
     ↓
Send verification token
     ↓
User clicks link
     ↓
Verify token
     ↓
emailVerified = true
```

This can help ensure that the account's email address is controlled by the user.

---

# 30. Account States

Instead of thinking only:

```text
User exists
```

your system may eventually need states such as:

```text
ACTIVE
SUSPENDED
DISABLED
EMAIL_UNVERIFIED
DELETED
```

Then authentication can consider:

```text
Valid credentials
       ↓
Account state
       ↓
Allowed?
```

A suspended account shouldn't simply become usable because the password is correct.

---

# 31. Brute-Force Protection Architecture

For:

```http
POST /auth/login
```

you can combine:

```text
Input validation
      ↓
Rate limit
      ↓
User lookup
      ↓
Password verification
      ↓
Login result
      ↓
Security event logging
```

For repeated failures:

```text
Monitor
   ↓
Detect unusual activity
   ↓
Slow/block requests
```

Be careful not to make your system easy to abuse for account lockout attacks.

---

# 32. MFA — Multi-Factor Authentication

Password authentication is one factor:

```text
Something you know
```

MFA adds another factor, such as:

```text
Something you have
```

or:

```text
Something you are
```

For example:

```text
Password
   +
Authenticator code
```

For your LMS, MFA could be particularly useful for:

```text
Admin accounts
Instructor accounts
High-risk actions
```

We don't necessarily need to force MFA on every student immediately.

---

# 33. Reauthentication for Sensitive Actions

Suppose an authenticated user wants to:

```text
Change password
Change email
Delete account
Disable MFA
View security sessions
```

Being logged in for months shouldn't necessarily be enough.

For sensitive operations:

```text
Current session
      ↓
Reauthenticate
      ↓
Sensitive action
```

This reduces damage from stolen sessions.

---

# 34. Token Theft Scenario

Let's simulate an attack.

```text
Attacker steals access token
        ↓
Calls LMS API
```

If token is short-lived:

```text
Limited attack window
```

If the attacker also gets a refresh token:

```text
Refresh token
      ↓
New access token
      ↓
Persistent access
```

This is why:

```text
Refresh token protection
+
Rotation
+
Revocation
+
Session management
```

are critical.

---

# 35. Token Revocation

JWTs are often described as "stateless."

But security requirements can make pure statelessness complicated.

Suppose:

```text
JWT valid for 15 minutes
```

You cannot necessarily make the already-issued JWT magically disappear unless you introduce a server-side control mechanism.

Possible strategies include:

```text
Short access-token lifetime
+
Refresh-token revocation
+
Session store
+
Token versioning
```

This is why refresh sessions are useful.

---

# 36. Token Versioning

Another useful technique:

Database:

```text
userId
tokenVersion = 3
```

Token:

```text
userId
tokenVersion = 3
```

If you need to invalidate all tokens:

```text
tokenVersion = 4
```

Now tokens containing version `3` are rejected.

This can be useful for events such as:

```text
Password change
Account compromise
Force logout
Security reset
```

There are tradeoffs, so we'll choose the approach that fits your architecture rather than blindly adding every technique.

---

# 37. Authentication Logging

Useful security events:

```text
LOGIN_SUCCESS
LOGIN_FAILURE
LOGOUT
PASSWORD_CHANGED
PASSWORD_RESET_REQUESTED
PASSWORD_RESET_COMPLETED
EMAIL_VERIFIED
SESSION_REVOKED
ALL_SESSIONS_REVOKED
MFA_ENABLED
MFA_DISABLED
```

Example:

```json
{
  "event": "LOGIN_FAILURE",
  "userId": "123",
  "requestId": "req_456",
  "timestamp": "..."
}
```

But never log:

```text
password
accessToken
refreshToken
API key
resetToken
```

---

# 38. Suspicious Login Detection

Later you could detect patterns like:

```text
20 failed logins
       ↓
Same account
       ↓
Different IPs
       ↓
Short period
```

Or:

```text
Successful login
       ↓
Unusual location/device
       ↓
Sensitive operation
```

Your application can respond with:

```text
Additional verification
Session revocation
Security notification
Temporary restrictions
```

Don't blindly block based on one signal; false positives are a real concern.

---

# 39. Authentication Architecture for Your LMS

A mature design could look like:

```text
                         USER
                           │
                           ↓
                    POST /login
                           │
                           ↓
                    Input Validation
                           │
                           ↓
                     Rate Limiting
                           │
                           ↓
                    Password Verify
                           │
                           ↓
                    Account Status
                           │
                           ↓
               ┌───────────┴───────────┐
               ↓                       ↓
        Access Token            Refresh Session
        Short-lived             Long-lived
               │                       │
               │                  Hash in DB
               │                       │
               ↓                       ↓
             APIs                  /refresh
                                       │
                                       ↓
                              Rotation + Revocation
```


And:

# 41. Security Properties We Want

Your authentication system should achieve:

```text
Confidentiality
      ↓
Credentials remain secret

Integrity
      ↓
Tokens cannot be modified into valid identities

Availability
      ↓
Authentication remains usable

Account isolation
      ↓
User A cannot become User B

Session control
      ↓
Sessions can be revoked

Auditability
      ↓
Important authentication events are recorded
```

---

# 42. Authentication Threat Model

Let's map common threats.

|Threat|Example|Defense|
|---|---|---|
|Brute force|Repeated password guesses|Rate limiting|
|Credential stuffing|Reused leaked password|MFA + monitoring|
|Token theft|Stolen access token|Short lifetime|
|Refresh-token theft|Stolen refresh token|Rotation + revocation|
|Session hijacking|Stolen session|Secure transport/cookies|
|User enumeration|Different login errors|Generic errors|
|Reset abuse|Reused reset token|Short-lived single-use token|
|Account takeover|Compromised password|MFA + monitoring|
|Session persistence|Old sessions remain active|Session revocation|
|Privilege abuse|Student becomes admin|Server-side authorization|

---

# 43. Common Beginner Mistakes

### ❌ Mistake 1

Putting sensitive tokens into URLs:

```text
/api/refresh?token=...
```

URLs can appear in logs, browser history, proxies, etc.

---

### ❌ Mistake 2

Returning sensitive user objects directly:

```js
res.json(user);
```

---

### ❌ Mistake 3

Trusting the client's role:

```js
if (req.body.role === "admin")
```

---

### ❌ Mistake 4

Never expiring sessions.

---

### ❌ Mistake 5

Never revoking refresh tokens.

---

### ❌ Mistake 6

No rate limiting on login.

---

### ❌ Mistake 7

Logging authentication tokens.

---

### ❌ Mistake 8

Using the same secret everywhere.

```text
development
staging
production
```

Each environment should have properly separated secrets.

---

# 44. Your Authentication Security Checklist

Use this when reviewing your LMS:

```text
[ ] Passwords are securely hashed
[ ] Password hashes are never returned
[ ] Login input is validated
[ ] Login is rate limited
[ ] Generic authentication errors
[ ] Access tokens expire
[ ] Refresh tokens are protected
[ ] Refresh tokens can be revoked
[ ] Refresh token rotation considered
[ ] Sessions can be invalidated
[ ] Logout invalidates the server-side session
[ ] Password changes can revoke sessions
[ ] Reset tokens are random
[ ] Reset tokens expire
[ ] Reset tokens are single-use
[ ] Email verification is secure
[ ] Account states are enforced
[ ] Sensitive actions can require reauthentication
[ ] MFA considered for privileged users
[ ] Authentication events are logged
[ ] Secrets are never logged
[ ] HTTPS is enforced in production
[ ] Cookies use appropriate security flags
```
