# 🗄️ Lesson 14.7 — Database Security

Now we move to one of the most important layers of your AI LMS:

```text
React
   ↓
Express API
   ↓
Authorization
   ↓
Prisma
   ↓
PostgreSQL
```

Everything eventually reaches the database.

If the database is compromised, an attacker could potentially access:

```text
Users
Courses
Enrollments
Progress
Quizzes
AI conversations
RAG documents
Refresh sessions
Audit logs
```

So database security is not simply:

> "Prevent SQL injection."

It is about protecting the **entire data layer**.

---

# 1. What Database Security Means

Database security means protecting:

```text
Confidentiality
Integrity
Availability
```

### Confidentiality

Unauthorized users shouldn't see data.

```text
Student A
   ↓
❌ Student B's private data
```

### Integrity

Unauthorized users shouldn't modify data.

```text
Student
   ↓
❌ Change course ownership
```

### Availability

The database should remain usable.

```text
Attacker
   ↓
Huge expensive queries
   ↓
Database overloaded
```

So:

```text
Database Security
       │
 ┌─────┼─────┐
 ↓     ↓     ↓
Data  Access Availability
```

---

# 2. Your Database Attack Surface

Your LMS database isn't exposed through only one thing.

Think:

```text
                    PostgreSQL
                        │
        ┌───────────────┼───────────────┐
        ↓               ↓               ↓
     Prisma          Database       Backups
        │             Users            │
        ↓               │              ↓
     Express            │          Backup Files
        │               │
        ↓               ↓
     API Users       Admin/Dev
```

Potential attack surfaces:

```text
Database credentials
Connection strings
API queries
Raw SQL
Prisma queries
Migrations
Backups
Database users
Admin tools
Logs
Development environments
Production infrastructure
```

---

# 3. The Most Important Rule

> **Your PostgreSQL database should never be directly exposed to the public internet unless there is a very strong operational reason and appropriate controls.**

Your normal architecture should be:

```text
Internet
   ↓
Frontend
   ↓
API
   ↓
Private Database
```

Not:

```text
Internet
   ↓
PostgreSQL
```

The API should act as the controlled boundary.

---

# 4. Database Credentials

Your application needs something like:

```env
DATABASE_URL="postgresql://..."
```

This is sensitive.

Never put it into:

```text
React
GitHub
Screenshots
Frontend environment variables
Public logs
Client-side JavaScript
```

Correct:

```text
React
   ↓
Express
   ↓
DATABASE_URL
   ↓
PostgreSQL
```

The browser should never know your database credentials.

---

# 5. Database Least Privilege

This is one of the most important concepts.

Suppose your application connects to PostgreSQL using:

```text
postgres
```

with full administrative privileges.

That's convenient.

But it's dangerous.

Imagine:

```text
Application vulnerability
       ↓
Database credentials compromised
       ↓
Attacker becomes database superuser
       ↓
Everything is exposed
```

Instead:

```text
Application
    ↓
Limited DB User
    ↓
Only required permissions
```

This is **least privilege**.

---

# 6. Database Users

Conceptually, production could have separate roles such as:

```text
postgres-admin
      ↓
Administrative operations

lms-app
      ↓
Normal application queries

migration-user
      ↓
Schema migrations
```

The application doesn't need unrestricted administrative power.

This limits the blast radius of a compromise.

---

# 7. Blast Radius

Suppose your application is compromised.

### Bad:

```text
App compromised
     ↓
DB superuser
     ↓
DROP DATABASE
CREATE ROLE
Read everything
Modify everything
```

### Better:

```text
App compromised
     ↓
Limited DB role
     ↓
Only permitted operations
```

This is called reducing the **blast radius**.

Security isn't only:

> "Can we prevent every attack?"

It's also:

> **"What happens if one layer is compromised?"**

---

# 8. SQL Injection

Now let's revisit injection from a database perspective.

Bad:

```js
const query = `
  SELECT *
  FROM users
  WHERE email = '${email}'
`;
```

If the input is malicious, it may alter the SQL statement.

The fundamental problem is:

```text
User Input
   ↓
String concatenation
   ↓
SQL command
```

Don't construct SQL this way.

---

# 9. Parameterized Queries

The safer pattern is:

```text
User input
    ↓
Parameter
    ↓
SQL engine
```

The database treats the parameter as data rather than SQL syntax.

Prisma's normal query APIs handle parameterization for you.

For example:

```ts
await prisma.user.findUnique({
  where: {
    email,
  },
});
```

This is preferable to constructing SQL manually.

---

# 10. Prisma Does Not Make You Invincible

This is important.

Using Prisma does **not** mean:

```text
Prisma
 ↓
100% security
```

You can still create vulnerabilities through:

```text
Raw SQL
Unsafe query construction
Bad authorization
Sensitive data exposure
Mass assignment
Bad database permissions
Poor schema design
Untrusted migrations
Unsafe external tools
```

The ORM protects certain classes of problems, but **your application logic still has to be secure**.

---

# 11. Prisma Raw SQL

Sometimes raw SQL is necessary.

For example:

```ts
prisma.$queryRaw(...)
```

Raw SQL needs extra care.

The safe principle is:

```text
Use parameterized values
```

and avoid manually concatenating untrusted input into SQL.

Conceptually:

```text
❌ User input + SQL string

✅ SQL + parameterized user input
```

Whenever you use raw SQL, perform a security review.

---

# 12. Authorization Is Still Required

Imagine your API correctly uses Prisma:

```ts
await prisma.progress.findMany({
  where: {
    userId,
  },
});
```

The query may be perfectly safe from SQL injection.

But where did `userId` come from?

If it came from:

```http
GET /progress/:userId
```

and the server doesn't check authorization, you can still have:

```text
BOLA / IDOR
```

So:

```text
SQL Injection protection
        ≠
Authorization
```

Both are required.

---

# 13. Database Scoping

A powerful security pattern is to include authorization conditions in database queries.

Instead of:

```ts
const course = await prisma.course.findUnique({
  where: {
    id: courseId,
  },
});
```

you might use a query that also represents ownership when appropriate:

```ts
const course = await prisma.course.findFirst({
  where: {
    id: courseId,
    instructorId: userId,
  },
});
```

Now:

```text
Course ID
    +
Instructor ID
    ↓
Database
```

The database returns the resource only if both conditions match.

---

# 14. Why Database Scoping Is Powerful

Imagine a bug accidentally removes a service-layer ownership check.

If the query itself is scoped:

```text
courseId
+
instructorId
```

the database still refuses to return another instructor's course.

This is:

> **Defense in depth.**

---

# 15. Database Constraints

Your database should enforce important invariants whenever possible.

Examples:

```text
NOT NULL
UNIQUE
FOREIGN KEY
CHECK
PRIMARY KEY
```

Don't rely only on your application code.

For example:

```text
email must be unique
```

Don't rely solely on:

```ts
if (existingUser) {
  throw ...
}
```

Also enforce uniqueness at the database level.

---

# 16. Why Database Constraints Matter

Imagine two requests arrive simultaneously:

```text
Request A → check email
Request B → check email
```

Both see:

```text
No user exists
```

Both attempt:

```text
INSERT
```

Without a database-level unique constraint:

```text
Duplicate email
```

With:

```text
UNIQUE(email)
```

PostgreSQL itself protects the invariant.

This is much safer.

---

# 17. Foreign Keys

Suppose:

```text
Course
   ↓
Lesson
```

A lesson should belong to a valid course.

A foreign key can enforce:

```text
lesson.courseId
      ↓
course.id
```

This prevents invalid relationships.

Without constraints, you could accidentally end up with:

```text
Lesson
courseId = 999999

Course 999999
doesn't exist
```

That's bad data integrity.

---

# 18. Referential Integrity

For your LMS:

```text
User
 │
 ├── Enrollment
 │       │
 │       └── Course
 │
 └── Progress
         │
         └── Lesson
```

Foreign keys help ensure these relationships remain valid.

Database constraints aren't just "database theory."

They are security and integrity controls.

---

# 19. CHECK Constraints

Suppose progress percentage must be:

```text
0 ≤ progress ≤ 100
```

Your application can validate it.

But the database can also enforce the invariant.

Conceptually:

```sql
CHECK (progress >= 0 AND progress <= 100)
```

Then even if a bug appears in the API:

```text
progress = 999
```

PostgreSQL rejects it.

---

# 20. Sensitive Data

Your database may eventually contain:

```text
email
name
phone
learning history
quiz results
AI conversations
```

Some of this can be sensitive.

Ask:

```text
Do we need to store it?
Who needs access?
How long should we keep it?
Should it be encrypted?
Should it be anonymized?
```

This is **data minimization**.

---

# 21. Don't Store Data "Just in Case"

A common mistake:

```text
"We might need this later."
```

Then the database becomes:

```text
User
├── everything
├── old tokens
├── unnecessary metadata
├── unnecessary personal data
└── old secrets
```

More data means:

```text
More attack surface
More privacy risk
More backup exposure
More compliance concerns
```

Store what you actually need.

---

# 22. Password Hashes

Your database will store:

```text
passwordHash
```

not:

```text
password
```

But remember:

> A password hash is still sensitive.

If an attacker obtains password hashes, they can attempt offline password cracking.

Therefore:

```text
Password hash
   ↓
Protected database
   ↓
Limited DB access
   ↓
Encrypted backups
```

---

# 23. Refresh Token Data

If you're using refresh-token sessions, don't casually store raw long-lived tokens.

Prefer:

```text
refresh token
     ↓
hash
     ↓
database
```

Then your session table could contain:

```text
id
userId
tokenHash
expiresAt
revokedAt
createdAt
```

This reduces the value of a database leak.

---

# 24. Database Encryption

There are several layers to think about.

### Encryption in transit

```text
Application
     ↓
TLS
     ↓
PostgreSQL
```

### Encryption at rest

```text
Disk
 ↓
Encrypted storage
```

### Application-level encryption

For especially sensitive fields:

```text
Sensitive value
      ↓
Encryption
      ↓
Database
```

These solve different problems.

---

# 25. Don't Automatically Encrypt Everything

Encryption has tradeoffs.

Suppose you encrypt:

```text
email
```

then searching:

```text
WHERE email = ?
```

becomes more complicated.

So ask:

```text
How sensitive is this data?
Do we need searchable fields?
Who should decrypt it?
Where is the encryption key stored?
What happens during key rotation?
```

Use encryption deliberately.

---

# 26. Database Credentials in Production

Never commit:

```env
DATABASE_URL=postgresql://user:password@host/db
```

to Git.

Bad:

```text
GitHub
   ↓
.env
   ↓
DATABASE_URL
```

Better:

```text
Secret Manager / Deployment Secrets
             ↓
         Application
             ↓
       DATABASE_URL
```

Your production secret should be managed by your deployment environment.

---

# 27. Database Network Security

Ideally:

```text
Internet
   ↓
API
   ↓
Private network
   ↓
PostgreSQL
```

Not:

```text
Internet
   ↓
PostgreSQL :5432
```

If PostgreSQL must be remotely accessible, use appropriate network restrictions, TLS, strong authentication, and firewall/security-group controls.

---

# 28. PostgreSQL Port

The default PostgreSQL port is:

```text
5432
```

You shouldn't assume:

```text
0.0.0.0:5432
```

is appropriate for production.

Prefer network-level restrictions:

```text
Only API server
       ↓
PostgreSQL
```

rather than:

```text
Everyone
       ↓
PostgreSQL
```

---

# 29. Database Connection Security

Your application may create many database connections.

If attackers can cause unlimited connections:

```text
Requests
   ↓
Connections
   ↓
PostgreSQL
   ↓
Resource exhaustion
```

Use:

```text
Connection pooling
Connection limits
Timeouts
Query limits
```

Your infrastructure and Prisma configuration should be designed to avoid exhausting database connections.

---

# 30. Slow Queries Can Become Security Problems

Suppose an endpoint allows:

```http
GET /courses?search=...
```

and generates an extremely expensive query.

An attacker may repeatedly call it:

```text
Expensive query
Expensive query
Expensive query
...
```

Eventually:

```text
PostgreSQL CPU ↑
Response time ↑
Connection usage ↑
Application slows
```

That's a form of resource exhaustion.

So database performance and database security are connected.

---

# 31. Pagination

Never allow:

```http
GET /users?limit=100000000
```

Use:

```text
Default limit
Maximum limit
```

For example:

```text
default = 20
max = 100
```

and validate it.

This prevents clients from accidentally or intentionally requesting huge datasets.

---

# 32. Avoid Returning Entire Tables

Bad:

```ts
const users = await prisma.user.findMany();
```

for a public endpoint.

You may return:

```text
Thousands of users
Sensitive fields
Huge response
```

Instead:

```text
Pagination
+
Selected fields
+
Authorization
```

---

# 33. Select Only Required Fields

Suppose:

```text
User
├── id
├── name
├── email
├── passwordHash
├── refreshToken
└── role
```

Don't return:

```ts
select: {
  ...
}
```

without thinking.

Prefer an explicit safe projection:

```ts
select: {
  id: true,
  name: true,
  email: true,
  role: true,
}
```

This reduces accidental data exposure.

---

# 34. Soft Delete vs Hard Delete

Suppose a user deletes their account.

### Hard delete

```text
DELETE
 ↓
Data gone
```

### Soft delete

```text
deletedAt = timestamp
```

Soft deletion can help with:

```text
Audit
Recovery
Referential relationships
Business requirements
```

But it also means:

> Deleted data still exists.

Therefore you must make sure soft-deleted records aren't accidentally exposed.

---

# 35. Soft Delete Security Problem

Imagine:

```text
User
deletedAt = 2026-08-14
```

but a query does:

```ts
prisma.user.findMany()
```

without:

```text
deletedAt IS NULL
```

Now deleted users may appear.

So if you use soft deletion:

```text
Every relevant query
   ↓
Exclude deleted records
```

You need a consistent strategy.

---

# 36. Database Migrations

Your schema will change:

```text
Phase 3
   ↓
User
   ↓
Course
   ↓
Enrollment
   ↓
Progress
```

Later:

```text
Add AIConversation
Add RAGDocument
Add Quiz
```

Migrations are powerful.

But migrations can also destroy data.

Example:

```text
DROP COLUMN
```

or:

```text
DROP TABLE
```

Therefore production migrations require care.

---

# 37. Safe Migration Principles

Before a production migration:

```text
Backup
   ↓
Review migration
   ↓
Test on staging
   ↓
Check data impact
   ↓
Run migration
   ↓
Verify
```

Don't casually execute destructive migrations against production.

---

# 38. Expand-and-Contract Migration

A useful production pattern.

Suppose you want to rename:

```text
username
```

to:

```text
displayName
```

Instead of immediately:

```text
DROP username
```

you can do:

```text
Step 1
Add displayName

Step 2
Write both fields

Step 3
Backfill data

Step 4
Move reads to displayName

Step 5
Stop writing username

Step 6
Remove username later
```

This reduces downtime and compatibility problems.

---

# 39. Database Backups

Your database contains valuable information.

You need backups.

Conceptually:

```text
PostgreSQL
     ↓
Backup
     ↓
Secure Storage
```

But:

> **A backup is also sensitive data.**

If your production database is secure but your backup is public:

```text
Attacker
   ↓
Backup
   ↓
Everything
```

So backups need:

```text
Encryption
Access control
Retention policy
Monitoring
Recovery testing
```

---

# 40. Backup ≠ Recovery

Having:

```text
backup.sql
```

doesn't guarantee you can recover.

You should test:

```text
Backup
  ↓
Restore
  ↓
Verify data
```

This is called recovery testing.

A backup you've never restored is not something you should blindly trust.

---

# 41. RAG Database Security

Your AI LMS will eventually have:

```text
Course Documents
      ↓
Chunks
      ↓
Embeddings
      ↓
pgvector
```

Imagine:

```text
Course A documents
Course B documents
Course C documents
```

all in the same vector database.

Your retrieval query must respect authorization.

Conceptually:

```text
Similarity Search
      +
Authorized Course IDs
      ↓
Results
```

Not:

```text
Similarity Search
      ↓
ALL documents
```

---

# 42. RAG Data Leakage

Imagine:

```text
Student A
  ↓
Course A
```

Student A asks:

> "What is in the instructor-only material?"

If retrieval isn't access-controlled:

```text
Vector search
   ↓
Instructor document
   ↓
LLM
   ↓
Student sees it
```

That's a data-access vulnerability.

The LLM isn't necessarily the root cause.

The database/retrieval authorization boundary is.

# 43. Multi-Tenant Thinking

Even if your LMS isn't currently multi-tenant, it's useful to understand the idea.

Imagine:

```text
Organization A
 ├── Users
 ├── Courses
 └── Documents

Organization B
 ├── Users
 ├── Courses
 └── Documents
```

A query must never accidentally cross:

```text
Organization A
      ↓

```

The same principle applies to:

```text
User

RAG documents
```

# 44. Row-Level Security — Concept

PostgreSQL supports **Row-Level Security (RLS)**.

It allows policies that control which rows a database role can access.

Conceptually:

```text
Database
   ↓
RLS Policy
   ↓
Which rows are visible?
```

For example:

```text
User A
   ↓
Only rows belonging to User A
```

RLS can be powerful for certain architectures, especially multi-tenant systems.

But it adds complexity.

For your Express + Prisma architecture, you should first build a strong understanding of:

```text
Application authorization
+
Database constraints
+
Scoped queries
```

Then decide where RLS provides meaningful additional protection.

You should be able to investigate suspicious database activity.

Useful operational information may include:

```text
Slow queries
Connection failures
Authentication failures
Migration events
Administrative actions
Database errors
```

But don't log:

```text
Passwords
Raw tokens
Secrets
Sensitive query parameters
```

unless there is a carefully controlled and justified security process.

---

# 46. Database Errors

Suppose PostgreSQL returns:

```text
duplicate key value violates unique constraint...
```

Don't blindly expose internal database details to the client.

Instead:

```text
Database
   ↓
Internal error
   ↓
Application error mapping
   ↓
Safe API response
```

For example:

```json
{
  "success": false,
  "message": "Email is already registered."
}
```

rather than exposing:

```text
PostgreSQL constraint name
Table name
SQL details
Stack trace
```

---

# 47. Prisma Error Handling

Prisma provides structured errors.

Your service layer can map them to appropriate application errors.

Conceptually:

```text
Prisma error
    ↓
Identify error type
    ↓
Map to AppError
    ↓
Safe response
```

For example:

```text
Unique constraint
      ↓
409 Conflict
```

rather than:

```text
500 Database exploded
```

This improves both security and developer experience.

# 48. Database Access Through Repository Layer

Your architecture already follows:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Prisma
    ↓
PostgreSQL
```

Keep that separation.

The repository should be the controlled place for database operations.

For example:

```text
findCourseForInstructor()
findProgressForUser()
findEnrollment()
findConversationForUser()
```

These names make the security boundary visible.

Compare:

```text

```

with:

```text
findCourseForInstructor()
```

The second communicates an authorization assumption.

# 49. Don't Let Controllers Build Arbitrary Queries

Avoid:

```ts
controller
   ↓
req.query
   ↓
dynamic Prisma query
   ↓
database
```

Instead:

```text
Controller
   ↓
Validate
   ↓
Service
   ↓
Repository
   ↓

```

This makes the system easier to review.

# 50. Database Security and Transactions

Transactions protect data integrity.

Example:

```text
Enrollment
   ↓
Create enrollment
   ↓
Update course count
   ↓
Create progress record
```

If step 2 fails but step 1 succeeds, your data may become inconsistent.

Use a transaction where the operations must succeed or fail together.

```text
BEGIN
 ↓
Operation A
 ↓
Operation B
 ↓
Operation C
 ↓
COMMIT
```

If something fails:

```text
ROLLBACK
```

---

# 51. Transactions Are Also Security

Imagine a course enrollment flow:

```text
Create enrollment
      ↓
Grant course access
      ↓
Create progress
```

If these operations aren't coordinated properly, you might accidentally:

```text
Grant access
without valid enrollment
```

or:

```text
Create enrollment
without proper access state
```

Data integrity directly affects authorization.

Use this when reviewing your production database:

```text

[ ] DATABASE_URL kept secret
[ ] No credentials committed to Git
[ ] Prisma queries are scoped
[ ] Raw SQL is reviewed carefully
[ ] No unsafe string-built SQL
[ ] Authorization enforced
[ ] Foreign keys configured
[ ] Unique constraints configured
[ ] CHECK constraints where useful
[ ] Sensitive fields protected
[ ] Passwords stored as secure hashes
[ ] Refresh tokens protected
[ ] Pagination limits exist
[ ] Expensive queries controlled
[ ] Database connections limited
[ ] Migrations reviewed
[ ] Production migrations tested
[ ] Backups encrypted
[ ] Backups access-controlled

[ ] Database errors aren't leaked

```

# 🧠 55. The Most Important Database Security Rules

If you remember only these:

### Rule 1

> **Never expose PostgreSQL directly to the public internet unnecessarily.**

### Rule 2

> **Use least-privileged database accounts.**

### Rule 3

> **Never build SQL using untrusted string concatenation.**

### Rule 4

> **Prisma protects against many injection problems, but it doesn't replace authorization.**

### Rule 5

> **Use database constraints to enforce important invariants.**

### Rule 6

> **Scope database queries according to the user's permissions.**

### Rule 7

> **Never expose sensitive fields unnecessarily.**

### Rule 8

> **Protect backups as carefully as production data.**

### Rule 9

> **Treat migrations as potentially destructive production operations.**

### Rule 10

> **RAG retrieval must obey the same authorization boundaries as normal application data.**

Your database security model should be:

```text
                    PostgreSQL
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
     Access Control   Integrity    Availability
          │             │             │
          ↓             ↓             ↓
      DB Roles      Constraints     Limits
          │             │             │
          └─────────────┼─────────────┘
                        ↓
                   Secure Data
```

And your application flow:

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Service
   ↓
Scoped Repository Query
   ↓
Prisma
   ↓
PostgreSQL
   ↓
Constraints
   ↓
Safe Response
```

The biggest lesson is:

> 🔥 **Database security is not just about protecting PostgreSQL from hackers. It's about making sure that even when application code receives a malicious request, the database layer still has strong boundaries around who can access and modify which data.**

```text
Users

Progress
AI Conversations
RAG Documents

```

because these will become some of your most valuable data assets.
