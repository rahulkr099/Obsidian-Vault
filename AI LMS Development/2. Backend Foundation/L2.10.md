# Lesson 2.10 — Backend Testing

Now we're going to add **testing** to the AI LMS backend.

This is an important transition because until now we've mainly been learning:

```text
How to build the backend
```

Now we'll learn:

```text
How to prove the backend works
```

A professional backend isn't just:

```text
Code → works on my machine
```

It's:

```text
Code
 ↓
Tests
 ↓
Confidence
 ↓
Refactor safely
 ↓
Deploy
```

---

# 1. Why Testing Matters

Imagine you have:

```text
50 API endpoints
```

You change:

```text
Course Service
```

and accidentally break:

```text
Enrollment
Progress
Quiz
```

Manually testing everything every time becomes painful.

Automated tests can tell you:

```text
✅ Course creation works
✅ Duplicate courses are rejected
✅ Unauthorized users are rejected
✅ Pagination works
✅ Invalid input is rejected
❌ Enrollment test failed
```

That's much faster.

---

# 2. The Three Main Types of Tests

For your backend, understand these three:

```text
Unit Tests
Integration Tests
End-to-End / API Tests
```

Think of them as different zoom levels.

```text
              Entire Application
                     │
              ┌──────┴──────┐
              │             │
          API Tests     Integration
                            │
                         Unit Tests
```

---

# 3. Unit Tests

A unit test tests a **small isolated piece of code**.

For example:

```ts
calculateTotalPages(100, 20)
```

should return:

```text
5
```

You don't need:

```text
Express
PostgreSQL
Prisma
HTTP
```

Just the function.

Example:

```ts
function calculateTotalPages(
  total: number,
  limit: number
) {
  return Math.ceil(total / limit);
}
```

Test:

```ts
expect(
  calculateTotalPages(100, 20)
).toBe(5);
```

That's a unit test.

---

# 4. What Should We Unit Test?

Good candidates:

```text
Business rules
Utility functions
Data transformations
Permission checks
Pagination calculations
Price calculations
Token helpers
Validation helpers
```

For example:

```text
isCourseOwner()
calculateProgress()
calculateTotalPages()
canPublishCourse()
```

These are easy to test.

---

# 5. Integration Tests

Integration tests check whether multiple parts work together.

For example:

```text
Service
   ↓
Repository
   ↓
Database
```

You might test:

```text
Create course
   ↓
Service
   ↓
Repository
   ↓
PostgreSQL
   ↓
Course actually exists
```

Now you're testing integration between components.

# 9. Your First Test

Create:

```text
src/utils/pagination.ts
```

```ts
export function calculateTotalPages(
  total: number,
  limit: number
) {
  return Math.ceil(total / limit);
}
```

Now:

```text
src/utils/pagination.test.ts
```

```ts
import { describe, expect, it } from "vitest";
import { calculateTotalPages } from "./pagination";

describe("calculateTotalPages", () => {
  it("calculates the total number of pages", () => {
    expect(
      calculateTotalPages(100, 20)
    ).toBe(5);
  });
});
```

Run:

```bash
npm test
```

You should see something like:

```text
✓ calculates the total number of pages
```

Congratulations.

You just wrote your first automated backend test.

# 10. Understand `describe`, `it`, `expect`

This syntax is worth remembering.

### `describe`

Groups related tests.

```ts
describe("calculateTotalPages", () => {
```

### `it`

Describes one behavior.

```ts
it("calculates the total number of pages", () => {
```

### `expect`

Checks the result.

```ts
expect(result).toBe(5);
```

Think:

```text
describe
    ↓
What am I testing?

it
    ↓
What behavior am I testing?

expect
    ↓
What should happen?
```

---

# 11. Test More Cases

Don't test only:

```text
100 / 20
```

Test:

```ts
describe("calculateTotalPages", () => {
  it("calculates exact pages", () => {
    expect(
      calculateTotalPages(100, 20)
    ).toBe(5);
  });

  it("rounds up partial pages", () => {
    expect(
      calculateTotalPages(101, 20)
    ).toBe(6);
  });

  it("returns one page for fewer items", () => {
    expect(
      calculateTotalPages(10, 20)
    ).toBe(1);
  });
});
```

This is better because you're testing different behaviors.

---

# 12. Test Behavior, Not Implementation

This is a very important principle.

Bad mindset:

> "I need to test that this function calls this exact line."

Better:

> "I need to test that the user gets the correct result."

For example:

```text
Bad:
"Did Prisma's findMany get called?"

Better:
"Does the API return the correct courses?"
```

Implementation can change.

Behavior should remain stable.

# 13. Testing Services

Suppose we have:

```ts
export async function createCourse(input) {
  const existing =
    await courseRepository.findByTitleAndInstructor(
      input.title,
      input.instructorId
    );

  if (existing) {
    throw new AppError(
      "Course already exists",
      409
    );
  }

  return courseRepository.create(input);
}
```

There are two important behaviors.

### Case 1

No duplicate:

```text
repository.find → null
repository.create → course
```

Expected:

```text
course created
```

### Case 2

Duplicate exists:

```text
repository.find → existing course
```

Expected:

```text
AppError 409
```

# 14. Mocking

For a unit test, we don't necessarily want a real database.

We can mock:

```text
courseRepository
```

Conceptually:

```text
Service
   ↓
Fake Repository
```

instead of:

```text
Service
   ↓
Real Repository
   ↓
PostgreSQL
```

This makes the service test fast.

---

# 15. Why Mock the Repository?

Imagine your service test runs:

```text
100 times
```

If each test connects to PostgreSQL:

```text
100 DB connections
```

That can become slow and complicated.

Instead:

```text
Service
   ↓
Mock repository
```

The test becomes focused on business logic.

---

# 16. But Don't Mock Everything

This is a common mistake.

If you mock:

```text
Service
Repository
Prisma
Database
Express
```

you're essentially testing nothing meaningful.

You need a balance.

A good strategy:

```text
Unit tests
→ mock dependencies

Integration tests
→ use real database

API tests
→ exercise real application flow
```

# 17. API Testing With Supertest

Install:

```bash
npm install -D supertest
npm install -D @types/supertest
```

Now suppose your Express app is exported:

```ts
export const app = express();
```

You can test:

```ts
import request from "supertest";
import { app } from "../app";

it("returns health status", async () => {
  const response = await request(app)
    .get("/health");

  expect(response.status).toBe(200);
});
```

This sends a real HTTP request to your Express application.

---

# 18. Why Export `app` Separately?

This is an important architecture decision.

Don't make your `app.ts` immediately start the server.

Prefer:

```text
app.ts
→ configure Express

server.ts
→ start listening
```

### `app.ts`

```ts
export const app = express();
```

### `server.ts`

```ts
import { app } from "./app";

app.listen(PORT);
```

Why?

Tests need:

```text
app
```

but don't need:

```text
app.listen()
```

Supertest can interact directly with the Express app.

# 19. Health Check Test

Create:

```http
GET /health
```

Response:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

Test:

```ts
import request from "supertest";
import { describe, expect, it } from "vitest";
import { app } from "../app";

describe("GET /health", () => {
  it("returns healthy status", async () => {
    const response = await request(app)
      .get("/health");

    expect(response.status).toBe(200);

    expect(response.body.success)
      .toBe(true);
  });
});
```

This is a very useful first API test.

# 30. Test Isolation

Imagine Test A creates:

```text
Course A
```

Then Test B expects:

```text
No courses
```

Test B could fail because Test A left data behind.

That's bad.

Tests should ideally be independent:

```text
Test A
  ↓
Setup
  ↓
Test
  ↓
Cleanup

Test B
  ↓
Setup
  ↓
Test
  ↓
Cleanup
```

This is called **test isolation**.

# 33. What Not to Waste Time Testing

Don't obsess over trivial code like:

```ts
function add(a, b) {
  return a + b;
}
```

unless it's part of important business logic.

And don't aim for:

```text
100% coverage
```

just for the number.

A project can have:

```text
100% coverage
```

and still have terrible tests.

The goal is:

> **High confidence in important behavior.**

# 34. Test Pyramid

A useful mental model:

```text
                 /\
                /  \
               / API\
              /------\
             /        \
            /Integration\
           /------------\
          /              \
         /   Unit Tests  \
        /________________\
```

Usually:

```text
Many unit tests
Some integration tests
Fewer full API tests
```

Why?

Unit tests are:

```text
Fast
Cheap
Easy to debug
```

API tests are:

```text
Slower
More dependencies
More setup
```

# 41. The Golden Rule

When adding a feature, think:

```text
Feature
  ↓
Implementation
  ↓
Test
```

Not:

```text
Build everything
  ↓
Maybe test at the end
```

For example:

```text
Create course
    ↓
Implement
    ↓
Test
    ↓
Publish course
    ↓
Implement
    ↓
Test
```

This makes debugging much easier.
