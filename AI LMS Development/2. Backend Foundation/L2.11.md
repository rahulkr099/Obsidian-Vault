# Lesson 2.11 — Rate Limiting

Now we're adding another important production feature to your AI LMS:

> **Rate limiting controls how many requests a client can make within a certain period.**

Without it, someone could repeatedly hit:

```text
POST /api/v1/auth/login
POST /api/v1/ai/tutor
POST /api/v1/ai/generate-course
```

thousands of times.

That can cause:

```text
Server overload
Brute-force attacks
Database pressure
AI API costs
Abuse
Denial of service
```

So rate limiting is both a **security feature** and a **resource-management feature**.

---

# 1. Simple Example

Suppose we configure:

```text
100 requests
per 15 minutes
```

A client sends:

```text
Request 1   ✓
Request 2   ✓
Request 3   ✓
...
Request 100 ✓
Request 101 ✗
```

The API responds:

```http
429 Too Many Requests
```

`429` is the standard HTTP status code for rate limiting.

---

# 2. Why Your AI LMS Needs It

Your LMS will eventually have endpoints like:

```text
GET  /api/v1/courses
POST /api/v1/auth/login
POST /api/v1/auth/register
POST /api/v1/ai/tutor
POST /api/v1/ai/generate-course
POST /api/v1/quizzes/:id/submit
```

These should **not all have the same rate limit**.

For example:

```text
GET /courses
    ↓
fairly cheap

POST /auth/login
    ↓
security-sensitive

POST /ai/tutor
    ↓
expensive

POST /ai/generate-course
    ↓
very expensive
```

This is an important production-thinking habit.

---

# 3. Don't Use One Global Limit for Everything

A beginner might do:

```ts
app.use(rateLimiter);
```

and stop there.

That's okay as a basic protection layer, but it's not ideal.

Instead:

```text
Global limiter
       ↓
General protection

Auth limiter
       ↓
Login/register

AI limiter
       ↓
AI endpoints

Upload limiter
       ↓
File operations
```

Different resources have different risks.

---

# 4. Install Express Rate Limit

A popular Express package is:

```bash
npm install express-rate-limit
```

Then:

```ts
import rateLimit from "express-rate-limit";
```

---

# 5. Create a General Rate Limiter

Create:

```text
src/middleware/rateLimiter.ts
```

Example:

```ts
import rateLimit from "express-rate-limit";

export const generalRateLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100,
});
```

Meaning:

```text
15 minutes
+
100 requests
```

---

# 6. Add It to the API

You could do:

```ts
app.use(
  "/api",
  generalRateLimiter,
  apiRoutes
);
```

Now requests under:

```text
/api/*
```

are rate limited.

For example:

```text
GET /api/v1/courses
GET /api/v1/users/me
POST /api/v1/courses
```

all count toward the general limit.

---

# 7. What Happens When the Limit Is Reached?

The client receives:

```http
429 Too Many Requests
```

You should return a consistent response.

For example:

```json
{
  "success": false,
  "error": {
    "message": "Too many requests. Please try again later."
  }
}
```

The exact response should match your API error format from Lesson 2.2.

---

# 8. Why 429?

HTTP already gives us a standard status:

```text
429 Too Many Requests
```

So don't use:

```text
400
```

for rate limiting.

`400` means:

> Bad request.

`429` means:

> You sent too many requests.

---

# 9. Authentication Needs Stricter Limits

Consider:

```http
POST /api/v1/auth/login
```

Suppose someone tries:

```text
admin@example.com
password1
password2
password3
password4
...
```

This is a brute-force attack.

You want a stricter limiter.

For example:

```ts
export const authRateLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 10,
});
```

Then:

```text
10 attempts / 15 minutes
```

is much more appropriate than:

```text
100 requests / 15 minutes
```

for login.

---

# 10. Registration

Registration is also abuse-prone.

Someone could automate:

```text
POST /register
POST /register
POST /register
POST /register
...
```

creating thousands of fake accounts.

So:

```text
POST /auth/register
```

should have its own reasonable limit.

---

# 11. Password Reset

Password reset is particularly sensitive.

For example:

```http
POST /api/v1/auth/forgot-password
```

should have a stricter rate limit.

Otherwise someone can repeatedly trigger reset emails.

That's both:

```text
Security problem
+
Email cost problem
```

---

# 12. AI Endpoints Are Different

Now we reach one of the most important parts for your LMS.

Imagine:

```http
POST /api/v1/ai/tutor
```

Each request might call an external LLM API.

Suppose one request costs:

```text
₹0.10
```

Someone sends:

```text
10,000 requests
```

Potential cost:

```text
₹1,000
```

And that's just one attacker.

So your AI endpoints need more than a basic global rate limiter.

---

# 13. AI Rate Limiting

For example:

```text
20 AI requests
per hour
per user
```

This is much more meaningful than:

```text
100 requests
per 15 minutes
per IP
```

because authenticated users should usually have their own usage limits.

For example:

```text
Rahul
 ↓
20 AI requests/hour

User B
 ↓
20 AI requests/hour
```

---

# 14. IP-Based vs User-Based Rate Limiting

This is important.

### IP-based

```text
IP address
   ↓
Rate limit
```

Good for:

```text
Unauthenticated APIs
Login
Registration
Public endpoints
```

### User-based

```text
Authenticated user
   ↓
Rate limit
```

Better for:

```text
AI tutor
AI generation
Course analysis
Personalized recommendations
```

Ideally, you may use both.

---

# 15. Why IP-Only Isn't Enough

Suppose:

```text
100 users
```

are behind the same network.

They might share:

```text
Public IP
```

If you have:

```text
10 requests / IP
```

then all 100 users could potentially affect each other.

This can happen with:

```text
College Wi-Fi
Office networks
NAT
Mobile carriers
```

So user-aware limiting is better for authenticated operations.

---

# 16. The Limiter Key

A rate limiter needs to answer:

> "Who is making these requests?"

Possible keys:

```text
IP address
User ID
API key
Organization ID
```

For your LMS:

```text
Public API
    → IP

Authenticated API
    → User ID

AI usage
    → User ID

Admin/API integrations
    → API key
```

---

# 17. Important Architecture Detail

Remember our middleware order.

For an authenticated user:

```text
Request
  ↓
Request ID
  ↓
Security
  ↓
Authentication
  ↓
User identified
  ↓
User-aware Rate Limiter
  ↓
Controller
```

You can't use:

```ts
req.user.id
```

before authentication has populated `req.user`.

So middleware order matters.

---

# 18. Example

Imagine:

```ts
router.post(
  "/ai/tutor",
  authenticate,
  aiRateLimiter,
  aiController.ask
);
```

Flow:

```text
POST /ai/tutor
       ↓
authenticate
       ↓
req.user = user_123
       ↓
aiRateLimiter
       ↓
check user_123 usage
       ↓
controller
```

That's clean.

---

# 19. Global + Route-Specific Limits

You can have:

```text
Global
100 requests / 15 minutes

Auth
10 requests / 15 minutes

AI
20 requests / hour

Password reset
5 requests / hour
```

Conceptually:

```text
                 API
                  │
          Global Limiter
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
      Auth        AI       Normal
       ↓          ↓          ↓
    10/15m      20/hour   100/15m
```

This is much better than one giant limit.

---

# 20. Rate Limiting Is Not Authentication

Another important distinction:

```text
Authentication
```

answers:

> Who are you?

while:

```text
Rate limiting
```

answers:

> How often can you perform this operation?

A user can be correctly authenticated and still be rate-limited.

For example:

```text
User authenticated ✓
AI quota exceeded ✗
```

---

# 21. Rate Limiting Is Not Authorization

Authorization asks:

> Are you allowed to do this?

For example:

```text
Student → cannot publish course
```

Rate limiting asks:

> How frequently can you perform the action?

For example:

```text
Student → 20 AI requests/hour
```

These are different concerns.

---

# 22. Response Headers

Rate limiting systems can expose information through headers such as:

```text
RateLimit-Limit
RateLimit-Remaining
RateLimit-Reset
```

Conceptually:

```http
RateLimit-Limit: 100
RateLimit-Remaining: 72
RateLimit-Reset: 120
```

This tells the client:

```text
Maximum → 100
Remaining → 72
Reset → 120 seconds
```

Exact header behavior depends on the limiter configuration/version.

The important idea is that clients can understand their quota.

---

# 23. Don't Trust Client-Supplied User IDs

Suppose someone sends:

```http
X-User-ID: admin
```

Don't use that to decide the rate limit.

Instead:

```text
Authentication
      ↓
Verified token/session
      ↓
req.user.id
```

Then:

```text
req.user.id
      ↓
Rate limit key
```

The identity must come from your trusted authentication mechanism.

---

# 24. Distributed Applications

There's another problem.

Suppose your LMS has:

```text
Server A
Server B
Server C
```

If each server keeps rate-limit counters in local memory:

```text
Server A → 5 requests
Server B → 5 requests
Server C → 5 requests
```

a user could potentially make:

```text
15 requests
```

even if the intended limit is:

```text
10
```

because each server has its own counter.

---

# 25. Redis

This is where Redis becomes useful.

Instead of:

```text
Server A
   ↓
Memory

Server B
   ↓
Memory
```

you can use:

```text
Server A ──┐
Server B ──┼──→ Redis
Server C ──┘
```

All servers share the same rate-limit state.

For your first version, you don't need Redis immediately.

But it's important to understand why production systems often use a shared store.

---

# 26. Rate Limiting and Horizontal Scaling

Eventually:

```text
Load Balancer
      │
 ┌────┼────┐
 ↓    ↓    ↓
API  API  API
 A    B    C
 └────┼────┘
      ↓
    Redis
```

Then:

```text
User
 ↓
Load Balancer
 ↓
Any API server
 ↓
Redis rate-limit counter
```

Now the limit works consistently.

---

# 27. Fixed Window

The simplest rate limiter is:

```text
100 requests
between 10:00–10:15
```

At 10:15:

```text
counter resets
```

This is called a **fixed window**.

Easy to understand, but there are edge cases around the window boundary.

---

# 28. Sliding Window

A sliding window looks at:

```text
the previous N minutes
```

rather than fixed clock boundaries.

For example:

```text
10:14:30 → requests
10:15:00 → still counts
```

It gives smoother behavior.

---

# 29. Token Bucket

Another common model is:

```text
Bucket
capacity = 20 tokens
```

Each request consumes:

```text
1 token
```

Tokens refill over time.

This allows controlled bursts while still enforcing an average rate.

You don't need to implement these algorithms yourself for your current LMS.

The important thing is to know they exist.

---

# 30. Rate Limit vs Quota

This distinction is particularly useful for AI.

### Rate limit

> How fast can you make requests?

Example:

```text
20 requests/hour
```

### Quota

> How much total usage are you allowed?

Example:

```text
50,000 AI tokens/month
```

For an AI LMS, you may eventually need both.

For example:

```text
Rate:
20 AI requests/hour

Monthly quota:
100,000 AI tokens/month
```

---

# 31. AI LMS Example

Suppose your pricing plans eventually become:

```text
Free
├── 10 AI requests/day
└── 20,000 tokens/month

Pro
├── 100 AI requests/day
└── 500,000 tokens/month
```

Now the system isn't simply:

```text
rateLimit = 100
```

It becomes a **usage management system**.

That's a future feature, but your architecture should leave room for it.

---

# 32. Don't Put AI Billing Logic in the Rate Limiter

This is another architecture lesson.

Bad:

```text
Rate Limiter
 ├── check requests
 ├── calculate AI tokens
 ├── check subscription
 ├── calculate billing
 └── call database
```

Too much responsibility.

Better:

```text
Authentication
      ↓
Rate Limiter
      ↓
AI Usage Service
      ↓
AI Service
```

Each layer has its own responsibility.

# 33. Recommended Middleware Structure

Your middleware folder now becomes:

```text
middleware/
├── auth.ts
├── errorHandler.ts
├── notFound.ts
├── rateLimiter.ts
├── requestId.ts
├── requestLogger.ts
└── validate.ts
```

And your routes can specify the appropriate limiter.

Example:

```ts
router.post(
  "/login",
  authRateLimiter,
  validate(loginSchema),
  authController.login
);
```

AI:

```ts
router.post(
  "/tutor",
  authenticate,
  aiRateLimiter,
  validate(aiTutorSchema),
  aiController.ask
);
```

Normal public route:

```ts
router.get(
  "/courses",
  generalRateLimiter,
  courseController.getCourses
);
```

# 36. One Important Ordering Detail

Don't blindly put every middleware in one global chain.

For example:

```text
Authentication
      ↓
AI rate limiter
```

makes sense for user-based AI limits.

But:

```text
Authentication
      ↓
Login rate limiter
```

doesn't make sense because the user isn't authenticated yet.

For login:

```text
Login Rate Limiter
      ↓
Validation
      ↓
Login Controller
```

For authenticated AI:

```text
Authentication
      ↓
AI Rate Limiter
      ↓
Validation
      ↓
AI Controller
```

Middleware order should match the information each middleware needs.

# 37. Testing Rate Limits

We learned testing in Lesson 2.10.

Now connect the two.

You should test:

```text
Request within limit
       ↓
200 ✓
```

and:

```text
Request exceeds limit
       ↓
429 ✓
```

For login:

```text
10 attempts
   ↓
allowed

11th attempt
   ↓
429
```

For AI:

```text
quota exceeded
   ↓
429
```

This makes rate limiting a tested part of your API contract.

# 38. Don't Accidentally Block Yourself During Development

When testing locally, a very strict limiter can become annoying.

For example:

```text
5 requests / minute
```

while you're developing:

```text
GET
GET
GET
POST
GET
GET
```

Suddenly:

```text
429
```

Use environment-specific configuration.

For example:

```env
RATE_LIMIT_MAX=100
```

and potentially separate development/test configuration.

# 🎯 Interview Question

### "Why shouldn't you use the same rate limit for every endpoint?"

A strong answer:

> "Different endpoints have different security and resource costs. A public course listing can tolerate more requests, while login needs stricter protection against brute-force attacks and AI endpoints may need much stricter limits because each request can consume expensive external resources."

That's exactly the kind of reasoning interviewers like.
