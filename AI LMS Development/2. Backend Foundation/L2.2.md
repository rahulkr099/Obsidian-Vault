# Lesson 2.2 — `AppError` + Global Error Handler

In **Lesson 2.1**, we created a consistent API response style.

Now we're going to solve the next major backend problem:

> **How should our application handle errors consistently?**

Right now, an error could look like:

```text
Prisma error
Express error
Validation error
JavaScript error
Authentication error
```

and each one could produce a different response.

We want:

```text
Any error
   ↓
Global Error Handler
   ↓
One predictable API response
```

---

# 1. The Problem With Normal `Error`

Suppose our course service does:

```ts
throw new Error('Course not found');
```

The problem is that normal JavaScript `Error` doesn't tell our API:

```text
HTTP status → 404
Error code → COURSE_NOT_FOUND
Safe message → Course not found
```

We need our own application error.

---

# 2. Create `AppError`

Create:

```bash
cd ~/Projects/ai-lms/apps/api

mkdir -p src/errors
touch src/errors/AppError.ts
```

Add:

```ts
export class AppError extends Error {
  public readonly statusCode: number;
  public readonly code: string;
  public readonly isOperational: boolean;

  constructor(
    message: string,
    statusCode: number,
    code: string,
    isOperational = true,
  ) {
    super(message);

    this.name = 'AppError';
    this.statusCode = statusCode;
    this.code = code;
    this.isOperational = isOperational;

    Error.captureStackTrace(this, AppError);
  }
}
```

---

# 3. Understand `AppError`

Our error now contains:

```text
AppError
├── message
├── statusCode
├── code
└── isOperational
```

For example:

```ts
throw new AppError(
  'Course not found',
  404,
  'COURSE_NOT_FOUND',
);
```

produces:

```text
message:
Course not found

statusCode:
404

code:
COURSE_NOT_FOUND
```

This is much more useful than:

```ts
throw new Error('Course not found');
```

---

# 4. Why Have an Error Code?

Consider these two errors:

```text
Course not found
User not found
```

Both could use:

```text
404
```

but they're different application errors.

So:

```json
{
  "code": "COURSE_NOT_FOUND"
}
```

allows the frontend to understand what happened without trying to parse the message.

Later React can do:

```ts
if (error.code === 'COURSE_NOT_FOUND') {
  // show course-not-found UI
}
```

This is much better than:

```ts
if (error.message === 'Course not found') {
  ...
}
```

Messages can change.

Error codes should remain stable.

---

# 5. What Is an Operational Error?

This is an important backend concept.

An **operational error** is an expected problem that our application knows how to handle.

Examples:

```text
User not found
Invalid credentials
Course not found
Validation failed
Unauthorized
Forbidden
Rate limit exceeded
```

These are not necessarily bugs.

For example:

```text
GET /courses/abc
```

and course doesn't exist.

That's expected:

```text
404
COURSE_NOT_FOUND
```

---

# 6. Programming Errors

Now consider:

```ts
const user = null;

user.name;
```

That's a programming bug.

Or:

```ts
someUndefinedFunction();
```

That's unexpected.

We should distinguish:

```text
Expected problem
       ↓
AppError
       ↓
Safe response


Unexpected bug
       ↓
Global handler
       ↓
Log details
       ↓
Generic response
```

This distinction becomes very useful in production.

# 7. Create Global Error Handler

Create:

```bash
touch src/errors/errorHandler.ts
```

Add:

```ts
import type { ErrorRequestHandler } from 'express';

import { AppError } from './AppError.js';

export const errorHandler: ErrorRequestHandler = (
  error,
  _req,
  res,
  _next,
) => {
  if (error instanceof AppError) {
    res.status(error.statusCode).json({
      success: false,
      error: {
        code: error.code,
        message: error.message,
      },
    });

    return;
  }

  console.error(error);

  res.status(500).json({
    success: false,
    error: {
      code: 'INTERNAL_SERVER_ERROR',
      message: 'Something went wrong',
    },
  });
};
```

This is our first global error boundary.

---

# 8. Why `ErrorRequestHandler`?

Express error middleware has a special signature:

```ts
(
  error,
  req,
  res,
  next
)
```

Notice the **four parameters**.

Normal middleware:

```ts
(req, res, next)
```

Error middleware:

```ts
(error, req, res, next)
```

That first parameter tells Express:

> This middleware handles errors.

---

# 9. Add the Error Handler to `app.ts`

Open:

```text
src/app.ts
```

At the top:

```ts
import { errorHandler } from './errors/errorHandler.js';
```

Then make sure the error handler is registered **after your routes**:

```ts
app.use('/api/v1', apiRouter);

app.use(errorHandler);
```

The order matters.

Think:

```text
Request
   ↓
Middleware
   ↓
Routes
   ↓
Controller
   ↓
Service
   ↓
Error
   ↓
errorHandler
```

If you put the error handler before the routes, it won't work the way we want.

# 19. Don't Expose Internal Errors

Imagine PostgreSQL produces:

```text
PrismaClientKnownRequestError:
Unique constraint failed on the fields:
(`email`)
```

We should **not** blindly send this to the browser.

Bad:

```json
{
  "success": false,
  "error": {
    "message": "PrismaClientKnownRequestError..."
  }
}
```

This can expose internal implementation details.

Instead:

```json
{
  "success": false,
  "error": {
    "code": "INTERNAL_SERVER_ERROR",
    "message": "Something went wrong"
  }
}
```

The detailed error belongs in server logs.

During development, you may want more information.

But don't send stack traces to normal production users.

# 23. HTTP Status Codes You Should Know

For backend interviews and real development, memorize the common ones.

### `200 OK`

Successful request.

```http
GET /courses
```

---

### `201 Created`

Resource created.

```http
POST /courses
```

---

### `204 No Content`

Successful operation with no response body.

Often used for:

```http
DELETE /courses/:id
```

---

### `400 Bad Request`

The request itself is invalid.

Example:

```json
{
  "email": "not-an-email"
}
```

---

### `401 Unauthorized`

Authentication is missing or invalid.

```text
No valid access token
```

---

### `403 Forbidden`

User is authenticated but doesn't have permission.

```text
Student → tries to delete instructor course
```

---

### `404 Not Found`

Resource doesn't exist.

```text
COURSE_NOT_FOUND
```

---

### `409 Conflict`

Request conflicts with existing data.

Example:

```text
Email already registered
```

---

### `422 Unprocessable Content`

The request structure may be valid, but semantic validation fails.

We'll decide carefully where to use `400` vs `422` when we build validation.

---

### `429 Too Many Requests`

Rate limit exceeded.

This will matter for:

```text
Login
AI
Password reset
```

---

### `500 Internal Server Error`

Unexpected server failure.

---

### `503 Service Unavailable`

Service temporarily unavailable.

Useful when:

```text
database unavailable
external service unavailable
```

depending on the exact situation.

---

# 24. A Useful Mental Model

Think of status codes like this:

```text
2xx → Success
3xx → Redirect
4xx → Client/request problem
5xx → Server problem
```

The exact code matters because clients can make decisions based on it.

# 25. Error Ownership

This is a subtle but important architecture concept.

Suppose:

```text
Repository
```

doesn't find a course.

Should the repository throw:

```ts
throw new AppError(
  'Course not found',
  404,
  'COURSE_NOT_FOUND',
);
```

Usually, **no**.

The repository should mainly report the data result:

```text
course = null
```

Then:

```text
Service
```

understands the business meaning:

```text
null
 ↓
COURSE_NOT_FOUND
 ↓
404
```

So:

```text
Repository
    ↓
Data access

Service
    ↓
Business decision
```

This separation becomes very important as the application grows.

---


# 28. Don't Catch Every Error

Avoid this:

```ts
try {
  const course = await service.getCourse(id);
} catch (error) {
  res.status(500).json({
    success: false,
  });
}
```

Why?

Because you're destroying useful information.

A `404` becomes:

```text
500
```

A validation error becomes:

```text
500
```

A database error becomes:

```text
500
```

Everything becomes the same.

Instead:

```text
throw
 ↓
global error handler
```

The global handler decides how to respond.

# 30. One Problem We Still Have

Our controllers currently use:

```ts
async getCourseById(req, res) {
  const course = await courseService.getCourseById(...);
}
```

What happens if:

```ts
courseService.getCourseById()
```

throws?

Without proper async handling, Express versions/configuration matter and we don't want every controller manually managing rejected promises.

That's exactly what we'll solve in **Lesson 2.3 — Async Handler + Thin Controllers**.

We'll create:

```text
asyncHandler()
```

so this:

```ts
asyncHandler(async (req, res) => {
  ...
});
```

automatically forwards errors to:

```text
Global Error Handler
```
