# Lesson 2.4 — Zod Request Validation

Now we're going to solve one of the **most important backend security and reliability problems**:

> **Never trust data coming from the client.**

A browser can send anything.

For example, our API expects:

```json
{
  "title": "Node.js Backend",
  "description": "Learn backend development"
}
```

But a client could send:

```json
{
  "title": 123,
  "description": true,
  "isAdmin": true
}
```

Or:

```json
{
  "title": "",
  "description": ""
}
```

Or even:

```json
{
  "title": "A".repeat(100000)
}
```

Our backend needs to decide:

```text
Request
   ↓
Is this valid?
   ├── No → Reject
   └── Yes
         ↓
      Controller
```

For the AI LMS, we'll use **Zod**.

---

# 1. What Is Zod?

Zod is a TypeScript-first validation library.

You define:

```ts
const schema = z.object({
  title: z.string(),
});
```

Then Zod checks:

```json
{
  "title": "Node.js"
}
```

against that schema.

Think:

```text
TypeScript
    ↓
Compile-time safety

Zod
    ↓
Runtime safety
```

This distinction is extremely important.

---

# 2. TypeScript Alone Isn't Enough

Suppose we write:

```ts
type CreateCourseInput = {
  title: string;
};
```

This protects us while writing TypeScript.

But HTTP requests come from outside our application.

The client can send:

```json
{
  "title": 123
}
```

TypeScript doesn't magically validate network requests.

So:

```text
Client
  ↓
JSON
  ↓
JavaScript runtime
  ↓
Zod
  ↓
Type-safe application
```

# 5. Create Course Schema

Create:

```bash
touch src/modules/courses/course.schema.ts
```

Add:

```ts
import { z } from 'zod';

export const createCourseSchema = z.object({
  title: z
    .string()
    .trim()
    .min(3, 'Title must be at least 3 characters')
    .max(150, 'Title cannot exceed 150 characters'),

  description: z
    .string()
    .trim()
    .min(10, 'Description must be at least 10 characters')
    .max(5000, 'Description cannot exceed 5000 characters'),

  categoryId: z.string().min(1, 'Category is required'),
});
```

Now we've described what a valid course creation request looks like.

# 10. Validate Request Body

Now we need middleware.

Create:

```bash
mkdir -p src/middlewares
touch src/middlewares/validate.ts
```

Add:

```ts
import type { RequestHandler } from 'express';
import type { z } from 'zod';

import { AppError } from '../errors/AppError.js';

export const validateBody = (
  schema: z.ZodType,
): RequestHandler => {
  return (req, _res, next) => {
    const result = schema.safeParse(req.body);

    if (!result.success) {
      next(
        new AppError(
          'Request validation failed',
          400,
          'VALIDATION_ERROR',
        ),
      );

      return;
    }

    req.body = result.data;

    next();
  };
};
```

---

# 11. Why `safeParse()`?

Zod provides:

```ts
schema.parse(...)
```

and:

```ts
schema.safeParse(...)
```

`parse()` throws when validation fails.

`safeParse()` returns:

```text
success: true
```

or:

```text
success: false
```

For middleware, `safeParse()` is convenient because we can explicitly decide what to do.

---

# 12. The Validation Flow

Our middleware now does:

```text
req.body
   ↓
Zod schema
   ↓
safeParse()
   │
   ├── success
   │      ↓
   │   req.body = parsed data
   │      ↓
   │   next()
   │
   └── failure
          ↓
       AppError
          ↓
       errorHandler
```

That's clean.

# 24. Add Error Details

Update `AppError.ts`:

```ts
export class AppError extends Error {
  public readonly statusCode: number;
  public readonly code: string;
  public readonly isOperational: boolean;
  public readonly details?: unknown;

  constructor(
    message: string,
    statusCode: number,
    code: string,
    isOperational = true,
    details?: unknown,
  ) {
    super(message);

    this.name = 'AppError';
    this.statusCode = statusCode;
    this.code = code;
    this.isOperational = isOperational;
    this.details = details;

    Error.captureStackTrace(this, AppError);
  }
}
```

Now our errors can optionally contain:

```text
details
```

# 31. Should We Use `.strict()`?

You can make the schema reject unknown keys:

```ts
const schema = z
  .object({
    ...
  })
  .strict();
```

Then:

```json
{
  "title": "...",
  "description": "...",
  "categoryId": "...",
  "isAdmin": true
}
```

would fail.

For APIs where you want clients to be very explicit, `.strict()` can be useful.

For our LMS, we'll use it selectively rather than applying it blindly to every schema.

# 33. Create Generic Param Middleware

Our current middleware is:

```ts
validateBody()
```

Let's make a reusable:

```ts
validateParams()
```

Update `validate.ts`:

```ts
export const validateParams = (
  schema: z.ZodType,
): RequestHandler => {
  return (req, _res, next) => {
    const result = schema.safeParse(req.params);

    if (!result.success) {
      next(
        new AppError(
          'Request validation failed',
          400,
          'VALIDATION_ERROR',
          true,
          result.error.flatten(),
        ),
      );

      return;
    }

    req.params = result.data;

    next();
  };
};
```

# 35. Validate Query Parameters

This becomes especially useful in our next lessons for pagination.

Suppose:

```http

```

We can define:

```ts
export const courseQuerySchema = z.object({

    .number()
    .int()
    .positive()
    .default(1),

  limit: z.coerce
    .number()
    .int()
    .positive()
    .max(100)
    .default(20),
```

Notice:

```ts

```

Why?

Because URL query parameters arrive as strings:

```text

```

is initially:

```ts

```

not:

```ts

```

`z.coerce.number()` converts it.

# 39. Validation vs Business Rules

This distinction is important.

### Validation

```text
title must be a string
title must be 3–150 chars
email must be valid
limit must be ≤ 100
```

belongs to:

```text
Zod
```

### Business rules

```text
Instructor must own course
Student must be enrolled
Course cannot be published without lessons
Quiz requires at least 1 question
```

belong to:

```text
Service layer
```

Don't put all business rules inside Zod.

# 43. Important TypeScript Issue

Depending on your Express and Zod versions, you may encounter a TypeScript issue when assigning:

```ts
req.query = result.data;
```

because Express's `req.query` type is deliberately broad.

If TypeScript complains, don't immediately use:

```ts
as any
```

We'll solve this more cleanly when we build our request typing layer.

For now, if your current Express types accept it, keep it.

If they don't, we can preserve parsed values through `res.locals` instead:

```ts
res.locals.query = result.data;
```

That is often a cleaner production pattern.
