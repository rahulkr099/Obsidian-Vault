# Lesson 2.5 — Sanitization + Security Middleware

Now we move from **validation** to **sanitization and security**.

In Lesson 2.4, we used **Zod** to make sure incoming data has the correct shape and type.

But validation answers:

> “Is this data allowed?”

Sanitization answers:

> “Can we safely clean this data before using it?”

And security middleware answers:

> “How do we protect the application from common attacks?”

---

## 1. Validation vs Sanitization

Suppose the client sends:

```json
{
  "name": "   Rahul Kumar   ",
  "email": "  RAHUL@EXAMPLE.COM  "
}
```

Validation can tell us:

```text
name → string ✓
email → valid email ✓
```

But we may want:

```json
{
  "name": "Rahul Kumar",
  "email": "rahul@example.com"
}
```

That's sanitization.

### Simple difference

|Concept|Purpose|
|---|---|
|Validation|Reject invalid data|
|Sanitization|Clean/normalize data|
|Authentication|Who are you?|
|Authorization|What are you allowed to do?|
|Security middleware|Protect the HTTP application|

---

# 2. Where Should Sanitization Happen?

A good backend pipeline looks like:

```text
Request
   ↓
Security Middleware
   ↓
Parsing
   ↓
Sanitization
   ↓
Validation
   ↓
Authentication
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

However, don't blindly sanitize everything.

Different data needs different treatment.

For example:

```text
email      → normalize
username   → trim
search     → trim
password   → DON'T trim automatically
URL        → validate carefully
description → preserve legitimate text
```

This is important.

**Sanitization should be intentional, not destructive.**

---

# 3. Create a Sanitization Utility

For our AI LMS backend, we can create:

```text
src/
├── utils/
│   ├── sanitize.ts
│   └── asyncHandler.ts
```

Example:

```ts
export function sanitizeString(value: unknown): unknown {
  if (typeof value !== "string") {
    return value;
  }

  return value.trim();
}
```

Then:

```ts
sanitizeString("   hello   ");
```

returns:

```text
"hello"
```

---

# 4. Recursive Sanitization

Requests can contain nested objects:

```json
{
  "profile": {
    "name": " Rahul ",
    "bio": " Full Stack Developer "
  }
}
```

A useful sanitizer can recursively clean strings.

```ts
export function sanitizeObject(value: unknown): unknown {
  if (typeof value === "string") {
    return value.trim();
  }

  if (Array.isArray(value)) {
    return value.map(sanitizeObject);
  }

  if (value && typeof value === "object") {
    const result: Record<string, unknown> = {};

    for (const [key, val] of Object.entries(value)) {
      result[key] = sanitizeObject(val);
    }

    return result;
  }

  return value;
}
```

Now:

```ts
sanitizeObject({
  name: " Rahul ",
  profile: {
    bio: " Developer "
  }
});
```

produces:

```ts
{
  name: "Rahul",
  profile: {
    bio: "Developer"
  }
}
```

# 5. Be Careful With Passwords

This is a common beginner mistake.

Don't automatically do:

```ts
password = password.trim();
```

Why?

Because:

```text
"password"
```

and:

```text
"password "
```

could intentionally be different passwords.

Instead, let your password validation decide what is allowed.

For example:

```ts
const passwordSchema = z
  .string()
  .min(8)
  .max(100);
```

Then validate it without modifying the original value.

# 6. Security Middleware

Now let's look at the security layer.

You've already worked with some of these in your previous backend projects. Now we're organizing them into a proper production architecture.

---

# 7. Helmet

Helmet adds security-related HTTP headers.

Install:

```bash
npm install helmet
```

Then:

```ts
import helmet from "helmet";

app.use(helmet());
```

Conceptually:

```text
Browser
   ↓
HTTP Response
   ↓
Security Headers
```

Helmet helps protect against several common browser-based attacks and unsafe defaults.

Don't think of Helmet as:

> "Helmet makes my API secure."

Instead think:

> "Helmet gives my Express application safer HTTP defaults."

---

# 8. CORS

CORS controls which browser origins can make requests to your backend.

Example:

```ts
import cors from "cors";

app.use(
  cors({
    origin: process.env.CLIENT_URL,
    credentials: true,
  })
);
```

If your frontend is:

```text
https://app.example.com
```

you might configure:

```env
CLIENT_URL=https://app.example.com
```

Avoid this in production:

```ts
origin: "*"
```

especially when using credentials/cookies.

---

# 9. Request Body Limits

Your API shouldn't accept unlimited request bodies.

For example:

```ts
app.use(
  express.json({
    limit: "1mb",
  })
);
```

Why?

Imagine someone sends:

```text
POST /api/users
```

with a gigantic request body.

Without reasonable limits, attackers can consume memory and resources.

For normal APIs:

```text
100kb
500kb
1mb
```

may be reasonable depending on the application.

For your LMS, however, **large course files should not be uploaded through normal JSON APIs**.

We'll eventually handle files separately using object storage.

---

# 10. Don't Put Everything Into Middleware

This is extremely important for your architecture.

Don't create:

```text
sanitizeEverythingMiddleware
doEverythingMiddleware
securityMiddlewareThatDoesEverything
```

Instead:

```text
middleware/
├── auth.ts
├── errorHandler.ts
├── rateLimiter.ts
├── requestId.ts
└── validate.ts

utils/
├── sanitize.ts
└── asyncHandler.ts
```

Each component should have one clear responsibility.

This fits perfectly with our architecture:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
```

---

# 11. Recommended Middleware Order

A clean Express application can look like:

```ts
app.use(helmet());

app.use(
  cors({
    origin: process.env.CLIENT_URL,
    credentials: true,
  })
);

app.use(
  express.json({
    limit: "1mb",
  })
);

app.use(express.urlencoded({ extended: true }));
```

Then:

```ts
app.use("/api/v1", routes);
```

And finally:

```ts
app.use(notFoundHandler);
app.use(errorHandler);
```

So the overall structure becomes:

```text
                    Express App
                        │
          ┌─────────────┴─────────────┐
          │                           │
     Security                     Parsing
      Helmet                       JSON
      CORS                       URL encoded
          │                           │
          └─────────────┬─────────────┘
                        ↓
                     Routes
                        ↓
                   Middleware
                        ↓
                   Controller
                        ↓
                     Service
                        ↓
                  Repository
                        ↓
                    Database
```

---

# 12. One Important Security Rule

Never trust:

```text
req.body
req.params
req.query
req.headers
req.cookies
```

Everything coming from the client should be considered **untrusted input**.

Even if your frontend has:

```ts
if (!email) {
  return;
}
```

the attacker can completely bypass your frontend and directly call:

```bash
curl
```

against your API.

Therefore:

```text
Frontend validation
        +
Backend validation
        +
Sanitization
        +
Authorization
```

is the correct approach.

Suppose we have:



Our pipeline:

```text
Request
   ↓

   ↓

   ↓

   ↓

   ↓
Authentication
   ↓
Authorization
   ↓

   ↓

   ↓

   ↓
```

The controller should **not** contain:

```ts
if (!title) ...
```
