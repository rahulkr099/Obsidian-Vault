# Lesson 2.6 — Repository + Service Architecture

This is a **very important lesson** for your AI LMS project.

You've already decided that you don't want this:

```text
Route
  ↓
Controller
  ↓
Prisma
```

Instead, we'll build:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Prisma
  ↓
PostgreSQL
```

The main idea is simple:

> **Controller handles HTTP. Service handles business logic. Repository handles database operations.**

---

# 1. Why Do We Need This?

Imagine your course creation endpoint.

Without separation, your controller might become:

```ts
export async function createCourse(req, res) {
  const { title, description, level } = req.body;

  if (!title) {
    throw new AppError("Title is required", 400);
  }

  if (!req.user) {
    throw new AppError("Unauthorized", 401);
  }

  const existingCourse = await prisma.course.findFirst({
    where: {
      title,
      instructorId: req.user.id,
    },
  });

  if (existingCourse) {
    throw new AppError("Course already exists", 409);
  }

  const course = await prisma.course.create({
    data: {
      title,
      description,
      level,
      instructorId: req.user.id,
    },
  });

  res.status(201).json({
    success: true,
    data: course,
  });
}
```

It works.

But notice what's happening.

The controller is doing:

```text
HTTP handling
+
Validation
+
Business logic
+
Database queries
+
Response formatting
```

That's too much responsibility.

---

# 2. Our Goal

We want:

```text
Controller
   ↓
Service
   ↓
Repository
```

Each layer has one job.

### Controller

> "What HTTP request did I receive?"

### Service

> "What should my application do?"

### Repository

> "How do I communicate with the database?"

This separation becomes extremely valuable as your AI LMS grows.

---

# 3. Controller Layer

The controller should be **thin**.

For example:

```ts
export async function createCourse(req, res) {
  const course = await courseService.createCourse({
    instructorId: req.user.id,
    ...req.body,
  });

  res.status(201).json({
    success: true,
    data: course,
  });
}
```

That's much cleaner.

The controller doesn't know:

```text
How Prisma works
How PostgreSQL works
How courses are searched
How duplicate courses are detected
How business rules work
```

It simply:

```text
Request
   ↓
Service
   ↓
Response
```

---

# 4. Service Layer

Now we put business logic inside the service.

```ts
export async function createCourse(input: CreateCourseInput) {
  const existingCourse =
    await courseRepository.findByTitleAndInstructor(
      input.title,
      input.instructorId
    );

  if (existingCourse) {
    throw new AppError(
      "You already have a course with this title",
      409
    );
  }

  return courseRepository.create(input);
}
```

Now the service is responsible for:

```text
Business rules
Business decisions
Workflow
Combining repositories
Throwing business errors
```

This is where the **real application logic** lives.

---

# 5. Repository Layer

The repository talks to Prisma.

Example:

```ts
export async function findByTitleAndInstructor(
  title: string,
  instructorId: string
) {
  return prisma.course.findFirst({
    where: {
      title,
      instructorId,
    },
  });
}
```

And:

```ts
export async function create(data: CreateCourseInput) {
  return prisma.course.create({
    data,
  });
}
```

That's the repository's job.

It shouldn't decide:

> "Should this instructor be allowed to create this course?"

That's business logic.

The repository should mostly answer:

> "Can I find/create/update/delete this database record?"

# 9. Repository Example

Let's create a course repository.

```ts
import { prisma } from "../../config/database";

export const courseRepository = {
  findById(id: string) {
    return prisma.course.findUnique({
      where: { id },
    });
  },

  findByTitleAndInstructor(
    title: string,
    instructorId: string
  ) {
    return prisma.course.findFirst({
      where: {
        title,
        instructorId,
      },
    });
  },

  create(data: {
    title: string;
    description?: string;
    level: string;
    instructorId: string;
  }) {
    return prisma.course.create({
      data,
    });
  },
};
```

Notice something important.

The repository doesn't know anything about HTTP.

There is no:

```ts
req
res
next
```

And there shouldn't be.

---

# 10. Service Example

```ts
import { AppError } from "../../utils/AppError";
import { courseRepository } from "./course.repository";

export const courseService = {
  async createCourse(input) {
    const existingCourse =
      await courseRepository.findByTitleAndInstructor(
        input.title,
        input.instructorId
      );

    if (existingCourse) {
      throw new AppError(
        "Course with this title already exists",
        409
      );
    }

    return courseRepository.create(input);
  },
};
```

The service doesn't know anything about:

```text
HTTP status codes
Express response objects
JSON formatting
```

It only knows the application's rules.

# 11. Controller Example

```ts
import { courseService } from "./course.service";

export async function createCourse(req, res) {
  const course = await courseService.createCourse({
    title: req.body.title,
    description: req.body.description,
    level: req.body.level,
    instructorId: req.user.id,
  });

  res.status(201).json({
    success: true,
    data: course,
  });
}
```

That's a **thin controller**.

And that's exactly what we want.

# 12. A More Important Example

Suppose later your LMS allows:

```text
Instructor
   ↓
Create Course
   ↓
Create Course Record
   ↓
Create Default Section
   ↓
Create Welcome Lesson
   ↓
Generate AI Course Outline
   ↓
Return Course
```

Where should this logic live?

**Service.**

Something like:

```ts
async function createCourse(input) {
  // validate business rules

  const course = await courseRepository.create(input);

  await sectionRepository.createDefault(course.id);

  await lessonRepository.createWelcomeLesson(course.id);

  await aiService.generateCourseOutline(course.id);

  return course;
}
```

The controller remains:

```ts
async function createCourse(req, res) {
  const course = await courseService.createCourse({
    ...req.body,
    instructorId: req.user.id,
  });

  res.status(201).json({
    success: true,
    data: course,
  });
}
```

This is where the architecture starts becoming powerful.

# 13. Repository ≠ Business Logic

This distinction is extremely important for interviews.

Bad:

```ts
async function createCourse(data) {
  if (data.level === "BEGINNER") {
    // some business rule
  }

  return prisma.course.create({
    data,
  });
}
```

The repository shouldn't make business decisions.

Better:

```text
Service
   ↓
"Is this course allowed?"
   ↓
Repository
   ↓
"Store this course."
```

---

# 14. Service ≠ Database Implementation

The service shouldn't contain lots of Prisma queries.

Bad:

```ts
async function createCourse(data) {
  const course = await prisma.course.create({
    data,
  });

  const section = await prisma.section.create({
    data: ...
  });

  return course;
}
```

Better:

```ts
async function createCourse(data) {
  const course = await courseRepository.create(data);

  await sectionRepository.createDefault(course.id);

  return course;
}
```

Now the service coordinates.

# 15. Think of It Like a Restaurant

This analogy will help you remember.

```text
Customer
   ↓
Waiter
   ↓
Chef
   ↓
Kitchen Staff
   ↓
Storage
```

Backend:

```text
Client
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

### Controller = Waiter

Takes the request and returns the response.

### Service = Chef

Decides what needs to happen.

### Repository = Kitchen/storage staff

Gets or stores the required ingredients/data.

### Database = Storage

Actually stores the data.

The waiter shouldn't walk into the storage room and start cooking.

Likewise:

> **Controller shouldn't directly manipulate Prisma.**

---

# 16. Should Every Service Have a Repository?

Usually, for a CRUD-heavy application like our LMS, yes, it's a good default.

But don't turn this into a religion.

For example, a tiny utility might not need:

```text
Controller
 ↓
Service
 ↓
Repository
```

You can keep simple code simple.

The architecture should **reduce complexity**, not create unnecessary files.

# 18. One Important Improvement: Repository Interfaces

As you become more advanced, you may see:

```ts
interface CourseRepository {
  findById(id: string): Promise<Course | null>;
  create(data: CreateCourseInput): Promise<Course>;
}
```

Then:

```ts
class PrismaCourseRepository implements CourseRepository {
  // Prisma implementation
}
```

This can be useful when you need:

```text
Testing
Multiple databases
Mock repositories
Dependency injection
Large applications
```

But **don't add this complexity yet**.

For your current project:

```text
Service
   ↓
Repository object
   ↓
Prisma
```

is perfectly fine.

We'll introduce abstractions when they actually provide value.

# 19. The Rule You Should Remember

When writing backend code, ask:

### Controller

> "Is this HTTP-related?"

If yes → Controller.

### Service

> "Is this a business decision or workflow?"

If yes → Service.

### Repository

> "Is this database access?"

If yes → Repository.

For example:

```text
req.body
req.params
res.status()
res.json()
```

→ Controller

```text
Can user enroll?
Can instructor publish?
Can student submit?
Should course be generated?
Should duplicate be allowed?
```

→ Service

```text
findUnique()
findMany()
create()
update()
delete()
```

→ Repository
