# Lesson 2.7 — Logging + Request IDs

This lesson is about making your backend **observable**.

When your AI LMS is small, you can use:

```bash
console.log()
```

But once you have:

```text
Users
Courses
Lessons
Quizzes
AI generation
Payments
Background jobs
PostgreSQL
Redis
External APIs
```

simple `console.log()` becomes difficult to manage.

We want logs that help us answer:

> **What happened, when did it happen, which request caused it, and how long did it take?**

---

# 1. Why Logging Matters

Imagine your deployed LMS shows:

```text
500 Internal Server Error
```

A user reports:

> "The course creation failed."

Without useful logging, you might see:

```text
Error
```

Not very helpful.

With proper logging:

```text
2026-08-14T00:15:21.312Z
ERROR
requestId=req_8f31a2
method=POST
path=/api/v1/courses
userId=user_123
status=500
duration=842ms
error="Database connection timeout"
```

Now debugging becomes much easier.

---

# 2. What Is a Log?

A log is simply a record of something that happened inside your application.

For example:

```text
INFO  Server started
INFO  User logged in
INFO  Course created
WARN  Rate limit approaching
ERROR Database query failed
```

A useful logging system usually has levels.

---

# 3. Log Levels

The common levels are:

```text
DEBUG
INFO
WARN
ERROR
```

### DEBUG

Detailed information useful during development.

```text
DEBUG Checking course ownership
```

### INFO

Normal application events.

```text
INFO Course created
```

### WARN

Something unusual happened, but the application can continue.

```text
WARN AI provider response was slow
```

### ERROR

Something failed.

```text
ERROR Database connection failed
```

For your LMS, this is a good starting point.

---

# 4. Why `console.log()` Isn't Enough

You might currently write:

```ts
console.log("User created", user);
```

Problems:

### Problem 1 — No structure

You get arbitrary strings.

### Problem 2 — Difficult searching

Finding a specific request becomes difficult.

### Problem 3 — Sensitive data

You might accidentally log:

```text
password
accessToken
refreshToken
API key
```

### Problem 4 — No request relationship

You don't know which logs belong to the same request.

That's where **request IDs** become extremely useful.

---

# 5. What Is a Request ID?

Imagine a user sends:

```http
POST /api/v1/courses
```

We generate:

```text
req_7f8a91
```

Then every log generated during that request gets the same ID:

```text
INFO  req_7f8a91 Course creation started
INFO  req_7f8a91 Checking instructor
INFO  req_7f8a91 Creating course
INFO  req_7f8a91 Course created
```

If something fails:

```text
ERROR req_7f8a91 Database timeout
```

You can search:

```text
req_7f8a91
```

and see the entire request lifecycle.

---

The architecture becomes:

```text
Client
  │
  ↓

  │
  ↓

  │
  ↓

  │
  ↓
Controller
  │
  ↓

  │

```

The request ID travels through the whole operation.

---

# 7. Generate a Request ID

Node.js already provides a good UUID generator.

```ts
import { randomUUID } from "node:crypto";
```

Then:

```ts
const requestId = randomUUID();
```

Example:

```text
4b8c1a34-7b3d-4f6a-a2c4-91c6b8e0d7ab
```

You can prefix it:

```ts
const requestId = `req_${randomUUID()}`;
```

---

# 8. Create Request ID Middleware

Create:

```text
src/middleware/requestId.ts
```

Example:

```ts
import { randomUUID } from "node:crypto";
import type { Request, Response, NextFunction } from "express";

export function requestId(
  req: Request,
  res: Response,
  next: NextFunction
) {
  const id = req.header("x-request-id") ?? `req_${randomUUID()}`;

  res.setHeader("x-request-id", id);

  req.requestId = id;

  next();
}
```

But there's one TypeScript problem.

Express's `Request` type doesn't know about:

```ts
req.requestId
```

yet.

We'll fix that properly.

---

# 9. Extending Express Request

Create:

```text
src/types/express.d.ts
```

Then:

```ts
declare global {
  namespace Express {
    interface Request {
      requestId: string;
    }
  }
}

export {};
```

Now TypeScript understands:

```ts
req.requestId
```

This technique is called **declaration merging**.

You'll use this pattern often in TypeScript backend development.

---

# 10. Register the Middleware

In `app.ts`:

```ts
app.use(requestId);
```

Put it early in your middleware chain.

For example:

```ts
app.use(helmet());

app.use(
  cors({
    origin: process.env.CLIENT_URL,
    credentials: true,
  })
);

app.use(requestId);

app.use(
  express.json({
    limit: "1mb",
  })
);
```

Now every request gets an ID.

---

# 11. Logging Request Completion

We can use the request lifecycle to log:

```text
HTTP method
URL
status code
duration
request ID
```

Create:

```text
src/middleware/requestLogger.ts
```

Example:

```ts
import type { Request, Response, NextFunction } from "express";

export function requestLogger(
  req: Request,
  res: Response,
  next: NextFunction
) {
  const start = Date.now();

  res.on("finish", () => {
    const duration = Date.now() - start;

    console.log({
      requestId: req.requestId,
      method: req.method,
      path: req.originalUrl,
      statusCode: res.statusCode,
      duration: `${duration}ms`,
    });
  });

  next();
}
```

Now a request might produce:

```text
{
  requestId: "req_123",
  method: "POST",
  path: "/api/v1/courses",
  statusCode: 201,
  duration: "142ms"
}
```

Already much better than:

```text
Course created
```

---

# 12. Why Measure Duration?

Suppose your API becomes slow.

You see:

```text
POST /courses → 3200ms
```

Now you know something is wrong.

You can investigate:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
PostgreSQL
```

Maybe the database query takes:

```text
2900ms
```

Or perhaps the AI provider takes:

```text
2800ms
```

This is the beginning of **performance observability**.

---

# 13. Structured Logging

Instead of:

```ts
console.log(
  "Course created by instructor " +
  userId
);
```

prefer structured data:

```ts
console.log({
  level: "info",
  event: "course.created",
  userId,
  requestId: req.requestId,
});
```

This is called **structured logging**.

The important idea is:

> Logs should contain data that machines can understand, not just sentences humans can read.

---

# 14. Create a Logger Utility

Instead of using `console.log()` everywhere, create:

```text
src/utils/logger.ts
```

Start simple:

```ts
type LogContext = Record<string, unknown>;

export const logger = {
  info(message: string, context?: LogContext) {
    console.log({
      level: "info",
      message,
      ...context,
    });
  },

  warn(message: string, context?: LogContext) {
    console.warn({
      level: "warn",
      message,
      ...context,
    });
  },

  error(message: string, context?: LogContext) {
    console.error({
      level: "error",
      message,
      ...context,
    });
  },
};
```

Now:

```ts
logger.info("Course created", {
  courseId,
  userId,
  requestId,
});
```

produces structured information.

---

# 15. Why Create a Logger Abstraction?

You might ask:

> Why not just use `console.log()`?

Because later you can replace the implementation.

Today:

```text
logger
 ↓
console
```

Later:

```text
logger
 ↓
Pino
 ↓
Log aggregation service
```

Your application code doesn't need to change everywhere.

For production Node.js applications, **Pino** is a strong option because it is designed for fast structured logging.

But don't rush into adding another library yet.

First understand the architecture.

---

# 16. Request ID + User ID

Once authentication runs, you can combine:

```text
requestId
+
userId
```

Example:

```ts
logger.info("Course created", {
  requestId: req.requestId,
  userId: req.user.id,
  courseId: course.id,
});
```

Now you can answer:

```text
Which request?
→ req_abc123

Which user?
→ user_xyz

Which course?
→ course_789
```

This becomes extremely useful when debugging user reports.

---

# 17. Error Logging

Remember our error handler from earlier?

Now we can improve it.

Something like:

```ts
logger.error("Request failed", {
  requestId: req.requestId,
  method: req.method,
  path: req.originalUrl,
  statusCode: error.statusCode,
  error: error.message,
});
```

Then return the user-safe response:

```json
{
  "success": false,
  "error": {
    "message": "Something went wrong",
    "requestId": "req_123"
  }
}
```

This is a **very useful production pattern**.

---

# 18. Why Return the Request ID to the Client?

Imagine the user contacts support:

> "I got an error while generating my course."

Instead of asking:

> "Can you tell me exactly what happened?"

you can ask them for:

```text
Request ID: req_abc123
```

Then you search your logs:

```text
req_abc123
```

and find the complete request history.

This is especially useful for your AI LMS because AI generation can involve several external systems.

Imagine:

```text
POST /api/v1/ai/course-outline
```

Request:

```text
req_93f2a8
```

Logs:

---

# 20. Never Log Sensitive Information

This is **extremely important**.

Never casually log:

```text
❌ passwords
❌ access tokens
❌ refresh tokens
❌ API keys
❌ cookies
❌ authorization headers
❌ private user information
```

Don't do:

```ts
logger.info("Request", {
  headers: req.headers,
  body: req.body,
});
```

because you could accidentally expose:

```text
Authorization: Bearer ...
Cookie: refreshToken=...
password: ...
```

Instead, selectively log fields.

---

# 21. Development vs Production

During development, you may want:

```text
DEBUG
INFO
WARN
ERROR
```

Production might use:

```text
INFO
WARN
ERROR
```

because excessive debug logging can create:

```text
Huge log volume
Higher storage cost
More noise
Potential data leakage
```

You can control this using:

```env
LOG_LEVEL=info
```

Later, a proper logger such as Pino can handle log levels cleanly.

---

# 22. Logging Database Queries

Be careful here.

You might be tempted to log:

```text
Every SQL query
```

That's useful during debugging but can become noisy in production.

Instead, focus on meaningful events:

```text
course.created
course.updated
course.deleted
user.login
user.logout
enrollment.created
ai.generation.started
ai.generation.completed
ai.generation.failed
```

This is much more useful.

I recommend a consistent naming style:

```text

```

This will become extremely useful when searching logs.

# 24. Request ID vs User ID

Don't confuse these.

### Request ID

Identifies **one HTTP request**.

```text
req_123
```

### User ID

Identifies **one user**.

```text
user_456
```

One user can generate hundreds of request IDs:

```text
user_456
   ├── req_001
   ├── req_002
   ├── req_003
   └── req_004
```

So:

```text
User ID → user
Request ID → request
```

Both are valuable.

---

# 25. Request ID vs Trace ID

Later you'll encounter:

```text
requestId
traceId
spanId
```

For now, understand the basic difference:

```text
requestId
```

usually identifies one incoming HTTP request.

A distributed system may have:

```text
HTTP Request
    ↓
API
    ↓
AI Service
    ↓
Queue
    ↓
Worker
    ↓
Database
```

Then a **trace ID** can connect the entire distributed operation.

We'll eventually talk about this when we reach more advanced backend/DevOps topics.

For our current LMS:

> **Request ID is enough.**

# 27. A Small but Important Improvement

You can also accept an existing request ID:

```ts
const id =
  req.header("x-request-id") ??
  `req_${randomUUID()}`;
```

Why?

Suppose another service calls your API:

```http
X-Request-ID: req_abc123
```

You can preserve it.

This becomes useful when multiple services communicate with each other.

However, don't blindly trust arbitrary IDs forever. Later, when we discuss distributed systems, we'll look at better tracing practices.
