# Lesson 3.10 — Query Optimization

This lesson connects almost everything we've learned so far:

```text
Schema
   ↓
Relationships
   ↓
Indexes
   ↓
Constraints
   ↓
Queries
   ↓
Query Planner
   ↓
Performance
```

The goal isn't:

> "Make every query as fast as possible."

The real goal is:

> **Understand why a query is slow and improve it based on evidence.**

That mindset is extremely important for backend engineering.

---

# 1. What Is Query Optimization?

Query optimization means improving how a database query executes so that it uses reasonable:

```text
CPU
Memory
Disk I/O
Network
Database time
```

For example:

```sql
SELECT *
FROM lessons
WHERE course_id = 'abc';
```

might be fast with:

```text
10 lessons
```

but much slower with:

```text
10 million lessons
```

The query itself hasn't changed.

The **data scale** has.

That's why database performance becomes increasingly important as applications grow.

---

# 2. The Wrong Way to Optimize

A beginner sees:

```text
API is slow
```

and thinks:

```text
Add an index.
```

Then:

```text
Still slow.
```

So:

```text
Add another index.
```

Then:

```text
Add five more indexes.
```

This is not database engineering.

Instead:

```text
Slow query
   ↓
Measure
   ↓
EXPLAIN ANALYZE
   ↓
Understand plan
   ↓
Identify bottleneck
   ↓
Optimize
   ↓
Measure again
```

---

# 3. The Query Planner

PostgreSQL has a **query planner/optimizer**.

When you execute:

```sql
SELECT *
FROM lessons
WHERE course_id = 'abc';
```

PostgreSQL doesn't simply execute the SQL literally.

It decides:

> "What's the cheapest way to get these rows?"

It might choose:

```text
Sequential Scan
```

or:

```text
Index Scan
```

or:

```text
Bitmap Index Scan
```

or another execution strategy.

Conceptually:

```text
SQL
 ↓
Parser
 ↓
Planner
 ↓
Execution Plan
 ↓
Executor
 ↓
Results
```

---

# 4. What Is a Query Plan?

A query plan describes **how PostgreSQL intends to execute a query**.

For example:

```text
Index Scan
  Index Cond: (course_id = 'abc')
```

means PostgreSQL plans to use an index.

Or:

```text
Seq Scan on lessons
  Filter: (course_id = 'abc')
```

means PostgreSQL plans to scan the table sequentially and filter rows.

---

# 5. `EXPLAIN`

The first tool you should learn is:

```sql
EXPLAIN
```

For example:

```sql
EXPLAIN
SELECT *
FROM lessons
WHERE course_id = 'abc';
```

PostgreSQL returns a plan.

You can use it to understand:

```text
What scan is being used?
What does PostgreSQL expect to read?
What operations are expensive?
```

---

# 6. `EXPLAIN ANALYZE`

Now the important one:

```sql
EXPLAIN ANALYZE
SELECT *
FROM lessons
WHERE course_id = 'abc';
```

`EXPLAIN` tells you the planned execution.

`EXPLAIN ANALYZE` actually executes the query and reports what happened.

This lets you compare:

```text
Estimated
vs
Actual
```

That's extremely useful.

---

# 7. Example Query Plan

You might see something like:

```text
Index Scan using lessons_course_id_idx on lessons
  (cost=0.29..12.40 rows=10 width=120)
  (actual time=0.05..0.08 rows=10 loops=1)
```

Don't worry about memorizing everything.

Let's break it down.

---

# 8. `cost`

You may see:

```text
cost=0.29..12.40
```

These are PostgreSQL's **estimated cost units**.

They are not milliseconds.

Think:

```text
cost
↓
relative estimate used by planner
```

Don't say:

> "The query costs 12.40 milliseconds."

That's incorrect.

---

# 9. `actual time`

You may see:

```text
actual time=0.05..0.08
```

These are actual execution times, typically in milliseconds.

So:

```text
cost
→ planner estimate

actual time
→ what happened during execution
```

---

# 10. `rows`

You may see:

```text
rows=10
```

The planner expected around 10 rows.

With `EXPLAIN ANALYZE`, you may see:

```text
rows=10
```

for the actual result.

But sometimes you get:

```text
estimated rows = 10
actual rows = 50,000
```

That's a warning sign.

Why?

Because the planner made a very inaccurate estimate.

That can lead to a poor execution plan.

---

# 11. `loops`

You may see:

```text
loops=1
```

This means the operation ran once.

You might also see:

```text
loops=1000
```

Then even a small operation can become expensive.

For example:

```text
0.1 ms × 1000 loops
```

can become significant.

This is especially important when analyzing joins.

---

# 12. Sequential Scan

Suppose:

```text
lessons
```

contains:

```text
10 million rows
```

and you run:

```sql
SELECT *
FROM lessons
WHERE course_id = 'abc';
```

PostgreSQL might use:

```text
Seq Scan on lessons
```

Sequential scan means:

> PostgreSQL reads through the table and checks rows against the condition.

Conceptually:

```text
Row 1 → check
Row 2 → check
Row 3 → check
...
Row 10,000,000 → check
```

That can be expensive.

---

# 13. But Sequential Scan Isn't Always Bad

This is extremely important.

Suppose:

```text
lessons = 100 rows
```

and your query needs:

```text
90 rows
```

An index might not provide much benefit.

PostgreSQL may reasonably choose:

```text
Seq Scan
```

because reading the table directly is cheaper.

So:

```text
Seq Scan ≠ automatically bad
```

Never optimize purely because you see:

```text
Seq Scan
```

Look at:

```text
table size
rows returned
query pattern
actual execution time
```

---

# 14. Index Scan

If PostgreSQL has a useful index:

```text
course_id
```

it might choose:

```text
Index Scan
```

Conceptually:

```text
Query
 ↓
Index
 ↓
Find matching row locations
 ↓
Fetch rows
```

For selective queries, this can be much faster than scanning the entire table.

---

# 15. Bitmap Index Scan

You may encounter:

```text
Bitmap Index Scan
```

and:

```text
Bitmap Heap Scan
```

Don't panic.

A simplified idea is:

```text
Index
 ↓
Build bitmap of matching pages/rows
 ↓
Read relevant table pages
```

PostgreSQL may choose this when there are many matching rows and using individual index lookups would be less efficient.

The planner is choosing between different strategies.

---

# 16. Index Scan vs Sequential Scan

Think:

```text
Small table
    ↓
Seq Scan may be best

Large table + highly selective filter
    ↓
Index Scan may be best

Many matching rows
    ↓
Bitmap strategy may be best
```

The planner decides based on statistics and estimated costs.

That's why blindly forcing an index is usually a bad idea.

---

# 17. The `SELECT *` Problem

Consider:

```sql
SELECT *
FROM users
WHERE id = 'abc';
```

This may be perfectly fine for a small result.

But suppose:

```text
users
```

has many columns:

```text
id
name
email
password_hash
bio
profile_image
preferences
settings
metadata
...
```

and you only need:

```text
name
email
```

Better:

```sql
SELECT name, email
FROM users
WHERE id = 'abc';
```

This reduces unnecessary data transfer and can make queries more efficient.

So:

> **Select only what you need when practical.**

---

# 18. Why `SELECT *` Can Become Expensive

Imagine your API returns:

```json
{
  "id": "...",
  "name": "Rahul",
  "email": "...",
  "passwordHash": "...",
  "preferences": {...},
  "largeMetadata": {...}
}
```

But the frontend only needs:

```json
{
  "name": "Rahul",
  "email": "..."
}
```

You're unnecessarily moving data:

```text
Database
 ↓
Backend
 ↓
Network
 ↓
Frontend
```

So query optimization isn't only about database CPU.

It can also reduce:

```text
I/O
memory
network
serialization
```

---

# 19. Index Only Scans

Sometimes PostgreSQL can satisfy a query entirely from an index.

For example, suppose:

```sql
SELECT email
FROM users
WHERE email = 'rahul@example.com';
```

and an appropriate index contains everything PostgreSQL needs.

It may be able to use an:

```text
Index Only Scan
```

instead of fetching the full table row.

This can be very efficient.

You don't need to optimize specifically for index-only scans yet, but it's useful to know they exist.

---

# 20. Query Optimization Starts With the Query

Suppose you write:

```sql
SELECT *
FROM lessons
WHERE course_id = 'abc';
```

First ask:

```text
Do I need every column?
```

Maybe:

```sql
SELECT id, title, lesson_order
FROM lessons
WHERE course_id = 'abc'
ORDER BY lesson_order;
```

is more appropriate.

Now we have a more precise query.

---

# 21. `WHERE` Conditions

Indexes are especially useful when columns appear in filtering conditions.

For example:

```sql
WHERE user_id = ?
```

or:

```sql
WHERE course_id = ?
```

or:

```sql
WHERE created_at >= ?
```

But whether an index helps depends on:

```text
selectivity
table size
data distribution
query frequency
```

Again:

> **Measure. Don't guess.**

---

# 22. `ORDER BY`

Consider:

```sql
SELECT id, title
FROM courses
ORDER BY created_at DESC
LIMIT 20;
```

If this query runs constantly and the table is large, an index involving:

```text
created_at
```

may help.

In Prisma:

```prisma
@@index([createdAt(sort: Desc)])
```

But don't create the index just because `ORDER BY` exists.

Check actual workload and query plans.

---

# 23. `LIMIT`

This is another useful optimization.

Suppose:

```sql
SELECT *
FROM courses
ORDER BY created_at DESC
LIMIT 20;
```

The database only needs:

```text
20 rows
```

rather than every course.

This can make a huge difference when combined with an appropriate index.

Compare:

```text
100 rows
vs
10 million rows
```

and:

```sql
LIMIT 20
```

can significantly reduce the amount of work needed.

---

# 24. Pagination

Suppose your LMS has:

```text
10 million courses
```

Don't do:

```sql
SELECT *
FROM courses
LIMIT 20 OFFSET 5000000;
```

Large offsets can become inefficient because PostgreSQL may still need to walk past many rows.

A common alternative is **cursor/keyset pagination**.

For example:

```sql
SELECT id, title, created_at
FROM courses
WHERE created_at < '2026-08-14T10:00:00Z'
ORDER BY created_at DESC
LIMIT 20;
```

Then the next request uses the last row's position as the cursor.

Conceptually:

```text
Page 1
   ↓
last_created_at
   ↓
Page 2
   ↓
next cursor
   ↓
Page 3
```

This is a very useful technique for large datasets.

---

# 25. Offset vs Cursor Pagination

### Offset

```text
page = 1000
offset = 19980
```

Simple.

Good for:

```text
small/moderate datasets
admin tables
simple UIs
```

### Cursor

```text
after = last_record_id
```

Better for:

```text
large datasets
feeds
infinite scrolling
high-volume APIs
```

For your AI LMS, you'll likely use both depending on the endpoint.

---

# 26. Query Optimization and Joins

Suppose:

```sql
SELECT
    lessons.id,
    lessons.title,
    courses.title
FROM lessons
JOIN courses
    ON lessons.course_id = courses.id
WHERE courses.id = 'abc';
```

PostgreSQL has to:

```text
find course
     ↓
find matching lessons
     ↓
join rows
```

Good schema design and useful indexes can make this efficient.

For example:

```text
courses.id
→ primary key

lessons.course_id
→ useful index candidate
```

This is why our earlier lessons on relationships and indexes matter.

---

# 27. N+1 Query Problem

This is extremely important for application developers.

Suppose you fetch:

```text
10 courses
```

Then your code does:

```text
For each course:
    fetch lessons
```

You might accidentally create:

```text
1 query → courses
10 queries → lessons
```

Total:

```text
11 queries
```

This is called the **N+1 query problem**.

---

# 28. N+1 Example

Bad pattern:

```ts
const courses = await prisma.course.findMany();

for (const course of courses) {
  const lessons = await prisma.lesson.findMany({
    where: {
      courseId: course.id,
    },
  });
}
```

If there are:

```text
100 courses
```

you could end up with:

```text
1 + 100 = 101 queries
```

That can become expensive.

---

# 29. Prisma Relations Can Help

Instead of manually querying every course:

```ts
const courses = await prisma.course.findMany({
  include: {
    lessons: true,
  },
});
```

Now Prisma can handle the relation loading strategy.

Depending on configuration and query shape, Prisma may use different SQL strategies.

The important lesson is:

> **Be aware of how many database queries your application is actually generating.**

Don't assume one line of Prisma equals one SQL query or that relation loading always behaves identically in every version/configuration.

---

# 30. Avoid Huge Nested Queries

The opposite problem also exists.

You might write:

```ts
include: {
  lessons: {
    include: {
      quizzes: {
        include: {
          questions: true,
        },
      },
    },
  },
}
```

Now you could retrieve a huge amount of data.

Your API might only need:

```text
course title
+
lesson title
```

So instead of:

```text
fetch everything
```

design the query around the endpoint's actual requirements.

---

# 31. Prisma `select`

For example:

```ts
const courses = await prisma.course.findMany({
  select: {
    id: true,
    title: true,
  },
});
```

Instead of:

```ts
const courses = await prisma.course.findMany();
```

This makes your intent explicit.

You can also select nested fields:

```ts
const courses = await prisma.course.findMany({
  select: {
    id: true,
    title: true,
    lessons: {
      select: {
        id: true,
        title: true,
      },
    },
  },
});
```

This is often better than returning huge objects.

---

# 32. Avoid Filtering in JavaScript

Suppose you have:

```ts
const courses = await prisma.course.findMany();

const active = courses.filter(course => course.status === "ACTIVE");
```

You may have fetched:

```text
100,000 courses
```

just to keep:

```text
20,000
```

Instead, let PostgreSQL filter:

```ts
const courses = await prisma.course.findMany({
  where: {
    status: "ACTIVE",
  },
});
```

Now:

```text
Database
   ↓
filter
   ↓
send only needed rows
```

This is almost always the better direction for large datasets.

---

# 33. Don't Fetch More Rows Than You Need

Bad:

```ts
const users = await prisma.user.findMany();
```

if you only need:

```text
one user
```

Use:

```ts
const user = await prisma.user.findUnique({
  where: {
    id: userId,
  },
});
```

Or if you need a small set:

```ts
take: 20
```

The principle:

> **Push filtering, sorting, and limiting into the database whenever appropriate.**

---

# 34. Query Performance and Data Modeling

Sometimes a slow query isn't really a query problem.

It might be a schema problem.

For example:

```text
One giant table
```

containing:

```text
user
course
lesson
quiz
progress
AI messages
```

could make many queries awkward.

A properly normalized relational model:

```text
User
Course
Lesson
Enrollment
Quiz
Question
Attempt
Progress
AIConversation
AIMessage
```

allows PostgreSQL to work with targeted data structures.

This is why database design comes before optimization.

---

# 35. Statistics

PostgreSQL maintains statistics about your data.

The query planner uses them to estimate:

```text
How many rows will this filter return?
Which plan is cheaper?
Should I use an index?
Which join strategy should I use?
```

If statistics are inaccurate or stale, PostgreSQL may choose a poor plan.

PostgreSQL's automatic maintenance mechanisms help keep these statistics updated.

You can also manually run:

```sql
ANALYZE users;
```

when needed.

You won't normally need to manually run `ANALYZE` for every application request.

---

# 36. Estimated vs Actual Rows

Suppose:

```text
Estimated rows: 10
Actual rows: 500,000
```

That's a huge mismatch.

The planner expected:

```text
10
```

but got:

```text
500,000
```

This can cause PostgreSQL to choose a bad strategy.

For example, it may choose a nested loop based on the expectation of a tiny result when a different join strategy would be better for a huge result.

This is why:

```sql
EXPLAIN ANALYZE
```

is so useful.

---

# 37. Query Optimization and Joins

PostgreSQL can use different join strategies.

You'll commonly encounter:

```text
Nested Loop
Hash Join
Merge Join
```

Don't worry about mastering all of them yet.

Understand the basic idea:

```text
Nested Loop
→ repeatedly match rows

Hash Join
→ build hash structure and match

Merge Join
→ work with sorted inputs
```

The planner chooses based on estimates and costs.

We'll revisit these when you work more deeply with query plans.

---

# 38. Nested Loop Isn't Automatically Bad

This follows the same principle as sequential scans.

Suppose:

```text
Table A → 10 rows
Table B → 10 rows
```

A nested loop may be perfectly fine.

But:

```text
Table A → 1 million rows
Table B → 10 million rows
```

could require a very different strategy.

So:

```text
Nested Loop ≠ bad
Seq Scan ≠ bad
Index Scan ≠ always good
```

You need context.

---

# 39. Functions on Indexed Columns

Consider:

```sql
SELECT *
FROM users
WHERE LOWER(email) = 'rahul@example.com';
```

If your normal index is:

```text
email
```

PostgreSQL may not be able to use that ordinary index efficiently because the query applies:

```text
LOWER(email)
```

to the column.

You might need a functional index:

```sql
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));
```

This is an advanced example of an important principle:

> **The way you write a query affects whether an index can be useful.**

---

# 40. Don't Optimize Prematurely

Suppose your LMS has:

```text
100 users
```

and:

```text
20 courses
```

Don't spend days optimizing a query that takes:

```text
0.8 ms
```

Optimize when there is evidence.

A good engineering cycle is:

```text
Build
 ↓
Measure
 ↓
Find bottleneck
 ↓
Optimize
 ↓
Measure again
```

Not:

```text
Guess
 ↓
Add indexes everywhere
 ↓
Hope
```

# 41. Query Optimization Example — AI LMS

Imagine this endpoint:

```text
GET /courses/:courseId/lessons
```

Initial Prisma query:

```ts
const lessons = await prisma.lesson.findMany({
  where: {
    courseId,
  },
});
```

Possible performance considerations:

```text
courseId index?
```

Likely useful if the table is large.

Then maybe:

```ts
const lessons = await prisma.lesson.findMany({
  where: {
    courseId,
  },
  select: {
    id: true,
    title: true,
    lessonOrder: true,
  },
  orderBy: {
    lessonOrder: "asc",
  },
});
```

Now we have:

```text
filter
+
select
+
order
```

We might consider an index aligned with the access pattern:

```prisma
@@index([courseId, lessonOrder])
```

But again:

> Verify with actual query plans and workload before assuming it's necessary.

# 42. Another Example — Student Dashboard

Suppose the dashboard needs:

```text
Student's active enrollments
+
course information
+
progress
```

A poorly designed implementation could make:

```text
20+ database queries
```

A better approach might:

```text
1. Identify required data
2. Design appropriate relations
3. Use targeted queries
4. Select only required columns
5. Add indexes for frequent filters
6. Measure query execution
```

Optimization is therefore not just about SQL.

It's about the **entire data-access design**.

---

# 43. Query Optimization Checklist

When an API endpoint is slow, go through this list:

```text
1. Which query is actually slow?

2. How many database queries does the request execute?

3. Are we fetching unnecessary columns?

4. Are we fetching unnecessary rows?

5. Is there an N+1 problem?

6. Are WHERE columns indexed appropriately?

7. Is composite index order correct?

8. Is ORDER BY expensive?

9. Is OFFSET very large?

10. What does EXPLAIN ANALYZE show?

11. Are estimated and actual rows very different?

12. Is the database or application layer actually the bottleneck?
```

This is a professional debugging process.

---

# 44. Database Optimization vs Application Optimization

Sometimes the database isn't the problem.

Imagine:

```text
API response = 2 seconds
```

You investigate.

Database:

```text
20 ms
```

Application:

```text
1.8 seconds
```

Then adding indexes won't help.

The bottleneck could be:

```text
AI API
serialization
network
CPU
external API
authentication
file processing
```

Always identify the actual bottleneck first.

---

# 45. Performance Is a Measurement Problem

This is one of the biggest lessons from this module.

Never say:

> "This query feels slow."

Instead find:

```text
Actual execution time
Rows examined
Rows returned
Query count
Query plan
CPU
I/O
```

Then make a change.

Then measure again.

This is the difference between:

```text
optimization
```

and:

```text
guessing
```

# 47. The Big Picture of Database Performance

You can think of performance as:

```text
                 Query
                   ↓
          ┌─────────────────┐
          │ Query Planner   │
          └────────┬────────┘
                   ↓
        ┌─────────────────────┐
        │ Execution Plan      │
        │                     │
        │ Seq Scan            │
        │ Index Scan          │
        │ Join                │
        │ Sort                │
        │ Filter              │
        └──────────┬──────────┘
                   ↓
               PostgreSQL
                   ↓
                 Data
```

And your job is to understand:

> **Why did PostgreSQL choose this plan, and is it appropriate for this workload?**

That's database engineering.

# 48. What You Should Know for Interviews

You should be able to explain:

### What is query optimization?

Improving database query execution to reduce unnecessary resource usage and execution time.

### What is `EXPLAIN`?

It shows PostgreSQL's planned execution strategy.

### What is `EXPLAIN ANALYZE`?

It executes the query and reports actual execution statistics alongside the plan.

### What is a sequential scan?

Reading through the table to find matching rows.

### What is an index scan?

Using an index to locate relevant rows.

### Is sequential scan always bad?

No. For small tables or queries returning a large portion of the table, it may be optimal.

### What is N+1?

One query retrieves parent records, followed by one additional query per parent record.

### How do you optimize?

Measure first, inspect the query plan, identify the bottleneck, make a targeted change, and measure again.
