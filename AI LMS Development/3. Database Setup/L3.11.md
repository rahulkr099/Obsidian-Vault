# Lesson 3.11 — Database Seeding

Now we're at **Lesson 3.11**, and this one is extremely practical for your AI LMS.

Imagine you reset your database:

```text
users       → empty
courses     → empty
lessons     → empty
enrollments → empty
quizzes     → empty
```

Now you need to manually create:

```text
1 admin
5 instructors
20 students
10 courses
100 lessons
50 enrollments
```

That's painful.

**Database seeding** solves this.

---

# 1. What Is Database Seeding?

Seeding means:

> **Automatically inserting predefined data into your database.**

Think:

```text
Empty Database
      ↓
Seed Script
      ↓
Users
Courses
Lessons
Enrollments
etc.
```

For your AI LMS:

```text
Seed
 │
 ├── Admin
 ├── Instructor
 ├── Students
 ├── Courses
 ├── Lessons
 ├── Enrollments
 └── Progress
```

Now you can start developing immediately.

---

# 2. Why Do We Need Seeding?

Without seeding:

```text
Reset database
      ↓
Empty
      ↓
Create data manually
      ↓
Start testing
```

With seeding:

```text
Reset database
      ↓
Run seed
      ↓
Development data ready
```

For a developer, this is a huge productivity improvement.

---

# 3. Seeding vs Production Data

This distinction is important.

### Seed data

Usually used for:

```text
Development
Testing
Local demos
CI environments
Initial setup
```

### Production data

Usually comes from:

```text
Real users
Real courses
Real enrollments
Real activity
```

You generally don't want to run a development seed script against production.

Imagine:

```text
Production
↓
10,000 real users
↓
Run seed script
↓
💥
```

So keep your seed workflow controlled.

---

# 4. Prisma Seed

Prisma supports a seed script that you can configure for your project.

A common structure:

```text
ai-lms/
├── prisma/
│   ├── schema.prisma
│   └── seed.ts
├── src/
├── package.json
└── tsconfig.json
```

Your seed logic lives in:

```text
prisma/seed.ts
```

---

# 5. A Simple Seed Script

For example:

```ts
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

async function main() {
  await prisma.user.create({
    data: {
      name: "Rahul",
      email: "rahul@example.com",
      passwordHash: "hashed-password",
    },
  });
}

main()
  .catch((error) => {
    console.error(error);
    process.exit(1);
  })
  .finally(async () => {
    await prisma.$disconnect();
  });
```

Conceptually:

```text
seed.ts
   ↓
Prisma Client
   ↓
PostgreSQL
   ↓
Insert development data
```

---

# 6. Why Use `main()`?

You could put everything at the top level, but this structure is cleaner:

```ts
async function main() {
  // seed logic
}
```

Then:

```ts
main()
  .catch(...)
  .finally(...);
```

This gives you a clear entry point and proper error handling/cleanup.

---

# 7. Configure the Seed Command

Your Prisma project needs to know how to execute the seed script.

Depending on your Prisma version/setup, this is configured in your project configuration/package tooling.

For a TypeScript project, a common approach is to use a TypeScript runner such as:

```text
tsx
```

and configure the Prisma seed command to execute:

```bash
tsx prisma/seed.ts
```

The exact configuration can differ across Prisma versions, so always follow the version you're using.

The important concept is:

```text
Prisma
   ↓
seed command
   ↓
prisma/seed.ts
```

---

# 8. Running the Seed

Once configured, you can run the seed command supported by your Prisma setup.

A common workflow is:

```bash
npx prisma db seed
```

This executes your seed script.

You should see your data appear in PostgreSQL.

---

# 9. Seed One User

Let's start simple.

```ts
async function main() {
  await prisma.user.create({
    data: {
      name: "Rahul",
      email: "rahul@example.com",
      passwordHash: "hashed-password",
    },
  });
}
```

Run:

```bash
npx prisma db seed
```

Database:

```text
users

Rahul
rahul@example.com
```

Run it again, though, and you may get:

```text
❌ Unique constraint violation
```

because:

```text
email = rahul@example.com
```

already exists.

This introduces an important concept.

---

# 10. Idempotent Seeding

A good seed script should ideally be **idempotent**.

In simple terms:

> Running the seed repeatedly should produce the same intended development state instead of continuously creating duplicates or failing unnecessarily.

For example:

```text
Run seed
 ↓
10 users

Run seed again
 ↓
Still 10 users
```

rather than:

```text
Run 1 → 10 users
Run 2 → 20 users
Run 3 → 30 users
```

This makes development much easier.

---

# 11. `upsert`

One useful Prisma operation is:

```ts
await prisma.user.upsert({
  where: {
    email: "rahul@example.com",
  },
  update: {
    name: "Rahul",
  },
  create: {
    name: "Rahul",
    email: "rahul@example.com",
    passwordHash: "hashed-password",
  },
});
```

Think:

```text
Does user exist?
      │
 ┌────┴────┐
YES        NO
 │          │
UPDATE     CREATE
```

This is very useful for seed data.

---

# 12. Why `upsert` Works Well for Seed Data

Suppose you want a known development admin:

```text
admin@example.com
```

You can use:

```ts
await prisma.user.upsert({
  where: {
    email: "admin@example.com",
  },
  update: {},
  create: {
    name: "Development Admin",
    email: "admin@example.com",
    passwordHash: "hashed-password",
  },
});
```

Now:

```text
First run
→ create

Second run
→ already exists
```

Much more reliable.

---

# 13. Be Careful With `update`

Consider:

```ts
update: {
  name: "Development Admin",
}
```

Every seed run will reset the name.

That may be exactly what you want for development.

But if you have:

```ts
update: {
  passwordHash: ...
}
```

you're also resetting the password every time.

So decide whether your seed should:

```text
preserve existing data
```

or:

```text
reset it to a known state
```

# 14. Creating Related Data

Now let's create:

```text
User
 ↓
Course
 ↓
Lessons
```

You could create the user first:

```ts
const instructor = await prisma.user.create({
  data: {
    name: "Instructor",
    email: "instructor@example.com",
    passwordHash: "hashed-password",
  },
});
```

Then:

```ts
const course = await prisma.course.create({
  data: {
    title: "Backend Engineering",
    instructorId: instructor.id,
  },
});
```

Then:

```ts
await prisma.lesson.create({
  data: {
    courseId: course.id,
    title: "Introduction to PostgreSQL",
    lessonOrder: 1,
  },
});
```

The relationship is:

```text
Instructor
    ↓
Course
    ↓
Lesson
```

---

# 15. Nested Creates

Prisma also supports nested writes.

For example:

```ts
const course = await prisma.course.create({
  data: {
    title: "Backend Engineering",

    instructor: {
      connect: {
        id: instructor.id,
      },
    },

    lessons: {
      create: [
        {
          title: "PostgreSQL Basics",
          lessonOrder: 1,
        },
        {
          title: "Database Indexes",
          lessonOrder: 2,
        },
      ],
    },
  },
});
```

This lets you create related records together.

Conceptually:

```text
Course
 ├── Lesson 1
 └── Lesson 2
```

---

# 16. `connect`

This:

```prisma
instructor: {
  connect: {
    id: instructor.id
  }
}
```

means:

> Connect this course to an existing user.

You aren't creating a new user.

You're referencing an existing one.

---

# 17. `create`

This:

```prisma
lessons: {
  create: [...]
}
```

means:

> Create new related records.

So:

```text
connect
→ existing record

create
→ new record
```

This distinction is important when working with Prisma relations.

---

# 18. Seed Order Matters

Suppose:

```text
Lesson → Course
```

A lesson needs a valid course.

Therefore:

```text
Course first
      ↓
Lesson second
```

Similarly:

```text
User
 ↓
Course
 ↓
Lesson
 ↓
Enrollment
 ↓
Progress
```

A logical seed order might be:

```text
1. Users
2. Courses
3. Lessons
4. Enrollments
5. Progress
6. Quizzes
7. Questions
8. Attempts
9. AI conversations
```

This follows your foreign-key dependencies.

---

# 19. Why Seed Order Matters

Suppose you try:

```text
Create lesson
```

before:

```text
Create course
```

but:

```text
lesson.courseId
```

references:

```text
course.id
```

PostgreSQL will reject it.

Because:

```text
course doesn't exist
```

So your seed script should generally follow the dependency graph.

---

# 20. AI LMS Seed Architecture

Eventually your seed might look like:

```text
seed.ts
│
├── seedUsers()
│
├── seedCourses()
│
├── seedLessons()
│
├── seedEnrollments()
│
├── seedProgress()
│
├── seedQuizzes()
│
├── seedQuestions()
│
└── seedAIData()
```

Instead of one giant function.

This makes it easier to maintain.

---

# 21. Example Seed Structure

```ts
async function main() {
  const users = await seedUsers();

  const courses = await seedCourses(users);

  await seedLessons(courses);

  await seedEnrollments(users, courses);

  await seedProgress(users, courses);
}
```

This gives you a clear dependency flow.

---

# 22. Don't Hard-Code IDs Everywhere

A beginner might do:

```ts
await prisma.lesson.create({
  data: {
    courseId: "abc123",
  },
});
```

This is fragile.

Instead:

```ts
const course = await prisma.course.create({
  data: {
    title: "Backend Engineering",
  },
});

await prisma.lesson.create({
  data: {
    courseId: course.id,
    title: "PostgreSQL",
  },
});
```

Now the actual database-generated ID is used.

Better.

---

# 23. Seed Data Should Be Predictable

Good seed data should have predictable identities.

For example:

```text
admin@example.com
instructor@example.com
student1@example.com
student2@example.com
```

Courses:

```text
MERN Stack
PostgreSQL
TypeScript
Backend Engineering
```

This makes manual testing easier.

You know exactly which accounts and records exist.

---

# 24. Use Environment-Safe Passwords

Your seed users may need passwords.

Never store real production passwords in the repository.

Instead, use known development-only credentials and hash them properly.

For example:

```ts
const passwordHash = await bcrypt.hash(
  "development-password",
  12
);
```

Then:

```ts
await prisma.user.create({
  data: {
    name: "Development Admin",
    email: "admin@example.com",
    passwordHash,
  },
});
```

Don't store:

```text
passwordHash = "password123"
```

as if it were a real hash.

---

# 25. Don't Seed Real Secrets

Your seed file should never contain:

```text
production database password
production JWT secret
production API keys
real user passwords
real OAuth secrets
```

Keep secrets in environment variables.

For example:

```env
SEED_ADMIN_PASSWORD=...
```

and access it in development.

But be careful about accidentally printing secrets to logs.

---

# 26. Fake Data vs Realistic Data

There are two useful kinds of seed data.

### Small deterministic seed

```text
2 users
2 courses
10 lessons
```

Useful for:

```text
daily development
debugging
manual testing
```

### Larger realistic seed

```text
100 users
50 courses
1000 lessons
5000 enrollments
```

Useful for:

```text
performance testing
pagination testing
index testing
dashboard testing
```

Both are valuable.

---

# 27. Seed Data for Testing Pagination

Remember Lesson 3.10?

We discussed:

```text
OFFSET
cursor pagination
large datasets
```

If your database contains:

```text
10 courses
```

you can't meaningfully test:

```text
page 100
```

A larger seed dataset lets you test real behavior.

For example:

```text
1000 courses
```

Then you can test:

```text
?page=10
```

or cursor pagination.

---

# 28. Seed Data for Testing Indexes

The same applies to indexes.

With:

```text
20 users
```

almost every query is fast.

You won't learn much about:

```text
Seq Scan
Index Scan
Query planner
```

But with:

```text
1,000,000 lesson_progress records
```

you can meaningfully investigate query performance.

A seed script can therefore help with performance experiments.

---

# 29. Deterministic IDs

Sometimes it's useful to use predictable IDs in test/development data.

For example:

```text
course-backend
course-typescript
course-postgresql
```

instead of random UUIDs.

But don't force this everywhere.

A good approach is often:

```text
Production
→ generated UUIDs

Development seed
→ stable identifiers where useful
```

Stable identifiers can make tests and debugging easier.

---

# 30. `deleteMany()` and Resetting Seed Data

Another common development approach is:

```ts
await prisma.lessonProgress.deleteMany();
await prisma.enrollment.deleteMany();
await prisma.lesson.deleteMany();
await prisma.course.deleteMany();
await prisma.user.deleteMany();
```

Then recreate everything.

But remember foreign keys.

You generally need to delete child records before parent records:

```text
Progress
   ↓
Enrollment
   ↓
Lesson
   ↓
Course
   ↓
User
```

unless your database relationships intentionally use cascading deletes.

---

# 31. Don't Blindly Delete Production Data

This is worth emphasizing:

```ts
await prisma.user.deleteMany();
```

is extremely dangerous if executed against production.

A seed/reset script should be clearly designed for development/test environments.

You can add environment checks:

```ts
if (process.env.NODE_ENV === "production") {
  throw new Error("Seed script cannot run in production");
}
```

The exact environment strategy can vary, but the safety idea is important.

---

# 32. Seeding and Transactions

A seed script often performs many related operations.

You may use:

```ts
await prisma.$transaction(async (tx) => {
  // seed related data
});
```

This can ensure that a group of operations succeeds or fails together.

However, don't automatically put an enormous seed dataset into one massive transaction.

For large datasets, transaction size and memory/runtime considerations matter.

For a small development seed, a transaction can be perfectly reasonable.

---

# 33. `createMany`

If you need many independent records, Prisma provides:

```ts
await prisma.user.createMany({
  data: [
    {
      name: "Rahul",
      email: "rahul@example.com",
    },
    {
      name: "Aman",
      email: "aman@example.com",
    },
  ],
});
```

This can be more efficient than:

```ts
await prisma.user.create(...);
await prisma.user.create(...);
await prisma.user.create(...);
```

for bulk inserts.

But there are differences between `createMany` and individual `create` calls, especially around nested writes and returned records.

Use the right tool for the situation.

---

# 34. `createMany` and Relations

A beginner might try:

```ts
await prisma.lesson.createMany({
  data: [
    {
      title: "Lesson 1",
      course: {
        connect: {
          id: courseId,
        },
      },
    },
  ],
});
```

This isn't the same as normal nested `create`.

`createMany` has more limited relation capabilities.

For bulk data:

```text
createMany
→ efficient bulk insertion

create
→ richer nested relation operations
```

Remember that distinction.

# 35. Seed Script Example

Let's create a simple AI LMS seed.

```ts
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

async function main() {
  const instructor = await prisma.user.upsert({
    where: {
      email: "instructor@example.com",
    },
    update: {},
    create: {
      name: "Demo Instructor",
      email: "instructor@example.com",
      passwordHash: "development-hash",
    },
  });

  const student = await prisma.user.upsert({
    where: {
      email: "student@example.com",
    },
    update: {},
    create: {
      name: "Demo Student",
      email: "student@example.com",
      passwordHash: "development-hash",
    },
  });

  const course = await prisma.course.create({
    data: {
      title: "Backend Engineering",
      description: "Learn backend development.",
      instructorId: instructor.id,
    },
  });

  await prisma.lesson.createMany({
    data: [
      {
        courseId: course.id,
        title: "PostgreSQL Basics",
        lessonOrder: 1,
      },
      {
        courseId: course.id,
        title: "Database Indexes",
        lessonOrder: 2,
      },
      {
        courseId: course.id,
        title: "Transactions",
        lessonOrder: 3,
      },
    ],
  });

  await prisma.enrollment.create({
    data: {
      userId: student.id,
      courseId: course.id,
    },
  });
}

main()
  .catch((error) => {
    console.error(error);
    process.exit(1);
  })
  .finally(async () => {
    await prisma.$disconnect();
  });
```

This demonstrates:

```text
User
 ↓
Course
 ↓
Lessons
 ↓
Enrollment
```

---

# 36. One Problem With That Example

Notice:

```ts
await prisma.course.create(...)
```

If you run the seed twice:

```text
Course 1
Course 2
Course 3
...
```

You'll create duplicates.

The users are protected by:

```text
email + upsert
```

but courses aren't.

So you need to decide:

```text
Should course data be recreated?
Should it be upserted?
Should the database be reset before seeding?
```

This is part of designing a good seed strategy.

---

# 37. Three Common Seed Strategies

## Strategy A — Reset then seed

```text
Reset database
      ↓
Seed from scratch
```

Best for:

```text
local development
throwaway environments
```

---

## Strategy B — Upsert known records

```text
Existing?
 ├── YES → update/preserve
 └── NO  → create
```

Best for:

```text
stable demo accounts
known development records
```

---

## Strategy C — Generate fresh test data

```text
Generate 1000 users
Generate 100 courses
Generate 10,000 enrollments
```

Best for:

```text
performance testing
load testing
pagination testing
```

Your project may use all three at different times.

---

# 38. Seeding and Migrations Are Different

This distinction is extremely important.

### Migration

Changes:

```text
database structure
```

For example:

```text
Create Course table
Add role column
Create index
```

### Seed

Adds:

```text
data
```

For example:

```text
Admin user
Demo course
Demo lessons
```

So:

```text
Migration
→ structure

Seed
→ data
```

# 42. Seed Edge Cases

Good seed data should include edge cases.

For example:

```text
Course with no lessons
Course with many lessons
Student with no enrollments
Student with many enrollments
Completed course
Partially completed course
Quiz with no attempts
Quiz with many attempts
```

Why?

Because applications often fail on:

```text
empty state
large state
unexpected state
```

not the happy path.

# 46. Seed vs Factory

You may eventually hear about **test factories**.

Seed:

```text
"Create the standard development database."
```

Factory:

```text
"Create whatever test data this particular test needs."
```

For example:

```ts
const user = await createUser();
const course = await createCourse({
  instructorId: user.id,
});
```

Factories are especially useful for automated tests.

For now:

```text
Seed
→ development environment

Factories
→ tests
```

is a useful mental model.

# 47. Common Seeding Mistakes

### Mistake 1

Using real production data.

```text
❌
```

Never casually copy real user data into local development.

---

### Mistake 2

Hard-coding production secrets.

```text
❌
```

---

### Mistake 3

Creating duplicates every run.

```text
seed
→ duplicates
→ duplicates
→ duplicates
```

---

### Mistake 4

Ignoring foreign-key order.

```text
Lesson before Course
```

can fail.

---

### Mistake 5

Making seed scripts destructive without protection.

```ts
deleteMany()
```

can be dangerous.

---

### Mistake 6

Only creating happy-path data.

You should also seed:

```text
empty
partial
complete
large
edge-case
```

scenarios.
