# 4. Entity #1 — User

Everything starts with the user.

A user could be:

```text
Admin
Instructor
Student
```

So:

```text
User
  │
  └── Role
```

A basic model:

```prisma
model User {
  id           String   @id @default(uuid())
  name         String
  email        String   @unique
  passwordHash String
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

But we need to decide how roles work.

---

# 5. Role Design

We have two common approaches.

### Approach A — Enum

```prisma
enum Role {
  ADMIN
  INSTRUCTOR
  STUDENT
}
```

Then:

```prisma
role Role @default(STUDENT)
```

Simple.

---

### Approach B — Role Table

```text
User
  ↓
Role
```

with:

```text
roles
-----
id
name
```

This is more flexible.

For our first AI LMS version, an enum is perfectly reasonable:

```prisma
enum Role {
  ADMIN
  INSTRUCTOR
  STUDENT
}
```

Later, if permissions become more complex, we can introduce:

```text
Role
Permission
RolePermission
```

---

# 6. User Model

So our initial user model becomes:

```prisma
enum Role {
  ADMIN
  INSTRUCTOR
  STUDENT
}

model User {
  id           String   @id @default(uuid())
  name         String
  email        String   @unique
  passwordHash String
  role         Role     @default(STUDENT)
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

Notice:

```text
email
  ↓
UNIQUE

role
  ↓
DEFAULT STUDENT
```

We're already applying lessons 3.9 and 3.5.

# 7. Entity #2 — Course

An instructor creates courses.

So:

```text
User
 │
 │ instructor
 ↓
Course
```

A course needs:

```text
id
title
description
instructorId
status
createdAt
updatedAt
```

We might have:

```prisma
enum CourseStatus {
  DRAFT
  PUBLISHED
  ARCHIVED
}
```

Then:

```prisma
model Course {
  id           String       @id @default(uuid())
  title        String
  description  String?
  instructorId String
  status       CourseStatus @default(DRAFT)
  createdAt    DateTime     @default(now())
  updatedAt    DateTime     @updatedAt

  instructor User @relation(
    fields: [instructorId],
    references: [id]
  )

  @@index([instructorId])
  @@index([status])
}
```

---

# 8. Why `instructorId` Needs an Index

We'll frequently ask:

```text
"Show me all courses created by this instructor."
```

SQL conceptually:

```sql
SELECT *
FROM courses
WHERE instructor_id = ?;
```

Therefore:

```prisma
@@index([instructorId])
```

is a sensible candidate.

This connects directly to:

```text
Lesson 3.7 — Indexes
Lesson 3.10 — Query Optimization
```

# 9. Entity #3 — Module

A course can contain modules.

Think:

```text
Course
 │
 ├── Module 1
 ├── Module 2
 └── Module 3
```

For example:

```text
Course: Backend Engineering

Module 1 → HTTP
Module 2 → Express
Module 3 → PostgreSQL
Module 4 → Authentication
```

So:

```prisma
model Module {
  id         String   @id @default(uuid())
  courseId   String
  title      String
  moduleOrder Int
  createdAt  DateTime @default(now())

  course Course @relation(
    fields: [courseId],
    references: [id]
  )

  @@index([courseId, moduleOrder])
}
```

---

# 10. Why `courseId + moduleOrder`?

We frequently need:

```text
Get modules for course
ordered by module number
```

So:

```sql
WHERE course_id = ?
ORDER BY module_order;
```

A composite index:

```prisma
@@index([courseId, moduleOrder])
```

can align well with this access pattern.

This is a practical example of query-driven indexing.

# 11. Entity #4 — Lesson

Now:

```text
Course
   ↓
Module
   ↓
Lesson
```

A lesson belongs to a module.

```prisma
model Lesson {
  id          String   @id @default(uuid())
  moduleId    String
  title       String
  content     String?
  lessonOrder Int
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  module Module @relation(
    fields: [moduleId],
    references: [id]
  )

  @@index([moduleId, lessonOrder])
}
```

Now the hierarchy is:

```text
Course
  │
  ├── Module
  │     ├── Lesson
  │     ├── Lesson
  │     └── Lesson
  │
  └── Module
        ├── Lesson
        └── Lesson
```

This is much better than putting every lesson directly under the course if your LMS needs modules.

---

# 12. Why Module Is Valuable

You might ask:

> Why not simply have Course → Lesson?

We could.

But modules provide:

```text
organization
navigation
progress grouping
analytics
curriculum structure
```

For example:

```text
Course
│
├── Module 1 — PostgreSQL
│   ├── Introduction
│   ├── Tables
│   └── Relationships
│
├── Module 2 — Prisma
│   ├── Schema
│   ├── Migrations
│   └── Transactions
│
└── Module 3 — Optimization
    ├── Indexes
    └── Query Plans
```

This is much closer to a real LMS.

# 13. Entity #5 — Enrollment

Now students can enroll in courses.

This creates a many-to-many relationship:

```text
User
 │
 ├── Enrollment ── Course
 │
 └── Enrollment ── Course
```

A student can enroll in many courses.

A course can have many students.

Therefore:

```text
User ←→ Course
```

requires a junction table:

```text
Enrollment
```

---

# 14. Enrollment Model

```prisma
enum EnrollmentStatus {
  ACTIVE
  COMPLETED
  CANCELLED
}

model Enrollment {
  userId     String
  courseId   String
  status     EnrollmentStatus @default(ACTIVE)
  enrolledAt DateTime         @default(now())

  user User @relation(
    fields: [userId],
    references: [id]
  )

  course Course @relation(
    fields: [courseId],
    references: [id]
  )

  @@id([userId, courseId])
  @@index([courseId])
}
```

The important part:

```prisma
@@id([userId, courseId])
```

This prevents:

```text
Student 1 + Course 1
Student 1 + Course 1
```

from being inserted twice.

# 15. Entity #6 — Lesson Progress

We need to know:

> How far has a student progressed through a lesson?

So:

```text
User
 │
 └── LessonProgress ── Lesson
```

Model:

```prisma
model LessonProgress {
  userId      String
  lessonId    String
  progress    Int      @default(0)
  completedAt DateTime?

  user User @relation(
    fields: [userId],
    references: [id]
  )

  lesson Lesson @relation(
    fields: [lessonId],
    references: [id]
  )

  @@id([userId, lessonId])
  @@index([lessonId])
}
```

Again:

```text
userId + lessonId
```

uniquely identifies one student's progress for one lesson.

---

# 16. Progress Constraint

We previously said:

```text
0 ≤ progress ≤ 100
```

Prisma schema alone may not fully express this PostgreSQL `CHECK` constraint depending on your Prisma version/setup.

So we'd add it through a migration:

```sql
ALTER TABLE lesson_progress
ADD CONSTRAINT lesson_progress_range
CHECK (progress >= 0 AND progress <= 100);
```

Now the database itself protects the rule.

# 17. Entity #7 — Quiz

A lesson may have a quiz.

```text
Lesson
  ↓
Quiz
```

For example:

```prisma
model Quiz {
  id        String   @id @default(uuid())
  lessonId  String   @unique
  title     String
  createdAt DateTime @default(now())

  lesson    Lesson   @relation(
    fields: [lessonId],
    references: [id]
  )

  questions QuizQuestion[]
}
```

Why:

```prisma
lessonId @unique
```

?

Because we're choosing the rule:

> One lesson has at most one quiz.

If later you decide a lesson can contain multiple quizzes, we'd change this relationship.

This is an important example of how **business requirements drive schema design**.

---

# 18. Entity #8 — Quiz Questions

A quiz contains questions.

```text
Quiz
 │
 ├── Question
 ├── Question
 └── Question
```

Model:

```prisma
model QuizQuestion {
  id        String   @id @default(uuid())
  quizId    String
  question  String
  options   Json
  answer    String
  points    Int      @default(1)
  order     Int

  quiz Quiz @relation(
    fields: [quizId],
    references: [id]
  )

  @@index([quizId, order])
}
```

---

# 19. Why `Json` for Options?

A multiple-choice question might have:

```json
[
  "MongoDB",
  "PostgreSQL",
  "Redis",
  "MySQL"
]
```

You could create another table:

```text
QuestionOption
```

which is more relational.

Or for a simple LMS:

```text
options JSONB
```

can be reasonable.

This is an architectural choice.

Don't automatically think:

> "Everything must be a separate table."

The right choice depends on:

```text
query patterns
data complexity
constraints
relationships
future requirements
```

# 20. Entity #9 — Quiz Attempt

A student can attempt a quiz multiple times.

So:

```text
User
 │
 └── QuizAttempt
          │
          └── Quiz
```

Model:

```prisma
model QuizAttempt {
  id          String   @id @default(uuid())
  userId      String
  quizId      String
  score       Int
  maxScore    Int
  startedAt   DateTime @default(now())
  completedAt DateTime?

  user User @relation(
    fields: [userId],
    references: [id]
  )

  quiz Quiz @relation(
    fields: [quizId],
    references: [id]
  )

  answers QuizAnswer[]

  @@index([userId, quizId])
}
```

Notice:

```text
userId + quizId
```

is **not unique**.

Why?

Because:

```text
Student
  ↓
Quiz
  ↓
Attempt 1
Attempt 2
Attempt 3
```

is allowed.

This is a good example of choosing constraints based on business rules.

---

# 21. Entity #10 — Quiz Answer

Each attempt contains answers.

```text
QuizAttempt
    ↓
QuizAnswer
```

Example:

```prisma
model QuizAnswer {
  id         String @id @default(uuid())
  attemptId  String
  questionId String
  answer     String
  isCorrect  Boolean

  attempt QuizAttempt @relation(
    fields: [attemptId],
    references: [id]
  )

  question QuizQuestion @relation(
    fields: [questionId],
    references: [id]
  )

  @@index([attemptId])
}
```

Potentially:

```prisma
@@unique([attemptId, questionId])
```

if each attempt can contain only one answer per question.

That is another business rule.

# 22. Entity #11 — AI Conversation

Now we reach the interesting part.

Our LMS has AI.

A student might ask:

```text
"Explain PostgreSQL indexes."
```

We need to store the conversation.

So:

```text
User
 │
 └── AIConversation
```

Potentially the conversation can also be associated with:

```text
Course
Module
Lesson
```

Why?

Because an AI tutor may be operating in the context of a lesson.

---

# 23. AI Conversation Model

```prisma
model AIConversation {
  id        String   @id @default(uuid())
  userId    String
  courseId  String?
  lessonId  String?
  title     String?
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  user User @relation(
    fields: [userId],
    references: [id]
  )

  course Course? @relation(
    fields: [courseId],
    references: [id]
  )

  lesson Lesson? @relation(
    fields: [lessonId],
    references: [id]
  )

  messages AIMessage[]

  @@index([userId, updatedAt])
  @@index([lessonId])
}
```

Now we can support:

```text
General AI chat
```

where:

```text
courseId = NULL
lessonId = NULL
```

or:

```text
Lesson-specific AI tutor
```

where:

```text
courseId = ...
lessonId = ...
```

---

# 24. Why Are `courseId` and `lessonId` Nullable?

Because not every AI conversation needs a course.

For example:

```text
User:
"Explain recursion."
```

could be a general conversation.

But:

```text
User:
"Explain this lesson's example."
```

could be tied to:

```text
Course → Module → Lesson
```

So:

```text
courseId String?
lessonId String?
```

gives flexibility.

---

# 25. Entity #12 — AI Message

A conversation contains messages.

```text
AIConversation
      ↓
AIMessage
      ↓
User / Assistant / System
```

We might use:

```prisma
enum AIMessageRole {
  SYSTEM
  USER
  ASSISTANT
  TOOL
}
```

Then:

```prisma
model AIMessage {
  id             String        @id @default(uuid())
  conversationId String
  role           AIMessageRole
  content        String
  createdAt      DateTime      @default(now())

  conversation AIConversation @relation(
    fields: [conversationId],
    references: [id]
  )

  @@index([conversationId, createdAt])
}
```

This index is important because we'll frequently query:

```text
Give me messages for this conversation
ordered by time.
```

---

# 26. Why Store Messages Separately?

Don't store an entire conversation in one giant JSON column.

Bad approach:

```text
AIConversation
└── messages JSON
```

For a simple prototype, this can work.

But for a real LMS:

```text
AIConversation
      ↓
AIMessage
      ↓
many messages
```

is usually much easier to query and manage.

We can ask:

```text
Give me latest 20 messages.
```

or:

```text
Count messages.
```

or:

```text
Delete old messages.
```

much more easily.


```prisma
model AIUsage {

```

This becomes very useful for:


# 28. Entity #14 — Activity

An LMS often needs an activity/audit trail.

Examples:

```text
USER_REGISTERED
COURSE_ENROLLED
LESSON_COMPLETED
QUIZ_COMPLETED
COURSE_COMPLETED
AI_CHAT_STARTED
```

We can create:

```prisma
enum ActivityType {
  USER_REGISTERED
  COURSE_ENROLLED
  LESSON_COMPLETED
  QUIZ_COMPLETED
  COURSE_COMPLETED
  AI_CHAT_STARTED
}

model Activity {
  id        String       @id @default(uuid())
  userId    String
  type      ActivityType
  metadata  Json?
  createdAt DateTime     @default(now())

  user User @relation(
    fields: [userId],
    references: [id]
  )

  @@index([userId, createdAt])
  @@index([type, createdAt])
}
```

# 29. Why Use JSON for Activity Metadata?

Suppose:

```text
LESSON_COMPLETED
```

needs:

```json
{
  "lessonId": "...",
  "courseId": "..."
}
```

while:

```text
QUIZ_COMPLETED
```

needs:

```json
{
  "quizId": "...",
  "score": 90
}
```

Instead of creating many activity-specific tables, we can store flexible metadata.

This is one of the places where JSON can be useful.

But don't use JSON for everything.

# 37. Quiz Architecture

```prisma
model Quiz {
  id        String   @id @default(uuid())
```

# 43. Normalization

Our design follows relational normalization principles.

For example, don't store:

```text
course.students = [
  "Rahul",
  "Aman",
  "Priya"
]
```

inside the course row.

Instead:

```text
Course
   ↑
Enrollment
   ↓
User
```

Why?

Because we can then efficiently ask:

```text
Which courses is Rahul enrolled in?

Who is enrolled in this course?

When did Rahul enroll?

Is Rahul's enrollment completed?
```

This is one of the biggest benefits of relational databases.

---

# 44. Don't Over-Normalize

However, don't go too far.

For example, you don't necessarily need:

```text
CourseTitle
CourseDescription
CourseStatus
CourseMetadata
```

as separate tables.

Normalization is not:

> "Make as many tables as possible."

It's:

> **Store data in a structure that reduces unnecessary duplication while keeping relationships and queries practical.**

# 51. Course Completion

```text

 ├── 10 lessons
 ├── Student completed 8
 └── Progress = 80%
```

### Calculated dynamically?

```text
completed lessons / total lessons
```

### Stored?

```text
CourseEnrollment.progress = 80
```

Both are possible.

---

# 52. Calculated vs Stored Data

### Calculate

Advantages:

```text
always derived from source
no duplication
```

Disadvantages:

```text
potentially expensive queries
```

### Store

Advantages:

```text
fast reads
easy dashboard queries
```

Disadvantages:

```text
must keep it synchronized
```

For a simple LMS, I'd initially calculate some derived values.

As your application grows, you can introduce carefully maintained denormalized fields where measurements show they are useful.

---

# 53. Don't Store Everything Just Because It's Fast

For example:

```text
course.progress = 80
```

can become wrong if:

```text
LessonProgress
```

changes but:

```text
course.progress
```

isn't updated.

Now you have:

```text
Source of truth → 70%
Cached value    → 80%
```

That's a consistency bug.

So ask:

> **What is the source of truth?**

This question is extremely important in database architecture.

---

# 54. Source of Truth

For lesson progress:

```text
LessonProgress
```

could be the source of truth.

Then:

```text
Course progress
```

can be derived.

For AI usage:

```text
AIUsage
```

could be the source of truth for token usage.

For enrollment:

```text
Enrollment
```

is the source of truth.

Good architecture clearly defines these.

# 55. Soft Delete

Now another architectural decision.

Suppose an instructor deletes a course.

Should we physically remove:

```text
Course
Lessons
Quizzes
Attempts
Progress
AI conversations
```

?

Maybe not.

We could use:

```text
deletedAt DateTime?
```

Example:

```prisma
deletedAt DateTime?
```

Then:

```text
NULL
→ active

timestamp
→ deleted
```

This is called **soft deletion**.

---

# 56. Do We Need Soft Delete Everywhere?

No.

Don't automatically add:

```text
deletedAt
```

to every model.

For example:

```text
AIMessage
```

may have different retention requirements.

For:

```text
audit/activity
```

you may want append-only behavior rather than deletion.

Database architecture should reflect actual requirements.

# 58. UUIDs

For our AI LMS, UUIDs are a good default for primary identifiers:

```prisma

```

Benefits include:


Authorization must still be enforced.

For example:



A UUID alone doesn't provide authorization.

# 66. The Three Questions You Should Ask for Every Table

Whenever you create a new model, ask:

### 1. What does this entity represent?

```text
Course
→ educational course
```

### 2. What are its invariants?

```text
title → required
instructor → must exist
status → valid enum
```

### 3. How will the application query it?

```text
courses by instructor
courses by status
recent courses
```

Then decide:

```text
relationships
constraints
indexes
```

This process will make you much better at database design.

---

# 67. The Four Questions for Every Relationship

Ask:

```text
1. One-to-one?
2. One-to-many?
3. Many-to-many?
4. Optional or required?
```

Examples:

```text
User → Course
one instructor → many courses

Course → Module
one course → many modules

Module → Lesson
one module → many lessons

User ↔ Course
many-to-many → Enrollment

Lesson → Quiz
one-to-zero/one
```

This prevents many schema mistakes.

---

# 68. The Five Questions for Every Index

Before adding an index:

```text
1. What query needs it?
2. How frequently does that query run?
3. How selective is the filter?
4. Does column order match the query?
5. Did EXPLAIN ANALYZE show a benefit?
```

This is much better than:

```text
"Let's index everything."
```

---

# 69. The Transaction Question

For every multi-step operation ask:

> **If step 3 fails, should steps 1 and 2 remain?**

If the answer is:

```text
NO
```

you probably need a transaction.

Example:

```text
Create quiz attempt
Create answers
Update progress
```

If progress update fails, should the attempt remain?

If:

```text
NO
```

use a transaction.

---

# 70. The Constraint Question

Ask:

> **Can PostgreSQL enforce this invariant?**

If yes, strongly consider doing it.

Examples:

```text
Email unique
→ UNIQUE

Enrollment unique
→ composite PRIMARY KEY

Course must exist
→ FOREIGN KEY

Progress 0–100
→ CHECK

Name required
→ NOT NULL
```

This makes your database resilient.

# 71. Your AI LMS Database Philosophy

I recommend you follow these principles throughout the project:

```text
1. Model the domain clearly.

2. Keep data normalized initially.

3. Use foreign keys.

4. Use constraints for important invariants.

5. Add indexes based on query patterns.

6. Use transactions for atomic business operations.

7. Measure query performance before optimizing.

8. Keep seed data realistic.

9. Define clear sources of truth.

10. Avoid premature complexity.

11. Let migrations evolve the schema.

12. Treat security as a cross-cutting concern.
```

That last one is especially important.
