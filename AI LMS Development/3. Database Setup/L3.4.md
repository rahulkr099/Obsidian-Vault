# Lesson 3.4 — Database Relationships

This is one of the **most important lessons in database design**.

You already know:

```text
Primary Key → identifies a row
Foreign Key → connects rows
```

Now we'll answer:

> **What kind of connection exists between two entities?**

There are three fundamental relationship types:

```text
1 : 1    One-to-One
1 : N    One-to-Many
N : M    Many-to-Many
```

We'll use the **AI LMS** throughout this lesson.

---

# 1. What Is a Relationship?

Suppose we have:

```text
User
Course
```

We need to ask:

> How many courses can one user have?

Maybe:

```text
Rahul → React
Rahul → Node.js
Rahul → PostgreSQL
```

One user can have many courses.

But perhaps:

> How many users can be enrolled in one course?

```text
React Course
├── Rahul
├── Aman
├── Priya
└── Ravi
```

One course can also have many users.

So:

```text
User ↔ Course
```

is:

```text
Many-to-Many
```

Understanding this relationship correctly is the heart of relational database design.

---

# 2. One-to-One — 1:1

A one-to-one relationship means:

> One record in table A is associated with at most one record in table B, and vice versa.

Example:

```text
User → UserProfile
```

Imagine:

```text
User
└── Profile
```

Each user has one profile.

And each profile belongs to one user.

So:

```text
User 1 ───── 1 Profile
```

---

# 3. Example: User and Profile

Suppose:

```text
users

id | name
---|------
1  | Rahul
2  | Aman
```

And:

```text
profiles

id | user_id | bio
---|---------|----------------
1  | 1       | Backend learner
2  | 2       | Frontend learner
```

Relationship:

```text
users.id
   ↑
   │
profiles.user_id
```

Each profile belongs to one user.

---

# 4. How Do We Enforce 1:1?

Here's the interesting part.

A foreign key alone doesn't guarantee one-to-one.

Suppose:

```text
profiles

id | user_id
---|--------
1  | 1
2  | 1
3  | 1
```

Now user `1` has three profiles.

That's:

```text
User 1 → Many Profiles
```

Not 1:1.

We need a `UNIQUE` constraint:

```sql
CREATE TABLE profiles (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL UNIQUE,
    bio TEXT,

    FOREIGN KEY (user_id)
        REFERENCES users(id)
);
```

The important part:

```sql
user_id UUID NOT NULL UNIQUE
```

Now:

```text
user_id = 1
```

can appear only once.

Therefore:

```text
User 1 ─── Profile 1
```

is guaranteed.

---

# 5. Prisma 1:1 Relationship

The equivalent Prisma model could look like:

```prisma
model User {
  id      String  @id @default(uuid())
  name    String
  profile Profile?
}

model Profile {
  id     String @id @default(uuid())
  userId String @unique
  bio    String?

  user User @relation(fields: [userId], references: [id])
}
```

Notice:

```prisma
userId String @unique
```

That `@unique` is what helps enforce the one-to-one relationship.

---

# 6. When Should You Use 1:1?

Don't create one-to-one tables just because you can.

A separate table makes sense when the data has a different purpose or lifecycle.

For example:

```text
User
├── authentication data
│
└── Profile
    ├── bio
    ├── avatar
    └── website
```

Maybe your `users` table is focused on authentication:

```text
users
├── id
├── email
├── password_hash
└── created_at
```

while:

```text
profiles
├── id
├── user_id
├── bio
├── avatar_url
└── website
```

contains profile information.

This separation can be useful.

---

# 7. One-to-Many — 1:N

This is probably the **most common relationship** you'll use.

It means:

> One record can be associated with many records.

But each child record belongs to one parent.

For example:

```text
Course → Lessons
```

One course has many lessons.

But one lesson belongs to one course.

Therefore:

```text
Course 1 ───── N Lessons
```

---

# 8. AI LMS Example

Imagine:

```text
React Mastery
│
├── Introduction
├── Components
├── Props
├── State
├── Hooks
└── Context
```

One course:

```text
React Mastery
```

has many lessons.

But:

```text
Hooks
```

belongs to exactly one course.

So:

```text
Course
   │
   ├── Lesson
   ├── Lesson
   ├── Lesson
   └── Lesson
```

is:

```text
1 : N
```

---

# 9. Where Does the Foreign Key Go?

This is a **very important rule**:

> In a one-to-many relationship, the foreign key normally goes on the **many side**.

We have:

```text
Course 1 ───── N Lesson
```

Therefore:

```text
lessons.course_id
```

contains the foreign key.

Not:

```text
courses.lesson_id
```

Why?

Because one course can have many lessons.

A single `course_id` can appear in many lesson rows:

```text
lessons

id | course_id | title
---|-----------|-------------
1  | 100       | Introduction
2  | 100       | Components
3  | 100       | Props
4  | 100       | State
```

That's perfectly natural.

---

# 10. PostgreSQL Example

```sql
CREATE TABLE courses (
    id UUID PRIMARY KEY,
    title TEXT NOT NULL
);

CREATE TABLE lessons (
    id UUID PRIMARY KEY,
    course_id UUID NOT NULL,
    title TEXT NOT NULL,

    FOREIGN KEY (course_id)
        REFERENCES courses(id)
);
```

Now:

```text
courses.id
    ↑
    │
    │ referenced by
    │
lessons.course_id
```

---

# 11. Prisma 1:N

```prisma
model Course {
  id      String   @id @default(uuid())
  title   String
  lessons Lesson[]
}

model Lesson {
  id       String @id @default(uuid())
  title    String
  courseId String

  course Course @relation(
    fields: [courseId],
    references: [id]
  )
}
```

Here:

```prisma
lessons.courseId
```

is the foreign key.

And:

```prisma
lessons Lesson[]
```

means:

> A course can have many lessons.

---

# 12. Another AI LMS Example

Consider:

```text
Instructor → Courses
```

One instructor can create many courses.

But each course has one instructor.

Therefore:

```text
Instructor 1 ───── N Courses
```

The foreign key goes here:

```text
courses.instructor_id
```

So:

```text
users
  │
  │ id
  ↓
courses
  └── instructor_id
```

---

# 13. Many-to-Many — N:M

Now we reach the most interesting relationship.

Suppose:

```text
User ↔ Course
```

A student can enroll in many courses:

```text
Rahul
├── React
├── Node
└── PostgreSQL
```

And a course can have many students:

```text
React
├── Rahul
├── Aman
├── Priya
└── Ravi
```

Therefore:

```text
User N ───── M Course
```

This is **many-to-many**.

---

# 14. Why Can't We Just Put a Foreign Key in `users`?

A beginner might try:

```text
users

id | name | course_id
```

But Rahul could have:

```text
React
Node
PostgreSQL
```

How do we store multiple course IDs?

Maybe:

```text
course_id = "1,2,3"
```

Bad idea.

We've already seen why comma-separated relationships are problematic.

Instead, we introduce a **junction table**.

---

# 15. Junction Table

Create:

```text
enrollments
```

It connects:

```text
users
```

and:

```text
courses
```

Structure:

```text
users
   │
   │
   ↓
enrollments
   ↑
   │
   │
courses
```

The table might contain:

```text
enrollments

user_id | course_id
--------|----------
1       | 10
1       | 11
1       | 12
2       | 10
3       | 10
```

Now everything works.

---

# 16. Understanding the Junction Table

Look at:

```text
user_id | course_id
--------|----------
1       | 10
```

It means:

> User 1 is enrolled in Course 10.

Then:

```text
1 | 11
```

means:

> User 1 is enrolled in Course 11.

And:

```text
2 | 10
```

means:

> User 2 is enrolled in Course 10.

So the junction table represents the **relationship itself**.

This is an important idea.

---

# 17. The Junction Table Often Contains More Information

This is where many-to-many becomes even more useful.

Suppose enrollment needs:

```text
enrolledAt
completedAt
status
```

Then:

```text
enrollments

id
user_id
course_id
enrolled_at
completed_at
status
```

Now the relationship has its own data.

For example:

```text
Rahul
   ↓
Enrollment
   ├── course = React
   ├── status = active
   ├── enrolledAt = ...
   └── completedAt = NULL
```

This is why we don't just think:

```text
User ↔ Course
```

We think:

```text
User → Enrollment ← Course
```

---

# 18. PostgreSQL Many-to-Many

A clean implementation:

```sql
CREATE TABLE enrollments (
    user_id UUID NOT NULL,
    course_id UUID NOT NULL,
    enrolled_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    PRIMARY KEY (user_id, course_id),

    FOREIGN KEY (user_id)
        REFERENCES users(id),

    FOREIGN KEY (course_id)
        REFERENCES courses(id)
);
```

The composite primary key:

```sql
PRIMARY KEY (user_id, course_id)
```

prevents:

```text
Rahul → React
Rahul → React
```

from being inserted twice.

---

# 19. Prisma Many-to-Many

You can model it explicitly:

```prisma
model User {
  id          String       @id @default(uuid())
  name        String
  enrollments Enrollment[]
}

model Course {
  id          String       @id @default(uuid())
  title       String
  enrollments Enrollment[]
}

model Enrollment {
  userId     String
  courseId   String
  enrolledAt DateTime      @default(now())

  user   User   @relation(fields: [userId], references: [id])
  course Course @relation(fields: [courseId], references: [id])

  @@id([userId, courseId])
}
```

This is called an **explicit many-to-many relationship**.

For your AI LMS, explicit junction tables are often preferable because relationships such as enrollment usually have their own fields.

---

# 20. Implicit vs Explicit Many-to-Many in Prisma

Prisma can also create a many-to-many relationship more directly.

Conceptually:

```prisma
model User {
  id      String   @id @default(uuid())
  courses Course[]
}

model Course {
  id    String @id @default(uuid())
  users User[]
}
```

Prisma can manage the underlying relation table.

But here's the problem.

What if you need:

```text
enrolledAt
status
completedAt
```

You can't treat the relationship as just:

```text
User ↔ Course
```

anymore.

You need:

```text
Enrollment
```

So for an LMS:

```text
User
 ↓
Enrollment
 ↓
Course
```

is usually the better mental model.

---

# 21. AI LMS Relationship Map

Let's model the core LMS.

### User → Courses

Through enrollment:

```text
User N ─── M Course
          ↓
      Enrollment
```

### Course → Lessons

```text
Course 1 ─── N Lesson
```

### User → Lesson Progress

```text
User N ─── M Lesson
          ↓
    LessonProgress
```

Why many-to-many?

Because:

```text
One user → many lessons
```

and:

```text
One lesson → many users
```

The relationship is:

```text
User
  ↓
LessonProgress
  ↑
Lesson
```

# 22. Lesson Progress Example

Suppose:

```text
User 1
```

has completed:

```text
Lesson 10
Lesson 11
Lesson 15
```

We could have:

```text
lesson_progress

user_id | lesson_id | completed
--------|-----------|----------
1       | 10        | true
1       | 11        | true
1       | 15        | true
```

But there's more.

We might want:

```text
started_at
completed_at
progress_percentage
last_position
```

So:

```text
lesson_progress
├── user_id
├── lesson_id
├── progress_percent
├── started_at
├── completed_at
└── last_position
```

This is a relationship with **important business data**.

# 23. Quiz Relationships

Now consider:

```text
Course → Quiz
```

A course could have multiple quizzes.

```text
Course 1 ─── N Quiz
```

Then:

```text
Quiz → Question
```

One quiz contains many questions:

```text
Quiz 1 ─── N Question
```

And:

```text
User → QuizAttempt
```

A user can make many attempts:

```text
User 1 ─── N QuizAttempt
```

So our LMS starts looking like:

```text
User
 │
 ├──── Enrollment ───── Course
 │                         │
 │                         ├──── Lesson

 │                                └──── Question

 ├──── LessonProgress ─── Lesson
 │

```

This is the kind of thinking we want.

# 24. Relationship Cardinality

You'll often hear the word **cardinality**.

It basically describes:

> How many records can be associated with how many other records?

Examples:

```text
1:1
```

means:

```text
One ↔ One
```

```text
1:N
```

means:

```text
One ↔ Many
```

```text
N:M
```

means:

```text
Many ↔ Many
```

When designing databases, you should be comfortable saying:

> "Course and Lesson have a one-to-many relationship."

That's database-engineering language.

---

# 25. Optional Relationships

Not every relationship is mandatory.

Consider:

```text
User → Profile
```

Maybe a user can register without completing their profile.

Then:

```text
User 1 ─── 0..1 Profile
```

The `0..1` means:

> zero or one.

In Prisma:

```prisma
profile Profile?
```

The `?` indicates the relationship is optional.

---

# 26. Required Relationships

Now consider:

```text
Lesson → Course
```

A lesson probably cannot exist without a course.

So:

```text
Lesson 1 ─── 1 Course
```

from the lesson's perspective.

The foreign key should therefore be required:

```prisma
courseId String
```

rather than:

```prisma
courseId String?
```

So:

```text
Optional relationship
→ nullable foreign key

Required relationship
→ non-null foreign key
```

This is a very useful rule.

---

# 27. Don't Confuse Relationship Direction

Suppose:

```text
Course 1 ─── N Lesson
```

This doesn't mean:

```text
Course has a lesson_id
```

It means:

```text
Lesson has course_id
```

Remember:

> **The foreign key normally lives on the many side.**

So:

```text
Course
   │
   │ 1
   ↓
Lesson
   ↑
   │ N
```

Database:

```text
lessons.course_id
```

# 28. A Real-World Design Exercise

Requirement:

> An instructor can create multiple courses. Each course contains multiple lessons. Students can enroll in multiple courses. Students can track their progress through lessons.

Let's derive it.

### Step 1 — Entities

```text
User
Course
Lesson
Enrollment
LessonProgress
```

### Step 2 — Relationships

Instructor:

```text
User 1 ─── N Course
```

Student enrollment:

```text
User N ─── M Course
```

Course lessons:

```text
Course 1 ─── N Lesson
```

Lesson progress:

```text
User N ─── M Lesson
```

### Step 3 — Junction tables

Many-to-many relationships require:

```text
Enrollment
LessonProgress
```

So:

```text
User
 ├── Course
 │     └── Lesson
 │
 ├── Enrollment ───── Course
 │
 └── LessonProgress ─ Lesson
```

That's a proper relational model.

---

# 29. The Important Insight

Here's something you'll encounter constantly in real applications:

> **A many-to-many relationship often becomes an entity of its own.**

For example:

```text
User ↔ Course
```

becomes:

```text
User → Enrollment ← Course
```

because enrollment has information:

```text
status
enrolledAt
completedAt
```

Similarly:

```text
User ↔ Lesson
```

becomes:

```text
User → LessonProgress ← Lesson
```

because progress has:

```text
percentage
startedAt
completedAt
lastPosition
```

This is a very powerful database-design pattern.

---

# 30. Quick Decision Framework

When you see two entities, ask:

### Question 1

Can one A have many B?

### Question 2

Can one B have many A?

Then:

```text
A one + B one
→ 1:1

A one + B many
→ 1:N

A many + B many
→ N:M
```

Then ask:

> Does the relationship itself have data?

If yes, create a separate entity/table.

# 32. The Golden Rules

Remember these five rules:

### Rule 1

**1:1**

Use a foreign key plus `UNIQUE`.

```text
user_id UNIQUE
```

### Rule 2

**1:N**

Put the foreign key on the **many side**.

```text
lessons.course_id
```

### Rule 3

**N:M**

Use a junction table.

```text
enrollments
```

### Rule 4

If the relationship has its own attributes, make it an explicit entity.

```text
Enrollment
LessonProgress
```

### Rule 5

Always model relationships according to **business rules**, not according to what happens to be convenient in Prisma.
