# Lesson 3.5 — Prisma Schema

Now we reach the part where **Prisma connects your application code with PostgreSQL**.

You've already learned:

```text
3.1 → How to think relationally
3.2 → How to design PostgreSQL tables
3.3 → Primary & foreign keys
3.4 → Relationships
```

Now we'll express those ideas using **Prisma Schema Language**.

The important mindset is:

> **Prisma is not replacing database knowledge. Prisma is a tool that lets your application work with the database more comfortably.**

---

# 1. What Is Prisma?

Prisma is an ORM/toolkit for working with databases.

Your application might be written in:

```text
TypeScript / JavaScript
```

Your database speaks:

```text
PostgreSQL / SQL
```

Prisma sits between them:

```text
┌──────────────────────┐
│ TypeScript           │
│ Express / Next.js    │
└──────────┬───────────┘
           │
           ↓
┌──────────────────────┐
│ Prisma Client        │
└──────────┬───────────┘
           │
           ↓
┌──────────────────────┐
│ PostgreSQL            │
└──────────────────────┘
```

For example, instead of manually writing:

```sql
SELECT * FROM users WHERE id = ...;
```

you can use Prisma Client:

```ts
const user = await prisma.user.findUnique({
  where: {
    id: userId,
  },
});
```

But remember:

> You should understand the SQL that Prisma is conceptually producing.

That's why we learned PostgreSQL first.

# 3. Basic Prisma Schema

A basic schema contains three important blocks:

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
}

model User {
  id   String @id
  name String
}
```

Think:

```text
generator
   ↓
How Prisma Client is generated

datasource
   ↓
Which database we're using

model
   ↓
Database table
```

---

# 4. `datasource`

For PostgreSQL:

```prisma
datasource db {
  provider = "postgresql"
}
```

This tells Prisma:

> My database is PostgreSQL.

The actual connection URL is normally provided through an environment variable rather than hard-coded into your source code.

For example:

```env
DATABASE_URL="postgresql://..."
```

This is important because database credentials should not be committed to Git.

---

# 5. `generator`

You'll commonly see:

```prisma
generator client {
  provider = "prisma-client-js"
}
```

This tells Prisma to generate the Prisma Client that your TypeScript/JavaScript application will use.

Conceptually:

```text
schema.prisma
      ↓
Prisma
      ↓
Generated Prisma Client
      ↓
TypeScript application
```

# 6. `model`

A Prisma model generally represents a database table.

For example:

```prisma
model User {
  id    String
  name  String
  email String
}
```

Conceptually:

```text
Prisma model
      ↓
PostgreSQL table

User
      ↓
users
```

Depending on configuration, Prisma maps model/table naming accordingly.

# 9. `@id`

This is one of the most important Prisma attributes.

```prisma
id String @id
```

means:

> `id` is the primary key.

Equivalent PostgreSQL concept:

```sql
id TEXT PRIMARY KEY
```

For your applications, a common pattern is:

```prisma
id String @id @default(uuid())
```

Now Prisma/database generates a UUID by default.

Conceptually:

```text
User created
    ↓
No ID supplied
    ↓
UUID generated
    ↓
Stored as primary key
```

---

# 10. `@default`

`@default` defines a default value.

Example:

```prisma
createdAt DateTime @default(now())
```

When you create a user without specifying `createdAt`:

```ts
await prisma.user.create({
  data: {
    name: "Rahul",
  },
});
```

the database can automatically set:

```text
createdAt = current timestamp
```

Other examples:

```prisma
id        String  @default(uuid())
isActive  Boolean @default(true)
```

---

# 11. A Good User Model

Let's build one:

```prisma
model User {
  id           String   @id @default(uuid())
  name         String
  email        String   @unique
  passwordHash String
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

Let's understand each field.

### ID

```prisma
id String @id @default(uuid())
```

Primary key with UUID generation.

### Name

```prisma
name String
```

Required string.

### Email

```prisma
email String @unique
```

Email cannot be duplicated.

### Password

```prisma
passwordHash String
```

Stores the password hash.

### Created

```prisma
createdAt DateTime @default(now())
```

Automatically records creation time.

### Updated

```prisma
updatedAt DateTime @updatedAt
```

Prisma automatically updates this field when the record changes.

---

# 12. `@unique`

Suppose:

```prisma
email String @unique
```

This means:

```text
rahul@example.com
```

cannot appear twice.

So this:

```text
id | email
---|-------------------
1  | rahul@example.com
2  | aman@example.com
```

is valid.

But:

```text
id | email
---|-------------------
1  | rahul@example.com
2  | rahul@example.com
```

is rejected.

Remember:

```text
@id
→ primary key

@unique
→ unique constraint
```

---

# 13. Optional Fields

Suppose a user's bio isn't required.

Use:

```prisma
bio String?
```

The `?` means nullable/optional.

So:

```prisma
model Profile {
  id  String @id @default(uuid())
  bio String?
}
```

Both are valid:

```text
bio = "Backend developer"
```

and:

```text
bio = NULL
```

Compare:

```prisma
name String
```

versus:

```prisma
bio String?
```

The first is required.

The second is optional.

---

# 14. `@relation`

Now we get to the most important part.

Suppose:

```text
Course
   ↓
Lesson
```

A course has many lessons.

In Prisma:

```prisma
model Course {
  id      String   @id @default(uuid())
  title   String
  lessons Lesson[]
}

model Lesson {
  id       String @id @default(uuid())
  title    String
  courseId String

  course Course @relation(
    fields: [courseId],
    references: [id]
  )
}
```

This is worth understanding carefully.

---

# 15. Understanding `Lesson`

Look at:

```prisma
courseId String
```

This is the actual foreign-key field.

Then:

```prisma
course Course
```

is the Prisma relation field.

And:

```prisma
@relation(
  fields: [courseId],
  references: [id]
)
```

means:

```text
lesson.courseId
      ↓
course.id
```

So:

```text
id="7e0e7g"
courseId
   │
   │ references
   ↓
Course.id
```

---

# 16. `fields` vs `references`

This is one of the most important Prisma concepts.

```prisma
@relation(
  fields: [courseId],
  references: [id]
)
```

means:

```text
fields
   ↓
Which field in THIS model stores the FK?

references
   ↓
Which field in the OTHER model does it point to?
```

Therefore:

```prisma
fields: [courseId]
```

means:

```text
Lesson.courseId
```

and:

```prisma
references: [id]
```

means:

```text
Course.id
```

So:

```text
Lesson.courseId → Course.id
```

---

# 17. The Parent Side

Now look at:

```prisma
model Course {
  id      String   @id @default(uuid())
  title   String
  lessons Lesson[]
}
```

The:

```prisma
lessons Lesson[]
```

means:

> One course can have many lessons.

Notice that `lessons` isn't a database column like `courseId`.

It's a **Prisma relation field**.

That's a critical distinction.

---

# 18. Relation Fields vs Database Fields

Consider:

```prisma
model Lesson {
  id       String @id @default(uuid())
  title    String
  courseId String

  course Course @relation(fields: [courseId], references: [id])
}
```

There are:

```text
Database fields
────────────────
id
title
courseId
```

and:

```text
Prisma relation field
─────────────────────
course
```

`courseId` is physically stored.

`course` represents the relationship in Prisma.

This distinction will save you a lot of confusion later.

# 19. One-to-Many Complete Example

Here's the full model:

```prisma
model User {
  id      String   @id @default(uuid())
  name    String
  courses Course[]
}

model Course {
  id           String   @id @default(uuid())
  title        String
  instructorId String

  instructor User     @relation(fields: [instructorId], references: [id])
  lessons    Lesson[]
}

model Lesson {
  id       String @id @default(uuid())
  title    String
  courseId String

  course Course @relation(fields: [courseId], references: [id])
}
```

The relationship graph:

```text
User
 │
 │ 1
 │
 └──────── N
          Course
             │
             │ 1
             │
             └──────── N
                      Lesson
```

# 20. One-to-One in Prisma

Let's create:

```text
User → Profile
```

Prisma:

```prisma
model User {
  id      String   @id @default(uuid())
  name    String
  profile Profile?
}

model Profile {
  id     String @id @default(uuid())
  userId String @unique
  bio    String?

  user User @relation(fields: [userId], references: [id])
}
```

The important part:

```prisma
userId String @unique
```

Without `@unique`, multiple profiles could point to the same user.

With `@unique`:

```text
User 1 → Profile 1
```

is enforced.

---

# 21. Many-to-Many with an Explicit Model

For our LMS:

```text
User ↔ Course
```

we'll use:

```text
Enrollment
```

Prisma:

```prisma
model User {
  id          String       @id @default(uuid())
  name        String
  enrollments Enrollment[]
}

model Course {
  id          String       @id @default(uuid())
  title       String
  enrollments Enrollment[]
}

model Enrollment {
  userId     String
  courseId   String
  enrolledAt DateTime @default(now())

  user   User   @relation(fields: [userId], references: [id])
  course Course @relation(fields: [courseId], references: [id])

  @@id([userId, courseId])
}
```

The important part:

```prisma
@@id([userId, courseId])
```

This creates a composite primary key.

It means:

```text
(userId, courseId)
```

must be unique.

So:

```text
(1, 10) ✅
(1, 20) ✅
(2, 10) ✅
(1, 10) ❌
```

---

# 22. `@id` vs `@@id`

This difference is important.

### One field

```prisma
id String @id
```

Use:

```text
@id
```

### Multiple fields

```prisma
@@id([userId, courseId])
```

Use:

```text
@@id
```

So:

```text
@id
→ field-level primary key

@@id
→ model-level composite primary key
```

---

# 23. `@unique` vs `@@unique`

Same idea.

One field:

```prisma
email String @unique
```

Multiple fields:

```prisma
@@unique([userId, courseId])
```

For example:

```prisma
model Enrollment {
  id       String @id @default(uuid())
  userId   String
  courseId String

  @@unique([userId, courseId])
}
```

This means the combination must be unique.

---

# 24. Explicit vs Implicit Many-to-Many

Prisma can represent many-to-many relationships without you defining the junction model manually.

For example:

```prisma
model User {
  id      String   @id @default(uuid())
  courses Course[]
}

model Course {
  id    String @id @default(uuid())
  users User[]
}
```

Prisma can manage the underlying relationship table.

But for your AI LMS, I recommend learning **explicit many-to-many relationships first**.

Why?

Because real LMS relationships often need metadata:

```text
Enrollment
├── enrolledAt
├── status
├── completedAt
└── progress
```

So:

```text
User ↔ Course
```

becomes:

```text
User → Enrollment ← Course
```

This gives you much more control.

---

# 25. Enums

Prisma also supports enums.

Suppose enrollment can have:

```text
ACTIVE
COMPLETED
CANCELLED
```

You could define:

```prisma
enum EnrollmentStatus {
  ACTIVE
  COMPLETED
  CANCELLED
}
```

Then:

```prisma
model Enrollment {
  userId     String
  courseId   String
  status     EnrollmentStatus @default(ACTIVE)
  enrolledAt DateTime         @default(now())

  user   User   @relation(fields: [userId], references: [id])
  course Course @relation(fields: [courseId], references: [id])

  @@id([userId, courseId])
}
```

This is much safer than storing arbitrary strings:

```text
"active"
"Active"
"ACTIVE"
"actve"
"finished"
```

Enums give your data a controlled set of values.

---

# 26. Mapping Prisma Names to Database Names

You may prefer:

```prisma
createdAt
```

in TypeScript.

But your PostgreSQL naming convention might be:

```text
created_at
```

Prisma supports mapping.

For example:

```prisma
createdAt DateTime @default(now()) @map("created_at")
```

And:

```prisma
model User {
  id        String   @id @default(uuid())
  createdAt DateTime @default(now()) @map("created_at")

  @@map("users")
}
```

Now:

```text
Prisma
createdAt
```

maps to:

```text
PostgreSQL
created_at
```

And:

```text
Prisma model User
```

maps to:

```text
PostgreSQL table users
```

This is useful when you want idiomatic TypeScript naming while keeping PostgreSQL naming conventions.

# 27. A More Complete AI LMS Schema

Let's now combine what we've learned.

```prisma
enum EnrollmentStatus {
  ACTIVE
  COMPLETED
  CANCELLED
}

model User {
  id           String       @id @default(uuid())
  name         String
  email        String       @unique
  passwordHash String
  createdAt    DateTime     @default(now())
  updatedAt    DateTime     @updatedAt

  courses      Course[]
  enrollments  Enrollment[]
  progress     LessonProgress[]
}

model Course {
  id           String       @id @default(uuid())
  title        String
  description  String?
  instructorId String
  createdAt    DateTime     @default(now())

  instructor   User          @relation(fields: [instructorId], references: [id])
  lessons      Lesson[]
  enrollments  Enrollment[]
}

model Lesson {
  id          String   @id @default(uuid())
  courseId    String
  title       String
  content     String?
  lessonOrder Int
  createdAt   DateTime @default(now())

  course      Course           @relation(fields: [courseId], references: [id])
  progress    LessonProgress[]
}

model Enrollment {
  userId     String
  courseId   String
  status     EnrollmentStatus @default(ACTIVE)
  enrolledAt DateTime         @default(now())

  user       User   @relation(fields: [userId], references: [id])
  course     Course @relation(fields: [courseId], references: [id])

  @@id([userId, courseId])
}

model LessonProgress {
  userId        String
  lessonId      String
  progress      Int      @default(0)
  completedAt   DateTime?

  user          User     @relation(fields: [userId], references: [id])
  lesson        Lesson   @relation(fields: [lessonId], references: [id])

  @@id([userId, lessonId])
}
```

Don't worry about memorizing this.

We're going to build it piece by piece throughout Phase 3.

# 28. Read the Schema Like a Database Engineer

Look at:

```prisma
model Lesson {
  id          String   @id @default(uuid())
  courseId    String
  title       String
  content     String?
  lessonOrder Int

  course Course @relation(fields: [courseId], references: [id])
}
```

You should be able to mentally translate it to:

```text
lessons
────────────────────────
id            PK
course_id     FK → courses.id
title
content       nullable
lesson_order
```

That's the skill we're looking for.

Similarly:

```prisma
model Enrollment {
  userId   String
  courseId String

  user   User   @relation(...)
  course Course @relation(...)

  @@id([userId, courseId])
}
```

should immediately make you think:

```text
enrollments
─────────────────────
user_id      FK
course_id    FK
PRIMARY KEY (user_id, course_id)
```

If you can translate between the two, you're learning correctly.

# 29. Prisma Doesn't Remove SQL

This is a very important career lesson.

You might write:

```ts
const courses = await prisma.course.findMany({
  where: {
    instructorId: userId,
  },
});
```

But underneath, PostgreSQL is doing database work.

Conceptually:

```sql
SELECT *
FROM courses
WHERE instructor_id = ...;
```

Therefore, when you eventually learn:

```text
Indexes
EXPLAIN
Transactions
Locks
Query optimization
Constraints
Isolation
```

your Prisma knowledge won't be enough by itself.

You need both:

```text
Prisma
+
PostgreSQL
```

That's exactly why this Phase 3 order is important.

# 31. A Common Beginner Mistake

Don't write Prisma like this:

```text
"I need a course page."

↓
Create Course table.

"I need a lesson page."

↓
Create Lesson table.

"I need a dashboard."

↓
Create Dashboard table.
```

That's UI-driven database design.

Instead:

```text
Business domain
      ↓
Entities
      ↓
Relationships
      ↓
Database
      ↓
API
      ↓
UI
```

A dashboard usually doesn't need its own table.

It's a **view of existing data**.

---

# 32. Another Important Rule

Don't put everything into one Prisma model just because it's convenient.

Bad:

```prisma
model User {
  id          String
  name        String
  course1     String?
  course2     String?
  course3     String?
  lesson1     String?
  lesson2     String?
  lesson3     String?
}
```

That's not relational design.

Instead:

```text
User
Course
Lesson
Enrollment
Progress
```

and connect them with relationships.
