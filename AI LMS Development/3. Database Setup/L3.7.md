# Lesson 3.7 — PostgreSQL Indexes

Now we're getting into a topic that separates:

> **“I can use PostgreSQL.”**

from:

> **“I understand how PostgreSQL performs.”**

Indexes are one of the most important tools for making database queries fast.

But there's a catch:

> **Indexes are not automatically good.**

Too few indexes → slow reads.  
Too many indexes → slower writes and more storage.

So the goal is to learn **when and why an index should exist**.

---

# 1. The Basic Problem

Imagine your `users` table contains:

```text
10 rows
```

Searching for:

```sql
SELECT *
FROM users
WHERE email = 'rahul@example.com';
```

is easy.

But imagine:

```text
10 million users
```

PostgreSQL has to find one particular email.

How should it search?

Without an appropriate index, it may need to inspect a huge number of rows.

That's where an index helps.

---

# 2. What Is an Index?

An index is a separate data structure that helps PostgreSQL find rows more efficiently.

Think about a book.

Without an index:

```text
Find "PostgreSQL"
        ↓
Read page 1
Read page 2
Read page 3
...
Read hundreds of pages
```

With an index:

```text
PostgreSQL
    ↓
Page 427
```

Database indexes work on the same general idea:

```text
Query
  ↓
Index
  ↓
Find relevant row locations
  ↓
Read required rows
```

---

# 3. Without an Index

Suppose:

```text
users

id | name  | email
---|-------|-------------------
1  | Rahul | rahul@example.com
2  | Aman  | aman@example.com
3  | Priya | priya@example.com
...
```

Query:

```sql
SELECT *
FROM users
WHERE email = 'rahul@example.com';
```

Without an index on `email`, PostgreSQL may perform a:

```text
Sequential Scan
```

Conceptually:

```text
Row 1 → check email
Row 2 → check email
Row 3 → check email
Row 4 → check email
...
```

For a huge table, that can become expensive.

---

# 4. With an Index

Create:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Now PostgreSQL has a structure optimized for finding values in `email`.

Conceptually:

```text
Query
 ↓
email index
 ↓
rahul@example.com
 ↓
matching row
```

Much less data may need to be examined.

---

# 5. Prisma `@unique` Already Creates an Index

Remember:

```prisma
email String @unique
```

This isn't just an application-level rule.

It creates a uniqueness constraint in the database, backed by an appropriate unique index/structure.

So:

```prisma
email String @unique
```

means:

```text
Email must be unique
        +
Database can efficiently enforce that uniqueness
```

You don't normally need to create another ordinary index on the exact same column just for lookup purposes.

---

# 6. Indexes Are Not Free

This is extremely important.

Suppose you have:

```text
users
```

and create:

```text
email index
name index
created_at index
role index
status index
```

Now every insert/update may need to maintain several indexes.

So:

```text
More indexes
     ↓
Faster some reads
     ↓
More storage
     ↓
More write overhead
```

Therefore:

> **Don't index every column.**

---

# 7. The Most Important Question

Before creating an index, ask:

> **What queries will my application actually run frequently?**

For example, your AI LMS might frequently run:

```sql
SELECT *
FROM users
WHERE email = ...;
```

That's a good candidate for an index.

Another:

```sql
SELECT *
FROM lessons
WHERE course_id = ...;
```

Also a strong candidate.

Another:

```sql
SELECT *
FROM lesson_progress
WHERE user_id = ...
  AND lesson_id = ...;
```

This suggests a composite index or unique composite key.

Index design should come from **query patterns**.

---

# 8. Indexes and Your AI LMS

Consider these tables:

```text
users
courses
lessons
enrollments
lesson_progress
```

Potential queries:

```text
Find user by email
Find courses by instructor
Find lessons by course
Find enrollments by user
Find progress by user + lesson
```

We can derive useful indexes from these access patterns.

---

# 9. Indexing `email`

Your login flow probably needs:

```sql
SELECT *
FROM users
WHERE email = 'rahul@example.com';
```

So:

```prisma
email String @unique
```

is a good design.

The database needs uniqueness anyway, and the unique structure supports efficient lookup.

---

# 10. Indexing Foreign Keys

Suppose:

```text
lessons
```

contains:

```text
id
course_id
title
```

Your application frequently asks:

```sql
SELECT *
FROM lessons
WHERE course_id = '...';
```

Then:

```text
course_id
```

is a strong index candidate.

In Prisma:

```prisma
model Lesson {
  id       String @id @default(uuid())
  courseId String
  title    String

  course Course @relation(fields: [courseId], references: [id])

  @@index([courseId])
}
```

This creates an index for:

```text
courseId
```

---

# 11. Important: Foreign Key ≠ Automatically the Right Index

A foreign key establishes referential integrity.

It doesn't mean:

> "Every query involving this foreign key will automatically be fast."

You should still think about indexes based on query patterns.

For example:

```text
lessons.course_id
```

is commonly queried, so indexing it often makes sense.

---

# 12. Prisma `@@index`

For a single field:

```prisma
@@index([courseId])
```

This means:

> Create an index on `courseId`.

Example:

```prisma
model Lesson {
  id       String @id @default(uuid())
  courseId String
  title    String

  course Course @relation(fields: [courseId], references: [id])

  @@index([courseId])
}
```

---

# 13. Composite Indexes

Now consider:

```text
lesson_progress
```

Suppose your application frequently asks:

```sql
SELECT *
FROM lesson_progress
WHERE user_id = ...
  AND lesson_id = ...;
```

We have two columns:

```text
user_id
lesson_id
```

We can create:

```prisma
@@index([userId, lessonId])
```

This is a **composite index**.

---

# 14. Composite Index Order Matters

This is extremely important.

Suppose:

```prisma
@@index([userId, lessonId])
```

This is not exactly equivalent to:

```prisma
@@index([lessonId, userId])
```

The order matters.

Think of:

```text
(userId, lessonId)
```

as being organized primarily by:

```text
userId
```

and then within each user:

```text
lessonId
```

So this index is especially useful for queries such as:

```sql
WHERE user_id = ?
```

and:

```sql
WHERE user_id = ?
AND lesson_id = ?
```

But it may be much less useful for:

```sql
WHERE lesson_id = ?
```

alone.

---

# 15. The Leftmost Prefix Idea

Suppose you have:

```prisma
@@index([userId, lessonId])
```

Think:

```text
userId → lessonId
```

Queries using the left side are favored.

### Good fit

```sql
WHERE user_id = ?
```

### Good fit

```sql
WHERE user_id = ?
AND lesson_id = ?
```

### Often not the best fit

```sql
WHERE lesson_id = ?
```

This is why **index column order matters**.

---

# 16. Example With AI LMS

Suppose:

```text
lesson_progress

user_id
lesson_id
progress
completed_at
```

Most common query:

> Get Rahul's progress for lesson 25.

```sql
SELECT *
FROM lesson_progress
WHERE user_id = 'rahul-id'
AND lesson_id = 'lesson-25';
```

A composite index:

```prisma
@@index([userId, lessonId])
```

can support this access pattern.

However, if you already have:

```prisma
@@id([userId, lessonId])
```

then the primary key itself already creates a unique index-like structure for that combination.

So you **wouldn't normally add the exact same composite index again**.

That's an important optimization.

---

# 17. Primary Keys Are Indexed

When you define:

```prisma
id String @id
```

PostgreSQL needs to enforce uniqueness of that primary key, so an appropriate index is created.

Therefore:

```sql
WHERE id = ...
```

is normally very efficient.

You don't need:

```prisma
@@index([id])
```

just because `id` is frequently queried.

That would usually be redundant.

---

# 18. Unique Fields Also Have Supporting Structures

Similarly:

```prisma
email String @unique
```

already creates the database structure needed to enforce uniqueness.

So don't do this unnecessarily:

```prisma
email String @unique

@@index([email])
```

You're likely duplicating the same purpose.

---

# 19. Indexing `createdAt`

Suppose your LMS dashboard frequently asks:

> Give me the newest courses.

Query:

```sql
SELECT *
FROM courses
ORDER BY created_at DESC
LIMIT 20;
```

An index on:

```text
created_at
```

may help depending on the query and table size.

Prisma:

```prisma
@@index([createdAt])
```

You can also specify sort direction where appropriate:

```prisma
@@index([createdAt(sort: Desc)])
```

The exact benefit depends on the query, PostgreSQL version, table size, and other factors.

Don't assume an index is always faster—verify with query plans.

---

# 20. `WHERE` + `ORDER BY`

Suppose you query:

```sql
SELECT *
FROM courses
WHERE instructor_id = ?
ORDER BY created_at DESC
LIMIT 20;
```

Now think about the query pattern:

```text
filter by instructor
        +
sort by creation time
```

A composite index may be useful:

```prisma
@@index([instructorId, createdAt(sort: Desc)])
```

This is more targeted than creating:

```text
index(instructorId)
index(createdAt)
```

without thinking about the actual query.

This is the beginning of **query-driven index design**.

---

# 21. Indexing for `JOIN`

Suppose:

```sql
SELECT *
FROM lessons
JOIN courses
ON lessons.course_id = courses.id;
```

The relationship uses:

```text
lessons.course_id
```

An index there can often help PostgreSQL efficiently locate matching lesson rows, especially for common filtered/joined access patterns.

Again:

```text
Foreign key
    +
Common query pattern
    ↓
Potential index
```

Don't mechanically index every FK. Consider how the table is queried.

---

# 22. B-Tree — The Default Index

PostgreSQL's most common index type is:

```text
B-tree
```

When you write:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

PostgreSQL normally creates a B-tree index.

B-trees are excellent for many common operations:

```text
=
<
>
<=
>=
ORDER BY
range queries
```

For example:

```sql
WHERE age > 18
```

or:

```sql
WHERE created_at >= '2026-01-01'
```

---

# 23. You Don't Need to Memorize the Tree

Don't worry about memorizing the internal implementation yet.

Understand the practical idea:

```text
Sequential scan
→ potentially inspect many rows

B-tree index
→ navigate an ordered structure toward relevant values
```

That's enough at this stage.

We'll go deeper into query planning when we reach **3.10 Query Optimization**.

---

# 24. Other PostgreSQL Index Types

PostgreSQL supports other index types too:

```text
B-tree
Hash
GIN
GiST
SP-GiST
BRIN
```

For normal application queries, start with:

> **B-tree**

You'll encounter specialized indexes later.

For example, AI applications may use `GIN` for certain `JSONB` or full-text-related workloads, while very large naturally ordered tables can sometimes benefit from `BRIN`.

But don't reach for specialized indexes without a real use case.

---

# 25. Indexes and `LIKE`

Consider:

```sql
SELECT *
FROM users
WHERE email LIKE 'rahul%';
```

A B-tree index can often help with a prefix search like:

```text
rahul%
```

But:

```sql
WHERE email LIKE '%rahul%'
```

is a different problem.

The leading wildcard makes ordinary B-tree usage much less straightforward.

This is why:

```text
Search requirements
       ↓
Index strategy
```

must be considered together.

---

# 26. Case-Insensitive Search

Suppose your application searches:

```text
RAHUL@EXAMPLE.COM
rahul@example.com
Rahul@Example.com
```

You may decide to normalize email addresses in your application.

Another approach is to use PostgreSQL-specific features such as `citext` or functional indexes.

For example, conceptually:

```sql
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));
```

Then queries using:

```sql
WHERE LOWER(email) = LOWER(...)
```

can potentially use the functional index.

This is an example of a more advanced index.

For your LMS, keep email normalization simple and consistent first.

---

# 27. Indexes and Write Performance

Suppose your table has:

```text
1 million rows
```

and:

```text
10 indexes
```

When inserting a row:

```text
INSERT
  ↓
Table updated
  ↓
Index 1 updated
Index 2 updated
Index 3 updated
...
Index 10 updated
```

So indexes aren't free.

The more indexes you have, the more work PostgreSQL may need to perform during writes.

Therefore:

> **Index for important access patterns, not for every column.**

---

# 28. Indexes Consume Storage

Indexes are stored separately from the table data.

So:

```text
Table
+
Indexes
+
Other database structures
```

all consume disk space.

A huge table with many unnecessary indexes can waste significant storage.

---

# 29. Index Selectivity

Here's another useful concept.

Suppose:

```text
users
```

contains:

```text
10 million rows
```

and you index:

```text
email
```

Email values are highly varied.

That's generally a good candidate.

Now suppose you index:

```text
is_active
```

where:

```text
9,999,000 rows → true
1,000 rows      → false
```

The index may be less useful for many queries because the column has very low selectivity.

Selectivity roughly means:

> How effectively does a column distinguish rows?

High-cardinality fields such as:

```text
email
id
uuid
```

are often strong index candidates.

Low-cardinality fields such as:

```text
is_active
gender
status
```

need more careful consideration.

But don't reduce index design to selectivity alone—query patterns and table size matter too.

---

# 30. Indexing Boolean Columns

A beginner often thinks:

```text
is_completed
```

therefore:

```prisma
@@index([isCompleted])
```

Not necessarily.

Suppose:

```text
99% → completed = true
1%  → completed = false
```

An index may not be particularly helpful for every query.

You need to consider:

```text
How many rows?
How selective?
What query?
How often?
What does EXPLAIN show?
```

---

# 31. Partial Indexes

PostgreSQL can create indexes only for rows satisfying a condition.

For example, suppose you often query:

```text
WHERE deleted_at IS NULL
```

A partial index can sometimes be useful:

```sql
CREATE INDEX idx_active_users
ON users(id)
WHERE deleted_at IS NULL;
```

Now only active/non-deleted rows are represented in that index.

This is an advanced PostgreSQL optimization.

Prisma doesn't expose every PostgreSQL feature equally through the schema language, so sometimes you may use custom SQL migrations.

We'll keep this in mind for later.

---

# 32. Soft Delete Example

Suppose your users table has:

```text
deleted_at
```

Then your application frequently queries:

```sql
SELECT *
FROM users
WHERE deleted_at IS NULL;
```

As the table grows, you may consider a partial index or another targeted strategy.

The important lesson isn't:

> "Always create a partial index."

It's:

> **Indexes should reflect real query patterns.**

---

# 33. How to Know Whether an Index Helps

Don't guess.

Use:

```sql
EXPLAIN
```

or:

```sql
EXPLAIN ANALYZE
```

For example:

```sql
EXPLAIN ANALYZE
SELECT *
FROM lessons
WHERE course_id = '...';
```

PostgreSQL will show the query plan.

You may see things like:

```text
Seq Scan
Index Scan
Bitmap Index Scan
Bitmap Heap Scan
```

These tell you how PostgreSQL executed the query.

We'll study these properly in **Lesson 3.10 — Query Optimization**.

For now, remember:

> **EXPLAIN is how you investigate query performance instead of guessing.**

---

# 34. Sequential Scan Isn't Always Bad

This is a very important point.

You might see:

```text
Seq Scan
```

and think:

> "My database is broken!"

No.

Suppose your table has only:

```text
50 rows
```

and your query needs:

```text
40 rows
```

A sequential scan may be perfectly reasonable.

An index isn't automatically faster.

PostgreSQL's query planner chooses what it thinks is cheapest.

So:

```text
Seq Scan ≠ bad
Index Scan ≠ automatically good
```

This is why we use `EXPLAIN ANALYZE`.

---

# 35. AI LMS Index Strategy

Let's design some sensible indexes.

### Users

```prisma
model User {
  id    String @id @default(uuid())
  email String @unique
}
```

`email` already has uniqueness support.

No need for:

```prisma
@@index([email])
```

just for the same purpose.

---

### Courses

Suppose instructors frequently see their courses:

```prisma
model Course {
  id           String @id @default(uuid())
  instructorId String

  @@index([instructorId])
}
```

Good candidate.

---

### Lessons

Suppose course pages frequently load lessons:

```prisma
model Lesson {
  id       String @id @default(uuid())
  courseId String
  title    String

  @@index([courseId])
}
```

Good candidate.

---

### Enrollments

Suppose:

```prisma
@@id([userId, courseId])
```

already exists.

That supports the exact `(userId, courseId)` combination.

But suppose you frequently query:

```sql
WHERE user_id = ?
```

The composite primary key beginning with `userId` can often support that access pattern.

So you may not need another separate `userId` index.

However, if you frequently query:

```sql
WHERE course_id = ?
```

the `(userId, courseId)` index is not equivalent to an index beginning with `courseId`.

You may then want:

```prisma
@@index([courseId])
```

This is a classic example of **index order and query patterns**.

# 37. A Practical Index Checklist

Before adding an index, ask:

```text
1. What query am I optimizing?

2. Is the column used in WHERE?

3. Is it used in JOIN?

4. Is it used in ORDER BY?

5. Is it a range query?

6. What is the column's selectivity?

7. Does an existing index already cover this?

8. Does index column order match the query?

9. How frequently is the query executed?

10. What does EXPLAIN ANALYZE say?
```

You don't need to ask all ten every time.

But this is the mindset you should develop.

# 38. Common Beginner Mistakes

### Mistake 1

Index every column.

```text
❌
name
email
age
role
status
created_at
updated_at
...
```

No.

---

### Mistake 2

Duplicate indexes.

For example:

```prisma
email String @unique

@@index([email])
```

Usually unnecessary.

---

### Mistake 3

Ignore composite index order.

```text
(userId, lessonId)
```

and:

```text
(lessonId, userId)
```

are not interchangeable.

---

### Mistake 4

Assume indexes always improve performance.

They don't.

---

### Mistake 5

Never inspect query plans.

If the application becomes slow:

```text
❌ "Let's add indexes everywhere."

✅ "Let's inspect the query plan."
```

```text

  ↓

  ↓

  ↓

```

```text

```

## Next — Lesson 3.8: Transactions

This one is **extremely important for backend engineering**.

We'll learn what happens when one business operation requires multiple database changes.

For example, when a student enrolls:

```text
Create enrollment
      ↓
Update course statistics
      ↓
Create activity record
      ↓
Update something else
```

What if step 3 fails after steps 1 and 2 succeed?

You could end up with inconsistent data.

Transactions solve this:

```text
BEGIN
  ↓
Operation 1
  ↓
Operation 2
  ↓
Operation 3
  ↓
COMMIT
```

or, if something fails:

```text
BEGIN
  ↓
Operation 1
  ↓
Operation 2
  ↓
❌ Operation 3
  ↓
ROLLBACK
```

We'll cover **ACID, atomicity, commit, rollback, isolation, Prisma `$transaction()`, and real AI LMS examples**.
