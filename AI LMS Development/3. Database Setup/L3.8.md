# Lesson 3.8 — Database Transactions

This is one of the most important backend concepts in Phase 3.

So far we've learned how to design tables and relationships. Now we need to answer:

> **What happens when one business operation requires multiple database changes?**

For example, suppose a student enrolls in a course.

Maybe your backend needs to:

```text
1. Create enrollment
2. Create initial lesson progress
3. Update course statistics
4. Create activity record
```

What if step 1 succeeds, step 2 succeeds, but step 3 fails?

Without a transaction, your database could be left in an inconsistent state.

Transactions solve this problem.

---

# 1. What Is a Transaction?

A **transaction** is a group of database operations that PostgreSQL treats as one logical unit.

Think:

```text
Transaction
    │
    ├── Operation 1
    ├── Operation 2
    ├── Operation 3
    └── Operation 4
```

Either:

```text
ALL succeed
```

or:

```text
ALL are rolled back
```

This gives you a very important guarantee:

> **The database doesn't end up halfway through a business operation.**

---

# 2. A Simple Example

Suppose you have:

```text
accounts
```

with:

```text
Rahul → ₹10,000
Aman  → ₹5,000
```

Rahul transfers ₹1,000 to Aman.

We need two operations:

```text
1. Rahul - ₹1,000
2. Aman + ₹1,000
```

Without a transaction:

```text
Rahul - ₹1,000
       ↓
Database crashes
       ↓
Aman never receives ₹1,000
```

Now:

```text
Rahul → ₹9,000
Aman  → ₹5,000
```

₹1,000 disappeared.

That's unacceptable.

With a transaction:

```text
BEGIN

Rahul - ₹1,000
Aman  + ₹1,000

COMMIT
```

If something fails:

```text
BEGIN

Rahul - ₹1,000
Aman + ₹1,000
       ↓
       ❌ failure

ROLLBACK
```

The database returns to the previous consistent state.

---

# 3. The Four ACID Properties

Transactions are usually explained using **ACID**.

```text
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

These four concepts are very important for interviews.

Let's understand them simply.

---

# 4. A — Atomicity

Atomicity means:

> **The transaction happens completely or not at all.**

Suppose:

```text
Operation 1 ✅
Operation 2 ✅
Operation 3 ❌
```

The database rolls back the previous operations.

So:

```text
Before transaction
      ↓
Operation 1
      ↓
Operation 2
      ↓
Operation 3 fails
      ↓
ROLLBACK
      ↓
Back to previous state
```

Think:

```text
All or nothing.
```

---

# 5. C — Consistency

Consistency means:

> **A successful transaction should leave the database in a valid state according to its rules.**

Suppose:

```text
users.id
```

is referenced by:

```text
courses.instructor_id
```

If a transaction tries to create an invalid foreign-key reference:

```text
instructor_id = 999999
```

and user 999999 doesn't exist, PostgreSQL rejects it.

The database remains consistent.

Constraints help enforce consistency.

---

# 6. I — Isolation

Isolation means:

> **Concurrent transactions should not interfere with each other in unsafe ways.**

Imagine two users try to purchase the last available seat at exactly the same time.

```text
Available seats = 1
```

Transaction A:

```text
Check seats → 1
```

Transaction B:

```text
Check seats → 1
```

If both independently decide:

```text
"Great! I'll take it."
```

you might sell two seats.

Database isolation and concurrency controls help prevent such problems.

We'll discuss isolation levels later in this lesson.

---

# 7. D — Durability

Durability means:

> **Once a transaction successfully commits, the database should preserve that result even if there is a crash afterward.**

For example:

```text
COMMIT
   ↓
Transaction successful
   ↓
Server crashes
   ↓
Database restarts
   ↓
Committed data remains
```

This is one of the core guarantees provided by a durable database system.

---

# 8. The Transaction Lifecycle

Conceptually:

```text
BEGIN
  ↓
Operation 1
  ↓
Operation 2
  ↓
Operation 3
  ↓
COMMIT
```

If something fails:

```text
BEGIN
  ↓
Operation 1
  ↓
Operation 2
  ↓
❌ Operation 3
  ↓
ROLLBACK
```

So the basic lifecycle is:

```text
BEGIN
COMMIT
ROLLBACK
```

---

# 9. PostgreSQL Transaction Example

Let's say we have:

```text
accounts
```

We could write:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

If something goes wrong:

```sql
ROLLBACK;
```

Now PostgreSQL treats the operations as one unit.

# 11. Prisma Transactions

Prisma provides:

```ts
prisma.$transaction()
```

This is the main API you'll use.

For example:

```ts
await prisma.$transaction(async (tx) => {
  await tx.enrollment.create({
    data: {
      userId,
      courseId,
    },
  });

  await tx.lessonProgress.createMany({
    data: progressRecords,
  });
});
```

Think:

```text
prisma
   ↓
$transaction
   ↓
Operation 1
Operation 2
   ↓
COMMIT
```

If an operation throws an error:

```text
Operation 1 ✅
Operation 2 ❌
      ↓
ROLLBACK
```

---

# 12. `tx` Is Important

Look carefully:

```ts
await prisma.$transaction(async (tx) => {
  await tx.enrollment.create(...);
  await tx.lessonProgress.createMany(...);
});
```

Inside the transaction, use:

```text
tx
```

rather than:

```text
prisma
```

for the operations that should belong to the transaction.

Think:

```text
prisma
   ↓
normal database client

tx
   ↓
transaction-bound client
```

---

# 13. Interactive Transactions

The previous example is called an **interactive transaction**.

Example:

```ts
const result = await prisma.$transaction(async (tx) => {
  const enrollment = await tx.enrollment.create({
    data: {
      userId,
      courseId,
    },
  });

  const progress = await tx.lessonProgress.createMany({
    data: progressRecords,
  });

  return {
    enrollment,
    progress,
  };
});
```

The function:

```text
async (tx) => { ... }
```

runs inside the transaction.

---

# 14. Sequential Transactions

Prisma also supports an array form:

```ts
await prisma.$transaction([
  prisma.user.update({
    where: { id: userId },
    data: { ... },
  }),

  prisma.activity.create({
    data: { ... },
  }),
]);
```

This is useful when you already know the operations you need to execute together.

Conceptually:

```text
Transaction
├── Query 1
└── Query 2
```

For more complex logic where one query depends on the result of another, the interactive form is often more useful.

---

# 15. When Should You Use a Transaction?

Use a transaction when:

> **Multiple database operations must succeed or fail together.**

For example:

```text
Create order
+
Create order items
+
Reduce inventory
```

These should probably be treated as one logical operation.

Similarly:

```text
Create quiz attempt
+
Create answers
+
Update progress
```

may need transactional handling.

---

# 16. When You Don't Need a Transaction

Don't wrap every single query in a transaction.

For example:

```ts
const user = await prisma.user.findUnique({
  where: { id: userId },
});
```

There's usually no reason to make a transaction around a single simple read.

Likewise:

```ts
await prisma.course.findMany();
```

doesn't normally need a transaction.

Transactions have overhead and should be used when they provide a consistency benefit.

---

# 17. Transactions Are Not Just About Errors

A common beginner thought is:

> "I need a transaction because my code might throw an error."

That's only part of it.

The deeper reason is:

> **The operations form one logical unit of work.**

Even if every query usually succeeds, you need atomicity because the database should never represent a half-completed business operation.

---

# 18. Example: Enrollment

Suppose enrollment involves:

```text
1. Create enrollment
2. Create progress records
3. Record activity
```

Without transaction:

```text
Enrollment created       ✅
Progress created         ✅
Activity creation       ❌
```

Database:

```text
Enrollment exists
Progress exists
Activity missing
```

Maybe that's okay—or maybe it violates your business rules.

If these three operations must be atomic:

```text
BEGIN

Enrollment
Progress
Activity

COMMIT
```

If any fails:

```text
ROLLBACK
```

Everything is undone.

---

# 19. Transaction Boundaries

One of the most useful concepts is:

> **Where should the transaction start and end?**

A transaction should usually cover one coherent business operation.

For example:

```text
Enroll student
   ↓
BEGIN
   ↓
Create enrollment
Create initial progress
Create activity
   ↓
COMMIT
```

Don't create a transaction that lasts for:

```text
10 minutes
```

while your application performs unrelated work.

Long transactions can cause:

```text
locks
contention
resource usage
performance problems
```

Keep transaction boundaries focused.

---

# 20. Don't Call External APIs Inside a Database Transaction

This is a very important real-world rule.

Suppose you're processing:

```text
Create payment record
      ↓
Call Stripe
      ↓
Generate AI response
      ↓
Update database
```

Don't casually do:

```ts
await prisma.$transaction(async (tx) => {
  await tx.payment.create(...);

  await someExternalAPI();

  await tx.order.update(...);
});
```

Why?

The database transaction remains open while waiting for the external API.

That can create:

```text
long transaction
     ↓
locks held longer
     ↓
contention
     ↓
poor performance
```

External systems also cannot participate in your PostgreSQL transaction automatically.

We'll revisit patterns for this when we study more advanced architecture.

---

# 21. Transaction Isolation

Now let's talk about the **I** in ACID.

Imagine two transactions:

```text
Transaction A
Transaction B
```

running simultaneously.

The database must decide:

> What can A see from B?

and:

> What can B see from A?

This is controlled by **transaction isolation**.

---

# 22. Common Isolation Levels

PostgreSQL supports:

```text
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

You may also hear:

```text
READ UNCOMMITTED
```

but PostgreSQL effectively treats it differently and uses `READ COMMITTED` behavior.

For now, focus on the three practical levels above.

---

# 23. READ COMMITTED

This is PostgreSQL's default isolation level.

Conceptually:

> A query sees data committed before that query began, plus its own changes.

Imagine:

```text
Transaction A
Transaction B
```

B hasn't committed a change yet.

A won't normally see B's uncommitted data.

This prevents **dirty reads**.

---

# 24. Dirty Read

A dirty read would look like:

```text
Transaction A
   ↓
Changes balance to ₹9,000
   ↓
Not committed

Transaction B
   ↓
Reads ₹9,000
```

Then A rolls back:

```text
ROLLBACK
```

Now B read data that never actually existed as committed state.

That's a dirty read.

PostgreSQL's normal behavior prevents this.

---

# 25. Repeatable Read

Suppose a transaction performs the same query twice.

You want the transaction to see a stable snapshot.

Conceptually:

```text
Transaction starts
      ↓
Query → 10 rows
      ↓
Other transaction commits changes
      ↓
Query again
      ↓
Same transaction snapshot
```

This gives stronger consistency than READ COMMITTED.

You don't need to use it everywhere.

---

# 26. Serializable

This is the strongest standard isolation level PostgreSQL provides.

The goal is:

> Make concurrent transactions behave as if they ran one after another.

Conceptually:

```text
A then B
```

or:

```text
B then A
```

rather than allowing unsafe interleavings.

But stronger isolation can result in:

```text
serialization failures
retries
more contention
```

So it should be used when the business operation actually needs that level of protection.

---

# 27. The Last Seat Example

Suppose:

```text
course seats = 1
```

Two users try to enroll simultaneously.

A:

```text
Read seats → 1
```

B:

```text
Read seats → 1
```

Both think:

```text
"There's one seat available."
```

This is a concurrency problem.

Simply wrapping code in a transaction isn't always enough.

You also need an appropriate strategy for **concurrent updates**.

Possible solutions include:

```text
atomic UPDATE
row locking
appropriate isolation
unique constraints
optimistic concurrency
```

Transactions are one part of concurrency control—not the entire story.

---

# 28. Row-Level Locking

PostgreSQL can lock specific rows.

For example:

```sql
SELECT *
FROM courses
WHERE id = '...'
FOR UPDATE;
```

This tells PostgreSQL:

> Lock this row for update within the transaction.

Then another transaction trying to update that same row may need to wait.

This can be useful for operations where you need to safely read and then modify a specific record.

We'll cover locking more deeply when we get into advanced query/concurrency topics.

---

# 29. Prisma Isolation Levels

Prisma allows transaction options such as isolation level in supported versions/configurations.

Conceptually:

```ts
await prisma.$transaction(
  async (tx) => {
    // transaction work
  },
  {
    isolationLevel: Prisma.TransactionIsolationLevel.Serializable,
  }
);
```

The exact options depend on your Prisma version.

The important idea is:

```text
Prisma transaction
       ↓
PostgreSQL transaction
       ↓
Isolation behavior
```

Prisma doesn't remove the underlying database concepts.

# 30. Transactions and Constraints Work Together

This is a powerful idea.

Suppose your enrollment table has:

```text
PRIMARY KEY (user_id, course_id)
```

This prevents duplicate enrollment.

Now your transaction:

```text
Create enrollment
Create progress
```

benefits from both:

```text
Transaction
→ atomicity

Constraint
→ data validity
```

Good database design uses both.

---

# 31. Transaction vs Validation

These solve different problems.

### Validation

Asks:

> Is this input acceptable?

Example:

```text
email is valid?
title is present?
progress is between 0 and 100?
```

### Transaction

Asks:

> Should these database operations succeed or fail together?

Example:

```text
Create enrollment
+
Create progress
+
Create activity
```

So:

```text
Validation ≠ Transaction
```

You often need both.

---

# 32. Transaction vs Constraint

Similarly:

### Constraint

Protects a database rule:

```text
email UNIQUE
course_id NOT NULL
foreign key
```

### Transaction

Protects a multi-operation workflow:

```text
Operation A
+
Operation B
+
Operation C
```

Together:

```text
Application
   ↓
Validation
   ↓
Transaction
   ↓
Constraints
   ↓
Consistent database
```

# 33. A Real AI LMS Example

Imagine a student submits a quiz.

The backend needs to:

```text
1. Create QuizAttempt
2. Save submitted answers
3. Calculate score
4. Update lesson/course progress
5. Record activity
```

Suppose:

```text
QuizAttempt       ✅
Answers           ✅
Score             ✅
Progress update   ❌
Activity          ❌
```

Without a transaction, you could have:

```text
quiz attempt exists
answers exist
but progress doesn't reflect the attempt
```

If your business rule says these operations must be atomic:

```text
BEGIN
  Create attempt
  Save answers
  Calculate/update score
  Update progress
  Record activity
COMMIT
```

If anything fails:

```text
ROLLBACK
```

Now the system doesn't contain a half-completed quiz submission.

# 34. Transaction Design in Service Architecture

This connects nicely with the architecture you've been learning.

You prefer:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

Suppose:

```text
EnrollmentService
```

needs multiple repository operations.

The transaction boundary often belongs around the **business operation**, not around every repository function independently.

Conceptually:

```text
Controller
    ↓
EnrollmentService
    ↓
BEGIN TRANSACTION
    ├── EnrollmentRepository
    ├── ProgressRepository
    └── ActivityRepository
    ↓
COMMIT
```

This is a very useful architectural pattern.

---

# 35. A Potential Service Example

Conceptually:

```ts
async function enrollStudent(userId: string, courseId: string) {
  return prisma.$transaction(async (tx) => {
    const enrollment = await tx.enrollment.create({
      data: {
        userId,
        courseId,
      },
    });

    await tx.activity.create({
      data: {
        userId,
        type: "COURSE_ENROLLED",
      },
    });

    return enrollment;
  });
}
```

The controller doesn't need to know:

```text
BEGIN
COMMIT
ROLLBACK
```

The service owns the business operation.

This fits nicely with your controller → service → repository architecture.

# 36. Don't Overuse Transactions

Suppose you have:

```text
GET /courses
```

and you're simply retrieving courses.

Don't automatically do:

```text
BEGIN
SELECT courses
COMMIT
```

unless you have a specific consistency requirement.

Transactions are most valuable when:

```text
Multiple operations
+
One logical business action
+
Atomicity/consistency matters
```

---

# 37. Transaction Duration Matters

Avoid:

```text
BEGIN
   ↓
Database query
   ↓
HTTP request
   ↓
AI API call
   ↓
User interaction
   ↓
Another database query
   ↓
COMMIT
```

That's a terrible transaction boundary.

Instead:

```text
External work
   ↓
Prepare data
   ↓
Short DB transaction
   ↓
COMMIT
```

Keep transactions as short as practical.

### Mistake 1 — Transaction around everything

```text
❌ Every query = transaction
```

Unnecessary overhead and complexity.

---

### Mistake 2 — Long transactions

```text
❌ Transaction stays open while calling external services
```

Potential locking and performance problems.

---

### Mistake 3 — Mixing `prisma` and `tx`

Inside:

```ts
prisma.$transaction(async (tx) => {
```

you generally want transactional queries to use:

```text
tx
```

not the outside client.

---

### Mistake 4 — Thinking transaction solves every concurrency problem

It doesn't.

You may also need:

```text
constraints
locking
atomic updates
isolation levels
retry logic
```

# 39. The Most Important Mental Model

Think of a transaction as:

```text
Business operation
       ↓
Multiple DB operations
       ↓
┌──────────────────────┐
│     TRANSACTION      │
│                      │
│  Operation 1         │
│  Operation 2         │
│  Operation 3         │
│                      │
└──────────────────────┘
       ↓
   All succeed
       ↓
     COMMIT

OR

   One fails
       ↓
    ROLLBACK
```

That is the core idea.

# 40. Interview Questions You Should Be Able to Answer

### Q1. What is a transaction?

A transaction is a group of database operations treated as one logical unit, where changes can be committed together or rolled back together.

### Q2. What does ACID mean?

```text
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

### Q3. Why use transactions?

To maintain consistency when multiple database operations must succeed or fail together.

### Q4. What is rollback?

Undo the uncommitted changes made by the transaction.

### Q5. What is commit?

Permanently apply the transaction's changes.

### Q6. Does every query need a transaction?

No.

### Q7. Can a transaction prevent every concurrency problem?

No. You may also need constraints, locks, atomic operations, appropriate isolation, and retries.
