# 🔐 Phase 4 — Lesson 4.1: Authentication Architecture

Welcome to **Phase 4**.

In Phase 3, we learned how to design and work with our database:

```text
Application
    ↓
Prisma
    ↓
PostgreSQL
```

Now we're going to build the layer that answers one of the most important questions in any application:

> **Who is making this request?**

That is **authentication**.

And because our AI LMS has students, instructors, and admins, we'll also need **authorization**.

---

# 1. Authentication vs Authorization

These two words are often confused.

### Authentication

Authentication answers:

> **Who are you?**

For example:

```text
User → email + password
          ↓
      Verify identity
          ↓
      Rahul / User #123
```

### Authorization

Authorization answers:

> **What are you allowed to do?**

For example:

```text
Rahul
  ↓
role = STUDENT
  ↓
Can enroll in courses
Can watch lessons
Can take quizzes

Cannot:
Create courses
Delete users
Access admin dashboard
```

So remember:

```text
Authentication
       ↓
   WHO are you?

Authorization
       ↓
WHAT can you do?
```

This distinction will be extremely important throughout the LMS.

# 4. User Registration Architecture

Let's start with registration.

A user sends:

```http
POST /api/v1/auth/register
```

with something like:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123!"
}
```

The request should travel through our architecture:

```text
Client
  ↓
Route
  ↓
Validation Middleware
  ↓
Controller
  ↓
Authentication Service
  ↓
User Repository
  ↓
Prisma
  ↓
PostgreSQL
```

Notice something important.

The controller isn't directly talking to PostgreSQL.

That's consistent with the architecture we established earlier:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Prisma
    ↓
PostgreSQL
```

---

# 5. Registration Flow

Let's break it down.

### Step 1 — Client sends credentials

```text
name
email
password
```

### Step 2 — Validate input

For example:

```text
Is email valid?
Is password long enough?
Is name valid?
```

### Step 3 — Normalize the email

For example:

```text
Rahul@Example.COM
```

could be normalized to:

```text
rahul@example.com
```

The exact normalization policy should be deliberate rather than blindly modifying every possible email address.

### Step 4 — Check existing account

```text
Does this email already exist?
```

### Step 5 — Hash password

Never store:

```text
StrongPassword123!
```

Instead:

```text
StrongPassword123!
        ↓
Password hashing algorithm
        ↓
$hashedPassword...
```

### Step 6 — Create user

```text
User
├── id
├── name
├── email
├── passwordHash
├── role
└── timestamps
```

### Step 7 — Return safe response

We should **not** return:

```text
passwordHash
```

# 6. Login Architecture

Now suppose the user already has an account.

They send:

```http
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "StrongPassword123!"
}
```

Architecture:

```text
Client
  ↓
POST /auth/login
  ↓
Validation
  ↓
Controller
  ↓
Authentication Service
  ↓
User Repository
  ↓
Find user
  ↓
Verify password
  ↓
Create authentication session/tokens
  ↓
Response
```

Conceptually:

```text
Email + Password
       ↓
Find User
       ↓
Verify Password
       ↓
       ├── ❌ Invalid
       │
       └── ✅ Valid
              ↓
         Authenticate
              ↓
       Issue credentials
```

# 8. Why Do We Need an Access Token?

Imagine the user logs in.

Then they request:

```http
GET /api/v1/courses/my-courses
```

How does the server know who they are?

The request needs some form of authentication credential.

Conceptually:

```text
Request
   ↓
Credential
   ↓
Verify credential
   ↓
Identify user
   ↓
req.user
```

Then our application can have:

```text
req.user.id
req.user.role
```

or another carefully defined authentication context.

For example:

```javascript
req.user = {
  id: "user_123",
  role: "STUDENT"
};
```

The exact shape will be decided later.

# 9. Authentication Middleware

This leads us to one of the most important components.

```text
Authentication Middleware
```

Suppose:

```http
GET /api/v1/profile
```

comes in.

The request passes through:

```text
Request
   ↓
Authentication Middleware
   ↓
Controller
```

The middleware performs something conceptually like:

```text
Credential
    ↓
Extract
    ↓
Verify
    ↓
Identify user
    ↓
Attach authentication context
    ↓
Continue
```

If valid:

```text
Request
   ↓
Authentication
   ↓
req.user
   ↓
Controller
```

If invalid:

```text
Request
   ↓
Authentication
   ↓
❌ 401 Unauthorized
```

# 10. Authentication and Authorization Are Different Middleware

This distinction is extremely useful.

Imagine:

```http
POST /api/v1/courses
```

A user needs to be authenticated:

```text
Authentication
      ↓
Who is this?
```

Then we need authorization:

```text
Authorization
      ↓
Is this user allowed to create a course?
```

So:

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Controller
```

For example:

```text
Student
   ↓
Authenticated ✅
   ↓
Create Course?
   ↓
Authorization ❌
```

Whereas:

```text
Instructor
   ↓
Authenticated ✅
   ↓
Create Course?
   ↓
Authorization ✅
```

# 12. Authentication Architecture vs Business Logic

Here's an important architectural rule.

Don't do this everywhere:

```javascript
if (req.user.role === "ADMIN") {
   // huge business logic
}
```

Instead, try to separate concerns:

```text
Authentication
      ↓
Identity
      ↓
Authorization
      ↓
Business Logic
```

For example:

```text
Authentication Middleware
        ↓
Identify user
        ↓
Authorization Middleware
        ↓
Check permission
        ↓
Controller
        ↓
Service
        ↓
Repository
```

This keeps your backend easier to maintain.

---

# 13. Resource Ownership

RBAC isn't enough.

Consider:

```text
Instructor A
    ↓
Course A

Instructor B
    ↓
Course B
```

Both are instructors.

Therefore:

```text
Instructor A
role = INSTRUCTOR
```

does **not** automatically mean:

```text
Instructor A can edit every course.
```

We need another check:

```text
Does this course belong to this instructor?
```

Architecture:

```text
Authentication
       ↓
Is user authenticated?
       ↓
Authorization
       ↓
Is user an instructor?
       ↓
Resource authorization
       ↓
Does instructor own this course?
       ↓
Service
```

This concept will become extremely important in **4.11 Resource-Based Authorization**.

```text
 ├── Courses

 └── Progress
```

For example:

```text

 ├──── Session
 │
 └──── Session
```

Why multiple sessions?

Because a user might be logged in from:

```text
Laptop
Phone
Tablet
```

This gives us much better control over authentication.

# 15. Session Thinking

A useful mental model is:

```text
User
  ↓
Authentication Session
  ↓
Tokens
```

For example:

```text
User #123

Session A
├── Laptop
└── Active

Session B
├── Phone
└── Active
```

Later, the user could:

```text
Logout from this device
```

without necessarily logging out everywhere.

Or:

```text
Logout from all devices
```

This becomes possible when authentication is designed as a **session system**, rather than treating JWT as the entire authentication architecture.

Conceptually:

```text

Invalidate authentication state
```

# 21. HTTP Status Codes You'll Use

Authentication will make these especially important.

### `401 Unauthorized`

Usually means:

> The request has not been successfully authenticated.

Examples:

```text
Missing credential
Invalid credential
Expired credential
```

### `403 Forbidden`

Usually means:

> The user is authenticated, but isn't allowed to perform this action.

Example:

```text
Student
   ↓
Authenticated ✅
   ↓
Admin endpoint
   ↓
403 Forbidden
```

Remember:

```text
401 → Authentication problem
403 → Authorization problem
```

This distinction is important for both implementation and interviews.

# 🧠 Interview-Level Understanding

If an interviewer asks:

> **"How would you design authentication for an LMS?"**

You should be able to explain something like:

```text
I would separate authentication from authorization.

Authentication verifies the user's identity and establishes
an authentication context for the request.

Authorization determines whether that authenticated user has
the required role or permission.

For the backend, I'd keep controllers thin and use a
controller → service → repository architecture.

User and authentication-related state would be stored in
PostgreSQL through Prisma.

The system would support short-lived access credentials,
refresh-token/session management, logout and revocation,
role-based access control, and resource-level authorization.

For an LMS, I would have at least Student, Instructor and
Admin roles, while also checking resource ownership for
instructor-owned resources such as courses.
```

That's a **much stronger answer** than simply saying:

> "I use JWT authentication."
