# 🔐 Phase 4 — Lesson 4.10: Authorization Fundamentals

We've now built the **authentication foundation**:

```text
Registration
    ↓
Password Hashing
    ↓
Login
    ↓
Access Token
    ↓
Refresh Token
    ↓
Token Rotation
    ↓
Sessions
```

All of that answers:

> **"Who is this user?"**

Now we move to the next question:

> **"What is this user allowed to do?"**

That is **authorization**.

---

# 1. Authentication vs Authorization

This is one of the most important distinctions in backend development.

### Authentication

```text
Who are you?
```

Example:

```text
Rahul → user_123
```

### Authorization

```text
What are you allowed to do?
```

Example:

```text
user_123 → can view own profile
user_123 → cannot delete another user's account
```

So:

```text
Authentication
      ↓
Identity
      ↓
Authorization
      ↓
Permissions
```

---

# 2. Real-Life Example

Imagine an AI LMS.

There are three users:

```text
Rahul      → STUDENT
Priya      → INSTRUCTOR
Admin      → ADMIN
```

They all successfully log in.

Therefore:

```text
Authentication
    ↓
All three are valid users
```

But their permissions are different:

```text
STUDENT
├── View courses
├── Take quizzes
└── View own progress

INSTRUCTOR
├── Create courses
├── Edit own courses
├── Create quizzes
└── View student submissions

ADMIN
├── Manage users
├── Manage courses
├── Manage instructors
└── System administration
```

That's authorization.

---

# 3. The Authorization Pipeline

A protected request should conceptually follow:

```text
HTTP Request
     ↓
Authentication
     ↓
Who is the user?
     ↓
Authorization
     ↓
Can this user perform this action?
     ↓
Business Logic
```

For example:

```http
DELETE /api/v1/courses/course_123
```

The server asks:

```text
1. Is the token valid?
2. Who is the user?
3. Is the user allowed to delete courses?
4. Does the user own this course?
5. Perform deletion.
```

---

# 4. Authentication Is Not Enough

Suppose:

```text
Rahul
userId = user_123
role = STUDENT
```

His JWT is perfectly valid.

Now he sends:

```http
DELETE /api/v1/courses/course_456
```

JWT verification succeeds:

```text
Signature ✅
Expiration ✅
Identity ✅
```

But that doesn't mean:

```text
Delete permission ✅
```

Therefore:

```text
Valid JWT
      ≠
Permission to perform every action
```

---

# 5. Three Important Authorization Questions

For almost every protected endpoint, ask:

### 1. Who?

```text
Who is making this request?
```

Authentication.

### 2. What?

```text
What operation are they trying to perform?
```

For example:

```text
read
create
update
delete
publish
grade
```

### 3. Which resource?

```text
Which object are they trying to access?
```

For example:

```text
course_123
quiz_456
user_789
```

Then authorization becomes:

```text
User
 +
Action
 +
Resource
 ↓
Allowed?
```

This is a powerful mental model.

---

# 6. Example: Student Profile

Request:

```http
GET /api/v1/users/user_123
```

Suppose the authenticated user is:

```text
user_123
```

Then:

```text
User = user_123
Resource = user_123
Action = read
```

Allowed.

But:

```text
Authenticated user = user_123
Resource = user_456
Action = read
```

might not be allowed.

This is called **resource-level authorization** or **ownership authorization**, depending on the exact rule.

---

# 7. Role-Based Access Control

One of the simplest authorization models is:

> **RBAC — Role-Based Access Control**

Instead of giving every user individual permissions, assign a role.

For example:

```text
STUDENT
INSTRUCTOR
ADMIN
```

Then define what each role can do.

---

# 8. Simple RBAC Table

For our LMS:

|Action|Student|Instructor|Admin|
|---|--:|--:|--:|
|View courses|✅|✅|✅|
|Enroll in course|✅|❌/optional|✅|
|Create course|❌|✅|✅|
|Edit own course|❌|✅|✅|
|Edit any course|❌|❌|✅|
|Delete own course|❌|Maybe|✅|
|Delete any course|❌|❌|✅|
|Manage users|❌|❌|✅|
|Take quiz|✅|❌/optional|✅|
|Grade students|❌|✅|✅|

The exact permissions are a **business decision**.

Don't assume that a role automatically gives permission to everything.

---

# 9. Role Is Not Permission

This distinction is important.

A role:

```text
INSTRUCTOR
```

is a grouping.

A permission:

```text
course:update
```

is an actual capability.

So:

```text
Role
 ↓
Permissions
 ↓
Actions
```

For example:

```text
INSTRUCTOR
    ↓
course:create
course:update
quiz:create
submission:grade
```

---

# 10. Why Permissions Are Better Than Huge Role Checks

You could write:

```typescript
if (user.role === "ADMIN") {
  // allow
}
```

everywhere.

But eventually you'll have:

```text
ADMIN
INSTRUCTOR
STUDENT
TEACHING_ASSISTANT
CONTENT_REVIEWER
MODERATOR
SUPPORT_AGENT
```

and your code becomes:

```text
if ADMIN
else if INSTRUCTOR
else if MODERATOR
else if ...
```

This becomes difficult to maintain.

Instead:

```text
User
 ↓
Role
 ↓
Permissions
 ↓
Policy
```

is more scalable.

---

# 11. Basic Permission Naming

A useful convention is:

```text
resource:action
```

Examples:

```text
course:read
course:create
course:update
course:delete

quiz:read
quiz:create
quiz:update
quiz:delete

user:read
user:update
user:delete

submission:read
submission:grade
```

This is simple and readable.

---

# 12. More Specific Permissions

Sometimes we need:

```text
course:update:any
course:update:own
```

or:

```text
user:read:any
user:read:own
```

But don't overcomplicate permissions too early.

Start with:

```text
course:update
```

and use ownership rules separately when appropriate.

---

# 13. Ownership Authorization

This is extremely important for an LMS.

Suppose Priya is an instructor:

```text
userId = instructor_123
```

She owns:

```text
Course A
Course B
```

But not:

```text
Course C
```

So:

```http
PATCH /api/v1/courses/course_A
```

should be allowed.

But:

```http
PATCH /api/v1/courses/course_C
```

should be rejected.

Even though:

```text
role = INSTRUCTOR
```

is valid.

This is **ownership-based authorization**.

---

# 14. Role + Ownership

Real applications often combine multiple authorization rules.

For example:

```text
Can update course?
```

The policy could be:

```text
ADMIN
   OR
(INSTRUCTOR AND owns course)
```

So:

```text
ADMIN
→ yes

INSTRUCTOR + own course
→ yes

INSTRUCTOR + someone else's course
→ no

STUDENT
→ no
```

This is much more realistic than pure RBAC.

---

# 15. Example Authorization Logic

Conceptually:

```typescript
function canUpdateCourse(user, course) {
  if (user.role === "ADMIN") {
    return true;
  }

  if (
    user.role === "INSTRUCTOR" &&
    course.instructorId === user.id
  ) {
    return true;
  }

  return false;
}
```

Notice:

```text
role
+
resource ownership
```

are both checked.

---

# 16. Never Trust `userId` From the Request

This is one of the most important backend security rules.

Suppose the frontend sends:

```json
{
  "userId": "user_456"
}
```

You should not use this as the authenticated identity.

The authenticated identity comes from:

```text
Verified Access Token
        ↓
req.user.id
```

So:

```text
❌ req.body.userId
```

should not decide:

> "Who is making this request?"

Instead:

```text
✅ req.user.id
```

comes from authenticated server-side context.

---

# 17. Example: Update Profile

Bad:

```typescript
await userRepository.update(
  req.body.userId,
  req.body
);
```

An attacker can simply send:

```json
{
  "userId": "someone_else"
}
```

Better:

```typescript
await userRepository.update(
  req.user.id,
  req.body
);
```

Now the server determines identity.

---

# 18. Authorization Middleware

We can create middleware like:

```typescript
requireRole("ADMIN")
```

Conceptually:

```typescript
function requireRole(role: Role) {
  return (req, res, next) => {
    if (req.user.role !== role) {
      throw new ForbiddenError();
    }

    next();
  };
}
```

Then:

```text
POST /admin/users
        ↓
requireRole("ADMIN")
        ↓
Controller
```

This is useful for simple role-based rules.

---

# 19. Multiple Roles

Sometimes:

```text
ADMIN
OR
INSTRUCTOR
```

can access an endpoint.

We could create:

```typescript
requireRole(
  "ADMIN",
  "INSTRUCTOR"
);
```

Conceptually:

```typescript
if (!allowedRoles.includes(req.user.role)) {
  throw new ForbiddenError();
}
```

This is convenient for coarse-grained authorization.

---

# 20. But Don't Put Everything in Middleware

Here's an important architectural point.

This is good:

```text
requireRole("ADMIN")
```

for:

```text
/admin/users
```

But ownership checks often need database data.

For example:

```text
PATCH /courses/:courseId
```

We need:

```text
course.instructorId
```

Middleware doesn't necessarily need to fetch the course.

A better pattern can be:

```text
Controller
   ↓
Service
   ↓
Load resource
   ↓
Authorization policy
   ↓
Update
```

This keeps business rules close to the operation.

---

# 21. Authorization Service / Policy

We can create functions such as:

```typescript
canUpdateCourse(user, course)
canDeleteCourse(user, course)
canViewSubmission(user, submission)
canGradeSubmission(user, submission)
```

Then:

```text
Course Service
     ↓
canUpdateCourse()
     ↓
Repository
```

This makes authorization rules reusable and testable.

---

# 22. Policy-Based Thinking

Instead of thinking:

```text
if role === ADMIN
```

think:

```text
Policy:
Who can perform action X on resource Y?
```

For example:

```text
Policy:
course:update
```

Inputs:

```text
user
course
```

Output:

```text
true / false
```

This is a much more scalable mental model.

---

# 23. `401` vs `403`

You absolutely need to know this.

### `401 Unauthorized`

Usually means:

> The request does not have valid authentication credentials.

Examples:

```text
No access token
Expired access token
Invalid access token
```

Conceptually:

```text
Who are you?
→ I don't have a valid answer.
```

---

### `403 Forbidden`

Usually means:

> The server knows who you are, but you aren't allowed to perform this action.

Example:

```text
Student
 ↓
DELETE /courses/123
 ↓
Authenticated ✅
Authorized ❌
 ↓
403
```

Mental model:

```text
401 → "I don't know/accept who you are."

403 → "I know who you are, but you can't do this."
```

---

# 24. Example

Request:

```http
GET /api/v1/admin/users
```

No access token:

```text
401 Unauthorized
```

Valid student token:

```text
Authentication ✅
Authorization ❌
```

Response:

```text
403 Forbidden
```

Valid admin token:

```text
Authentication ✅
Authorization ✅
```

Continue.

# 25. RBAC in the Database

We have two choices.

### Simple approach

Put a role directly on the user:

```prisma
enum Role {
  STUDENT
  INSTRUCTOR
  ADMIN
}

model User {
  id   String @id @default(uuid())
  role Role   @default(STUDENT)
}
```

This is excellent for our first version.

---

# 26. Why Start Simple?

You don't need:

```text
Role
RolePermission
Permission
UserRole
UserPermission
```

on day one.

That can become unnecessary complexity.

For our AI LMS, begin with:

```text
User
 ↓
Role
```

Then introduce more advanced permission structures when the application's requirements actually need them.

This is an important engineering principle:

> **Don't build an authorization framework before you understand the authorization requirements.**

Suppose later we need:

```text
ADMIN
CONTENT_MANAGER
INSTRUCTOR
TEACHING_ASSISTANT
MODERATOR
SUPPORT
```

and administrators should be able to configure permissions dynamically.

Then we might move toward:

```text
User
 ↓
UserRole
 ↓
Role
 ↓
RolePermission
 ↓
Permission
```

Conceptually:

```text
User
  │
  ▼
Role
  │
  ▼
Permissions
```

This is more flexible but more complex.

# 28. RBAC vs Ownership

Let's compare.

### RBAC

Answers:

```text
What can this role generally do?
```

Example:

```text
INSTRUCTOR
→ course:create
```

### Ownership

Answers:

```text
Does this user own this particular resource?
```

Example:

```text
course.instructorId === user.id
```

Real applications frequently need both.

---

# 29. RBAC + Ownership

Our LMS might use:

```text
                         Authorization
                               │
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
                RBAC                    Ownership
                 │                           │
          "Can instructors             "Does this
           update courses?"              instructor
                                         own course?"
                 │                           │
                 └─────────────┬─────────────┘
                               ▼
                             ALLOW
```

This is a much more realistic architecture.

POST /api/v1/courses

# 32. Example: Course Delete

Policy:

```text
ADMIN
OR
INSTRUCTOR who owns course
```

But perhaps your business rules say instructors aren't allowed to delete published courses.

Now the policy becomes:

```text
ADMIN
OR
(
  INSTRUCTOR
  AND owns course
  AND course.status != PUBLISHED
)
```

See how authorization is becoming a business rule?

This is why authorization deserves careful architecture.

# 33. Resource State Matters

Suppose:

```text
Course status:
DRAFT
```

Instructor owns it.

Delete:

```text
Allowed
```

But:

```text
Course status:
PUBLISHED
```

Delete:

```text
Maybe not allowed
```

Therefore authorization may depend on:

```text
User
+
Role
+
Ownership
+
Resource state
+
Action
```

This leads us toward more advanced authorization models.

---

# 34. ABAC

Another authorization model is:

> **Attribute-Based Access Control**

Instead of only:

```text
role = INSTRUCTOR
```

we consider attributes.

For example:

```text
User:
role = INSTRUCTOR
department = COMPUTER_SCIENCE

Course:
department = COMPUTER_SCIENCE
status = DRAFT
```

Policy:

```text
Instructor can edit
if:

role == INSTRUCTOR
AND
user.department == course.department
AND
course.status == DRAFT
```

Now we're using attributes.

---

# 35. RBAC vs ABAC

||RBAC|ABAC|
|---|---|---|
|Main idea|Roles|Attributes|
|Simplicity|High|Lower|
|Example|ADMIN can manage users|Instructor can edit courses in their department|
|Good for|Basic permissions|Complex policies|
|Flexibility|Medium|High|
|Complexity|Lower|Higher|

We don't need full ABAC in the first version of our LMS.

But you should understand it.

---

# 36. Relationship-Based Authorization

Another interesting model is:

> **Relationship-Based Access Control**

For example:

```text
User
 ↓
instructor_of
 ↓
Course
```

Then:

```text
Can user edit course?
```

becomes:

```text
Is user an instructor of this course?
```

This is essentially the relationship:

```text
user --instructor_of--> course
```

Our ownership check is already a simple form of relationship-based authorization.

---

# 37. Why This Matters for AI LMS

Our LMS has many relationships:

```text
Student
 ├── enrolled_in → Course
 ├── submitted → Quiz
 └── owns → Progress

Instructor
 ├── teaches → Course
 └── grades → Submission

Admin
 └── manages → Platform
```

So authorization will naturally become relationship-heavy.

For example:

```text
Can Student X view Course Y?
```

Maybe:

```text
Course is public
OR
Student is enrolled
```

That's more than just:

```text
role === STUDENT
```

---

# 38. Example: Course Access

Suppose:

```text
Student A
Course X
```

Policy:

```text
Can view course content?
```

Possible rule:

```text
course.isPublished
AND
(
  course.isPublic
  OR enrollment exists
)
```

Now authorization depends on:

```text
Role
+
Course state
+
Enrollment relationship
```

This is exactly why authorization needs to be designed carefully.

# 39. Don't Put Authorization in the Frontend

This is a very common mistake.

You might hide a button:

```jsx
{user.role === "ADMIN" && (
  <DeleteButton />
)}
```

That's good for UX.

But it is **not security**.

An attacker can simply call:

```http
DELETE /api/v1/users/123
```

manually.

Therefore:

```text
Frontend authorization
→ UX

Backend authorization
→ Security
```

You need the backend check.

---

# 40. Defense in Depth

The frontend can say:

```text
Don't show this button.
```

The backend must say:

```text
Don't allow this operation.
```

So:

```text
Frontend
   ↓
Hide unavailable actions

Backend
   ↓
Enforce authorization
```

Both are useful.

---

# 41. Authorization at the Service Layer

For your architecture, I recommend thinking like this:

```text
Controller
   ↓
Service
   ↓
Authorization Policy
   ↓
Repository
```

For example:

```typescript
async function updateCourse(
  user: AuthenticatedUser,
  courseId: string,
  input: UpdateCourseInput
) {
  const course = await courseRepository.findById(courseId);

  if (!course) {
    throw new NotFoundError("Course not found");
  }

  if (!canUpdateCourse(user, course)) {
    throw new ForbiddenError();
  }

  return courseRepository.update(courseId, input);
}
```

This is much better than putting authorization logic into the React frontend.

---

# 42. Don't Query More Than Necessary

Suppose the policy only requires:

```text
course.instructorId
```

Don't load:

```text
course
├── instructor
├── students
├── quizzes
├── lessons
├── progress
└── AI conversations
```

just to check ownership.

Query only what the policy needs.

For example:

```text
SELECT id, instructorId
FROM courses
WHERE id = ?
```

Then authorize.

This is both cleaner and more efficient.

---

# 43. Authorization and Repository Queries

Sometimes authorization can be enforced directly in the database query.

For example:

```typescript
await prisma.course.updateMany({
  where: {
    id: courseId,
    instructorId: user.id,
  },
  data: input,
});
```

Then:

```text
updated count = 1
→ authorized + updated

updated count = 0
→ not found or not allowed
```

This can be a very powerful pattern.

However, don't blindly combine every authorization rule into database queries. Complex policies are often clearer as explicit policy/service logic.

---

# 44. The "Query Then Check" Pattern

Common:

```text
1. Load resource
2. Check permission
3. Perform operation
```

Example:

```typescript
const course = await courseRepository.findById(courseId);

if (!canUpdateCourse(user, course)) {
  throw new ForbiddenError();
}

await courseRepository.update(courseId, input);
```

Very readable.

---

# 45. The "Authorize in Query" Pattern

Alternative:

```typescript
const result = await prisma.course.updateMany({
  where: {
    id: courseId,
    instructorId: user.id,
  },
  data: input,
});
```

This gives:

```text
Authorization condition
+
Data mutation
```

in one database operation.

This can reduce race conditions between:

```text
check
```

and:

```text
update
```

But error semantics need careful handling.

---

# 46. Time-of-Check vs Time-of-Use

Here's an advanced backend concept.

Suppose:

```text
1. Check user owns course
2. Another transaction changes ownership
3. Update course
```

Now the authorization decision was based on stale state.

This is called a:

> **TOCTOU — Time-of-Check to Time-of-Use** problem.

Database transactions and appropriately designed conditional operations can reduce these issues.

Again, your Phase 3 database knowledge directly matters here.

---

# 47. Authorization Is a Business Rule

Don't think of authorization as just middleware.

For example:

```text
"Only instructors can create courses."
```

is a business rule.

And:

```text
"An instructor can only edit courses they own."
```

is another business rule.

And:

```text
"Published courses can only be modified by admins."
```

is another.

So authorization belongs close to the **domain/service layer**, even if some coarse role checks are implemented as middleware.

---

# 48. Coarse vs Fine-Grained Authorization

### Coarse

```text
/admin/*
 ↓
requireRole(ADMIN)
```

Easy.

### Fine-grained

```text
PATCH /courses/:id
 ↓
Is instructor?
 ↓
Does instructor own course?
 ↓
Is course editable?
```

More complex.

A good architecture often uses:

```text
Middleware
→ coarse checks

Service/policy
→ fine-grained checks
```

---

# 49. Authorization Error Handling

Don't leak internal information.

Bad:

```json
{
  "error": "Course belongs to instructor user_987 and you are user_123"
}
```

This leaks information.

Prefer something like:

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "You are not allowed to perform this action."
  }
}
```

For resources that shouldn't be revealed, a `404` may sometimes be preferable.

---

# 50. Don't Confuse Hiding With Security

This:

```css
display: none;
```

is not authorization.

This:

```jsx
if (!isAdmin) return null;
```

is not authorization.

This:

```text
POST /admin/delete-user
```

must still be protected on the server.

The attacker doesn't need your UI.

They can use:

```text
curl
Postman
browser DevTools
custom scripts
```

Therefore:

> **The API is the security boundary.**

Our LMS has an AI layer.

Imagine:

```text
POST /api/v1/ai/chat
```

Can a student access another student's AI conversation?

Obviously:

❌

# 52. Admin Does Not Mean "Skip All Checks"

A naive implementation:

```typescript
if (user.role === "ADMIN") {
  return true;
}
```

everywhere can be dangerous.

Sometimes an admin should have broad access.

But some operations may require:

```text
explicit permission
audit logging
confirmation
two-person approval
```

depending on the system.

For our LMS, we'll keep admin powerful, but still structure authorization explicitly.

# 53. Role Hierarchy Is Not Always Safe

You might think:

```text
ADMIN > INSTRUCTOR > STUDENT
```

But roles aren't always a simple hierarchy.

For example:

```text
CONTENT_REVIEWER
```

may be allowed to:

```text
review courses
```

but not:

```text
manage users
```

And:

```text
SUPPORT_AGENT
```

might be allowed to:

```text
view account metadata
```

but not:

```text
change passwords
```

So don't automatically assume:

```text
higher role = every lower-role permission
```

unless your business model explicitly defines that.

# 55. Authorization Testing

Every authorization rule should have tests.

For:

```text
course:update
```

test:

```text
Student + own course
→ ❌

Instructor + own course
→ ✅

Instructor + another course
→ ❌

Admin + any course
→ ✅
```

This is much better than testing only:

```text
"Admin works."
```

Authorization bugs are often caused by missing negative tests.

---

# 56. Negative Tests Are Extremely Important

Security testing asks:

> "Can an attacker do something they shouldn't?"

For example:

```text
Student → delete course
Student → access another user's progress
Instructor → edit another instructor's course
User A → revoke User B's session
```

All must fail.

In security engineering:

```text
Positive tests
+
Negative tests
```

are both essential.

# 57. Authorization Checklist

For every protected endpoint, ask:

```text
1. Is authentication required?

2. Who is the authenticated user?

3. What action is being attempted?

4. What resource is being accessed?

5. What role/permission is required?

6. Does ownership matter?

7. Does resource state matter?

8. Can the client manipulate identity fields?

9. Is the authorization check performed server-side?

10. Is there a negative test?
```

This checklist will become extremely useful during the later security phase.

# 🧠 Interview-Level Question

### "What's the difference between authentication and authorization?"

A strong answer:

> Authentication establishes the identity of the requester, while authorization determines whether that authenticated identity is allowed to perform a particular action on a particular resource. In an API, authentication might verify an access token and populate the authenticated user, while authorization could then check the user's role, permissions, resource ownership, and resource state before allowing the operation.

That's the answer you should remember.

# 🎯 Lesson 4.10 Takeaways

```text
1. Authentication asks:
   "Who are you?"

2. Authorization asks:
   "What are you allowed to do?"

3. A valid JWT does not automatically grant permission.

4. RBAC uses roles such as:
   STUDENT
   INSTRUCTOR
   ADMIN

5. Permissions represent actual capabilities.

6. Ownership checks determine whether a user controls
   a particular resource.

7. Real applications often combine:
   Role + Permission + Ownership + Resource State.

8. Never trust client-supplied userId for authentication.

9. Backend authorization is mandatory.
   Frontend checks are only for UX.

10. 401 usually means authentication failed.

11. 403 usually means authentication succeeded but
    authorization failed.

12. Coarse authorization can live in middleware.

13. Fine-grained authorization usually belongs in
    services/policies.

14. Database queries can sometimes enforce ownership
    directly.

15. Authorization rules need strong negative tests.
```
