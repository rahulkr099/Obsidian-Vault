# 🔐 Phase 4 — Lesson 4.11: RBAC in Practice

In **Lesson 4.10**, we learned the theory:

```text
Authentication
      ↓
Authorization
      ↓
Role
      ↓
Permission
      ↓
Ownership
      ↓
Resource state
      ↓
Allow / Deny
```

Now let's actually design this for our **AI LMS backend**.

Our goal is not to build an unnecessarily complicated authorization framework. We want something that is:

- easy to understand
    
- secure
    
- testable
    
- scalable
    
- compatible with our **Controller → Service → Repository** architecture
    

---

# 1. Our AI LMS Roles

We'll start with three main roles:

```text
STUDENT
INSTRUCTOR
ADMIN
```

Later, we could add:

```text
CONTENT_REVIEWER
TEACHING_ASSISTANT
MODERATOR
SUPPORT_AGENT
```

But don't add roles just because they sound useful.

A role should exist because the application has a real authorization requirement for it.

# 2. Start With a Simple Prisma Role

For our current architecture:

```prisma
enum Role {

  ADMIN

model User {
  id        String   @id @default(uuid())

  password  String

  updatedAt DateTime @updatedAt

  sessions Session[]

```

This is enough for our first RBAC implementation.

We don't need five additional tables yet.

# 3. What Should Each Role Do?

Let's create a rough permission matrix.

|Permission|Student|Instructor|Admin|
|---|--:|--:|--:|
|`course:read`|✅|✅|✅|
|`course:create`|❌|✅|✅|
|`course:update`|❌|Own|Any|
|`course:delete`|❌|Own|Any|
|`quiz:take`|✅|❌|Maybe|
|`quiz:create`|❌|✅|✅|
|`submission:read`|Own|Assigned|Any|
|`submission:grade`|❌|Assigned|Any|
|`progress:read`|Own|Assigned students|Any|
|`user:read`|Own|Limited|Any|
|`user:update`|Own|❌|Any|

Notice something important:

**A permission isn't always simply yes/no.**

For example:

```text
course:update
```

could mean:

```text
Instructor → own courses
Admin       → any course
```

That's why we'll combine **RBAC + ownership/policy checks**.

Don't scatter strings throughout your code.

Avoid:


everywhere.

# 6. Why Keep This in Code?

Because our permissions are currently application rules.

For example:

```text
INSTRUCTOR
→ can create courses
```

isn't something the user needs to configure.

It's part of our application's design.

Putting it in code gives us:

```text
simple
type-safe
version controlled
easy to test
```

Later, if we need administrators to dynamically configure permissions, we can move this into PostgreSQL.

# 7. Permission Checking Function

Now create:

```typescript
function hasPermission(
  role: Role,
  permission: string
): boolean {
  return ROLE_PERMISSIONS[role].includes(permission);
}
```

Then:

```typescript
hasPermission(
  "INSTRUCTOR",
  "course:create"
);
```

returns:

```text
true
```

while:

```typescript
hasPermission(
  "STUDENT",
  "course:create"
);
```

returns:

```text
false
```

# 8. Type Safety

Since we're using TypeScript, we can make this stronger.

```typescript
export const PERMISSIONS = {
  COURSE_READ: "course:read",
  COURSE_CREATE: "course:create",
  COURSE_UPDATE: "course:update",
  COURSE_DELETE: "course:delete",

  QUIZ_TAKE: "quiz:take",
  QUIZ_CREATE: "quiz:create",

  SUBMISSION_READ: "submission:read",
  SUBMISSION_GRADE: "submission:grade",

  PROGRESS_READ: "progress:read",

  USER_READ: "user:read",
  USER_UPDATE: "user:update",
} as const;

export type Permission =
  typeof PERMISSIONS[keyof typeof PERMISSIONS];
```

Now:

```typescript
Permission
```

is a union of valid permission strings.

This prevents accidental values like:

```text
"course:creat"
```

from silently spreading through your code.

# 9. Permission Middleware

Now we can create:

```typescript
requirePermission(permission)
```

Conceptually:

```typescript
function requirePermission(
  permission: Permission
) {
  return (req, res, next) => {
    const user = req.user;

    if (!user) {
      throw new UnauthorizedError();
    }

    if (!hasPermission(user.role, permission)) {
      throw new ForbiddenError();
    }

    next();
  };
}
```

Now our route becomes:

```typescript
router.post(
  "/courses",
  authenticate,
  requirePermission(PERMISSIONS.COURSE_CREATE),
  courseController.create
);
```

That's much cleaner than putting authorization directly into the controller.

The request now looks like:

# 11. `authenticate` vs `requirePermission`

Don't mix these.

### `authenticate`

Answers:

```text
Who is the user?
```

Example:

```text
JWT
 ↓
verify
 ↓
req.user
```

### `requirePermission`

Answers:

```text
Can this user's role perform this operation?
```

Example:

```text
req.user.role
 ↓
permission lookup
 ↓
allow/deny
```

This separation is very useful.

# 12. Role Middleware

Sometimes we don't even need a permission.

For example:

```text
/admin/users
```

might simply require:

```text
ADMIN
```

We can create:

```typescript
requireRole("ADMIN")
```

Example:

```typescript
router.get(
  "/admin/users",
  authenticate,
  requireRole("ADMIN"),
  adminController.listUsers
);
```

This is appropriate for coarse-grained access.

---

# 13. When to Use `requireRole`

Use it for things like:

```text
/admin/*
```

or:

```text
/admin/system-settings
```

where the rule is fundamentally:

```text
Only administrators.
```

Don't use role middleware for every authorization decision.

---

# 14. When to Use `requirePermission`

Use permissions when you want:

```text
course:create
quiz:create
submission:grade
```

For example:

```typescript
router.post(
  "/courses",
  authenticate,
  requirePermission(PERMISSIONS.COURSE_CREATE),
  courseController.create
);
```

This makes your routes self-documenting.

Someone reading the route immediately understands:

```text
course:create
```

---

# 15. But Here's the Problem

Consider:

```typescript
router.patch(
  "/courses/:courseId",
  authenticate,
  requirePermission(PERMISSIONS.COURSE_UPDATE),
  courseController.update
);
```

This checks:

```text
Does this role have course:update?
```

But it doesn't answer:

> Does this instructor own **this particular course**?

That's where policy logic comes in.

---

# 16. Permission ≠ Authorization Decision

Suppose:

```text
INSTRUCTOR
```

has:

```text
course:update
```

But:

```text
course.instructorId = instructor_B
```

while:

```text
req.user.id = instructor_A
```

Then:

```text
Permission → YES
Ownership  → NO
```

Final decision:

```text
DENY
```

Therefore:

```text
Permission
+
Resource policy
=
Final authorization
```

# 17. Course Policy

Let's create:

```typescript
function canUpdateCourse(
  user: AuthenticatedUser,
  course: Course
): boolean {
  if (user.role === "ADMIN") {
    return true;
  }

  if (
    user.role === "INSTRUCTOR" &&
    course.instructorId === user.id
  ) {
    return true;
  }

  return false;
}
```

Now the business rule is explicit.

---

# 18. Course Service

Our service can use the policy:

```typescript
async function updateCourse(
  user: AuthenticatedUser,
  courseId: string,
  input: UpdateCourseInput
) {
  const course =
    await courseRepository.findById(courseId);

  if (!course) {
    throw new NotFoundError("Course not found");
  }

  if (!canUpdateCourse(user, course)) {
    throw new ForbiddenError();
  }

  return courseRepository.update(
    courseId,
    input
  );
}
```

This is a very good place for fine-grained authorization.

---

# 19. Why Service Instead of Controller?

We could write:

```typescript
if (req.user.role === "ADMIN") ...
```

inside the controller.

But then your controller becomes responsible for:

```text
HTTP
authorization
business logic
database interaction
```

Instead:

```text
Controller
   ↓
Service
   ↓
Policy
   ↓
Repository
```

keeps the architecture clean.

---

# 20. Policy Functions Should Be Small

Good:

```typescript
canUpdateCourse(user, course)
```

Bad:

```typescript
megaAuthorizationFunction(
  user,
  action,
  resource,
  database,
  request,
  environment,
  ...
)
```

Start with simple functions.

A policy should ideally answer:

```text
true / false
```

without doing unrelated work.

Let's define it clearly:

```text

→ any course

→ own course
```

```text
               Own      Other
```

Notice:

### Create course

Policy:

```text

```

Therefore:

```text

```

may be enough.

### Update course

Course already exists.

Policy:

```text
ADMIN
OR

```

Therefore:

```text

```

# 24. Delete Course

Let's define:

```typescript
function canDeleteCourse(
  user: AuthenticatedUser,
  course: Course
) {
  if (user.role === "ADMIN") {
    return true;
  }

  if (
    user.role === "INSTRUCTOR" &&
    course.instructorId === user.id &&
    course.status === "DRAFT"

    return true;
  }

  return false;
}
```

Now we added:

```text
role
+
ownership
+

```

That's a real authorization policy.

# 27. Submission Policy

Conceptually:

```typescript
function canViewSubmission(
  user,
  submission
) {
  if (user.role === "ADMIN") {
    return true;
  }

  if (submission.studentId === user.id) {
    return true;
  }

  if (
    user.role === "INSTRUCTOR" &&
    submission.course.instructorId === user.id
  ) {
    return true;
  }

  return false;
}
```

Now we have:

```text
Admin
+
Student ownership
+
Instructor relationship
```

# 28. Don't Put Huge Relationship Trees in JWT

You might be tempted to put:

```json
{
  "id": "user_123",
  "role": "INSTRUCTOR",
  "courseIds": [
    "course_1",
    "course_2",
    "course_3"
  ]
}
```

into the JWT.

Don't.

Why?

Because course relationships can change.

Suppose:

```text
Instructor A
→ owns Course X
```

JWT contains:

```text
course_X
```

Later the admin transfers Course X to Instructor B.

The old JWT might still say:

```text
course_X
```

Now authorization data is stale.

Better:

```text
JWT
→ identity + basic claims

Database
→ current relationships
```

---

# 29. What Should Go in the JWT?

Keep claims relatively small.

For example:

```json
{
  "sub": "user_123",
  "role": "INSTRUCTOR",
  "iat": 1786700000,
  "exp": 1786700900
}
```

Potentially:

```text
permissions
```

if they are stable and you understand the invalidation implications.

But don't turn the JWT into your entire authorization database.

---

# 30. Role in JWT vs Database

If the JWT contains:

```text
role = INSTRUCTOR
```

and the database later changes:

```text
role = STUDENT
```

the old access token may still contain:

```text
INSTRUCTOR
```

until it expires.

This is one reason access tokens should be short-lived.

Another option is:

```text
tokenVersion
```

or server-side checks for high-risk operations.

For our initial LMS architecture:

```text
short-lived access token
+
refresh-session revocation
```

is a sensible balance.

---

# 31. Admin Role Changes

Suppose:

```text
Rahul
role = INSTRUCTOR
```

Admin changes:

```text
INSTRUCTOR → STUDENT
```

Existing access token:

```text
role = INSTRUCTOR
```

could remain valid temporarily.

A strong strategy is:

```text
Role change
 ↓
Revoke existing sessions
 ↓
User logs in again
 ↓
New tokens contain new role
```

This makes authorization changes take effect cleanly.

After authentication middleware:

```typescript
req.user
```

might contain:

```typescript

```

Example:

```json
{
  "id": "user_123",
  "role": "INSTRUCTOR"
```

This gives downstream services the minimum identity information they need.

# 33. Don't Put Full User Objects in `req.user`

Avoid:

```typescript
req.user = {
  id,
  email,
  password,
  profile,
  courses,
  sessions,
  ...

```

Instead:

```typescript

```

```text

 ↓

 ↓

```

# 34. `requireRole` Implementation

A clean version:

```typescript
function requireRole(...allowedRoles: Role[]) {
  return (req, res, next) => {
    if (!req.user) {
      throw new UnauthorizedError();
    }

    if (!allowedRoles.includes(req.user.role)) {
      throw new ForbiddenError();
    }

    next();
  };
}
```

Usage:

```typescript
router.get(
  "/admin/users",
  authenticate,
  requireRole("ADMIN"),
  adminController.listUsers
);
```

# 35. `requirePermission` Implementation

Conceptually:

```typescript
function requirePermission(
  permission: Permission

    if (
      !hasPermission(
```

# 39. What If the Course Doesn't Exist?

Request:

```http
PATCH /courses/does-not-exist
```

The service finds:

```text
null
```

Return:

```text
404 Not Found
```

Don't run an ownership check against a nonexistent resource.

Correct order:

```text
Load resource
 ↓
Does it exist?
 ↓
Authorization
 ↓
Operation
```

---

# 40. What If the Course Exists But Belongs to Someone Else?

Suppose:

```text
course_123
instructorId = instructor_B
```

and:

```text
req.user.id = instructor_A
```

Then:

```text
Resource exists
+
User authenticated
+
Permission exists
+
Ownership fails
```

Final result:

```text
403
```

Or, depending on your resource-enumeration policy, you may intentionally return `404`.

The important thing is that the API should not accidentally expose sensitive information.

# 41. Database-Level Authorization

Sometimes we can combine authorization with the query.

Example:

```typescript
const result =
  await prisma.course.updateMany({
    where: {
      id: courseId,
      instructorId: user.id,

    data: input,

```

If:

```text
count = 1
```

then:

```text
authorized + updated
```

If:

```text
count = 0
```

then:

```text
not found OR not owned
```

This can be useful for simple ownership rules.

# 42. When Not to Do This

Suppose authorization is:

```text
ADMIN
OR
INSTRUCTOR
AND owns course
AND course is draft
AND department matches
AND instructor is active
```

Trying to encode everything into one query can become difficult to understand.

At that point:

```text

 ↓

 ↓

```

is often clearer.

Choose clarity over cleverness.

# 50. When to Move Permissions Into PostgreSQL

Consider database-driven permissions if:

```text
Admins need to create roles dynamically
Admins need to change permissions without deployment
Different organizations have different roles
You are building multi-tenant authorization
Permissions vary significantly by tenant
```

For example:

```text
Tenant A:
Instructor can delete courses.

```

Now static code becomes less convenient.

That's when a database-backed authorization model starts making sense.

# 52. The Golden Rule

Here's the rule I want you to remember:

> **Never authorize based only on what the client claims. Authorize based on authenticated identity and server-side state.**

Bad:

```text
req.body.userId
req.body.role
req.body.isAdmin
```

Good:

```text
verified token
     ↓
req.user.id
req.user.role
     ↓
database resource
     ↓
policy
```

This single principle prevents many authorization vulnerabilities.

# 🧠 Interview Question

### "How would you implement RBAC in a Node.js + TypeScript application?"

A strong answer:

> I would store a user's role, such as STUDENT, INSTRUCTOR, or ADMIN, and map each role to a set of permissions. Authentication middleware would verify the access token and attach the authenticated user's identity to the request. Coarse-grained checks could use `requireRole()` or `requirePermission()` middleware. For resource-specific authorization, such as allowing an instructor to edit only their own course, I would perform the check in a service-level policy using the authenticated user and server-side resource data. I would also test both positive and negative authorization cases.

That's a strong practical answer.

# 🎯 Lesson 4.11 Takeaways

```text
1. Start RBAC with simple roles.

2. Keep permissions centralized.

3. Use TypeScript constants/types for permissions.

4. requireRole() is useful for coarse authorization.

5. requirePermission() is useful for permission-based routes.

6. Permission checks don't automatically handle ownership.

7. Resource-specific rules belong in policies/services.

8. Example:
   ADMIN → any course
   INSTRUCTOR → own course
   STUDENT → no update

9. Don't trust userId, role, or admin flags from request bodies.

10. req.user should come from verified authentication.

11. Don't put large authorization state inside JWTs.

12. Database relationships should be checked when necessary.

13. Frontend authorization improves UX but does not provide security.

14. Test authorization failures aggressively.

15. Don't build a complex permission database until the
    application's requirements justify it.
```
