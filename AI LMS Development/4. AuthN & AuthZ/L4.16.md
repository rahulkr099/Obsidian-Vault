# 🔐 Phase 4 — Lesson 4.16: OAuth Account Linking, Identity Mapping & Provider Strategy

In **Lesson 4.15**, we learned how OAuth/OIDC works:

```text
User
 ↓
Google
 ↓
Authorization Code
 ↓
Backend
 ↓
Validate identity
 ↓
LMS User
 ↓
Our Session
```

Now we're going deeper into one of the **most important real-world problems**:

> **How do we correctly connect a Google/GitHub/Microsoft account to our own `User` record?**

This sounds simple:

```text
Google → User
```

But in production, this is where account takeover, duplicate accounts, and broken authentication systems can happen.

---

# 1. The Core Problem

Suppose our LMS has:

```text
User #101
email = rahul@example.com
```

Rahul registered using:

```text
Email + Password
```

Later he clicks:

```text
Continue with Google
```

Google gives us:

```text
email = rahul@example.com
sub = 123456789
```

What should we do?

There are several possibilities:

```text
A. Create a new User
B. Find User by email
C. Link Google to existing User
D. Ask user to authenticate existing account first
```

Choosing incorrectly can create serious security problems.

---

# 2. Separate `User` From `Account`

This is the most important database design idea in this lesson.

Don't design:

```prisma
model User {
  googleId    String?
  githubId    String?
  microsoftId String?
}
```

This becomes messy very quickly.

Instead:

```text
User
 │
 ├── Account → Google
 ├── Account → GitHub
 └── Account → Microsoft
```

Think:

> **User = LMS identity**

> **Account = authentication identity from an external provider**

---

# 3. Our `User` Model

Our core user remains:

```prisma
model User {
  id            String   @id @default(uuid())

  email         String   @unique
  passwordHash  String?

  emailVerified Boolean  @default(false)

  mfaEnabled    Boolean  @default(false)

  role          Role     @default(STUDENT)

  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  accounts      Account[]
  sessions      Session[]
}
```

Notice:

```text
passwordHash?
```

Why optional?

Because a user created exclusively through Google might initially have:

```text
passwordHash = null
```

They authenticate through Google instead.

---

# 4. The `Account` Model

Now:

```prisma
model Account {
  id                String   @id @default(uuid())

  userId            String

  provider          String
  providerAccountId String

  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  @@unique([provider, providerAccountId])
  @@index([userId])
}
```

For example:

```text
Account
────────────────────────────
provider          GOOGLE
providerAccountId 1092837...
userId            user_123
```

---

# 5. Why `providerAccountId`?

Google may provide:

```text
sub = "109283749812..."
```

GitHub may provide:

```text
id = 982374
```

Microsoft may provide another identifier.

These are **provider-specific external identifiers**.

Our database normalizes them into:

```text
provider
+
providerAccountId
```

For example:

```text
GOOGLE + 12345
GITHUB + 98234
```

---

# 6. Why Not Use Email as the External Identity?

Because email addresses can change.

Consider:

```text
Google Account
sub = 12345
email = rahul@gmail.com
```

Later:

```text
email = rahulkumar@gmail.com
```

The provider's stable subject identifier can remain:

```text
sub = 12345
```

So:

```text
provider + providerAccountId
```

is much better for identifying the external account.

---

# 7. The Unique Constraint

This is critical:

```prisma
@@unique([provider, providerAccountId])
```

It guarantees:

```text
GOOGLE + 12345
```

can belong to only one LMS account.

Without this constraint, a bug could create:

```text
Google 12345
   ↓
User A

Google 12345
   ↓
User B
```

That's unacceptable.

---

# 8. One User Can Have Multiple Accounts

Our design allows:

```text
User 123
 │
 ├── Password
 │
 ├── Google
 │
 ├── GitHub
 │
 └── Microsoft
```

This gives the user multiple ways to authenticate.

For example:

```text
Continue with Google
Continue with GitHub
Email + Password
```

All lead to:

```text
User 123
```

and therefore the same:

```text
courses
progress
certificates
AI conversations
enrollments
```

---

# 9. Authentication Identity vs Application Identity

This distinction is extremely important.

### External identity

```text
Google
sub = 12345
```

### LMS identity

```text
User
id = user_123
```

The relationship is:

```text
Google
  ↓
Account
  ↓
User
```

The LMS should use:

```text
user.id
```

for internal ownership and authorization.

Not:

```text
google.sub
```

---

# 10. Why This Matters for Course Ownership

Suppose:

```text
Google sub = 12345
LMS user = user_123
```

Rahul creates:

```text
Course
id = course_456
ownerId = user_123
```

Later he logs in using GitHub.

GitHub:

```text
sub = 98765
```

If GitHub is linked to the same user:

```text
GitHub
 ↓
Account
 ↓
user_123
```

Rahul still owns:

```text
course_456
```

That's exactly what we want.

# 11. First OAuth Login

Let's design it carefully.

Rahul clicks:

```text
Continue with Google
```

Google authenticates him.

Our backend receives:

```text
provider = GOOGLE
providerAccountId = 12345
email = rahul@example.com
```

First step:

```text
Find Account
WHERE
provider = GOOGLE
AND
providerAccountId = 12345
```

---

# 12. Case 1 — Account Exists

Suppose we find:

```text
Account
provider = GOOGLE
providerAccountId = 12345
userId = user_123
```

Then:

```text
Account
 ↓
User 123
 ↓
Create Session
```

Very simple.

No new account.

No duplicate user.

---

# 13. Returning Login Flow

```text
Google
 ↓
Google identity
 ↓
Find Account
 ↓
Found
 ↓
Find User
 ↓
Check account status
 ↓
Create Session
 ↓
Access Token
```

Notice:

> We don't search for the user by email first.

We already know the external identity.

---

# 14. Case 2 — Account Doesn't Exist

Suppose:

```text
GOOGLE + 12345
```

doesn't exist.

Now we need to determine whether a corresponding LMS user already exists.

We might find:

```text
User
email = rahul@example.com
```

Now we have a potential account-linking situation.

---

# 15. Never Blindly Merge

This is dangerous:

```typescript
const user = await findUserByEmail(email);

if (user) {
  await createAccount({
    userId: user.id,
    provider: "GOOGLE",
    providerAccountId: googleSub,
  });
}
```

It looks convenient.

But account linking is a security-sensitive operation.

You need to establish that the provider identity should actually be connected to that LMS account.

---

# 16. Why Automatic Email Linking Can Be Dangerous

Imagine an existing account:

```text
User A
email = rahul@example.com
```

Now an OAuth provider returns:

```text
email = rahul@example.com
```

If we automatically link:

```text
Google Account
 ↓
User A
```

we are saying:

> "Matching email is sufficient proof that this external identity belongs to User A."

That may be acceptable under some carefully defined provider/application policies, but it should **not** be treated as a universal safe rule.

---

# 17. Safer Approach

For an existing LMS account:

```text
OAuth login
 ↓
No matching external Account
 ↓
Email matches existing LMS User
 ↓
Don't automatically link
 ↓
Ask user to authenticate existing LMS account
```

For example:

```text
We found an existing account
using this email.

Please sign in with your existing
password to connect Google.
```

Then:

```text
Existing password
+
Google OAuth
```

proves control of both authentication methods.

---

# 18. Explicit Linking Flow

The safest mental model is:

```text
Existing LMS User
        │
        ▼
Authenticate
        │
        ▼
Settings
        │
        ▼
Connected Accounts
        │
        ▼
Connect Google
        │
        ▼
Google OAuth
        │
        ▼
Validate provider identity
        │
        ▼
Create Account relation
```

Now account linking is intentional.

---

# 19. Connected Accounts UI

Our LMS could have:

```text
Security
────────────────────────

Email
rahul@example.com
✓ Verified

Password
✓ Set

Multi-factor authentication
✓ Enabled

Connected accounts

Google       ✓ Connected
GitHub       + Connect
Microsoft    + Connect
```

This gives the user a clear view of authentication methods.

# 20. Account Linking API

For example:

```http
POST /api/v1/auth/google/link
```

But the OAuth flow itself usually starts with:

```http
GET /api/v1/auth/google/link
```

The backend knows:

```text
current authenticated user
```

and starts an OAuth transaction specifically for linking.

This is different from:

```http
GET /auth/google/login
```

which is intended for login.

---

# 21. Login and Linking Are Different OAuth Flows

We should conceptually have:

```text
Google Login
```

and:

```text
Google Account Linking
```

They may use similar OAuth machinery, but their business meaning is different.

### Login

```text
Who is this person?
```

### Linking

```text
Which external identity should be attached
to this already-authenticated LMS account?
```

Don't mix these flows.

---

# 22. OAuth Transaction Context

When starting OAuth, store context such as:

```text
purpose = LOGIN
```

or:

```text
purpose = LINK_ACCOUNT
```

For example:

```text
OAuthTransaction
────────────────────
state
codeVerifier
nonce
provider
purpose
userId?
expiresAt
```

For login:

```text
purpose = LOGIN
userId = null
```

For linking:

```text
purpose = LINK_ACCOUNT
userId = user_123
```

This is a powerful architecture.

---

# 23. Why `purpose` Matters

Suppose Rahul is already logged in.

He starts:

```text
Connect Google
```

The callback returns:

```text
Google identity
```

The server must know:

```text
"This is a linking operation."
```

not:

```text
"This is a brand-new login."
```

Otherwise you can accidentally replace the user's current authentication context.

---

# 24. OAuth Transaction Model

We could eventually create:

```prisma
model OAuthTransaction {
  id           String   @id @default(uuid())

  stateHash    String   @unique
  codeVerifierEncrypted String?

  provider     String
  purpose      OAuthPurpose

  userId       String?

  expiresAt    DateTime
  consumedAt   DateTime?

  createdAt    DateTime @default(now())

  @@index([userId])
}
```

And:

```prisma
enum OAuthPurpose {
  LOGIN
  LINK_ACCOUNT
}
```

The exact fields can evolve.

The important concept is:

> **OAuth is a temporary stateful transaction, not just a redirect URL.**

---

# 25. Store Sensitive OAuth State Carefully

Remember:

```text
codeVerifier
```

is sensitive.

Depending on your architecture, you can store it:

```text
server-side
```

or protect it appropriately if stored client-side.

Don't casually put it into:

```text
localStorage
```

and assume it's safe.

Likewise, state values should be:

```text
random
short-lived
bound to the transaction
```

# 26. Account Linking Service

Our architecture follows the pattern we've been using:

```text
Controller
   ↓
Service
   ↓
Repository
```

Controller:

```typescript
async function googleCallback(req, res) {
  const result =
    await oauthService.handleCallback({
      code: req.query.code,
      state: req.query.state,
    });

  // response / redirect
}
```

The controller should stay thin.

---

# 27. OAuth Service

The service can handle:

```text
validate transaction
 ↓
exchange code
 ↓
validate identity
 ↓
determine purpose
 ↓
find Account
 ↓
login or link
 ↓
create session
```

Conceptually:

```typescript
async function handleCallback(input) {
  const transaction =
    await transactionRepository.find(...);

  const identity =
    await providerService.exchangeAndVerify(...);

  if (transaction.purpose === "LOGIN") {
    return loginWithProvider(identity);
  }

  if (transaction.purpose === "LINK_ACCOUNT") {
    return linkProviderAccount(
      transaction.userId,
      identity
    );
  }
}
```

This is a clean separation.

---

# 28. Repository Responsibilities

Repositories should handle database operations.

For example:

```typescript
findAccountByProviderIdentity(
  provider,
  providerAccountId
)
```

```typescript
createAccount(data)
```

```typescript
findUserById(userId)
```

```typescript
findUserByEmail(email)
```

```typescript
deleteAccount(accountId)
```

The service decides **why and when** these operations happen.

---

# 29. Provider Adapter Pattern

Now suppose we support:

```text
Google
GitHub
Microsoft
```

Don't make one giant service:

```typescript
if (provider === "google") ...
else if (provider === "github") ...
else if (provider === "microsoft") ...
```

everywhere.

Instead, define a provider interface.

Conceptually:

```typescript
interface OAuthProvider {
  getAuthorizationUrl(...): string;

  exchangeCode(...): Promise<TokenSet>;

  getIdentity(...): Promise<OAuthIdentity>;
}
```

Then:

```text
OAuthProvider
   │
   ├── GoogleProvider
   ├── GitHubProvider
   └── MicrosoftProvider
```

This is much easier to extend.

---

# 30. Normalized Identity

Each provider returns different fields.

Google might give:

```json
{
  "sub": "12345",
  "email": "rahul@example.com",
  "email_verified": true
}
```

GitHub may expose different names.

Our provider adapters normalize everything into:

```typescript
interface OAuthIdentity {
  provider: OAuthProviderName;
  providerAccountId: string;
  email?: string;
  emailVerified?: boolean;
  name?: string;
  avatarUrl?: string;
}
```

Now the rest of our application doesn't need to know provider-specific details.

---

# 31. This Is a Very Good Abstraction

Instead of:

```text
Google response
GitHub response
Microsoft response
```

our application receives:

```text
OAuthIdentity
```

Example:

```typescript
{
  provider: "GOOGLE",
  providerAccountId: "12345",
  email: "rahul@example.com",
  emailVerified: true
}
```

or:

```typescript
{
  provider: "GITHUB",
  providerAccountId: "98765",
  email: "rahul@example.com",
  emailVerified: true
}
```

The application logic stays provider-agnostic.

---

# 32. Provider Enum

Instead of free-form strings everywhere:

```prisma
enum OAuthProvider {
  GOOGLE
  GITHUB
  MICROSOFT
}
```

Then:

```prisma
model Account {
  id                String        @id @default(uuid())

  userId            String
  provider          OAuthProvider
  providerAccountId String

  user User @relation(...)

  @@unique([provider, providerAccountId])
}
```

This prevents:

```text
google
GOOGLE
Google
google-oauth
```

from becoming accidental separate values.

---

# 33. External Identity Uniqueness

Our invariant is:

```text
(provider, providerAccountId)
```

must identify exactly one LMS user.

Formally:

```text
GOOGLE + 12345
        ↓
exactly one User
```

This is an excellent database invariant.

---

# 34. Another Useful Invariant

An account should not be linked twice.

For example:

```text
Google 12345
```

cannot belong to:

```text
User A
```

and:

```text
User B
```

The unique database constraint protects this even if two requests race.

This is an important lesson:

> **Security rules should be enforced at the database level whenever possible.**

---

# 35. Race Condition Example

Imagine two requests arrive simultaneously:

```text
Request A:
Connect Google

Request B:
Connect Google
```

Both check:

```text
Does account exist?
→ No
```

Then both attempt:

```text
INSERT Account
```

Without a database unique constraint:

```text
Duplicate Account ❌
```

With:

```prisma
@@unique([provider, providerAccountId])
```

one insert succeeds and the other fails.

Database constraints protect us from concurrency bugs.

---

# 36. Handling Unique Constraint Errors

Our service should gracefully handle:

```text
unique constraint violation
```

For example:

```text
Google account is already linked
```

But be careful with the exact response.

You don't want to expose unnecessary information to an attacker.

---

# 37. What If Google Account Is Already Linked to Another User?

Suppose Rahul tries:

```text
Connect Google
```

but that Google identity already belongs to:

```text
User 456
```

We must **not** silently move it.

The result should be:

```text
❌ Cannot link this Google account.
It is already connected to another LMS account.
```

Then the user can authenticate into the correct LMS account and resolve the situation.

---

# 38. Never Reassign External Accounts Automatically

Bad:

```text
Account already exists
 ↓
Update userId = currentUser
```

This could allow account takeover.

Imagine:

```text
Google account
 ↓
User A
```

Attacker somehow initiates linking from User B.

If we simply reassign:

```text
Google account
 ↓
User B
```

User A loses access through Google.

Even worse, the attacker may gain it.

Therefore:

> External identities should never be silently reassigned.

---

# 39. Unlinking

Suppose Rahul has:

```text
Password
Google
GitHub
```

He clicks:

```text
Disconnect Google
```

Before doing this, check:

```text
Does the user have another authentication method?
```

For example:

```text
passwordHash != null
```

or:

```text
another Account exists
```

If not:

```text
❌ Don't allow unlinking.
```

unless the user is intentionally going through a secure account-recovery or account-deletion flow.

---

# 40. Authentication Method Count

We can conceptually calculate:

```text
authenticationMethods =
    password ? 1 : 0
    +
    linkedAccounts.count
    +
    passkeys.count
```

If:

```text
authenticationMethods = 1
```

don't allow removing that last method without another safe replacement.

---

# 41. Email From OAuth

Should we always update:

```text
User.email
```

from Google?

No.

Consider:

```text
LMS email
rahul@example.com

Google email
rahul2@example.com
```

If Google login automatically changes the LMS email:

```text
User.email = rahul2@example.com
```

you may accidentally change:

- notifications
    
- recovery address
    
- unique identity
    
- billing information
    
- certificates
    
- account records
    

Instead, email changes should follow a dedicated account-email-change workflow.

---

# 42. Provider Email vs LMS Email

Keep them conceptually separate:

```text
User
 └── email
```

and:

```text
Account
 └── provider identity
      └── provider email
```

You may store provider email if useful for auditing or account management, but it should not automatically overwrite the LMS email.

---

# 43. Provider Email Can Change

Suppose:

```text
Google:
rahul@gmail.com
```

later becomes:

```text
rahulkumar@gmail.com
```

The provider identity remains:

```text
Google
+
same subject
```

Therefore our account link remains intact.

This is another reason:

> **Use provider subject, not provider email, as the external identity key.**

---

# 44. Verified Email

OAuth providers can expose whether the provider considers the email verified.

For example:

```text
emailVerified = true
```

This can help our application decide whether to mark:

```text
User.emailVerified
```

But provider semantics differ.

So our provider adapter should normalize:

```typescript
emailVerified?: boolean;
```

and our application policy should decide what to do with it.

---

# 45. Don't Assume Every Provider Is Equivalent

Google:

```text
verified email semantics
```

GitHub:

```text
email privacy / primary email APIs
```

Microsoft:

```text
different identity and tenant concepts
```

These providers aren't identical.

The provider adapter layer lets us handle those differences cleanly.

---

For our AI LMS, I'd recommend starting with:


Then:

```text

```

Then potentially:

Why?

You could technically add:


# 48. Account Linking Security

Let's create a threat model.

### Threat 1

Attacker steals OAuth authorization code.

Defense:

```text
PKCE
```

### Threat 2

Attacker injects OAuth response.

Defense:

```text
state
```

### Threat 3

Attacker tries to link their Google account to victim.

Defense:

```text
authenticated linking flow
+
recent authentication
```

### Threat 4

Attacker tries to steal already-linked Google account.

Defense:

```text
provider identity uniqueness
```

### Threat 5

Attacker exploits email matching.

Defense:

```text
don't blindly auto-link
```

### Threat 6

User removes their only login method.

Defense:

```text
minimum authentication-method invariant
```

Imagine Rahul's session is:

```text
3 months old
```

and the browser is unattended.

Someone accesses the settings page.

They click:

```text
Connect Google
```

We shouldn't necessarily allow it immediately.

Require:

```text
recent authentication
```

For example:

```text
Password
```

or:

```text
existing MFA
```

before starting the linking flow.

This is another use of step-up authentication.

# 50. Linking Flow With MFA

If Rahul has:

```text

+
MFA
```

then:

```text
Connect Google
```

could require:

```text
Password
+

+

```

This is strong protection for account-linking operations.

# 51. Account Linking State Machine

Think of linking as:

```text
START
  │
  ▼
RECENT_AUTH_REQUIRED
  │
  ▼
OAUTH_STARTED
  │
  ▼
OAUTH_CALLBACK
  │
  ▼
IDENTITY_VALIDATED
  │
  ▼
CHECK_EXISTING_ACCOUNT
  │
  ├── Already linked to this user → SUCCESS
  │
  ├── Linked to another user → REJECT
  │
  └── Not linked → CREATE LINK
```

This is much safer than:

```text
callback → insert
```

---

# 52. First Login State Machine

For login:

```text
START
  │
  ▼
OAUTH_STARTED
  │
  ▼
CALLBACK
  │
  ▼
IDENTITY_VALIDATED
  │
  ▼
ACCOUNT_EXISTS?
  │
  ├── YES → LOGIN USER
  │
  └── NO
        │
        ▼
    EMAIL MATCH?
        │
        ├── NO → CREATE USER
        │
        └── YES → EXISTING ACCOUNT FLOW
```

This is an excellent backend design exercise.

---

# 53. Duplicate Account Problem

Suppose Rahul has:

```text
User 1
email = rahul@example.com
```

He logs in through Google.

Then:

```text
User 2
email = rahul@example.com
```

is accidentally created.

Now:

```text
User 1
 ├── course progress
 └── certificates

User 2
 ├── Google login
 └── empty progress
```

This is a terrible user experience.

Therefore, account identity resolution is one of the most important parts of social authentication.

---

# 54. Account Merge

What if duplicate accounts already exist?

We could build:

```text
Account Merge
```

but this is dangerous.

Merging might require moving:

```text
courses
enrollments
progress
certificates
payments
AI conversations
notifications
activity logs
```

and resolving conflicts.

Therefore:

> **Prevent duplicate accounts rather than depending on account merging later.**

---

# 55. Account Merge Should Be Rare

If we ever implement merging, it should require:

```text
strong authentication
+
explicit confirmation
+
transaction
+
audit log
```

and careful handling of every related resource.

This is far beyond our current phase.

---

# 56. Audit Logging

Account linking should generate an audit event:

```text
ACCOUNT_LINKED
```

with metadata such as:

```text
userId
provider
timestamp
IP
user-agent/device information
```

Be careful not to log:

```text
access tokens
refresh tokens
client secrets
authorization codes
TOTP secrets
```

Audit logs should help investigate events without becoming a new credential leak.

---

# 57. Account Unlink Audit

Likewise:

```text
ACCOUNT_UNLINKED
```

is useful.

Also:

```text
MFA_ENABLED
```

# 🧠 Interview Question

### "Why should you have a separate Account table instead of storing Google ID directly on User?"

A strong answer:

> A separate Account model decouples the application's user identity from external authentication providers. A single user can have multiple authentication methods such as password, Google, GitHub, or Microsoft. The Account table can store the provider and stable provider-specific subject ID, with a unique constraint on `(provider, providerAccountId)`. This prevents duplicate external identities and makes adding new providers much easier. It also keeps provider-specific authentication details out of the core User model.

That's a very good backend interview answer.
