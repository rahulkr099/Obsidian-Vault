# 🔐 Phase 4 — Lesson 4.17: Unified Session & Token Architecture

We have now built several authentication methods:

```text
Email + Password
Google OAuth
GitHub OAuth
MFA / TOTP
Email Verification
Password Reset
```

The important question now is:

> **After any of these authentication methods succeeds, how does our LMS create and manage one consistent session?**

We don't want:

```text
Google → Google session
Password → Password session
GitHub → GitHub session
```

Instead:

```text
Google ───────┐
Password ─────┤
GitHub ───────┤
Passkey ──────┤
               ▼
          LMS User
               │
               ▼
          LMS Session
               │
        ┌──────┴──────┐
        ▼             ▼
   Access Token   Refresh Token
```

This is one of the most important architectural decisions in our authentication system.

---

# 1. Authentication Method vs Session

These are different things.

### Authentication method

Answers:

> **How did the user prove their identity?**

Examples:

```text
Password
Google
GitHub
Passkey
TOTP
```

### Session

Answers:

> **Does this browser/device currently have an authenticated relationship with our LMS?**

For example:

```text
Rahul
 ├── Chrome Laptop Session
 ├── Firefox Session
 └── Mobile Session
```

The authentication method creates or strengthens authentication.

The session represents the ongoing login.

---

# 2. Everything Should Converge Into One Session System

Our architecture should be:

```text
Password Login
       │
       ▼
       ┐
Google Login ──────┐
       │            │
GitHub Login ──────┤
       │            │
Passkey ───────────┤
                    ▼
               Authenticated
                    │
                    ▼
                 Session
```

This is extremely useful.

Why?

Because logout doesn't care **how the user logged in**.

It simply revokes the session.

---

# 3. Example

Rahul logs in with Google:

```text
Google
 ↓
Identity verified
 ↓
LMS User #123
 ↓
Session #A
```

Later he logs in with password:

```text
Password
 ↓
Verified
 ↓
LMS User #123
 ↓
Session #B
```

Now:

```text
User #123
 ├── Session A → Laptop
 └── Session B → Phone
```

Same user.

Different sessions.

---

# 4. Why Multiple Sessions?

Users commonly use multiple devices:

```text
Laptop
Phone
Tablet
College computer
```

We shouldn't force:

```text
One user = one session
```

unless the product specifically requires that.

A better model:

```text
User
  │
  └── Sessions[]
```

---

# 5. Session Model

A useful Prisma model:

```prisma
model Session {
  id           String   @id @default(uuid())

  userId       String

  refreshTokenHash String

  expiresAt    DateTime
  revokedAt    DateTime?

  createdAt    DateTime @default(now())
  lastUsedAt   DateTime?

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  @@index([userId])
}
```

This is the basic structure.

We can later add:

```text
device
ipAddress
userAgent
authMethod
```

depending on our requirements.

---

# 6. Session Is Server-Side State

A common beginner architecture is:

```text
JWT
 ↓
Everything inside token
```

But a better mental model is:

```text
Client
 ↓
Token
 ↓
Server
 ↓
Session
 ↓
User
```

The session gives us server-side control.

---

# 7. Why Do We Need Sessions If We Have JWTs?

Because JWTs are difficult to revoke individually.

Suppose:

```text
Access Token
expires in 15 minutes
```

If the user clicks:

```text
Logout
```

we ideally want:

```text
session revoked
```

A server-side session record gives us control over the refresh process.

---

# 8. Access Token

The access token is usually:

```text
short-lived
```

For example:

```text
10–15 minutes
```

The exact duration is a security/product decision.

It is used for:

```http
Authorization: Bearer <access-token>
```

The backend validates it and identifies the user/session context.

---

# 9. Refresh Token

The refresh token is longer-lived.

Conceptually:

```text
Access Token
   ↓
short lifetime

Refresh Token
   ↓
longer lifetime
```

When the access token expires:

```text
Refresh Token
      ↓
POST /auth/refresh
      ↓
New Access Token
```

The user doesn't need to enter their password again.

---

# 10. Why Not Make the Access Token Long-Lived?

Suppose:

```text
accessToken expires in 30 days
```

An attacker steals it.

They potentially have:

```text
30 days
```

of access.

With:

```text
accessToken = 15 minutes
```

the damage window is much smaller.

That's why:

> **Access tokens should generally be short-lived.**

---

# 11. Refresh Token Rotation

Suppose:

```text
Refresh Token A
```

is used.

Don't keep using it forever.

Instead:

```text
Refresh A
   ↓
Validate
   ↓
Issue Refresh B
   ↓
Invalidate A
```

Then:

```text
A → invalid
B → active
```

This is called:

> **Refresh token rotation**

---

# 12. Why Rotate?

Suppose attacker steals:

```text
Refresh Token A
```

User legitimately uses A:

```text
A → B
```

Now attacker tries:

```text
A
```

again.

Our server can detect:

```text
A already used
```

This may indicate:

> **Refresh-token reuse**

which is a serious security signal.

---

# 13. Refresh Token Reuse Detection

Imagine:

```text
User:
A → B → C
```

Attacker has old:

```text
A
```

Attacker tries:

```text
A
```

Our system sees:

```text
A = already rotated/revoked
```

Now we can respond with a strong security action such as:

```text
Revoke the affected session/token family
```

Depending on the architecture, you may revoke all refresh tokens associated with that session family.

This is much safer than simply issuing another token.

---

# 14. Token Family

Think of refresh tokens as a family:

```text
Family #123

A
 ↓
B
 ↓
C
 ↓
D
```

If:

```text
A
```

is reused after rotation, something suspicious happened.

The server can invalidate the family:

```text
A ❌
B ❌
C ❌
D ❌
```

Then require the user to authenticate again.

---

# 15. Session vs Refresh Token

These are related but not identical.

Think:

```text
Session
   │
   └── Refresh Token State
```

The session represents:

```text
"Rahul's authenticated device/session"
```

The refresh token represents:

```text
"Credential that can obtain new access tokens for this session"
```

Keeping these concepts separate makes revocation much easier.

---

# 16. Should We Store the Refresh Token?

Don't store raw refresh tokens in PostgreSQL.

Bad:

```text
refreshToken =
"eyJhbGciOi..."
```

Instead:

```text
raw refresh token
      ↓
hash
      ↓
database
```

Similar to:

```text
Password reset token
Email verification token
Recovery code
```

---

# 17. Why Hash Refresh Tokens?

Suppose the database leaks.

If we stored:

```text
refreshToken = ABC123
```

an attacker could immediately use it.

If we store:

```text
refreshTokenHash = hash(ABC123)
```

the database doesn't directly contain the usable credential.

This follows our security principle:

> **Don't store reusable secrets in plaintext when you don't need to.**

---

# 18. Token Hashing

For high-entropy random refresh tokens, a cryptographic hash such as SHA-256 can be appropriate.

Conceptually:

```typescript
import crypto from "node:crypto";

function hashToken(token: string) {
  return crypto
    .createHash("sha256")
    .update(token)
    .digest("hex");
}
```

Then:

```text
raw token
   ↓
SHA-256
   ↓
database
```

Unlike passwords, refresh tokens should be generated with enough randomness that brute-forcing their hashes isn't practical.

---

# 19. Access Token Should Usually Be Stateless

A common architecture is:

```text
Access Token
 ↓
JWT
 ↓
short lifetime
```

The backend verifies:

```text
signature
expiration
issuer
audience
subject
```

without querying the database on every request.

This gives us:

```text
Fast API authentication
```

while refresh/session state remains server-controlled.

---

# 20. Hybrid Architecture

This gives us a powerful design:

```text
             CLIENT
                │
                ▼
         Access Token
                │
                ▼
          API Request
                │
                ▼
        JWT Verification
                │
                ▼
        User / Session Context
```

And:

```text
             CLIENT
                │
                ▼
         Refresh Token
                │
                ▼
       /auth/refresh
                │
                ▼
       Database Session
                │
                ▼
      Rotation / Revocation
                │
                ▼
       New Access Token
```

So:

```text
Access token → mostly stateless
Refresh/session → stateful
```

This is a very useful architecture.

---

# 21. What Goes Inside the Access Token?

Keep it minimal.

For example:

```json
{
  "sub": "user_123",
  "sid": "session_456",
  "iss": "ai-lms",
  "aud": "ai-lms-api",
  "iat": 1786710000,
  "exp": 1786710900
}
```

Potentially:

```text
role
```

if your architecture benefits from it.

But don't put sensitive data inside.

---

# 22. `sub`

`sub` means:

> Subject.

For our LMS:

```text
sub = user_123
```

This identifies the authenticated user.

---

# 23. `sid`

We can include:

```text
sid = session_456
```

This identifies the session.

That's useful because:

```text
User 123
 ├── Session A
 ├── Session B
 └── Session C
```

The token can tell us:

```text
Which session is making this request?
```

---

# 24. Why Session ID Is Useful

Suppose Rahul wants:

```text
Logout this device
```

We can identify:

```text
session_456
```

and revoke it.

Other sessions remain active:

```text
Laptop → revoked
Phone → active
Tablet → active
```

This is much better than:

```text
Logout → destroy all sessions
```

for every situation.

---

# 25. Global Logout

Sometimes Rahul wants:

```text
Log out everywhere
```

Then:

```text
User 123
 ├── Session A ❌
 ├── Session B ❌
 ├── Session C ❌
 └── Session D ❌
```

This is a powerful security feature.

It is especially useful after:

```text
password change
account compromise
lost device
suspicious login
```

---

# 26. Session Revocation

Our model:

```prisma
revokedAt DateTime?
```

allows:

```text
revokedAt = null
```

meaning:

```text
active
```

and:

```text
revokedAt = now()
```

meaning:

```text
revoked
```

This is much better than deleting the record immediately.

---

# 27. Why Not Delete the Session?

Suppose you delete:

```text
Session #123
```

You lose the history.

Keeping:

```text
revokedAt
```

lets you preserve:

```text
Session created
Session revoked
```

This is useful for:

- auditing
    
- security investigation
    
- device management
    
- debugging

# 29. Why Store `authMethod`?

It can help with:

```text
security auditing
session management
login history
support/debugging
```

For example:

```text
Session A
authMethod = GOOGLE

Session B
authMethod = PASSWORD
```

This doesn't mean authorization depends on the method.

It's primarily metadata.

---

# 30. Don't Trust Session Metadata From the Client

Don't let the client say:

```json
{
  "authMethod": "GOOGLE"
}
```

and store it blindly.

The backend knows how authentication actually occurred.

Therefore:

```text
OAuth success
 ↓
server determines:
authMethod = GOOGLE
```

# 36. Refresh Flow

Suppose Rahul has:

```text
Access Token A
Refresh Token R1
```

Access token expires.

Frontend sends:

```http
POST /auth/refresh
```

with:

```text
Refresh Token R1
```

Backend:

```text
Hash R1
 ↓
Find session
 ↓
Is session active?
 ↓
Is token valid?
 ↓
Rotate R1 → R2
 ↓
Issue Access Token B
 ↓
Return R2
```

---

# 37. Refresh Rotation in Database

Suppose:

```text
Session #123
refreshTokenHash = hash(R1)
```

Request:

```text
R1
```

After successful rotation:

```text
Session #123
refreshTokenHash = hash(R2)
```

Now:

```text
R1 → invalid
R2 → valid
```

# 38. Better Rotation Model

A more advanced system may use separate refresh-token records:

```text
Session
   │
   └── RefreshToken[]
```

For example:

```prisma
model RefreshToken {
  id        String   @id @default(uuid())

  sessionId String

  tokenHash String   @unique

  familyId  String

  expiresAt DateTime
  usedAt    DateTime?
  revokedAt DateTime?

  createdAt DateTime @default(now())

  session Session @relation(...)
}
```

This provides more detailed rotation and reuse detection.

# 39. Token Family Architecture

Then:

```text
Session A
 │
 └── Family F1
      ├── R1
      ├── R2
      ├── R3
      └── R4
```

Each refresh rotates:

```text
R1 → R2
R2 → R3
R3 → R4
```

If:

```text
R2
```

is reused after it was consumed:

```text
🚨 Possible token theft
```

Then revoke the family:

```text
F1 ❌
```

# 40. Why a Separate RefreshToken Table?

It gives us better visibility:

```text
User
 ↓
Session
 ↓
RefreshToken[]
```

We can track:

```text
created
used
revoked
expired
family
```

This is useful for advanced security.

For our first implementation, a refresh-token hash directly on `Session` is simpler.

Later we can evolve it.

# 41. Logout

Basic logout:

```http
POST /auth/logout
```

Backend:

```text
Authenticated session
        ↓
Revoke session
```

For example:

```text
revokedAt = now()
```

Then:

```text
refresh token
 ↓
session revoked
 ↓
❌ cannot refresh
```

---

# 42. What Happens to the Access Token?

Suppose:

```text
Access Token
expires in 10 minutes
```

User logs out.

The access token may technically remain cryptographically valid until expiration.

This is one reason short access-token lifetimes are useful.

For higher-security applications, you can add server-side revocation mechanisms, but that increases complexity.

---

# 43. Logout Does Not Necessarily Mean Instant JWT Death

This is an important conceptual point.

If you use stateless JWT verification:

```text
JWT
signature valid
exp not reached
```

the server may still accept it.

Therefore:

```text
Logout
```

primarily needs to prevent:

```text
future refresh
```

and then the short-lived access token naturally expires.

---

# 44. Logout Everywhere

Endpoint:

```http
POST /auth/logout-all
```

Backend:

```text
UPDATE sessions
SET revokedAt = now()
WHERE userId = currentUser
AND revokedAt IS NULL
```

Now:

```text
Laptop ❌
Phone ❌
Tablet ❌
```

All sessions are revoked.

---

# 45. Logout One Device

Endpoint:

```http
DELETE /auth/sessions/:sessionId
```

or:

```http
POST /auth/sessions/:sessionId/revoke
```

Backend verifies:

```text
session.userId === currentUser.id
```

before revoking it.

This is a resource-ownership check.

---

# 46. Never Allow Arbitrary Session Revocation

Bad:

```text
DELETE /sessions/:id
```

without verifying ownership.

Attacker could attempt:

```text
/session/user_123-session
```

and revoke another user's session.

Therefore:

```text
currentUser
   ↓
session belongs to currentUser?
   ↓
yes → revoke
no → reject
```

This connects authentication with authorization.

# 49. Don't Trust IP Address as Identity

An important lesson:

```text
IP address ≠ user identity
```

Users can:

```text
change networks
use mobile data
use VPNs
use college Wi-Fi
```

So don't implement:

```text
if IP changed → logout
```

as your primary security model.

IP is useful as **risk/context information**, not a permanent identity.

# 50. Refresh Token Storage in Cookies

For browser-based applications, one common secure approach is:

```text
Refresh Token
 ↓
HttpOnly Secure cookie
```

This prevents JavaScript from directly reading the cookie.

Example properties:

```text
HttpOnly
Secure
SameSite
```

with exact `SameSite` configuration based on your frontend/backend deployment architecture.

---

# 51. Access Token Storage

There are several designs.

You might:

```text
keep access token in memory
```

and:

```text
keep refresh token in HttpOnly cookie
```

This reduces exposure compared with storing long-lived tokens in `localStorage`.

For our LMS, we'll eventually make the frontend architecture consistent with this model.

---

# 52. Why `localStorage` Is Risky

If malicious JavaScript executes in your page because of an XSS vulnerability:

```javascript
localStorage.getItem("refreshToken")
```

could expose a long-lived credential if you stored one there.

This is one reason:

```text
HttpOnly cookie
```

is attractive for refresh tokens.

However, cookies introduce their own CSRF considerations, so they must be configured and used correctly.

---

# 53. Cookie + CSRF

If authentication relies on cookies, browsers automatically attach them to requests in situations that may create CSRF risk.

Therefore, depending on your architecture:

```text
Cookie authentication
+
CSRF defenses
```

may be necessary.

We'll study CSRF more deeply in the dedicated security phase.

# 59. Session Service Example

Conceptually:

```typescript
async function createSession(input) {
  const refreshToken =
    generateSecureRandomToken();

  const refreshTokenHash =
    hashToken(refreshToken);

  const session =
    await sessionRepository.create({
      userId: input.userId,
      refreshTokenHash,
      authMethod: input.authMethod,
      expiresAt: calculateExpiry(),
      ipAddress: input.ipAddress,
      userAgent: input.userAgent,
    });

  const accessToken =
    createAccessToken({
      userId: input.userId,
      sessionId: session.id,
    });

  return {
    accessToken,
    refreshToken,
  };
}
```

This is simplified but captures the architecture.

# 60. Refresh Service

Likewise:

```typescript
async function refreshSession(refreshToken) {
  const tokenHash = hashToken(refreshToken);

  const session =
    await sessionRepository.findByTokenHash(
      tokenHash
    );

  validateSession(session);

  const newRefreshToken =
    generateSecureRandomToken();

  await rotateRefreshToken(
    session,
    newRefreshToken
  );

  const accessToken =
    createAccessToken({
      userId: session.userId,
      sessionId: session.id,
    });

  return {
    accessToken,
    refreshToken: newRefreshToken,
  };
}
```

Again, simplified.

# 61. Validate Session

A refresh request should check:

```text
session exists
AND
not revoked
AND
not expired
AND
token matches
```

Conceptually:

```typescript
if (!session) {
  throw new UnauthorizedError();
}

if (session.revokedAt) {
  throw new UnauthorizedError();
}

if (session.expiresAt <= new Date()) {
  throw new UnauthorizedError();
}
```

# 62. Session Expiration

Sessions shouldn't live forever.

For example:

```text
Session lifetime
=
30 days
```

and:

```text
Access token lifetime
=
15 minutes
```

These are independent concepts.

You might have:

```text
Access Token:
15 min

Session / Refresh:
30 days
```

The exact values depend on the application's security requirements.

---

# 63. Sliding vs Fixed Session Expiration

Two common models.

### Fixed expiration

```text
Login
 ↓
30 days
 ↓
Session expires
```

Refreshing doesn't extend the absolute expiration.

### Sliding expiration

```text
Login
 ↓
30 days
 ↓
Activity
 ↓
extend
 ↓
30 more days
```

Sliding sessions can improve UX but increase the lifetime of a potentially compromised credential.

A good system may use:

```text
idle timeout
+
absolute maximum lifetime
```

instead of unlimited sliding renewal.

---

# 64. Idle Timeout

For example:

```text
No activity for 7 days
 ↓
Session expires
```

This reduces risk from abandoned devices.

Again, exact values are product/security decisions.

---

# 65. Absolute Session Lifetime

Even if the user is constantly active:

```text
session
 ↓
refresh
 ↓
refresh
 ↓
refresh
```

you may eventually require:

```text
full re-authentication
```

after an absolute maximum period.

This prevents a stolen long-lived session from remaining valid indefinitely.

---

# 66. Step-Up Authentication and Sessions

Suppose Rahul is already logged in.

He wants to:

```text
Change email
```

We can require:

```text
recent authentication
```

without necessarily destroying his entire session.

Conceptually:

```text
Session
 ↓
Step-up challenge
 ↓
Password/MFA
 ↓
Sensitive operation
```

This is a mature authentication pattern.

---

# 67. Session Revocation Triggers

When should we revoke sessions?

Potential triggers:

```text
Logout
Password reset
Password change
MFA disabled
Suspicious refresh-token reuse
Account suspension
Account deletion
Admin security action
```

Not every application must revoke all sessions for every event, but the policy should be deliberate.

---

# 68. Password Change Policy

Suppose Rahul changes his password.

Should all sessions be revoked?

A strong security policy often does:

```text
Password changed
 ↓
Revoke existing sessions
 ↓
Require login again
```

This is especially useful if the password was changed because of suspected compromise.

Some applications preserve the current session and revoke others; the exact policy should be explicit.

---

# 69. Password Reset Is Different

For password reset:

```text
Forgot password
 ↓
Reset password
```

I'd generally favor:

```text
revoke existing sessions
```

because the reset flow itself may indicate the previous authentication credentials are no longer trusted.

This prevents:

```text
Attacker's old session
 ↓
continues working
```

after the password has been reset.

---

# 70. Account Suspension

Suppose:

```text
User.status = SUSPENDED
```

Existing sessions should not continue granting normal access.

This means authentication middleware may need to consider:

```text
session
+
user status
```

rather than trusting only a valid JWT.

This is another reason server-side session/user state matters.

---

# 71. JWT and Account Status

Suppose the JWT says:

```text
sub = user_123
```

and is cryptographically valid.

But the database now says:

```text
user.status = SUSPENDED
```

Should the request succeed?

For sensitive systems:

```text
No.
```

This is why some authorization decisions require current server-side state.

---

# 72. Don't Put Too Much Into JWT

Avoid:

```json
{
  "sub": "123",
  "role": "ADMIN",
  "email": "rahul@example.com",
  "mfaEnabled": true,
  "emailVerified": true,
  "subscription": "premium",
  "permissions": [...],
  "accountStatus": "ACTIVE",
  "profile": {...}
}
```

This becomes:

```text
large
stale
hard to revoke
hard to reason about
```

Keep tokens minimal.

---

# 73. Access Token Claims

A better minimal design:

```json
{
  "sub": "user_123",
  "sid": "session_456",
  "iss": "ai-lms",
  "aud": "ai-lms-api",
  "iat": 1786710000,
  "exp": 1786710900
}
```

Then retrieve additional information from trusted server-side state when necessary.

---

# 74. Session Authentication Context

The backend can construct:

```typescript
req.auth = {
  userId: payload.sub,
  sessionId: payload.sid,
};
```

Then:

```text
req.auth.userId
req.auth.sessionId
```

become the trusted authentication context.

The controller doesn't need to understand JWT internals.

Then our route:

```typescript
router.post(
  "/courses",
  authenticate,
  requireVerifiedEmail,
  requirePermission("COURSE_CREATE"),
  courseController.create

```

works regardless of whether the user logged in with:

```text

GitHub
Passkey
```

That's the beauty of unified sessions.

# 76. Authentication Method Becomes Irrelevant to Most APIs

After:

```text

```

the application usually doesn't care:

```text

```

It cares:

```text
Who are you?
Which session?
Is your account active?
Are you authorized?
Do you own this resource?
```

This separation is extremely important.


# 🧠 Interview Question

### "How would you design sessions for an application supporting password login, Google OAuth, MFA, and multiple devices?"

A strong answer:

> I would separate authentication methods from application sessions. Password, OAuth, and passkey authentication would all ultimately resolve to the same internal user and then call a centralized session service. Each device would have its own server-side session with a hashed refresh token. Access tokens would be short-lived JWTs containing minimal claims such as user ID and session ID. Refresh tokens would be rotated on every use, with reuse detection and session/token-family revocation. Sessions would have expiration and revocation state, allowing individual device logout and global logout. Sensitive actions could require step-up authentication. This allows the application authorization layer to remain independent of how the user authenticated.

That is a very strong backend architecture answer.

# 🎯 Lesson 4.17 Takeaways

```text
1. Authentication method and session are different concepts.

2. Password, Google, GitHub, and Passkey authentication should
   eventually converge into one LMS session system.

3. One user can have multiple sessions across devices.

4. Access tokens should generally be short-lived.

5. Refresh tokens should be longer-lived but carefully controlled.

6. Store refresh-token hashes rather than raw refresh tokens.

7. Rotate refresh tokens after successful use.

8. Detect refresh-token reuse.

9. Consider token-family/session revocation when reuse is detected.

10. Server-side sessions provide revocation and device management.

11. Access tokens can be mostly stateless while refresh/session
    state remains server-controlled.

12. Keep JWT claims minimal.

13. Include a session identifier if it helps with session
    management.

14. Logout should revoke the session and prevent future refresh.

15. Support individual-session logout and global logout.

16. Always verify that a session belongs to the current user before
    allowing session management operations.

17. Password reset, account suspension, MFA changes, and suspicious
    activity may require session revocation according to policy.

18. Don't rely entirely on JWT claims for rapidly changing security
    state such as account suspension.

19. Use a centralized Session Service.

20. Most application code should not care whether the user logged
    in using Google, password, GitHub, or another method.

21. Authentication determines WHO the user is.

22. Authorization determines WHAT the user can do.

23. Sessions connect authentication to ongoing API access.
```
