# 🔐 Phase 4 — Lesson 4.20: Authorization Implementation & Testing

In **4.19**, we learned the architecture:

```text
Authentication
      ↓
Permissions
      ↓
Resource ownership
      ↓
Business policy
      ↓
Allow / Deny
```

Now let's turn that architecture into something you could actually implement in your AI LMS.

The goal of this lesson is not just to understand authorization theoretically. You should be able to look at an endpoint and answer:

> **Exactly where and how is access being decided?**

---

# 1. Our Authorization Stack

For the AI LMS, we'll use this structure:

```text
                    Request
                       │
                       ▼
                authenticate()
                       │
                       ▼
                   req.auth
                       │
                       ▼
             requirePermission()
                       │
                       ▼
                  Controller
                       │
                       ▼
                    Service
                       │
              ┌────────┴────────┐
              ▼                 ▼
        Resource Lookup      Policy Check
              │                 │
              └────────┬────────┘
                       ▼
                   Repository
```

Notice something important:

**Not every authorization decision belongs in middleware.**

---

# 2. Three Levels of Authorization

We can divide authorization into three levels.

### Level 1 — Authentication

```text
Is the request authenticated?
```

```typescript
authenticate
```

### Level 2 — Capability

```text
Can this user perform this type of action?
```

```typescript
requirePermission("COURSE_UPDATE")
```

### Level 3 — Resource Policy

```text
Can this user perform the action on THIS resource?
```

```text
course.ownerId === userId
```

So:

```text
WHO?
 ↓
WHAT?
 ↓
WHICH RESOURCE?
```

This is a very useful mental model.

---

# 3. Example: Update Course

Consider:

```http
PATCH /api/v1/courses/course_123
```

We need to answer three questions.

### Question 1

```text
Is the user authenticated?
```

### Question 2

```text
Does the user have COURSE_UPDATE?
```

### Question 3

```text
Can the user update course_123?
```

Only when all required checks pass:

```text
ALLOW
```

---

# 4. Route Definition

Our route could look like:

```typescript
router.patch(
  "/courses/:courseId",
  authenticate,
  requirePermission(PERMISSIONS.COURSE_UPDATE),
  courseController.update
);
```

This reads almost like English:

> Authenticate the user → verify course-update permission → execute controller.

That's a good route design.

---

# 5. Controller

The controller should extract trusted identity:

```typescript
async function update(req: Request, res: Response) {
  const auth = requireAuth(req);

  const course = await courseService.update({
    userId: auth.userId,
    courseId: req.params.courseId,
    data: req.body,
  });

  res.json({
    data: course,
  });
}
```

Notice:

```typescript
userId: auth.userId
```

not:

```typescript
userId: req.body.userId
```

---

# 6. Service

Now the service handles the resource-specific rule:

```typescript
async function updateCourse(input: UpdateCourseInput) {
  const course =
    await courseRepository.findById(input.courseId);

  if (!course) {
    throw new NotFoundError("Course");
  }

  if (course.ownerId !== input.userId) {
    throw new ForbiddenError();
  }

  return courseRepository.update(
    input.courseId,
    input.data
  );
}
```

This is much safer.

---

# 7. Why the Service Checks Ownership

Because:

```text
COURSE_UPDATE
```

only means:

> The user has the capability to update courses.

It does **not** mean:

> The user can update every course in the database.

The service knows the specific resource:

```text
course_123
```

Therefore it can make the ownership decision.

---

# 8. Admin Exception

Suppose admins can update any course.

Then our policy becomes:

```text
SUPER_ADMIN → allow
ADMIN       → allow
INSTRUCTOR  → own course only
STUDENT     → deny
```

We could write:

```typescript
function canUpdateCourse(
  user: User,
  course: Course
) {
  if (user.role === "SUPER_ADMIN") {
    return true;
  }

  if (user.role === "ADMIN") {
    return true;
  }

  if (user.role === "INSTRUCTOR") {
    return course.ownerId === user.id;
  }

  return false;
}
```

---

# 9. Move This Into a Policy

Instead of putting that logic directly inside the service:

```text
course.policy.ts
```

could contain:

```typescript
export function canUpdateCourse(
  user: User,
  course: Course
): boolean {
  if (user.role === "SUPER_ADMIN") {
    return true;
  }

  if (user.role === "ADMIN") {
    return true;
  }

  if (user.role === "INSTRUCTOR") {
    return course.ownerId === user.id;
  }

  return false;
}
```

Then:

```typescript
if (!canUpdateCourse(user, course)) {
  throw new ForbiddenError();
}
```

This makes authorization rules easier to find.

# 11. Course Policy

For example:

```typescript
export const coursePolicy = {
  canRead(user, course) {
    // ...
  },

  canUpdate(user, course) {
    // ...
  },

  canDelete(user, course) {
    // ...
  },

  canPublish(user, course) {
    // ...
  },
};
```

Then the service becomes:

```typescript
if (!coursePolicy.canUpdate(user, course)) {
  throw new ForbiddenError();
}
```

Very readable.

---

# 12. Don't Pass Express `req` Into Policies

Avoid:

```typescript
coursePolicy.canUpdate(req, course)
```

Instead:

```typescript
coursePolicy.canUpdate(user, course)
```

or even:

```typescript
coursePolicy.canUpdate(
  {
    id: auth.userId,
    role: user.role,
  },
  course
);
```

The policy should be independent of Express.

---

# 13. Authorization Should Be Testable Without HTTP

This is a huge benefit.

You should be able to test:

```typescript
expect(
  coursePolicy.canUpdate(
    instructor,
    ownCourse
  )
).toBe(true);
```

and:

```typescript
expect(
  coursePolicy.canUpdate(
    instructor,
    anotherInstructorCourse
  )
).toBe(false);
```

without starting the Express server.

This makes authorization testing much easier.

# 14. Permission Constants

Let's create:

```typescript
export const PERMISSIONS = {
  COURSE_READ: "COURSE_READ",
  COURSE_CREATE: "COURSE_CREATE",
  COURSE_UPDATE: "COURSE_UPDATE",
  COURSE_DELETE: "COURSE_DELETE",

  ASSIGNMENT_CREATE: "ASSIGNMENT_CREATE",
  ASSIGNMENT_GRADE: "ASSIGNMENT_GRADE",

  USER_READ: "USER_READ",
  USER_UPDATE: "USER_UPDATE",
  USER_SUSPEND: "USER_SUSPEND",

  ANALYTICS_READ: "ANALYTICS_READ",
} as const;
```

Then:

```typescript
type Permission =
  typeof PERMISSIONS[keyof typeof PERMISSIONS];
```

Now TypeScript knows the valid permissions.

# 16. `hasPermission()`

Our authorization service could start very simply:

```typescript
function hasPermission(
  role: Role,
  permission: Permission
): boolean {
  return ROLE_PERMISSIONS[role]
    .includes(permission);
}
```

Then:

```typescript
hasPermission(
  "INSTRUCTOR",
  "COURSE_UPDATE"
);
```

returns:

```text
true
```

while:

```typescript
hasPermission(
  "STUDENT",
  "COURSE_UPDATE"
);
```

returns:

```text
false
```

---

# 17. One TypeScript Detail

Depending on how your TypeScript types are defined, `.includes()` on a readonly tuple can produce type errors.

Don't blindly fight the compiler.

You can define the mapping using a suitable:

```typescript
Record<Role, readonly Permission[]>
```

for example:

```typescript
const ROLE_PERMISSIONS:
  Record<Role, readonly Permission[]> = {
    STUDENT: [
      PERMISSIONS.COURSE_READ,
      PERMISSIONS.ENROLLMENT_CREATE,
    ],

    INSTRUCTOR: [
      PERMISSIONS.COURSE_CREATE,
      PERMISSIONS.COURSE_UPDATE,
    ],

    ADMIN: [
      PERMISSIONS.USER_READ,
      PERMISSIONS.USER_SUSPEND,
    ],

    SUPER_ADMIN: [],
  };
```

This is a good example of using TypeScript to make authorization data safer.

---

# 18. `requirePermission()`

Now:

```typescript
function requirePermission(
  permission: Permission
) {
  return (
    req: Request,
    res: Response,
    next: NextFunction
  ) => {
    const auth = requireAuth(req);

    // obtain current role / permissions
    // then check permission

    next();
  };
}
```

In a simple system, the role can be available from trusted server-side user state.

In a more advanced system, permissions can come from a database or authorization service.

---

# 19. Don't Put Role in the Request Body

Never:

```json
{
  "role": "ADMIN"
}
```

and then:

```typescript
const role = req.body.role;
```

Authorization should never depend on client-selected roles.

The role should come from:

```text
trusted database state
```

or another trusted authorization source.

---

# 20. What About Role in the JWT?

You _can_ include a role in an access token.

Example:

```json
{
  "sub": "user_123",
  "role": "INSTRUCTOR"
}
```

But remember:

> JWT claims can become stale.

Suppose:

```text
08:00 → INSTRUCTOR
09:00 → role changed to STUDENT
```

A token issued at 08:00 may still contain:

```text
INSTRUCTOR
```

until it expires.

Therefore don't treat long-lived JWT role claims as perfect real-time authorization state.

---

# 21. Better Approach

For normal operations:

```text
short-lived access token
+
server-side authorization state when needed
```

For highly sensitive actions:

```text
JWT
+
current user/role/permission state
```

This provides stronger control.

---

# 22. Authorization Cache

At higher scale:

```text
Request
 ↓
JWT
 ↓
Redis
 ↓
Permissions
```

can reduce database queries.

But again:

> **Do not introduce Redis merely because you are building a backend.**

First build:

```text
PostgreSQL
+
Prisma
+
clean authorization service
```

Then optimize based on actual bottlenecks.

# 23. The Most Important Authorization Vulnerability: IDOR

Let's understand this deeply.

IDOR means:

> **Insecure Direct Object Reference**

Suppose Rahul owns:

```text
course_101
```

The API:

```http
GET /courses/course_101
```

works.

Rahul changes the URL:

```http
GET /courses/course_102
```

where:

```text
course_102.ownerId = another_user
```

If the server only does:

```text
course exists?
```

Rahul gets another user's data.

That's an authorization failure.

---

# 24. Correct Implementation

Instead:

```text
course exists?
        ↓
does user have permission?
        ↓
does user own course?
        ↓
allow
```

Or for an admin:

```text
course exists?
        ↓
is admin?
        ↓
allow
```

The resource ID alone never grants access.

---

# 25. IDOR in AI Conversations

Imagine:

```http
GET /ai/conversations/conv_123
```

Rahul owns:

```text
conv_123
```

Another user:

```text
user_999
```

tries:

```http
GET /ai/conversations/conv_123
```

The backend must check:

```text
conversation.userId === req.auth.userId
```

Otherwise the attacker can read another user's AI conversations.

For an AI LMS, this is particularly important because conversations may contain private learning information.

---

# 26. IDOR in Progress

Imagine:

```http
GET /students/student_123/progress
```

Don't blindly trust:

```text
student_123
```

from the URL.

If Rahul is:

```text
student_456
```

he shouldn't automatically be able to request:

```text
student_123
```

The endpoint needs an authorization policy.

---

# 27. Better API Design

Instead of:

```http
GET /students/:studentId/progress
```

for the student's own progress, consider:

```http
GET /me/progress
```

Now the identity comes directly from:

```text
req.auth.userId
```

rather than from a client-provided ID.

This is a very useful API design technique.

# 28. `/me` Endpoints

We can use:

```text

GET /me/profile
```

# 29. When We Need Explicit IDs

Sometimes an instructor needs:

```http
GET /students/student_123/progress
```

because instructors legitimately inspect students.

Then authorization becomes:

```text
Is instructor?
        ↓
Does instructor have access to this course?
        ↓
Is student enrolled in that course?
        ↓
Allow
```

This is a **relationship-based policy**.


Instructor A requests:


# 31. Authorization Is About Relationships

This is the point where backend authorization gets interesting.

Instead of just:

```text
user.role === INSTRUCTOR
```

we ask:

```text
user
 ↓
has permission?
 ↓
belongs to organization?
 ↓
owns resource?
 ↓
manages course?
 ↓
student enrolled?
```

Authorization becomes a graph of trusted relationships.

---

# 32. Policy Example

```typescript
async function canViewStudentProgress({
  instructorId,
  courseId,
  studentId,
}: {
  instructorId: string;
  courseId: string;
  studentId: string;
}) {
  const course =
    await courseRepository.findById(courseId);

  if (!course) {
    return false;
  }

  if (course.ownerId !== instructorId) {
    return false;
  }

  return enrollmentRepository.exists({
    courseId,
    studentId,
  });
}
```

Now the service can enforce the policy.

---

# 33. Don't Trust URL Structure

This:

```http
/courses/course_123/students/student_456
```

does **not** mean:

```text
student_456 belongs to course_123
```

The server must verify the relationship.

URLs are identifiers, not authorization proofs.

For every authorization rule, write tests.

For:


# 41. `403` vs `404` for Authorization

Suppose another user requests:

```http
GET /ai/conversations/secret_123
```

and it belongs to someone else.

Two possible responses:

```text
403 Forbidden
```

or:

```text
404 Not Found
```

### 403

Communicates:

> The resource exists, but you're not allowed to access it.

### 404

Communicates:

> The resource isn't available to you / isn't found.

Sometimes `404` is preferable because it doesn't reveal whether the resource exists.

This is particularly useful for sensitive resources.

---

# 42. Don't Leak Resource Existence

Imagine an attacker tries:

```text
conversation_001
conversation_002
conversation_003
...
```

If your API responds:

```text
404
403
404
403
```

the attacker may learn which IDs belong to real users.

For sensitive resources, carefully consider whether unauthorized resources should appear as `404`.

For example:

```text

```

could log:

```text

```

But don't log sensitive content.

For example, don't log:

```text

```

just because an authorization check failed.

# 45. Fail Closed

One of the most important security principles:

> **If authorization cannot be confidently determined, deny access.**

Bad:

```typescript
if (permissionCheckFailed) {
  next();
}
```

❌

Better:

```typescript
if (!permissionCheckPassed) {
  throw new ForbiddenError();
}
```

Security systems should generally:

```text
unknown → deny
```

not:

```text
unknown → allow
```

---

# 46. Default Deny

Our permission system should follow:

```text
No permission
    ↓
DENY
```

Not:

```text
No permission
    ↓
maybe allow
```

For example, if a new permission is added:

```text
COURSE_PUBLISH
```

and we haven't explicitly granted it to instructors:

```text
INSTRUCTOR
 ↓
COURSE_PUBLISH?
 ↓
NO
 ↓
DENY
```

This is safer.

---

# 47. Avoid Wildcard Permissions Too Early

Be careful with:

```text
*
```

meaning:

```text
everything
```

or:

```text
COURSE_*
```

These can become dangerous.

Explicit permissions are easier to audit.

If you eventually introduce wildcards, make sure the semantics are very clear.

---

# 48. Super Admin Should Be Audited

For:

```text
SUPER_ADMIN
```

consider logging:

```text
who
what
which resource
when
why/context
```

especially for:

```text
user suspension
role changes
account deletion
security configuration
```

This becomes important in production systems.

# 49. Authorization and Database Queries

There is another important optimization.

Instead of:

```text
find course
 ↓
check ownership
 ↓
update course
```

sometimes you can enforce ownership directly in the database query.

For example:

```text
UPDATE course
WHERE id = courseId
AND ownerId = userId
```

Then:

```text
rows affected = 0
```

could mean:

```text
not found OR not authorized
```

This can reduce race conditions and make the operation atomic.

But the exact implementation depends on your domain and whether you need to distinguish `404` from `403`.

---

# 50. Authorization + Transactions

Suppose:

```text
check ownership
 ↓
do something
```

between those operations another state changes.

For important operations, transaction boundaries can matter.

For example:

```text
BEGIN
 ↓
check resource
 ↓
authorization condition
 ↓
update
 ↓
COMMIT
```

This becomes especially important for:

```text
financial actions
role changes
enrollment limits
seat allocation
```

Our LMS may eventually have some transactional operations like enrollment limits or certificate issuance.

---

# 51. Authorization Doesn't Replace Database Constraints

Suppose:

```text
Course.ownerId → User.id
```

The database should enforce that relationship.

Application authorization says:

```text
"Rahul is allowed to update this course."
```

Database constraints say:

```text
"This course owner must actually exist."
```

Both are necessary.

# 🧠 Interview Question

### "How would you prevent IDOR in a REST API?"

A strong answer:

> I would never treat a resource ID supplied in the URL as proof of access. After authentication, I would obtain the user identity from the trusted authentication context and check whether the user has the required permission and relationship to the resource. For example, when updating a course, I would verify both `COURSE_UPDATE` permission and that the course belongs to the instructor, unless the user has an administrative capability. I would also write automated tests specifically covering cross-user resource access.

---

# 🧠 Another Interview Question

### "Where should authorization logic live?"

A good answer:

> Generic authentication and coarse-grained permission checks can live in middleware. Resource-specific authorization such as ownership, enrollment relationships, or whether an instructor manages a particular course belongs closer to the domain, typically in services or dedicated policy modules. Repositories should focus on persistence rather than HTTP authentication or authorization decisions.

# 🎯 Lesson 4.20 Takeaways

```text
1. Authorization should be implemented in layers.

2. Authentication answers WHO.

3. Permission checks answer WHAT.

4. Resource policies answer WHICH RESOURCE.

5. Use requirePermission() for reusable capability checks.

6. Keep resource-specific ownership rules in policies/services.

7. Never trust userId, role, or ownership information from the client.

8. /me endpoints can eliminate many unnecessary IDOR risks.

9. URL IDs are identifiers, not authorization proofs.

10. Every sensitive resource needs an explicit ownership/access policy.

11. AI conversations and uploaded documents require particularly
    careful ownership checks.

12. Authorization should fail closed.

13. Default should be DENY when access cannot be established.

14. Test both unit-level policies and API-level authorization.

15. Always test cross-user access.

16. Consider 404 instead of 403 when revealing resource existence
    would itself leak sensitive information.

17. Keep authorization policies independent of Express.

18. Keep repositories focused on data access.

19. Use short-lived tokens and current server-side state when
    authorization needs to react quickly to role/permission changes.

20. Don't overengineer RBAC initially.

21. Start with:
    User.role
       ↓
    Permission map
       ↓
    Policy/ownership checks

22. Later, if the LMS becomes a multi-tenant SaaS:
    Organization
       ↓
    Membership
       ↓
    Role
       ↓
    Permission
       ↓
    Resource Policy
```
