# 🔐 Phase 4 — Lesson 4.6: Access Tokens & JWT

Now we reach one of the most commonly misunderstood topics in backend development:

> **JWT (JSON Web Token)**

You've already learned:

```text
4.1 Authentication Architecture
        ↓
4.2 User & Identity Design
        ↓
4.3 Password Hashing
        ↓
4.4 Registration
        ↓
4.5 Login & Credential Verification
```

Now we need to answer:

> **After successful login, how does the server recognize the user on future API requests?**

One common answer is an **access token**.

And JWT is one format we can use for that token.

---

# 1. The Problem JWT Solves

Imagine Rahul logs in:

```text
POST /api/v1/auth/login
```

The server verifies:

```text
Email ✅
Password ✅
Account allowed ✅
```

The server now knows:

```text
This is User #123.
```

But what happens when Rahul sends another request?

```http
GET /api/v1/courses
```

The server needs some way to know:

```text
Who is making this request?
```

We could send the email every time, but we cannot simply trust:

```json
{
  "userId": "123"
}
```

because anyone could modify it.

We need a **verifiable credential**.

---

# 2. Access Token

An access token is a credential that the client presents when accessing protected APIs.

Conceptually:

```text
Login
  ↓
Authentication succeeds
  ↓
Access Token
  ↓
Client
  ↓
Protected API requests
```

For example:

```http
GET /api/v1/courses/me
Authorization: Bearer <access-token>
```

The server can verify the token and establish:

```text
req.user
```

or an equivalent authentication context.

---

# 3. JWT Is a Token Format

This distinction is extremely important:

```text
Access Token
     ↓
A credential used for API access
```

while:

```text
JWT
     ↓
A standardized token format
```

Therefore:

```text
JWT ≠ Authentication itself
JWT ≠ Session management itself
JWT ≠ Authorization itself
```

You can use JWT as an access-token format.

But authentication is the larger system we have been designing.

---

# 4. JWT Structure

A JWT normally contains three parts:

```text
Header.Payload.Signature
```

For example, conceptually:

```text
xxxxx.yyyyy.zzzzz
```

Three sections:

```text
┌──────────┐
│  Header  │
└────┬─────┘
     .
┌──────────┐
│ Payload  │
└────┬─────┘
     .
┌──────────┐
│ Signature│
└──────────┘
```

Let's understand each.

---

# 5. JWT Header

The header contains information about how the JWT is protected.

For example:

```json
{
  "alg": "RS256",
  "typ": "JWT"
}
```

Common fields:

```text
alg
typ
```

### `alg`

Specifies the cryptographic algorithm.

For example:

```text
HS256
RS256
ES256
```

### `typ`

Usually:

```text
JWT
```

The header is not secret.

---

# 6. JWT Payload

The payload contains **claims**.

For example:

```json
{
  "sub": "user_123",
  "role": "STUDENT",
  "iat": 1755120000,
  "exp": 1755120900
}
```

These claims tell the server things about the token.

Common claims include:

```text
sub
iss
aud
exp
iat
nbf
jti
```

We'll understand the important ones now.

---

# 7. `sub` — Subject

`sub` means:

> **Who is this token about?**

For our LMS:

```json
{
  "sub": "user_123"
}
```

means:

```text
This token represents User #123.
```

This is usually the most important identity claim.

---

# 8. Why Use `sub` Instead of Email?

You might wonder:

```json
{
  "email": "rahul@example.com"
}
```

Why not just put the email in the token?

Because the user's email can change.

Our internal identity is:

```text
userId
```

while:

```text
email
```

is an account attribute.

Therefore:

```text
sub = stable user identity
```

is generally cleaner.

---

# 9. `iss` — Issuer

`iss` means:

> **Who issued this token?**

For example:

```json
{
  "iss": "ai-lms-api"
}
```

The server can verify that the token came from the expected issuer.

Conceptually:

```text
Token
 ↓
iss = ai-lms-api
 ↓
Expected issuer?
 ↓
Yes / No
```

This becomes especially useful when your system has multiple services or authentication providers.

---

# 10. `aud` — Audience

`aud` means:

> **Who is this token intended for?**

For example:

```json
{
  "aud": "ai-lms-api"
}
```

Imagine your organization has:

```text
AI LMS API
AI LMS Admin API
AI LMS AI Service
```

A token intended for one service shouldn't automatically be accepted by another.

Audience validation helps establish that boundary.

---

# 11. `iat` — Issued At

`iat` means:

> **When was this token issued?**

Example:

```json
{
  "iat": 1755120000
}
```

It's represented as a timestamp.

This can be useful for:

```text
Token age
Security decisions
Debugging
Auditing
```

---

# 12. `exp` — Expiration

This is extremely important.

```json
{
  "exp": 1755120900
}
```

means the token should no longer be accepted after its expiration time.

Conceptually:

```text
Access Token
     ↓
Valid for a short period
     ↓
Expires
     ↓
No longer accepted
```

This limits the damage if an access token is stolen.

---

# 13. Why Short-Lived Access Tokens?

Imagine an attacker steals an access token.

If it lasts:

```text
30 days
```

the attacker potentially has a large window of opportunity.

If it lasts:

```text
10 minutes
```

the exposure window is much smaller.

So:

```text
Short access-token lifetime
        +
Refresh mechanism
```

is a common architecture.

We'll discuss refresh tokens in Lesson 4.7.

---

# 14. `nbf` — Not Before

`nbf` means:

> The token should not be accepted before this time.

Conceptually:

```json
{
  "nbf": 1755120000
}
```

If the current time is earlier than `nbf`:

```text
Token
 ↓
Not active yet
 ↓
Reject
```

You won't need this for every token, but you should know what it means.

---

# 15. `jti` — JWT ID

`jti` gives the token a unique identifier.

Example:

```json
{
  "jti": "token_abc123"
}
```

This can be useful for:

```text
Auditing
Token tracking
Revocation systems
Security events
```

However, simply having a `jti` doesn't automatically make a JWT revocable.

That's an important distinction.

---

# 16. A Practical LMS Access Token

Our access token payload might conceptually contain:

```json
{
  "sub": "user_123",
  "role": "STUDENT",
  "iss": "ai-lms-api",
  "aud": "ai-lms-api",
  "iat": 1755120000,
  "exp": 1755120900,
  "jti": "token_abc123"
}
```

But notice something:

> We don't need to put everything about the user inside the token.

---

# 17. Don't Put Too Much Data in JWT

Bad idea:

```json
{
  "sub": "user_123",
  "email": "...",
  "name": "...",
  "phone": "...",
  "address": "...",
  "profile": "...",
  "permissions": "...",
  "courseHistory": "...",
  "aiConversations": "..."
}
```

This creates unnecessary problems.

Remember:

```text
JWT payload
     ↓
Not encrypted by default
```

Anyone who possesses the token can generally decode the header and payload.

So:

```text
JWT
≠
Secret storage
```

---

# 18. JWT Is Usually Encoded, Not Encrypted

This is one of the most important JWT concepts.

Suppose you have:

```json
{
  "sub": "user_123",
  "role": "STUDENT"
}
```

The payload is encoded into the JWT.

Anyone holding the token can decode it.

But they cannot simply modify it and have the server accept the modified version if the signature is properly verified.

So:

```text
JWT payload
→ readable

JWT signature
→ protects integrity/authenticity
```

---

# 19. What Does the Signature Do?

The signature allows the server to detect tampering.

Conceptually:

```text
Header
   +
Payload
   ↓
Cryptographic signing
   ↓
Signature
```

The JWT becomes:

```text
Header.Payload.Signature
```

If someone modifies:

```text
role = STUDENT
```

to:

```text
role = ADMIN
```

the original signature no longer matches.

The server can detect this.

---

# 20. The Critical Security Principle

Suppose an attacker changes:

```json
{
  "sub": "user_123",
  "role": "ADMIN"
}
```

to:

```json
{
  "sub": "user_123",
  "role": "ADMIN"
}
```

and sends it to your API.

The server should:

```text
Verify signature
      ↓
Signature doesn't match
      ↓
Reject token
```

This is why:

> **Never trust JWT claims until the token has been properly verified.**

---

# 21. Signing Algorithms

There are two broad families you'll commonly encounter.

## Symmetric

Example:

```text
HS256
```

Conceptually:

```text
Signing
    ↓
Secret key

Verification
    ↓
Same secret key
```

So:

```text
Server
 ├── sign
 └── verify
      ↓
same secret
```

---

# 22. Asymmetric

Examples:

```text
RS256
ES256
```

These use:

```text
Private Key
+
Public Key
```

Conceptually:

```text
Private Key
     ↓
Sign

Public Key
     ↓
Verify
```

This is useful when multiple services need to verify tokens but should not possess the private signing key.

---

# 23. HS256 vs RS256

Think of them like this:

||HS256|RS256|
|---|---|---|
|Type|Symmetric|Asymmetric|
|Signing|Secret|Private key|
|Verification|Same secret|Public key|
|Key distribution|Simpler|More involved|
|Multi-service verification|Less convenient|Excellent|
|Good for simple API|Yes|Yes|

For our initial monolithic AI LMS backend, HS256 can be perfectly workable if implemented correctly.

For a multi-service architecture, asymmetric signing can become more attractive.

---

# 24. Don't Let the Token Choose Its Own Algorithm

A classic JWT security mistake historically involved trusting the token's `alg` value without enforcing the expected algorithm.

Your server should have a configured policy:

```text
Expected algorithm:
RS256
```

Then:

```text
Token says:
RS256

Server expects:
RS256

→ continue
```

If:

```text
Token says:
something unexpected
```

the server should reject it.

The key principle:

> **The server decides which algorithms are trusted. The token does not get to define your security policy.**

---

# 25. Access Token Verification

When a protected request arrives:

```http
GET /api/v1/courses/me
Authorization: Bearer <token>
```

our authentication middleware eventually performs something conceptually like:

```text
Extract token
    ↓
Parse token
    ↓
Verify signature
    ↓
Validate claims
    ↓
Check expiration
    ↓
Check issuer
    ↓
Check audience
    ↓
Create authentication context
```

Then:

```text
req.user
```

can contain the verified identity information.

---

# 26. Never Decode and Trust

This is a dangerous pattern:

```javascript
const payload = jwt.decode(token);

req.user = payload;
```

Why?

Because decoding doesn't prove that the token is authentic.

An attacker could create:

```json
{
  "sub": "victim-user",
  "role": "ADMIN"
}
```

encode it and send it to you.

So:

```text
decode
≠
verify
```

This distinction is extremely important.

---

# 27. Decode vs Verify

### Decode

```text
JWT
 ↓
Read header/payload
```

No cryptographic trust is established.

### Verify

```text
JWT
 ↓
Signature verification
+
Claim validation
 ↓
Trusted token, assuming your verification policy is correct
```

For authentication:

```text
❌ decode and trust

✅ verify and validate
```

---

# 28. JWT Access Middleware

Conceptually:

```typescript
async function authenticate(req, res, next) {
  const token = extractBearerToken(req);

  if (!token) {
    throw unauthorized();
  }

  const payload = verifyAccessToken(token);

  req.user = {
    id: payload.sub,
    role: payload.role
  };

  next();
}
```

The important part is that:

```text
verifyAccessToken()
```

must perform proper cryptographic verification and claim checks.

---

# 29. Should We Trust `role` From the JWT?

This is an interesting design decision.

Suppose the token contains:

```json
{
  "sub": "user_123",
  "role": "STUDENT"
}
```

The server verifies the token.

Can we use:

```text
role = STUDENT
```

for authorization?

Often yes, **if your token issuance and lifetime strategy account for role changes**.

But there's a problem.

Suppose:

```text
10:00
User role = STUDENT
Token issued
```

Then:

```text
10:05
Admin promotes user → INSTRUCTOR
```

The existing token may still say:

```text
role = STUDENT
```

Or the reverse:

```text
INSTRUCTOR
```

gets demoted to:

```text
STUDENT
```

while an old token still says:

```text
INSTRUCTOR
```

This is why authorization design and token lifetime matter.

---

# 30. A Safer Minimal Token

For our LMS, we can keep access tokens relatively small.

For example:

```json
{
  "sub": "user_123",
  "iss": "ai-lms-api",
  "aud": "ai-lms-api",
  "iat": 1755120000,
  "exp": 1755120900,
  "jti": "token_abc123"
}
```

Then the backend can retrieve current user information when stronger consistency is needed.

This gives us a useful principle:

> **A token should carry enough information to establish identity, not become a complete copy of the user database.**

---

# 31. Stateless vs Stateful Authentication

JWT is often described as "stateless."

What does that mean?

A truly stateless access-token verification can work like:

```text
Request
   ↓
JWT
   ↓
Verify signature
   ↓
Read claims
   ↓
Authenticate
```

The server doesn't need to look up a session record for every request.

That's convenient.

But our overall authentication system can still be **stateful** because we have:

```text
User
Sessions
Refresh tokens
Revocation
Password resets
```

So don't think:

```text
JWT = entire authentication system is stateless
```

Instead:

```text
Access-token verification
→ can be stateless

Authentication system
→ can still have server-side state
```

This is a much more accurate mental model.

---

# 32. Why Not Store Everything in JWT?

Because then every change becomes difficult.

Imagine the token contains:

```text
role = INSTRUCTOR
```

and the user is demoted.

An already-issued token may continue to carry:

```text
INSTRUCTOR
```

until it expires.

Server-side session/state can provide stronger control.

That's why our architecture uses:

```text
Short-lived Access Token
        +
Refresh Session
```

rather than trying to make JWT solve everything.

---

# 33. Access Token Lifetime

There isn't one universal correct value.

Common systems may use:

```text
5 minutes
10 minutes
15 minutes
30 minutes
```

depending on risk and architecture.

For our LMS, we can start with a **short-lived access token** and adjust based on the refresh/session strategy.

The important principle is:

```text
Shorter lifetime
→ smaller exposure window

Longer lifetime
→ less frequent refresh
```

It's a trade-off.

---

# 34. What Happens When Access Token Expires?

Suppose:

```text
Access Token
   ↓
Expires
```

The client makes:

```http
GET /api/v1/courses
```

The server returns:

```http
401 Unauthorized
```

The client can then use the refresh mechanism:

```text
Refresh Token
      ↓
Refresh endpoint
      ↓
New Access Token
```

We'll implement this architecture in:

> **Lesson 4.7 — Refresh Tokens**

---

# 35. Access Token Theft

Suppose someone steals an access token.

They may be able to send:

```http
Authorization: Bearer <stolen-token>
```

until the token expires or otherwise becomes invalid.

That's why we combine:

```text
Short token lifetime
+
HTTPS
+
Secure storage/transport
+
XSS protection
+
Refresh-token security
+
Monitoring
```

JWT itself doesn't prevent token theft.

---

# 36. JWT Does Not Encrypt Data

Never put sensitive information into a normal signed JWT expecting it to be secret.

For example:

```json
{
  "password": "..."
}
```

is obviously wrong.

Also avoid unnecessary sensitive information such as:

```text
Government ID
Private address
Medical information
Private messages
```

A signed JWT generally provides **integrity**, not confidentiality.

If you genuinely need encrypted token contents, that's a different design using encrypted tokens/JWE, and it has different trade-offs.

---

# 37. JWT Payload Size Matters

Suppose every request contains:

```text
50 KB JWT
```

Then:

```text
100 requests
×
50 KB
=
5 MB
```

of unnecessary network traffic.

So keep access tokens small.

A good token often needs only:

```text
sub
iss
aud
iat
exp
jti
```

and perhaps a small amount of authorization information when appropriate.

# 40. Better TypeScript Design

Instead of allowing arbitrary payloads everywhere, define an internal type:

```typescript
interface AccessTokenClaims {
  sub: string;
  iss: string;
  aud: string;
  iat: number;
  exp: number;
  jti: string;
}
```

Then your authentication code knows exactly what it expects.

This reduces accidental token design drift.

---

# 41. Token Generation Should Be Centralized

Don't generate JWTs in controllers:

```text
❌ auth.controller.ts
```

Instead, something like:

```text
shared/security/token.ts
```

or:

```text
modules/auth/token.service.ts
```

could own token creation and verification.

Architecture:

```text
Auth Service
     ↓
Token Service
     ↓
JWT library
```

This makes algorithm and claim policy centralized.

---

# 42. Environment Secrets

If using HS256, your signing secret is extremely sensitive.

For example:

```text
JWT_SECRET=...
```

Never:

```text
❌ Commit it to Git
❌ Put it in frontend code
❌ Put it in source code
❌ Log it
```

Use environment/secret management.

And make sure the secret is sufficiently strong and randomly generated.

---

# 43. If Using RS256

With asymmetric signing:

```text
Private Key
   ↓
Server signs token
```

and:

```text
Public Key
   ↓
Services verify token
```

The private key must remain highly protected.

The public key can be distributed to services that need verification.

This architecture becomes useful when your AI LMS eventually evolves toward:

```text
API Service
AI Service
Worker Service
Admin Service
```

and multiple components need to verify authentication credentials.

# 46. Authentication vs Authorization Again

Suppose:

```text
JWT
sub = user_123
```

The JWT establishes:

```text
Who is the user?
```

But it doesn't automatically establish:

```text
Can user_123 delete this course?
```

That's authorization.

So:

```text
JWT verification
      ↓
Authentication
      ↓
Authorization
      ↓
Resource ownership
```

# 47. Common JWT Mistakes

### Mistake 1 — Putting passwords in JWT

```text
❌ password
❌ passwordHash
```

Never.

---

### Mistake 2 — Trusting decoded payload

```typescript
jwt.decode(token)
```

and treating it as authenticated.

❌ Dangerous.

---

### Mistake 3 — Extremely long-lived access tokens

```text

```

can greatly increase exposure if stolen.

### Mistake 4 — Hardcoding secrets

```typescript

```

❌ Never.

---

### Mistake 5 — Accepting arbitrary algorithms

```text
Token decides algorithm
```

❌ Don't let untrusted input define your cryptographic policy.

---

### Mistake 6 — Putting huge data into the token

```text
Entire user profile
Course history
AI conversations
```

❌ Keep it small.

---

### Mistake 7 — Assuming JWT is encrypted

```text
JWT
≠
Encrypted data
```

---

### Mistake 8 — Assuming JWT solves authorization

```text
JWT valid
≠
User can do anything
```

# 48. A Better Mental Model

Think of the access token as a **signed identity statement**:

```text
"This credential was issued by our trusted authentication
system for user X, under these claims, and it is valid
according to these constraints."
```

It does **not** mean:

```text
"This user can access everything."
```

That's the job of authorization.

# 🧠 Interview-Level Question

### "What does JWT prove?"

A strong answer:

> A properly verified JWT can provide authenticated claims issued by a trusted signer, such as the identity represented by the `sub` claim and constraints such as issuer, audience, and expiration. It provides integrity and authenticity of the signed claims, but a normal JWT does not provide confidentiality. JWT verification also does not by itself determine whether the user is authorized to perform a specific action.

That's the level of understanding you want.

# 🎯 Lesson 4.6 Takeaways

Remember these:

```text
1. Access Token ≠ JWT.
   JWT is one token format that can be used for access tokens.

2. JWT has:
   Header + Payload + Signature.

3. JWT payloads are normally readable, not encrypted.

4. Signature protects the integrity/authenticity of the token.

5. sub identifies the token's subject.

6. exp limits token lifetime.

7. iss identifies the issuer.

8. aud identifies the intended audience.

9. jti can identify a specific token.

10. Never decode and trust a JWT.
    Verify it.

11. Don't put passwords or sensitive information in JWTs.

12. Keep access tokens short-lived.

13. The server must control trusted algorithms.

14. JWT authentication does not replace authorization.

15. JWT access tokens can be stateless while the overall
    authentication system still maintains server-side sessions.
```

The most important architecture to remember:

```text
LOGIN
  ↓
Credential Verification
  ↓
Session
  ↓
Access JWT
  ↓
API Request
  ↓
JWT Verification
  ↓
Authentication
```
