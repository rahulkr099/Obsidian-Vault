# 🔐 Phase 4 — Lesson 4.8: Token Rotation & Revocation

In **Lesson 4.7**, we built the refresh-token architecture:

```text
Login
  ↓
Access Token + Refresh Token
  ↓
Access Token expires
  ↓
Refresh Token
  ↓
New Access Token + New Refresh Token
```

Now we're going deeper.

The important question is:

> **What happens if a refresh token is stolen, reused, or needs to be invalidated?**

This is where **rotation, revocation, token families, replay detection, and database transactions** become important.

---

# 1. Why Refresh Tokens Need Rotation

Suppose Rahul logs in.

The server creates:

```text
Access Token A
Refresh Token A
```

The refresh token is stored server-side as a hash:

```text
Session
├── userId
├── refreshTokenHash(A)
└── revokedAt = null
```

Later, Rahul refreshes:

```text
Refresh A
   ↓
New Access B
```

If we simply keep Refresh A valid:

```text
Refresh A
   ↓
Refresh again
   ↓
Refresh again
   ↓
Refresh again
```

the same credential can be reused indefinitely until expiration.

That's not ideal.

Instead:

```text
Refresh A
   ↓
Invalidate A
   ↓
Create Refresh B
```

This is:

> **Refresh-token rotation**

---

# 2. The Token Chain

Think of refresh tokens as a chain:

```text
Refresh A
    ↓
Refresh B
    ↓
Refresh C
    ↓
Refresh D
```

Each successful refresh consumes the previous token and produces a new one.

So:

```text
A → B → C → D
```

Only the **current token** should be usable.

---

# 3. Why Rotation Improves Security

Imagine an attacker steals:

```text
Refresh B
```

Rahul also has Refresh B.

Rahul legitimately refreshes:

```text
B
 ↓
C
```

Now:

```text
B = old
C = current
```

If the attacker later tries:

```text
B
```

the server can recognize:

```text
B was already consumed.
```

That is a strong signal of possible token theft.

Without rotation:

```text
B
 ↓
new access token
```

could continue working.

Rotation gives us **replay detection**.

---

# 4. What Is Replay?

A replay attack happens when a previously valid credential is reused.

For example:

```text
Refresh Token A
      ↓
Legitimate use
      ↓
A becomes invalid
```

Later:

```text
Attacker
   ↓
Refresh Token A
   ↓
Try again
```

That's:

> **Refresh-token replay / reuse**

Our rotation system can detect this.

---

# 5. Token Reuse Detection

Suppose the session state looks like:

```text
Current token = C
```

The server receives:

```text
Refresh B
```

But B was already rotated to C.

Therefore:

```text
B != current token
```

We can detect:

```text
🚨 Refresh-token reuse
```

At this point, we should not simply generate another token.

Instead, we can revoke the relevant session/token family.

---

# 6. Why Revoke the Session?

Suppose an attacker has:

```text
Refresh B
```

and Rahul has:

```text
Refresh C
```

If we only invalidate B:

```text
B → invalid
C → still active
```

the attacker may already possess another credential.

A stronger response is:

```text
Reuse detected
      ↓
Revoke session
      ↓
All refresh tokens in that session become unusable
      ↓
User must authenticate again
```

This sacrifices convenience for security.

For suspicious credential reuse, that's often the right trade-off.

---

# 7. Token Families

Let's introduce a useful concept:

> **Token family**

Imagine Rahul logs in from his laptop.

That session produces:

```text
Family A

Refresh A1
   ↓
Refresh A2
   ↓
Refresh A3
   ↓
Refresh A4
```

All these tokens belong to the same authentication session.

If:

```text
A2
```

is reused after it has already been replaced by:

```text
A3
```

we know something suspicious happened.

---

# 8. Multiple Devices

Now Rahul logs in from his phone.

That's another session:

```text
User Rahul
│
├── Laptop Session
│     └── A1 → A2 → A3
│
└── Phone Session
      └── B1 → B2 → B3
```

This is why **session-level revocation** is useful.

If the laptop token is compromised:

```text
Laptop Session → revoke
```

The phone can remain active:

```text
Phone Session → active
```

---

# 9. Session vs Token

This distinction is important.

A token is:

```text
credential
```

A session is:

```text
server-side authentication state
```

Think:

```text
Session
   │
   ├── current refresh token
   ├── user
   ├── expiration
   └── revocation state
```

The refresh token is the credential used to access that session.

---

# 10. Better Session Model

Our Prisma model can evolve into something like:

```prisma
model Session {
  id               String    @id @default(uuid())
  userId           String

  refreshTokenHash String    @unique

  expiresAt        DateTime
  revokedAt        DateTime?

  createdAt        DateTime  @default(now())
  lastUsedAt       DateTime?

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  @@index([userId])
}
```

This gives us:

```text
Session
├── identity
├── current refresh credential
├── lifetime
├── revocation state
└── usage information
```

---

# 11. Do We Need a Separate Token Table?

There are two common designs.

### Simple design

Store only the current refresh-token hash:

```text
Session
└── refreshTokenHash
```

When rotation happens:

```text
A → B
```

replace the hash.

This is simple and works well.

### More detailed design

Create a separate token table:

```text
Session
   ↓
RefreshToken
├── hash
├── issuedAt
├── usedAt
├── revokedAt
└── replacedBy
```

This gives you detailed token history.

For our AI LMS, I recommend starting with the simpler session-based design and only introducing a separate token table if we actually need detailed token lineage.

---

# 12. The Refresh Algorithm

Let's define the process carefully.

When the client sends Refresh A:

```text
1. Extract refresh token
2. Hash/identify it
3. Find session
4. Check session exists
5. Check session isn't revoked
6. Check session hasn't expired
7. Verify token is current
8. Generate new refresh token
9. Store new hash
10. Generate new access token
11. Return new credentials
```

The critical part:

```text
Steps 7–9
```

must be handled carefully because of concurrency.

---

# 13. The Race Condition

Imagine:

```text
Request A ──────┐
                │
                ▼
           Refresh A
                │
Request B ──────┤
                │
                ▼
           Refresh A
```

Both requests may arrive almost simultaneously.

If both execute:

```text
find session
```

they could both see:

```text
Refresh A = valid
```

Then:

```text
Request A → creates B
Request B → creates C
```

Now the system has an ambiguous state.

This is a **race condition**.

---

# 14. Why This Matters in Browsers

This isn't just theoretical.

A browser application can accidentally send multiple refresh requests because of:

```text
Multiple API calls
React effects
Axios interceptors
Network retries
Multiple tabs
Concurrent requests
```

For example:

```text
Request 1 → 401
Request 2 → 401
Request 3 → 401
```

All three may try:

```text
POST /auth/refresh
```

at nearly the same time.

Your backend must handle this safely.

---

# 15. Database Transactions

This is where Phase 3 becomes useful.

We want token rotation to behave atomically.

Conceptually:

```text
BEGIN
   ↓
Check current token
   ↓
Invalidate/replace current token
   ↓
Create new state
   ↓
COMMIT
```

If something fails:

```text
ROLLBACK
```

So we don't end up with half-completed authentication state.

---

# 16. Atomicity

We want:

```text
Old Token
   ↓
Consumed
   +
New Token
   ↓
Stored
```

to happen as one logical operation.

Not:

```text
Old Token consumed
       ↓
💥 server crashes
       ↓
New Token never stored
```

A transaction helps ensure the database doesn't remain in an inconsistent state.

---

# 17. Conditional Update

There's another useful technique.

Instead of:

```text
find session
```

and later:

```text
update session
```

we can perform an update that includes the expected current state.

Conceptually:

```text
UPDATE sessions
SET refreshTokenHash = newHash
WHERE id = sessionId
AND refreshTokenHash = oldHash
AND revokedAt IS NULL
```

Then check:

```text
Rows updated = 1
```

means:

```text
✅ We successfully consumed the expected token.
```

If:

```text
Rows updated = 0
```

then:

```text
❌ The token was no longer current.
```

This is an excellent way to protect against concurrent refresh operations.

---

# 18. Why This Is Better

Suppose two requests both have:

```text
oldHash = A
```

Request A executes first:

```text
A → B
```

Now the database contains:

```text
current = B
```

Request B tries:

```text
WHERE current = A
```

But:

```text
current = B
```

So:

```text
0 rows updated
```

Request B knows:

```text
A was already consumed.
```

Now we can treat it as:

```text
refresh-token reuse
```

or handle it according to our concurrency policy.

---

# 19. Transaction + Conditional Update

For a robust implementation:

```text
Transaction
   │
   ├── Validate session
   │
   ├── Conditionally rotate current token
   │
   ├── Update session
   │
   └── Commit
```

This combines:

```text
Database transaction
+
Optimistic concurrency control
```

You don't always need complicated locking.

Often, a carefully designed conditional update is enough.

---

# 20. Optimistic Concurrency

The idea is:

> "I assume nobody changed this record. I'll update it only if it is still in the state I expect."

For refresh tokens:

```text
Expected:
refreshTokenHash = A
```

Then:

```text
UPDATE ... WHERE refreshTokenHash = A
```

If it succeeds:

```text
I won the race.
```

If it fails:

```text
Someone changed it first.
```

This is a powerful backend pattern far beyond authentication.

---

# 21. Token Rotation State Machine

We can visualize a refresh token as:

```text
             ┌───────────┐
             │   ACTIVE  │
             └─────┬─────┘
                   │
              successful
                refresh
                   │
                   ▼
             ┌───────────┐
             │ CONSUMED  │
             └───────────┘
```

But if an old token is used again:

```text
CONSUMED
   │
   │ reuse
   ▼
SUSPICIOUS
   │
   ▼
SESSION REVOKED
```

This is the basic security state machine.

---

# 22. Session State Machine

At a higher level:

```text
              ┌──────────┐
              │  ACTIVE  │
              └────┬─────┘
                   │
          ┌────────┼────────┐
          │        │        │
          ▼        ▼        ▼
       Logout   Expiry   Reuse
          │        │        │
          ▼        ▼        ▼
      REVOKED   EXPIRED  REVOKED
```

Once:

```text
revokedAt != null
```

the session shouldn't be usable for refreshing.

# 23. Logout

Now logout becomes simple.

Request:

```http
POST /api/v1/auth/logout
```

The server identifies the current session and sets:

```text
revokedAt = now()
```

Then:

```text
Refresh Token
      ↓
Session revoked
      ↓
Cannot refresh
```

The browser should also clear its refresh cookie.

```text

Phone

```

Database:

```text

├── Session A
├── Session B
└── Session C
```

Logout all:


Result:

```text

Session C → revoked
```

Now all refresh credentials stop working.

# 25. Password Change

A strong security policy is:

```text
Password changed
      ↓
Revoke existing sessions
      ↓
Require login again
```

Why?

Suppose an attacker already has a refresh token.

Rahul changes his password.

If we don't revoke sessions:

```text
Old refresh token
      ↓
Still works
```

That's undesirable.

So:

```text
Password change
      ↓
Revoke sessions
```

is a good security measure.

---

# 26. Password Reset

Password reset should usually be even stronger.

Imagine:

```text
Forgot password
 ↓
Reset password
```

After a successful reset:

```text
Revoke existing sessions
```

This prevents previously issued refresh credentials from remaining active indefinitely.

# 31. Why Revoke the Current Token Too?

Imagine the attacker has:

```text
A
```

and Rahul has:

```text
C
```

We don't know whether the attacker has only A or somehow obtained other credentials.

Once reuse is detected, treating the session as compromised is safer:

```text
Revoke session
```

This forces fresh authentication.

This is a classic security trade-off:

```text
Security
   ↑
Convenience
   ↓
```

For suspicious token reuse, security generally wins.

---

# 32. What If Reuse Was Just a Race Condition?

This is a subtle problem.

Suppose:

```text
Request A
Request B
```

both use the same refresh token because the frontend accidentally made duplicate refresh calls.

One wins:

```text
A → B
```

The second sees:

```text
A is no longer current
```

Should we immediately revoke the entire session?

That could log the user out unnecessarily.

This is why real-world refresh systems need to distinguish between:

```text
Expected concurrency
```

and:

```text
Actual token theft
```

Possible approaches include:

```text
Short reuse grace window
Refresh request deduplication
Client-side refresh locking
Server-side concurrency handling
Token-family logic
```

For our first implementation, we'll prioritize correctness and clear behavior before adding complicated grace periods.

# 33. Frontend Refresh Deduplication

Backend security is important, but the frontend can also prevent duplicate refreshes.

Imagine:

```text
API request A → 401
API request B → 401
API request C → 401
```

Instead of:

```text
A → refresh
B → refresh
C → refresh
```

the frontend can do:

```text
A ─┐
B ─┼──→ one refresh request
C ─┘
          ↓
      New access token
          ↓
     Retry A/B/C
```

This is often called:

> **Refresh request deduplication / single-flight refresh**

It's a very useful pattern for your React/Axios frontend.

# 36. Refresh Endpoint Pseudocode

Here's the conceptual service:

```typescript
async function refresh(refreshToken: string) {
  const tokenHash = hashRefreshToken(refreshToken);

  const session = await sessionRepository.findByTokenHash(
    tokenHash
  );

  if (!session) {
    throw invalidRefreshToken();
  }

  if (session.revokedAt) {
    throw invalidRefreshToken();
  }

  if (session.expiresAt <= new Date()) {
    throw invalidRefreshToken();
  }

  const newRefreshToken = generateRefreshToken();
  const newRefreshTokenHash =
    hashRefreshToken(newRefreshToken);

  const user = await userRepository.findById(
    session.userId
  );

  const accessToken = generateAccessToken(user);

  await sessionRepository.rotate({
    sessionId: session.id,
    oldTokenHash: tokenHash,
    newTokenHash: newRefreshTokenHash,
  });

  return {
    accessToken,
    refreshToken: newRefreshToken,
  };
}
```

This is intentionally simplified.

The important part is the workflow.

# 37. Where the Transaction Belongs

A clean architecture might be:

```text
Auth Service
     ↓

     ↓
Prisma transaction
```

The service owns the business workflow.

The repository owns the database operations.

For example:

```text
Auth Service
    ↓

    ↓
Prisma transaction
```

This keeps the controller thin.

# 38. Transaction Example

Conceptually:

```typescript
await prisma.$transaction(async (tx) => {
  const session = await tx.session.findFirst({
    where: {
      id: sessionId,
      refreshTokenHash: oldTokenHash,
      revokedAt: null,
    },
  });

  if (!session) {
    throw new InvalidRefreshTokenError();
  }

  await tx.session.update({
    where: {
      id: session.id,
    },
    data: {
      refreshTokenHash: newTokenHash,
      lastUsedAt: new Date(),
    },
  });
});
```

But there is a subtle issue:

> A transaction by itself doesn't automatically solve every concurrency problem.

We need appropriate isolation/conditional updates/locking strategy depending on the exact implementation.

---

# 39. Don't Overuse Database Locks

You might hear:

> "Just lock the row."

Sometimes that's appropriate.

But don't automatically reach for pessimistic locking.

Often:

```text
Conditional update
+
Unique constraint
+
Transaction
```

is enough.

Use the simplest concurrency mechanism that correctly enforces your invariant.

---

# 40. Our Core Invariant

An important engineering skill is defining the invariant.

For our refresh session:

> **Only the current, non-revoked, non-expired refresh credential may rotate the session.**

That's our security invariant.

Everything else follows from it.

```text
Current token?
      │
      ├── No → reject
      │
      └── Yes
           │
           ▼
      Not revoked?
           │
           ├── No → reject
           │
           └── Yes
                │
                ▼
           Not expired?
                │
                ├── No → reject
                │
                └── Yes
                     │
                     ▼
                  Rotate
```

# 41. Revocation Rules

We can define a clear policy:

### Logout

```text
Current session → revoked
```

### Logout all devices

```text
All user sessions → revoked
```

### Password change

```text
Existing sessions → revoked
```

### Password reset

```text
Existing sessions → revoked
```

### Refresh-token reuse

```text
Affected session/token family → revoked
```

### Session expiration

```text
Session → unusable
```

This gives the system predictable behavior.

# 42. What Happens to Access Tokens?

Remember:

```text
Access JWT
```

may still be valid for a short time after:

```text
logout
```

or:

```text
session revocation
```

because the access token is designed to be short-lived and independently verifiable.

So:

```text
Refresh revoked
+
Access token still valid for 5 minutes
```

can be acceptable depending on your threat model.

If immediate invalidation is required, introduce server-side access-token revocation/version checks.

Don't add that complexity unless you actually need it.

---

# 43. Why Short Access Tokens Matter Even More Now

Suppose:

```text
Access Token = 15 min
Refresh Token = 30 days
```

and refresh session gets revoked.

The attacker might still have:

```text
Access Token
```

but only for the remaining short period.

Therefore:

```text
Short access lifetime
+
Refresh revocation
```

gives us a strong balance.

# 🧠 Interview-Level Question

### "How would you securely implement refresh-token rotation?"

A strong answer:

> I would generate a cryptographically random refresh token, store only its hash in a server-side session, and keep the actual token in a secure HttpOnly cookie for a browser application. Each successful refresh would atomically replace the current refresh-token hash with a new one and issue a new access token and refresh token. If an already-consumed refresh token is presented again, I would treat it as potential token reuse and revoke the affected session or token family. The rotation operation should be designed to handle concurrent refresh requests safely using transactions and conditional database updates.

That's a strong backend-engineering answer.

# 🎯 Lesson 4.8 Takeaways

Keep these in your notes:

```text
1. Refresh-token rotation means each refresh consumes
   the previous refresh token.

2. Refresh tokens should be cryptographically random.

3. Store only a hash of the refresh token.

4. Keep refresh sessions server-side.

5. A refresh-token family represents the chain of rotated
   credentials for a session.

6. Reuse of an old refresh token can indicate token theft.

7. Suspicious reuse can trigger session/token-family revocation.

8. Logout should revoke the server-side refresh session.

9. "Logout all devices" should revoke all active sessions
   belonging to the user.

10. Password changes/resets should generally revoke existing
    sessions.

11. Refresh rotation must account for concurrent requests.

12. Transactions alone aren't enough; use appropriate
    conditional updates or concurrency controls.

13. Keep access tokens short-lived so revoked sessions don't
    leave long-lived access credentials.

14. Never log refresh tokens or other authentication secrets.

15. Define explicit security invariants before implementing
    concurrency logic.
```

# 🔥 The Most Important Concept

Don't memorize only:

```text
JWT
Refresh Token
Cookie
```

Understand the actual security model:

```text
                 SESSION
                    │
                    ▼
            Current Refresh Token
                    │
          ┌─────────┴─────────┐
          │                   │
       Valid                 Invalid
          │                   │
          ▼                   ▼
       Rotate               Reject
          │
          ▼
     New Refresh Token
          │
          ▼
     Old Token Dead
```

And:

```text
Old Token Used Again
        ↓
Replay / Reuse
        ↓
Potential Credential Theft
        ↓
Revoke Session
        ↓
Require Fresh Login
```

That's the core idea behind secure refresh-token rotation.
