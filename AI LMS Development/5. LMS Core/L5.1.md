# Lesson 5.1 — Introduction to LLMs & AI Application Architecture

Welcome to **Phase 5 — AI Engineering for the LMS**. 🚀

```text

  ↓

  ↓
```

Now we're going to add an **AI layer** without destroying that architecture.

The first thing to understand is:

> **An LLM is a component inside your application, not your entire application.**

Your AI LMS should eventually look roughly like this:

```text

                                      │               │
```

# 1. What Is an LLM?

**LLM = Large Language Model.**

An LLM is a machine-learning model trained on a very large amount of text and other data so that it can understand and generate language.

Examples include models from providers such as OpenAI, Anthropic, Google, Meta, etc.

For your application, you can think of an LLM as:

```text
Input
  ↓
LLM
  ↓
Generated output
```

For example:

```text
Input:

"Explain JWT authentication in simple words."

                ↓

              LLM

                ↓

"JWT authentication is a way..."
```

But an important point:

### Your application does not become an AI application just because it calls an LLM.

The interesting engineering work happens around the model:

```text
Your application
      ↓
Context
      ↓
Prompt
      ↓
LLM
      ↓
Validation
      ↓
Business logic
      ↓
Database
      ↓
User
```

That's what we're going to learn in Phase 5.

# 2. Traditional API vs AI API

You've already built normal REST APIs.

For example:

```http
GET /api/v1/courses/123
```

The backend knows exactly what operation to perform.

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
   ↓
Response
```

AI requests are different.

Consider:

```http
POST /api/v1/ai/tutor
```

with:

```json
{
  "message": "Explain middleware in Express"
}
```

The backend doesn't have a predefined answer for every possible question.

Instead:

```text
Request
   ↓
Controller
   ↓
AI Service
   ↓
LLM
   ↓
AI Response
```

Later, with RAG:

```text
Request
   ↓
Controller
   ↓
AI Service
   ↓
Retrieve relevant course content
   ↓
LLM
   ↓
Validate response
   ↓
Response
```

This difference is fundamental.

# 3. What Actually Happens When You Ask an LLM a Question?

Suppose the student asks:

> "What is middleware in Express?"

Your application eventually sends something conceptually like:

```text
You are an educational assistant.

Explain the following question to a beginner:

What is middleware in Express?
```

The model processes this input and generates tokens.

Conceptually:

```text
Input
 ↓
Tokenization
 ↓
Model processing
 ↓
Next-token prediction
 ↓
Next-token prediction
 ↓
Next-token prediction
 ↓
...
 ↓
Output
```

The model generates the response **token by token**.

---

# 4. What Is a Token?

A token is a small piece of text that the model processes.

A token isn't necessarily:

```text
one word = one token
```

For example:

```text
"authentication"
```

might be represented as multiple tokens depending on the tokenizer/model.

Similarly:

```text
"Hello world"
```

is broken into token representations before being processed.

You don't need to memorize tokenization details yet.

What matters for application development is:

### Tokens affect:

- context limits
    
- cost
    
- latency
    
- prompt size
    
- response size
    

So eventually you'll care about:

```text
Input tokens
+
Output tokens
=
Total token usage
```

# 5. Context Window

An LLM cannot process an infinite amount of information in a single request.

It has a **context window**.

Think of it as the amount of information the model can consider during one interaction.

For example:

```text
System instructions
+
Conversation history
+
Course content
+
Student question
+
Other context
```

all consume context.

Imagine:

```text
┌──────────────────────────────┐
│       Context Window         │
│                              │
│ System instructions          │
│ Conversation                 │
│ Course material              │
│ Retrieved documents           │
│ User question                │
│                              │
└──────────────────────────────┘
```

This becomes extremely important when we build **RAG in lessons 5.8–5.10**.

You don't want to send an entire 500-page course PDF to the model for every question.

Instead:

```text
500-page PDF
     ↓
retrieve relevant pieces
     ↓
send only relevant context
     ↓
LLM
```

That's one of the reasons RAG exists.

---

# 6. Prompt vs Context

These terms can sometimes be confusing.

Think of the **prompt** as the instructions/input you send to the model.

For example:

```text
You are an AI tutor.

Explain concepts using simple language.

Question:
What is middleware?
```

The broader **context** may include:

```text
System instructions
+
Previous conversation
+
Course information
+
Retrieved documents
+
Current question
```

So:

```text
Context
 ├── Instructions
 ├── Conversation history
 ├── Course material
 └── User question
```

Then the model generates the response.

---

# 7. System Instructions

A very important concept for your AI Tutor.

You don't want the model to behave like a random chatbot.

You want:

> "You are an educational assistant for this LMS."

For example, conceptually:

```text
You are an AI tutor.

Your goal is to help students understand course material.

Rules:
1. Explain concepts clearly.
2. Prefer simple examples.
3. Do not intentionally provide answers to restricted assessments.
4. If course context is provided, prioritize it.
5. If the information is unavailable, say that you don't have enough context.
```

This creates a consistent behavior.

Later we'll improve these prompts significantly.

---

# 8. Temperature

You will often see a setting called **temperature**.

It controls how much variation/randomness is allowed in generation.

Conceptually:

```text
Lower temperature
        ↓
More predictable
More consistent
```

while:

```text
Higher temperature
        ↓
More variation
More creative
```

For example:

### Quiz generation

You generally want:

```text
consistent
structured
predictable
```

### Brainstorming

You may want:

```text
more creative
varied
```

For your LMS, don't blindly use a high temperature everywhere.

Different AI features may have different requirements.

# 9. LLMs Are Not Your Database

This is one of the most important lessons.

Suppose your LMS has:

```text
Course: Advanced Node.js

Lesson:
"Redis is an in-memory data store..."
```

You should **not** think:

```text
LLM = database
```

Instead:

```text
PostgreSQL
     ↓
Source of truth
```

and:

```text
LLM
     ↓
Reasoning / generation
```

For example:

```text
Student
   ↓
"What is the Redis strategy taught in this course?"
   ↓
Backend
   ↓
Database / retrieval system
   ↓
Relevant content
   ↓
LLM
   ↓
Answer
```

This distinction will become extremely important when we build RAG.

# 10. LLMs Can Be Wrong

This is another critical concept.

An LLM can produce an answer that **sounds correct but isn't correct**.

This is commonly called a **hallucination**.

For example:

```text
Student:
"What does Lesson 4 say about Redis?"

LLM:
"Lesson 4 says Redis uses XYZ..."
```

But maybe Lesson 4 never said that.

Therefore:

```text
LLM output ≠ guaranteed truth
```

This is why your AI LMS needs:

- validation
    
- trusted context
    
- retrieval
    
- authorization
    
- error handling
    
- appropriate system instructions
    

Later, RAG will help ground answers in your actual course content.

# 11. AI Should Be a Service

Now we reach the most important architectural lesson.

You already learned:

```text
Controller
    ↓
Service
    ↓
Repository
```

Don't do this:

```ts
export async function askTutor(req, res) {
  const response = await someLLMProvider.call(...);

  res.json(response);
}
```

It might work.

But it's poor architecture for a growing application.

Instead:

```text
Controller
    ↓
AI Service
    ↓
AI Provider
```

For example:

```text
ai/
├── ai.controller.ts
├── ai.service.ts
├── ai.provider.ts
└── ai.types.ts
```

Then:

```text
ai.controller
      ↓
ai.service
      ↓
ai.provider
      ↓
LLM API
```

---

# 12. Why Separate the AI Provider?

Imagine today you use:

```text
Provider A
```

Later you want:

```text
Provider B
```

If you've scattered provider-specific code throughout your application:

```text
controller
service
routes
utils
jobs
...
```

changing providers becomes painful.

Instead:

```text
Application
     ↓
AI Service
     ↓
AI Provider Interface
     ↓
┌─────────────┬─────────────┐
│             │             │
Provider A  Provider B   Local Model
```

Your application doesn't need to know every provider's internal details.

This is an example of **abstraction**.

---

# 13. AI Provider Abstraction

Conceptually:

```ts
interface AIProvider {
  generateText(input: string): Promise<string>;
}
```

Then you could have:

```text
OpenAIProvider
AnthropicProvider
LocalProvider
```

all implementing the same interface.

Your AI service can use:

```text
AIProvider
```

rather than depending directly on one provider everywhere.

Don't worry about implementing this today—we'll build it properly in **5.2**.

# 14. AI Service vs AI Provider

Understand this distinction clearly.

### AI Service

Contains **your application's AI business logic**.

For example:

```text

```

### AI Provider

Handles communication with the external model.

```text

     ↓
Provider SDK/API
     ↓

```

So eventually:

```text
AI Controller
      ↓
AI Service
      ↓
AI Provider
      ↓
LLM
```

# 16. Where Does PostgreSQL Fit?

Your existing architecture doesn't disappear.

For example:

```text
Student
   ↓
AI Tutor
   ↓
AI Service
   ├── PostgreSQL
   │     └── conversations/messages
   │
   ├── Vector DB
   │     └── course embeddings
   │
   └── LLM
         └── generate response
```

Each component has a different responsibility.

|Component|Responsibility|
|---|---|
|PostgreSQL|Application data|
|Redis|Cache/jobs/rate limiting|
|Vector DB|Semantic retrieval|
|LLM|Generate/transform language|
|Backend|Business rules|
|Frontend|User interface|

This separation will save you from many architectural problems later.

# 17. AI Request Lifecycle

Let's trace your future AI Tutor.

Student writes:

```text
"Explain JWT authentication."
```

### Step 1 — Frontend

```text
POST /api/v1/ai/tutor
```

### Step 2 — Authentication middleware

```text
Who is this student?
```

### Step 3 — Authorization

```text
Can this student access this course?
```

### Step 4 — Controller

Receives the request.

### Step 5 — AI Service

Determines what needs to happen.

### Step 6 — Retrieval

Later we'll search relevant course content.

### Step 7 — AI Provider

Send:

```text
Instructions
+
Relevant context
+
Student question
```

### Step 8 — LLM

Generates the answer.

### Step 9 — Validation

Check the response.

### Step 10 — Persistence

Potentially save:

```text
conversation
message
AI usage
```

### Step 11 — Response

Send the answer back to React.

So:

```text
Student
   ↓
React
   ↓
Express
   ↓
Auth
   ↓
Authorization
   ↓
Controller
   ↓
AI Service
   ↓
Retrieval
   ↓
AI Provider
   ↓
LLM
   ↓
Validation
   ↓
PostgreSQL
   ↓
React
```

That's the architecture you should have in your head.
