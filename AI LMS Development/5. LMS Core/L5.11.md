# Lesson 5.11 — AI Evaluation & Observability

This is one of the most important lessons in Phase 5.

So far, we've learned how to **build AI features**:

```text
5.6 → Summarization
5.7 → Quiz Generation
5.8 → Embeddings
5.9 → Document Processing
5.10 → RAG
```

But now we need to answer a much harder engineering question:

> **How do we know whether our AI system is actually working well?**

An AI application isn't production-ready just because it returns an answer.

We need to measure:

```text
Quality
Correctness
Relevance
Latency
Token usage
Cost
Failures
Retrieval quality
```

That's what **evaluation + observability** is about.

---

# 1. Normal Backend vs AI Backend

In a normal API:

```text
Request
   ↓
Business Logic
   ↓
Database
   ↓
Response
```

We can inspect:

```text
HTTP status
latency
database errors
```

Pretty straightforward.

But an AI request looks like:

```text
Student Question
      ↓
Query Processing
      ↓
Embedding
      ↓
Vector Search
      ↓
Retrieved Chunks
      ↓
Prompt
      ↓
LLM
      ↓
Generated Answer
      ↓
Streaming
```

There are many more places where things can go wrong.

---

# 2. AI Can Fail in Many Different Ways

Imagine the student asks:

> "Why are refresh tokens used?"

Your Tutor answers:

> "Refresh tokens are used to store passwords securely."

That's obviously wrong.

But where did the problem occur?

Possibilities:

```text
Question
   ↓
❌ Query rewriting
   ↓
Embedding
   ↓
❌ Retrieval
   ↓
Wrong context
   ↓
Prompt
   ↓
LLM
```

Or:

```text
Question
   ↓
Retrieval ✓
   ↓
Correct context ✓
   ↓
Prompt ✓
   ↓
❌ LLM generation
```

Without observability, you only see:

```text
Wrong answer
```

You don't know **why**.

---

# 3. Evaluation vs Observability

These are related but different.

## Evaluation

Asks:

> **"How good is the AI?"**

Example:

```text
Does the answer correctly explain JWT?
```

---

## Observability

Asks:

> **"What happened inside the AI request?"**

Example:

```text
Which chunks were retrieved?
Which model was used?
How many tokens?
How long did retrieval take?
How long did generation take?
Did the request fail?
```

Think:

```text
Evaluation
    ↓
Quality

Observability
    ↓
Visibility
```

You need both.

---

# 4. The AI Request as a Trace

Think of one Tutor request as a **trace**.

```text
Trace
│
├── Authentication
│
├── Query processing
│
├── Embedding
│
├── Vector search
│
├── Context building
│
├── Prompt construction
│
├── LLM generation
│
└── Response
```

Each part can have timing and metadata.

For example:

```text
Trace ID: abc123

Embedding:       120ms
Vector Search:    35ms
Prompt Build:      2ms
LLM:            1850ms
Total:          2007ms
```

Now you can see where the time is going.

---

# 5. Why Trace IDs Matter

Suppose a student reports:

> "The AI Tutor gave me a wrong answer."

You need to find that exact request.

Give every AI request a unique ID:

```text
traceId = "tr_8f92..."
```

Then your logs can contain:

```text
[tr_8f92]
retrieval started

[tr_8f92]
retrieval completed

[tr_8f92]
llm request started

[tr_8f92]
llm request completed
```

Now you can reconstruct what happened.

This is the same correlation-ID concept you use in distributed backend systems.

---

# 7. Never Log API Keys

Obviously:

```text
❌ OPENAI_API_KEY
❌ database passwords
❌ access tokens
❌ refresh tokens
```

Your observability system should never become a security vulnerability.

Log:

```text
model
provider
request ID
latency
usage
```

but not credentials.

---

# 8. Don't Automatically Log Everything

You might think:

```text
console.log(req)
console.log(prompt)
console.log(response)
```

everywhere.

That's a bad production strategy.

You could expose:

```text
student conversations
private course content
personal information
sensitive data
```

Instead, decide deliberately:

```text
What do we need for debugging?
What must remain private?
What can be sampled?
What can be anonymized?
```

Observability needs privacy controls.

# 10. Latency

Latency means:

> How long did the request take?

Example:

```text
Tutor request
     ↓
2.4 seconds
```

But average latency isn't enough.

Suppose:

```text
99 requests → 1 second
1 request   → 30 seconds
```

Average might hide the bad experience.

That's why we care about:

```text
p50
p95
p99
```

---

# 11. Percentiles

### p50

50% of requests are faster than this.

Think:

> Typical user experience.

### p95

95% of requests are faster than this.

Think:

> What slower users experience.

### p99

99% are faster than this.

Think:

> Extreme tail latency.

For example:

```text
p50 = 1.2s
p95 = 3.8s
p99 = 8.5s
```

That's much more informative than:

```text
average = 1.7s
```

---

# 12. Measure Each Stage

Don't only measure:

```text
Total AI request = 3 seconds
```

Break it down:

```text
Authentication       20ms
Query rewrite        100ms
Embedding            180ms
Vector search         40ms
Prompt building        5ms
LLM                  2400ms
Database save          30ms
```

Now you know:

```text
LLM = bottleneck
```

This makes optimization much easier.

---

# 13. Time to First Token

For streaming AI responses, another useful metric is:

> **TTFT — Time to First Token**

Example:

```text
User sends question
        ↓
1.3 sec
        ↓
First token appears
```

That 1.3 seconds is TTFT.

The user may tolerate a response that takes 8 seconds if text starts appearing quickly.

Compare:

```text
A:
wait 5 seconds
then entire answer appears

B:
first token in 1 second
then answer streams for 5 seconds
```

B usually feels much faster.

---

# 14. Total Generation Time

Also track:

```text
Generation start
        ↓
Last token
```

For example:

```text
TTFT = 1.1s
Total generation = 4.7s
```

Together:

```text
User experience
+
LLM performance
```

become measurable.

# 16. Why RAG Can Increase Token Usage

Remember:

```text
Question
+
Retrieved chunks
+
Conversation history
+
System prompt
```

all become input.

If you retrieve too much:

```text
10 chunks
 ×
500 tokens
 =
5000 tokens
```

plus conversation history and instructions.

So:

> **Poor retrieval can increase both cost and latency.**

# 17. Cost Tracking

Your backend should eventually estimate:

```text
cost per request
```

Conceptually:

```text
inputTokens × inputPrice
+
outputTokens × outputPrice
```

The exact pricing depends on your chosen provider/model, so don't hard-code a fictional universal price.

Store enough usage information to calculate cost using the provider's current pricing.

# 20. AI Evaluation

Observability tells us:

```text
what happened
```

Evaluation tells us:

```text
was it good?
```

For your AI Tutor, create a dataset.

Example:

```text
Question:
What is a JWT?

Expected concept:
JWT is a token format used to transmit claims
between parties and can be used for authentication.
```

Then run the Tutor.

Compare:

```text
Expected
   vs
Generated
```

---

# 21. Evaluation Dataset

Create something like:

```text
ai-evaluation/
├── tutor-questions.json
├── quiz-generation.json
└── summarization.json
```

Example:

```json
{
  "question": "What is a JWT?",
  "courseId": "backend-101",
  "expectedConcepts": [
    "JSON Web Token",
    "claims",
    "authentication"
  ]
}
```

You don't necessarily need one exact expected sentence.

For AI systems, **expected concepts** can often be more useful.

---

# 22. Why Exact String Matching Is Bad

Suppose expected answer:

```text
JWT is a token used for authentication.
```

AI says:

```text
A JSON Web Token can be used to authenticate
requests between a client and server.
```

Different words.

Same concept.

If you use:

```text
expected === generated
```

you mark it wrong.

That's not useful.

AI evaluation needs semantic and rubric-based thinking.

---

# 23. Rubric-Based Evaluation

Create criteria:

```text
Correctness       0–5
Relevance         0–5
Groundedness      0–5
Clarity           0–5
Completeness      0–5
```

Example:

```text
Correctness:   5
Relevance:     5
Groundedness:  4
Clarity:       5
Completeness:  4
```

Total:

```text
23 / 25
```

Now you have a structured evaluation.

---

# 24. Groundedness

For RAG, one of the most important metrics is:

> **Is the answer supported by the retrieved context?**

Suppose the retrieved context says:

```text
JWT signatures verify token integrity.
```

But the AI says:

> "JWT always uses RSA-4096."

If the context doesn't support that claim, we have a grounding problem.

So evaluate:

```text
Answer claims
      ↓
Supported by retrieved context?
```

---

# 25. Retrieval Evaluation

We also need to evaluate retrieval independently.

Suppose:

```text
Question:
Why does JWT use a signature?
```

Expected chunk:

```text
JWT Signature section
```

Run:

```text
Vector Search
```

If the correct chunk appears in:

```text
Top 5
```

that's a retrieval success.

This gives us:

```text
Recall@5
```

---

# 26. Retrieval Metrics

Useful metrics include:

```text
Recall@K
Precision@K
MRR
NDCG
```

You don't need to master all of them immediately.

For your LMS, start with:

```text
Recall@5
```

because it's easy to understand.

Question:

> Did the relevant chunk appear in the first five results?

---

# 27. MRR — Mean Reciprocal Rank

Suppose the relevant result appears at:

```text
Rank 1 → 1/1 = 1.0
Rank 2 → 1/2 = 0.5
Rank 3 → 1/3 ≈ 0.33
```

MRR averages these values across queries.

Higher is better.

It rewards getting the correct result near the top.

---

# 28. Retrieval Evaluation Example

Suppose 5 questions:

```text
Q1 → relevant chunk rank 1
Q2 → rank 2
Q3 → rank 1
Q4 → rank 5
Q5 → not found
```

You can calculate:

```text
Recall@5 = 4/5 = 80%
```

This immediately tells you:

> Retrieval needs improvement.

For your LMS:

```text

├── ambiguous questions
```

# 30. Include Hard Questions

Don't only test:

```text
"What is JWT?"
```

Also test:

```text
"Why should refresh tokens have longer lifetimes?"

"What happens if an access token expires?"

"Compare access tokens and refresh tokens."

"What does this course say about token rotation?"
```

And:

```text
"How does Kubernetes scheduling work?"
```

when Kubernetes isn't in the course.

That last one tests whether your Tutor can say:

> "I don't have enough course information."

---

# 31. Regression Testing

This is a very important engineering concept.

Suppose today:

```text
RAG score = 91%
```

You change:

```text
chunk size
```

and suddenly:

```text
RAG score = 76%
```

Your evaluation dataset catches the regression.

So:

```text
Code/Prompt/Model change
        ↓
Run evaluations
        ↓
Compare metrics
```

This is how AI development becomes engineering rather than guessing.

---

# 32. Prompt Versioning

Suppose you have:

```text
Tutor prompt v1
```

Then you improve it:

```text
Tutor prompt v2
```

Store:

```text
promptVersion = "tutor-v2"
```

with the AI request.

Now if something changes:

```text
Trace
  ↓
promptVersion = tutor-v2
```

you know which prompt produced the answer.

---

# 33. Model Versioning

Same idea.

Record:

```text
model
```

and, when available, the exact model/version identifier you used.

For example:

```text
model = chosen-model
```

Don't assume that model behavior will remain identical forever.

Your evaluation system should tell you if a model change affects quality.

---

# 34. Embedding Model Versioning

```text

```

Suppose you change embedding models.

```text

```

```text

```

That's a compatibility problem.

If you migrate embeddings:

```text

 ↓
Re-embed documents
 ↓
Model B vectors
```

Track the embedding model version.

Suppose one Tutor request retrieves:

```text

Chunk B
Chunk C

```

You may want to know:

```text

Which chunks were actually included?
```

So:

```text
ai_requests
     │
     └── ai_retrievals
             ├── chunk A
             ├── chunk B
             ├── chunk C
             └── chunk D
```

This makes RAG debugging much easier.

# 55. Don't Store Huge Prompts Blindly

You may want to store prompts for debugging, but large prompts can:

```text
increase database size
increase privacy risk
increase storage cost
```

Instead consider:

```text
promptVersion
promptHash
selected metadata
```

and only retain full prompts/responses under an appropriate retention policy when needed.

For development, more detailed logging may be acceptable.

For production, be much more careful.

# 58. Logs vs Metrics vs Traces

These three concepts are important.

### Logs

Tell you:

> What happened?

```text

```

### Metrics

Tell you:

> How often/how much?

```text

```

### Traces

Tell you:

> What happened across the entire request?

```text
Request
 ↓
Embedding
 ↓
Search
 ↓
LLM
 ↓
Response
```

Together:

```text
Logs
+
Metrics
+
Traces
=
Observability
```
