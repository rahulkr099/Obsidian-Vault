# 2. First Principle — Never Put the API Key in React

This is extremely important.

### ❌ Bad

```text
React
   ↓
LLM API
```

with the API key inside React.

Why?

Because frontend code is delivered to the user's browser.

Anything shipped to the browser should be considered potentially visible to the user.

You don't want:

```text
OPENAI_API_KEY=...
```

inside your frontend.

---

# 3. Correct Architecture

Use:

```text
React
   ↓
Your Backend
   ↓
LLM Provider
```

Therefore:

```text
                  Internet
                     │
                     ▼
                  React
                     │
                     │ HTTPS
                     ▼
              Your Express API
                     │
                     │ API key
                     ▼
                LLM Provider
```

The API key remains on the server.

---

# 4. Environment Variables

Your backend should have something like:

```env
AI_API_KEY=your-secret-key
```

And:

```env
AI_MODEL=your-model
```

Never commit the real `.env` file.

Your `.gitignore` should contain:

```gitignore
.env
.env.*
!.env.example
```

Then create:

```text
.env.example
```

with:

```env
AI_API_KEY=
AI_MODEL=
```

This file can safely be committed because it contains no secret.

---

# 5. Why Environment Variables?

Imagine your code contains:

```ts
const apiKey = "sk-xxxxxxxx";
```

That's a serious problem.

It can accidentally end up in:

```text
GitHub
logs
screenshots
shared code
Docker images
```

Instead:

```ts
const apiKey = process.env.AI_API_KEY;
```

The secret stays outside the source code.

---

# 6. Don't Access Environment Variables Everywhere

You might initially write:

```ts
process.env.AI_API_KEY
```

inside every file.

Avoid that.

Create a central configuration layer.

For example:

```text
src/
├── config/
│   └── env.ts
```

Conceptually:

```ts
const env = {
  aiApiKey: process.env.AI_API_KEY,
  aiModel: process.env.AI_MODEL,
};
```

Then your application uses:

```ts
env.aiApiKey
```

instead of repeatedly accessing:

```ts
process.env.AI_API_KEY
```

This gives you a single place to validate configuration.

---

# 7. Validate Environment Variables

This is even better.

Suppose the application starts without:

```env
AI_API_KEY
```

You don't want to discover the problem only when a student asks the AI Tutor something.

Instead:

```text
Application starts
       ↓
Validate environment
       ↓
Missing AI_API_KEY
       ↓
Fail immediately
```

This is called **fail fast**.

For your TypeScript backend, Zod is a good choice because you've already been using it.

Conceptually:

```ts
const envSchema = z.object({
  AI_API_KEY: z.string().min(1),
  AI_MODEL: z.string().min(1),
});
```

Then:

```text
process.env
    ↓
Zod
    ↓
validated configuration
```

We'll use this pattern throughout the project.

# 8. Provider SDK vs Raw HTTP

There are generally two ways to communicate with an LLM provider.

### Option 1

Use the provider's SDK:

```text
Node.js
   ↓
Provider SDK
   ↓
LLM API
```

### Option 2

Use HTTP directly:

```text
Node.js
   ↓
fetch()
   ↓
HTTPS
   ↓
LLM API
```

Both approaches are useful.

For your LMS, I recommend understanding **both concepts**, but using the official SDK when it makes the integration cleaner.

Why?

Because SDKs usually handle things such as:

- request formatting
    
- authentication headers
    
- response parsing
    
- types
    
- streaming
    
- provider-specific details
    

---

# 9. The Basic LLM Request

Conceptually, an LLM request contains:

```text
model
+
messages/input
+
optional configuration
```

For example:

```json
{
  "model": "some-model",
  "messages": [
    {
      "role": "user",
      "content": "Explain middleware in Express."
    }
  ]
}
```

The provider processes this and returns generated content.

Think:

```text
Input
 ↓
Model
 ↓
Generated output
```

---

# 10. Messages and Roles

Modern LLM APIs commonly work with different message roles.

The most important ones for now are:

```text
system
user
assistant
```

Think of them like:

### `system`

Defines behavior.

```text
You are an educational tutor.
```

### `user`

The student's request.

```text
Explain middleware.
```

### `assistant`

Previous AI responses.

```text
Middleware is...
```

Therefore a conversation can conceptually look like:

```text
system:
You are an AI tutor.

user:
What is middleware?

assistant:
Middleware is...

user:
Give me an example.
```

We'll use this heavily in **5.4**.

# 11. First AI Service

Let's keep our architecture clean.

```text
src/
└── modules/
    └── ai/
        ├── ai.controller.ts
        ├── ai.service.ts
        ├── ai.routes.ts
        └── ai.types.ts
```

The controller should be small.

Conceptually:

```ts
export async function chat(req, res) {
  const result = await aiService.chat(req.body.message);

  res.json({
    success: true,
    data: result,
  });
}
```

Notice:

### The controller doesn't know how the LLM works.

It simply delegates.

---

# 12. AI Service

The service contains application logic.

Conceptually:

```ts
class AIService {
  async chat(message: string) {
    // prepare AI request
    // call provider
    // process response

    return response;
  }
}
```

Later this becomes much more powerful:

```text
AIService
   │
   ├── tutor()
   ├── summarize()
   ├── generateQuiz()
   └── generateStudyPlan()
```

That's why we created an AI service layer.

---

# 13. AI Provider

Now create another abstraction.

```text
src/
└── modules/
    └── ai/
        ├── ai.controller.ts
        ├── ai.service.ts
        ├── ai.provider.ts
        └── ai.routes.ts
```

The provider's responsibility:

> Talk to the external LLM service.

Conceptually:

```ts
interface AIProvider {
  generateText(input: AIInput): Promise<string>;
}
```

Then:

```text
AI Service
    ↓
AI Provider
    ↓
External LLM
```

---

# 14. Why Three Layers?

You might think:

> "Rahul, isn't this too much code for one API?"

For a simple chatbot, maybe.

But we're building a large LMS.

Consider what we'll eventually have:

```text
AI Service
    │
    ├── Tutor
    ├── Summarizer
    ├── Quiz Generator
    └── Study Planner
            │
            ▼
       AI Provider
            │
      ┌─────┼─────┐
      ↓     ↓     ↓
   Provider A
   Provider B
   Local Model
```

This separation gives you flexibility.

---

# 15. Provider Interface

A simple abstraction could look like:

```ts
export interface AIProvider {
  generateText(input: string): Promise<string>;
}
```

Then an implementation:

```ts
export class SomeAIProvider implements AIProvider {
  async generateText(input: string): Promise<string> {
    // Call external API
    // Return generated text
  }
}
```

The AI service doesn't care which provider is being used.

That's the important part.

# 17. Validation Comes Before the AI

Never blindly accept:

```json
{
  "message": "..."
}
```

Validate it.

For example:

```ts
const chatSchema = z.object({
  message: z
    .string()
    .trim()
    .min(1)
    .max(4000),
});
```

Why?

Because users can send:

```json
{
  "message": ""
}
```

or enormous requests.

Validation protects your application and controls unnecessary AI usage.

---

# 18. AI Requests Can Be Expensive

This is an important difference from normal APIs.

Suppose someone repeatedly sends:

```text
POST /api/v1/ai/chat
```

Every request might consume:

```text
tokens
money
CPU
network
provider quota
```

Therefore your AI endpoints need stronger protection.

Eventually we'll add:

```text
Authentication
      ↓
Authorization
      ↓
Validation
      ↓
Rate Limiting
      ↓
AI Request
```

Not:

```text
Internet
   ↓
Unlimited LLM requests
```

---

# 19. Error Handling

External services can fail.

For example:

```text
LLM provider unavailable
API key invalid
rate limit exceeded
request timeout
network failure
model unavailable
invalid response
```

Your backend shouldn't expose raw provider errors to the student.

Bad:

```json
{
  "error": "ProviderError: HTTP 429..."
}
```

Better:

```json
{
  "success": false,
  "error": {
    "code": "AI_SERVICE_UNAVAILABLE",
    "message": "The AI service is temporarily unavailable."
  }
}
```

Internally, however, log enough information to diagnose the issue.

---

# 20. Timeouts

Imagine:

```text
Student
 ↓
AI request
 ↓
LLM
 ↓
...
 ↓
30 seconds
```

You don't want your server waiting forever.

Use a reasonable timeout.

Conceptually:

```text
Request
   ↓
Start timer
   ↓
LLM
   ↓
Timeout?
 ┌─┴─┐
No  Yes
│    │
↓    ↓
OK  Error
```

Later, we'll combine this with retries and fallbacks.

---

# 21. Retries

Some failures are temporary.

For example:

```text
Request
 ↓
Provider
 ↓
Temporary network error
```

You may retry.

But be careful.

Don't do:

```text
retry forever
```

Instead:

```text
Attempt 1
   ↓
failed
   ↓
Attempt 2
   ↓
failed
   ↓
Attempt 3
   ↓
stop
```

Also, not every error should be retried.

For example:

```text
Invalid API key
```

doesn't become valid just because you retry it.

You should eventually record useful information such as:

```text
requestId
userId

output tokens
latency

```

For example:

```text

──────────────

model: xyz
latency: 1.8s

outputTokens: 430
status: success
```

But **don't blindly log the student's complete private message**.

AI logging can itself become a privacy issue.

---

# 23. Don't Store Secrets in Logs

Never log:

```text
API key
refresh token
password
authorization header
```

For example, avoid:

```ts
console.log(process.env.AI_API_KEY);
```

Obviously, that would be disastrous in production.

# 27. One Important Improvement: Dependency Injection

As the project becomes larger, don't instantiate everything randomly inside services.

Instead, conceptually:

```text
AI Provider
    ↓
AI Service
    ↓
Controller
```

The service receives the provider.

For example:

```ts
const provider = new SomeAIProvider();

const aiService = new AIService(provider);
```

Now testing becomes easier.

You can replace the real provider with:

```text
FakeAIProvider
```

during tests.

Then:

```text
AI Service
    ↓
Fake Provider
```

instead of making real AI requests.

That's going to be very useful when we reach testing later.

---

# 28. AI Provider Abstraction — Why This Matters

Imagine your production environment uses:

```text
Provider A
```

but tests use:

```text
Fake Provider
```

Architecture:

```text
                 AI Service
                     │
                     ▼
                AIProvider
                 /       \
                /         \
               ▼           ▼
        Real Provider   Fake Provider
```

This is much easier to test.

It also means your business logic doesn't become tightly coupled to one external company.

# 🎯 Lesson 5.2 Takeaway

The most important architecture to remember is:

```text
                Client
                  ↓
             Express API
                  ↓
             Controller
                  ↓
              AI Service
                  ↓
             AI Provider
                  ↓
                LLM
```

And the security boundary is:

```text
┌─────────────────────────────┐
│          SERVER             │
│                             │
│  API Key                    │
│     ↓                       │
│  AI Provider                │
│     ↓                       │
│  LLM                        │
│                             │
└─────────────────────────────┘
             ↑
             │
          HTTPS
             │
             ↓
┌─────────────────────────────┐
│         BROWSER             │
│          React              │
└─────────────────────────────┘
```

**Never expose the LLM API key to the browser.**

And one more important principle:

> **Your AI service should contain your application's AI logic; your AI provider should contain the provider-specific integration.**

That separation will pay off heavily when we reach **RAG, testing, multiple models, and AI security**.
