# Lesson 5.4 — Building the AI Tutor

In **5.1–5.3**, we built the foundation:

```text
5.1 → How LLM applications work
5.2 → Connect Node.js + TypeScript to an LLM
5.3 → Design predictable prompts
```

Now we combine those concepts into the **first real AI feature of your LMS: the AI Tutor**.

This is the first lesson where the AI becomes a genuine part of the product.

---

# 1. What Are We Building?

A student should be able to open a course and ask:

> "What is middleware in Express?"

The system should eventually work like this:

```text
Student
   ↓
React
   ↓
POST /api/v1/ai/tutor
   ↓
Authentication
   ↓
Authorization
   ↓
AI Controller
   ↓
AI Tutor Service
   ↓
Prompt Builder
   ↓
AI Provider
   ↓
LLM
   ↓
Response
   ↓
React
```

Later, after we implement RAG:

```text
Student
   ↓
Question
   ↓
Retrieve course material
   ↓
Relevant context
   ↓
Prompt
   ↓
LLM
   ↓
Course-grounded answer
```

For **5.4**, we'll focus on the basic Tutor first.

---

# 2. What Makes This Different From a Normal Chatbot?

A generic chatbot might simply do:

```text
Question
   ↓
LLM
   ↓
Answer
```

Our LMS Tutor should know about the application around it:

```text
Student
Course
Module
Lesson
Conversation
Question
```

For example:

```text
Student: Rahul
Course: Backend Engineering
Module: Authentication
Lesson: JWT
Question: "Why do we need refresh tokens?"
```

That context can eventually help the AI produce a much more useful answer.

---

# 3. The First Version

Don't make the first version too complicated.

Our V1:

```text
Student question
      ↓
AI Tutor Service
      ↓
Prompt
      ↓
LLM
      ↓
Answer
```

We'll gradually add:

```text
V2 → conversation history
V3 → course/lesson context
V4 → RAG
V5 → personalization
```

This is much easier to build and debug.

# 4. AI Tutor API

Let's define our first endpoint:

```http
POST /api/v1/ai/tutor
```

Request:

```json
{
  "message": "Explain middleware in Express."
}
```

Response:

```json
{
  "success": true,
  "data": {
    "message": "Middleware is a function that runs..."
  }
}
```

Later we'll add:

```json
{
  "courseId": "...",
  "lessonId": "...",
  "conversationId": "...",
  "message": "..."
}
```

But don't add unnecessary fields before we need them.

---

# 5. Authentication Comes First

Your AI Tutor should not be an anonymous unlimited LLM endpoint.

The request should go through:

```text
Request
   ↓
Authentication
   ↓
AI Tutor
```

For example:

```text
Authorization: Bearer <access-token>
```

Your authentication middleware identifies:

```text
req.user
```

Then the AI service knows which student is making the request.

This becomes very important later for:

- conversations
    
- course access
    
- rate limiting
    
- AI usage
    
- personalization
    

---

# 6. Authorization

Authentication answers:

> **Who are you?**

Authorization answers:

> **Are you allowed to do this?**

Suppose the Tutor is attached to a paid/private course.

You don't want:

```text
Student A
   ↓
Course B content
   ↓
AI Tutor
```

if Student A isn't enrolled in Course B.

Eventually:

```text
Student
   ↓
Authentication
   ↓
Enrollment check
   ↓
Course context
   ↓
AI Tutor
```

This is one of the most important security concepts in your AI LMS.

---

# 7. Request Validation

Use the validation pattern you've already learned.

For example:

```ts
const tutorSchema = z.object({
  message: z
    .string()
    .trim()
    .min(1)
    .max(4000),
});
```

Then:

```text
HTTP request
    ↓
Zod
    ↓
Valid?
 ┌──┴──┐
No    Yes
↓      ↓
400   AI Tutor
```

Never send an empty or massive request directly to the LLM.

---

# 8. Controller

The controller should remain thin.

Conceptually:

```ts
export async function tutor(req, res) {
  const result = await tutorService.ask({
    userId: req.user.userId,
    message: req.body.message,
  });

  return res.json({
    success: true,
    data: result,
  });
}
```

Notice what the controller does **not** do:

```text
❌ Build giant prompt
❌ Call LLM
❌ Save conversation
❌ Check database manually
❌ Calculate tokens
```

Those belong elsewhere.

---

# 9. Tutor Service

The Tutor Service is responsible for the application logic.

Conceptually:

```ts
class TutorService {
  async ask(input: TutorInput) {
    // prepare context
    // build prompt
    // call provider
    // process result

    return {
      message: response,
    };
  }
}
```

Think:

```text
Controller
    ↓
TutorService
    ↓
PromptBuilder
    ↓
AIProvider
```

---

# 10. Tutor Prompt

From lesson 5.3, we already know the prompt should define behavior.

A basic Tutor prompt could be:

```text
You are an AI tutor for an online learning platform.

Your goal is to help students understand technical concepts.

Use simple language and practical examples.

If the question is technical, explain unfamiliar terms.

Do not invent course-specific information.

Student question:
{question}
```

Then:

```text
{question}
```

gets replaced with the student's actual message.

---

# 11. Prompt Builder

Don't construct the prompt directly inside your provider.

Create something like:

```text
ai/
├── prompts/
│   └── tutor.prompt.ts
```

Conceptually:

```ts
export function buildTutorPrompt(input: {
  question: string;
}) {
  return `
You are an AI tutor...

Student question:
${input.question}
`;
}
```

Then:

```text
TutorService
     ↓
buildTutorPrompt()
     ↓
AIProvider
```

This separation will become very useful later.

---

# 12. AI Provider

The provider is responsible for communicating with the external model.

Conceptually:

```ts
interface AIProvider {
  generateText(input: AIRequest): Promise<string>;
}
```

Then:

```text
TutorService
      ↓
AIProvider
      ↓
LLM API
```

The Tutor Service doesn't need to know whether the provider uses:

```text
Provider A
Provider B
Local model
```

It only needs the interface.

---

# 13. Why This Architecture Is Good

Imagine your application grows.

You eventually have:

```text
Tutor
Summarizer
Quiz Generator
Study Planner
```

Without separation:

```text
Everything
   ↓
One giant AI file
```

That becomes difficult to maintain.

Instead:

```text
AI
├── Tutor
├── Summarizer
├── Quiz Generator
└── Study Planner
       │
       ▼
   AI Provider
```

Each feature has its own business logic.

---

# 14. Conversation History

Now we introduce an important feature.

Suppose the student asks:

```text
User:
What is JWT?
```

AI:

```text
JWT is a token format...
```

Then the student asks:

```text
User:
Why do we need refresh tokens?
```

The second question depends on the first answer.

If we send only:

```text
"Why do we need refresh tokens?"
```

the model may still answer correctly, but it doesn't have the conversation context.

Instead:

```text
Conversation
├── User: What is JWT?
├── Assistant: JWT is...
└── User: Why do we need refresh tokens?
```

can be sent to the model.

---

# 15. Database Design for Conversations

Your roadmap already included:

```text
ai_conversations
ai_messages
```

That's a good design.

Think:

```text
ai_conversations
-----------------
id
userId
courseId
title
createdAt
updatedAt
```

and:

```text
ai_messages
------------
id
conversationId
role
content
createdAt
```

Relationship:

```text
User
 │
 └── Conversations
        │
        └── Messages
              ├── user
              ├── assistant
              ├── user
              └── assistant
```

---

# 16. Why Separate Conversations and Messages?

Don't put everything inside one huge record.

Bad design:

```text
conversation
{
  userId,
  messages: [...]
}
```

It might work initially, but relational data becomes harder to query and maintain.

Better:

```text
Conversation
     │
     ├── Message
     ├── Message
     ├── Message
     └── Message
```

Now you can easily:

```text
fetch conversation
fetch latest messages
count messages
paginate messages
delete conversation
```

---

# 17. Message Roles

Store the role:

```text
user
assistant
```

Potentially later:

```text
system
tool
```

For example:

```text
ai_messages

id | conversationId | role      | content
---|----------------|-----------|----------------
1  | abc            | user      | What is JWT?
2  | abc            | assistant | JWT is...
3  | abc            | user      | Why use refresh tokens?
```

This makes reconstructing the conversation straightforward.

---

# 18. Should We Store the System Prompt?

This depends on your design.

You don't necessarily need to store the complete system prompt in every message.

You can version it:

```text
TUTOR_PROMPT_VERSION = "1.0"
```

and store metadata such as:

```text
promptVersion
model
```

with the AI interaction.

Why?

Because later you may change:

```text
Tutor Prompt v1
```

to:

```text
Tutor Prompt v2
```

and want to know which version produced an answer.

# 21. Don't Send Unlimited History

This is important.

Imagine a student has:

```text
500 messages
```

You don't necessarily want:

```text
all 500 messages
   ↓
LLM
```

Every time.

That causes:

- larger requests
    
- higher cost
    
- slower responses
    
- context-window pressure
    

Instead, eventually we can use:

```text
Latest N messages
+
Conversation summary
+
Current question
```

For example:

```text
Conversation summary
       +
last 10 messages
       +
current question
```

We'll explore this later as the AI system gets more advanced.

# 22. Course Context

Now we start making the Tutor LMS-aware.

Suppose:

```text

Lesson:
Authentication

```

We can provide:

```text

Lesson:

```

This gives the AI additional context.

But there's a critical distinction:

### Course metadata is not the same as course content.

For example:

```text
Course:
Node.js Backend Engineering
```

doesn't tell the AI what your lesson actually teaches.

That's why RAG will come later.

As your application grows, structured message construction is better.

Conceptually:

```text

      ↓

      ↓

      ↓

      ↓

```

# 26. Response Handling

The provider returns something like:

```text
generated text
```

The Tutor Service should process it.

At minimum:

```text
empty response?
    ↓
error
```

Otherwise:

```text
response
   ↓
save assistant message
   ↓
return to controller
```

Don't save:

```text
undefined
null
empty string
```

as a successful AI response.

---

# 27. AI Errors vs Application Errors

Not every error is the same.

### Application error

```text
Conversation doesn't exist
```

### Authorization error

```text
Student isn't enrolled
```

### Validation error

```text
message is empty
```

### Provider error

```text
LLM unavailable
```

### Rate limit

```text
Too many AI requests
```

These should eventually have different error codes.

For example:

```json
{
  "success": false,
  "error": {
    "code": "AI_PROVIDER_UNAVAILABLE",
    "message": "The AI service is temporarily unavailable."
  }
}
```

---

# 28. Rate Limiting the Tutor

AI endpoints deserve special treatment.

Suppose someone writes a script:

```text
while(true) {
    POST /ai/tutor
}
```

Without protection:

```text
Your server
   ↓
LLM provider
   ↓
💸💸💸
```

So eventually we'll implement:

```text
User
 ↓
Rate Limiter
 ↓
AI Tutor
```

For example, you could have different limits for:

```text
normal API → generous limit
AI API → stricter limit
```

Redis will later make this more powerful.

# 🎯 Lesson 5.4 Takeaways

You should now understand how to build the first real AI feature of the LMS.

The important concepts are:

```text
1. AI Tutor is an application feature, not just an API call.

2. Authentication should happen before AI access.

3. Authorization matters when course content is involved.

4. Controllers should remain thin.

5. Tutor business logic belongs in a service.

6. Prompt construction should be separated from provider code.

7. Conversations and messages should be persisted separately.

8. Don't send unlimited conversation history.

9. AI responses should be treated as untrusted output.

10. Rate limits and usage tracking matter because AI calls cost money.
```

And the architecture:

```text

                 Authentication
```
