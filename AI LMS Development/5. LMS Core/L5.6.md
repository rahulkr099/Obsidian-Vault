# Lesson 5.6 — AI Summarization Pipeline

In **5.5**, we made the AI Tutor stream responses progressively.

Now we're building the second useful AI feature for your LMS:

> **Automatically summarize course lessons into useful study notes.**

The roadmap defines this feature as:

```text
Lesson
  ↓
AI
  ↓
Short summary
  ↓
Key concepts
  ↓
Important points
```

This lesson is important because we'll introduce a major AI engineering concept:

> **Structured AI output.**

Instead of asking the LLM for a random paragraph, we'll ask it to produce data that our backend can validate and store safely.

---

# 1. What Are We Building?

Suppose an instructor has this lesson:

```text
Lesson: PostgreSQL Indexes

Content:

An index is a data structure that helps a database
find rows more efficiently...

Indexes can improve read performance but may increase
storage requirements and write overhead...
```

The instructor clicks:

```text
Generate AI Summary
```

Our system produces:

```text
Summary:
An index helps PostgreSQL find rows more efficiently...

Key Concepts:
- Database indexes
- Query performance
- Storage overhead
- Write performance

Takeaways:
- Indexes can speed up reads.
- Indexes consume additional storage.
- Too many indexes can affect writes.
```

The architecture:

```text
Lesson
  ↓
Summarization Service
  ↓
Prompt Builder
  ↓
AI Provider
  ↓
LLM
  ↓
Structured Output
  ↓
Zod Validation
  ↓
PostgreSQL
```

---

# 2. Why Summarization Is Useful in an LMS

A normal LMS gives students:

```text
Long lesson
    ↓
Student reads everything
```

Your AI LMS can provide:

```text
Long lesson
    ↓
AI Summary
    ↓
Quick revision
```

This can help with:

- revision
    
- exam preparation
    
- understanding long lessons
    
- extracting important concepts
    
- generating study notes
    

But there's an important rule:

> The AI should summarize the actual lesson content, not invent a new lesson.

---

# 3. Who Should Generate the Summary?

There are two good possibilities.

### Instructor-generated

```text
Instructor
   ↓
Create lesson
   ↓
Generate summary
   ↓
Save summary
```

This is ideal for creating reusable course material.

### Student-generated

```text
Student
   ↓
Open lesson
   ↓
"Summarize this"
   ↓
AI
```

This can be more personalized.

For your first implementation, I'd recommend:

```text
Instructor
   ↓
Generate canonical lesson summary
   ↓
Save it
```

Then later you can add student-specific summaries.

---

# 4. Why We Shouldn't Store the AI Response as Plain Text Only

You could ask:

```text
"Summarize this lesson."
```

and save:

```text
summary = "..."
```

That works.

But we want more useful data.

Instead:

```json
{
  "summary": "...",
  "keyConcepts": [
    "...",
    "...",
    "..."
  ],
  "takeaways": [
    "...",
    "...",
    "..."
  ]
}
```

Now your frontend can display each section separately.

---

# 5. Structured Output

This is the major concept of today's lesson.

Normal AI output:

```text
PostgreSQL indexes are...
They help...
They can also...
```

Structured output:

```json
{
  "summary": "PostgreSQL indexes...",
  "keyConcepts": [
    "Indexes",
    "Query performance",
    "Write overhead"
  ],
  "takeaways": [
    "Indexes speed up reads",
    "Indexes require storage"
  ]
}
```

Think:

```text
Unstructured AI
       ↓
Text

Structured AI
       ↓
Data
```

For an application, structured data is much easier to work with.

---

# 6. Why Structured Output Matters

Suppose your React frontend wants:

```text
Summary
Key Concepts
Important Takeaways
```

If the AI returns random Markdown:

```text
## Summary
...
```

your backend has to interpret that text.

That's fragile.

Instead:

```text
LLM
 ↓
Structured object
 ↓
Zod
 ↓
Database
```

Now your application knows exactly what each field means.

---

# 7. Define the Schema First

Before asking the AI for output, define what your application expects.

For example:

```ts
const summarySchema = z.object({
  summary: z.string().min(1),
  keyConcepts: z.array(z.string()).min(1).max(10),
  takeaways: z.array(z.string()).min(1).max(10),
});
```

This gives you a contract:

```text
summary       → string
keyConcepts   → array of strings
takeaways     → array of strings
```

Now the AI output can be checked against that contract.

---

# 8. AI Output Is Untrusted

This principle from the previous lessons becomes extremely important here.

Never think:

```text
LLM
 ↓
valid JSON
 ↓
database
```

Instead:

```text
LLM
 ↓
AI output
 ↓
Parse
 ↓
Validate
 ↓
Business rules
 ↓
Database
```

The AI is an external system.

Treat its output like you would treat an external API response.

# 10. The Summarization API

We could design an endpoint like:

```http
POST /api/v1/ai/summarize
```

Request:

```json
{
  "lessonId": "lesson_123"
}
```

This is better than sending the entire lesson from React:

```json
{
  "lessonId": "lesson_123",
  "content": "very large lesson..."
}
```

Why?

Because the backend already owns the lesson.

The backend can do:

```text
lessonId
   ↓
PostgreSQL
   ↓
lesson content
```

This is safer and prevents the client from modifying the source content sent to the AI.

---

# 11. Backend Flow

The request becomes:

```text
POST /ai/summarize
       ↓
Authentication
       ↓
Authorization
       ↓
Validate lessonId
       ↓
Find lesson
       ↓
Check instructor ownership
       ↓
Get lesson content
       ↓
Summarization Service
       ↓
AI Provider
       ↓
Validate output
       ↓
Save summary
       ↓
Return result
```

Notice something important:

### The frontend doesn't provide the lesson content.

The server gets it from the database.

---

# 12. Why Authorization Matters

Imagine:

```text
Instructor A
   ↓
Course A
   ↓
Lesson A
```

and:

```text
Instructor B
```

tries:

```http
POST /api/v1/ai/summarize
```

with:

```json
{
  "lessonId": "lesson-A"
}
```

Your backend must check:

```text
Does Instructor B own Lesson A?
```

If not:

```text
403 Forbidden
```

This is exactly the kind of authorization logic that makes your project production-like.

---

# 13. Don't Trust the Lesson ID Alone

A common mistake is:

```ts
const lesson = await lessonRepository.findById(lessonId);

generateSummary(lesson.content);
```

without checking ownership.

Instead:

```text
lessonId
   ↓
Lesson
   ↓
Module
   ↓
Course
   ↓
Instructor
   ↓
Current user
```

You need to establish that the user is allowed to perform this operation.

# 14. The Summarization Prompt

A good first prompt:

```text
You are an educational summarizer.

Your task is to summarize the provided lesson content.

Requirements:
- Preserve the important technical concepts.
- Do not invent information.
- Remove unnecessary repetition.
- Keep the summary suitable for students.
- Extract the most important concepts.
- Provide useful revision takeaways.

Lesson:
{lessonContent}
```

But now we have a second requirement:

```text
Return structured data.
```

# 15. Expected Output

Conceptually:

```json
{
  "summary": "A concise explanation of the lesson.",
  "keyConcepts": [

    "Concept 2",
    "Concept 3"
  ],
  "takeaways": [
    "Important point 1",
    "Important point 2"
  ]

```

The important thing is that your backend knows what to expect.

---

# 16. Prompt + Schema

The ideal architecture is:

```text
Prompt
   +
Output Schema
   ↓
LLM
   ↓
Structured Result
```

The exact mechanism for structured output depends on the model/provider SDK.

But your application's principle remains the same:

```text
Expected structure
       ↓
Validation
```

---

# 17. Why We Need Zod Even With Structured Output

You might ask:

> "If the AI provider supports structured output, why do we need Zod?"

Because your backend should still validate external data.

Think:

```text
Provider guarantees format
        ↓
Your application still validates
        ↓
Database
```

Defense in depth.

For example, maybe the AI returns:

```json
{
  "summary": "",
  "keyConcepts": [],
  "takeaways": []
}
```

Technically valid JSON.

But your application may decide:

```text
summary must not be empty
at least 1 key concept
at least 1 takeaway
```

That's a **business rule**.

---

# 18. Schema Validation vs Business Validation

These are slightly different.

### Schema validation

```text
Is this the right data type?
```

For example:

```text
summary → string
```

### Business validation

```text
Does this make sense for our application?
```

For example:

```text
summary must contain meaningful content
keyConcepts <= 10
```

So:

```text
AI Output
   ↓
Schema validation
   ↓
Business validation
   ↓
Database
```

---

# 19. Saving the Summary

You have several options.

### Option A — Add fields to `lessons`

```text
lessons

id
title
content
summary
...
```

Simple.

### Option B — Separate table

```text
lesson_summaries

id
lessonId
summary
keyConcepts
takeaways
promptVersion
model
createdAt
updatedAt
```

For your project, I prefer the second approach if you want to track AI-generated artifacts properly.

Why?

Because later you might regenerate the summary.

---

# 20. Regeneration

Suppose an instructor clicks:

```text
Regenerate Summary
```

Now:

```text
Old summary
     ↓
New AI request
     ↓
New summary
```

If you overwrite everything, you lose history.

You could instead track:

```text
lesson_summaries
----------------
id
lessonId
version
summary
...
```

Then:

```text
Lesson 1
   │
   ├── Summary v1
   └── Summary v2
```

You don't necessarily need version history in V1, but understand the design possibility.

---

# 21. Prompt Versioning

Remember the lesson 5.3 concept:

```text
TUTOR_PROMPT_VERSION = "1.0"
```

Do the same for summaries:

```text
SUMMARY_PROMPT_VERSION = "1.0"
```

Why?

Suppose you generate 1,000 summaries using:

```text
v1
```

Then change the prompt to:

```text
v2
```

You should be able to determine:

```text
Which prompt generated this summary?
```

Store:

```text
promptVersion
```

with the AI-generated artifact.

---

# 22. Model Metadata

You can also store:

```text
model
```

For example:

```text
model = "some-model"
```

This becomes valuable when comparing:

```text
Model A
Model B
```

for:

- quality
    
- latency
    
- cost
    

Eventually your AI analytics can answer:

```text
Which model produces the best quiz questions?
```

---

# 23. Summary Generation Should Be Idempotent-ish

Think about:

```text
POST /ai/summarize
```

If the instructor accidentally clicks twice:

```text
Request 1
Request 2
```

you may generate two AI requests.

That costs money.

You can eventually prevent duplicate work by checking:

```text
Does a summary already exist?
```

or supporting:

```text
forceRegenerate=true
```

Conceptually:

```text
Summary exists?
 ├── No → generate
 └── Yes
       ├── normal request → return existing
       └── regenerate → generate new
```

The exact behavior is a product decision.

---

# 24. Long Lessons

Now we hit an important limitation.

Suppose your lesson contains:

```text
100,000 words
```

Sending the entire thing to the LLM may be problematic.

Remember the context window from 5.1.

You eventually need:

```text
Long lesson
    ↓
Chunk
    ↓
Summarize chunks
    ↓
Combine summaries
    ↓
Final summary
```

This is sometimes called a **map-reduce style summarization pipeline**.

---

# 25. Map-Reduce Summarization

Imagine:

```text
Large Lesson
     │
     ├── Chunk 1
     ├── Chunk 2
     ├── Chunk 3
     └── Chunk 4
```

Summarize each:

```text
Chunk 1 → Summary 1
Chunk 2 → Summary 2
Chunk 3 → Summary 3
Chunk 4 → Summary 4
```

Then:

```text
Summary 1
Summary 2
Summary 3
Summary 4
     ↓
Final summarizer
     ↓
Final Summary
```

Architecture:

```text
             Large Lesson
                   │
             ┌─────┴─────┐
             ▼           ▼
          Chunking      ...
             │
       ┌─────┼─────┐
       ▼     ▼     ▼
      AI    AI    AI
       │     │     │
       ▼     ▼     ▼
      S1    S2    S3
       └─────┼─────┘
             ▼
       Final Summary
```

We won't implement this complexity yet.

It becomes much more relevant when we build document processing in **5.9**.

---

# 26. Summary vs RAG

Don't confuse them.

### Summarization

```text
Large content
   ↓
Condensed content
```

### RAG

```text
Question
   ↓
Retrieve relevant content
   ↓
Answer
```

So:

```text
Summarization = compress information
RAG = retrieve information
```

Both will be useful in your LMS.

---

# 27. AI Summary Should Not Replace the Original Lesson

Very important.

Never do:

```text
Lesson content
    ↓
AI summary
    ↓
delete original
```

The original lesson is your source of truth.

Keep:

```text
Original lesson
      +
AI-generated summary
```

Think:

```text
PostgreSQL
   │
   ├── original lesson
   │
   └── generated summary
```

AI content should be derived data.

---

# 28. What Happens When the Lesson Changes?

Suppose:

```text
Lesson v1
   ↓
Summary v1
```

Then the instructor edits the lesson:

```text
Lesson v2
```

Now:

```text
Summary v1
```

may be outdated.

You need a strategy.

For example:

```text
Lesson updated
   ↓
Mark summary stale
```

Then:

```text
Summary status = STALE
```

and the instructor can regenerate it.

This is a very good production-style design.

---

# 29. Summary Status

You could have:

```text
PENDING
PROCESSING
COMPLETED
FAILED
STALE
```

For example:

```text
Lesson updated
      ↓
Summary → STALE
```

Then:

```text
Generate
      ↓
PROCESSING
      ↓
COMPLETED
```

This becomes even more useful once we introduce **background jobs in later phases**.

# 30. Synchronous vs Background Summarization

For a small lesson:

```text
POST /ai/summarize
   ↓
LLM
   ↓
Response
```

may be fine.

For a huge PDF:

```text
Upload PDF
   ↓
Extract
   ↓
Chunk
   ↓
Generate embeddings
   ↓
Summarize
```

you should use a background job.

Eventually:

```text

 ↓

 ↓
BullMQ
 ↓
Worker
 ↓
AI
 ↓

```

That's part of the advanced backend architecture we'll reach later.

# 38. A Very Important Rule

Don't let the frontend decide what the summary means.

Bad:

```text
Frontend
 ↓
parse Markdown
 ↓
figure out concepts
```

Better:

```text
AI
 ↓
structured result
 ↓
Backend validates
 ↓
Frontend renders fields
```

The backend should remain the source of truth for application data.

---

# 39. What About Hallucinations?

Even with a strong prompt:

```text
Do not invent information.
```

the model can still make mistakes.

For summarization, we reduce this risk by telling it:

```text
Use only the supplied lesson content.
Do not introduce external information.
```

And eventually we can evaluate the summary against the original content.

But remember:

> Prompt instructions reduce risk; they don't magically guarantee correctness.

This is why AI-generated educational content should have appropriate review mechanisms, especially for canonical course material.

# 42. Testing the Summarizer

Because AI output isn't deterministic, don't test:

```text
expect(summary).toBe(
  "PostgreSQL indexes are..."
);
```

Instead test structure.

For example:

```text
✓ summary exists
✓ summary is a string
✓ keyConcepts is an array
✓ takeaways is an array
✓ no more than 10 concepts
✓ invalid AI output is rejected
```

And in unit tests, use a fake AI provider.

```text
SummaryService
      ↓
FakeAIProvider
```

instead of making real API calls.

This connects back to the provider abstraction from 5.2.

# 44. Common Mistakes

### ❌ Mistake 1 — Trusting AI output

```text
LLM
 ↓
Database
```

Instead:

```text
LLM
 ↓
Validation
 ↓
Database
```

---

### ❌ Mistake 2 — Sending lesson content from the browser

Prefer:

```text
lessonId
 ↓
Backend
 ↓
Database
 ↓
lesson content
```

---

### ❌ Mistake 3 — One giant AI service

Avoid:

```text
ai.service.ts
  ├── tutor
  ├── summarize
  ├── quiz
  ├── planner
  └── 1000 lines
```

Separate business features logically.

---

### ❌ Mistake 4 — Replacing the original lesson

Keep:

```text
Original lesson
+
AI summary
```

---

### ❌ Mistake 5 — Ignoring stale summaries

If the lesson changes:

```text
old summary ≠ current lesson
```

Track that state.

# 🎯 Lesson 5.6 Takeaways

The key lessons today are:

```text
1. AI output should be treated as untrusted external data.

2. Structured output is much better than arbitrary text
   when the application needs specific fields.

3. Define your expected schema before processing AI output.

4. Validate AI output with Zod.

5. Separate schema validation from business validation.

6. Keep original course content as the source of truth.

7. AI-generated summaries should be treated as derived data.

8. Lesson changes can make existing summaries stale.

9. Prompt version and model metadata are useful for AI operations.

10. Long content may require chunking and multi-step summarization.

11. Instructor review can make AI-generated educational content safer.

12. The same structured-output architecture will power the
    AI Quiz Generator.
```
