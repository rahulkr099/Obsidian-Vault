# Lesson 5.8 — Embeddings & Semantic Search

In **5.7**, we built the AI Quiz Generator.

Now we're moving into one of the most important parts of the AI LMS:

> **How can our application find information that is relevant to a student's question, even when the exact words don't match?**

This is where **embeddings** and **semantic search** come in.

The roadmap places this lesson before document processing and RAG: we first learn how text becomes vectors, then use those vectors to retrieve relevant learning content.

---

# 1. The Problem With Normal Search

Suppose your lesson contains:

```text
JWT authentication allows a server to verify
the identity of a user using a signed token.
```

A student asks:

```text
How does login authentication work with tokens?
```

A normal keyword search might look for:

```text
"login"
"authentication"
"tokens"
```

It might find the lesson because `"authentication"` matches.

But consider:

```text
Student:
How can a server know who the user is?
```

The lesson may not contain:

```text
"know who the user is"
```

Yet the meaning is strongly related.

This is where semantic search helps.

---

# 2. Keyword Search vs Semantic Search

### Keyword search

```text
Query:
"How can a server know who the user is?"

Searches for:
exact / related words
```

### Semantic search

```text
Query
 ↓
Meaning
 ↓
Find content with similar meaning
```

So:

```text
Keyword Search
"authentication"
       ↓
matching words

Semantic Search
"How can a server identify a user?"
       ↓
matching meaning
```

This distinction is fundamental to RAG.

---

# 3. What Is an Embedding?

An embedding is a numerical representation of text that captures semantic information.

For example:

```text
"JWT authentication"
```

might become something conceptually like:

```text
[0.12, -0.43, 0.87, 0.21, ...]
```

The actual vector will have many dimensions.

Don't focus on the exact numbers.

Think:

```text
Text
 ↓
Embedding Model
 ↓
Vector
```

---

# 4. Why Convert Text Into Numbers?

Computers are very good at comparing numbers.

Suppose:

```text
Text A
"JWT is used for authentication."
```

becomes:

```text
Vector A
```

and:

```text
Text B
"Tokens can be used to authenticate users."
```

becomes:

```text
Vector B
```

Because the meanings are related, their vectors should be relatively close in vector space.

Another unrelated sentence:

```text
"PostgreSQL uses indexes to improve queries."
```

might produce:

```text
Vector C
```

which would be farther away.

Conceptually:

```text
                 Vector Space

        JWT authentication
              ●
             /
            /
           ●  Token-based login

                              ●
                         PostgreSQL indexes
```

# 9. Why We Need Chunking

Suppose a lesson is:

```text

```

You don't want:

```text

   ↓
one embedding
```

Instead:

```text

 ↓

Chunk 2
Chunk 3
Chunk 4
...
```

Then:

```text

Chunk 2 → Vector 2
Chunk 3 → Vector 3

```

This allows retrieval to find the **specific part of the lesson** relevant to the question.

We'll study chunking more deeply in **5.9**.

# 11. Similarity

Once everything is represented as vectors, we need to measure:

> How similar are these vectors?

One popular metric is:

**Cosine similarity.**

Conceptually:

```text
Vector A
    ↘
     similarity
    ↗
Vector B
```

If two vectors point in similar directions:

```text
high similarity
```

If they're unrelated:

```text
low similarity
```

You don't need to memorize the mathematical formula yet.

Understand the purpose:

```text
similar meaning
      ↓
similar vectors
      ↓
high similarity
```

---

# 12. Cosine Similarity

The mathematical definition is:

# [  
\text{cosine similarity}(A,B)

\frac{A \cdot B}  
{|A||B|}  
]

Where:

```text
A · B
```

is the dot product.

And:

```text
||A||
```

is the magnitude of vector A.

The result is commonly interpreted as:

```text
closer to 1
    ↓
more similar

closer to 0
    ↓
less similar
```

Depending on the embedding/vector space and normalization, exact ranges and interpretation can vary, but the core idea remains the same.

---

# 13. Why Not Just Use Euclidean Distance?

You may also hear about:

```text
Euclidean distance
```

which measures geometric distance between points.

Another common metric is:

```text
dot product
```

Vector databases can support different distance/similarity metrics.

The important engineering rule is:

> Use a metric appropriate to your embedding model and vector database configuration.

Don't randomly mix metrics without understanding the provider's recommendations.

# 16. What Is pgvector?

`pgvector` is a PostgreSQL extension that adds vector data types and similarity search capabilities.

Conceptually, instead of:

```text
content TEXT
```

you can have:

```text
content TEXT
embedding VECTOR
```

Then PostgreSQL can perform similarity searches over the embeddings.

This is powerful because your relational data and vector data can live together.

Let's trace a real student question.

Student asks:

> "Why does JWT use a signature?"

Step 1:

```text

```

```text

 ↓
Embedding Model
 ↓

```

Step 3:

```text
Query Vector
 ↓

```

Step 4:

```text

```

For example:

```text

```

```text

 ↓
```


---

# 20. Top-K Retrieval

You don't usually retrieve every matching chunk.

Instead, select the top **K** results.

For example:

```text
K = 5
```

Then:

```text
Vector Search
      ↓
Top 5 chunks
```

Conceptually:

```text
1000 chunks
   ↓
similarity search
   ↓
top 5
   ↓
LLM
```

This is much more efficient than sending all 1,000 chunks to the model.

---

# 21. Similarity Threshold

Top-K alone isn't always enough.

Suppose the student's question has nothing to do with your course.

The vector database might still return:

```text
Chunk A → 0.31
Chunk B → 0.29
Chunk C → 0.27
```

They're the "best" results, but they're not actually relevant.

So you can use a threshold:

```text
similarity >= threshold
```

For example, conceptually:

```text
0.85 ✓
0.82 ✓
0.79 ✓
0.41 ✗
```

The exact threshold needs to be tested with your embedding model and data.

Don't blindly choose a universal number.

---

# 22. Top-K + Threshold

A useful retrieval strategy:

```text
Query
 ↓
Vector Search
 ↓
Top K
 ↓
Similarity threshold
 ↓
Relevant chunks
```

For example:

```text
Top 10
     ↓
filter low similarity
     ↓
Top relevant 3–5
```

This helps reduce irrelevant context.

# 24. Embedding Model Consistency

Here's a very important rule:

> **Use the same embedding space for your stored documents and queries.**

Suppose you embedded course chunks using:

```text
Embedding Model A
```

Then you should generally query using the same compatible embedding model.

Don't do:

```text
Documents → Model A
Query → Model B
```

and assume the vectors are directly comparable.

Think:

```text
Documents
   ↓
Embedding Model X
   ↓
Vector Space X

Query
   ↓
Embedding Model X
   ↓
Vector Space X
```

Now comparison makes sense.

---

# 25. Embedding Dimensions

Every embedding model produces vectors with a particular dimensionality.

For example, conceptually:

```text
Model X → 768 dimensions
```

or:

```text
Model Y → 1536 dimensions
```

Your vector storage needs to match the chosen dimensionality.

So if your database column expects:

```text
VECTOR(768)
```

you can't suddenly insert:

```text
VECTOR(1536)
```

without changing the schema/design.

This is another reason to choose and document your embedding model early.

---



This is much more efficient.

# 28. What Happens When a Lesson Changes?

Suppose:

```text
Lesson v1
 ↓
Chunks
 ↓
Embeddings
```

Then the instructor edits the lesson:

```text
Lesson v2
```

The old embeddings may now be stale.

You need:

```text
Lesson updated
   ↓
Delete/update old chunks
   ↓
Create new chunks
   ↓
Generate new embeddings
```

So your system must keep the vector index synchronized with the source content.

---

# 29. Chunk IDs and Versions

You can make this easier by storing:

```text
lessonId
chunkIndex
contentHash
embeddingModel
```

For example:

```text
lessonId:
lesson_123

chunkIndex:
4

contentHash:
abc123

embeddingModel:
model-x
```

Then your system can determine whether a chunk needs re-embedding.

---

# 30. Hashing Can Save Work

Imagine an instructor changes only the lesson title.

The actual content doesn't change.

You don't necessarily need to regenerate embeddings.

You can calculate a content hash:

```text
content
 ↓
SHA-256
 ↓
hash
```

If:

```text
oldHash === newHash
```

then:

```text
content unchanged
```

No need to re-embed.

This is a nice optimization for later.

# 31. Semantic Search vs Full-Text Search

Don't think semantic search replaces traditional search.

They solve different problems.

### Full-text search

Good for:

```text

names
IDs
specific phrases
technical keywords
```

### Semantic search

Good for:

```text

conceptual similarity
natural-language questions
paraphrased queries
```

A mature LMS can eventually use:

```text
Keyword Search
       +
Semantic Search
       ↓
Hybrid Search
```

This is often better than relying on only one retrieval method.

# 43. Evaluation Becomes Important

How do we know our retrieval system works?

Create test questions:

```text
Question 1
"Why does JWT use a signature?"

Expected:
JWT signature lesson chunk

Question 2
"How do indexes speed up database queries?"

Expected:
PostgreSQL index chunk
```

Then measure:

```text
Did the correct chunk appear in top 5?
```

This is called **retrieval evaluation**.

A simple metric is:

### Recall@K

If the relevant chunk appears in the first K results:

```text
success
```

For example:

```text
Recall@5 = 92%
```

means the relevant information was found within the top five results for about 92% of test queries, assuming your evaluation set and relevance labels are defined appropriately.

This is a very useful metric for your AI LMS.

# 45. A Useful Debugging Strategy

When your future AI Tutor gives a bad answer, don't immediately blame the LLM.

Debug the pipeline:

```text
Question
   ↓
Query embedding
   ↓
Search
   ↓
Retrieved chunks
   ↓
Prompt
   ↓
LLM
   ↓
Answer
```

Ask:

### Step 1

Did we retrieve the correct chunk?

### Step 2

Did we include the chunk in the prompt?

### Step 3

Did the prompt clearly tell the model to use it?

### Step 4

Did the model produce the correct answer?

This separates:

```text
Retrieval problem
```

from:

```text
Generation problem
```

That is a very valuable AI engineering skill.

# 51. Don't Store Embeddings in JSON

Avoid thinking:

```json
{
  "embedding": [0.12, 0.43, ...]
}
```

inside a generic JSON field for your actual vector-search implementation.

Why?

Because you want the database to efficiently perform:

```text
similarity search
```

over the vector.

A vector-capable column/index is much more appropriate.

---

# 52. Vector Indexes

As your number of vectors grows:

```text
100
1,000
10,000
100,000
1,000,000
```

searching every vector linearly can become expensive.

Vector databases and pgvector support indexing strategies designed to make nearest-neighbor search more efficient.

You'll hear terms such as:

```text
HNSW
IVFFlat
```

You don't need to implement them blindly today.

Understand the purpose:

```text
Vector Index
     ↓
Faster similarity search
```

When you actually configure pgvector, choose the index based on your workload and current documentation.

---

# 53. HNSW — High-Level Idea

HNSW is a graph-based approximate nearest-neighbor search method.

Don't worry about the mathematical implementation yet.

Think:

```text
Millions of vectors
       ↓
Smart graph/index structure
       ↓
Find nearby vectors efficiently
```

It trades some exactness for much faster search.

For many modern semantic-search workloads, approximate nearest-neighbor search is very useful.

---

# 54. Exact vs Approximate Search

### Exact

Compare query against:

```text
every vector
```

Potentially expensive at scale.

### Approximate

Use an index to find:

```text
very likely nearest vectors
```

much faster.

So:

```text
Small dataset
→ exact may be fine

Large dataset
→ vector index becomes important
```

For your academic LMS, you may not need millions of vectors, but learning the production concept is valuable.

---

# 55. Security Consideration

Embeddings can contain information about the source content.

Don't assume:

```text
Vector = harmless random numbers
```

Your vector store is still part of your application's data layer.

Protect it with:

```text
database permissions
authorization
access filters
backups
encryption/security controls
```

And most importantly:

```text
Don't return arbitrary retrieved chunks to users
without checking their access.
```
