# Lesson 5.9 — Document Processing & Chunking

In **5.8**, we learned embeddings and semantic search.

We saw:

```text
Course Content
    ↓
Chunking
    ↓
Embeddings
    ↓
Vector Store
```

Today we're going to build the missing piece:

> **How do we take real educational content and turn it into clean, searchable chunks?**

This is extremely important because **bad document processing → bad chunks → bad embeddings → bad retrieval → bad AI answers.**

---

# 1. Why Do We Need Document Processing?

Your LMS won't contain only short database fields.

Eventually, instructors may upload:

```text
PDF
DOCX
Markdown
TXT
Lesson content
Lecture notes
Video transcripts
```

For example:

```text
Operating Systems.pdf
    ↓
50 pages
    ↓
Text extraction
    ↓
Clean text
    ↓
Chunks
    ↓
Embeddings
    ↓
Vector database
```

The AI doesn't directly understand a PDF file sitting in your filesystem.

We need an ingestion pipeline.

---

# 2. The Document Ingestion Pipeline

Our future pipeline:

```text
                    Document
                       │
                       ▼
                  File Storage
                       │
                       ▼
                 Text Extraction
                       │
                       ▼
                    Cleaning
                       │
                       ▼
                   Chunking
                       │
                       ▼
                  Metadata
                       │
                       ▼
                  Embeddings
                       │
                       ▼
                PostgreSQL/pgvector
```

This is called a **document ingestion pipeline**.

---

# 3. The Most Important Principle

Remember:

> **The original document is the source of truth.**

We create derived data:

```text
Original PDF
    │
    ├── extracted text
    ├── chunks
    └── embeddings
```

Don't replace the original document with processed data.

Think:

```text
Original
   ↓
Derived representations
```

not:

```text
Original
   ↓
Delete original
```

---

# 4. Step 1 — Store the Original File

Suppose an instructor uploads:

```text
nodejs-authentication.pdf
```

Your application might store the actual file in:

```text

```

```text

```

while PostgreSQL stores metadata:

```text

```

Notice that the database doesn't necessarily need to contain the entire PDF binary.

So track the document lifecycle.

For example:


```text

```

# 6. Why Processing Should Usually Be Asynchronous

Imagine uploading a:

```text

```

Processing may involve:

```text

 ↓

 ↓

 ↓

```

This could take several seconds or longer.

You don't want:

```text

   ↓

   ↓

```

Instead:

```text

   ↓

   ↓
Return quickly
   ↓

   ↓

```

Eventually your architecture becomes:

```text

 ↓

 ↓
Worker
 ↓

 ↓
Embedding Service
 ↓
Vector DB
```

We'll use this idea more deeply in later backend/production phases.

```text

```


# 13. Text Cleaning

Typical cleaning operations include:

```text
Remove excessive whitespace
Normalize line breaks
Remove obvious repeated headers
Remove obvious repeated footers
Normalize Unicode
Remove unnecessary page markers
```

But be careful.

Don't aggressively clean everything.

For example:

```text
function foo()
```

shouldn't accidentally become:

```text
functionfoo()
```

Preserve meaningful structure.

---

# 14. Don't Over-Clean

This is a common mistake.

You might write:

```text
text.replace(/\s+/g, " ")
```

and flatten everything.

That can destroy:

```text
headings
paragraphs
code blocks
lists
tables
```

For an educational LMS, structure can be valuable.

A better approach is:

```text
Raw document
    ↓
Conservative cleaning
    ↓
Preserve meaningful structure
```

---

# 15. Headings Are Valuable Metadata

Suppose the document contains:

```text
## JWT Authentication

JWT allows...

### Access Tokens

Access tokens...

### Refresh Tokens

Refresh tokens...
```

Don't treat all of this as anonymous text.

Keep:

```text
heading:
JWT Authentication
```

or:

```text
section:
Refresh Tokens
```

with the chunks.

Then metadata becomes:

```text
courseId
lessonId
documentId
sectionTitle
pageNumber
chunkIndex
```

This can significantly improve retrieval quality.

# 16. Step 4 — Chunking

Now we reach the heart of today's lesson.

Suppose we have:

```text
100,000 characters
```

We need to split it into manageable pieces.

```text
Document
    ↓
Chunk 1
Chunk 2
Chunk 3
...
```

These are called **chunks**.

---

# 17. Why Not Embed the Entire Document?

Because retrieval needs precision.

Suppose the entire textbook becomes one vector:

```text
Textbook
   ↓
Vector
```

Student asks:

> "What is JWT refresh token rotation?"

The vector represents:

```text
everything in the textbook
```

That's too broad.

Instead:

```text
Textbook
   ↓
1000 chunks
   ↓
1000 vectors
```

Now the search can find the specific relevant section.

---

# 18. Chunk Size

You might see recommendations such as:

```text
500 tokens
800 tokens
1000 tokens
```

But there isn't one universally correct chunk size.

It depends on:

- document type
    
- content structure
    
- embedding model
    
- query style
    
- retrieval strategy
    
- context window
    
- desired answer quality
    

For your LMS, start with a reasonable range and **evaluate it**.

Don't blindly copy someone's "perfect chunk size."

---

# 19. Token-Based vs Character-Based Chunking

You can chunk by:

### Characters

```text
1000 characters
```

Simple.

### Words

```text
250 words
```

Also simple.

### Tokens

```text
500 tokens
```

More aligned with LLM context usage.

Tokens are generally the more useful concept for AI systems, but character/word-based chunking can be perfectly reasonable for an initial implementation.

---

# 20. Semantic Chunking

There's another approach:

Instead of:

```text
every 500 tokens
```

we try to split based on meaning.

For example:

```text
Heading
 ↓
Paragraph
 ↓
Paragraph
 ↓
Example
```

becomes one chunk.

Then:

```text
Next heading
 ↓
Paragraph
 ↓
Example
```

becomes another.

This preserves educational concepts better.

---

# 21. Structure-Aware Chunking

For your LMS, I strongly recommend eventually using:

```text
Heading-aware
+
Paragraph-aware
+
Token-aware
```

chunking.

For example:

```text
Course
  ↓
Module
  ↓
Lesson
  ↓
Section
  ↓
Paragraphs
  ↓
Chunk
```

Rather than simply:

```text
every 1000 characters
```

This is especially useful for technical educational material.

---

# 22. Example

Suppose your lesson is:


```text

```

```text

```

```text

```

This is much better for retrieval.

# 23. Chunk Overlap

Now there's another important concept:

**overlap**.

Suppose we split:

```text
Chunk 1:
A B C D E

Chunk 2:
F G H I J
```

A concept might span the boundary:

```text
Chunk 1:
A B C D

Chunk 2:
E F G H
```

The context around `E` could be lost.

With overlap:

```text
Chunk 1:
A B C D E

Chunk 2:
D E F G H
```

Now:

```text
D E
```

appears in both chunks.

---

# 24. Why Use Overlap?

Overlap helps preserve context at chunk boundaries.

Conceptually:

```text
Chunk 1
████████████

      ████████████
      Chunk 2
```

The shared area is the overlap.

For example:

```text
Chunk size:
800 tokens

Overlap:
100 tokens
```

This is only an example.

You should evaluate what works for your content.

---

# 25. Too Much Overlap Is Also Bad

Suppose:

```text
Chunk size = 500
Overlap = 400
```

Then you're duplicating a huge amount of content.

That means:

```text
more chunks
more embeddings
more storage
more retrieval redundancy
more cost
```

So:

```text
small overlap
```

can preserve continuity without creating massive duplication.

Again:

> **Chunk size and overlap are retrieval parameters to evaluate, not magic constants.**

# 28. Why `chunkIndex`?

Suppose a lesson has:

```text

```

```text

```

# 29. Why `contentHash`?

Suppose the instructor uploads the same document again.

You can calculate:

```text
hash(document content)
```

If the hash is unchanged:

```text
same content
```

you may not need to reprocess everything.

Similarly for chunks:

```text
Chunk content
   ↓
Hash
```

If the chunk hasn't changed:

```text
don't regenerate embedding
```

This can save significant processing.

---

# 30. Document Versioning

Suppose:

```text
Lesson v1
```

produces:

```text
Chunk A
Chunk B
Chunk C
```

Instructor edits the lesson:

```text
Lesson v2
```

Now:

```text
Chunk A → unchanged
Chunk B → changed
Chunk C → unchanged
```

Ideally:

```text
A → reuse embedding
B → regenerate embedding
C → reuse embedding
```

This is more efficient than rebuilding everything.

Not every PDF contains selectable text.

```text
Image
```

If you run a normal text extractor:

```text

```

You need:

```text

```

OCR means:

So your document system should eventually distinguish:

```text

```

# 34. Code Should Be Treated Carefully

This is especially important for your LMS because you're teaching programming.

Consider:

```ts
const user = await prisma.user.findUnique({
  where: { id: userId }
});
```

A bad text cleaner might turn it into:

```text
const user = await prisma.user.findUnique({ where: { id: userId } });
```

which may still be okay.

But an even worse parser could destroy formatting completely.

For technical documents:

```text
code blocks
```

should ideally remain identifiable.

Metadata could include:

```text
contentType = "text"
```

or:

```text
contentType = "code"
```

when appropriate.

---

# 35. Tables Are Also Difficult

A PDF table might extract as:

```text

Rahul 22 85
Aman 21 91
```

The relationship between columns may be lost.

So document processing isn't simply:

```text
PDF → string
```

It's often:

```text

 ↓
document structure
 ↓
text + metadata
```

For high-quality RAG, preserving structure can make a big difference.

# 36. Don't Embed Navigation Noise

Suppose every page contains:

```text
AI LMS — Backend Engineering
Chapter 4
Page 27
```

If you embed all of this repeatedly:

```text
Header
Header
Header
Header
```

you're wasting storage and potentially affecting retrieval.

Repeated headers/footers should often be detected and removed.

But again:

> Don't remove content blindly.

---

# 37. Chunking Strategy for Your LMS

For your project, a good starting strategy is:

```text
1. Preserve headings.
2. Preserve paragraphs.
3. Preserve code blocks.
4. Split very large sections.
5. Add modest overlap.
6. Attach course/lesson metadata.
7. Keep page numbers when available.
8. Generate content hashes.
```

This is a better starting point than:

```text
split every N characters
```

---

# 38. Example Chunking Algorithm

Conceptually:

```text
Document
   ↓

   ↓
For each section:
   │
   ├── Small enough?
   │      ↓
   │     Keep
   │
```

```text
+

```

# 39. Don't Chunk Before Cleaning

Bad pipeline:

```text
Raw PDF
 ↓
Chunk
 ↓
Clean
```

You may end up with:

```text
Chunk 1:
header + actual content

Chunk 2:
footer + actual content
```

Better:

```text
Raw document
 ↓
Extract
 ↓
Clean
 ↓
Structure
 ↓
Chunk
```

Order matters.

---

# 40. Don't Embed Before Chunking

Another obvious but important rule:

```text
Document
 ↓
Embedding
 ↓
Chunk
```

doesn't make sense for our retrieval system.

Instead:

```text
Document
 ↓
Chunk
 ↓
Embedding each chunk
```

because retrieval needs the vectors at the chunk level.

# 42. Failure Handling

Suppose:

```text
PDF extraction ✓
Cleaning ✓
Chunking ✓
Embedding ✗
```

Don't mark:

```text
READY
```

Instead:

```text
FAILED
```

and record the reason:

```text

```

Then you can retry.

This becomes particularly important when processing thousands of documents.

---

# 43. Retry Strategy

Imagine the embedding API temporarily fails:

```text
Request
 ↓
503
```

You shouldn't immediately give up.

A background worker could retry:

```text
Attempt 1
 ↓
failure

Attempt 2
 ↓
failure

Attempt 3
 ↓
success
```

Eventually we'll handle these patterns with job queues and retry policies.

---

# 44. Idempotency

Document processing should ideally be safe to retry.

Suppose:

```text
Job 123
```

runs twice.

You don't want:

```text
Chunk 1
Chunk 1
Chunk 2
Chunk 2
```

in your database.

Use identifiers/hashes/status checks to make processing idempotent.

For example:

```text
documentId + version + chunkIndex
```

can help uniquely identify a chunk.

---

# 45. Document Processing and Transactions

Don't put the entire document pipeline inside one PostgreSQL transaction.

Bad:

```text
BEGIN
 ↓
Extract PDF
 ↓
OCR
 ↓
Generate embeddings
 ↓
COMMIT
```

These operations can take a long time.

Instead:

```text
Process externally
 ↓
Validate result
 ↓
Short database transaction
 ↓
Save metadata/results
```

Same principle as our AI Quiz Generator.

# 53. Common Chunking Mistakes

### ❌ Mistake 1 — One vector for the entire course

```text
Course
 ↓
One embedding
```

Too coarse.

---

### ❌ Mistake 2 — Arbitrary tiny chunks

```text
"JWT"

"uses"

"tokens"

"for"

"authentication"
```

Now each chunk has almost no context.

---

### ❌ Mistake 3 — Huge chunks

```text
20,000 tokens
```

Retrieval becomes less precise and context becomes expensive.

---

### ❌ Mistake 4 — No metadata

You retrieve:

```text
"Refresh tokens..."
```

but don't know:

```text
Which course?
Which lesson?
Which page?
```

Bad for citations and access control.

---

### ❌ Mistake 5 — No overlap

Important context can be split across boundaries.

---

### ❌ Mistake 6 — Excessive overlap

Creates unnecessary duplication and cost.

---

### ❌ Mistake 7 — Destroying code formatting

Especially bad for a programming LMS.

---

# 54. A Practical Chunking Strategy

For your first implementation, I'd use this mental algorithm:

```text
1. Extract text.
2. Normalize obvious formatting noise.
3. Identify headings/sections.
4. Keep paragraphs together when possible.
5. Split oversized sections.
6. Respect a target token range.
7. Add modest overlap.
8. Attach metadata.
9. Generate content hash.
10. Generate embeddings.
```

This is a much stronger starting point than blindly splitting strings.

# 🎯 Lesson 5.9 Takeaways

Remember these core ideas:

```text
1. Document processing converts raw files into AI-searchable knowledge.

2. The original document remains the source of truth.

3. Extract text before creating embeddings.

4. Clean conservatively; don't destroy useful structure.

5. Preserve headings, paragraphs, code, and useful metadata.

6. Chunk documents before embedding them.

7. Chunk size should be chosen based on your content and evaluated,
   not treated as a universal magic number.

8. Modest overlap can preserve context between chunks.

9. Every chunk should have useful metadata.

10. contentHash can prevent unnecessary reprocessing.

11. Large document processing should eventually run in background workers.

12. Scanned PDFs may require OCR.

13. Code and tables need special care during extraction.

14. Document processing should be retryable and preferably idempotent.

15. Authorization must remain connected to document and chunk metadata.

16. Good RAG starts with good document processing.
```

The most important pipeline to remember is:

```text
             RAW KNOWLEDGE
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
         PDF     Lesson   Transcript
          │        │        │
```
