# Lesson 6.3 — Lesson Completion

In **6.2 — Learning Progress**, we established an important idea:

> **Individual lesson-completion records should be the source of truth for calculating learning progress.**

Now we'll build that system.

The basic flow is:

```text
Student
   ↓
Enrollment
   ↓
Course
   ↓
Section
   ↓
Lesson
   ↓
Lesson Completion
```

The roadmap places **Lesson Completion** immediately after Learning Progress, because completion events are what allow us to calculate reliable course progress.

---

# 1. What is lesson completion?

Suppose a course contains:

```text
Course: Backend Engineering

Section 1
 ├── HTTP Fundamentals
 ├── Express Basics
 └── Middleware

Section 2
 ├── Authentication
 ├── Authorization
 └── Security
```

A student watches:

```text
HTTP Fundamentals       ✅
Express Basics          ✅
Middleware              👀
Authentication          ❌
Authorization           ❌
Security                ❌
```

The system needs to record:

```text
Student X completed Lesson A
Student X completed Lesson B
```

That's what `LessonCompletion` represents.

---

# 2. Why not just add `completed = true` to Lesson?

This is a very common beginner mistake.

You might think:

```prisma
model Lesson {
  id        String  @id
  title     String
  completed Boolean
}
```

But imagine:

```text
Student A → Lesson 1 ✅
Student B → Lesson 1 ❌
Student C → Lesson 1 ✅
```

A single `completed` field on `Lesson` cannot represent this.

Completion belongs to the **relationship between a student/enrollment and a lesson**.

Therefore:

```text
Lesson
   ↑
   │
LessonCompletion
   │
   ↓
Enrollment
```

Conceptually:

```text
Enrollment

        │
        N
```

```text

```

```text

```

# 4. Prisma model

A practical starting point:

```prisma
model LessonCompletion {
  id           String   @id @default(uuid())

  enrollmentId String
  lessonId     String

  completedAt  DateTime @default(now())

  enrollment   Enrollment @relation(
    fields: [enrollmentId],
    references: [id]
  )

  lesson       Lesson @relation(
    fields: [lessonId],
    references: [id]
  )

  @@unique([enrollmentId, lessonId])
  @@index([enrollmentId])
  @@index([lessonId])
}
```

And the related models would contain:

```prisma
model Enrollment {
  id           String @id @default(uuid())

  studentId    String
  courseId     String

  completions  LessonCompletion[]
}
```

and:

```prisma
model Lesson {
  id           String @id @default(uuid())

  title        String

  completions  LessonCompletion[]
}
```

The most important line is:

```prisma
@@unique([enrollmentId, lessonId])
```

---

# 5. Why the unique constraint matters

Imagine the student clicks:

```text
Mark as complete
```

Then the browser sends:

```http
POST /api/v1/lessons/lesson_123/complete
```

But because of a slow connection, the request gets sent twice:

```text
Request A ──┐
            ├── complete lesson
Request B ──┘
```

Without a unique constraint:

```text
LessonCompletion
────────────────
1. enrollment_1 + lesson_1
2. enrollment_1 + lesson_1
```

That's bad.

With:

```prisma
@@unique([enrollmentId, lessonId])
```

the database guarantees:

```text
enrollment_1 + lesson_1
            ↓
        ONE record
```

This is **database-level protection**.

---

# 6. Completion endpoint

A clean API could be:

```http
POST /api/v1/lessons/:lessonId/complete
```

For example:

```http
POST /api/v1/lessons/lesson_123/complete
Authorization: Bearer <token>
```

Notice that we're not sending:

```json
{
  "studentId": "student_123"
}
```

The backend already knows who the student is:

```ts
const studentId = req.user.userId;
```

This prevents users from pretending to complete lessons for someone else.

# 8. The most important authorization check

Suppose:

```text
Course A
 └── Lesson A1

Course B
 └── Lesson B1
```

Rahul is enrolled in:

```text
Course A
```

Rahul should **not** be able to complete:

```text
Lesson B1
```

just because he knows its ID.

So the backend must verify:

```text
Authenticated Student
        ↓
Enrollment
        ↓
Course
        ↓
Lesson
```

In other words:

```text
Does this lesson belong to a course
that this student is enrolled in?
```

This is an important authorization rule.

---

# 9. Don't trust the lesson ID alone

A dangerous implementation would be:

```ts
await prisma.lessonCompletion.create({
  data: {
    enrollmentId,
    lessonId,
  },
});
```

without verifying the relationship.

A malicious user might discover:

```text
lesson_987
```

and attempt to mark it complete.

The service should first establish:

```text
lesson
  ↓
section
  ↓
course
  ↓
student enrollment
```

Only then should completion be allowed.

---

# 10. Service logic

Conceptually:

```ts
async function completeLesson(
  studentId: string,
  lessonId: string
) {
  const lesson = await lessonRepository.findById(lessonId);

  if (!lesson) {
    throw new AppError("Lesson not found", 404);
  }

  const enrollment =
    await enrollmentRepository.findByStudentAndCourse(
      studentId,
      lesson.courseId
    );

  if (!enrollment) {
    throw new AppError(
      "You are not enrolled in this course",
      403
    );
  }

  return lessonCompletionRepository.create({
    enrollmentId: enrollment.id,
    lessonId,
  });
}
```

This is simplified because your exact Phase 5 schema may represent the course relationship through sections.

The important concept is:

```text
lesson → course → enrollment → student
```

---

# 11. What if the lesson is already completed?

This is where **idempotency** becomes important.

Suppose:

```text
POST /lessons/123/complete
```

is called three times.

We don't want:

```text
Completion 1
Completion 2
Completion 3
```

We want:

```text
Lesson 123 = completed
```

and one completion record.

There are several ways to handle this.

### Option A — Return existing record

```text
Already completed?
        ↓
Return existing completion
```

### Option B — Catch unique constraint error

```text
INSERT
  ↓
Unique constraint violation
  ↓
Treat as already completed
```

### Option C — Database upsert

Prisma supports an `upsert` operation:

```ts
await prisma.lessonCompletion.upsert({
  where: {
    enrollmentId_lessonId: {
      enrollmentId,
      lessonId,
    },
  },
  create: {
    enrollmentId,
    lessonId,
  },
  update: {},
});
```

This is particularly useful for idempotent operations.

---

# 12. What does `upsert` mean?

Think:

```text
upsert
=
update if exists
+
insert if doesn't exist
```

For our case:

```text
Does completion exist?
       │
   ┌───┴───┐
   │       │
  YES      NO
   │       │
 update   insert
```

Since completion doesn't have much to update, we can effectively make the operation:

```text
"Ensure this lesson is completed."
```

That's a powerful way to think about APIs.

---

# 13. Should completion be reversible?

This is a product decision.

Option 1:

```text
POST /complete
```

and once completed:

```text
Cannot undo
```

Option 2:

```text
POST   /complete
DELETE /complete
```

allowing:

```text
completed → incomplete
```

Which is better?

For an educational LMS, it often makes sense to allow the user to revisit a completed lesson without losing completion status.

You don't necessarily need an "uncomplete" action.

# 16. Updating progress after completion

Suppose our system maintains a progress summary:

```text
LearningProgress
────────────────────
completedLessons
percentage
lastActivityAt
```

When the student completes a lesson:

```text
1. Create completion
2. Count completed lessons
3. Calculate percentage
4. Update progress
5. Update last activity
```

Conceptually:

```text
Student completes lesson
          ↓
LessonCompletion created
          ↓
Count completions
          ↓
Calculate progress
          ↓
Update LearningProgress
```

But there's an important issue.

What if:

```text
Step 1 succeeds
Step 2 succeeds
Step 3 fails
```

Now our database might be inconsistent.

That's where transactions become useful.

---

# 17. Transaction

We can group related operations:

```ts
await prisma.$transaction(async (tx) => {
  await tx.lessonCompletion.upsert({
    where: {
      enrollmentId_lessonId: {
        enrollmentId,
        lessonId,
      },
    },
    create: {
      enrollmentId,
      lessonId,
    },
    update: {},
  });

  await tx.learningProgress.update({
    where: {
      enrollmentId,
    },
    data: {
      lastActivityAt: new Date(),
    },
  });
});
```

Conceptually:

```text
BEGIN
  ↓
Complete lesson
  ↓
Update progress
  ↓
COMMIT
```

If something goes wrong:

```text
ROLLBACK
```

---

# 18. A subtle issue: progress calculation

Imagine:

```text
Total lessons = 100
Completed = 40
```

Then:

```text
40%
```

But suppose an instructor adds 10 more lessons.

Now:

```text
40 / 110
=
36.36%
```

This means progress can change even though the student didn't lose completed lessons.

That's not necessarily a bug.

It is a **course-content versioning/product-design question**.

For now, our rule can simply be:

> Current course progress is calculated against the currently published lessons.

Later, if the LMS needs stable course versions, we can introduce course-versioning.

---

# 19. Completion vs watching

This distinction will become especially important in **6.5 — Video / Content Progress**.

A student might watch:

```text
Video = 42%
```

but the lesson isn't necessarily complete.

So:

```text
Video Progress
       ≠
Lesson Completion
```

For example:

```text
Video watched: 92%
Lesson completed: false
```

Depending on your product rules, we might automatically mark it complete after a threshold.

For example:

```text
watch >= 90%
      ↓
eligible for completion
```

But that's a business rule, not something we should blindly assume.

# 22. Error cases

A production endpoint needs predictable errors.

|Situation|Response|
|---|--:|
|Not authenticated|`401`|
|Lesson doesn't exist|`404`|
|Student not enrolled|`403`|
|Lesson doesn't belong to enrolled course|`403`|
|Already completed|`200` / idempotent success|
|Database failure|`500`|

The exact status for "already completed" can vary depending on API design.

I prefer making the operation **idempotent**, so repeating the same request doesn't feel like an error.

# 23. Security checklist

For this endpoint:

```http
POST /api/v1/lessons/:lessonId/complete
```

the backend should verify:

```text
✓ User is authenticated
✓ User is a student / allowed role
✓ Lesson exists
✓ Course exists
✓ Student is enrolled
✓ Enrollment is active
✓ Lesson belongs to that course
✓ Completion belongs to that enrollment
✓ Duplicate completion is impossible
```

Notice how many security checks happen **before** the database write.

This is why authorization is a core backend engineering skill.

---

# 24. Database constraints

Our database should protect important invariants.

### One completion per lesson per enrollment

```prisma
@@unique([enrollmentId, lessonId])
```

### Fast lookup by enrollment

```prisma
@@index([enrollmentId])
```

### Fast lookup by lesson

```prisma
@@index([lessonId])
```

Why index `enrollmentId`?

Because we'll frequently ask:

```text
Give me all lessons completed by this student
for this enrollment.
```

Why index `lessonId`?

Because instructors or analytics systems may ask:

```text
How many students completed this lesson?
```

These indexes become especially useful as your LMS grows.

---

# 25. Don't create unnecessary indexes

You shouldn't automatically index every column.

For example:

```text
completedAt
```

doesn't necessarily need an index just because it exists.

Indexes have costs:

```text
More indexes
    ↓
More storage
    ↓
More write overhead
```

So indexes should be based on actual query patterns.

This connects directly back to your Phase 3 database engineering lessons.
