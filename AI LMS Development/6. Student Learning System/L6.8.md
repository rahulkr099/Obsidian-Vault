# Lesson 6.8 — Learning History

In **6.7 — Notes**, we added personal student data.

Now we need to answer a different question:

> **What has the student actually done while learning?**

This is the purpose of **Learning History**.

Your roadmap places **6.8 Learning History** after enrollment, progress, completion, content progress, bookmarks, and notes.

---

# 1. What is Learning History?

Imagine Rahul is learning:

```text
Course: Backend Engineering
```

During one day, he:

```text
10:00 → Opened course
10:05 → Started Lesson 1
10:25 → Completed Lesson 1
10:30 → Started Lesson 2
10:45 → Created a bookmark
10:50 → Added a note
11:10 → Completed Lesson 2
```

Instead of only keeping the **current state**, we can keep meaningful events:

```text
Learning History
────────────────────────────
10:00  Course opened
10:05  Lesson started
10:25  Lesson completed
10:45  Bookmark created
10:50  Note created
11:10  Lesson completed
```

This gives us a timeline of the student's learning activity.

---

# 2. History vs current state

This is one of the most important concepts in this lesson.

Consider:

```text
ContentProgress
position = 1800
```

This tells us:

> Where is the student now?

But it doesn't tell us:

```text
What happened yesterday?
What lesson did they complete first?
When did they create the bookmark?
When did they last study?
```

Learning History answers those questions.

So:

```text
Current State
     ↓
"What is true now?"

Learning History
     ↓
"What happened?"
```

---

# 3. Example

Current state:

```text
Course Progress = 60%
Current Lesson = Lesson 15
```

History:

```text
August 12
  Lesson 12 completed

August 13
  Lesson 13 completed
  Lesson 14 completed

August 14
  Lesson 15 started
  Bookmark created
  Note created
```

These are different types of information.

---

# 4. Why do we need history?

Learning history can power features such as:

```text
Recent activity
Learning timeline
Student dashboard
Instructor analytics
Study streaks
Course activity
Learning statistics
Recommendations
```

For example:

```text
Recent Activity

✓ Completed "JWT Authentication"
  10 minutes ago

🔖 Bookmarked "Refresh Token Rotation"
  20 minutes ago

📝 Added a note to "PostgreSQL Indexes"
  30 minutes ago
```

---

# 5. What should we record?

This is where we need to be careful.

We **shouldn't record every tiny action**.

For example, we probably don't need:

```text
Mouse moved
Mouse moved
Mouse moved
Video position = 101
Video position = 102
Video position = 103
```

That would create enormous amounts of useless data.

Instead, record **meaningful learning events**.

For example:

```text
COURSE_ENROLLED
LESSON_STARTED
LESSON_COMPLETED
BOOKMARK_CREATED
NOTE_CREATED
NOTE_UPDATED
QUIZ_COMPLETED
COURSE_COMPLETED
CERTIFICATE_ISSUED
```

---

# 6. Event-based thinking

A useful way to think about Learning History is:

```text
Student action
      ↓
Meaningful event
      ↓
History record
```

For example:

```text
Student completes lesson
        ↓
LESSON_COMPLETED
        ↓
LearningHistory record
```

Or:

```text
Student creates bookmark
        ↓
BOOKMARK_CREATED
        ↓
LearningHistory record
```

This is much cleaner than trying to store every frontend interaction.

---

# 7. Database model

A generic model could look like:

```prisma
model LearningHistory {
  id           String   @id @default(uuid())

  enrollmentId String
  type         LearningEventType

  lessonId     String?

  metadata     Json?

  createdAt    DateTime @default(now())

  enrollment   Enrollment @relation(
    fields: [enrollmentId],
    references: [id]
  )

  lesson       Lesson? @relation(
    fields: [lessonId],
    references: [id]
  )

  @@index([enrollmentId, createdAt])
  @@index([lessonId])
}
```

And:

```prisma
enum LearningEventType {
  COURSE_ENROLLED
  LESSON_STARTED
  LESSON_COMPLETED
  BOOKMARK_CREATED
  NOTE_CREATED
  NOTE_UPDATED
  QUIZ_COMPLETED
  COURSE_COMPLETED
  CERTIFICATE_ISSUED
}
```

The exact event list can evolve as the LMS grows.

---

# 8. Why use an enum?

Instead of:

```text
type = "lesson completed"
```

or:

```text
type = "LessonCompleted"
```

we define controlled values:

```text
LESSON_STARTED
LESSON_COMPLETED
BOOKMARK_CREATED
```

This prevents inconsistent values such as:

```text
"lesson_completed"
"LessonCompleted"
"lesson-complete"
"completed_lesson"
```

A controlled event type makes querying much easier.

---

# 9. Why is `lessonId` optional?

Not every learning event belongs to a lesson.

For example:

```text
COURSE_ENROLLED
```

belongs to the course/enrollment.

But:

```text
LESSON_COMPLETED
```

belongs to a specific lesson.

So:

```text
COURSE_ENROLLED
    ↓
lessonId = NULL

LESSON_COMPLETED
    ↓
lessonId = lesson_123
```

This gives us flexibility.

---

# 10. Why use `metadata`?

Sometimes an event needs additional information.

For example:

```text
QUIZ_COMPLETED
```

might contain:

```json
{
  "score": 85,
  "attempt": 2
}
```

Or:

```text
VIDEO_COMPLETED
```

might contain:

```json
{
  "watchedPercentage": 95
}
```

Instead of creating dozens of columns:

```text
score
attempt
watchedPercentage
position
...
```

we can use:

```text
metadata
```

for event-specific information.

But don't put everything into JSON.

Core relationships should remain proper relational columns.

---

# 11. Relational data vs metadata

Good:

```text
enrollmentId
lessonId
type
createdAt
```

These are important structured fields.

Additional event-specific information:

```json
{
  "score": 85
}
```

can go into metadata.

Think:

```text
Important queryable structure
        ↓
Relational columns

Extra event details
        ↓
JSON metadata
```

---

# 12. Why not make 10 different history tables?

You might think:

```text
LessonHistory
BookmarkHistory
NoteHistory
QuizHistory
CourseHistory
...
```

This can become unnecessarily complicated.

A unified event table is often easier for a student's timeline:

```text
LearningHistory
────────────────────────
10:00 COURSE_ENROLLED
10:05 LESSON_STARTED
10:20 LESSON_COMPLETED
10:25 BOOKMARK_CREATED
10:30 NOTE_CREATED
```

Now:

```text
GET /learning-history
```

can return everything in chronological order.

---

# 13. But don't turn it into a garbage table

A common mistake is creating:

```text
Activity
───────
userId
action
data
```

and putting absolutely everything into it.

Then six months later:

```text
action = "whatever"
data = { ... }
```

and nobody knows what it means.

Instead, define:

```text
Event types
Event meaning
Event metadata
Retention rules
```

Keep the event system intentional.

---

# 14. Who owns the history?

Our relationship:

```text
User
  ↓
Enrollment
  ↓
LearningHistory
```

This is useful because history is tied to a specific course-learning experience.

For example:

```text
Rahul
 ├── React Course
 │     └── History
 │
 └── PostgreSQL Course
       └── History
```

This makes course-specific history easy to retrieve.

```text

lessonId: lesson_456
metadata:
{
  "positionSeconds": 1840
}
createdAt: 2026-08-14 10:35
```

Then a note:

```text
LearningHistory
────────────────────────────────
id: history_3
enrollmentId: enrollment_123
type: NOTE_CREATED

metadata:
{
  "noteId": "note_789"
}
createdAt: 2026-08-14 10:40
```

---

# 16. Should we store the actual note content?

Usually, no.

Don't duplicate:

```text
Note.content
```

inside:

```text
LearningHistory.metadata
```

Instead:

```json
{
  "noteId": "note_789"
}
```

Then:

```text
LearningHistory
       ↓
noteId
       ↓
Note
```

Why?

Because the history event says:

> "A note was created."

The `Note` entity contains:

> "What the note currently says."

This prevents unnecessary duplication.

---

# 17. Event vs entity

This distinction is very important.

### Entity

Represents current state:

```text
Note
Bookmark
Enrollment
LearningProgress
```

### Event

Represents something that happened:

```text
NOTE_CREATED
BOOKMARK_CREATED
LESSON_COMPLETED
```

So:

```text
Entity
→ What exists?

Event
→ What happened?
```

This is a fundamental backend/system-design concept.

---

# 18. Creating history

When a meaningful action happens:

```text
Student completes lesson
```

we can perform:

```text
1. Create LessonCompletion
2. Create LearningHistory event
3. Update progress
```

These operations are related.

We may want a transaction:

```text
BEGIN

Create LessonCompletion
Create LearningHistory
Update LearningProgress

COMMIT
```

If something fails:

```text
ROLLBACK
```

This keeps the student's learning state consistent.

---

# 19. Example transaction

Conceptually:

```ts
await prisma.$transaction(async (tx) => {
  await tx.lessonCompletion.upsert({
    where: {
      enrollmentId_lessonId: {
        enrollmentId,
        lessonId,
      },
    },
    create: {
      enrollmentId,
      lessonId,
    },
    update: {},
  });

  await tx.learningHistory.create({
    data: {
      enrollmentId,
      type: "LESSON_COMPLETED",
      lessonId,
    },
  });
});
```

Now:

```text
Lesson completed
        +
History recorded
```

happen together.

---

# 20. A subtle problem: duplicate events

Remember from 6.3:

```text
POST /lessons/:lessonId/complete
```

should be idempotent.

But now there's another issue.

Suppose the student sends the request twice:

```text
Request A → complete
Request B → complete
```

If we use `upsert` for completion but blindly create history:

```text
LessonCompletion
→ one record

LearningHistory
→ two LESSON_COMPLETED events
```

Is that okay?

Maybe not.

We need to distinguish:

```text
First completion
```

from:

```text
Repeated completion request
```

---

# 21. Preventing duplicate meaningful events

One approach:

```text
Check whether completion already existed.
```

If it didn't:

```text
Create completion
Create LESSON_COMPLETED history
```

If it already existed:

```text
Don't create another completion event.
```

Conceptually:

```text
Existing completion?
      │
   ┌──┴──┐
  YES    NO
   │      │
  no     create
history  completion
         +
         history
```

This gives us a clean event timeline.

---

# 22. History is not necessarily audit logging

Don't confuse:

```text
Learning History
```

with:

```text
Security Audit Log
```

Learning history:

```text
Student completed Lesson 5
Student created bookmark
Student completed quiz
```

Security audit log:

```text
Admin changed user role
Failed login
Password reset requested
Permission denied
```

They serve different purposes.

You may eventually have both:

```text
LearningHistory
SecurityAuditLog
```

The latter connects strongly with your later security engineering phase.

# 24. Pagination is important

Learning history can grow indefinitely.

Suppose:

```text
100 lessons
+
500 bookmarks
+
300 notes
+
200 quiz attempts
```

You could easily have:

```text
1000+ events
```

Don't return everything.

Use:

```http
GET /api/v1/learning-history?page=1&limit=20
```

And sort:

```text
createdAt DESC
```

so the newest activity appears first.

# 25. Index design

A very useful index is:

```prisma
@@index([enrollmentId, createdAt])
```

Why?

A common query is:

```text
Give me this student's learning history
ordered by newest activity.
```

The database can efficiently work with:

```text
enrollmentId
+
createdAt
```

This is a good example of designing indexes around actual queries.

# 29. Privacy considerations

Learning history is personal data.

For example:

```text
Student studied at 2 AM
Student repeatedly revisited Lesson 5
Student bookmarked certain topics
```

This shouldn't automatically be visible to everyone.

Default:

```text
Student
   ↓
Own history
```

An instructor may receive aggregate information such as:

```text
70% of students completed Lesson 5
```

rather than:

```text
Rahul studied Lesson 5 at 2:13 AM
```

unless the product explicitly requires detailed instructor visibility.

This is an important privacy-by-design principle.

---

# 30. Don't over-track students

A tempting design is:

```text
Track everything
```

But more tracking means:

```text
More storage
More complexity
More privacy concerns
More maintenance
```

Instead:

> **Track events that provide clear product value.**

Good:

```text
LESSON_COMPLETED
QUIZ_COMPLETED
COURSE_COMPLETED
BOOKMARK_CREATED
```

Potentially unnecessary:

```text
MOUSE_MOVED
BUTTON_HOVERED
EVERY_VIDEO_SECOND
```

unless you have a specific analytics requirement.

# 34. Don't use metadata for everything

Bad design:

```json
{
  "studentId": "...",
  "courseId": "...",
  "lessonId": "...",
  "type": "...",
  "createdAt": "..."
}
```

all inside:

```text
metadata
```

That makes querying much harder.

Instead:

```text
enrollmentId → column
lessonId → column
type → column
createdAt → column
```

and:

```text
metadata → additional information
```

Good database design means choosing the right structure for the right data.

# 38. Important design rule

A powerful rule to remember:

> **Don't use the history table as the source of truth for current learning state.**

For example, don't calculate:

```text
Current progress
```

only by looking at events if you already have proper completion records.

Instead:

```text
LessonCompletion
→ current completion state

ContentProgress
→ current content state

Bookmark
→ current bookmark state

Note
→ current note state

LearningHistory
→ record of meaningful events
```

This separation makes your system easier to maintain.

---

# 39. Event history vs event sourcing

You may hear a more advanced term:

> **Event Sourcing**

That is a different architecture where the events themselves become the primary source of truth.

For example:

```text
LESSON_STARTED
LESSON_COMPLETED
LESSON_UNCOMPLETED
...
```

and the current state is rebuilt from those events.

We are **not** doing full event sourcing here.

Our LMS uses a simpler model:

```text
Normal relational state
+
Learning history events
```

That's much more appropriate for your current project.
