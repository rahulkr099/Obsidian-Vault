# Lesson 6.9 — Student Dashboard

Now that we've built:

```text
6.1 Enrollment
6.2 Learning Progress
6.3 Lesson Completion
6.4 Course Progress
6.5 Content Progress
6.6 Bookmarks
6.7 Notes
6.8 Learning History
```

we finally have enough learning data to build something students actually see every day:

> **The Student Dashboard.**

The dashboard is the **presentation layer** that brings all of those systems together.

---

# 1. What is a Student Dashboard?

A student dashboard answers questions like:

```text
What am I learning?
Where did I stop?
How much have I completed?
What should I continue?
What did I recently do?
What did I bookmark?
What courses need my attention?
```

A simple dashboard could look like:

```text
┌─────────────────────────────────────────────┐
│ Welcome back, Rahul 👋                     │
│                                             │
│ Continue Learning                           │
│ ┌─────────────────────────────────────────┐ │
│ │ Backend Engineering                     │ │
│ │ ███████████░░░░░░ 62%                   │ │
│ │ Lesson 15: Redis Fundamentals           │ │
│ │                         Continue →      │ │
│ └─────────────────────────────────────────┘ │
│                                             │
│ My Courses                                  │
│                                             │
│ PostgreSQL       ███████░░ 70%              │
│ TypeScript       █████░░░░ 50%              │
│ React            █████████ 90%              │
│                                             │
│ Recent Activity                             │
│ ✓ Completed JWT Authentication              │
│ 🔖 Bookmarked Refresh Tokens                │
│ 📝 Added a note                              │
└─────────────────────────────────────────────┘
```

Notice something important:

> The dashboard itself doesn't create most of this information.

It **reads information produced by the learning systems we built earlier.**

---

# 2. Dashboard is an aggregation layer

Think about the architecture:

```text
                    Student
                       │
                       ↓
                  Dashboard API
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
   Enrollment      Progress        History
        │              │              │
        ↓              ↓              ↓
     Courses         Lessons       Activities
```

And additionally:

```text
Bookmarks
Notes
Content Progress
Lesson Completion
```

So the dashboard is essentially:

```text
Multiple learning systems
        ↓
     Aggregate
        ↓
 Student Dashboard
```

This is a very important backend pattern.

---

# 3. Dashboard should not become a new source of truth

Don't create:

```text
StudentDashboard
----------------
courseProgress
completedLessons
bookmarkCount
noteCount
lastLesson
...
```

and manually maintain all of it unless there is a specific performance reason.

Instead:

```text
Enrollment
Progress
Completion
Bookmarks
Notes
History
      ↓
Dashboard response
```

The dashboard should initially be a **view of existing data**.

# 5. Continue Learning

This should probably be the most important dashboard section.

Why?

Because the student's next action is often:

> **Continue where I left off.**

Suppose:

```text
Course:
Backend Engineering

Progress:
62%

Current lesson:
Redis Fundamentals

Position:
18:42
```

Dashboard:

```text
Continue Learning

Backend Engineering
62% complete

Redis Fundamentals
18:42

[ Continue Learning ]
```

Clicking the button takes the student directly to:

```text
/course/backend-engineering/learn/redis-fundamentals
```

and the video resumes at:

```text
18:42
```

# 6. How do we determine "Continue Learning"?

This is more interesting than it looks.

We already have:

```text
Enrollment
ContentProgress
LessonCompletion
LearningHistory
```

We can use these to determine the next lesson.

For example:

```text
Lesson 1 → completed
Lesson 2 → completed
Lesson 3 → completed
Lesson 4 → incomplete
Lesson 5 → incomplete
```

Then:

```text
Continue Learning
      ↓
Lesson 4
```

But if the student has content progress on Lesson 4:

```text
positionSeconds = 920
```

then:

```text
Continue Lesson 4
Resume at 15:20
```

---

# 7. A simple algorithm

Conceptually:

```text
1. Find active enrollments
2. Find course lessons
3. Find completed lessons
4. Find incomplete lessons
5. Find latest content progress
6. Select the most appropriate lesson
```

For example:

```text
Completed:
1, 2, 3

Progress:
4 → 15:20

Next lesson:
4
```

Therefore:

```text
Continue Learning
→ Lesson 4 at 15:20
```

# 11. Course status

Each course could have a status:

```text
NOT_STARTED
IN_PROGRESS
COMPLETED
```

Example:

```text
Course A → NOT_STARTED
Course B → IN_PROGRESS
Course C → COMPLETED
```

This can be derived.

For example:

```text
No completed lessons
AND
No meaningful activity
        ↓
NOT_STARTED
```

```text
Some progress
AND
< 100%
        ↓
IN_PROGRESS
```

```text
100%
        ↓
COMPLETED
```

But remember from 6.4:

> **100% progress and completion eligibility are not necessarily identical.**

If later we require a final quiz, completion status must also consider that.

# 12. Dashboard API

We don't want the frontend making 15 separate requests:

```text
GET /enrollments
GET /courses
GET /progress
GET /history
GET /bookmarks
GET /notes
GET /...
```

That can create unnecessary network overhead.

Instead, we can provide an aggregation endpoint:

```http
GET /api/v1/student/dashboard
```

The backend returns the dashboard data.

Example:

```json
{
  "success": true,
  "data": {
    "summary": {},
    "continueLearning": {},
    "courses": [],
    "recentActivity": [],
    "bookmarks": []
  }
}
```

This is an example of a **Backend-for-Frontend (BFF)-style aggregation endpoint**.

# 14. Dashboard service

The controller should stay thin:

```ts
export const getStudentDashboard = asyncHandler(
  async (req, res) => {
    const studentId = req.user.userId;

    const dashboard =
      await dashboardService.getStudentDashboard(
        studentId
      );

    res.json({
      success: true,
      data: dashboard,
    });
  }
);
```

Notice:

```text
Controller
    ↓
dashboardService
```

The service coordinates the other services/repositories.

---

# 15. Should the dashboard service contain database queries?

Ideally, avoid turning it into a giant Prisma file.

Bad:

```ts
dashboardService.ts

500 lines of Prisma queries
```

Better:

```text
Dashboard Service
       │
       ├── Enrollment Repository
       ├── Progress Repository
       ├── History Repository
       ├── Bookmark Repository
       └── Course Repository
```

Then:

```text
Dashboard Service
→ orchestration

Repositories
→ data access
```

This matches the architecture you've been following throughout the LMS.

# 16. Parallel database queries

Some dashboard data is independent.

For example:

```text
Courses
History
Bookmarks
```

could potentially be fetched in parallel.

Conceptually:

```ts
const [
  courses,
  recentActivity,
  bookmarks,
] = await Promise.all([
  courseService.getStudentCourses(studentId),
  historyService.getRecent(studentId),
  bookmarkService.getRecent(studentId),
]);
```

Instead of:

```text
courses
  ↓
wait
  ↓
history
  ↓
wait
  ↓
bookmarks
```

we can do:

```text
courses ───────┐
history ───────┼──→ dashboard
bookmarks ─────┘
```

This can reduce total response time.

But don't blindly parallelize queries that depend on one another.

# 17. Dashboard query design

Suppose we have:

```text
4 enrolled courses
```

A naive implementation might do:

```text
Get courses
   ↓
for each course:
    get progress
    get lessons
    get history
```

This can produce the classic:

> **N+1 query problem.**

For example:

```text
1 query → courses

4 queries → progress
4 queries → lessons
4 queries → activity
```

Total:

```text
13 queries
```

For 100 courses:

```text
301+ queries
```

That can become inefficient.

---

# 18. Avoiding N+1

Instead of:

```text
Course 1 → query
Course 2 → query
Course 3 → query
...
```

design repository queries that fetch aggregated information in batches.

For example:

```text
Get all enrollments
        ↓
Get progress for all enrollment IDs
        ↓
Group results in application/service layer
```

Or use carefully designed Prisma relations/aggregations.

The exact implementation depends on your schema.

The important lesson:

> **Think about query count, not just whether each individual query works.**

# 19. Dashboard is a read-heavy feature

A student might open the dashboard:

```text
Morning
Afternoon
Evening
```

while the dashboard doesn't modify much data.

This makes it a:

```text
READ-HEAVY
```

feature.

That means future optimizations may include:

```text
Caching
Precomputed summaries
Redis
Materialized views
```

But don't introduce them yet unless needed.

# 20. Caching

Suppose:

```text
10,000 students
```

and many students repeatedly open their dashboard.

We might eventually cache:

```text
student_dashboard:user_123
```

for a short period.

For example:

```text
Dashboard request
       ↓
Redis
       ↓
Cache hit?
   /        \
 YES         NO
 ↓            ↓
Return     PostgreSQL
             ↓
          Cache result
```

This becomes relevant in later infrastructure phases.

---

# 21. Don't cache everything

Some information should remain fresh.

For example:

```text
Course Progress
```

can change immediately after completing a lesson.

If the dashboard cache lives for:

```text
30 minutes
```

the student might still see:

```text
62%
```

after reaching:

```text
65%
```

So caching introduces a trade-off:

```text
Freshness
   ↕
Performance
```

A short TTL or targeted cache invalidation can solve this later.

# 27. Learning summary

We can display:

```text
Learning Summary

4 Courses Enrolled
1 Course Completed
37 Lessons Completed
12 Hours Learned
```

But be careful with:

```text
12 Hours Learned
```

We need a reliable definition.

If we only have periodic video progress updates, then:

```text
positionSeconds
```

doesn't necessarily equal actual watch time.

For example, a student could seek forward.

So metrics must be based on clearly defined rules.

Don't invent impressive-looking numbers without reliable underlying data.

---

# 28. "Hours learned" is harder than it looks

Suppose:

```text
Video duration = 60 minutes
Student seeks from 5:00 → 50:00
```

If we calculate:

```text
50 minutes watched
```

we would be wrong.

The student may have watched only:

```text
5 minutes
```

Therefore, accurate watch-time analytics may require tracking:

```text
watched intervals
```

rather than only:

```text
current position
```

For now, we should avoid presenting highly precise watch-time metrics unless we have designed the tracking system for it.

This is an important product/data-quality lesson.

# 29. Dashboard and authorization

The dashboard endpoint:

```http
GET /api/v1/student/dashboard
```

should use:

```ts
req.user.userId
```

to determine the student.

It should **never** accept:

```http
GET /student/dashboard?studentId=123
```

as the source of identity.

Otherwise:

```text
Student A
   ↓
changes studentId
   ↓
Student B's dashboard
```

That's an IDOR-style authorization problem.

The authenticated identity should be authoritative.

---

# 30. Dashboard should expose only allowed data

Suppose the database contains:

```text
Student profile
Payment information
Internal admin flags
Private notes
Security data
```

The dashboard shouldn't simply return:

```ts
prisma.user.findUnique(...)
```

and serialize everything.

Instead, explicitly select what the dashboard needs.

For example:

```text
name
avatar
courses
progress
recentActivity
bookmarks
```

This follows the principle:

> **Return the minimum data required by the client.**

# 34. Dashboard endpoint vs many endpoints

There are two common approaches.

### Approach A — One dashboard endpoint

```text
GET /student/dashboard
```

Returns everything.

### Approach B — Multiple endpoints

```text
GET /student/courses
GET /student/activity
GET /student/bookmarks
GET /student/stats
```

Which is better?

For an initial dashboard:

```text
One aggregation endpoint
```

is often convenient.

But internally, keep the services modular.

So:

```text
One HTTP endpoint
       ↓
Multiple services
```

This gives us the best of both worlds.

# 36. Don't duplicate business logic

Bad:

```text
CourseService calculates progress one way.

DashboardService calculates progress differently.
```

Then:

```text
Course page → 62%
Dashboard → 65%
```

That's a serious problem.

Instead:

```text
ProgressService
      ↓
single source of progress calculation
```

Then both:

```text
Course Page
Dashboard
```

use the same logic.

This is a very important architecture rule:

> **Business rules should have one authoritative implementation.**

# 37. Example service composition

Conceptually:

```ts
async function getStudentDashboard(studentId: string) {
  const [
    summary,
    continueLearning,
    courses,
    recentActivity,
    bookmarks,
  ] = await Promise.all([
    studentService.getSummary(studentId),
    learningService.getContinueLearning(studentId),
    courseService.getStudentCourses(studentId),
    historyService.getRecent(studentId, 10),
    bookmarkService.getRecent(studentId, 5),
  ]);

  return {
    summary,
    continueLearning,
    courses,
    recentActivity,
    bookmarks,
  };
}
```

Notice:

```text
DashboardService
```

is coordinating rather than reinventing every domain rule.

# 39. Don't let the frontend become the business layer

Avoid:

```ts
// frontend
const completed =
  courses.reduce(...);

const percentage =
  completed / total * 100;
```

for trusted learning state.

The backend should provide:

```json
{
  "progressPercentage": 62
}
```

The frontend should mainly:

```text
Render
Format
Animate
Navigate
```

not determine authoritative learning state.

# 40. Dashboard loading state

The dashboard combines multiple pieces of data.

The UI should handle:

```text
Loading
Success
Empty
Error
Partial failure
```

For example:

```text
Loading...
```

Then:

```text
Dashboard loaded
```

If bookmarks fail but courses load:

```text
Courses ✓
Progress ✓
Activity ✓
Bookmarks ⚠️
```

Whether you support partial failures depends on your API architecture.

A single aggregation endpoint can simplify this, because the backend can decide how to handle individual internal failures.

---

# 41. Error handling

Suppose:

```text
GET /student/dashboard
```

fails.

Don't return:

```text
500
database error: PrismaClientKnownRequestError...
```

to the client.

Instead:

```json
{
  "success": false,
  "error": {
    "code": "DASHBOARD_FETCH_FAILED",
    "message": "Unable to load dashboard."
  }
}
```

Log the detailed technical error on the server.

This follows the error-handling architecture from earlier phases.

# 42. Dashboard performance

Let's imagine:

```text
100,000 students
```

and every student opens the dashboard after login.

The dashboard becomes a high-read endpoint.

Things to monitor:

```text
Response time
Database query count
Database CPU
Cache hit rate
Payload size
Slow queries
```

Don't optimize prematurely.

First:

```text
Correct
↓
Measure
↓
Identify bottleneck
↓
Optimize
```

That's the proper engineering workflow.

# 47. Important backend lessons

### Lesson 1 — Dashboard is an aggregation layer

```text
Multiple domain systems
        ↓
Dashboard
```

### Lesson 2 — Don't create duplicate sources of truth

Progress should still come from:

```text
Progress / Completion
```

not from a random dashboard table.

### Lesson 3 — Avoid N+1 queries

Think about:

```text
Number of database queries
```

not only individual query correctness.

### Lesson 4 — Reuse business logic

```text
ProgressService
      ↓
Course Page
Dashboard
Instructor Dashboard
```

Everyone should get consistent results.

### Lesson 5 — The backend owns authoritative state

The frontend renders the dashboard.

The backend determines:

```text
Progress
Completion
Enrollment
Permissions
```

## Answers

```text
1. Because the dashboard should present existing learning
   state, not maintain another potentially inconsistent copy.

2. It gives the frontend one convenient aggregation
   endpoint while allowing the backend to use multiple
   internal services.

3. It happens when one query retrieves a list and then
   additional queries are executed for each item,
   producing many unnecessary database queries.

4. Otherwise different parts of the application could
   calculate progress differently and show inconsistent
   results.

5. The most appropriate course and lesson for the student
   to continue, including the saved content position when
   available.

6. Return an empty but valid dashboard and let the UI show
   something like "Explore Courses."

7. It identifies the authenticated student without trusting
   a student ID supplied by the client.

8. First build the correct system, measure performance, find
   real bottlenecks, and then introduce caching where it
   provides a clear benefit.
```
