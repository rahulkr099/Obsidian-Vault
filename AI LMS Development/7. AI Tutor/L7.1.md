# Lesson 7.1 — AI Architecture & LLM Fundamentals

Welcome to **Phase 7: AI Tutor**. 🚀

Until Phase 6, our system was mostly a traditional LMS:

```text
Student
   ↓
Next.js
   ↓
API
   ↓
Services
   ↓
Prisma
   ↓
PostgreSQL
```

Now we're going to introduce an AI system into that architecture.

The goal of this lesson is **not** to immediately write an AI chatbot. First, you need to understand **how an AI-powered backend should be designed**.

---

# 1. What Are We Actually Building?

Our LMS will eventually have an AI tutor.

A student might ask:

> "Explain recursion in simple words."

The request should roughly flow like this:

```text
Student
   ↓
Frontend
   ↓
POST /api/v1/ai/chat
   ↓
Authentication
   ↓
AI Controller
   ↓
AI Service
   ↓
Context Builder
   ↓
LLM Provider
   ↓
AI Response
   ↓
Save Conversation
   ↓
Student
```

The important idea is:

> **The LLM should not become your application's business logic.**

Your application controls the AI.

---

# 2. What Is an LLM?

LLM stands for:

**Large Language Model**

Examples include models from providers such as OpenAI, Anthropic, Google, etc.

At a high level:

```text
Input
  ↓
LLM
  ↓
Generated output
```

For example:

```text
Input:
"Explain binary search."

Output:
"Binary search is an algorithm that..."
```

But an LLM doesn't automatically know your LMS data.

For example, suppose your database contains:

```text
Course:
Backend Engineering

Lesson:
Redis Caching

Instructor:
Rahul

Private Notes:
...
```

The model doesn't automatically have access to your PostgreSQL database.

You have to explicitly provide the information it should use.

---

# 3. The Most Important Mental Model

Think about an LLM as a function:

```text
LLM(input) → output
```

Your application sits around that function.

```text
                ┌──────────────┐
User ──────────→│ Your Backend │
                └──────┬───────┘
                       │
                       ↓
                Prepare context
                       │
                       ↓
                ┌──────────────┐
                │     LLM      │
                └──────┬───────┘
                       │
                       ↓
                Validate response
                       │
                       ↓
                    User
```

This distinction is extremely important for backend engineering.

---

# 4. AI Application ≠ LLM

A common beginner mistake is thinking:

```text
AI application
=
LLM API call
```

It isn't.

A real AI application contains many components:

```text
Authentication
      ↓
Authorization
      ↓
Input validation
      ↓
Prompt/context construction
      ↓
LLM provider
      ↓
Output handling
      ↓
Persistence
      ↓
Usage tracking
      ↓
Logging
      ↓
Error handling
```

The LLM is only **one component**.


# 6. AI Provider

We don't want our entire application to depend directly on one AI company.

Bad architecture:

```text
AI Controller
      ↓
OpenAI SDK
      ↓
OpenAI
```

Imagine six months later you want to use another provider.

You could end up changing code everywhere.

Instead:

```text
AI Controller
      ↓
AI Service
      ↓
AI Provider Interface
      ↓
┌────────────┬─────────────┐
↓            ↓             ↓
Provider A  Provider B   Provider C
```

This is called **provider abstraction**.

We'll build this properly in **Lesson 7.2**.

---

# 7. Why Provider Abstraction Matters

Suppose your application currently uses:

```text
Provider A
```

Later you want:

```text
Provider B
```

Without abstraction:

```text
Controllers
Services
Utilities
Workers
Tests
       ↓
Provider A SDK
```

You have to change many places.

With abstraction:

```text
Application
     ↓
AIProvider
     ↓
Provider A
```

Changing providers becomes much easier.

This is a classic software engineering principle:

> **Depend on abstractions, not concrete implementations.**

---

# 8. Prompt

The instructions we send to an LLM are generally called a **prompt**.

A simple example:

```text
Explain binary search to a beginner.
```

But our AI tutor will eventually use structured context.

Conceptually:

```text
System instructions
+
Student question
+
Course information
+
Lesson information
+
Conversation history
```

Then:

```text
                Context
                   ↓
             ┌───────────┐
             │    LLM    │
             └─────┬─────┘
                   ↓
                Answer
```

---

# 9. System Instructions vs User Message

It's useful to separate instructions from the student's question.

For example:

```text
System:
You are an educational AI tutor.
Explain concepts clearly.
Do not invent information about the course.

User:
Explain database normalization.
```

The system establishes the AI's behavior.

The user provides the current request.

We'll later design this more carefully because **prompt injection and AI security** become important in Phase 14.

---

# 10. Context

Context is the information available to the model for generating its response.

Suppose the student is studying:

```text
Course:
Database Engineering

Lesson:
Database Normalization

Previous conversation:
Student: What is 1NF?
AI: ...
Student: What about 2NF?
```

The next request might be:

```text
"Can you give me an example?"
```

That question doesn't contain enough information by itself.

The backend needs to understand:

```text
Course
   ↓
Lesson
   ↓
Conversation
   ↓
Current question
```

This is why **context management** will be a major part of Phase 7.

---

# 11. Context Window

LLMs have a limited amount of information they can process in a single request.

Think of it as:

```text
┌───────────────────────────────┐
│        Context Window         │
│                               │
│ System instructions           │
│ Course context                │
│ Lesson context                │
│ Conversation history          │
│ Current question              │
│                               │
└───────────────────────────────┘
```

If you keep adding more and more conversation history:

```text
Message 1
Message 2
Message 3
...
Message 500
```

eventually you cannot simply send everything.

Therefore, a production AI application needs strategies such as:

```text
Recent messages
      +
Important context
      +
Summaries
      +
Retrieved information
```

We'll study this properly in **Lesson 7.7** and much more deeply in Phase 8.

---

# 12. Stateless vs Stateful AI

This is an important backend concept.

### Stateless request

Every request is independent.

```text
Request 1 → LLM
Request 2 → LLM
Request 3 → LLM
```

The model doesn't automatically remember previous requests.

Your backend has to provide the necessary context.

---

### Stateful application

Your application stores conversation information.

For example:

```text
Conversation
     │
     ├── Message 1
     ├── Message 2
     ├── Message 3
     └── Message 4
```

Then when the student sends a new message:

```text
Database
   ↓
Conversation history
   ↓
Context builder
   ↓
LLM
```

This gives the user the experience of a continuous conversation.

---

# 13. Our Database Will Matter

Because we're building an LMS, AI conversations should eventually be associated with users.

Conceptually:

```text
User
 │
 └── Conversations
       │
       ├── Conversation
       │      ├── Message
       │      ├── Message
       │      └── Message
       │
       └── Conversation
              ├── Message
              └── Message
```

We can also associate conversations with:

```text
Course
Lesson
```

For example:

```text
User
 ↓
Conversation
 ↓
Course
 ↓
Lesson
```

This becomes extremely useful later for course-aware tutoring.

Our goal isn't to build:

This is much more powerful than a generic chatbot.

# 16. AI vs RAG

This distinction is very important.

### Phase 7

We'll build:

```text
Application context
       ↓
LLM
       ↓
Response
```

### Phase 8

We'll build:

```text
LMS Documents
       ↓
Chunking
       ↓
Embeddings
       ↓
Vector Database
       ↓
Retrieval
       ↓
Relevant Context
       ↓
LLM
       ↓
Response
```

That's RAG:

**Retrieval-Augmented Generation**

So don't worry about embeddings and vector databases yet.

---

# 17. Why We Don't Start With RAG

A common AI-project mistake is:

```text
"Let's add embeddings!"
```

before understanding the basic AI architecture.

Then the developer ends up with:

```text
Frontend
 ↓
Random AI API
 ↓
Vector DB
 ↓
Prompt
 ↓
????
```

Instead, we'll build progressively:

```text
LLM fundamentals
       ↓
AI service
       ↓
Conversation
       ↓
Context
       ↓
Course awareness
       ↓
RAG
```

This will make the architecture much easier to understand.

# 18. AI Service in Our Backend

Following our existing architecture:

```text
Controller
    ↓
Service
    ↓
Provider
```

Conceptually:

```text
AIController
     ↓
AIService
     ↓
AIProvider
```

The controller shouldn't contain things like:

```text
construct prompt
load conversation
call LLM
calculate tokens
save message
handle provider errors
```

That's too much responsibility.

Instead:

```text
AIController
```

should mainly handle:

```text
HTTP request
      ↓
validate input
      ↓
call service
      ↓
HTTP response
```

And:

```text
AIService
```

handles the AI business logic.

# 20. AI Usage Is Not Free

Another major difference from normal APIs:

```text
GET /courses
```

might be cheap.

But:

```text
AI request
```

can consume paid model resources.

Therefore, we need:

```text
Usage tracking
     ↓
Rate limits
     ↓
Quotas
     ↓
Cost monitoring
```

For example:

```text
Student
   ↓
10 AI requests/hour
```

or:

```text
Free user
   ↓
X tokens/day

Premium user
   ↓
Y tokens/day
```

We'll cover this in **Lesson 7.10**.

# 21. AI Errors Are Different

Traditional API:

```text
Database unavailable
      ↓
500 Internal Server Error
```

AI systems can fail in many ways:

```text
Provider unavailable
Rate limit
Timeout
Invalid response
Token limit
Model overloaded
Network failure
Content filtering
Unexpected provider error
```

So we'll eventually build:

```text
AI Service
    ↓
Provider
    ↓
Error normalization
    ↓
Application error
```

This prevents provider-specific errors from leaking throughout your application.

That's **Lesson 7.11**.

# 22. Observability

For production AI applications, you need to know:

```text
Who requested AI?
Which model?
How long did it take?
How many tokens?
Did it fail?
How much did it cost?
```

Conceptually:

```text
AI Request
    │
    ├── userId
    ├── model
    ├── latency
    ├── input tokens
    ├── output tokens
    ├── status
    └── estimated cost
```

This becomes very important once your LMS has real users.

We'll cover this in **7.12**.

# 24. What You Should Remember

If you remember only **10 things** from this lesson, remember these:

1. **LLM is only one component of an AI application.**
    
2. Your backend should control the AI workflow.
    
3. Don't tightly couple your application to one AI provider.
    
4. Use an **AI service layer**.
    
5. Conversations need persistent storage if we want chat history.
    
6. Context determines what information the model can use.
    
7. Phase 7 builds the AI foundation; **Phase 8 adds RAG**.
    
8. AI requests need usage limits because they can cost money.
    
9. AI providers can fail, so error handling and retries matter.
    
10. Production AI needs **observability and cost tracking**.
