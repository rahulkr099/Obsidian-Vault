# Lesson 7.10 — AI Streaming & Real-Time Responses

Until now, our AI Tutor works like this:

```text
Student
   ↓
Send question
   ↓
Wait...
   ↓
LLM generates complete answer
   ↓
Backend receives complete answer
   ↓
Frontend receives complete answer
```

For a short answer, that's fine.

But imagine the AI is generating a 500-word explanation.

The student sees:

```text
Thinking...
Thinking...
Thinking...
Thinking...
```

and then suddenly:

```text
Here is the entire answer.
```

Modern AI applications usually provide a better experience:

```text
Student
   ↓
Question
   ↓
AI starts generating
   ↓
"PostgreSQL..."
   ↓
"PostgreSQL indexes..."
   ↓
"PostgreSQL indexes help..."
   ↓
Complete answer
```

This is **streaming**.

---

# 1. What Is AI Streaming?

Streaming means sending the AI response to the client **incrementally as it is generated**, instead of waiting for the entire response.

Without streaming:

```text
LLM
 │
 │ generates entire response
 │
 ↓
Backend
 │
 │ entire response
 ↓
Frontend
```

With streaming:

```text
LLM
 │
 ├── chunk 1 ──→ Backend ──→ Frontend
 ├── chunk 2 ──→ Backend ──→ Frontend
 ├── chunk 3 ──→ Backend ──→ Frontend
 ├── chunk 4 ──→ Backend ──→ Frontend
 └── done
```

The user starts seeing the answer much earlier.

---

# 2. Why Streaming Matters for Our LMS

Streaming is especially useful for an AI Tutor because explanations can be long.

Imagine:

```text
Question:
Explain database normalization with examples.
```

Without streaming:

```text
0 sec ─────────────────────────────── 8 sec
             waiting...
                                      ↓
                              complete answer
```

With streaming:

```text
0 sec ── first words
1 sec ── more words
2 sec ── more words
3 sec ── more words
...
```

The **perceived latency** becomes much better.

---

# 3. Important Concept: Time to First Token

There are two useful measurements.

### Time to First Token — TTFT

How long until the user sees the first generated content?

```text
Request
   ↓
1.2 seconds
   ↓
First token
```

### Total Generation Time

How long until the entire response finishes?

```text
Request
   ↓
8 seconds
   ↓
Complete response
```

Streaming primarily improves the experience of the first one.

Even if total generation still takes 8 seconds, the user isn't staring at an empty screen for 8 seconds.

---

# 4. Streaming Does Not Make the Model Faster

This is important.

Streaming does **not necessarily reduce total generation time**.

It changes:

```text
How the response is delivered
```

rather than:

```text
How quickly the model thinks.
```

So:

```text
Without streaming:
8 sec → complete response

With streaming:
1 sec → first chunk
8 sec → complete response
```

The total time may be similar, but the experience is much better.

---

# 5. Streaming Architecture

Our architecture changes slightly.

Previously:

```text
Controller
   ↓
AITutorService
   ↓
AIProvider
   ↓
LLM
   ↓
Complete response
```

Now:

```text
Controller
   ↓
AITutorService
   ↓
AIProvider
   ↓
LLM
   ↓
Async Stream
   ↓
Controller
   ↓
Client
```

The AI provider doesn't necessarily return:

```ts
Promise<string>
```

It may return something closer to:

```ts
AsyncIterable<AIChunk>
```

---

# 6. What Is a Chunk?

A chunk is a small piece of the generated response.

For example, the model might conceptually produce:

```text
Chunk 1:
"PostgreSQL"

Chunk 2:
" indexes"

Chunk 3:
" are"

Chunk 4:
" data"

Chunk 5:
" structures..."
```

The exact chunk boundaries depend on the provider.

Don't assume:

```text
one chunk = one word
```

or:

```text
one chunk = one sentence
```

A chunk is simply an incremental piece of output.

---

# 7. Your Application Shouldn't Depend on Provider Chunk Format

Suppose Provider A gives:

```json
{
  "delta": "PostgreSQL"
}
```

Provider B might give:

```json
{
  "text": "PostgreSQL"
}
```

Your application shouldn't care.

Remember our provider abstraction:

```text
Provider A
      ↓
Provider Adapter
      ↓
Internal AI Stream

Provider B
      ↓
Provider Adapter
      ↓
Internal AI Stream
```

So define your own internal representation.

For example:

```ts
interface AIStreamChunk {
  type: "text";
  content: string;
}
```

Now:

```text
Provider
   ↓
AIStreamChunk
   ↓
AITutorService
```

---

# 8. Streaming Interface

Our AI provider could eventually expose:

```ts
interface AIProvider {
  generateText(
    input: GenerateTextInput
  ): Promise<AIResponse>;

  streamText(
    input: GenerateTextInput
  ): AsyncIterable<AIStreamChunk>;
}
```

Notice the difference:

```text
generateText()
    ↓
Promise<AIResponse>
```

versus:

```text
streamText()
    ↓
AsyncIterable<AIStreamChunk>
```

The first gives one final result.

The second gives multiple results over time.

---

# 9. What Is `AsyncIterable`?

You don't need to memorize the entire JavaScript specification.

Think of:

```ts
AsyncIterable<T>
```

as:

> "A sequence of values that will arrive asynchronously."

For example:

```ts
for await (const chunk of stream) {
  console.log(chunk);
}
```

Conceptually:

```text
chunk 1
   ↓
chunk 2
   ↓
chunk 3
   ↓
chunk 4
```

The loop waits for each chunk as it arrives.

This is very useful for AI streaming.

---

# 10. Example

Suppose:

```ts
const stream =
  provider.streamText(input);
```

Then:

```ts
for await (const chunk of stream) {
  console.log(chunk.content);
}
```

The output might appear gradually:

```text
PostgreSQL
PostgreSQL indexes
PostgreSQL indexes are
PostgreSQL indexes are useful
...
```

The exact behavior depends on how you combine chunks.

---

# 11. Why We Need a Streaming HTTP Protocol

Now the backend has a stream.

But how do we send that stream to the browser?

We need an HTTP mechanism suitable for incremental data.

One common choice is:

# Server-Sent Events — SSE

---

# 12. What Is SSE?

Server-Sent Events allow the server to continuously send events to the browser over a single HTTP connection.

Conceptually:

```text
Browser
   │
   │ HTTP request
   ↓
Server
   │
   │ event 1
   ├────────────────→ Browser
   │
   │ event 2
   ├────────────────→ Browser
   │
   │ event 3
   ├────────────────→ Browser
   │
   │ done
   └────────────────→ Browser
```

The connection remains open while the server is sending events.

---

# 13. SSE Is One-Way

This is an important property.

SSE is primarily:

```text
Server
   ↓
Client
```

The client sends the initial HTTP request:

```text
Client
   ↓
Server
```

Then the server streams updates:

```text
Server
   ↓
Client
```

For our AI Tutor, this can work very well because:

```text
Student sends question
```

then:

```text
Server streams AI response
```

---

# 14. SSE vs WebSockets

You may hear:

> "Shouldn't we use WebSockets for real-time applications?"

Not always.

### SSE

Good for:

```text
Server → Client streaming
```

### WebSockets

Good for:

```text
Two-way real-time communication
```

For example:

```text
SSE:
AI response streaming
notifications
progress updates
live status

WebSocket:
multiplayer game
collaborative editor
two-way live communication
```

For our AI response streaming use case, **SSE is a simple and good option**.

---

# 15. SSE Message Format

SSE responses use an event-oriented format.

Conceptually:

```text
data: {"content":"PostgreSQL"}

data: {"content":" indexes"}

data: {"content":" are useful"}

data: {"done":true}
```

Each event is separated appropriately according to the SSE protocol.

The browser can consume these events as they arrive.

---

# 16. HTTP Headers

The server needs to tell the client that this is an SSE stream.

Conceptually:

```http
Content-Type: text/event-stream
```

You generally also want caching disabled:

```http
Cache-Control: no-cache
```

and often:

```http
Connection: keep-alive
```

The exact connection behavior can vary depending on your infrastructure/proxy.

---

# 17. Express Example

A simplified Express controller could look like:

```ts
async function streamTutorResponse(
  req: Request,
  res: Response
) {
  res.setHeader(
    "Content-Type",
    "text/event-stream"
  );

  res.setHeader(
    "Cache-Control",
    "no-cache"
  );

  res.setHeader(
    "Connection",
    "keep-alive"
  );

  // stream...
}
```

Then:

```ts
for await (const chunk of stream) {
  res.write(
    `data: ${JSON.stringify(chunk)}\n\n`
  );
}
```

And when finished:

```ts
res.end();
```

This is the basic mechanism.

---

# 18. Don't Put Provider Logic in the Controller

Avoid:

```ts
for await (const chunk of openaiStream) {
  res.write(...);
}
```

inside the controller if you're trying to maintain a clean architecture.

Instead:

```text
Controller
   ↓
AITutorService
   ↓
AIProvider
```

The controller should deal with HTTP.

The AI service should deal with tutor behavior.

The provider should deal with the AI vendor.

---

# 19. Better Architecture

```text
HTTP Request
     ↓
AI Controller
     ↓
AITutorService
     ↓
Context Manager
     ↓
AIProvider.streamText()
     ↓
Internal AI Stream
     ↓
Controller / Stream Adapter
     ↓
SSE
     ↓
Browser
```

The controller is responsible for transporting the stream.

# 20. Streaming Request Flow

Let's trace a real request.

Student asks:

> "Explain B-tree indexes."

### Step 1

Browser:

```text
POST /api/v1/ai/conversations/conv_123/messages
```

### Step 2

Backend authenticates the student.

### Step 3

Backend verifies conversation/course access.

### Step 4

User message is persisted.

### Step 5

Context manager builds:

```text
Tutor instructions
+
Course
+
Lesson
+
History
+
Current question
```

### Step 6

AI provider starts streaming.

### Step 7

Backend receives chunks.

### Step 8

Backend sends chunks through SSE.

### Step 9

Browser displays them incrementally.

### Step 10

When generation finishes:

```text
stream complete
```

### Step 11

Persist the final assistant response.

# 21. The Hard Part: Saving the Assistant Message

This is where streaming introduces an important backend problem.

Suppose the chunks are:

```text
"PostgreSQL"
" indexes"
" are"
" data structures..."
```

The database needs the final response:

```text
"PostgreSQL indexes are data structures..."
```

So the server can accumulate chunks:

```ts
let fullResponse = "";

for await (const chunk of stream) {
  fullResponse += chunk.content;

  sendToClient(chunk);
}
```

Then after completion:

```ts
await messageService.createAssistantMessage(
  conversationId,
  fullResponse
);
```

Now:

```text
Stream
  ↓
Client
  +
Accumulator
  ↓
Final response
  ↓
Database
```

---

# 22. Why Accumulate the Response?

Because the database message should normally represent the complete assistant response.

Otherwise you'd end up with:

```text
Message 1: PostgreSQL
Message 2: indexes
Message 3: are
Message 4: useful
```

That's not what we want.

We want:

```text
One assistant message:
"PostgreSQL indexes are useful..."
```

---

# 23. Streaming Architecture

Keep this diagram:

```text
                         LLM
                          │
                     streaming
                          │
                          ↓
                    AI Provider
                          │
                          ↓
                    AIStreamChunk
                          │
             ┌────────────┴────────────┐
             ↓                         ↓
          Browser                  Accumulator
             ↓                         ↓
         Live UI                 Full Response
                                       │
                                       ↓
                                  PostgreSQL
```

This is the heart of AI streaming.

# 24. What If the Connection Closes?

Suppose:

```text
Student
   ↓
AI starts generating
   ↓
10 chunks sent
   ↓
Browser disconnects
```

What happens?

This is an important production problem.

We don't want:

```text
LLM keeps generating
```

forever if the client is gone.

We should detect the request/connection closing and potentially cancel the AI generation.

---

# 25. AbortController

JavaScript provides:

```ts
AbortController
```

which is commonly used to cancel asynchronous operations that support abort signals.

Conceptually:

```text
Browser disconnect
       ↓
AbortController.abort()
       ↓
AI request cancelled
```

For example:

```ts
const controller =
  new AbortController();
```

Then the provider can receive:

```ts
signal: controller.signal
```

if the underlying SDK supports cancellation.

---

# 26. Detecting Client Disconnect

In Node/Express, you can listen for connection-related events.

Conceptually:

```ts
req.on("close", () => {
  controller.abort();
});
```

Then:

```text
Client disconnect
      ↓
req.close
      ↓
AbortController
      ↓
Cancel AI generation
```

This can save:

```text
compute
tokens
money
server resources
```

---

# 27. Cancellation Is More Important Than It Looks

Imagine 100 students.

Each starts a long AI response.

Then they navigate away.

Without cancellation:

```text
100 disconnected clients
       ↓
100 AI generations still running
```

That's wasteful.

With cancellation:

```text
Client leaves
   ↓
Cancel generation
   ↓
Release resources
```

This becomes important as your LMS grows.

---

# 28. What If the AI Provider Doesn't Support Cancellation?

Then your provider abstraction can expose cancellation where possible:

```ts
interface AIStreamOptions {
  signal?: AbortSignal;
}
```

Provider adapters can translate that into the vendor's supported cancellation mechanism.

If a provider doesn't support it, the adapter can do the best possible behavior.

Again:

```text
Application
   ↓
Provider abstraction
   ↓
Provider-specific implementation
```

---

# 29. Streaming Errors

Now consider:

```text
Chunk 1
Chunk 2
Chunk 3
ERROR
```

The response isn't complete.

The frontend might already have:

```text
PostgreSQL indexes are...
```

on the screen.

What should happen?

The server can send an SSE error event:

```text
event: error
data: {"message":"Generation failed"}
```

Then close the stream.

The frontend can show:

```text
Generation interrupted.
Please try again.
```

---

# 30. Don't Pretend a Failed Stream Completed

Avoid:

```text
AI generated 60%
       ↓
Database
       ↓
Mark assistant message completed
```

unless you explicitly support partial messages.

Instead, distinguish:

```text
completed
failed
cancelled
```

This is a good place for a message/generation status.

---

# 31. Message Status

Earlier we discussed that a message could eventually have:

```text
pending
completed
failed
```

Streaming makes this more useful.

For example:

```text
Assistant generation
       ↓
pending
       ↓
streaming
       ↓
completed
```

or:

```text
pending
  ↓
streaming
  ↓
failed
```

You don't necessarily need to expose all these states in your initial schema.

But the concept is important.

---

# 32. Should We Create the Assistant Message Before Streaming?

There are two common approaches.

### Approach A

Create assistant message after successful completion.

```text
LLM
 ↓
Stream
 ↓
Complete
 ↓
Save assistant message
```

Simple.

### Approach B

Create a pending assistant message first.

```text
Create pending message
 ↓
Stream
 ↓
Update message
 ↓
completed
```

More complex but useful if you need:

```text
resume
failure tracking
generation state
```

For our initial LMS, **Approach A is simpler**.

---

# 33. What About Partial Responses?

Suppose:

```text
AI:
"PostgreSQL indexes are data structures..."
```

then network failure occurs.

Should we save:

```text
"PostgreSQL indexes are data structures..."
```

as the assistant message?

Usually not as a normal completed assistant response.

You could store it as:

```text
status = failed
content = partial content
```

if your product needs recovery/debugging.

But don't silently mark partial content as complete.

---

# 34. SSE Event Types

Don't send only raw text if you need more control.

You can define application-level event types:

```text
event: message_start
event: content
event: content
event: content
event: message_complete
```

For errors:

```text
event: error
```

For example:

```text
event: message_start
data: {"messageId":"msg_123"}

event: content
data: {"content":"PostgreSQL"}

event: content
data: {"content":" indexes"}

event: message_complete
data: {"messageId":"msg_123"}
```

This gives the frontend a clear state machine.

---

# 35. Streaming State Machine

Think of the frontend state as:

```text
idle
  ↓
connecting
  ↓
streaming
  ↓
completed
```

or:

```text
streaming
   ↓
error
```

or:

```text
streaming
   ↓
cancelled
```

This is much better than:

```text
isLoading = true
```

for everything.

---

# 36. Frontend Event Handling

A browser can consume SSE using `EventSource` for standard GET-based streams.

However, our AI request often needs a request body:

```json
{
  "message": "Explain indexes"
}
```

For POST-based AI streaming, many applications use:

```text
fetch()
+
ReadableStream
```

instead of `EventSource`.

This is an important distinction.

---

# 37. SSE Does Not Mean You Must Use `EventSource`

The SSE protocol is about the server's event-stream format.

The browser can consume a stream using:

```text
fetch()
+
ReadableStream
```

when you need:

```text
POST
request body
authentication headers
```

This can be a better fit for our chat API.

---

# 38. Browser Streaming With `fetch`

Conceptually:

```ts
const response = await fetch(
  "/api/v1/ai/chat",
  {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      message: "Explain indexes",
    }),
  }
);
```

Then:

```ts
const reader =
  response.body?.getReader();
```

Now the frontend can read chunks.

---

# 39. Browser ReadableStream

Conceptually:

```ts
while (true) {
  const { value, done } =
    await reader.read();

  if (done) break;

  // process chunk
}
```

This gives us incremental network data.

The frontend can update the assistant message as chunks arrive.

---

# 40. Why Not Wait for `response.json()`?

Because:

```ts
await response.json();
```

waits for the complete response body.

That's exactly what we're trying to avoid.

For streaming:

```text
fetch()
   ↓
response.body
   ↓
ReadableStream
   ↓
incremental chunks
```

---

# 41. Chunk Parsing

There is another subtle problem.

Network chunks do not necessarily correspond to application events.

Suppose the server sends:

```text
data: {"content":"Hello"}\n\n
data: {"content":" world"}\n\n
```

The browser's network reader might receive:

```text
data: {"content":"Hello"}\n\ndata: {"con
```

then:

```text
tent":" world"}\n\n
```

So you cannot assume:

```text
one network chunk = one SSE event
```

You need a small parser/buffer.

This is a very important real-world streaming concept.

---

# 42. Stream Buffering

Conceptually:

```text
Network chunks
      ↓
Buffer
      ↓
Find complete SSE event
      ↓
Parse event
      ↓
Update UI
```

For example:

```text
buffer += incomingChunk;

while (buffer contains complete event) {
   extract event;
   parse event;
   update UI;
}
```

This is normal stream processing.

---

# 43. Don't Overcomplicate the First Version

For your first implementation:

```text
POST
 ↓
fetch
 ↓
ReadableStream
 ↓
SSE parser
 ↓
React state
```

is enough.

You don't need WebSockets, Redis Streams, Kafka, or a complicated event bus just to stream an AI answer.

Keep the architecture simple.

# 45. Streaming UX


# 46. Don't Save Every Chunk to PostgreSQL

This is a very common mistake.

Bad:

```text
chunk 1 → UPDATE DB
chunk 2 → UPDATE DB
chunk 3 → UPDATE DB
chunk 4 → UPDATE DB
...
```

Imagine hundreds of chunks.

That's unnecessary database traffic.

Better:

```text
chunks
  ↓
memory accumulator
  ↓
complete response
  ↓
one database write
```

This is much more efficient.

# 48. Streaming and Structured Output

Now we encounter an interesting problem.

In Lesson 7.9 we discussed structured output:

```json
{
  "type": "explanation",
  "title": "...",
  "answer": "..."
}
```

How do we stream JSON safely?

It's more complicated than streaming plain text.

You might receive:

```text
{
  "type":
```

then:

```text
 "explanation"
```

then:

```text
, "title":
```

etc.

The JSON is incomplete until the end.

---

# 49. Don't Assume Every Chunk Is Valid JSON

This is wrong:

```ts
JSON.parse(chunk);
```

because:

```text
chunk 1 = "{"
```

is not valid JSON.

Instead:

```text
Stream
 ↓
Accumulate
 ↓
Complete structured output
 ↓
Parse
 ↓
Validate
```

So structured response streaming often requires a provider-supported structured streaming mechanism or buffering until the object is complete.

---

# 50. Plain Text Streaming vs Structured Streaming

### Plain text

Very straightforward:

```text
chunk
 ↓
display immediately
```

### Structured response

Usually:

```text
chunk
 ↓
accumulate
 ↓
complete structure
 ↓
parse
 ↓
validate
 ↓
render structured UI
```

This distinction is important.

For the initial AI Tutor chat, **plain text streaming** is a good starting point.

For quizzes/flashcards, structured output can be handled separately.

# 51. Streaming and Markdown

Our AI will probably generate Markdown:

```text
## PostgreSQL Indexes

An index is...

- Faster lookup
- Reduced scanning
```

Streaming Markdown creates another UI consideration.

Early chunks may contain:

```text
## Postg
```

then:

```text
## PostgreSQL
```

then:

```text
## PostgreSQL Indexes
```

The frontend Markdown renderer needs to handle partial content gracefully.

Most modern UI implementations can progressively render the accumulated text.

---

# 52. Streaming and Code Blocks

This is even more interesting.

The model might generate:

````text
```typescript
const user = ...
```
````

During streaming, the frontend might temporarily receive:

````text
```typescript
const user =
````

The code block hasn't closed yet.

So the renderer must tolerate incomplete Markdown.

This is another reason to keep the streaming UI robust.

# 53. Streaming Errors at Different Layers

There are several places a failure can occur:

```text
Client
 ↓
HTTP
 ↓
Backend
 ↓
Context Manager
 ↓
AI Provider
 ↓
LLM
```

For example:

### Authorization failure

```text
403
```

No stream should start.

### Context failure

```text
500
```

No stream or an error event.

### Provider failure after streaming starts

```text
SSE error event
```

### Client disconnect

```text
Abort generation
```

Understanding these different failure points is important.

---

# 54. HTTP Errors Before Streaming

Before you send the first stream event, you can still use normal HTTP status codes.

For example:

```text
401 Unauthorized
403 Forbidden
404 Not Found
429 Rate Limited
500 Internal Server Error
```

Once the streaming response has started, things are different.

You may need to communicate errors as stream events because the HTTP response is already established.

---

# 55. This Creates an Important Boundary

Before streaming:


# 58. Streaming and Reverse Proxies

Your application might eventually look like:

```text

   ↓

   ↓

   ↓

   ↓
```

If the proxy buffers the entire response, your carefully implemented streaming endpoint might appear to the browser as:


instead of real-time chunks.

So streaming must be tested through the **actual production network path**, not only localhost.

# 65. Example Server Logic

Simplified:

```ts
async function streamTutor(
  input: TutorInput,
  res: Response,
  req: Request
) {
  const abortController =
    new AbortController();

  req.on("close", () => {
    abortController.abort();
  });

  let fullResponse = "";

  const stream =
    tutorService.stream(
      input,
      {
        signal: abortController.signal,
      }
    );

  for await (const event of stream) {
    if (event.type === "content") {
      fullResponse += event.content;

      res.write(
        `event: content\n` +
        `data: ${JSON.stringify(event)}\n\n`
      );
    }
  }

  await messageService.createAssistantMessage(
    input.conversationId,
    fullResponse
  );

  res.write(
    `event: complete\n` +
    `data: {}\n\n`
  );

  res.end();
}
```

This is simplified, but notice the important pieces:

```text
AbortController
+
stream
+
accumulator
+
SSE
+
database persistence
```

# 70. Idempotency

Imagine the frontend retries the request because of a network problem.

You could accidentally generate:

```text

 ↓

```

Duplicate generation.

For important production workflows, **idempotency** can help.

For example:

```text

```

We don't need full idempotency implementation today, but remember the problem.

# 71. Streaming + Retry

If:

```text

```

```text

```

the user may receive two different answers.

So retries for streaming requests need more careful handling than ordinary API requests.

Possible strategies include:

```text

idempotency

```

# 80. Common Mistakes

### ❌ Mistake 1 — Sending the complete response only

Then you aren't really streaming.

### ❌ Mistake 2 — Saving every chunk to PostgreSQL

Creates unnecessary database writes.

### ❌ Mistake 3 — Ignoring client disconnects

Can waste AI generation and money.

### ❌ Mistake 4 — Assuming network chunks equal SSE events

They don't necessarily.

### ❌ Mistake 5 — Using WebSockets automatically

Use the simplest technology that fits the requirement.

### ❌ Mistake 6 — Putting provider-specific stream objects throughout your application

Normalize them behind your provider abstraction.

### ❌ Mistake 7 — Treating a partial response as completed

Track stream completion and failure properly.

### ❌ Mistake 8 — Forgetting production proxies

Local streaming working doesn't guarantee production streaming.

# 🧠 Interview Question

### How would you implement streaming AI responses in a Node.js backend?

A strong answer:

> "I would expose a streaming method from the AI provider abstraction that returns an async iterable of normalized chunks. The service would build and authorize the AI context, then the HTTP layer would forward those chunks to the client using an SSE-style event stream. At the same time, the backend would accumulate the generated text and persist the complete assistant message after successful completion. I'd also use an AbortController to cancel generation when the client disconnects and handle errors that occur after streaming has started."

That's a very solid backend answer.
