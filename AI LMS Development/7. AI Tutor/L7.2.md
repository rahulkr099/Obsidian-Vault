# Lesson 7.2 — AI Provider Abstraction

In Lesson 7.1, we established an important idea:

> **The LLM provider should be an implementation detail, not something your entire application depends on.**

Today we'll turn that idea into a proper TypeScript architecture.

Our target is:

```text
AI Controller
      ↓
AI Service
      ↓
AI Provider Interface
      ↓
┌──────────────┬──────────────┐
│              │              │
OpenAI      Anthropic      Another
Provider     Provider       Provider
```

This is a very useful backend design pattern because it keeps your business logic independent from a particular AI vendor.

---

# 1. The Problem With Direct SDK Usage

Imagine you write this inside your service:

```ts
import OpenAI from "openai";

const openai = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
});

const response = await openai.chat.completions.create({
  model: "some-model",
  messages,
});
```

It works.

But now imagine your `AIService` becomes:

```text
AIService
 ├── OpenAI SDK
 ├── OpenAI models
 ├── OpenAI error handling
 ├── OpenAI token format
 └── OpenAI response format
```

Now your service is tightly coupled to OpenAI.

If you later want another provider:

```text
AIService
   ↓
????
```

you have to modify your business logic.

That's what we want to avoid.

---

# 2. What Does "Abstraction" Mean?

Abstraction means:

> **Expose what the application needs, while hiding implementation details.**

Our application doesn't really care whether the provider is OpenAI, Anthropic, or something else.

It cares about:

```text
"Generate an AI response."
```

So we define that capability.

Conceptually:

```ts
interface AIProvider {
  generateResponse(...): Promise<...>;
}
```

Now the application depends on:

```text
AIProvider
```

instead of:

```text
OpenAI
```

---

# 3. The Dependency Direction

Our architecture becomes:

```text
AIController
     ↓
AIService
     ↓
AIProvider
     ↓
Concrete Provider
```

For example:

```text
AIService
    ↓
AIProvider
    ↓
OpenAIProvider
```

The important part is that:

```text
AIService → AIProvider
```

not:

```text
AIService → OpenAI SDK
```

---

# 4. TypeScript Interface

Let's create a simple abstraction.

```ts
export interface AIProvider {
  generateResponse(
    request: AIRequest
  ): Promise<AIResponse>;
}
```

Then define our types:

```ts
export interface AIRequest {
  messages: AIMessage[];
  model?: string;
}

export interface AIResponse {
  content: string;
}
```

And:

```ts
export interface AIMessage {
  role: "system" | "user" | "assistant";
  content: string;
}
```

Now our service knows only about these types.

It doesn't know anything about a particular provider SDK.

---

# 5. Why Interfaces Are Useful Here

Suppose we create:

```ts
class OpenAIProvider implements AIProvider {
  async generateResponse(
    request: AIRequest
  ): Promise<AIResponse> {
    // OpenAI implementation
  }
}
```

We could also create:

```ts
class AnthropicProvider implements AIProvider {
  async generateResponse(
    request: AIRequest
  ): Promise<AIResponse> {
    // Anthropic implementation
  }
}
```

Both satisfy:

```ts
AIProvider
```

Therefore:

```text
AIService
    ↓
AIProvider
```

doesn't care which implementation it receives.

---

# 6. Polymorphism

This is also a practical example of **polymorphism**.

The service expects:

```ts
AIProvider
```

but it can receive:

```text
OpenAIProvider
AnthropicProvider
AnotherProvider
```

as long as each one implements the required contract.

Think:

```text
AIProvider
    │
    ├── OpenAIProvider
    ├── AnthropicProvider
    └── MockAIProvider
```

This is especially useful for testing.

# 8. The Provider Contract

Let's make the contract a little more useful.

```ts
export interface AIProvider {
  generateText(
    request: GenerateTextRequest
  ): Promise<GenerateTextResponse>;
}
```

Types:

```ts
export interface GenerateTextRequest {
  messages: AIMessage[];
  model: string;
  temperature?: number;
}
```

Response:

```ts
export interface GenerateTextResponse {
  content: string;
  usage?: {
    inputTokens?: number;
    outputTokens?: number;
    totalTokens?: number;
  };
}
```

Notice something important.

We aren't returning the provider's raw response.

We're returning **our own application format**.

---

# 9. Why Not Return the Raw Provider Response?

Suppose Provider A returns:

```json
{
  "choices": [
    {
      "message": {
        "content": "Hello"
      }
    }
  ]
}
```

Provider B might return:

```json
{
  "content": [
    {
      "text": "Hello"
    }
  ]
}
```

If your service consumes those raw structures:

```text
AIService
   ↓
Provider-specific response
```

your service becomes provider-dependent.

Instead:

```text
Provider A
     ↓
normalize
     ↓
AIResponse
```

and:

```text
Provider B
     ↓
normalize
     ↓
AIResponse
```

Now:

```text
AIService
     ↓
AIResponse
```

The service sees one consistent format.

---

# 10. Provider Adapter

The concrete provider is essentially an **adapter**.

For example:

```text
OpenAI API
     ↓
OpenAIProvider
     ↓
AIResponse
```

The provider translates between:

```text
External API format
```

and:

```text
Our internal application format
```

This is a very valuable architecture pattern.

---

# 11. Example OpenAI Provider

Conceptually:

```ts
class OpenAIProvider implements AIProvider {
  constructor(
    private readonly client: OpenAI
  ) {}

  async generateText(
    request: GenerateTextRequest
  ): Promise<GenerateTextResponse> {
    const response = await this.client.chat.completions.create({
      model: request.model,
      messages: request.messages,
      temperature: request.temperature,
    });

    return {
      content: response.choices[0]?.message?.content ?? "",
      usage: {
        inputTokens: response.usage?.prompt_tokens,
        outputTokens: response.usage?.completion_tokens,
        totalTokens: response.usage?.total_tokens,
      },
    };
  }
}
```

The exact SDK/API we'll use can change.

The important architectural concept is:

```text
External API
      ↓
Provider Adapter
      ↓
Our internal interface
```

---

# 12. AI Service

Now our service becomes much cleaner.

```ts
class AIService {
  constructor(
    private readonly provider: AIProvider
  ) {}

  async generateResponse(
    request: AIRequest
  ) {
    return this.provider.generateText({
      messages: request.messages,
      model: "some-model",
    });
  }
}
```

Notice what is missing.

There is no:

```ts
import OpenAI from "openai";
```

inside the service.

That's exactly what we want.

---

# 13. Dependency Injection

How does `AIService` get the provider?

Through **dependency injection**.

Instead of:

```ts
class AIService {
  private provider = new OpenAIProvider();
}
```

we do:

```ts
class AIService {
  constructor(
    private readonly provider: AIProvider
  ) {}
}
```

Then:

```ts
const provider = new OpenAIProvider(client);

const aiService = new AIService(provider);
```

The service doesn't create its dependency.

The dependency is given to it.

---

# 14. Why This Matters

Consider testing.

Without dependency injection:

```text
AIService
   ↓
Real AI API
```

Every test could potentially call the real provider.

That's bad because:

```text
Slow
Expensive
Unreliable
Hard to reproduce
```

With dependency injection:

```text
AIService
   ↓
MockAIProvider
```

Now your tests can run without calling an external AI service.

---

# 15. Mock Provider

We can create:

```ts
class MockAIProvider implements AIProvider {
  async generateText(): Promise<GenerateTextResponse> {
    return {
      content: "Mock AI response",
    };
  }
}
```

Then:

```ts
const provider = new MockAIProvider();

const service = new AIService(provider);
```

Your service behaves as though an AI provider exists.

This is excellent for automated testing.

---

# 16. Provider Selection

Eventually we might have:

```text
AI_PROVIDER=openai
```

in environment configuration.

Then our application can choose:

```text
Environment
     ↓
Provider Factory
     ↓
OpenAIProvider
```

or:

```text
AI_PROVIDER=anthropic
     ↓
Provider Factory
     ↓
AnthropicProvider
```

Conceptually:

```ts
function createAIProvider(): AIProvider {
  switch (config.ai.provider) {
    case "openai":
      return new OpenAIProvider(...);

    case "anthropic":
      return new AnthropicProvider(...);

    default:
      throw new Error("Unsupported AI provider");
  }
}
```

The rest of the application doesn't change.

---

# 17. Provider Factory

We can isolate this decision:

```text
                Provider Factory
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       OpenAI       Anthropic      Mock
```

Then:

```text
Application Startup
        ↓
Provider Factory
        ↓
AIProvider
        ↓
AIService
```

This keeps provider selection away from business logic.

---

# 18. Don't Over-Abstraction

There is an important engineering lesson here.

Abstraction is useful, but **too much abstraction is also bad**.

Don't build:

```text
AIProviderFactoryManager
AIProviderResolver
AIProviderStrategyFactory
AIProviderAdapterFactory
AIProviderRegistry
AIProviderOrchestrator
```

just because you can.

😂

For our project, initially we need something simple:

```text
AIProvider
   ↓
OpenAIProvider
```

Later:

```text
AIProvider
   ├── OpenAIProvider
   ├── AnthropicProvider
   └── MockAIProvider
```

Add complexity only when it provides real value.

---

# 19. What Belongs in AIProvider?

Good provider-level responsibilities:

```text
Call external AI API
Convert request format
Convert response format
Normalize provider errors
Extract usage information
Handle provider-specific details
```

Bad provider responsibilities:

```text
Check whether student is enrolled
Load course from database
Check lesson permissions
Build LMS business logic
Save conversations
Apply student quotas
```

Those belong elsewhere.

---

# 20. AI Service Responsibilities

The AI service can eventually coordinate:

```text
Validate business rules
       ↓
Load conversation
       ↓
Check course access
       ↓
Build context
       ↓
Check usage
       ↓
Call AIProvider
       ↓
Save response
       ↓
Record usage
```

So:

```text
AIService
```

is responsible for **application/business logic**.

While:

```text
AIProvider
```

is responsible for **communication with the external AI system**.

This separation is critical.

# 23. Internal vs External Types

One subtle but important idea:

**Don't allow external provider types to leak into your application.**

Bad:

```ts
import type {
  OpenAIResponse
} from "some-sdk";
```

throughout your application.

Instead:

```text
Provider SDK
     ↓
OpenAIProvider
     ↓
AIResponse
     ↓
Application
```

Your application owns:

```ts
AIMessage
AIRequest
AIResponse
```

not the external SDK.

This gives you much more control.

---

# 24. Provider Errors

Suppose an external provider returns:

```text
429 Too Many Requests
```

Don't let that provider-specific error travel through the whole application.

Instead:

```text
OpenAI Error
    ↓
OpenAIProvider
    ↓
AIProviderRateLimitError
    ↓
AIService
    ↓
Application Error
    ↓
Controller
```

Then your API can return a consistent response.

For example:

```json
{
  "success": false,
  "error": {
    "code": "AI_RATE_LIMITED",
    "message": "AI service is temporarily busy."
  }
}
```

We'll develop this much further in **Lesson 7.11**.

# 25. A Very Important Rule

Remember this:

> **The provider knows about the AI vendor. The service knows about your application.**

For example:

### Provider

```text
OpenAI SDK
Model name
Provider API
Provider errors
Provider tokens
```

### Service

```text
Student
Course
Lesson
Conversation
Permissions
Usage limits
Business rules
```

This one distinction will prevent a lot of architectural problems.

---

# 26. Where Configuration Lives

Don't scatter:

```ts
process.env.OPENAI_API_KEY
```

through your application.

Instead, your configuration system should handle it.

Conceptually:

```text
Environment
     ↓
Config
     ↓
Provider Factory
     ↓
Provider
```

For example:

```ts
const config = {
  ai: {
    provider: "openai",
    apiKey: "...",
  },
};
```

Then:

```text
Provider
```

receives configuration through its constructor.

This makes testing and configuration management cleaner.

---

# 27. Security Connection

Never send the provider API key to the frontend.

Bad:

```text
Next.js
   ↓
OPENAI_API_KEY
```

Absolutely not.

Correct:

```text
Next.js
   ↓
Backend
   ↓
AI Provider
   ↓
API Key
```

The key belongs on the server.

This will become even more important in **Phase 14 — Security Engineering**.

# 28. Practical TypeScript Design

A simple version could look like this:

```ts
export type AIMessageRole =
  | "system"
  | "user"
  | "assistant";

export interface AIMessage {
  role: AIMessageRole;
  content: string;
}

export interface GenerateTextRequest {
  messages: AIMessage[];
  model: string;
  temperature?: number;
}

export interface GenerateTextResponse {
  content: string;
  usage?: {
    inputTokens?: number;
    outputTokens?: number;
    totalTokens?: number;
  };
}

export interface AIProvider {
  generateText(
    request: GenerateTextRequest
  ): Promise<GenerateTextResponse>;
}
```

Then:

```ts
export class AIService {
  constructor(
    private readonly provider: AIProvider
  ) {}

  async generateResponse(
    request: GenerateTextRequest
  ) {
    return this.provider.generateText(request);
  }
}
```

This is intentionally simple.

We're establishing the architecture first.

# 30. What You Learned

You should now understand these concepts:

|Concept|Meaning|
|---|---|
|AI Provider|External service used to generate AI output|
|Provider Abstraction|Hide provider-specific implementation|
|Interface|Contract that providers must follow|
|Adapter|Converts external API format into internal format|
|Dependency Injection|Give dependencies to a class instead of creating them inside|
|Provider Factory|Selects the provider implementation|
|Mock Provider|Fake provider used for testing|
|AI Service|Contains application/business logic|
|Provider|Handles external AI communication|

---

# 🧠 Interview-Level Understanding

If an interviewer asks:

> **"Why would you abstract an AI provider?"**

A good answer is:

> "I don't want my application business logic tightly coupled to a specific AI vendor. I define an internal provider interface and implement adapters for each provider. The AI service depends on that interface, which makes provider switching, testing, error normalization, and configuration easier."

That's a much stronger answer than:

> "Because interfaces are good."

# 🔥 Architecture Challenge

Before moving to **7.3**, try to design this yourself:

```text
AIProvider
   ↓
OpenAIProvider
   ↓
AIService
   ↓
AIController
```

Think about these questions:

### 1. Who should create `OpenAIProvider`?

### 2. Should `AIService` import the OpenAI SDK?

### 3. What should happen if the provider returns a completely different response structure?

### 4. How would you test `AIService` without calling a real AI API?

### 5. Where should `OPENAI_API_KEY` live?

### 6. What should happen if you replace OpenAI with another provider?

If your answers are roughly:

```text
1. Composition root / factory
2. No
3. Provider adapter normalizes it
4. Inject MockAIProvider
5. Backend environment/configuration
6. Replace provider implementation, not business logic
```

then you've understood the core of **Lesson 7.2**. 🚀
