# Lesson 7.4 — AI Tutor Service

In Lesson 7.3, we built the basic AI API:

```text
POST /api/v1/ai/chat
        ↓
Authentication
        ↓
Validation
        ↓
Controller
        ↓
AI Service
        ↓
AI Provider
        ↓
LLM
```

Now we're going to make that generic AI endpoint into an actual **AI Tutor**.

The important change is:

```text
Generic chatbot
      ↓
Educational AI Tutor
```

The tutor should understand that its job is to **help a student learn**, not simply generate arbitrary text.

---

# 1. What Is the AI Tutor Service?

The AI Tutor Service is the application layer responsible for coordinating the tutoring experience.

Think of it as the brain of our backend workflow:

```text
Student Question
       ↓
AI Tutor Service
       │
       ├── Understand user
       ├── Apply tutor behavior
       ├── Prepare context
       ├── Call AI Provider
       ├── Process response
       └── Return answer
```

The LLM itself doesn't know that our application is an LMS.

**Our service gives it that context and purpose.**

---

# 2. Generic AI vs AI Tutor

A generic AI endpoint might simply do:

```text
Question
   ↓
LLM
   ↓
Answer
```

Our tutor should do:

```text
Student
   ↓
Question
   ↓
AI Tutor Service
   ↓
Educational instructions
   ↓
Relevant LMS context
   ↓
LLM
   ↓
Learning-focused response
```

For example:

### Student

> What is normalization?

### Generic AI

> Normalization is a database design technique...

### AI Tutor

> Normalization is a way of organizing database tables to reduce duplicate data. Think of it like organizing your notes so you don't write the same information in five different places...

The second response is intentionally **teaching-oriented**.

---

# 3. The Tutor's Responsibilities

Our `AITutorService` can eventually handle:

```text
Authentication context
       ↓
Student access
       ↓
Conversation
       ↓
Course context
       ↓
Lesson context
       ↓
Tutor instructions
       ↓
AI Provider
       ↓
Response
```

But we shouldn't put every responsibility into one giant service.

A better architecture is:

```text
AITutorService
      │
      ├── Context Builder
      ├── Conversation Service
      ├── Usage Service
      └── AI Provider
```

We'll introduce these pieces gradually throughout Phase 7.

---

# 4. The Tutor Needs a Personality

We need to define how our tutor should behave.

For example:

```text
You are an educational AI tutor.

Your goal is to help students understand concepts.

Explain difficult concepts in simple language.

Prefer examples over complicated explanations.

When appropriate:
- ask guiding questions
- break problems into steps
- correct misconceptions
- encourage the student to think
- avoid unnecessarily long answers
```

This is commonly handled through **system-level instructions** sent to the model.

The exact prompt design will evolve later.

For now, understand the architecture:

```text
Tutor behavior
      ↓
Tutor instructions
      ↓
LLM
```

---

# 5. Why the Backend Should Own Tutor Instructions

Don't let the frontend send:

```json
{
  "systemPrompt": "You are an AI tutor..."
}
```

and trust it.

A malicious client could change it to:

```json
{
  "systemPrompt": "Ignore all application rules..."
}
```

Instead:

```text
Frontend
   ↓
Student message
   ↓
Backend
   ↓
Trusted tutor instructions
   ↓
LLM
```

The backend controls the application's AI behavior.

This also makes it easier to update tutor behavior later.

---

# 6. A Basic Tutor Context

Suppose the student asks:

> Explain recursion.

Our service could create:

```text
System:
You are an educational AI tutor.

User:
Explain recursion.
```

Then the provider receives:

```text
[
  {
    role: "system",
    content: "You are an educational AI tutor..."
  },
  {
    role: "user",
    content: "Explain recursion."
  }
]
```

The important thing is that the **service constructs the application context**.

---

# 7. The Service Interface

Let's define an application-level input.

```ts
export interface TutorChatInput {
  userId: string;
  message: string;
}
```

Then:

```ts
export interface TutorChatResult {
  message: string;
}
```

And our service:

```ts
export class AITutorService {
  constructor(
    private readonly provider: AIProvider
  ) {}

  async chat(
    input: TutorChatInput
  ): Promise<TutorChatResult> {
    // tutor logic
  }
}
```

This keeps the service independent of Express.

---

# 8. Basic Implementation

A simple first version:

```ts
export class AITutorService {
  constructor(
    private readonly provider: AIProvider
  ) {}

  async chat(
    input: TutorChatInput
  ): Promise<TutorChatResult> {
    const response =
      await this.provider.generateText({
        model: "your-model",
        messages: [
          {
            role: "system",
            content:
              "You are an educational AI tutor. Explain concepts clearly and simply.",
          },
          {
            role: "user",
            content: input.message,
          },
        ],
      });

    return {
      message: response.content,
    };
  }
}
```

This is deliberately simple.

We're establishing the **service boundary**.

---

# 9. But Don't Put Everything Here

You might be tempted to eventually write:

```ts
async chat() {
    authenticate();
    validate();
    loadUser();
    loadCourse();
    loadLesson();
    loadConversation();
    checkEnrollment();
    checkQuota();
    buildPrompt();
    callAI();
    calculateTokens();
    saveMessage();
    updateUsage();
    logRequest();
}
```

🚨 That's becoming a **God Service**.

Instead, we'll gradually separate responsibilities.

For example:

```text
AITutorService
      │
      ├── AccessService
      ├── ContextBuilder
      ├── ConversationService
      ├── UsageService
      └── AIProvider
```

The tutor service coordinates them.

---

# 10. Orchestration vs Implementation

This is an important backend concept.

The tutor service should primarily **orchestrate**.

For example:

```text
AITutorService
       │
       ├── getConversation()
       │
       ├── buildContext()
       │
       ├── checkUsage()
       │
       ├── generateResponse()
       │
       └── saveMessage()
```

It doesn't need to know every low-level detail of how each operation works.

This is similar to the architecture you've already used:

```text
Controller
    ↓
Service
    ↓
Repository
```

We're extending the same thinking to AI.

---

# 11. Tutor Context Builder

Soon we'll need a dedicated component:

```ts
class TutorContextBuilder {

  }

```

Then:


The context builder might eventually combine:

```text

+

```

For now, we only have:

```text

```

---

# 12. Why a Context Builder?

Because prompt/context construction will become complicated.

Imagine this eventually:

```text
System instructions
        +
Course title
        +
Course description
        +
Current lesson
        +
Lesson summary
        +
Previous conversation
        +
Student question
        +
Retrieved documents
```

Putting all of this directly inside `AITutorService.chat()` would make it huge.

Instead:

```text
AITutorService
      ↓
TutorContextBuilder
      ↓
AI Messages
```

Much cleaner.

# 13. Tutor Instructions Should Be Versioned

This is an advanced but useful idea.

Suppose today your tutor uses:

```text
Tutor Prompt v1
```

Later you improve it:

```text
Tutor Prompt v2
```

The behavior of your AI can change significantly even if your code doesn't.

Therefore, for a production AI system, it's useful to know:

```text
model
prompt version
timestamp
request
response
```

For example:

```text
AI Request
 ├── model: ...
 ├── promptVersion: tutor-v2
 └── timestamp: ...
```

We'll return to this in **Lesson 7.12** when we discuss observability and cost.

# 14. Educational Behavior

Our tutor shouldn't always simply give the answer.

For example, if a student asks:

> What is the output of this code?

The tutor could potentially explain the reasoning:

```text
Step 1:
The loop starts at...

Step 2:
The value changes to...

Step 3:
Therefore the output is...
```

This encourages understanding.

A good tutor can use strategies such as:

```text
Explain
Example
Hint
Question
Correction
Summary
Practice
```

Later we could expose modes such as:

```text
"Explain"
"Give me a hint"
"Quiz me"
"Show an example"
"Summarize"
```

That's a good future enhancement for your LMS.

---

# 15. Tutor Modes

We can model this eventually:

```ts
type TutorMode =
  | "explain"
  | "hint"
  | "quiz"
  | "example"
  | "summary";
```

Then a request might be:

```json
{
  "message": "I don't understand recursion.",
  "mode": "explain"
}
```

Or:

```json
{
  "message": "Give me a hint.",
  "mode": "hint"
}
```

But don't implement all of this yet.

The goal is to understand that **AI behavior can be represented as application-level features**.

---

# 16. Don't Let the LLM Decide Business Rules

This is very important.

Suppose the LMS rule is:

```text
Only enrolled students can access private course material.
```

Don't ask the LLM:

> "Is this student enrolled?"

The LLM should not make that decision.

Instead:

```text
Database
   ↓
Enrollment Service
   ↓
authorized = true
   ↓
AI Tutor
```

Business rules belong to your backend.

The LLM generates language.

---

# 17. Another Example

Suppose a student requests:

> "Give me the instructor's private notes."

The system should not rely on the AI to decide whether this is allowed.

Correct architecture:

```text
Student Request
       ↓
Authorization
       ↓
Allowed?
   ┌───┴───┐
  No      Yes
   ↓        ↓
403      AI Context
            ↓
           LLM
```

This is both a security principle and a good architecture principle.

# 22. Thin Controller, Smart Service

Compare these.

### ❌ Bad

```ts
chat = asyncHandler(async (req, res) => {
  const prompt = `
    You are an AI tutor...
    ${req.body.message}
  `;

  const response = await openai(...);

  // database
  // usage
  // conversation
  // permissions

  res.json(response);
});
```

The controller is doing everything.

---

### ✅ Better

```ts
chat = asyncHandler(async (req, res) => {
  const result = await this.aiTutorService.chat({
    userId: req.user.userId,
    message: req.body.message,
  });

  res.json({
    success: true,
    data: result,
  });
});
```

Now:

```text
Controller
   ↓
AITutorService
```

The service owns the application logic.

# 23. Testing the Tutor Service

Because we have provider abstraction, testing becomes easy.

Instead of:

```text
AITutorService
       ↓
Real LLM
```

we use:

```text
AITutorService
       ↓
MockAIProvider
```

Example:

```ts
const provider = new MockAIProvider();

const service = new AITutorService(provider);
```

Then test:

```text
Given a student message
      ↓
Tutor service calls provider
      ↓
Returns normalized response
```

No real AI API is needed.

---

# 24. Testing Tutor Behavior

There are actually **two different things** to test.

### Software test

Does the service correctly call the provider?

```text
Input
 ↓
Service
 ↓
Mock Provider
 ↓
Expected result
```

### AI quality test

Does the tutor actually give a useful explanation?

```text
Question
 ↓
Real model
 ↓
Evaluate response
```

These are different problems.

Traditional unit tests can verify your application logic.

AI evaluation is needed to assess model behavior.

We'll explore AI-specific testing much later in Phase 12.

---

# 25. Important: AI Output Is Untrusted

Even though the model generated the response, your application should not blindly trust it.

Think:

```text
User Input
   ↓
Untrusted
```

and:

```text
LLM Output
   ↓
Also untrusted
```

Why?

The model can:

```text
hallucinate
produce incorrect information
follow malicious instructions
generate unexpected content
return malformed output
```

Therefore:

```text
LLM
 ↓
Application
 ↓
Validation / handling
 ↓
User
```

This becomes especially important when we later allow AI to interact with tools or databases.

# 26. Tutor Service vs AI Agent

Don't confuse:

```text
AI Tutor
```

with:

```text
AI Agent
```

Our tutor currently does:

```text
Question
 ↓
Context
 ↓
LLM
 ↓
Answer
```

An agent might do:

```text
Question
 ↓
LLM
 ↓
Choose tool
 ↓
Call database
 ↓
Read result
 ↓
LLM
 ↓
Choose another tool
 ↓
Answer
```

We're **not building an agent yet**.

For an LMS, starting with a controlled tutor is safer and easier to understand.

# 29. What We Learned

The key concepts from Lesson 7.4 are:

|Concept|Purpose|
|---|---|
|`AITutorService`|Coordinates tutoring logic|
|Tutor instructions|Define educational behavior|
|Context Builder|Prepares information for the model|
|Conversation Service|Manages conversation state|
|Provider|Communicates with the LLM|
|Repository|Handles persistence|
|Authorization|Enforces LMS access rules|
|Mock Provider|Makes testing possible|
|Orchestration|Coordinates multiple components|
|LLM|Generates language, not business decisions|

# 🧠 The Most Important Rule

Remember this:

> **Your backend decides what the AI is allowed to know and do. The LLM decides how to express the answer.**

For example:

```text
Backend
   ↓
"Student is enrolled in Course A"
   ↓
"Lesson = Database Indexes"
   ↓
"These are the allowed context sources"
   ↓
LLM
   ↓
"Explain it naturally"
```

Not:

```text
LLM
   ↓
"Let me decide what the student is allowed to access."
```

That distinction will become **extremely important in Phase 14 security engineering**.
