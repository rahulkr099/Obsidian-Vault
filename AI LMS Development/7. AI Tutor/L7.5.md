# Lesson 7.5 — Conversation Management

In the previous lessons, we built the foundation:

```text
7.1  AI Architecture
      ↓
7.2  AI Provider Abstraction
      ↓
7.3  AI Chat API
      ↓
7.4  AI Tutor Service
```

Until now, our AI tutor is basically **one question → one answer**.

Now we're going to make it a real conversational system:

```text
Student
   ↓
Conversation
   ├── User message
   ├── AI response
   ├── User message
   ├── AI response
   └── ...
```

This lesson focuses on the **conversation itself**—its identity, ownership, lifecycle, and authorization.

Message persistence and detailed message history will come in **Lesson 7.6**.

---

# 1. What Is a Conversation?

A conversation is a container that groups related AI interactions.

For example:

```text
Conversation
ID: conv_123

Student: Rahul
Course: PostgreSQL
Lesson: Indexes

Messages:
    1. What is an index?
    2. An index is...
    3. When should I use one?
    4. You should use...
```

The important distinction is:

```text
Conversation ≠ Message
```

A conversation is the **parent**.

Messages are the **children**.

```text
Conversation
      │
      ├── Message
      ├── Message
      ├── Message
      └── Message
```

---

# 2. Why Do We Need a Conversation?

Without conversations, every request could look like:

```text
POST /ai/chat

{
  "message": "Explain indexes"
}
```

Then:

```text
POST /ai/chat

{
  "message": "Why do we need one?"
}
```

The second message is ambiguous.

What does **"one"** refer to?

The application needs a way to say:

```text
These messages belong to the same discussion.
```

That's what a conversation ID provides.

---

# 3. Conversation ID

We can give every conversation a unique identifier:

```text
conv_123
```

Then our API can look like:

```http
POST /api/v1/ai/conversations/conv_123/messages
```

Now the backend knows:

```text
User
 ↓
Conversation conv_123
 ↓
New message
```

This is much better than trying to infer which conversation the student means.

---

# 4. Conversation as a Database Entity

Conceptually, our database could have:

```text
User
 │
 └── Conversation
       │
       ├── Message
       ├── Message
       └── Message
```

A conversation might contain:

```text
id
userId
courseId
lessonId
title
createdAt
updatedAt
```

Don't worry about the exact Prisma schema yet.

The important idea is the **relationship**.

---

# 5. Why `userId` Matters

Every conversation should belong to a user.

For example:

```text
User A
 ├── Conversation 1
 └── Conversation 2

User B
 ├── Conversation 3
 └── Conversation 4
```

This lets us enforce:

```text
User A → can access Conversation 1
User A → can access Conversation 2

User B → cannot access Conversation 1
User B → cannot access Conversation 2
```

This is an authorization boundary.

---

# 6. The Dangerous Version

Imagine our API is:

```http
GET /api/v1/ai/conversations/123
```

and the backend simply does:

```ts
const conversation =
  await conversationRepository.findById("123");
```

That's dangerous.

Suppose:

```text
Conversation 123 → belongs to Rahul
```

and another user changes the URL:

```text
/conversations/123
```

If we don't check ownership, they might see Rahul's conversation.

This is a classic **Broken Access Control / IDOR/BOLA-style problem**.

We'll revisit this heavily in Phase 14.

---

# 7. Correct Ownership Check

Instead of:

```ts
findById(conversationId)
```

we conceptually want:

```ts
findByIdAndUserId(
  conversationId,
  userId
)
```

So:

```text
conversationId = conv_123
userId = user_456
```

Database query:

```text
Find conversation
WHERE
    id = conv_123
AND
    userId = user_456
```

If it doesn't belong to that user:

```text
Not Found / Forbidden
```

depending on your API design.

---

# 8. Why `findByIdAndUserId` Is Better

Suppose you do this:

```ts
const conversation =
  await repository.findById(id);

if (conversation.userId !== userId) {
  throw new ForbiddenError();
}
```

This can work.

But a repository method such as:

```ts
findByIdAndUserId(id, userId)
```

can make the ownership condition part of the data access operation itself.

Conceptually:

```text
Request
  ↓
userId + conversationId
  ↓
Repository
  ↓
Only user's conversation
```

This makes accidental data exposure harder.

# 9. Conversation Lifecycle

A conversation has a lifecycle.

Think:

```text
Create
  ↓
Active
  ↓
Updated
  ↓
Archived
  ↓
Deleted
```

Not every application needs all of these states.

For our LMS, we can initially keep it simple:

```text
Created
   ↓
Active
   ↓
Deleted
```

Later we can add:

```text
Archived
```

if it becomes useful.

# 10. Creating a Conversation

A student might click:

> **New AI Tutor Chat**

The frontend sends:

```http

```

Potential response:

```json
{
  "success": true,
  "data": {
    "id": "conv_123",
    "title": "New conversation"
  }

```

Now the frontend knows:

```text
conversationId = conv_123
```

Future messages use that ID.

# 11. Why Create the Conversation Separately?

We could also create the conversation automatically when the first message arrives.

For example:

```http
POST /conversations/auto/messages
```

Backend:

```text
No conversation?
   ↓
Create one
   ↓
Save message
```

This is also valid.

There are two common approaches.

### Explicit creation

```text
Create conversation
       ↓
Send messages
```

### Lazy creation

```text
Send first message
       ↓
Create conversation automatically
```

For learning purposes, understanding explicit creation is useful because it makes the lifecycle very clear.

# 14. Why `courseId` and `lessonId`?

This is where our LMS becomes interesting.

A conversation doesn't have to be generic.

It can belong to:

```text
Course
```

and optionally:

```text
Lesson
```

For example:

```text
Conversation
   │
   ├── userId
   ├── courseId
   └── lessonId
```

So we can know:

```text
Rahul
   ↓
PostgreSQL Course
   ↓
Indexes Lesson
   ↓
AI Conversation
```

This becomes very useful for the course-aware tutor in **Lesson 7.8**.

We could support:

### General AI conversation

```text

 ↓

```

### Course conversation


### Lesson conversation


---

# 16. Don't Duplicate Course Information

Suppose the conversation has:

```text
courseId
lessonId
```

but the message also stores:

```text
courseId
lessonId
```

Now you have duplicate information.

That creates possible inconsistencies:

```text
Conversation:
courseId = course_A

Message:
courseId = course_B
```

Which one is correct?

Unless there's a strong reason, keep ownership/context at the appropriate level.

For now:

```text
Conversation
 ├── courseId
 └── lessonId

Message
 └── conversationId
```

That's a clean starting point.

# 17. Conversation Title

The conversation could have a title:

```text
"Understanding PostgreSQL Indexes"
```

Initially, we could use:

```text
"New Conversation"
```

Later, the system could generate a title automatically.

For example:

```text
First message:
"Why are B-tree indexes used in PostgreSQL?"

        ↓

Generated title:
"PostgreSQL B-tree Indexes"
```

That's a nice future feature.

But don't make AI-generated titles part of the core conversation system yet.

# 19. Conversation Repository

The repository handles database operations.

Conceptually:

```ts
interface ConversationRepository {
  create(data: CreateConversationData): Promise<Conversation>;

  findByIdAndUserId(
    conversationId: string,
    userId: string
  ): Promise<Conversation | null>;

    userId: string

    conversationId: string

```

The exact methods can evolve.

The key is:

```text
Service
   ↓
Repository
   ↓
Prisma
   ↓
PostgreSQL
```

# 20. Controller

The controller remains thin:

```ts
create = asyncHandler(async (req, res) => {
  const conversation =
    await this.conversationService.create({
      userId: req.user.userId,
      courseId: req.body.courseId,
      lessonId: req.body.lessonId,
    });

  res.status(201).json({
    success: true,
    data: conversation,
  });
});
```

That's it.

No Prisma code.

No AI SDK.

No complex authorization logic.

# 22. Never Return Everyone's Conversations

This is a critical rule.

Bad:

```ts
repository.findMany();
```

for a student-facing endpoint.

Correct:

```ts
repository.findManyByUserId(userId);
```

The query must be scoped to the authenticated user.

This pattern will appear throughout your LMS:

```text
Student
 ↓
Only student's resources
```

---

# 23. Getting One Conversation

Request:

```http
GET /api/v1/ai/conversations/conv_123
```

Flow:

```text
JWT
 ↓
userId
 ↓
conversationId
 ↓
repository.findByIdAndUserId()
 ↓
conversation
```

If the conversation doesn't belong to the user:

```text
No matching record
```

This is a powerful pattern:

```text
resourceId + authenticatedUserId
```

Use it everywhere sensitive resources are involved.

---

# 24. Deleting a Conversation

Request:

```http
DELETE /api/v1/ai/conversations/conv_123
```

We need:

```text
Authentication
       ↓
Ownership
       ↓
Delete
```

Never:

```text
DELETE FROM conversations
WHERE id = conversationId
```

without considering ownership.

Better:

```text
DELETE
WHERE
    id = conversationId
AND
    userId = authenticatedUserId
```

Again, this is access control enforced close to the data operation.

---

# 25. What Happens to Messages?

Suppose:

```text
Conversation
 ├── Message 1
 ├── Message 2
 └── Message 3
```

and we delete the conversation.

What happens to the messages?

We have two choices.

### Cascade delete

```text
Delete Conversation
       ↓
Delete Messages
```

### Restrict deletion

```text
Delete Conversation
       ↓
Messages remain
```

For our LMS, **cascade behavior** is usually a natural design if messages have no meaning outside their conversation.

This is a database design decision we'll handle carefully when implementing the Prisma schema.

---

# 26. Conversation Ownership Is Not the Same as Course Access

Here's an important distinction.

Suppose:

```text
User
 ↓
Conversation
 ↓
Course
```

Owning the conversation does **not automatically mean** the user can access every piece of course content.

We may need:

```text
Conversation ownership
+
Course enrollment
+
Lesson access
```

For example:

```text
User owns conversation
        ↓
Is user enrolled in course?
        ↓
Yes
        ↓
Can use course context
```

The AI should never bypass LMS authorization.

Don't confuse these.

Example:

```text
Conversation ID:

```

```text

```

Relationship:

```text

   │
   ├── msg_001
   ├── msg_002
   └── msg_003
```

# 29. Database Relationship

Conceptually:

```text

 │

 ↓
```

# 30. Why Not Store Everything in One Table?

You might think:

```text
AIConversation
--------------------------------
userId
message1
response1
message2
response2
message3
response3
```

This is a terrible design.

What happens when there are:

```text
100 messages?
500 messages?
1000 messages?
```

The row becomes enormous and difficult to manage.

Instead:

```text
Conversation
     ↓
Messages
```

is normalized and scalable.

This distinction is important for the next lesson.

### Conversation Management

```text

When created?

```

Deals with:

```text

```

So:

```text

```

# 32. Conversation State

At the simplest level:

```text
Conversation
   ↓
active
```

But eventually we might have:

```text
active
archived
deleted
```

For example:

```ts
type ConversationStatus =
  | "active"
  | "archived";
```

Deletion may be represented by actual deletion or soft deletion, depending on your data-retention requirements.

Don't add status fields unless they serve a real requirement.

---

# 33. Soft Delete vs Hard Delete

### Hard delete

Actually remove:

```text
Conversation
Message
```

from the database.

### Soft delete

Keep the records but mark:

```text
deletedAt = timestamp
```

Soft deletion can help with:

```text
Recovery
Audit
Data retention
```

But it also makes every query more complicated.

For an academic project, don't add soft deletion everywhere just because production systems sometimes use it.

Choose it when there's a clear requirement.

# 35. Ordering Conversations

Usually students want:

```text

        ↓
```

That way:

# 40. Service Example

```ts
export class ConversationService {
  constructor(
    private readonly repository: ConversationRepository
  ) {}

  async create(
    input: CreateConversationInput
  ) {
    return this.repository.create(input);
  }

  async getById(
    conversationId: string,
    userId: string
  ) {
    const conversation =
      await this.repository.findByIdAndUserId(
        conversationId,
        userId
      );

    if (!conversation) {
      throw new AppError(
        "Conversation not found",
        404
      );
    }

    return conversation;
  }
}
```

Notice:

```text
Service
 ↓
Repository
```

and the service applies the application-level rule:

```text
Conversation must belong to the current user.
```

---

# 41. One Improvement to Think About

You might notice:

```ts
findByIdAndUserId()
```

already scopes the query.

That's good.

But you should still think about authorization at the service level.

Why?

Because ownership may not be the only rule.

For example:

```text
User owns conversation
        ↓
But course enrollment expired
        ↓
Cannot access course-specific context
```

So the service may eventually coordinate multiple authorization checks.

# 42. Common Mistakes

## Mistake 1 — No ownership check

```ts
findById(conversationId)
```

❌ Potential data leak.

---

## Mistake 2 — Passing the whole `req`

```ts
conversationService.create(req)
```

❌ Couples service to Express.

---

## Mistake 3 — Mixing messages and conversations

```text
Conversation table
   ↓
all messages as columns
```

❌ Poor relational design.

---

## Mistake 4 — Returning every user's conversations

```ts
findMany()
```

❌ Security problem.

---

## Mistake 5 — Overengineering

```text
ConversationStateMachine
ConversationEventBus
ConversationOrchestrator
ConversationManagerFactory
```

for a basic CRUD feature.

❌ Too much complexity.

Start simple.

# 44. What You Should Remember

If you remember only these points:

1. **Conversation is the parent of messages.**
    
2. Every conversation should have a unique ID.
    
3. Every student conversation must be scoped to its owner.
    
4. `conversationId + userId` is a powerful authorization pattern.
    
5. Course and lesson relationships make the tutor LMS-aware.
    
6. Conversation management and message management are separate concerns.
    
7. Don't put messages directly into the conversation row.
    
8. Conversation listing should be paginated.
    
9. `updatedAt` can help sort recently active conversations.
    
10. Keep the service independent of Express and Prisma.
