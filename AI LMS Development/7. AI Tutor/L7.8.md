# Lesson 7.8 — Course-Aware AI

In Lesson 7.7, we built **Context Management**.

We learned that the AI should not receive everything from the database:

```text
Full history
     ↓
Context Manager
     ↓
Relevant context
     ↓
LLM
```

Now we connect that context system to the actual **LMS course structure**.

The goal is to transform:

```text
Generic AI
```

into:

```text
Course-aware AI Tutor
```

For example, instead of asking a generic AI:

> "Explain indexing."

our LMS should know:

```text
Student
 ↓
Course: Database Engineering
 ↓
Lesson: PostgreSQL Indexes
 ↓
Question: Explain indexing
 ↓
AI Tutor
```

That makes the answer much more useful.

---

# 1. What Does Course-Aware Mean?

A course-aware tutor understands the educational context in which the student is asking the question.

For example:

```text
Course:
Database Engineering

Module:
PostgreSQL

Lesson:
Indexes

Student:
Why are indexes useful?
```

The AI can answer specifically around the student's current lesson.

Without course context:

```text
"Indexes are data structures..."
```

With course context:

```text
"You've been working with PostgreSQL in this lesson.
In PostgreSQL, an index helps the database locate rows
without scanning the entire table..."
```

The second answer is much more relevant.

# 3. Course Context Is Data

Suppose our course contains:

```text
Course:
Database Engineering

Description:
Learn relational database design,
PostgreSQL, Prisma, indexing, transactions...

Current Lesson:
PostgreSQL Indexes

Lesson Summary:
Indexes improve lookup performance...
```

This information can be included as context.

Conceptually:

```text
SYSTEM
You are an educational AI tutor.

COURSE
Database Engineering

LESSON
PostgreSQL Indexes

LESSON SUMMARY
Indexes improve database lookup performance.

STUDENT QUESTION
Why do indexes make queries faster?
```

The model now understands the educational setting.

# 4. But There Is a Critical Security Problem

Here's the important part.

Suppose:

```text
Course A
Course B
Course C
```

A student is enrolled in:

```text
Course A
```

but not:

```text
Course B
```

The AI should **not** automatically receive Course B's private content.

So:

```text
Course context
      ↓
Authorization
      ↓
Allowed?
```

must happen **before** context is provided to the LLM.

---

# 5. Authorization vs Context

These are two different concepts.

### Authorization asks:

> Is this student allowed to access this course?

### Context asks:

> Which allowed course information is useful for answering this question?

Think:

```text
                    Request
                       │
                       ↓
                 Authorization
                       │
                 ┌─────┴─────┐
                No           Yes
                ↓              ↓
              403         Context Builder
                              ↓
                         Course Context
                              ↓
                             LLM
```

This distinction is extremely important.

---

# 6. Never Let the LLM Decide Access

Bad architecture:

```text
Student
   ↓
LLM
   ↓
"Is this student enrolled?"
```

The LLM should not make authorization decisions.

Correct:

```text
Student
   ↓
Backend
   ↓
EnrollmentRepository
   ↓
Authorized?
   ↓
Context Builder
   ↓
LLM
```

The database and backend enforce permissions.

The model generates language.

# 7. Course Enrollment

Our LMS already has the concept of enrollment.

Conceptually:

```text
User
 │
 │
 └── Enrollment
        │
        └── Course
```

So when a student asks:

```text
courseId = course_123
```

we can check:

```text
Does user_456 have access to course_123?
```

Something like:

```ts
const enrollment =
  await enrollmentRepository.findByUserAndCourse(
    userId,
    courseId
  );
```

If there is no valid enrollment:

```ts
throw new ForbiddenError(
  "You do not have access to this course."
);
```

---

# 8. Why Do This Before AI Context?

Imagine this dangerous flow:

```text
Student
 ↓
Request Course B
 ↓
Load Course B private content
 ↓
Build AI prompt
 ↓
Authorization check
```

You've already loaded sensitive information.

Instead:

```text
Student
 ↓
Authorization
 ↓
Allowed?
 ↓
Load Course B context
```

This is a **least-privilege** approach.

Only retrieve data after establishing that the user can access it.

# 10. Alternative API Design

We could also use:

```http
POST /api/v1/ai/conversations/:conversationId/messages
```

Then the backend gets the course from:

```text
Conversation
   ↓
courseId
```

Both approaches are valid.

For our LMS, I prefer keeping the **conversation as the source of conversational context**, while the course relationship is stored on the conversation.

So:

```text
Conversation
 ├── userId
 ├── courseId
 └── lessonId
```

Then:

```text
conversationId
      ↓
courseId
      ↓
authorization
```

# 11. Why Not Trust `courseId` From the Frontend?

Suppose the frontend sends:

```json
{
  "courseId": "course_A",
  "message": "..."
}
```

The backend should not assume:

```text
course_A belongs to this student.
```

The client controls the request.

Therefore:

```text
Frontend
   ↓
courseId
   ↓
Backend
   ↓
Database authorization check
```

The backend verifies everything.

```ts
class CourseContextService {
```

Then:

```text

      ↓

```

This prevents the tutor service from becoming huge.

# 13. Course Context Should Be Minimal

Don't send the entire course database record to the LLM.

For example, suppose the database contains:

```text
Course
 ├── id
 ├── instructorId
 ├── internalStatus
 ├── price
 ├── privateNotes
 ├── createdAt
 ├── updatedAt
 └── description
```

The AI may only need:

```text
Course title
Course description
Current lesson
Lesson summary
```

So:

```text
Database entity
      ↓
Context projection
      ↓
Only useful fields
      ↓
LLM
```

This reduces both:

```text
data exposure
```

and:

```text
token usage
```

# 14. Context Projection

This is a useful backend concept.

Instead of:

```ts
return entireCourse;
```

we create:

```ts
return {
  title: course.title,
  description: course.description,
};
```

Then:

```text
Database
   ↓
Application object
   ↓
AI-safe context
```

This is another form of **least privilege**.

Only provide the component with what it actually needs.

# 24. Course Authorization Is Different From Conversation Authorization

This is subtle.

Suppose:

```text
Conversation belongs to Rahul
```

That doesn't necessarily mean:

```text
Rahul currently has access to the course.
```

So we may need both:

```text
Conversation ownership
+
Course access
```

For example:

```text
Conversation
     ↓
Owned by user?
     ↓
Yes
     ↓
Course
     ↓
User enrolled?
     ↓
Yes
     ↓
Context
```

This layered authorization is very important.

# 25. What If the Student Leaves the Course?

Imagine:

```text
Monday:
Student enrolled in Course A

Tuesday:
Conversation created

Friday:
Enrollment revoked

Saturday:
Student tries to ask AI about Course A
```

Should the conversation still work?

That's a business rule.

The backend should decide.

For a protected course tutor, a reasonable rule might be:

```text
No active course access
        ↓
No new course-aware AI requests
```

But perhaps the user can still view their old conversation.

This demonstrates why:

```text
Conversation ownership
```

and:

```text
Course access
```

are separate concepts.

---

# 26. Don't Delete Conversations Automatically

If enrollment ends, don't automatically assume:

```text
Enrollment deleted
 ↓
Delete conversation
```

That could be destructive.

Instead, define clear policies:

```text
Course access
→ controls access to course resources

Conversation ownership
→ controls conversation ownership

Data retention
→ controls how long records remain
```

These are separate concerns.


# 40. Why Lesson Access Might Matter

Suppose:

```text
Course
 ├── Lesson 1
 ├── Lesson 2
 └── Lesson 3
```

The student may have:

```text
Course access = yes
Lesson 1 = yes
Lesson 2 = yes
Lesson 3 = locked
```

If the AI blindly loads Lesson 3 content:

```text
Student
 ↓
AI
 ↓
Locked Lesson 3 content
```

you've bypassed the LMS's access-control model.

Therefore:

```text
Lesson access
```

must also be considered before including lesson-specific content.

---

# 41. This Is Why AI Changes Backend Security

A traditional API might protect:

```text
GET /lessons/123
```

But if you build an AI endpoint:

```text
POST /ai/chat
```

and the AI has access to lesson data, then the student might indirectly extract protected information through the AI.

For example:

> "Summarize the locked lesson."

Therefore:

```text
Direct API authorization
+
AI context authorization
```

must both be correct.

This is a major concept you'll revisit in Phase 14.

# 43. Example Service Design

Conceptually:

```ts
class CourseContextService {
  async getForTutor(
    userId: string,
    courseId: string
  ): Promise<CourseAIContext> {

    await this.authorizationService
      .assertCourseAccess(userId, courseId);

    const course =
      await this.courseRepository
        .findById(courseId);

    return {
      title: course.title,
      description: course.description,
      learningObjectives:
        course.learningObjectives,
    };
  }
}
```

Notice the sequence:

```text
Authorization
     ↓
Data retrieval
     ↓
AI projection
```

That's exactly what we want.

# 45. AITutorService

Now the orchestration becomes clearer:

```ts
async chat(input: TutorChatInput) {

  const conversation =
    await this.conversationService
      .getById(input.conversationId, input.userId);

  const courseContext =
    await this.courseContextService
      .getForTutor(
        input.userId,
        conversation.courseId
      );

  const lessonContext =
    await this.lessonContextService
      .getForTutor(
        input.userId,
        conversation.lessonId
      );

  const context =
    await this.contextManager.build({
      ...input,
      courseContext,
      lessonContext,
    });

  return this.provider.generateText(context);
}
```

This is still simplified, but the architecture is becoming clear.

# 50. Common Mistakes

### ❌ Mistake 1 — Trusting frontend `courseId`

Always verify access on the backend.

### ❌ Mistake 2 — Passing the entire course object

Create an AI-specific projection.

### ❌ Mistake 3 — Letting LLM decide authorization

Backend code decides access.

### ❌ Mistake 4 — Loading protected content before authorization

Authorize first, then retrieve.

### ❌ Mistake 5 — Sending the entire course to the model

Use metadata and eventually RAG.

### ❌ Mistake 6 — Mixing course authorization with prompt construction

Keep them as separate responsibilities.

### ❌ Mistake 7 — Assuming conversation ownership means course access

They are separate permissions.

---

# 51. The Golden Rule

Remember:

> **Authorize first. Retrieve second. Project third. Send last.**

The pipeline should be:

```text
Student
   ↓
Authentication
   ↓
Authorization
   ↓
Retrieve allowed data
   ↓
Create AI-safe projection
   ↓
Context Manager
   ↓
LLM
```

This one rule will protect you from many AI-specific security problems.

---

# 52. Interview Question

### How would you prevent an AI tutor from exposing a student's locked course content?

A strong answer:

> "I wouldn't rely on the LLM to enforce access control. The backend would first authenticate the user and verify course and lesson access. Only authorized content would then be transformed into an AI-specific context projection and passed to the context manager. The LLM would never receive unauthorized course data."

That's an excellent answer for a backend/AI interview.
