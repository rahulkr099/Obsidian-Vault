# Lesson 8.1 — Embeddings

Welcome to **Phase 8: RAG + pgvector**.

This is an important phase because we're moving from:

```text
AI Tutor
   ↓
LLM
   ↓
Answer
```

to:

```text
Course Knowledge
       ↓
   Embeddings
       ↓
   Vector Search
       ↓
Relevant Knowledge
       ↓
      LLM
       ↓
   Better Answer
```

Today we'll focus only on **embeddings**. Don't worry about pgvector or RAG implementation yet. Those come later.

---

## 1. What is an Embedding?

An **embedding** is a numerical representation of data that captures its meaning.

For our AI LMS, the most important use case is converting text into a vector of numbers.

For example:

```text
"JavaScript is a programming language."
```

might become something conceptually like:

```text
[0.21, -0.73, 0.14, 0.92, -0.31, ...]
```

A real embedding may contain hundreds or thousands of numbers.

We call this vector an **embedding**.

```text
Text
 ↓
Embedding Model
 ↓
Vector
```

The important idea is:

> Similar meanings should produce vectors that are close to each other in vector space.

---

# 2. Why Do We Need Embeddings?

Suppose your LMS contains these lessons:

```text
Lesson A:
"What is a database?"

Lesson B:
"Introduction to relational databases"

Lesson C:
"How to make chocolate cake"

Lesson D:
"JavaScript functions and parameters"
```

A student asks:

```text
"What is a relational DB?"
```

A traditional keyword search might look for:

```text
relational
DB
database
```

But embeddings allow us to search based more on **meaning**.

The system can understand that:

```text
"relational DB"
```

is semantically related to:

```text
"relational databases"
```

even if the exact words aren't identical.

That's one of the foundations of RAG.

---

# 3. Keyword Search vs Semantic Search

This distinction is extremely important.

### Keyword search

```text
Query:
"How does a database store information?"
```

The search engine primarily looks for matching words.

```text
database
store
information
```

### Semantic search

The query becomes:

```text
"What is the meaning of this question?"
```

and is represented as a vector.

Then we search for vectors that have similar meaning.

```text
Question
   ↓
Embedding
   ↓
Vector Search
   ↓
Semantically Similar Content
```

This is why embeddings are so useful for RAG.

---

# 4. Think of an Embedding as a Coordinate

Imagine a simple 2D world.

We could represent concepts using two numbers:

```text
             Programming
                  ↑
                  |
          Python  |  JavaScript
                  |
                  |
Database ---------+---------- Web
                  |
                  |
               Cooking
                  |
                  ↓
```

This is obviously much simpler than a real embedding model.

A real embedding space might have:

```text
768 dimensions
1536 dimensions
3072 dimensions
```

depending on the embedding model.

You can't visualize those dimensions directly, but mathematically they're just coordinates.

For example:

```text
Text A → [0.12, 0.81, -0.33, ...]
Text B → [0.14, 0.79, -0.31, ...]
```

If they're close in vector space, their meanings may be related.

---

# 5. Embeddings Are Not Just "Numbers"

This is a common beginner misunderstanding.

You might think:

```text
"database"
    ↓
[0.2, 0.8, 0.1]
```

means:

```text
0.2 = database
0.8 = programming
0.1 = storage
```

Usually, you **cannot interpret individual dimensions like that**.

The meaning is distributed across the vector.

Think of the entire vector as representing the semantic information.

```text
❌ Individual number = specific meaning

✅ Entire vector = representation of meaning
```

This is a very important mental model.

---

# 6. How Embeddings Work

At a high level:

```text
Input Text
    ↓
Tokenizer / Model Processing
    ↓
Neural Network
    ↓
Numerical Representation
    ↓
Embedding Vector
```

For example:

```text
"PostgreSQL is a relational database."
```

goes into an embedding model.

The model produces:

```text
[
  0.018,
 -0.241,
  0.673,
  ...
]
```

The exact values aren't important to us.

What matters is that the vector can be compared with other vectors.

# 7. Query Embeddings

Now let's introduce an important concept for RAG.

Suppose our database contains:

```text
"Normalization reduces redundancy in relational databases."

"JavaScript functions can accept parameters."

"PostgreSQL supports foreign key constraints."
```

The student asks:

```text
"Why do we normalize databases?"
```

We create an embedding for the student's question:

```text
Question
   ↓
Embedding
   ↓
Query Vector
```

We also have embeddings for our stored content:

```text
Chunk 1 → Vector 1
Chunk 2 → Vector 2
Chunk 3 → Vector 3
```

Now we compare:

```text
Query Vector
     ↓
Similarity
     ↓
Vector 1
Vector 2
Vector 3
```

The most relevant vectors are retrieved.

We'll study the actual similarity calculations in **Lesson 8.2 and 8.7**.

# 8. Document Embeddings

Our LMS will contain course materials.

Imagine an instructor uploads:

```text
DBMS.pdf
```

We eventually process it like this:

```text
DBMS.pdf
   ↓
Extract text
   ↓
Split into chunks
   ↓
Generate embedding for each chunk
   ↓
Store chunks + embeddings
```

For example:

```text
Chunk 1:
"Normalization is the process..."

Embedding 1:
[0.21, -0.31, 0.77, ...]

Chunk 2:
"A primary key uniquely identifies..."

Embedding 2:
[0.18, -0.25, 0.72, ...]

Chunk 3:
"A foreign key references..."

Embedding 3:
[0.11, -0.12, 0.81, ...]
```

Later, students can search these chunks semantically.

---

# 9. The Two Important Types of Embeddings

For our RAG system, you'll encounter two major things being embedded:

### A. Documents / chunks

```text
Course material
      ↓
Embedding
      ↓
Stored in database
```

### B. User queries

```text
Student question
      ↓
Embedding
      ↓
Used for searching
```

The basic idea is:

```text
Stored Content
      ↓
    Vectors


Student Question
      ↓
    Vector

      ↓

Compare vectors
      ↓
Find relevant content
```

This is the foundation of semantic retrieval.

---

# 10. Embedding Dimensions

An embedding has a fixed number of dimensions.

For example, imagine:

```text
Embedding dimension = 4

[0.21, 0.45, -0.17, 0.82]
```

Real models might produce much larger vectors.

For example:

```text
[ x₁, x₂, x₃, ..., x₁₅₃₆ ]
```

where:

```text
dimension = 1536
```

The dimension depends on the embedding model.

### Important rule

If your database expects:

```text
1536 dimensions
```

you cannot suddenly insert:

```text
768 dimensions
```

into the same vector field.

Your embedding model and vector storage must agree on dimensionality.

---

# 11. Embedding Model Choice

An embedding is produced by an **embedding model**.

Conceptually:

```text
Embedding Model
       ↓
Text → Vector
```

Different models have different characteristics:

```text
Model
 ├── Embedding dimension
 ├── Quality
 ├── Speed
 ├── Cost
 ├── Language support
 └── Maximum input size
```

For our LMS, we should not choose a model simply because it is popular.

We should consider:

```text
Quality
   +
Cost
   +
Latency
   +
Language support
   +
Infrastructure
```

We'll make the actual model/provider decision when we build the implementation.

---

# 12. Embeddings Are Usually Not Generated on Every Search for Documents

This is an important architecture decision.

Suppose an instructor uploads:

```text
Operating Systems.pdf
```

We don't want to regenerate embeddings for every student question.

Instead:

### During ingestion

```text
PDF
 ↓
Chunks
 ↓
Embeddings
 ↓
Database
```

Then:

### During search

```text
Student Question
 ↓
Query Embedding
 ↓
Search stored vectors
 ↓
Relevant chunks
```

So the expensive document embedding work is generally done during **ingestion**, while query embeddings are generated when users search.

# 13. Updating Course Material

Suppose an instructor replaces:

```text
DBMS-v1.pdf
```

with:

```text
DBMS-v2.pdf
```

We can't blindly keep the old embeddings.

We need something like:

```text
Old document
    ↓
Old chunks
    ↓
Old embeddings
```

and then:

```text
New document
    ↓
New chunks
    ↓
New embeddings
```

We'll later design proper lifecycle management for this in **8.5 and 8.6**.

# 14. Embedding Metadata

An embedding shouldn't exist without knowing what it belongs to.

For example:

```text
Embedding
├── vector
├── chunkId
├── documentId
├── lessonId
├── courseId
├── embeddingModel
└── createdAt
```

This becomes extremely useful later.

Suppose a student is viewing:

```text
Course: Database Management System
Lesson: Normalization
```

We don't necessarily want to search every vector in the entire LMS.

We can filter:

```text
courseId = currentCourseId
```

or even:

```text
courseId = currentCourseId
lessonId = currentLessonId
```

Then perform vector similarity search.

This is one reason **database design and RAG architecture are connected**.

# 15. Embeddings and Your AI LMS

Our eventual architecture will look like:

```text
                    ┌───────────────┐
                    │ Course Upload │
                    └───────┬───────┘
                            ↓
                       Text Extraction
                            ↓

                            ↓
```


```text

```

That's the basic RAG loop.

# 16. A Very Important Distinction

Don't confuse these three things:

### LLM

Used primarily to **generate / understand responses**.

```text
Question + Context
       ↓
      LLM
       ↓
    Answer
```

### Embedding Model

Used to **represent text as vectors**.

```text
Text
 ↓
Embedding Model
 ↓
Vector
```

### Vector Database / pgvector

Used to **store and search vectors**.

```text
Vectors
   ↓
pgvector
   ↓
Similarity Search
```

Together:

```text
Embedding Model
       ↓
    Vectors
       ↓
   pgvector
       ↓
Relevant Context
       ↓
      LLM
       ↓
     Answer
```

This distinction will save you a lot of confusion throughout Phase 8.

---

# 17. What Embeddings Don't Do

Embeddings don't magically:

```text
❌ answer questions
❌ generate paragraphs
❌ reason like an LLM
❌ replace PostgreSQL
❌ replace an LLM
```

Their main job in our system is:

```text
Convert information into a representation
that allows meaningful similarity comparisons.
```
