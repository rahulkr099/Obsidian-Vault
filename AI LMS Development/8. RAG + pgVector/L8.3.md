# Lesson 8.3 — PostgreSQL + pgvector

In **8.1**, we learned that embeddings turn text into vectors.

In **8.2**, we learned how vector search finds similar vectors.

Now we connect those ideas to the database already powering your LMS:

```text
PostgreSQL
    +
pgvector
    ↓
Store + Search Embeddings
```

This is a particularly useful architecture for your project because you don't necessarily need a completely separate vector database just to build your first serious RAG system.

---

# 1. What Is pgvector?

**pgvector** is a PostgreSQL extension that adds support for storing and searching vector embeddings.

Normally PostgreSQL stores things like:

```text
users
courses
lessons
enrollments
progress
```

With pgvector, PostgreSQL can also work with:

```text
embeddings
vectors
similarity search
```

So your architecture becomes:

```text
┌─────────────────────────────┐
│         PostgreSQL          │
│                             │
│ Users                       │
│ Courses                     │
│ Lessons                     │
│ Enrollments                 │
│ Progress                    │
│                             │
│ +                           │
│                             │
│ Course Chunks               │
│ Embeddings                  │
└─────────────────────────────┘
```

This is a major advantage for an LMS because your **relational data and AI retrieval data can live together**.

---

# 2. Why PostgreSQL + pgvector?

You could use:

```text
PostgreSQL
+
separate vector database
```

But then your architecture might become:

```text
PostgreSQL
     ↓
Relational Data

Vector DB
     ↓
Embeddings
```

Now your application has to coordinate two database systems.

For your project, we can initially use:

```text
PostgreSQL
      +
   pgvector
```

and keep:

```text

Courses
Lessons
Documents
Chunks
Embeddings
```

connected inside one database system.

That makes the architecture easier to understand and maintain.

# 3. PostgreSQL Without pgvector

Normally, PostgreSQL has data types such as:

```sql
TEXT
INTEGER
BOOLEAN
TIMESTAMP
UUID
JSONB
```

For example:

```sql
CREATE TABLE lessons (
    id UUID PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT NOT NULL
);
```

But PostgreSQL doesn't normally have a native vector type available for arbitrary embedding workloads.

pgvector adds that capability.

Conceptually:

```sql
embedding vector(1536)
```

means:

> Store a vector containing 1536 dimensions.

---

# 4. Enabling pgvector

At the PostgreSQL level, pgvector is installed as an extension.

Conceptually:

```sql
CREATE EXTENSION vector;
```

After that, PostgreSQL can understand the vector type.

For example:

```sql
CREATE TABLE document_chunks (
    id UUID PRIMARY KEY,
    content TEXT NOT NULL,
    embedding vector(1536)
);
```

Now the table can store:

```text
content
+
embedding
```

---

# 5. What Does `vector(1536)` Mean?

Remember the previous lesson.

An embedding might look conceptually like:

```text
[0.12, -0.42, 0.73, ...]
```

Suppose the embedding model produces:

```text
1536 values
```

Then we use:

```sql
vector(1536)
```

The number must match the embedding model's output dimension.

So:

```text
Embedding model
      ↓
1536 dimensions
      ↓
PostgreSQL
      ↓
vector(1536)
```

If the model produces 768 dimensions:

```text
vector(768)
```

would be appropriate instead.

---

# 6. Why Dimension Consistency Matters

Imagine your database contains:

```text
embedding vector(1536)
```

Then your application tries to insert:

```text
768-dimensional vector
```

That's a mismatch.

Think of it like this:

```text
Database expects:

[ x₁, x₂, x₃, ... x₁₅₃₆ ]

Application sends:

[ x₁, x₂, x₃, ... x₇₆₈ ]
```

They don't fit.

Therefore, when designing RAG:

> **Choose your embedding model and vector dimension deliberately.**

Don't randomly change embedding models halfway through your system.

# 9. Vector Similarity Operators

Now comes the important part.

Storing vectors isn't enough.

We need to **search them**.

pgvector supports distance/similarity operations.

The main concepts you'll encounter are:

```text
<->   Euclidean/L2 distance

<#>   Negative inner product

<=>   Cosine distance
```

Notice something interesting:

**pgvector commonly represents these as distances rather than directly returning "similarity."**

For example:

```text
smaller distance
      ↓
more similar
```

This connects directly to what we learned in 8.2.

---

# 10. Cosine Distance

Suppose we have:

```text
query vector
```

and stored vectors.

Conceptually:

```text
Query
  ↓
Compare against stored vectors
  ↓
Calculate cosine distance
  ↓
Order by smallest distance
```

A simplified query can look like:

```sql
SELECT
    id,
    content,
    embedding <=> '[0.1, 0.2, 0.3]' AS distance
FROM document_chunks
ORDER BY embedding <=> '[0.1, 0.2, 0.3]'
LIMIT 5;
```

The important idea is:

```text
ORDER BY distance ASC
```

because lower distance means closer vectors.

---

# 11. Why `LIMIT 5`?

This connects to **Top-K retrieval** from Lesson 8.2.

```sql
LIMIT 5
```

means:

> Return the five closest vectors.

So:

```text
100,000 chunks
       ↓
vector search
       ↓
rank by distance
       ↓
LIMIT 5
       ↓
5 candidate chunks
```

Those five chunks can later be passed to the RAG context-building stage.

---

# 12. A Simple Example

Imagine our database has:

```text
Chunk A
Chunk B
Chunk C
Chunk D
```

The query is:

```text
"What is normalization?"
```

After embedding, we have:

```text
Query Vector
```

The database calculates:

```text
Chunk A → 0.08
Chunk B → 0.41
Chunk C → 0.13
Chunk D → 0.76
```

Since we're using distance:

```text
0.08 → closest
0.13 → next
0.41 → next
0.76 → farthest
```

So:

```text
Top 2:

Chunk A
Chunk C
```

---

# 13. Distance vs Similarity

This causes confusion for many developers.

In Lesson 8.2 we talked about:

```text
similarity
```

But with pgvector you'll often write:

```text
distance
```

Remember:

```text
Similarity:
higher = better

Distance:
lower = better
```

For cosine distance:

```text
smaller distance
       ↓
greater similarity
```

Don't accidentally sort the wrong way.

For example:

```sql
ORDER BY embedding <=> query_vector ASC
```

is conceptually correct for finding the closest vectors.

# 14. Metadata Filtering + pgvector

This is where PostgreSQL becomes particularly powerful for your LMS.

Suppose:

```text
Course ID = 101
```

We don't want to search every course.

We can combine normal PostgreSQL filtering with vector search.

Conceptually:

```sql
SELECT
    id,
    content
FROM document_chunks
WHERE course_id = '101'
ORDER BY embedding <=> '[...]'
LIMIT 5;
```

So the database performs:

```text
Course filtering
       +
Vector similarity
       ↓
Relevant course chunks
```

This is exactly what we need for a course-aware AI Tutor.

---

# 15. Lesson-Level Retrieval

We can go further:

```sql
WHERE course_id = '101'
  AND lesson_id = '501'
```

Then:

```sql
ORDER BY embedding <=> '[...]'
LIMIT 5;
```

Now our search is:

```text
LMS
 ↓
Course
 ↓
Lesson
 ↓
Vector Search
 ↓
Top-K
```

This gives us a powerful retrieval hierarchy.

# 18. Vector Indexes

Now we reach an important performance topic.

Imagine:

```text
100 chunks
```

A simple vector search is probably fine.

But imagine:

```text
10 million chunks
```

Comparing the query vector against every single vector can become expensive.

We need indexes.

Conceptually:

```text
Without index:

Query
 ↓
Compare against every vector
 ↓
10,000,000 comparisons
```

With an appropriate vector index:

```text
Query
 ↓
Vector index
 ↓
Candidate vectors
 ↓
Nearest neighbors
```

This can make retrieval much faster.

---

# 19. Approximate Nearest Neighbor Search

You'll encounter the term:

**ANN — Approximate Nearest Neighbor.**

The idea is:

> Find very good nearest neighbors much faster than exhaustively comparing every vector.

It is called **approximate** because the system may trade a little exactness for much better performance.

This tradeoff is often worthwhile for large datasets.

---

# 20. HNSW

One important index type supported by pgvector is:

**HNSW — Hierarchical Navigable Small World.**

You don't need to understand every mathematical detail yet.

Conceptually:

```text
Millions of vectors
       ↓
     HNSW
       ↓
Fast approximate nearest-neighbor search
```

HNSW is particularly important for modern semantic search systems.

We'll later discuss:

- index creation
    
- index parameters
    
- recall
    
- speed
    
- memory usage
    
- tuning
    

For now, just remember:

```text
HNSW
   =
A vector index designed for fast
nearest-neighbor search.
```

---

# 21. IVFFlat

Another pgvector index you may encounter is:

**IVFFlat**.

It also supports approximate nearest-neighbor search.

Very roughly:

```text
IVFFlat
   ↓
Divide vectors into groups/lists
   ↓
Search relevant groups
   ↓
Return candidates
```

So you'll commonly encounter:

```text
HNSW
IVFFlat
```

when learning pgvector.

For our project, we'll choose based on the workload rather than blindly using one.

---

# 22. Exact vs Approximate Search

This is an important engineering tradeoff.

### Exact search

```text
Compare against all relevant vectors
```

Advantages:

```text
Maximum exactness
Simple concept
```

Disadvantages:

```text
Can become expensive at scale
```

### Approximate search

```text
Use a vector index
```

Advantages:

```text
Much faster
Scales better
```

Disadvantages:

```text
May not always return the mathematically exact nearest neighbors
```

So:

```text
Small dataset
   ↓
Exact search may be enough

Large dataset
   ↓
Approximate search becomes attractive
```

# 23. Prisma and pgvector

Now we reach something especially relevant to your project.

Your application uses:

```text
TypeScript
+
Prisma
+
PostgreSQL
```

So naturally you might ask:

> "Can Prisma handle vectors?"

The answer requires some care.

Prisma's standard ORM abstractions don't always expose every pgvector feature as conveniently as normal scalar fields and relations.

For advanced vector operations, you may need to use:

```text
Prisma
   +
Raw SQL
```

for certain operations.

For example:

```text
Normal CRUD
   ↓
Prisma Client

Advanced vector search
   ↓
Prisma raw SQL / supported vector functionality
```

The exact Prisma capabilities depend on the Prisma version and supported pgvector integration you're using, so when we implement this later, we'll verify the current API rather than assuming a particular syntax.

# 27. A Critical Security Point

Vector search does **not** automatically provide authorization.

Suppose:

```text
Student A
```

asks a question.

The vector database finds:

```text
Course B private instructor material
```

because it's semantically similar.

That's a security problem.

Therefore:

```text
Authentication
      ↓
Authorization
      ↓
Allowed course/document scope
      ↓
Vector retrieval
```

or otherwise ensure your retrieval query itself enforces the correct access boundary.

Never assume:

```text
"Vector similarity = permission"
```

They are completely different concerns.

---

# 28. A Critical RAG Point

Vector similarity doesn't mean:

> "This chunk is definitely the correct answer."

It means:

> "This chunk is relatively close to the query according to the selected embedding and similarity metric."

Therefore our RAG system still needs:

```text
Retrieval
   ↓
Ranking
   ↓
Filtering
   ↓
Context selection
   ↓
LLM
   ↓
Answer validation / grounding
```

This is why RAG engineering is more than just:

```text
Store embeddings
+
Call LLM
```
