# Lesson 8.4 — Document Chunking

In **8.1**, we learned how text becomes embeddings.

In **8.2**, we learned how vectors can be searched.

In **8.3**, we connected vector search to PostgreSQL + pgvector.

Now we face one of the most practical RAG problems:

> **What happens when a course document is too large to embed or retrieve as one giant piece of text?**

The answer is **document chunking**.

---

# 1. What Is Document Chunking?

**Chunking** means breaking a large document into smaller pieces.

For example:

```text
50-page PDF
     ↓
   Chunking
     ↓
┌──────────────┐
│ Chunk 1      │
├──────────────┤
│ Chunk 2      │
├──────────────┤
│ Chunk 3      │
├──────────────┤
│ ...          │
├──────────────┤
│ Chunk 100    │
└──────────────┘
```

Instead of generating one embedding for the entire PDF:

```text
PDF
 ↓
1 embedding
```

we generally do:

```text
PDF
 ↓
Text extraction
 ↓
Chunks
 ↓
Embedding for each chunk
```

So:

```text
Document
   ↓
Chunk 1 → Embedding 1
Chunk 2 → Embedding 2
Chunk 3 → Embedding 3
...
Chunk N → Embedding N
```

This is the foundation of our RAG ingestion pipeline.

---

# 2. Why Not Embed the Entire Document?

Suppose an instructor uploads:

```text
DBMS.pdf
```

with 100 pages.

The document contains:

```text
Introduction
ER Model
Relational Model
Keys
Normalization
Transactions
Concurrency
Recovery
...
```

A student asks:

> "What is 3NF?"

If the entire PDF has only one embedding:

```text
DBMS.pdf
   ↓
One vector
```

we can retrieve the entire document, but that doesn't tell us exactly which part is relevant.

We want:

```text
Question:
"What is 3NF?"

       ↓

Retrieve:

Chunk 73
"Third Normal Form removes..."
```

rather than:

```text
Retrieve:
Entire 100-page PDF
```

Chunking gives our retrieval system **finer-grained knowledge**.

---

# 3. The Basic RAG Ingestion Pipeline

Our pipeline now becomes:

```text
                  PDF
                   ↓
             Text Extraction
                   ↓
                Cleaning
                   ↓
                Chunking
                   ↓
          ┌────────┼────────┐
          ↓        ↓        ↓
       Chunk 1  Chunk 2  Chunk 3
          ↓        ↓        ↓
       Embed    Embed    Embed
          ↓        ↓        ↓
          └────────┼────────┘
                   ↓
             PostgreSQL
               + pgvector
```

Later, retrieval works in reverse:

```text
Student Question
       ↓
Query Embedding
       ↓
Vector Search
       ↓
Relevant Chunks
       ↓
LLM
```

---

# 4. What Makes a Good Chunk?

A good chunk should ideally be:

```text
Small enough
     +
Meaningful enough
     +
Self-contained enough
```

For example, this is a good chunk:

```text
Normalization is the process of organizing
data in a relational database to reduce
redundancy and improve data integrity.
```

But this might be a poor chunk:

```text
Normalization is the process...
```

if the missing next sentence contains the actual explanation.

So chunking isn't simply:

```text
"Cut text every N characters."
```

Good chunking tries to preserve **meaning**.

---

# 5. The Main Chunking Problem

Imagine the source text says:

```text
A primary key uniquely identifies each row
in a relational table.

A foreign key is a column that references
a key in another table.
```

If we split it badly:

```text
Chunk 1:
"A primary key uniquely identifies each row
in a relational table. A foreign"

Chunk 2:
"key is a column that references..."
```

we've broken the meaning.

The word:

```text
"foreign"
```

has been separated from:

```text
"key"
```

That's bad chunking.

---

# 6. Chunk Boundaries Matter

A better strategy is:

```text
Chunk 1:
A primary key uniquely identifies each row
in a relational table.

Chunk 2:
A foreign key is a column that references
a key in another table.
```

Now each chunk represents a coherent concept.

Therefore:

> **Good chunk boundaries usually follow the structure of the document.**

Potential boundaries include:

```text
Heading
Paragraph
Section
Subsection
List
Table
Code block
Page boundary
```

depending on the document.

---

# 7. Chunk Size

One of the most important chunking decisions is:

> **How large should each chunk be?**

Suppose we use:

```text
100 characters
```

The chunks may be too small.

```text
"Normalization is a database..."
```

Then:

```text
"...technique used to reduce..."
```

Information becomes fragmented.

But if we use:

```text
50,000 characters
```

we may recreate the original problem.

So there is a middle ground.

---

# 8. Think in Tokens, Not Just Characters

LLMs generally work with **tokens**, not characters.

For example:

```text
"PostgreSQL is powerful"
```

is broken into tokens by a tokenizer.

The exact tokenization depends on the model/tokenizer.

Therefore, when designing a RAG system, you'll often hear:

```text
chunk size = X tokens
```

rather than:

```text
chunk size = X characters
```

This gives us better control over the amount of information sent through the model pipeline.

---

# 9. There Is No Universal Perfect Chunk Size

This is extremely important.

You might see recommendations such as:

```text
256 tokens
512 tokens
1000 tokens
1500 tokens
```

But don't treat one number as universally correct.

The right chunk size depends on:

```text
Document type
+
Embedding model
+
Question type
+
Retrieval strategy
+
LLM context window
+
Expected answer style
```

For your LMS, a textbook chapter may benefit from different chunking than:

```text
Programming code
```

or:

```text
FAQ
```

or:

```text
Lecture transcript
```

---

# 10. Chunk Overlap

Now we introduce another important concept:

**overlap**.

Suppose we split:

```text
A B C D E F G H I J
```

into chunks of five units.

Without overlap:

```text
Chunk 1:
A B C D E

Chunk 2:
F G H I J
```

The boundary is hard.

With overlap:

```text
Chunk 1:
A B C D E

Chunk 2:
D E F G H

Chunk 3:
G H I J
```

Some information appears in both neighboring chunks.

This is called **chunk overlap**.

---

# 11. Why Use Overlap?

Consider:

```text
Chunk 1:
Normalization reduces redundancy and improves
database design.

Chunk 2:
First Normal Form requires atomic values...
```

Now imagine the important relationship between the two concepts sits right at the boundary.

Without overlap, retrieval might lose some context.

With overlap:

```text
Chunk 1
     ↘
      Shared Context
     ↗
Chunk 2
```

we have a better chance of preserving the meaning around boundaries.

---

# 12. But Too Much Overlap Is Also Bad

Suppose:

```text
Chunk size = 500 tokens
Overlap = 450 tokens
```

Then almost every chunk contains nearly the same content.

That causes:

```text
More chunks
+
More embeddings
+
More storage
+
More retrieval duplicates
+
Higher processing cost
```

So:

```text
Too little overlap
    ↓
Context may be lost

Too much overlap
    ↓
Redundancy and cost
```

Again, we're looking for a sensible balance.

---

# 13. Example With a Course Lesson

Imagine a lesson contains:

```text
# Normalization

Normalization is the process of organizing
data in relational databases.

## First Normal Form

A table is in 1NF when each field contains
atomic values.

## Second Normal Form

A table is in 2NF when it is in 1NF and
has no partial dependency.

## Third Normal Form

A table is in 3NF when it is in 2NF and
has no transitive dependency.
```

A structure-aware chunker might produce:

```text
Chunk 1:
Normalization
+ introduction

Chunk 2:
First Normal Form
+ explanation

Chunk 3:
Second Normal Form
+ explanation

Chunk 4:
Third Normal Form
+ explanation
```

That's much better than randomly splitting the entire lesson every 500 characters.

---

# 14. Hierarchical Chunking

For an LMS, document structure can be extremely useful.

Think:

```text
Course
 ↓
Section
 ↓
Lesson
 ↓
Heading
 ↓
Paragraph
```

We can preserve this structure in our metadata.

For example:

```text
Chunk:
"Third Normal Form removes transitive
dependencies."

Metadata:
{
  courseId: "...",
  lessonId: "...",
  section: "Normalization",
  heading: "Third Normal Form"
}
```

Now retrieval can use both:

```text
Semantic similarity
+
Document structure
```

This is much more powerful.

---

# 15. Metadata Is Part of the Chunk

A common beginner mistake is to store only:

```text
content
embedding
```

But we should also think about:

```text
courseId
lessonId
documentId
section
heading
pageNumber
chunkIndex
```

For example:

```text
{
  content: "Third Normal Form...",
  courseId: "course_123",
  lessonId: "lesson_45",
  documentId: "doc_9",
  heading: "Third Normal Form",
  pageNumber: 18,
  chunkIndex: 12
}
```

This metadata becomes extremely valuable when generating citations later in **8.12**.

---

# 16. Chunk Index

Every chunk should generally have an order.

For example:

```text
Chunk 0
Chunk 1
Chunk 2
Chunk 3
...
```

Why?

Suppose retrieval returns:

```text
Chunk 17
Chunk 18
Chunk 19
```

We know they are neighboring sections.

This can help with:

```text
Context reconstruction
Source display
Debugging
Document navigation
Citation generation
```

---

# 17. Page Numbers

For PDFs, page numbers can be especially useful.

Suppose:

```text
Chunk 42
```

came from:

```text
Page 18
```

We can store:

```text
pageNumber = 18
```

Then later the AI can show:

```text
Source:
DBMS.pdf — Page 18
```

This becomes very useful for student trust.

Instead of:

```text
AI says something...
```

the student can see:

```text
📄 DBMS.pdf
Page 18
```

We'll build proper source references later.

---

# 18. Code Needs Different Chunking

This is particularly important for an AI LMS containing programming courses.

Suppose the lesson contains:

```js
function calculateTotal(price, tax) {
  return price + tax;
}
```

We don't want to randomly split:

```text
function calculateTotal(price,
```

from:

```text
tax) {
  return price + tax;
}
```

That destroys the code's meaning.

For programming material, chunk boundaries should ideally respect:

```text
Function
Class
Method
Code block
Example
Explanation
```

So chunking strategy should depend on **content type**.

---

# 19. Tables Need Special Care

Suppose a PDF contains:

|Normal Form|Main Requirement|
|---|---|
|1NF|Atomic values|
|2NF|No partial dependency|
|3NF|No transitive dependency|

If we extract the PDF badly, we might get:

```text
1NF
2NF
3NF
Atomic values
No partial dependency
No transitive dependency
```

The relationship between the columns may be lost.

That's a problem.

For tables, we may need specialized extraction or transformation so the resulting chunk preserves the relationship.

For example:

```text
1NF → Atomic values
2NF → No partial dependency
3NF → No transitive dependency
```

is much more useful.

---

# 20. PDFs Are Not Plain Text

This is another important lesson.

A PDF might visually contain:

```text
Heading
Paragraph
Table
Image
Code
Footer
Page number
```

but its underlying text representation may not preserve that structure perfectly.

So:

```text
PDF
 ↓
Text extraction
```

is itself a challenging step.

Our eventual pipeline should be:

```text
PDF
 ↓
Extraction
 ↓
Cleaning
 ↓
Structure detection
 ↓
Chunking
```

not simply:

```text
PDF
 ↓
split every 500 characters
```

---

# 21. Cleaning Before Chunking

Before chunking, we often need to clean extracted text.

For example, a PDF might produce:

```text
Normalization is the process of
organizing data...

Page 1

Normalization is the process of
organizing data...
```

because a header/footer was extracted repeatedly.

We don't want:

```text
Page 1
Page 2
Page 3
```

inside our semantic content.

So:

```text
Raw document
      ↓
Cleaning
      ↓
Chunking
      ↓
Embedding
```

is generally a better pipeline.

---

# 22. Don't Destroy Important Information During Cleaning

Cleaning is not:

```text
Remove everything that looks unusual.
```

For example, this:

```text
function hello() {
  console.log("Hello");
}
```

contains formatting that may matter.

Likewise:

```text
SELECT *
FROM users
WHERE id = 10;
```

shouldn't be flattened into meaningless text.

So our cleaning process should be **content-aware**.

---

# 23. Recursive Chunking

A common strategy is **recursive chunking**.

The basic idea:

> Try to split the document using large meaningful boundaries first, and only split further when a piece is still too large.

For example:

```text
Document
 ↓
Sections
 ↓
Paragraphs
 ↓
Sentences
 ↓
Words
```

Conceptually:

```text
Try section
    ↓
Too large?
    ↓ yes
Try paragraph
    ↓
Too large?
    ↓ yes
Try sentence
    ↓
Too large?
    ↓ yes
Split further
```

This is often much better than blindly cutting text at fixed positions.

---

# 24. Example of Recursive Chunking

Suppose:

```text
Section A
```

contains:

```text
Paragraph 1
Paragraph 2
Paragraph 3
Paragraph 4
```

If the entire section fits our desired size:

```text
Section A → One chunk
```

If it's too large:

```text
Section A
 ↓
Paragraph 1 + Paragraph 2
Paragraph 3 + Paragraph 4
```

If Paragraph 3 itself is too large:

```text
Paragraph 3
 ↓
Sentences
```

The algorithm progressively finds reasonable boundaries.

---

# 25. Fixed-Size Chunking

The simplest approach is:

```text
Take N tokens
Take next N tokens
Take next N tokens
...
```

Example:

```text
500 tokens
500 tokens
500 tokens
```

Advantages:

```text
Simple
Predictable
Easy to implement
```

Disadvantages:

```text
May break semantic boundaries
May split sentences
May split code
May split tables
```

It's useful as a baseline, but not always the best production strategy.

---

# 26. Sentence-Based Chunking

Another strategy:

```text
Split into sentences
       ↓
Combine sentences until size limit
```

For example:

```text
Sentence 1
Sentence 2
Sentence 3
```

becomes:

```text
Chunk 1:
Sentence 1 + Sentence 2

Chunk 2:
Sentence 3 + Sentence 4
```

This usually preserves meaning better than arbitrary character splitting.

---

# 27. Paragraph-Based Chunking

Similarly:

```text
Paragraph 1
Paragraph 2
Paragraph 3
```

can become:

```text
Chunk 1:
Paragraph 1 + Paragraph 2

Chunk 2:
Paragraph 3 + Paragraph 4
```

This works well for many educational documents because paragraphs often represent coherent concepts.

---

# 28. Structure-Aware Chunking

For your LMS, this is particularly attractive.

We can use:

```text
Course
Section
Lesson
Heading
Subheading
Paragraph
Code block
Table
```

to decide where chunks should be created.

For example:

```text
Lesson: Database Indexes

Heading:
B-Tree Index

Paragraph:
A B-tree index...

Code:
CREATE INDEX ...

Heading:
Hash Index

Paragraph:
Hash indexes...
```

Potential chunks:

```text
Chunk 1
B-Tree Index
+ explanation
+ relevant example

Chunk 2
Hash Index
+ explanation
```

That's far more meaningful than:

```text
Characters 1–1000
Characters 1001–2000
```

---

# 29. Chunking and Retrieval Quality

This is perhaps the most important concept of today's lesson.

Suppose the question is:

> "Why does 3NF remove transitive dependency?"

If our chunk contains:

```text
Third Normal Form
```

but not the explanation:

```text
A table is in 3NF when...
```

retrieval might technically find the right chunk but provide insufficient context.

So:

```text
Good chunking
      ↓
Better retrieval
      ↓
Better context
      ↓
Better LLM answer
```

Therefore:

> **RAG quality starts before the vector database.**

It starts during document preparation.

---

# 30. Chunking and Hallucinations

Bad chunking can indirectly increase hallucinations.

Imagine:

```text
Question:
"What are the requirements for 2NF?"
```

Retrieved chunk:

```text
"Second Normal Form..."
```

but the actual requirements were split into another chunk.

The LLM may receive incomplete context.

Then:

```text
Incomplete retrieval
       ↓
Incomplete context
       ↓
LLM fills the gap
       ↓
Potential hallucination
```

Good chunking helps reduce this problem.

It doesn't eliminate hallucinations, but it improves the quality of retrieved context.

---

# 31. Chunking and Cost

More chunks means:

```text
More embeddings
      ↓
More embedding API usage
      ↓
More storage
```

And if we retrieve too many chunks:

```text
More context
      ↓
More LLM tokens
      ↓
Higher cost
```

So we need to optimize:

```text
Chunk size
+
Chunk overlap
+
Top-K
+
Context size
```

This is why RAG is both a **quality problem and a systems-engineering problem**.

---

# 32. Chunking Strategy for Our LMS

For our project, I recommend that we eventually aim for something like:

```text
              Course Material
                     ↓
              Extract Content
                     ↓
                  Clean
                     ↓
            Detect Structure
                     ↓
        ┌────────────┼────────────┐
        ↓            ↓            ↓
    Paragraph      Code          Table
        ↓            ↓            ↓
        └────────────┼────────────┘
                     ↓
             Semantic Chunks
                     ↓
              Add Metadata
                     ↓
                Embeddings
                     ↓
           PostgreSQL + pgvector
```

The exact chunk size and overlap should be **tested**, not assumed.

# 33. A Useful Chunk Metadata Design

A future chunk record might look conceptually like:

```ts
type DocumentChunk = {
  id: string;
  documentId: string;
  courseId: string;
  lessonId: string;

  content: string;

  chunkIndex: number;

  heading?: string;
  pageNumber?: number;

  tokenCount: number;

  embedding: number[];

  createdAt: Date;
};
```

Notice something important:

```text
embedding
```

is only one part of the record.

The rest of the metadata helps us understand:

```text
Where did this content come from?
```

That becomes essential for citations.

---

# 34. A Chunk Is More Than Text

Think of a chunk as:

```text
Chunk
├── Content
├── Position
├── Source
├── Course
├── Lesson
├── Structure
└── Embedding
```

For example:

```text
Chunk 37

Course:
DBMS

Lesson:
Normalization

Heading:
Third Normal Form

Page:
18

Content:
"Third Normal Form..."

Embedding:
[0.12, -0.34, ...]
```

Now our retrieval system has both:

```text
semantic information
```

and:

```text
contextual metadata
```

---

# 35. Common Chunking Mistakes

### Mistake 1 — One embedding per document

```text
PDF
 ↓
1 embedding
```

Usually too coarse for detailed retrieval.

---

### Mistake 2 — Extremely small chunks

```text
"Normalization"
```

The chunk has almost no useful context.

---

### Mistake 3 — Extremely large chunks

```text
Entire chapter
```

Retrieval becomes less precise.

---

### Mistake 4 — No overlap when boundaries matter

Important context can be split.

---

### Mistake 5 — Too much overlap

Storage and retrieval become unnecessarily expensive.

---

### Mistake 6 — Destroying structure

Tables and code can become meaningless after extraction.

---

### Mistake 7 — Losing metadata

Then later you can't easily answer:

```text
Which course?
Which lesson?
Which page?
Which document?
```

---

### Mistake 8 — Choosing chunk size without testing

A number copied from a tutorial isn't automatically optimal for your LMS.

---

# 36. The Professional Mindset

Don't ask:

> "What is the perfect chunk size?"

Ask:

> **"What chunking strategy gives the best retrieval quality for my content and query types?"**

That's a much better engineering question.

Eventually we can evaluate:

```text
Chunking Strategy A
       vs
Chunking Strategy B
```

using a set of real student questions.

For example:

```text
Question:
"What is 3NF?"

Expected source:
Lesson 7, Section 3
```

Then measure whether our retriever finds the expected chunk.

This turns chunking into something we can **test scientifically**, rather than guessing.

# 🧠 Lesson 8.4 Cheat Sheet

```text
Document Chunking
→ Breaking large documents into smaller meaningful pieces.

Chunk
→ A retrievable piece of a document.

Chunk Size
→ How much content each chunk contains.

Chunk Overlap
→ Shared content between neighboring chunks.

Fixed-Size Chunking
→ Split based on a fixed token/character size.

Sentence Chunking
→ Build chunks from sentences.

Paragraph Chunking
→ Build chunks from paragraphs.

Recursive Chunking
→ Try large meaningful boundaries first,
  then split further when necessary.

Structure-Aware Chunking
→ Use headings, sections, paragraphs,
  code blocks, tables, etc.

Metadata
→ Information such as courseId, lessonId,
  documentId, pageNumber, and chunkIndex.

Good Chunking
→ Meaningful + retrievable + sufficiently contextual.
```

```text
Bad document
      ↓
Bad chunks
      ↓
Bad embeddings
      ↓
Bad retrieval
      ↓
Bad context
      ↓
Bad AI answer
```

But:

```text
Well-structured document
      ↓
Good chunks
      ↓
Good embeddings
      ↓
Good retrieval
      ↓
Relevant context
      ↓

```

So remember:

> **RAG doesn't begin with the LLM. RAG begins with how you prepare the knowledge.**
