# Lesson 8.6 — Vector Storage

In **8.5**, we learned how to generate embeddings from document chunks.

Now we need to answer:

> **Where do we store the chunks, their embeddings, and all the information needed to retrieve and cite them later?**

For our AI LMS, the answer is:

```text
PostgreSQL
    +
pgvector
```

But we're not simply storing a vector.

We need to design a structure that connects:

```text
Course
   ↓
Lesson
   ↓
Document
   ↓
Chunk
   ↓
Embedding
```

This lesson is about designing that storage layer properly.

---

# 1. What Is Vector Storage?

Vector storage means storing an embedding in a database so that we can search it later.

For example:

```text
Chunk:

"Normalization reduces redundancy
in relational databases."
```

produces:

```text
Embedding:

[0.21, -0.42, 0.73, ...]
```

We need to store both:

```text
Content
+
Embedding
```

because the vector helps us **find** the chunk, while the content is what we actually want to **give to the LLM**.

So:

```text
Vector
  ↓
Find relevant content

Content
  ↓
Provide context
```

---

# 2. Don't Store Only the Vector

This is a common mistake.

Imagine your database contains:

```text
id: 1827

embedding:
[0.12, -0.31, 0.72, ...]
```

Later vector search returns:

```text
id: 1827
```

Now what?

You need to know:

```text
What document?
What course?
What lesson?
What page?
What content?
```

Therefore, a useful vector record needs both:

```text
Vector
+
Content
+
Metadata
```

---

# 3. The Core Data Hierarchy

For our LMS, think about the relationship like this:

```text
Course
  │
  ├── Section
  │
  └── Lesson
        │
        └── Document
              │
              └── Chunk
                    │
                    └── Embedding
```

For example:

```text
Course:
Database Management System

Section:
Relational Model

Lesson:
Normalization

Document:
DBMS Notes.pdf

Chunk:
"Third Normal Form removes..."

Embedding:
[0.12, -0.34, ...]
```

This hierarchy gives our RAG system context.

---

# 4. Why Keep Course Information?

Imagine your LMS contains:

```text
Course A
 └── DBMS
      └── Normalization

Course B
 └── Interview Preparation
      └── Database Questions
```

Both courses might contain content about databases.

A student studying Course A asks:

> "Explain normalization."

We want retrieval to prioritize:

```text
Course A
   ↓
Relevant chunks
```

rather than unrelated content from Course B.

Therefore, the vector data needs a connection to:

```text
courseId
```

---

# 5. Why Keep Lesson Information?

Course-level filtering may not be enough.

Suppose:

```text
DBMS Course
├── ER Model
├── Relational Algebra
├── Normalization
├── Transactions
└── Indexing
```

The student is currently studying:

```text
Normalization
```

We can prioritize:

```text
courseId = DBMS
lessonId = Normalization
```

Then:

```text
Vector Search
```

happens inside the relevant scope.

This gives us:

```text
Course-aware retrieval
+
Lesson-aware retrieval
```

---

# 6. Document and Chunk Are Different

This distinction is very important.

Suppose:

```text
DBMS.pdf
```

contains 100 pages.

We don't want:

```text
Document
   ↓
One embedding
```

Instead:

```text
Document
   ↓
Chunk 1
Chunk 2
Chunk 3
...
Chunk 500
```

Each chunk can have its own embedding.

So:

```text
Document
   │
   ├── Chunk 1 → Vector 1
   ├── Chunk 2 → Vector 2
   ├── Chunk 3 → Vector 3
   └── Chunk N → Vector N
```

---

# 7. Why Store the Document Separately?

Suppose an instructor deletes:

```text
DBMS.pdf
```

We should be able to find all associated chunks:

```text
Document
   ↓
Chunks
   ↓
Embeddings
```

and remove them.

This is much easier when we have proper relationships.

For example:

```text
documents.id
      ↓
document_chunks.document_id
```

Then:

```text
Delete document
      ↓
Delete related chunks
```

can be handled safely.

---

# 8. A Basic Vector Storage Table

A simplified PostgreSQL table might look like:

```sql
CREATE TABLE document_chunks (
    id UUID PRIMARY KEY,

    document_id UUID NOT NULL,

    content TEXT NOT NULL,

    embedding vector(1536) NOT NULL
);
```

This is enough to demonstrate the basic concept.

But our actual LMS will need more metadata.

---

# 9. A More Useful Design

Conceptually:

```sql
CREATE TABLE document_chunks (
    id UUID PRIMARY KEY,

    document_id UUID NOT NULL,
    course_id UUID NOT NULL,
    lesson_id UUID NOT NULL,

    content TEXT NOT NULL,

    chunk_index INTEGER NOT NULL,

    heading TEXT,
    page_number INTEGER,

    token_count INTEGER,

    embedding vector(1536) NOT NULL,

    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

Don't treat this as our final schema yet.

The important thing is understanding **why each field exists**.

---

# 10. Understanding Each Field

### `id`

Unique identity of the chunk.

```text
chunk_123
```

We need this to reference the chunk.

---

### `document_id`

Tells us:

> Which document produced this chunk?

```text
DBMS.pdf
```

---

### `course_id`

Tells us:

> Which course does this chunk belong to?

Useful for retrieval filtering.

---

### `lesson_id`

Tells us:

> Which lesson does this chunk belong to?

Useful for lesson-level retrieval.

---

### `content`

The actual text.

Example:

```text
"Third Normal Form removes transitive
dependencies."
```

This is eventually sent to the LLM as context.

---

### `chunk_index`

The position of the chunk:

```text
0
1
2
3
...
```

This helps us reconstruct document order.

---

### `heading`

For example:

```text
"Third Normal Form"
```

Useful for:

- retrieval context
    
- debugging
    
- citations
    
- UI display
    

---

### `page_number`

For PDFs:

```text
18
```

This can later become:

```text
Source: DBMS.pdf — Page 18
```

---

### `token_count`

Approximate number of tokens in the chunk.

Useful for:

```text
context budgeting
cost estimation
debugging
retrieval limits
```

---

### `embedding`

The actual vector:

```text
[0.12, -0.34, 0.81, ...]
```

This is the pgvector field.

---

# 11. Why Store `token_count`?

Suppose retrieval returns:

```text
20 chunks
```

but each chunk contains:

```text
800 tokens
```

Then:

```text
20 × 800
=
16,000 tokens
```

That might be too much context.

If we store:

```text
token_count
```

we can make smarter decisions.

For example:

```text
Retrieve Top 10
       ↓
Sort/filter by relevance
       ↓
Keep context under token budget
```

So `token_count` is not mandatory for vector search, but it can become very useful in a production RAG pipeline.

---

# 12. Why Store `chunk_index`?

Imagine retrieval returns:

```text
Chunk 17
Chunk 18
Chunk 19
```

We know:

```text
17 → before 18
18 → before 19
```

This can help when we want to combine neighboring chunks.

For example:

```text
Retrieved Chunk 18
        ↓
Also consider Chunk 17 and 19
```

This is sometimes useful when one chunk doesn't contain enough surrounding context.

---

# 13. Metadata as a JSON Field

There are two common approaches.

### Separate columns

```text
course_id
lesson_id
page_number
heading
chunk_index
```

### JSON metadata

```json
{
  "pageNumber": 18,
  "heading": "Third Normal Form",
  "chunkIndex": 12
}
```

PostgreSQL supports `JSONB`, so you could have:

```text
metadata JSONB
```

---

# 14. Which Should We Use?

For fields we frequently filter on, I generally prefer explicit columns.

For example:

```text
course_id
lesson_id
document_id
```

because these are important application-level relationships.

For less predictable metadata:

```text
pageNumber
sectionTitle
sourceType
language
```

a JSONB field can sometimes be useful.

So a hybrid design can be:

```text
Explicit columns
+
JSONB metadata
```

For example:

```text
course_id
lesson_id
document_id
content
embedding
metadata
```

where:

```json
{
  "heading": "Third Normal Form",
  "pageNumber": 18,
  "chunkIndex": 12
}
```

---

# 15. Don't Duplicate Data Without a Reason

You might ask:

> Why store `course_id` if we can get it through `document_id`?

Because retrieval performance and query simplicity matter.

Without `course_id`:

```text
chunk
 ↓
document
 ↓
lesson
 ↓
course
```

We may need several joins before filtering.

With:

```text
chunk.course_id
```

we can filter directly.

But there's a tradeoff:

```text
Duplicated data
      ↓
Potential consistency problems
```

So if we denormalize, we should do it deliberately.

This is where your **Phase 3 database knowledge** becomes important.

---

# 16. Normalized vs Denormalized RAG Data

A normalized design might look like:

```text
Course
 ↓
Lesson
 ↓
Document
 ↓
Chunk
```

and the chunk only stores:

```text
document_id
```

A more retrieval-oriented design might store:

```text
document_id
course_id
lesson_id
```

directly on the chunk.

This is technically redundant because the relationships already exist.

But it can make retrieval queries simpler and faster.

The correct question isn't:

> "Is duplication always bad?"

It's:

> **"Does this denormalization solve a real performance or query problem, and can we keep the data consistent?"**

That's a real database-engineering mindset.

---

# 17. Vector Storage and Authorization

This is one of the most important parts of the design.

Suppose:

```text
Instructor A
 └── Course A
      └── Private document

Instructor B
 └── Course B
```

A student should never retrieve Instructor A's private document merely because the embedding is similar.

Therefore:

```text
Vector similarity
      ≠
Authorization
```

We need:

```text
User authentication
        ↓
Access control
        ↓
Allowed course/document scope
        ↓
Vector retrieval
```

This is a security concern we'll revisit deeply in Phase 14.

---

# 18. Retrieval Query Concept

Suppose a student is studying:

```text
course_123
```

and asks:

```text
"What is 3NF?"
```

Conceptually:

```sql
SELECT
    id,
    content,
    page_number,
    heading
FROM document_chunks
WHERE course_id = 'course_123'
ORDER BY embedding <=> :query_embedding
LIMIT 5;
```

Now the database gives us:

```text
Chunk 42
Chunk 91
Chunk 93
Chunk 101
Chunk 105
```

and each result contains enough information to understand:

```text
What content?
Where did it come from?
Which course?
Which lesson?
Which page?
```

---

# 19. The Vector Is for Retrieval

This distinction is worth repeating.

The embedding:

```text
[0.12, -0.33, ...]
```

is mainly useful for:

```text
finding similar content
```

The LLM doesn't normally need to see:

```text
[0.12, -0.33, ...]
```

Instead, after vector search:

```text
Vector
 ↓
Find Chunk
 ↓
Get Chunk Content
 ↓
Send Content to LLM
```

So:

```text
Embedding
   ↓
Search mechanism

Content
   ↓
LLM context
```

---

# 20. The Retrieval Result

Instead of returning only:

```text
content
```

our repository can return something richer:

```ts
type RetrievedChunk = {
  id: string;
  content: string;

  documentId: string;
  courseId: string;
  lessonId: string;

  heading?: string;
  pageNumber?: number;

  similarityScore: number;
};
```

Notice:

```text
similarityScore
```

isn't necessarily stored permanently.

It can be calculated during retrieval.

For example:

```text
Chunk A → 0.94
Chunk B → 0.89
Chunk C → 0.84
```

Then the RAG service can rank and select them.

---

# 21. Distance vs Similarity in Results

Remember from 8.3:

pgvector often gives us a **distance**.

For example:

```text
Chunk A → 0.08
Chunk B → 0.13
Chunk C → 0.25
```

Smaller is better.

Our application might transform that into a similarity-like value if useful for the UI or internal ranking.

But don't blindly call:

```text
distance = similarity
```

They are different concepts.

It's better to keep the terminology clear:

```text
distance
```

when you're dealing with pgvector's distance operator.

---

# 22. Document Lifecycle

Vector storage also needs to support document lifecycle.

Suppose:

```text
DBMS.pdf
```

is:

```text
ACTIVE
```

Then the instructor uploads a new version.

We might have:

```text
DBMS.pdf v1
DBMS.pdf v2
```

We need to decide:

```text
Which version is searchable?
```

A useful design could include:

```text
document.version
document.status
```

For example:

```text
DRAFT
PROCESSING
READY
ARCHIVED
FAILED
```

Then retrieval only searches:

```text
READY
```

documents.

---

# 23. Why Status Matters

Imagine an instructor uploads:

```text
Operating Systems.pdf
```

and embedding generation is still running.

If we immediately allow retrieval:

```text
Student question
 ↓
Search
```

the system might only see:

```text
30% of the document
```

because the remaining chunks aren't embedded yet.

So we should have:

```text
Document
   ↓
PROCESSING
```

and only make it available when:

```text
Document
   ↓
READY
```

This gives us a clean state transition:

```text
UPLOAD
  ↓
PROCESSING
  ↓
READY
```

or:

```text
PROCESSING
  ↓
FAILED
```

---

# 24. Deleting Documents

Suppose the instructor deletes:

```text
DBMS.pdf
```

We should also remove its chunks and embeddings.

Conceptually:

```text
Document
   ↓
Delete
   ↓
Document Chunks
   ↓
Embeddings
```

This is where database relationships and cascading behavior become important.

We need to carefully decide whether:

```text
ON DELETE CASCADE
```

is appropriate.

For tightly owned data like:

```text
Document → Chunk
```

it can make sense.

But we shouldn't blindly add cascade deletes everywhere.

---

# 25. Updating Documents

Suppose:

```text
DBMS.pdf v1
```

contains:

```text
500 chunks
```

and the instructor updates one section.

The simplest approach is:

```text
Delete old chunks
      ↓
Reprocess document
      ↓
Create new chunks
      ↓
Generate new embeddings
```

This is easy to understand.

A more advanced system could detect:

```text
Only 3 chunks changed
```

and re-embed only those.

That is **incremental indexing**.

We'll keep this optimization in mind but don't need it for our first version.

---

# 26. Embedding Model Information

We should know which model generated each vector.

For example:

```text
embedding_model
embedding_dimension
```

could be stored.

Conceptually:

```text
embedding_model:
"embedding-model-v1"

embedding_dimension:
1536
```

Why?

Because if we later change the model:

```text
Model V1
   ↓
Model V2
```

we know which vectors need to be regenerated.

---

# 27. Embedding Versioning Strategy

A simple strategy:

```text
embedding_model = "model-a"
embedding_version = 1
```

Later:

```text
embedding_model = "model-b"
embedding_version = 2
```

Then we can run a migration:

```text
Old vectors
   ↓
Re-embedding job
   ↓
New vectors
```

This is especially important if you have a large LMS.

---

# 28. Multi-Tenant Thinking

Even though our LMS isn't necessarily a SaaS platform yet, it's useful to understand this.

Imagine:

```text
Organization A
 └── Course A

Organization B
 └── Course B
```

We may eventually need:

```text
organization_id
```

in our retrieval scope.

Then:

```text
organization
   ↓
course
   ↓
lesson
   ↓
document
   ↓
chunk
```

Vector similarity should never accidentally cross tenant boundaries.

This is another example of:

```text
metadata filtering
+
authorization
```

being essential.

Our vector storage layer now looks like:

```text

          ┌──────────────┴──────────────┐
```

# 30. Repository Layer

Because we've already adopted:

```text
Controller
   ↓
Service
   ↓
Repository
```

we should keep vector database operations inside a repository.

For example:

```text
VectorRepository
```

might expose:

```ts
searchSimilarChunks()
createChunk()
createManyChunks()
deleteDocumentChunks()
findChunkById()
```

The service shouldn't need to know:

```text
How pgvector works internally.
```

---

# 31. Example Repository Responsibilities

### `createManyChunks()`

Stores:

```text
chunks
+
embeddings
+
metadata
```

### `searchSimilarChunks()`

Accepts:

```text
queryEmbedding
courseId
lessonId?
limit
```

and returns:

```text
RetrievedChunk[]
```

### `deleteDocumentChunks()`

Removes all chunks associated with a document.

This gives us a clean boundary:

```text
RAG Service
     ↓
Vector Repository
     ↓
PostgreSQL
```

---

# 32. Why `createMany` Matters

Imagine:

```text
5,000 chunks
```

Don't necessarily insert:

```text
5,000 individual database requests
```

Instead, use batch/bulk insertion where appropriate.

Conceptually:

```text
5000 chunks
    ↓
Batch insert
    ↓
PostgreSQL
```

This improves:

```text
throughput
latency
database efficiency
```

But again, batch sizes should be chosen carefully based on actual database and driver behavior.

---

# 33. Transaction Considerations

Suppose we create:

```text
Document
```

and then:

```text
Chunks
```

and:

```text
Embedding metadata
```

We need to decide which operations should be atomic.

For example:

```text
Create document metadata
```

should probably happen separately from:

```text
Long-running embedding generation
```

because embedding generation may take a long time.

A better workflow is:

```text
Transaction:
Create document
Mark PROCESSING
Commit

Then:

Background worker
 ↓
Generate embeddings
 ↓
Store chunks
 ↓
Mark READY
```

Don't keep a database transaction open while waiting for an external AI API.

That's a very important production principle.

---

# 34. Why Long Transactions Are Dangerous

Imagine:

```text
BEGIN TRANSACTION

Call embedding provider
Wait 2 seconds
Call embedding provider
Wait 2 seconds
...
```

A large document could keep the transaction open for minutes.

That's bad because long-running transactions can:

```text
hold locks
consume resources
increase contention
complicate failures
```

Instead:

```text
Short database transaction
        ↓
External processing
        ↓
Another short database transaction
```

This is a much healthier architecture.

---

# 35. Data Consistency

Now imagine:

```text
Chunk exists
```

but:

```text
Embedding doesn't exist
```

That's an incomplete RAG record.

Or:

```text
Embedding exists
```

but:

```text
Chunk content is missing
```

That's also problematic.

So we need a consistent state.

Conceptually:

```text
Chunk
+
Embedding
+
Metadata
```

should be stored together whenever possible.

---

# 36. Unique Constraints

We don't want duplicate chunks.

For example:

```text
documentId = doc_123
chunkIndex = 15
```

could be unique within a document.

Conceptually:

```text
UNIQUE(document_id, chunk_index)
```

Then accidentally processing the same document twice doesn't automatically create duplicate chunk positions.

This works together with the idempotency concepts from Lesson 8.5.

---

# 37. But Chunk Index Alone May Not Be Enough

Suppose you reprocess the document.

The content at:

```text
chunkIndex = 15
```

may change.

So we may also need:

```text
documentVersion
```

or:

```text
contentHash
```

depending on our lifecycle strategy.

For a simple first version:

```text
document_id + chunk_index
```

can be enough.

For a more advanced version:

```text
document_id
+
document_version
+
chunk_index
```

is safer.

# 39. The Retrieval Record

```ts
type RetrievedChunk = {
```

```text

       ↓

RAG Service
       ↓
Context Builder
```

The RAG service doesn't need to understand the raw SQL.

# 🧠 Lesson 8.6 Cheat Sheet

```text
Vector Storage
→ Store embeddings together with the content
  and metadata they represent.

Chunk
→ Small retrievable piece of a document.

Embedding
→ Numerical representation used for similarity search.

Metadata
→ Information describing where the chunk came from.

Important fields:
→ documentId
→ courseId
→ lessonId
→ chunkIndex
→ pageNumber
→ heading
→ tokenCount
→ embedding

Lifecycle:
→ PENDING
→ PROCESSING
→ READY
→ FAILED

Repository:
→ Encapsulates pgvector/database operations.

Retrieval:
→ Filter + vector similarity + ranking + Top-K.

Authorization:
→ Separate concern from vector similarity.

Idempotency:
→ Prevent duplicate chunk/vector records.
```
