# Lesson 8.7 — Similarity Search

In **8.6**, we designed how our LMS stores:

```text
Course
   ↓
Lesson
   ↓
Document
   ↓
Chunk
   ↓
Embedding
```

Now we will focus on the actual retrieval problem:

> **Given a student's question, how do we find the most relevant chunks from PostgreSQL + pgvector?**

This is where our RAG system starts becoming genuinely useful.

---

# 1. What Is Similarity Search?

Similarity search means:

> Find stored vectors that are most similar to a query vector.

Our flow is:

```text
Student Question
       ↓
Query Embedding
       ↓
Query Vector
       ↓
Similarity Search
       ↓
Ranked Chunks
       ↓
Top-K Results
```

For example:

```text
Question:

"What is normalization?"
```

becomes:

```text
Query Vector
[0.21, -0.42, 0.73, ...]
```

Our database contains:

```text
Chunk 1 → Vector 1
Chunk 2 → Vector 2
Chunk 3 → Vector 3
Chunk 4 → Vector 4
```

The database compares the query vector against the stored vectors.

---

# 2. What Are We Actually Searching?

This is an important distinction.

We aren't searching directly for:

```text
"What is normalization?"
```

inside the vector column.

We're searching for the **vector representation of that question**.

So:

```text
"What is normalization?"
          ↓
    Embedding Model
          ↓
      Query Vector
          ↓
   Vector Similarity
          ↓
   Stored Embeddings
```

Then we use the matching chunk IDs to retrieve the actual text.

---

# 3. The Complete Search Process

Imagine we have:

```text
Chunk A
"Normalization reduces redundancy..."

Chunk B
"Primary keys uniquely identify rows..."

Chunk C
"Foreign keys connect related tables..."

Chunk D
"JavaScript functions accept arguments..."
```

Each chunk has an embedding.

Student asks:

```text
"Why is normalization useful?"
```

We do:

```text
Question
   ↓
Embedding
   ↓
Query Vector
   ↓
Compare against vectors
   ↓
Rank
   ↓
Top-K
```

Maybe we get:

```text
Chunk A → distance 0.07
Chunk C → distance 0.38
Chunk B → distance 0.45
Chunk D → distance 0.91
```

Therefore:

```text
Chunk A
```

is our strongest result.

---

# 4. Similarity vs Distance

Remember from Lesson 8.3:

pgvector commonly exposes **distance operators**.

For example:

```text
<->   L2 distance
<#>   Negative inner product
<=>   Cosine distance
```

When using distance:

```text
smaller distance
       ↓
more similar
```

So:

```text
0.05
```

is generally a better match than:

```text
0.80
```

when using the same distance metric.

---

# 5. Cosine Distance

For many embedding-based applications, cosine distance is an important choice.

Conceptually:

```text
Vector A
    ↘
     angle
    ↗
Vector B
```

We're interested in the orientation of the vectors.

The closer the directions:

```text
smaller cosine distance
```

and therefore:

```text
greater semantic similarity
```

The exact behavior depends on the metric and embedding setup, so we should evaluate the chosen metric with our actual data.

---

# 6. Basic pgvector Search

Suppose we have:

```sql
embedding vector(1536)
```

A simplified cosine-distance query looks like:

```sql
SELECT
    id,
    content,
    document_id,
    lesson_id,
    embedding <=> $1 AS distance
FROM document_chunks
ORDER BY embedding <=> $1
LIMIT 5;
```

Here:

```text
$1
```

represents the query embedding.

The database:

```text
1. compares vectors
2. calculates distance
3. sorts by distance
4. returns the first 5
```

---

# 7. Why `ORDER BY` Matters

Suppose our distances are:

```text
Chunk A → 0.08
Chunk B → 0.31
Chunk C → 0.12
Chunk D → 0.72
```

We want:

```text
0.08
0.12
0.31
0.72
```

So:

```sql
ORDER BY embedding <=> $1 ASC
```

makes sense for cosine distance.

If you accidentally use descending order:

```sql
ORDER BY embedding <=> $1 DESC
```

you'd retrieve the least similar results first.

That's a very common implementation mistake.

---

# 8. Top-K Retrieval

Suppose our LMS contains:

```text
500,000 chunks
```

We don't want to return all of them.

Instead:

```sql
LIMIT 5
```

means:

```text
Return the 5 closest candidates.
```

This is **Top-K retrieval**.

```text
500,000 chunks
       ↓
Vector Search
       ↓
Rank
       ↓
Top 5
```

---

# 9. Choosing K

The value of K matters.

For example:

```text
K = 1
```

might give:

```text
Only one chunk
```

while:

```text
K = 50
```

might provide too much context.

A rough conceptual comparison:

```text
K too small
   ↓
Missing useful information

K too large
   ↓
Noise
+
More tokens
+
Higher cost
```

For our LMS, K should be treated as a **retrieval parameter to evaluate**, not a magic constant.

---

# 10. Metadata Filtering

Now comes one of the most important concepts in your AI LMS.

Suppose we have:

```text
Course A
 ├── Lesson 1
 ├── Lesson 2
 └── Lesson 3

Course B
 ├── Lesson 1
 ├── Lesson 2
 └── Lesson 3
```

The query:

```text
"What is normalization?"
```

could match content from both courses.

But the student is currently studying:

```text
Course A
```

We should search within the correct scope.

Conceptually:

```sql
WHERE course_id = $courseId
```

combined with:

```sql
ORDER BY embedding <=> $queryEmbedding
```

So:

```text
Course Filter
      +
Vector Search
```

---

# 11. Course-Scoped Similarity Search

Our query can conceptually become:

```sql
SELECT
    id,
    content,
    lesson_id,
    document_id,
    embedding <=> $1 AS distance
FROM document_chunks
WHERE course_id = $2
ORDER BY embedding <=> $1
LIMIT 5;
```

Now we're saying:

> Find the five closest chunks **inside this course**.

That's much more useful than searching the entire LMS.

---

# 12. Lesson-Scoped Search

We can narrow it further.

Suppose the student is viewing:

```text
Course:
DBMS

Lesson:
Normalization
```

Then:

```sql
WHERE course_id = $2
  AND lesson_id = $3
```

followed by vector ranking.

Our retrieval becomes:

```text
All LMS Content
       ↓
Course
       ↓
Lesson
       ↓
Vector Search
       ↓
Top-K
```

This supports the **lesson-aware AI Tutor** we want to build.

---

# 13. But Should We Always Search Only the Current Lesson?

Not necessarily.

Imagine the student asks:

> "How is 3NF related to functional dependencies?"

The answer may require content from:

```text
Current lesson
+
Earlier lesson
```

If we restrict retrieval too aggressively:

```text
Current Lesson ONLY
```

we might miss useful information.

So a better system may have retrieval levels:

```text
Level 1
Current Lesson

       ↓ if insufficient

Level 2
Current Course

       ↓ if insufficient

Level 3
Other permitted course knowledge
```

This is a powerful retrieval strategy.

---

# 14. Hierarchical Retrieval

We can think of it like:

```text
              Student Question
                     ↓
             Current Lesson
                     ↓
              Good Results?
                ↙       ↘
              YES        NO
               ↓          ↓
             Done      Current Course
                           ↓
                     Good Results?
                       ↙       ↘
                     YES        NO
                      ↓          ↓
                    Done      Wider Scope
```

This allows the system to prioritize the student's current context without unnecessarily restricting retrieval.

---

# 15. Similarity Threshold

Top-K has a subtle problem.

Suppose the LMS contains:

```text
DBMS
Operating Systems
JavaScript
Networking
```

Student asks:

> "Explain quantum entanglement."

Even if nothing is relevant, vector search can still return:

```text
Top 5 results
```

because something must be ranked above something else.

That doesn't mean the results are actually useful.

So we can introduce a **similarity/distance threshold**.

Conceptually:

```text
Query
 ↓
Vector Search
 ↓
Distance
 ↓
Is result sufficiently close?
```

For distance:

```text
distance <= threshold
```

could mean:

```text
Potentially relevant
```

while:

```text
distance > threshold
```

could mean:

```text
Probably not relevant
```

But the threshold must be evaluated with your chosen embedding model and dataset.

---

# 16. Why Thresholds Are Not Universal

Suppose:

```text
Query A → distance 0.15
Query B → distance 0.15
```

You can't automatically conclude:

```text
Both are equally useful.
```

Similarity scores depend on:

```text
embedding model
query wording
document type
chunking
similarity metric
dataset
```

Therefore, don't blindly copy:

```text
threshold = 0.2
```

from a tutorial.

Instead, we should eventually create an evaluation dataset and determine what works well for our LMS.

---

# 17. Combining Top-K and Threshold

A better retrieval strategy can use both:

```text
Top-K
+
Threshold
```

For example:

```text
Search Top 10
       ↓
Remove results below relevance threshold
       ↓
Use remaining results
```

Suppose:

```text
K = 10
```

but only four results are sufficiently relevant:

```text
1 → good
2 → good
3 → good
4 → good
5 → weak
6 → weak
...
```

We keep:

```text
4 useful chunks
```

instead of blindly using all ten.

---

# 18. Filtering Before vs After Search

There are two conceptual approaches.

### Filter before retrieval

```text
Course Filter
     ↓
Vector Search
```

### Search first, filter later

```text
Vector Search
     ↓
Filter
```

For your LMS, filtering as part of the database query is generally preferable when the filter represents a hard scope such as:

```text
courseId
tenantId
access scope
document status
```

Why?

Because you don't want irrelevant or unauthorized data becoming candidates in the first place.

---

# 19. Authorization Is Different

Suppose a student belongs to:

```text
Course A
```

but the database contains:

```text
Course B
Private Instructor Notes
```

Even if Course B has a highly similar vector:

```text
Course B chunk → distance 0.01
```

the student should not retrieve it.

So:

```text
Similarity
      ≠
Permission
```

Your retrieval query must respect the user's allowed scope.

This is especially important once our LMS has:

```text
Student
Instructor
Admin
```

roles.

---

# 20. Document Status Filtering

Remember Lesson 8.6?

We introduced document states:

```text
PENDING
PROCESSING
READY
FAILED
```

We shouldn't retrieve chunks from documents that aren't ready.

Conceptually:

```sql
WHERE course_id = $courseId
  AND document_status = 'READY'
```

Then:

```text
Vector Search
```

So the retrieval pipeline becomes:

```text
Permission Scope
      ↓
Course/Lesson Scope
      ↓
Ready Documents
      ↓
Vector Search
      ↓
Top-K
```

This prevents incomplete ingestion from leaking into answers.

---

# 21. Hybrid Retrieval

Now we can introduce a more advanced idea.

Vector search is great for semantic meaning.

Keyword search is great for exact terms.

Suppose the student asks:

> "What does `bcrypt.compare()` do?"

A semantic search may understand the concept.

But exact keyword matching is also extremely useful for:

```text
bcrypt.compare
Prisma.$transaction
useEffect
HTTP 401
JWT
```

Therefore, production search can combine:

```text
Keyword Search
       +
Vector Search
       ↓
Hybrid Retrieval
```

We don't need to implement this yet.

But keep it in mind.

---

# 22. Why Hybrid Search Can Be Better

Imagine course material contains:

```text
"JWT access tokens expire after 15 minutes."
```

Student asks:

```text
"What does JWT mean?"
```

Vector search understands semantic similarity.

Now student asks:

```text
"What is the value of JWT_EXPIRES_IN?"
```

Exact keyword matching can be very powerful.

So:

```text
Semantic search
→ meaning

Keyword search
→ exact terms
```

Combining both can improve retrieval for mixed educational content.

---

# 23. Retrieval Score and Ranking

Suppose our vector search returns:

```text
Chunk A → distance 0.08
Chunk B → distance 0.11
Chunk C → distance 0.14
```

The natural ranking is:

```text
A
B
C
```

But later, if we use hybrid retrieval, ranking becomes more complex.

We might have:

```text
Vector score
+
Keyword score
+
Metadata relevance
```

and calculate a combined ranking.

For now, keep our system simple:

```text
Filter
 ↓
Vector similarity
 ↓
Distance ranking
 ↓
Top-K
```

---

# 24. Neighboring Chunks

Sometimes the best chunk isn't enough.

Suppose retrieval finds:

```text
Chunk 50
```

but the explanation continues in:

```text
Chunk 51
```

We could optionally retrieve neighboring chunks:

```text
Chunk 50
   ↓
Chunk 49 + Chunk 50 + Chunk 51
```

This is sometimes called **context expansion**.

It can improve completeness.

But it can also introduce irrelevant information.

So it should be used carefully.

---

# 25. Context Expansion Example

Suppose:

```text
Chunk 10:
"Second Normal Form requires..."

Chunk 11:
"This means a table must..."

Chunk 12:
"For example..."
```

Vector search finds:

```text
Chunk 11
```

If we only retrieve Chunk 11, the explanation might feel incomplete.

Context expansion can retrieve:

```text
10 + 11 + 12
```

giving the LLM more coherent context.

This is another reason why `chunkIndex` from Lesson 8.6 is useful.

---

# 26. Duplicate Retrieval

Chunk overlap can sometimes cause:

```text
Chunk 20
Chunk 21
Chunk 22
```

to contain almost identical information.

If Top-K returns all three:

```text
Top 3
```

we might waste context.

So retrieval can eventually include:

```text
deduplication
```

or:

```text
diversity-aware ranking
```

The goal isn't simply:

> "Give the LLM the most similar chunks."

It's:

> **"Give the LLM a small set of highly relevant and useful context."**

That's a more mature RAG goal.

---

# 27. Retrieval vs Context Selection

This distinction is important.

### Retrieval

Find candidate chunks:

```text
100,000 chunks
      ↓
Top 20
```

### Context selection

Choose what actually goes to the LLM:

```text
20 candidates
      ↓
Filter / rank / deduplicate
      ↓
5 useful chunks
```

So:

```text
Vector Search
      ↓
Candidate Retrieval
      ↓
Context Selection
      ↓
LLM
```

We'll explore this more deeply in Lesson 8.8.

---

# 28. Query Rewriting

Another advanced idea is **query rewriting**.

Student asks:

> "Can you explain that again?"

The question by itself is poor for vector search.

We need conversation context:

```text
Previous:
"What is 3NF?"

Student:
"Can you explain that again?"
```

The system could transform it into:

```text
"Explain Third Normal Form in simple terms."
```

Then generate the embedding.

So:

```text
Conversation
      ↓
Query Understanding
      ↓
Rewritten Query
      ↓
Embedding
      ↓
Vector Search
```

We'll explore query/context management in later lessons.

---

# 29. Search Query Should Not Automatically Be the LLM Prompt

This is another important architectural distinction.

Suppose the student asks:

```text
"Explain normalization with an example."
```

The query used for vector search might be:

```text
"normalization database redundancy relational tables"
```

while the LLM prompt might remain:

```text
"Explain normalization with an example."
```

These are different jobs.

```text
Search query
→ Find relevant knowledge

User question
→ Generate the answer
```

Don't confuse them.

# 31. Practical SQL Design

A simplified query could eventually resemble:

```sql
SELECT
    dc.id,
    dc.content,
    dc.document_id,
    dc.lesson_id,
    dc.heading,
    dc.page_number,
    dc.chunk_index,

    dc.embedding <=> $1 AS distance

FROM document_chunks dc

JOIN documents d
    ON d.id = dc.document_id

WHERE dc.course_id = $2
  AND d.status = 'READY'

ORDER BY dc.embedding <=> $1

LIMIT $3;
```

The important parts are:

```text
$1 → query embedding
$2 → course scope
$3 → K
```

This isn't our final production query yet, but it shows how the pieces fit together.

---

# 32. Why Join `documents`?

Suppose the chunk itself doesn't store:

```text
document.status
```

Then we can retrieve the status through the relationship:

```text
document_chunks
      ↓
documents
```

and filter:

```text
d.status = 'READY'
```

This is another example of combining:

```text
Relational database logic
+
Vector search
```

inside PostgreSQL.

---

# 33. Query Performance

Imagine:

```text
1 million chunks
```

and every search has:

```text
WHERE course_id = ...
ORDER BY embedding <=> ...
```

We need to think about:

```text
vector indexes
relational indexes
query plans
filter selectivity
database size
```

For example, an index on:

```text
course_id
```

may help the relational filtering side.

And a vector index helps approximate nearest-neighbor search.

But the interaction between filtering and vector indexes can be subtle.

We should **measure actual query performance** rather than assuming an index automatically makes everything faster.

---

# 34. Exact Search vs Approximate Search

For a small dataset:

```text
10,000 chunks
```

exact search may be perfectly acceptable.

For a huge dataset:

```text
10,000,000 chunks
```

approximate search becomes much more attractive.

So:

```text
Small
 ↓
Exact search may be enough

Large
 ↓
ANN index
 ↓
Faster retrieval
```

This is a performance decision, not an automatic requirement.

# 35. Retrieval Evaluation

Here's where things become really interesting.

We shouldn't judge our retrieval system only by:

```text
"It seems to work."
```

We should test it.

Create questions:

```text
Q1:
What is 3NF?

Expected:
Normalization lesson

Q2:
What is a foreign key?

Expected:
Relational model lesson

Q3:
How does indexing improve queries?

Expected:
Database indexing lesson
```

Then measure:

```text
Did Top-K contain the correct chunk?
```

If:

```text
10 questions
8 retrieve the expected chunk
```

we have:

```text
Recall@K = 80%
```

This is a very useful way to evaluate retrieval.

---

# 36. Recall@K

For example:

```text
K = 5
```

means:

> Did the relevant chunk appear within the top five retrieved results?

Suppose:

```text
20 test questions
```

and:

```text
17
```

had the correct source in their Top-5 results.

Then:

```text
Recall@5 = 17 / 20
        = 85%
```

This is much more meaningful than saying:

> "The chatbot seems pretty good."

---

# 37. Why Retrieval Evaluation Matters

Suppose the LLM gives a wrong answer.

Where did the problem occur?

Possibilities:

```text
Document extraction
      ↓
Chunking
      ↓
Embedding
      ↓
Retrieval
      ↓
Context selection
      ↓
Prompt
      ↓
LLM
```

If we don't evaluate retrieval separately, everything becomes:

```text
"AI gave a bad answer."
```

Instead, we can ask:

```text
Did retrieval find the correct content?
```

If no:

```text
Retrieval problem.
```

If yes:

```text
Maybe context/prompt/LLM problem.
```

This is extremely useful for debugging.

---

# 42. The Most Important Distinction

Remember these three stages:

```text
RETRIEVAL
   ↓
Find relevant candidates

RANKING
   ↓
Order candidates by relevance

CONTEXT SELECTION
   ↓
Choose what the LLM actually receives
```

They aren't necessarily the same operation.

A mature RAG system treats them separately.

---

# 43. Common Similarity Search Mistakes

### Mistake 1 — Wrong sort direction

Using:

```sql
ORDER BY distance DESC
```

when smaller distance means better.

---

### Mistake 2 — Searching the entire LMS

Without:

```text
courseId
lessonId
tenantId
```

or other relevant scope.

---

### Mistake 3 — Trusting Top-K blindly

The fifth result isn't necessarily useful.

---

### Mistake 4 — Using arbitrary thresholds

A threshold copied from another project may not work for your embedding model.

---

### Mistake 5 — Ignoring document status

Don't retrieve chunks from documents still being processed.

---

### Mistake 6 — Treating similarity as authorization

A similar chunk doesn't mean the user can access it.

---

### Mistake 7 — Sending every retrieved chunk to the LLM

Retrieval and context selection are different stages.

---

### Mistake 8 — Never evaluating retrieval

Without test questions, you don't know whether your retrieval actually works.
