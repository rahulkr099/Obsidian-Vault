# Lesson 8.8 — Building the Retrieval Pipeline

In **8.7**, we learned similarity search:

```text
Student Question
      ↓
Query Embedding
      ↓
Vector Search
      ↓
Top-K Results
```

But a production RAG system needs more than a single database query.

We need to turn those pieces into a complete pipeline that decides:

> **What information should the AI Tutor receive before generating its answer?**

---

# 1. Retrieval Is a Pipeline, Not a Single Query

A beginner implementation might look like:

```text
Question
   ↓
Embedding
   ↓
Vector Search
   ↓
Top 5
   ↓
LLM
```

That can work for a demo.

For our AI LMS, we want something closer to:

```text
Student Question
       ↓
Query Understanding
       ↓
Access Control
       ↓
Query Embedding
       ↓
Metadata Filtering
       ↓
Candidate Retrieval
       ↓
Ranking
       ↓
Threshold Filtering
       ↓
Deduplication
       ↓
Context Expansion
       ↓
Context Budgeting
       ↓
Final Context
       ↓
LLM
```

This is the **retrieval pipeline**.

---

# 2. Why Do We Need So Many Steps?

Imagine the student asks:

> "Explain 3NF with an example."

Our vector database might return:

```text
Chunk 72 → 0.08
Chunk 73 → 0.09
Chunk 68 → 0.11
Chunk 91 → 0.14
Chunk 120 → 0.19
```

Technically, these are the closest results.

But:

```text
Closest ≠ Always useful
```

Maybe:

```text
Chunk 72
→ Definition of 3NF

Chunk 73
→ Example of 3NF

Chunk 68
→ 2NF

Chunk 91
→ BCNF

Chunk 120
→ Database history
```

We don't necessarily want all five.

So retrieval needs **reasoning and filtering around the vector search**.

---

# 3. Step 1 — Understand the User's Question

Before searching, we should understand what the student is asking.

Example:

```text
"Explain 3NF with an example."
```

Potential information:

```text
Topic:
3NF

Intent:
Explanation

Requested detail:
Example

Domain:
Database normalization
```

Another question:

```text
"Give me a simple example."
```

is incomplete by itself.

We may need conversation context:

```text
Previous:
"What is 3NF?"

Student:
"Give me a simple example."
```

The retrieval system should understand:

```text
"Give me a simple example of 3NF."
```

This is called **query understanding / query contextualization**.

---

# 4. Step 2 — Check Access

Before retrieving anything, we should determine what the student is allowed to access.

For example:

```text
Student
   ↓
Enrollment
   ↓
Course
```

If the student isn't enrolled in:

```text
Course A
```

we shouldn't retrieve:

```text
Course A private material
```

So:

```text
Question
   ↓
User identity
   ↓
Permission scope
   ↓
Allowed content
```

This is extremely important.

Never rely on vector similarity for authorization.

---

# 5. Retrieval Security Rule

Remember this:

> **Filter by permission before trusting retrieved content.**

Bad architecture:

```text
Search everything
      ↓
Find relevant chunk
      ↓
Check permission
```

Better:

```text
Determine allowed scope
      ↓
Search only permitted content
```

Why?

Because unauthorized information should ideally never become a candidate.

---

# 6. Step 3 — Generate the Query Embedding

After understanding the query:

```text
"Explain 3NF with an example."
```

we generate:

```text
Query Embedding
```

Conceptually:

```text
Question
   ↓
Embedding Model
   ↓
[0.21, -0.42, 0.73, ...]
```

This vector is then used against our stored chunk embeddings.

---

# 7. Step 4 — Apply Metadata Filters

Now we know:

```text
Student:
student_123

Course:
DBMS

Lesson:
Normalization
```

We can search within:

```text
course_id = DBMS
```

and potentially:

```text
lesson_id = Normalization
```

plus:

```text
document.status = READY
```

So:

```text
Allowed Content
       ↓
Course Filter
       ↓
Lesson Filter
       ↓
READY Documents
       ↓
Vector Search
```

---

# 8. Current Lesson vs Current Course

Don't always force:

```text
lesson_id = currentLesson
```

Suppose the student asks:

> "How does 3NF depend on functional dependencies?"

The answer may be in another lesson.

A useful strategy is:

```text
First:
Current Lesson

If insufficient:
Current Course

If still insufficient:
Other allowed sources
```

Conceptually:

```text
Current Lesson
      ↓
Enough?
 ├── YES → use results
 └── NO
       ↓
Current Course
       ↓
Enough?
 ├── YES → use results
 └── NO
       ↓
Wider permitted knowledge
```

This makes retrieval more flexible.

---

# 9. Step 5 — Candidate Retrieval

Now we perform vector search.

Suppose our course has:

```text
50,000 chunks
```

We might retrieve:

```text
Top 20
```

rather than immediately asking the LLM to use them all.

So:

```text
50,000 chunks
      ↓
Vector Search
      ↓
20 candidates
```

These are **candidate chunks**.

We're not finished yet.

---

# 10. Why Retrieve More Than We Need?

Suppose our final context should contain:

```text
5 chunks
```

Why retrieve 20?

Because the best five after further processing might not simply be the first five vector results.

For example:

```text
Top 20
   ↓
Remove duplicates
   ↓
Remove weak matches
   ↓
Remove irrelevant sections
   ↓
Select diverse useful chunks
   ↓
Final 5
```

This gives us room for better context selection.

---

# 11. Candidate Retrieval vs Final Retrieval

Think of it as:

```text
Candidate Retrieval
       ↓
"Give me potentially useful information."

Context Selection
       ↓
"Give me the best information for this answer."
```

This distinction is very useful.

---

# 12. Step 6 — Ranking

The first ranking is usually vector distance.

For example:

```text
Chunk 72 → 0.07
Chunk 73 → 0.09
Chunk 68 → 0.11
Chunk 91 → 0.16
Chunk 120 → 0.21
```

Lower distance means stronger similarity for the chosen distance metric.

But later we may have more ranking signals.

For example:

```text
Vector relevance
+
Keyword relevance
+
Current lesson relevance
+
Document quality
```

Then we can calculate a combined ranking.

For the first version, keep it simple.

---

# 13. Step 7 — Relevance Threshold

Suppose we retrieve:

```text
Chunk A → 0.07
Chunk B → 0.09
Chunk C → 0.12
Chunk D → 0.53
Chunk E → 0.61
```

Maybe:

```text
A
B
C
```

are useful while:

```text
D
E
```

are weak.

A threshold lets us reject poor results.

Conceptually:

```text
distance <= acceptable range
```

The exact threshold should be **experimentally determined**.

Don't blindly choose a number from another RAG project.

---

# 14. What If No Chunks Pass the Threshold?

This is an important situation.

Suppose the student asks:

> "Explain quantum computing."

but our course only contains:

```text
HTML
CSS
JavaScript
React
Node.js
```

Vector search might still return something.

But if nothing passes our relevance threshold:

```text
No reliable context
```

we should not pretend we found the answer.

Instead, the system can respond with something like:

> "I couldn't find enough information about that topic in the course material."

This is a major part of **grounded AI behavior**.

---

# 15. Don't Force the LLM to Answer

A dangerous architecture is:

```text
No relevant chunks
      ↓
Still ask LLM
      ↓
LLM generates answer from general knowledge
```

That can create answers that look confident but aren't grounded in the course.

A safer RAG behavior is:

```text
No relevant evidence
       ↓
Tell the student
       ↓
No sufficient course context found
```

Depending on the product requirements, we can optionally offer:

```text
"Would you like a general explanation?"
```

But that should be a deliberate product decision.

---

# 16. Step 8 — Deduplication

Chunk overlap can create duplicates.

Suppose:

```text
Chunk 20
```

contains:

```text
Normalization reduces redundancy...
```

and:

```text
Chunk 21
```

contains:

```text
Normalization reduces redundancy...
Second Normal Form...
```

Both may be retrieved.

Sending both could waste context.

So:

```text
Retrieved Candidates
       ↓
Deduplication
       ↓
Unique Useful Chunks
```

---

# 17. Simple Deduplication

We can use:

```text
chunkId
```

to remove exact duplicate records.

For example:

```ts
const unique = new Map(
  chunks.map(chunk => [chunk.id, chunk])
);
```

But that's only **record-level deduplication**.

Two different chunks may contain nearly identical content.

That's a harder problem.

---

# 18. Semantic Deduplication

Suppose:

```text
Chunk A:
"Normalization reduces redundancy."

Chunk B:
"Database normalization helps reduce data redundancy."
```

Different IDs.

But semantically almost identical.

We could eventually use:

```text
semantic similarity
```

to detect near-duplicates.

However, don't add complexity too early.

For our first implementation:

```text
Exact duplicate removal
```

is enough.

---

# 19. Step 9 — Context Expansion

Suppose retrieval finds:

```text
Chunk 50
```

but the explanation continues in:

```text
Chunk 51
```

We can optionally expand:

```text
Chunk 49
Chunk 50
Chunk 51
```

This is useful when chunk boundaries split a concept.

Our `chunkIndex` from Lesson 8.6 makes this possible.

---

# 20. When Should We Expand?

Not every result needs expansion.

For example:

```text
Chunk 50:
"3NF removes transitive dependency."
```

might already be complete.

But:

```text
Chunk 50:
"3NF removes..."

Chunk 51:
"...transitive dependency because..."
```

needs surrounding context.

So context expansion can be conditional.

---

# 21. Step 10 — Context Budgeting

Now we have:

```text
10 useful chunks
```

But perhaps the LLM context budget allows:

```text
4,000 tokens
```

and our chunks contain:

```text
6,500 tokens
```

We can't simply send everything.

We need:

```text
Context Budget
      ↓
Select highest-value chunks
```

This is **context budgeting**.

---

# 22. Why Context Size Matters

More context isn't always better.

Imagine:

```text
100 chunks
```

containing:

```text
50,000 tokens
```

The LLM now has to process a huge amount of information.

This can cause:

```text
Higher cost
More latency
More noise
Potentially weaker focus
```

So:

> **The goal isn't maximum context. The goal is sufficient useful context.**

---

# 23. Token-Based Context Selection

Suppose:

```text
Chunk A → 700 tokens
Chunk B → 500 tokens
Chunk C → 600 tokens
Chunk D → 1,200 tokens
Chunk E → 900 tokens
```

Our context budget is:

```text
2,000 tokens
```

We might select:

```text
A + B + C = 1,800
```

instead of:

```text
A + B + C + D + E = 3,900
```

This is why storing `tokenCount` is useful.

---

# 24. Context Selection Algorithm

A simple first approach:

```text
1. Sort by relevance
2. Start with empty context
3. Add the best chunk
4. Check token budget
5. Add next chunk if it fits
6. Continue
7. Stop when budget is reached
```

Conceptually:

```text
Candidates
   ↓
Sort by relevance
   ↓
Chunk 1 → fits? ✓
Chunk 2 → fits? ✓
Chunk 3 → fits? ✓
Chunk 4 → too large ✗
Chunk 5 → fits? ✓
   ↓
Final Context
```

This is simple and effective as a starting point.

---

# 25. But Relevance Alone Isn't Enough

Suppose:

```text
Chunk A → 0.07
Chunk B → 0.08
Chunk C → 0.09
Chunk D → 0.10
```

All four are highly similar.

But they might all discuss the **same sentence**.

Meanwhile:

```text
Chunk E → 0.14
```

could contain the example the student specifically needs.

So we eventually want:

```text
Relevance
+
Diversity
```

rather than relevance alone.

---

# 26. Diversity in Retrieval

Imagine the question:

> "Explain 3NF with an example."

We ideally want:

```text
Definition
+
Explanation
+
Example
```

not:

```text
Definition
+
Definition
+
Definition
```

This is why advanced retrieval systems sometimes use **diversity-aware ranking**.

One well-known family of approaches is based on **Maximal Marginal Relevance (MMR)**.

You don't need to implement it yet.

Just understand the goal:

> **Select chunks that are both relevant to the query and not redundant with each other.**

---

# 27. Step 11 — Ordering Context

Suppose we select:

```text
Chunk 50
Chunk 51
Chunk 48
Chunk 52
```

We probably don't want to send them in random order.

We can reconstruct document order:

```text
Chunk 48
Chunk 50
Chunk 51
Chunk 52
```

or potentially:

```text
Chunk 48
Chunk 49
Chunk 50
Chunk 51
```

depending on what was retrieved.

Ordering can improve coherence.

---

# 28. Source Grouping

Suppose retrieval finds:

```text
DBMS.pdf
Chunk 72

DBMS.pdf
Chunk 73

Normalization Notes.pdf
Chunk 12

DBMS.pdf
Chunk 75
```

We can group them:

```text
DBMS.pdf
 ├── Chunk 72
 ├── Chunk 73
 └── Chunk 75

Normalization Notes.pdf
 └── Chunk 12
```

This helps later when building citations.

---

# 29. Context Formatting

Eventually, our RAG service should transform retrieved chunks into structured context.

For example:

```text
[Source 1]
Document: DBMS Notes
Lesson: Normalization
Section: Third Normal Form
Page: 18

Third Normal Form removes transitive dependencies.

[Source 2]
Document: DBMS Notes
Lesson: Normalization
Section: Third Normal Form
Page: 19

For example, consider a table...
```

Then the LLM receives:

```text
Retrieved Context
+
Student Question
```

rather than raw vectors.

---

# 30. The LLM Doesn't Need the Vector

Remember:

```text
Embedding
```

is used for:

```text
retrieval
```

The LLM needs:

```text
actual text
```

So:

```text
Vector Search
      ↓
Chunk Content
      ↓
Context
      ↓
LLM
```

not:

```text
Vector Search
      ↓
Vector
      ↓
LLM
```

---

# 31. A Useful `RetrievedChunk` Structure

We can define:

```ts
type RetrievedChunk = {
  id: string;

  content: string;

  documentId: string;
  courseId: string;
  lessonId: string;

  heading?: string;
  pageNumber?: number;
  chunkIndex: number;

  tokenCount: number;

  distance: number;
};
```

Then our pipeline can transform:

```text
RetrievedChunk[]
```

into:

```text
ContextChunk[]
```

where only the information needed by the LLM remains.

---

# 32. Context Builder

A dedicated service can handle this:

```text
ContextBuilder
```

Responsibilities:

```text
deduplication
ordering
token budgeting
source formatting
context expansion
```

Then our architecture becomes:

```text
RAG Service
    ↓
Retriever
    ↓
Retrieved Chunks
    ↓
Context Builder
    ↓
Final Context
    ↓
LLM
```

This is cleaner than putting everything inside one giant function.

---

# 33. Don't Build One Giant `ragService()`

Avoid eventually having:

```ts
async function ragService() {
  // authenticate
  // query rewrite
  // generate embedding
  // database search
  // deduplicate
  // rerank
  // format context
  // call LLM
  // save conversation
  // return response
}
```

That becomes difficult to maintain.

Instead:

```text
QueryService
EmbeddingService
Retriever
ContextBuilder
LLMService
CitationService
```

Each handles a focused responsibility.

This matches the controller → service → repository architecture we've been using throughout the LMS.

---

# 34. Suggested Architecture

Conceptually:

```text
AI Tutor Controller
        ↓
AI Tutor Service
        │
        ├── QueryService
        │
        ├── EmbeddingService
        │
        ├── Retriever
        │
        ├── ContextBuilder
        │
        └── LLMService
                  │
                  ↓
              AI Provider
```

And:

```text
Retriever
    ↓
VectorRepository
    ↓
PostgreSQL + pgvector
```

This gives us clear boundaries.

---

# 35. Retrieval Failure Handling

The pipeline should handle cases such as:

### No results

```text
No relevant chunks found.
```

### Weak results

```text
Results exist, but none pass threshold.
```

### Database failure

```text
Vector search failed.
```

### Embedding failure

```text
Query embedding could not be generated.
```

### Provider failure

```text
LLM unavailable.
```

Each should have a controlled behavior.

---

# 36. Don't Hide Retrieval Failures

Bad:

```text
Vector search failed
      ↓
Call LLM anyway
```

The LLM may answer from its general training.

Better:

```text
Vector search failed
      ↓
Return controlled error
```

or:

```text
No sufficient course context found
```

depending on the failure.

This helps preserve the core RAG promise:

> **The AI Tutor should ground course-specific answers in course-specific knowledge.**

---

For debugging, we should eventually record:

```text
query
courseId
lessonId
retrievedChunkIds
distances
numberOfCandidates
numberAfterThreshold
finalContextTokens
```

For example:

```text
Query:
"What is 3NF?"

Candidates:
20

After threshold:
8

Final chunks:
5

Context tokens:
2,900
```

This information is incredibly useful when debugging bad answers.

Eventually, one AI Tutor request could produce a trace like:

```text
  ├── Query understanding
```

> Why is the AI Tutor slow?

instead of guessing.

# 39. Retrieval Evaluation

We should test the retrieval pipeline independently from the LLM.

Create a test dataset:

```text
Question                         Expected Source
--------------------------------------------------
What is 1NF?                    Normalization/1NF
What is 2NF?                    Normalization/2NF
What is 3NF?                    Normalization/3NF
What is a foreign key?          Relational Model
What is an index?               Indexing
```

Then test:

```text
Question
   ↓
Retriever
   ↓
Top-K
```

and measure whether the expected source appears.

---

# 40. Useful Retrieval Metrics

Some useful metrics include:

```text
Recall@K
Precision@K
MRR
nDCG
```

For now, focus on:

```text
Recall@K
```

Example:

```text
100 questions
```

and the correct chunk appears in:

```text
Top 5 → 91 questions
```

Then:

```text
Recall@5 = 91%
```

That's a useful baseline.

---

# 41. Why Retrieval Quality Comes Before LLM Quality

Imagine:

```text
Retriever Recall@5 = 40%
```

and:

```text
LLM = excellent
```

The LLM can't answer correctly if it never receives the right information.

But:

```text
Retriever Recall@5 = 95%
```

gives the LLM much better evidence.

So:

```text
Good Retrieval
      ↓
Good Context
      ↓
Better Generation
```

This is why RAG engineering isn't simply "connect an LLM to a vector database."

# 43. A Practical First Version

Don't try to implement every advanced technique immediately.

For our first working AI LMS, I recommend:

```text
1. Authenticate user
2. Check course access
3. Generate query embedding
4. Search permitted READY chunks
5. Retrieve Top-K
6. Apply a tested relevance threshold
7. Remove duplicate chunk IDs
8. Sort selected chunks by document position
9. Respect a token budget
10. Build context
11. Send context to LLM
```

That's already a strong foundation.

Later we can add:

```text
Hybrid Search
Query Rewriting
MMR
Reranking
Semantic Deduplication
Context Compression
```

# 45. The Most Important Concept

Don't think:

```text
RAG = Vector Database
```

Think:

```text
RAG =
    Query Understanding
  + Access Control
  + Retrieval
  + Ranking
  + Context Selection
  + Generation
```

The vector database is only one component.

# 🧠 Lesson 8.8 Cheat Sheet

```text
Retrieval Pipeline
→ Complete process of turning a user question
  into useful context for the LLM.

Query Understanding
→ Determine what the student is asking.

Access Control
→ Determine which knowledge the student can access.

Metadata Filtering
→ Restrict search to relevant/allowed content.

Candidate Retrieval
→ Retrieve potentially useful chunks.

Top-K
→ Number of candidates returned.

Threshold
→ Remove weakly relevant candidates.

Deduplication
→ Remove repeated content.

Context Expansion
→ Retrieve neighboring chunks when useful.

Context Budget
→ Maximum amount of information sent to the LLM.

Context Selection
→ Choose the most useful chunks.

Context Builder
→ Convert retrieved chunks into structured LLM context.

Recall@K
→ Measures whether relevant information appears
  within the top K results.
```

