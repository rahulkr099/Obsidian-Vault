# Lesson 9.10 — Instructor Review

The Phase 9 roadmap defines **9.10 as “Instructor Review”**, after question validation and before AI explanations.

This lesson completes an important part of the AI assessment pipeline:

```text
AI generates questions
        ↓
Question validation
        ↓
Instructor review
        ↓
Publish
        ↓
Students attempt quiz
```

The key idea is:

> **AI should generate and validate assessment content, but the instructor should have the final authority to approve it.**

---

# 1. Why Instructor Review Is Needed

Even after all our validation from 9.9, an AI-generated question can still be unsuitable.

For example:

> Which database is the best database?

It might pass some technical checks, but an instructor may decide:

```text
❌ Too subjective
❌ Not useful for this lesson
```

Or:

> What is PostgreSQL?

The instructor might say:

```text
❌ Too easy for this advanced quiz
```

So the final pipeline becomes:

```text
AI
 ↓
Automatic Validation
 ↓
Instructor
 ↓
Final Decision
```

This gives us a **human-in-the-loop assessment system**.

---

# 2. Human-in-the-Loop

The concept is simple:

```text
AI
 ↓
Suggestion
 ↓
Human Review
 ↓
Decision
```

The AI doesn't own the assessment.

The instructor does.

This is especially important because educational content can affect:

- student grades
    
- course completion
    
- certificates
    
- learning progress
    

Therefore, the instructor should be able to override AI-generated content.

---

# 3. Review Status

A generated question should have a lifecycle.

For example:

```ts
type QuestionReviewStatus =
  | "DRAFT"
  | "APPROVED"
  | "REJECTED";
```

Flow:

```text
DRAFT
  ↓
Instructor reviews
  ↓
┌───────────────┐
↓               ↓
APPROVED       REJECTED
```

We can later add:

```text
NEEDS_REVISION
```

if the instructor wants to modify the question instead of completely rejecting it.

---

# 4. A Better Lifecycle

For the full assessment system, I'd recommend thinking about several states:

```text
GENERATED
    ↓
VALIDATING
    ↓
DRAFT
    ↓
INSTRUCTOR_REVIEW
    ↓
APPROVED
    ↓
PUBLISHED
```

Rejected path:

```text
INSTRUCTOR_REVIEW
       ↓
   REJECTED
```

Revision path:

```text
INSTRUCTOR_REVIEW
       ↓
NEEDS_REVISION
       ↓
EDITED
       ↓
INSTRUCTOR_REVIEW
```

This is much more realistic than simply:

```text
draft → published
```

---

# 5. Question vs Quiz Review

There are actually two things the instructor may review:

### Individual question

```text
Question
 ↓
Approve / Reject / Edit
```

### Entire quiz

```text
Quiz
 ↓
Review all questions
 ↓
Approve quiz
 ↓
Publish
```

For example:

```text
Quiz
├── Q1 ✅
├── Q2 ✅
├── Q3 ❌
├── Q4 ✅
└── Q5 ✅
```

The instructor might reject Q3 and regenerate it.

---

# 6. What Should the Instructor See?

The instructor doesn't need to see the entire internal AI pipeline.

A useful review screen might show:

```text
┌─────────────────────────────────────────┐
│ Question Review                          │
├─────────────────────────────────────────┤
│ Difficulty: Medium                      │
│ Type: MCQ                               │
│                                         │
│ What does map() return?                 │
│                                         │
│ ○ A new array                           │
│ ○ The original array                   │
│ ○ A string                              │
│ ○ A boolean                             │
│                                         │
│ Correct Answer: A                       │
│                                         │
│ Explanation:                            │
│ map() returns a new array...            │
│                                         │
│ AI Validation: ✓ Passed                 │
│                                         │
│ [Edit] [Approve] [Reject]               │
└─────────────────────────────────────────┘
```

The instructor gets enough information to make a decision quickly.

---

# 7. Show Validation Information

Since Lesson 9.9 already validates the question, we can show a small quality summary:

```text
Validation
──────────
✓ Schema valid
✓ Options valid
✓ Grounded in lesson
✓ No duplicate detected
✓ Difficulty: Medium
```

This helps the instructor trust the generated question.

But don't overwhelm them with:

```text
embedding vectors
LLM prompts
internal model tokens
raw validation JSON
```

Those are internal system details.

---

# 8. Instructor Should Be Able to Edit

Approval shouldn't be the only option.

Suppose AI generates:

> What does the `map` method do?

The instructor might prefer:

> What does the JavaScript `map()` method return, and how does it process each element?

Instead of rejecting the entire question:

```text
[Edit]
```

allows the instructor to improve it.

So the workflow becomes:

```text
AI Question
    ↓
Instructor
    ↓
┌─────────┬─────────┬──────────┐
↓         ↓         ↓
Approve   Edit     Reject
```

---

# 9. Editing Is Better Than Regenerating Sometimes

Imagine the AI question is 90% correct.

Only the wording is weak.

Regenerating creates another AI request:

```text
AI
 ↓
New question
 ↓
Validate
 ↓
Maybe another problem
```

Editing may be much faster.

Example:

AI:

> What is the use of PostgreSQL transactions?

Instructor:

> Why are PostgreSQL transactions useful when multiple related operations must succeed together?

Same concept, much better wording.

---

# 10. Important: Track Who Changed What

If the instructor edits an AI-generated question, we should know:

```text
Generated by:
AI

Modified by:
Instructor

Approved by:
Instructor
```

This is important for auditing.

Conceptually:

```text
Question
├── generatedAt
├── generatedBy = AI
├── updatedAt
├── updatedBy = instructor
├── reviewedAt
└── reviewedBy = instructor
```

The exact database structure can be finalized later.

---

# 11. Audit History

Suppose the question changes several times:

```text
Version 1
AI generated

Version 2
Instructor edited

Version 3
Instructor corrected answer

Version 4
Instructor approved
```

A good system can preserve that history.

For example:

```text
Question History

v1 → Generated by AI
v2 → Edited by Rahul
v3 → Correct answer changed
v4 → Approved
```

This is especially useful when something goes wrong later.

---

# 12. Why Auditability Matters

Imagine a student says:

> "The answer key was wrong."

The instructor should be able to investigate:

```text
Question
 ↓
Who created it?
 ↓
Who edited it?
 ↓
Who approved it?
 ↓
What was the original answer?
```

Without history, debugging becomes much harder.

---

# 13. Approval Is Not the Same as Publishing

This distinction is important.

### Approved

Instructor says:

> This question is ready.

### Published

The question becomes available to students.

So:

```text
DRAFT
 ↓
APPROVED
 ↓
PUBLISHED
```

Why separate them?

Because an instructor might approve questions while the quiz itself is still being prepared.

---

# 14. Quiz Publishing

Suppose the instructor generates:

```text
10 questions
```

Then:

```text
Q1 → Approved
Q2 → Approved
Q3 → Approved
...
Q10 → Approved
```

Only then:

```text
Quiz
 ↓
Publish
```

The system should prevent:

```text
Quiz Published
    ↓
Contains rejected/draft questions
```

unless your business rules explicitly allow it.

---

# 15. Publication Rules

A quiz could require:

```text
All questions approved
```

before publishing.

For example:

```ts
const canPublish =
  questions.length > 0 &&
  questions.every(
    q => q.reviewStatus === "APPROVED"
  );
```

If:

```text
Q1 APPROVED
Q2 APPROVED
Q3 DRAFT
```

then:

```text
canPublish = false
```

The instructor needs to resolve Q3.

---

# 16. Instructor Authorization

Only the correct instructor should be allowed to review a question.

Suppose:

```text
Instructor A
   ↓
Course A
   ↓
Quiz A
```

Instructor B shouldn't be able to:

```http
PATCH /api/v1/quizzes/quiz-A/questions/q1
```

just because they know the ID.

The backend must verify ownership/permission:

```text
Authenticated user
       ↓
Instructor?
       ↓
Owns course?
       ↓
Owns quiz?
       ↓
Can review?
```

This connects directly to the authorization concepts you'll revisit in Phase 14.

---

# 17. Don't Trust the Frontend Role

A malicious user could modify:

```json
{
  "role": "INSTRUCTOR"
}
```

in the browser.

So never rely on:

```text
React state
```

for authorization.

The backend should determine:

```text
Who is this user?
What role do they have?
What resource do they own?
What action are they allowed to perform?
```

---

# 18. Review API

A possible endpoint:

```http
PATCH /api/v1/questions/:questionId/review
```

Request:

```json
{
  "action": "APPROVE"
}
```

Or:

```json
{
  "action": "REJECT",
  "reason": "Question is ambiguous."
}
```

Or:

```json
{
  "action": "EDIT",
  "question": {
    "text": "Updated question..."
  }
}
```

But I'd keep actions separate rather than creating one giant endpoint if the operations become complex.

For example:

```http
POST /questions/:id/approve
POST /questions/:id/reject
PATCH /questions/:id
```

This can make authorization and audit behavior clearer.

---

# 19. Rejection Reason

When rejecting a question, ask for a reason.

For example:

```json
{
  "action": "REJECT",
  "reason": "Two options are arguably correct."
}
```

Possible reasons:

```text
AMBIGUOUS
INCORRECT
IRRELEVANT
TOO_EASY
TOO_HARD
DUPLICATE
POOR_WORDING
NOT_GROUNDED
OTHER
```

This data can become valuable later.

---

# 20. Rejection Can Improve the System

Suppose instructors frequently reject AI questions because:

```text
POOR_WORDING → 35%
TOO_EASY → 25%
AMBIGUOUS → 20%
DUPLICATE → 10%
OTHER → 10%
```

Now you know where the generation pipeline needs improvement.

You could improve:

```text
generation prompts
validation rules
difficulty instructions
duplicate detection
```

This creates a feedback loop:

```text
AI
 ↓
Generate
 ↓
Validate
 ↓
Instructor Review
 ↓
Rejection Data
 ↓
Improve Generation
```

That's a very useful long-term design.

---

# 21. Review Comments

An instructor might want to leave:

> "Good concept, but make the distractors more realistic."

So a review can contain:

```text
reviewerId
status
comment
createdAt
```

Example:

```json
{
  "status": "NEEDS_REVISION",
  "comment": "Make option C less obviously incorrect."
}
```

Then someone can revise the question.

---

# 22. Revision Workflow

A good workflow:

```text
DRAFT
 ↓
INSTRUCTOR_REVIEW
 ↓
NEEDS_REVISION
 ↓
EDIT
 ↓
VALIDATE AGAIN
 ↓
INSTRUCTOR_REVIEW
 ↓
APPROVED
```

Notice something important:

> **After editing, validate the question again.**

Don't assume instructor edits automatically make it valid.

---

# 23. Why Revalidation Matters

Suppose the original MCQ is:

```text
A. map()
B. filter()
C. push()
D. pop()
```

Instructor edits option B:

```text
B. map()
```

Now:

```text
A = map()
B = map()
```

The instructor accidentally introduced a duplicate.

Therefore:

```text
Edit
 ↓
Validation
 ↓
Approval
```

not:

```text
Edit
 ↓
Directly publish
```

---

# 24. AI-Generated vs Instructor-Edited

We should preserve the distinction.

For example:

```text
source = AI
```

initially.

After editing:

```text

```

This is useful for analytics.

You might later discover:

```text
AI-only questions:
72% approved immediately

AI-edited questions:
28%

AI-rejected questions:
10%
```

That tells you how effective your generation system is.

# 27. Bulk Review

Suppose AI generates:

```text
50 questions
```

Reviewing them individually could be painful.

You can eventually support:

```text
Select Q1-Q10
       ↓
Approve Selected
```

But be careful.

Bulk approval is powerful and risky.

A safer rule might be:

```text
Bulk approve only questions
that have passed all validations.
```

And perhaps still require confirmation.

# 28. Instructor Review + Validation

The combined pipeline is:

```text
                     AI
                      ↓
                Generate Quiz
                      ↓
               Auto Validation
                      ↓
            ┌─────────┴─────────┐
            ↓                   ↓
          PASS                 FAIL
            ↓                   ↓
        Instructor          Regenerate
          Review
            ↓
      ┌─────┼──────┐
      ↓     ↓      ↓
   Approve Edit  Reject
      ↓     ↓
      │   Validate
      │     ↓
      │   Review
      │
      └──────→ Publish
```

This is the core architecture of 9.10.

---

# 29. What About AI Reviewing Its Own Question?

We already have automatic validation.

You could have:

```text
Generator AI
    ↓
Validator AI
    ↓
Instructor
```

This is useful.

But don't do:

```text
Generator AI
    ↓
Same model
    ↓
"Is your question correct?"
    ↓
Yes
```

That doesn't provide much independence.

A separate validation stage with explicit criteria is better.

And even then:

> **Instructor review remains the final quality gate.**

# 30. Database Design Concept

At a high level, you could have:

```text
Question
├── id
├── quizId
├── type
├── text
├── difficulty
├── reviewStatus
├── generatedAt
├── approvedAt
├── approvedBy
└── ...
```

And a separate review history:

```text
QuestionReview
├── id
├── questionId
├── reviewerId
├── action
├── comment
└── createdAt
```

Why separate `QuestionReview`?

Because one question can have multiple reviews:

```text
Review 1 → NEEDS_REVISION
Review 2 → APPROVED
```

You preserve the history instead of overwriting it.

# 31. Review Actions

A clean enum could be:

```prisma
enum ReviewAction {
  APPROVE
  REJECT
  REQUEST_REVISION
}
```

And status:

```prisma
enum ReviewStatus {
  DRAFT
  IN_REVIEW
  NEEDS_REVISION
  APPROVED
  REJECTED
  PUBLISHED
}
```

Don't necessarily create every enum immediately; the exact schema should follow your final assessment workflow.

The important architectural idea is:

```text
Current status
+
Historical review actions
```

# 32. Instructor Review and Transactions

Approval changes important assessment state.

For example:

```text
Question status
Quiz status
Audit record
```

These related changes should be handled carefully.

For example:

```text
BEGIN
  update question status
  create review record
  create audit event
COMMIT
```

If one operation fails:

```text
ROLLBACK
```

This prevents inconsistent states.

---

# 33. Prevent Editing Published Questions Carelessly

Suppose:

```text
Quiz published
 ↓
Students already attempted it
```

Now an instructor changes:

```text
correctAnswer
```

This could completely change the historical meaning of previous attempts.

So published assessment content needs special handling.

Possible policy:

```text
PUBLISHED
 ↓
Locked
```

If modification is necessary:

```text
Create new version
```

rather than silently changing the existing question.

This is a very important production-level assessment concept.

---

# 34. Question Versioning

Imagine:

```text
Question v1
"What does map() return?"
```

Later:

```text
Question v2
"What does map() return and how does it process each element?"
```

Existing attempt:

```text
Attempt 1 → Question v1
```

New attempt:

```text
Attempt 2 → Question v2
```

Now historical results remain accurate.

Conceptually:

```text
Question
 ├── Version 1
 ├── Version 2
 └── Version 3
```

You don't necessarily need to implement sophisticated versioning immediately, but your architecture should not make it impossible.

# 40. Review API Architecture

A clean backend architecture might look like:

```text
review.controller.ts
        ↓
review.service.ts
        ↓
authorization
        ↓
question repository
        ↓
validation service
        ↓
review repository
        ↓
audit service
```

The controller should remain thin.

For example:

```ts
async function approveQuestion(
  req,
  res
) {
  const result =
    await reviewService.approveQuestion({
      questionId: req.params.questionId,
      instructorId: req.user.userId,
    });

  return res.json(result);
}
```

Business rules remain inside the service.

---

# 41. Authorization Checks

Inside the service:

```text
Question exists?
      ↓
Quiz exists?
      ↓
Course exists?
      ↓
Instructor owns course?
      ↓
Question is reviewable?
      ↓
Approve
```

This is much safer than simply:

```text
PATCH question WHERE id = ...
```

---

# 42. Review State Machine

A useful way to think about the workflow is as a state machine:

```text
                 ┌──────────────┐
                 │    DRAFT     │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │  IN_REVIEW   │
                 └──────┬───────┘
                    ┌───┼────┐
                    ↓   ↓    ↓
               APPROVED  │  REJECTED
                    │    │
                    │    ↓
                    │ NEEDS_REVISION
                    │    │
                    │    ↓
                    │   EDIT
                    │    │
                    │    ↓
                    │ IN_REVIEW
                    │
                    ↓
                 PUBLISHED
```

The application should explicitly control which transitions are allowed.

For example:

```text
REJECTED → PUBLISHED
```

should not be allowed directly.

---

# 43. State Transition Validation

Instead of:

```ts
question.status = "PUBLISHED";
```

from anywhere, use a controlled service:

```ts
transitionQuestionStatus(
  question,
  "PUBLISHED"
);
```

The service checks:

```text
Current status?
Target status?
Allowed transition?
Required permissions?
```

This prevents invalid states.

# 45. The Instructor Is the Final Quality Gate

This is the biggest lesson.

Your AI pipeline:

```text
Generate
 ↓
Validate
 ↓
Review
```

doesn't mean:

```text

```

```text

 ↓
System validates
 ↓
Instructor decides
```

That's a much stronger design for an educational platform.

# 🧠 Key Takeaways

### 1. Instructor review is the human quality gate

```text
AI
 ↓
Validation
 ↓
Instructor
 ↓
Publish
```

### 2. Give instructors three important actions

```text
Approve
Edit
Reject
```

And optionally:

```text
Request Revision
```

### 3. Revalidate after editing

```text
Edit
 ↓
Validate again
 ↓
Approve
```

### 4. Keep review history

Don't only store:

```text
status = APPROVED
```

Also preserve:

```text
who
what
when
why
```

### 5. Separate approval from publishing

```text
APPROVED
   ↓
PUBLISHED
```

### 6. Protect review endpoints with authorization

The backend must verify:

```text
Instructor
+
Course ownership
+
Quiz ownership
+
Permission
```

### 7. Published assessments need protection

Changing a question after students have attempted it can affect historical results.

Consider:

```text
versioning
or
locking
```

### 8. Instructor feedback can improve AI

```text
AI
 ↓
Instructor Review
 ↓
Rejection / Revision Data
 ↓
Better Prompts + Validation
 ↓
Better Questions
```
