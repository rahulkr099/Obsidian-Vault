# Lesson 9.5 — Short Answer Questions

According to the Phase 9 roadmap, **9.5 is “Short Answer”**. It comes after MCQs and True/False questions, and before difficulty levels.

Short-answer questions are more challenging than MCQs because the student has to **produce the answer themselves** instead of selecting from predefined options.

---

## 1. What Is a Short-Answer Question?

Example:

> **What does the JavaScript `map()` method return?**

Student might answer:

```text
A new array containing the results
of calling a function on each element.
```

Unlike an MCQ:

```text
A. A new array
B. A string
C. A boolean
D. The original array
```

there are no predefined choices.

Our system therefore needs to deal with:

```text
Question
   ↓
Student's free-text answer
   ↓
AI / evaluation logic
   ↓
Score
```

This makes short-answer assessment much more interesting.

---

# 2. Why Short Answers Are Harder

For MCQ:

```text
Student answer
      ↓
Compare with correct option
      ↓
Correct / Incorrect
```

For short answer:

```text
Student answer
      ↓
"map() returns a new array..."
      ↓
What does this mean?
      ↓
Does it satisfy the expected answer?
```

Two students could write:

```text
Student A:
"map returns a new array."

Student B:
"map creates another array by applying
a function to every item."
```

Both can be correct even though their exact strings are different.

Therefore:

> **We cannot rely on simple string matching.**

---

# 3. Basic Data Model

A short-answer question could look like:

```ts
type ShortAnswerQuestion = {
  type: "SHORT_ANSWER";
  question: string;
  expectedAnswer: string;
  keyPoints: string[];
  explanation: string;
  difficulty: "EASY" | "MEDIUM" | "HARD";
};
```

For example:

```json
{
  "type": "SHORT_ANSWER",
  "question": "What does the map() method return?",
  "expectedAnswer": "A new array containing the transformed values.",
  "keyPoints": [
    "returns a new array",
    "applies a function to each element"
  ],
  "explanation": "map() creates a new array by applying a callback to each element."
}
```

Notice something important:

```text
expectedAnswer
+
keyPoints
```

This gives the evaluator more information than one model answer.

---

# 4. Why Key Points Matter

Suppose the expected answer is:

> `map()` returns a new array containing the transformed values.

A student writes:

> `It creates another array from the original array.`

A simple string comparison might say:

```text
❌ Different
```

But semantically, it could be correct.

If we have:

```json
{
  "keyPoints": [
    "returns a new array",
    "transforms elements"
  ]
}
```

we can evaluate whether the student demonstrated those concepts.

---

# 5. Short Answer Generation

Our generation pipeline becomes:

```text
Lesson Content
      ↓
Learning Objective
      ↓
AI Question Generator
      ↓
Short-Answer Question
      ↓
Expected Answer
      ↓
Key Points
      ↓
Validation
      ↓
Database
```

The AI shouldn't generate only:

```text
question
```

It should generate the information needed to evaluate that question later.

---

# 6. Prompt Design

A simplified prompt could be:

```text
You are an educational assessment generator.

Generate a short-answer question using only
the provided lesson content.

Requirements:

- The question must have a clear expected answer.
- The answer should require the student to explain
  or describe a concept.
- Provide an expected answer.
- Provide the key concepts required for a correct answer.
- Avoid questions with many equally valid interpretations.
- Do not introduce information outside the lesson.
```

Then:

```text
LESSON CONTENT

...
```

The output should be structured.

---

# 7. Example Generated Question

```json
{
  "type": "SHORT_ANSWER",
  "question": "Why does map() return a new array?",
  "expectedAnswer": "map() applies a callback to each element and returns a new array containing the resulting values.",
  "keyPoints": [
    "callback is applied to each element",
    "a new array is returned",
    "resulting values are stored in the new array"
  ],
  "explanation": "map() does not use the original array as the returned result."
}
```

This is much more useful than:

```json
{
  "question": "Explain map()."
}
```

---

# 8. Keep Questions Focused

A bad short-answer question:

> Explain everything you know about JavaScript arrays.

That's too broad.

The evaluator would have difficulty deciding:

```text
What exactly should the student mention?
```

A better question:

> What is the difference between `map()` and `filter()`?

Now we can define expected concepts:

```text
map()
→ transforms elements

filter()
→ selects elements based on a condition

both
→ return a new array
```

This makes evaluation much easier.

---

# 9. Expected Answer vs Exact Answer

This is one of the most important ideas in this lesson.

Don't design the system like:

```ts
studentAnswer === expectedAnswer
```

For example:

```text
Expected:
"map() returns a new array."

Student:
"The map method creates another array."
```

Exact comparison:

```text
❌ false
```

Semantic comparison:

```text
✅ likely correct
```

So short-answer evaluation will eventually require **semantic understanding**.

That will be covered specifically in **Lesson 9.7 — AI Answer Evaluation**.

---

# 10. Normalize Before Evaluation

Before sending a student answer to an evaluator, we can perform basic normalization.

For example:

```text
"Map() returns a new array."
```

could be normalized to:

```text
"map returns a new array"
```

Possible normalization steps:

```text
trim whitespace
lowercase
remove unnecessary punctuation
normalize repeated spaces
```

But be careful.

We shouldn't aggressively modify the student's answer because punctuation or formatting might sometimes matter.

Normalization is only a preprocessing step.

It is **not** a replacement for semantic evaluation.

---

# 11. Example

Student submits:

```text
"map returns a NEW array."
```

Expected:

```text
"map() returns a new array."
```

After simple normalization:

```text
map returns a new array
```

Both are essentially the same.

But consider:

```text
Student:
"map changes the original array."
```

This is not just a formatting difference.

It's a conceptual difference.

That's where semantic evaluation becomes necessary.

---

# 12. Key-Point Based Evaluation

Suppose we have:

```json
{
  "keyPoints": [
    "returns a new array",
    "callback is applied to each element"
  ]
}
```

Student answer:

> `map()` runs a function for every element and gives us another array containing the results.

We can identify:

```text
✓ callback/function applied to elements
✓ new array
```

So the answer demonstrates the required understanding.

---

# 13. Partial Credit

Short answers naturally support partial credit.

Suppose the question is:

> Explain the difference between `map()` and `filter()`.

Expected concepts:

```text
map()
→ transforms each element

filter()
→ selects elements based on condition
```

Student answers:

> `map()` transforms elements.

The student has demonstrated:

```text
✓ map()
✓ transformation
✗ filter()
✗ comparison
```

So instead of:

```text
0 / 1
```

we could eventually give:

```text
0.5 / 1
```

This is one reason short-answer evaluation is more advanced than MCQ scoring.

---

# 14. Don't Let the AI Decide Everything

This is important.

A dangerous architecture would be:

```text
Student Answer
      ↓
AI
      ↓
"Correct"
      ↓
Give 100%
```

We shouldn't blindly trust that.

Instead:

```text
Student Answer
      ↓
Preprocessing
      ↓
Evaluation
      ↓
Validation / Rules
      ↓
Score
      ↓
Stored Result
```

The AI can assist with semantic evaluation, but your application should define the scoring rules.

---

# 15. A Better Evaluation Result

Eventually, the evaluator could produce something like:

```json
{
  "score": 0.8,
  "maxScore": 1,
  "correct": true,
  "matchedKeyPoints": [
    "returns a new array",
    "callback is applied to each element"
  ],
  "missingKeyPoints": [],
  "feedback": "Good explanation. You correctly described how map() processes each element and returns a new array."
}
```

Or for a partial answer:

```json
{
  "score": 0.5,
  "maxScore": 1,
  "correct": false,
  "matchedKeyPoints": [
    "map transforms elements"
  ],
  "missingKeyPoints": [
    "filter selects elements based on a condition"
  ],
  "feedback": "You correctly explained map(), but you did not explain how filter() differs."
}
```

This will become much more relevant in **9.7**.

---

# 16. Question Types Within Short Answer

"Short answer" can mean different things.

### Definition

> What is a database index?

### Explanation

> Why are indexes useful?

### Comparison

> What is the difference between SQL and NoSQL?

### Process

> Explain the steps involved in a database transaction.

### Code understanding

> What will this function return?

We don't necessarily need separate database types for every variation.

We can have:

```text
SHORT_ANSWER
```

and optionally metadata:

```ts
type ShortAnswerSubtype =
  | "DEFINITION"
  | "EXPLANATION"
  | "COMPARISON"
  | "PROCESS"
  | "CODE";
```

This could improve analytics and generation later.

---

# 17. Keep the Expected Answer Reasonably Short

Remember the purpose:

```text
SHORT ANSWER
```

not:

```text
ESSAY
```

A good question might expect:

```text
1–3 sentences
```

rather than:

```text
500-word explanation
```

We can include an expected answer length in the generation configuration.

For example:

```ts
type ShortAnswerConfig = {
  maxWords?: number;
  minWords?: number;
};
```

But this is a guideline, not an absolute rule.

A student should not be marked wrong merely because they used fewer words while still demonstrating the required understanding.

---

# 18. Word Limits Are Also Useful for Cost Control

Imagine someone generates:

```text
100 short-answer questions
```

and each expected answer is:

```text
1000 words
```

That is wasteful.

We can define sensible generation limits:

```text
questionCount
answerLength
```

This controls:

```text
AI cost
database size
evaluation cost
response time
```

This is another place where application-level controls matter.

---

# 19. Prevent Unanswerable Questions

AI could generate:

> What would happen if JavaScript were redesigned tomorrow?

That's not a useful assessment question.

The answer isn't grounded in the lesson.

Our generation rules should require:

```text
Question must be answerable
using the provided lesson material.
```

So:

```text
Lesson
 ↓
Question
 ↓
Can student answer from lesson?
 ↓
Yes → continue
No  → reject/regenerate
```

This becomes even stronger once we use RAG grounding.

---

# 20. Short Answer + RAG

Our Phase 8 RAG system can help here.

Instead of:

```text
Course
 ↓
AI
 ↓
Question
```

we can eventually use:

```text
Lesson
 ↓
Relevant chunks
 ↓
Learning concepts
 ↓
AI
 ↓
Short-answer question
```

For example:

```text
Retrieved context:

"PostgreSQL transactions allow multiple database
operations to execute as a single logical unit."
```

AI could generate:

> What is the purpose of a database transaction?

Expected answer:

> A transaction groups database operations into one logical unit so they can succeed or fail together.

This is grounded in actual course material.

# 21. Database Considerations

A short-answer question might eventually be represented as:

```text
Question
├── id
├── quizId
├── type
├── text
├── expectedAnswer
├── explanation
└── difficulty
```

And possibly:

```text
QuestionKeyPoint
├── id
├── questionId
└── text
```

This gives us:

```text
Question
   ↓
Key Points
   ├── Concept A
   ├── Concept B
   └── Concept C
```

This can be useful for detailed evaluation.

However, we'll make the final Prisma/PostgreSQL design based on the complete assessment requirements rather than locking it in prematurely.

---

# 22. Student Attempt Model

When a student answers:

```text
Question
   ↓
Student Attempt
   ↓
Student Answer
```

For example:

```json
{
  "questionId": "q_123",
  "answer": "map returns a new array containing the transformed values."
}
```

The system can later store:

```text
studentAnswer
score
maxScore
evaluationStatus
feedback
evaluatedAt
```

This is important because AI evaluation may not always happen instantly.

---

# 23. Synchronous vs Asynchronous Evaluation

For MCQ:

```text
Student submits
      ↓
Immediate comparison
      ↓
Score
```

For short answer:

```text
Student submits
      ↓
AI evaluation
      ↓
Potentially slower
      ↓
Score
```

So eventually we may have:

```text
SUBMITTED
    ↓
EVALUATING
    ↓
EVALUATED
```

This becomes particularly useful if AI evaluation is moved to a background worker in Phase 11.

---

# 24. Don't Show Evaluation Details Too Early

Suppose the student submits an answer.

We shouldn't immediately expose internal evaluation metadata like:

```text
matchedKeyPoints
model
evaluationPrompt
confidence
```

The student needs something simple:

```text
Score: 0.8 / 1

Feedback:
Good answer. You correctly explained that
map() returns a new array.
```

Internal evaluation data should remain internal unless there's a clear reason to expose it.

# 25. Short Answer Generation Service

Our architecture remains consistent:

```text
quiz.controller.ts
        ↓
quiz.service.ts
        ↓
ai-question.service.ts
        ↓
AI Provider
```

Example interface:

```ts
interface AIQuestionService {
  generateMCQs(
    input: GenerateQuestionInput
  ): Promise<MCQQuestion[]>;

  generateTrueFalse(
    input: GenerateQuestionInput
  ): Promise<TrueFalseQuestion[]>;

  generateShortAnswers(
    input: GenerateQuestionInput
  ): Promise<ShortAnswerQuestion[]>;
}
```

This is much cleaner than putting AI logic into controllers.

---

# 26. A Complete Example

Suppose the lesson is:

```text
PostgreSQL transactions group multiple database
operations into a single logical unit. If a transaction
fails, changes can be rolled back.
```

AI generates:

### Question

> Why are database transactions useful?

### Expected answer

> They group multiple database operations into one logical unit so the changes can succeed or be rolled back together.

### Key points

```text
✓ groups multiple operations
✓ treats them as one logical unit
✓ supports rollback on failure
```

Now a student writes:

> Transactions allow several operations to be handled together, and if something fails, the changes can be rolled back.

This is clearly a good answer even though it doesn't match the expected answer word-for-word.

That's exactly why semantic evaluation matters.

# 27. Short Answer Quality Checklist

Before accepting a generated question:

```text
□ Question is relevant to lesson
□ Question has a clear expected answer
□ Question is not overly broad
□ Expected answer is supported by lesson content
□ Key concepts are defined
□ Question isn't ambiguous
□ Question isn't subjective
□ Expected answer isn't unnecessarily long
□ Explanation is valid
□ Difficulty is appropriate
□ No duplicate question
```

We'll later move most of these checks into the dedicated **9.9 Question Validation** system.

---

# 28. MCQ vs True/False vs Short Answer

Now our three question types look like this:

|Type|Student does|Main evaluation|
|---|---|---|
|**MCQ**|Selects an option|Exact answer|
|**True/False**|Selects true/false|Boolean comparison|
|**Short Answer**|Writes an answer|Semantic evaluation|

The complexity increases:

```text
MCQ
 ↓
True/False
 ↓
Short Answer
```

Not necessarily because short answers are harder to generate, but because **evaluating free-form answers is much harder**.

# 🧠 Key Takeaways

### 1. Short answers cannot use simple string comparison

```text
❌ studentAnswer === expectedAnswer
```

We need semantic evaluation.

### 2. Generate more than just the question

A useful generated object contains:

```text
question
expectedAnswer
keyPoints
explanation
difficulty
```

### 3. Keep questions focused

Avoid:

> "Explain everything about JavaScript."

Prefer:

> "What is the difference between `map()` and `filter()`?"

### 4. Key points make evaluation easier

```text
Expected Answer
      +
Key Points
      ↓
Better Evaluation
```

### 5. AI should not directly determine the final score

Use:

```text
Student Answer
      ↓
AI Evaluation
      ↓
Application Scoring Rules
      ↓
Final Result
```

### 6. Ground the question in course content

```text
Lesson
 ↓
RAG Context
 ↓
AI
 ↓
Question
```

### 7. Short answers open the door to partial credit

```text
0
0.25
0.5
0.75
1.0
```

depending on your scoring design.
