# Lesson 9.6 — Difficulty Levels

The Phase 9 roadmap defines **9.6 specifically as “Difficulty Levels”**.

So far, we've built three question types:

```text
9.3 → MCQ
9.4 → True / False
9.5 → Short Answer
```

Now we need a system that can tell the difference between:

```text
Easy
Medium
Hard
```

The important point is:

> **Difficulty should represent the cognitive challenge of a question, not simply how complicated the wording looks.**

---

# 1. Why Difficulty Matters

Imagine these two questions:

### Question A

> What does `map()` return?

```text
Difficulty → Easy
```

### Question B

> Given an array of student scores, explain how you could use `map()` and `filter()` together to create a new array containing only adjusted scores above a certain threshold.

```text
Difficulty → Hard
```

Both are about JavaScript arrays, but they require very different levels of thinking.

Difficulty helps your LMS create:

```text
Beginner Quiz
Intermediate Quiz
Advanced Quiz
```

and later allows analytics such as:

```text
Student performs well on Easy
Student struggles with Hard
```

---

# 2. Start With Three Levels

For our first implementation:

```ts
type Difficulty =
  | "EASY"
  | "MEDIUM"
  | "HARD";
```

Keep it simple.

We don't need:

```text
VERY_EASY
EASY
LOW_MEDIUM
MEDIUM
HIGH_MEDIUM
HARD
VERY_HARD
EXTREME
```

Three levels are enough to build a useful first version.

---

# 3. Difficulty Is Not Question Type

Don't confuse:

```text
Question Type
```

with:

```text
Difficulty
```

For example:

```text
MCQ + EASY
MCQ + HARD

TRUE_FALSE + EASY
TRUE_FALSE + HARD

SHORT_ANSWER + EASY
SHORT_ANSWER + HARD
```

So our question model conceptually becomes:

```text
Question
├── type
├── difficulty
├── question
└── ...
```

Example:

```json
{
  "type": "MCQ",
  "difficulty": "MEDIUM",
  "question": "Which array method should be used to..."
}
```

---

# 4. What Makes a Question Easy?

An easy question generally requires:

```text
Recall
Recognition
Basic understanding
```

Example:

> Which method adds an element to the end of a JavaScript array?

```text
A. push()
B. pop()
C. shift()
D. unshift()
```

The student mainly needs to remember the concept.

### Typical Easy characteristics

```text
✓ Directly covered in lesson
✓ One main concept
✓ Little reasoning
✓ Familiar terminology
✓ Short/simple context
```

---

# 5. What Makes a Question Medium?

Medium questions require some:

```text
Understanding
Comparison
Application
Reasoning
```

Example:

> You want to create a new array containing only numbers greater than 50. Which method is most appropriate?

```text
A. map()
B. filter()
C. push()
D. pop()
```

The student needs to understand what the methods actually do.

### Typical Medium characteristics

```text
✓ Requires understanding
✓ May combine related concepts
✓ Requires some reasoning
✓ May involve a simple scenario
```

---

# 6. What Makes a Question Hard?

Hard questions require more:

```text
Analysis
Multiple concepts
Application
Problem solving
```

Example:

> You have an array of student scores. You need to increase every score by 10%, then keep only scores above 80. Explain which array operations you would use and why.

The student needs to reason about:

```text
map()
   ↓
transform scores

filter()
   ↓
select scores
```

### Typical Hard characteristics

```text
✓ Multiple concepts
✓ More reasoning
✓ Scenario-based
✓ Requires application
✓ May require explanation or comparison
```

---

# 7. Important Rule: Difficulty ≠ Length

This is a common mistake.

Consider:

> What does `map()` do?

Only five words.

Easy.

Now:

> Which method should you use when you want to create a new array containing only elements that satisfy a given condition?

Longer, but still potentially easy.

And:

> Given a dataset where each item contains nested student information, explain how you would transform the structure while preserving the original array and then select only records satisfying a condition.

Longer and more complex.

So:

```text
Long question ≠ Hard question
Short question ≠ Easy question
```

Difficulty comes from **thinking required**.

---

# 8. A Difficulty Model

We can think about difficulty using several dimensions:

```text
Difficulty
   │
   ├── Concept complexity
   ├── Reasoning required
   ├── Number of concepts
   ├── Context complexity
   ├── Ambiguity
   └── Application required
```

For example:

|Factor|Easy|Medium|Hard|
|---|---|---|---|
|Concepts|1|1–2|Multiple|
|Reasoning|Low|Moderate|High|
|Application|Low|Moderate|High|
|Context|Simple|Scenario|Complex|
|Recall|High|Medium|Low|

This isn't a mathematical formula yet. It's a useful framework for generating questions.

---

# 9. Difficulty Should Be Part of the Generation Request

When an instructor requests:

```json
{
  "difficulty": "HARD"
}
```

the AI should receive that requirement.

Conceptually:

```text
Instructor
    ↓
difficulty = HARD
    ↓
Quiz Service
    ↓
AI Question Service
    ↓
AI
```

The AI should not randomly decide:

```text
"Actually, I'll generate easy questions."
```

---

# 10. Prompting for Difficulty

We can tell the AI:

```text
Generate a HARD question.

The question should:
- require reasoning
- combine relevant concepts
- require application
- avoid simple memorization
- remain answerable using the provided lesson content
```

For medium:

```text
Generate a MEDIUM question.

The question should:
- test understanding
- require some reasoning
- use a simple practical scenario
- avoid purely factual recall
```

For easy:

```text
Generate an EASY question.

The question should:
- test basic understanding
- focus on one concept
- avoid complex reasoning
- remain directly answerable from the lesson
```

---

# 11. But Don't Blindly Trust the AI's Difficulty

This is extremely important.

Suppose we ask:

```text
Generate a HARD question.
```

The AI returns:

> What does `push()` do?

It may label it:

```text
HARD
```

But our application shouldn't blindly accept that.

We need:

```text
AI Difficulty
      ↓
Validation
      ↓
Application Decision
```

Later, we can build a more sophisticated difficulty validation system.

---

# 12. Difficulty Metadata

Our generated question could contain:

```json
{
  "type": "MCQ",
  "difficulty": "MEDIUM",
  "question": "...",
  "options": [],
  "correctAnswer": "...",
  "explanation": "..."
}
```

The database stores:

```text
difficulty = MEDIUM
```

Then we can query:

```text
Easy questions
Medium questions
Hard questions
```

This becomes useful for quiz generation.

---

# 13. Instructor Quiz Configuration

Imagine the instructor creates a quiz:

```json
{
  "title": "JavaScript Arrays Quiz",
  "questionCount": 10,
  "difficulty": "MEDIUM"
}
```

Our system generates:

```text
10 × MEDIUM
```

Or we can support a distribution:

```json
{
  "easy": 3,
  "medium": 5,
  "hard": 2
}
```

Then:

```text
Quiz
├── Easy × 3
├── Medium × 5
└── Hard × 2
```

This is much more useful than forcing every question to have the same difficulty.

---

# 14. Difficulty Distribution

A beginner quiz might use:

```text
Easy     → 70%
Medium   → 30%
Hard     → 0%
```

An intermediate quiz:

```text
Easy     → 30%
Medium   → 50%
Hard     → 20%
```

An advanced quiz:

```text
Easy     → 10%
Medium   → 40%
Hard     → 50%
```

These are examples, not fixed rules.

Your LMS can eventually let instructors customize the distribution.

---

# 15. Don't Make Difficulty Random

Avoid:

```ts
difficulty = random([
  "EASY",
  "MEDIUM",
  "HARD",
]);
```

That produces inconsistent quizzes.

Instead:

```text
Instructor configuration
        ↓
Generation blueprint
        ↓
AI
        ↓
Questions
```

The application controls the intended difficulty.

---

# 16. Difficulty and Question Type

Difficulty should work across all three question types.

### MCQ

```text
EASY
"What does push() do?"

MEDIUM
"Which method should you use for this situation?"

HARD
"Which combination of methods solves this problem?"
```

### True/False

```text
EASY
"push() adds elements to the end."

MEDIUM
"map() modifies the original array."

HARD
"A chain of operations produces a particular result."
```

### Short Answer

```text
EASY
"Define an array."

MEDIUM
"Explain the difference between map() and filter()."

HARD
"Explain how you would combine map() and filter()
to solve a particular problem."
```

Same difficulty concept, different question formats.

---

# 17. Difficulty and Cognitive Levels

A useful educational framework is to think in terms of cognitive work.

A simplified progression:

```text
Remember
   ↓
Understand
   ↓
Apply
   ↓
Analyze
```

We can roughly map this:

```text
EASY
→ Remember / basic Understand

MEDIUM
→ Understand / Apply

HARD
→ Apply / Analyze
```

This is more meaningful than saying:

```text
Hard = longer question
```

---

# 18. Example: Same Topic, Three Difficulties

Let's use PostgreSQL transactions.

### Easy

> What is a database transaction?

Tests:

```text
Recall
```

---

### Medium

> Why are transactions useful when multiple database operations must succeed together?

Tests:

```text
Understanding
```

---

### Hard

> A course enrollment process creates an enrollment record and updates the student's course count. Explain how a transaction can prevent the database from ending up in an inconsistent state if the second operation fails.

Tests:

```text
Application
+
Reasoning
```

Same topic.

Different cognitive demand.

---

# 19. Difficulty and RAG

Because our LMS already has RAG:

```text
Lesson
 ↓
Relevant chunks
 ↓
AI
```

we need to be careful that **hard questions remain grounded**.

Hard does not mean:

> "Ask something outside the lesson."

For example, if the lesson only teaches:

```text
PostgreSQL transactions
```

the AI shouldn't suddenly ask about:

```text
distributed two-phase commit
```

just because the instructor requested `HARD`.

So:

```text
HARD
≠
Outside the curriculum
```

Instead:

```text
Lesson knowledge
      +
Deeper reasoning
      ↓
Hard question
```

---

# 20. Difficulty and Hallucination

Consider this request:

```text
Generate a HARD question from this lesson.
```

The AI might think:

> "I'll add advanced information to make it harder."

That's dangerous.

We want:

```text
Hardness
    ↓
Reasoning complexity
```

not:

```text
Hardness
    ↓
Extra knowledge
```

This is one reason grounding with course content is important.

---

# 21. Difficulty Validation

Eventually, we can create a validation layer:

```text
Generated Question
       ↓
Structural Validation
       ↓
Content Validation
       ↓
Difficulty Validation
       ↓
Accept / Regenerate
```

For example:

```text
Requested:
HARD

Generated:
"What is map()?"

Evaluation:
Too simple

Result:
REJECT
```

Then:

```text
Generate replacement
```

This belongs conceptually with the broader validation work in **9.9**.

# 22. Difficulty and Student Performance

Once students start taking quizzes, difficulty becomes even more useful.

Suppose:

```text
Easy:
85% average

Medium:
72% average

Hard:
38% average
```

That tells us something.

But don't immediately conclude:

> "Students don't understand the topic."

Maybe:

```text
Hard questions are poorly written.
```

or:

```text
Hard questions are incorrectly classified.
```

This is why **difficulty analytics** need to be combined with question-quality analytics.

That becomes relevant in **9.12 — Assessment Analytics**.

# 23. Dynamic Difficulty — Later

Eventually, your LMS could become adaptive.

For example:

```text
Student
   ↓
Easy question
   ↓
Correct
   ↓
Medium question
   ↓
Correct
   ↓
Hard question
```

Or:

```text
Student
   ↓
Medium
   ↓
Incorrect
   ↓
Easy reinforcement
```

This becomes an **adaptive assessment system**.

We don't need to build it now, but our difficulty model should be designed so that it can support it later.

---

# 24. Difficulty Should Be Immutable Per Question Attempt

Suppose a student attempts a quiz today.

The question is:

```text
difficulty = HARD
```

Later, an instructor changes its classification to:

```text
MEDIUM
```

Historical analytics shouldn't suddenly change.

Therefore, assessment systems often need to preserve the difficulty associated with the question/attempt at the relevant time.

This is something we'll think about when designing the final assessment database.

---

# 25. API Design

A quiz-generation request might look like:

```json
{
  "lessonId": "lesson_123",
  "questionCount": 10,
  "difficulty": "MEDIUM"
}
```

Or:

```json
{
  "lessonId": "lesson_123",
  "distribution": {
    "EASY": 3,
    "MEDIUM": 5,
    "HARD": 2
  }
}
```

The second design is more flexible.

But don't support both immediately unless there's a real need.

A clean first version could start with:

```ts
difficulty: Difficulty;
```

Then add distributions later.

---

# 26. TypeScript Definition

Create a shared enum/type:

```ts
export const Difficulty = {
  EASY: "EASY",
  MEDIUM: "MEDIUM",
  HARD: "HARD",
} as const;

export type Difficulty =
  (typeof Difficulty)[keyof typeof Difficulty];
```

Now the rest of your application can use:

```ts
difficulty: Difficulty;
```

This avoids random strings such as:

```text
"easy"
"Easy"
"EASY"
"beginner"
```

appearing throughout your codebase.

---

# 27. Database Representation

With Prisma, we could eventually use an enum:

```prisma
enum Difficulty {
  EASY
  MEDIUM
  HARD
}
```

Then:

```prisma
model Question {
  id         String     @id @default(cuid())
  text       String
  difficulty Difficulty
}
```

This provides database-level protection.

For example, the database won't accept:

```text
SUPER_HARD
```

if your enum only contains:

```text
EASY
MEDIUM
HARD
```

This is a good example of multiple validation layers:

```text
Request Validation
        ↓
Business Validation
        ↓
Database Constraint
```

---

# 28. Don't Overuse Difficulty

Difficulty is useful, but don't use it for everything.

Don't assume:

```text
Hard question
=
better question
```

A good educational assessment needs a mixture.

For a beginner JavaScript lesson:

```text
3 Easy
5 Medium
2 Hard
```

may be much better than:

```text
10 Hard
```

The goal is to measure learning, not make students suffer.

---

# 29. A Better Generation Blueprint

Instead of simply:

```text
Generate 10 questions.
```

our system could eventually send:

```json
{
  "questionCount": 10,
  "difficultyDistribution": {
    "EASY": 3,
    "MEDIUM": 5,
    "HARD": 2
  },
  "questionTypes": {
    "MCQ": 6,
    "TRUE_FALSE": 2,
    "SHORT_ANSWER": 2
  }
}
```

Now the AI receives a clear blueprint:

```text
10 total
│
├── 3 Easy
├── 5 Medium
└── 2 Hard

Question types:
├── 6 MCQ
├── 2 True/False
└── 2 Short Answer
```

This is much more powerful than simply asking:

> "Generate a quiz."

# 31. What We Are Not Doing Yet

Don't jump ahead to:

```text
❌ Adaptive learning algorithm
❌ Automatic difficulty prediction model
❌ Student ability estimation
❌ Complex psychometrics
❌ AI-based difficulty classifier
```

Those are possible future improvements.

For **9.6**, we need a solid foundation:

```text
Easy
Medium
Hard
```

with clear rules for what each means.

# 🧠 Key Takeaways

### 1. Difficulty measures cognitive challenge

Not:

```text
question length
```

but:

```text
reasoning
understanding
application
analysis
```

### 2. Start with three levels

```text
EASY
MEDIUM
HARD
```

### 3. Difficulty is independent of question type

```text
MCQ + HARD
True/False + HARD
Short Answer + HARD
```

are all valid.

### 4. Don't let AI freely decide difficulty

```text
Instructor
   ↓
Difficulty Requirement
   ↓
AI
   ↓
Validation
```

### 5. Hard does not mean outside the lesson

```text
Hard
=
deeper reasoning

NOT

Hard
=
new information
```

### 6. Difficulty can later power adaptive learning

```text
Student performance
       ↓
Difficulty selection
       ↓
Next question
```

That's a powerful future feature for your AI LMS.
