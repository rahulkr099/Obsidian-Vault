# Lesson 9.8 — Quiz Scoring

In the Phase 9 roadmap, **9.8 is “Quiz Scoring.”**

In Lesson 9.7, we learned how AI can evaluate free-text answers.

Now we need to answer a different question:

> **How does the LMS convert individual question results into a reliable final quiz score?**

This is where we should make an important architectural distinction:

```text
Question Evaluation
        ↓
Question Score
        ↓
Quiz Scoring
        ↓
Final Quiz Result
```

---

# 1. What Is Quiz Scoring?

Suppose a quiz contains:

```text
10 questions
```

A student answers:

```text
8 correct
2 incorrect
```

The LMS needs to calculate:

```text
Score = 8 / 10
      = 80%
```

But our AI LMS is more complex because we have:

```text
MCQ
True / False
Short Answer
```

These can have different scoring rules.

For example:

```text
MCQ          → exact comparison
True/False   → exact comparison
Short Answer → AI evaluation
```

Yet all of them must eventually produce a **question score**.

---

# 2. The Most Important Architecture

Don't let every question type calculate the final quiz score independently.

Instead:

```text
MCQ Evaluation
      ↓
Question Score
      │
True/False Evaluation
      ↓
Question Score
      │
Short Answer Evaluation
      ↓
Question Score
      │
      └──────────┐
                 ↓
            Quiz Scoring
                 ↓
            Final Result
```

This gives us one centralized scoring system.

---

# 3. Question Score vs Quiz Score

These are different.

### Question score

Example:

```text
Question 1
5 / 5
```

### Quiz score

Example:

```text
Total:
42 / 50
```

Then:

```text
42 / 50 = 84%
```

So:

```text
Question Scores
      ↓
Total Earned Marks
      ↓
Total Possible Marks
      ↓
Percentage
```

---

# 4. Give Questions Explicit Marks

Instead of assuming every question is worth 1 mark, we can define:

```ts
type QuestionScoreConfig = {
  maxScore: number;
};
```

For example:

```text
MCQ           → 1 mark
True/False    → 1 mark
Short Answer  → 5 marks
```

Then a quiz might contain:

```text
5 MCQs          × 1 = 5
3 True/False    × 1 = 3
2 Short Answers × 5 = 10
```

Total:

```text
18 marks
```

This is more flexible than assuming:

```text
10 questions = 10 marks
```

---

# 5. Question Result

After evaluating a question, we want a common representation.

```ts
type QuestionResult = {
  questionId: string;
  maxScore: number;
  earnedScore: number;
  isCorrect: boolean;
};
```

For example:

```json
{
  "questionId": "q_123",
  "maxScore": 5,
  "earnedScore": 4,
  "isCorrect": false
}
```

Why `isCorrect: false`?

Because a short-answer question can receive:

```text
4 / 5
```

without being completely correct.

So we may eventually need something like:

```ts
type EvaluationStatus =
  | "CORRECT"
  | "PARTIAL"
  | "INCORRECT";
```

---

# 6. Deterministic Scoring for MCQ

MCQs don't need AI to calculate the score.

Suppose:

```text
Stored answer:
B

Student answer:
B
```

Then:

```ts
const isCorrect =
  submittedAnswer === correctAnswer;
```

If correct:

```text
earnedScore = maxScore
```

Otherwise:

```text
earnedScore = 0
```

For a 1-mark question:

```text
Correct → 1
Wrong   → 0
```

This is deterministic.

---

# 7. Deterministic Scoring for True/False

Same idea.

Stored:

```text
true
```

Student:

```text
true
```

Result:

```text
1 / 1
```

If:

```text
stored = false
student = true
```

then:

```text
0 / 1
```

Again:

> **Do not use an LLM to evaluate something that can be evaluated deterministically.**

This saves:

- money
    
- latency
    
- complexity
    
- possible AI mistakes
    

---

# 8. AI-Assisted Scoring for Short Answers

Short answers are different.

Lesson 9.7 might produce:

```json
{
  "score": 0.8,
  "correct": true
}
```

If the question is worth:

```text
5 marks
```

we calculate:

```text
5 × 0.8
= 4
```

So:

```text
AI evaluation
      ↓
normalized score = 0.8
      ↓
scoring service
      ↓
4 / 5
```

This separation is extremely important.

---

# 9. Never Let AI Return Final Marks

Avoid asking:

> "Give this student a score out of 5."

Instead ask for a normalized evaluation:

```text
0.0 → completely incorrect
1.0 → completely correct
```

Then your backend determines:

```ts
earnedScore =
  normalizedScore * maxScore;
```

This gives your application control over scoring.

---

# 10. Score Normalization

Let's define:

```text
normalizedScore ∈ [0, 1]
```

Examples:

```text
0.0 → 0%
0.25 → 25%
0.5 → 50%
0.75 → 75%
1.0 → 100%
```

Then:

```text
earnedScore =
normalizedScore × maxScore
```

Example:

```text
normalizedScore = 0.75
maxScore = 4

earnedScore = 0.75 × 4
            = 3
```

Final:

```text
3 / 4
```

---

# 11. Quiz Total

Suppose we have:

```text
Question 1 → 1 / 1
Question 2 → 1 / 1
Question 3 → 0 / 1
Question 4 → 0.5 / 1
Question 5 → 1 / 1
```

Total earned:

```text
1 + 1 + 0 + 0.5 + 1
= 3.5
```

Total possible:

```text
5
```

Percentage:

```text
3.5 / 5 × 100
= 70%
```

So:

```text
Score = 3.5 / 5
Percentage = 70%
```

---

# 12. General Formula

The core formula is:

```text
Total Earned
────────────── × 100
Total Possible
```

In TypeScript:

```ts
const percentage =
  (totalEarned / totalPossible) * 100;
```

This should be calculated by your backend.

Never trust:

```json
{
  "score": 100
}
```

sent by the frontend.

---

# 13. The Frontend Should Never Decide the Score

Bad architecture:

```text
Student
   ↓
React
   ↓
Calculate score
   ↓
Send score to backend
```

A student could modify JavaScript and submit:

```json
{
  "score": 100
}
```

Instead:

```text
Student
   ↓
Submit answers
   ↓
Backend
   ↓
Evaluate answers
   ↓
Calculate score
   ↓
Store result
```

The server is the source of truth.

---

# 14. Quiz Submission Flow

A clean flow:

```text
Student
   ↓
Submit Quiz
   ↓
POST /quiz-attempts
   ↓
Backend
   ↓
Load Quiz Questions
   ↓
Evaluate Answers
   ↓
Calculate Scores
   ↓
Store Attempt
   ↓
Return Result
```

For example:

```http
POST /api/v1/quizzes/:quizId/attempts
```

Request:

```json
{
  "answers": [
    {
      "questionId": "q1",
      "answer": "map()"
    },
    {
      "questionId": "q2",
      "answer": true
    }
  ]
}
```

The client sends **answers**, not scores.

---

# 15. Never Trust Question IDs From the Client

The student might modify:

```json
{
  "questionId": "another-student-question"
}
```

The backend must verify:

```text
Does this question belong to this quiz?
```

Flow:

```text
quizId
  ↓
Question
  ↓
Does question.quizId === quizId?
```

If not:

```text
400 / 404
```

depending on your API design.

This is an authorization/data-integrity concern.

---

# 16. Prevent Answer Injection

Suppose a quiz contains:

```text
q1
q2
q3
```

The client submits:

```json
{
  "questionId": "q999",
  "answer": "..."
}
```

The backend shouldn't blindly process it.

Validate:

```text
Question exists?
Question belongs to quiz?
Question is active?
Student is allowed to attempt quiz?
```

Then evaluate.

---

# 17. Quiz Attempt

A student needs an attempt record.

Conceptually:

```text
Quiz
 ↓
QuizAttempt
 ↓
Student Answers
```

For example:

```text
QuizAttempt
├── id
├── quizId
├── studentId
├── startedAt
├── submittedAt
├── totalScore
├── maxScore
└── percentage
```

And:

```text
QuizAttempt
     ↓
AttemptAnswer
├── questionId
├── answer
├── earnedScore
└── maxScore
```

This gives us historical assessment data.

---

# 18. Why Store Individual Answers?

Don't store only:

```text
QuizAttempt
score = 80
```

You lose useful information.

Instead:

```text
QuizAttempt
     │
     ├── Q1 → 1/1
     ├── Q2 → 1/1
     ├── Q3 → 0/1
     ├── Q4 → 0.5/1
     └── Q5 → 1/1
```

Now you can analyze:

```text
Which questions caused problems?
Which concepts are weak?
Which question types are difficult?
```

This will become very useful in **9.12 Assessment Analytics**.

---

# 19. Score Status

For AI-evaluated answers, the quiz may not immediately have a final score.

For example:

```text
5 MCQs
2 Short Answers
```

MCQs:

```text
Immediately evaluated
```

Short answers:

```text
Waiting for AI
```

So the attempt could have:

```ts
type AttemptStatus =
  | "IN_PROGRESS"
  | "SUBMITTED"
  | "EVALUATING"
  | "COMPLETED"
  | "FAILED";
```

Flow:

```text
IN_PROGRESS
     ↓
SUBMITTED
     ↓
EVALUATING
     ↓
COMPLETED
```

This becomes especially useful when we later introduce background jobs.

---

# 20. What If AI Evaluation Fails?

Suppose:

```text
MCQs → evaluated
Short answers → AI timeout
```

We shouldn't say:

```text
Student score = 0
```

Instead:

```text
Attempt
  ↓
EVALUATING
  ↓
Retry AI evaluation
```

The student's original answer remains stored.

Once evaluation succeeds:

```text
EVALUATING
    ↓
COMPLETED
```

This is an important reliability principle.

---

# 21. Transactions

Quiz submission is a good candidate for a database transaction.

Imagine:

```text
1. Create QuizAttempt
2. Create Answer 1
3. Create Answer 2
4. Create Answer 3
5. Calculate score
6. Update QuizAttempt
```

What if step 4 fails?

We don't want:

```text
QuizAttempt exists
Answers 1 & 2 exist
Answer 3 missing
Score partially stored
```

We want the database to maintain consistency.

Conceptually:

```text
BEGIN
  create attempt
  create answers
  update score
COMMIT
```

If something fails:

```text
ROLLBACK
```

Because you've already studied PostgreSQL transactions in the earlier database phase, this is a practical application of that knowledge.

# 22. Scoring Service

A clean architecture could have:

```text
Quiz Service
     ↓
Evaluation Service
     ↓
Scoring Service
     ↓
Attempt Repository
```

For example:

```ts
class ScoringService {
  calculateQuestionScore(
    evaluation: EvaluationResult,
    maxScore: number
  ) {
    return evaluation.score * maxScore;
  }

  calculateQuizScore(
    questionResults: QuestionResult[]
  ) {
    // calculate totals
  }
}
```

This keeps scoring logic reusable.

---

# 23. A Better Scoring Function

Conceptually:

```ts
function calculatePercentage(
  earned: number,
  possible: number
) {
  if (possible <= 0) {
    throw new Error(
      "Total possible score must be greater than zero"
    );
  }

  return (earned / possible) * 100;
}
```

Then:

```ts
const percentage =
  calculatePercentage(
    totalEarned,
    totalPossible
  );
```

Simple, predictable, testable.

---

# 24. Rounding

Suppose:

```text
earned = 7
possible = 9
```

Then:

```text
7 / 9 × 100
= 77.777...
```

You might display:

```text
77.78%
```

But be careful about where rounding happens.

Prefer:

```text
Store precise value
        ↓
Round for display
```

rather than repeatedly rounding intermediate calculations.

For example:

```ts
const percentage =
  (earned / possible) * 100;

const displayPercentage =
  Number(percentage.toFixed(2));
```

The exact database representation can be decided when we finalize the assessment schema.

---

# 25. Passing Score

A quiz may have:

```text
Passing percentage = 60%
```

Then:

```text
percentage >= 60
```

means:

```text
PASSED
```

Otherwise:

```text
FAILED
```

We could represent:

```ts
type AttemptResult =
  | "PASSED"
  | "FAILED"
  | "PENDING";
```

But the important rule is:

> **Passing logic belongs to the application, not the AI.**

---

# 26. Example

Suppose:

```text
Total possible = 20
Student earned = 15
```

Then:

```text
15 / 20 × 100
= 75%
```

If passing is:

```text
60%
```

then:

```text
75 >= 60
```

Result:

```text
PASSED
```

---

# 27. Weighted Questions

Not every question needs equal weight.

Suppose:

```text
MCQ:
1 mark

Short Answer:
5 marks
```

Then:

```text
MCQ × 5 = 5
Short Answer × 3 = 15
```

Total:

```text
20 marks
```

A student's score might be:

```text
MCQ:
4 / 5

Short Answer:
12 / 15
```

Total:

```text
16 / 20
= 80%
```

This is more flexible than simply counting correct answers.

---

# 28. Don't Use "Number Correct" for Mixed Assessments

This:

```text
8 correct / 10 questions
= 80%
```

works only when every question has equal weight.

For mixed assessment:

```text
MCQ = 1 mark
Short answer = 5 marks
```

you need:

```text
earned marks / possible marks
```

not:

```text
correct questions / total questions
```

That's an important distinction.

---

# 29. Attempt Immutability

Once a student submits an attempt:

```text
QuizAttempt
```

you generally shouldn't silently change historical results because the quiz was later edited.

For example:

```text
Monday:
Quiz = 10 questions

Wednesday:
Instructor changes question 5
```

Monday's attempt should still represent what the student actually answered.

This means assessment systems need to think carefully about:

```text
quiz version
question version
attempt snapshot
```

We don't need to fully implement versioning in this lesson, but keep it in mind.

# 34. Idempotency

Imagine the student double-clicks:

```text
Submit
Submit
```

You don't want:

```text
Attempt 1
Attempt 2
Attempt 3
```

created accidentally.

Your system needs to define what happens when a submission is repeated.

For example:

```text
Attempt already submitted?
        ↓
Yes → return existing result
```

or:

```text
Allow another attempt?
        ↓
Create a new attempt intentionally
```

The exact policy depends on the LMS requirements.

But this is an important backend concept.

---

# 35. Retakes

An LMS may allow:

```text
Attempt 1 → 55%
Attempt 2 → 72%
Attempt 3 → 88%
```

Now we need to decide:

```text
Final score =
latest attempt?
highest attempt?
average?
```

That's a business rule.

For example:

```ts
type RetakePolicy =
  | "HIGHEST"
  | "LATEST"
  | "AVERAGE";
```

Don't let the AI decide this.

---

# 36. Score Calculation Should Be Testable Without AI

This is a very important engineering principle.

Your scoring logic should work with:

```ts
const results = [
  {
    earnedScore: 1,
    maxScore: 1,
  },
  {
    earnedScore: 0.5,
    maxScore: 1,
  },
  {
    earnedScore: 4,
    maxScore: 5,
  },
];
```

Then:

```text
Total earned = 5.5
Total possible = 7

Percentage = 78.57%
```

No AI call is required.

This makes scoring:

```text
fast
deterministic
cheap
testable
```

---

# 37. Unit Tests

You should eventually test cases like:

```text
5 / 5 → 100%
0 / 5 → 0%
2.5 / 5 → 50%
7 / 10 → 70%
```

And edge cases:

```text
0 possible marks → error
negative score → reject
earned > possible → reject
NaN → reject
Infinity → reject
```

This is exactly the type of logic that should have strong unit tests.

---

# 38. Protect Against Invalid AI Scores

Suppose the evaluator returns:

```json
{
  "score": 1.5
}
```

But the valid range is:

```text
0 → 1
```

Reject it.

Similarly:

```json
{
  "score": -0.2
}
```

must be rejected.

Your Zod schema should enforce:

```ts
z.number().min(0).max(1)
```

Then:

```text
AI
 ↓
Zod
 ↓
Invalid
 ↓
Retry / failure handling
```

Never calculate:

```text
1.5 × 5 = 7.5 / 5
```

---

# 39. Score Integrity

The backend should guarantee:

```text
0 <= earnedScore <= maxScore
```

and:

```text
0 <= percentage <= 100
```

These should be application invariants.

Think:

```text
                 Score Integrity
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
   Question Score   Quiz Score    Percentage
```

No matter where the result comes from, these rules must hold.

# 🧠 Key Takeaways

### 1. The server calculates the score

```text
Frontend
→ submits answers

Backend
→ evaluates + scores
```

### 2. Use deterministic scoring whenever possible

```text
MCQ
True/False
```

don't need an LLM.

### 3. AI evaluation is mainly for free-text answers

```text
Short Answer
    ↓
AI Evaluation
    ↓
Normalized score
```

### 4. Separate evaluation from scoring

```text
AI Evaluation
      ↓
Question Result
      ↓
Scoring Service
      ↓
Quiz Result
```

### 5. Score using marks, not simply question count

Especially when questions have different weights:

```text
earned marks
─────────────
possible marks
```

### 6. Preserve individual question results

Don't store only:

```text
80%
```

Store:

```text
Q1 → 1/1
Q2 → 0/1
Q3 → 0.5/1
...
```

This becomes extremely valuable for analytics.

### 7. Keep scoring deterministic and testable

Your scoring system should work even if:

```text
AI is unavailable.
```
