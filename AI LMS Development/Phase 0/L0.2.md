### Important security rule

An instructor can modify **only their own courses**.

For example:

```text
Instructor A
    │
    ├── React Course
    └── Node Course

Instructor B
    │
    └── Python Course
```

Instructor A:

```text
React Course → UPDATE ✅
Node Course  → UPDATE ✅
Python Course → UPDATE ❌
```

This is called **resource-level authorization**.

It's more advanced than simply checking:

```text
role === "INSTRUCTOR"
```

Later we'll implement something like:

```text
role check
     ↓
course ownership check
```

# 5. RBAC vs Ownership

This is an important backend concept.

Suppose we have:

```http
PATCH /api/v1/courses/123
```

First:

```text
Is user authenticated?
        ↓
Is user an instructor/admin?
        ↓
Does course 123 exist?
        ↓
If instructor:
    Does course belong to this instructor?
        ↓
Allow update
```

So:

```text
Authentication
      ↓
Authorization
      ↓
Resource Ownership
```

This is the security model I want you to implement.

# 8. Backend Authorization

Frontend route protection is useful for UX.

But **never trust it for security**.

For example, hiding this button:

```text
Delete Course
```

from students is not enough.

A student could manually send:

```http
DELETE /api/v1/courses/123
```

So the backend must reject it:

```text
Student
   ↓
DELETE /courses/123
   ↓
Authorization middleware
   ↓
403 Forbidden
```

The frontend protects the interface.

**The backend protects the actual system.**

This is an important interview point.


# 10. Course Ownership

Our course will have:

```text
Course
   │
   └── instructorId
            │
            ▼
           User
```

So:

```text
courses

id
title
description
instructorId
categoryId
status
createdAt
updatedAt
```

Example:

```text
User
id = 101
role = INSTRUCTOR
```

creates:

```text
Course
id = 500
instructorId = 101
```

Now the backend can determine ownership.

# 11. A Small but Important Decision

I recommend that **students cannot create courses**.

Seems obvious, but we explicitly define it now because every permission decision eventually becomes backend logic.

Our rule:

```text
STUDENT
    ↓
consume learning content

INSTRUCTOR
    ↓
create learning content

ADMIN
    ↓
manage the platform
```

That's a clean mental model.
