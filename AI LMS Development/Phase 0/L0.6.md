# 1. Monorepo or Separate Repositories?

For this project, I recommend a **monorepo**.

Instead of:

```text
ai-lms-frontend
ai-lms-backend
```

we'll have:

```text
ai-lms/
```

containing both.

Why?

Because they belong to the same product and we'll eventually share:

- TypeScript types
    
- validation schemas
    
- configuration
    
- API contracts

# 4. Why `features/`?

This is a major architectural choice.

Instead of:

```text
components/
├── CourseCard.tsx
├── CourseForm.tsx
├── Quiz.tsx
├── Login.tsx
├── AIChat.tsx
└── ...
```

we organize around business features:

```text
features/
│
├── courses/
│   ├── components/
│   ├── hooks/
│   ├── api.ts
│   ├── types.ts
│   └── schemas.ts
│
├── quizzes/
│   ├── components/
│   ├── hooks/
│   ├── api.ts
│   └── types.ts
│
└── ai/
    ├── components/
    ├── hooks/
    ├── api.ts
    └── types.ts
```

As the application becomes larger, this makes it much easier to find things.

# 7. Inside a Backend Module

For example:

```text
modules/courses/
│
├── course.controller.ts
├── course.service.ts
├── course.repository.ts
├── course.routes.ts
├── course.schema.ts
├── course.types.ts
└── course.mapper.ts
```

The flow:

```text
course.routes
      ↓
course.controller
      ↓
course.service
      ↓
course.repository
      ↓
Prisma
      ↓
PostgreSQL
```

This is the architecture we've been discussing.

# 8. What Does Each File Do?

### `course.routes.ts`

Defines endpoints:

```text
GET /courses
POST /courses
PATCH /courses/:id
```

---

### `course.controller.ts`

Handles HTTP:

```text
req
 ↓
service
 ↓
res
```

---

### `course.service.ts`

Contains business logic:

```text
validate instructor
check category
generate slug
create course
```

---

### `course.repository.ts`

Handles database queries:

```text
findById()
findBySlug()
create()
update()
delete()
```

---

### `course.schema.ts`

Validates input:

```text
title
description
categoryId
level
```

We'll use Zod.

---

### `course.types.ts`

TypeScript-specific types.

---

### `course.mapper.ts`

Transforms database/domain objects into API responses when useful.

For example:

```text
Database object
      ↓
Mapper
      ↓
Public API object
```

This prevents accidentally returning internal fields.

# 15. Shared Types

One interesting advantage of the monorepo is:

```text

```

For example:

```text

Quiz
ApiResponse
Pagination
```

can potentially be shared between:

```text
React
   ↑
packages/types
   ↓
Express
```

This reduces duplicated TypeScript definitions.

However, we shouldn't blindly share every backend type with the frontend.

For example:

```text
passwordHash
```

should obviously never become a frontend type.

# 22. One Important Correction to Our Earlier Architecture

We have talked about:

```text
AI Service
Vector DB
Redis
BullMQ
Object Storage
```

But **not all of these need to be separate applications**.

Our initial backend can be:

```text
                    Express API
                        │
        ┌───────────────┼────────────────┐
        │               │                │
      Courses          Auth              AI
        │                                │
        │                                │
        └─────────── PostgreSQL ─────────┘
                         │
                       Redis
```

Later:

```text
Redis
  ↓
BullMQ
  ↓
Worker
```

The architecture evolves as the application needs it.

That's exactly how I want you to learn backend engineering: **don't add technology without a problem to solve.**
