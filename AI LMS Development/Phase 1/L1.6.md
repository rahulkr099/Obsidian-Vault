# Lesson 1.6 — Prisma + First Migration

This is a **major milestone**.

Until now:

```text
React
  ↓
Express
  ↓
Docker
  ↓
PostgreSQL
```

Now we're going to add:

```text
React
  ↓
Express + TypeScript
  ↓
Prisma
  ↓
PostgreSQL
  ↓
Docker
```

We'll use the **current Prisma 7 setup**. Prisma 7 is currently the generally available release, and its setup differs from older tutorials: the database URL is configured in `prisma.config.ts`, and PostgreSQL uses the `@prisma/adapter-pg` driver adapter. ([Prisma](https://docs.prisma.io/docs/getting-started?utm_source=chatgpt.com "Prisma 7 getting started | Prisma Documentation"))

---

# 1. What Is Prisma?

Prisma is our database toolkit.

Instead of writing SQL everywhere:

```sql
SELECT *
FROM courses
WHERE id = '123';
```

we can write TypeScript:

```ts
const course = await prisma.course.findUnique({
  where: {
    id: courseId,
  },
});
```

Prisma gives us:

```text
Prisma
├── Prisma Schema
├── Prisma Client
├── Prisma Migrate
└── Prisma Studio
```

The important pieces for us are:

### Prisma Schema

Defines our database models.

### Prisma Client

Allows TypeScript to query PostgreSQL.

### Prisma Migrate

Keeps database schema changes in version-controlled migrations.

Prisma officially describes Prisma ORM as providing type-safe database access, migrations, and a visual data editor. ([Prisma](https://www.prisma.io/docs/orm?utm_source=chatgpt.com "What is Prisma ORM? (Overview) | Prisma Documentation"))

# 5. Understand `prisma.config.ts`

You'll get something conceptually like:

```ts
import 'dotenv/config';
import { defineConfig, env } from 'prisma/config';

export default defineConfig({
  schema: 'prisma/schema.prisma',

  migrations: {
    path: 'prisma/migrations',
  },

  datasource: {
    url: env('DATABASE_URL'),
  },
});
```

This is an important Prisma 7 change.

In older Prisma versions, you may see:

```prisma
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

But in Prisma 7, the URL is configured in `prisma.config.ts`. ([Prisma](https://docs.prisma.io/docs/orm/v6/reference/prisma-config-reference?utm_source=chatgpt.com "Reference documentation for the prisma config file | Prisma Documentation"))

# 12. Why `cuid()`?

Instead of:

```prisma
id Int @id @default(autoincrement())
```

we're using:

```prisma
id String @id @default(cuid())
```

For this application, string IDs give us useful properties:

```text
123
124
125
```

versus:

```text
clx7x8...
clx7x9...
clx7xa...
```

We don't need sequential IDs exposed through URLs.

For example:

```text
/courses/clx8abc...
```

instead of:

```text
/courses/123
```

It's not a security mechanism by itself, but it avoids unnecessarily exposing sequential identifiers.

# 17. Module

Add:

```prisma
model Module {
  id          String @id @default(cuid())
  courseId    String
  title       String
  description String?
  position    Int

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  course  Course   @relation(fields: [courseId], references: [id], onDelete: Cascade)
  lessons Lesson[]

  @@unique([courseId, position])
  @@index([courseId])
}
```

Notice:

```prisma
@@unique([courseId, position])
```

This means:

> A course can't have two modules with the same position.

For example:

```text
Course A
 ├── Module 1
 ├── Module 2
 └── Module 3
```

but not:

```text
Course A
 ├── Module 1
 ├── Module 1  ❌
 └── Module 3
```

# 19. Enrollment

Now let's add the student-course relationship.

```prisma
model Enrollment {
  id         String   @id @default(cuid())
  studentId  String
  courseId   String
  enrolledAt DateTime @default(now())
  completedAt DateTime?

  student User   @relation(fields: [studentId], references: [id], onDelete: Cascade)
  course  Course @relation(fields: [courseId], references: [id], onDelete: Cascade)

  @@unique([studentId, courseId])
  @@index([studentId])
  @@index([courseId])
}
```

This is our many-to-many relationship:

```text
Student
   ↕
Enrollment
   ↕
Course
```

And:

```prisma
@@unique([studentId, courseId])
```

prevents duplicate enrollment.

# 43. Create Prisma Client Instance

Create:

```text
apps/api/src/config/prisma.ts
```

Add:

```ts
import 'dotenv/config';

import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from '../../generated/prisma/client.js';

const connectionString = process.env.DATABASE_URL;

if (!connectionString) {
  throw new Error('DATABASE_URL is not configured');
}

const adapter = new PrismaPg({
  connectionString,
});

export const prisma = new PrismaClient({
  adapter,
});
```

This follows Prisma's current PostgreSQL driver-adapter approach. ([Prisma](https://docs.prisma.io/docs/prisma-orm/quickstart/postgresql?utm_source=chatgpt.com "Quickstart: Prisma ORM with PostgreSQL (10 min) | Prisma Documentation"))

# 44. Why Do We Create One Prisma Client?

Don't do this:

```ts
// course.service.ts
const prisma = new PrismaClient();

// user.service.ts
const prisma = new PrismaClient();

// quiz.service.ts
const prisma = new PrismaClient();
```

That can create unnecessary database connections.

Instead:

```text
prisma.ts
   │
   └── one shared Prisma client
             │
       ┌─────┼─────┐
       ▼     ▼     ▼
    Course User  Quiz
```

Each repository imports the shared client.

# 51. `migrate dev` vs `db push`

This is extremely important.

You may see:

```bash
prisma db push
```

online.

### `db push`

Good for:

```text
quick prototyping
throwaway experiments
```

It pushes the schema without creating a migration history.

### `migrate dev`

Good for our actual project:

```text
schema
 ↓
migration
 ↓
database
```

We want migrations tracked in Git.

Prisma's documentation describes `migrate dev` as the development command that creates/applies migrations and maintains migration history. ([Prisma](https://docs.prisma.io/docs/cli/migrate/dev?utm_source=chatgpt.com "prisma migrate dev | Create & Apply Migrations | Prisma Documentation"))

So for our AI LMS:

```text
Development
    ↓
prisma migrate dev
```

and later production:

```text
Production
    ↓
prisma migrate deploy
```

---

# 52. Never Delete Migration History Casually

We'll eventually have:

```text
prisma/migrations/
├── ..._init/
├── ..._add_auth_fields/
├── ..._add_quizzes/
├── ..._add_ai_usage/
└── ...
```

These migrations should be committed to Git.

They tell us:

> How did our database evolve?

This becomes extremely valuable when working in a team.
