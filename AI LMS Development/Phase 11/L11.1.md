# Lesson 11.1 — Redis Fundamentals

Phase 11 is specifically **Redis & Background Jobs**, and the first lesson is **Redis Fundamentals**. The roadmap places caching, temporary data, rate limiting, queues, workers, retries, monitoring, and idempotency after this foundation.

Today, the goal is **not** to jump into BullMQ or background workers. First, you need to understand **what Redis actually is, how it stores data, and why your AI LMS needs it.**

---

## 1. What is Redis?

**Redis** is an in-memory data store.

The simplest way to think about it:

```text
PostgreSQL
    ↓
Permanent application data

Redis
    ↓
Fast / temporary / frequently accessed data
```

Redis primarily keeps data in **RAM**, which makes reads and writes extremely fast.

For example:

```text
PostgreSQL:

course
 ├── id
 ├── title
 ├── description
 └── instructorId
```

Redis could contain:

```text
course:123 → cached course data
```

---

# 2. Why do we need Redis?

Imagine your LMS receives this request:

```http
GET /api/v1/courses/123
```

Without caching:

```text
Client
   ↓
Express API
   ↓
Service
   ↓
Prisma
   ↓
PostgreSQL
   ↓
Response
```

Every request reaches PostgreSQL.

Now imagine:

```text
10,000 users
     ↓
same popular course
     ↓
10,000 database queries
```

That's unnecessary work.

With Redis:

```text
Client
   ↓
Express API
   ↓
Redis
   ↓
Found?
 ┌──┴──┐
Yes    No
 ↓      ↓
Data   PostgreSQL
          ↓
        Redis
          ↓
        Data
```

This concept becomes **Lesson 11.2 — Caching**.

For now, remember:

> Redis can act as a very fast data store between your application and slower persistent systems.

---

# 3. Redis Is Not a Replacement for PostgreSQL

This distinction is extremely important.

Don't think:

```text
PostgreSQL ❌
Redis ✅
```

Instead:

```text
             Your Application
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
      PostgreSQL            Redis
      permanent             fast/
      data                  temporary
```

### PostgreSQL

Use it for things such as:

```text
Users
Courses
Lessons
Enrollments
Quiz attempts
Progress
Certificates
Payments
```

These are **business records** that shouldn't disappear just because your server restarts.

### Redis

Good candidates include:

```text
Cache
OTP
Temporary tokens
Rate-limit counters
Sessions
Job queues
Locks
Temporary AI state
```

We'll explore each of these later in Phase 11.

---

# 4. Redis Data Model

Redis works differently from PostgreSQL.

PostgreSQL thinks in:

```text
Database
   ↓
Tables
   ↓
Rows
   ↓
Columns
```

Redis is much more like:

```text
Key
 ↓
Value
```

Example:

```text
user:123:name → "Rahul"
```

Another:

```text
course:456:title → "Advanced TypeScript"
```

Conceptually:

```text
┌────────────────────┬─────────────────────┐
│ Key                │ Value               │
├────────────────────┼─────────────────────┤
│ user:123:name      │ Rahul               │
│ course:456:title   │ Advanced TypeScript  │
│ otp:789            │ 492831              │
└────────────────────┴─────────────────────┘
```

---

# 5. Redis Keys

Good key naming is extremely important.

Instead of:

```text
123
```

prefer:

```text
user:123
```

Instead of:

```text
456
```

use:

```text
course:456
```

For a student's course progress:

```text
progress:user:123:course:456
```

For an OTP:

```text
otp:user:123
```

For a cache:

```text
cache:course:456
```

This gives your Redis database a logical structure.

A useful pattern is:

```text
resource:identifier
```

or:

```text
namespace:resource:identifier
```

---

# 6. Redis Strings

The simplest Redis data type is a **String**.

Example:

```text
SET user:123:name "Rahul"
```

Then:

```text
GET user:123:name
```

Result:

```text
Rahul
```

You can also store numbers:

```text
SET course:123:views 100
```

Then:

```text
INCR course:123:views
```

Result:

```text
101
```

This becomes useful for counters.

For example:

```text
AI requests today
        ↓
ai:usage:user:123
        ↓
      counter
```

---

# 7. TTL — Time To Live

One of Redis's most useful features is **expiration**.

Suppose you generate an OTP:

```text
otp:user:123 → 582913
```

You don't want it to remain forever.

You can give it a lifetime:

```text
SET otp:user:123 582913 EX 300
```

`300` means:

```text
300 seconds
=
5 minutes
```

After five minutes:

```text
otp:user:123
```

automatically disappears.

Conceptually:

```text
Create OTP
   ↓
582913
   ↓
5 minutes
   ↓
Expired
   ↓
Deleted automatically
```

This is extremely useful for:

```text
OTP
Password reset tokens
Email verification
Temporary sessions
Cached data
Rate-limit counters
Temporary locks
```

We'll use this heavily in later lessons.

---

# 8. Redis Hashes

Sometimes you don't want:

```text
user:123:name
user:123:email
user:123:role
```

as separate keys.

Redis has **Hashes**.

Conceptually:

```text
user:123
 ├── name → Rahul
 ├── email → rahul@example.com
 └── role → student
```

Example commands:

```text
HSET user:123 name "Rahul"
HSET user:123 role "student"
```

Then:

```text
HGET user:123 name
```

returns:

```text
Rahul
```

You can think of a Redis Hash as a small object-like structure.

---

# 9. Redis Lists

Redis also supports **Lists**.

Conceptually:

```text
notifications:user:123

[ notification-1,
  notification-2,
  notification-3 ]
```

You can add items to the beginning or end.

Lists can be useful for things like:

```text
Recent activity
Simple queues
Recent notifications
Message lists
```

However, for our production background-job architecture, we'll later use a proper queue system rather than manually building everything with Redis Lists.

---

# 10. Redis Sets

A **Set** stores unique values.

Example:

```text
course:123:students
```

could contain:

```text
user:101
user:102
user:103
```

If you try to add:

```text
user:101
```

again, it remains unique.

Sets are useful when you care about:

```text
membership
uniqueness
relationships
```

For example:

```text
course:123:online-users
```

---

# 11. Sorted Sets

Redis also provides **Sorted Sets**.

Think:

```text
Student       Score
-------------------
Rahul          95
Aman           91
Priya          88
```

This can be useful for:

```text
Leaderboards
Ranking
Scores
Priority systems
Time-based data
```

For your LMS:

```text
course:123:leaderboard
```

could potentially store students and their scores.

---

# 12. Important Redis Data Types

For now, remember these:

```text
Redis
│
├── String
├── Hash
├── List
├── Set
└── Sorted Set
```

Don't try to memorize every Redis command.

Instead, understand **why each structure exists**.

|Type|Think of it as|Example|
|---|---|---|
|String|Single value|OTP|
|Hash|Object|User session|
|List|Ordered collection|Recent activity|
|Set|Unique collection|Online users|
|Sorted Set|Ranked collection|Leaderboard|

# 14. Redis vs PostgreSQL

This is a common interview question.

### PostgreSQL

```text
Persistent
↓
Disk-based
↓
Relational
↓
SQL
↓
Strong data relationships
↓
Transactions
```

### Redis

```text
Primarily memory-based
↓
Very fast
↓
Key-value/data-structure store
↓
TTL support
↓
Excellent for temporary/fast-access workloads
↓
Queues/counters/cache/session use cases
```

But don't oversimplify it to:

> "Redis is memory, PostgreSQL is disk."

Redis can persist data too, and PostgreSQL uses memory heavily for caching. The important distinction is **what kind of workload and data semantics you're choosing the system for**.

# 15. Installing Redis

Since you're using Linux Mint, you can install Redis locally.

First check whether it already exists:

```bash
redis-server --version
```

If installed, you'll get something similar to:

```text
Redis server v=...
```

Also check the CLI:

```bash
redis-cli --version
```

If not installed, on a Debian/Ubuntu-based system:

```bash
sudo apt update
sudo apt install redis-server
```

Then check:

```bash
sudo systemctl status redis-server
```

You want the service to be running.

# 19. Connecting Redis to TypeScript

For your Node.js backend, we'll use a Redis client library.

A common choice is:

```bash
npm install redis
```

Then conceptually:

```ts
import { createClient } from "redis";

const redis = createClient({
  url: process.env.REDIS_URL,
});

redis.on("error", (error) => {
  console.error("Redis error:", error);
});

await redis.connect();
```

Environment variable:

```env
REDIS_URL=redis://localhost:6379
```

Then:

```ts
await redis.set("name", "Rahul");

const name = await redis.get("name");

console.log(name);
```

Output:

```text
Rahul
```

# 20. Don't Create Redis Connections Everywhere

This is an important architecture lesson.

Avoid doing this in every service:

```ts
const redis = createClient();

await redis.connect();
```

Instead, create a **shared Redis client**.

For example:

```text
src/
├── config/
│   ├── env.ts
│   └── redis.ts
│
├── modules/
│   ├── auth/
│   ├── courses/
│   └── ai/
│
└── app.ts
```

Then your application has one controlled Redis connection.

Conceptually:

```text
Redis Client
     │
 ┌───┼───────────┐
 ↓   ↓           ↓
Auth Course      AI
```

This fits nicely with the architecture you've already been building.

# 22. Redis Security

Because Redis can contain sensitive temporary information, don't think of it as "just a cache."

For example, you may eventually store:

```text
password reset token
session information
AI usage counters
job information
temporary user data
```

So:

```text
❌ Public Redis
❌ No authentication in production
❌ Redis exposed directly to the internet
❌ Sensitive data without a reason
```

A production architecture should generally keep Redis on a protected/private network.

Security will also be revisited in your dedicated security phase.

# 23. The Most Important Mental Model

Remember this:

```text
PostgreSQL
    ↓
Source of truth
```

while:

```text
Redis
    ↓
Fast-access / temporary / coordination layer
```

For example:

```text
          Course
             │
             ↓
        PostgreSQL
       source of truth
             │
             ↓
           Redis
           cache
             │
             ↓
           Client
```

If Redis disappears:

```text
Redis ❌
   ↓
Application
   ↓
PostgreSQL
   ↓
Rebuild cache
```

Your permanent course data should still exist.

That's a very useful way to think about Redis.
