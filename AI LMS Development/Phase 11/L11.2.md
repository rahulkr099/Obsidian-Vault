# Lesson 11.2 — Caching

In **Phase 11**, lesson 11.2 is **Caching**. The roadmap places it immediately after Redis Fundamentals and before temporary data, rate limiting, and queues.

The goal today is to understand **how Redis can reduce unnecessary database work** and how to implement caching properly in your AI LMS.

---

## 1. What is caching?

Caching means:

> **Keep frequently needed data somewhere faster so we don't have to calculate or fetch it again every time.**

Without caching:

```text
User
 ↓
API
 ↓
Service
 ↓
PostgreSQL
 ↓
Response
```

With caching:

```text
User
 ↓
API
 ↓
Redis
 ↓
Response
```

If Redis doesn't have the data:

```text
User
 ↓
API
 ↓
Redis ──→ ❌ Cache miss
              ↓
          PostgreSQL
              ↓
            Redis
              ↓
           Response
```

So Redis becomes a **fast-access layer** in front of PostgreSQL.

---

# 2. Why do we need caching?

Imagine your LMS has:

```http
GET /api/v1/courses/123
```

Suppose the same course is viewed by 5,000 students.

Without caching:

```text
5,000 requests
      ↓
5,000 PostgreSQL queries
```

With caching:

```text
First request
     ↓
PostgreSQL
     ↓
Redis

Next 4,999 requests
     ↓
Redis
```

Much less database work.

The important point is:

> Caching is primarily about reducing repeated expensive work.

---

# 3. What should we cache?

Not everything should be cached.

Good candidates:

```text
Popular courses
Course details
Course categories
Public course lists
Dashboard statistics
Frequently accessed configuration
Expensive calculations
AI-related temporary results
```

Poor candidates:

```text
Highly sensitive data
Data that changes every second
Data that must always be absolutely fresh
Large objects that are rarely requested
Data where caching creates more complexity than benefit
```

For your LMS, a course details endpoint is a good beginner example.

---

# 4. The Cache-Aside Pattern

This is the most important caching pattern for this lesson.

You'll commonly hear:

> **Cache-aside**

The flow is:

```text
Application
    ↓
Check Redis
    ↓
Cache exists?
   / \
 Yes  No
  ↓    ↓
Return PostgreSQL
       ↓
     Store in Redis
       ↓
      Return
```

Let's break it down.

---

# 5. Cache Hit

Suppose:

```text
course:123
```

already exists in Redis.

Request:

```http
GET /api/v1/courses/123
```

Flow:

```text
Request
   ↓
Redis GET course:123
   ↓
Found ✅
   ↓
Return cached course
```

This is called a:

**Cache hit**

Example:

```text
Redis
└── course:123
      ↓
{
  "id": "123",
  "title": "TypeScript Fundamentals"
}
```

No PostgreSQL query is necessary.

---

# 6. Cache Miss

Now suppose Redis doesn't contain the course.

```text
Request
   ↓
Redis GET course:123
   ↓
Not found ❌
   ↓
PostgreSQL
   ↓
Course found
   ↓
Store in Redis
   ↓
Return response
```

This is a:

**Cache miss**

So:

```text
Cache hit  → Redis has the data
Cache miss → Redis doesn't have the data
```

These two terms are extremely common in backend engineering.

---

# 7. Example with Your LMS

Suppose we have:

```http
GET /api/v1/courses/:courseId
```

Our service might conceptually work like this:

```ts
async function getCourse(courseId: string) {
  const cacheKey = `course:${courseId}`;

  // 1. Check Redis
  const cachedCourse = await redis.get(cacheKey);

  if (cachedCourse) {
    return JSON.parse(cachedCourse);
  }

  // 2. Query PostgreSQL
  const course = await courseRepository.findById(courseId);

  if (!course) {
    throw new AppError("Course not found", 404);
  }

  // 3. Store in Redis
  await redis.set(
    cacheKey,
    JSON.stringify(course),
    {
      EX: 300,
    }
  );

  // 4. Return data
  return course;
}
```

Conceptually:

```text
Redis
 ↓
hit?
 ↓
Yes → return

No
 ↓
Prisma
 ↓
PostgreSQL
 ↓
Redis.set()
 ↓
return
```

---

# 8. Why Use a TTL?

Imagine we cache:

```text
course:123
```

forever.

Then the instructor changes:

```text
Course title
```

PostgreSQL:

```text
"Advanced TypeScript"
```

Redis:

```text
"TypeScript Fundamentals"
```

Now we have:

```text
PostgreSQL = new data
Redis      = old data
```

This is called:

> **Stale cache data**

One simple solution is **TTL**.

For example:

```text
Cache course
     ↓
TTL = 5 minutes
     ↓
Automatically expires
```

Redis:

```redis
SET course:123 "{...}" EX 300
```

After 300 seconds:

```text
course:123
    ↓
expired
```

The next request will fetch fresh data from PostgreSQL.

---

# 9. Choosing a TTL

There isn't one perfect TTL.

Think about how frequently the data changes.

### Course categories

Could use:

```text
TTL = 30 minutes
```

### Course details

Maybe:

```text
TTL = 5 minutes
```

### Popular courses

Maybe:

```text
TTL = 10 minutes
```

### Extremely dynamic data

Maybe:

```text
TTL = 10 seconds
```

The exact value depends on your application.

The important question is:

> **How stale can this data safely become?**

---

# 10. Cache Invalidation

TTL alone isn't always enough.

Suppose:

```text
Course
 ↓
Redis cache
```

Then an instructor updates the course.

We could immediately delete the cache:

```text
UPDATE course
      ↓
PostgreSQL updated
      ↓
DEL course:123
```

Then:

```text
Next GET
   ↓
Redis miss
   ↓
PostgreSQL
   ↓
Fresh data
   ↓
Redis
```

This is called:

> **Cache invalidation**

---

# 11. The Update Flow

Imagine:

```http
PATCH /api/v1/courses/123
```

We could do:

```text
Request
   ↓
Validate
   ↓
Update PostgreSQL
   ↓
Delete Redis cache
   ↓
Return response
```

For example:

```ts
await courseRepository.update(courseId, data);

await redis.del(`course:${courseId}`);
```

Now we don't leave stale course data sitting in Redis.

---

# 12. Why Not Update Redis Instead?

You might wonder:

> Why not update PostgreSQL and Redis together?

You can, but it introduces additional complexity.

For example:

```text
PostgreSQL update
      ↓
success
      ↓
Redis update
      ↓
failure ❌
```

Now the two systems may disagree.

With cache-aside:

```text
PostgreSQL
    ↓
Source of truth

Redis
    ↓
Disposable cache
```

If Redis fails, the application can often fall back to PostgreSQL.

That's a much safer mental model.

---

# 13. Cache Invalidation Strategy

For your LMS, a simple strategy is:

### Read

```text
Redis → PostgreSQL → Redis
```

### Create

```text
PostgreSQL
    ↓
Invalidate related cache
```

### Update

```text
PostgreSQL
    ↓
Invalidate cache
```

### Delete

```text
PostgreSQL
    ↓
Invalidate cache
```

So:

```text
READ
 ↓
Cache-aside

WRITE
 ↓
Database first
 ↓
Invalidate cache
```

This is a very useful pattern.

---

# 14. Cache Keys

Good cache keys matter.

For courses:

```text
course:123
```

For categories:

```text
course-category:12
```

For a user's dashboard:

```text
dashboard:student:123
```

For course progress:

```text
progress:student:123:course:456
```

For course search:

```text
courses:search:typescript:page:1
```

The key should tell you what the cached data represents.

---

# 15. Namespacing

As your application grows, Redis might contain hundreds or thousands of keys.

Instead of:

```text
123
456
789
```

use:

```text
course:123
user:123
progress:123:456
dashboard:student:123
```

Think of the prefix as a namespace:

```text
course:
user:
progress:
dashboard:
```

This makes debugging much easier.

---

# 16. Caching Lists Is Harder

Caching one course is easy:

```text
course:123
```

But imagine:

```http
GET /api/v1/courses
```

You might cache:

```text
courses:page:1
```

Now instructor updates a course.

Which caches should be invalidated?

Potentially:

```text
courses:page:1
courses:page:2
courses:popular
courses:category:programming
courses:search:typescript
...
```

This is where caching becomes more complicated.

That's why we should **start with simple object caching** before trying to cache every endpoint.

---

# 17. Cache Stampede

Here's an interesting problem.

Suppose:

```text
course:123
```

expires at exactly the wrong time.

Suddenly:

```text
1,000 requests
      ↓
Redis
      ↓
Cache miss
      ↓
1,000 PostgreSQL queries
```

Instead of helping PostgreSQL, caching just created a huge spike.

This problem is commonly called:

> **Cache stampede**

Later, more advanced techniques can help:

```text
Locks
Request coalescing
Stale-while-revalidate
Jittered TTLs
Prewarming
```

You don't need to implement all of these now.

Just understand the problem.

---

# 18. Cache Penetration

Another interesting problem:

An attacker repeatedly requests:

```text
GET /courses/nonexistent-1
GET /courses/nonexistent-2
GET /courses/nonexistent-3
...
```

If every request causes:

```text
Redis miss
 ↓
PostgreSQL
 ↓
Nothing found
```

then PostgreSQL can get unnecessary traffic.

Possible solutions include:

```text
Negative caching
Rate limiting
Input validation
Abuse detection
```

We'll encounter rate limiting in **11.4**.

---

# 19. Don't Cache Sensitive Data Carelessly

Imagine:

```text
user:123
```

contains:

```json
{
  "passwordHash": "...",
  "refreshToken": "...",
  "email": "..."
}
```

Don't blindly cache the entire database object.

Instead, cache only what you actually need.

For example:

```json
{
  "id": "123",
  "name": "Rahul",
  "role": "student"
}
```

The principle is:

> **Cache the minimum useful data.**

This also reduces memory usage.

---

# 20. Cache Serialization

Redis values are commonly stored as strings.

Suppose your PostgreSQL query returns:

```ts
const course = {
  id: "123",
  title: "TypeScript",
  published: true,
};
```

Before storing:

```ts
await redis.set(
  "course:123",
  JSON.stringify(course)
);
```

When reading:

```ts
const cached = await redis.get("course:123");

const course = cached
  ? JSON.parse(cached)
  : null;
```

So:

```text
JavaScript object
      ↓
JSON.stringify()
      ↓
Redis string
      ↓
JSON.parse()
      ↓
JavaScript object
```

---

# 21. A Better Cache Helper

As the project grows, you'll probably want reusable cache utilities.

For example:

```ts
async function getCached<T>(
  key: string
): Promise<T | null> {
  const value = await redis.get(key);

  if (!value) {
    return null;
  }

  return JSON.parse(value) as T;
}
```

And:

```ts
async function setCached<T>(
  key: string,
  value: T,
  ttl: number
) {
  await redis.set(
    key,
    JSON.stringify(value),
    {
      EX: ttl,
    }
  );
}
```

Then:

```ts
const cachedCourse =
  await getCached<Course>(`course:${courseId}`);
```

This gives you type safety at the application level.

# 22. Cache Service Architecture

Since you're following:

```text
Controller
    ↓
Service
    ↓
Repository
```

don't turn your repository into a Redis mess.

A cleaner conceptual architecture is:

```text
Controller
    ↓
Service
    ├── Cache
    └── Repository
            ↓
        PostgreSQL
```

For example:

```text
CourseService
   │
   ├── Redis
   │
   └── CourseRepository
            │
            ↓
       PostgreSQL
```

The service decides:

```text
Should I read from cache?
Should I query the database?
Should I invalidate cache?
```

The repository remains focused on database operations.

This fits very nicely with the architecture you've been learning throughout the project.

---

# 23. Practical Example — Course Service

A simplified version:

```ts
async function getCourse(courseId: string) {
  const key = `course:${courseId}`;

  // Cache
  const cached = await getCached<Course>(key);

  if (cached) {
    return cached;
  }

  // Database
  const course =
    await courseRepository.findById(courseId);

  if (!course) {
    throw new AppError(
      "Course not found",
      404
    );
  }

  // Cache
  await setCached(
    key,
    course,
    300
  );

  return course;
}
```

Update:

```ts
async function updateCourse(
  courseId: string,
  data: UpdateCourseInput
) {
  const course =
    await courseRepository.update(
      courseId,
      data
    );

  await redis.del(
    `course:${courseId}`
  );

  return course;
}
```

The flow is:

```text
GET
 ↓
Redis
 ↓
hit → return

miss
 ↓
PostgreSQL
 ↓
Redis
 ↓
return
```

And:

```text
UPDATE
 ↓
PostgreSQL
 ↓
Invalidate Redis
 ↓
return
```

---

# 24. What Happens If Redis Goes Down?

This is a very important production question.

Suppose:

```text
API
 ↓
Redis ❌
```

Should your entire LMS stop working?

Ideally, **not for cache-only functionality**.

For example:

```text
Redis unavailable
      ↓
Cache unavailable
      ↓
Query PostgreSQL
      ↓
Continue serving request
```

This is called designing for **graceful degradation**.

However, whether Redis failure can be tolerated depends on the feature.

For a simple course cache:

```text
Redis failure → fallback to PostgreSQL
```

For a later job queue:

```text
Redis failure → background job system unavailable
```

That's a different situation.

We'll deal with this more deeply in the queue lessons.

---

# 25. Cache Metrics

Once caching is running, you should measure it.

Useful metrics include:

```text
Cache hits
Cache misses
Hit ratio
Evictions
Memory usage
Average Redis latency
```

A simple metric:

```text
Hit Ratio =
Cache Hits
───────────────
Total Requests
```

Example:

```text
Hits = 900
Misses = 100

Hit ratio = 90%
```

A high hit ratio usually means your cache is helping.

But don't blindly chase a 99% hit rate.

The real question is:

> **Is caching improving the application's performance and reducing unnecessary work?**

# 26. Cache Flow for Your AI LMS

Let's put everything together.

### Reading a course

```text
Student
   ↓
GET /courses/123
   ↓
CourseService
   ↓
Redis
   ↓
┌───────────────┐
│ Cache exists? │
└───────┬───────┘
        │
    ┌───┴───┐
   YES      NO
    ↓        ↓
 Return   PostgreSQL
            ↓
         Redis.set()
            ↓
          Return
```

### Updating a course

```text
Instructor
    ↓
PATCH /courses/123
    ↓
CourseService
    ↓
PostgreSQL UPDATE
    ↓
Redis DEL course:123
    ↓
Response
```

This is the core caching architecture I want you to understand before moving forward.

# 🧠 Interview Questions

After this lesson, you should be able to answer these without memorizing definitions.

### Q1. What is caching?

Your answer should be roughly:

> Caching stores frequently accessed data in a faster storage layer so the application doesn't repeatedly perform expensive operations.

### Q2. What is a cache hit?

```text
Requested data exists in cache.
```

### Q3. What is a cache miss?

```text
Requested data doesn't exist in cache.
```

### Q4. What is cache-aside?

```text
Application checks cache first.
If missing, it gets data from the database and stores it in cache.
```

### Q5. Why use TTL?

```text
To automatically expire cached data and reduce stale data.
```

### Q6. What is cache invalidation?

```text
Removing or updating cached data when the underlying source changes.
```

### Q7. Why shouldn't Redis replace PostgreSQL?

```text
PostgreSQL is the persistent source of truth for relational business data.
Redis is better suited to fast-access, temporary, caching, and coordination workloads.
```

# 🎯 The Mental Model to Remember

Don't memorize Redis commands.

Remember this architecture:

```text
             READ
              │
              ↓
          ┌───────┐
          │ Redis │
          └───┬───┘
              │
        ┌─────┴─────┐
      HIT           MISS
       │              │
       ↓              ↓
    Return       PostgreSQL
                      │
                      ↓
                    Redis
                      │
                      ↓
                   Return
```

And for writes:

```text
             WRITE
               ↓
          PostgreSQL
               ↓
        Invalidate Redis
               ↓
            Return
```

That's the **cache-aside + invalidation** pattern you'll use throughout this project.
