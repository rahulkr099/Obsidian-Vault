# Lesson 11.3 — Session / Temporary Data

The roadmap defines **11.3 as “Session / Temporary Data”**, after Redis Fundamentals and Caching, and before Redis Rate Limiting.

In this lesson, we'll learn **when Redis should hold short-lived data**, how TTL makes that data expire automatically, and how this fits into your AI LMS.

---

## 1. What is temporary data?

Temporary data is information that:

- is needed for a short period
    
- doesn't need permanent storage
    
- can expire automatically
    
- may be recreated if it disappears
    

Examples:

```text
OTP
Password reset token
Email verification token
Temporary session data
Login attempt counters
Temporary AI state
One-time verification codes
Short-lived locks
```

Think:

```text
PostgreSQL
    ↓
Permanent business data

Redis
    ↓
Temporary / short-lived data
```

---

# 2. Why Redis is good for temporary data

Suppose a user requests an OTP.

```text
POST /auth/send-otp
```

We generate:

```text
492831
```

We only need it for 5 minutes.

Putting it in PostgreSQL is possible, but Redis is often a better fit:

```text
Generate OTP
    ↓
Redis
    ↓
TTL = 5 minutes
    ↓
Automatically disappears
```

We don't need a scheduled cleanup job.

---

# 3. TTL is the Key Feature

Remember from 11.2:

```redis
SET otp:user:123 492831 EX 300
```

This means:

```text
Key:
otp:user:123

Value:
492831

Expiration:
300 seconds
```

So:

```text
0 min
 ↓
OTP created

1 min
 ↓
still valid

3 min
 ↓
still valid

5 min
 ↓
expired

5+ min
 ↓
Redis returns nothing
```

This makes Redis extremely useful for temporary information.

# 4. Temporary Data vs Permanent Data

Let's compare.

### User

```text

```

This is permanent business data.

Use:

```text

```

### Password reset token

```text
reset-token:user:123
```

This is temporary.

Use:

```text
Redis
```

So:

```text
User

Reset token
 ↓

```

# 5. Example: OTP System

Let's design a simple OTP flow.

```text
User
 ↓
Enter email
 ↓
POST /auth/send-otp
 ↓
Generate OTP
 ↓
Redis
 ↓
Send email
```

Redis:

```text
otp:user:123 → 492831
TTL → 5 minutes
```

Then the user submits:

```http
POST /auth/verify-otp
```

with:

```json
{
  "otp": "492831"
}
```

Backend:

```text
Request
   ↓
Redis GET otp:user:123
   ↓
Compare OTP
   ↓
Correct?
 ┌──┴──┐
Yes    No
 ↓      ↓
Success Error
```

After successful verification:

```text
DEL otp:user:123
```

This is important because an OTP should generally be **single-use**.

---

# 6. Why Delete After Successful Verification?

Suppose:

```text
OTP = 492831
```

User verifies successfully.

If we leave it in Redis:

```text
otp:user:123 → 492831
```

until the TTL expires, the same OTP might potentially be reused.

Better:

```text
Verify successfully
       ↓
DEL otp:user:123
```

Now:

```text
GET otp:user:123
```

returns:

```text
(nil)
```

So the OTP becomes:

```text
short-lived
+
single-use
```

---

# 7. Important: Hash OTPs Instead of Storing Them Plainly

For a production system, don't casually store sensitive verification secrets in plaintext.

Instead of:

```text
Redis:
otp:user:123 → 492831
```

you can store a cryptographic hash of the OTP and compare the hash of the submitted code.

Conceptually:

```text
Generated OTP
     ↓
Hash
     ↓
Redis
```

Then:

```text
Submitted OTP
     ↓
Hash
     ↓
Compare with Redis
```

This reduces exposure if Redis data is accessed unexpectedly.

For a learning implementation, we'll first understand the flow and then harden it.

# 10. Session Data

Redis can also hold session-related information.

For example:

```text
session:abc123
```

could contain:

```json
{
  "userId": "123",
  "role": "student"
}
```

with:

```text
TTL = 30 minutes
```

Then:

```text
Request
 ↓
Session ID
 ↓
Redis
 ↓
User information
```

However, whether you should use Redis-backed sessions depends on your authentication architecture.

Your LMS has already been designed around authentication concepts such as access tokens and refresh tokens, so **don't automatically replace your existing auth architecture with Redis sessions**.

Instead, understand Redis as an option for temporary session state.

---

# 11. Redis Session vs JWT

This is an important distinction.

### JWT-style authentication

```text
Client
 ↓
Access Token
 ↓
API
 ↓
Verify token
```

The server doesn't necessarily need Redis to verify every access token.

### Redis-backed session

```text
Client
 ↓
Session ID
 ↓
API
 ↓
Redis
 ↓
Session data
```

Redis becomes the place where session state lives.

So:

```text
JWT
→ token carries claims

Session
→ server stores session state
```

Neither is automatically "better."

The correct choice depends on your architecture and requirements.

# 12. Temporary AI Data

Redis can also help your AI LMS.

Suppose a student is having an AI conversation.

You might temporarily maintain:

```text
ai:conversation:123
```

with recent context.

For example:

```text
User:
Explain recursion.

AI:
Recursion is...

User:
Give me an example.

AI:
Here's one...
```

You may not want every piece of temporary state to be stored permanently.

Redis can hold short-lived context:

```text
AI conversation
      ↓
Redis
      ↓
TTL
      ↓
expires
```

However, if your application needs permanent conversation history, that belongs in PostgreSQL.

This distinction is important:

```text
Temporary context
    ↓
Redis

Permanent conversation history
    ↓
PostgreSQL
```

---

# 13. Temporary Data Doesn't Mean Unimportant

This is a common misunderstanding.

"Temporary" does **not** mean "unimportant."

For example:

```text
Password reset token
```

may only live for 15 minutes, but during those 15 minutes it is highly sensitive.

So temporary Redis data still needs:

```text
Authentication
Access control
Network protection
Safe key design
Minimal data
Proper expiration
Logging discipline
```

We'll revisit these topics in Phase 14 security engineering.

# 14. Redis Key Design for Temporary Data

Use descriptive keys.

Instead of:

```text
123
```

use:

```text
otp:user:123
```

Instead of:

```text
abc123
```

use:

```text
password-reset:user:123
```

Instead of:

```text
xyz
```

use:

```text
email-verification:user:123
```

A useful pattern is:

```text
<feature>:<purpose>:<identifier>
```

Examples:

```text
otp:user:123
session:abc123
password-reset:user:123
email-verification:user:123
ai-context:conversation:456
```

---

# 15. Don't Put Sensitive Information in the Key

Avoid:

```text
otp:rahul@example.com
```

when you can use:

```text
otp:user:123
```

Why?

Because Redis keys can appear in:

```text
logs
debugging tools
monitoring systems
error messages
```

Use identifiers instead of sensitive information whenever possible.

# 16. Multiple OTP Requests

Suppose a user clicks:

```text
Send OTP
```

three times.

You could end up with:

```text
OTP 1 → 123456
OTP 2 → 789012
OTP 3 → 456789
```

A clean approach is to use one key:

```text
otp:user:123
```

and overwrite it:

```text
new OTP
    ↓
SET otp:user:123
    ↓
old OTP replaced
```

Then only the newest OTP is valid.

This is a very useful pattern.

---

# 17. OTP Attempt Limits

Here's where temporary data connects to security.

Suppose someone keeps trying:

```text
111111
222222
333333
444444
...
```

We can maintain:

```text
otp:attempts:user:123
```

with a TTL.

Example:

```text
otp:attempts:user:123 → 3
```

Each failed attempt:

```text
INCR otp:attempts:user:123
```

Once the limit is reached:

```text
Too many attempts
```

This starts moving toward **Lesson 11.4 — Redis Rate Limiting**.

So don't implement the complete system here; just understand the relationship.

# 18. Temporary Locks

Redis can also help coordinate operations.

Imagine:

```text
Student
 ↓
Generate certificate
```

Two requests arrive almost simultaneously:

```text
Request A ──┐
            ├──→ Generate certificate
Request B ──┘
```

You don't necessarily want both requests generating the same resource.

A temporary lock can conceptually be:

```text
lock:certificate:user:123
```

with a short TTL.

```text
Request A
   ↓
Acquire lock
   ↓
Process
   ↓
Release lock
```

Meanwhile:

```text
Request B
   ↓
Lock exists
   ↓
Don't process
```

We'll go deeper into distributed locking later when the system requires it.

# 19. Redis TTL Commands

You should become comfortable with these.

### Set expiration

```redis
SET key value EX 300
```

### Check remaining TTL

```redis
TTL key
```

### Delete

```redis
DEL key
```

### Set expiration on existing key

```redis
EXPIRE key 300
```

### Check whether key exists

```redis
EXISTS key
```

For example:

```redis
SET otp:user:123 492831 EX 300
```

Then:

```redis
TTL otp:user:123
```

and:

```redis
EXISTS otp:user:123
```

# 20. Building a Temporary Data Service

Instead of scattering Redis operations throughout your application, you can create a small abstraction.

For example:

```text
src/
├── config/
│   └── redis.ts
│
├── infrastructure/
│   └── redis/
│       └── redis.service.ts
│
└── modules/
    └── auth/
```

The Redis service can provide:

```ts
async setTemporary(
  key: string,
  value: string,
  ttlSeconds: number
) {
  await redis.set(key, value, {
    EX: ttlSeconds,
  });
}
```

And:

```ts
async getTemporary(key: string) {
  return redis.get(key);
}
```

And:

```ts
async removeTemporary(key: string) {
  await redis.del(key);
}
```

Then your authentication service doesn't need to know every Redis command.

---

# 21. Example OTP Service

Conceptually:

```ts
async function createOtp(userId: string) {
  const otp = generateOtp();

  const key = `otp:user:${userId}`;

  await redis.set(key, hashOtp(otp), {
    EX: 300,
  });

  await emailService.sendOtp(otp);
}
```

Verification:

```ts
async function verifyOtp(
  userId: string,
  otp: string
) {
  const key = `otp:user:${userId}`;

  const storedHash = await redis.get(key);

  if (!storedHash) {
    throw new AppError(
      "OTP expired",
      400
    );
  }

  if (!verifyOtpHash(otp, storedHash)) {
    throw new AppError(
      "Invalid OTP",
      400
    );
  }

  await redis.del(key);

  return true;
}
```

The architecture becomes:

```text
AuthService
    │
    ├── Redis
    │     └── Temporary OTP
    │
    └── EmailService
          └── Send OTP
```

# 22. Redis Failure

Now an important production question:

> What if Redis is unavailable when the user requests an OTP?

For temporary data, you need to decide whether Redis is a **required dependency** for that operation.

For example:

```text
POST /auth/send-otp
        ↓
Redis unavailable
        ↓
Cannot safely create temporary OTP state
        ↓
Return controlled error
```

Don't silently pretend the OTP was stored.

This is different from caching.

For caching:

```text
Redis down
   ↓
Maybe fallback to PostgreSQL
```

For OTP storage:

```text
Redis down
   ↓
Temporary state cannot be safely stored
```

So the failure strategy depends on the feature.

# 24. What Should NOT Go Into Redis?

Avoid using Redis as a dumping ground.

Don't automatically put:

```text
Users
Courses
Lessons
Enrollments
Quiz attempts
Certificates
Payments
```

into Redis as the primary storage.

Those belong in PostgreSQL.

Instead:

```text
PostgreSQL
→ durable business state

Redis
→ temporary / cached / coordination state
```

# 26. Important Design Principle

Here's a rule I want you to remember:

> **If the data disappears, can your system recover it or regenerate it?**

If yes, Redis may be a good candidate.

Example:

```text
OTP
```

Can generate another one.

```text
Cache
```

Can rebuild from PostgreSQL.

```text
Temporary session state
```

Can potentially expire.

But:

```text
Course
Enrollment
Quiz attempt
Certificate
```

You cannot casually lose those.

They belong in durable storage.

# 🧠 Interview Questions

### 1. Why use Redis for OTPs?

Because OTPs are short-lived temporary data, and Redis provides fast access plus automatic expiration through TTL.

### 2. Why not store OTPs permanently in PostgreSQL?

You can, but Redis is a natural fit for short-lived state that needs automatic expiration and doesn't represent permanent business data.

### 3. What happens when a Redis key expires?

Redis removes it according to its expiration mechanism, and subsequent reads won't return the expired key.

### 4. What is TTL?

**Time To Live** — the amount of time a key is allowed to remain available before expiration.

### 5. Should sessions always use Redis?

No. Redis-backed sessions are one architectural option. The correct choice depends on the authentication/session design.

### 6. Should Redis be your source of truth?

Generally, for the temporary/caching use cases we're discussing here, **no**. PostgreSQL remains the durable source of truth for your LMS business data.
