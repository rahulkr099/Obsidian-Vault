# 1. What Is Performance Testing?

Performance testing measures how your application behaves under different workloads.

We care about:

```text
Response time
Throughput
Concurrency
Resource usage
Error rate
Database performance
AI latency
```

For example:

```text
10 users
   ↓
API works well

100 users
   ↓
API still works

1,000 users
   ↓
Database becomes slow
```

Performance testing helps us discover where that happens.

---

# 2. Functional vs Performance Testing

Functional testing asks:

```text
Does login work?
```

Performance testing asks:

```text
How quickly does login work
when 500 users log in simultaneously?
```

Functional:

```text
POST /login
   ↓
200 OK
```

Performance:

```text
500 concurrent requests
       ↓
POST /login
       ↓
Response time?
Error rate?
CPU?
Memory?
Database load?
```

Both are necessary.

---

# 3. Important Performance Terms

You should know these terms.

### Latency

How long one request takes.

Example:

```text
GET /courses
   ↓
120 ms
```

### Throughput

How much work the system handles over time.

For example:

```text
500 requests/second
```

### Concurrency

How many operations are happening at the same time.

Example:

```text
100 concurrent users
```

### Error rate

Percentage of failed requests.

```text
10 failures / 1000 requests
= 1%
```

---

# 4. Response Time Percentiles

Don't only look at average response time.

Suppose:

```text
Requests:

50ms
55ms
60ms
70ms
5000ms
```

Average:

```text
~1 second
```

That hides the fact that most requests were fast and one was extremely slow.

Instead, use percentiles.

---

# 5. p50

**p50** means the median.

Roughly:

> 50% of requests are faster than this value.

Example:

```text
p50 = 100ms
```

Half of requests complete within around 100ms.

---

# 6. p95

**p95** means:

> 95% of requests are faster than this value.

Example:

```text
p95 = 300ms
```

This means the slowest 5% are above approximately 300ms.

p95 is very useful for web APIs.

---

# 7. p99

**p99** means:

> 99% of requests are faster than this value.

Example:

```text
p99 = 1.2s
```

Only about 1% are slower.

For user-facing systems, p95 and p99 often reveal problems that averages hide.

---

# 8. Example

Suppose:

```text
GET /api/v1/courses

p50 = 80ms
p95 = 220ms
p99 = 900ms
```

Interpretation:

```text
Typical request:
80ms

Slow requests:
220ms+

Worst 1%:
900ms+
```

You now know there is a tail-latency problem.

# 9. What Is Load Testing?

Load testing means:

> Test the application under an expected workload.

For example:

```text
100 concurrent users
```

performing realistic operations:

```text
Browse courses
Open lessons
Submit quizzes
Ask AI questions
View progress
```

We're asking:

```text
Can the system handle expected traffic?
```

---

# 10. Stress Testing

Stress testing pushes beyond normal expected capacity.

Example:

```text
100 users
200 users
500 users
1000 users
2000 users
```

Eventually:

```text
System
   ↓
Starts degrading
```

We want to discover:

```text
Where does it break?
How does it break?
Can it recover?
```

---

# 11. Spike Testing

Spike testing means suddenly increasing traffic.

Example:

```text
10 users
   ↓
20 users
   ↓
500 users
```

immediately.

This simulates events such as:

```text
Exam starts
New course released
Assignment deadline
College announcement
```

For an LMS, spike testing is particularly useful.

---

# 12. Soak Testing

Soak testing means running a moderate load for a long period.

Example:

```text
100 concurrent users
        ↓
1 hour
```

or:

```text
50 users
   ↓
6 hours
```

It can reveal:

```text
Memory leaks
Connection leaks
Resource exhaustion
Growing queues
Slow degradation
```

---

# 13. Capacity Testing

Capacity testing asks:

> What is the maximum useful workload our system can handle before performance becomes unacceptable?

For example:

```text
100 users    → healthy
250 users    → healthy
500 users    → acceptable
750 users    → degraded
1000 users   → failing
```

Your capacity might be:

```text
~500 concurrent users
```

depending on your defined performance requirements.

---

Monitor:


# 33. Connection Pooling

Your Node application connects to PostgreSQL through a connection pool.

Suppose:

```text
Pool size = 10
```

and:

```text
100 concurrent requests
```

They can't all have a database connection simultaneously.

Some requests wait.

This can produce:

```text
Latency ↑
```

You should monitor:

```text
Active connections
Idle connections
Waiting requests
Connection exhaustion
```

Don't simply increase pool size indefinitely.

Your PostgreSQL server also has limits.

```text

```

```text

```


Performance testing should consider:


# 37. Garbage Collection

Node.js uses garbage collection.

If your application creates lots of temporary objects:

```text
Requests
   ↓
Objects
   ↓
Garbage collection
```

High allocation rates can increase CPU usage and latency.

You don't need to optimize GC immediately.

First:

```text
Measure
   ↓
Identify bottleneck
   ↓
Optimize
```

---

# 38. Event Loop Performance

Node.js has an event loop.

If something blocks it:

```text
Request A
   ↓
CPU-heavy synchronous work
   ↓
500ms
```

other requests can wait.

You can monitor event-loop delay and use profiling tools when needed.

The lesson:

> **Fast I/O doesn't help if your JavaScript thread is blocked.**

# 44. Little's Law

A useful performance concept is:

```text
L = λ × W
```

Where:

```text
L = average number of items in the system
λ = throughput
W = average time in system
```

For example:

```text
Throughput = 20 requests/sec
Average response time = 0.5 sec
```

Then:

```text
L = 20 × 0.5
  = 10
```

Roughly 10 requests are in the system at a time.

You don't need to use this every day, but understanding it helps when reasoning about concurrency and queues.

# 58. Circuit Breaker

A circuit breaker can prevent your application from repeatedly hitting a failing external service.

Conceptually:

```text
Normal
  ↓
Provider failing
  ↓

  ↓

  ↓
Wait
  ↓

```

This can protect your system during provider outages.

You don't necessarily need to implement this now, but performance and resilience testing will eventually make the concept useful.

# 74. Common Performance Mistakes

### ❌ Testing only `/health`

Doesn't represent real usage.

### ❌ Using unrealistic traffic

A thousand requests/sec from one endpoint doesn't necessarily represent users.

### ❌ Ignoring database performance

Backend APIs often become DB-bound.

### ❌ Ignoring p95/p99

Average latency hides slow users.

### ❌ Calling real AI thousands of times

Expensive and unnecessary.

### ❌ Increasing server size immediately

Find the bottleneck first.

### ❌ Adding indexes everywhere

Indexes have costs too.

### ❌ Ignoring connection pools

Can cause production failures.

### ❌ No performance baseline

Then you can't prove improvement.

### ❌ Running tests against production carelessly

Potentially dangerous.
