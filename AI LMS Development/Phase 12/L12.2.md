# 🧪 Lesson 12.2 — Integration Testing

In **12.1**, we tested one small unit in isolation.

Now we move one level higher:

```text
Unit Testing
     ↓
One piece of code
     ↓
Integration Testing
     ↓
Multiple pieces working together
```

For your AI LMS, this is especially important because your backend follows:

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
PostgreSQL
```

Integration testing verifies that these parts **actually cooperate correctly**.

---

# 1. What Is Integration Testing?

Integration testing checks whether multiple components work correctly together.

For example, suppose you have:

```text
Course Controller
       ↓
Course Service
       ↓
Course Repository
       ↓
PostgreSQL
```

A unit test might test:

```text
CourseService
```

by itself.

An integration test might test:

```text
CourseService
      +
CourseRepository
      +
Test Database
```

The goal is to find problems that unit tests cannot detect.

---

# 2. Unit vs Integration Testing

This distinction is extremely important.

### Unit test

```text
Service
  ↓
Mock Repository
```

You are testing the service's own logic.

### Integration test

```text
Service
  ↓
Real Repository
  ↓
Test Database
```

Now you're testing whether the pieces integrate correctly.

Think:

```text
UNIT

Service
  ↓
Fake dependency


INTEGRATION

Service
  ↓
Repository
  ↓
Database
```

---

# 3. Why Do We Need Integration Tests?

Imagine this service:

```ts
async function createCourse(data: CreateCourseInput) {
  return courseRepository.create(data);
}
```

Your unit test passes:

```text
Service test
     ↓
Mock repository
     ↓
✅
```

But maybe your repository contains:

```ts
prisma.course.create({
  data: {
    instructorId: data.userId,
    title: data.title
  }
});
```

and the actual Prisma schema expects:

```text
instructorId
```

to reference a different table or field.

The unit test won't catch that because the repository was mocked.

An integration test can.

```text
Service
   ↓
Repository
   ↓
Prisma
   ↓
PostgreSQL
   ↓
❌ Foreign key error
```

This is exactly why integration testing exists.

---

# 4. Integration Testing in Your Architecture

Your backend architecture is:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

We don't necessarily test all four layers together every time.

Instead, we choose meaningful boundaries.

For example:

```text
Service
   ↓
Repository
   ↓
Database
```

is a useful integration boundary.

Later, API testing can cover:

```text
HTTP
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
```

So the testing layers gradually build up.

---

# 6. Integration Tests Should Use a Test Environment

Never run destructive integration tests against your real production database.

Instead:

```text
Production

PostgreSQL
     ↑
Real application


Testing

Test PostgreSQL
     ↑
Integration tests
```

For your project:

```text
Development DB
Test DB
Production DB
```

should be treated as separate environments.

---

# 7. Why a Real Database Is Useful

You might wonder:

> "Why not mock Prisma?"

Because then you aren't testing the database integration.

Consider:

```text
Prisma schema
      ↓
Migration
      ↓
PostgreSQL
```

There can be problems involving:

```text
Foreign keys
Unique constraints
Nullability
Relations
Transactions
Cascade behavior
Indexes
Database-specific behavior
```

A real test database can catch these.

---

# 8. Test Database Lifecycle

A typical integration-test lifecycle looks like:

```text
Start Test Environment
        ↓
Prepare Database
        ↓
Run Test
        ↓
Verify Data
        ↓
Clean Database
        ↓
Next Test
```

For example:

```text
Before tests
    ↓
Create schema
    ↓
Run tests
    ↓
Reset database
    ↓
Finish
```

We want tests to be isolated from one another.

---

# 9. Test Isolation

Imagine test A creates:

```text
User #1
```

Then test B expects:

```text
Database is empty
```

But User #1 is still there.

Now:

```text
Test A → ✅
Test B → ❌
```

The problem isn't necessarily the application.

It's the test environment.

Good integration tests should be isolated:

```text
Test A
  ↓
Clean DB
  ↓
Test B
  ↓
Clean DB
  ↓
Test C
```

---

# 10. Database Reset Strategies

There are several approaches.

### Strategy 1 — Delete test data

```text
DELETE FROM ...
```

Simple but can become complicated when many tables are related.

### Strategy 2 — Transaction rollback

```text
BEGIN
   ↓
Run test
   ↓
ROLLBACK
```

This can be very fast and useful when the architecture supports it.

### Strategy 3 — Database reset

Reset the test database between tests or test suites.

For your LMS, we'll choose the strategy based on what we're testing and how Prisma/PostgreSQL are configured.

# 11. Integration Testing Relationships

This is where integration testing becomes very valuable for your LMS.

Suppose:

```text
User
  │
  └── Instructor
          │
          └── Course
                  │
                  ├── Section
                  │
                  └── Lesson
```

An integration test can verify that:

```text
Create Instructor
      ↓
Create Course
      ↓
Create Section
      ↓
Create Lesson
```

actually works with the real database relationships.

---

# 12. Example: Course + Instructor

Suppose your Prisma model conceptually contains:

```prisma
model User {
  id      String   @id
  courses Course[]
}

model Course {
  id           String @id
  title        String
  instructorId String
  instructor   User   @relation(...)
}
```

An integration test should verify:

```text
Create user
     ↓
Create course
     ↓
course.instructorId
     ↓
Correct user
```

Then query the database:

```text
Course
  ↓
Instructor
```

and confirm the relationship works.

This catches issues that isolated unit tests cannot.

---

# 13. Testing Constraints

Your database may have constraints such as:

```text
email UNIQUE
course title required
instructorId required
foreign key
```

For example:

```text
Create User
email = rahul@example.com
```

works.

Then:

```text
Create another User
email = rahul@example.com
```

should fail if the email is unique.

An integration test verifies that the actual database enforces this rule.

---

# 14. Testing Transactions

Transactions are another excellent integration-test target.

Imagine enrollment:

```text
Create Enrollment
      ↓
Update Course Enrollment Count
      ↓
Create Activity Log
```

Suppose the third operation fails.

Without a transaction:

```text
Enrollment created       ✅
Count updated            ✅
Activity log             ❌
```

You could end up with inconsistent data.

With a transaction:

```text
BEGIN
   ↓
Enrollment
   ↓
Count
   ↓
Activity Log
   ↓
Failure
   ↓
ROLLBACK
```

Everything is reverted.

Integration testing is the right place to verify this behavior against the real database.

---

# 15. Integration Testing and Prisma

Since your project uses Prisma:

```text
Application
    ↓
Prisma Client
    ↓
PostgreSQL
```

we can test the actual Prisma interaction.

For example:

```ts
const course = await courseRepository.create({
  title: "React Fundamentals",
  instructorId
});
```

Then verify:

```ts
const savedCourse = await prisma.course.findUnique({
  where: {
    id: course.id
  }
});
```

Conceptually:

```text
Repository
    ↓
INSERT
    ↓
PostgreSQL
    ↓
SELECT
    ↓
Verify
```

That's a real integration test.

---

# 16. Don't Make Every Test an Integration Test

This is a common beginner mistake.

Suppose you have:

```text
500 tests
```

and every test does:

```text
Application
 ↓
Prisma
 ↓
PostgreSQL
```

Your test suite can become:

```text
Slow
Fragile
Hard to debug
Expensive to run
```

Instead:

```text
Unit Tests
    ↓
Lots

Integration Tests
    ↓
Moderate

API / E2E
    ↓
Smaller number
```

That's why the testing pyramid is useful.

# 19. Integration Tests and Mocks

You might remember from 12.1:

> Unit tests often use mocks.

Integration tests generally use **fewer mocks**.

For example:

### Unit test

```text
CourseService
     ↓
Mock Repository
```

### Integration test

```text
CourseService
     ↓
Real Repository
     ↓
Real Prisma
     ↓
Test PostgreSQL
```

We still might mock something external, such as an email provider or AI provider.

That's okay.

The goal isn't:

> "Never mock anything."

The goal is:

> **Test the integration boundary that matters.**

---

# 20. Integration Test Example

Conceptually, a test might look like:

```ts
describe("CourseRepository integration", () => {
  it("creates and retrieves a course", async () => {
    const instructor = await createTestUser();

    const course = await courseRepository.create({
      title: "React Fundamentals",
      instructorId: instructor.id
    });

    const saved = await courseRepository.findById(course.id);

    expect(saved).not.toBeNull();
    expect(saved?.title).toBe("React Fundamentals");
    expect(saved?.instructorId).toBe(instructor.id);
  });
});
```

Notice the difference from a unit test.

We're not replacing the repository with a mock.

We're testing the real repository against the test database.

# 21. Integration Test Fixtures

Creating test data repeatedly can become annoying.

For example:

```text
Create user
Create course
Create section
Create lesson
```

for every test.

We can create reusable **test fixtures/factories**.

Conceptually:

```ts
const instructor = await createTestInstructor();

const course = await createTestCourse({
  instructorId: instructor.id
});
```

Then tests become much easier to read.

Later, we'll build proper factories for:

```text
User
Course
Section
Lesson
Enrollment
Quiz
Question
Conversation
Document
```

# 22. Integration Tests Should Be Readable

Compare:

### Hard to understand

```text
test1()
test2()
test3()
```

with:

```text
creates a course with a valid instructor
rejects duplicate enrollment
rolls back enrollment transaction when progress creation fails
```

The second style tells you exactly what behavior the application promises.

Your tests become living documentation.

---

# 23. Common Integration Testing Mistakes

### ❌ Using production database

Never.

```text
TEST → production DB
```

is a dangerous setup.

---

### ❌ Sharing state between tests

```text
Test A creates data
       ↓
Test B accidentally depends on it
```

Tests should be independently runnable.

---

### ❌ Mocking everything

If you mock:

```text
Repository
Prisma
Database
```

then you're barely testing integration.

---

### ❌ Testing too much

Don't make one integration test perform:

```text
Registration
Login
Course creation
Enrollment
Quiz
AI
Certificate
```

Keep tests focused.

---

### ❌ Ignoring cleanup

Test data should not leak into other tests.

# 24. Unit + Integration Together

Now you can see how the two complement each other.

```text
                 Course Feature
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
     Unit Tests             Integration Tests
          │                       │
          ↓                       ↓
Business logic             Service + Repository

```

Unit tests tell you:

> **Does this piece work correctly?**

Integration tests tell you:

> **Do these pieces work correctly together?**

# 🧠 The Most Important Lesson

Don't think:

> "Integration testing means testing everything together."

Instead:

> **Integration testing means deliberately testing the boundaries where components communicate.**

For your architecture:

```text
Service ↔ Repository
Repository ↔ Prisma
Prisma ↔ PostgreSQL
```

are important integration boundaries.

Later:

```text
HTTP ↔ Controller
```

will become an API-testing boundary.

And:

```text
Application ↔ AI Provider
Application ↔ Redis
Application ↔ Email Provider
```

will become important external-service boundaries.
