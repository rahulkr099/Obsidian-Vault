# 🧪 Lesson 12.3 — API Testing

In **12.1**, we tested individual functions.

In **12.2**, we tested multiple internal components working together.

Now we move to the **API boundary**.

The goal is to verify that your API behaves correctly when a real client sends HTTP requests.

```text
Client
  ↓
HTTP Request
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
  ↓
HTTP Response
```

For your AI LMS, API testing will become one of the most useful testing skills because your React/Next.js frontend, mobile clients, or other services will communicate with the backend through these APIs.

---

# 1. What Is API Testing?

API testing means automatically sending requests to your API and checking the responses.

Suppose your LMS has:

```http
POST /api/v1/courses
```

An API test can send:

```json
{
  "title": "React Fundamentals",
  "description": "Learn React from basics"
}
```

and verify:

```text
Status → 201
Response → course created
Database → course exists
```

So instead of manually opening Postman every time:

```text
Postman
   ↓
Send request
   ↓
Look at response
```

we automate it:

```text
Test
  ↓
HTTP request
  ↓
API
  ↓
Assertion
  ↓
✅ / ❌
```

---

# 2. Why API Testing Is Important

Your backend may contain hundreds of functions.

But clients don't directly call:

```ts
createCourseService()
```

They call:

```http
POST /api/v1/courses
```

Therefore, we need to verify the **public contract** of the API.

For example:

```text
POST /courses
        ↓
What status code?
What response?
What validation?
What authentication?
What database change?
```

API testing answers these questions automatically.

---

# 3. API Testing vs Integration Testing

These two are closely related, but the boundary is different.

### Integration test

You might test:

```text
Service
   ↓
Repository
   ↓
Database
```

### API test

You start from:

```text
HTTP
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
```

So:

```text
Integration
     ↓
Internal application boundaries

API testing
     ↓
External HTTP boundary
```

A useful mental model:

> **API tests treat your backend more like a client would.**

---

# 4. What Should an API Test Verify?

A good API test doesn't only check:

```text
status === 200
```

It can verify several things.

### Request

```text
HTTP method
URL
headers
body
query parameters
path parameters
```

### Response

```text
status code
response body
response structure
headers
error format
```

### Side effects

```text
database changes
created records
updated records
deleted records
events/jobs
```

For your LMS, all of these matter.

# 5. Example — Course Creation

Suppose:

```http
POST /api/v1/courses
```

Request:

```json
{
  "title": "React Fundamentals",
  "description": "Learn React"
}
```

A successful test could verify:

```text
Request
   ↓
201 Created
   ↓
Response contains course ID
   ↓
Database contains course
```

Conceptually:

```ts
const response = await request(app)
  .post("/api/v1/courses")
  .set("Authorization", `Bearer ${token}`)
  .send({
    title: "React Fundamentals",
    description: "Learn React"
  });

expect(response.status).toBe(201);
expect(response.body.data.title)
  .toBe("React Fundamentals");
```

The exact testing library/setup will be implemented in the project later; focus first on the testing concepts.

# 6. Test the HTTP Method

The API contract includes the HTTP method.

For example:

```text
GET
POST
PUT
PATCH
DELETE
```

Suppose:

```http
POST /api/v1/courses
```

creates a course.

We should verify that:

```http
GET /api/v1/courses
```

doesn't accidentally perform creation logic.

Likewise:

```http
DELETE /api/v1/courses/:id
```

should actually use the intended deletion behavior.

---

# 7. Test Status Codes

Status codes are part of your API contract.

Common ones:

```text
200 OK
201 Created
204 No Content

400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests

500 Internal Server Error
```

For example:

### Successful creation

```text
POST /courses
      ↓
201 Created
```

### Missing authentication

```text
POST /courses
      ↓
401 Unauthorized
```

### Authenticated student attempting instructor operation

```text
POST /courses
      ↓
403 Forbidden
```

### Course doesn't exist

```text
GET /courses/unknown-id
      ↓
404 Not Found
```

Testing these distinctions is very important.

---

# 8. Don't Just Test Successful Requests

A beginner might write:

```text
Create course
   ↓
201
```

and stop.

Professional API testing also checks failures.

For example:

```text
Missing title
Invalid title
Empty body
Invalid ID
Missing token
Invalid token
Expired token
Wrong role
Duplicate record
Nonexistent resource
Too many requests
```

Think:

```text
        API
         │
   ┌─────┴─────┐
   ↓           ↓
Success      Failure
```

Both paths need tests.

---

# 9. Request Validation Testing

Your backend uses request validation.

Suppose:

```http
POST /api/v1/courses
```

requires:

```json
{
  "title": "React Fundamentals"
}
```

What happens if the client sends:

```json
{}
```

Expected:

```text
400 / 422
```

depending on your API contract.

We should test:

```text
Missing required fields
Wrong data types
Invalid strings
Too-long strings
Unexpected fields
Malformed values
```

For example:

```json
{
  "title": 123
}
```

should not reach your business logic as if it were a valid course title.

---

# 10. Path Parameter Testing

Consider:

```http
GET /api/v1/courses/:courseId
```

We should test:

### Valid ID

```text
GET /courses/abc123
```

### Nonexistent ID

```text
GET /courses/not-found
```

### Malformed ID

```text
GET /courses/!!!
```

### Missing ID

```text
GET /courses/
```

The API should respond according to its contract rather than crashing.

---

# 11. Query Parameter Testing

Your LMS will likely have APIs such as:

```http
GET /api/v1/courses?page=1&limit=10
```

or:

```http
GET /api/v1/courses?search=react
```

We should test:

```text
page
limit
search
sort
order
category
status
```

and invalid values:

```text
page=-1
limit=abc
limit=999999999
```

Your validation layer should handle these safely.

# 14. Authorization Testing Through APIs

Suppose:

```text
POST /api/v1/courses
```

is only available to instructors.

Test:

```text

   ↓

   ↓

```

```text

   ↓
```

# 15. Resource Ownership Testing

This is one of the most important API-testing scenarios for your LMS.

Suppose:

```text
Instructor A
   ↓
Course A

Instructor B
   ↓
Course B
```

Instructor A sends:

```http
PATCH /api/v1/courses/B
```

Expected:

```text
403 Forbidden
```

or possibly:

```text
404 Not Found
```

depending on how your API is designed.

The important thing is:

```text
Instructor A
      ❌
Course B
```

This tests against **IDOR/BOLA-style authorization problems**, which we'll explore more deeply in Phase 14.

---

# 16. Response Schema Testing

Don't only test values.

Test the **shape** of the response.

Suppose:

```json
{
  "success": true,
  "data": {
    "id": "123",
    "title": "React Fundamentals"
  }
}
```

We can verify:

```text
success exists
data exists
data.id exists
data.title exists
```

This is useful because a backend refactor might accidentally change:

```json
{
  "course": {}
}
```

when the frontend expects:

```json
{
  "data": {}
}
```

The API test catches the contract break.

---

# 17. API Contract

Think of your API as a contract:

```text
CLIENT
  │
  │ Request
  ↓
┌─────────────────┐
│       API       │
│                 │
│ Request format  │
│ Status codes    │
│ Response format │
│ Error format    │
└─────────────────┘
  │
  │ Response
  ↓
CLIENT
```

The contract includes:

```text
URL
HTTP method
Request structure
Authentication
Status codes
Response structure
Error structure
```

API tests protect this contract.

---

# 18. Error Response Testing

Your backend has a standardized error architecture.

Suppose the API returns:

```json
{
  "success": false,
  "error": {
    "code": "COURSE_NOT_FOUND",
    "message": "Course not found"
  }
}
```

An API test should verify that structure.

For example:

```text
404
 ↓
success = false
 ↓
error.code = COURSE_NOT_FOUND
```

This is much better than only testing:

```text
status === 404
```

because clients also depend on the error structure.

---

# 19. Testing Headers

HTTP headers can also be part of the contract.

For example:

```text
Content-Type
Cache-Control
Location
Security headers
CORS headers
```

For a successful JSON response:

```text
Content-Type
     ↓
application/json
```

For a creation endpoint, you might also have a `Location` header depending on your API design.

Don't test every header mechanically.

Test headers that are **meaningful to your application's behavior or security**.

# 24. Don't Over-Test Implementation Details

Suppose the controller currently calls:

```ts
courseService.createCourse()
```

Your API test shouldn't care about the exact internal method name.

The test should care about:

```text
POST /courses
    ↓
Correct response
    ↓
Correct behavior
```

Why?

Because you may later refactor:

```text
Controller
 ↓
Service
```

into:

```text
Controller
 ↓
Use Case
 ↓
Service
```

The API contract doesn't need to change.

Good API tests survive internal refactoring.

# 28. What Makes a Good API Test?

A good API test should be:

```text
✅ Fast enough
✅ Repeatable
✅ Independent
✅ Realistic
✅ Focused
✅ Easy to understand
```

For example:

# 30. A More Complete API Test

Conceptually:

```ts
describe("POST /api/v1/courses", () => {
  it("creates a course for an instructor", async () => {
    const instructor = await createTestInstructor();
    const token = await loginAs(instructor);

    const response = await request(app)
      .post("/api/v1/courses")
      .set("Authorization", `Bearer ${token}`)
      .send({
        title: "React Fundamentals",
        description: "Learn React"
      });

    expect(response.status).toBe(201);

    expect(response.body.success).toBe(true);

    expect(response.body.data).toMatchObject({
      title: "React Fundamentals",
      description: "Learn React"
    });
  });
});
```

Then another test:

```ts
it("rejects course creation for a student", async () => {
  // student token
  // POST /courses
  // expect 403
});
```

And:

```ts
it("rejects course creation without authentication", async () => {
  // no token
  // POST /courses
  // expect 401
});
```

The actual syntax may differ depending on the test stack we choose, but the testing logic remains the same.
