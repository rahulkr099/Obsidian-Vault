# 🗄️ Lesson 12.4 — Database Testing

In **12.1**, we tested individual functions.

In **12.2**, we tested components working together.

In **12.3**, we tested the HTTP/API boundary.

Now we focus specifically on the database:

```text
Application
    ↓
Repository
    ↓
Prisma
    ↓
PostgreSQL
```

The goal is to verify that your **data is actually stored, related, constrained, updated, and deleted correctly**.

For your AI LMS, this is especially important because almost every major feature depends on PostgreSQL:

```text
Users
Courses
Lessons
Enrollments
Progress
Quizzes
Questions
AI Conversations
Messages
Documents
Embeddings
```

---

# 1. What Is Database Testing?

Database testing verifies that your application and database behave correctly together.

For example:

```text
Create Course
      ↓
PostgreSQL
      ↓
Course actually exists?
```

We need to verify more than just:

```text
API → 201
```

We also want:

```text
API → 201
       ↓
Database
       ↓
Correct record
       ↓
Correct relationships
       ↓
Correct constraints
```

---

# 2. Why Database Testing Matters

Imagine this API:

```http
POST /api/v1/courses
```

returns:

```text
201 Created
```

You might think:

> "Everything works."

But perhaps the database contains:

```text
course.instructorId = NULL
```

or:

```text
course.title = ""
```

or the wrong user is connected to the course.

The API response alone might not reveal these problems.

Database testing catches them.

# 5. CRUD Testing

CRUD means:

```text
Create
Read
Update
Delete
```

For example, for courses:

```text
Create Course
      ↓
Read Course
      ↓
Update Course
      ↓
Delete Course
```

Each operation should be tested against the real test database.

---

# 6. Create Testing

Suppose:

```ts
const course = await courseRepository.create({
  title: "React Fundamentals",
  instructorId
});
```

We shouldn't only check:

```text
course.id exists
```

We should verify the database.

Conceptually:

```text
Create
  ↓
SELECT
  ↓
Verify
```

For example:

```ts
const savedCourse = await prisma.course.findUnique({
  where: {
    id: course.id
  }
});

expect(savedCourse).not.toBeNull();
expect(savedCourse?.title).toBe("React Fundamentals");
expect(savedCourse?.instructorId).toBe(instructorId);
```

This verifies that the data was actually persisted.

---

# 7. Read Testing

Suppose we create:

```text
Course A
Course B
Course C
```

Then:

```ts
courseRepository.findMany()
```

should return the expected records.

We should test:

```text
No courses
      ↓
[]

One course
      ↓
[Course A]

Multiple courses
      ↓
[Course A, Course B, Course C]
```

We can also test:

```text
Filtering
Sorting
Pagination
Search
```

These become especially important for your LMS course catalog.

---

# 8. Update Testing

Suppose:

```text
React Fundamentals
```

becomes:

```text
Advanced React Fundamentals
```

We should verify:

```text
Before
 ↓
React Fundamentals

UPDATE
 ↓
Advanced React Fundamentals

SELECT
 ↓
Advanced React Fundamentals
```

The important thing is that the **actual database state** changes correctly.

---

# 9. Delete Testing

Deletion needs special attention because your LMS has relationships.

Imagine:

```text
Course
  ↓
Sections
  ↓
Lessons
  ↓
Progress
```

If you delete the course:

```text
What happens to Sections?
What happens to Lessons?
What happens to Enrollments?
What happens to Progress?
```

This is a database design decision.

Your tests should protect that decision.

---

# 10. Foreign Key Testing

Foreign keys are one of the most important things to test.

Suppose:

```text
Course
   ↓
instructorId
   ↓
User
```

A course should not reference a nonexistent user if your schema requires a valid foreign key.

Conceptually:

```text
User #123
   ↓
Course
   ↓
instructorId = 123
```

Valid.

But:

```text
Course
   ↓
instructorId = 999999
```

where user `999999` doesn't exist should fail according to the database/schema rules.

This protects **referential integrity**.

---

# 11. Referential Integrity

Think about:

```text
User
 │
 ├── Course
 │
 └── Enrollment
```

The database should prevent invalid relationships.

For example:

```text
Enrollment
   ↓
studentId
   ↓
User
```

If the user doesn't exist, the enrollment should not become an orphaned record.

Database tests verify these relationships.

---

# 12. Unique Constraint Testing

Suppose your user model has:

```text
email UNIQUE
```

We should test:

```text
User A
email = rahul@example.com
      ↓
Created
```

Then:

```text
User B
email = rahul@example.com
      ↓
Should fail
```

This is different from application validation.

Even if your Zod validation checks the email format, the **database constraint** provides another layer of protection.

---

# 13. Required Fields

Suppose a course requires:

```text
title
instructorId
```

Then:

```text
title = null
```

should fail if the database column is non-nullable.

Likewise:

```text
instructorId = null
```

should fail when the relationship is required.

This protects your data even if something bypasses the normal application validation.

---

# 14. Database Constraints vs Application Validation

This distinction is very important.

You may have:

```text
Request
   ↓
Zod
   ↓
Service
   ↓
Prisma
   ↓
PostgreSQL
```

Zod might say:

```text
title cannot be empty
```

But PostgreSQL might also enforce:

```text
title NOT NULL
```

These serve different purposes.

### Application validation

Provides:

```text
Good user experience
Clear API errors
Early rejection
```

### Database constraints

Provide:

```text
Data integrity
Protection at persistence layer
Consistency
```

Professional applications generally use **both**.

---

# 15. Default Values

Suppose:

```text
createdAt
```

is automatically populated.

A database test should verify:

```text
Create Course
      ↓
createdAt exists
```

Similarly:

```text
isPublished = false
```

might have a default.

Test:

```text
Create Course
      ↓
isPublished === false
```

unless explicitly specified otherwise.

# 16. Testing Relationships

Your LMS database will have many relationships.

For example:

```text
User
  │
  ├─────────────┐
  ↓             ↓
Course       Enrollment
  │
  ↓
Section
  │
  ↓
Lesson
```

Database tests should verify these relationships.

For example:

```text
Create Instructor
      ↓
Create Course
      ↓
Create Section
      ↓
Create Lesson
      ↓
Query Course with relations
```

Expected:

```text
Course
 ├── instructor
 └── sections
       └── lessons
```

---

# 17. Testing One-to-Many Relationships

Example:

```text
Course
  ↓
Sections
```

One course can have many sections.

Test:

```text
Course A
   ↓
Section 1
Section 2
Section 3
```

Then query:

```text
Course A
```

and verify:

```text
sections.length === 3
```

This catches incorrect relation definitions and query mistakes.

---

# 18. Testing Many-to-Many Relationships

Your LMS may eventually have relationships such as:

```text
Students ↔ Courses
```

through:

```text
Enrollment
```

Conceptually:

```text
Student A ──┐
Student B ──┼── Courses
Student C ──┘
```

A student can enroll in multiple courses.

A course can have multiple students.

We should test:

```text
Student A
   ↓
Course 1
Course 2
```

and:

```text
Course 1
   ↓
Student A
Student B
Student C
```

The database must maintain these relationships correctly.

---

# 19. Testing Cascade Behavior

This is one of the most important database tests.

Suppose:

```text
Course
   ↓
Section
   ↓
Lesson
```

If the course is deleted, your schema might specify:

```text
Course deleted
      ↓
Sections deleted
      ↓
Lessons deleted
```

or it might prevent deletion.

Both can be valid designs depending on the business rules.

The important thing is that your test verifies the **intended behavior**.

For example:

```text
Delete Course
     ↓
Query Sections
     ↓
Expected: []
```

if cascade deletion is part of your design.

---

# 20. Soft Delete vs Hard Delete

Your LMS may eventually need to distinguish:

### Hard delete

```text
DELETE
 ↓
Record disappears
```

### Soft delete

```text
deletedAt = timestamp
```

Record remains in the database but is treated as deleted.

Database tests should verify the chosen behavior.

For example:

```text
Soft Delete Course
      ↓
Course still exists
      ↓
deletedAt != null
```

and normal queries should exclude it if that is part of the repository contract.

---

# 21. Transaction Testing

Transactions are extremely important for your backend.

Imagine enrollment:

```text
BEGIN
  ↓
Create Enrollment
  ↓
Create Progress
  ↓
Create Activity Log
  ↓
COMMIT
```

If something fails:

```text
BEGIN
  ↓
Enrollment ✅
  ↓
Progress ❌
  ↓
ROLLBACK
```

After the test:

```text
Enrollment → doesn't exist
Progress   → doesn't exist
Activity   → doesn't exist
```

This is exactly the behavior we want to verify.

---

# 22. Testing Atomicity

A transaction should be **atomic**.

That means:

```text
Everything succeeds
      ↓
COMMIT
```

or:

```text
Something fails
      ↓
ROLLBACK
```

Not:

```text
Some succeeded
Some failed
Data inconsistent
```

A powerful database integration test deliberately causes one operation to fail and checks that the earlier operations were rolled back.

---

# 23. Testing Concurrency

Later, you may have situations like:

```text
Student A
     ↓
Enroll Course

Student B
     ↓
Enroll Course
```

at almost the same time.

Database behavior matters.

Similarly:

```text
Two requests
     ↓
Same resource
     ↓
Concurrent update
```

could create race conditions.

We don't need to solve every concurrency problem in this lesson, but database tests should eventually cover important cases involving:

```text
Transactions
Unique constraints
Concurrent updates
Race conditions
```

Performance/load testing will go deeper into this later.

---

# 24. Testing Prisma Queries

Since we're using Prisma, repositories will contain queries like:

```ts
await prisma.course.findMany(...)
```

or:

```ts
await prisma.course.findUnique(...)
```

or:

```ts
await prisma.course.create(...)
```

A database test should verify that the **real Prisma query produces the intended database behavior**.

For example:

```text
Repository
    ↓
Prisma Query
    ↓
PostgreSQL
    ↓
Expected Result
```

This is much stronger than simply mocking Prisma.

---

# 25. Don't Mock Prisma in Database Tests

Remember the distinction:

### Unit test

```text
Repository
   ↓
Mock Prisma
```

Possible.

### Database integration test

```text
Repository
   ↓
Real Prisma
   ↓
Real test PostgreSQL
```

Preferred.

If you mock Prisma here, you're no longer testing the actual database integration.

---

# 26. Test Database Isolation

Your test database should be separate from:

```text
Development
Production
```

Think:

```text
                PostgreSQL
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   Development     Test      Production
```

Never:

```text
Test
  ↓
Production DB
```

Your test environment should have its own:

```text
DATABASE_URL
```

---

# 27. Database Reset

Suppose:

```text
Test A
  ↓
Create User
```

Then:

```text
Test B
  ↓
Expected no users
```

If Test A's data remains:

```text
Test B → ❌
```

So we need a reliable reset strategy.

Conceptually:

```text
Before suite
     ↓
Prepare database

Test 1
     ↓
Cleanup

Test 2
     ↓
Cleanup

Test 3
     ↓
Cleanup
```

The exact implementation will depend on your Prisma/PostgreSQL setup.

---

# 28. Test Fixtures and Factories

Database tests often need lots of data.

Instead of repeating:

```ts
await prisma.user.create(...)
await prisma.course.create(...)
await prisma.section.create(...)
```

we can create test factories.

For example:

```ts
const instructor = await createTestInstructor();

const course = await createTestCourse({
  instructorId: instructor.id
});
```

Then:

```ts
const lesson = await createTestLesson({
  courseId: course.id
});
```

This makes database tests much easier to read.

---

# 29. Factories Should Produce Valid Data

A test factory should normally create valid default data.

For example:

```text
createTestUser()
```

could generate:

```text
valid email
valid password hash
valid name
valid role
```

Then a specific test overrides what it needs.

For example:

```ts
createTestUser({
  role: "INSTRUCTOR"
});
```

This is much cleaner than manually constructing the entire object in every test.

---

# 30. Testing Data Integrity

A good database test asks:

> "Can invalid application behavior create invalid database state?"

Examples:

```text
Course without instructor
Enrollment without student
Lesson without course
Duplicate enrollment
Message without conversation
Embedding without document
```

If the database design prevents these states, tests should verify that protection.

This distinction is important.

### API test



# 34. A Practical Database Test

Imagine:

```text
createEnrollment(studentId, courseId)
```

A useful database integration test could be:

```text
Arrange
   ↓
Create Student
Create Course

Act
   ↓
Create Enrollment

Assert
   ↓
Enrollment exists

Verify
   ↓
studentId correct
courseId correct
createdAt exists
```

Then a second test:

```text
Same student
+
Same course
+
Second enrollment
       ↓
Constraint/business rule rejects it
```

This gives you strong protection around one important piece of LMS data.

# 35. Testing Database Failures

Don't only test successful database operations.

Think about failures:

```text
Unique constraint violation
Foreign key violation
Transaction failure
Connection failure
Timeout
Invalid data
```

Your application should convert database failures into appropriate application-level errors.

For example:

```text
PostgreSQL
   ↓
Unique constraint error
   ↓
Repository/Service
   ↓
Application error
   ↓
API
   ↓
409 Conflict
```

This connects database testing to API testing from 12.3.

# 36. Testing the Repository Layer

Because your architecture uses:

```text
Controller
   ↓
Service
   ↓
Repository
```

database tests are particularly useful for the repository.

For example:

```text
course.repository.ts
```

might expose:

```text
create()
findById()
findMany()
update()
delete()
```

We can create database tests for each important behavior.

```text
create()
   ↓
DB record exists

findById()
   ↓
Correct record returned

update()
   ↓
Correct fields changed

delete()
   ↓
Correct deletion behavior
```

This creates a strong persistence layer.

---

# 37. What Makes a Good Database Test?

Good database tests are:

```text
✅ Isolated
✅ Repeatable
✅ Deterministic
✅ Using a dedicated test DB
✅ Testing real Prisma/database behavior
✅ Testing meaningful constraints
✅ Cleaning up correctly
```

Avoid:

```text
❌ Production database
❌ Shared test state
❌ Mocking Prisma when testing DB integration
❌ Depending on test execution order
❌ Leaving test data behind
```

# 38. Database Testing Pyramid

You can think of your database tests like:

```text
                 Database
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
       CRUD      Relations   Constraints
        │           │           │
        └───────────┼───────────┘
                    ↓
               Transactions
                    ↓
              Data Integrity
```

The goal isn't to test PostgreSQL itself.

We're testing:

> **Whether our application uses PostgreSQL correctly.**

# 🧠 Most Important Mental Model

Remember this:

> **Your database is not just storage. It is part of your application's correctness system.**

For example:

```text
Application validation
        +
Business logic
        +
Database constraints
        =
Data integrity
```

If your application has a bug, the database should still protect itself where possible.

For your LMS:

```text
Student
   ↓
Enrollment
   ↓
Course
```

should never become invalid just because one application layer made a mistake.
