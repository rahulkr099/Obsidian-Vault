# 🔐 Lesson 12.5 — Authentication Testing

Now we move into testing one of the most important parts of your AI LMS: **authentication**.

So far:

```text
12.1 Unit Testing
        ↓
12.2 Integration Testing
        ↓
12.3 API Testing
        ↓
12.4 Database Testing
        ↓
12.5 Authentication Testing ← YOU ARE HERE
```

Authentication testing asks:

> **Can the right user authenticate successfully, and are invalid or malicious authentication attempts rejected correctly?**

For your LMS, the authentication flow will roughly be:

```text
Register
   ↓
Password Hashing
   ↓
Login
   ↓
Access Token
   ↓
Refresh Token
   ↓
Protected API
   ↓
Logout / Revocation
```

---

# 1. Authentication vs Authorization

Before testing, keep these two concepts separate.

### Authentication

> **Who are you?**

```text
Email + Password
       ↓
     Login
       ↓
   User Identity
```

### Authorization

> **What are you allowed to do?**

```text
Authenticated User
       ↓
Student / Instructor / Admin
       ↓
Permissions
```

So:

```text
Authentication
       ↓
Identity

Authorization
       ↓
Permissions
```

**12.5 focuses on authentication.**

Authorization gets its dedicated lesson in **12.6**.

---

# 2. What Are We Testing?

Your authentication system should eventually contain:

```text
Registration
Login
Password hashing
Access tokens
Refresh tokens
Token expiration
Logout
Session invalidation
Password reset
Email verification
```

We'll test both:

```text
✅ Valid behavior
```

and:

```text
❌ Invalid behavior
```

---

# 3. Authentication Testing Mindset

Don't think:

> "Does login work?"

Think:

```text
Can valid users login?
Can invalid users login?
Can users bypass authentication?
Can expired credentials be reused?
Can tokens be reused after logout?
Can users abuse login?
Can sensitive information leak?
```

That's the mindset of authentication testing.

---

# 4. Registration Testing

Suppose:

```http
POST /api/v1/auth/register
```

Request:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123!"
}
```

A successful registration should produce something like:

```text
Request
   ↓
Validate input
   ↓
Check duplicate user
   ↓
Hash password
   ↓
Create database record
   ↓
Response
```

Our test should verify the entire expected behavior.

---

# 5. Successful Registration

Test:

```text
Valid name
Valid email
Valid password
```

Expected:

```text
201 Created
```

Then verify the database:

```text
User exists
Email is correct
Password is hashed
```

Notice something important:

We should **never expect the database to contain the plaintext password**.

---

# 6. Password Hashing Test

Suppose the user enters:

```text
password123
```

The database should contain something like:

```text
$2b$...
```

or another appropriate password-hash representation.

It should **not** contain:

```text
password123
```

A database/authentication test should verify:

```text
plaintext password
       ❌
       ↓
Database

hashed password
       ✅
       ↓
Database
```

This is a critical security property.

---

# 7. Never Test the Exact Hash

A common mistake would be:

```text
expect(user.password)
  .toBe("$2b$10$....");
```

Don't do this.

Hashes can legitimately differ because secure password hashing normally uses a salt.

Instead, test properties such as:

```text
Password ≠ plaintext
Password hash exists
Correct password verifies
Wrong password fails
```

---

# 8. Duplicate Registration

Suppose:

```text
User A
email = rahul@example.com
```

already exists.

Then:

```text
POST /register
email = rahul@example.com
```

should fail according to your API contract.

For example:

```text
409 Conflict
```

or another chosen error response.

Test:

```text
Existing user
      ↓
Register again
      ↓
Rejected
      ↓
No duplicate user created
```

---

# 9. Invalid Registration Input

Test invalid requests such as:

```text
Missing name
Missing email
Missing password
Invalid email
Empty password
Weak password
Extremely long input
Unexpected fields
```

For example:

```json
{
  "email": "not-an-email",
  "password": "123"
}
```

should never reach the password/database logic as a valid registration.

---

# 10. Login Testing

Now:

```http
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "StrongPassword123!"
}
```

The flow is:

```text
Email + Password
       ↓
Find user
       ↓
Verify password
       ↓
Generate authentication credentials
       ↓
Return response
```

We need to test every important branch.

---

# 11. Successful Login

Valid credentials:

```text
Correct email
Correct password
```

Expected:

```text
200 OK
```

Depending on your architecture, the response may contain or establish:

```text
Access token
Refresh token
Session information
User information
```

The test should verify the contract you designed.

---

# 12. Wrong Password

Suppose:

```text
Email: correct
Password: incorrect
```

Expected:

```text
Authentication rejected
```

Usually:

```text
401 Unauthorized
```

The important thing is that the application does **not** authenticate the user.

```text
Correct email
+
Wrong password
       ↓
❌ No authenticated session
```

---

# 13. Nonexistent User

Suppose:

```text
unknown@example.com
```

doesn't exist.

Attempt login:

```text
unknown@example.com
+
password
```

Expected:

```text
Authentication rejected
```

Usually:

```text
401 Unauthorized
```

---

# 14. Don't Leak Whether an Email Exists

Be careful with error messages.

Bad approach:

```text
"User does not exist"
```

for nonexistent users, while:

```text
"Incorrect password"
```

for existing users.

An attacker can use this to discover registered accounts.

A safer authentication response generally uses a generic message such as:

```text
"Invalid credentials"
```

Your authentication tests should verify that your chosen response doesn't unnecessarily reveal account existence.

---

# 15. Access Token Testing

After login, your application may issue an access token.

Conceptually:

```text
Login
  ↓
Access Token
  ↓
Protected API
```

For example:

```http
GET /api/v1/me
Authorization: Bearer <access-token>
```

Test:

```text
Valid token
    ↓
200
```

and:

```text
Invalid token
    ↓
401
```

---

# 16. Missing Token

Protected endpoint:

```http
GET /api/v1/me
```

No token:

```text
Request
   ↓
Authentication middleware
   ↓
401 Unauthorized
```

This should be one of the basic authentication tests for every protected API group.

---

# 17. Malformed Token

Test things like:

```text
Authorization:
Authorization: Bearer
Authorization: Invalid
Authorization: Bearer abc
```

The application should reject malformed credentials safely.

It should not:

```text
❌ Crash
❌ Return 500
❌ Treat user as authenticated
```

Expected:

```text
401 Unauthorized
```

according to your API contract.

---

# 18. Invalid Signature

Suppose someone modifies a JWT.

Original:

```text
Header.Payload.Signature
```

Attacker modifies:

```text
Header.ModifiedPayload.Signature
```

The signature should no longer be valid.

Test:

```text
Modified token
      ↓
401
```

This verifies that your server actually validates token integrity.

---

# 19. Expired Token

Tokens shouldn't remain valid forever.

Suppose:

```text
Access token
expires in 15 minutes
```

After expiration:

```text
Expired token
      ↓
Protected API
      ↓
401
```

This is extremely important.

Otherwise:

```text
Token stolen
   ↓
Attacker
   ↓
Can use it indefinitely
```

---

# 20. Testing Refresh Tokens

Your architecture uses refresh tokens to obtain new access tokens.

Conceptually:

```text
Access Token
     ↓
Expires
     ↓
Refresh Token
     ↓
New Access Token
```

Test:

```text
Valid refresh token
      ↓
New access token
```

Then:

```text
Invalid refresh token
      ↓
Rejected
```

And:

```text
Expired refresh token
      ↓
Rejected
```

---

# 21. Refresh Token Rotation

If your design uses refresh-token rotation, test:

```text
Refresh Token A
      ↓
Refresh
      ↓
Access Token B
Refresh Token B
```

Then:

```text
Old Refresh Token A
      ↓
Should no longer work
```

This protects against replay attacks.

The exact behavior depends on the refresh-token architecture you implement, but your tests should explicitly protect the chosen behavior.

---

# 22. Refresh Token Database Testing

If refresh tokens or their hashes are stored in PostgreSQL, we should verify:

```text
Login
   ↓
Refresh-token record
   ↓
Database
```

Then:

```text
Logout
   ↓
Refresh token revoked/deleted
```

depending on your implementation.

So authentication testing connects directly to the database testing we covered in **12.4**.

---

# 23. Logout Testing

Suppose:

```http
POST /api/v1/auth/logout
```

After logout:

```text
Refresh token
      ↓
Revoked
```

Then attempt:

```text
POST /refresh-token
```

using the old refresh token.

Expected:

```text
Rejected
```

This is an important test.

A logout endpoint that returns:

```text
200 OK
```

but leaves refresh credentials usable is not doing enough.

---

# 24. Access Token vs Refresh Token

Keep this distinction clear.

### Access token

Usually:

```text
Short-lived
Used frequently
Sent with protected API requests
```

### Refresh token

Usually:

```text
Longer-lived
Used to obtain new access tokens
Needs stronger protection
Can be revoked
```

Testing should treat them differently.

```text
Access token
    ↓
API authorization

Refresh token
    ↓
New access token
```

---

# 25. Token Expiration Testing

You don't want your tests to literally wait 15 minutes.

Instead, the test environment should allow controlled expiration behavior.

Conceptually:

```text
Test clock
   ↓
Token created
   ↓
Advance time
   ↓
Token expires
   ↓
Request
   ↓
401
```

This is much faster and deterministic.

The exact technique depends on the testing framework and token implementation we'll choose.

---

# 26. Password Reset Testing

Your eventual authentication system may have:

```http
POST /api/v1/auth/forgot-password
```

and:

```http
POST /api/v1/auth/reset-password
```

Test the workflow:

```text
Forgot password
      ↓
Reset token
      ↓
Email
      ↓
New password
      ↓
Password updated
```

Then verify:

```text
Old password
    ↓
❌

New password
    ↓
✅
```

---

# 27. Password Reset Token Testing

Reset tokens should have expiration.

Test:

```text
Valid reset token
      ↓
Password reset succeeds
```

Then:

```text
Expired reset token
      ↓
Rejected
```

And:

```text
Already-used reset token
      ↓
Rejected
```

if your implementation makes tokens single-use.

---

# 28. Password Change and Sessions

Suppose an authenticated user changes their password.

Depending on your security policy, existing sessions/tokens may need to be invalidated.

A possible test:

```text
Login
 ↓
Access Token A
 ↓
Change Password
 ↓
Old authentication credentials
 ↓
Expected behavior
```

The exact expectation should be defined by your authentication design.

The important thing is to **test the policy explicitly** rather than leaving it undefined.

---

# 29. Email Verification Testing

If your LMS requires email verification:

```text
Register
   ↓
Verification token
   ↓
Email
   ↓
Verify
   ↓
Account verified
```

Test:

```text
Valid verification token
      ↓
Success
```

and:

```text
Invalid token
      ↓
Rejected
```

and:

```text
Expired token
      ↓
Rejected
```

and, if applicable:

```text
Already-used token
      ↓
Rejected
```

---

# 30. Brute-Force Protection

Authentication endpoints are common targets for automated attacks.

Suppose someone repeatedly tries:

```text
POST /login
```

with different passwords.

Your system may use:

```text
Rate limiting
Account throttling
IP-based controls
Credential protections
```

The test should verify that excessive attempts eventually produce your intended response, such as:

```text
429 Too Many Requests
```

or another controlled behavior.

Don't make your normal test suite accidentally trigger this limit; isolate the test configuration.

---

# 31. Timing and Information Leakage

Authentication can leak information through differences in behavior.

For example:

```text
Existing user + wrong password
```

versus:

```text
Nonexistent user
```

should not expose obvious account enumeration signals.

We don't need to build complicated timing-analysis tests yet.

But we should at least test the **observable API behavior**:

```text
Same generic error
No sensitive details
No stack trace
No password information
```

---

# 32. Sensitive Data Testing

Authentication responses should not accidentally return:

```text
password hash
refresh token database record
security questions
private secrets
internal authentication metadata
```

For example, a `/me` response might contain:

```json
{
  "id": "123",
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "STUDENT"
}
```

but not:

```json
{
  "passwordHash": "...",
  "refreshTokenHash": "..."
}
```

API tests should explicitly check for sensitive-field leakage.

# 34. Authentication Test Flow

A realistic test suite might look like:

```text
              AUTHENTICATION
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   Register       Login       Logout
       │            │            │
       ↓            ↓            ↓
   Password      Access       Revoke
    Hashing       Token        Session
                    │
                    ↓
              Refresh Token
                    │
                    ↓
              Token Rotation
                    │
                    ↓

```

Every important transition should have tests.

# 35. Example: Complete Login Test

Conceptually:

```ts
describe("POST /api/v1/auth/login", () => {
  it("logs in with valid credentials", async () => {
    await createTestUser({
      email: "student@example.com",
      password: "StrongPassword123!"
    });

    const response = await request(app)
      .post("/api/v1/auth/login")
      .send({
        email: "student@example.com",
        password: "StrongPassword123!"
      });

    expect(response.status).toBe(200);
    expect(response.body.data.accessToken).toBeDefined();
  });
});
```

Then:

```ts
it("rejects an incorrect password", async () => {
  // create user
  // login with wrong password
  // expect 401
});
```

Then:

```ts
it("rejects an unknown user", async () => {
  // login with nonexistent email
  // expect 401
});
```

The exact response shape should match **your project's API contract**.

Authentication testing becomes more useful when combined with a protected endpoint.

For example:

```http

```

Test:

```text
No token
   ↓
401

Invalid token
   ↓
401

Expired token
   ↓
401

Valid token
   ↓
200
```

This verifies that authentication isn't just generating tokens—it is actually protecting your API.

# 37. Authentication Testing Layers

We can now combine several testing types:

```text
                    AUTH
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
      Unit      Integration       API
       │             │             │
Password       DB persistence    Login endpoint

```

This gives us much stronger confidence.

---

# 38. Don't Test Only the Happy Path

This is probably the biggest lesson.

Bad:

```text
Login with correct password
        ↓
200
```

Better:

```text
Correct password
Wrong password
Unknown user
Missing fields
Invalid email
Malformed token
Expired token
Revoked token
Refresh token reuse
Logout
Rate limiting
Sensitive data
```

Authentication is a **security boundary**, so failure behavior matters almost as much as success behavior.

---

# 39. Authentication Test Independence

Each authentication test should ideally start with controlled state.

For example:

```text
Test A
Create user
Login
Cleanup

Test B
Create user
Wrong password
Cleanup

Test C
Create user
Refresh token
Cleanup
```

Don't make:

```text
Test B
depends on Test A
```

Otherwise tests can become order-dependent and unreliable.

---

# 40. Authentication Test Data

Create reusable factories:

```text
createTestStudent()
createTestInstructor()
createTestAdmin()
createTestUser()
```

Then:

```ts
const student = await createTestStudent();
```

You can also create:

```text
createExpiredToken()
createInvalidToken()
createRevokedRefreshToken()
```

This makes authentication tests much cleaner.

# 🧠 The Most Important Mental Model

Think of authentication as a state machine:

```text
                   ┌──────────────┐
                   │   Logged Out │
                   └──────┬───────┘
                          │
                       Login
                          │
                          ↓
                   ┌──────────────┐
                   │  Authenticated│
                   └──────┬───────┘
                          │
                    Access Token
                          │
                    ┌─────┴─────┐
                    ↓           ↓
                 Valid        Expired
                    │           │
                    ↓           ↓
                  API        Refresh
                                │
                                ↓
                           New Token
                                │
                                ↓
                         Authenticated
```

Logout:

```text
Authenticated
      ↓
Logout
      ↓
Revoked / invalid session
      ↓
Logged Out
```

Your tests should verify these transitions.

# 🛠️ Practical Exercise

Design tests for this flow:

```text
Register
   ↓
Login
   ↓
Access protected endpoint
   ↓
Refresh token
   ↓
Logout
   ↓
Try refresh again
```

Your expected behavior should be:

```text
1. Registration
   → success

2. Login
   → success

3. Protected endpoint
   → success with valid access token

4. Access token expires
   → rejected

5. Refresh token
   → new access credentials

6. Logout
   → success

7. Reuse old refresh token
   → rejected
```

Then add failure scenarios:

```text
Wrong password
Invalid token
Expired token
Malformed token
Unknown user
Duplicate registration
Invalid reset token
```

If you can design this test flow clearly, you've understood the core of authentication testing.
