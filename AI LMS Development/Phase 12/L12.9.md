# 🌐 Lesson 12.9 — External Service Mocking

In **12.7**, we learned how to test AI services.

In **12.8**, we tested RAG.

Now we solve a problem that appears throughout your AI LMS:

> **How do we test code that depends on external services without actually calling those services every time?**

Your application may communicate with:

```text
AI Provider
Email Provider
OAuth Provider
Cloud Storage
Payment Gateway
Webhooks
Third-party APIs
```

If every test calls the real service, your test suite becomes:

```text
Slow
Expensive
Unreliable
Internet-dependent
Hard to reproduce
```

So we introduce **mocking**.

---

# 1. What Is External Service Mocking?

Suppose your application does:

```text
Your API
   ↓
AI Provider
```

Normally:

```text
Test
 ↓
Your API
 ↓
Internet
 ↓
Real AI Provider
```

Instead:

```text
Test
 ↓
Your API
 ↓
Fake/Mock Provider
 ↓
Controlled Response
```

Now your test controls exactly what the external service does.

---

# 2. Why Mock External Services?

Imagine you have:

```text
1,000 tests
```

and each test calls an external API.

Problems:

### Slow

Network calls take time.

### Expensive

Some APIs charge per request.

### Unreliable

The external service can go down.

### Rate limits

You might receive:

```text
429 Too Many Requests
```

### Non-deterministic

AI responses can change.

### CI problems

Your GitHub Actions runner may not have access to your provider or credentials.

So:

> **External services should usually be replaced with controlled test doubles in most automated tests.**

---

# 3. What Is a Test Double?

"Mock" is often used as a general word, but there are several kinds of test doubles.

The important ones are:

```text
Test Double
    │
    ├── Dummy
    ├── Stub
    ├── Spy
    ├── Mock
    └── Fake
```

Understanding the difference will make your testing much stronger.

---

# 4. Dummy

A dummy is an object that exists only because the code requires something.

It isn't actually used.

Example:

```ts
const dummyLogger = {};
```

Maybe your service requires a logger:

```ts
new UserService(repository, dummyLogger);
```

but the particular test doesn't care about logging.

That's a dummy.

---

# 5. Stub

A stub provides a predetermined response.

Suppose:

```text
UserService
   ↓
EmailService
```

We don't want to send a real email.

Stub:

```ts
emailService.send = async () => ({
  success: true
});
```

Now:

```text
UserService
   ↓
Stub Email Service
   ↓
success
```

We're controlling the dependency's output.

---

# 6. Spy

A spy records what happened.

Suppose:

```text
EmailService.send()
```

We want to know:

```text
Was it called?
How many times?
With what arguments?
```

A spy lets us check:

```text
send()
 ↓
called once
 ↓
with correct email
```

This is useful when testing interactions.

---

# 7. Mock

A mock is generally a test double where we define expected interactions.

For example:

```text
emailService.send()
```

Expected:

```text
called once
with:
recipient = student@example.com
```

If that interaction doesn't happen, the test fails.

Different testing frameworks use the word "mock" somewhat differently, so focus on the behavior rather than terminology.

---

# 8. Fake

A fake is a simplified working implementation.

For example:

```text
Real Email Service
       ↓
SMTP provider
```

Fake:

```text
Fake Email Service
       ↓
Stores emails in memory
```

Instead of actually sending:

```text
email@example.com
```

the fake might store:

```ts
sentEmails.push(email);
```

Then the test can inspect it.

---

# 9. Mock vs Fake

A simple distinction:

```text
Mock/Stub
   ↓
"Return this response."

Fake
   ↓
"Behave like a simplified version."
```

For example:

### Fake storage

```text
upload(file)
   ↓
Store file in memory
```

### Mock storage

```text
upload(file)
   ↓
Return predetermined URL
```

Both are useful.

---

# 10. Why Dependency Injection Helps

External service mocking becomes much easier when your architecture uses dependency injection.

Suppose:

```ts
class CourseService {
  constructor(
    private storage: StorageService
  ) {}
}
```

Production:

```text
CourseService
     ↓
S3Storage
```

Testing:

```text
CourseService
     ↓
FakeStorage
```

This is one of the biggest benefits of the architecture you've been learning.

---

# 11. External Service Interface

You can define an abstraction:

```ts
interface StorageService {
  upload(file: File): Promise<{
    url: string;
  }>;

  delete(key: string): Promise<void>;
}
```

Production implementation:

```text
S3StorageService
```

Testing implementation:

```text
FakeStorageService
```

Your application doesn't need to know the difference.

# 17. Webhook Testing

External services may call your application.

For example:

```text
Payment Provider
       ↓
POST /api/v1/webhooks/payment
       ↓
Your Server
```

You can simulate the external service:

```text
Fake webhook
   ↓
Your API
```

Then test:

```text
Valid signature
Invalid signature
Duplicate event
Unknown event
Malformed payload
```

This is extremely useful for real-world backend development.

---

# 18. Mocking External APIs with an HTTP Mock

Another approach is to intercept HTTP requests.

Suppose your code calls:

```text
POST https://api.example.com/generate
```

Instead of reaching the internet:

```text
Test
 ↓
HTTP Mock
 ↓
Fake Response
```

This is useful when the code under test directly uses an HTTP client.

Conceptually:

```text
axios/fetch
    ↓
HTTP interceptor
    ↓
Fake API response
```

This lets you test your actual HTTP integration code.

---

# 19. When to Use an HTTP Mock

Use an HTTP mock when you specifically want to test:

```text
HTTP method
URL
Headers
Request body
Query parameters
Response parsing
Status codes
```

For example:

```text
Your service
   ↓
HTTP client
   ↓
Mock external API
```

This is different from simply replacing the entire provider class.

---

# 20. Two Levels of External Mocking

You can mock at different boundaries.

### Level 1 — Dependency mock

```text
Service
 ↓
Mock provider
```

Fast and simple.

### Level 2 — HTTP mock

```text
Service
 ↓
Real HTTP client
 ↓
HTTP mock server/interceptor
 ↓
Fake API
```

More realistic.

A good test suite can use both.

# 22. Don't Mock Too Much

There's a danger:

```text
Everything mocked
```

Then your tests may pass while the real integration is broken.

For example:

```text
Mock:
axios
AI provider
database
repository
service
controller
```

What are you actually testing?

Almost nothing meaningful.

Therefore:

> **Mock the boundary you don't control, not everything around the code under test.**

---

# 23. The Dependency Boundary

This is the most useful mental model.

Suppose:

```text
Your Code
   ↓
External API
```

The boundary is here:

```text
Your Code │ External Service
          │
          ↓
       Mock Here
```

Keep:

```text
Your logic → REAL
```

Replace:

```text
External dependency → FAKE/MOCK
```

# 24. Test External Failures

External services don't only succeed.

Test:

```text
200 Success
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
429 Rate Limited
500 Server Error
502 Bad Gateway
503 Unavailable
Timeout
Network Failure
```

You don't necessarily need every status code for every service.

Test the failures your application actually handles.

---

# 25. Example: AI Provider 429

Suppose:

```text
AI Provider
   ↓
429 Too Many Requests
```

Your application might:

```text
Retry
   ↓
Backoff
   ↓
Try again
```

or:

```text
Return controlled error
```

A mock should simulate the provider's response.

Then verify your actual retry/error-handling logic.

Suppose:

```text
       ↓

```

Now what should happen?

This is a business decision.

Maybe:

```text

```

```text

```


# 28. Mocking Timeouts

Suppose:

```text
External API
   ↓
Never responds
```

Your test should simulate:

```text
Timeout
```

without actually waiting 30 seconds.

For example:

```text
Fake dependency
   ↓
throws TimeoutError immediately
```

Then verify:

```text
Application
   ↓
Controlled error
```

This keeps tests fast.

---

# 29. Mocking Network Errors

You should also test:

```text
ECONNRESET
ECONNREFUSED
DNS failure
Network unavailable
```

You don't need every low-level network error.

But your external integration should have a generic failure path.

For example:

```text
Network failure
   ↓
Service error
   ↓
503
```

according to your application's error contract.

---

# 30. Mocking Environment Variables

External services usually require:

```text
API_KEY
BASE_URL
CLIENT_ID
CLIENT_SECRET
```

Tests shouldn't use production credentials.

Instead:

```text
TEST_API_KEY
TEST_BASE_URL
```

or fake values.

For example:

```text
AI_API_KEY=test-key
```

The mock provider doesn't need a real secret.

---

# 31. Never Put Real Secrets in Tests

Avoid:

```text
OPENAI_API_KEY=sk-real-key
```

inside:

```text
Git repository
Test file
CI logs
Fixture
```

Use:

```text
Fake credentials
Environment-specific secrets
Secret manager in CI
```

Real credentials should only exist where actually required.

---

# 32. Contract Testing

Now we reach a more advanced concept.

Suppose your application expects an external API to return:

```json
{
  "id": "123",
  "status": "success"
}
```

The provider changes it to:

```json
{
  "requestId": "123",
  "state": "completed"
}
```

Your application may break.

**Contract testing** helps protect the assumptions between systems.

Think:

```text
Your Service
      ↕
API Contract
      ↕
External Provider
```

---

# 33. Consumer-Driven Contracts

Your application is the **consumer**.

The external API is the **provider**.

Your tests can document:

```text
Request:
POST /generate

Expected:
200

Response:
{
  id,
  output
}
```

If the provider changes its API, the contract test can expose the mismatch.

This becomes increasingly useful in microservices and large systems.

---

# 34. Don't Overuse Contract Tests

For your current AI LMS:

You don't need dozens of complicated contract tests.

Start with:

```text
Important external APIs
Critical request/response shapes
Authentication requirements
Error formats
```

Use contract testing where a provider's interface is important enough to justify it.

# 41. External Service Idempotency

Some operations should not happen twice.

For example:

```text
Payment
   ↓
Charge customer
```

If the network times out:

```text
Client doesn't know whether payment succeeded
```

Retrying blindly could cause:

```text
Double charge
```

Therefore external APIs often use **idempotency keys**.

Tests should verify:

```text
Same operation
+
Same idempotency key
       ↓
No duplicate effect
```

This is especially important if your LMS eventually has payments.

---

# 42. Webhook Duplicate Testing

External services may send the same webhook more than once.

Example:

```text
payment.completed
      ↓
Webhook
      ↓
Your server
```

Provider retries:

```text
payment.completed
      ↓
Same webhook again
```

Your application should avoid processing the event twice when appropriate.

Test:

```text
Webhook #1
   ↓
Processed

Webhook #2
   ↓
Recognized as duplicate
   ↓
No duplicate side effect
```

This is an important real-world backend test.

---

# 43. Testing Webhook Signatures

```text

   ↓

   ↓

```

Test:

```text

   ↓
Accepted
```

and:

```text
Invalid signature
   ↓
Rejected
```

This connects external-service mocking with security testing.

---

# 44. External Service Mocking and Logging

When an external provider fails, your application should log useful information.

For example:

```text
Provider: AI
Operation: generate
Error: timeout
Request ID: ...
```

But avoid logging:

```text
API keys
Access tokens
Refresh tokens
Sensitive user content
```

Tests can verify that your error mapping doesn't accidentally expose secrets.

# 46. What Should Remain Real?

A common question is:

> "If we mock everything, what are we actually testing?"

Good question.

Keep **your code** real.

For example:

```text
Controller          REAL
Service             REAL
Repository          REAL
Validation          REAL
Business logic      REAL
Error mapping       REAL

External API        MOCK
```

For database integration tests:

```text
PostgreSQL          REAL TEST DB
Prisma              REAL
Repository          REAL
External API        MOCK
```

This gives you meaningful confidence.

---

# 47. External Mocking Levels

A useful table:

|Test type|Your code|Database|External API|
|---|---|---|---|
|Unit|Real|Mock|Mock|
|Integration|Real|Real test DB|Mock|
|API|Real|Real test DB|Mock|
|Contract|Real client|Usually irrelevant|Mock/provider contract|
|E2E|Real|Real test DB|Selected real/sandbox|
|AI Evaluation|Real|Real/controlled|Real AI|

This isn't an absolute rule, but it's a useful default.

---

# 48. Common Mistakes

### ❌ Calling real external APIs in every test

Too slow and expensive.

### ❌ Mocking your own business logic

Then you're testing your mocks.

### ❌ Mocking the database in database tests

That defeats the purpose.

### ❌ Never testing real integration

Mocks can hide integration mistakes.

### ❌ Using production credentials

Dangerous.

### ❌ Ignoring provider failure

Real providers fail.

### ❌ Forgetting duplicate webhooks

Can create duplicate side effects.

### ❌ Retrying non-idempotent operations blindly

Can cause duplicate operations.

# 49. A Good External Service Test

A strong test usually looks like:

```text
Arrange
   ↓
Create fake dependency
   ↓
Configure response

Act
   ↓
Call real application code

Assert
   ↓
Application behavior
```

For example:

```text
Arrange:
FakeEmailProvider → success

Act:
Register user

Assert:
User created
Email sent once
Correct recipient
Correct verification token
```

---

# 50. A Good Failure Test

```text
Arrange:
FakeStorage → throws timeout

Act:
Upload document

Assert:
Controlled application error
No invalid database state
No leaked provider details
```

This is the kind of test that catches real production bugs.

---

# 51. A Good Retry Test

```text
Arrange:
Provider:
  Call 1 → 503
  Call 2 → 503
  Call 3 → success

Act:
Call service

Assert:
3 provider calls
Final result successful
Retry limit respected
```

Then:

```text
Call 1 → 503
Call 2 → 503
Call 3 → 503

Expected:
Final controlled failure
```

---

# 52. External Service Testing Checklist

For each external dependency, ask:

```text
1. What does our application send?
2. What does it expect back?
3. What happens on success?
4. What happens on 4xx?
5. What happens on 5xx?
6. What happens on timeout?
7. What happens on network failure?
8. Is retry appropriate?
9. Is the operation idempotent?
10. What happens after partial failure?
11. Can we safely mock it?
12. Do we need a real integration test?
```

This is an excellent checklist for your backend projects.
