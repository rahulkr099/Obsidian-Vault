# Lesson 13.1 — Docker Fundamentals 🐳

This is the **first lesson of Phase 13 — Docker, CI/CD & Production**.

Our goal today is not to memorize Docker commands. We want to understand **why Docker exists, how it works, and how it will fit into your AI LMS architecture**.

---

## 1. What is Docker?

Docker is a platform that lets us package an application together with the environment it needs to run.

Think about a normal Node.js application:

```text
Your Application
      +
Node.js
      +
npm packages
      +
System dependencies
      +
Environment configuration
```

Without Docker, another developer might get:

```text
"It works on my machine."
```

because their environment is different.

Docker tries to solve this by packaging the application into a **container**.

```text
Application
     +
Dependencies
     +
Runtime
     ↓
 Docker Image
     ↓
 Docker Container
```

---

# 2. The Problem Docker Solves

Imagine your AI LMS backend requires:

```text
Node.js 22
PostgreSQL 17
Redis
Prisma
Environment variables
Specific npm packages
```

Your machine might have:

```text
Node.js 22
PostgreSQL 17
Redis 7
```

But another developer might have:

```text
Node.js 20
PostgreSQL 16
Redis 6
```

Now something could behave differently.

Docker gives us a reproducible environment.

```text
              Docker
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
 Developer              Production
       │                   │
       └──── Same Image ───┘
```

The idea is:

> **Build once, run consistently in different environments.**

---

# 3. Docker vs Virtual Machine

This is one of the most important concepts.

### Virtual Machine

A VM generally contains:

```text
Physical Machine
       ↓
Operating System
       ↓
Hypervisor
       ↓
Virtual Machine
       ↓
Guest OS
       ↓
Application
```

For example:

```text
Host Linux
   ↓
VM
   ↓
Ubuntu
   ↓
Node.js
   ↓
Application
```

The VM has its own complete operating system.

---

### Docker Container

Docker containers share the host's kernel while isolating the application environment.

Conceptually:

```text
Host Operating System
        │
     Docker
        │
 ┌──────┼────────┐
 ↓      ↓        ↓
App  PostgreSQL Redis
```

This usually makes containers much lighter than full VMs.

### Simple comparison

|Virtual Machine|Container|
|---|---|
|Includes guest OS|Shares host kernel|
|Usually heavier|Usually lightweight|
|Slower startup|Fast startup|
|Larger resource usage|Lower overhead|
|Strong OS-level isolation|Process-level isolation|

Don't think:

> "Docker is a lightweight VM."

That's a useful beginner analogy, but technically they work differently.

---

# 4. What Is a Container?

A **container is a running instance of an image**.

Think:

```text
Image
  ↓
Container
```

Similar to:

```text
Class
  ↓
Object
```

An image is the packaged blueprint.

A container is the running thing created from that blueprint.

For example:

```text
node:22 image
      ↓
Node container
```

---

# 5. What Is a Docker Image?

A Docker image is a **read-only template** used to create containers.

For your backend, we might eventually create:

```text
AI LMS Backend Image
```

which contains things such as:

```text
Node.js runtime
Application code
Production dependencies
Configuration needed by the application
```

Then:

```text
AI LMS Backend Image
        ↓
   Container #1
```

and potentially:

```text
AI LMS Backend Image
        ↓
   Container #1
   Container #2
   Container #3
```

The same image can be used to create multiple containers.

---

# 6. Image vs Container

Remember this distinction:

```text
IMAGE
─────
Blueprint / package

CONTAINER
─────────
Running instance of that image
```

Example:

```text
node:22
   ↓
Docker Image
   ↓
Container
   ↓
Running Node.js application
```

This distinction will become very important when we learn deployment.

---

# 7. Docker Engine

Docker needs something that actually manages containers.

That's the **Docker Engine**.

Conceptually:

```text
You
 │
 │ docker run
 ↓
Docker CLI
 │
 ↓
Docker Engine
 │
 ├── Images
 ├── Containers
 ├── Networks
 └── Volumes
```

The Docker Engine is responsible for running and managing containers.

Let's verify Docker on your Linux Mint system.


```text
Docker version 28.x.x
```

The exact version doesn't matter for this lesson.

Then:

```bash

```

# 10. Your First Container

Let's run a very simple container:

```bash
docker run hello-world
```

Docker will roughly perform:

```text
docker run
    ↓
Find hello-world image locally
    ↓
If missing → download image
    ↓
Create container
    ↓
Start container
    ↓
Run program
    ↓
Program exits
```

You'll get a message explaining that Docker successfully ran a container.

---

# 11. What Happened Internally?

When you executed:

```bash
docker run hello-world
```

you didn't manually:

```text
download source code
install dependencies
configure environment
start application
```

Docker handled the container lifecycle.

Conceptually:

```text
docker run hello-world
        │
        ↓
   Docker Engine
        │
        ↓
  hello-world image
        │
        ↓
   New container
        │
        ↓
      Run
        │
        ↓
     Exit
```

---

# 12. Why Did the Container Stop?

This is a common beginner question.

You might run:

```bash
docker ps
```

and see nothing.

But:

```bash
hello-world
```

ran successfully.

Why?

Because the container's main process finished.

A container normally lives while its main process is running.

For example:

```text
Container
   ↓
Node server running
   ↓
Container keeps running
```

But:

```text
Container
   ↓
hello-world prints message
   ↓
Program exits
   ↓
Container stops
```

This is an extremely important Docker concept.

---

# 13. Running a Long-Lived Container

Let's run an Nginx container:

```bash
docker run -d nginx
```

Here:

```text
-d
```

means **detached mode**.

Docker starts the container in the background.

Now:

```bash
docker ps
```

You should see an Nginx container running.

Something like:

```text
CONTAINER ID   IMAGE   STATUS
abc123         nginx   Up ...
```

---

# 14. Container Names

Docker automatically generates names.

You can give your container a meaningful name:

```bash
docker run -d --name my-nginx nginx
```

Now:

```bash
docker ps
```

will show:

```text
my-nginx
```

This becomes useful when managing multiple services.

For our LMS, we'd eventually have names conceptually like:

```text
lms-api
lms-postgres
lms-redis
```

---

# 15. Stopping a Container

Stop Nginx:

```bash
docker stop my-nginx
```

Check:

```bash
docker ps
```

It should no longer appear because `docker ps` shows running containers.

To see stopped containers too:

```bash
docker ps -a
```

You might see:

```text
my-nginx
Exited
```

---

# 16. Removing a Container

Remove it:

```bash
docker rm my-nginx
```

Then:

```bash
docker ps -a
```

It should be gone.

Remember:

```text
docker stop
    ↓
Stops container

docker rm
    ↓
Removes container
```

Stopping and removing are different operations.

---

# 17. Images vs Containers Again

After running Nginx:

```bash
docker images
```

you'll find an image such as:

```text
nginx
```

Then:

```bash
docker ps -a
```

shows the container created from that image.

So:

```text
nginx IMAGE
     │
     ├── Container A
     ├── Container B
     └── Container C
```

One image can create multiple containers.

# 18. Docker Ports

Here's an important concept for web development.

Suppose Nginx inside the container listens on:

```text
Port 80
```

The container has its own networking environment.

Your browser, however, needs a way to access it from your machine.

We map ports:

```bash
docker run -d --name my-nginx -p 8080:80 nginx
```

The syntax is:

```text
HOST_PORT:CONTAINER_PORT
```

So:

```text
8080:80
```

means:

```text
Your Computer
localhost:8080
       │
       ↓
Docker Container
port 80
       │
       ↓
Nginx
```

Now open:

```text
http://localhost:8080
```

and you should see the Nginx page.

# 19. Why Port Mapping Matters for Our LMS

```text
3000
```

```text
8080:3000
```

```text
Browser
   ↓
localhost:8080
   ↓
Docker
   ↓
LMS API container :3000
```

Later, production networking will become more sophisticated.

# 20. Docker Volumes

Containers are designed to be replaceable.

But databases need persistent data.

Imagine:

```text
PostgreSQL container
       ↓
Student data
Course data
Progress data
```

If the container disappears, we don't want the database to disappear with it.

That's why Docker provides **volumes**.

Conceptually:

```text
PostgreSQL Container
        │
        ↓
     Volume
        │
        ↓
 Persistent Data
```

We'll study this properly in **Lesson 13.4 — PostgreSQL Container**.

For now, remember:

> **Container = application environment; Volume = persistent data.**

---

# 21. Docker Networks

Our LMS will eventually have multiple containers:

```text
Backend
PostgreSQL
Redis
```

They need to communicate.

Docker networks allow containers to communicate with each other.

Conceptually:

```text
        Docker Network
             │
      ┌──────┼──────┐
      ↓      ↓      ↓
   Backend  DB     Redis
```

Later your backend might connect to PostgreSQL using the service/container name rather than `localhost`.

For example:

```text
postgresql:5432
```

instead of:

```text
localhost:5432
```

This is a very important concept we'll use in Docker Compose.

# 22. Environment Variables

Your application has configuration such as:

```text
DATABASE_URL
REDIS_URL
JWT_SECRET
AI_API_KEY
```

We shouldn't hard-code these into the Docker image.

Instead:

```text
Docker Container
      ↑
Environment Variables
```

For example:

```bash
docker run -e NODE_ENV=production my-lms-api
```

Later we'll handle production secrets more securely.

```text
                 Docker
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
    Images     Containers    Volumes
       │           │           │
       │           │           └── Persistent data
       │           │

       │
       └── Blueprints
```

And:

```text
Containers
    │
    ↓
Networks
    │
    ↓
Service communication
```

# 25. Important Docker Commands

Don't try to memorize hundreds of commands.

For now, know these:

|Command|Purpose|
|---|---|
|`docker --version`|Check Docker|
|`docker info`|Docker system information|
|`docker images`|List images|
|`docker ps`|Running containers|
|`docker ps -a`|All containers|
|`docker run`|Create + start container|
|`docker stop`|Stop container|
|`docker start`|Start stopped container|
|`docker rm`|Remove container|
|`docker rmi`|Remove image|
|`docker logs`|View container logs|
|`docker exec`|Execute command inside container|

These will become second nature through practice.
