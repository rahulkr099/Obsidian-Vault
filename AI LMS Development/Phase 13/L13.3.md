# Lesson 13.3 — Docker Compose 🐳

In **13.2**, we learned how to create a Docker image for a TypeScript backend.

But our AI LMS will not have only one service.

Eventually we'll have:

```text
AI LMS Backend
      │
      ├── PostgreSQL
      │
      └── Redis
```

Running all of these manually would become annoying.

That's where **Docker Compose** comes in.

---

# 1. What Is Docker Compose?

Docker Compose lets us define and run **multiple Docker containers as one application stack**.

Instead of doing this:

```bash
docker run ...
docker run ...
docker run ...
```

we can define everything in one file:

```text
docker-compose.yml
```

and run:

```bash
docker compose up
```

Conceptually:

```text
              Docker Compose
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      API       PostgreSQL     Redis
```

For your AI LMS, this will become extremely useful.

---

# 2. Why Do We Need Compose?

Imagine manually starting your LMS:

```bash
docker run ai-lms-api
docker run postgres
docker run redis
```

Then you need to configure:

```text
ports
environment variables
networks
volumes
dependencies
health checks
```

Now imagine doing this every morning.

Not fun. 😄

Compose allows us to describe the whole environment as configuration.

```text
compose.yaml
      ↓
API
PostgreSQL
Redis
Networks
Volumes
Environment
```

Then:

```bash
docker compose up
```

starts the stack.

---

# 3. Docker Compose vs Docker

Think of the relationship like this:

```text
Docker
  ↓
Runs individual containers

Docker Compose
  ↓
Coordinates multiple containers
```

For example:

```text
Docker:

Backend container
```

while Compose:

```text
Compose
  │
  ├── Backend
  ├── PostgreSQL
  └── Redis
```

---

# 4. The Compose File

Modern Docker Compose commonly uses:

```text
compose.yaml
```

You may also see:

```text
docker-compose.yml
```

Both are widely used.

For our project, we'll use:

```text
compose.yaml
```

Example:

```yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"

  postgres:
    image: postgres:17

  redis:
    image: redis:7
```

This already describes three services.

---

# 5. What Is a Service?

A service represents a container configuration in Compose.

Here:

```yaml
services:
  api:
  postgres:
  redis:
```

we have three services:

```text
api
postgres
redis
```

Conceptually:

```text
api
 ↓
AI LMS Backend

postgres
 ↓
PostgreSQL

redis
 ↓
Redis
```

Compose uses these service definitions to create and manage the containers.

---

# 6. The `api` Service

```yaml
services:
  api:
    build: .
```

This means:

> Build the API image using the Dockerfile in the current directory.

So if you have:

```text
backend/
├── Dockerfile
├── compose.yaml
├── package.json
└── src/
```

then:

```yaml
build: .
```

uses that directory as the build context.

---

# 7. `image` vs `build`

This is an important distinction.

### `image`

```yaml
postgres:
  image: postgres:17
```

means:

> Use an existing image.

Docker will obtain:

```text
postgres:17
```

### `build`

```yaml
api:
  build: .
```

means:

> Build an image using our Dockerfile.

So:

```text
PostgreSQL
   ↓
Existing Image
```

while:

```text
AI LMS API
   ↓
Our Dockerfile
   ↓
Our Image
```

---

# 8. Port Mapping

For our API:

```yaml
api:
  build: .
  ports:
    - "3000:3000"
```

This means:

```text
Host
localhost:3000
     ↓
Container
:3000
```

Same concept we learned in 13.2.

---

# 9. PostgreSQL Service

Let's make the PostgreSQL service more realistic:

```yaml
postgres:
  image: postgres:17
  environment:
    POSTGRES_USER: lms_user
    POSTGRES_PASSWORD: lms_password
    POSTGRES_DB: ai_lms
```

Now PostgreSQL starts with:

```text
Username:
lms_user

Password:
lms_password

Database:
ai_lms
```

For learning, this is fine.

For production, we should **not hard-code real secrets** like this.

We'll handle production environment management in **13.6**.

---

# 10. PostgreSQL Port

We could write:

```yaml
postgres:
  image: postgres:17
  ports:
    - "5432:5432"
```

This makes PostgreSQL available from your host:

```text
localhost:5432
```

But there's an important point.

### Containers don't necessarily need host ports to communicate.

The API can communicate with PostgreSQL through the Compose network.

So eventually we may not need to expose PostgreSQL publicly to the host at all.

This is a very important production principle:

> **Only expose ports that actually need to be accessed from outside the Docker network.**

---

# 11. Redis Service

Similarly:

```yaml
redis:
  image: redis:7
```

Our architecture becomes:

```text
               Docker Compose
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
      API       PostgreSQL      Redis
     :3000         :5432        :6379
```

---

# 12. Compose Networking

This is one of the most important concepts in today's lesson.

When Compose creates the application stack, services can communicate over the Compose network.

For example:

```text
api
 │
 │ postgres:5432
 ↓
postgres
```

and:

```text
api
 │
 │ redis:6379
 ↓
redis
```

Notice something important:

We're using:

```text
postgres
redis
```

instead of:

```text
localhost
```

---

# 13. Why `localhost` Is Wrong Here

Suppose your API is running inside:

```text
api container
```

and you configure:

```text
DATABASE_URL=postgresql://localhost:5432/ai_lms
```

What does `localhost` mean?

It means:

```text
api container itself
```

not the PostgreSQL container.

So the API won't find PostgreSQL there.

Instead:

```text
DATABASE_URL=postgresql://lms_user:password@postgres:5432/ai_lms
```

Here:

```text
postgres
```

is the Compose service name.

The network resolves it to the PostgreSQL container.

---

# 14. Service Names Become Hostnames

This is a very useful mental model:

```yaml
services:
  api:
  postgres:
  redis:
```

Inside the Compose network:

```text
postgres → PostgreSQL service
redis    → Redis service
api      → API service
```

Therefore:

```text
api → postgres:5432
api → redis:6379
```

This is one of the biggest differences between normal local development and containerized development.

---

# 15. Complete Development Compose File

Let's create a simple version:

```yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
      DATABASE_URL: postgresql://lms_user:lms_password@postgres:5432/ai_lms
      REDIS_URL: redis://redis:6379
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: lms_user
      POSTGRES_PASSWORD: lms_password
      POSTGRES_DB: ai_lms
    ports:
      - "5432:5432"

  redis:
    image: redis:7
    ports:
      - "6379:6379"
```

This is already a useful local development stack.

---

# 16. `depends_on`

Look at:

```yaml
depends_on:
  - postgres
  - redis
```

This tells Compose that the API depends on those services.

Conceptually:

```text
PostgreSQL ──┐
             ├──→ API
Redis ───────┘
```

However, there's an important detail:

> `depends_on` does not automatically guarantee that PostgreSQL is fully ready to accept connections.

It mainly controls startup ordering.

Later we'll improve this with **health checks**.

---

# 17. Start the Entire Stack

From the directory containing `compose.yaml`:

```bash
docker compose up
```

Compose will:

```text
Read compose.yaml
      ↓
Build API image
      ↓
Pull PostgreSQL image
      ↓
Pull Redis image
      ↓
Create network
      ↓
Create containers
      ↓
Start services
```

You'll see logs from multiple services.

---

# 18. Run in Background

Instead:

```bash
docker compose up -d
```

The `-d` means detached mode.

Your terminal remains available.

Then:

```bash
docker compose ps
```

You should see something conceptually like:

```text
NAME              SERVICE     STATUS
project-api       api         running
project-postgres  postgres    running
project-redis     redis       running
```

# 19. View Logs

```bash

```

Only API:

```bash

```

```bash
docker compose logs -f api
```

The `-f` means follow.

This is very useful during development.

# 20. Stop the Stack

Run:

```bash

```

This stops and removes the containers and network created by the Compose project.

Conceptually:

```text
docker compose up
       ↓
Create environment

docker compose down
       ↓
Remove environment
```

# 21. What Happens to PostgreSQL Data?

This is where volumes become important.

If PostgreSQL doesn't use a volume:

```text
PostgreSQL Container
      ↓
Container removed
      ↓
Data may be lost
```

We want:

```text
PostgreSQL Container
      ↓
Docker Volume
      ↓
Persistent Database Data
```

We'll cover PostgreSQL volumes deeply in **13.4**.

---

# 22. Add a PostgreSQL Volume

For example:

```yaml
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: lms_user
      POSTGRES_PASSWORD: lms_password
      POSTGRES_DB: ai_lms
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

Now:

```text
PostgreSQL
    │
    ↓
postgres_data
    │
    ↓
Persistent storage
```

If the container is recreated, the data can remain in the volume.

---

# 23. Why the Volume Path Looks Strange

PostgreSQL stores its database files inside its container filesystem.

For the official PostgreSQL image, the standard data directory is:

```text
/var/lib/postgresql/data
```

We map:

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data
```

Meaning:

```text
Docker Volume
postgres_data
      ↓
Container
/var/lib/postgresql/data
```

---

# 24. Redis Volume

For our initial Redis development setup, persistence may not be necessary depending on how we use Redis.

Remember:

```text
PostgreSQL
→ permanent application data

Redis
→ cache / temporary data / queues
```

Some Redis workloads do need persistence, though, and we'll decide based on the specific use case in **13.5**.

Don't automatically treat Redis as "database storage" just because it stores data.

# 26. Custom Network

Compose automatically creates a network for the project.

You can also explicitly define one:

```yaml
networks:
  lms-network:
```

Then:

```yaml
services:
  api:
    networks:
      - lms-network

  postgres:
    networks:
      - lms-network

  redis:
    networks:
      - lms-network

networks:
  lms-network:
```

Architecture:

```text
             lms-network
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
      API     PostgreSQL  Redis
```

For a simple Compose project, the default network is often enough.

We'll use explicit networks when they improve clarity or when we need multiple networks.

# 34. Important: Don't Put Everything in One Container

A common beginner approach is:

```text
One container
 ├── Node
 ├── PostgreSQL
 └── Redis
```

Avoid that.

Prefer:

```text
API Container
PostgreSQL Container
Redis Container
```

Why?

Each service has a separate responsibility.

```text
API
→ application logic

PostgreSQL
→ relational data

Redis
→ cache/queues/temporary data
```

This follows the principle of **separation of concerns**.

# 35. Health Checks

A production-quality Compose setup should eventually know whether services are actually healthy.

For PostgreSQL, we can eventually use:

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U lms_user -d ai_lms"]
  interval: 10s
  timeout: 5s
  retries: 5
```

Conceptually:

```text
PostgreSQL starts
      ↓
Health check
      ↓
Ready? ── No → Keep waiting
      │
     Yes
      ↓
Healthy
```

We'll use this more seriously as we approach production.

---

# 36. Environment Variables — Don't Do This in Production

Our learning example contains:

```yaml
POSTGRES_PASSWORD: lms_password
```

That's okay for a throwaway local environment.

But don't use this pattern for real production secrets.

Eventually we'll use:

```text
Environment
     ↓
Secrets
     ↓
Application
```

rather than committing secrets to GitHub.

This becomes **Lesson 13.6 — Production Environment**.

# 37. Common Mistakes

### ❌ Mistake 1

Using:

```env
DATABASE_URL=...@localhost:5432/...
```

inside the API container.

Use:

```text
postgres:5432
```

instead.

---

### ❌ Mistake 2

Assuming `depends_on` means PostgreSQL is ready.

It doesn't guarantee application readiness.

Use health checks where necessary.

---

### ❌ Mistake 3

Deleting the Compose environment without thinking about volumes.

Always understand:

```bash
docker compose down
```

versus commands that explicitly remove volumes.

Don't casually delete database volumes.

---

### ❌ Mistake 4

Putting all services into one container.

Keep:

```text
API
DB
Redis
```

separate.

---

### ❌ Mistake 5

Hard-coding production secrets.

Local development:

```text
temporary password
```

is fine.

Production:

```text
secret management
```

is required.
