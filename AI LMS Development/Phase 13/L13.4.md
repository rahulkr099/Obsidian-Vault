# Lesson 13.4 — PostgreSQL Container 🐘🐳

In **13.3**, we created a Compose environment with:

```text
AI LMS API
     │
     ├── PostgreSQL
     │
     └── Redis
```

Today we'll focus specifically on **PostgreSQL inside Docker** and connect it properly to your **Prisma-based backend**.

The goal is:

```text
TypeScript API
      ↓
Prisma
      ↓
Docker Network
      ↓
PostgreSQL Container
      ↓
Docker Volume
      ↓
Persistent Database
```

---

# 1. Why Run PostgreSQL in Docker?

Normally, you might install PostgreSQL directly on Linux:

```text
Linux Mint
   ↓
PostgreSQL
   ↓
Database
```

That's perfectly valid.

But for our AI LMS, Docker gives us a reproducible development environment:

```text
Docker Compose
      │
      ↓
PostgreSQL Container
```

Anyone who clones the project can eventually run:

```bash
docker compose up
```

and get the same PostgreSQL environment.

No need to manually install and configure PostgreSQL first.

---

# 2. PostgreSQL Container Architecture

Our local environment should eventually look like:

```text
                 Docker Compose
                       │
              ┌────────┴────────┐
              ↓                 ↓
          API Container     PostgreSQL
              │             Container
              │                 │
              │                 ↓
              │            Docker Volume
              │                 │
              └──── Network ────┘
```

The API doesn't communicate with PostgreSQL through:

```text
localhost
```

Instead:

```text
postgres:5432
```

because `postgres` will be the Compose service name.

---

# 3. PostgreSQL Image

In `compose.yaml`:

```yaml
services:
  postgres:
    image: postgres:17
```

This tells Docker:

> Use the PostgreSQL 17 image.

Docker will download it if it doesn't already exist locally.

You can verify images with:

```bash
docker images
```

---

# 4. PostgreSQL Environment Variables

The official PostgreSQL image uses environment variables to initialize the database.

Example:

```yaml
postgres:
  image: postgres:17
  environment:
    POSTGRES_USER: lms_user
    POSTGRES_PASSWORD: lms_password
    POSTGRES_DB: ai_lms
```

This creates:

```text
User:
lms_user

Password:
lms_password

Database:
ai_lms
```

Think of it as:

```text
POSTGRES_USER
      ↓
Database user

POSTGRES_PASSWORD
      ↓
User password

POSTGRES_DB
      ↓
Initial database
```

---

# 5. Important: Initialization Happens on First Creation

There's an important Docker/PostgreSQL behavior to understand.

These variables are primarily used when PostgreSQL initializes a **new data directory**.

Suppose:

```text
POSTGRES_PASSWORD=abc
```

and PostgreSQL initializes its database.

Later you change:

```text
POSTGRES_PASSWORD=xyz
```

but the existing PostgreSQL volume still contains the initialized database.

Changing the Compose environment variable doesn't automatically recreate the database credentials.

This is one reason understanding volumes is important.

---

# 6. Why We Need a Volume

Imagine we run PostgreSQL:

```text
PostgreSQL Container
       ↓
Database files
```

Then:

```bash
docker compose down
```

The container is removed.

If the database data only existed inside the container filesystem, we'd risk losing it.

Instead:

```text
PostgreSQL Container
       │
       ↓
Docker Volume
       │
       ↓
Persistent Database Files
```

The container becomes replaceable while the data remains persistent.

---

# 7. PostgreSQL Volume Configuration

Add:

```yaml
services:
  postgres:
    image: postgres:17

    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

Let's break this down.

```yaml
- postgres_data:/var/lib/postgresql/data
```

means:

```text
postgres_data
      ↓
/var/lib/postgresql/data
```

inside the PostgreSQL container.

---

# 8. Named Volumes

This:

```yaml
volumes:
  postgres_data:
```

creates a Docker-managed named volume.

Check volumes:

```bash
docker volume ls
```

You'll eventually see something similar to:

```text
DRIVER    VOLUME NAME
local     ai-lms_postgres_data
```

The exact name can depend on the Compose project name.

---

# 9. Volume Lifecycle

Suppose:

```text
postgres_data
      ↓
PostgreSQL data
```

Then:

```bash
docker compose down
```

normally removes the containers and network, but the named volume remains.

Then:

```bash
docker compose up
```

can create a new PostgreSQL container using the same volume.

So:

```text
Old PostgreSQL Container
        ↓
      removed
        ↓
postgres_data remains
        ↓
New PostgreSQL Container
        ↓
Same database data
```

That's exactly what we want during development.

---

# 10. Be Careful With Volumes

There's a dangerous command:

```bash
docker compose down -v
```

The `-v` means remove associated volumes.

So:

```bash
docker compose down
```

is very different from:

```bash
docker compose down -v
```

Think:

```text
down
 ↓
Remove containers/network

down -v
 ↓
Remove containers/network
 +
Remove volumes
```

If your database is stored in that volume:

```text
down -v
   ↓
Database data deleted
```

So don't casually run:

```bash
docker compose down -v
```

when you care about your development database.

---

# 11. Exposing PostgreSQL Port

You can configure:

```yaml
ports:
  - "5432:5432"
```

This means:

```text
Your Linux machine
localhost:5432
       ↓
PostgreSQL container
5432
```

This is useful if you want to connect with:

- PostgreSQL CLI
    
- DBeaver
    
- pgAdmin
    
- Prisma Studio
    
- another local tool
    

---

# 12. Does the API Need Port 5432 Exposed?

No.

This is an important distinction.

The API can connect to PostgreSQL through the Docker network:

```text
API
 ↓
postgres:5432
 ↓
PostgreSQL
```

without PostgreSQL being exposed to your host.

So we could have:

```yaml
postgres:
  image: postgres:17
```

without:

```yaml
ports:
  - "5432:5432"
```

The database would still be reachable from other containers on the Compose network.

This is often preferable for production.

---

# 13. Local Development vs Production

For local development, exposing:

```text
5432:5432
```

can be convenient.

For production, you usually don't want:

```text
Internet
    ↓
PostgreSQL:5432
```

Instead:

```text
Internet
   ↓
API
   ↓
Private Network
   ↓
PostgreSQL
```

This is an important security principle.

---

# 14. Complete PostgreSQL Service

A good development configuration:

```yaml
services:
  postgres:
    image: postgres:17

    environment:
      POSTGRES_USER: lms_user
      POSTGRES_PASSWORD: lms_password
      POSTGRES_DB: ai_lms

    ports:
      - "5432:5432"

    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

This gives us:

```text
PostgreSQL 17
     │
     ├── User: lms_user
     ├── Database: ai_lms
     ├── Host Port: 5432
     └── Persistent Volume
```

```bash
docker compose up -d postgres
```

Then:

```bash
docker compose ps
```

---

# 16. Check PostgreSQL Logs

Run:

```bash
docker compose logs postgres
```

For continuous logs:

```bash
docker compose logs -f postgres
```

Look for a message indicating PostgreSQL is ready to accept connections.

Don't confuse:

```text
Container started
```

with:

```text
Database ready
```

The application might start before PostgreSQL has finished initializing.

# 17. Connect Using `psql`

If `psql` exists on your machine, you can connect through the mapped port:

```bash
psql -h localhost -p 5432 -U lms_user -d ai_lms
```

It will ask for the password.

Enter:

```text
lms_password
```

for this local learning setup.

---

# 18. Connect From Inside the Container

You can also use:

```bash
docker compose exec postgres psql -U lms_user -d ai_lms
```

This is particularly useful because you don't need PostgreSQL installed on your host.

Conceptually:

```text
Linux Mint
   │
   ↓
Docker Compose
   │
   ↓
PostgreSQL Container
   │
   ↓
psql
```

# 20. Docker + Prisma

Now we connect the pieces.

Suppose your API has:

```env
DATABASE_URL="postgresql://lms_user:lms_password@postgres:5432/ai_lms"
```

Notice:

```text
@postgres:5432
```

not:

```text
@localhost:5432
```

Why?

Because inside the API container:

```text
postgres
```

resolves to the PostgreSQL Compose service.

Architecture:

```text
API Container
     │
     │ DATABASE_URL
     ↓
postgres:5432
     │
     ↓
PostgreSQL Container
```

---

# 21. Prisma Doesn't Need to Know About Docker

This is an important architectural idea.

Prisma only sees:

```text
DATABASE_URL
```

For example:

```env
DATABASE_URL="postgresql://lms_user:lms_password@postgres:5432/ai_lms"
```

Prisma connects to PostgreSQL.

Docker is responsible for making:

```text
postgres
```

reachable.

So responsibilities remain separated:

```text
Docker
 ↓
Runtime/networking

Prisma
 ↓
Database access

PostgreSQL
 ↓
Database engine
```

# 27. PostgreSQL Health Checks

Let's improve our Compose configuration.

```yaml
postgres:
  image: postgres:17

  environment:
    POSTGRES_USER: lms_user
    POSTGRES_PASSWORD: lms_password
    POSTGRES_DB: ai_lms

  volumes:
    - postgres_data:/var/lib/postgresql/data

  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U lms_user -d ai_lms"]
    interval: 10s
    timeout: 5s
    retries: 5
```

The important part:

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U lms_user -d ai_lms"]
```

PostgreSQL provides:

```text
pg_isready
```

to check whether the server is accepting connections.

---

# 28. Why Health Checks Matter

Without health checks:

```text
API starts
   ↓
Immediately connects to PostgreSQL
   ↓
PostgreSQL isn't ready
   ↓
Connection error ❌
```

With health checks:

```text
PostgreSQL starts
       ↓
Health check
       ↓
Not ready
       ↓
Keep checking
       ↓
Ready ✅
       ↓
API can connect
```

This becomes important for reliable deployments.

---

# 29. `depends_on` + Health Check

We can combine them.

For example:

```yaml
services:
  api:
    build: .
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:17

    environment:
      POSTGRES_USER: lms_user
      POSTGRES_PASSWORD: lms_password
      POSTGRES_DB: ai_lms

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lms_user -d ai_lms"]
      interval: 10s
      timeout: 5s
      retries: 5
```

Now Compose can use PostgreSQL's health status when deciding when to start the API.

# 33. Backup Is Different From a Volume

Very important:

> A Docker volume is **not a backup strategy**.

A volume protects against things like:

```text
Container recreation
Container replacement
```

But it doesn't automatically protect you from:

```text
Disk failure
Accidental deletion
Corruption
Ransomware
Bad migration
Human error
```

Production databases need actual backups.

We'll cover production database considerations later.

# 34. Common Mistakes

### ❌ Mistake 1 — Using `localhost` from API container

Wrong:

```text
postgresql://...@localhost:5432/ai_lms
```

Correct inside Compose:

```text
postgresql://...@postgres:5432/ai_lms
```

---

### ❌ Mistake 2 — No volume

```yaml
postgres:
  image: postgres:17
```

works, but your persistence strategy isn't defined.

Use:

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data
```

---

### ❌ Mistake 3 — Running `down -v` casually

```bash
docker compose down -v
```

can delete your database volume.

---

### ❌ Mistake 4 — Thinking container health means database health

A container can be running while PostgreSQL isn't ready.

That's why:

```text
healthcheck
```

matters.

---

### ❌ Mistake 5 — Exposing PostgreSQL unnecessarily

Don't expose:

```text
5432
```

to the host unless you actually need it.

For production, databases should generally stay on a private network.

# 35. Recommended Development `compose.yaml`

For this stage, a reasonable version is:

```yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
      DATABASE_URL: postgresql://lms_user:lms_password@postgres:5432/ai_lms
      REDIS_URL: redis://redis:6379
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started

  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: lms_user
      POSTGRES_PASSWORD: lms_password
      POSTGRES_DB: ai_lms
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lms_user -d ai_lms"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7

volumes:
  postgres_data:
```

This is still a **development configuration**.

Don't treat those credentials as production-safe.

# 🧠 What You Should Remember

There are **five concepts** I really want you to remember from this lesson.

### 1. PostgreSQL is a separate service

```text
API ≠ Database
```

They should run independently.

### 2. Use the service name inside Docker

```text
postgres:5432
```

not:

```text
localhost:5432
```

when connecting from another container.

### 3. Use volumes for persistence

```text
PostgreSQL
    ↓
postgres_data
```

### 4. Health checks matter

```text
Container running
      ≠
Database ready
```

### 5. Volume ≠ Backup

```text
Volume
→ persistence

Backup
→ disaster recovery
```

Both are important in production.
