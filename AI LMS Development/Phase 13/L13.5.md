# Lesson 13.5 — Redis Container ⚡

In **13.4**, we containerized PostgreSQL and connected it to the API through the Docker network.

Now we'll do the same for **Redis**.

Redis will support several parts of your AI LMS:

```text
Redis
 ├── Caching
 ├── Rate limiting
 ├── Sessions / temporary data
 ├── Background jobs
 ├── Queues
 └── Job coordination
```

The goal today is:

```text
AI LMS API
    │
    ├──────────────→ PostgreSQL
    │
    └──────────────→ Redis
                         │
                    Docker Container
```

---

# 1. What Is Redis?

Redis is an in-memory data store.

Unlike PostgreSQL, which is primarily your application's persistent relational database, Redis is commonly used for **fast temporary or operational data**.

Think:

```text
PostgreSQL
    ↓
Long-term application data

Redis
    ↓
Fast temporary/operational data
```

For your LMS:

```text
PostgreSQL
 ├── Users
 ├── Courses
 ├── Lessons
 ├── Enrollments
 └── Progress

Redis
 ├── Cache
 ├── Rate limits
 ├── Job queues
 └── Temporary state
```

---

# 2. Why Do We Need Redis?

Imagine a student opens a course page.

Your API might repeatedly query:

```text
Course
 ├── Instructor
 ├── Sections
 ├── Lessons
 └── Metadata
```

PostgreSQL can handle this.

But if the same information is requested thousands of times, we may not want every request to hit PostgreSQL.

Instead:

```text
Request
   ↓
Redis
   ↓
Cached result
```

This can reduce database work and improve response time.

# 6. Redis Port

Redis uses:

```text
6379
```

```bash

  --name my-redis \
```

```text

6379
```

# 8. Redis Service Name

This is important.

If your Compose file says:

```yaml
services:
  redis:
    image: redis:7
```

then the service hostname is:

```text
redis
```

So from the API container:

```text
redis:6379
```

works.

Don't use:

```text
localhost:6379
```

from inside the API container.

Remember the rule from 13.4:

```text
Inside container:

localhost
   ↓
This same container
```

Whereas:

```text
redis
   ↓
Redis service/container
```

---

# 9. Redis URL

A common Redis connection URL is:

```env
REDIS_URL="redis://redis:6379"
```

Break it down:

```text
redis://
   ↓
Redis protocol

redis
   ↓
Docker Compose service name

6379
   ↓
Redis port
```

So:

```text
redis://redis:6379
```

means:

> Connect to the Redis service on port 6379.

```ts
const redisUrl = process.env.REDIS_URL;
```

Conceptually:

```text
Environment
     ↓
REDIS_URL
     ↓
Redis Client
```

# 11. Redis Client

Node.js applications need a Redis client library.

Common choices include:

```text
redis
ioredis
```

For our architecture, the important concept is independent of the specific library:

```text
Node.js
   ↓
Redis Client
   ↓
Redis Server
```

For example, with the official `redis` package:

```bash
npm install redis
```

Then:

```ts
import { createClient } from "redis";

const client = createClient({
  url: process.env.REDIS_URL,
});

await client.connect();
```

The important part is:

```ts
process.env.REDIS_URL
```

rather than hard-coding:

```ts
"redis://localhost:6379"
```

# 12. Basic Redis Operations

Redis stores data as key/value-style data.

For example:

```text
Key:
course:123

Value:
course information
```

Conceptually:

```text
course:123 → {...}
```

You can set:

```text
SET course:123 "Introduction to React"
```

and retrieve:

```text
GET course:123
```

Redis is extremely fast because its core operations are designed around in-memory data access.

# 15. Redis Data Is Not the Same as PostgreSQL Data

This distinction is extremely important.

Suppose we have:

```text
Student:
Rahul

Course:
Node.js Backend
```

These are core application records.

They belong in:

```text
PostgreSQL
```

But:

```text
Cached course response
```

can belong in:

```text
Redis
```

So:

```text
PostgreSQL
→ Source of truth

Redis
→ Fast operational layer
```

This is a very useful production architecture principle.

# 16. Cache Example

Suppose:

```text
GET /courses/123
```

Normally:

```text
Request
   ↓
API
   ↓
PostgreSQL
   ↓
Course
```

With Redis caching:

```text
Request
   ↓
API
   ↓
Redis
   │
   ├── Cache hit → Return result
   │
   └── Cache miss
           ↓
       PostgreSQL
           ↓
       Store in Redis
           ↓
       Return result
```

This is the basic cache-aside pattern.

---

# 17. Cache-Aside Pattern

Suppose:

```text
course:123
```

doesn't exist in Redis.

Then:

```text
Redis
  ↓
MISS
  ↓
PostgreSQL
  ↓
Course found
  ↓
Redis SET
  ↓
Return course
```

Next request:

```text
Redis
  ↓
HIT
  ↓
Return course
```

This can significantly reduce repeated database queries.

---

# 18. TTL — Time To Live

We usually don't want cached data to remain forever.

Redis supports expiration.

Example:

```text
SET course:123 "React Course" EX 300
```

`300` means:

```text
300 seconds
= 5 minutes
```

After that:

```text
course:123
    ↓
Expires
```

This is called:

> **TTL — Time To Live**

---

# 19. Why TTL Matters for an LMS

Imagine caching:

```text
Course listing
```

for:

```text
5 minutes
```

That's reasonable.

But caching:

```text
Student's payment status
```

for a long time could be problematic.

So caching isn't simply:

```text
"Put everything in Redis."
```

You need to decide:

```text
What?
How long?
When to invalidate?
Is stale data acceptable?
```

This is real backend engineering.

---

# 20. Cache Invalidation

Suppose:

```text
Course title:
"Node.js Basics"
```

is cached.

Then instructor changes it to:

```text
"Advanced Node.js"
```

But Redis still contains:

```text
Node.js Basics
```

Now we have stale data.

We need invalidation.

Possible approach:

```text
Instructor updates course
        ↓
PostgreSQL updated
        ↓
Delete Redis cache
        ↓
Next request
        ↓
Fetch fresh data
        ↓
Store new cache
```

Conceptually:

```text
UPDATE course
     ↓
INVALIDATE course:123
```

Cache invalidation is one of the hardest parts of caching, so we should design it carefully.

---

# 21. Redis for Rate Limiting

You already learned rate limiting earlier.

Redis is useful when the application runs across multiple API instances.

Imagine:

```text
             Load Balancer
                  │
          ┌───────┴───────┐
          ↓               ↓
       API #1           API #2
          │               │
          └───────┬───────┘
                  ↓
                Redis
```

Both API instances can share rate-limit state.

For example:

```text
user:123
requests = 97
```

Without shared Redis state, each API instance might maintain its own counter.

That can make distributed rate limiting inaccurate.

# 22. Redis for Background Jobs

This is particularly important for your AI LMS.

Suppose an instructor uploads a large course PDF.

We don't necessarily want:

```text
HTTP request
   ↓

   ↓

   ↓
```

Instead:

```text

    ↓
API
    ↓
Queue job
    ↓
Redis
    ↓
Background Worker
    ↓
Extract text
    ↓
Chunk
    ↓
Generate embeddings
    ↓
Store vectors
```

Redis can act as part of the queue infrastructure.

We'll explore this deeply in Phase 11, but now Docker gives us the infrastructure to run Redis locally.

# 23. Redis for Temporary AI State

Our AI tutor might need temporary state such as:

```text
Conversation processing
Rate limits
Temporary job status
Short-lived locks
Streaming coordination
```

Redis can be useful here.

But don't automatically put permanent conversation history into Redis.

For example:

```text
AI conversation history
```

that users expect to persist could belong in:

```text
PostgreSQL
```

while:

```text
temporary AI generation state
```

could belong in:

```text
Redis
```

Again:

```text
PostgreSQL → durable source of truth
Redis → fast temporary/operational state
```

---

# 24. Redis Persistence

Redis can persist data to disk using mechanisms such as:

```text
RDB
AOF
```

But this doesn't mean Redis should automatically replace PostgreSQL.

For our LMS:

```text
PostgreSQL
→ primary durable database

Redis
→ cache / queues / temporary operational data
```

If a cache disappears:

```text
Redis lost
   ↓
Application can rebuild cache
```

If your primary student/course database disappears:

```text
PostgreSQL lost
   ↓
Major data loss
```

That's a very different situation.

---

# 25. Do We Need a Redis Volume?

For a pure cache:

```text
Usually not necessary.
```

If Redis is being used for important durable queues or persistent operational data, the decision becomes more nuanced.

For example:

```text
Cache
→ disposable

Queue
→ may need recovery guarantees

Critical persistent state
→ should probably live in PostgreSQL or another durable store
```

So don't blindly add:

```yaml
volumes:
  - redis_data:/data
```

just because PostgreSQL has a volume.

Choose persistence based on the Redis workload.

# 28. Complete Development Stack

At this point your Compose architecture can look like:

```yaml

      test: ["CMD-SHELL", "pg_isready -U lms_user -d ai_lms"]

      timeout: 5s
      retries: 5

  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

  postgres_data:
```

Notice:

```text
PostgreSQL
→ Persistent volume

Redis
→ No volume yet
```

That's intentional.

# 32. Redis and PostgreSQL Have Different Jobs

Don't think:

```text
PostgreSQL = slow database
Redis = fast database
```

That's too simplistic.

Think:

```text
PostgreSQL
→ relational, durable application data

Redis
→ in-memory operational data structures and fast coordination
```

PostgreSQL gives you:

```text
Relations
Transactions
Constraints
Durability
SQL
Indexes
```

Redis gives you things like:

```text
Key-value access
TTL
Counters
Queues
Pub/Sub
Fast temporary state
```

They complement each other.

# 34. Redis Security

Even in development, start building good habits.

Don't expose Redis publicly in production:

```text
❌ Internet
    ↓
Redis :6379
```

Prefer:

```text
Internet
   ↓
API
   ↓
Private Docker/network
   ↓
Redis
```

Also:

```text
❌ No hard-coded production passwords
❌ No public Redis port
❌ No sensitive data without a reason
```

This connects directly to **Phase 14 — Security Engineering**.

# 35. Common Mistakes

### ❌ Mistake 1 — Using `localhost`

Inside API container:

```text
redis://localhost:6379
```

Wrong.

Use:

```text
redis://redis:6379
```

---

### ❌ Mistake 2 — Treating Redis as the primary database

Don't put your entire LMS database in Redis.

Use:

```text
PostgreSQL
```

for the primary relational data.

---

### ❌ Mistake 3 — Caching everything

Caching creates consistency problems.

Always ask:

```text
Does this data need caching?
How stale can it be?
How will we invalidate it?
```

---

### ❌ Mistake 4 — Assuming Redis data is automatically permanent

Redis is commonly used for temporary/operational data.

Understand the durability requirements of each workload.

---

### ❌ Mistake 5 — Exposing Redis unnecessarily

Avoid:

```yaml
ports:
  - "6379:6379"
```

unless your host actually needs to access Redis.

The API can communicate with:

```text
redis:6379
```

through the Docker network.
