# Lesson 13.7 — GitHub Actions ⚙️

In **13.6**, we separated development, testing, and production configuration.

Now we're going to automate what happens when you push code to GitHub.

The goal is:

```text
Developer
    ↓
git push
    ↓
GitHub
    ↓
GitHub Actions
    ↓
Install
    ↓
Lint
    ↓
TypeScript Check
    ↓
Test
    ↓
Build
    ↓
✅ / ❌
```

This is the foundation of our **CI/CD pipeline**.

---

# 1. What Is GitHub Actions?

GitHub Actions is GitHub's automation system.

It can automatically execute tasks when something happens in your repository.

For example:

```text
git push
Pull Request
New release
Manual trigger
Scheduled event
```

Then GitHub can run:

```text
npm install
npm run lint
npm test
npm run build
docker build
deploy
```

---

# 2. Why Do We Need It?

Imagine you're working on the AI LMS.

You make a change:

```text
StudentController.ts
```

You push it:

```bash
git push
```

Without CI:

```text
You
 ↓
Push
 ↓
Hope everything works 😅
```

With GitHub Actions:

```text
You
 ↓
Push
 ↓
GitHub Actions
 ↓
Lint
 ↓
TypeScript
 ↓
Tests
 ↓
Build
 ↓
Result
```

Now GitHub gives you feedback automatically.

# 3. CI vs CD

You'll hear these terms constantly.

### CI — Continuous Integration

Automatically verify that new code works with the existing codebase.

```text
Code
 ↓

 ↓

 ↓
Validate
```

### CD — Continuous Delivery / Deployment

Automatically prepare or deploy validated code.

```text
Code
 ↓
CI
 ↓
Docker
 ↓
Production
```

# 6. Your First Workflow

Create:

```text
.github/workflows/ci.yml
```

Start with:

```yaml
name: Backend CI

on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
```

Don't worry about understanding every line yet.

We'll break it down.

---

# 7. `name`

```yaml
name: Backend CI
```

This gives the workflow a human-readable name.

GitHub will show something like:

```text
Backend CI
```

in the Actions interface.

You could call it:

```text
AI LMS Backend CI
```

which would be clearer for your project.

---

# 8. `on`

This defines **when the workflow should run**.

Example:

```yaml
on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main
```

This means:

```text
Push to main
      ↓
Run workflow
```

and:

```text
Pull request targeting main
      ↓
Run workflow
```

---

# 9. Why Pull Requests Matter

Imagine you're working on:

```text
feature/course-enrollment
```

You create:

```text
Pull Request
       ↓
main
```

GitHub Actions runs:

```text
Lint
Test
Build
```

If everything passes:

```text
✅
```

If something fails:

```text
❌
```

This helps prevent broken code from entering `main`.

---

# 10. `jobs`

A workflow contains one or more jobs.

Example:

```yaml
jobs:
  test:
```

The job is called:

```text
test
```

Later, we might have:

```yaml
jobs:
  lint:
  test:
  build:
```

or combine some of those depending on what makes sense.

---

# 11. `runs-on`

```yaml
runs-on: ubuntu-latest
```

This tells GitHub which runner environment should execute the job.

Think:

```text
GitHub
   ↓
Temporary Ubuntu machine
   ↓
Run your commands
```

GitHub provides the machine for the workflow run.

When the job finishes, the runner environment is generally discarded.

---

# 12. What Is a Runner?

A runner is the machine that executes your workflow.

Conceptually:

```text
GitHub Actions
      ↓
Runner
      ↓
Linux
      ↓
Node.js
      ↓
Your commands
```

For your backend, `ubuntu-latest` is a sensible starting point.

---

# 13. `steps`

Inside a job:

```yaml
steps:
```

contains the individual actions/commands.

Example:

```yaml
steps:
  - name: Checkout repository
    uses: actions/checkout@v4

  - name: Setup Node.js
    uses: actions/setup-node@v4

  - name: Install dependencies
    run: npm ci
```

So:

```text
Job
 ↓
Step 1
 ↓
Step 2
 ↓
Step 3
```

---

# 14. `uses`

This:

```yaml
uses: actions/checkout@v4
```

uses an existing GitHub Action.

Instead of writing the logic to download your repository yourself, you use GitHub's checkout action.

Conceptually:

```text
uses
 ↓
Reusable action
```

---

# 15. Checkout Repository

This step:

```yaml
- name: Checkout repository
  uses: actions/checkout@v4
```

gets your repository's code onto the runner.

Before checkout:

```text
GitHub Runner
    ↓
No project files
```

After checkout:

```text
GitHub Runner
    ↓
AI LMS source code
```

Without checkout, your later commands wouldn't have your project files.

---

# 16. Setup Node.js

Next:

```yaml
- name: Setup Node.js
  uses: actions/setup-node@v4
  with:
    node-version: 22
```

This tells the runner to use Node.js 22.

Why specify it?

Because you want CI to use a known runtime.

You don't want:

```text
Developer → Node 22
CI → Node 18
Production → Node 20
```

unless that's intentional.

Ideally:

```text
Development
    ↓
CI
    ↓
Production
```

should use compatible versions.

---

# 17. Install Dependencies

```yaml
- name: Install dependencies
  run: npm ci
```

Remember from Lesson 13.2:

```text
npm ci
```

is useful for reproducible dependency installation.

It uses:

```text
package.json
+
package-lock.json
```

Your workflow becomes:

```text
Checkout
   ↓
Node 22
   ↓
npm ci
```

---

# 18. Run Tests

Then:

```yaml
- name: Run tests
  run: npm test
```

GitHub runs:

```bash
npm test
```

If tests pass:

```text
✅
```

If tests fail:

```text
❌
```

And the job fails.

That's the behavior we want.

---

# 19. Exit Codes

GitHub Actions relies heavily on command exit codes.

Generally:

```text
0
↓
Success

non-zero
↓
Failure
```

For example:

```bash
npm test
```

could finish with:

```text
exit code 0
```

meaning success.

If tests fail:

```text
exit code 1
```

and GitHub knows the step failed.

This is an important Linux/backend concept as well.



# 21. Add Linting

Suppose your `package.json` has:

```json
{
  "scripts": {
    "lint": "eslint ."
  }

```

Then:

```yaml
- name: Lint
  run: npm run lint
```

Now CI checks:

```text
Code style
Potential mistakes
TypeScript
Tests
```

This is much stronger than only running tests.

# 22. Add Build

Your backend should eventually have:

```json
{
  "scripts": {
    "build": "tsc"
  }
}
```

Then:

```yaml
- name: Build
  run: npm run build
```

This catches issues that might not be discovered by unit tests.

For example:

```text
Tests pass
      ↓
Production build fails ❌
```

CI catches it before deployment.

# 23. Our First Real CI Workflow

Now our workflow can look like:

```yaml
name: AI LMS Backend CI

on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

jobs:
  quality:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: TypeScript check
        run: npm run typecheck

      - name: Run tests
        run: npm test

      - name: Build
        run: npm run build
```

This is a very good starting point.

---

# 24. Why `cache: npm`?

Here:

```yaml
with:
  node-version: 22
  cache: npm
```

GitHub Actions can cache npm-related data between workflow runs.

Conceptually:

```text
First run
   ↓
Download dependencies
   ↓
Cache

Next run
   ↓
Reuse cache
   ↓
Faster
```

Caching doesn't mean you should skip:

```bash
npm ci
```

The dependency installation should still happen.

The cache simply makes it more efficient.

# 32. GitHub Actions Secrets

From Lesson 13.6, we know:

```text
Secrets
   ↓
Never commit them
```

GitHub Actions has a secrets mechanism.

Conceptually:

```text
GitHub Repository
       │
       ↓
Repository Secrets
       │
       ↓
Workflow
```

Example:

```yaml
env:
  SOME_SECRET: ${{ secrets.SOME_SECRET }}
```

But don't expose secrets in logs.

And don't add secrets unless the workflow actually needs them.

---

# 33. Don't Put Secrets in Workflow YAML

Avoid:

```yaml
env:
  JWT_SECRET: my-super-secret
```

That's just another form of committing a secret to Git.

Use GitHub's secret storage for sensitive values.

# 39. Step Names

Prefer:

```yaml
- name: Install dependencies
```

instead of:

```yaml
- run: npm ci
```

Why?

Because when something fails, GitHub displays:

```text
✓ Checkout repository
✓ Setup Node.js
✓ Install dependencies
✗ TypeScript check
```

That's much easier to understand.

---

# 40. `uses` vs `run`

This distinction is important.

### `uses`

Uses a reusable GitHub Action:

```yaml
uses: actions/checkout@v4
```

### `run`

Executes a shell command:

```yaml
run: npm test
```

Think:

```text
uses → reusable action

run → command
```

---

# 41. GitHub Actions Security

Because GitHub Actions can execute commands on machines and potentially access secrets, workflows must be treated as code.

Be careful with:

```text
Pull requests
Third-party actions
Secrets
Shell commands
Untrusted input
Permissions
```

For example, don't blindly install random GitHub Actions from unknown sources.

We'll revisit CI/CD security in Phase 14.

---

# 42. Pinning Actions

You may see:

```yaml
uses: actions/checkout@v4
```

This is convenient.

For higher supply-chain security, teams may pin actions to immutable commit SHAs.

For learning, version tags such as:

```text
@v4
```

are easier to understand.

Later, during the security phase, we'll discuss why action pinning matters.

# 46. If Your Project Doesn't Have Every Script Yet

You may not have all of these scripts currently:

```text
npm run lint
npm run typecheck
npm test
npm run build
```

That's okay.

For the workflow to pass, the scripts must exist.

Your `package.json` will eventually contain something like:

```json
{
  "scripts": {
    "dev": "tsx watch src/server.ts",
    "build": "tsc",
    "start": "node dist/server.js",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run"
  }
}
```

The exact tools may differ depending on the testing setup we've established in your project.

The important thing is that CI calls the project's **official scripts**, rather than duplicating project logic inside YAML.

---

# 47. Why `package.json` Scripts Matter

Instead of putting:

```yaml
run: npx tsc --noEmit
```

everywhere, prefer:

```yaml
run: npm run typecheck
```

Why?

Because the project's command is defined in one place:

```text
package.json
```

Then:

```text
Local development
       ↓
npm run typecheck

CI
       ↓
npm run typecheck
```

Same command.

Less duplication.
