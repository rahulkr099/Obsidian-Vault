# Lesson 13.8 — Complete CI Pipeline 🚀

In **13.7**, we created a basic GitHub Actions workflow:

```text
git push / Pull Request
        ↓
GitHub Actions
        ↓
npm ci
        ↓
lint
        ↓
typecheck
        ↓
test
        ↓
build
```

Now we're going to make it much closer to a **real backend CI pipeline** for your AI LMS.

Our target is:

```text
                         GitHub
                           │
                    Push / Pull Request
                           ↓
                    GitHub Actions
                           │
                    ┌──────┴──────┐
                    ↓             ↓
                PostgreSQL      Redis
                    │             │
                    └──────┬──────┘
                           ↓
                     Backend Tests
                           ↓
                         Lint
                           ↓
                     TypeScript
                           ↓
                    Integration Tests
                           ↓
                         Build
                           ↓
                     Docker Build
                           ↓
                       ✅ PASS
```

The key idea:

> **CI should prove that the application can be installed, validated, tested, and built in a clean environment.**

---

# 1. Why Basic CI Isn't Enough

Our previous workflow checked:

```text
Lint
TypeScript
Unit tests
Build
```

That's good, but your backend depends on external services:

```text
PostgreSQL
Redis
```

So imagine this:

```text
npm test
   ↓
Tests pass locally
```

but your application actually has:

```text
❌ Broken PostgreSQL connection
❌ Broken Redis connection
```

Your basic CI might never discover it.

That's why we need integration testing with real service containers.

---

# 2. What Should Our CI Validate?

For the AI LMS backend:

```text
                    CI
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
 Dependencies     Code Quality   Services
       │             │             │
     npm ci      ┌────┴────┐    PostgreSQL
                 ↓         ↓    Redis
               Lint    TypeScript
                           │
                           ↓
                         Tests
                           │
                           ↓
                         Build
                           │
                           ↓
                    Docker Build
```

Each layer catches a different class of problem.

---

# 3. The CI Pipeline Stages

We'll use this general order:

```text
1. Checkout
2. Setup Node
3. Install dependencies
4. Start PostgreSQL
5. Start Redis
6. Validate environment
7. Lint
8. TypeScript check
9. Unit tests
10. Integration tests
11. Build
12. Docker build
```

Not every project needs every step on every pull request, but this is a strong target for our LMS.

---

# 4. GitHub Actions Services

GitHub Actions allows a job to run supporting services.

For example:

```yaml
services:
  postgres:
  redis:
```

Conceptually:

```text
GitHub Runner
      │
      ├── Node.js
      │
      ├── PostgreSQL
      │
      └── Redis
```

Your tests can then communicate with those services.

---

# 5. PostgreSQL Service

Example:

```yaml
services:
  postgres:
    image: postgres:17
    env:
      POSTGRES_USER: lms_user
      POSTGRES_PASSWORD: lms_password
      POSTGRES_DB: ai_lms_test
    ports:
      - 5432:5432
    options: >-
      --health-cmd="pg_isready -U lms_user -d ai_lms_test"
      --health-interval=10s
      --health-timeout=5s
      --health-retries=5
```

This gives the CI runner a PostgreSQL instance.

---

# 6. Redis Service

Similarly:

```yaml
redis:
  image: redis:7
  ports:
    - 6379:6379
  options: >-
    --health-cmd="redis-cli ping"
    --health-interval=10s
    --health-timeout=5s
    --health-retries=5
```

Now CI has:

```text
PostgreSQL :5432
Redis :6379
```

available for integration tests.

---

# 7. CI Database

Notice the database:

```text
ai_lms_test
```

not:

```text
ai_lms
```

That's intentional.

Tests should operate on a dedicated test database.

Architecture:

```text
Development
    ↓
ai_lms_dev

CI
    ↓
ai_lms_test

Production
    ↓
ai_lms_prod
```

Never point CI at your real production database.

---

# 8. Environment Variables in CI

Now we can provide:

```yaml
env:
  NODE_ENV: test
  DATABASE_URL: postgresql://lms_user:lms_password@localhost:5432/ai_lms_test
  REDIS_URL: redis://localhost:6379
```

Notice something interesting.

Earlier we said:

```text
API container → postgres:5432
```

But GitHub Actions is different.

The Node.js test process is running directly on the GitHub runner:

```text
GitHub Runner
    ↓
Node.js
```

while PostgreSQL is a service container.

Therefore:

```text
localhost:5432
```

is appropriate for this particular setup.

This is an important networking distinction.

---

# 9. Two Different Networking Situations

### Docker Compose

```text
API Container
      ↓
postgres:5432
```

### GitHub Actions service

```text
GitHub Runner
      ↓
localhost:5432
      ↓
PostgreSQL service container
```

So don't blindly copy:

```text
postgres:5432
```

into every environment.

Always ask:

> **Where is the process making the connection?**

---

# 10. Database Migration Before Tests

Your integration tests may expect tables to exist.

Therefore CI should usually run migrations before tests.

For Prisma:

```bash
npx prisma migrate deploy
```

The flow becomes:

```text
PostgreSQL starts
      ↓
Prisma migrations
      ↓
Database schema ready
      ↓
Tests
```

This is much closer to a real deployment environment.

---

# 11. Why `migrate deploy`?

For CI:

```bash
npx prisma migrate deploy
```

is generally the appropriate migration command when applying existing migrations.

Remember:

```text
Development
→ prisma migrate dev

CI/Deployment
→ prisma migrate deploy
```

The CI environment should not be generating random new migrations.

The migrations should already exist in Git.

---

# 12. Migration Flow

Your Git repository contains:

```text
prisma/
└── migrations/
    ├── 202608...
    ├── 202608...
    └── 202608...
```

CI:

```text
GitHub
   ↓
Checkout
   ↓
Prisma migrations
   ↓
PostgreSQL
```

Then:

```text
Database schema
       ↓
Matches repository migrations
```

---

# 13. Why This Is Powerful

Suppose someone changes:

```prisma
model Course {
  ...
}
```

and forgets to create a migration.

CI can expose the problem depending on how your validation and migration workflow is configured.

This prevents:

```text
Code
  ↓
Production
  ↓
Database schema mismatch ❌
```

from being discovered too late.

---

# 14. Unit Tests vs Integration Tests

This distinction is important.

### Unit test

Tests one component in isolation.

Example:

```text
CourseService
    ↓
Mock repository
    ↓
Expected result
```

### Integration test

Tests real components together.

Example:

```text
API
 ↓
Service
 ↓
Repository
 ↓
Prisma
 ↓
PostgreSQL
```

And potentially:

```text
API
 ↓
Redis
```

Integration tests are particularly valuable for your backend because your application has real infrastructure dependencies.

---

# 15. Example Integration Test

Imagine:

```text
POST /api/v1/courses
```

An integration test could:

```text
Send HTTP request
      ↓
Express route
      ↓
Controller
      ↓
Service
      ↓
Repository
      ↓
Prisma
      ↓
PostgreSQL
```

Then verify:

```text
HTTP 201
Course created
Database record exists
```

That's much more valuable than only testing the controller with mocks.

---

# 16. Redis Integration Test

Similarly:

```text
API
 ↓
Redis Client
 ↓
Redis
```

Test:

```text
SET key
 ↓
GET key
 ↓
Expected value
```

This confirms:

```text
REDIS_URL
Redis client
Docker/service networking
Redis server
```

are all working together.

# 17. CI Environment Variables

A simplified workflow might contain:

```yaml
env:
  NODE_ENV: test
  DATABASE_URL: postgresql://lms_user:lms_password@localhost:5432/ai_lms_test
  REDIS_URL: redis://localhost:6379
```

These are test credentials, not production credentials.

This is acceptable for a temporary CI database.

---

# 18. Don't Use Production Secrets for Tests

Avoid:

```text
CI
 ↓
Production DATABASE_URL ❌
```

Instead:

```text
CI
 ↓
Temporary PostgreSQL
 ↓
Temporary test data
```

This gives us isolation.

# 19. Full CI Example

A useful starting point for your backend could be:

```yaml
name: AI LMS Backend CI

on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

jobs:
  quality:
    runs-on: ubuntu-latest

    env:
      NODE_ENV: test
      DATABASE_URL: postgresql://lms_user:lms_password@localhost:5432/ai_lms_test
      REDIS_URL: redis://localhost:6379
      JWT_SECRET: test-secret-that-is-at-least-32-characters-long

    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: lms_user
          POSTGRES_PASSWORD: lms_password
          POSTGRES_DB: ai_lms_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd="pg_isready -U lms_user -d ai_lms_test"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

      redis:
        image: redis:7
        ports:
          - 6379:6379
        options: >-
          --health-cmd="redis-cli ping"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run database migrations
        run: npx prisma migrate deploy

      - name: Lint
        run: npm run lint

      - name: TypeScript check
        run: npm run typecheck

      - name: Run tests
        run: npm test

      - name: Build
        run: npm run build
```

This is a **development/learning CI configuration**, not yet our final production pipeline.

---

# 20. Why Services Are Defined at Job Level

Notice:

```yaml
jobs:
  quality:
    services:
      postgres:
      redis:
```

The services belong to the job.

So the job gets:

```text
quality job
   │
   ├── Node.js
   ├── PostgreSQL
   └── Redis
```

When the job finishes, these temporary service containers go away.

That's exactly what we want for CI.

---

# 21. CI Should Be Reproducible

A strong CI pipeline should start from a clean environment.

Think:

```text
Fresh runner
    ↓
Checkout repository
    ↓
Install dependencies
    ↓
Start services
    ↓
Migrate database
    ↓
Run checks
```

Don't rely on:

```text
"Something I installed on my laptop last week."
```

CI should prove the repository itself contains what is required to build and test the application.

---

# 22. `npm ci` Instead of `npm install`

In CI, prefer:

```bash
npm ci
```

rather than:

```bash
npm install
```

because CI should reproduce the dependency tree defined by:

```text
package-lock.json
```

This helps prevent:

```text
Developer dependencies
      ≠
CI dependencies
```

---

# 23. Lockfile

Your repository should contain:

```text
package.json
package-lock.json
```

Commit both.

```bash
git add package.json package-lock.json
```

Then:

```text
npm ci
```

can install the locked dependency versions.

---

# 24. What If `package-lock.json` Is Missing?

Then:

```bash
npm ci
```

will fail.

That's actually useful.

It tells you:

> Your dependency state isn't reproducibly defined.

Generate the lockfile locally:

```bash
npm install
```

then commit:

```text
package-lock.json
```

---

# 25. Test Database Cleanup

Tests should ideally not depend on leftover data.

For example:

```text
Test 1
 ↓
Create user

Test 2
 ↓
Expected database to be empty
```

If Test 1 leaves data behind:

```text
Test 2
 ↓
Unexpected existing user
```

Tests become flaky.

So integration testing needs a database cleanup/reset strategy.

Depending on your setup, that might involve:

```text
Transactions
Database reset
Test fixtures
Truncation
Dedicated test database
```

We'll build this into the testing layer rather than hiding it inside CI YAML.

---

# 26. Don't Put Test Logic Inside GitHub Actions

Avoid writing huge shell scripts like:

```yaml
run: |
  create user
  insert course
  delete course
  check redis
  ...
```

Instead:

```text
GitHub Actions
      ↓
npm test
      ↓
Test suite
```

Your application tests should live in the repository.

For example:

```text
tests/
├── unit/
├── integration/
└── fixtures/
```

CI's job is to **execute** them.

---

# 27. Separate Test Types

Your project could eventually use:

```text
tests/
├── unit/
│   ├── auth.service.test.ts
│   └── course.service.test.ts
│
├── integration/
│   ├── auth.api.test.ts
│   ├── course.api.test.ts
│   └── redis.test.ts
│
└── fixtures/
```

Then:

```text
Unit
 ↓
Fast feedback

Integration
 ↓
Infrastructure verification
```

---

# 28. Build Validation

After:

```bash
npm test
```

we should run:

```bash
npm run build
```

Why?

Tests and compilation answer different questions.

```text
Tests:
"Does the behavior work?"

Build:
"Can the application actually compile into the production artifact?"
```

You need both.

---

# 29. Docker Build Validation

Since we're deploying with Docker, CI should eventually verify:

```bash
docker build .
```

or:

```bash
docker build -t ai-lms-api:test .
```

This catches Docker-specific problems.

For example:

```text
Local Node environment
      ↓
Works

Docker build
      ↓
COPY mistake
      ↓
❌
```

Without Docker build validation, you might discover this only during deployment.

---

# 30. Add Docker Build

We can add:

```yaml
- name: Build Docker image
  run: docker build -t ai-lms-api:test .
```

Now:

```text
Code
 ↓
npm build
 ↓
Docker build
```

Both need to pass.

---

# 31. Why Build Twice?

You might ask:

> If `npm run build` passes, why run Docker build?

Because they're testing different layers.

### `npm run build`

Tests:

```text
TypeScript
Application compilation
Build configuration
```

### `docker build`

Tests:

```text
Dockerfile
Build context
COPY paths
Dependencies inside image
Production image construction
```

So:

```text
Application build
+
Container build
```

is valuable.

---

# 32. Docker Image Naming

For CI:

```bash
docker build -t ai-lms-api:test .
```

The image name is:

```text
ai-lms-api
```

and tag:

```text
test
```

Later we'll use tags like:

```text
ai-lms-api:1.0.0
ai-lms-api:abc1234
```

where the commit SHA can identify exactly which source produced the image.

That becomes important in deployment.

---

# 33. Image Reproducibility

Imagine:

```text
Commit A
 ↓
Docker Image A

Commit B
 ↓
Docker Image B
```

We want to know:

```text
Which code created this production image?
```

A useful strategy is tagging images using:

```text
Git commit SHA
```

For example:

```text
ai-lms-api:a84f21c
```

Then:

```text
a84f21c
```

identifies the exact Git commit.

We'll use this idea in later deployment lessons.

---

# 34. CI Pipeline Failure Strategy

A good pipeline should stop when a critical check fails.

For example:

```text
Lint
 ↓
❌
```

Don't continue as if everything is fine.

Similarly:

```text
Migration
 ↓
❌
```

should stop the test job.

This gives a simple principle:

> **A failed prerequisite should fail the pipeline.**

---

# 35. Parallel Jobs

As the project grows, we might split jobs:

```text
                 CI
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
       Lint      Test      Build
```

This can make CI faster.

But there's a tradeoff.

Separate jobs may require:

```text
Repeated dependency installation
Repeated setup
Artifact transfer
```

For your current project, one well-structured job is easier to understand.

We'll optimize later if CI becomes slow.

---

# 36. Job Dependencies

If we eventually split jobs:

```yaml
jobs:
  lint:
    ...

  test:
    ...

  build:
    needs:
      - lint
      - test
```

Then:

```text
Lint ──┐
       ├──→ Build
Test ──┘
```

`needs` controls job dependencies.

For now, sequential steps inside one job are simpler.

# 39. CI and Secrets

Our current test setup uses:

```text
JWT_SECRET=test-secret...
```

That's not a real production secret.

For CI-only fake values, this is generally acceptable because:

```text
It's not sensitive
It's not used outside CI
```

But if a test needs a real external API key:

```text
AI_API_KEY
```

don't hard-code it.

Use:

```yaml
${{ secrets.AI_API_KEY }}
```

only if the test truly needs the real service.

Even better:

> Mock external AI providers during normal CI whenever possible.

This makes CI faster, cheaper, and more reliable.

---

# 40. Don't Call Real AI APIs in Every CI Run

Imagine every pull request does:

```text
Pull Request
 ↓
100 AI requests
 ↓
External provider
```

Problems:

```text
Cost
Rate limits
Slow tests
Network failures
Non-deterministic responses
```

Instead:

```text
CI
 ↓
Mock AI provider
 ↓
Predictable response
```

Then have a smaller set of dedicated integration/e2e tests for real provider integration if needed.

This is a particularly important design decision for your AI LMS.

---

# 41. External Services vs Local Services

Good CI design:

```text
PostgreSQL
→ local CI service

Redis
→ local CI service

AI Provider
→ mock/fake

Email Provider
→ mock/fake

Payment Provider
→ mock/sandbox
```

This reduces external dependencies.

# 42. CI Security Permissions

GitHub Actions workflows can have permissions.

A safer pattern is to give workflows only the permissions they need.

For example:

```yaml
permissions:
  contents: read
```

This says the workflow only needs read access to repository contents.

For a basic CI pipeline, that's often enough.

We'll discuss permissions and workflow security more deeply in Phase 14.

# 45. What CI Has Proven

If this pipeline passes, we have evidence that:

```text
✓ Dependencies can be installed

✓ Database migrations can run
```

# 46. What CI Has NOT Proven

A passing CI pipeline does **not** automatically mean:

```text
❌ Production is configured correctly
❌ Production database is healthy
❌ Deployment works
❌ AI provider is available
❌ Frontend works perfectly
❌ Security is perfect
❌ Application can handle 10,000 users
```

CI is one layer of engineering.

Think:

```text
CI
 ↓
Quality gate
```

not:

```text
CI
 ↓
Everything is guaranteed
```
