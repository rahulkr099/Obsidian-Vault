# Lesson 13.9 — Automated Testing in CI 🧪

In **13.8**, we built a CI pipeline that can:

```text

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓
```

Now we're going to focus deeply on the **testing part**.

For your AI LMS, we want CI to automatically verify:

```text

Redis Tests

Coverage
```

The goal is:

> Every important backend change should be automatically tested before it reaches `main`.

---

# 1. Why Automated Testing Matters

Imagine you modify:

```text
CourseService
```

You think:

```text
"Everything should still work."
```

But your change accidentally breaks:

```text
Course enrollment
Progress tracking
Authorization
Database queries
Redis caching
```

Without automated tests:

```text
Code change
   ↓
Push
   ↓
Production
   ↓
Users discover bug ❌
```

With CI:

```text
Code change
   ↓
Push
   ↓
Tests
   ↓
❌ Failure
   ↓
Fix before merge
```

That's the purpose of automated testing.

---

# 2. Testing Pyramid

A useful testing model is:

```text
              /\
             /  \
            / E2E\
           /------\
          /  API   \
         /----------\
        / Integration\
       /--------------\
      /   Unit Tests   \
     /------------------\
```

The bottom should contain many fast tests.

The top contains fewer, slower tests.

For your backend:

```text
Many
 ↓
Unit tests

Moderate
 ↓
Integration/API tests

Few
 ↓
End-to-end tests
```

---

# 3. Unit Tests

A unit test tests a small piece of code in isolation.

For example:

```text
CourseService
```

could be tested without PostgreSQL.

Architecture:

```text
CourseService
      ↓
Mock Repository
      ↓
Expected result
```

Example:

```ts
it("returns the course", async () => {
  repository.findById.mockResolvedValue(course);

  const result = await service.getCourse("123");

  expect(result).toEqual(course);
});
```

The database isn't required.

---

# 4. Why Unit Tests Are Fast

Suppose you have:

```text
500 unit tests
```

If each takes:

```text
5 ms
```

the entire suite can be very fast.

That's why unit tests are ideal for:

```text
Business logic
Validation
Utility functions
Permission logic
Transformations
Calculations
```

# 9. Which Test Framework?

For a modern TypeScript backend, common choices include:

```text
Vitest

```

Since our roadmap has already been using the idea of Jest/Vitest testing, choose **one** and keep it consistent.

# 12. First Unit Test

Suppose we have:

```ts
export function calculateProgress(
  completed: number,
  total: number
) {
  return Math.round((completed / total) * 100);
}
```

Test:

```ts
import { describe, expect, it } from "vitest";
import { calculateProgress } from "../../src/utils/progress";

describe("calculateProgress", () => {
  it("calculates percentage", () => {
    expect(calculateProgress(5, 10)).toBe(50);
  });
});
```

Run:

```bash
npm test
```

Expected:

```text
✓ calculates percentage
```

---

# 13. Testing Edge Cases

Don't only test the happy path.

For:

```ts
calculateProgress(5, 10)
```

also think about:

```text
0 / 10
10 / 10
1 / 3
0 / 0
11 / 10
```

Testing is not:

```text
"Does the normal case work?"
```

It's:

> "Does the system behave correctly across realistic and invalid conditions?"

# 14. Service Unit Test

Suppose:

```ts
class CourseService {
  constructor(
    private readonly repository: CourseRepository
  ) {}

  async getCourse(id: string) {
    const course = await this.repository.findById(id);

    if (!course) {
      throw new AppError("Course not found", 404);
    }

    return course;
  }
}
```

We can mock the repository.

```ts
const repository = {
  findById: vi.fn(),
};
```

Then:

```ts
repository.findById.mockResolvedValue(course);
```

Now the service can be tested without PostgreSQL.

---

# 15. Why Mock the Repository?

Your architecture is:

```text
Service
   ↓
Repository
```

When testing the service, we want to ask:

> Does the service make the correct decisions?

We don't want the test to fail because PostgreSQL is unavailable.

So:

```text
Service Test
    ↓
Mock Repository
```

while:

```text
Repository Test
    ↓
Real PostgreSQL
```

This creates clear test responsibilities.

# 20. Test Fixtures

Integration tests need predictable data.

For example:

```ts
const user = {
  email: "student@test.local",
  name: "Test Student",
};
```

A fixture is reusable test data.

Example:

```text
tests/
└── fixtures/
    ├── user.ts
    ├── course.ts
    └── enrollment.ts
```

This prevents every test from manually recreating the same data.

---

# 21. Test Data Should Be Obvious

Use clearly fake data:

```text
student@test.local
instructor@test.local
course@test.local
```

Don't use:

```text
realuser@gmail.com
real production account
```

Testing should never accidentally interact with real users.

# 22. Database Cleanup

Imagine:

```text
Test A
 ↓
Creates user
```

Then:

```text
Test B
 ↓
Finds unexpected user
```

Now Test B depends on Test A.

That's bad.

Tests should be independent.

```text
Test A ──┐
         ├── Independent
Test B ──┤
         │
Test C ──┘
```

---

# 23. Test Isolation

The ideal property is:

```text
Run Test A
```

or:

```text
Run Test B
```

or:

```text
Run B then A
```

and the result should still be predictable.

A test should not depend on another test's database state.

---

# 24. Cleanup Strategy

Several approaches exist.

### Approach 1 — Delete test data

After each test:

```text
DELETE users
DELETE courses
```

Simple, but potentially slow.

### Approach 2 — Database transactions

```text
BEGIN
 ↓
Test
 ↓
ROLLBACK
```

Very useful for certain database tests.

### Approach 3 — Reset database between suites

For example:

```text
Test suite starts
 ↓
Reset database
 ↓
Run tests
```

The right strategy depends on the architecture and testing framework.

---

# 25. Don't Blindly Reset the Database

Be careful with commands that reset databases.

Never configure:

```text
Database reset
```

against a production database.

Use a hard separation:

```text
ai_lms_test
```

and environment validation.

You can even enforce:

```ts
if (env.NODE_ENV !== "test") {
  throw new Error("Database reset is only allowed in test environment");
}
```

This is a very good safety habit.

You could test:

```ts
  EX: 60,
```

# 33. Testing Cache Behavior

Suppose:

```text

```

uses Redis.

A useful test can verify:

### First request

```text
Redis MISS
 ↓

 ↓

```

### Second request


---

# 34. But Don't Over-Test Implementation Details

Bad test:

```text
expect(redis.get).toHaveBeenCalledExactlyOnce()
```

when the real requirement is:

```text
Course data is returned correctly.
```

Tests should focus on **behavior**, not every internal implementation detail.

Prefer:

```text
Given course exists
When client requests course
Then correct course is returned
```

rather than:

```text
Redis.get must be called exactly once
```

unless that behavior itself is important.

---

# 35. Test the Contract

Think in terms of:

```text
Given
When
Then
```

Example:

```text
Given
a valid authenticated instructor

When
they create a course

Then
the API returns 201
and the course exists in PostgreSQL
```

This style makes tests easy to understand.

---

# 36. Test Naming

Bad:

```ts
it("works", ...)
```

Better:

```ts
it("creates a course for an authenticated instructor", ...)
```

Even better:

```ts
it("returns 403 when a student attempts to create a course", ...)
```

A test failure should tell you what broke.

# 40. Coverage

Coverage tells you how much of your code is executed by tests.

Common measurements:

```text
Statements
Branches
Functions
Lines
```

For example:

```text
Statements: 87%
Branches:   78%
Functions:  91%
Lines:      86%
```

But:

> **High coverage does not automatically mean high-quality tests.**

You can have 100% coverage and still have bad tests.

---

# 41. What Coverage Is Good For

Coverage can reveal:

```text
Untested code
Uncovered branches
Unused paths
Missing edge cases
```

For example:

```ts
if (user.role === "ADMIN") {
  ...
}
```

If your tests never exercise the admin branch:

```text
Branch coverage
 ↓
Missing
```

That's useful information.

---

# 42. Don't Chase 100% Blindly

You don't need:

```text
100%
```

for every file.

Focus on important business logic:

```text
Authentication
Authorization
Payments
Enrollment
Progress
Course access
AI orchestration
Security-sensitive logic
```

A thoughtful:

```text
85%
```

can be better than a meaningless:

```text
100%
```

---

# 43. Coverage Thresholds

Vitest can be configured with coverage thresholds.

Conceptually:

```text
Statements ≥ 80%
Branches ≥ 75%
Functions ≥ 80%
Lines ≥ 80%
```

If coverage falls below the threshold:

```text
CI
 ↓
Coverage
 ↓
Below threshold
 ↓
❌
```

This prevents the test suite from slowly becoming worse.

But don't add strict thresholds before your test suite is mature.

# 50. Flaky Tests

A flaky test:

```text
Sometimes passes
Sometimes fails
```

without a code change.

Example causes:

```text
Timing
Race conditions
Shared state
Random data
External APIs
Network dependency
Improper cleanup
```

Flaky tests are dangerous because developers eventually start ignoring failures.

```text
❌ CI failed again
"Probably flaky."
```

Never allow that to become normal.

---

# 51. Deterministic Tests

Good tests should be:

```text
Repeatable
Predictable
Isolated
Fast enough
```

If you run:

```bash
npm test
```

five times:

```text
PASS
PASS
PASS
PASS
PASS
```

That's what we want.

---

# 52. Time and Date Testing

Your LMS will have:

```text
Course expiration
Enrollment dates
Progress timestamps
Token expiration
Scheduled jobs
```

Tests involving:

```ts
new Date()
```

can become fragile.

Prefer controllable clocks or fixed timestamps in tests.

For example:

```text
2026-08-14T10:00:00Z
```

rather than relying on the current system time.

This makes tests deterministic.

---

# 53. Random IDs

Your application may use:

```text
UUID
nanoid
random tokens
```

Tests should not depend on unpredictable values unnecessarily.

Instead:

```text
assert format
assert existence
assert relationship
```

rather than:

```text
expect(id).toBe("some-random-value")
```

unless randomness itself is what you're testing.

---

# 54. Testing Passwords

Never test with real passwords.

Use fake values:

```text
TestPassword123!
```

And don't log:

```text
password
JWT
refresh token
API key
```

during tests.

Test output can end up in:

```text
CI logs
```

which is another reason to keep secrets out of tests.

```text
   ↓
Node setup
   ↓
npm ci
   ↓
Start services
   ↓
Migrations
   ↓
Lint
   ↓
TypeScript
   ↓
Unit tests
   ↓

   ↓
```

Why this order?

Because:


generally makes CI faster.

For example, there's little point spending several minutes running integration tests if:

```text
TypeScript compilation
```

already fails.

# 🧠 Lesson 13.9 Summary

The testing architecture you should remember is:

```text
                     AI LMS Tests
                          │
             ┌────────────┼────────────┐
             ↓            ↓            ↓
           Unit       Integration      E2E
             │            │             │
             ↓            ↓             ↓
          Services      API          Full user
          Utilities      DB           journeys
          Business      Redis
          Rules
```

And the CI pipeline:

```text
                  Pull Request
                       ↓
                GitHub Actions
                       ↓
                   npm ci
                       ↓
              PostgreSQL + Redis
                       ↓
                Prisma Migration
                       ↓
                     Lint
                       ↓
                  TypeScript
                       ↓
                  Unit Tests
                       ↓
              Integration Tests
                       ↓
                    Coverage
                       ↓
                     Build
                       ↓
                 Docker Build
                       ↓
                    ✅ PASS
```

### The five rules to remember

**1. Unit tests** → test business logic in isolation.

**2. Integration tests** → test real PostgreSQL, Redis, Prisma, API layers.

**3. Test isolation** → one test must not depend on another test's state.

**4. CI should use temporary test infrastructure** → never production databases or production secrets.

**5. Test behavior, not implementation details** → verify what the application promises to do.
