# 🔐 Lesson 14.1 — Security Fundamentals & Threat Modeling

Welcome to **Phase 14**. This is where we stop thinking only like developers and start thinking like **security engineers**.

Your goal for this lesson is not to memorize security terms.

Your goal is to develop this habit:

> **Whenever I build a feature, I should automatically ask: What can go wrong? Who can abuse it? What data could be exposed?**

We'll apply everything to your **AI LMS**.

---

# 1. What Is Application Security?

Application security means protecting your application from:

- unauthorized access
    
- data theft
    
- data modification
    
- service abuse
    
- malicious input
    
- account takeover
    
- information leakage
    
- infrastructure attacks
    

Think about your LMS:

```text
                    AI LMS
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
      Users          Courses          AI
        │              │              │
   Credentials      Content         Prompts
        │              │              │
        └──────────────┼──────────────┘
                       ↓
                    Database
```

There are valuable things inside this system.

An attacker doesn't necessarily care about your code.

They care about the **assets** your system protects.

---

# 2. What Is an Asset?

An **asset** is something valuable that needs protection.

For your AI LMS:

|Asset|Example|
|---|---|
|User account|Email, password hash|
|Authentication tokens|Access/refresh tokens|
|Personal data|Name, profile information|
|Course content|Lessons, PDFs, videos|
|Student progress|Completion and scores|
|Quiz data|Questions and answers|
|Instructor data|Course ownership|
|Admin functionality|User management|
|AI conversations|Student ↔ AI messages|
|RAG documents|Course materials|
|AI API keys|Provider credentials|
|Database|All application data|

The important question is:

> **What happens if this asset is stolen, modified, deleted, or made unavailable?**

---

# 3. The CIA Triad

One of the most important security fundamentals is the **CIA Triad**.

It means:

```text
             Security
                │
       ┌────────┼────────┐
       ↓        ↓        ↓
 Confidentiality Integrity Availability
```

## 3.1 Confidentiality

Only authorized people should see the data.

Example:

```text
Student A
   ↓
Student A's progress
```

Student B should not be able to access it.

Bad:

```http
GET /api/v1/users/student-A/progress
```

where Student B can simply change the ID.

---

## 3.2 Integrity

Data should not be changed by unauthorized people.

Example:

```text
Instructor
   ↓
Course
   ↓
Price = ₹999
```

A random student should not be able to change:

```text
price = ₹1
```

Integrity means:

> **The data remains correct and trustworthy.**

---

## 3.3 Availability

The application should remain usable.

Imagine an attacker sends:

```text
1,000,000 requests
       ↓
/api/v1/ai/chat
```

Your server could become overloaded.

Or someone repeatedly calls an expensive AI endpoint:

```text
POST /api/v1/ai/generate
```

and generates a huge AI bill.

That's an **availability and resource-abuse problem**.

# 5. What Is a Threat?

A **threat** is something that could potentially cause harm to your system or its assets.

Example:

```text
Asset:
Student progress

Threat:
Unauthorized user accesses another student's progress.
```

Another:

```text
Asset:
AI API key

Threat:
Key leaks through GitHub.
```

Another:

```text
Asset:
RAG database

Threat:
Malicious document injects instructions into the AI context.
```

---

# 6. What Is a Vulnerability?

A **vulnerability** is a weakness that can be exploited.

Example:

Your API contains:

```js
app.get("/users/:id", getUser);
```

And the controller does:

```js
const user = await User.findById(req.params.id);
```

without checking whether the logged-in user owns that resource.

The vulnerability is:

```text
Missing authorization check
```

An attacker might exploit it by changing:

```text
/users/123
```

to:

```text
/users/124
```

---

# 7. Threat vs Vulnerability vs Attack

These three concepts are easy to confuse.

### Threat

Something that could cause harm.

```text
Attacker wants to steal user data.
```

### Vulnerability

A weakness that allows it.

```text
Missing authorization check.
```

### Attack

The actual attempt.

```text
Attacker changes user ID in the URL.
```

Think:

```text
Threat
  ↓
Vulnerability
  ↓
Attack
  ↓
Impact
```

---

# 8. What Is Risk?

Risk is basically:

> **How likely is something to happen, and how bad would the result be?**

A simple model:

```text
Risk ≈ Likelihood × Impact
```

Example:

### Threat A

```text
Attacker reads another student's progress.
```

Likelihood:

```text
High
```

Impact:

```text
Medium
```

Risk:

```text
High
```

### Threat B

```text
Attacker temporarily breaks a development-only endpoint.
```

Likelihood:

```text
Medium
```

Impact:

```text
Low
```

Risk:

```text
Low
```

This helps us prioritize.

You can't fix everything simultaneously.

# 9. What Is an Attack Surface?

The **attack surface** is the collection of places where an attacker can interact with your system.

Your LMS might look like:

```text
                    Internet
                       │
       ┌───────────────┼────────────────┐
       ↓               ↓                ↓
    Frontend          API             Files
       │               │                │
       │        ┌──────┼──────┐         │
       │        ↓      ↓      ↓         │
       │       Auth   LMS     AI         │
       │               │      │          │
       │               │      ↓          │
       │               │    RAG          │
       │               │      │          │
       └───────────────┼──────┼──────────┘
                       ↓      ↓
                    Database Redis
```

Every exposed component can potentially become part of the attack surface.

# 11. Threat Modeling

Now we reach the main topic of this lesson.

**Threat modeling** means systematically identifying:

```text
What are we protecting?
Who could attack it?
How could they attack it?
What could happen?
How do we reduce the risk?
```

A simple process:

```text
1. Identify assets
       ↓
2. Identify actors
       ↓
3. Map the system
       ↓
4. Find attack surfaces
       ↓
5. Identify threats
       ↓
6. Analyze risk
       ↓
7. Add security controls
       ↓
8. Re-evaluate
```

# 13. Step 2 — Identify Trust Boundaries

A **trust boundary** is where data moves from one security context to another.

Example:

```text
Browser
   │
   │ HTTP
   ↓
Backend
```

There is a trust boundary here.

Why?

Because the browser is controlled by the user.

Therefore:

> **Never trust anything simply because it came from your frontend.**

For example:

```js
{
  role: "admin"
}
```

coming from the browser means nothing.

The server must determine the user's actual role from trusted server-side data.

---

## Example: Unauthorized RAG Access

Imagine:

```text
Course A → Instructor A
Course B → Instructor B
```

Student A is enrolled only in Course A.

But your RAG query accidentally searches:

```text
ALL course documents
```

instead of:

```text
Course A documents
```

Then the AI could retrieve Course B content.

That's a security vulnerability.

The problem isn't necessarily the LLM.

The problem is:

```text
Missing authorization at retrieval layer
```

This is a very important lesson.

# 17. Security Must Exist at Every Layer

For sensitive data, don't rely on one check.

Think:

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Resource ownership
   ↓
Database filtering
   ↓
RAG filtering
   ↓
Output validation
```

For example:

```text
Student asks AI about Course A
```

We should verify:

```text
Is user authenticated?
        ↓
Is user enrolled in Course A?
        ↓
Can user access this lesson?
        ↓
Can retrieval access these documents?
        ↓
Should this content be included?
        ↓
Can the AI response expose something sensitive?
```

That's **defense in depth**.

---

# 18. Defense in Depth

Never depend on one security control.

Bad architecture:

```text
Frontend authorization
        ↓
Everything trusted
```

Better:

```text
Frontend
   ↓
API authentication
   ↓
API authorization
   ↓
Resource ownership
   ↓
Database constraints
   ↓
Output filtering
```

If one layer fails, another layer can still protect the system.

# 19. STRIDE

We'll use **STRIDE** as one threat-modeling framework.

```text
S → Spoofing
T → Tampering
R → Repudiation
I → Information Disclosure
D → Denial of Service
E → Elevation of Privilege
```

Let's apply it.

---

## S — Spoofing

Pretending to be someone else.

Example:

```text
Attacker
   ↓
Stolen authentication token
   ↓
Pretends to be Student A
```

---

## T — Tampering

Unauthorized modification.

Example:

```text
Student
   ↓
Changes course price
```

---

## R — Repudiation

A user denies performing an action and the system lacks enough evidence to determine what happened.

Example:

```text
Instructor deletes course
```

But your system has no useful audit record.

You may want:

```text
userId
action
resource
timestamp
requestId
```

This connects directly with the logging work you've already done.

---

## I — Information Disclosure

Unauthorized data exposure.

Example:

```text
Student A
   ↓
Student B's private data
```

---

## D — Denial of Service

Making the application unavailable.

Example:

```text
Millions of requests
        ↓
API
        ↓
Server overloaded
```

For an AI LMS, another example is:

```text
Expensive AI endpoint
        ↓
Repeated requests
        ↓
Huge API bill
```

---

## E — Elevation of Privilege

A user gains permissions they shouldn't have.

Example:

```text
Student
   ↓
becomes
   ↓
Admin
```

This is extremely dangerous.

---

# 20. STRIDE Applied to Your LMS

|Threat|LMS Example|Security Control|
|---|---|---|
|Spoofing|Stolen token|Token security|
|Tampering|Modify another course|Authorization|
|Repudiation|Delete course without audit|Audit logs|
|Information Disclosure|Access another student's data|Access control|
|Denial of Service|API flooding|Rate limiting|
|Elevation of Privilege|Student → Admin|RBAC + server checks|

This table is worth remembering.

# 22. Security Questions You Should Develop

From now on, whenever you create an endpoint, ask:

### Authentication

> Who are you?

```text
req.user
```

### Authorization

> Are you allowed to do this?

```text
role / permission
```

### Ownership

> Does this resource belong to you?

```text
course.instructorId === req.user.id
```

### Input

> Can this input be malicious?

```text
Zod
sanitization
limits
```

### Data

> Could this response expose sensitive information?

```text
DTO / response filtering
```

### Abuse

> Can someone call this endpoint too many times?

```text
rate limiting
quotas
```

### Logging

> Can we understand what happened later?

```text
requestId
audit logs
security events
```

### External services

> Are we sending sensitive information somewhere else?

```text
AI provider
email provider
storage
```

This mindset is more valuable than memorizing hundreds of vulnerabilities.

# 24. Security Design Principle #1

## Never Trust the Client

This is one of the most important backend principles.

Suppose the frontend sends:

```json
{
  "role": "admin"
}
```

Do **not** do:

```js
if (req.body.role === "admin") {
  // allow
}
```

Instead:

```text
Request
   ↓
Authentication
   ↓
Identify user
   ↓
Fetch trusted permissions
   ↓
Authorize action
```

The browser belongs to the user.

Therefore:

> **The frontend is a convenience layer, not a security boundary.**

---

# 25. Security Design Principle #2

## Least Privilege

Give users and services only the permissions they need.

Example:

```text
Student
 ├── Read enrolled courses
 ├── Update own progress
 └── Take quizzes

Instructor
 ├── Create courses
 ├── Update own courses
 └── View student progress

Admin
 ├── Manage users
 ├── Manage courses
 └── Security operations
```

Don't give everyone:

```text
admin: true
```

just because it's easier.

---

# 26. Security Design Principle #3

## Fail Securely

Suppose authorization fails.

Bad:

```js
if (permissionCheckFails) {
  next();
}
```

Better:

```text
Authorization fails
        ↓
Request denied
        ↓
403 Forbidden
```

Security-sensitive failures should normally **deny access**, not accidentally grant it.

---

# 27. Security Design Principle #4

## Minimize Data Exposure

Suppose your database contains:

```text
User
├── id
├── name
├── email
├── passwordHash
├── refreshToken
└── resetToken
```

Never return everything:

```js
res.json(user);
```

Instead return only what the client needs:

```json
{
  "id": "123",
  "name": "Rahul",
  "email": "example@email.com"
}
```

Sensitive fields should stay server-side.

---

# 28. Security Design Principle #5

## Assume External Input Is Malicious

These are all untrusted:

```text
req.body
req.params
req.query
headers
cookies
uploaded files
URLs
usernames
search queries
AI prompts
course documents
RAG content
```

Therefore:

```text
Input
 ↓
Validate
 ↓
Normalize
 ↓
Authorize
 ↓
Process
```

# 29. Mini Exercise 🧠

Before moving to Lesson 14.2, try to identify the security problem in each example.

### Example 1

```js
app.get("/users/:id", async (req, res) => {
  const user = await getUser(req.params.id);
  res.json(user);
});
```

**Question:** What's missing?

Authorization/resource ownership validation.

A logged-in user may be able to request another user's information simply by changing `:id`.

---

### Example 2

```js
app.post("/ai/chat", async (req, res) => {
  const response = await callLLM(req.body.message);
  res.json(response);
});
```

What security problems should you think about?

```text
Authentication?
Authorization?
Rate limiting?
Input limits?
Prompt injection?
AI cost abuse?
Sensitive information?
```

Exactly.

---

### Example 3

```js
app.patch("/users/:id", updateUser);
```

What should you ask?

```text
Who is making the request?
        ↓
Are they authenticated?
        ↓
Are they allowed to update users?
        ↓
Can they update THIS user?
        ↓
Which fields can they modify?
```

That's threat modeling.
