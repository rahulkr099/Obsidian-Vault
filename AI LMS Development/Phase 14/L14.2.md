# 🛡️ Lesson 14.2 — OWASP Top 10

Now that you understand **threats, vulnerabilities, attack surfaces, risk, and threat modeling**, we can move to one of the most important security references for web developers: **OWASP Top 10**.

The goal is **not** to memorize a list.

The goal is to look at your AI LMS and recognize:

> **“This feature could have this type of security problem.”**

---

# 1. What Is OWASP?

**OWASP** stands for:

> **Open Worldwide Application Security Project**

OWASP provides security guidance, tools, documentation, and community resources for application developers and security engineers.

The **OWASP Top 10** is a well-known awareness list of major categories of web application security risks.

For your journey, think of it as a:

```text
Security Checklist
       ↓
What can go wrong?
       ↓
Where can it happen?
       ↓
How do I prevent it?
```

---

# 2. The OWASP Top 10

The current OWASP Top 10 web application risk categories are:

```text
A01  Broken Access Control
A02  Cryptographic Failures
A03  Injection
A04  Insecure Design
A05  Security Misconfiguration
A06  Vulnerable and Outdated Components
A07  Identification and Authentication Failures
A08  Software and Data Integrity Failures
A09  Security Logging and Monitoring Failures
A10  Server-Side Request Forgery (SSRF)
```

We'll connect every one to your **AI LMS**.

---

# 3. A01 — Broken Access Control

🔥 **This is especially important for your LMS.**

Access control answers:

> **Is this user allowed to perform this action on this resource?**

Suppose:

```text
Student A
   ↓
Course A
```

Student A should not be able to modify Course B.

But imagine your endpoint:

```http
PATCH /api/v1/courses/:courseId
```

and your backend does:

```js
const course = await courseRepository.findById(req.params.courseId);

await courseRepository.update(course.id, req.body);
```

without checking ownership.

An attacker could simply change:

```text
courseId = course-B
```

---

## The vulnerability

```text
Authentication
      ↓
       ✅
User is logged in

Authorization
      ↓
       ❌
User isn't authorized for this course
```

Being logged in doesn't mean you're allowed to do everything.

---

# 4. Authentication vs Authorization

Remember this distinction.

### Authentication

> **Who are you?**

```text
Login
 ↓
User identified
```

### Authorization

> **What are you allowed to do?**

```text
Student
 ↓
Can read enrolled course

Instructor
 ↓
Can modify own course

Admin
 ↓
Can manage users
```

Therefore:

```text
Authentication ≠ Authorization
```

---

# 5. Broken Access Control in Your LMS

Potential examples:

```text
Student → Admin API
Student → Instructor API
Instructor A → Instructor B's course
Student A → Student B's progress
User → Another user's private messages
User → Another user's certificates
```

A particularly dangerous example:

```http
GET /api/v1/users/123/progress
```

If changing:

```text
123 → 124
```

reveals another user's progress, you potentially have an authorization vulnerability.

This type of problem is commonly associated with **IDOR/BOLA-style access-control failures**.

---

# 6. How We Prevent It

Don't rely only on the frontend.

Instead:

```text
Request
   ↓
Authentication
   ↓
Identify user
   ↓
Check role/permission
   ↓
Check resource ownership
   ↓
Perform operation
```

For example:

```js
if (course.instructorId !== req.user.userId) {
  throw new ForbiddenError();
}
```

And ideally the authorization logic belongs in a well-defined service/policy layer rather than being randomly duplicated across controllers.

---

# 7. A02 — Cryptographic Failures

This category is about incorrectly protecting sensitive information through cryptography.

Examples of sensitive data:

```text
Passwords
Authentication tokens
Personal information
Private documents
Secrets
```

A common beginner mistake is storing passwords like:

```text
password = "rahul123"
```

❌ Never do that.

Instead:

```text
Password
   ↓
Password hashing algorithm
   ↓
Password hash
   ↓
Database
```

---

# 8. Hashing vs Encryption

These are different.

### Hashing

Generally one-way:

```text
password
   ↓
hash
```

You don't normally decrypt a password hash.

### Encryption

Reversible with the correct key:

```text
plaintext
   ↓
encryption
   ↓
ciphertext
   ↓
decryption
   ↓
plaintext
```

For passwords, use a dedicated password-hashing approach rather than reversible encryption.

---

# 9. AI LMS Example — Sensitive Data

Suppose your AI conversation contains:

```text
Student's private information
```

and your application sends unnecessary sensitive information to an external AI provider.

That's a security and privacy concern.

Before sending data externally, ask:

```text
Do we need this data?
        ↓
Can we minimize it?
        ↓
Can we anonymize it?
        ↓
Should it be sent at all?
```

Security isn't only about passwords.

---

# 10. A03 — Injection

Injection happens when untrusted input is interpreted as something else.

Common examples include:

```text
SQL Injection
Command Injection
NoSQL Injection
LDAP Injection
Template Injection
```

The classic example is SQL injection.

Imagine unsafe query construction:

```js
const query = `
  SELECT * FROM users
  WHERE email = '${email}'
`;
```

If `email` contains malicious SQL syntax, the resulting query can be manipulated.

---

# 11. Prisma and Injection

Your LMS uses Prisma.

That's good because normal Prisma query APIs use parameterized queries.

For example:

```ts
await prisma.user.findUnique({
  where: {
    email,
  },
});
```

is much safer than manually constructing SQL strings.

But don't think:

> "I use Prisma, therefore injection is impossible."

You can still introduce danger when using:

```text
Raw SQL
Dynamic queries
Unsafe external libraries
Shell commands
Template engines
```

Security depends on **how you use the tools**.

# 13. A04 — Insecure Design

This one is different.

A vulnerability can sometimes exist because the system was designed incorrectly from the beginning.

Example:

```text
AI generation endpoint
        ↓
No user quota
        ↓
No rate limit
        ↓
No maximum input
        ↓
Unlimited expensive requests
```

Even if the code is technically functioning correctly, the **design itself is unsafe**.

---

# 14. LMS Example — Course Enrollment

Imagine your design says:

```text
POST /courses/:id/enroll
```

and enrollment is always allowed.

But your business requirement says:

```text
Private course
   ↓
Only invited students
```

If the design never included an authorization concept for private courses, you have a design-level security problem.

The problem isn't necessarily one bad line of code.

The problem is:

> **The security requirement wasn't designed into the system.**

---

# 15. Security Requirements

This is why security should begin during system design.

For each feature, define:

```text
Who can access it?
Who can modify it?
What data is exposed?
What limits exist?
What happens under abuse?
What should be logged?
```

Example:

```text
AI Tutor
```

Security requirements:

```text
Only authenticated users
        ↓
Only enrolled-course context
        ↓
Rate limits
        ↓
Token/input limits
        ↓
Usage quotas
        ↓
Sensitive-data protection
        ↓
Audit/usage logging
```

---

# 16. A05 — Security Misconfiguration

This happens when security settings are incorrect, unsafe, or left at insecure defaults.

Examples:

```text
Debug mode in production
Overly permissive CORS
Missing security headers
Exposed stack traces
Default passwords
Open admin endpoints
Unnecessary services
Public database
```

---

# 17. Express Example

Bad production behavior:

```js
app.use((err, req, res, next) => {
  res.status(500).json({
    error: err.stack,
  });
});
```

This could expose:

```text
File paths
Internal code
Database information
Library versions
Implementation details
```

Instead, users should receive a safe error response while detailed information goes to controlled logs.

---

# 18. CORS Misconfiguration

Suppose your backend accepts requests from:

```text
*
```

without carefully considering credentials and application architecture.

You may unintentionally expose APIs to unwanted origins.

Security configuration should be intentional:

```text
Allowed origins
Allowed methods
Allowed headers
Credentials
```

Don't blindly copy:

```js
cors()
```

into production without understanding the resulting policy.

---

# 19. A06 — Vulnerable and Outdated Components

Your application depends on:

```text
Express
Prisma
React
Next.js
Zod
Redis
AI SDKs
Docker images
npm packages
```

If one dependency has a known vulnerability, your application may inherit risk.

Example:

```text
Your Application
      ↓
Package A
      ↓
Package B
      ↓
Vulnerable Package
```

This is why dependency security matters.

---

# 20. Dependency Security Workflow

A practical workflow:

```text
Install dependency
       ↓
Lock version
       ↓
Monitor vulnerabilities
       ↓
Update regularly
       ↓
Run security checks
       ↓
Test application
```

Useful commands include:

```bash
npm audit
```

and checking outdated dependencies:

```bash
npm outdated
```

But don't blindly update everything in production.

Updates should be tested.

# 22. LMS Authentication Example

Suppose:

```http
POST /api/v1/auth/login
```

has no rate limiting.

An attacker can repeatedly attempt passwords.

```text
Attempt 1
Attempt 2
Attempt 3
...
Attempt 1,000,000
```

You need controls such as:

```text
Rate limiting
Login monitoring
Account protections

```

# 23. Password Reset Is Security-Critical

Developers sometimes protect:

```text
/login
```

but forget:

```text
/forgot-password
```

Imagine a reset token that:

```text
Never expires
```

or:

```text
Can be reused
```

That's dangerous.

A secure password reset flow should consider:

```text
Random token
      ↓
Short expiration
      ↓
Single use
      ↓
Invalidate after password change
```

# 26. A09 — Security Logging and Monitoring Failures

Imagine someone successfully accesses another user's account.

But your application logs nothing useful.

Later:

```text
What happened?
Who did it?
When?
Which IP/request?
Which resource?
```

You have no answer.

That's a security problem.

---

# 27. What Should We Log?

Security-related events can include:

```text
Login success
Login failure
Logout
Password reset
Permission changes
Role changes
Suspicious requests
Account lockouts
Sensitive administrative actions
File uploads
AI usage
Security violations
```

For important events, useful fields might include:

```text
userId
action
resource
timestamp
requestId
result
```

But be careful:

> **Never log passwords, access tokens, API keys, or other secrets.**

# 28. A10 — Server-Side Request Forgery (SSRF)

SSRF is a vulnerability where an attacker can make your server send requests to unintended destinations.

This becomes particularly interesting for your LMS if you support something like:

```text
Import course content from URL
```

Suppose the API accepts:

```json
{
  "url": "https://example.com/course.pdf"
}
```

Your server does:

```text
Server
  ↓
fetch(url)
```

If you don't restrict URLs properly, an attacker may try to make your server request internal resources.

---

# 29. Why SSRF Is Dangerous

Your server may have access to resources that the public internet cannot directly access.

Conceptually:

```text
Internet
   ↓
Your API
   ↓
Internal network
```

The attacker attempts to abuse your server as a proxy.

Potential targets could include:

```text
Internal services
Cloud metadata endpoints
Private network resources
Administrative interfaces
```

We'll study SSRF protection more deeply later.

# 31. A Very Important Point

OWASP categories often **overlap**.

For example:

```text
Student accesses another student's course
```

could involve:

```text
A01 Broken Access Control
        +
A04 Insecure Design
        +
A09 Logging Failure
```

Security vulnerabilities don't always fit neatly into one box.

The categories are there to help you **think systematically**.

# 34. The Security Engineer's Mindset

A normal developer might think:

```text
"Does this endpoint work?"
```

A security-minded developer asks:

```text
"Does it work?"

"Who can call it?"

"What if they aren't supposed to?"

"What if they change the ID?"

"What if the input is malicious?"

"What if they call it 100,000 times?"

"What if the database is compromised?"

"What if the AI receives malicious instructions?"

"What information could leak?"

"What gets logged?"
```

That's the mindset we're building throughout Phase 14.
