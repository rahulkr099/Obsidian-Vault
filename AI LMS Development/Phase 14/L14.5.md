# 🔐 Lesson 14.5 — Authorization & Access Control

This is one of the **most important security lessons for your AI LMS**.

Authentication answers:

> **Who are you?**

Authorization answers:

> **What are you allowed to do?**

A user can be perfectly authenticated and still be completely unauthorized to perform an action.

---

# 1. Authentication vs Authorization

Imagine:

```text
Rahul logs in
     ↓
Authentication
     ↓
✅ Identity confirmed
```

Now Rahul tries:

```http
DELETE /api/v1/users/another-user
```

The server must ask:

```text
Is Rahul allowed to do this?
```

If not:

```http
403 Forbidden
```

So:

```text
Authentication
      ↓
Who are you?

Authorization
      ↓
What can you do?
```

---

# 2. Why Authorization Is Critical for Your LMS

Your LMS has different types of users:

```text
                    LMS
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
     Student      Instructor     Admin
```

Each has different capabilities.

### Student

```text
Read enrolled courses
Complete lessons
Take quizzes
View own progress
Use AI tutor
```

### Instructor

```text
Create courses
Edit own courses
Create lessons
Manage quizzes
View student progress
```

### Admin

```text
Manage users
Manage courses
Manage system settings
View security information
```

The danger appears when these boundaries are incorrectly implemented.

---

# 3. The First Principle

> **Never trust the frontend to enforce authorization.**

Suppose your React application hides the Admin button:

```text
Student
   ↓
React
   ↓
Admin button hidden
```

That's good for UX.

But it is **not security**.

A student can still manually send:

```http
DELETE /api/v1/users/123
```

using:

```text
curl
Postman
browser DevTools
custom scripts
```

Therefore:

```text
Frontend authorization
        ≠
Security authorization
```

The backend must enforce the rule.

---

# 4. Authorization Flow

A protected request should conceptually go through:

```text
Request
   ↓
Authentication
   ↓
Identify user
   ↓
Check permission
   ↓
Check resource ownership
   ↓
Execute operation
```

For example:

```text
PATCH /courses/123
       ↓
Is user authenticated?
       ↓
Is user an instructor?
       ↓
Does course 123 belong to this instructor?
       ↓
Can this operation be performed?
       ↓
UPDATE
```

---

# 5. RBAC — Role-Based Access Control

The simplest authorization model is **RBAC**.

RBAC means:

> **Role-Based Access Control**

Your LMS could have:

```text
STUDENT
INSTRUCTOR
ADMIN
```

Then define permissions:

```text
STUDENT
├── course:read
├── lesson:read
├── progress:update
└── quiz:attempt

INSTRUCTOR
├── course:create
├── course:update
├── lesson:create
├── lesson:update
└── progress:read

ADMIN
├── user:manage
├── course:manage
└── system:manage
```

This is cleaner than scattering role checks everywhere.

---

# 6. Role vs Permission

Don't confuse these.

### Role

```text
INSTRUCTOR
```

### Permission

```text
course:update
```

A role can contain multiple permissions:

```text
INSTRUCTOR
    ↓
┌──────────────────┐
│ course:create    │
│ course:update    │
│ lesson:create    │
│ quiz:create      │
│ progress:read    │
└──────────────────┘
```

This becomes more flexible than:

```js
if (user.role === "instructor")
```

everywhere.

---

# 7. Why Permission-Based Authorization Is Better

Imagine later you add:

```text
COURSE_MANAGER
MODERATOR
TEACHING_ASSISTANT
```

If your entire codebase is:

```js
if (role === "instructor")
```

you'll need to change many places.

With permissions:

```text
course:update
```

you can assign that permission to:

```text
Instructor
Course Manager
Teaching Assistant
```

without changing the endpoint's fundamental logic.

---

# 8. Simple RBAC Middleware

Conceptually:

```ts
const authorize = (...allowedRoles: Role[]) => {
  return (req, res, next) => {
    if (!allowedRoles.includes(req.user.role)) {
      throw new ForbiddenError();
    }

    next();
  };
};
```

Then:

```ts
router.post(
  "/courses",
  authenticate,
  authorize("INSTRUCTOR", "ADMIN"),
  createCourse
);
```

This protects the **role boundary**.

But we're not finished.

---

# 9. The Biggest Mistake: Role ≠ Ownership

Suppose:

```text
Instructor A
    ↓
Course A

Instructor B
    ↓
Course B
```

Both are:

```text
INSTRUCTOR
```

If we only check:

```text
role === INSTRUCTOR
```

then Instructor A might be able to modify Course B.

That's a serious vulnerability.

We need:

```text
Role
 +
Ownership
```

---

# 10. Resource Ownership

Suppose:

```text
Course
├── id
├── title
└── instructorId
```

Request:

```http
PATCH /courses/123
```

Authenticated user:

```text
userId = 456
```

Database:

```text
course.instructorId = 789
```

Then:

```text
456 !== 789
```

Therefore:

```http
403 Forbidden
```

The user is an instructor, but **not the owner of this resource**.

---

# 11. IDOR

A common access-control problem is called:

> **Insecure Direct Object Reference (IDOR)**

Imagine:

```http
GET /api/v1/users/101/progress
```

Student A can access it.

Then they change:

```text
101 → 102
```

and see Student B's progress.

The vulnerability is:

```text
User controls object ID
        ↓
Backend trusts it
        ↓
Unauthorized object returned
```

---

# 12. BOLA

In API security, you'll also hear:

> **Broken Object Level Authorization (BOLA)**

This is closely related to the same fundamental problem:

```text
User
 ↓
Requests object
 ↓
API fails to verify permission
 ↓
Unauthorized object access
```

For your LMS, BOLA is particularly important because you will have many resource IDs:

```text
userId
courseId
lessonId
quizId
attemptId
certificateId
conversationId
documentId
```

Every one of these can become an authorization boundary.

---

# 13. Example — Student Progress

Suppose:

```http
GET /api/v1/progress/:userId
```

Bad:

```ts
const progress = await progressRepository.findByUserId(
  req.params.userId
);
```

The server trusts the requested ID.

Better for a "my progress" endpoint:

```http
GET /api/v1/me/progress
```

Then:

```ts
const progress =
  await progressRepository.findByUserId(req.user.userId);
```

This removes unnecessary user-controlled identifiers.

---

# 14. `/me` Endpoints

For user-owned resources, this can be a very clean pattern:

```text
GET    /api/v1/me
GET    /api/v1/me/progress
GET    /api/v1/me/courses
GET    /api/v1/me/certificates
PATCH  /api/v1/me/profile
```

Instead of:

```text
GET /users/:userId/progress
```

when the user is simply requesting their own information.

This doesn't eliminate authorization, but it reduces unnecessary ID-based attack surfaces.

---

# 15. Ownership Is Not Always Simple

Sometimes ownership is indirect.

For example:

```text
Student
   ↓
Enrollment
   ↓
Course
   ↓
Lesson
```

Student doesn't directly own the lesson.

Instead:

```text
Student is enrolled in Course
        ↓
Lesson belongs to Course
        ↓
Student can access Lesson
```

So authorization becomes a relationship check.

---

# 16. Example — Lesson Access

Request:

```http
GET /api/v1/lessons/500
```

You might need to verify:

```text
Lesson 500
   ↓
Course 25
   ↓
User 100 enrolled?
```

If:

```text
Enrollment exists
```

then:

```text
✅ Access
```

Otherwise:

```text
❌ Forbidden
```

This is why good database design from Phase 3 is so important.

---

# 17. Authorization Is Closely Connected to Database Design

Your database relationships might look like:

```text
User
 │
 ├───────────────┐
 ↓               ↓
Course        Enrollment
 │               │
 ↓               ↓
Lesson          User
```

Authorization can then use those relationships.

For example:

```text
User
 ↓
Enrollment
 ↓
Course
 ↓
Lesson
```

The database gives you the information needed to determine access.

---

# 18. Don't Fetch First and Authorize Later

Consider:

```ts
const lesson = await lessonRepository.findById(lessonId);

if (lesson.courseId !== courseId) {
   throw new ForbiddenError();
}
```

This can be okay depending on context, but often it's better to scope the database query itself.

For example, conceptually:

```ts
const lesson = await prisma.lesson.findFirst({
  where: {
    id: lessonId,
    course: {
      enrollments: {
        some: {
          userId,
        },
      },
    },
  },
});
```

Then the database only returns the lesson if the relationship exists.

This is powerful **defense in depth**.

---

# 19. Authorization at Multiple Layers

A strong architecture might look like:

```text
Request
   ↓
Authentication
   ↓
Role / Permission
   ↓
Service Authorization
   ↓
Database Scoping
   ↓
Operation
```

For example:

```text
Instructor
    ↓
Can manage courses
    ↓
Is this their course?
    ↓
Does database query enforce ownership?
    ↓
Update
```

If one layer has a mistake, another layer can reduce the damage.

---

# 20. Privilege Escalation

Privilege escalation means:

> A user gains permissions they shouldn't have.

Example:

```text
STUDENT
   ↓
somehow changes role
   ↓
ADMIN
```

Never allow this:

```http
PATCH /api/v1/users/me
```

with:

```json
{
  "role": "ADMIN"
}
```

if your generic profile update accepts arbitrary fields.

---

# 21. Mass Assignment + Privilege Escalation

This is a dangerous combination.

Bad:

```ts
await prisma.user.update({
  where: { id: req.user.userId },
  data: req.body,
});
```

Attacker:

```json
{
  "name": "Rahul",
  "role": "ADMIN"
}
```

Now the attacker potentially changes their own privilege.

Better:

```ts
const updateData = {
  name: req.body.name,
  bio: req.body.bio,
  avatarUrl: req.body.avatarUrl,
};
```

Only explicitly allowed fields are updated.

---

# 22. Admin Authorization

Admin endpoints should be particularly strict.

Example:

```http
DELETE /api/v1/users/:userId
```

Possible policy:

```text
Authenticated?
      ↓
ADMIN?
      ↓
Permission: user:delete?
      ↓
Allowed?
```

Do not rely on:

```text
Frontend hides Delete button
```

The backend must enforce it.

---

# 23. Prevent Self-Privilege Changes

Be careful with endpoints like:

```http
PATCH /users/:id
```

If an admin can change roles, that's fine.

But a student shouldn't be able to send:

```json
{
  "role": "ADMIN"
}
```

You might have separate operations:

```text
PATCH /me/profile
```

for normal user profile changes.

And:

```text
PATCH /admin/users/:id/role
```

for privileged role management.

This separation makes authorization much easier to reason about.

---

# 24. Function-Level Authorization

You can think of permissions as actions:

```text
course:create
course:read
course:update
course:delete

lesson:create
lesson:update
lesson:delete

quiz:create
quiz:publish

user:suspend
user:delete
```

Then:

```text
Instructor
   ↓
course:create
course:update
lesson:create
quiz:create
```

Admin:

```text
Admin
   ↓
*
```

Although in a real system, even admins should ideally operate under explicit policies and least privilege rather than a vague "everything forever" concept.

---

# 25. Resource-Level Authorization

Function-level:

```text
Can instructor update courses?
```

Resource-level:

```text
Can instructor update THIS course?
```

You need both.

```text
Role Permission
      +
Resource Permission
```

Example:

```text
Instructor
   ↓
course:update
   ↓
Course 123
   ↓
instructorId == currentUser.id
```

Only then:

```text
✅ UPDATE
```

---

# 26. Action-Level Authorization

Sometimes access depends on the action.

Example:

```text
Instructor
```

might be allowed to:

```text
edit draft course
```

but not:

```text
publish course
```

Maybe only:

```text
INSTRUCTOR + course:publish
```

or:

```text
ADMIN
```

can publish.

So:

```text
Same resource
     ↓
Different actions
     ↓
Different permissions
```

# 27. Course Lifecycle Example

Your LMS may eventually have:

```text
DRAFT
 ↓
REVIEW
 ↓
PUBLISHED
 ↓
ARCHIVED
```

Different users may have different capabilities.

### Instructor

```text
Create draft
Edit draft
Submit for review
```

### Admin/Reviewer

```text
Review
Publish
Reject
Archive
```

This is **authorization combined with business rules**.

---

# 28. Authorization vs Business Logic

They're related but not identical.

Authorization:

> Can this person perform this operation?

Business rule:

> Is this operation valid right now?

Example:

```text
Instructor owns course
        ↓
Authorization: ✅
        ↓
Course is already archived
        ↓
Business rule: ❌
```

So:

```text
Authorization
     +
Business Rules
```

both need to pass.

---

# 29. Service Layer Is a Good Place for Complex Authorization

Your architecture:

```text
Controller
    ↓
Service
    ↓
Repository
```

works well here.

Controller:

```ts
updateCourseController
```

Service:

```text
verify user
verify permission
verify ownership
verify course state
apply update
```

Repository:

```text
database operation
```

This keeps the controller thin and the security/business logic centralized.

---

# 30. Example Service Flow

Conceptually:

```ts
async function updateCourse(
  userId: string,
  courseId: string,
  input: UpdateCourseInput
) {
  const course = await courseRepository.findById(courseId);

  if (!course) {
    throw new NotFoundError("Course not found");
  }

  if (course.instructorId !== userId) {
    throw new ForbiddenError("Not allowed");
  }

  if (course.status === "ARCHIVED") {
    throw new ConflictError("Course is archived");
  }

  return courseRepository.update(courseId, input);
}
```

Notice the sequence:

```text
Find resource
   ↓
Authorization
   ↓
Business rule
   ↓
Update
```

---

# 31. Avoid Inconsistent Authorization

A dangerous codebase can have:

```text
Controller A
   ↓
checks ownership

Controller B
   ↓
doesn't

Controller C
   ↓
checks role only

Controller D
   ↓
forgets everything
```

This creates security holes.

Prefer reusable policies/services:

```text
authorizeCourseOwner()
authorizeEnrollment()
authorizePermission()
```

or a centralized policy approach.

---

# 32. Policy-Based Authorization

As your LMS grows, you can move toward policies.

Example:

```ts
canUpdateCourse(user, course)
```

returns:

```text
true / false
```

The policy can consider:

```text
role
permissions
ownership
course status
account status
```

For example:

```text
canUpdateCourse(
    user,
    course
)
```

might mean:

```text
user.active
AND
(
  user.role == ADMIN
  OR
  (
    user.role == INSTRUCTOR
    AND course.instructorId == user.id
  )
)
```

This is much easier to test than scattered authorization conditions.

# 33. Student Authorization Model

Let's define some basic policies.

### View course

```text
Public course
     ↓
Anyone

Private course
     ↓
Enrolled student
OR
Instructor
OR
Admin
```

### Complete lesson

```text
Authenticated student
+
Enrolled
+
Lesson belongs to enrolled course
```

### Update progress

```text
Authenticated student
+
Own progress
```

### View another student's progress

```text
Instructor
+
Student enrolled in instructor's course
```

### Manage users

```text
Admin only
```

This is much clearer than simply thinking:

```text
if role === "student"
```

# 34. Instructor Authorization Model

Instructor A:

```text
Course A
```

Instructor B:

```text
Course B
```

Instructor A can:

```text
Course A
├── Update
├── Create lesson
├── Create quiz
└── View enrolled students
```

But cannot:

```text
Course B
├── Update ❌
├── Delete ❌
├── Create lesson ❌

```

Unless a separate permission explicitly allows it.


```text

```

# 36. Authorization and AI/RAG

This is **extremely important**.

Suppose:

```text
Student A
   ↓
Course A
```

and:

```text
Student B
   ↓
Course B
```

The AI request:

```http
POST /api/v1/ai/chat
```

contains:

```json
{
  "courseId": "course-B",
  "message": "Summarize chapter 3"
}
```

Student A must not be able to access Course B just because they know its ID.

You need:

```text
Authentication
      ↓
Course access check
      ↓
RAG filter
      ↓
Retrieval
      ↓
LLM
```

# 37. Authorization Must Reach the RAG Layer

A common mistake:

```text
API
 ↓
Checks user
 ↓
RAG searches everything
```

🚨 Not enough.

Imagine:

```text
PostgreSQL / pgvector
        ↓
All course embeddings
```

Your retrieval query must respect authorization boundaries.

Conceptually:

```text
Search:
  similarity(query)
+
  courseId = authorizedCourse
+
  user-access rules
```

Otherwise the AI could expose data the user isn't allowed to access.


# 40. Security by Default

A good rule:

> **If authorization isn't explicitly granted, access should be denied.**

Conceptually:

```text
Permission exists?
     │
   ┌─┴─┐
  Yes  No
   │    │
 Allow Deny
```

Not:

```text
Permission exists?
     │
   No
   ↓
Maybe allow
```

Security should fail closed.

---

# 41. 401 vs 403

Another important API concept.

### 401 Unauthorized

Usually means:

> Authentication is missing or invalid.

Example:

```http
GET /profile
```

without a valid authentication credential.

Response:

```http
401 Unauthorized
```

---

### 403 Forbidden

Usually means:

> The server knows who you are, but you're not allowed to perform this action.

Example:

```text
Student
   ↓
DELETE /admin/users/123
   ↓
403 Forbidden
```

Simple rule:

```text
401 → Who are you?
403 → You're known, but not allowed.
```

---

# 42. Don't Accidentally Leak Resource Existence

Consider:

```http
GET /courses/123
```

Suppose Course 123 is private.

If unauthorized users always receive:

```text
403 Course exists but you cannot access it
```

you may reveal that the course exists.

Depending on your application, you might instead return:

```text
404 Not Found
```

for resources the user should not even know about.

The right choice depends on your information-disclosure requirements.

# 43. Authorization Matrix

For your LMS, it is useful to maintain a matrix.

|Resource|Student|Instructor|Admin|
|---|---|---|---|
|Public course|Read|Read|Read|
|Enrolled course|Read|Read|Read|
|Own progress|Read/Write|—|—|
|Student progress|Own|Own-course students|All|
|Create course|❌|✅|✅|
|Update own course|❌|✅|✅|
|Update other course|❌|❌|Maybe|
|Create lesson|❌|Own course|✅|
|Manage users|❌|❌|✅|
|AI Tutor|✅|✅|✅|
|RAG course data|Authorized courses|Authorized courses|Authorized|
|Audit logs|❌|❌|Restricted admin|

This isn't your final permission model, but it is a useful starting design.

# 50. Practical Authorization Pattern for Your Project

Given your existing:

```text
Controller
    ↓
Service
    ↓
Repository
```

I'd recommend thinking in three layers.

### Layer 1 — Middleware

Handle broad identity/permission checks:

```text
authenticate
requireRole
requirePermission
```

### Layer 2 — Service

Handle resource-specific authorization:

```text
isCourseOwner
isEnrolled
canUpdateLesson
canViewProgress
```

### Layer 3 — Repository

Scope database queries whenever practical:

```text
findCourseForInstructor()
findLessonForEnrolledStudent()
findProgressForUser()
```

This makes accidental data exposure much harder.

```ts
router.patch(
  "/courses/:courseId",
  authenticate,
  authorize("INSTRUCTOR"),
  updateCourse
);
```

Question:

> Is this enough?

**No.**

Why?

```text
Instructor A
    ↓
Course B
```

The role is correct, but ownership hasn't been checked.

### Example B

```ts
router.get(
  "/users/:userId/progress",
  authenticate,
  getProgress
);
```

Question:

> What's missing?

Potentially:

```text
Resource ownership
OR
Instructor/admin authorization
```

```ts
router.patch(
```

Request:

```json
{
  "name": "Rahul",
```

> What's the problem?

**Mass assignment / privilege escalation.**

# 🧠 52. Your Authorization Mental Model

Whenever you see:

```text
/resource/:id
```

immediately ask:

```text
Who is requesting it?
       ↓
Are they authenticated?
       ↓
Are they allowed to access this resource?
       ↓
Does this resource belong to them?
       ↓
Are they allowed to perform THIS action?
       ↓
Is the resource in a valid state?
```

That mental checklist will save you from many serious backend vulnerabilities.

# 🎯 Lesson 14.5 Summary

The key concepts:

```text
Authentication
     ↓
Who are you?

Authorization
     ↓
What can you do?

RBAC
     ↓
Role-based permissions

Resource Ownership
     ↓
Can you access THIS resource?

IDOR / BOLA
     ↓
Unauthorized object access

Least Privilege
     ↓
Only give necessary permissions

Policy-based Authorization
     ↓
Centralize complex access rules

Defense in Depth
     ↓
Protect at multiple layers
```

For your AI LMS:

```text
Student
 ├── Own data
 ├── Enrolled courses
 └── Authorized AI/RAG context

Instructor
 ├── Own courses
 ├── Own course content
 └── Authorized student progress

Admin
 └── Administrative permissions
```

And the **golden rule**:

> 🔥 **Never ask only "Is this user an instructor?" Ask "Is this user an instructor, are they allowed to perform this action, and are they allowed to perform it on this specific resource?"**

That distinction is what separates basic role checking from real authorization engineering.
