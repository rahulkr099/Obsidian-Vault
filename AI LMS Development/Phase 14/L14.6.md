# 🌐 Lesson 14.6 — Web Security

Now we move from **API security** to the security of the actual web application.

Your architecture looks roughly like:

```text
React + TypeScript
        ↓
     Browser
        ↓
   HTTPS / Web
        ↓
   Express API
        ↓
 PostgreSQL / Redis / AI
```

The browser is a special environment because it executes code, stores browser data, sends cookies automatically, follows redirects, and communicates with other origins.

So we need to protect both:

```text
Browser
   ↕
Frontend
   ↕
Backend
```

The main topics today are:

```text
XSS
CSRF
CORS
Cookies
Clickjacking
Content Security Policy
Security Headers
Open Redirects
Session Attacks
```

---

# 1. The Web Security Mindset

For every web application, ask:

```text
What can JavaScript execute?
What can the browser send automatically?
What data can the browser store?
Which websites can communicate with my API?
Can an attacker make the browser perform an action?
Can an attacker inject content?
Can an attacker steal session information?
```

For your AI LMS, this matters because you'll have:

```text
Login
Dashboard
Course content
User profiles
AI chat
File uploads
Instructor tools
Admin tools
```

All of these interact with the browser.

---

# 2. XSS — Cross-Site Scripting

XSS happens when an attacker gets malicious JavaScript executed in another user's browser.

Imagine a comment field:

```text
Course review
```

A malicious user submits content containing executable HTML/JavaScript.

If your application renders it unsafely:

```text
Attacker input
     ↓
Database
     ↓
React application
     ↓
Browser executes it
```

Now the attacker's code runs in another user's browser.

---

# 3. Why XSS Is Dangerous

An XSS attack can potentially allow malicious code to:

```text
Read page content
Perform actions as the user
Modify the UI
Steal accessible browser data
Interact with APIs
Redirect users
```

If authentication material is accessible to JavaScript, XSS can become especially dangerous.

This is one reason authentication storage decisions matter.

---

# 4. React Helps — But Doesn't Make You Immune

React escapes normal text rendering.

For example:

```tsx
<p>{userInput}</p>
```

is generally much safer than manually injecting HTML.

But React provides an escape hatch:

```tsx
<div
  dangerouslySetInnerHTML={{
    __html: userInput
  }}
/>
```

🚨 This is dangerous when `userInput` is not properly sanitized.

---

# 5. The Dangerous `dangerouslySetInnerHTML`

Imagine your LMS allows instructors to create lesson content.

The lesson might contain:

```html
<h2>JavaScript Basics</h2>
<p>Learn variables...</p>
```

You might want rich HTML.

But if arbitrary HTML is accepted:

```text
Instructor/User input
       ↓
Raw HTML
       ↓
Browser
```

you need a trusted sanitization strategy.

Otherwise malicious HTML could become:

```text
User content
    ↓
HTML
    ↓
JavaScript execution
```

---

# 6. Where XSS Can Enter Your LMS

Potential sources:

```text
User profile
Course title
Course description
Lesson content
Comments
Reviews
Discussion posts
AI responses
Search results
Uploaded content
Admin-created HTML
```

Don't think:

> "Only comments can have XSS."

Any user-controlled content that eventually reaches an HTML execution context deserves attention.

---

# 7. Stored XSS

One major type is **stored XSS**.

Flow:

```text
Attacker
   ↓
Malicious content
   ↓
Database
   ↓
Victim opens page
   ↓
Browser executes malicious content
```

Example:

```text
Course review
    ↓
Stored in PostgreSQL
    ↓
Displayed to students
```

If rendered unsafely, every student viewing that review could be affected.

---

# 8. Reflected XSS

Another type is reflected XSS.

Conceptually:

```text
Attacker
   ↓
Malicious URL/input
   ↓
Server
   ↓
Response
   ↓
Browser
```

For example:

```text
/search?q=<malicious-input>
```

If your application places the query into an unsafe HTML context, it can become an XSS vulnerability.

Modern frameworks reduce many of these risks, but unsafe HTML rendering and custom DOM manipulation can reintroduce them.

---

# 9. DOM-Based XSS

DOM-based XSS occurs when client-side JavaScript takes untrusted data and places it into a dangerous DOM context.

Conceptually:

```text
URL / browser input
       ↓
JavaScript
       ↓
innerHTML
       ↓
Browser
```

Be careful with APIs such as:

```text
innerHTML
outerHTML
document.write
eval
```

and other dangerous dynamic execution patterns.

---

# 10. XSS Prevention

Use multiple layers.

### Layer 1

Prefer React's normal escaping:

```tsx
<p>{content}</p>
```

### Layer 2

Avoid unnecessary raw HTML.

### Layer 3

If rich HTML is genuinely required:

```text
Untrusted HTML
      ↓
Trusted sanitizer
      ↓
Safe HTML
      ↓
Render
```

### Layer 4

Use a suitable Content Security Policy.

### Layer 5

Protect authentication/session material.

That's defense in depth.

---

# 11. CSRF — Cross-Site Request Forgery

CSRF is different from XSS.

The basic idea:

> An attacker tricks a victim's browser into making an authenticated request to your application.

Suppose the victim is logged into:

```text
https://lms.example.com
```

The browser has an authentication cookie.

Then the victim visits:

```text
https://malicious.example
```

The malicious site attempts to cause:

```text
POST https://lms.example.com/api/...
```

If the browser automatically includes the authentication cookie and the server has inadequate CSRF defenses, the request could potentially succeed.

---

# 12. XSS vs CSRF

Remember:

|XSS|CSRF|
|---|---|
|Malicious code executes in your application context|Attacker causes the browser to make a request|
|Often involves injected script/content|Often abuses automatically attached credentials|
|Targets browser execution|Targets authenticated actions|
|CSP/sanitization help|SameSite/CSRF tokens/origin checks help|

A useful mental model:

```text
XSS
Attacker → Code executes in your page

CSRF
Attacker → Browser performs action on your site
```

---

# 13. Why Cookies Matter for CSRF

Cookies are automatically attached by the browser when their rules match.

For example:

```text
Browser
   ↓
Request to LMS
   ↓
Cookie automatically included
```

That's convenient.

But it means:

> Authentication stored in cookies requires careful CSRF consideration.

This is one reason `SameSite` is important.

---

# 14. SameSite Cookies

Cookies can have:

```text
SameSite=Strict
SameSite=Lax
SameSite=None
```

Conceptually:

### Strict

More restrictive cross-site cookie behavior.

### Lax

Allows some common top-level navigation behavior while restricting many cross-site requests.

### None

Allows cross-site cookie sending, but requires:

```text
Secure
```

The right choice depends on your deployment architecture.

Don't blindly copy a cookie configuration from another project.

---

# 15. CSRF Tokens

Another common defense is a CSRF token.

Conceptually:

```text
Server
  ↓
CSRF token
  ↓
Trusted frontend
  ↓
Request + CSRF token
  ↓
Server verifies token
```

An attacker's website doesn't normally have access to the legitimate application's CSRF token.

So:

```text
Valid authentication
       +
Valid CSRF token
       ↓
Allow action
```

This is particularly relevant when using cookie-based authentication.

---

# 16. Origin Validation

For sensitive requests, the server can also examine headers such as:

```text
Origin
Referer
```

For example:

```text
Origin: https://app.example.com
```

The server can verify that the request originates from an expected application context.

This can be an additional defense.

---

# 17. CORS

CORS stands for:

> **Cross-Origin Resource Sharing**

Suppose:

```text
Frontend
https://app.example.com

API
https://api.example.com
```

These are different origins.

The browser uses CORS rules to determine whether frontend JavaScript is allowed to access the API response.

---

# 18. What CORS Actually Protects

CORS mainly controls:

> **Which browser origins can read responses from your API.**

It does **not** mean:

```text
Only allowed websites can send requests.
```

And it definitely does not replace:

```text
Authentication
Authorization
Rate limiting
Input validation
```

Remember:

```text
CORS ≠ Authentication
CORS ≠ Authorization
```

---

# 19. Dangerous CORS Configuration

Be careful with overly broad policies such as:

```text
Access-Control-Allow-Origin: *
```

Especially when authentication uses credentials/cookies.

You generally want an intentional allowlist:

```text
Allowed origins:
    https://app.example.com
```

rather than:

```text
Everyone
```

---

# 20. CORS + Credentials

If your architecture uses cookies across origins, you may need credentialed requests.

Conceptually:

```text
Frontend
   ↓
credentials
   ↓
API
```

Then the server must carefully configure:

```text
Allowed origin
Allowed credentials
Allowed methods
Allowed headers
```

You cannot safely combine arbitrary origins with credentialed access.

---

# 21. Your React + Express Architecture

Suppose:

```text
React
https://app.example.com
       │
       │ HTTPS
       ↓
Express
https://api.example.com
       │
       ↓
PostgreSQL
```

Your API should explicitly understand:

```text
Trusted frontend origin
        ↓
CORS policy
```

But the API should still independently verify:

```text
Authentication
Authorization
```

---

# 22. Clickjacking

Clickjacking happens when an attacker tricks users into clicking something on your application, often by embedding it inside another page or frame.

Conceptually:

```text
Attacker Website
      ↓
Invisible/overlaid frame
      ↓
Your LMS
```

The victim thinks they're clicking:

```text
"Play Video"
```

but could actually be interacting with:

```text
"Delete Account"
```

if the UI is manipulated.

---

# 23. Preventing Clickjacking

Browser security policies can restrict whether your application can be framed.

Important mechanisms include:

```text
Content-Security-Policy:
frame-ancestors ...

X-Frame-Options
```

For modern applications, CSP `frame-ancestors` provides a flexible mechanism for controlling embedding.

---

# 24. Content Security Policy — CSP

CSP is one of the most useful browser security mechanisms.

It tells the browser:

> **Which types of content are allowed to execute or load.**

Conceptually:

```text
Content-Security-Policy:
    default-src 'self';
    script-src 'self';
    img-src 'self' https:;
    connect-src 'self' https://api.example.com;
```

The exact policy must match your application.

Don't copy this blindly.

---

# 25. Why CSP Helps Against XSS

Suppose an attacker somehow injects:

```html
<script src="https://evil.example/script.js"></script>
```

If your CSP says:

```text
script-src 'self'
```

the browser can block scripts from unauthorized sources.

So:

```text
XSS vulnerability
      ↓
CSP
      ↓
Potentially reduce impact
```

But:

> **CSP is not a replacement for preventing XSS.**

It's another layer.

---

# 26. CSP and Your AI LMS

Your frontend may communicate with:

```text
API
AI services
Image storage
Video storage
Analytics
```

So CSP needs to account for legitimate connections.

For example:

```text
connect-src
```

may need to allow your API origin.

Similarly:

```text
img-src
media-src
font-src
```

may need appropriate trusted sources.

The goal is:

```text
Allow what you need
      ↓
Block everything else
```

---

# 27. Security Headers

Security headers can provide browser-level protections.

Common examples include:

```text
Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options
Referrer-Policy
Permissions-Policy
X-Frame-Options
```

Modern browser security configuration should be intentional and tested because some headers/policies can affect application functionality.

---

# 28. HSTS

HSTS stands for:

> HTTP Strict Transport Security

It tells compatible browsers:

> **Use HTTPS for this site.**

Conceptually:

```text
http://lms.example.com
       ↓
HTTPS
```

HSTS helps prevent certain downgrade and insecure-transport scenarios.

Only enable production HSTS settings after understanding your domain/subdomain architecture because aggressive settings can have operational consequences.

---

# 29. HTTPS

Never treat HTTPS as optional for production authentication.

Without HTTPS:

```text
Browser
   ↓
HTTP
   ↓
Network
```

Sensitive traffic can potentially be observed or modified.

With HTTPS:

```text
Browser
   ↓
Encrypted TLS connection
   ↓
Server
```

HTTPS protects the connection against many network-level threats.

---

# 30. Open Redirects

An open redirect happens when your application redirects users to an attacker-controlled URL.

Suppose:

```text
https://lms.example.com/login?next=https://evil.example
```

and your server blindly does:

```text
redirect(next)
```

The user may trust:

```text
lms.example.com
```

but gets redirected to:

```text
evil.example
```

This can be useful in phishing attacks.

---

# 31. Safe Redirects

Prefer allowlists or validated internal paths.

For example:

```text
Allowed:
 /dashboard
 /courses
 /profile
```

Instead of:

```text
Any arbitrary URL
```

If external redirects are genuinely required, validate the destination carefully.

---

# 32. Session Attacks

A session represents the user's authenticated state.

Possible attacks include:

```text
Session theft
Session fixation
Session replay
Session hijacking
```

Let's understand them.

---

# 33. Session Theft

Attacker obtains a valid session/token.

```text
User
 ↓
Session
 ↓
Attacker steals it
 ↓
Authenticated API access
```

Defenses:

```text
HTTPS
Secure cookie configuration
Short-lived access tokens
Refresh-token protection
Session revocation
XSS prevention
```

---

# 34. Session Fixation

Conceptually:

```text
Attacker obtains session identifier
        ↓
Victim authenticates
        ↓
Application continues using same session
        ↓
Attacker knows authenticated session
```

The general defense is:

> **Regenerate authentication/session identifiers after successful authentication or privilege changes.**

For token-based architectures, the equivalent design concern is ensuring authentication credentials aren't predictably reused across privilege transitions.

---

# 35. Session Replay

An attacker captures a valid token and reuses it.

```text
Valid token
    ↓
Request 1
    ↓
Request 2
    ↓
Request 3
```

Defenses can include:

```text
Short-lived access tokens
Refresh-token rotation
Revocation
Session monitoring
TLS
```

---

# 36. Account Takeover Chain

Let's combine the lessons.

An attacker could theoretically do:

```text
Weak password
     ↓
Credential stuffing
     ↓
Account takeover
     ↓
Stolen session
     ↓
AI API abuse
     ↓
Private course access
     ↓
RAG data leakage
```

This demonstrates why:

```text
Authentication
+
Authorization
+
Web security
+
AI security
```

must work together.

---

# 37. Web Security and Your AI Chat

Your AI chat UI may display:

```text
User message
AI response
Course references
Source documents
Markdown
Code blocks
Links
```

This introduces additional rendering concerns.

For example:

```text
AI response
    ↓
Markdown renderer
    ↓
HTML
```

You must ensure that untrusted generated content doesn't become executable HTML.

---

# 38. AI Output Is Not Automatically Trusted

This is an important AI security principle:

> **Treat LLM output as untrusted data.**

Even though the output came from your AI provider, it can contain:

```text
HTML
URLs
Unexpected markup
Instructions
Malicious content from retrieved documents
```

So:

```text
LLM output
    ↓
Validate / sanitize / safely render
    ↓
UI
```

Don't assume:

```text
LLM → trusted HTML
```

---

# 39. RAG + Web Security

Suppose a malicious document contains:

```text
Ignore all previous instructions...
```

RAG retrieves it.

Then:

```text
Document
   ↓
Embedding
   ↓
Retrieval
   ↓
LLM
   ↓
Response
```

The AI response could potentially contain malicious content.

Your frontend should still safely render that response.

So we have:

```text
RAG security
      +
LLM output handling
      +
XSS protection
```

---

# 40. File Links and Download Security

Suppose the LMS displays:

```text
Download course PDF
```

Don't assume that the file URL itself provides authorization.

For private resources:

```text
User
 ↓
Authentication
 ↓
Course authorization
 ↓
File authorization
 ↓
Signed/controlled access
```

A copied URL shouldn't automatically grant unauthorized access.

We'll go much deeper into this in **14.10**.

---

# 41. Browser Storage

Your frontend may need to store:

```text
User preferences
UI state
Non-sensitive cached data
```

Be careful with storing:

```text
Passwords
Refresh tokens
API keys
Sensitive personal data
Long-lived authentication credentials
```

in browser-accessible storage.

The browser environment should be considered partially hostile because JavaScript running in your origin can access many browser storage mechanisms.

---

# 42. LocalStorage and XSS

If you store:

```text
accessToken
```

in:

```js
localStorage
```

then JavaScript running under your application's origin may potentially read it.

If an XSS vulnerability exists:

```text
XSS
 ↓
JavaScript execution
 ↓
localStorage
 ↓
Token theft
```

This doesn't automatically mean localStorage is always wrong.

It means:

> **Your token-storage decision and XSS threat model must be considered together.**

---

# 43. Cookie-Based Authentication

With an HttpOnly cookie:

```text
Browser
  ↓
HttpOnly cookie
  ↓
Server
```

JavaScript cannot directly read the cookie.

That can reduce some token-theft paths through XSS.

But now you must carefully handle:

```text
CSRF
SameSite
CORS
Origin validation
```

Security is about tradeoffs, not magic storage locations.

---

# 44. Don't Put Secrets in Frontend Code

This is extremely important.

React/Vite frontend code eventually becomes public browser code.

Never put:

```text
OPENAI_API_KEY
DATABASE_URL
JWT_SECRET
PRIVATE_API_KEY
```

inside frontend environment variables intended for server secrets.

Anything shipped to the browser should be considered potentially visible to users.

---

# 45. API Proxy Pattern for AI

Instead of:

```text
React
   ↓
OpenAI API
   ↓
API key exposed
```

use:

```text
React
   ↓
Your Express API
   ↓
AI Provider
```

Then:

```text
AI API key
   ↓
Server environment
```

The browser never receives the provider's secret key.

This is particularly important for your AI LMS.

# 48. A Real Attack Chain

Let's imagine a poorly secured LMS:

```text
Attacker
   ↓
Finds XSS in course review
   ↓
JavaScript executes
   ↓
Steals accessible session credential
   ↓
Uses authenticated API
   ↓
Authorization is weak
   ↓
Accesses instructor resources
   ↓
Calls AI endpoints
   ↓
Abuses expensive AI generation
```

Notice how several security failures combine:

```text
XSS
+
Authentication weakness
+
Authorization weakness
+
AI abuse
```

Real attacks often involve **chains of vulnerabilities**, not one isolated bug.

```text

 ↓
```

```text
CSRF
```
```text
 ↓
```

```text
CORS
 ↓
Control browser cross-origin access

Cookies
 ↓
Secure authentication/session handling

 ↓

 ↓
```

Your AI LMS should eventually follow this model:

```text
                    Browser
                       │
                     HTTPS
                       │
                       ↓
                 React Frontend
                       │
              Safe HTML Rendering
                       │
                       ↓
                  Express API
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
        CORS          Auth         CSRF
          │            │            │
          └────────────┼────────────┘
                       ↓
                 Authorization
                       ↓
                 PostgreSQL
                       ↓
                    AI/RAG
```

### 🔥 The biggest takeaway

> **The browser is not a trusted environment. Treat user input, browser storage, URLs, cookies, uploaded content, and AI-generated content carefully.**

Once you understand that, many web-security decisions become much easier.
