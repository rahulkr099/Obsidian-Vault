# 4. `config/`

```text
config/
├── env.ts
└── database.ts
```

This folder contains application configuration.

### `env.ts`

Responsible for:

```text
Environment variables
Environment validation
Configuration values
```

For example:

```env
NODE_ENV=development
PORT=5000
DATABASE_URL=...
CLIENT_URL=http://localhost:5173
JWT_SECRET=...
```

You don't want environment variables scattered throughout the application.

Instead:

```text
process.env
     ↓
config/env.ts
     ↓
application
```

---

# 5. Database Configuration

```text
config/database.ts
```

This should be the central place for Prisma.

Conceptually:

```ts
import { PrismaClient } from "@prisma/client";

export const prisma = new PrismaClient();
```

Then repositories use:

```ts
import { prisma } from "../../config/database";
```

This prevents you from creating random Prisma clients throughout the application.

# 6. `middleware/`

Our middleware folder contains things that operate at the HTTP boundary.

```text
middleware/
├── auth.ts
├── errorHandler.ts
├── notFound.ts
├── rateLimiter.ts
├── requestId.ts
├── requestLogger.ts
└── validate.ts
```

### `auth.ts`

Answers:

> Who is this user?

### `validate.ts`

Answers:

> Is this request valid?

### `rateLimiter.ts`

Answers:

> Is this client sending too many requests?

### `requestId.ts`

Answers:

> How do we identify this request?

### `requestLogger.ts`

Answers:

> What happened during this request?

### `errorHandler.ts`

Answers:

> How do we turn errors into API responses?

Each middleware has one clear responsibility.

# 15. Why Separate Routes From Modules?

Because routes describe the **external API**.

Modules describe the **internal business domain**.

For example:

```text

          ↓
modules/courses/course.controller
          ↓
modules/courses/course.service
```

This separation makes future API versions easier.

# 18. `app.ts` vs `server.ts`

This is an important design decision.

### `app.ts`

Creates and configures Express.

```ts
export const app = express();
```

### `server.ts`

Starts the server.

```ts
app.listen(PORT);
```

Think:

```text
app.ts
    ↓
Application definition

server.ts
    ↓
Application startup
```

---

# 19. Why Separate Them?

Testing.

Your test can import:

```ts
import { app } from "../src/app";
```

without starting a real server.

Supertest can then do:

```ts
request(app)
```

This is cleaner.

# 21. Complete Request Lifecycle

Let's follow:

```http
POST /api/v1/courses
```

### Step 1

Request enters Express.

```text
Client
 ↓
Express
```

### Step 2

Security headers.

```text
Helmet
```

### Step 3

Request gets an ID.

```text
req_abc123
```

### Step 4

Request gets logged.

### Step 5

Global rate limiter checks the request.

### Step 6

API version router handles:

```text
/api/v1
```

### Step 7

Course route matches:

```text
/courses
```

### Step 8

Authentication verifies the user.

### Step 9

Authorization verifies the user's role.

### Step 10

Zod validates the body.

### Step 11

Controller calls:

```text

```

### Step 12

Service executes business rules.

### Step 13

Repository accesses Prisma.

### Step 14

Prisma talks to PostgreSQL.

### Step 15

Result returns upward.

```text
PostgreSQL
 ↓
Prisma
 ↓
Repository
 ↓
Service
 ↓
Controller
 ↓
HTTP Response
```

# 22. What Does a Thin Controller Look Like?

A good controller might be:

```ts
export const createCourse = asyncHandler(
  async (req, res) => {
    const course =
      await courseService.createCourse({
        ...req.body,
        instructorId: req.user!.id,
      });

    res.status(201).json({
      success: true,
      data: course,
    });
  }
);
```

That's excellent.

Notice what isn't here:

```text
No Prisma
No SQL
No business rules
No complicated calculations
No giant try/catch
```

That's the goal.

---

# 23. What Does a Bad Controller Look Like?

Avoid this:

```ts
async function createCourse(req, res) {
  const user = await prisma.user.findUnique(...);

  if (!user) ...

  if (user.role !== "INSTRUCTOR") ...

  const existing = await prisma.course.findFirst(...);

  if (existing) ...

  const course = await prisma.course.create(...);

  await prisma.section.create(...);

  await prisma.lesson.create(...);

  res.json(...);
}
```

The controller has become:

```text
Authentication
Authorization
Business Logic
Database
Workflow
HTTP
```

Everything is mixed together.

---

# 24. Service Layer Example

A better service:

```ts
export async function createCourse(input) {
  const existing =
    await courseRepository.findByTitleAndInstructor(
      input.title,
      input.instructorId
    );

  if (existing) {
    throw new AppError(
      "Course already exists",
      409
    );
  }

  const course =
    await courseRepository.create(input);

  return course;
}
```

Later this can grow into:

```text
Validate business rules
 ↓
Create course
 ↓
Create default section
 ↓
Create welcome lesson
 ↓
Trigger AI generation
 ↓
Create audit event
```

without turning the controller into a mess.

# 25. Repository Example

```ts
export const courseRepository = {
  findById(id: string) {
    return prisma.course.findUnique({
      where: { id },
    });
  },

  create(data: CreateCourseData) {
    return prisma.course.create({
      data,
    });
  },

  update(id: string, data: UpdateCourseData) {
    return prisma.course.update({
      where: { id },
      data,
    });
  },
};
```

Again:

> Repository talks to the database.

# 26. Error Flow

Our production skeleton needs one centralized error handler.

```text
Controller
   ↓
Service
   ↓
AppError
   ↓
asyncHandler
   ↓
errorHandler
   ↓
HTTP response
```

For example:

```ts
throw new AppError(
  "Course not found",
  404
);
```

becomes:

```json
{
  "success": false,
  "error": {
    "message": "Course not found",
    "requestId": "req_abc123"
  }
}
```

The client doesn't need to know the internal stack trace.

---

# 27. Production Error Rule

Never expose:

```text
database connection string
SQL queries
stack traces
API keys
internal service information
```

to users in production.

Instead:

```text
Client
 ↓
Safe error message

Server
 ↓
Detailed logs
```

For example:

### Client

```json
{
  "success": false,
  "error": {
    "message": "Something went wrong",
    "requestId": "req_abc123"
  }
}
```

### Server logs

```text
ERROR
requestId=req_abc123
error=PrismaClientKnownRequestError
database=...
stack=...
```

That separation is important.

# 39. The Most Important Rules

I want you to remember these **10 rules**.

### Rule 1

**Controllers should be thin.**

```text
HTTP → Service → Response
```

### Rule 2

**Services contain business logic.**

```text
Business decisions → Service
```

### Rule 3

**Repositories handle database access.**

```text
Database operations → Repository
```

### Rule 4

**Validate at the API boundary.**

```text
Untrusted input → Validation → Application
```

### Rule 5

**Don't trust the frontend.**

Backend must validate everything important.

### Rule 6

**Don't expose internal errors.**

Log details server-side.

### Rule 7

**Every important request should be traceable.**

Use request IDs.

### Rule 8

**Protect expensive endpoints.**

Use appropriate rate limits.

### Rule 9

**Test business-critical behavior.**

Don't chase meaningless 100% coverage.

### Rule 10

**Start as a modular monolith.**

Only introduce distributed architecture when the problem requires it.
