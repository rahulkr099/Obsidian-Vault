# Lesson 2.3 — Async Handler + Thin Controllers

Now we're going to clean up our controllers.

At the moment, our controller looks like:

```ts
async getCourses(_req, res) {
  const courses = await courseService.getCourses();

  res.json({
    success: true,
    data: courses,
  });
}
```

This looks fine.

But as the application grows, we'll have dozens of controllers:

```text
Auth
Courses
Lessons
Quizzes
Enrollments
Progress
AI
Admin
Payments
```

We don't want every controller worrying about:

```text
try/catch
next(error)
error forwarding
```

So we'll create an `asyncHandler`.

---

# 1. The Problem

Imagine we wrote:

```ts
async getCourse(req, res, next) {
  try {
    const course = await courseService.getCourse(req.params.id);

    res.json({
      success: true,
      data: course,
    });
  } catch (error) {
    next(error);
  }
}
```

This works.

But now every controller needs:

```ts
try {
   ...
} catch (error) {
   next(error);
}
```

Imagine 50 controllers.

That's a lot of repetition.

---

# 2. What We Want

We want this:

```ts
getCourse: asyncHandler(async (req, res) => {
  const course = await courseService.getCourse(req.params.id);

  res.json({
    success: true,
    data: course,
  });
}),
```

If something fails:

```text
Service throws
      ↓
asyncHandler
      ↓
next(error)
      ↓
Global errorHandler
```

That's the whole idea.

---

# 3. Create `asyncHandler`

Create:

```bash
cd ~/Projects/ai-lms/apps/api

mkdir -p src/utils
touch src/utils/asyncHandler.ts
```

Add:

```ts
import type { NextFunction, Request, RequestHandler, Response } from 'express';

type AsyncHandler = (
  req: Request,
  res: Response,
  next: NextFunction,
) => Promise<unknown>;

export const asyncHandler = (
  handler: AsyncHandler,
): RequestHandler => {
  return (req, res, next) => {
    Promise.resolve(handler(req, res, next)).catch(next);
  };
};
```

---

# 4. Understand `asyncHandler`

Suppose:

```ts
asyncHandler(async (req, res) => {
  const course = await courseService.getCourse(...);

  res.json(course);
});
```

Internally:

```text
async function
     ↓
Promise
     ↓
success → response
error   → catch(next)
```

So:

```ts
.catch(next)
```

is the important part.

It forwards the error to Express.

---

# 5. Where Does `next(error)` Go?

Remember our previous lesson:

```text
AppError
   ↓
Global Error Handler
```

Now our complete error flow becomes:

```text
Controller
    │
    ▼
Service
    │
    ▼
throws AppError
    │
    ▼
asyncHandler
    │
    ▼
next(error)
    │
    ▼
global errorHandler
    │
    ▼
JSON response
```

This is exactly what we want.

# 6. Refactor `course.controller.ts`

Currently we have:

```ts
export const courseController = {
  async getCourses(_req, res) {
    const courses = await courseService.getCourses();

    res.json({
      success: true,
      data: courses,
    });
  },
};
```

Let's change it.

```ts
import type { Request, Response } from 'express';

import { asyncHandler } from '../../utils/asyncHandler.js';
import { courseService } from './course.service.js';

export const courseController = {
  getCourses: asyncHandler(async (_req: Request, res: Response) => {
    const courses = await courseService.getCourses();

    res.json({
      success: true,
      data: courses,
    });
  }),

  getCourseCount: asyncHandler(async (_req: Request, res: Response) => {
    const count = await courseService.getCourseCount();

    res.json({
      success: true,
      data: {
        count,
      },
    });
  }),

  getCourseById: asyncHandler(async (req: Request, res: Response) => {
    const course = await courseService.getCourseById(req.params.id);

    res.json({
      success: true,
      data: course,
    });
  }),
};
```

Notice something important.

There is **no `try/catch`**.

---

# 7. Why Is This Better?

Before:

```text
Controller
├── business logic
├── response
└── try/catch
```

Now:

```text
Controller
└── HTTP input → Service → HTTP response
```

Error handling is centralized.

This keeps controllers thin.

---

# 8. What Should a Controller Actually Do?

A controller should mainly perform three things:

```text
1. Read HTTP input
2. Call service
3. Send HTTP response
```

For example:

```ts
getCourse: asyncHandler(async (req, res) => {
  const course = await courseService.getCourseById(req.params.id);

  res.status(200).json({
    success: true,
    data: course,
  });
}),
```

That's a good controller.

---

# 9. What Should NOT Be in the Controller?

Avoid:

```ts
const course = await prisma.course.findUnique(...);
```

❌ Database logic.

Avoid:

```ts
if (course.instructorId !== req.user.id) {
  ...
}
```

❌ Business logic.

Avoid:

```ts
if (!req.body.title) {
  ...
}
```

❌ Validation logic.

Avoid:

```ts
const passwordHash = await bcrypt.hash(...);
```

❌ Authentication/business logic.

The controller should remain the HTTP boundary.

# 13. Why `Promise.resolve()`?

Our implementation:

```ts
Promise.resolve(handler(req, res, next)).catch(next);
```

makes the wrapper work with promise-returning handlers.

Conceptually:

```text
handler()
   ↓
Promise
   ↓
.catch(next)
```

So when:

```ts
throw new AppError(...)
```

happens inside an async function, the returned Promise becomes rejected.

Then:

```ts
.catch(next)
```

forwards it to Express.

---

# 14. A Simpler Version

You may see implementations online like:

```ts
export const asyncHandler = (
  fn: RequestHandler,
): RequestHandler => {
  return (req, res, next) => {
    Promise.resolve(fn(req, res, next)).catch(next);
  };
};
```

This is fine.

Our explicit type:

```ts
type AsyncHandler = (...)
```

helps us understand exactly what we're accepting.

For this project, I'd keep the explicit version for now.

# 16. Important Route Ordering

We currently have:

```ts
router.get('/', courseController.getCourses);
router.get('/count', courseController.getCourseCount);
router.get('/:id', courseController.getCourseById);
```

The `/count` route should appear **before**:

```text
/:id
```

Why?

Because:

```text
/count
```

could otherwise be interpreted as:

```text
id = "count"
```

So this:

```text
/count
```

must come before:

```text
/:id
```

This is a small detail that causes real bugs.

# 17. Controller Type Inference

Because our `asyncHandler` is typed, TypeScript can help us.

For example:

```ts
getCourses: asyncHandler(async (_req, res) => {
```

You may not need:

```ts
(_req: Request, res: Response)
```

because the wrapper provides the types.

So we can simplify:

```ts
export const courseController = {
  getCourses: asyncHandler(async (_req, res) => {
    const courses = await courseService.getCourses();

    res.json({
      success: true,
      data: courses,
    });
  }),
};
```

I prefer this.

Less noise.

# 19. The "Thin Controller" Rule

For our AI LMS, I'd like you to follow this rule:

> **If your controller starts becoming complicated, the logic probably belongs somewhere else.**

For example, if you have:

```ts
getCourse: asyncHandler(async (req, res) => {
  // 80 lines
})
```

that's a warning sign.

A healthy controller might look like:

```text
5–15 lines
```

Not always, but that's a useful target.

# 22. One More Improvement: `next` Is Not Needed in Controllers

You might wonder:

> Why does our async handler receive `next` if our controller doesn't?

Because the wrapper itself handles it:

```ts
return (req, res, next) => {
  Promise.resolve(
    handler(req, res, next),
  ).catch(next);
};
```

Your controller only needs:

```ts
async (req, res) => {
```

This keeps the controller clean.

---

# 23. What About Express 5?

Modern Express 5 has improved Promise rejection handling for middleware and route handlers.

You may therefore see code that doesn't use a custom async wrapper.

However, we're deliberately introducing `asyncHandler` here because it gives us:

```text
consistent pattern
explicit architecture
easy migration/understanding
```

And more importantly, you'll encounter this pattern constantly in existing Express codebases.

Understanding it is valuable even when a framework can handle some of it for you.

---

# 24. Don't Overuse `try/catch`

A common beginner pattern is:

```ts
try {
  ...
} catch (error) {
  ...
}
```

everywhere.

Instead:

```text
Expected error
      ↓
AppError
      ↓
global handler

Unexpected error
      ↓
global handler
```

Use local `try/catch` when you actually need to **recover from or transform** an error.

For example:

```ts
try {
  await someExternalService();
} catch {
  return fallbackValue();
}
```

That's a legitimate reason.

But catching just to send an HTTP 500 from every controller is unnecessary.

---

# 25. A Useful Interview Question

If an interviewer asks:

> **"Why do you use an async handler in Express?"**

A good answer:

> "It wraps async route handlers and forwards rejected promises to Express's centralized error middleware, so controllers don't need repetitive try/catch blocks."

Short and technically correct.

---

# 26. Another Interview Question

> **"Why should controllers be thin?"**

Answer:

> "Controllers should mainly handle HTTP concerns. Keeping business logic in services and database access in repositories makes the code easier to test, maintain, and reuse."

That's exactly the architecture we're building.
