# Lesson 2.8 — API Versioning

Now we're moving into a topic that becomes important when your backend starts having **real users and real clients**.

The main problem API versioning solves is:

> **How can we improve our API without suddenly breaking applications that already use it?**

For your AI LMS, we'll use:

```text
/api/v1/...
```

as our starting point.

---

# 1. The Problem Without Versioning

Imagine your LMS initially has:

```http
GET /api/courses/:id
```

Response:

```json
{
  "id": "course_123",
  "title": "TypeScript Fundamentals",
  "instructor": "Rahul"
}
```

Your frontend depends on this response.

Six months later, you redesign the API:

```json
{
  "courseId": "course_123",
  "name": "TypeScript Fundamentals",
  "instructor": {
    "id": "user_123",
    "name": "Rahul"
  }
}
```

Now your old frontend expects:

```js
course.title
```

but the new API returns:

```js
course.name
```

Your frontend breaks.

---

# 2. Versioning Solves This

Instead of changing the existing API directly:

```text
/api/courses
```

we create:

```text
/api/v1/courses
```

Then later:

```text
/api/v2/courses
```

Now:

```text
Frontend v1
     ↓
/api/v1/courses
```

while:

```text
New frontend
     ↓
/api/v2/courses
```

Both can temporarily exist.

---

# 3. Our AI LMS API

We'll use:

```text
/api/v1
```

as the base path.

For example:

```text
/api/v1/auth/register
/api/v1/auth/login
/api/v1/users/me
/api/v1/courses
/api/v1/courses/:id
/api/v1/lessons
/api/v1/quizzes
/api/v1/enrollments
/api/v1/progress
```

This is a simple and practical approach.

---

# 4. Why Version the API?

There are several reasons.

### 1. Breaking changes

Example:

```text
title → name
```

### 2. Removing fields

Old:

```json
{
  "title": "...",
  "description": "...",
  "legacyField": "..."
}
```

New:

```json
{
  "title": "...",
  "description": "..."
}
```

### 3. Changing authentication

Maybe:

```text
JWT
```

becomes:

```text
OAuth / session-based authentication
```

### 4. Changing response structures

For example:

```text
course.instructor
```

becomes:

```text
course.instructor.id
course.instructor.name
```

### 5. Major business changes

Suppose your enrollment system changes significantly.

A new API version gives you room to evolve it.

---

# 5. Where Should Versioning Live?

I recommend:

```text
src/
└── routes/
    ├── v1/
    │   ├── auth.routes.ts
    │   ├── user.routes.ts
    │   ├── course.routes.ts
    │   └── index.ts
    │
    └── index.ts
```

Then:

```text
app.ts
   ↓
/api/v1
   ↓
v1 routes
```

---

# 6. Route Structure

Your `app.ts` can look like:

```ts
import v1Routes from "./routes/v1";

app.use("/api/v1", v1Routes);
```

Then:

```ts
// routes/v1/index.ts

import { Router } from "express";
import authRoutes from "../../modules/auth/auth.routes";
import courseRoutes from "../../modules/courses/course.routes";
import userRoutes from "../../modules/users/user.routes";

const router = Router();

router.use("/auth", authRoutes);
router.use("/users", userRoutes);
router.use("/courses", courseRoutes);

export default router;
```

Now:

```text
authRoutes
    ↓
/api/v1/auth

userRoutes
    ↓
/api/v1/users

courseRoutes
    ↓
/api/v1/courses
```

---

# 7. Don't Put `v1` Everywhere

Avoid this:

```text
modules/courses/
├── v1-course.controller.ts
├── v1-course.service.ts
├── v1-course.repository.ts
```

That's usually unnecessary.

Instead:

```text
routes/
└── v1/

modules/
└── courses/
    ├── course.controller.ts
    ├── course.service.ts
    ├── course.repository.ts
    └── course.schema.ts
```

The route layer decides which API version is being exposed.

---

# 8. Why?

Because your business logic might remain the same.

For example:

```text
v1 request
    ↓
Course Service
    ↓
Course Repository
```

Later:

```text
v2 request
    ↓
Course Service
    ↓
Course Repository
```

If the underlying business logic hasn't changed, there is no reason to duplicate it.

---

# 9. When Do You Actually Need V2?

This is important.

Don't create:

```text
v1
v2
v3
```

just because you can.

Create a new version when you introduce a **breaking change**.

For example:

### V1

```json
{
  "id": "123",
  "title": "React"
}
```

### V2

```json
{
  "courseId": "123",
  "name": "React"
}
```

Changing:

```text
title → name
```

is potentially breaking.

That's a good reason for V2.

---

# 10. What Is NOT a Breaking Change?

Suppose V1 returns:

```json
{
  "id": "123",
  "title": "React"
}
```

and you add:

```json
{
  "id": "123",
  "title": "React",
  "description": "Learn React"
}
```

Adding optional information can often be backward-compatible.

But be careful.

Some clients may expect an exact response shape, so API compatibility isn't always as simple as "adding a field is safe."

---

# 11. Another Example

Suppose your LMS initially returns:

```json
{
  "id": "course_123",
  "title": "Node.js",
  "lessons": 10
}
```

Later you want:

```json
{
  "id": "course_123",
  "title": "Node.js",
  "stats": {
    "lessonCount": 10,
    "studentCount": 250
  }
}
```

If you completely replace:

```text
lessons
```

with:

```text
stats.lessonCount
```

old clients may break.

You could introduce:

```text
/api/v2/courses/:id
```

---

# 12. Versioning Is Not Just URLs

There are several ways to version APIs.

### 1. URL

```text
/api/v1/courses
```

### 2. Header

```http
Accept: application/vnd.lms.v1+json
```

### 3. Query parameter

```text
/api/courses?version=1
```

For your project, I recommend:

> **URL-based versioning.**

It's simple, obvious, and easy to work with.

---

# 13. Why URL Versioning Is Good for Your LMS

When debugging, you can immediately see:

```text
GET /api/v1/courses
```

or:

```text
GET /api/v2/courses
```

Your frontend developers can easily understand it.

Your API documentation can group endpoints by version.

Your logs can show the version naturally.

And you don't need complicated content-negotiation logic.

---

# 14. API Versioning + Request IDs

Remember our previous lesson?

Now combine them.

A log might look like:

```text
INFO
requestId=req_82abc
method=GET
path=/api/v1/courses/123
status=200
duration=85ms
```

This gives you:

```text
Version
+
Endpoint
+
Request
+
Performance
```

Very useful.

---

# 15. API Versioning + Controllers

Your flow becomes:

```text
Client
  ↓
/api/v1/courses
  ↓
V1 Router
  ↓
Course Controller
  ↓
Course Service
  ↓
Course Repository
  ↓
Prisma
  ↓
PostgreSQL
```

Notice that the service doesn't care whether the request came from V1 or V2.

That's a good thing.

---

# 16. A More Advanced Scenario

Suppose V2 needs a completely different response.

You could have:

```text
/api/v1/courses/:id
        ↓
v1 controller
        ↓
course service
```

and:

```text
/api/v2/courses/:id
        ↓
v2 controller
        ↓
course service
```

The same service can return the underlying domain data.

The controllers can format it differently.

For example:

```ts
// V1
res.json({
  success: true,
  data: {
    id: course.id,
    title: course.title,
  },
});
```

V2:

```ts
res.json({
  success: true,
  data: {
    courseId: course.id,
    name: course.title,
  },
});
```

The business logic remains shared.

---

# 17. Don't Duplicate Business Logic

Bad:

```text
v1 controller
    ↓
v1 service
    ↓
v1 repository

v2 controller
    ↓
v2 service
    ↓
v2 repository
```

You could end up maintaining two copies of everything.

Instead:

```text
v1 controller ──┐
                ├──→ Course Service → Course Repository
v2 controller ──┘
```

Only duplicate what actually needs to be different.

---

# 18. Deprecation

Eventually, you may want to stop supporting V1.

For example:

```text
V1
↓
Deprecated
↓
V2 recommended
```

You can communicate this through:

```http
Deprecation: true
```

or documentation and migration notices.

The exact mechanism depends on your API strategy.

The important idea is:

> **Don't silently kill an API that clients depend on.**

---

This is important for you.

You don't need:


# 22. One More Important Idea: API Contract

API versioning becomes much more useful when you treat your API as a **contract**.

For example:

```http
POST /api/v1/courses
```

expects:

```json
{
  "title": "TypeScript",
  "description": "Learn TypeScript",
  "level": "BEGINNER"
}
```

and guarantees something like:

```json
{
  "success": true,
  "data": {
    "id": "...",
    "title": "TypeScript"
  }
}
```

Your frontend depends on this contract.

So changing the contract is a serious decision.

That's why:

```text
Validation
+
Response format
+
Versioning
+
Documentation
```

all work together.
