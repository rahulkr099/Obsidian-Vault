# Lesson 2.9 — Pagination, Filtering & Sorting

This is one of the most practical backend lessons in the whole Phase 2.

When your AI LMS has only:

```text
20 courses
```

this works:

```ts
prisma.course.findMany()
```

But imagine:

```text
100,000 courses
```

Returning everything would be a bad idea.

We need APIs that can say:

```text
Give me courses 21–40
Only beginner courses
Sort newest first
Search for "TypeScript"
```

That's where **pagination, filtering, sorting, and searching** come in.

---

# 1. The Problem

Suppose we have:

```http
GET /api/v1/courses
```

A naive implementation:

```ts
const courses = await prisma.course.findMany();
```

Imagine the database returns:

```text
100,000 records
```

Problems:

```text
Huge database response
       ↓
Huge JSON response
       ↓
More network usage
       ↓
More server memory
       ↓
Slower frontend
       ↓
Poor user experience
```

Instead, we want:

```http
GET /api/v1/courses?page=1&limit=20
```

The server returns only 20 courses.

---

# 2. The Four Concepts

We'll learn four related concepts:

```text
Pagination
Filtering
Sorting
Searching
```

### Pagination

> Which subset of records should I return?

### Filtering

> Which records should match?

### Sorting

> In what order should I return them?

### Searching

> Which records match a text query?

---

# 3. Pagination

The most common API style is:

```text
?page=1&limit=20
```

Meaning:

```text
page 1
20 items per page
```

Then:

```text
?page=2&limit=20
```

returns the next 20.

Conceptually:

```text
Database
────────────────────────────────────────

1  2  3  4  5 ... 20
                     → Page 1

21 22 23 ... 40
                     → Page 2

41 42 43 ... 60
                     → Page 3
```

---

# 4. Offset Pagination

With PostgreSQL/Prisma, a simple implementation uses:

```text
skip
take
```

For:

```text
page = 2
limit = 20
```

calculate:

```ts
skip = (page - 1) * limit;
```

So:

```ts
skip = (2 - 1) * 20;
```

which gives:

```text
skip = 20
```

Then:

```ts
prisma.course.findMany({
  skip: 20,
  take: 20,
});
```

---

# 5. Basic Repository

Your repository might contain:

```ts
export async function findMany(options: {
  skip: number;
  limit: number;
}) {
  return prisma.course.findMany({
    skip: options.skip,
    take: options.limit,
  });
}
```

But we can make this much more powerful.

---

# 6. Query Parameters

A request:

```http
GET /api/v1/courses?page=2&limit=20
```

gives Express:

```ts
req.query.page
req.query.limit
```

Important:

> Query parameters arrive as strings.

So:

```ts
req.query.page
```

might be:

```text
"2"
```

not:

```text
2
```

This is another reason we need validation.

---

# 7. Validate Query Parameters

We can use Zod.

```ts
import { z } from "zod";

export const courseListSchema = z.object({
  page: z.coerce.number().int().min(1).default(1),

  limit: z.coerce.number().int().min(1).max(100).default(20),
});
```

The important part is:

```ts
z.coerce.number()
```

It converts:

```text
"2"
```

into:

```text
2
```

---

# 8. Why Limit Maximum Matters

Never allow:

```http
?page=1&limit=100000000
```

Otherwise someone could request an enormous amount of data.

Use:

```ts
.max(100)
```

for example.

Then:

```text
limit=20     ✓
limit=50     ✓
limit=100    ✓
limit=500    ✗
```

The exact maximum depends on your application.

For your LMS:

```text
20–50
```

is a sensible starting range for normal listing APIs.

---

# 9. Pagination Metadata

Don't return only:

```json
{
  "success": true,
  "data": [...]
}
```

The frontend needs to know:

```text
Which page?
How many items?
Are there more?
How many total?
```

A better response:

```json
{
  "success": true,
  "data": [],
  "meta": {
    "page": 2,
    "limit": 20,
    "total": 157,
    "totalPages": 8
  }
}
```

Now the frontend can easily create:

```text
← Previous   1  2  3  4  5  ...   Next →
```

---

# 10. Calculate Total Pages

Suppose:

```text
total = 157
limit = 20
```

Then:

```ts
const totalPages = Math.ceil(total / limit);
```

Result:

```text
8
```

because:

```text
157 / 20 = 7.85
```

and we round up.

---

# 11. The Important Prisma Trick

We need two operations:

```text
Get current page
+
Get total count
```

We could do:

```ts
const courses = await prisma.course.findMany(...);

const total = await prisma.course.count(...);
```

That's fine.

But Prisma also allows:

```ts
const [courses, total] = await Promise.all([
  prisma.course.findMany(...),
  prisma.course.count(...),
]);
```

This allows both operations to run concurrently.

---

# 12. Service Layer

The service can calculate pagination.

```ts
export async function getCourses(page: number, limit: number) {
  const skip = (page - 1) * limit;

  const [courses, total] =
    await courseRepository.findManyPaginated({
      skip,
      limit,
    });

  return {
    courses,
    meta: {
      page,
      limit,
      total,
      totalPages: Math.ceil(total / limit),
    },
  };
}
```

Notice:

> Pagination calculation is application logic, so the service is a good place for it.

The repository performs the database operations.

# 13. Filtering

Now suppose our courses have:

```text
BEGINNER
INTERMEDIATE
ADVANCED
```

We want:

```http
GET /api/v1/courses?level=BEGINNER
```

The repository can translate that into:

```ts
where: {
  level: "BEGINNER",
}
```

---

# 14. Combining Pagination + Filtering

Now:

```http
GET /api/v1/courses?level=BEGINNER&page=2&limit=20
```

means:

```text
Filter:
level = BEGINNER

Pagination:
page = 2
limit = 20
```

Prisma:

```ts
prisma.course.findMany({
  where: {
    level: "BEGINNER",
  },
  skip: 20,
  take: 20,
});
```

And the count must use the **same filter**:

```ts
prisma.course.count({
  where: {
    level: "BEGINNER",
  },
});
```

Otherwise your pagination metadata becomes incorrect.

---

# 15. Build a Query Schema

We can make the query schema:

```ts
import { z } from "zod";

export const courseListSchema = z.object({
  page: z.coerce
    .number()
    .int()
    .min(1)
    .default(1),

  limit: z.coerce
    .number()
    .int()
    .min(1)
    .max(100)
    .default(20),

  level: z
    .enum(["BEGINNER", "INTERMEDIATE", "ADVANCED"])
    .optional(),
});
```

Now:

```http
GET /courses?level=BEGINNER
```

is valid.

But:

```http
GET /courses?level=whatever
```

is rejected.

---

# 16. Sorting

Suppose the user wants:

```text
Newest courses first
```

We could provide:

```http
GET /api/v1/courses?sort=createdAt
```

or:

```http
GET /api/v1/courses?sort=-createdAt
```

A common convention is:

```text
createdAt
```

→ ascending

and:

```text
-createdAt
```

→ descending.

But **never directly put user input into Prisma's `orderBy` without validation/allowlisting**.

---

# 17. Allowlist Sort Fields

Create:

```ts
const allowedSortFields = [
  "createdAt",
  "title",
  "updatedAt",
];
```

Then parse:

```ts
const sort = "-createdAt";
```

into:

```text
field = createdAt
direction = desc
```

and:

```ts
orderBy: {
  createdAt: "desc",
}
```

---

# 18. Why Allowlisting Is Important

Don't blindly do something like:

```ts
orderBy: {
  [req.query.sort]: "desc",
}
```

Instead, decide what your API supports.

For example:

```text
createdAt ✓
updatedAt ✓
title     ✓

password  ✗
internalField ✗
randomValue ✗
```

This gives you a predictable API.

---

# 19. Searching

Now the interesting part.

Suppose the user searches:

```http
GET /api/v1/courses?search=typescript
```

We want to find courses where:

```text
title contains "typescript"
OR
description contains "typescript"
```

With Prisma:

```ts
where: {
  OR: [
    {
      title: {
        contains: search,
        mode: "insensitive",
      },
    },
    {
      description: {
        contains: search,
        mode: "insensitive",
      },
    },
  ],
}
```

Now:

```text
TypeScript Fundamentals
Advanced TypeScript
TypeScript with Node.js
```

could all match.

---

# 20. Combine Everything

Now we can build:

```http
GET /api/v1/courses
  ?page=2
  &limit=20
  &level=BEGINNER
  &search=typescript
  &sort=-createdAt
```

This means:

```text
Search:
typescript

Filter:
BEGINNER

Sort:
newest first

Pagination:
page 2
20 records
```

That's already a **real-world API**.

---

# 21. The Repository

A repository can accept a query object:

```ts
type CourseListOptions = {
  skip: number;
  limit: number;
  level?: "BEGINNER" | "INTERMEDIATE" | "ADVANCED";
  search?: string;
  sortBy: "createdAt" | "updatedAt" | "title";
  sortOrder: "asc" | "desc";
};
```

Then:

```ts
export async function findMany(options: CourseListOptions) {
  const where = {
    ...(options.level && {
      level: options.level,
    }),

    ...(options.search && {
      OR: [
        {
          title: {
            contains: options.search,
            mode: "insensitive",
          },
        },
        {
          description: {
            contains: options.search,
            mode: "insensitive",
          },
        },
      ],
    }),
  };

  return Promise.all([
    prisma.course.findMany({
      where,
      skip: options.skip,
      take: options.limit,
      orderBy: {
        [options.sortBy]: options.sortOrder,
      },
    }),

    prisma.course.count({
      where,
    }),
  ]);
}
```

This is a good example of the repository doing **database work**, while the service decides how to interpret the API query.

---

# 22. Service

The service can turn the API query into repository options:

```ts
export async function getCourses(query: CourseListQuery) {
  const page = query.page;
  const limit = query.limit;

  const skip = (page - 1) * limit;

  const sort = query.sort ?? "-createdAt";

  const sortOrder = sort.startsWith("-")
    ? "desc"
    : "asc";

  const sortBy = sort.replace("-", "");

  const [courses, total] =
    await courseRepository.findMany({
      skip,
      limit,
      level: query.level,
      search: query.search,
      sortBy,
      sortOrder,
    });

  return {
    data: courses,
    meta: {
      page,
      limit,
      total,
      totalPages: Math.ceil(total / limit),
    },
  };
}
```

But remember: **validate `sortBy` before it reaches the repository**.

# 26. Pagination Has a Hidden Problem

Offset pagination:

```text
page=10000
```

can become expensive for huge datasets.

Imagine:

```text
10 million records
```

and:

```text
OFFSET 9999800
LIMIT 20
```

The database may need to walk through a large number of rows before reaching the requested records.

For your current LMS project, offset pagination is perfectly reasonable.

But there is another technique.

---

# 27. Cursor Pagination

Instead of:

```text
page=100
```

you use something like:

```text
cursor=course_abc123
```

Conceptually:

```text
Current position
      ↓
course_abc123
      ↓
Give me the next 20
```

Example:

```http
GET /api/v1/courses?limit=20&cursor=abc123
```

This is called **cursor-based pagination**.

It can perform much better for very large datasets.

---

# 28. Offset vs Cursor

|Offset|Cursor|
|---|---|
|`page=2`|`cursor=abc123`|
|Easy to understand|More complex|
|Great for admin panels|Great for large feeds|
|Easy numbered pages|Usually next/previous|
|Can slow on huge offsets|Better for large datasets|
|Good for LMS dashboards|Good for activity feeds|

For your AI LMS:

### Use offset pagination for:

```text
Course listing
Admin tables
User management
Quiz management
```

### Consider cursor pagination for:

```text
Activity feeds
Notifications
Discussion feeds
Large progress/event streams
```

Don't implement cursor pagination everywhere just because it's "more advanced."

---

# 29. Pagination + Database Indexes

This is another important connection.

Suppose we frequently filter:

```text
level
```

and sort:

```text
createdAt
```

Your database may benefit from indexes.

For example, in Prisma:

```prisma
model Course {
  id           String   @id @default(cuid())
  title        String
  level        CourseLevel
  createdAt    DateTime @default(now())

  @@index([level])
  @@index([createdAt])
}
```

Indexes are a database optimization topic we'll study more deeply later.

The key idea:

> **Pagination doesn't magically make an inefficient query fast.**

You still need good database design.

---

# 30. Don't Overload One Endpoint

You might eventually be tempted to support:

```text
page
limit
search
level
category
instructor
status
minPrice
maxPrice
sort
createdAfter
createdBefore
...
```

all inside one endpoint.

That's okay if the endpoint remains understandable.

But if the query becomes extremely complicated, consider whether you actually need:

```text
Advanced search API
```

or a dedicated search engine.

For your LMS:

```text
PostgreSQL
+
proper indexes
```

will be enough for a long time.

You don't need Elasticsearch/OpenSearch on day one.

---

# 31. Important Security Rule

Never trust:

```text
page
limit
sort
filter
search
```

just because they're query parameters.

Validate them.

For example:

```text
page < 1             → reject
limit > 100          → reject
invalid level        → reject
unknown sort field   → reject
search too long      → reject
```

A good query schema is part of your API security.

Your listing request now looks like:

```text
GET /api/v1/courses
       │
       ↓
Query Validation
       │
       ↓
Controller
       │
       ↓
Service
       │
       ├── page
       ├── limit
       ├── filters
       ├── search
       └── sorting
       │

       │
       ├── WHERE
       ├── ORDER BY

       └── LIMIT
       │
       ↓

```

This is a very common backend pattern.
