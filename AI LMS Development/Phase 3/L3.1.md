# 3.1 — Relational Database Thinking

Before PostgreSQL or Prisma, we need to understand **relational thinking**.

Suppose our AI LMS has users.

A beginner might think:

```text
User
 ├── name
 ├── email
 ├── course
 ├── lessons
 ├── quiz
 └── progress
```

But a relational database doesn't normally store everything inside one giant record.

Instead, we break the system into meaningful entities.

For example:

```text
users
courses
lessons
enrollments
progress
quizzes
questions
answers
```

Then we define how these entities are connected.

For example:

```text
User
 │
 ├── Enrollment ─── Course
 │                    │
 │                    └── Lesson
 │
 └── Progress ─────── Lesson
```

This is the fundamental idea of relational database design.

---

# 1. What is a Relation?

In relational databases, a **relation is essentially a table**.

For example:

```text
users
------------------------------------------------
id | name       | email
------------------------------------------------
1  | Rahul      | rahul@example.com
2  | Aman       | aman@example.com
3  | Priya      | priya@example.com
```

Each row represents one entity.

Each column represents an attribute.

So:

```text
Table  → users

Row    → one user

Column → property of the user
```

---

# 2. Think in Entities

When designing a database, don't immediately think:

> “What tables should I create?”

Instead ask:

> **“What things exist in my system?”**

For an LMS:

```text
User
Course
Lesson
Enrollment
Quiz
Question
Answer
Submission
Progress
AI Conversation
```

These are **entities**.

Then ask what information each entity needs.

### User

```text
User
├── id
├── name
├── email
├── passwordHash
└── createdAt
```

### Course

```text
Course
├── id
├── title
├── description
├── instructorId
└── createdAt
```

### Lesson

```text
Lesson
├── id
├── courseId
├── title
├── content
└── order
```

Notice something important:

```text
Lesson
   │
   └── courseId
```

That `courseId` tells us which course the lesson belongs to.

We'll study this properly in **3.3 and 3.4**.

---

# 3. Why Not Put Everything in One Table?

Imagine this:

```text
users

id | name | email | course | lesson | quiz | progress
```

Suppose Rahul has three courses.

We might end up with:

```text
1 | Rahul | rahul@example.com | React | Hooks | Quiz 1 | 80%
1 | Rahul | rahul@example.com | React | Router | Quiz 2 | 70%
1 | Rahul | rahul@example.com | Node  | Express | Quiz 3 | 90%
```

Now we have duplicated:

```text
Rahul
rahul@example.com
```

And many other problems appear.

For example:

### Problem 1 — Duplicate data

The same user information appears repeatedly.

### Problem 2 — Updating data

If Rahul changes his email:

```text
rahul@example.com
```

we may need to update many rows.

### Problem 3 — Deleting data

If we delete one course, we might accidentally lose unrelated information.

### Problem 4 — Difficult queries

Questions such as:

> “Give me all courses Rahul is enrolled in.”

become unnecessarily complicated.

---

# 4. Normalize the Data

Instead, we separate the entities.

```text
users
```

```text
courses
```

```text
lessons
```

```text
enrollments
```

For example:

### users

```text
id | name  | email
---|-------|-------------------
1  | Rahul | rahul@example.com
```

### courses

```text
id | title
---|----------------
1  | React Mastery
2  | Node.js Backend
```

### enrollments

```text
id | userId | courseId
---|--------|---------
1  | 1      | 1
2  | 1      | 2
```

Now the database says:

```text
Rahul
  │
  ├── React Mastery
  │
  └── Node.js Backend
```

This is much cleaner.

---

# 5. The Most Important Question

Whenever you design a database, ask:

> **What does one row represent?**

For example:

```text
users
```

One row represents:

```text
ONE USER
```

For:

```text
courses
```

One row represents:

```text
ONE COURSE
```

For:

```text
enrollments
```

One row represents:

```text
ONE USER ENROLLING IN ONE COURSE
```

This simple question prevents many database design mistakes.

---

# 6. Attributes vs Entities

This is another important distinction.

Suppose we have:

```text
User
```

These are attributes:

```text
name
email
passwordHash
createdAt
```

But:

```text
Course
Lesson
Quiz
```

are separate entities.

Why?

Because they have their **own identity and lifecycle**.

A course can exist independently of a particular user.

A lesson can exist independently of a particular enrollment.

Therefore:

```text
User
Course
Lesson
```

should generally be separate tables.

---

# 7. Relationships Are the Heart of Relational Databases

Now consider:

```text
User ─── Course
```

How are they connected?

A user can enroll in multiple courses.

A course can have multiple users.

Therefore:

```text
User ←→ Course
```

is a:

> **Many-to-Many relationship**

We usually represent this using an intermediate table:

```text
enrollments
```

So:

```text
User
 │
 ├──── Enrollment ──── Course
 │
 └──── Enrollment ──── Course
```

We'll spend an entire lesson on relationships.

---

# 8. Database Design Starts With Business Rules

This is one of the most valuable backend engineering concepts.

Don't start with:

```text
What Prisma syntax should I write?
```

Start with:

```text
What rules does my application have?
```

For example:

### LMS rule

> A student can enroll in many courses.

Database implication:

```text
User → Enrollment → Course
```

### LMS rule

> A course contains many lessons.

Database implication:

```text
Course → Lessons
```

### LMS rule

> A lesson belongs to exactly one course.

Database implication:

```text
Lesson → Course
```

### LMS rule

> A student can have progress for each lesson.

Database implication:

```text
User → Progress ← Lesson
```

This is **database modeling from business requirements**.

That's the skill we want to develop.

---

# 9. Relational Thinking Example

Imagine this requirement:

> Students can enroll in courses. Each course contains multiple lessons. Students can complete lessons and attempt quizzes.

Don't immediately write Prisma.

First extract the entities:

```text
User
Course
Lesson
Enrollment
Progress
Quiz
QuizAttempt
```

Then relationships:

```text
User
 │
 ├──── Enrollment ──── Course
 │                       │
 │                       └──── Lesson
 │
 └──── Progress ──────── Lesson
 │
 └──── QuizAttempt ───── Quiz
```

Only after this should we start thinking about:

```text
PostgreSQL
        ↓
tables
        ↓
keys
        ↓
constraints
        ↓
indexes
        ↓
Prisma schema
```

That's the workflow I want you to follow throughout this phase.

---

# 10. A Mental Model You Should Remember

When designing any backend database, use this sequence:

```text
Requirements
     ↓
Entities
     ↓
Attributes
     ↓
Relationships
     ↓
Keys
     ↓
Constraints
     ↓
Indexes
     ↓
Tables
     ↓
Queries
```

For example:

```text
"Learners can enroll in courses"
             ↓
          User
          Course
             ↓
       Enrollment
             ↓
       Foreign Keys
             ↓
      Database Tables
```

This is much more powerful than memorizing Prisma syntax.

# 12. Your First Database Design Rule

Remember this:

> **Don't design tables from the UI. Design them from the domain.**

For example, your UI might have:

```text
Dashboard
Course Page
Lesson Page
Quiz Page
AI Tutor
Profile
```

These aren't necessarily database tables.

Instead:

```text
Dashboard
    ↓
combines data from
    ↓
User
Enrollment
Progress
Course
```

Likewise:

```text
Course Page
    ↓
Course
Module
Lesson
Enrollment
Progress
```

This distinction is extremely important for backend engineering.

# 13. Interview Perspective

If an interviewer asks:

> “Design a database for an LMS.”

Don't immediately answer:

```text
I'll create a User table and Course table...
```

Start by asking:

```text
Who are the users?

What can they do?

What entities exist?

What relationships exist?

What rules must the database enforce?

What queries will be frequent?
```

Then design the schema.

That's the mindset we're building in Phase 3.
