# Lesson 3.6 — Prisma Migrations

Now we move from:

```text
schema.prisma
```

to:

```text
actual PostgreSQL database
```

This is where database engineering becomes much more practical.

A migration is basically a **versioned change to your database structure**.

Think of it like Git, but for your database schema.

---

# 1. The Problem Migrations Solve

Imagine your first database has:

```text
users
courses
```

Later, you decide:

> "I need lessons."

You add:

```text
lessons
```

Then:

> "Courses need a publication status."

You add:

```text
status
```

Then:

> "Users need a role."

You add:

```text
role
```

Your database changes over time:

```text
Database v1
    ↓
Database v2
    ↓
Database v3
    ↓
Database v4
```

How do you reliably track those changes?

**Migrations.**

---

# 2. What Is a Migration?

A migration is a recorded change to the database schema.

For example:

```text
Initial database
      ↓
Create users
      ↓
Migration 001
      ↓
Create courses
      ↓
Migration 002
      ↓
Create lessons
      ↓
Migration 003
```

You can think of migrations as:

```text
Git commits
     ↓
code history

Database migrations
     ↓
database schema history
```

---

# 3. Why Not Just Modify PostgreSQL Manually?

Suppose you run:

```sql
ALTER TABLE users
ADD COLUMN role TEXT;
```

Your local database now has:

```text
users
├── id
├── name
├── email
└── role
```

But your teammate's database might still have:

```text
users
├── id
├── name
└── email
```

Now the databases are different.

Even worse, production might have a third version.

Migrations solve this by creating a **repeatable history of schema changes**.

---

# 4. Prisma's Migration Workflow

The typical workflow is:

```text
1. Change schema.prisma
          ↓
2. Generate migration
          ↓
3. Review migration
          ↓
4. Apply migration
          ↓
5. Commit migration to Git
```

For development:

```bash
npx prisma migrate dev --name init
```

This is one of the commands you'll use frequently.

---

# 5. Initial Prisma Schema

Suppose we start with:

```prisma
model User {
  id        String   @id @default(uuid())
  name      String
  email     String   @unique
  createdAt DateTime @default(now())
}
```

Your PostgreSQL database doesn't necessarily have this table yet.

Run:

```bash
npx prisma migrate dev --name init
```

Prisma will create a migration.

Conceptually:

```text
schema.prisma
      ↓
Prisma compares desired schema
      ↓
Generate SQL
      ↓
Apply SQL
      ↓
PostgreSQL
```

---

# 6. What Does the Migration Look Like?

Prisma creates something similar to:

```text
prisma/
└── migrations/
    └── 20260814000000_init/
        └── migration.sql
```

The exact timestamp/name will differ.

Inside:

```text
migration.sql
```

you'll find SQL generated for your schema.

For example, conceptually:

```sql
CREATE TABLE "User" (
    "id" TEXT NOT NULL,
    "name" TEXT NOT NULL,
    "email" TEXT NOT NULL,
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "User_pkey" PRIMARY KEY ("id")
);

CREATE UNIQUE INDEX "User_email_key"
ON "User"("email");
```

This is important.

Prisma isn't magically creating tables.

It generates database instructions.

---

# 7. Prisma Schema vs Migration

These are different things.

### `schema.prisma`

Describes:

> **What the database should look like.**

### Migration

Describes:

> **How to change the database from one state to another.**

Think:

```text
schema.prisma
     ↓
Desired state

migration
     ↓
Transition to desired state
```

This distinction is extremely important.

---

# 8. Example: Adding a Course

Initially:

```prisma
model User {
  id    String @id @default(uuid())
  name  String
  email String @unique
}
```

Then you add:

```prisma
model Course {
  id    String @id @default(uuid())
  title String
}
```

Now run:

```bash
npx prisma migrate dev --name add_courses
```

Prisma generates a migration that essentially says:

```sql
CREATE TABLE "Course" (
    "id" TEXT NOT NULL,
    "title" TEXT NOT NULL,

    CONSTRAINT "Course_pkey" PRIMARY KEY ("id")
);
```

Now the database has:

```text
User
Course
```

---

# 9. Adding a Column

Suppose you already have:

```prisma
model Course {
  id    String @id @default(uuid())
  title String
}
```

Now you add:

```prisma
description String?
```

Then:

```bash
npx prisma migrate dev --name add_course_description
```

The migration may generate SQL conceptually similar to:

```sql
ALTER TABLE "Course"
ADD COLUMN "description" TEXT;
```

Now your database has:

```text
courses
├── id
├── title
└── description
```

---

# 10. Migration Names Matter

Use meaningful names.

Good:

```text
init
add_courses
add_course_description
add_enrollment
add_lesson_progress
add_user_role
add_course_indexes
```

Bad:

```text
change
update
test
fix
new
stuff
abc
```

Six months later:

```text
20260814_add_enrollment
```

tells you something useful.

Whereas:

```text
20260814_update
```

doesn't.

---

# 11. Migration History

Your project may eventually look like:

```text
prisma/
├── schema.prisma
└── migrations/
    ├── 20260814000100_init/
    │   └── migration.sql
    │
    ├── 20260814000200_add_courses/
    │   └── migration.sql
    │
    ├── 20260814000300_add_lessons/
    │   └── migration.sql
    │
    └── 20260814000400_add_enrollment/
        └── migration.sql
```

This gives you a history:

```text
Initial schema
      ↓
Users
      ↓
Courses
      ↓
Lessons
      ↓
Enrollments
```

That's valuable for teams and production deployments.

---

# 12. Migrations Should Be Committed to Git

This is extremely important.

You should commit:

```text
prisma/schema.prisma
prisma/migrations/
```

to Git.

For example:

```bash
git add prisma/schema.prisma prisma/migrations
git commit -m "add course and lesson schema"
```

Why?

Because your teammates need the same database changes.

---

# 13. What Should NOT Go Into Git?

Never commit your real database credentials.

For example:

```env
DATABASE_URL="postgresql://username:password@..."
```

should generally be kept out of Git.

Use:

```text
.env
```

and add it to:

```text
.gitignore
```

Instead, commit something like:

```text
.env.example
```

containing:

```env
DATABASE_URL="postgresql://..."
```

with placeholder/example values.

---

# 14. `migrate dev`

This is your primary **development** migration command.

```bash
npx prisma migrate dev --name add_courses
```

It is designed for development.

Conceptually it:

```text
1. Reads schema.prisma
2. Detects schema changes
3. Generates migration
4. Applies migration
5. Updates migration history
6. Regenerates Prisma Client when needed
```

It's extremely convenient during development.

---

# 15. `migrate deploy`

Production is different.

You don't want your production server casually creating new migrations.

Instead, you commit migrations to Git and deploy them.

Then production runs:

```bash
npx prisma migrate deploy
```

Conceptually:

```text
Developer
   ↓
schema.prisma
   ↓
migrate dev
   ↓
migration files
   ↓
Git
   ↓
CI/CD
   ↓
Production
   ↓
migrate deploy
   ↓
PostgreSQL
```

This is a much safer production workflow.

---

# 16. Development vs Production

Remember this table:

|Environment|Command|
|---|---|
|Development|`prisma migrate dev`|
|Production/CI|`prisma migrate deploy`|

Don't casually use:

```bash
prisma migrate dev
```

against production.

That's not the workflow we want.

---

# 17. `prisma db push`

You may also encounter:

```bash
npx prisma db push
```

This synchronizes the database with your Prisma schema **without creating migration files**.

It can be useful for:

- prototypes
    
- quick experiments
    
- local throwaway databases
    

But don't confuse it with migration-based development.

Think:

```text
migrate dev
→ schema changes + migration history

db push
→ synchronize database directly
```

For your serious AI LMS project, we'll primarily use migrations.

---

# 18. Why `db push` Isn't Our Main Workflow

Imagine:

```text
schema.prisma
      ↓
db push
      ↓
Database changed
```

But:

```text
What exact change happened?
```

You don't have a normal migration history describing the change.

With migrations:

```text
schema change
      ↓
migration.sql
      ↓
Git
      ↓
team
      ↓
production
```

Much better for a real application.

---

# 19. What Happens When You Change Existing Data?

This is where migrations become more serious.

Suppose your database contains:

```text
users

id | name
---|------
1  | Rahul
2  | Aman
3  | Priya
```

Now you add:

```prisma
role String
```

But `role` is required.

Existing rows don't have a role.

What should PostgreSQL do?

You cannot blindly add a required column without considering existing data.

This is a **migration design problem**.

---

# 20. Safe Schema Evolution

Suppose you want:

```text
role
```

with:

```text
STUDENT
INSTRUCTOR
ADMIN
```

A safer strategy might be:

### Step 1

Add it as nullable or with a safe default.

```text
role nullable
```

### Step 2

Backfill existing users.

```text
Rahul → STUDENT
Aman  → STUDENT
Priya → STUDENT
```

### Step 3

Make it required if appropriate.

```text
role NOT NULL
```

This kind of staged migration becomes extremely important in production systems.

---

# 21. Why Production Migrations Are Harder

Imagine your AI LMS has:

```text
1 million users
500,000 enrollments
10 million lesson progress records
```

You can't think:

> "I'll just change the schema."

A schema change may involve:

```text
locks
data migration
downtime
query performance
backward compatibility
deployment order
rollback strategy
```

That's why database migrations are a serious backend-engineering skill.

---

# 22. Migration Files Are History

Here's an important principle:

> **Don't edit old migrations after they've been applied to shared environments.**

Suppose:

```text
001_init
002_add_courses
003_add_lessons
```

has already been deployed.

Don't open:

```text
002_add_courses/migration.sql
```

and rewrite history.

Instead create:

```text
004_change_courses
```

This preserves the migration history.

Think of it exactly like Git history.

You generally don't rewrite shared history just because you changed your mind.

---

# 23. Migration Rollback

A common beginner assumption is:

> "Every migration should have an automatic undo."

Not necessarily.

Prisma migrations are primarily **forward migrations**.

If you need to undo a schema change, you generally create a new migration that reverses the desired change rather than relying on a magical rollback button.

For example:

```text
001 → create courses
002 → add description
003 → remove description
```

rather than manually rewriting:

```text
002
```

after it has been deployed.

---

# 24. Migration + Application Deployment

Here's an important production concept.

Suppose version 1 of your application expects:

```text
users
├── id
├── email
```

You want version 2:

```text
users
├── id
├── email
└── role
```

A dangerous deployment might be:

```text
Deploy application
       ↓
Application immediately expects role
       ↓
Database doesn't have role
       ↓
💥
```

Instead:

```text
Migration
   ↓
Database supports new structure
   ↓
Application deployment
   ↓
Application uses new structure
```

For more complex changes, you often need a **backward-compatible transition** where both old and new application versions can work temporarily.

This is a very valuable production concept.

# 25. Migration Status

Prisma provides commands to inspect migration state.

For example:

```bash
npx prisma migrate status
```

This helps identify whether:

```text
local schema
database
migration history
```

are in sync.

When debugging database problems, this command can be useful.

---

# 26. Resetting Development Database

During development, you may sometimes want to completely rebuild your database.

Prisma provides:

```bash
npx prisma migrate reset
```

This is destructive.

Conceptually:

```text
DROP data
   ↓
Reapply migrations
   ↓
Fresh database
```

So be careful.

Never casually run this against a database containing data you care about.

For local development, however, it can be very useful.

# 28. Review Generated SQL

This is something I strongly recommend for you.

Don't treat Prisma as:

> "I don't need to know SQL anymore."

After generating a migration, open:

```text
prisma/migrations/.../migration.sql
```

Read it.

For example:

```sql
CREATE TABLE "Lesson" (
    "id" TEXT NOT NULL,
    "courseId" TEXT NOT NULL,
    "title" TEXT NOT NULL,

    CONSTRAINT "Lesson_pkey" PRIMARY KEY ("id")
);
```

Ask yourself:

```text
What table is being created?

What is the primary key?

Which column is required?

Where is the foreign key?

What indexes were created?

What happens when the referenced row is deleted?
```

This habit will make you much stronger at backend engineering.

---

# 29. Migration Problems You Should Learn to Recognize

### Problem 1 — Migration drift

Your database doesn't match your migration history.

```text
schema
  ≠
database
```

### Problem 2 — Failed migration

A migration starts but fails halfway or cannot complete successfully.

### Problem 3 — Data migration

A schema change requires modifying existing records.

### Problem 4 — Dangerous migration

A seemingly simple change could lock or rewrite a large table.

### Problem 5 — Application/schema mismatch

The application expects a schema that production doesn't have yet.

These are real backend engineering problems.

---

# 30. Schema Migration vs Data Migration

This distinction is important.

### Schema migration

Changes database structure:

```text
Add table
Add column
Add index
Add constraint
Change relationship
```

### Data migration

Changes existing data:

```text
Move old values
Normalize existing records
Backfill new columns
Convert old formats
```

Sometimes one migration involves both.

For example:

```text
Add role column
      ↓
Populate existing users
      ↓
Add NOT NULL constraint
```

That's both schema and data work.

# 31. Migrations in a Team

Imagine you and another developer work on the AI LMS.

You create:

```text
add_courses
```

Your teammate creates:

```text
add_user_profile
```

Both migration histories are committed to Git.

When the project is deployed, the migration system applies the required migrations in order.

This is much safer than:

> "Hey, I changed the production database manually. Make the same change on your machine."

That doesn't scale.
