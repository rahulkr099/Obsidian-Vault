# Lesson 3.9 — PostgreSQL Constraints

This lesson is about **protecting your data at the database level**.

So far, we've learned:

```text
Schema
Keys
Relationships
Indexes
Transactions
```

Now we're going to make PostgreSQL enforce rules such as:

```text
"Email cannot be duplicated."
"Course title cannot be NULL."
"Progress must be between 0 and 100."
"This lesson must belong to an existing course."
```

These rules are called **constraints**.

---

# 1. What Is a Constraint?

A constraint is a rule enforced by the database.

Think:

```text
Application
    ↓
"Please store this data."
    ↓
PostgreSQL
    ↓
Does it obey the rules?
    ↓
YES → store it
NO  → reject it
```

For example:

```sql
email TEXT UNIQUE NOT NULL
```

means:

```text
email
 ├── cannot be NULL
 └── cannot be duplicated
```

---

# 2. Why Do We Need Database Constraints?

You might think:

> "My backend already validates the data."

That's good—but it's not enough.

Imagine your API validates:

```text
progress = 0–100
```

But another script directly accesses PostgreSQL and executes:

```sql
INSERT INTO lesson_progress (progress)
VALUES (500);
```

Without a database constraint:

```text
500
```

could be stored.

Now your database contains invalid data.

Therefore:

```text
Frontend validation
        +
Backend validation
        +
Database constraints
```

gives you stronger protection.

---

# 3. The Main Constraints

The important PostgreSQL constraints you'll use are:

```text
PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
DEFAULT
```

We've already seen some of these.

Now we'll put them together.

---

# 4. `NOT NULL`

`NOT NULL` means:

> This column must have a value.

Example:

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL
);
```

This is invalid:

```sql
INSERT INTO users (id, name)
VALUES ('...', 'Rahul');
```

because:

```text
email
```

is required.

PostgreSQL rejects the insert.

---

# 5. Prisma `?` and `NOT NULL`

Remember:

```prisma
name String
```

means the field is required.

Conceptually:

```text
name → NOT NULL
```

While:

```prisma
bio String?
```

means:

```text
bio → nullable
```

So:

```prisma
model User {
  id   String @id @default(uuid())
  name String
  bio  String?
}
```

roughly means:

```text
id     NOT NULL
name   NOT NULL
bio    nullable
```

---

# 6. `PRIMARY KEY`

We've already learned this.

A primary key:

```text
identifies each row uniquely
```

Example:

```sql
id UUID PRIMARY KEY
```

It gives us:

```text
UNIQUE
+
NOT NULL
+
row identity
```

So this:

```text
id = NULL
```

is invalid.

And:

```text
id = same value as another row
```

is invalid.

---

# 7. `UNIQUE`

`UNIQUE` means:

> No two rows can have the same value in this column or combination.

Example:

```sql
email TEXT UNIQUE
```

This is valid:

```text
rahul@example.com
aman@example.com
```

This is invalid:

```text
rahul@example.com
rahul@example.com
```

---

# 8. Why `UNIQUE` Is Important for Authentication

Imagine your users table:

```text
users

id | email
---|--------------------
1  | rahul@example.com
2  | rahul@example.com
```

Now:

```text
Which Rahul account should login use?
```

That's a data-integrity problem.

So:

```prisma
email String @unique
```

is very important.

The database itself guarantees:

```text
one email → one user
```

assuming that's the business rule you've chosen.

---

# 9. `FOREIGN KEY`

A foreign key guarantees that a relationship points to an existing record.

Example:

```sql
CREATE TABLE lessons (
    id UUID PRIMARY KEY,
    course_id UUID NOT NULL,

    FOREIGN KEY (course_id)
        REFERENCES courses(id)
);
```

Now:

```text
course_id = existing course
```

is valid.

But:

```text
course_id = non-existent course
```

is rejected.

This protects **referential integrity**.

---

# 10. `CHECK`

This is one of the most useful constraints.

`CHECK` lets you define a condition.

For example:

```sql
progress INTEGER CHECK (progress >= 0 AND progress <= 100)
```

Now PostgreSQL rejects:

```text
-10
```

and:

```text
150
```

but accepts:

```text
0
50
100
```

---

# 11. AI LMS Progress Example

Suppose:

```text
lesson_progress
```

contains:

```text
progress
```

Your application expects:

```text
0–100
```

Don't rely only on TypeScript:

```ts
if (progress < 0 || progress > 100) {
  throw new Error("Invalid progress");
}
```

Also protect the database:

```sql
progress INTEGER NOT NULL
    CHECK (progress >= 0 AND progress <= 100)
```

Now even if another application tries:

```sql
INSERT INTO lesson_progress (progress)
VALUES (999);
```

PostgreSQL says:

```text
❌ CHECK constraint violated
```

---

# 12. Prisma `@@check`

Depending on your Prisma version/features, database `CHECK` constraints may require custom SQL migrations rather than being fully expressed in the Prisma schema.

For example, the migration SQL can contain:

```sql
ALTER TABLE lesson_progress
ADD CONSTRAINT progress_range
CHECK (progress >= 0 AND progress <= 100);
```

This is an important lesson:

> **Prisma doesn't expose every PostgreSQL feature equally through its schema language.**

When necessary, you can use SQL migrations.

That's one reason you should learn PostgreSQL instead of treating Prisma as a replacement for it.

---

# 13. `DEFAULT`

A default value is used when the application doesn't provide a value.

Example:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

If you insert:

```sql
INSERT INTO users (id, name)
VALUES ('...', 'Rahul');
```

PostgreSQL automatically sets:

```text
created_at = current timestamp
```

---

# 14. Prisma `@default`

In Prisma:

```prisma
createdAt DateTime @default(now())
```

means:

```text
If createdAt isn't supplied
        ↓
Use current timestamp
```

Another example:

```prisma
isActive Boolean @default(true)
```

New users become:

```text
isActive = true
```

unless you explicitly provide another value.

---

# 15. Default vs Required

These are different concepts.

Consider:

```prisma
isActive Boolean @default(true)
```

The field is still effectively required at the database level, but the database knows what value to use when you omit it.

So:

```text
NOT NULL
+
DEFAULT
```

means:

> A value must exist, but the database can generate one if you don't provide it.

---

# 16. Combining Constraints

A real column may use several rules.

For example:

```sql
email TEXT NOT NULL UNIQUE
```

This means:

```text
email
 ├── required
 └── unique
```

Or:

```sql
progress INTEGER NOT NULL
    CHECK (progress >= 0 AND progress <= 100)
```

This means:

```text
progress
 ├── required
 └── 0–100 only
```

Good schema design often combines multiple constraints.

---

# 17. AI LMS Example — Users

A sensible user table might have:

```text
users
├── id              PRIMARY KEY
├── name            NOT NULL
├── email           NOT NULL + UNIQUE
├── password_hash   NOT NULL
├── created_at      NOT NULL + DEFAULT
└── updated_at      NOT NULL
```

Conceptually:

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Now PostgreSQL is already protecting several rules.

---

# 18. AI LMS Example — Courses

Suppose:

> Every course must have a title and instructor.

We could have:

```sql
CREATE TABLE courses (
    id UUID PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    instructor_id UUID NOT NULL,

    FOREIGN KEY (instructor_id)
        REFERENCES users(id)
);
```

Rules:

```text
id
→ unique

title
→ required

instructor_id
→ required

instructor_id
→ must reference existing user
```

That's much stronger than simply having:

```text
courses
├── id
├── title
└── instructor_id
```

with no database rules.

---

# 19. AI LMS Example — Lessons

Requirement:

> A lesson must belong to a course.

```sql
CREATE TABLE lessons (
    id UUID PRIMARY KEY,
    course_id UUID NOT NULL,
    title VARCHAR(200) NOT NULL,
    content TEXT,
    lesson_order INTEGER NOT NULL,

    FOREIGN KEY (course_id)
        REFERENCES courses(id),

    CHECK (lesson_order > 0)
);
```

Now:

```text
course_id
→ must exist

title
→ required

lesson_order
→ must be greater than 0
```

The database understands the business rules.

---

# 20. AI LMS Example — Enrollment

Requirement:

> A student cannot enroll in the same course twice.

This is a perfect use case for a composite primary key.

```sql
CREATE TABLE enrollments (
    user_id UUID NOT NULL,
    course_id UUID NOT NULL,
    enrolled_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    PRIMARY KEY (user_id, course_id),

    FOREIGN KEY (user_id)
        REFERENCES users(id),

    FOREIGN KEY (course_id)
        REFERENCES courses(id)
);
```

Now:

```text
User 1 + Course 10
```

can exist once.

But:

```text
User 1 + Course 10
User 1 + Course 10
```

is rejected.

---

# 21. Why Constraints Are Better Than Application-Only Rules

Suppose your service does:

```ts
const existing = await prisma.enrollment.findUnique(...);

if (existing) {
  throw new Error("Already enrolled");
}

await prisma.enrollment.create(...);
```

Looks good.

But there's a concurrency problem.

Two requests can arrive at nearly the same time:

```text
Request A → check → no enrollment
Request B → check → no enrollment

Request A → create
Request B → create
```

Now you have a duplicate.

But if the database has:

```text
PRIMARY KEY (user_id, course_id)
```

the database itself guarantees uniqueness.

This is a very important backend lesson:

> **Application validation improves behavior; database constraints enforce invariants.**

---

# 22. Constraints + Transactions

Now combine the previous two lessons.

Suppose:

```text
Enrollment
+
Lesson Progress
+
Activity
```

must be created together.

Use:

```text
Transaction
```

And:

```text
(user_id, course_id)
```

must be unique.

Use:

```text
Constraint
```

So:

```text
Transaction
    ↓
Atomicity

Constraint
    ↓
Data validity
```

These mechanisms solve different problems and work together.

---

# 23. `ON DELETE`

Foreign keys can also define what happens when the referenced row is deleted.

Example:

```sql
FOREIGN KEY (course_id)
REFERENCES courses(id)
ON DELETE CASCADE
```

If the course is deleted:

```text
Course
   ↓
Lessons
   ↓
Deleted automatically
```

Another option:

```sql
ON DELETE RESTRICT
```

means:

```text
Course has lessons
      ↓
Attempt delete
      ↓
❌ Block deletion
```

And:

```sql
ON DELETE SET NULL
```

means:

```text
Parent deleted
      ↓
Foreign key becomes NULL
```

provided the foreign-key column allows NULL.

Choose these based on business rules.

---

# 24. Cascading Can Be Dangerous

Imagine:

```text
User
 ├── Enrollment
 ├── Progress
 ├── Quiz Attempts
 ├── AI Conversations
 └── Activity Logs
```

Now you add:

```text
ON DELETE CASCADE
```

to everything.

Delete one user:

```text
User deleted
   ↓
Enrollment deleted
   ↓
Progress deleted
   ↓
Quiz attempts deleted
   ↓
AI conversations deleted
   ↓
Activity logs deleted
```

That could be disastrous.

Especially for:

```text
audit logs
financial records
historical information
compliance data
```

Don't use `CASCADE` just because it's convenient.

---

# 25. Business Rules vs Database Rules

Not every business rule belongs in a database constraint.

For example:

> "A student should be allowed to enroll only if they have completed prerequisite course X."

That's often application/business logic.

You might implement:

```text
Service
   ↓
Check prerequisites
   ↓
Transaction
   ↓
Create enrollment
```

But:

> "The same student cannot have two enrollments for the same course."

is an excellent database invariant:

```text
PRIMARY KEY (user_id, course_id)
```

This distinction is important.

---

# 26. Database Invariants

An **invariant** is a rule that should always be true.

Examples:

```text
Email is unique.

Every lesson belongs to an existing course.

Progress is between 0 and 100.

An enrollment cannot be duplicated.

A quiz attempt belongs to an existing quiz.

A course must have an instructor.
```

These are excellent candidates for database-level enforcement.

Think:

```text
Invariant
   ↓
Can PostgreSQL enforce it?
   ↓
YES → consider a constraint
```

---

# 27. Constraint Naming

You can give constraints meaningful names.

For example:

```sql
CONSTRAINT lesson_progress_range
CHECK (progress >= 0 AND progress <= 100)
```

Instead of leaving everything with an automatically generated name.

This makes errors easier to understand.

For example:

```text
lesson_progress_range violated
```

is much more useful than some obscure generated identifier.

---

# 28. `CHECK` With Multiple Conditions

You can have:

```sql
CHECK (
    progress >= 0
    AND progress <= 100
)
```

Or:

```sql
CHECK (
    score >= 0
    AND score <= max_score
)
```

You can create sophisticated business rules.

But be careful:

> Complex constraints can become difficult to maintain.

Don't try to encode your entire business layer inside SQL constraints.

---

# 29. `CHECK` and NULL

There's a subtle point worth knowing.

Consider:

```sql
CHECK (progress >= 0 AND progress <= 100)
```

If `progress` is `NULL`, the `CHECK` condition doesn't necessarily fail because SQL uses three-valued logic.

If you require a value, combine:

```sql
progress INTEGER NOT NULL
CHECK (progress >= 0 AND progress <= 100)
```

This gives:

```text
NULL      → ❌
-1        → ❌
50        → ✅
101       → ❌
```

This is a great example of why `NOT NULL` and `CHECK` often work together.

---

# 30. Constraints and Security

Constraints are also part of defensive engineering.

Imagine your API has a bug that allows:

```text
progress = -500
```

If your database has:

```sql
CHECK (progress >= 0 AND progress <= 100)
```

the invalid data still can't be stored.

This is not a replacement for security controls, but it's an important **defense-in-depth** technique.

Later, in your dedicated security phase, you'll see the same philosophy across:

```text
validation
authorization
database constraints
rate limiting
logging
input sanitization
```

# 32. A Strong AI LMS Model

Let's combine what we've learned.

```prisma
enum EnrollmentStatus {
  ACTIVE
  COMPLETED
  CANCELLED
}

model User {
  id           String       @id @default(uuid())
  name         String
  email        String       @unique
  passwordHash String
  createdAt    DateTime     @default(now())
  updatedAt    DateTime     @updatedAt

  courses      Course[]
  enrollments  Enrollment[]
  progress     LessonProgress[]
}

model Course {
  id           String       @id @default(uuid())
  title        String
  description  String?
  instructorId String
  createdAt    DateTime     @default(now())

  instructor   User          @relation(fields: [instructorId], references: [id])
  lessons      Lesson[]
  enrollments  Enrollment[]

  @@index([instructorId])
}

model Lesson {
  id          String   @id @default(uuid())
  courseId    String
  title       String
  content     String?
  lessonOrder Int
  createdAt   DateTime @default(now())

  course      Course           @relation(fields: [courseId], references: [id])
  progress    LessonProgress[]

  @@index([courseId])
}

model Enrollment {
  userId     String           @
  courseId   String
  status     EnrollmentStatus @default(ACTIVE)
  enrolledAt DateTime         @default(now())

  user       User   @relation(fields: [userId], references: [id])
  course     Course @relation(fields: [courseId], references: [id])

  @@id([userId, courseId])
}

model LessonProgress {
  userId      String
  lessonId    String
  progress    Int      @default(0)
  completedAt DateTime?

  user        User     @relation(fields: [userId], references: [id])
  lesson      Lesson   @relation(fields: [lessonId], references: [id])

  @@id([userId, lessonId])
}
```

One correction: the `Enrollment.userId` line should simply be:

```prisma
userId String
```

So the complete model is conceptually:

```prisma
model Enrollment {
  userId     String
  courseId   String
  status     EnrollmentStatus @default(ACTIVE)
  enrolledAt DateTime         @default(now())

  user   User   @relation(fields: [userId], references: [id])
  course Course @relation(fields: [courseId], references: [id])

  @@id([userId, courseId])
}
```

And for `LessonProgress`, we would add a database-level check for:

```text
0 <= progress <= 100
```

through a migration if your Prisma setup doesn't express that constraint directly.

# 33. Database Protection Layers

At this point, your backend can have multiple protection layers:

```text
                    Request
                       ↓
              ┌────────────────┐
              │ Frontend        │
              │ validation      │
              └───────┬────────┘
                      ↓
              ┌────────────────┐
              │ Backend         │
              │ validation      │
              └───────┬────────┘
                      ↓
              ┌────────────────┐
              │ Service logic   │
              │ business rules  │
              └───────┬────────┘
                      ↓
              ┌────────────────┐
              │ Transaction     │
              └───────┬────────┘
                      ↓
              ┌────────────────┐
              │ PostgreSQL      │
              │ constraints     │
              └────────────────┘
```

Each layer has a different job.

That's much stronger than trusting a single layer.

---

# 34. A Very Important Principle

Here's a principle I want you to remember:

> **Never rely on application code alone to protect critical database invariants.**

If the database can enforce something safely, let the database enforce it.

For example:

```text
Unique email
→ UNIQUE

Valid progress range
→ CHECK

Existing course
→ FOREIGN KEY

Required title
→ NOT NULL

No duplicate enrollment
→ PRIMARY KEY / UNIQUE
```

Your application should still validate inputs, but the database becomes the final guard.

---

# 35. Common Beginner Mistakes

### Mistake 1 — Only validating in frontend

```text
Frontend says valid
      ↓
Database trusts it
```

Bad.

Frontend can be bypassed.

---

### Mistake 2 — Only validating in backend

Better, but still not enough.

Other processes may access the database.

---

### Mistake 3 — No foreign keys

You can end up with orphaned records.

---

### Mistake 4 — No unique constraint

Your application may accidentally create duplicate records under concurrency.

---

### Mistake 5 — Overusing `CHECK`

Don't turn the database into your entire business logic engine.

---

### Mistake 6 — Overusing `CASCADE`

You can accidentally delete large amounts of important data.

---

# 36. Constraint Decision Framework

When designing a field, ask:

### Does it have to exist?

```text
YES → NOT NULL
```

### Must it be unique?

```text
YES → UNIQUE
```

### Does it identify a row?

```text
YES → PRIMARY KEY
```

### Does it reference another entity?

```text
YES → FOREIGN KEY
```

### Must its value satisfy a condition?

```text
YES → CHECK
```

### Does it have a sensible automatic value?

```text
YES → DEFAULT
```

This is a very useful mental checklist.

---

# 37. Interview Perspective

If an interviewer asks:

> Why do we need database constraints if we already validate in the backend?

A strong answer is:

> Backend validation protects the application boundary and provides good error messages, but database constraints protect the data itself. They prevent invalid states even when data is inserted through another service, script, race condition, or buggy code path.

That's a much stronger answer than:

> "Because the database needs validation."

The key concepts:

```text
NOT NULL
    ↓

UNIQUE
    ↓

PRIMARY KEY
    ↓

FOREIGN KEY
```

And the bigger principle:

> **The database should protect the integrity of the data it stores.**
