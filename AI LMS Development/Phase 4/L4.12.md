# 🔐 Phase 4 — Lesson 4.12: Password Security & Password Lifecycle

We've now built:

```text
Authentication
├── Registration
├── Login
├── Access Tokens
├── Refresh Tokens
├── Token Rotation
├── Sessions
└── Authorization / RBAC
```

Now we're going deeper into one of the most sensitive parts of the system:

> **How should an application safely handle passwords throughout their entire lifecycle?**

For our AI LMS, the password lifecycle is:

```text
Register
   ↓
Hash password
   ↓
Store hash
   ↓
Login
   ↓
Verify password
   ↓
Change password
   ↓
Revoke sessions
```

And when a user forgets their password:

```text
Forgot password
   ↓
Generate reset token
   ↓
Send reset link
   ↓
User submits new password
   ↓
Invalidate reset token
   ↓
Update password hash
   ↓
Revoke existing sessions
```

---

# 1. First Rule: Never Store Passwords

Never do this:

```text
email: rahul@example.com
password: Rahul@123
```

Not in:

```text
PostgreSQL
MongoDB
logs
JWT
cookies
Redis
analytics
```

Instead:

```text
Password
   ↓
Password hashing algorithm
   ↓
Password hash
   ↓
Database
```

Example:

```text
Password:
MyPassword123!

Stored:
$argon2id$v=19$...
```

The database should contain the hash, not the original password.

---

# 2. Encryption vs Hashing

This distinction is extremely important.

### Encryption

```text
Plaintext
   ↓
Encryption
   ↓
Ciphertext
   ↓
Decrypt
   ↓
Plaintext
```

Encryption is reversible.

### Hashing

```text
Password
   ↓
Hash
   ↓
Hash
```

You don't decrypt a password hash.

Instead, when the user logs in:

```text
Submitted password
       ↓
Verify against stored hash
       ↓
Match?
```

So passwords should be **hashed**, not encrypted for normal authentication storage.

---

# 3. Why Hashing Works

Suppose Rahul registers:

```text
Password:
Rahul@123
```

The server calculates:

```text
hash("Rahul@123")
```

and stores:

```text
$argon2id$...
```

Later Rahul logs in:

```text
"Rahul@123"
      ↓
password verification
      ↓
stored hash
      ↓
MATCH
```

The application never needs to know the original password after registration.

---

# 4. Don't Use SHA-256 for Passwords

A common beginner mistake:

```typescript
crypto.createHash("sha256")
```

for passwords.

SHA-256 is excellent for many general hashing purposes, but it's designed to be fast.

Password hashing should intentionally be:

```text
slow
memory-intensive
configurable
salted
```

Why?

Because attackers can try huge numbers of guesses against leaked password hashes.

---

# 5. Password Hashing Algorithms

Common password-hashing choices include:

```text
Argon2id
bcrypt
scrypt
PBKDF2
```

For a modern Node.js application, **Argon2id** is an excellent choice when available.

For our AI LMS:

```text
Password
   ↓
Argon2id
   ↓
Database
```

---

# 6. Why Argon2id?

Argon2 was designed specifically for password hashing.

Argon2id is designed to make password cracking more expensive by using:

```text
CPU
+
Memory
+
Time
```

This is useful because attackers often use specialized hardware to try many password guesses.

A password hash should make each guess expensive.

---

# 7. What Is a Salt?

A salt is a random value used during password hashing.

Conceptually:

```text
password + random salt
        ↓
     Argon2id
        ↓
       hash
```

Suppose two users choose:

```text
password = "password123"
```

Without unique salts:

```text
User A → same hash
User B → same hash
```

With salts:

```text
User A:
password + salt_A
      ↓
hash_A

User B:
password + salt_B
      ↓
hash_B
```

So identical passwords don't produce identical stored hashes.

---

# 8. Do We Store the Salt?

Yes.

But you generally don't need a separate `salt` column when using modern password-hashing libraries.

The encoded Argon2/bcrypt hash normally contains the information required for verification, including the salt and parameters.

So your database might simply have:

```prisma
passwordHash String
```

rather than:

```prisma
password String
salt String
```

---

# 9. Password Schema

Our User model could contain:

```prisma
model User {
  id           String   @id @default(uuid())
  email        String   @unique
  passwordHash String

  role         Role     @default(STUDENT)

  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  sessions     Session[]
}
```

Notice:

```text
passwordHash
```

not:

```text
password
```

This naming is useful because it reminds developers:

> This field contains a hash, not the original password.

---

# 10. Password Hashing Service

Don't hash passwords directly inside controllers.

Instead:

```typescript
async function hashPassword(password: string) {
  return argon2.hash(password);
}
```

And:

```typescript
async function verifyPassword(
  password: string,
  passwordHash: string
) {
  return argon2.verify(
    passwordHash,
    password
  );
}
```

Then:

```text
Auth Service
   ↓
Password Utility
   ↓
Argon2id
```

This keeps the implementation centralized.

# 11. Registration Flow

Let's follow registration:

```text
POST /auth/register
        ↓
Validate input
        ↓
Normalize email
        ↓
Check existing user
        ↓
Validate password policy
        ↓
Hash password
        ↓
Create user
        ↓
Create session
        ↓
Return authentication result
```

The critical part:

```text
Raw password
     ↓
Hash
     ↓
Database
```

The raw password should disappear from application memory as soon as practical.

---

# 12. Password Validation

Hashing alone isn't enough.

We should have a password policy.

For example:

```text
Minimum length
Reasonable maximum length
```

A modern approach should prioritize **length** over complicated rules like:

```text
Must contain:
uppercase
lowercase
number
symbol
special character
```

A long passphrase can be much stronger than a short complex password.

For example:

```text
correct-horse-battery-staple-style-long-passphrase
```

can be much stronger than:

```text
R@1x!
```

---

# 13. Don't Make Password Rules Too Annoying

Bad UX:

```text
Password must contain:
1 uppercase
1 lowercase
1 number
1 symbol
1 emoji
2 mathematical symbols
```

Users respond by creating predictable passwords:

```text
Password@1
Password@2
Password@3
```

A better strategy:

```text
Strong minimum length
+
Block extremely common passwords
+
Allow password managers
+
Allow long passwords
```

---

# 14. Maximum Password Length

This is an interesting security detail.

Don't accidentally reject legitimate long passwords.

For example:

```text
max length = 20
```

is unnecessarily restrictive.

Instead, choose a generous maximum appropriate for your system.

Also consider protection against pathological inputs so an attacker can't send enormous strings designed to consume excessive CPU or memory.

---

# 15. Login Flow

Login becomes:

```text
POST /auth/login
       ↓
Validate email/password
       ↓
Find user
       ↓
Verify password hash
       ↓
Check account state
       ↓
Create session
       ↓
Issue access token
       ↓
Issue refresh token
```

Important:

> Never hash the submitted password and compare strings manually when using a password-hashing algorithm like Argon2id.

Use the library's verification function.

---

# 16. Why?

Modern password hashes contain parameters such as:

```text
algorithm
version
memory cost
time cost
parallelism
salt
hash
```

The verification library understands this format.

So:

```typescript
argon2.verify(
  storedHash,
  submittedPassword
);
```

is the correct pattern.

---

# 17. User Enumeration

Consider login:

```text
POST /auth/login
```

If the email doesn't exist:

```text
"User does not exist"
```

If the email exists but password is wrong:

```text
"Incorrect password"
```

This allows attackers to discover registered accounts.

Better:

```text
"Invalid email or password."
```

for both cases.

This gives a more consistent authentication response.

---

# 18. Timing Considerations

There can also be timing differences between:

```text
user doesn't exist
```

and:

```text
user exists
but password is wrong
```

A robust authentication implementation should avoid making account existence trivially distinguishable through timing.

The exact implementation depends on the password library and application design.

The important principle:

> Don't accidentally create an easy account-enumeration oracle.

---

# 19. Password Change

Now suppose the user is already logged in.

Endpoint:

```http
PATCH /api/v1/auth/password
```

Request:

```json
{
  "currentPassword": "old-password",
  "newPassword": "new-password"
}
```

Flow:

```text
Authenticated user
       ↓
Load password hash
       ↓
Verify current password
       ↓
Validate new password
       ↓
Hash new password
       ↓
Update passwordHash
       ↓
Revoke existing sessions
       ↓
Require fresh authentication
```

This is a critical security workflow.

---

# 20. Why Verify the Current Password?

Suppose someone gains temporary access to Rahul's already-open browser.

If they can simply send:

```text
PATCH /auth/password
```

with:

```text
newPassword = attackerPassword
```

they could permanently take over the account.

Therefore, requiring the current password provides an additional security barrier.

For especially sensitive environments, you may require recent authentication or step-up authentication instead.

---

# 21. Password Change + Sessions

Remember Lesson 4.9.

Suppose Rahul has:

```text
Laptop → Session A
Phone  → Session B
Tablet → Session C
```

He changes his password.

A strong policy is:

```text
Password changed
       ↓
Revoke A
Revoke B
Revoke C
       ↓
Login again
```

Why?

Because we don't know whether an existing session has been compromised.

---

# 22. Should the Current Session Also Be Revoked?

Yes, often.

The simplest secure policy is:

```text
Password change
      ↓
Revoke all sessions
      ↓
Authenticate again
```

This gives us a clean security boundary.

Another UX-friendly approach is to keep the current session while revoking all others, but that requires careful design.

For our LMS:

> **Revoke all sessions after password change** is a simple and strong default.

---

# 23. Password Reset

Now the more difficult case:

> Rahul forgot his password.

He can't provide:

```text
currentPassword
```

So we need:

```text
Forgot password
       ↓
Password reset token
       ↓
Verify token
       ↓
Set new password
```

---

# 24. Forgot Password Endpoint

We can design:

```http
POST /api/v1/auth/forgot-password
```

Request:

```json
{
  "email": "rahul@example.com"
}
```

The server generates a reset credential.

But there is an important rule:

> **Never send the password-reset token back in the API response.**

It should be delivered through a trusted out-of-band channel such as email.

---

# 25. Reset Token

Conceptually:

```text
Random reset token
       ↓
Email link
       ↓
https://lms.example/reset-password?token=...
```

The token should be:

```text
cryptographically random
single-use
short-lived
unguessable
```

---

# 26. Don't Use JWT for Password Reset Unless You Have a Strong Reason

A JWT can be made to work, but a random opaque reset token is often simpler.

For example:

```text
crypto.randomBytes(...)
```

produces a high-entropy random credential.

Then:

```text
raw token
   ↓
send to user
```

and:

```text
hash(raw token)
   ↓
store in database
```

This follows the same principle we used for refresh tokens.

---

# 27. Store Only the Reset Token Hash

Don't store:

```text
resetToken = abc123...
```

Instead:

```text
resetTokenHash = hash(abc123...)
```

Database:

```text
PasswordReset
├── userId
├── tokenHash
├── expiresAt
├── usedAt
└── createdAt
```

Then:

```text
Email link
    ↓
raw token
    ↓
hash
    ↓
database lookup
```

---

# 28. Password Reset Model

A useful Prisma model:

```prisma
model PasswordResetToken {
  id        String    @id @default(uuid())
  userId    String

  tokenHash String    @unique

  expiresAt DateTime
  usedAt    DateTime?

  createdAt DateTime  @default(now())

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  @@index([userId])
}
```

Now we have:

```text
User
 │
 └── PasswordResetToken
```

---

# 29. Why `usedAt`?

A reset token should be single-use.

Suppose:

```text
Token A
```

is successfully used.

Then:

```text
usedAt = now()
```

Now:

```text
Token A
 ↓
usedAt != null
 ↓
reject
```

This prevents replay.

---

# 30. Why `expiresAt`?

Reset links shouldn't work forever.

For example:

```text
Token created
     ↓
short expiration window
     ↓
expires
```

The exact lifetime should be chosen based on your application's risk and email-delivery UX.

The important rule:

```text
expired token
→ reject
```

---

# 31. Password Reset Flow

Complete flow:

```text
POST /forgot-password
        ↓
Find account
        ↓
Generate random token
        ↓
Hash token
        ↓
Store hash + expiry
        ↓
Send email
```

Then:

```text
User clicks link
        ↓
Frontend receives token
        ↓
User enters new password
        ↓
POST /reset-password
        ↓
Hash submitted token
        ↓
Find reset record
        ↓
Check expiry
        ↓
Check usedAt
        ↓
Hash new password
        ↓
Update passwordHash
        ↓
Mark reset token used
        ↓
Revoke sessions
```

---

# 32. Transaction for Password Reset

Several operations need to happen together:

```text
Update password
+
Mark reset token used
+
Revoke sessions
```

We don't want:

```text
Password updated
       ↓
💥 server crash
       ↓
Token still appears unused
```

or:

```text
Token marked used
       ↓
Password update fails
```

Therefore, use a database transaction for the critical state transition.

Conceptually:

```typescript
await prisma.$transaction(async (tx) => {
  // verify reset token

  // update password hash

  // mark token as used

  // revoke sessions
});
```

---

# 33. One-Time Token Invariant

Our invariant:

> A password-reset token can successfully change a password at most once.

We enforce this through:

```text
usedAt
+
expiration
+
transaction
```

This is another example of defining an invariant before writing code.

---

# 34. Multiple Reset Requests

Suppose Rahul clicks:

```text
Forgot Password
```

three times.

We might have:

```text
Token A
Token B
Token C
```

Should all remain valid?

Probably not.

A simple policy:

```text
Generate new reset token
       ↓
Invalidate previous active reset tokens
```

Then:

```text
A → invalid
B → invalid
C → active
```

This reduces the number of valid recovery credentials.

---

# 35. Alternative: Delete Old Tokens

We can do:

```typescript
await prisma.passwordResetToken.deleteMany({
  where: {
    userId,
  },
});
```

then create a new token.

This is simple.

But if you need auditing, you may prefer:

```text
usedAt
invalidatedAt
```

and retain historical records.

Again:

```text
simple first
+
more detail when required
```

---

# 36. Don't Reveal Whether an Email Exists

This endpoint:

```http
POST /auth/forgot-password
```

is another account-enumeration risk.

Don't respond:

```text
"That email doesn't exist."
```

Instead:

```text
"If an account exists for this email, we sent password reset instructions."
```

This way:

```text
Existing account
→ same response

Non-existing account
→ same response
```

---

# 37. Rate Limiting Password Reset

Attackers can abuse:

```text
POST /auth/forgot-password
```

to send thousands of emails.

Therefore:

```text
Rate limiting
+
Abuse protection
```

is important.

For example:

```text
per IP
+
per email/account
```

with appropriate limits.

Don't rely solely on IP-based rate limiting because many users can share an IP and attackers can rotate IPs.

---

# 38. Login Rate Limiting

The same applies to:

```text
POST /auth/login
```

Attackers can try:

```text
password1
password2
password3
...
```

So authentication endpoints should have appropriate throttling.

We will go deeper into this in our security-focused phase.

---

# 39. Password Reset Rate Limiting

Also protect:

```text
POST /auth/forgot-password
POST /auth/reset-password
```

For example:

```text
Forgot password
→ limited attempts

Reset token verification
→ limited attempts
```

The exact limits should account for legitimate users, email delays, and distributed abuse.

---

# 40. Password Reset Token Entropy

Don't generate:

```typescript
Math.random().toString()
```

for security-sensitive reset credentials.

Use a cryptographically secure random generator.

In Node.js:

```typescript
import crypto from "node:crypto";

const token =
  crypto.randomBytes(32).toString("hex");
```

Now:

```text
32 random bytes
=
256 bits of entropy
```

assuming the random generator is used correctly.

That's vastly different from predictable application-level randomness.

---

# 41. Token Hashing

Then:

```typescript
const tokenHash = hashToken(token);
```

You could use a cryptographic hash for the reset token because the reset token is already a high-entropy random secret.

The important distinction:

```text
Password
→ slow password hash

Random reset token
→ cryptographic hash is generally sufficient
```

Why?

Because a random 256-bit token doesn't need the same expensive password-guessing resistance as a human-chosen password.

---

# 42. Password Reset Email

The email might contain:

```text
You requested a password reset.

Click the link below to create a new password.

[Reset Password]

This link expires soon and can only be used once.

If you didn't request this, you can safely ignore this email.
```

Don't include:

```text
current password
password hash
session token
```

or other sensitive information.

---

# 43. Reset Token in URL

A common pattern:

```text
https://lms.example/reset-password?token=...
```

But remember:

URLs can potentially appear in:

```text
browser history
server logs
analytics
referrer headers
```

Therefore, password-reset flows need careful handling.

One good pattern is:

```text
Reset link
 ↓
Frontend
 ↓
Exchange/submit token quickly
 ↓
Don't retain token unnecessarily
```

and ensure logging/analytics don't capture the full URL.

---

# 44. Don't Log Reset Tokens

Never:

```typescript
console.log(resetToken);
```

Not even during development if logs might persist somewhere.

Instead:

```text
Reset token generated
userId=123
expiresAt=...
```

if operational logging is necessary.

---

# 45. Password Change vs Password Reset

These are different workflows.

### Password change

User knows current password:

```text
current password
+
new password
```

### Password reset

User forgot current password:

```text
reset token
+
new password
```

Both should end with:

```text
new password hash
+
session invalidation
```

---

# 46. Password Reset Should Revoke Sessions

Imagine an attacker has:

```text
Session A
Session B
```

Rahul forgets his password and resets it.

If we don't revoke sessions:

```text
Old sessions
   ↓
still active
```

That defeats part of the purpose of password recovery.

Therefore:

```text
Password reset
      ↓
Revoke all sessions
```

is a strong default.

---

# 47. Password History

Should we prevent:

```text
Old password
→ new password
→ old password again
```

?

Some enterprise systems maintain password history.

For our LMS:

> Don't add password-history complexity unless there is a real requirement.

If you later need it:

```text
PasswordHistory
├── userId
├── passwordHash
└── createdAt
```

But be careful about retention and storage requirements.

---

# 48. Password Reuse

For a student LMS, forcing:

```text
"Cannot reuse your last 10 passwords"
```

may be unnecessary.

Instead prioritize:

```text
long passwords
password manager support
rate limiting
secure reset
session revocation
MFA later
```

Good security is not simply "more restrictions."

---

# 49. Compromised Password Detection

Another useful improvement is checking passwords against known compromised-password datasets.

For example:

```text
User chooses:
password123
```

Your system can reject it because it is extremely common or compromised.

This is stronger than only checking:

```text
uppercase
lowercase
number
symbol
```

The exact implementation can be added later.

---

# 50. Password Manager Support

Don't break password managers.

Avoid unnecessary restrictions such as:

```text
maxlength="20"
```

or strange password characters being rejected.

A password field should generally support:

```html
<input
  type="password"
  autocomplete="new-password"
/>
```

For login:

```html
<input
  type="password"
  autocomplete="current-password"
/>
```

These small details improve real-world authentication UX.

---

# 51. Email Normalization

Password security starts before hashing.

Suppose:

```text
Rahul@Example.com
rahul@example.com
```

Are these the same account?

Your application should define a consistent email normalization strategy.

At minimum:

```text
trim whitespace
```

and usually normalize case according to your account identity policy.

The exact rules around email addresses should be chosen carefully rather than blindly transforming every part.

---

# 52. Never Normalize Passwords Like Emails

For example:

```typescript
email = email.toLowerCase();
```

may be appropriate depending on your email identity policy.

But don't do:

```typescript
password = password.toLowerCase();
```

Passwords are case-sensitive credentials.

Likewise, don't trim password input unless your password policy explicitly says so.

If the user intentionally chose:

```text
" MyPassword "
```

changing it silently can create authentication surprises.

---

# 53. Password DTO

A password-change input might be:

```typescript
interface ChangePasswordInput {
  currentPassword: string;
  newPassword: string;
}
```

A reset input:

```typescript
interface ResetPasswordInput {
  token: string;
  newPassword: string;
}
```

Notice:

```text
password
```

never becomes part of:

```text
UserResponseDTO
```

---

# 54. Never Return Password Fields

Even though the database field is:

```text
passwordHash
```

don't return:

```json
{
  "id": "123",
  "email": "rahul@example.com",
  "passwordHash": "$argon2id$..."
}
```

Not even to the frontend.

Your user DTO should look like:

```json
{
  "id": "123",
  "email": "rahul@example.com",
  "role": "STUDENT"
}
```

---

# 55. Logging Password Operations

Useful:

```text
PASSWORD_CHANGED
PASSWORD_RESET_SUCCESS
PASSWORD_RESET_REQUESTED
```

Avoid:

```text
password=...
currentPassword=...
newPassword=...
resetToken=...
```

Logs often have a much longer lifetime than developers expect.

Treat logs as sensitive production data.

---

# 56. Account Locking

Should we lock the account after:

```text
5 failed attempts
```

?

Possibly, but permanent account locking can create denial-of-service problems.

Imagine an attacker deliberately fails login attempts against Rahul's account.

If:

```text
5 failures
→ account permanently locked
```

the attacker can lock Rahul out.

Better approaches can include:

```text
progressive delays
temporary throttling
IP/device signals
risk-based controls
CAPTCHA/challenges where appropriate
```

We'll explore this more in security engineering.

# 59. A Strong Password Service

Conceptually:

```typescript
class PasswordService {
  async hash(password: string) {
    return argon2.hash(password);
  }

  async verify(
    password: string,
    hash: string
  ) {
    return argon2.verify(hash, password);
  }
}
```

Then:

```text
AuthService
   ↓
PasswordService
   ↓
Argon2
```

This makes the rest of your application independent of the exact hashing implementation.

# 60. Password Change Service

Conceptually:

```typescript
async function changePassword(
  userId: string,
  currentPassword: string,
  newPassword: string
) {
  const user =
    await userRepository.findById(userId);

  if (!user) {
    throw new NotFoundError();
  }

  const valid = await passwordService.verify(
    currentPassword,
    user.passwordHash
  );

  if (!valid) {
    throw new InvalidCredentialsError();
  }

  const newHash =
    await passwordService.hash(newPassword);

  await prisma.$transaction(async (tx) => {
    await userRepository.updatePassword(
      tx,
      userId,
      newHash
    );

    await sessionRepository.revokeAllForUser(
      tx,
      userId
    );
  });
}
```

The exact repository signatures will depend on our implementation, but notice the architecture:

```text
Service
 ↓
Password verification
 ↓
Transaction
 ├── update password
 └── revoke sessions
```

# 61. Why a Transaction?

We want these operations to behave as one logical security change:

```text
Password changed
+
Old sessions revoked
```

not:

```text
Password changed
+
old sessions remain active
```

because of a partial failure.

# 62. Password Reset Service

Conceptually:

```typescript
async function resetPassword(
  token: string,
  newPassword: string
) {
  const tokenHash = hashToken(token);

  await prisma.$transaction(async (tx) => {
    const resetToken =
      await resetRepository.findValidToken(
        tx,
        tokenHash
      );

    if (!resetToken) {
      throw new InvalidResetTokenError();
    }

    const newHash =
      await passwordService.hash(newPassword);

    await userRepository.updatePassword(
      tx,
      resetToken.userId,
      newHash
    );

    await resetRepository.markUsed(
      tx,
      resetToken.id
    );

    await sessionRepository.revokeAllForUser(
      tx,
      resetToken.userId
    );
  });
}
```

Again:

```text
verify
+
update
+
consume
+
revoke
```

happens atomically.

# 63. Security Invariants

Let's define them.

### Password invariant

```text
Raw passwords are never persisted.
```

### Reset invariant

```text
A reset token can only be used once.
```

### Expiration invariant

```text
An expired reset token cannot change a password.
```

### Session invariant

```text
Password reset invalidates existing refresh sessions.
```

### Authentication invariant

```text
A user must prove knowledge of the current password
to perform a normal password change.
```

These invariants are excellent material for security tests.

# 65. Important Negative Test

Never only test:

```text
"Password reset works."
```

Also test:

```text
"Can I reuse the reset token?"
```

Expected:

```text
❌ No
```

Test:

```text
"Can I use an expired reset token?"
```

Expected:

```text
❌ No
```

Test:

```text
"Can another user use this reset token?"
```

Expected:

```text
❌ No
```

Security testing is heavily about proving that bad behavior is impossible.

# 🧠 Interview-Level Question

### "How would you implement a secure forgot-password flow?"

A strong answer:

> I would accept the email address and return the same generic response regardless of whether the account exists, to reduce account enumeration. For an existing account, I would generate a cryptographically secure random reset token, store only a hash of that token with a short expiration and single-use state, and send the raw token through a trusted email link. When the user submits the token and new password, I would verify the hashed token, expiration, and unused state, then atomically update the password hash, mark the reset token as used, and revoke existing sessions. I would also rate-limit the password-reset endpoints and never log or return the reset token unnecessarily.

That's a very strong backend interview answer.

# 🎯 Lesson 4.12 Takeaways

```text
1. Never store plaintext passwords.

2. Passwords should be hashed, not reversibly encrypted.

3. Prefer a dedicated password hashing algorithm such as
   Argon2id rather than fast general-purpose hashes.

4. Modern password hashes handle salts and parameters for you.

5. Use password-library verification functions instead of
   manually comparing hashes.

6. Use long, reasonable password policies rather than
   overly complicated character requirements.

7. Never return passwordHash in API responses.

8. Don't reveal whether an account exists during forgot-password
   requests.

9. Password reset tokens should be:
   - random
   - high entropy
   - short-lived
   - single-use

10. Store only the reset-token hash.

11. Mark reset tokens as used after successful reset.

12. Password changes should verify the current password.

13. Password changes and resets should generally revoke
    existing sessions.

14. Use transactions for critical password-reset state changes.

15. Rate-limit authentication and password-reset endpoints.

16. Never log passwords, reset tokens, or authentication secrets.

17. Test negative security cases aggressively.
```
