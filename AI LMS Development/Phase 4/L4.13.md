# 🔐 Phase 4 — Lesson 4.13: Email Verification & Account Activation

In the previous lesson, we secured the **password lifecycle**:

```text
Password
   ↓
Hash
   ↓
Login
   ↓
Change / Reset
   ↓
Session Revocation
```

Now we'll add another important part of authentication:

> **How does the application know that the user actually controls the email address they registered with?**

This gives us:

```text
Registration
    ↓
Create account
    ↓
Send verification email
    ↓
User clicks link
    ↓
Verify token
    ↓
Mark email as verified
    ↓
Allow normal account usage
```

For our AI LMS, this will be especially useful because email can later be used for:

- password recovery
    
- important account notifications
    
- course notifications
    
- security alerts
    
- account ownership
    
- eventually MFA/recovery workflows
    

---

# 1. Why Email Verification?

Suppose someone registers:

```text
email = someone@example.com
```

How do we know they control that mailbox?

We don't.

The user could have typed:

```text
wrong@example.com
```

or someone else's email.

Email verification gives us a basic proof:

```text
User entered email
        ↓
Server sends secret link
        ↓
User receives email
        ↓
User uses secret link
        ↓
We know they likely control the mailbox
```

It's not perfect identity verification, but it's useful **email ownership verification**.

---

# 2. Email Verification Is Not Authentication

This distinction is important.

Email verification answers:

```text
"Does this person control this email address?"
```

Authentication answers:

```text
"Who is this authenticated account?"
```

Authorization answers:

```text
"What is this account allowed to do?"
```

So our system now has:

```text
Email Verification
        ↓
Authentication
        ↓
Authorization
```

These are separate concepts.

# 5. Should Unverified Users Be Allowed to Login?

There isn't one universal answer.

You have several choices.

### Option A — Don't allow login

```text
Register
   ↓
Verify email
   ↓
Login
```

### Option B — Allow limited login

```text
Register
   ↓
Login
   ↓
Limited account
   ↓
Verify email
   ↓
Full access
```

### Option C — Allow login but restrict sensitive actions

For our AI LMS, I prefer:

```text
Register
   ↓
Account created
   ↓
Email unverified
   ↓
Limited authentication
   ↓
Require verification for important actions
```

This gives a better user experience while still allowing us to protect important operations.


```text

```

# 7. Verification Token

We need a temporary secret.

Conceptually:

```text
Random token
     ↓
Email link
```

Example:

```text
https://lms.example/verify-email?token=...
```

The token should be:

```text
cryptographically random
high entropy
short-lived
single-use
```

Same principles as our password reset tokens.

---

# 8. Never Use `Math.random()`

Don't do:

```typescript
const token = Math.random()
  .toString(36);
```

This is not suitable for security-sensitive tokens.

Instead:

```typescript
import crypto from "node:crypto";

const token =
  crypto.randomBytes(32).toString("hex");
```

Now:

```text
32 bytes
=
256 bits of randomness
```

assuming the cryptographic random generator is functioning correctly.

---

# 9. Store Only the Token Hash

We have:

```text
raw token
```

which goes to the user.

But in our database:

```text
tokenHash
```

should be stored.

The flow is:

```text
Random token
      │
      ├──────────────→ Email
      │
      ▼
   Hash token
      │
      ▼
 PostgreSQL
```

This means a database leak doesn't immediately expose active verification links.

```prisma
    references: [id],
    onDelete: Cascade

```

And:

```prisma
model User {
  id                    String                  @id @default(uuid())
  email                 String                  @unique
  passwordHash          String

  emailVerified         Boolean                 @default(false)

  role                  Role                    @default(STUDENT)

  emailVerificationTokens EmailVerificationToken[]

  sessions              Session[]
}
```

The exact relation naming can be adjusted to match the schema we've built earlier.

# 11. Why `usedAt`?

Suppose:

```text
Token A
```

is successfully used.

Set:

```text
usedAt = current time
```

Then:

```text
Token A
 ↓
usedAt != null
 ↓
reject
```

This gives us a strong invariant:

> **An email verification token can only be used once.**

---

# 12. Why `expiresAt`?

Verification links shouldn't work forever.

For example:

```text
Token created
     ↓
expiresAt
     ↓
expired
```

After expiration:

```text
❌ verification rejected
```

The exact expiration duration is a product/security decision. A relatively short window is generally appropriate, while allowing the user to request a fresh link.

# 14. Important: Don't Send the Raw Token in the API Response

Bad:

```json
{
  "user": {...},
  "verificationToken": "abc123..."
}
```

Why?

Because now the frontend/API client has the verification secret.

The token should normally travel through the intended email-verification channel.

Your API response can simply say:

```json
{
  "message": "Account created. Please check your email to verify your account."
}
```

# 17. Verification Flow

The backend receives:

```text

```

Then:

```text

    ↓

    ↓

    ↓
```

# 18. Use a Transaction

We need two important changes:

```text
User:
emailVerified = true

Token:
usedAt = now()
```

We want these to succeed together.

Conceptually:

```typescript
await prisma.$transaction(async (tx) => {
  // find valid verification token

  // mark email verified

  // mark token as used
});
```

This prevents inconsistent states.

---

# 19. Verification Invariants

Let's define our security invariants.

### Invariant 1

```text
An expired token cannot verify an email.
```

### Invariant 2

```text
A used token cannot be reused.
```

### Invariant 3

```text
A token can verify only the user associated with it.
```

### Invariant 4

```text
A successful verification marks the email as verified.
```

### Invariant 5

```text
Successful verification consumes the token.
```

These are excellent candidates for automated tests.

# 20. Example Verification Service

Conceptually:

```typescript
async function verifyEmail(token: string) {
  const tokenHash = hashToken(token);

  await prisma.$transaction(async (tx) => {
    const record =
      await verificationRepository
        .findValidToken(tx, tokenHash);

    if (!record) {
      throw new InvalidVerificationTokenError();
    }

    await userRepository.markEmailVerified(
      tx,
      record.userId
    );

    await verificationRepository.markUsed(
      tx,
      record.id
    );
  });
}
```

The service owns the business flow.

---

# 21. What Does `findValidToken` Mean?

Instead of:

```typescript
findToken(tokenHash)
```

we can make the repository query enforce validity:

```text
tokenHash matches
AND
usedAt IS NULL
AND
expiresAt > NOW()
```

Conceptually:

```typescript
where: {
  tokenHash,
  usedAt: null,
  expiresAt: {
    gt: new Date(),
  },
}
```

This is nice because invalid tokens never reach the service as valid candidates.

# 22. What If the User Is Already Verified?

Suppose:

```text
emailVerified = true
```

and they click an old verification link.

Don't try to change anything.

You can return an appropriate result such as:

```text
"Email is already verified."
```

However, be careful about what information you expose in security-sensitive contexts.

The important part is:

```text
already verified
→ don't create a new state transition
```

# 24. Invalidate Old Verification Tokens

Suppose:

```text
Token A
Token B
Token C
```

are all active.

A user clicks Token A.

If all remain valid, they can potentially be reused.

A simpler design is:

```text
New verification request
       ↓
Invalidate previous tokens
       ↓
Create one new token
```

So:

```text
A → invalid
B → invalid
C → active
```

This keeps the system easier to reason about.

---

# 25. Resend Rate Limiting

This endpoint is especially important to protect:

```http
POST /auth/resend-verification
```

Otherwise an attacker could repeatedly request emails to:

```text
victim@example.com
```

and cause an email flood.

So use:

```text
rate limit
+
cooldown
+
abuse protection
```

Potentially based on:

```text
IP
+
email/account
```

---

# 26. Don't Reveal Whether the Account Exists

Imagine:

```http
POST /auth/resend-verification
```

with:

```json
{
  "email": "victim@example.com"
}
```

If you respond:

```text
"Account doesn't exist."
```

you've created an account-enumeration endpoint.

Instead, use a generic response:

```text
"If an eligible account exists,
verification instructions will be sent."
```

This is the same principle we used for password reset.

# 27. Verification Token vs Access Token

These are completely different.

### Access token

Used for:

```text
API authentication
```

Example:

```text
Authorization: Bearer <access-token>
```

### Verification token

Used for:

```text
proving email ownership
```

They should not be treated as interchangeable credentials.

# 28. Don't Put Verification State in the JWT Forever

Suppose the access token contains:

```json
{
  "sub": "user_123",
  "emailVerified": false
}
```

The user verifies the email.

But the old access token still says:

```text
emailVerified = false
```

That's stale.

You could solve this by:

```text
new token
```

after verification.

Or avoid relying heavily on the JWT claim for authorization decisions and check current server-side state where necessary.

For our system, the simplest approach is:

```text
email verification
     ↓
refresh/re-authenticate
     ↓
new access token
```

There are two common designs.

### Option A

```text

 ↓

 ↓

```

### Option B

```text

 ↓

 ↓
Automatically create authenticated session
```

Better UX.

Neither is universally correct.

For our learning project, I recommend understanding both, but keeping authentication/session creation explicit.

# 30. If We Already Created a Session During Registration

Suppose registration does:

```text
Create User
 ↓
Create Session
 ↓
Issue Access Token
 ↓
Send verification email
```

Then the user already has a session.

After verification:

```text
emailVerified = true
```

The existing access token may still have:

```text
emailVerified = false
```

if that claim was included.

One clean solution:

```text
Verification success
 ↓
Revoke current session
 ↓
Create new session
 ↓
Issue fresh tokens
```

But this adds complexity.

Another:

```text
Verification success
 ↓
Existing session remains
 ↓
Server reads current user state when needed
```

The choice depends on how your authorization model is designed.

For the first version:

```text

 ↓

 ↓

```

After verification:

# 32. Middleware: `requireVerifiedEmail`

We can create:

```typescript
function requireVerifiedEmail(
  req,
  res,
  next
) {
  if (!req.user) {
    throw new UnauthorizedError();
  }

  if (!req.user.emailVerified) {
    throw new ForbiddenError(
      "Email verification required"
    );
  }

  next();
}
```

But remember:

`req.user.emailVerified` must come from a trustworthy source.

If it's only copied from an old JWT, it may be stale.

For important operations, current server-side state is safer.

# 41. Verification Link Security

Suppose an attacker obtains:

```text
verificationToken
```

They can potentially verify the email.

That's why the token needs:

```text
high entropy
short lifetime
single use
secure storage
```

But remember:

Email verification generally proves **mailbox control**, not that the person is the legal owner of the identity.

For higher assurance, you'd need stronger identity verification.

---

# 42. Don't Put Sensitive User Data in the Token

Avoid creating tokens containing:

```json
{
  "userId": "123",
  "email": "rahul@example.com",
  "role": "ADMIN"
}
```

especially if the token is simply encoded rather than cryptographically protected.

Use an opaque random token:

```text
4d9b...very-long-random-value
```

and resolve it server-side.

---

# 43. Verification Token Expiration

Database:

```text
createdAt
expiresAt
```

When verifying:

```text
expiresAt > now
```

must be true.

Don't trust:

```text
client-provided expiry
```

The server decides whether the token is valid.

# 44. Verification Token Replay

Suppose:

```text
Token A
```

was already used.

Attacker tries:

```text
Token A
```

again.

Database:

```text
usedAt != null
```

Therefore:

```text
❌ Reject
```

This is why one-time state is essential.

# 45. What Happens If the User Changes Their Email?

This is an important edge case.

Suppose:

```text
old email:
rahul@example.com

new email:
rahul2@example.com
```

The new email hasn't been verified yet.

We should generally:

```text
emailVerified = false
```

for the new address.

Then:

```text
Send verification token
 ↓
new email
 ↓
verify
```

The account shouldn't silently treat an unverified new address as trusted.

# 47. Don't Immediately Replace the Email

Suppose the user requests:

```text
newEmail = attacker@example.com
```

If you immediately change:

```text
user.email
```

before verifying it, you could accidentally create account-recovery problems.

A better design may temporarily store:

```text
pendingEmail
```

and only replace the actual email after verification.

For example:

```prisma
pendingEmail String?
```

Then:

```text
current email
+
pending email
```

until verification succeeds.

# 48. Verification After Email Change

```text

```


# 52. What If Email Sending Fails?

Important question.

Suppose:

```text
User created ✅
Verification token created ✅
Email sending ❌
```

Should registration fail?

There are multiple strategies.

### Strategy A

```text
Transaction-like registration
→ don't complete until email accepted
```

### Strategy B

```text
Create account
→ queue email
→ retry failed delivery
```

For production systems, asynchronous delivery with retry is often better.

But this requires queue infrastructure.

For our learning version:

```text
Create account
+
store verification token
+
attempt email
```

and provide:

```text
resend verification
```

as recovery.

---

# 53. Email Provider Failure Shouldn't Leak Secrets

If an email provider returns an error, don't return:

```text
SMTP password
API key
provider response containing internal details
```

to the frontend.

Return something generic:

```text
"Unable to send verification email. Please try again later."
```

And log the operational details securely on the server.

# 59. Interview Question

### "How would you implement email verification securely?"

A strong answer:

> After registration, I would generate a cryptographically secure random verification token and store only a hash of it along with the user ID, expiration time, and single-use state. I would send the raw token through a verification email. When the user submits the token, the backend hashes it and looks up a token that hasn't expired or been used. Inside a database transaction, it would mark the user's email as verified and consume the token. Verification and resend endpoints should be rate-limited, should not reveal whether an account exists, and raw verification tokens should never be logged.

That's a solid backend interview answer.
