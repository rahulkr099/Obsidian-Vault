# 🔐 Phase 4 — Lesson 4.15: OAuth 2.0 & Social Login Fundamentals

We've reached an important step in our authentication journey.

So far, our AI LMS has primarily used:

```text
Email
  +
Password
  +
MFA
  ↓
Our Authentication System
```

But users increasingly expect:

```text
Continue with Google
Continue with GitHub
Continue with Microsoft
```

Instead of asking users to create another password.

This is where **OAuth 2.0** comes in.

---

# 1. What Is OAuth 2.0?

OAuth 2.0 is primarily an **authorization framework**.

It allows one application to obtain limited access to resources controlled by a user without requiring the user to give the application their password.

For example:

```text
AI LMS
   ↓
"Login with Google"
   ↓
Google
   ↓
User authenticates with Google
   ↓
Google gives our application an authorization result
   ↓
AI LMS identifies/links the user
```

The most important idea:

> **Your application never needs the user's Google password.**

---

# 2. OAuth Is Not Originally an Authentication Protocol

This distinction is extremely important.

OAuth 2.0 answers:

> "Can this application obtain authorization from this user?"

For identity/login, we commonly use:

> **OpenID Connect (OIDC)** on top of OAuth 2.0.

So:

```text
OAuth 2.0
   ↓
Authorization
```

while:

```text
OpenID Connect
   ↓
Authentication / Identity
```

When someone says:

```text
"Login with Google"
```

the actual system generally involves:

```text
OAuth 2.0
+
OpenID Connect
```

---

# 3. The Actors

OAuth introduces several important actors.

### Resource Owner

Usually:

```text
User
```

### Client

Our application:

```text
AI LMS
```

### Authorization Server

For example:

```text
Google
```

### Resource Server

The API holding the user's resources.

For Google, this could be:

```text
Google APIs
```

So:

```text
User
 │
 ▼
AI LMS
 │
 ▼
Google Authorization Server
 │
 ▼
Google APIs
```

---

# 4. Our AI LMS as the Client

Suppose Rahul clicks:

```text
[ Continue with Google ]
```

Our LMS is the:

```text
OAuth Client
```

Google is the:

```text
Authorization Server
```

The user is:

```text
Resource Owner
```

---

# 5. Why OAuth Instead of Asking for a Google Password?

Imagine our LMS showed:

```text
Google email:
Google password:
```

This would be terrible.

The LMS would be asking users to give us credentials belonging to another service.

OAuth avoids this:

```text
AI LMS
   ↓
Google
   ↓
User authenticates directly with Google
   ↓
Google gives LMS an authorization result
```

Our application never sees the Google password.

---

# 6. The High-Level Flow

The modern flow we want to learn is:

```text
User
  ↓
AI LMS
  ↓
Google Authorization Endpoint
  ↓
User authenticates
  ↓
Google redirects back
  ↓
Authorization Code
  ↓
AI LMS Backend
  ↓
Exchange Code
  ↓
Tokens / Identity Information
  ↓
Find or create LMS user
  ↓
Create our own session
```

The important word is:

> **Authorization Code**

---

# 7. Authorization Code Flow

Let's walk through it carefully.

The user visits:

```text
GET /auth/google
```

Our backend redirects them to Google.

Something conceptually like:

```text
https://accounts.google.com/...
  ?client_id=...
  &redirect_uri=...
  &response_type=code
  &scope=...
  &state=...
```

The user then interacts with Google.

---

# 8. User Authenticates at Google

Google displays:

```text
Sign in with Google

Email
Password

[Continue]
```

The important point:

```text
Google handles authentication
```

not:

```text
AI LMS
```

Our LMS doesn't receive the Google password.

---

# 9. Consent

Depending on the requested scopes and Google's existing consent state, the user may see something like:

```text
AI LMS wants access to:

✓ Basic profile information
✓ Email address
```

The user can approve or deny.

This is an important OAuth principle:

> The user controls whether the client receives the requested authorization.

---

# 10. Redirect URI

After successful authorization, Google redirects the browser back to our application.

For example:

```text
https://lms.example.com/auth/google/callback?code=...
```

This URL is called the:

> **Redirect URI**

The authorization code is sent to this endpoint.

---

# 11. Why Redirect URIs Matter So Much

Suppose our legitimate callback is:

```text
https://lms.example.com/auth/google/callback
```

An attacker shouldn't be able to replace it with:

```text
https://attacker.example.com/callback
```

If authorization responses can be redirected to arbitrary attacker-controlled locations, OAuth can become dangerously insecure.

Therefore:

> Redirect URIs must be explicitly registered and validated.

---

# 12. Never Use Wildcard Redirect URIs Carelessly

Avoid configurations like:

```text
https://*.example.com/*
```

unless you fully understand the security implications.

Prefer exact registered redirect URIs:

```text
https://lms.example.com/auth/google/callback
```

For local development:

```text
http://localhost:5000/auth/google/callback
```

and production:

```text
https://api.lms.example.com/auth/google/callback
```

should be explicitly configured.

---

# 13. The Authorization Code

After Google authenticates the user:

```text
Google
   ↓
authorization code
   ↓
Browser
   ↓
AI LMS callback
```

The code is temporary.

It is not our application's normal login session.

This is an important distinction:

```text
Authorization Code
≠
Access Token
≠
AI LMS Session
```

---

# 14. Why Use a Code?

Imagine Google directly placed an access token in the browser redirect.

That creates additional exposure.

Instead:

```text
Google
 ↓
Short-lived authorization code
 ↓
Backend
 ↓
Secure token exchange
```

The backend performs the sensitive exchange.

This is why the Authorization Code flow is widely used.

---

# 15. Backend Exchanges the Code

Our callback:

```http
GET /auth/google/callback?code=abc...
```

receives the code.

The backend then contacts Google:

```text
AI LMS Backend
      ↓
Google Token Endpoint
      ↓
authorization_code
      ↓
Tokens
```

The browser doesn't need to directly perform the confidential token exchange.

---

# 16. Client Secret

Traditional OAuth clients can have:

```text
client_id
client_secret
```

The `client_id` identifies the application.

The `client_secret` authenticates the application to the provider where applicable.

For a confidential backend:

```text
GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET
```

should be stored securely.

Never:

```text
commit .env
```

to Git.

---

# 17. Backend vs Frontend

This is where architecture matters.

For our AI LMS, I recommend:

```text
React Frontend
       │
       ▼
Node/Express Backend
       │
       ▼
Google OAuth
```

The backend handles:

```text
authorization callback
code exchange
identity validation
account linking
session creation
```

The frontend should not receive Google's client secret.

---

# 18. PKCE

Now we reach one of the most important OAuth security mechanisms:

> **PKCE — Proof Key for Code Exchange**

Pronounced:

```text
"pixy"
```

PKCE protects the authorization-code flow against certain code interception attacks.

It is especially important for public clients such as mobile and browser-based applications, and is widely recommended for modern OAuth authorization-code flows.

---

# 19. The PKCE Idea

Before redirecting to Google, our client generates:

```text
code_verifier
```

A random secret.

Then calculates:

```text
code_challenge
```

from it.

Conceptually:

```text
Random code_verifier
        ↓
Hash / transform
        ↓
code_challenge
```

The authorization request sends:

```text
code_challenge
```

but the client keeps:

```text
code_verifier
```

secret.

---

# 20. PKCE Flow

```text
AI LMS
  │
  ├── generate code_verifier
  │
  ├── derive code_challenge
  │
  ▼
Google
  │
  │ user authenticates
  │
  ▼
Authorization Code
  │
  ▼
AI LMS
  │
  ├── authorization code
  └── code_verifier
  │
  ▼
Google Token Endpoint
  │
  ▼
Tokens
```

Google verifies that:

```text
code_verifier
```

matches the earlier:

```text
code_challenge
```

---

# 21. Why PKCE Helps

Suppose an attacker somehow obtains the authorization code.

They still don't have:

```text
code_verifier
```

Therefore:

```text
stolen authorization code
+
missing code_verifier
=
cannot successfully redeem it
```

This gives the authorization-code flow an additional protection layer.

---

# 22. `state` Parameter

Another extremely important OAuth concept:

> **The `state` parameter protects the OAuth flow against request forgery and login-CSRF-style attacks.**

When starting OAuth:

```text
AI LMS
   ↓
generate random state
   ↓
Google
```

The callback returns:

```text
code
+
state
```

Our application verifies:

```text
returned state
==
original state
```

If not:

```text
❌ reject
```

---

# 23. Why `state` Matters

Imagine an attacker creates an OAuth authorization response for **their** Google account.

They somehow trick Rahul's browser into visiting the callback.

Without proper state validation, the LMS could accidentally associate the attacker's OAuth identity with Rahul's application session/account.

This is one class of **login CSRF / account confusion** problems.

So:

```text
state
=
"This OAuth callback belongs to the login attempt I started."
```

---

# 24. `state` Must Be Unpredictable

Don't use:

```javascript
const state = "login";
```

or:

```javascript
const state = userId;
```

Use a cryptographically random value.

For example:

```typescript
import crypto from "node:crypto";

const state = crypto
  .randomBytes(32)
  .toString("hex");
```

Then bind it to the login attempt.

---

# 25. `state` vs PKCE

They solve different problems.

### `state`

Protects the OAuth transaction from:

```text
request forgery
login CSRF
```

### PKCE

Protects authorization-code redemption from:

```text
code interception
```

So modern OAuth flows often use:

```text
state
+
PKCE
```

not one instead of the other.

---

# 26. OAuth Scopes

When our LMS asks Google for access, it specifies:

```text
scope
```

For basic login, we want minimal identity information.

For example:

```text
openid
email
profile
```

With OpenID Connect:

```text
openid
```

is particularly important.

---

# 27. Principle of Least Privilege

Don't request:

```text
Google Drive
Google Calendar
Gmail
Contacts
YouTube
```

if all you need is:

```text
email
basic profile
```

Ask only for the permissions your application actually needs.

This is:

> **Least privilege**

and is a major security principle.

---

# 28. OAuth Access Token

After the code exchange, Google may issue an:

```text
access_token
```

This token allows the client/application to access permitted Google resources.

For example:

```text
Google access token
      ↓
Google API
```

It is **not** the same as:

```text
AI LMS access token
```

This distinction is extremely important.

---

# 29. Google Token vs Our Token

We might have:

```text
Google Access Token
       ↓
Google APIs
```

and:

```text
AI LMS Access Token
       ↓
AI LMS APIs
```

These are separate security domains.

Our application should not simply use Google's token as our own API authentication token.

Instead:

```text
Google authentication
       ↓
Identify user
       ↓
Create/link LMS account
       ↓
Create our own session
       ↓
Issue LMS tokens
```

---

# 30. ID Token

With OpenID Connect, we can also receive an:

> **ID Token**

This is typically a JWT containing identity-related claims.

Conceptually:

```json
{
  "iss": "https://accounts.google.com",
  "sub": "provider-user-id",
  "aud": "our-client-id",
  "email": "user@example.com",
  "email_verified": true
}
```

The exact claims and behavior depend on the provider and configuration.

---

# 31. Access Token vs ID Token

This is one of the most common OAuth interview questions.

### Access Token

Used to access APIs:

```text
Access Token
   ↓
Google API
```

### ID Token

Used by the client/application to learn about the authenticated identity in an OpenID Connect flow.

```text
ID Token
   ↓
Identity information
```

Therefore:

> **Don't treat an access token and an ID token as interchangeable.**

---

# 32. Don't Trust an ID Token Just Because It's a JWT

A common beginner mistake:

```text
JWT.decode(idToken)
```

and then:

```text
"Great, email is Rahul."
```

No.

Decoding is not verification.

You need to validate relevant claims and the token's cryptographic signature.

Important claims include things such as:

```text
iss
aud
exp
iat
sub
```

and, depending on the flow/provider:

```text
nonce
```

---

# 33. Important ID Token Claims

### `iss`

Issuer.

Example:

```text
https://accounts.google.com
```

Your backend should ensure the token came from the expected issuer.

### `aud`

Audience.

Should correspond to your OAuth client.

### `exp`

Expiration time.

Expired token:

```text
❌ reject
```

### `sub`

Stable provider-specific subject identifier.

This is extremely useful for identifying the provider account.

---

# 34. Use Provider `sub` as the External Identity

Suppose Google returns:

```text
sub = "109823749812..."
```

Don't rely only on:

```text
email
```

for permanently identifying the Google account.

Instead, store:

```text
provider = GOOGLE
providerSubject = "109823749812..."
```

This gives us a stable external identity mapping.

---

# 35. Social Account Model

Instead of adding:

```text
googleId
githubId
facebookId
microsoftId
```

directly to `User`, a scalable design is:

```prisma
model Account {
  id                String   @id @default(uuid())

  userId            String

  provider          String
  providerAccountId String

  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  @@unique([provider, providerAccountId])
  @@index([userId])
}
```

Then:

```text
User
 ├── Google Account
 ├── GitHub Account
 └── Microsoft Account
```

This is much more scalable.

---

# 36. Why the Unique Constraint?

We want:

```text
(provider, providerAccountId)
```

to be unique.

For example:

```text
GOOGLE + 123456
```

must map to only one LMS user.

Otherwise:

```text
Google account
     ↓
User A
User B
```

could create serious account confusion.

So:

```prisma
@@unique([provider, providerAccountId])
```

is important.

# 39. What If Email Already Exists?

This is one of the most dangerous account-linking situations.

Suppose Rahul already has:

```text
User
email = rahul@example.com
```

created using:

```text
email + password
```

Then he clicks:

```text
Continue with Google
```

Google returns:

```text
email = rahul@example.com
```

Should we automatically connect Google?

**Not blindly.**

Matching email alone can create account-linking risks depending on provider guarantees and application policy.

---

# 40. Safer Account Linking

A safer approach:

```text
Existing LMS account
       ↓
User authenticates normally
       ↓
Settings → Connected Accounts
       ↓
"Connect Google"
       ↓
Google OAuth
       ↓
Verify provider identity
       ↓
Link Account
```

Now the user has explicitly authenticated into the existing LMS account before linking the provider identity.

---

# 41. Account Linking

Our database becomes:

```text
User
 ├── Password authentication
 ├── Google Account
 └── GitHub Account
```

This is powerful because the same LMS user can have multiple authentication methods.

---

# 42. Don't Accidentally Create Duplicate Users

Bad design:

```text
Email login:
rahul@example.com
 ↓
User A
```

Then:

```text
Google:
rahul@example.com
 ↓
User B
```

Now:

```text
Rahul
 ├── User A
 └── User B
```

His courses, progress, certificates, and AI history could become split.

Therefore:

> Account identity and account linking need careful design.

---

# 43. Email Matching Is Not Enough

Suppose:

```text
LMS account:
rahul@example.com
```

and OAuth provider says:

```text
rahul@example.com
```

Even if the strings match, the application needs a trustworthy identity-linking policy.

Provider email verification status matters too.

But even a verified provider email doesn't automatically mean:

```text
"Always merge accounts."
```

Your application should deliberately define its account-linking rules.

---

# 44. Recommended LMS Policy

For our project:

### New OAuth user

```text
No matching external account
        ↓
If no LMS account exists
        ↓
Create LMS user
        ↓
Create provider account
```

### Existing provider account

```text
Provider account exists
        ↓
Find LMS user
        ↓
Login
```

### Existing email-only LMS account

```text
Same email
        ↓
Don't blindly merge
        ↓
Ask user to authenticate existing account
        ↓
Explicitly link provider
```

This is much safer.

---

# 45. OAuth Callback

Our route might be:

```text
GET /api/v1/auth/google/callback
```

The callback receives:

```text
code
state
```

Our backend should:

```text
1. Validate state
2. Validate OAuth transaction
3. Exchange code
4. Validate returned tokens/identity
5. Find or create/link account
6. Create LMS session
7. Redirect user to frontend
```

---

# 46. Don't Create the LMS Session Before OAuth Validation

Bad:

```text
Google callback
 ↓
Create LMS session
 ↓
Later validate Google token
```

Instead:

```text
Google callback
 ↓
Validate OAuth response
 ↓
Identify provider user
 ↓
Find/link LMS account
 ↓
Create session
```

Authentication should happen **before** issuing our session.

---

# 47. OAuth State Storage

Where should `state` live?

Options include:

```text
server-side session
Redis
secure short-lived cookie
database
```

For our architecture, a secure short-lived cookie or server-side session/challenge can work.

The important principle:

> The callback must be able to compare the returned `state` against the original login attempt.

Don't simply trust a state value sent by the browser without binding it to the initiated transaction.

---

# 48. State Cookie

For example:

```text
oauth_state = random_value
```

could be stored in a cookie with security attributes such as:

```text
HttpOnly
Secure
SameSite
short expiration
```

depending on the exact architecture.

Then callback:

```text
cookie state
     ==
query state
```

If not:

```text
❌ reject
```

---

# 49. PKCE Storage

Similarly, if using PKCE:

```text
code_verifier
```

must survive the redirect.

You can associate it with the login transaction using:

```text
secure cookie
server-side session
Redis
```

The exact choice depends on your architecture.

The important rule:

> The attacker should not be able to replace the verifier for an OAuth login attempt.

---

# 50. Nonce in OpenID Connect

Another important concept:

> **Nonce**

A nonce is a random value associated with an OIDC authentication request.

It helps detect replay/substitution of ID tokens.

Conceptually:

```text
Login start
 ↓
generate nonce
 ↓
Google
 ↓
ID Token
 ↓
validate nonce
```

So modern OIDC security can involve:

```text
state
+
PKCE
+
nonce
```

Each has a different role.

---

# 51. State vs Nonce vs PKCE

Memorize this table:

|Mechanism|Main purpose|
|---|---|
|`state`|Protect OAuth transaction / login CSRF|
|PKCE|Protect authorization code exchange|
|`nonce`|Bind OIDC ID token to the authentication request|

This distinction is excellent interview material.

# 54. Don't Put Provider Tokens in LocalStorage

A common mistake:

```javascript
localStorage.setItem(
  "googleAccessToken",
  token
);
```

For our LMS, there's generally no reason to expose or persist Google tokens in the frontend if our backend is handling the provider integration.

The browser should primarily have:

```text
LMS authentication state
```

not unnecessary third-party provider credentials.

# 56. OAuth Does Not Give Google LMS Permissions

Suppose Rahul logs in with Google.

That does **not** automatically mean:

```text

```

or:

```text

```

Google tells us about the external identity.

Our application determines:

```text

permissions
ownership
account status
```

This is critical.

---

# 57. Don't Trust Provider Data for Authorization

Never do:

```typescript
if (googleUser.email === "admin@example.com") {
  role = "ADMIN";
}
```

That's fragile.

Instead:

```text
Google identity
 ↓
LMS User
 ↓
Database role
 ↓
Authorization
```

Your application's database remains authoritative for application permissions.

# 60. OAuth Security Checklist

For a production-quality OAuth integration:

```text
□ Authorization Code flow
□ PKCE
□ state validation
□ nonce validation for OIDC
□ Exact redirect URI
□ Secure client credentials
□ Minimal scopes
□ Validate issuer
□ Validate audience
□ Validate expiration
□ Validate ID-token signature
□ Use provider subject as identity
□ Safe account linking
□ Don't trust frontend claims
□ Don't expose provider secrets
□ Rate-limit authentication endpoints
□ Create LMS session only after validation
```

### Mistake 10

```text
Creating LMS session before provider identity is validated
```

These are excellent interview talking points.

---

# 62. OAuth Attack Scenario

Let's understand a simplified login-CSRF scenario.

Attacker:

```text
Google Account
attacker@example.com
```

Attacker starts an OAuth flow and obtains an authorization response for their account.

Then somehow causes the victim to complete that response in the victim's browser.

If our application doesn't properly bind the OAuth callback to the login attempt:

```text
Victim browser
      ↓
OAuth callback
      ↓
Attacker's Google identity
      ↓
LMS session
```

The victim might unknowingly become logged into the attacker's account.

That's why:

```text
state
```

is so important.

---

# 63. Account Confusion

Another scenario:

```text
Rahul's LMS account
        │
        └── courses/progress
```

Attacker manipulates OAuth linking.

If the application accidentally links:

```text
attacker Google account
        ↓
Rahul LMS account
```

the attacker could gain access to Rahul's LMS account.

This is why:

```text
account linking
```

must be treated as a high-risk operation.

---

# 64. Explicit Account Linking

A good pattern:

```text
Rahul already logged in
        ↓
Settings
        ↓
Connected Accounts
        ↓
Connect Google
        ↓
OAuth
        ↓
Google identity validated
        ↓
Check provider account isn't linked elsewhere
        ↓
Create Account relation
```

Now the user explicitly initiated the linking.

---

# 65. Unlinking Accounts

Suppose Rahul has:

```text
Password
Google
GitHub
```

He wants to remove Google.

Should we allow it?

Maybe, but don't let users accidentally remove their **last authentication method**.

For example:

```text
Password ❌
Google ❌
GitHub ❌
```

could lock them out.

Therefore:

> Before unlinking an authentication method, ensure another secure authentication method remains available.

This is another excellent business/security invariant.

---

# 66. Example Invariant

```text
A user must retain at least one valid recovery/authentication
method unless they are intentionally deleting the account.
```

Depending on your system, this might mean:

```text
password
OR
OAuth account
OR
passkey
OR
another approved recovery mechanism
```

---

# 67. OAuth + Email Verification

Suppose Google says:

```text
email_verified = true
```

Should we set:

```text
LMS.emailVerified = true
```

?

Often yes, if the provider's identity and verification semantics meet your application's requirements.

But don't blindly assume every provider has identical semantics.

The backend should define a clear provider-specific policy.

---

# 68. OAuth and MFA

Another interesting point:

If the user authenticates through Google, Google may already have strong authentication/MFA on the provider side.

But:

```text
Google MFA
```

is not automatically:

```text
LMS MFA
```

Our LMS may still require:

```text
LMS MFA
```

for sensitive operations.

This is a policy decision.

---

# 69. Step-Up Authentication

Suppose Rahul logged in using Google.

Later he wants to:

```text
Change password
Disable MFA
Change email
Delete account
```

These are sensitive operations.

We may require:

```text
recent authentication
```

even though he already has an active session.

This is called:

> **Step-up authentication**

We'll use this concept repeatedly as our security architecture becomes more mature.

Our final mental model:

```text
                       USER

                         ▼
                    AI LMS Login

              ┌──────────┴──────────┐
              ▼                     ▼
         Email/Password           OAuth
              │                     │

           Verify                 Google
```

# 🧠 Interview Question

### "Explain OAuth login with Google."

A strong answer:

> I would use the OAuth 2.0 Authorization Code flow with OpenID Connect. The application redirects the user to Google with a registered redirect URI, appropriate scopes, a random state value, and PKCE. After authentication, Google redirects back with an authorization code. The backend validates the state and exchanges the code using the PKCE verifier. It then validates the returned OIDC identity, including the issuer, audience, expiration, signature, and provider subject. The application finds or creates the corresponding LMS account, or explicitly links the provider account to an existing authenticated user. Finally, the LMS creates its own session and access/refresh tokens. Google tokens are not used as LMS API tokens.

That's a very strong answer for a junior-to-mid backend interview.

# 🎯 Lesson 4.15 Takeaways

```text
1. OAuth 2.0 is primarily an authorization framework.

2. OpenID Connect builds authentication/identity on top of OAuth.

3. Use Authorization Code flow for modern server-side OAuth.

4. PKCE protects the authorization-code exchange.

5. state protects the OAuth transaction against request-forgery
   and login-CSRF-style attacks.

6. nonce helps bind an OIDC ID token to the authentication request.

7. Redirect URIs must be tightly controlled.

8. OAuth access tokens and LMS access tokens are different.

9. ID tokens must be properly validated, not merely decoded.

10. Use provider + provider subject as the external identity.

11. Don't automatically merge accounts just because emails match.

12. Explicit account linking is safer.

13. Never expose OAuth client secrets to the frontend.

14. Request only the scopes your application actually needs.

15. OAuth authentication should eventually create an LMS session.

16. Provider authentication does not determine your LMS roles.

17. Application roles and permissions remain controlled by your
    own database.

18. Account linking/unlinking is a security-sensitive operation.

19. Password reset and OAuth recovery must not accidentally
    bypass important security controls.

20. OAuth, MFA, sessions, RBAC, and ownership are separate layers.
```

The most important thing from this lesson is:

```text

  │

  ▼
OAuth / OIDC

  ▼

  ▼
```
