
---

# 1. The Problem Authentication Middleware Solves

Suppose we have:

```http
GET /api/v1/courses/my
Authorization: Bearer eyJ...
```

Our controller needs to know:

```text
Who is making this request?
```

It should **not** have to manually:

```text
extract JWT
verify JWT
decode claims
query session
find user
check account status
```

inside every controller.

Bad:

```typescript
async function getMyCourses(req, res) {
  const token = req.headers.authorization;

  // verify token
  // find session
  // find user
  // ...
}
```

Then every controller repeats the same security logic.

---

# 2. Middleware Gives Us a Security Boundary

Instead:

```text
GET /courses/my
       ↓
authenticate
       ↓
req.auth
       ↓
controller
```

The controller receives an already-authenticated request context.

For example:

```typescript
req.auth.userId
req.auth.sessionId
```

---

# 3. What Is `req.auth`?

We can define:

```typescript
interface AuthContext {
  userId: string;
  sessionId: string;
}
```

Then:

```typescript
req.auth = {
  userId: "user_123",
  sessionId: "session_456",
};
```

This means:

> The server has verified that this request is associated with this LMS user and session.

---

# 4. Very Important: `req.auth` Is Not the User Object

Don't immediately make:

```typescript
req.auth = user;
```

Instead keep authentication context separate.

For example:

```typescript
req.auth = {
  userId: "user_123",
  sessionId: "session_456",
};
```

while:

```text
User
 ├── id
 ├── email
 ├── role
 ├── status
 └── ...
```

is application data.

This separation makes the architecture cleaner.

---

# 5. Authentication Context

Think of:

```text
req.auth
```

as:

> **Who has been authenticated for this request?**

For example:

```text
userId
sessionId
```

Potentially:

```text
authMethod
```

if your application needs it.

---

# 6. User Data

Think of:

```text
req.user
```

as:

> **Information about the LMS user.**

For example:

```typescript
req.user = {
  id: "user_123",
  email: "rahul@example.com",
  role: "STUDENT",
  status: "ACTIVE",
};
```

But don't automatically load a huge user object on every request.

We'll discuss that shortly.

---

# 7. Why Not Put Everything in `req.auth`?

You might be tempted to do:

```typescript
req.auth = {
  userId,
  sessionId,
  email,
  role,
  permissions,
  subscription,
  name,
  avatar,
  ...
};
```

This creates several problems:

```text
stale data
large context
unclear ownership
too much database coupling
```

Keep authentication context minimal.

A good default:

```typescript
req.auth = {
  userId,
  sessionId,
};
```

# 10. Step 1 — Extract the Authorization Header

The request:

```http
Authorization: Bearer eyJhbGci...
```

Our middleware extracts:

```typescript
const header = req.headers.authorization;
```

Then validate the format.

Expected:

```text
Bearer <token>
```

---

# 11. Don't Accept Arbitrary Formats

Bad:

```typescript
const token = req.headers.authorization;
jwt.verify(token, secret);
```

Why?

Because the header contains:

```text
Bearer <token>
```

not just:

```text
<token>
```

We should parse it explicitly.

Conceptually:

```typescript
function extractBearerToken(
  header?: string
) {
  if (!header) {
    return null;
  }

  const [scheme, token] = header.split(" ");

  if (scheme !== "Bearer" || !token) {
    return null;
  }

  return token;
}
```

---

# 12. Don't Trust the Token Yet

After extracting:

```text
eyJ...
```

we still don't know whether it is valid.

The next step is:

```text
JWT verification
```

---

# 13. Decode vs Verify

This distinction is critical.

### Decode

```text
JWT
 ↓
read payload
```

doesn't prove authenticity.

### Verify

```text
JWT
 ↓
signature verification
 ↓
claims validation
```

proves that the token was correctly signed and satisfies the required token constraints.

Never use:

```javascript
jwt.decode(token)
```

as authentication.

---

# 14. JWT Verification

Our middleware needs to verify things such as:

```text
signature
expiration
issuer
audience
algorithm
```

Depending on the JWT library and architecture.

Conceptually:

```typescript
const payload = verifyAccessToken(token);
```

If verification fails:

```text
401 Unauthorized
```

---

# 15. Why 401?

HTTP status codes matter.

### 401 Unauthorized

Means:

> Authentication is missing or invalid.

Examples:

```text
No token
Expired token
Invalid token
Malformed token
```

### 403 Forbidden

Means:

> The user is authenticated, but doesn't have permission.

Example:

```text
Authenticated STUDENT
       ↓
POST /admin/users
       ↓
403 Forbidden
```

Memorize:

```text
401 → Who are you?
403 → I know who you are, but you can't do this.
```

---

# 16. Validate JWT Claims

Suppose the token is structurally valid.

We still need claims.

Our token might contain:

```json
{
  "sub": "user_123",
  "sid": "session_456",
  "iss": "ai-lms",
  "aud": "ai-lms-api",
  "iat": 1786710000,
  "exp": 1786710900
}
```

We need to validate these according to our token policy.

---

# 17. `sub`

We expect:

```text
sub = userId
```

For example:

```text
sub = user_123
```

If `sub` is missing:

```text
❌ reject
```

We need a valid subject to construct:

```typescript
req.auth.userId
```

---

# 18. `sid`

If our architecture uses session IDs:

```text
sid = session_456
```

Then:

```typescript
req.auth.sessionId = payload.sid;
```

If our token doesn't contain a session ID, we need a different architecture.

The important thing is consistency.

---

# 19. Issuer

Our access token might say:

```text
iss = "ai-lms"
```

The middleware verifies that it came from our expected issuer.

Why?

Imagine another service issues a JWT with:

```text
sub = user_123
```

If our API blindly trusts any valid JWT signed with an incorrectly shared key/configuration, identity confusion can occur.

Issuer validation helps define:

> Who is allowed to issue tokens for this API?

---

# 20. Audience

Our API may expect:

```text
aud = "ai-lms-api"
```

Then:

```text
aud !== "ai-lms-api"
```

means:

```text
❌ reject
```

This protects against accepting a token intended for a different service.

---

# 21. Algorithm Validation

Don't blindly accept whatever algorithm the token claims.

Your JWT verification configuration should explicitly allow the algorithm(s) your system uses.

Conceptually:

```typescript
verify(token, key, {
  algorithms: ["RS256"],
  issuer: "ai-lms",
  audience: "ai-lms-api",
});
```

The exact algorithm depends on our key architecture.

---

# 22. Symmetric vs Asymmetric JWT Signing

Two common approaches:

### HS256

```text
one secret
```

```text
AI LMS
 ├── signs
 └── verifies
```

### RS256

```text
private key
     ↓
sign

public key
     ↓
verify
```

For a distributed architecture, asymmetric signing can be attractive because verification services don't need the signing private key.

We'll study key management more deeply in the security phase.

# 23. After JWT Verification

Suppose we now have:

```text
sub = user_123
sid = session_456
```

We can build:

```typescript
req.auth = {
  userId: "user_123",
  sessionId: "session_456",
};
```

Now the request has an authentication context.

# 24. Should We Query PostgreSQL?

This is an important architectural decision.

Option A:

```text
JWT valid
 ↓
No DB query
 ↓
req.auth
```

Fast.

Option B:

```text
JWT valid
 ↓
Query Session
 ↓
Query User
 ↓
req.auth
```

More current server-side state.

Neither is universally correct.

We need to decide based on what our API needs.

---

# 25. When JWT Verification Alone Is Enough

Suppose:

```text
GET /public/courses
```

No authentication required.

For a normal authenticated endpoint:

```text
GET /profile
```

if we only need:

```text
userId
```

and the access token is trusted and short-lived, we may not need to load the entire user on every request.

For example:

```text
JWT
 ↓
verify
 ↓
req.auth.userId
 ↓
service
```

The service can query only what it needs.

---

# 26. When We Need Database State

Suppose the user is:

```text
SUSPENDED
```

but the JWT is still cryptographically valid.

The token might say:

```text
sub = user_123
```

but database says:

```text
status = SUSPENDED
```

If our API must immediately block suspended users, we need current server-side state.

Then:

```text
JWT
 ↓
Session/User lookup
 ↓
status check
 ↓
allow/reject
```

---

# 27. Session Revocation

Same problem.

Suppose:

```text
Access Token
expires in 10 minutes
```

User logs out.

We revoke:

```text
Session #456
```

But the access token might still technically be valid until expiration.

If every request checks the session:

```text
JWT
 ↓
session lookup
 ↓
revoked?
 ↓
reject
```

we get immediate revocation.

But we pay for a database/cache lookup.

---

# 28. The Tradeoff

### Pure stateless access-token validation

```text
Fast
+
scales easily
-
revocation isn't instant
-
user state may become stale
```

### Stateful session validation

```text
Immediate revocation
+
current account status
+
stronger control
-
additional lookup
-
more infrastructure
```

The right choice depends on the application.

# 29. Hybrid Approach

For our AI LMS, a practical architecture is:

```text
Access Token
      ↓
JWT verification
      ↓
req.auth
      ↓
Most endpoints continue
```

and for sensitive situations:

```text
JWT
 ↓
Session lookup
 ↓
User/account status
```

For example:

```text
Normal API
→ JWT only

Sensitive operation
→ JWT + current session/user state
```

This gives us a useful balance.

# 30. Cache Can Reduce the Cost

If we need current session state frequently:

```text
Request
 ↓
JWT
 ↓
Redis
 ↓
Session status
```

instead of:

```text
Request
 ↓
JWT
 ↓
PostgreSQL
```

We can later introduce Redis for high-volume session checks.

But don't add Redis just because it's popular.

Start simple.

# 31. Middleware Should Not Load Everything

A common mistake:

```typescript
async function authenticate(req, res, next) {
  const user = await userRepository.findById(...);

  req.user = user;

  next();
}
```

for every request.

Then:

```text
100 requests
 ↓
100 unnecessary User queries
```

This can become expensive.

Authentication middleware should do only what authentication requires.

---

# 32. Keep Middleware Focused

Good:

```text
authenticate
→ prove request is authenticated
→ establish req.auth
```

Then:

```text
requireRole
→ authorization
```

Then:

```text
loadUser
→ fetch user data if needed
```

This separation makes the pipeline easier to understand.

# 33. Authentication Middleware

Conceptually:

```typescript
async function authenticate(req, res, next) {
  try {
    const token =
      extractBearerToken(
        req.headers.authorization
      );

    if (!token) {
      throw new UnauthorizedError();
    }

    const payload =
      verifyAccessToken(token);

    req.auth = {
      userId: payload.sub,
      sessionId: payload.sid,
    };

    next();
  } catch {
    next(new UnauthorizedError());
  }
}
```

This is deliberately simple.

---

# 34. TypeScript Express Request Typing

TypeScript doesn't automatically know:

```text
req.auth
```

exists.

We should extend the Express request type.

For example:

```typescript
declare global {
  namespace Express {
    interface Request {
      auth?: AuthContext;
    }
  }
}
```

Then:

```typescript
interface AuthContext {
  userId: string;
  sessionId: string;
}
```

Now TypeScript understands:

```typescript
req.auth?.userId
```

---

# 35. Optional vs Required `req.auth`

Because not every route requires authentication:

```text
GET /health
```

might have:

```text
req.auth = undefined
```

But after:

```text
authenticate
```

we know it exists.

We can create a helper:

```typescript
function requireAuth(req: Request) {
  if (!req.auth) {
    throw new UnauthorizedError();
  }

  return req.auth;
}
```

Then controllers can safely use:

```typescript
const auth = requireAuth(req);

auth.userId
auth.sessionId
```

You may remember we previously used:

```text
req.user.userId
```

or:

```text
req.user.id
```

The problem is ambiguity.

Is `req.user`:

```text
database user?

```

Using:

```text
req.auth
```

I'd recommend:

```typescript
req.auth
```

for:


# 38. Don't Trust `req.body.userId`

Suppose:

```http
POST /courses
```

body:

```json
{
  "userId": "user_999",
  "title": "My Course"
}
```

Never use:

```typescript
const ownerId = req.body.userId;
```

for ownership.

Use:

```typescript
const ownerId = req.auth.userId;
```

The client controls:

```text
req.body
```

The server controls:

```text
req.auth
```

This is one of the most important security rules in backend development.

---

# 39. Example Ownership Vulnerability

Suppose Rahul is:

```text
user_123
```

He sends:

```json
{
  "userId": "admin_999"
}
```

If the backend trusts that field:

```text
Course owner = admin_999
```

Now Rahul has manipulated ownership.

Instead:

```typescript
const ownerId = req.auth.userId;
```

Result:

```text
Course owner = user_123
```

The client cannot choose the owner.

---

# 40. Never Trust Client Identity Headers

Don't do:

```http
X-User-Id: admin_123
```

and then:

```typescript
req.userId = req.headers["x-user-id"];
```

unless you're inside a carefully secured trusted-service architecture.

For normal browser requests:

```text
client-controlled headers
=
untrusted
```

Authentication identity must come from verified credentials.

---

# 41. `req.auth` Should Be Server-Created

The lifecycle should be:

```text
Client
 ↓
Bearer Token
 ↓
Authentication Middleware
 ↓
JWT Verification
 ↓
Server creates req.auth
```

Not:

```text
Client
 ↓
userId
 ↓
req.auth
```

That would destroy the entire purpose of authentication.

# 42. Authorization Middleware

Once we have:

```text
req.auth
```

we can implement authorization.

Example:

```typescript
function requireRole(role: Role) {
  return async (req, res, next) => {
    // load/check current user role
  };
}
```

Then:

```typescript
router.post(
  "/courses",
  authenticate,
  requireRole("INSTRUCTOR"),
  courseController.create
);
```

Pipeline:

```text
authenticate
     ↓
requireRole
     ↓
controller
```

# 43. Authentication vs Authorization

This distinction must become automatic in your mind.

### Authentication

```text
authenticate
```

asks:

> Who are you?

### Authorization

```text
requireRole
requirePermission
ownership check
```

asks:

> Are you allowed to do this?

# 45. Role Middleware Isn't Enough

Suppose:

```text

```

Rahul tries:

```text

```


Consider:

```typescript
router.post(
```

This is wrong.

`requireRole` runs before authentication.

Instead:

# 50. Validation vs Authentication

Suppose:

```http
POST /courses
```

body:

```json
{
  "title": ""
}
```

Should we validate the body before authentication?

Sometimes yes, sometimes no.

But for security-sensitive routes, you generally don't want expensive business processing to happen for unauthenticated requests.

A common practical order is:

```text
authentication
+
request validation
```

followed by:

```text
authorization/business logic
```

The exact order can depend on what information you need and whether validation itself can leak information.

---

# 51. Error Handling

Don't return detailed JWT errors.

Bad:

```json
{
  "error": "jwt expired at 2026-08-14T00:23:44"
}
```

This exposes unnecessary internal details.

Prefer:

```json
{
  "message": "Authentication required"
}
```

or a consistent authentication error response.

Detailed information should generally remain in server logs, not client responses.

---

# 52. Avoid Authentication Error Leaks

For login:

Bad:

```text
Email doesn't exist.
```

versus:

```text
Password is wrong.
```

This can help attackers enumerate accounts.

Prefer a generic response:

```text
Invalid email or password.
```

The same principle applies to authentication middleware.

---

```text
reason category
```

But don't log:

```text

```

Never.

# 55. `req.auth` and Service Layer

Should we pass the entire request into the service?

Avoid:

```typescript
courseService.create(req);
```

This couples the service to Express.

Instead:

```typescript
const auth = requireAuth(req);

await courseService.create({
  userId: auth.userId,
  title: req.body.title,
});
```

Now the service is framework-independent.

---

# 56. Controller Example

```typescript
async function createCourse(req, res) {
  const auth = requireAuth(req);

  const course = await courseService.create({
    ownerId: auth.userId,
    title: req.body.title,
  });

  res.status(201).json({
    data: course,
  });
}
```

The controller extracts the authenticated identity.

The service receives:

```text
ownerId
```

not:

```text
req
```

```typescript
async function createCourse(input) {

```

The service doesn't know:

```text

JWT
headers
cookies
```

That's good architecture.

# 59. Don't Put Authorization in the Repository

Avoid:

```typescript
courseRepository.delete(courseId, req.user.id);
```

The repository shouldn't know about:

```text
HTTP
JWT
roles
cookies
```

It should execute data operations.

Authorization policy belongs above it.

# 60. Resource Ownership Check

Suppose:

```text
DELETE /courses/:courseId
```

The controller gets:

```text
userId
courseId
```

The service can enforce:

```text
course.ownerId === userId
```

For example:

```typescript
async function deleteCourse({
  courseId,
  userId,
}) {
  const course =
    await courseRepository.findById(courseId);

  if (!course) {
    throw new NotFoundError("Course");
  }

  if (course.ownerId !== userId) {
    throw new ForbiddenError();
  }

  return courseRepository.delete(courseId);
}
```

This is authorization based on ownership.

---

# 61. Avoid IDOR

This protects against:

> **Insecure Direct Object Reference (IDOR)**

Imagine:

```text
/course/123
```

belongs to Rahul.

Rahul changes:

```text
/course/124
```

If the backend only checks:

```text
course exists?
```

Rahul might access someone else's course.

Instead:

```text
course exists?
+
user owns course?
```

Both must be checked.

# 62. Authentication Middleware Is Not Authorization

A common beginner mistake:

```text
authenticate
```

means:

```text
"user is allowed to do everything."
```

No.

It only establishes:

```text
this request belongs to user_123
```

Authorization still needs:

```text
role
permission
ownership
policy
```

---

# 63. `req.auth` Is a Security Boundary

Treat:

```text
req.auth.userId
```

as trusted **only because the server created it after authentication verification**.

But remember:

```text
req.auth
```

is only as trustworthy as the middleware that generated it.

If you accidentally do:

```typescript
req.auth = {
  userId: req.body.userId
};
```

you have destroyed the boundary.

---

# 64. Don't Allow Controllers to Override `req.auth`

Avoid:

```typescript
req.auth.userId = req.body.userId;
```

The authentication context should be immutable from the application perspective.

Conceptually:

```text
Token
 ↓
verify
 ↓
req.auth
 ↓
read-only identity
```

# 75. Current User Helper

A useful helper:

```typescript
function requireAuth(
  req: Request
): AuthContext {
  if (!req.auth) {
    throw new UnauthorizedError();
  }

  return req.auth;
}
```

Then:

```typescript
const { userId } = requireAuth(req);
```

This is cleaner than:

```typescript

   ...
}
```

in every controller.

# 🧠 Interview Question

### "How would you implement authentication middleware in Express?"

A strong answer:

> I would create centralized authentication middleware that extracts the Bearer access token, verifies its signature and required JWT claims such as issuer, audience, expiration, and subject, and then creates a server-controlled authentication context such as `req.auth = { userId, sessionId }`. I would not trust user IDs or roles from request bodies or headers. For routes requiring immediate session revocation or current account state, I would additionally validate the session against server-side state. Authentication and authorization would remain separate, and controllers would receive authenticated domain values rather than handling JWT logic directly.

That's a solid backend interview answer.

# 🎯 Lesson 4.18 Takeaways

```text
1. Authentication middleware establishes the identity of the request.

2. Use a centralized authenticate middleware.

3. Verify JWTs; never use decode() as authentication.

4. Validate signature, expiration, issuer, audience, and required
   claims.

5. Keep req.auth minimal.

6. Prefer:
   req.auth.userId
   req.auth.sessionId

7. Keep req.auth separate from the database User object.

8. Don't trust userId, role, or ownership information supplied by
   the client.

9. Authentication and authorization are separate layers.

10. 401 means authentication failed or is missing.

11. 403 means authentication succeeded but permission is insufficient.

12. Not every request needs a database user lookup.

13. Sensitive operations may require current session/account state.

14. Server-side session checks provide stronger revocation control.

15. Controllers should not directly parse or verify JWTs.

16. Services should receive domain values rather than Express req.

17. Repositories should not know about HTTP or JWTs.

18. Middleware ordering matters.

19. OAuth, password login, and future passkeys should all converge
   into the same API authentication middleware after session creation.

20. req.auth is a security boundary created by trusted server-side
   authentication logic.
```
