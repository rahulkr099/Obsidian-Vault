# 🔐 Phase 4 — Lesson 4.19: Authorization Architecture — RBAC, Permissions & Ownership

In the previous lesson we answered:

> **Who is making this request?**

Using:

```text
Authentication
      ↓
req.auth
      ↓
userId
sessionId
```

Now we answer the second question:

> **What is this user allowed to do?**

This is **authorization**.

---

# 1. Authentication vs Authorization

This distinction should become automatic for you.

### Authentication

```text
WHO are you?
```

Example:

```text
Rahul
userId = user_123
```

### Authorization

```text
WHAT are you allowed to do?
```

Example:

```text
Rahul can:
✓ enroll in courses
✓ submit assignments
✓ view lessons

Rahul cannot:
✗ delete another student's account
✗ create platform-wide roles
✗ manage system configuration
```

So:

```text
Authentication
      ↓
Identity
      ↓
Authorization
      ↓
Permissions
```

---

# 2. Our AI LMS Has Different Users

Let's start with:

```text
STUDENT
INSTRUCTOR
ADMIN
SUPER_ADMIN
```

For example:

```text

 ├── learn
 ├── enroll
 ├── submit assignments
 └── view own progress

Instructor
 ├── create courses
 ├── manage own courses
 ├── grade students
 └── view course analytics

Admin
 ├── manage users
 ├── moderate courses
 └── manage platform content

Super Admin
 └── platform-wide administration
```

But there's an important problem.

Roles alone aren't enough.

---

# 3. Why Roles Alone Become Messy

Suppose we write:

```typescript
if (user.role === "ADMIN") {
   ...
}
```

everywhere.

Soon we have:

```text
if ADMIN
if INSTRUCTOR
if STUDENT
if SUPER_ADMIN
if INSTRUCTOR || ADMIN
if ADMIN && VERIFIED
...
```

After several hundred endpoints, authorization becomes difficult to maintain.

Instead, we introduce **permissions**.

# 4. Permission-Based Thinking

Instead of:

```text

```

we ask:

```text

```

For example:

```text

COURSE_DELETE

USER_UPDATE
USER_SUSPEND

ENROLLMENT_CREATE
ENROLLMENT_READ

ASSIGNMENT_CREATE
ASSIGNMENT_GRADE

```

Now authorization becomes more explicit.

Example:

```text
 ↓
```

Another user:


# 7. But Here's the Problem

Suppose:

```text

```

and:

```text

```

Rahul has:

```text

```


# 8. Role + Permission + Ownership

The real decision is:

```text
Can user perform action?
```

depends on:

```text
Role
+
Permission
+
Resource ownership
+
Business rules
```

For example:

```text

Permission = COURSE_UPDATE
Course.ownerId = Rahul
```

→ allowed.

But:

```text
Rahul
Role = INSTRUCTOR
Permission = COURSE_UPDATE
Course.ownerId = Amit
```

→ denied.

# 23. `requirePermission()`

Conceptually:

```typescript
function requirePermission(permission: Permission) {
  return async (req, res, next) => {
    const auth = requireAuth(req);

    const allowed =
      await authorizationService.hasPermission(
        auth.userId,
        permission
      );

    if (!allowed) {
      return next(new ForbiddenError());
    }

    next();
  };
}
```

Notice:

```text
middleware
 ↓
authorization service
```

The middleware doesn't contain all authorization logic itself.

# 25. Ownership Check


```typescript
async function canUpdateCourse(
  userId: string,
  courseId: string

  if (!course) {
    throw new NotFoundError("Course");

```

# 26. Authorization Should Be Close to the Domain

The rule:

```text
Instructor can modify their own course
```

is a **business/domain rule**.

Therefore the service layer is a good place for it.

Example:

```typescript
async function updateCourse({
  userId,
  courseId,
  data,
}) {
  const course =
    await courseRepository.findById(courseId);

  if (!course) {
    throw new NotFoundError("Course");
  }

  if (course.ownerId !== userId) {
    throw new ForbiddenError();
  }

  return courseRepository.update(
    courseId,
    data
  );
}
```

---

# 27. Why Not Put Ownership in Middleware?

You could create:

```text

```

but now middleware needs to know:

```text

Database
Course ownership rules
```

This can become messy.

A useful rule:

> **Generic authorization belongs in middleware; resource-specific authorization usually belongs in the service/domain layer.**

# 31. Policy Function

Conceptually:

```typescript
function canUpdateCourse(
  user: User,
  course: Course
) {
  if (user.role === "SUPER_ADMIN") {
    return true;
  }

  if (user.role === "ADMIN") {
    return true;
  }

  if (user.role === "INSTRUCTOR") {
    return course.ownerId === user.id;
  }

  return false;
}
```

This is much clearer than scattered conditions.

# 43. Never Trust Role From JWT Forever




This is another reason access tokens should be short-lived.

```typescript
  typeof PERMISSIONS[keyof typeof PERMISSIONS];
```

Then:

```typescript

  permission: Permission

  // ...
}
```

Now TypeScript can catch:

```text

```

as a typo.

This is one of the places where TypeScript gives us real architectural value.

# 🧠 Interview Question

### "What is the difference between RBAC and resource ownership?"

A strong answer:

> RBAC determines what actions a user's role is generally allowed to perform. Ownership determines whether that user can perform the action on a specific resource. For example, an instructor may have the `COURSE_UPDATE` permission, but they should normally only be able to update courses they own. Therefore authorization often combines role or permission checks with resource-level ownership or policy checks.

---

# 🧠 Another Interview Question

### "Why is `requirePermission()` often better than hardcoding role checks?"

A strong answer:

> Roles are usually bundles of permissions. If an endpoint checks only for a specific role, adding another role with the same capability requires changing the endpoint. Permission-based authorization decouples the capability from the role. For example, both `INSTRUCTOR` and `CONTENT_EDITOR` could have `COURSE_CREATE`, allowing the endpoint to simply require that permission.

# 🎯 Lesson 4.19 Takeaways

```text
1. Authentication answers "Who are you?"

2. Authorization answers "What are you allowed to do?"

3. RBAC means Role-Based Access Control.

4. Roles should generally represent groups of permissions.

5. Permissions should use consistent names such as:
   COURSE_CREATE
   COURSE_UPDATE
   COURSE_DELETE

6. requireRole() is useful for simple role boundaries.

7. requirePermission() is more flexible for larger systems.

8. Authentication does not mean the user can access everything.

9. Resource ownership is separate from role permission.

10. An instructor may update courses they own but not another
    instructor's courses.

11. Ownership checks help prevent IDOR vulnerabilities.

12. Generic authorization can live in middleware.

13. Resource-specific authorization usually belongs in the
    service/domain layer.

14. Don't trust userId, role, or ownership information from the client.

15. req.auth.userId should be the source of authenticated identity.

16. Don't put every authorization rule into one giant service.

17. Start simple with User.role + permission mapping.

18. Move to database-backed Role/Permission models when requirements
    justify it.

19. Multi-tenant authorization can later add:
    Organization → Membership → Role → Permission.

20. AI conversations, learning progress, submissions, and other
    personal LMS data require strict ownership checks.

21. Authorization should be tested using an explicit permission matrix.

22. RBAC + permissions + ownership + policies gives us a much stronger
    authorization architecture than simple role checks.
```
