# 🔐 Phase 4 — Lesson 4.21: Authorization Policies & Ownership Patterns

In **4.19**, we learned the authorization model.

In **4.20**, we implemented the basic structure and testing strategy.

Now we're going one level deeper:

> **How do we design authorization policies that stay clean when the AI LMS becomes large?**

This is where authorization starts becoming real backend engineering rather than just:

```typescript
if (user.role === "ADMIN")
```

---

# 1. The Problem With Scattered Authorization

Imagine your project has 50 controllers.

You might start writing:

```typescript
if (user.role === "ADMIN") {
  // ...
}
```

Then:

```typescript
if (
  user.role === "ADMIN" ||
  user.role === "INSTRUCTOR"
) {
  // ...
}
```

Then:

```typescript
if (
  user.role === "INSTRUCTOR" &&
  course.ownerId === user.id
) {
  // ...
}
```

Then:

```typescript
if (
  user.role === "ADMIN" ||
  (
    user.role === "INSTRUCTOR" &&
    course.ownerId === user.id &&
    course.status !== "ARCHIVED"
  )
) {
  // ...
}
```

Soon authorization is scattered everywhere.

That's dangerous.

---

# 2. What We Want Instead

We want:

```text
                    Authorization
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
       Permissions     Policies      Ownership
            │             │             │
            └─────────────┼─────────────┘
                          ▼
                    Final Decision
```

Instead of controllers knowing all the rules.

---

# 3. Policy

A **policy** answers a specific authorization question.

For example:

```text
Can this user update this course?
```

or:

```text
Can this instructor view this student's progress?
```

or:

```text
Can this student access this assignment?
```

A policy should ideally be:

```text
focused
predictable
testable
domain-specific
```

---

# 4. Course Policy

Let's create:

```text
src/policies/course.policy.ts
```

Conceptually:

```typescript
export function canUpdateCourse(
  user: User,
  course: Course
): boolean {
  if (user.role === "SUPER_ADMIN") {
    return true;
  }

  if (user.role === "ADMIN") {
    return true;
  }

  if (user.role === "INSTRUCTOR") {
    return course.ownerId === user.id;
  }

  return false;
}
```

Now the rule lives in one place.

---

# 5. Controller Doesn't Need the Rule

The controller shouldn't contain:

```typescript
if (
  user.role === "ADMIN" ||
  (
    user.role === "INSTRUCTOR" &&
    course.ownerId === user.id
  )
) {
  // ...
}
```

Instead:

```typescript
if (!coursePolicy.canUpdate(user, course)) {
  throw new ForbiddenError();
}
```

Much easier to understand.

---

# 6. Why Policies Are Useful

Imagine the LMS eventually has:

```text
Course
Lesson
Assignment
Submission
Enrollment
Certificate
AIConversation
UploadedDocument
```

Each resource can have its own policies:

```text
course.policy.ts
lesson.policy.ts
assignment.policy.ts
submission.policy.ts
enrollment.policy.ts
certificate.policy.ts
ai-conversation.policy.ts
document.policy.ts
```

Now when you need to understand:

> Who can modify an AI conversation?

you know exactly where to look.

---

# 7. Policy Should Not Know About Express

Avoid:

```typescript
coursePolicy.canUpdate(req, res, course);
```

Instead:

```typescript
coursePolicy.canUpdate(user, course);
```

The policy should not care whether the request came from:

```text
Express
Fastify
GraphQL
CLI
background worker
```

This makes it reusable.

---

# 8. Policy Should Not Query Randomly

Ideally:

```typescript
canUpdateCourse(user, course)
```

receives the information it needs.

It shouldn't secretly perform:

```text
database query
database query
database query
```

inside a simple boolean function.

Bad:

```typescript
async function canUpdateCourse(userId, courseId) {
  const user = await ...
  const course = await ...
  const organization = await ...
  ...
}
```

Now policy logic is coupled to persistence.

A better pattern is:

```text
Service
 ↓
load required data
 ↓
Policy
 ↓
decision
```

---

# 9. Service + Policy

For example:

```typescript
async function updateCourse(input) {
  const user =
    await userRepository.findById(input.userId);

  const course =
    await courseRepository.findById(input.courseId);

  if (!course) {
    throw new NotFoundError("Course");
  }

  if (!coursePolicy.canUpdate(user, course)) {
    throw new ForbiddenError();
  }

  return courseRepository.update(
    course.id,
    input.data
  );
}
```

The responsibilities are clear:

```text
Repository
→ retrieves data

Policy
→ decides authorization

Service
→ coordinates operation
```

---

# 10. Policy Is a Decision Function

Think:

```text
Policy
=
Input
→ Decision
```

For example:

```text
User + Course
      ↓
canUpdateCourse()
      ↓
true / false
```

This makes policies extremely easy to test.

---

# 11. Policy Tests

Example:

```typescript
describe("canUpdateCourse", () => {
  it("allows an instructor to update own course", () => {
    expect(
      canUpdateCourse(
        instructor,
        ownCourse
      )
    ).toBe(true);
  });

  it("rejects instructor updating another course", () => {
    expect(
      canUpdateCourse(
        instructor,
        anotherCourse
      )
    ).toBe(false);
  });

  it("allows admin", () => {
    expect(
      canUpdateCourse(
        admin,
        anotherCourse
      )
    ).toBe(true);
  });

  it("rejects student", () => {
    expect(
      canUpdateCourse(
        student,
        ownCourse
      )
    ).toBe(false);
  });
});
```

These tests document your security rules.

---

# 12. Policy Tests Are Security Tests

Don't think:

```text
unit tests = functionality
security tests = something separate
```

Authorization policy tests are directly security-related.

If this test fails:

```text
Instructor A
→ can update Instructor B's course
```

you have a security vulnerability.

---

# 13. Ownership

Ownership is one of the most common authorization relationships.

For example:

```text
Course.ownerId
```

means:

```text
Course
  ↓
owned by
  ↓
User
```

Then:

```typescript
course.ownerId === user.id
```

can establish ownership.

---

# 14. Different Resources Have Different Owners

This is important.

### Course

```text
course.ownerId
```

### AI Conversation

```text
conversation.userId
```

### Submission

```text
submission.studentId
```

### Progress

```text
progress.userId
```

### Certificate

Could be:

```text
certificate.studentId
```

The field names don't have to be identical.

What matters is understanding the relationship.

---

# 15. Don't Create a Generic `ownerId` Everywhere Just for Consistency

You might think:

```text
Everything should use ownerId.
```

Not necessarily.

A domain model should use meaningful names.

For example:

```text
studentId
instructorId
createdById
issuedToUserId
```

can be clearer than forcing:

```text
ownerId
```

everywhere.

Database naming should describe the actual relationship.

---

# 16. Ownership Isn't Always Enough

Consider an assignment.

```text
Assignment
 └── courseId
```

Who can modify it?

Maybe:

```text
Instructor who owns course
```

But the assignment itself doesn't have:

```text
ownerId
```

So authorization becomes relational:

```text
User
 ↓
Instructor
 ↓
Course
 ↓
Assignment
```

This is called relationship-based authorization.

---

# 17. Relationship-Based Authorization

Suppose:

```text
Instructor A
    ↓
Course 101
    ↓
Assignment 501
```

Instructor A can update Assignment 501.

But:

```text
Instructor B
    ↓
Course 202
```

cannot update Assignment 501.

The rule is:

```text
user manages assignment's course
```

not:

```text
assignment.ownerId === user.id
```

---

# 18. Policy Example

```typescript
async function canUpdateAssignment({
  user,
  assignment,
  course,
}: {
  user: User;
  assignment: Assignment;
  course: Course;
}) {
  if (user.role === "ADMIN") {
    return true;
  }

  if (user.role !== "INSTRUCTOR") {
    return false;
  }

  return course.ownerId === user.id;
}
```

The service loads:

```text
Assignment
Course
User
```

and the policy decides.

---

# 19. Why This Matters for an LMS

An LMS is full of relationships:

```text
Student
 ↓
Enrollment
 ↓
Course
 ↓
Lesson
 ↓
Assignment
 ↓
Submission
```

Authorization often depends on these relationships.

For example:

> Can this instructor grade this submission?

The answer isn't simply:

```text
role === INSTRUCTOR
```

It might be:

```text
INSTRUCTOR
+
owns the course
+
submission belongs to that course
```

# 20. Submission Policy

Imagine:

```typescript
function canGradeSubmission(
  user,
  submission,
  course
) {
  if (user.role === "ADMIN") {
    return true;
  }

  if (user.role !== "INSTRUCTOR") {
    return false;
  }

  return course.ownerId === user.id;
}
```

Now the policy expresses the actual business relationship.

---

# 21. Student Access Policy

Suppose:

```text
GET /courses/:courseId/lessons/:lessonId
```

A student shouldn't necessarily access every lesson.

Maybe:

```text
Student
 ↓
Enrollment
 ↓
Course
 ↓
Lesson
```

The policy could require:

```text
course published
+
student enrolled
+
lesson available
```

This is no longer simple RBAC.

---

# 22. Course Access Policy

Conceptually:

```typescript
function canAccessCourse(
  user,
  course,
  enrollment
) {
  if (user.role === "ADMIN") {
    return true;
  }

  if (user.role === "INSTRUCTOR") {
    return course.ownerId === user.id;
  }

  if (user.role === "STUDENT") {
    return (
      course.status === "PUBLISHED" &&
      enrollment?.studentId === user.id
    );
  }

  return false;
}
```

Now authorization includes:

```text
role
+
ownership
+
enrollment
+
resource state
```

---

# 23. Authorization Can Depend on Resource State

This is a very important concept.

Suppose:

```text
Course.status = DRAFT
```

A student shouldn't access it.

After:

```text
Course.status = PUBLISHED
```

they can.

Therefore:

```text
authorization
```

can depend on:

```text
resource state
```

not just the user's identity.

---

# 24. Example

```text
Student
+
enrolled
+
course = DRAFT
```

→ deny.

```text
Student
+
enrolled
+
course = PUBLISHED
```

→ allow.

Same user.

Same role.

Different resource state.

---

# 25. Business Policy vs Permission

This distinction is important.

Permission:

```text
COURSE_READ
```

means:

> This user has the general capability to read courses.

Policy:

```text
canAccessCourse()
```

means:

> Can this user read this particular course right now?

These are different layers.

---

# 26. The Full Decision

```text
User
 ↓
Authentication
 ↓
Permission
 ↓
Resource
 ↓
Relationship
 ↓
Resource State
 ↓
Policy
 ↓
ALLOW / DENY
```

This is much closer to how real production authorization works.

---

# 27. Policy Return Values

A simple policy can return:

```typescript
true | false
```

But sometimes you want a reason.

For example:

```typescript
type AuthorizationResult =
  | { allowed: true }
  | {
      allowed: false;
      reason: "NOT_OWNER";
    };
```

Then:

```typescript
const result =
  coursePolicy.canUpdate(user, course);
```

This can be useful for logging and debugging.

But be careful not to expose internal authorization reasons to attackers.

---

# 28. Internal vs External Error Messages

Internally:

```text
NOT_OWNER
```

can be useful.

Externally:

```json
{
  "message": "You are not allowed to perform this action."
}
```

may be better.

Don't return:

```json
{
  "reason": "Course belongs to instructor_456"
}
```

because that can leak information.

---

# 29. Authorization Decision Object

A mature policy might return:

```typescript
{
  allowed: false,
  reason: "NOT_ENROLLED"
}
```

The service can:

```text
log reason
```

while the API returns:

```text
403
```

or possibly:

```text
404
```

depending on the resource.

---

# 30. Policy Composition

Sometimes you need multiple conditions.

For example:

```text
canUpdateCourse
=
hasPermission
+
isOwner
+
courseNotArchived
```

Conceptually:

```typescript
return (
  hasPermission &&
  isOwner &&
  !course.isArchived
);
```

This is policy composition.

---

# 31. Avoid Huge Boolean Expressions

Don't create:

```typescript
if (
  user.role === "ADMIN" ||
  user.role === "SUPER_ADMIN" ||
  (
    user.role === "INSTRUCTOR" &&
    course.ownerId === user.id &&
    course.status !== "ARCHIVED" &&
    user.status === "ACTIVE" &&
    organization.id === course.organizationId &&
    ...
  )
)
```

This becomes unreadable.

Instead:

```typescript
if (!userPolicy.isActive(user)) {
  return false;
}

if (!coursePolicy.canUpdate(user, course)) {
  return false;
}

return true;
```

Or use smaller policy functions.

---

# 32. Policy Naming

Use names that describe the action.

Good:

```text
canReadCourse
canUpdateCourse
canDeleteCourse
canPublishCourse
canGradeSubmission
canViewStudentProgress
canAccessAIConversation
```

Avoid vague:

```text
checkCourse
validateCourse
processCourseAccess
handleCourseSecurity
```

Specific names communicate intent.

---

# 33. Policies Should Be Deterministic When Possible

Given:

```text
user
course
```

the same state should generally produce:

```text
same decision
```

This makes them:

```text
easy to test
easy to reason about
easy to audit
```

Avoid hidden external dependencies where possible.

---

# 34. Time-Based Policies

Some authorization rules can depend on time.

Example:

```text
Assignment submission deadline
```

A student may submit:

```text
before deadline → allowed
after deadline → denied
```

This is technically authorization/business policy.

For example:

```typescript
function canSubmitAssignment(
  student,
  assignment,
  now
) {
  if (assignment.deadline < now) {
    return false;
  }

  return true;
}
```

Notice we explicitly pass:

```text
now
```

This makes the policy easier to test.

---

# 35. Why Pass `now`?

Instead of:

```typescript
new Date()
```

inside every policy:

```typescript
function canSubmitAssignment(
  student,
  assignment,
  now
)
```

Then tests can use:

```text
2026-08-14 10:00
```

or:

```text
2026-08-15 10:00
```

and verify behavior deterministically.

This is a small but powerful engineering technique.

---

# 36. AI LMS Example: Assignment

Suppose:

```text
Assignment
deadline = 10:00
```

Student requests submission at:

```text
09:55
```

Policy:

```text
enrolled?
+

+
```

→ allow.

At:


# 37. AI Conversation Policy

Our AI LMS might eventually allow:

```text
Student
 ├── create conversation
 ├── read own conversation
 ├── delete own conversation
```

But perhaps instructors can:

```text
view AI usage analytics
```

without reading the student's private conversation content.

This is an important distinction.

For example:

```text
ANALYTICS_READ
```

should not automatically mean:

```text
AI_CONVERSATION_READ_ALL
```

Use granular permissions.

---

# 38. Principle of Least Privilege

This is a core security principle:

> **Give users only the permissions they actually need.**

Bad:

```text
INSTRUCTOR
→ everything
```

Better:

```text
INSTRUCTOR
→ course management
→ assignment grading
→ course analytics
```

but not:

```text
user deletion
platform settings
security configuration
```

---

# 39. Permission Granularity

Too broad:

```text
COURSE_MANAGE
```

Maybe this allows:

```text
create
read
update
delete
publish
archive
```

But perhaps an instructor should:

```text
create
update
```

while only admins can:

```text
delete
publish
```

Therefore granular permissions can be useful:

```text
COURSE_CREATE
COURSE_UPDATE
COURSE_DELETE
COURSE_PUBLISH
COURSE_ARCHIVE
```

Don't make every possible action a permission automatically, though.

Choose granularity based on real policy differences.

---

# 40. Dangerous Permissions

Some permissions deserve extra attention:

```text
USER_DELETE
USER_SUSPEND
ROLE_ASSIGN
ROLE_REMOVE
PERMISSION_GRANT
PLATFORM_CONFIG_UPDATE
AUDIT_LOG_READ
```

These should usually be restricted to highly trusted roles.

---

# 41. Role Assignment Is Especially Sensitive

Suppose an admin can assign:

```text
SUPER_ADMIN
```

to another user.

That effectively gives the user platform-wide authority.

Therefore:

```text
ROLE_ASSIGN
```

should itself be protected.

You don't want:

```text
ADMIN
→ automatically
SUPER_ADMIN assignment
```

unless that's explicitly intended.

---

# 42. Prevent Privilege Escalation

A classic attack:

```text
Student
 ↓
changes request
 ↓
role = ADMIN
```

We already prevent this by not trusting client input.

But there are more subtle cases.

For example:

```text
Instructor
→ creates a role
→ gives itself ADMIN permissions
```

Authorization must protect the **authorization system itself**.

This is called preventing privilege escalation.

---

# 43. Self-Assignment

Be careful with:

```text
POST /roles
```

or:

```text
POST /users/:id/roles
```

An admin might be allowed to manage some roles but not higher-privileged roles.

Example policy:

```text
ADMIN
→ can assign STUDENT
→ can assign INSTRUCTOR

SUPER_ADMIN
→ can assign ADMIN
→ can assign SUPER_ADMIN
```

This is much safer.

---

# 44. Hierarchical Roles

You may be tempted to define:

```text
SUPER_ADMIN > ADMIN > INSTRUCTOR > STUDENT
```

and assume higher role automatically inherits everything.

This can work, but be careful.

Role hierarchies can become confusing.

A permission-based model is often easier to reason about:

```text
SUPER_ADMIN
→ permissions A, B, C...

ADMIN
→ permissions A, B...

INSTRUCTOR
→ permissions A...
```

Use inheritance only when it clearly simplifies the system.

---

# 45. Explicit Permission Sets

A safer model is:

```text
STUDENT
→ explicit permissions

INSTRUCTOR
→ explicit permissions

ADMIN
→ explicit permissions

SUPER_ADMIN
→ explicit permissions
```

Then changes are visible.

---

```text

```

with:


For example:

# 47. Authorization Review Checklist

Whenever you create an endpoint, ask:

```text
1. Is authentication required?

2. What permission is required?

3. What resource is being accessed?

4. Who owns the resource?

5. Can another relationship grant access?

6. Does resource state matter?

7. Does organization/tenant matter?

8. Can an admin bypass ownership?

9. What happens when authorization fails?

10. Do we have tests for another user's resource?
```

This checklist will prevent many security bugs.

# 🧠 Interview Question

### "Why should authorization policies be separated from controllers?"

A strong answer:

> Controllers should mainly translate HTTP requests into application operations. If authorization rules are embedded in controllers, they become scattered and tightly coupled to Express. Separating policies allows authorization rules to be reused by HTTP handlers, background jobs, tests, and other application entry points. It also makes security rules easier to review and test independently.

---

# 🧠 Interview Question

### "How would you authorize an instructor to grade a student's assignment?"

A strong answer:

> First authenticate the instructor. Then verify the instructor has the required grading permission. Next load the submission and its associated course. Finally, verify that the instructor is authorized to manage that course, typically through ownership or an instructor-course relationship. Only after those checks pass should the service perform the grading operation.

Notice the sequence:

```text
Authentication
 ↓
Permission
 ↓
Resource
 ↓
Relationship
 ↓
Action
```

# 🎯 Lesson 4.21 Takeaways

```text
1. Don't scatter authorization conditions across controllers.

2. A policy answers a specific authorization question.

3. Policies should be domain-focused and independently testable.

4. Policies should not depend on Express.

5. Prefer:
   service → load data → policy → decision

6. Ownership is only one type of authorization relationship.

7. LMS resources often use relationship-based authorization.

8. An instructor may manage a course and therefore its lessons,
   assignments, and submissions.

9. Resource state can affect authorization.

10. Permissions describe general capabilities.

11. Policies determine whether a capability applies to a specific
    resource and situation.

12. Use the principle of least privilege.

13. Protect role and permission management itself.

14. Prevent privilege escalation.

15. Be careful with SUPER_ADMIN.

16. Authorization should work outside HTTP when possible.

17. Policies should ideally be deterministic and easy to unit test.

18. Sensitive authorization failures should be logged carefully.

19. Don't expose internal authorization reasons to attackers.

20. Every protected endpoint should have a clear authorization
    contract.

21. For the AI LMS, authorization will frequently involve:
    User + Role + Permission + Resource + Relationship + State.

22. This architecture prepares us for future organization/tenant
    authorization without forcing us to implement it too early.
```
