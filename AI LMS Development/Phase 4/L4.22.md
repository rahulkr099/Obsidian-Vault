# 🔐 Phase 4 — Lesson 4.22: Authorization for Nested Resources

In **4.21**, we learned about policies, ownership, relationships, and resource state.

Now we're going to focus on one of the most important patterns for your AI LMS:

> **How do you authorize access when one resource belongs to another resource?**

Examples:

```text
Course
 └── Lesson

Course
 └── Assignment
      └── Submission

Course
 └── Enrollment

User
 └── AI Conversation
      └── AI Message
```

This is called **nested-resource authorization**.

---

# 1. The Core Problem

Suppose we have:

```http
PATCH /courses/course_123/lessons/lesson_456
```

The user isn't directly asking to modify just a lesson.

The relationship is:

```text
User
 ↓
Course
 ↓
Lesson
```

So we need to determine:

```text
Does the user have access to Course 123?
        ↓
Does Lesson 456 actually belong to Course 123?
        ↓
Is the user allowed to modify that lesson?
```

This is much more than:

```typescript
lesson.id === lessonId
```

---

# 2. Why Nested Resources Matter

An LMS naturally creates hierarchical relationships.

For example:

```text
Course
├── Module
│   ├── Lesson
│   ├── Lesson
│   └── Lesson
│
├── Assignment
│   └── Submission
│
└── Quiz
    └── Question
```

A request may identify a deeply nested resource:

```http
/courses/123/modules/5/lessons/20
```

The backend must verify that the relationships are real.

---

# 3. Never Trust the URL Hierarchy

This is a very important rule.

Suppose:

```text
course_123
lesson_456
```

The request is:

```http
PATCH /courses/course_123/lessons/lesson_456
```

You **cannot assume**:

```text
lesson_456 belongs to course_123
```

just because the URL says so.

The database must verify it.

---

# 4. The IDOR Problem

Imagine:

```text
Course A
 └── Lesson A
```

and:

```text
Course B
 └── Lesson B
```

An attacker could try:

```http
PATCH /courses/A/lessons/B
```

If your backend simply does:

```typescript
lessonRepository.findById("B")
```

and updates it, the attacker may modify a lesson belonging to another course.

That's an authorization vulnerability.

---

# 5. Correct Relationship Check

Instead of:

```typescript
findLessonById(lessonId)
```

we need something closer to:

```text
find lesson
WHERE
lesson.id = lessonId
AND
lesson.courseId = courseId
```

Now the database itself verifies the relationship.

---

# 6. Prisma Example

Suppose:

```prisma
model Lesson {
  id       String @id @default(uuid())
  title    String

  courseId String
  course   Course @relation(
    fields: [courseId],
    references: [id]
  )
}
```

We can query:

```typescript
const lesson = await prisma.lesson.findFirst({
  where: {
    id: lessonId,
    courseId,
  },
});
```

Now:

```text
lessonId = lesson_456
courseId = course_123
```

must match the same database record.

---

# 7. Why `findFirst()` Can Be Useful Here

We're not merely asking:

```text
Does lesson_456 exist?
```

We're asking:

```text
Does lesson_456 exist
AND
does it belong to course_123?
```

Therefore:

```typescript
findFirst({
  where: {
    id: lessonId,
    courseId,
  },
});
```

is a natural query.

If no record is returned:

```text
Not found / inaccessible
```

depending on your API policy.

---

# 8. Authorization Flow

For:

```http
PATCH /courses/:courseId/lessons/:lessonId
```

we can use:

```text
Request
 ↓
Authentication
 ↓
Permission
 ↓
Course + Lesson relationship
 ↓
Course authorization
 ↓
Lesson policy
 ↓
Update
```

This is the pattern to remember.

---

# 9. Parent Resource Authorization

Suppose:

```text
Course 123
ownerId = instructor_1
```

and:

```text
Lesson 456
courseId = 123
```

Instructor 1 wants to update Lesson 456.

The authorization chain is:

```text
Instructor 1
      ↓
owns Course 123
      ↓
Course 123 contains Lesson 456
      ↓
can manage Lesson 456
      ↓
ALLOW
```

The lesson inherits its management authority from the course relationship.

---

# 10. Instructor B

Now:

```text
Instructor 2
```

requests:

```http
PATCH /courses/123/lessons/456
```

Even though:

```text
Instructor 2
```

might have:

```text
LESSON_UPDATE
```

the course belongs to:

```text
Instructor 1
```

Therefore:

```text
DENY
```

This is why permissions alone aren't enough.

---

# 11. Permission + Relationship

The complete rule might be:

```text
LESSON_UPDATE
+
Instructor manages parent Course
+
Lesson belongs to Course
```

Only then:

```text
ALLOW
```

---

# 12. Service Implementation

A clean service could look conceptually like:

```typescript
async function updateLesson({
  userId,
  courseId,
  lessonId,
  data,
}: UpdateLessonInput) {

  const lesson =
    await lessonRepository.findByCourseAndId(
      courseId,
      lessonId
    );

  if (!lesson) {
    throw new NotFoundError("Lesson");
  }

  const course =
    await courseRepository.findById(courseId);

  if (!course) {
    throw new NotFoundError("Course");
  }

  const user =
    await userRepository.findById(userId);

  if (!lessonPolicy.canUpdate(
    user,
    lesson,
    course
  )) {
    throw new ForbiddenError();
  }

  return lessonRepository.update(
    lessonId,
    data
  );
}
```

---

# 13. But We Can Improve This

We might not need to load everything separately.

Suppose the lesson query includes the course:

```typescript
const lesson =
  await prisma.lesson.findFirst({
    where: {
      id: lessonId,
      courseId,
    },
    include: {
      course: true,
    },
  });
```

Now we have:

```text
lesson
 └── course
```

and can check:

```typescript
lesson.course.ownerId === userId
```

This reduces unnecessary queries.

---

# 14. But Don't Optimize Too Early

There are two reasonable designs:

### Clear version

```text
load lesson
load course
check policy
```

### Optimized version

```text
load lesson + course
check policy
```

Start with the clearer implementation.

Optimize when profiling shows the query pattern matters.

---

# 15. Repository Method

Since you're following:

```text
Controller
    ↓
Service
    ↓
Repository
```

we could create:

```typescript
lessonRepository.findByCourseAndId(
  courseId,
  lessonId
);
```

This is better than exposing Prisma details throughout your services.

---

# 16. Repository

Conceptually:

```typescript
async function findByCourseAndId(
  courseId: string,
  lessonId: string
) {
  return prisma.lesson.findFirst({
    where: {
      id: lessonId,
      courseId,
    },
  });
}
```

The repository handles:

```text
Prisma
query structure
database access
```

The service handles:

```text
authorization
business rules
workflow
```

---

# 17. Nested Resource Does Not Always Mean Nested URL

You could have:

```http
/courses/:courseId/lessons/:lessonId
```

or:

```http
/lessons/:lessonId
```

Both can be valid.

The important part is the authorization relationship, not the URL structure.

---

# 18. When Nested URLs Are Useful

Nested URLs communicate hierarchy:

```http
/courses/123/lessons/456
```

This tells the client:

> Lesson 456 is being accessed in the context of Course 123.

This can make APIs easier to understand.

---

# 19. When Nested URLs Become Too Deep

Avoid things like:

```http
/courses/1/modules/2/lessons/3/assignments/4/questions/5/submissions/6
```

This becomes difficult to maintain.

A better API may use:

```http
/submissions/6
```

while internally verifying:

```text
Submission
 ↓
Assignment
 ↓
Course
 ↓
User authorization
```

The database relationship can be deep without forcing the URL to be deep.

---

# 20. Rule of Thumb

Use nesting when the parent provides useful context.

For example:

```http
/courses/:courseId/lessons
```

makes sense.

But:

```http
/courses/:courseId/lessons/:lessonId
```

might be enough.

Don't keep nesting indefinitely.

---

# 21. Nested Creation

Consider:

```http
POST /courses/:courseId/lessons
```

The user wants to create a lesson.

The backend should:

```text
authenticate
 ↓
COURSE_CREATE / LESSON_CREATE permission
 ↓
load Course
 ↓
authorize Course management
 ↓
create Lesson with courseId from URL
```

Important:

Don't accept:

```json
{
  "courseId": "another-course"
}
```

from the client and blindly use it.

The route already establishes the intended parent:

```text
/course_123/lessons
```

and the backend should verify that parent.

---

# 22. Never Let Body Override URL Ownership

Suppose:

```http
POST /courses/course_A/lessons
```

body:

```json
{
  "title": "My lesson",
  "courseId": "course_B"
}
```

Don't do:

```typescript
const courseId = req.body.courseId;
```

Instead:

```typescript
const courseId = req.params.courseId;
```

The body shouldn't be allowed to redefine the relationship.

---

# 23. Even Better: Don't Accept Parent ID in Body

For nested creation:

```http
POST /courses/course_A/lessons
```

body:

```json
{
  "title": "Introduction to React"
}
```

Server:

```typescript
const courseId = req.params.courseId;
```

Then:

```text
Lesson.courseId = courseId
```

This is safer and cleaner.

---

# 24. Nested Deletion

Suppose:

```http
DELETE /courses/123/lessons/456
```

We should verify:

```text
Lesson 456 belongs to Course 123
```

before deleting.

Never:

```typescript
deleteLesson(lessonId);
```

without considering the parent relationship.

---

# 25. Database-Level Relationship

Our schema:

```prisma
model Course {
  id      String   @id @default(uuid())
  title   String
  lessons Lesson[]
}

model Lesson {
  id       String @id @default(uuid())
  title    String

  courseId String
  course   Course @relation(
    fields: [courseId],
    references: [id]
  )
}
```

This gives PostgreSQL a real relationship:

```text
Course.id
   ↑
Lesson.courseId
```

The database prevents orphaned lessons unless you explicitly configure cascading behavior.

---

# 26. Cascade Deletion

Suppose a course is deleted.

What happens to its lessons?

Possible policies:

```text
Course deleted
    ↓
Lessons deleted
```

or:

```text
Course deleted
    ↓
Lessons retained
```

For an LMS, the first might make sense in some situations, but you should be careful.

If courses have:

```text
submissions
progress
certificates
analytics
```

deleting everything can be destructive.

---

# 27. Soft Delete

Instead of physically deleting:

```text
Course
```

we might use:

```prisma
deletedAt DateTime?
```

Then:

```text
deletedAt = null
```

means active.

```text
deletedAt = timestamp
```

means deleted/archived.

This is often safer for educational data.

---

# 28. Authorization + Soft Delete

Suppose:

```text
Course.deletedAt != null
```

Then:

```text
Student → cannot access
Instructor → maybe can restore
Admin → can manage
```

Again, resource state affects authorization.

---

# 29. Parent Authorization Can Be Inherited

Suppose:

```text
Instructor
 ↓
owns Course
 ↓
owns Lessons through Course
```

We can define:

```text
canManageCourse(user, course)
```

and then:

```text
canManageLesson(user, lesson, course)
```

could rely on the course policy.

For example:

```typescript
function canUpdateLesson(
  user: User,
  course: Course
) {
  return coursePolicy.canUpdate(
    user,
    course
  );
}
```

This avoids duplicating:

```text
ADMIN
SUPER_ADMIN
INSTRUCTOR
ownership
```

logic in every child resource.

---

# 30. Policy Reuse

Imagine:

```text
Course
 ├── Lesson
 ├── Assignment
 ├── Quiz
 └── Module
```

All of these are managed by the course owner.

Instead of four separate implementations:

```text
lessonPolicy
assignmentPolicy
quizPolicy
modulePolicy
```

each repeating:

```text
user.role === ADMIN
OR
course.ownerId === user.id
```

we can reuse:

```text
coursePolicy.canManage()
```

Then child policies focus only on child-specific rules.

---

# 31. Example

```typescript
function canUpdateAssignment(
  user: User,
  assignment: Assignment,
  course: Course
) {
  if (!coursePolicy.canManage(user, course)) {
    return false;
  }

  if (assignment.status === "LOCKED") {
    return false;
  }

  return true;
}
```

Now we have:

```text
Parent authorization
+
Child-specific rule
```

Clean.

---

# 32. Student Side

The same concept works for students.

Suppose:

```text
Student
 ↓
Enrollment
 ↓
Course
 ↓
Assignment
```

To submit an assignment:

```text
student authenticated
        ↓
assignment exists
        ↓
assignment belongs to course
        ↓
student enrolled in course
        ↓
assignment is open
        ↓
deadline not passed
        ↓
ALLOW
```

This is a complete authorization/business policy.

---

# 33. Don't Mix All These Checks in the Controller

Avoid:

```typescript
if (!req.user) ...

if (req.user.role !== "STUDENT") ...

const course = ...

if (!course) ...

const enrollment = ...

if (!enrollment) ...

if (assignment.deadline < new Date()) ...

if (assignment.status !== "OPEN") ...
```

This creates a giant controller.

Instead:

```text
Controller
 ↓
Service
 ↓
Policy
```

---

# 34. Service Example

```typescript
async function submitAssignment({
  userId,
  assignmentId,
  content,
}) {
  const assignment =
    await assignmentRepository.findWithCourse(
      assignmentId
    );

  if (!assignment) {
    throw new NotFoundError("Assignment");
  }

  const enrollment =
    await enrollmentRepository.findByStudentAndCourse(
      userId,
      assignment.courseId
    );

  if (
    !assignmentPolicy.canSubmit({
      userId,
      assignment,
      enrollment,
    })
  ) {
    throw new ForbiddenError();
  }

  return submissionRepository.create({
    assignmentId,
    studentId: userId,
    content,
  });
}
```

This is much easier to reason about.

---

# 35. Policy

```typescript
function canSubmit({
  userId,
  assignment,
  enrollment,
}: {
  userId: string;
  assignment: Assignment;
  enrollment: Enrollment | null;
}) {
  if (!enrollment) {
    return false;
  }

  if (assignment.status !== "OPEN") {
    return false;
  }

  if (
    assignment.deadline &&
    assignment.deadline < new Date()
  ) {
    return false;
  }

  return enrollment.studentId === userId;
}
```

We would improve the `new Date()` issue by passing a `now` value, as discussed in 4.21.

---

# 36. Relationship Checks Should Be Explicit

Don't make authorization assumptions like:

```text
"He's enrolled, so he can access everything."
```

Maybe the student is enrolled in:

```text
Course A
```

but requesting:

```text
Assignment from Course B
```

The relationship must be checked:

```text
Enrollment.courseId === Assignment.courseId
```

# 37. Relationship Chain

For the assignment example:

```text
studentId
    │
    ▼
Enrollment
    │
 courseId
    │
    ▼
 Course
    │
    ▼

```

The authorization decision depends on the entire chain.

# 38. Prisma Query for Relationship

We could query enrollment:

```typescript
const enrollment =
  await prisma.enrollment.findUnique({
    where: {
      studentId_courseId: {
        studentId,
        courseId,
      },
    },
  });
```

assuming:

```prisma
@@unique([studentId, courseId])
```

This is a good example of how **database constraints support authorization**.

---

# 39. Authorization Through Unique Constraints

Suppose:

```prisma
model Enrollment {
  studentId String
  courseId  String

  @@unique([studentId, courseId])
}
```

Now there can only be one enrollment for:

```text
student + course
```

This simplifies our authorization logic.

We can ask:

```text
Does this relationship exist?
```

If yes:

```text
student is enrolled in course
```

---

# 40. Database Design and Authorization Are Connected

This is an important backend insight.

Good database modeling makes authorization easier.

For example:

```text
Enrollment
studentId
courseId
```

allows us to answer:

```text
Is student X enrolled in course Y?
```

efficiently.

Similarly:

```text
Course.ownerId
```

answers:

```text
Does instructor X own course Y?
```

Database design isn't separate from authorization design.

---

# 41. Nested Resource Authorization Pattern

You can memorize this:

```text
1. Authenticate user
2. Validate IDs
3. Load parent/resource relationship
4. Verify relationship exists
5. Check permission
6. Apply policy
7. Perform operation
```

Depending on the endpoint, steps 5 and 6 may happen before or after some lookups.

The key is:

> **Never perform the protected operation before the authorization decision.**

---

# 42. Authorization Before Sensitive Data Exposure

Be careful about:

```typescript
const submission =
  await repository.findById(id);

res.json(submission);
```

If the authorization check happens **after** serialization or logging, you may accidentally expose data.

Prefer:

```text
lookup
 ↓
authorize
 ↓
return data
```

And don't log sensitive objects before authorization.

---

# 43. Nested Resources and API Design

Good:

```http
GET /courses/123/lessons
```

Useful because:

```text
we're asking for lessons belonging to course 123
```

Also good:

```http
GET /lessons/456
```

when the lesson ID is globally unique.

What matters most is that your backend consistently verifies relationships when they affect authorization.

---

# 44. Avoid Ambiguous APIs

Bad:

```http
POST /update-course-lesson
```

with body:

```json
{
  "courseId": "...",
  "lessonId": "...",
  "userId": "..."
}
```

Too much authority is being delegated to client input.

Better:

```http
PATCH /courses/:courseId/lessons/:lessonId
```

and derive:

```text
userId
```

from authentication.

---

# 45. Never Accept `userId` for Ownership

This deserves repeating.

Bad:

```json
{
  "userId": "user_123"
}
```

and then:

```typescript
const userId = req.body.userId;
```

Better:

```typescript
const userId = requireAuth(req).userId;
```

The client tells us:

```text
what resource they want
```

but authentication tells us:

```text
who they are
```

---

# 46. Nested Authorization and Mass Assignment

Suppose:

```http
PATCH /courses/123/lessons/456
```

body:

```json
{
  "title": "New title",
  "courseId": "course_999",
  "ownerId": "user_999"
}
```

If you blindly spread:

```typescript
{
  ...req.body
}
```

you could allow the client to change ownership or relationships.

Instead, whitelist fields:

```typescript
const data = {
  title: req.body.title,
  description: req.body.description,
};
```

This connects authorization with **input validation and mass-assignment protection**.

---

# 47. Relationship Fields Should Usually Be Server-Controlled

Fields such as:

```text
courseId
studentId
ownerId
createdById
organizationId
```

should generally be controlled by the server according to the operation.

For example:

```text
POST /courses/:courseId/lessons
```

The server determines:

```text
courseId = req.params.courseId
createdById = req.auth.userId
```

The client doesn't get to choose those trusted relationships arbitrarily.

# 49. Don't Expose Storage Keys

Even if authorization succeeds, don't necessarily return:

```text

```

Instead generate a controlled access mechanism, such as a short-lived signed URL when using object storage.

This is another example of:

```text

+

+
```

working together.

# 50. Deep Authorization

Consider:

```text
Organization
 ↓
Course
 ↓
Module
 ↓
Lesson
 ↓
Assignment
 ↓
Submission
```

You don't necessarily want to perform six authorization queries for every request.

Instead, identify the **minimum relationship chain** needed to make the decision.

For example:

```text
Submission
 ↓
Assignment
 ↓
Course.ownerId
```

may be enough.

Don't load the entire object graph.

---

# 51. Authorization Query Design

Bad:

```text
load organization
load user
load course
load module
load lesson
load assignment
load submission
```

just because the resources are related.

Better:

```text
load submission
with assignment.course.ownerId
```

if that is all the policy requires.

Authorization should be precise.

---

# 52. Example Prisma Query

Conceptually:

```typescript
const submission =
  await prisma.submission.findUnique({
    where: {
      id: submissionId,
    },
    include: {
      assignment: {
        include: {
          course: {
            select: {
              ownerId: true,
            },
          },
        },
      },
    },
  });
```

Now we can determine:

```text
submission
 ↓
assignment
 ↓
course.ownerId
```

without retrieving unnecessary data.

---

# 53. Select Only What You Need

Security and performance both benefit from:

```typescript
select: {
  ownerId: true
}
```

instead of:

```typescript
include: {
  course: true
}
```

if you only need ownership.

This reduces:

```text
data transfer
memory
accidental exposure
```

---

# 54. Authorization and Data Minimization

This is an underrated security principle.

If the policy only needs:

```text
course.ownerId
```

don't retrieve:

```text
course.description
course.internalNotes
course.analytics
course.aiSettings
```

Authorization queries should retrieve the minimum information necessary.

# 🧠 Interview Question

### "How would you secure a nested endpoint like `/courses/:courseId/lessons/:lessonId`?"

A strong answer:

> I would not trust the URL hierarchy itself. First I would authenticate the user and check the required permission. Then I would query the lesson using both the lesson ID and course ID to verify that the lesson actually belongs to that course. After that I would apply the course or lesson authorization policy, such as verifying that the instructor owns the course or that the student is enrolled. Only after those checks succeed would I perform the operation.

# 🎯 Lesson 4.22 Takeaways

```text
1. Nested resources create authorization relationships.

2. Never assume a child resource belongs to the parent simply
   because both IDs appear in the URL.

3. Verify parent-child relationships in the database.

4. Example:
   lesson.id + lesson.courseId

5. Permissions alone aren't enough.

6. A user may have LESSON_UPDATE but still not be allowed to
   update every lesson.

7. Parent authorization can often determine child authorization.

8. Course ownership can determine access to its lessons,
   assignments, modules, and quizzes.

9. Student authorization often depends on Enrollment.

10. Nested resource creation should derive relationship IDs
    from trusted route/authentication context.

11. Never allow client input to arbitrarily change:
    ownerId
    userId
    courseId
    organizationId

12. Avoid excessively deep REST URLs.

13. Deep database relationships don't require deeply nested URLs.

14. Use repository methods that express relationship queries clearly.

15. Retrieve only the fields required for authorization.

16. Relationship constraints such as:
    @@unique([studentId, courseId])
    can simplify authorization.

17. Authorization and database design are closely connected.

18. Nested authorization is especially important for:
    courses
    lessons
    assignments
    submissions
    progress
    AI conversations
    uploaded documents

19. Always test cross-parent and cross-user access.

20. The server must derive the authenticated user identity;
    never trust userId from the request body.
```
