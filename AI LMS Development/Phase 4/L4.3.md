# 🔐 Phase 4 — Lesson 4.3: Password Hashing

Now we reach one of the most important parts of authentication:

> **How do we safely store passwords?**

The rule is simple:

```text
❌ Never store plaintext passwords
❌ Never encrypt passwords for normal authentication
❌ Never use plain SHA-256 for passwords

✅ Use a password-hashing algorithm designed for passwords
```

For our AI LMS, we'll use this lesson to understand the concepts first, then implement them in the next authentication steps.

---

# 1. The Basic Problem

Suppose a user registers:

```text
Email:
rahul@example.com

Password:
MyPassword123
```

A beginner might do:

```text
User
├── email
└── password = "MyPassword123"
```

This is extremely dangerous.

If the database is leaked:

```text
Database breach
      ↓
Users' passwords exposed
```

The attacker immediately has the actual passwords.

And the damage can extend beyond your LMS because users often reuse passwords on other websites.

---

# 2. What We Want Instead

We want:

```text
Password
   ↓
Password Hashing Algorithm
   ↓
Password Hash
   ↓
Database
```

So instead of:

```text
password = "MyPassword123"
```

we store something resembling:

```text
passwordHash = "$argon2id$..."
```

The important property is:

> **You should not be able to recover the original password from the stored hash.**

---

# 3. Hashing vs Encryption

This distinction is extremely important.

## Encryption

Encryption is designed to be reversible.

```text
Plaintext
   ↓
Encryption
   ↓
Ciphertext
   ↓
Decryption
   ↓
Plaintext
```

You have a key that allows you to recover the original data.

Useful for things like:

```text
Sensitive files
Messages
Stored secrets
```

---

## Hashing

Hashing is designed to be one-way.

```text
Password
   ↓
Hash function
   ↓
Hash
```

You don't normally do:

```text
Hash
 ↓
Original password
```

Instead, when the user logs in:

```text
Submitted password
       ↓
Password verification
       ↓
Stored password hash
       ↓
Match?
```

Therefore:

```text
Encryption
→ reversible

Password hashing
→ intentionally one-way
```

---

# 4. Why Can't We Just Use SHA-256?

You may already know:

```javascript
crypto.createHash("sha256")
```

and think:

```text
password
   ↓
SHA-256
   ↓
store hash
```

This is **not a good password-storage strategy**.

Why?

Because SHA-256 is designed to be extremely fast.

That's great for many cryptographic applications.

But for passwords, we actually want hashing to be **expensive enough** that an attacker cannot cheaply test billions of guesses.

---

# 5. The Attacker's Perspective

Imagine an attacker gets:

```text
email
passwordHash
```

They don't necessarily need to reverse the hash mathematically.

They can simply try passwords:

```text
password1
password2
password123
qwerty
letmein
...
```

For each guess:

```text
Guess
 ↓
Hash
 ↓
Compare with stolen hash
```

If the hashing algorithm is extremely fast:

```text
Millions/billions of guesses
        ↓
Very quickly
```

That's bad.

---

# 6. Password Hashing Should Be Expensive

Password hashing algorithms are deliberately designed to make guessing more expensive.

Conceptually:

```text
Normal hash:

Password
   ↓
Very fast
   ↓
Hash
```

Password hashing:

```text
Password
   ↓
Expensive computation
   ↓
Hash
```

The goal is:

```text
Legitimate login
→ acceptable delay

Attacker
→ enormous cost for millions/billions of guesses
```

This is one of the fundamental ideas behind password security.

---

# 7. Salt

Now we introduce another important concept:

> **Salt**

A salt is a unique random value associated with a password hash.

Conceptually:

```text
Password
   +
Random Salt
   ↓
Password Hashing Algorithm
   ↓
Password Hash
```

For example:

```text
Password:
hello123

Salt:
random-value-A

        ↓

Hash:
...
```

Another user might have:

```text
Password:
hello123

Salt:
random-value-B

        ↓

Hash:
...
```

Even though the passwords are identical, the resulting hashes should be different.

---

# 8. Why Do We Need Salt?

Imagine two users have:

```text
User A → password123
User B → password123
```

Without unique salts:

```text
User A → same hash
User B → same hash
```

An attacker can identify users with the same password.

With salts:

```text
User A
password123 + saltA
        ↓
hashA

User B
password123 + saltB
        ↓
hashB
```

Now:

```text
hashA ≠ hashB
```

This makes precomputed attacks such as rainbow-table attacks much less useful.

---

# 9. Does the Salt Need to Be Secret?

No.

This is a common misunderstanding.

The salt does not need to be hidden like a password.

Conceptually:

```text
Database
├── passwordHash
└── salt information
```

Modern password-hashing formats generally encode the salt and the algorithm parameters inside the stored hash string.

The important secret is:

```text
Password
```

not:

```text
Salt
```

---

# 10. Modern Password Hashing Algorithms

Some important algorithms are:

```text
Argon2
bcrypt
scrypt
PBKDF2
```

For modern applications, **Argon2id** is an excellent choice when available.

We'll focus primarily on:

```text
Argon2id
```

and also understand:

```text
bcrypt
```

because you'll encounter bcrypt frequently in existing Node.js projects.

---

# 11. Why Argon2id?

Argon2 was designed specifically for password hashing.

One of its major advantages is that it can require not only CPU work but also memory.

Conceptually:

```text
Password
   ↓
Argon2id
   ├── CPU cost
   ├── Memory cost
   └── Time cost
```

This makes large-scale password guessing more expensive.

The `id` variant is generally the recommended Argon2 variant for password storage.

---

# 12. Memory-Hard Hashing

This is a valuable concept to understand.

A traditional computation might mainly require:

```text
CPU
```

But Argon2 can deliberately require substantial:

```text
Memory + CPU
```

Imagine an attacker has:

```text
GPU
GPU
GPU
GPU
GPU
```

They might be able to perform huge numbers of simple computations.

But if each password guess requires significant memory:

```text
Guess
 ↓
Memory allocation
 ↓
Computation
 ↓
Result
```

scaling the attack becomes more expensive.

That's the idea behind **memory-hard password hashing**.

---

# 13. Work Factor

A password hashing algorithm usually has configurable parameters.

Conceptually:

```text
Password
   ↓
Hashing cost
   ↓
Hash
```

Higher cost:

```text
More secure against guessing
        +
More expensive for your server
```

Lower cost:

```text
Faster login
        +
Cheaper for attackers
```

Therefore we're trying to find a sensible balance.

---

# 14. Don't Pick Parameters Randomly

You might see tutorials saying:

```text
Use cost = 10
```

or:

```text
Use cost = 12
```

Don't blindly copy those numbers.

Hardware changes.

Your production server may be very different from:

```text
Your laptop
```

So password-hashing parameters should be **benchmarked on the environment where your application runs**.

The principle is:

> Make password verification expensive enough to resist guessing while keeping normal authentication responsive.

---

# 15. Registration Flow

Now let's apply this to our LMS.

User sends:

```json
{
  "email": "rahul@example.com",
  "password": "MyStrongPassword"
}
```

Our server does:

```text
Request
   ↓
Validate password
   ↓
Hash password
   ↓
Create user
   ↓
Store passwordHash
```

Database:

```text
User
├── email
└── passwordHash
```

Not:

```text
User
├── email
└── password
```

---

# 16. Login Flow

Now the user logs in.

They send:

```text
email
password
```

The server:

```text
Find user
   ↓
Retrieve passwordHash
   ↓
Verify submitted password
   ↓
Match?
```

If yes:

```text
Authentication successful
```

If no:

```text
Authentication failed
```

Notice something important:

We don't need to know the original password.

---

# 17. Password Verification Is Not "Hash and Compare"

A common simplified explanation is:

```text
hash(inputPassword) === storedHash
```

Conceptually this is okay, but with modern password-hashing algorithms the actual verification process also needs to use the parameters and salt encoded in the stored hash.

The library handles that for us.

So think:

```text
submittedPassword
        ↓
password verifier
        ↓
stored password hash
        ↓
true / false
```

rather than manually implementing the cryptographic process.

---

# 18. Example With Argon2

In Node.js, a common package is:

```bash
npm install argon2
```

Then conceptually:

```javascript
import argon2 from "argon2";

const passwordHash = await argon2.hash(password);
```

You store:

```text
passwordHash
```

For verification:

```javascript
const valid = await argon2.verify(
  passwordHash,
  password
);
```

The result:

```text
true
```

or:

```text
false
```

The important point is:

> **Let a well-maintained password-hashing library handle the cryptographic details.**

Don't implement Argon2 yourself.

---

# 19. Argon2id

When using Argon2, we generally want:

```text
Argon2id
```

rather than manually experimenting with the other Argon2 variants.

Conceptually:

```javascript
const hash = await argon2.hash(password, {
  type: argon2.argon2id
});
```

The exact cost parameters should be benchmarked and configured appropriately for your deployment environment.

---

# 20. What Does the Stored Hash Contain?

A modern password-hash string can contain information about:

```text
Algorithm
Salt
Cost parameters
Derived hash
```

Conceptually:

```text
$algorithm$parameters$salt$hash
```

Therefore, you don't necessarily need separate database columns like:

```text
salt
memoryCost
timeCost
```

for a standard Argon2 encoded hash.

The encoded hash can contain the necessary verification information.

---

# 21. Password Validation vs Password Hashing

These are different responsibilities.

### Validation

Before hashing:

```text
Is the password acceptable?
```

For example:

```text
Minimum length
Maximum length
Possibly password-breach checks
```

### Hashing

After validation:

```text
Convert password into a secure stored representation.
```

Architecture:

```text
Password
   ↓
Validation
   ↓
Hashing
   ↓
Database
```

Don't confuse:

```text
password validation
```

with:

```text
password security
```

A password being 12 characters long doesn't make a plaintext password safe to store.

---

# 22. Don't Overdo Password Rules

You might be tempted to create:

```text
At least:
1 uppercase
1 lowercase
1 number
1 special character
1 Sanskrit character
1 mathematical symbol
...
```

This doesn't automatically make authentication secure.

Modern password guidance generally emphasizes:

```text
Long passwords/passphrases
+
Block known-compromised passwords
+
Secure password hashing
+
Rate limiting
```

rather than forcing users through unnecessarily complicated composition rules.

For our LMS, we'll prioritize **length and compromised-password defenses** over arbitrary complexity rules.

---

# 23. Password Length and DoS

There is another subtle issue.

Imagine someone sends:

```text
password = "A" repeated 10 million times
```

If your server spends huge resources hashing it, attackers could abuse password hashing as a computational DoS vector.

Therefore:

```text
Request
   ↓
Password length limit
   ↓
Hashing
```

is important.

This is another reason validation happens **before** expensive operations.

---

# 24. Never Log Passwords

This sounds obvious, but accidental logging happens.

Never do:

```javascript
console.log(req.body);
```

when the body contains:

```json
{
  "email": "rahul@example.com",
  "password": "secret"
}
```

Because your logs could become another source of credential leakage.

Instead:

```text
Logging
   ↓
Remove sensitive fields
   ↓
Store safe information
```

For example:

```text
Login attempt
userId
requestId
IP metadata
result
```

while avoiding the actual password.

---

# 25. Don't Return Password Hashes

Even though the hash isn't the plaintext password, there's usually no reason for your API to expose it.

Bad:

```json
{
  "id": "...",
  "email": "...",
  "passwordHash": "$argon2id$..."
}
```

Good:

```json
{
  "id": "...",
  "email": "...",
  "role": "STUDENT"
}
```

A useful architectural habit is to define explicit **safe user response objects** instead of accidentally returning the entire database record.

---

# 26. What If the Database Is Stolen?

Suppose:

```text
Attacker
   ↓
Database breach
   ↓
passwordHash
```

A strong password-hashing strategy means the attacker still has to perform expensive password guesses.

That's why we use:

```text
Salt
+
Memory-hard / slow password hashing
+
Strong parameters
```

But remember:

> Password hashing reduces the impact of a database breach. It does not make a breach harmless.

Attackers may still crack weak passwords.

---

# 27. Password Reuse

Imagine Rahul uses:

```text
MyPassword123
```

on:

```text
LMS
GitHub
Email
Banking
```

If the LMS database is compromised and the password is cracked, the attacker may try it elsewhere.

Therefore, authentication security includes more than hashing:

```text
Password hashing
+
Rate limiting
+
MFA where appropriate
+
Breach-password detection
+
Session security
```

We'll gradually cover these.

# 29. Where Password Hashing Belongs

Remember our architecture:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Prisma
    ↓
PostgreSQL
```

Where should password hashing happen?

A good design is:

```text
Controller
    ↓
Auth Service
    ↓
Password Hashing
    ↓
Repository
    ↓
Prisma
```

The repository's job is primarily data access.

The authentication service owns authentication-related business logic.

So:

```text
❌ Controller hashes password
❌ Repository decides password policy

✅ Authentication Service coordinates password hashing
```

This keeps responsibilities clean.

---

# 30. A Better Internal Structure

As our project grows, something like this could make sense:

```text
src/
├── modules/
│   └── auth/
│       ├── auth.controller.ts
│       ├── auth.service.ts
│       ├── auth.repository.ts
│       ├── auth.routes.ts
│       ├── auth.schema.ts
│       └── auth.types.ts
│
└── shared/
    └── security/
        └── password.ts
```

Then:

```text
auth.service.ts
        ↓
password.ts
        ↓
Argon2
```

This gives us a reusable security utility without putting cryptographic code into controllers.

---

# 31. Why Not Hash Password in Prisma Middleware?

You might encounter patterns like:

```text
Prisma middleware
     ↓
Automatically hash password
```

It can look convenient.

But there are trade-offs.

Authentication logic can become hidden inside database behavior.

For a learning project focused on backend architecture, I prefer making the flow explicit:

```text
Auth Service
    ↓
Hash password
    ↓
Repository
    ↓
Database
```

It's easier to reason about and test.

The same hashing rule applies after password reset.

Never:

```text
Reset password
      ↓

```


# 34. Common Beginner Mistakes

### Mistake 1

```javascript
user.password = password;
```

❌ Never.

---

### Mistake 2

```javascript
crypto
  .createHash("sha256")
  .update(password)
  .digest("hex");
```

❌ Not appropriate as your password-storage algorithm.

---

### Mistake 3

```javascript
const encrypted = encrypt(password);
```

❌ Passwords generally don't need reversible encryption.

---

### Mistake 4

```javascript
console.log(password);
```

❌ Never log credentials.

---

### Mistake 5

```javascript
return user;
```

❌ Be careful about returning database records containing `passwordHash`.

---

### Mistake 6

Using an extremely low hashing cost because:

```text
"Login should be super fast."
```

❌ You're optimizing the wrong side of the security trade-off.

---

### Mistake 7

Using extremely expensive parameters without benchmarking.

```text
Every login = huge CPU/memory usage
```

❌ This can hurt your own application and potentially create a DoS risk.

---

# 35. Argon2 vs bcrypt

You'll encounter both.

|Feature|Argon2id|bcrypt|
|---|---|---|
|Designed for passwords|✅|✅|
|Memory-hard|✅|Limited|
|Common in Node projects|Increasingly common|Very common|
|Modern choice|Excellent|Still widely used|
|Good to know|⭐⭐⭐⭐⭐|⭐⭐⭐⭐|

For **our new LMS**, I'd prefer:

```text
Argon2id
```

But you should absolutely understand bcrypt because you'll see it in existing projects, tutorials, codebases, and interviews.

---

# 36. What About PBKDF2?

PBKDF2 is another established password-derived key/password hashing approach.

It is still used in many systems and can be configured with a large iteration count.

So you may encounter:

```text
Argon2id
bcrypt
scrypt
PBKDF2
```

The key lesson isn't:

> "Only one algorithm is allowed."

The key lesson is:

> **Use a well-established password-hashing/KDF algorithm with properly chosen parameters rather than inventing your own scheme.**

# 🧠 Interview Question

### "Why shouldn't you use SHA-256 to store passwords?"

A strong answer:

> SHA-256 is designed to be a fast general-purpose cryptographic hash. Password storage needs a deliberately expensive and preferably memory-hard algorithm so that large-scale password guessing becomes costly. Algorithms such as Argon2id, bcrypt, scrypt, and appropriately configured PBKDF2 are designed for this purpose and use salts and tunable work factors.

That's the level of understanding we're aiming for.

# 🎯 Lesson 4.3 Takeaways

Remember these:

```text
1. Never store plaintext passwords.

2. Password hashing is different from encryption.

3. Don't use plain SHA-256 as a password-storage strategy.

4. Salts make identical passwords produce different hashes.

5. Argon2id is an excellent modern choice.

6. Password hashing should be intentionally expensive.

7. Hashing parameters should be benchmarked for your environment.

8. Validate password size before expensive hashing.

9. Never log passwords or expose password hashes through APIs.

10. Password hashing belongs in authentication/security logic,
    not in controllers or random database code.
```

The core idea:

```text
             PASSWORD
                 │
                 ▼
          Input Validation
                 │
                 ▼
             Argon2id
                 │
                 ▼
           passwordHash
                 │
                 ▼
             PostgreSQL
```

And on login:

```text
Submitted Password
        │
        ▼
   Verify Against
   Stored Hash
        │
   ┌────┴────┐
   ▼         ▼
Invalid    Valid
   │         │
  401       Session
```
