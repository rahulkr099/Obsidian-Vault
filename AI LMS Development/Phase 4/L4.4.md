Our goal:

> Build a registration system where a user can safely create an account without being able to manipulate their role or expose sensitive information.

# 1. The Registration Endpoint

We'll create:

```http
POST /api/v1/auth/register
```

The client sends:

```json
{
  "name": "Rahul Kumar",
  "email": "rahul@example.com",
  "password": "StrongPassword123!"
}
```

The server should eventually respond with something like:

```json
{
  "success": true,
  "data": {
    "user": {
      "id": "user-id",
      "name": "Rahul Kumar",
      "email": "rahul@example.com",
      "role": "STUDENT"
    }
  }
}
```

Notice what is **missing**:

```text
password
passwordHash
```

We never expose those.

# 3. Step 1 — Define the Registration Input

The client should only be allowed to provide fields that actually belong to registration.

For example:

```typescript
interface RegisterInput {
  name: string;
  email: string;
  password: string;
}
```

Notice there is no:

```typescript
role
```

No:

```typescript
passwordHash
```

No:

```typescript
emailVerifiedAt
```

No:

```typescript
id
```

Those are **server-controlled fields**.

---

# 4. Never Trust Client-Controlled Privileges

A malicious client could send:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123!",
  "role": "ADMIN"
}
```

If your backend does:

```typescript
const user = await prisma.user.create({
  data: req.body
});
```

you have a serious security problem.

The client just tried to assign itself administrative privileges.

Instead:

```text
Client
  ↓
Allowed fields only
  ↓
Server assigns role
  ↓
STUDENT
```

The database default can help:

```prisma
role UserRole @default(STUDENT)
```

But don't rely on the client to omit malicious fields.

Your validation/schema should reject or strip fields that aren't part of the registration contract.

---

# 5. Step 2 — Validate the Request

We already learned request validation in Phase 2.

Registration should validate:

```text
name
email
password
```

For example:

```text
name
 ├── required
 ├── string
 └── reasonable length

email
 ├── required
 ├── string
 └── valid format

password
 ├── required
 ├── string
 ├── minimum length
 └── maximum length
```

Remember:

```text
Validation
    ≠
Security
```

Validation prevents malformed input.

Password hashing protects stored credentials.

Both are necessary.

---

# 6. Password Maximum Length

We discussed this in Lesson 4.3.

You don't want someone sending:

```text
password = "A" repeated 50 million times
```

and forcing your server to spend excessive resources hashing it.

So:

```text
Password
   ↓
Length validation
   ↓
Hash
```

not:

```text
Password
   ↓
Hash enormous input
   ↓
Validate afterward
```

Validation should happen before expensive operations.

---

# 7. Step 3 — Normalize the Email

Suppose the user submits:

```text
"  Rahul@Example.COM  "
```

We can normalize the basic representation:

```text
"rahul@example.com"
```

For our application, a reasonable baseline is:

```typescript
const email = input.email.trim().toLowerCase();
```

Then use the normalized value for:

```text
lookup
uniqueness
storage
login
```

Consistency is important.

---

# 8. Why Normalize Before Checking?

Suppose the database contains:

```text
rahul@example.com
```

and someone sends:

```text
RAHUL@EXAMPLE.COM
```

If you don't normalize consistently:

```text
Find:
RAHUL@EXAMPLE.COM

Database:
rahul@example.com
```

Your application might incorrectly think the account doesn't exist.

Then you could run into a database uniqueness conflict later.

So:

```text
Input
 ↓
Normalize
 ↓
Check
 ↓
Create
```

is cleaner.

---

# 9. Step 4 — Check Whether the User Exists

Now:

```text
email
  ↓
User Repository
  ↓
Find by email
```

Conceptually:

```typescript
const existingUser = await userRepository.findByEmail(email);
```

If a user exists:

```text
❌ Registration cannot continue
```

If not:

```text
✅ Continue
```

---

# 10. Should We Check Before Hashing?

Yes.

Imagine:

```text
User already exists
```

There's no reason to spend CPU/memory resources hashing a password that will never be used.

So:

```text
Validate
   ↓
Normalize
   ↓
Check existing user
   ↓
Hash password
   ↓
Create
```

is generally sensible.

---

# 11. But There Is a Race Condition

Here's an important database concept.

Imagine two requests arrive almost simultaneously:

```text
Request A
Request B
```

Both ask:

```text
Does rahul@example.com exist?
```

Both receive:

```text
No
```

Then both try:

```text
Create user
```

Without a database uniqueness constraint, you could end up with:

```text
User A → rahul@example.com
User B → rahul@example.com
```

That's why application-level checks are **not enough**.

---

# 12. Database UNIQUE Constraint

Our Prisma model has:

```prisma
email String @unique
```

This creates a database-level uniqueness guarantee.

So:

```text
Application check
      +
Database constraint
```

gives us robust protection.

Think:

```text
Application
    ↓
"Does user exist?"
```

is for:

```text
Better application behavior
```

while:

```text
Database
    ↓
UNIQUE(email)
```

is for:

```text
Data integrity
```

Both are useful.

---

# 13. Step 5 — Hash the Password

Now we can safely hash:

```text
password
   ↓
Argon2id
   ↓
passwordHash
```

Conceptually:

```typescript
const passwordHash = await argon2.hash(password);
```

The original password should not continue through your application unnecessarily.

After hashing:

```text
password
     ↓
passwordHash
```

The database receives:

```text
passwordHash
```

not:

```text
password
```

# 14. Step 6 — Create the User

Our repository receives the data required to create a user:

```typescript
const user = await userRepository.create({
  name,
  email,
  passwordHash
});
```

Notice:

```text
role
```

is not coming from the client.

The database default handles:

```text
STUDENT
```

or the service can explicitly assign it according to your controlled registration policy.

---

# 15. What Does the Repository Do?

The repository should focus on database access.

For example:

```typescript
async create(data: CreateUserData) {
  return prisma.user.create({
    data
  });
}
```

It shouldn't decide:

```text
Should this user be allowed to register?
Should password be strong?
Should role be ADMIN?
```

Those are application/authentication concerns.

Architecture:

```text
Controller
   ↓
Service
   ↓
Repository
```

---

# 16. What Does the Service Do?

The service coordinates the registration process.

Conceptually:

```typescript
async register(input: RegisterInput) {
  const email = normalizeEmail(input.email);

  const existingUser =
    await userRepository.findByEmail(email);

  if (existingUser) {
    throw new AppError(...);
  }

  const passwordHash =
    await hashPassword(input.password);

  return userRepository.create({
    name: input.name,
    email,
    passwordHash
  });
}
```

This is business logic.

The service understands:

```text
Registration rules
```

The repository understands:

```text
Database operations
```

---

# 17. What Does the Controller Do?

The controller should stay thin.

Conceptually:

```typescript
async register(req, res) {
  const user = await authService.register(req.body);

  return res.status(201).json({
    success: true,
    data: {
      user: toSafeUser(user)
    }
  });
}
```

The controller should not contain:

```text
Password hashing
Database queries
Complex registration logic
Authorization rules
```

That's what our architecture from Phase 2 is designed to prevent.

---

# 18. Safe User Response

Suppose Prisma returns:

```typescript
{
  id: "...",
  name: "Rahul",
  email: "rahul@example.com",
  passwordHash: "$argon2id$...",
  role: "STUDENT",
  emailVerifiedAt: null,
  createdAt: ...,
  updatedAt: ...
}
```

We should not return the entire object.

Instead:

```typescript
function toSafeUser(user: User) {
  return {
    id: user.id,
    name: user.name,
    email: user.email,
    role: user.role,
    emailVerifiedAt: user.emailVerifiedAt,
    createdAt: user.createdAt
  };
}
```

This is a useful pattern:

> **Database object ≠ API response object**

---

# 19. Why Explicit Response Mapping Is Better

This is risky:

```typescript
return res.json(user);
```

because someone might later add:

```text
securitySecret
internalFlag
passwordHash
someSensitiveField
```

to the database model.

Suddenly the API may expose it.

Instead:

```text
Database Model
      ↓
Explicit Mapping
      ↓
API DTO
```

This creates a security boundary.

# 23. Duplicate Email Errors

Suppose:

```text
rahul@example.com
```

already exists.

The application can detect it:

```text
existingUser !== null
```

and return an appropriate client error.

A typical choice is:

```http
409 Conflict
```

because the requested resource conflicts with existing state.

For example:

```json
{
  "success": false,
  "error": {
    "code": "EMAIL_ALREADY_REGISTERED",
    "message": "An account with this email already exists."
  }
}
```

Your exact error format should remain consistent with the API error structure from Phase 2.

# 24. But Be Careful With User Enumeration

There's a subtle security issue.

Suppose an attacker tries:

```text
alice@example.com
bob@example.com
rahul@example.com
admin@example.com
```

and your API clearly tells them:

```text
Email exists
Email doesn't exist
Email exists
Email doesn't exist
```

They can build a list of registered accounts.

That's called:

> **User/account enumeration**

For a public application, you may eventually want generic messaging in some flows.

For example:

```text
"If the account exists, you will receive further instructions."
```

This is particularly important for:

```text
Password reset
Email verification
Account recovery
```

For the registration endpoint, there's a UX/security trade-off, and we'll discuss it when we harden authentication.

# 26. Prisma Unique Constraint Error

Prisma can report a uniqueness violation when:

```text
email @unique
```

is violated.

Conceptually:

```typescript
try {
  return await userRepository.create(data);
} catch (error) {
  if (isUniqueConstraintError(error)) {
    throw new AppError(
      "An account with this email already exists.",
      409
    );
  }

  throw error;
}
```

The exact implementation depends on your Prisma version and error types.

The important architectural idea is:

> **Don't expose raw database errors to the client.**

---

# 27. Never Return Raw Database Errors

Bad:

```json
{
  "error": "PrismaClientKnownRequestError: Unique constraint failed on..."
}
```

This can expose:

```text
Database structure
Internal implementation
Table/field names
Technical details
```

Instead:

```json
{
  "success": false,
  "error": {
    "code": "EMAIL_ALREADY_REGISTERED",
    "message": "An account with this email already exists."
  }
}
```

Your logs can contain more technical information, but your client response should be controlled.

# 30. Example Password Utility

A simple abstraction:

```typescript
// shared/security/password.ts

import argon2 from "argon2";

export async function hashPassword(
  password: string
): Promise<string> {
  return argon2.hash(password, {
    type: argon2.argon2id,
  });
}

export async function verifyPassword(
  passwordHash: string,
  password: string
): Promise<boolean> {
  return argon2.verify(passwordHash, password);
}
```

Now the service doesn't need to know the cryptographic details.

It just says:

```typescript
const passwordHash = await hashPassword(password);
```

That's a clean abstraction.

# 31. Example Registration Service

Conceptually:

```typescript
async function register(input: RegisterInput) {
  const email = input.email.trim().toLowerCase();

  const existingUser =
    await userRepository.findByEmail(email);

  if (existingUser) {
    throw new AppError(
      "An account with this email already exists.",
      409
    );
  }

  const passwordHash =
    await hashPassword(input.password);

  const user = await userRepository.create({
    name: input.name,
    email,
    passwordHash,
  });

  return toSafeUser(user);
}
```

Notice how readable this is.

The service describes the business workflow:

```text
Normalize
   ↓
Check
   ↓
Hash
   ↓
Create
   ↓
Return safe user
```

That's exactly what we want.

# 🧠 Important Interview Concepts

### Why do we check for an existing email if the database already has `UNIQUE`?

Because:

```text
Application check
→ better UX / controlled response

Database constraint
→ final data-integrity guarantee
```

You want both.

---

### Why shouldn't the client send `role`?

Because:

```text
Client-controlled privilege
=
Privilege escalation vulnerability
```

The server must determine privileges.

---

### Why hash after checking whether the account exists?

Because password hashing is intentionally expensive.

There's no reason to spend those resources when the registration will fail anyway.

---

### Why shouldn't we return the Prisma `User` object directly?

Because the database model may contain:

```text
passwordHash
security fields
internal metadata
```

The API should return an explicit safe representation.

```text

3. Hash passwords before storing them.

4. Validate before expensive hashing.

5. Never expose passwordHash.

6. Never return raw database errors.

7. Keep controller thin.

8. Keep database logic in repositories.

9. Keep registration business logic in the service.

10. Treat the database as the final authority for data integrity.
```
