# 🔐 Phase 4 — Lesson 4.5: Login & Credential Verification

In **Lesson 4.4**, we built registration:

```text
Validate
   ↓
Normalize email
   ↓
Check user
   ↓
Hash password
   ↓
Create user
```

Now we're going in the opposite direction.

The user already exists. Our job is to determine:

> **Are these credentials valid, and should this user be authenticated?**

Our login flow will eventually become:

```text
POST /api/v1/auth/login
        ↓
Validate input
        ↓
Normalize email
        ↓
Find user
        ↓
Verify password
        ↓
Check account state
        ↓
Create session
        ↓
Issue authentication credentials
```

---

# 1. What Does Login Actually Mean?

A beginner often thinks:

```text
email + password
       ↓
JWT
```

But that's too simplified.

Login actually involves several decisions:

```text
Credentials
    ↓
Does the account exist?
    ↓
Is the password correct?
    ↓
Is the account allowed to authenticate?
    ↓
Should a session be created?
    ↓
What credentials should be issued?
```

So authentication is a **decision-making process**, not just token generation.

---

# 2. Login Endpoint

We'll use:

```http
POST /api/v1/auth/login
```

Request:

```json
{
  "email": "rahul@example.com",
  "password": "StrongPassword123!"
}
```

The server processes this information and, if authentication succeeds, eventually creates an authenticated session.

# 4. Step 1 — Validate Input

The first step is exactly like registration.

We need:

```text
email
password
```

Example schema conceptually:

```text
email
 ├── required
 ├── string
 └── valid format

password
 ├── required
 ├── string
 └── reasonable maximum length
```

We don't hash the password before validation.

Remember:

```text
Validation
   ↓
Expensive password operation
```

not:

```text
Password
   ↓
Hash huge malicious input
   ↓
Validation
```

---

# 5. Step 2 — Normalize Email

Suppose the user sends:

```text
  Rahul@Example.COM
```

We normalize:

```text
rahul@example.com
```

Then use this same representation for the database lookup.

```text
Input
 ↓
trim
 ↓
lowercase
 ↓
database lookup
```

This should match the normalization policy we established during registration.

Consistency is more important than cleverness here.

# 6. Step 3 — Find the User

Now:

```text
email
  ↓
User Repository
  ↓
PostgreSQL
```

Conceptually:

```typescript
const user = await userRepository.findByEmail(email);
```

There are two possibilities:

```text

     ↓
Continue

User doesn't exist
     ↓
Authentication failure
```

# 7. The Important Security Question

What should we return when the user doesn't exist?

Bad:

```json
{
  "message": "No account exists with this email."
}
```

And what if the password is wrong?

```json
{
  "message": "Incorrect password."
}
```

Now an attacker can determine which emails are registered.

For example:

```text
attacker
   ↓
100,000 emails
   ↓
Login attempts
   ↓
"Email doesn't exist"
"Wrong password"
"Wrong password"
"Email doesn't exist"
```

They can build an account database.

This is called:

> **User/account enumeration.**

---

# 8. Generic Authentication Errors

A safer approach is to use a generic message:

```json
{
  "success": false,
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Invalid email or password."
  }
}
```

Use the same general response whether:

```text
User doesn't exist
```

or:

```text
Password is incorrect
```

From the client's perspective:

```text
Authentication failed.
```

---

# 9. But There Is a Subtle Problem

You might think:

```text
if (!user) return error immediately;
```

and:

```text
if (user && passwordWrong) verify password;
```

is enough.

But there can be a timing difference.

For example:

```text
Non-existent user
    ↓
Database lookup
    ↓
Return quickly
```

versus:

```text
Existing user
    ↓
Database lookup
    ↓
Argon2 verification
    ↓
Return later
```

An attacker could potentially measure response timing.

This is called a:

> **Timing side channel.**

We don't need to make your first implementation excessively complicated, but you should understand that **security isn't only about response messages**.

---

# 10. Password Verification

If the user exists, retrieve:

```text
passwordHash
```

Then:

```text
Submitted password
       ↓
Argon2id verify
       ↓
Stored passwordHash
       ↓
true / false
```

Conceptually:

```typescript
const validPassword = await verifyPassword(
  user.passwordHash,
  password
);
```

If:

```text
false
```

authentication fails.

If:

```text
true
```

we continue.

---

# 11. Never Compare Passwords Yourself

Don't do:

```javascript
if (password === user.passwordHash) {
   ...
}
```

Obviously, that doesn't work because the stored value is a hash.

Don't manually implement:

```text
salt
iterations
memory
hash
comparison
```

either.

Use the password library's verification function.

For Argon2:

```typescript
await argon2.verify(
  storedHash,
  submittedPassword
);
```

The library understands the parameters encoded in the stored hash.

# 12. Authentication Decision

Now we have:

```text
User exists?
     ↓
Password valid?
```

Conceptually:

```text
              Login
                │
                ▼
           Find User
                │
          ┌─────┴─────┐
          ▼           ▼
       Not found     Found
          │            │
          │            ▼

          │            │

          │       ▼         ▼
          │     Invalid    Valid
          │       │         │

```

Only after successful authentication do we start talking about sessions and tokens.

# 13. Account State

A password can be correct while the account still shouldn't be allowed to log in.

For example:

```text
User
├── emailVerifiedAt
├── suspendedAt
├── disabledAt
└── ...
```

Our current model has:

```text
emailVerifiedAt
```

So eventually we might have a policy such as:

```text
Correct credentials
       ↓
Is account allowed to authenticate?
       ↓
Yes / No
```

Possible states:

```text
Active
Unverified
Suspended
Disabled
```

We should keep this separate from password verification.

---

# 14. Authentication vs Account State

This distinction is important.

Suppose:

```text
email = correct
password = correct
```

but:

```text
account = suspended
```

Then:

```text
Credentials valid
+
Account not allowed
=
Login rejected
```

So:

```text
Credential verification
```

and:

```text
Account policy
```

are separate decisions.

---

# 15. Should Unverified Users Be Allowed to Login?

This is a product decision.

Option A:

```text
Register
 ↓
Verify email
 ↓
Login
```

Option B:

```text
Register
 ↓
Login
 ↓
Restricted until verification
```

Option C:

```text
Register
 ↓
Authenticated
 ↓
Limited access
 ↓
Verify email
```

There's no universal answer.

For our LMS, we can choose a policy later when we implement email verification.

The important thing is that the authentication architecture **supports the decision**.

# 17. Why Create a Session?

Suppose Rahul logs in from:

```text
Laptop
```

We create:

```text
Session A
```

Then Rahul logs in from:

```text
Phone
```

We create:

```text
Session B
```

Database:

```text
User
 │
 ├── Session A
 │
 └── Session B
```

This gives us control over authentication state.

For example:

```text
Logout laptop
```

could revoke:

```text
Session A
```

while:

```text
Session B
```

remains active.

---

# 18. Login Is Not the Same as JWT Generation

This is a very important mental model.

Don't think:

```text
Login
 ↓
JWT
```

Think:

```text
Login
 ↓
Credential verification
 ↓
Authentication decision
 ↓
Session creation
 ↓
Access credential
 ↓
Refresh credential
```

JWT is only one possible mechanism for carrying authentication information.

It isn't the authentication architecture itself.

# 23. Login Service

Our service might conceptually look like:

```typescript
async function login(input: LoginInput) {
  const email = normalizeEmail(input.email);

  const user = await userRepository.findByEmail(email);

  if (!user) {
    throw invalidCredentialsError();
  }

  const validPassword = await verifyPassword(
    user.passwordHash,
    input.password
  );

  if (!validPassword) {
    throw invalidCredentialsError();
  }

  // Account-state checks
  // Session creation
  // Token generation

  return ...;
}
```

Notice how the controller doesn't know how passwords work.

That's good.

---

# 24. A Reusable Invalid Credentials Error

Instead of:

```text
UserNotFoundError
PasswordIncorrectError
```

being exposed to the client, we can have a generic authentication failure:

```typescript
throw new AppError(
  "Invalid email or password.",
  401,
  "INVALID_CREDENTIALS"
);
```

The internal logs can still distinguish events when appropriate.

But the external API doesn't need to reveal which credential failed.

---

# 25. Should We Always Return 401?

For invalid login credentials:

```http
401 Unauthorized
```

is generally appropriate.

For example:

```text
Wrong email
→ 401

Wrong password
→ 401
```

For authorization failures after successful authentication:

```http
403 Forbidden
```

For example:

```text
Student
 ↓
Authenticated
 ↓
Admin operation
 ↓
403
```

Remember:

```text
401
→ Authentication failed / missing

403
→ Authentication succeeded, but permission denied
```

# 26. What About Rate Limiting?

Imagine an attacker tries:

```text
password1
password2
password3
...
password999999
```

Without rate limiting:

```text
Login endpoint
      ↓
Unlimited guesses
```

That's dangerous.

So login should eventually have:

```text

+

```

We already learned rate limiting in Phase 2, and now we're applying it to authentication.

# 27. Don't Lock Accounts Too Aggressively

You might think:

```text
5 failed attempts
↓
Permanently lock account
```

But an attacker could intentionally lock other people's accounts.

That's an example of an **account lockout denial-of-service problem**.

So account abuse protection needs careful design.

Possible strategies include:

```text
Rate limiting
Progressive delays
Temporary throttling
Risk-based detection
Credential breach detection
```

We'll revisit this during authentication hardening.

---

# 28. Login Logging

We should log authentication events, but never passwords.

Useful information can include:

```text
requestId
userId (when known)
event type
success/failure
timestamp
IP metadata where appropriate
user-agent/device metadata where appropriate
```

For example:

```text
LOGIN_SUCCESS
userId=...
requestId=...
```

or:

```text
LOGIN_FAILURE
reason=invalid_credentials
requestId=...
```

But never:

```text
password=StrongPassword123!
```

---

# 29. Logging and User Enumeration

Be careful here.

Internally, you might know:

```text
User not found
```

or:

```text
Password mismatch
```

But externally:

```text
Invalid email or password.
```

This gives us:

```text
Internal diagnostics
        +
External security boundary
```

This is a very useful backend design pattern.

---

# 30. Timing Considerations

Let's revisit the timing issue.

Imagine:

```text
Request A
nonexistent email
→ 20 ms
```

and:

```text
Request B
existing email + wrong password
→ 180 ms
```

An attacker could potentially detect:

```text
"This email probably exists."
```

Password hashing itself is intentionally expensive, so the difference can be meaningful.

There are advanced techniques for reducing such side channels, including performing comparable work even when a user doesn't exist.

But don't blindly add complexity.

The practical lesson for now is:

> **Authentication systems should avoid unnecessary observable differences between failure paths.**

We'll revisit this during security hardening.

---

# 31. Login and Transactions

Should login use a database transaction?

Usually, simple credential verification doesn't require a transaction:

```text
Find user
+
Verify password
```

But session creation can involve additional state.

For example:

```text
Create Session
Update lastLoginAt
Create audit event
```

If several database operations must succeed together, a transaction may become appropriate.

This is another place where Phase 3 transaction knowledge matters.


# 33. What About `lastLoginIp`?

You might see:

```text

```

in some systems.

This can be useful for security auditing, but it introduces privacy considerations and isn't always necessary.

For our LMS, I'd prefer thinking of login events as **audit records** rather than putting lots of security history directly into the `User` row.

For example:

```text

   ↓

```

This scales better for audit history.

# 🧠 Interview-Level Question

### "How would you implement login securely?"

A strong answer would be:

> I would validate and normalize the credentials, retrieve the user through the repository layer, and verify the supplied password against the stored password hash using a password-hashing library such as Argon2id. Authentication failures should return a generic error to reduce user enumeration. After successful credential verification, I'd check account state, create an authentication session, and issue appropriate credentials. The endpoint would also have rate limiting and security-focused logging without logging passwords or other sensitive credentials.

That's much stronger than:

> "I compare the password and generate a JWT."
