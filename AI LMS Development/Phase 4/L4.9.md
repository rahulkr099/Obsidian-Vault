# 🔐 Phase 4 — Lesson 4.9: Logout, Session Management & Device Sessions

In **4.8**, we built the security foundation for refresh-token rotation:

```text
Refresh A
   ↓
Refresh B
   ↓
Refresh C
```

and learned:

```text
old token reuse
      ↓
possible token theft
      ↓
revoke session
```

Now we're going to build the **session-management layer** around that system.

The goal is to make our authentication system behave like a real production application:

```text
Login
 ↓
Session created
 ↓
User uses application
 ↓
Refresh token rotates
 ↓
User can view sessions
 ↓
User can logout one device
 ↓
User can logout all devices
 ↓
Password change can revoke sessions
```

---

# 1. What Is a Session?

Let's make this distinction very clear.

A **user** is an identity:

```text
User
id = user_123
```

A **session** represents one authenticated login context:

```text
Session
id = session_abc
userId = user_123
```

Therefore:

```text
User
 │
 ├── Session A
 ├── Session B
 └── Session C
```

One user can have many sessions.

---

# 2. Real-World Example

Suppose Rahul logs into the LMS from:

```text
💻 Laptop
📱 Phone
🖥️ College Computer
```

We shouldn't create three users.

Instead:

```text
Rahul
 │
 ├── Laptop Session
 ├── Phone Session
 └── College Computer Session
```

This allows us to control each login independently.

---

# 3. Why Sessions Matter

Without server-side sessions, logout becomes difficult.

Imagine we only have:

```text
JWT Access Token
```

The server verifies:

```text
Signature ✅
Expiration ✅
```

But how does it know:

> "Rahul clicked logout on his laptop."

A stateless JWT doesn't automatically know that.

With sessions:

```text
Session
   ↓
revokedAt = now()
```

Now the server has an explicit authentication state.

---

# 4. Our Session Model

Our Prisma model can look like:

```prisma
model Session {
  id               String    @id @default(uuid())
  userId           String

  refreshTokenHash String    @unique

  expiresAt        DateTime
  revokedAt        DateTime?

  createdAt        DateTime  @default(now())
  lastUsedAt       DateTime?

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  @@index([userId])
}
```

Let's understand what each field does.

---

# 5. `id`

```prisma
id String @id @default(uuid())
```

This uniquely identifies the session.

Example:

```text
session_abc123
```

The session ID is not the refresh token.

That's an important distinction.

```text
Session ID
≠
Refresh Token
```

---

# 6. `userId`

```prisma
userId String
```

This tells us:

```text
Which user owns this session?
```

Relationship:

```text
User
  │
  ├── Session
  ├── Session
  └── Session
```

---

# 7. `refreshTokenHash`

```prisma
refreshTokenHash String @unique
```

This identifies the current refresh credential associated with the session.

We store:

```text
hash(refreshToken)
```

not:

```text
refreshToken
```

So a database leak doesn't immediately give an attacker usable refresh tokens.

---

# 8. `expiresAt`

```prisma
expiresAt DateTime
```

This represents the maximum lifetime of the session.

For example:

```text
Created:
August 14

Expires:
September 14
```

Even if the user keeps refreshing:

```text
August 20
August 25
September 1
```

the session eventually expires unless your system explicitly uses a different policy.

---

# 9. `revokedAt`

```prisma
revokedAt DateTime?
```

`null` means:

```text
Session has not been revoked.
```

A timestamp means:

```text
Session was revoked.
```

Example:

```text
revokedAt = 2026-08-14T18:30:00Z
```

Now the session is no longer usable for refresh.

---

# 10. `lastUsedAt`

```prisma
lastUsedAt DateTime?
```

This tells us when the session was last used.

For example:

```text
createdAt:
August 1

lastUsedAt:
August 14
```

This can help with:

```text
Session management UI
Security auditing
Inactive-session cleanup
User visibility
```

---

# 11. Why Not Delete Revoked Sessions Immediately?

You might think:

```text
Logout
 ↓
DELETE session
```

Sometimes that's fine.

But keeping the record can be useful.

For example:

```text
Session
├── revokedAt
├── createdAt
└── lastUsedAt
```

can help with:

```text
Security auditing
Incident investigation
Reuse detection
Historical records
```

So a common strategy is:

```text
Active session
     ↓
Revoked
     ↓
Retained temporarily
     ↓
Eventually cleaned up
```

This is called **retention/cleanup**.

---

# 12. Logout Endpoint

We'll eventually have:

```http
POST /api/v1/auth/logout
```

The purpose is:

> Revoke the current authenticated session.

Conceptually:

```text
Client
  ↓
POST /auth/logout
  ↓
Identify current session
  ↓
Revoke session
  ↓
Clear refresh cookie
  ↓
Success
```

---

# 13. Why POST Instead of GET?

Don't use:

```http
GET /auth/logout
```

Logout changes server-side state.

Therefore:

```http
POST /auth/logout
```

is a better semantic choice.

Generally:

```text
GET
→ retrieve information

POST
→ perform an action / create state

DELETE
→ delete a resource
```

Logout is an authentication action, so `POST` is perfectly reasonable.

---

# 14. Identifying the Current Session

This is an important design question.

When Rahul sends:

```http
POST /auth/logout
```

how do we know which session should be revoked?

The refresh credential can identify the session.

For example:

```text
Refresh Token
      ↓
Hash
      ↓
Session lookup
      ↓
Session ID
```

Then:

```text
Session ID
   ↓
revoke
```

This works nicely if the refresh token is stored in an HttpOnly cookie.

---

# 15. Logout Flow

Conceptually:

```text
POST /auth/logout
        │
        ▼
Read refresh cookie
        │
        ▼
Hash refresh token
        │
        ▼
Find session
        │
        ▼
Mark revokedAt
        │
        ▼
Clear cookie
        │
        ▼
204 No Content
```

Notice:

> We don't need to know the user's password.

Logout is not re-authentication.

---

# 16. What If the Refresh Token Is Missing?

Suppose:

```text
POST /auth/logout
```

but the browser doesn't have a refresh cookie.

We can make logout **idempotent** from the client's perspective.

In other words:

```text
Already logged out
+
Logout again
=
Still logged out
```

This is often better UX than returning an unnecessary error.

For example:

```http
204 No Content
```

can still be returned.

---

# 17. Clearing the Cookie

If the refresh token lives in:

```text
HttpOnly cookie
```

logout should also clear it.

Conceptually:

```http
Set-Cookie:
refreshToken=;
Max-Age=0;
HttpOnly;
Secure;
...
```

The cookie attributes should match the original cookie configuration appropriately.

Otherwise you can accidentally leave the browser holding an old cookie.

---

# 18. What About the Access Token?

Remember:

```text
Access JWT
```

may still technically be valid until expiration.

So logout doesn't necessarily mean:

```text
Access JWT immediately invalid
```

unless you have an explicit access-token revocation strategy.

Our preferred architecture is:

```text
Access Token
→ short-lived

Refresh Session
→ revocable
```

This means the user won't be able to obtain a new access token after logout.

---

# 19. Logout All Devices

Now consider:

```http
POST /api/v1/auth/logout-all
```

This is useful when:

```text
User suspects account compromise
User changes password
User wants complete logout
```

The server can revoke all active sessions:

```text
User
 │
 ├── Session A → revoked
 ├── Session B → revoked
 └── Session C → revoked
```

# 20. Database Query

Conceptually:

```typescript
await prisma.session.updateMany({
  where: {
    userId,
    revokedAt: null,
  },
  data: {
    revokedAt: new Date(),
  },

```

This is a good example of using a database operation that directly expresses the business rule.

# 21. What About the Current Access Token?

Again:

```text
Access Token
```

could remain valid for a short period.

But:

```text
All refresh sessions
→ revoked
```

means:

```text
No new access tokens
```

Once existing access tokens expire:

```text
User
 ↓
must login again
```

This is why keeping access tokens short-lived is so useful.

# 23. Never Return the Refresh Token

The session API should never return:

```json
{
  "refreshTokenHash": "..."
}
```

and definitely not:

```json
{
  "refreshToken": "..."
}
```

Instead return safe metadata:

```text
Session ID
Device
Created at
Last used
Current?
```

Think:

```text
Database session
      ↓
Safe session DTO
      ↓
API response
```

# 24. Current Session

When listing sessions, the user should know:

```text
Which session am I using right now?
```

We can identify the current session through the refresh token:

```text
Current refresh token
      ↓
Session ID
      ↓
current = true
```

Then:

```text
Laptop
→ Current

Phone
→ Other

Tablet
→ Other
```

# 25. Session Revocation Endpoint

We can support:

```http
DELETE /api/v1/auth/sessions/:sessionId
```

For example:

```http
DELETE /api/v1/auth/sessions/session_abc
```

This means:

> Log out this particular session.

But there's an important security requirement.

---

# 26. Ownership Check

Rahul must not be able to do:

```http
DELETE /auth/sessions/victim-session
```

and revoke someone else's session.

The query must include ownership:

```text
sessionId
+
userId
```

Conceptually:

```typescript
await prisma.session.updateMany({
  where: {
    id: sessionId,
    userId: authenticatedUserId,
    revokedAt: null,
  },
  data: {
    revokedAt: new Date(),
  },
});
```

This is an example of **resource-level authorization**.

---

# 27. Never Trust the Session ID Alone

Bad:

```typescript
await prisma.session.update({
  where: {
    id: sessionId,
  },
  data: {
    revokedAt: new Date(),
  },
});
```

Why?

Because:

```text
sessionId
```

doesn't establish ownership.

Better:

```text
sessionId
+
authenticated userId
```

This is a very important backend security pattern.

---

# 28. Authentication vs Authorization

Here's the distinction again:

```text
JWT verification
       ↓
Who is this?
       ↓
Authentication
```

Then:

```text
Can this user revoke session X?
       ↓
Authorization
```

So:

```text
Authentication
→ establishes identity

Authorization
→ establishes permission
```

Our session-management endpoints need both.

---

# 29. Session ID Is Not a Secret

A session ID may appear in:

```text
GET /auth/sessions
```

or:

```text
DELETE /auth/sessions/:sessionId
```

That's okay as long as authorization is enforced.

The actual secret is:

```text
Refresh Token
```

Therefore:

```text
Session ID
≠
Refresh Token
```

Don't use the session ID itself as a credential.

---

# 30. Session Device Information

How do we know:

```text
Linux Laptop
Android Phone
```

?

We can derive a device description from request metadata such as:

```text
User-Agent
```

For example:

```text
Mozilla/5.0 ...
```

But don't blindly display the raw User-Agent.

Instead:

```text
User-Agent
    ↓
Parser
    ↓
Browser + OS
    ↓
"Firefox on Linux"
```

This can improve UX.

---

# 31. Don't Trust User-Agent Completely

User-Agent strings are client-controlled.

An attacker can send:

```text
User-Agent: iPhone
```

from a Linux machine.

So:

```text
Device metadata
→ informational
```

not:

```text
Device metadata
→ security proof
```

Never authorize a request because:

```text
"User-Agent says Android."
```

---

# 32. IP Address

We could also store:

```text
createdIp
lastUsedIp
```

But IP addresses have privacy and operational considerations.

They can also change frequently:

```text
Mobile network
VPN
ISP
Wi-Fi
Corporate network
```

So don't build security decisions that assume:

```text
IP = permanent identity
```

IP information can be useful for auditing and risk signals, but it is not a reliable identity by itself.

# 33. Session Cleanup

Suppose the database has:

```text
100,000 expired sessions
```

Eventually we need cleanup.

For example:

```text
Expired sessions
       ↓
Background job
       ↓
Delete old records
```

We don't necessarily need to delete immediately when they expire.

We can retain them for a reasonable period for auditing and then clean them.

This will become relevant when we study background jobs and production operations.

# 34. Database Indexing

Remember our index:

```prisma
@@index([userId])
```

Why?

Because we frequently perform:

```text
WHERE userId = ?
```

For example:

```text
GET /auth/sessions
```

requires:

```text
Find all sessions for this user
```

An index makes that query much more efficient as the table grows.

---

# 35. Query Patterns

Our session table will commonly receive queries like:

### Current user's sessions

```text
WHERE userId = ?
```

### Current session

```text
WHERE refreshTokenHash = ?
```

### Specific session owned by user

```text
WHERE id = ?
AND userId = ?
```

### Active sessions

```text
WHERE userId = ?
AND revokedAt IS NULL
```

### Cleanup

```text
WHERE expiresAt < now
```

These query patterns should influence our indexes.

---

# 36. Composite Index

As the application grows, we may consider:

```prisma
@@index([userId, revokedAt])
```

because we frequently query:

```text
userId
+
revokedAt
```

But don't blindly add indexes everywhere.

Indexes improve reads but have costs:

```text
More disk
More memory
Slower writes
More maintenance
```

Add them based on actual query patterns.

# 39. Controller Responsibilities

Remember your architecture:

```text
Controller
Service
Repository
```

The controller should remain thin.

For example:

```typescript
async function logout(req, res) {
  await authService.logout({
    refreshToken: req.cookies.refreshToken,
  });

  clearRefreshCookie(res);

  return res.status(204).send();
}
```

The controller should **not** contain:

```text
Prisma queries
Token hashing
Revocation rules
Rotation logic
Business decisions
```

---

# 40. Service Responsibilities

The service decides:

```text
Is this session valid?
Should it be revoked?
Which sessions belong to the user?
Can this user revoke this session?
```

For example:

```typescript
async function logoutSession(userId, sessionId) {
  const session = await sessionRepository.findById(sessionId);

  if (!session || session.userId !== userId) {
    throw new NotFoundError("Session not found");
  }

  await sessionRepository.revoke(session.id);
}
```

The service contains the business rule.

---

# 41. Repository Responsibilities

The repository handles database operations:

```typescript
findById()
findByUserId()
findByRefreshTokenHash()
revoke()
revokeAllForUser()
updateLastUsed()
```

Conceptually:

```text
Auth Service
     ↓
Session Repository
     ↓
Prisma
     ↓
PostgreSQL
```

This matches the architecture you've been practicing throughout the LMS roadmap.

# 42. Why Return "Not Found" Instead of "Forbidden"?

Suppose Rahul tries:

```http
DELETE /auth/sessions/session_belonging_to_someone_else
```

If the service responds:

```text
403 Forbidden
```

it reveals:

> "This session exists, but you don't own it."

A safer API can treat it as:

```text
404 Not Found
```

because from Rahul's perspective:

```text
"This session is not available to you."
```

This reduces resource enumeration.

The exact choice depends on API semantics, but the principle is useful.

---

# 43. Session Enumeration

Imagine an attacker tries:

```text
session_001
session_002
session_003
...
```

and gets different responses depending on whether the session exists.

They could learn information about your system.

Therefore:

```text
Resource existence
+
Authorization
+
Consistent error behavior
```

matter even for session management.

---

# 44. Logout-All Authorization

The endpoint:

```http
POST /auth/logout-all
```

should require an authenticated user.

Conceptually:

```text
Request
 ↓
Access JWT
 ↓
Authentication middleware
 ↓
req.user.id
 ↓
Revoke sessions belonging to req.user.id
```

Never accept:

```json
{
  "userId": "someone-else"
}
```

from the client to decide whose sessions should be revoked.

---

# 45. Bad Design

Don't do:

```json
POST /auth/logout-all

{
  "userId": "user_123"
}
```

and then:

```text
UPDATE sessions
WHERE userId = user_123
```

because the client controls:

```text
userId
```

A malicious user could simply change it.

Instead:

```text
Authenticated identity
       ↓
req.user.id
       ↓
database query
```

This is a core backend security principle:

> **Never trust client-supplied identity when the server already knows the authenticated identity.**

# 46. Password Change and Sessions

Suppose:

```text
User
 ├── Session A
 ├── Session B
 └── Session C
```

Rahul changes his password.

Policy:

```text
Password changed
       ↓
Revoke A
Revoke B
Revoke C
```

Then:

```text
Login again
```

This is especially useful for protecting users after suspected credential compromise.

# 47. Account Suspension

Suppose an administrator suspends a user:

```text
User
 ↓
suspended
```

Should their sessions continue working?

Probably not.

A robust system can:

```text
Account suspended
       ↓
Revoke sessions
```

and prevent new authentication.

This demonstrates why account state and session state need to work together.

# 48. Session Management and Authorization

Imagine:

```text
Student
```

tries:

```http
DELETE /auth/sessions/admin-session
```

Authentication tells us:

```text
User = Student
```

Authorization tells us:

```text
Does this Student own admin-session?
No.
```

Therefore:

```text
404/403
```

depending on our chosen API policy.

This pattern will be reused everywhere:

```text
Authentication
      ↓
Authorization
      ↓
Resource operation
```

# 53. Session Expiration Cleanup

Suppose:

```text
Session A
expiresAt = yesterday
```

It doesn't necessarily need to be deleted immediately.

We can have a periodic cleanup job:

```text
Every hour/day
      ↓
Find old expired/revoked sessions
      ↓
Delete them
```

For example:

```text
DELETE FROM sessions
WHERE expiresAt < now() - retention_period
```

This keeps the database healthy.

We'll eventually learn background workers/jobs in the later infrastructure phases.

# 55. Never Log Secrets

Your logs should look like:

```text
LOGIN_SUCCESS userId=123
SESSION_REVOKED sessionId=abc
REFRESH_TOKEN_REUSE userId=123
```

Not:

```text
refreshToken=eyJ...
accessToken=eyJ...
password=...
refreshTokenHash=...
```

Even a hash of a high-entropy token is still sensitive operational data.

Treat authentication material carefully.

# 58. Important Invariants

Let's define our system's invariants.

### Invariant 1

```text
A revoked session cannot refresh.
```

### Invariant 2

```text
An expired session cannot refresh.
```

### Invariant 3

```text
Only the current refresh token can rotate a session.
```

### Invariant 4

```text
A user can only manage their own sessions.
```

### Invariant 5

```text
Refresh tokens are never returned by session-list APIs.
```

### Invariant 6


# 🧠 Interview-Level Question

### "How would you implement session management for a multi-device application?"

A strong answer:

> I would create a server-side session for each successful login. Each session would belong to a user and contain a hash of the current refresh token, expiration information, and revocation state. Refresh tokens would be rotated on every refresh, while the previous token would become invalid. The system would support revoking an individual session or all sessions for a user. Session-management operations would always verify ownership using the authenticated user's identity rather than trusting a client-supplied user ID. Password changes, password resets, and suspicious refresh-token reuse could revoke existing sessions.

That's the kind of answer that shows actual backend understanding.

# 🎯 Lesson 4.9 Takeaways

Keep these in your notes:

```text
1. A user can have multiple authentication sessions.

2. Each device/login can have its own session.

3. A session should be server-side state.

4. Store refresh-token hashes, not raw refresh tokens.

5. revokedAt represents session revocation.

6. expiresAt represents session lifetime.

7. Logout should revoke the current session.

8. Logout-all should revoke all sessions belonging to
   the authenticated user.

9. Users must only be able to manage their own sessions.

10. Never trust a client-supplied userId for session ownership.

11. Session APIs should return safe metadata, never credentials.

12. Password changes/resets can revoke existing sessions.

13. Suspicious refresh-token reuse should trigger stronger
    security actions.

14. Expired/revoked sessions can be cleaned up asynchronously.

15. Session operations should have strong automated tests.
```
