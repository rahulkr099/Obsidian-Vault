# Lesson 5.7 — AI Quiz Generator

In **5.6**, we built the AI summarization pipeline:

```text
Lesson
   ↓
AI
   ↓
Structured Output
   ↓
Zod Validation
   ↓
Database
```

Now we're going to reuse that architecture to build one of the most useful AI features in your LMS:

> **Automatically generate quizzes from course lessons.**

The roadmap specifically includes an **AI Quiz Generator** where an instructor can provide a lesson and have the system generate questions, options, correct answers, explanations, and difficulty.

This lesson is especially valuable because it combines:

- AI
    
- structured output
    
- Zod
    
- database design
    
- authorization
    
- existing quiz architecture
    
- validation
    
- educational logic
    

---

# 1. What Are We Building?

Suppose an instructor has:

```text
Course: Backend Engineering

Lesson:
"JWT Authentication"
```

They click:

```text
Generate AI Quiz
```

The system generates:

```text
Question 1
What does JWT stand for?

A. Java Web Token
B. JSON Web Token
C. JavaScript Web Transfer
D. JSON Web Transfer

Correct Answer:
B

Explanation:
JWT stands for JSON Web Token...

Difficulty:
easy
```

Then:

```text
Question 2
...
```

The instructor can review the generated quiz before publishing it.


# 3. Why Should AI Generate a Draft?

AI can make mistakes.

For example, it might generate:

```text
Question:
What does JWT stand for?

Correct answer:
Java Web Token
```

which is wrong.

If your backend immediately publishes that question:

```text
AI
 ↓
Database
 ↓
Students
```

you could put incorrect educational content in front of students.

Instead:

```text
AI
 ↓
Draft
 ↓
Instructor Review
 ↓
Publish
```

This gives humans the final decision.

---

# 4. AI-Generated Content Is Not Automatically Correct

Remember:

```text
LLM output
   ≠
Truth
```

The AI may produce:

- incorrect answers
    
- ambiguous questions
    
- duplicate questions
    
- irrelevant questions
    
- poorly worded options
    
- multiple correct answers
    
- explanations that contradict the source
    

Therefore your backend should perform validation, and your instructor should have the ability to review.

---

# 5. Quiz Output Structure

We need a predictable structure.

A quiz could look like:

```json
{
  "title": "JWT Authentication Quiz",
  "description": "Test your understanding of JWT authentication.",
  "questions": [
    {
      "question": "What does JWT stand for?",
      "options": [
        "Java Web Token",
        "JSON Web Token",
        "JavaScript Web Transfer",
        "JSON Web Transfer"
      ],
      "correctAnswer": "JSON Web Token",
      "explanation": "JWT stands for JSON Web Token.",
      "difficulty": "easy"
    }
  ]
}
```

This is application data.

Therefore:

```text
LLM
 ↓
Structured output
 ↓
Validation
 ↓
Database
```

---

# 6. Define the Schema First

Before asking the LLM to generate anything, define what your backend expects.

For example:

```ts
const questionSchema = z.object({
  question: z.string().min(1),
  options: z.array(z.string().min(1)).length(4),
  correctAnswer: z.string().min(1),
  explanation: z.string().min(1),
  difficulty: z.enum([
    "easy",
    "medium",
    "hard",
  ]),
});
```

Then:

```ts
const quizSchema = z.object({
  title: z.string().min(1),
  description: z.string().min(1),
  questions: z.array(questionSchema).min(1).max(20),
});
```

Now your application has a clear contract.

---

# 7. Why Exactly Four Options?

For your first version:

```text
4 options
1 correct answer
3 incorrect answers
```

This makes the quiz predictable.

You could later support:

```text
2 options
3 options
4 options
5 options
```

but don't introduce unnecessary complexity initially.

For an academic project, consistency is more valuable.

---

# 8. The Important Business Rule

Here's an important validation problem.

Suppose AI generates:

```json
{
  "options": [
    "JSON Web Token",
    "Java Web Token",
    "JSON Web Token",
    "Web JSON Token"
  ],
  "correctAnswer": "JSON Web Token"
}
```

The schema is technically valid.

But there are duplicate options.

So we need business validation:

```text
options
 ↓
remove/check duplicates
 ↓
exactly 4 unique options
```

This demonstrates an important concept:

> **Schema-valid data can still be logically invalid.**

---

# 9. Another Business Rule — Correct Answer Must Exist

Suppose:

```json
{
  "options": [
    "A",
    "B",
    "C",
    "D"
  ],
  "correctAnswer": "E"
}
```

This passes:

```text
correctAnswer → string
```

but it's invalid because:

```text
"E" ∉ options
```

So validate:

```text
correctAnswer
       ↓
must exist inside options
```

# 10. Question Validation Pipeline

For every question:

```text
AI output
   ↓

   ↓

   ↓
All options unique?
   ↓
Correct answer exists?
   ↓
Question non-empty?
   ↓
Explanation non-empty?
   ↓
Valid difficulty?
```

Only after all of that:

```text

```

# 11. Difficulty Levels

We'll use:

```text
easy
medium
hard
```

But don't blindly trust the AI's difficulty.

Later you could create rules such as:

```text
Easy
→ definition / basic understanding

Medium
→ application / comparison

Hard
→ reasoning / scenario
```

This gives your quiz system more consistency.

# 12. Prompt Design

Now we need a specialized quiz prompt.

Conceptually:

```text
You are an educational quiz generator.

Generate multiple-choice questions based ONLY
on the provided lesson content.

Requirements:

- Generate 5 questions.
- Each question must have exactly 4 options.
- Exactly one option must be correct.
- Every question must have an explanation.
- Assign a difficulty: easy, medium, or hard.
- Avoid duplicate questions.
- Avoid ambiguous questions.
- Do not introduce information not present in the lesson.

Lesson:
{lessonContent}
```

Then we request the expected structured format.

---

# 13. Why "Based ONLY on the Lesson"?

This is extremely important.

Suppose your lesson says:

```text
JWT consists of:
header
payload
signature
```

We don't want the AI suddenly generating:

```text
Question:
Which RFC defines XYZ advanced JWT behavior?
```

if that topic wasn't taught.

The quiz should test:

```text
what students learned
```

not:

```text
what the model happens to know
```

---

# 14. Source-Grounded Quiz Generation

The ideal pipeline is:

```text
Lesson
  ↓
AI
  ↓
Questions
```

not:

```text
Lesson
  +
AI's general knowledge
  ↓
Questions
```

Eventually RAG can make this even stronger for large course resources.

---

# 15. API Design

We could use:

```http
POST /api/v1/ai/quizzes
```

Request:

```json
{
  "lessonId": "lesson_123",
  "questionCount": 10
}
```

The backend then retrieves the lesson.

Notice:

### Don't send lesson content from React.

Prefer:

```text
lessonId
   ↓
Backend
   ↓
Database
   ↓
Lesson content
```

This prevents the frontend from modifying the source content being used for generation.

---

# 16. Question Count

Allowing:

```json
{
  "questionCount": 10
}
```

is useful.

But validate it:

```ts
questionCount: z
  .number()
  .int()
  .min(1)
  .max(20)
```

Don't allow:

```text
questionCount = 100000
```

because that could create an expensive AI request.

---

# 17. AI Cost Control

This is another reason for validation.

Imagine someone sends:

```json
{
  "questionCount": 5000
}
```

Your backend shouldn't blindly forward that request to the LLM.

Use:

```text
1–20 questions
```

for example.

Then:

```text
User input
   ↓
Validation
   ↓
Safe request
   ↓
AI
```

AI endpoints need strong input controls.

---

# 18. Instructor Authorization

The endpoint should check:

```text
Who is requesting this?
        ↓
Is this an instructor?
        ↓
Does this instructor own the lesson?
```

For example:

```text
Instructor A
   ↓
Course A
   ↓
Lesson A
```

Instructor B shouldn't be able to generate content for Lesson A.

So:

```text
Authentication
      ↓
Authorization
      ↓
Ownership check
      ↓
AI generation
```

# 20. Prompt Builder

Keep the prompt separate:

```text
ai/
├── prompts/
│   ├── tutor.prompt.ts
│   ├── summary.prompt.ts
│   └── quiz.prompt.ts
```

```ts
function buildQuizPrompt(input: {

Lesson:
${input.lessonContent}

```

Now the service stays cleaner.

Now perform additional checks.

For each question:

```text

✓

✓
```

# 24. Duplicate Questions

AI might generate:

```text
Q1:
What is JWT?

Q2:
What does JWT stand for?

Q3:
What does JSON Web Token mean?
```

These might be effectively the same question.

Simple exact-string comparison won't catch every semantic duplicate.

For V1, use basic checks:

```text
normalized question strings
```

and perhaps reject obvious duplicates.

Later, semantic similarity could be used, but that's unnecessary complexity right now.

---

# 25. Question Quality

Some things can't easily be validated using Zod.

For example:

```text
What is Node.js?

A. Node.js
B. Node.js
C. Node.js
D. Node.js
```

The structure might be valid if duplicates weren't checked.

Or:

```text
Question:
Is this true?

A. Yes
B. No
C. Maybe
D. Sometimes
```

The question may be poorly designed.

This is why:

```text
AI
 ↓
Validation
 ↓
Instructor review
```

is the safest workflow.

# 34. AI vs Deterministic Logic

This is a powerful engineering principle.

Use AI for:

```text
understanding content
generating questions
writing explanations
```

Use normal code for:

```text
counting questions
checking duplicates
checking options
checking permissions
calculating scores
saving records
```

Think:

```text
AI
 ↓
Creative / language task

Backend
 ↓
Rules / correctness / security
```

Don't ask the AI to perform deterministic work that your backend can perform reliably.

# 39. Transaction Safety

Suppose you generate:

```text
10 questions
```

and save them one at a time.

Then:

```text
Question 1 ✓
Question 2 ✓
Question 3 ✓
Question 4 ✓
Question 5 ✗
```

Now your database has a partial quiz.

That's undesirable.

Use a database transaction:

```text
BEGIN
   ↓
Create quiz
   ↓
Create questions
   ↓
Create options
   ↓
Everything succeeds?
   ↓
COMMIT
```

If something fails:

```text
ROLLBACK
```

This connects directly to the PostgreSQL/Prisma concepts from Phase 3.

---

# 40. Transaction Architecture

Think:

```text
AI
 ↓
Validate entire quiz
 ↓
Prisma transaction
 ├── Create Quiz
 ├── Create Questions
 ├── Create Options
 └── Commit
```

If validation fails:

```text
No transaction
```

If database insertion fails:

```text
Rollback
```

This keeps your data consistent.

---

# 41. Don't Put the AI Call Inside a Database Transaction

This is a subtle but important point.

Avoid:

```text
BEGIN TRANSACTION
   ↓
Call LLM
   ↓
Wait 10 seconds
   ↓
Save quiz
COMMIT
```

Why?

Database transactions should generally be kept short.

Better:

```text
Call LLM
   ↓
Validate
   ↓
Start DB transaction
   ↓
Save quiz
   ↓
Commit
```

Excellent backend design principle.

# 🎯 Lesson 5.7 Takeaways

The most important ideas today:

```text
1. AI-generated quizzes should initially be drafts.

2. AI output must be validated before entering the database.

3. Schema validation and business validation are different.

4. Exactly one correct answer should exist for an MCQ.

5. Options should be unique.

6. The correct answer must exist among the options.

7. AI should generate language/content; backend should enforce rules.

8. Don't let AI output directly dictate your database structure.

9. Use database transactions when creating the quiz and its questions.

10. Don't keep a database transaction open while waiting for the LLM.

11. Instructor review provides an important human quality-control layer.

12. Long lessons may eventually require RAG or document processing.
```

The most important pipeline is:

```text
                Lesson
                   ↓
             Quiz Prompt
                   ↓
                  LLM
                   ↓
          Structured Quiz
                   ↓
             Zod Validation
                   ↓
        Business Validation
                   ↓
          Prisma Transaction
                   ↓
              Draft Quiz
                   ↓
          Instructor Review
                   ↓
               Publish
```

And the bigger principle:

> **Use AI for generation and language; use deterministic backend code for security, validation, permissions, transactions, and business rules.**
