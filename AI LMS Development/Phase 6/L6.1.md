# Lesson 6.1 — Enrollment System

Phase 6 is the **Student Learning System**, and the first lesson is **Enrollment System**. Your roadmap places enrollment at 6.1, after the LMS Core phase has already established courses and course access.

The key idea:

> **Enrollment is the relationship that says a student is officially associated with a course and can learn from it.**

---

## 1. What is enrollment?

Imagine:

```text
Student
Rahul
   │
   │ enrolls in
   ↓
Course
Node.js Backend Engineering
```

The important thing is that **one student can enroll in many courses**, and **one course can have many students**.

That means:

```text
Students           Courses

Student A ──────── Course X
    │                 │
    ├─────────────── Course Y
    │
Student B ──────── Course X
```

This is a **many-to-many relationship**.

We don't normally store this directly inside either `Student` or `Course`.

Instead, we create a separate table:

```text
Student
   │
   │
   ▼
Enrollment
   ▲
   │
   │
Course
```

---

# 2. Why do we need an Enrollment table?

A beginner might think:

```text
User
courses: [...]
```

or:

```text
Course
students: [...]
```

But this becomes problematic.

Enrollment itself has useful information.

For example:

```text
Enrollment
────────────────────────────
studentId
courseId
enrolledAt
status
completedAt
```

Now we can answer:

- When did the student enroll?
    
- Is the enrollment active?
    
- Has the student completed the course?
    
- When was it completed?
    

Later, Phase 6.2–6.11 will build more learning functionality around this foundation.

# 3. Basic database design

At a simple level:

```text
User
──────
id
name
email
role


Course
──────
id
title
description
instructorId


Enrollment
──────────
id
studentId
courseId
status
enrolledAt
completedAt
```

Relationships:

```text
User 1 ──────── N Enrollment
Course 1 ────── N Enrollment
```

Therefore:

```text
User N ───────── N Course
        through
       Enrollment
```

This is one of the most important relational database patterns you'll use throughout the LMS.

---

# 4. Prisma model

A simplified Prisma design could look like:

```prisma
model User {
  id          String       @id @default(uuid())
  name        String
  email       String       @unique

  enrollments Enrollment[]
}

model Course {
  id          String       @id @default(uuid())
  title       String

  enrollments Enrollment[]
}

model Enrollment {
  id          String   @id @default(uuid())

  studentId   String
  courseId    String

  enrolledAt  DateTime @default(now())
  status      EnrollmentStatus @default(ACTIVE)

  student     User     @relation(fields: [studentId], references: [id])
  course      Course   @relation(fields: [courseId], references: [id])

  @@unique([studentId, courseId])
  @@index([studentId])
  @@index([courseId])
}

enum EnrollmentStatus {
  ACTIVE
  COMPLETED
  CANCELLED
}
```

Don't worry about memorizing this yet.

Instead, understand **why each part exists**.

---

# 5. The most important constraint

Look carefully at:

```prisma
@@unique([studentId, courseId])
```

This prevents:

```text
Rahul → Node.js Course
Rahul → Node.js Course
Rahul → Node.js Course
```

from creating three enrollments.

We want:

```text
Rahul + Node.js Course = ONE enrollment
```

This is an example of an important principle:

> **Business rules should be enforced by the database whenever possible.**

Don't rely only on:

```ts
if (alreadyEnrolled) {
   throw new Error(...)
}
```

Why?

Because two requests can arrive almost simultaneously:

```text
Request A ──┐
            ├── check → not enrolled
Request B ──┘
            └── check → not enrolled
```

Both might try to insert.

The database's unique constraint gives us the final protection.

# 7. Controller

The controller should stay thin.

Conceptually:

```ts
export const enrollInCourse = asyncHandler(async (req, res) => {
  const studentId = req.user.userId;
  const { courseId } = req.params;

  const enrollment = await enrollmentService.enroll({
    studentId,
    courseId,
  });

  res.status(201).json({
    success: true,
    data: enrollment,
  });
});
```

Notice what the controller **doesn't** do.

It doesn't:

```text
❌ query Prisma
❌ check course status
❌ calculate enrollment rules
❌ handle database errors
```

That's service/repository responsibility.

---

# 8. Service layer

The service contains the business logic.

Conceptually:

```ts
async function enroll(studentId: string, courseId: string) {
  const course = await courseRepository.findById(courseId);

  if (!course) {
    throw new AppError("Course not found", 404);
  }

  if (!course.isPublished) {
    throw new AppError("Course is not available", 400);
  }

  const existing = await enrollmentRepository.findByStudentAndCourse(
    studentId,
    courseId
  );

  if (existing) {
    throw new AppError("Already enrolled", 409);
  }

  return enrollmentRepository.create({
    studentId,
    courseId,
  });
}
```

The exact implementation can evolve later.

The important separation is:

```text
Controller
→ receives request

Service
→ decides whether enrollment is allowed

Repository
→ talks to database
```

# 9. Repository

The repository should handle persistence.

For example:

```ts
async function create(data: {
  studentId: string;
  courseId: string;
}) {
  return prisma.enrollment.create({
    data,
  });
}
```

And:

```ts
async function findByStudentAndCourse(
  studentId: string,
  courseId: string
) {
  return prisma.enrollment.findUnique({
    where: {
      studentId_courseId: {
        studentId,
        courseId,
      },
    },
  });
}
```

That second query works because of:

```prisma
@@unique([studentId, courseId])
```

Prisma generates a compound unique selector.

# 10. What should happen when someone enrolls?

Let's define a proper flow.

### Request

```http
POST /api/v1/courses/course_123/enroll
Authorization: Bearer <token>
```

### Step 1 — Authenticate

```text
Who is making this request?
```

Example:

```text
studentId = user_456
```

### Step 2 — Find course

```text
course_123 exists?
```

If not:

```text
404 Not Found
```

### Step 3 — Check course availability

For example:

```text
isPublished = true
```

If unpublished:

```text
400 Bad Request
```

### Step 4 — Check existing enrollment

```text
user_456 + course_123
```

already exists?

If yes:

```text
409 Conflict
```

### Step 5 — Create enrollment

```text
Enrollment
─────────────────────────
studentId: user_456
courseId:  course_123
status:    ACTIVE
```

### Step 6 — Return response

```json
{
  "success": true,
  "data": {
    "id": "enrollment_123",
    "courseId": "course_123",
    "status": "ACTIVE"
  }
}
```

# 11. Enrollment status

We introduced:

```text
ACTIVE
COMPLETED
CANCELLED
```

Think about their meaning.

### ACTIVE

```text
Student can continue learning.
```

### COMPLETED

```text
Student has fulfilled course completion requirements.
```

### CANCELLED

```text
Enrollment is no longer active.
```

This gives us a useful lifecycle:

```text
              ┌─────────────┐
              │   ACTIVE    │
              └──────┬──────┘
                     │
              course completed
                     │
                     ▼
              ┌─────────────┐
              │  COMPLETED  │
              └─────────────┘

ACTIVE
  │
  │ cancellation
  ▼
CANCELLED
```

```text

6.3 Lesson Completion
6.4 Course Progress

```

# 12. Enrollment vs Course Access

These two concepts are related but **not exactly the same**.

### Enrollment

Answers:

> "Is this student enrolled in this course?"

### Access control

Answers:

> "Is this student currently allowed to access this particular resource?"

For example:

```text
Rahul
  ↓
Enrollment = ACTIVE
  ↓
Course
  ↓
Section
  ↓
Lesson
```

The user might be enrolled but a particular lesson could still have restrictions.

This distinction becomes important as your LMS becomes more sophisticated.

# 14. Security considerations

Enrollment is also an authorization problem.

A student should not be able to do:

```http
POST /api/v1/courses/course_123/enroll
```

and somehow enroll another student.

The backend should determine the student from:

```ts
req.user.userId
```

rather than trusting:

```json
{
  "studentId": "some-other-user"
}
```

So avoid:

```ts
// ❌ Don't trust client-provided identity
const { studentId, courseId } = req.body;
```

Prefer:

```ts
// ✅ Identity comes from authenticated session/token
const studentId = req.user.userId;
const { courseId } = req.params;
```

This connects directly with the security principles in your roadmap: authentication and authorization are cross-cutting concerns, not something we postpone until Phase 14.

# 15. Important edge cases

A production-quality enrollment system needs to think about:

|Situation|Expected behavior|
|---|---|
|Course doesn't exist|`404`|
|Course unpublished|Reject|
|User isn't authenticated|`401`|
|User isn't allowed to enroll|`403`|
|Already enrolled|`409`|
|Enrollment cancelled|Define re-enrollment policy|
|Course becomes unpublished later|Define access policy|
|Concurrent enrollment requests|DB constraint protects uniqueness|

That last one is especially important.

# 16. The race-condition problem

Imagine the user double-clicks the **Enroll** button.

Two requests arrive:

```text
Request A ────────┐
                  │
                  ├── check enrollment
                  │
Request B ────────┘
```

Both might see:

```text
No enrollment found
```

Then:

```text
A → INSERT
B → INSERT
```

Without a database constraint, you could get duplicates.

With:

```prisma
@@unique([studentId, courseId])
```

PostgreSQL rejects the second insert.

So:

```text
Application validation
        +
Database constraint
        =
Much safer system
```

This is an excellent example of why the database knowledge from Phase 3 matters.

# 17. What NOT to store in Enrollment

Don't turn `Enrollment` into a giant table containing everything:

```text
❌ enrollment
   ├── progress
   ├── currentLesson
   ├── videoPosition
   ├── notes
   ├── bookmarks
   ├── quizScore
   ├── certificate
   └── every activity
```

Instead, separate concepts:

```text
Enrollment
    │
    ├── Progress
    │
    ├── Lesson Completion
    │
    ├── Video Progress
    │
    ├── Bookmark
    │
    ├── Note
    │
    ├── Learning History
    │
    └── Certificate
```

That's exactly where the remaining Phase 6 lessons will take us.

# 19. Mini implementation challenge 🧠

Before moving to **6.2**, try designing this yourself.

### Requirement

Create an enrollment API:

```text
POST /api/v1/courses/:courseId/enroll
```

It should:

```text
1. Get student ID from authenticated user
2. Get course ID from route params
3. Check whether course exists
4. Check whether course is published
5. Check whether student is already enrolled
6. Create enrollment
7. Return enrollment
```

Database:

```text
User
Course
Enrollment
```

Constraint:

```text
(studentId, courseId) must be unique
```

Architecture:

```text
Route
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Prisma
  ↓
PostgreSQL
```

### Your goal

Don't just copy the Prisma model.

Try to answer these three questions yourself:

**1. Why is `Enrollment` a separate table?**

**2. Why should `studentId + courseId` be unique?**

**3. Why should `studentId` come from authentication rather than `req.body`?**

If you can explain those three clearly, you've understood the core of **Lesson 6.1**.
