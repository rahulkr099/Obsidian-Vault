# Lesson 6.10 — Instructor Progress Dashboard

In **6.9 — Student Dashboard**, we built the dashboard from the student's point of view:

> **"How am I progressing?"**

Now we switch perspective.

The instructor wants to know:

> **"How are my students progressing through my course?"**

This is the purpose of the **Instructor Progress Dashboard**.

---

# 1. Student Dashboard vs Instructor Dashboard

### Student

```text
My Courses
     ↓
My Progress
     ↓
My Bookmarks
     ↓
My Notes
     ↓
My Learning History
```

### Instructor

```text
My Courses
     ↓
My Students
     ↓
Student Progress
     ↓
Course Analytics
     ↓
At-risk Students
```

So the data is similar, but the **questions are different**.

---

# 2. What should an instructor see?

For a course such as:

```text
Backend Engineering
```

the instructor might see:

```text
Students enrolled: 428

Average progress: 64%

Completed course: 92 students

In progress: 310 students

Not started: 26 students
```

Then:

```text
Student Progress

Rahul Kumar       82%   Active today
Amit              74%   Active yesterday
Priya             61%   Active today
Neha              32%   No activity for 12 days
```

This allows instructors to understand the health of their course.

---

# 3. Important privacy boundary

This dashboard is **not** simply:

```text
SELECT * FROM learning_history;
```

An instructor should only see students and learning data for courses they are authorized to manage.

The authorization relationship is:

```text
Instructor
    ↓
Course ownership / teaching permission
    ↓
Enrollments
    ↓
Student progress
```

Not:

```text
Instructor
    ↓
Every student in database ❌
```

This distinction is extremely important.

---

# 4. Authorization comes first

Suppose:

```text
Instructor A
   ↓
Course A
```

and:

```text
Instructor B
   ↓
Course B
```

Instructor A requests:

```http
GET /api/v1/instructor/courses/course-B/progress
```

The backend must reject the request.

The service should first verify:

```text
Is this instructor allowed to manage Course B?
```

Only then:

```text
Fetch enrollments
Fetch progress
Return analytics
```

---

# 5. API design

A useful endpoint:

```http
GET /api/v1/instructor/courses/:courseId/progress
```

The authenticated instructor comes from:

```ts
req.user.userId
```

The backend then checks:

```text
Instructor
   ↓
Course
   ↓
Permission
   ↓
Progress
```

Example response:

```json
{
  "success": true,
  "data": {
    "courseId": "course_123",
    "totalStudents": 428,
    "averageProgress": 64,
    "completedStudents": 92,
    "inProgressStudents": 310,
    "notStartedStudents": 26
  }
}
```

---

# 6. Course-level overview

The first part of the dashboard should provide a quick summary.

For example:

```text
┌─────────────────────────────────────┐
│ Backend Engineering                 │
│                                     │
│ 428 Students                        │
│                                     │
│ Average Progress      64%           │
│ Completed             92            │
│ In Progress            310          │
│ Not Started            26           │
└─────────────────────────────────────┘
```

This gives the instructor an immediate overview.

---

# 7. Student-level progress

The instructor also needs individual information.

Example:

```text
Student             Progress   Last Active
────────────────────────────────────────────
Rahul Kumar            82%      Today
Amit                   74%      Yesterday
Priya                  61%      Today
Neha                   32%      12 days ago
```

This allows the instructor to identify:

```text
High performers
Students falling behind
Inactive students
Students who completed the course
```

---

# 8. Don't expose unnecessary student data

The instructor probably needs:

```text
name
avatar
progress
last activity
completion status
```

They don't necessarily need:

```text
private notes
personal bookmarks
private AI conversations
unrelated account information
```

For example:

```text
Student Note:
"I don't understand this topic."
```

should **not automatically become visible** to the instructor just because the instructor owns the course.

Remember:

> **Course ownership does not automatically mean ownership of the student's private learning data.**

---

# 9. Course progress calculation

Suppose:

```text
Course
30 lessons
```

Students:

```text
Student A → 30/30
Student B → 20/30
Student C → 15/30
Student D → 0/30
```

Progress:

```text
A → 100%
B → 66.67%
C → 50%
D → 0%
```

Average:

```text
(100 + 66.67 + 50 + 0) / 4
≈ 54.17%
```

The dashboard might show:

```text
Average Progress: 54%
```

---

# 10. Average progress has a limitation

Suppose we have:

```text
Student A → 100%
Student B → 100%
Student C → 0%
Student D → 0%
```

Average:

```text
50%
```

That doesn't tell the whole story.

The instructor should also see distribution:

```text
100%       → 2 students
75–99%     → 0
50–74%     → 0
25–49%     → 0
1–24%      → 0
0%         → 2 students
```

So:

> **Averages are useful, but distributions provide better context.**

---

# 11. Progress distribution

A useful dashboard widget:

```text
Progress Distribution

100%       ████████████  92
75–99%     █████████████████  140
50–74%     ███████████████    120
25–49%     ███████             50
1–24%      ███                 15
0%         ██                  11
```

The exact visualization belongs to the frontend.

The backend should provide structured numbers:

```json
{
  "distribution": {
    "completed": 92,
    "75To99": 140,
    "50To74": 120,
    "25To49": 50,
    "1To24": 15,
    "notStarted": 11
  }
}
```

---

# 12. Why not calculate this in React?

Avoid making the frontend download:

```text
428 students
```

and then calculate:

```text
average
distribution
completion rate
```

in the browser.

Instead:

```text
PostgreSQL
   ↓
Backend aggregation
   ↓
Dashboard API
   ↓
Frontend visualization
```

The server is the right place for authoritative analytics calculations.

---

# 13. Database aggregation

This is where SQL becomes powerful.

We can conceptually ask:

```sql
SELECT
    COUNT(*) AS total_students,
    AVG(progress) AS average_progress
FROM ...
```

Or:

```text
COUNT completed
COUNT in-progress
COUNT not-started
```

The exact SQL depends on our schema.

With Prisma, we can use:

```text
count
aggregate
groupBy
```

where appropriate.

---

# 14. Important distinction: enrollment vs student

Suppose a student enrolls in the same course twice due to a data problem.

You don't want:

```text
Student count = 2
```

when it's actually:

```text
One student
```

Therefore, enrollment and student identity must be handled carefully.

For course analytics, you usually want:

```text
Distinct students
```

rather than blindly counting rows.

This is another reason good database constraints matter.

---

# 15. Active students

The instructor may want:

```text
Active students:
245
```

But what does "active" mean?

We need a clear definition.

For example:

```text
Active =
at least one meaningful learning event
within the last 7 days
```

Then:

```text
Today
Yesterday
Last 7 days
Last 30 days
```

could be separate metrics.

Don't just use:

```text
lastLoginAt
```

because logging into the LMS doesn't necessarily mean learning.

Better:

```text
LearningHistory
+
meaningful learning events
```

can determine learning activity.

---

# 16. Last activity

For each student:

```text
lastActivityAt
```

can be derived from:

```text
LearningHistory
```

For example:

```text
Rahul
Last activity: 2026-08-14 10:32

Neha
Last activity: 2026-08-02 14:20
```

Then the dashboard can show:

```text
Rahul → Active today
Neha → Inactive for 12 days
```

This is much more useful than simply showing account login information.

---

# 17. At-risk students

Now we can build a useful instructor feature:

> **Which students may need help?**

For example:

```text
At-Risk Students

Neha
Progress: 32%
Last activity: 12 days ago

Ravi
Progress: 18%
Last activity: 21 days ago
```

But be careful with the wording.

The system doesn't actually know:

> "Neha will fail."

It only detects a pattern.

Better:

```text
Needs Attention
```

or:

```text
Inactive Learners
```

instead of making strong assumptions.

---

# 18. Defining "needs attention"

A simple rule might be:

```text
progress < 40%
AND
no meaningful learning activity for 14 days
```

Then:

```text
Student
     ↓
Progress < threshold?
     ↓
Inactive for threshold?
     ↓
Needs Attention
```

These thresholds should eventually be configurable.

---

# 19. Don't hardcode business rules everywhere

Avoid:

```ts
if (
  progress < 40 &&
  daysSinceActivity > 14
) {
  // ...
}
```

scattered across multiple controllers.

Instead:

```text
StudentProgressService
       ↓
AttentionRule
```

or a clearly defined domain policy.

This keeps the logic reusable.

# 22. Sorting

Instructors might want:

```text
Sort by:
```

```text
Progress ↓
Progress ↑
Last Activity ↓
Last Activity ↑
Name A-Z
Name Z-A
```

For example:

```http
GET /instructor/courses/course_123/students
    ?sort=progress
    &order=desc
```

The backend should validate allowed values.

Don't directly concatenate arbitrary user input into SQL.

# 23. Filtering

Useful filters:

```text
Progress:
0–25%
25–50%
50–75%
75–100%

Activity:
Active today
Active this week
Inactive

Status:
Not started
In progress
Completed
```

Example:

```http
GET /instructor/courses/course_123/students
    ?status=IN_PROGRESS
```

or:

```http
?minProgress=0&maxProgress=25
```

Again, validate these values.

---

# 24. Search

The instructor might search:

```text
Rahul
```

Request:

```http
GET /instructor/courses/course_123/students
    ?search=Rahul
```

The backend can search:

```text
name
email
```

But be careful about exposing student email addresses in the response.

Only include fields the instructor actually needs.

---

# 25. Instructor access control

There are several possible roles:

```text
ADMIN
INSTRUCTOR
STUDENT
```

Suppose:

```text
Instructor A
```

owns:

```text
Course A
Course B
```

but not:

```text
Course C
```

Then:

```text
Course A → allowed
Course B → allowed
Course C → forbidden
```

The authorization service should determine this.

This is **resource-level authorization**, not merely:

```text
role === "INSTRUCTOR"
```

---

# 26. Role check isn't enough

A common mistake:

```ts
if (req.user.role !== "INSTRUCTOR") {
  throw new AppError("Forbidden", 403);
}
```

This only answers:

> Is this person an instructor?

It doesn't answer:

> Does this instructor have permission to access **this course**?

You need both:

```text
Role authorization
       +
Resource authorization
```

---

# 27. Better authorization flow

```text
Request
   ↓
Authenticated?
   ↓
Role = INSTRUCTOR?
   ↓
Does instructor manage this course?
   ↓
YES
   ↓
Fetch analytics
```

If any check fails:

```text
403 Forbidden
```

or sometimes:

```text
404 Not Found
```

depending on whether you want to hide resource existence.

---

# 28. Course ownership vs teaching permission

Don't assume every course must have exactly one instructor.

Later you might support:

```text
Course
 ├── Instructor A
 ├── Instructor B
 └── Teaching Assistant C
```

So instead of:

```text
course.instructorId
```

you might eventually have:

```text
CourseInstructor
```

or:

```text
CourseMember
```

with permissions.

For example:

```text
INSTRUCTOR
TEACHING_ASSISTANT
ANALYST
```

This becomes useful as the LMS grows.

---

# 29. Don't expose private notes

Suppose Rahul has:

```text
Private Note:
"I'm struggling with database normalization."
```

The instructor dashboard should not automatically display:

```text
Rahul's private notes
```

Instead, the instructor might see:

```text
Rahul
Progress: 32%
Last activity: 12 days ago
```

Later, if you explicitly build a feature like:

```text
Student asks instructor for help
```

then the student can choose to share information.

Privacy should be intentional.

---

# 30. Instructor recent activity

An instructor might want a lightweight activity feed:

```text
Recent Course Activity

Rahul completed JWT Authentication
2 minutes ago

Priya completed PostgreSQL Indexes
8 minutes ago

Amit enrolled in the course
20 minutes ago
```

This can use:

```text
LearningHistory
+
Enrollment events
```

But again, don't expose unnecessary personal details.

---

# 31. Course activity vs student history

Student dashboard:

```text
"My activity"
```

Instructor dashboard:

```text
"Activity in my course"
```

Same underlying event system:

```text
LearningHistory
```

different authorization and filtering:

```text
Student:
WHERE enrollment belongs to current student

Instructor:
WHERE enrollment belongs to course
AND instructor manages course
```

This is a great example of **reusing data with different access policies**.

---

# 32. Course completion rate

A useful metric:

```text
Completion Rate
=
Completed Students
────────────────── × 100
Total Students
```

Example:

```text
92 / 428 × 100
≈ 21.5%
```

Dashboard:

```text
Course Completion Rate: 21.5%
```

But remember:

> A low completion rate doesn't automatically mean the course is bad.

Some students may have enrolled and never intended to finish.

Analytics provide signals, not absolute explanations.

---

# 33. Lesson completion analysis

The instructor may also want:

```text
Which lessons are students completing?
```

Example:

```text
Lesson                         Completion
─────────────────────────────────────────
Introduction                    95%
REST APIs                       88%
Authentication                  72%
Redis                           51%
Advanced Caching                32%
```

This can identify difficult or drop-off-heavy lessons.

# 34. Lesson drop-off

Suppose:

```text
Lesson 1 → 95% reached
Lesson 2 → 90%
Lesson 3 → 84%
Lesson 4 → 52%
Lesson 5 → 50%
```

We can detect:

```text
Lesson 4
↓
Large drop
```

This may indicate:

```text
Difficult concept
Poor explanation
Too long
Technical issue
Missing prerequisite
```

But again:

> **Analytics show where to investigate; they don't automatically explain why.**

---

# 35. Backend aggregation

For lesson-level completion:

```text
Course
   ↓
Lessons
   ↓
LessonCompletion
   ↓
GROUP BY lesson
   ↓
Completion counts
```

Conceptually:

```sql
SELECT
    lesson_id,
    COUNT(*) AS completed_students
FROM lesson_completion
WHERE enrollment_id IN (...)
GROUP BY lesson_id;
```

Then combine with:

```text
total enrolled students
```

to calculate completion percentage.

---

# 36. Performance considerations

Suppose:

```text
Course
100 lessons

Students
100,000
```

A naive dashboard could process:

```text
100,000 × 100
=
10 million
```

potential student-lesson combinations.

That's where proper indexing and aggregation become important.

Useful indexes may include:

```text
LessonCompletion
(enrollmentId, lessonId)

LearningHistory
(enrollmentId, createdAt)

Enrollment
(courseId, studentId)
```

The exact indexes should follow the actual query patterns.

---

# 37. Don't calculate everything on every request forever

At small scale:

```text
Request
 ↓
PostgreSQL aggregation
 ↓
Response
```

is perfectly reasonable.

At larger scale:

```text
Raw learning events
      ↓
Background aggregation
      ↓
Course analytics summary
      ↓
Dashboard
```

may become better.

This connects to future topics:

```text
Background jobs
Redis
Caching
Analytics pipelines
```

But don't build that complexity prematurely.

---

# 38. Instructor dashboard vs analytics system

The dashboard might show:

```text
Average Progress: 64%
```

But a complete analytics platform might later support:

```text
Daily active learners
Weekly retention
Lesson drop-off
Completion funnel
Cohort analysis
Quiz performance
Time-to-completion
```

For 6.10, we're building the **operational dashboard**, not a full data warehouse.

---

# 39. AI-powered instructor dashboard

This is where your AI LMS can become impressive.

Instead of showing only:

```text
Average Progress: 64%
```

later the AI could generate:

```text
AI Course Insight

"Students are progressing well through authentication,

```

# 40. Instructor dashboard architecture

A clean architecture:

```text
                 Instructor
                     │
                     ↓
          Instructor Dashboard API
                     │
                     ↓
          Instructor Dashboard Service
                     │
       ┌─────────────┼──────────────┐
       ↓             ↓              ↓
 Authorization    Progress       History
       │             │              │
       ↓             ↓              ↓
 Course Access    Enrollment    Learning Events
                     │
                     ↓
                  Lessons
```

The key point:

```text
Authorization
```

should happen **before** sensitive analytics are returned.

# 41. Controller example

```ts
export const getCourseProgress = asyncHandler(
  async (req, res) => {
    const instructorId = req.user.userId;
    const { courseId } = req.params;

    const dashboard =
      await instructorDashboardService
        .getCourseProgress({
          instructorId,
          courseId,
        });

    res.json({
      success: true,
      data: dashboard,
    });
  }
);
```

Thin controller.

---

# 42. Service example

Conceptually:

```ts
async function getCourseProgress({
  instructorId,
  courseId,
}) {
  await authorizationService.assertCanManageCourse(
    instructorId,
    courseId
  );

  const summary =
    await progressRepository.getCourseSummary(courseId);

  const students =
    await progressRepository.getStudentProgress(
      courseId
    );

  const distribution =
    calculateProgressDistribution(students);

  return {
    summary,
    distribution,
    students,
  };
}
```

Notice the order:

```text
Authorization
      ↓
Data access
      ↓
Aggregation
      ↓
Response
```

---

# 43. Keep the response DTO clean

Don't return raw Prisma models:

```ts
return prisma.enrollment.findMany(...);
```

Instead transform the result into an API contract:

```ts
{
  studentId,
  studentName,
  progressPercentage,
  completedLessons,
  totalLessons,
  lastActivityAt,
  status
}
```

This prevents your database schema from becoming your public API contract.

---

# 44. Sorting and pagination belong together

Suppose the instructor asks:

```text
Show lowest-progress students first.
```

Use:

```http
?page=1&limit=20&sort=progress&order=asc
```

The database should do the sorting and pagination whenever possible.

Don't:

```text
Fetch 10,000 students
        ↓
Send to Node.js
        ↓
Sort
        ↓
Take 20
```

Prefer:

```text
PostgreSQL
   ↓
ORDER BY
   ↓
LIMIT
   ↓
OFFSET / cursor
   ↓
Node.js
```

This reduces memory and network usage.

---

# 45. Cursor pagination

For very large datasets, cursor pagination may eventually be better than offset pagination.

Instead of:

```http
?page=100
```

you might use:

```http
?cursor=student_123
```

Conceptually:

```text
Page 1
 ↓
last item cursor
 ↓
Page 2
 ↓
next cursor
```

For our first implementation, normal pagination is enough.

But knowing cursor pagination will help later when your LMS grows.

---

# 46. What if a student leaves the course?

Suppose:

```text
Student
   ↓
Enrollment
   ↓
Course
```

Then the enrollment becomes:

```text
CANCELLED
```

Should the instructor dashboard count them?

Usually:

```text
Active enrollment
```

should be defined clearly.

For example:

```text
ACTIVE
COMPLETED
```

count toward active course analytics.

But:

```text
CANCELLED
REFUNDED
```

might not.

Again:

> Define analytics based on business rules, not accidental database behavior.

---

# 47. Course completion and instructor analytics

Suppose:

```text
Student A → 100%
```

but hasn't passed the final assessment.

Don't necessarily count them as:

```text
Completed Student
```

Instead:

```text
Progress = 100%
Completion Status = Pending Assessment
```

This is exactly why we separated:

```text
Progress
```

from:

```text
Completion Eligibility
```

in 6.4.

That earlier design decision now pays off.

```text
Personal learning data
```

unless explicitly authorized.

### 4. Use database aggregation

Don't download huge datasets just to calculate simple statistics in Node.js.

### 5. Avoid N+1 queries

Especially important for:

```text
Courses
Students
Lessons
Progress
```

### 6. Reuse existing domain logic

Don't create a second progress calculation.

### 7. Analytics are signals

```text
Low progress
```

doesn't automatically mean:

```text
Student is failing
```

Use careful terminology.
