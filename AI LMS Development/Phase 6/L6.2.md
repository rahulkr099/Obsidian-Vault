# Lesson 6.2 — Learning Progress

In **Lesson 6.1**, we created the relationship between a student and a course:

```text
Student
   ↓
Enrollment
   ↓
Course
```

Now we need to answer a more interesting question:

> **How much of the course has the student actually learned?**

This is the purpose of **Learning Progress**.

---

# 1. What is learning progress?

Suppose a course contains:

```text
Course: Node.js Backend Engineering

Section 1
 ├── Lesson 1
 ├── Lesson 2
 └── Lesson 3

Section 2
 ├── Lesson 4
 ├── Lesson 5
 └── Lesson 6
```

Rahul has enrolled in the course.

After some learning:

```text
Lesson 1  ✅
Lesson 2  ✅
Lesson 3  ⏳
Lesson 4  ❌
Lesson 5  ❌
Lesson 6  ❌
```

We can say:

```text
Completed = 2
Total = 6

Progress = 2 / 6 = 33.33%
```

So learning progress gives us a measurable representation of a student's journey through a course.

---

# 2. Enrollment is not progress

This distinction is very important.

In Lesson 6.1:

```text
Enrollment
```

answered:

> "Is this student enrolled in this course?"

Learning Progress answers:

> "How far has this student progressed through the course?"

For example:

```text
Student
   │
   ├── Enrollment
   │      └── Course A
   │
   └── Learning Progress
          ├── 20% completed
          ├── 5 lessons completed
          └── last activity
```

So:

```text
Enrollment ≠ Progress
```

---

# 3. What should progress represent?

This is where real system design begins.

A naive design might simply store:

```text
progress = 50
```

But that number doesn't tell us much.

Instead, we should be able to derive progress from meaningful learning data.

For example:

```text
Enrollment
──────────────
studentId
courseId

Learning Progress
─────────────────
completedLessons
lastLessonId
percentage
lastActivityAt
```

But we need to think carefully before storing all of these.

---

# 4. Source of truth

One of the most important database concepts here is:

> **Decide what the source of truth is before storing derived data.**

Suppose a course has 10 lessons.

We store:

```text
completedLessons = 5
percentage = 50
```

Now imagine a lesson is deleted.

The actual number becomes:

```text
4 / 9
```

but the database might still contain:

```text
completedLessons = 5
percentage = 50
```

Now our data is inconsistent.

A better design is to treat the actual completion records as the source of truth.

```text
Enrollment
     │
     ↓
Lesson Progress
     │
     ├── Lesson 1 → completed
     ├── Lesson 2 → completed
     ├── Lesson 3 → incomplete
     └── Lesson 4 → incomplete
```

Then:

```text
Course Progress
=
completed lessons / total lessons
```

This leads naturally into **Lesson 6.3 — Lesson Completion**.

---

# 5. Progress hierarchy

For our LMS, think about progress at multiple levels:

```text
Course
  │
  ├── Section 1
  │      ├── Lesson 1 ✅
  │      ├── Lesson 2 ✅
  │      └── Lesson 3 ❌
  │
  └── Section 2
         ├── Lesson 4 ❌
         ├── Lesson 5 ❌
         └── Lesson 6 ❌
```

Therefore:

```text
Lesson Progress
      ↓
Section Progress
      ↓
Course Progress
```

Eventually:

```text
Course Progress
      ↓
Student Dashboard
```

---

# 6. A useful database design

We can create a progress record associated with an enrollment.

Conceptually:

```prisma
model Enrollment {
  id          String   @id @default(uuid())

  studentId   String
  courseId    String

  enrolledAt  DateTime @default(now())
  status      EnrollmentStatus @default(ACTIVE)

  progress    LearningProgress?
}

model LearningProgress {
  id             String   @id @default(uuid())
  enrollmentId   String   @unique

  percentage     Float    @default(0)
  lastActivityAt DateTime?

  enrollment     Enrollment @relation(
    fields: [enrollmentId],
    references: [id]
  )
}
```

This creates:

```text
Enrollment 1 ───── 1 LearningProgress
```

But there's an important question:

> Should `percentage` be the source of truth?

**No.**

It's better treated as a **derived/cache value**.

The actual lesson completion records should eventually provide the underlying information.

---

# 7. Why have a progress table then?

You might ask:

> "If lesson completion is the source of truth, why store LearningProgress?"

Good question.

Because frequently calculating everything can become expensive.

Imagine:

```text
100,000 students
×
1,000 lessons
```

If every dashboard request calculates all lesson completion records from scratch, the database can do a lot of unnecessary work.

So we can maintain useful aggregate information:

```text
LearningProgress
────────────────────
percentage
completedLessons
lastActivityAt
```

while the detailed completion records remain the authoritative data.

This is a common engineering pattern:

```text
Source of truth
       ↓
Derived data
       ↓
Fast reads
```

---

# 8. The danger of duplicated data

Suppose we store:

```text
LessonCompletion
   ↓
10 completed

LearningProgress
   ↓
completedLessons = 9
```

Which one is correct?

We have a consistency problem.

Therefore, if we maintain derived values, we must update them carefully.

For example:

```text
Lesson completed
      ↓
Create completion record
      ↓
Update progress summary
```

These operations should ideally happen together.

That brings us back to something you learned in Phase 3:

> **Transactions.**

---

# 9. Transactional progress update

Imagine a student completes Lesson 5.

We might need to perform:

```text
BEGIN TRANSACTION

1. Create lesson completion
2. Update progress summary
3. Update last activity

COMMIT
```

If step 2 fails:

```text
ROLLBACK
```

We don't want:

```text
Lesson completion = YES
Progress summary = old value
```

because that creates inconsistent state.

Conceptually:

```ts
await prisma.$transaction(async (tx) => {
  await tx.lessonCompletion.create({
    data: {
      enrollmentId,
      lessonId,
    },
  });

  await tx.learningProgress.update({
    where: {
      enrollmentId,
    },
    data: {
      lastActivityAt: new Date(),
    },
  });
});
```

We'll implement the detailed version in **6.3**.

---

# 10. Progress percentage

A simple formula is:

```text
Progress %
=
Completed Lessons
────────────────── × 100
Total Lessons
```

Example:

```text
Completed = 7
Total = 10

7 / 10 × 100
= 70%
```

Another example:

```text
Completed = 15
Total = 24

15 / 24 × 100
= 62.5%
```

For UI, we might display:

```text
63%
```

But internally, we can preserve more precision if needed.

---

# 11. Edge case: zero lessons

What happens if:

```text
Total lessons = 0
```

Then:

```text
completed / total
```

becomes division by zero.

So we need a rule.

For example:

```ts
const percentage =
  totalLessons === 0
    ? 0
    : (completedLessons / totalLessons) * 100;
```

This is a small detail, but production systems are full of these small edge cases.

---

# 12. What counts as "completed"?

This is a product decision.

For a text lesson:

```text
Student opens lesson
        ↓
Read lesson
        ↓
Mark complete
```

For a video:

```text
Watch video
    ↓
90% watched
    ↓
Completed
```

For a quiz:

```text
Submit quiz
    ↓
Pass required score
    ↓
Completed
```

Therefore, we shouldn't assume that every lesson has the same completion rule.

Eventually our system may support:

```text
Lesson type
    │
    ├── ARTICLE
    ├── VIDEO
    ├── QUIZ
    └── ASSIGNMENT
```

and each type can have different completion logic.

That's another reason not to simply store:

```text
progress = 50
```

---

# 13. Progress is more than a percentage

A useful learning system can track:

```text
Percentage
Completed lessons
Current lesson
Last activity
Last activity time
Time spent
```

For example:

```json
{
  "percentage": 62.5,
  "completedLessons": 15,
  "totalLessons": 24,
  "currentLessonId": "lesson_42",
  "lastActivityAt": "2026-08-14T10:15:00Z"
}
```

This allows the frontend to display:

```text
Continue Learning

Node.js Backend Engineering

████████████░░░░░░░░ 63%

Continue:
Error Handling in Express
```

---

# 14. Current lesson vs completed lesson

These are different concepts.

Suppose:

```text
Lesson 1 ✅
Lesson 2 ✅
Lesson 3 👀 currently watching
Lesson 4 ❌
```

The student hasn't completed Lesson 3 yet.

So:

```text
Completed Lesson = Lesson 2
Current Lesson   = Lesson 3
```

Don't confuse:

```text
currentLesson
```

with:

```text
lastCompletedLesson
```

They serve different purposes.

---

# 15. Last activity

A very useful field is:

```text
lastActivityAt
```

For example:

```text
2026-08-14 10:20
```

Why?

The dashboard can show:

```text
Recently Learning

Node.js Backend Engineering
Last studied: Today
```

It can also help us build:

```text
Learning History
```

which is Lesson 6.8.

---

# 16. Progress API

We could eventually expose:

```http
GET /api/v1/courses/:courseId/progress
```

The backend might return:

```json
{
  "success": true,
  "data": {
    "courseId": "course_123",
    "percentage": 62.5,
    "completedLessons": 15,
    "totalLessons": 24,
    "currentLessonId": "lesson_42",
    "lastActivityAt": "2026-08-14T10:20:00Z"
  }
}
```

Notice that the backend provides information useful to the UI without forcing the frontend to understand database internals.

---

# 17. Authorization

Progress is private student data.

Rahul should be able to see:

```text
Rahul's progress
```

but not:

```text
Another student's progress
```

So this is dangerous:

```http
GET /api/v1/students/123/progress
```

if we simply trust the URL.

A safer student-facing endpoint could be:

```http
GET /api/v1/me/progress
```

or:

```http
GET /api/v1/courses/:courseId/progress
```

where the authenticated user comes from:

```ts
req.user.userId
```

The service then verifies:

```text
Does this user have an enrollment
for this course?
```

If not:

```text
403 Forbidden
```

or, depending on the API design:

```text
404 Not Found
```

to avoid revealing information.

---

# 18. Don't trust percentage from frontend

Never do this:

```json
{
  "courseId": "123",
  "percentage": 100
}
```

and blindly save:

```text
percentage = 100
```

A malicious user could simply send:

```json
{
  "percentage": 100
}
```

and pretend they completed the course.

Instead:

```text
Frontend
    ↓
"I completed lesson 7"
    ↓
Backend verifies
    ↓
Database records completion
    ↓
Backend calculates progress
```

The client can **request an action**.

The server determines the resulting state.

This is an extremely important backend principle.

---

# 19. Idempotency

Suppose the frontend accidentally sends:

```http
POST /lessons/lesson_7/complete
```

twice.

We don't want:

```text
Completion 1
Completion 2
```

for the same lesson.

We want:

```text
Lesson 7 = completed
```

only once.

A unique constraint can help:

```prisma
@@unique([enrollmentId, lessonId])
```

So:

```text
Student + Lesson
       ↓
one completion record
```

This is another example of using the database to enforce business rules.

# 20. Progress architecture

The architecture we are moving toward is:

```text
                    Student
                       │
                       ↓
                  Enrollment
                       │
                       ↓
              Lesson Completion
                       │
                       ↓
              Learning Progress
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
       Current Lesson       Percentage
             │                   │
             └─────────┬─────────┘
                       ↓
                Student Dashboard
```

Later:

```text
Learning Progress
      ↓
Course Completion
      ↓
Certificate
```

# 23. A subtle design question

Suppose an instructor adds:

```text
Lesson 25
```

after Rahul has completed all 24 lessons.

Previously:

```text
24 / 24 = 100%
```

Now:

```text
24 / 25 = 96%
```

Is that what we want?

Maybe.

Or perhaps the course version should be frozen for enrolled students.

This introduces an advanced concept:

```text
Course versioning
```

We don't need to solve it today.

But it's exactly the kind of question that separates:

```text
"CRUD application"
```

from:

```text
"real system design"
```

We'll keep these kinds of edge cases in mind as the LMS grows.

---

# 24. What you should remember

There are **five big ideas** from this lesson.

### 1. Enrollment and progress are different

```text
Enrollment
→ student is taking the course

Progress
→ how far the student has gone
```

### 2. Detailed completion should be the source of truth

```text
LessonCompletion
       ↓
Course Progress
```

### 3. Derived progress can improve performance

```text
Completion records
       ↓
Progress summary
       ↓
Fast dashboard queries
```

### 4. Server calculates trusted state

Never trust:

```text
percentage = 100
```

from the browser.

### 5. Database constraints matter

For example:

```text
(enrollmentId, lessonId)
        ↓
      UNIQUE
```

prevents duplicate completion records.
