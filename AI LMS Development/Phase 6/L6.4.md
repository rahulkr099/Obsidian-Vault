# Lesson 6.4 — Course Progress

In **6.3 — Lesson Completion**, we created the detailed records that tell us which lessons a student has completed.

Now we need to turn those records into a useful answer:

> **"How much of this course has the student completed?"**

This is **course-level progress**.

---

## 1. From Lesson Completion to Course Progress

We now have:

```text
Student
   ↓
Enrollment
   ↓
Course
   ↓
Lessons
   ↓
LessonCompletion
```

Example:

```text
Course: Node.js Backend Engineering

10 Lessons

Lesson 1  ✅
Lesson 2  ✅
Lesson 3  ✅
Lesson 4  ❌
Lesson 5  ❌
Lesson 6  ❌
Lesson 7  ❌
Lesson 8  ❌
Lesson 9  ❌
Lesson 10 ❌
```

Therefore:

```text
Completed = 3
Total = 10

Progress = 3 / 10 × 100
         = 30%
```

The system can show:

```text
Node.js Backend Engineering

██████░░░░░░░░░░░░ 30%

3 / 10 lessons completed
```

---

# 2. The important relationship

Remember:

```text
Lesson Completion
        ↓
Course Progress
```

We should **not** manually ask the student:

```json
{
  "progress": 30
}
```

Instead, the backend should derive it from trusted learning data.

```text
LessonCompletion records
        ↓
Count completed lessons
        ↓
Count course lessons
        ↓
Calculate percentage
```

This is one of the most important principles in this lesson.

---

# 3. The basic formula

The simplest formula is:

```text
Course Progress %
=
Completed Lessons
─────────────────── × 100
Total Lessons
```

Example:

```text
Completed = 12
Total = 30

12 / 30 × 100
= 40%
```

Another:

```text
Completed = 17
Total = 24

17 / 24 × 100
= 70.83%
```

For the frontend we might display:

```text
71%
```

but internally we can keep the more precise value.

---

# 4. The zero-lesson problem

Consider a newly created course:

```text
Course
   ↓
0 lessons
```

Then:

```text
0 / 0
```

is undefined.

So we need a rule:

```ts
const percentage =
  totalLessons === 0
    ? 0
    : (completedLessons / totalLessons) * 100;
```

For our LMS:

```text
No lessons
   ↓
0% progress
```

is a reasonable default.

---

# 5. Where should the calculation happen?

This is an important architecture decision.

We don't want the frontend doing:

```ts
const progress =
  completedLessons / totalLessons * 100;
```

as the source of truth.

The backend should provide trusted progress information.

The flow becomes:

```text
Next.js
   ↓
GET /courses/:courseId/progress
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
PostgreSQL
   ↓
Calculate / retrieve progress
   ↓
JSON response
```

The frontend is then responsible mainly for **displaying** the result.

---

# 6. What data do we actually need?

For a course-progress response, useful information could be:

```json
{
  "courseId": "course_123",
  "completedLessons": 12,
  "totalLessons": 30,
  "percentage": 40,
  "lastActivityAt": "2026-08-14T10:30:00Z"
}
```

We can later add:

```text
currentLesson
completedSections
remainingLessons
estimatedTimeRemaining
```

But don't add fields just because they might be useful someday.

Start with the actual requirements.

---

# 7. The database query problem

Imagine:

```text
10,000 students
100 lessons per course
```

If every dashboard request requires us to scan huge numbers of records, performance can become an issue.

A basic approach might be:

```text
1. Count all lessons in course
2. Count completed lessons for student's enrollment
3. Calculate percentage
```

Conceptually:

```text
totalLessons =
COUNT(Lesson WHERE courseId = X)

completedLessons =
COUNT(LessonCompletion WHERE enrollmentId = Y)
```

Then:

```text
percentage =
completedLessons / totalLessons * 100
```

This is simple and often a perfectly good starting point.

---

# 8. Prisma implementation

Suppose our schema allows lessons to be connected to courses through sections.

We could have a repository method such as:

```ts
async function getCourseProgress(
  enrollmentId: string,
  courseId: string
) {
  const totalLessons = await prisma.lesson.count({
    where: {
      section: {
        courseId,
      },
    },
  });

  const completedLessons =
    await prisma.lessonCompletion.count({
      where: {
        enrollmentId,
      },
    });

  const percentage =
    totalLessons === 0
      ? 0
      : (completedLessons / totalLessons) * 100;

  return {
    totalLessons,
    completedLessons,
    percentage,
  };
}
```

The exact Prisma relation names depend on the schema we established during the earlier LMS lessons.

The important idea is the query strategy:

```text
Course
  ↓
Count lessons

Enrollment
  ↓
Count completed lessons
```

---

# 9. Why enrollment matters

Suppose:

```text
Rahul
   ↓
Enrollment A
   ↓
Course A
```

and:

```text
Student B
   ↓
Enrollment B
   ↓
Course A
```

Both students are taking the same course.

But their progress is different:

```text
Rahul
12 / 30 = 40%

Student B
5 / 30 = 16.67%
```

Therefore, progress isn't simply:

```text
Course → Progress
```

It's:

```text
Student + Course → Progress
```

More precisely:

```text
Enrollment → Progress
```

This is why the `Enrollment` entity is such an important part of our model.

---

# 10. Course progress belongs to an enrollment

Think of the data hierarchy like this:

```text
Course
   │
   │
   ├── Student A
   │      └── Enrollment
   │             └── 40%
   │
   ├── Student B
   │      └── Enrollment
   │             └── 16%
   │
   └── Student C
          └── Enrollment
                 └── 80%
```

The course itself doesn't have:

```text
progress = 40%
```

because progress is different for every student.

---

# 11. What about `LearningProgress`?

In Lesson 6.2, we discussed a possible:

```text
LearningProgress
```

record.

For example:

```prisma
model LearningProgress {
  id             String   @id @default(uuid())
  enrollmentId   String   @unique

  percentage     Float    @default(0)
  lastActivityAt DateTime?

  enrollment     Enrollment @relation(...)
}
```

This can be useful as a **summary/cache**.

But we need to maintain a clear distinction:

```text
LessonCompletion
       ↓
SOURCE OF TRUTH

LearningProgress
       ↓
DERIVED SUMMARY
```

That distinction is extremely important.

---

# 12. Why store a progress summary?

Suppose the student dashboard loads:

```text
10 courses
```

and each course requires:

```text
COUNT lessons
COUNT completions
CALCULATE percentage
```

for every request.

As the LMS grows, this could become expensive.

A summary can make reads faster:

```text
LessonCompletion
       ↓
aggregation
       ↓
LearningProgress
       ↓
fast dashboard read
```

This is a common backend pattern:

> **Store detailed source data, then maintain derived data when fast reads are important.**

---

# 13. But don't blindly duplicate data

Suppose:

```text
LessonCompletion
completed = 12

LearningProgress
completedLessons = 11
```

Now we have inconsistent data.

So if we maintain summary information, updates must be carefully designed.

For example:

```text
Student completes lesson
        ↓
Create completion
        ↓
Update progress summary
```

These operations can happen inside a transaction.

---

# 14. Transactional update

Conceptually:

```ts
await prisma.$transaction(async (tx) => {
  await tx.lessonCompletion.upsert({
    where: {
      enrollmentId_lessonId: {
        enrollmentId,
        lessonId,
      },
    },
    create: {
      enrollmentId,
      lessonId,
    },
    update: {},
  });

  // Recalculate or update summary
  await tx.learningProgress.update({
    where: {
      enrollmentId,
    },
    data: {
      lastActivityAt: new Date(),
    },
  });
});
```

The goal is:

```text
Completion updated
       +
Progress summary updated
       =
Consistent state
```

If something fails:

```text
ROLLBACK
```

---

# 15. A better way to think about percentage

Don't think:

```text
percentage = a random number stored in database
```

Think:

```text
percentage
    =
a representation of learning state
```

The underlying state is:

```text
Lesson 1 → completed
Lesson 2 → completed
Lesson 3 → incomplete
...
```

The percentage is simply a summary:

```text
12 completed
30 total
↓
40%
```

This makes the system easier to reason about.

# 16. Course progress API

A useful endpoint could be:

```http
GET /api/v1/courses/:courseId/progress
```

The authenticated user is obtained from:

```ts
req.user.userId
```

The service then:

```text
1. Find the course
2. Find user's enrollment
3. Verify access
4. Count total lessons
5. Count completed lessons
6. Calculate progress
7. Return result
```

Example response:

```json
{
  "success": true,
  "data": {
    "courseId": "course_123",
    "completedLessons": 12,
    "totalLessons": 30,
    "percentage": 40
  }
}
```

---

# 17. Authorization

This endpoint contains private student information.

Rahul should be able to request:

```http
GET /courses/course_A/progress
```

if he is enrolled.

But he shouldn't be able to see another student's progress simply by manipulating a URL.

Bad design:

```http
GET /students/student_999/courses/course_A/progress
```

without strong authorization.

Better:

```http
GET /courses/course_A/progress
```

and derive the student from:

```ts
req.user.userId
```

Then:

```text
courseId
   ↓
studentId from auth
   ↓
find enrollment
   ↓
verify access
   ↓
return progress
```

---

# 18. What if the user isn't enrolled?

Suppose Rahul requests:

```http
GET /courses/course_B/progress
```

but isn't enrolled.

The service should not calculate and return the data.

Instead:

```text
Find enrollment
      ↓
Not found
      ↓
403 Forbidden
```

Depending on your security design, you may instead return `404` to avoid exposing whether certain resources exist.

The important point is:

> **Progress must be protected by enrollment/authorization checks.**

---

# 19. Course completion

Now we can define another useful concept.

If:

```text
Completed = Total
```

then:

```text
Progress = 100%
```

We might consider the course complete.

But don't automatically assume:

```text
100% = certificate
```

because later we may have requirements such as:

```text
All lessons completed
+
Final quiz passed
+
Assignment submitted
```

Therefore:

```text
Course Progress = 100%
```

and:

```text
Course Completion Eligibility
```

can be separate concepts.

This will become important in **6.11 — Certificates**.

---

# 20. Course progress vs course completion

This distinction is worth remembering.

### Course progress

```text
How far have you gone?
```

Example:

```text
78%
```

### Course completion

```text
Have you satisfied all completion requirements?
```

Example:

```text
YES
```

They often correlate, but they're not always identical.

---

# 21. What happens when lessons change?

This is one of the most interesting system-design problems.

Suppose:

```text
Monday:
10 lessons
10 completed
100%
```

Then the instructor adds:

```text
Lesson 11
```

Now:

```text
10 / 11
= 90.91%
```

Should Rahul suddenly see:

```text
91%
```

even though he didn't lose any progress?

There are multiple possible product rules.

### Option A — Current course content

Progress is always:

```text
completed / current lessons
```

### Option B — Enrollment snapshot

The student's original course version is used.

### Option C — Course versions

Every published course version has its own lesson set.

For our current LMS, we can start with **Option A** because it's simpler.

But knowing this problem exists is valuable.

# 22. Rounding

Suppose:

```text
17 / 24 × 100
= 70.833333...
```

We don't want the UI showing:

```text
70.83333333333333%
```

We can round for presentation:

```ts
const percentage = Number(
  ((completedLessons / totalLessons) * 100).toFixed(2)
);
```

Result:

```text
70.83
```

The frontend might display:

```text
71%
```

depending on the UI.

A useful rule:

> **Keep meaningful precision internally; round for presentation.**

---

# 23. Don't let the frontend calculate trusted progress

Avoid relying on:

```ts
// ❌ Client-controlled
const percentage = localStorage.getItem("progress");
```

or:

```json
{
  "percentage": 100
}
```

The backend should determine the trusted value.

The frontend can maintain temporary UI state, but the server remains authoritative.

---

# 24. Performance consideration

At small scale:

```text
COUNT lessons
+
COUNT completions
```

is usually straightforward.

But imagine:

```text
1 million enrollments
100 lessons/course
```

Now dashboards may generate a huge number of aggregation queries.

Possible future improvements include:

```text
Indexes
Materialized summaries
Cached progress
Background aggregation
Redis
Database optimization
```

These concepts connect to later phases:

```text
Phase 11 → Redis + Background Jobs
Phase 12 → Testing / Performance
Phase 13 → Production
```

So don't prematurely optimize.

Start with the simplest correct implementation.

# 25. Useful indexes

For our queries, these are particularly useful:

```prisma
@@unique([enrollmentId, lessonId])
```

and:

```prisma
@@index([enrollmentId])
```

Why?

Because we frequently ask:

```text
Give me all completions
for this enrollment.
```

We may also need indexes around the course/section/lesson relationships depending on the exact schema.

The general principle:

> **Indexes should follow real query patterns.**

# 28. A very important backend principle

Consider this request:

```http
POST /courses/course_123/progress
```

with:

```json
{
  "percentage": 100
}
```

A weak backend might say:

```text
"Okay, save 100."
```

A stronger backend says:

```text
"Why should I trust the client?"

Instead:
   ↓
Look at actual completion records
   ↓
Calculate trusted state
```

This is a general rule you'll use everywhere:

```text
Client
   ↓
Request
   ↓
Server validates
   ↓
Server determines state
   ↓
Database
```

Not:

```text
Client
   ↓
"Here is the state"
   ↓
Database
```

That mindset is extremely important for backend engineering.
