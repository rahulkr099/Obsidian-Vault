# Lesson 6.5 — Video / Content Progress

In **6.4 — Course Progress**, we calculated progress from completed lessons.

But there's a problem:

> A student doesn't always consume a lesson in one action.

This is especially true for **videos**.

A student might watch:

```text
Video: 60 minutes

Student watches:
00:00 → 27:35
```

then closes the browser.

When they return, the LMS should say:

```text
Continue watching from 27:35
```

That's the purpose of **Video / Content Progress**.

---

# 1. Lesson completion vs content progress

These are two different things.

### Lesson completion

Answers:

> "Has the student completed this lesson?"

```text
Lesson 5
   ↓
Completed = true
```

### Content progress

Answers:

> "How far has the student gone through the lesson's content?"

```text
Lesson 5
   ↓
Video position = 27:35
```

Therefore:

```text
Content Progress
        ≠
Lesson Completion
```

Example:

```text
Video duration: 60 min
Watched: 27 min

Content progress: 45%

Lesson completed: false
```

Later, based on your product rules:

```text
Watched ≥ required threshold
        ↓
Lesson completed
```

But these should remain conceptually separate.

---

# 2. Why do we need content progress?

Consider an online course:

```text
Course
 └── Section
      └── Lesson
           └── 60-minute video
```

The student watches:

```text
00:00
 ↓
10:00
 ↓
20:00
 ↓
30:00
```

They close the browser.

Without progress tracking:

```text
Student returns
      ↓
Video starts at 00:00
```

Bad experience.

With progress tracking:

```text
Student returns
      ↓
Backend says:
position = 30:00
      ↓
Video resumes
```

Much better.

---

# 3. What should we store?

A useful content-progress record might contain:

```text
ContentProgress
──────────────────────
id
enrollmentId
lessonId
positionSeconds
durationSeconds
percentage
lastWatchedAt
completed
```

But we should be careful about storing redundant information.

For example:

```text
positionSeconds = 1800
durationSeconds = 3600
```

already allows us to calculate:

```text
1800 / 3600 × 100
= 50%
```

So `percentage` could be derived.

A simpler source-of-truth design is:

```text
positionSeconds
durationSeconds
lastWatchedAt
```

and calculate:

```text
percentage =
positionSeconds / durationSeconds × 100
```

---

# 4. Video progress model

Conceptually:

```text
Enrollment
     │
     │ 1:N
     ↓
ContentProgress
     │
     │ N:1
     ↓
Lesson
```

For example:

```text
Enrollment
────────────────
Rahul + React Course
        │
        ↓
ContentProgress
────────────────
lessonId: lesson_12
position: 1650
duration: 3600
```

Meaning:

```text
27 minutes 30 seconds
out of
60 minutes
```

---

# 5. Prisma model

A possible design:

```prisma
model ContentProgress {
  id              String   @id @default(uuid())

  enrollmentId    String
  lessonId        String

  positionSeconds Int      @default(0)
  durationSeconds Int?

  lastWatchedAt   DateTime @default(now())

  enrollment      Enrollment @relation(
    fields: [enrollmentId],
    references: [id]
  )

  lesson          Lesson @relation(
    fields: [lessonId],
    references: [id]
  )

  @@unique([enrollmentId, lessonId])
  @@index([enrollmentId])
  @@index([lessonId])
}
```

The important constraint:

```prisma
@@unique([enrollmentId, lessonId])
```

means:

```text
One student enrollment
        +
One lesson
        ↓
One current progress record
```

We don't want:

```text
Rahul + Lesson 12
Rahul + Lesson 12
Rahul + Lesson 12
```

for the current position.

---

# 6. Why `positionSeconds`?

Don't store:

```text
position = "27:35"
```

as your primary database value.

Prefer:

```text
positionSeconds = 1655
```

Why?

Because numbers are much easier to calculate.

For example:

```text
1655 seconds
÷ 60
= 27 minutes
```

The frontend can convert it to:

```text
27:35
```

when displaying it.

---

# 7. Why not store only percentage?

Suppose:

```text
Video duration = 60 minutes
Progress = 50%
```

You can calculate:

```text
30 minutes
```

But storing the actual position is more useful.

For example:

```text
positionSeconds = 1837
```

lets the video resume at exactly:

```text
30:37
```

The percentage can always be derived.

So:

```text
Source of truth
      ↓
positionSeconds
      ↓
percentage
```

---

# 8. Updating progress

Imagine the student is watching:

```text
Video duration = 3600 seconds
```

At:

```text
30 seconds
```

frontend sends:

```http
PATCH /api/v1/lessons/lesson_123/progress
```

with:

```json
{
  "positionSeconds": 30
}
```

Later:

```json
{
  "positionSeconds": 60
}
```

Then:

```json
{
  "positionSeconds": 90
}
```

Eventually:

```text
positionSeconds = 1800
```

The database stores the **latest position**.

---

# 9. Don't send a request every millisecond

A video player can update its current position very frequently.

You might receive:

```text
1 sec
2 sec
3 sec
4 sec
5 sec
...
```

If you send an HTTP request for every second:

```text
60 requests/minute/student
```

That's wasteful.

Imagine:

```text
10,000 students
×
60 requests/minute
```

That's:

```text
600,000 requests/minute
```

just for playback position.

We need a better strategy.

---

# 10. Debouncing / throttling

A practical approach is to periodically save progress.

For example:

```text
Video playing
    ↓
Collect position locally
    ↓
Every 10–15 seconds
    ↓
Send latest position
```

Example:

```text
00:00 → local
00:05 → local
00:10 → local
00:15 → SAVE
00:20 → local
00:25 → local
00:30 → SAVE
```

This drastically reduces requests.

---

# 11. Save when important events happen

Don't rely only on periodic updates.

Also save when:

```text
Pause
Seek
Video ends
Tab closes
Page navigation
```

For example:

```text
Student presses pause
        ↓
Immediately save position
```

This gives us a nice combination:

```text
Periodic save
+
Important event save
```

# 13. API design

A useful endpoint:

```http
PATCH /api/v1/lessons/:lessonId/progress
```

Request:

```json
{
  "positionSeconds": 1655
}
```

Response:

```json
{
  "success": true,
  "data": {
    "lessonId": "lesson_123",
    "positionSeconds": 1655,
    "percentage": 45.97
  }
}
```

The backend can calculate:

```text
1655 / 3600 × 100
≈ 45.97%
```

---

# 14. Validate the position

Never blindly trust:

```json
{
  "positionSeconds": 999999999
}
```

If the video is only:

```text
3600 seconds
```

then:

```text
999999999 > 3600
```

is invalid.

The backend should validate:

```text
positionSeconds >= 0
```

and:

```text
positionSeconds <= durationSeconds
```

Depending on the system, you may allow a tiny tolerance because media duration can sometimes differ slightly between client and server.

---

# 15. What if the client lies?

Suppose the student sends:

```json
{
  "positionSeconds": 3600
}
```

without actually watching the video.

Can the backend know for sure?

Not always.

This is an important distinction:

```text
Content progress
      ↓
Client-reported observation
```

It isn't automatically proof of actual learning.

For a basic LMS, we can accept client-reported playback position with reasonable validation.

For stricter systems, we could combine:

```text
Playback events
+
Server-side rules
+
Minimum watch time
+
Seek detection
+
Quiz/assessment completion
```

But don't over-engineer this initially.

---

# 16. Resume functionality

The main benefit of saving position is:

```text
Student watches
      ↓
30:25
      ↓
Leaves
      ↓
Returns tomorrow
      ↓
Backend returns 30:25
      ↓
Video resumes
```

Frontend:

```ts
video.currentTime = positionSeconds;
```

Conceptually:

```text
GET progress
    ↓
positionSeconds = 1825
    ↓
video.currentTime = 1825
```

Now the student continues where they left off.

---

# 17. What about completed lessons?

Suppose the student reaches the end:

```text
positionSeconds ≈ durationSeconds
```

We might decide:

```text
Video reaches completion threshold
          ↓
Mark lesson completed
```

For example:

```text
position >= 90% of duration
```

could trigger completion.

But this is a **business rule**.

Another LMS might require:

```text
100% watched
```

Another might require:

```text
90% watched + quiz passed
```

Therefore, keep these concepts separate:

```text
Video Progress
      ↓
Completion Eligibility
      ↓
Lesson Completion
```

---

# 18. Don't automatically mark completion in every case

Suppose a student watches:

```text
0 → 60%
```

then seeks to:

```text
95%
```

A naive system might say:

```text
95% reached
↓
Completed!
```

But they skipped most of the video.

A stricter system might track:

```text
watched ranges
```

such as:

```text
0–30%
45–60%
95–100%
```

and determine actual coverage.

That is more complicated.

For our first implementation, we can use a simpler threshold.

The important thing is understanding the trade-off.

---

# 19. Content progress isn't only video

The lesson is called:

> **Video / Content Progress**

because the same concept can apply to other content.

### Video

```text
positionSeconds
durationSeconds
```

### Article

Could track:

```text
readingProgress
scroll position
```

### PDF

Could track:

```text
currentPage
```

### Audio

Could track:

```text
positionSeconds
durationSeconds
```

### Interactive lesson

Could track:

```text
currentStep
completedSteps
```

So the broader concept is:

```text
Content Progress
       │
       ├── Video
       ├── Audio
       ├── PDF
       ├── Article
       └── Interactive Content
```

# 20. Should everything use the same table?

There are two approaches.

### Approach A — Generic progress table

```text
ContentProgress
──────────────────
enrollmentId
lessonId
type
position
metadata
```

Flexible, but potentially less type-safe.

### Approach B — Specialized progress models

```text
VideoProgress
PDFProgress
ArticleProgress
```

More explicit, but more tables.

For your LMS, I'd initially keep the design **simple and lesson-oriented**, then specialize only when the product actually needs different behavior.

Avoid building a giant abstraction before you know the requirements.

---

# 21. Security

This endpoint:

```http
PATCH /lessons/:lessonId/progress
```

must not allow:

```text
Student A
   ↓
Update Student B's progress
```

The backend should:

```text
1. Authenticate user
2. Find lesson
3. Find lesson's course
4. Find user's enrollment
5. Verify enrollment is active
6. Update only that enrollment's progress
```

The frontend should never send:

```json
{
  "studentId": "another_student"
}
```

as the authority.

Use:

```ts
req.user.userId
```

instead.

---

# 22. Idempotency

Suppose the same request arrives twice:

```json
{
  "positionSeconds": 1800
}
```

No problem.

The second request simply sets:

```text
positionSeconds = 1800
```

again.

This is naturally close to an **idempotent update**.

That's useful because network retries are common.

---

# 23. What if requests arrive out of order?

This is a more interesting problem.

Imagine:

```text
Request A → position = 1800
Request B → position = 1500
```

but due to network timing:

```text
B arrives first
A arrives second
```

Fine:

```text
final = 1800
```

But imagine:

```text
A = 1800
B = 1500
```

and B arrives after A.

Now the database could incorrectly move the student backward:

```text
1800
 ↓
1500
```

We may want to prevent that.

---

# 24. Preventing backward progress

One possible rule:

```text
newPosition >= currentPosition
```

Then:

```text
current = 1800
incoming = 1500
```

could be rejected or ignored.

But there is a problem:

> What if the student intentionally seeks backward?

For example:

```text
Student wants to rewatch:
30:00 → 10:00
```

We shouldn't permanently change the saved resume position just because they seek backward.

A useful strategy is:

```text
Current playback position
        ≠
Highest saved progress
```

For example:

```text
savedPosition = 1800
student seeks to = 600
```

We might continue saving:

```text
resumePosition = 600
```

because that's where the student actually stopped.

Or we might separately track:

```text
furthestPosition = 1800
lastPosition = 600
```

This depends on the product behavior.

This is a great example of why **requirements should drive database design**.

---

# 25. Two useful fields

For a richer video system, we could eventually have:

```text
lastPositionSeconds
furthestPositionSeconds
```

Example:

```text
lastPosition = 600
furthestPosition = 1800
```

Meaning:

```text
Student is currently at 10:00
but has reached 30:00 before.
```

This can help with completion rules.

But again, don't add it unless you actually need the behavior.

---

# 26. Progress update frequency

A reasonable starting strategy:

```text
Every 10–15 seconds
+
Pause
+
Page navigation
+
Video end
```

For example:

```text
00:00
   ↓
playing
   ↓
00:15 → save
   ↓
00:30 → save
   ↓
00:45 → save
   ↓
pause → save immediately
```

If the browser crashes at:

```text
00:53
```

the latest server position might be:

```text
00:45
```

So the student loses only about:

```text
8 seconds
```

rather than the entire session.

That's a good trade-off.

---

# 27. Database writes vs user experience

There is always a trade-off:

```text
Save every second
      ↓
Very accurate
      ↓
Huge database traffic
```

versus:

```text
Save every 30 minutes
      ↓
Very cheap
      ↓
Poor resume experience
```

A practical middle ground:

```text
10–15 second periodic updates
+
important events
```

This is a classic engineering trade-off:

```text
Accuracy
   ↕
Cost
   ↕
Complexity
```

# 29. Controller

The controller stays thin:

```ts
export const updateContentProgress = asyncHandler(
  async (req, res) => {
    const studentId = req.user.userId;
    const { lessonId } = req.params;

    const progress =
      await contentProgressService.update({
        studentId,
        lessonId,
        positionSeconds: req.body.positionSeconds,
      });

    res.json({
      success: true,
      data: progress,
    });
  }
);
```

The controller doesn't decide:

```text
❌ Is the student enrolled?
❌ Is this lesson part of the course?
❌ Is the position valid?
❌ Should completion be triggered?
```

The service handles those decisions.

---

# 30. Repository

The repository handles persistence:

```ts
async function upsertProgress(data: {
  enrollmentId: string;
  lessonId: string;
  positionSeconds: number;
}) {
  return prisma.contentProgress.upsert({
    where: {
      enrollmentId_lessonId: {
        enrollmentId: data.enrollmentId,
        lessonId: data.lessonId,
      },
    },
    create: data,
    update: {
      positionSeconds: data.positionSeconds,
      lastWatchedAt: new Date(),
    },
  });
}
```

Again:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Prisma
```

Keep this separation.

# 34. What NOT to do

### ❌ Don't store video progress in the User table

```text
User
 └── currentVideoPosition
```

A student can have many courses and many lessons.

---

### ❌ Don't store one global progress number

```text
User.progress = 73
```

Progress is course-specific.

---

### ❌ Don't trust the client

```text
{
  "percentage": 100
}
```

The server should determine trusted state.

---

### ❌ Don't write to PostgreSQL every second

You'll create unnecessary load.

---

### ❌ Don't mix playback position with completion

```text
position = 90%
```

doesn't necessarily mean:

```text
lesson completed
```

unless your business rule says so.

---

# 35. Important design principle

One of the biggest lessons here is:

> **Track the smallest useful piece of state, then derive higher-level information from it.**

For example:

```text
positionSeconds
      ↓
video percentage
      ↓
completion eligibility
      ↓
lesson completion
      ↓
course progress
      ↓
certificate eligibility
```

This creates a much cleaner architecture than storing unrelated numbers everywhere.
