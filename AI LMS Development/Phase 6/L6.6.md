# Lesson 6.6 — Bookmarks

In **6.5 — Video / Content Progress**, we tracked where a student stopped inside a lesson.

Now we add another useful learning feature:

> **Bookmarks let a student save a lesson or learning point so they can quickly return to it later.**

For example:

```text
Student is studying:
"JWT Authentication"

              ↓

Interesting section:
"Refresh Token Rotation"

              ↓

🔖 Bookmark
```

Later:

```text
Student Dashboard
      ↓
My Bookmarks
      ↓
Refresh Token Rotation
      ↓
Jump back to lesson
```

This fits naturally after content progress because both features are **student-specific learning state**. Your roadmap places Bookmarks as **6.6**, immediately after Video / Content Progress.

---

# 1. What exactly is a bookmark?

At the simplest level:

```text
Bookmark
──────────────
Student
Lesson
Created At
```

But for your LMS, we can make it more useful.

A bookmark might represent:

```text
Bookmark
──────────────────────
student/enrollment
lesson
position
title/note
createdAt
```

For a video:

```text
Lesson:
JWT Authentication

Position:
18:42
```

For a text lesson:

```text
Lesson:
Database Transactions

Position:
Section 4
```

So a bookmark doesn't necessarily mean:

> "Save this entire lesson."

It can mean:

> **"Save this specific learning point so I can return to it."**

---

# 2. Bookmark vs Progress

These two features are very different.

### Progress

Answers:

> Where did the student stop?

```text
Video:
42:15
```

### Bookmark

Answers:

> What did the student intentionally save for later?

```text
🔖 JWT refresh-token rotation
at 42:15
```

So:

```text
ContentProgress
     ↓
Automatic learning state

Bookmark
     ↓
Intentional student action
```

This distinction is important.

A student doesn't have to bookmark the place where they stopped.

For example:

```text
Last position:
52:30

Bookmark:
18:45 — "Important security concept"
```

# 3. Basic database model

Conceptually:

```text
Enrollment
    │
    │ 1:N
    ↓
Bookmark
    │
    │ N:1
    ↓
Lesson
```

A student can have:

```text
Enrollment
   │
   ├── Bookmark → Lesson 1
   ├── Bookmark → Lesson 5
   ├── Bookmark → Lesson 8
   └── Bookmark → Lesson 12
```

---

# 4. Why associate bookmarks with enrollment?

Remember our architecture:

```text
User
  ↓
Enrollment
  ↓
Course
```

A bookmark belongs to a student's learning experience inside a course.

So:

```text
Enrollment
   ↓
Bookmark
   ↓
Lesson
```

is a clean relationship.

This also gives us an important authorization rule:

> A student should only be able to create bookmarks for lessons they are allowed to access.

---

# 5. Prisma model

A basic model could be:

```prisma
model Bookmark {
  id           String   @id @default(uuid())

  enrollmentId String
  lessonId     String

  positionSeconds Int?
  note           String?

  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  enrollment     Enrollment @relation(
    fields: [enrollmentId],
    references: [id]
  )

  lesson         Lesson @relation(
    fields: [lessonId],
    references: [id]
  )

  @@index([enrollmentId])
  @@index([lessonId])
}
```

This gives us:

```text
Bookmark
├── enrollmentId
├── lessonId
├── positionSeconds
├── note
├── createdAt
└── updatedAt
```

---

# 6. Should `positionSeconds` be optional?

Yes.

Why?

Because not every lesson is a video.

For example:

### Video lesson

```text
Bookmark
──────────────
lessonId: lesson_10
position: 1835
```

Meaning:

```text
30:35
```

### Article lesson

```text
Bookmark
──────────────
lessonId: lesson_11
position: null
note: "Important explanation of normalization"
```

So:

```text
positionSeconds = optional
```

makes the bookmark system more flexible.

---

# 7. Should bookmarks be unique?

This depends on the product design.

Suppose Rahul bookmarks:

```text
JWT Authentication
at 10:30
```

and later:

```text
JWT Authentication
at 25:40
```

Should those be:

```text
Bookmark 1
Bookmark 2
```

or should the second replace the first?

There are two valid designs.

---

## Option A — One bookmark per lesson

```text
Student + Lesson
       ↓
ONE bookmark
```

Then:

```prisma
@@unique([enrollmentId, lessonId])
```

This is simple.

---

## Option B — Multiple bookmarks per lesson

```text
Student + Lesson
       ↓
Many bookmarks
```

For example:

```text
JWT Authentication

🔖 10:30 — Access tokens
🔖 25:40 — Refresh tokens
🔖 38:20 — Token rotation
```

This is more powerful.

For an AI LMS, **I prefer Option B** because students may want to save multiple important points from the same lesson.

Therefore, don't add:

```prisma
@@unique([enrollmentId, lessonId])
```

unless the product requirement is explicitly "one bookmark per lesson."

---

# 8. Bookmark IDs

Each bookmark should have its own ID:

```text
bookmark_123
bookmark_456
bookmark_789
```

This makes operations simple:

```http
DELETE /api/v1/bookmarks/bookmark_123
```

rather than:

```http
DELETE /api/v1/courses/course_123/lessons/lesson_5/bookmark
```

Both approaches can work, but resource IDs make individual bookmark management straightforward.

# 9. Creating a bookmark

A possible endpoint:

```http
POST /api/v1/lessons/:lessonId/bookmarks
```

Request:

```json
{
  "positionSeconds": 1835,
  "note": "Important explanation of refresh token rotation"
}
```

Notice what is **not** included:

```json
{
  "studentId": "student_123"
}
```

The backend gets the student from authentication:

```ts
const studentId = req.user.userId;
```

# 11. Service logic

Conceptually:

```ts
async function createBookmark({
  studentId,
  lessonId,
  positionSeconds,
  note,
}) {
  const lesson = await lessonRepository.findById(lessonId);

  if (!lesson) {
    throw new AppError("Lesson not found", 404);
  }

  const enrollment =
    await enrollmentRepository.findByStudentAndCourse(
      studentId,
      lesson.courseId
    );

  if (!enrollment) {
    throw new AppError(
      "You are not enrolled in this course",
      403
    );
  }

  return bookmarkRepository.create({
    enrollmentId: enrollment.id,
    lessonId,
    positionSeconds,
    note,
  });
}
```

The important chain is:

```text
Student
   ↓
Enrollment
   ↓
Course
   ↓
Lesson
```

before creating the bookmark.

---

# 12. Why this authorization check matters

Imagine:

```text
Course A
 └── Lesson A1

Course B
 └── Lesson B1
```

Rahul is enrolled only in:

```text
Course A
```

He somehow discovers:

```text
lesson_B1
```

and sends:

```http
POST /lessons/lesson_B1/bookmarks
```

The server must reject it.

Otherwise Rahul could create records for content he shouldn't have access to.

So:

```text
Authentication
     +
Enrollment verification
     +
Lesson/course relationship
```

protects the operation.

---

# 13. Bookmark position

For videos, the frontend might send:

```json
{
  "positionSeconds": 1835
}
```

The backend should validate:

```text
positionSeconds >= 0
```

and ideally:

```text
positionSeconds <= duration
```

if duration is available and trusted.

For example:

```text
Duration = 3600
Position = 1835
```

is valid.

But:

```text
Position = 999999
```

shouldn't be accepted blindly.

# 15. Validate bookmark notes

Never accept unlimited text.

For example, define a reasonable limit:

```ts
const bookmarkSchema = z.object({
  positionSeconds: z.number().int().min(0).optional(),

  note: z
    .string()
    .trim()
    .max(1000)
    .optional(),
});
```

The exact limit is a product decision.

The important idea is:

```text
Client input
    ↓
Schema validation
    ↓
Business validation
    ↓
Database
```

# 17. Don't return unnecessary database data

Suppose the `Lesson` table contains:

```text
id
title
description
content
videoUrl
metadata
createdAt
updatedAt
```

The bookmark list probably doesn't need the entire lesson.

Instead:

```text
Bookmark
+
lesson.id
+
lesson.title
+
course.title
```

might be enough.

This is an important API design principle:

> **Return the data the client needs, not the entire database object.**

# 20. Deleting a bookmark

Possible endpoint:

```http
DELETE /api/v1/bookmarks/:bookmarkId
```

But there's an important security question:

> What if Rahul sends another student's bookmark ID?

The service must verify ownership.

Conceptually:

```text
bookmarkId
    ↓
Find bookmark
    ↓
Get enrollment
    ↓
Get student
    ↓
Compare with req.user.userId
    ↓
Delete only if authorized
```

Never do:

```ts
await prisma.bookmark.delete({
  where: {
    id: bookmarkId,
  },
});
```

without authorization checks.

---

# 21. Better repository query

A safer pattern is to make ownership part of the query.

Conceptually:

```ts
await prisma.bookmark.deleteMany({
  where: {
    id: bookmarkId,
    enrollment: {
      studentId,
    },
  },
});
```

Then check whether:

```text
count === 1
```

If:

```text
count === 0
```

the bookmark either:

```text
doesn't exist
```

or:

```text
doesn't belong to the student
```

Depending on your security policy, you can return `404` rather than revealing which one.

This is a powerful pattern:

> **Push authorization conditions as close to the database query as practical.**

# 28. Useful database indexes

Our model might have:

```prisma
@@index([enrollmentId])
@@index([lessonId])
```

Why?

Because common queries include:

```text
Give me this student's bookmarks.
```

and:

```text
Find bookmarks for this lesson.
```

If you frequently query:

```text
enrollmentId + createdAt
```

you could eventually consider:

```prisma
@@index([enrollmentId, createdAt])
```

But don't add composite indexes without a real query need.

# 31. Controller example

The controller remains thin:

```ts
export const createBookmark = asyncHandler(
  async (req, res) => {
    const studentId = req.user.userId;
    const { lessonId } = req.params;

    const bookmark =
      await bookmarkService.create({
        studentId,
        lessonId,
        positionSeconds: req.body.positionSeconds,
        note: req.body.note,
      });

    res.status(201).json({
      success: true,
      data: bookmark,
    });
  }
);
```

Notice:

```text
Controller
→ extracts request data

Service
→ handles business logic

Repository
→ handles persistence
```

Exactly the architecture we've been following.

# 33. What if the course is unpublished?

Suppose:

```text
Student enrolled in Course A
```

Then instructor unpublishes Course A.

Should the student still be able to access existing bookmarks?

That's a product rule.

Possible policies:

### Policy A

```text
Unpublished
↓
Existing students retain access
```

### Policy B

```text
Unpublished
↓
No student access
```

For an LMS, Policy A is often more user-friendly.

But the important lesson is:

> **Authorization behavior must be defined as a product rule rather than accidentally emerging from database queries.**

---

# 34. What if a lesson is deleted?

Suppose Rahul has:

```text
Bookmark → Lesson 10
```

Then an instructor deletes Lesson 10.

What happens to the bookmark?

We have several choices:

```text
Delete bookmark automatically
```

or:

```text
Keep bookmark but mark content unavailable
```

or:

```text
Soft-delete lesson
```

For a learning platform, soft deletion can sometimes be valuable because historical records may still reference the lesson.

This is another reason database relationships and deletion behavior need careful design.

---

# 35. Referential integrity

If we have:

```text
Bookmark
    ↓
Lesson
```

we should decide what happens when the lesson is deleted.

For example:

```prisma
onDelete: Cascade
```

would mean:

```text
Delete Lesson
     ↓
Delete its bookmarks
```

But you shouldn't automatically choose cascade everywhere.

Think about the data lifecycle first.

For bookmarks, cascade may be reasonable if the bookmark has no meaning without the lesson.

For historical learning records, however, you might want a different strategy.

# 38. Key principles from 6.6

Remember these:

### 1. Bookmark is student-specific

```text
Same lesson
   ↓
Different students
   ↓
Different bookmarks
```

### 2. Bookmark is intentional

Unlike progress, the student explicitly creates it.

### 3. Don't confuse bookmark with completion

```text
Bookmark ≠ Completed
```

### 4. Don't assume one bookmark per lesson

Multiple bookmarks can be useful for videos.

### 5. Authorization is mandatory

A student can only bookmark content they're allowed to access.

### 6. Position should be numeric

Prefer:

```text
positionSeconds = 1475
```

over:

```text
"24:35"
```

### 7. Think ahead to AI

Bookmarks can become excellent entry points for:

```text
AI explanations
AI quizzes
Revision
RAG
Personalized learning
```
