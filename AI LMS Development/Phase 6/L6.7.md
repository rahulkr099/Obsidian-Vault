# Lesson 6.7 — Notes

In **6.6 — Bookmarks**, we built a way for students to save an important location.

Now we add something different:

> **Notes let students write and save their own thoughts, explanations, questions, and reminders while learning.**

For example:

```text
Lesson: JWT Authentication
Position: 24:35

📝 Note:
"Refresh token rotation is important because
stolen refresh tokens should not remain valid forever."
```

This is especially useful in an AI LMS because later we can allow the AI Tutor to work with a student's notes.

---

# 1. Bookmark vs Note

This distinction is important.

### Bookmark

```text
🔖 "Save this location."
```

Example:

```text
24:35
```

### Note

```text
📝 "Save my thoughts about this content."
```

Example:

```text
"Need to revise refresh token rotation."
```

So:

```text
Bookmark
    ↓
Where?

Note
    ↓
What do I think?
```

They can work together:

```text
Lesson
  │
  ├── 🔖 Bookmark at 24:35
  │
  └── 📝 Note:
       "Important security concept"
```

---

# 2. Why notes belong to the student

Suppose the lesson is:

```text
"Database Transactions"
```

Rahul writes:

```text
"Transactions ensure multiple operations
behave as one unit."
```

Another student might write:

```text
"Need to understand isolation levels again."
```

Same lesson, completely different notes.

Therefore:

```text
Lesson
   │
   ├── Student A → Note A
   ├── Student B → Note B
   └── Student C → Note C
```

Notes belong to the **student's learning context**, not to the lesson itself.

---

# 3. Database relationship

A useful model is:

```text
Enrollment
    │
    │ 1:N
    ↓
  Note
    │
    │ N:1
    ↓
 Lesson
```

Conceptually:

```text
User
  ↓
Enrollment
  ↓
Note
  ↓
Lesson
  ↓
Course
```

This allows us to answer:

> Which student created this note, and where in the course does it belong?

---

# 4. Prisma model

A simple model:

```prisma
model Note {
  id           String   @id @default(uuid())

  enrollmentId String
  lessonId     String

  content      String
  positionSeconds Int?

  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  enrollment   Enrollment @relation(
    fields: [enrollmentId],
    references: [id]
  )

  lesson       Lesson @relation(
    fields: [lessonId],
    references: [id]
  )

  @@index([enrollmentId])
  @@index([lessonId])
}
```

The important fields are:

```text
enrollmentId
lessonId
content
positionSeconds
createdAt
updatedAt
```

---

# 5. Why `positionSeconds`?

This is particularly useful for videos.

Suppose the student writes:

```text
"Access tokens expire, refresh tokens are used
to obtain new access tokens."
```

while watching:

```text
18:42
```

We can store:

```text
positionSeconds = 1122
```

Then the UI can show:

```text
📝 18:42
Access tokens expire...
```

When the student clicks the note:

```text
Open Lesson
      ↓
Jump to 18:42
```

This creates a much better learning experience.

---

# 6. But position should be optional

Not every note needs a precise location.

For example:

```text
Course:
PostgreSQL

General note:
"Revise indexing before interview."
```

This might not belong to a particular video timestamp.

Therefore:

```text
positionSeconds = NULL
```

is perfectly valid.

So:

```text
Note
├── lessonId
├── content
└── optional positionSeconds
```

---

# 7. Note creation API

A possible endpoint:

```http
POST /api/v1/lessons/:lessonId/notes
```

Request:

```json
{
  "content": "Important concept — revise this before the exam.",
  "positionSeconds": 1480
}
```

The backend obtains the student from:

```ts
const studentId = req.user.userId;
```

Not:

```json
{
  "studentId": "..."
}
```

The client should never be trusted to tell the server whose note is being created.

---

# 8. Request flow

The architecture remains:

```text
HTTP Request
     ↓
Authentication
     ↓
Validation
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Prisma
     ↓
PostgreSQL
```

The controller should remain thin.

---

# 9. Controller

Conceptually:

```ts
export const createNote = asyncHandler(
  async (req, res) => {
    const studentId = req.user.userId;
    const { lessonId } = req.params;

    const note = await noteService.create({
      studentId,
      lessonId,
      content: req.body.content,
      positionSeconds: req.body.positionSeconds,
    });

    res.status(201).json({
      success: true,
      data: note,
    });
  }
);
```

The controller isn't responsible for deciding:

```text
❌ Does this student have access?
❌ Does the lesson exist?
❌ Is the note valid?
❌ Does this note belong to the student?
```

Those belong in the service/repository layers.

---

# 10. Validation

Notes contain user-generated text, so validation is important.

For example:

```ts
const createNoteSchema = z.object({
  content: z
    .string()
    .trim()
    .min(1)
    .max(5000),

  positionSeconds: z
    .number()
    .int()
    .min(0)
    .optional(),
});
```

This prevents:

```text
Empty notes
Extremely large notes
Negative positions
Invalid data types
```

The exact limits can be changed later.

---

# 11. Why not allow unlimited note length?

Imagine someone sends:

```text
content = "A" × 50 million characters
```

That could cause:

```text
Large request
     ↓
Large database row
     ↓
Memory usage
     ↓
Potential abuse
```

So input limits are part of both:

```text
Validation
+
Security
```

A reasonable note limit might initially be:

```text
5000 characters
```

and we can adjust it based on actual product requirements.

---

# 12. Service layer

The service needs to establish that the student can access the lesson.

Conceptually:

```ts
async function createNote({
  studentId,
  lessonId,
  content,
  positionSeconds,
}) {
  const lesson = await lessonRepository.findById(lessonId);

  if (!lesson) {
    throw new AppError("Lesson not found", 404);
  }

  const enrollment =
    await enrollmentRepository.findByStudentAndCourse(
      studentId,
      lesson.courseId
    );

  if (!enrollment) {
    throw new AppError(
      "You are not enrolled in this course",
      403
    );
  }

  return noteRepository.create({
    enrollmentId: enrollment.id,
    lessonId,
    content,
    positionSeconds,
  });
}
```

The key authorization chain:

```text
Authenticated Student
        ↓
Enrollment
        ↓
Course
        ↓
Lesson
```

---

# 13. Why authorization matters

Suppose:

```text
Rahul
  ↓
Course A
```

but he isn't enrolled in:

```text
Course B
```

He somehow discovers:

```text
lesson_B_123
```

and sends:

```http
POST /lessons/lesson_B_123/notes
```

The server should reject it.

Otherwise, Rahul could create records for content he doesn't have access to.

So:

```text
Authentication
    +
Enrollment authorization
    =
Protected notes
```

---

# 14. Reading notes

A student needs to retrieve their notes.

Possible endpoint:

```http
GET /api/v1/notes
```

Or:

```http
GET /api/v1/courses/:courseId/notes
```

Or:

```http
GET /api/v1/lessons/:lessonId/notes
```

The choice depends on the UI.

For example, the lesson page might need:

```text
GET /lessons/lesson_123/notes
```

while the dashboard might need:

```text
GET /courses/course_123/notes
```

Both can be useful.

---

# 15. Never trust a note ID for ownership

Suppose Rahul requests:

```http
GET /api/v1/notes/note_999
```

The backend must verify:

```text
note_999
    ↓
belongs to Rahul?
```

Don't simply do:

```ts
const note = await prisma.note.findUnique({
  where: {
    id: noteId,
  },
});
```

and return it.

Otherwise:

```text
Rahul
  ↓
changes note ID
  ↓
reads another student's note
```

That's an **authorization vulnerability**.

---

# 16. Ownership-aware queries

A safer approach is to include the student relationship in the query.

Conceptually:

```ts
const note = await prisma.note.findFirst({
  where: {
    id: noteId,
    enrollment: {
      studentId,
    },
  },
});
```

Now the database query itself expresses:

> Find this note **only if it belongs to this student**.

This pattern is very useful for multi-user applications.

---

# 17. Updating notes

Students should usually be able to edit their notes.

Endpoint:

```http
PATCH /api/v1/notes/:noteId
```

Request:

```json
{
  "content": "Updated explanation of refresh tokens."
}
```

Flow:

```text
Request
  ↓
Authenticate
  ↓
Find note + verify ownership
  ↓
Validate content
  ↓
Update
```

Again:

```text
User identity
→ req.user.userId
```

not the request body.

---

# 18. Deleting notes

Endpoint:

```http
DELETE /api/v1/notes/:noteId
```

But deletion must be ownership-aware.

Conceptually:

```ts
await prisma.note.deleteMany({
  where: {
    id: noteId,
    enrollment: {
      studentId,
    },
  },
});
```

Then:

```text
count === 1
    ↓
deleted

count === 0
    ↓
not found / not authorized
```

Depending on your API security policy, returning `404` can avoid revealing whether another user's note exists.

---

# 19. Note lifecycle

The basic lifecycle is:

```text
Create
  ↓
Read
  ↓
Update
  ↓
Delete
```

But the important thing is:

```text
Student
   ↓
owns
   ↓
Note
```

So every operation should respect ownership.

# 20. Notes vs public discussions

Don't confuse private student notes with course discussions.

### Private note

```text
Rahul
  ↓
"My understanding of JWT"
  ↓
Only Rahul
```

### Course discussion

```text
Rahul
  ↓
Question
  ↓
Other students
  ↓
Instructor
```

These should be separate systems.

Our Phase 6.7 notes are **personal learning notes**.

# 23. Notes and Learning History

Later we'll build:

```text
6.8 — Learning History
```

A note creation could become a meaningful activity:

```text
10:32
Created note in JWT Authentication
```

But we shouldn't necessarily store every note edit as a separate history record.

We need to distinguish:

```text
Current state
```

from:

```text
Activity/event history
```

That's an important architecture concept.

---

# 24. Should we keep note edit history?

For a simple LMS:

```text
Note
   ↓
current content only
```

is enough.

For an advanced system:

```text
Note
   ↓
Version 1
Version 2
Version 3
```

could allow undo/history.

But don't build versioning unless there is a real requirement.

This is a good example of avoiding premature complexity.

---

# 25. Database indexes

Useful indexes include:

```prisma
@@index([enrollmentId])
@@index([lessonId])
```

Because common queries are:

```text
Give me all notes for this student.
```

and:

```text
Give me all notes for this lesson.
```

If we frequently need:

```text
student + lesson
```

we may later use a composite index depending on the actual query patterns.

Again:

> **Indexes should follow queries, not guesses.**

---

# 26. Ordering notes

For a lesson page, we might want:

```text
Notes
──────────────
08:20
18:45
31:12
```

So for video lessons:

```text
ORDER BY positionSeconds ASC
```

This lets the student see notes in the same order as the content.

For a general notes dashboard, we may instead use:

```text
ORDER BY updatedAt DESC
```

showing the most recently edited notes first.

The correct ordering depends on the screen.

# 27. Pagination

Suppose Rahul has:

```text
2,000 notes
```

```http

```

with all 2,000 records.

Use:

```http
GET /notes?page=1&limit=20
```

This is the same pagination concept from Phase 2.

For example:



# 31. Privacy

Personal notes can contain sensitive information.

Therefore:

```text
Student A's notes
       ↓
Student A only
```

By default, the instructor should not automatically see them.

If you later add:

```text
Share note
```

that should be an explicit feature with explicit authorization.

Never assume:

```text
Instructor → can read every student note
```

just because the instructor owns the course.

This is a good example of **least privilege**.

# 32. API response

A useful note response:

```json
{
  "success": true,
  "data": {
    "id": "note_123",
    "lessonId": "lesson_42",
    "lessonTitle": "JWT Authentication",
    "positionSeconds": 1480,
    "content": "Important security concept.",
    "createdAt": "2026-08-14T10:30:00Z",
    "updatedAt": "2026-08-14T10:30:00Z"
  }
}
```

Notice that we can include:

```text
lessonTitle
```

without exposing the entire lesson object.

This is a good API response design.

# 33. Soft delete or hard delete?

For personal notes, hard deletion can be perfectly reasonable:

```text
DELETE
  ↓
Note removed
```

You might choose soft deletion if:

```text
Audit requirements
Note recovery
Version history
```

are important.

For our initial LMS:

```text
Personal note
→ hard delete
```

is a reasonable default.

# 34. Important edge cases

Let's think like backend engineers.

### Empty note

```text
""
```

Reject.

### Huge note

```text
50 MB
```

Reject.

### Negative position

```text
-100
```

Reject.

### Position beyond video duration

```text
999999
```

Reject or normalize.

### Lesson doesn't exist

```text
404
```

### Student isn't enrolled

```text
403
```

### Another user's note

```text
Do not return it.
```

### Duplicate notes

Usually allowed.

A student can intentionally write:

```text
"Important"
```

twice if the product doesn't restrict it.

---

# 35. Notes are not necessarily unique

Unlike enrollment:

```text
student + course
```

or lesson completion:

```text
enrollment + lesson
```

notes usually don't need a uniqueness constraint.

For example:

```text
Same lesson
   ↓
Note 1
Note 2
Note 3
```

is perfectly valid.

So don't add:

```prisma
@@unique([enrollmentId, lessonId])
```

unless your product explicitly wants only one note per lesson.

This separation is healthy.

## Answers

```text
1. A bookmark saves a useful location; a note stores
   the student's own thoughts or information.

2. Because different students can have different notes
   about the same lesson.

3. Some notes are attached to a specific video position,
   while others are general lesson notes.

4. Not necessarily. A student may want multiple notes
   in the same lesson.

5. Do not return or modify it. Ownership must be verified.

6. To prevent huge requests, excessive database storage,
   and potential abuse.

7. The AI can use personal notes to understand what the
   student struggled with and provide more personalized
   explanations, revision, and RAG-based answers.

8. req.user.userId, because it comes from trusted
   authentication rather than client-controlled input.
```
