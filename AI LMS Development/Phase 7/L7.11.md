# Lesson 7.11 — AI Reliability, Error Handling & Retries

So far, our AI Tutor can:

```text
Student
   ↓
Authentication
   ↓
Authorization
   ↓
Course + Lesson Context
   ↓
Conversation History
   ↓
Context Management
   ↓
Prompt
   ↓
AI Provider
   ↓
LLM
   ↓
Streaming
```

But there's one big problem:

> **AI providers can fail.**

Networks fail. Providers rate-limit requests. Models time out. Streams disconnect. Structured output can be invalid.

A production AI application must expect these failures.

---

# 1. AI Is an External Dependency

Your application controls:

```text
id="c0xq5e"
PostgreSQL
Your services
Your API
Your frontend
```

But it doesn't control:

```text
id="f4k2hs"
AI provider
Internet
Model availability
Provider rate limits
Provider latency
```

So architecturally:

```text
Your Application
       │
       ↓
  AI Provider
       │
       ↓
     LLM
```

The provider is an **external dependency**.

And external dependencies can fail.

---

# 2. Never Assume the AI Request Will Succeed

Beginner approach:

```ts
const response =
  await aiProvider.generateText(input);

return response;
```

This assumes:

```text
request
  ↓
success
```

Production approach:

```text
request
  ↓
timeout?
  ↓
rate limited?
  ↓
provider error?
  ↓
invalid output?
  ↓
network failure?
  ↓
retry?
  ↓
fallback?
  ↓
final result
```

Reliability means designing for failure **before** failure happens.

---

# 3. Common AI Failures

Let's categorize them.

### 1. Authentication failure

```text
Invalid API key
```

### 2. Rate limit

```text
Too many requests
```

### 3. Timeout

```text
Provider took too long
```

### 4. Network error

```text
Connection failed
```

### 5. Provider outage

```text
AI service unavailable
```

### 6. Invalid model/configuration

```text
Model unavailable
```

### 7. Invalid structured output

```text
Expected JSON
Received malformed data
```

### 8. Streaming failure

```text
Response started
        ↓
Connection interrupted
```

### 9. Internal application error

```text
Context builder failed
Database failed
```

Each type should be handled differently.

---

# 4. Don't Treat Every Error the Same

This is one of the most important concepts.

Suppose:

```text
401 Unauthorized
```

Retrying usually doesn't help.

```text
Database connection failure
```

A retry might help.

```text
429 Rate Limited
```

A delayed retry might help.

```text
400 Invalid Request
```

Retrying the exact same request probably won't help.

So:

> **Retry only errors that are potentially recoverable.**

---

# 5. Error Categories

A useful classification is:

```text
                 AI Error
                    │
       ┌────────────┼─────────────┐
       ↓            ↓             ↓
    Retryable    Non-retryable   User-caused
       │            │             │
    timeout      bad API key     invalid input
    429          invalid model   unauthorized
    temporary    malformed req   forbidden
    network
```

This makes retry decisions much easier.

---

# 6. Retryable vs Non-Retryable

### Usually retryable

```text
temporary network failure
provider timeout
temporary provider outage
429 rate limit
some 5xx errors
```

### Usually not retryable

```text
invalid API key
invalid request
invalid model name
forbidden access
malformed application input
authorization failure
```

The exact classification depends on the provider.

---

# 7. Why Retrying Can Be Dangerous

Suppose the student clicks:

> Generate a quiz.

Your backend calls the AI.

The request times out.

You retry automatically.

Now:

```text
Attempt 1
Attempt 2
```

That's okay if the operation is safe.

But imagine an AI operation that triggers some external side effect.

If you blindly retry:

```text
Attempt 1 → side effect
Attempt 2 → side effect again
```

you can duplicate the operation.

For our tutor, generation is mostly read/generate-oriented, so retries are easier.

But this is why **idempotency** matters.

---

# 8. What Is Idempotency?

An operation is idempotent if repeating it doesn't unintentionally create additional effects.

For example:

```text
GET /courses/123
```

can usually be repeated safely.

But:

```text
POST /payments
```

can create multiple payments if repeated carelessly.

AI generation is usually not a database side effect by itself, but our surrounding application might have side effects such as:

```text
usage records
credits
analytics
messages
```

So we should design carefully.

---

# 9. Request IDs

A useful concept is a unique request ID:

```text
req_abc123
```

For example:

```json
{
  "requestId": "req_abc123",
  "message": "Explain indexes."
}
```

The backend can use it for:

```text
logging
tracing
deduplication
debugging
```

You don't necessarily need the client to generate it. The server can generate an internal request ID.

---

# 10. Retry Architecture

Instead of putting retry logic everywhere:

```text
Controller
   ↓
try
catch
retry
retry
retry
```

create a reusable reliability layer:

```text
AIProvider
      ↓
Retry Policy
      ↓
Provider Adapter
      ↓
External AI API
```

Or:

```text
AITutorService
      ↓
ReliableAIClient
      ↓
AIProvider
```

This keeps reliability logic centralized.

---

# 11. Exponential Backoff

Suppose a provider returns:

```text
429 Too Many Requests
```

Don't immediately do:

```text
retry
retry
retry
retry
```

That can make the situation worse.

Instead use **exponential backoff**.

Conceptually:

```text
Attempt 1 → wait 500ms
Attempt 2 → wait 1s
Attempt 3 → wait 2s
Attempt 4 → wait 4s
```

The delay increases after each failure.

---

# 12. Why Backoff Works

Imagine 1,000 clients receive:

```text
429
```

If all immediately retry:

```text
1,000 requests
 ↓
provider
 ↓
429
 ↓
1,000 retries
 ↓
429
```

The system can become even more overloaded.

Backoff spreads retries over time:

```text
request
  ↓
delay
  ↓
retry
```

This is much healthier.

---

# 13. Add Jitter

There's another improvement:

> **Jitter**

Instead of every client waiting exactly:

```text
2 seconds
```

we add some randomness:

```text
1.7 sec
2.2 sec
1.9 sec
2.4 sec
```

This prevents many clients from retrying simultaneously.

Conceptually:

```text
delay =
baseDelay * 2^attempt
+
randomJitter
```

This is a common distributed-systems technique.

---

# 14. Retry Limits

Never retry forever.

Bad:

```text
while (true) {
  retry();
}
```

Instead:

```text
maxAttempts = 3
```

For example:

```text
Attempt 1
   ↓
failure
   ↓
Attempt 2
   ↓
failure
   ↓
Attempt 3
   ↓
failure
   ↓
Stop
```

Then return a controlled error.

---

# 15. Why Three Attempts?

Three is just an example.

The correct number depends on:

```text
operation
latency
cost
provider behavior
user experience
```

For an interactive AI chat, you generally don't want:

```text
10 retries
```

because the user could wait far too long.

A small number of controlled retries is usually better.

---

# 16. Total Timeout Budget

Retries create another problem.

Suppose each attempt can take:

```text
30 seconds
```

and you allow:

```text
3 attempts
```

Potentially:

```text
90 seconds
```

That's terrible for interactive chat.

So you need both:

```text
Per-attempt timeout
+
Overall request deadline
```

For example:

```text
Total budget = 20 seconds
```

Even if an individual retry is technically possible, the overall user request should stop when the deadline is reached.

---

# 17. Timeout vs Abort

These are related but different.

### Timeout

Your application says:

> This request has taken too long.

### Abort

Your application actively cancels the operation.

For example:

```text
Timeout
   ↓
AbortController.abort()
```

Or:

```text
User clicks Stop
   ↓
AbortController.abort()
```

The same cancellation mechanism can often handle both.

---

# 18. AbortController

We saw this in streaming.

For example:

```ts
const controller =
  new AbortController();

setTimeout(() => {
  controller.abort();
}, timeout);
```

Then pass:

```ts
signal: controller.signal
```

to the provider if supported.

Now:

```text
timeout
 ↓
abort
 ↓
provider request cancelled
```

This prevents work from continuing unnecessarily.

---

# 19. Error Translation

Your AI provider may return something like:

```text
SomeVendorSpecificError
```

Don't expose that directly to the frontend.

Instead, translate it into your application's error model.

For example:

```ts
class AIProviderError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly retryable: boolean
  ) {
    super(message);
  }
}
```

Then:

```text
Provider-specific error
        ↓
AIProviderError
        ↓
Application
```

---

# 20. Application Error Types

You might eventually have:

```ts
type AIErrorCode =
  | "AI_TIMEOUT"
  | "AI_RATE_LIMITED"
  | "AI_UNAVAILABLE"
  | "AI_INVALID_RESPONSE"
  | "AI_CONFIGURATION_ERROR";
```

Now the rest of your application doesn't care which provider produced the error.

---

# 21. User-Friendly Errors

Don't return:

```json
{
  "error": "ECONNRESET at socket..."
}
```

to the student.

Instead:

```json
{
  "success": false,
  "error": {
    "code": "AI_UNAVAILABLE",
    "message": "The AI tutor is temporarily unavailable. Please try again."
  }
}
```

The user needs a useful message.

Your logs can contain the technical details.

---

# 22. Internal Error vs Public Error

Keep two layers:

```text
Internal:
"Provider returned 503 after 12.4 seconds"

Public:
"AI tutor is temporarily unavailable."
```

This prevents:

```text
sensitive internals
provider details
stack traces
configuration information
```

from leaking to users.

---

# 23. Error Logging

When an AI request fails, log useful metadata:

```text
requestId
userId
conversationId
provider
model
errorCode
attempt
duration
```

But avoid blindly logging:

```text
entire conversation
private course content
tokens/secrets
sensitive user data
```

Use structured logging and data minimization.

---

# 24. Example Log

Conceptually:

```json
{
  "level": "error",
  "event": "ai_generation_failed",
  "requestId": "req_123",
  "conversationId": "conv_456",
  "provider": "provider-a",
  "model": "model-x",
  "errorCode": "AI_TIMEOUT",
  "attempt": 2,
  "durationMs": 8000
}
```

This is much more useful than:

```text
ERROR AI FAILED
```

---

# 25. Retry Flow

A clean retry flow:

```text
AI Request
    ↓
Attempt 1
    ↓
Failure
    ↓
Is retryable?
   / \
 No   Yes
 ↓      ↓
Fail   Backoff
         ↓
      Attempt 2
         ↓
       Success?
       /     \
     Yes      No
      ↓        ↓
   Return    Retry?
```

This should be deterministic and easy to test.

---

# 26. Don't Retry Validation Errors

Suppose the student sends:

```text
message = ""
```

Your validation catches it.

Don't do:

```text
validation failed
 ↓
retry AI
```

That's pointless.

Instead:

```text
400 Bad Request
```

immediately.

---

# 27. Don't Retry Authorization Errors

Suppose:

```text
Student isn't enrolled in course.
```

Result:

```text
403 Forbidden
```

Don't retry.

Authorization won't become valid just because you called the same function again.

---

# 28. Don't Retry Invalid API Keys

Suppose the provider returns:

```text
401
```

Retrying three times doesn't magically make the API key correct.

This should normally trigger:

```text
configuration alert
```

rather than repeated user-facing retries.

---

# 29. Rate Limit Handling

Rate limiting is different.

Suppose:

```text
429
```

The provider may tell you:

```text
Retry-After: 2
```

If the provider gives a retry delay, respect it where appropriate.

Conceptually:

```text
429
 ↓
Retry-After
 ↓
Wait
 ↓
Retry
```

Don't blindly use your own delay if the provider explicitly tells you when to retry.

---

# 30. Provider Outages

Suppose:

```text
Provider A
   ↓
503
```

If you have only one provider:

```text
AI unavailable
```

But if your architecture supports multiple providers:

```text
Provider A
   ↓
failure
   ↓
Provider B
   ↓
success
```

you can implement **fallback providers**.

---

# 31. Fallback Providers

Our abstraction makes this possible:

```text
AIProvider
 ├── ProviderA
 └── ProviderB
```

Then:

```text
Primary Provider
      ↓
   failure
      ↓
Fallback Provider
```

But don't automatically fall back for every error.

For example:

```text
invalid API key
```

should probably not cause:

```text
switch provider
```

while:

```text
temporary outage
```

might.

---

# 32. Provider Routing

Eventually we could have:

```text
AI Router
   ↓
Choose provider
```

based on:

```text
availability
cost
latency
model capability
task
```

For example:

```text
Explanation
   ↓
Provider A

Complex reasoning
   ↓
Provider B

Fallback
   ↓
Provider C
```

This becomes more useful as your AI LMS grows.

---

# 33. Don't Build Multi-Provider Complexity Too Early

For your first version:

```text
One provider
+
Clean abstraction
```

is enough.

You want:

```text
Provider abstraction
```

now.

You don't necessarily need:

```text
5 providers
routing engine
load balancing
fallback tree
```

on day one.

Build complexity only when you have a real requirement.

---

# 34. Circuit Breaker

Now we get into distributed systems.

Suppose Provider A is completely down.

Without protection:

```text
Request
 ↓
Provider A
 ↓
failure
 ↓
retry
 ↓
failure
 ↓
retry
 ↓
failure
```

Every user request keeps hammering the broken provider.

A **circuit breaker** can temporarily stop requests.

---

# 35. Circuit Breaker States

A basic circuit breaker has:

```text
CLOSED
   ↓
failures exceed threshold
   ↓
OPEN
   ↓
wait
   ↓
HALF-OPEN
   ↓
test request
   ↓
success → CLOSED
failure → OPEN
```

---

# 36. Closed State

Normal operation:

```text
Request
 ↓
Provider
 ↓
Success
```

Circuit:

```text
CLOSED
```

---

# 37. Open State

Too many failures:

```text
Provider
 ↓
failure
 ↓
failure
 ↓
failure
```

Circuit becomes:

```text
OPEN
```

Now requests fail fast:

```text
Request
 ↓
Circuit Breaker
 ↓
Provider unavailable
```

We don't even call the provider.

This protects:

```text
your server
provider
latency
user experience
```

---

# 38. Half-Open State

After waiting:

```text
OPEN
 ↓
cooldown
 ↓
HALF-OPEN
```

Allow a small test request.

If successful:

```text
HALF-OPEN
 ↓
success
 ↓
CLOSED
```

If failed:

```text
HALF-OPEN
 ↓
failure
 ↓
OPEN
```

This is a classic resilience pattern.

---

# 39. Do You Need a Circuit Breaker Now?

Probably not for your first LMS version.

But you should understand the concept.

Your progression can be:

```text
Version 1
Basic error handling

Version 2
Timeouts + retries

Version 3
Fallback provider

Version 4
Circuit breaker
```

Don't implement advanced distributed-system machinery before you need it.

---

# 40. Streaming Reliability

Now combine today's lesson with Lesson 7.10.

Suppose:

```text
AI stream starts
 ↓
Chunk 1
 ↓
Chunk 2
 ↓
Chunk 3
 ↓
Provider disconnects
```

What happens?

You should:

```text
detect failure
 ↓
stop stream
 ↓
notify client
 ↓
do not mark completed
 ↓
log failure
```

You may optionally retry, but streaming retries are more complicated.

---

# 41. Should We Retry a Broken Stream?

Not automatically in every case.

Imagine:

```text
50% response already sent
```

If you restart the generation:

```text
new stream
 ↓
entire answer starts again
```

The frontend could receive duplicate content.

Therefore:

> **Streaming retries require special handling.**

For an initial implementation, it can be safer to:

```text
stream failure
 ↓
send error
 ↓
let user retry
```

rather than automatically restarting the entire generation.

---

# 42. User-Initiated Retry

A nice UX is:

```text
AI response failed.

[ Try again ]
```

The user explicitly chooses to retry.

This avoids:

```text
automatic duplicate generation
```

and gives the user control.

---

# 43. Failed vs Cancelled

These are not the same.

### Failed

```text
Something went wrong.
```

### Cancelled

```text
User intentionally stopped generation.
```

Your application should distinguish them.

For example:

```ts
type GenerationStatus =
  | "completed"
  | "failed"
  | "cancelled";
```

This becomes useful for analytics.

---

# 44. Context Failure

AI generation might fail before the provider is even called.

For example:

```text
Load course
 ↓
Database timeout
```

That's not an AI provider failure.

So our architecture should distinguish:

```text
Application failure
```

from:

```text
Provider failure
```

For example:

```text
Database
 ↓
DB error

AI Provider
 ↓
Provider error
```

Don't retry an AI request if the real problem is a broken database connection.

---

# 45. Error Boundary

Our tutor pipeline can look like:

```text
Request
  ↓
Validation
  ↓
Authorization
  ↓
Context
  ↓
AI Reliability Layer
  ↓
AI Provider
  ↓
Output Validation
  ↓
Response
```

Each stage can fail.

Each stage should have an appropriate error strategy.

---

# 46. Reliability Matrix

A useful mental table:

|Failure|Retry?|User sees|
|---|---|---|
|Invalid input|❌|Fix request|
|Unauthorized|❌|Access denied|
|Forbidden|❌|Access denied|
|Invalid API key|❌|Temporary service error|
|429 rate limit|✅ sometimes|Try again shortly|
|Provider 503|✅|Temporary unavailable|
|Timeout|✅ limited|Try again|
|DB failure|✅ limited|Temporary error|
|Invalid AI output|✅ once|Try again|
|Client cancellation|❌|Generation stopped|
|Stream interruption|Usually manual retry|Generation interrupted|

The exact behavior depends on your application.

---

# 47. Structured Output Failure

Remember Lesson 7.9.

Suppose:

```text
LLM
 ↓
JSON
 ↓
Schema validation
 ↓
FAILED
```

This is potentially retryable.

You can do:

```text
Attempt 1
 ↓
invalid structure
 ↓
Retry with stricter instruction
 ↓
Attempt 2
```

But limit retries.

For example:

```text
max structured-output retries = 1
```

Then:

```text
still invalid
 ↓
AI_INVALID_RESPONSE
```

---

# 48. Don't Retry Bad Prompts Forever

Suppose your prompt consistently produces invalid output.

Then:

```text
retry
retry
retry
```

doesn't solve the root problem.

You need:

```text
prompt improvement
schema improvement
provider configuration
model change
```

Reliability mechanisms should not hide application bugs.

---

# 49. Graceful Degradation

What happens if AI is unavailable?

Your LMS should still work.

For example:

```text
Course browsing       → works
Lessons               → works
Assignments           → works
Progress tracking     → works
AI Tutor              → temporarily unavailable
```

This is **graceful degradation**.

Don't make the entire LMS depend on the AI service being healthy.

---

# 50. AI Is a Feature, Not the Entire Application

This is an important architecture principle.

Your system:

```text
                    LMS
                     │
      ┌──────────────┼──────────────┐
      ↓              ↓              ↓
   Courses        Progress        AI Tutor
      │              │              │
   PostgreSQL     PostgreSQL      AI Provider
```

If the AI provider fails:

```text
Courses        → still work
Progress       → still work
AI Tutor       → degraded
```

That's good architecture.

---

# 51. Rate Limiting Your Own AI Endpoint

Provider rate limits aren't enough.

You should also protect your API.

For example:

```text
Student
 ↓
POST /ai/chat
 ↓
Application rate limiter
 ↓
AI Provider
```

You might enforce:

```text
X requests / minute
```

or:

```text
Y generations / hour
```

depending on your product.

This prevents abuse and controls cost.

---

# 52. Usage Limits

Eventually you might have:

```text
Free Student
→ 20 AI requests/day

Premium Student
→ 200 AI requests/day
```

The backend can check:

```text
User
 ↓
Usage
 ↓
Limit
 ↓
AI
```

This is another reason to track AI generations.

---

# 53. Cost Protection

Imagine a malicious client sends:

```text
10,000 AI requests
```

Even if the provider handles the rate limit, your bill could become large.

So:

```text
Authentication
+
Rate limiting
+
Usage limits
+
Token limits
+
Request size limits
```

are all important.

---

# 54. Request Size Limits

Don't allow:

```text
message = 5 MB
```

without a reason.

A student could send enormous text and cause:

```text
large input tokens
higher cost
higher latency
```

Validate input length before AI generation.

For example:

```text
maximum message size
```

and eventually:

```text
maximum estimated input tokens
```

# 56. Retry Utility

A reusable retry function could conceptually look like:

```ts
async function retry<T>(
  operation: () => Promise<T>,
  options: RetryOptions
): Promise<T> {
  // attempt
  // determine retryability
  // backoff
  // retry
}
```

The important part isn't the exact implementation.

The important part is:

```text
retry policy
```

should be centralized.

---

# 57. Retry Policy

For example:

```ts
interface RetryPolicy {
  maxAttempts: number;
  shouldRetry(error: unknown): boolean;
  getDelay(attempt: number): number;
}
```

Then:

```text
AI Reliability Layer
       ↓
RetryPolicy
```

This makes the behavior testable.

---

# 58. Don't Put Retry Logic in Every Provider

Bad:

```text
ProviderA
  retry...

ProviderB
  retry...

ProviderC
  retry...
```

Now each provider behaves differently.

Better:

```text
ReliableAIClient
      ↓
RetryPolicy
      ↓
AIProvider
```

Provider adapters should primarily handle provider-specific communication.

---

# 59. Error Normalization

Similarly:

```text
Provider A error
Provider B error
Provider C error
```

should become:

```text
AI_TIMEOUT
AI_RATE_LIMITED
AI_UNAVAILABLE
AI_INVALID_RESPONSE
```

Then your retry layer can make decisions consistently.

---

# 60. Testing Reliability

This is where normal software engineering becomes very important.

You should be able to simulate:

```text
provider succeeds
provider times out
provider returns 429
provider returns 500
provider returns invalid output
provider stream fails
database fails
client disconnects
```

Then verify:

```text
retry happened?
correct number of times?
correct delay?
correct public error?
message persisted?
stream closed?
```

Don't wait for real provider outages to discover these bugs.

---

# 61. Mock the AI Provider

Because we created:

```ts
interface AIProvider
```

we can create:

```ts
class FakeAIProvider
```

for tests.

Example:

```ts
class FakeAIProvider
  implements AIProvider {

  async generateText() {
    throw new AIProviderError(
      "Temporary failure",
      "AI_UNAVAILABLE",
      true
    );
  }
}
```

Now you can test:

```text
AI unavailable
 ↓
retry
 ↓
fallback
```

without calling a real AI API.

This is one of the biggest benefits of provider abstraction.

# 67. The Golden Rule

Remember this:

> **Treat AI as an unreliable external dependency.**

Don't build your system around:

```text
AI will always respond.
```

Build around:

```text
AI might fail.
What should my application do when it does?
```

That mindset is what separates a demo from a production system.

# 68. What You Learned

|Concept|Purpose|
|---|---|
|Retry|Recover from temporary failures|
|Exponential backoff|Prevent aggressive retries|
|Jitter|Spread retry traffic|
|Timeout|Stop excessively slow requests|
|AbortController|Cancel active work|
|Error normalization|Hide provider-specific errors|
|Fallback|Use another provider when appropriate|
|Circuit breaker|Stop hammering unhealthy providers|
|Idempotency|Prevent duplicate side effects|
|Graceful degradation|Keep LMS working when AI fails|
|Rate limiting|Protect the AI endpoint|
|Usage limits|Control cost|
|Fault injection|Test failure scenarios|
|Observability|Understand production failures|

# 🧠 Interview Question

### How would you make an AI API reliable in production?

A strong answer:

> "I'd treat the AI provider as an unreliable external dependency. I'd use timeouts and cancellation, classify errors into retryable and non-retryable categories, use limited retries with exponential backoff and jitter for temporary failures, normalize provider errors into application-level errors, and optionally use a fallback provider. I'd also protect the endpoint with rate limits and usage quotas, log structured request metadata for observability, and ensure the LMS can continue operating if the AI service is unavailable."

That's a very strong backend engineering answer.
