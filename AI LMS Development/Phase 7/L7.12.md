# 1. What Is Observability?

Observability means being able to understand what is happening inside your application by looking at the data it produces.

For our AI system:

```text
Student
   ↓
AI Request
   ↓
Provider
   ↓
LLM
   ↓
Response
```

We want to know:

```text
Who requested it?
Which course?
Which lesson?
Which model?
How long did it take?
How many tokens?
How much did it cost?
Did it succeed?
Did we retry?
Did streaming fail?
```

That's AI observability.

---

# 2. Logging vs Metrics vs Traces

These three concepts are closely related but different.

### Logs

Tell you:

> **What happened?**

Example:

```text
AI request failed with timeout.
```

### Metrics

Tell you:

> **How much/how often?**

Example:

```text
AI requests today: 15,230
Average latency: 2.4 sec
Error rate: 1.7%
```

### Traces

Tell you:

> **How did one request travel through the system?**

Example:

```text
HTTP Request
   ↓ 12ms
Auth
   ↓ 8ms
Database
   ↓ 42ms
Context Builder
   ↓ 30ms
AI Provider
   ↓ 2.4s
Response
```

A production AI system benefits from all three.

# 5. Why Keep an AI Generation Record?

Because the normal message table doesn't contain enough information.

Your message might contain:

```text
User:
Explain indexes.

Assistant:
Indexes improve lookup performance...
```

But it doesn't tell you:

```text
Which model?
How many tokens?
How much did it cost?
How long did it take?
How many retries?
```

Therefore:

```text
Messages
   +
AI Generations
```

are separate concepts.

# 6. Message vs Generation

Think of it like this:

### Message

Represents:

> **What the student and tutor said.**

### Generation

Represents:

> **How the AI produced the tutor response.**

So:

```text
Conversation
   │
   ├── User Message
   │
   └── Assistant Message
           │
           ↓
      AI Generation
```

The assistant message can reference the generation that produced it.

# 9. Provider and Model

Always record:

```text
provider
model
```

For example:

```text
provider = "provider-a"
model = "model-x"
```

Why?

Because models change.

Suppose:

```text
August:
model-x
```

and later:

```text
September:
model-y
```

If students suddenly report that answers are worse, you need to know which model produced which responses.

---

# 10. Token Usage

AI providers commonly measure usage in tokens.

Very roughly:

```text
Input tokens
+
Output tokens
=
Total tokens
```

For example:

```text
Input: 1,200
Output: 500
────────────
Total: 1,700
```

The exact tokenization depends on the model.

Don't think of:

```text
1 token = 1 word
```

because that's not generally true.

---

# 11. Why Input Tokens Matter

Remember our context architecture:

```text
System instructions
+
Course context
+
Lesson context
+
Conversation history
+
Student question
```

All of that can contribute to input tokens.

So a request that looks tiny:

```text
"Explain indexes."
```

might actually send a large context:

```text
5,000 input tokens
```

This is why context management matters for both:

```text
performance
cost
```

---

# 12. Output Tokens

The generated response also consumes tokens.

For example:

```text
Student asks:
"What is normalization?"

AI response:
500 tokens
```

Output tokens contribute to cost and latency.

Therefore:

```text
input tokens
+
output tokens
```

should be tracked separately.

---

# 13. Total Tokens

You can calculate:

```text
totalTokens =
  inputTokens +
  outputTokens
```

For example:

```text
1,000 + 400 = 1,400
```

But keep the original fields too.

Don't store only total tokens.

You want to know:

```text
input = 1000
output = 400
```

because they have different implications.

---

# 14. Token Growth Problem

Imagine a conversation:

```text
Message 1 → 500 tokens
Message 2 → 900 tokens
Message 3 → 1,500 tokens
Message 4 → 2,300 tokens
Message 5 → 3,800 tokens
```

Why is it growing?

Because we're sending conversation history back to the model.

Eventually:

```text
input tokens ↑
cost ↑
latency ↑
```

This is one of the reasons we built the context manager in Lesson 7.7.

---

# 15. Context Efficiency

Suppose two students ask exactly the same question:

```text
"Explain B-tree indexes."
```

Student A has:

```text
2 messages of history
```

Student B has:

```text
100 messages of history
```

Their AI requests could have very different input-token usage.

So we should track:

```text
inputTokens
```

and investigate unusually large contexts.

# 16. Cost Calculation

The provider may charge based on token usage.

Conceptually:

```text
input cost =
input tokens × input price

output cost =
output tokens × output price
```

Then:

```text
estimated cost =
input cost + output cost
```

For example, if the hypothetical pricing were:

```text
Input:
$1 / 1M tokens

Output:
$4 / 1M tokens
```

and we used:

```text
Input = 10,000
Output = 2,000
```

then:

```text
Input:
10,000 / 1,000,000 × $1
= $0.01

Output:
2,000 / 1,000,000 × $4
= $0.008

Total:
$0.018
```

**These numbers are only an example.**

In your application, keep pricing configuration separate because provider pricing can change.

---

# 17. Don't Hardcode Pricing Everywhere

Avoid:

```ts
const cost =
  tokens * 0.000004;
```

scattered throughout your application.

Instead:

```text
Pricing Configuration
       ↓
Cost Calculator
       ↓
AI Generation
```

For example:

```ts
interface ModelPricing {
  inputPerMillionTokens: number;
  outputPerMillionTokens: number;
}
```

Then:

```ts
function calculateCost(
  inputTokens: number,
  outputTokens: number,
  pricing: ModelPricing
) {
  // calculate
}
```

This makes pricing changes much easier.

---

# 18. Estimated Cost vs Actual Billing

Be careful with the word **cost**.

Your application may calculate:

```text
estimatedCost
```

based on token usage and known pricing.

But that may not perfectly match the provider's invoice because there can be:

```text
cached tokens
different pricing tiers
special model pricing
discounts
provider-specific billing rules
```

So call it:

```text
estimatedCost
```

unless you have authoritative billing data.

---

# 19. Time to First Token

For streaming AI, one of the most useful metrics is:

```text
TTFT
```

or:

> Time To First Token

Suppose:

```text
Request started:
10:00:00.000

First chunk:
10:00:01.200
```

Then:

```text
TTFT = 1.2 seconds
```

This measures how quickly the user starts seeing the response.

---

# 20. Total Latency

Another metric:

```text
totalDurationMs
```

For example:

```text
Request:
10:00:00

Generation complete:
10:00:05

Duration:
5 seconds
```

Now you have:

```text
TTFT = 1.2 sec
Total = 5 sec
```

This tells you much more than simply:

```text
AI took 5 sec
```

---

# 21. Why TTFT and Total Latency Together?

Imagine:

### Request A

```text
TTFT = 1 sec
Total = 5 sec
```

### Request B

```text
TTFT = 4 sec
Total = 5 sec
```

Both took 5 seconds total.

But B feels much slower because the student waits 4 seconds before seeing anything.

So:

```text
TTFT
+
Total latency
```

give a much better picture of user experience.

# 30. But Be Careful With Student Privacy

Don't collect everything just because you can.

For analytics, you might need:

```text

courseId
lessonId

```

You may not need to store:

```text

```

And logs should not contain secrets or unnecessary private content.

The principle is:

> **Collect what you need, not everything available.**

# 33. Why Nullable `conversationId`?

It depends on your application.

Some AI operations may happen outside normal conversations:


You may not always have a conversation.

So designing:

```text

```

can make the generation system more flexible.

Again, use your actual domain requirements.

# 34. Indexes Matter

Suppose your admin dashboard asks:

```text
Give me AI usage for today.
```

You might query:

```text
createdAt
```

Or:

```text
userId + createdAt
```

Or:

```text
courseId + createdAt
```

Therefore, your database indexes should reflect your analytics queries.

For example:

```text
(userId, createdAt)
(courseId, createdAt)
(provider, model, createdAt)
(status, createdAt)
```

Don't blindly create all of them.

Create indexes based on real query patterns.

# 47. Caching

Another powerful optimization:

Suppose many students ask:


Caching is best considered for suitable deterministic or low-personalization operations.



# 🧠 Final Phase 7 Interview Question

### "How would you design an AI Tutor backend for an LMS?"

A strong answer could be:

> "I would separate the AI Tutor into controller, service, context-management, and provider layers. The controller would handle HTTP concerns, while the tutor service would handle the educational business logic. I'd use a provider abstraction so the application isn't tightly coupled to one AI vendor. Conversations and messages would be persisted in PostgreSQL, and the context manager would construct course, lesson, and conversation context. For good UX, I'd support streaming responses through SSE or a streaming HTTP response. Since AI providers are unreliable external dependencies, I'd use timeouts, cancellation, limited retries with exponential backoff, rate limiting, and normalized errors. AI outputs would be parsed and schema-validated before reaching the frontend. Finally, I'd track provider, model, prompt version, token usage, latency, TTFT, retries, status, and estimated cost for observability and cost control."

If you can explain that architecture comfortably in an interview, you're demonstrating much more than **"I know how to call an AI API."**

You're demonstrating **backend + AI engineering thinking**.
