# Lesson 7.3 — Building the AI Chat API

In Lesson 7.2, we created the abstraction:

```text
Controller
    ↓
AI Service
    ↓
AI Provider
    ↓
LLM
```

Now we're going to expose that system through an actual HTTP API.

Our goal is to build something conceptually like:

```http
POST /api/v1/ai/chat
```

with:

```json
{
  "message": "Explain recursion in simple words."
}
```

and return:

```json
{
  "success": true,
  "data": {
    "message": "Recursion is when a function calls itself..."
  }
}
```

The important part is that we'll build it using the **backend architecture you've already learned**, rather than putting everything inside one controller.

---

# 4. Never Trust the Client

Even though the frontend might have:

```ts
interface ChatRequest {
  message: string;
}
```

that doesn't mean the backend can trust it.

A malicious client could send:

```json
{
  "message": 123
}
```

or:

```json
{
  "message": ""
}
```

or:

```json
{
  "message": ".... extremely large input ...."
}
```

Therefore:

```text
Frontend validation
       +
Backend validation
```

The backend validation is the security boundary.

---

# 6. Why Limit Message Size?


So input validation isn't only about correctness.

It can also be:

# 7. Authentication Comes First

Our AI endpoint should not be publicly accessible.

We want:


```text

   ↓
```

The authenticated user's identity might be attached to:

```ts

```

```ts

```

# 8. Why Does AI Need Authentication?

Because the AI service may:

```text
cost money
```


# 9. Controller Responsibility

Our controller should remain thin.

Something like:

```ts
export class AIController {
  constructor(
    private readonly aiService: AIService
  ) {}

  chat = asyncHandler(async (req, res) => {
    const result = await this.aiService.chat({
      userId: req.user.userId,
      message: req.body.message,
    });

    res.status(200).json({
      success: true,
      data: result,
    });
  });
}
```

Notice what the controller **doesn't** do.

It doesn't:

```text
call OpenAI
load database
build prompts
check token usage
save conversations
```

That's service-level work.

---

# 10. AI Service

The service receives the application-level request:

```ts
{
  userId,
  message
}
```

and coordinates the operation.

Conceptually:

```ts
class AIService {
  async chat(input: ChatInput) {
    // business logic
  }
}
```

Eventually:

```text
AIService
   │
   ├── validate access
   ├── load conversation
   ├── build context
   ├── check usage
   ├── call provider
   ├── save messages
   └── return result
```

For Lesson 7.3, we'll keep it smaller.

# 11. Calling the Provider

# 12. Basic Service Flow

Our first service implementation can conceptually be:

```ts
class AIService {
  constructor(
    private readonly provider: AIProvider
  ) {}

  async chat(input: ChatInput) {
    const response = await this.provider.generateText({
      model: "your-model",
      messages: [
        {
          role: "user",
          content: input.message,
        },
      ],
    });

    return {
      message: response.content,
    };
  }
}
```

That's enough to establish the basic flow.

# 14. Response Format

Your project already has a standard API response pattern.

Keep that consistent.

For example:

```json
{
  "success": true,
  "data": {
    "message": "Recursion is a technique where..."
  }
}
```

Don't create a completely different response format just because this is an AI endpoint.

Consistency across your API matters.

---

# 15. Error Response

Suppose the AI provider fails.

Don't return:

```json
{
  "error": "Some random SDK error..."
}
```

Instead, normalize it through your existing error system.

For example:

```json
{
  "success": false,
  "error": {
    "code": "AI_PROVIDER_ERROR",
    "message": "The AI service is temporarily unavailable."
  }
}
```

Your existing:

```text
AppError
   ↓
Global Error Handler
```

should remain responsible for formatting the HTTP error.

---

# 16. Don't Leak Provider Details

Imagine the provider returns:

```text
API_KEY_INVALID
internal_model_error_xyz
provider_stack_trace
```

Never send those directly to the student.

Bad:

```json
{
  "error": "OpenAIError: ..."
}
```

Better:

```json
{
  "success": false,
  "error": {
    "code": "AI_PROVIDER_ERROR",
    "message": "Unable to generate a response right now."
  }
}
```

The detailed error can go to your server logs.

---

# 17. Logging

AI requests should be observable.

For example:

```text

userId=123
requestId=abc
```

Then:

```text
AI request completed
requestId=abc
latency=1.8s
```

If it fails:

```text
AI request failed
requestId=abc
provider=...
error=...
```

Don't log:

```text
API keys
access tokens
sensitive conversation content
```

unless you have a very deliberate and secure reason.

# 19. Route Structure

Conceptually:

```ts
router.post(
  "/chat",
  authenticate,
  validate(chatSchema),
  aiController.chat
);
```

Mounted under:

```ts
app.use("/api/v1/ai", aiRouter);
```

Therefore:

```text
POST /api/v1/ai/chat
```

The middleware order is important.

```text
authenticate
      ↓
validate
      ↓
controller
```

You can also choose validation before authentication depending on your security and API design, but for our LMS we'll keep the overall principle clear:

> **Every protected AI operation must pass through the appropriate authentication and validation boundaries before business logic executes.**

---

# 20. Should Authorization Be Here?

Eventually, yes.

Authentication answers:

> **Who are you?**

Authorization answers:

> **Are you allowed to do this?**

For a basic AI chat endpoint:

```text
Student authenticated?
      ↓
Yes
      ↓
Can use AI?
      ↓
Yes
```

But later we may need:

```text
Is this user enrolled in the course?
```

or:

```text
Does this user have access to this lesson?
```

That belongs in the service/business-logic layer.

---

# 21. Why Authorization Shouldn't Live in the Controller

Avoid:

```ts
if (req.user.role === "student") {
   // huge logic
}
```

inside the controller.

The controller should not become a giant business-rule file.

Instead:

```text
Controller
    ↓
AI Service
    ↓
Access rules
```

This keeps the controller thin.

---

# 22. DTO / Input Type

Define an application-level type:

```ts
interface ChatInput {
  userId: string;
  message: string;
}
```

Then:

```ts
aiService.chat(input)
```

This is better than passing the entire Express `Request` object into the service.

Avoid:

```ts
aiService.chat(req);
```

Prefer:

```ts
aiService.chat({
  userId: req.user.userId,
  message: req.body.message,
});
```

This keeps your service independent from Express.

---

# 23. Why This Is Important

But if it depends on:


then it can be called from:

```text

```

This is good architecture.

# 26. Streaming — Important Preview

You might have noticed that AI applications often show:

```text
Generating...
Hello...
Hello Rahul...
Hello Rahul, recursion...
```

instead of waiting for the entire response.

That's called **streaming**.

For example:

```text
LLM
 ↓
token
 ↓
token
 ↓
token
 ↓
token
```

and the frontend receives the response progressively.

Streaming is useful, but we're **not making it the first implementation**.

First understand:

```text
Request
 ↓
Complete AI response
 ↓
HTTP response
```

Then we can introduce streaming when the basic API is stable.

---

# 27. Why Build Non-Streaming First?

Because debugging this:

```text

 ↓

 ↓

 ↓
LLM
 ↓
Response
```

is much easier than debugging:

```text

 ↓
Streaming
 ↓
Service
 ↓
Provider stream
 ↓
Chunks
 ↓
Network
 ↓
Frontend stream parser
```

Build the simple version first.

Then optimize.

That's a good engineering habit.

# 35. Interview Question

### Why shouldn't we pass Express's `Request` object into `AIService`?

Because that would couple the business logic to the HTTP framework.

Bad:

```ts
aiService.chat(req);
```

Better:

```ts
aiService.chat({
  userId: req.user.userId,
  message: req.body.message,
});
```

Now:

```text
Express
   ↓
Controller
   ↓
Plain application data
   ↓
Service
```

The service doesn't care where the data came from.

That's clean architecture thinking.

---

# 36. Another Interview Question

### Why shouldn't the controller directly call the AI SDK?

Because controllers should coordinate HTTP concerns, while AI provider communication and business logic belong in dedicated layers.

Bad:

```text
Controller
 ├── validation
 ├── prompt construction
 ├── OpenAI SDK
 ├── database
 ├── token calculation
 └── response
```

Good:

```text
Controller
    ↓
AI Service
    ↓
AI Provider
```

Each layer has a clear responsibility.
