# Lesson 7.6 — Message History & Persistence

In Lesson 7.5, we created the **conversation layer**:

```text
User
  ↓
Conversation
  ↓
Messages
```

Now we build the message layer.

Our goal is to turn this:

```text
Question
   ↓
Answer
```

into this:

```text
Conversation
   │
   ├── User: What is normalization?
   ├── AI: Normalization is...
   ├── User: Why do we need it?
   ├── AI: We use it to...
   └── User: Give me an example.
```

This is what allows the AI tutor to feel like a real conversation.

---

# 1. What Is Message History?

Message history is the ordered collection of messages belonging to a conversation.

For example:

```text
Conversation: conv_123

1. user      → What is PostgreSQL?
2. assistant → PostgreSQL is...
3. user      → Why is it relational?
4. assistant → It is relational because...
```

The history gives the AI context about what happened earlier.

Without it:

```text
Student:
"Why is it useful?"
```

The AI might not know what **"it"** refers to.

With history:

```text
User:
What is an index?

AI:
An index is...

User:
Why is it useful?
```

the meaning becomes much clearer.

---

# 2. Conversation vs Message

Keep this distinction very clear.

### Conversation

Represents the discussion:

```text
id
userId
courseId
lessonId
title
createdAt
updatedAt
```

### Message

Represents one individual interaction:

```text
id
conversationId
role
content
createdAt
```

Relationship:

```text
Conversation
     │
     ├── Message
     ├── Message
     ├── Message
     └── Message
```

One conversation can have many messages.

---

# 3. Message Roles

Every AI conversation needs to distinguish who produced a message.

A simple model is:

```text
user
assistant
system
```

For example:

```json
{
  "role": "user",
  "content": "Explain indexes."
}
```

and:

```json
{
  "role": "assistant",
  "content": "An index is..."
}
```

A system message could contain:

```text
You are an educational AI tutor...
```

---

# 4. Why Store the Role?

Suppose the database contains:

```text
Message 1:
"Explain recursion."

Message 2:
"Recursion is..."
```

The model needs to know:

```text
Message 1 → user
Message 2 → assistant
```

Otherwise, it cannot correctly reconstruct the conversation.

So the message role is part of the message's meaning.

---

# 5. TypeScript Type

We can define:

```ts
export type MessageRole =
  | "user"
  | "assistant"
  | "system";
```

Then:

```ts
export interface Message {
  id: string;
  conversationId: string;
  role: MessageRole;
  content: string;
  createdAt: Date;
}
```

This gives us a clear application-level representation.

---

# 6. Database Relationship

Our relational model is:

```text
User
 │
 │ 1
 ↓
Conversation
 │
 │ 1
 ↓
Message
```

More explicitly:

```text
users
  │
  └──── conversations
             │
             └──── messages
```

Foreign keys:

```text
conversations.user_id
        ↓
users.id
```

and:

```text
messages.conversation_id
        ↓
conversations.id
```

This is exactly the kind of relationship you learned during the database phase.

---

# 7. Why `conversationId` Is Important

Every message needs to belong to a conversation.

For example:

```text
Message A
conversationId = conv_123

Message B
conversationId = conv_123

Message C
conversationId = conv_456
```

Now the database knows:

```text
conv_123
 ├── A
 └── B

conv_456
 └── C
```

Without `conversationId`, you can't reliably group messages.

---

# 8. Message Ordering

This is one of the most important parts.

Suppose:

```text
1. User: What is Prisma?
2. AI: Prisma is...
3. User: Why use it?
4. AI: It provides...
```

The AI must receive them in the same logical order.

We could order by:

```text
createdAt ASC
```

or use a dedicated sequence number.

For a basic implementation:

```text
ORDER BY createdAt ASC
```

is reasonable.

---

# 9. Why Not Trust Array Order?

Suppose your database returns:

```text
Message 4
Message 1
Message 3
Message 2
```

If you simply pass that array to the model:

```text
LLM
 ↑
Wrong order
```

the conversation can become confusing.

Always explicitly establish ordering.

---

# 10. Message Repository

Following your repository architecture:

```ts
interface MessageRepository {
  create(
    input: CreateMessageInput
  ): Promise<Message>;

  findByConversationId(
    conversationId: string
  ): Promise<Message[]>;

  findRecentByConversationId(
    conversationId: string,
    limit: number
  ): Promise<Message[]>;
}
```

The repository handles database operations.

Not the controller.

Not the AI provider.

---

# 11. Creating a Message

Define:

```ts
interface CreateMessageInput {
  conversationId: string;
  role: MessageRole;
  content: string;
}
```

Then:

```ts
await messageRepository.create({
  conversationId,
  role: "user",
  content: "Explain indexes.",
});
```

The repository persists it.

---

# 12. User Message vs AI Message

When the student sends:

```text
Explain PostgreSQL indexes.
```

we save:

```text
role = user
```

Then the AI generates:

```text
An index is a data structure...
```

We save:

```text
role = assistant
```

So the database becomes:

```text
Conversation conv_123

1. user
   Explain PostgreSQL indexes.

2. assistant
   An index is a data structure...
```

---

# 13. The Correct Order of Persistence

There is an important question:

> When should we save the user message?

A good flow is:

```text
Student message
      ↓
Validate
      ↓
Authorize conversation
      ↓
Save user message
      ↓
Build context
      ↓
Call LLM
      ↓
Save assistant message
      ↓
Return response
```

This means the user's message exists even if the AI provider fails.

That can be useful for:

```text
retry
debugging
conversation history
failure tracking
```

---

# 14. What If the AI Call Fails?

Suppose:

```text
User message
      ↓
Saved successfully
      ↓
LLM request
      ↓
Provider timeout
```

Now the conversation contains:

```text
User:
Explain PostgreSQL indexes.

Assistant:
???
```

That's not necessarily a problem.

We could eventually add a message status such as:

```text
pending
completed
failed
```

But don't add it until there's a real requirement.

For our initial design, the application can record the failure through logs/usage tracking.

# 15. Message History Retrieval

Suppose we have:

```text
Conversation 123

1. What is PostgreSQL?
2. PostgreSQL is...
3. Why is it relational?
4. Because...
5. What is an index?
6. An index is...
```

We can retrieve:

```ts
const messages =
  await messageRepository.findByConversationId(
    conversationId
  );
```

Then:

```text
Database
   ↓
Messages
   ↓
Context Builder
   ↓
AI Provider
```

---

# 16. But Should We Send Every Message?

This is a very important question.

Imagine a conversation has:

```text
10 messages
```

Easy.

But what if it has:

```text
500 messages?
5,000 messages?
```

Sending everything to the model every time can become:

```text
expensive
slow
too large
```

So:

> **Database history and LLM context are not necessarily the same thing.**

This distinction is extremely important.

---

# 17. Stored History vs Active Context

Think of two layers:

```text
                    Conversation
                         │
                         ↓
                 Full Message History
                         │
                         ↓
                  Context Selection
                         │
                ┌────────┴────────┐
                ↓                 ↓
          Recent messages      Summary
                │                 │
                └────────┬────────┘
                         ↓
                    LLM Context
```

We can store everything while only sending the **useful subset** to the model.

We'll explore this much more in **Lesson 7.7 — Context Management**.

---

# 18. Recent Messages

One simple strategy is:

```text
Get last 20 messages
```

For example:

```ts
findRecentByConversationId(
  conversationId,
  20
);
```

Then:

```text
Database
   ↓
Last 20 messages
   ↓
LLM
```

This is simple and useful for the first version.

But it has limitations.

---

# 19. The Problem With Only Recent Messages

Imagine the student says:

```text
Message 1:
My project uses PostgreSQL.

...

Message 50:
What database am I using?
```

If we only keep the latest few messages, the AI might not know.

This is why advanced systems use:

```text
Recent messages
+
Conversation summary
+
Relevant context
```

We'll build toward that.

---

# 20. Message History Service

Instead of putting message retrieval directly into `AITutorService`, we can introduce:

```ts
class MessageService {
  constructor(
    private readonly repository: MessageRepository
  ) {}

  async getConversationHistory(
    conversationId: string
  ) {
    return this.repository
      .findByConversationId(conversationId);
  }
}
```

Then:

```text
AITutorService
      ↓
MessageService
      ↓
MessageRepository
      ↓
PostgreSQL
```

This keeps responsibilities separated.

---

# 21. A More Useful Method

We could eventually have:

```ts
getRecentMessages(
  conversationId: string,
  limit: number
)
```

and:

```ts
getMessagesBefore(
  conversationId: string,
  cursor: string
)
```

This supports:

```text

```

# 22. Message Pagination for the Frontend

Imagine a conversation contains:

```text
1,000 messages
```

The frontend shouldn't download all 1,000 immediately.

Instead:

```http
GET /api/v1/ai/conversations/conv_123/messages?limit=30
```

Then:

```text
Frontend
   ↓
30 messages
```

When the student scrolls upward:

```text
Load older messages
```

This is a normal pagination problem.

---

# 23. Cursor Pagination

For chat history, cursor pagination is often a good fit.

Conceptually:

```http
GET /messages?limit=30&before=msg_100
```

Meaning:

> Give me 30 messages before `msg_100`.

This works naturally for historical chat data.

We'll leave the exact implementation for when we build the API.

---

# 24. Message Timestamps

Every message should have:

```text
createdAt
```

For example:

```text
10:01:00 — user
10:01:02 — assistant
10:02:15 — user
10:02:18 — assistant
```

This is useful for:

```text
ordering
UI display
debugging
analytics
```

---

# 25. Should We Store `updatedAt`?

Messages are usually immutable.

Once:

```text
User:
Explain indexes.
```

is saved, we generally don't modify its content.

So a message may only need:

```text
createdAt
```

rather than:

```text
createdAt
updatedAt
```

unless you have a specific editing requirement.

This is a good example of avoiding unnecessary database fields.

---

# 26. Message Immutability

A useful design principle:

> **Treat AI conversation messages as append-only records.**

Instead of:

```text
UPDATE message
```

you generally:

```text
INSERT new message
```

For example:

```text
User message
   ↓
Assistant response
   ↓
User correction
   ↓
Assistant response
```

This preserves the history.

---

# 27. What About Editing a User Message?

Suppose the frontend allows:

> Edit message

You have two choices.

### Option A — Modify the existing message

Simple, but history is lost.

### Option B — Create a new branch/version

More sophisticated.

For our LMS, I'd initially recommend **not implementing message editing**.

Keep the conversation append-only.

You can always add editing later if it becomes a useful feature.

---

# 28. Message Content

The simplest field is:

```text
content: string
```

For example:

```json
{
  "role": "user",
  "content": "Explain normalization."
}
```

But eventually AI systems may support richer content:

```text
text
image
file
tool result
structured data
```

For our first implementation:

```text
content = text
```

is enough.

Don't overdesign the message model prematurely.

---

# 29. System Messages

One question:

> Should tutor system instructions be stored as database messages?

Not necessarily.

You could have:

```text
Database
 ↓
user messages
assistant messages
```

while system instructions are generated dynamically:

```text
TutorContextBuilder
      ↓
System instructions
      +
Stored conversation messages
```

This is often cleaner because system instructions are **application configuration**, not necessarily user conversation data.

# 31. Don't Couple Your Database to the Provider

Suppose your provider expects:

```ts
{
  role: "user",
  content: "..."
}
```

Another provider may use a slightly different format.

Don't design your PostgreSQL schema specifically around one vendor.

Instead:

```text
PostgreSQL
   ↓
Application Message
   ↓
Context Builder
   ↓
AI Provider
   ↓
Provider-specific format
```

This keeps the architecture flexible.

# 32. Saving Both Sides

A complete interaction should normally produce:

```text
User Message
      ↓
AI Request
      ↓
Assistant Message
```

For example:

```text
messages

1. user
   Explain recursion.

2. assistant
   Recursion is a technique...
```

This means the conversation can be reconstructed later.

---

# 33. Important: Save the Actual Response

Don't only return the AI response to the frontend.

Bad:

```text
LLM
 ↓
Frontend
```

and then forget it.

Instead:

```text
LLM
 ↓
AI Service
 ↓
Message Repository
 ↓
PostgreSQL
 ↓
Frontend
```

Now the conversation survives:

```text
page refresh
logout
new device
future session
```

# 34. Transaction Considerations

Here's an interesting database question.

Suppose:

```text
1. Save user message
2. Call LLM
3. Save assistant message
```

Should all three operations be one database transaction?

Usually **no**.

Why?

Because the LLM call is an external network operation.

You don't want a database transaction to remain open while waiting for an AI provider.

Bad:

```text
BEGIN TRANSACTION
      ↓
Save user message
      ↓
Wait 5 seconds for LLM
      ↓
Save assistant message
      ↓
COMMIT
```

This keeps a database transaction open during a network call.

Not ideal.

---

# 35. Better Flow

Instead:

```text
Save user message
      ↓
Commit
      ↓
Call LLM
      ↓
Save assistant message
```

Now the database isn't holding a transaction open while waiting for an external provider.

This is an important backend engineering principle:

> **Don't keep database transactions open across slow external network operations unless you have a very specific reason.**

---

# 36. What If Saving the Assistant Message Fails?

Suppose:

```text
User message → saved
LLM → successful
Assistant message → database failure
```

Now we have:

```text
User message
      ↓
AI response exists
      ↓
AI response wasn't persisted
```

This is a reliability problem.

Later, we can solve these kinds of issues with:

```text
retries
idempotency
background jobs
durable event patterns
```

especially in Phase 11.

For now, we log the failure properly and return an appropriate error.

# 37. Message IDs

Every message needs its own unique ID.

For example:

```text
msg_001
msg_002
msg_003
```

Why?

Because the frontend may need to:

```text
identify a message
load history
paginate
reference a message
track feedback
```

A message ID also makes debugging much easier.

---

# 38. Ordering With IDs

Don't assume message IDs themselves provide chronological ordering.

For example:

```text
msg_z9
msg_a2
msg_b7
```

Their lexical order doesn't necessarily tell you the creation order.

Use:

```text
createdAt
```

or an explicit sequence field.

This is a subtle but important database design detail.

---

# 39. Sequence Numbers

An alternative is:

```text
sequence = 1
sequence = 2
sequence = 3
```

Then:

```text
ORDER BY sequence ASC
```

This can be useful for very strict ordering.

But don't automatically add it.

For our initial implementation:

```text
createdAt + unique ID
```

is sufficient.

---

# 40. Message Metadata

Eventually, AI messages may need metadata such as:

```text
model
inputTokens
outputTokens
latency
provider
```

For example:

```text
Assistant message
 ├── content
 ├── model
 ├── inputTokens
 ├── outputTokens
 └── createdAt
```

Should all of that live directly on the message?

Possibly, but we should think carefully about what belongs to:

```text
Message
```

versus:

```text
AI generation record
```

We'll revisit this when discussing **cost and observability in 7.12**.

For now, keep the message model focused on the conversation.

# 44. Message History and Context Are Different

This is probably the **most important concept of today's lesson**.

Suppose your database has:

```text
10,000 messages
```

That doesn't mean:

```text
LLM receives 10,000 messages
```

Instead:

```text
10,000 stored messages
        ↓
Context selection
        ↓
Relevant subset
        ↓
LLM
```

The database is the **source of conversation history**.

The context builder decides what the model actually sees.

---

All while keeping the database unchanged.

That's excellent separation of concerns.

# 48. Common Mistakes

## Mistake 1 — Storing the entire chat in one JSON column

You might think:

```text
Conversation
   ↓
messages: JSON
```

For a basic prototype, this can work.

But for our relational LMS, individual messages give us much better:

```text
querying
pagination
indexing
analytics
ownership
ordering
```

So we'll use a proper `Message` entity.

---

## Mistake 2 — Sending unlimited history to the LLM

```text
All messages
   ↓
LLM
```

❌ Can become expensive and inefficient.

---

## Mistake 3 — Saving only user messages

Then the next request doesn't have the AI's previous answer.

❌ Incomplete conversation.

Save both:

```text
user
assistant
```

---

## Mistake 4 — Keeping DB transaction open during LLM call

```text
BEGIN
 ↓
DB
 ↓
LLM
 ↓
DB
 ↓
COMMIT
```

❌ Avoid this in the normal flow.

---

## Mistake 5 — Letting users access messages directly by ID

For example:

```http
GET /messages/msg_123
```

without verifying:

```text
message
 ↓
conversation
 ↓
current user
```

❌ Potential authorization vulnerability.

---

# 49. Message Authorization

Suppose a user requests:

```http
GET /api/v1/ai/messages/msg_123
```

Don't just check:

```text
message.id = msg_123
```

You need to establish:

```text
message
   ↓
conversation
   ↓
conversation.userId
   ↓
authenticated user
```

For nested resources, ownership often flows through the parent.

This is another excellent real-world backend authorization problem.

---

# 50. What You Should Remember

Remember these 10 points:

1. A **conversation contains messages**.
    
2. Every message belongs to exactly one conversation.
    
3. Messages need a role such as `user` or `assistant`.
    
4. Message order matters.
    
5. Store user and assistant messages.
    
6. Store history in PostgreSQL; don't treat the LLM context as the database.
    
7. Don't send unlimited history to the model.
    
8. Avoid database transactions across slow external AI calls.
    
9. Message access must respect conversation ownership.
    
10. **Stored history ≠ LLM context.**
    

That last point is the big one.

# 🧠 Interview Question

### Why shouldn't we send the entire conversation history to the LLM on every request?

A strong answer:

> "Because conversation history can grow very large, increasing latency, token usage, and cost. I would persist the complete history in the database but use a context-management layer to select recent or relevant messages, summaries, and eventually retrieved course content before sending the request to the model."

That's a solid backend + AI architecture answer.
