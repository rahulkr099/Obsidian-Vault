# Lesson 9.1 — AI Quiz Generation

This lesson starts **Phase 9: AI-Generated Assessments**.

The goal is to understand how your LMS can take existing course material and use an AI model to generate a complete quiz in a **structured, predictable format**.

---

## 1. What are we building?

Suppose an instructor has this lesson:

> **JavaScript Arrays**  
> Arrays are ordered collections of values. JavaScript arrays can contain multiple values and provide methods such as `map()`, `filter()`, and `reduce()`.

The instructor clicks:

```text
Generate Quiz
```

Our backend should be able to produce something like:

```text
Quiz
 ├── Question 1
 ├── Question 2
 ├── Question 3
 ├── Question 4
 └── Question 5
```

Each question should contain structured information such as:

```text
question
type
options
correctAnswer
explanation
difficulty
```

The important idea is:

> **AI generates the content, but your application controls the structure and validation.**

---

# 2. Why not simply ask the AI for a quiz?

A beginner implementation might do this:

```text
"Generate 5 questions about JavaScript arrays."
```

Then the AI might return:

```text
1. What is an array?

2. Which method is used to transform an array?

3. Explain reduce().
```

This creates problems.

Your backend doesn't reliably know:

```text
Where does one question end?

What type is the question?

Which answer is correct?

What are the options?

What is the difficulty?

Is the generated response valid JSON?

```

Therefore, our architecture should be:

```text
Course/Lesson Content
        ↓
     AI Prompt
        ↓
    LLM Provider
        ↓
 Structured Output
        ↓
    Validation
        ↓
   Quiz Database
```

---

# 3. AI should not own your database structure

This is a very important backend principle.

Don't let the AI decide your database structure.

Your application defines the schema:

```text
Quiz
 ├── id
 ├── lessonId
 ├── title
 └── questions

Question
 ├── id
 ├── quizId
 ├── type
 ├── text
 ├── options
 ├── correctAnswer
 ├── explanation
 └── difficulty
```

The AI only provides the **content**.

```text
Application
    │
    ├── defines schema
    ├── validates data
    ├── saves data
    └── controls permissions
             ↑
             │
            AI
             │
        generates content
```

This separation becomes extremely important later when we build **AI security** in Phase 14.

---

# 4. Where does the quiz content come from?

Since Phase 7 and Phase 8 already exist, we shouldn't make the AI generate questions from nothing.

We have:

```text
Course
  ↓
Section
  ↓
Lesson
  ↓
Lesson Content
```

For example:

```text
Course: JavaScript
Section: Arrays
Lesson: Array Methods
```

The lesson content becomes the input to the quiz generator.

Eventually, the architecture can become:

```text
Lesson
  ↓
Content
  ↓
Relevant Context
  ↓
AI Quiz Generator
  ↓
Generated Questions
```

And because we already built RAG in Phase 8:

```text
Lesson
   ↓
Retrieve relevant chunks
   ↓
RAG Context
   ↓
AI
   ↓
Quiz
```

This helps prevent questions from being unrelated to the actual course.

# 5. Basic Quiz Generation Flow

Let's design the backend flow.

```text
Instructor
    │
    │ POST /api/v1/quizzes/generate
    ↓
Controller
    ↓
Quiz Service
    ↓
Fetch Lesson
    ↓
Prepare AI Prompt
    ↓
AI Provider
    ↓
Structured Quiz
    ↓
Validate
    ↓
Save Quiz
    ↓
Return Response
```

Notice something important:

The **controller does not call the AI directly**.

We maintain the architecture we've already been following:

```text
Controller
    ↓
Service
    ↓
Repository
```

With an AI layer:

```text
Controller
    ↓
Quiz Service
    ↓
AI Service
    ↓
AI Provider
```

# 6. Example API

We could eventually expose:

```http
POST /api/v1/quizzes/generate
```

Request:

```json
{
  "lessonId": "lesson_123",
  "questionCount": 5,
  "difficulty": "medium"
}
```

The instructor might also provide:

```json
{
  "questionTypes": [
    "MCQ",
    "TRUE_FALSE"
  ]
}
```

So the request becomes:

```json
{
  "lessonId": "lesson_123",
  "questionCount": 10,
  "difficulty": "medium",
  "questionTypes": [
    "MCQ",
    "TRUE_FALSE"
  ]
}
```

The API is responsible for validating this request.

---

# 7. The AI Prompt

The service prepares instructions for the model.

Conceptually:

```text
You are an educational assessment generator.

Generate a quiz using only the provided lesson content.

Requirements:
- Generate 5 questions.
- Difficulty: medium.
- Questions must test understanding.
- Do not introduce information not present in the lesson.
- Return structured quiz data.
```

Then:

```text
LESSON CONTENT

JavaScript arrays are ordered collections...
...
```

The important phrase here is:

> **using only the provided lesson content**

This reduces hallucinated questions.

---

# 8. Structured Output

We want something like:

```json
{
  "title": "JavaScript Arrays Quiz",
  "questions": [
    {
      "type": "MCQ",
      "question": "Which method transforms every element of an array?",
      "options": [
        "map()",
        "filter()",
        "find()",
        "push()"
      ],
      "correctAnswer": "map()",
      "explanation": "map() creates a new array by applying a function to each element.",
      "difficulty": "medium"
    }
  ]
}
```

This is much better than free-form text.

Your backend can now work with the response programmatically.

---

# 9. But Never Trust AI Output

This is one of the biggest lessons of this phase.

Even if the AI returns:

```json
{
  "questions": [...]
}
```

you should **not immediately save it to PostgreSQL**.

Instead:

```text
AI Response
    ↓
Schema Validation
    ↓
Valid?
  ↙   ↘
Yes    No
 ↓      ↓
Save   Reject/Retry
```

For your TypeScript backend, we can use the same validation philosophy you've already learned with Zod.

For example:

```ts
const quizQuestionSchema = z.object({
  type: z.enum(["MCQ", "TRUE_FALSE", "SHORT_ANSWER"]),
  question: z.string().min(1),
  options: z.array(z.string()).optional(),
  correctAnswer: z.string().min(1),
  explanation: z.string().min(1),
  difficulty: z.enum(["EASY", "MEDIUM", "HARD"]),
});
```

Then:

```ts
const result = quizQuestionSchema.safeParse(aiOutput);
```

Only valid data continues.

# 10. AI Provider Abstraction

Don't tightly couple your quiz service to one AI provider.

Avoid:

```ts
quizService
   ↓
OpenAI SDK
```

Prefer:

```text
Quiz Service
      ↓
AI Service
      ↓
AI Provider Interface
      ↓
┌──────────────┬──────────────┐
│ Provider A   │ Provider B   │
└──────────────┴──────────────┘
```

For example:

```ts
interface AIQuizGenerator {
  generateQuiz(input: GenerateQuizInput): Promise<GeneratedQuiz>;
}
```

Then the service doesn't care which model is being used.

This will become useful when you want to experiment with different models based on:

```text
quality
cost
speed
context window
availability
```

---

# 11. Question Count Should Be Controlled

Don't allow the instructor to request unlimited questions.

Bad:

```json
{
  "questionCount": 100000
}
```

That could create:

```text
huge prompt
     ↓
huge AI response
     ↓
huge cost
     ↓
slow request
```

Instead, your API should impose limits.

For example:

```text
minimum: 1
maximum: 50
```

The exact limit can be decided when we implement the endpoint.

This is both an **engineering** and **security/cost-control** concern.

---

# 12. Generation Should Be Reproducible Enough to Debug

Suppose an instructor says:

> "The generated quiz was terrible."

You should have enough information to investigate.

Eventually, we may store metadata such as:

```text
model
promptVersion
generationTimestamp
questionCount
difficulty
lessonId
```

For example:

```json
{
  "model": "some-model",
  "promptVersion": "quiz-v1",
  "questionCount": 10,
  "difficulty": "medium"
}
```

Don't necessarily store every piece of raw AI data forever; we'll make that decision later based on privacy, cost, and debugging needs.

# 13. Quiz Generation vs Quiz Attempt

These are two different operations.

### Generation

```text
Instructor
   ↓
Generate quiz
   ↓
AI
   ↓
Quiz stored in DB
```

### Attempt

```text
Student
   ↓
Start quiz
   ↓
Answer questions
   ↓
Submit
   ↓
Evaluate
   ↓
Score
```

Don't mix these responsibilities.

This separation will make Lessons **9.7 and 9.8** much easier.

---

# 14. Synchronous vs Background Generation

At first you might implement:

```text
POST /generate
      ↓
AI call
      ↓
wait
      ↓
response
```

This is acceptable for a first version.

But AI generation can take time.

A more production-ready architecture is:

```text
Instructor
    ↓
POST /generate
    ↓
Create Job
    ↓
Redis Queue
    ↓
Background Worker
    ↓
AI Provider
    ↓
Validate
    ↓
Save Quiz
```

Then:

```text
Instructor
     ↓
"Generating..."
     ↓
Quiz Ready
```

We'll cover queues and background workers properly in **Phase 11**.

So don't over-engineer it right now.

# 16. Important Design Rule

Remember this:

```text
AI ≠ Source of Truth
```

The source of truth remains:

```text
PostgreSQL
```

AI is a **content generation tool**.

So:

```text
AI generates
      ↓
Application validates
      ↓
Application decides
      ↓
Database stores
```

Never:

```text
AI generates
      ↓
Database blindly stores
```
