# Lesson 9.2 — Question Generation

In **Lesson 9.1**, we designed the overall AI quiz-generation pipeline.

Now we go one level deeper:

> **How does the AI generate individual questions from lesson content?**

The goal is to make question generation **controlled, structured, relevant, and easy to validate**.

---

## 1. Quiz vs Question

First, keep these two concepts separate.

A **quiz** is a collection:

```text
Quiz
 ├── Question 1
 ├── Question 2
 ├── Question 3
 ├── Question 4
 └── Question 5
```

A **question** is an individual assessment item:

```text
Question
 ├── type
 ├── question
 ├── options
 ├── correctAnswer
 ├── explanation
 └── difficulty
```

So our generation pipeline becomes:

```text
Lesson Content
      ↓
Question Generation
      ↓
Question 1
Question 2
Question 3
...
      ↓
Quiz
```

---

# 2. What Should the AI Know?

The AI should receive enough educational context to generate useful questions.

For example:

```text
Course:
JavaScript

Section:
Arrays

Lesson:
Array Methods

Content:
JavaScript provides methods such as map(),
filter(), and reduce() for working with arrays.
```

Then we provide generation requirements:

```text
Generate 5 questions.

Difficulty:
Medium

Focus:
Understanding array methods

Avoid:
Questions unrelated to the lesson.
```

Conceptually:

```text
Lesson
  +
Question Requirements
  +
Generation Rules
       ↓
      AI
       ↓
Questions
```

---

# 3. Don't Generate Questions From the Entire Course

Suppose your LMS contains:

```text
Course
 ├── JavaScript Basics
 ├── Variables
 ├── Functions
 ├── Arrays
 ├── Objects
 ├── Async JavaScript
 └── Node.js
```

The instructor is creating a quiz for:

```text
Arrays
```

We shouldn't send the entire course unnecessarily.

Instead:

```text
Course
   ↓
Section
   ↓
Lesson
   ↓
Relevant Content
   ↓
AI
```

This improves:

- relevance
    
- token usage
    
- generation quality
    
- cost
    

And later, RAG can make this even better.

---

# 4. Question Generation Input

Let's define an input object.

```ts
type GenerateQuestionsInput = {
  lessonId: string;
  questionCount: number;
  difficulty: "EASY" | "MEDIUM" | "HARD";
  questionType: "MCQ" | "TRUE_FALSE" | "SHORT_ANSWER";
};
```

For example:

```ts
const input = {
  lessonId: "lesson_123",
  questionCount: 5,
  difficulty: "MEDIUM",
  questionType: "MCQ",
};
```

Notice that the AI isn't deciding these values.

The **application provides them**.

---

# 5. Why the Application Should Control These Parameters

Don't let the AI decide:

```text
questionCount
difficulty
questionType
lessonId
```

Instead:

```text
Instructor
    ↓
Application
    ↓
Generation Parameters
    ↓
AI
```

This gives you predictable behavior.

For example, if the instructor requests:

```text
5 MCQs
```

the AI shouldn't suddenly return:

```text
3 MCQs
2 True/False
```

unless your application explicitly allows mixed question types.

---

# 6. Generating One Question

Conceptually, our AI service could have:

```ts
interface AIQuestionGenerator {
  generateQuestion(
    input: GenerateQuestionInput
  ): Promise<GeneratedQuestion>;
}
```

Where:

```ts
type GenerateQuestionInput = {
  content: string;
  type: QuestionType;
  difficulty: Difficulty;
};
```

And:

```ts
type GeneratedQuestion = {
  type: QuestionType;
  question: string;
  options?: string[];
  correctAnswer: string;
  explanation: string;
};
```

This keeps the AI layer clean.

---

# 7. Generating Multiple Questions

Our quiz service can then request multiple questions.

Conceptually:

```ts
const questions = await aiQuestionGenerator.generateQuestions({
  content: lesson.content,
  count: 5,
  difficulty: "MEDIUM",
  type: "MCQ",
});
```

The AI should return:

```json
{
  "questions": [
    {
      "question": "...",
      "options": ["...", "...", "...", "..."],
      "correctAnswer": "...",
      "explanation": "...",
      "difficulty": "MEDIUM"
    },
    {
      "question": "...",
      "options": ["...", "...", "...", "..."],
      "correctAnswer": "...",
      "explanation": "...",
      "difficulty": "MEDIUM"
    }
  ]
}
```

---

# 8. Prompt Design

A good question-generation prompt should have clear sections.

For example:

```text
ROLE

You are an educational assessment generator.

CONTEXT

Use only the provided lesson content.

TASK

Generate 5 multiple-choice questions.

REQUIREMENTS

- Questions must be relevant to the lesson.
- Questions should test understanding.
- Avoid duplicate questions.
- Use the requested difficulty.
- Each MCQ must have four options.
- Exactly one option must be correct.

LESSON CONTENT

...
```

This is much better than:

```text
"Make some questions."
```

The more clearly we define the task, the easier it becomes to validate the result.

---

# 9. Test Understanding, Not Just Memory

This is an important educational principle.

Suppose the lesson says:

> `map()` creates a new array by transforming each element.

A weak question would be:

```text
What does map() do?
```

A better question could be:

```text
Which result is produced when map() is used
to multiply every number in an array by 2?
```

The second question tests whether the student understands how the method works.

So our prompt should encourage:

```text
Recall
+
Understanding
+
Application
```

rather than generating only definition-based questions.

---

# 10. Avoid Questions Outside the Source

Suppose the lesson only discusses:

```text
map()
filter()
reduce()
```

The AI shouldn't generate:

```text
Which JavaScript engine executes Node.js?
```

even if the question is technically related to JavaScript.

We want:

```text
Lesson Content
      ↓
Question
      ↓
Relevant to lesson
```

not:

```text
Entire AI knowledge
      ↓
Random JavaScript question
```

This becomes especially important when we combine this system with RAG.

---

# 11. Duplicate Question Prevention

Imagine generating 10 questions and receiving:

```text
Q1: What does map() do?

Q2: What is the purpose of map()?

Q3: Which method transforms an array?

Q4: Which method creates a transformed array?
```

These are almost the same question.

We want diversity.

The generation requirements should therefore include:

```text
Avoid semantic duplicates.
Use different concepts from the provided content.
Vary the way concepts are tested.
```

Later, we can add programmatic similarity checks as well.

---

# 12. Question Distribution

For a larger quiz, we shouldn't test only one tiny part of the lesson.

For example:

```text
Lesson topics:

map()
filter()
reduce()
forEach()
```

A 10-question quiz might roughly cover:

```text
map()       → 2
filter()    → 2
reduce()    → 2
forEach()   → 2
Comparison  → 2
```

This gives better coverage.

Eventually, we could introduce a concept like:

```ts
type QuestionBlueprint = {
  topic: string;
  count: number;
};
```

For example:

```ts
const blueprint = [
  { topic: "map()", count: 2 },
  { topic: "filter()", count: 2 },
  { topic: "reduce()", count: 2 },
];
```

The AI then generates according to the blueprint.

---

# 13. Structured Output Is Critical

We don't want:

```text
Question 1:
...
Answer:
...
```

as uncontrolled text.

Instead, we want predictable data:

```json
{
  "question": "Which method creates a new array?",
  "options": [
    "map()",
    "push()",
    "pop()",
    "shift()"
  ],
  "correctAnswer": "map()",
  "explanation": "map() returns a new array..."
}
```

Then TypeScript can safely process it.

---

# 14. Validate Every Generated Question

AI output is **untrusted input**.

We can define a Zod schema:

```ts
const generatedQuestionSchema = z.object({
  type: z.enum([
    "MCQ",
    "TRUE_FALSE",
    "SHORT_ANSWER",
  ]),

  question: z.string().min(10),

  options: z
    .array(z.string().min(1))
    .optional(),

  correctAnswer: z.string().min(1),

  explanation: z.string().min(1),

  difficulty: z.enum([
    "EASY",
    "MEDIUM",
    "HARD",
  ]),
});
```

For multiple questions:

```ts
const generatedQuestionsSchema = z.object({
  questions: z.array(generatedQuestionSchema),
});
```

Then:

```ts
const result =
  generatedQuestionsSchema.safeParse(aiResponse);
```

Only validated data proceeds.

---

# 15. Semantic Validation

Schema validation alone isn't enough.

This can technically pass:

```json
{
  "question": "What is JavaScript?",
  "options": ["A", "B", "C", "D"],
  "correctAnswer": "A"
}
```

But it might be a terrible question.

So we need two levels of validation:

```text
AI Output
   ↓
Structural Validation
   ↓
Semantic Validation
   ↓
Accept
```

### Structural validation

Checks:

```text
Is question present?
Are options present?
Is correctAnswer present?
Is difficulty valid?
```

### Semantic validation

Checks things like:

```text
Is the question relevant?
Is the correct answer actually among the options?
Are options meaningfully different?
Is the question duplicated?
Does it match the requested difficulty?
```

We'll go much deeper into this in **Lesson 9.9 — Question Validation**.

---

# 16. Correct Answer Must Exist

For MCQ:

```text
options:
A
B
C
D
```

The correct answer must be one of them.

For example:

```ts
const isValidAnswer =
  question.options.includes(question.correctAnswer);
```

If:

```text
correctAnswer = "E"
```

while options are:

```text
A
B
C
D
```

the question should be rejected.

This is a simple example of **application-level validation**.

---

# 17. Don't Expose Correct Answers to Students

This is a very important backend rule.

When the student requests a quiz:

```http
GET /api/v1/quizzes/:quizId
```

the response should **not** contain:

```json
{
  "correctAnswer": "map()"
}
```

Otherwise the student can inspect the API response and get every answer.

Instead, student-facing data should look like:

```json
{
  "question": "Which method transforms an array?",
  "options": [
    "map()",
    "filter()",
    "push()",
    "pop()"
  ]
}
```

The correct answer remains server-side.

Later:

```text
Student submits answer
       ↓
Backend
       ↓
Compare with stored answer
       ↓
Calculate score
```

This connects directly to **Lesson 9.8 — Quiz Scoring**.

# 18. Generation and Storage

A clean service architecture could look like:

```text
quiz.controller.ts
        ↓
quiz.service.ts
        ↓
ai-question.service.ts
        ↓
AI Provider
        ↓
Zod Validation
        ↓
quiz.repository.ts
        ↓
Prisma
        ↓
PostgreSQL
```

Responsibilities:

### Controller

Handles:

```text
HTTP request
authentication
request validation
response
```

### Service

Handles:

```text
business logic
lesson retrieval
generation parameters
workflow
```

### AI Service

Handles:

```text
prompt
model
structured output
AI provider
```

### Repository

Handles:

```text
database operations
```

This keeps the system maintainable.

# 19. One Important Improvement: Don't Make 10 Separate AI Calls

Suppose the instructor requests:

```text
10 questions
```

A naive implementation might do:

```text
AI call
 ↓ Q1

AI call
 ↓ Q2

AI call
 ↓ Q3

...
```

That's potentially:

```text
10 AI requests
```

Instead, we can often request:

```text
Generate 10 questions
```

in a single structured generation.

```text
One AI request
      ↓
Q1
Q2
Q3
...
Q10
```

Benefits:

- lower latency
    
- fewer API calls
    
- potentially lower cost
    
- easier orchestration
    

However, very large generations can have quality issues, so later we can decide when batching is appropriate.

# 20. Regeneration

Sometimes an instructor won't like a question.

For example:

```text
Question 4
❌ Too easy
```

We shouldn't regenerate the entire quiz.

We can eventually support:

```http
POST /api/v1/questions/:questionId/regenerate
```

Flow:

```text
Existing Question
       ↓
Regeneration Request
       ↓
AI
       ↓
New Question
       ↓
Validation
       ↓
Instructor Review
```

This is a useful feature for the LMS.

We'll connect it with **Lesson 9.10 — Instructor Review**.

# 21. Generation Metadata

It's useful to know how a question was generated.

For example:

```text
questionId
quizId
lessonId
model
difficulty
questionType
promptVersion
createdAt
```

A `promptVersion` is particularly useful.

Imagine:

```text
quiz-v1
quiz-v2
quiz-v3
```

You change your prompt and suddenly question quality improves.

Now you can know which questions were generated using which prompt version.

That's useful for debugging and analytics.
