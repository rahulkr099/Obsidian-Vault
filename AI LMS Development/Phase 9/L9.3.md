# Lesson 9.3 — Multiple Choice Questions (MCQs)

In the roadmap, **9.3 is specifically “Multiple Choice”**, followed by True/False in 9.4 and Short Answer in 9.5.

In Lesson 9.2, we learned the general question-generation pipeline. Now we'll specialize it for **MCQs**.

---

## 1. What is an MCQ?

An MCQ contains:

```text
Question
   ↓
Multiple Options
   ↓
One Correct Answer
```

Example:

```text
Question:
Which JavaScript method creates a new array by
transforming every element?

A. filter()
B. map()
C. push()
D. pop()

Correct Answer:
B. map()
```

For our LMS, we want to represent this as structured data:

```json
{
  "type": "MCQ",
  "question": "Which JavaScript method creates a new array by transforming every element?",
  "options": [
    "filter()",
    "map()",
    "push()",
    "pop()"
  ],
  "correctAnswer": "map()",
  "explanation": "map() creates a new array by applying a function to each element."
}
```

# 2. The MCQ Generation Pipeline

Our architecture becomes:

```text
Lesson Content
      ↓
Question Requirements
      ↓
AI Question Generator
      ↓
MCQ Structured Output
      ↓
Schema Validation
      ↓
MCQ-specific Validation
      ↓
Store / Review
```

The important new part is:

```text
MCQ-specific Validation
```

Because MCQs have rules that other question types don't have.

---

# 3. MCQ Data Model

Let's define a TypeScript type.

```ts
type MCQQuestion = {
  type: "MCQ";
  question: string;
  options: string[];
  correctAnswer: string;
  explanation: string;
  difficulty: "EASY" | "MEDIUM" | "HARD";
};
```

Now TypeScript understands that an MCQ must contain:

```text
type
question
options
correctAnswer
explanation
difficulty
```

---

# 4. How Many Options?

A common design is:

```text
A
B
C
D
```

So:

```ts
options: [
  "Option A",
  "Option B",
  "Option C",
  "Option D"
]
```

We can enforce this at the application level:

```ts
const mcqSchema = z.object({
  type: z.literal("MCQ"),

  question: z.string().min(1),

  options: z
    .array(z.string().min(1))
    .length(4),

  correctAnswer: z.string().min(1),

  explanation: z.string().min(1),

  difficulty: z.enum([
    "EASY",
    "MEDIUM",
    "HARD",
  ]),
});
```

Now an AI response with only three options fails validation.

---

# 5. The Most Important Rule

For a normal single-answer MCQ:

> **Exactly one option must be correct.**

For example:

```text
Question:
Which method creates a new array?

A. map()
B. push()
C. pop()
D. shift()
```

Correct:

```text
A. map()
```

But this is invalid:

```text
A. map()
B. filter()
C. pop()
D. shift()

Correct:
A and B
```

unless we explicitly design a **multiple-select question type**.

For our current MCQ system:

```text
1 question
+
4 options
+
1 correct answer
```

---

# 6. Validate the Correct Answer

After the AI generates the question:

```ts
const isValid = question.options.includes(
  question.correctAnswer
);
```

For example:

```ts
options = [
  "map()",
  "filter()",
  "push()",
  "pop()"
];

correctAnswer = "map()";
```

This passes.

But:

```ts
correctAnswer = "reduce()";
```

fails because:

```text
reduce()
```

isn't one of the options.

This simple validation prevents a surprisingly common AI-generation problem.

---

# 7. Better Representation: Correct Answer Index

There's another approach.

Instead of:

```json
{
  "correctAnswer": "map()"
}
```

we could use:

```json
{
  "correctAnswerIndex": 0
}
```

For:

```text
0 → map()
1 → filter()
2 → push()
3 → pop()
```

Then:

```json
{
  "options": [
    "map()",
    "filter()",
    "push()",
    "pop()"
  ],
  "correctAnswerIndex": 0
}
```

This has an advantage:

The answer is directly tied to the option position.

But it also creates a different concern: if options are reordered, the index must be updated.

For our LMS, either approach can work. I would lean toward storing a stable answer representation internally and making sure the API contract is consistent.

---

# 8. Don't Trust Option Ordering

Suppose the AI always generates:

```text
A = correct
B = wrong
C = wrong
D = wrong
```

Students could start guessing:

> "The answer is probably B because the system usually puts the correct answer first."

That's terrible assessment design.

We should randomize option order.

For example, AI produces:

```text
map()
filter()
push()
pop()
```

Our application can shuffle them:

```text
push()
map()
pop()
filter()
```

The backend must still know which one is correct.

So the architecture becomes:

```text
AI
 ↓
Generate question
 ↓
Validate
 ↓
Shuffle options
 ↓
Store
```

Not:

```text
AI
 ↓
Store immediately
```

---

# 9. Why Shuffle on the Server?

You might think:

> "Why not shuffle options in React?"

You can shuffle the **display order** on the frontend, but you need to be careful with answer evaluation.

A clean approach is to keep the canonical question on the server and send a safe student-facing representation.

For example:

```text
Database
    ↓
Canonical question
    ↓
API
    ↓
Student-specific option order
```

The server remains responsible for scoring.

Remember:

```text
Student
   ↓
Answer
   ↓
Backend
   ↓
Stored correct answer
   ↓
Score
```

Never trust:

```text
Frontend → "I got this answer correct"
```

---

# 10. Good vs Bad MCQs

AI can easily generate technically valid but poor questions.

### Bad

```text
What is JavaScript?

A. A programming language
B. Something
C. Something else
D. Another thing
```

Problems:

- too vague
    
- weak distractors
    
- tests simple recall
    
- doesn't specifically test the lesson
    

### Better

```text
Which array method returns a new array containing
only elements that satisfy a condition?

A. map()
B. filter()
C. push()
D. reduce()
```

Now the question tests actual understanding.

---

# 11. What Are Distractors?

The incorrect options are called **distractors**.

For:

```text
Which method transforms every element of an array?

A. map()       ← Correct
B. filter()    ← Distractor
C. push()      ← Distractor
D. pop()       ← Distractor
```

Good distractors should be:

```text
plausible
related
clearly incorrect after understanding the concept
```

Bad distractors are:

```text
A. map()
B. banana
C. car
D. operating system
```

They're obviously wrong.

The student can answer without understanding JavaScript.

---

# 12. Prompt the AI for Good Distractors

Our prompt can explicitly say:

```text
Generate plausible distractors.

Distractors should:
- relate to the topic
- represent common misunderstandings
- be clearly incorrect based on the lesson
- have similar levels of detail
```

This produces much better assessments.

---

# 13. Avoid Giving Away the Answer

Consider:

```text
Which method creates a new array?

A. map()
B. filter()
C. push()
D. map() is used to create a new array
```

Option D basically gives away the answer.

The options should have similar structure.

Better:

```text
A. map()
B. filter()
C. push()
D. pop()
```

---

# 14. Option Length Matters

Another common AI problem:

```text
A. map()

B. filter()

C. push()

D. map() is a method that creates a completely
new array by executing a callback function against
each element in the original array.
```

The longest answer looks suspicious.

We can instruct the AI:

```text
Keep options reasonably similar in length and style.
Do not make the correct answer obviously longer.
```

Again, this improves assessment quality.

---

# 15. Avoid Double Negatives

Bad:

```text
Which of the following is NOT an invalid
way to avoid NOT using arrays?
```

This is confusing.

Prompt requirements should include:

```text
Use clear and direct wording.
Avoid unnecessary negative phrasing.
Avoid double negatives.
```

The goal is to test knowledge, not reading confusion.

---

# 16. Question Generation Prompt

A simplified prompt could look like:

```text
You are an educational assessment generator.

Generate one multiple-choice question
using only the provided lesson content.

Requirements:
- Exactly 4 options.
- Exactly 1 correct answer.
- Create 3 plausible distractors.
- Test understanding rather than trivial recall.
- Keep options similar in style and length.
- Avoid ambiguous wording.
- Do not introduce information outside the lesson.
- Include a short explanation.

Return structured JSON.
```

Then:

```text
LESSON CONTENT:

JavaScript array methods allow developers
to transform, filter, and process arrays...
```

# 18. MCQ Generation Service

Our architecture could look like:

```ts
class QuizService {
  async generateMCQs(input: GenerateMCQInput) {
    const lesson = await lessonRepository.findById(
      input.lessonId
    );

    if (!lesson) {
      throw new AppError(
        "Lesson not found",
        404
      );
    }

    const questions =
      await aiQuestionService.generateMCQs({
        content: lesson.content,
        count: input.count,
        difficulty: input.difficulty,
      });

    // Validate and process questions

    return questions;
  }
}
```

The controller remains thin.

```text
Controller
    ↓
QuizService
    ↓
AIQuestionService
```

This follows the architecture we've been using throughout the LMS.

# 19. One MCQ vs Many MCQs

We should support both concepts internally.

### One question

```ts
generateMCQ()
```

Useful when:

```text
Instructor regenerates Question 4
```

### Multiple questions

```ts
generateMCQs()
```

Useful when:

```text
Instructor creates a new quiz
```

So:

```text
generateMCQs()
      ↓
generateMCQ() × N
```

or one batched AI generation, depending on the implementation.

We don't necessarily need N separate model calls.

# 20. MCQ Database Design

Eventually our database might have something conceptually like:

```text
Quiz
 │
 ├── Question
 │      ├── type
 │      ├── text
 │      ├── explanation
 │      └── difficulty
 │
 └── QuestionOption
        ├── text
        └── isCorrect
```

There are two common designs.

### Option A — JSON options

```text
Question
 ├── options JSON
 └── correctAnswer
```

### Option B — Separate table

```text
Question
    ↓
QuestionOption
```

For a serious LMS, a separate option structure can provide better relational control and flexibility.

But we'll make the final database design when we reach the database-related implementation work.

# 21. Student API Must Be Different

Instructor/admin may need:

```json
{
  "question": "...",
  "options": ["A", "B", "C", "D"],
  "correctAnswer": "B",
  "explanation": "..."
}
```

But student should receive:

```json
{
  "question": "...",
  "options": ["A", "B", "C", "D"]
}
```

Notice:

```text
correctAnswer ❌
explanation   ❌
```

Then after submission:

```text
Student Answer
      ↓
Backend
      ↓
Correct Answer
      ↓
Score
```

This prevents simple API inspection from revealing the answers.

# 24. MCQ Quality Checklist

Before accepting an AI-generated MCQ:

```text
□ Question is relevant to lesson
□ Question is understandable
□ Exactly 4 options
□ Exactly 1 correct answer
□ Correct answer exists in options
□ No duplicate options
□ Distractors are plausible
□ No obvious answer pattern
□ No unnecessary clues
□ Explanation is correct
□ Difficulty matches requested level
□ No unsupported information
```

We'll turn this into a proper validation system in **9.9**.
