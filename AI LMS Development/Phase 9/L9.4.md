# Lesson 9.4 — True / False Questions

The Phase 9 roadmap defines **9.4 as “True / False”**, immediately after Multiple Choice and before Short Answer.

In 9.3, we built the idea of an MCQ:

```text
Question
   ↓
4 options
   ↓
1 correct answer
```

A **True/False question** is simpler:

```text
Statement
   ↓
TRUE or FALSE
```

But simplicity doesn't mean we can blindly trust AI-generated statements. We still need strong generation rules and validation.

---

## 1. What Are True/False Questions?

Example:

> JavaScript's `map()` method returns a new array.

Answer:

```text
TRUE
```

Another:

> JavaScript's `push()` method removes the last element from an array.

Answer:

```text
FALSE
```

Our system can represent this as:

```json
{
  "type": "TRUE_FALSE",
  "question": "JavaScript's map() method returns a new array.",
  "correctAnswer": true,
  "explanation": "map() creates and returns a new array after applying the callback to each element.",
  "difficulty": "EASY"
}
```

Notice that we don't need:

```text
options: ["True", "False"]
```

because the two possible answers are already defined by the question type.

---

# 2. Data Model

A simple TypeScript representation:

```ts
type TrueFalseQuestion = {
  type: "TRUE_FALSE";
  question: string;
  correctAnswer: boolean;
  explanation: string;
  difficulty: "EASY" | "MEDIUM" | "HARD";
};
```

The important difference from MCQ is:

```text
MCQ
correctAnswer → string / option

TRUE_FALSE
correctAnswer → boolean
```

For example:

```ts
correctAnswer: true
```

or:

```ts
correctAnswer: false
```

This is cleaner than storing:

```ts
correctAnswer: "TRUE"
```

as a random string.

---

# 3. Why True/False Questions Are Tricky

At first glance:

```text
MCQ → difficult
True/False → easy
```

But there's a problem.

AI can create statements that are technically true but **ambiguous**.

For example:

> JavaScript arrays are easy to use.

Is that true?

There is no objective answer.

Another:

> JavaScript arrays are always better than objects.

Again, subjective and overly broad.

A good True/False question should be:

```text
specific
objective
fact-based
unambiguous
related to the lesson
```

---

# 4. Good vs Bad Statements

### Bad

```text
JavaScript is a great programming language.
```

Problem:

```text
Subjective ❌
```

---

### Bad

```text
Arrays are usually useful.
```

Problem:

```text
Vague ❌
```

---

### Better

```text
The JavaScript map() method returns a new array.
```

This can be objectively evaluated:

```text
TRUE
```

---

### Better

```text
The JavaScript pop() method removes the first element of an array.
```

This is objectively false:

```text
FALSE
```

because `pop()` removes the last element.

---

# 5. The AI Prompt

We can specifically instruct the model:

```text
Generate a True/False question
using only the provided lesson content.

Requirements:

- The statement must be objectively true or false.
- Avoid subjective statements.
- Avoid vague wording.
- Avoid double negatives.
- Avoid unnecessary complexity.
- Do not introduce information outside the lesson.
- The statement must have exactly one correct answer.
- Include a short explanation.
```

This is much better than:

```text
Generate some True/False questions.
```

---

# 6. Structured Output

We want the model to return something predictable:

```json
{
  "type": "TRUE_FALSE",
  "question": "The JavaScript pop() method removes the last element of an array.",
  "correctAnswer": true,
  "explanation": "pop() removes and returns the last element of an array.",
  "difficulty": "EASY"
}
```

Our backend then validates this.

---

# 7. Zod Validation

A basic schema:

```ts
const trueFalseQuestionSchema = z.object({
  type: z.literal("TRUE_FALSE"),

  question: z
    .string()
    .min(1),

  correctAnswer: z.boolean(),

  explanation: z
    .string()
    .min(1),

  difficulty: z.enum([
    "EASY",
    "MEDIUM",
    "HARD",
  ]),
});
```

Now:

```json
{
  "correctAnswer": true
}
```

is valid.

But:

```json
{
  "correctAnswer": "true"
}
```

is not.

That's useful because AI sometimes returns values in slightly different formats.

---

# 8. Why Boolean Is Better

Compare:

```ts
correctAnswer: "TRUE"
```

with:

```ts
correctAnswer: true
```

The boolean representation is better for application logic.

For example:

```ts
const isCorrect =
  studentAnswer === question.correctAnswer;
```

Very simple.

Student submits:

```ts
true
```

Database has:

```ts
true
```

Result:

```text
true === true
      ↓
    Correct
```

---

# 9. Don't Let the Student Decide the Correct Answer

Remember the security principle from 9.3.

The frontend should submit:

```json
{
  "questionId": "question_123",
  "answer": true
}
```

The backend retrieves:

```text
question_123
      ↓
correctAnswer = false
```

Then:

```ts
const isCorrect =
  submittedAnswer === storedAnswer;
```

The client should **never** submit:

```json
{
  "isCorrect": true
}
```

because the client cannot be trusted.

---

# 10. Avoid Double Negatives

This is especially important for True/False questions.

Bad:

> It is not uncommon for `map()` to not avoid modifying the original array.

Now the student has to decode multiple negatives instead of demonstrating knowledge.

Better:

> `map()` creates a new array instead of modifying the original array.

Much clearer.

Our prompt should explicitly tell the AI:

```text
Avoid double negatives.
```

---

# 11. Avoid Tricky Wording

Don't try to trick students with unnecessary wording.

Bad:

> It is false that `push()` does not add an element to the end of an array.

The student needs to mentally process:

```text
false
not
does not
```

That's unnecessary.

Better:

> The `push()` method adds one or more elements to the end of an array.

---

# 12. Avoid Absolute Words

AI-generated questions sometimes contain:

```text
always
never
all
none
only
completely
```

For example:

> JavaScript arrays **always** contain values of the same type.

This is false, but it may test whether the student noticed the word `always` rather than whether they understand arrays.

We should instruct the AI:

```text
Avoid unnecessary absolute words unless
they are explicitly supported by the lesson.
```

---

# 13. Don't Make the Answer Pattern Obvious

With True/False quizzes, another problem appears:

```text
Q1 → TRUE
Q2 → TRUE
Q3 → TRUE
Q4 → TRUE
Q5 → TRUE
```

Students might simply guess:

```text
TRUE
```

We should therefore aim for a balanced distribution.

For example, for 10 questions:

```text
TRUE  → 5
FALSE → 5
```

Not necessarily exactly 50/50 every time, but we should avoid obvious patterns.

---

# 14. Who Controls the Distribution?

Not the AI.

Our application can specify:

```ts
type TrueFalseGenerationConfig = {
  total: number;
  trueCount?: number;
  falseCount?: number;
};
```

For example:

```ts
{
  total: 10,
  trueCount: 5,
  falseCount: 5
}
```

The AI generates according to the requested distribution.

Then the application validates the result.

---

# 15. Important: Don't Generate False Statements by Simply Negating True Ones

Suppose the lesson says:

> `pop()` removes the last element.

A naive AI might generate:

> `pop()` does not remove the last element.

This technically creates a false statement, but it's a weak assessment.

A better false statement could be:

> `pop()` removes the first element of an array.

Now the student has to distinguish between:

```text
pop()
    ↓
last element
```

and:

```text
shift()
    ↓
first element
```

This tests understanding.

---

# 16. Use Common Misconceptions

This is where True/False questions become much more valuable.

Suppose students commonly confuse:

```text
pop()  → last
shift() → first
```

We could generate:

> `pop()` removes the first element of an array.

Answer:

```text
FALSE
```

Explanation:

> `pop()` removes the last element. `shift()` removes the first element.

Now the question tests a real misconception.

---

# 17. Explanation Is Important

Don't just store:

```json
{
  "correctAnswer": false
}
```

Store an explanation too:

```json
{
  "correctAnswer": false,
  "explanation": "pop() removes the last element of an array, while shift() removes the first element."
}
```

This becomes extremely useful later.

The explanation can be shown after submission:

```text
Your answer: ❌ Incorrect

Correct answer: FALSE

Why?

pop() removes the last element of an array.
```

This connects directly to **9.11 — AI Explanations**.

---

# 18. Difficulty Levels

Even though detailed difficulty handling belongs to **9.6**, True/False questions can still carry a difficulty value.

### Easy

Direct fact:

> `push()` adds elements to the end of an array.

### Medium

Conceptual distinction:

> `map()` modifies the original array rather than returning a new array.

### Hard

Application/concept combination:

> Calling `map()` without using its returned value can still modify the original array through a mutating operation inside the callback.

The third one requires considerably more understanding.

We'll formalize difficulty later.

# 19. True/False Generation Service

We can keep the service architecture consistent:

```text
Controller
    ↓
Quiz Service
    ↓
AI Question Service
    ↓
AI Provider
```

For example:

```ts
interface AIQuestionService {
  generateMCQs(
    input: GenerateQuestionInput
  ): Promise<MCQQuestion[]>;

  generateTrueFalse(
    input: GenerateQuestionInput
  ): Promise<TrueFalseQuestion[]>;
}
```

The quiz service doesn't need to know how the AI provider works internally.

---

# 20. Example Service Flow

Conceptually:

```ts
async function generateTrueFalseQuestions(
  input: GenerateQuestionInput
) {
  const lesson =
    await lessonRepository.findById(input.lessonId);

  if (!lesson) {
    throw new AppError(
      "Lesson not found",
      404
    );
  }

  const generated =
    await aiQuestionService.generateTrueFalse({
      content: lesson.content,
      count: input.count,
      difficulty: input.difficulty,
    });

  return validateTrueFalseQuestions(generated);
}
```

Notice:

```text
Lesson
 ↓
AI
 ↓
Validation
 ↓
Return
```

Not:

```text
Controller
 ↓
OpenAI SDK
```

# 21. Validation Beyond Zod

Zod can check:

```text
type = TRUE_FALSE
correctAnswer = boolean
question = string
explanation = string
```

But it can't determine whether the statement is actually true.

For example:

```json
{
  "type": "TRUE_FALSE",
  "question": "JavaScript was created in 1980.",
  "correctAnswer": false,
  "explanation": "JavaScript was created in 1995."
}
```

The structure is valid.

But we still need to ask:

```text
Is the statement supported by our lesson?
```

That's semantic validation.

We'll address this much more deeply in **9.9 Question Validation**.

# 22. Grounding the Question

Because we already built RAG in Phase 8, we can eventually ground the question generation.

Instead of:

```text
AI's general knowledge
        ↓
Question
```

we want:

```text
Lesson
  ↓
Relevant chunks
  ↓
Grounded context
  ↓
AI
  ↓
True/False question
```

For example:

```text
Retrieved chunk:

"The push() method adds one or more elements
to the end of an array."
```

AI generates:

> `push()` adds elements to the end of an array.

That's directly supported by the source.

---

# 23. Student-Facing API

When the student starts the quiz, don't send:

```json
{
  "question": "push() adds elements to the end.",
  "correctAnswer": true,
  "explanation": "..."
}
```

Instead:

```json
{
  "questionId": "q_123",
  "type": "TRUE_FALSE",
  "question": "push() adds elements to the end of an array."
}
```

The frontend can display:

```text
┌────────────────────────────────────────┐
│ push() adds elements to the end of an │
│ array.                                 │
│                                        │
│ ○ True                                 │
│ ○ False                                │
└────────────────────────────────────────┘
```

The correct answer remains server-side.

---

# 24. Submission

Student submits:

```json
{
  "questionId": "q_123",
  "answer": true
}
```

Backend:

```text
Student Answer
      ↓
true
      ↓
Stored Answer
      ↓
true
      ↓
Correct
```

If the stored answer is:

```text
false
```

then:

```text
true !== false
       ↓
    Incorrect
```

This logic will become part of the broader scoring system in **9.8**.

---

# 25. A Better Generation Strategy

For a 10-question True/False quiz, instead of asking:

```text
Generate 10 True/False questions.
```

we can provide a blueprint:

```text
Generate 10 questions.

Distribution:
- 5 TRUE
- 5 FALSE

Requirements:
- Cover different concepts.
- Avoid duplicate statements.
- Use only lesson content.
- Include plausible misconceptions.
- Avoid double negatives.
- Avoid subjective claims.
```

Then:

```text
AI
 ↓
10 questions
 ↓
Application validation
 ↓
Distribution validation
```

# 27. MCQ vs True/False

|Feature|MCQ|True/False|
|---|---|---|
|Options|Usually 4|2|
|Correct answers|1|Boolean|
|Distractors|Important|Not applicable|
|Main challenge|Good options|Unambiguous statement|
|Common problem|Weak distractors|Ambiguous wording|
|Validation|Options + answer|Boolean + statement|
|Guessing risk|Medium|Higher|
|Explanation|Useful|Very useful|

The biggest difference is:

```text
MCQ
→ quality of options matters

True/False
→ quality of the statement matters
```

---

# 28. A Practical Example

Suppose the lesson is about JavaScript array methods.

### Generated question

```text
Question:
The filter() method creates a new array containing
elements that satisfy a condition.

Answer:
TRUE
```

### Generated false question

```text
Question:
The filter() method modifies the original array by
removing elements that don't satisfy a condition.

Answer:
FALSE
```

Explanation:

```text
filter() returns a new array and does not directly
modify the original array.
```

Both questions test the same concept from different angles.

But generating both in the same quiz would be somewhat repetitive.

That's why our generation system should consider **concept coverage and duplication**.

---

# 29. Important Design Principle

True/False questions are not supposed to be:

```text
AI
 ↓
Random facts
 ↓
TRUE/FALSE
```

They should be:

```text
Learning Objective
       ↓
Lesson Content
       ↓
Important Concept
       ↓
Possible Misconception
       ↓
True/False Statement
       ↓
Validation
```

That's a much stronger educational pipeline.

# 🧠 Key Takeaways

Remember these points from 9.4:

### 1. Represent the answer as a boolean

```ts
correctAnswer: boolean;
```

### 2. The statement must be objective

Avoid:

```text
great
easy
better
useful
```

unless the lesson explicitly defines those ideas.

### 3. Avoid double negatives

Keep the wording simple.

### 4. Don't generate weak false statements

Instead of simply negating facts, test common misconceptions.

### 5. Keep answers server-side

```text
Frontend → student's answer
Backend  → determines correctness
```

### 6. Ground questions in course material

```text
Lesson
 ↓
Relevant Context
 ↓
AI
 ↓
Question
```

### 7. Validate AI output

```text
AI
 ↓
Zod
 ↓
Business validation
 ↓
Database
```
