# 1. What is a Permissions Matrix?

A **Permissions Matrix** is a table that defines **which roles can perform which actions** in the system.

It answers questions like:

- Can a guest create posts?
    
- Can an author delete another author's post?
    
- Can an admin ban users?
    
- Can a reader publish blogs?
    

Instead of scattering these rules throughout the code, you define them clearly in one place.

---

## Simple Definition

```text
User Role

↓

Allowed Actions

↓

Authorization Rules

↓

Backend Implementation
```

---

# 2. Authentication vs Authorization

Many beginners confuse these.

## Authentication

Authentication answers:

> **Who are you?**

Example:

```text
User

↓

Login

↓

JWT Verified

↓

Identity Confirmed
```

Authentication identifies the user.

---

## Authorization

Authorization answers:

> **What are you allowed to do?**

Example:

```text
User Logged In

↓

Role = Reader

↓

Create Blog?

↓

No
```

Authorization checks permissions.

---

### Comparison

|Authentication|Authorization|
|---|---|
|Verifies identity|Verifies permissions|
|Login|Access control|
|JWT|RBAC|
|"Who are you?"|"What can you do?"|

---

# 3. What is RBAC?

**RBAC (Role-Based Access Control)** is an authorization model where permissions are assigned to **roles**, and users inherit permissions through their assigned role.

Example:

```text
User

↓

Role

↓

Permissions
```

Instead of giving permissions to every individual user, you assign a role.

Example:

```text
Rahul

↓

Author

↓

Can Create Posts

Can Edit Own Posts

Can Publish Posts
```

---

# 4. Why Use RBAC?

Without RBAC:

```text
User A

↓

50 permissions

User B

↓

50 permissions

User C

↓

50 permissions
```

This becomes difficult to manage.

With RBAC:

```text
Author

↓

Create

Edit

Delete Own Posts

Publish

Reader

↓

Read

Comment

Like

Admin

↓

Everything
```

Much simpler.

# 5. Designing Roles

Example: Blog Platform

```text
Guest

↓

Reader

↓

Author

↓

Admin
```

Each role has different responsibilities.

---

## Guest

Can:

- Visit homepage
    
- Read public blogs
    
- Search posts
    

Cannot:

- Comment
    
- Like
    
- Publish
    

---

## Reader

Can:

- Read posts
    
- Comment
    
- Like
    
- Bookmark
    

Cannot:

- Publish
    
- Manage users
    

---

## Author

Can:

- Everything Reader can
    
- Create posts
    
- Edit own posts
    
- Publish posts
    
- Delete own posts
    

Cannot:

- Delete other authors' posts
    
- Manage users
    

---

## Admin

Can:

- Manage users
    
- Delete any post
    
- Remove comments
    
- Ban users
    
- View reports

# 8. Permission Levels

Sometimes roles aren't enough.

Example:

```text
Author

↓

Own Post

↓

Edit Allowed
```

But:

```text
Author

↓

Someone Else's Post

↓

Edit Denied
```

This is called **ownership-based authorization**.

# 14. Permission Naming

Professional systems often use permission names instead of hardcoding roles.

Examples:

```text
post:create

post:update

post:publish

post:delete

comment:create

comment:delete

user:manage

analytics:view
```

This allows more flexibility if roles change later.

# 15. Common Authorization Errors

## Error 1

Checking only authentication.

Wrong:

```text
JWT Valid

↓

Allow Everything
```

Authentication alone is not enough.

---

## Error 2

Ignoring ownership.

Example:

Any author can edit any article.

This is a serious security issue.

---

## Error 3

Hardcoding roles everywhere.

Bad:

```javascript
if (user.role === "ADMIN")
```

Repeated in dozens of files.

Prefer centralized authorization logic.

---

## Error 4

Putting authorization inside repositories.

Repositories should only access data.

Authorization belongs in the service layer.

---

## Error 5

Returning incorrect HTTP status codes.

Remember:

**401 Unauthorized** _(more precisely, unauthenticated)_

- User is not logged in.
    
- Invalid or missing JWT.
    

---

**403 Forbidden**

- User is authenticated.
    
- But lacks permission.

# 17. Permission Checklist

For every action, ask:

- Is login required?
    
- Which roles can perform it?
    
- Does ownership matter?
    
- What business rules apply?
    
- What happens if permission is denied?
    
- What HTTP status should be returned?

# Interview Questions

### Q1. What is a permissions matrix?

**Answer:**

A permissions matrix is a table that maps user roles to the actions they are allowed or denied to perform within a system. It serves as the foundation for implementing authorization.

---

### Q2. What is the difference between authentication and authorization?

**Answer:**

Authentication verifies a user's identity, while authorization determines what actions that authenticated user is allowed to perform.

---

### Q3. What is RBAC?

**Answer:**

Role-Based Access Control (RBAC) is an authorization model in which permissions are assigned to roles, and users gain permissions by being assigned one or more roles.

---

### Q4. Why is ownership-based authorization important?

**Answer:**

Because users with the same role may own different resources. Ownership checks ensure that users can only modify or delete resources they own unless a higher-privileged role, such as an administrator, is permitted to do so.

# Key Takeaways

- **Authentication** answers **"Who are you?"**
    
- **Authorization** answers **"What are you allowed to do?"**
    
- A **Permissions Matrix** documents which roles can perform which actions.
    
- Most real-world systems combine **RBAC** with **ownership-based authorization**.
    
- Keep authorization logic centralized in the **service layer**, not scattered across controllers or repositories.
    
- As applications grow, prefer **permission-based design** (e.g., `post:create`, `user:manage`) because it scales better than checking roles everywhere.

# Real-World Backend Perspective

In many production applications, authorization doesn't stop at checking a role.

For example:

```text
PATCH /posts/123
```

The backend might check:

```text
JWT Valid?

↓

User Exists?

↓

User Has "post:update" Permission?

↓

User Owns Post?

↓

Post Is Not Locked?

↓

Update Allowed
```

A single API request may involve:

- Authentication
    
- RBAC
    
- Ownership checks
    
- Business rules
    
- Resource state validation
    

This layered approach keeps your backend secure and maintainable.
