# Backend Engineering — Requirements Analysis Notes

# Module 13 — Identify Data

> **Goal:** Learn how to identify **what data your application needs to store**, **why it needs that data**, and **how different pieces of data relate to each other**. This is the bridge between **Requirements Analysis** and **Data Modeling**.

---

# Learning Objectives

By the end of this module, you should be able to:

- Identify entities from requirements.
    
- Differentiate entities from attributes.
    
- Discover relationships between entities.
    
- Identify ownership of data.
    
- Prepare for database design.
    

---

# 1. What Does "Identify Data" Mean?

Before creating a database, ask:

> **"What information does the application need to remember?"**

For example, a Blog Platform needs to remember:

- Users
    
- Posts
    
- Comments
    
- Likes
    

If the system doesn't need to remember something, it usually doesn't belong in the database.

# 2. Why is Data Identification Important?

Many beginners create databases like this:

```text
users

posts

comments
```

without asking:

- What data is actually needed?
    
- Who owns this data?
    
- How long should it exist?
    
- Who can update it?
    

Professional backend engineers identify data **before** designing tables or collections.

---

# 3. What is an Entity?

An **Entity** is a real-world object or concept that the application stores information about.

Think of entities as **nouns**.

Examples:

Blog Platform:

```text
User

Post

Comment

Category

Tag

Like
```

Food Delivery:

```text
Customer

Restaurant

Order

Menu

Payment
```

Hospital:

```text
Patient

Doctor

Appointment

Prescription

Invoice
```

---

# 4. How to Find Entities

Read the requirements.

Highlight every important noun.

Example Requirement:

> "Users can create posts and readers can comment."

Nouns:

```text
Users

Posts

Readers

Comments
```

Possible Entities:

```text
User

Post

Comment
```

Notice:

"Reader" is a **role**, not a separate entity.

---

# 5. What are Attributes?

An **Attribute** is a piece of information about an entity.

Example:

Entity:

```text
User
```

Attributes:

```text
id

name

email

password

role

createdAt
```

Another example:

Entity:

```text
Post
```

Attributes:

```text
id

title

content

slug

status

createdAt
```

---

# 6. Entity vs Attribute

Many beginners confuse these.

Example:

|Entity|Attribute|
|---|---|
|User|Name|
|User|Email|
|Post|Title|
|Post|Content|
|Comment|Message|

Remember:

Entities have attributes.

Attributes do **not** become separate tables unless they represent independent data.

# 9. Relationships Between Entities

Entities rarely exist alone.

Example:

```text
User

↓

writes

↓

Post
```

Another:

```text
Post

↓

has

↓

Comments
```

Relationships are essential for database design.

---

# 10. Types of Relationships

## One-to-One (1:1)

Example:

```text
User

↓

Profile
```

One user has one profile.

---

## One-to-Many (1:N)

Example:

```text
User

↓

Posts
```

One user writes many posts.

Each post belongs to one user.

---

## Many-to-Many (M:N)

Example:

```text
Posts

↓

Tags
```

One post has many tags.

One tag belongs to many posts.

Usually implemented using a junction table or linking collection.

# 12. Data Ownership

Every piece of data should have an owner.

Example:

```text
Post

↓

Owner

↓

Author
```

Only the owner should normally edit the post.

---

Another example:

```text
Comment

↓

Owner

↓

Comment Creator
```

Ownership influences authorization.

# 13. Data Lifecycle

Ask:

When is data created?

When is it updated?

When is it deleted?

Example:

Blog Post

```text
Draft

↓

Published

↓

Archived

↓

Deleted
```

The lifecycle affects:

- Business rules
    
- Database fields
    
- APIs
    

---

# 14. Temporary vs Persistent Data

Not everything belongs in the database.

Example:

Login Request

```text
Email

Password
```

These are temporary inputs.

---

Database stores:

```text
Email

Hashed Password
```

Not:

```text
Confirm Password
```

Confirm Password exists only during registration.

---

# 15. Derived Data

Some values can be calculated.

Example:

```text
Total Likes
```

Instead of storing:

```text
likesCount
```

You might calculate:

```text
COUNT(likes)
```

Or you may store it for performance.

Ask:

> Should this value be stored or calculated?

---

# 16. Sensitive Data

Some data requires special protection.

Examples:

```text
Password

Refresh Token

OTP

API Keys
```

These require:

- Encryption or hashing where appropriate
    
- Access restrictions
    
- Careful logging practices
    

Never expose sensitive data in API responses.

# 18. Questions to Identify Data

For every requirement, ask:

- What information must be stored?
    
- Who owns this data?
    
- Is it permanent?
    
- Can it change?
    
- Should it be deleted?
    
- Does another entity reference it?
    
- Is it sensitive?
    
- Can it be derived?
    

These questions reveal missing data.

---

# 19. Common Mistakes

## Mistake 1

Creating an entity for everything.

Wrong:

```text
Login
```

Login is a process, not an entity.

---

## Mistake 2

Ignoring ownership.

Without ownership:

Anyone might edit anyone else's data.

---

## Mistake 3

Storing derived values unnecessarily.

Ask whether values should be calculated instead.

---

## Mistake 4

Storing temporary data.

Example:

```text
Confirm Password
```

Never store it.

---

## Mistake 5

Forgetting timestamps.

Most entities benefit from:

```text
createdAt

updatedAt
```

Sometimes:

```text
deletedAt
```

for soft deletion.

---

# 20. Data Identification Checklist

For every entity, ask:

- What is its purpose?
    
- What attributes does it have?
    
- Which attributes are required?
    
- Who owns it?
    
- Which entities reference it?
    
- What is its lifecycle?
    
- Is any data sensitive?
    
- Is any data derived?
    
- When is it created?
    
- When is it deleted?

# Interview Questions

### Q1. What is an entity?

**Answer:**

An entity is a real-world object or concept about which the system stores information, such as a User, Post, Order, or Comment.

---

### Q2. What is the difference between an entity and an attribute?

**Answer:**

An entity represents an object being modeled, while an attribute is a property that describes that entity. For example, `User` is an entity, while `email` is one of its attributes.

---

### Q3. Why is identifying relationships between entities important?

**Answer:**

Relationships help determine how data is connected, which influences database schema design, query efficiency, foreign keys or references, and business logic.

---

### Q4. What is data ownership?

**Answer:**

Data ownership identifies which user or system is responsible for a piece of data. It is essential for implementing authorization and enforcing business rules, such as allowing only the creator of a post to edit it.

# Key Takeaways

- Data identification is the foundation of good database design.
    
- Entities represent **things**, while attributes describe those things.
    
- Every entity should have clear relationships and ownership.
    
- Not all data should be stored—distinguish between persistent, temporary, sensitive, and derived data.
    
- A well-identified data model makes API design, authorization, validation, and querying much easier.

# Real-World Backend Perspective

Experienced backend engineers don't jump directly into creating tables or MongoDB collections.

Instead, they often create a simple document like this:

|Entity|Purpose|Owner|
|---|---|---|
|User|Store account information|User|
|Post|Store blog content|Author|
|Comment|Store discussions|Comment creator|
|Like|Record user likes|User|
|Category|Organize posts|Admin|

This document helps the entire team understand the domain before any schema or code is written.
