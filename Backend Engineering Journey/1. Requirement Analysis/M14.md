# Backend Engineering — Requirements Analysis Notes

# Module 14 — Identify Queries

> **Goal:** Learn how to identify the queries your application must answer before designing the database. Professional backend engineers don't design databases around tables—they design them around **how the data will be queried**.

---

# Learning Objectives

By the end of this module, you should be able to:

- Understand why queries drive database design.
    
- Identify read and write operations.
    
- Design databases based on access patterns.
    
- Discover indexing requirements.
    
- Optimize APIs through query analysis.
    

---

# 1. What Does "Identify Queries" Mean?

Every application asks questions.

For example, Instagram asks:

```text
Show me my feed.

↓

Show comments.

↓

Show likes.

↓

Search users.

↓

Show notifications.
```

Those are queries.

Before designing a database, ask:

> **"What questions must the application answer?"**

# 2. Why Are Queries Important?

Many beginners design databases like this:

```text
users

posts

comments
```

Then later realize:

```text
Search is slow.

↓

Analytics is slow.

↓

Homepage loads slowly.
```

The problem wasn't the database.

The problem was **designing tables before understanding queries.**

Professional engineers ask:

> **"How will this data be used?"**

before asking:

> **"Where should this data be stored?"**

# 8. Queries Drive Indexes

Suppose this query is very common:

```text

WHERE

email = ?
```

Database should index:

```text

```

---

Another query:

```text
Find Posts

WHERE

slug = ?
```

Index:

```text
slug
```

---

Another:

```text
Find Posts

WHERE

authorId = ?
```

Index:

```text
authorId
```

Without understanding queries, indexes become guesswork.

# 21. Common Mistakes

## Mistake 1

Designing tables before identifying queries.

Always identify queries first.

---

## Mistake 2

Ignoring search requirements.

Search often requires different optimizations than simple lookups.

---

## Mistake 3

Loading too much data.

Always consider:

- Pagination
    
- Filtering
    
- Sorting
    

---

## Mistake 4

Missing indexes.

If a field is frequently searched, filtered, or sorted, it may need an index.

---

## Mistake 5

Optimizing every query equally.

Focus first on:

- Frequently executed queries.
    
- User-facing queries.

# Interview Questions

### Q1. Why should backend engineers identify queries before designing the database?

**Answer:**

Because the way data is queried determines how it should be structured, indexed, and related. Designing around access patterns leads to better performance and simpler APIs.

---

### Q2. What are the four main types of database operations?

**Answer:**

The four main operations are:

- Create
    
- Read
    
- Update
    
- Delete (CRUD)
    

These form the basis of most backend APIs.

---

### Q3. How do queries influence indexes?

**Answer:**

Frequently searched, filtered, sorted, or joined fields often require indexes to improve query performance and reduce database response time.

---

### Q4. Why is query frequency important?

**Answer:**

High-frequency queries affect more users and consume more resources, so they should be optimized before infrequent administrative or reporting queries.

# Key Takeaways

- Design your database around **the questions it must answer**, not just the entities it stores.
    
- User stories naturally reveal the queries your application needs.
    
- Queries influence APIs, relationships, indexes, pagination, filtering, sorting, and aggregation.
    
- High-frequency queries deserve the most optimization effort.
    
- Thinking about queries early helps avoid expensive database redesigns later.
    

---

# Real-World Backend Perspective

When a senior backend engineer reviews a database design, they often ask questions like:

- "How will the homepage fetch posts?"
    
- "How often will this query run?"
    
- "Which fields are filtered?"
    
- "Do we need pagination?"
    
- "Should this field be indexed?"
    
- "Can this aggregation be cached?"
    

Notice that these questions focus on **how the application accesses data**, not just how the data is stored.
