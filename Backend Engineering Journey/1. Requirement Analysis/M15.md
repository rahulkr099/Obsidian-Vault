# Module 15 — Identify APIs

> **Goal:** Learn how to transform business requirements, user stories, workflows, and queries into a professional API design. APIs are **contracts** between the frontend (or other clients) and your backend—not just Express routes.

# 1. What Does "Identify APIs" Mean?

An API (Application Programming Interface) defines **how clients communicate with your backend**.

It answers questions like:

- What endpoint should the frontend call?
    
- Which HTTP method should be used?
    
- What data should be sent?
    
- What response should be returned?
    
- What errors are possible?
    

Think of an API as a **contract**.

# 3. APIs Represent Resources

In REST, APIs are designed around **resources (nouns)**, not actions (verbs).

Good:

```http
GET /posts
```

Bad:

```http
GET /getPosts
```

Good:

```http
POST /posts
```

Bad:

```http
POST /createPost
```

Resources usually come from your entities:

```text
User

↓

Post

↓

Comment

↓

Category

↓

Tag
```

# 4. Mapping CRUD to HTTP Methods

|Operation|HTTP Method|
|---|---|
|Create|POST|
|Read|GET|
|Update|PATCH or PUT|
|Delete|DELETE|

|Action|API|
|---|---|
|Create Post|POST /posts|
|Get Posts|GET /posts|
|Get One Post|GET /posts/:id|
|Update Post|PATCH /posts/:id|
|Delete Post|DELETE /posts/:id|

# 9. API Naming Conventions

Good:

```http
/users

/posts

/comments
```

Avoid:

```http
/userList

/blogPosts

/createComment
```

General rules:

- Use plural nouns.
    
- Use lowercase.
    
- Use hyphens instead of spaces or camelCase.
    
- Keep names predictable.

# 10. Query Parameters

Instead of creating many endpoints:

Bad:

```http
GET /latestPosts

GET /popularPosts

GET /nodePosts
```

Use query parameters:

```http
GET /posts?sort=latest
```

---

```http
GET /posts?sort=popular
```

---

```http
GET /posts?category=nodejs
```

---

```http
GET /posts?author=rahul
```

Query parameters make APIs more flexible.

---

# 11. Pagination

Professional APIs return limited data.

Example:

```http
GET /posts?page=2&limit=20
```

Response:

```json
{
  "page": 2,
  "limit": 20,
  "total": 154,
  "data": []
}
```

Avoid returning thousands of records at once.

---

# 12. Filtering

Example:

```http
GET /posts?status=published
```

---

```http
GET /posts?category=nodejs
```

---

```http
GET /posts?author=rahul
```

Filters reduce unnecessary data transfer.

# 13. Sorting

Example:

```http
GET /posts?sort=createdAt
```

---

Descending:

```http
GET /posts?sort=-createdAt
```

Or:

```http
GET /posts?sort=latest
```

Choose a consistent style and document it.

# 14. Search

- Title

Success Response

```json
{
```

# 17. Error Responses

Example:

```json
  "success": false,
```

Keep error responses consistent.

# 18. HTTP Status Codes

Common status codes:

|Code|Meaning|
|---|---|
|200|OK|
|201|Created|
|204|No Content|
|400|Bad Request|
|401|Unauthorized (authentication required or invalid)|
|403|Forbidden|
|404|Not Found|
|409|Conflict|
|422|Unprocessable Entity (validation/business rule failures, if your API uses it)|
|500|Internal Server Error|

Example:

Create Post

```http
POST /posts
```

Return:

```http
201 Created
```

Delete:

```http
DELETE /posts/5
```

Return:

```http
204 No Content
```

# 20. API Design Checklist

For every endpoint, ask:

- What user story does it support?
    
- Which HTTP method fits?
    
- Which resource is involved?
    
- Does it require authentication?
    
- Does it require authorization?
    
- What request data is needed?
    
- What response should be returned?
    
- What errors are possible?

# 22. Common Mistakes

## Mistake 1

Designing APIs before understanding requirements.

Always derive APIs from user stories and workflows.

---

## Mistake 2

Using verbs in URLs.

Wrong:

```http
/createUser
```

Correct:

```http
/users
```

---

## Mistake 3

Returning inconsistent responses.

Keep response structures predictable.

---

## Mistake 4

Ignoring HTTP status codes.

Use the correct code for each outcome.

---

## Mistake 5

Creating too many specialized endpoints.

Prefer query parameters when appropriate.

# Interview Questions

### Q1. What is an API contract?

**Answer:**

An API contract defines how clients interact with the backend. It specifies endpoints, HTTP methods, request formats, response formats, authentication requirements, and possible error responses.

---

### Q2. Why should APIs be designed around resources?

**Answer:**

RESTful APIs treat resources (such as users, posts, and comments) as the primary objects. This creates predictable, scalable, and easy-to-understand endpoints.

---

### Q3. When should you use `POST`, `GET`, `PATCH`, and `DELETE`?

**Answer:**

- `POST` for creating resources.
    
- `GET` for retrieving resources.
    
- `PATCH` for partially updating resources.
    
- `DELETE` for removing resources.
    

---

### Q4. Why are pagination and filtering important?

**Answer:**

They reduce unnecessary data transfer, improve API performance, and allow clients to request only the data they need.

# Key Takeaways

- APIs are **contracts**, not just Express routes.
    
- Design APIs from **requirements**, not from database tables.
    
- Use **RESTful resource-based URLs** with appropriate HTTP methods.
    
- Keep request and response formats consistent.
    
- Support pagination, filtering, sorting, and search for scalable APIs.
    
- Good API design simplifies frontend development and long-term maintenance.

# Real-World Backend Perspective

Before implementing an endpoint, experienced backend engineers often create an API specification like this:

|Endpoint|Purpose|Controller|Service|Repository|
|---|---|---|---|---|
|`POST /posts`|Create post|`createPost()`|`createPost()`|`create()`|
|`GET /posts`|List posts|`getPosts()`|`getPosts()`|`findAll()`|
|`PATCH /posts/:id`|Update post|`updatePost()`|`updatePost()`|`updateById()`|

This mapping keeps the architecture organized and makes it easy for frontend developers, QA engineers, and other backend developers to understand the system.
