# Backend Engineering — Requirements Analysis Notes

# Module 17 — Performance Thinking

> **Goal:** Learn how to think about performance **before** writing code. Professional backend engineers don't wait until an application becomes slow—they design systems that can grow from **100 users to millions** by considering performance from the beginning.

---

# Learning Objectives

By the end of this module, you should be able to:

- Understand performance thinking.
    
- Identify performance bottlenecks.
    
- Estimate application growth.
    
- Design efficient APIs and database queries.
    
- Recognize when caching, indexing, or scaling may be needed.
    

---

# 1. What is Performance Thinking?

Performance Thinking means asking:

> **"Will this still work when the application becomes successful?"**

Many beginners ask:

```text
Will my code work?
```

Professional backend engineers ask:

```text
Will my code still work with

100 users?

↓

10,000 users?

↓

1 million users?
```

Performance is about planning for growth, not just making features work.

---

# 2. Why is Performance Thinking Important?

Suppose you build a Blog Platform.

Today:

```text
50 users
```

Everything is fast.

Six months later:

```text
500,000 users
```

Now:

- Homepage takes 8 seconds.
    
- Search is slow.
    
- Database CPU is 100%.
    
- Users leave.
    

Performance should be considered **during design**, not after complaints.

# 5. Performance Checklist

For every feature, ask:

- How often will it be used?
    
- How much data will it process?
    
- Is it read-heavy or write-heavy?
    
- Does it need pagination?
    
- Does it need caching?
    
- Which database fields should be indexed?
    
- Can unnecessary work be avoided?
    

---

# 6. Identify High-Traffic Features

Not every API receives the same traffic.

Example:

Blog Platform

Homepage

```text
GET /posts
```

Millions of requests.

---

Admin Dashboard

```text
GET /admin/reports
```

Few requests.

Optimize high-traffic APIs first.

---

# 7. Read-Heavy vs Write-Heavy Systems

## Read-Heavy

Examples:

- Blog Platform
    
- News Website
    
- YouTube
    
- Documentation Site
    

Most requests are:

```text
GET
```

Optimization focuses on:

- Caching
    
- Indexes
    
- Read replicas
    

---

## Write-Heavy

Examples:

- Chat Application
    
- Payment System
    
- Banking
    

Most requests are:

```text
POST

PATCH
```

Optimization focuses on:

- Transactions
    
- Efficient writes
    
- Queue processing
    

Understanding your workload helps choose the right architecture.

---

# 8. Query Performance

Bad:

```text
Load

100,000 posts

↓

Filter in JavaScript
```

Good:

```text
Database

↓

WHERE

status = published

↓

LIMIT 20
```

Always let the database do the filtering when possible.

---

# 9. Index Thinking

Suppose users frequently search by email.

Query:

```sql
SELECT *

FROM users

WHERE email = ?
```

Without an index:

```text
Database

↓

Check Every Row
```

With an index:

```text
Database

↓

Jump Directly

↓

Return Result
```

Indexes make frequent lookups much faster, though they also increase storage and slightly slow writes.

---

# 10. Pagination Thinking

Bad:

```http
GET /posts
```

Returns:

```text
100,000 posts
```

Good:

```http
GET /posts?page=1&limit=20
```

Benefits:

- Faster responses
    
- Less memory usage
    
- Better user experience
    

---

# 11. Filtering Early

Instead of:

```text
Database

↓

Return Everything

↓

Application Filters
```

Prefer:

```text
Database

↓

Filter

↓

Return Needed Data Only
```

Move filtering as close to the data as possible.

---

# 12. Selecting Only Needed Data

Bad:

```text
Return

Every Field

From User
```

Good:

```text
Return

Name

Avatar
```

Avoid transferring unnecessary data.

---

# 13. Caching

Imagine this query:

```http
GET /posts
```

Executed:

```text
1000 times

per minute
```

Instead of querying the database every time:

```text
Client

↓

Cache

↓

Database
```

Frequently requested data may be cached.

Common examples:

- Homepage
    
- Trending posts
    
- Categories
    

Remember:

Cache only when it provides clear value and you have a strategy to keep it reasonably fresh.

---

# 14. Performance Bottlenecks

A bottleneck is the slowest part of the system.

Example:

```text
Client

↓

Backend

↓

Database

↓

Response
```

Possible bottlenecks:

- Slow database query
    
- Large file upload
    
- Slow external API
    
- Network latency
    
- CPU-intensive processing
    

Always identify the bottleneck before optimizing.

# 17. Image & File Performance

Avoid:

```text
Upload

200 MB image
```

Better:

- Set upload limits.
    
- Compress images where appropriate.
    
- Store files in object storage.
    
- Store only file references in the database.

# Interview Questions

### Q1. What is performance thinking?

**Answer:**

Performance thinking is the practice of considering scalability, efficiency, and resource usage during system design rather than waiting until performance problems appear in production.

---

### Q2. Why is pagination important?

**Answer:**

Pagination limits the amount of data returned in a single request, reducing response time, memory usage, network transfer, and database load.

---

### Q3. When should you use caching?

**Answer:**

Caching is useful for frequently requested data that does not change often or can tolerate short periods of staleness, such as homepages, categories, or trending content.

---

### Q4. What is a performance bottleneck?

**Answer:**

A bottleneck is the slowest component in a system that limits overall performance, such as an inefficient database query, slow external service, or CPU-intensive operation.

# Key Takeaways

- Think about performance from the beginning, not after deployment.
    
- Design around **real usage patterns** and expected growth.
    
- Optimize high-traffic queries before low-traffic ones.
    
- Use pagination, filtering, indexing, and caching where appropriate.
    
- Measure performance before making optimization decisions.
    
- Good backend engineers ask **"Will this still perform well when the application grows?"**

A senior backend engineer asks:
