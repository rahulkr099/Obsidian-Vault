# Backend Engineering — Requirements Analysis Notes

# Module 19 — Acceptance Criteria

> **Goal:** Learn how to define **exactly when a feature is considered complete**. Acceptance criteria transform vague requirements into **clear, measurable, and testable conditions** that developers, testers, product managers, and stakeholders all agree upon.

---

# Learning Objectives

By the end of this module, you should be able to:

- Understand what acceptance criteria are.
    
- Write clear and testable acceptance criteria.
    
- Connect user stories to acceptance criteria.
    
- Differentiate acceptance criteria from requirements and test cases.
    
- Use acceptance criteria as the definition of "Done."
    

---

# 1. What are Acceptance Criteria?

Acceptance Criteria are **specific conditions that must be satisfied before a feature is considered complete.**

They answer one question:

> **"How do we know this feature is finished?"**

Without acceptance criteria:

```text
Feature

↓

Maybe Done?
```

With acceptance criteria:

```text
Feature

↓

Meets Every Condition

↓

Accepted
```

---

# 2. Why Are Acceptance Criteria Important?

Imagine a Product Manager says:

> "Users should be able to publish blog posts."

Questions immediately arise:

- Can anyone publish?
    
- Should drafts be allowed?
    
- Is a title required?
    
- Is content required?
    
- What if the post is already published?
    

Acceptance criteria answer all these questions before coding begins.

---

# 3. Requirements vs Business Rules vs Acceptance Criteria

Many beginners confuse these concepts.

### Functional Requirement

Defines **what** the system should do.

Example:

```text
The system shall allow
authors to publish posts.
```

---

### Business Rule

Defines **under what conditions** the action is allowed.

Example:

```text
Only verified authors
may publish.
```

---

### Acceptance Criteria

Defines **how we verify the feature is complete.**

Example:

```text
✓ Author is verified

✓ User owns the post

✓ Title exists

✓ Content exists

✓ Status changes to Published

✓ Published date stored
```

---

# 4. Characteristics of Good Acceptance Criteria

Good acceptance criteria are:

- Clear
    
- Specific
    
- Measurable
    
- Testable
    
- Unambiguous
    

Bad:

```text
The page should load quickly.
```

Good:

```text
Homepage loads

within 2 seconds

under expected traffic.
```

Specific criteria are easier to test.

# 15. Acceptance Criteria and Testing

Acceptance criteria become test cases.

Example:

Acceptance Criterion:

```text
Email must be unique.
```

Tests:

```text
Create user

↓

Success

↓

Create again

↓

409 Conflict
```

QA teams often derive tests directly from acceptance criteria.

# 17. Given / When / Then Format

Another professional style uses **Given / When / Then**.

Feature:

Publish Blog

```text
Given

Author owns draft

When

Publish requested

Then

Post becomes Published
```

Another:

```text
Given

Missing title

When

Publish requested

Then

Validation error returned
```

This format is common in Agile teams and Behavior-Driven Development (BDD).

# 18. Definition of Done

Acceptance Criteria contribute to the **Definition of Done (DoD).**

A feature is complete only if:

```text
Acceptance Criteria

↓

Implemented

↓

Tested

↓

Reviewed

↓

Approved

↓

Merged
```

Coding alone is not enough.

# 19. Common Mistakes

## Mistake 1

Acceptance criteria too vague.

Bad:

```text
Should work correctly.
```

---

## Mistake 2

Combining multiple unrelated features.

Each feature should have its own acceptance criteria.

---

## Mistake 3

Ignoring failure scenarios.

Test both:

- Success
    
- Failure
    

---

## Mistake 4

Acceptance criteria that cannot be tested.

If it cannot be verified, rewrite it.

---

## Mistake 5

Changing business rules without updating acceptance criteria.

Keep them synchronized.

# 20. Acceptance Criteria Checklist

For every feature, ask:

- What must be true before the feature starts?
    
- What validations are required?
    
- Which business rules apply?
    
- What changes in the database?
    
- What response should the API return?
    
- What errors are possible?
    
- How will QA verify completion?

# Interview Questions

### Q1. What are acceptance criteria?

**Answer:**

Acceptance criteria are specific, measurable, and testable conditions that define when a feature is considered complete and acceptable to stakeholders.

---

### Q2. How are acceptance criteria different from business rules?

**Answer:**

Business rules define the policies and constraints of the system, while acceptance criteria define how to verify that a feature correctly implements those rules and meets the requirements.

---

### Q3. Why are acceptance criteria important for testing?

**Answer:**

Acceptance criteria provide clear conditions that QA engineers and developers can use to create test cases and objectively determine whether a feature works as intended.

---

### Q4. What is the "Given / When / Then" format?

**Answer:**

It is a structured way of writing acceptance criteria:

- **Given** – the initial context.
    
- **When** – the action performed.
    
- **Then** – the expected outcome.
    

This format improves clarity and is widely used in Behavior-Driven Development (BDD).

# Key Takeaways

- Acceptance criteria define **what "done" means** for a feature.
    
- They should be **clear, measurable, and testable**.
    
- Every major business rule should have corresponding acceptance criteria.
    
- Acceptance criteria guide developers, QA engineers, and stakeholders toward the same expectations.
    
- Well-written acceptance criteria reduce misunderstandings, rework, and bugs.
    

---

# Real-World Backend Perspective

During sprint planning, a Product Manager might ask:

> "Is the **Publish Blog** feature complete?"

An experienced backend engineer doesn't answer:

> "The endpoint is working."

Instead, they verify:

- ✅ Business rules implemented
    
- ✅ API returns correct responses
    
- ✅ Database updates correctly
    
- ✅ Authorization enforced
    
- ✅ Edge cases handled
    
- ✅ Tests passing
    
- ✅ Acceptance criteria satisfied
    

Only then is the feature considered complete.
