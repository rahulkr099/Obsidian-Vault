# Backend Engineering — Requirements Analysis Notes

# Module 3 — Stakeholder Analysis

> **Goal:** Learn how to identify everyone involved in a software system, understand their goals, responsibilities, permissions, and pain points, so you can build a backend that serves all users—not just one type of user.

---

# Learning Objectives

By the end of this module, you should be able to:

- Understand what a stakeholder is.
    
- Identify all stakeholders in a system.
    
- Analyze each stakeholder's goals and problems.
    
- Map permissions and responsibilities.
    
- Discover missing requirements through stakeholder analysis.
    

---

# 1. What is a Stakeholder?

A **stakeholder** is any person, group, or organization that is affected by or has an interest in the software system.

They may:

- Use the application.
    
- Manage the application.
    
- Own the application.
    
- Support the application.
    
- Build the application.
    

### Simple Definition

> **A stakeholder is anyone who gains value from the system or influences how it works.**

---

# 2. Why is Stakeholder Analysis Important?

If you only think about one type of user, you'll likely miss important features.

### Example

Imagine you're building a Blog Platform.

If you only think about **Authors**, you might build:

- Create post
    
- Edit post
    
- Delete post
    

But what about:

- Readers?
    
- Admins?
    
- Guests?
    

Without considering them, you might forget:

- Search
    
- Content moderation
    
- Spam detection
    
- User management
    

Stakeholder analysis helps you build a complete system.

---

# 3. Types of Stakeholders

Stakeholders are usually divided into two categories.

## A. Primary Stakeholders

These directly use the application.

Examples:

- Customer
    
- Reader
    
- Author
    
- Student
    
- Teacher
    
- Doctor
    
- Patient
    

---

## B. Secondary Stakeholders

These support, manage, or influence the system.

Examples:

- Admin
    
- Company Owner
    
- Customer Support
    
- Developers
    
- System Administrator
    
- Business Analyst

# 5. Stakeholder Analysis Template

For every stakeholder, answer these questions:

|Question|Purpose|
|---|---|
|Who are they?|Identify the stakeholder|
|What is their goal?|Understand why they use the system|
|What tasks do they perform?|Discover required features|
|What permissions do they need?|Design authorization|
|What problems do they face?|Improve user experience|

# 7. Identify Goals Instead of Features

Don't ask:

> "What pages does the user need?"

Ask:

> "What is the user's goal?"

Example:

Instead of:

```text
Dashboard
```

Think:

```text
Author wants to manage articles efficiently.
```

Now many features naturally appear:

- Dashboard
    
- Drafts
    
- Analytics
    
- Scheduled publishing
    

Goals reveal better requirements than screens.

---

# 8. Stakeholder Goals Can Conflict

Different stakeholders often have different priorities.

### Example

Author

```text
Publish articles quickly.
```

Admin

```text
Review articles before publishing.
```

Owner

```text
Increase platform quality.
```

Backend engineers must design systems that balance these needs.

# 10. Stakeholder Analysis and Authorization

Stakeholder analysis naturally leads to role-based access control (RBAC).

Example:

|Feature|Guest|Reader|Author|Admin|
|---|:-:|:-:|:-:|:-:|
|View Posts|✅|✅|✅|✅|
|Create Post|❌|❌|✅|✅|
|Edit Own Post|❌|❌|✅|✅|
|Delete Any Post|❌|❌|❌|✅|
|Manage Users|❌|❌|❌|✅|

This table becomes the foundation for your authorization logic.

# 12. Questions to Ask Every Stakeholder

A backend engineer should ask:

### Goals

- What are you trying to achieve?
    

---

### Daily Tasks

- What do you do most often?
    

---

### Pain Points

- What wastes your time?
    

---

### Permissions

- What actions should you be allowed to perform?
    

---

### Success

- What would make this system successful for you?
    

These questions reveal hidden requirements.

---

# 13. Common Mistakes

## Mistake 1

Ignoring Admin users.

Many beginners only design features for end users.

---

## Mistake 2

Assuming all users behave the same way.

Different users have different goals.

---

## Mistake 3

Giving everyone the same permissions.

This creates serious security risks.

---

## Mistake 4

Focusing only on screens.

Focus on user goals instead.

---

## Mistake 5

Not considering future stakeholders.

For example:

Today:

```text
Reader

Author

Admin
```

Tomorrow:

```text
Moderator

Editor

Premium Member

Advertiser
```

Design with reasonable flexibility.

# Interview Questions

### Q1. What is a stakeholder?

**Answer:**

A stakeholder is any individual, group, or organization that uses, manages, owns, supports, or is affected by a software system.

---

### Q2. Why is stakeholder analysis important?

**Answer:**

It helps identify user needs, permissions, responsibilities, and pain points, ensuring that the system meets the requirements of all relevant users instead of focusing on only one group.

---

### Q3. What is the difference between primary and secondary stakeholders?

**Answer:**

Primary stakeholders directly use the application, such as customers or authors. Secondary stakeholders support or manage the application, such as administrators, business owners, or developers.

---

### Q4. How does stakeholder analysis help backend engineers?

**Answer:**

It guides the design of APIs, authorization rules, workflows, data models, and business logic by clearly defining what each stakeholder can do and what they need from the system.

# Key Takeaways

- Every software system has multiple stakeholders with different goals.
    
- Stakeholder analysis helps uncover hidden requirements early.
    
- Focus on **goals**, not just interface screens.
    
- Permissions and authorization should be based on stakeholder roles.
    
- Good stakeholder analysis leads to better APIs, workflows, business rules, and security.
