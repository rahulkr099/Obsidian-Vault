# 1. What is a User Story?

A **User Story** is a short description of a feature from the perspective of the user.

It explains:

- **Who** wants something?
    
- **What** do they want?
    
- **Why** do they want it?
    

A user story focuses on the **user's goal**, not on technical implementation.

---

## Standard Format

```text
As a <type of user>,

I want <goal>,

So that <benefit>.
```

This simple format keeps the focus on solving user problems.

---

# 2. Why Do We Write User Stories?

Instead of saying:

```text
Build authentication.
```

Write:

```text
As a visitor,

I want to create an account,

So that I can save my personal data.
```

The second version explains **why** the feature exists.

That "why" helps engineers make better decisions.

---

# 3. User Story vs Requirement

Many beginners think they are the same.

|User Story|Requirement|
|---|---|
|Written from the user's perspective|Written from the system's perspective|
|Focuses on user goals|Focuses on system behavior|
|Simple and easy to understand|More detailed and technical|
|Helps identify features|Helps define implementation|

---

### Example

User Story

```text
As an author,

I want to save drafts,

So that I don't lose unfinished work.
```

Requirement

```text
The system shall allow authenticated authors
to save unpublished blog posts.
```

Both describe the same feature, but at different levels.


Let's break it down.

### User

```text
Reader
```

Who needs the feature?

---

### Goal

```text
Search blog posts
```

What are they trying to do?

---

### Benefit

```text
Find articles quickly
```

Why do they need it?

# 5. Characteristics of Good User Stories

A good user story should be:

- Clear
    
- Short
    
- User-focused
    
- Valuable
    
- Testable
    

A useful guideline is the **INVEST** principle.

|Letter|Meaning|
|---|---|
|**I**|Independent|
|**N**|Negotiable|
|**V**|Valuable|
|**E**|Estimable|
|**S**|Small|
|**T**|Testable|

### Example

Bad:

```text
As a user,

I want a better website.
```

Good:

```text
As a reader,

I want to bookmark blog posts,

So that I can read them later.
```

# 7. Breaking Large Stories into Smaller Stories

Large stories are called **Epics**.

Example:

Epic:

```text
As a customer,

I want to order food,

So that I can receive meals at home.
```

This is too large.

Break it down.

---

Story 1

```text
Browse restaurants
```

---

Story 2

```text
View menu
```

---

Story 3

```text
Add items to cart
```

---

Story 4

```text
Place order
```

---

Story 5

```text
Track delivery
```

Each smaller story can be implemented independently.

---

# 8. User Stories Drive Backend Design

Consider this story.

```text
As an author,

I want to save drafts,

So that I can continue writing later.
```

Backend implications:

Database:

```text
Post

status = draft
```

API:

```text
POST /posts

PATCH /posts/:id
```

Business Rules:

```text
Only author can edit draft.
```

Validation:

```text
Draft title may be optional.
```

A single story affects multiple backend components.

---

# 9. User Stories Reveal Business Rules

Example:

```text
As a reader,

I want to like a post,

So that I can show appreciation.
```

Business rules discovered:

- Only logged-in users can like.
    
- One user can like a post only once.
    
- Users can remove their like.
    
- Deleted posts cannot be liked.
    

These rules were not explicitly mentioned, but they naturally arise from the story.

Example:


---

Example:

```text
As a reader,

I want to comment on a post.
```

Possible API:

```http
POST /posts/:id/comments
```

Requirements drive APIs—not the other way around.

---

# 11. User Stories Help Identify Database Entities

Stories often reveal what data must be stored.

Example:

```text
As a reader,

I want to bookmark posts.
```

Possible entity:

```text
Bookmarks
```

Fields:

- id
    
- userId
    
- postId
    
- createdAt
    

---

Another story:

```text
As an author,

I want scheduled publishing.
```

New database field:

```text
publishAt
```

Stories help discover missing fields and entities.

---

# 12. User Stories Help Testing

Every story can become one or more test cases.

Story:

```text
As a visitor,

I want to register.
```

Test cases:

- Valid email → Success
    
- Duplicate email → Error
    
- Invalid email → Error
    
- Weak password → Error
    
- Missing fields → Error
    

This makes testing more structured.

# 13. Common Mistakes

## Mistake 1

Writing technical stories.

Wrong:

```text
As a developer,

I want Express middleware.
```

User stories should describe user value, not implementation details.

---

## Mistake 2

Missing the benefit.

Bad:

```text
As a user,

I want dark mode.
```

Better:

```text
As a user,

I want dark mode,

So that I can comfortably read at night.
```

---

## Mistake 3

Making stories too large.

If a story cannot be completed in a reasonable amount of work, split it into smaller stories.

---

## Mistake 4

Writing stories without understanding the user.

Always create personas first.

# Interview Questions

### Q1. What is a user story?

**Answer:**

A user story is a short, user-focused description of a feature that explains who wants it, what they want, and why they want it.

---

### Q2. Why are user stories important?

**Answer:**

They help developers understand user needs, prioritize features, design APIs and databases, define business rules, and create test cases.

---

### Q3. What is the standard format of a user story?

**Answer:**

```text
As a <user>,

I want <goal>,

So that <benefit>.
```

---

### Q4. What is an Epic?

**Answer:**

An Epic is a large user story that is too broad to implement in one iteration. It is broken down into smaller, manageable user stories.

# Key Takeaways

- User stories describe features from the **user's perspective**.
    
- The **"So that..."** part explains the business value.
    
- One user story can influence APIs, database design, business rules, and testing.
    
- Large stories (Epics) should be divided into smaller stories.
    
- User stories bridge the gap between business requirements and technical implementation.

# Practice Exercise

Choose one application:

- Blog Platform
    
- URL Shortener
    
- Todo App
    
- Student Attendance System
    
- E-commerce Store
    

Write:

1. **15 user stories** covering different user roles.
    
2. Identify **3 Epics** and break each into **4–6 smaller user stories**.
    
3. For **5 user stories**, identify:
    
    - Required API(s)
        
    - Database entity/entity changes
        
    - Business rules
        
    - Test cases
        
4. Mark each story as **Must Have**, **Should Have**, or **Could Have** (MoSCoW prioritization).
