> **Goal:** Learn how to convert business needs and user stories into clear, detailed system capabilities that define **what the backend must do**.

By the end of this module, you should be able to:

- Understand what functional requirements are.

# 1. What are Functional Requirements?

A **Functional Requirement (FR)** describes **what the system must do**.

It defines the behavior and capabilities of the application.

Think of it as a contract:

> **"The system shall..."**

Examples:

- The system shall allow users to register.
    
- The system shall authenticate users.
    
- The system shall allow authors to publish blog posts.
    
- The system shall allow readers to search articles.
    

Functional requirements describe **features**, not implementation.

---

## Simple Definition

```text
Business Goal

↓

User Story

↓

Functional Requirement

↓

API

↓

Backend Code
```

Functional requirements connect business needs to implementation.

---

# 2. User Story vs Functional Requirement

Suppose we have this user story.

```text
As a reader,

I want to search blog posts,

So that I can quickly find articles.
```

Functional Requirement:

```text
The system shall allow users
to search blog posts
using keywords.
```

Notice the difference.

|User Story|Functional Requirement|
|---|---|
|User perspective|System perspective|
|Focuses on user goal|Focuses on system behavior|
|Simple language|More precise and measurable|

---

# 3. Characteristics of Good Functional Requirements

A good functional requirement should be:

- Clear
    
- Specific
    
- Testable
    
- Complete
    
- Unambiguous
    
- Consistent
    

Bad Example:

```text
The system should be user-friendly.
```

This is vague.

Good Example:

```text
The system shall allow users
to reset their password
using a registered email address.
```

Anyone can understand exactly what the system must do.

---

# 4. Functional Requirement Template

A common template is:

```text
The system shall
<action>

when

<condition>

so that

<expected outcome>.
```

Example:

```text
The system shall send
an email verification link

when

a new user registers

so that

only verified users can log in.
```

---

# 5. Organizing Functional Requirements

Instead of writing random requirements, organize them into modules.

Example:

```text
Authentication

↓

Posts

↓

Comments

↓

Likes

↓

Notifications

↓

Administration
```

Each module contains related requirements.

# 7. Functional Requirements Drive Backend Design

Consider this requirement.

```text
The system shall allow
authors to save drafts.
```

What does this imply?

Database:

```text
posts

status

draft
```

API:

```http
POST /posts

PATCH /posts/:id
```

Business Rule:

```text
Only the owner
can edit a draft.
```

Validation:

```text
Content can be empty
while saving a draft.
```

One requirement influences multiple parts of the backend.

---

# 10. Functional Requirements Reveal Business Rules

Requirement:

```text
The system shall allow
users to like posts.
```

Business Rules:

- Only logged-in users can like.
    
- One user can like a post only once.
    
- Deleted posts cannot receive likes.
    
- Users may remove their likes.
    

Notice that requirements often uncover rules that need separate documentation.

---

# 11. Functional Requirements and Validation

Requirement:

```text
The system shall allow
users to register.
```

Validation Rules:

- Email must be unique.
    
- Password must meet minimum length.
    
- Name cannot be empty.
    
- Email format must be valid.
    

These validations become part of the backend logic.

---

# 12. Functional Requirements Help Testing

Requirement:

```text
The system shall allow
users to log in.
```

Test Cases:

- Correct email + password → Success
    
- Wrong password → Error
    
- Unknown email → Error
    
- Inactive account → Error
    
- Empty password → Error
    

Every functional requirement should have corresponding tests.

---

# 13. Traceability

Professional teams often maintain **traceability** to ensure every requirement is implemented and tested.

Example:

|User Story|Functional Requirement|API|Test Case|
|---|---|---|---|
|Register account|FR-1|`POST /auth/register`|Registration tests|
|Login|FR-2|`POST /auth/login`|Login tests|
|Save draft|FR-9|`PATCH /posts/:id`|Draft tests|
|Search posts|FR-17|`GET /posts?search=`|Search tests|

This helps teams track progress and avoid missing functionality.

# 14. Common Mistakes

## Mistake 1

Writing implementation details.

Wrong:

```text
The system shall use MongoDB.
```

This is a technical decision, not a functional requirement.

Correct:

```text
The system shall store user profiles.
```

---

## Mistake 2

Combining multiple requirements.

Wrong:

```text
The system shall register,
log in,
reset password,
and verify email.
```

Split them into separate requirements.

---

## Mistake 3

Writing vague requirements.

Wrong:

```text
The system shall be secure.
```

Correct:

```text
The system shall require authentication before allowing users to create posts.
```

---

## Mistake 4

Ignoring error scenarios.

Good requirements should also consider failures.

Example:

```text
The system shall display an appropriate error
when a duplicate email is used during registration.
```

# Interview Questions

### Q1. What is a functional requirement?

**Answer:**

A functional requirement describes what the system must do. It defines the features and behaviors that the software should provide to meet user and business needs.

---

### Q2. How is a functional requirement different from a user story?

**Answer:**

A user story describes a feature from the user's perspective, while a functional requirement describes the system's behavior in a precise and testable way.

---

### Q3. Why should functional requirements be testable?

**Answer:**

Testable requirements allow QA engineers and developers to verify whether the feature works as expected and meets the defined behavior.

---

### Q4. Can one functional requirement affect multiple backend components?

**Answer:**

Yes. A single functional requirement can influence API design, database schema, business rules, validation logic, authorization, and test cases.

# Key Takeaways

- Functional requirements describe **what the system must do**, not **how it is built**.
    
- Write requirements that are clear, specific, and testable.
    
- Organize requirements into functional modules such as Authentication, Posts, and Comments.
    
- Every functional requirement can influence APIs, data models, validation, authorization, and testing.
    
- Maintaining traceability between user stories, requirements, APIs, and tests helps build reliable software.
