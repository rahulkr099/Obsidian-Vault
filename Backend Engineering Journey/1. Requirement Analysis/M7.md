# Backend Engineering — Requirements Analysis Notes

# Module 7 — Non-Functional Requirements (NFRs)

> **Goal:** Learn how to define **how well** a backend system should work. Non-Functional Requirements determine the quality, reliability, security, scalability, and maintainability of your application in production.

---

# Learning Objectives

By the end of this module, you should be able to:

- Understand what Non-Functional Requirements (NFRs) are.
    
- Differentiate NFRs from Functional Requirements.
    
- Identify different categories of NFRs.
    
- Write measurable and testable NFRs.
    
- Understand how NFRs influence architecture and technology choices.
    

---

# 1. What are Non-Functional Requirements?

A **Non-Functional Requirement (NFR)** defines **how well the system should perform**, rather than **what it should do**.

Think of it like this:

Functional Requirement:

```text
The system shall allow users to log in.
```

Non-Functional Requirement:

```text
The login request shall complete within 2 seconds.
```

Both are important:

- Functional Requirements define **features**.
    
- Non-Functional Requirements define **quality**.
    

---

# 2. Functional vs Non-Functional Requirements

|Functional Requirement|Non-Functional Requirement|
|---|---|
|What the system does|How well it does it|
|Defines features|Defines quality|
|Login|Login within 2 seconds|
|Create Post|Save within 500 ms|
|Search Blogs|Search results in under 1 second|
|Upload Image|Maximum file size 10 MB|

Remember:

> **FR = Features**
> 
> **NFR = Quality**

---

# 3. Why are NFRs Important?

Many beginner developers only focus on making features work.

Imagine a blog application where:

- Login works.
    
- Search works.
    
- Comments work.
    

But:

- Every request takes 15 seconds.
    
- Passwords are stored in plain text.
    
- The server crashes when 100 users visit.
    
- Data is lost after a restart.
    

Technically, the features work—but the application is not usable.

NFRs ensure the application performs well in real-world conditions.

# 5. Performance

Performance measures **how fast** the system responds.

Examples:

```text
Homepage loads within 2 seconds.

↓

Login completes within 1 second.

↓

Search results returned within 500 ms.

↓

API response time below 300 ms.
```

### Backend Implications

To achieve good performance, you may need:

- Database indexing
    
- Caching
    
- Efficient queries
    
- Pagination
    
- Compression
    

---

# 6. Scalability

Scalability measures the system's ability to handle growth.

Example:

Today:

```text
100 users
```

Tomorrow:

```text
1,000 users
```

Next Year:

```text
1,000,000 users
```

The system should continue working efficiently as demand increases.

### Backend Implications

You might use:

- Load balancing
    
- Horizontal scaling
    
- Redis caching
    
- Database replication
    
- CDN
    

---

# 7. Availability

Availability measures how often the system is accessible.

Example:

```text
99.9% uptime
```

This means users should almost always be able to access the application.

### Backend Techniques

- Multiple servers
    
- Health checks
    
- Automatic restarts
    
- Cloud deployment
    
- Failover systems
    

---

# 8. Reliability

Reliability means the system consistently performs correctly.

Example:

If a user publishes a blog post:

```text
Publish

↓

Save Successfully

↓

Never lose data
```

The same operation should produce the expected result every time.

### Backend Considerations

- Database transactions
    
- Proper error handling
    
- Data backups
    
- Retry mechanisms
    

---

# 9. Security

Security protects the system and user data.

Examples:

```text
Passwords must be hashed.

↓

HTTPS required.

↓

JWT authentication.

↓

Role-based authorization.

↓

Input validation.

↓

Rate limiting.
```

### Backend Technologies

- bcrypt or Argon2
    
- Helmet
    
- CORS
    
- JWT
    
- CSRF protection (where applicable)
    
- SQL/NoSQL injection prevention
    

---

# 10. Maintainability

Maintainability measures how easy the system is to update.

Good backend projects have:

```text
Controllers

↓

Services

↓

Repositories

↓

Utilities

↓

Tests
```

Benefits:

- Easier debugging
    
- Easier feature additions
    
- Easier onboarding of new developers
    

---

Users experience a smoother application.

# 15. Writing Good NFRs

Bad:

```text
The application should be fast.
```

Good:

```text
95% of API requests
shall complete within 300 ms.
```

Bad:

```text
The system should be secure.
```

Good:

```text
All passwords shall be hashed
using Argon2 or bcrypt.
```

Good NFRs are **measurable**.

# 16. NFRs Influence Architecture

Imagine this requirement:

```text

```

Would a single server be enough?

Probably not.

Possible architecture:

```text

↓

Load Balancer

↓

Backend Servers

↓

Redis

↓

```

A single NFR can completely change the system design.

# 20. Common Mistakes

## Mistake 1

Ignoring NFRs completely.

Features alone don't create good software.

---

## Mistake 2

Writing vague requirements.

Wrong:

```text
Fast
```

Correct:

```text
95% of requests
under 300 ms.
```

---

## Mistake 3

Thinking security is optional.

Security is a requirement from day one.

---

## Mistake 4

Optimizing too early.

Design for expected growth, but don't over-engineer for unrealistic scale.

---

## Mistake 5

Forgetting monitoring.

Without logs and metrics, production issues become difficult to diagnose.

# 21. Quality Attribute Scenarios

A useful way to write NFRs is:

**Source → Event → Environment → Artifact → Response → Response Measure**

Example:

```text
Source:
User

↓

Event:
Search request

↓

Environment:
Normal operation

↓

Artifact:
Search API

↓

Response:
Return matching posts

↓

Response Measure:
Within 500 ms
```

This format makes NFRs very precise.

# Interview Questions

### Q1. What is a Non-Functional Requirement?

**Answer:**

A Non-Functional Requirement defines how well a system should perform. It describes quality attributes such as performance, scalability, security, availability, reliability, and maintainability rather than specific features.

---

### Q2. What is the difference between Functional and Non-Functional Requirements?

**Answer:**

Functional requirements describe **what** the system should do, while non-functional requirements describe **how well** the system should perform those functions.

---

### Q3. Give examples of common Non-Functional Requirements.

**Answer:**

Examples include:

- API response time under 300 ms
    
- Password hashing with bcrypt or Argon2
    
- 99.9% uptime
    
- Support for one million users
    
- Structured logging and monitoring
    
- Automated backups
    

---

### Q4. Why are NFRs important for backend engineers?

**Answer:**

NFRs influence architecture, infrastructure, API design, database optimization, deployment strategies, and operational practices. They ensure that a backend system remains fast, secure, reliable, and maintainable in production.

# Key Takeaways

- Non-Functional Requirements define the **quality** of the system.
    
- Good NFRs are **specific, measurable, and testable**.
    
- Performance, scalability, security, reliability, and maintainability are essential for production-ready backend systems.
    
- NFRs directly influence architecture, infrastructure, APIs, and database design.
    
- A backend engineer should think beyond "Does it work?" and ask, "Will it continue to work well under real-world conditions?"
