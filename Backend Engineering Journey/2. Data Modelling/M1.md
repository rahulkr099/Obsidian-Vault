# Module 1 — Understanding the Problem

> **Goal:** Learn to understand the business before thinking about databases, APIs, or code.

---

# Why This Module Matters

Many beginners hear:

> "Build a Blog App"

and immediately create:

```text
User
Post
Comment
```

This is called **solution-first thinking**.

Professional backend engineers think differently.

They ask:

- What problem are we solving?
    
- Who will use this system?
    
- What actions will users perform?
    
- What business rules exist?
    

The database is **a result of understanding the problem**, not the starting point.

---

# The Backend Engineer's First Job

Your first responsibility is **not writing code**.

It is understanding the business domain.

Imagine someone says:

> "We need a food delivery application."

Before thinking about Express or MongoDB, you should ask questions.

Examples:

- Who can order food?
    
- Can restaurants reject orders?
    
- Can users cancel orders?
    
- Can delivery partners see all orders?
    
- Can customers schedule deliveries?
    
- Is payment online or cash?
    
- Are refunds supported?
    

Notice that none of these questions mention databases.

---

# Step 1 — Read the Requirements Carefully

Requirements describe what the application must do.

Example:

```text
Users can register.

Users can login.

Users can write blogs.

Users can edit blogs.

Users can publish blogs.

Users can comment.

Users can follow authors.

Admins can remove posts.
```

Do not skim.

Read multiple times.

Highlight important words.

Example:

```text
publish
edit
comment
follow
admin
```

These words usually become features later.

---

# Step 2 — Separate Functional and Non-Functional Requirements

## Functional Requirements

These describe **what the application does.**

Example:

```text
Create account

Login

Create post

Edit profile

Like post

Comment
```

---

## Non-Functional Requirements

These describe **how the application should behave.**

Examples:

```text
Fast

Secure

Scalable

Reliable

Available

Responsive
```

Example:

```text
Search results should appear within 500ms.
```

or

```text
Passwords must be encrypted.
```

---

# Step 3 — Identify the Actors

Actors are the people or systems interacting with your application.

Example Blog App:

```text
Visitor

Registered User

Admin
```

Example E-commerce:

```text
Customer

Seller

Admin

Payment Gateway

Delivery Partner
```

Every actor has different permissions.

---

# Step 4 — Identify Business Goals

Ask:

> Why does this application exist?

Example:

Blog App

Goal:

```text
Allow people to publish articles.
```

Ride Sharing

Goal:

```text
Connect riders with drivers.
```

Todo App

Goal:

```text
Help users manage tasks.
```

Knowing the goal helps you make better design decisions.

---

# Step 5 — Highlight Business Rules

Business rules are conditions that must always be true.

Examples:

```text
Only logged-in users can create posts.
```

```text
Only authors can edit their own posts.
```

```text
Only admins can delete users.
```

```text
A user cannot like the same post twice.
```

These rules later become:

- validations
    
- authorization checks
    
- database constraints
    

---

# Step 6 — Find Important Nouns and Verbs

This is a simple but powerful technique.

Requirements:

```text
Users publish blog posts.

Users comment.

Users like posts.
```

Nouns:

```text
User

Post

Comment

Like
```

These often become entities.

Verbs:

```text
publish

comment

like
```

These usually become operations or APIs.

---

# Step 7 — Clarify Ambiguous Requirements

Never assume.

Suppose the requirement says:

```text
Users can edit posts.
```

Ask:

```text
Can they edit after publishing?

Can admins edit any post?

Is edit history required?

Should readers know the post was edited?
```

Small questions now prevent major redesign later.

---

# Step 8 — Identify Constraints

Some requirements limit how the system behaves.

Examples:

```text
Maximum image size

Maximum title length

Maximum post length

Password policy

Username rules
```

Example:

```text
Username

3–20 characters

Only letters and numbers
```

These become validation rules later.

---

# Step 9 — Write Assumptions

Sometimes requirements are incomplete.

Instead of guessing silently, document your assumptions.

Example:

```text
Assumption:

Posts are public by default.
```

```text
Assumption:

Only logged-in users can comment.
```

```text
Assumption:

Users have only one profile.
```

Clear assumptions reduce misunderstandings.

---

# Step 10 — Create a Requirement Checklist

Convert the requirements into a checklist.

Example:

```text

☐ Create Post

☐ Update Post

☐ Delete Post

☐ Comment
```

This checklist will guide development later.

# Common Beginner Mistakes

### Mistake 1

Creating schemas immediately.

Wrong:

```text
User

Post

Comment
```

Correct:

```text
Understand requirements first.
```

---

### Mistake 2

Ignoring business rules.

Requirement:

```text
One user can like a post only once.
```

If ignored, you'll later need complex fixes.

---

### Mistake 3

Not asking questions.

If something is unclear:

Ask.

Never assume.

---

### Mistake 4

Thinking only about CRUD.

Real applications include:

- permissions
    
- workflows
    
- approvals
    
- notifications
    
- analytics
    
- auditing
    

Requirements should capture these too.

# Example Walkthrough

Suppose the requirement is:

```text
Build a Library Management System.
```

After analysis, you might identify:

Actors:

```text
Student

Librarian

Admin
```

Features:

```text
Issue book

Return book

Reserve book

Search books

Pay fine
```

Business Rules:

```text
A student can borrow at most 5 books.

Books can be reserved only if unavailable.

Fine applies after due date.

Only librarians can issue books.
```

Already, you have a much clearer understanding before writing any code.

# Real-World Tips

- Read the requirements at least twice.
    
- Underline nouns (potential entities).
    
- Circle verbs (potential actions).
    
- Write down every business rule.
    
- List all actors and their permissions.
    
- Record assumptions explicitly.
    
- If anything is unclear, ask questions before designing.

# Mini Exercise

Analyze the requirements for a simple **Expense Tracker** application.

Requirements:

```text
Users can register and log in.
Users can record income and expenses.
Users can categorize transactions.
Users can edit or delete their own transactions.
Users can view monthly reports.
Admins can manage categories.
```

Try to identify:

1. Functional requirements.
    
2. Non-functional requirements (assume reasonable ones).
    
3. Actors.
    
4. Business goal.
    
5. Business rules.
    
6. Important nouns.
    
7. Important verbs.
    
8. Any assumptions you would make.
    

Don't think about the database yet. Focus only on understanding the problem. This habit will make every later module—queries, entities, relationships, schema design, and indexing—much easier.
