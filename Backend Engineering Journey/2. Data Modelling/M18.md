# Module 18 — Design Reviews & Trade-offs

> **Goal:** Learn how professional backend engineers review a system design, identify weaknesses, compare alternatives, justify trade-offs, and explain _why_ they made certain design decisions.

---

# Why This Module Matters

Most backend developers can build an application.

Professional backend engineers can also answer:

- **Why did you choose MongoDB instead of PostgreSQL?**
    
- **Why did you embed this document instead of referencing it?**
    
- **Why did you denormalize likesCount?**
    
- **Why did you choose cursor pagination instead of page numbers?**
    
- **Why did you create this compound index?**
    

In interviews and design reviews, these questions matter as much as the implementation.

# What Is a Design Review?

A design review is a structured discussion where engineers evaluate whether a proposed design is:

- Correct
    
- Maintainable
    
- Performant
    
- Secure
    
- Scalable
    
- Easy to understand
    

The goal is **not** to prove someone wrong.

The goal is to improve the system.

---

# The Engineering Mindset

Instead of asking:

> "Is this design perfect?"

Ask:

> **"What are the trade-offs of this design?"**

Every design has advantages and disadvantages.

There is no perfect solution.

---

# What Is a Trade-off?

A trade-off means:

> **You gain one benefit by accepting another cost.**

Example:

Denormalization.

Benefit:

```text
Fast reads
```

Cost:

```text
Duplicate data
```

Neither choice is always correct.

It depends on the application's needs.

---

# Step 1 — Review Requirements

Start by asking:

```text
Does this design satisfy every requirement?
```

Example:

Requirement:

```text
Users can follow each other.
```

Your design:

```text
User

Post

Comment
```

Problem:

No Follow entity.

Requirement not satisfied.

---

# Step 2 — Review Queries

Ask:

```text
Can every important query be executed efficiently?
```

Example:

Homepage:

```text
Latest Posts
```

Index:

```text
(status, publishedAt)
```

Good.

---

Search:

```text
Search by title.
```

No text index.

Potential issue.

---

# Step 3 — Review Relationships

Example:

```text
Post

↓

Comments
```

Question:

Should comments be embedded?

If comments can grow to hundreds of thousands,

embedding is a poor choice.

Reference instead.

---

# Step 4 — Review Normalization Decisions

Question:

Why is:

```text
likesCount
```

stored inside Post?

Answer:

To avoid running:

```javascript
count()
```

for every page load.

Trade-off:

```text
Faster reads

↓

Slightly more complex writes
```

---

# Step 5 — Review Constraints

Ask:

```text
Can duplicate likes exist?
```

If yes,

need:

```text
(UserId, PostId)
```

compound unique constraint.

---

# Step 6 — Review Indexes

Question:

Why index:

```text
email
```

Answer:

Login query.

---

Question:

Why index:

```text
bio
```

No queries use it.

Remove the index.

Indexes should always justify themselves.

---

# Step 7 — Review Growth

Suppose:

Today:

```text
100 users
```

Tomorrow:

```text
5 million users
```

Ask:

- Which collections grow fastest?
    
- Which APIs become slower?
    
- Which indexes become larger?
    
- Which queries need caching?
    

---

# Step 8 — Review Security

Question:

Does:

```http
GET /users/me
```

return:

```text
password
```

If yes,

major security issue.

---

Question:

Can users update:

```text
role
```

If yes,

critical vulnerability.

---

# Step 9 — Review API Design

Question:

Why:

```http
GET /posts?status=published
```

instead of:

```http
GET /publishedPosts
```

Answer:

Filtering scales better.

Future:

```http
GET /posts?
status=published

&author=rahul

&sort=-likes
```

One endpoint handles many cases.

---

# Step 10 — Review Maintainability

Suppose:

Business wants:

```text
Scheduled publishing.
```

Current schema:

```text
status
```

Need:

```text
publishAt
```

Easy addition.

Good design.

---

Suppose:

Need:

```text
Multiple authors.
```

Current schema:

```text
authorId
```

Can evolve to:

```javascript
authors:[]
```

Minimal changes.

# Example Design Review — Blog Application

Entities:

```text
User

Post

Comment

Like
```

---

## Question 1

Why separate Comment collection?

Answer:

Unlimited growth.

Independent pagination.

Better performance.

---

## Question 2

Why:

```text
likesCount
```

inside Post?

Answer:

Homepage loads quickly.

Avoid expensive count queries.

---

## Question 3

Why:

```text
slug
```

instead of:

```text
_id
```

in URLs?

Better:

- SEO
    
- Readability
    
- Sharing
    

---

## Question 4

Why:

```text
(status, publishedAt)
```

compound index?

Because homepage filters by:

```text
status
```

and sorts by:

```text
publishedAt
```

---

## Question 5

Why soft delete?

Users can restore accidentally deleted posts.

Admin retains moderation history.

# Comparing Alternatives

Professional engineers compare multiple solutions.

Example:

Comments.

---

## Option A

Embed.

Advantages:

- One query.
    
- Simpler.
    

Disadvantages:

- Huge documents.
    
- Difficult pagination.
    

---

## Option B

Separate collection.

Advantages:

- Unlimited growth.
    
- Easy pagination.
    
- Better indexing.
    

Disadvantages:

- Additional query.
    

Conclusion:

Choose Option B.

# Another Example

Pagination.

---

## Offset Pagination

```http
?page=20
```

Advantages:

Simple.

Disadvantages:

Slower for large datasets.

---

## Cursor Pagination

```http
?cursor=abc123
```

Advantages:

Faster.

Better consistency.

Disadvantages:

Slightly more complex.

Trade-off depends on scale.

---

# Another Example

MongoDB vs PostgreSQL

MongoDB

Advantages:

- Flexible schema
    
- Easy document modeling
    
- Great for nested data
    

Disadvantages:

- No native foreign keys
    
- Complex joins are harder
    

---

PostgreSQL

Advantages:

- Strong consistency
    
- Excellent joins
    
- Rich SQL features
    

Disadvantages:

- Schema changes require more planning
    

Choose based on project requirements, not personal preference.

---

# Another Example

JWT vs Session Authentication

JWT

Advantages:

- Stateless
    
- Good for APIs
    
- Scales horizontally
    

Disadvantages:

- Token revocation is harder
    

---

Sessions

Advantages:

- Easy logout
    
- Server-controlled
    

Disadvantages:

- Requires session storage
    

Neither is universally better.

# Design Review Questions

When reviewing any backend system, ask:

### Requirements

```text
Does it solve every business requirement?
```

---

### Data Model

```text
Are entities correct?

Are relationships correct?

Can data grow safely?
```

---

### Validation

```text
Can invalid data enter the system?
```

---

### Constraints

```text
Can duplicate data exist?
```

---

### Performance

```text
Will common queries stay fast?
```

---

### Security

```text
Can users access data they shouldn't?
```

---

### Scalability

```text
Which parts will become bottlenecks?
```

---

### Maintainability

```text
Can future features be added easily?
```

# Common Interview Questions

## Why MongoDB?

Good answer:

```text
Flexible schema

Document model

Rapid development

Good fit for hierarchical data
```

Not:

```text
Because I like MongoDB.
```

---

## Why normalize?

Good answer:

```text
Reduce duplication

Improve consistency

Simplify updates
```

---

## Why denormalize?

Good answer:

```text
Improve read performance

Reduce expensive aggregation queries
```

---

## Why this index?

Good answer:

```text
Supports the homepage query.

Filters by status.

Sorts by publishedAt.
```

---

## Why soft delete?

Good answer:

```text
Recovery

Auditing

Business requirements
```

# Common Beginner Mistakes

## Mistake 1

Thinking every decision has one correct answer.

Most engineering decisions involve trade-offs.

---

## Mistake 2

Choosing technologies because they're popular.

Choose based on requirements.

---

## Mistake 3

Ignoring future changes.

Always ask:

> "How would this design evolve?"

---

## Mistake 4

Optimizing everything early.

Optimize real bottlenecks,

not imaginary ones.

---

## Mistake 5

Unable to explain decisions.

If you can't explain:

```text
Why?
```

you probably don't fully understand the design.

---

# Best Practices

- Review your design before writing code.
    
- Justify every important design decision.
    
- Compare alternative approaches.
    
- Understand the trade-offs of each choice.
    
- Design for maintainability, not just correctness.
    
- Use requirements—not trends—to guide architecture.
    
- Be ready to explain every schema, API, and index in an interview.
    

---

# Design Review Checklist

Before implementation, ask:

```text
✓ Are all requirements covered?

✓ Can every important query run efficiently?

✓ Are relationships appropriate?

✓ Are indexes justified?

✓ Are validation and constraints sufficient?

✓ Is security addressed?

✓ Can the system grow?

✓ Can future features be added easily?

✓ Can I explain every major design decision?
```

If you can confidently answer **yes** to each question, your design is likely ready for implementation.
