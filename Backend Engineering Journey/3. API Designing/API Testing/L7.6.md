# Lesson 7.6 — Mocking External Services

> **Goal:** Learn how professional backend engineers test applications that depend on third-party services without making real network calls.

---

# Learning Objectives

By the end of this lesson, you will understand:

- What mocking is
    
- Why external services should be mocked
    
- Which services should be mocked
    
- Different types of test doubles
    
- Where mocking fits into Unit, Integration, and E2E tests
    
- Best practices used by professional backend teams
    

---

# The Problem

Imagine your application looks like this:

```text
User

↓

Your API

↓

Stripe Payment API

↓

Gmail API

↓

Cloudinary

↓

Redis

↓

Google Maps API
```

Every request depends on external systems.

Now imagine running 500 automated tests.

Without mocking:

- 500 real payments
    
- 500 real emails
    
- 500 real image uploads
    

That would be expensive, slow, and unreliable.

---

# What is Mocking?

A **mock** is a fake version of a dependency.

Instead of calling the real service, your code interacts with something that behaves like the real service.

Example:

Real world:

```text
UserService

↓

Stripe API
```

Testing:

```text
UserService

↓

Fake Stripe API
```

Your application believes it is talking to Stripe, but it is actually talking to your fake implementation.

---

# Why Mock External Services?

Professional teams mock external services because:

- Tests become much faster
    
- Tests become predictable
    
- No internet dependency
    
- No API costs
    
- No accidental emails
    
- No accidental payments
    

---

# Real Example

Suppose registration sends a welcome email.

Production:

```text
POST /register

↓

Create User

↓

Send Email

↓

Return Success
```

Without mocking:

Every test sends an email.

Bad idea.

---

With mocking:

```text
POST /register

↓

Create User

↓

Pretend Email Sent

↓

Return Success
```

Now the test is fast and safe.

---

# Common Services to Mock

## Email Services

Examples:

- SendGrid
    
- Amazon SES
    
- Gmail API
    
- Mailgun
    

Instead of sending:

```text
Welcome Rahul!
```

Your mock simply records:

```text
sendEmail()

called once
```

---

## Payment Gateways

Examples:

- Stripe
    
- Razorpay
    
- PayPal
    

Never charge real money during tests.

Mock response:

```json
{
  "paymentId": "pay_test_123",
  "status": "success"
}
```

---

## Cloud Storage

Examples:

- Cloudinary
    
- AWS S3
    
- Firebase Storage
    

Instead of uploading a real image:

```text
profile.png
```

Return:

```text
https://fake-storage/profile.png
```

---

## SMS Services

Examples:

- Twilio
    
- MSG91
    

Instead of sending an OTP:

```text
654321
```

The mock simply stores:

```text
OTP generated

↓

654321
```

No SMS is actually sent.

---

## Maps APIs

Examples:

- Google Maps
    
- Mapbox
    

Instead of requesting live location:

Return:

```json
{
    "city": "Delhi"
}
```

Every test gets the same response.

---

## External REST APIs

Suppose:

```text
Weather API
```

Production:

```text
Temperature

↓

31°C
```

Tomorrow:

```text
28°C
```

Now your test fails unexpectedly.

Instead:

Mock:

```text
Always return

30°C
```

Your tests stay deterministic.

---

# What Should Be Mocked?

Generally, mock anything that is:

- Outside your application
    
- Slow
    
- Paid
    
- Unreliable
    
- Not under your control
    

Examples:

✅ Email

✅ Payment

✅ SMS

✅ Cloud Storage

✅ External APIs

---

# What Should NOT Be Mocked?

Inside your application:

```text
Controller

↓

Service

↓

Repository
```

These components should usually work together during integration tests.

Mocking everything defeats the purpose of integration testing.

---

# Types of Test Doubles

Professional testing literature uses several kinds of "fake" objects.

---

## Dummy

Used only to satisfy a parameter.

Example:

```text
User object

↓

Not actually used
```

---

## Stub

Returns predefined data.

Example:

```text
getUser()

↓

Always returns Rahul
```

Useful when you need predictable inputs.

---

## Fake

A simplified working implementation.

Example:

Instead of MongoDB:

```text
Use an in-memory list.
```

The fake behaves like a database but is much simpler.

---

## Spy

Records how a function was used.

Example:

```text
sendEmail()

↓

Called?

↓

How many times?

↓

With what arguments?
```

Very useful for verification.

---

## Mock

Defines expected interactions.

Example:

```text
Payment Service

↓

Should be called once

↓

With ₹500
```

If your code behaves differently, the test fails.

---

# Mocking in Unit Tests

Unit tests should mock almost every external dependency.

Example:

```text
UserService

↓

Mock Repository

↓

Mock Email Service

↓

Mock Logger
```

Now you're testing only the business logic.

---

# Mocking in Integration Tests

Integration tests usually keep:

```text
Controller

↓

Service

↓

Repository

↓

Test Database
```

But still mock:

```text
Stripe

Email

SMS

Cloudinary
```

This balances realism with speed.

---

# Mocking in E2E Tests

E2E tests use as many real components as possible.

However, external services are often replaced with:

- Sandbox environments
    
- Fake servers
    
- Test accounts
    

Example:

Stripe provides a test mode with fake credit cards.

This lets you test payment flows safely.

---

# Benefits of Mocking

## Faster Tests

Real API:

```text
800 ms
```

Mock:

```text
2 ms
```

Huge difference when running hundreds of tests.

---

## No Internet Needed

Tests work even if you're offline.

---

## Stable Results

External APIs change.

Mocks do not.

---

## Lower Cost

No:

- Email charges
    
- SMS charges
    
- Payment fees
    
- API usage costs
    

---

## Safe Testing

You never accidentally:

- Charge customers
    
- Send emails
    
- Upload files
    
- Delete cloud data

# Common Beginner Mistakes

❌ Mocking everything

Result:

You never test how your own components interact.

Instead:

Only mock external dependencies.

---

❌ Calling real payment APIs

Bad:

```text
Test

↓

Real Credit Card
```

Use sandbox environments or mocks.

---

❌ Ignoring failure scenarios

Mock failures too.

Example:

```text
Stripe Timeout

↓

Your API

↓

Returns 503
```

Your application should handle external failures gracefully.

---

❌ Returning unrealistic mock data

Bad:

```json
{
    "success": true
}
```

If the real API returns 20 fields, your mock should resemble that structure closely.

---

# Professional Example

Suppose your Todo application sends a Slack notification when a task is completed.

Architecture:

```text
TodoService

↓

Slack API
```

Unit Test:

```text
TodoService

↓

Mock Slack Service
```

Verify:

- Task marked as completed.
    
- Slack notification function called once.
    
- Correct message passed.
    

No real Slack message is sent.

---

# Best Practices

✅ Mock external services, not your business logic.

✅ Use realistic mock responses.

✅ Test both success and failure scenarios.

✅ Keep mocks simple and maintainable.

✅ Prefer official sandbox environments when available.

✅ Make tests deterministic.

# Real Backend Example (MERN)

Suppose your project has this flow:

```text
POST /users/register

↓

Validate Input

↓

Hash Password

↓

Save User (MongoDB)

↓

Upload Avatar (Cloudinary)

↓

Send Welcome Email (SendGrid)

↓

Return Response
```

### Unit Test

- Mock MongoDB repository
    
- Mock Cloudinary
    
- Mock SendGrid
    

Focus only on the registration logic.

---

### Integration Test

- Use a real **test MongoDB**
    
- Mock Cloudinary
    
- Mock SendGrid
    

Verify the controller, service, repository, and database work together.

---

### E2E Test

- Use the real application
    
- Use a test database
    
- Use Cloudinary test configuration (or a fake storage service)
    
- Use SendGrid sandbox or a fake mail server
    

Verify the complete user registration journey.

---

# Key Takeaways

- Mocking replaces external dependencies with controlled, fake implementations.
    
- Mock external systems like payment gateways, email providers, cloud storage, SMS services, and third-party APIs.
    
- Unit tests rely heavily on mocks, while integration tests use real application components but still mock external services.
    
- E2E tests aim to be as realistic as possible and often use sandbox environments for third-party integrations.
    
- Good mocks make tests fast, predictable, safe, and inexpensive.
