# What is an API?

**API** stands for **Application Programming Interface**.

An API is a **contract** that defines how two software systems communicate with each other.

Think of it as a **messenger**:

```
Client
   │
   │ Request
   ▼
API
   │
   ▼
Server

Server
   │
   │ Response
   ▼
API
   │
   ▼
Client
```

The client never talks directly to the database.

Instead:

```
Frontend
     ↓
API
     ↓
Backend
     ↓
Database
```

---

# Real-Life Analogy

Imagine a restaurant.

```
Customer
    │
    ▼
Waiter (API)
    │
    ▼
Kitchen
```

The customer:

- doesn't enter the kitchen
    
- doesn't cook food
    
- doesn't know how food is prepared
    

The waiter:

- takes the order
    
- communicates with the kitchen
    
- brings the food back
    

The waiter is the API.

# Example

You open Instagram.

```
App
 ↓
GET /posts
 ↓
Server
 ↓
Database
```

The server responds:

```json
[
  {
    "id": 1,
    "caption": "Hello"
  },
  {
    "id": 2,
    "caption": "Vacation"
  }

The app displays the posts.

---

# Without APIs

Imagine if a frontend could directly access the database.

```
Frontend
      │
      ▼
Database
```

Problems:

- Anyone could delete data.
    
- Database structure becomes exposed.
    
- No validation.
    
- No security.
    
- Hard to change the database later.
    
- Business rules cannot be enforced.
    

---

# With APIs

```
Frontend
     │
     ▼
API
     │
     ▼
Database
```

Benefits:

- Security
    
- Validation
    
- Authentication
    
- Authorization
    
- Business logic
    
- Consistent responses
    
- Easier maintenance

# Types of APIs

### 1. Public APIs

Available for everyone.

Examples:

- GitHub API
    
- OpenWeather API
    
- Stripe Public APIs
    

---

### 2. Private APIs

Used only within an organization.

Example:

```
Frontend
      ↓
Company Backend API
```

Most company projects use private APIs.

---

### 3. Partner APIs

Shared with trusted partners.

Example:

A payment gateway provides APIs to e-commerce companies.

---

### 4. Internal APIs (Microservices)

Used between services.

```
User Service

Order Service

Payment Service

Notification Service
```

These services communicate using APIs.

---

Forms

Images

Text
```

---

### API

Made for programs.

```
JSON

HTTP

XML

Protocol Buffers
```

Humans don't usually interact with APIs directly.

# Why Not Give the Database to Everyone?

Imagine this:

```
DELETE FROM users;
```

If everyone had database access, anyone could accidentally or intentionally delete all users.

APIs protect the database by allowing only approved operations.

# API Responsibilities

A well-designed API should:

- Receive requests.
    
- Validate data.
    
- Authenticate users.
    
- Check permissions.
    
- Execute business logic.
    
- Access the database.
    
- Return structured responses.
    
- Handle errors gracefully.

# Key Terms

|Term|Meaning|
|---|---|

|API|Communication layer|

|Response|Data returned by the server|

# Common Misconceptions

### ❌ API = Database

Wrong.

An API interacts with the database but is not the database itself.

---

### ❌ API = Backend

Wrong.

The backend includes:

- Controllers
    
- Services
    
- Repositories
    
- Database
    
- Authentication
    
- Validation
    
- Logging
    
- Background jobs
    
- APIs
    

The API is one interface of the backend.

---

### ❌ API Only Returns Data

Wrong.

An API can:

- Create data
    
- Update data
    
- Delete data
    
- Trigger actions (e.g., send emails, process payments)
    
- Start workflows
    

---

# Best Practices Introduced

- Treat the API as a **contract** between client and server.
    
- Never expose the database directly.
    
- Keep business logic inside the backend, not the frontend.
    
- Return structured, predictable responses.
    
- Design APIs with security and maintainability in mind from the beginning.
