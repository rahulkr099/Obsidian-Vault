# What is API-First Thinking?

**API-First Thinking** means:

> **Design the API contract before writing backend code.**

Instead of starting with:

```
Express Routes
↓
Controllers
↓
Database
```

Professional teams often start with:

```
Business Requirements
        ↓
Resources
        ↓
API Design
        ↓
API Documentation
        ↓
Frontend & Backend Development
```

The API becomes the **blueprint** that both frontend and backend teams follow.

---

# Why API-First?

Imagine your team is building a **Blog Application**.

### Without API-First

The frontend developer asks:

> "How do I fetch posts?"

Backend developer replies:

> "I'll create something."

A day later:

```http
GET /blog
```

Frontend starts using it.

The next day, backend changes it to:

```http
GET /posts
```

The frontend breaks.

Another day:

Response changes from:

```json
{
  "posts": [...]
}
```

to:

```json
[
  ...
]
```

The frontend breaks again.

This happens because there was **no agreed contract**.

---

# With API-First

Before writing any code, the team agrees on:

```http
GET /posts
```

Request:

```
No body
```

Response:

```json
{
    "success": true,
    "data": [
        {
            "id": 1,
            "title": "Learning APIs"
        }
    ]
}
```

Now:

- Frontend knows what to expect.
    
- Backend knows what to implement.
    
- QA knows what to test.
    
- Documentation is ready from day one.
    

Everyone works from the same specification.

---

# API Contract

An **API Contract** is an agreement between the client and the server.

It defines:

- Endpoint
    
- HTTP Method
    
- Request format
    
- Response format
    
- Status codes
    
- Error responses
    
- Authentication requirements
    
- Validation rules
    

Example:

```
Endpoint:
GET /posts
```

Method:

```
GET
```

Success Response:

```json
{
    "success": true,
    "data": []
}
```

Possible Errors:

```
401 Unauthorized

500 Internal Server Error
```

Everyone agrees not to change this contract without discussion.

# Code-First vs API-First

## Code-First

Typical beginner workflow:

```
Requirements
      ↓
Express Route
      ↓
Controller
      ↓
Database
      ↓
Frontend adapts
```

Problems:

- APIs change frequently.
    
- Frontend breaks often.
    
- Documentation is outdated.
    
- Difficult to scale.
    
- Inconsistent response formats.
    

---

## API-First

Professional workflow:

```
Requirements
        ↓
API Contract
        ↓
Frontend Development
        ↓
Backend Development
        ↓
Testing
```

Benefits:

- Stable APIs.
    
- Independent frontend/backend work.
    
- Better documentation.
    
- Easier testing.
    
- Predictable responses.
    

---

# Example: User Login

Requirement:

> Users should log in using email and password.

Instead of directly coding:

```javascript
router.post("/login")
```

Design the contract first.

### Endpoint

```http
POST /auth/login
```

Request Body

```json
{
    "email": "rahul@example.com",
    "password": "mypassword"
}
```

Success Response

```json
{
    "success": true,
    "message": "Login successful",
    "data": {
        "accessToken": "...",
        "user": {
            "id": 1,
            "name": "Rahul"
        }
    }
}
```

Possible Errors

```
400 Invalid Input

401 Invalid Credentials

500 Server Error
```

Only after agreeing on this contract should implementation begin.

# API Mocking

One major advantage of API-First is that the frontend doesn't have to wait for the backend.

Example:

Backend isn't finished yet.

The frontend can temporarily use:

```json
{
    "success": true,
    "data": [
        {
            "id": 1,
            "title": "Mock Post"
        }
    ]
}
```

Later, when the real backend is ready, the frontend replaces the mock with actual API calls—without changing the UI logic.

# Why API Changes Are Expensive

Suppose the frontend expects:

```json
{
    "title": "API Design"
}
```

But the backend changes it to:

```json
{
    "postTitle": "API Design"
}
```

Every frontend component using `title` must now be updated.

This can introduce bugs and waste development time.

**Rule:** Once an API is public or shared, avoid breaking changes unless absolutely necessary.

# API as a Product

Professional developers often think of APIs as products.

Just as a good product should be:

- Easy to use
    
- Consistent
    
- Reliable
    
- Well documented
    
- Stable
    

A good API should have the same qualities.

---

# Real-World Example

Imagine an e-commerce app.

The mobile app, website, admin dashboard, and third-party partners all use the same backend.

```
            Mobile App
                 │
Website ─────────┼──────── API
                 │
Admin Dashboard  │
                 │
Third-Party Apps
```

If the API contract changes unexpectedly, **every client application may break**.

That's why stable API design is so important.

---

# API Design Before Database?

A common question is:

> "Should I design the database first or the API first?"

The answer depends on the project stage.

A practical sequence is:

```
Business Requirements
        ↓
Identify Resources
        ↓
High-Level API Design
        ↓
Data Modeling
        ↓
Refine API
        ↓
Implementation
```

Notice that **API Design and Data Modeling evolve together**. One influences the other.

---

# Best Practices

- Design APIs before implementation.
    
- Treat the API contract as a shared agreement.
    
- Keep response structures consistent.
    
- Avoid unnecessary breaking changes.
    
- Document APIs early.
    
- Review API designs with the team before coding.
    

---

# Common Mistakes

❌ Writing Express routes before understanding the requirements.

❌ Letting frontend developers guess response formats.

❌ Frequently changing endpoint names.

❌ Returning different response structures for similar endpoints.

❌ Updating APIs without versioning or communicating the changes.

# Key Terms

|Term|Meaning|
|---|---|
|API-First|Designing APIs before implementation|
|API Contract|Agreed specification for requests and responses|
|Mock API|Fake API used during development|
|Code-First|Writing code before designing the API|
|Breaking Change|A change that causes existing clients to stop working|
|API Specification|Detailed documentation of the API contract|

# Interview Questions

### 1. What is API-First Design?

**Answer:** API-First Design is the practice of designing and agreeing on the API contract before implementing the backend. It allows frontend, backend, and QA teams to work independently while ensuring consistency.

---

### 2. What is an API Contract?

**Answer:** An API contract defines how clients and servers communicate. It specifies endpoints, HTTP methods, request and response formats, status codes, authentication requirements, and validation rules.

---

### 3. What are the advantages of API-First over Code-First?

**Answer:**

- Parallel frontend and backend development.
    
- Better documentation.
    
- Fewer integration issues.
    
- Stable and predictable APIs.
    
- Easier testing and maintenance.
