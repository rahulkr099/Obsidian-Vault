# Module 1 — Understanding API Design

# Lesson 1.3 — Resource-Oriented Design

> **Goal:** Learn how to identify resources from business requirements and design REST APIs around resources (nouns) instead of actions (verbs).

---

# Learning Objectives

After this lesson, you should be able to:

- Understand what a resource is.
    
- Identify resources from business requirements.
    
- Design APIs using nouns instead of verbs.
    
- Know why resource-oriented APIs are easier to maintain.
    
- Avoid common endpoint design mistakes.
    

---

# What is a Resource?

A **resource** is any piece of information or entity that your application manages.

Think of it as a **thing**, not an action.

Examples:

|Application|Resources|
|---|---|
|Blog|Users, Posts, Comments, Categories|
|E-commerce|Products, Orders, Customers, Carts|
|Todo|Users, Tasks, Projects|
|Chat|Users, Messages, Conversations|
|Food Delivery|Restaurants, Menus, Orders, Drivers|

Notice something?

Every resource is a **noun**.

---

# Resources vs Actions

Beginners often think about **actions**:

- Login
    
- Create Post
    
- Delete User
    
- Like Post
    
- Add Comment
    

Professional API designers think about **resources**:

- Users
    
- Posts
    
- Comments
    
- Likes
    
- Orders
    

The action is communicated by the **HTTP method**, not by the URL.

---

# Bad API Design

```http
GET /getPosts

POST /createPost

POST /deletePost

POST /updatePost
```

Problems:

- Verb-heavy URLs.
    
- Inconsistent naming.
    
- Difficult to scale.
    
- Harder to understand.
    

---

# Good API Design

```http
GET /posts

POST /posts

PATCH /posts/:id

DELETE /posts/:id
```

The URL represents the **resource**.

The HTTP method represents the **action**.

---

# Why Nouns?

Suppose someone sees:

```http
GET /posts
```

They immediately understand:

> "This API deals with posts."

Now compare it with:

```http
GET /fetchAllBlogArticles
```

Questions arise:

- Does it include drafts?
    
- Does it include deleted posts?
    
- Is it only for blogs?
    
- Is it paginated?
    

Simple resource names reduce confusion.

---

# Finding Resources from Requirements

Requirement:

> Users can write blog posts.

Resources:

```text
User

Post
```

---

Requirement:

> Readers can comment on posts.

Resources:

```text
User

Post

Comment
```

---

Requirement:

> Users can like posts.

Resources:

```text
User

Post

Like
```

---

Requirement:

> Authors organize posts into categories.

Resources:

```text
Category

Post
```

Notice that we didn't create resources like:

- WritePost
    
- DeletePost
    
- PublishPost
    

Instead, we identified the **things** the system manages.

# Example: Blog Requirements

Suppose the product manager says:

- Users register.
    
- Users log in.
    
- Users create posts.
    
- Users edit posts.
    
- Users delete posts.
    
- Users comment on posts.
    
- Users like posts.
    
- Users follow authors.
    

Let's identify the resources.

```text
User

Post

Comment

Like

Follow
```

Now we already know what tables (or collections) and endpoints we'll probably need.

---

# Mapping Resources to Endpoints

Resource:

```text
Post
```

Endpoints:

```http
GET /posts

GET /posts/:id

POST /posts

PATCH /posts/:id

DELETE /posts/:id
```

Notice that **every endpoint revolves around the same resource**.

---

# Nested Resources

Some resources naturally belong to others.

Example:

A comment belongs to a post.

```http
GET /posts/10/comments
```

Meaning:

> Get comments of Post 10.

Create comment:

```http
POST /posts/10/comments
```

This clearly shows the relationship.

---

# When NOT to Nest

Imagine:

```http
GET /posts/10/comments/5
```

This is acceptable.

But:

```http
GET /users/5/posts/10/comments/7/replies/3
```

This becomes difficult to read and maintain.

Avoid deeply nested URLs.

A common guideline is to limit nesting to **one or two levels**.

---

# Resource Collections vs Single Resources

Collection:

```http
GET /posts
```

Returns many posts.

---

Single Resource:

```http
GET /posts/15
```

Returns only Post 15.

---

Think of it like:

```text
Library → Collection

Book → Single Resource
```

---

# Resources Have Relationships

```text
User
  │
  ├── Posts

  ├── Comments
  │
```

# Resource Lifecycle

Every resource usually follows a lifecycle.

Example:

```text
Post

Created
   ↓
Edited
   ↓
Published
   ↓
Archived
   ↓
Deleted
```

Your API should support the operations required at each stage.

# Resource Naming Rules

Use **plural nouns**.

Good:

```http
/users

/posts

/orders

/comments
```

Avoid:

```http
/getUsers

/createUser

/deleteComment

/updateOrder
```

The HTTP method already tells us the action.

---

# Resource-Oriented Thinking

Instead of asking:

> "How do I create a post?"

Ask:

> "What resource am I managing?"

Instead of:

> "How do I delete a user?"

Ask:

> "How does the User resource behave?"

This mindset leads to cleaner API design.

---

# Best Practices

- Design APIs around resources, not actions.
    
- Use nouns in URLs.
    
- Use HTTP methods for actions.
    
- Keep URLs simple and meaningful.
    
- Use plural resource names.
    
- Keep nesting shallow.
    
- Identify resources directly from business requirements.
    

---

# Common Mistakes

❌ Using verbs in URLs.

```http
POST /createPost
```

---

❌ Mixing naming styles.

```http
/users

/getPosts

/orders
```

---

❌ Deeply nested endpoints.

```http
/users/1/posts/2/comments/3/replies/4
```

---

❌ Designing endpoints before identifying resources.

---

# Key Terms

|Term|Meaning|
|---|---|
|Resource|A business entity managed by the API|
|Collection|A group of resources (e.g., `/posts`)|
|Single Resource|One specific resource (e.g., `/posts/10`)|
|Nested Resource|A resource related to another (e.g., `/posts/10/comments`)|
|Resource-Oriented Design|Designing APIs around nouns rather than verbs|

# Interview Questions

### 1. What is a resource in REST API design?

**Answer:**  
A resource is any business entity or piece of data managed by the system, such as a user, post, product, or order. Resources are typically represented by nouns.

---

### 2. Why should URLs use nouns instead of verbs?

**Answer:**  
URLs identify resources, while HTTP methods (GET, POST, PATCH, DELETE) specify the action. This separation makes APIs more consistent, intuitive, and easier to maintain.

---

### 3. When should you use nested resources?

**Answer:**  
Use nested resources when one resource naturally belongs to another, such as comments belonging to a post (`/posts/:id/comments`). Avoid excessive nesting beyond one or two levels.

---

# 💡 Backend Engineering Insight

One of the biggest mindset shifts from beginner to professional backend development is this:

- **Beginners think in terms of features:** "Create post", "Delete comment", "Update profile".
    
- **Professionals think in terms of domain models:** "Post", "Comment", "User", "Profile".
    

Once you've identified the right resources, your **database schema**, **API endpoints**, **service layer**, and **authorization rules** all become much easier to design.
