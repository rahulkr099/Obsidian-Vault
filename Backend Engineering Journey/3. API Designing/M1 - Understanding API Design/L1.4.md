> **Goal:** Understand the complete journey of an API request—from a user action in the browser to the backend, database, and back to the user.

# The Big Picture

Imagine a user visits your Blog application and clicks **"Publish Post"**.

It may seem like one simple action, but many steps happen behind the scenes.

```text
User
  │
  ▼
Frontend (React)
  │
  ▼
API Request (HTTP)
  │
  ▼
Backend (Express)
  │
  ▼
Controller
  │
  ▼
Service
  │
  ▼
Repository
  │
  ▼
Database (MongoDB/PostgreSQL)
  │
  ▼
Repository
  │
  ▼
Service
  │
  ▼
Controller
  │
  ▼
HTTP Response
  │
  ▼
Frontend
  │
  ▼
User
```

This entire process often takes only a few hundred milliseconds.

---

# Step 1 — User Performs an Action

The journey always begins with a user.

Example:

The user fills out a form.

```text
Title:
Learning REST APIs

Content:
This is my first blog...
```

Then clicks:

```text
Publish
```

The browser itself doesn't save anything.

It asks the backend to do it.

---

# Step 2 — Frontend Creates an HTTP Request

React gathers the form data.

Example:

```javascript
const data = {
    title: "Learning REST APIs",
    content: "This is my first blog..."
};
```

Then sends it.

```http
POST /posts
```

Request Body:

```json
{
    "title": "Learning REST APIs",
    "content": "This is my first blog..."
}
```

The frontend doesn't know **how** posts are stored.

It only knows the API contract.

---

# Step 3 — The HTTP Request Travels Across the Internet

The request leaves the browser.

```text
Browser
    │
    ▼
Internet
    │
    ▼
Backend Server
```

It contains:

- URL
    
- HTTP Method
    
- Headers
    
- Cookies (if any)
    
- Authentication token (if any)
    
- Request body
    

Example:

```http
POST /posts
Authorization: Bearer eyJhb...
Content-Type: application/json
```

---

# Step 4 — Express Receives the Request

Express receives the request.

Example:

```javascript
POST /posts
```

Express checks its routes.

```text
POST /posts
      │
      ▼
Post Controller
```

The matching controller is executed.

---

# Step 5 — Controller Handles the Request

The controller is the **entry point** of your business logic.

Responsibilities:

- Read request data.
    
- Validate request format.
    
- Call the service layer.
    
- Return a response.
    

Example:

```javascript
createPost(req, res)
```

Notice:

The controller should **not** contain business logic.

It coordinates the request.

---

# Step 6 — Service Layer Executes Business Logic

The controller calls:

```text
PostService.createPost()
```

The service answers business questions.

Example:

- Is the user logged in?
    
- Is the user allowed to publish?
    
- Is the title unique?
    
- Is the user banned?
    
- Has the daily posting limit been reached?
    

This is where business rules live.

---

# Step 7 — Repository Talks to the Database

If all business rules pass:

```text
PostRepository.create()
```

The repository:

- Builds the database query.
    
- Saves the post.
    
- Returns the result.
    

Example:

```text
Insert document into MongoDB
```

or

```sql
INSERT INTO posts (...)
```

Notice:

The service never writes database queries directly.

---

# Step 8 — Database Stores the Data

Database receives the query.

```text
Posts Collection

↓

New Document Added
```

Example:

```json
{
    "_id": "...",
    "title": "Learning REST APIs",
    "author": "...",
    "createdAt": "..."
}
```

The database sends the saved document back.

---

# Step 9 — Response Travels Back

The data moves upward.

```text
Database
    ▲
Repository
    ▲
Service
    ▲
Controller
```

Controller returns:

```http
201 Created
```

Response:

```json
{
    "success": true,
    "message": "Post created successfully",
    "data": {
        "id": 15,
        "title": "Learning REST APIs"
    }
}
```

---

# Step 10 — Frontend Receives the Response

React receives:

```javascript
response.data
```

Now it can:

- Show success message.
    
- Redirect.
    
- Refresh the post list.
    
- Clear the form.
    

The backend doesn't update the UI.

It only returns data.

---

```text
User Clicks Button
        │
        ▼

        │
        ▼

        │
        ▼
Controller
        │
        ▼

        ▼

        ▼

        ▲

        ▲

        ▲

```

This is the path nearly every backend request follows.

# Responsibilities of Each Layer

## Frontend

Responsible for:

- UI
    
- User interaction
    
- Forms
    
- API calls
    
- Displaying responses
    

Should **not** contain:

- Database queries
    
- Business rules
    
- Authentication logic
    

---

## Controller

Responsible for:

- Reading requests.
    
- Calling services.
    
- Returning responses.
    

Should **not** contain:

- Database queries.
    
- Business rules.
    

---

## Service

Responsible for:

- Business logic.
    
- Business rules.
    
- Validation based on business requirements.
    
- Orchestrating multiple repositories or external services.
    

Should **not** contain:

- HTTP-specific code.
    
- Response formatting.
    

---

## Repository

Responsible for:

- Database operations.
    
- Query construction.
    
- CRUD operations.
    

Should **not** contain:

- Business decisions.
    

---

## Database

Responsible for:

- Persisting data.
    
- Enforcing constraints.
    
- Executing queries.
    

Should **not** know anything about:

- Users.
    
- HTTP.
    
- Controllers.
    
- Services.
    

---

# Why Use Layers?

Imagine everything lived inside one Express route.

```javascript
router.post("/posts", ...)
```

Inside it:

- Validate request.
    
- Check permissions.
    
- Query database.
    
- Send email.
    
- Save audit logs.
    
- Return response.
    

Soon the file becomes 300+ lines long.

This is difficult to:

- Read.
    
- Test.
    
- Reuse.
    
- Debug.
    

Layered architecture keeps each part focused on one responsibility.

# Common Mistakes

### ❌ Controller contains SQL or MongoDB queries.

---

### ❌ Service returns Express responses.

```javascript
res.status(200)
```

The service should not know about Express.

---

### ❌ Repository validates business rules.

Repositories should only manage data access.

---

### ❌ Frontend decides authorization.

Authorization must always be enforced on the backend.

---

# Best Practices

- Keep layers independent.
    
- Let each layer have a single responsibility.
    
- Controllers stay thin.
    
- Services contain business logic.
    
- Repositories handle data access.
    
- Keep the frontend focused on presentation and interaction.

# Key Terms

|Term|Meaning|
|---|---|
|Client|The application sending the request (browser, mobile app)|

# Interview Questions

### 1. Explain the lifecycle of an API request.

**Answer:**  
A user action triggers the frontend to send an HTTP request. The request reaches the backend, where the controller receives it, the service executes business logic, the repository interacts with the database, and the result is returned through the same layers as an HTTP response to the frontend.

---

### 2. Why shouldn't controllers contain business logic?

**Answer:**  
Controllers should focus on handling HTTP requests and responses. Moving business logic to the service layer improves reusability, testability, and maintainability.

---

### 3. What is the responsibility of the repository layer?

**Answer:**  
The repository layer handles all database interactions, including CRUD operations and query execution. It abstracts data access from the rest of the application.

# 💡 Backend Engineering Insight

This layered flow:

```text
Frontend
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

is one of the most common architectures used in modern backend development. Whether you're using **Express**, **NestJS**, **Spring Boot**, **ASP.NET Core**, or **Laravel**, the same separation of responsibilities appears again and again.

Understanding this flow deeply will make it much easier to learn new frameworks because the concepts stay the same even if the syntax changes.
