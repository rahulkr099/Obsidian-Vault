# What is Validation?

Validation answers one question:

> **"Can this data safely move to the next step?"**

Every request entering your backend must be checked before it reaches the database.

Example:

```http
POST /posts
```

Request:

```json
{
    "title": "Learning Express",
    "content": "..."
}
```

Before saving this post, your application must verify:

- Is the request format correct?
    
- Does it follow business rules?
    
- Can it be safely stored in the database?
    

That's validation.

---

# Why Validation Matters

Imagine someone sends:

```json
{
    "title": "",
    "content": ""
}
```

Or:

```json
{
    "title": 12345
}
```

Or:

```json
{
    "unexpectedField": "hack"
}
```

Without validation:

```text
Client

↓

Database
```

Invalid data gets stored.

Eventually:

- APIs break
    
- Reports become incorrect
    
- Frontend crashes
    
- Users lose trust

# Three Types of Validation

## 1. Request Validation

Question:

> **"Is this HTTP request valid?"**

Example:

```json
{
    "title": "",
    "content": ""
}
```

Checks:

- Required fields
    
- Data types
    
- String length
    
- Email format
    
- Query parameters
    
- Route parameters
    

Usually handled in the **Controller**.

---

## 2. Business Validation

Question:

> **"Does this request make sense for the business?"**

Example:

A user tries to:

```text
Like

the same post twice.
```

Request format:

✅ Valid

Business rule:

❌ Invalid

Another example:

```text
Publish post

without category
```

Again:

Request is valid.

Business rule is violated.

Usually handled in the **Service**.

---

## 3. Database Validation

Question:

> **"Can this data be stored safely?"**

Examples:

```text
Unique email

Required field

Unique slug
```

These rules protect the database even if application code fails.

Handled by:

- Database
    
- ORM/ODM (like Mongoose)

# Why Not Put Everything in the Controller?

Bad architecture:

```text
Controller

↓

Validate Request

↓

Check Business Rules

↓

Query Database

↓

Save Data
```

Controller becomes huge.

Difficult to maintain.

---

Instead:

```text
Controller

↓

Service

↓

Repository

↓

Database
```

Each layer has one responsibility.

---

# Layer Responsibilities

## Controller

Responsible for:

```text
HTTP

↓

Validation

↓

Response
```

Knows about:

- Express
    
- Requests
    
- Responses
    

Should NOT know business rules.

---

## Service

Responsible for:

```text
Business Rules
```

Knows about:

- Policies
    
- Permissions
    
- Workflows
    
- Business decisions
    

Should NOT know MongoDB queries.

---

## Repository

Responsible for:

```text
Database Operations
```

Knows about:

- MongoDB
    
- SQL
    
- Queries
    

Should NOT contain business logic.

---

## Database

Responsible for:

```text
Data Integrity
```

Protects data even if application code contains bugs.

# Why Multiple Layers?

Imagine the controller misses something.

The database still protects:

```text
Unique email

NOT NULL

Unique slug
```

Validation layers act like multiple security checkpoints.

---

# Validation is Defense in Depth

Think of an airport.

```text
Entrance Security

↓

Passport Check

↓

Boarding Gate

↓

Aircraft Door
```

One missed check doesn't compromise the entire system.

Backend validation works the same way.

---

# Common Beginner Mistakes

## ❌ Validate Everything in Controllers

Controllers become thousands of lines long.

Instead:

Only validate the HTTP request.

---

## ❌ Business Rules in Repositories

Bad:

```text
Repository

↓

Check if user owns post
```

Ownership is a business rule.

It belongs in the Service.

---

## ❌ Trust the Client

Never assume:

```json
{
    "role": "admin"
}
```

is truthful.

Always validate and verify on the server.

---

## ❌ Rely Only on Database Validation

Database validation is the **last line of defense**, not the first.

Reject bad requests before they reach the database whenever possible.

---

# Professional Validation Pipeline

```text
Client

↓

Controller
(Request Validation)

↓

Service
(Business Validation)

↓

Repository
(Database Operations)

↓

Database
(Data Integrity)

↓

Response
```

This is the validation strategy used in well-structured backend applications.

---

# Best Practices

✅ Validate early.

✅ Keep each layer responsible for its own type of validation.

✅ Don't duplicate validation unnecessarily.

✅ Never trust client input.

✅ Let the database enforce critical integrity rules.

✅ Keep controllers thin and services focused on business logic.

# Key Takeaways

- Validation is a multi-layered process, not a single step.
    
- **Request Validation** checks the structure and format of incoming HTTP requests.
    
- **Business Validation** enforces application rules and policies.
    
- **Database Validation** protects data integrity at the persistence layer.
    
- Each layer has a clear responsibility, leading to cleaner, more maintainable backend architecture.
    
- Multiple validation layers provide defense in depth and prevent invalid data from reaching production systems.
