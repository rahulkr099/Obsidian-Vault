# Lesson 10.2 — Request Validation (Controller Layer)

> **Goal:** Learn how to validate HTTP requests before they reach your business logic, keeping controllers clean and preventing invalid requests from entering your application.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand what request validation is
    
- Know what should be validated in the controller
    
- Validate request body, route parameters, query parameters, and headers
    
- Understand why validation libraries are used
    
- Keep controllers thin
    
- Return proper HTTP responses for invalid requests
    

---

# What is Request Validation?

Request validation answers one question:

> **"Is this HTTP request structurally valid?"**

It does **not** answer:

- Can this user edit the post?
    
- Does the email already exist?
    
- Is the post published?
    

Those are **business validations**.

---

# Where Does It Happen?

The request first reaches your controller.

```text
Client

↓

Express Route

↓

Controller

↓

Service

↓

Repository
```

The controller should reject invalid requests immediately.

---

# What Should the Controller Validate?

The controller validates HTTP-related data.

Specifically:

- Request Body
    
- Route Parameters
    
- Query Parameters
    
- Headers
    

Nothing more.

---

# 1. Request Body Validation

Example:

```http
POST /posts
```

Request:

```json
{
    "title": "Learning Express",
    "content": "..."
}
```

Questions:

- Is `title` present?
    
- Is `title` a string?
    
- Is `content` present?
    
- Is `content` too long?
    

These are request validation rules.

---

Another request:

```json
{
    "title": 12345
}
```

Problem:

```text
Title

should be a string.
```

Reject immediately.

---

# 2. Route Parameter Validation

Example:

```http
GET /posts/123
```

Route parameter:

```text
123
```

Questions:

- Is it present?
    
- Is it a valid ID?
    
- Is it the correct format?
    

Bad request:

```http
GET /posts/abc@@@
```

If your application expects a MongoDB ObjectId or UUID, validate the format before continuing.

---

# 3. Query Parameter Validation

Example:

```http
GET /posts?page=2&limit=10
```

Questions:

- Is `page` a number?
    
- Is `limit` positive?
    
- Is `limit` within the allowed maximum?
    

Bad:

```http
GET /posts?page=-5
```

Return:

```http
400 Bad Request
```

---

# Another Example

Bad:

```http
GET /posts?limit=10000
```

Suppose your API allows:

```text
Maximum

100
```

Reject the request or cap the limit, depending on your API policy.

---

# 4. Header Validation

Some APIs require headers.

Example:

```http
Authorization: Bearer <token>
```

Controller can verify:

- Header exists
    
- Correct format
    

Authentication middleware later verifies the token itself.

---

# What the Controller Should NOT Validate

Suppose:

```http
POST /register
```

Request:

```json
{
    "email":"rahul@example.com"
}
```

Question:

Does this email already exist?

❌ Not controller validation.

Why?

Because it requires a database query.

That belongs in the **Service**.

---

Another example.

Question:

Can Rahul publish this post?

Requires:

- User role
    
- Business policy
    

Again:

Service layer.

---

# Validation Libraries

Instead of writing many `if` statements:

```text
if (...)

if (...)

if (...)

if (...)
```

Professional teams use validation libraries.

Popular choices:

- Joi
    
- Zod
    
- express-validator
    

These help define validation rules in a clear, reusable way.

# Validation Flow

Example:

```http
POST /posts
```

Flow:

```text
Receive Request

↓

Validate Body

↓

Validate Params

↓

Validate Query

↓

Call Service
```

Only valid requests reach the service.

# Example Validation Rules

Suppose the request is:

```json
{
  "title": "...",
  "content": "...",
  "category": "technology"
}
```

Controller checks:

```text
Title

Required

String

1–150 characters
```

---

Content:

```text
Required

String
```

---

Category:

```text
Required

String
```

Notice that the controller only checks the **shape** of the data.

It does **not** verify whether the category exists.

---

# Validation Error Response

Suppose:

```json
{
    "title":""
}
```

Response:

```http
400 Bad Request
```

Example response body:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "details": [
      {
        "field": "title",
        "message": "Title is required."
      }
    ]
  }
}
```

A consistent error format makes APIs easier to use.

# Thin Controllers

Bad controller:

```text
Validate Request

↓

Check User Role

↓

Query Database

↓

Business Rules

↓

Save Data
```

Huge controller.

Hard to maintain.

---

Good controller:

```text
Validate Request

↓

Call Service

↓

Return Response
```

Simple.

Readable.

# Common Beginner Mistakes

## ❌ Database Queries in Controllers

Bad:

```text
Controller

↓

Check if email exists
```

Move this to the Service.

---

## ❌ Skipping Query Validation

Developers validate the body but forget:

```http
?page=-5
```

Every input source should be validated.

---

## ❌ Generic Error Messages

Bad:

```text
Invalid request
```

Better:

```text
Title is required.

Limit must be between 1 and 100.
```

Specific errors help API consumers fix their requests quickly.

---

## ❌ Duplicating Validation Rules

If multiple controllers need the same validation:

Don't copy and paste.

Create reusable validation schemas or middleware.

# Best Practices

✅ Validate every input source:

- Body
    
- Params
    
- Query
    
- Headers
    

✅ Reject invalid requests early.

✅ Use validation libraries instead of manual checks.

✅ Keep controllers thin.

✅ Return consistent `400 Bad Request` responses.

✅ Reuse validation schemas across endpoints.

# Mini Exercise

Design request validation for:

```http
POST /posts
```

Request:

```json
{
    "title": "...",
    "content": "...",
    "category": "...",
    "tags": ["..."]
}
```

For each field, decide:

- Is it required?
    
- What data type should it be?
    
- Are there length limits?
    
- Are there allowed values?
    

Remember: only include **request validation** rules, not business rules.

---

# Key Takeaways

- Request validation checks the **structure and format** of incoming HTTP requests.
    
- Controllers (or validation middleware) should validate request bodies, route parameters, query parameters, and headers.
    
- Controllers should **not** perform business validation or database lookups.
    
- Validation libraries like Joi, Zod, and express-validator help create reusable, maintainable validation rules.
    
- Reject invalid requests early with clear and consistent `400 Bad Request` responses.
    
- Thin controllers lead to cleaner and more maintainable backend architectures.
