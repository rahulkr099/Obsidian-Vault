# Lesson 10.3 — Business Validation (Service Layer)

> **Goal:** Learn how to enforce business rules in the Service Layer and understand why these validations should never live in the Controller or Repository.

This is one of the biggest differences between **junior** and **professional** backend code.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand what business validation is
    
- Distinguish request validation from business validation
    
- Know why business rules belong in the Service Layer
    
- Design services that enforce business rules consistently
    
- Return appropriate HTTP status codes for business validation failures
    

---

# What is Business Validation?

Business validation answers one question:

> **"Does this action make sense according to the application's business rules?"**

Notice that this is **not** about data format.

Example:

```json
{
    "email": "rahul@example.com"
}
```

The email format is correct.

But...

What if the email already exists?

That's a **business rule**, not a request validation rule.

---

# Request Validation vs Business Validation

Request:

```http
POST /auth/register
```

Body:

```json
{
    "email": "rahul@example.com",
    "password": "secret123"
}
```

### Controller checks

- Email is present
    
- Email format is valid
    
- Password is at least 8 characters
    

All good.

---

### Service checks

- Is this email already registered?
    

If yes:

```http
409 Conflict
```

The request is valid.

The business rule is not.

---

# Why Doesn't It Belong in the Controller?

Suppose the controller checks:

```text
Email exists?
```

How?

It must query the database.

Now the controller starts doing:

- HTTP handling
    
- Database queries
    
- Business decisions
    

Its responsibilities become mixed.

Instead:

```text
Controller

↓

Service

↓

Repository
```

The controller stays simple.

---

# Example 1 — Duplicate Email

Business rule:

> Every email must be unique.

Flow:

```text
Controller

↓

Service

↓

UserRepository.findByEmail()

↓

Exists?

↓

409 Conflict
```

The service coordinates the rule.

---

# Example 2 — Duplicate Slug

Blog request:

```http
POST /posts
```

Body:

```json
{
    "title": "Learning Express"
}
```

Slug generated:

```text
learning-express
```

Business rule:

Two posts cannot share the same slug.

Service:

```text
Generate slug

↓

Check database

↓

Slug exists?

↓

409 Conflict
```

# Example 3 — Authorization

Requirement:

> Only the author can edit a post.

Request:

```http
PATCH /posts/25
```

Request format:

✅ Valid

Business rule:

```text
Current User

↓

Post Owner?

↓

No

↓

403 Forbidden
```

The controller cannot decide this.

The service can.

# Example 4 — Publish Rules

Requirement:

A post can only be published if it has:

- Title
    
- Content
    
- Category
    
- Thumbnail
    

Request:

```http
PATCH /posts/25
```

Body:

```json
{
    "status": "published"
}
```

Service checks:

```text
Title?

↓

Content?

↓

Category?

↓

Thumbnail?

↓

Allowed?
```

If any requirement is missing:

```http
422 Unprocessable Entity
```

The request is valid.

The business rule isn't satisfied.

Business rule:

Request:

# Business Validation Flow

```text
Client

↓

Controller
(Request Valid?)

↓

Service
(Business Valid?)

↓

Repository

↓

Database
```

This separation keeps each layer focused.

---

# Controller vs Service

## Controller

Knows:

- Express
    
- HTTP
    
- Requests
    
- Responses
    

Should **not** know:

- Company policies
    
- User permissions
    
- Business workflows
    

---

## Service

Knows:

- Business rules
    
- Permissions
    
- Ownership
    
- State transitions
    
- Cross-resource validation
    

This is the heart of your application.

---

# Cross-Resource Validation

Requirement:

> Add a comment.

Request:

```http
POST /posts/25/comments
```

Business checks:

```text
Post exists?

↓

Post published?

↓

User not blocked?

↓

Allowed
```

These checks involve multiple resources.

They belong in the service.

---

# State Transition Validation

Suppose posts have:

```text
Draft

↓

Published

↓

Archived
```

Business rule:

Archived posts cannot return to Draft.

Service:

```text
Archived

↓

Draft

↓

Rejected
```

Controllers shouldn't know these workflow rules.

---

# Choosing the Right Status Code

|Situation|Status Code|
|---|---|
|Email already exists|`409 Conflict`|
|User lacks permission|`403 Forbidden`|
|Related resource not found|`404 Not Found`|
|Business rule violated|`422 Unprocessable Entity`|

Using the right status code helps API consumers understand what went wrong.

---

# Common Beginner Mistakes

## ❌ Business Logic in Controllers

Bad:

```text
Controller

↓

Check ownership

↓

Check duplicate email

↓

Check slug
```

Controllers become difficult to maintain.

---

## ❌ Business Logic in Repositories

Bad:

```text
Repository

↓

Only author can edit
```

Repositories should only access the database.

---

## ❌ Ignoring Business Rules

Example:

Allowing:

```text
Like

Like

Like

Like
```

The database fills with duplicate relationships.

---

## ❌ Returning 400 for Everything

Not every error is:

```http
400 Bad Request
```

Use status codes that describe the actual problem.

# Best Practices

✅ Keep business rules in the Service Layer.

✅ Let controllers handle HTTP concerns only.

✅ Use repositories only for data access.

✅ Return meaningful status codes.

✅ Think in terms of business policies, not database tables.

# Key Takeaways

- Business validation enforces the rules of your application, not the structure of HTTP requests.
    
- The Service Layer is responsible for business rules such as permissions, uniqueness, ownership, and workflow constraints.
    
- Controllers should remain focused on HTTP request handling.
    
- Repositories should remain focused on data access.
    
- Different business validation failures should return appropriate HTTP status codes, such as `403`, `404`, `409`, or `422`.
    
- Keeping business logic in the Service Layer makes your application easier to maintain, test, and extend.
