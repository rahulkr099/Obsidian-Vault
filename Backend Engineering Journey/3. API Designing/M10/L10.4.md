# Lesson 10.4 — Database Validation (Repository & Database Layer)

> **Goal:** Learn how the database protects your data from becoming inconsistent, even if bugs exist in your application.

Think of the database as the **last security checkpoint** before data is permanently stored.

# Why Database Validation Exists

Imagine your application has a bug.

Instead of:

```json
{
    "title": "Learning Express"
}
```

It accidentally sends:

```json
{
    "title": null
}
```

Suppose the controller missed it.

Suppose the service also missed it.

Should the database save it?

**No.**

The database should reject invalid data.

---

# Validation Layers

Your application now has three validation layers:

```text
Controller

↓

Service

↓

Database
```

Each protects the next layer.

If one layer misses something, another can still stop bad data.

---

# The Repository's Role

Remember your architecture:

```text
Controller

↓

Service

↓

Repository

↓

Database
```

The repository is responsible for:

- Executing queries
    
- Saving data
    
- Updating data
    
- Deleting data
    

It is **not** responsible for business decisions.

Example:

```text
Repository

↓

Save Post
```

Not:

```text
Repository

↓

Can user publish?
```

That belongs in the service.

---

# Database Constraints

Databases enforce rules automatically.

Common constraints include:

- Required fields
    
- Unique values
    
- Reference integrity
    
- Data types
    

Let's examine each.

---

# 1. Required Fields

Blog Post:

```text
Title

Content

Author
```

These should always exist.

Bad data:

```json
{
    "title": null
}
```

Database:

```text
Rejected
```

This prevents incomplete records.

---

# 2. Unique Constraint

Requirement:

Every user email must be unique.

Existing user:

```text
rahul@example.com
```

New request:

```text
rahul@example.com
```

Database:

```text
Duplicate

↓

Rejected
```

Even if your service accidentally misses the duplicate check, the database still protects the data.

---

# Another Example

Blog slugs:

```text
learning-nodejs
```

Should appear only once.

Duplicate slug:

```text
Rejected
```

---

# 3. Reference Integrity

Suppose comments belong to posts.

Request:

```http
POST /posts/999/comments
```

But:

```text
Post 999

doesn't exist.
```

Your service should detect this.

If it doesn't, the database should reject invalid references (depending on the database and schema design).

---

# SQL vs MongoDB

## SQL Databases

Usually enforce:

- Foreign Keys
    
- NOT NULL
    
- UNIQUE
    
- CHECK constraints
    

These are built into the database engine.

---

## MongoDB

MongoDB doesn't have traditional foreign keys.

Instead, integrity is usually maintained through:

- Schema validation
    
- Mongoose validation
    
- Application logic
    

Example:

```text
postId

must be an ObjectId
```

---

# Mongoose Schema Validation

A schema can enforce rules like:

```text
Title

↓

Required
```

```text
Email

↓

Unique
```

```text
Status

↓

Allowed values only
```

These validations run before MongoDB stores the document.

---

# Allowed Values

Suppose:

```text
status
```

Allowed:

```text
draft

published

archived
```

Bad request:

```text
status = active
```

Database layer rejects it.

---

# Data Types

Suppose:

```text
views
```

Should be:

```text
Number
```

Bad:

```text
views = "many"
```

Schema validation rejects it.

---

# Indexes Are Part of Data Integrity

Indexes are often discussed for performance, but they also enforce rules.

Example:

Unique index:

```text
email
```

Benefits:

- Fast lookup
    
- Prevents duplicates
    

---

Compound unique index:

```text
userId

postId
```

Used for:

```text
Likes
```

Prevents:

```text
Same user

↓

Likes same post twice
```

Even if your service has a bug, the database prevents duplicate relationships.

# Database is the Last Line of Defense

Suppose:

Controller:

❌ Forgot validation

↓

Service:

❌ Bug

↓

Repository:

Stores data

↓

Database:

```text
Required field missing

↓

Reject
```

Without database validation:

Bad data enters permanently.

---

# Common Beginner Mistakes

## ❌ Relying Only on Controllers

Controllers can contain bugs.

Database validation provides an additional safety net.

---

## ❌ Skipping Unique Constraints

Checking uniqueness only in the service is risky.

Two requests arriving simultaneously can both pass the check.

A database-level unique constraint prevents this race condition.

---

## ❌ Putting Business Rules in the Database

Bad:

```text
Only admins can publish posts.
```

That's a business rule.

Keep it in the service.

---

## ❌ Assuming MongoDB Prevents Everything

MongoDB is flexible.

Without schema validation, invalid documents can still be inserted.

# Best Practices

✅ Treat the database as the final safety net.

✅ Use required constraints for mandatory fields.

✅ Use unique constraints for identifiers like email and slug.

✅ Use schema validation for data types and allowed values.

✅ Let repositories handle persistence, not business logic.

✅ Never rely on only one validation layer.

# Key Takeaways

- The database is the **last line of defense** against invalid data.
    
- Repositories communicate with the database but should not contain business logic.
    
- Database constraints enforce data integrity through required fields, uniqueness, data types, and schema rules.
    
- Unique indexes prevent duplicate records and help avoid race conditions.
    
- Business rules remain in the Service Layer; data integrity rules belong in the database.
    
- A robust backend uses **all three validation layers**: Controller, Service, and Database.
