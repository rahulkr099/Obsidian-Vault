# Lesson 11.1 — Understanding API Errors

> **Goal:** Learn what API errors are, why they occur, and how professional APIs communicate errors consistently.

A well-designed API doesn't just return successful responses—it also returns **clear, predictable, and useful error responses**.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand what an API error is
    
- Differentiate success responses from error responses
    
- Understand 4xx vs 5xx status codes
    
- Distinguish operational errors from programmer errors
    
- Choose the correct HTTP status code for common situations
    

---

# What is an API Error?

An API error means:

> **The server could not successfully complete the client's request.**

Example:

```http
GET /posts/999
```

Suppose Post **999** doesn't exist.

Instead of returning random data:

The API should return:

```http
404 Not Found
```

The client immediately understands the problem.

---

# Success vs Error Responses

## Success

```http
GET /posts/25
```

Response:

```http
200 OK
```

```json
{
  "success": true,
  "data": {
    "id": 25,
    "title": "Learning REST APIs"
  }
}
```

---

## Error

```http
GET /posts/999
```

Response:

```http
404 Not Found
```

```json
{
  "success": false,
  "error": {
    "message": "Post not found."
  }
}
```

Both responses follow a predictable structure.

---

# Why Error Handling Matters

Imagine two APIs.

API A:

```json
{
    "error":"Something went wrong"
}
```

API B:

```json
{
  "success": false,
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "The requested post does not exist."
  }
}
```

Which one is easier for frontend developers?

Clearly **API B**.

Professional APIs communicate errors clearly.

# Where Can Errors Occur?

A request travels through several layers:

```text
Client

↓

Controller

↓

Service

↓

Repository

↓

Database
```

Errors can happen at any stage.

---

Example:

Controller:

```text
Missing title
```

Service:

```text
User not allowed
```

Repository:

```text
Database timeout
```

Database:

```text
Duplicate email
```

Different layers produce different types of errors.

---

# Two Types of Errors

Professional backend engineers divide errors into two categories.

---

# 1. Operational Errors

These are **expected** errors.

Examples:

```text
Invalid password

Email already exists

Post not found

Unauthorized request
```

These happen because of user input or normal application behavior.

The application should handle them gracefully.

---

# 2. Programmer Errors

These are **unexpected** bugs.

Examples:

```text
Undefined variable

Null pointer

Syntax bug

Wrong function call
```

These indicate problems in the code itself.

Users should never see internal details about these errors.

---

# Example

Suppose:

```http
POST /register
```

Body:

```json
{
    "email":"invalid-email"
}
```

This is:

```text
Operational Error
```

The user made a mistake.

Return:

```http
400 Bad Request
```

---

Another example:

```text
TypeError:

Cannot read property 'name'
```

This is:

```text
Programmer Error
```

The developer must fix the bug.

Return:

```http
500 Internal Server Error
```

without exposing technical details.

---

# Client Errors vs Server Errors

HTTP status codes are grouped into categories.

---

## 4xx — Client Errors

Meaning:

> The client sent an invalid or unacceptable request.

Examples:

|Status|Meaning|
|---|---|
|400|Bad Request|
|401|Unauthorized|
|403|Forbidden|
|404|Not Found|
|409|Conflict|
|422|Unprocessable Entity|

These are usually operational errors.

---

## 5xx — Server Errors

Meaning:

> The server failed while processing a valid request.

Examples:

|Status|Meaning|
|---|---|
|500|Internal Server Error|
|502|Bad Gateway|
|503|Service Unavailable|

These usually indicate server-side problems.

---

# Common Status Codes

Let's connect them to business situations.

---

## 400 Bad Request

The request itself is invalid.

Example:

```http
POST /posts
```

Body:

```json
{
    "title":""
}
```

Title is required.

---

## 401 Unauthorized

User is not authenticated.

Example:

```http
GET /profile
```

Missing JWT.

---

## 403 Forbidden

User is authenticated but lacks permission.

Example:

Rahul tries to delete another user's post.

---

## 404 Not Found

Requested resource doesn't exist.

Example:

```http
GET /posts/999
```

---

## 409 Conflict

Request conflicts with existing data.

Example:

```text
Duplicate email

Duplicate slug

Duplicate like
```

---

## 422 Unprocessable Entity

The request is valid.

But business rules reject it.

Example:

```text
Publish post

↓

Missing category
```

---

## 500 Internal Server Error

Unexpected bug.

Example:

```text
Database crashed

↓

Unhandled exception
```

---

# Choosing the Correct Status Code

Suppose:

```http
POST /auth/register
```

Existing email:

```http
409 Conflict
```

Not:

```http
400 Bad Request
```

The request format is correct.

The conflict is with existing data.

---

Another example.

```http
PATCH /posts/25
```

User isn't the author.

Return:

```http
403 Forbidden
```

Not:

```http
401 Unauthorized
```

The user is authenticated.

They simply don't have permission.

```text

↓

↓
```

# Common Beginner Mistakes

## ❌ Returning 200 for Errors

Bad:

```http
200 OK
```

```json
{
    "success": false
}
```

If the request failed, use an error status code.

---

## ❌ Returning 500 for Everything

Not every error is a server error.

Example:

Missing required field.

Correct:

```http
400 Bad Request
```

---

## ❌ Confusing 401 and 403

Remember:

```text
401

↓

Not Logged In
```

```text
403

↓

Logged In

↓

Permission Denied
```

---

## ❌ Exposing Internal Errors

Bad:

```json
{
    "error":"MongoServerError: Duplicate key..."
}
```

Clients shouldn't see database implementation details.

# Best Practices

✅ Use the correct HTTP status code.

✅ Keep error responses consistent.

✅ Separate operational and programmer errors.

✅ Never expose stack traces or database errors to clients.

✅ Return meaningful error messages that help API consumers fix the problem.

# Key Takeaways

- API errors communicate why a request failed.
    
- Use **4xx** status codes for client-side problems and **5xx** status codes for server-side failures.
    
- Operational errors are expected and should be handled gracefully.
    
- Programmer errors indicate bugs and should not expose internal details.
    
- Choosing the correct HTTP status code makes APIs easier to understand and integrate.
    
- Consistent error responses are a hallmark of professional API design.
