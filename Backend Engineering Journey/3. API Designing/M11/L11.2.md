# Lesson 11.2 — Designing a Professional Error System

> **Goal:** Build a consistent, reusable, and production-ready error handling system for your backend application.

A professional backend doesn't scatter error handling throughout the codebase. Instead, it follows **one centralized error architecture**.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Design a consistent error response format
    
- Understand why custom error classes are useful
    
- Know what information an API error should contain
    
- Design a centralized error handling strategy
    
- Separate client-facing errors from internal errors
    

---

# The Problem

Imagine three controllers.

## UserController

```text
return

"User not found"
```

---

## PostController

```text
return

"Post doesn't exist"
```

---

## CommentController

```text
return

"No comment"
```

Every controller returns errors differently.

Frontend developers now have to handle multiple formats.

This quickly becomes difficult to maintain.

---

# A Professional Error System

Every endpoint should return errors in the same structure.

Example:

```json
{
  "success": false,
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "The requested post does not exist."
  }
}
```

Whether the error comes from authentication, posts, comments, or users, the format remains consistent.

---

# Why Consistency Matters

Frontend code becomes much simpler.

Instead of checking many response shapes, it always expects:

```text
success

↓

error

↓

code

↓

message
```

Predictability is a major benefit of good API design.

---

# Anatomy of an Error Response

A professional response usually contains:

```json
{
  "success": false,
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "The requested post does not exist."
  }
}
```

Let's understand each field.

---

## success

```json
false
```

Quickly tells the client that the request failed.

---

## code

Example:

```text
POST_NOT_FOUND
```

This is a machine-readable identifier.

Frontend applications can react based on the code instead of parsing text messages.

Example:

```text
EMAIL_ALREADY_EXISTS

INVALID_PASSWORD

POST_NOT_FOUND

COMMENT_NOT_FOUND
```

---

## message

Example:

```text
The requested post does not exist.
```

This is human-readable.

It explains the problem clearly.

---

# Why Use Error Codes?

Imagine supporting multiple languages.

English:

```text
Post not found.
```

Spanish:

```text
Publicación no encontrada.
```

The message changes.

The code:

```text
POST_NOT_FOUND
```

remains the same.

Frontend logic stays unchanged.

---

# Custom Error Class

Instead of creating errors like:

```text
throw new Error(...)
```

Professional applications often create a custom error type.

Conceptually:

```text
AppError

↓

Status Code

↓

Error Code

↓

Message
```

Now every error carries the information needed to build a proper HTTP response.

---

# Example

Suppose the service detects:

```text
Post not found.
```

Instead of returning random values:

It creates a structured error containing:

```text
404

POST_NOT_FOUND

"The requested post does not exist."
```

The global error handler uses this information to generate the HTTP response.

# Where Are Errors Created?

Different layers create different errors.

## Controller

Request validation.

Example:

```text
Missing title
```

---

## Service

Business validation.

Example:

```text
Duplicate email

User not allowed

Post already published
```

---

## Repository

Database-related failures.

Example:

```text
Record not found

Database constraint violation
```

---

The response format remains identical.

# Centralized Error Handling

Without centralization:

```text
Controller

↓

try/catch

↓

Controller

↓

try/catch

↓

Controller

↓

try/catch
```

Lots of duplicated code.

---

Professional approach:

```text
Controller

↓

Throw Error

↓

Global Error Handler

↓

HTTP Response
```

Every error passes through one place.

---

# Global Error Handler

Think of it as the application's emergency department.

Flow:

```text
Error

↓

Global Error Handler

↓

Convert to HTTP Response

↓

Send to Client
```

Controllers and services don't need to worry about formatting responses.

---


Flow:

```text
Controller

↓

Service

↓

Post not found

↓

AppError

↓

Global Error Handler

```

Simple and consistent.

# Internal vs External Information

Suppose MongoDB returns:

```text
MongoServerError:

Duplicate key

collection: users
```

Should the client receive this?

No.

Client receives:

```json
{
  "success": false,
  "error": {
    "code": "EMAIL_ALREADY_EXISTS",
    "message": "Email is already registered."
  }
}
```

Internal implementation details stay hidden.

---

# Safe Error Messages

Good:

```text
Email already registered.
```

Bad:

```text
Duplicate key error:

users.email_1
```

The second message exposes database details.

---

# Operational vs Programmer Errors

Operational:

```text
User not found

Duplicate email

Unauthorized
```

Safe to show.

---

Programmer error:

```text
TypeError:

Cannot read property...
```

Never expose this.

Log it internally.

Return:

```http
500 Internal Server Error
```

# Common Beginner Mistakes

## ❌ Different Error Formats

Bad:

```json
{
    "message":"Error"
}
```

Another endpoint:

```json
{
    "error":"Not found"
}
```

Another:

```json
{
    "success":false,
    "msg":"Invalid"
}
```

Choose one format and use it everywhere.

---

## ❌ Returning Raw Database Errors

Never expose:

- SQL queries
    
- MongoDB errors
    
- Stack traces
    

These are for developers, not API consumers.

---

## ❌ Copying try/catch Everywhere

Instead:

Centralize error handling.

---

## ❌ Using Messages as Logic

Frontend should not check:

```text
if(message=="Post not found")
```

Use:

```text
POST_NOT_FOUND
```

Machine-readable codes are much more reliable.

---

# Professional Error Design Checklist

Every error should have:

✅ HTTP Status Code

✅ Error Code

✅ Human-readable Message

✅ Consistent Response Structure

Every application should have:

✅ One Global Error Handler

✅ One Error Response Format

---

# Best Practices

✅ Standardize all error responses.

✅ Create custom application errors instead of generic ones.

✅ Use machine-readable error codes.

✅ Keep human-readable messages clear and concise.

✅ Hide internal implementation details.

✅ Let a global error handler generate responses.

---

# Key Takeaways

- A professional API uses one consistent error response format across every endpoint.
    
- Custom application errors carry structured information such as HTTP status, error code, and message.
    
- Global error handlers eliminate duplicated error-handling code.
    
- Error codes are stable identifiers for applications, while messages are written for humans.
    
- Never expose internal implementation details like stack traces or database errors to clients.
    
- Centralized error handling makes backend applications easier to maintain, debug, and extend.
