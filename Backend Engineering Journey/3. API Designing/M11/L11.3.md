# Lesson 11.3 — Error Handling Across the Architecture

> **Goal:** Learn how errors move through the Controller → Service → Repository → Database architecture and where each layer should create, throw, catch, and handle errors.

This lesson connects your **Backend Architecture Roadmap**, **Service Layer Design**, **Repository Pattern**, **Validation Strategy**, and **Error Handling** into one complete request flow.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand how errors travel through the application
    
- Know which layer should create an error
    
- Know which layer should catch an error
    
- Understand the purpose of the global error handler
    
- Understand how asynchronous errors are handled
    

---

# The Big Picture

Every request follows this path:

```text
Client

↓

Route

↓

Controller

↓

Service

↓

Repository

↓

Database

↓

Response
```

Errors follow the same path—but in reverse.

```text
Database

↑

Repository

↑

Service

↑

Controller

↑

Global Error Handler

↑

Client
```

---

# Where Should Errors Be Created?

Every layer can detect different problems.

The rule is:

> **The layer that discovers the problem should create (throw) the error.**

Let's examine each layer.

---

# Controller Errors

The controller understands HTTP.

Example:

```http
POST /posts
```

Request:

```json
{
    "title": ""
}
```

Problem:

```text
Title is required.
```

The controller detects it.

Creates:

```text
400 Bad Request

VALIDATION_ERROR
```

No reason to call the service.

---

# Service Errors

The service understands business rules.

Example:

```http
PATCH /posts/25
```

Business rule:

Only the author can edit.

Flow:

```text
Service

↓

Current User == Author?

↓

No

↓

403 Forbidden
```

The controller doesn't know this rule.

The service does.

---

Another example:

```http
POST /posts/25/likes
```

Business rule:

```text
Already liked?
```

Service:

```text
409 Conflict
```

---

# Repository Errors

Repositories understand data access.

Suppose:

```text
Repository

↓

Database timeout
```

or

```text
Connection lost
```

Repository detects the database problem.

It should throw a repository or infrastructure-related error.

The service decides whether to transform it into an application error or let it bubble up.

---

# Database Errors

Example:

Unique constraint violated.

```text
Duplicate Email
```

Database rejects the insert.

Repository receives the error.

It may translate it into a more meaningful application error before it reaches the service.

---

# Complete Flow Example

Request:

```http
POST /auth/register
```

Request body:

```json
{
    "email":"rahul@example.com"
}
```

Flow:

```text
Controller

↓

Request Valid

↓

Service

↓

Email Exists?

↓

Yes

↓

Throw EMAIL_ALREADY_EXISTS

↓

Global Error Handler

↓

409 Response
```

Notice:

The controller never formats the error.


```text
↓

↓

↓

↓

```

# Error Propagation

Errors move upward.

```text
Database

↓

Repository

↓

Service

↓

Controller

↓

Global Error Handler

↓

Client
```

Each layer can:

- Handle the error
    
- Transform the error
    
- Pass the error upward
    

---

# Should Every Layer Catch Errors?

No.

A common beginner mistake is wrapping every function in:

```text
try

↓

catch
```

Most layers should simply allow the error to propagate.

Catch an error **only if you can add value**.

For example:

- Add context
    
- Convert it into a business error
    
- Perform cleanup
    
- Log it
    

Otherwise, let it continue to the global error handler.

---

# Example

Repository:

```text
Database

↓

Duplicate Key Error
```

Repository can translate it into:

```text
EMAIL_ALREADY_EXISTS
```

Now the service no longer depends on MongoDB's error format.

This keeps your architecture loosely coupled.

---

# Asynchronous Errors

Most backend operations are asynchronous.

Examples:

- Database queries
    
- File uploads
    
- External APIs
    

These operations can fail at any time.

Instead of manually handling errors in every asynchronous function, professional applications use centralized async error handling so all failures eventually reach the global error handler.

---

# Global Error Handler

Every uncaught application error eventually reaches:

```text
Global Error Handler
```

Responsibilities:

- Determine HTTP status code
    
- Format response
    
- Hide sensitive information
    
- Log unexpected errors
    
- Send response
    

It does **not** decide business rules.

---

# Logging

Suppose:

```text
Database Connection Failed
```

Client should receive:

```http
500 Internal Server Error
```

Server logs:

```text
Timestamp

Request

Stack Trace

Database Error

Correlation ID
```

The client gets a safe message.

Developers get detailed logs.

---

# Example

Client receives:

```json
{
  "success": false,
  "error": {
    "code": "INTERNAL_SERVER_ERROR",
    "message": "Something went wrong."
  }
}
```

Internal log:

```text
MongoServerError

Connection timeout

Stack Trace

Request ID: abc123
```

Different audiences receive different information.

Example:


```text

↓

↓
```

Every layer has one responsibility.

# Error Responsibility Matrix

|Layer|Creates Errors|Handles Errors|
|---|---|---|
|Controller|Request validation|Rarely|
|Service|Business rules|Sometimes|
|Repository|Database/infrastructure translation|Sometimes|
|Database|Constraint violations|No|
|Global Error Handler|No|Yes|

# Common Beginner Mistakes

## ❌ Catching Every Error

Bad:

```text
Controller

↓

try/catch

↓

Service

↓

try/catch

↓

Repository

↓

try/catch
```

This creates repetitive code.

---

## ❌ Swallowing Errors

Bad:

```text
Catch Error

↓

Do Nothing

↓

Continue
```

The client receives incorrect success responses.

Always propagate or handle errors appropriately.

---

## ❌ Returning Database Errors Directly

Bad:

```text
MongoServerError:

Duplicate Key
```

Return a meaningful application error instead.

---

## ❌ Logging Everything

Don't log every validation error.

Example:

```http
POST /posts
```

Missing title:

```http
400 Bad Request
```

This is expected.

Log:

- Unexpected bugs
    
- Database failures
    
- External service failures
    
- Security-related events
    

---

# Real Blog Example

Request:

```http
DELETE /posts/25
```

Flow:

```text
Controller

↓

Validate ID

↓

Service

↓

Post Exists?

↓

Current User Owns Post?

↓

Repository

↓

Delete

↓

Response
```

If ownership fails:

```text
403 Forbidden
```

If database fails:

```text
500 Internal Server Error
```

Different errors originate in different layers.

---

# Best Practices

✅ Let the layer that detects the problem create the error.

✅ Don't catch errors unless you can add value.

✅ Translate low-level infrastructure errors into meaningful application errors.

✅ Use one global error handler.

✅ Log unexpected errors, not every client mistake.

✅ Return consistent responses to API consumers.

# Key Takeaways

- Errors should be created by the layer that discovers the problem.
    
- Controllers handle request validation errors.
    
- Services handle business rule violations.
    
- Repositories interact with the database and can translate infrastructure errors.
    
- The global error handler is responsible for generating consistent HTTP responses.
    
- Catch errors only when you can meaningfully handle, transform, or log them.
    
- A well-designed error flow keeps each architectural layer focused on its own responsibility.
