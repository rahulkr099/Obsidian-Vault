# Endpoint 2 — Login

```http
POST /auth/login
```

Possible errors:

|Error|Status|Layer|
|---|---|---|
|Missing email/password|400|Controller|
|User not found|401|Service|
|Wrong password|401|Service|
|Database failure|500|Repository|

Notice:

We don't tell the client whether:

- Email exists
    
- Password is wrong
    

Instead:

```http
401 Unauthorized
```

This avoids revealing information to attackers.

# One Error Response Format

Every endpoint should return errors in the same structure.

Example:

```json
{
  "success": false,
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "The requested post does not exist."
  }
}
```

Examples:

```text
EMAIL_ALREADY_EXISTS

INVALID_CREDENTIALS

POST_NOT_FOUND

COMMENT_NOT_FOUND

LIKE_ALREADY_EXISTS

ACCESS_DENIED

VALIDATION_ERROR
```

The frontend always knows where to find the error information.

# Logging Strategy

Not every error should be logged.

### Usually Don't Log

- Missing required field
    
- Invalid email
    
- Wrong page number
    

These are common client mistakes.

---

### Log

- Database failures
    
- Unexpected exceptions
    
- External API failures
    
- Authentication attacks
    
- Authorization violations (depending on security requirements)
    

Logs help developers—not clients.

# Error Responsibility Summary

|Layer|Responsibility|
|---|---|
|Authentication Middleware|Authentication errors (`401`)|
|Controller|Request validation (`400`)|
|Service|Business rules (`403`, `404`, `409`, `422`)|
|Repository|Database interaction and infrastructure error translation|
|Database|Data integrity constraints|
|Global Error Handler|Format and send error responses|
|Logger|Record unexpected or operationally important errors|

# Common Beginner Mistakes

## ❌ Returning Different Error Formats

Authentication:

```json
{
    "message":"Unauthorized"
}
```

Posts:

```json
{
    "error":"Post not found"
}
```

Comments:

```json
{
    "msg":"Invalid"
}
```

Every endpoint should use the same response format.

---

## ❌ Using 500 for Business Errors

Bad:

```http
500 Internal Server Error
```

for:

```text
Duplicate email
```

Correct:

```http
409 Conflict
```

---

## ❌ Exposing Internal Details

Bad:

```text
MongoServerError

Duplicate Key

users_email_unique
```

Good:

```json
{
  "success": false,
  "error": {
    "code": "EMAIL_ALREADY_EXISTS",
    "message": "Email is already registered."
  }
}
```

---

## ❌ Logging Every Validation Error

Thousands of users forgetting a required field is normal.

Log unexpected problems, not routine client mistakes.

# Professional Error Handling Checklist

Before shipping an endpoint, ask:

### Controller

- Are invalid requests rejected with `400`?
    

---

### Authentication

- Are unauthenticated requests rejected with `401`?
    

---

### Service

- Are business rules enforced?
    
- Are appropriate status codes returned?
    

---

### Repository

- Are infrastructure errors translated into application errors where appropriate?
    

---

### Database

- Are constraints protecting data integrity?
    

---

### Global Error Handler

- Does every error produce a consistent response?
    

---

### Logging

- Are unexpected failures recorded?
    

If the answer to all is **Yes**, your endpoint has a production-ready error strategy.
