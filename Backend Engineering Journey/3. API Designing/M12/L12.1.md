> **Goal:** Understand why API security matters and learn the security mindset that professional backend engineers use when designing applications.

Before learning JWTs, OAuth, CORS, or rate limiting, you need to understand **what you're trying to protect and why**.

Security is not a feature you add later—it's part of your architecture from the beginning.

# What is API Security?

API security is the practice of protecting your backend from:

- Unauthorized users
    
- Malicious requests
    
- Data theft
    
- Data modification
    
- Service disruption
    

The goal is:

> **Only the right users should perform the right actions on the right resources.**

---

# Example

Blog API:

```http
GET /posts
```

Should anyone access it?

Maybe **yes**.

---

Another endpoint:

```http
DELETE /posts/:id
```

Should everyone access it?

Definitely **no**.

Security decides who is allowed to do what.

# The CIA Triad

Every security decision can be explained using three principles.

```text
Confidentiality

Integrity

Availability
```

Professional backend engineers constantly balance these three.

---

# 1. Confidentiality

Meaning:

> **Only authorized people should see the data.**

Example:

User profile:

```http
GET /profile
```

Should another user see your password?

No.

Should anyone see refresh tokens?

No.

Confidentiality protects private information.

---

Examples:

Protect:

- Passwords
    
- Email addresses (depending on the application)
    
- Refresh tokens
    
- Admin data
    
- Payment information
    

---

# 2. Integrity

Meaning:

> **Data should not be modified by unauthorized users.**

Example:

Rahul owns Post 25.

Aman sends:

```http
PATCH /posts/25
```

Should it succeed?

No.

Integrity ensures data changes only happen through authorized actions.

---

Examples:

Protect against:

- Editing someone else's posts
    
- Changing another user's profile
    
- Modifying payment records
    
- Deleting other users' data
    

---

# 3. Availability

Meaning:

> **The system should remain accessible to legitimate users.**

Imagine someone sends:

```text
100,000 requests

per second
```

The server crashes.

Nobody can use the application.

Availability protects against service disruption.

---

Examples:

Protect with:

- Rate limiting
    
- Load balancing
    
- Caching
    
- Monitoring
    
- Auto-scaling
    

---

# Authentication vs Authorization

This is one of the most common interview questions.

---

## Authentication

Question:

> **Who are you?**

Example:

```http
POST /auth/login
```

User enters:

```text
Email

Password
```

Server verifies identity.

If successful:

User becomes authenticated.

---

## Authorization

Question:

> **What are you allowed to do?**

Example:

```http
DELETE /posts/25
```

Server checks:

```text
Current User

↓

Owns Post?

↓

Yes

↓

Allow
```

or

```text
Admin?

↓

Yes

↓

Allow
```

---

Easy way to remember:

```text
Authentication

↓

Who are you?

Authorization

↓

What can you do?
```

---

# Common API Threats

Professional backend engineers assume that clients can send **any request**.

Let's look at common threats.

---

## Unauthorized Access

Attacker tries:

```http
DELETE /posts/25
```

Without logging in.

Protection:

- Authentication
    

---

## Privilege Escalation

Normal user attempts:

```http
DELETE /users/1
```

Protection:

- Authorization
    
- RBAC (Role-Based Access Control)
    

---

## Injection Attacks

Attacker sends malicious input.

Example:

```text
Search query

↓

Malicious payload
```

Protection:

- Input validation
    
- Input sanitization
    
- Parameterized queries
    

We'll study these in Lesson 12.4.

---

## Brute Force

Attacker tries:

```text
Password 1

Password 2

Password 3

...

Password 10000
```

Protection:

- Rate limiting
    
- Account lockout
    
- Strong passwords
    

---

## Token Theft

Attacker steals:

```text
JWT

Refresh Token
```

Protection:

- HTTPS
    
- Secure cookies
    
- Token expiration
    

---

## Denial of Service (DoS)

Attacker floods:

```text
Millions of Requests
```

Protection:

- Rate limiting
    
- Reverse proxy
    
- Load balancer
    

---

# Never Trust the Client

One of the most important backend principles.

Suppose the frontend sends:

```json
{
    "role":"admin"
}
```

Should you trust it?

Never.

Always verify:

- JWT
    
- Database
    
- Permissions
    

The client can be modified.

The server must make security decisions.

# Common Beginner Mistakes

## ❌ Trusting Frontend Validation

Frontend validation improves user experience.

It does **not** provide security.

Always validate again on the server.

---

## ❌ Thinking Login Equals Security

Logging in proves identity.

It doesn't automatically grant permissions.

Authentication ≠ Authorization.

---

## ❌ Adding Security at the End

Security should influence:

- Requirements
    
- Data model
    
- API design
    
- Service design
    

Not just deployment.

---

## ❌ Relying on One Security Feature

JWT alone doesn't secure an application.

Neither does HTTPS.

Professional systems use multiple layers.

# Key Takeaways

- API security protects your application from unauthorized access, malicious actions, and service disruption.
    
- The **CIA Triad**—Confidentiality, Integrity, and Availability—is the foundation of security decisions.
    
- **Authentication** answers "Who are you?" while **Authorization** answers "What are you allowed to do?"
    
- Never trust data sent by the client; always verify it on the server.
    
- Security is most effective when implemented as **Defense in Depth**, with multiple independent layers of protection.
    
- Security should be considered during requirements analysis, API design, and architecture—not added as a final step.
