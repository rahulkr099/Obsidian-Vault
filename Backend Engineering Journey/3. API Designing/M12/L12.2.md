# Lesson 12.2 — Authentication & Session Security

> **Goal:** Learn how professional backend engineers verify user identity and securely manage user sessions in modern web applications.

Authentication is one of the first security features every backend engineer implements. However, production authentication is much more than simply checking an email and password.

- Understand logout, password reset, and email verification

# What is Authentication?

Authentication answers one question:

> **"Who is making this request?"**

Example:

```http
POST /auth/login
```

User sends:

```json
{
  "email": "rahul@example.com",
  "password": "mypassword"
}
```

The server verifies the credentials.

If correct:

The user becomes authenticated.

---

# Authentication Flow

A typical login flow looks like this:

```text
User

↓

Login Request

↓

Controller

↓

Authentication Service

↓

User Repository

↓

Database

↓

Password Verification

↓

Generate Tokens

↓

Response
```

Notice that authentication is a complete workflow—not just one database query.

---

# Why Passwords Should Never Be Stored Directly

Imagine storing passwords like this:

|Email|Password|
|---|---|
|[rahul@example.com](mailto:rahul@example.com)|password123|

If the database is leaked:

Every user's password is exposed.

This is a serious security breach.

---

# Password Hashing

Instead of storing:

```text
password123
```

Store something like:

```text
$2b$12$9Y...
```

This is called a **hash**.

Properties:

- One-way
    
- Cannot be reversed
    
- Same password always verifies correctly
    
- Safe to store in the database
    

---

# Hashing vs Encryption

Many beginners confuse these.

## Hashing

```text
Password

↓

Hash

↓

Cannot Recover Original Password
```

Used for:

- Passwords
    

---

## Encryption

```text
Data

↓

Encrypted

↓

Can Be Decrypted Using a Key
```

Used for:

- Sensitive files
    
- Payment information
    
- Messages
    

Passwords should be **hashed**, not encrypted.

---

# Password Verification

During login:

User enters:

```text
password123
```

Server:

```text
Hash(password123)

↓

Compare with Stored Hash

↓

Match?

↓

Login Success
```

The server never compares plain-text passwords.

---

# bcrypt vs Argon2

Popular password hashing algorithms:

- bcrypt
    
- Argon2
    

Both are designed to be intentionally slow, making brute-force attacks much harder.

Today, **Argon2** is considered more modern, while **bcrypt** remains widely used and trusted.

---

# JWT (JSON Web Token)

After successful login:

The server doesn't ask the user for their password on every request.

Instead:

It creates an **Access Token**.

Example:

```text
User

↓

Login

↓

Access Token

↓

Future Requests
```

Now requests look like:

```http
GET /posts
Authorization: Bearer <access-token>
```

---

# Access Token

Purpose:

Identify the user on future requests.

Contains information such as:

- User ID
    
- Role
    
- Expiration time
    

The server verifies the token instead of asking for credentials again.

---

# Why Tokens Expire

Imagine a token that never expires.

If an attacker steals it:

They can use it forever.

Instead:

```text
Access Token

↓

15 minutes

↓

Expires
```

Short-lived tokens reduce risk.

---

# Refresh Token

Question:

If the Access Token expires every 15 minutes, should users log in repeatedly?

No.

Instead:

```text
Access Token

↓

Expires

↓

Refresh Token

↓

New Access Token
```

Refresh tokens provide a better user experience while maintaining security.

---

# Access Token vs Refresh Token

|Access Token|Refresh Token|
|---|---|
|Short-lived|Long-lived|
|Sent with API requests|Used only to obtain a new Access Token|
|Higher exposure|Better protected|
|Frequent use|Occasional use|

---

# Authentication Flow with Refresh Tokens

```text
Login

↓

Access Token

+

Refresh Token

↓

Client

↓

Access Token Expires

↓

Refresh Endpoint

↓

New Access Token
```

The user stays logged in without re-entering their password.

---

# Where Should Tokens Be Stored?

This depends on your application.

## Option 1 — localStorage

Advantages:

- Easy to use
    

Disadvantages:

- Accessible by JavaScript
    
- More vulnerable to XSS attacks
    

---

## Option 2 — HTTP-Only Secure Cookies

Advantages:

- JavaScript cannot read them
    
- Better protection against XSS
    

Disadvantages:

- Require CSRF protection for some architectures
    

Many production applications store **Refresh Tokens** in **HTTP-only Secure Cookies**.

---

# Logout

Logging out is more than deleting a token on the frontend.

Typical flow:

```text
User

↓

Logout Request

↓

Invalidate Refresh Token

↓

Delete Cookie

↓

Response
```

Now the refresh token can no longer be used.

---

# Password Reset

A secure password reset flow:

```text
User

↓

Forgot Password

↓

Email

↓

Temporary Reset Token

↓

Reset Password

↓

Delete Reset Token
```

Never send passwords through email.

---

# Email Verification

After registration:

```text
Register

↓

Verification Email

↓

Verification Link

↓

Account Activated
```

Benefits:

- Prevent fake accounts
    
- Confirm email ownership
    
- Improve security
    

---

# Authentication Middleware

Authentication should happen before reaching your controller.

```text
Client

↓

Authentication Middleware

↓

Controller

↓

Service

↓

Repository
```

Responsibilities:

- Read the Access Token
    
- Verify it
    
- Identify the current user
    
- Attach the user to the request
    

Controllers should not verify JWTs themselves.

---

# Blog API Example

Protected endpoint:

```http
POST /posts
```

Flow:

```text
Client

↓

JWT

↓

Authentication Middleware

↓

Authenticated User

↓

Post Controller

↓

Post Service

↓

Repository

↓

Database
```

The controller already knows who the user is.

---

# Authentication vs Authorization

Authentication:

```text
Who are you?
```

Authorization:

```text
Can you create this post?
```

Authentication happens first.

Authorization comes next.

---

# Common Beginner Mistakes

## ❌ Storing Plain Passwords

Never store passwords directly.

Always hash them.

---

## ❌ Using JWT Without Expiration

Tokens should always expire.

---

## ❌ Long-Lived Access Tokens

Bad:

```text
Access Token

↓

365 days
```

Good:

```text
15–30 minutes
```

Refresh tokens handle long-term sessions.

---

## ❌ Putting Authentication in Controllers

Bad:

```text
Controller

↓

Verify JWT

↓

Continue
```

Instead:

Use middleware.

---

## ❌ Sending Passwords Back to Clients

Never include passwords—even hashed passwords—in API responses.

---

# Authentication Architecture

```text
Client

↓

Login

↓

Authentication Service

↓

Password Verification

↓

Generate Tokens

↓

Client Stores Tokens

↓

Future Requests

↓

Authentication Middleware

↓

Controller

↓

Service

↓

Repository

↓

Database
```

This is the typical authentication architecture used in production Node.js applications.

---

# Best Practices

✅ Hash passwords with bcrypt or Argon2.

✅ Use short-lived Access Tokens.

✅ Use Refresh Tokens for long-lived sessions.

✅ Store Refresh Tokens securely (commonly in HTTP-only Secure Cookies).

✅ Verify tokens in middleware.

✅ Never expose passwords or sensitive tokens.

✅ Implement secure logout and password reset flows.

# Key Takeaways

- Authentication verifies the identity of the user.
    
- Passwords must always be stored as secure hashes, never as plain text.
    
- Access Tokens identify users during API requests and should be short-lived.
    
- Refresh Tokens allow users to stay logged in without repeatedly entering credentials.
    
- Authentication logic belongs in middleware, keeping controllers clean.
    
- Secure authentication requires careful token management, logout handling, password reset, and email verification.
