# Lesson 12.3 — Authorization & Access Control

> **Goal:** Learn how professional backend engineers decide what an authenticated user is allowed to do.

Authentication answers:

> **"Who are you?"**

Authorization answers:

> **"What are you allowed to do?"**

Many security vulnerabilities happen because authentication is implemented correctly, but authorization is forgotten or implemented incorrectly.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand authorization
    
- Perform ownership checks
    
- Design Role-Based Access Control (RBAC)
    
- Understand Permission-Based Access Control
    
- Protect resources correctly
    
- Know where authorization belongs in your architecture
    

---

# Authentication Comes First

A request arrives:

```http
PATCH /posts/25
```

Authentication verifies:

```text
Rahul
```

Now the server knows **who** made the request.

But another question remains:

```text
Can Rahul edit Post 25?
```

That is authorization.

---

# Authorization Flow

```text
Client

↓

Authentication Middleware

↓

Current User

↓

Authorization

↓

Controller

↓

Service

↓

Repository

↓

Database
```

Authentication identifies the user.

Authorization decides whether the action is allowed.

# Example 1 — Ownership

Requirement:

> Users can edit only their own posts.

Database:

```text
Post

id: 25

authorId: 10
```

Authenticated user:

```text
User ID = 10
```

Result:

```text
Allow
```

---

Another request:

Authenticated user:

```text
User ID = 30
```

Result:

```http
403 Forbidden
```

---

# Ownership Check

The service compares:

```text
Current User ID

↓

Post Author ID

↓

Match?

↓

Yes → Continue

No → 403 Forbidden
```

This is one of the most common authorization rules.

---

# Example 2 — Delete Comment

Requirement:

> Users can delete only their own comments.

Request:

```http

```

Service:

```text
Comment Owner?

↓

Current User?

↓

Yes

↓

Delete
```

Otherwise:

```http
403 Forbidden
```

# Role-Based Access Control (RBAC)

RBAC means:

Permissions are assigned to **roles**, not individual users.

Example:

```text
ADMIN

EDITOR

AUTHOR

USER
```

Each role has different capabilities.

---

Example:

|Action|User|Author|Admin|
|---|:-:|:-:|:-:|
|Read posts|✅|✅|✅|
|Create posts|❌|✅|✅|
|Edit own posts|❌|✅|✅|
|Delete own posts|❌|✅|✅|
|Delete any post|❌|❌|✅|
|Delete users|❌|❌|✅|

RBAC keeps authorization simple.

---

# Resource-Level Authorization

Sometimes a role isn't enough.

Example:

Two authors:

```text
Rahul

Aman
```

Both have:

```text
AUTHOR
```

Rahul still cannot edit Aman's post.

Why?

Because authorization depends on:

- Role
    
- Ownership
    

Both must be checked.

# Permission-Based Access Control

Large applications sometimes use permissions instead of simple roles.

Example:

```text
posts:create

posts:update

posts:delete

users:delete

comments:moderate
```

A role simply becomes a collection of permissions.

Example:

```text
ADMIN

↓

posts:create

posts:update

posts:delete

users:delete

comments:moderate
```

This approach provides more flexibility.

---

# RBAC vs Permissions

RBAC:

```text
Role

↓

Permissions
```

Permission-based:

```text
Check Individual Permission
```

Small projects often start with RBAC.

Large enterprise systems frequently use permissions.

# Where Does Authorization Belong?

Many beginners place authorization inside controllers.

Bad:

```text
Controller

↓

Check User Role

↓

Check Ownership

↓

Update Database
```

Controllers become difficult to maintain.

---

Professional architecture:

```text
Controller

↓

Service

↓

Repository
```

Authorization belongs in the **Service Layer**.

Why?

Because authorization is a **business rule**.

---

# Example

Requirement:

Only premium users can download reports.

Question:

HTTP concern?

Business rule?

Yes.

Service Layer.

# 401 vs 403

A common interview question.

## 401 Unauthorized

Actually means:

```text
Not Authenticated
```

Example:

Missing JWT.

---

## 403 Forbidden

Means:

```text
Authenticated

↓

Permission Denied
```

Example:

Rahul tries to edit Aman's post.

---

Easy way to remember:

```text
401

↓

Who are you?

403

↓

I know who you are.

You still cannot do that.
```

# Common Beginner Mistakes

## ❌ Authorization in Controllers

Move it to the service.

---

## ❌ Trusting User IDs from the Client

Bad:

```json
{
    "userId": 42
}
```

Use the authenticated user from the JWT instead.

---

## ❌ Checking Roles Only

Even if two users share the same role:

```text
AUTHOR
```

Ownership still matters.

---

## ❌ Returning 401 for Permission Problems

Remember:

Missing login:

```http
401 Unauthorized
```

Permission denied:

```http
403 Forbidden
```

# Best Practices

✅ Authenticate before authorizing.

✅ Keep authorization in the Service Layer.

✅ Verify ownership before modifying resources.

✅ Use RBAC for small to medium applications.

✅ Consider permission-based authorization for larger systems.

✅ Never trust role or user information sent by the client.

# Key Takeaways

- Authentication identifies the user; authorization determines what the user is allowed to do.
    
- Authorization rules are business rules and belong in the **Service Layer**.
    
- Ownership checks are one of the most common forms of authorization.
    
- RBAC simplifies authorization by assigning permissions to roles.
    
- Larger systems often use permission-based access control for greater flexibility.
    
- `401 Unauthorized` is used for missing or invalid authentication, while `403 Forbidden` is used when an authenticated user lacks permission.
