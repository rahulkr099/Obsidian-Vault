# Lesson 12.4 — Protecting APIs from Common Attacks

> **Goal:** Learn how professional backend engineers protect APIs against the most common security attacks and understand where each protection belongs in the application architecture.

You don't need to become a security researcher to build secure APIs.

But you **must** understand the attacks your application is exposed to and how to defend against them.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand common API attacks
    
- Know how SQL and NoSQL Injection work
    
- Understand XSS and CSRF
    
- Learn why CORS exists
    
- Understand Rate Limiting
    
- Know the purpose of security headers
    
- Build a defense-in-depth strategy
    

---

# Security Starts Before Code

A professional backend doesn't think:

```text
How do I stop this attack?
```

Instead it asks:

```text
What attacks is this endpoint exposed to?
```

Every endpoint has risks.

Example:

```http
POST /auth/login
```

Possible attacks:

- Brute force
    
- Password guessing
    
- Credential stuffing
    

Different endpoint:

```http
GET /posts
```

Different risks:

- Abuse
    
- Excessive requests
    
- Data scraping
    

Security depends on the business operation.

---

# Attack 1 — SQL Injection

Imagine a login query:

```text
SELECT *

FROM users

WHERE email = ?
```

If developers build queries incorrectly, attackers may inject malicious SQL.

Example input:

```text
' OR 1=1 --
```

Instead of searching for one user, the query logic can be altered.

---

## Protection

Professional applications use:

- Parameterized queries
    
- ORM libraries
    
- Input validation
    

Never build SQL queries by concatenating user input.

---

# Attack 2 — NoSQL Injection

MongoDB applications are also vulnerable.

Suppose the backend accepts arbitrary JSON without validation.

Attacker sends:

```json
{
  "email": {
    "$ne": null
  }
}
```

Instead of checking one email, the query logic changes.

---

## Protection

- Validate request body
    
- Sanitize input
    
- Never trust JSON operators from clients
    
- Use strict schema validation
    

---

# Attack 3 — Cross-Site Scripting (XSS)

Imagine a comment:

```text
Great article!
```

Now imagine:

```html
<script>alert("Hacked")</script>
```

If your application stores and renders this script without escaping or sanitizing it, users who view the page may execute the attacker's code.

---

## Types

### Stored XSS

Stored in the database.

Example:

Blog comments.

---

### Reflected XSS

Returned immediately in the response.

Usually from URL parameters.

---

## Protection

- Sanitize user input
    
- Escape HTML output
    
- Use a Content Security Policy (CSP)
    
- Never trust user-generated HTML
    

---

# Attack 4 — Cross-Site Request Forgery (CSRF)

Imagine you're logged into a banking website.

While still logged in, you visit a malicious website.

That website secretly sends:

```http
POST /transfer
```

Because your browser automatically includes your cookies, the request may appear legitimate.

---

## Protection

- CSRF Tokens
    
- SameSite cookies
    
- Verify Origin or Referer headers
    

If you're using **JWTs in the Authorization header**, CSRF risk is usually much lower than with cookie-based authentication, but it depends on your authentication design.

---

# Attack 5 — Brute Force

Attacker repeatedly tries:

```text
password1

password2

password3

...

password100000
```

Goal:

Guess the password.

---

## Protection

Rate limiting.

Example:

```text
5 login attempts

↓

1 minute wait
```

This dramatically slows attackers.

---

# Attack 6 — Denial of Service (DoS)

Attacker sends:

```text
100,000 requests

per second
```

Server becomes overloaded.

Legitimate users can't access the application.

---

## Protection

- Rate limiting
    
- Reverse proxy (e.g., Nginx)
    
- Load balancers
    
- Auto scaling
    
- Caching
    

---

# Rate Limiting

Example policy:

```text
100 requests

per minute

per IP
```

If exceeded:

```http
429 Too Many Requests
```

Different endpoints can have different limits.

Example:

```http
POST /auth/login
```

Very strict.

---

```http
GET /posts
```

More generous.

---

# CORS (Cross-Origin Resource Sharing)

Imagine:

Frontend:

```text
https://blog.com
```

Backend:

```text
https://api.blog.com
```

Browsers enforce security rules for cross-origin requests.

CORS allows your server to decide:

- Which origins may access it
    
- Which methods are allowed
    
- Which headers are accepted
    

---

## Bad Configuration

```text
Allow Everyone
```

Sometimes acceptable for public APIs, but risky for authenticated applications.

---

## Better

Allow only trusted frontend origins.

Example:

```text
https://blog.com
```

---

# Security Headers

HTTP responses can include headers that improve browser security.

Examples:

- Content Security Policy (CSP)
    
- X-Content-Type-Options
    
- Referrer-Policy
    
- X-Frame-Options
    

In Express, many of these are commonly configured using **Helmet**.

These headers reduce the risk of browser-based attacks.

---

# Input Sanitization

Validation answers:

```text
Is this input valid?
```

Sanitization answers:

```text
Can this input be made safe?
```

Example:

Input:

```text
   Rahul
```

Sanitized:

```text
Rahul
```

Another example:

Remove dangerous HTML before storing comments (depending on your application's requirements).

---

# Validation vs Sanitization

Validation:

```text
Accept

Reject
```

Sanitization:

```text
Clean

Normalize
```

Both are important.

# Common Attack → Protection Matrix

|Attack|Protection|
|---|---|
|SQL Injection|Parameterized queries, ORM, validation|
|NoSQL Injection|Validation, sanitization, strict schemas|
|XSS|Escaping output, sanitization, CSP|
|CSRF|CSRF tokens, SameSite cookies|
|Brute Force|Rate limiting, account lockout|
|DoS|Rate limiting, load balancing|
|Unauthorized Access|Authentication|
|Privilege Escalation|Authorization|

# Common Beginner Mistakes

## ❌ Trusting Client Input

Never assume:

```json
{
  "role": "admin"
}
```

is truthful.

Always verify on the server.

---

## ❌ Disabling CORS Completely

Many beginners allow every origin during development and forget to tighten it before production.

---

## ❌ No Rate Limiting

Without limits:

```http
POST /auth/login
```

can be attacked thousands of times per second.

---

## ❌ Only Validating Input

Validation alone doesn't stop every attack.

Use:

- Validation
    
- Sanitization
    
- Authentication
    
- Authorization
    

Together.

---

## ❌ Exposing Stack Traces

Attackers should never learn:

- File paths
    
- Database names
    
- Internal code
    

Return safe error messages.

---

# Defense in Depth

A secure application doesn't depend on one feature.

Instead:

```text
HTTPS

↓

Rate Limiter

↓

CORS

↓

Authentication

↓

Authorization

↓

Validation

↓

Sanitization

↓

Database Constraints
```

If one layer fails, another still protects the system.

---

# Best Practices

✅ Use parameterized queries or an ORM/ODM.

✅ Validate and sanitize all user input.

✅ Configure CORS carefully.

✅ Apply rate limiting to sensitive endpoints.

✅ Use security headers.

✅ Escape user-generated content before rendering.

✅ Think in terms of multiple security layers.

# Key Takeaways

- Every API endpoint faces different security risks.
    
- SQL and NoSQL Injection are prevented through safe query practices, validation, and sanitization.
    
- XSS is prevented by safely handling user-generated content and using browser security features like CSP.
    
- CSRF primarily affects cookie-based authentication and is mitigated with CSRF tokens and secure cookie settings.
    
- Rate limiting protects against brute-force attacks and request flooding.
    
- CORS controls which browser-based origins may access your API.
    
- Security is strongest when multiple independent defenses work together. This is known as **Defense in Depth**.
