# Lesson 12.5 — Secure API Design

> **Goal:** Learn how to design APIs that are secure by default instead of trying to "add security later."

Many developers think security means:

- JWT ✅
    
- bcrypt ✅
    
- Helmet ✅
    

That's only part of the picture.

Professional backend engineers design **every endpoint** with security in mind.

# Security Starts During API Design

Imagine you are designing:

```http
GET /users/:id
```

Question:

Should every user receive:

```json
{
    "id": 1,
    "name": "Rahul",
    "email": "rahul@example.com",
    "passwordHash": "...",
    "refreshToken": "...",
    "role": "admin"
}
```

Absolutely not.

Good API design includes deciding **what should never leave the server**.

---

# Principle of Least Privilege

One of the most important security principles.

Definition:

> Give users **only the permissions they need**, and nothing more.

Example:

Blog application.

Reader:

Can:

- Read posts
    

Cannot:

- Delete posts
    
- Edit users
    
- Access admin dashboard
    

---

Author:

Can:

- Create posts
    
- Edit own posts
    

Cannot:

- Delete all users
    

---

Admin:

Can:

- Manage users
    
- Moderate comments
    
- Delete any post
    

Every role receives the minimum permissions necessary.

Authentication:

Required.

# Don't Expose Sensitive Data

Imagine:

```http
GET /profile
```

Bad response:

```json
{
  "id": 1,
  "name": "Rahul",
  "email": "rahul@example.com",
  "passwordHash": "...",
  "refreshToken": "...",
  "otp": "123456"
}
```

Never expose:

- Password hashes
    
- Refresh tokens
    
- OTPs
    
- Internal IDs (when unnecessary)
    
- Secret keys
    

Instead:

```json
{
  "id": 1,
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

Return only what the client needs.

---

# Data Minimization

Ask yourself:

> **Does the frontend actually need this field?**

If the answer is:

"No."

Don't return it.

Example:

Instead of:

```json
{
    "id":1,
    "name":"Rahul",
    "createdAt":"...",
    "updatedAt":"...",
    "internalVersion":5,
    "refreshToken":"..."
}
```

Return:

```json
{
    "id":1,
    "name":"Rahul"
}
```

Less data means:

- Better security
    
- Smaller responses
    
- Better performance

# File Upload Security

Suppose users upload profile pictures.

Never trust:

```text
resume.pdf.exe
```

or

```text
virus.png
```

Check:

- File type
    
- MIME type
    
- Maximum size
    
- Allowed extensions
    

Store uploads outside your application code directory when appropriate.

---


# Secret Management

Applications need secrets:

- JWT secret
    
- Database password
    
- API keys
    
- Email credentials
    

Never write:

```text
const JWT_SECRET = "my-secret";
```

inside source code.

Instead:

Use environment variables.

Example:

```text
.env

↓

JWT_SECRET

DATABASE_URL

SMTP_PASSWORD
```

Even better, in production use a dedicated secret manager provided by your cloud platform when available.

---

# Logging Securely

Suppose login fails.

Good log:

```text
Login failed

Email: rahul@example.com

Time: 10:15
```

Bad log:

```text
Password:

secret123
```

Never log:

- Passwords
    
- Access tokens
    
- Refresh tokens
    
- OTPs
    
- Credit card numbers
    

Logs often live for months.

Treat them as sensitive.

---

# Safe Error Messages

Suppose login fails.

Bad:

```text
Email exists.

Password incorrect.
```

Attackers now know:

The email is valid.

Better:

```text
Invalid email or password.
```

Don't leak unnecessary information.

---

# Resource Enumeration

Imagine:

```http
GET /users/1
```

Response:

```http
404 Not Found
```

Another request:

```http
GET /users/2
```

Response:

```http
200 OK
```

Attackers can discover valid users.

Sometimes applications intentionally provide generic responses for sensitive operations to reduce information leakage.

The right approach depends on the business requirements.

---

# Secure Password Reset

Bad flow:

```text
Email

↓

New Password
```

Good flow:

```text
Forgot Password

↓

Temporary Token

↓

Email

↓

Verify Token

↓

Reset Password
```

Passwords should only change after verifying ownership of the account.

---

# HTTPS Everywhere

Never send:

- Passwords
    
- Tokens
    
- Personal information
    

over plain HTTP.

Always use:

```text
HTTPS
```

Encryption protects data while it travels across the network.

# Security Design Checklist

Before creating any endpoint, ask:

### Authentication

Who can access it?

---

### Authorization

Who can perform this action?

---

### Validation

What input must be checked?

---

### Sanitization

Can user input contain dangerous content?

---

### Response

Am I exposing unnecessary data?

---

### Logging

Am I logging sensitive information?

---

### Secrets

Does this endpoint use any API keys or credentials?

---

### Transport

Should this endpoint require HTTPS?

The answer is almost always **yes**.

# Common Beginner Mistakes

## ❌ Returning Entire Database Objects

Return DTOs (Data Transfer Objects) or carefully selected response fields instead of raw database documents.

---

## ❌ Hardcoding Secrets

Never commit:

- API keys
    
- Database passwords
    
- JWT secrets
    

to Git.

---

## ❌ Logging Sensitive Information

Logs are not a secure storage location.

---

## ❌ Allowing Any File Upload

Always validate uploaded files.

---

## ❌ Giving Too Many Permissions

Don't make everyone:

```text
ADMIN
```

Use the Principle of Least Privilege.

---

# Best Practices

✅ Return only the data the client needs.

✅ Keep secrets outside source code.

✅ Use HTTPS everywhere.

✅ Validate uploaded files.

✅ Design secure password reset flows.

✅ Avoid exposing implementation details.

✅ Apply the Principle of Least Privilege.

# Key Takeaways

- Security should be part of API design from the beginning, not added later.
    
- Follow the **Principle of Least Privilege** by granting only the minimum permissions required.
    
- Never expose sensitive data such as password hashes, refresh tokens, or secrets in API responses.
    
- Use environment variables or dedicated secret managers to protect application secrets.
    
- Validate file uploads and never trust user-supplied files.
    
- Log useful operational information, but never log sensitive credentials or tokens.
    
- Design every endpoint by asking what needs protection, who should have access, and what information should be exposed.
