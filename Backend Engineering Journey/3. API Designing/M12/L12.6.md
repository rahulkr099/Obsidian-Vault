# Endpoint 1 — Register

```http
POST /auth/register
```

Authentication:

❌ Not required

Authorization:

❌ Not required

Validation:

✅ Name

✅ Email

✅ Password

Sanitization:

✅ Trim input

Rate Limit:

✅ Strict

Example:

```text
5 requests / minute / IP
```

Reason:

Prevent spam registrations.

---

# Endpoint 2 — Login

```http
POST /auth/login
```

Authentication:

❌ Not required

Authorization:

❌ Not required

Validation:

✅ Email

✅ Password

Rate Limit:

✅ Very strict

Example:

```text
5 login attempts

↓

Temporary cooldown
```

Reason:

Prevent brute-force attacks.

# Middleware Pipeline

A protected endpoint:

```http
PATCH /posts/:id
```

Pipeline:

```text
HTTPS

↓

Rate Limiter

↓

Helmet

↓

CORS

↓

Authentication Middleware

↓

Validation Middleware

↓

Controller

↓

Service
(Authorization)

↓

Repository

↓

Database

↓

Response
```

Notice:

Authorization happens inside the Service Layer because it depends on business rules.

---

# Security Responsibility Matrix

|Layer|Responsibility|
|---|---|
|HTTPS|Encrypt traffic|
|Rate Limiter|Prevent brute force and abuse|
|Helmet|Add browser security headers|
|CORS|Restrict browser origins|
|Authentication Middleware|Verify identity|
|Validation Middleware|Validate request format|
|Controller|Handle HTTP concerns|
|Service|Authorization and business security|
|Repository|Database operations|
|Database|Data integrity constraints|

Each layer contributes to the application's overall security.

# Rate Limiting Strategy

Not every endpoint needs the same limits.

|Endpoint|Suggested Policy|
|---|---|
|`/auth/login`|Very strict|
|`/auth/register`|Strict|
|`/auth/refresh`|Moderate|
|`GET /posts`|Moderate|
|`POST /posts`|Moderate|
|`POST /comments`|Moderate|
|`POST /likes`|Moderate|

High-risk endpoints deserve tighter limits.

---

# CORS Strategy

Frontend:

```text
https://blog.example.com
```

Backend:

```text
https://api.blog.example.com
```

Allow:

- Trusted frontend origins
    
- Required methods
    
- Required headers
    

Avoid using a wildcard (`*`) for authenticated browser applications.

---

# Secure Response Design

Bad:

```json
{
  "passwordHash": "...",
  "refreshToken": "...",
  "otp": "123456"
}
```

Good:

```json
{
  "id": 1,
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

Return only what the client actually needs.

---

# Logging Strategy

Log:

- Login failures (without passwords)
    
- Account lockouts
    
- Admin actions
    
- Post deletions
    
- Database failures
    
- Unexpected exceptions
    

Do **not** log:

- Passwords
    
- JWTs
    
- Refresh tokens
    
- OTPs
    
- API secrets

# Common Beginner Mistakes

## ❌ Protecting Only Admin Endpoints

Even user endpoints require:

- Authentication
    
- Authorization
    
- Validation
    

Security is not just for administrators.

---

## ❌ Same Rate Limit Everywhere

Different endpoints have different risks.

Design rate limits based on the operation.

---

## ❌ Returning Sensitive Information

Never expose:

- Password hashes
    
- Refresh tokens
    
- Internal database fields
    

---

## ❌ Mixing Authentication and Authorization

Remember:

Authentication:

> Who are you?

Authorization:

> What are you allowed to do?

Keep them separate.

---

## ❌ Thinking Security Ends After Login

Authentication is only the beginning.

Every request must continue through:

- Authorization
    
- Validation
    
- Sanitization
    
- Database constraints
