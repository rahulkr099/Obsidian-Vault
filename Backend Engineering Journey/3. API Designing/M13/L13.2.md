# Lesson 13.2 — API Versioning Strategies

> **Goal:** Learn the most common API versioning strategies, understand their trade-offs, and know when to use each one.

There is no single "correct" versioning strategy.

Professional backend engineers choose the approach that best fits their application, team, and clients.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand the major API versioning strategies
    
- Compare URI, Header, Media Type, and Query Parameter versioning
    
- Know the advantages and disadvantages of each
    
- Choose the right strategy for different projects
    
- Understand why most REST APIs use URI versioning
    

---

# Four Common Strategies

Most REST APIs use one of these approaches:

```text
URI Versioning

Header Versioning

Media Type Versioning

Query Parameter Versioning
```

Let's examine each one.

---

# Strategy 1 — URI Versioning

The version is part of the URL.

Example:

```http
GET /api/v1/posts
```

Later:

```http
GET /api/v2/posts
```

---

## Example

Version 1:

```http
GET /api/v1/posts
```

Response:

```json
{
  "title": "REST APIs"
}
```

---

Version 2:

```http
GET /api/v2/posts
```

Response:

```json
{
  "headline": "REST APIs",
  "likes": 120
}
```

Both versions can exist simultaneously.

---

## Advantages

✅ Easy to understand

Clients immediately know:

```text
v1

or

v2
```

---

Easy documentation.

Example:

```text
/docs/v1

/docs/v2
```

---

Easy testing.

Postman collections are straightforward.

---

Simple routing.

Example:

```text
/api/v1

↓

Controller V1

/api/v2

↓

Controller V2
```

---

## Disadvantages

URLs change.

Some developers argue:

A resource shouldn't change its URI simply because its representation changes.

---

# Strategy 2 — Header Versioning

Version is sent inside an HTTP header.

Example:

```http
GET /posts

API-Version: 2
```

The URL remains the same.

---

Another example:

```http
GET /posts

X-API-Version: 2
```

---

## Advantages

Clean URLs.

```http
GET /posts
```

never changes.

---

Version information stays in headers.

Resources remain consistent.

---

## Disadvantages

Harder to discover.

Looking only at the URL doesn't reveal the version.

Testing tools require additional header configuration.

Documentation is slightly more complex.

---

# Strategy 3 — Media Type Versioning

Version is encoded inside the `Accept` header.

Example:

```http
GET /posts
Accept: application/vnd.blog.v2+json
```

The server returns the appropriate representation.

---

## Advantages

Follows HTTP content negotiation principles.

Useful when multiple representations of the same resource are supported.

---

## Disadvantages

Not beginner-friendly.

Harder to read.

Harder to debug.

More complicated for frontend developers.

---

# Strategy 4 — Query Parameter Versioning

Version appears in the query string.

Example:

```http
GET /posts?version=2
```

---

## Advantages

Easy to implement.

Simple for experimentation.

---

## Disadvantages

Version becomes optional.

Some clients may forget it.

Caching systems may become more complex.

Generally not preferred for long-term public APIs.

---

# Comparing the Strategies

|Strategy|Example|
|---|---|
|URI|`/api/v2/posts`|
|Header|`API-Version: 2`|
|Media Type|`Accept: application/vnd.blog.v2+json`|
|Query Parameter|`/posts?version=2`|

---

|Strategy|Easy to Read|Easy to Test|Popular|
|---|:-:|:-:|:-:|
|URI|✅|✅|⭐⭐⭐⭐⭐|
|Header|❌|⚠️|⭐⭐⭐|
|Media Type|❌|⚠️|⭐⭐|

# Which One Should You Choose?

It depends.

---

## Internal APIs

Small company.

Single frontend.

Header versioning can work well.

---

## Public REST APIs

Most companies choose:

```text
/api/v1
```

Why?

Simple.

Easy to understand.

Easy to document.

---

## Enterprise APIs

Some organizations prefer:

Header

or

Media Type

because they align more closely with HTTP standards and keep resource URLs stable.

---

# Real Blog Example

Current endpoint:

```http
GET /api/v1/posts
```

Later:

Need new response.

Create:

```http
GET /api/v2/posts
```

The frontend chooses when to migrate.

No existing application breaks.

---

# Migration Strategy

Suppose:

Today:

```text
v1
```

Tomorrow:

```text
v2
```

Professional rollout:

```text
Release v2

↓

Keep v1 Running

↓

Update Documentation

↓

Clients Migrate

↓

Deprecate v1

↓

Remove v1
```

Avoid forcing all clients to upgrade immediately.

---

# Routing Example

URI versioning often leads to routing like:

```text
/api/v1

↓

V1 Controllers

↓

V1 Services
```

---

```text
/api/v2

↓

V2 Controllers

↓

V2 Services
```

Repositories and database models are often shared where possible.

---

# Do You Always Need a New Version?

No.

Suppose:

Current response:

```json
{
  "title": "REST APIs"
}
```

New response:

```json
{
  "title": "REST APIs",
  "likes": 100
}
```

Breaking?

No.

Keep:

```text
v1
```

No new version needed.

---

# Real Startup Example

Imagine your **Todo API**.

Old:

```json
{
    "title":"Learn Express"
}
```

New requirement:

Priority.

New response:

```json
{
    "title":"Learn Express",
    "priority":"High"
}
```

Existing clients ignore unknown fields.

No new version required.

---

Later:

Rename:

```text
title
```

to

```text
taskName
```

Breaking.

Now:

Create:

```text
v2
```

# Common Beginner Mistakes

## ❌ Creating v2 for Every New Feature

Adding optional fields usually doesn't require a new version.

---

## ❌ Never Versioning

Eventually:

Breaking changes become unavoidable.

Without versioning:

Clients unexpectedly fail.

---

## ❌ Supporting Many Versions Forever

Supporting:

```text
v1

v2

v3

v4

v5
```

creates significant maintenance overhead.

Plan for deprecation.

---

## ❌ Mixing Strategies

Avoid:

```http
GET /api/v2/posts?version=3
```

Choose one primary strategy and use it consistently.

# Best Practices

✅ Prefer URI versioning for most REST APIs.

✅ Keep versioning consistent across the entire API.

✅ Version only for breaking changes.

✅ Support old versions during migration.

✅ Clearly document version differences.

# Key Takeaways

- API versioning strategies determine how clients request different versions of an API.
    
- **URI versioning** (`/api/v1/...`) is the most common and practical choice for REST APIs because it is easy to understand, document, and test.
    
- **Header** and **Media Type** versioning keep URLs stable but increase complexity.
    
- **Query parameter** versioning is simple but is generally less suitable for long-term API evolution.
    
- New API versions should be introduced only for **breaking changes**.
    
- A clear migration and deprecation strategy is just as important as choosing a versioning method.
