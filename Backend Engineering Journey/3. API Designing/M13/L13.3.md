# Version 1

Suppose your Blog API starts with:

```http
GET    /api/v1/posts
GET    /api/v1/posts/:id

POST   /api/v1/posts
PATCH  /api/v1/posts/:id
DELETE /api/v1/posts/:id
```

Response:

```json
{
    "id": 25,
    "title": "REST APIs",
    "content": "...",
    "author": "Rahul"
}
```

Everything works.

The frontend is deployed.

Mobile applications are deployed.

Third-party developers integrate your API.

---

# Six Months Later

The product team requests:

- Categories
    
- Tags
    
- Reactions
    
- Author object
    
- Cursor pagination
    

Should you immediately modify every endpoint?

No.

Let's evaluate each change.

---

# Change 1 — Add Likes

Current response:

```json
{
    "id": 25,
    "title": "REST APIs"
}
```

New response:

```json
{
    "id": 25,
    "title": "REST APIs",
    "likes": 150
}
```

Breaking?

❌ No.

Existing clients ignore the new field.

Stay on:

```text
v1
```

---

# Change 2 — Add Tags

Current:

```json
{
    "title": "REST APIs"
}
```

New:

```json
{
    "title": "REST APIs",
    "tags": [
        "backend",
        "nodejs"
    ]
}
```

Breaking?

❌ No.

No new version.

---

# Change 3 — Rename Title

Current:

```json
{
    "title": "REST APIs"
}
```

New:

```json
{
    "headline": "REST APIs"
}
```

Breaking?

✅ Yes.

Frontend:

```javascript
post.title
```

Now fails.

Need:

```text
/api/v2
```

---

# Change 4 — Nested Author

Current:

```json
{
    "author": "Rahul"
}
```

New:

```json
{
    "author": {
        "id": 1,
        "name": "Rahul"
    }
}
```

Breaking?

Usually **Yes**.

The response structure changes.

Existing clients must update.

---

# Change 5 — Pagination

Current:

```http
GET /api/v1/posts?page=2
```

Business wants:

Cursor pagination.

```http
GET /api/v2/posts?cursor=abc123
```

Breaking?

Yes.

Different pagination model.

---

# Version 2

Now the API becomes:

```http
GET /api/v2/posts

POST /api/v2/posts

PATCH /api/v2/posts/:id

DELETE /api/v2/posts/:id
```

Response:

```json
{
    "id": 25,
    "headline": "REST APIs",
    "author": {
        "id": 1,
        "name": "Rahul"
    },
    "likes": 150,
    "tags": [
        "backend"
    ]
}
```

Version 1 still exists.

# Supporting Multiple Versions

Professional APIs often support:

```text
v1

v2
```

at the same time.

Example:

```text
/api/v1/posts

↓

Old Frontend
```

---

```text
/api/v2/posts

↓

New Frontend
```

Both continue working.

---

# Routing Strategy

Your routing may look like:

```text
Routes

├── v1/
│   ├── posts
│   └── auth
│
└── v2/
    ├── posts
    └── auth
```

Each version has its own routing layer.

---

# Can Code Be Shared?

Yes.

Example:

```text
v1 Controller

↓

Shared Service

↓

Shared Repository
```

Only the response formatting differs.

---

Sometimes:

```text
v2 Controller

↓

Shared Service

↓

Shared Repository
```

This minimizes duplicated code.

---

# When Should Code Be Separate?

Suppose:

Version 2 introduces:

- New business rules
    
- New database queries
    
- New validation
    

Now:

```text
v1 Service

↓

Repository
```

and

```text
v2 Service

↓

Repository
```

may need separate implementations.

Share code where practical, but don't force it.

---

# Deprecation Strategy

Never remove:

```text
v1
```

overnight.

Instead:

```text
Release v2

↓

Recommend Migration

↓

Continue Supporting v1

↓

Announce End-of-Life

↓

Retire v1
```

This gives clients time to upgrade.

---

# Documentation

Document each version separately.

Example:

```text
/docs/v1

/docs/v2
```

Include:

- Endpoints
    
- Request examples
    
- Response examples
    
- Migration notes
    

Clients should understand exactly what changed.

---

# Migration Guide

Professional teams publish migration guides.

Example:

```
Version 2 Changes

• title → headline

• author is now an object

• Added likes

• Cursor pagination replaces page pagination
```

Migration documentation saves client developers time.

# Version Decision Matrix

|Change|New Version?|
|---|:-:|
|Add optional field|❌|
|Add optional query parameter|❌|
|Rename field|✅|
|Remove field|✅|
|Change data type|✅|
|Change authentication requirements|Usually ✅|
|Change endpoint URL|✅|
|Fix internal bug|❌|

# Common Beginner Mistakes

## ❌ Breaking Clients Without Notice

Changing response fields unexpectedly can break production applications.

---

## ❌ Copying the Entire Project

Don't duplicate everything for every version.

Share:

- Repository
    
- Database
    
- Utilities
    
- Middleware
    

Separate only what actually changes.

---

## ❌ Supporting Every Version Forever

Old versions consume:

- Development time
    
- Testing effort
    
- Security maintenance
    

Eventually retire them.

---

## ❌ Forgetting Documentation

Every version should have clear documentation and migration instructions.

# Complete API Evolution Pipeline

```text
New Requirement

↓

Analyze Change

↓

Breaking?

├── No
│     ↓
│  Backward-Compatible Update
│
└── Yes
      ↓
Create v2

↓

Update Documentation

↓

Release

↓

Support v1 + v2

↓

Migration

↓

Deprecation

↓

Retire v1
```

This decision process is followed in many production APIs.

---

# Best Practices

✅ Prefer backward-compatible changes whenever possible.

✅ Create a new version only for breaking changes.

✅ Keep old versions available during migration.

✅ Share business logic between versions when appropriate.

✅ Publish migration guides.

✅ Clearly communicate deprecation timelines.
