# What is OpenAPI?

The **OpenAPI Specification (OAS)** is a standard format for describing REST APIs.

Think of it as a blueprint for your API.

Instead of writing documentation manually in a Word document or README, you describe your API in a structured format.

Example:

```text
API

↓

OpenAPI Specification

↓

Interactive Documentation
```

---

# What is Swagger?

Many beginners think:

Swagger = OpenAPI

Not exactly.

Originally:

- Swagger was both the specification and the tooling.
    

Today:

- **OpenAPI** is the specification (the standard).
    
- **Swagger UI** is one of the most popular tools for displaying OpenAPI documentation.
    

---

# Easy Way to Remember

```text
OpenAPI

↓

The Specification

(Description)
```

```text
Swagger UI

↓

The Viewer

(User Interface)
```

Think of it like this:

- OpenAPI = the book
    
- Swagger UI = the reader
    

---

# Why Use OpenAPI?

Without OpenAPI:

Documentation is often:

- Written manually
    
- Inconsistent
    
- Outdated
    

---

With OpenAPI:

You describe the API once.

Then tools can automatically generate:

- Interactive documentation
    
- Client SDKs
    
- Validation rules
    
- API testing tools
    

---

# OpenAPI Describes Everything

A complete specification describes:

```text
API Information

↓

Endpoints

↓

Parameters

↓

Request Bodies

↓

Responses

↓

Authentication

↓

Errors

↓

Schemas
```

Everything about the API is in one place.

---

# Basic Structure

An OpenAPI document typically contains sections such as:

```text
API Info

↓

Servers

↓

Paths

↓

Components

↓

Security

↓

Tags
```

Let's understand each.

---

# 1. API Information

General information.

Example:

```text
Blog API

Version 1.0

Description
```

Helps developers understand:

- API name
    
- Current version
    
- Purpose
    

---

# 2. Servers

Describes where the API is hosted.

Example:

```text
Development

Production

Staging
```

Clients know which server to use.

---

# 3. Paths

Every endpoint is documented.

Example:

```http
GET /posts

POST /posts

PATCH /posts/{id}
```

Each endpoint includes detailed information.

---

# 4. Parameters

OpenAPI documents every parameter.

Examples:

Path:

```http
/posts/{id}
```

Query:

```http
?page=2
```

Headers:

```http
Authorization
```

Clients immediately know what is required.

---

# 5. Request Body

Example:

```http
POST /posts
```

OpenAPI documents:

```json
{
  "title": "...",
  "content": "...",
  "category": "..."
}
```

It also explains:

- Required fields
    
- Optional fields
    
- Data types
    

---

# 6. Responses

Every success response is documented.

Example:

```http
201 Created
```

Body:

```json
{
  "id": 25,
  "title": "REST APIs"
}
```

---

Error responses are also documented.

Example:

```http
404 Not Found
```

Body:

```json
{
  "success": false,
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "Post not found."
  }
}
```

---

# 7. Authentication

OpenAPI explains:

Which endpoints require:

```text
JWT
```

Example:

```http
Authorization:

Bearer <token>
```

Frontend developers immediately understand how to authenticate requests.

---

# 8. Components

Many APIs repeat the same objects.

Example:

User:

```json
{
    "id":1,
    "name":"Rahul"
}
```

Instead of rewriting it everywhere:

OpenAPI allows reusable components.

Benefits:

- Less duplication
    
- Easier maintenance
    
- Consistency
    

---

# 9. Tags

Large APIs become easier to navigate.

Example:

```text
Authentication

Posts

Comments

Likes

Users
```

Swagger UI groups endpoints using these tags.

---

# Interactive Documentation

One of Swagger UI's biggest strengths:

You can:

- Read the documentation
    
- Enter parameters
    
- Send requests
    
- See responses
    

All from your browser.

This is why many developers use Swagger UI during development and testing.

---

# Blog API Example

Suppose your Blog API has:

```http
POST /posts
```

Swagger UI can display:

Purpose:

```text
Create a new blog post.
```

Authentication:

```text
Required
```

Request Example:

```json
{
  "title": "Learning Express",
  "content": "...",
  "category": "Backend"
}
```

Responses:

```http
201 Created

400 Bad Request

401 Unauthorized

409 Conflict
```

Everything appears in one interactive page.

# Common Beginner Mistakes

## ❌ Confusing Swagger with OpenAPI

Remember:

OpenAPI:

The specification.

Swagger UI:

One tool that displays it.

---

## ❌ Documenting Only Successful Responses

Every endpoint should also document:

```http
400

401

403

404

409

422

500
```

---

## ❌ Repeating Schemas

Don't copy the same User object dozens of times.

Use reusable components.

---

## ❌ Forgetting Authentication

Protected endpoints should clearly document:

```http
Authorization:

Bearer Token
```

---

## ❌ Outdated Documentation

An OpenAPI document should evolve together with the API.

---

# Best Practices

✅ Use the OpenAPI Specification as the single source of truth.

✅ Organize endpoints with tags.

✅ Reuse schemas through components.

✅ Document both success and error responses.

✅ Clearly document authentication requirements.

✅ Keep the specification synchronized with the implementation.

# Key Takeaways

- The **OpenAPI Specification (OAS)** is the industry standard for describing REST APIs.
    
- **Swagger UI** is a popular tool that renders OpenAPI specifications as interactive documentation.
    
- An OpenAPI document describes endpoints, parameters, request bodies, responses, authentication, and reusable schemas.
    
- Interactive documentation helps developers understand and test APIs without reading backend code.
    
- Reusable components reduce duplication and improve consistency across large APIs.
    
- Keeping the OpenAPI specification synchronized with the implementation ensures reliable and trustworthy documentation.
