# Lesson 14.3 — Writing Professional API Documentation

> **Goal:** Learn how to write API documentation that is clear, practical, and useful for frontend developers, mobile developers, QA engineers, and third-party developers.

Knowing **OpenAPI** and **Swagger** is only half the job.

The other half is writing documentation that answers developers' questions before they have to ask them.

Professional documentation is about **clarity**, not just completeness.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Write clear endpoint documentation
    
- Document requests and responses effectively
    
- Document authentication and authorization
    
- Explain errors and status codes
    
- Write useful examples
    
- Organize documentation professionally
    

---

# Every Endpoint Should Tell a Story

When someone opens your documentation, they should immediately understand:

- What does this endpoint do?
    
- Who can use it?
    
- What should I send?
    
- What will I receive?
    
- What can go wrong?
    

If any of these questions remain unanswered, the documentation is incomplete.

---

# A Standard Documentation Template

For every endpoint, document the following sections:

```text
Purpose

↓

HTTP Method

↓

URL

↓

Authentication

↓

Path Parameters

↓

Query Parameters

↓

Request Body

↓

Success Response

↓

Error Responses

↓

Example Request

↓

Example Response

↓

Notes
```

This structure works for almost every REST API.

---

# Example Endpoint

```http
POST /posts
```

---

## 1. Purpose

Don't write:

```text
Create post.
```

Better:

```text
Creates a new blog post for the authenticated user.
```

Explain the business purpose, not just the technical action.

---

## 2. HTTP Method

Document:

```http
POST
```

And explain why.

Example:

> Creates a new resource.

---

## 3. URL

```http
POST /posts
```

Keep endpoint names consistent with the rest of the API.

---

## 4. Authentication

Clearly state:

```text
Authentication Required

Bearer Token
```

If public:

```text
No authentication required.
```

Never make developers guess.

---

# Documenting Parameters

## Path Parameters

Example:

```http
GET /posts/{id}
```

Document:

|Parameter|Type|Description|
|---|---|---|
|id|Integer|Unique identifier of the post|

---

## Query Parameters

Example:

```http
GET /posts?page=2&limit=10&sort=newest
```

Document each one.

|Parameter|Required|Description|
|---|:-:|---|
|page|No|Page number|
|limit|No|Number of results|
|sort|No|Sorting order|

Include:

- Default values
    
- Allowed values
    
- Maximum limits
    

---

# Request Body Documentation

Example:

```json
{
  "title": "Learning Express",
  "content": "...",
  "category": "Backend"
}
```

Document every field.

|Field|Type|Required|Description|
|---|---|:-:|---|
|title|String|✅|Post title|
|content|String|✅|Main article content|
|category|String|✅|Post category|

Also mention validation rules.

Example:

```text
Title

Required

Maximum 150 characters
```

---

# Response Documentation

Document successful responses.

Example:

```http
201 Created
```

Response:

```json
{
  "id": 25,
  "title": "Learning Express",
  "author": "Rahul"
}
```

Explain important fields.

---

# Error Documentation

Many APIs only document success.

Professional APIs document failures too.

Example:

|Status|Meaning|
|---|---|
|400|Validation failed|
|401|Authentication required|
|403|Permission denied|
|404|Post not found|
|409|Duplicate resource|
|500|Internal server error|

---

Include example errors.

Example:

```json
{
  "success": false,
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "Post not found."
  }
}
```

---

# Document Authentication

Example:

```http
Authorization:

Bearer <access-token>
```

Also explain:

- How to obtain the token
    
- Which endpoints require it
    
- What happens if it's missing
    

---

# Document Pagination

Example:

```http
GET /posts?page=2&limit=20
```

Explain:

- Default page size
    
- Maximum limit
    
- Pagination metadata
    

Example response:

```json
{
  "data": [],
  "pagination": {
    "page": 2,
    "limit": 20,
    "totalPages": 8
  }
}
```

If using cursor pagination, explain how the cursor works.

---

# Document Filtering and Sorting

Example:

```http
GET /posts?category=Backend&sort=newest
```

Explain:

Allowed values.

Example:

```text
Sort

newest

oldest

popular
```

This prevents incorrect requests.

---

# Document Versioning

If multiple API versions exist:

Document them separately.

Example:

```text
/api/v1

/api/v2
```

Also explain:

What changed between versions.

Migration notes help developers upgrade more easily.

---

# Write Good Examples

Examples should look realistic.

Bad:

```json
{
    "title":"abc"
}
```

Good:

```json
{
  "title": "Learning Express Middleware",
  "content": "Middleware executes before controllers...",
  "category": "Backend"
}
```

Realistic examples improve understanding.

---

# Add Notes When Needed

Some business rules aren't obvious.

Example:

```text
Only the post owner or an administrator can update a post.
```

Another:

```text
Published posts cannot be edited after 24 hours.
```

These rules are valuable to API consumers.

---

# Organizing Large Documentation

Group related endpoints.

Example:

```text
Authentication

↓

Posts

↓

Comments

↓

Likes

↓

Users

↓

Errors

↓

Pagination
```

Developers find endpoints much faster.

# Common Documentation Mistakes

## ❌ Missing Examples

Developers often understand examples faster than descriptions.

Always include sample requests and responses.

---

## ❌ Documenting Only Happy Paths

Also explain:

- Validation errors
    
- Authorization failures
    
- Missing resources
    

---

## ❌ Using Internal Terminology

Instead of:

```text
Execute PostService.create()
```

Write:

```text
Creates a new blog post.
```

Documentation should describe behavior, not implementation.

---

## ❌ Forgetting Business Rules

If only administrators can delete users:

Document it.

Don't expect developers to discover it through trial and error.

---

## ❌ Inconsistent Documentation

If one endpoint documents authentication and another doesn't, developers become confused.

Use the same structure everywhere.

# Professional Documentation Checklist

For every endpoint, verify:

### Purpose

Is the business goal explained?

---

### Authentication

Is it clear whether authentication is required?

---

### Parameters

Are all path and query parameters documented?

---

### Request Body

Are all fields explained?

---

### Validation

Are constraints documented?

---

### Responses

Are both success and error responses included?

---

### Examples

Are realistic examples provided?

---

### Business Rules

Have important rules been explained?

If the answer to all is **Yes**, your documentation is production-ready.

---

# Best Practices

✅ Use a consistent structure for every endpoint.

✅ Write from the API consumer's perspective.

✅ Include realistic request and response examples.

✅ Document authentication and authorization requirements.

✅ Explain validation rules and business constraints.

✅ Keep documentation synchronized with API changes.

# Key Takeaways

- Professional API documentation should answer what an endpoint does, how to use it, and what to expect.
    
- Every endpoint should consistently document its purpose, parameters, request body, responses, errors, and examples.
    
- Realistic examples make documentation significantly easier to understand.
    
- Business rules and authorization requirements are just as important as technical details.
    
- Organizing documentation into logical sections improves navigation for large APIs.
    
- Great documentation focuses on helping API consumers succeed without needing to read backend code.
