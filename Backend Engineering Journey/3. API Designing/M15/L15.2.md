# Lesson 15.2 — Optimizing API Responses

> **Goal:** Learn how to design API responses that are small, efficient, and fast by sending only the data the client actually needs.

A common mistake beginners make is thinking:

> **"The database query is fast, so my API is optimized."**

But performance also depends on **how much data you return** and **how often you send it**.

A well-designed response can significantly reduce:

- Response time
    
- Bandwidth usage
    
- Server load
    
- Client processing time
    

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Avoid over-fetching
    
- Return only required fields
    
- Design efficient pagination
    
- Use response compression
    
- Understand ETags
    
- Understand Conditional Requests
    
- Optimize API responses
    

---

# The Problem: Over-Fetching

Suppose the homepage displays:

```text
10 blog posts
```

Each card shows:

- Title
    
- Author
    
- Published Date
    

---

Your API returns:

```json
{
  "id": 1,
  "title": "...",
  "content": "...",
  "author": "...",
  "comments": [...],
  "likes": 240,
  "updatedAt": "...",
  "createdAt": "...",
  "tags": [...],
  "draft": false,
  "seo": {...}
}
```

Most of this data is never displayed.

This is called **over-fetching**.

---

# Return Only What the Client Needs

Homepage:

```http
GET /posts
```

Return:

```json
{
  "id": 1,
  "title": "Learning Express",
  "author": "Rahul",
  "publishedAt": "2026-08-04"
}
```

---

Post Details Page:

```http
GET /posts/1
```

Now return:

```json
{
  "id": 1,
  "title": "...",
  "content": "...",
  "author": {...},
  "comments": [...],
  "likes": 250
}
```

Different screens often require different amounts of data.

---

# Field Selection

Sometimes clients should choose which fields they need.

Example:

```http
GET /posts?fields=title,author
```

Response:

```json
{
  "title": "Learning Express",
  "author": "Rahul"
}
```

Another request:

```http
GET /posts?fields=title,likes
```

Response:

```json
{
  "title": "Learning Express",
  "likes": 250
}
```

Benefits:

- Smaller responses
    
- Less bandwidth
    
- Faster parsing
    

---

# Pagination

Never return every record.

Bad:

```http
GET /posts
```

Returns:

```text
100,000 posts
```

Very slow.

---

Better:

```http
GET /posts?page=1&limit=10
```

Response:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 10
  }
}
```

The server sends only what the client needs now.

---

# Choose Sensible Limits

Avoid allowing:

```http
GET /posts?limit=100000
```

Instead:

Set a maximum.

Example:

```text
Default:

10

Maximum:

100
```

This protects your API.

---

# Filtering

Instead of returning everything:

```http
GET /posts
```

Allow filtering.

Example:

```http
GET /posts?category=Backend
```

Now the server returns only relevant data.

Benefits:

- Less data transfer
    
- Faster queries
    
- Better user experience
    

---

# Sorting

Example:

```http
GET /posts?sort=newest
```

or

```http
GET /posts?sort=popular
```

Sorting on the server is usually more efficient than returning everything and letting the client sort.

---

# Response Compression

Text-based responses compress very well.

Instead of sending:

```text
150 KB
```

Compression may reduce it to:

```text
35 KB
```

Common algorithms:

- Gzip
    
- Brotli
    

Most production servers enable compression automatically for appropriate content types.

---

# Benefits of Compression

Without compression:

```text
150 KB

↓

Network
```

---

With compression:

```text
35 KB

↓

Network
```

Smaller payloads generally mean faster transfers, especially on slower connections.

---

# ETags

Imagine:

```http
GET /posts
```

The response hasn't changed.

Should the server resend everything?

Not necessarily.

The server can include an **ETag**.

Think of it as a fingerprint for the response.

Example:

```text
ETag:

abc123xyz
```

---

# Conditional Requests

The client stores:

```text
ETag:

abc123xyz
```

Later it asks:

```http
GET /posts
If-None-Match: abc123xyz
```

The server checks.

If nothing changed:

```http
304 Not Modified
```

No response body is sent.

This saves:

- Bandwidth
    
- Processing time
    

---

# Without ETags

```text
Client

↓

GET /posts

↓

Full Response

↓

Again

↓

Full Response

↓

Again

↓

Full Response
```

---

# With ETags

```text
Client

↓

GET /posts

↓

Full Response

↓

Next Request

↓

304 Not Modified
```

Much less data travels across the network.

---

# Avoid Large Nested Objects

Bad:

```json
{
  "post": {
    "comments": [
      {
        "user": {
          "profile": {
            ...
```

Huge responses become slow.

Instead:

Return only what's needed.

Allow clients to request additional resources separately when appropriate.

---

# Optimize Response Structure

Good:

```json
{
  "data": [],
  "pagination": {}
}
```

Avoid deeply nested structures unless they provide real value.

Simple responses are:

- Faster to serialize
    
- Easier to parse
    
- Easier to maintain

# Response Optimization Pipeline

```text
Client

↓

Pagination

↓

Filtering

↓

Sorting

↓

Field Selection

↓

Compression

↓

ETag

↓

```

Each step contributes to a smaller and faster response.

# Common Beginner Mistakes

## ❌ Returning Entire Documents

Don't send every database field by default.

Return only what the client needs.

---

## ❌ No Pagination

Returning thousands of records:

- Slows the server
    
- Slows the client
    
- Wastes bandwidth
    

---

## ❌ No Compression

Large JSON responses consume unnecessary bandwidth.

Enable compression in production.

---

## ❌ Ignoring Browser Caching

Without ETags:

Clients repeatedly download unchanged data.

---

## ❌ Unlimited Query Parameters

Never allow:

```http
limit=1000000
```

Always enforce sensible limits.

---

# Response Optimization Checklist

Before exposing an endpoint, ask:

### Does the client need every field?

---

### Should field selection be supported?

---

### Should pagination be used?

---

### Should filtering reduce unnecessary data?

---

### Should sorting happen on the server?

---

### Should responses be compressed?

---

### Would ETags improve repeated requests?

If the answer is **Yes**, apply the appropriate optimization.

---

# Best Practices

✅ Return only the data required by the client.

✅ Use pagination for collection endpoints.

✅ Support filtering and sorting when appropriate.

✅ Compress large responses with Gzip or Brotli.

✅ Use ETags and Conditional Requests for cacheable resources.

✅ Set reasonable limits on response size.

---

# Key Takeaways

- API response optimization is about reducing unnecessary work and unnecessary data transfer.
    
- Avoid over-fetching by returning only the fields the client needs.
    
- Pagination is essential for collection endpoints.
    
- Filtering, sorting, and field selection improve efficiency and flexibility.
    
- Compression reduces response size and improves network performance.
    
- ETags and Conditional Requests prevent sending unchanged data repeatedly.
    
- Efficient response design improves performance for both the server and the client.
