# Lesson 15.3 — Database Performance

> **Goal:** Learn how to optimize database access, identify slow queries, and understand why the database is usually the biggest performance bottleneck in backend applications.

A common misconception is:

> **"Express is slow."**

In reality, for most backend applications, Express spends only a few milliseconds processing a request.

The database often consumes **80–95% of the total response time**.

If you optimize your database access, your API usually becomes much faster.

---

By the end of this lesson, you will be able to:

- Understand why databases become bottlenecks

# Where Does Time Go?

Imagine this request:

```http
GET /posts
```

Measured timings:

|Layer|Time|
|---|---|
|Authentication|3 ms|
|Validation|2 ms|
|Controller|4 ms|
|Service|8 ms|
|Database|650 ms|
|Response|15 ms|

Total:

```text
682 ms
```

Notice:

Almost all of the time is spent in the database.

---

# Why Databases Become Slow

Common reasons:

- Missing indexes
    
- Returning too much data
    
- Full table scans
    
- Too many queries
    
- Complex joins/aggregations
    
- Fetching related data inefficiently
    

---

# Selecting Only Required Fields

Suppose your homepage shows:

- Title
    
- Author
    
- Published Date
    

Your query should fetch only those fields.

Bad:

```text
SELECT *

FROM posts
```

This retrieves every column.

---

Better:

```text
SELECT

title,

author,

published_at
```

Only the required data is loaded.

---

## MongoDB Example

Instead of retrieving the entire document, project only the fields you need.

Example conceptually:

```text
Find posts

↓

Return title

Return author

Return publishedAt
```

This reduces:

- Memory usage
    
- Network traffic
    
- Serialization time
    

---

# Indexes

An index helps the database find records quickly.

Imagine a book.

Without an index:

```text
Page 1

↓

Page 2

↓

Page 3

↓

...

↓

Page 700
```

You search every page.

---

With an index:

```text
Index

↓

Page 423
```

The answer is found much faster.

---

# Blog Example

Endpoint:

```http
GET /posts?category=Backend
```

Without an index:

```text
Check

Post 1

Post 2

Post 3

...

Post 500,000
```

---

With an index:

```text
Category Index

↓

Backend Posts
```

Much less work.

---

# What Should Be Indexed?

Frequently searched fields.

Examples:

```text
slug

email

category

createdAt

userId
```

Examples from your Blog API:

|Endpoint|Useful Index|
|---|---|
|`/posts/:slug`|slug|
|`/posts?category=Backend`|category|
|`/users/:id/posts`|authorId|
|Login|email|

Don't index every field.

Indexes improve reads but increase storage and slow writes slightly.

---

# Full Table Scan

Suppose you have:

```text
1,000,000 posts
```

Query:

```http
GET /posts?author=Rahul
```

Without an index:

```text
Read

1

2

3

...

1,000,000
```

That's called a **Full Table Scan** (or full collection scan in document databases).

It is expensive.

---

# N+1 Query Problem

One of the most common backend performance issues.

Imagine:

```http
GET /posts
```

Returns:

```text
10 posts
```

For every post:

Fetch author.

The server performs:

```text
1 Query

↓

Posts
```

Then:

```text
10 Queries

↓

Authors
```

Total:

```text
11 Queries
```

---

Now imagine:

```text
100 posts
```

Now:

```text
101 Queries
```

Performance drops quickly.

---

# Better Approach

Instead of:

```text
Posts

↓

Author

↓

Author

↓

Author
```

Fetch related data efficiently using joins, population, batching, or aggregation—depending on your database.

Result:

Far fewer database round trips.

---

# Pagination Helps the Database

Bad:

```http
GET /posts
```

Returns:

```text
200,000 posts
```

Database:

Works hard.

Network:

Works hard.

Client:

Works hard.

---

Better:

```http
GET /posts?page=1&limit=10
```

Much less work.

Pagination improves performance across the entire system.

---

# Sorting

Suppose:

```http
GET /posts?sort=newest
```

Sorting large datasets without an appropriate index can be expensive.

Frequently sorted fields should often be indexed.

Examples:

```text
createdAt

publishedAt

views
```

---

# Filtering

Instead of:

```http
GET /posts
```

Return everything.

Use:

```http
GET /posts?category=Backend
```

Filtering reduces:

- Query cost
    
- Response size
    
- Memory usage
    

---

# Aggregation

Sometimes the frontend needs statistics.

Example:

```text
Posts

↓

Count

↓

Likes

↓

Average
```

Performing calculations in the database is often more efficient than loading every record into your application and calculating there.

---

# Connection Pooling

Opening a new database connection for every request is expensive.

Professional applications keep a pool of reusable connections.

Conceptually:

```text
Request

↓

Connection Pool

↓

Existing Connection

↓

Database
```

Benefits:

- Faster requests
    
- Reduced connection overhead
    
- Better scalability
    

Most modern database drivers manage pooling automatically.

---

# Common Beginner Mistakes

## ❌ Using `SELECT *`

Retrieve only the fields you need.

---

## ❌ No Indexes

Without indexes:

Every query becomes slower as the dataset grows.

---

## ❌ Returning Thousands of Rows

Always paginate.

---

## ❌ N+1 Queries

Avoid querying the database repeatedly inside loops.

---

## ❌ Optimizing Controller Code First

The controller often contributes only a tiny fraction of the total response time.

Optimize the database first.

---

# Database Optimization Checklist

Before shipping an endpoint, ask:

### Are indexes available for frequently searched fields?

---

### Are only required fields retrieved?

---

### Is pagination implemented?

---

### Is filtering reducing unnecessary data?

---

### Is sorting efficient?

---

### Could this endpoint suffer from N+1 queries?

---

### Can aggregation reduce application work?

If the answer to these questions is **Yes**, your endpoint is likely to perform much better.

---

# Best Practices

✅ Index frequently queried fields.

✅ Select only required fields.

✅ Paginate large datasets.

✅ Avoid N+1 query patterns.

✅ Use aggregation when appropriate.

✅ Let the database do what it is optimized to do.

---

# Key Takeaways

- The database is often the largest contributor to API response time.
    
- Fetch only the data you need—avoid `SELECT *` or returning entire documents unnecessarily.
    
- Index frequently queried and sorted fields to avoid expensive scans.
    
- The N+1 query problem can severely degrade performance as data grows.
    
- Pagination, filtering, and efficient sorting reduce work for the database, network, and client.
    
- Good API design and good database design reinforce each other to produce fast, scalable applications.
