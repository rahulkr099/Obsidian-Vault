# Lesson 15.4 — Caching Strategies

> **Goal:** Learn how professional backend engineers use caching to make APIs dramatically faster while reducing server and database load.

Imagine your Blog API receives:

```http
GET /posts
```

every second.

If every request goes to the database:

```text
Client

↓

Server

↓

Database

↓

Response
```

the database quickly becomes the bottleneck.

Caching solves this problem.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand why caching works
    
- Learn different types of caching
    
- Understand Cache-Control headers
    
- Know when to cache

- Design cache strategies for APIs

# What is Caching?

Caching means:

> **Store frequently used data temporarily so future requests can be served faster.**

Instead of:

```text
Client

↓

Database

↓

Response
```

Use:

```text
Client

↓

Cache

↓

Response
```

The database doesn't need to work every time.

---

# Why Caching Matters

Suppose:

```http
GET /posts
```

takes:

```text
Database

↓

450 ms
```

Cached:

```text
Cache

↓

8 ms
```

Huge improvement.

---

# Cache Hit vs Cache Miss

## Cache Hit

Requested data already exists.

```text
Client

↓

Cache

↓

Found

↓

Response
```

Database is skipped.

---

## Cache Miss

Requested data isn't cached.

```text
Client

↓

Cache

↓

Not Found

↓

Database

↓

Store in Cache

↓

Response
```

Future requests become faster.

---

# Types of Caching

Professional systems use several kinds of caches.

```text
Browser Cache

↓

CDN Cache

↓

Server Cache

↓

Database Cache
```

Each solves a different problem.

---

# Browser Cache

The user's browser stores responses.

Example:

```http
GET /logo.png
```

The browser may reuse the cached file instead of downloading it again.

Benefits:

- Faster page loads
    
- Reduced network usage
    

Usually more useful for static assets than dynamic API responses.

---

# CDN Cache

A **Content Delivery Network (CDN)** stores content close to users.

Example:

User in India:

```text
India CDN
```

User in Germany:

```text
Germany CDN
```

Instead of requesting data from one distant server, users receive content from a nearby location.

Best suited for:

- Images
    
- CSS
    
- JavaScript
    
- Public files
    

Some public API responses can also benefit from CDN caching.

---

# Server-Side Cache

The backend stores frequently requested data.

Example:

```http
GET /posts
```

Flow:

```text
Client

↓

Server Cache

↓

Found

↓

Response
```

The database isn't contacted.

A common tool used in Node.js applications is **Redis**.

---

# Database Cache

Some databases internally cache frequently accessed data.

Benefits:

- Faster repeated queries
    
- Reduced disk access
    

As backend developers, you usually configure queries and indexes, while the database engine handles much of this caching automatically.

---

# Cache-Control Headers

The server can tell clients how to cache responses.

Example:

```http
Cache-Control: max-age=300
```

Meaning:

```text
Store this response

for

5 minutes
```

For the next five minutes, the client may reuse the cached response.

---

# Common Cache-Control Directives

### Public

```text
public
```

Anyone may cache the response.

Useful for:

- Public blog posts
    
- Documentation
    

---

### Private

```text
private
```

Only the end user's browser should cache it.

Useful for:

- User profile responses
    

---

### No Cache

```text
no-cache
```

The cached response must be revalidated before reuse.

---

### No Store

```text
no-store
```

Do not store the response at all.

Useful for:

- Banking
    
- Password reset
    
- Sensitive personal data
    

---

# What Should Be Cached?

Good candidates:

```text
Public Blog Posts

Categories

Tags

Popular Posts

Documentation
```

These don't change frequently.

---

# What Should NOT Be Cached?

Avoid caching:

```text
User Profile

Payment Data

JWT Tokens

Password Reset Responses

Sensitive Personal Information
```

Security is more important than performance.

---

# Cache Invalidation

One of the hardest problems in software engineering is knowing **when to remove stale data**.

Suppose:

```http
GET /posts
```

is cached.

Now:

```http
PATCH /posts/25
```

updates a post.

Should the cache still return the old version?

No.

You need to refresh or remove the cached entry.

---

# Cache Invalidation Flow

```text
GET /posts

↓

Cache

↓

Response
```

Later:

```text
PATCH /posts

↓

Update Database

↓

Invalidate Cache

↓

Next Request

↓

Fresh Data
```

Keeping cached data fresh is essential.

---

# Time-Based Expiration

Sometimes it's acceptable for cached data to be slightly old.

Example:

```text
Cache

↓

Expires

↓

5 Minutes
```

After five minutes:

A new database query refreshes the cache.

---

# Blog API Example

Endpoint:

```http
GET /posts
```

Strategy:

```text
Cache

↓

5 Minutes
```

Excellent candidate.

---

Endpoint:

```http
POST /posts
```

Do not cache.

Instead:

```text
Create Post

↓

Clear Posts Cache
```

The next request receives updated data.

---

# Caching Pipeline

```text
Client

↓

CDN (Optional)

↓

Browser Cache

↓

Server Cache

↓

Controller

↓

Service

↓

Repository

↓

Database

↓

Response
```

Requests stop as soon as a cache contains the needed data.

---

# Caching vs Database

Without cache:

```text
Client

↓

Database

↓

Response
```

Every request increases database load.

---

With cache:

```text
Client

↓

Cache

↓

Response
```

The database is contacted much less often.

---

# Trade-Off

Caching improves:

- Speed
    
- Scalability
    
- Database load
    

But introduces one challenge:

```text
Freshness
```

Cached data may become outdated.

Backend engineers must balance:

- Performance
    
- Accuracy

# Common Beginner Mistakes

## ❌ Caching Everything

Not every endpoint benefits from caching.

Dynamic or sensitive data often should not be cached.

---

## ❌ Never Clearing Cache

Updating the database but keeping stale cache leads to inconsistent responses.

---

## ❌ Ignoring Cache-Control

Without proper cache headers:

Browsers cannot cache efficiently.

---

## ❌ Caching Sensitive Data

Never cache:

- Passwords
    
- Tokens
    
- Banking information
    

unless you fully understand the security implications and architecture.

---

## ❌ Assuming Cache Is Always Faster

Caching itself has costs.

Only cache data that is requested frequently enough to justify it.

---

# Caching Checklist

Before caching an endpoint, ask:

### Is the data requested frequently?

---

### Does the data change rarely?

---

### Is the data safe to cache?

---

### How long should it remain cached?

---

### When should the cache be invalidated?

---

### Should the browser, CDN, or server cache it?

If you can answer these questions clearly, you have a solid caching strategy.

---

# Best Practices

✅ Cache frequently requested, mostly read-only data.

✅ Use appropriate `Cache-Control` headers.

✅ Invalidate cache after data changes.

✅ Use short expiration times when freshness is important.

✅ Avoid caching sensitive information.

✅ Measure the impact of caching on response time and database load.

# Key Takeaways

- Caching stores frequently requested data so it can be served much faster than querying the database every time.
    
- Common caching layers include browser caches, CDNs, server-side caches, and database caches.
    
- Cache hits avoid unnecessary database work, while cache misses populate the cache for future requests.
    
- `Cache-Control` headers tell clients and intermediaries how responses may be cached.
    
- Not all data should be cached—dynamic and sensitive information often requires fresh responses.
    
- Cache invalidation is essential to prevent users from receiving stale data.
