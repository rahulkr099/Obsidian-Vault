# Endpoint 1 — Get All Posts

```http
GET /posts
```

## Requirements

Homepage displays:

- Title
    
- Slug
    
- Featured Image
    
- Author
    
- Published Date
    

---

## Bad Design

Returns:

```json
{
  "title": "...",
  "content": "...",
  "comments": [...],
  "likes": 250,
  "seo": {},
  "draft": false,
  "updatedAt": "...",
  "createdAt": "...",
  "analytics": {}
}
```

Problems:

- Large payload
    
- Slow serialization
    
- Wasted bandwidth
    

---

## Better Response

```json
{
  "title": "...",
  "slug": "...",
  "author": "...",
  "featuredImage": "...",
  "publishedAt": "..."
}
```

Only the required data is returned.

---

## Query Parameters

Support:

```http
GET /posts?page=1&limit=10
```

```http
GET /posts?category=Backend
```

```http
GET /posts?sort=newest
```

```http
GET /posts?fields=title,slug,author
```

These reduce unnecessary database work and network usage.

---

## Database Optimization

Useful indexes:

```text
slug

category

publishedAt

authorId
```

---

## Caching

Good candidate.

Example:

```text
Cache

↓

5 minutes
```

---

## Compression

Enable:

- Gzip
    
- Brotli
    

---

## ETag

Useful because homepage content doesn't change every second.

# Endpoint 2 — Get Single Post

```http
GET /posts/:slug
```

---

## Database

Index:

```text
slug
```

instead of searching every post.

---

## Response

Return:

- Title
    
- Content
    
- Author
    
- Tags
    
- Likes
    

Avoid unrelated information.

---

## Caching

Excellent candidate.

Frequently read.

Rarely updated.

---

## ETag

Highly recommended.

Readers often revisit articles.

---

# Endpoint 3 — Create Post

```http
POST /posts
```

Caching?

❌ No.

This endpoint changes data.

---

Optimization focus:

- Fast validation
    
- Efficient database insert
    
- Return only created resource
    

---

After successful creation:

```text
Clear

Posts Cache
```

Future readers receive updated content.

---

# Endpoint 4 — Update Post

```http
PATCH /posts/:id
```

Caching?

No.

---

After update:

```text
Update Database

↓

Invalidate

Single Post Cache

↓

Invalidate

Posts List Cache
```

Otherwise users receive stale data.

---

# Endpoint 5 — Delete Post

```http
DELETE /posts/:id
```

Performance priorities:

- Efficient lookup
    
- Index on `id`
    
- Cache invalidation
    

---

# Endpoint 6 — Add Comment

```http
POST /posts/:id/comments
```

Optimization:

Index:

```text
postId
```

This makes comment retrieval efficient.

After creating a comment:

```text
Invalidate

Post Cache
```

The comment count and comment list have changed.

---

# Endpoint 7 — Like Post

```http
POST /posts/:id/likes
```

Useful indexes:

```text
postId

userId
```

Business rule:

Prevent duplicate likes efficiently.

Caching:

No.

Invalidate affected post cache after a successful like.

# Optimizing Queries

Bad:

```text
Find Posts

↓

Load Every Field

↓

Return Everything
```

---

Better:

```text
Find Posts

↓

Filter

↓

Sort

↓

Paginate

↓

Select Required Fields

↓

Return Response
```

The database performs less work, and the response is much smaller.

# Performance Checklist

Whenever you create a new endpoint, ask:

## Response

- Am I returning only the required fields?
    

---

## Pagination

- Could this endpoint return many records?
    

---

## Filtering

- Can unnecessary records be excluded?
    

---

## Sorting

- Is sorting handled efficiently?
    

---

## Database

- Are proper indexes available?
    

---

## Queries

- Can I avoid N+1 queries?
    

---

## Compression

- Will compression significantly reduce response size?
    

---

## Caching

- Is this endpoint read-heavy?
    

---

## ETag

- Will clients request the same data repeatedly?

# Common Beginner Mistakes

## ❌ Optimizing Without Measuring

Always identify the bottleneck first.

---

## ❌ Returning Entire Documents

Send only what the client needs.

---

## ❌ Forgetting Pagination

Large collections should always be paginated.

---

## ❌ No Cache Strategy

Read-heavy endpoints usually benefit from caching.

---

## ❌ Ignoring Indexes

A great API design cannot compensate for poor database indexing.

---

## ❌ Optimizing Tiny Details First

Improving a 2 ms controller is less valuable than fixing a 700 ms database query.

Focus on the largest bottleneck.

---

# Best Practices

✅ Design APIs to return only necessary data.

✅ Paginate collection endpoints.

✅ Use indexes for frequently queried fields.

✅ Cache read-heavy endpoints.

✅ Compress large responses.

✅ Use ETags for resources that change infrequently.

✅ Measure before and after every optimization.
