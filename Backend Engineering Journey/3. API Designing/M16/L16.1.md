# Lesson 16.1 — Logging & Monitoring

> **Goal:** Learn how professional backend engineers understand what is happening inside a production API using logs and monitoring.

Imagine this situation:

Your Blog API has been running perfectly for weeks.

At **2:15 AM**, users suddenly report:

> **"We can't create posts."**

The first question isn't:

> **"How do I fix it?"**

The first question is:

> **"What happened?"**

That's where **logging** and **monitoring** become essential.

# What is Logging?

Logging is the process of recording important events that happen inside your application.

Example:

```text
User Logged In

↓

Log Entry
```

Another:

```text
Post Created

↓

Log Entry
```

Another:

```text
Database Error

↓

Log Entry
```

Logs help you understand what happened before, during, and after an issue.

---

# Why Logging Matters

Without logs:

```text
API Failed

↓

Why?

↓

Unknown
```

---

With logs:

```text
API Failed

↓

Database Timeout

↓

Request ID

↓

Affected Endpoint

↓

Root Cause Found
```

Logs turn guessing into investigation.

---

# What Should Be Logged?

Not everything.

Focus on events that help diagnose issues or understand system behavior.

Good examples:

- Server started
    
- Server stopped
    
- User logged in
    
- User logged out
    
- Post created
    
- Post updated
    
- Post deleted
    
- Validation failures
    
- Authentication failures
    
- Authorization failures
    
- Database errors
    
- Unexpected exceptions
    

---

# What Should NOT Be Logged?

Never log sensitive information.

Avoid:

- Passwords
    
- JWT Access Tokens
    
- Refresh Tokens
    
- OTP codes
    
- Credit card numbers
    
- API secrets
    

Bad:

```text
Password:

mySecret123
```

Good:

```text
User login attempt failed.
```

Protect user privacy and system security.

---

# Log Levels

Not every log has the same importance.

Professional applications classify logs into levels.

---

## INFO

Normal application events.

Examples:

```text
Server Started

User Logged In

Post Created
```

These help understand normal activity.

---

## WARN

Something unusual happened.

Examples:

```text
Rate Limit Reached

Invalid Input

Slow Database Query
```

The application still works, but attention may be needed.

---

## ERROR

An operation failed.

Examples:

```text
Database Connection Failed

Payment Failed

File Upload Failed
```

Errors require investigation.

---

## DEBUG

Detailed information used during development.

Examples:

```text
Request Body

SQL Query

Function Arguments
```

Usually disabled in production because it generates a large volume of logs.

---

# Log Level Flow

```text
DEBUG

↓

INFO

↓

WARN

↓

ERROR
```

Severity increases as you move downward.

---

# Good Log Messages

Bad:

```text
Something failed.
```

Good:

```text
Failed to create post.

User ID: 42

Reason: Validation failed
```

A useful log answers:

- What happened?
    
- Where did it happen?
    
- Why did it happen?
    

---

# Structured Logging

Instead of writing free-form text, professional systems often use structured logs.

Bad:

```text
User created post.
```

Better:

```json
{
  "level": "INFO",
  "event": "POST_CREATED",
  "userId": 42,
  "postId": 125
}
```

Benefits:

- Easier to search
    
- Easier to filter
    
- Easier for monitoring tools to process

# Monitoring

Logging tells you **what happened**.

Monitoring tells you **how the system is performing right now**.

Examples:

- How many requests per minute?
    
- How many errors today?
    
- Average response time?
    
- CPU usage?
    
- Memory usage?
    

Monitoring helps you detect problems before users report them.

---

# Important Metrics

Professional teams commonly monitor:

## Request Count

```text
2,500 Requests

Last Minute
```

Shows application traffic.

---

## Error Rate

```text
1.2%
```

A sudden increase may indicate a deployment issue or service outage.

---

## Response Time

Example:

```text
Average

180 ms
```

If it jumps to:

```text
2,500 ms
```

Something needs investigation.

---

## CPU Usage

Example:

```text
92%
```

High CPU may indicate expensive computations or too much traffic.

---

## Memory Usage

Example:

```text
85%
```

Consistently high memory usage may indicate inefficient data handling or memory leaks.

---

# Blog API Logging Strategy

|Endpoint|What to Log|
|---|---|
|POST /auth/login|Login success/failure (never passwords)|
|POST /posts|Post created|
|PATCH /posts/:id|Post updated|
|DELETE /posts/:id|Post deleted|
|POST /posts/:id/comments|Comment created|
|POST /posts/:id/likes|Like added|
|Global Error Handler|Unexpected exceptions|

---

# Logging vs Monitoring

|Logging|Monitoring|
|---|---|
|Records individual events|Tracks system health|
|Helps investigate incidents|Helps detect incidents|
|Event-focused|Metric-focused|
|Example: "User 42 created a post."|Example: "Error rate increased to 5%."|

They complement each other.

# Real Production Scenario

Users report:

```text
Creating posts is slow.
```

Monitoring shows:

```text

↑ Increased
```

Logs show:


Now you know:

- **What** happened (logs)
    
- **How widespread** it is (monitoring)

# Common Beginner Mistakes

## ❌ Logging Everything

Too many logs make it difficult to find important information.

Log meaningful events.

---

## ❌ Logging Sensitive Data

Never log:

- Passwords
    
- Tokens
    
- Secrets
    

---

## ❌ Using One Log Level

Everything shouldn't be logged as `INFO`.

Choose appropriate levels.

---

## ❌ Ignoring Monitoring

Logs alone won't tell you if response times have doubled.

Monitor key metrics continuously.

---

## ❌ Writing Vague Logs

Bad:

```text
Error occurred.
```

Better:

```text
Failed to create post.

Reason: Duplicate slug.
```

Specific logs save debugging time.

---

# Logging Checklist

Before deploying an API, ask:

### Are important business events logged?

---

### Are sensitive values excluded?

---

### Are appropriate log levels used?

---

### Are logs structured?

---

### Are response time and error rate monitored?

---

### Can production issues be investigated using logs?

If the answer is **Yes**, your logging strategy is in good shape.

---

# Best Practices

✅ Log meaningful events, not everything.

✅ Never log sensitive information.

✅ Use log levels consistently.

✅ Prefer structured logging over plain text.

✅ Monitor response time, errors, CPU, and memory.

✅ Use logs and monitoring together to diagnose production issues.

# Key Takeaways

- Logging records important events that occur inside your application.
    
- Monitoring tracks the overall health and performance of the system.
    
- Use log levels (`DEBUG`, `INFO`, `WARN`, `ERROR`) to classify events by severity.
    
- Structured logs are easier to search, filter, and analyze than plain text logs.
    
- Never log sensitive information such as passwords or tokens.
    
- Together, logging and monitoring help teams detect, investigate, and resolve production issues quickly.
