# Lesson 16.3 — Idempotency & Reliability

> **Goal:** Learn how to design APIs that remain reliable even when requests are retried because of network failures, client timeouts, or duplicate submissions.

One of the biggest challenges in distributed systems is this:

> **Did the server receive my request or not?**

Sometimes the server successfully processes the request, but the response never reaches the client because of a network issue.

The client doesn't know whether to retry.

This is where **idempotency** becomes essential.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand idempotency
    
- Know which HTTP methods are idempotent
    
- Understand idempotency keys
    
- Design APIs that safely handle retries
    
- Prevent duplicate operations
    
- Build more reliable backend systems
    

---

# The Problem

Suppose a user clicks:

```http
POST /posts
```

The server:

- Creates the post
    
- Sends a response
    

But the network fails before the client receives it.

The client sees:

```text
Request Failed
```

Did the post get created?

The client doesn't know.

So it retries.

---

# Without Idempotency

First request:

```text
Create Post

↓

Success
```

Network fails.

Client retries:

```text
Create Post

↓

Success
```

Now the database contains:

```text
Post #101

Post #102
```

Duplicate posts.

---

# What is Idempotency?

An operation is **idempotent** if performing it multiple times produces the **same final result** as performing it once.

Example:

```text
Operation

↓

Run Once

↓

Final State
```

Run again:

```text
Operation

↓

Same Final State
```

Nothing changes.

---

# Everyday Example

Imagine a light switch.

Turning it **ON**:

```text
OFF

↓

ON
```

Press **ON** again:

```text
ON

↓

ON
```

Still ON.

That's idempotent.

---

# HTTP Methods and Idempotency

Some HTTP methods are naturally idempotent.

|Method|Idempotent?|
|---|:-:|
|GET|✅|
|PUT|✅|
|PATCH|Usually ✅*|
|DELETE|✅|
|POST|❌|

* `PATCH` depends on the type of update being performed.

---

# GET

```http
GET /posts/25
```

Request it:

1 time

↓

10 times

↓

100 times

The database doesn't change.

Safe.

---

# DELETE

```http
DELETE /posts/25
```

First request:

```text
Post Exists

↓

Deleted
```

Second request:

```text
Already Deleted
```

Still deleted.

Final state is unchanged.

---

# PUT

```http
PUT /users/42
```

Body:

```json
{
  "name": "Rahul"
}
```

Sending the same request repeatedly leaves the user with:

```text
Rahul
```

No duplicate resources are created.

---

# POST is Different

```http
POST /posts
```

Request:

```json
{
  "title": "Learning Express"
}
```

Every request creates:

```text
Post #101

↓

Post #102

↓

Post #103
```

Multiple resources.

POST is **not** idempotent by default.

---

# Why Retries Happen

Clients retry because of:

- Slow internet
    
- Temporary server failures
    
- Network timeouts
    
- Mobile connectivity issues
    
- Automatic retry mechanisms
    

Retries are normal in distributed systems.

Your API should handle them safely.

---

# The Solution — Idempotency Keys

The client generates a unique key.

Example:

```text
Idempotency-Key:

abc123xyz
```

Request:

```http
POST /posts
Idempotency-Key: abc123xyz
```

The server stores:

```text
abc123xyz

↓

Response
```

---

# First Request

```text
Client

↓

POST

↓

Idempotency Key

↓

Not Seen Before

↓

Create Resource

↓

Store Result
```

---

# Retry

Client sends:

```http
POST /posts
Idempotency-Key: abc123xyz
```

Server:

```text
Key Already Exists

↓

Return Previous Response
```

No duplicate resource is created.

---

# Blog API Example

User clicks:

```http
POST /posts
```

Header:

```http
Idempotency-Key: post-2026-001
```

First request:

```text
Create Post

↓

Store Response
```

Retry:

```text
Existing Key

↓

Return Stored Response
```

Still one post.

---

# Where Are Idempotency Keys Stored?

A common workflow:

```text
Request

↓

Read Idempotency Key

↓

Lookup Storage

↓

Key Exists?

├── Yes → Return Stored Response
│
└── No
      ↓
Process Request
      ↓
Store Key + Response
      ↓
Return Response
```

Storage might be:

- Redis
    
- Database
    
- In-memory cache (for simple applications)
    

---

# How Long Should Keys Be Stored?

Usually:

```text
5 minutes

30 minutes

24 hours
```

depending on business requirements.

Keeping keys forever wastes storage.

---

# Real-World Example — Payments

Imagine:

```http
POST /payments
```

Without idempotency:

Network timeout.

Client retries.

Possible result:

```text
₹500 Paid

↓

₹500 Paid Again
```

Customer charged twice.

---

With idempotency:

```text
Same Key

↓

Previous Payment Returned

↓

No Second Charge
```

This is why payment APIs almost always support idempotency keys.

---

# Does the Blog API Need Idempotency?

Let's evaluate.

---

## Create Post

```http
POST /posts
```

Useful?

✅ Yes.

Prevents duplicate posts if the client retries.

---

## Login

```http
POST /auth/login
```

Usually:

❌ Not necessary.

Logging in twice doesn't create duplicate resources.

---

## Like Post

```http
POST /posts/:id/likes
```

Useful?

Yes.

Although you should also enforce a database/business rule that one user can like a post only once.

Idempotency provides an additional layer of protection.

---

## Delete Post

```http
DELETE /posts/:id
```

Already idempotent.

No idempotency key is usually needed.

# Reliability

Reliable APIs:

- Handle retries safely
    
- Avoid duplicate operations
    
- Recover gracefully from temporary failures
    

Reliability is about maintaining consistent behavior even when networks are unreliable.

---

# Reliable Request Flow

```text
Client

↓

POST

↓

Idempotency Key

↓

Validation

↓

Business Logic

↓

Database

↓

Store Response

↓

Return Response
```

If the client retries, the same response can be returned.

---

# Common Beginner Mistakes

## ❌ Ignoring Retries

Real clients retry requests.

Design for it.

---

## ❌ Creating Duplicate Resources

Repeated POST requests should be considered carefully.

---

## ❌ Storing Idempotency Keys Forever

Choose an appropriate expiration time.

---

## ❌ Confusing Idempotency with Authentication

Authentication identifies the user.

Idempotency prevents duplicate operations.

They solve different problems.

---

## ❌ Assuming Only Payment APIs Need Idempotency

Many create operations can benefit from it.

Examples:

- Creating orders
    
- Booking tickets
    
- Uploading files
    
- Creating posts
    

---

# Reliability Checklist

Before exposing a write endpoint, ask:

### Can the client retry this request?

---

### Could retries create duplicate data?

---

### Should this endpoint support idempotency keys?

---

### Where will idempotency keys be stored?

---

### When should they expire?

If these questions are answered, your API is more resilient.

---

# Best Practices

✅ Design APIs to handle retries safely.

✅ Use idempotency keys for important create operations.

✅ Return the original response for repeated requests with the same key.

✅ Expire idempotency keys after an appropriate period.

✅ Combine idempotency with business rules and database constraints.

# Key Takeaways

- Idempotency ensures that repeating the same operation leads to the same final result.
    
- `GET`, `PUT`, and `DELETE` are naturally idempotent, while `POST` usually is not.
    
- Network failures and automatic retries are common in real systems.
    
- Idempotency keys allow servers to recognize duplicate requests and return the original response instead of performing the operation again.
    
- Payment, order, booking, and other resource-creation APIs commonly use idempotency keys.
    
- Building reliable APIs means designing for failures, retries, and unpredictable networks—not just successful requests.
