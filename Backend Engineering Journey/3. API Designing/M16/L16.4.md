# Lesson 16.4 — Health Checks & Graceful Shutdown

> **Goal:** Learn how production APIs report their health and how they shut down safely without interrupting users or losing data.

Imagine your Blog API is running on a production server.

Suddenly:

- You deploy a new version.
    
- The server crashes.
    
- Kubernetes or Docker restarts the application.
    

What happens to users who are making requests?

Professional applications are designed to handle these situations safely using **health checks** and **graceful shutdown**.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand health checks
    
- Differentiate liveness and readiness
    
- Design a health endpoint
    
- Understand graceful shutdown
    
- Handle in-flight requests
    
- Close resources safely during shutdown

# Why Health Checks Matter

Imagine your API server has:

- Lost its database connection
    
- Run out of memory
    
- Become unresponsive
    

Users only notice after requests start failing.

Instead, infrastructure should detect problems automatically.

Health checks allow servers to answer:

> **"Are you healthy?"**

---

# Health Check Endpoint

Most APIs expose a simple endpoint.

Example:

```http
GET /health
```

Possible response:

```json
{
  "status": "healthy"
}
```

Monitoring systems call this endpoint regularly.

---

# Why Not Check the Homepage?

Instead of requesting:

```http
GET /posts
```

Infrastructure uses:

```http
GET /health
```

Why?

Because:

- Faster
    
- Simpler
    
- Doesn't depend on business data
    
- Easy to automate
    

---

# What Should a Health Check Verify?

A simple health check might verify:

```text
Application Running

↓

Database Connected

↓

Required Services Available

↓

Ready to Accept Requests
```

If any critical dependency fails, the endpoint can report an unhealthy state.

---

# Liveness Check

Question:

> **"Is the application alive?"**

Example:

```text
Process Running?

↓

Yes
```

Liveness does **not** check whether the application is ready to serve traffic.

It simply verifies that the process is still functioning.

---

# Readiness Check

Question:

> **"Can this application handle requests right now?"**

Suppose:

```text
Application Running

↓

Database Disconnected
```

The server is alive.

But it is **not ready**.

Readiness should fail.

---

# Difference

|Liveness|Readiness|
|---|---|
|Is the application running?|Can it handle requests?|
|Detects crashed processes|Detects unavailable dependencies|
|Often simpler|Usually checks external services|

# Why Graceful Shutdown?

Suppose your server receives:

```http
POST /posts
```

While processing:

The server suddenly stops.

Possible result:

- Database transaction interrupted
    
- Client receives no response
    
- Inconsistent state
    

Professional servers avoid this.

---

# Graceful Shutdown

Instead of:

```text
Server

↓

Immediately Stops
```

Use:

```text
Stop Accepting New Requests

↓

Finish Existing Requests

↓

Close Database

↓

Exit
```

This protects user requests.

---

# Request During Shutdown

Without graceful shutdown:

```text
Request

↓

Server Stops

↓

Failure
```

---

With graceful shutdown:

```text
Request

↓

Finish Processing

↓

Response Sent

↓

Server Stops
```

Much safer.

---

# Graceful Shutdown Flow

```text
Shutdown Signal

↓

Stop New Requests

↓

Complete Active Requests

↓

Close Database Connections

↓

Close Cache Connections

↓

Write Final Logs

↓

Exit
```

Each step prevents resource leaks and incomplete work.

---

# Resources to Close

During shutdown, applications should release resources such as:

```text
Database Connections

↓

Redis Connections

↓

Message Queues

↓

File Handles

↓

Log Streams
```

This ensures a clean shutdown.

---

# Blog API Example

Current requests:

```text
GET /posts

PATCH /posts/25

POST /comments
```

Shutdown begins.

Server:

- Rejects new requests.
    
- Finishes these active requests.
    
- Closes resources.
    
- Exits safely.

# Rolling Deployments

Professional deployments often replace servers one at a time.

```text
Server A

↓

Graceful Shutdown

↓

New Version Starts

↓

Traffic Moves

↓

Server B

↓

Repeat
```

Users experience little or no downtime.

---

# Health Check Pipeline

```text
Monitoring System

↓

GET /health

↓

Application

↓

Dependencies Checked

↓

Healthy?

↓

Yes → Continue Traffic

No → Remove from Service
```

This allows orchestration platforms to make intelligent decisions.

---

# Production Architecture

```text
Client

↓

Load Balancer

↓

Health Check

↓

Healthy Server

↓

Application

↓

Database
```

If a server becomes unhealthy:

The load balancer stops sending traffic to it.

# Common Beginner Mistakes

## ❌ No Health Endpoint

Monitoring systems have no simple way to determine application health.

---

## ❌ Returning Healthy When Dependencies Fail

If the database is unavailable, the application usually isn't ready.

---

## ❌ Immediate Shutdown

Active requests may fail unexpectedly.

---

## ❌ Forgetting Database Connections

Leaving connections open can cause resource leaks and slow recovery.

---

## ❌ Ignoring In-Flight Requests

Users shouldn't lose requests simply because a deployment starts.

---

# Health & Shutdown Checklist

Before deploying, ask:

### Does the application expose a health endpoint?

---

### Can monitoring determine if the application is healthy?

---

### Does readiness verify critical dependencies?

---

### Does shutdown stop new requests first?

---

### Are active requests allowed to finish?

---

### Are database and cache connections closed properly?

If the answer to these questions is **Yes**, your application is much closer to production quality.

---

# Best Practices

✅ Expose a dedicated health endpoint.

✅ Separate liveness and readiness checks.

✅ Verify critical dependencies in readiness checks.

✅ Gracefully finish active requests before shutting down.

✅ Close all external connections cleanly.

✅ Design deployments to minimize downtime.

# Key Takeaways

- Health checks allow infrastructure to determine whether an application is alive and ready to serve requests.
    
- **Liveness** checks verify that the process is running, while **readiness** checks verify that it can safely handle traffic.
    
- A dedicated health endpoint should be lightweight and focus on critical dependencies.
    
- Graceful shutdown protects users by allowing active requests to finish before the application exits.
    
- Closing database, cache, and other external connections prevents resource leaks.
    
- Health checks and graceful shutdown are essential parts of running reliable production systems.
