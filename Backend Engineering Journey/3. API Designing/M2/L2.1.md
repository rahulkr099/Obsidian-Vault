# Module 2 — Requirements → Endpoints

# Lesson 2.1 — Understanding Business Requirements

> **Goal:** Learn how to read business requirements like a backend engineer and convert them into a technical plan before writing a single line of code.

---

# Learning Objectives

After this lesson, you should be able to:

- Understand what business requirements are.
    
- Differentiate between business and technical requirements.
    
- Identify functional and non-functional requirements.
    
- Extract useful information from a requirement document.
    
- Avoid jumping directly into coding.
    

---

# Why Requirements Matter

One of the biggest mistakes beginners make is this:

```text
Requirement
      ↓
Start Coding
```

Professional backend engineers follow a different approach:

```text
Requirements
      ↓
Analysis
      ↓
Resources
      ↓
API Design
      ↓
Data Modeling
      ↓
Implementation
```

A well-designed backend starts with understanding the problem—not writing code.

---

# What is a Business Requirement?

A business requirement describes **what the system should do**, not **how it should do it**.

Example:

> Users should be able to publish blog posts.

Notice that it doesn't say:

- Use Express.
    
- Use MongoDB.
    
- Create a `posts` collection.
    
- Create `POST /posts`.
    

Those are **technical decisions**.

---

# Business Requirement vs Technical Requirement

## Business Requirement

```text
Users can comment on blog posts.
```

---

## Technical Requirement

```text
POST /posts/:id/comments

Store comments in MongoDB

Validate comment length

Return HTTP 201
```

The business team cares about the first statement.

The backend team decides the second.

# Example: Blog Application

Imagine the product manager gives you this document.

---

## Blog Requirements

- Users can register.
    
- Users can log in.
    
- Users can create posts.
    
- Users can edit their own posts.
    
- Users can delete their own posts.
    
- Readers can view posts.
    
- Readers can search posts.
    
- Readers can comment.
    
- Users can like posts.
    
- Users can follow authors.
    

---

A beginner immediately starts creating routes.

A professional starts asking questions.

---

# Backend Engineer's Mindset

Instead of coding immediately, ask:

- Who are the users?
    
- What data do we need?
    
- What permissions exist?
    
- What actions are allowed?
    
- What rules exist?
    
- What relationships exist?
    
- What validations are required?
    

These questions lead to a much better design.

---

# Step 1 — Identify Actors

Actors are the people or systems interacting with the application.

For the blog app:

```text
Guest

Registered User

Author

Admin
```

Each actor has different permissions.

---

# Step 2 — Identify Features

Features describe what users can do.

```text
Register

Login

Create Post

Edit Post

Delete Post

Comment

Search

Like

Follow
```

These are not API endpoints yet.

They are capabilities.

---

# Step 3 — Identify Resources

From the features, identify the resources.

```text
User

Post

Comment

Like

Follow
```

Notice how features become resources.

This will later help us design:

- Database tables/collections
    
- API endpoints
    
- Services
    

---

# Step 4 — Identify Relationships

Now ask:

How are resources connected?

```text
User
 │
 ├── creates → Posts
 │
 ├── writes → Comments
 │
 ├── likes → Posts
 │
 └── follows → Users
```

Relationships influence both:

- Database schema
    
- API structure
    

---

# Step 5 — Identify Rules

Business rules are extremely important.

Example:

```text
Only logged-in users can create posts.
```

Another:

```text
Only the author can edit a post.
```

Another:

```text
A user cannot like the same post twice.
```

These rules belong in the **service layer**, not the controller.

---

# Functional Requirements

Functional requirements describe what the application does.

Examples:

- Register users.
    
- Login users.
    
- Create posts.
    
- Delete comments.
    
- Search posts.
    

Think of them as **features**.

---

# Non-Functional Requirements

Non-functional requirements describe **how well** the system should perform.

Examples:

- Response time under 500 ms.
    
- Support 10,000 users.
    
- Secure authentication.
    
- High availability.
    
- Daily backups.
    
- Scalable architecture.
    

These don't add features, but they shape the implementation.

---

# Hidden Requirements

Many requirements are implied, not explicitly written.

Requirement:

> Users can edit posts.

Hidden questions:

- Can users edit any post?
    
- Only their own?
    
- Can admins edit all posts?
    
- Can deleted posts be edited?
    
- Is there a time limit?
    

Professional developers always clarify these assumptions.

---

# Ambiguous Requirements

Requirement:

> Users can upload images.

Questions to ask:

- Maximum file size?
    
- Allowed formats?
    
- Number of images?
    
- Where are images stored?
    
- Can images be deleted?
    
- Are animated GIFs allowed?
    

Never guess when requirements are unclear.

---

# Turning Requirements into Questions

Requirement:

> Users can search posts.

Questions:

- Search by title?
    
- Search by content?
    
- Search by author?
    
- Partial matches?
    
- Case-sensitive?
    
- Paginated?
    
- Sort by relevance?
    

Good backend engineers ask these questions before implementation.

---

# Requirement Analysis Example

Requirement:

> Users can like posts.

Analysis:

Actors:

```text
Registered User
```

Resource:

```text
Like
```

Business Rules:

```text
One like per user per post.

Only logged-in users can like.

Users can remove their like.
```

Possible APIs:

```http
POST /posts/:id/likes

DELETE /posts/:id/likes
```

Possible Database:

```text
Like

userId

postId

createdAt
```

Notice how everything starts from one simple requirement.

---

# Why This Process Matters

Suppose you skip analysis.

You might build:

```http
POST /posts/:id/likes
```

Later the product manager says:

> "Users should also be able to dislike posts."

Now you need to redesign everything.

Good requirement analysis reduces costly redesigns.

        ▼

        ▼

        │
        ▼
Identify Resources

        ▼
Identify Relationships
        │
        ▼

        │
        ▼

        │
        ▼

Notice that coding is one of the last steps.

# Common Mistakes

❌ Starting Express before understanding requirements.

❌ Confusing features with API endpoints.

❌ Ignoring business rules.

❌ Not asking clarifying questions.

❌ Assuming missing details.

❌ Designing the database before understanding the domain.

---

# Best Practices

- Read the requirements multiple times.
    
- Separate business requirements from technical decisions.
    
- Identify actors first.
    
- Identify resources before endpoints.
    
- Write down business rules explicitly.
    
- Ask questions whenever requirements are ambiguous.
    
- Treat requirement analysis as the foundation of your backend design.

# Key Terms

|Term|Meaning|
|---|---|
|Business Requirement|What the system should do|
|Technical Requirement|How the system will do it|
|Actor|A user or system interacting with the application|
|Feature|A capability provided by the application|
|Resource|A business entity managed by the system|
|Business Rule|A constraint or policy governing behavior|
|Functional Requirement|A feature the system provides|
|Non-Functional Requirement|A quality attribute like performance or security|

# Interview Questions

### 1. What is the difference between a business requirement and a technical requirement?

**Answer:**  
A business requirement describes **what** the system should accomplish, while a technical requirement describes **how** it will be implemented using specific technologies, APIs, or database designs.

---

### 2. Why is requirement analysis important before API design?

**Answer:**  
Requirement analysis helps identify actors, resources, business rules, and validations. This leads to well-designed APIs and reduces costly changes later in development.

---

### 3. What are functional and non-functional requirements?

**Answer:**  
Functional requirements describe the system's features (e.g., user login), while non-functional requirements describe quality attributes such as performance, scalability, security, and reliability.
