# Module 2 — Requirements → Endpoints

# Lesson 2.2 — Identifying Resources from Requirements

> **Goal:** Learn how to identify the resources (business entities) in a system by analyzing business requirements. This is one of the most important skills for designing APIs, databases, and backend architecture.

---

# Learning Objectives

After this lesson, you should be able to:

- Extract resources from business requirements.
    
- Distinguish between resources, actions, and attributes.
    
- Identify primary and supporting resources.
    
- Recognize relationships between resources.
    
- Avoid common mistakes when identifying resources.
    

---

# Why Resources Matter

Every backend application revolves around **resources**.

Once you've identified the correct resources, you can naturally derive:

- Database tables or collections
    
- API endpoints
    
- Service classes
    
- Repository classes
    
- Authorization rules
    
- Validation rules
    

Professional backend engineers don't start by designing routes—they start by identifying the domain's resources.

---

# The Resource Identification Process

Use this simple workflow:

```text
Business Requirements
        │
        ▼
Identify Nouns
        │
        ▼
Filter Business Entities
        │
        ▼
Identify Relationships
        │
        ▼
Determine Ownership
        │
        ▼
Finalize Resources
```

Notice that we begin with **nouns**, because resources are almost always nouns.

---

# Step 1 — Read the Requirements Carefully

Example requirements:

- Users can register.
    
- Users can create blog posts.
    
- Readers can comment on posts.
    
- Users can like posts.
    
- Authors can organize posts into categories.
    

Don't think about Express or MongoDB yet.

Just understand the business.

---

# Step 2 — Highlight the Nouns

From the requirements:

```text
Users
Blog Posts
Readers
Comments
Categories
Likes
Authors
```

These nouns are your starting point.

However, not every noun becomes a resource.

---

# Step 3 — Remove Duplicate Concepts

Notice:

```text
Users
Readers
Authors
```

Are these different resources?

Usually, **no**.

They are different **roles** of the same resource.

Resource:

```text
User
```

Roles:

```text
Guest

Reader

Author

Admin
```

One `User` resource can have different permissions.

---

# Step 4 — Separate Resources from Actions

Requirement:

> Users can create posts.

Beginners often think:

```text
CreatePost
```

Wrong.

The resource is:

```text
Post
```

Action:

```text
Create
```

Remember:

- **Resource = Noun**
    
- **Action = HTTP Method**
    

Example:

```http
POST /posts
```

`POST` represents the action.

`posts` represents the resource.

---

# Step 5 — Separate Resources from Attributes

Requirement:

> Posts have a title and content.

Are these resources?

```text
Title ❌

Content ❌
```

These are **attributes** of the `Post` resource.

Resource:

```text
Post
```

Attributes:

```text
title

content

slug

createdAt

updatedAt
```

# Primary vs Supporting Resources

Some resources are central to the application.

Blog App:

Primary:

```text
User

Post
```

Supporting:

```text
Comment

Category

Like
```

Supporting resources usually exist because primary resources exist.

---

# Strong vs Weak Resources

A **strong resource** can exist independently.

Example:

```text
User
```

A **weak resource** depends on another resource.

Example:

```text
Comment
```

A comment without a post usually doesn't make sense.

---

# Hidden Resources

Sometimes requirements don't explicitly mention all resources.

Requirement:

> Users can reset their password.

Possible hidden resources:

```text
Password Reset Token
```

Requirement:

> Users verify email.

Possible hidden resources:

```text
Verification Token
```

Requirement:

> Users receive notifications.

Possible hidden resource:

```text
Notification
```

Professional engineers look beyond the obvious.

---

# Resource Ownership

Ask:

Who owns this resource?

Example:

```text
Post
```

Owner:

```text
User
```

Comment:

Owner:

```text
User
```

Category:

Owner?

Depends on the business.

Could be:

- Admin
    
- Author
    
- System
    

Ownership influences authorization.

---

# Resource Lifecycle

Every resource changes over time.

Example:

```text
Draft
   ↓
Published
   ↓
Archived
   ↓
Deleted
```

These are **states**, not separate resources.

# Common Mistakes

## Mistake 1

Treating actions as resources.

```text
CreatePost ❌

DeleteUser ❌
```

Correct:

```text
Post ✅

User ✅
```

---

## Mistake 2

Treating attributes as resources.

```text
Title ❌

Email ❌

Password ❌
```

Correct:

```text
User

Post
```

---

## Mistake 3

Creating duplicate resources.

```text
Reader

Author

Member
```

Usually:

```text
User
```

Different roles.

---

## Mistake 4

Ignoring hidden resources.

Example:

Authentication often needs:

```text
Refresh Token

Session

Verification Token
```

Even if the requirements don't mention them explicitly.

# Resource Checklist

Whenever you identify a potential resource, ask:

- Is it a noun?
    
- Does it represent business data?
    
- Does it have its own attributes?
    
- Does it have a lifecycle?
    
- Does it need CRUD operations?
    
- Does it have relationships?
    
- Does it require authorization?
    

If most answers are **yes**, it's probably a resource.

# Professional Workflow

Backend engineers often create a resource inventory before coding.

Example:

|Resource|Owner|Main Attributes|Relationships|
|---|---|---|---|
|User|System|name, email|Posts, Comments|
|Post|User|title, content|Comments, Likes|
|Comment|User|text|Post|
|Category|Admin|name|Posts|
|Like|User|createdAt|Post|

This inventory becomes the foundation for the database and API.

# Best Practices

- Start with business requirements.
    
- Highlight nouns.
    
- Separate resources from actions.
    
- Separate resources from attributes.
    
- Merge duplicate concepts.
    
- Look for hidden resources.
    
- Document relationships early.
    
- Think about ownership and lifecycle.

# Key Terms

|Term|Meaning|
|---|---|
|Resource|A business entity managed by the system|
|Attribute|A property of a resource|
|Action|An operation performed on a resource|
|Primary Resource|Core entity of the application|
|Supporting Resource|Entity that supports another resource|
|Strong Resource|Can exist independently|
|Weak Resource|Depends on another resource|
|Ownership|The user or system responsible for a resource|
|Lifecycle|The stages a resource goes through during its existence|

# Interview Questions

### 1. How do you identify resources from business requirements?

**Answer:**  
I read the requirements carefully, identify the nouns, remove duplicates, separate actions and attributes from business entities, identify relationships and ownership, and then finalize the resources that represent the application's core data.

---

### 2. What is the difference between a resource and an attribute?

**Answer:**  
A resource is an independent business entity, such as a `User` or `Post`. An attribute is a property of that resource, such as a user's email or a post's title.

---

### 3. Why is identifying resources important before API design?

**Answer:**  
Resources form the foundation for API endpoints, database schemas, service layers, validation, and authorization. Correctly identifying them leads to a clean and scalable backend architecture.

# 💡 Backend Engineering Insight

One habit you'll notice in experienced backend engineers is that they often create a **Domain Model** before writing code.

For a blog application, it might look like this:

```text
User
 ├── creates → Post
 ├── writes → Comment
 ├── likes → Post
 └── follows → User

Post
 ├── belongs to → Category
 ├── has many → Comments
 └── has many → Likes
```

This simple diagram becomes the blueprint for:

- ✅ Database schema
    
- ✅ API endpoints
    
- ✅ Service layer
    
- ✅ Authorization rules
    
- ✅ Validation logic
    

By investing time in modeling the domain first, implementation becomes much more straightforward and maintainable.
