# Step 1 — Start with the Resource

Suppose your resource is:

```text
Post
```

Ask yourself:

> "What operations can users perform on this resource?"

Possible operations:

- Create
    
- Read
    
- Update
    
- Delete
    

These are called **CRUD** operations.

---

# CRUD → HTTP Methods

|CRUD Operation|HTTP Method|Endpoint|
|---|---|---|
|Create|POST|`/posts`|
|Read All|GET|`/posts`|
|Read One|GET|`/posts/:id`|
|Update|PATCH|`/posts/:id`|
|Delete|DELETE|`/posts/:id`|

Notice that **the URL stays almost the same**.

The HTTP method changes the action.

# Why Not Use Verbs?

Many beginners design APIs like this:

```http
POST /createPost

POST /deletePost

POST /updatePost

GET /getPosts
```

Problems:

- Verb-heavy URLs
    
- Inconsistent naming
    
- Difficult to extend
    
- Harder to understand
    

REST solves this by separating:

- **Resource → URL**
    
- **Action → HTTP Method**
    

---

# The Golden Rule

Think of the URL as a **noun**.

Think of the HTTP method as a **verb**.

Example:

```http
POST /posts
```

Read it like English:

> "Create a post."

Another:

```http
DELETE /posts/25
```

Means:

> "Delete post 25."

The URL doesn't need verbs.

# What About Login?

This is where many beginners get confused.

Is login a resource?

No.

Login is an **action**.

But what resource is involved?

Usually:

```text
Session

Authentication
```

Professional APIs often use:

```http
POST /auth/login

POST /auth/logout

POST /auth/refresh
```

or

```http
POST /sessions
```

Both are acceptable, depending on the API style.

We'll cover authentication in detail later.

# Collection vs Single Resource

Collection:

```http
GET /posts
```

Returns:

```json
[
  {...},
  {...},
  {...}
]
```

---

Single Resource:

```http
GET /posts/15
```

Returns:

```json
{
  "id": 15,
  "title": "REST API Design"
}
```

The URL tells you whether you're requesting one resource or many.

---

# Nested Resources

Suppose every comment belongs to a post.

Requirement:

> View comments for a post.

Good design:

```http
GET /posts/15/comments
```

Create comment:

```http
POST /posts/15/comments
```

The URL clearly expresses the relationship.

---

# Another Example

Requirement:

> View all orders of a customer.

Good:

```http
GET /customers/5/orders
```

This is more meaningful than:

```http
GET /orders?customer=5
```

when the relationship is central to the domain.

---

# Avoid Deep Nesting

Avoid:

```http
/users/5/posts/10/comments/3/replies/8
```

This is difficult to read.

Instead:

```http
GET /replies/8
```

or

```http
GET /comments/3/replies
```

A common guideline is **no more than two levels** of nesting.

---

# Choosing Resource Names

Always use:

Plural nouns.

Good:

```http
/users

/posts

/comments

/orders
```

Avoid:

```http
/user

/post

/comment
```

Plural resources usually represent collections and align with REST conventions.

---

# Endpoint Naming Rules

Use:

- lowercase
    
- hyphens for multiple words
    
- no spaces
    
- no camelCase
    
- no underscores
    

Good:

```http
/blog-posts

/order-items
```

Avoid:

```http
/BlogPosts

/blogPosts

/blog_posts

/GetPosts
```

Consistency improves readability.

---

# Common Mistakes

### ❌ Using verbs in URLs

```http
/createPost

/deleteUser
```

---

### ❌ Using POST for everything

```http
POST /getUsers

POST /deleteUser
```

Use the appropriate HTTP methods instead.

---

### ❌ Mixing naming styles

```http
/getUsers

/posts

DeleteComment
```

Be consistent.

---

### ❌ Deep nesting

```http
/users/5/posts/10/comments/3/replies/8
```

Prefer simpler, flatter URLs.

---

### ❌ Designing endpoints before identifying resources

This often leads to inconsistent APIs and unnecessary redesign later.

---

# Best Practices

- Start with business requirements.
    
- Identify resources first.
    
- Use plural nouns.
    
- Let HTTP methods express actions.
    
- Keep URLs simple.
    
- Use nesting only when it clearly represents ownership.
    
- Follow consistent naming conventions across the entire API.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Endpoint|A URL that exposes an API resource|
|Collection Endpoint|Operates on multiple resources (e.g., `/posts`)|
|Resource Endpoint|Operates on a single resource (e.g., `/posts/:id`)|
|Nested Endpoint|Represents a child resource (e.g., `/posts/:id/comments`)|
|CRUD|Create, Read, Update, Delete|
|REST Convention|Standard practices for designing REST APIs|

# Interview Questions

### 1. How do you derive API endpoints from business requirements?

**Answer:**  
I first identify the business resources, determine the operations users can perform on them, map those operations to appropriate HTTP methods, and then design resource-oriented endpoints using REST conventions.

---

### 2. Why should REST endpoints use nouns instead of verbs?

**Answer:**  
Endpoints identify resources, while HTTP methods represent actions. Using nouns keeps APIs consistent, predictable, and easier to understand and maintain.

---

### 3. When should you use nested endpoints?

**Answer:**  
Nested endpoints are appropriate when a child resource naturally belongs to a parent resource, such as comments belonging to a post (`/posts/:id/comments`). Nesting should remain shallow—typically no more than one or two levels.

---

# 💡 Backend Engineering Insight

A common misconception is that **one business feature equals one API endpoint**.

Consider this feature:

> "Users can manage blog posts."

A beginner may think:

```http
POST /managePosts
```

A backend engineer thinks in terms of the resource lifecycle:

```http
GET    /posts
GET    /posts/:id
POST   /posts
PATCH  /posts/:id
DELETE /posts/:id
```

The resource (`Post`) remains constant, while the HTTP method defines the operation. This approach scales naturally as your application grows and makes your API intuitive for anyone consuming it.
