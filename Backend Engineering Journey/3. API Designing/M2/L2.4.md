# Why HTTP Methods Matter

Consider these two endpoints:

```http
POST /posts
```

and

```http
DELETE /posts/15
```

The URL tells us **what resource** we're working with (`posts`).

The HTTP method tells us **what action** we want to perform.

Think of it like this:

```text
HTTP Method = Verb
URL = Noun
```

Example:

```text
GET     /posts
 ↑         ↑
Verb     Noun
```

---

# The Five Most Common HTTP Methods

|Method|Purpose|
|---|---|
|GET|Retrieve data|
|POST|Create a new resource|
|PUT|Replace an entire resource|
|PATCH|Update part of a resource|
|DELETE|Remove a resource|

These five methods cover the majority of REST APIs.

---

# 1. GET — Read Data

Use `GET` when you want to retrieve data.

Example:

```http
GET /posts
```

Returns all posts.

---

```http
GET /posts/25
```

Returns one post.

Example response:

```json
{
  "id": 25,
  "title": "REST APIs",
  "author": "Rahul"
}
```

---

## Characteristics of GET

- Doesn't modify data
    
- Can be cached
    
- Can be bookmarked
    
- Safe
    
- Idempotent
    

We'll define **Safe** and **Idempotent** shortly.

---

# 2. POST — Create Data

Use `POST` to create a new resource.

Example:

```http
POST /posts
```

Request:

```json
{
  "title": "Learning APIs",
  "content": "..."
}
```

Response:

```http
201 Created
```

New resource:

```json
{
  "id": 101,
  "title": "Learning APIs"
}
```

---

## Characteristics of POST

- Creates new data
    
- Usually changes the database
    
- Not idempotent
    
- Not safe
    

If you send the same request twice:

```http
POST /posts
```

You may create two posts.

---

# 3. PUT — Replace an Entire Resource

Suppose this post exists.

```json
{
  "title": "API Design",
  "content": "REST",
  "author": "Rahul"
}
```

PUT request:

```http
PUT /posts/15
```

Body:

```json
{
  "title": "Advanced API Design",
  "content": "REST APIs",
  "author": "Rahul"
}
```

The server replaces the entire resource with the new representation.

Think:

```text
Old Resource
      ↓
Replace Everything
      ↓
New Resource
```

---

# Important Rule

With `PUT`, the client sends the **complete representation** of the resource.

Missing fields may be overwritten or reset, depending on the implementation.

---

# 4. PATCH — Partial Update

Suppose only the title changes.

Current post:

```json
{
  "title": "API Design",
  "content": "REST",
  "author": "Rahul"
}
```

PATCH request:

```http
PATCH /posts/15
```

Body:

```json
{
  "title": "Advanced API Design"
}
```

Result:

```json
{
  "title": "Advanced API Design",
  "content": "REST",
  "author": "Rahul"
}
```

Only the specified field changes.

---

# PATCH vs PUT

Suppose a user wants to update only their profile picture.

Using PUT:

```json
{
  "name": "...",
  "email": "...",
  "bio": "...",
  "profilePicture": "new.png"
}
```

Entire resource.

---

Using PATCH:

```json
{
  "profilePicture": "new.png"
}
```

Much simpler.

---

# Which One Should You Use?

Modern REST APIs often prefer:

```http
PATCH
```

because users rarely replace an entire resource.

Most updates are partial.

That's why you'll commonly see:

```http
PATCH /users/:id

PATCH /posts/:id
```

instead of `PUT`.

---

# 5. DELETE

Delete removes a resource.

Example:

```http
DELETE /posts/15
```

Possible response:

```http
204 No Content
```

or

```http
200 OK
```

with:

```json
{
  "success": true
}
```

---

# Safe Methods

A **Safe** method does **not change server data**.

Safe:

```http
GET
```

Unsafe:

```http
POST

PATCH

PUT

DELETE
```

Reading data should never modify the database.

---

# Idempotent Methods

This is one of the most common backend interview questions.

---

## What is Idempotency?

A request is **idempotent** if making the same request multiple times has the same effect as making it once.

---

### Example

Delete post:

```http
DELETE /posts/15
```

First request:

```text
Post deleted.
```

Second request:

```text
Still deleted.
```

Final state:

```text
No post.
```

Same result.

Therefore:

DELETE is idempotent.

---

### Another Example

```http
PATCH /posts/15
```

Request:

```json
{
  "published": true
}
```

Sending this request:

1 time:

```text
published = true
```

10 times:

```text
published = true
```

Final state is the same.

PATCH **can be idempotent**, depending on the operation.

---

### POST Example

```http
POST /posts
```

Request:

```json
{
  "title": "REST"
}
```

First request:

```text
Post #1 created.
```

Second request:

```text
Post #2 created.
```

Different final state.

POST is **not idempotent**.

---

# Safe vs Idempotent Table

|Method|Safe|Idempotent|
|---|---|---|
|GET|✅ Yes|✅ Yes|
|POST|❌ No|❌ No|
|PUT|❌ No|✅ Yes|
|PATCH|❓ Usually*|❓ Depends*|
|DELETE|❌ No|✅ Yes|

> **Note:** `PATCH` depends on what the patch operation does. Setting a field to a fixed value (e.g., `"published": true`) is idempotent. Incrementing a counter is not.

# Why Not Use POST for Everything?

Many beginners write:

```http
POST /getPosts

POST /deleteUser

POST /updatePost
```

Technically possible?

Yes.

Professional?

No.

Problems:

- Loses semantic meaning.
    
- Prevents proper caching.
    
- Harder for API consumers.
    
- Doesn't follow REST conventions.
    
- Makes documentation confusing.

# Common Mistakes

### ❌ Using POST for updates

```http
POST /updatePost
```

Better:

```http
PATCH /posts/:id
```

---

### ❌ Using GET to delete

```http
GET /deletePost/5
```

Very dangerous.

GET should never delete data.

---

### ❌ Using PUT for tiny updates

```http
PUT /users/10
```

Body:

```json
{
  "name": "Rahul"
}
```

If your API treats `PUT` as full replacement, this may unintentionally overwrite missing fields. Prefer `PATCH` for partial updates.

---

### ❌ Ignoring idempotency

Choosing the wrong method can make retries unsafe and introduce duplicate data.

---

# Best Practices

- Use methods according to their intended meaning.
    
- Prefer `PATCH` for partial updates.
    
- Use `PUT` only when replacing the complete resource.
    
- Never modify data using `GET`.
    
- Think about idempotency when designing APIs, especially for retry scenarios.
    
- Keep APIs consistent across all resources.

|Term|Meaning|
|---|---|
|HTTP Method|Defines the action performed on a resource|

|Idempotent|Repeating the same request produces the same final state|
|CRUD|Create, Read, Update, Delete|

# Interview Questions

### 1. What is the difference between `PUT` and `PATCH`?

**Answer:**  
`PUT` replaces the entire resource representation, while `PATCH` updates only the specified fields. `PATCH` is preferred for partial updates, which are more common in modern APIs.

---

### 2. Which HTTP methods are idempotent?

**Answer:**  
`GET`, `PUT`, and `DELETE` are idempotent. `PATCH` may or may not be idempotent depending on the operation, while `POST` is generally not idempotent because repeating it can create additional resources.

---

### 3. Why should `GET` never modify data?

**Answer:**  
`GET` is defined as a safe method. Clients, browsers, caches, and crawlers assume it only retrieves data. Modifying server state during a `GET` request can lead to unexpected behavior and security issues.

---

# 💡 Backend Engineering Insight

Many developers memorize HTTP methods as:

- GET = Read
    
- POST = Create
    
- PATCH = Update
    
- DELETE = Delete
    

Professional backend engineers go one step further and ask:

> **"What is the semantic meaning of this request?"**

For example, if a mobile app loses its internet connection and retries a request, an idempotent API prevents accidental duplicate operations. Understanding the semantics behind HTTP methods helps you design APIs that are not only RESTful but also reliable in real-world distributed systems.
