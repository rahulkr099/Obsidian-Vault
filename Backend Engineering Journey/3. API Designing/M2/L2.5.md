# What is a User Story?

A **user story** is a short description of a feature from the user's perspective.

A common format is:

> **As a `<role>`, I want `<goal>` so that `<benefit>`.**

Example:

> As an **author**, I want to **publish a blog post** so that **readers can read it**.

User stories describe **what users want**, not how the system is implemented.

---

# Why Backend Engineers Care About User Stories

Many beginners read a user story and immediately write:

```javascript
router.post("/posts")
```

Professional backend engineers think like this:

```text
User Story
      ↓
Actor
      ↓
Resource
      ↓
Business Rules
      ↓
Validation
      ↓
Authorization
      ↓
API Design
      ↓
Implementation
```

The API is a result of analysis—not the starting point.

# User Story 4

> As an author, I want to edit my own blog posts.

---

### Endpoint

```http
PATCH /posts/:id
```

---

### Business Rules

- Post must exist.
    
- User must own the post.
    
- Deleted posts cannot be edited.
    

---

### Validation

Only update the provided fields.

---

### Authorization

```text
User ID == Author ID
```

Otherwise:

```http
403 Forbidden
```

# The Backend Engineer's Checklist

Before implementing any endpoint, ask yourself:

### 1. Who is the actor?

Example:

```text
Guest

Author

Admin
```

---

### 2. What resource is involved?

```text
Post
```

---

### 3. What action is being performed?

```text
Create

Read

Update

Delete
```

---

### 4. What are the business rules?

Example:

- Only authors can edit their own posts.
    
- Guests cannot create posts.
    

---

### 5. What validation is needed?

Example:

- Title required.
    
- Content required.
    
- Slug unique.
    

---

### 6. Is authentication required?

Example:

```http
POST /posts
```

Yes.

---

### 7. Is authorization required?

Example:

Can this user edit **this** post?

---

### 8. What should the response look like?

```json
{
  "success": true,
  "data": { }
}
```

---

### 9. Which HTTP status code fits?

Examples:

```http
200 OK

201 Created

204 No Content

400 Bad Request

401 Unauthorized

403 Forbidden

404 Not Found
```

# Common Mistakes

### ❌ Jumping directly to Express routes

```javascript
router.post("/posts")
```

without understanding the business rules.

---

### ❌ Forgetting authorization

Authenticated users are **not** automatically allowed to modify every resource.

---

### ❌ Creating unnecessary endpoints

```http
POST /publishPost
```

The `POST /posts` endpoint already represents publishing a new post.

---

### ❌ Mixing business rules with endpoint design

Endpoints identify **what** you're interacting with. Business rules decide **whether** the action is allowed.

---

# Best Practices

- Start with user stories, not routes.
    
- Identify actors and resources first.
    
- Write down business rules explicitly.
    
- Design endpoints using REST conventions.
    
- Think about authentication and authorization early.
    
- Decide on validation before implementation.
    
- Keep API contracts consistent across all endpoints.

# Interview Questions

### 1. How do you convert a user story into an API endpoint?

**Answer:**  
I identify the actor, determine the resource being managed, understand the business rules and validations, choose the appropriate HTTP method, design the endpoint using REST conventions, and define the request, response, and status codes.

---

### 2. Why should API design begin with user stories?

**Answer:**  
User stories capture the business requirements from the user's perspective. Designing APIs from these stories ensures the endpoints solve real business problems rather than reflecting implementation details.

---

### 3. What's the difference between authentication and authorization in API design?

**Answer:**  
Authentication verifies the user's identity (e.g., through a JWT or session). Authorization determines whether that authenticated user has permission to perform a specific action on a particular resource.

# 💡 Backend Engineering Insight

A junior developer often asks:

> **"What endpoint should I create?"**

A senior backend engineer asks:

> **"What business problem am I solving?"**

That's a subtle but important shift in mindset.

If you always start with the business problem, the right resources, HTTP methods, validations, and authorization rules usually become much easier to identify.
