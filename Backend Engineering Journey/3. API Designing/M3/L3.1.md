# Lesson 3.1 — What is REST?

> **Goal:** Understand what REST really is, where it came from, and why it became the standard for web APIs.

- Recognize the characteristics of a RESTful API.

# What is REST?

**REST** stands for:

> **Representational State Transfer**

It is **not**:

- a programming language ❌
    
- a framework ❌
    
- a library ❌
    
- a protocol ❌
    

REST is an **architectural style** for designing networked applications.

Think of REST as a **set of design principles** rather than a strict set of rules.

---

# Why Was REST Created?

Before REST became popular, web services were often complex and tightly coupled.

Developers wanted a simpler way for different systems to communicate over the web.

In 2000, **Roy Fielding** described REST in his doctoral dissertation as an architectural style for distributed systems.

The goal was to make systems:

- Simpler
    
- More scalable
    
- Easier to understand
    
- Easier to evolve
    

---

# REST Uses HTTP

REST is built on top of HTTP.

Think of the relationship like this:

```text
HTTP = Communication Protocol

REST = Design Style Using HTTP
```

HTTP defines:

- GET
    
- POST
    
- PATCH
    
- DELETE
    
- Headers
    
- Status codes
    

REST defines:

- How to organize resources
    
- How clients interact with them
    
- Architectural constraints
    

---

# REST Is About Resources

REST revolves around **resources**.

Examples:

```text
User

Post

Comment

Order

Product
```

Each resource has its own URI.

Example:

```http
/users

/posts

/comments

/orders
```

Clients interact with these resources using HTTP methods.

---

# REST Request Flow

Suppose a user wants to read blog posts.

```text
Browser
     │
GET /posts
     │
     ▼
Backend API
     │
Retrieve Posts
     │
     ▼
Database
     │
     ▼
JSON Response
```

REST doesn't care whether the database is:

- MongoDB
    
- PostgreSQL
    
- MySQL
    
- SQLite
    

The client only interacts with the API.

---

# Why "Representational State Transfer"?

The name sounds complicated, but it's actually describing a simple idea.

Suppose this post exists:

```json
{
    "id": 1,
    "title": "REST APIs",
    "author": "Rahul"
}
```

This JSON is a **representation** of the resource.

The actual resource lives inside the database.

The API sends a representation of that resource to the client.

Similarly, when the client updates a post:

```json
{
    "title": "Advanced REST APIs"
}
```

it sends another representation back to the server.

The **state** of the resource changes through these representations.

---

# Example

Database:

```text
Post

ID: 10

Title:
REST Basics

Content:
...
```

Representation sent to the client:

```json
{
    "id": 10,
    "title": "REST Basics"
}
```

The client never accesses the database directly.

It only sees representations.

# What Makes an API RESTful?

A RESTful API generally:

- Uses resources (nouns).
    
- Uses HTTP methods correctly.
    
- Is stateless.
    
- Returns resource representations.
    
- Uses meaningful status codes.
    
- Has a consistent interface.
    

Example:

```http
GET /posts

POST /posts

PATCH /posts/15

DELETE /posts/15
```

This follows REST conventions.

---

# REST Is Not Just CRUD

Many beginners think:

```text
REST = CRUD
```

That's incomplete.

CRUD is only one part.

REST also emphasizes:

- Resource identification
    
- Stateless communication
    
- Uniform interfaces
    
- Cacheability
    
- Layered architecture
    
- Client-server separation
    

These architectural ideas are what make REST scalable.

---

# REST vs HTTP

Many people confuse these terms.

|HTTP|REST|
|---|---|
|Protocol|Architectural style|
|Defines request/response communication|Defines how to design APIs using HTTP|
|Includes methods and status codes|Includes resource-oriented design and constraints|

You can use HTTP without following REST.

Example:

```http
POST /getUsers
```

This uses HTTP correctly but is not considered good REST design.

---

# REST vs RPC

Imagine you want to delete a post.

### RPC Style

```http
POST /deletePost
```

The endpoint describes the action.

---

### REST Style

```http
DELETE /posts/15
```

The endpoint identifies the resource.

The HTTP method expresses the action.

This separation makes APIs more predictable.

---

# REST Encourages Consistency

Imagine an application with these endpoints:

```http
GET /users

POST /users

PATCH /users/15

DELETE /users/15
```

Now add products.

Without REST:

```http
POST /createProduct

POST /updateProduct

POST /deleteProduct
```

Completely different style.

With REST:

```http
GET /products

POST /products

PATCH /products/15

DELETE /products/15
```

The consistency makes APIs easier to learn and use.

- Easy to understand
    
- Language independent
    
- Platform independent
    
- Widely supported
    
- Scalable
    
- Predictable
    
- Easy to document
    
- Easy to consume from web and mobile applications

# Does REST Have to Use JSON?

No.

REST can return many representations.

Examples:

- JSON
    
- XML
    
- HTML
    
- Plain text
    

Today, JSON is the most common because it's lightweight and easy to work with.

---

# REST Is an Architectural Style, Not a Law

You'll sometimes hear:

> "This API isn't truly RESTful."

That's because REST is a style with guiding principles.

Real-world APIs often make practical trade-offs.

For example:

```http
POST /auth/login
```

This isn't a pure resource-oriented endpoint, but it's a common and practical convention.

Understanding the principles helps you know **when** and **why** exceptions are reasonable.

---

# Common Misconceptions

### ❌ REST = JSON

Wrong.

JSON is just a common representation format.

---

### ❌ REST = HTTP

Wrong.

REST uses HTTP but is not HTTP.

---

### ❌ Every API is REST

Wrong.

Some APIs follow:

- GraphQL
    
- gRPC
    
- SOAP
    
- RPC
    
- WebSockets
    

REST is only one architectural style.

---

### ❌ REST Means Only CRUD

Wrong.

REST includes broader architectural principles like statelessness, cacheability, and a uniform interface.

---

# Best Practices

- Think in terms of resources.
    
- Use HTTP methods according to their meaning.
    
- Keep APIs consistent.
    
- Return meaningful representations.
    
- Separate clients from server implementation details.
    
- Learn the principles before memorizing endpoint patterns.

# Interview Questions

### 1. What is REST?

**Answer:**  
REST (Representational State Transfer) is an architectural style for designing networked applications. It defines principles for building scalable, resource-oriented APIs using standard HTTP methods.

---

### 2. What is the difference between REST and HTTP?

**Answer:**  
HTTP is the communication protocol that defines requests, responses, methods, and status codes. REST is an architectural style that uses HTTP to design consistent, resource-oriented APIs.

---

### 3. Why is REST so widely used?

**Answer:**  
REST is simple, stateless, scalable, language-independent, and works well with the existing web infrastructure. Its consistent conventions make APIs easier to understand, document, and maintain.

---

# 💡 Backend Engineering Insight

One thing you'll notice in professional backend teams is that they rarely ask:

> **"Is this endpoint RESTful?"**

Instead, they ask:

- Is it **consistent**?
    
- Is it **predictable**?
    
- Is it **easy for API consumers to understand**?
    
- Does it follow our team's API conventions?
    

REST provides a strong foundation, but real-world engineering is about applying its principles thoughtfully rather than following them rigidly.
