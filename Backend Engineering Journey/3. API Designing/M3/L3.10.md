# Why This Lesson Matters

Many APIs work correctly but are difficult to maintain.

For example:

```http
POST /getUsers
POST /updateUser
POST /deleteUser
```

The API functions, but it ignores REST conventions and becomes inconsistent as it grows.

Professional backend engineers don't just build APIs that work—they build APIs that are **predictable, easy to understand, and easy to extend**.

---

# Mistake 1 — Using Verbs in URIs

### ❌ Bad

```http
POST /createPost
POST /updatePost
POST /deletePost
```

---

### ✅ Good

```http
POST   /posts
PATCH  /posts/:id
DELETE /posts/:id
```

### Why?

The URI identifies the **resource**.

The HTTP method expresses the **action**.

---

# Mistake 2 — Using POST for Everything

Some beginners write:

```http
POST /getUsers
POST /getPosts
POST /deleteComment
POST /loginUser
```

---

### Better

```http
GET /users
GET /posts
DELETE /comments/:id
POST /auth/login
```

Each HTTP method has semantic meaning.

Using the correct method allows:

- Browsers
    
- Caches
    
- Proxies
    
- Other developers
    

to understand your API.

---

# Mistake 3 — Returning `200 OK` for Every Response

### ❌ Bad

Validation failed:

```http
200 OK
```

```json
{
  "error": "Email already exists"
}
```

---

### ✅ Better

```http
409 Conflict
```

```json
{
  "success": false,
  "message": "Email already exists"
}
```

Use status codes correctly.

# Common Status Codes

|Situation|Status|
|---|---|
|Success|200 OK|
|Resource Created|201 Created|
|No Content|204 No Content|
|Invalid Input|400 Bad Request|
|Authentication Required|401 Unauthorized|
|Permission Denied|403 Forbidden|
|Resource Not Found|404 Not Found|
|Duplicate Resource|409 Conflict|

|Server Error|500 Internal Server Error|

# Mistake 4 — Inconsistent Response Formats

Endpoint A:

```json
{
  "data": {}
}
```

Endpoint B:

```json
{
  "result": {}
}
```

Endpoint C:

```json
{
  "post": {}
}
```

Frontend developers now need different parsing logic.

---

### Better

Success:

```json
{
  "success": true,
  "data": {}
}
```

Error:

```json
{
  "success": false,
  "message": "Validation failed"
}
```

Consistency reduces bugs.

---

# Mistake 5 — Exposing Database Details

Database:

```text
posts
```

Internal fields:

```text
_id
__v
passwordHash
internalNotes
```

Don't expose unnecessary internal information.

---

### Bad

```json
{
  "_id": "...",
  "__v": 2,
  "passwordHash": "...",
  "internalNotes": "..."
}
```

---

### Better

```json
{
  "id": 15,
  "title": "REST API Design",
  "author": "Rahul"
}
```

The API should expose only what clients need.

---

# Mistake 6 — Deeply Nested Resources

### Bad

```http
/users/5/posts/12/comments/8/replies/3
```

Difficult to read.

Hard to maintain.

---

### Better

```http
/comments/8/replies
```

or

```http
/replies/3
```

Keep nesting shallow.

A common guideline is:

> Maximum two levels.

---

# Mistake 7 — Poor Resource Naming

### Bad

```http
/getUsers
/userList
/fetchPosts
```

---

### Better

```http
/users
/posts
/comments
/orders
```

Use plural nouns.

---

# Mistake 8 — Wrong Use of Query Parameters

### Bad

```http
GET /posts?id=15
```

This identifies a single resource.

---

### Better

```http
GET /posts/15
```

Use query parameters only for:

- Filtering
    
- Sorting
    
- Searching
    
- Pagination
    

---

Good examples:

```http
GET /posts?page=2
```

```http
GET /posts?search=node
```

```http
GET /posts?category=backend
```

---

# Mistake 9 — Ignoring Idempotency

Suppose:

```http
POST /payments
```

User retries.

Payment processed twice.

---

Professional APIs prevent duplicate operations using:

- Idempotency keys
    
- Unique database constraints
    
- Retry-safe design
    

---

# Mistake 10 — Ignoring Validation

Request:

```json
{
  "title": ""
}
```

Without validation:

Database receives bad data.

---

Validate:

- Required fields
    
- Length
    
- Format
    
- Business rules
    

before saving.

---

# Mistake 11 — Mixing Business Logic with Routing

Controller:

```javascript
router.post("/posts", async (req, res) => {
    // 300 lines of business logic
});
```

Difficult to maintain.

---

Better:

```text
Controller

↓

Service

↓

Repository

↓

Database
```

Each layer has a clear responsibility.

---

# Mistake 12 — Leaking Internal Errors

### Bad

```json
{
  "error": "MongoServerError: E11000 duplicate key..."
}
```

Users don't need internal database details.

---

Better

```json
{
  "success": false,
  "message": "Email already exists."
}
```

Log detailed errors internally.

Return safe, user-friendly messages externally.

---

# Mistake 13 — No API Versioning

Version 1:

```http
GET /users
```

Later:

Breaking changes.

Old mobile app stops working.

---

Better:

```http
GET /v1/users
```

Future:

```http
GET /v2/users
```

This allows older clients to continue functioning while newer clients migrate.

---

# Mistake 14 — Ignoring Pagination

Imagine:

```http
GET /posts
```

Returns:

```text
2 million posts
```

Huge response.

---

Better:

```http
GET /posts?page=1&limit=20
```

Smaller, faster, and easier to consume.

---

# Mistake 15 — Ignoring Security

Common mistakes:

- No authentication
    
- No authorization
    
- No rate limiting
    
- No input sanitization
    
- No CORS configuration
    
- No HTTPS
    

Security should be part of the design, not an afterthought.

---

# Mistake 16 — Inconsistent Naming

Users:

```http
/users
```

Products:

```http
/getProducts
```

Orders:

```http
/orderList
```

Every endpoint feels different.

---

Instead:

```http
/users
/products
/orders
/comments
```

Maintain one naming convention across the entire API.

---

# Mistake 17 — Not Thinking About Future Growth

Current endpoint:

```http
GET /posts
```

Later:

Need:

- Search
    
- Pagination
    
- Filtering
    
- Sorting
    

Professional design anticipates evolution.

Example:

```http
GET /posts?search=node&page=2&sort=-createdAt
```

# REST API Design Checklist

Before implementing an endpoint, ask yourself:

### Resource

- Does the URI represent a resource?
    
- Is it a noun?
    
- Is it plural?
    

---

### HTTP Method

- Am I using the correct method?
    
- Is it safe?
    
- Is it idempotent where appropriate?
    

---

### URI

- Lowercase?
    
- Hyphenated if needed?
    
- Shallow nesting?
    
- Path parameters used only for resource identification?
    

---

### Query Parameters

- Filtering?
    
- Searching?
    
- Sorting?
    
- Pagination?
    

---

### Validation

- Required fields?
    
- Correct format?
    
- Business rules?
    

---

### Authentication

- Who is the user?
    

---

### Authorization

- Can this user perform this action?
    

---

### Responses

- Correct status code?
    
- Consistent response format?
    

---

### Security

- Input sanitized?
    
- Rate limited?
    
- Authentication enforced?
    
- Sensitive data hidden?
    

---

### Performance

- Pagination?
    
- Caching?
    
- Efficient queries?
    
- Appropriate indexes?
    

---

### Documentation

- Endpoint documented?
    
- Request examples?
    
- Response examples?
    
- Error cases?

# Professional API Example

```http
GET    /posts

GET    /posts/:id

POST   /posts

PATCH  /posts/:id

DELETE /posts/:id

GET    /posts?search=node

GET    /posts?page=2&limit=20

POST   /posts/:id/comments

GET    /posts/:id/comments
```

Notice:

- Consistent
    
- Predictable
    
- Resource-oriented
    
- Scalable

# Best Practices

- Think in terms of resources.
    
- Keep URIs clean and consistent.
    
- Use HTTP methods correctly.
    
- Return meaningful status codes.
    
- Validate all incoming data.
    
- Hide implementation details.
    
- Design with scalability and future growth in mind.
    
- Document every public API.
    

---

# Key Terms

|Term|Meaning|
|---|---|

|Endpoint|Combination of URI and HTTP method|
|Validation|Ensuring incoming data meets requirements|
|Pagination|Dividing large datasets into smaller pages|
|Versioning|Supporting API evolution without breaking existing clients|

# Interview Questions

### 1. What are some common REST API design mistakes?

**Answer:**  
Common mistakes include using verbs in URIs, using `POST` for every operation, returning incorrect HTTP status codes, exposing database internals, inconsistent response formats, deep URI nesting, ignoring pagination, and lacking API versioning.

---

### 2. Why should APIs avoid exposing database fields?

**Answer:**  
Database schemas are implementation details that may change over time. Exposing internal fields couples clients to the database structure, increases security risks, and makes future refactoring more difficult.

---

### 3. Why is consistency so important in API design?

**Answer:**  
Consistency makes APIs easier to learn, consume, document, test, and maintain. It reduces frontend complexity because clients can interact with different resources using the same patterns.

---

### 4. Why should pagination be included in API design?

**Answer:**  
Returning very large collections in a single response increases bandwidth usage, memory consumption, and response time. Pagination improves performance, scalability, and user experience.

```text

      ↓
Validation
      ↓
Authentication
      ↓
Authorization
      ↓

      ↓
Performance
      ↓

```

This structured thinking catches many design problems before any code is written.

A well-designed API is often the result of **careful planning**, not just good programming.
