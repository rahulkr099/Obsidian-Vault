# What are REST Constraints?

When Roy Fielding introduced REST, he didn't define it as a list of endpoints or HTTP methods.

Instead, he defined **architectural constraints**.

Think of them as design principles.

If an API follows these principles, it is considered more RESTful.

These constraints make systems:

- Easier to scale
    
- Easier to maintain
    
- Easier to evolve
    
- Easier to understand
    

---

# The Six REST Constraints

```text
REST
 │
 ├── Client-Server
 ├── Stateless
 ├── Cacheable
 ├── Uniform Interface
 ├── Layered System
 └── Code on Demand (Optional)
```

We'll study each one in detail.

---

# 1. Client–Server Constraint

## Definition

The client and server must have **separate responsibilities**.

The client is responsible for:

- User Interface (UI)
    
- User interactions
    
- Sending requests
    
- Displaying responses
    

The server is responsible for:

- Business logic
    
- Authentication
    
- Authorization
    
- Database operations
    
- Validation
    

---

## Diagram

```text
Client (React)
      │
HTTP Request
      │
      ▼
Backend API
      │
      ▼
Database
```

The client never communicates directly with the database.

---

## Blog App Example

User clicks:

```text
Publish Post
```

Frontend:

```http
POST /posts
```

Backend:

- Validate request
    
- Authenticate user
    
- Save post
    
- Return response
    

Frontend:

Displays:

```text
Post published successfully.
```

Each side has its own responsibility.

---

## Benefits

- Frontend and backend can be developed independently.
    
- Mobile apps and web apps can use the same backend.
    
- Backend implementation can change without affecting clients.
    

Example:

```text
React App
Android App
iOS App
Admin Panel
        │
        ▼
REST API
```

One backend supports multiple clients.

---

# 2. Stateless Constraint

This is probably the most important REST constraint.

---

## Definition

Every HTTP request must contain **all the information** needed to process it.

The server should **not remember previous requests**.

Each request is independent.

---

## Example

Request:

```http
GET /posts
Authorization: Bearer <token>
```

Tomorrow:

```http
GET /posts
Authorization: Bearer <token>
```

The server treats both requests independently.

---

## Wrong Mental Model

Some beginners think:

```text
User logged in yesterday.

↓

Server remembers forever.
```

REST does **not** work this way.

The client must send authentication information with every protected request (or through mechanisms like cookies that accompany each request).

---

## Why Stateless?

Imagine 1 million users.

If the server had to remember every user's previous request:

```text
Server
 ├── User 1 State
 ├── User 2 State
 ├── User 3 State
 ├── ...
 └── User 1,000,000 State
```

Memory usage grows quickly.

Stateless APIs avoid this problem.

---

## Benefits

- Easier to scale.
    
- Easier to load balance.
    
- Easier to recover after crashes.
    
- Simpler architecture.
    

---

# 3. Cacheable Constraint

Some responses can be reused instead of regenerated.

Example:

```http
GET /categories
```

Categories rarely change.

Instead of asking the server every time:

```text
Browser
     │
Cache
     │
     ▼
API
```

The browser (or another cache) can reuse the previous response if allowed.

---

## Blog Example

Homepage:

```http
GET /posts?page=1
```

If nothing changed recently, a cached response may be used.

This reduces:

- Server load
    
- Database queries
    
- Response time
    

---

## Benefits

- Faster APIs.
    
- Lower server costs.
    
- Better user experience.
    

We'll explore HTTP caching headers and ETags in a later module.

# 4. Uniform Interface

This is the heart of REST.

Every resource should follow the same design conventions.

---

Instead of:

```http
GET /fetchPosts

POST /createPost

POST /updatePost
```

REST uses:

```http
GET /posts

POST /posts

PATCH /posts/:id

DELETE /posts/:id
```

Every resource follows a similar pattern.

---

## Consistency Example

Users:

```http
GET /users

POST /users

PATCH /users/:id
```

Products:

```http
GET /products

POST /products

PATCH /products/:id
```

Orders:

```http
GET /orders

POST /orders

PATCH /orders/:id
```

Developers don't have to learn a different style for every resource.

---

## Uniform Interface Includes

- Resource-oriented URLs
    
- Standard HTTP methods
    
- Consistent response formats
    
- Predictable status codes
    

This consistency is one reason REST APIs are easy to use.

---

# 5. Layered System

A client doesn't need to know how many layers exist between it and the server.

Example:

```text
Client
   │
Load Balancer
   │
API Gateway
   │
Authentication Service
   │
Backend API
   │
Database
```

The client simply sends:

```http
GET /posts
```

It doesn't care whether the request passes through:

- Reverse proxy
    
- CDN
    
- Firewall
    
- API Gateway
    
- Load Balancer
    

---

## Why Layers?

Layers provide:

- Security
    
- Scalability
    
- Monitoring
    
- Logging
    
- Rate limiting
    
- Caching
    

without changing the client.

---

# 6. Code on Demand (Optional)

This is the only optional REST constraint.

The server may send executable code to the client.

Examples:

- JavaScript
    
- WebAssembly
    

For example:

```text
Browser
      │
HTML
CSS
JavaScript
```

The browser downloads JavaScript and executes it.

Modern REST APIs rarely rely on this constraint directly, which is why it is considered optional.

---

# Summary of All Constraints

|Constraint|Purpose|
|---|---|
|Client–Server|Separate responsibilities|
|Stateless|Each request is independent|
|Cacheable|Improve performance|
|Uniform Interface|Consistent API design|
|Layered System|Hide internal architecture|
|Code on Demand|Optional client-side executable code|

Imagine you're using an online shopping app.

You request:

```http
GET /products
```

Behind the scenes:

```text
Mobile App
     │
CDN
     │
Load Balancer
     │
API Gateway
     │
Authentication
     │
Backend
     │
Redis Cache
     │
Database
```

You only see:

```json
[
  {
    "id": 1,
    "name": "Laptop"
  }
]
```

That's the power of REST constraints.

# Common Misconceptions

## ❌ Stateless Means No Login

Wrong.

You can absolutely have authentication in a REST API.

The important point is that **each request contains the information needed for authentication** (for example, an access token or an authenticated cookie).

---

## ❌ Layered System Means Microservices

Wrong.

A layered system can exist in:

- Monoliths
    
- Microservices
    
- Serverless architectures
    

It's about separating concerns, not choosing a deployment style.

---

## ❌ Cache Means Only Browser Cache

Wrong.

Responses can be cached by:

- Browsers
    
- CDNs
    
- Reverse proxies
    
- API gateways
    
- Backend caches
    

---

## ❌ REST Requires JSON

Wrong.

REST is independent of the data format.

JSON is simply the most common representation.

---

# Best Practices

- Keep client and server responsibilities separate.
    
- Design APIs to be stateless.
    
- Use HTTP caching where appropriate.
    
- Follow consistent naming and response conventions.
    
- Design systems that can grow by adding layers without affecting clients.
    
- Use Code on Demand only when it genuinely adds value.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Constraint|A rule or principle that guides REST architecture|
|Stateless|Every request is self-contained|
|Cacheable|Responses may be reused to improve performance|
|Uniform Interface|Consistent interaction with resources|
|Layered System|Multiple hidden infrastructure layers between client and server|
|Code on Demand|Optional ability for the server to send executable code|

# Interview Questions

### 1. What are the six REST constraints?

**Answer:**

1. Client–Server
    
2. Stateless
    
3. Cacheable
    
4. Uniform Interface
    
5. Layered System
    
6. Code on Demand (optional)
    

---

### 2. Why is statelessness important in REST?

**Answer:**  
Statelessness ensures that every request is independent and contains all the information required for processing. This simplifies server design, improves scalability, and makes load balancing easier.

---

### 3. What is the purpose of the Uniform Interface constraint?

**Answer:**  
The Uniform Interface provides consistent ways to identify resources, use HTTP methods, and structure responses. This predictability makes APIs easier to understand, document, and maintain.

---

### 4. Why is Code on Demand considered optional?

**Answer:**  
Unlike the other five constraints, a REST system can still be considered RESTful without sending executable code to clients. It's an optional capability that can enhance functionality in some scenarios but is not required.

# 💡 Backend Engineering Insight

Many interviewers ask:

> **"What is REST?"**

A weak answer is:

> "REST uses GET, POST, PUT, PATCH, and DELETE."

A strong answer is:

> "REST is an architectural style defined by Roy Fielding. It is based on six constraints—Client–Server, Statelessness, Cacheability, Uniform Interface, Layered System, and the optional Code on Demand. These constraints help build scalable, maintainable, and loosely coupled distributed systems."

That answer demonstrates you understand the **architecture**, not just the syntax.
