> **Goal:** Learn how to distinguish between resources and actions, and design clean REST APIs even for operations like login, logout, publish, like, and password reset that don't fit neatly into CRUD.

# Learning Objectives

After this lesson, you should be able to:

- Differentiate between resources and actions.
    
- Identify whether a requirement should become a resource or an action.
    
- Design RESTful endpoints for non-CRUD operations.

# Why This Lesson Matters

One of the most common mistakes beginners make is designing APIs around **actions**.

Example:

```http
POST /createPost

POST /deletePost

POST /updatePost

POST /publishPost

POST /loginUser
```

These APIs work, but they don't follow REST principles well.

Professional backend engineers first ask:

> **"What resource is being managed?"**

---

# Resource vs Action

## Resource

A **resource** is a business entity.

Examples:

```text
User

Post

Comment

Order

Product

Payment
```

Resources are usually **nouns**.

---

## Action

An **action** is something performed on a resource.

Examples:

```text
Create

Read

Update

Delete

Publish

Like

Archive

Reset Password
```

Actions are usually **verbs**.

---

# The Golden Rule

Think of an API as a sentence.

```text
HTTP Method  +  Resource

↓

Verb         +  Noun
```

Example:

```http
POST /posts
```

Read it as:

> Create a post.

Another:

```http
DELETE /posts/15
```

Read it as:

> Delete post 15.

The HTTP method already expresses the action.

Correct:

POST /posts
```

```

---

Requirement:

# Thinking Like a Backend Engineer

Don't ask:

> "What endpoint should I create?"

Instead ask:

> "What resource is changing?"

# Real-World Examples

Requirement:

> Customer places an order.

Resource:

```text
Order
```

Endpoint:

```http
POST /orders
```

---

Requirement:

> Customer updates shipping address.

Resource:

```text
Order
```

Endpoint:

```http
PATCH /orders/:id
```

---

Requirement:

> Customer cancels order.

Resource:

Still:

```text
Order
```

Possible endpoint:

```http
PATCH /orders/:id
```

Body:

```json
{
    "status": "cancelled"
}
```

Notice something?

We didn't create:

```http
POST /cancelOrder
```

Instead, we updated the **state** of the resource.

---

# State Changes vs Actions

Suppose a blog post can be:

```text
Draft

↓

Published

↓

Archived

↓

Deleted
```

These are **states**.

Publishing isn't necessarily a new action endpoint.

It may simply be:

```http
PATCH /posts/:id
```

Request:

```json
{
    "status": "published"
}
```

The resource changed state.

---

# Example — Archive Post

Instead of:

```http
POST /archivePost
```

Use:

```http
PATCH /posts/:id
```

```json
{
    "status": "archived"
}
```

Again, REST focuses on **resource state**.

---

# Example — Mark Todo Complete

Wrong:

```http
POST /completeTask
```

Better:

```http
PATCH /tasks/:id
```

```json
{
    "completed": true
}
```

Even better:

```json
{
    "status": "completed"
}
```

# When Actions Become Resources

Some actions involve their own data and lifecycle.

Example:

Likes.

Requirement:

> User likes a post.

Question:

Is "Like" just an action?

Not always.

A like has data:

```text
userId

postId

createdAt
```

That's enough to treat it as a resource.

Endpoint:

```http
POST /posts/:id/likes
```

Remove:

```http
DELETE /posts/:id/likes
```

---

# Comments

Requirement:

> User comments on a post.

Comment has:

```text
text

author

createdAt
```

Comment is clearly a resource.

Endpoints:

```http
POST /posts/:id/comments

GET /posts/:id/comments
```

---

# Bookmarks

Bookmark contains:

```text
userId

postId

createdAt
```

Resource:

```text
Bookmark
```

Endpoints:

```http
POST /posts/:id/bookmarks

DELETE /posts/:id/bookmarks
```

---

# Followers

Following someone creates a relationship.

Resource:

```text
Follow
```

Endpoints:

```http
POST /users/:id/follow

DELETE /users/:id/follow
```

Some teams also design it as:

```http
POST /follows
```

with:

```json
{
    "followingId": 15
}
```

Both are reasonable. The choice depends on your API conventions and domain model.

---

# Search

Requirement:

> Search blog posts.

Should we create:

```http
POST /searchPosts
```

No.

Search retrieves resources.

Better:

```http
GET /posts?search=api
```

Searching is simply another way of retrieving the `Post` resource.

---

# Filtering

Requirement:

> Show published posts.

Good:

```http
GET /posts?status=published
```

---

Requirement:

> Show technology posts.

```http
GET /posts?category=technology
```

Filtering doesn't create a new resource.

---

# Sorting

Requirement:

Newest posts first.

```http
GET /posts?sort=-createdAt
```

Again:

Still:

```text
Post
```

Not:

```http
GET /latestPosts
```

---

# Pagination

Requirement:

Show page 3.

Good:

```http
GET /posts?page=3&limit=10
```

No need for:

```http
GET /pageThreePosts
```

---

# Authentication

This is one of the biggest exceptions beginners notice.

Requirement:

User logs in.

Should we write:

```http
POST /users/login
```

or

```http
POST /login
```

Most professional APIs use:

```http
POST /auth/login

POST /auth/logout

POST /auth/refresh
```

Why?

Because authentication is a **domain** or **service** rather than a CRUD resource like `Post` or `Comment`.

Another REST-oriented design is:

```http
POST /sessions
DELETE /sessions/current
```

where a login creates a session resource.

Both styles are seen in real-world APIs.

---

# Password Reset

Wrong:

```http
POST /resetPassword
```

Possible designs:

```http
POST /auth/forgot-password

POST /auth/reset-password
```

Or model the reset request as a resource:

```http
POST /password-reset-tokens
```

Again, different APIs choose different trade-offs.

---

# Email Verification

Common:

```http
POST /auth/verify-email
```

or

```http
POST /email-verification-tokens
```

# Resource Decision Tree

Ask yourself:

```text
Does it represent business data?
           │
     Yes───┴────No
      │           │
      ▼           ▼
 Resource      Is it changing
                  resource state?
                     │
              Yes────┴────No
               │            │
               ▼            ▼
        PATCH existing   Domain/service
          resource       operation
```

# Best Practices

- Model business entities as resources.
    
- Use HTTP methods to represent actions.
    
- Treat state changes as updates to resources where appropriate.
    
- Use query parameters for filtering, searching, sorting, and pagination.
    
- Accept practical exceptions for domains like authentication when they improve clarity.
    
- Keep your API consistent rather than trying to force every endpoint into a rigid pattern.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Resource|A business entity managed by the API|
|Action|An operation performed on a resource|
|Resource State|The current condition of a resource (e.g., draft, published)|
|Domain Operation|An operation related to a specific business domain, such as authentication|
|Query Parameter|Additional information used to filter or modify retrieval of resources|

# Interview Questions

### 1. What is the difference between a resource and an action?

**Answer:**  
A resource is a business entity managed by the API, such as a `User` or `Post`. An action is an operation performed on that resource, such as creating, updating, or deleting it. In REST, URLs identify resources, while HTTP methods express actions.

---

### 2. Why is `POST /createPost` considered poor REST design?

**Answer:**  
Because the URL includes a verb. In REST, the endpoint should identify the resource (`/posts`), and the HTTP method (`POST`) already communicates that the operation is to create a new resource.

---

### 3. Why do many APIs use `/auth/login` instead of `/sessions`?

**Answer:**  
`/auth/login` is a practical and widely recognized convention that is easy for developers to understand. Modeling login as `POST /sessions` is more resource-oriented because it treats a session as the resource being created. Both approaches are valid, and teams choose based on consistency, clarity, and project conventions.

---

# 💡 Backend Engineering Insight

A useful question to ask whenever you're designing an endpoint is:

> **"Am I creating a new thing, changing an existing thing, or simply retrieving things?"**

For example:

|Requirement|Think Like a Backend Engineer|Endpoint|
|---|---|---|
|Publish a post|Change the post's state|`PATCH /posts/:id`|
|Like a post|Create a Like resource|`POST /posts/:id/likes`|
|Search posts|Retrieve Posts with filters|`GET /posts?search=api`|
|Update profile picture|Update part of a User|`PATCH /users/:id`|

This mindset helps you design APIs that are consistent, intuitive, and much easier to extend as your application grows.
