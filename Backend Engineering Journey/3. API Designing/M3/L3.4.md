# Why URI Design Matters

A URI (Uniform Resource Identifier) is the **address of a resource**.

Example:

```http
GET /posts
```

When another developer sees this endpoint, they should immediately understand:

- What resource it represents.
    
- What kind of data it returns.
    
- How it relates to other endpoints.
    

A well-designed URI is **self-explanatory**.

---

# What is a URI?

In REST, a URI identifies a resource.

Examples:

```http
/users

/posts

/comments

/orders
```

Notice something?

Every URI identifies a **resource**, not an action.

---

# Rule 1 — Use Nouns, Not Verbs

❌ Bad

```http
/createUser

/getPosts

/deleteComment

/updateProfile
```

---

✅ Good

```http
/users

/posts

/comments

/profiles
```

The HTTP method already tells us the action.

Example:

```http
POST /users
```

Read it as:

> Create a user.

---

# Rule 2 — Use Plural Resource Names

Professional APIs almost always use plural nouns.

✅ Good

```http
/users

/posts

/orders

/products
```

---

❌ Avoid

```http
/user

/post

/order

/product
```

---

## Why Plural?

Think of every endpoint as a **collection**.

Example:

```http
GET /users
```

Returns:

```json
[
  { "id": 1 },
  { "id": 2 }
]
```

Even:

```http
GET /users/15
```

means:

> Retrieve **User 15** from the **Users collection**.

This keeps the API consistent.

---

# Rule 3 — Use Lowercase Letters

✅ Good

```http
/users

/blog-posts

/order-items
```

---

❌ Avoid

```http
/Users

/BlogPosts

/ORDER
```

URLs are easier to read and less error-prone when consistently lowercase.

---

# Rule 4 — Use Hyphens for Multiple Words

Multiple-word resources should use **hyphens (`-`)**.

✅ Good

```http
/blog-posts

/order-items

/user-profiles
```

---

❌ Avoid camelCase

```http
/blogPosts

/orderItems
```

---

❌ Avoid snake_case

```http
/blog_posts

/order_items
```

---

Why?

Hyphens are easier to read and are the most widely recommended convention for URIs.

---

# Rule 5 — Don't Include File Extensions

❌ Bad

```http
/posts.json

/users.xml
```

---

✅ Good

```http
/posts

/users
```

The response format is determined by headers (such as `Accept`), not by the URL.

---

# Rule 6 — Keep URIs Simple

Good:

```http
/users

/posts

/comments
```

---

Avoid:

```http
/allUsersList

/blogArticlesCollection

/getEveryComment
```

Simple names are easier to remember.

---

# Rule 7 — Resource Hierarchy

Suppose:

A post has comments.

Hierarchy:

```text
Post
 └── Comment
```

URI:

```http
/posts/15/comments
```

Meaning:

Comments belonging to Post 15.

---

Another example:

```text
Customer
 └── Order
```

URI:

```http
/customers/5/orders
```

This clearly communicates the relationship.

---

# Rule 8 — Avoid Deep Nesting

Bad:

```http
/users/5/posts/10/comments/4/replies/7
```

Hard to read.

---

Better:

```http
/comments/4/replies
```

or

```http
/replies/7
```

---

A common recommendation:

**Maximum two levels of nesting.**

---

# Rule 9 — Path Parameters vs Query Parameters

This is one of the most common interview questions.

---

## Path Parameters

Use path parameters to identify a **specific resource**.

Example:

```http
GET /posts/15
```

Here:

```text
15
```

identifies a specific post.

---

Another:

```http
GET /users/22
```

Specific user.

---

## Query Parameters

Use query parameters to:

- Filter
    
- Search
    
- Sort
    
- Paginate
    
- Select fields
    

Example:

```http
GET /posts?category=backend
```

---

Search:

```http
GET /posts?search=node
```

---

Pagination:

```http
GET /posts?page=2&limit=10
```

---

Sorting:

```http
GET /posts?sort=-createdAt
```

---

Field Selection:

```http
GET /posts?fields=title,author
```

---

# Quick Comparison

Path Parameter:

```http
/posts/15
```

Specific resource.

---

Query Parameter:

```http
/posts?page=2
```

Modifies how a collection is retrieved.

---

# Rule 10 — Don't Encode Actions in the URI

Wrong:

```http
/publishPost

/deleteUser

/archiveOrder
```

---

Better:

```http
PATCH /posts/15
```

Body:

```json
{
    "status": "published"
}
```

REST focuses on the **resource state**, not action-based URLs.

---

# Rule 11 — Keep Naming Consistent

Suppose you use:

```http
/users
```

Don't suddenly write:

```http
/getProducts

/ordersList

/createComment
```

Instead:

```http
/products

/orders

/comments
```

Consistency is more important than personal preference.

---

# Blog API Example

Good API:

```http
GET    /posts
GET    /posts/15

POST   /posts

PATCH  /posts/15

DELETE /posts/15

GET    /posts/15/comments

POST   /posts/15/comments

GET    /categories

GET    /users/15/posts
```

Every endpoint follows the same style.

---

# E-Commerce Example

```http
GET /products

GET /products/25

POST /orders

GET /orders/100

PATCH /orders/100

DELETE /orders/100

GET /customers/8/orders
```

Easy to understand.

---

# Todo App Example

```http
GET /tasks

POST /tasks

PATCH /tasks/15

DELETE /tasks/15

GET /projects/2/tasks
```

Again, the same pattern.

---

# Common Mistakes

### ❌ Verb-based URLs

```http
/createPost
```

---

### ❌ Mixed casing

```http
/GetUsers

/blogPosts

/order_items
```

---

### ❌ Singular and plural mixed

```http
/user

/posts

/comment
```

---

### ❌ Query parameter for a unique resource

Bad:

```http
/posts?id=15
```

Better:

```http
/posts/15
```

---

### ❌ Path parameter for filtering

Bad:

```http
/posts/backend
```

Better:

```http
/posts?category=backend
```

---

# URI Design Checklist

Before finalizing a URI, ask yourself:

- Does it represent a resource?
    
- Is it a noun?
    
- Is it plural?
    
- Is it lowercase?
    
- Does it use hyphens for multiple words?
    
- Is nesting shallow?
    
- Am I using path parameters only for resource identification?
    
- Am I using query parameters for filtering, sorting, searching, and pagination?
    
- Is it consistent with the rest of the API?
    

If the answer is **yes** to all, your URI is likely well-designed.

---

# Best Practices

- Use nouns.
    
- Use plural resource names.
    
- Keep URIs lowercase.
    
- Use hyphens for readability.
    
- Avoid verbs.
    
- Use path parameters for resource identity.
    
- Use query parameters for retrieval options.
    
- Keep nesting limited.
    
- Maintain consistency across the API.

# Interview Questions

### 1. Why do REST APIs usually use plural resource names?

**Answer:**  
Plural names represent collections of resources and provide consistency. For example, `/users` represents the users collection, while `/users/15` identifies a specific user within that collection.

---

### 2. When should you use path parameters instead of query parameters?

**Answer:**  
Use path parameters to identify a specific resource, such as `/posts/15`. Use query parameters to filter, search, sort, paginate, or otherwise modify how a collection of resources is retrieved, such as `/posts?page=2&search=node`.

---

### 3. Why should verbs be avoided in REST URIs?

**Answer:**  
REST URIs identify resources, while HTTP methods express actions. Using nouns keeps APIs consistent, predictable, and aligned with REST principles.

---

# 💡 Backend Engineering Insight

Many beginners memorize URI rules one by one. Professional backend engineers think in terms of **resource identity** versus **resource retrieval options**.

A simple mental model is:

### If it answers **"Which resource?"** → Path Parameter

```http
GET /posts/42
GET /users/7
GET /orders/1001
```

The path uniquely identifies the resource.

---

### If it answers **"How should I retrieve it?"** → Query Parameter

```http
GET /posts?search=api
GET /posts?category=backend
GET /posts?page=2&limit=10
GET /posts?sort=-createdAt
```

The query changes _how_ the collection is returned, not _which_ resource the path identifies.

This distinction will make your APIs much more intuitive and is exactly how experienced backend engineers reason about URI design.
