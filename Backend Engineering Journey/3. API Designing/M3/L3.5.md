# GET Revisited

GET retrieves a representation of a resource.

Example:

```http
GET /posts/15
```

Response:

```json
{
    "id": 15,
    "title": "REST"
}
```

Characteristics:

- Safe
    
- Idempotent
    
- Cacheable
    
- No request body (by convention)
    

---

# Can GET Have a Request Body?

Technically:

HTTP doesn't completely forbid it.

Practically:

**Don't do it.**

Many:

- Browsers
    
- Proxies
    
- Frameworks
    
- Reverse proxies
    

ignore GET request bodies.

Use query parameters instead.

Bad:

```http
GET /posts

Body:
{
    "category":"backend"
}
```

Good:

```http
GET /posts?category=backend
```

---

# POST Revisited

POST creates a new resource.

Example:

```http
POST /posts
```

Body:

```json
{
    "title":"REST"
}
```

POST can also be used for operations that don't neatly fit CRUD, such as:

```http
POST /auth/login

POST /auth/logout

POST /payments
```

---

# PUT Revisited

Remember:

PUT replaces the **entire representation**.

Current resource:

```json
{
    "name":"Rahul",
    "email":"abc@gmail.com",
    "age":22
}
```

PUT request:

```json
{
    "name":"Rahul Kumar",
    "email":"abc@gmail.com",
    "age":22
}
```

Entire resource replaced.

---

# Why PUT is Idempotent

Request:

```http
PUT /users/5
```

Same body:

```json
{
    "name":"Rahul"
}
```

Sent:

1 time

↓

User becomes Rahul

Sent:

100 times

↓

User is still Rahul

Final state is unchanged.

Therefore:

PUT is idempotent.

---

# PATCH Revisited

PATCH updates only selected fields.

Example:

```http
PATCH /users/5
```

```json
{
    "bio":"Backend Engineer"
}
```

Everything else stays unchanged.

---

# PATCH Can Be Non-Idempotent

Example:

```json
{
    "views": "+1"
}
```

Every request increases views.

Request once:

```
Views = 11
```

Request again:

```
Views = 12
```

Different result.

Not idempotent.

---

Better PATCH:

```json
{
    "status":"published"
}
```

Repeated requests:

```
Published
Published
Published
```

Same final state.

---

# DELETE Revisited

DELETE removes a resource.

Example:

```http
DELETE /posts/10
```

After deletion:

Sending DELETE again:

Still deleted.

That's why DELETE is idempotent.

# HEAD Method

Many beginners never hear about HEAD.

HEAD works like GET.

Difference:

No response body.

Example:

```http
HEAD /posts/10
```

Response:

```http
200 OK

Content-Length: 854

Content-Type: application/json
```

No JSON body.

---

# Why Use HEAD?

Suppose you want to know:

- Does the resource exist?
    
- How large is it?
    
- Has it changed?
    

Without downloading the entire response.

Useful for:

- File downloads
    
- Caching
    
- CDNs
    
- Performance optimization
    

---

# OPTIONS Method

OPTIONS asks:

> "What operations are allowed here?"

Example:

```http
OPTIONS /posts
```

Response:

```http
Allow:

GET

POST

OPTIONS
```

---

# Why Browsers Use OPTIONS

This is something every frontend/backend developer eventually encounters.

Imagine:

React App

↓

```text
localhost:5173
```

calls

```text
api.example.com
```

Browser notices:

Different origin.

Before sending:

```http
POST /posts
```

Browser first sends:

```http
OPTIONS /posts
```

This is called a:

## CORS Preflight Request

---

# What Happens?

Browser asks:

```
Can I send this POST request?
```

Server replies:

```
Allowed Origins

Allowed Methods

Allowed Headers
```

Only then does the browser send the actual request.

---

# Typical Flow

```text
Browser
    │
OPTIONS /posts
    │
Server
    │
200 OK
    │
Browser
    │
POST /posts
```

This is why you sometimes see two requests in the browser's Network tab.

---

# If CORS Fails

Browser stops.

Actual POST is never sent.

This explains many common frontend/backend integration issues.

---

# TRACE Method

TRACE is used for diagnostics.

Example:

```http
TRACE /posts
```

Server echoes the request.

Useful for debugging.

Rarely enabled today because of security concerns.

---

# CONNECT Method

Used by proxies.

Example:

Browser

↓

Proxy

↓

HTTPS Server

CONNECT creates a tunnel between the client and the destination.

Most application developers never implement CONNECT themselves.

Safe:


Unsafe:


# Cacheable Methods

Usually cacheable:

```http
GET

HEAD
```

Sometimes:

POST can be cached with explicit headers, but this is uncommon.

PUT, PATCH, and DELETE are generally not cached.

# Common Mistakes

### ❌ Using POST for everything

```http
POST /getUsers

POST /deleteUser
```

---

### ❌ Ignoring OPTIONS

Then wondering why CORS fails.

---

### ❌ Sending body with GET

Many servers ignore it.

Use query parameters.

---

### ❌ Using PUT for every update

Most updates are partial.

PATCH is often a better choice.

---

### ❌ Forgetting HEAD exists

HEAD can save bandwidth when you only need metadata.

---

# Best Practices

- Use HTTP methods according to their semantics.
    
- Use `PATCH` for partial updates.
    
- Reserve `PUT` for complete replacement.
    
- Never rely on a GET request body.
    
- Understand that browsers may automatically send `OPTIONS` requests because of CORS.
    
- Use `HEAD` when you only need response metadata.

# Key Terms

|Term|Meaning|
|---|---|
|HEAD|Returns headers without a response body|
|OPTIONS|Returns supported methods and is used for CORS preflight|
|TRACE|Diagnostic method that echoes the request|
|CONNECT|Creates a tunnel, commonly through an HTTP proxy|
|Preflight Request|An `OPTIONS` request sent by the browser before certain cross-origin requests|

# Interview Questions

### 1. What is the difference between `GET` and `HEAD`?

**Answer:**  
Both retrieve information about a resource. `GET` returns the response body, while `HEAD` returns only the response headers. `HEAD` is useful for checking metadata such as content length or last modification time without downloading the full content.

---

### 2. Why does the browser send an `OPTIONS` request before some API calls?

**Answer:**  
For certain cross-origin requests, the browser performs a CORS preflight by sending an `OPTIONS` request. It checks whether the server allows the intended HTTP method, headers, and origin before sending the actual request.

---

### 3. Can a `GET` request have a request body?

**Answer:**  
Although the HTTP specification doesn't completely prohibit it, many browsers, servers, proxies, and frameworks ignore or reject GET request bodies. The recommended approach is to use query parameters instead.

---

### 4. When would you use `HEAD` instead of `GET`?

**Answer:**  
Use `HEAD` when you only need metadata—such as whether a resource exists, its content type, content length, or last modified time—without downloading the response body.

# 💡 Backend Engineering Insight

One thing that surprises many developers is that **HTTP methods aren't just for your backend—they're also signals to browsers, proxies, caches, CDNs, and load balancers.**

For example:

```http
GET /posts
```

A browser or CDN may cache the response.

```http
OPTIONS /posts
```

A browser may automatically send this before your frontend's `POST` request because of CORS.

```http
HEAD /files/report.pdf
```

A download manager can check the file size without downloading the file.

Choosing the correct HTTP method doesn't just make your API cleaner—it allows the entire web infrastructure to work efficiently.
