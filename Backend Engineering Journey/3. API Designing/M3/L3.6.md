# Why This Topic Matters

Imagine this situation.

A user clicks:

```text
Pay ₹1000
```

The frontend sends:

```http
POST /payments
```

The payment is processed.

But...

The internet connection drops before the response reaches the user.

The user thinks:

> "Payment failed."

So they click **Pay Again**.

Without proper design:

```text
₹1000 charged

↓

₹1000 charged again
```

The customer loses ₹2000.

This is why idempotency matters.

---

# What is a Safe Request?

A request is **Safe** if it **does not modify server state**.

Safe means:

> Reading only.

Example:

```http
GET /posts
```

You can request it:

1 time

10 times

1000 times

The database should remain unchanged.

---

## Safe Methods

|Method|Safe|
|---|---|
|GET|✅|
|HEAD|✅|
|OPTIONS|✅|
|POST|❌|
|PUT|❌|
|PATCH|❌|
|DELETE|❌|

---

# Safe Doesn't Mean No Work

Suppose:

```http
GET /posts
```

Server may:

- Log the request
    
- Record metrics
    
- Update cache statistics
    

These internal operations don't change the **business resource**.

The `Post` resources remain unchanged.

So the request is still considered **safe**.

---

# What is an Idempotent Request?

A request is **idempotent** if:

> Sending it multiple times produces the same final state as sending it once.

Notice the important phrase:

**Same final state**

It does **not** necessarily mean:

- Same response
    
- Same status code
    

It means the **resource ends up in the same state**.

---

# DELETE Example

Suppose:

```http
DELETE /posts/15
```

First request:

```text
Post removed.
```

Second request:

```text
Already removed.
```

Third request:

```text
Still removed.
```

Final database:

```text
Post does not exist.
```

Same final state.

DELETE is idempotent.

---

# PUT Example

Current user:

```json
{
  "name": "Rahul"
}
```

Request:

```http
PUT /users/5
```

```json
{
  "name": "Rahul Kumar"
}
```

Repeat:

1 time

↓

Rahul Kumar

Repeat:

50 times

↓

Still Rahul Kumar

Final state doesn't change.

PUT is idempotent.

---

# PATCH Example (Idempotent)

```http
PATCH /posts/15
```

```json
{
  "status": "published"
}
```

Repeat:

```text
Published

Published

Published
```

Final state:

Published.

Idempotent.

---

# PATCH Example (Not Idempotent)

```http
PATCH /posts/15
```

```json
{
  "views": "+1"
}
```

Request:

1

↓

Views = 11

Request:

Again

↓

Views = 12

Final state changes every time.

Not idempotent.

---

# POST Example

```http
POST /orders
```

Request:

```json
{
  "productId": 10
}
```

First request:

```text
Order #101 created.
```

Second request:

```text
Order #102 created.
```

Third request:

```text
Order #103 created.
```

Three different orders.

POST is generally **not idempotent**.

# Safe vs Idempotent

Many beginners confuse them.

Think of them independently.

---

### GET

Safe?

✅ Yes

✅ Yes

---

### DELETE

Safe?

❌ No

Deletes data.

Idempotent?

✅ Yes

Delete multiple times.

Still deleted.

---

### POST

Safe?

❌ No

Creates data.

Idempotent?

❌ No

Creates duplicates.

---

### PUT

Safe?

❌ No

Updates data.

Idempotent?

✅ Yes

Final state stays the same.

# Why Idempotency Matters

Modern applications rarely have perfect networks.

Imagine:

```text
Phone
     │
Weak Internet
     │
Backend
```

User presses:

```text
Submit
```

Network times out.

Frontend retries.

Without idempotency:

```text
Order

↓

Duplicate Order
```

Bad experience.

# Retry Mechanisms

Many systems automatically retry requests.

Examples:

- Mobile apps
    
- Browsers
    
- Load balancers
    
- API gateways
    
- Reverse proxies
    
- Message queues
    

Your backend should be designed with retries in mind.

User orders pizza.

```http

```

Network timeout.

Frontend retries.

Without protection:

```text

Pizza
```

Restaurant starts preparing three pizzas.

Retry:

# Solution — Idempotency Keys

Many production APIs support **Idempotency-Key**.

Client generates:

```text
abc123xyz
```

Request:

```http
POST /payments

Idempotency-Key: abc123xyz
```

Server stores:

```text
abc123xyz

↓

Payment Success
```

---

If the same request arrives again:

```http
POST /payments

Idempotency-Key: abc123xyz
```

Server checks:

Already processed.

Instead of charging again:

Returns previous result.

---

# Visual Flow

Without key:

```text
POST

↓

Payment

↓

Retry

↓

Payment Again
```

---

With key:

```text
POST

↓

Save Key

↓

Retry

↓

Key Exists

↓

Return Previous Response
```

No duplicate payment.

# Designing Idempotent APIs

Suppose:

Requirement:

> User likes a post.

Bad:

```http
POST /posts/15/likes
```

Every request:

```text
Like

Like

Like
```

Duplicates.

---

Better:

Database constraint:

```text
Unique:

userId

postId
```

Second request:

Simply return:

```http

```

or

```http

```

depending on the API design.

Final state:

One like.

# Designing Retry-Friendly APIs

Ask yourself:

If this request is retried:

- Will duplicates appear?
    
- Will money be charged twice?
    
- Will inventory decrease twice?
    
- Will notifications be sent twice?
    

If yes:

Design needs improvement.

# Common Mistakes

### ❌ Ignoring retries

Networks fail.

Retries happen.

Always assume requests may arrive more than once.

---

### ❌ Assuming POST runs only once

Not true.

Mobile apps frequently retry.

---

### ❌ Increment Operations

```json
{
    "views":"+1"
}
```

Repeated PATCH changes state.

Not idempotent.

---

### ❌ Payment Without Idempotency

Very dangerous.

Always support duplicate request protection.

---

# Best Practices

- Understand the difference between **Safe** and **Idempotent**.
    
- Design APIs assuming requests may be retried.
    
- Use idempotency keys for critical operations.
    
- Enforce uniqueness with database constraints where appropriate.
    
- Make update operations idempotent whenever possible.
    
- Think about distributed systems, not just local development.

# Key Terms

|Term|Meaning|
|---|---|
|Safe|Does not modify business resources|
|Idempotent|Repeating the request produces the same final resource state|
|Retry|Sending the same request again after a timeout or failure|
|Idempotency Key|A unique client-generated identifier used to detect duplicate requests|
|Duplicate Request|The same logical operation sent more than once|

# Interview Questions

### 1. What is the difference between a safe request and an idempotent request?

**Answer:**  
A safe request does not modify the state of business resources on the server, while an idempotent request guarantees that repeating the same request results in the same final resource state as sending it once.

---

### 2. Why is `DELETE` idempotent but not safe?

**Answer:**  
`DELETE` modifies the server by removing a resource, so it is not safe. However, deleting the same resource multiple times leaves the server in the same final state—the resource remains deleted—making it idempotent.

---

### 3. What is an idempotency key, and why is it important?

**Answer:**  
An idempotency key is a unique identifier sent with a request (typically for operations like payments or order creation). The server stores the key and, if it receives the same key again, returns the original result instead of performing the operation again. This prevents duplicate processing caused by retries.

---

### 4. Why are idempotency keys especially important for payment APIs?

**Answer:**  
Payment requests may be retried due to network failures or timeouts. Without idempotency keys, the same payment could be processed multiple times, leading to duplicate charges. Idempotency keys ensure the payment is executed only once for a given logical request.

---

# 💡 Backend Engineering Insight

A junior developer often thinks:

> **"The user clicked the button once, so the request will only arrive once."**

A senior backend engineer assumes the opposite:

- The network may fail.
    
- The browser or mobile app may retry.
    
- A proxy or load balancer may retry.
    
- The user may click the button multiple times.
    

So they design critical APIs—especially for **payments, bookings, and orders**—to be **retry-safe**.

This mindset is one of the key differences between building a demo application and building a production-ready backend.
