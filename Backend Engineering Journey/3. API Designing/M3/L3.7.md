# What is Statelessness?

Statelessness means:

> **Every request contains all the information the server needs to process it.**

The server should **not rely on memory of previous requests**.

Every request stands on its own.

---

# A Simple Example

User wants to see their posts.

The frontend sends:

```http
GET /posts
Authorization: Bearer eyJhbGciOiJIUzI1Ni...
```

The server receives:

- HTTP Method
    
- URL
    
- Headers
    
- Authentication Token
    

The server can process the request immediately.

It doesn't need to remember what happened yesterday.

---

# Every Request is Independent

Imagine three requests.

```text
Request 1
↓

GET /posts
Authorization: Token A
```

---

```text
Request 2
↓

GET /comments
Authorization: Token A
```

---

```text
Request 3
↓

PATCH /posts/15
Authorization: Token A
```

Each request carries everything required.

The server treats them independently.

---

# Visualizing Statelessness

```text
Client
   │
Request 1
   ▼
Server

(No memory kept)

Client
   │
Request 2
   ▼
Server

(No memory kept)

Client
   │
Request 3
   ▼
Server
```

Each request is a fresh interaction.

---

# What is State?

State is information remembered between requests.

Example:

```text
User logged in

↓

Server remembers the login

↓

Future requests rely on that memory
```

This is **stateful** behavior.

---

# Stateful System

Imagine a hotel.

Receptionist remembers you.

Day 1:

```text
Hello Rahul.

Room 305.
```

Day 2:

Receptionist remembers everything.

No identification needed.

The receptionist stores state.

---

# Stateless System

Airport security.

Every time:

Show passport.

Show boarding pass.

Every checkpoint verifies independently.

No one relies on previous checkpoints.

This is stateless.

---

# Why REST Prefers Statelessness

Suppose your website has:

```text
100 Users
```

Server stores:

```text
100 Sessions
```

Easy.

Now:

```text
10 Million Users
```

Server stores:

```text
10 Million Sessions
```

Memory usage grows dramatically.

Stateless systems avoid this issue.

---

# Stateful Authentication

Traditional session authentication works like this.

Login:

```http
POST /login
```

Server creates:

```text
Session

↓

sessionId = abc123
```

Stores:

```text
Server Memory

↓

abc123

↓

User Rahul
```

Client receives:

```text
Cookie

↓

abc123
```

Future requests:

```http
GET /posts

Cookie:
sessionId=abc123
```

Server:

Looks up memory.

Finds Rahul.

---

# Diagram

```text
Browser
     │
sessionId
     ▼
Server Memory
     │
User Object
```

The server remembers every logged-in user.

---

# Problems with Stateful Sessions

Imagine:

```text
Server A
```

stores:

```text
Rahul's Session
```

Now the next request goes to:

```text
Server B
```

Server B doesn't know Rahul.

Result:

```text
Unauthorized
```

This creates scalability problems.

---

# Load Balancer Problem

```text
            Load Balancer
             /         \
            /           \
     Server A       Server B
```

Request 1:

↓

Server A

Request 2:

↓

Server B

If sessions exist only on Server A:

Authentication fails.

---

# Solutions for Stateful Systems

Some companies use:

Shared session storage.

Example:

```text
Server A
       │
Server B
       │
Redis
```

Every server reads the same session store.

Works well, but adds infrastructure complexity.

# Stateless Authentication (JWT)

Modern REST APIs often use JWTs.

Login:

```http
POST /auth/login
```

Server generates:

```text
JWT
```

Example:

```text
eyJhbGciOiJIUzI...
```

Client stores it.

Future request:

```http
GET /posts

Authorization:
Bearer eyJhbGciOiJIUzI...
```

Server verifies the token.

No session lookup required.

---

# JWT Flow

```text
Client
   │
Login
   ▼
Server
   │
JWT
   ▼
Client
   │
GET /posts
Authorization: Bearer JWT
   ▼
Server
```

Every request contains the authentication information.

This aligns well with the stateless REST constraint.

---

# Why JWT Scales Better

Imagine:

```text
100 Servers
```

Every server can verify the JWT independently.

```text
Client

↓

Server A

or

↓

Server B

or

↓

Server C
```

No shared session memory required.

---

# Stateless Doesn't Mean No Authentication

A common misunderstanding is:

> REST is stateless, so users can't log in.

Wrong.

Users absolutely authenticate.

The key difference is:

The **authentication information accompanies each request**.

Examples:

```http
Authorization: Bearer <JWT>
```

or

```http
Cookie: sessionId=...
```

The server processes each request based on the credentials sent with that request.

---

# Cookies Can Also Be Stateless

Many beginners think:

```text
Cookie

↓

Always Stateful
```

Not necessarily.

Suppose the cookie contains:

```text
JWT
```

The server verifies it.

No session lookup.

Still stateless.

It's not the cookie itself that determines statefulness—it's whether the server must remember information between requests.

---

# Comparing Authentication Approaches

|Feature|Session-Based|JWT-Based|
|---|---|---|
|Server stores login state|✅ Yes|❌ No|
|Scales easily across many servers|Requires shared session storage or sticky sessions|✅ Yes|
|Every request carries credentials|Usually via session cookie|Usually via JWT in `Authorization` header (or cookie)|
|REST-friendly|Less aligned with statelessness|More aligned with statelessness|

# Stateless Request Example

Request:

```http
GET /posts/15

Authorization:
Bearer JWT
```

Server:

1. Verify token.
    
2. Identify user.
    
3. Process request.
    
4. Return response.
    

Forget everything.

Next request starts fresh.

---

# Backend Responsibilities

Each request should include:

- URL
    
- HTTP Method
    
- Headers
    
- Authentication
    
- Request Body (if needed)
    

The server should not depend on:

- Previous request memory
    
- Logged-in user stored in RAM
    
- Client interaction history

```text
              CDN
               │
        Load Balancer
        /     |      \
       /      |       \
 API Server API Server API Server
       \      |      /
        \     |     /
         Database
```

Because the API is stateless:

Any server can process any request.

This is one reason stateless APIs are highly scalable.

# When State is Still Needed

Not everything is stateless.

Examples:

- Shopping carts
    
- Game progress
    
- Chat rooms
    
- Temporary drafts
    

The **application** may manage state in a database or cache.

The important point is:

The **HTTP server** doesn't rely on remembering previous requests in its own memory.

---

# Common Misconceptions

### ❌ Stateless means "no login"

Wrong.

Authentication is fully compatible with stateless APIs.

---

### ❌ JWT is required for REST

Wrong.

REST doesn't require JWT.

JWT is simply one popular way to implement stateless authentication.

---

### ❌ Cookies always break REST

Wrong.

A cookie carrying a signed JWT can still support a stateless design because the server doesn't need to store session state.

---

### ❌ Stateless means the application has no data

Wrong.

Resources are still stored in databases.

Statelessness refers to **request processing**, not data persistence.

---

# Best Practices

- Design each request to be self-contained.
    
- Don't rely on server memory between requests.
    
- Choose authentication mechanisms that suit your application's needs.
    
- Ensure any server instance can process any request.
    
- Store persistent application data in databases, not server memory.

# Key Terms

|Term|Meaning|
|---|---|
|Stateless|Each request is independent and self-contained|
|Stateful|The server remembers information between requests|
|Session|Server-side authentication state|
|JWT|A signed token containing claims that can be verified by the server|

# Interview Questions

### 1. What does statelessness mean in REST?

**Answer:**  
Statelessness means every HTTP request contains all the information required to process it. The server does not rely on memory of previous requests when handling the current one.

---

### 2. Why are stateless APIs easier to scale?

**Answer:**  
Because any server instance can handle any request without needing shared in-memory session state. This works well with load balancers and horizontal scaling.

---

### 3. Does REST require JWT?

**Answer:**  
No. REST does not mandate JWT. JWT is simply a common technique for implementing stateless authentication. Other approaches are also possible.

---

### 4. What's the difference between session-based and JWT-based authentication?

**Answer:**  
In session-based authentication, the server stores login state and associates it with a session ID. In JWT-based authentication, the client sends a signed token with each request, allowing the server to verify the user's identity without storing session state.

---

# 💡 Backend Engineering Insight

One common misconception in interviews is:

> **"JWT authentication is always better than sessions."**

The better answer is:

> **"It depends on the system's requirements."**

For example:

- A traditional web application with server-rendered pages may work very well with session-based authentication.
    
- A distributed API serving web, mobile, and third-party clients often benefits from stateless authentication using JWTs or similar token-based approaches.
    

Experienced backend engineers don't choose technologies based on trends—they choose them based on the architecture and requirements.
