# Why Caching Matters

Imagine your blog receives:

```text
100,000 visitors/day
```

Every visitor opens the homepage.

Without caching:

```text
Visitor
    │
GET /posts
    │
Backend
    │
Database
```

100,000 requests reach your database.

---

With caching:

```text
Visitor
    │
GET /posts
    │
Cache
    │
Backend (only when needed)
```

Now maybe only:

```text
2,000
```

requests reach the database.

Huge improvement.

---

# What is Caching?

Caching means:

> **Store a copy of a response so it can be reused later.**

Instead of regenerating the same response repeatedly, the cache returns the stored copy.

---

Example:

```http
GET /categories
```

Categories rarely change.

Instead of querying the database every time:

```text
Database

↓

JSON

↓

Cache

↓

Future requests served from cache
```

---

# Real-Life Example

Imagine a library.

Without caching:

```text
Need Book

↓

Go to Warehouse

↓

Bring Book
```

Every single time.

---

With caching:

```text
Need Book

↓

Already on Reading Table

↓

Read Immediately
```

Much faster.

---

# Benefits of Caching

- Faster response times
    
- Lower database load
    
- Lower server CPU usage
    
- Better user experience
    
- Lower infrastructure costs
    
- Improved scalability

# Types of Caches

There isn't just one cache.

A request may pass through several.

```text
Browser

↓

CDN

↓

Reverse Proxy

↓

Backend

↓

Database
```

Let's study each one.

---

# 1. Browser Cache

The browser stores responses locally.

Example:

```http
GET /logo.png
```

First request:

```text
Browser

↓

Server
```

Second request:

```text
Browser

↓

Local Cache
```

No network request.

---

Works well for:

- Images
    
- CSS
    
- JavaScript
    
- Fonts
    

Sometimes even API responses.

---

# 2. CDN Cache

CDN = Content Delivery Network.

Examples:

- Cloudflare
    
- Fastly
    
- Akamai
    

Instead of every user contacting your server:

```text
User

↓

Nearby CDN

↓

Server (if needed)
```

The CDN stores copies close to users.

---

# Example

User:

India

↓

Cloudflare India

↓

Returns cached response.

No request reaches your server.

---

# 3. Reverse Proxy Cache

Tools like:

- Nginx
    
- Varnish
    

can cache API responses.

Example:

```text
Client

↓

Nginx

↓

Express

↓

Database
```

Repeated requests:

```text
Client

↓

Nginx Cache
```

Backend isn't involved.

---

# 4. Application Cache

Sometimes your application caches expensive database queries.

Example:

```text
Express

↓

Redis

↓

MongoDB
```

If Redis has the data:

Database isn't queried.

---

# REST Cacheability

One REST constraint says:

> Responses should indicate whether they are cacheable.

The server communicates this using HTTP headers.

---

# Cache-Control Header

The most common cache header.

Example:

```http
Cache-Control: max-age=3600
```

Meaning:

Cache this response for:

```text
3600 seconds

↓

1 hour
```

---

During that hour:

Repeated requests may use the cached response instead of contacting the server.

---

# Common Cache-Control Directives

## max-age

```http
Cache-Control: max-age=600
```

Cache for:

```text
10 minutes
```

---

## no-cache

```http
Cache-Control: no-cache
```

Meaning:

Before using the cached copy, check with the server to ensure it's still valid.

It **does not** mean "don't cache at all."

---

## no-store

```http
Cache-Control: no-store
```

Meaning:

Never store this response.

Useful for:

- Banking
    
- Passwords
    
- Sensitive information
    

---

## public

```http
Cache-Control: public
```

Shared caches (like CDNs) may store the response.

---

## private

```http
Cache-Control: private
```

Only the user's browser should cache it.

Shared caches should not.

Useful for user-specific responses.

---

# Example

Homepage:

```http
GET /posts
```

Header:

```http
Cache-Control: public, max-age=300
```

Meaning:

Everyone may cache this page for:

```text
5 minutes
```

---

User Profile:

```http
GET /me
```

Header:

```http
Cache-Control: private
```

Because every user has different data.

# ETag

ETag stands for **Entity Tag**.

Think of it as a fingerprint for a resource.

Example:

```http
GET /posts/15
```

Response:

```http
ETag: "abc123"
```

The browser remembers:

```text
abc123
```

---

Later:

Browser asks:

```http
GET /posts/15

If-None-Match: "abc123"
```

Server checks.

If nothing changed:

Returns:

```http
304 Not Modified
```

No response body.

The browser uses its cached copy.

---

# Visual Flow

```text
Browser
    │
GET /posts
    │
ETag: abc123
    ▼
Cache

Later

Browser

↓

If-None-Match: abc123

↓

Server

↓

304 Not Modified
```

No JSON needs to be downloaded again.

---

# Last-Modified

Another validation mechanism.

Response:

```http
Last-Modified:

Mon, 03 Aug 2026 09:00 GMT
```

Browser remembers this timestamp.

Next request:

```http
If-Modified-Since:

Mon, 03 Aug 2026 09:00 GMT
```

Server checks.

Nothing changed?

Returns:

```http
304 Not Modified
```

---

# ETag vs Last-Modified

|ETag|Last-Modified|
|---|---|
|Fingerprint of content|Timestamp|
|More precise|Less precise|
|Detects any content change|Based on modification time|
|Preferred when available|Simpler to generate|

Many APIs use both.

---

# 304 Not Modified

Instead of:

```http
200 OK
```

with:

```json
{
  ...
}
```

Server returns:

```http
304 Not Modified
```

Body:

Nothing.

Browser already has the content.

This saves:

- Bandwidth
    
- CPU
    
- Response time

# What Should Be Cached?

Good candidates:

```text
Categories

Countries

Public Blog Posts

Product Catalog

Documentation

Static Images
```

---

Usually avoid caching:

```text
Bank Balance

Shopping Cart

Notifications

User Profile

```

# Cache Invalidation

Imagine:

```text
GET /posts
```

Cached for:

```text
1 hour
```

A new blog post is published.

The cache still contains old data.

Users don't see the new post.

This is called:

**Stale Cache**

---

Cache invalidation means updating or clearing cached data when the underlying data changes.

This is often considered one of the hardest problems in software engineering.

---

# Real Example

Blog homepage:

```http
GET /posts
```

Header:

```http
Cache-Control: public, max-age=300
```

Reader refreshes page.

Within:

5 minutes.

Response:

Served from cache.

After:

5 minutes.

Cache expires.

Backend generates a fresh response.

# Common Mistakes

### ❌ Caching sensitive user data

Never cache responses containing private information in shared caches.

---

### ❌ Using `no-store` everywhere

Disables useful caching.

Only use it when truly necessary.

---

### ❌ Forgetting cache invalidation

Updated data remains invisible to users until the cache expires or is cleared.

---

### ❌ Ignoring ETags

ETags can significantly reduce bandwidth for frequently requested resources.

---

# Best Practices

- Cache public, rarely changing resources.
    
- Use `Cache-Control` appropriately.
    
- Use `ETag` or `Last-Modified` for conditional requests.
    
- Return `304 Not Modified` when content hasn't changed.
    
- Avoid caching sensitive responses in shared caches.
    
- Plan cache invalidation carefully whenever data can change.

# Key Terms

|Term|Meaning|
|---|---|
|Cache|Stored copy of a response|
|Cache-Control|HTTP header controlling caching behavior|
|ETag|Fingerprint representing a specific version of a resource|
|Last-Modified|Timestamp of the resource's last update|
|304 Not Modified|Indicates the client's cached copy is still valid|
|CDN|Content Delivery Network|
|Reverse Proxy|Server that can cache and forward requests|

# Interview Questions

### 1. Why is caching important in REST APIs?

**Answer:**  
Caching reduces server load, database queries, response times, and bandwidth usage by allowing clients or intermediaries to reuse previously generated responses.

---

### 2. What is the purpose of the `Cache-Control` header?

**Answer:**  
`Cache-Control` tells browsers and intermediate caches how a response should be cached. It can specify directives such as `max-age`, `public`, `private`, `no-cache`, and `no-store`.

---

### 3. What is an ETag?

**Answer:**  
An ETag is a unique identifier representing a specific version of a resource. Clients can send it back in an `If-None-Match` header, allowing the server to respond with `304 Not Modified` if the resource hasn't changed.

---

### 4. What is the difference between `no-cache` and `no-store`?

**Answer:**

- `no-cache` allows a response to be stored, but it must be revalidated with the server before being reused.
    
- `no-store` instructs clients and caches not to store the response at all.

# 💡 Backend Engineering Insight

As a backend engineer, you'll usually deal with **three different kinds of caching**, and it's important not to confuse them:

|Type|Managed By|Example|
|---|---|---|
|**HTTP Cache**|Browser, CDN, Reverse Proxy|`Cache-Control`, `ETag`, `304 Not Modified`|
|**Application Cache**|Your backend|Redis storing expensive query results|
|**Database Cache**|Database engine|Query plans, buffer pools, internal page caches|

A common beginner mistake is thinking that **Redis replaces HTTP caching**.

It doesn't.

They solve different problems:

- **HTTP caching** reduces unnecessary network traffic and backend requests.
    
- **Redis** reduces expensive work inside your backend after a request reaches it.
    

In production systems, it's common to use **both** together.
