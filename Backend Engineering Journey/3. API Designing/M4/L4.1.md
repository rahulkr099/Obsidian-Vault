# What is an HTTP Request?

An HTTP request is a message sent from a client to a server asking it to perform an action.

Example:

```text
Browser
     │
HTTP Request
     ▼
Backend API
```

The server processes the request and sends back an HTTP response.

---

# Anatomy of an HTTP Request

A request has five main parts:

```text
HTTP Request
     │
     ├── Method
     ├── URL
     ├── Headers
     ├── Cookies
     └── Body (optional)
```

Let's explore each one.

---

# Example HTTP Request

```http
POST /posts HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGc...
Content-Type: application/json
Accept: application/json

{
    "title": "REST API Design",
    "content": "Learning request design."
}
```

This may look intimidating at first, but each line has a specific purpose.

---

# Part 1 — HTTP Method

The first word is the HTTP method.

```http
POST /posts HTTP/1.1
```

Here:

```text
POST
```

tells the server:

> "I want to create a new resource."

Examples:

```http
GET /posts
```

Retrieve posts.

---

```http
POST /posts
```

Create a post.

---

```http
PATCH /posts/10
```

Update post 10.

---

```http
DELETE /posts/10
```

Delete post 10.

---

# Part 2 — URL

The second part is the URL.

Example:

```http
POST /posts
```

The URL identifies **which resource** the client wants to interact with.

Another example:

```http
GET /users/15
```

Resource:

```text
User 15
```

---

# URL Components

Consider this URL:

```text
https://api.blog.com/posts/15?published=true&page=2
```

Break it down:

```text
https://
```

Protocol (HTTPS)

---

```text
api.blog.com
```

Host

---

```text
/posts/15
```

Path

---

```text
?published=true&page=2
```

Query parameters

---

```text
https://api.blog.com/posts/15?published=true&page=2

│       │           │                └── Query Parameters
│       │           └─────────────────── Path
│       └─────────────────────────────── Host

```

# Part 3 — Headers

Headers provide **metadata** about the request.

They are **not** the main data.

Think of them as labels attached to a package.

Example:

```http
Authorization: Bearer eyJhbGc...
```

Tells the server:

Who is making the request?

---

Another:

```http
Content-Type: application/json
```

Tells the server:

The request body contains JSON.

---

Another:

```http
Accept: application/json
```

Tells the server:

The client wants JSON in the response.

---

# Common Request Headers

|Header|Purpose|
|---|---|
|Authorization|User authentication|
|Content-Type|Format of request body|
|Accept|Desired response format|
|User-Agent|Information about the client|
|Origin|Indicates where the request came from (important for CORS)|
|Accept-Language|Preferred language|

We'll study headers in detail in a later lesson.

---

# Part 4 — Cookies

Cookies are small pieces of data automatically sent by browsers.

Example:

```http
Cookie: refreshToken=abc123
```

The browser includes cookies with matching requests if their scope and security settings allow it.

Common uses:

- Sessions
    
- Refresh tokens
    
- User preferences
    

Cookies are **browser-specific**.

API clients like Postman or Bruno send cookies only if you configure them.

---

# Part 5 — Request Body

The body contains the **main data** being sent to the server.

Example:

```json
{
    "title": "REST API Design",
    "content": "Learning request design."
}
```

Usually present with:

```http
POST
PUT
PATCH
```

Usually absent with:

```http
GET
DELETE
HEAD
OPTIONS
```

> **Note:** While the HTTP specification doesn't strictly forbid a body on `GET` or `DELETE`, it's uncommon and many servers, clients, and intermediaries ignore it. Prefer query parameters for `GET` and avoid relying on request bodies for `DELETE` unless you control both client and server.

```http

Host: api.blog.com        ← Header
Authorization: Bearer ... ← Header
Content-Type: application/json ← Header

{
  "title": "REST API Design"
}                          ← Body
```

Every request follows this general structure.

# Reading Requests Like a Backend Engineer

Suppose you receive:

```http
PATCH /users/5 HTTP/1.1
Authorization: Bearer token123
Content-Type: application/json

{
    "bio": "Backend Engineer"
}
```

A backend engineer immediately understands:

- Method → PATCH
    
- Resource → User 5
    
- Authentication → Bearer token
    
- Data format → JSON
    
- Update → `bio`
    

No code is needed to understand the request.

# Postman Example

In Postman, you usually fill in:

```text

```

```text

```


# Axios Example

You write:

```javascript
axios.post("/posts", {
    title: "REST"
});
```

Axios automatically creates:

- Method
    
- URL
    
- Headers
    
- Body

---

# Fetch Example

```javascript
fetch("/posts", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify({
        title: "REST"
    })
});
```

Again, JavaScript builds the HTTP request for you.

---

# cURL Example

```bash
curl -X POST http://localhost:5000/posts \
  -H "Content-Type: application/json" \
  -d '{"title":"REST"}'
```

This command sends the same type of HTTP request from the terminal.

# Common Mistakes

### ❌ Forgetting `Content-Type`

Without it:

```http
Content-Type: application/json
```

the server may not know how to parse the request body.

---

### ❌ Missing Authorization Header

Protected endpoints require authentication.

Without:

```http
Authorization: Bearer token
```

the server may return:

```http
401 Unauthorized
```

---

### ❌ Sending a Body with `GET`

```http
GET /posts
```

```json
{
  "category": "backend"
}
```

Use:

```http
GET /posts?category=backend
```

instead.

---

### ❌ Using Query Parameters for Large Objects

Bad:

```text
/posts?title=REST&content=VeryLongContent...
```

Better:

```http
POST /posts
```

with a JSON body.

---

# Best Practices

- Understand every part of the request before writing backend code.
    
- Use headers only for metadata.
    
- Use the body for resource data.
    
- Use query parameters for filtering and searching.
    
- Include the appropriate `Content-Type`.
    
- Send authentication credentials in the expected place (such as an `Authorization` header or cookie, depending on your API design).

# Interview Questions

### 1. What are the main parts of an HTTP request?

**Answer:**

An HTTP request typically consists of:

- Request line (method, path, HTTP version)
    
- Headers
    
- Cookies (when present)
    
- Request body (when applicable)
    

---

### 2. What is the purpose of request headers?

**Answer:**

Headers carry metadata about the request, such as authentication credentials, the request body's content type, the preferred response format, and information about the client.

---

### 3. When is a request body typically used?

**Answer:**

Request bodies are commonly used with `POST`, `PUT`, and `PATCH` requests to send resource data to the server. `GET` requests generally use query parameters instead of a body.

---

### 4. What is the difference between the URL and the request body?

**Answer:**

The URL identifies the target resource and may include path or query parameters. The request body contains the actual data being sent to create or update a resource.

# 💡 Backend Engineering Insight

When debugging APIs, experienced backend engineers often ignore the code at first and inspect the **raw HTTP request**.

Their mental checklist looks like this:

```text
Method?
   ↓
Correct URL?
   ↓
Correct Headers?
   ↓
Authentication Present?
   ↓
Correct Content-Type?
   ↓
Body Valid JSON?
```

Many API issues—such as `400 Bad Request`, `401 Unauthorized`, or `415 Unsupported Media Type`—can be identified just by reading the request carefully.

Learning to "read the wire" is one of the fastest ways to become effective at backend debugging.
