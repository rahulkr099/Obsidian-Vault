# Why This Lesson Matters

One of the biggest differences between a beginner and an experienced backend engineer is **where they place data**.

Imagine you need to update a user's profile picture.

Should it go in:

- URL?
    
- Query parameter?
    
- Header?
    
- Cookie?
    
- Request body?
    

Only one choice is appropriate.

Professional API design starts by answering this question correctly.

---

# The Golden Rule

Every piece of request data has a purpose.

Choose its location based on **what it represents**, not personal preference.

Use this decision tree whenever you design an API.

```text
Does it identify a specific resource?
            │
          Yes
            ▼
     Path Parameter
```

```text
Does it change how resources are retrieved?
(Search, Filter, Sort, Pagination)
            │
          Yes
            ▼
    Query Parameter
```

```text
Is it the actual resource data
being created or updated?
            │
          Yes
            ▼
      Request Body
```

```text
Is it request metadata?
(Auth, Content-Type, Language)
            │
          Yes
            ▼
         Headers
```

```text
Is it browser-managed session
or preference information?
            │
          Yes
            ▼
         Cookies
```

This simple framework solves most API design questions.

# Part 1 — Path Parameters

## Purpose

Use path parameters to identify **one specific resource**.

Example:

```http
GET /posts/15
```

Question:

Which post?

Answer:

```text
Post 15
```

---

More examples:

```http
GET /users/8
```

Specific user.

---

```http
DELETE /comments/22
```

Specific comment.

---

```http
PATCH /orders/1001
```

Specific order.

---

## Rule

Ask yourself:

> **"Can I point to exactly one resource?"**

If yes,

use a **path parameter**.

---

# Good Examples

```http
GET /users/5
```

```http
PATCH /posts/15
```

```http
DELETE /orders/100
```

---

# Bad Examples

```http
GET /users?id=5
```

This identifies one resource.

Prefer:

```http
GET /users/5
```

---

# Part 2 — Query Parameters

## Purpose

Query parameters **modify how resources are retrieved**.

They don't identify the resource.

---

Example:

```http
GET /posts?page=2
```

Question:

Which page?

Answer:

```text
Page 2
```

Still retrieving posts.

---

Search:

```http
GET /posts?search=node
```

---

Filter:

```http
GET /posts?category=backend
```

---

Sort:

```http
GET /posts?sort=-createdAt
```

---

Limit:

```http
GET /posts?limit=20
```

---

Field Selection:

```http
GET /posts?fields=title,author
```

---

## Rule

Query parameters answer questions like:

- Which page?
    
- Which category?
    
- Which sort order?
    
- Which search keyword?
    
- How many items?
    

---

# Good Examples

```http
GET /products?page=2
```

```http
GET /products?category=laptop
```

```http
GET /products?sort=price
```

---

# Bad Example

```http
GET /products?productId=15
```

If you want one product,

use:

```http
GET /products/15
```

---

# Part 3 — Request Body

## Purpose

The request body contains the **resource data**.

Usually with:

- POST
    
- PUT
    
- PATCH
    

---

Create post:

```http
POST /posts
```

Body:

```json
{
    "title": "REST APIs",
    "content": "Learning request design."
}
```

---

Update user:

```http
PATCH /users/5
```

Body:

```json
{
    "bio": "Backend Engineer"
}
```

---

Order creation:

```http
POST /orders
```

Body:

```json
{
    "productId": 15,
    "quantity": 2
}
```

---

## Rule

Ask yourself:

> **"Is this the actual data I'm creating or updating?"**

If yes,

it belongs in the body.

---

# Good Examples

```json
{
    "email":"abc@gmail.com"
}
```

---

```json
{
    "title":"REST"
}
```

---

```json
{
    "completed":true
}
```

---

# Bad Example

```http
POST /posts?title=REST&content=VeryLongArticle...
```

Large resource data should not be placed in query parameters.

---

# Part 4 — Headers

## Purpose

Headers carry **metadata**.

Metadata describes the request but is not the resource itself.

---

Example:

```http
Authorization: Bearer eyJhbGc...
```

Authentication information.

---

Another:

```http
Content-Type: application/json
```

Body format.

---

Another:

```http
Accept: application/json
```

Desired response format.

---

Another:

```http
Accept-Language: en-US
```

Preferred language.

---

## Rule

Headers answer questions like:

- Who is making the request?
    
- What format is the body?
    
- What response format is expected?
    
- Which language is preferred?
    

---

# Good Header Examples

```http
Authorization: Bearer token
```

---

```http
Content-Type: application/json
```

---

```http
Accept: application/json
```

---

# Bad Example

```http
Title: REST APIs
```

Title is resource data.

It belongs in the body.

---

# Part 5 — Cookies

Cookies are mainly used by browsers.

Typical uses:

- Session IDs
    
- Refresh tokens
    
- User preferences
    
- Theme settings
    
- Language preferences
    

Example:

```http
Cookie: refreshToken=abc123
```

The browser automatically sends matching cookies with requests.

---

## Rule

Cookies store **browser-related state**, not the resource being created or updated.

---

# Good Cookie Example

```http
Cookie:
refreshToken=abc123
```

---

# Bad Example

```http
Cookie:
title=REST APIs
```

A blog title is resource data.

It belongs in the request body.

---

# Putting It All Together

Suppose the frontend wants:

> Update Post 15

New title:

REST API Design

Authenticated user.

Preferred response:

JSON.

Request:

```http
PATCH /posts/15

Authorization: Bearer token
Content-Type: application/json
Accept: application/json

{
    "title":"REST API Design"
}
```

Notice:

|Data|Location|
|---|---|
|Post ID|Path Parameter|
|Authentication|Header|
|Content-Type|Header|
|Response Format|Header|
|New Title|Body|

Each piece of information is exactly where it belongs.

# Common Mistakes

## ❌ Resource ID in Query

Bad:

```http
GET /users?id=5
```

Better:

```http
GET /users/5
```

---

## ❌ Search in Body

Bad:

```http
POST /posts

{
    "search":"node"
}
```

Better:

```http
GET /posts?search=node
```

---

## ❌ Authentication in Body

Bad:

```json
{
    "token":"abc123"
}
```

Better:

```http
Authorization:
Bearer abc123
```

---

## ❌ Resource Data in Headers

Bad:

```http
Title: REST APIs
```

Better:

```json
{
    "title":"REST APIs"
}
```

---

## ❌ Large Data in Query Parameters

Bad:

```http
POST /posts?title=REST&content=VeryLongArticle...
```

Use the request body instead.

# Best Practices

- Use **path parameters** for resource identity.
    
- Use **query parameters** for retrieval options.
    
- Use the **body** for resource data.
    
- Use **headers** for metadata.
    
- Use **cookies** for browser-managed information.
    
- Keep each piece of data in its appropriate place.

# Interview Questions

### 1. When should you use path parameters instead of query parameters?

**Answer:**  
Use path parameters to identify a specific resource, such as `/users/5`. Use query parameters to modify how a collection is retrieved, such as filtering, searching, sorting, or pagination (`/users?page=2`).

---

### 2. Why shouldn't authentication tokens be sent in the request body?

**Answer:**  
Authentication information is request metadata, not resource data. It belongs in the `Authorization` header (or, depending on the authentication strategy, in a secure cookie), which follows standard HTTP conventions.

---

### 3. What kind of data belongs in the request body?

**Answer:**  
The request body contains the resource data being created or updated, such as a new blog post, user profile information, or an order.

---

### 4. When are cookies commonly used?

**Answer:**  
Cookies are commonly used by browsers to automatically send session identifiers, refresh tokens, and user preferences with matching requests.

# 💡 Backend Engineering Insight

A useful habit is to ask **one question** for every field in a request:

|Question|Put It Here|
|---|---|
|**Which resource?**|Path Parameter|
|**How should I retrieve it?**|Query Parameter|
|**What data am I sending?**|Request Body|
|**How should the request be handled?**|Headers|
|**What browser-managed state should travel automatically?**|Cookies|

For example, consider updating a user's profile:

```http
PATCH /users/42?notify=true
Authorization: Bearer <token>
Content-Type: application/json
Cookie: refreshToken=...

{
  "displayName": "Rahul",
  "bio": "Backend Engineer"
}
```

Everything has a clear responsibility:

- `/users/42` → **Which user?**
    
- `notify=true` → **How should the update behave?**
    
- `Authorization` → **Who is making the request?**
    
- `Cookie` → **Browser-managed authentication state**
    
- JSON body → **What data should change?**
    

When every piece of data has a single, well-defined place, your APIs become easier to understand, document, and maintain.
