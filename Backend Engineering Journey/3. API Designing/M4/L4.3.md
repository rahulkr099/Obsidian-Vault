# Module 4 — Request Design

# Lesson 4.3 — Request Body Design

> **Goal:** Learn how to design request bodies that are clean, readable, scalable, and easy to validate. A well-designed request body makes APIs easier to use, maintain, and evolve over time.

---

# Learning Objectives

After this lesson, you should be able to:

- Design clean JSON request bodies.
    
- Decide between flat and nested structures.
    
- Use arrays and objects appropriately.
    
- Distinguish required and optional fields.
    
- Design request bodies for `POST`, `PUT`, and `PATCH`.
    
- Understand the DTO (Data Transfer Object) mindset.

# Why Request Body Design Matters

Imagine these two APIs.

### API A

```json
{
    "a": "Rahul",
    "b": "rahul@gmail.com",
    "c": "9876543210",
    "d": true
}
```

---

### API B

```json
{
    "name": "Rahul",
    "email": "rahul@gmail.com",
    "phone": "9876543210",
    "isVerified": true
}
```

Which one is easier to understand?

Clearly, **API B**.

Good request bodies should be **self-explanatory**.

---

# What is a Request Body?

The request body contains the **actual resource data** sent by the client.

Example:

```http
POST /posts
```

```json
{
    "title": "REST API Design",
    "content": "Learning backend development."
}
```

The body describes the new **Post** resource.

---

# When is a Request Body Used?

Most commonly with:

|Method|Request Body|
|---|---|
|POST|✅ Usually|
|PUT|✅ Yes|
|PATCH|✅ Yes|
|GET|❌ Usually No|
|DELETE|❌ Usually No|

---

# Principle 1 — Use Meaningful Field Names

Bad:

```json
{
    "t": "REST",
    "c": "Content"
}
```

---

Good:

```json
{
    "title": "REST",
    "content": "Content"
}
```

The API should explain itself.

---

# Principle 2 — Keep JSON Flat When Possible

Suppose we're creating a user.

Good:

```json
{
    "name": "Rahul",
    "email": "rahul@gmail.com",
    "phone": "9876543210"
}
```

Simple.

Easy to validate.

---

Avoid unnecessary nesting.

Bad:

```json
{
    "user": {
        "details": {
            "personal": {
                "name": "Rahul"
            }
        }
    }
}
```

This adds complexity without adding value.

---

# When Nesting Makes Sense

Suppose you're creating an order.

Each order has a shipping address.

Good:

```json
{
    "productId": 15,
    "quantity": 2,
    "shippingAddress": {
        "street": "MG Road",
        "city": "Bengaluru",
        "pincode": "560001"
    }
}
```

Here, nesting represents a real business relationship.

---

# Principle 3 — Use Arrays for Collections

Suppose a blog post has multiple tags.

Good:

```json
{
    "title": "REST APIs",
    "tags": [
        "backend",
        "nodejs",
        "express"
    ]
}
```

---

Another example:

Order items:

```json
{
    "items": [
        {
            "productId": 1,
            "quantity": 2
        },
        {
            "productId": 3,
            "quantity": 1
        }
    ]
}
```

Arrays naturally represent multiple values.

---

# Principle 4 — Required vs Optional Fields

Example:

User Registration.

Required:

- Name
    
- Email
    
- Password
    

Optional:

- Bio
    
- Website
    
- Profile Picture
    

Request:

```json
{
    "name": "Rahul",
    "email": "rahul@gmail.com",
    "password": "StrongPassword123",
    "bio": "Backend Engineer"
}
```

The API should clearly define which fields are mandatory.

---

# Principle 5 — Don't Trust Client Defaults

Bad:

```json
{
    "role": "admin"
}
```

A client should not decide security-sensitive values like user roles.

Instead:

```json
{
    "name": "Rahul",
    "email": "rahul@gmail.com"
}
```

The server assigns:

```text
role = "user"
```

Business rules belong on the server.

---

# Principle 6 — POST vs PUT vs PATCH Bodies

## POST

Creates a new resource.

```http
POST /posts
```

```json
{
    "title": "REST",
    "content": "..."
}
```

Contains all required data to create the resource.

---

## PUT

Replaces the entire resource.

```http
PUT /users/15
```

```json
{
    "name": "Rahul",
    "email": "rahul@gmail.com",
    "bio": "Backend Engineer"
}
```

Represents the complete resource.

---

## PATCH

Updates only specific fields.

```http
PATCH /users/15
```

```json
{
    "bio": "Senior Backend Engineer"
}
```

Only changed fields are included.

---

# Principle 7 — Avoid Sending Unnecessary Data

Suppose you're updating only the title.

Bad:

```json
{
    "title": "REST",
    "content": "...",
    "author": "...",
    "createdAt": "...",
    "updatedAt": "...",
    "likes": 45
}
```

---

Better:

```json
{
    "title": "REST"
}
```

Smaller payloads are easier to validate and process.

---

# Principle 8 — Don't Send Server-Controlled Fields

Bad:

```json
{
    "id": 15,
    "createdAt": "2026-08-04",
    "updatedAt": "2026-08-05"
}
```

These fields should be managed by the server.

Usually, clients should **not** send:

- `id`
    
- `createdAt`
    
- `updatedAt`
    
- `passwordHash`
    
- `isDeleted`
    
- `role`
    
- `createdBy`
    

---

# Principle 9 — Use Consistent Naming

Choose one naming style.

Most JSON APIs use **camelCase**.

Good:

```json
{
    "firstName": "Rahul",
    "lastName": "Kumar",
    "profilePicture": "image.png"
}
```

Avoid mixing:

```json
{
    "first_name": "Rahul",
    "lastName": "Kumar",
    "ProfilePicture": "image.png"
}
```

Consistency improves readability.

---

# Principle 10 — Think Like a DTO

DTO stands for:

**Data Transfer Object**

Think of the request body as a contract between the client and server.

Example:

```json
{
    "title": "REST APIs",
    "content": "...",
    "tags": [
        "backend"
    ]
}
```

The client promises to send these fields.

The server promises to understand them.

Neither side should depend on internal database structures.

---

# File Upload Requests

Not every request body is JSON.

Uploading a profile picture:

```http
POST /users/profile-picture
Content-Type: multipart/form-data
```

Body:

```text
profilePicture = image.png
```

`multipart/form-data` is designed for files and form fields.

JSON is not suitable for binary file uploads.

# Common Mistakes

## ❌ Cryptic Field Names

```json
{
    "n": "Rahul"
}
```

Use descriptive names.

---

## ❌ Sending Database Fields

```json
{
    "_id": "...",
    "__v": 0
}
```

The client shouldn't know about database internals.

---

## ❌ Unnecessary Nesting

```json
{
    "user": {
        "details": {
            "profile": {
                "name": "Rahul"
            }
        }
    }
}
```

Keep structures as simple as the domain allows.

---

## ❌ Sending Empty Fields

Instead of:

```json
{
    "bio": ""
}
```

Consider omitting optional fields if they're not being provided, depending on your API contract.

---

## ❌ Mixing Data Types

Bad:

```json
{
    "quantity": "2"
}
```

Better:

```json
{
    "quantity": 2
}
```

Use the correct data types.

---

# Best Practices

- Use meaningful field names.
    
- Keep JSON flat unless nesting reflects real business relationships.
    
- Use arrays for collections.
    
- Clearly define required and optional fields.
    
- Keep request bodies minimal.
    
- Never trust client-controlled security fields.
    
- Keep naming consistent.
    
- Think of the body as an API contract, not a database row.

# Key Terms

|Term|Meaning|
|---|---|
|Request Body|The main data sent by the client|
|JSON|The most common format for API request bodies|
|DTO|Data Transfer Object used to exchange data between client and server|
|Nested Object|An object inside another object|
|Array|A list of values or objects|

# Interview Questions

### 1. What is the purpose of a request body?

**Answer:**  
A request body carries the resource data that the client wants to create or update. It is commonly used with `POST`, `PUT`, and `PATCH` requests.

---

### 2. When should you use nested objects in a request body?

**Answer:**  
Use nested objects when they represent a real business relationship, such as a shipping address inside an order. Avoid unnecessary nesting that makes the request harder to read and validate.

---

### 3. Why shouldn't clients send fields like `id` or `createdAt`?

**Answer:**  
These are server-controlled fields. Allowing clients to set them can lead to inconsistent data, security issues, and violations of business rules.

---

### 4. What is a DTO?

**Answer:**  
A DTO (Data Transfer Object) is a structured representation of the data exchanged between the client and server. It defines the API contract without exposing internal database models.

# 💡 Backend Engineering Insight

A common beginner approach is:

> **"My request body should match my database schema."**

Professional backend engineers think differently:

```text
Frontend
      │
      ▼
Request DTO
      │
Validation
      │
Business Logic
      │
Database Model
```

The **Request DTO** is an **API contract**, not a mirror of your database.

For example, your database might contain:

```text
id
passwordHash
createdAt
updatedAt
isDeleted
role
```

But your registration request should only include:

```json
{
  "name": "Rahul",
  "email": "rahul@gmail.com",
  "password": "StrongPassword123"
}
```

The server is responsible for generating IDs, hashing passwords, assigning roles, and setting timestamps.

Keeping the API contract independent from the database makes your backend easier to refactor without breaking clients—a hallmark of well-designed backend systems.
