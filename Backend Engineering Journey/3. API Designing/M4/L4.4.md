# Why Validation Matters

Imagine a registration API.

The client sends:

```json
{
    "name": "",
    "email": "not-an-email",
    "password": "12"
}
```

Without validation:

```text
Request

↓

Controller

↓

Database

↓

Bad Data Stored
```

Now your database contains invalid information.

Validation prevents bad data from entering your system.

---

# What is Validation?

Validation means:

> **Checking whether incoming data meets the application's rules before processing it.**

Examples:

- Is the email valid?
    
- Is the password long enough?
    
- Is the title empty?
    
- Does the referenced user exist?
    
- Is the user allowed to perform this action?
    

---

# The Four Layers of Validation

Professional backend applications usually validate at multiple layers.

```text
Client
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Database
```

Each layer has a different responsibility.

---

# Layer 1 — Client Validation

Example:

HTML:

```html
<input required type="email">
```

React:

```javascript
if (!email) {
    showError();
}
```

Purpose:

Improve user experience.

The user gets immediate feedback.

---

## Important

Client validation is **never enough**.

Users can:

- Disable JavaScript.
    
- Use Postman.
    
- Use cURL.
    
- Call your API directly.
    

The backend **must always validate again**.

---

# Layer 2 — Controller Validation

The controller checks:

- Required fields
    
- Data types
    
- Basic formats
    

Example request:

```json
{
    "email": "abc@gmail.com",
    "password": "secret123"
}
```

Controller validates:

- Email exists
    
- Password exists
    
- Email format
    
- Password length
    

If validation fails:

```http
400 Bad Request
```

or

```http
422 Unprocessable Entity
```

depending on your API design.

---

## Typical Controller Validation

- Required fields
    
- String length
    
- Number range
    
- Email format
    
- UUID format
    
- Date format
    
- Enum values
    

---

## Example

```json
{
    "title": ""
}
```

Reject immediately.

No need to call the service.

---

# Layer 3 — Service Validation

The service validates **business rules**.

Example:

Registration.

Controller already knows:

- Email format is valid.
    

Service asks:

- Does this email already exist?
    

---

Another example:

Order creation.

Controller validates:

```json
{
    "productId": 15,
    "quantity": 2
}
```

Service validates:

- Product exists.
    
- Stock available.
    
- User allowed to order.
    

These require business knowledge.

---

# Example Flow

```text
POST /orders

↓

Controller

✓ JSON valid

↓

Service

✓ Product exists

✓ Stock available

✓ User active

↓

Repository
```

---

# Layer 4 — Database Validation

The database protects data integrity.

Examples:

Unique email:

```text
Email

↓

UNIQUE INDEX
```

Duplicate?

Database rejects it.

---

Another:

Foreign Key:

```text
Order

↓

Customer ID
```

Customer doesn't exist?

Database rejects it.

---

## Database Should Protect Itself

Never assume validation always happens in the application.

The database should enforce rules like:

- Unique email
    
- Unique username
    
- Foreign keys
    
- Not null
    
- Check constraints (where supported)
    

---

Bad:


---

## 4. Length Validation

```text
8 characters
```

Reject:

```text
abc
```

---

## 5. Range Validation

Age:

```text
18–120
```

Reject:

```text
-5
```

---

## 6. Enum Validation

Allowed:

```text

published

```

Reject:

```text

```

---

## 7. Business Validation

Product stock.

Database:

```text

```

```text

```

Controller cannot know this.

Service rejects it.

# Input Sanitization

Validation checks correctness.

Sanitization cleans input.

Example:

User submits:

```text
   Rahul
```

Trim:

```text
Rahul
```

---

Lowercase email:

```text
ABC@GMAIL.COM
```

↓

```text
abc@gmail.com
```

---

Sanitization often happens before validation.

# Validation Libraries

Popular Node.js libraries:

- Joi
    
- Zod
    
- Yup
    
- Express Validator
    

Example (Joi):


The exact library is less important than understanding **where** validation belongs.

# Error Responses

Bad:

```json
{
    "error": "Invalid"
}
```

Not helpful.

---

Better:


# Common Mistakes

## ❌ Everything in Controller

```text
Controller

↓

500 lines
```

Controllers become difficult to maintain.

---

## ❌ Everything in Service

Now every request reaches the service, even when the JSON is malformed.

Basic validation should happen earlier.

---

## ❌ Trusting Client Validation

Never trust browsers.

Always validate on the server.

---

## ❌ Database Only

Relying only on database errors leads to poor user experience and less meaningful error messages.

---

# Best Practices

- Validate at multiple layers.
    
- Keep controller validation focused on request structure.
    
- Keep business rules in the service layer.
    
- Let the database enforce data integrity.
    
- Sanitize before validating when appropriate.
    
- Return clear validation errors.
    
- Never trust client input.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Validation|Checking whether input satisfies defined rules|
|Sanitization|Cleaning or normalizing input before processing|
|Business Validation|Rules based on business logic|
|Data Integrity|Ensuring the database remains consistent and correct|
|DTO Validation|Validating the request contract before entering business logic|

# Interview Questions

### 1. Why shouldn't validation exist only on the frontend?

**Answer:**  
Frontend validation improves user experience but cannot be trusted for security or correctness. Clients can bypass it using tools like Postman or cURL, so the backend must always validate incoming requests.

---

### 2. What is the difference between controller validation and service validation?

**Answer:**  
Controller validation checks request syntax and structure, such as required fields, data types, and formats. Service validation enforces business rules, such as checking whether a product exists or whether a user is allowed to perform an action.

---

### 3. Why should the database also enforce validation?

**Answer:**  
The database is the final line of defense for data integrity. Constraints such as unique indexes, foreign keys, and non-null fields protect the data even if application-level validation is bypassed or contains a bug.

---

### 4. What is the difference between validation and sanitization?

**Answer:**  
Validation checks whether input meets the required rules, while sanitization modifies or cleans input into a consistent form—for example, trimming whitespace or converting email addresses to lowercase.

---

# 💡 Backend Engineering Insight

One of the most common beginner mistakes is treating **validation** as a single step.

Professional backend engineers think in layers:

```text
Client
   │
   ▼
"Is the form complete?"

Controller
   │
   ▼
"Is the request well-formed?"

Service
   │
   ▼
"Does this operation make business sense?"

Database
   │
   ▼
"Can this data safely exist?"
```

Each layer answers a **different question**.

This separation keeps your codebase easier to test, easier to maintain, and much more resilient as your application grows.
