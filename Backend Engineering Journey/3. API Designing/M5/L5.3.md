# Why Status Codes Matter

Suppose you call:

```http
POST /posts
```

The server responds:

```http
200 OK
```

Did it:

- Create the post?
    
- Update an existing post?
    
- Ignore the request?
    

The status code alone doesn't fully answer those questions.

Now compare:

```http
201 Created
```

Immediately you know:

> A new resource was successfully created.

Good status codes make APIs self-explanatory.

---

# Status Code Categories

Every HTTP status code belongs to one of five categories.

|Range|Category|Meaning|
|---|---|---|
|**1xx**|Informational|Request is being processed|
|**2xx**|Success|Request completed successfully|
|**3xx**|Redirection|Client should perform another request|
|**4xx**|Client Error|Client sent an invalid request|
|**5xx**|Server Error|Server failed to process a valid request|

Think of them as:

```text
1xx → Please wait

2xx → Success

3xx → Go somewhere else

4xx → Client mistake

5xx → Server mistake
```

---

# 1xx — Informational

Rarely used in application development.

Example:

```http
100 Continue
```

Client:

> "Can I send the request body?"

Server:

> "Yes, continue."

You'll rarely return 1xx responses from Express or similar frameworks.

---

# 2xx — Success Responses

These are the responses you'll use most often.

---

# 200 OK

The default success response.

Use for:

- GET
    
- Successful PATCH
    
- Successful PUT
    
- DELETE (when returning a body)
    

Example:

```http
GET /posts/15

↓

200 OK
```

---

Response:

```json
{
    "success": true,
    "data": {
        "id": 15
    }
}
```

---

# 201 Created

Use when a **new resource is created**.

Example:

```http
POST /posts
```

↓

```http
201 Created
```

Response:

```json
{
    "success": true,
    "data": {
        "id": 15
    }
}
```

Optionally include:

```http
Location: /posts/15
```

---

# 202 Accepted

Often misunderstood.

Meaning:

> The server accepted the request, but processing will happen later.

Example:

```http
POST /reports
```

Generating a large report may take several minutes.

Instead of making the client wait:

```http
202 Accepted
```

Response:

```json
{
    "success": true,
    "message": "Report generation started."
}
```

The client may later check:

```http
GET /reports/123/status
```

---

# Real-world Examples of 202

- Video processing
    
- Email sending
    
- Image resizing
    
- Background jobs
    
- AI model inference
    
- Large data exports
    

---

# 204 No Content

Use when:

The operation succeeded.

No response body is needed.

Example:

```http
DELETE /posts/15
```

↓

```http
204 No Content
```

Body:

Nothing.

---

Do **not** send JSON with `204`.

Bad:

```http
204 No Content
```

```json
{
    "success": true
}
```

A `204` response must not include a response body.

---

# 3xx — Redirection

Less common in REST APIs, but important to understand.

---

# 301 Moved Permanently

Resource moved permanently.

Example:

```text
/api/v1/posts

↓

/api/v2/posts
```

Clients may update stored links.

---

# 302 Found

Temporary redirect.

The original URL may still be used in the future.

---

# 304 Not Modified

Used with caching.

Client sends:

```http
If-None-Match: abc123
```

Server checks.

Nothing changed.

Returns:

```http
304 Not Modified
```

No body.

The client uses its cached copy.

---

# 307 Temporary Redirect

Like `302`, but preserves the original HTTP method.

Example:

```http
POST /login
```

↓

Redirect

↓

Still:

```http
POST
```

Not changed to `GET`.

---

# 308 Permanent Redirect

Permanent version of `307`.

The request method is preserved.

---

# 4xx — Client Errors

The client made a mistake.

The server is working correctly.

---

# 400 Bad Request

The request is malformed.

Examples:

- Invalid JSON
    
- Missing required field
    
- Invalid parameter format
    

Example:

```json
{
    "email":
}
```

Invalid JSON.

↓

```http
400 Bad Request
```

---

# 401 Unauthorized

Meaning:

Authentication is required or invalid.

Examples:

- Missing token
    
- Expired token
    
- Invalid token
    

Response:

```http
401 Unauthorized
```

---

Think:

> "Who are you?"

---

# 403 Forbidden

Authentication succeeded.

Permission denied.

Example:

Regular user tries:

```http
DELETE /users/5
```

Only admins may do that.

↓

```http
403 Forbidden
```

Think:

> "I know who you are, but you're not allowed."

---

# 401 vs 403

This is a very common interview question.

|401|403|
|---|---|
|Not authenticated|Authenticated but not authorized|
|Login required|Permission denied|

---

# 404 Not Found

Resource doesn't exist.

Example:

```http
GET /posts/999
```

↓

```http
404 Not Found
```

---

# 409 Conflict

The request conflicts with the current state.

Example:

Registration.

Email already exists.

↓

```http
409 Conflict
```

Another example:

Creating a username that's already taken.

---

# 410 Gone

Different from 404.

404:

> Maybe it never existed.

410:

> It existed, but has been permanently removed.

Example:

A discontinued public API endpoint or permanently deleted resource.

---

# 412 Precondition Failed

Used with conditional requests.

Example:

Client says:

```http
If-Match: abc123
```

Server:

Current ETag:

```text
xyz999
```

Doesn't match.

↓

```http
412 Precondition Failed
```

Helps prevent accidental overwrites.

---

# 415 Unsupported Media Type

Example:

API expects:

```http
Content-Type: application/json
```

Client sends:

```http
Content-Type: text/plain
```

↓

```http
415 Unsupported Media Type
```

---

# 422 Unprocessable Entity

The request syntax is valid.

Business validation fails.

Example:

```json
{
    "email": "not-an-email"
}
```

JSON is valid.

Email isn't.

Many APIs use:

```http
422 Unprocessable Entity
```

for validation errors.

Some APIs instead use `400`. Either approach can be valid if applied consistently.

---

# 429 Too Many Requests

Rate limit exceeded.

Example:

API allows:

```text
100 requests/minute
```

Client sends:

```text
500 requests
```

↓

```http
429 Too Many Requests
```

Often includes:

```http
Retry-After: 60
```

Meaning:

Try again in one minute.

---

# 5xx — Server Errors

The client did nothing wrong.

The server failed.

---

# 500 Internal Server Error

Unexpected server failure.

Example:

Unhandled exception.

Database crash.

Null reference.

Use:

```http
500 Internal Server Error
```

Don't expose stack traces to clients.

---

# 502 Bad Gateway

Usually occurs with reverse proxies.

Example:

```text
Client

↓

Nginx

↓

Backend
```

Backend sends an invalid response.

Nginx returns:

```http
502 Bad Gateway
```

---

# 503 Service Unavailable

Server is temporarily unavailable.

Examples:

- Maintenance
    
- Overloaded server
    

Often includes:

```http
Retry-After
```

---

# 504 Gateway Timeout

Gateway waited too long.

Example:

```text
Client

↓

Load Balancer

↓

Backend

↓

Database
```

Database never responds.

Gateway returns:

```http
504 Gateway Timeout
```

---

# Status Code Decision Tree

```text
Request received
       │
       ▼
Success?
       │
 ┌─────┴─────┐
 │           │
Yes          No
 │           │
 ▼           ▼
2xx       Client or Server?
             │
      ┌──────┴──────┐
      │             │
   Client         Server
      │             │
      ▼             ▼
     4xx           5xx
```

# Common Mistakes

### ❌ Returning 200 for every response

Bad:

```http
200 OK
```

Validation failed?

Still:

```http
200 OK
```

Incorrect.

---

### ❌ Using 500 for client mistakes

Bad:

```text
User forgot email

↓

500
```

Should be:

```http
400 Bad Request
```

or

```http
422 Unprocessable Entity
```

---

### ❌ Returning 404 instead of 403

If the user is authenticated but lacks permission:

Use:

```http
403 Forbidden
```

> **Note:** Some applications intentionally return `404 Not Found` instead of `403 Forbidden` to avoid revealing that a protected resource exists. This is a security design choice, not a REST requirement.

---

### ❌ Returning JSON with 204

Don't send a response body.

---

# Best Practices

- Use the most specific status code available.
    
- Let status codes communicate the result.
    
- Don't overload `200 OK`.
    
- Distinguish authentication from authorization.
    
- Use `201` for creation.
    
- Use `204` when no response body is needed.
    
- Reserve `5xx` for server failures.

# Status Code Cheat Sheet

|Code|Meaning|Typical Use|
|---|---|---|
|200|OK|Successful retrieval or update|
|201|Created|New resource created|
|202|Accepted|Processing will happen later|
|204|No Content|Success with no response body|
|301|Moved Permanently|Permanent redirect|
|302|Found|Temporary redirect|
|304|Not Modified|Cached response is still valid|
|307|Temporary Redirect|Temporary redirect preserving method|
|308|Permanent Redirect|Permanent redirect preserving method|
|400|Bad Request|Malformed request|
|401|Unauthorized|Authentication required or failed|
|403|Forbidden|Permission denied|
|404|Not Found|Resource doesn't exist|
|409|Conflict|State conflict (e.g., duplicate email)|
|410|Gone|Resource permanently removed|
|412|Precondition Failed|Conditional request failed|
|415|Unsupported Media Type|Wrong `Content-Type`|
|422|Unprocessable Entity|Validation/business input error|
|429|Too Many Requests|Rate limit exceeded|
|500|Internal Server Error|Unexpected server failure|
|502|Bad Gateway|Upstream server returned an invalid response|
|503|Service Unavailable|Temporary outage or maintenance|
|504|Gateway Timeout|Upstream server took too long|

# Interview Questions

### 1. What is the difference between `200 OK` and `201 Created`?

**Answer:**  
`200 OK` indicates a successful request, typically for retrieval or updates. `201 Created` specifically indicates that a new resource has been created and may include a `Location` header pointing to it.

---

### 2. What is the difference between `401 Unauthorized` and `403 Forbidden`?

**Answer:**  
`401 Unauthorized` means the client is not authenticated or has invalid credentials. `403 Forbidden` means the client is authenticated but does not have permission to perform the requested action.

---

### 3. When should you return `204 No Content`?

**Answer:**  
Use `204 No Content` when the operation succeeds but there is no meaningful response body to return, such as after a successful delete or certain update operations.

---

### 4. What is the difference between `400 Bad Request` and `422 Unprocessable Entity`?

**Answer:**  
`400 Bad Request` is commonly used for malformed or structurally invalid requests (such as invalid JSON). `422 Unprocessable Entity` is commonly used when the request is syntactically correct but fails validation or business rules (such as an invalid email format). Not all APIs distinguish between them, so consistency is important.

---

# 💡 Backend Engineering Insight

One pattern you'll notice in mature backend systems is:

> **Status codes describe the HTTP outcome.**  
> **Response bodies describe the business outcome.**

For example:

```http
409 Conflict
```

```json
{
  "success": false,
  "message": "Email already exists.",
  "code": "EMAIL_ALREADY_EXISTS"
}
```

The HTTP status tells every client, proxy, and monitoring tool that there was a **conflict**.

The JSON body gives your application-specific details that the frontend can display or handle programmatically.

Using **both** together makes your API easier to integrate, debug, and monitor.
