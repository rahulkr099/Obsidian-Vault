# Why Error Response Design Matters

Imagine you're building a frontend.

One endpoint returns:

```json
{
    "error": "Wrong"
}
```

Another returns:

```json
{
    "message": "Something happened"
}
```

Another returns:

```json
{
    "errors": [
        "Email"
    ]
}
```

Now the frontend needs different code for every endpoint.

Professional APIs return errors in one predictable format.

---

# The Goal

Every error should answer four questions:

1. Did the request fail?
    
2. What went wrong?
    
3. Which field caused the problem (if any)?
    
4. What should the client do next?
    

---

# Standard Error Response

A common structure is:

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": [
        {
            "field": "email",
            "message": "Email is required."
        }
    ]
}
```

Each field has a purpose.

|Field|Purpose|
|---|---|
|success|Indicates failure|
|message|Summary of the error|
|errors|Detailed validation or field-level errors|
|code|Optional application-specific error code|

---

# Error Categories

Most backend errors fall into five groups.

```text
Request Errors
        │
        ├── Validation Errors
        ├── Authentication Errors
        ├── Authorization Errors
        ├── Business Logic Errors
        └── Server Errors
```

Let's study each one.

---

# Validation Errors

Example:

```json
{
    "email": "",
    "password": "123"
}
```

Problems:

- Email missing
    
- Password too short
    

Response:

```http
422 Unprocessable Entity
```

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": [
        {
            "field": "email",
            "message": "Email is required."
        },
        {
            "field": "password",
            "message": "Password must be at least 8 characters."
        }
    ]
}
```

Notice:

The frontend knows exactly what to highlight.

---

# Authentication Errors

Example:

```http
Authorization:
Bearer invalid-token
```

Response:

```http
401 Unauthorized
```

```json
{
    "success": false,
    "message": "Authentication required."
}
```

Another example:

Expired token.

```json
{
    "success": false,
    "message": "Access token has expired."
}
```

---

# Authorization Errors

User logged in.

Attempts:

```http
DELETE /users/5
```

Only admins may do this.

Response:

```http
403 Forbidden
```

```json
{
    "success": false,
    "message": "You do not have permission to perform this action."
}
```

---

# Business Logic Errors

These are not syntax errors.

The request is valid.

The business rule fails.

Example:

Registration.

Email already exists.

Response:

```http
409 Conflict
```

```json
{
    "success": false,
    "message": "Email already exists."
}
```

Another example:

```text
Stock = 2
```

User orders:

```text
5
```

Response:

```json
{
    "success": false,
    "message": "Insufficient stock."
}
```

---

# Resource Not Found

Example:

```http
GET /posts/999
```

Response:

```http
404 Not Found
```

```json
{
    "success": false,
    "message": "Post not found."
}
```

---

# Server Errors

Unexpected failures.

Examples:

- Database unavailable
    
- Unhandled exception
    
- Third-party service failure
    

Response:

```http
500 Internal Server Error
```

```json
{
    "success": false,
    "message": "An unexpected error occurred."
}
```

Do **not** expose internal details.

---

# Never Expose Internal Errors

Bad:

```json
{
    "error": "MongoServerError: E11000 duplicate key..."
}
```

Or:

```json
{
    "stack": "..."
}
```

Clients don't need database names or stack traces.

These details belong in your logs, not your API responses.

---

# User Message vs Internal Error

Think of two audiences.

```text
Client
      │
Friendly Message
```

```text
Backend Logs
      │
Detailed Error
```

Example:

Client sees:

```json
{
    "message": "Something went wrong."
}
```

Logs contain:

```text
MongoServerError:
Duplicate key:
users.email
```

This keeps your API secure while preserving debugging information.

---

# Custom Error Codes

Many APIs include a machine-readable code.

Example:

```json
{
    "success": false,
    "code": "EMAIL_ALREADY_EXISTS",
    "message": "Email already exists."
}
```

The frontend can use `code` for programmatic handling.

Example:

```text
EMAIL_ALREADY_EXISTS
```

↓

Show:

```text
Please use another email.
```

Codes remain stable even if messages change.

---

# Global Error Handler

Instead of writing error handling everywhere:

Bad:

```text
Controller A

try...

catch...
```

```text
Controller B

try...

catch...
```

```text
Controller C

try...

catch...
```

Professional applications use one centralized error handler.

```text
Controller
      │
Throws Error
      │
Global Error Handler
      │
HTTP Response
```

Benefits:

- Consistent responses
    
- Less duplicated code
    
- Easier maintenance
    

---

# Custom Error Classes

Instead of throwing generic errors:

```javascript
throw new Error("Email exists");
```

Create meaningful error types.

```text
ValidationError

AuthenticationError

AuthorizationError

NotFoundError

ConflictError
```

Each maps naturally to an HTTP status code.

This keeps your controllers and services much cleaner.

---

# Error Flow

```text
Client
    │
Request
    │
Controller
    │

    │
Repository
    │

```

Suppose:

Duplicate email.

Repository detects the issue.

↓

Throws:

```text

```

↓

```http

```

↓

# Common Mistakes

## ❌ Different Error Formats

Endpoint A:

```json
{
    "error":"..."
}
```

Endpoint B:

```json
{
    "message":"..."
}
```

Choose one consistent structure.

---

## ❌ Returning `200 OK` for Errors

Bad:

```http
200 OK
```

```json
{
    "success": false
}
```

Use the correct HTTP status code.

---

## ❌ Exposing Stack Traces

Never send:

```json
{
    "stack":"..."
}
```

to clients.

---

## ❌ Vague Messages

Bad:

```json
{
    "message":"Invalid."
}
```

Better:

```json
{
    "message":"Password must contain at least one uppercase letter."
}
```

Clear messages help API consumers fix problems quickly.

---

# Best Practices

- Use one error response format across the API.
    
- Return the correct HTTP status code.
    
- Keep client messages clear and safe.
    
- Log detailed errors internally.
    
- Use custom error codes for common business cases.
    
- Centralize error handling with a global handler.
    
- Create custom error classes instead of generic errors.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Validation Error|Input does not satisfy validation rules|
|Authentication Error|Identity cannot be verified|
|Authorization Error|User lacks permission|
|Business Error|Business rule prevents the operation|
|Global Error Handler|Centralized component that formats errors|
|Error Code|Stable identifier for a specific error type|

# Interview Questions

### 1. Why should APIs use a consistent error response format?

**Answer:**  
A consistent format allows frontend applications to handle errors uniformly, reduces conditional logic, and makes the API easier to document and maintain.

---

### 2. Why shouldn't stack traces be returned to clients?

**Answer:**  
Stack traces reveal internal implementation details that may create security risks. They should be logged on the server while clients receive safe, user-friendly error messages.

---

### 3. What is the purpose of a global error handler?

**Answer:**  
A global error handler catches application errors in one place, converts them into consistent HTTP responses, reduces duplicate code, and simplifies maintenance.

---

### 4. Why are custom error codes useful?

**Answer:**  
Custom error codes provide stable identifiers for specific error conditions. Frontend applications can react programmatically to these codes without relying on message text, which may change over time.

# 💡 Backend Engineering Insight

A mature backend treats **errors as part of the API contract**, not as unexpected events.

A common production flow looks like this:

```text
Controller
      │
Validation
      │
Service
      │
Throw Custom Error
      │
Global Error Handler
      │
HTTP Status + JSON Response
      │
Frontend
```

This approach gives you three important benefits:

- **Consistency:** Every endpoint returns errors in the same format.
    
- **Maintainability:** Error handling logic lives in one place.
    
- **Security:** Internal implementation details stay in server logs instead of being exposed to clients.
    

This architecture is widely used in production Node.js backends because it scales well as applications grow.
