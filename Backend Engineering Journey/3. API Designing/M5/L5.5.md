# Why Pagination Matters

Imagine your blog application has:

```text
5 posts
```

Returning all posts is easy.

Now imagine:

```text
5,000 posts
```

Still manageable.

Now imagine:

```text
5,000,000 posts
```

Returning every post in one response would:

- Consume a lot of memory
    
- Increase response time
    
- Waste bandwidth
    
- Slow down the frontend
    
- Put unnecessary load on the database
    

Professional APIs return data in **small chunks**, called **pages**.

---

# What is Pagination?

Pagination means dividing a large dataset into smaller parts.

Instead of:

```http
GET /posts
```

returning:

```text
5,000,000 posts
```

it returns:

```text
20 posts
```

at a time.

---

# Why Professional APIs Use Pagination

Without pagination:

```text
Client

↓

GET /posts

↓

Database

↓

5,000,000 rows

↓

Server Memory

↓

Huge JSON

↓

Slow Network
```

---

With pagination:

```text
Client

↓

GET /posts?page=1&limit=20

↓

Database

↓

20 rows

↓

Fast Response
```

Much more efficient.

---

# Offset Pagination

The most common approach.

Example:

```http
GET /posts?page=2&limit=10
```

Meaning:

```text
Page = 2

Limit = 10
```

Return:

Posts:

```text
11–20
```

---

Database query (conceptually):

```sql
LIMIT 10
OFFSET 10
```

---

Response:

```json
{
    "success": true,
    "data": [
        ...
    ],
    "meta": {
        "page": 2,
        "limit": 10,
        "total": 143,
        "totalPages": 15
    }
}
```

---

# Understanding Offset

Suppose:

```text
100 posts
```

Limit:

```text
10
```

Requests:

```text
Page 1

↓

Posts 1–10
```

---

```text
Page 2

↓

Posts 11–20
```

---

```text
Page 3

↓

Posts 21–30
```

Simple.

Easy to understand.

---

# Advantages of Offset Pagination

✅ Easy to implement

✅ Easy to understand

✅ Works well for admin dashboards

✅ Works well for small datasets

---

# Disadvantages of Offset Pagination

Imagine:

```text
10 million posts
```

Request:

```http
GET /posts?page=500000
```

Database must skip millions of rows before returning results.

This becomes slower as the offset grows.

---

Another issue:

Suppose:

Page 1:

```text
A
B
C
D
```

Someone inserts:

```text
X
```

Now Page 2 may contain duplicate or missing items.

Offset pagination can become inconsistent when data changes frequently.

---

# Cursor Pagination

Instead of page numbers,

use a cursor.

Example:

```http
GET /posts?cursor=abc123&limit=10
```

The cursor usually represents the last item received.

Example:

```text
Last Post ID = 25
```

Next request:

```http
GET /posts?cursor=25
```

Server returns:

Posts after:

```text
25
```

---

Response:

```json
{
    "success": true,
    "data": [
        ...
    ],
    "meta": {
        "nextCursor": "35",
        "hasNextPage": true
    }
}
```

---

# Why Cursor Pagination is Faster

Database:

Instead of:

```sql
OFFSET 500000
```

it simply asks:

```sql
WHERE id > 25
LIMIT 10
```

Much faster.

---

# Where Cursor Pagination is Used

Common examples:

- Instagram feed
    
- Facebook timeline
    
- Twitter/X timeline
    
- LinkedIn feed
    
- Infinite scrolling
    
- Chat messages
    

Whenever data changes frequently, cursor pagination is often a better choice.

---

# Offset vs Cursor

|Offset Pagination|Cursor Pagination|
|---|---|
|Page numbers|Cursor/token|
|Easy to implement|Slightly more complex|
|Can become slow on large datasets|Performs well on large datasets|
|Good for admin panels|Good for feeds and infinite scroll|
|Can produce duplicates when data changes|More stable as data changes|

# Metadata

Metadata describes the response.

Not the actual data.

Example:

```json
{
    "success": true,
    "data": [...],
    "meta": {
        "page": 2,
        "limit": 10,
        "total": 143,
        "totalPages": 15
    }
}
```

The frontend uses `meta` to build pagination controls.

---

# Common Metadata Fields

|Field|Meaning|
|---|---|
|page|Current page|
|limit|Items per page|
|total|Total number of items|
|totalPages|Number of pages|
|hasNextPage|More data available|
|hasPreviousPage|Previous page exists|
|nextCursor|Cursor for next request|
|previousCursor|Cursor for previous request (optional)|

# Should Every API Return Total Count?

Not always.

Counting rows can be expensive for very large datasets.

For example:

```text
500 million rows
```

A full count may be slower than fetching one page of results.

In such cases, APIs often return:

```json
{
    "meta": {
        "hasNextPage": true,
        "nextCursor": "abc123"
    }
}
```

instead of an exact total.

Choose based on performance needs.

---

# Common Mistakes

## ❌ Returning Everything

```http
GET /posts
```

↓

```text
5 million posts
```

Always paginate large collections.

---

## ❌ No Metadata

Bad:

```json
{
    "data":[...]
}
```

The frontend doesn't know:

- Current page
    
- Total pages
    
- Whether more data exists
    

---

## ❌ Using Offset for Large Feeds

Feeds change constantly.

Cursor pagination is usually a better fit.

---

## ❌ Very Large Limits

Bad:

```http
GET /posts?limit=100000
```

A good API enforces a maximum limit, such as:

```text
100
```

or

```text
200
```

to protect performance.

---

# Best Practices

- Paginate all collection endpoints that can grow large.
    
- Use offset pagination for dashboards and simple lists.
    
- Use cursor pagination for feeds and infinite scrolling.
    
- Include useful metadata.
    
- Enforce a reasonable maximum page size.
    
- Think about database performance, not just API convenience.

# Interview Questions

### 1. Why is pagination important?

**Answer:**  
Pagination reduces response size, improves performance, lowers memory usage, decreases bandwidth consumption, and makes APIs scalable for large datasets.

---

### 2. What is the difference between offset pagination and cursor pagination?

**Answer:**  
Offset pagination uses page numbers and offsets, making it simple but less efficient for very large datasets. Cursor pagination uses a marker (cursor) to continue from the last item, providing better performance and more consistent results for changing datasets.

---

### 3. When should you use cursor pagination?

**Answer:**  
Cursor pagination is well suited for frequently changing datasets such as social media feeds, chat messages, activity logs, and infinite scrolling interfaces.

---

### 4. What information should pagination metadata include?

**Answer:**  
Common metadata includes the current page, page size (`limit`), total items (when practical), total pages, whether another page exists, and cursor information for cursor-based pagination.

# 💡 Backend Engineering Insight

When designing list endpoints, experienced backend engineers don't just ask:

> **"How do I return the data?"**

They also ask:

> **"How will clients navigate the data?"**

Think about these common products:

|Product|Typical Pagination|
|---|---|
|Admin Dashboard|Offset (`page` + `limit`)|
|E-commerce Product List|Offset (`page` + `limit`)|
|Blog Articles|Offset (`page` + `limit`)|
|Instagram Feed|Cursor|
|Twitter/X Timeline|Cursor|
|WhatsApp Chat|Cursor|
|Notification Feed|Cursor|

For your MERN projects—such as a **Blog App**, **Todo App**, or **URL Shortener Dashboard**—**offset pagination** is usually the right starting point because it's simple and user-friendly.

As you build systems with high-volume, continuously changing data (feeds, chats, activity streams), **cursor pagination** becomes the preferred design.
