# Why Authentication Exists

Imagine your Blog API.

Anyone can:

```http
DELETE /posts/15
```

What happens?

Everyone can delete everyone's posts.

That's a serious security problem.

The server must answer:

```text
Who is making this request?
```

This is the purpose of authentication.

---

# What is Authentication?

Authentication means:

> **Verifying the identity of a user.**

The server asks:

```text
Who are you?
```

The user proves their identity.

Example:

```text
Email

+

Password
```

If correct:

The server trusts that the user is who they claim to be.

---

# Real-World Example

Think about entering a college.

Security guard asks:

```text
Who are you?
```

You show:

```text
College ID Card
```

The guard verifies it.

Now you are authenticated.

---

# What is Authorization?

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What are you allowed to do?
```

Example:

You are logged in.

Can you:

```text
Delete another user's account?
```

Maybe not.

That depends on permissions.

---

# Authentication vs Authorization

|Authentication|Authorization|
|---|---|
|Verifies identity|Verifies permissions|
|"Who are you?"|"What can you do?"|
|Happens first|Happens after authentication|
|Login|Access control|

---

# Identity vs Permission

Suppose:

Rahul logs in.

Identity:

```text
User ID = 21
```

Permission:

```text
Role = Admin
```

Identity tells us **who**.

Permission tells us **what**.

Never confuse them.

# Authentication Lifecycle

Every authentication system follows a similar lifecycle.

```text
Register
     │
     ▼
Login
     │
     ▼
Identity Verified
     │
     ▼
Access Token Issued
     │
     ▼
Protected API Requests
     │
     ▼
Token Expires
     │
     ▼
Refresh Token
     │
     ▼
New Access Token
     │
     ▼
Logout
```

We'll study each step in later lessons.

---

# Registration

The user creates an account.

Example:

```http
POST /auth/register
```

The server:

- Validates input
    
- Hashes the password
    
- Stores the user
    
- Sends a verification email (optional)
    

Registration is **not** authentication.

It creates an identity.

---

# Login

Example:

```http
POST /auth/login
```

The user provides credentials.

The server verifies them.

If valid:

Authentication succeeds.

---

# Protected Requests

Example:

```http
GET /profile
```

The client proves:

```text
I am Rahul.
```

The server verifies that proof before returning protected data.

---

# Logout

The user ends the authenticated session.

Depending on the authentication strategy, the server may invalidate a session, revoke a refresh token, or simply remove client-side credentials.

# Two Big Authentication Approaches

There are two major authentication models.

```text
Authentication

│

├── Stateful

└── Stateless
```

Let's understand both.

---

# Stateful Authentication

The server remembers every logged-in user.

Example:

```text
User

↓

Login

↓

Server

↓

Creates Session

↓

Stores Session
```

Every request includes:

```text
Session ID
```

The server checks:

```text
Session Database
```

If found:

User is authenticated.

---

Visual:

```text
Client

↓

Session ID

↓

Server

↓

Session Store

↓

User
```

The server stores authentication state.

Hence:

**Stateful**.

---

# Stateless Authentication

The server doesn't store login state.

Instead:

```text
Login

↓

Server

↓

Creates Token

↓

Returns Token

↓

Client Stores Token
```

Every request includes the token.

The server verifies the token.

No session lookup is required.

---

Visual:

```text
Client

↓

JWT

↓

Server

↓

Verify JWT

↓

Allow Request
```

The server doesn't need to remember each logged-in user between requests.

---

# Stateful vs Stateless

|Stateful|Stateless|
|---|---|
|Server stores sessions|Client stores token|
|Session lookup required|Token verification|
|Session ID|JWT or another token|
|Easy logout|Logout requires token invalidation strategy|
|Traditional web apps|Modern APIs and SPAs|

Both approaches are widely used.

The right choice depends on the application's requirements.

# Why JWT Became Popular

Modern frontend applications often have:

- React
    
- Mobile apps
    
- Smart TVs
    
- Desktop applications
    
- Third-party APIs
    

JWT makes it easier for different clients to authenticate using the same API.

Example:

```text
React

↓

API

↓

JWT

↓

Protected Route
```

We'll study JWT in detail later.

For now, just remember:

JWT is **one implementation of stateless authentication**, not authentication itself.

# Authentication Doesn't Mean Security

Suppose:

```text
User

↓

Correct Password

↓

Authenticated
```

Can they now:

```text
DELETE /users
```

Not necessarily.

Authentication only proves identity.

Authorization decides permissions.

# Authentication Flow Example

Let's walk through a Blog API.

---

## Step 1 — Register

```http
POST /auth/register
```

Server:

```text
Create User
```

---

## Step 2 — Login

```http
POST /auth/login
```

Server:

```text
Verify Password
```

---

## Step 3 — Token Issued

```text
Access Token

+

Refresh Token
```

Returned to the client.

---

## Step 4 — Protected Request

```http

```

Header:

```http

```

Server:

```text

↓
```

## Step 5 — Token Expires

The access token is no longer valid.

The client requests a new one.

```http

```

Server:

```text

```

```http
POST /auth/logout
```

# Common Mistakes

## ❌ Confusing Authentication with Authorization

Authentication:

```text
Who are you?
```

Authorization:

```text
Can you do this?
```

---

## ❌ Thinking JWT Equals Authentication

JWT is only one way to implement authentication.

Authentication is the overall process.

---

## ❌ Assuming Login Means Unlimited Access

Users may still have different permissions.

Always perform authorization checks.

---

## ❌ Storing Plain Passwords

Never store:

```text
password = "secret123"
```

Always store a **hashed password**.

We'll cover password hashing in later lessons.

---

# Best Practices

- Separate authentication from authorization.
    
- Think of authentication as identity verification.
    
- Use short-lived access tokens.
    
- Keep authorization checks separate from login logic.
    
- Never store plaintext passwords.
    
- Design authentication as a complete lifecycle, not just a login endpoint.

# Interview Questions

### 1. What is the difference between authentication and authorization?

**Answer:**  
Authentication verifies a user's identity ("Who are you?"). Authorization determines what that authenticated user is allowed to do ("What are you allowed to access or perform?").

---

### 2. What is the difference between stateful and stateless authentication?

**Answer:**  
In stateful authentication, the server stores session information and checks it on each request. In stateless authentication, the client sends a token (such as a JWT), and the server verifies the token without storing per-user session state.

---

### 3. Why is JWT considered stateless?

**Answer:**  
A JWT contains information that allows the server to verify it without looking up a session in server-side storage. The server validates the token's signature and claims instead of retrieving session data.

---

### 4. Why is authorization still required after authentication?

**Answer:**  
Authentication only proves who the user is. Authorization checks whether that authenticated user has permission to perform a specific action or access a particular resource.

# 💡 Backend Engineering Insight

A common beginner mindset is:

```text
Login
   │
   ▼
Done
```

Professional backend engineers think in terms of an **authentication lifecycle**:

```text
Register
    │
Login
    │
Issue Tokens
    │
Authenticate Requests
    │
Authorize Actions
    │
Refresh Tokens
    │
Logout
```

Authentication is not a single endpoint—it's a complete system.

Understanding this lifecycle makes it much easier to design secure APIs, implement middleware, and explain authentication flows confidently in backend interviews.
