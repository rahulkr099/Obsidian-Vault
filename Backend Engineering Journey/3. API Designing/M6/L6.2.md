# Why Registration Matters

Registration is the **entry point** into your application.

A mistake here can lead to:

- Duplicate users
    
- Weak passwords
    
- Fake accounts
    
- Security vulnerabilities
    
- Poor user experience
    

Professional registration APIs are designed carefully.

---

# Registration Flow

A production registration flow looks like this:

```text
User
   │
Fill Registration Form
   │
POST /auth/register
   │
Controller Validation
   │
Service Validation
   │
Check Duplicate Email
   │
Hash Password
   │
Save User
   │
Generate Verification Token
   │
Send Verification Email
   │
Return Response
```

Every step has a purpose.

---

# Step 1 — Endpoint Design

A common REST endpoint is:

```http
POST /auth/register
```

Why `POST`?

Because we're **creating a new user account**.

---

# Step 2 — Request Body

Example:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "password": "StrongPassword123"
}
```

Notice what is included:

- Name
    
- Email
    
- Password
    

Nothing more.

---

# What Should NOT Be Included?

Clients should **not** send:

```json
{
    "role": "admin",
    "isVerified": true,
    "createdAt": "...",
    "id": 100
}
```

These are server-controlled fields.

The server decides:

- User ID
    
- Role
    
- Verification status
    
- Timestamps
    

---

# Step 3 — Controller Validation

The controller checks:

- Required fields
    
- Email format
    
- Password length
    
- Name length
    

Example:

```json
{
    "email": "invalid-email"
}
```

Response:

```http
422 Unprocessable Entity
```

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": [
        {
            "field": "email",
            "message": "Email must be valid."
        }
    ]
}
```

---

# Step 4 — Service Validation

Now the service checks business rules.

Example:

```text
Does email already exist?
```

If yes:

```http
409 Conflict
```

```json
{
    "success": false,
    "message": "Email already exists."
}
```

Controller doesn't know this.

Only the service does.

---

# Step 5 — Password Hashing

Never store:

```text
password = "StrongPassword123"
```

Instead:

```text
StrongPassword123
        │
Hash Function (e.g., bcrypt, Argon2)
        │
Hashed Password
```

Database stores:

```text
$2b$12$...
```

The original password cannot be recovered from the hash.

> **Important:** Hashing happens **before saving** the user.

---

# Step 6 — Create User

After validation:

```text
Create User
```

Example database record:

```text
id = 21

name = Rahul

email = rahul@example.com

passwordHash = $2b$12$...

role = user

isVerified = false
```

Notice:

The password itself is never stored.

---

# Step 7 — Email Verification (Recommended)

Many production systems require email verification.

Flow:

```text
Create User
      │
Generate Verification Token
      │
Send Email
      │
User Clicks Link
      │
Email Verified
```

Until verification:

```text
isVerified = false
```

---

# Should Users Be Allowed to Login Before Verification?

This depends on the application.

### Option 1 — Require Verification First

Used by:

- Banking
    
- Healthcare
    
- SaaS platforms
    

Safer.

---

### Option 2 — Allow Login With Limited Features

Used by:

- Some social media apps
    
- Some startups
    

Users can log in but must verify their email before accessing certain features.

Choose based on business requirements.

---

# Success Response

```http
201 Created
```

```json
{
    "success": true,
    "message": "Registration successful. Please verify your email.",
    "data": {
        "id": 21,
        "name": "Rahul",
        "email": "rahul@example.com"
    }
}
```

Notice:

No password.

No hash.

No verification token.

---

# Should Registration Return Tokens?

There are two common approaches.

### Option 1 — Return Tokens Immediately

```text
Register
      │
User Logged In
```

Common in:

- Small apps
    
- Consumer apps
    

---

### Option 2 — Require Email Verification

```text
Register
      │
Verify Email
      │
Login
      │
Receive Tokens
```

Common in:

- Professional SaaS
    
- Enterprise applications
    

Both are valid.

# Common Mistakes

## ❌ Storing Plain Passwords

Never do this.

```text
password = "secret123"
```

Always hash passwords.

---

## ❌ Returning Password Hash

Bad:

```json
{
    "passwordHash": "$2b$..."
}
```

Clients never need this.

---

## ❌ Trusting Client Role

Bad:

```json
{
    "role": "admin"
}
```

The server assigns roles.

---

## ❌ Skipping Duplicate Checks

Without checking email uniqueness:

```text
rahul@example.com
```

could register multiple times.

Use:

- Service validation
    
- Database unique constraint
    

---

## ❌ Weak Password Rules

Avoid accepting:

```text
12345
```

Enforce reasonable password requirements.

---

# Best Practices

- Use `POST /auth/register`.
    
- Validate input before processing.
    
- Check for duplicate email addresses.
    
- Hash passwords before storing them.
    
- Store only the password hash.
    
- Return `201 Created` after successful registration.
    
- Never expose sensitive information.
    
- Use email verification for applications where account ownership matters.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Registration|Creating a new user account|
|Password Hash|Secure representation of a password|
|Verification Token|Token used to verify email ownership|
|Duplicate Check|Ensures unique email or username|
|Email Verification|Confirms that the user owns the email address|

# Interview Questions

### 1. Why should passwords be hashed before storing them?

**Answer:**  
Hashing protects user passwords if the database is compromised. Unlike encryption, password hashes are designed to be one-way, making it computationally difficult to recover the original password.

---

### 2. Should the client send the user's role during registration?

**Answer:**  
No. Roles are server-controlled values. Allowing clients to choose their own roles could create serious security vulnerabilities.

---

### 3. Why should duplicate email checks exist in both the service layer and the database?

**Answer:**  
The service layer provides a clear business error message (such as "Email already exists"), while the database's unique constraint guarantees data integrity even if multiple requests occur simultaneously.

---

### 4. Should a registration API return authentication tokens?

**Answer:**  
It depends on the application's requirements. Some applications log users in immediately after registration, while others require email verification before issuing authentication tokens.

# 💡 Backend Engineering Insight

One of the biggest differences between a beginner project and a production system is **thinking about registration as a workflow instead of a database insert**.

A beginner often thinks:

```text
POST /register
      │
Save User
```

A professional thinks:

```text
Receive Request
      │
Validate Input
      │
Check Business Rules
      │
Hash Password
      │
Save User
      │
Generate Verification Token
      │
Send Email
      │
Return Response
```

This mindset helps you build systems that are secure, maintainable, and ready for real users—not just functional demos.
