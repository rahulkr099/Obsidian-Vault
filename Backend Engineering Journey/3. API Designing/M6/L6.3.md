# Why Login Is Different from Registration

Registration creates a user account.

```text
New User

↓

Create Account
```

Login verifies an existing account.

```text
Existing User

↓

Verify Identity

↓

Grant Access
```

The login API never creates a user—it only proves identity.

---

# Login Flow

A production login flow looks like this:

```text
User
   │
Enter Email & Password
   │
POST /auth/login
   │
Validate Request
   │
Find User
   │
Verify Password
   │
Check Account Status
   │
Generate Tokens
   │
Return Response
```

Every step must succeed before the user is authenticated.

---

# Step 1 — Endpoint Design

The standard endpoint is:

```http
POST /auth/login
```

Why `POST`?

Because credentials are sensitive and belong in the request body, not in the URL.

---

# Step 2 — Request Body

Example:

```json
{
    "email": "rahul@example.com",
    "password": "StrongPassword123"
}
```

Only the required credentials should be sent.

Do **not** send:

```json
{
    "email": "rahul@example.com",
    "password": "StrongPassword123",
    "role": "admin"
}
```

The server already knows the user's role.

---

# Step 3 — Controller Validation

The controller checks:

- Email is present
    
- Password is present
    
- Email format is valid
    

Example:

```json
{
    "email": "",
    "password": ""
}
```

Response:

```http
422 Unprocessable Entity
```

---

# Step 4 — Find User

The service searches:

```text
Email

↓

Database
```

If no user exists:

```http
401 Unauthorized
```

Notice:

Don't reveal whether:

- Email exists
    
- Password is wrong
    

Both should return the same generic error.

Example:

```json
{
    "success": false,
    "message": "Invalid email or password."
}
```

This prevents attackers from discovering registered email addresses.

---

# Step 5 — Verify Password

The stored password is a hash.

Database:

```text
$2b$12$...
```

Incoming password:

```text
StrongPassword123
```

The server compares:

```text
Password

↓

Hash Comparison

↓

Match?
```

If the comparison fails:

```http
401 Unauthorized
```

Never compare plaintext passwords.

---

# Step 6 — Check Account Status

Before issuing tokens, verify the account.

Examples:

```text
Is Email Verified?

Is Account Active?

Is Account Locked?

Is User Suspended?
```

If any check fails:

Return the appropriate response.

Example:

```http
403 Forbidden
```

```json
{
    "success": false,
    "message": "Please verify your email before logging in."
}
```

---

# Step 7 — Generate Tokens

If authentication succeeds:

Generate:

```text
Access Token

+

Refresh Token
```

We'll study token generation in Lesson 6.4.

For now, think of them as:

```text
Access Token

↓

Short-lived access
```

```text
Refresh Token

↓

Obtain new access tokens
```

---

# Step 8 — Return Response

Example:

```http
200 OK
```

```json
{
    "success": true,
    "message": "Login successful.",
    "data": {
        "user": {
            "id": 21,
            "name": "Rahul",
            "email": "rahul@example.com"
        },
        "accessToken": "..."
    }
}
```

The refresh token is commonly sent as a secure HTTP-only cookie:

```http
Set-Cookie:
refreshToken=...
```

---

# Should You Return the Entire User?

No.

Bad:

```json
{
    "passwordHash": "...",
    "__v": 0,
    "createdAt": "...",
    "updatedAt": "..."
}
```

Good:

```json
{
    "id": 21,
    "name": "Rahul",
    "email": "rahul@example.com"
}
```

Return only what the client needs.

# Remember Me

Many login forms include:

```text
☑ Remember Me
```

What does it usually affect?

Not the access token.

It often affects:

- Refresh token lifetime
    
- Session duration
    

Example:

Without Remember Me:

```text
Refresh Token

↓

7 Days
```

With Remember Me:

```text
Refresh Token

↓

30 Days
```

The exact values depend on business requirements.

# Failed Login Attempts

Suppose someone tries:

```text
Wrong Password

↓

Wrong Password

↓

Wrong Password

↓

100 Times
```

Production systems protect against brute-force attacks.

Common strategies:

- Rate limiting
    
- Temporary account lock
    
- CAPTCHA after repeated failures
    
- IP-based throttling

# Common Mistakes

## ❌ Returning Different Messages

Bad:

```text
Email not found.
```

Then:

```text
Wrong password.
```

This helps attackers determine whether an email address exists.

Use:

```text
Invalid email or password.
```

for both cases.

---

## ❌ Returning Password Hash

Never expose:

```json
{
    "passwordHash": "..."
}
```

---

## ❌ Skipping Account Status Checks

Authenticated doesn't always mean allowed.

Always verify:

- Active
    
- Verified
    
- Not locked
    
- Not suspended
    

---

## ❌ Storing Access Tokens in the Database

In a typical JWT-based stateless system, access tokens are **not** stored in the database. They are verified cryptographically.

Refresh tokens, however, are often stored (or represented by stored identifiers/hashes) so they can be revoked or rotated.

---

## ❌ Using GET for Login

Bad:

```http
GET /login?email=...
```

Credentials may appear in browser history, logs, or URLs.

Always use:

```http
POST /auth/login
```

---

# Best Practices

- Use `POST /auth/login`.
    
- Return a generic error for invalid credentials.
    
- Verify passwords using secure hash comparison.
    
- Check account status before issuing tokens.
    
- Return only the required user information.
    
- Send refresh tokens using secure HTTP-only cookies.
    
- Protect against brute-force attacks with rate limiting and account protection mechanisms.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Login|Verifying an existing user's identity|
|Credentials|Information used for authentication (such as email and password)|
|Password Verification|Comparing a plaintext password with its stored hash|
|Access Token|Short-lived credential for API access|
|Refresh Token|Credential used to obtain new access tokens|
|Remember Me|Option that typically extends session or refresh token lifetime|

# Interview Questions

### 1. Why should login APIs return a generic "Invalid email or password" message?

**Answer:**  
A generic message prevents attackers from determining whether a specific email address exists in the system, reducing the risk of user enumeration attacks.

---

### 2. Why should login use `POST` instead of `GET`?

**Answer:**  
Credentials are sensitive information. `POST` sends them in the request body, while `GET` places them in the URL, which can be logged, cached, or stored in browser history.

---

### 3. Should a login API return the user's password hash?

**Answer:**  
No. Password hashes are internal security data and must never be exposed to clients.

---

### 4. Why should account status be checked after password verification?

**Answer:**  
Even if credentials are correct, the account may be unverified, suspended, locked, or inactive. These checks ensure only eligible users receive authentication tokens.

# 💡 Backend Engineering Insight

A beginner often thinks of login as:

```text
Email
   │
Password
   │
Login Success
```

A production backend treats login as a **security workflow**:

```text
Validate Request
      │
Find User
      │
Verify Password
      │
Check Account Status
      │
Issue Tokens
      │
Return Safe Response
```

Every step exists to balance **security**, **usability**, and **performance**.

That's why login is one of the most carefully designed endpoints in any backend application.
