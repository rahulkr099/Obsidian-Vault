# The Problem

Imagine a login API returns one token:

```text
Access Token

↓

Valid for 1 year
```

If an attacker steals it:

```text
Attacker

↓

Uses Token

↓

Full Access

↓

For 1 Year
```

This is dangerous.

---

Now imagine:

```text
Access Token

↓

Expires in

15 Minutes
```

Much safer.

But...

What happens after 15 minutes?

The user would need to log in again.

That creates a poor user experience.

---

# The Solution

Modern applications use **two tokens**.

```text
Login

↓

Access Token

+

Refresh Token
```

Each has a different job.

---

# Access Token

Purpose:

Access protected APIs.

Example:

```http
GET /profile
```

Header:

```http
Authorization: Bearer <access-token>
```

Server verifies it.

If valid:

Return data.

---

# Refresh Token

Purpose:

Obtain a **new Access Token**.

It is **not** used for accessing normal APIs.

Instead:

```http
POST /auth/refresh
```

↓

New Access Token.

---

# Comparison

|Access Token|Refresh Token|
|---|---|
|Short-lived|Long-lived|
|Used for API requests|Used only to get new access tokens|
|Sent frequently|Sent rarely|
|Higher exposure|Better protected|
|Often expires in minutes|Often expires in days or weeks|

---

# Token Lifetimes

Example:

```text
Access Token

↓

15 Minutes
```

```text
Refresh Token

↓

30 Days
```

The exact lifetime depends on your application's security requirements.

---

# Login Flow

```text
User
   │

   │

   │

   │

```

```json

    "success": true,
    "data": {
        "accessToken": "...",
        "user": {
            "id": 21,
            "name": "Rahul"
        }
    }
}
```

Refresh Token:

Usually sent using:

```http
Set-Cookie:
refreshToken=...
```

# Accessing Protected APIs

Client requests:

```http
GET /profile
```

Header:

```http
Authorization: Bearer access-token
```

Server:

```text
Verify Token

↓

Return Profile
```

# What Happens When the Access Token Expires?

Timeline:

```text
Login

↓

Access Token

↓

15 Minutes

↓

Expired
```

Client tries:

```http
GET /profile
```

↓

```http
401 Unauthorized
```

Now the client uses the refresh token.

---

# Refresh Flow

Client:

```http
POST /auth/refresh
```

The refresh token is commonly sent automatically as a secure HTTP-only cookie by the browser.

Server:

```text
Verify Refresh Token

↓

Generate New Access Token

↓

Return New Access Token
```

Response:

```json
{
    "success": true,
    "data": {
        "accessToken": "new-token"
    }
}
```

The user continues using the application without logging in again.

---

# Refresh Endpoint

Standard endpoint:

```http
POST /auth/refresh
```

Purpose:

Issue a new Access Token.

Nothing else.

---

# Refresh Flow Diagram

```text
Access Token Expired
        │
POST /auth/refresh
        │
Verify Refresh Token
        │
Generate New Access Token
        │
Return New Token
```

---

# Why Not Use the Refresh Token Everywhere?

Suppose the refresh token is sent with every request.

If it's stolen:

```text
Attacker

↓

Generate New Tokens Forever
```

That's why refresh tokens should be:

- Used only for refresh requests.
    
- Protected carefully.
    
- Sent much less frequently than access tokens.
    

---

# Secure Cookie Design

Refresh tokens are commonly stored in cookies.

Example:

```http
Set-Cookie:
refreshToken=...
```

Important cookie settings:

```text
HttpOnly

Secure

SameSite
```

These reduce common attacks such as client-side script access and unintended cross-site requests.

---

# Logout Flow

Endpoint:

```http
POST /auth/logout
```

Purpose:

End authentication.

Depending on your implementation, the server may:

- Remove the stored refresh token (or mark it revoked).
    
- Clear the refresh token cookie.
    
- End the user's authenticated session.
    

Response:

```json
{
    "success": true,
    "message": "Logged out successfully."
}
```

---

# Logout Diagram

```text
POST /auth/logout
        │
Invalidate Refresh Token
        │
Clear Cookie
        │
Logout Complete
```

---

# What About the Access Token?

Access tokens are typically short-lived.

If a user logs out:

```text
Access Token

↓

Expires Soon
```

Since it expires quickly, many JWT-based systems don't explicitly revoke every access token.

The refresh token is what prevents obtaining new access tokens after logout.

---

# Token Rotation

Production systems often rotate refresh tokens.

Instead of:

```text
Refresh Token A

↓

Reuse Forever
```

They do:

```text
Refresh Token A

↓

Refresh

↓

Refresh Token B

↓

Refresh

↓

Refresh Token C
```

Each successful refresh invalidates the previous refresh token.

Benefits:

- Better security
    
- Limits damage if a refresh token is stolen
    

---

# Token Revocation

Suppose:

User changes password.

Existing refresh tokens should no longer work.

Server:

```text
Password Changed

↓

Revoke Refresh Tokens

↓

Require Login Again
```

Other common reasons to revoke refresh tokens:

- User logs out
    
- Suspicious activity
    
- Administrator disables the account

# Common Mistakes

## ❌ Long-Lived Access Tokens

Bad:

```text
Access Token

↓

365 Days
```

Short-lived access tokens reduce the impact if one is compromised.

---

## ❌ Returning Refresh Tokens in JavaScript-Accessible Storage

For browser-based applications, refresh tokens are commonly stored in secure, HTTP-only cookies rather than JavaScript-accessible storage such as `localStorage`.

---

## ❌ Using Refresh Tokens for Normal APIs

Bad:

```http
GET /profile
```

Header:

```text
Refresh Token
```

Use:

Access Token.

---

## ❌ Never Rotating Refresh Tokens

Rotation improves security.

Many production systems implement it.

---

## ❌ Forgetting Logout

Logout should prevent future refreshes by revoking or invalidating the refresh token.

---

# Best Practices

- Use short-lived access tokens.
    
- Use long-lived refresh tokens.
    
- Store refresh tokens in secure HTTP-only cookies for browser clients.
    
- Use `POST /auth/refresh`.
    
- Rotate refresh tokens when practical.
    
- Revoke refresh tokens on logout and other sensitive account events.
    
- Keep access and refresh token responsibilities separate.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Access Token|Short-lived token used to access protected APIs|
|Refresh Token|Long-lived token used to obtain new access tokens|
|Token Rotation|Replacing the refresh token with a new one after use|
|Token Revocation|Making a token unusable before its expiration|
|Secure Cookie|Cookie configured with security attributes such as `HttpOnly`, `Secure`, and `SameSite`|

# Interview Questions

### 1. Why do modern applications use both an access token and a refresh token?

**Answer:**  
Access tokens are short-lived to reduce the impact if they are compromised. Refresh tokens allow users to obtain new access tokens without logging in again, improving both security and user experience.

---

### 2. Why are refresh tokens commonly stored in HTTP-only cookies?

**Answer:**  
HTTP-only cookies are not accessible to JavaScript, which reduces the risk of refresh tokens being stolen through client-side script attacks. Cookie attributes such as `Secure` and `SameSite` provide additional protection.

---

### 3. What is token rotation?

**Answer:**  
Token rotation is the practice of issuing a new refresh token whenever one is used successfully and invalidating the old one. This limits the usefulness of a stolen refresh token.

---

### 4. Why is `POST /auth/refresh` used instead of sending the refresh token with every API request?

**Answer:**  
Refresh tokens are powerful credentials that should be exposed as little as possible. Restricting their use to the refresh endpoint reduces their exposure and limits the damage if they are compromised.

# 💡 Backend Engineering Insight

One of the biggest mindset shifts is understanding that **access tokens and refresh tokens serve different purposes**.

Think of them like this:

```text
Access Token
      │
Daily Entry Pass
      │
Expires Quickly
```

```text
Refresh Token
      │
Pass Office
      │
Issues New Entry Passes
```

You don't show your "pass office" credentials every time you enter a building—you use them only when you need a new entry pass.

Professional authentication systems follow the same idea:

- **Access Token** → Used frequently for protected APIs.
    
- **Refresh Token** → Used sparingly to obtain new access tokens.
    

Keeping those responsibilities separate is one of the foundations of secure token-based authentication.
