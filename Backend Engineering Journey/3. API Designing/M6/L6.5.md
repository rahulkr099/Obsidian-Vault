# Why These APIs Matter

Imagine a user:

```text
Forgot Password

↓

Cannot Login
```

Without a recovery system:

The account is effectively unusable.

Now imagine another user:

```text
Registers

↓

Mistypes Email

↓

Never Verifies Account
```

You need a secure way to verify email ownership.

These are two different workflows:

- Password Recovery
    
- Email Verification
    

---

# Password Reset Flow

A production password reset flow looks like this:

```text
Forgot Password
        │
POST /auth/forgot-password
        │
Generate Reset Token
        │
Send Email
        │
User Clicks Link
        │
POST /auth/reset-password
        │
Verify Token
        │
Hash New Password
        │
Save Password
        │
Revoke Existing Refresh Tokens
        │
Success
```

---

# Step 1 — Forgot Password

Endpoint:

```http
POST /auth/forgot-password
```

Request:

```json
{
    "email": "rahul@example.com"
}
```

---

# What Happens Internally?

Server:

```text
Find User

↓

Generate Reset Token

↓

Store Token (or its hash)

↓

Set Expiration

↓

Send Email
```

The user receives:

```text
https://example.com/reset-password?token=abc123
```

---

# Very Important Security Rule

Suppose:

Email exists.

Response:

```json
{
    "message": "Password reset email sent."
}
```

Now suppose:

Email doesn't exist.

Bad response:

```json
{
    "message": "Email not found."
}
```

An attacker can now discover which email addresses are registered.

Instead, always return the same response:

```json
{
    "success": true,
    "message": "If an account exists for this email, a password reset link has been sent."
}
```

This prevents **account enumeration**.

---

# Step 2 — Reset Password

Endpoint:

```http
POST /auth/reset-password
```

Request:

```json
{
    "token": "abc123",
    "newPassword": "StrongPassword123"
}
```

---

# Server Validation

The server checks:

```text
Token Exists?

↓

Not Expired?

↓

Not Already Used?

↓

Associated User Exists?
```

If everything is valid:

```text
Hash New Password

↓

Update Database

↓

Invalidate Token

↓

Revoke Existing Refresh Tokens
```

---

# Why Revoke Refresh Tokens?

Imagine:

Someone stole the user's refresh token.

The user changes their password.

If the old refresh token still works:

The attacker remains logged in.

Professional systems often revoke refresh tokens after a password change.

---

# Token Expiration

Reset tokens should expire.

Example:

```text
Generated

↓

15 Minutes

↓

Expired
```

Expired tokens should return:

```http
400 Bad Request
```

or

```http
410 Gone
```

depending on your API design.

Example:

```json
{
    "success": false,
    "message": "Password reset link has expired."
}
```

---

# One-Time Use Tokens

Password reset tokens should be usable only once.

Flow:

```text
Reset Token

↓

Used

↓

Deleted / Invalidated
```

Even if someone copies the link later:

It no longer works.

# Email Verification Flow

Registration:

```text

↓

↓

Send Email

↓

↓

↓

```

# Verification Endpoint

A common endpoint is:

```http
POST /auth/verify-email
```

Request:

```json
{
    "token": "verification-token"
}
```

Server:

```text
Verify Token

↓

Find User

↓

Set isVerified = true

↓

Invalidate Token

↓

Return Success
```

---

# Response

```json
{
    "success": true,
    "message": "Email verified successfully."
}
```

---

# Resend Verification Email

Sometimes users lose the email.

Endpoint:

```http
POST /auth/resend-verification
```

Request:

```json
{
    "email": "rahul@example.com"
}
```

Server:

```text
Generate New Token

↓

Invalidate Old Token

↓

Send New Email
```

---

# Verification Token Expiration

Example:

```text
Verification Token

↓

24 Hours

↓

Expired
```

User requests:

```http
POST /auth/resend-verification
```

↓

New token.

---

# Password Reset vs Email Verification

|Password Reset|Email Verification|
|---|---|
|Recover account access|Confirm email ownership|
|Changes password|Activates account|
|Usually shorter expiration|Often longer expiration|
|Used after login problems|Used after registration|
|Revokes existing sessions/tokens (often)|Usually doesn't affect sessions|

# Token Storage

Should you store the raw reset token?

Production systems often:

```text
Generate Token

↓

Hash Token

↓

Store Hash

↓

Email Original Token
```

When the user returns the token:

```text
Incoming Token

↓

Hash It

↓

Compare With Stored Hash
```

This protects users if the database is compromised.

# Common Mistakes

## ❌ Revealing Email Existence

Bad:

```json
{
    "message": "Email not found."
}
```

Good:

```json
{
    "message": "If an account exists, instructions have been sent."
}
```

---

## ❌ Never Expiring Tokens

Bad:

```text
Reset Token

↓

Valid Forever
```

Always set an expiration.

---

## ❌ Allowing Token Reuse

Bad:

```text
Reset Password

↓

Same Token Still Works
```

Always invalidate used tokens.

---

## ❌ Storing Plain Reset Tokens

Store a hash of the token when practical.

---

## ❌ Not Revoking Refresh Tokens After Password Change

Users expect changing their password to protect their account.

Revoking refresh tokens helps achieve that.

---

# Best Practices

- Use `POST /auth/forgot-password`.
    
- Use `POST /auth/reset-password`.
    
- Use `POST /auth/verify-email`.
    
- Use `POST /auth/resend-verification`.
    
- Return generic responses for email-based recovery requests.
    
- Set expiration times for tokens.
    
- Make tokens one-time use.
    
- Hash passwords before saving.
    
- Revoke refresh tokens after password changes.
    
- Invalidate old verification tokens when generating new ones.
    

---

# Key Terms

|Term|Meaning|
|---|---|
|Reset Token|Temporary token used to reset a password|
|Verification Token|Token used to confirm email ownership|
|Token Expiration|Time after which a token becomes invalid|
|One-Time Token|Token that can only be used once|
|Account Enumeration|Discovering whether an account exists by observing API responses|

# Interview Questions

### 1. Why should password reset endpoints return the same response whether the email exists or not?

**Answer:**  
To prevent account enumeration attacks. Returning a generic response stops attackers from discovering which email addresses are registered.

---

### 2. Why should password reset tokens expire?

**Answer:**  
Short expiration times reduce the risk that a stolen or leaked token can be used to take over an account.

---

### 3. Why should password reset tokens be one-time use?

**Answer:**  
Once a password has been changed, the reset token should no longer be valid. This prevents the same token from being reused to reset the password again.

---

### 4. Why should refresh tokens often be revoked after a password change?

**Answer:**  
If a refresh token has been stolen, revoking it prevents an attacker from continuing to obtain new access tokens after the legitimate user changes their password.

# 💡 Backend Engineering Insight

A beginner often thinks:

```text
Forgot Password

↓

Change Password
```

A production backend thinks:

```text
Forgot Password
      │
Generate Secure Token
      │
Store Token (or Hash)
      │
Set Expiration
      │
Email User
      │
Verify Token
      │
Hash New Password
      │
Revoke Refresh Tokens
      │
Invalidate Reset Token
      │
Success
```

Every step protects the user from a different security risk.

That's why password recovery is considered a **security workflow**, not just a database update.
