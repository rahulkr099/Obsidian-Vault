# Authentication vs Authorization

Remember:

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

Example:

```text
Rahul

↓

Logs In

↓

Authenticated
```

Now Rahul requests:

```http
DELETE /users/25
```

Should this be allowed?

Authentication cannot answer that.

Authorization can.

---

# Authentication Flow

```text
User

↓

Login

↓

Authenticated

↓

Requests Resource

↓

Authorization Check

↓

Allowed?

↓

Yes / No
```

Notice:

Authorization happens **after** authentication.

# Identity Isn't Permission

Suppose:

```text
User ID = 21
```

This tells us:

Who the user is.

Now:

```text
Role = Admin
```

This tells us:

What the user can do.

Identity ≠ Permission.

# Permission-Based Authorization

Instead of roles,

permissions are assigned directly.

Example:

```text

```


```text

```

# Ownership-Based Authorization

One of the most common authorization rules.

Example:

```http
PATCH /posts/15
```

Question:

Who owns Post 15?

Suppose:

```text

```

Logged-in user:

```text
User 21
```

Allowed.

---

Now:

Logged-in user:

```text
User 33
```

Not allowed.

Return:

```http
403 Forbidden
```

# Common Mistakes

## ❌ Authorization in the Frontend Only

Never rely on:

```javascript
if (user.role === "admin") {
    showDeleteButton();
}
```

The backend **must** enforce authorization.

The frontend only improves the user experience.

---

## ❌ Checking Only Authentication

Bad:

```text
Logged In?

↓

Yes

↓

Delete Anyone's Data
```

Authentication alone is not enough.

---

## ❌ Hardcoding Roles Everywhere

Bad:

```javascript
if (role === "admin")
```

Repeated across dozens of files.

Centralize authorization logic.

---

## ❌ Returning 404 Instead of 403 Without a Reason

Use:

```http
403 Forbidden
```

when the user is authenticated but lacks permission.

Some high-security systems intentionally return `404 Not Found` to avoid revealing that a resource exists, but this should be a deliberate design decision.

---

## ❌ Trusting Client-Supplied User IDs

Bad:

```json
{
    "userId": 21
}
```

The authenticated user's identity should come from the verified authentication context (for example, the validated token), not from client input.

---

# Best Practices

- Authenticate before authorizing.
    
- Keep authorization logic in the service layer or dedicated authorization components.
    
- Use RBAC for common role-based permissions.
    
- Use ownership checks for user-owned resources.
    
- Protect sensitive endpoints.
    
- Never trust the frontend for authorization.
    
- Return `403 Forbidden` for permission failures.

# Interview Questions

### 1. What is the difference between RBAC and ownership-based authorization?

**Answer:**  
RBAC grants permissions based on a user's role, such as Admin or Moderator. Ownership-based authorization allows actions based on whether the authenticated user owns the resource, such as editing their own post.

---

### 2. Why shouldn't authorization rely on the frontend?

**Answer:**  
Frontend checks can be bypassed. Only backend authorization can reliably enforce access control because every request must be validated on the server.

---

### 3. Why should authentication happen before authorization?

**Answer:**  
Authorization decisions depend on knowing who the user is. Without authentication, the server has no trusted identity on which to base permission checks.

---

### 4. Where should authorization logic typically live?

**Answer:**  
Business-specific authorization checks typically belong in the service layer or a dedicated authorization component, where they can be reused consistently across controllers while keeping controllers focused on request handling.

# 💡 Backend Engineering Insight

One of the biggest differences between beginner and production systems is **how authorization is modeled**.

A beginner often thinks:

```text
Login
   │
Delete Everything
```

A production backend thinks:

```text
Authenticate User
      │
Load Resource
      │
Check Role
      │
Check Ownership
      │
Check Business Rules
      │
Allow or Reject
```

Notice that authorization is **not just checking a role**.

Professional systems often combine:

- **Authentication** → Who is making the request?
    
- **Role checks** → Does their role permit this action?
    
- **Ownership checks** → Do they own this resource?
    
- **Business rules** → Is the action allowed under current conditions?
    

For example, in your **URL Shortener** project, a user may be authenticated, but they should only be able to update or delete **their own shortened URLs**. That's a classic ownership-based authorization rule.
