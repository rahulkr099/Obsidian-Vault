# Security Is a Layered System

Authentication isn't secure because you use JWT or sessions.

It's secure because **multiple security layers** work together.

```text
User
   │
HTTPS
   │
Authentication
   │
Authorization
   │
Secure Cookies
   │
Rate Limiting
   │
Password Hashing
   │
CSRF Protection
   │
Session Management
```

Every layer protects against different threats.

---

# HTTPS

The first security layer.

Without HTTPS:

```text
Browser

↓

Internet

↓

Server
```

Traffic can potentially be intercepted or modified by attackers on the network.

With HTTPS:

```text
Browser

↓

Encrypted Connection

↓

Server
```

Credentials and tokens are encrypted while in transit.

---

# Never Send Tokens Over HTTP

Bad:

```text
http://example.com
```

Good:

```text
https://example.com
```

Production authentication should always use HTTPS.

---

# Password Hashing

Never store:

```text
password = "secret123"
```

Instead:

```text
Password

↓

Hash Function
(bcrypt / Argon2)

↓

Password Hash
```

Database:

```text
$2b$12$...
```

If the database is leaked, attackers don't immediately obtain users' original passwords.

---

# Why Hashing Instead of Encryption?

Encryption:

```text
Encrypt

↓

Decrypt
```

Hashes:

```text
Password

↓

Hash

↓

No Practical Reverse Operation
```

Authentication compares hashes rather than recovering passwords.

---

# Cookie Security

Refresh tokens are commonly stored in cookies.

Production cookies often use:

```text
HttpOnly

Secure

SameSite
```

Each serves a different purpose.

---

# HttpOnly

Without HttpOnly:

```javascript
document.cookie
```

JavaScript can read cookies.

With HttpOnly:

JavaScript cannot access the cookie.

This helps reduce the impact of many XSS attacks.

---

# Secure Cookie

Example:

```text
Secure = true
```

Meaning:

The cookie is sent only over HTTPS.

Never over HTTP.

---

# SameSite

Helps reduce CSRF attacks.

Common values:

```text
Strict

Lax

None
```

General idea:

- **Strict** – Cookie sent only in same-site requests.
    
- **Lax** – Allows some top-level navigation while protecting many cross-site requests.
    
- **None** – Cookie is sent in cross-site requests and must also use `Secure`.
    

Choose based on your application's needs.

---

# CSRF (Cross-Site Request Forgery)

Imagine:

User logs into:

```text
bank.com
```

Their browser stores an authentication cookie.

Now they visit:

```text
evil.com
```

That malicious site tries to submit a request to the bank.

CSRF protections help ensure that requests really originate from your application.

Common defenses include:

- `SameSite` cookies
    
- CSRF tokens (especially for cookie-based auth)
    
- Checking `Origin` or `Referer` headers where appropriate
    

---

# XSS (Cross-Site Scripting)

Imagine:

A malicious script runs inside your page.

If tokens are stored in JavaScript-accessible storage:

```javascript
localStorage.getItem("token")
```

The script may be able to read them.

That's one reason refresh tokens are commonly stored in HTTP-only cookies.

---

# Rate Limiting

Suppose someone tries:

```text
Login

↓

1,000 Requests Per Minute
```

Your login endpoint should not allow unlimited attempts.

Example policy:

```text
5 Login Attempts

↓

1 Minute

↓

Temporarily Block
```

Rate limiting reduces brute-force attacks and abuse.

---

# Brute-Force Protection

Attack:

```text
Password1

Password2

Password3

...
```

Production defenses include:

- Rate limiting
    
- Temporary delays
    
- CAPTCHA after repeated failures
    
- IP throttling
    
- Device-based detection
    

---

# Account Lockout

Example:

```text
5 Failed Logins

↓

Lock Account

↓

15 Minutes
```

Benefits:

Reduces automated guessing.

Be careful not to make lockout easy to abuse against legitimate users.

---

# Session Expiration

No session should last forever.

Example:

```text
Access Token

↓

15 Minutes
```

Refresh Token:

```text
30 Days
```

Inactive sessions should eventually expire.

---

# Logout from All Devices

Example:

Rahul logs in:

```text
Laptop

Phone

Tablet
```

Changes password.

Professional systems often invalidate refresh tokens across all devices, requiring each device to authenticate again.

---

# Device Sessions

Many applications show:

```text
Active Sessions

Laptop

Phone

Tablet
```

Users can choose:

```text
Logout

Phone
```

Without affecting:

```text
Laptop
```

This requires tracking refresh tokens or sessions per device.

---

# Logging Security Events

Useful events to log:

```text
Successful Login

Failed Login

Password Reset

Email Changed

Password Changed

Logout

New Device Login
```

Logs help detect suspicious activity and assist investigations.

Avoid logging sensitive values such as passwords or raw tokens.

---

# Authentication Middleware

Instead of repeating authentication logic:

Bad:

```text
Controller A

↓

Verify Token
```

Controller B:

```text
Verify Token
```

Professional systems use reusable middleware.

```text
Request

↓

Authentication Middleware

↓

Controller
```

One implementation.

Many endpoints.

---

# Security Headers

Many applications also return security-related HTTP headers.

Examples:

```text
Content-Security-Policy

X-Content-Type-Options

Referrer-Policy

Permissions-Policy
```

Frameworks like Helmet can help configure many of these in Node.js.

---

# Sensitive Data

Never expose:

```json
{
    "passwordHash":"...",
    "refreshToken":"...",
    "verificationToken":"..."
}
```

Responses should contain only what the client actually needs.

---

# Security Flow

```text
Login Request
      │
HTTPS
      │
Validate Input
      │
Verify Password
      │
Generate Tokens
      │
Set Secure Cookie
      │
Return Access Token
```

Every step contributes to security.

# Common Mistakes

## ❌ Storing Plain Passwords

Never.

Always hash passwords using a strong password hashing algorithm such as bcrypt or Argon2.

---

## ❌ Long-Lived Access Tokens

Bad:

```text
Access Token

↓

1 Year
```

Use short-lived access tokens.

---

## ❌ No Rate Limiting

Login endpoints should always have abuse protection.

---

## ❌ Sending Tokens Over HTTP

Always use HTTPS in production.

---

## ❌ Returning Sensitive Information

Never expose:

- Password hashes
    
- Reset tokens
    
- Verification tokens
    
- Refresh tokens in API responses (for browser-based apps)
    

---

## ❌ Logging Passwords

Bad:

```text
Login:

Password = secret123
```

Never log:

- Passwords
    
- Raw access tokens
    
- Raw refresh tokens
    

---

# Best Practices

- Always use HTTPS.
    
- Hash passwords with bcrypt or Argon2.
    
- Store refresh tokens in HTTP-only secure cookies for browser clients.
    
- Use `Secure` and appropriate `SameSite` cookie attributes.
    
- Rate-limit authentication endpoints.
    
- Protect against brute-force attacks.
    
- Set reasonable session and token expiration times.
    
- Support logout and logout-from-all-devices.
    
- Log security events, not secrets.
    
- Apply security as multiple layers, not a single feature.
    

---

# Security Checklist

Before deploying an authentication system:

✅ HTTPS enabled

✅ Passwords hashed

✅ Access tokens short-lived

✅ Refresh tokens protected

✅ Cookies use `HttpOnly`

✅ Cookies use `Secure`

✅ Appropriate `SameSite` setting

✅ Login rate limiting

✅ Password reset available

✅ Email verification available

✅ Refresh token revocation implemented

✅ Sensitive data excluded from responses

# Key Terms

|Term|Meaning|
|---|---|
|HTTPS|Encrypted communication between client and server|
|HttpOnly Cookie|Cookie inaccessible to JavaScript|
|Secure Cookie|Cookie sent only over HTTPS|
|SameSite|Cookie attribute that controls cross-site sending behavior|
|CSRF|Attack that tricks a browser into sending unwanted authenticated requests|
|XSS|Attack where malicious scripts run in a trusted web page|
|Rate Limiting|Restricting request frequency|
|Brute Force|Repeated password guessing attack|
|Session Expiration|Automatic ending of authentication after a period of time|

# Interview Questions

### 1. Why should refresh tokens be stored in HTTP-only cookies?

**Answer:**  
HTTP-only cookies prevent JavaScript from reading the refresh token, reducing the impact of client-side script attacks. Combined with `Secure` and appropriate `SameSite` settings, they provide stronger protection for browser-based applications.

---

### 2. Why are short-lived access tokens considered more secure?

**Answer:**  
If an access token is compromised, its usefulness is limited by its short lifetime. This reduces the window during which an attacker can use it.

---

### 3. What is the purpose of rate limiting on login endpoints?

**Answer:**  
Rate limiting helps protect against brute-force attacks, credential stuffing, and other forms of abuse by limiting how frequently authentication requests can be made.

---

### 4. Why should passwords be hashed instead of encrypted?

**Answer:**  
Password hashing is a one-way process designed for password storage. Authentication works by comparing hashes rather than decrypting passwords, so the original password does not need to be recoverable.

# 💡 Backend Engineering Insight

Many beginners think security is a single feature:

```text
JWT

↓

Secure
```

Professional backend engineers think in **layers**:

```text
HTTPS
   │
Input Validation
   │
Password Hashing
   │
Authentication
   │
Authorization
   │
Secure Cookies
   │
Rate Limiting
   │
CSRF Protection
   │
Logging
```

If one layer fails, the others still provide protection.

This is known as **defense in depth**, and it's one of the core principles behind production security architectures.
