# The Authentication Design Process

Professional backend engineers don't start with JWT or cookies.

They start with business questions.

```text
Requirements
      │
      ▼
Who are the users?
      │
      ▼
What resources are protected?
      │
      ▼
Authentication Flow
      │
      ▼
Authorization Rules
      │
      ▼
Token Strategy
      │
      ▼
Security Measures
```

Technology comes **after** design.

# Choosing an Authentication Strategy

Not every application needs the same approach.

|Application|Recommended Strategy|
|---|---|
|Blog|JWT + Refresh Token|
|Todo App|JWT + Refresh Token|
|URL Shortener Dashboard|JWT + Refresh Token|
|E-commerce|JWT + Refresh Token + RBAC|
|LMS|JWT + Refresh Token + RBAC|
|Banking|Short-lived tokens, strict security, MFA (often)|

Authentication depends on business requirements, not trends.

# Common Design Mistakes

## ❌ Designing Authentication First

Start with:

```text
Requirements

↓

Users

↓

Resources

↓

Authentication
```

---

## ❌ Giving Every User Admin Rights

Always define roles explicitly.

---

## ❌ Forgetting Ownership Checks

Logged-in users should not automatically access all data.

---

## ❌ Returning Sensitive Information

Never expose:

- Password hashes
    
- Reset tokens
    
- Verification tokens
    
- Internal security data
    

---

## ❌ Mixing Authentication and Authorization

Authentication:

```text
Who?
```

Authorization:

```text
Can they?
```

Keep them separate.

---

# Best Practices

- Design authentication from business requirements.
    
- Keep authentication and authorization separate.
    
- Protect sensitive endpoints.
    
- Use ownership checks whenever resources belong to users.
    
- Apply RBAC where multiple roles exist.
    
- Keep access tokens short-lived.
    
- Protect refresh tokens.
    
- Build authentication as a complete lifecycle.

# Interview Questions

### 1. How would authentication differ between a Blog application and an E-commerce application?

**Answer:**  
A Blog application typically needs simple authentication with ownership-based authorization. An E-commerce application often requires multiple user roles (customer, seller, admin), more complex authorization rules, and additional security around orders, payments, and product management.

---

### 2. Why should authentication be designed from business requirements instead of starting with JWT?

**Answer:**  
JWT is an implementation choice, not a business requirement. Understanding who the users are, what resources they need, and how they interact with the system leads to better authentication and authorization decisions.

---

### 3. When should you use ownership-based authorization?

**Answer:**  
Ownership-based authorization is appropriate when resources belong to individual users, such as blog posts, todo items, shortened URLs, or personal orders.

---

### 4. What are the essential authentication endpoints in a production API?

**Answer:**  
A typical production authentication API includes:

- `POST /auth/register`
    
- `POST /auth/login`
    
- `POST /auth/logout`
    
- `POST /auth/refresh`
    
- `POST /auth/forgot-password`
    
- `POST /auth/reset-password`
    
- `POST /auth/verify-email`
    
- `POST /auth/resend-verification`

# 💡 Backend Engineering Insight

One of the biggest mindset shifts is moving from **technology-first** thinking to **system-first** thinking.

A beginner often says:

```text
I'll use JWT.
```

A backend engineer says:

```text
Who are the users?

↓

What can they access?

↓

How long should sessions last?

↓

What happens if a password is stolen?

↓

How do users recover their account?

↓

Which authentication strategy best fits these requirements?
```

Notice that **JWT, cookies, sessions, or OAuth are implementation details**. The real design begins with understanding the application's business needs and security requirements.
