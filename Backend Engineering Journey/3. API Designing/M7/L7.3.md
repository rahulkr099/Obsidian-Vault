# Lesson 7.3 — Unit Testing

> **Goal:** Learn how to test individual pieces of your backend code in isolation, so you can verify your business logic quickly and confidently.

By the end of this lesson, you will be able to:

---

# What is a Unit Test?

A **unit** is the smallest testable part of your application.

Examples:

- A function
    
- A method
    
- A class
    
- A utility
    

A **unit test** checks whether that single unit behaves correctly.

Example:

```javascript
function add(a, b) {
    return a + b;
}
```

Test:

```javascript
expect(add(2, 3)).toBe(5);
```

Simple, fast, and isolated.

---

# Why Unit Testing Matters

Imagine this function:

```javascript
function calculateDiscount(price) {
    return price * 0.9;
}
```

It works today.

Tomorrow someone changes it:

```javascript
return price * 0.8;
```

Suddenly every order gets a 20% discount.

A unit test catches this immediately.

---

# Unit Testing Philosophy

A unit test answers one question:

> **"Does this piece of code behave correctly?"**

Nothing more.

Nothing less.

---

# Characteristics of a Good Unit Test

A good unit test is:

- Fast
    
- Independent
    
- Repeatable
    
- Easy to read
    
- Easy to maintain
    

If a test depends on a database or internet connection, it is **not** a true unit test.

---

# What Should Be Unit Tested?

Good candidates:

✅ Validation functions

```javascript
validateEmail()
```

---

✅ Password strength

```javascript
isStrongPassword()
```

---

✅ Price calculation

```javascript
calculateTotal()
```

---

✅ Slug generation

```javascript
generateSlug()
```

---

✅ JWT utility

```javascript
createAccessToken()
```

---

✅ Pagination logic

```javascript
getPagination()
```

---

# What Should NOT Be Unit Tested?

Avoid testing:

❌ MongoDB

❌ Express routing

❌ Network requests

❌ External APIs

❌ File systems

These belong to integration or end-to-end tests.

# Anatomy of a Test

Example:

```javascript
test("adds two numbers", () => {
    expect(add(2, 3)).toBe(5);
});
```

Three parts:

```text
Test Name

↓

Execute Function

↓

Verify Result
```

---

# AAA Pattern

Professional developers often follow:

```text
Arrange

↓

Act

↓

Assert
```

---

Example:

```javascript
// Arrange
const price = 100;

// Act
const result = calculateDiscount(price);

// Assert
expect(result).toBe(90);
```

This structure makes tests easier to understand.

---

# Testing Business Logic

Suppose:

```javascript
function canVote(age) {
    return age >= 18;
}
```

Tests:

```javascript
expect(canVote(20)).toBe(true);

expect(canVote(10)).toBe(false);
```

Test different scenarios, not just one.

---

# Testing Edge Cases

Many bugs hide at the boundaries.

Example:

```javascript
canVote(18)
```

Should return:

```text
true
```

Also test:

```text
17

18

19

0

-1

100
```

These are edge cases.

---

# Testing Exceptions

Example:

```javascript
function divide(a, b) {
    if (b === 0)
        throw new Error("Division by zero");

    return a / b;
}
```

Test:

```text
Input

↓

10, 0

↓

Error Expected
```

Good unit tests verify both successful results and expected failures.

---

# Mocking

Real applications depend on:

- MongoDB
    
- Redis
    
- Email service
    
- Payment gateway
    

Unit tests should **not** call them.

Instead, use a **mock**.

---

Real world:

```text
UserService

↓

MongoDB
```

Unit testing:

```text
UserService

↓

Fake MongoDB (Mock)
```

Now the test is:

- Faster
    
- More reliable
    
- Independent
    

---

# Example

Without mocking:

```text
Create User

↓

Save to MongoDB
```

Problem:

- Slow
    
- Needs database
    
- Can fail due to network
    

---

With mocking:

```text
Create User

↓

Pretend database saved user

↓

Continue testing
```

You only verify your business logic.

---

# Why Mock?

Imagine testing:

```text
Send Welcome Email
```

Do you really want 500 test emails sent?

Of course not.

Mock the email service.

---

# Mock Example (Concept)

```text
Email Service

↓

Real Email ❌

↓

Fake Email ✅
```

The fake service records:

```text
Was sendEmail() called?

How many times?

With which arguments?
```

---

# Test Naming

Poor:

```text
Test 1
```

Good:

```text
should_return_404_when_user_not_found
```

Even better:

```text
should_create_user_when_input_is_valid
```

A test name should describe the expected behavior.

---

# Independent Tests

Bad:

```text
Test A

creates user

↓

Test B

depends on Test A
```

If Test A fails, Test B also fails.

Good tests never depend on each other.

---

# Deterministic Tests

A test should produce the same result every time.

Bad:

```javascript
expect(random()).toBe(5);
```

Tomorrow it may return 8.

Instead, mock randomness or control the input.

---

# Fast Tests

A unit test should finish in milliseconds.

If one test takes several seconds, investigate why.

A suite of hundreds of unit tests should still run quickly.

---

# Common Beginner Mistakes

❌ Testing multiple functions in one test

Instead:

One behavior per test.

---

❌ Writing huge tests

Instead:

Keep them short and focused.

---

❌ Depending on databases

Instead:

Mock external dependencies.

---

❌ Ignoring edge cases

Instead:

Test:

- Minimum values
    
- Maximum values
    
- Empty strings
    
- Invalid inputs
    
- Null values
    
- Undefined values
    

---

❌ Writing unreadable test names

Instead:

Describe the expected behavior clearly.

---

# Professional Workflow

```text
Write Function

↓

Write Unit Tests

↓

Run Tests

↓

Fix Bugs

↓

Commit Code
```

Many developers even follow **Test-Driven Development (TDD)**, where they write the test before the implementation. While not every team uses TDD strictly, understanding the approach is valuable.

---

# Best Practices

✅ Test one behavior per test.

✅ Follow the Arrange–Act–Assert pattern.

✅ Mock databases and external services.

✅ Test both valid and invalid inputs.

✅ Cover edge cases.

✅ Keep tests fast and independent.

✅ Use clear, descriptive test names.

# Real Backend Example

Consider a `UserService` method:

```text
createUser()

↓

Validate email

↓

Hash password

↓

Save user

↓

Return response
```

A good unit test would **mock the repository**, then verify:

- Validation runs correctly.
    
- Password hashing is called.
    
- The repository is asked to save the user.
    
- The returned object has the expected values.
    

Notice that no real database is involved. You're testing the service's business logic, not MongoDB.

---

# Key Takeaways

- A unit test verifies one small piece of code in isolation.
    
- Unit tests should be fast, deterministic, and independent.
    
- Business logic is the primary target for unit testing.
    
- Mock external systems like databases, email providers, and payment gateways.
    
- Test success cases, failure cases, and edge cases.
    
- Clear test names and the Arrange–Act–Assert pattern make tests easier to maintain.
