# Lesson 7.4 — Integration Testing

> **Goal:** Learn how to test multiple components of your backend working together to ensure your API behaves correctly as a complete system.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand what integration testing is

- Test controllers, services, repositories, and databases together
    
- Test authentication and middleware
    
- Understand test databases
    
- Write maintainable integration tests
    

---

# What is Integration Testing?

A unit test checks **one component**.

An integration test checks **multiple components working together**.

Imagine this API:

```http
POST /api/v1/users
```

When a request comes in, many parts work together:

```text
Request

↓

Express Router

↓

Middleware

↓

Controller

↓

Service

↓

Repository

↓

MongoDB

↓

Response
```

An integration test verifies that **this entire flow works correctly**.

---

# Why Integration Testing?

Suppose every unit test passes.

But...

The controller sends the wrong data to the service.

The service calls the wrong repository function.

The repository saves incorrect fields.

Your unit tests may still pass because each component was tested separately.

Integration testing catches these problems.

---

# Real Example

Imagine:

```text
UserController

↓

UserService

↓

UserRepository

↓

MongoDB
```

A unit test checks each box individually.

An integration test checks the **whole pipeline**.

---

# Unit Test vs Integration Test

|Unit Test|Integration Test|
|---|---|
|Tests one function|Tests multiple components|
|Very fast|Slightly slower|
|Uses mocks|Uses real components|
|No database|Usually test database|
|Isolated|Connected system|

# Example Flow

Suppose the user registers.

Request:

```http
POST /register
```

Body:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "password": "secret123"

```

The integration test verifies:

- Validation works
    
- Controller receives request
    
- Service hashes password
    
- Repository saves user
    
- Database stores record
    
- Response is `201 Created`
    

Everything should work together.

# Test Database

Never use production data.

Instead:

```
Production DB ❌

↓

Test DB ✅
```

The test database should:

- Start empty
    
- Be safe to modify
    
- Be recreated for each test run
    

---

# Why a Separate Database?

Imagine your integration test deletes a user.

Using production:

```
DELETE /users/5
```

Congratulations...

You just deleted a real customer.

Always isolate test data.

---

# Test Lifecycle

Professional integration tests usually follow this pattern:

```text
Before Tests

↓

Create Test Database

↓

Run Tests

↓

Clean Database

↓

Close Connections
```

This keeps every test run consistent.

# Testing Validation

Example request:

```json
{
    "email": "invalid"
}
```

Expected:

```
400 Bad Request
```

```

```

# External Services

Suppose registration sends:

- Welcome email
    
- SMS
    
- Analytics event
    

Should your integration test call the real services?

Usually **no**.

Instead:

```

↓
```

---

# Error Handling

Suppose the database is unavailable.

Expected:

```
500 Internal Server Error
```

Or a custom error response.

Your application should fail gracefully.

---

# Test Isolation

Bad:

```
Test A

creates user

↓

Test B

depends on Test A
```

Good:

Each test prepares its own data and cleans up afterward.

No test should depend on another.

---

# Common Beginner Mistakes

❌ Using production database

Instead:

Use a dedicated test database.

---

❌ Assuming only the response matters

Instead:

Verify the database state too.

---

❌ Writing one huge integration test

Instead:

Write smaller tests, each focused on one behavior.

---

❌ Ignoring failure cases

Instead:

Test:

- Invalid data
    
- Unauthorized users
    
- Missing records
    
- Duplicate resources
    
- Server errors

# Integration Testing Tools

Common tools in the Node.js ecosystem:

- **Supertest** – Sends HTTP requests directly to your Express application without opening a real network port.
    
- **Jest** or **Vitest** – Test runners and assertion libraries.
    
- **MongoDB Memory Server** – Creates an in-memory MongoDB instance for fast, isolated tests.
    
- **Testcontainers** – Starts real Docker containers (MongoDB, PostgreSQL, Redis, etc.) for testing, giving behavior closer to production.

# Real Backend Example

Suppose your architecture is:

```text
Route

↓

Auth Middleware

↓

Controller

↓

Service

↓

Repository

↓

MongoDB
```

An integration test for `POST /login` should verify:

- Invalid credentials return `401 Unauthorized`.
    
- Valid credentials return `200 OK`.
    
- The response includes a valid access token.
    
- Refresh tokens (if used) are stored correctly.
    
- The user record remains consistent in the database.
    

This confirms that multiple layers of your application work together correctly.

---

# Best Practices

✅ Use a separate test database.

✅ Test complete request flows.

✅ Verify both API responses and database changes.

✅ Test authentication and authorization.

✅ Keep tests independent.

✅ Mock external services such as email and payment providers.

✅ Clean up test data after every test.

---

# Key Takeaways

- Integration tests verify that multiple application components work together correctly.
    
- They test the complete request flow—from routing and middleware to the database and response.
    
- A dedicated test database is essential for safe and repeatable testing.
    
- Verify both the API response and the resulting database state.
    
- Mock external services while using real application components where appropriate.
    
- Integration tests complement unit tests by catching issues that arise when components interact.
