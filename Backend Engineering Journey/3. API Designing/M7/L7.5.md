# Lesson 7.5 — End-to-End (E2E) Testing

> **Goal:** Learn how to test your application exactly as a real user or client would use it, ensuring the entire system works correctly from start to finish.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand what End-to-End (E2E) testing is
    
- Differentiate E2E testing from Unit and Integration testing
    
- Design complete user journey tests
    
- Know what should be covered in E2E tests
    
- Understand common E2E testing tools
    
- Follow industry best practices

# What is End-to-End Testing?

Imagine a real user opens your application.

They:

- Register
    
- Login
    
- Create a post
    
- Edit it
    
- Delete it
    
- Logout
    

An **End-to-End (E2E) test** verifies that this entire journey works correctly.

It doesn't test just one function or one API.

It tests the **entire application**.

---

# Real Example

Consider a blogging platform.

A user's journey looks like this:

```text
Open Website

↓

Register

↓

Verify Email

↓

Login

↓

Create Blog

↓

Edit Blog

↓

Delete Blog

↓

Logout
```

An E2E test automates this whole sequence.

---

# Why E2E Testing Matters

Suppose:

- Registration works
    
- Login works
    
- Create Post works
    

Individually, everything passes.

But after login:

```text
JWT isn't saved correctly.
```

Now users cannot create posts.

Unit tests won't catch it.

Integration tests may not catch it.

An E2E test almost certainly will.

---

# Testing Levels

```text

↓

Integration

↓
```

---

# Comparison

|Unit|Integration|E2E|
|---|---|---|
|One function|Multiple components|Entire application|
|Fast|Medium|Slow|
|Uses mocks|Partial mocks|Minimal mocks|
|Developer-focused|Backend-focused|User-focused|

# When Should E2E Tests Run?

Usually:

```text

↓

↓

Run Unit Tests

```

---

# Why Not Write Hundreds of E2E Tests?

Because they are:

- Slow
    
- Expensive
    
- Hard to maintain
    

Remember the testing pyramid:

```text
        E2E
         ▲
    Integration
         ▲
      Unit Tests
```

Most tests should still be unit tests.

Only critical user journeys should be covered by E2E tests.

---

# Common Beginner Mistakes

❌ Writing E2E tests for every function

Instead:

Test complete business workflows.

---

❌ Ignoring failure scenarios

Instead:

Test:

- Invalid credentials
    
- Expired tokens
    
- Missing permissions
    
- Validation failures
    
- Server errors
    

---

❌ Running E2E tests against production

Instead:

Use a dedicated testing or staging environment.

---

❌ Depending on previous tests

Instead:

Each E2E test should create and clean up its own data where practical.

# Best Practices

✅ Focus on critical business flows.

✅ Keep E2E tests independent.

✅ Run them in testing or staging environments.

✅ Verify both success and failure paths.

✅ Use realistic test data.

✅ Clean up created data after tests.

✅ Keep the number of E2E tests manageable.

# Real Industry Perspective

Let's compare the three testing levels using your **MERN backend** architecture:

### Unit Test

```text
UserService.createUser()

↓

Tests only the business logic

↓

Mocks UserRepository
```

---

### Integration Test

```text
POST /register

↓

Express

↓

Controller

↓

Service

↓

Repository

↓

MongoDB Test Database
```

---

### End-to-End Test

```text
React Frontend

↓

User fills Registration Form

↓

Backend API

↓

MongoDB

↓

JWT Cookie/Token

↓

User Dashboard Loads Successfully
```

Each level builds confidence in a different part of the system.

---

# Key Takeaways

- End-to-End tests verify complete user journeys across the entire application.
    
- They provide the highest confidence that the system behaves correctly from a user's perspective.
    
- E2E tests are slower and more expensive than unit and integration tests, so they should focus on critical business workflows.
    
- Run E2E tests in testing or staging environments, not production.
    
- Use E2E tests together with unit and integration tests as part of a balanced testing strategy.
