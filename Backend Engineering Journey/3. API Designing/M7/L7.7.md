# What is Test Data?

**Test data** is the data your tests use to verify application behavior.

Example:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "password": "secret123"
}
```

This user exists only for testing.

---

# Why Test Data Matters

Imagine this test:

```http
POST /register
```

First run:

```text
rahul@example.com
```

Success.

Second run:

```text
rahul@example.com
```

Failure.

Reason:

```text
Email already exists.
```

Your test becomes unreliable.

Good test data management prevents this.

---

# Goals of Test Data Management

Professional teams want tests that are:

- Independent
    
- Repeatable
    
- Predictable
    
- Easy to maintain
    
- Fast
    

---

# Types of Test Data

## Static Data

Always the same.

Example:

```json
{
    "role": "admin"
}
```

Good for:

- Roles
    
- Permissions
    
- Countries
    
- Categories
    

---

## Dynamic Data

Generated during testing.

Example:

```text
rahul_12345@example.com
```

Useful for:

- Registration
    
- Orders
    
- Payments
    
- Temporary resources
    

---

## Seed Data

Data inserted before tests start.

Example:

```text
Admin User

↓

Categories

↓

Default Settings
```

Every test begins with this known state.

---

## Fixture Data

Predefined datasets used repeatedly.

Example:

```text
fixtures/

users.json

posts.json

products.json
```

These files make tests easier to reuse and maintain.

---

# Test Lifecycle

A common workflow:

```text
Start Test

↓

Insert Test Data

↓

Run Test

↓

Verify Result

↓

Delete Test Data
```

Each test starts clean and ends clean.

---

# Database State

Before test:

```text
Users

0
```

Test creates:

```text
Rahul
```

After cleanup:

```text
Users

0
```

The database returns to its original state.

---

# Why Cleanup Matters

Imagine:

Test A

creates:

```text
User A
```

Test B assumes:

```text
No users exist.
```

Test B now fails.

The failure isn't in the code.

It's caused by leftover test data.

---

# Test Isolation

Every test should behave as if it is the only test running.

Bad:

```text
Test A

↓

Creates User

↓

Test B

Uses Same User
```

Good:

```text
Test A

Creates

↓

Deletes

↓

Finished
```

Test B starts fresh.

---

# Strategies for Test Isolation

## Strategy 1: Fresh Database

Every test suite creates a new database.

```text
New Database

↓

Run Tests

↓

Delete Database
```

Very reliable.

---

## Strategy 2: Transactions

Database changes are wrapped in a transaction.

```text
Begin Transaction

↓

Run Test

↓

Rollback
```

No permanent changes remain.

This approach is common with SQL databases like PostgreSQL and MySQL.

---

## Strategy 3: Cleanup After Each Test

```text
Run Test

↓

Delete Test Records
```

A simple and widely used strategy.

---

# Unique Test Data

Avoid:

```text
rahul@example.com
```

Repeatedly.

Instead:

```text
rahul_1001@example.com

rahul_1002@example.com

rahul_1003@example.com
```

Unique data prevents collisions.

---

# Data Factories

Professional teams often use **factories**.

Instead of writing:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com"
}
```

Again and again...

Create a factory:

```text
createUser()
```

Every call generates:

```text
Unique Name

↓

Unique Email

↓

Default Password
```

This keeps tests concise and consistent.

---

# Example

Factory output:

User 1

```text
Rahul1

rahul1@example.com
```

---

User 2

```text
Rahul2

rahul2@example.com
```

Automatically generated.

```text

```

Instead of creating them every time:

```text

```

Reuse them across tests.

# Common Beginner Mistakes

❌ Reusing the same email address

Instead:

Generate unique values.

---

❌ Sharing data between tests

Instead:

Each test creates its own data.

---

❌ Forgetting cleanup

Result:

Random failures.

Always clean up.

---

❌ Using production data

Never copy production customer information into test databases.

Use synthetic or anonymized data.

---

❌ Hardcoding everything

Instead:

Use factories and fixtures to reduce duplication.

---

# Professional Workflow

```text
Create Test Database

↓

Seed Required Data

↓

↓

↓

```

# Best Practices

✅ Keep tests independent.

✅ Use factories for dynamic data.

✅ Use fixtures for reusable datasets.

✅ Seed only what is necessary.

✅ Clean up after every test.

✅ Use unique values where required.

✅ Never use production customer data.

---

# Key Takeaways

- Test data is the foundation of reliable automated testing.
    
- Good test data management makes tests repeatable, independent, and predictable.
    
- Use **fixtures** for reusable static data and **factories** for generating dynamic data.
    
- Seed only the data needed for a test, and always clean up afterward.
    
- Keep test environments isolated from production.
    
- Realistic and varied test data—including edge cases—helps uncover bugs before deployment.
