# What is Continuous Integration (CI)?

Continuous Integration means:

> **Every code change is automatically verified.**

Instead of trusting developers to manually run tests, the CI server does it automatically.

Workflow:

```text
Developer Pushes Code

↓

CI Server Starts

↓

Install Dependencies

↓

Run Tests

↓

Generate Report

↓

Pass or Fail
```

---

# What is Continuous Deployment (CD)?

After CI succeeds:

```text
Tests Pass

↓

Deploy Application

↓

Production Updated
```

This process is called **Continuous Deployment** (or **Continuous Delivery**, depending on how releases are approved).

---

# CI vs CD

|CI|CD|
|---|---|
|Build application|Deploy application|
|Run tests|Release application|
|Verify code|Publish code|
|Detect bugs|Deliver features|

They work together.

# Common Beginner Mistakes

## ❌ Skipping Tests Before Push

Instead:

Let CI verify every commit.

---

## ❌ Ignoring Failed Pipelines

Bad:

```text
Tests Failed

↓

Merge Anyway
```

Always investigate failures before merging.

---

## ❌ Storing Secrets in Git

Never commit:

```text
JWT_SECRET

API Keys

Passwords
```

Use CI secrets instead.

---

## ❌ Running Only Unit Tests

A strong pipeline includes:

- Linting
    
- Unit tests
    
- Integration tests
    
- (Critical) E2E tests
    
- Security checks
    

---

## ❌ Deploying Without CI

Manual deployments increase the chance of human error.

Automation reduces risk.

# Industry Tips

### 1. Keep Unit Tests Fast

Most pipelines spend the majority of testing time on unit tests because they provide quick feedback.

---

### 2. Run E2E Tests Selectively

Many teams run:

- Unit + Integration tests on **every pull request**
    
- Full E2E tests before releases or on the main branch
    

This balances speed and confidence.

---

### 3. Make CI Fail Fast

If linting fails, there's no need to continue running expensive tests.

Example:

```text
ESLint Failed

↓

Stop Pipeline
```

This saves time and compute resources.

---

### 4. Treat CI Failures Seriously

A red pipeline means the codebase is not in a releasable state. Teams usually fix CI failures before starting new work.
