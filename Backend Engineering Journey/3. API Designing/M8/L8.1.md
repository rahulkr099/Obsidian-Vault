# Lesson 8.1 — Why Query APIs Matter

### Learning Objectives

By the end of this lesson, you will understand:

- Why simple CRUD APIs are not enough
    
- The difference between retrieving resources and querying resources
    
- How users naturally expect filtering, sorting, searching, and pagination
    
- How poor query design affects performance and user experience
    

---

### The Problem

Suppose your Blog API has:

```text
1,000,000 posts
```

You expose only:

```http
GET /posts
```

What happens?

The server tries to return one million posts.

Problems:

- Huge response size
    
- Slow database query
    
- High memory usage
    
- Slow frontend rendering
    
- Wasted network bandwidth
    

Simple CRUD breaks down as data grows.

---

### What Real Applications Need

Imagine the homepage of a blog.

A user wants:

- Published posts only
    
- Category = Technology
    
- Sorted by newest
    
- First 10 results
    

They are not asking for **all** posts.

They are asking for a **query**.

---

### CRUD vs Query APIs

CRUD:

```http
GET /posts
```

Returns a collection.

Query API:

```http
GET /posts?status=published&category=technology&sort=-publishedAt&page=1&limit=10
```

Returns exactly what the client requested.

---

### Common Query Operations

Professional APIs typically support:

```text
Filtering

↓

Sorting

↓

Pagination

↓

Searching

↓

Field Selection
```

Together, these allow clients to retrieve only the data they need.

---

### Real Examples

GitHub

```http
GET /repos?sort=updated
```

---

YouTube

```http
GET /videos?category=music
```

---

Shopify

```http
GET /orders?status=paid
```

---

Stripe

```http
GET /payments?limit=20
```

Notice that these APIs expose **one resource** with different query options instead of creating separate endpoints.

---

### Bad API Design

Avoid creating endpoints like:

```http
GET /publishedPosts

GET /technologyPosts

GET /recentPosts

GET /popularPosts
```

As requirements grow, you'll end up with dozens of nearly identical endpoints.

---

### Better Design

Keep one resource:

```http
GET /posts
```

Customize behavior with query parameters:

```http
GET /posts?status=published

GET /posts?category=technology

GET /posts?status=published&category=technology
```

One endpoint serves many use cases.

---

### Query Parameters Are Optional

This is important.

These are all valid:

```http
GET /posts
```

```http
GET /posts?page=2
```

```http
GET /posts?category=technology
```

```http
GET /posts?category=technology&page=2
```

Clients choose only the parameters they need.

---

### Designing for Flexibility

Suppose tomorrow the business asks for:

> "Show published JavaScript articles written by Rahul."

You don't need a new endpoint.

Simply extend the query:

```http
GET /posts?status=published&category=javascript&author=rahul
```

Good query design scales with new requirements.

---

### Query Flow

A typical request looks like:

```text
Client

↓

GET /posts?category=technology&page=2

↓

Controller

↓

Validate Query Parameters

↓

Service

↓

Repository

↓

Database Query

↓

Response
```

Notice that the resource remains `/posts`; only the query changes.

---

### Common Beginner Mistakes

❌ Creating a new endpoint for every filter.

Instead:

Use query parameters.

---

❌ Returning the entire dataset.

Instead:

Support pagination.

---

❌ Mixing filters into the path.

Bad:

```http
GET /posts/published/technology
```

Good:

```http
GET /posts?status=published&category=technology
```

---

### Best Practices

✅ Keep the resource path stable.

✅ Express optional criteria with query parameters.

✅ Design queries to be composable (multiple filters together).

✅ Avoid creating duplicate endpoints for different views of the same resource.

---

### Key Takeaways

- CRUD endpoints are only the starting point; real applications need flexible querying.
    
- Query parameters allow clients to filter and customize results without creating new endpoints.
    
- A single endpoint can serve many business requirements.
    
- Designing query APIs well keeps your API scalable and easy to maintain.
