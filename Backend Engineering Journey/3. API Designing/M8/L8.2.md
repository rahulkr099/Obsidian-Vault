# Lesson 8.2 — Filtering APIs

> **Goal:** Learn how to design clean, flexible, and scalable filtering APIs without creating dozens of unnecessary endpoints.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand what filtering is
    
- Design single and multiple filters
    
- Handle boolean, enum, date, and numeric filters
    
- Combine filters effectively
    
- Avoid common API design mistakes
    
- Design filters that map efficiently to database queries
    

---

# What is Filtering?

Filtering means:

> **Return only the resources that match certain conditions.**

Instead of returning every blog post:

```http
GET /posts
```

Return only the ones the client needs.

Example:

```http
GET /posts?category=technology
```

---

# Why Filtering Matters

Imagine your database contains:

```text
1,000,000 posts
```

A user wants only:

- Technology posts
    
- Published posts
    

Returning all one million posts would waste:

- Database resources
    
- Network bandwidth
    
- Client memory
    
- User time
    

Filtering solves this.

---

# Query Parameters are for Filtering

Professional APIs use query parameters.

Example:

```http
GET /posts?category=technology
```

Not:

```http
GET /technologyPosts
```

The resource is still:

```text
Posts
```

Only the query changes.

---

# Single Filter

Example:

```http
GET /posts?category=technology
```

Meaning:

```text
Return only technology posts.
```

---

Another example:

```http
GET /posts?author=rahul
```

Meaning:

```text
Return Rahul's posts.
```

---

# Multiple Filters

Real users rarely search using one condition.

Example:

```http
GET /posts?category=technology&status=published
```

Meaning:

```text
Technology

AND

Published
```

Both conditions must match.

---

Another example:

```http
GET /posts?author=rahul&category=nodejs
```

Return:

```text
Rahul's Node.js posts.
```

---

# Boolean Filters

Some fields are true/false.

Blog example:

```text
featured

published

commentsEnabled
```

Request:

```http
GET /posts?featured=true
```

Another:

```http
GET /posts?published=false
```

These are simple and expressive.

---

# Enum Filters

Suppose your blog supports statuses:

```text
draft

published

archived
```

Request:

```http
GET /posts?status=published
```

The API should validate that only allowed values are accepted.

---

# Date Range Filters

Example:

```http
GET /posts?publishedAfter=2025-01-01
```

Or:

```http
GET /posts?publishedBefore=2025-12-31
```

Combine them:

```http
GET /posts?publishedAfter=2025-01-01&publishedBefore=2025-12-31
```

Meaning:

```text
Posts published during 2025.
```

---

# Numeric Range Filters

Suppose posts have a view count.

Request:

```http
GET /posts?minViews=1000
```

Or:

```http
GET /posts?maxViews=5000
```

Or both:

```http
GET /posts?minViews=1000&maxViews=5000
```

Meaning:

```text
Views

1000 ≤ views ≤ 5000
```

---

# Filtering by Multiple Values

Suppose users want:

- Technology
    
- Programming
    

Instead of making two requests:

Use:

```http
GET /posts?category=technology,programming
```

Meaning:

```text
category IN

Technology

Programming
```

This pattern is common in REST APIs.

---

# Combining Filters

A realistic request:

```http
GET /posts?category=nodejs&status=published&featured=true&author=rahul
```

The API applies every filter together.

This approach is flexible and avoids creating new endpoints for every combination.

---

# Database Perspective

Client:

```http
GET /posts?category=nodejs&status=published
```

Backend flow:

```text
Controller

↓

Validate Query

↓

Service

↓

Repository

↓

Database

↓

WHERE category = 'nodejs'
AND status = 'published'
```

Good filter design maps naturally to efficient database queries.

---

# Validation

Suppose:

```http
GET /posts?status=active
```

But allowed values are:

```text
draft

published

archived
```

Response:

```http
400 Bad Request
```

Never silently ignore invalid filters.

---

# Bad API Designs

❌ Separate endpoints:

```http
GET /publishedPosts

GET /featuredPosts

GET /technologyPosts
```

As features grow, this becomes impossible to maintain.

---

❌ Path-based filters:

```http
GET /posts/published/nodejs
```

These paths become difficult to extend.

Query parameters are much more flexible.

---

# Best Practices

✅ Use query parameters for optional filters.

✅ Allow multiple filters to be combined.

✅ Validate filter values.

✅ Keep filter names descriptive.

✅ Design filters that match database indexes.

---

Design query URLs for:

1. Published AI posts.
    
2. Rahul's featured JavaScript posts.
    
3. Draft posts created after January 1, 2026.
    
4. Posts with 5,000–10,000 views.
    
5. Published Node.js posts with comments enabled.
    

Use only:

```http
GET /posts
```

---

# Key Takeaways

- Filtering allows clients to retrieve only the data they need.
    
- Query parameters are the standard way to express filters in REST APIs.
    
- Multiple filters should be composable in a single request.
    
- Validate filter values before querying the database.
    
- Well-designed filters naturally translate into efficient database queries.
