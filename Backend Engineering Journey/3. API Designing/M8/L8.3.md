# Lesson 8.3 — Sorting & Pagination

> **Goal:** Learn how to design APIs that return data in a meaningful order and efficiently handle large datasets using professional pagination strategies.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand why sorting and pagination are essential
    
- Design sorting APIs
    
- Design multi-field sorting
    
- Implement offset pagination
    
- Understand cursor pagination
    
- Choose the right pagination strategy for different applications
    

---

# Why Sorting Matters

Suppose your blog has:

```text
100,000 posts
```

Request:

```http
GET /posts
```

Question:

**Which post should come first?**

Without sorting, the order is unpredictable and may change depending on the database.

Professional APIs always define a sorting strategy.

---

# Default Sorting

Every API should have a default order.

For a Blog API:

```http
GET /posts
```

Default:

```text
Newest posts first
```

Equivalent to:

```http
GET /posts?sort=-publishedAt
```

This gives users consistent results even if they don't specify sorting.

---

# Sorting Syntax

Use a query parameter.

Example:

```http
GET /posts?sort=title
```

Meaning:

```text
Sort by title (ascending)
```

---

Descending:

```http
GET /posts?sort=-title
```

The minus (`-`) indicates descending order.

This pattern is widely used in APIs.

---

# Sorting Examples

Newest first:

```http
GET /posts?sort=-createdAt
```

---

Oldest first:

```http
GET /posts?sort=createdAt
```

---

Most viewed:

```http
GET /posts?sort=-views
```

---

Alphabetically:

```http
GET /posts?sort=title
```

---

# Multi-field Sorting

Sometimes one field isn't enough.

Suppose two posts have the same number of views.

Request:

```http
GET /posts?sort=-views,-createdAt
```

Meaning:

1. Sort by views (highest first)
    
2. If views are equal, sort by newest
    

This provides stable, predictable ordering.

---

# Sorting Best Practices

Only allow sorting on approved fields.

Allowed:

```text
title

createdAt

views

publishedAt
```

Reject:

```http
GET /posts?sort=password
```

Return:

```http
400 Bad Request
```

Never expose internal or sensitive fields.

---

# Why Pagination Matters

Imagine:

```text
1,000,000 posts
```

Returning all of them in one response would:

- Consume lots of memory
    
- Slow down the database
    
- Increase response time
    
- Waste bandwidth
    

Pagination solves this by returning a small subset.

---

# Offset Pagination

The most common approach.

Example:

```http
GET /posts?page=1&limit=10
```

Meaning:

```text
Page 1

10 posts
```

---

Next page:

```http
GET /posts?page=2&limit=10
```

Then:

```http
GET /posts?page=3&limit=10
```

Simple and easy to understand.

---

# How Offset Pagination Works

Suppose:

```text
Page = 3

Limit = 10
```

The database skips:

```text
20 records
```

Then returns:

```text
Records 21–30
```

Conceptually:

```text
Skip

↓

Limit

↓

Response
```

---

# Response Metadata

Don't return only the posts.

Also include metadata.

Example:

```json
{
  "success": true,
  "data": [...],
  "pagination": {
    "page": 2,
    "limit": 10,
    "total": 145,
    "totalPages": 15,
    "hasNext": true,
    "hasPrevious": true
  }
}
```

This helps frontend applications build pagination controls.

---

# Problems with Offset Pagination

Imagine:

User requests:

```http
GET /posts?page=5
```

While reading:

10 new posts are added.

Now page 5 contains different records than before.

Users may:

- Miss posts
    
- See duplicate posts
    

Large offsets are also slower because the database has to skip many records.

---

# Cursor Pagination

Instead of page numbers, use a cursor.

Example:

```http
GET /posts?cursor=65fa12ab&limit=10
```

Meaning:

```text
Return the next 10 posts after cursor 65fa12ab
```

The cursor usually represents:

- An ID
    
- A timestamp
    
- Another unique sortable value
    

---

# Cursor Flow

```text
Request

↓

Last Post ID

↓

Database

↓

Next 10 Posts

↓

New Cursor

↓

Next Request
```

No records are skipped.

---

# Cursor Response

Example:

```json
{
  "success": true,
  "data": [...],
  "nextCursor": "65fa1c98",
  "hasNext": true
}
```

The client uses `nextCursor` for the following request.

---

# Offset vs Cursor

|Offset Pagination|Cursor Pagination|
|---|---|
|Uses page numbers|Uses cursor/token|
|Easy to implement|Slightly more complex|
|Good for admin dashboards|Excellent for feeds and timelines|
|Slower on large datasets|Fast on large datasets|
|Can produce duplicates or gaps if data changes|Stable even when new records are inserted|

---

# When to Use Which?

### Offset Pagination

Best for:

- Admin dashboards
    
- Reports
    
- Small datasets
    
- Applications where jumping to page 25 is useful
    

Example:

```http
GET /users?page=4&limit=20
```

---

### Cursor Pagination

Best for:

- Social media feeds
    
- Chat messages
    
- News feeds
    
- Activity logs
    
- Infinite scrolling
    

Example:

```http
GET /posts?cursor=65fa12ab&limit=20
```

---

# Combining Sorting and Pagination

Sorting should happen **before** pagination.

Example:

```http
GET /posts?sort=-publishedAt&page=2&limit=10
```

Flow:

```text
Sort

↓

Page

↓

Limit

↓

Response
```

If you paginate before sorting, users will get inconsistent results.

---

# Combining Filtering, Sorting, and Pagination

A real production request:

```http
GET /posts?category=nodejs&status=published&sort=-views&page=2&limit=10
```

Processing order:

```text
Filter

↓

Sort

↓

Paginate

↓

Return Response
```

This order ensures accurate and predictable results.

---

# Common Beginner Mistakes

❌ Returning every record

Instead:

Always paginate collections.

---

❌ No default sorting

Instead:

Define a sensible default, such as newest first.

---

❌ Sorting by sensitive fields

Instead:

Whitelist sortable fields.

---

❌ Applying pagination before sorting

Instead:

Sort first, then paginate.

---

❌ Allowing huge limits

Bad:

```http
GET /posts?limit=100000
```

Instead:

Set a maximum.

Example:

```text
Maximum limit = 100
```

# Best Practices

✅ Always define a default sort order.

✅ Whitelist sortable fields.

✅ Paginate every collection endpoint.

✅ Limit the maximum page size.

✅ Use offset pagination for dashboards.

✅ Use cursor pagination for feeds and large datasets.

✅ Include pagination metadata in responses.

---

# Key Takeaways

- Sorting ensures data is returned in a consistent and meaningful order.
    
- Pagination prevents large responses and improves performance.
    
- Offset pagination is simple and ideal for page-based navigation.
    
- Cursor pagination is more efficient and stable for continuously changing datasets.
    
- Apply operations in this order: **Filter → Sort → Paginate → Respond**.
    
- Always include pagination metadata to help API consumers navigate results.
