> **Goal:** Learn how to design clean, scalable search APIs that help users quickly find the resources they need.

# What is Search?

Search allows users to find resources **when they don't know the exact value**.

Suppose your blog has:

```text
How to Learn Node.js

Express Middleware Guide

MongoDB Indexing

REST API Design
```

A user types:

```text
node
```

The API should find:

```text
How to Learn Node.js
```

even though the full title isn't provided.

---

# Search vs Filtering

This is one of the most misunderstood topics in API design.

## Filtering

Filtering matches **known values**.

Example:

```http
GET /posts?category=technology
```

The client already knows:

```text
category = technology
```

---

## Searching

Searching matches **unknown values**.

Example:

```http
GET /posts?search=node
```

The client doesn't know:

- the exact title
    
- the author
    
- the slug
    

They just know the keyword.

---

# Think Like a User

Filtering:

> Show me Technology posts.

Searching:

> I remember reading something about Node.js.

Different user intentions.

---

# Search Parameter

The most common design:

```http
GET /posts?search=node
```

Meaning:

```text
Find posts related to "node".
```

Simple and intuitive.

---

# Searching Multiple Fields

Suppose users search:

```text
express
```

Should the API search only the title?

Usually no.

Professional APIs often search:

- Title
    
- Description
    
- Tags
    
- Author name
    

One search query can match several fields.

---

# Partial Matching

User types:

```text
prog
```

Expected result:

```text
Programming Basics
```

The user shouldn't need to type the full title.

This is called **partial matching**.

---

# Case Insensitive Search

These should all return the same results:

```text
node

Node

NODE
```

Professional search APIs ignore letter casing unless there's a specific reason not to.

---

# Full-Text Search

Imagine searching:

```text
backend architecture
```

The API should find posts containing:

- backend
    
- architecture
    

even if they appear in different parts of the content.

This is **full-text search**.

Instead of searching only titles, the database searches larger text fields efficiently.

---

# Search Flow

```text
Client

↓

GET /posts?search=node

↓

Controller

↓

Validate Query

↓

Service

↓

Repository

↓

Database Search

↓

Results
```

Notice that search is still handled through the same resource endpoint.

---

# Combining Search with Filtering

A realistic request:

```http
GET /posts?search=node&category=technology
```

Meaning:

```text
Search for "node"

↓

Only Technology posts
```

Search and filtering work together.

---

# Combining Everything

Production example:

```http
GET /posts?search=node&category=technology&sort=-views&page=1&limit=10
```

Processing order:

```text
Search

↓

Filter

↓

Sort

↓

Paginate

↓

Response
```

---

# Search Response

Example:

```json
{
  "success": true,
  "data": [
    {
      "title": "Node.js Authentication"
    },
    {
      "title": "Node.js Streams"
    }
  ]
}
```

The response format should remain consistent with other endpoints.

---

# Search Performance

Imagine:

```text
5,000,000 posts
```

Searching every document one by one would be extremely slow.

Professional applications use:

- Database indexes
    
- Full-text indexes
    
- Dedicated search engines (for very large systems)
    

Good API design considers how the backend will execute the search efficiently.

---

# Search Suggestions

Many applications provide suggestions while typing.

User types:

```text
nod
```

Suggestions:

```text
Node.js

Node Streams

Node Authentication
```

API:

```http
GET /posts?search=nod&limit=5
```

The frontend can display these as autocomplete suggestions.

---

# Search Result Ordering

Suppose:

```text
Node.js Guide

Advanced Node.js

JavaScript Basics
```

Search:

```text
node
```

The most relevant results should appear first.

Professional search systems often rank results by relevance instead of simply sorting alphabetically.

---

# When NOT to Use Search

Bad:

```http
GET /posts?search=published
```

If `published` is a status field, use filtering instead:

```http
GET /posts?status=published
```

Rule:

- Known structured values → Filter
    
- Free-form user input → Search
    

---

# Common Beginner Mistakes

## ❌ Creating Separate Search Endpoints

Bad:

```http
GET /searchPosts
```

Better:

```http
GET /posts?search=node
```

The resource remains `posts`.

---

## ❌ Confusing Search and Filter

Bad:

```http
GET /posts?search=technology
```

if `technology` is actually a category.

Better:

```http
GET /posts?category=technology
```

---

## ❌ Searching Sensitive Fields

Don't allow searches on:

- Passwords
    
- Tokens
    
- Internal IDs
    
- Private information
    

Search only appropriate public fields.

---

## ❌ Ignoring Pagination

Search results can also be huge.

Always paginate them.

Bad:

```http
GET /posts?search=node
```

Better:

```http
GET /posts?search=node&page=1&limit=10
```

# Best Practices

✅ Use a `search` query parameter.

✅ Search only meaningful fields.

✅ Keep search case-insensitive.

✅ Combine search with filters.

✅ Paginate search results.

✅ Maintain the same response structure as other endpoints.

---

# Key Takeaways

- Searching helps users find resources using free-form keywords.
    
- Filtering is for known structured values; searching is for unknown text.
    
- Use a `search` query parameter instead of creating separate search endpoints.
    
- Search should work seamlessly with filtering, sorting, and pagination.
    
- Large datasets require indexed or full-text search for good performance.
    
- Keep search APIs simple, consistent, and predictable.
