# Lesson 8.5 — Field Selection & Response Optimization

> **Goal:** Learn how to design APIs that return only the data clients need, reducing response size and improving performance.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand why field selection is important
    
- Design APIs that support field selection
    
- Reduce response payloads
    
- Balance flexibility and security
    
- Optimize API responses
    
- Know when field selection should and shouldn't be used
    

---

# The Problem

Suppose your Blog document looks like this:

```json
{
  "id": "1",
  "title": "Learning Node.js",
  "content": "...5000 words...",
  "author": {
    "id": "10",
    "name": "Rahul"
  },
  "category": "Technology",
  "tags": ["Node", "Backend"],
  "views": 1250,
  "likes": 250,
  "comments": 50,
  "createdAt": "...",
  "updatedAt": "...",
  "publishedAt": "...",
  "readingTime": 12
}
```

Now imagine the homepage.

It only needs:

- Title
    
- Author
    
- Published date
    

Returning everything wastes bandwidth.

---

# Why Response Optimization Matters

Suppose:

```text
20 posts
```

Each post contains:

```text
5 KB
```

Total response:

```text
100 KB
```

But the homepage only needs:

```text
20 KB
```

That's an **80% reduction** in transferred data.

---

# Field Selection

Clients can request only specific fields.

Example:

```http
GET /posts?fields=title,author,publishedAt
```

Meaning:

```text
Return only

Title

Author

Published Date
```

---

# Example Response

Instead of:

```json
{
  "title": "...",
  "content": "...",
  "views": "...",
  "likes": "...",
  "comments": "..."
}
```

Return:

```json
{
  "title": "...",
  "author": "...",
  "publishedAt": "..."
}
```

Only the requested fields.

# Combining with Other Queries

A production request:

```http
GET /posts?category=nodejs&sort=-views&page=1&limit=10&fields=title,views,author
```

Processing order:

```text
Filter

↓

Sort

↓

Paginate

↓

Select Fields

↓

Response
```

---

# Default Fields

If no `fields` parameter is provided:

```http
GET /posts
```

The API returns a sensible default response.

Clients shouldn't be forced to specify fields every time.

---

# Security Considerations

Never allow every field to be selected.

Suppose your User model contains:

```text
password

refreshToken

emailVerificationToken
```

This request:

```http
GET /users?fields=password
```

Should **never** expose sensitive data.

Only allow a whitelist of safe fields.

---

# Whitelisting Fields

Allowed:

```text
title

author

views

category

publishedAt
```

Not allowed:

```text
password

refreshToken

resetPasswordToken
```

Always validate the requested fields.

---

# Response Size Matters

Suppose:

Mobile user

↓

Slow internet

↓

Large response

↓

Slow page load

Returning fewer fields improves:

- Speed
    
- User experience
    
- Data usage
    

---

# Nested Field Selection

Suppose:

```json
author

↓

name

email

avatar
```

Client wants:

```text
Author Name
```

Professional APIs may support:

```http
GET /posts?fields=title,author.name
```

Only the required nested field is returned.

---

# Field Selection vs Filtering

Don't confuse them.

Filtering:

```http
GET /posts?category=technology
```

Changes:

```text
Which posts
```

are returned.

---

Field Selection:

```http
GET /posts?fields=title,views
```

Changes:

```text
Which fields
```

are returned.

Different purposes.

# Common Beginner Mistakes

## ❌ Returning Entire Documents

Bad:

Homepage receives:

```text
Content

Comments

Likes

Metadata
```

even though it only needs titles.

---

## ❌ Allowing Sensitive Fields

Never expose:

- Passwords
    
- Tokens
    
- Internal notes
    

Use a whitelist.

---

## ❌ Ignoring Validation

Request:

```http
GET /posts?fields=title,hackedField
```

Return:

```http
400 Bad Request
```

or ignore invalid fields based on your API design.

Be consistent.

---

## ❌ Using Different Response Shapes Everywhere

Keep responses predictable.

Whether returning 3 fields or 10 fields, the overall response structure should remain consistent.

# Best Practices

✅ Return sensible default fields.

✅ Allow clients to request additional fields when needed.

✅ Whitelist allowed fields.

✅ Never expose sensitive information.

✅ Combine field selection with filtering, sorting, and pagination.

✅ Keep the response structure consistent.

---

# Key Takeaways

- Field selection lets clients request only the data they need.
    
- Smaller responses improve performance, especially on slow networks.
    
- Filtering decides **which resources** are returned; field selection decides **which attributes** of those resources are returned.
    
- Always whitelist allowed fields and never expose sensitive data.
    
- Field selection works best when combined with filtering, sorting, and pagination.
    
- Keep response structures consistent regardless of the selected fields.
