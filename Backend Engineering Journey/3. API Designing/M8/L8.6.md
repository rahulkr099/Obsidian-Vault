# Lesson 8.6 — Building a Professional Query API

> **Goal:** Combine filtering, sorting, pagination, search, and field selection into a single production-ready endpoint.

This lesson ties together everything you've learned in Module 8.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Design a production-ready query endpoint
    
- Process query parameters in the correct order
    
- Validate query parameters
    
- Map API queries to database queries
    
- Design consistent API responses
    
- Think like a backend engineer instead of just writing Express code

# The Business Requirement

The product manager says:

> "Users should be able to browse blog posts."

Sounds simple.

But then more requirements arrive.

Users should:

- Search posts
    
- Filter by category
    
- Filter by author
    
- Filter by status
    
- Sort results
    
- Paginate results
    
- Select only required fields
    

Instead of creating many endpoints:

```http
GET /technologyPosts

GET /recentPosts

GET /featuredPosts

GET /nodePosts
```

We'll design **one professional endpoint**.

---

# Final Endpoint

```http
GET /posts
```

Everything else becomes optional query parameters.

---

# Complete Example

```http
GET /posts?
category=nodejs&
status=published&
author=rahul&
search=authentication&
sort=-views&
page=2&
limit=10&
fields=title,author,views,publishedAt
```

One endpoint.

Many capabilities.

---

# Complete Query Flow

Professional request processing follows a logical order.

```text
Client Request

↓

Validate Query Parameters

↓

Search

↓

Filter

↓

Sort

↓

Paginate

↓

Field Selection

↓

Database Query

↓

Format Response

↓

Return Response
```

Every professional API follows a similar pipeline.

---

# Step 1 — Validate Query Parameters

Before touching the database:

Validate:

```text
page

limit

sort

fields

category

status
```

Reject invalid values.

Example:

```http
GET /posts?page=-1
```

Response:

```http
400 Bad Request
```

Validation should happen before any database work.

---

# Step 2 — Apply Search

Request:

```http
GET /posts?search=node
```

Meaning:

Find posts containing:

```text
node
```

Search usually checks:

- title
    
- summary
    
- tags
    

---

# Step 3 — Apply Filters

Example:

```http
GET /posts?
category=nodejs&
status=published
```

Only matching posts remain.

Think:

```text
1,000,000 posts

↓

100,000 Technology

↓

40,000 Published

↓

Continue
```

Each filter narrows the dataset.

---

# Step 4 — Sort Results

Example:

```http
GET /posts?sort=-views
```

Now the filtered posts are ordered.

Highest views first.

Always sort **before** pagination.

---

# Step 5 — Paginate

Example:

```http
GET /posts?page=2&limit=10
```

Now return only:

```text
Posts

11–20
```

instead of every matching post.

---

# Step 6 — Field Selection

Example:

```http
GET /posts?fields=title,views,author
```

Now reduce each document.

Instead of:

```json
{
  "title": "...",
  "content": "...",
  "comments": "...",
  "likes": "...",
  "views": "..."
}
```

Return:

```json
{
  "title": "...",
  "views": "...",
  "author": "..."
}
```

Smaller responses.

Faster APIs.

---

# Step 7 — Database Query

Conceptually:

```text
Repository

↓

Build Query

↓

Apply Filters

↓

Apply Sorting

↓

Apply Pagination

↓

Apply Projection

↓

Execute Query
```

Notice how every query parameter maps naturally to a database operation.

---

# Example Request

```http
GET /posts?
category=nodejs&
status=published&
sort=-publishedAt&
page=1&
limit=5&
fields=title,author,publishedAt
```

---

```json
{
  "success": true,
  "data": [
    {
      "title": "Node.js Authentication",
      "author": "Rahul",
      "publishedAt": "2026-05-10"
    }
  ],

    "total": 42,
    "totalPages": 9,

    "hasPrevious": false
  }

```

Notice that the response includes both the data and useful pagination metadata.

# Mapping to Your Architecture

You have been learning this architecture:

```text
Route

↓

Controller

↓

Service

↓

Repository

↓

MongoDB
```

Now let's map responsibilities.

---

## Controller

Responsibilities:

- Read query parameters
    
- Validate request
    
- Call service
    

Not responsible for:

- Building MongoDB queries
    
- Business logic
    

---

## Service

Responsibilities:

- Apply business rules
    
- Decide default sorting
    
- Enforce maximum page size
    
- Prepare query options
    

---

## Repository

Responsibilities:

- Convert options into database queries
    
- Execute MongoDB query
    
- Return results
    

The repository should know MongoDB.

The service should not.

---

# Query Object

After validation, the controller might pass something conceptually like:

```text
{
 category,
 status,
 search,
 sort,
 page,
 limit,
 fields
}
```

The service receives one clean object instead of parsing HTTP details.

---

# Default Values

Professional APIs always define defaults.

If the client sends:

```http
GET /posts
```

The API might use:

```text
page = 1

limit = 10

sort = -publishedAt

fields = default response
```

Clients don't need to specify everything.

---

# Maximum Limits

Bad request:

```http
GET /posts?limit=50000
```

Instead:

```text
Maximum limit = 100
```

If a client requests more:

Either:

```text
Use 100
```

or

Return:

```http
400 Bad Request
```

Choose one policy and keep it consistent.

---

# Invalid Fields

Bad:

```http
GET /posts?sort=password
```

Good response:

```http
400 Bad Request
```

Reason:

```text
password

is not sortable
```

Always validate client input.

---

# Index Considerations

Suppose clients often request:

```http
GET /posts?
category=nodejs&
status=published&
sort=-publishedAt
```

Your database should have indexes that support these common query patterns.

API design and database design go together.

---

# Common Beginner Mistakes

## ❌ Creating Separate Endpoints

Bad:

```http
GET /recentPosts

GET /popularPosts

GET /featuredPosts
```

Good:

```http
GET /posts?sort=-publishedAt

GET /posts?sort=-views

GET /posts?featured=true
```

---

## ❌ Mixing Query Parameters into the Path

Bad:

```http
GET /posts/nodejs/published
```

Good:

```http
GET /posts?category=nodejs&status=published
```

---

## ❌ No Validation

Never trust:

```http
GET /posts?page=-50
```

Validate every query parameter.

---

## ❌ Returning Huge Responses

Always support:

- Pagination
    
- Field selection

# Best Practices

✅ One endpoint should support multiple query capabilities.

✅ Validate every query parameter.

✅ Apply operations in this order:

```text
Search

↓

Filter

↓

Sort

↓

Paginate

↓

Field Selection
```

✅ Define sensible defaults.

✅ Limit maximum page size.

✅ Design queries with database indexes in mind.

✅ Keep controllers thin and repositories responsible for database queries.
