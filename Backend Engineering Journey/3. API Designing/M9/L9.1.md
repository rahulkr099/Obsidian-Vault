# Lesson 9.1 — Understanding Resource Relationships

> **Goal:** Learn how relationships between database entities influence REST API design.

This lesson connects what you learned in **Data Modeling** with **API Design**.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand how database relationships become REST APIs
    
- Identify parent and child resources
    
- Design APIs for One-to-One, One-to-Many, and Many-to-Many relationships
    
- Decide which resource "owns" a relationship
    
- Think about APIs from a business perspective
    

---

# Why Relationships Matter

Real applications don't have isolated resources.

A Blog application has:

```text
Users

↓

Posts

↓

Comments

↓

Likes

↓

Categories
```

These resources are connected.

Your API should reflect these relationships naturally.

---

# From Database to API

Suppose your ER diagram looks like this:

```text
User

1

↓

Many

Post
```

Database relationship:

```text
One User

↓

Many Posts
```

API relationship:

```http
GET /users/:id/posts
```

The database relationship directly influences the API.

---

# Common Relationship Types

## One-to-One (1:1)

Example:

```text
User

↓

Profile
```

One user has one profile.

API:

```http
GET /users/:id/profile
```

Another example:

```http
PATCH /users/:id/profile
```

---

## One-to-Many (1:N)

Example:

```text
User

↓

Posts
```

One user can write many posts.

API:

```http
GET /users/:id/posts
```

Create a post:

```http
POST /users/:id/posts
```

Although, as we'll discuss later, many teams prefer:

```http
POST /posts
```

We'll learn **why** in the next lesson.

---

## One Post → Many Comments

Relationship:

```text
Post

↓

Comments
```

API:

```http
GET /posts/:id/comments
```

Create:

```http
POST /posts/:id/comments
```

This relationship feels natural because comments belong to a post.

---

## Many-to-Many (M:N)

Example:

```text
Users

↔

Posts

(Likes)
```

One user can like many posts.

One post can be liked by many users.

API:

```http
POST /posts/:id/likes
```

Remove like:

```http
DELETE /posts/:id/likes
```

The relationship itself becomes an API operation.

---

# Parent and Child Resources

Consider:

```text
Post

↓

Comment
```

Question:

**Can a comment exist without a post?**

Usually:

No.

Therefore:

```text
Post

is the parent.
```

Comment is the child.

---

Example:

```http
GET /posts/25/comments
```

Reads naturally:

> Get comments belonging to Post 25.

---

# Another Example

```text
Category

↓

Posts
```

Relationship:

```http
GET /categories/:id/posts
```

Meaning:

Return every post inside this category.

---

# Ownership

Every relationship has an owner.

Example:

```text
Post

↓

Comments
```

Question:

Who owns the comments?

Answer:

```text
Post
```

So creating a comment naturally starts from the post.

---

Example:

```http
POST /posts/:id/comments
```

Not:

```http
POST /comments
```

(We'll compare these approaches in Lesson 9.2.)

---

# Thinking from Business Requirements

Requirement:

> Show all posts written by Rahul.

Ask yourself:

Which resource is the parent?

Answer:

```text
User
```

API:

```http
GET /users/:id/posts
```

---

Requirement:

> Show comments on a blog post.

Parent:

```text
Post
```

API:

```http
GET /posts/:id/comments
```

---

Requirement:

> Show all posts in Technology.

Parent:

```text
Category
```

API:

```http
GET /categories/:id/posts
```

Notice that we are deriving endpoints from relationships—not memorizing URLs.

---

# Relationship Flow

Example:

```http
GET /posts/42/comments
```

Flow:

```text
Client

↓

Controller

↓

Comment Service

↓

Comment Repository

↓

Database

↓

Comments for Post 42

↓

Response
```

The relationship affects both the API and the database query.

---

# Relationship vs Independent Resource

Some resources always belong to another resource.

Example:

```text
Comment

↓

Belongs to Post
```

Others can stand alone.

Example:

```text
User

Post

Category
```

Knowing the difference helps you choose the right endpoint design.

---

# Mapping Relationships to Queries

Example:

```http
GET /users/10/posts
```

Repository conceptually performs:

```text
Find all posts

WHERE

authorId = 10
```

---

Example:

```http
GET /posts/20/comments
```

Repository performs:

```text
Find comments

WHERE

postId = 20
```

The URL naturally maps to the database query.

---

# Common Beginner Mistakes

## ❌ Ignoring Relationships

Bad:

```http
GET /everything
```

One endpoint should not return unrelated data.

---

## ❌ Creating Unclear Endpoints

Bad:

```http
GET /getUserPosts
```

Good:

```http
GET /users/:id/posts
```

The URL describes the relationship.

---

## ❌ Confusing Parent Resources

Requirement:

> Get comments for a post.

Bad:

```http
GET /users/:id/comments
```

Unless the requirement is specifically:

> Show all comments written by a user.

Always identify the correct parent.

---

# Real Blog API Relationships

Our Blog application contains:

```text
User

↓

Posts

↓

Comments

↓

Likes
```

Categories:

```text
Category

↓

Posts
```

These relationships lead naturally to endpoints such as:

```http
GET /users/:id/posts

GET /posts/:id/comments

GET /categories/:id/posts

POST /posts/:id/likes
```

No guessing is required.

---

# Best Practices

✅ Start from the business relationship.

✅ Identify the parent resource.

✅ Let URLs reflect resource relationships.

✅ Keep resource names consistent.

✅ Think about how the database relationship maps to the API.

# Key Takeaways

- Database relationships directly influence REST API design.
    
- One-to-One, One-to-Many, and Many-to-Many relationships each lead to different endpoint patterns.
    
- Parent-child relationships help determine which resource appears first in the URL.
    
- Design APIs from business requirements and resource relationships rather than inventing arbitrary endpoints.
    
- Well-designed relationship APIs naturally map to efficient database queries.
