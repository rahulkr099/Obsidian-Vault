# Lesson 9.2 — Nested Resource Design

> **Goal:** Learn when to use nested resources and when to use top-level resources in a REST API.

This is one of the most common API design questions in backend interviews and real projects.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand what nested resources are
    
- Decide when nesting is appropriate
    
- Know when top-level resources are better
    
- Avoid deeply nested URLs
    
- Design clean, maintainable REST APIs
    

---

# What is a Nested Resource?

A nested resource shows that one resource belongs to another.

Example:

```http
GET /posts/123/comments
```

Read it like English:

> Get the comments of post **123**.

The URL itself expresses the relationship.

---

# Top-Level Resource

The same data can often be accessed through a top-level resource.

Example:

```http
GET /comments?postId=123
```

This means:

> Get comments where `postId = 123`.

Both APIs can return the same data.

The question is:

**Which design is better?**

---

# Example 1 — Blog Comments

Requirement:

> Show comments for a specific post.

Natural relationship:

```text
Post
  ↓
Comments
```

API:

```http
GET /posts/:postId/comments
```

This is a great use of nesting because comments are being viewed **in the context of a post**.

---

# Example 2 — Comment Moderation

Requirement:

> Admin wants to see every comment in the system.

Would this work?

```http
GET /posts/:postId/comments
```

No.

The admin doesn't care about one specific post.

Better:

```http
GET /comments
```

This endpoint treats comments as an independent resource.

---

# Same Resource, Different Use Cases

Your API can have both:

```http
GET /posts/:postId/comments
```

and

```http
GET /comments
```

Why?

Because they answer different business questions.

---

# Creating a Comment

Requirement:

> Add a comment to Post 25.

Natural API:

```http
POST /posts/25/comments
```

The parent post is already known.

The request body doesn't need:

```json
{
    "postId": 25
}
```

The URL already provides it.

---

# Updating a Comment

Requirement:

> Edit Comment 80.

Should you write:

```http
PATCH /posts/25/comments/80
```

Usually **no**.

Better:

```http
PATCH /comments/80
```

Why?

Because the comment already has its own identity.

You don't need the post ID to update it.

---

# Deleting a Comment

Good:

```http
DELETE /comments/80
```

Not:

```http
DELETE /posts/25/comments/80
```

Once a resource has its own unique ID, a top-level endpoint is usually simpler.

---

# A Useful Rule

Use nesting to **find or create** child resources.

Use top-level endpoints to **manage** existing child resources.

Example:

Create:

```http
POST /posts/:postId/comments
```

Update:

```http
PATCH /comments/:commentId
```

Delete:

```http
DELETE /comments/:commentId
```

This pattern is common in professional APIs.

---

# Another Example — User Posts

Requirement:

> Show Rahul's posts.

API:

```http
GET /users/:userId/posts
```

Requirement:

> Edit Post 42.

Good:

```http
PATCH /posts/42
```

No need for:

```http
PATCH /users/10/posts/42
```

The post ID is enough.

---

# Deep Nesting

Suppose someone designs:

```http
GET /users/5/posts/12/comments/8/replies
```

This is difficult to read.

Imagine adding more relationships:

```text
Organization

↓

Team

↓

User

↓

Post

↓

Comment

↓

Reply
```

The URL becomes very long.

---

# Recommended Nesting Depth

Professional APIs usually keep nesting to:

```text
Parent

↓

Child
```

Maximum:

```text
Grandparent

↓

Parent

↓

Child
```

Beyond that, consider query parameters or top-level resources.

---

# Example

Good:

```http
GET /posts/:postId/comments
```

Acceptable:

```http
GET /users/:userId/posts/:postId
```

Avoid:

```http
GET /organizations/:orgId/teams/:teamId/users/:userId/posts/:postId/comments
```

This becomes difficult to maintain.

---

# Nested vs Query Parameter

Suppose you want comments for a post.

Option 1:

```http
GET /posts/25/comments
```

Option 2:

```http
GET /comments?postId=25
```

### When to use nested?

When you're navigating from a parent resource.

### When to use query parameters?

When comments are already treated as an independent collection and filtering is more appropriate.

Both are valid depending on the use case.

---

# Relationship Ownership

Question:

Who owns a comment?

```text
Post

↓

Comment
```

Therefore:

Creating:

```http
POST /posts/:postId/comments
```

makes perfect sense.

Question:

Who owns a post?

```text
User

↓

Post
```

But after creation, the post becomes its own resource.

So:

```http
PATCH /posts/:postId
```

is preferred.

---

# Real Blog API

A professional Blog API might contain:

```http
GET    /posts

GET    /posts/:postId

POST   /posts

PATCH  /posts/:postId

DELETE /posts/:postId

GET    /posts/:postId/comments

POST   /posts/:postId/comments

PATCH  /comments/:commentId

DELETE /comments/:commentId
```

Notice the balance between nested and top-level endpoints.

---

# Database Perspective

Request:

```http
GET /posts/25/comments
```

Repository:

```text
Find comments

WHERE postId = 25
```

---

Request:

```http
PATCH /comments/80
```

Repository:

```text
Update comment

WHERE id = 80
```

The database query remains simple.

---

# Common Beginner Mistakes

## ❌ Nesting Everything

Bad:

```http
PATCH /posts/12/comments/50
```

Good:

```http
PATCH /comments/50
```

---

## ❌ Ignoring Relationships

Bad:

```http
POST /comments
```

Body:

```json
{
    "postId": 25
}
```

While valid, if the business action is clearly "add a comment to this post," a nested endpoint is often more expressive.

---

## ❌ Deeply Nested URLs

Bad:

```http
/users/1/posts/2/comments/3/replies/4
```

Keep URLs simple.

---

## ❌ Duplicating APIs

Don't create:

```http
GET /userPosts

GET /postComments

GET /categoryPosts
```

Use resource-oriented URLs instead.

---

# Professional Decision Framework

When designing a relationship endpoint, ask:

### Question 1

Does the child exist without the parent?

If **No**, nesting is usually appropriate.

---

### Question 2

Does the child have its own identity?

If **Yes**, give it top-level endpoints for update and delete operations.

---

### Question 3

Is the parent only being used to filter?

If **Yes**, a query parameter may be cleaner.

Example:

```http
GET /comments?postId=25
```

---

# Best Practices

✅ Use nested endpoints for creating child resources.

✅ Use nested endpoints when navigating parent → child.

✅ Use top-level endpoints for updating or deleting existing resources.

✅ Avoid nesting deeper than two or three levels.

✅ Design URLs around business relationships, not database tables.

---

# Key Takeaways

- Nested resources clearly express parent-child relationships.
    
- Use nested endpoints when creating or listing child resources within the context of a parent.
    
- Once a child resource has its own identity, manage it through top-level endpoints.
    
- Avoid excessive nesting because it makes APIs harder to understand and maintain.
    
- The best API design depends on the business requirement, not just the database schema.
