# Lesson 9.3 — Relationship Operations

> **Goal:** Learn how to design APIs that create, update, and remove relationships between resources in a RESTful way.

In this lesson, we're **not creating new resources** like Posts or Users. Instead, we're creating or removing **relationships** between existing resources.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Design APIs for relationship operations
    
- Distinguish between creating a resource and creating a relationship
    
- Design APIs for likes, follows, bookmarks, enrollments, etc.
    
- Prevent duplicate relationships
    
- Apply authentication and authorization correctly
    
- Choose appropriate HTTP methods
    

---

# Creating a Resource vs Creating a Relationship

These are different concepts.

Creating a resource:

```http
POST /posts
```

Creates:

```text
A new Post
```

---

Creating a relationship:

```http
POST /posts/25/likes
```

Creates:

```text
Relationship

User ↔ Post
```

No new post is created.

Only a **Like** relationship.

---

# Common Relationship Operations

Most applications have relationships like:

```text
User ↔ Post

(Likes)
```

```text
User ↔ User

(Follows)
```

```text
User ↔ Course

(Enrollments)
```

```text
User ↔ Product

(Bookmarks)
```

These all follow similar API design principles.

---

# Example — Liking a Post

Business requirement:

> User likes Post 25.

API:

```http
POST /posts/25/likes
```

Meaning:

Create a relationship between:

```text
Current User

↓

Post 25
```

---

# Removing a Like

Business requirement:

> User removes their like.

API:

```http
DELETE /posts/25/likes
```

Meaning:

Remove the relationship.

The post still exists.

The user still exists.

Only the **Like** relationship disappears.

---

# Where is the User ID?

Notice:

```http
POST /posts/25/likes
```

There's no:

```http
userId
```

Why?

Because authentication already tells us who the user is.

Example:

```text
JWT

↓

User ID = 42
```

The server already knows the current user.

Never trust clients to send their own user ID for actions like liking or following.

---

# Example — Following a User

Business requirement:

> Rahul follows Aman.

API:

```http
POST /users/15/follow
```

Meaning:

Current user follows:

```text
User 15
```

---

Unfollow:

```http
DELETE /users/15/follow
```

Again, only the relationship changes.

---

# Example — Bookmarking

Business requirement:

> Save Post 100 for later.

API:

```http
POST /posts/100/bookmarks
```

Remove bookmark:

```http
DELETE /posts/100/bookmarks
```

Simple and expressive.

---

# Example — Course Enrollment

Business requirement:

> Student enrolls in Course 20.

API:

```http
POST /courses/20/enrollments
```

Drop course:

```http
DELETE /courses/20/enrollments
```

---

# Preventing Duplicate Relationships

Imagine:

```http
POST /posts/25/likes
```

User clicks twice.

Without checks:

Database:

```text
Like

Like
```

Duplicate records.

Instead:

Check:

```text
Does relationship already exist?
```

If yes:

Return:

```http
409 Conflict
```

or simply treat it as a no-op, depending on your API design.

The important thing is that the relationship should not be duplicated.

---

# Authorization

Requirement:

> User removes someone else's like.

Should this be allowed?

No.

Relationship operations must verify ownership.

Example:

```text
Current User

↓

Owns Like?

↓

Yes → Continue

No → 403 Forbidden
```

---

# Database Perspective

Suppose Likes are stored as:

```text
userId

postId
```

Request:

```http
POST /posts/25/likes
```

Repository:

```text
Insert

userId = 42

postId = 25
```

---

Delete:

```http
DELETE /posts/25/likes
```

Repository:

```text
Delete

WHERE

userId = 42

AND

postId = 25
```

The relationship is uniquely identified by both IDs.

---

# Idempotency

Consider:

```http
DELETE /posts/25/likes
```

User sends the request twice.

Result:

- First request removes the like.
    
- Second request finds nothing to remove.
    

The second request should not corrupt data.

This is one reason `DELETE` is considered **idempotent**.

---

# When to Create a Separate Resource

Not every relationship should be represented only by a nested endpoint.

Suppose an enrollment stores:

```text
Student

Course

Enrollment Date

Grade

Status

Certificate
```

Now the relationship has its own data.

It may become its own resource:

```http
GET /enrollments/:id

PATCH /enrollments/:id
```

The relationship itself has grown into a full entity.

---

# Real Blog API

Relationship endpoints:

```http
POST   /posts/:postId/likes

DELETE /posts/:postId/likes

POST   /posts/:postId/comments

GET    /posts/:postId/comments

PATCH  /comments/:commentId

DELETE /comments/:commentId
```

Notice:

- Comments become independent resources after creation.
    
- Likes remain lightweight relationships.

# Common Beginner Mistakes

## ❌ Passing userId in the Body

Bad:

```json
{
    "userId": 42
}
```

Good:

Use authentication.

The server already knows the user.

---

## ❌ Creating Duplicate Likes

Always check whether the relationship already exists.

---

## ❌ Using GET to Modify Data

Bad:

```http
GET /posts/25/like
```

GET should never change server state.

Use:

```http
POST /posts/25/likes
```

---

## ❌ Deleting the Resource Instead of the Relationship

Bad:

```http
DELETE /posts/25
```

when the intention is only to remove a like.

Delete the relationship, not the resource.

---

# Best Practices

✅ Use `POST` to create relationships.

✅ Use `DELETE` to remove relationships.

✅ Identify the current user through authentication.

✅ Prevent duplicate relationships.

✅ Check authorization before modifying relationships.

✅ Treat relationships with additional business data as separate resources when appropriate.

# Key Takeaways

- Relationship operations connect existing resources rather than creating new ones.
    
- Use `POST` to create relationships and `DELETE` to remove them.
    
- Authentication should identify the acting user; clients should not supply their own user ID for these actions.
    
- Prevent duplicate relationships and enforce authorization rules.
    
- If a relationship gains significant business data (such as grades, statuses, or certificates), it may deserve to become its own resource.
