# Lesson 9.4 — Designing the Blog Relationship API

> **Goal:** Design the complete relationship layer of the Blog API using everything you've learned in this module.

# Step 1 — Understand the Business Requirements

Our Blog application has these resources:

```text
Users

Posts

Comments

Likes

Categories
```

Business requirements:

- Users can create posts.
    
- Users can comment on posts.
    
- Users can like posts.
    
- Users can browse posts by category.
    
- Users can view another author's posts.
    
- Users can edit and delete only their own comments.
    

Instead of immediately writing endpoints, we first identify the relationships.

---

# Step 2 — Identify Relationships

```text
User
   │
   ├── writes
   ▼
Post

Post
   │
   ├── has
   ▼
Comment

User
   │
   ├── likes
   ▼
Post

Category
   │
   ├── contains
   ▼
Post
```

These relationships naturally become REST APIs.

---

# Step 3 — Design the Endpoints

## User → Posts

Requirement:

> Show Rahul's posts.

API:

```http
GET /users/:userId/posts
```

Reason:

- Parent = User
    
- Child = Posts
    

---

## Category → Posts

Requirement:

> Show Technology posts.

API:

```http
GET /categories/:categoryId/posts
```

Reason:

The request starts from a category.

---

## Post → Comments

Requirement:

> Show comments for Post 25.

API:

```http
GET /posts/:postId/comments
```

Reason:

Comments belong to a post.

---

## Create Comment

Requirement:

> Add a comment to Post 25.

API:

```http
POST /posts/:postId/comments
```

Request Body:

```json
{
    "content": "Excellent article!"
}
```

Notice:

No `postId` in the body.

The URL already identifies the parent resource.

---

## Update Comment

Requirement:

> Edit Comment 80.

API:

```http
PATCH /comments/:commentId
```

Reason:

The comment already has its own identity.

---

## Delete Comment

Requirement:

> Delete Comment 80.

API:

```http
DELETE /comments/:commentId
```

Again, no need to include the post ID.

---

## Like a Post

Requirement:

> Like Post 25.

API:

```http
POST /posts/:postId/likes
```

Authentication identifies the user.

The body is empty.

---

## Unlike a Post

```http
DELETE /posts/:postId/likes
```

Only the relationship is removed.

---

# Final API Design

```http
GET    /users/:userId/posts

GET    /categories/:categoryId/posts

GET    /posts/:postId/comments

POST   /posts/:postId/comments

PATCH  /comments/:commentId

DELETE /comments/:commentId

POST   /posts/:postId/likes

DELETE /posts/:postId/likes
```

This covers the relationship layer of the Blog API.

---

# Controller Responsibilities

Each controller should focus on one resource.

## CommentController

Handles:

```http
GET    /posts/:postId/comments

POST   /posts/:postId/comments

PATCH  /comments/:commentId

DELETE /comments/:commentId
```

Responsibilities:

- Read route parameters
    
- Validate input
    
- Call the service
    
- Return HTTP responses
    

---

## LikeController

Handles:

```http
POST /posts/:postId/likes

DELETE /posts/:postId/likes
```

Responsibilities:

- Read `postId`
    
- Get current user from authentication
    
- Call the service
    

---

# Service Responsibilities

The service contains business rules.

Example:

### CommentService

Rules:

- Post must exist.
    
- Comment cannot be empty.
    
- Only the comment owner can edit.
    
- Only the comment owner or an admin can delete.
    

---

### LikeService

Rules:

- Post must exist.
    
- User cannot like the same post twice.
    
- User can remove only their own like.
    

---

# Repository Responsibilities

The repository only interacts with the database.

Examples:

### CommentRepository

Conceptually:

```text
findByPostId()

create()

update()

delete()
```

---

### LikeRepository

Conceptually:

```text
exists()

create()

delete()
```

No business logic belongs here.

---

# Database Queries

Request:

```http
GET /posts/25/comments
```

Repository query:

```text
Find comments

WHERE postId = 25
```

---

Request:

```http
POST /posts/25/likes
```

Repository query:

```text
Insert

userId = Current User

postId = 25
```

---

Request:

```http
DELETE /posts/25/likes
```

Repository query:

```text
Delete

WHERE

userId = Current User

AND

postId = 25
```

Simple and efficient.

---

# Database Indexes

Good API design considers database performance.

## Comments

Frequently queried by:

```text
postId
```

Index:

```text
postId
```

---

Often sorted by newest:

```text
postId

createdAt
```

Compound index:

```text
(postId, createdAt)
```

---

## Likes

Common query:

```text
userId

postId
```

Create a **unique compound index**:

```text
(userId, postId)
```

Benefits:

- Prevents duplicate likes
    
- Speeds up lookups
    
- Speeds up deletes
    

---

## Posts

Frequently queried:

```text
authorId
```

Index:

```text
authorId
```

---

Frequently queried:

```text
categoryId
```

Index:

```text
categoryId
```

Notice how API design and indexing go hand in hand.

# Common Beginner Mistakes

## ❌ Putting Business Logic in Controllers

Bad:

```text
Controller

↓

Check ownership

↓

Validate business rules

↓

Query database
```

Controllers become difficult to maintain.

---

## ✅ Keep Controllers Thin

Better:

```text
Controller

↓

Service

↓

Repository
```

Each layer has one responsibility.

---

## ❌ Missing Database Indexes

API:

```http
GET /posts/:postId/comments
```

Without an index on `postId`, performance will degrade as the number of comments grows.

---

## ❌ Passing User ID in the Body

Bad:

```json
{
    "userId": 42
}
```

Good:

Read the user from the authenticated request.
