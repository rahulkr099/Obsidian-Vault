## A Beginner Project

Most tutorials follow this structure:

```text
Client
   ↓
Route
   ↓
Controller
   ↓
MongoDB
```

Example:

```javascript
POST /posts
```

The controller does everything:

```text
Receive request

↓

Validate input

↓

Generate slug

↓

Check user

↓

Upload image

↓

Save database

↓

Send notification

↓

Return response
```

Everything is inside one file.

---

## Example Controller

```javascript
async function createPost(req, res) {
    // Validate input

    // Check user

    // Generate slug

    // Upload image

    // Save post

    // Send notification

    // Return response
}
```

At first this looks fine.

Then your project grows.

## The Main Problem

The controller now has **too many responsibilities**.

It is:

- Reading HTTP requests
    
- Validating business rules
    
- Talking to MongoDB
    
- Calling external APIs
    
- Sending emails
    
- Handling permissions
    
- Formatting responses
    

This breaks an important software engineering principle.

---

## Single Responsibility Principle (SRP)

A class or function should have **one reason to change**.

A controller should only care about HTTP communication.

It should **not** know:

- how to publish a blog
    
- how to generate a slug
    
- how permissions work
    
- how notifications are sent
    

Those belong elsewhere.

---

## What Is Business Logic?

Business logic means:

> The rules that describe how your application should behave.

Example:

Publishing a post.

Rules:

```text
User must exist

↓

Post must exist

↓

User must own the post

↓

Post must be Draft

↓

Generate slug

↓

Set publishedAt

↓

Change status

↓

Notify followers

↓

Update analytics
```

These rules are **not** related to Express.

They are related to your application's behavior.

---

## Introducing the Service Layer

Professional architecture separates responsibilities.

```text
Client
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Each layer has one clear job.

---

## What Each Layer Does

### Route

Chooses which controller to call.

Example:

```text
POST /posts

↓

PostController.create()
```

---

### Middleware

Handles common tasks before the controller.

Examples:

- Authentication
    
- Logging
    
- Rate limiting
    
- Request validation
    

---

### Controller

The controller is very small.

Responsibilities:

- Read request
    
- Call service
    
- Return response
    

Example:

```javascript
const post = await postService.createPost(data);

return res.status(201).json(post);
```

Notice there is almost no business logic.

---

### Service

This is the brain of the application.

It contains:

- Business rules
    
- Workflows
    
- Permissions
    
- Validation beyond request format
    
- Coordination between repositories
    

Example:

```text
Create slug

↓

Check ownership

↓

Save post

↓

Notify users

↓

Return result
```

---

### Repository

Repository only talks to the database.

Example:

```javascript
findById()

create()

update()

delete()

findBySlug()
```

No business decisions are made here.

---

## Real Blog Example

Imagine a user clicks:

```text
Publish
```

The flow becomes:

```text
HTTP Request

↓

Controller

↓

PostService.publishPost()

↓

PostRepository.find()

↓

Validate ownership

↓

Update status

↓

NotificationService.send()

↓

Repository.save()

↓

Response
```

Notice how every layer has one purpose.

---

## Benefits of a Service Layer

### 1. Cleaner Controllers

Instead of 300 lines:

```javascript
async function publishPost() {
   // everything here
}
```

You get:

```javascript
async function publishPost(req, res) {

    const result = await postService.publishPost(
        req.user.id,
        req.params.id
    );

    res.json(result);
}
```

Very easy to read.

---

### 2. Easier Testing

You can test business logic without Express.

```text
Test:

publishPost()

No server

No routes

No HTTP
```

---

### 3. Reusable Logic

Both REST API and future GraphQL API can use the same service.

```text
REST Controller

↓

PostService

↑

GraphQL Resolver
```

No duplicated business logic.

---

### 4. Better Teamwork

Different developers can work independently.

```text
Frontend Team

↓

Controllers

↓

Backend Team

↓

Services

↓

Database Team

↓

Repositories
```

---

### 5. Easier Maintenance

If publishing rules change:

```text
Only PostService changes.
```

Controllers remain untouched.

---

## Beginner vs Professional

|Beginner|Professional|
|---|---|
|Fat controllers|Thin controllers|
|Business logic in controllers|Business logic in services|
|Database directly from controller|Repository pattern|
|Hard to test|Easy to test|
|Code duplication|Reusable services|
|Difficult maintenance|Easy maintenance|

---

## Common Misconception

Many beginners think:

> "Service Layer is just an extra file."

It isn't.

The Service Layer is where your application's **business decisions** live.

Without it, your project becomes harder to maintain as it grows.

---

## Key Takeaways

- Controllers should handle **HTTP**, not business logic.
    
- Business rules belong in the **Service Layer**.
    
- Repositories only interact with the **database**.
    
- Separating responsibilities makes your code cleaner, easier to test, and easier to scale.
    
- Professional backend applications rely on this layered architecture to manage complexity.

## Mini Exercise

For each task below, decide which layer should handle it:

|Task|Layer|
|---|---|
|Read `req.body`|?|
|Check if the user owns a post|?|
|Find a post by ID in MongoDB|?|
|Return `201 Created`|?|
|Generate a slug|?|

**Answers:**

- Read `req.body` → **Controller**
    
- Check ownership → **Service**
    
- Find post by ID → **Repository**
    
- Return `201 Created` → **Controller**
    
- Generate slug → **Service**
