# Module 1 — Lesson 1.2: Identifying Business Logic

> **Goal:** Learn how to recognize business logic and decide whether code belongs in the Controller, Service, Repository, or Middleware.

This is one of the most important backend skills. Many interview questions indirectly test this ability.

---

# What is Business Logic?

Business logic is **the rules that make your application behave correctly**.

Think of it like this:

> If someone changed how the business works tomorrow, **which code would you need to change?**

That code is usually business logic.

---

## Example 1 — Blog Application

Requirement:

> Only the owner of a post can publish it.

Where should this rule go?

```text
Controller ❌

Service ✅

Repository ❌
```

Why?

Because it is a **business rule**, not an HTTP concern or a database concern.

---

## Example 2 — URL Shortener

Requirement:

> Premium users can create custom short URLs.

Where does this belong?

```text
Controller ❌

Service ✅

Repository ❌
```

The service decides whether the user is allowed.

---

## Example 3 — Todo App

Requirement:

> Completed tasks cannot be edited.

Again:

```text
Controller ❌

Service ✅
```

# A Simple Trick

Whenever you hear words like:

- only
    
- must
    
- cannot
    
- should
    
- allowed
    
- required
    
- maximum
    
- minimum
    
- before
    
- after
    
- if
    
- when
    

you're probably looking at **business logic**.

Examples:

```text
User must verify email.

Order cannot be cancelled after shipping.

Student must enroll before taking exams.

Driver must have a valid license.

Coupon expires after 30 days.
```

These are all service-layer responsibilities.

# What Is NOT Business Logic?

Let's compare.

## Controller Responsibilities

The controller handles HTTP.

Example:

```javascript
const title = req.body.title;
const id = req.params.id;

const result = await postService.publishPost(id);

res.json(result);
```

Controller responsibilities:

- Read `req.body`
    
- Read `req.params`
    
- Read `req.query`
    
- Read headers
    
- Call service
    
- Return response
    

Nothing more.

---

## Middleware Responsibilities

Middleware handles shared request processing.

Examples:

```text
Authentication

↓

Logging

↓

Rate limiting

↓

Request validation

↓

CORS

↓

JWT verification
```

Notice that these are **technical concerns**, not business rules.

---

## Repository Responsibilities

Repository only communicates with the database.

Example:

```javascript
findById(id)

create(data)

update(id, data)

delete(id)
```

Repository should never decide:

```text
Can the user publish?

Is the coupon valid?

Is the order cancelled?
```

Those are business decisions.

# Thinking Like an Engineer

Instead of asking:

> "Where should I write this code?"

Ask:

> "Whose responsibility is this?"

---

Example:

```text
Read URL parameter
```

Who owns HTTP?

Controller.

---

Example:

```text
Generate a unique slug
```

Who owns business rules?

Service.

---

Example:

```text
Update MongoDB
```

Who owns persistence?

Repository.

# Common Mistakes Beginners Make

### Mistake 1

Checking ownership inside the controller.

```javascript
if (post.author !== user.id) {
    ...
}
```

Better:

```javascript
await postService.publishPost(user.id, postId);
```

The service decides whether publishing is allowed.

---

### Mistake 2

Using `req` inside the service.

Bad:

```javascript
postService.publish(req);
```

Why?

The service now depends on Express.

Good:

```javascript
postService.publishPost({
    userId,
    postId
});
```

The service receives only the data it needs.

---

### Mistake 3

Putting business rules inside the repository.

Bad:

```javascript
if (user.role !== "admin") {
    throw Error();
}

await Post.updateOne(...);
```

The repository should not know about roles or permissions.

Its job is simply to perform database operations.

# Mental Checklist

Whenever you write new code, ask yourself:

|Question|Layer|
|---|---|
|Am I reading an HTTP request?|Controller|
|Am I enforcing a business rule?|Service|
|Am I querying the database?|Repository|
|Am I authenticating or validating the request format?|Middleware|
|Am I sending an HTTP response?|Controller|

If you can't answer clearly, the code is probably in the wrong place.

---

# Interview Insight

A common interview question is:

> "Where should authorization logic go?"

A strong answer is:

> **Authentication** (verifying who the user is) is usually handled by middleware. **Authorization** (checking whether the authenticated user is allowed to perform an action) belongs in the service layer because it is a business rule.

---

# Key Takeaways

- Business logic consists of the rules that define how your application behaves.
    
- Controllers manage HTTP requests and responses only.
    
- Services contain business rules, workflows, and authorization decisions.
    
- Repositories perform database operations and nothing else.
    
- Middleware handles cross-cutting concerns like authentication and request validation.
    
- Asking **"Whose responsibility is this?"** is the fastest way to place code in the correct layer.

## Mini Exercise

Decide which layer each task belongs to.

|Task|Your Answer|
|---|---|
|Read `req.query.page`|?|
|Check whether a coupon has expired|?|
|Insert a new order into MongoDB|?|
|Verify JWT token|?|
|Return HTTP 403|?|
|Ensure a user cannot enroll in the same course twice|?|

**Answers:**

- Read `req.query.page` → **Controller**
    
- Check whether a coupon has expired → **Service**
    
- Insert a new order into MongoDB → **Repository**
    
- Verify JWT token → **Middleware**
    
- Return HTTP 403 → **Controller**
    
- Ensure a user cannot enroll in the same course twice → **Service**
