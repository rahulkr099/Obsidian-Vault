# Module 1 — Lesson 1.3: Fat Controllers vs Thin Controllers

> **Goal:** Learn how professional backend engineers keep controllers small, readable, and easy to maintain.

This lesson is one of the biggest mindset shifts you'll make as a backend developer.

---

# What Is a Fat Controller?

A **fat controller** is a controller that does much more than handling HTTP requests.

Instead of just receiving a request and sending a response, it starts making business decisions, querying the database, validating rules, sending emails, and much more.

Example:

```text
Controller

↓

Validate input

↓

Check permissions

↓

Query database

↓

Generate slug

↓

Upload image

↓

Send email

↓

Update analytics

↓

Return response
```

One function is doing everything.

---

# Why Fat Controllers Are Bad

Imagine your project starts small.

```javascript
POST /posts
```

At first, your controller might only have 20 lines.

After a few months, new features are added.

- Categories
    
- Tags
    
- Drafts
    
- Notifications
    
- Search
    
- Image uploads
    
- Analytics
    
- Activity logs
    
- Admin approval
    

Now the same controller becomes:

```text
500+ lines

Many if-else blocks

Many database queries

Several API calls
```

Finding bugs becomes difficult.

---

# Example of a Fat Controller

```javascript
async function publishPost(req, res) {
    const postId = req.params.id;
    const userId = req.user.id;

    const post = await Post.findById(postId);

    if (!post) {
        return res.status(404).json({
            message: "Post not found"
        });
    }

    if (post.author.toString() !== userId) {
        return res.status(403).json({
            message: "Not allowed"
        });
    }

    if (post.status === "published") {
        return res.status(400).json({
            message: "Already published"
        });
    }

    post.slug = generateSlug(post.title);

    post.status = "published";
    post.publishedAt = new Date();

    await post.save();

    await Notification.create({
        user: userId,
        message: "Post published"
    });

    res.json(post);
}
```

At first glance, this looks okay.

But notice what it is doing.

---

# Count the Responsibilities

The controller is:

✅ Reading request

```text
req.params
```

✅ Checking permissions

```text
author === user
```

✅ Applying business rules

```text
Already published?
```

✅ Generating slug

```text
generateSlug()
```

✅ Updating database

```text
save()
```

✅ Creating notification

```text
Notification.create()
```

✅ Returning response

Too many jobs.

---

# The Single Responsibility Principle

Remember SRP:

> A class or function should have only one reason to change.

Ask yourself:

If tomorrow the publishing rules change...

Should the controller change?

**No.**

If tomorrow notification logic changes...

Should the controller change?

**No.**

If tomorrow slug generation changes...

Should the controller change?

**No.**

The controller should only change if the HTTP API changes.

---

# What Is a Thin Controller?

A **thin controller** does only three things.

```text
Read Request

↓

Call Service

↓

Return Response
```

That's it.

---

# Professional Version

```javascript
async function publishPost(req, res) {

    const result = await postService.publishPost({
        userId: req.user.id,
        postId: req.params.id
    });

    res.json(result);

}
```

Beautiful.

Only a few lines.

Very easy to read.

---

# Where Did Everything Go?

All business logic moved into the service.

```text
Controller

↓

PostService.publishPost()

↓

Repository

↓

Database
```

---

# Inside the Service

The service now owns the workflow.

```text
Find post

↓

Check ownership

↓

Validate status

↓

Generate slug

↓

Update post

↓

Create notification

↓

Return updated post
```

Notice that this is exactly what business logic should look like.

---

# Real Flow

```text
HTTP Request

↓

Controller

↓

PostService

↓

PostRepository

↓

MongoDB
```

The controller no longer knows how publishing works.

It simply asks:

> "PostService, please publish this post."

# Another Example

## Beginner Login Controller

```javascript
async function login(req, res) {

    const user = await User.findOne({
        email: req.body.email
    });

    if (!user) {
        return res.status(404).json(...);
    }

    const match = await bcrypt.compare(
        req.body.password,
        user.password
    );

    if (!match) {
        return res.status(401).json(...);
    }

    const token = jwt.sign(...);

    res.json(token);

}
```

Looks familiar?

Many tutorials teach this.

---

## Professional Login Controller

```javascript
async function login(req, res) {

    const result = await authService.login({
        email: req.body.email,
        password: req.body.password
    });

    res.json(result);

}
```

Almost nothing remains.

# Benefits of Thin Controllers

## 1. Easy to Read

Instead of reading 300 lines...

You read:

```javascript
await postService.publishPost(...)
```

Immediately understandable.

---

## 2. Easy to Test

Controllers don't need complicated tests.

You only verify:

```text
Did it call the service?

↓

Did it return the correct response?
```

Business logic is tested separately.

---

## 3. Easier Refactoring

Imagine changing:

```text
Slug generation
```

Only:

```text
PostService
```

changes.

The controller stays untouched.

---

## 4. Reusable

Suppose tomorrow your company builds:

- REST API
    
- GraphQL API
    
- CLI tool
    
- Background worker
    

All can call:

```text
PostService.publishPost()
```

One business implementation.

Multiple interfaces.

---

# A Simple Rule

If your controller starts asking questions like:

```text
Does the user own this?

Is this already published?

Can this order be cancelled?

Has the coupon expired?

Should notification be sent?
```

You're writing business logic.

Move it into the service.

---

# What Should Stay in the Controller?

Controllers should only:

✔ Read request

```javascript
req.body
req.params
req.query
req.headers
```

✔ Call service

```javascript
await service.method(...)
```

✔ Return response

```javascript
res.json(...)

res.status(...)
```

Nothing more.

---

# What Should Never Stay in the Controller?

❌ Permission checks

❌ Pricing rules

❌ Discount calculations

❌ Workflow decisions

❌ Email logic

❌ Slug generation

❌ Inventory updates

❌ Database transactions

❌ Multiple repository coordination

These belong in services.

---

# Interview Tip

Suppose an interviewer asks:

> "How do you know a controller has become too large?"

A good answer:

> "When it starts containing business rules, permission checks, workflow logic, multiple database operations, or calls to external services, it's no longer acting as a controller. Those responsibilities should move into the Service Layer, leaving the controller responsible only for HTTP request handling and response generation."

This shows you understand architecture, not just coding.

---

# Best Practices

✅ Keep controllers under roughly **20–40 lines** in most cases.

✅ One controller method should represent **one API endpoint**.

✅ Controllers should depend on services, not directly on database models.

✅ Pass only the required data to services, not the entire `req` object.

---

# Summary

|Fat Controller ❌|Thin Controller ✅|
|---|---|
|Business rules|Calls service|
|Database queries|Reads request|
|Permission checks|Returns response|
|Workflow logic|Handles HTTP only|
|Hard to test|Easy to test|
|Large functions|Small functions|
|Hard to maintain|Easy to maintain|

# Mini Exercise

For each line below, decide whether it belongs in the **Controller** or the **Service**.

|Code|Layer|
|---|---|
|`const id = req.params.id`|?|
|Check whether the user owns the post|?|
|`res.status(200).json(post)`|?|

**Answers:**

- `res.status(200).json(post)` → **Controller**

- Decide whether the post can be published → **Service**
    
- Call `postService.publishPost()` → **Controller**
