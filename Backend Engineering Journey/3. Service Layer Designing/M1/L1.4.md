# Module 1 — Lesson 1.4: Putting It All Together

> **Goal:** Build a complete mental model of the backend request flow and learn a simple framework to decide where every piece of code belongs.

By the end of this lesson, you should be able to look at almost any backend feature and immediately know which layer is responsible for each task.

---

# The Complete Backend Flow

Let's follow a real request.

A user clicks **Publish Post** in a blog application.

```text
Client
   │
   ▼
Router
   │
   ▼
Middleware
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Database
```

Every layer has exactly **one responsibility**.

---

# Step 1 — Client

The frontend sends:

```http
POST /posts/123/publish
Authorization: Bearer <token>
```

The client doesn't know anything about business rules.

It simply requests:

> "Please publish this post."

---

# Step 2 — Router

The router maps the URL.

```javascript
router.post(
    "/posts/:id/publish",
    authenticate,
    postController.publishPost
);
```

The router decides:

> Which controller should handle this request?

Nothing else.

---

# Step 3 — Middleware

Middleware performs common tasks.

Example:

```text
Verify JWT

↓

Extract user

↓

Attach user to req

↓

Continue
```

After middleware:

```javascript
req.user = {
    id: "user123",
    role: "author"
};
```

Notice:

The middleware **doesn't decide** whether the user is allowed to publish.

It only proves who the user is.

---

# Authentication vs Authorization

This is a common interview topic.

## Authentication

Question:

> Who are you?

Example:

```text
Verify JWT

↓

Find user

↓

Attach req.user
```

Usually handled by middleware.

---

## Authorization

Question:

> Are you allowed to do this?

Example:

```text
Does this user own the post?

↓

Is this user an admin?
```

Usually handled inside the service.

---

# Step 4 — Controller

The controller receives the request.

```javascript
async function publishPost(req, res) {

    const result = await postService.publishPost({
        userId: req.user.id,
        postId: req.params.id
    });

    res.json(result);

}
```

Notice how small it is.

Responsibilities:

- Read request
    
- Call service
    
- Return response
    

---

# Step 5 — Service

This is where the application starts thinking.

```text
Find post

↓

Check ownership

↓

Check draft status

↓

Generate slug

↓

Set publishedAt

↓

Update status

↓

Create activity

↓

Send notification

↓

Return updated post
```

Everything here is business logic.

---

# Step 6 — Repository

Repository talks to MongoDB.

Example:

```javascript
findById()

update()

create()

delete()
```

The repository does **not** ask:

- Can this post be published?
    
- Is the user the owner?
    
- Should a notification be sent?
    

It simply executes database operations.

---

# Step 7 — Database

MongoDB stores the data.

Nothing more.

---

# A Decision Framework

Whenever you write code, ask these questions in order.

## Question 1

Am I reading something from HTTP?

Examples:

- `req.body`
    
- `req.params`
    
- `req.query`
    
- `req.headers`
    

Answer:

```text
Controller
```

---

## Question 2

Am I enforcing a business rule?

Examples:

```text
Only premium users

Cannot publish twice

Maximum five projects

Order already shipped
```

Answer:

```text
Service
```

---

## Question 3

Am I communicating with MongoDB?

Examples:

```javascript
find()

findOne()

create()

updateOne()

deleteOne()
```

Answer:

```text
Repository
```

---

## Question 4

Am I authenticating the request?

Examples:

```text
Verify JWT

Decode token

Attach user
```

Answer:

```text
Middleware
```

---

## Question 5

Am I returning JSON or an HTTP status?

Examples:

```javascript
res.status(201)

res.json()

res.send()
```

Answer:

```text
Controller
```

# Common Beginner Mistakes

## Mistake 1

Passing `req` directly into services.

Bad:

```javascript
postService.publish(req);
```

Good:

```javascript
postService.publish({
    userId: req.user.id,
    postId: req.params.id
});
```

Services should not depend on Express.

---

## Mistake 2

Using Mongoose models inside controllers.

Bad:

```javascript
const post = await Post.findById(id);
```

Good:

```javascript
const post = await postRepository.findById(id);
```

Controllers should talk to services, not the database.

---

## Mistake 3

Putting permissions in repositories.

Bad:

```javascript
if (user.role !== "admin") {
    throw new Error();
}
```

Repositories shouldn't know about roles.

---

## Mistake 4

Sending emails from controllers.

Bad:

```javascript
await emailService.send(...);
```

Better:

```text
Controller

↓

OrderService

↓

EmailService
```

The service decides **when** an email should be sent.

# The Golden Rule

When you're unsure where code belongs, ask:

> **What responsibility does this code have?**

If it...

- Handles HTTP → **Controller**
    
- Enforces business rules → **Service**
    
- Talks to the database → **Repository**
    
- Handles authentication or shared request concerns → **Middleware**
    
- Maps URLs to handlers → **Router**
    

This simple question will guide most of your architectural decisions.
