# Rule 1 — Use Transactions for One Business Action

A transaction should represent **one complete business action**.

✅ Good

```text
Place Order

↓

Create Order

↓

Reduce Stock

↓

Create Payment
```

Everything belongs to one workflow.

---

# Rule 2 — Don't Use Transactions for Everything

❌ Unnecessary

```text
Create Category
```

One database operation doesn't usually need a transaction.

Use transactions only when **multiple related operations** must succeed together.

---

# Rule 3 — Keep Transactions Short

Good:

```text
Start Transaction

↓

Database Operations

↓

Commit
```

Avoid doing slow work inside a transaction.

Example:

```text
Upload File

↓

Call External API

↓

Wait 30 Seconds
```

These can keep database resources locked longer than necessary.

---

# Rule 4 — Don't Mix Unrelated Work

Bad:

```text
Create Order

↓

Update User Theme

↓

Send Newsletter
```

Only include operations that belong to the same business action.

---

# Rule 5 — Think Before Coding

Ask yourself:

```text
Is this one business action?

↓

Will partial success cause problems?

↓

Do all database changes
need to stay consistent?
```

If the answer is **Yes**, use a transaction.

# Common Mistakes

## ❌ Transaction for Every Query

Transactions have overhead.

Don't use them unless they're needed.

---

## ❌ Forgetting Failure Cases

Always ask:

> **"What happens if step 3 fails?"**

If the answer is "the system becomes inconsistent," a transaction is probably needed.

---

## ❌ Long Transactions

The longer a transaction runs, the more database resources it may hold.

Keep them focused and as short as practical.

---

# Interview Questions

### Q1. When should you use a transaction?

**Answer:**

> When one business action performs multiple related database operations that must all succeed or all fail.

---

### Q2. Should every database operation use a transaction?

**Answer:**

> No. Single, independent operations usually don't need one. Transactions are mainly for multi-step workflows where consistency matters.

---

### Q3. What is the difference between a commit and a rollback?

**Answer:**

- **Commit** → Permanently save all changes.
    
- **Rollback** → Undo all changes made during the transaction.

# One-Page Cheat Sheet

|Concept|Meaning|
|---|---|
|**Transaction**|Multiple operations treated as one unit|
|**Commit**|Save all changes|
|**Rollback**|Undo all changes|
|**Use When**|Multi-step business workflow|
|**Avoid When**|Single independent operation|
