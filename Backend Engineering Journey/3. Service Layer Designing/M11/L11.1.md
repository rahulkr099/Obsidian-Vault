# Lesson 11.1 — Why Services Call Multiple Repositories

> **Goal:** Understand why one service often needs multiple repositories.

---

# One Repository

Simple feature:

```text
PostService

↓

PostRepository
```

Creating a post only affects posts.

One repository is enough.

---

# Multiple Repositories

Requirement:

> User publishes a blog post.

Workflow:

```text
PostService

↓

PostRepository

↓

ActivityRepository

↓

NotificationRepository
```

The service coordinates all three.

---

# Another Example

Requirement:

> Customer places an order.

```text
OrderService

↓

OrderRepository

↓

InventoryRepository

↓

PaymentRepository
```

Each repository manages its own data.

---

# Responsibilities

## Service

Responsible for:

- Business workflow
    
- Calling repositories
    
- Coordinating operations
    

---

## Repository

Responsible for:

- Reading data
    
- Writing data
    
- Database queries
    

Nothing more.

---

# Why Not Repository-to-Repository?

❌ Bad

```text
OrderRepository

↓

InventoryRepository
```

Repositories should not call each other.

The **Service Layer** coordinates them.

---

# Professional Flow

```text
Controller

↓

OrderService

↓

OrderRepository

InventoryRepository

PaymentRepository
```

The service is the orchestrator.

---

# Interview Question

**Q:** Why should a service call multiple repositories instead of repositories calling each other?

**Good Answer:**

> Each repository should manage only one type of data. The Service Layer coordinates multiple repositories because it owns the business workflow, keeping repositories simple and loosely coupled.

---

# Key Takeaways

- One service can call many repositories.
    
- Repositories should never call each other.
    
- Services coordinate business workflows.
    
- Repositories focus only on data access.
