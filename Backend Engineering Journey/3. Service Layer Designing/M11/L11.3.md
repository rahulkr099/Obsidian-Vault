# Module 11 — Lesson 11.3: Transactions with Multiple Repositories ⭐⭐⭐⭐⭐

> **Goal:** Learn how transactions keep multiple repository operations consistent.

When a service calls multiple repositories, those operations often belong to **one business action**.

If one operation fails, the others should usually be rolled back.

---

# Example — Place Order

Requirement:

> Customer places an order.

Workflow:

```text
OrderService

↓

OrderRepository
(Create order)

↓

InventoryRepository
(Reduce stock)

↓

PaymentRepository
(Create payment)
```

These repositories should participate in **one transaction**.

---

# Success Case

```text
Create Order ✅

↓

Reduce Stock ✅

↓

Create Payment ✅

↓

Commit
```

Everything succeeds.

---

# Failure Case

```text
Create Order ✅

↓

Reduce Stock ✅

↓

Create Payment ❌

↓

Rollback
```

The transaction undoes the previous operations.

The database returns to its original state.

---

# Who Starts the Transaction?

The **Service Layer**.

```text
Start Transaction

↓

Call Repository A

↓

Call Repository B

↓

Call Repository C

↓

Commit / Rollback
```

Repositories should **use** the transaction, not create it.

---

# Repository Responsibility

A repository should simply perform its query.

Example:

```text
Save Order

Update Stock

Create Payment
```

It shouldn't decide:

- When to commit
    
- When to rollback
    

Those decisions belong to the service.

---

# Best Practices

✅ Service starts and controls the transaction.

✅ Repositories execute database operations.

✅ Commit only after every step succeeds.

✅ Roll back if any step fails.

---

# Interview Question

**Q:** Who should manage a transaction when multiple repositories are involved?

**Good Answer:**

> The Service Layer should manage the transaction because it owns the complete business workflow. Repositories simply execute database operations within the transaction.

---

# Key Takeaways

- One business workflow can involve multiple repositories.
    
- The **Service Layer** controls the transaction.
    
- Repositories remain focused on data access.
    
- Commit on success, rollback on failure.
