# Module 11 — Lesson 11.4: Orchestration Best Practices ⭐⭐⭐⭐⭐

> **Goal:** Learn the practical rules for coordinating multiple repositories in a clean backend architecture.

This lesson summarizes Module 11.

---

# Rule 1 — Services Orchestrate

The service owns the workflow.

```text
Controller

↓

OrderService

↓

OrderRepository

InventoryRepository

PaymentRepository
```

The service decides:

- What happens first
    
- What happens next
    
- When the workflow is complete
    

---

# Rule 2 — Repositories Stay Focused

Each repository should manage **one entity**.

Example:

```text
UserRepository

↓

Users only
```

```text
PostRepository

↓

Posts only
```

Avoid mixing unrelated entities in one repository.

---

# Rule 3 — Repositories Never Call Each Other

❌ Bad

```text
PostRepository

↓

UserRepository
```

✅ Good

```text
PostService

↓

PostRepository

UserRepository
```

The service coordinates them.

---

# Rule 4 — Keep Business Rules in Services

Requirement:

> Publish a post.

The service decides:

```text
Can publish?

↓

Update post

↓

Create activity

↓

Notify users
```

Repositories simply execute queries.

---

# Rule 5 — Use Transactions When Needed

If multiple repositories modify related data:

```text
Repository A

↓

Repository B

↓

Repository C
```

Wrap the workflow in a **transaction** so everything succeeds or rolls back together.

---

# Professional Architecture

```text
Route

↓

Middleware

↓

Controller

↓

Service

↓

Repository A

Repository B

Repository C

↓

Database
```

Each layer has one responsibility.

---

# Common Mistakes

## ❌ Fat Repositories

```text
Repository

↓

Business Rules

↓

Permissions

↓

Validation
```

Repositories should only access data.

---

## ❌ God Services

```text
UserService

↓

Posts

Orders

Payments

Emails
```

Split services by business domain.

---

## ❌ Repository-to-Repository Calls

This creates tight coupling and makes the code harder to maintain.

Always let the **Service Layer** coordinate.

---

# Interview Questions

### Q1. Can one service use multiple repositories?

**Answer:**

> Yes. A service coordinates multiple repositories to complete a single business workflow.

---

### Q2. Should repositories call each other?

**Answer:**

> No. Repositories should remain independent. The Service Layer is responsible for orchestration.

---

### Q3. Where should transactions be managed?

**Answer:**

> In the Service Layer, because it owns the complete business workflow across multiple repositories.

# Practice Exercise

Design the workflow for:

> **A customer places an order.**

Expected orchestration:

```text
OrderService

↓

OrderRepository
(Create Order)

↓

InventoryRepository
(Update Stock)

↓

PaymentRepository
(Create Payment)

↓

Commit Transaction
```

Notice how **repositories never communicate with each other**. The **OrderService** coordinates the entire workflow.
