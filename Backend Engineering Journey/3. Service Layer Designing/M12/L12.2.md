# Module 12 — Lesson 12.2: Custom Error Classes ⭐⭐⭐⭐⭐

> **Goal:** Learn why professional backends use custom error classes instead of generic errors.

---

# The Problem with Generic Errors

❌ Bad

```javascript
throw new Error("Something went wrong");
```

Questions:

- What went wrong?
    
- Was it a validation problem?
    
- Was the user unauthorized?
    
- Was the resource missing?
    

The error doesn't tell us.

---

# Use Meaningful Errors

Instead, throw errors that describe the problem.

```text
NotFoundError

ForbiddenError

ConflictError

ValidationError

UnauthorizedError
```

Now anyone reading the code immediately understands what happened.

---

# Example 1 — Post Not Found

Instead of:

```javascript
throw new Error("Post not found");
```

Use:

```javascript
throw new NotFoundError("Post not found");
```

---

# Example 2 — Unauthorized Access

Requirement:

> User tries to edit another user's post.

```javascript
throw new ForbiddenError(
    "You do not own this post."
);
```

Much clearer than:

```javascript
throw new Error("Access denied");
```

---

# Example 3 — Duplicate Email

Requirement:

> User registers with an existing email.

```javascript
throw new ConflictError(
    "Email already exists."
);
```

The error clearly explains the business problem.

---

# Common Custom Errors

|Error|When to Use|
|---|---|
|`ValidationError`|Invalid input|
|`NotFoundError`|Resource doesn't exist|
|`UnauthorizedError`|User not logged in|
|`ForbiddenError`|User lacks permission|
|`ConflictError`|Resource already exists|

---

# Where Are They Thrown?

```text
Controller

↓

Service

↓

throw NotFoundError()

↓

Controller / Global Error Handler

↓

HTTP Response
```

The **Service** reports the problem.

The **Controller or Global Error Handler** decides how to respond.

---

# Best Practices

✅ Throw specific errors.

✅ Make error names describe the business problem.

✅ Avoid generic `Error` for expected business failures.

---

# Interview Question

**Q:** Why use custom error classes instead of `Error`?

**Good Answer:**

> Custom error classes make errors more meaningful and easier to handle. Instead of checking error messages, the application can react based on the error type, such as `NotFoundError` or `ForbiddenError`, resulting in cleaner and more maintainable code.

---

# Key Takeaways

- Use **specific** error classes.
    
- Error names should describe the problem.
    
- Services throw business errors.
    
- Controllers or global error handlers convert them into HTTP responses.
