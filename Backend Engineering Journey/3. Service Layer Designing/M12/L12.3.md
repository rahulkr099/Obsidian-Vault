# Module 12 — Lesson 12.3: Error Flow (Service → Controller) ⭐⭐⭐⭐⭐

> **Goal:** Learn how errors travel through a professional backend application.

A common beginner mistake is handling errors everywhere.

Professional backends follow **one consistent error flow**.

---

# The Error Flow

```text
Client

↓

Controller

↓

Service

↓

Throw Error

↓

Global Error Handler

↓

HTTP Response
```

Each layer has one responsibility.

---

# Step 1 — Service Detects the Problem

Example:

> User tries to publish a post that doesn't exist.

The service checks:

```text
Post exists?

↓

No

↓

Throw NotFoundError
```

The service **does not** send an HTTP response.

It simply reports the business error.

---

# Step 2 — Controller

The controller calls the service.

```text
Call Service

↓

Success → Return Response

↓

Failure → Pass Error
```

The controller shouldn't decide **how** to handle every error.

It forwards the error to the global error handler.

---

# Step 3 — Global Error Handler

The global error handler converts business errors into HTTP responses.

Example:

```text
NotFoundError

↓

404 Not Found
```

```text
ForbiddenError

↓

403 Forbidden
```

```text
ValidationError

↓

400 Bad Request
```

---

# Complete Example

Requirement:

> Delete a post.

Flow:

```text
Controller

↓

PostService

↓

Post not found

↓

Throw NotFoundError

↓

Global Error Handler

↓

404 Response
```

Simple.

Consistent.

---

# Why Is This Better?

Without a global error handler:

```text
Controller A

↓

Error Handling

---------------

Controller B

↓

Error Handling

---------------

Controller C

↓

Error Handling
```

Lots of duplicated code.

With a global error handler:

```text
Controllers

↓

Global Error Handler
```

One place handles errors for the whole application.

---

# Responsibilities

|Layer|Responsibility|
|---|---|
|**Service**|Detect and throw business errors|
|**Controller**|Call service and forward errors|
|**Global Error Handler**|Convert errors into HTTP responses|

---

# Best Practices

✅ Services throw meaningful errors.

✅ Controllers stay thin.

✅ Use one global error handler.

✅ Keep error handling consistent across the application.

---

# Interview Question

**Q:** Why use a global error handler?

**Good Answer:**

> A global error handler centralizes error handling, avoids duplicated code in controllers, and ensures consistent HTTP responses across the application. Services focus on throwing business errors, while the global handler decides how to present them to the client.

---

# Key Takeaways

- Services **throw** errors.
    
- Controllers **forward** errors.
    
- Global error handlers **respond** to errors.
    
- Each layer has a single responsibility.
