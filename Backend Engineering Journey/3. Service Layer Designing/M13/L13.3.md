# Module 13 — Lesson 13.3: When to Extract a Domain Service ⭐⭐⭐⭐⭐

> **Goal:** Learn how to recognize when logic should be moved into its own Domain Service.

A common beginner question is:

> **"Should I create a new service for everything?"**

**No.**

Start simple. Extract a Domain Service only when it provides clear value.

---

# Sign 1 — Logic Is Repeated

Suppose you generate slugs in multiple places.

```text
PostService

↓

Generate Slug

----------------

CategoryService

↓

Generate Slug

----------------

ProductService

↓

Generate Slug
```

Extract:

```text
SlugService
```

Now everyone reuses the same logic.

---

# Sign 2 — One Responsibility Emerges

Suppose `PostService` contains:

```text
Create Post

↓

Resize Image

↓

Upload Image

↓

Generate Thumbnail
```

Image processing is becoming its own responsibility.

Extract:

```text
ImageService
```

---

# Sign 3 — Multiple Services Need It

Suppose both:

```text
UserService

↓

Send Email
```

and

```text
OrderService

↓

Send Email
```

need email functionality.

Create:

```text
EmailService
```

instead of duplicating code.

---

# Don't Extract Too Early

❌ Bad

```text
NameFormatterService

PhoneFormatterService

AgeCalculatorService
```

Creating tiny services for every helper can overcomplicate your application.

Extract only when the logic is:

- Reusable
    
- Significant
    
- A clear business responsibility
    

---

# Simple Decision Rule

Ask yourself:

```text
Is this logic reused?

↓

Does it have one clear responsibility?

↓

Will multiple services use it?
```

If most answers are **Yes**, consider creating a Domain Service.

---

# Best Practices

✅ Extract **shared business logic**.

✅ Keep feature services focused.

✅ Don't create unnecessary services.

---

# Interview Question

**Q:** When should you extract a Domain Service?

**Good Answer:**

> I extract a Domain Service when the logic has a single responsibility, is reused across multiple services, or has grown large enough to deserve its own abstraction. I avoid creating separate services for trivial or one-time logic.

---

# Key Takeaways

- Don't create services too early.
    
- Extract when logic is **shared** or **growing**.
    
- Keep services focused on one responsibility.
    
- Favor simplicity over unnecessary abstraction.
