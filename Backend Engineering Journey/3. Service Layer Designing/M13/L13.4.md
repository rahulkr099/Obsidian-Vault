# Module 13 — Lesson 13.4: Domain Service Best Practices ⭐⭐⭐⭐⭐

> **Goal:** Learn the practical rules for designing clean and reusable Domain Services.

This lesson summarizes Module 13.

---

# Rule 1 — One Service, One Responsibility

✅ Good

```text
EmailService

↓

Send emails
```

❌ Bad

```text
EmailService

↓

Send emails

↓

Generate PDFs

↓

Upload files
```

Each Domain Service should have **one clear responsibility**.

---

# Rule 2 — Keep Feature Services Small

Instead of:

```text
PostService

↓

Generate Slug

↓

Resize Image

↓

Upload Image

↓

Send Notification

↓

Save Post
```

Use:

```text
PostService

↓

SlugService

↓

ImageService

↓

NotificationService
```

`PostService` coordinates the workflow.

---

# Rule 3 — Reuse, Don't Duplicate

If multiple services need the same logic:

```text
UserService

↓

Send Email

----------------

OrderService

↓

Send Email
```

Extract:

```text
EmailService
```

Write it once and reuse it.

---

# Rule 4 — Don't Over-Engineer

❌ Don't create a service for every small helper.

Bad:

```text
DateFormatterService

StringFormatterService

NumberFormatterService
```

Create a Domain Service only when it represents a meaningful business capability.

---

# Rule 5 — Services Can Work Together

It's normal for one service to use another.

Example:

```text
PostService

↓

SlugService

↓

NotificationService
```

Each service remains focused while working together.

---

# Common Mistakes

### ❌ God Service

```text
AppService

↓

Posts

Users

Orders

Emails

Payments
```

Too many responsibilities.

---

### ❌ Duplicate Logic

Copying the same email or slug generation code into multiple services.

---

### ❌ Tiny Unnecessary Services

Creating dozens of services that are used only once.

---

# Interview Questions

### Q1. What is the Single Responsibility Principle for Domain Services?

**Answer:**

> A Domain Service should focus on one business responsibility, such as sending emails or generating slugs, and should not mix unrelated concerns.

---

### Q2. When should multiple services use the same Domain Service?

**Answer:**

> When they share the same business capability, such as sending emails, uploading files, or generating slugs. This avoids code duplication and keeps the architecture consistent.

---

### Q3. Can one service call another service?

**Answer:**

> Yes. It's common for a feature service like `PostService` to coordinate reusable domain services such as `SlugService` or `NotificationService`, as long as responsibilities remain clear.

# Practice Exercise

Design the services for this feature:

> **A user uploads a profile picture.**

A clean design could be:

```text
ProfileService

↓

ImageService
(Resize image)

↓

StorageService
(Upload file)

↓

UserRepository
(Update profile)
```

Notice how **`ProfileService` coordinates the workflow**, while each Domain Service handles its own specialized responsibility.
