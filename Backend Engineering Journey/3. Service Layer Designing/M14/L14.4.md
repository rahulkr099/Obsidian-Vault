# Module 14 — Lesson 14.4: Cross-Service Communication Best Practices ⭐⭐⭐⭐⭐

> **Goal:** Learn the practical rules for designing clean communication between services.

This lesson summarizes Module 14.

---

# Rule 1 — Call a Service Only When It Owns the Responsibility

✅ Good

```text
PostService

↓

NotificationService
```

`NotificationService` owns notifications.

---

❌ Bad

```text
PostService

↓

SMTP Code

↓

Send Email
```

Email logic doesn't belong in `PostService`.

---

# Rule 2 — Avoid Circular Dependencies

❌ Bad

```text
UserService

↓

OrderService

↓

UserService
```

✅ Good

```text
OrderService

↓

UserService
```

Keep dependencies **one-way**.

---

# Rule 3 — Pass DTOs, Not Entire Objects

❌ Bad

```javascript
notificationService.send(user);
```

The service receives unnecessary data.

---

✅ Good

```javascript
notificationService.send({
    userId,
    email
});
```

Pass only what the service needs.

---

# Rule 4 — Hide Implementation Details

`PostService` shouldn't know:

- SMTP
    
- Firebase
    
- AWS SES
    

It should only know:

```text
EmailService.send(dto)
```

---

# Rule 5 — Keep the Workflow in the Calling Service

Example:

```text
PostService

↓

Save Post

↓

NotificationService

↓

EmailService
```

`PostService` controls the workflow.

The other services perform their specialized responsibilities.

---

# Common Mistakes

### ❌ Duplicating Logic

```text
PostService

↓

Send Email

----------------

OrderService

↓

Send Email
```

Create one:

```text
EmailService
```

---

### ❌ Passing Large Objects

Instead of:

```javascript
notificationService.send(post);
```

Pass:

```javascript
notificationService.send({
    postId,
    title
});
```

Keep services loosely coupled.

---

# Interview Questions

### Q1. When should one service call another?

**Answer:**

> When the second service owns a different business responsibility, such as notifications, emails, or file storage.

---

### Q2. Why avoid circular dependencies?

**Answer:**

> They tightly couple services, make testing harder, and create maintenance problems. Dependencies should flow in one direction.

---

### Q3. Why pass DTOs instead of models?

**Answer:**

> DTOs transfer only the required data, reduce coupling, and prevent one service from depending on another service's internal data structure.

|Communication|Use DTOs|
|Implementation|Hide internal details|

# Practice Exercise

Design the communication for:

> **A customer places an order and receives a confirmation email.**

Expected design:

```text
OrderService

↓

OrderRepository

↓

EmailService.send(dto)
```

Notice that:

- `OrderService` owns the workflow.
    
- `EmailService` owns email delivery.
    
- Neither service knows the other's internal implementation.
