# Module 15 — Lesson 15.2: PermissionService ⭐⭐⭐⭐⭐

> **Goal:** Learn how a `PermissionService` centralizes authorization rules.

Instead of writing permission checks in every service, create one service responsible for permissions.

---

# Without PermissionService

```text
PostService

↓

Ownership Check

----------------

CommentService

↓

Ownership Check

----------------

TodoService

↓

Ownership Check
```

The same logic is repeated.

---

# With PermissionService

```text
PostService

↓

PermissionService

↓

PostRepository
```

```text
CommentService

↓

PermissionService

↓

CommentRepository
```

Every service asks the same `PermissionService`.

---

# Example Responsibilities

```text
PermissionService

↓

canView()

↓

canEdit()

↓

canDelete()

↓

canPublish()
```

Each method returns:

```text
Allow

OR

Deny
```

---

# Blog App Example

Requirement:

> User edits a post.

Workflow:

```text
PostService

↓

PermissionService.canEdit()

↓

Allowed?

↓

Update Post
```

`PostService` doesn't contain the permission logic itself.

---

# Why Is This Better?

Suppose the rule changes.

Old rule:

```text
Owner only
```

New rule:

```text
Owner

OR

Admin
```

Instead of updating every service, you update:

```text
PermissionService
```

Only one place changes.

---

# Best Practices

✅ Keep permission rules centralized.

✅ Reuse them across services.

✅ Keep repositories unaware of permissions.

---

# Interview Question

**Q:** Why create a `PermissionService`?

**Good Answer:**

> A `PermissionService` centralizes authorization rules so they are implemented once and reused across multiple services. This reduces duplication, keeps behavior consistent, and makes permission changes easier to maintain.

---

# Key Takeaways

- `PermissionService` owns authorization rules.
    
- Feature services reuse permission checks.
    
- Update permission logic in one place.
    
- Keep services cleaner and more maintainable.
