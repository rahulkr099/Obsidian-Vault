# Lesson 16.1 — What is Idempotency?

> **Goal:** Understand what it means for a service to be idempotent.

---

# Definition

An operation is **idempotent** if:

> **Performing it multiple times has the same final result as performing it once.**

---

# Example — Publish a Post

First request:

```text
publishPost()

↓

Status = Published
```

Second request:

```text
publishPost()

↓

Already Published

↓

No Change
```

The post is still published.

The final state is the same.

---

# Bad Example

Suppose every call creates a notification.

```text
publishPost()

↓

Notification Created
```

Call it again:

```text
publishPost()

↓

Another Notification Created
```

Now you've created duplicate notifications.

---

# Real Examples

### ✅ Idempotent

```text
Set Status = Published

Set User Role = Admin

Mark Task = Completed
```

Calling them again doesn't change the final state.

---

### ❌ Not Idempotent

```text
Create Order

Charge Credit Card

Increase Wallet Balance
```

Calling these twice may create duplicates.

---

# Why Is It Important?

Imagine a client sends:

```text
publishPost()
```

The server succeeds, but the response is lost.

The client retries the request.

If your service is idempotent:

```text
No Problem

↓

Same Final State
```

---

# Best Practices

✅ Design update operations to be safe for retries.

✅ Check the current state before changing it.

---

# Interview Question

**Q:** What is an idempotent service?

**Good Answer:**

> An idempotent service produces the same final state even if the same request is executed multiple times. This makes retries safe and prevents duplicate or inconsistent data.

---

# Key Takeaways

- Idempotency makes retries safe.
    
- Multiple identical requests should produce the same final state.
    
- Check the current state before making changes.
    
- This is especially important in distributed systems and APIs.
