# Module 16 — Lesson 16.2: Designing Idempotent Services ⭐⭐⭐⭐⭐

> **Goal:** Learn how to design service methods that are safe to retry.

The key idea is:

> **Before changing state, check the current state.**

---

# Example 1 — Publish Post

Requirement:

> Publish a post.

Workflow:

```text
Find Post

↓

Already Published?

↓

Yes → Return

↓

No → Publish
```

Calling `publishPost()` again doesn't change anything.

---

# Example 2 — Complete Task

Requirement:

> Complete a task.

Workflow:

```text
Find Task

↓

Already Completed?

↓

Yes → Return

↓

No → Complete
```

The task is completed only once.

---

# Example 3 — Verify Email

Requirement:

> Verify user email.

Workflow:

```text
Find User

↓

Already Verified?

↓

Yes → Return

↓

No → Verify
```

A second request doesn't change the result.

---

# The General Pattern

```text
Find Resource

↓

Check Current State

↓

Already Done?

↓

Yes → Return

↓

No → Perform Action
```

This pattern works for many update operations.

---

# Avoid This

❌ Bad

```text
publishPost()

↓

Always Update

↓

Always Send Notification
```

Every retry repeats the work.

---

# Better

```text
publishPost()

↓

Check State

↓

Update Only If Needed
```

Now retries are safe.

---

# Best Practices

✅ Check the current state first.

✅ Return success if the desired state already exists.

✅ Avoid creating duplicate side effects.

---

# Interview Question

**Q:** How do you design an idempotent service?

**Good Answer:**

> I first check the current state of the resource. If it is already in the desired state, I return without making changes. Otherwise, I perform the update. This makes repeated requests safe.

---

# Key Takeaways

- Check before updating.
    
- Don't repeat completed work.
    
- Make retries produce the same final state.
    
- This pattern is ideal for state-change operations.
