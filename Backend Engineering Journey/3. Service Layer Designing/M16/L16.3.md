# Module 16 — Lesson 16.3: Common Use Cases ⭐⭐⭐⭐⭐

> **Goal:** Learn where idempotency is important in real backend applications.

Not every API needs to be idempotent.

Focus on operations that may be **retried** or **accidentally repeated**.

---

# 1. Publish Post ✅

```text
publishPost()

↓

Already Published?

↓

Yes → Return

↓

No → Publish
```

Multiple requests produce the same final state.

---

# 2. Complete Task ✅

```text
completeTask()

↓

Already Completed?

↓

Yes → Return

↓

No → Complete
```

---

# 3. Verify Email ✅

```text
verifyEmail()

↓

Already Verified?

↓

Yes → Return

↓

No → Verify
```

---

# 4. Payment ❗

A payment **must not** be charged twice.

Bad:

```text
Retry

↓

Charge Card Again
```

Professional systems use an **idempotency key** so the same payment request is processed only once.

---

# 5. Create Order ❗

Bad:

```text
Retry

↓

Create Another Order
```

Instead, detect that the request has already been processed and return the existing result.

---

# When Is Idempotency Important?

Usually for operations like:

- Payment
    
- Order creation
    
- Email verification
    
- Publishing
    
- Completing tasks
    

These operations may be retried because of network failures or user actions.

---

# When Is It Less Important?

Example:

```text
Search Posts

↓

Get Profile
```

These are read operations.

Running them multiple times doesn't change data.

---

# Best Practices

✅ Make important state changes safe to retry.

✅ Prevent duplicate side effects (payments, orders, notifications).

---

# Interview Question

**Q:** Give some examples of idempotent operations.

**Good Answer:**

> Examples include publishing a post, completing a task, verifying an email, and updating a user's profile. These operations can safely be retried because repeating them does not change the final state.

> For operations like payments or order creation, idempotency is achieved using techniques such as idempotency keys to prevent duplicate processing.

---

# Key Takeaways

- Many update operations should be idempotent.
    
- Payments and order creation require extra care.
    
- Prevent duplicate side effects.
    
- Design with retries in mind.
