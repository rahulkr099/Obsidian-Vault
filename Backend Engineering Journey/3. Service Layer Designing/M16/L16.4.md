# Rule 1 — Check Before Updating

Always check the current state.

```text
Find Resource

↓

Already in desired state?

↓

Yes → Return

↓

No → Update
```

Example:

```text
publishPost()

↓

Already Published?

↓

Yes → Return

↓

No → Publish
```

---

# Rule 2 — Prevent Duplicate Side Effects

❌ Bad

```text
Retry

↓

Send Email Again

↓

Create Notification Again
```

✅ Better

```text
Retry

↓

Detect Previous Success

↓

Don't Repeat
```

Avoid duplicate:

- Emails
    
- Notifications
    
- Payments
    
- Orders
    

---

# Rule 3 — Use Idempotency Keys When Needed

For operations like:

- Payments
    
- Order creation
    

Clients can send:

```text
Idempotency-Key:
abc123
```

If the same key arrives again:

```text
Return Previous Result

↓

Don't Process Again
```

This is a common approach in payment systems.

---

# Rule 4 — Design for Retries

Never assume:

```text
The request will only arrive once.
```

Network failures happen.

Users double-click buttons.

Mobile apps retry automatically.

Your service should handle these safely.

---

# Rule 5 — Keep Business State Consistent

The goal is:

```text
1 Request

↓

or

10 Identical Requests

↓

Same Final State
```

That's what idempotency guarantees.

# Interview Questions

### Q1. What is idempotency?

**Answer:**

> Idempotency means that executing the same operation multiple times results in the same final state as executing it once.

---

### Q2. Why is idempotency important?

**Answer:**

> It allows clients to safely retry requests after network failures without creating duplicate data or inconsistent state.

---

### Q3. How do payment systems prevent duplicate charges?

**Answer:**

> They commonly use **idempotency keys**. If the same request with the same key is received again, the system returns the previous result instead of processing the payment again.
