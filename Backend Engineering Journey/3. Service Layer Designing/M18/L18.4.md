# Module 18 — Lesson 18.4: Dependency Injection Best Practices ⭐⭐⭐⭐⭐

> **Goal:** Learn the practical rules for using Dependency Injection in professional backend applications.

This lesson summarizes Module 18.

---

# Rule 1 — Don't Create Dependencies Inside Services

❌ Bad

```javascript
class UserService {
    constructor() {
        this.userRepository = new UserRepository();
    }
}
```

`UserService` is tightly coupled to `UserRepository`.

---

✅ Good

```text
Application

↓

Create UserRepository

↓

Inject into UserService
```

The service simply uses the dependency.

---

# Rule 2 — Prefer Constructor Injection

Constructor injection makes dependencies explicit.

```text
PostService

↓

PostRepository

↓

NotificationService
```

When someone reads the constructor, they immediately know what the service depends on.

---

# Rule 3 — Depend on Abstractions

Instead of depending on a specific implementation:

```text
MongoPostRepository
```

Depend on a repository contract (interface).

Later you can replace it with:

```text
PostgresPostRepository
```

without changing `PostService`.

> **Note:** JavaScript doesn't have interfaces built in, but the same design principle still applies. TypeScript uses interfaces, while plain JavaScript often relies on objects with the same API.

---

# Rule 4 — Use DI for External Dependencies

Inject things like:

- Repositories
    
- Services
    
- Email providers
    
- Cache clients
    
- Payment gateways
    

Avoid creating them with `new` inside your business services.

---

# Rule 5 — Don't Overuse DI

Not everything needs to be injected.

Simple utilities are fine to import directly.

Example:

```text
Date Helper

String Helper

Math Helper
```

Reserve DI for components that may change, be mocked, or have external dependencies.

---

# Common Mistakes

### ❌ Creating Dependencies Everywhere

```text
new Repository()

new EmailService()

new CacheService()
```

inside business services.

---

### ❌ Injecting Everything

Don't inject simple helper functions just for the sake of using DI.

---

### ❌ Hiding Dependencies

A constructor should clearly show what the service needs.

---

# Interview Questions

### Q1. What is Dependency Injection?

**Answer:**

> Dependency Injection is a design pattern where a class receives its dependencies from the outside instead of creating them itself.

---

### Q2. Why is Constructor Injection preferred?

**Answer:**

> It makes dependencies explicit, reduces coupling, and makes testing easier by allowing dependencies to be replaced with mocks.

---

### Q3. What kinds of components should be injected?

**Answer:**

> Components like repositories, services, database clients, cache clients, and external integrations should typically be injected because they are replaceable and easy to mock during testing.

# One-Page Cheat Sheet

|Principle|Best Practice|
|---|---|
|Create dependencies|Outside the service|
|Inject dependencies|Through the constructor|
|Testing|Inject mocks instead of real implementations|
|Depend on|Abstractions/contracts when possible|
|Avoid|`new` inside business services|
