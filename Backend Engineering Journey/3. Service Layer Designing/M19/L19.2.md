# Module 19 — Lesson 19.2: Mocking Repositories ⭐⭐⭐⭐⭐

> **Goal:** Learn how to test services without connecting to a real database.

A **mock repository** is a fake repository used only for testing.

Instead of:

```text
PostService

↓

MongoDB
```

Use:

```text
PostService

↓

MockPostRepository
```

Now your test doesn't need a database.

---

# Why Mock?

Suppose you're testing:

```text
publishPost()
```

You don't care whether MongoDB works.

You care whether:

- The business rules are correct.
    
- The service behaves correctly.
    

---

# Example

Production:

```text
PostService

↓

PostRepository

↓

MongoDB
```

Testing:

```text
PostService

↓

MockPostRepository
```

The service code stays exactly the same.

---

# What Can a Mock Do?

A mock can pretend to return data.

Example:

```text
findById()

↓

Return Fake Post
```

Or:

```text
findById()

↓

Return null
```

Now you can test different scenarios.

---

# Example Test Cases

Requirement:

> Publish a post.

Test 1:

```text
Post Exists

↓

Expect Success
```

Test 2:

```text
Post Not Found

↓

Expect NotFoundError
```

Test 3:

```text
Already Published

↓

Expect ConflictError
```

No real database is needed.

---

# Best Practices

✅ Mock repositories.

✅ Don't connect to a real database in unit tests.

✅ Test only the service's business logic.

---

# Interview Question

**Q:** Why use a mock repository in unit tests?

**Good Answer:**

> A mock repository replaces the real database, allowing the service to be tested in isolation. This makes tests fast, reliable, and focused on business logic instead of database behavior.

---

# Key Takeaways

- Mock repositories replace real databases.
    
- Unit tests should isolate the service.
    
- Test different scenarios by controlling mock responses.
    
- Fast tests lead to faster development.
