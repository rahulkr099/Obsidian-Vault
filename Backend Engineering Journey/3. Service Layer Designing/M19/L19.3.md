# Module 19 — Lesson 19.3: Testing Business Rules ⭐⭐⭐⭐⭐

> **Goal:** Learn what business rules should be tested in the Service Layer.

Don't test **how** the service works.

Test **what** the business expects.

---

# Example — Publish Post

Requirement:

> Only draft posts can be published.

Business rule:

```text
Draft?

↓

Yes → Publish

↓

No → ConflictError
```

Your test should verify both cases.

---

# Example — Authorization

Requirement:

> Only the owner or an admin can delete a post.

Tests:

```text
Owner

↓

Success
```

```text
Admin

↓

Success
```

```text
Other User

↓

ForbiddenError
```

---

# Example — Validation

Requirement:

> Title is required.

Tests:

```text
Title Exists

↓

Success
```

```text
Title Missing

↓

ValidationError
```

---

# Think in Scenarios

Instead of testing methods, test business situations.

Example for `publishPost()`:

```text
Post Exists?

↓

Already Published?

↓

User Authorized?
```

Each branch should have a test.

---

# What Should You Test?

✅ Success cases

✅ Failure cases

✅ Edge cases

Example:

```text
Draft

Published

Missing Post

Unauthorized User
```

---

# Best Practices

✅ Test one business rule per test.

✅ Give tests meaningful names.

✅ Cover both positive and negative scenarios.

---

# Interview Question

**Q:** What should unit tests for a service verify?

**Good Answer:**

> Unit tests should verify the service's business rules, including success cases, failure cases, authorization, validation, and edge cases. External dependencies should be mocked so the tests focus only on business logic.

---

# Key Takeaways

- Test business rules, not implementation details.
    
- Cover success, failure, and edge cases.
    
- Mock external dependencies.
    
- Write tests that describe business behavior.
