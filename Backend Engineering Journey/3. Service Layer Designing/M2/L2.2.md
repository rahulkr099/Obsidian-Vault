# Module 2 — Lesson 2.2: Communication Between Layers

> **Goal:** Learn which layers are allowed to communicate, which are not, and why following these rules makes your backend clean, scalable, and easy to maintain.

This lesson teaches one of the most important architectural principles:

> **Every layer has boundaries.**

Professional backend engineers respect these boundaries.

---

# The Golden Rule

A layer should communicate **only with the layer immediately below it**.

```text
Router
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Think of it like climbing stairs.

You go one step at a time.

You don't jump from the first floor to the fifth floor.

---

# Allowed Communication

Let's see the correct flow.

```text
Controller
      │
      ▼
Service
      │
      ▼
Repository
      │
      ▼
Database
```

Each layer knows only the next layer.

This creates **loose coupling**.

---

# What Is Loose Coupling?

Loose coupling means:

> A layer depends as little as possible on other layers.

For example:

```text
Controller

↓

PostService
```

The controller knows:

- A service exists.
    
- It has a method called `publishPost()`.
    

The controller does **not** know:

- MongoDB
    
- Mongoose
    
- Collections
    
- Database queries
    

That's the service's responsibility.

---

# Example 1 — Correct Flow

Publishing a post.

```text
Controller

↓

PostService.publishPost()

↓

PostRepository.findById()

↓

MongoDB
```

Everything follows the architecture.

---

# Example 2 — Wrong Flow

```text
Controller

↓

MongoDB
```

Example:

```javascript
const post = await Post.findById(id);
```

What's wrong?

The controller now knows database details.

If you later replace MongoDB with PostgreSQL, many controllers must change.

---

# Why Is That Bad?

Imagine you have:

```text
25 Controllers
```

Each one directly uses Mongoose.

Now your company decides to migrate.

You must edit:

```text
25 Controllers
```

Instead, if only repositories know about MongoDB:

```text
Repository

↓

MongoDB
```

Only repositories change.

Huge advantage.

---

# Services Should Not Know HTTP

Bad example:

```javascript
async function publishPost(req, res) {

}
```

Why?

Now the service depends on Express.

Professional services receive only data.

Good:

```javascript
await postService.publishPost({

    userId,

    postId

});
```

The service doesn't care whether the request came from:

- Express
    
- GraphQL
    
- CLI
    
- Background Job
    

It only receives data.

---

# Repositories Should Not Know Business Rules

Bad:

```javascript
async function publishPost() {

    if(user.role !== "admin"){

    }

}
```

Why?

The repository is not responsible for permissions.

Its only job:

```text
Read data

Write data

Update data

Delete data
```

Nothing more.

---

# One-Way Dependencies

A very important rule:

Dependencies move **downward**.

```text
Controller

↓

Service

↓

Repository
```

Never upward.

Bad:

```text
Repository

↓

Controller
```

This creates circular dependencies.

---

# Visualizing Dependencies

```text
Controller
      │
      ▼
Service
      │
      ▼

```

Notice:

The arrows go only downward.

MongoDB

Simple.

Clean.

Predictable.

# Can Services Call Other Services?

Yes.

Example:

Publishing a post.

```text
PostService

↓

NotificationService

↓

EmailService
```

Flow:

```text
PostService

↓

NotificationService.send()

↓

EmailService.send()

↓

SMTP Server
```

This is perfectly acceptable.

---

# Example

```javascript
await notificationService.notifyFollowers(post);

await emailService.sendAuthorEmail(user);
```

The service coordinates the workflow.

---

# Can Controllers Call Multiple Services?

Yes, but **carefully**.

Good example:

```javascript
const profile = await profileService.getProfile(id);

const settings = await settingService.getSettings(id);
```

But if controllers start coordinating business workflows like this:

```javascript
await userService.create();

await emailService.send();

await notificationService.send();

await analyticsService.track();
```

Then the controller is becoming **fat**.

Better:

```javascript
await userService.register(data);
```

The `UserService` coordinates everything internally.

---

# Repository Should Never Call Services

Bad architecture:

```text
Repository

↓

Service
```

Repositories should never say:

```javascript
notificationService.send();
```

Repositories should focus only on persistence.

---

# Middleware Should Not Call Services for Business Workflows

Middleware is not part of the application's business process.

Good middleware:

```text
Verify JWT

↓

Attach user

↓

Next()
```

Bad middleware:

```text
Verify JWT

↓

Publish post

↓

Create notification
```

That's service logic.

---

# Communication Matrix

|From|Can Call|
|---|---|
|Router|Middleware, Controller|
|Middleware|Controller|
|Controller|Service|
|Service|Repository, Other Services|
|Repository|Database|
|Database|Nobody|

This is a good mental model for most backend applications.

---

User creates a custom short URL.

```text

UserRepository.find()

↓

Check Premium

↓

URLRepository.findAlias()

↓

URLRepository.create()
```

The controller never asks:

```text

```

The service decides.

# Common Communication Mistakes

## Mistake 1

Controller → Repository

❌ Skips business rules.

---

## Mistake 2

Repository → Email Service

❌ Repository should not trigger workflows.

---

## Mistake 3

Service → `res.json()`

❌ Service shouldn't know Express.

---

## Mistake 4

Repository → Controller

❌ Wrong dependency direction.

---

## Mistake 5

Controller performing workflow coordination

❌ Creates fat controllers.

---

# Interview Tip

A common question:

> "Can a controller directly call a repository?"

A professional answer:

> "Technically it can, but architecturally it shouldn't. The Service Layer centralizes business logic, keeps controllers thin, prevents duplication, and makes the application easier to test and maintain."

That answer shows architectural maturity.

---

# Best Practices

✅ Controllers depend only on services.

✅ Services coordinate business workflows.

✅ Repositories focus only on data access.

✅ Services may call multiple repositories and other services.

✅ Keep dependencies flowing in one direction.

# Key Takeaways

- Layers should communicate only with the appropriate neighboring layers.
    
- Controllers should never bypass services to access repositories directly.
    
- Services may orchestrate multiple repositories and domain services.
    
- Repositories should never contain business rules or call services.
    
- One-way dependencies reduce coupling and make future changes easier.
