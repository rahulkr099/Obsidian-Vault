# Module 2 — Lesson 2.3: Layer Dependencies and Architecture Rules

> **Goal:** Learn the architectural rules that keep backend applications maintainable as they grow. This lesson introduces dependency direction, coupling, cohesion, and circular dependencies.

This is the kind of knowledge that separates someone who can **build a backend** from someone who can **design a backend**.

---

# What Is a Dependency?

A dependency means:

> One piece of code relies on another piece of code.

Example:

```javascript
const post = await postService.publishPost(data);
```

Here,

```text
Controller
     ↓
PostService
```

The controller **depends on** `PostService`.

---

# Dependency Direction

Professional backend applications have **one-way dependencies**.

```text
Controller
      │
      ▼
Service
      │
      ▼
Repository
      │
      ▼
Database
```

Notice that everything flows downward.

This is intentional.

---

# Why One-Way Dependencies?

Imagine changing your database.

Today:

```text
MongoDB
```

Tomorrow:

```text
PostgreSQL
```

If only the repository knows about MongoDB:

```text
Repository
      ↓
MongoDB
```

Only repositories need to change.

Controllers and services remain untouched.

That's the power of proper dependencies.

---

# Rule 1 — Controllers Should Not Know Database Details

Bad:

```javascript
const post = await Post.findById(id);
```

Now the controller knows:

- Mongoose
    
- MongoDB
    
- Database models
    

Good:

```javascript
const post = await postService.getPost(id);
```

The controller doesn't care where the data comes from.

---

# Rule 2 — Services Should Not Know HTTP

Bad:

```javascript
async function createPost(req, res) {

}
```

Now the service depends on Express.

Good:

```javascript
await postService.createPost({
    title,
    content,
    authorId
});
```

The service only knows business data.

---

# Rule 3 — Repositories Should Not Know Business Rules

Bad:

```javascript
if (user.role !== "admin") {
    throw new Error();
}
```

Repositories should never decide:

- Who is allowed
    
- Which workflow runs
    
- Which notification is sent
    

Their only job:

```text
Read

Write

Update

Delete
```

---

# Loose Coupling

Coupling measures **how strongly two parts of your application depend on each other**.

### Tight Coupling ❌

```text
Controller

↓

MongoDB

↓

Email

↓

Redis

↓

Stripe
```

The controller knows everything.

Changing one dependency affects many files.

---

### Loose Coupling ✅

```text
Controller

↓

Service

↓

Repository
```

Each layer knows very little about the others.

That's easier to maintain.

---

# High Cohesion

Cohesion measures **how focused a class or module is**.

Good cohesion means:

> One module has one clear purpose.

Example:

```text
PostService

↓

Publishing

Editing

Archiving

Deleting
```

Everything relates to posts.

---

Bad cohesion:

```text
PostService

↓

Publish posts

Send emails

Generate invoices

Process payments

Resize images
```

These responsibilities don't belong together.

---

# Keep Services Focused

Instead of one huge service:

```text
UserService

↓

Login

Payments

Emails

Notifications

Profile

Analytics

Passwords
```

Split it into:

```text
AuthenticationService

ProfileService

PasswordService

NotificationService
```

Each service has one responsibility.

---

# Circular Dependencies

One of the most common architectural problems.

Imagine:

```text
UserService
      │
      ▼
NotificationService
      │
      ▼
UserService
```

Now both services depend on each other.

This is called a **circular dependency**.

---

# Why Is It Bad?

Problems include:

- Hard to understand
    
- Hard to test
    
- Initialization issues
    
- Difficult refactoring
    
- Hidden bugs
    

Avoid circular dependencies whenever possible.

---

# Better Design

Instead of:

```text
UserService

↓

NotificationService

↓

UserService
```

Design:

```text
UserService

↓

NotificationService
```

Only one direction.

---

# Example — Blog Publishing

Suppose publishing a blog requires:

- Updating the post
    
- Sending notifications
    
- Updating search index
    

Professional design:

```text
PostService
     │
     ├────────► NotificationService
     │
     └────────► SearchService
```

Notice:

Neither service calls `PostService` back.

No circular dependency.

---

# Layer Independence

Each layer should be replaceable.

Imagine replacing Express.

Today:

```text
Express

↓

Controller

↓

Service
```

Tomorrow:

```text
Fastify

↓

Controller

↓

Service
```

Services don't change because they never depended on Express.

---

# The Dependency Rule

A simple rule to remember:

> Higher layers depend on lower layers.

```text
Controller
      │
      ▼
Service
      │
      ▼
Repository
```

Never the opposite.

---

# Real Example — URL Shortener

Flow:

```text
URLController

↓

URLService

↓

URLRepository

↓

MongoDB
```

Now imagine adding:

```text
Redis Cache
```

The controller doesn't change.

Only the repository may change.

This is a major architectural advantage.

---

# Bad Architecture Example

```text
Controller

↓

Repository

↓

Service

↓

Database
```

What's wrong?

The repository is calling the service.

Business logic is mixed with data access.

The dependency direction is broken.

---

# Good Architecture Example

```text
Controller

↓

Service

↓

Repository

↓

Database
```

Simple.

Predictable.

Easy to test.

---

# Coupling vs Cohesion

A common interview topic.

|Coupling|Cohesion|
|---|---|
|Relationship between modules|Focus within one module|
|Lower is better|Higher is better|
|Reduce unnecessary dependencies|Keep one clear responsibility|

Remember:

> **Low Coupling + High Cohesion = Good Design**

---

# Real-World Analogy

Think of a hospital.

```text
Reception

↓

Doctor

↓

Laboratory
```

The receptionist doesn't perform blood tests.

The laboratory doesn't decide the treatment.

Each department has a clear responsibility.

Backend layers work the same way.

---

# Architecture Checklist

Before writing code, ask yourself:

✅ Does this layer have only one responsibility?

✅ Am I calling only the correct layer?

✅ Can this layer be replaced without changing others?

✅ Am I creating unnecessary dependencies?

✅ Would this code still work if Express changed?

✅ Would this code still work if MongoDB changed?

If most answers are "yes," your design is probably healthy.

---

# Interview Insight

An interviewer may ask:

> "What is the difference between coupling and cohesion?"

A strong answer:

> **Coupling** describes how much one module depends on another. We aim for **low coupling** so changes stay isolated. **Cohesion** describes how focused a module is on a single responsibility. We aim for **high cohesion** because focused modules are easier to understand, test, and maintain.

---

# Key Takeaways

- Dependencies should always flow downward through the architecture.
    
- Controllers depend on services; services depend on repositories.
    
- Services should not depend on Express or HTTP objects.
    
- Repositories should not contain business logic.
    
- Aim for **low coupling** and **high cohesion**.
    
- Avoid circular dependencies between services.
    
- Each layer should be replaceable with minimal impact on the rest of the application.
