# Lesson 3.1 — Controller Responsibilities

> **Goal:** Learn what a controller should do—and, more importantly, what it should never do.

---

## The Controller is the HTTP Layer

Think of the controller as a **translator**.

It translates:

```text
HTTP Request
      ↓
Business Request

Business Response
      ↓
HTTP Response
```

It connects Express with your application's business logic.

---

# Responsibilities of a Controller

A controller should do only these things:

### 1. Read the HTTP Request

```javascript
const { title, content } = req.body;
const postId = req.params.id;
const page = req.query.page;
const userId = req.user.id;
```

---

### 2. Call the Appropriate Service

```javascript
const post = await postService.createPost({
    title,
    content,
    authorId: userId
});
```

The controller delegates the work.

---

### 3. Return an HTTP Response

```javascript
res.status(201).json({
    success: true,
    data: post
});
```

The controller knows how to speak HTTP.

---

### 4. Handle Service Errors

```javascript
try {
    const post = await postService.createPost(data);

    res.status(201).json(post);

} catch (error) {
    next(error);
}
```

Usually, a global error handler formats the final response.

---

# What a Controller Should NOT Do

## ❌ Business Rules

Bad:

```javascript
if (post.author.toString() !== req.user.id) {
    return res.status(403).json(...);
}
```

Good:

```javascript
await postService.publishPost({
    userId,
    postId
});
```

The service checks ownership.

---

## ❌ Database Queries

Bad:

```javascript
const post = await Post.findById(id);
```

Good:

```javascript
const post = await postService.getPost(id);
```

---

## ❌ Workflow Coordination

Bad:

```javascript
await post.save();

await notificationService.send();

await analyticsService.track();
```

Good:

```javascript
await postService.publishPost(data);
```

The service coordinates everything.

---

# Thin Controller Example

```javascript
async function publishPost(req, res, next) {
    try {
        const post = await postService.publishPost({
            userId: req.user.id,
            postId: req.params.id
        });

        res.status(200).json(post);

    } catch (error) {
        next(error);
    }
}
```

Notice how easy it is to read.

---

# Fat vs Thin

|Fat Controller ❌|Thin Controller ✅|
|---|---|
|Business logic|Calls service|
|Database queries|Reads request|
|Permission checks|Returns response|
|Long functions|Small functions|
|Hard to test|Easy to test|

---

# Best Practices

✅ One controller method = one API endpoint.

✅ Keep controllers around **20–40 lines** whenever possible.

✅ Pass only the required data to the service.

Instead of:

```javascript
postService.createPost(req);
```

Use:

```javascript
postService.createPost({
    title,
    content,
    authorId
});
```

This keeps your service independent of Express.

---

# Interview Question

**Q:** What are the responsibilities of a controller?

**Good Answer:**

> "A controller handles HTTP concerns. It reads the request, calls the appropriate service, returns the HTTP response, and forwards errors to the error-handling middleware. It should not contain business logic or database queries."

---

# Key Takeaways

- A controller is the **HTTP layer** of your application.
    
- It should **read requests, call services, and return responses**.
    
- It should **not** contain business rules, workflow logic, or direct database access.
    
- Thin controllers make your application easier to test, maintain, and extend.
