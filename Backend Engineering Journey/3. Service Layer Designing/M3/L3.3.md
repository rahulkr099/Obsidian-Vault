# Module 3 — Lesson 3.3: Repository Responsibilities

> **Goal:** Learn the purpose of the Repository Layer, how to design clean repositories, and why they should only handle data access.

If the **Service Layer is the brain**, then the **Repository Layer is the librarian**.

It knows **where the data is**, but it doesn't decide **what should happen** with that data.

---

# What is a Repository?

A repository is responsible for **communicating with the database**.

Its only job is:

```text
Read data

↓

Write data

↓

Update data

↓

Delete data
```

Nothing more.

---

# Repository Responsibilities

A repository should:

### ✅ Read Data

```javascript
findById(id)
```

---

### ✅ Create Data

```javascript
create(data)
```

---

### ✅ Update Data

```javascript
update(id, data)
```

---

### ✅ Delete Data

```javascript
delete(id)
```

---

### ✅ Perform Database Queries

Examples:

```javascript
findByEmail(email)

findBySlug(slug)

findPublishedPosts()

findByAuthor(authorId)
```

These are data retrieval methods.

---

# What a Repository Should NOT Do

## ❌ Business Rules

Bad:

```javascript
if (post.status === "published") {
    throw new Error();
}
```

Question:

> Should a published post be editable?

That's a **business rule**.

It belongs in the **Service**.

---

## ❌ Permission Checks

Bad:

```javascript
if (user.role !== "admin") {
    throw new Error();
}
```

Repositories should never decide who is allowed.

---

## ❌ Send Emails

Bad:

```javascript
await emailService.send(...);
```

Repositories don't know workflows.

---

## ❌ Return HTTP Responses

Bad:

```javascript
res.status(404).json(...)
```

Repositories shouldn't know Express exists.

---

# A Professional Flow

```text
Controller

↓

PostService

↓

PostRepository

↓

MongoDB
```

Each layer has one responsibility.

---

# Example Repository

```javascript
class PostRepository {

    async findById(id) {
        return await Post.findById(id);
    }

    async create(data) {
        return await Post.create(data);
    }

    async update(id, data) {
        return await Post.findByIdAndUpdate(
            id,
            data,
            { new: true }
        );
    }

}
```

Notice:

No business logic.

Only database operations.

---

# Example Service Using Repository

```javascript
async function publishPost({ userId, postId }) {

    const post = await postRepository.findById(postId);

    if (!post) {
        throw new NotFoundError();
    }

    if (post.author.toString() !== userId) {
        throw new ForbiddenError();
    }

    post.status = "published";

    return await postRepository.update(
        postId,
        post
    );

}
```

The service decides **what** to do.

The repository decides **how** to access the data.


---

Another example:


---

# Generic vs Domain Methods

Sometimes beginners create methods like:

```javascript
executeQuery()

run()

fetch()
```

These names are vague.

Prefer domain-specific methods.

Example:

```javascript
findBySlug()

findDraftPosts()

findPublishedPosts()
```

Much clearer.

---

# Repository Pattern Benefits

## 1. Database Independence

Today:

```text
MongoDB
```

Tomorrow:

```text
PostgreSQL
```

Only the repository changes.

Services remain the same.

---

## 2. Easier Testing

When testing a service:

```text
Mock Repository

↓

Test Business Rules
```

No real database needed.

---

## 3. Cleaner Code

Instead of:

```javascript
Post.findById(...)

Post.findOne(...)

Post.update(...)
```

everywhere,

all database access stays inside one place.

# Common Beginner Mistakes

## Mistake 1

Putting business logic inside repositories.

❌ Wrong.

---

## Mistake 2

Making repositories too smart.

Example:

```javascript
publishPost()
```

Publishing is a business action.

Better:

```javascript
update()
```

The service decides when to call it.

---

## Mistake 3

Controllers calling repositories directly.

```text
Controller

↓

Repository
```

This bypasses business rules.

Always go through the service.

---

# Best Practices

✅ Repositories only communicate with the database.

✅ Keep methods small and predictable.

✅ Use meaningful method names.

✅ Don't mix business logic with data access.

✅ Let services decide **when** and **why** a repository method is called.

---

# Interview Question

**Q:** Why use a Repository Pattern instead of querying Mongoose directly from the service?

**Good Answer:**

> "The Repository Pattern separates data access from business logic. It keeps services focused on business rules, makes testing easier by allowing repositories to be mocked, and makes it easier to switch databases or optimize queries without changing service code."

# Summary

|Controller|Service|Repository|
|---|---|---|
|Reads HTTP request|Business rules|Database queries|
|Calls service|Coordinates workflow|CRUD operations|
|Returns HTTP response|Calls repositories|Returns data|
|No business logic|No HTTP|No business logic|

# Mini Exercise

Which layer should contain each task?

|Task|Layer|
|---|---|
|`findByEmail(email)`|?|
|Check whether the user is an admin|?|
|Save a new post|?|
|Decide whether a post can be published|?|
|Return `404 Not Found`|?|

**Answers:**

- `findByEmail(email)` → **Repository**
    
- Check whether the user is an admin → **Service**
    
- Save a new post → **Repository**
    
- Decide whether a post can be published → **Service**
    
- Return `404 Not Found` → **Controller**
