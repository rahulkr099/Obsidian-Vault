# The 5-Layer Mental Model

Whenever you build a feature, think in this order:

```text
HTTP Request
      │
      ▼
Controller
      │
      ▼
Service
      │
      ▼
Repository
      │
      ▼
Database
```

Ask yourself:

> **"Which layer owns this responsibility?"**

---

# Layer Responsibility Cheat Sheet

|Layer|Responsibility|Should NOT Do|
|---|---|---|
|**Router**|Map URL to controller|Business logic|
|**Middleware**|Authentication, logging, validation|Business workflows|
|**Controller**|Read request, call service, return response|Database queries, business rules|
|**Service**|Business rules, workflows, permissions|HTTP handling|
|**Repository**|Database access|Business logic|

---

# Decision Checklist

When writing code, use this flowchart:

```text
Does it read req.body, req.params, req.query?
            │
           Yes
            │
      → Controller

Does it decide what the business allows?
            │
           Yes
            │
       → Service

Does it read/write the database?
            │
           Yes
            │
     → Repository

Does it verify JWT or log requests?
            │
           Yes
            │
     → Middleware

Does it return res.json()?
            │
           Yes
            │
      → Controller
```

# Common Beginner Mistakes

## ❌ Controller doing everything

```javascript
const post = await Post.findById(id);

if(post.author !== req.user.id){
   ...
}

await post.save();
```

This mixes **HTTP**, **business rules**, and **database access**.

---

## ✅ Correct

```javascript
const post = await postService.publishPost({
    userId,
    postId
});
```

Simple.

Readable.

Professional.

# The Golden Rules

### Rule 1

Controllers should be **thin**.

---

### Rule 2

Services should contain **business rules**.

---

### Rule 3

Repositories should contain **database queries only**.

---

### Rule 4

Middleware handles **cross-cutting concerns**.

---

### Rule 5

Dependencies always move downward.

```text
Controller
      ↓
Service
      ↓
Repository
```

Never the opposite.

# Interview Questions

## Q1. Why do we need a Service Layer?

**Answer:**

> It separates business logic from HTTP handling and database access, making the application easier to maintain, test, and extend.

---

## Q2. Why shouldn't controllers access the database directly?

**Answer:**

> Because controllers should focus on HTTP. Accessing the database directly mixes responsibilities and duplicates business logic.

---

## Q3. Why use the Repository Pattern?

**Answer:**

> It isolates data access, improves testability, and allows database implementations to change without affecting business logic.

---

## Q4. Where should authorization logic live?

**Answer:**

> Authentication (who the user is) usually belongs in middleware. Authorization (whether the user is allowed to perform an action) belongs in the Service Layer because it is a business rule.

---

## Q5. Can a service call another service?

**Answer:**

> Yes. Services can coordinate multiple repositories and other services as part of a business workflow.

Example:

```text
OrderService
      │
      ├── PaymentService
      ├── InventoryService
      └── NotificationService
```

|**Middleware**|Handles shared request concerns.|
|**Controller**|Translates HTTP into a service call.|

|**Repository**|Reads and writes data.|

# Practice Assignment

Design the architecture for this feature:

> **A student submits an assignment.**

Before coding, answer these questions:

1. What endpoint will the router expose?
    
2. What middleware is required?
    
3. What data will the controller extract?
    
4. What business rules belong in the service?
    
5. Which repositories are needed?
    
6. What should the controller return?
    

If you can answer those six questions confidently, you're thinking like a backend engineer.
