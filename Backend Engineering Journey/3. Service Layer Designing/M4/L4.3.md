# Module 4 — Lesson 4.3: Handling Edge Cases ⭐⭐⭐⭐⭐

> **Goal:** Learn how professional backend engineers think about failures before they happen.

One of the biggest differences between beginners and experienced backend engineers is this:

- **Beginners think about the happy path.**
    
- **Professionals think about the unhappy paths too.**
    

---

# What is an Edge Case?

An edge case is a situation that is **possible but not the normal flow**.

Example:

Normal flow:

```text
User publishes a draft post.

↓

Success
```

Edge cases:

```text
Post doesn't exist

↓

User isn't the owner

↓

Already published

↓

Database is unavailable
```

A good backend handles all of them.

---

# Happy Path vs Edge Cases

Requirement:

> User publishes a blog post.

### Happy Path

```text
Find post

↓

User owns post

↓

Publish

↓

Success
```

---

### Edge Cases

```text
Post not found

Already published

Unauthorized user

Database timeout
```

You should think about **both**.

# A Simple Framework

Whenever you get a feature, ask these questions:

### 1. Does the resource exist?

Example:

```text
Post?

User?

Course?

Order?
```

---

### 2. Is the user allowed?

```text
Owner?

Admin?

Premium?

Verified?
```

---

### 3. Is the current state valid?

```text
Already published?

Already completed?

Already enrolled?
```

---

### 4. Are the inputs valid?

```text
Future date?

Valid email?

Positive quantity?
```

---

### 5. Can something fail externally?

```text
Database

Payment gateway

Email API

Cloud storage
```

Always assume external systems can fail.

# Thinking in States

Many features depend on the current state.

Example:

A blog post.

```text
Draft

↓

Published

↓

Archived
```

Ask yourself:

Can you:

- Publish an archived post?
    
- Archive a draft?
    
- Edit a published post?
    

The answers are business rules.

---

# Race Conditions (Basic Idea)

Imagine two users click at the same time.

Example:

```text
Seat available = 1
```

User A:

```text
Reserve seat
```

User B:

```text
Reserve seat
```

Without proper handling:

```text
Two reservations

One seat
```

This is called a **race condition**.

You'll learn solutions (transactions, locking, optimistic concurrency) later, but it's important to recognize the problem now.

# Error Handling

When an edge case happens:

Don't return random errors.

Use meaningful errors.

Example:

|Situation|Error|
|---|---|
|Post missing|`NotFoundError`|
|Not owner|`ForbiddenError`|
|Already published|`BadRequestError`|
|Invalid input|`ValidationError`|

Your controller or global error handler converts these into HTTP responses.

# Common Beginner Mistakes

## ❌ Only testing success

Example:

```text
Create user

↓

Works

↓

Done
```

Professionals also test:

- Duplicate email
    
- Invalid password
    
- Database failure
    

---

## ❌ Ignoring current state

Bad:

```text
Publish

↓

Publish again

↓

Publish again
```

The service should prevent invalid state changes.

---

## ❌ Forgetting authorization

Example:

```text
User edits someone else's post
```

Always ask:

> "Is this user allowed?"

---

# Professional Checklist

Before implementing any feature, ask:

```text
✓ Does the resource exist?

✓ Is the user authenticated?

✓ Is the user authorized?

✓ Is the current state valid?

✓ Are inputs valid?

✓ Can external systems fail?

✓ What should happen if something fails?
```

If you answer these questions, your implementation will be much more robust.

---

# Interview Question

**Q:** When implementing a backend feature, how do you think about edge cases?

**Good Answer:**

> I first identify the happy path, then systematically check resource existence, authorization, current state, input validity, and external dependencies. I design the service to handle these cases with meaningful errors instead of assuming everything succeeds.

---

# Key Takeaways

- Always think beyond the happy path.
    
- Consider resource existence, permissions, state, validation, and external failures.
    
- Edge cases belong primarily in the **Service Layer** because they are business decisions.
    
- Thinking about failures early leads to more reliable backend systems.
