# The Professional Workflow

When a new feature arrives, don't start coding.

Instead, follow this process:

```text
Requirement
      ↓
Business Rules
      ↓
Edge Cases
      ↓
Service Method
      ↓
Repository Calls
      ↓
Implementation
```

This is how experienced backend engineers think.

---

# Example 1 — Blog App

## Requirement

> Users can archive blog posts.

---

## Step 1 — Business Rules

```text
Post must exist

↓

User must own the post

↓

Post must not already be archived

↓

Update archivedAt
```

---

## Step 2 — Edge Cases

```text
Post not found

↓

Unauthorized user

↓

Already archived
```

---

## Step 3 — Service Method

```javascript
archivePost({
    userId,
    postId
});
```

Notice the method describes a **business action**.

---

## Step 4 — Repository Calls

```text
PostRepository.findById()

↓

PostRepository.update()
```

# Designing Good Service Methods

Good service methods describe **business capabilities**.

Good:

```javascript
publishPost()

archivePost()

cancelOrder()

resetPassword()

enrollStudent()
```

Bad:

```javascript
update()

process()

execute()

handleRequest()
```

Good names explain **what the business is doing**.

---

# Before Writing Code

Ask yourself these questions:

```text
What is the requirement?

↓

What are the business rules?

↓

What can go wrong?

↓

What service method represents this action?

↓

Which repositories are needed?
```

If you answer these first, coding becomes much easier.

# Module 4 Summary

By the end of this module, you can turn a product requirement into a backend design using this framework:

```text
Requirement
      ↓
Business Rules
      ↓
Edge Cases
      ↓
Service Method
      ↓
Repository Calls
      ↓
Code
```

This approach helps you write cleaner services, catch problems earlier, and communicate your design clearly during interviews.

---

# Key Takeaways

- Never jump directly from a requirement to code.
    
- Identify business rules before implementation.
    
- Think about edge cases early.
    
- Design service methods around **business actions**.
    
- Let repositories focus only on data access.
