# Lesson 5.1 — Understanding User Stories

> **Goal:** Learn how backend engineers read a user story.

Most features start as a **user story**, not code.

Example:

> **As a user, I want to publish my blog post so that other users can read it.**

A beginner thinks:

```text
Need an API endpoint.
```

A backend engineer thinks:

```text
What business action is happening?

↓

Publish Post
```

---

# User Story → Business Action

Example:

```text
User Story

↓

User publishes a blog

↓

Business Action

↓

publishPost()
```

Notice:

We are identifying **what the system does**, not **how** it does it.

# Think in Business Language

Good service names:

```text
publishPost()

placeOrder()

completeTask()

cancelBooking()

resetPassword()
```

These are actions the business understands.

---

# Common Beginner Mistake

Requirement:

> User publishes a blog.

Beginner thinks:

```text
POST /posts/:id/publish
```

Professional thinks:

```text
publishPost()
```

The HTTP endpoint is important, but **the service should be designed around the business action**, not the API route.

---

# Interview Question

**Q:** Why do backend engineers start with user stories?

**Good Answer:**

> User stories describe business requirements. By identifying the business action first, we can design clean service methods before thinking about controllers, routes, or database queries.

---

# Key Takeaways

- Start with the **user story**, not the code.
    
- Extract the **business action**.
    
- Design the service around that action.
    
- Think in terms of **business capabilities**, not HTTP endpoints.
