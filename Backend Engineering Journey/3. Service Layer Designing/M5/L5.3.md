# Module 5 — Lesson 5.3: Return Values & Error Handling ⭐⭐⭐⭐⭐

> **Goal:** Learn what a service should return, when it should throw errors, and how errors flow through a professional backend.

This is one of the most common interview topics.

---

# The Golden Rule

A service should **return data** or **throw an error**.

It should **never return an HTTP response**.

---

# Good Flow

```text
Controller
      │
      ▼
Service
      │
      ├── Success → Return Data
      │
      └── Failure → Throw Error
```

The controller is responsible for sending the HTTP response.

---

# Success Case

Suppose a user publishes a post.

## Service

```javascript
async function publishPost(dto) {

    // Business logic

    return updatedPost;

}
```

Notice:

The service returns business data.

---

## Controller

```javascript
async function publishPost(req, res, next) {

    try {

        const post = await postService.publishPost({
            userId: req.user.id,
            postId: req.params.id
        });

        res.status(200).json(post);

    } catch (error) {
        next(error);
    }

}
```

The controller converts the result into an HTTP response.

---

# Failure Case

Suppose the post doesn't exist.

## Service

```javascript
if (!post) {
    throw new NotFoundError("Post not found");
}
```

The service doesn't say:

```javascript
res.status(404).json(...)
```

It simply throws an error.

---

# Why Throw Errors?

Imagine the service is used by:

- REST API
    
- GraphQL
    
- Background Job
    
- CLI Tool
    

A service shouldn't know whether the caller needs:

- HTTP 404
    
- GraphQL error
    
- Console message
    

It simply reports:

> "The post doesn't exist."

The caller decides how to present that error.

---

# Error Flow

```text
Controller

↓

Service

↓

throw NotFoundError

↓

Global Error Handler

↓

HTTP 404 Response
```

Clean separation of responsibilities.

---

# Custom Errors

Instead of:

```javascript
throw new Error("Something went wrong");
```

Prefer meaningful errors.

```javascript
throw new NotFoundError();

throw new ForbiddenError();

throw new ValidationError();

throw new ConflictError();
```

These clearly describe what happened.

---

# Example

## Service

```javascript
async function deletePost(dto) {

    const post = await postRepository.findById(dto.postId);

    if (!post) {
        throw new NotFoundError("Post not found");
    }

    if (post.author.toString() !== dto.userId) {
        throw new ForbiddenError("Not allowed");
    }

    return await postRepository.delete(dto.postId);

}
```

---

## Controller

```javascript
async function deletePost(req, res, next) {

    try {

        await postService.deletePost({
            userId: req.user.id,
            postId: req.params.id
        });

        res.sendStatus(204);

    } catch (error) {
        next(error);
    }

}
```

Notice:

The service never sends HTTP responses.

---

# What Should Services Return?

Usually one of these:

### Return Entity

```javascript
return post;
```

---

### Return List

```javascript
return posts;
```

---

### Return Summary

```javascript
return {

    totalOrders,

    totalRevenue

};
```

---

### Return Nothing

Example:

```javascript
await postService.deletePost(dto);
```

The controller returns:

```javascript
204 No Content
```

---

# Common Beginner Mistakes

## ❌ Returning HTTP Status

```javascript
return res.status(404).json(...);
```

Services shouldn't know Express.

---

## ❌ Returning Strings

```javascript
return "Success";
```

Better:

Return meaningful data.

---

## ❌ Catching Every Error

Bad:

```javascript
try {

} catch {

    return null;

}
```

This hides problems.

Let unexpected errors bubble up unless you have a good reason to handle them.

---

# Error Responsibility

|Layer|Responsibility|
|---|---|
|Service|Throw meaningful business errors|
|Controller|Forward errors with `next(error)`|
|Global Error Handler|Convert errors into HTTP responses|

This keeps each layer focused.

---

# Interview Question

**Q:** Should a service return `res.status(404)`?

**Good Answer:**

> No. Services should remain independent of HTTP. They should return business data on success or throw meaningful errors on failure. Controllers and global error handlers are responsible for converting those errors into HTTP responses.

---

# Best Practices

✅ Return business data.

✅ Throw custom errors.

✅ Never return Express responses.

✅ Let the controller or global error handler handle HTTP.

---

```text
Request
   │
   ▼
Controller
   │
   ▼
Service
   │
   ├── Success → Return Data
   │
   └── Failure → Throw Error
   │
   ▼

   ▼

```

# Mini Exercise

Where should each action happen?

|Action|Layer|
|---|---|
|Throw `NotFoundError`|?|
|Return `res.status(404)`|?|
|Return updated user object|?|
|Call `next(error)`|?|

### Answers

- Throw `NotFoundError` → **Service**
    
- Return `res.status(404)` → **Controller** (or Global Error Handler)
    
- Return updated user object → **Service**
    
- Call `next(error)` → **Controller**
