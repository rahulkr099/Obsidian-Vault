# Module 5 — Lesson 5.4: Service Design Best Practices ⭐⭐⭐⭐⭐

> **Goal:** Learn the practical rules professional backend engineers follow when designing service layers.

This lesson summarizes everything from Module 5 into a set of rules you can apply to every project.

---

# The 10 Golden Rules of Service Design

## Rule 1 — Design Around Business Actions

Good:

```javascript
publishPost()

placeOrder()

cancelOrder()

resetPassword()

enrollStudent()
```

Bad:

```javascript
execute()

process()

handle()

updateData()
```

**Ask yourself:**

> "Does this method represent something the business understands?"

---

## Rule 2 — Accept a DTO

Instead of:

```javascript
login(email, password);
```

Prefer:

```javascript
login({
    email,
    password
});
```

Benefits:

- Easier to read
    
- Easier to extend
    
- Fewer parameter-order bugs
    

---

## Rule 3 — Never Accept `req` or `res`

❌ Bad

```javascript
postService.create(req);
```

✅ Good

```javascript
postService.create({
    title,
    content,
    authorId
});
```

Your service should work without Express.

---

## Rule 4 — Keep Business Logic in Services

Business questions belong here.

Examples:

```text
Can this user publish?

Can this coupon be used?

Can this order be cancelled?
```

These should never be inside controllers.

---

## Rule 5 — Keep Services Focused

Bad:

```text
UserService

↓

Login

Payments

Emails

Analytics

Invoices
```

Good:

```text
AuthService

UserService

PaymentService

EmailService
```

Each service has one domain.

---

## Rule 6 — Use Repositories for Data Access

Bad:

```javascript
await Post.findById(id);
```

inside the service.

Better:

```javascript
await postRepository.findById(id);
```

The service shouldn't know database details.

---

## Rule 7 — Return Data, Throw Errors

Success:

```javascript
return post;
```

Failure:

```javascript
throw new NotFoundError();
```

Never:

```javascript
res.status(404).json(...);
```

---

## Rule 8 — One Method, One Responsibility

Bad:

```javascript
managePost(action);
```

Good:

```javascript
publishPost()

archivePost()

restorePost()
```

Each method should do one business action well.

---

## Rule 9 — Think Before Coding

Always follow this process:

```text
Requirement
      ↓
Business Rules
      ↓
Edge Cases
      ↓
Service Method
      ↓
Repository Calls
      ↓
Code
```

Planning first reduces bugs later.

---

## Rule 10 — Services Should Be Reusable

Your service should work for:

```text
REST API

↓

GraphQL

↓

Background Jobs

↓

CLI Scripts

↓

Scheduled Tasks
```

A good service doesn't care **who** is calling it.

---

# A Professional Service

Imagine reading this:

```javascript
await orderService.placeOrder({
    userId,
    items,
    couponCode,
    shippingAddress
});
```

Without opening the implementation, you already understand what it does.

That's the goal of a good interface.

---

# Service Design Checklist

Before finishing a service, ask yourself:

```text
✓ Does the method represent a business action?

✓ Is the name clear?

✓ Does it receive a DTO?

✓ Does it avoid req and res?

✓ Does it call repositories instead of models?

✓ Does it return data or throw errors?

✓ Is the responsibility focused?
```

If every answer is **Yes**, you're on the right track.

# Common Interview Questions

## Q1. Why shouldn't services use `req` and `res`?

**Answer:**

> Services should remain independent of Express so they can be reused from REST APIs, GraphQL, background jobs, or tests.

---

## Q2. Why use DTOs?

**Answer:**

> DTOs make method signatures clearer, easier to extend, and reduce coupling between the HTTP layer and the Service Layer.

---

## Q3. What should a service return?

**Answer:**

> A service should return business data on success or throw meaningful errors on failure. It should not return HTTP responses.

---

## Q4. Can one service call another?

**Answer:**

> Yes. A service can coordinate multiple repositories and other services as part of a business workflow.

Example:

```text
OrderService
      │
      ├── PaymentService
      ├── InventoryService
      └── NotificationService
```

---

# Complete Flow

```text
Client
   │
   ▼
Controller
   │
   ▼
Service
   │
   ├── Repository
   ├── EmailService
   ├── PaymentService
   └── NotificationService
```

The **Service Layer** is the orchestrator of the application's business logic.

---

# Module 5 Summary

You now know how to:

- Design service methods around **business actions**.
    
- Use **DTOs** instead of `req` and `res`.
    
- Return business data and throw meaningful errors.
    
- Keep services focused and reusable.
    
- Build service interfaces that are easy to understand and maintain.

# One-Page Cheat Sheet

|Topic|Best Practice|
|---|---|
|Method names|`publishPost()`, `placeOrder()`|
|Parameters|Single DTO object|
|Business rules|Service|
|Database access|Repository|
|HTTP responses|Controller|
|Errors|Throw in Service, handle in Controller/Error Middleware|
|Express dependency|Never inside Service|
