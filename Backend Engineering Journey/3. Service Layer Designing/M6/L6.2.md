# Module 6 — Lesson 6.2: Request Validation vs Business Validation ⭐⭐⭐⭐⭐

> **Goal:** Learn the difference between request validation and business validation, and know exactly where each validation belongs.

This is one of the most common backend interview topics.

---

# The Simple Rule

Ask yourself one question:

> **"Am I validating the data, or am I validating the business?"**

If you're validating the **shape or format** of data → **Request Validation**

If you're validating **application rules** → **Business Validation**

---

# Request Validation

Question:

> **"Is the request structurally valid?"**

Examples:

```text
Email format

↓

Password length

↓

Required fields

↓

Data type

↓

Maximum length
```

These checks happen **before** the service runs.

Example:

```json
{
    "email": "rahul@example.com",
    "password": "secret123"
}
```

Checks:

```text
✓ Email exists

✓ Email is valid

✓ Password exists

✓ Password ≥ 8 characters
```

No database access is needed.

---

# Business Validation

Question:

> **"Should the application allow this action?"**

Examples:

```text
User already enrolled?

↓

Order already shipped?

↓

Post already published?

↓

User owns this resource?
```

These require business knowledge.

Usually they also require database queries.

---

# Example 1 — User Registration

Requirement:

> Register a new user.

### Request Validation

```text
Email required

↓

Email format

↓

Password length

↓

Name required
```

---

### Business Validation

```text
Email already registered?

↓

Invitation required?

↓

Company allows registration?
```

Notice:

Checking whether the email **already exists** is a business decision because it requires querying your system and applying application rules.

# Why Separate Them?

Suppose someone sends:

```json
{
    "email": "abc"
}
```

The email format is invalid.

There is no point querying the database.

Request validation stops the request immediately.

This saves:

- Database queries
    
- CPU time
    
- Service execution
    

---

# Flow

```text
Client

↓

Request Validation

↓

Controller

↓

Service

↓

Business Validation

↓

Repository
```

Only valid requests reach your service.

---

# Common Beginner Mistake

Putting everything into Joi.

Example:

```text
Email format

↓

Password length

↓

User already exists

↓

User owns resource
```

Problem:

Joi validates data.

It shouldn't contain business decisions.

---

# Another Mistake

Putting format validation into the service.

Bad:

```javascript
if (!email.includes("@")) {
    ...
}
```

This belongs in request validation.

The service should assume the data format is already valid.

---

# A Quick Decision Rule

Ask:

### Does it require a database query?

Usually:

→ **Business Validation**

Example:

```text
Email already exists?

↓

Product in stock?

↓

Order exists?
```

---

### Can it be checked without the database?

Usually:

→ **Request Validation**

Example:

```text
Email format

↓

Password length

↓

Required field
```

---

# Real Example

Requirement:

> User changes password.

### Request Validation

```text
Current password provided

↓

New password ≥ 8 characters

↓

Confirm password present
```

---

### Business Validation

```text
Current password correct

↓

New password different

↓

Account active
```

Different responsibilities.

---

# Interview Question

**Q:** Why shouldn't business validation be done in Joi or Zod?

**Good Answer:**

> Joi and Zod are designed to validate the structure and format of incoming data. Business validation depends on application rules and often requires database access, so it belongs in the Service Layer.

---

# Best Practices

✅ Validate request format before reaching the service.

✅ Keep business rules inside services.

✅ Don't duplicate the same validation across multiple layers.

✅ Let each layer focus on its responsibility.

# Mini Exercise

Identify the correct validation layer.

|Rule|Layer|
|---|---|
|Username is required|?|
|Username already taken|?|
|Price must be greater than zero|?|
|User can review a product only after purchasing it|?|
|Phone number matches the expected format|?|

### Answers

- Username is required → **Request Validation**
    
- Username already taken → **Business Validation**
    
- Price must be greater than zero → **Request Validation** (basic numeric constraint)
    
- User can review a product only after purchasing it → **Business Validation**
    
- Phone number matches the expected format → **Request Validation**
