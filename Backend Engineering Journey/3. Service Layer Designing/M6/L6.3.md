# Module 6 — Lesson 6.3: Database Validation ⭐⭐⭐⭐⭐

> **Goal:** Learn why the database must still validate data, even if your controller and service already do validation.

A common beginner question is:

> **"If I already validated everything in my application, why does the database need validation too?"**

The answer is simple:

> **Never trust the application alone. The database is the final guardian of your data.**

---

# The Three Layers Together

```text
Request Validation
        │
        ▼
Business Validation
        │
        ▼
Database Validation
```

Think of it as **three security gates**.

Each gate protects against different problems.

---

# What is Database Validation?

Database validation ensures that **invalid data can never be stored**, even if something goes wrong in your application.

Examples:

- Required fields
    
- Unique values
    
- Data types
    
- Length limits
    
- Foreign key constraints (SQL)
    

---

# Example 1 — User Registration

Suppose your service checks:

```text
Email is unique
```

At the same time:

User A registers:

```text
rahul@example.com
```

User B also registers:

```text
rahul@example.com
```

Both requests arrive almost simultaneously.

Without a database constraint:

```text
Two users

Same email
```

This breaks your application.

---

# Database Protection

Example (Mongoose):

```javascript
email: {
    type: String,
    required: true,
    unique: true
}
```

Now the database refuses duplicate emails.

Even if your service misses it.

# Why Can't We Rely Only on Services?

Imagine another developer writes:

```javascript
await User.create(data);
```

They accidentally skip the service.

Without database constraints:

```text
Invalid data

↓

Stored forever
```

The database protects against programming mistakes.

# Interview Question

**Q:** If you already check that an email is unique in the Service Layer, why also make it unique in the database?

**Good Answer:**

> Because service checks are not enough. Concurrent requests, programming mistakes, or skipped service calls can still insert duplicate data. A database uniqueness constraint guarantees data integrity even when the application layer fails.

---

# Best Practices

✅ Use request validation for input format.

✅ Use services for business rules.

✅ Use the database for data integrity.

✅ Never rely on only one validation layer.

# Mini Exercise

Choose the correct layer.

|Validation|Layer|
|---|---|
|Email is required|?|
|Email format|?|
|Email must be unique|?|
|User owns the order|?|
|Order already shipped|?|
|Status must be one of `draft`, `published`, `archived`|?|

### Answers

- Email is required → **Database** (and often also **Request Validation** for a better user experience)
    
- Email format → **Request Validation**
    
- Email must be unique → **Database** (typically also checked in the service to provide a friendly error)
    
- User owns the order → **Service**
    
- Order already shipped → **Service**
    
- Status must be one of `draft`, `published`, `archived` → **Database** (enum constraint)
