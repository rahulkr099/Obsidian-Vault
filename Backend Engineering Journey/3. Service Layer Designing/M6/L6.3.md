# Module 6 — Lesson 6.3: Organizing Service Methods ⭐⭐⭐⭐⭐

> **Goal:** Learn how to group service methods logically so your application stays organized as it grows.

A common beginner mistake is creating one huge service.

---

# ❌ Bad Design — God Service

```text
UserService

↓

login()

logout()

createPost()

deletePost()

sendEmail()

uploadImage()

placeOrder()

refundOrder()
```

Problems:

- Too many responsibilities
    
- Hard to maintain
    
- Hard to test
    
- Difficult for teams to work on
    

---

# ✅ Good Design — Group by Business Domain

```text
AuthService

↓

login()

logout()

refreshToken()
```

```text
PostService

↓

createPost()

publishPost()

archivePost()
```

```text
OrderService

↓

placeOrder()

cancelOrder()

refundOrder()
```

Each service owns **one business domain**.

---

# Blog App Example

Instead of:

```text
BlogService

↓

Posts

Comments

Likes

Tags

Categories
```

Split it into:

```text
PostService

CommentService

LikeService

TagService

CategoryService
```

Much cleaner.

---

# URL Shortener Example

```text
UrlService

↓

createShortUrl()

deleteShortUrl()

updateShortUrl()

getAnalytics()
```

If analytics becomes very complex later, you might introduce:

```text
AnalyticsService
```

Design should evolve with the application.

---

# A Simple Rule

Ask yourself:

> **"Do these methods belong to the same business domain?"**

If **yes** → Same service.

If **no** → Different services.

Example:

```text
login()

logout()
```

Same domain → **AuthService** ✅

---

Example:

```text
login()

placeOrder()
```

Different domains → Different services ❌

---

# Best Practices

✅ Group methods by **business domain**.

✅ Keep each service focused.

✅ Split services when responsibilities become unrelated.

---

# Interview Question

**Q:** How do you decide whether methods belong in the same service?

**Good Answer:**

> I group methods by business domain and responsibility. If the methods solve the same business problem, they belong in the same service. If they represent different domains, I create separate services to keep the code maintainable.

---

# Key Takeaways

- One service = One business domain.
    
- Avoid "God Services."
    
- Group related business capabilities together.
    
- Split services as the application grows.
