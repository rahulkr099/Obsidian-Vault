# The Complete Validation Flow

Whenever a request comes to your backend, validation happens in stages.

```text
Client
   │
   ▼
Request Validation
   │
   ▼
Controller
   │
   ▼
Service
(Business Validation)
   │
   ▼
Repository
   │
   ▼
Database
(Database Validation)
```

Each layer protects the application in a different way.

---

# Example — User Registration

## Step 1 — Request Validation

Request:

```json
{
    "email": "rahul@example.com",
    "password": "secret123"
}
```

Checks:

```text
✓ Email exists

✓ Email format is valid

✓ Password exists

✓ Password has minimum length
```

If validation fails:

```text
HTTP 400 Bad Request
```

The request never reaches the service.

---

## Step 2 — Service (Business Validation)

Now the data format is valid.

The service checks:

```text
Email already registered?

↓

Invitation required?

↓

Registration allowed?
```

If any rule fails:

```text
Throw Business Error
```

Example:

```javascript
throw new ConflictError(
    "Email already exists"
);
```

---

## Step 3 — Repository

The repository simply performs the database operation.

```javascript
userRepository.create(data);
```

No business rules.

---

## Step 4 — Database Validation

Database checks:

```text
Unique email

↓

Required fields

↓

Schema constraints
```

If something slips through:

```text
Database rejects it
```

---

# Error Flow

Suppose two users register at the same time with the same email.

```text
User A
        │
        ▼
Email available

--------------------

User B
        │
        ▼
Email available
```

Both services think the email is available.

The database finally says:

```text
Duplicate key

↓

Reject second request
```

That's why database validation is essential.

# Common Validation Mistakes

## ❌ Everything in the Controller

```text
Controller

↓

Format checks

↓

Business rules

↓

Database queries
```

The controller becomes huge.

---

## ❌ Everything in Joi

Joi should validate:

```text
Format

Required fields

Types
```

Not:

```text
User owns resource

Coupon expired
```

---

## ❌ No Database Constraints

Never assume:

```text
The service already checked it.
```

The database should still enforce critical constraints.

# The Professional Validation Checklist

For every new feature, ask:

### Request Layer

```text
Is the request well-formed?
```

---

### Service Layer

```text
Is the action allowed?
```

---

### Database Layer

```text
Is the data safe to store?
```

If all three answers are **Yes**, the request is ready to succeed.

# Interview Questions

## Q1. Why do we validate at three different layers?

**Answer:**

> Each layer solves a different problem. Request validation checks input format, the Service Layer enforces business rules, and the database guarantees data integrity. Together they create a reliable backend.

---

## Q2. Should the database still have constraints if the service validates everything?

**Answer:**

> Yes. Database constraints protect against race conditions, programming mistakes, and unexpected application failures.

---

## Q3. Where should "User already owns this post" be validated?

**Answer:**

> In the Service Layer because it is a business rule that depends on application data.
