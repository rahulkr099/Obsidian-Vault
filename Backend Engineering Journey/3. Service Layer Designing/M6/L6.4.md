> **Goal:** Learn the practical rules for designing clean, maintainable service interfaces.

---

# Rule 1 — Design Before You Code

Don't do this:

```text
Open editor

↓

Start coding

↓

Keep adding methods
```

Do this:

```text
Requirements

↓

Design Service Interface

↓

Review

↓

Implement
```

---

# Rule 2 — Methods Should Represent Business Actions

✅ Good

```text
publishPost()

placeOrder()

resetPassword()

enrollStudent()
```

❌ Bad

```text
execute()

process()

handle()

run()
```

---

# Rule 3 — One Method = One Responsibility

❌ Bad

```text
managePost(action)
```

✅ Good

```text
publishPost()

archivePost()

deletePost()
```

Each method should perform one business action.

---

# Rule 4 — One Service = One Business Domain

Good:

```text
AuthService

PostService

CommentService

OrderService
```

Avoid:

```text
AppService
```

that contains everything.

---

# Rule 5 — Keep Interfaces Small

Instead of:

```text
UserService

↓

40 methods
```

Prefer:

```text
AuthService

ProfileService

PasswordService
```

Smaller services are easier to understand and test.

---

# A Professional Example

Before implementation, your design might look like this:

```text
PostService

↓

createPost()

updatePost()

publishPost()

archivePost()

restorePost()

deletePost()

getPost()

listPosts()
```

Only after you're happy with the interface should you implement the methods.

---

# Service Design Checklist

Before writing code, ask yourself:

```text
✓ Does every method represent a business action?

✓ Are method names clear?

✓ Does each method have one responsibility?

✓ Does this service own one business domain?

✓ Is anything unrelated mixed into this service?
```

If every answer is **Yes**, you have a good interface.

---

# Common Beginner Mistakes

## ❌ Designing while coding

Adding methods randomly as new features appear.

---

## ❌ Generic method names

```text
execute()

process()

handle()
```

---

## ❌ One huge service

```text
UserService

↓

Authentication

Posts

Orders

Payments

Emails
```

Split responsibilities instead.

---

# Interview Question

**Q:** What makes a good service interface?

**Good Answer:**

> A good service interface exposes clear business capabilities, uses meaningful method names, keeps one responsibility per method, groups related methods into the same business domain, and is designed before implementation.

# Practice Exercise

Design the interface for a **Library Management System**.

A clean answer might be:

```text
BookService

↓

borrowBook()

returnBook()

reserveBook()

cancelReservation()

searchBooks()
```

Notice that each method represents a **business capability**, and every method belongs to the **Book** domain.
