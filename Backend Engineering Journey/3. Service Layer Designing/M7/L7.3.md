# Module 7 — Lesson 7.3: Permission-Based Authorization ⭐⭐⭐⭐⭐

> **Goal:** Learn how professional applications move beyond roles and use permissions for fine-grained access control.

Small applications usually use **roles**.

Large applications often use **permissions**.

---

# Why Roles Become Difficult

Suppose your application has these roles:

```text
Admin

Manager

Editor

Author

Support

Customer
```

Now a new requirement arrives:

> Managers can refund orders, but Support cannot.

Then another:

> Editors can publish posts but cannot delete them.

Soon your roles become complicated.

---

# The Solution: Permissions

Instead of asking:

```text
Is this user an Admin?
```

Ask:

```text
Does this user have permission
to refund orders?
```

This is more flexible.

---

# Example Permissions

```text
post:create

post:update

post:publish

post:delete

user:delete

order:refund

course:grade
```

Each permission represents one business capability.

---

# Role vs Permission

### RBAC

```text
Admin

↓

Can do everything
```

Simple, but less flexible.

---

### Permission-Based

```text
Manager

↓

order:view

order:update

order:refund
```

Different users with the same role can even have different permission sets if needed.

---

# Example

Requirement:

> User refunds an order.

Instead of:

```javascript
if(user.role !== "admin")
```

Use:

```javascript
if (
    !user.permissions.includes(
        "order:refund"
    )
) {
    throw new ForbiddenError();
}
```

The service checks the required permission.

# Roles Can Contain Permissions

A common design is:

```text
Role

↓

Collection of Permissions
```

Example:

```text
Admin

↓

All permissions

-------------------

Editor

↓

post:create

post:update

post:publish

-------------------

Support

↓

order:view

customer:view
```

The application checks permissions, while roles are simply a convenient way to group them.

---

# Where Does Permission Checking Happen?

Exactly like other authorization rules.

```text
Controller

↓

Service

↓

Permission Check

↓

Repository
```

The service decides whether the action is allowed.

---

# Helper Function

Instead of repeating:

```javascript
if (!user.permissions.includes(...))
```

many times,

you can create a helper.

Example:

```javascript
permissionService.hasPermission(
    user,
    "order:refund"
);
```

Now your service stays cleaner.

# Common Beginner Mistakes

## ❌ Hardcoding Roles Everywhere

```javascript
if(role === "admin")

if(role === "admin")

if(role === "admin")
```

Later, adding a new role becomes difficult.

---

## ✅ Check Capabilities

Instead:

```text
Can refund?

↓

Can publish?

↓

Can delete?
```

Think in terms of **what the user can do**, not **what the user is called**.

---

## ❌ Trusting the Frontend

The frontend may hide a button.

Example:

```text
Delete Button Hidden
```

Good for user experience.

But the backend must still verify the permission before performing the action.

---

# Interview Question

**Q:** When would you use permissions instead of only roles?

**Good Answer:**

> Roles work well for simple systems, but permissions provide fine-grained control. They allow different users or roles to perform specific actions such as `order:refund` or `post:publish` without creating many specialized roles.

---

# Best Practices

✅ Use **roles** for simple applications.

✅ Use **permissions** when authorization becomes more detailed.

✅ Group permissions into roles.

✅ Check permissions inside the **Service Layer**.

---

### Answers
