# Module 7 — Lesson 7.4: Authorization Best Practices ⭐⭐⭐⭐⭐

> **Goal:** Learn the practical security rules that professional backend engineers follow when implementing authorization.

This lesson summarizes everything from Module 7 into a simple set of rules you can apply to every backend project.

---

# The Authorization Flow

Every protected request should follow this flow:

```text
Client
   │
   ▼
Authentication
(Who are you?)
   │
   ▼
Controller
   │
   ▼
Service
(Can you do this?)
   │
   ▼
Repository
```

Remember:

- **Authentication** identifies the user.
    
- **Authorization** decides whether the action is allowed.
    

---

# Rule 1 — Never Trust the Frontend

Bad:

```javascript
if (req.body.isAdmin) {
    // Allow
}
```

The client can send any value.

Good:

```javascript
if (req.user.role === "admin") {
    // Allow
}
```

Use information from the authenticated user, not from the request body.

---

# Rule 2 — Authorization Belongs in Services

Bad:

```javascript
if (post.author !== req.user.id) {
    return res.status(403).json(...);
}
```

inside the controller.

Good:

```javascript
await postService.deletePost({
    userId: req.user.id,
    postId: req.params.id
});
```

The service performs the authorization.

---

# Rule 3 — Check Before Changing Data

Wrong order:

```text
Update Database

↓

Check Permission
```

Correct order:

```text
Check Permission

↓

Update Database
```

Always verify authorization first.

---

# Rule 4 — Prefer "Owner or Admin"

Many real applications use this rule.

```text
Owner?

↓

Yes → Allow

↓

No

↓

Admin?

↓

Yes → Allow

↓

No

↓

Reject
```

Simple and effective.

---

# Rule 5 — Think in Capabilities

Instead of:

```text
Is user an Admin?
```

Think:

```text
Can this user

publish?

refund?

delete?

grade?
```

Capabilities scale better than hardcoded roles.

---

# Rule 6 — Return Proper Errors

Unauthorized request:

```text
ForbiddenError
```

Resource missing:

```text
NotFoundError
```

Invalid input:

```text
ValidationError
```

Use errors that clearly describe the problem.

---

# Common Security Mistakes

## ❌ Only Protecting the Frontend

Example:

```text
Hide Delete Button
```

Users can still call the API directly.

The backend must enforce authorization.

---

## ❌ Skipping Ownership Checks

Requirement:

> Edit profile.

Always verify:

```text
Does this profile belong to the user?
```

---

## ❌ Hardcoding Roles Everywhere

Bad:

```javascript
if(role==="admin")

if(role==="admin")

if(role==="admin")
```

As the application grows, this becomes difficult to maintain.

Use helper methods or a permission service instead.

---

# A Reusable Permission Helper

Instead of repeating checks:

```javascript
if (!isOwner && !isAdmin) {
    throw new ForbiddenError();
}
```

You can centralize them.

Example:

```javascript
permissionService.canDeletePost(
    user,
    post
);
```

Benefits:

- Less duplication
    
- Easier to test
    
- Easier to update rules
    

---

# Complete Example

Requirement:

> Delete a blog post.

Flow:

```text
Authenticate User

↓

Find Post

↓

Owner?

↓

Admin?

↓

Delete Post

↓

Return Success
```

Notice that authorization happens **before** the delete operation.

# Authorization Checklist

Before implementing a feature, ask:

```text
✓ Who is the user?

✓ What resource is being accessed?

✓ Does the resource exist?

✓ Does the user own it?

✓ Does the user's role allow this?

✓ Does the user have the required permission?

✓ Only then perform the action.
```

This checklist helps prevent common security bugs.

# Interview Questions

## Q1. Why shouldn't the frontend handle authorization?

**Answer:**

> The frontend can improve the user experience by hiding unavailable actions, but it cannot enforce security. Anyone can call the backend API directly, so authorization must always be enforced on the server.

---

## Q2. Where should authorization checks live?

**Answer:**

> Authorization is a business rule, so it belongs in the Service Layer. Controllers should pass the authenticated user's information to the service, and the service decides whether the action is allowed.

---

## Q3. What is the difference between RBAC and permission-based authorization?

**Answer:**

> RBAC grants permissions based on roles such as Admin or Editor. Permission-based authorization checks specific capabilities like `post:publish` or `order:refund`, providing finer control.

# Mini Project

Design the authorization for this requirement:

> **A teacher can grade assignments, but students can only view their own submissions.**

### Solution

**Authentication**

```text
Verify JWT

↓

Identify user
```

**Authorization**

```text
Teacher?

↓

Can grade assignment

-----------------

Student?

↓

Own submission?

↓

Allow viewing
```

**Service Methods**

```javascript
assignmentService.gradeAssignment()

assignmentService.viewSubmission()
```

The service contains the authorization rules.
