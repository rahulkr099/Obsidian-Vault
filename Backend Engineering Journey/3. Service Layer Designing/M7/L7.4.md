# Module 7 — Lesson 7.4: DTO Best Practices ⭐⭐⭐⭐⭐

> **Goal:** Learn the practical rules professional backend engineers follow when using DTOs.

This lesson summarizes the entire module.

---

# Rule 1 — Never Pass `req` or `res`

❌ Bad

```javascript
await postService.createPost(req);
```

✅ Good

```javascript
await postService.createPost({
    authorId: req.user.id,
    title: req.body.title,
    content: req.body.content
});
```

A service should not know Express exists.

---

# Rule 2 — Pass Only What Is Needed

❌ Bad

```javascript
{
    user,
    post,
    settings,
    session,
    cookies
}
```

If the service only needs:

```javascript
{
    userId,
    postId
}
```

Pass only those fields.

---

# Rule 3 — Keep DTOs as Plain Objects

A DTO should contain:

- Data ✅
    

It should **not** contain:

- Business logic ❌
    
- Database queries ❌
    
- Methods ❌
    

Example:

```javascript
{
    email,
    password
}
```

---

# Rule 4 — Don't Expose Sensitive Data

Bad Response DTO:

```javascript
{
    id,
    name,
    email,
    password,
    refreshToken
}
```

Good Response DTO:

```javascript
{
    id,
    name,
    email
}
```

Only return what the client actually needs.

---

# Rule 5 — DTOs Make Services Reusable

Because services don't depend on Express:

The same service can be called from:

```text
REST API

↓

GraphQL

↓

Cron Job

↓

Background Worker

↓

CLI Script
```

The service only expects a DTO.

---

# Complete Flow

```text
HTTP Request

↓

Controller

↓

Request DTO

↓

Service

↓

Response DTO

↓

Controller

↓

HTTP Response
```

This keeps every layer independent.

---

# Common Beginner Mistakes

### ❌ Passing `req`

```javascript
service(req);
```

---

### ❌ Returning the entire database document

```javascript
return user;
```

This may expose internal fields.

---

### ❌ Passing huge objects

Instead of:

```javascript
{
    user,
    post,
    comments,
    session,
    cookies
}
```

Pass only:

```javascript
{
    userId,
    postId
}
```

# Interview Questions

### Q1. Why use DTOs?

**Answer:**

> DTOs reduce coupling between layers by transferring only the required data. They make services reusable, easier to test, and independent of frameworks like Express.

---

### Q2. Why shouldn't services receive `req`?

**Answer:**

> Because `req` is an Express object. A service should only depend on business data, not on the web framework.

---

### Q3. Why use Response DTOs?

**Answer:**

> Response DTOs prevent exposing internal or sensitive fields and provide a stable API response format.

# One-Page Cheat Sheet

|DTO Type|Purpose|Example|
|---|---|---|
|**Request DTO**|Data sent to Service|`{ userId, title }`|
|**Response DTO**|Data returned to Controller|`{ id, title }`|
|**Internal DTO**|Data exchanged between Services|`{ userId, postTitle }`|
