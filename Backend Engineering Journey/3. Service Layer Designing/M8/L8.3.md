# Module 8 — Lesson 8.3: Database Validation ⭐⭐⭐⭐⭐

> **Goal:** Learn why the database should still validate data even after Request and Business Validation.

A common beginner question is:

> **"If I've already validated everything in my application, why does the database need validation?"**

Because **the database is the last line of defense**.

---

# The Three Validation Layers

```text
Request Validation

↓

Business Validation

↓

Database Validation
```

If the first two layers miss something, the database protects your data.

---

# What Does Database Validation Do?

The database enforces **data integrity**.

Common constraints:

- Required fields
    
- Unique values
    
- Enum values
    
- Data types
    
- Foreign key constraints (SQL)
    

---

# Example 1 — Unique Email

Even if your service checks:

```text
Email already exists?
```

Two users might register at almost the same time.

```text
User A

↓

rahul@example.com

----------------

User B

↓

rahul@example.com
```

Both requests pass the service check.

The database's **unique constraint** prevents duplicate records.

---

# Example 2 — Blog Status

Allowed values:

```text
draft

published

archived
```

Database constraint:

```javascript
status: {
    enum: [
        "draft",
        "published",
        "archived"
    ]
}
```

Invalid values cannot be stored.

---

# Example 3 — Required Field

Suppose every post must have a title.

Database rule:

```text
title

↓

required
```

Even if a developer accidentally skips request validation, the database still rejects invalid data.

---

# Responsibility Comparison

|Layer|Responsibility|
|---|---|
|Request Validation|Is the request well-formed?|
|Business Validation|Is the action allowed?|
|Database Validation|Is the data safe to store?|

Each layer has a different job.

---

# Common Mistakes

## ❌ Only Relying on the Service

```text
Service checks uniqueness

↓

Database has no unique constraint
```

Risk:

Duplicate data because of race conditions.

---

## ❌ Putting Business Rules in the Database

Bad example:

```text
Only premium users
can create custom aliases.
```

This is a **business rule**.

It belongs in the **Service Layer**, not the database.

---

# Best Practices

✅ Use database constraints for:

- Uniqueness
    
- Required fields
    
- Allowed values
    
- Data integrity
    

✅ Keep business rules in the Service Layer.

---

# Interview Question

**Q:** If the service already checks that an email is unique, why should the database also enforce uniqueness?

**Good Answer:**

> Because concurrent requests or programming mistakes can bypass the service check. A database uniqueness constraint guarantees data integrity even if the application layer fails.

---

# Key Takeaways

- The database is the **final safeguard**.
    
- Use it to enforce **data integrity**, not business rules.
    
- Database validation complements request and business validation.
    
- All three validation layers work together.
