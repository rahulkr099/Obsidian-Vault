# Lesson 9.1 — Why Authorization Belongs in Services

> **Goal:** Understand why authorization is a business rule.

---

## Authentication vs Authorization

**Authentication**

```text
Who are you?
```

Example:

- Verify JWT
    
- Identify user
    

Usually done in **middleware**.

---

**Authorization**

```text
What are you allowed to do?
```

Examples:

- Can this user edit the post?
    
- Can this user delete this order?
    
- Can this user refund this payment?
    

These are **business rules**.

---

# Professional Flow

```text
Route

↓

Authentication Middleware

↓

Controller

↓

Service

↓

Repository
```

Middleware identifies the user.

The **Service** decides whether the action is allowed.

---

# Example

Requirement:

> User deletes a blog post.

Service workflow:

```text
Find post

↓

Check ownership

↓

Delete post
```

The ownership check belongs inside the service.

---

# Why Not the Controller?

❌ Bad

```text
Controller

↓

Check ownership

↓

Call service
```

If another controller needs the same rule, you'll duplicate it.

---

✅ Good

```text
Controller

↓

postService.deletePost(dto)
```

The service handles authorization once and can be reused everywhere.

---

# Best Practices

✅ Authentication → **Middleware**

✅ Authorization → **Service Layer**

✅ Controllers should not contain business permission checks.

---

# Interview Question

**Q:** Why should authorization be handled in the Service Layer?

**Good Answer:**

> Authorization is a business rule. The Service Layer has access to business data and workflows, making it the correct place to decide whether an action is allowed. This also keeps controllers thin and avoids duplicated authorization logic.

---

# Key Takeaways

- Authentication identifies the user.
    
- Authorization decides what the user can do.
    
- Authorization belongs in the **Service Layer**.
    
- Controllers should simply call the service.
