# Module 9 — Lesson 9.2: Ownership Checks ⭐⭐⭐⭐⭐

> **Goal:** Learn how to implement the most common authorization rule: **A user can only modify their own resources.**

Ownership checks are used in almost every backend application.

---

# What is an Ownership Check?

Before performing an action, ask:

> **"Does this resource belong to the current user?"**

If yes:

```text
Allow
```

If no:

```text
Reject
```

---

# Example — Blog App

Requirement:

> User edits a post.

Workflow:

```text
Find post

↓

Compare owner

↓

Update post
```

The comparison is:

```text
post.authorId

==

currentUser.id
```

If they match, the update is allowed.

---

# Example — Todo App

Requirement:

> User deletes a task.

Workflow:

```text
Find task

↓

Task belongs to user?

↓

Delete task
```

---

# Example — URL Shortener

Requirement:

> User edits a short URL.

Workflow:

```text
Find URL

↓

Owner?

↓

Update URL
```

A user must not be able to edit someone else's short URL.

---

# Where Does This Check Belong?

✅ Correct

```text
Controller

↓

UrlService

↓

Ownership Check

↓

Repository
```

❌ Wrong

```text
Controller

↓

Ownership Check

↓

Repository
```

Ownership is a **business rule**, so it belongs in the **Service Layer**.

---

# Simple Pseudocode

```text
Find resource

↓

Owner matches current user?

↓

Yes → Continue

No → Throw ForbiddenError
```

This pattern works for almost every resource.

---

# Common Mistakes

## ❌ Trusting the Client

Bad:

```text
Client says:

"I own this post."
```

Never trust the client.

Always verify ownership using data from your database.

---

## ❌ Skipping the Check

Suppose your API is:

```text
PUT /posts/:id
```

Without an ownership check:

```text
Any logged-in user

↓

Can edit any post
```

This is a serious security bug.

---

# Best Practices

✅ Load the resource first.

✅ Compare the resource owner's ID with the authenticated user's ID.

✅ Reject unauthorized requests before making changes.

---

# Interview Question

**Q:** How do you implement an ownership check?

**Good Answer:**

> The service first retrieves the resource, compares the resource owner's ID with the authenticated user's ID, and throws a `ForbiddenError` if they don't match. Only if the user is the owner does the service continue with the operation.

---

# Key Takeaways

- Ownership checks are the most common authorization rule.
    
- Always verify ownership on the server.
    
- Keep ownership checks inside the **Service Layer**.
    
- Never trust data sent by the client.
