# Module 1 — Introduction to the Repository Pattern

## Lesson 1.1 — Why We Need a Repository

### 🎯 Learning Objectives

By the end of this lesson, you will understand:

- Why repositories exist.
    
- The problems with writing database queries everywhere.
    
- How the Repository Pattern improves code quality.
    
- Where a repository fits in a backend application.
    
- When you should use it in a Node.js + Express + MongoDB project.
    

---

# What Problem Are We Solving?

Imagine you're building a **Blog App**.

Your first API is:

```http
POST /posts
```

A beginner often writes code like this:

```text
Controller
    │
    ├── Validate input
    ├── Check authentication
    ├── Check permissions
    ├── Create slug
    ├── Save post to MongoDB
    ├── Send notification
    └── Return response
```

The controller is doing **everything**.

This quickly becomes difficult to maintain.

---

# Moving Business Logic to the Service

A better approach is:

```text
Controller
      │
      ▼
Service
      │
      ▼
MongoDB
```

The controller only handles HTTP.

The service contains business logic.

Example:

```text
Controller

↓

postService.createPost()

↓

Post.create()
```

This is much better.

But there's still a problem.

---

# The Remaining Problem

Your service now directly talks to MongoDB.

Example:

```text
Service

↓

Post.findById()

↓

Post.find()

↓

Post.updateOne()

↓

Post.aggregate()
```

Now your service knows:

- Mongoose methods
    
- Database queries
    
- MongoDB operators
    
- Aggregation pipelines
    
- Population logic
    

Your business logic is mixed with database logic.

---

# A Real Example

Suppose you need to publish a post.

Without a repository:

```javascript
async function publishPost(postId) {
    const post = await Post.findById(postId);

    if (!post) {
        throw new Error("Post not found");
    }

    post.status = "published";

    await post.save();

    return post;
}
```

The service is directly using Mongoose.

If tomorrow you change the database, every service using `Post.findById()` or `post.save()` may need updates.

---

# Introducing the Repository Pattern

Instead of accessing the database directly, create a repository.

```text
Controller
      │
      ▼
Service
      │
      ▼
Repository
      │
      ▼
MongoDB
```

Now the service communicates only with the repository.

---

# The Same Example with a Repository

```text
Controller

↓

PostService

↓

PostRepository

↓

MongoDB
```

Service:

```javascript
async function publishPost(postId) {
    const post = await postRepository.findById(postId);

    if (!post) {
        throw new Error("Post not found");
    }

    return await postRepository.publish(postId);
}
```

Repository:

```javascript
async function findById(id) {
    return await Post.findById(id);
}

async function publish(id) {
    return await Post.findByIdAndUpdate(
        id,
        { status: "published" },
        { new: true }
    );
}
```

Notice the difference:

- **Service** decides _what_ should happen.
    
- **Repository** knows _how_ to interact with the database.
    

---

# Responsibilities Become Clear

### Controller

Responsible for:

- Reading requests
    
- Returning responses
    
- HTTP status codes
    

Should **not**:

- Write business logic
    
- Access the database
    

---

### Service

Responsible for:

- Business rules
    
- Validation that depends on business logic
    
- Permissions
    
- Workflows
    

Example:

```text
Can this user publish this post?

↓

Should notifications be sent?

↓

Should user statistics be updated?
```

The service decides **what** needs to happen.

---

### Repository

Responsible for:

- Reading data
    
- Writing data
    
- Updating data
    
- Deleting data
    
- Database queries
    
- Aggregation
    
- Pagination
    

The repository decides **how** to get the data.

---

# Benefits of the Repository Pattern

## 1. Separation of Concerns

Every layer has one clear responsibility.

```text
Controller

↓

Service

↓

Repository

↓

Database
```

This makes the application easier to understand.

---

## 2. Easier Maintenance

Suppose you change:

```text
MongoDB

↓

PostgreSQL
```

Without repositories:

Every service may need changes.

With repositories:

Only the repository layer changes, while controllers and services stay mostly the same.

---

## 3. Better Testability

Suppose you're testing `publishPost()`.

Without a repository:

Your test needs a real database or complex Mongoose mocks.

With a repository:

```javascript
postRepository.findById = async () => ({
    id: 1,
    status: "draft",
});
```

You can mock the repository and test only the business logic.

---

## 4. Cleaner Services

Bad:

```javascript
const post = await Post.findOne(...);
await Post.updateOne(...);
await Post.aggregate(...);
```

Good:

```javascript
const post = await postRepository.findById(id);

await postRepository.update(id, data);

const stats = await postRepository.getStatistics();
```

The service reads like plain English.

---

## 5. Reusable Data Access

Different services can reuse the same repository methods.

Example:

```text
Admin Service

↓

PostRepository.findById()
```

```text
Analytics Service

↓

PostRepository.findById()
```

No duplicated database queries.

---

# Common Misconception

Many developers think:

> "Repositories are only useful for large projects."

Not true.

Even a small Todo App benefits because:

- Controllers stay simple.
    
- Services stay focused on business logic.
    
- Database code stays in one place.
    
- Future changes become easier.

---

# Key Takeaways

- The **Repository Pattern** separates business logic from database logic.
    
- Controllers should only handle HTTP requests and responses.
    
- Services contain business rules and workflows.
    
- Repositories handle all database interactions.
    
- This structure makes applications more maintainable, testable, and scalable.
    
- Repositories let your service layer remain independent of the database implementation.
