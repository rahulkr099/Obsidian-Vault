# The Big Picture

A professional backend application is divided into layers.

```text
                HTTP Request
                     │
                     ▼
                 Route Layer
                     │
                     ▼
              Middleware Layer
                     │
                     ▼
              Controller Layer
                     │
                     ▼
                Service Layer
                     │
                     ▼
             Repository Layer
                     │
                     ▼
                 Database
                     │
                     ▼
                HTTP Response
```

Each layer has **one clear responsibility**.

Think of it like a restaurant.

```text
Customer
    │
    ▼
Receptionist
    │
    ▼
Waiter
    │
    ▼
Chef
    │
    ▼
Kitchen Store
```

No one does everyone else's job.

The same idea applies to backend architecture.

# Example: Create a Blog Post

Request:

```http
POST /api/posts
```

The request travels through each layer.

```text
Client

↓

Route

↓

Authentication Middleware

↓

Validation Middleware

↓

Controller

↓

Service

↓

Repository

↓

MongoDB
```

Then the response travels back.

---

# Layer 1 — Route

### Responsibility

The Route decides **which controller should handle the request**.

Example:

```text
POST /posts

↓

postController.createPost
```

### Route Should

- Define API endpoints
    
- Connect endpoints to controllers
    
- Group related routes
    

### Route Should NOT

- Validate data
    
- Query the database
    
- Write business logic
    

Routes should stay very small.

---

# Layer 2 — Middleware

Middleware performs tasks **before the controller runs**.

Examples:

```text
Authentication

↓

Authorization

↓

Input Validation

↓

Rate Limiting

↓

Logging
```

### Middleware Should

- Verify JWT tokens
    
- Validate request data
    
- Check permissions (basic)
    
- Log requests
    
- Handle CORS
    
- Apply rate limits
    

### Middleware Should NOT

- Create blog posts
    
- Update the database
    
- Implement business workflows
    

---

# Layer 3 — Controller

The controller is the **bridge between HTTP and your application**.

Example:

```text
HTTP Request

↓

Controller

↓

Service

↓

HTTP Response
```

### Controller Responsibilities

- Read request data
    
- Read URL parameters
    
- Read query parameters
    
- Call the correct service
    
- Return HTTP responses
    

Example flow:

```text
req.body

↓

postService.createPost()

↓

res.status(201).json(...)
```

### Controller Should NOT

- Query MongoDB
    
- Check business rules
    
- Calculate statistics
    
- Send emails
    
- Handle complex logic
    

Controllers should stay thin.

---

# Layer 4 — Service

The Service contains **business logic**.

It answers questions like:

```text
Can the user publish this post?

↓

Should a notification be sent?

↓

Should the author's post count increase?

↓

Should activity be logged?
```

The Service coordinates multiple operations.

Example:

```text
Create Post

↓

Generate Slug

↓

Save Post

↓

Update User Statistics

↓

Log Activity

↓

Return Result
```

### Service Should

- Implement business rules
    
- Coordinate workflows
    
- Call repositories
    
- Call external services
    
- Handle application logic
    

### Service Should NOT

- Use `Post.find()`
    
- Write MongoDB queries
    
- Use SQL directly
    

---

# Layer 5 — Repository

The Repository is responsible for **all database interactions**.

Example:

```text
Service

↓

postRepository.findById()

↓

MongoDB
```

### Repository Responsibilities

- Create records
    
- Read records
    
- Update records
    
- Delete records
    
- Search
    
- Filter
    
- Pagination
    
- Aggregation
    

### Repository Should NOT

- Send emails
    
- Check permissions
    
- Return HTTP responses
    
- Decide business rules
    

Repositories only manage data.

---

# Layer 6 — Database

The database stores your application's data.

Examples:

- MongoDB
    
- PostgreSQL
    
- MySQL
    
- SQLite
    

The database should never be accessed directly by controllers or services.

# A Simple Responsibility Table

|Layer|Main Responsibility|Should NOT Do|
|---|---|---|
|Route|Map URL to controller|Business logic|
|Middleware|Pre-processing requests|Database operations|
|Controller|Handle HTTP requests/responses|Business logic|
|Service|Business rules and workflows|Database queries|
|Repository|Data access|Business logic|
|Database|Store data|Application logic|

# Common Beginner Mistakes

### ❌ Controller Does Everything

```text
Controller

↓

Validation

↓

Business Logic

↓

MongoDB Query

↓

Email

↓

Response
```

This becomes hard to maintain.

---

### ❌ Service Uses Mongoose Everywhere

```javascript
Post.find()
Post.findById()
Post.updateOne()
Post.aggregate()
```

Now the service is tightly coupled to MongoDB.

---

### ❌ Repository Contains Business Logic

Bad example:

```javascript
publishPost()
approveComment()
banUser()
```

These are **business actions**, so they belong in the **Service**.

A repository should expose data operations like:

```text
findById()
create()
update()
delete()
findPublished()
count()
```

---

# Benefits of This Architecture

When each layer has one responsibility:

- ✅ Code is easier to understand.
    
- ✅ Testing becomes simpler.
    
- ✅ Features are easier to add.
    
- ✅ Changing the database affects only repositories.
    
- ✅ Business rules stay in one place.
    
- ✅ Teams can work on different layers independently.

# Key Takeaways

- A professional backend application is built using **layers**, each with a single responsibility.
    
- The **Controller** handles HTTP.
    
- The **Service** handles business logic.
    
- The **Repository** handles data access.
    
- Keeping responsibilities separate makes the application easier to test, maintain, and scale.
    
- This layered architecture is widely used in real-world Node.js applications, especially in medium to large codebases.
