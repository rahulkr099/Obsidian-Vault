# Lesson 10.1 — Common Repository Anti-Patterns

## 🎯 Learning Objectives

By the end of this lesson, you will understand:

- Why they make applications difficult to maintain.
    
- How to identify bad repository designs.
    
- Best practices for keeping repositories clean.
    

---

# What is an Anti-Pattern?

An **anti-pattern** is a common solution that initially seems correct but creates problems as the application grows.

Example:

```text
Works Today

↓

Hard to Maintain Tomorrow
```

Professional developers avoid these patterns early.

---

# Anti-Pattern 1 — Huge Repository

Imagine this repository:

```text
UserRepository

↓

150 Methods
```

It contains:

- CRUD
    
- Search
    
- Analytics
    
- Notifications
    
- Reports
    
- Authentication
    
- Settings
    

Finding the right method becomes difficult.

---

### Better Design

Split responsibilities.

```text
UserRepository

↓

CRUD
```

```text
UserAnalyticsRepository

↓

Reports
```

```text
UserSettingsRepository

↓

Settings
```

Each repository has a clear purpose.

---

# Anti-Pattern 2 — Business Logic Inside Repository

Bad:

```text
publishPost()

approveComment()

banUser()
```

These methods represent **business actions**.

Repositories should perform data operations.

---

### Correct Design

Service:

```text
Check Permissions

↓

Validate Rules

↓

Repository.update()
```

The Service decides **what** should happen.

The Repository updates the database.

---

# Anti-Pattern 3 — Controller Calls Repository Directly

Bad architecture:

```text
Controller

↓

Repository
```

Business logic is skipped.

---

Correct architecture:

```text
Controller

↓

Service

↓

Repository
```

The Service Layer should never be bypassed.

---

# Anti-Pattern 4 — Returning HTTP Responses

Bad:

```text
Repository

↓

404 Not Found
```

Repositories don't know:

- HTTP
    
- Express
    
- Status codes
    

They should only return data or throw application errors.

---

# Anti-Pattern 5 — Exposing Database APIs

Bad interface:

```text
findOne()

findMany()

aggregate()

updateOne()
```

These are MongoDB concepts.

Better:

```text
findByEmail()

findPublished()

findPopular()
```

The interface should describe the application's language.

---

# Anti-Pattern 6 — One Repository for Everything

Bad:

```text
ApplicationRepository
```

Handles:

- Users
    
- Posts
    
- Comments
    
- Orders
    
- Payments
    

Eventually it becomes impossible to maintain.

---

### Better

```text
UserRepository

PostRepository

CommentRepository

OrderRepository

PaymentRepository
```

One repository per entity (or responsibility).

---

# Anti-Pattern 7 — Duplicate Queries

Imagine:

```text
Service A

↓

Post.findById()
```

```text
Service B

↓

Post.findById()
```

```text
Service C

↓

Post.findById()
```

Now every service duplicates the same query.

A repository prevents this.

---

# Repository Checklist

A good repository should answer **YES** to these questions:

✅ Does it manage one entity?

✅ Does it expose business-friendly methods?

✅ Does it avoid business logic?

✅ Does it hide database implementation?

✅ Is it reusable?

---

# Common Beginner Mistakes

### ❌ Repository Imports Express

Repositories should never use:

- `req`
    
- `res`
    
- HTTP status codes
    

---

### ❌ Service Imports Mongoose

The Service should never use:

```text
Post.find()

Post.updateOne()
```

Only repositories should import models.

---

### ❌ Repository Sends Emails

Email sending belongs to a separate service.

Repositories manage data only.

---

# Best Practices

✅ Keep repositories small.

✅ Keep one responsibility per repository.

✅ Use business-friendly method names.

✅ Keep business logic in services.

✅ Keep HTTP in controllers.

---

# Key Takeaways

- A repository should focus only on **data access**.
    
- Avoid huge repositories with unrelated responsibilities.
    
- Never bypass the Service Layer.
    
- Keep business logic, HTTP logic, and database logic in their proper layers.
    
- Clean repositories are easier to test, maintain, and extend.

# Lesson 10.2 — Refactoring Repositories

## 🎯 Learning Objectives

By the end of this lesson, you will understand:

- When to refactor a repository.
    
- How to split large repositories.
    
- Read/Write repository separation.
    
- How to keep repositories maintainable.
    

---

# When Should You Refactor?

Suppose your `PostRepository` grows like this:

```text
CRUD

↓

Search

↓

Analytics

↓

Caching

↓

Reports

↓

Statistics
```

Eventually:

```text
PostRepository

↓

120 Methods
```

Finding anything becomes difficult.

---

# Step 1 — Identify Responsibilities

Ask:

> What different jobs is this repository performing?

Example:

```text
CRUD

Analytics

Search

Reports
```

Each may deserve its own repository.

---

# Step 2 — Split by Responsibility

Instead of:

```text
PostRepository
```

Create:

```text
PostRepository

↓

CRUD
```

```text
PostAnalyticsRepository

↓

Statistics
```

```text
PostSearchRepository

↓

Searching
```

---

# Read/Write Separation

Large systems sometimes separate reading and writing.

Example:

```text
PostReadRepository

↓

Read Operations
```

```text
PostWriteRepository

↓

Create

Update

Delete
```

This is useful when:

- Read traffic is much higher.
    
- Different databases are used for reads and writes.
    

---

# Example Architecture

```text
PostReadRepository

↓

findById()

search()

findPublished()
```

```text
PostWriteRepository

↓

create()

update()

delete()
```

Each repository stays focused.

---

# Should Every Project Do This?

No.

For:

- Todo Apps
    
- Blog Apps
    
- Portfolio Projects
    

One repository is usually enough.

Split repositories only when complexity increases.

---

# Signs It's Time to Refactor

Your repository has:

- Over 50–100 methods.
    
- Multiple unrelated responsibilities.
    
- Difficult-to-find methods.
    
- Frequent merge conflicts.
    
- Large files.
    

These are good indicators.

---

# Don't Refactor Too Early

Some developers create:

```text
PostReadRepository

PostWriteRepository

PostAnalyticsRepository

PostCacheRepository
```

for a simple CRUD app.

This is unnecessary complexity.

Start simple.

Refactor when needed.

---

# Practical Example

### Small Blog App

```text
PostRepository
```

Perfectly fine.

---

### Large Blogging Platform

```text
PostRepository

PostAnalyticsRepository

PostSearchRepository
```

Better organization.

---

### Enterprise System

```text
PostReadRepository

PostWriteRepository

PostAnalyticsRepository

PostCacheRepository
```

Only when justified.

---

# Common Mistakes

## ❌ Splitting Too Early

Don't over-engineer.

---

## ❌ Keeping Everything Together Forever

Large repositories become difficult to maintain.

---

## ❌ Splitting by Database Tables Only

Think about **responsibilities**, not just entities.

---

# Best Practices

✅ Start with one repository.

✅ Refactor when responsibilities grow.

✅ Split by responsibility, not by habit.

✅ Keep repositories cohesive.

---

---

# Key Takeaways

- Refactor repositories when they become too large or take on multiple responsibilities.
    
- Split repositories by **responsibility**, not just by entity.
    
- Read/Write separation is useful in large systems, but unnecessary for most small projects.
    
- Avoid both **under-engineering** and **over-engineering**.
    
- Let your application's complexity guide your architecture.
