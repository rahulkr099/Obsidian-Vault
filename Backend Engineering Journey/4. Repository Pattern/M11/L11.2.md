# Module 11 — Blog Application Case Study

# Lesson 11.2 — End-to-End Request Flow

> **Golden Rule:** A request should flow **through each layer exactly once**, with each layer performing **one responsibility**.

---

# 🎯 Learning Objectives

By the end of this lesson, you will understand:

- The complete lifecycle of a backend request.
    
- How all architectural layers work together.
    
- The responsibility of each layer.
    
- How repositories fit into a real application.
    
- Common mistakes in request flow.

# The Big Picture

Let's follow a real request from the client to the database.

Suppose a user creates a blog post.

```http
POST /api/posts
```

The request travels through the application like this:

```text
Client
   │
   ▼
Route
   │
   ▼
Middleware
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
MongoDB
   │
   ▼
Response
```

Every layer has **one responsibility**.

---

# Step 1 — Client Sends Request

Example:

```http
POST /api/posts

{
    "title": "Repository Pattern",
    "content": "..."
}
```

The client knows nothing about:

- Services
    
- Repositories
    
- MongoDB
    

It only sends an HTTP request.

---

# Step 2 — Route

The route maps the URL to the correct controller.

```text
POST /posts

↓

postController.createPost
```

Responsibilities:

- Match URL
    
- Match HTTP method
    
- Call controller
    

Nothing more.

---

# Step 3 — Middleware

The request passes through middleware.

Example:

```text
Verify JWT

↓

Validate Input

↓

Rate Limiter
```

If validation fails:

```text
400 Bad Request
```

The request never reaches the controller.

---

# Step 4 — Controller

The controller reads the HTTP request.

Responsibilities:

```text
Read req.body

↓

Read req.params

↓

Read req.user

↓

Call Service

↓

Return Response
```

The controller **does not**:

- Query MongoDB
    
- Apply business rules
    
- Write SQL
    

---

# Step 5 — Service

Now business logic begins.

Example workflow:

```text
Verify User

↓

Generate Slug

↓

Check Duplicate Slug

↓

Create Post

↓

Update Statistics

↓

Create Activity
```

Notice:

The service coordinates multiple repositories.

---

# Step 6 — Repository

The repository performs the database operations.

Example:

```text
Insert Post

↓

Find User

↓

Update Statistics
```

The repository knows:

- MongoDB
    
- Mongoose
    
- Queries
    
- Indexes
    
- Transactions
    

The Service doesn't.

---

# Step 7 — Database

MongoDB executes the queries.

Possible outcomes:

```text
Insert Successful
```

or

```text
Duplicate Key
```

The repository translates database errors into application-friendly errors.

---

# Step 8 — Response Travels Back

After success:

```text
Repository

↓

Service

↓

Controller

↓

Client
```

The controller returns:

```http
201 Created
```

---

# Example: Publish Post

Let's follow a larger workflow.

User clicks:

```http
POST /posts/123/publish
```

Flow:

```text
Controller

↓

PostService

↓

PostRepository

↓

UserRepository

↓

ActivityRepository

↓

MongoDB
```

The Service coordinates everything.


# Another Example: Delete Account

Deleting an account affects multiple entities.

Flow:

```text
Delete User

↓

Delete Posts

↓

Delete Comments

↓

Delete Likes

↓

Create Audit Log
```

Repositories involved:

```text
UserRepository

PostRepository

CommentRepository

LikeRepository

AuditRepository
```

The Service coordinates all of them, possibly inside a transaction.

# Complete Architecture

```text
                 Client
                    │
                    ▼
                 Routes
                    │
                    ▼
              Middleware
                    │
                    ▼
               Controller
                    │
                    ▼
                 Service
          ┌─────────┼─────────┐
          ▼         ▼         ▼
 UserRepo PostRepo CommentRepo
          │         │         │
          └─────────┼─────────┘
                    ▼
                 MongoDB
```

This is a common architecture in professional backend applications.

# Common Mistakes

## ❌ Controller Talks to Repository

Bad:

```text
Controller

↓

Repository
```

Business logic is skipped.

---

## ❌ Repository Talks to Controller

Impossible.

Repositories shouldn't know HTTP exists.

---

## ❌ Service Talks Directly to MongoDB

Bad:

```text
Service

↓

Post.find()
```

Always go through the repository.

---

## ❌ Repository Calls Another Repository

Bad:

```text
PostRepository

↓

UserRepository
```

Repositories should remain independent.

The Service coordinates them.

---

# Responsibility Matrix

|Layer|Main Responsibility|
|---|---|
|Route|URL mapping|
|Middleware|Authentication, validation, logging|
|Controller|HTTP request & response|
|Service|Business logic & workflows|
|Repository|Database access|
|Database|Data storage|

---

# Best Practices

✅ Keep each layer focused on one responsibility.

✅ Controllers should stay thin.

✅ Services should coordinate workflows.

✅ Repositories should own data access.

✅ Database details should never leave the repository.

# Key Takeaways

- A backend request flows through **Route → Middleware → Controller → Service → Repository → Database**.
    
- Each layer has a single responsibility.
    
- The Service Layer coordinates business workflows.
    
- The Repository Layer handles all database access.
    
- Keeping this flow consistent makes your application easier to maintain, test, and scale.
