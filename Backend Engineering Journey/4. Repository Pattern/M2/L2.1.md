# Module 2 — Designing Repositories

> **Goal:** Learn how to think like a backend engineer by designing repositories around **data operations**, not database queries.

---

# Lesson 2.1 — Thinking in Data Operations

## 🎯 Learning Objectives

By the end of this lesson, you will understand:

- What a data operation is.
    
- Why repositories should represent application needs instead of database queries.
    
- How to identify repository methods.
    
- How to design a repository before writing any code.
    

---

# Stop Thinking Like the Database

When beginners build a backend, they often think:

> "How do I write this MongoDB query?"

Professional developers think differently:

> "What data does my application need?"

This small change makes a huge difference.

---

# Start with the Application

Imagine you're building a **Blog App**.

Instead of opening Mongoose documentation, first ask:

> What can users do with blog posts?

Possible answers:

```text
Create a post

Read a post

Edit a post

Delete a post

Search posts

View published posts

View posts by an author

Count posts
```

Each action represents a **data operation**.

These operations will become repository methods.

---

# From Requirements to Repository Methods

Suppose your product requirements are:

- Users can create posts.
    
- Users can edit their own posts.
    
- Visitors can read published posts.
    
- Users can search posts.
    
- Admins can delete posts.
    

The repository naturally becomes:

```text
PostRepository

create()

findById()

findPublished()

findByAuthor()

search()

update()

delete()

count()
```

Notice that these methods describe **what the application needs**, not **how MongoDB works**.

---

# Think in Business Language

Bad method names:

```text
findOne()

find()

aggregate()

updateOne()

deleteMany()
```

These are database terms.

Better method names:

```text
findPublished()

findBySlug()

findByAuthor()

findPopular()

countPublished()

search()
```

These describe the application's language.

---

# Example: User Login

Requirement:

```text
Users log in using email.
```

Bad repository design:

```text
findOne({
    email
})
```

Good repository design:

```text
findByEmail(email)
```

The service doesn't care how the database finds the user.

It only cares that it can retrieve a user by email.

---

# Example: Blog Search

Requirement:

```text
Users search published posts.
```

Bad:

```text
find({
    title: ...
})
```

Good:

```text
search({
    keyword,
    tag,
    author
})
```

The repository hides the query details.

---

# Repository Methods Should Match Features

Imagine these features:

```text
Latest Posts

Popular Posts

Posts by Category

Posts by Author

Draft Posts

Published Posts
```

A clean repository might look like:

```text
PostRepository

create()

findById()

findBySlug()

findLatest()

findPopular()

findByCategory()

findByAuthor()

findDrafts()

findPublished()
```

Each method exists because the application needs it.

---

# Another Example: Todo App

Features:

```text
Create Todo

Mark Complete

View Pending

View Completed

Delete Todo
```

Repository:

```text
TodoRepository

create()

findById()

findPending()

findCompleted()

update()

delete()
```

Again, the methods reflect the application's needs.

---

# Another Example: URL Shortener

Features:

```text
Create Short URL

Find by Short Code

Increment Click Count

View Analytics

Delete Link
```

Repository:

```text
UrlRepository

create()

findByShortCode()

incrementClicks()

getAnalytics()

delete()
```

The repository speaks the language of the application.

---

# Benefits of Thinking This Way

Instead of writing random database queries throughout your codebase, you have a clear list of reusable operations.

For example:

```text
Service

↓

findBySlug()

↓

Repository

↓

MongoDB Query
```

If the query changes later, you only update the repository.

The service stays unchanged.

---

# Common Mistakes

### ❌ Designing Around MongoDB

```text
find()

findOne()

aggregate()

updateOne()

deleteOne()
```

These expose database details.

---

### ❌ One Method for Everything

```text
find(options)
```

Now every service must understand complex query options.

---

### ❌ Repository Knows Business Rules

Bad:

```text
publishPost()

approveComment()

banUser()
```

These belong in the **Service Layer**, not the repository.

---

# A Good Rule

Ask yourself:

> "If I switch from MongoDB to PostgreSQL, should this method name change?"

If the answer is **yes**, it's probably too database-specific.

Example:

Bad:

```text
aggregatePosts()
```

Good:

```text
findPopularPosts()
```

The implementation can change, but the method name stays meaningful.

---

# Visual Summary

```text
Application Requirements
           │
           ▼
Data Operations
           │
           ▼
Repository Methods
           │
           ▼
Database Queries
```

Always design **from top to bottom**, never from the database upward.

---

# Key Takeaways

- Design repositories based on **application features**, not database APIs.
    
- Repository methods should use **business language**.
    
- Services should ask **what** data they need, not **how** to retrieve it.
    
- A well-designed repository is easy to understand, reuse, and maintain.
    
- Good repository design makes switching databases much easier.
