# What is a Repository Interface?

A **repository interface** is simply the **public API** of your repository.

It defines **what operations other parts of the application can perform**.

Think of it as a contract.

Example:

```text
PostRepository

create()

findById()

findBySlug()

findPublished()

update()

delete()

count()
```

The **Service Layer** only knows these methods.

It does **not** know:

- Mongoose
    
- MongoDB queries
    
- SQL
    
- Aggregation pipelines
    

---

# Think Before Writing Code

Many beginners open VS Code and immediately start writing queries.

Professional developers first ask:

> "What operations will this repository provide?"

For a Blog App, the requirements are:

```text
Create Post

Read Post

Edit Post

Delete Post

Search Posts

Count Posts
```

So the interface becomes:

```text
PostRepository

create()

findById()

findBySlug()

search()

update()

delete()

count()
```

Only after designing the interface do you implement the methods.

---

# Good Repository Naming

Repository methods should describe **what they return or do**, not how they do it.

### Good Examples

```text
findById()

findByEmail()

findBySlug()

findPublished()

findLatest()

findByAuthor()

count()

create()

update()

delete()
```

These names are easy to understand.

---

### Bad Examples

```text
find()

findOne()

executeQuery()

runAggregation()

mongoSearch()

```

These reveal database details or are too vague.

---

# One Method, One Responsibility

Good:

```text
findById(id)
```

This method has one clear purpose.

Bad:

```text
find(options)
```

Now every caller needs to know:

- which options are supported
    
- how filtering works
    
- how sorting works
    

The repository becomes harder to use.

---

# Design Around Features

Imagine your Blog App has these features:

```text
Latest Posts

Published Posts

Posts by Author

Popular Posts

Draft Posts
```

A clean interface might be:

```text
PostRepository

findLatest()

findPublished()

findDrafts()

findByAuthor()

findPopular()
```

Notice how every method maps to a feature.

---

# Keep Business Logic Out

Bad:

```text
publishPost()

approveComment()

banUser()

activateAccount()
```

These are **business actions**.

They belong in the **Service Layer**.

Repositories should only perform data operations.

Instead:

```text
update()

findById()

create()

delete()
```

The service decides **what** to update.

The repository performs the update.

---

# Method Parameters Should Be Simple

Good:

```text
findById(id)

findByEmail(email)

findBySlug(slug)
```

The purpose is obvious.

---

For searching and filtering, group related options together.

Example:

```text
search({
    keyword,
    category,
    author,
    sort,
    page,
    limit
})
```

This is much cleaner than creating dozens of methods like:

```text
findByCategory()

findByCategorySorted()

findByCategorySortedPaginated()

findByCategorySortedPaginatedDescending()
```

---

# Return Meaningful Results

A repository should return **application data**, not HTTP responses.

Good:

```text
Post Object

User Object

Array of Posts

Boolean

Count
```

Bad:

```text
{
    status: 200,
    message: "Success"
}
```

HTTP belongs to the **Controller**, not the repository.

---

# Keep Repositories Focused

Good:

```text
PostRepository

create()

findById()

findPublished()

update()

delete()
```

Everything is related to posts.

---

Bad:

```text
PostRepository

createPost()

loginUser()

sendEmail()

createComment()

generatePDF()
```

Now the repository is doing unrelated work.

Each repository should manage **one entity** or one clear responsibility.

---

# Example: Blog App Repository Interface

```text
PostRepository

create(post)

findById(id)

findBySlug(slug)

findPublished(options)

findByAuthor(authorId)

search(filters)

update(id, data)

delete(id)

count(filters)
```

Notice that:

- Every method has a clear purpose.
    
- Names describe business concepts.
    
- No MongoDB-specific terms appear.
    

---

# Example: User Repository

```text
UserRepository

create(user)

findById(id)

findByEmail(email)

findByUsername(username)

update(id, data)

delete(id)

count()
```

Again, the interface is simple and easy to understand.

---

# Common Mistakes

### ❌ Huge Repositories

```text
UserRepository

150 methods
```

Large repositories become difficult to maintain.

---

### ❌ Database-Specific Names

```text
aggregateUsers()

mongoSearch()

findOneAndUpdate()
```

These expose implementation details.

---

### ❌ Returning HTTP Responses

Bad:

```text
return {
    status: 404,
    message: "User not found"
}
```

Repositories should return data (or `null`) and let the service/controller decide how to respond.

---

### ❌ Mixing Multiple Entities

Bad:

```text
PostRepository

createPost()

createUser()

createComment()
```

Create separate repositories instead:

```text
PostRepository

UserRepository

CommentRepository
```

---

# Visual Summary

```text
Application Features
         │
         ▼
Repository Interface
         │
         ▼
Repository Implementation
         │
         ▼
Database
```

The interface stays stable even if the database implementation changes.

---

# Best Practices Checklist

✅ Use business-friendly method names.

✅ Keep one responsibility per method.

✅ Keep one responsibility per repository.

✅ Hide database implementation details.

✅ Return data, not HTTP responses.

✅ Design the interface before writing database queries.

---

# Key Takeaways

- A repository interface is the **contract** between the Service Layer and the data layer.
    
- Method names should describe **application operations**, not database operations.
    
- Repositories should stay focused on a single entity or responsibility.
    
- Keep business logic in the **Service Layer**, not in repositories.
    
- A clean interface makes your application easier to understand, test, and maintain.

## 📌 Module 2 Summary

In this module, you learned how to design repositories **before writing code**.

The design process is:

```text
Requirements
      │
      ▼
Application Features
      │
      ▼
Data Operations
      │
      ▼
Repository Interface
      │
      ▼
Repository Implementation
```

This mindset helps you build repositories that are clean, reusable, and independent of the underlying database.
