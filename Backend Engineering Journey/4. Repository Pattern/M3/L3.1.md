# What is CRUD?

CRUD represents the four fundamental data operations:

```text
Create

↓

Read

↓

Update

↓

Delete
```

Almost every application performs these operations.

Examples:

|Application|CRUD Example|
|---|---|
|Blog|Create, read, update, delete posts|
|Todo|Create, complete, delete todos|
|E-commerce|Create, update, delete products|
|URL Shortener|Create, retrieve, delete URLs|

---

# CRUD in a Layered Architecture

A request should follow this flow:

```text
Client
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
MongoDB
```

Only the **Repository** communicates with MongoDB.

---

# Repository Structure

For a Blog App:

```text
PostRepository

create()

findById()

findAll()

update()

delete()
```

Each method performs **one data operation**.

---

# Create Operation

Requirement:

> Users can create blog posts.

Repository:

```javascript
async create(postData) {
    return await Post.create(postData);
}
```

Notice:

- The repository receives data.
    
- It saves the data.
    
- It returns the created document.
    

It does **not**:

- Validate business rules.
    
- Check permissions.
    
- Send notifications.
    

Those belong to the Service Layer.

---

# Read Operation

Requirement:

> Find a post by its ID.

Repository:

```javascript
async findById(id) {
    return await Post.findById(id);
}
```

The repository hides the Mongoose query.

The Service simply calls:

```javascript
const post = await postRepository.findById(postId);
```

The service doesn't know whether the data comes from:

- MongoDB
    
- PostgreSQL
    
- Redis
    
- Cache
    

---

# Read Multiple Records

Requirement:

> Display all published posts.

Repository:

```javascript
async findPublished() {
    return await Post.find({
        status: "published"
    });
}
```

The service only asks:

```javascript
postRepository.findPublished();
```

It doesn't care how the query works.

---

# Update Operation

Requirement:

> Edit a blog post.

Repository:

```javascript
async update(id, updateData) {
    return await Post.findByIdAndUpdate(
        id,
        updateData,
        { new: true }
    );
}
```

The service decides **what should change**.

The repository performs the update.

---

# Delete Operation

Requirement:

> Delete a blog post.

Repository:

```javascript
async delete(id) {
    return await Post.findByIdAndDelete(id);
}
```

Simple.

The repository performs one job.


Responsibilities:

### Controller

```text
Read request

↓

↓

```

---

### Service

```text
Check ownership

↓

Validate business rules

↓

Call repository
```

---

### Repository

```text
Update database

↓

Return updated document
```

# What Should NOT Be Inside a Repository?

Bad example:

```javascript
async update(id, data, user) {

    if (user.role !== "admin") {
        throw new Error("Forbidden");
    }

    return await Post.findByIdAndUpdate(id, data);
}
```

Why is this wrong?

Permission checking is **business logic**.

It belongs in the Service Layer.

Correct flow:

```text
Service

↓

Permission Check

↓

Repository.update()
```

---

# Keep Repository Methods Small

Good:

```text
create()

findById()

update()

delete()
```

Each method has one responsibility.

Bad:

```text
createAndNotify()

updateAndLog()

deleteAndArchive()
```

These mix business logic with data access.

---

# Returning Results

Repositories should return **data**, not HTTP responses.

Good:

```javascript
return post;
```

Good:

```javascript
return null;
```

Bad:

```javascript
return {
    status: 404,
    message: "Post not found"
};
```

HTTP belongs to the Controller.

---

# Example Repository

```javascript
class PostRepository {

    async create(data) {}

    async findById(id) {}

    async findPublished() {}

    async update(id, data) {}

    async delete(id) {}

}
```

Notice how clean the interface is.

---

# Common Mistakes

### ❌ Business Logic Inside Repository

```javascript
publishPost()
approveComment()
```

Wrong layer.

---

### ❌ Returning HTTP Status Codes

```javascript
return res.status(404);
```

Repositories should never know Express exists.

---

### ❌ Controller Accessing Repository Directly

```text
Controller

↓

Repository
```

This skips the Service Layer.

Correct:

```text
Controller

↓

Service

↓

Repository
```

---

# Best Practices

✅ One method = one data operation.

✅ Keep methods small and focused.

✅ Return data, not HTTP responses.

✅ No business logic inside repositories.

✅ Hide database implementation from services.

---

# Key Takeaways

- CRUD repositories provide a clean interface for database operations.
    
- Services decide **what** should happen; repositories decide **how** to access the data.
    
- Each repository method should perform one clear data operation.
    
- Keeping repositories focused improves readability, testing, and maintainability.
