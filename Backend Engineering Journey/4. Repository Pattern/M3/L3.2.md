# Module 3 — Building CRUD Repositories

# Lesson 3.2 — Hiding Database Implementation Details

> **Golden Rule:** The **Service Layer** should know **what data it needs**, not **how that data is stored**.

---

# 🎯 Learning Objectives

By the end of this lesson, you will understand:

- Why services should not know Mongoose.
    
- How repositories hide database implementation.
    
- How this makes changing databases easier.
    
- What data repositories should return.
    
- Best practices for repository implementations.
    

---

# What Does "Hide Database Details" Mean?

Imagine your service needs a blog post.

The service should simply say:

```text
I need the post with ID 123.
```

It should **not** say:

```text
Use Mongoose's findById()

↓

Populate the author

↓

Use lean()

↓

Select only these fields

↓

Handle MongoDB errors
```

Those are **database implementation details**.

The repository handles them.

---

# Without a Repository

Suppose you're using Mongoose.

Your service might look like this:

```javascript
async function getPost(id) {
    return await Post.findById(id)
        .populate("author")
        .select("-__v")
        .lean();
}
```

Problems:

- Service knows Mongoose.
    
- Service knows `populate()`.
    
- Service knows `select()`.
    
- Service knows `lean()`.
    

Business logic and database logic are mixed together.

---

# With a Repository

The service becomes much simpler.

```javascript
async function getPost(id) {
    return await postRepository.findById(id);
}
```

That's all.

The repository hides everything else.

---

# Repository Implementation

```javascript
async findById(id) {
    return await Post.findById(id)
        .populate("author")
        .select("-__v")
        .lean();
}
```

Only the repository knows:

- Mongoose
    
- Queries
    
- Populate
    
- Projection
    
- Performance optimizations
    

The service doesn't.

---

# Why Is This Important?

Imagine your company decides to switch databases.

Today:

```text
MongoDB
```

Next year:

```text
PostgreSQL
```

Without repositories:

```text
Service A

↓

Post.findById()
```

```text
Service B

↓

Post.find()
```

```text
Service C

↓

Post.aggregate()
```

Every service needs changes.

---

With repositories:

```text
Service

↓

postRepository.findById()
```

Only the repository changes.

The service remains exactly the same.

---

# Real Example

Today:

```javascript
postRepository.findBySlug(slug);
```

MongoDB implementation:

```javascript
Post.findOne({
    slug
});
```

Tomorrow:

PostgreSQL implementation:

```sql
SELECT *
FROM posts
WHERE slug = ?
```

The service still calls:

```javascript
postRepository.findBySlug(slug);
```

No changes required.

---

# Repositories Hide Query Complexity

Suppose your application displays:

- Author
    
- Category
    
- Tags
    

MongoDB implementation:

```javascript
Post.findById(id)
.populate("author")
.populate("category")
.populate("tags")
```

The service doesn't care.

It simply calls:

```javascript
postRepository.findById(id);
```

---

# Repositories Hide Performance Optimizations

Imagine you later optimize the query.

Old implementation:

```javascript
Post.findById(id);
```

Optimized implementation:

```javascript
Post.findById(id)
.select("title slug content")
.lean();
```

Did the service change?

No.

Only the repository changed.

This is one of the biggest advantages of the Repository Pattern.

---

# Repositories Hide Error Translation

MongoDB may throw:

```text
CastError

DuplicateKeyError

ValidationError
```

The repository can translate them into application-friendly errors.

Example:

```text
DuplicateKeyError

↓

ConflictError
```

The service no longer needs to understand MongoDB error types.

---

# What Should Repositories Return?

Repositories should return **application data**.

Good:

```javascript
return post;
```

Good:

```javascript
return null;
```

Good:

```javascript
return posts;
```

Avoid returning raw HTTP responses.

Bad:

```javascript
return {
    status: 404,
    message: "Not Found"
};
```

Repositories don't know Express.

---

# Returning Domain Objects

Suppose your database document contains:

```text
_id

title

content

__v

createdAt

updatedAt
```

Your application might only need:

```text
id

title

content
```

The repository can map the data before returning it.

This keeps the Service Layer clean and independent of database-specific fields.

# Common Mistakes

## ❌ Exposing Mongoose Models

Bad:

```javascript
return Post;
```

Repositories should return data, not the model itself.

---

## ❌ Returning Query Builders

Bad:

```javascript
return Post.find();
```

Now the service can modify the query.

The repository loses control.

Instead:

```javascript
return await Post.find();
```

---

## ❌ Letting Services Call Mongoose

Bad:

```javascript
const post = await Post.findById(id);
```

Correct:

```javascript
const post = await postRepository.findById(id);
```

The service should never import the model directly.

# Best Practices

✅ Keep Mongoose code inside repositories.

✅ Return application data.

✅ Hide query optimizations.

✅ Hide database-specific errors.

✅ Hide database-specific field names.

✅ Keep the service independent of the database.

---

# Key Takeaways

- The repository is the **only layer that should know how the database works**.
    
- Services should interact with repositories through **clean, business-friendly methods**.
    
- Repositories hide queries, optimizations, and database-specific APIs.
    
- This separation makes your application easier to maintain, test, and migrate to another database.
    
- If you ever switch from MongoDB to PostgreSQL, the **Repository Layer** is where most of the changes should happen.

# 📌 Module 3 Summary

In this module, you learned how to build **clean CRUD repositories** and keep the **Service Layer completely independent of the database**.

The flow is now:

```text
Client
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼

```

The **Service Layer** focuses on **business rules**, while the **Repository Layer** focuses on **data access**.

This separation is a key characteristic of professional backend architectures and prepares you for more advanced topics like filtering, pagination, transactions, and performance optimization.
