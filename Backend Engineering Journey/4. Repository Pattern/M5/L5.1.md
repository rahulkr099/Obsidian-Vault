# What Are Relationships?

Real-world applications rarely have isolated data.

Example:

A blog post has:

- An author
    
- Comments
    
- Categories
    
- Tags
    

Instead of storing everything inside one document, databases create **relationships**.

Example:

```text
User
 └── has many Posts

Post
 └── belongs to User
```

---

# Common Relationship Types

## One-to-One (1:1)

Example:

```text
User

↓

Profile
```

Each user has one profile.

---

## One-to-Many (1:N)

Example:

```text
User

↓

Posts
```

One user can write many posts.

---

## Many-to-Many (N:N)

Example:

```text
Post

↓

Tags
```

A post can have many tags.

A tag can belong to many posts.

# Loading Related Data

Suppose a user opens a blog post.

The page needs:

```text
Post

Author

Comments

Category
```

The service simply asks:

```javascript
postRepository.findById(postId);
```

The repository decides how to retrieve the relationships.

---

# MongoDB Example

Internally, the repository might use:

```javascript
Post.findById(id)
    .populate("author")
    .populate("category");
```

The Service Layer never sees `populate()`.

It only knows:

```javascript
postRepository.findById(id);
```

---

# SQL Example

If your application uses PostgreSQL:

Internally, the repository might execute:

```sql
SELECT *
FROM posts
JOIN users
ON ...
```

Again, the service doesn't change.

Only the repository implementation changes.

---

# Why Is This Important?

Imagine switching databases.

Today:

```text
MongoDB

↓

populate()
```

Tomorrow:

```text
PostgreSQL

↓

JOIN
```

The Service Layer still calls:

```javascript
postRepository.findById(id);
```

This is another benefit of hiding database details.

---

# Should Every Query Load Relationships?

No.

Imagine the homepage:

```text
Latest Posts
```

Do we need:

- Author details?
    
- Comments?
    
- Tags?
    
- Likes?
    

Maybe not.

Loading unnecessary relationships wastes:

- Memory
    
- CPU
    
- Database time
    

---

# Different Repository Methods

Instead of one method for everything:

```text
findById()
```

Create methods for different use cases.

Example:

```text
findSummaryById()

findDetailsById()
```

Summary:

```text
Title

Slug

Published Date
```

Details:

```text
Title

Content

Author

Comments

Tags

Category
```

This improves performance.

---

# Avoid Over-Populating

Bad:

```text
Post

↓

Author

↓

Comments

↓

Likes

↓

Followers

↓

Settings

↓

Notifications
```

Now one request loads half the database.

---

Good:

Load only what the current feature needs.

---

# Repository Responsibility

Repository:

```text
Load Data

↓

Load Relationships

↓

Return Clean Result
```

Service:

```text
Business Rules
```

Never mix them.

---

# Example Flow

```text
Controller

↓

Service

↓

postRepository.findDetailsById()

↓

MongoDB

↓

Post + Author + Category

↓

Service
```

The Service doesn't know how the data was retrieved.

---

# Common Mistakes

## ❌ Service Uses `populate()`

Bad:

```javascript
const post = await Post.findById(id)
.populate("author");
```

Service should never import Mongoose models.

---

## ❌ Repository Always Loads Everything

Bad:

Every query loads:

- Author
    
- Comments
    
- Likes
    
- Tags
    
- Categories
    

Even when only the title is needed.

---

## ❌ Business Decisions Inside Repository

Bad:

```javascript
if(user.role === "admin")
```

Repositories shouldn't make permission decisions.

---

# Visual Summary

```text
Service
      │
      ▼
Repository
      │
      ├── Load Post
      ├── Load Author
      ├── Load Category
      └── Load Comments
      │
      ▼
Database
```

The repository owns relationship loading.

---

# Best Practices

✅ Load only the relationships you need.

✅ Hide `populate()` and SQL `JOIN`s inside repositories.

✅ Create separate methods for summary and detailed views.

✅ Keep business rules inside services.

---

# Key Takeaways

- Relationships connect related entities such as Users, Posts, and Comments.
    
- The Repository Layer is responsible for loading related data.
    
- The Service Layer should never use `populate()` or SQL `JOIN`s directly.
    
- Load only the data needed for the current feature to improve performance.
    
- Separate methods like `findSummaryById()` and `findDetailsById()` can keep queries efficient.
