# What is Aggregation?

CRUD operations usually return **individual records**.

Example:

```text
Find Post

↓

Return One Post
```

Aggregation combines **many records** to produce **summaries, reports, or statistics**.

Example:

```text
100 Posts

↓

Count Posts Per Month

↓

Monthly Report
```

Instead of returning raw data, aggregation returns **processed information**.

---

# Why Do We Need Aggregation?

Imagine your Blog Admin Dashboard.

It needs:

```text
Total Posts

↓

Total Comments

↓

Most Popular Posts

↓

Top Authors

↓

Posts Per Month
```

These aren't simple CRUD operations.

They require calculations.

---

# CRUD vs Aggregation

### CRUD

```text
Find Post #101
```

Returns:

```text
One Post
```

---

### Aggregation

```text
Find Top 10 Authors
```

Returns:

```text
Author List

+

Post Counts
```

Aggregation summarizes data.

# Repository Design

The Service Layer asks:

```javascript
analyticsRepository.getTopAuthors();
```

The repository performs the complex query.

---

# Example Interface

```text
AnalyticsRepository

getTopAuthors()

getPopularPosts()

getMonthlyStatistics()

getCategoryStatistics()

getCommentStatistics()
```

Notice the method names describe **business reports**, not database operations.

---

# Repository Responsibilities

The repository performs:

```text
Grouping

↓

Counting

↓

Summing

↓

Sorting

↓

Returning Results
```

The Service simply receives the final report.

---

# Blog Example

Requirement:

> Show the top 5 authors.

Service:

```javascript
const authors =
await analyticsRepository.getTopAuthors();
```

The Service doesn't know:

- Aggregation pipelines
    
- SQL GROUP BY
    
- MongoDB operators
    

Only the repository knows.

# Aggregation vs Business Logic

Suppose management asks:

> "Who is the most active author?"

The repository can calculate:

```text
Author

↓

Total Posts
```

The Service decides:

```text
Reward the top author.
```

Notice the separation:

Repository:

- Collects data
    

Service:

- Makes decisions
    

---

# Keep Aggregation Out of Services

Bad:

```text
Service

↓

Load 10,000 Posts

↓

Count Them

↓

Calculate Statistics
```

This wastes memory and CPU.

---

Good:

```text
Repository

↓

Database Calculates Statistics

↓

Return Final Result
```

Databases are optimized for these operations.

---

# Separate Analytics Repository

In larger projects, analytics queries often become complex.

Instead of:

```text
PostRepository

↓

100 Analytics Methods
```

Create:

```text
PostRepository

↓

CRUD
```

```text
AnalyticsRepository

↓

Reports

↓

Statistics

↓

Charts
```

This keeps repositories focused.

---

# Common Mistakes

## ❌ Counting in the Service

Bad:

```javascript
const posts =
await repository.findAll();

const count = posts.length;
```

The database should count the records.

---

## ❌ Huge Repository

Bad:

```text
PostRepository

↓

CRUD

↓

Analytics

↓

Charts

↓

Reports

↓

Exports
```

Split responsibilities.

---

## ❌ Returning Raw Database Results

Repositories should return data that is easy for the Service Layer to use.

Instead of exposing raw aggregation details, return meaningful application data.

# Best Practices

✅ Keep aggregation queries inside repositories.

✅ Use descriptive method names.

✅ Return processed data.

✅ Create a dedicated `AnalyticsRepository` when reports become large.

✅ Let the database perform calculations.

---

# Key Takeaways

- Aggregation summarizes data instead of returning individual records.
    
- The Repository Layer should own all aggregation queries.
    
- Services should ask for reports, not build them.
    
- Databases are optimized for counting, grouping, and sorting large datasets.
    
- Separate analytics repositories can keep your codebase organized as your application grows.
