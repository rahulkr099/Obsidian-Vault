# Module 6 — Transactions & Error Handling

> **Goal:** Learn how repositories safely perform multiple database operations and how they hide database-specific errors from the Service Layer.

# Lesson 6.1 — Repository Error Handling

## 🎯 Learning Objectives

By the end of this lesson, you will understand:

- Why repositories should handle database errors.
    
- The difference between database errors and business errors.
    
- How repositories translate database-specific errors.
    
- Best practices for error handling.
    

---

# What Are Database Errors?

Every database can produce errors.

Examples:

```text
MongoDB

↓

Duplicate Key Error

Cast Error

Validation Error

Connection Error
```

```text
PostgreSQL

↓

Unique Constraint Error

Foreign Key Error

Connection Error
```

These errors are **database-specific**.

Your Service Layer should **not** understand them.

---

# Business Errors vs Database Errors

This is one of the most important concepts in backend architecture.

## Business Error

Example:

```text
User is not the owner

↓

Cannot edit post
```

or

```text
Post is already published
```

These are application rules.

They belong in the **Service Layer**.

---

## Database Error

Example:

```text
Duplicate email

↓

Database rejects insert
```

or

```text
Database connection lost
```

These belong in the **Repository Layer**.

---

# Example Flow

Suppose a user registers.

```text
Controller

↓

Service

↓

UserRepository.create()

↓

MongoDB
```

If MongoDB reports:

```text
Duplicate Email
```

The repository translates it into an application error.

---

# Without Translation

Service:

```text
DuplicateKeyError

Code: 11000

MongoDB Error Object...
```

Now the Service Layer knows MongoDB.

This creates tight coupling.

---

# With Translation

Repository:

```text
MongoDB DuplicateKeyError

↓

ConflictError

↓

Service
```

Now the service receives:

```text
Email already exists
```

It doesn't care whether the database is MongoDB or PostgreSQL.

---

# Why Translation Matters

Imagine changing databases.

Today:

```text
MongoDB

↓

Error Code 11000
```

Tomorrow:

```text
PostgreSQL

↓

Unique Constraint Violation
```

Only the repository changes.

The Service Layer remains exactly the same.

---

# Common Database Errors

## Duplicate Data

Example:

```text
Two users

↓

Same Email
```

Repository returns:

```text
ConflictError
```

---

## Invalid ID

Example:

```text
Wrong ObjectId
```

Repository returns:

```text
InvalidIdentifierError
```

---

## Database Offline

Example:

```text
Cannot connect
```

Repository returns:

```text
DatabaseUnavailableError
```

---

## Missing Record

Example:

```text
Post not found
```

Repositories usually return:

```text
null
```

The Service Layer decides what to do.

Example:

```text
null

↓

Throw NotFoundError
```

Notice the separation.

---

# Repository Responsibilities

The repository should:

- Execute queries.
    
- Catch database-specific errors.
    
- Translate them into application errors.
    
- Return clean results.
    

It should **not**:

- Decide HTTP status codes.
    
- Return Express responses.
    
- Check permissions.
    
- Apply business rules.
    

---

# Example Flow

User updates profile.

```text
Controller

↓

Service

↓

Repository

↓

MongoDB
```

MongoDB returns:

```text

```

Repository:

```text
Duplicate username

↓

```

Service:

```text
Display

```

# Common Mistakes

## ❌ Service Reads MongoDB Error Codes

Bad:

```text
if(error.code === 11000)
```

Now the Service Layer depends on MongoDB.

---

## ❌ Repository Returns HTTP Responses

Bad:

```text
404 Not Found
```

Repositories should never know Express.

---

## ❌ Business Rules Inside Repository

Bad:

```text
if(user.role !== "admin")
```

Permission checks belong in the Service Layer.

---

# Best Practices

✅ Translate database errors.

✅ Return application-friendly errors.

✅ Return `null` for missing records when appropriate.

✅ Hide database-specific details.

✅ Keep repositories independent from HTTP.

---

# Key Takeaways

- Database errors belong in the Repository Layer.
    
- Business errors belong in the Service Layer.
    
- Repositories should translate database-specific errors into application-friendly errors.
    
- The Service Layer should never depend on MongoDB or PostgreSQL error codes.
    
- This makes changing databases much easier.
