# Lesson 6.2 — Transactions

> **Golden Rule:** If multiple database operations must either **all succeed** or **all fail**, use a **transaction**.

---

By the end of this lesson, you will understand:

- The role of the Repository and Service layers in transactions.

# What is a Transaction?

A transaction is a group of database operations that are treated as **one unit of work**.

Two possible outcomes:

```text
All Operations Succeed

↓

Commit
```

or

```text
One Operation Fails

↓

Rollback Everything
```

There is no middle ground.

---

# Why Do We Need Transactions?

Imagine a banking application.

Rahul transfers ₹1000 to Amit.

The process is:

```text
Subtract ₹1000

↓

Add ₹1000
```

Suppose the first step succeeds:

```text
Rahul

₹10,000

↓

₹9,000
```

Then the server crashes before adding money to Amit.

Now:

```text
Rahul

₹9,000

↓

Amit

Still ₹5,000
```

₹1000 has disappeared.

This is unacceptable.

A transaction prevents this.

---

# Transaction Flow

```text
Start Transaction

↓

Operation 1

↓

Operation 2

↓

Operation 3

↓

Commit
```

If any operation fails:

```text
Start Transaction

↓

Operation 1

↓

Operation 2 ❌

↓

Rollback

↓

Database Restored
```

---

# Blog App Example

Publishing a blog post requires:

```text
Update Post

↓

Increase Author Post Count

↓

Create Activity Log
```

These operations should succeed together.

Without a transaction:

```text
Post Published ✅

↓

Statistics Failed ❌

↓

Activity Missing ❌
```

The system becomes inconsistent.

---

# With a Transaction

```text
Update Post

↓

Update Statistics

↓

Create Activity

↓

Commit
```

If one step fails:

```text
Rollback Everything
```

Now the database remains consistent.

---

# Which Layer Owns the Transaction?

This is a common interview question.

### Repository

Responsible for:

- Executing database operations.
    
- Participating in a transaction.
    

---

### Service

Responsible for:

- Deciding **when** a transaction is needed.
    
- Coordinating multiple repository calls.
    

Think of it like this:

```text
Service

↓

"These operations must succeed together."
```

The repository does **not** decide whether a transaction is needed.

---

# Example Flow

User publishes a post.

```text
Controller

↓

Service

↓

PostRepository

↓

UserRepository

↓

ActivityRepository

↓

Database
```

The Service coordinates the workflow.

The repositories execute the database operations.

# Another Example

E-commerce checkout:

```text
Create Order

↓

Reduce Product Stock

↓

Create Payment Record

↓

Create Invoice
```

If payment fails:

Everything should roll back.

# URL Shortener Example

Suppose premium users have click limits.

Creating a short URL requires:

```text
Create URL

↓

Update User Usage

↓

Create Activity Log
```

If updating usage fails:

The URL should not be created.

# What Should Be Inside a Transaction?

Use transactions only for operations that must stay consistent.

Good examples:

```text
Create Order

↓

Reduce Inventory
```

```text
Create User

↓

Create User Profile
```

```text
Publish Post

↓

Update Statistics
```

---

# What Should NOT Be Inside a Transaction?

Avoid long-running tasks.

Bad examples:

```text
Send Email

↓

Upload Image

↓

Call Payment Gateway

↓

Generate PDF
```

These are not database operations.

If they take several seconds, they keep the transaction open, which hurts performance.

---

# Repository Responsibilities

Repositories should:

- Execute database queries.
    
- Participate in a transaction when one exists.
    
- Never decide whether to start one.
    

---

# Service Responsibilities

Services should:

- Decide whether a transaction is needed.
    
- Coordinate multiple repositories.
    
- Handle business rules.

# Common Mistakes

## ❌ Every Operation Uses a Transaction

Bad:

```text
Find Post

↓

Transaction
```

Reading data usually doesn't need one.

Transactions have overhead.

---

## ❌ Repository Starts Transactions Everywhere

Bad:

```text
PostRepository

↓

Starts Transaction
```

The repository doesn't know whether another repository will also be called.

The Service has the bigger picture.

---

## ❌ Long Transactions

Bad:

```text
Start Transaction

↓

Upload Images

↓

Resize Images

↓

Send Email

↓

Commit
```

Transactions should be as short as possible.

---

# Best Practices

✅ Use transactions only when multiple database changes must stay consistent.

✅ Let the Service Layer coordinate transactions.

✅ Keep transactions short.

✅ Avoid external API calls inside transactions.

✅ Roll back if any database operation fails.

---

# Real-World Examples

|Application|Transaction Needed?|Reason|
|---|---|---|
|Bank Transfer|✅ Yes|Money must stay consistent|
|Place Order|✅ Yes|Order, payment, and inventory must match|
|Publish Blog Post|✅ Usually|Update related records together|
|User Login|❌ No|Only reading/updating one record|
|Search Posts|❌ No|Read-only operation|

---

# Key Takeaways

- A transaction ensures **all operations succeed together or all fail together**.
    
- Transactions protect data consistency.
    
- The **Service Layer** decides **when** to use a transaction.
    
- The **Repository Layer** performs database operations within the transaction.
    
- Keep transactions short and avoid non-database work inside them.
