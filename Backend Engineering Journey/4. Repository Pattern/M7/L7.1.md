# Why Should We Optimize Queries?

Imagine your Blog App grows from:

```text
100 Posts
```

to

```text
10,000,000 Posts
```

A query that takes **20 ms** today might take **2 seconds** later.

As your application grows:

- More users
    
- More data
    
- More traffic
    

Efficient queries become essential.

---

# Repository's Responsibility

Performance optimization belongs inside the **Repository Layer**.

The Service Layer simply asks:

```javascript
postRepository.findPublished();
```

The repository decides:

- Which fields to fetch.
    
- Whether to use `lean()`.
    
- Which indexes are useful.
    
- How to optimize the query.
    

---

# Optimization 1 — Projection

Suppose a post contains:

```text
title

content

author

tags

comments

likes

createdAt

updatedAt
```

Your homepage only displays:

```text
Title

Author

Published Date
```

Loading everything wastes resources.

Instead, the repository returns only the required fields.

This is called **projection**.

---

# Why Projection Helps

Without projection:

```text
Database

↓

Large Documents

↓

API
```

With projection:

```text
Database

↓

Only Required Fields

↓

API
```

Benefits:

- Faster queries
    
- Less memory
    
- Smaller network responses
    

---

# Optimization 2 — Lean Queries (MongoDB)

Normally, Mongoose returns **full Mongoose documents**.

These include:

- Methods
    
- Change tracking
    
- Extra metadata
    

Sometimes you only need plain data.

A **lean query** returns a simple JavaScript object.

Benefits:

- Faster
    
- Lower memory usage
    
- Ideal for read-only APIs
    

The Service Layer doesn't need to know whether `lean()` was used.

---

# Optimization 3 — Indexes

Imagine searching:

```text
Find User by Email
```

Without an index:

```text
Database

↓

Checks Every User
```

This is called a **full collection scan**.

---

With an index:

```text
Database

↓

Jump Directly to Matching User
```

Much faster.

---

# Common Indexed Fields

Blog App:

```text
email

slug

authorId

categoryId

createdAt
```

These fields are searched frequently.

---

# Repository Hides Optimization

The service simply writes:

```javascript
postRepository.findBySlug(slug);
```

The repository ensures:

- The query uses an index.
    
- Only required fields are returned.
    
- A lean query is used when appropriate.
    

The service doesn't change.

---

# Query Only What You Need

Bad:

```text
Load 100 Posts

↓

Each Post

↓

50 Comments

↓

Author

↓

Category

↓

Likes
```

When the homepage only displays titles.

---

Good:

```text
Load

Title

Slug

Author Name
```

Small queries are fast queries.

---

# Example: Homepage vs Details Page

Homepage:

```text
Title

Author

Published Date
```

Post Details:

```text
Title

Content

Author

Comments

Category
```

The repository should provide different methods for these different needs.

---

# Avoid the N+1 Query Problem

Imagine loading:

```text
100 Posts
```

Then for each post:

```text
Load Author
```

Total queries:

```text
1

+

100

=

101 Queries
```

This is called the **N+1 Query Problem**.

Instead, use efficient relationship loading (`populate()` in MongoDB or `JOIN` in SQL) when appropriate.

---

# Common Mistakes

## ❌ Loading Entire Documents

Only fetch what you actually need.

---

## ❌ Forgetting Indexes

Searching millions of records without indexes becomes extremely slow.

---

## ❌ Repository Returns Huge Objects

Return only the fields required by the current feature.

---

## ❌ Service Optimizes Queries

Bad:

```text
Service decides projection

↓

Service decides indexing
```

Optimization belongs in repositories.

---

# Best Practices

✅ Use projections.

✅ Use lean queries for read-only operations.

✅ Index frequently searched fields.

✅ Return only required data.

✅ Create separate repository methods for different views.

---

---

# Key Takeaways

- Performance optimization belongs in the **Repository Layer**.
    
- Use projections to reduce the amount of data returned.
    
- Use lean queries for read-only operations in MongoDB.
    
- Index frequently searched fields.
    
- Avoid loading unnecessary relationships and data.
    
- Design repository methods around the data each feature actually needs.
