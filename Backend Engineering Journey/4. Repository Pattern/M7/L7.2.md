# What is Caching?

A **cache** is a fast temporary storage that keeps frequently used data.

Instead of asking the database every time:

```text
Client

↓

Database

↓

Response
```

We first check the cache.

```text
Client

↓

Cache

↓

Database (only if needed)
```

The cache is much faster than the database.

---

# Why Do We Need Caching?

Imagine your homepage.

Every visitor requests:

```text
Latest Posts
```

Without caching:

```text
1000 Users

↓

1000 Database Queries
```

Even though the homepage data barely changes.

---

With caching:

```text
1000 Users

↓

1 Database Query

↓

999 Cache Reads
```

The database workload drops significantly.

---

# What is Redis?

**Redis** is one of the most popular caching systems.

Architecture:

```text
Application

↓

Redis

↓

MongoDB
```

Redis stores data in memory, making it much faster than reading from disk.

---

# The Cache-Aside Pattern

This is the most common caching strategy.

Flow:

```text
Request

↓

Check Cache
```

If found:

```text
Cache Hit

↓

Return Cached Data
```

If not found:

```text
Cache Miss

↓

Query Database

↓

Store Result in Cache

↓

Return Data
```

---

# Cache Hit vs Cache Miss

## Cache Hit

```text
Request

↓

Redis

↓

Data Found

↓

Response
```

No database query.

Very fast.

---

## Cache Miss

```text
Request

↓

Redis

↓

Data Missing

↓

MongoDB

↓

Save to Redis

↓

Response
```

The next request becomes much faster.

# Repository Responsibilities

The Service Layer asks:

```javascript
postRepository.findBySlug(slug);
```

The repository decides:

```text
Cache?

↓

Database?

↓

Save Cache?
```

The Service Layer doesn't know caching exists.

---

# Example Flow

```text
Controller

↓

Service

↓

Repository

↓

Redis

↓

MongoDB
```

If Redis has the data:

MongoDB isn't touched.

---

# What Should Be Cached?

Good candidates:

```text
Published Posts

Categories

Tags

Popular Posts

Application Settings
```

These don't change frequently.

---

# What Should NOT Be Cached?

Avoid caching:

```text
Bank Balance

Live Inventory

OTP Codes

Payment Status

Active Sessions
```

These change frequently or require real-time accuracy.

---

# Cache Invalidation

One of the hardest problems in software is:

> **Knowing when to remove outdated cache data.**

Example:

A post is updated.

Cached version:

```text
Old Title
```

Database:

```text
New Title
```

If we don't update the cache:

Users continue seeing the old title.

---

# Solution

Whenever data changes:

```text
Update Database

↓

Delete Cache

↓

Next Request

↓

Reload Cache
```

This keeps cached data fresh.

---

# Cache TTL (Time To Live)

Sometimes cache expires automatically.

Example:

```text
Homepage Cache

↓

Expires After

5 Minutes
```

After expiration:

The next request reloads data from the database.

# Common Mistakes

## ❌ Caching Everything

Not every query needs caching.

Frequently changing data often performs worse with unnecessary cache management.

---

## ❌ Service Knows About Redis

Bad:

```text
Service

↓

Redis

↓

Repository
```

Repositories should own caching.

---

## ❌ Never Invalidating Cache

Updating the database without clearing the cache causes stale data.

---

## ❌ Very Long Cache Lifetime

Example:

```text
Homepage

↓

Cache

↓

7 Days
```

Users may never see new content.

Choose sensible expiration times.

# Best Practices

✅ Cache frequently read data.

✅ Use the Cache-Aside Pattern.

✅ Invalidate cache after updates.

✅ Set appropriate TTL values.

✅ Keep caching inside the Repository Layer.

# Key Takeaways

- A cache stores frequently accessed data for faster retrieval.
    
- **Redis** is commonly used for caching in backend applications.
    
- The **Cache-Aside Pattern** is the most widely used caching strategy.
    
- Cache only data that is read often and changes infrequently.
    
- Always invalidate or refresh the cache after updating the underlying data.
    
- The **Repository Layer** should manage caching so the Service Layer remains unaware of it.
