# What is Repository Composition?

Real-world features often need data from **multiple repositories**.

Example:

Publishing a blog post.

The application needs to:

```text
Update Post

↓

Update User Statistics

↓

Create Activity Log
```

Instead of putting everything into one repository, each repository handles its own entity.

```text
PostRepository

UserRepository

ActivityRepository
```

This is **Repository Composition**.

---

# Who Coordinates the Repositories?

A common beginner mistake is:

```text
PostRepository

↓

Calls UserRepository
```

Or:

```text
UserRepository

↓

Calls PostRepository
```

Repositories should **not** call each other.

The **Service Layer** coordinates them.

---

# Correct Architecture

```text
Controller
      │
      ▼
Service
      │
 ┌────┼─────┐
 ▼    ▼     ▼
Post User Activity
Repo Repo  Repo
```

The Service knows the workflow.

Repositories only know their own data.

Requirement:

```text

↓
```

The repositories never communicate directly.

# Why?

Imagine this:

```text
PostRepository

↓

UserRepository

↓

PostRepository

↓

UserRepository
```

Now the repositories depend on each other.

This creates **tight coupling**.

---

# Circular Dependency

A circular dependency happens when two components depend on each other.

Example:

```text
PostRepository

↓

UserRepository

↓

PostRepository
```

Neither can work independently.

This becomes difficult to:

- Test
    
- Maintain
    
- Understand

# Common Mistakes

## ❌ Repository Calls Repository

Bad:

```text
PostRepository

↓

UserRepository
```

Repositories should never depend on each other.

---

## ❌ Business Workflow in Repository

Bad:

```text
publishPost()

↓

Update User

↓

Create Activity
```

The repository is now coordinating business logic.

That belongs in the Service Layer.

---

## ❌ One Giant Repository

Bad:

```text
ApplicationRepository

↓

Users

↓

Posts

↓

Comments

↓

Payments

↓

Orders
```

This becomes impossible to maintain.

---

# Best Practices

✅ Keep repositories independent.

✅ Let the Service Layer coordinate multiple repositories.

✅ Avoid circular dependencies.

✅ One repository = one entity.

✅ Keep business workflows inside services.

# Key Takeaways

- **Repository Composition** means using multiple repositories together to complete a business workflow.
    
- Repositories should **never call each other**.
    
- The **Service Layer** coordinates multiple repositories.
    
- Keeping repositories independent prevents circular dependencies and makes the code easier to test and maintain.
    
- This design scales well as applications grow and new repositories are added.
