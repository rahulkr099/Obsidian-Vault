# Module 9 — Testing Repositories

> **Goal:** Learn how to test repositories and services correctly by separating **database testing** from **business logic testing**.

---

# Lesson 9.1 — Testing Repositories

## 🎯 Learning Objectives

By the end of this lesson, you will understand:

- Why repositories need testing.
    
- What should be tested in a repository.
    
- Why repository tests should use a real database.
    
- Best practices for repository testing.
    

---

# Why Test Repositories?

The repository is responsible for talking to the database.

If a repository is wrong:

```text
Service

↓

Repository ❌

↓

Wrong Data

↓

Entire Application
```

Even if your business logic is perfect, incorrect database queries will cause bugs.

---

# What Should Repository Tests Verify?

Repository tests focus on **database behavior**, not business rules.

Examples:

```text
Can a record be created?

↓

Can it be found?

↓

Can it be updated?

↓

Can it be deleted?
```

---

# Test Against a Real Database

A common beginner mistake is mocking the database while testing repositories.

Bad:

```text
Repository

↓

Fake Database
```

This doesn't verify that your actual queries work.

Better:

```text
Repository

↓

Test Database

↓

Verify Real Results
```

Repository tests are usually **integration tests**.

---

# Example: Testing `create()`

Repository:

```text
create(postData)
```

Test:

```text
Create Post

↓

Retrieve Post

↓

Verify Stored Data
```

You're verifying that the repository actually writes to the database correctly.

---

# Example: Testing `findById()`

Flow:

```text
Insert Test Post

↓

findById(id)

↓

Verify Returned Post
```

Test both:

- Existing ID
    
- Non-existing ID
    

---

# Example: Testing `update()`

Flow:

```text
Create Post

↓

Update Title

↓

Read Again

↓

Verify New Title
```

---

# Example: Testing `delete()`

Flow:

```text
Create Post

↓

Delete Post

↓

findById()

↓

Should Return null
```

---

# Test Search & Filtering

If your repository supports:

```text
search(filters)
```

Test different scenarios:

- Search by keyword
    
- Filter by category
    
- Filter by author
    
- Multiple filters together
    

---

# Test Pagination

Repository:

```text
findPublished({
    page,
    limit
})
```

Verify:

- Correct number of records
    
- Correct page
    
- Correct ordering
    

---

# Test Relationships

Suppose:

```text
Post

↓

Author
```

Verify that related data is returned correctly.

Examples:

- Post includes author
    
- Missing relationships handled correctly
    

---

# Test Aggregation

Repository:

```text
getTopAuthors()
```

Verify:

- Correct counts
    
- Correct ordering
    
- Correct grouping
    

---

# Test Transactions

Suppose:

```text
Create Order

↓

Reduce Inventory

↓

Create Payment
```

Simulate a failure.

Verify:

```text
Rollback

↓

Database Remains Consistent
```

---

# Common Mistakes

## ❌ Testing Business Logic Here

Repository tests shouldn't verify:

```text
Can user publish?

↓

Permission checks

↓

Business workflows
```

Those belong to **Service tests**.

---

## ❌ Mocking the Database

Repository tests should verify **real queries**.

---

## ❌ Ignoring Edge Cases

Always test:

- Missing records
    
- Duplicate values
    
- Invalid IDs
    
- Empty results
    

---

# Best Practices

✅ Test against a test database.

✅ Verify CRUD operations.

✅ Test filtering and pagination.

✅ Test transactions.

✅ Keep repository tests focused on data access.

---

# Key Takeaways

- Repository tests are primarily **integration tests**.
    
- Test real database behavior.
    
- Verify CRUD, filtering, relationships, pagination, and transactions.
    
- Don't mix business logic into repository tests.

# Lesson 9.2 — Mocking Repositories in Service Tests

## 🎯 Learning Objectives

By the end of this lesson, you will understand:

- Why services should mock repositories.
    
- What should be tested in services.
    
- The difference between repository tests and service tests.
    

---

# What Does the Service Need?

The Service doesn't care whether the data comes from:

- MongoDB
    
- PostgreSQL
    
- Redis
    

It only needs data.

So instead of using a real database:

```text
Service

↓

Fake Repository

↓

Controlled Data
```

---

# Example

Suppose:

```text
publishPost(postId)
```

The service should test:

```text
Find Post

↓

Check Ownership

↓

Check Status

↓

Publish
```

The repository is mocked.

---

# Why Mock?

Without mocks:

```text
Service Test

↓

Real Database
```

Now failures may come from:

- Database
    
- Network
    
- Query bugs
    

You don't know whether the business logic failed.

---

With mocks:

```text
Service Test

↓

Mock Repository
```

You're testing **only the business logic**.

---

# Example Workflow

Mock:

```text
findById()

↓

Returns Draft Post
```

Service:

```text
publishPost()
```

Verify:

```text
Repository.update()

↓

Called Once
```

---

# What Should Service Tests Verify?

Examples:

- Permission checks
    
- Business rules
    
- Workflow order
    
- Error handling
    
- Calls to repositories
    

---

# Repository vs Service Tests

|Repository Tests|Service Tests|
|---|---|
|Real database|Mock repository|
|Verify queries|Verify business logic|
|CRUD|Permissions|
|Pagination|Workflows|
|Transactions|Business decisions|

---

# Testing Pyramid

```text
          Unit Tests
      (Services with Mocks)
              ▲
              │
      Integration Tests
 (Repositories + Database)
              ▲
              │
       End-to-End Tests
```

Each layer tests a different responsibility.

---

# Common Mistakes

## ❌ Service Tests Using Real Database

Service tests become slow and difficult to debug.

---

## ❌ Repository Tests Using Mocks

You never verify whether your queries actually work.

---

## ❌ Duplicating Tests

Don't test the same behavior in both layers.

---

# Best Practices

✅ Mock repositories in service tests.

✅ Use a real database in repository tests.

✅ Keep unit tests fast.

✅ Keep integration tests realistic.

---

# Visual Summary

```text
Repository Tests
        │
        ▼
Real Database
```

```text
Service Tests
        │
        ▼
Mock Repository
```

Each layer is tested independently.

---

# Key Takeaways

- **Repository tests** verify **database behavior**.
    
- **Service tests** verify **business logic**.
    
- Mock repositories when testing services.
    
- Use a real database when testing repositories.
    
- This separation produces faster, more reliable, and easier-to-maintain tests.
