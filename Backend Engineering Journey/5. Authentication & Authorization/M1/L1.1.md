# Why This Topic Matters

Many beginners think authentication and authorization are the same thing because they often happen one after another.

They are actually two different security checks.

Think of a company office.

1. The security guard checks your ID card before allowing you inside.
    
2. Once inside, your department decides which rooms you can enter.
    

The first is **authentication**.

The second is **authorization**.

Backend applications work the same way.

---

# What is Authentication?

Authentication answers one question:

> **"Who are you?"**

The server verifies that the user is really who they claim to be.

Examples:

- Email + Password
    
- Google Login
    
- GitHub Login
    
- OTP
    
- Fingerprint
    
- Face ID
    

If verification succeeds, the server knows the user's identity.

---

## Blog App Example

Rahul enters:

```text
Email:
rahul@example.com

Password:
********
```

Server checks:

```text
Does this email exist?

↓

Yes

↓

Does the password match?

↓

Yes

↓

User authenticated
```

At this point, the server knows:

```text
User ID = 6428...

Name = Rahul

Role = Author
```

Authentication is complete.

---

# What is Authorization?

Authorization answers another question:

> **"What are you allowed to do?"**

Now that the server knows who you are, it decides what actions you can perform.

Examples:

- Create a post
    
- Edit a post
    
- Delete a comment
    
- Manage users
    
- Access admin dashboard
    

---

## Blog Example

Rahul wants to publish a blog.

Server asks:

```text
Is Rahul an Author?

↓

Yes

↓

Allow
```

Now Rahul wants to delete another author's article.

Server asks:

```text
Does Rahul own this post?

↓

No

↓

Is Rahul an Admin?

↓

No

↓

Reject
```

Authentication succeeded.

Authorization failed.

---

# Authentication vs Authorization

|Authentication|Authorization|
|---|---|
|Verifies identity|Verifies permissions|
|Happens first|Happens after authentication|
|Answers "Who are you?"|Answers "What can you do?"|
|Login process|Permission check|
|Creates user identity|Grants or denies actions|

---

# Real Request Flow

Suppose Rahul wants to update a blog post.

```text
Client

↓

PUT /posts/123
```

The backend processes it like this:

```text
Receive Request

↓

Authentication

↓

Who is this user?

↓

Rahul

↓

Authorization

↓

Can Rahul edit this post?

↓

Yes

↓

Controller

↓

Service

↓

Repository

↓

Database
```

Only after both checks succeed does the request reach the business logic.

The server doesn't even check permissions because it doesn't know who the user is.

# Example 2 — Authorization Fails

```text

↓

Password Correct

↓

User Authenticated

↓

Delete Another User's Post

↓

Permission Denied

↓

403 Forbidden
```

The user is valid, but not allowed to perform the action.

# Blog App Permissions

|User|Can Read|Can Create|Can Edit Own|Can Delete Own|Can Delete Others|
|---|---|---|---|---|---|
|Guest|✅|❌|❌|❌|❌|
|Reader|✅|❌|❌|❌|❌|
|Author|✅|✅|✅|✅|❌|
|Admin|✅|✅|✅|✅|✅|

Notice that **all authenticated users do not have the same permissions**.

---

# Where Authentication Happens

Usually in middleware.

```text
Client

↓

Authentication Middleware

↓

Controller
```

The middleware verifies:

- JWT
    
- Session
    
- Cookie
    
- API Key
    

If verification fails:

```text
Stop request
```

---

# Where Authorization Happens

After authentication.

```text
Client

↓

Authentication Middleware

↓

Authorization Middleware

↓

Controller
```

Authorization checks things like:

- User role
    
- User permissions
    
- Resource ownership
    

---

# Common HTTP Status Codes

|Status Code|Meaning|Example|
|---|---|---|
|**200 OK**|Request succeeded|User viewed profile|
|**201 Created**|Resource created|New blog post|
|**401 Unauthorized**|Authentication failed|Invalid or missing token|
|**403 Forbidden**|Authentication succeeded but permission denied|Reader tries to delete a post|
|**404 Not Found**|Resource doesn't exist|Invalid post ID|

# Common Beginner Mistakes

### ❌ Mistake 1

Thinking login means unlimited access.

Correct:

```text
Login

↓

Identity verified

↓

Still need permission checks
```

---

### ❌ Mistake 2

Skipping authorization.

Example:

```javascript
DELETE /posts/:id
```

If you only verify the JWT but never check ownership, any logged-in user could delete any post.

---

### ❌ Mistake 3

Trusting the frontend.

Frontend:

```text
Hide Delete Button
```

Backend:

```text
Must still verify permissions.
```

Never rely on the frontend for security.

# Real-World Analogy

Imagine an airport.

### Authentication

Security checks your passport.

```text
Passport Valid?

↓

Yes

↓

Enter Airport
```

---

### Authorization

Your boarding pass determines where you can go.

```text
Business Lounge?

↓

Allowed

↓

Economy Lounge?

↓

Different access
```

Authentication proves your identity.

Authorization determines your access.

---

# Best Practices

- Always authenticate before authorizing.
    
- Never trust client-side role information.
    
- Perform permission checks on the server.
    
- Return appropriate HTTP status codes.
    
- Keep authentication and authorization separate.
    

---

# Summary

In this lesson, you learned:

- Authentication verifies **who the user is**.
    
- Authorization determines **what the user can do**.
    
- Authentication happens before authorization.
    
- Both checks are essential for secure backend applications.
    
- Middleware is commonly used to perform these checks before the request reaches your business logic.
