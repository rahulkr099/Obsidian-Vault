# Module 1 — Authentication vs Authorization

# Lesson 1.2 — Real-world Authentication Flow in a Blog App

> **Goal:** Understand the complete authentication flow from login to accessing protected APIs, and see where each backend component participates.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Follow the complete authentication lifecycle.
    
- Understand how the client and server communicate.
    
- Know the responsibilities of each backend layer.
    
- See where authentication and authorization happen.
    
- Understand why this architecture is used in production.
    

---

# The Big Picture

Imagine Rahul wants to create a new blog post.

Before the post is created, the backend must answer two questions:

1. **Who is making this request?** (Authentication)
    
2. **Are they allowed to create a post?** (Authorization)
    

Only after both checks pass should the business logic run.

---

# Overall Flow

```text
User
   │
   ▼
Login
   │
   ▼
Server verifies credentials
   │
   ▼
Access Token + Refresh Token
   │
   ▼
Client stores tokens
   │
   ▼
Protected API Request
   │
   ▼
Authentication Middleware
   │
   ▼
Authorization Check
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Database
```

This is the flow you'll implement in almost every modern backend application.

---

# Step 1 — User Logs In

Rahul enters:

```text
Email:
rahul@example.com

Password:
********
```

The frontend sends:

```http
POST /api/auth/login
```

Example request:

```json
{
  "email": "rahul@example.com",
  "password": "password123"
}
```

The backend has not trusted Rahul yet.

It must verify his identity.

---

# Step 2 — Server Verifies Credentials

The authentication service performs several checks.

```text
Receive Login Request
        │
        ▼
Validate Input
        │
        ▼
Find User by Email
        │
        ▼
Compare Password Hash
        │
        ▼
Check Email Verified
        │
        ▼
Check Account Status
```

If every check succeeds:

```text
User Authenticated
```

Otherwise:

```text
Login Failed
```

---

# Step 3 — Generate Tokens

After successful authentication:

```text
Generate Access Token

Generate Refresh Token
```

Example:

```text
Access Token
Expires in 15 minutes

Refresh Token
Expires in 7 days
```

We'll study these tokens in detail later.

For now, just remember:

- Access Token → Access protected APIs.
    
- Refresh Token → Get a new Access Token.
    

---

# Step 4 — Client Stores Tokens

Typical browser application:

```text
Access Token

↓

Memory or Secure Cookie
```

```text
Refresh Token

↓

HttpOnly Cookie
```

Why?

Because JavaScript cannot read an HttpOnly cookie, making it much harder for attackers to steal.

---

# Step 5 — User Creates a Blog Post

Rahul clicks:

```text
Create Post
```

The frontend sends:

```http
POST /api/posts
```

It also sends the Access Token.

Example:

```http
Authorization: Bearer eyJhbGciOi...
```

The server now needs to verify the token.

---

# Step 6 — Authentication Middleware

The request reaches the middleware first.

```text
Incoming Request
        │
        ▼
Authentication Middleware
```

The middleware checks:

- Is a token present?
    
- Is it valid?
    
- Has it expired?
    
- Was it signed by our server?
    

If everything is correct:

```text
Token Valid

↓

Extract User ID

↓

Attach User to Request
```

Example:

```javascript
req.user = {
    userId: "64ab...",
    role: "author"
}
```

Notice:

The middleware **does not create posts**.

Its only job is to identify the user.

---

# Step 7 — Authorization

Now the backend knows:

```text
User ID

Role
```

Next question:

```text
Can this user create a blog post?
```

If Rahul is:

```text
Role = Author
```

Result:

```text
Allow
```

If Rahul is:

```text
Guest
```

Result:

```text
Reject
```

Authentication answered:

> Who are you?

Authorization answered:

> What can you do?

---

# Step 8 — Controller

Only after both checks pass:

```text
Controller
```

Controller responsibilities:

- Read request data.
    
- Call the service.
    
- Return the response.
    

Controllers should stay thin.

Example:

```text
Receive Request

↓

Call Service

↓

Return Response
```

---

# Step 9 — Service Layer

The service contains business rules.

Example:

```text
Is the title unique?

↓

Generate Slug

↓

Prepare Data

↓

Save Post
```

Business decisions belong here.

---

# Step 10 — Repository Layer

The repository communicates with the database.

```text
Create Post

↓

MongoDB
```

The repository should not know anything about JWTs, roles, or permissions.

It only performs database operations.

# What Happens if Authentication Fails?

Example:

```text
Missing Token
```

Flow:

```text
Request

↓

Authentication Middleware

↓

Reject

↓

401 Unauthorized
```

The controller is never called.

---

# What Happens if Authorization Fails?

Example:

Rahul tries to delete another author's post.

```text
Authentication

↓

Success

↓

Ownership Check

↓

Failed

↓

403 Forbidden
```

Again, the controller or service should not continue with the operation.

---

# Responsibility of Each Layer

|Layer|Responsibility|
|---|---|
|Client|Sends login credentials and tokens|
|Authentication Middleware|Verifies identity|
|Authorization|Checks permissions|
|Controller|Handles HTTP request and response|
|Service|Business logic|
|Repository|Database access|
|Database|Stores data|

A good backend gives each layer one clear responsibility.

---

# Common Beginner Mistakes

### ❌ Mixing Authentication with Business Logic

Bad:

```text
Controller

↓

Verify JWT

↓

Compare Password

↓

Save Post
```

Everything is mixed together.

Better:

```text
Authentication Middleware

↓

Authorization

↓

Controller

↓

Service
```

---

### ❌ Repository Checking Roles

Bad:

```text
Repository

↓

Is User Admin?
```

Repositories should never decide permissions.

---

### ❌ Trusting Frontend Roles

Frontend:

```json
{
    "role": "admin"
}
```

Never trust this.

The server must determine the user's role from a verified source, such as the authenticated user record.

---

# Production Architecture

A professional backend often looks like this:

```text
Client

↓

Route

↓

Authentication Middleware

↓

Authorization Middleware

↓

Controller

↓

Service

↓

Repository

↓

Database
```

Each layer has a single responsibility, making the application secure, maintainable, and scalable.

---

# Key Takeaways

- Authentication verifies the user's identity.
    
- Authorization checks whether the authenticated user can perform the requested action.
    
- Middleware handles authentication before the request reaches the controller.
    
- Controllers coordinate requests, services contain business logic, and repositories interact with the database.
    
- Keeping responsibilities separated results in cleaner and more secure backend applications.
