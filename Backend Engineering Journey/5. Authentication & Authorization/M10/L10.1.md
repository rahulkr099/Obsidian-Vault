# Module 10 — Password Reset

# Lesson 10.1 — Password Reset Architecture

> **Goal:** Learn how professional backend applications design a secure password reset system that protects user accounts while providing a simple recovery experience.

Password reset is one of the most attacked authentication features.

A professional backend engineer doesn't think:

> "How do I reset the password?"

Instead, they think:

> "How do I let the real user recover their account without helping an attacker?"

# Why Password Reset Exists

Users forget passwords.

Without password reset:

```text
Forgot Password

↓

Cannot Login

↓

Account Lost
```

Password reset allows users to recover access **without contacting support**.

---

# Password Reset vs Password Change

Many beginners confuse these.

## Password Change

The user is already authenticated.

```text
Login

↓

Settings

↓

Change Password
```

The user proves identity by already being logged in (and often by entering the current password).

---

## Password Reset

The user cannot log in.

```text
Forgot Password

↓

Recovery

↓

New Password
```

Identity must be verified in another way.

Usually:

```text
Email Ownership
```

---

# Complete Password Reset Flow

```text
Forgot Password

↓

Enter Email

↓

Generate Reset Token

↓

Send Email

↓

User Clicks Link

↓

Verify Token

↓

Enter New Password

↓

Update Password

↓

Invalidate Sessions

↓

Login With New Password
```

Notice:

The password is **never** changed until the token is verified.

---

# Blog App Example

Rahul forgets his password.

```text
Rahul

↓

Forgot Password

↓

rahul@example.com

↓

Reset Email Sent
```

Rahul opens:

```text
Email

↓

Reset Password Link
```

Backend:

```text
Verify Token

↓

Allow Password Reset
```

---

# Password Reset is NOT Authentication

Authentication asks:

```text
Who are you?
```

Password reset asks:

```text
Can you prove you own this account?
```

The proof comes from the reset token sent to the registered email address.

---

# Password Reset Architecture

```text
Client

↓

Forgot Password API

↓

User Service

↓

User Repository

↓

Database

↓

Email Service

↓

Reset Email
```

Notice:

The Email Service is separate from authentication logic.

# Email Enumeration Attack

This is one of the most common interview topics.

Suppose Rahul exists.

Aman tries:

```text
Forgot Password

↓

rahul@example.com
```

Bad response:

```text
Email Exists
```

Now Aman knows Rahul has an account.

---

Now Aman tries:

```text
unknown@example.com
```

Response:

```text
Email Not Found
```

Now Aman can identify which email addresses are registered.

This is called **email enumeration**.

---

# Secure Response

Professional applications respond the same way for both cases.

Whether the email exists or not:

```text
"If an account exists for this email,
a password reset link has been sent."
```

The attacker learns nothing.

The real user still receives the email.

---

# Reset States

Think in terms of states.

```text
Normal Account

↓

Reset Requested

↓

Reset Email Sent

↓

Token Verified

↓

Password Updated

↓

Normal Account
```

This state-based design makes the flow predictable.

---

# Should Password Reset Require Login?

No.

If the user could log in:

```text
Login

↓

Change Password
```

There would be no need for password reset.

Password reset exists specifically for users who **cannot authenticate**.

---

# Should the Account Be Locked?

Usually:

No.

The account remains usable.

The password changes **only after** successful verification.

Some applications may temporarily limit repeated reset requests, but they don't generally lock the account just because a reset was requested.

---

# Where Does Reset Logic Belong?

Following our architecture:

```text
Route

↓

Controller

↓

User Service

↓

User Repository

↓

Database
```

### Controller

- Receive request
    
- Return response
    

---

### User Service

Responsible for:

- Generating reset tokens
    
- Applying reset policies
    
- Updating passwords
    
- Invalidating sessions
    

---

### Repository

Responsible for:

- Reading users
    
- Updating stored data
    

No business rules.

---

### Email Service

Responsible for:

- Sending reset emails
    
- Email templates
    
- Delivery
    

---

# Reset Request Flow

```text
Forgot Password Request

↓

Validate Email Format

↓

Find User

↓

Generate Reset Token

↓

Store Hashed Token

↓

Send Email

↓

Return Generic Response
```

The client never knows whether the email exists.

---

# Reset Confirmation Flow

```text
Receive Token

↓

Validate Token

↓

Token Expired?

↓

No

↓

Hash New Password

↓

Save Password

↓

Invalidate Sessions

↓

Delete Reset Token

↓

Success
```

Everything happens in one secure transaction.

# Production Design Questions

Before implementation, decide:

- How long should reset tokens remain valid?
    
- Should requesting a new reset invalidate the previous token?
    
- How many reset emails can be requested?
    
- Should password reset invalidate every active session?
    
- Should the user be notified after a successful password reset?
    

Professional systems answer these questions before coding.

---

# Common Beginner Mistakes

## ❌ Revealing Whether an Email Exists

Bad:

```text
Email Not Found
```

Use a generic response instead.

---

## ❌ Changing Password Before Verification

Wrong flow:

```text
Forgot Password

↓

Password Changed
```

Always verify the reset token first.

---

## ❌ Mixing Password Reset with Login

Keep these flows separate.

```text
Authentication

↓

Identity
```

```text
Password Reset

↓

Account Recovery
```

---

## ❌ Sending Emails from Controllers

Controllers should never contain email provider logic.

Use a dedicated Email Service.

---

## ❌ Forgetting Session Invalidation

If the password changes:

Old sessions should no longer remain trusted.

We'll cover this in Lesson 10.3.

---

# Best Practices

- Keep password reset independent from authentication.
    
- Return the same response whether the email exists or not.
    
- Generate reset tokens only on the backend.
    
- Handle email sending through a dedicated service.
    
- Design password reset as a separate workflow.
    
- Plan session invalidation after a successful reset.

# Interview Questions

### Q1. What's the difference between password change and password reset?

**Answer:**

A password change is performed by an authenticated user, while a password reset is an account recovery process for users who cannot log in.

---

### Q2. Why shouldn't the API reveal whether an email exists?

**Answer:**

Revealing whether an email is registered enables email enumeration attacks, allowing attackers to discover valid user accounts.

---

### Q3. Where should password reset logic be implemented?

**Answer:**

In the service layer, because generating reset tokens, updating passwords, and applying security policies are business rules.

---

### Q4. Should a password be updated immediately after a reset request?

**Answer:**

No. The password should only be updated after the reset token has been successfully verified.
