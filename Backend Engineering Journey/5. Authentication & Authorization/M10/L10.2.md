# Module 10 — Password Reset

# Lesson 10.2 — Password Reset Tokens

> **Goal:** Learn how professional backend applications design secure password reset tokens that prevent account takeover, replay attacks, and unauthorized password changes.

A password reset token is one of the **most sensitive secrets** your backend generates.

If an attacker obtains a valid reset token, they can often take over the user's account.

That's why production applications treat reset tokens with the same care as passwords.

# What is a Password Reset Token?

A password reset token is a **temporary secret** that proves the user owns the account.

Flow:

```text
Forgot Password

↓

Generate Reset Token

↓

Send Email

↓

User Clicks Link

↓

Verify Token

↓

Allow Password Change
```

Notice:

The token **does not reset the password**.

It only authorizes the password reset.

---

# Reset Token Lifecycle

A production system follows this lifecycle.

```text
Generate Token

↓

Hash Token

↓

Store Hash

↓

Send Original Token

↓

User Clicks Link

↓

Verify Token

↓

Update Password

↓

Delete Token
```

Every stage is important.

---

# Token Requirements

A reset token should be:

- Cryptographically random
    
- Long enough
    
- Unpredictable
    
- Temporary
    
- Single-use
    

It should never be based on:

- User ID
    
- Email
    
- Timestamp
    
- Username
    

---

# Good vs Bad Tokens

❌ Bad

```text
rahul123
```

```text
reset2026
```

```text
user45
```

Predictable.

---

✅ Good

```text
M8fj3QwYvL1nK9...
```

Generated using a cryptographically secure random generator.

---

# Backend Responsibility

Only the backend generates tokens.

Never:

```text
Frontend

↓

Generate Reset Token
```

Always:

```text
Backend

↓

Generate Secure Token
```

---

# Reset Link

The email contains a URL like:

```text
https://blogapp.com/reset-password?token=abc123...
```

When clicked:

```text
Browser

↓

Backend

↓

Verify Token
```

The backend decides whether the request is valid.

---

# Should Tokens Be Stored?

Yes.

The server must compare the incoming token with a stored value.

Workflow:

```text
Generate Token

↓

Store Token Information

↓

Send Email
```

---

# Hashing Reset Tokens

Professional systems usually store:

```text
Hash(Token)
```

instead of:

```text
Original Token
```

This is the same security principle used for passwords.

---

# Why Hash the Token?

Imagine someone gains read access to your database.

Plain text storage:

```text
Database Leak

↓

Reset Token Visible

↓

Account Takeover
```

Hashed storage:

```text
Database Leak

↓

Hash Visible

↓

Original Token Protected
```

Hashing reduces the impact of a database compromise.

---

# Verification Process

When the user clicks the link:

```text
Receive Token

↓

Hash Incoming Token

↓

Compare With Stored Hash

↓

Match?

↓

Allow Reset
```

The original token never needs to be stored.

---

# Token Expiration

Reset tokens should expire quickly.

Example:

```text
Generate Token

↓

Valid For

↓

15 Minutes
```

or

```text
30 Minutes
```

Choose a duration appropriate for your application's security requirements.

---

# Why Short Expiration?

Suppose:

```text
Email Stolen

↓

Reset Link Still Valid

↓

2 Days Later
```

The attacker has more opportunity to misuse it.

Short-lived tokens reduce this risk.

---

# Single-Use Tokens

Once the password is reset:

```text
Update Password

↓

Delete Reset Token
```

The token must become invalid immediately.

---

# Replay Attack

Bad design:

```text
Reset Password

↓

Click Same Link Again

↓

Still Works
```

Good design:

```text
Reset Password

↓

Delete Token

↓

Second Attempt

↓

Reject
```

---

# Multiple Reset Requests

Rahul clicks:

```text
Forgot Password
```

Three times.

Professional flow:

```text
Generate New Token

↓

Invalidate Old Token

↓

Store New Token

↓

Send Email
```

Only the latest reset link works.

---

# Expired Token

Backend:

```text
Token Expired?

↓

Yes

↓

Reject

↓

Request New Reset Email
```

Never extend an expired token.

Always create a new one.

---

# Invalid Token

Suppose someone changes the URL.

```text
...?token=random
```

Backend:

```text
Find Token

↓

Not Found

↓

Reject
```

Never allow password changes without a valid token.

---

# Where Does Token Logic Belong?

Architecture:

```text
Route

↓

Controller

↓

User Service

↓

Repository
```

### User Service

Responsible for:

- Token generation
    
- Token hashing
    
- Token verification
    
- Expiration checks
    
- Token deletion
    

### Repository

Responsible for:

- Persisting token data
    

No business rules.

---

# Production Design Decisions

Before implementation, define:

- Token expiration time
    
- Maximum active reset tokens
    
- Whether new requests invalidate old tokens
    
- Maximum reset requests per hour
    
- Logging strategy for reset attempts
    

These policies improve both security and maintainability.

---

# Common Beginner Mistakes

## ❌ Predictable Tokens

Never use:

```text
userId + timestamp
```

Generate cryptographically secure random values.

---

## ❌ Plain Text Storage

Store hashed reset tokens instead of the original values.

---

## ❌ Long-Lived Tokens

Bad:

```text
Valid For

30 Days
```

Reset tokens should be temporary.

---

## ❌ Reusable Tokens

Delete or invalidate the token immediately after a successful password reset.

---

## ❌ Multiple Valid Tokens

When creating a new reset token:

```text
Old Token

↓

Invalidate

↓

New Token

↓

Store
```

Keep only one valid reset token per user.

---

# Best Practices

- Generate cryptographically secure random tokens.
    
- Store hashed tokens.
    
- Set short expiration times.
    
- Make tokens single-use.
    
- Invalidate previous reset tokens.
    
- Keep token logic in the service layer.
    
- Delete token data after a successful reset.

# Interview Questions

### Q1. Why should password reset tokens be hashed?

**Answer:**

Hashing protects the original token if the database is compromised. The backend compares hashes without storing the original secret.

---

### Q2. Why should reset tokens expire quickly?

**Answer:**

A short expiration reduces the time window in which a stolen or intercepted reset link can be misused.

---

### Q3. Why should reset tokens be single-use?

**Answer:**

Single-use tokens prevent replay attacks by ensuring the same reset link cannot be reused after the password has been changed.

---

### Q4. What should happen when a user requests another password reset?

**Answer:**

Generate a new reset token, invalidate the previous one, store the new hashed token, and send a new reset email.

# 💡 Backend Engineering Tip

Although **email verification tokens** and **password reset tokens** look similar, they serve different purposes:

```text
Email Verification

↓

Prove Email Ownership

────────────────

Password Reset

↓

Recover Account Access
```

Both should be:

- Random
    
- Hashed before storage
    
- Single-use
    
- Time-limited
    

But a **password reset token** protects something even more sensitive—the ability to change a user's password. That's why many applications use a **shorter expiration time** and stricter security policies for reset tokens than for email verification tokens.
