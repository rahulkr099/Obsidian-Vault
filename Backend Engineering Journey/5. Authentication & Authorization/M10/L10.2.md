# What is a Unit Test?

A **unit** is the smallest testable part of your application.

Examples:

- A function
    
- A service method
    
- A utility function
    

A unit test verifies that one unit behaves correctly.

---

# Why Unit Testing?

Suppose your service contains:

```text
createPost()
```

It contains business rules like:

- Title is required.
    
- User must be an author.
    
- Maximum 5 drafts allowed.
    

A unit test verifies these rules without involving:

- Express
    
- MongoDB
    
- HTTP requests
    

---

# The Unit Under Test

Our architecture:

```text
Controller

↓

Service

↓

Repository

↓

Database
```

For unit testing:

```text
Service

↓

Test Directly
```

The service is the **Unit Under Test (UUT)**.

---

# Why Test Services?

Controllers mostly:

- Read request
    
- Call service
    
- Return response
    

Repositories mostly:

- Execute database queries
    

Services contain:

```text
Business Rules
```

That's where unit testing provides the most value.

---

# Dependencies

Suppose:

```text
PostService

↓

PostRepository
```

If the repository uses MongoDB:

A unit test should **not** connect to a real database.

Instead:

```text
Mock Repository
```

---

# What is Mocking?

Mocking means replacing a real dependency with a fake one.

Instead of:

```text
MongoDB
```

Use:

```text
Fake Repository
```

The fake repository returns predefined results.

---

# Example

Real repository:

```text
findPost()

↓

Database
```

Mock repository:

```text
findPost()

↓

Fake Data
```

The service doesn't know the difference.

---

# Unit Test Flow

```text
Test

↓

Mock Repository

↓

Service

↓

Assertion
```

Fast.

No database.


# Assertions

A test should verify expectations.

Example:

```text
Expected

↓

Received
```

If they match:

```text
PASS
```

Otherwise:

```text
FAIL
```

Assertions are the heart of testing.

---

# Test Structure

Most unit tests follow this pattern:

```text
Arrange

↓

Act

↓

Assert
```

---

## Arrange

Prepare:

```text
Mock Data

Mock Repository

Service
```

---

## Act

Call:

```text
createPost()
```

---

## Assert

Verify:

```text
Correct Result
```

or

```text
Correct Error
```

---

# Failure Test

Scenario:

Expected:


# Mocking External Services

Suppose registration sends an email.

Service:

```text
Register User

↓

Email Service
```

A unit test should **not** send a real email.

Instead:

```text
Mock Email Service
```

Verify:

```text
Email Function Called
```

---

# Mocking JWT

Suppose:

```text
Generate JWT
```

Instead of generating a real token:

Use:

```text
Mock Token
```

The test focuses on your business logic.

---

# Mocking Time

Example:

Password reset token expires.

Instead of waiting:

```text
30 Minutes
```

Mock the current time.

Tests remain fast.

```text

```

# What Should NOT Be Tested?

In a unit test:

Don't test:

- MongoDB
    
- Express
    
- JWT library
    
- bcrypt library
    

Those libraries already have their own tests.

Test **your code**.

---

# Good Unit Test Characteristics

A unit test should be:

- Fast
    
- Independent
    
- Predictable
    
- Easy to read
    
- Easy to maintain
    

Running thousands of unit tests should take only a short time.

---

# Naming Tests

Good names explain behavior.

Examples:

```text
Should Create Post
```

```text
Should Reject Empty Title
```

```text
Should Throw NotFoundError
```

Avoid vague names like:

```text
Test1
```

---

# Common Beginner Mistakes

## ❌ Using a Real Database

Bad:

```text
Unit Test

↓

MongoDB
```

Use mocks instead.

---

## ❌ Testing Multiple Services Together

Bad:

```text
Service A

↓

Service B

↓

Database
```

That's closer to an integration test.

---

## ❌ Not Testing Failure Cases

Only testing:

```text
Success
```

isn't enough.

Also test:

- Invalid input
    
- Unauthorized user
    
- Missing resource
    
- Duplicate email
    

---

## ❌ Mocking Too Much

Don't mock the code you're trying to test.

Mock **dependencies**, not the unit itself.

---

## ❌ Writing Huge Tests

A unit test should verify one behavior.

Not an entire feature.

---

# Best Practices

- Test the service layer.
    
- Mock repositories and external services.
    
- Follow Arrange–Act–Assert.
    
- Write descriptive test names.
    
- Test success and failure paths.
    
- Keep tests isolated and fast.
    
- Verify business rules.

# Interview Questions

### Q1. What is a unit test?

**Answer:**

A unit test verifies one small unit of code (such as a service method or function) in isolation by mocking its dependencies.

---

### Q2. Why mock the repository?

**Answer:**

Because a unit test should verify business logic, not database behavior. Mocking keeps tests fast, deterministic, and independent of external systems.

---

### Q3. Which layer is usually the best candidate for unit testing?

**Answer:**

The **service layer**, because it contains the application's business rules and decision-making logic.

---

### Q4. What does Arrange–Act–Assert mean?

**Answer:**

- **Arrange:** Prepare the test data and mocks.
    
- **Act:** Execute the unit being tested.
    
- **Assert:** Verify the expected outcome.

# 💡 Backend Engineering Tip

Think of a **unit test** as asking one simple question:

```text
"If I give this service
these inputs,

does it make the correct
business decision?"
```

Notice that it **doesn't ask**:

- Can MongoDB save data?
    
- Can Express handle routes?
    
- Can JWT generate tokens?
    

Those belong to other tests.

A professional backend testing strategy separates responsibilities:

```text
Unit Tests

↓

Business Logic

────────────────

Integration Tests

↓

Components Working Together

────────────────

API Tests

↓

Real HTTP Requests
```

This separation keeps your test suite fast, reliable, and easy to maintain.
