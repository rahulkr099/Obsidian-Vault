# What is API Testing?

API testing treats your backend like a real client would.

Instead of calling:

```text
PostService.createPost()
```

You send:

```http
POST /api/posts
```

Exactly like a frontend application.

---

# API Testing Flow

```text
Client

↓

HTTP Request

↓

Backend

↓

HTTP Response

↓

Assertions
```

The backend is tested from the outside.

---

# Difference from Integration Testing

Integration testing focuses on:

```text
Internal Components
```

API testing focuses on:

```text
Public API Behavior
```

The client doesn't care about:

- Service layer
    
- Repository
    
- Internal implementation
    

The client cares about:

- Status code
    
- Response body
    
- Headers
    
- Cookies

Rahul logs in.

Response:

```json

    "user": {}
```

The API test verifies the entire response.

# What Should Be Tested?

Every endpoint should verify:

- Status code
    
- Response body
    
- Response headers
    
- Cookies (if applicable)
    
- Response time (optional)
    
- Error messages

# Edge Cases

Professional engineers don't only test normal scenarios.

Examples:

- Empty body
    
- Very long title
    
- Invalid ObjectId
    
- Expired JWT
    
- Missing Authorization header
    
- Duplicate email
    
- Invalid page number
    
- SQL/NoSQL injection attempts
    
- Extremely large payloads
    

Edge cases improve API reliability.

# Test Coverage

Coverage answers:

> **How much of my code is exercised by tests?**

High coverage is helpful, but:

> **Meaningful tests are more important than high percentages.**

A few high-quality tests are often better than many weak ones.

# Production Testing Mindset

Before deployment, ask:

- Can users register?
    
- Can users log in?
    
- Can users reset passwords?
    
- Are protected routes secure?
    
- Are validation errors correct?
    
- Are authorization checks enforced?
    
- Are error responses consistent?
    

Think like both a user and an attacker.

# Common Beginner Mistakes

## ❌ Only Testing Success Cases

Also test:

- Invalid input
    
- Unauthorized requests
    
- Forbidden requests
    
- Missing resources
    
- Server errors
    

---

## ❌ Ignoring Response Format

Don't check only:

```http
200 OK
```

Also verify:

- JSON structure
    
- Required fields
    
- Data types
    

---

## ❌ Manual Testing Only

Manual testing is useful during development, but automated tests help catch regressions and save time over the long term.

---

## ❌ Ignoring Edge Cases

Always think:

> What if the client sends unexpected input?

---

## ❌ Deploying Without Running Tests

Always execute your automated test suite before deployment.

---

# Best Practices

- Test every API endpoint.
    
- Verify both success and failure responses.
    
- Organize tests by feature.
    
- Automate API tests.
    
- Include edge cases.
    
- Run tests in CI/CD.
    
- Keep tests easy to read and maintain.

# Interview Questions

### Q1. What is API testing?

**Answer:**

API testing verifies backend behavior by sending real HTTP requests and checking the responses, just as a frontend application or API consumer would.

---

### Q2. What should every API test verify?

**Answer:**

At minimum, it should verify the HTTP status code, response body, and any important headers or cookies.

---

### Q3. Why automate API tests?

**Answer:**

Automated tests are fast, repeatable, reduce manual effort, and help detect regressions before deployment.

---

### Q4. Why are edge cases important?

**Answer:**

Edge cases verify that the API behaves correctly when it receives unusual, invalid, or unexpected input, improving reliability and security.

# 💡 Backend Engineering Tip

A reliable backend is built on **multiple layers of testing**, not just one.

Think of it like this:

```text
Unit Tests

↓

"Does my business logic work?"

────────────────

Integration Tests

↓

"Do my backend components work together?"

────────────────

API Tests

↓

"Does the application behave correctly for clients?"

────────────────

CI/CD

↓

"Can this safely be deployed?"
```

Each layer catches different kinds of problems. Together, they help you release new features with confidence.
