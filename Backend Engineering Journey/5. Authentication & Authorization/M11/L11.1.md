# Module 11 — Authentication Middleware

# Lesson 11.1 — Authentication Middleware Architecture

> **Goal:** Learn how professional backend applications authenticate every protected request using reusable middleware.

Logging in once **does not mean** the backend remembers the user forever.

HTTP is **stateless**.

That means **every protected request must prove the user's identity again.**

Authentication middleware is responsible for doing exactly that.

---

# The Problem

Rahul logs in successfully.

```text
POST /login

↓

JWT Issued
```

Five minutes later:

```http
POST /posts
```

How does the server know this request came from Rahul?

It doesn't.

Every request is independent.

---

# HTTP is Stateless

Unlike desktop applications,

HTTP works like this:

```text
Request 1

↓

Response

──────────────

Request 2

↓

Response

──────────────

Request 3

↓

Response
```

The server does **not automatically remember** previous requests.

Every protected request must provide proof of identity.

---

# Solution

Every protected request carries:

```text
Access Token (JWT)
```

Example:

```http
Authorization: Bearer <access_token>
```

The backend verifies this token **before** executing any business logic.

---

# Where Should Authentication Happen?

Some beginners do this:

```text
Route

↓

Controller

↓

Verify JWT

↓

Business Logic
```

Now every controller repeats the same authentication code.

Bad design.

---

Professional applications use:

```text
Route

↓

Authentication Middleware

↓

Controller

↓

Service
```

Authentication happens once.

Controllers remain clean.

---

# Request Lifecycle

A protected request flows like this:

```text
Client

↓

Express Route

↓

Authentication Middleware

↓

Controller

↓

Service

↓

Repository

↓

Database

↓

Response
```

Authentication is performed **before** reaching the controller.

---

# Public vs Protected Routes

Not every endpoint requires authentication.

---

## Public Routes

Examples:

```text
POST /register

POST /login

POST /forgot-password

GET /health
```

Anyone can access these.

---

## Protected Routes

Examples:

```text
POST /posts

PUT /posts/:id

DELETE /posts/:id

GET /profile
```

Authentication is required.

Rahul requests:

```http

```

Flow:

```text

↓

↓

↓

Yes

↓

Controller

↓

```

---

```text

↓

Authentication Middleware

↓

No Token

↓

401 Unauthorized
```

The controller never runs.

---

# Authentication Middleware Responsibilities

Authentication middleware should only answer:

> **Who is making this request?**

Its responsibilities:

- Read access token.
    
- Verify JWT.
    
- Load authenticated user.
    
- Attach user to the request.
    
- Reject invalid requests.
    

Nothing more.

---

# What Authentication Middleware Should NOT Do

It should **not**:

- Check roles
    
- Check permissions
    
- Check ownership
    
- Perform business logic
    
- Query unrelated data
    

Those belong elsewhere.

---

# Authentication vs Authorization

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

These are separate responsibilities.

Example:

```text
Authentication

↓

Rahul
```

Then:

```text
Authorization

↓

Can Rahul delete this post?
```

Authentication happens first.

Authorization comes later.

---

# Middleware Chain

Professional request pipeline:

```text
Request

↓

Authentication Middleware

↓

Authorization Middleware

↓

Validation Middleware

↓

Controller

↓

Service

↓

Repository
```

Each middleware has one responsibility.

---

# Why Middleware?

Imagine you have:

- 20 Controllers
    
- 100 Protected APIs
    

Without middleware:

```text
Controller A

↓

Verify JWT

──────────

Controller B

↓

Verify JWT

──────────

Controller C

↓

Verify JWT
```

Lots of duplicate code.

---

With middleware:

```text
Authentication Middleware

↓

All Protected Controllers
```

Write once.

Reuse everywhere.

---

# Attaching the User

After successful authentication:

```text
Verify JWT

↓

Load User

↓

Attach User

↓

Request Continues
```

Later layers can simply use:

```text
Authenticated User
```

instead of verifying the token again.

# Common Beginner Mistakes

## ❌ Verifying JWT in Controllers

Bad:

```text
Controller

↓

Verify JWT
```

Controllers shouldn't handle authentication.

---

## ❌ Mixing Authentication and Authorization

Bad:

```text
Verify JWT

↓

Check Role

↓

Business Logic
```

Authentication and authorization should be separate concerns.

---

## ❌ Trusting Client Data

Never trust:

```json
{
  "role": "admin"
}
```

Identity must come from a verified token and trusted data sources.

---

## ❌ Authenticating Public Routes

Don't require authentication for:

- Register
    
- Login
    
- Forgot Password
    

Public endpoints should remain accessible.

---

## ❌ Skipping Middleware

Never allow protected controllers to bypass authentication middleware.

---

# Best Practices

- Authenticate every protected request.
    
- Keep authentication in middleware.
    
- Keep controllers free of authentication logic.
    
- Separate authentication from authorization.
    
- Protect only the routes that require authentication.
    
- Follow the Route → Middleware → Controller → Service architecture.

# Interview Questions

### Q1. Why is authentication middleware needed?

**Answer:**

Because HTTP is stateless. Every protected request must prove the user's identity before accessing protected resources.

---

### Q2. Why shouldn't controllers verify JWTs?

**Answer:**

Doing so duplicates code across controllers and mixes authentication with request handling. Middleware centralizes authentication and keeps controllers focused on business logic.

---

### Q3. What's the responsibility of authentication middleware?

**Answer:**

To verify the user's identity by validating the access token, loading the authenticated user, attaching the user to the request, and rejecting invalid requests.

---

### Q4. Does authentication middleware perform authorization?

**Answer:**

No. Authentication identifies the user. Authorization determines what that authenticated user is allowed to do.

# 💡 Backend Engineering Tip

Think of authentication middleware as the **security gate** of your backend.

```text
Incoming Request

↓

Security Gate
(Authentication Middleware)

↓

Identity Verified?

├── No → 401 Unauthorized
│
└── Yes
      ↓
Controller

↓

Business Logic
```

Everything behind this gate can safely assume:

> **"The user has already been authenticated."**

That assumption keeps your controllers simple, your services focused on business logic, and your architecture clean and maintainable.
