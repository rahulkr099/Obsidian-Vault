# Module 11 — Authentication Middleware

# Lesson 11.2 — JWT Verification & User Context

> **Goal:** Learn how professional authentication middleware verifies JWTs, loads the authenticated user, and creates a trusted user context for the rest of the request.

Authentication middleware does much more than simply calling `jwt.verify()`.

Its job is to transform an **anonymous HTTP request** into an **authenticated request** that the rest of your application can trust.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand the complete JWT verification process.
    
- Learn where JWTs are read from.
    
- Verify JWT signatures.
    
- Handle invalid and expired tokens.
    
- Load the authenticated user.
    
- Build a trusted user context.
    

---

# The Problem

Rahul sends:

```http
POST /api/posts
```

Along with:

```http
Authorization: Bearer eyJhbGciOi...
```

The backend must answer:

```text
Can I trust this token?
```

Not:

```text
Does this request contain a token?
```

Having a token isn't enough.

It must be **verified**.

---

# Authentication Flow

```text
Receive Request
       │
       ▼
Extract JWT
       │
       ▼
Verify Signature
       │
       ▼
Check Expiration
       │
       ▼
Read Payload
       │
       ▼
Find User
       │
       ▼
Attach User
       │
       ▼
Continue Request
```

Every protected request follows this flow.

---

# Step 1 — Extract the Token

The middleware first looks for the token.

Common locations:

### Authorization Header

```http
Authorization: Bearer <access_token>
```

---

### HttpOnly Cookie

```text
accessToken
```

Depending on your authentication strategy, the middleware reads the token from the appropriate location.

---

# Step 2 — Is a Token Present?

```text
Token Found?

├── No
│
└── Yes
```

If no token exists:

```http
401 Unauthorized
```

There is nothing to verify.

---

# Step 3 — Verify the Signature

Next:

```text
JWT

↓

Verify Signature
```

The middleware checks whether:

- The token was signed by your server.
    
- The token has not been modified.
    

If verification fails:

```http
401 Unauthorized
```

The request stops here.

---

# Why Verify the Signature?

Suppose someone changes:

```json
{
    "role": "user"
}
```

to

```json
{
    "role": "admin"
}
```

Without signature verification:

```text
Modified Token

↓

Trusted

↓

Security Failure
```

With verification:

```text
Modified Token

↓

Invalid Signature

↓

Rejected
```

The signature protects the integrity of the token.

---

# Step 4 — Check Expiration

Even a valid token may be expired.

```text
JWT Verified

↓

Expired?

├── Yes → Reject
│
└── No → Continue
```

Expired tokens should never access protected resources.

---

# Step 5 — Read the Payload

Once verified:

```text
JWT Payload

↓

userId

email

role

issuedAt

expiresAt
```

The payload identifies **who** the request belongs to.

Remember:

The payload is trusted **only after** successful verification.

---

# Step 6 — Load the User

Many beginners stop after reading the payload.

Professional applications usually continue:

```text
JWT

↓

userId

↓

Database

↓

User
```

Why?

Because the database contains the latest user information.

---

# Why Load the User?

Imagine Rahul's account has been deleted.

Old JWT:

```text
userId = 123
```

Payload still exists.

Database:

```text
User Not Found
```

Result:

```http
401 Unauthorized
```

Without checking the database, deleted users might continue accessing the system until the token expires.

---

# Another Example

Admin disables Rahul's account.

JWT:

```text
Still Valid
```

Database:

```text
status = suspended
```

Authentication middleware can reject the request based on the latest account status.

---

# Build the User Context

After loading the user:

```text
Verified User

↓

Attach To Request

↓

Continue
```

The request now contains a **trusted user context**.

Conceptually:

```text
Request

↓

Authenticated User

↓

Controller
```

Controllers don't need to decode the JWT again.

---

# Trusted vs Untrusted Data

Before authentication:

```text
Incoming Request

↓

Unknown User
```

After authentication:

```text
Verified JWT

↓

Database User

↓

Trusted Context
```

Everything after the middleware uses trusted identity information.

---

# Should Controllers Verify JWT Again?

No.

Once middleware completes:

```text
Controller

↓

Authenticated User Already Available
```

Re-verifying the JWT wastes resources and duplicates logic.

---

# What Should the Middleware Attach?

The middleware should attach only what the application needs.

Common examples:

```text
User ID

Email

Role

Account Status
```

Avoid attaching unnecessary or sensitive information.

---

# Middleware Responsibilities

Authentication middleware should:

- Extract the token.
    
- Verify the JWT.
    
- Check expiration.
    
- Load the user.
    
- Build the trusted user context.
    
- Reject invalid requests.
    

Nothing else.

Authorization comes later.

---

# Common Beginner Mistakes

## ❌ Only Checking If a Token Exists

Bad:

```text
Token Present

↓

Allow
```

Always verify the signature and expiration.

---

## ❌ Trusting an Unverified Payload

Never read user information before verifying the JWT.

---

## ❌ Never Checking the Database

A valid JWT doesn't guarantee the account still exists or is active.

---

## ❌ Loading the User in Every Controller

Authentication middleware should do it once.

Controllers simply use the authenticated user.

---

## ❌ Mixing Authentication with Authorization

Authentication:

```text
Who is the user?
```

Authorization:

```text
Can the user perform this action?
```

Keep them separate.

---

# Best Practices

- Verify every JWT.
    
- Reject expired tokens.
    
- Load the latest user from the database.
    
- Build one trusted user context.
    
- Stop the request immediately on authentication failure.
    
- Keep authentication middleware focused only on identity verification.
    

---

# Interview Questions

### Q1. Why verify the JWT signature?

**Answer:**

To ensure the token was issued by the server and has not been modified by a client or attacker.

---

### Q2. Why load the user from the database after verifying the JWT?

**Answer:**

The database contains the latest account state. A user may have been deleted, suspended, or had their permissions changed after the JWT was issued.

---

### Q3. Why attach the user to the request?

**Answer:**

It creates a trusted user context that controllers and services can use without decoding or verifying the JWT again.

---

### Q4. Should authentication middleware perform authorization?

**Answer:**

No. Authentication establishes identity. Authorization decides what the authenticated user is allowed to do.

# 💡 Backend Engineering Tip

A common misconception is:

```text
JWT

↓

User Authenticated
```

A more professional way to think about it is:

```text
JWT

↓

Verify Signature

↓

Check Expiration

↓

Load Current User

↓

Build Trusted User Context

↓

Continue Request
```

The JWT proves **who the client claims to be**, while the database confirms **who the user is right now**. Combining both gives your application a much stronger and more secure authentication model.
