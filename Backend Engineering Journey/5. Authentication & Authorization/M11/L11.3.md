# Module 11 — Authentication Middleware

# Lesson 11.3 — Protecting Routes

> **Goal:** Learn how professional backend applications protect API endpoints using authentication middleware and build a clean request pipeline.

Authentication middleware is only useful if it's applied **correctly**.

The question is no longer:

> **How do we verify the user?**

Instead, it becomes:

> **Which routes should require authentication, and where should authentication happen?**

---

# Learning Objectives

By the end of this lesson, you will be able to:

# The Problem

Your Blog App has these APIs:

```text
POST /register

POST /login

GET /posts

POST /posts

PUT /posts/:id

DELETE /posts/:id

GET /profile
```

Question:

Should every route require authentication?

No.

---

# Public Routes

Public routes can be accessed without logging in.

Examples:

```text
POST /register

POST /login

POST /forgot-password

GET /verify-email

GET /posts

GET /post/:slug
```

Anyone can use these endpoints.

---

# Protected Routes

Protected routes require a verified user.

Examples:

```text
POST /posts

PUT /posts/:id

DELETE /posts/:id

GET /profile

POST /logout
```

Authentication is mandatory.

---

# Route Architecture

Professional applications organize routes like this:

```text
Public Route

↓

Controller
```

and

```text
Protected Route

↓

Authentication Middleware

↓

Controller
```

Controllers shouldn't know whether authentication happened.

They simply assume:

```text
Authenticated User Exists
```

# Route-Level Protection

Authentication belongs to the route.

Conceptually:

```text
POST /posts

↓

Requires Authentication
```

While:

```text
POST /login

↓

Public
```

The route decides whether authentication middleware should execute.

---

# Middleware Pipeline

Professional Express applications process requests through a pipeline.

```text
Request
    │
    ▼
Authentication
    │
    ▼
Authorization
    │
    ▼
Validation
    │
    ▼
Controller
    │
    ▼
Service
    │
    ▼
Repository
    │
    ▼
Database
```

Each stage has one responsibility.

---

# Why Middleware Order Matters

Imagine this order:

```text
Request

↓

Controller

↓

Authentication
```

Too late.

The controller has already started executing.

Correct order:

```text
Request

↓

Authentication

↓

Controller
```

Always authenticate **before** business logic.

# Authentication Failure

If authentication fails:

```text
Authentication Middleware

↓

401 Unauthorized

↓

Stop Request
```

Nothing else runs.

Not:

- Controller
    
- Service
    
- Repository
    

The request ends immediately.

---

# Authentication Success

If authentication succeeds:

```text
JWT Verified

↓

User Loaded

↓

Request.user Created

↓

Continue
```

Everything after this can trust the user identity.

---

# Controller Responsibilities

Controllers should only:

```text
Receive Request

↓

Call Service

↓

Return Response
```

Controllers should **not**:

- Verify JWT
    
- Decode tokens
    
- Check authentication
    

That already happened.

---

# Service Responsibilities

Services assume:

```text
Authenticated User

↓

Business Rules
```

Example:

```text
Create Post

↓

Use request.user.id

↓

Save Post
```

The service doesn't authenticate the user.

It simply uses the authenticated identity.

# Authentication vs Validation

Consider:

```http
POST /posts
```

Question:

Should validation happen before authentication?

Professional APIs usually authenticate first.

Reason:

If the request isn't authenticated,

there is no reason to spend resources validating it.

Typical order:

```text
Authentication

↓

Authorization

↓

Validation

↓

Business Logic
```

Some applications may validate basic request syntax earlier (for example, parsing JSON), but authentication generally happens before business-level validation.

# Preparing for Authorization

Authentication tells us:

```text
Rahul
```

```text
Can Rahul

↓

Delete This Post?
```

That's authorization.

Authentication and authorization work together but remain separate.

# Common Beginner Mistakes

## ❌ Protecting Every Route

Bad:

```text
/register

↓

Authentication Required
```

Users couldn't even create an account.

---

## ❌ Forgetting to Protect Sensitive Routes

Bad:

```text
DELETE /posts/:id

↓

Public
```

Anyone could delete posts.

---

## ❌ Authentication Inside Controllers

Controllers should never verify JWTs.

Use middleware.

---

## ❌ Mixing Authentication and Authorization

Authentication:

```text
Who is the user?
```

Authorization:

```text
Can the user perform this action?
```

Keep them independent.

---

## ❌ Wrong Middleware Order

Never execute business logic before authentication.

---

# Best Practices

- Clearly separate public and protected routes.
    
- Apply authentication at the routing layer.
    
- Authenticate before controllers.
    
- Stop the request immediately if authentication fails.
    
- Keep controllers focused on request handling.
    
- Prepare authenticated user context for authorization.
    

---

# Interview Questions

### Q1. Where should authentication middleware be applied?

**Answer:**

At the routing layer, before the request reaches the controller.

---

### Q2. Why shouldn't controllers verify JWTs?

**Answer:**

Because authentication is a cross-cutting concern. Middleware centralizes it, removes duplicate code, and keeps controllers focused on handling requests.

---

### Q3. What happens when authentication fails?

**Answer:**

The middleware immediately returns a **401 Unauthorized** response, and the request never reaches the controller or service layer.

---

### Q4. Why separate authentication and authorization?

**Answer:**

Authentication establishes the user's identity. Authorization determines whether that authenticated user has permission to perform a specific action.

# 💡 Backend Engineering Tip

A useful mental model for request processing is:

```text
Can I trust you?
        │
        ▼
Authentication
        │
        ▼
What are you allowed to do?
        │
        ▼
Authorization
        │
        ▼
Is your request valid?
        │
        ▼
Validation
        │
        ▼
Execute Business Logic
```

Each question is answered by a different layer. This separation keeps your backend modular, secure, and easy to maintain as it grows.
