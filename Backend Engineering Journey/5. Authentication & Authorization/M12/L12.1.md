# Module 12 — Authorization Fundamentals

# Lesson 12.1 — Authorization Architecture

> **Goal:** Learn how professional backend applications decide whether an authenticated user is allowed to perform a specific action.

Authentication answers:

> **Who are you?**

Authorization answers:

> **What are you allowed to do?**

These are two completely different problems.

---

By the end of this lesson, you will be able to:

- Understand authorization architecture.

# Authentication is NOT Enough

Suppose Rahul logs in successfully.

```text
Rahul

↓

Authenticated
```

Now Rahul sends:

```http
DELETE /posts/25
```

Can the backend delete the post?

Authentication cannot answer that.

It only says:

```text
This is Rahul.
```

The next question is:

```text
Can Rahul delete Post 25?
```

That's authorization.

---

# Authentication vs Authorization

Authentication:

```text
Who are you?
```

Authorization:

```text
What are you allowed to do?
```

Example:

```text
JWT Verified

↓

Rahul Identified

↓

Authorization

↓

Allow?
```

Notice that authorization **always depends on successful authentication**.

---

# Authorization Workflow

A protected request follows this flow:

```text
Request

↓

Authentication

↓

Authenticated User

↓

Authorization

↓

Business Logic

↓

Database
```

Authentication happens first.

Authorization happens second.

---

# Blog App Example

Rahul owns:

```text
Post #15
```

Aman owns:

```text
Post #20
```

Rahul sends:

```http
DELETE /posts/20
```

Authentication:

```text
Rahul
```

Authorization:

```text
Does Rahul own Post #20?

↓

No

↓

403 Forbidden
```

Identity alone is not enough.

---

# Authorization is a Business Rule

Professional engineers treat authorization as part of the business logic.

Example business rule:

```text
Only the author
can edit a post.
```

Another:

```text
Only admins
can delete users.
```

These rules come from business requirements, not from JWT or Express.

---

# Where Does Authorization Belong?

Many beginners place authorization inside controllers.

Bad architecture:

```text
Controller

↓

Check Role

↓

Check Ownership

↓

Business Logic
```

Controllers become large and difficult to maintain.

---

A cleaner architecture is:

```text
Route

↓

Authentication Middleware

↓

Authorization

↓

Controller

↓

Service

↓

Repository
```

Or, when the decision depends on business data:

```text
Controller

↓

Service

↓

Authorization Rule

↓

Repository
```

The location depends on **what information is needed**.

---

# Middleware vs Service Authorization

Professional applications use **both**.

---

## Middleware

Good for simple rules.

Example:

```text
Only Logged-In Users
```

or

```text
Only Admins
```

No database lookup required.

---

## Service Layer

Good for business rules.

Example:

```text
Can Rahul edit this post?
```

The service needs to load the post first.

Example:

```text
Load Post

↓

Compare Owner

↓

Allow?
```

This belongs in the service layer.

---

# Why Some Authorization Cannot Be Middleware

Imagine:

```http
PUT /posts/101
```

Middleware only knows:

```text
Rahul
```

It doesn't know:

```text
Who owns Post 101?
```

The service loads:

```text
Post

↓

ownerId

↓

Compare With Rahul
```

Only then can the decision be made.

---

# Authorization Decision

Every authorization rule ends with:

```text
Allow
```

or

```text
Reject
```

Example:

```text
Authenticated

↓

Has Permission?

↓

Yes

↓

Continue
```

Otherwise:

```http
403 Forbidden
```

---

# Authorization Pipeline

```text
Request

↓

Authentication

↓

Load User

↓

Authorization

↓

Controller

↓

Service

↓

Repository

↓

Database
```

The request reaches business logic only if authorization succeeds.

---

# Fail Fast

If authorization fails:

```text
Authorization

↓

403 Forbidden

↓

Stop Request
```

Don't continue to:

- Controller
    
- Service
    
- Repository
    

Reject the request immediately.

Think of authorization as policies.

Examples:

```text
Only Owners

Only Verified Users
```

Every protected feature should have a clear policy.

# Authorization is NOT Data Validation

Validation asks:

```text
Is this request valid?
```

Authorization asks:

```text
Can this user perform it?
```

Example:

```http
POST /posts
```

Valid request:

```json
{
  "title": "JWT Guide"
}
```

Validation:

```text
Title Exists

↓

Valid
```

Authorization:

```text
Authenticated?

↓

Allowed To Create?

↓

Yes
```

These are separate checks.

---

# Authorization is NOT Repository Logic

Repositories should never decide:

```text
Can User Delete?
```

Repositories only do:

```text
Find

Create

Update

Delete
```

Business decisions belong above the repository.

# Common Beginner Mistakes

## ❌ Thinking Authentication is Enough

Bad:

```text
JWT Valid

↓

Allow Everything
```

Authentication does not grant unlimited access.

---

## ❌ Putting Every Authorization Rule in Middleware

Middleware works well for general rules.

Ownership checks often require business data and belong in the service layer.

---

## ❌ Returning 401 Instead of 403

Remember:

```text
401

↓

Not Authenticated
```

```text
403

↓

Authenticated

↓

Not Allowed
```

This distinction is important.

---

## ❌ Mixing Authorization with Repository Code

Repositories should not know about:

- Roles
    
- Permissions
    
- Ownership
    

Keep business rules in the service layer.

---

## ❌ Hardcoding Rules Everywhere

Bad:

```text
Controller A

↓

Role Check

──────────

Controller B

↓

Role Check

──────────

Controller C

↓

Role Check
```

Centralize authorization logic.

---

# Best Practices

- Authenticate before authorizing.
    
- Treat authorization as a business rule.
    
- Use middleware for simple access rules.
    
- Use the service layer for ownership and business-specific rules.
    
- Return **403 Forbidden** when authorization fails.
    
- Keep repositories free of authorization logic.

# Interview Questions

### Q1. What's the difference between authentication and authorization?

**Answer:**

Authentication identifies the user, while authorization determines what that authenticated user is allowed to do.

---

### Q2. Why isn't authentication enough?

**Answer:**

Knowing who the user is doesn't determine whether they have permission to perform a specific action. Authorization applies the application's business rules.

---

### Q3. Should every authorization rule be implemented in middleware?

**Answer:**

No. Simple rules like "user must be logged in" or "user must be an admin" fit well in middleware. Resource-specific rules, such as ownership checks, usually belong in the service layer because they require business data.

---

### Q4. When should the API return **403 Forbidden**?

**Answer:**

When the user has been successfully authenticated but does not have permission to perform the requested action.

# 💡 Backend Engineering Tip

A useful mental model is:

```text
Authentication

↓

Identity

↓

"I know this is Rahul."

────────────────────

Authorization

↓

Decision

↓

"Can Rahul perform this action?"
```

Keep these responsibilities separate.

When authentication answers **who**, authorization can focus entirely on **what**, making your backend easier to maintain, test, and extend as new business rules are introduced.
