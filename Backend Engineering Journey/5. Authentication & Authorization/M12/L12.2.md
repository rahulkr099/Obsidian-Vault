# Module 12 — Authorization Fundamentals

# Lesson 12.2 — Roles & Permissions

> **Goal:** Learn how professional backend applications use roles and permissions to control access to different features.

Not every authenticated user should have the same capabilities.

For example:

- Readers can read posts.
    
- Authors can write posts.
    
- Editors can moderate content.
    
- Admins can manage the platform.
    

Authorization answers these questions using **roles** and **permissions**.

---

# Learning Objectives

By the end of this lesson, you will be able to:

- Understand roles and permissions.
    
- Learn the difference between RBAC and permission-based authorization.
    
- Design a permission model.
    
- Understand role hierarchy.
    
- Decide when to use roles and when to use permissions.

# The Problem

Imagine your Blog App has three users.

```text
Rahul

↓

Author
```

```text
Aman

↓

Reader
```

```text
Admin

↓

Administrator
```

Now all three request:

```http
POST /posts
```

Should everyone be allowed?

No.

The backend must make a decision.

---

# What is a Role?

A **role** is a collection of responsibilities assigned to a user.

Examples:

```text
Guest

Reader

Author

Editor

Admin
```

Instead of checking dozens of permissions directly, the application first identifies the user's role.

---

# Role-Based Access Control (RBAC)

RBAC means:

```text
User

↓

Role

↓

Permissions
```

The application grants permissions based on the assigned role.

---

# Role Hierarchy

Many applications have a hierarchy.

```text
Guest

↓

Reader

↓

Author

↓

Editor

↓

Admin
```

Higher roles often inherit lower-role capabilities.

Example:

```text
Admin

↓

Can Read Posts

Can Create Posts

Can Delete Posts
```

The Admin doesn't need every permission defined manually if inheritance is part of your design.

---

# What is a Permission?

A **permission** represents a single action.

Examples:

```text
post:create

post:update

post:delete

comment:create

comment:delete

user:update
```

Permissions describe **what can be done**, independent of who is doing it.

---

# Permission-Based Authorization

Instead of asking:

```text
Role = Admin?
```

Ask:

```text
Has Permission?

↓

post:delete
```

This approach is more flexible.

---

# Roles vs Permissions

## Role

```text
Author
```

Represents:

A job or responsibility.

---

## Permission

```text
post:create
```

Represents:

A specific capability.

---

# RBAC Architecture

```text
Request

↓

Authentication

↓

User

↓

Role

↓

Permission Check

↓

Allow / Reject
```

The permission check happens after authentication.

---

# Permission-Based Architecture

```text
Request

↓

Authentication

↓

User

↓

Permission List

↓

Permission Check

↓

Allow / Reject
```

Instead of relying only on a role, the system evaluates individual permissions.

---

# Which Should You Use?

## Small Applications

Example:

- Blog
    
- Portfolio CMS
    
- Todo App
    

RBAC is usually sufficient.

Example:

```text
Reader

Author

Admin
```

Simple and easy to manage.

---

## Large Applications

Example:

- Banking
    
- ERP
    
- CRM
    
- Enterprise SaaS
    

Permissions provide more flexibility.

Example:

```text
invoice:create

invoice:approve

invoice:refund

user:suspend

report:view
```

Different users can have different permission combinations.

---

# Combining Roles and Permissions

Many production systems combine both.

```text
User

↓

Role

↓

Default Permissions

↓

Additional Permissions
```

Example:

```text
Author

↓

Can Create Posts

↓

Extra Permission

↓

feature:beta-access
```

This keeps the system flexible.

---

# Designing Permissions

Good permission names are:

```text
resource:action
```

Examples:

```text
post:create

post:update

post:delete

comment:update

comment:delete

user:manage
```

This naming convention scales well.

---

# Avoid Role Explosion

A common problem:

```text
Author

Senior Author

Premium Author

VIP Author

Content Author

Verified Author
```

Too many roles become difficult to maintain.

Instead:

```text
Author

+

Extra Permissions
```

Keep roles broad and permissions specific.

---

# Where Should Permission Checks Happen?

Simple role checks may occur in middleware.

Example:

```text
Admin Only
```

However, business-specific permission decisions often belong in the service layer.

Example:

```text
Can approve invoice?
```

The service may need business data before making the decision.

# Common Beginner Mistakes

## ❌ Hardcoding Admin Checks Everywhere

Bad:

```text
if (role == "admin")
```

Repeated throughout the application.

Centralize authorization logic instead.

---

## ❌ Using Roles for Every Rule

Not every authorization rule belongs to a role.

Some require ownership or business conditions.

---

## ❌ Creating Too Many Roles

Avoid role explosion.

Use permissions for fine-grained control.

---

## ❌ Mixing Authentication and Permissions

Authentication identifies the user.

Permissions determine capabilities.

These are separate concerns.

---

## ❌ Poor Permission Names

Bad:

```text
permission1
```

Good:

```text
post:update
```

Use meaningful, consistent naming.

---

# Best Practices

- Use roles to represent responsibilities.
    
- Use permissions to represent capabilities.
    
- Keep permission names consistent.
    
- Avoid creating unnecessary roles.
    
- Centralize permission checks.
    
- Combine roles and permissions when flexibility is needed.

# Interview Questions

### Q1. What is RBAC?

**Answer:**

Role-Based Access Control (RBAC) is an authorization model where permissions are assigned to roles, and users receive permissions through their assigned roles.

---

### Q2. What's the difference between a role and a permission?

**Answer:**

A role represents a user's responsibility (such as Author or Admin), while a permission represents a specific capability (such as `post:create` or `post:delete`).

---

### Q3. When should you use permission-based authorization instead of only roles?

**Answer:**

Permission-based authorization is better for larger or more complex systems where users need fine-grained, customizable access rather than a few predefined roles.

---

### Q4. What is role explosion?

**Answer:**

Role explosion occurs when an application creates too many narrowly defined roles, making the authorization system difficult to understand and maintain.

# 💡 Backend Engineering Tip

A useful way to think about authorization is:

```text
Authentication

↓

Who is the user?

────────────────

Role

↓

What is their responsibility?

────────────────

Permission

↓

What actions can they perform?

────────────────

Ownership

↓

Can they perform
this action on
this specific resource?
```

This layered approach is how many production systems implement authorization: identity first, then capabilities, and finally resource-specific checks.
