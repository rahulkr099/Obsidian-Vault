# Module 12 — Authorization Fundamentals

# Lesson 12.3 — Ownership Authorization

> **Goal:** Learn how professional backend applications protect user-owned resources by verifying ownership before allowing operations like update or delete.

One of the biggest misconceptions beginners have is:

> **"If the user is authenticated, they can update the resource."**

This is wrong.

Authentication proves **who the user is**.

Ownership authorization determines **whether that user owns the resource they're trying to access.**

# The Problem

Suppose your Blog App has two users.

```text
Rahul

↓

Author
```

```text
Aman

↓

Author
```

Rahul owns:

```text
Post #10
```

Aman owns:

```text
Post #20
```

Rahul sends:

```http
DELETE /posts/20
```

Should the request succeed?

No.

# Authentication Isn't Enough

Authentication says:

```text
Rahul

↓

Authenticated
```

Authorization asks:

```text
Does Rahul own
Post #20?
```

Result:

```text
No

↓

403 Forbidden
```

# Ownership Rule

A common business rule:

```text
Only the owner

can modify

their own resource.
```

This applies to many applications.

# Ownership Flow

```text
Authenticated User

↓

Load Resource

↓

Compare Owner

↓

Allow?

├── No → 403
│
└── Yes
      ↓
Continue
```

Notice:

You cannot check ownership without loading the resource.

# Why Middleware Isn't Enough

Suppose:

```http
PUT /posts/101
```

Middleware knows:

```text
Rahul
```

But it doesn't know:

```text
Owner of Post 101
```

The application must first load the post.

---

# Correct Flow

```text
Authentication

↓

Service

↓

Repository

↓

Load Post

↓

Compare ownerId

```

# Where Does Ownership Logic Belong?

Many beginners write:

```text
Controller

↓

Compare ownerId
```

Bad.

Controllers become cluttered.

---

Professional architecture:

```text
Controller

↓

Post Service

↓

Ownership Check

↓

Repository
```

The service owns the business rule.

---

# Why the Service Layer?

Because ownership is a **business decision**.

Example:

```text
Only Author

Can Edit Own Post
```

This is not a database rule.

It is not a routing rule.

It is business logic.

# Ownership vs Permission

Permission:

```text
Can Edit Posts
```

Ownership:

```text
Can Edit

This

Specific Post
```

Permissions answer:

> **What actions are possible?**

Ownership answers:

> **Which resource can those actions be applied to?**

---

# Repository Responsibility

Repositories should:

```text
Find Post

Update Post

Delete Post
```

Repositories should **not** decide:

```text
Is Rahul Allowed?
```

Business rules belong above the repository.

---

# Common Beginner Mistakes

## ❌ Trusting the Resource ID

Bad:

```text
PUT /posts/20

↓

Update
```

Always verify ownership first.

---

## ❌ Ownership Checks in Controllers

Controllers should coordinate requests.

Ownership belongs in the service layer.

---

## ❌ Returning 404 Instead of 403 Without a Strategy

When a user accesses someone else's resource, you need a consistent policy.

Common approaches are:

- **403 Forbidden** – the resource exists, but access is denied.
    
- **404 Not Found** – intentionally hide the existence of the resource to reduce information disclosure.
    

Choose one approach and apply it consistently across your API.

---

## ❌ Skipping Authorization for Updates

Authentication alone is not enough.

Always verify ownership or permissions before modifying resources.

---

## ❌ Mixing Repository and Authorization Logic

Repositories shouldn't know:

- Roles
    
- Ownership
    
- Permissions
    

Keep them focused on data access.

---

# Best Practices

- Authenticate before checking ownership.
    
- Load the resource before making authorization decisions.
    
- Keep ownership checks in the service layer.
    
- Combine roles and ownership when necessary.
    
- Define a consistent strategy for forbidden vs hidden resources.
    
- Protect every update and delete operation.

# Interview Questions

### Q1. What is ownership authorization?

**Answer:**

Ownership authorization verifies that the authenticated user owns the specific resource they are trying to access or modify.

---

### Q2. Why can't middleware always perform ownership checks?

**Answer:**

Because ownership often depends on resource data stored in the database. The application usually needs to load the resource before it can compare the owner with the authenticated user.

---

### Q3. Why should ownership logic be implemented in the service layer?

**Answer:**

Ownership is a business rule. The service layer contains business logic and has access to both the authenticated user and the resource data needed for the decision.

---

### Q4. Can an admin bypass ownership checks?

**Answer:**

Yes, if the application's business rules allow it. A common pattern is to let admins manage any resource while regular users can only manage resources they own.

# 💡 Backend Engineering Tip

Professional authorization often follows this decision sequence:

```text
Is the user authenticated?

↓

Yes

↓

Does the user's role
allow this action?

↓

Yes

↓

Does the user own
this resource?

↓

Yes

↓

Execute Business Logic
```

This layered approach keeps your authorization predictable, scalable, and easy to extend. As your application grows—from a simple blog to a multi-tenant SaaS—you'll add more authorization rules, but this fundamental decision-making process remains the same.
