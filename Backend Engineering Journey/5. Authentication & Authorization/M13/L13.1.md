# What is RBAC?

RBAC stands for:

```text
Role-Based Access Control
```

Instead of asking:

```text
Can Rahul create a post?
```

The backend asks:

```text
What is Rahul's role?
```

Then:

```text
Does this role

allow this action?
```

---

Suppose your Blog App has:

```text

```

```text
Author?

↓

```

```text
Admin?

↓

Allow
```

# RBAC Workflow

```text
Client Request

↓

Authentication

↓

Authenticated User

↓

Read User Role

↓

Role Allowed?

├── No → 403
│
└── Yes
      ↓
Controller
```

Notice:

RBAC starts **after authentication**.

Authentication:

```text

↓

```

RBAC:

```text
Rahul

↓

Role = Author

↓

```

These are two different responsibilities.

# Role Storage

Typically:

```text

↓

Role
```

Example:

```text
User

↓

```

The role becomes part of the authenticated user context after login.

# Route-Level RBAC

Some routes require specific roles.

Example:

```http

```

```text

```

```text

```

RBAC can make this decision **before** the controller executes.

# What RBAC Answers

RBAC answers:

```text
Does this role

allow this action?
```

Example:

```text
Admin

↓

Delete User

↓

Yes
```

---

RBAC does **not** answer:

```text
Does Rahul

own this post?
```

That's ownership authorization.

---

# RBAC vs Ownership

Suppose Rahul is:

```text
Author
```

Authors can edit posts.

But Rahul sends:

```http
PUT /posts/20
```

RBAC says:

```text
Authors

Can Edit Posts

↓

Yes
```

Ownership asks:

```text
Does Rahul

Own Post #20?

↓

No
```

Final result:

```text
403 Forbidden
```

RBAC grants the capability.

Ownership applies it to a specific resource.

---

# RBAC vs Permissions

RBAC:

```text
Role

↓

Author
```

Permissions:

```text
post:create

post:update
```

Many applications begin with RBAC.

As they grow:

```text
RBAC

↓

Permissions
```

We'll cover permission-based authorization later.

# Where Does RBAC Belong?

Simple role checks belong in middleware.

Example:

```text
Admin Only
```

Flow:

```text
Authentication

↓

RBAC Middleware

↓

Controller
```

---

Business rules remain in the service layer.

Example:

```text
Admin

↓

Delete Any Post
```

or

```text
Author

↓

Delete Own Post
```

The service may still need ownership checks.

# Common Beginner Mistakes

## ❌ Using Only RBAC

Bad assumption:

```text
Author

↓

Can Edit

Every Post
```

Ownership checks are still needed.

---

## ❌ Hardcoding Roles Everywhere

Bad:

```text
if role == "admin"

if role == "author"

if role == "reader"
```

Centralize role checks in middleware.

---

## ❌ Mixing RBAC with Authentication

Authentication identifies the user.

RBAC evaluates the user's role.

Keep these responsibilities separate.

---

## ❌ Repository Knows Roles

Repositories should never contain:

- Role checks
    
- Permission checks
    
- Ownership checks
    

Repositories only access data.

---

## ❌ Skipping Ownership

RBAC alone doesn't protect individual resources.

Always combine RBAC with ownership when required.

---

# Best Practices

- Authenticate first.
    
- Apply RBAC before controllers.
    
- Keep role checks centralized.
    
- Use ownership checks for user-owned resources.
    
- Keep repositories free of authorization logic.
    
- Design roles around responsibilities, not individual users.

# Interview Questions

### Q1. What is RBAC?

**Answer:**

Role-Based Access Control (RBAC) is an authorization model where access decisions are based on the user's assigned role.

---

### Q2. Does RBAC replace ownership authorization?

**Answer:**

No. RBAC determines whether a role is allowed to perform an action, while ownership authorization determines whether the user can perform that action on a specific resource.

---

### Q3. Where should RBAC checks be implemented?

**Answer:**

Simple role checks are commonly implemented in middleware before the request reaches the controller.

---

### Q4. Why shouldn't repositories perform RBAC?

**Answer:**

Repositories are responsible for data access. Authorization is a business concern and belongs in middleware or the service layer.

# 💡 Backend Engineering Tip

Think of RBAC as a **coarse-grained authorization layer**:

```text
Authentication

↓

Who are you?

↓

RBAC

↓

Can your role perform this type of action?

↓

Ownership

↓

Can you perform it on this specific resource?
```

This layered approach is used in many production systems because it separates **general capabilities** (roles) from **resource-specific decisions** (ownership), making the authorization system easier to maintain and extend.
