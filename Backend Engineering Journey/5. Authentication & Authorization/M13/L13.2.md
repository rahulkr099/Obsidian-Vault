# The Problem

Imagine your Blog App has these APIs:

```text
POST /posts

DELETE /posts/:id

DELETE /users/:id

GET /admin/dashboard

PUT /profile
```

Without middleware, every controller might start with:

```text
Is User Admin?

↓

Yes?

↓

Continue
```

After a few months:

```text
PostController

↓

Role Check

────────────

UserController

↓

Role Check

────────────

CommentController

↓

Role Check

────────────

AdminController

↓

Role Check
```

The same authorization logic is repeated everywhere.

---

# The Solution

Move role checks into reusable middleware.

Architecture:

```text
Request

↓

Authentication

↓

Role Middleware

↓

Controller

↓

Service
```

Now every controller assumes:

```text
Authorization

Already Completed
```

---

# Middleware Responsibilities

Role middleware should answer only one question:

```text
Does this user's role

allow this route?
```

It should **not**:

- Verify JWT
    
- Load the user
    
- Validate request body
    
- Check resource ownership
    
- Execute business logic
    

Each responsibility belongs to a different layer.

---

# Request Pipeline

A protected request becomes:

```text
Client

↓

↓

Role Middleware

↓

Validation

↓

Controller

↓

Service
```

Notice the order.

Authentication always comes first.

# Role Middleware vs Ownership

Suppose:

Rahul:

```text
Role = Author
```

Requests:

```http
DELETE /posts/20
```

Role middleware:

```text
Author

↓

Can Delete Posts

↓

Allowed
```

But ownership still matters.

Service:

```text
Load Post

↓

Owner = Aman

↓

Reject
```

Role middleware **does not replace** ownership checks.

# Common Beginner Mistakes

## ❌ Verifying JWT Again

Role middleware should never verify JWTs.

Authentication already did that.

---

## ❌ Mixing Roles with Business Logic

Bad:

```text
Controller

↓

Role Check

↓

Update Database
```

Separate authorization from business logic.

---

## ❌ Ownership Checks in Role Middleware

Role middleware doesn't know resource ownership.

Leave ownership to the service layer.

---

## ❌ Duplicating Role Checks

Never repeat:

```text
if role == Admin
```

in multiple controllers.

Centralize the logic.

---

## ❌ Returning 401 Instead of 403

Remember:

```text
401

↓

Not Authenticated
```

```text
403

↓

Authenticated

↓

Not Authorized
```

---

# Best Practices

- Authenticate before checking roles.
    
- Build reusable role middleware.
    
- Keep middleware focused on authorization.
    
- Keep controllers free of role checks.
    
- Use ownership checks separately.
    
- Return **403 Forbidden** when role checks fail.

# Interview Questions

### Q1. Why use role middleware instead of checking roles in every controller?

**Answer:**

Role middleware centralizes authorization logic, eliminates duplicate code, improves maintainability, and keeps controllers focused on handling requests.

---

### Q2. Should role middleware verify JWTs?

**Answer:**

No. JWT verification is the responsibility of authentication middleware. Role middleware assumes the user has already been authenticated.

---

### Q3. Can role middleware replace ownership authorization?

**Answer:**

No. Role middleware determines whether the user's role allows the action. Ownership authorization determines whether the user can perform that action on a specific resource.

---

### Q4. Why should role middleware return **403 Forbidden**?

**Answer:**

Because the user has already been authenticated. The problem is not identity; it's insufficient permission to access the requested resource.

# 💡 Backend Engineering Tip

Think of role middleware as a **security checkpoint**:

```text
Request

↓

Authentication

↓

"Who are you?"

↓

RBAC

↓

"Does your role allow this action?"

↓

Ownership

↓

"Can you perform it
on this resource?"

↓

Business Logic
```

Each layer answers a different question. By keeping those questions separate, your authorization system remains clean, scalable, and much easier to maintain as your application grows.
