# RBAC Alone Isn't Enough

Suppose Rahul is:

```text
Role

↓

Author
```

Authors can edit posts.

Rahul sends:

```http
PUT /posts/25
```

RBAC says:

```text
Role = Author

↓

Allowed
```

But now the application asks:

```text
Does Rahul own

Post #25?
```

If the owner is Aman:

```text
No

↓

403 Forbidden
```

RBAC gave Rahul the **ability** to edit posts.

Ownership determines **which** posts he can edit.

# Admin Exception

Admins often bypass ownership.

Example:

```text
Role = Admin

↓

Skip Ownership

↓

Delete Post
```

Business rule:

```text
Admin

↓

Manage Entire System
```

Notice:

This is a **business decision**, not a technical requirement.

# Role Changes

Suppose Rahul is promoted.

Yesterday:

```text
Reader
```

Today:

```text
Author
```

The next request should use:

```text
Role = Author
```

Always use the **current role**, not the role the user had months ago.

---

# Suspended Users

Suppose Rahul violates community guidelines.

Admin changes:

```text
status

↓

Suspended
```

Rahul still has:

```text
Role = Author
```

Should RBAC allow access?

No.

Authentication (or a related account-status check) should reject suspended accounts before RBAC is evaluated.

Example flow:

```text
Authentication

↓

User Loaded

↓

Status = Suspended

↓

403 Forbidden
```

The account is authenticated, but business rules prevent further access.

---

# Soft Delete

Suppose a user account is deactivated.

Database:

```text
deletedAt

↓

Not Null
```

Old JWT:

```text
Still Valid
```

Authentication should detect:

```text
User

↓

Inactive

↓

Reject
```

Never rely only on JWT payloads.

Always check the current user record.

# Temporary Roles

Some applications assign roles temporarily.

Example:

```text

↓

```

After expiration:

```text

↓

Reader
```

Authorization should always reflect the latest role assignment.

# Solution

Instead of creating dozens of roles:

```text

↓

```

Example:


Roles remain simple.

Permissions provide flexibility.

# Common Beginner Mistakes

## ❌ Believing RBAC Solves Every Authorization Problem

RBAC controls **general capabilities**.

Ownership and business rules still matter.

---

## ❌ Forgetting Current Account Status

Always use the latest account state from the database.

A valid JWT doesn't guarantee an active account.

---

## ❌ Creating Too Many Roles

Avoid role explosion.

Use permissions for fine-grained access.

---

## ❌ Trusting Old JWT Data

Always verify the current user record.

Roles and account status may have changed.

---

## ❌ Mixing Every Authorization Rule Together

Keep separate layers for:

- Authentication
    
- Account status
    
- RBAC
    
- Ownership
    
- Business rules

# Best Practices

- Combine RBAC with ownership authorization.
    
- Always use the latest user information.
    
- Check account status before processing requests.
    
- Keep roles broad and stable.
    
- Introduce permissions when RBAC alone becomes insufficient.
    
- Audit important authorization changes.

# Interview Questions

### Q1. Why isn't RBAC enough for production applications?

**Answer:**

RBAC determines what actions a role may perform, but it doesn't handle resource ownership or many business-specific authorization rules. Production systems often combine RBAC with ownership checks and permissions.

---

### Q2. What is role explosion?

**Answer:**

Role explosion occurs when too many narrowly defined roles are created, making the authorization system difficult to understand and maintain.

---

### Q3. Why should the backend load the current user instead of trusting the JWT?

**Answer:**

The user's role or account status may have changed after the JWT was issued. Loading the current user ensures authorization decisions use the latest information.

---

### Q4. Should administrators always bypass ownership checks?

**Answer:**

Not necessarily. Whether administrators can bypass ownership checks is a business decision that depends on the application's requirements.

# 💡 Backend Engineering Tip

Think of production authorization as a sequence of security gates:

```text
Is the user authenticated?

↓

Is the account active?

↓

Does the role allow this action?

↓

Does the user own this resource?

↓

Do business rules allow it?

↓

Execute Business Logic
```

Each gate filters out requests that shouldn't proceed. This layered approach is what makes modern backend authorization secure, maintainable, and scalable.
