# The Problem with Only Roles

Imagine your Blog App grows into a large CMS.

Roles:

```text
Reader

Author

Editor

Admin
```

Now management asks:

> "Editors can publish posts, but only Senior Editors can feature posts."

Then:

> "Guest Authors can write drafts but cannot publish."

Then:

> "Content Managers can publish, feature, and archive posts."

Soon your roles become:

```text
Reader

Author

Guest Author

Verified Author

Senior Author

Editor

Senior Editor

Content Manager

Admin
```

This is called:

```text
Role Explosion
```

The number of roles keeps increasing.

---

# The Better Approach

Instead of creating new roles:

Assign capabilities.

Example:

```text
post:create

post:update

post:publish

post:feature

post:archive
```

Now the application asks:

```text
Does Rahul have

post:publish?
```

instead of:

```text
Is Rahul

Senior Editor?
```

---

# What is a Permission?

A permission represents **one specific action**.

Examples:

```text
post:create

post:update

post:delete

comment:create

comment:delete

user:suspend
```

Each permission answers:

> **Can this user perform this action?**

---

# Permission-Based Authorization (PBAC)

Architecture:

```text
User

↓

Permissions

↓

Allowed?
```

Instead of:

```text
User

↓

Role

↓

Allowed?
```

The authorization decision is based on capabilities rather than job titles.

---

# Blog App Example

Rahul has:

```text
post:create

post:update

comment:create
```

Rahul requests:

```http
POST /posts
```

Backend:

```text
Has post:create?

↓

Yes

↓

Continue
```

---

Now Rahul requests:

```http
DELETE /posts/15
```

Backend:

```text
Has post:delete?

↓

No

↓

403 Forbidden
```

No role comparison is needed.

# Permission Naming

Professional applications usually follow:

```text
resource:action
```

Examples:

```text
post:create

post:update

post:delete

comment:create

user:update

user:delete
```

Benefits:

- Consistent
    
- Easy to search
    
- Easy to extend

# Permission Flow

```text

↓

↓

Authenticated User

↓

Load Permissions

↓

Permission Exists?

├── No → 403
│
└── Yes
      ↓

```

This replaces role comparison with permission comparison.

# Where Do Permissions Come From?

There are two common approaches.

---

## Approach 1 — Roles Own Permissions

Example:

```text
Author

↓

post:create

post:update

comment:create
```

Admin:

```text
Admin

↓

All Permissions
```

Users receive permissions through their assigned role.

---

## Approach 2 — Direct User Permissions

Example:

Rahul:

```text
post:create

post:update

report:view
```

Aman:

```text
comment:create

comment:delete
```

Each user has their own permission set.

This provides maximum flexibility.

---

# Hybrid Model (Most Common)

Most production applications combine both.

```text
User

↓

Role

↓

Default Permissions

↓

Extra User Permissions

↓

Final Permission Set
```

Example:

```text
Author

↓

Default Permissions

↓

+

feature:beta-access
```

This avoids creating unnecessary roles.

---

# Roles vs Permissions

## Role

Represents:

```text
Who are you
inside the organization?
```

Example:

```text
Author
```

---

## Permission

Represents:

```text
What can you do?
```

Example:

```text
post:publish
```

Roles describe responsibility.

Permissions describe capability.

---

# Permission Doesn't Replace Ownership

Suppose Rahul has:

```text
post:update
```

Rahul requests:

```http
PUT /posts/25
```

Permission check:

```text
Has post:update?

↓

Yes
```

Ownership check:

```text
Owns Post #25?

↓

No

↓

403 Forbidden
```

Permission grants the capability.

Ownership decides whether it applies to this specific resource.

Imagine your application adds:

# Repository Responsibilities

Repositories should never ask:

```text
Does User Have

post:update?
```

Repositories only:

```text
Find

Create

Update

Delete
```

Authorization belongs above the repository.

# Common Beginner Mistakes

## ❌ Creating Hundreds of Roles

Bad:

```text
Junior Editor

Senior Editor

Regional Editor

Global Editor
```

Use permissions instead.

---

## ❌ Poor Permission Names

Bad:

```text
permission1

permission2
```

Good:

```text
post:update

user:delete
```

---

## ❌ Believing Permissions Replace Ownership

Permissions answer:

```text
Can perform action?
```

Ownership answers:

```text
Can perform it

on this resource?
```

You usually need both.

---

## ❌ Hardcoding Permission Checks

Avoid writing permission checks throughout your controllers.

Centralize them in middleware or dedicated authorization services.

---

## ❌ Mixing Authentication and Permissions

Authentication identifies the user.

Permissions determine capabilities.

Keep these concerns separate.

---

# Best Practices

- Use consistent `resource:action` permission names.
    
- Keep roles broad and stable.
    
- Add permissions for fine-grained control.
    
- Combine permissions with ownership authorization.
    
- Centralize permission checks.
    
- Keep repositories free of authorization logic.

# Interview Questions

### Q1. Why do large applications use permissions instead of only roles?

**Answer:**

Permissions provide fine-grained control and prevent role explosion. They allow administrators to grant specific capabilities without creating many new roles.

---

### Q2. What's the difference between a role and a permission?

**Answer:**

A role represents a user's responsibility (such as Author or Admin), while a permission represents a specific capability (such as `post:create` or `post:delete`).

---

### Q3. Can permissions replace ownership authorization?

**Answer:**

No. Permissions determine whether a user can perform an action in general, while ownership determines whether the user can perform that action on a specific resource.

---

### Q4. Why use the `resource:action` naming convention?

**Answer:**

It creates a consistent, scalable naming system that is easy to understand, organize, and extend as the application grows.

# 💡 Backend Engineering Tip

A good way to think about authorization evolution is:

```text
Small App

↓

RBAC

──────────────

Growing App

↓

RBAC

+

Permissions

──────────────

Enterprise App

↓

RBAC

+

Permissions

+

Ownership

+

Business Rules
```

Notice that **permissions don't replace roles**—they refine them. Most mature backend systems layer these concepts together to build an authorization model that is both flexible and maintainable.
