# The Problem

Imagine your Blog App has these APIs:

```text
POST   /posts

PUT    /posts/:id

DELETE /posts/:id

POST   /comments

DELETE /comments/:id

GET    /analytics
```

Without middleware, every controller starts with:

```text
Does user have permission?

↓

Yes?

↓

Continue
```

Soon your codebase becomes:

```text
PostController

↓

Permission Check

──────────────

CommentController

↓

Permission Check

──────────────

AnalyticsController

↓

Permission Check
```

The same logic is repeated everywhere.

---

# The Solution

Move permission checks into reusable middleware.

Architecture:

```text
Request

↓

Authentication

↓

Permission Middleware

↓

Controller

↓

Service
```

Controllers only receive requests that have already been authorized.

---

# Middleware Responsibility

Permission middleware answers one question:

```text
Does this user

have the required permission?
```

It should **not**:

- Verify JWT
    
- Load the authenticated user
    
- Validate request data
    
- Check resource ownership
    
- Execute business logic
    

Each concern belongs to a different layer.

---

```text

↓
```

# Multiple Allowed Permissions

Some endpoints may allow more than one capability.

Example:

```http
GET /analytics
```

Allowed:

```text
analytics:view

analytics:manage
```

Flow:

```text
User Permissions

↓

Match Any Required Permission?

↓

Yes

↓

Continue
```

The middleware succeeds if the application's authorization policy says that **any one** of the required permissions is sufficient.

---

# Multiple Required Permissions

Sometimes an action requires **more than one** permission.

Example:

```http
POST /admin/reports
```

Required:

```text
report:create

report:publish
```

Flow:

```text
User Permissions

↓

Has Both?

↓

Yes

↓

Continue
```

This is stricter than the previous example.

# Where Do Permissions Come From?

Authentication already loaded:

```text
Authenticated User
```

The user now has:

```text
Permissions

↓

post:create

post:update

comment:create
```

Permission middleware simply reads this information.

It does **not** authenticate again.

# Route-Level Protection

Think of routes as declaring their required capabilities.

Example:

```text
POST /posts

↓

Requires

↓

post:create
```

Another:

```text
DELETE /users

↓

Requires

↓

user:delete
```

Every route clearly communicates its authorization requirement.

# Controller Responsibilities

Controllers should never ask:

```text
Has Permission?
```

Instead:

```text
Controller

↓

Business Logic
```

Authorization has already happened.

---

# Permission Middleware vs Ownership

Suppose Rahul has:

```text
post:update
```

Rahul requests:

```http
PUT /posts/20
```

Permission middleware:

```text
Has post:update?

↓

Yes
```

Service:

```text
Load Post

↓

Owner = Aman

↓

403 Forbidden
```

Permission middleware grants the capability.

Ownership determines whether the capability applies to this specific resource.

---

# Permission Middleware vs RBAC

Many production systems combine both.

Example:

```text
Authentication

↓

RBAC

↓

Permissions

↓

Ownership

↓

Business Logic
```

RBAC provides broad access.

Permissions provide fine-grained control.

Ownership protects individual resources.

# Common Beginner Mistakes

## ❌ Checking Permissions in Every Controller

Bad:

```text
Controller

↓

Permission Check
```

Centralize permission checks in middleware.

---

## ❌ Verifying JWT Again

Authentication already verified the JWT.

Permission middleware should never repeat this.

---

## ❌ Confusing Permissions with Ownership

Having:

```text
post:update
```

does **not** automatically mean:

```text
Can update every post.
```

Ownership may still apply.

---

## ❌ Poor Permission Naming

Avoid:

```text
edit

delete

create
```

Prefer:

```text
post:update

post:delete

post:create
```

---

## ❌ Returning 401 Instead of 403

Remember:

```text
401

↓

Not Authenticated
```

```text
403

↓

Authenticated

↓

Missing Permission
```

---

# Best Practices

- Authenticate before checking permissions.
    
- Centralize permission checks in middleware.
    
- Use consistent permission names.
    
- Keep controllers free of authorization logic.
    
- Combine permissions with ownership when required.
    
- Return **403 Forbidden** for insufficient permissions.

# Interview Questions

### Q1. Why use permission middleware?

**Answer:**

Permission middleware centralizes authorization logic, eliminates duplicate code, and keeps controllers focused on business logic.

---

### Q2. Should permission middleware verify JWTs?

**Answer:**

No. JWT verification belongs to authentication middleware. Permission middleware assumes the user has already been authenticated.

---

### Q3. Can permission middleware replace ownership authorization?

**Answer:**

No. Permission middleware verifies whether the user has the required capability. Ownership authorization determines whether the user can apply that capability to a specific resource.

---

### Q4. Why return **403 Forbidden** instead of **401 Unauthorized**?

**Answer:**

Because the user is already authenticated. The request is denied due to insufficient permissions, not because the user's identity is unknown.

# 💡 Backend Engineering Tip

A mature authorization pipeline often looks like this:

```text
Authentication

↓

Account Status

↓

Role Check (optional)

↓

Permission Check

↓

Ownership Check

↓

Business Rules

↓

Controller

↓

Service
```

Each layer answers a different question:

- **Authentication:** Who is the user?
    
- **Permission:** Can this user perform this action?
    
- **Ownership:** Can they perform it on this specific resource?
    
- **Business Rules:** Is the action valid under the application's rules?
    

Keeping these responsibilities separate results in a backend that is secure, maintainable, and easy to extend.
