# Where Do Permissions Come From?

There are three common models.

---

# Model 1 — Role → Permission Mapping

Most common.

```text
Admin

↓

All Permissions
```

```text
Author

↓

post:create

post:update

comment:create
```

The user inherits permissions from their role.

Architecture:

```text
User

↓

Role

↓

Permissions

↓

Authorization
```

Simple.

Easy to maintain.

---

# Model 2 — Direct User Permissions

Instead of roles:

Rahul:

```text
post:create

post:update

report:view
```

Aman:

```text
comment:create

comment:delete
```

Every user has their own permission list.

Benefits:

- Very flexible
    

Disadvantages:

- Difficult to manage at scale
    

---

# Model 3 — Hybrid Model (Most Common)

Professional systems usually combine both.

```text
User

↓

Role

↓

Default Permissions

↓

Extra Permissions

↓

Final Permission Set
```

Example:

Rahul:

```text
Role

↓

Author
```

Default:

```text
post:create

post:update
```

Extra:

```text
analytics:view
```

Final permissions:

```text
post:create

post:update

analytics:view
```

This is the model used by many production systems.

---

# Permission Groups

Large applications organize permissions into groups.

Example:

```text
Posts

↓

post:create

post:update

post:delete
```

```text
Comments

↓

comment:create

comment:delete
```

```text
Users

↓

user:create

user:update

user:delete
```

Benefits:

- Easier management
    
- Easier documentation
    
- Easier audits
    

---

# Permission Hierarchy

Some permissions imply others.

Example:

```text
post:manage
```

may represent:

```text
post:create

post:update

post:delete
```

This is a design choice.

Be explicit about what each higher-level permission includes.

---

# Dynamic Permission Evaluation

Some permissions depend on context.

Example:

```text
invoice:approve
```

Business rule:

```text
Amount

↓

< ₹50,000

↓

Manager

────────────

> ₹50,000

↓

Director
```

Permission alone isn't enough.

Business rules still apply.

---

# Multi-Tenant Applications

Suppose your SaaS has:

```text
Company A
```

and

```text
Company B
```

Rahul belongs to:

```text
Company A
```

Permission:

```text
user:update
```

Should Rahul update users in Company B?

No.

Flow:

```text
Authentication

↓

Permission

↓

Tenant Check

↓

Ownership

↓

Allow
```

Tenant isolation is another authorization layer.

---

# Role Changes

Yesterday:

```text
Rahul

↓

Author
```

Today:

```text
Rahul

↓

Editor
```

Tomorrow's request should use:

```text
Editor Permissions
```

Always use the **latest** role and permission assignments.

---

# Revoking Permissions

Suppose:

```text
analytics:view
```

is removed from Rahul.

Old JWT:

```text
Still Valid
```

If you trust only the JWT:

```text
Rahul

↓

Still Has Permission
```

Professional applications typically reload the current user and permission information (or use another reliable strategy such as token versioning or short-lived access tokens) so authorization reflects recent changes.

---

# Permission Caching

Loading permissions from the database on every request can become expensive.

Some applications cache permission data.

Example:

```text
Database

↓

Redis Cache

↓

Permission Middleware
```

Benefits:

- Faster authorization
    
- Reduced database load
    

Challenge:

The cache must be refreshed or invalidated when roles or permissions change.

---

# Permission Audit

Professional systems record:

```text
Permission Granted

Permission Revoked

Role Changed

Access Denied
```

Audit logs help with:

- Compliance
    
- Security investigations
    
- Troubleshooting

# Avoid Permission Explosion

Just like role explosion:

Bad:

```text
post:create:v1

post:create:v2

post:create:premium

post:create:admin
```

Instead:

```text
post:create
```

Use business rules for special cases.

Keep permission names stable and meaningful.

# Common Beginner Mistakes

## ❌ Giving Every User Direct Permissions

This becomes difficult to maintain.

Prefer roles with optional extra permissions.

---

## ❌ Creating Hundreds of Permissions

Permissions should represent **business capabilities**, not tiny implementation details.

---

## ❌ Never Updating Cached Permissions

Permission caches must stay synchronized with the source of truth.

---

## ❌ Trusting Stale Permission Data

Always ensure authorization decisions reflect current user roles and permissions.

---

## ❌ Forgetting Tenant Isolation

In multi-tenant applications, permissions alone aren't enough.

Always verify organizational boundaries.

---

# Best Practices

- Use roles for broad responsibilities.
    
- Use permissions for fine-grained capabilities.
    
- Prefer a hybrid authorization model.
    
- Organize permissions into logical groups.
    
- Keep permission names consistent.
    
- Keep authorization data synchronized with current account state.
    
- Audit important authorization changes.

# Interview Questions

### Q1. What is the most common permission model in production?

**Answer:**

A hybrid model where users inherit default permissions from roles and may also receive additional user-specific permissions.

---

### Q2. Why is assigning permissions directly to every user usually discouraged?

**Answer:**

Because it becomes difficult to manage, audit, and maintain as the number of users grows. Roles provide a scalable way to manage common permission sets.

---

### Q3. Why is permission caching useful?

**Answer:**

Caching reduces database lookups and improves performance, especially in applications that perform authorization checks on every request. However, cache invalidation must be handled carefully.

---

### Q4. Why aren't permissions alone enough in a multi-tenant application?

**Answer:**

Because users must also be restricted to their own organization or tenant. A permission like `user:update` should not automatically grant access to resources belonging to another tenant.

# 💡 Backend Engineering Tip

A mature authorization system is built in layers, not around a single concept:

```text
Authentication

↓

Account Status

↓

Roles

↓

Permissions

↓

Tenant Isolation

↓

Ownership

↓

Business Rules

↓

Controller

↓

Service
```

Notice that **permissions are just one layer**. Production backends combine multiple authorization mechanisms so that each layer solves a specific security problem. This layered design is what makes enterprise authorization systems both secure and scalable.
