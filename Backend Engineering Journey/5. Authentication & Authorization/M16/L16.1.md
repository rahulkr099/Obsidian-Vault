# What is a Cookie?

A cookie is a **small piece of data** stored by the browser.

The server can ask the browser to save it.

Example:

```text
Server

↓

Set Cookie

↓

Browser Stores Cookie
```

Later:

```text
Browser

↓

Automatically Sends Cookie

↓

Server
```

Cookies make it possible to maintain a session across multiple HTTP requests.

---

# Authentication with Cookies

Login:

```text
User Login

↓

Server Creates Refresh Token

↓

Server Sets Cookie

↓

Browser Stores Cookie
```

Next request:

```text
Browser

↓

Cookie

↓

Server

↓

Authenticate User
```

The browser automatically includes eligible cookies in requests.

# Where Can Tokens Be Stored?

Common options:

```text
Cookies

Local Storage

Session Storage

Memory
```

Each has different security and usability trade-offs.

---

# Local Storage

Advantages:

- Simple API
    
- Persists across browser restarts
    
- Easy to access from JavaScript
    

Example:

```text
Browser

↓

localStorage

↓

Access Token
```

---

Disadvantage:

JavaScript can read it.

If malicious JavaScript executes in your page (for example, due to an XSS vulnerability), it may be able to access tokens stored there.

---

# Cookies

Advantages:

- Can be configured as HttpOnly
    
- Can be configured as Secure
    
- Automatically included with matching requests
    

Example:

```text
Browser

↓

HttpOnly Cookie

↓

Server
```

---

# HttpOnly

HttpOnly means:

```text
JavaScript

↓

Cannot Read Cookie
```

Example:

```text
document.cookie

↓

Refresh Token?

↓

No Access
```

This reduces the impact of many XSS attacks by preventing client-side scripts from reading the cookie value.

---

# Secure Cookie

Secure means:

```text
HTTPS

↓

Cookie Sent
```

```text
HTTP

↓

Cookie Not Sent
```

Always use Secure cookies in production environments served over HTTPS.

---

# SameSite Attribute

SameSite helps control when browsers send cookies with cross-site requests.

Three common modes:

---

## Strict

```text
Same Site Only
```

Highest protection.

Cross-site requests generally do not include the cookie.

---

## Lax

```text
Mostly Same Site

↓

Some Top-Level Navigation Allowed
```

A good default for many applications.

---

## None

```text
Cross-Site Allowed
```

Required when cookies need to be sent across different sites (for example, some frontend/backend deployments).

Modern browsers require:

```text
SameSite=None

+

Secure
```

---

# Cookie Expiration

Cookies can expire.

Example:

```text
Refresh Token

↓

7 Days
```

After expiration:

```text
Browser Removes Cookie
```

Users need to authenticate again or obtain a new session according to your authentication design.

---

# Browser Authentication Flow

```text
Login

↓

Set HttpOnly Cookie

↓

Browser Stores Cookie

↓

Protected Request

↓

Browser Sends Cookie

↓

Authentication
```

Notice:

JavaScript doesn't need to manually attach the cookie.

The browser handles it.

---

# Why Many Applications Use Cookies for Refresh Tokens

Common production architecture:

```text
Access Token

↓

Memory

──────────────

Refresh Token

↓

HttpOnly Cookie
```

Why?

- Access tokens are short-lived.
    
- Refresh tokens are long-lived and deserve stronger protection.
    
- HttpOnly reduces exposure to client-side JavaScript.
    

---

# Cookies vs Local Storage

|Feature|Cookies|Local Storage|
|---|---|---|
|Automatic with requests|✅|❌|
|Accessible by JavaScript|Configurable (`HttpOnly` prevents access)|✅|
|Can be `HttpOnly`|✅|❌|
|Can be `Secure`|✅|❌|
|Expiration support|✅|Manual|
|Common use|Refresh Tokens|Short-lived UI data or, in some architectures, access tokens|

Neither option is universally "best." The right choice depends on your application's architecture and security requirements.

# CSRF Overview

If the browser automatically sends cookies:

```text
Browser

↓

Automatically Sends Cookie
```

Cross-site requests may also include cookies depending on browser rules and cookie settings.

This is why applications using cookie-based authentication often add protections such as:

- SameSite cookies
    
- CSRF tokens
    
- Origin/Referer validation (when appropriate)
    

We'll study CSRF in more detail later.

# Common Beginner Mistakes

## ❌ Storing Everything in localStorage

Long-lived refresh tokens stored in localStorage are more exposed if malicious JavaScript gains access to the page.

---

## ❌ Not Using Secure Cookies

Cookies containing authentication information should be marked `Secure` in production.

---

## ❌ Forgetting HttpOnly

Without `HttpOnly`:

```text
JavaScript

↓

Can Read Cookie
```

---

## ❌ Using SameSite=None Without Secure

Modern browsers generally reject:

```text
SameSite=None

+

Not Secure
```

---

## ❌ Assuming Cookies Alone Solve Every Security Problem

Cookies help, but they do not eliminate risks such as CSRF or XSS.

Security requires multiple layers.

---

# Best Practices

- Store refresh tokens in HttpOnly cookies for browser-based applications when appropriate.
    
- Use Secure cookies in production.
    
- Choose an appropriate SameSite policy.
    
- Keep access tokens short-lived.
    
- Use HTTPS everywhere.
    
- Combine cookie security with CSRF protection and other security measures where needed.

# Interview Questions

### Q1. Why are HttpOnly cookies considered more secure for refresh tokens?

**Answer:**

Because JavaScript cannot read HttpOnly cookies, reducing the impact of many XSS attacks that attempt to steal tokens.

---

### Q2. What does the Secure cookie attribute do?

**Answer:**

It instructs the browser to send the cookie only over HTTPS connections.

---

### Q3. Why is `SameSite=None` usually combined with `Secure`?

**Answer:**

Modern browsers require cookies with `SameSite=None` to also have the `Secure` attribute.

---

### Q4. Should every token always be stored in cookies?

**Answer:**

No. The storage strategy depends on the application's architecture, client type, and security requirements. Many browser applications store refresh tokens in HttpOnly cookies while handling access tokens differently.

# 💡 Backend Engineering Tip

A common production pattern for browser applications is:

```text
Access Token

↓

Short-Lived

↓

Stored in Memory

────────────────────

Refresh Token

↓

Long-Lived

↓

Stored in HttpOnly Secure Cookie
```

This design balances **security** and **user experience**. Short-lived access tokens reduce the impact of token theft, while HttpOnly cookies help protect long-lived refresh tokens from client-side JavaScript access. Combined with HTTPS, proper cookie settings, and server-side validation, this forms a strong foundation for secure session management.
