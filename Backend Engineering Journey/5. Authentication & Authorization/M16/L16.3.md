# Why Account Security Matters

Suppose Rahul uses a strong password.

That's great.

But what if an attacker tries:

```text
1 Million Login Attempts
```

Or:

```text
Stolen Password

↓

Login
```

A secure backend must defend against these attacks automatically.

# Common Authentication Attacks

Professional applications defend against:

```text
Brute Force

Credential Stuffing

Password Spraying

Session Hijacking

Token Theft
```

Let's understand each one.

---

# Brute-Force Attack

Attacker:

```text
Password1

↓

Password2

↓

Password3

↓

...

↓

Correct Password
```

Goal:

Guess one user's password.

---

## Defense

Use:

- Rate limiting
    
- Account lockout
    
- Strong passwords
    
- MFA (where appropriate)
    

---

# Login Rate Limiting

Professional systems limit login attempts.

Example:

```text
5 Attempts

↓

1 Minute

↓

Too Many Requests
```

Response:

```http
429 Too Many Requests
```

This slows automated attacks.

---

# Account Lockout

Suppose:

```text
5 Failed Logins
```

Then:

```text
Lock Account

↓

15 Minutes
```

During the lockout period:

```http
403 Forbidden
```

Be careful:

Very aggressive lockout policies can also be abused to temporarily deny access to legitimate users.

---

# Credential Stuffing

Attacker already has:

```text
Email

+

Password
```

from another website.

They try:

```text
Same Credentials

↓

Your Blog App
```

Because many users reuse passwords,

this attack is very common.

---

## Defense

- MFA
    
- Password breach monitoring (where applicable)
    
- Encourage unique passwords
    
- Detect unusual login behavior
    

---

# Password Spraying

Instead of trying many passwords for one account,

the attacker tries:

```text
One Common Password

↓

Many Users
```

Example:

```text
Password123

↓

Rahul

↓

Aman

↓

Neha

↓

...
```

---

## Defense

- Strong password policies
    
- MFA
    
- Rate limiting
    
- Login monitoring
    

---

# Session Hijacking

Attacker steals:

```text
Refresh Token
```

or

```text
Session Cookie
```

They attempt:

```text
Authenticate

↓

Victim's Account
```

---

## Defense

- HTTPS
    
- HttpOnly cookies
    
- Secure cookies
    
- Short-lived access tokens
    
- Refresh token rotation
    

---

# Suspicious Login Detection

Example:

Yesterday:

```text
India
```

Five minutes later:

```text
Germany
```

This may indicate suspicious activity.

Applications can:

- Request re-authentication
    
- Notify the user
    
- Temporarily limit sensitive actions
    

Always design these checks carefully to avoid false positives.

---

# Device Tracking

Professional applications often track sessions.

Example:

```text
Laptop

Phone

Tablet
```

Each device has:

- Login time
    
- Last activity
    
- Session ID
    

Users can then:

```text
View Active Sessions

↓

Remove One

↓

Logout All
```

---

# Security Notifications

Example:

```text
New Login

↓

Send Email
```

Or:

```text
Password Changed

↓

Notify User
```

Notifications help users detect unauthorized activity quickly.

---

# Reauthentication

Some actions deserve extra verification.

Example:

```text
Change Password

↓

Ask for Current Password
```

Or:

```text
Delete Account

↓

Reauthenticate
```

Being logged in doesn't always mean every action should be allowed without additional confirmation.

---

# Secure Password Policy

Require passwords that are:

- Long
    
- Difficult to guess
    
- Not commonly used
    

Modern guidance generally favors **long passphrases** over forcing many special rules, because they're often easier for users to remember and harder to crack.

---

# Account Recovery

If the user forgets the password:

```text
Forgot Password

↓

Reset Token

↓

Email

↓

New Password
```

Recovery should always verify the user's identity before allowing a password change.

# Common Beginner Mistakes

## ❌ Unlimited Login Attempts

Attackers can keep guessing passwords indefinitely.

Always limit repeated login attempts.

---

## ❌ Long-Lived Sessions

Sessions that never expire increase risk if a device is compromised.

---

## ❌ Ignoring Failed Login Attempts

Monitor unusual authentication activity.

---

## ❌ No Login Notifications

Users should know when important account events occur.

---

## ❌ Weak Password Policy

Avoid allowing passwords that are extremely easy to guess.

---

# Best Practices

- Rate limit authentication endpoints.
    
- Keep sessions short and manageable.
    
- Rotate refresh tokens.
    
- Track active devices.
    
- Notify users about important account events.
    
- Require reauthentication for sensitive actions.
    
- Encourage strong, unique passwords.
    
- Offer MFA for additional protection.

# Interview Questions

### Q1. Why is rate limiting important?

**Answer:**

Rate limiting reduces the effectiveness of automated attacks such as brute-force and password spraying by limiting how many requests can be made in a given period.

---

### Q2. What is credential stuffing?

**Answer:**

Credential stuffing is an attack where stolen username/password pairs from another service are reused to try logging into your application.

---

### Q3. Why should users be notified about new logins?

**Answer:**

Login notifications help users quickly detect unauthorized access and take action, such as changing their password or logging out other sessions.

---

### Q4. Why require reauthentication for sensitive actions?

**Answer:**

Because an existing authenticated session may not be sufficient for high-risk operations like changing a password or deleting an account. Reauthentication adds another layer of protection.

# 💡 Backend Engineering Tip

A secure authentication system doesn't rely on a single defense.

Think in terms of **defense in depth**:

```text
Strong Passwords

↓

Rate Limiting

↓

JWT Verification

↓

Secure Cookies

↓

Refresh Token Rotation

↓

Session Tracking

↓

MFA

↓

Audit Logs
```

If one layer fails, the others continue protecting the account. This layered security model is what you'll find in well-designed production backend systems.
