# Lesson 17.1 — OAuth Fundamentals

> **Goal:** Understand what OAuth is, why it exists, and how the OAuth Authorization Code Flow works from start to finish.

One of the biggest misconceptions is:

> **OAuth = Login with Google**

That's not actually true.

Google Login is **one application of OAuth**.

OAuth itself is an **authorization framework**.

Understanding this difference is very important for backend interviews.

# Why Was OAuth Created?

Imagine your Blog App wants access to a user's Google profile.

Without OAuth:

```text
User

↓

Shares Google Password

↓

Blog App Logs In

↓

Gets Data
```

Problems:

- Your app knows the user's password.
    
- If your app is hacked, the password is exposed.
    
- The user has no fine-grained control.
    

This approach is unsafe.

---

# OAuth Solution

Instead:

```text
User

↓

Google Login

↓

Google Grants Permission

↓

Blog App Gets Access Token

↓

Reads Profile
```

Notice:

The Blog App **never knows the user's Google password**.

---

# Authentication vs Authorization

Authentication:

```text
Who are you?
```

Authorization:

```text
What are you allowed to access?
```

OAuth was designed for:

```text
Authorization
```

Many applications also use OAuth as part of a login experience, but its original purpose is delegated authorization.

# OAuth Terminology

There are four important actors.

---

## 1. Resource Owner

Usually:

```text
Rahul
```

The user who owns the data.

---

## 2. Client

Example:

```text
Blog App
```

The application requesting access.

---

## 3. Authorization Server

Example:

```text
Google
```

Responsible for:

- Login
    
- User consent
    
- Token issuance
    

---

## 4. Resource Server

Example:

```text
Google APIs
```

Contains protected resources such as:

- Profile
    
- Email
    
- Calendar
    
- Drive

# Authorization Code Flow

Professional web applications commonly use:

```text
Authorization Code Flow
```

Flow:

```text
User

↓

Blog App

↓

Google Login

↓

Authorization Code

↓

Backend

↓

Access Token

↓

Google API

↓

User Profile
```

This is the most common OAuth flow for server-side web applications.

---

# Step 1 — User Starts Login

Rahul clicks:

```text
Continue with Google
```

Backend redirects to Google.

---

# Step 2 — Google Login

Google authenticates Rahul.

```text
Email

↓

Password

↓

Google Login
```

Your application never sees these credentials.

---

# Step 3 — User Grants Consent

Google displays:

```text
Allow Blog App

to access

your email?
```

User chooses:

```text
Allow
```

or

```text
Deny
```

The user stays in control.

---

# Step 4 — Authorization Code

Google redirects:

```text
Blog App

↓

Authorization Code
```

Important:

The code is **not** an access token.

It is a short-lived credential that your backend exchanges securely.

---

# Step 5 — Token Exchange

Backend:

```text
Authorization Code

↓

Google

↓

Access Token
```

This exchange happens **server-to-server**.

The client secret stays on the backend.

---

# Step 6 — Access Google API

Backend:

```text
Access Token

↓

Google Profile API

↓

User Data
```

Example:

```text
Name

Email

Picture
```

---

# Step 7 — Your Authentication System

Now your backend decides:

```text
User Exists?

├── No
│     ↓
│   Create User
│
└── Yes
      ↓
Continue
```

Then:

```text
Issue

Your Own JWT
```

This is important.

After Google verifies the user,

**your application still manages its own authentication and sessions.**

# Why Not Send the Access Token Directly?

Because:

```text
Authorization Code

↓

Backend

↓

Token Exchange
```

keeps:

- Client Secret
    
- Token Exchange
    

on the server.

This is safer than exposing sensitive credentials to the browser.

---

# OAuth Scopes

Scopes define:

```text
What Can Be Accessed?
```

Examples:

```text
email

profile

calendar.read

drive.read
```

Request only the scopes your application actually needs.

This follows the **principle of least privilege**.

# Common Beginner Mistakes

## ❌ Thinking OAuth Is Authentication

OAuth is an authorization framework.

It can also be used as part of an authentication process.

---

## ❌ Trusting Google Without Creating Your Own Session

After Google verifies the user:

```text
Google Login

↓

Your JWT

↓

Your Session
```

Your application should manage its own authentication.

---

## ❌ Requesting Too Many Scopes

Bad:

```text
Email

Calendar

Drive

Contacts

Photos
```

if your application only needs:

```text
Email

Profile
```

Request the minimum permissions required.

---

## ❌ Exchanging Tokens in the Frontend

For server-side applications:

The authorization code should be exchanged on the backend, where the client secret can remain confidential.

---

## ❌ Ignoring User Consent

Users should always understand what information your application is requesting.

---

# Best Practices

- Use the Authorization Code Flow for server-side web applications.
    
- Keep the client secret on the backend.
    
- Request only required scopes.
    
- Create or link users in your own database.
    
- Issue your own JWT after successful OAuth login.
    
- Follow the principle of least privilege.

# Interview Questions

### Q1. What is OAuth?

**Answer:**

OAuth is an authorization framework that allows an application to access protected resources on behalf of a user without knowing the user's password.

---

### Q2. Does OAuth replace your application's authentication?

**Answer:**

No. OAuth can verify the user's identity through a provider, but your application should still create its own session or issue its own JWT.

---

### Q3. What is the Authorization Code?

**Answer:**

It is a short-lived code returned by the authorization server that the backend exchanges for access tokens.

---

### Q4. Why are scopes important?

**Answer:**

Scopes define which resources an application can access. Requesting only the required scopes improves security and user trust.

# 💡 Backend Engineering Tip

One of the most common interview questions is:

> **"If Google authenticates the user, why do you still create your own JWT?"**

The answer is:

```text
Google

↓

Proves Identity

────────────────────

Your Backend

↓

Creates Local User

↓

Issues Your JWT

↓

Controls Sessions

↓

Applies Roles & Permissions
```

Google authenticates the user **for Google**. Your application still needs its own authentication token so it can enforce its own roles, permissions, ownership rules, session management, and business logic independently of Google.
