# What is User Identity?

Before a backend can authenticate someone, it must know **who that person is**.

This is called **user identity**.

Think of identity as the unique way your application recognizes a user.

Example:

```text
Rahul

↓

Email:
rahul@example.com

↓

User Found

↓

Authenticate Password
```

Without a way to identify the user, the server doesn't know which account to authenticate.

---

# Identity vs Authentication

These terms are related but different.

### Identity

> **Who is this account?**

Example:

```text
Email

↓

rahul@example.com
```

---

### Authentication

> **Can this person prove they own this account?**

Example:

```text
Email

+

Password

↓

Authenticated
```

Identity comes first.

Authentication comes second.

---

# Two Types of Identifiers

Professional systems usually have **two identifiers**.

## 1. Internal Identifier

Used by the database.

Example:

```text
User ID

66fa93d8c51...
```

or

```text
UUID

4f67ea9d...
```

Users never need to remember this.

---

## 2. Public Identifier

Used to find the account.

Examples:

- Email
    
- Username
    
- Phone Number
    
- Google Account
    

Example:

```text
Login

↓

rahul@example.com
```

---

# Common Identity Methods

Most applications use one or more of these.

```text
Email

Username

Phone Number

OAuth Provider
```

Let's understand each one.

---

# Option 1 — Email

The most common identity.

Example:

```text
rahul@example.com
```

Workflow:

```text
Enter Email

↓

Find User

↓

Verify Password
```

### Advantages

- Easy to remember.
    
- Usually unique.
    
- Works with password reset.
    
- Supports email verification.
    
- Simple to implement.
    

### Disadvantages

- User can change email.
    
- Email must be verified.
    
- Requires email service.
    

---

## Best For

- Blog
    
- Portfolio
    
- SaaS
    
- LMS
    
- E-commerce
    
- Admin Dashboard
    

Our Blog App will use **email** as the primary login identifier.

---

# Option 2 — Username

Example:

```text
rahul_dev
```

Workflow:

```text
Username

↓

Find User

↓

Verify Password
```

### Advantages

- Easy to type.
    
- User-friendly.
    
- Good for public profiles.
    

### Disadvantages

- Must be unique.
    
- Users may compete for names.
    
- Renaming can affect profile links.
    

---

## Best For

- GitHub
    
- Reddit
    
- Discord
    
- Forums
    
- Social Media
    

---

# Option 3 — Phone Number

Example:

```text
+91 9876543210
```

Authentication usually uses OTP.

```text
Phone

↓

Send OTP

↓

Verify OTP

↓

Login
```

### Advantages

- Very convenient.
    
- No password required (if OTP-based).
    
- Useful on mobile devices.
    

### Disadvantages

- SMS costs money.
    
- Phone numbers can change.
    
- OTP delivery may fail.
    

---

## Best For

- Banking
    
- Food Delivery
    
- Ride Sharing
    
- Messaging Apps
    

---

# Option 4 — OAuth Provider ID

Instead of creating a password, users log in with another provider.

Example:

```text
Continue with Google
```

Workflow:

```text
Google Login

↓

Google verifies user

↓

Returns Google ID

↓

Create/Login User
```

The backend stores something like:

```text
googleId

11829384756291
```

Notice:

The backend trusts **Google's verification**, not the user's password.

---

## Best For

- SaaS
    
- Developer Tools
    
- Productivity Apps
    
- Modern Web Applications

# Comparing Identity Methods

|Method|Unique|Easy to Remember|Can Change|Requires Verification|
|---|:-:|:-:|:-:|:-:|
|Email|✅|✅|✅|✅|
|Username|✅|✅|✅|Sometimes|
|Phone|✅|❌|✅|✅|
|OAuth ID|✅|N/A|Usually No|Verified by Provider|

---

# What Should Be Truly Unique?

Every user should have an internal ID that never changes.

Example:

```text
User ID

↓

66fa93d8...
```

Other identifiers can change.

Example:

```text
Old Email

↓

New Email
```

The internal ID remains the same.

This is why relationships in the database should reference the **User ID**, not the email.

---

# Blog App Example

Suppose Rahul writes a post.

```text
Post

↓

Author

↓

User ID
```

Instead of:

```text
Author Email
```

Why?

If Rahul changes his email:

```text
rahul@example.com

↓

rahul.dev@example.com
```

All posts still belong to the same **User ID**.

---

# A Production-Ready Identity Strategy

For our Blog App, we'll use:

```text
Internal ID

↓

MongoDB ObjectId
```

For login:

```text
Email
```

For display:

```text
Username
```

The flow becomes:

```text
User

↓

Email

↓

Find User

↓

Verify Password

↓

Return User ID

↓

Generate JWT
```

This is simple, scalable, and commonly used.

---

# Can We Support Multiple Login Methods?

Yes.

Many modern applications allow users to log in using different methods.

Example:

```text
Email + Password

OR

Google Login

OR

GitHub Login
```

All of them eventually point to the same user record.

```text
Google Account

↓

User ID

↓

Same User
```

This avoids creating duplicate accounts.

# Identity in the Database

A simplified `User` document might look like:

```json
{
  "_id": "66fa93d8...",
  "email": "rahul@example.com",
  "username": "rahul_dev",
  "password": "<hashed_password>",
  "googleId": null
}
```

Notice:

- `_id` is the permanent internal identifier.
    
- `email` is used for login.
    
- `username` is for display.
    
- `googleId` is optional and used if the user signs in with Google.

# Common Beginner Mistakes

## ❌ Using Email as the Relationship Key

Bad:

```text
Post

↓

authorEmail
```

If the email changes, relationships become harder to manage.

Better:

```text
Post

↓

authorId
```

---

## ❌ Assuming Email Never Changes

Users often change email addresses.

Design your system so changing an email doesn't break existing data.

---

## ❌ Allowing Duplicate Emails

Bad:

```text
User A

↓

rahul@example.com
```

```text
User B

↓

rahul@example.com
```

The server won't know which account to authenticate.

Always enforce a unique constraint.

---

## ❌ Trusting OAuth Email Alone

Some OAuth providers may return an email that isn't verified.

Always check the provider's verification status and follow your application's account-linking rules.

---

# Best Practices

- Use a permanent internal user ID.
    
- Use email as the primary login identifier for most web applications.
    
- Keep usernames separate from login logic when possible.
    
- Reference users by ID, not by email or username.
    
- Enforce uniqueness for login identifiers.
    
- Design for future support of OAuth and multiple login methods.
    

---

# Summary

In this lesson, you learned:

- **Identity** identifies the user; **authentication** proves ownership of that identity.
    
- Every user should have a permanent internal ID.
    
- Email is the best primary login method for most backend applications.
    
- Usernames are useful for public display but should not replace the internal ID.
    
- Phone numbers and OAuth providers are valuable alternatives depending on the application.
    
- Store relationships using the user's internal ID to keep your system stable and scalable.
