# Why User Model Design Matters

The **User** model is one of the most important models in any backend application.

Almost every feature depends on it.

Examples:

- Login
    
- Registration
    
- JWT
    
- Password Reset
    
- Email Verification
    
- RBAC
    
- Profile
    
- Audit Logs
    
- Notifications
    

A poorly designed user model becomes difficult to maintain as the application grows.

# The User Model in a Blog App

Our Blog App has users who can:

- Register
    
- Login
    
- Create posts
    
- Comment
    
- Update profile
    
- Reset password
    
- Verify email
    

So our user model should support all these features.

# Step 2 — Categorize Fields

Instead of adding fields randomly, group them by purpose.

```text
Identity Fields

Authentication Fields

Authorization Fields

Profile Fields

Security Fields

System Fields
```

This makes the model easier to understand.

---

# Identity Fields

These identify the user.

```javascript
_id
email
username
```

Example:

```json
{
  "_id": "66fa...",
  "email": "rahul@example.com",
  "username": "rahul_dev"
}
```

### Rules

- `_id` never changes.
    
- Email should be unique.
    
- Username should be unique (if used publicly).
    

---

# Authentication Fields

These help verify the user.

```javascript
password
emailVerified
```

Example:

```json
{
  "password": "$2b$12$...",
  "emailVerified": false
}
```

Notice:

Passwords are **hashed**, never stored in plain text.

---

# Authorization Fields

These define permissions.

Example:

```javascript
role
```

Possible values:

```text
reader

author

admin
```

Example:

```json
{
  "role": "author"
}
```

Later, we may also add permissions.

---

# Profile Fields

These improve the user experience.

Examples:

```javascript
name
avatar
bio
```

Example:

```json
{
  "name": "Rahul Kumar",
  "avatar": "avatar.png",
  "bio": "Backend Developer"
}
```

These fields are not required for authentication but are useful for the application.

---

# Security Fields

These help protect accounts.

Examples:

```javascript
lastLogin
passwordChangedAt
```

Future additions might include:

```javascript
failedLoginAttempts
accountLockedUntil
```

These support features like:

- Account lockout
    
- Password invalidation
    
- Security monitoring
    

---

# System Fields

Automatically managed by the application.

Examples:

```javascript
createdAt
updatedAt
```

These answer questions like:

```text
When was this account created?

When was it last updated?
```

Most ORMs/ODMs can manage these automatically.

---

# Putting It All Together

A production-ready user document might look like:

```json
{
  "_id": "66fa93d8...",
  "email": "rahul@example.com",
  "username": "rahul_dev",
  "password": "$2b$12$hashedPassword...",
  "name": "Rahul Kumar",
  "avatar": null,
  "bio": "",
  "role": "author",
  "emailVerified": false,
  "lastLogin": null,
  "passwordChangedAt": null,
  "createdAt": "2026-08-04T10:00:00Z",
  "updatedAt": "2026-08-04T10:00:00Z"
}
```

This model is clean, readable, and extensible.

# Which Fields Should Be Required?

|Field|Required|Reason|
|---|:-:|---|
|email|✅|Primary login identity|
|password|✅|Authentication|
|username|✅|Public identity (for our Blog App)|
|role|✅|Authorization|
|name|✅|Display name|
|avatar|❌|User can upload later|
|bio|❌|Optional profile|
|emailVerified|✅|Email verification status|
|createdAt|✅|System metadata|
|updatedAt|✅|System metadata|

---

# Fields That Should Be Unique

Always enforce uniqueness for:

```text
email

username
```

This prevents duplicate accounts.

Example:

```text
rahul@example.com

↓

Already Exists

↓

Registration Rejected
```

---

# Fields That Should Never Be Returned

Never expose sensitive fields in API responses.

Do **not** send:

```javascript
password
```

Later, you may also hide:

```javascript
passwordChangedAt
failedLoginAttempts
```

A safe response might look like:

```json
{
  "_id": "66fa93d8...",
  "name": "Rahul Kumar",
  "email": "rahul@example.com",
  "username": "rahul_dev",
  "role": "author"
}
```

---

# Future-Proofing the Model

As your application grows, you may add fields like:

```javascript
googleId
githubId
refreshToken
twoFactorEnabled
twoFactorSecret
```

Notice that the core structure remains the same.

A well-designed model evolves without major redesigns.

# Common Beginner Mistakes

## ❌ Storing Plain Text Passwords

Bad:

```json
{
  "password": "mypassword123"
}
```

Always store a **hashed password**.

---

## ❌ Using Email as Foreign Key

Bad:

```text
Post

↓

authorEmail
```

Better:

```text
Post

↓

authorId
```

IDs are stable; emails can change.

---

## ❌ Mixing Profile and Security Data

Avoid placing unrelated information together without organization.

Group fields by responsibility.

---

## ❌ Making Everything Required

Example:

```javascript
avatar
bio
website
linkedin
twitter
```

New users shouldn't have to fill every profile field just to register.

---

# Best Practices

- Use `_id` as the permanent identifier.
    
- Keep authentication, authorization, and profile fields separate.
    
- Store only hashed passwords.
    
- Enforce unique constraints on email and username.
    
- Never expose sensitive fields in API responses.
    
- Design the schema with future features in mind.

# 💡 Backend Engineering Tip

A **User model is not just a database schema—it is the foundation of your authentication system**. Spend time designing it well before writing login or registration code. A good schema reduces future refactoring and makes adding features like OAuth, MFA, refresh tokens, and audit logs much easier.
