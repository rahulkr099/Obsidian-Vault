# What Happens When a User Registers?

Imagine Rahul opens your Blog App and clicks **Sign Up**.

He enters:

```text
Name: Rahul Kumar

Username: rahul_dev

Email: rahul@example.com

Password: ********
```

When he clicks **Register**, a lot happens behind the scenes.

---

# Complete Registration Flow

```text
Client
   │
   ▼
POST /api/auth/register
   │
   ▼
Validate Request
   │
   ▼
Check Duplicate User
   │
   ▼
Hash Password
   │
   ▼
Create User
   │
   ▼
Generate Verification Token
   │
   ▼
Send Verification Email
   │
   ▼
Return Success Response
```

This is the standard flow used in many production applications.

---

# Step 1 — Client Sends Request

Example request:

```http
POST /api/auth/register
```

Body:

```json
{
  "name": "Rahul Kumar",
  "username": "rahul_dev",
  "email": "rahul@example.com",
  "password": "MyPassword123"
}
```

At this point, the backend trusts **nothing**.

Everything must be validated.

---

# Step 2 — Validate Input

The first responsibility is validating the request.

Check:

- Required fields exist.
    
- Email format is valid.
    
- Username format is valid.
    
- Password meets security rules.
    
- No unexpected fields are accepted.
    

Example:

```text
Request

↓

Validation

↓

Valid?

↓

Yes

↓

Continue
```

If validation fails:

```text
400 Bad Request
```

Never continue processing invalid data.

---

# Step 3 — Check for Duplicate Users

Now check whether the email or username already exists.

Example:

```text
Find User by Email

↓

Found?

↓

Yes

↓

Reject Registration
```

Then:

```text
Find User by Username

↓

Found?

↓

Yes

↓

Reject Registration
```

If both are unique:

```text
Continue
```

Always enforce uniqueness at the **database level** as well, because two requests could arrive at the same time.

---

# Step 4 — Hash the Password

Never store:

```text
password123
```

Instead:

```text
password123

↓

bcrypt / Argon2

↓

$2b$12$....
```

The original password is never saved.

Only the hash is stored.

---

# Step 5 — Create the User

Now create the user document.

Example:

```json
{
  "email": "rahul@example.com",
  "username": "rahul_dev",
  "password": "<hashed_password>",
  "role": "author",
  "emailVerified": false
}
```

Notice:

The user is **not verified yet**.

---

# Step 6 — Generate Email Verification Token

Generate a secure random token.

```text
User Created

↓

Generate Token

↓

Store Token

↓

Send Email
```

Example:

```text
Verification Link

https://example.com/verify?token=abc123
```

The user will click this later.

---

# Step 7 — Send Verification Email

Example:

```text
Welcome Rahul!

Click the link below to verify your account.
```

If email sending fails, your application should decide whether to:

- Retry sending.
    
- Allow login but remind the user to verify.
    
- Prevent login until verification succeeds.
    

We'll study these trade-offs in later modules.

---

# Step 8 — Return Response

Example response:

```json
{
  "success": true,
  "message": "Registration successful. Please verify your email."
}
```

Notice:

We do **not** return:

- Password
    
- Password hash
    
- Verification token

# Registration Flow in Backend Architecture

```text
Route
   │
   ▼
Validation Middleware
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Database
```

Each layer has one responsibility.

---

# Responsibility of Each Layer

## Route

Maps:

```http
POST /api/auth/register
```

to the controller.

---

## Validation Middleware

Checks:

- Email format
    
- Username format
    
- Password rules
    

Rejects invalid requests before they reach the controller.

---

## Controller

Responsibilities:

- Read request.
    
- Call service.
    
- Return response.
    

Controllers should **not** contain business logic.

---

## Service

The service performs the registration workflow.

Example:

```text
Validate Business Rules

↓

Check Duplicate User

↓

Hash Password

↓

Create User

↓

Generate Verification Token

↓

Trigger Email
```

Business logic belongs here.

---

## Repository

Repository responsibilities:

```text
Find User

Create User

Update User
```

Repositories should only communicate with the database.

# Registration Errors

## Duplicate Email

```text
rahul@example.com

↓

Already Exists

↓

409 Conflict
```

---

## Weak Password

```text
Password

↓

Too Short

↓

400 Bad Request
```

---

## Invalid Email

```text
rahul@

↓

Invalid Format

↓

400 Bad Request
```

---

## Unexpected Server Error

```text
Database Offline

↓

500 Internal Server Error
```

The client should receive a generic message, while detailed errors are logged on the server.

---

# Registration vs Login

|Registration|Login|
|---|---|
|Creates a new user|Verifies an existing user|
|Hashes password|Compares password|
|Sends verification email|Issues authentication tokens|
|Checks duplicates|Checks credentials|

They solve different problems.

---

# Common Beginner Mistakes

## ❌ Creating User Before Validation

Bad:

```text
Create User

↓

Validate
```

Correct:

```text
Validate

↓

Create User
```

---

## ❌ Forgetting Duplicate Checks

Without duplicate checks:

```text
User A

↓

rahul@example.com
```

```text
User B

↓

rahul@example.com
```

This creates inconsistent data and login issues.

---

## ❌ Returning Sensitive Data

Never return:

```json
{
  "password": "...",
  "passwordHash": "...",
  "verificationToken": "..."
}
```

Only return safe information.

---

## ❌ Mixing Everything in the Controller

Bad:

```text
Controller

↓

Validation

↓

Hash Password

↓

Database Query

↓

Send Email
```

Controllers become difficult to maintain.

Instead:

```text
Validation

↓

Controller

↓

Service

↓

Repository
```

# Production Considerations

As your application grows, the registration process may include:

- CAPTCHA
    
- Invite codes
    
- Referral codes
    
- Audit logging
    
- Welcome emails
    
- Analytics events
    
- Background jobs for sending emails
    

Because the workflow is well-structured, these features can be added without redesigning the entire system.

---

# Best Practices

- Validate input before doing any work.
    
- Enforce unique constraints in both the application and the database.
    
- Hash passwords before storing them.
    
- Never return sensitive fields in responses.
    
- Keep controllers thin.
    
- Place business logic in the service layer.
    
- Keep database operations inside repositories.
    
- Prepare the workflow for email verification and future features.

# 💡 Backend Engineering Tip

Think of **registration as a workflow, not a single database insert**.

A professional registration flow coordinates multiple responsibilities:

- Validate the request.
    
- Enforce business rules.
    
- Securely store user data.
    
- Trigger follow-up actions (like email verification).
    

Designing it this way makes your backend easier to test, maintain, and scale.
