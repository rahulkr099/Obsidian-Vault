# Why Password Security Matters

Imagine your Blog App has **100,000 users**.

Your database contains:

```text
Users
```

If you store passwords like this:

|Email|Password|
|---|---|
|[rahul@example.com](mailto:rahul@example.com)|MyPassword123|
|[aman@example.com](mailto:aman@example.com)|hello123|
|[priya@example.com](mailto:priya@example.com)|password|

A database leak immediately exposes every user's password.

This is one of the biggest security mistakes a backend developer can make.

---

# The Correct Approach

Instead of storing:

```text
MyPassword123
```

Store:

```text
$2b$12$8RZwM6Y....
```

This value is called a **hash**.

The original password is never stored.

---

# What is Hashing?

Hashing is a mathematical process that converts data into a fixed-length output.

Example:

```text
Password

↓

Hash Function

↓

Hash
```

Example:

```text
MyPassword123

↓

Hash Function

↓

8RZwM6Y......
```

Notice:

The output looks random.

---

# Properties of Hashing

A good password hashing algorithm has these properties:

### Same Input → Same Output

```text
hello123

↓

Hash

↓

ABCXYZ
```

Again:

```text
hello123

↓

Hash

↓

ABCXYZ
```

Same input always produces the same output.

---

### Different Input → Different Output

```text
hello123

↓

ABCXYZ
```

```text
hello124

↓

KLMNOP
```

Even one character changes the result completely.

---

### One-Way Process

This is the most important property.

```text
Password

↓

Hash

↓

Stored
```

But:

```text
Hash

↓

Original Password

↓

Impossible to Recover
```

A hash cannot be "decrypted."

---

# Hashing vs Encryption

Many beginners confuse these two concepts.

|Hashing|Encryption|
|---|---|
|One-way|Two-way|
|Cannot recover original data|Original data can be recovered|
|Used for passwords|Used for confidential data|
|No decryption key|Requires encryption/decryption keys|

---

## Encryption Example

```text
Message

↓

Encrypt

↓

Encrypted Data

↓

Decrypt

↓

Original Message
```

Useful for:

- Bank details
    
- API secrets
    
- Private documents
    

---

## Hashing Example

```text
Password

↓

Hash

↓

Store Hash

↓

Original Password Cannot Be Retrieved
```

Perfect for passwords.

---

# Why Not Encrypt Passwords?

Suppose you encrypted passwords.

```text
Password

↓

Encryption

↓

Encrypted Password
```

Later:

```text
Decrypt

↓

Original Password
```

Now ask yourself:

> **Where is the decryption key stored?**

If an attacker steals:

- Database
    
- Encryption key
    

They recover every password.

Hashing avoids this problem.

---

# Then How Does Login Work?

Rahul logs in.

He enters:

```text
MyPassword123
```

Backend:

```text
Entered Password

↓

Hash Again

↓

Compare

↓

Stored Hash

↓

Match?
```

If both hashes match:

```text
Login Success
```

The backend never needs the original password.

---

# The Problem with Basic Hashing

Imagine two users choose:

```text
password123
```

Using a basic hash:

```text
password123

↓

HASH123
```

Both users get:

```text
HASH123
```

An attacker immediately knows:

These users probably have the same password.

This is dangerous.

---

# What is a Salt?

A **salt** is a random value added to the password before hashing.

Instead of:

```text
Password

↓

Hash
```

We do:

```text
Password

+

Random Salt

↓

Hash
```

---

# Example

Rahul:

```text
Password

↓

MyPassword123

+

Salt A

↓

Hash A
```

Aman:

```text
Password

↓

MyPassword123

+

Salt B

↓

Hash B
```

Even though the passwords are identical:

```text
Hash A ≠ Hash B
```

This is exactly what we want.

---

# Why Salts Matter

Without salt:

|Password|Hash|
|---|---|
|password123|ABC123|
|password123|ABC123|

Attacker immediately knows:

Both users share the same password.

---

With salt:

|Password|Salt|Hash|
|---|---|---|
|password123|X82M|PQR...|
|password123|H19Z|LMN...|

Now every stored hash is unique.

---

# Rainbow Table Attacks

Attackers can prepare huge databases like:

|Password|Hash|
|---|---|
|password|HASH1|
|hello123|HASH2|
|admin|HASH3|

These are called **rainbow tables**.

Without salt:

```text
Database Hash

↓

Rainbow Table

↓

Original Password
```

With salt:

The precomputed table becomes useless because every password has a different random salt.

---

# bcrypt

**bcrypt** is one of the most widely used password hashing algorithms.

Features:

- Automatically generates a random salt.
    
- Designed specifically for passwords.
    
- Intentionally slow.
    
- Resistant to brute-force attacks.
    

Workflow:

```text
Password

↓

Generate Salt

↓

Hash Password

↓

Store Hash
```

The generated hash already contains the salt information, so you don't need to store it separately.

---

# Cost Factor (Work Factor)

bcrypt allows you to choose how expensive hashing should be.

Example:

```text
Cost = 10
```

or

```text
Cost = 12
```

Higher cost:

```text
More CPU Time

↓

Slower Hashing

↓

Harder to Crack
```

But:

```text
Too High

↓

Slow Login

↓

Poor User Experience
```

Choose a balanced value.

---

# Argon2

Argon2 is a newer password hashing algorithm.

It won the **Password Hashing Competition (PHC)**.

Advantages:

- Memory-hard.
    
- More resistant to modern hardware attacks.
    
- Configurable.
    
- Considered one of the best choices today.
    

---

# bcrypt vs Argon2

|Feature|bcrypt|Argon2|
|---|---|---|
|Mature|✅|✅|
|Widely Supported|✅|✅|
|Automatic Salt|✅|✅|
|Memory Hard|❌|✅|
|Recommended Today|✅|✅ (often preferred for new systems)|

Both are excellent.

If your stack supports Argon2 well, it's a strong modern choice.

bcrypt remains a very common and trusted choice.

# Common Beginner Mistakes

## ❌ Storing Plain Text Passwords

```text
Password

↓

Database
```

Never do this.

---

## ❌ Using Encryption Instead of Hashing

Encryption is reversible.

Passwords should not be.

---

## ❌ Using Fast Hash Functions

Algorithms like:

- MD5
    
- SHA-1
    

are excellent for data integrity but **not** for password storage because they are too fast and easier to brute-force with modern hardware.

---

## ❌ Creating Your Own Hashing Algorithm

Never invent your own security algorithm.

Use trusted libraries implementing bcrypt or Argon2.

---

## ❌ Reusing the Same Salt

Each password should have its own unique random salt.

Modern password hashing libraries handle this automatically.

---

# Best Practices

- Never store plain-text passwords.
    
- Never encrypt passwords for storage.
    
- Use bcrypt or Argon2.
    
- Let the library generate a unique salt automatically.
    
- Choose an appropriate work factor.
    
- Keep password hashing inside the authentication service, not in controllers or repositories.
    

---

# Summary

In this lesson, you learned:

- Passwords should be stored as **hashes**, not plain text.
    
- Hashing is a one-way process, unlike encryption.
    
- Salts ensure that identical passwords produce different hashes.
    
- bcrypt and Argon2 are industry-standard password hashing algorithms.
    
- Modern libraries automatically manage salts and secure hash generation.
    
- Slow password hashing algorithms help defend against brute-force attacks.
    

---

# 💡 Backend Engineering Tip

Treat password hashing as a **security boundary**, not just a coding task.

Whenever a password enters your backend:

```text
Receive Password

↓

Validate

↓

Hash Immediately

↓

Forget Original Password
```

After hashing, your application should never need to store or retrieve the original password again.
