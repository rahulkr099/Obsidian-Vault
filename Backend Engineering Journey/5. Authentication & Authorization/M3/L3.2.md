# The Password Lifecycle

A password doesn't just exist during registration.

It goes through multiple stages.

```text
User Chooses Password
        │
        ▼
Validate Password
        │
        ▼
Hash Password
        │
        ▼
Store Hash
        │
        ▼
Login Verification
        │
        ▼
Password Change
        │
        ▼
Password Reset
        │
        ▼
Rehash (if needed)
```

Professional developers think about the **entire lifecycle**, not just hashing.

---

# Stage 1 — Registration

User enters:

```text
MyPassword123!
```

Backend:

```text
Receive Password

↓

Validate Strength

↓

Hash Password

↓

Store Hash
```

Database stores:

```text
$2b$12$kL9......
```

Never:

```text
MyPassword123!
```

---

# Stage 2 — Login Verification

Many beginners think:

```text
Entered Password

↓

Compare Text

↓

Stored Password
```

This is wrong.

Instead:

```text
Entered Password

↓

Hash Using bcrypt/Argon2

↓

Compare With Stored Hash
```

Example:

```text
Entered

↓

MyPassword123

↓

Hash

↓

Matches Stored Hash?

↓

Yes

↓

Login Success
```

Notice:

The backend **never decrypts** anything.

---

# How bcrypt Verification Works

You may wonder:

> We generate a random salt during registration.
> 
> How does login know which salt to use?

The answer:

The bcrypt hash already contains:

- Algorithm
    
- Cost factor
    
- Salt
    
- Hash
    

Example (simplified):

```text
$2b$12$AbCdEfGhIjKlMnOpQrStUv...
```

When you call:

```javascript
bcrypt.compare(password, storedHash)
```

bcrypt automatically:

```text
Read Salt

↓

Hash Password Again

↓

Compare

↓

Return True/False
```

You don't manually manage salts.

# Stage 3 — Password Change

Suppose Rahul wants to change his password.

A secure workflow is:

```text
Current Password

↓

Verify Current Password

↓

Enter New Password

↓

Validate

↓

Hash New Password

↓

Update Database
```

Never allow password changes without verifying the current password (unless it's a password reset flow).

---

# Update Password Metadata

After changing the password:

Update:

```text
passwordChangedAt
```

Example:

```text
2026-08-04 15:30
```

This timestamp becomes useful later.

---

# Why passwordChangedAt Matters

Imagine:

```text
Login

↓

JWT Issued
```

Later:

```text
Password Changed
```

Old JWTs may still exist.

By comparing:

```text
Token Issued Time

↓

passwordChangedAt
```

the backend can reject tokens created before the password change.

This improves security.

---

# Stage 4 — Password Reset

Forgot Password is different from Change Password.

Password Change:

```text
User Knows Password

↓

Verify Current Password
```

Password Reset:

```text
User Forgot Password

↓

Verify Email

↓

Reset Token

↓

Set New Password
```

The current password is not required because identity is verified through the reset process.

---

# Password Reset Workflow

```text
Forgot Password

↓

Generate Secure Token

↓

Store Token (or its hash)

↓

Send Email

↓

User Clicks Link

↓

Verify Token

↓

Set New Password

↓

Hash Password

↓

Delete Reset Token
```

The reset token should be:

- Random
    
- Short-lived
    
- One-time use
    

---

# Should You Store Reset Tokens?

Bad:

```text
Database

↓

Raw Reset Token
```

Better:

```text
Database

↓

Hash of Reset Token
```

This follows the same idea as password storage.

If the database leaks, attackers cannot use the original reset token.

---

# Password History

Some applications prevent users from reusing recent passwords.

Example:

```text
Old Password

↓

New Password

↓

Same?

↓

Reject
```

Common in:

- Banking
    
- Enterprise software
    
- Government systems
    

For a Blog App, this is usually unnecessary.

---

# When Should You Rehash Passwords?

Suppose:

Five years ago:

```text
bcrypt cost = 10
```

Today:

```text
bcrypt cost = 12
```

When Rahul logs in:

```text
Verify Password

↓

Hash Uses Old Cost?

↓

Yes

↓

Rehash Password

↓

Update Database
```

The user doesn't notice anything, but security improves.

# Common Password Security Mistakes

## ❌ Returning Password Hash

Bad:

```json
{
  "email": "rahul@example.com",
  "password": "$2b$12$..."
}
```

Never expose password hashes.

---

## ❌ Logging Passwords

Bad:

```text
User Password:

MyPassword123
```

Logs often end up in monitoring systems.

Never log passwords.

---

## ❌ Emailing Passwords

Bad:

```text
Welcome!

Your password is:

MyPassword123
```

Never send passwords by email.

---

## ❌ Reversible Password Storage

Bad:

```text
Password

↓

Encrypt

↓

Decrypt Later
```

Passwords should not be recoverable.

---

## ❌ Skipping Password Verification

Bad:

```text
Change Password

↓

Update Password
```

Always verify the current password unless it's a verified password reset.

---

## ❌ Keeping Reset Tokens Forever

Bad:

```text
Reset Token

↓

Never Expires
```

Good:

```text
Reset Token

↓

Expires in 15 minutes
```

---

## ❌ Using the Same Password Everywhere

Although users control this, encourage:

- Unique passwords
    
- Password managers
    
- Strong passphrases
    

---

# Production Best Practices

✔ Hash passwords immediately after validation.

✔ Use bcrypt or Argon2.

✔ Never log passwords.

✔ Never expose password hashes.

✔ Update `passwordChangedAt` after password changes.

✔ Invalidate active sessions after password reset.

✔ Use short-lived reset tokens.

✔ Store hashed reset tokens.

✔ Rehash passwords when security requirements change.

# Interview Questions

### Q1. Why don't we decrypt passwords during login?

**Answer:**

Because passwords are **hashed**, not encrypted. The backend hashes the entered password again and compares it with the stored hash.

---

### Q2. Why is bcrypt better than SHA-256 for passwords?

**Answer:**

bcrypt is intentionally slow and automatically uses a unique salt, making brute-force attacks much harder. SHA-256 is designed to be fast, which is good for data integrity but not for password storage.

---

### Q3. Should the repository compare passwords?

**Answer:**

No. Password verification is part of the authentication business logic and belongs in the **service layer**. The repository should only read and write data.

---

### Q4. Why update `passwordChangedAt`?

**Answer:**

It allows the backend to invalidate tokens or sessions that were created before the password was changed, improving account security.
