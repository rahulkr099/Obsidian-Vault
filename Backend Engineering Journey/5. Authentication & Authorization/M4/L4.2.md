# Why Login Security Matters

Imagine your Blog App has **50,000 users**.

An attacker writes a script:

```text
Try Password

↓

123456

↓

password

↓

admin123

↓

hello123

↓

Repeat
```

If your backend has no protection, the attacker can try **millions of passwords**.

Professional applications never allow this.

# Scenario 1 — Invalid Credentials

Rahul enters:

```text
Email:
rahul@example.com

Password:
wrongpassword
```

Backend:

```text
Find User

↓

Compare Password

↓

No Match

↓

Reject
```

Response:

```http
401 Unauthorized
```

Example:

```json
{
  "success": false,
  "message": "Invalid email or password."
}
```

---

# Why Use a Generic Error Message?

Many beginners return:

```text
Email Not Found
```

or

```text
Wrong Password
```

This seems helpful but creates a security problem.

---

# User Enumeration Attack

Imagine an attacker tries:

```text
rahul@example.com
```

Server:

```text
Wrong Password
```

The attacker now knows:

> Rahul has an account.

Next:

```text
unknown@example.com
```

Server:

```text
Email Not Found
```

Now the attacker knows that email is **not registered**.

By repeating this process, they can build a list of valid users.

This is called **user enumeration**.

---

# Correct Response

Whether the email exists or not:

Always return:

```json
{
  "success": false,
  "message": "Invalid email or password."
}
```

The attacker learns nothing.

# Scenario 2 — Failed Login Counter

Each failed login increases a counter.

Example:

```text
Attempt 1

↓

failedLoginAttempts = 1
```

Next:

```text
Attempt 2

↓

failedLoginAttempts = 2
```

Eventually:

```text
failedLoginAttempts = 5
```

Now the application can take action.

---

# Account Lockout

Example policy:

```text
5 Failed Attempts

↓

Lock Account

↓

15 Minutes
```

Workflow:

```text
Failed Login

↓

Increment Counter

↓

Reached Limit?

↓

Yes

↓

Lock Account
```

---

# User Model Example

Your user document might include:

```javascript
failedLoginAttempts
accountLockedUntil
```

Example:

```json
{
  "failedLoginAttempts": 5,
  "accountLockedUntil": "2026-08-04T16:00:00Z"
}
```

---

# Successful Login

When login succeeds:

Reset the counter.

```text
Successful Login

↓

failedLoginAttempts = 0

↓

accountLockedUntil = null
```

This prevents permanent lockouts after a successful authentication.

---

# Locked Account Flow

```text
Login

↓

Account Locked?

↓

Yes

↓

Reject
```

Response:

```json
{
  "message": "Your account is temporarily locked."
}
```

No password comparison is needed once the lock is confirmed.

---

# Temporary vs Permanent Lock

## Temporary Lock

```text
5 Attempts

↓

15 Minutes

↓

Automatically Unlock
```

Most applications use this approach.

---

## Permanent Lock

```text
Too Many Attempts

↓

Administrator Unlock Required
```

Usually reserved for:

- Banking
    
- Enterprise software
    
- Government systems

# Login Rate Limiting

Instead of protecting only the account:

Protect the login endpoint.

Example:

```text
POST /login

↓

Maximum 10 Requests

↓

Per Minute

↓

Per IP Address
```

Extra requests receive:

```http
429 Too Many Requests
```

Rate limiting reduces automated attacks.

---

# Brute-Force Attack Protection

Without protection:

```text
Attacker

↓

1 Million Passwords
```

With protection:

```text
Attempt

↓

Rate Limit

↓

Account Lock

↓

```

Security is about making attacks expensive.

# Security Logging

Failed logins should be logged.

Example:

```text

↓

↓

↓
```

Useful for:

- Detecting attacks
    
- Monitoring suspicious activity

# Common Beginner Mistakes

## ❌ Different Error Messages

Bad:

```text
Email doesn't exist.
```

```text
Wrong password.
```

Better:

```text
Invalid email or password.
```

---

## ❌ Unlimited Login Attempts

Bad:

```text
Try Forever
```

Always have:

- Rate limiting
    
- Lockout policy
    

---

## ❌ Never Resetting Failed Attempts

Wrong:

```text
Successful Login

↓

Counter Still = 5
```

Always reset the counter after a successful login.

---

## ❌ Logging Passwords

Bad log:

```text
Password Entered:

MyPassword123
```

Never log passwords.

---

## ❌ Locking Forever

Permanent lockouts can frustrate legitimate users.

Most applications prefer:

```text
Temporary Lock

↓

Automatic Unlock
```

---

# Production Best Practices

- Use generic login error messages.
    
- Prevent user enumeration.
    
- Track failed login attempts.
    
- Temporarily lock accounts after repeated failures.
    
- Reset counters after successful login.
    
- Rate-limit login endpoints.
    
- Log security events, not passwords.
    
- Keep authentication logic in the service layer.

# Interview Questions

### Q1. Why shouldn't you return "Email not found"?

**Answer:**

It allows attackers to discover which email addresses are registered. Returning a generic message like **"Invalid email or password."** prevents user enumeration.

---

### Q2. Why use account lockout?

**Answer:**

To slow down brute-force attacks by temporarily blocking repeated failed login attempts.

---

### Q3. Should repositories compare passwords?

**Answer:**

No. Password comparison is business logic and belongs in the authentication service. Repositories should only read and update user data.

---

### Q4. Why reset the failed login counter after a successful login?

**Answer:**

A successful login proves the legitimate user has authenticated. Keeping old failed attempts could incorrectly lock the account later.

# 💡 Backend Engineering Tip

A secure login system is **not just about verifying a password**.

It combines multiple layers of protection:

- Input validation
    
- Password verification
    
- Generic error messages
    
- Account status checks
    
- Failed login tracking
    
- Rate limiting
    
- Security logging
    

When these work together, your authentication system becomes much more resilient against real-world attacks.
