# The Problem

Rahul logs into the Blog App.

```text
Email

↓

Password

↓

Login Successful
```

Now Rahul requests:

```http
GET /api/posts
```

How does the backend know this request is still from Rahul?

Should Rahul send:

```text
Email

Password
```

on every request?

Of course not.

The backend needs a way to **remember the authenticated user**.

There are two popular solutions:

```text
Session

OR

JWT
```

---

# Option 1 — Session-Based Authentication

A session is simply **a record stored on the server**.

After login:

```text
Rahul Logs In

↓

Server Creates Session

↓

Stores Session

↓

Returns Session ID
```

The browser stores only:

```text
Session ID
```

Usually inside a cookie.

---

# Session Authentication Flow

```text
Login

↓

Verify Password

↓

Create Session

↓

Store Session

↓

Return Session ID Cookie
```

Next request:

```text
Browser

↓

Session ID Cookie

↓

Server Finds Session

↓

User Authenticated
```

---

# Visual Example

Server memory (or Redis):

```text
Session ID

abc123

↓

User ID

66fa93...
```

Browser:

```text
Cookie

sessionId=abc123
```

When Rahul makes another request:

```text
Browser

↓

sessionId=abc123

↓

Server

↓

Find Session

↓

User = Rahul
```

---

# Where is User Information Stored?

In session authentication:

```text
Server

↓

Stores User Information
```

The browser only stores:

```text
Session ID
```

This is called **stateful authentication**.

---

# Why "Stateful"?

Because the server remembers every logged-in user.

Example:

```text
Server

↓

Session A

↓

Rahul
```

```text
Server

↓

Session B

↓

Aman
```

```text
Server

↓

Session C

↓

Priya
```

The server maintains authentication state.

---

# Advantages of Sessions

✅ Easy logout.

Delete the session.

```text
Delete Session

↓

User Logged Out
```

---

✅ Easy token revocation.

Delete one session.

Done.

---

✅ No sensitive user data stored in the browser.

The browser stores only:

```text
Session ID
```

---

# Disadvantages of Sessions

The server must store every session.

Example:

```text
1 Million Users

↓

1 Million Sessions
```

This consumes server resources.

---

In distributed systems:

```text
Server A

Server B

Server C
```

All servers must access the same session store.

Usually:

```text
Redis
```

---

# Option 2 — JWT Authentication

JWT stands for:

> **JSON Web Token**

Instead of storing authentication information on the server:

The server gives it to the client.

After login:

```text
Login

↓

Generate JWT

↓

Return JWT
```

---

Browser stores:

```text
JWT
```

Next request:

```text
Authorization

Bearer eyJhbGc...
```

The server verifies the JWT.

No session lookup required.

---

# JWT Authentication Flow

```text
Login

↓

Verify Password

↓

Generate JWT

↓

Return JWT

↓

Browser Stores JWT

↓

Protected Request

↓

Verify JWT

↓

Authenticated
```

---

# Visual Example

Browser:

```text
JWT

eyJhbGc...
```

Next request:

```http
Authorization: Bearer eyJhbGc...
```

Server:

```text
Verify Signature

↓

Extract User ID

↓

Authenticated
```

---

# Where is User Information Stored?

With JWT:

```text
Client

↓

Stores Token
```

The token contains information like:

```text
User ID

Role

Expiration
```

The server verifies it every request.

---

# Why "Stateless"?

Because the server does **not** store login sessions.

Example:

Instead of:

```text
Server

↓

Session
```

The server simply verifies:

```text
JWT

↓

Valid?

↓

Yes
```

No session lookup.

---

# Session vs JWT

|Sessions|JWT|
|---|---|
|Stateful|Stateless|
|Server stores session|Client stores token|
|Browser stores Session ID|Browser stores JWT|
|Easy logout|Requires token revocation strategy|
|Easy invalidation|More complex invalidation|
|Needs session storage|No session storage|

# Which is Faster?

Sessions:

```text
Request

↓

Database / Redis Lookup

↓

Authenticated
```

JWT:

```text
Request

↓

Verify Signature

↓

Authenticated
```

JWT avoids session lookups.

However, both approaches can perform well when designed properly. Network latency, database speed, caching, and infrastructure all affect performance.

---

# Which is More Secure?

This is a common interview question.

The answer is:

> **Neither is automatically more secure.**

Security depends on **how you implement them**.

Poorly implemented sessions are insecure.

Poorly implemented JWTs are also insecure.

Professional developers focus on secure implementation rather than assuming one technology is inherently safer.

---

# When Should You Use Sessions?

Sessions work well for:

- Traditional web applications
    
- Admin dashboards
    
- Internal company tools
    
- Applications with server-rendered pages
    

Especially when:

- Easy logout is important.
    
- Immediate session invalidation is required.
    

---

# When Should You Use JWT?

JWT works well for:

- REST APIs
    
- Mobile apps
    
- SPA applications (React, Vue, Angular)
    
- Microservices
    
- Distributed systems
    

Especially when:

- Multiple backend services need to verify the same token.
    
- You want stateless authentication.

# Common Beginner Mistakes

## ❌ Thinking JWT Eliminates Authentication

JWT doesn't replace login.

Login still happens first.

JWT simply remembers the authenticated user.

---

## ❌ Storing Sensitive Data Inside JWT

Bad:

```text
Password

Phone Number

Credit Card
```

JWTs should contain only the minimum information required for authentication and authorization.

---

## ❌ Thinking Stateless Means No Security

JWT must still be:

- Verified
    
- Expiration checked
    
- Signed correctly
    

Stateless does **not** mean security-free.

---

## ❌ Using Sessions Without Secure Cookies

Always use:

- HttpOnly
    
- Secure (in production over HTTPS)
    
- Appropriate SameSite setting
    

We'll study cookies later.

---

# Best Practices

- Understand both Sessions and JWT.
    
- Choose based on your application architecture.
    
- Keep authentication middleware separate from business logic.
    
- Never store sensitive information in JWT payloads.
    
- Use secure cookies when storing session IDs or refresh tokens.
    
- Design logout and token revocation from the beginning.

# Interview Questions

### Q1. What is the biggest difference between Sessions and JWT?

**Answer:**

Sessions are **stateful** because the server stores authentication state. JWTs are **stateless** because the client stores the token, and the server verifies it without maintaining a session.

---

### Q2. Does JWT require a database lookup on every request?

**Answer:**

Not necessarily. The server can verify the JWT's signature without looking up a session. However, some applications still query the database for fresh user information or account status.

---

### Q3. Is JWT always better?

**Answer:**

No. Sessions and JWT solve different problems. The right choice depends on your application's architecture and requirements.

---

### Q4. Can React applications use Sessions?

**Answer:**

Yes. React applications can authenticate using secure cookies and sessions. JWT is common with SPAs, but it's not the only option.

# 💡 Backend Engineering Tip

Don't ask:

> **"Should I use Sessions or JWT?"**

Ask:

> **"What authentication approach best fits my application's architecture and security requirements?"**

For your **MERN Blog App**, a common production approach is:

```text
Login

↓

Access Token (JWT)

↓

Refresh Token (HttpOnly Cookie)

↓

Authentication Middleware

↓

Protected APIs
```

This combines the scalability of JWT with the security benefits of refresh tokens.
