# What is a JWT?

JWT stands for:

> **JSON Web Token**

It is a compact string that proves a user has been authenticated.

Example:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJ1c2VySWQiOiI2NmZhOTNkOCIsInJvbGUiOiJhdXRob3IifQ.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

It looks complicated, but it's simply **three parts separated by dots**.

---

# JWT Structure

```text
Header

.

Payload

.

Signature
```

or

```text
xxxxx.yyyyy.zzzzz
```

Each part has a specific purpose.

---

# Visual Overview

```text
JWT
│
├── Header

└── Signature
```

We'll examine each part.

---

# Part 1 — Header

The header contains metadata about the token.

Example:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

Meaning:

```text
alg

↓

Signing Algorithm
```

Example:

```text
HS256
```

And:

```text
typ

↓

JWT
```

The header tells the server **how the token was signed**.

---

# Part 2 — Payload

The payload contains **claims**.

Claims are pieces of information.

Example:

```json
{
  "userId": "66fa93d8...",
  "role": "author",
  "exp": 1785840000
}
```

The payload usually contains:

- User ID
    
- Role
    
- Expiration time
    
- Token issue time
    

---

# Common JWT Claims

|Claim|Meaning|
|---|---|
|sub|Subject (usually user ID)|
|exp|Expiration time|
|iat|Issued at|
|iss|Issuer|
|aud|Audience|
|jti|JWT ID|

Applications can also add custom claims.

Example:

```json
{
  "userId": "66fa93d8...",
  "role": "author"
}
```

---

# Part 3 — Signature

The signature protects the token from tampering.

Conceptually:

```text
Header

+

Payload

+

Secret Key

↓

Signature
```

The server creates the signature using its secret key.

The client **never knows this key**.

---

# Complete JWT

```text
Header

↓

Payload

↓

Signature

↓

JWT
```

Example:

```text
xxxxx

.

yyyyy

.

zzzzz
```

---

# Why Do We Need the Signature?

Imagine Rahul has this payload:

```json
{
  "userId": "66fa93d8",
  "role": "author"
}
```

An attacker changes it to:

```json
{
  "userId": "66fa93d8",
  "role": "admin"
}
```

Without a signature:

The server might believe the attacker.

With a signature:

```text
Payload Changed

↓

Signature Invalid

↓

Reject Token
```

The signature detects tampering.

---

# JWT Verification

Whenever a protected request arrives:

```text
Receive JWT

↓

Verify Signature

↓

Valid?

↓

Yes

↓

Extract Payload

↓

Authenticated
```

If verification fails:

```text
401 Unauthorized
```

The request stops immediately.

---

# Signing vs Encryption

Many beginners think JWT is encrypted.

It isn't.

JWT is usually **signed**.

---

## Signing

Purpose:

```text
Detect Tampering
```

Signing answers:

> **Has this token been modified?**

---

## Encryption

Purpose:

```text
Hide Information
```

Encryption answers:

> **Can someone read this data?**

JWT signing does **not** hide the payload.

---

# Can Anyone Read the Payload?

Yes.

Anyone who has the token can decode:

- Header
    
- Payload
    

Example:

```text
JWT

↓

Decode

↓

Payload Visible
```

Only the signature cannot be forged without the secret key.

---

# Therefore Never Store Sensitive Data

Bad payload:

```json
{
  "password": "MyPassword123",
  "creditCard": "...",
  "phone": "9876543210"
}
```

Anyone with the token can read it.

---

# Good Payload

```json
{
  "userId": "66fa93d8",
  "role": "author",
  "exp": 1785840000
}
```

Store only the minimum information needed.

---

# JWT Creation Flow

```text
User Login

↓

Verify Password

↓

Create Payload

↓

Sign JWT

↓

Return JWT
```

The client stores the JWT.

---

# Protected Request Flow

```text
Client

↓

Authorization Header

↓

Authentication Middleware

↓

Verify Signature

↓

Extract User

↓

Continue
```

Business logic only runs after successful verification.

---

# Secret Key

The signature depends on a secret key.

Example:

```text
Header

+

Payload

+

SECRET_KEY

↓

Signature
```

This key must remain private.

Never expose it to the client.

---

# What Happens if the Secret Leaks?

If attackers obtain:

```text
JWT Secret
```

They may be able to create valid tokens (depending on the signing algorithm and implementation).

This is why secret management is extremely important.

---

# Token Expiration

Most JWTs include:

```text
exp
```

Example:

```text
Now

↓

15 Minutes

↓

Expired
```

When expired:

```text
Reject Token

↓

401 Unauthorized
```

The user needs a new access token.

---

# JWT Authentication Middleware

The middleware usually performs:

```text
Read Token

↓

Verify Signature

↓

Check Expiration

↓

Extract User

↓

Attach User

↓

Next()
```

Example:

```javascript
req.user = {
  userId: "...",
  role: "author"
}
```

Controllers can now use:

```javascript
req.user
```

without parsing the JWT again.

---

# Common Beginner Mistakes

## ❌ Thinking JWT is Encrypted

It isn't.

Anyone can decode the payload.

---

## ❌ Storing Passwords Inside JWT

Bad:

```json
{
  "password": "..."
}
```

Never do this.

---

## ❌ Trusting JWT Without Verification

Wrong:

```text
Receive Token

↓

Read Payload

↓

Allow Request
```

Correct:

```text
Receive Token

↓

Verify Signature

↓

Check Expiration

↓

Allow Request
```

Always verify first.

---

## ❌ Using a Weak Secret

Bad:

```text
secret123
```

Use a long, randomly generated secret stored securely in environment variables or a secret manager.

---

## ❌ Putting Too Much Data in JWT

JWTs should stay small.

Only include information needed for authentication and authorization.

---

# Best Practices

- Always verify the signature.
    
- Always check expiration.
    
- Keep payload minimal.
    
- Never store sensitive information in the payload.
    
- Protect your secret key.
    
- Keep JWT verification inside authentication middleware.

# Interview Questions

### Q1. What are the three parts of a JWT?

**Answer:**

- Header
    
- Payload
    
- Signature
    

---

### Q2. Can users read the JWT payload?

**Answer:**

Yes. A standard signed JWT is Base64URL-encoded, not encrypted, so its payload can be decoded by anyone who has the token.

---

### Q3. Why do we need a signature?

**Answer:**

The signature allows the server to detect whether the token has been modified after it was issued.

---

### Q4. Should passwords be stored in JWT?

**Answer:**

No. JWT payloads are readable. Only include the minimum claims required for authentication and authorization.

---

### Q5. What happens if a JWT expires?

**Answer:**

The server rejects it (typically with **401 Unauthorized**), and the client must obtain a new access token, usually through a refresh token flow.

# 💡 Backend Engineering Tip

A JWT is **proof of authentication**, not a miniature user database.

Think of it like a **boarding pass**:

- It contains enough information to identify the passenger and validate the trip.
    
- It does **not** contain everything about the passenger.
    
- The airline verifies that the boarding pass is genuine before allowing boarding.
    

Similarly, your backend should:

1. Verify the JWT.
    
2. Check its expiration.
    
3. Trust only verified claims.
    
4. Keep the token small and focused.
