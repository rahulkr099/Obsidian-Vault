# The Problem

Suppose Rahul logs into the Blog App.

The server issues:

```text
JWT

↓

Valid Forever
```

Sounds convenient.

But imagine Rahul's laptop is stolen.

The attacker now has:

```text
JWT

↓

Never Expires
```

The attacker can continue accessing Rahul's account indefinitely.

This is why **long-lived access tokens are dangerous**.

---

# Solution

Professional applications use **two tokens**.

```text
Access Token

+

Refresh Token
```

Each has a different purpose.

---

# Access Token

Purpose:

```text
Access Protected APIs
```

Example lifetime:

```text
15 Minutes
```

The client sends it with every protected request.

Example:

```http
Authorization: Bearer eyJhbGc...
```

---

# Refresh Token

Purpose:

```text
Generate New Access Token
```

Example lifetime:

```text
7 Days
```

The refresh token is **not** sent with every API request.

It is only used when the access token expires.

---

# Authentication Lifecycle

```text
Login

↓

Access Token (15 min)

↓

Refresh Token (7 days)

↓

Access Token Expires

↓

Use Refresh Token

↓

New Access Token

↓

Continue Using App
```

The user stays logged in without entering the password again.

---

# Login Flow

Rahul logs in.

```text
Verify Password

↓

Generate Access Token

↓

Generate Refresh Token

↓

Return Both Tokens
```

Authentication is complete.

---

# Normal API Request

When Rahul requests:

```http
GET /api/posts
```

The browser sends:

```text
Access Token
```

Server:

```text
Verify JWT

↓

Valid?

↓

Return Posts
```

Notice:

The refresh token is not used here.

---

# Access Token Expires

After 15 minutes:

```text
Access Token

↓

Expired
```

Server responds:

```http
401 Unauthorized
```

The frontend now knows it needs a new access token.

---

# Refresh Flow

Frontend sends:

```http
POST /api/auth/refresh
```

Including the refresh token.

Server:

```text
Verify Refresh Token

↓

Valid?

↓

Generate New Access Token

↓

Return Access Token
```

The user never sees this process.

This is called **silent authentication**.

---

```text
   │
   ▼

(15 Minutes)
   │
   ▼

   ▼
Refresh Token
   │
   ▼

```

# Why Use Two Tokens?

Suppose an attacker steals:

```text
Access Token
```

Worst case:

```text
15 Minutes
```

After that:

```text
Token Expires

↓

Cannot Be Used
```

This limits the damage.

---

# Why Not Use Refresh Token Everywhere?

Because refresh tokens are much more powerful.

If stolen:

```text
Refresh Token

↓

Generate Unlimited Access Tokens
```

Therefore:

Refresh tokens should be used **only** for refreshing authentication.

Never for normal API requests.

---

# Secure Token Storage

## Access Token

Common choices:

```text
Memory

OR

Secure Cookie
```

Many SPAs keep it in memory to reduce persistence after a page closes.

---

## Refresh Token

Best practice:

```text
HttpOnly Cookie
```

Why?

JavaScript cannot read an HttpOnly cookie.

This reduces the risk of token theft through XSS attacks.

---

# Refresh Token Rotation

Professional applications often replace the refresh token every time it's used.

Workflow:

```text
Refresh Token A

↓

Used

↓

Invalidate A

↓

Generate Refresh Token B
```

Now:

```text
Old Token

↓

Rejected
```

This is called **refresh token rotation**.

It limits the usefulness of a stolen refresh token.

---

# Logout

What should happen when Rahul logs out?

```text
Delete Access Token

↓

Invalidate Refresh Token

↓

Clear Cookies

↓

Logout Complete
```

Simply deleting the access token on the client is not enough if the refresh token remains valid.

---

# Token Revocation

Sometimes the backend must invalidate tokens before they expire.

Examples:

- Password changed
    
- Account disabled
    
- User manually logs out
    
- Refresh token suspected to be stolen
    

Workflow:

```text
Refresh Token

↓

Revoked

↓

Future Refresh Requests

↓

Rejected
```

This prevents continued access.

# Authentication Middleware

For protected APIs:

```text
Read Access Token

↓

Verify JWT

↓

Authenticated
```

Notice:

The middleware does **not** verify refresh tokens.

Refresh tokens are only verified by the refresh endpoint.

# Common Beginner Mistakes

## ❌ Long-Lived Access Tokens

Bad:

```text
Access Token

↓

1 Year
```

A stolen token remains useful for too long.

---

## ❌ Using Refresh Token for Every Request

Wrong:

```text
Protected API

↓

Refresh Token
```

Only use access tokens for normal API requests.

---

## ❌ Never Rotating Refresh Tokens

Bad:

```text
Same Refresh Token

↓

Forever
```

Rotation provides additional protection if a refresh token is compromised.

---

## ❌ Storing Refresh Tokens in Local Storage

Local storage is accessible to JavaScript.

A common production approach is to store refresh tokens in **HttpOnly cookies** to reduce XSS exposure.

---

## ❌ Forgetting Logout

If refresh tokens remain valid after logout:

```text
Logout

↓

Refresh Still Works
```

The user is not truly logged out.

Always invalidate refresh tokens during logout.

---

# Best Practices

- Keep access tokens short-lived.
    
- Store refresh tokens securely (commonly in HttpOnly cookies for browser apps).
    
- Use refresh tokens only for obtaining new access tokens.
    
- Consider refresh token rotation.
    
- Invalidate refresh tokens on logout.
    
- Protect the refresh endpoint with appropriate validation and monitoring.

# Interview Questions

### Q1. Why do we use access tokens and refresh tokens?

**Answer:**

Access tokens are short-lived and used for normal API requests. Refresh tokens are longer-lived and are used only to obtain new access tokens after they expire.

---

### Q2. Why not make access tokens valid for one year?

**Answer:**

If an attacker steals a long-lived access token, they can use it until it expires. Short-lived access tokens reduce the impact of token theft.

---

### Q3. Should refresh tokens be sent with every request?

**Answer:**

No. Refresh tokens should only be sent to the refresh endpoint when a new access token is needed.

---

### Q4. What is refresh token rotation?

**Answer:**

Each time a refresh token is used successfully, the server invalidates the old refresh token and issues a new one. This helps reduce the risk of replay attacks if a refresh token is stolen.

---

### Q5. Where should refresh tokens be stored in browser applications?

**Answer:**

A common production practice is to store them in **HttpOnly, Secure cookies** so they are not directly accessible to JavaScript.

# 💡 Backend Engineering Tip

For a typical **MERN Blog App**, a widely used production architecture is:

```text
Login

↓

Access Token (JWT)

↓

Stored in Memory

↓

Refresh Token

↓

Stored in HttpOnly + Secure Cookie

↓

Authentication Middleware

↓

Protected APIs
```

This approach balances user experience with security by keeping access tokens short-lived while allowing seamless re-authentication through refresh tokens.
