# Why Verify Email Addresses?

Imagine Rahul registers with:

```text
rahul@example.com
```

But what if Rahul accidentally types:

```text
rahul@gamil.com
```

Or a malicious user registers using someone else's email.

Without verification:

- Password reset won't work.
    
- Important emails go to the wrong person.
    
- Fake accounts increase.
    
- Communication becomes unreliable.
    

Email verification confirms:

> **The user actually owns the email address they registered with.**

```text
↓
```


This is the workflow used by many production applications.

# Step 1 — User Registers

Rahul fills out:

```text
Name

Email

Password
```

Backend:

```text
Validate

↓

Hash Password

↓

Create User
```

After creating the user:

```text
emailVerified = false
```

---

# Step 2 — Generate Verification Token

Generate a secure random token.

Example:

```text
A8F2X9P4LQ...
```

This token should be:

- Random
    
- Hard to guess
    
- Single use
    

Never generate predictable tokens like:

```text
123456
```

---

# Step 3 — Store the Token

A common production approach is:

```text
Generate Token

↓

Hash Token

↓

Store Hash
```

Why?

If the database leaks:

Attackers cannot use the original verification token.

This follows the same principle as password hashing.

---

# Step 4 — Set Expiration

Verification tokens should expire.

Example:

```text
Generated

↓

Valid for 24 Hours
```

After expiration:

```text
Reject Verification
```

The user must request a new verification email.

---

# Step 5 — Send Email

Example email:

```text
Welcome Rahul!

Click below to verify your email.

https://example.com/verify-email?token=abc123
```

The link contains the verification token.

---

# Step 6 — User Clicks the Link

Browser requests:

```http
GET /api/auth/verify-email?token=abc123
```

Backend:

```text
Read Token

↓

Hash Token

↓

Find Matching Record

↓

Check Expiration
```

If everything is valid:

Continue.

---

# Step 7 — Verify Email

Backend updates:

```text
emailVerified

↓

true
```

It also removes the verification token.

Now:

```text
User Verified
```

The token cannot be reused.

# One-Time Use Tokens

Suppose Rahul clicks:

```text
Verification Link
```

The backend verifies it.

If Rahul clicks the same link again:

```text
Token Already Used

↓

Reject
```

Verification tokens should be single-use.

---

# Expired Token

Suppose Rahul waits:

```text
3 Days
```

The token has expired.

Flow:

```text
Verify Token

↓

Expired

↓

Reject
```

Response:

```json
{
  "message": "Verification link has expired."
}
```

---

# Resend Verification Email

Sometimes users lose the email.

Workflow:

```text
Resend Request

↓

Generate New Token

↓

Invalidate Old Token

↓

Send New Email
```

Never keep multiple valid verification tokens for the same user.

# Common Beginner Mistakes

## ❌ Allowing Login Before Verification

Bad:

```text
Register

↓

Immediate Login
```

If your application requires verified emails, always enforce that check consistently.

---

## ❌ Never Expiring Tokens

Bad:

```text
Verification Token

↓

Valid Forever
```

Always set an expiration time.

---

## ❌ Reusing Tokens

Wrong:

```text
Verify

↓

Still Valid
```

Verification tokens should become invalid after successful use.

---

## ❌ Storing Raw Tokens

Bad:

```text
Database

↓

Original Token
```

Prefer storing a **hashed version** of the token.

---

## ❌ Sending Multiple Active Tokens

Wrong:

```text
Token A

Token B

Token C
```

Better:

```text
Invalidate Old

↓

Generate New
```

Only one verification token should be active at a time.

---

# Best Practices

- Require email verification for applications where email ownership matters.
    
- Generate cryptographically secure random verification tokens.
    
- Store hashed verification tokens.
    
- Set token expiration.
    
- Make verification tokens one-time use.
    
- Invalidate old tokens when sending a new verification email.
    
- Separate email sending into its own service.

# Interview Questions

### Q1. Why verify email addresses?

**Answer:**

To confirm that the user owns the email address, reduce fake accounts, and ensure features like password reset and important notifications work correctly.

---

### Q2. Should verification tokens expire?

**Answer:**

Yes. Expiration limits the usefulness of stolen or forgotten verification links.

---

### Q3. Why store hashed verification tokens?

**Answer:**

If the database is compromised, attackers cannot use the original verification token because only its hash is stored.

---

### Q4. Can a verification token be reused?

**Answer:**

No. After successful verification, the token should be invalidated so it cannot be used again.

# 💡 Backend Engineering Tip

Think of email verification as a **proof of communication**, not just a security feature.

It confirms that:

- The user controls the email address.
    
- Future emails (password resets, security alerts, notifications) can reach the correct recipient.
    
- Your application has a reliable communication channel with the user.
