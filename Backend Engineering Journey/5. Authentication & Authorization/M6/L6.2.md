# Why Password Reset is Important

Imagine Rahul forgets his password.

He cannot log in.

Without a password reset feature:

```text
Forgot Password

↓

No Recovery

↓

Account Lost
```

A password reset system allows Rahul to regain access securely.

---

# Password Change vs Password Reset

Many beginners confuse these two.

## Password Change

The user knows the current password.

```text
Current Password

↓

Verify

↓

New Password

↓

Update
```

---

## Password Reset

The user has forgotten the password.

```text
Forgot Password

↓

Verify Email Ownership

↓

Set New Password
```

No current password is required because identity is verified through a reset token.

# Step 1 — User Requests Password Reset

Rahul clicks:

```text
Forgot Password
```

Frontend sends:

```http
POST /api/auth/forgot-password
```

Example:

```json
{
  "email": "rahul@example.com"
}
```

---

# Step 2 — Validate Email

Backend checks:

```text
Valid Email Format?
```

If invalid:

```text
400 Bad Request
```

Otherwise:

Continue.

---

# Step 3 — Prevent User Enumeration

Suppose Rahul exists.

Suppose Aman doesn't.

Bad responses:

```text
Email Not Found
```

or

```text
Reset Email Sent
```

Attackers can discover valid accounts.

Instead:

Always return:

```json
{
  "message": "If an account exists, a password reset email has been sent."
}
```

Whether the email exists or not.

---

# Step 4 — Generate Reset Token

Generate a cryptographically secure random token.

Example:

```text
Y8K1MN4P...
```

Requirements:

- Random
    
- Difficult to guess
    
- One-time use
    

Never use predictable values like:

```text
123456
```

---

# Step 5 — Store the Token

Don't store:

```text
Original Token
```

Instead:

```text
Hash Token

↓

Store Hash
```

This follows the same principle as password hashing.

---

# Step 6 — Set Expiration

Reset tokens should expire quickly.

Example:

```text
15 Minutes
```

or

```text
30 Minutes
```

Long-lived reset tokens increase security risk.

---

# Step 7 — Send Reset Email

Example:

```text
Hello Rahul,

Click below to reset your password.

https://example.com/reset-password?token=abc123
```

The email contains the original token.

Only its hash is stored in the database.

---

# Step 8 — User Clicks the Link

Browser sends:

```http
POST /api/auth/reset-password
```

Example:

```json
{
  "token": "abc123",
  "newPassword": "NewPassword123!"
}
```

---

# Step 9 — Verify Reset Token

Backend performs:

```text
Hash Incoming Token

↓

Find Matching Hash

↓

Expired?

↓

Already Used?

↓

Continue
```

Only valid tokens are accepted.

---

# Step 10 — Update Password

Backend:

```text
Validate Password

↓

Hash Password

↓

Update User
```

Never store:

```text
New Password
```

Store only its hash.

---

# Step 11 — Remove Reset Token

After success:

```text
Delete Reset Token
```

The token cannot be reused.

---

# Step 12 — Invalidate Sessions

Suppose Rahul's password was stolen.

The attacker already has:

```text
Refresh Token
```

If Rahul changes the password:

The attacker should immediately lose access.

Backend:

```text
Password Changed

↓

Revoke Refresh Tokens

↓

Require New Login
```

This is an important production security practice.

# Should Old Passwords Still Work?

No.

Immediately after:

```text
Password Updated
```

The old password becomes invalid.

Future logins require:

```text
New Password
```

# What Happens if the Token Expires?

Example:

```text
Generated

↓

30 Minutes

↓

Expired
```

Result:

```text
Reject Request
```

User must request a new reset email.

# One-Time Use

Good:

```text
Reset Password

↓

Delete Token
```

Bad:

```text
Reset Password

↓

Token Still Valid
```

Reset tokens should never be reusable.

---

# Common Beginner Mistakes

## ❌ Returning "Email Not Found"

Bad:

```json
{
  "message": "Email not found."
}
```

This enables user enumeration.

---

## ❌ Storing Raw Tokens

Bad:

```text
Database

↓

Original Reset Token
```

Prefer storing only a hash.

---

## ❌ Never Expiring Reset Tokens

Bad:

```text
Valid Forever
```

Always set an expiration.

---

## ❌ Not Invalidating Sessions

Bad:

```text
Password Changed

↓

Old Refresh Tokens Still Work
```

Always revoke active sessions after a successful password reset.

---

## ❌ Weak Password Validation

The new password should follow the same password policy used during registration.

---

# Best Practices

- Return generic responses for forgot-password requests.
    
- Generate cryptographically secure random tokens.
    
- Store hashed reset tokens.
    
- Expire reset tokens quickly.
    
- Make reset tokens single-use.
    
- Hash the new password before storing it.
    
- Revoke refresh tokens after password reset.
    
- Log password reset events (but never passwords or reset tokens).

# Interview Questions

### Q1. Why shouldn't the backend return "Email not found" during password reset?

**Answer:**

Because it allows attackers to determine which email addresses are registered. A generic response prevents user enumeration.

---

### Q2. Why store hashed reset tokens?

**Answer:**

If the database is compromised, attackers cannot use the original reset tokens because only their hashes are stored.

---

### Q3. Why should reset tokens expire?

**Answer:**

Short-lived tokens reduce the window in which a stolen reset link can be abused.

---

### Q4. Why revoke refresh tokens after a password reset?

**Answer:**

A password reset may indicate that the account was compromised. Revoking refresh tokens forces all active sessions to re-authenticate, preventing continued access with previously issued tokens.

# 💡 Backend Engineering Tip

Think of a password reset as a **high-security operation**, not just a form submission.

A secure password reset should always:

```text
Verify Identity

↓

Verify Reset Token

↓

Hash New Password

↓

Delete Reset Token

↓

Revoke Sessions

↓

Require Fresh Authentication
```

This sequence protects the user's account even if it was previously compromised.
