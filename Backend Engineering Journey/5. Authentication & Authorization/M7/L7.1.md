# Lesson 7.1 — Authentication Middleware

> **Goal:** Learn how professional backend applications authenticate every protected request using middleware, verify JWTs securely, and attach the authenticated user to the request before any business logic runs.

# The Problem

Suppose Rahul wants to create a blog post.

Frontend sends:

```http
POST /api/posts
```

Should every controller do this?

```text
Read JWT

↓

Verify JWT

↓

Extract User

↓

Continue
```

Imagine you have:

- 20 controllers
    
- 100 protected routes
    

You would repeat the same authentication code everywhere.

That's bad design.

---

# The Solution

Move authentication into **middleware**.

Instead of:

```text
Controller

↓

Verify JWT
```

Use:

```text
Authentication Middleware

↓

Controller
```

Now every protected route automatically verifies the user.

---

# What is Middleware?

Middleware is a function that runs **before** the controller.

Example:

```text
Request

↓

Middleware

↓

Controller

↓

Response
```

Middleware can:

- Read the request.
    
- Modify the request.
    
- Stop the request.
    
- Continue the request.
    

Authentication is a perfect use case.

---

# Protected vs Public Routes

Not every route requires authentication.

## Public Routes

Examples:

```text
POST /login

POST /register

POST /forgot-password

GET /posts
```

Anyone can access them.

---

## Protected Routes

Examples:

```text
POST /posts

PUT /posts/:id

DELETE /posts/:id

GET /profile
```

Only authenticated users can access these.

---

# Step 1 — Read the Access Token

The middleware first looks for the token.

Example:

```http
Authorization:
Bearer eyJhbGc...
```

Workflow:

```text
Request

↓

Read Authorization Header

↓

Extract Token
```

If the token is missing:

```text
Reject
```

---

# Step 2 — Verify the JWT

Now verify:

```text
JWT

↓

Signature

↓

Expiration

↓

Valid?
```

If verification succeeds:

Continue.

Otherwise:

Reject.

---

# Step 3 — Extract User Information

After verification:

JWT payload:

```json
{
  "userId": "66fa...",
  "role": "author"
}
```

Middleware extracts:

```text
User ID

Role
```

---

# Step 4 — Attach User to Request

Instead of decoding the JWT again later:

Middleware attaches:

```javascript
req.user = {
    userId: "...",
    role: "author"
}
```

Now every controller can access:

```javascript
req.user
```

without verifying the token again.

---

# Step 5 — Continue the Request

If authentication succeeds:

```text
Authentication

↓

Success

↓

next()
```

Controller executes.

# Invalid Token

Suppose the token is modified.

```text
JWT

↓

Signature Invalid
```

Response:

```http
401 Unauthorized
```

Never continue.

---

# Expired Token

Suppose:

```text
Access Token

↓

Expired
```

Middleware:

```text
Reject

↓

401 Unauthorized
```

Frontend should then use the refresh token to obtain a new access token.

# What Should Middleware Do?

Authentication middleware should:

✔ Read token

✔ Verify token

✔ Check expiration

✔ Extract user

✔ Attach `req.user`

✔ Call `next()`

---

# What Should Middleware NOT Do?

Authentication middleware should **not**:

❌ Query business data

❌ Create blog posts

❌ Update database records

❌ Check post ownership

❌ Decide user permissions

Those belong elsewhere.

---

# Authentication vs Authorization

Authentication middleware answers:

```text
Who is this user?
```

Authorization answers:

```text
Can this user perform this action?
```

Example:

```text
Authentication

↓

Rahul

↓

Authorization

↓

Can Rahul delete this post?
```

These are separate responsibilities.

# Common Beginner Mistakes

## ❌ Verifying JWT Inside Controllers

Bad:

```text
Controller

↓

Verify JWT

↓

Business Logic
```

Authentication becomes duplicated.

---

## ❌ Not Calling next()

Suppose:

```text
Authentication Success
```

But:

```text
next()

↓

Missing
```

The request never reaches the controller.

---

## ❌ Trusting Client Data

Bad:

```json
{
    "userId": "...",
    "role": "admin"
}
```

Never trust values sent by the client.

Always trust:

```text
Verified JWT
```

---

## ❌ Mixing Authorization into Authentication Middleware

Bad:

```text
Verify JWT

↓

Delete Post
```

Authentication should not make authorization decisions.

Keep them separate.

---

## ❌ Returning Different Error Messages

Bad:

```text
Token Expired
```

```text
Invalid Signature
```

Detailed errors are useful for logs, but be careful about exposing unnecessary information to clients. A consistent authentication failure response is often sufficient.

---

# Best Practices

- Protect all sensitive routes with authentication middleware.
    
- Verify JWT before accessing its payload.
    
- Attach authenticated user information to `req.user`.
    
- Keep middleware focused only on authentication.
    
- Return **401 Unauthorized** for authentication failures.
    
- Let authorization happen in a separate layer.

# Interview Questions

### Q1. Why use authentication middleware?

**Answer:**

To centralize authentication logic, avoid code duplication, and ensure every protected request is verified before reaching business logic.

---

### Q2. Should controllers verify JWTs?

**Answer:**

No. JWT verification belongs in authentication middleware. Controllers should rely on the authenticated user attached to `req.user`.

---

### Q3. What is stored in `req.user`?

**Answer:**

Information extracted from the verified JWT (and optionally enriched from the database), such as the user's ID and role.

---

### Q4. What's the difference between authentication and authorization middleware?

**Answer:**

Authentication verifies **who the user is**. Authorization checks **whether that authenticated user is allowed to perform the requested action**.

# 💡 Backend Engineering Tip

Think of authentication middleware as the **security gate** of your backend.

Every protected request should follow this pipeline:

```text
Client Request

↓

Authentication Middleware

↓

Verified User

↓

Authorization

↓

Business Logic

↓

Database
```

If authentication fails, **nothing beyond the middleware should execute**. This separation keeps your backend secure, maintainable, and easy to extend.
