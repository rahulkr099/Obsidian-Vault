# Why Cookies Matter

Imagine Rahul logs into your Blog App.

The server issues:

```text
Access Token

↓

Refresh Token
```

Question:

> **Where should these tokens be stored?**

Common options:

```text
Memory

Local Storage

Session Storage

Cookies
```

Each option has trade-offs.

For browser applications, **refresh tokens are commonly stored in secure cookies**.

# What is a Cookie?

A cookie is a small piece of data that a server asks the browser to store.

Example:

```text
Server

↓

Set Cookie

↓

Browser Stores Cookie
```

Later:

```text
Browser

↓

Automatically Sends Cookie

↓

Server
```

This happens automatically.

---

# Login Example

Rahul logs in.

Server response:

```text

```

Browser stores:

```text

```

On the next request:

```text
Browser

↓

Automatically Sends Cookie
```

The frontend does not have to manually attach it.

# Cookie Attributes

Cookies are much more than:

```text
name=value
```

They also have security settings.

The three most important are:

```text
HttpOnly

Secure

SameSite
```

---

# HttpOnly

This is one of the most important cookie settings.

Example:

```text
HttpOnly = true
```

Meaning:

JavaScript **cannot read** the cookie.

---

# Without HttpOnly

Suppose your website has an XSS vulnerability.

Attacker's script:

```javascript
document.cookie
```

If refresh tokens are accessible:

```text
Refresh Token Stolen
```

---

# With HttpOnly

JavaScript tries:

```javascript
document.cookie
```

Browser:

```text
HttpOnly Cookie

↓

Not Accessible
```

The refresh token stays protected.

---

# Secure

Example:

```text
Secure = true
```

Meaning:

The browser only sends the cookie over:

```text
HTTPS
```

Never over:

```text
HTTP
```

This helps prevent token exposure over unencrypted connections.

---

# SameSite

SameSite controls **when the browser sends cookies with cross-site requests**.

There are three modes.

---

# SameSite = Strict

```text
Only Same Site
```

Example:

Rahul visits:

```text
blogapp.com
```

Cookie sent:

```text
Yes
```

If another website tries to send a request:

```text
evil.com

↓

blogapp.com
```

Cookie:

```text
Not Sent
```

Very secure.

But it may affect some user flows.

---

# SameSite = Lax

This is a balanced option.

Most normal navigation works.

Cross-site POST requests are more restricted.

Many applications use this as a sensible default.

---

# SameSite = None

```text
Send Cookie Everywhere
```

Required when:

- Frontend and backend are on different sites/domains.
    
- Third-party authentication flows.
    

Important:

If:

```text
SameSite=None
```

Then browsers require:

```text
Secure=true
```

Otherwise the cookie may be rejected.

---

# Cookie Lifetime

Cookies can expire.

Example:

```text
7 Days
```

After expiration:

```text
Browser Deletes Cookie
```

This is independent of JWT expiration.

---

# Where Should Tokens Be Stored?

## Access Token

Common options:

```text
Memory
```

or

```text
Short-Lived Cookie
```

Keeping access tokens in memory is common for SPAs because they disappear when the page is refreshed or closed.

---

## Refresh Token

Production recommendation:

```text
HttpOnly Cookie

+

Secure

+

SameSite
```

This provides strong protection in browser-based applications.

---

# Why Not Store Refresh Tokens in Local Storage?

Suppose an XSS attack occurs.

Attacker runs:

```javascript
localStorage.getItem(...)
```

If the refresh token is stored there:

```text
Refresh Token Stolen
```

An HttpOnly cookie helps reduce this risk because JavaScript cannot directly access it.

# CSRF (Cross-Site Request Forgery)

Cookies introduce another security consideration.

Imagine Rahul is logged into:

```text
blogapp.com
```

Without logging out, he visits:

```text
evil.com
```

If the browser automatically sends cookies to `blogapp.com` from that malicious site, the attacker may try to trigger unwanted actions.

This type of attack is called:

```text
CSRF
```

---

# How SameSite Helps

If:

```text
SameSite = Strict
```

Cross-site requests do not include the cookie.

The attack becomes much harder.

SameSite is one layer of defense against CSRF.

---

# Production Cookie Configuration

A typical production refresh token cookie:

```text
HttpOnly = true

Secure = true

SameSite = Lax

Max-Age = 7 Days
```

The exact `SameSite` value depends on your frontend and backend deployment.

# Common Beginner Mistakes

## ❌ Storing Refresh Tokens in Local Storage

Bad:

```text
localStorage
```

Prefer:

```text
HttpOnly Cookie
```

---

## ❌ Forgetting Secure

Bad:

```text
HTTP
```

Production applications should use HTTPS and `Secure` cookies.

---

## ❌ Using SameSite=None Without Secure

Modern browsers generally reject:

```text
SameSite=None

Secure=false
```

---

## ❌ Storing Sensitive Data in Cookies

Cookies should contain:

- Session IDs
    
- Refresh tokens
    

Not:

```text
Passwords

Credit Cards

Private Data
```

---

## ❌ Using Cookies for Everything

Remember:

Our architecture is:

```text
Access Token

↓

Authorization Header
```

Refresh:

```text
HttpOnly Cookie
```

Each has a specific purpose.

# Best Practices

- Store refresh tokens in HttpOnly cookies.
    
- Enable `Secure` in production.
    
- Choose an appropriate `SameSite` policy for your application.
    
- Use short-lived access tokens.
    
- Never store passwords in cookies.
    
- Protect applications against both XSS and CSRF.
    
- Test cookie behavior in development and production environments.

# Interview Questions

### Q1. Why use HttpOnly cookies?

**Answer:**

They prevent JavaScript from directly accessing the cookie, reducing the risk of refresh token theft through XSS attacks.

---

### Q2. What does the Secure attribute do?

**Answer:**

It ensures the browser sends the cookie only over HTTPS connections.

---

### Q3. What is SameSite used for?

**Answer:**

It controls when cookies are sent with cross-site requests and helps reduce the risk of CSRF attacks.

---

### Q4. Where should refresh tokens be stored?

**Answer:**

For browser-based applications, a common production practice is to store them in **HttpOnly, Secure cookies** with an appropriate `SameSite` policy.

---

### Q5. Should access tokens also be stored in HttpOnly cookies?

**Answer:**

There isn't a single correct answer. Some architectures store access tokens in memory and refresh tokens in HttpOnly cookies, while others store both in cookies. The best choice depends on your application's architecture, security requirements, and deployment model.

# 💡 Backend Engineering Tip

For a modern **MERN Blog App**, a widely adopted production pattern is:

```text
Access Token

↓

Memory

↓

Authorization Header

────────────────────────

Refresh Token

↓

HttpOnly Cookie

↓

Refresh Endpoint
```

This keeps normal API requests fast while protecting the long-lived refresh token with browser security features.
