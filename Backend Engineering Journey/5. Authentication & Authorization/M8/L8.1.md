# Authentication vs Authorization

These two concepts are often confused.

## Authentication

Answers:

> **Who are you?**

Example:

```text
JWT

↓

Verified

↓

Rahul
```

Authentication identifies the user.

---

## Authorization

Answers:

> **What are you allowed to do?**

Example:

```text
Rahul

↓

Delete Post

↓

Allowed?
```

Authorization decides whether the action is permitted.

---

# Simple Example

Rahul logs in.

Authentication:

```text
JWT

↓

Verified

↓

User = Rahul
```

Rahul now wants to delete a post.

Authorization:

```text
Does Rahul own the post?

↓

Yes

↓

Allow
```

Authentication happens first.

Authorization happens second.

# What is Ownership?

Ownership means:

> **Who owns this resource?**

Example:

Blog Post:

```text
Post

↓

authorId

↓

Rahul
```

Rahul owns the post.

---

# Blog App Example

Database:

```text
Post

ID: 123

authorId: Rahul
```

Rahul requests:

```http
DELETE /posts/123
```

Backend:

```text
Load Post

↓

authorId == Rahul?

↓

Yes

↓

```

```

```

```text

↓

↓

```

# Why Ownership Matters

Without ownership checks:

Rahul could delete:

```text
Aman's Post
```

Or edit:

```text
Priya's Post
```

This is a serious security issue.

---

# Where Should Ownership Checks Happen?

Many beginners put them inside controllers.

Bad:

```text
Controller

↓

Compare Owner

↓

Delete
```

Controllers become cluttered.

---

# Better Architecture

```text
Controller

↓

Service

↓

Ownership Check

↓

Repository
```

The service contains business rules.

Ownership is a business rule.

---

# Why Not Middleware?

Suppose:

```http
DELETE /posts/123
```

Middleware only knows:

```text
Rahul
```

It doesn't know:

```text
Who owns Post 123?
```

That requires loading the post from the database.

This belongs in the service layer.

# 401 vs 403

This is a common interview topic.

---

## 401 Unauthorized

Means:

```text
User Not Authenticated
```

Example:

```text
No JWT

↓

Invalid JWT

↓

Expired JWT
```

The user has not been successfully authenticated.

---

## 403 Forbidden

Means:

```text
User Authenticated

↓

Not Allowed
```

Example:

```text
Rahul

↓

Delete Someone Else's Post

↓

403
```

Authentication succeeded.

Authorization failed.

# Common Beginner Mistakes

## ❌ Skipping Ownership Checks

Bad:

```text
Delete Post

↓

No Owner Check
```

Any authenticated user can delete any post.

---

## ❌ Using 401 Instead of 403

Wrong:

```text
Authenticated

↓

403 Needed

↓

Returned 401
```

Remember:

- 401 → Authentication failed.
    
- 403 → Authorization failed.
    

---

## ❌ Checking Ownership in Repository

Bad:

```text
Repository

↓

Business Rules
```

Repositories should only access data.

Business rules belong in services.

---

## ❌ Trusting Client-Supplied Owner IDs

Bad:

```json
{
    "authorId": "rahul"
}
```

Never trust ownership information sent by the client.

Always determine ownership from:

- `req.user`
    
- Database records
    

---

# Best Practices

- Authenticate first.
    
- Load the resource.
    
- Check ownership in the service layer.
    
- Return **403 Forbidden** for authorization failures.
    
- Never trust client-provided ownership data.
    
- Keep repositories focused on database operations.

# Interview Questions

### Q1. What's the difference between authentication and authorization?

**Answer:**

Authentication identifies **who the user is**. Authorization determines **what that authenticated user is allowed to do**.

---

### Q2. Where should ownership checks be implemented?

**Answer:**

In the **service layer**, because ownership is a business rule that often requires loading resources from the database.

---

### Q3. When should you return 403 Forbidden?

**Answer:**

When the user is authenticated successfully but is not allowed to perform the requested action.

---

### Q4. Why shouldn't the client send `authorId`?

**Answer:**

Because client data can be modified. The backend should always determine ownership using the authenticated user (`req.user`) and the stored resource.

# 💡 Backend Engineering Tip

A simple rule used by many backend engineers is:

```text
Authentication

↓

"Who are you?"

────────────────

Authorization

↓

"What can you do?"

────────────────

Ownership

↓

"Is this resource yours?"
```

If you keep these three questions separate in your architecture, your code will be cleaner, easier to test, and much easier to scale.
