# The Problem with Roles

Suppose your Blog App has these roles:

```text
Admin

Author

Reader
```

This works well.

But after a few months, your company asks:

> Editors should approve posts but should not manage users.

Where do you put them?

```text
Admin

Editor

Author

Reader
```

Then another request:

> Moderators can delete comments but cannot edit posts.

Now another role:

```text
Moderator
```

Soon you have:

```text
Admin

Super Admin

Editor

Moderator

Author

Reader

Guest

Support

Manager
```

Managing roles becomes difficult.

---

# The Solution

Instead of assigning abilities directly through roles:

Assign **permissions**.

Example:

```text
post:create

post:update

post:delete

comment:delete

user:manage
```

Users (or roles) receive these permissions.

---

# What is a Permission?

A permission answers:

> **What action is allowed?**

Example:

```text
Permission

↓

post:create
```

Meaning:

The user can create blog posts.

---

# Resource : Action Pattern

A common naming convention is:

```text
resource:action
```

Examples:

```text
post:create

post:update

post:delete

comment:create

comment:delete

user:update

user:delete
```

This naming style is clear and scalable.

# Blog App Permissions

Example list:

```text

```

Every permission represents exactly one capability.

# Roles Can Still Exist

Permissions do **not** replace roles.

Instead:

```text
Role

↓

Permissions
```

Example:

Author:

```text
post:create

post:update

comment:create
```

Admin:

```text
post:create

post:update

post:delete

comment:delete

user:manage
```

Roles become groups of permissions.

# Ownership Still Matters

Suppose Rahul has:

```text
post:update
```

Can Rahul edit:

```text
Aman's Post?
```

Not necessarily.

Service:

```text
Permission

↓

Ownership

↓

Allow
```

Permissions define capability.

Ownership defines **which resource**.

# Where Should Permissions Be Stored?

For a small Blog App:

Permissions may be derived from the user's role.

For larger applications:


# Common Beginner Mistakes

## ❌ Creating Too Many Roles

Bad:

```text
Admin

Editor

Senior Editor

Junior Editor

Assistant Editor

...
```

Often a few roles plus permissions scale much better.

---

## ❌ Naming Permissions Poorly

Bad:

```text
delete

create

edit
```

Better:

```text
post:delete

comment:create

user:update
```

Resource + action is much clearer.

---

## ❌ Skipping Ownership

Permission:

```text
post:update
```

does not automatically mean:

```text
Update Every Post
```

Ownership rules still apply unless a broader permission explicitly allows otherwise.

---

## ❌ Mixing Authentication and Permission Checks

Bad:

```text
Verify JWT

↓

Permission Logic

↓

Business Logic
```

Keep each concern separate.

---

## ❌ Hardcoding Permissions Everywhere

Avoid:

```text
if(permission...)

if(permission...)

if(permission...)
```

Centralize permission checks in reusable middleware or authorization utilities.

---

# Best Practices

- Use a consistent `resource:action` naming convention.
    
- Keep permissions small and specific.
    
- Group permissions into roles when appropriate.
    
- Combine permissions with ownership checks.
    
- Keep permission checks separate from business logic.
    
- Return **403 Forbidden** for authorization failures.

# Interview Questions

### Q1. What's the difference between roles and permissions?

**Answer:**

Roles are collections of permissions. Permissions define specific actions a user is allowed to perform.

---

### Q2. Why use permissions instead of only roles?

**Answer:**

Permissions provide finer control and make it easier to support complex business requirements without creating a large number of roles.

---

### Q3. Can roles and permissions be used together?

**Answer:**

Yes. In many applications, roles are simply groups of permissions, combining the simplicity of roles with the flexibility of permissions.

---

### Q4. Do permissions replace ownership checks?

**Answer:**

No. Permissions determine **what actions** are allowed, while ownership determines **which resources** the user may act on.

# 💡 Backend Engineering Tip

Think of authorization as **layers of decision-making**:

```text
Authentication

↓

Who is the user?

────────────────

Permissions

↓

Can they perform this action?

────────────────

Ownership

↓

Can they perform it on THIS resource?

────────────────

Business Rules

↓

Does the current application state allow it?
```

For example, deleting a blog post might require:

- A valid authenticated user.
    
- The `post:delete` permission **or** an admin role.
    
- Ownership of the post (unless the user has global delete permission).
    
- The post not being locked or archived.
    

Each layer answers a different question, making your authorization system flexible, secure, and easy to maintain.
