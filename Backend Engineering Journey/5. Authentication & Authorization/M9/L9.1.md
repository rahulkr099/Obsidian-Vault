# Module 9 — Email Verification

# Lesson 9.1 — Email Verification Architecture

> **Goal:** Learn how to design a secure email verification system used in production backend applications.

Email verification is **not** about sending an email.

It's about answering one important question:

> **Does this user actually own this email address?**

---

- Avoid common design mistakes.

# Why Verify Email?

Imagine your Blog App allows anyone to register.

Rahul enters:

```text
rahul@example.com
```

But Aman registers using:

```text
rahul@example.com
```

If you don't verify ownership:

```text
Fake Registration

↓

Account Created

↓

Rahul Can No Longer Register
```

This creates security and usability problems.

---

# Goals of Email Verification

Email verification ensures that:

- The email address belongs to the user.
    
- The user can receive emails.
    
- Password reset emails reach the correct person.
    
- Notifications are delivered correctly.
    
- Fake accounts are reduced.
    

---

# Blog App Workflow

A professional workflow looks like this:

```text
Register

↓

Validate Input

↓

Hash Password

↓

Create User

↓

Generate Verification Token

↓

Send Verification Email

↓

Return Success
```

Notice:

The account is created **before** email verification.

↓

This makes the workflow easier to reason about.

# Can Unverified Users Log In?

There isn't one correct answer.

Common approaches:

### Option 1 — No Login Until Verified

```text
Register

↓

Verify Email

↓

Login
```

Very secure.

Common in banking and enterprise applications.

---

### Option 2 — Login Allowed, Features Restricted

```text
Register

↓

Login

↓

Limited Access

↓

Verify Email

↓

Full Access
```

Common in SaaS products.

---

### Blog App Decision

For our Blog App:

```text
Register

↓

Verify Email

↓

Login Allowed
```

This keeps the authentication flow simple.

---

# Verification is NOT Authentication

Authentication:

```text
Who are you?
```

Verification:

```text
Do you own this email?
```

These are different concepts.

A user may have:

```text
Correct Password

↓

Authenticated

↓

Email Not Verified
```

Authentication succeeds.

Verification still fails.

# Email Verification vs Email Validation

These are different.

### Email Validation

Checks:

```text
Correct Email Format
```

Example:

```text
rahul@example.com
```

---

### Email Verification

Checks:

```text
Does Rahul Actually Own It?
```

Validation happens immediately.

Verification happens later.

# Where Does Verification Logic Belong?

Following our architecture:

```text
Route

↓

Controller

↓

User Service

↓

User Repository

↓

Database
```

The **User Service** should handle:

- Creating verification tokens.
    
- Updating verification status.
    
- Applying verification business rules.
    

The repository should only persist data.

# Common Design Decisions

Before implementing, answer questions like:

- Can users request multiple verification emails?
    
- Does each new email invalidate the previous token?
    
- Should verification links expire?
    
- Can users change their email before verification?
    
- What happens if they click the same link twice?
    

Professional systems define these behaviors upfront.

---

# Common Beginner Mistakes

## ❌ Trusting the Email Without Verification

Bad:

```text
Register

↓

Account Active
```

Anyone can register with someone else's email.

---

## ❌ Mixing Verification with Login

Keep them separate.

```text
Authentication

↓

Identity
```

```text
Verification

↓

Email Ownership
```

---

## ❌ Sending Email from Controllers

Bad:

```text
Controller

↓

SMTP Logic
```

Use a dedicated email service.

---

## ❌ No Resend Option

Users may never receive the first email.

Always provide a secure resend mechanism.

---

## ❌ No Expiration Policy

Verification links should never remain valid indefinitely.

We'll cover secure expiration in the next lesson.

---

# Best Practices

- Create the user before sending the verification email.
    
- Keep verification separate from authentication.
    
- Store the verification status in the user record.
    
- Handle email sending through a dedicated service.
    
- Plan for expired links and resending emails.
    
- Define verification policies before implementation.

# Interview Questions

### Q1. Why is email verification important?

**Answer:**

It proves that the user owns the email address, reduces fake accounts, and ensures important emails such as password resets and notifications reach the correct person.

---

### Q2. Should email verification happen before or after user creation?

**Answer:**

In most applications, the user record is created first in a pending verification state. After successful verification, the account is activated.

---

### Q3. Is email verification part of authentication?

**Answer:**

No. Authentication verifies the user's identity, while email verification confirms ownership of the registered email address.

---

### Q4. Where should email verification logic be implemented?

**Answer:**

In the service layer, because generating verification tokens, updating account status, and applying verification policies are business rules.
