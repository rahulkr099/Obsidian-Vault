# Why Error Handling Matters

Imagine Rahul requests:

```http

```

But the post doesn't exist.

Without error handling:

```text

↓

↓
```

This creates inconsistent APIs and makes debugging difficult.

# Types of Errors

Backend applications generally deal with two categories.

---

## 1. Operational Errors

Expected errors.

Examples:

- Invalid input
    
- User not found
    
- Invalid password
    
- JWT expired
    
- Forbidden request
    
- Resource not found
    

These are part of normal application behavior.

---

## 2. Programmer Errors

Unexpected bugs.

Examples:

```text
Undefined Variable

Null Reference

Syntax Error

Wrong Function Call
```

These indicate problems in the application's code.

# Error Response Structure

Professional APIs often return a consistent format.

Example:

```json
{
    "success": false,
    "message": "Validation failed."
}
```

Sometimes additional information is included:

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": []
}
```

The format stays consistent across the application.

# Development vs Production

During development:

Developers often need:

- Stack trace
    
- File name
    
- Line number
    

During production:

Clients should receive:

```json
{
    "success": false,
    "message": "Something went wrong."
}
```

Sensitive implementation details should stay on the server.

---

# Logging

Error responses are for clients.

Logs are for developers.

Example log:

```text
Time

Route

User ID

Stack Trace
```

Logs help diagnose issues without exposing internal details to users.

# Common Beginner Mistakes

## ❌ try...catch Everywhere

Bad:

```text
Controller A

try...

Controller B

try...

Controller C

try...
```

This leads to duplicated error handling.

Use centralized error middleware instead.

---

## ❌ Returning Different Error Formats

Bad:

```json
{
    "error": "..."
}
```

Another endpoint:

```json
{
    "message": "..."
}
```

Use one consistent response format.

---

## ❌ Returning 500 for Everything

Not every error is a server error.

Example:

```text
Missing Title

↓

400
```

Not:

```text
500
```

---

## ❌ Exposing Stack Traces

Bad production response:

```text
Stack Trace

File Paths

Database Details
```

Never expose internal implementation details to API consumers.

---

## ❌ Ignoring Error Logging

Returning an error without logging it makes debugging production problems much harder.

---

# Best Practices

- Create a custom `AppError` class.
    
- Centralize error handling.
    
- Use appropriate HTTP status codes.
    
- Return consistent JSON responses.
    
- Log errors on the server.
    
- Hide implementation details in production.
    
- Keep controllers focused on business logic.

# Interview Questions

### Q1. Why use a custom `AppError` class?

**Answer:**

It allows you to include useful metadata such as an HTTP status code and message, making error handling consistent across the application.

---

### Q2. Why centralize error handling?

**Answer:**

It eliminates duplicated error formatting, keeps controllers clean, and ensures every endpoint returns errors in a consistent format.

---

### Q3. Should stack traces be returned to clients?

**Answer:**

No. Stack traces should be logged internally but not exposed in production responses because they may reveal sensitive implementation details.

---

### Q4. What's the difference between an operational error and a programmer error?

**Answer:**

Operational errors are expected application conditions (such as invalid input or missing resources). Programmer errors are bugs in the code, such as null references or incorrect logic.
