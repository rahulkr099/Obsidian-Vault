# What is a Verification Token?

A verification token is a **temporary secret** sent to the user's email.

Example:

```text
Rahul Registers

↓

Generate Token

↓

Send Email

↓

User Clicks Link

↓

Verify Token

↓

Activate Account
```

The token proves that the user has access to the email inbox.

---

# Token Lifecycle

A professional verification token follows this lifecycle:

```text
Generate Token

↓

Store Token

↓

Send Email

↓

User Clicks Link

↓

Validate Token

↓

Activate Account

↓

Delete Token
```

Notice:

The token exists only until verification is complete.

---

# Token Requirements

A verification token should be:

- Random
    
- Unpredictable
    
- Long enough
    
- Single-use
    
- Temporary
    

It should **never** be guessable.

---

# Good vs Bad Tokens

❌ Bad

```text
123456
```

```text
rahul123
```

```text
verify123
```

Easy to guess.

---

✅ Good

```text
8dF3xPq9Lk2...
```

Generated using a cryptographically secure random generator.

---

# Where Does the Token Come From?

The backend generates it.

Never allow:

```text
Client

↓

Generate Token
```

Instead:

```text
Backend

↓

Generate Secure Token
```

The server is always responsible for token generation.

---

# Verification Link

The email usually contains a link like:

```text
https://blogapp.com/verify-email?token=abc123...
```

When the user clicks:

```text
Browser

↓

Backend

↓

Verify Token
```

The backend performs all validation.

---

# Should Tokens Be Stored?

Yes.

The server needs something to compare against.

Workflow:

```text
Generate Token

↓

Store Token

↓

Send Token
```

Without storage, verification isn't possible.

---

# Plain Token vs Hashed Token

Many beginners store:

```text
Verification Token

↓

Database
```

in plain text.

Professional applications usually store:

```text
Hash(Token)

↓

Database
```

Just like passwords.

---

# Why Hash the Token?

Imagine the database is compromised.

If the token is stored as plain text:

```text
Database Leak

↓

Token Exposed

↓

Account Can Be Verified
```

If the token is hashed:

```text
Database Leak

↓

Hash Exposed

↓

Original Token Hidden
```

Hashing reduces risk if the database is exposed.

---

# Verification Flow with Hashing

```text
Generate Token

↓

Hash Token

↓

Store Hash

↓

Send Original Token

↓

User Clicks Link

↓

Hash Incoming Token

↓

Compare Hashes

↓

Activate Account
```

The original token is never stored.

---

# Token Expiration

Verification tokens should expire.

Example:

```text
Generate Token

↓

Valid For

↓

24 Hours
```

After expiration:

```text
Reject

↓

Request New Token
```

Old verification links should not remain valid forever.

---

# Why Expiration Matters

Imagine:

```text
Verification Email

↓

Still Valid

↓

3 Years Later
```

This is unnecessary and increases security risk.

Temporary tokens should remain temporary.

---

# One-Time Use Tokens

A verification token should be usable only once.

Good flow:

```text
Verify

↓

Activate Account

↓

Delete Token
```

Second attempt:

```text
Token Missing

↓

Reject
```

This prevents replay attacks.

---

# Replay Attack

Without deleting the token:

```text
Click Link

↓

Verified

↓

Click Again

↓

Still Valid
```

A token should not remain reusable after successful verification.

---

# Invalid Tokens

Suppose a user changes the URL:

```text
...?token=abcxyz
```

Backend:

```text
Token Found?

↓

No

↓

Reject
```

Never activate an account without a valid token.

---

# Multiple Verification Emails

Suppose Rahul clicks:

```text
Resend Verification
```

A good strategy:

```text
Generate New Token

↓

Invalidate Old Token

↓

Send New Email
```

Only the newest token remains valid.

---

# Verification States

```text
Pending

↓

Token Valid

↓

Verified

↓

Token Deleted
```

Simple and secure.

---

# Where Does Token Logic Belong?

Architecture:

```text
Route

↓

Controller

↓

User Service

↓

User Repository
```

The **User Service** should:

- Generate tokens
    
- Hash tokens
    
- Validate tokens
    
- Handle expiration
    
- Delete used tokens
    

The repository simply stores and retrieves data.

---

# Common Design Decisions

Before implementation, decide:

- How long should tokens remain valid?
    
- Should a new token invalidate the old one?
    
- Can verified users request another token?
    
- How many resend requests are allowed?
    

Production systems define these rules clearly.

---

# Common Beginner Mistakes

## ❌ Using Predictable Tokens

Bad:

```text
user123
```

Use cryptographically secure random tokens.

---

## ❌ Storing Tokens in Plain Text

Prefer storing hashed tokens whenever practical.

---

## ❌ Never Expiring Tokens

Bad:

```text
Valid Forever
```

Temporary tokens should expire.

---

## ❌ Allowing Unlimited Reuse

Always invalidate a verification token after successful use.

---

## ❌ Not Invalidating Old Tokens

When issuing a new verification token, invalidate the previous one.

---

# Best Practices

- Generate tokens on the backend.
    
- Use cryptographically secure random values.
    
- Store hashed tokens.
    
- Set an expiration time.
    
- Make tokens single-use.
    
- Invalidate previous tokens when creating new ones.
    
- Keep token logic inside the service layer.

# Interview Questions

### Q1. Why should verification tokens be random?

**Answer:**

Random tokens are difficult to guess, reducing the risk of unauthorized account verification.

---

### Q2. Why hash verification tokens before storing them?

**Answer:**

Hashing protects the original token if the database is compromised. The server can compare hashes without storing the original secret.

---

### Q3. Why should verification tokens expire?

**Answer:**

Expiration limits the time window in which a stolen or forgotten verification link can be misused.

---

### Q4. Why should verification tokens be single-use?

**Answer:**

Single-use tokens prevent replay attacks by ensuring a verification link cannot be reused after the account has been activated.

# 💡 Backend Engineering Tip

A good way to think about verification tokens is:

```text
Password

↓

Hash

↓

Store

────────────────

Verification Token

↓

Hash

↓

Store
```

Both are **secrets**.

The difference is:

- **Passwords** may live for years.
    
- **Verification tokens** should be **temporary**, **single-use**, and **automatically expire**.
    

This mindset helps you design secure verification systems that scale well in production.
