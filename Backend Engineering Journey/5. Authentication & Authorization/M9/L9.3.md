# The Problem


# Synchronous vs Asynchronous Errors

## Synchronous

```text
Execute Code

↓

Error

↓

Immediately Thrown
```

These are relatively easy to catch.

---

## Asynchronous

Example:

```text
Database Query

↓

Promise Rejected

↓

Unhandled
```

Modern Node.js applications perform many asynchronous operations.

These require special handling.

# The Problem with Async Controllers

Imagine:

```text
Controller

↓

await Database Query

↓

Database Error
```

Without proper handling:

```text
Unhandled Promise Rejection
```

The global error middleware may never receive the error.

---

# The Solution — asyncHandler

Instead of writing:

```text
try

↓

catch

↓

next(error)
```

inside every controller,

use a reusable wrapper.

Conceptually:

```text
Request

↓

asyncHandler

↓

Controller

↓

Error?

↓

Global Error Handler
```

This eliminates repetitive `try...catch` blocks.

# Process-Level Errors

Some errors happen outside request handling.

Examples:

```text
Unhandled Promise Rejection
```

```text
Uncaught Exception
```

These affect the Node.js process itself.

Professional applications:

- Log the error.
    
- Shut down gracefully if necessary.
    
- Restart using a process manager (for example, PM2, Docker, or Kubernetes).

# Common Beginner Mistakes

## ❌ try...catch in Every Controller

Bad:

```text
Controller A

try...

Controller B

try...

Controller C

try...
```

Use a reusable `asyncHandler`.

---

## ❌ Ignoring Promise Rejections

Bad:

```text
Promise Rejected

↓

Nothing Happens
```

Unhandled promise rejections can destabilize your application.

---

## ❌ Returning Raw Database Errors

Bad response:

```text
MongoServerError...

Collection...

Index...
```

Clients should receive clean, user-friendly messages.

---

## ❌ Logging Sensitive Data

Never log:

- Passwords
    
- JWT secrets
    
- Refresh tokens
    
- Credit card numbers
    
- Personal secrets
    

Log only what is needed for debugging.

---

## ❌ Hiding Every Error During Development

During development, detailed logs help you fix issues quickly.

In production, hide implementation details from clients.

---

# Best Practices

- Use a reusable `asyncHandler` for asynchronous controllers.
    
- Throw custom `AppError` instances for expected errors.
    
- Keep one global error middleware.
    
- Log errors on the server.
    
- Return consistent JSON responses.
    
- Hide sensitive implementation details in production.
    
- Handle process-level exceptions and promise rejections appropriately.
    
- Never expose confidential information in logs or API responses.

# Interview Questions

### Q1. Why use an `asyncHandler`?

**Answer:**

It automatically forwards asynchronous errors to the global error handler, eliminating repetitive `try...catch` blocks in controllers.

---

### Q2. Why not return raw database errors?

**Answer:**

Database errors may expose internal implementation details. Instead, convert them into user-friendly API responses and log the original error internally.

---

### Q3. What's the difference between request-level errors and process-level errors?

**Answer:**

Request-level errors occur while handling a specific HTTP request. Process-level errors affect the Node.js process itself, such as uncaught exceptions or unhandled promise rejections.

---

### Q4. Should stack traces be shown in production?

**Answer:**

No. Stack traces should be logged internally but not returned to clients because they may reveal sensitive implementation details.

# 💡 Backend Engineering Tip

A production-ready backend should have **one entry point for requests and one exit point for errors**.

Think of it like this:

```text
Incoming Request

↓

Validation

↓

Authentication

↓

Authorization

↓

Business Logic

↓

Database

────────────────

If Anything Fails

↓

Throw AppError

↓

Global Error Handler

↓

Structured Logging

↓

Consistent API Response
```

This architecture keeps your codebase clean, makes debugging much easier, and provides a consistent experience for frontend developers and API consumers.
