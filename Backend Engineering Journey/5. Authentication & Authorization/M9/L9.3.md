# Complete Registration Flow

Let's look at the complete architecture.

```text
User Registers
      │
      ▼
Validate Request
      │
      ▼
Check Duplicate Email
      │
      ▼
Hash Password
      │
      ▼
Create User
      │
      ▼
Generate Verification Token
      │
      ▼
Hash Token
      │
      ▼
Store Token + Expiration
      │
      ▼
Send Verification Email
      │
      ▼
Return Success Response
```

Notice:

The backend **does not wait** for the user to verify the email.

Registration is complete.

Verification happens later.

# Login Before Verification

If your application requires verification first:

```text

↓

↓

↓

↓

```

# Expired Token

Suppose the token expired.

```text
Verify Token

↓

Expired

↓

Reject

↓

Ask User To Resend Verification Email
```

Never extend an expired token.

Generate a new one.

---

# Invalid Token

User modifies the URL:

```text
...?token=abcdef
```

Backend:

```text
Find Token

↓

Not Found

↓

Reject
```

Never activate an account without a valid token.

# Already Verified User

Suppose Rahul clicks the same link again.

Flow:

```text
Account Already Verified

↓

Return Informative Response
```

No changes are made.

The operation should remain safe.

# Resend Verification Flow

Users often request another email.

Workflow:

```text
Pending Verification

↓

Resend Request

↓

Generate New Token

↓

Hash Token

↓

Replace Old Token

↓

Send Email
```

Only one token should remain valid.

---

# Should Every Resend Create a New Token?

Yes.

Bad:

```text
Same Token Forever
```

Good:

```text
Old Token

↓

Invalidate

↓

Generate New Token
```

This reduces the risk of old links being misused.

---

# Email Change Before Verification

Suppose Rahul entered:

```text

```

Instead of:

```text

```

Possible workflow:

```text
Pending Verification

↓

Change Email

↓

Generate New Token

↓

Send New Email
```

The old verification token becomes invalid.

# Production Considerations

Professional systems usually consider:

- Expiration time
    
- Maximum resend attempts
    
- Rate limiting resend requests
    
- Logging verification attempts
    
- Preventing email enumeration
    
- Monitoring delivery failures
    

These improve both security and reliability.

# Common Beginner Mistakes

## ❌ Activating the Account Before Verification

Bad:

```text
Register

↓

Active User
```

Always activate **after** successful verification if your application requires verified emails.

---

## ❌ Reusing Verification Tokens

Generate a fresh token for every resend request.

---

## ❌ Keeping Old Tokens

Always invalidate previous verification tokens when issuing a new one.

---

## ❌ Mixing Email Sending with Controllers

Controllers should not contain SMTP or email provider logic.

Use a dedicated email service.

---

## ❌ Forgetting Cleanup

After successful verification:

```text
Delete Verification Token

↓

Clear Expiration
```

Temporary data should not remain in the database.

---

# Best Practices

- Create the account in a pending verification state.
    
- Generate secure, single-use verification tokens.
    
- Hash verification tokens before storage.
    
- Expire tokens after a reasonable time.
    
- Invalidate previous tokens when resending.
    
- Keep email logic in a dedicated service.
    
- Remove verification data after activation.
    
- Design the verification endpoint to be safe if called multiple times.

# Interview Questions

### Q1. What happens after successful email verification?

**Answer:**

The account is activated, the verification status is updated, the verification token and expiration are removed, and the user can access features that require a verified email.

---

### Q2. What should happen if the verification token has expired?

**Answer:**

Reject the request and require the user to request a new verification email with a newly generated token.

---

### Q3. Why should old verification tokens be invalidated?

**Answer:**

Invalidating old tokens reduces the attack surface and ensures only the newest verification link can activate the account.

---

### Q4. Where should verification logic be implemented?

**Answer:**

In the service layer, because generating tokens, verifying them, activating accounts, and applying verification policies are business rules.

# 💡 Backend Engineering Tip

A complete email verification system is more than just sending a link. Think of it as a **state machine**:

```text
Register

↓

Pending Verification

↓

Verification Email Sent

↓

Token Valid?

├── No → Reject
│
└── Yes
      ↓
Activate Account

↓

Delete Verification Token

↓

Verified User
```

Designing it as a sequence of state transitions makes the implementation easier to reason about, easier to test, and more secure.
