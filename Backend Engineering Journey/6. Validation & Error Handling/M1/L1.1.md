# What is Validation?

**Validation** is the process of checking whether the incoming data is **correct, complete, and follows the expected rules** before your application processes it.

Think of validation as a **security guard** at the entrance of your application.

```
Client
   │
   ▼
Validation
   │
Valid?
 ├── Yes → Continue
 └── No  → Reject Request
```

If invalid data enters your application, it can cause:

- Application crashes
    
- Security vulnerabilities
    
- Corrupted database records
    
- Poor user experience
    

---

# Why Can't We Trust the Client?

Many beginners think:

> "The frontend already validates the form, so the backend doesn't need validation."

This is **incorrect**.

Anyone can bypass your frontend.

For example:

```
Frontend
   │
   ▼
POST /register
```

A malicious user can skip the frontend entirely and send requests directly using:

- Postman
    
- curl
    
- Insomnia
    
- Their own script
    
- Another application
    

Example:

```http
POST /register
```

```json
{
  "email": "not-an-email",
  "password": ""
}
```

Without backend validation, this request could reach your database.

# Real Example

Imagine your registration form requires:

- Name
    
- Email
    
- Password
    

Expected request:

```json
{
  "name": "Rahul",
  "email": "rahul@gmail.com",
  "password": "StrongPassword123"
}
```

Now imagine someone sends:

```json
{
  "name": "",
  "email": "abc",
  "password": "1"
}
```

Should your application create this user?

**No.**

The backend should reject it.

Example response:

```http
400 Bad Request
```

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    {
      "field": "email",
      "message": "Invalid email format"
    },
    {
      "field": "password",
      "message": "Password must be at least 8 characters."
    }
  ]
}
```

# Validation vs Sanitization

These two terms are often confused.

## Validation

Validation **checks** the data.

Example:

```
Email must be valid.

Password length ≥ 8.

Age ≥ 18.
```

Validation asks:

> "Is this data acceptable?"

---

## Sanitization

Sanitization **cleans** the data.

Example:

Input:

```
"   Rahul   "
```

After sanitization:

```
"Rahul"
```

Another example:

```
HELLO@GMAIL.COM
```

Normalize:

```
hello@gmail.com
```

Sanitization asks:

> "How can I make this safe and consistent?"

---

## Simple Comparison

|Validation|Sanitization|
|---|---|
|Checks data|Cleans data|
|Accept or reject|Modify safely|
|Returns errors|Returns cleaned values|
|Example: Email format|Example: Trim spaces|

Both are important.

# What Happens Without Validation?

Imagine a blog application.

Request:

```json
{
  "title": "",
  "content": "",
  "category": "???"
}
```

Without validation:

```
Client
   │
   ▼
Controller
   │
   ▼
Database
```

Your database now stores invalid records.

Later:

- Search breaks.
    
- UI looks incorrect.
    
- Users see empty posts.
    
- Reports become unreliable.

# Validation Layers

Professional applications validate data at multiple levels.

```
Client
   │
   ▼
Request Validation
   │
   ▼
Business Validation
   │
   ▼
Database Validation
```

We'll study each layer in later lessons.

For now, remember:

### 1. Request Validation

Checks the request format and structure.

Examples:

- Required fields
    
- Email format
    
- Password length
    
- Valid ObjectId
    
- Pagination values
    

---

### 2. Business Validation

Checks business rules.

Examples:

- Email already exists
    
- User already liked the post
    
- Cannot publish an empty draft
    
- Cannot delete another user's comment
    

The request is valid, but the **action** isn't.

---

### 3. Database Validation

The final safety net.

Examples:

- Unique email
    
- Unique username
    
- Foreign key constraints
    
- Required database fields
    

Even if your application has a bug, the database still protects its data.

# Real Backend Flow

```
Client
   │
   ▼
Express Route
   │
   ▼
Validation Middleware
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Database
```

If validation fails:

```
Client
   │
   ▼
Validation
   │
   ├── Valid → Continue
   └── Invalid → Return 400
```

The request never reaches your business logic or database.

---

# Best Practices

- ✅ Never trust client input.
    
- ✅ Validate every public API endpoint.
    
- ✅ Reject invalid data as early as possible.
    
- ✅ Keep validation separate from business logic.
    
- ✅ Use reusable validation schemas.
    
- ✅ Let the database enforce important constraints too.
    

---

# Common Beginner Mistakes

❌ Validating only on the frontend.

❌ Assuming React forms make the backend safe.

❌ Mixing validation logic inside controllers.

❌ Skipping validation for route parameters.

❌ Believing MongoDB will fix bad input automatically.

---

# Interview Questions

### Q1. Why do we need backend validation if the frontend already validates?

**Answer:**  
Frontend validation improves user experience, but it can be bypassed. The backend must always validate requests because clients cannot be trusted.

---

### Q2. What is the difference between validation and sanitization?

**Answer:**  
Validation checks whether data meets defined rules. Sanitization cleans or normalizes the data before processing or storing it.

---

### Q3. What are the three validation layers?

**Answer:**

1. Request validation
    
2. Business validation
    
3. Database validation
    

---

# Key Takeaways

- Validation protects your application from bad or malicious input.
    
- Backend validation is mandatory, even if the frontend validates.
    
- Validation checks data; sanitization cleans it.
    
- Professional backends use multiple validation layers.
    
- Invalid requests should be rejected **before** they reach the service or database.
