# What is Request Validation?

Request validation is the **first line of defense** in your backend.

Its job is to ensure the request has the correct **shape**, **type**, and **format** before your application does any business logic.

Think of it like checking a ticket before allowing someone into a movie theater.

```text
Client
   │
   ▼
Request Validation
   │
Valid?
├── Yes → Controller
└── No  → Return Error
```

If the request is invalid, it should stop immediately.

---

# What Should Be Validated?

A request contains more than just the request body.

There are four common places to validate.

## 1. Request Body (`req.body`)

Example:

```http
POST /users
```

```json
{
  "name": "Rahul",
  "email": "rahul@gmail.com",
  "password": "Strong123"
}
```

Typical validations:

- Required fields
    
- String length
    
- Email format
    
- Password strength
    
- Number ranges
    
- Enum values
    

---

## 2. Route Parameters (`req.params`)

Example:

```http
GET /posts/64fd123abc456
```

```javascript
req.params.id
```

Validate:

- MongoDB ObjectId
    
- UUID
    
- Integer ID
    
- Slug format
    

Never send an invalid ID to your database.

---

## 3. Query Parameters (`req.query`)

Example:

```http
GET /posts?page=2&limit=10&sort=-createdAt
```

```javascript
req.query.page
req.query.limit
```

Validate:

- Page number
    
- Limit
    
- Sort fields
    
- Search keyword length
    
- Filter values
    

Example:

```text
page >= 1

limit <= 100
```

---

## 4. File Uploads (`req.file` / `req.files`)

Example:

```http
POST /profile/avatar
```

Validate:

- File exists
    
- File size
    
- MIME type
    
- Allowed extensions
    

Example:

Accept:

```text
profile.jpg
```

Reject:

```text
virus.exe
```

# Where Should Request Validation Happen?

A professional Express application validates **before the controller**.

```text
Client
   │
   ▼
Route
   │
   ▼
Validation Middleware
   │
   ▼
Controller
   │
   ▼
Service
```

The controller should receive only valid data.

---

# Bad Example

```text
Controller

Check email

Check password

Check name

Check age

Create user
```

The controller becomes large and difficult to maintain.

---

# Good Example

```text
Route
   │
Validation Middleware
   │
Controller
   │
Service
```

The controller focuses only on handling the request and response.

# Example: User Registration

Suppose your API is:

```http
POST /register
```

Incoming request:

```json
{
  "name": "Rahul",
  "email": "rahul@gmail.com",
  "password": "Strong123"
}
```

Validation rules:

|Field|Rules|
|---|---|
|name|Required, 2–50 characters|
|email|Required, valid email|
|password|Required, minimum 8 characters|

If validation fails:

```http
400 Bad Request
```

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    {
      "field": "password",
      "message": "Password must be at least 8 characters."
    }
  ]
}
```

Notice that the controller is never called.

# Validation Flow

```text
Client Request
      │
      ▼
Validate Request
      │
      ├── Invalid
      │      │
      │      ▼
      │   Return 400
      │
      ▼
Controller
      ▼
Service
      ▼
Repository
```

Reject invalid requests as early as possible.

# Common Validation Rules

## String

- Required
    
- Minimum length
    
- Maximum length
    

Example:

```text
2–50 characters
```

---

## Number

Example:

```text
Age

Minimum = 18

Maximum = 100
```

---

## Email

Example:

```text
rahul@gmail.com
```

Reject:

```text
rahulgmail.com
```

---

## Enum

Only allow predefined values.

Example:

```text
Role

Admin

User

Moderator
```

Reject:

```text
SuperAdmin
```

(if it isn't supported)

---

## Array

Example:

```json
{
  "tags": [
    "Node",
    "Express"
  ]
}
```

Validate:

- Array type
    
- Maximum items
    
- No duplicates

# Should Validation Check the Database?

**No.**

Request validation checks only the **format and structure** of the request.

For example:

✔ Is the email valid?

✔ Is the password long enough?

✔ Is the page number positive?

It should **not** check:

- Email already exists
    
- Username already taken
    
- User owns this post
    

Those are **business validation** rules and belong in the service layer.

---

# Best Practices

- ✅ Validate every public endpoint.
    
- ✅ Validate `body`, `params`, `query`, and uploaded files.
    
- ✅ Use validation middleware instead of controller logic.
    
- ✅ Return clear and consistent error messages.
    
- ✅ Keep validation rules reusable.
    

---

# Common Beginner Mistakes

❌ Validating inside every controller.

❌ Forgetting route parameter validation.

❌ Trusting query parameters.

❌ Accepting unlimited file uploads.

❌ Mixing request validation with database queries.

---

# Interview Questions

### Q1. Where should request validation happen?

**Answer:**  
In validation middleware before the request reaches the controller.

---

### Q2. What parts of a request should be validated?

**Answer:**

- Request body (`req.body`)
    
- Route parameters (`req.params`)
    
- Query parameters (`req.query`)
    
- Uploaded files (`req.file` / `req.files`)
    

---

### Q3. Should request validation check if an email already exists?

**Answer:**  
No. That is a business rule and belongs in the service layer.

---

# Key Takeaways

- Request validation is the first defense against invalid input.
    
- Validate all incoming data: body, params, query, and files.
    
- Perform validation before the controller.
    
- Request validation checks **structure and format**, not business rules.
    
- Keeping validation in middleware makes your code cleaner, reusable, and easier to maintain.
