# Why Do We Need Multiple Validation Layers?

Imagine a user wants to register.

Request:

```json
{
  "name": "Rahul",
  "email": "rahul@gmail.com",
  "password": "Strong123"
}
```

Many beginners try to perform **all validations in one place**, usually the controller.

Example:

```text
Controller
├── Check email format
├── Check password length
├── Check if email exists
├── Check business rules
├── Save user
```

This makes the controller large and difficult to maintain.

Professional applications split responsibilities across layers.

---

# The Three Validation Layers

```text
Client
   │
   ▼
Request Validation
   │
   ▼
Business Validation
   │
   ▼
Database Validation
```

Each layer has one responsibility.

---

# 1. Request Validation

Purpose:

> Is the request **well-formed**?

Examples:

- Required fields
    
- Email format
    
- Password length
    
- ObjectId format
    
- Query parameters
    

Example:

```json
{
  "email": "abc"
}
```

Reject immediately.

Reason:

The request itself is invalid.

---

# 2. Business Validation

Purpose:

> Is this operation allowed?

Examples:

- Email already exists
    
- User already liked this post
    
- Cannot publish an empty draft
    
- User cannot delete another user's comment
    

Example:

```text
POST /likes
```

Request:

```json
{
    "postId":"123"
}
```

Suppose the user has already liked the post.

The request format is valid.

But the business rule says:

```text
One user can like only once.
```

Return:

```http
409 Conflict
```

---

# 3. Database Validation

Purpose:

Protect database integrity.

Examples:

- Unique email
    
- Unique username
    
- Foreign key constraint
    
- Required columns
    

Even if your application has a bug, the database still prevents invalid data.

---

# Complete Validation Flow

```text
Client
   │
   ▼
Validation Middleware
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Database
```

Each layer performs only its own responsibility.

# Real Blog Example

Suppose:

```http
POST /posts
```

Body:

```json
{
  "title":"Learning Node",
  "content":"...",
  "category":"Programming"

```

### Request Validation

Check:

- Title required
    
- Content required
    
- Category valid
    

---

### Business Validation

Check:

- User account is active
    
- Daily post limit not exceeded
    
- Category exists
    

---

### Database Validation

Check:

- Slug unique
    
- Required fields
    
- Database constraints

# Responsibility Table

|Layer|Responsibility|
|---|---|
|Validation Middleware|Validate request format|
|Controller|Call service|
|Service|Business rules|
|Repository|Database operations|
|Database|Final data integrity|

Notice that the controller contains **almost no validation logic**.

---

# Why Not Validate Everything in the Controller?

Imagine 100 API endpoints.

If every controller validates:

- Email
    
- Password
    
- Pagination
    
- ObjectId
    

You'll duplicate code everywhere.

Instead:

```text
Route
   │
Validation Middleware
   │
Controller
```

Cleaner.

Reusable.

Easy to test.

---

# Common Beginner Mistakes

❌ Checking "email already exists" in validation middleware.

❌ Performing database queries inside request validators.

❌ Putting all validation inside controllers.

❌ Relying only on MongoDB unique indexes.

---

# Best Practices

- ✅ Request validation checks format only.
    
- ✅ Business validation lives in the service layer.
    
- ✅ Database constraints are the last safety net.
    
- ✅ Each layer should have a single responsibility.
    
- ✅ Fail early whenever possible.
    

---

# Interview Questions

### Q1. Why shouldn't request validation check if an email already exists?

**Answer:**  
Because checking email uniqueness requires a database query and is a business rule. Request validation should only validate the request's structure and format.

---

### Q2. What is the purpose of database validation?

**Answer:**  
To enforce data integrity through constraints such as unique indexes, required fields, and foreign keys, even if the application contains bugs.

---

### Q3. Which layer should check if a user can delete a post?

**Answer:**  
The **service layer**, because ownership is a business rule.

---

# Key Takeaways

- Validation is divided into **request**, **business**, and **database** layers.
    
- Request validation checks **format**.
    
- Business validation checks **rules**.
    
- Database validation protects **data integrity**.
    
- Following this separation makes your backend cleaner, easier to test, and easier to maintain.
