# The Problem: Duplicate Validation

Imagine you have these APIs:

```http
POST /register
POST /admin/users
PUT /users/profile
```

Each API requires an email.

A beginner might write:

```javascript
// Controller 1
if (!email.includes("@")) {
    ...
}

// Controller 2
if (!email.includes("@")) {
    ...
}

// Controller 3
if (!email.includes("@")) {
    ...
}
```

The same validation is copied multiple times.

Problems:

- Difficult to maintain
    
- Easy to introduce bugs
    
- Hard to update
    
- Violates the **DRY (Don't Repeat Yourself)** principle
    

---

# Professional Solution

Write the validation once.

Reuse it everywhere.

```text
Email Validator
       │
       ├── Register API
       ├── Update Profile API
       └── Admin API
```

One change updates every endpoint.

# Project Structure

A common Express project structure looks like this:

```text
src/
│
├── controllers/
├── services/
├── repositories/
├── routes/
│
├── validators/
│     ├── auth.validator.js
│     ├── post.validator.js
│     ├── user.validator.js
│     └── common.validator.js
│
├── middleware/
│     └── validate.js
│
└── app.js
```

Notice that **validation has its own folder**.

# Validation Middleware

Instead of validating inside controllers:

```text
Route
   │
Controller
   │
Validation
```

Professional applications do this:

```text
Route
   │
Validation Middleware
   │
Controller
```

The controller receives only validated data.

---

# Request Flow

```text
Client
   │
   ▼
Route
   │
   ▼
Validation Middleware
   │
Valid?
├── No → Return 400
└── Yes
      │
      ▼
Controller
      ▼
Service
```

The controller doesn't need to ask:

- Is email valid?
    
- Is password long enough?
    
- Is title empty?
    

Those checks are already done.

# Joi

Joi is one of the most popular validation libraries for Node.js.

It allows you to define validation rules as schemas.

Conceptually:

```text
Register Schema

Name

Email

Password
```

Then:

```text
Validate(requestBody)
```

If invalid:

```text
Return 400
```

---

# Zod

Zod is another popular validation library.

It's especially common in:

- TypeScript
    
- React
    
- Full-stack applications
    

Advantages:

- Great TypeScript support
    
- Type inference
    
- Easy integration with modern frameworks
    

---

# Joi vs Zod

|Feature|Joi|Zod|
|---|---|---|
|JavaScript|⭐⭐⭐⭐⭐|⭐⭐⭐⭐|
|TypeScript|⭐⭐⭐|⭐⭐⭐⭐⭐|
|Mature ecosystem|✅|✅|
|Express projects|Very common|Common|
|React integration|Good|Excellent|

### Which should you learn?

For your **MERN + Express** roadmap:

- **Learn Joi first** because it's widely used in Express backends.
    
- Later, learn **Zod**, especially if you work with TypeScript or Next.js.
    

The concepts are nearly identical. Once you understand one library, switching to another is straightforward.

# Best Practices

- ✅ Keep validation inside a dedicated `validators/` folder.
    
- ✅ Use validation middleware.
    
- ✅ Reuse common validation rules.
    
- ✅ Keep controllers free from validation logic.
    
- ✅ Separate request validation from business validation.
    

---

# Common Beginner Mistakes

❌ Writing validation inside controllers.

❌ Copy-pasting validation rules.

❌ Creating one huge validator file for the entire project.

❌ Mixing business rules into Joi/Zod schemas.

❌ Creating different email validation logic for different APIs.

# Interview Questions

### Q1. Why use a validation library instead of writing `if` statements?

**Answer:**  
Validation libraries provide reusable, readable, maintainable schemas with consistent error handling. They reduce duplication and improve code quality.

---

### Q2. Why use validation middleware?

**Answer:**  
It validates requests before they reach the controller, keeping controllers focused on handling business operations rather than input checking.

---

### Q3. Should Joi check whether an email already exists?

**Answer:**  
No. Joi validates the structure and format of data. Checking email uniqueness requires a database query and belongs in the service layer.

---

# Key Takeaways

- Reusable validation reduces duplication and makes your code easier to maintain.
    
- Store validation logic in dedicated validator files.
    
- Use middleware to validate requests before controllers.
    
- Joi and Zod solve the same problem; they differ mainly in ecosystem and TypeScript support.
    
- Business rules should never be mixed into request validation schemas.
