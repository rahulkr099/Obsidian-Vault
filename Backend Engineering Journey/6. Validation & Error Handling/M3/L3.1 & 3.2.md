# Why Error Handling Matters

Imagine two APIs in the same project.

API 1 returns:

```json
{
    "error": "Invalid email"
}
```

API 2 returns:

```json
{
    "message": "Something went wrong"
}
```

API 3 returns:

```json
{
    "success": false,
    "reason": "User not found"
}
```

Every API responds differently.

Problems:

- Frontend becomes harder to build.
    
- Documentation becomes inconsistent.
    
- Developers waste time handling different response formats.
    

Professional APIs use **one consistent structure**.

---

# Standard Error Response

A common format is:

```json
{
    "success": false,
    "message": "Validation failed",
    "errors": [
        {
            "field": "email",
            "message": "Invalid email format"
        }
    ]
}
```

### Explanation

|Field|Purpose|
|---|---|
|`success`|Indicates request failed|
|`message`|High-level description|
|`errors`|Detailed validation errors|

This structure should be used consistently across your APIs.

# HTTP Status Codes

Status codes tell the client **what happened**.

### 200 OK

Request succeeded.

Example:

```http
GET /posts
```

Response:

```http
200 OK
```

---

### 201 Created

A new resource was created.

Example:

```http
POST /users
```

Response:

```http
201 Created
```

---

### 204 No Content

Operation succeeded but there's nothing to return.

Example:

```http
DELETE /posts/123
```

Response:

```http
204 No Content
```

---

### 400 Bad Request

The request itself is invalid.

Examples:

- Missing required field
    
- Invalid email format
    
- Invalid ObjectId format
    

Example:

```json
{
    "email": "abc"
}
```

Return:

```http
400 Bad Request
```

---

### 401 Unauthorized

Authentication is required.

Examples:

- Missing JWT
    
- Invalid token
    
- Expired token
    

---

### 403 Forbidden

The user is authenticated but **not allowed**.

Example:

```text
User tries to delete another user's post.
```

Return:

```http
403 Forbidden
```

---

### 404 Not Found

Requested resource doesn't exist.

Example:

```http
GET /posts/999999
```

Return:

```http
404 Not Found
```

---

### 409 Conflict

The request conflicts with existing data.

Examples:

- Email already exists
    
- Username already taken
    
- User already liked the post
    

---

### 422 Unprocessable Entity

The request format is correct, but the data cannot be processed.

Some teams use this for validation errors, while others prefer `400`. The important thing is to stay consistent across your API.

---

### 500 Internal Server Error

Unexpected server error.

Examples:

- Unhandled exception
    
- Database connection failure
    
- Programming bug
    

Clients should **never** receive stack traces.

   ▼

   │

---

# Best Practices

- ✅ Use the correct HTTP status code.
    
- ✅ Keep error responses consistent.
    
- ✅ Return meaningful messages.
    
- ✅ Don't expose internal implementation details.
    
- ✅ Include field-specific errors for validation failures.
    

---

# Common Beginner Mistakes

❌ Returning `500` for every error.

❌ Returning `200 OK` even when validation fails.

❌ Sending stack traces to clients.

❌ Using different error formats across endpoints.

❌ Returning vague messages like:

```text
Something went wrong.
```

---

# Interview Questions

### Q1. What's the difference between `401` and `403`?

**Answer:**

- `401 Unauthorized` → The user is **not authenticated**.
    
- `403 Forbidden` → The user is authenticated but **does not have permission**.
    

---

### Q2. When should you use `409 Conflict`?

**Answer:**

When the request conflicts with existing resources, such as duplicate emails or usernames.

---

### Q3. Why should error responses have a consistent structure?

**Answer:**

It makes APIs easier to use, simplifies frontend development, improves documentation, and reduces maintenance.

---

# Key Takeaways

- HTTP status codes communicate the result of a request.
    
- Use the most appropriate status code for each situation.
    
- Keep one consistent error response format across your entire API.
    
- Never leak internal implementation details to clients.

# The Problem Without a Global Error Handler

Imagine every controller contains:

```javascript
try {
    // logic
} catch (error) {
    res.status(500).json({
        message: error.message
    });
}
```

Now imagine you have **50 controllers**.

You'll end up repeating the same error handling everywhere.

This violates the **DRY (Don't Repeat Yourself)** principle.

---

# Professional Solution

Instead of handling errors in every controller:

```text
Route
   │
Controller
   │
Service
   │
Repository
   │
Throw Error
   │
Global Error Handler
   │
HTTP Response
```

One place handles every error.

---

# Custom Error Classes

Instead of throwing plain errors:

```javascript
throw new Error("User not found");
```

Create meaningful error types.

Examples:

```text
AppError
ValidationError
AuthenticationError
AuthorizationError
NotFoundError
ConflictError
```

Benefits:

- Easier to identify the error.
    
- Appropriate status codes.
    
- Cleaner code.
    

---

# Example

Instead of:

```javascript
throw new Error("Email already exists");
```

Use:

```javascript
throw new ConflictError("Email already exists");
```

The global error handler knows:

- Status code = 409
    
- Message = "Email already exists"
    

---

# Async Error Handling

Most Express controllers are asynchronous.

Example:

```javascript
const user = await userService.createUser(data);
```

Errors from async functions should reach the global error handler.

Professional projects often use:

- Async wrapper functions
    
- Express async middleware
    
- Proper promise rejection handling
    

This prevents unhandled promise rejections.

---

Notice that the controller doesn't manually build the error response.

---

# Benefits of a Global Error Handler

### Consistency

Every API returns the same format.

---

### Cleaner Controllers

Controllers focus only on business flow.

---

### Easy Maintenance

Update one middleware instead of dozens of controllers.

---

### Better Logging

Log every error in one place.

---

### Better Security

Hide stack traces and sensitive information from clients.

---

# Best Practices

- ✅ Create a base `AppError` class.
    
- ✅ Extend it for common errors.
    
- ✅ Throw meaningful custom errors.
    
- ✅ Handle every error in one middleware.
    
- ✅ Keep controllers free from repetitive `try/catch` blocks where possible.

# Interview Questions

### Q1. Why use custom error classes?

**Answer:**

They make errors more meaningful, allow automatic status code mapping, improve readability, and simplify centralized error handling.

---

### Q2. Why use a global error handler?

**Answer:**

It centralizes error handling, keeps controllers clean, ensures consistent responses, improves logging, and enhances security.

---

### Q3. Why shouldn't you expose stack traces to clients?

**Answer:**

Stack traces may reveal sensitive implementation details, file paths, or internal logic that attackers could misuse.
