# 10.1 — What Is Backend Security?

Before writing:

```js
helmet()
cors()
rateLimit()
mongoSanitize()
hpp()
```

we need to answer a very basic question:

> **What are we actually trying to protect?**

## 1. Backend security in simple words

Backend security means:

> **Making sure that only allowed requests can safely interact with our application and data.**

Imagine your backend is a building.

```text
                INTERNET
                   │
                   ▼
          ┌─────────────────┐
          │    BACKEND      │
          │                 │
          │   API           │
          │   Database      │
          │   Users         │
          │   Secrets       │
          └─────────────────┘
```

Anyone on the internet can potentially send a request to your API.

For example:

```http
POST /api/v1/users
```

or:

```http
GET /api/v1/users/123
```

or:

```http
DELETE /api/v1/users/123
```

Your backend cannot simply assume:

> "The client is probably trustworthy."

The client could be:

- your React application
    
- Postman
    
- a mobile application
    
- another server
    
- a browser script
    
- an automated bot
    
- an attacker
    

So your backend needs its own security checks.

---

# 2. Never trust the client

This is one of the most important backend principles.

Suppose your React application sends:

```json
{
  "role": "user"
}
```

You might think:

> "The frontend only allows users to select `user`, so we're safe."

No.

Someone can completely bypass your frontend and send:

```json
{
  "role": "admin"
}
```

directly to your API.

Therefore:

```text
Frontend validation
        ≠
Backend security
```

The backend must independently enforce its rules.

---

# 3. Think of the API as a public entrance

Imagine:

```text
                  INTERNET
                     │
                     ▼
             ┌───────────────┐
             │     API       │
             │   ENTRANCE    │
             └───────┬───────┘
                     │
          ┌──────────┴──────────┐
          │                     │
       Allowed?              Dangerous?
          │                     │
          ▼                     ▼
       Continue               Reject
```

Security middleware acts like checkpoints.

For example:

```text
Request
   │
   ▼
CORS
   │
   ▼
Rate Limiter
   │
   ▼
Input Sanitization
   │
   ▼
Authentication
   │
   ▼
Authorization
   │
   ▼
Controller
```

Not every request needs every checkpoint, but the concept is important.

---

# 4. Security is not one package

This is another important idea.

You might see:

```js
app.use(helmet());
```

and think:

> "Helmet secures my backend."

No.

Helmet solves **some HTTP security concerns**.

Similarly:

```js
cors()
```

doesn't secure your entire API.

And:

```js
rateLimit()
```

doesn't prevent authentication attacks by itself.

Security is a **layered system**.

Think:

```text
                 BACKEND SECURITY
                        │
       ┌────────────────┼────────────────┐
       │                │                │
       ▼                ▼                ▼
    Network          Application      Database
    security          security        security
       │                │                │
       ▼                ▼                ▼
      CORS           Auth             Injection
      Headers        RBAC             Access
      Rate limit     Validation       Control
```

# 5. What are we protecting?

A backend normally needs to protect several things.

### A. User accounts

```text
email
password hash
sessions/tokens
profile
```

### B. Application data

```text
todos
orders
payments
messages
documents
```

### C. Secrets

```text
JWT secrets
database credentials
API keys
SMTP credentials
```

### D. Availability

Your server should remain usable.

For example, an attacker shouldn't be able to send:

```text
1 million requests
```

and easily take your application down.

This is where rate limiting becomes useful.

### E. Integrity

Users should not be able to modify things they don't own.

For example:

```text
User A
   ↓
tries to modify
   ↓
User B's Todo
```

Your backend must stop that.

---

# 6. Three major security goals

A useful way to think about security is:

```text
Confidentiality
Integrity
Availability
```

### Confidentiality

> Only authorized people can see the data.

Example:

```text
User A cannot read User B's private notes.
```

### Integrity

> Only authorized people can change the data.

Example:

```text
Normal user cannot change their role to admin.
```

### Availability

> The service should remain available to legitimate users.

Example:

```text
One IP cannot continuously hammer /login.
```

So:

```text
             SECURITY
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
Confidentiality Integrity Availability
     │             │           │
     ▼             ▼           ▼
    Auth          RBAC       Rate Limit
    Access        Ownership  DoS defense
```

---

# 7. Where does security happen?

Security doesn't belong in only one place.

It exists at multiple layers.

For example:

```text
Internet
   ↓
Reverse Proxy
   ↓
Express
   ↓
Security Middleware
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

Each layer has a responsibility.

For example:

### Middleware

Can inspect the request.

```text
Is this request too frequent?
```

### Authentication

Can answer:

```text
Who is this user?
```

### Authorization

Can answer:

```text
Is this user allowed to do this?
```

### Validation

Can answer:

```text
Is this input structurally valid?
```

### Service

Can enforce business rules.

```text
Can this user perform this operation?
```

### Repository

Can enforce safe database access.

```text
Only retrieve records belonging to this user.
```

---

# 8. Security is a layered defense

Suppose an attacker sends:

```http
POST /api/v1/auth/login
```

with thousands of attempts.

Different layers can respond:

```text
Request
   │
   ▼
Rate limiter
   │
   ├── Too many requests → 429
   │
   ▼
Validation
   │
   ├── Invalid body → 400
   │
   ▼
Authentication
   │
   ├── Wrong credentials → 401
   │
   ▼
Service
   │
   ▼
Database
```

Even if one security mechanism fails, other mechanisms still exist.

That's called **defense in depth**.

---

# 9. Security is also about correct architecture

Consider this controller:

```js
const deleteUser = async (req, res) => {
    const user = await User.findById(req.params.id);

    await User.deleteOne({
        _id: user._id
    });

    res.json({
        success: true
    });
};
```

It might technically work.

But security asks:

> **Who is allowed to delete this user?**

If there is no authorization check, an attacker might try:

```http
DELETE /users/another-user-id
```

Therefore we need something like:

```text
Authentication
      ↓
Who are you?
      ↓
Authorization
      ↓
Are you allowed?
      ↓
Service
      ↓
Repository
      ↓
Database
```

Security isn't simply adding packages.

**Good architecture itself contributes to security.**

# 12. A simple attack example

Imagine you have:

```http
POST /api/v1/todos
```

A normal request:

```json
{
  "title": "Learn Node.js"
}
```

But an attacker may try to:

### Spam the endpoint

```text
10,000 requests/second
```

→ Rate limiting helps.

### Send malicious input

```text
Unexpected database operators
```

→ Sanitization helps reduce injection risk.

### Send requests from an unwanted browser origin

```text
evil.example
```

→ CORS/origin controls may help in browser-based scenarios.

### Try to access another user's resource

```text
GET /todos/USER_B_TODO
```

→ Authentication + authorization + ownership checks.

### Exploit unsafe HTTP configuration

→ Security headers such as those provided by Helmet can help.

Notice something important:

**No single middleware solves all of these problems.**
