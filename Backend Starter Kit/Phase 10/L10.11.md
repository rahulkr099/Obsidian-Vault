# Lesson 10.11 — Rate Limiting Fundamentals

Now we move to another important security concept:

> **How do we stop one client from sending an unreasonable number of requests to our API?**

This is called **rate limiting**.

Your Phase 10 specifically places **Rate Limiting Fundamentals** after CORS and Helmet because you now understand the basic middleware idea needed to build it.

---

# 1. The problem rate limiting solves

Imagine your API has:

```http
POST /api/auth/login
```

A normal user might send:

```text
5 requests
```

But an attacker could send:

```text
10,000 requests
```

trying different passwords.

Without any protection:

```text
Attacker
   │
   ├── Request 1
   ├── Request 2
   ├── Request 3
   ├── ...
   └── Request 10,000
          │
          ▼
       Your API
```

This can cause:

```text
Brute-force attacks
Resource exhaustion
Abuse
High server load
API scraping
Credential attacks
```

Rate limiting puts a boundary around request frequency.

---

# 2. The basic idea

Rate limiting means:

> **Allow only a certain number of requests from a client during a certain period.**

For example:

```text
100 requests
per
1 minute
```

So:

```text
Client
  │
  ├── Request 1     ✓
  ├── Request 2     ✓
  ├── Request 3     ✓
  ├── ...
  ├── Request 100   ✓
  └── Request 101   ✗
```

The 101st request may receive:

```http
429 Too Many Requests
```

---

# 3. HTTP 429

The standard HTTP status code for rate limiting is:

```http
429 Too Many Requests
```

This is important.

Don't return:

```http
400 Bad Request
```

just because the client sent too many requests.

Don't return:

```http
500 Internal Server Error
```

either.

`429` communicates:

> "You have sent too many requests in the allowed period."

---

# 4. Rate limiting is middleware

You've already learned middleware.

So rate limiting fits naturally into Express:

```text
Request
   ↓
Rate limiter
   ↓
Allowed?
 ┌───────┴────────┐
 YES              NO
  ↓                ↓
next()           429
  ↓
Route
```

For example:

```js
app.use(rateLimiter);
```

This should now look familiar.

It's the same architectural idea as:

```js
app.use(corsMiddleware);
app.use(helmet());
```

Each middleware performs a specific job.

# 5. A simple mental model

Imagine a bucket:

```text
┌───────────────────┐
│  Request budget   │
│                   │
│  ● ● ● ● ● ● ●    │
│                   │
└───────────────────┘
```

Suppose the client gets:

```text
10 requests / minute
```

Every request consumes one token:

```text
Request 1
 ↓
● ● ● ● ● ● ● ● ●
```

Eventually:

```text
0 remaining
```

Then:

```text
Request
   ↓
No capacity
   ↓
429
```

This is one way rate-limiting algorithms work.

# 6. Rate limiting is not simply "blocking IPs"

A beginner often thinks:

```text
Rate limiting = IP blocking
```

Not exactly.

An IP address is just **one possible identifier**.

You could limit based on:

```text
IP address
User ID
API key
Session
Route
Combination of IP + user
```

For example:

```text
Public API
    ↓
IP-based limit

Authenticated API
    ↓
User-based limit

Login endpoint
    ↓
IP + account-based protection
```

We'll explore these distinctions later.

---

# 7. Why IP-based limiting is useful

For a public endpoint:

```http
GET /api/products
```

you might not know who the user is.

So you could track:

```text
Client IP
```

For example:

```text
192.168.1.10
```

and maintain:

```text
192.168.1.10 → 73 requests
```

Then:

```text
Limit = 100
Current = 73

73 < 100
   ↓
Allow
```

But:

```text
Current = 101

101 > 100
   ↓
429
```

---

# 8. But IP addresses aren't perfect

This is very important.

Imagine a college campus.

Thousands of students may access the internet through the same public IP:

```text
        College Network
              │
       ┌──────┼──────┐
       │      │      │
    Student Student Student
       │      │      │
       └──────┼──────┘
              │
         One public IP
```

If you aggressively rate-limit that IP:

```text
100 requests/minute
```

one person might consume the entire quota.

Now innocent users are affected.

So:

> **IP-based rate limiting is useful, but IP is not a perfect identity.**

---

# 9. The opposite problem

Imagine an attacker has access to many IP addresses:

```text
IP 1 → 100 requests
IP 2 → 100 requests
IP 3 → 100 requests
IP 4 → 100 requests
...
```

They can potentially distribute requests.

This is why serious applications often use multiple layers of rate limiting.

For example:

```text
IP limit
+
User/account limit
+
Endpoint-specific limit
```

This is much stronger than relying on one IP rule.

# 12. Rate limiting vs brute-force protection

They're related but not identical.

### Rate limiting

General concept:

```text
Too many requests
       ↓
Slow down / reject
```

### Brute-force protection

Specific security goal:

```text
Repeated attempts to guess credentials
       ↓
Detect/restrict attack
```

For example:

```text
POST /login
```

might have:

```text
5 attempts / minute
```

while your normal API has:

```text
100 requests / minute
```

So:

```text
Rate limiting
   ↓
General mechanism

Brute-force protection
   ↓
Specific security use case
```

---

# 13. Rate limiting and DDoS

Another common misunderstanding:

> "If I have rate limiting, I'm protected from DDoS."

Not necessarily.

Application-level rate limiting can help with:

```text
API abuse
Request floods
Brute-force attempts
Resource abuse
```

But a large distributed attack may overwhelm your infrastructure **before the request reaches your Express application**.

For example:

```text
Internet
   ↓
Huge traffic volume
   ↓
Network / load balancer
   ↓
Node.js
```

If the network is already saturated, Express rate limiting can't save you.

Large-scale DDoS protection usually involves infrastructure such as:

```text
CDN
WAF
Load balancer
Cloud protection
Network-level filtering
```

So:

```text
Express rate limiter
≠
Complete DDoS protection
```

---

# 14. Rate limiting protects resources

Suppose this endpoint performs expensive work:

```http
GET /api/reports/huge-report
```

The request may cause:

```text
Controller
   ↓
Service
   ↓
Database
   ↓
Aggregation
   ↓
Large response
```

One request might be okay.

10,000 requests could be disastrous.

Rate limiting creates a boundary:

```text
Normal usage
    ↓
Allowed

Excessive usage
    ↓
Rejected
```

So rate limiting isn't only about security.

It's also about **resource protection**.

---

# 15. Rate limiting as a budget

A useful way to think about it:

> **Every client gets a request budget.**

Example:

```text
100 requests
per minute
```

The client has:

```text
Budget = 100
```

Requests consume the budget.

When the budget is exhausted:

```text
Budget = 0
```

the server says:

```http
429 Too Many Requests
```

Eventually the budget resets/refills depending on the algorithm.

---

# 16. Fixed window algorithm

One simple rate-limiting algorithm is the **fixed window**.

Suppose:

```text
100 requests / 60 seconds
```

You divide time into windows:

```text
12:00:00 ───────── 12:00:59
12:01:00 ───────── 12:01:59
12:02:00 ───────── 12:02:59
```

For each window:

```text
Counter = 0
```

Each request:

```text
Counter++
```

If:

```text
Counter > 100
```

reject.

At the next window:

```text
Counter = 0
```

---

# 17. Fixed-window problem

There is an interesting weakness.

Suppose the limit is:

```text
100 requests/minute
```

An attacker sends:

```text
100 requests
at 12:00:59
```

Then:

```text
100 requests
at 12:01:00
```

Technically:

```text
Window 1 → 100
Window 2 → 100
```

So the attacker sent:

```text
200 requests
in roughly 2 seconds
```

This is called a **boundary problem**.

That's why other algorithms exist.

---

# 18. Sliding window

A sliding-window approach looks at a moving period.

Instead of:

```text
12:00 → 12:01
```

you can ask:

> "How many requests happened during the last 60 seconds from right now?"

For example:

```text
Now = 12:00:40

Look back:
11:59:40 → 12:00:40
```

Then one second later:

```text
Now = 12:00:41

Look back:
11:59:41 → 12:00:41
```

The window moves continuously.

This can provide more natural rate limiting.

---

# 19. Token bucket

Another popular algorithm is the **token bucket**.

Imagine:

```text
        Bucket
    ┌─────────────┐
    │ ● ● ● ● ●   │
    │ ● ●         │
    └─────────────┘
```

Tokens are added at a controlled rate.

A request consumes one token.

If a token exists:

```text
Request
   ↓
Take token
   ↓
Allow
```

If no token exists:

```text
Request
   ↓
No token
   ↓
Reject / wait
```

This approach can allow controlled bursts while maintaining an average rate.

---

# 20. Leaky bucket

Another conceptual model is the **leaky bucket**.

Imagine requests entering:

```text
┌─────────────┐
│ Request     │
│ Request     │
│ Request     │
│ Request     │
└──────┬──────┘
       │
       ▼
      💧
       │
       ▼
    controlled
      flow
```

The idea is to process requests at a controlled rate.

Different algorithms have different characteristics.

For your starter, you don't need to implement every algorithm yourself.

But understanding them makes libraries much less mysterious.

# 21. What does an Express rate limiter store?

A rate limiter needs to remember something.

For example:

```text
IP
Request count
Time information
```

Conceptually:

```text
192.168.1.10
      ↓
37 requests
      ↓
current window
```

Then when the next request arrives:

```text
192.168.1.10
      ↓
38 requests
```

Eventually:

```text
101 requests
      ↓
Limit = 100
      ↓
429
```

# 22. Where is that state stored?

This is a very important backend concept.

### Simple/local limiter

State might live in:

```text
Node.js process memory
```

For example:

```text
Server process
   │
   └── rate-limit counters
```

This can work for development or small setups.

But there is a problem.

---

# 23. Multiple server instances

Imagine production has:

```text
              Load Balancer
              /     |     \
             /      |      \
          Node 1   Node 2   Node 3
```

Suppose a client sends:

```text
60 requests → Node 1
60 requests → Node 2
```

If each server keeps its own counter:

```text
Node 1 → 60
Node 2 → 60
Node 3 → 0
```

Each server might think:

```text
"I'm still below the limit."
```

But globally:

```text
60 + 60 = 120
```

The client exceeded the intended limit.

---

# 24. Shared rate-limit storage

For distributed systems, you often need shared state.

A common architecture is:

```text
              Load Balancer
              /     |     \
             /      |      \
          Node 1   Node 2   Node 3
             \       |       /
              \      |      /
                   Redis
```

Now all instances can access the same counters.

Conceptually:

```text
Client IP
   ↓
Shared counter
   ↓
All Node instances see it
```

This becomes especially important when you deploy horizontally.

---

# 25. Don't blindly use in-memory rate limiting in production

This is an important practical lesson.

In development:

```text
One Node process
```

In production:

```text
Multiple processes/containers
```

A local memory counter may not represent the whole application.

Also, restarting the server may erase the counters.

So rate limiting architecture depends on deployment architecture.

---

# 26. Rate limiting and proxies

There's another important issue.

Your application might not directly see the real client IP.

Imagine:

```text
User
  ↓
CDN
  ↓
Load Balancer
  ↓
Nginx
  ↓
Express
```

Express may see:

```text
Proxy IP
```

instead of:

```text
User IP
```

If your application incorrectly trusts proxy headers, your rate limiter may identify clients incorrectly.

This connects with Express's:

```js
app.set("trust proxy", ...);
```

configuration.

We'll discuss this more when we build the actual limiter.

# 27. Rate limit response headers

A good rate limiter can also communicate information to the client.

Conceptually:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

This tells the client:

> "Try again after approximately 30 seconds."

Depending on the rate-limiter implementation, you may also encounter standardized or library-specific headers describing limits and remaining quota.

The important idea:

```text
Server
  ↓
429
  +
retry information
  ↓
Client
```

This makes API behavior easier to understand.

---

# 28. What should the client do with 429?

Suppose your frontend receives:

```http
429 Too Many Requests
```

It shouldn't blindly retry immediately:

```text
Request
 ↓
429
 ↓
Request
 ↓
429
 ↓
Request
 ↓
429
```

That's actually making the problem worse.

Instead, clients can use:

```text
Retry-After
```

and/or an appropriate backoff strategy.

For example:

```text
wait
 ↓
retry
```

rather than:

```text
retry immediately forever
```

---

# 29. Rate limiting should not punish normal users

A good rate limit isn't:

```text
"Make the number as small as possible."
```

It's:

> **Set a reasonable limit based on expected behavior and endpoint cost.**

For example:

```text
GET /products
→ relatively generous

POST /login
→ much stricter

POST /forgot-password
→ very strict

GET /healthz
→ special consideration
```

Different endpoints have different security and resource requirements.

# 31. Rate limiting isn't authorization

Suppose:

```text
User A
```

is allowed to access:

```http
GET /api/admin/users
```

and:

```text
User B
```

is not.

That's **authorization**.

Rate limiting asks:

```text
How many requests can this client make?
```

So:

```text
Authorization
→ Can you do this?

Rate limiting
→ How often can you do this?
```

Very different questions.

---

# 32. Rate limiting isn't validation

Validation asks:

```text
Is this request data valid?
```

For example:

```json
{
    "email": "hello@example.com"
}
```

Rate limiting asks:

```text
How many requests has this client already made?
```

So:

```text
Validation
       ↓
Request correctness

Rate limiting
       ↓
Request frequency
```

---

# 33. Rate limiting isn't authentication

Authentication asks:

```text
Who are you?
```

Rate limiting asks:

```text
How many requests have you made?
```

They can work together.

For example:

```text
Authenticated user
      ↓
User-specific rate limit
```

This becomes especially useful for APIs where each user has a quota.

# 35. What happens when the limit is exceeded?

Conceptually:

```text
Request
   ↓
Rate limiter
   │
   ├── count = 1   → next()
   ├── count = 2   → next()
   ├── count = 3   → next()
   │
   ...
   │
   └── count = 101
          ↓
        429
```

The important thing is:

```text
next()
```

is **not called** when the request should be rejected.

So the request doesn't continue to the route.

# 37. A very important production concern: distributed attacks

Suppose one attacker sends:

```text
1000 requests
```

from:

```text
IP A
```

Easy to detect.

But another attacker might distribute traffic:

```text
IP A → 100
IP B → 100
IP C → 100
IP D → 100
...
```

So a mature security architecture may use several signals:

```text
IP
+
account
+
API key
+
route
+
global infrastructure controls
```

This is why **rate limiting is a security layer, not a complete abuse-prevention system**.

# 42. Interview questions

### Q1. What is rate limiting?

A mechanism that restricts how many requests a client can make during a defined period.

### Q2. What HTTP status code represents too many requests?

```http
429 Too Many Requests
```

### Q3. Is rate limiting the same as authentication?

No.

### Q4. Is IP the only way to identify a client?

No. You can also use user IDs, API keys, sessions, routes, or combinations.

### Q5. Does Express rate limiting completely prevent DDoS attacks?

No. Large-scale attacks may need infrastructure-level protection.

### Q6. Why can in-memory rate limiting be problematic with multiple servers?

Each server can have a different counter, so there is no shared global view of request usage.

### Q7. Why might Redis be used?

To provide shared rate-limit state across multiple application instances.
