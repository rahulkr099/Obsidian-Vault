# Lesson 10.12 — Global Rate Limiting

In **10.11**, we learned the idea behind rate limiting.

Now we're going to turn that idea into an actual Express middleware.

The goal is to understand code like:

```js
app.use(globalRateLimiter);
```

instead of treating it as security magic.

---

# 1. What is Global Rate Limiting?

A **global rate limiter** is a rate limiter applied broadly to your API.

Imagine your backend has:

```text
/api/users
/api/posts
/api/comments
/api/products
/api/orders
/api/profile
```

Instead of adding a limiter separately to every route:

```js
router.use(rateLimiter);
```

you can apply one middleware near the application level:

```js
app.use(globalRateLimiter);
```

Conceptually:

```text
                    Request
                       │
                       ▼
             Global Rate Limiter
                       │
             ┌─────────┴─────────┐
             │                   │
          Allowed             Exceeded
             │                   │
             ▼                   ▼
           next()              429
             │
             ▼
           Routes
```

---

# 2. Why Global Rate Limiting?

Suppose you have:

```text
100 different endpoints
```

If every endpoint needs basic abuse protection, manually doing:

```js
router.get("/users", limiter, ...);
router.get("/posts", limiter, ...);
router.get("/products", limiter, ...);
```

becomes repetitive.

Global middleware gives you a safety net:

```js
app.use(globalRateLimiter);
```

Now requests entering the application pass through the limiter.

---

# 3. A simple example

Let's imagine our policy is:

```text
100 requests
per 15 minutes
per client
```

We could conceptually configure:

```js
const globalRateLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100
});
```

Then:

```js
app.use(globalRateLimiter);
```

The important parts are:

```js
windowMs
limit
```

Let's understand them properly.

---

# 4. `windowMs`

This represents the time window.

```js
windowMs: 15 * 60 * 1000
```

Break it down:

```text
15 minutes
× 60 seconds
× 1000 milliseconds
```

Therefore:

```text
900,000 milliseconds
```

So:

```js
windowMs: 900000
```

and:

```js
windowMs: 15 * 60 * 1000
```

mean the same thing.

But this:

```js
15 * 60 * 1000
```

is much easier for humans to understand.

---

# 5. `limit`

This defines how many requests are allowed during the window.

For example:

```js
limit: 100
```

means approximately:

```text
100 requests
within the configured window
```

So:

```js
const limiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100
});
```

can be read as:

> Allow up to 100 requests per 15-minute window for each client tracked by the limiter.

---

# 6. What happens internally?

Imagine:

```text
IP = 192.168.1.10
```

The limiter maintains some state conceptually like:

```text
192.168.1.10
       │
       ├── requests: 73
       └── window: current
```

Request arrives:

```text
73 → 74
```

Another:

```text
74 → 75
```

Eventually:

```text
99 → 100
```

Still allowed.

Next request:

```text
100 → 101
```

The limit has been exceeded.

Therefore:

```http
429 Too Many Requests
```

---

# 7. The middleware flow

Think about it exactly like your other middleware.

```js
app.use(globalRateLimiter);
```

A request arrives:

```text
GET /api/users
       │
       ▼
globalRateLimiter
       │
       ├── under limit ──→ next()
       │                      │
       │                      ▼
       │                  /api/users
       │
       └── over limit ───→ 429
```

The route doesn't execute when the request is rejected.

---

# 8. Why `429` matters

Suppose the client sends too many requests.

Your server should communicate clearly:

```http
HTTP/1.1 429 Too Many Requests
```

This means:

> You have exceeded the allowed request rate.

This is much better than returning:

```http
500 Internal Server Error
```

because `500` means something went wrong on the server.

Rate limiting is intentional behavior, not a server crash.

---

# 9. Add a useful response message

You might configure a custom response:

```js
const globalRateLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100,

    message: {
        success: false,
        message: "Too many requests. Please try again later."
    }
});
```

Then an excessive request could receive something like:

```json
{
    "success": false,
    "message": "Too many requests. Please try again later."
}
```

The exact response structure should match your API's normal response conventions.

---

# 10. Don't leak unnecessary information

A rate-limit response doesn't need to explain your internal implementation.

You generally don't need:

```json
{
    "counter": 101,
    "server": "node-3",
    "redisKey": "rate-limit:192..."
}
```

That exposes implementation details.

Prefer something simple:

```json
{
    "success": false,
    "message": "Too many requests. Please try again later."
}
```

---

# 11. Rate-limit headers

A rate limiter can also communicate information through response headers.

Depending on the library and configuration, you may see headers describing things such as:

```text
Limit
Remaining
Reset
```

For example, conceptually:

```http
RateLimit-Limit: 100
RateLimit-Remaining: 37
```

This allows clients to understand their current quota.

You don't need to memorize exact header names yet.

The important concept is:

```text
Server
   ↓
"You have a limit."
   ↓
"You have X requests remaining."
```

---

# 12. Why clients benefit from this

Imagine your frontend makes requests automatically.

Without useful rate-limit information:

```text
Frontend
   ↓
Request
   ↓
429
   ↓
Request
   ↓
429
   ↓
Request
   ↓
429
```

That's bad behavior.

A good client can instead:

```text
429
 ↓
Read retry information
 ↓
Wait
 ↓
Retry
```

This is especially important for automated clients and SDKs.

---

# 13. `Retry-After`

A server may also communicate when the client should retry:

```http
Retry-After: 30
```

Conceptually:

```text
429
 ↓
Wait approximately 30 seconds
 ↓
Try again
```

This is much better than blindly retrying immediately.

---

# 14. Where should global rate limiting go?

This is where your middleware knowledge becomes important.

You might have:

```js
app.use(cors());
app.use(helmet());
app.use(globalRateLimiter);

app.use(express.json());

app.use("/api/users", userRoutes);
```

The exact order depends on your application's design and the middleware's behavior.

But conceptually:

```text
Incoming request
       ↓
Security / traffic controls
       ↓
Body parsing
       ↓
Routes
```

We'll study the complete ordering later in:

# **10.20 — Security Middleware Ordering**

For now, understand that **global middleware placement determines what it protects**.

---

# 15. Global doesn't necessarily mean literally everything

This is an important distinction.

Suppose you write:

```js
app.use(globalRateLimiter);
```

before:

```js
app.get("/healthz", healthController);
```

Then `/healthz` also passes through the limiter.

That may or may not be what you want.

For example:

```text
/api/*
   ↓
rate limited

/healthz
   ↓
possibly excluded
```

You may intentionally exclude certain endpoints.

---

# 16. Health checks are special

Infrastructure may repeatedly call:

```http
GET /healthz
```

For example:

```text
Load Balancer
     │
     ├── health check
     ├── health check
     ├── health check
     └── ...
```

If your global rate limit is too aggressive, you could accidentally block your own infrastructure.

So sometimes:

```text
Health check
    ↓
No application rate limit
```

or a separate policy makes more sense.

This is why you don't blindly apply the same rule everywhere.

---

# 17. Static assets can also be different

Suppose your server serves:

```text
/images/logo.png
/css/app.css
/js/app.js
```

These requests may have very different traffic patterns from:

```http
POST /api/auth/login
```

A global limiter can still be useful, but you should understand what traffic it covers.

This becomes important as your application grows.

---

# 18. Global rate limiting is a safety net

Think of it like:

```text
                    API
                     │
             Global limiter
                     │
        ┌────────────┼────────────┐
        │            │            │
      Users         Posts       Products
        │            │            │
        ▼            ▼            ▼
     Routes        Routes       Routes
```

The global limiter gives the whole API a baseline protection.

Then later:

```text
Global limiter
      +
Login limiter
      +
Password reset limiter
      +
Expensive endpoint limiter
```

This is much stronger.

---

# 19. Global limit vs authentication limit

Suppose:

```text
Global:
100 requests / 15 min
```

But:

```text
/login:
5 attempts / 15 min
```

A user could make:

```text
GET /products
GET /posts
GET /users
...
```

up to the global limit.

But repeated login attempts have a much smaller budget.

Why?

Because the security risk is different.

```text
Normal endpoint
    ↓
Moderate abuse risk

Login endpoint
    ↓
Credential attack risk
    ↓
Stricter limit
```

We'll build this in **10.13**.

---

# 20. A common beginner mistake

Don't do this:

```js
const limiter = rateLimit({
    windowMs: 1000,
    limit: 1
});
```

and think:

> "More security = better."

Now normal users might experience:

```text
Request 1 → ✓
Request 2 → 429
Request 3 → 429
Request 4 → 429
```

Your API becomes painful to use.

Security needs to balance:

```text
Security
+
Usability
+
Performance
```

---

# 21. How do you choose a limit?

There isn't one universal number.

You should consider:

```text
Expected traffic
Endpoint cost
User behavior
Authentication status
Business requirements
Infrastructure capacity
Attack scenarios
```

For example:

```text
GET /products
→ high volume

POST /login
→ low volume

POST /forgot-password
→ very low volume

GET /expensive-report
→ low volume
```

Therefore:

```text
One limit for everything
```

is usually not the final architecture.

---

# 22. Rate limiting and APIs

For an API, think in terms of **request budgets**.

For example:

```text
Anonymous client
    ↓
100 requests / 15 min

Authenticated user
    ↓
500 requests / 15 min

Sensitive endpoint
    ↓
5 requests / 15 min
```

These are only example policies.

Don't copy these numbers blindly into production.

Your application's actual usage should determine them.

---

# 23. The IP problem

Here's something you'll encounter when we implement this.

Suppose your application receives:

```text
User
 ↓
Nginx
 ↓
Node.js
```

Node may see the proxy's address rather than the user's actual address.

If your rate limiter uses the wrong address:

```text
Everyone
   ↓
Same proxy IP
   ↓
One shared rate-limit bucket
```

That could be disastrous.

So rate limiting depends on correctly understanding:

```text
reverse proxy
trust proxy
client IP
```

We'll return to this when the implementation requires it.

---

# 24. Distributed servers

Now imagine:

```text
             Load Balancer
             /     |     \
            /      |      \
        Node 1   Node 2   Node 3
```

If each Node process has its own in-memory counter:

```text
Node 1 → 80
Node 2 → 20
Node 3 → 0
```

the client has actually made:

```text
80 + 20 = 100
```

But each server sees only its own portion.

This is why distributed rate limiting often requires shared storage.

---

# 25. Redis architecture

A common design is:

```text
                  Load Balancer
                 /      |      \
                /       |       \
             Node 1   Node 2   Node 3
                \       |       /
                 \      |      /
                     Redis
```

The counter is stored centrally.

Conceptually:

```text
client identity
      ↓
Redis counter
      ↓
increment
      ↓
check limit
```

Now all application instances see the same state.

---

# 26. Why Redis is a good fit

Redis is commonly used because it is:

```text
Fast
In-memory
Shared
Good at counters
Supports expiration
```

Rate limits often need:

```text
increment counter
+
expire counter
```

which maps naturally to Redis-style operations.

But don't introduce Redis just because it sounds "production-grade."

For a single-process learning application:

```text
Memory
```

can be enough.

Architecture should match the deployment.

---

# 27. Development vs production

This distinction matters.

### Development

You may have:

```text
1 Node process
1 machine
low traffic
```

A simple limiter is fine for learning.

### Production

You might have:

```text
multiple containers
load balancer
CDN
reverse proxy
multiple regions
```

Now you need to think about shared state and infrastructure.

So:

```text
Development solution
≠
Production architecture
```

But the underlying concept remains the same.

---

# 28. A clean implementation

A simple middleware module could eventually look like:

```js
import rateLimit from "express-rate-limit";

export const globalRateLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100,
    standardHeaders: true,
    legacyHeaders: false
});
```

Then:

```js
import { globalRateLimiter } from "./middlewares/security/rateLimiter.middleware.js";

app.use(globalRateLimiter);
```

Now let's understand the options.

---

# 29. `standardHeaders`

Modern rate-limit libraries can expose rate-limit information using standardized headers.

Conceptually:

```js
standardHeaders: true
```

means:

```text
Include modern rate-limit headers
```

This is useful for API clients.

---

# 30. `legacyHeaders`

You may encounter:

```js
legacyHeaders: false
```

This tells the library not to generate older `X-RateLimit-*` style headers.

So a configuration might be:

```js
const globalRateLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100,

    standardHeaders: true,
    legacyHeaders: false
});
```

Again, the exact supported options depend on the version of the library you're using.

Always check the installed package's current API rather than copying an old tutorial.

---

# 31. Why configuration belongs in one place

Imagine putting this directly into `app.js`:

```js
app.use(
    rateLimit({
        windowMs: 15 * 60 * 1000,
        limit: 100
    })
);
```

That's not necessarily wrong.

But your starter architecture separates security middleware.

A cleaner structure is:

```text
middlewares/
└── security/
    └── rateLimiter.middleware.js
```

Then:

```js
app.use(globalRateLimiter);
```

Your application entry point stays clean.

---

# 32. Separation of concerns

This is another architecture lesson.

### `app.js`

Should answer:

> Which middleware is used?

```js
app.use(globalRateLimiter);
```

### `rateLimiter.middleware.js`

Should answer:

> How is rate limiting configured?

```js
const globalRateLimiter = rateLimit({
    ...
});
```

So:

```text
app.js
 ↓
composition

rateLimiter.middleware.js
 ↓
implementation
```

This separation becomes extremely valuable as your backend grows.

---

# 33. What if the client sends a valid request?

Suppose:

```http
GET /api/users
```

and the client has not exceeded the limit.

The limiter does:

```text
Check count
   ↓
Within limit
   ↓
next()
```

Then:

```text
next()
 ↓
Authentication
 ↓
Authorization
 ↓
Controller
 ↓
Service
 ↓
Repository
```

This is exactly how the middleware architecture you've been learning in Phase 7–9 connects with security.

---

# 34. What if the limit is exceeded?

The flow becomes:

```text
Request
   ↓
Rate limiter
   ↓
Limit exceeded
   ↓
429
   ↓
STOP
```

The request should not continue:

```text
❌ Controller
❌ Service
❌ Repository
❌ Database
```

That's one reason putting rate limiting early can save application resources.

---

# 35. A useful security principle

The earlier you reject obviously abusive traffic, the less work your application needs to perform.

Compare:

### Without early rate limiting

```text
Request
 ↓
Authentication
 ↓
Validation
 ↓
Controller
 ↓
Service
 ↓
Database
 ↓
Expensive work
 ↓
Reject
```

### With rate limiting

```text
Request
 ↓
Rate limiter
 ↓
Reject
```

The second path is cheaper.

---

# 36. But don't put everything before everything else

There's a subtle point.

You need enough information to identify the client correctly.

For example, some rate-limiting policies might depend on:

```text
User ID
```

But you don't know the user ID until authentication has happened.

Therefore:

```text
IP-based global limiter
```

can happen early.

But:

```text
authenticated-user limiter
```

may need to happen after authentication.

This is why middleware ordering is an architectural decision.

We'll study this deeply in **10.20**.

# 38. Mini challenge

Suppose:

```js
const limiter = rateLimit({
    windowMs: 60 * 1000,
    limit: 10
});
```

What does this mean?

### Answer

Each client can make up to approximately:

```text
10 requests
within the configured 1-minute window
```

before the limiter starts rejecting requests according to its configured behavior.

---

# 39. Another challenge

Suppose:

```text
Client A → 10 requests
Client B → 3 requests
Client C → 10 requests
```

with:

```text
limit = 10
```

Does Client B get blocked because A and C used their limits?

**No**, assuming the limiter tracks clients separately.

Conceptually:

```text
Client A → 10/10
Client B → 3/10
Client C → 10/10
```

The key word is:

> **per client**

The exact client-key behavior depends on the limiter configuration.

---

# 40. Important distinction: global application vs global client

When we say:

> "Global rate limiting"

we usually mean:

```text
Applied globally across the application
```

It does **not** necessarily mean:

```text
One shared limit for every user combined.
```

For example:

```text
Application
   │
   ├── Client A → 100
   ├── Client B → 100
   └── Client C → 100
```

That's a global middleware with per-client limits.

This distinction is important.

---

# 43. What to remember from 10.12

Keep these ten points:

1. **Global rate limiting** gives the API a broad request-frequency safety net.
    
2. `windowMs` defines the time window.
    
3. `limit` defines the allowed request count.
    
4. Excessive requests commonly receive **HTTP 429**.
    
5. Rate limiting is middleware, so it can call `next()` or stop the request.
    
6. Global doesn't mean one quota shared by every user.
    
7. Client identification is critical, especially behind proxies.
    
8. In-memory state is simple but doesn't naturally provide shared state across multiple servers.
    
9. Distributed deployments may need shared rate-limit storage.
    
10. A global limiter should usually be combined with **stricter limits for sensitive endpoints**.
