# Lesson 10.13 — Authentication Rate Limiting

In **10.12**, we built the idea of a **global rate limiter**.

Now we need to answer an important question:

> Why should `/login` have a different rate limit from `/products`?

Because authentication endpoints are a much more attractive target for attackers.

---

# 1. The login endpoint is special

Imagine your API has:

```http
GET /api/products
```

and:

```http
POST /api/auth/login
```

A normal user might request products many times:

```text
Products
Products
Products
Products
...
```

That's usually normal application behavior.

But repeatedly calling:

```http
POST /api/auth/login
```

with different passwords is suspicious.

For example:

```text
POST /login
email: rahul@example.com
password: password1

POST /login
email: rahul@example.com
password: password2

POST /login
email: rahul@example.com
password: password3

...
```

An attacker may be trying to discover the correct password.

Therefore:

```text
Normal API
   ↓
relatively generous limit

Authentication
   ↓
much stricter limit
```

---

# 2. Global limiter isn't enough

Suppose your global limiter is:

```text
100 requests / 15 minutes
```

An attacker can make:

```text
100 login attempts
```

before being blocked.

That's still a lot of password guesses.

So we can add a second limiter:

```text
Global limiter
      +
Login limiter
```

For example:

```text
Global:
100 requests / 15 minutes

Login:
5 requests / 15 minutes
```

These numbers are examples, not universal production values.

---

# 3. The middleware architecture

Imagine:

```text
                    Request
                       │
                       ▼
              Global Rate Limiter
                       │
                       ▼
                 /api/auth/login
                       │
                       ▼
              Login Rate Limiter
                       │
                 ┌─────┴─────┐
                 │           │
              Allowed      Exceeded
                 │           │
                 ▼           ▼
             Login       429
             handler
```

So the login endpoint gets **extra protection**.

---

# 4. Why authentication needs stricter protection

Authentication is often the gateway to everything else.

If an attacker successfully discovers credentials, they might gain access to:

```text
Profile
Orders
Private data
Messages
Admin functionality
Financial information
```

Therefore:

```text
Authentication security
        ↓
Very important
```

Rate limiting is one layer that helps protect it.

---

# 5. Authentication rate limiting vs global rate limiting

Let's compare.

### Global rate limiter

Question:

> "Is this client sending too many requests to my API?"

Example:

```text
100 requests / 15 minutes
```

### Authentication rate limiter

Question:

> "Is this client making too many authentication attempts?"

Example:

```text
5 login attempts / 15 minutes
```

So:

```text
Global limiter
→ broad protection

Authentication limiter
→ targeted protection
```

---

# 6. Example Express configuration

Conceptually:

```js
import rateLimit from "express-rate-limit";

const globalRateLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100
});

const loginRateLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 5
});
```

Then:

```js
app.use(globalRateLimiter);
```

and specifically:

```js
router.post(
    "/login",
    loginRateLimiter,
    loginController
);
```

Now:

```text
Every API request
        ↓
Global limiter

Login request
        ↓
Global limiter
        ↓
Login limiter
        ↓
Login controller
```

---

# 7. Why use two limits?

Suppose:

```text
Global = 100
Login = 5
```

A client makes:

```text
GET /products
GET /posts
GET /users
GET /comments
...
```

They can use the general API within the global limit.

But:

```text
POST /login
```

has a smaller budget.

This is called **layered protection**.

```text
       Global protection
              │
       ┌──────┴──────┐
       │             │
    Normal         Sensitive
    routes          routes
                      │
                stricter limit
```

---

# 8. But there's a problem with only using IP

Suppose the login limiter tracks only:

```text
IP address
```

An attacker could potentially distribute requests:

```text
IP 1 → 5 attempts
IP 2 → 5 attempts
IP 3 → 5 attempts
IP 4 → 5 attempts
```

If the application only sees each IP independently, every IP gets its own allowance.

So:

> **IP-based rate limiting alone is not perfect brute-force protection.**

This is why authentication protection often needs more thought.

---

# 9. Account-based protection

Suppose the attacker targets:

```text
rahul@example.com
```

Instead of only tracking the IP, we can conceptually track:

```text
Account
```

For example:

```text
rahul@example.com
     ↓
login attempts = 5
```

Now even if requests come from different IPs, repeated attempts against the same account can trigger additional protection.

Conceptually:

```text
IP-based
    +
Account-based
```

is stronger than either one alone.

---

# 10. But don't immediately reveal that an account exists

Here's an important security issue.

Suppose the attacker sends:

```json
{
    "email": "someone@example.com",
    "password": "wrong"
}
```

and your API responds:

```json
{
    "message": "User exists but password is incorrect"
}
```

Now the attacker knows:

> This email belongs to a real account.

That's called **user/account enumeration**.

A safer approach is generally to keep authentication failure messages generic, such as:

```text
Invalid email or password.
```

This way the attacker doesn't easily learn whether the account exists.

---

# 11. Rate limiting and account enumeration are related

Imagine an attacker tests:

```text
admin@example.com
test@example.com
rahul@example.com
john@example.com
...
```

If your API responds differently for valid and invalid accounts, they can discover which accounts exist.

Rate limiting can slow this activity down.

But rate limiting alone doesn't solve enumeration.

You need:

```text
Generic authentication errors
+
Rate limiting
+
Brute-force protection
+
Monitoring
```

---

# 12. Login failure counting

Another useful concept is counting failed authentication attempts.

For example:

```text
User account
    │
    ├── failed attempt 1
    ├── failed attempt 2
    ├── failed attempt 3
    └── failed attempt 4
```

After some threshold:

```text
Temporary protection
```

might be triggered.

However, this must be designed carefully.

---

# 13. Why permanent account lockouts can be dangerous

Imagine:

```text
5 failed attempts
       ↓
Account locked
```

An attacker could intentionally submit five wrong passwords for another user's account.

Now the legitimate user is locked out.

This is called a kind of **denial-of-service through account lockout**.

Therefore, modern systems often prefer combinations such as:

```text
Rate limiting
+
Progressive delays
+
Temporary restrictions
+
Additional verification
```

rather than simply permanently locking the account.

---

# 14. Progressive delays

Instead of immediately blocking:

```text
Attempt 1 → normal
Attempt 2 → normal
Attempt 3 → normal
Attempt 4 → wait
Attempt 5 → wait longer
Attempt 6 → longer still
```

Conceptually:

```text
Failure
  ↓
small delay
  ↓
Failure
  ↓
larger delay
  ↓
Failure
  ↓
larger delay
```

This makes automated guessing much more expensive.

We'll discuss this more deeply in **10.14 — Brute-Force Protection**.

---

# 15. Login rate limiting isn't password security

A common misconception is:

> "If I rate-limit login, passwords are secure."

No.

You still need:

```text
Strong password hashing
Secure authentication
Session/token security
Password policies
Credential protection
```

Rate limiting simply makes repeated guessing harder.

Think:

```text
Password hashing
        +
Authentication security
        +
Rate limiting
        +
Brute-force protection
```

Each solves a different problem.

---

# 16. Password hashing vs rate limiting

Suppose you store passwords using a secure password hashing algorithm.

That protects:

```text
Stored passwords
```

Rate limiting protects:

```text
Repeated login attempts
```

So:

```text
Hashing
→ protects credentials at rest

Rate limiting
→ restricts repeated attempts
```

You need both.

---

# 17. What about registration?

Authentication isn't only login.

Consider:

```http
POST /api/auth/register
```

An attacker might spam registrations:

```text
user1@example.com
user2@example.com
user3@example.com
...
```

This can create:

```text
Database spam
Fake accounts
Email abuse
Resource consumption
```

So registration may also deserve a specific rate limit.

---

# 18. Password reset is even more sensitive

Consider:

```http
POST /api/auth/forgot-password
```

This endpoint may trigger an email:

```text
Forgot password
      ↓
Generate token
      ↓
Send email
```

If unlimited:

```text
Attacker
   ↓
1000 password-reset requests
   ↓
1000 emails
```

That can become:

```text
Email abuse
Cost
Spam
Denial of service
```

So password-reset endpoints often deserve strict limits too.

---

# 19. OTP endpoints

If your application uses OTP:

```http
POST /api/auth/send-otp
```

this is another obvious target.

Without rate limiting:

```text
Send OTP
Send OTP
Send OTP
Send OTP
...
```

could cause:

```text
SMS costs
Email costs
User annoyance
Abuse
```

So:

```text
OTP sending
→ strict rate limiting
```

is very important.

---

# 20. Different authentication endpoints

Your eventual security design might look like:

```text
/api/auth/login
    ↓
Strict limiter

/api/auth/register
    ↓
Moderate limiter

/api/auth/forgot-password
    ↓
Strict limiter

/api/auth/send-otp
    ↓
Very strict limiter
```

There isn't one universal configuration.

The business behavior of the endpoint matters.

---

# 21. Rate limiting based on IP + account

A useful conceptual model is:

```text
              Login attempt
                    │
           ┌────────┴────────┐
           │                 │
          IP              Account
           │                 │
           ▼                 ▼
     IP attempt count   Account attempts
           │                 │
           └────────┬────────┘
                    ▼
               Security decision
```

For example:

```text
IP limit:
20 attempts / 15 min

Account limit:
5 attempts / 15 min
```

These are merely illustrative numbers.

The idea is:

> An attacker should have difficulty bypassing protection by changing only one identifier.

---

# 22. Why not only use account-based limiting?

Because the attacker can attack many accounts.

Imagine:

```text
attacker
   │
   ├── user1
   ├── user2
   ├── user3
   ├── user4
   └── ...
```

If each account has its own limit, the attacker might distribute attempts.

Therefore:

```text
IP protection
+
Account protection
```

provides better coverage.

---

# 23. Why not only use IP-based limiting?

Because attackers can distribute across IP addresses.

Also:

```text
NAT
VPN
Mobile networks
Corporate networks
College networks
```

can cause many legitimate users to share an IP.

So neither IP nor account alone is perfect.

---

# 24. The important security principle

Don't think:

> "I need one perfect identifier."

Instead think:

> **Use multiple signals to make abuse expensive while minimizing harm to legitimate users.**

This is a much more realistic security mindset.

---

# 25. Route-specific middleware

You already know how Express route middleware works.

For example:

```js
router.post(
    "/login",
    loginRateLimiter,
    loginController
);
```

The flow is:

```text
POST /login
     │
     ▼
loginRateLimiter
     │
     ├── allowed → next()
     │
     └── blocked → 429
                       ↓
                  controller never runs
```

This is exactly the same middleware concept you've learned earlier.

The only difference is that the middleware has a security purpose.

---

# 26. Where should login limiting happen?

A simplified flow could be:

```text
Request
   ↓
CORS
   ↓
Global rate limiter
   ↓
Login-specific rate limiter
   ↓
Input validation
   ↓
Login controller
   ↓
Authentication
```

But don't memorize this as the final universal ordering.

There are subtle questions involving:

```text
Body parsing
IP identification
Proxy configuration
Authentication
Validation
Error handling
```

We'll reason about complete ordering later.

---

# 27. Don't rate-limit only successful logins

Suppose:

```text
Successful login = 1
Failed login = 1
```

The attacker is interested in failed attempts.

Therefore, your security system needs to consider **failed authentication attempts**, not just successful requests.

For example:

```text
Request
 ↓
Login attempt
 ↓
Authentication fails
 ↓
Increment failure-related protection
```

This is one of the concepts we'll expand in 10.14.

---

# 28. What if the attacker knows a valid password?

Rate limiting is still useful.

Suppose an attacker has stolen credentials:

```text
email + password
```

They may attempt to access the account repeatedly from different locations.

Rate limiting can still provide:

```text
Traffic control
Anomaly reduction
Credential abuse protection
```

But you may also need:

```text
MFA
Session controls
Device detection
Suspicious-login detection
```

Rate limiting is one layer, not the entire authentication security system.

---

# 29. Rate limiting and CAPTCHA

You may have seen:

```text
"I'm not a robot"
```

CAPTCHA can be another layer.

A possible escalation flow:

```text
Normal attempts
      ↓
No CAPTCHA

Suspicious behavior
      ↓
CAPTCHA

Continued abuse
      ↓
Rate limiting / temporary restriction
```

The exact design depends on your application.

The important idea:

> Security controls can be layered.

---

# 30. Don't make the user experience terrible

Security can go too far.

Imagine a normal user accidentally enters the wrong password:

```text
Attempt 1 → wrong
Attempt 2 → wrong
Attempt 3 → wrong
```

If you immediately:

```text
LOCK ACCOUNT FOREVER
```

that's terrible UX and can itself become an attack vector.

Better designs often use:

```text
Short delays
Temporary limits
Clear generic messaging
Additional verification
```

instead of overly aggressive permanent locks.

---

# 31. Example policy

Imagine we choose:

```text
Global API
100 requests / 15 min

Login
5 attempts / 15 min

Forgot password
3 requests / 15 min

Send OTP
3 requests / 10 min
```

Again, these are educational examples.

The architecture would be:

```text
                    API
                     │
              Global limiter
                     │
        ┌────────────┼────────────┐
        │            │            │
      Users        Login       OTP
                     │            │
                 strict        strict
                 limiter       limiter
```

---

# 32. One subtle issue: response timing

Imagine your login endpoint behaves differently:

```text
User doesn't exist
→ responds immediately

User exists
→ password hash checked
→ responds later
```

An attacker might measure response time to guess whether an account exists.

This is called a **timing side channel**.

Authentication security therefore isn't only about:

```text
status code
```

but can also involve:

```text
response message
response behavior
timing
```

This is beyond basic rate limiting, but it's useful to understand the bigger picture.

---

# 33. Authentication rate limiting in your starter

Your starter's security layer includes rate-limiting middleware, so eventually the architecture should make the distinction between:

```text
Global rate limiter
```

and:

```text
Authentication-specific protection
```

clear.

The goal isn't to create one huge middleware that does everything.

Instead:

```text
global limiter
     ↓
general protection

auth limiter
     ↓
authentication protection

brute-force logic
     ↓
repeated credential attack protection
```

Each layer has a focused responsibility.

---

# 34. Separation of responsibilities

A clean architecture might look like:

```text
rateLimiter.middleware.js
        │
        ├── globalRateLimiter
        └── authRateLimiter
```

But as the project becomes more complex, you may decide to separate them further.

The important principle is:

> **Don't put unrelated security decisions into one giant middleware.**

For example, avoid:

```js
securityMiddleware()
```

containing:

```text
CORS
Helmet
rate limiting
authentication
authorization
validation
sanitization
logging
```

That's difficult to understand and maintain.

---

# 35. The attack we're trying to slow down

Imagine:

```text
Attacker
   │
   ├── password123
   ├── password1234
   ├── admin123
   ├── qwerty123
   ├── letmein
   └── ...
```

Without rate limiting:

```text
Thousands of attempts
       ↓
Fast
       ↓
Cheap
```

With authentication rate limiting:

```text
Attempts
   ↓
Limited
   ↓
Slower
   ↓
More expensive
```

The objective is not necessarily:

> "Make attacks mathematically impossible."

It's:

> **Make automated abuse much harder and slower while protecting legitimate users.**

---

# 36. A key security mindset

Security controls often work by increasing the **cost of attack**.

For example:

```text
Password hashing
→ makes password cracking expensive

Rate limiting
→ makes repeated requests expensive

MFA
→ makes stolen-password attacks harder

CAPTCHA
→ makes automation harder
```

This is a very useful way to think about security.

# 37. Mini exercise 🧠

Suppose your API has:

```text
Global limit:
100 requests / 15 min

Login limit:
5 requests / 15 min
```

A client sends:

```text
GET /products × 50
POST /login × 5
```

Can they still make another:

```text
GET /products
```

assuming all requests are within the same window and no other rule applies?

**Yes.**

Why?

Because:

```text
Global:
50 / 100

Login:
5 / 5
```

The login budget is exhausted, but the global budget isn't.

So:

```text
GET /products
→ potentially allowed

POST /login
→ blocked
```

This is exactly why multiple rate-limit layers are useful.

A client sends:


Then sends:

```text
POST /login
```

What happens?

```text
Global count:
6 / 100

Login count:
6 / 5
```

```text
Login limiter
      ↓
429 Too Many Requests
```

The global limit isn't the problem.

The **route-specific limit** is.

# 39. Interview questions

### Q1. Why should login have a stricter rate limit?

Because repeated login attempts can be used for credential guessing and brute-force attacks.

### Q2. Is global rate limiting enough?

Not necessarily. Sensitive endpoints often need stricter, route-specific limits.

### Q3. Should authentication rate limiting use only IP addresses?

Not necessarily. IP-based and account-based signals can complement each other.

### Q4. Why can account lockouts be dangerous?

Attackers can intentionally trigger failed attempts against another user's account and prevent that user from logging in.

### Q5. What other endpoints may need strict rate limits?

Common examples include:

```text
Login
Password reset
OTP sending
Registration
Email verification
```

### Q6. Does rate limiting replace MFA?

No.

### Q7. What is the purpose of authentication rate limiting?

To make repeated authentication abuse and credential-guessing attacks harder and slower.
