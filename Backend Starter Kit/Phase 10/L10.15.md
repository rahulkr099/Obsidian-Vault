# Lesson 10.15 — MongoDB Injection

This is an important lesson because now we're moving from **HTTP-level security** into **database-level security**.

Your Phase 10 specifically places:

```text
10.15 MongoDB injection
10.16 express-mongo-sanitize
```

in this order. The purpose is to first understand **the attack**, and only then understand **the middleware that helps defend against it**.

---

# 1. First: what is injection?

The basic idea of injection is:

> **The attacker provides input that changes the meaning of something your application intended to treat as data.**

For example, imagine you expect:

```json
{
  "email": "rahul@example.com"
}
```

Your backend builds a MongoDB query:

```js
User.findOne({
    email: req.body.email
});
```

Normally:

```text
req.body.email
      ↓
"rahul@example.com"
      ↓
MongoDB query
```

That's fine.

But what if the attacker doesn't send a normal string?

What if they send an object containing a MongoDB query operator?

That's where the problem begins.

---

# 2. MongoDB queries are objects

This is the key thing you need to understand.

A MongoDB query can look like:

```js
{
    email: "rahul@example.com"
}
```

But MongoDB also supports **operators**.

For example:

```js
{
    age: {
        $gt: 18
    }
}
```

means roughly:

```text
age greater than 18
```

Another example:

```js
{
    role: {
        $in: ["admin", "manager"]
    }
}
```

means:

```text
role is admin OR manager
```

So MongoDB doesn't just understand:

```text
field → value
```

It also understands:

```text
field → operator → value
```

That's powerful for developers.

But it also means:

> **Untrusted user input must not accidentally become part of your query structure.**

---

# 3. A normal login query

Imagine your login code does:

```js
const user = await User.findOne({
    email: req.body.email
});
```

You expect:

```json
{
  "email": "rahul@example.com"
}
```

Then:

```js
req.body.email
```

is:

```text
"rahul@example.com"
```

So the query becomes:

```js
{
    email: "rahul@example.com"
}
```

Everything is normal.

---

# 4. What if the input is an object?

Now imagine someone sends something conceptually like:

```json
{
  "email": {
    "$ne": null
  }
}
```

Now your application might construct:

```js
{
    email: {
        $ne: null
    }
}
```

That no longer means:

```text
email equals this string
```

It means something like:

```text
email is not equal to null
```

That is a completely different query.

The attacker has influenced the **query structure**.

That's the basic idea behind MongoDB operator injection.

---

# 5. Why `$ne` is important

You will see MongoDB operators repeatedly in security discussions.

One is:

```text
$ne
```

which means:

```text
not equal
```

For example:

```js
{
    username: {
        $ne: "admin"
    }
}
```

means:

```text
username != "admin"
```

Another:

```js
{
    password: {
        $ne: null
    }
}
```

means:

```text
password is not null
```

The important security lesson isn't memorizing every MongoDB operator.

It's understanding:

> **Operators change query meaning.**

---

# 6. `$gt`

Another operator:

```text
$gt
```

means:

```text
greater than
```

Example:

```js
{
    age: {
        $gt: 18
    }
}
```

means:

```text
age > 18
```

Again, completely legitimate when **you**, the developer, intentionally create the query.

The security problem happens when:

```text
untrusted input
      ↓
becomes
      ↓
MongoDB operator
```

without you intending it.

---

# 7. `$in`

Another operator:

```text
$in
```

Example:

```js
{
    role: {
        $in: ["admin", "manager"]
    }
}
```

means:

```text
role is one of these values
```

Again:

```text
Developer-controlled operator
→ useful

Attacker-controlled operator
→ potentially dangerous
```

That's the distinction to remember.

---

# 8. `$regex`

MongoDB also supports:

```text
$regex
```

for pattern matching.

For example:

```js
{
    username: {
        $regex: "^rah"
    }
}
```

This could find usernames beginning with `rah`.

Again, perfectly valid MongoDB functionality.

But if you allow arbitrary user input to control query operators or expressions, you can create security and performance problems.

---

# 9. The dangerous boundary

Look at this:

```text
                 HTTP REQUEST
                      │
                      ▼
                 req.body
                      │
                      │ UNTRUSTED
                      ▼
                Your application
                      │
                      ▼
                MongoDB query
                      │
                      ▼
                   MongoDB
```

The important boundary is:

```text
UNTRUSTED INPUT
       ↓
DATABASE QUERY
```

You need to control what crosses that boundary.

---

# 10. Never think `req.body` is safe

This is one of the biggest lessons from your previous **Validation** phase.

Don't think:

```js
req.body
```

means:

```text
safe data
```

It means:

```text
data supplied by the client
```

And the client is controlled by:

```text
the user
```

or potentially:

```text
an attacker
```

So:

```js
req.body.email
```

must be treated as untrusted until your application validates and processes it appropriately.

---

# 11. JSON doesn't mean safe

You might think:

> "But JSON is structured. How can it be dangerous?"

Because JSON can contain objects.

For example:

```json
{
  "email": "rahul@example.com"
}
```

is normal.

But JSON can also contain:

```json
{
  "email": {
    "$ne": null
  }
}
```

It's still valid JSON.

The problem isn't:

```text
JSON
```

The problem is:

```text
untrusted structure
      ↓
database query
```

---

# 12. The application expects a string

Suppose your API specification says:

```text
email → string
```

You expect:

```json
{
  "email": "rahul@example.com"
}
```

But an attacker sends:

```json
{
  "email": {
    "$ne": null
  }
}
```

Now:

```text
Expected:
string

Received:
object
```

This is exactly why **validation** and **sanitization** matter.

---

# 13. Validation is the first important defense

From Phase 9, you learned:

```text
Request
   ↓
Validation
   ↓
Controller
```

For example:

```js
email: Joi.string().email().required()
```

This expresses:

> `email` should be a valid string email.

So:

```text
"rahul@example.com"
```

can pass.

But:

```js
{
    $ne: null
}
```

isn't a string.

Therefore, strong validation can reject the input.

This is one reason your roadmap deliberately puts:

```text
Phase 9 → Validation
Phase 10 → Security
```

in that order.

---

# 14. But validation and sanitization aren't the same

This distinction is extremely important.

### Validation

Asks:

> **Is this input allowed?**

Example:

```text
email must be a string email
```

### Sanitization

Asks:

> **Can we clean or transform this input into a safer form?**

Example:

```text
Remove dangerous MongoDB operator keys
```

So:

```text
Validation
    ↓
"Is this acceptable?"

Sanitization
    ↓
"Can this input be cleaned/normalized?"
```

We'll explore this distinction again in **10.18**.

---

# 15. Why MongoDB injection is different from SQL injection

You've probably heard of:

```text
SQL Injection
```

MongoDB is not SQL.

MongoDB queries are generally represented as JavaScript-like objects.

For example:

```js
{
    email: "rahul@example.com"
}
```

rather than:

```sql
SELECT * FROM users WHERE email = '...'
```

So the attack mechanism is different.

But the underlying security principle is similar:

> **Don't allow untrusted input to control the structure or behavior of your database query.**

---

# 16. SQL injection mental model

Traditional SQL injection often looks conceptually like:

```text
User input
   ↓
SQL string
   ↓
SQL syntax changes
```

MongoDB operator injection can look more like:

```text
User input
   ↓
MongoDB query object
   ↓
MongoDB operator appears
   ↓
Query meaning changes
```

So:

```text
SQL injection
→ manipulate SQL syntax

MongoDB injection
→ manipulate MongoDB query structure/operators
```

The underlying lesson is the same:

```text
Never blindly trust input.
```

---

# 17. A dangerous pattern

Be careful with code where you directly use an entire user-controlled object as a query.

For example:

```js
User.findOne(req.body);
```

This is much more dangerous than:

```js
User.findOne({
    email: req.body.email
});
```

Why?

Because the first version effectively says:

> "Client, tell me what MongoDB query I should execute."

That's a terrible boundary.

---

# 18. Explicit fields are safer

Prefer:

```js
User.findOne({
    email: req.body.email
});
```

rather than:

```js
User.findOne(req.body);
```

Now you control the query structure:

```text
Developer
   ↓
defines fields
   ↓
defines operators
   ↓
defines query
```

The user only supplies:

```text
field values
```

This is a much better architecture.

---

# 19. Allow-listing

This connects directly with your validation lessons.

Suppose your endpoint accepts:

```json
{
  "email": "rahul@example.com",
  "name": "Rahul"
}
```

You shouldn't automatically pass everything from `req.body` into your database.

Instead:

```js
const { email, name } = req.body;

const user = await User.findOne({
    email
});
```

You control what is used.

Conceptually:

```text
Client
 ↓
many possible fields
 ↓
allow-list
 ↓
known fields
 ↓
database
```

---

# 20. Why `req.body` spreading can be dangerous

Be careful with patterns like:

```js
User.findOne({
    ...req.body
});
```

The spread operator isn't inherently dangerous.

The problem is:

```text
What does req.body contain?
```

If an attacker can provide unexpected properties or nested objects, you may accidentally let them influence the query.

Better:

```js
const { email } = req.body;

User.findOne({
    email
});
```

Now the query structure is controlled by your code.

---

# 21. Another dangerous pattern: dynamic filters

Suppose you create an endpoint:

```http
GET /users?filter=...
```

and try to convert the user's filter directly into MongoDB syntax.

For example:

```js
User.find(req.query.filter);
```

This creates a dangerous boundary:

```text
URL query
   ↓
MongoDB query
```

Now your client can potentially influence query structure.

If you need filtering, design it explicitly.

For example:

```text
GET /users?role=admin
```

then your server creates:

```js
User.find({
    role: "admin"
});
```

The server controls the query.

---

# 22. Search APIs need care too

Imagine:

```http
GET /users?search=rahul
```

You might intentionally create:

```js
User.find({
    name: {
        $regex: search
    }
});
```

That's okay **if your application intentionally controls the operator**.

The user controls:

```text
search
```

but the application controls:

```text
$regex
```

This distinction is important.

```text
User controls:
"rahul"

Server controls:
$regex
```

That's much safer than letting the user submit arbitrary query operators.

---

# 23. Developer-controlled operator vs attacker-controlled operator

Compare these.

### Good architecture

```js
User.find({
    name: {
        $regex: search
    }
});
```

Here:

```text
$regex → developer controlled
search → user controlled
```

### Dangerous architecture

```js
User.find({
    name: req.body.name
});
```

where `name` can itself be an arbitrary object.

Now potentially:

```text
name
 ↓
{
   $regex: ...
}
```

can be supplied by the client.

That's the security boundary we're concerned about.

---

# 24. What is MongoDB operator injection?

A simple definition:

> **MongoDB operator injection occurs when untrusted input is able to introduce MongoDB operators into a query in a way the application did not intend.**

For example, conceptually:

```text
Expected:

email = "rahul@example.com"


Attacker:

email = {
    "$ne": null
}
```

The second input is no longer simply a value.

It contains query logic.

---

# 25. Why authentication is a common target

Login endpoints are especially interesting.

Consider:

```js
User.findOne({
    email: req.body.email
});
```

Attackers may try to manipulate the query so that:

```text
authentication logic
       ↓
behaves differently
```

This is why MongoDB injection becomes especially important around:

```text
Login
User lookup
Authorization
Search
Filtering
Admin queries
```

---

# 26. MongoDB injection can also be a DoS concern

Not every injection problem is about:

```text
"Can I log in?"
```

Some query operators or expensive patterns can potentially cause expensive database work.

For example:

```text
complex regular expressions
large queries
uncontrolled filters
```

could increase:

```text
CPU usage
database load
response time
```

So secure query construction also protects **availability**.

---

# 27. Security is about query ownership

Here's a powerful mental model:

### Bad

```text
Client
  ↓
defines query
  ↓
MongoDB
```

### Better

```text
Client
  ↓
provides values
  ↓
Application
  ↓
defines query
  ↓
MongoDB
```

Think:

> **The client should provide data, not database instructions.**

That's one of the best sentences to remember from this lesson.

# 28. Where does `mongoSanitize()` fit?

Now your starter code begins to make sense:

```js
app.use(mongoSanitize());
```

The middleware exists as an additional defense against MongoDB operator injection.

Conceptually:

```text
Request
   ↓
Mongo sanitization
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

But don't misunderstand this.

`mongoSanitize()` does **not** mean:

> "My MongoDB queries are now automatically secure."

It's a **defense-in-depth** layer.

We'll study exactly what `express-mongo-sanitize` does in **10.16**.

# 29. Defense in depth

This is another important security principle.

Don't rely on one protection.

Instead:

```text
                  Untrusted Input
                        │
                        ▼
                  ┌─────────────┐
                  │ Validation  │
                  └──────┬──────┘
                         ▼
                 ┌──────────────┐
                 │ Sanitization │
                 └──────┬───────┘
                        ▼
                 Explicit queries
                        │
                        ▼
                    MongoDB
```

If one layer makes a mistake, another layer may reduce the damage.

This is called:

> **Defense in depth.**

---

# 30. Don't put MongoDB operators everywhere

Suppose your application intentionally needs:

```js
{
    age: {
        $gte: 18
    }
}
```

That's fine.

The problem isn't:

```text
MongoDB operators
```

The problem is:

```text
UNTRUSTED user input
        ↓
UNCONTROLLED MongoDB operators
```

So don't fall into the beginner mistake:

> "All `$` operators are bad."

No.

They're normal MongoDB functionality.

The question is:

> **Who controls them?**

---

# 31. A useful example

Suppose you have:

```http
GET /products?minPrice=100
```

Your server can intentionally create:

```js
Product.find({
    price: {
        $gte: Number(minPrice)
    }
});
```

Here:

```text
Client controls:
100

Server controls:
$gte
price
query structure
```

That's a reasonable architecture.

But if you allow the client to provide the entire MongoDB filter:

```json
{
    "price": {
        "$gte": 100
    }
}
```

and blindly use it:

```js
Product.find(req.body.filter);
```

the security boundary becomes much weaker.

---

# 32. Validation gives you another boundary

Suppose:

```text
minPrice
```

must be:

```text
number
```

Your validation can enforce:

```js
minPrice: Joi.number().min(0)
```

Now:

```text
"100"
```

can be normalized/converted according to your validation strategy.

But:

```text
{
    "$gte": 100
}
```

is not a number.

So validation blocks unexpected structures.

---

# 33. Sanitization isn't a replacement for validation

This deserves repeating.

Imagine:

```text
Input
 ↓
mongoSanitize()
 ↓
MongoDB
```

You might think you're done.

You're not.

A secure application should still have:

```text
Input
 ↓
Validation
 ↓
Sanitization where appropriate
 ↓
Application logic
 ↓
Controlled database query
```

Your Phase 9 specifically teaches validation, including **whitelisting fields, stripping unknown fields, and the distinction between validation and sanitization**.

---

# 34. A secure mental model for repository code

Later, when you build:

```text
repositories/user.repository.js
```

you want something conceptually like:

```js
async findByEmail(email) {
    return User.findOne({
        email
    });
}
```

The repository controls:

```text
query structure
```

while the service supplies:

```text
email value
```

So:

```text
Service
  ↓
"Find this email"

Repository
  ↓
"Okay, I know how to query MongoDB."

MongoDB
```

This is another reason your architecture separates services and repositories. The roadmap explicitly teaches repositories as the database-query layer.

---

# 35. Don't trust even internal-looking data

Suppose you have:

```js
userId = req.user.id;
```

You might think:

> "This is trusted."

But your security design should still be deliberate about how values enter queries.

For example:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

is better than allowing the client to submit an entire query.

Your roadmap later emphasizes ownership queries such as:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

to prevent users from accessing another user's resources.

---

# 36. A very important rule

Whenever you write:

```js
Model.find(...)
Model.findOne(...)
Model.findById(...)
Model.updateOne(...)
Model.deleteOne(...)
```

ask yourself:

> **Which parts of this query are controlled by my application, and which parts came from the client?**

For example:

```js
User.findOne({
    email: req.body.email
});
```

Ask:

```text
email value → client controlled
query structure → server controlled
```

Good.

But:

```js
User.findOne(req.body);
```

Ask:

```text
query structure → client controlled
```

That's a red flag.
