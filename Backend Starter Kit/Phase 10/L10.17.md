# Lesson 10.17 — HTTP Parameter Pollution (HPP)

Now we move from **MongoDB injection** to a different kind of problem:

```text
HTTP Parameter Pollution
        ↓
HPP
        ↓
app.use(hpp());
```

Your starter contains:

```js
app.use(hpp());
```

The goal of this lesson is to understand **why duplicate HTTP parameters can become a security or logic problem**, before we learn how the `hpp` middleware handles them.

---

# 1. What is HTTP Parameter Pollution?

HTTP Parameter Pollution means sending the **same parameter multiple times** in one HTTP request.

For example:

```http
GET /users?role=user&role=admin
```

The parameter:

```text
role
```

appears twice.

That's the basic idea.

Normally, you might expect:

```text
role = user
```

or:

```text
role = admin
```

But now there are two values.

So the question becomes:

> **What should the application do with them?**

That's where problems can start.

---

# 2. A normal query parameter

Imagine:

```http
GET /products?category=books
```

Your Express application might see:

```js
req.query.category
```

as:

```text
"books"
```

Simple.

The flow is:

```text
Browser
   ↓
/products?category=books
   ↓
Express
   ↓
req.query.category
   ↓
"books"
```

No problem.

---

# 3. Now duplicate it

An attacker can send:

```http
GET /products?category=books&category=electronics
```

Now:

```text
category
   ↓
books
electronics
```

There are multiple values for the same parameter.

Depending on the framework/parser/configuration, the application may represent this as an array:

```js
req.query.category
```

could conceptually become:

```js
[
    "books",
    "electronics"
]
```

This is the important part:

> **A parameter you thought was a string may become an array when duplicated.**

---

# 4. Why is that dangerous?

Suppose your application expects:

```text
role → string
```

and you write:

```js
const role = req.query.role;
```

Normally:

```text
role = "user"
```

But a polluted request might produce:

```js
role = ["user", "admin"];
```

Now your application has to decide:

```text
What does this mean?
```

If your code wasn't designed for this, unexpected behavior can happen.

---

# 5. The security problem is ambiguity

This is the key concept.

Suppose:

```http
?role=user&role=admin
```

What does the request mean?

Possibilities:

```text
role = user
```

or:

```text
role = admin
```

or:

```text
role = ["user", "admin"]
```

or:

```text
first value wins
```

or:

```text
last value wins
```

Different layers of an application may interpret it differently.

That creates:

> **ambiguity**

And ambiguity in security-sensitive code is dangerous.

---

# 6. Think about validation

Imagine your validation schema says:

```js
role: Joi.string()
```

You expect:

```json
{
  "role": "user"
}
```

But the attacker sends:

```text
?role=user&role=admin
```

Now your application may receive:

```js
role: ["user", "admin"]
```

Your validation layer might:

```text
reject it
```

which is good.

But if your validation and business logic don't handle duplicate parameters consistently, you can get unexpected behavior.

---

# 7. The important question

Whenever you accept HTTP parameters, ask:

> **Can this parameter appear more than once?**

For example:

```text
?page=2
?limit=20
?role=admin
?sort=createdAt
```

You might assume each is a single value.

But HTTP requests can contain:

```text
?page=2&page=3
```

```text
?limit=20&limit=100
```

```text
?role=user&role=admin
```

So your backend must have a clear policy.

---

# 8. A simple Express example

Imagine:

```js
app.get("/products", (req, res) => {
    const category = req.query.category;

    console.log(category);
});
```

Normal request:

```http
GET /products?category=books
```

Conceptually:

```js
category === "books"
```

Duplicate request:

```http
GET /products?category=books&category=electronics
```

may become:

```js
category === ["books", "electronics"]
```

The exact parsing behavior depends on your query parser configuration, but the important lesson is:

> **Don't assume query parameters are always single strings.**

---

# 9. Why HPP exists

The `hpp` middleware is designed to help protect applications from **HTTP Parameter Pollution**.

Your starter:

```js
app.use(hpp());
```

means conceptually:

```text
HTTP request
     ↓
duplicate parameters
     ↓
HPP middleware
     ↓
normalized/handled parameters
     ↓
application
```

The middleware helps establish a predictable behavior for duplicate parameters.

---

# 10. HPP is not the same as validation

Just like our previous lesson:

```text
mongoSanitize
≠
validation
```

Similarly:

```text
hpp
≠
validation
```

HPP addresses:

```text
duplicate HTTP parameters
```

Validation addresses:

```text
Is this value the correct type?
Is it allowed?
Is it required?
Does it satisfy constraints?
```

They are different responsibilities.

---

# 11. Why duplicate parameters matter in real applications

Let's imagine a pagination endpoint:

```http
GET /users?page=2&limit=20
```

Your code:

```js
const page = Number(req.query.page);
const limit = Number(req.query.limit);
```

Looks simple.

But what about:

```http
GET /users?page=2&page=999999
```

Now:

```text
page
 ↓
multiple values
```

If one layer uses:

```text
first value
```

and another uses:

```text
last value
```

you can get inconsistent behavior.

---

# 12. Security-sensitive example

Imagine an endpoint:

```http
GET /reports?format=json
```

The application expects:

```text
format = "json"
```

Now someone sends:

```http
GET /reports?format=json&format=csv
```

One piece of code might see:

```text
json
```

while another might see:

```text
csv
```

If different components interpret the request differently, you have a **parser discrepancy**.

This general class of problem is important in web security.

---

# 13. Authorization example

Suppose you have:

```http
GET /admin?role=admin
```

and some middleware checks:

```js
if (req.query.role === "admin") {
    // allow
}
```

Now someone sends:

```http
GET /admin?role=user&role=admin
```

If the value becomes an array:

```js
["user", "admin"]
```

then the strict comparison:

```js
req.query.role === "admin"
```

may fail.

But if another part of your application converts or interprets the parameter differently, you could get inconsistent behavior.

The lesson isn't that this exact code is automatically exploitable.

The lesson is:

> **Security decisions should not depend on ambiguous input.**

---

# 14. Business logic example

Suppose you have:

```http
POST /coupon?discount=10
```

Your application expects:

```text
discount = 10
```

An attacker sends:

```http
POST /coupon?discount=10&discount=100
```

What should happen?

```text
10?
100?
[10, 100]?
```

If different pieces of your application make different assumptions, your business logic can break.

This is why HPP isn't only an "authentication security" issue.

It can affect:

```text
validation
authorization
business logic
database queries
logging
analytics
```

---

# 15. HPP can affect logs too

Imagine your access log records:

```text
role=admin
```

but the actual request contained:

```text
role=user&role=admin
```

If your logging system only displays one interpretation, an investigator might miss important information.

Security isn't only about preventing attacks.

It's also about:

> **making requests predictable and observable.**

---

# 16. Query parameters are client-controlled

This should now be familiar.

Anything in:

```text
req.query
```

comes from the client.

For example:

```http
GET /users?role=admin
```

means:

```js
req.query.role
```

is user-controlled.

Therefore:

```text
req.query
```

should always be treated as:

```text
UNTRUSTED INPUT
```

---

# 17. Duplicate parameters aren't necessarily malicious

This is important.

Some legitimate APIs intentionally allow:

```text
?id=1&id=2&id=3
```

because they want multiple IDs.

For example:

```http
GET /users?id=10&id=20&id=30
```

could legitimately mean:

```js
ids = [10, 20, 30]
```

So:

> **Duplicate parameters are not automatically an attack.**

The problem is when your application expects a single value but receives multiple values unexpectedly.

---

# 18. This is why HPP has configuration

You shouldn't think:

```js
hpp();
```

means:

```text
"Never allow duplicate parameters."
```

Some parameters may legitimately need multiple values.

For example:

```text
?tag=javascript&tag=node&tag=mongodb
```

could be completely valid.

So HPP can be configured with parameters that are intentionally allowed to occur multiple times.

Conceptually:

```js
hpp({
    whitelist: [
        "tag"
    ]
});
```

The exact configuration options depend on the version of the package you're using, but the architectural idea is:

```text
Most parameters
→ expected to be single-valued

Specific parameters
→ explicitly allowed to be repeated
```

---

# 19. Whitelisting is important

Suppose your API supports:

```http
GET /products?tag=node&tag=express&tag=mongodb
```

You might intentionally want:

```js
req.query.tag
```

to represent multiple values.

So you can establish:

```text
tag
 ↓
multiple values allowed
```

while:

```text
page
 ↓
one value only
```

This is much better than blindly assuming every parameter can be repeated.

---

# 20. Don't confuse HPP with CORS

You've already studied:

```text
CORS
```

CORS answers:

> **Which browser origins are allowed to make requests to my API?**

HPP answers:

> **What happens when the same HTTP parameter appears multiple times?**

Completely different problems.

---

# 21. Don't confuse HPP with rate limiting

Rate limiting:

```text
How many requests?
```

HPP:

```text
How are parameters represented?
```

For example:

```text
Rate limiting
→ 100 requests/minute

HPP
→ ?role=user&role=admin
```

Different security layers.

---

# 22. Don't confuse HPP with sanitization

MongoDB sanitization:

```text
MongoDB-specific dangerous input
```

HPP:

```text
duplicate HTTP parameters
```

For example:

```text
mongoSanitize()
→ protects database-query boundary

hpp()
→ helps normalize duplicate HTTP parameters
```

They can work together.

---

Your Phase 10 middleware is starting to form a picture:

                       │
          ┌────────────┼────────────┐

        CORS         Helmet       HPP

---

# 24. What happens without HPP?

Without HPP, your application still receives HTTP requests.

Nothing magically crashes.

For example:

```http
GET /products?sort=name&sort=price
```

may still work.

The problem is:

```text
What does your application THINK it received?
```

If developers assume:

```js
const sort = req.query.sort;
```

is always:

```text
string
```

they may accidentally introduce bugs.

---

# 25. Type confusion

This is a useful way to think about HPP.

Your code expects:

```text
string
```

but the attacker creates:

```text
array
```

For example:

```text
Expected:

sort = "name"


Received:

sort = ["name", "price"]
```

This is a form of:

> **input type confusion**

Your validation should help catch this too.

---

# 26. HPP and validation work together

Suppose:

```js
sort: Joi.string()
```

Then:

```text
sort=name
```

is valid.

But:

```text
sort=name&sort=price
```

may become:

```js
sort: ["name", "price"]
```

and should fail a strict string validation.

So you have:

```text
HPP
 +
Validation
```

working together.

Again:

```text
HPP isn't a replacement for validation.
```

---

# 27. Why middleware alone isn't enough

Imagine:

```js
app.use(hpp());
```

but your code does:

```js
const { sort } = req.query;

if (sort === "name") {
    ...
}
```

That's fine only if you know what `sort` can look like.

Good API design says:

```text
sort
→ one of:
"name"
"price"
"createdAt"
```

Then validation enforces that contract.

---

# 28. API contracts solve ambiguity

Suppose your API says:

```text
GET /products

sort:
    string
    allowed:
        name
        price
        createdAt
```

Now your server has a clear contract.

An attacker sends:

```text
?sort=name&sort=price
```

Your application can reject it because:

```text
expected → one string
received → multiple values
```

That's much stronger than simply hoping middleware handles everything.

---

# 29. HPP is defense in depth

Just like:

```text
mongoSanitize()
```

HPP is another defense layer.

Think:

```text
                  Client
                    │
                    ▼
             Untrusted request
                    │
         ┌──────────┼──────────┐
         ▼          ▼          ▼
       CORS       HPP      Sanitization
         │          │          │
         └──────────┼──────────┘
                    ▼
                Validation
                    │
                    ▼
               Application
```

No single middleware is responsible for all security.

---

# 30. A real-world style example

Imagine:

```http
GET /transactions?status=completed
```

Your application:

```js
const { status } = req.query;

Transaction.find({
    status
});
```

Normal:

```text
status = "completed"
```

Polluted:

```http
GET /transactions?status=completed&status=pending
```

Now potentially:

```text
status = ["completed", "pending"]
```

The database query may now behave differently than expected.

If your application didn't intend multiple statuses, that's a problem.

---

# 31. Another example: sorting

Imagine:

```http
GET /users?sort=createdAt
```

Your code:

```js
const sort = req.query.sort;
```

Then:

```js
User.find().sort(sort);
```

Now:

```http
?sort=createdAt&sort=password
```

creates an unexpected input structure.

Even if this doesn't immediately produce an exploit, it creates an input contract your code may not have considered.

The better approach is:

```text
Validate sort
Allow-list valid sort fields
Reject unexpected structures
```

---

# 32. Another example: pagination

Expected:

```http
?page=2&limit=20
```

Validation:

```text
page → integer
limit → integer
```

Attacker:

```http
?page=2&page=999999999
```

Potential result:

```text
page → array
```

Now:

```js
Number(page)
```

may behave unexpectedly.

Again:

> **Don't let assumptions about HTTP parameter shape go unchecked.**

# 33. What should you do as a developer?

Whenever you create:

```js
req.query.foo
```

ask:

### Question 1

Should `foo` be:

```text
string?
number?
boolean?
array?
```

### Question 2

Should multiple values be allowed?

### Question 3

What happens if the client sends:

```text
foo=a&foo=b
```

### Question 4

Does validation reject unexpected structures?

### Question 5

Does the application have a clear policy for duplicate parameters?

This mindset is more important than memorizing `hpp()`.

# 34. The `hpp()` middleware

Now your starter code:

```js
app.use(hpp());
```

should make more sense.

Conceptually:

```text
Request
   ↓
Repeated HTTP parameters
   ↓
hpp()
   ↓
More predictable parameter handling
   ↓
Application
```

Its purpose is not:

```text
"Make all HTTP requests secure."
```

Its purpose is:

```text
"Help defend against HTTP Parameter Pollution."
```

---

# 35. Why global middleware makes sense

HPP can be applied globally because query parameter pollution can appear across many routes:

```text
/users
/products
/orders
/search
/reports
/admin
```

Instead of remembering:

```js
hpp()
```

on every route, you can establish a global security policy:

```js
app.use(hpp());
```

Then all relevant downstream routes benefit from it.

---

# 36. But global doesn't mean universal behavior

Remember the earlier point about arrays.

Some APIs intentionally support repeated parameters.

For example:

```http
?tag=node&tag=express&tag=mongodb
```

So your global HPP policy may need exceptions/configuration for legitimate multi-value parameters.

This is an important real-world lesson:

> **Security middleware should match your API contract, not fight against it.**

---

# 37. HPP and REST API design

Good REST APIs should clearly define:

```text
Which parameters are:
- single values
- arrays
- optional
- required
- repeated
```

For example:

```text
GET /products

?page=2
&limit=20
&sort=price
&tag=node
&tag=express
```

You could define:

```text
page → integer
limit → integer
sort → one string
tag → array
```

Now your API has an explicit contract.

That's much better than:

```text
"Whatever comes in req.query is fine."
```

---

# 38. Security lesson: ambiguity is the enemy

This is perhaps the most important idea in HPP.

Imagine:

```text
Client says:
role=user&role=admin
```

If your application doesn't have a clear answer to:

```text
"What is role?"
```

then your security boundary is unclear.

Good systems make the answer deterministic:

```text
role must be exactly one allowed string
```

or:

```text
roles may be an array
```

but not:

```text
maybe string, maybe array, let's see what happens.
```
