# Lesson 10.18 — Input Sanitization

In **10.15–10.17**, we learned three different problems:

```text

      ↓
Dangerous MongoDB operators

HPP
      ↓
Duplicate HTTP parameters

Input Sanitization
      ↓

```

Your starter specifically includes:

```js

```

And your roadmap intentionally puts **10.18 Input sanitization** after MongoDB sanitization and HPP.

The most important thing today is understanding:

> **Validation and sanitization are not the same thing.**

---

# 1. What is input sanitization?

**Input sanitization** means processing user-provided data so that it is in a safer, expected form before your application uses it.

Simple flow:

```text
User input
    ↓
Sanitization
    ↓
Safer / normalized input
    ↓
Application
```

For example, a user might submit:

```text
"   Rahul   "
```

Your application may want:

```text
"Rahul"
```

So you can normalize whitespace:

```text
"   Rahul   "
       ↓
"Rahul"
```

That's sanitization/normalization.

---

# 2. Why do we need sanitization?

Remember our fundamental backend rule:

```text
req.body
req.query
req.params
```

all contain **client-controlled data**.

The client can send:

```text
normal data
```

but can also send:

```text
unexpected data
malicious data
extra fields
wrong formats
dangerous characters
unexpected structures
```

Therefore:

```text
Internet
   ↓
Untrusted input
   ↓
Your application
```

You shouldn't blindly use that input.

---

# 3. Sanitization vs validation

This is the most important distinction of this lesson.

### Validation asks:

> **Is this input acceptable?**

### Sanitization asks:

> **Can this input be cleaned or normalized into the form we want?**

For example:

```text
Input:
"   rahul@example.com   "
```

Sanitization might produce:

```text
"rahul@example.com"
```

Validation then asks:

```text
Is this a valid email?
```

So:

```text
Input
  ↓
Sanitize
  ↓
Validate
  ↓
Application
```

The exact ordering can vary depending on what transformation you're performing, but the concepts remain different.

Your Phase 9 explicitly includes both **normalizing input** and **validation vs sanitization**, which is why this Phase 10 lesson builds on that foundation.

Imagine a vegetable shop.

You receive:

```text

   ↓
Wash them
   ↓
Remove dirt
   ↓
Check quality
   ↓
Cook
```

Think of:

```text
Wash / clean
    ↓
Sanitization
```

and:

```text
Check quality
    ↓
Validation
```

You don't want to confuse:

```text
clean
```

with:

```text

```

A clean tomato can still be rotten.

Similarly:

```text
sanitized input
```

doesn't necessarily mean:

```text
valid input
```

# 5. Example: username

Suppose your API accepts:

```json
{
  "username": "   Rahul   "
}
```

You might normalize it:

```text
"   Rahul   "
       ↓
"Rahul"
```

Then validation can check:

```text
Is it a string?
Is it long enough?
Are only allowed characters present?
```

So:

```text
Sanitize
   ↓
"Rahul"

Validate
   ↓
valid username
```

---

# 6. Example: email

Suppose:

```text
"   Rahul@Example.COM   "
```

You might normalize:

```text
"rahul@example.com"
```

depending on your application's rules.

Then validation checks:

```text
Is this a valid email?
```

This is useful because normalization can make your data consistent.

For example, your database shouldn't accidentally contain:

```text
Rahul@example.com
rahul@example.com
 RAHUL@example.com
```

as separate logical users if your application treats email addresses case-insensitively.

However, be careful: **normalization rules should be intentional**, especially for identifiers such as email addresses.

---

# 7. Sanitization can improve consistency

Imagine users submit:

```text
"Rahul"
" Rahul"
"Rahul "
"  Rahul  "
```

Without normalization, you could store inconsistent values.

With appropriate sanitization:

```text
"Rahul"
```

you can make your data more consistent.

This is one reason sanitization isn't only about "stopping hackers."

It can also improve:

```text
data quality
consistency
searching
database cleanliness
```

---

# 8. But sanitization can change data

This is important.

Suppose the user sends:

```text
"hello world"
```

and your sanitizer removes spaces:

```text
"helloworld"
```

You changed the user's data.

That may be completely wrong for a field where spaces are meaningful.

For example:

```text
firstName
```

might allow spaces.

But:

```text
username
```

might not.

Therefore:

> **Don't sanitize everything in the same way.**

Sanitization rules should depend on the field and its purpose.

---

# 9. Never blindly "clean everything"

A beginner might think:

```text
Remove:
< >
$
.
'
"
/
\
spaces
```

from every input.

That is usually a bad idea.

Why?

Because many of these characters are legitimate.

For example:

```text
name:
"R&D"

address:
"12/A Main Road"

password:
"Rahul@123!"

message:
"Hello, world!"
```

If you blindly remove characters, you can corrupt valid data.

---

# 10. Passwords are a great example

Suppose the password is:

```text
Rahul@123!
```

You should **not** blindly sanitize it into:

```text
Rahul123
```

That changes the password.

Password processing should generally be:

```text
Receive password
     ↓
Validate password rules
     ↓
Hash password
     ↓
Store hash
```

Not:

```text
Receive password
     ↓
Remove special characters
     ↓
Hash
```

This is a very important practical lesson.

---

# 11. Sanitization is field-specific

Consider:

```text
firstName
email
username
password
description
searchTerm
URL
```

Each field has different requirements.

For example:

```text
firstName
→ trim whitespace

email
→ normalize according to your policy

username
→ normalize allowed format

password
→ don't arbitrarily alter it

description
→ preserve legitimate content
```

Therefore:

> **There is no universal "sanitize every input" function that is correct for every field.**

---

# 12. Sanitization vs escaping

Another important distinction.

These terms are often mixed together:

```text
sanitization
escaping
encoding
validation
normalization
```

They aren't identical.

### Sanitization

Remove or transform unwanted input.

### Escaping

Represent special characters safely for a particular output context.

### Encoding

Transform data into another representation.

### Validation

Check whether input meets your rules.

For example:

```text
HTML output
JavaScript output
SQL
MongoDB
URL
JSON
```

all have different security requirements.

---

# 13. Context matters

Suppose the user sends:

```text
Hello <b>Rahul</b>
```

Should you remove:

```text
<b>
```

?

That depends.

If this is:

```text
plain text field
```

you may not want HTML.

If this is:

```text
rich text editor
```

HTML-like markup might be intentional.

Therefore:

> **Security processing must understand the context where data will be used.**

This is a much better principle than:

```text
"Remove suspicious-looking characters."
```

---

# 14. Input sanitization vs output encoding

A common security mistake is thinking:

```text
"Sanitize everything when it enters the application."
```

and then forgetting about output.

Consider:

```text
User input
   ↓
Database
   ↓
HTML response
```

Even if input was stored safely, you still need to safely handle it when rendering HTML.

This is where:

```text
output encoding
```

becomes important.

In a typical React frontend, React's rendering model provides important escaping behavior for ordinary text, but you still need to be careful with mechanisms such as `dangerouslySetInnerHTML`.

So:

```text
Input handling
+
Output handling
```

are separate security concerns.

---

# 15. Example: user comment

User submits:

```text
Hello <script>...</script>
```

You have two possible strategies.

### Strategy A — store plain text

Treat the entire value as text:

```text
Hello <script>...</script>
```

and ensure the output context safely renders it as text.

### Strategy B — support HTML

If your application intentionally supports HTML, you need a much more careful HTML sanitization policy.

You cannot simply assume:

```text
"HTML is allowed"
```

means:

```text
"Store and render arbitrary HTML."
```

---

# 16. Why sanitization should happen deliberately

Suppose you write:

```js
const sanitizeInput = (req, res, next) => {
    // clean everything
    next();
};
```

Sounds nice.

But what exactly does:

```text
clean everything
```

mean?

That's the problem.

A security middleware should have a clear contract:

```text
What fields?
What transformations?
Why?
What characters?
What contexts?
What exceptions?
```

Otherwise you may introduce bugs.

# 18. `mongoSanitize()` vs `sanitizeInput`

This distinction is very important.

### `mongoSanitize()`

Purpose:

```text
MongoDB-specific input defense
```

Think:

```text
$
.
MongoDB operators
MongoDB query structure
```

### `sanitizeInput`

Purpose:

```text
Application-specific input cleaning/normalization
```

Think:

```text
trim whitespace
normalize values
remove/transform unwanted patterns
field-specific cleanup
```

So your middleware stack might contain both:

```js
app.use(mongoSanitize());

app.use(middleware.security.sanitizeInput);
```

because they solve different problems.

---

# 19. Why not combine them?

You could technically create one giant middleware that tries to do everything.

But that becomes difficult to understand.

For example:

```text
sanitizeEverything()
    ├── MongoDB sanitization
    ├── HTML sanitization
    ├── whitespace normalization
    ├── email normalization
    ├── URL normalization
    └── password transformation
```

That's dangerous architecture.

Why?

Because each type of data has different rules.

Better:

```text
MongoDB protection
        +
Application-specific normalization
        +
Validation
```

with clear responsibilities.

# 20. Sanitization and mass assignment

There's another important connection.

Suppose a client sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

Your application expects the client to update:

```text
name
email
```

but not:

```text
role
```

Simply sanitizing the input won't necessarily solve this.

You need **field allow-listing**.

For example:

```js
const { name, email } = req.body;
```

Now:

```text
name → allowed
email → allowed
role → ignored
```

This is closely related to what you learned in Phase 9 about **whitelisting fields and stripping unknown fields**.

---

# 21. Sanitization does not replace allow-listing

This is worth memorizing:

```text
Sanitization
≠
Allow-listing
```

Suppose:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

The value:

```text
"admin"
```

isn't necessarily "dirty."

It's simply:

```text
not allowed for this operation
```

That's an authorization/data-model issue, not something a generic sanitizer should fix.

---

# 22. Sanitization does not replace authorization

Imagine:

```text
User sends:
{
    "role": "admin"
}
```

The problem isn't:

```text
"admin" contains dangerous characters.
```

The problem is:

```text
"Should this user be allowed to modify role?"
```

That's authorization.

So:

```text
Sanitization
→ Is the data cleaned/normalized?

Authorization
→ Is the user allowed to perform this operation?
```

Very different.

---

# 23. Sanitization does not replace validation

Suppose:

```json
{
  "age": "banana"
}
```

A sanitizer might trim it:

```text
"banana"
```

But it's still invalid.

Validation must say:

```text
age must be a number
```

So:

```text
Sanitize
   ↓
"banana"

Validate
   ↓
❌ invalid
```

This is exactly why your roadmap separates these concepts.

---

# 24. Sanitization does not replace authentication

Suppose an unauthenticated attacker sends:

```http
POST /api/v1/users
```

with perfectly clean JSON:

```json
{
  "name": "Rahul"
}
```

The input may be completely sanitized.

But:

```text
Is this person authenticated?
```

is a separate question.

So:

```text
Authentication
→ Who are you?

Sanitization
→ How should this input be cleaned?

Validation
→ Is this input acceptable?
```

---

# 25. Sanitization does not replace rate limiting

An attacker could send:

```text
10,000 requests
```

containing perfectly clean data.

Sanitization won't help.

Rate limiting addresses:

```text
How many requests can this client make?
```

Again:

```text
Security controls
≠ interchangeable
```

# 27. What should a custom sanitizer actually do?

Suppose you want a username policy:

```text
username:
- trim whitespace
- lowercase
- allow only [a-z0-9_]
```

Conceptually:

```js
const sanitizeUsername = (value) => {
    return value
        .trim()
        .toLowerCase();
};
```

Then validation checks:

```text
Does it contain only allowed characters?
```

Notice the separation:

```text
Sanitize
→ trim + lowercase

Validate
→ check allowed format
```

---

# 28. Don't over-sanitize usernames

Suppose:

```text
Rahul_Dev
```

becomes:

```text
rahul_dev
```

Fine, if that's your policy.

But if your sanitizer does:

```js
value.replace(/[^a-z]/gi, "");
```

then:

```text
Rahul_Dev
```

becomes:

```text
RahulDev
```

You've silently changed the user's intended identifier.

Therefore:

> **Sanitization should be conservative and intentional.**

---

# 29. Normalization is often safer

In many APIs, a better goal isn't:

```text
"remove dangerous characters"
```

but:

```text
"normalize values into a predictable representation."
```

Examples:

```text
" Rahul "
    ↓
"Rahul"
```

```text
"RAHUL@EXAMPLE.COM"
    ↓
"rahul@example.com"
```

```text
"+91 98765 43210"
    ↓
normalized phone representation
```

The exact rules depend on your application's requirements.

---

# 30. Be careful with Unicode

This is a more advanced point, but useful for a developer.

Humans can represent text using different Unicode characters that may look similar.

For example:

```text
é
```

can sometimes be represented through different Unicode sequences.

So normalization can sometimes involve:

```text
Unicode normalization
```

But again:

> Don't normalize data just because you can.

Do it when your application's requirements call for it.

---

# 31. Search input is another interesting case

Suppose:

```http
GET /users?search=Rahul
```

You may normalize:

```text
" Rahul "
     ↓
"Rahul"
```

Then use the value in your search query.

But don't assume:

```text
sanitize searchTerm
```

means:

```text
safe for every output/query context
```

You still need to construct your database query safely.

For example:

```js
User.find({
    name: {
        $regex: searchTerm,
        $options: "i"
    }
});
```

Here:

```text
$regex
```

is controlled by the server.

That's the same principle we learned in 10.15.

---

# 32. Sanitization and regex are different concerns

Suppose user searches:

```text
search=.*
```

If your application uses:

```js
$regex: search
```

then:

```text
.*
```

has regex meaning.

Sanitizing MongoDB operators won't necessarily solve this.

You may need to decide:

```text
Should search support regex?
```

If not, escape the search term appropriately for the regex context or use another search mechanism.

This illustrates an important security principle:

> **Security depends on the context where data is used.**

# 33. One input can pass one layer and fail another

Imagine:

```text
Input:
"Rahul"
```

### Sanitization

```text
"Rahul"
```

Fine.

### Validation

```text

```

Fine.

### Authorization

```text

```

Maybe not.

### Database

```text
Can this value be safely used in the query?
```

Depends on how the query is constructed.

So a value isn't simply:

```text
safe
```

or:

```text

```

Security is contextual.

# 34. This is why "sanitize all input" is a bad slogan

A better rule is:

> **Validate input against an explicit contract, normalize it where appropriate, and safely handle it according to its output/storage context.**

Instead of:



# 44. Interview questions

### Q1. What is input sanitization?

Processing untrusted input to remove or transform unwanted patterns or normalize it into an appropriate form.

### Q2. Is sanitization the same as validation?

No.

```text
Validation → Is it acceptable?
Sanitization → Can/should it be cleaned or normalized?
```

### Q3. Is sanitized input automatically safe?

No.

Security depends on how and where the input is used.

### Q4. Should every special character be removed?

No. Legitimate data often contains special characters.

### Q5. Should passwords be blindly sanitized?

No. Arbitrary transformation can change the password.

### Q6. Does sanitization replace authorization?

No.

### Q7. Does `mongoSanitize()` replace general input sanitization?

No. They address different concerns.

Three different security concerns:

```text
mongoSanitize()
       ↓
MongoDB-specific protection

hpp()
       ↓
HTTP parameter pollution

sanitizeInput
       ↓
Application-specific input normalization/sanitization
```

Your Phase 10 is deliberately building these pieces separately so that the final security layer doesn't become a collection of unexplained packages.
