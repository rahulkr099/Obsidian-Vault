# Lesson 10.2 — Threat Model of a REST API

In **10.1**, we learned:

> Backend security means protecting our application, data, users, and availability from untrusted requests.

Now we take the next step:

> **Before securing an API, we should understand what can go wrong.**

This is called **threat modeling**.

---

# 1. What is a threat model?

A threat model is simply a structured way of asking:

> **"Who might attack my system, what might they try to do, and what are we protecting?"**

Instead of randomly adding:

```js
helmet();
cors();
rateLimit();
mongoSanitize();
```

we first think:

```text
What can an attacker do?
        ↓
What can they target?
        ↓
What damage can happen?
        ↓
What defense should we use?
```

That's much closer to how professional backend security works.

---

# 2. Think about your REST API as a target

Imagine we have a simple Notes API:

```text
                    INTERNET
                       │
             ┌─────────┴─────────┐
             │                   │
           User               Attacker
             │                   │
             └─────────┬─────────┘
                       ▼
                  REST API
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        Auth         Notes        Users
          │            │            │
          └────────────┼────────────┘
                       ▼
                    MongoDB
```

Our attacker doesn't need access to your source code.

They can simply send HTTP requests.

For example:

```http
GET /api/v1/notes
```

```http
POST /api/v1/auth/login
```

```http
GET /api/v1/users/123
```

```http
DELETE /api/v1/notes/456
```

So the API itself becomes the **attack surface**.

---

# 3. What is an attack surface?

The **attack surface** is the collection of places where an attacker can interact with your system.

For a REST API, that includes:

```text
Endpoints
HTTP methods
Request body
Query parameters
URL parameters
Headers
Cookies
Authentication
File uploads
Database queries
External services
```

For example:

```http
POST /api/v1/users
```

has several inputs:

```text
              POST /users
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
     Headers      Body       Cookies
                   │
                   ▼
             User-controlled
                 input
```

Every one of these boundaries deserves attention.

---

# 4. Example: Login endpoint

Suppose we have:

```http
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "secret123"
}
```

A beginner might think:

> "The only thing I need to check is whether the password is correct."

But an attacker could try many things.

### Attack 1 — Brute force

```text
admin@example.com
password1
password2
password3
password4
...
```

Potential defense:

```text
Rate limiting
+
Account protection
```

---

### Attack 2 — Malformed input

```json
{
  "email": 123,
  "password": []
}
```

Defense:

```text
Validation
```

---

### Attack 3 — Injection

An attacker might attempt malicious database operators or other crafted values.

Defense:

```text
Input validation
+
Sanitization
+
Safe database queries
```

---

### Attack 4 — Credential exposure

Suppose your logs accidentally contain:

```text
POST /login
email=rahul@example.com
password=secret123
```

That's a security problem.

Defense:

```text
Safe logging
+
Sensitive-data filtering
```

---

### Attack 5 — Token theft

After login, an attacker may try to steal or misuse authentication tokens.

Defense involves:

```text
Secure token design
+
Expiration
+
Secure cookies where appropriate
+
Refresh-token protection
```

Authentication itself is a later phase, but threat modeling helps us see why it needs careful design.

---

# 5. The attacker doesn't follow your UI

This is a very important concept.

Suppose your React application provides:

```text
Role:
[ User ▼ ]
```

and users cannot select:

```text
Admin
```

You might think:

> "Users can't become admins."

Wrong.

The attacker can completely ignore React.

They can send:

```http
POST /api/v1/users
Content-Type: application/json
```

with:

```json
{
  "email": "attacker@example.com",
  "role": "admin"
}
```

Therefore:

```text
             React UI
                │
                │ can be bypassed
                ▼
             REST API
                │
                ▼
          MUST enforce rules
```

This is why we repeatedly say:

> **Never trust the client.**

# 6. Identify your assets

Before thinking about attacks, identify what needs protection.

These are called **assets**.

For a typical MERN backend:

### User data

```text
Name
Email
Profile
Preferences
```

### Authentication data

```text
Password hashes
Access tokens
Refresh tokens
Reset tokens
```

### Business data

```text
Todos
Orders
Payments
Messages
Documents
```

### Secrets

```text
JWT secrets
MongoDB credentials
API keys
SMTP credentials
```

### Infrastructure

```text
Database
Backend server
Logs
Storage
Queues
```

Your threat model begins by asking:

> **What would hurt us if an attacker obtained, modified, or destroyed it?**

---

# 7. Identify your actors

Now ask:

> **Who interacts with the system?**

A simple application might have:

```text
                 SYSTEM
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      User       Admin       Attacker
```

### Normal user

Can:

```text
Create own notes
Read own notes
Update own notes
Delete own notes
```

### Admin

May additionally:

```text
Manage users
View reports
Change roles
```

### Attacker

Has no legitimate permission but can still send requests.

Important:

> **An attacker is still able to interact with your public API unless you prevent them.**

---

# 8. Identify entry points

Now list where requests enter.

For our API:

```text
/api/v1/auth/login
/api/v1/auth/signup
/api/v1/users/me
/api/v1/notes
/api/v1/notes/:id
```

Each endpoint is an entry point.

But don't only look at URLs.

Also consider:

```text
Request body
Query string
URL parameters
Headers
Cookies
File uploads
```

For example:

```http
GET /api/v1/notes?sort=createdAt
```

contains user-controlled query data:

```text
sort=createdAt
```

So your backend must decide:

> Which values are allowed?

This idea becomes especially important when we study **validation, sanitization, and HTTP Parameter Pollution** later in this phase.

---

# 9. What can an attacker try to achieve?

Instead of memorizing hundreds of attacks, start with a few major goals.

## Goal 1 — Read something they shouldn't

Example:

```text
User A
   ↓
tries to read
   ↓
User B's private note
```

This threatens:

```text
Confidentiality
```

---

## Goal 2 — Modify something they shouldn't

Example:

```text
User A
   ↓
tries to change
   ↓
User B's note
```

This threatens:

```text
Integrity
```

---

## Goal 3 — Delete something they shouldn't

Example:

```text
User
 ↓
DELETE /users/admin
```

Again:

```text
Integrity
+
Authorization
```

---

## Goal 4 — Become someone else

Example:

```text
Attacker
   ↓
tries to access
   ↓
another user's account
```

This can involve:

```text
Credential attacks
Token attacks
Session attacks
Authentication flaws
```

---

## Goal 5 — Overload the server

Example:

```text
Attacker
   ↓
100,000 requests
   ↓
/api/v1/auth/login
```

Potential result:

```text
Server resources consumed
        ↓
Legitimate users suffer
```

This threatens:

```text
Availability
```

---

# 10. A useful threat table

For a basic REST API, we can start with:

|Threat|Example|Main defense|
|---|---|---|
|Brute force|Repeated login attempts|Rate limiting|
|Unauthorized access|User B's note accessed|Authorization|
|Injection|Malicious database input|Validation + sanitization|
|Malicious browser origin|Cross-origin request|CORS/origin controls|
|Unsafe HTTP behavior|Missing security headers|Helmet|
|Parameter pollution|Repeated query parameters|HPP handling|
|Invalid input|Wrong data types|Validation|
|Sensitive data leakage|Password in logs|Safe logging|
|Token abuse|Stolen/abused token|Secure authentication design|

Notice something important:

**The defense is chosen after identifying the threat.**

That's the mindset we want.

---

# 11. Threat modeling is not just "finding hackers"

A threat model also asks:

> **What happens if our own code makes a mistake?**

For example:

```js
const user = await User.findById(req.params.id);
```

Maybe this works perfectly.

But if your endpoint is:

```http
GET /api/v1/users/:id
```

and there is no authorization check, you might accidentally expose private data.

That's a **design vulnerability**, even if nobody deliberately wrote an attack.

So threat modeling helps us find:

```text
Attacks
+
Architecture mistakes
+
Missing controls
+
Unsafe assumptions
```

---

# 12. Think in terms of trust levels

Not every component is equally trustworthy.

Imagine:

```text
          UNTRUSTED
              │
              ▼
        Internet client
              │
              ▼
        HTTP request
              │
              ▼
       Security checks
              │
              ▼
      Authenticated user
              │
              ▼
         Application
              │
              ▼
          Database
          TRUSTED
```

The incoming request should be treated as **untrusted**.

That's why we validate:

```js
req.body
req.params
req.query
req.headers
```

before using them.

We'll study this concept deeply in **10.3 — Trust Boundaries**.

# 13. Threat modeling our Notes API

Let's build a simple model.

Our application:

```text
Notes API
```

Endpoints:

```text
POST   /auth/signup
POST   /auth/login

GET    /notes
POST   /notes
GET    /notes/:id
PATCH  /notes/:id
DELETE /notes/:id
```

Assets:

```text
Users
Passwords
Tokens
Notes
Database
Secrets
```

Actors:

```text
Normal user
Admin
Unauthenticated attacker
```

Now ask:

### Can an attacker spam login?

Yes.

```text
→ Rate limiting
```

### Can User A request User B's note?

Potentially.

```text
→ Authentication
→ Authorization
→ Ownership check
```

### Can a request contain unexpected input?

Yes.

```text
→ Validation
→ Sanitization
```

### Can browser requests originate from another site?

Yes.

```text
→ CORS/origin policy
```

### Can HTTP responses lack useful security headers?

Yes.

```text
→ Helmet
```

Now the security architecture starts making sense.

# 14. Threat → Control → Location

This is a very useful professional habit.

Don't simply memorize:

```text
Helmet
CORS
Rate limiter
```

Instead memorize:

```text
THREAT
   ↓
CONTROL
   ↓
LOCATION
```

For example:

```text
Repeated requests
       ↓
Rate limiting
       ↓
Middleware
```

Another:

```text
Unsafe browser cross-origin behavior
       ↓
CORS policy
       ↓
Middleware
```

Another:

```text
Unauthorized resource access
       ↓
Authorization
       ↓
Middleware + service/business rules
```

Another:

```text
Unexpected request data
       ↓
Validation
       ↓
Validation middleware
```

This way, if you work on a completely different backend framework later, the knowledge still transfers.

---

# 15. Security is about reducing risk

A threat model doesn't necessarily say:

> "This attack is impossible."

Instead, it asks:

> **"How do we reduce the probability and impact of this attack?"**

For example, rate limiting doesn't magically make brute force impossible.

Instead:

```text
Without rate limit

Attacker
   ↓
100,000 attempts
```

With rate limiting:

```text
Attacker
   ↓
limited attempts
   ↓
429 Too Many Requests
```

The attack becomes much harder.

---

# 16. Don't confuse threat, vulnerability, and attack

These three words are related but different.

### Threat

Something that could cause harm.

Example:

```text
Attacker trying to steal user data
```

### Vulnerability

A weakness that makes the threat possible.

Example:

```text
Missing authorization check
```

### Attack

The actual attempt to exploit the weakness.

Example:

```http
GET /api/v1/notes/another-users-note-id
```

So:

```text
Threat
  ↓
Attacker wants private data

Vulnerability
  ↓
Missing ownership check

Attack
  ↓
Request another user's note
```

This distinction is very useful when debugging security issues.

---

# 17. The security review mindset

When you build a new endpoint, don't just ask:

> "Does it work?"

Ask these questions:

```text
1. Who can call this endpoint?

2. What input can they control?

3. What data can they access?

4. What data can they modify?

5. What happens if they send malformed input?

6. What happens if they call it 10,000 times?

7. What happens if they aren't authenticated?

8. What happens if they are authenticated as another user?

9. What happens if they manipulate URL/query parameters?

10. What sensitive information could leak?
```

This is **security thinking**.

---

# 18. Apply it to a real endpoint

Suppose we build:

```http
DELETE /api/v1/notes/:id
```

Don't immediately write:

```js
router.delete("/:id", deleteNote);
```

First think:

```text
Who?
 ↓
Authenticated user

Allowed?
 ↓
Must own the note or have permission

Input?
 ↓
Validate note ID

Too many requests?
 ↓
Possibly rate limit sensitive operations

Database?
 ↓
Query note by ID + owner

Errors?
 ↓
Don't leak sensitive information
```

Then the architecture might become:

```text
DELETE /notes/:id
        │
        ▼
 Authentication
        │
        ▼
 Validation
        │
        ▼
 Authorization / ownership
        │
        ▼
 Controller
        │
        ▼
 Service
        │
        ▼
 Repository
        │
        ▼
 MongoDB
```

This is exactly the kind of thinking we are building throughout your backend course.

# 20. Connection to your security middleware

Now we can finally connect today's lesson to the code you'll eventually build.


Don't read this as:

> "Five packages I have to memorize."

Read it as:

```text
                 THREATS
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
 Browser abuse   Input abuse   HTTP abuse
      │             │             │
      ▼             ▼             ▼
    CORS        Sanitization    Helmet
                  │
                  ▼
                 HPP
```

Then separately:

```text
Abuse through too many requests
          ↓
    Rate limiting
```

And later:

```text

       ↓

       ↓

```

Now the middleware starts having a **reason**.

# 21. Important: CORS is not authentication

This is a common beginner mistake.

Suppose you configure:

```js
cors({
    origin: "https://myfrontend.com"
});
```

Someone might think:

> "Now only my frontend can access the API."

Not exactly.

CORS is primarily a **browser security mechanism**.

A person can still use:

```text
curl
Postman
Python
another backend
```

to send requests to your API.

We'll explore this properly in:

**10.5 — CORS Fundamentals**

and:

**10.6 — Understanding Browser CORS**.

For now:

```text
CORS
≠
Authentication
```

# 22. The biggest lesson from 10.2

A beginner often starts security like this:

```text
"What security packages should I install?"
```

A better backend developer starts with:

```text
"What can go wrong?"
```

Then:

```text
"What asset could be affected?"
```

Then:

```text
"Why can it go wrong?"
```

Then:

```text
"What control reduces the risk?"
```

Then:

```text
"Where should that control live?"
```

That's threat modeling.

# Mini Exercise 🧠

Imagine this endpoint:

```http
PATCH /api/v1/users/:id
```

It allows users to update their profile.

Think about these five questions:

### 1. Who can call it?

```text
?
```

### 2. What can the attacker control?

```text
?
```

### 3. What could they try to access?

```text
?
```

### 4. What could they try to modify?

```text
?
```

### 5. What security controls might we need?

```text
?
```

### Suggested answer

```text
1. Who?
   → Authenticated user

2. Controlled input?
   → :id, req.body, headers, etc.

3. Access?
   → Another user's profile

4. Modification?
   → Another user's profile
   → Potentially sensitive fields such as role

5. Controls?
   → Authentication
   → Authorization/ownership
   → Validation
   → Field allow-listing
   → Rate limiting where appropriate
   → Safe database update
```

And notice a very important security issue:

```json
{
  "role": "admin"
}
```

should **not** automatically become an accepted update just because it is valid JSON.

That's an example of why **validation, authorization, and field allow-listing** matter.
