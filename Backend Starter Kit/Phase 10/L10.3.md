# Lesson 10.3 — Trust Boundaries

In **10.2**, we learned threat modeling.

We asked:

> **What can an attacker do to our REST API?**

Now we need to understand something even more fundamental:

> **Where does trusted data end and untrusted data begin?**

That boundary is called a **trust boundary**.

---

# 1. What is a trust boundary?

A trust boundary is simply:

> **A point where data moves from one level of trust to another.**

For a backend, the most important boundary is usually:

```text
Internet
   ↓
HTTP Request
   ↓
Your Backend
```

The request coming from the internet should be treated as **untrusted**.

So:

```text
                 TRUST BOUNDARY
                       │
                       ▼
UNTRUSTED             BACKEND
CLIENT                  │
  │                     │
  │ HTTP request        │
  └────────────────────►│
                        │
                        ▼
                   Application
                        │
                        ▼
                     MongoDB
```

The moment data crosses this boundary, your backend needs to ask:

> **"Can I safely trust this?"**

Usually, the answer initially is:

> **No.**

---

# 2. Why is this important?

Consider:

```js
const email = req.body.email;
```

Where did `req.body.email` come from?

Not from your database.

Not from your backend.

It came from the client.

The client could send:

```json
{
  "email": "rahul@example.com"
}
```

But it could also send:

```json
{
  "email": 123
}
```

or:

```json
{
  "email": {}
}
```

or unexpected fields:

```json
{
  "email": "attacker@example.com",
  "role": "admin",
  "isVerified": true
}
```

Therefore:

```text
req.body
     ↓
UNTRUSTED
```

until your application validates and processes it.

---

# 3. The simplest trust model

Think of your backend like this:

```text
        UNTRUSTED
            │
            │ HTTP
            ▼
     ┌──────────────┐
     │   Express    │
     └──────┬───────┘
            │
       Security checks
            │
            ▼
     ┌──────────────┐
     │ Application  │
     └──────┬───────┘
            │
       Safe operations
            │
            ▼
     ┌──────────────┐
     │   MongoDB    │
     └──────────────┘
```

The mistake beginners often make is imagining:

```text
Client → Backend → Database
```

as if everything is automatically trustworthy.

It isn't.

---

# 4. What exactly is untrusted?

Almost everything the client can control.

### Request body

```js
req.body
```

Example:

```json
{
  "title": "Learn Express"
}
```

---

### URL parameters

```js
req.params.id
```

For:

```http
GET /todos/123
```

the `123` is client-controlled.

The attacker can change it to:

```http
GET /todos/456
```

or another value entirely.

---

### Query parameters

```js
req.query
```

For:

```http
GET /todos?page=1&limit=20
```

the client controls:

```text
page
limit
```

They can send:

```http
GET /todos?page=-100&limit=999999999
```

unless your backend restricts them.

---

### Headers

The client controls many HTTP headers.

For example:

```http
User-Agent: something
```

and:

```http
X-Something: attacker-controlled-value
```

Some headers have special meaning, but the general principle remains:

> **Don't blindly trust client-provided headers.**

---

### Cookies

If your application uses cookies:

```js
req.cookies
```

those values also come from the client.

Even an authentication cookie should not simply be trusted because it exists.

It needs to be:

```text
received
   ↓
verified
   ↓
validated
   ↓
trusted identity established
```

---

# 5. Important distinction: authentication creates trust

Suppose a request contains:

```http
Authorization: Bearer eyJ...
```

Should we immediately trust:

```js
req.headers.authorization
```

?

No.

It's still client-provided.

The backend must verify the token.

```text
Authorization header
        │
        ▼
     Verify JWT
        │
        ├── Invalid → reject
        │
        ▼
    Valid token
        │
        ▼
 Trusted identity
        │
        ▼
      req.user
```

So:

```text
req.headers.authorization
       ↓
UNTRUSTED

verified JWT
       ↓
TRUSTED IDENTITY
```

This distinction is extremely important.

---

# 6. `req.user` is different

After authentication middleware runs:

```js
req.user = {
    id: userId,
    role: userRole
};
```

the rest of your application can treat this identity as **verified**, assuming your authentication middleware is correctly implemented.

The flow becomes:

```text
Client
  │
  │ Authorization header
  ▼
Authentication middleware
  │
  │ verify
  ▼
Trusted identity
  │
  ▼
req.user
```

This is one reason middleware is so useful.

It establishes information that later layers can rely on.

---

# 7. Trust isn't binary

This is an important professional concept.

It's not always:

```text
TRUSTED
or
UNTRUSTED
```

There can be different levels.

For example:

```text
Internet request
    ↓
Untrusted
```

After validation:

```text
Validated input
    ↓
Structurally trusted
```

After authentication:

```text
Verified identity
    ↓
Identity trusted
```

After authorization:

```text
Authorized operation
    ↓
Permission trusted
```

So we can think:

```text
UNTRUSTED
    ↓
VALIDATED
    ↓
AUTHENTICATED
    ↓
AUTHORIZED
    ↓
SAFE OPERATION
```

But even then, **don't blindly trust everything forever**.

---

# 8. Validation does not mean authorization

Suppose the request is:

```json
{
  "role": "admin"
}
```

A validation schema might say:

```text
role must be a string
```

The value:

```text
"admin"
```

is structurally valid.

But does that mean the user is allowed to set their role to admin?

No.

That's an **authorization/business rule**.

So:

```text
Validation
    ↓
"Is this data acceptable in shape/type/format?"

Authorization
    ↓
"Is this user allowed to perform this operation?"
```

This distinction will become extremely important in Phase 14 and Phase 15.

---

# 9. A classic mistake: trusting validated data too much

Imagine:

```js
const update = req.body;

await User.findByIdAndUpdate(
    req.user.id,
    update
);
```

Suppose validation accepts:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

The data is valid JSON.

Maybe the schema even says:

```text
role = string
```

But the user should not be able to update:

```text
role
```

Therefore you need an **allow-list**.

For example, conceptually:

```text
Allowed:
    name
    email
    avatar

Not allowed:
    role
    passwordHash
    refreshTokenHash
    isAdmin
```

This is a trust-boundary problem.

---

# 10. Trust boundaries exist inside your backend too

This is an important step beyond:

```text
Internet → Backend
```

You can also have boundaries between internal components.

For example:

```text
Controller
    │
    ▼
Service
    │
    ▼
Repository
    │
    ▼
MongoDB
```

Each layer has a different responsibility.

---

# 11. Controller → Service boundary

The controller receives HTTP data:

```js
req.body
req.params
req.query
req.user
```

Then it calls:

```js
userService.updateProfile(...)
```

The service should ideally receive a **well-defined application-level input**, not arbitrary HTTP objects.

Bad design:

```js
userService.updateProfile(req);
```

Why?

Now your service knows about Express.

Better:

```js
userService.updateProfile({
    userId: req.user.id,
    name: req.body.name,
    email: req.body.email
});
```

Now the service receives explicit data.

```text
HTTP world
    ↓
Controller
    ↓
Application data
    ↓
Service
```

This reduces accidental trust.

---

# 12. Service → Repository boundary

The service decides:

> "I want to find Rahul's note."

It might call:

```js
todoRepository.findByIdAndUserId(
    todoId,
    userId
);
```

Notice something important.

Instead of:

```js
todoRepository.findById(todoId);
```

we pass:

```text
todoId
+
userId
```

This creates a safer database operation.

```text
Service
   │
   │ todoId + userId
   ▼
Repository
   │
   ▼
MongoDB
```

The repository can then enforce:

```js
{
    _id: todoId,
    userId: userId
}
```

This helps prevent unauthorized resource access.

---

# 13. Why ownership belongs near the data access

Imagine:

```text
User A
  │
  └── Todo A

User B
  │
  └── Todo B
```

User A sends:

```http
GET /api/v1/todos/TODO_B
```

If your repository does:

```js
Todo.findById(todoId);
```

you could accidentally return User B's todo.

But:

```js
Todo.findOne({
    _id: todoId,
    userId: authenticatedUserId
});
```

creates a stronger boundary.

The query itself says:

> "Only return this resource if it belongs to this user."

This is a very powerful security habit.

---

# 14. Database data is not automatically safe either

This is subtle.

Many beginners think:

```text
Database = trusted
```

But database data can become outdated, corrupted, incorrectly migrated, or written by another part of the application.

For example:

```text
Old user record
    ↓
role: "administrator"
```

while your current application expects:

```text
"user"
"admin"
```

Therefore your application should still apply appropriate business rules.

The database is an important trusted source, but **trust should be based on the guarantees your system actually provides**.

---

# 15. External APIs are another boundary

Suppose your backend calls:

```text
Stripe
Cloudinary
Resend
Google
OpenAI
```

Conceptually:

```text
Your backend
     │
     │ HTTP request
     ▼
External service
```

You shouldn't assume the external service will always respond exactly as expected.

You should handle:

```text
timeouts
errors
unexpected responses
invalid data
service outages
```

So another boundary exists:

```text
YOUR SYSTEM
     │
     ▼
EXTERNAL SYSTEM
```

We'll encounter this more when we study email and background jobs.

---

# 16. File uploads are a major trust boundary

Suppose your API accepts:

```http
POST /api/v1/profile/avatar
```

with an uploaded file.

The user might upload:

```text
avatar.jpg
```

But the backend shouldn't blindly assume:

> "It's definitely a safe JPEG."

The attacker controls the upload.

You may need to check:

```text
file size
file type
content
filename
extension
storage location
```

The general principle:

```text
Uploaded file
     ↓
UNTRUSTED
     ↓
Validate/process safely
     ↓
Store
```

# 18. Trust boundary vs security boundary

They're closely related, but don't confuse them.

A **trust boundary** is where assumptions about trust change.

A **security control** is something we use to protect that boundary.

For example:

```text
Internet
   │
   │ trust boundary
   ▼
Express
```

Security controls might be:

```text
CORS
Rate limiting
Validation
Sanitization
Authentication
Authorization
```

So:

```text
Boundary
   +
Security controls
   =
Safer system
```

---

# 19. The "never trust, always verify" mindset

You may hear this phrase in security:

> **Never trust, always verify.**

For backend development, it means:

```text
Client says:
"I am user 123."

Backend:
"Prove it."

Client says:
"This is my Todo."

Backend:
"Prove you own it."

Client says:
"This input is safe."

Backend:
"Validate it."

Client says:
"I should be admin."

Backend:
"Show that you are authorized."
```

That's the mindset we're developing.

# 20. Trust boundaries and your middleware

Now you can understand why your security middleware exists.

### CORS

Controls browser cross-origin behavior.

```text
Browser
   ↓
CORS policy
   ↓
Backend
```

### Rate limiting

Controls how much traffic an actor can send.

```text
Client
   ↓
Rate limiter
   ↓
Application
```

### Sanitization

Reduces risk from dangerous input.

```text
Untrusted input
   ↓
Sanitization
   ↓
Application
```

### Authentication

Changes:

```text
Unknown client
```

into:

```text
Verified identity
```

### Authorization

Changes:

```text
Authenticated user
```

into:

```text
User with specific permission
```

# 21. A very important example: `req.user`

Let's follow this carefully.

Initially:

```text
HTTP request
     ↓
req.headers.authorization
```

This is:

```text
UNTRUSTED
```

Authentication middleware:

```text
Extract token
     ↓
Verify signature
     ↓
Check expiration
     ↓
Extract identity
```

Then:

```js
req.user = {
    id: "...",
    role: "user"
};
```

Now later layers can use:

```js
req.user.id
```

as the authenticated identity.

But authorization still needs to happen.

```text
Authentication
     ↓
"Rahul is user 123."
     ↓
Authorization
     ↓
"User 123 may modify this note."
```

So:

```text
Authentication ≠ Authorization
```

We'll study this formally in **10.4**.

# 22. Trust boundaries and input sanitization

Suppose:

```js
const title = req.body.title;
```

At this point:

```text
title
 ↓
UNTRUSTED
```

After validation:

```text
title
 ↓
Validated
```

After sanitization/normalization where appropriate:

```text
title
 ↓
Safe application representation
```

Then:

```text
Service
 ↓
Repository
 ↓
Database
```

This is why we don't want random client data flowing directly into database queries.

Bad mental model:

```text
req.body
   ↓
MongoDB
```

Better:

```text
req.body
   ↓
validation
   ↓
sanitization/normalization
   ↓
business rules
   ↓
safe database operation
```

# 23. Mini exercise

Consider:

```http
PATCH /api/v1/users/123
```

Body:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

Suppose the request is sent by user `456`.

Think through the trust boundaries.

### Step 1

Who controls the body?

**The client.**

Therefore:

```text
req.body
→ untrusted
```

### Step 2

Who controls `123`?

**The client.**

Therefore:

```text
req.params.id
→ untrusted
```

### Step 3

Who controls the authentication header?

**The client supplies it.**

But after verification:

```text
JWT
 ↓
verified
 ↓
req.user.id = 456
```

Now the identity is trusted.

### Step 4

Can user `456` modify user `123`?

Not automatically.

We need:

```text
authorization / ownership check
```

### Step 5

Can user `456` change their own role to admin?

Probably not.

Even if:

```json
{
  "role": "admin"
}
```

passes basic validation, the **business rule** should reject it.

This single example demonstrates:

```text
Trust boundary
+
Validation
+
Authentication
+
Authorization
+
Allow-listing
```

## The key mental model

Whenever you see:

```js
req.body
```

your brain should immediately say:

> **"This came from outside my trust boundary. I need to decide what I can safely accept from it."**

And whenever you see:

```js
req.user
```

after proper authentication, think:

> **"This represents a verified identity, but I still need to check what this identity is allowed to do."**

That distinction will make **10.4 — Authentication vs Authorization** much easier.
