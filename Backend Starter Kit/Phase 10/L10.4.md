# Lesson 10.4 — Authentication vs Authorization

This is one of the **most important concepts in backend security**.

If you clearly understand these two words:

```text
Authentication
Authorization
```

then later topics like JWT, protected routes, roles, permissions, RBAC, ownership checks, and access control will become much easier.

---

# 1. The simplest explanation

Remember these two questions:

> **Authentication = Who are you?**

> **Authorization = What are you allowed to do?**

That's the entire foundation.

For example, imagine a college:

```text
Student enters college
        │
        ▼
"Who are you?"
        │
        ▼
Show ID card
        │
        ▼
Authentication
```

Then:

```text
"Can you enter the computer lab?"
        │
        ▼
Check permissions
        │
        ▼
Authorization
```

So:

```text
Authentication
      ↓
Identity

Authorization
      ↓
Permission
```

---

# 2. Authentication

Authentication is the process of verifying someone's identity.

The backend wants to answer:

> **"Is this really the user they claim to be?"**

For example, a user sends:

```http
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "secret123"
}
```

The backend might:

```text
Receive email/password
        ↓
Find user
        ↓
Compare password
        ↓
Password correct?
        ↓
Create access token
        ↓
Return token
```

Now the backend knows:

```text
This request belongs to user 123.
```

That's authentication.

---

# 3. Common authentication methods

Authentication can happen in different ways.

### Password authentication

```text
email + password
```

### JWT authentication

```http
Authorization: Bearer <token>
```

### Session authentication

```text
Cookie
   ↓
Session ID
   ↓
Server-side session
```

### OAuth

For example:

```text
Login with Google
Login with GitHub
```

All of these solve the same fundamental problem:

> **Establishing the identity of the requester.**

---

# 4. Authentication in your Express backend

Eventually, your backend might have middleware conceptually like:

```js
router.get(
    "/profile",
    authenticate,
    getProfile
);
```

The request comes in:

```text
Client
  │
  ▼
GET /profile
  │
  ▼
authenticate middleware
  │
  ├── Token missing → reject
  │
  ├── Token invalid → reject
  │
  └── Token valid
          │
          ▼
      req.user
          │
          ▼
      Controller
```

The authentication middleware might establish:

```js
req.user = {
    id: "123",
    role: "user"
};
```

Now the controller knows:

```text
Who is making this request?
→ User 123
```

---

# 5. Authorization

Now imagine the user is successfully authenticated.

The backend knows:

```text
User ID = 123
```

But that doesn't mean the user can do everything.

Suppose:

```http
DELETE /api/v1/users/456
```

User `123` is authenticated.

But should user `123` be allowed to delete user `456`?

Probably not.

So the backend asks another question:

> **"Is user 123 allowed to perform this operation?"**

That's authorization.

---

# 6. Authentication does not give permission

This is extremely important.

Imagine:

```text
User logs in successfully.
```

Authentication:

```text
✓ User identity verified
```

But:

```text
Can this user delete another user?
```

Authorization:

```text
✗ No permission
```

Therefore:

```text
Authentication
       ↓
"Who are you?"
       ↓
User 123

Authorization
       ↓
"What can User 123 do?"
       ↓
Allowed / denied
```

---

# 7. Real-world example

Think about your bank.

You authenticate using:

```text
Username
Password
OTP
```

The bank now knows:

> "This is Rahul."

But can Rahul:

```text
Delete another customer's account?
```

No.

Can Rahul:

```text
Transfer money from another customer's account?
```

No.

Can Rahul:

```text
View his own balance?
```

Yes.

So authentication tells the bank:

```text
Who is Rahul?
```

Authorization tells the bank:

```text
What can Rahul do?
```

# 8. REST API example

Imagine these endpoints:

```text
GET    /users/me
GET    /users/:id
PATCH  /users/:id
DELETE /users/:id

POST   /admin/users
DELETE /admin/users/:id
```

A normal user might be allowed:

```text
GET /users/me
PATCH /users/me
```

but not:

```text
DELETE /admin/users/123
```

The user can be authenticated while still being unauthorized.

```text
                REQUEST

                   ▼
          ┌─────────────────┐
```


# 10. What happens if authentication fails?

Suppose:

```http
GET /api/v1/profile
```

requires authentication.

But the client sends no token:

```http
GET /api/v1/profile
```

The backend might return:

```http
401 Unauthorized
```

Conceptually:

```text
No valid identity
      ↓
Authentication failed
      ↓
401
```

---

# 11. What happens if authorization fails?

Now suppose the user is properly authenticated:

```text
User = 123
```

But they try:

```http
DELETE /api/v1/admin/users/456
```

and they don't have admin permission.

The backend might return:

```http
403 Forbidden
```

Conceptually:

```text
Identity verified
      ↓
Permission denied
      ↓
403
```

So remember:

```text
401 → Authentication problem

403 → Authorization problem
```

This distinction is very important.

---

# 12. 401 vs 403

Let's make this crystal clear.

### `401 Unauthorized`

The request does not have a valid authenticated identity.

Examples:

```text
No token
Invalid token
Expired token
Malformed token
```

Think:

> **"I don't know who you are."**

---

### `403 Forbidden`

The backend knows who you are, but you aren't allowed to perform the action.

Example:

```text
User = 123
Role = user

Trying:
DELETE /admin/users/456
```

Think:

> **"I know who you are, but you can't do that."**

---

# 13. Authentication middleware

A typical architecture could look like:

```js
router.get(
    "/profile",
    authenticate,
    profileController.getProfile
);
```

The authentication middleware handles:

```text
Token
 ↓
Verify
 ↓
Identify user
 ↓
req.user
```

For example:

```js
const authenticate = async (req, res, next) => {
    const token = extractToken(req);

    const payload = verifyToken(token);

    req.user = {
        id: payload.sub,
        role: payload.role
    };

    next();
};
```

This is simplified, but the architecture is important.

---

# 14. Authorization middleware

Now imagine an admin-only endpoint:

```js
router.delete(
    "/users/:id",
    authenticate,
    authorize("admin"),
    deleteUser
);
```

The flow is:

```text
Request
   │
   ▼
authenticate
   │
   ▼
Who is this?
   │
   ▼
req.user
   │
   ▼
authorize("admin")
   │
   ├── role=user → 403
   │
   └── role=admin
          │
          ▼
      Controller
```

This is a very common backend pattern.

---

# 15. Authentication vs role-based authorization

Suppose:

```js
req.user = {
    id: "123",
    role: "user"
};
```

Authentication tells us:

```text
User 123 is authenticated.
```

Authorization can inspect:

```text
role = user
```

and decide:

```text
Can this user access admin routes?
```

For example:

```js
if (req.user.role !== "admin") {
    return next(new ForbiddenError());
}
```

This is **role-based authorization**.

---

# 16. But authorization is bigger than roles

This is important.

Authorization isn't only:

```text
admin
user
```

It can also involve:

```text
Ownership
Permissions
Resource
Action
Organization
Subscription
Account state
```

For example:

```text
Can Rahul edit this todo?
```

The answer may depend on:

```text
Is Rahul authenticated?
+
Does Rahul own the todo?
+
Is the todo editable?
```

That's authorization.

---

# 17. Ownership authorization

Consider:

```text
User A
  └── Todo A

User B
  └── Todo B
```

User A requests:

```http
PATCH /todos/TODO_B
```

Authentication:

```text
✓ User A is authenticated
```

Authorization:

```text
✗ Todo B belongs to User B
```

Therefore:

```http
403 Forbidden
```

or, depending on your API's resource-exposure policy, sometimes a `404` is used to avoid revealing that the resource exists.

The important idea is:

> **Being logged in doesn't automatically mean you own the requested resource.**

---

# 18. Authorization can happen in the service layer

Don't assume authorization must always be middleware.

For example:

```js
const updateTodo = async ({ userId, todoId, data }) => {
    const todo = await todoRepository.findById(todoId);

    if (!todo) {
        throw new NotFoundError("Todo not found");
    }

    if (todo.userId !== userId) {
        throw new ForbiddenError("Not allowed");
    }

    return todoRepository.update(todoId, data);
};
```

This is authorization/business logic inside the service.

This can be useful when permission depends on the actual resource.

---

# 19. Middleware vs service authorization

There are two common cases.

### Simple permission

Example:

```text
Only admins can access this route.
```

Middleware works well:

```js
authorize("admin")
```

### Resource-specific permission

Example:

```text
User can edit a todo only if they own it.
```

Service/business logic often makes more sense:

```text
Find todo
   ↓
Check owner
   ↓
Update
```

So:

```text
Role-based permission
        ↓
Middleware often useful

Resource ownership
        ↓
Service/business logic often useful
```

We'll go much deeper into authorization later.

# 21. A complete example

Suppose we have:

```http
DELETE /api/v1/todos/123
```

Let's follow it.

### Step 1 — Request arrives

```text
DELETE /todos/123
```

Everything supplied by the client is initially untrusted.

### Step 2 — Authentication

```text
Authorization header
       ↓
Verify token
       ↓
User = 456
```

Now:

```js
req.user.id === "456"
```

### Step 3 — Find resource

```text

```

### Step 4 — Authorization

Database says:

```text
Todo 123
ownerId = 456
```

```text

```

Result:

```text
✓ Authorized
```

### Step 5 — Delete

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

```text

```

```text

```


# 22. The danger of checking only authentication

Consider this route:

```js
router.delete(
    "/todos/:id",
    authenticate,
    deleteTodo
);
```

This means:

```text
✓ Must be logged in
```

But it does **not automatically mean**:

```text
✓ Must own the todo
```

That's a common security bug.

A logged-in attacker could potentially do:

```http
DELETE /todos/someone-elses-todo
```

if the service doesn't check ownership.

So:

```text
Authentication
≠
Authorization
```

Again.

---

# 23. The danger of checking only frontend permissions

Suppose React hides the delete button:

```jsx
{todo.ownerId === user.id && (
    <button>Delete</button>
)}
```

Good UX.

But it isn't enough for security.

An attacker can manually call:

```http
DELETE /api/v1/todos/123
```

So:

```text
Frontend permission check
       ↓
UX

Backend authorization
       ↓
SECURITY
```

The backend must enforce the rule.

# 25. Authentication is not just "login"

Another common misunderstanding:

> "Authentication happens only during login."

Not exactly.

Login establishes authentication credentials/session/token.

But every protected request may need to **authenticate the request again**.

For JWT:

```text
LOGIN
  ↓
Credentials verified
  ↓
JWT issued
```

Later:

```text
GET /profile
  ↓
JWT received
  ↓
JWT verified
  ↓
User authenticated
```

Then:

```text
PATCH /profile
  ↓
JWT verified
  ↓
User authenticated
  ↓
Authorization check
  ↓
Update
```

# 27. Authentication and authorization errors

Let's build a simple decision tree:

```text
Request
   │
   ▼
Valid authentication?
   │
   ├── NO ──→ 401
   │
   ▼
User identified
   │
   ▼
Allowed to perform action?
   │
   ├── NO ──→ 403
   │
   ▼
Continue
```

This is extremely useful when debugging APIs.

# 28. A subtle point about 404

Suppose:

```http
GET /todos/123
```

and todo `123` belongs to another user.

You could return:

```http
403 Forbidden
```

which tells the requester:

> "The resource exists, but you're not allowed."

But sometimes APIs return:

```http
404 Not Found
```

instead.

Why?

Because revealing that the resource exists may itself leak information.

For example:

```text
Attacker guesses:
GET /users/12345
```

If they receive:

```text
403
```

they learn:

> "User 12345 exists."

If they receive:

```text
404
```

they may not know whether the user exists.

This is an example of **information disclosure**.

The exact choice depends on your API's security requirements.

# 29. Authentication vs authorization — comparison

|Authentication|Authorization|
|---|---|
|Who are you?|What can you do?|
|Establishes identity|Establishes permission|
|Happens before protected actions|Happens after identity is known|
|Password/token/session|Role/permission/ownership|
|Can result in `401`|Can result in `403`|
|Example: verify JWT|Example: check admin role|
|Example: login|Example: delete user|

A very simple memory trick:

```text
AUTHENTICATION
      ↓
     WHO?

AUTHORIZATION
      ↓
    ALLOWED?
```
