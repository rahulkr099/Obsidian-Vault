# Lesson 10.5 — CORS Fundamentals

Now we are starting the **actual security middleware concepts**.

You have probably already seen code like:

```js
app.use(cors());
```

or in your starter:

```js
app.use(middleware.security.cors);
```

Today we're going to understand **why CORS exists**, what problem it solves, and—very importantly—what it **does not** protect.

---

# 1. What is CORS?

CORS stands for:

> **Cross-Origin Resource Sharing**

The name sounds complicated, but the basic idea is simple:

> **CORS controls which origins are allowed to make browser-based cross-origin requests to your backend.**

Suppose your application has:

```text
Frontend
https://myapp.com
```

and:

```text
Backend
https://api.myapp.com
```

These are different **origins**.

The browser needs to know:

> "Is `https://myapp.com` allowed to communicate with `https://api.myapp.com`?"

CORS provides a mechanism for the server to answer that question.

---

# 2. First understand "origin"

Before understanding CORS, you must understand **origin**.

An origin consists of:

```text
scheme + host + port
```

For example:

```text
https://example.com:443
```

contains:

```text
scheme = https
host   = example.com
port   = 443
```

So these can be different origins:

```text
https://example.com
http://example.com
https://api.example.com
https://example.com:3000
```

Even though they may look related.

---

# 3. Same origin vs different origin

Suppose your frontend is:

```text
http://localhost:5173
```

and your backend is:

```text
http://localhost:5000
```

The host is the same:

```text
localhost
```

but the ports are different:

```text
5173
5000
```

Therefore:

```text
http://localhost:5173
        ≠
http://localhost:5000
```

They are **different origins**.

This is extremely common during MERN development.

You might have:

```text
React
localhost:5173

Express
localhost:5000
```

and CORS becomes relevant.

---

# 4. Why does the browser care?

Browsers have a security mechanism called the **Same-Origin Policy (SOP)**.

Its basic purpose is:

> **A webpage should not freely read sensitive responses from another origin without permission.**

Imagine you're logged into:

```text
https://bank.com
```

Then you visit:

```text
https://evil.com
```

Suppose JavaScript on `evil.com` tries to access:

```http
GET https://bank.com/account
```

If browsers allowed every website to freely read every other website's responses, that could be extremely dangerous.

For example, the malicious site could potentially try to read private information from services where you're logged in.

So the browser places restrictions around cross-origin requests.

---

# 5. CORS is mainly a browser mechanism

This is one of the **most important things to remember**.

CORS is primarily about:

```text
Browser
   ↓
Cross-origin request
   ↓
Backend
```

It is **not** a general firewall for your API.

For example:

```text
React browser
     │
     ▼
    CORS
```

But:

```text
Postman
curl
Python script
Another backend server
```

can still send HTTP requests to your API.

Therefore:

```text
CORS
≠
Authentication
≠
Authorization
≠
Firewall
```

---

# 6. The classic misunderstanding

A beginner sees:

```js
app.use(
    cors({
        origin: "https://myapp.com"
    })
);
```

and thinks:

> "Now only my frontend can access my backend."

That's not completely correct.

It means the **browser's cross-origin access rules** will be controlled according to that policy.

An attacker can still use:

```bash
curl
```

for example:

```bash
curl https://api.myapp.com/users
```

The request can reach the server.

Therefore, CORS does not replace:

```text
Authentication
Authorization
Rate limiting
Input validation
```

---

# 7. A simple example

Imagine:

```text
Frontend
http://localhost:5173
```

calls:

```text
Backend
http://localhost:5000/api/users
```

The browser sends the request.

The server can respond with a header such as:

```http
Access-Control-Allow-Origin: http://localhost:5173
```

The browser sees:

```text
Request origin:
http://localhost:5173

Server allows:
http://localhost:5173
```

So the browser allows the frontend JavaScript to access the response.

Conceptually:

```text
Browser
   │
   │ Origin: localhost:5173
   ▼
Backend
   │
   │ Access-Control-Allow-Origin:
   │ localhost:5173
   ▼
Browser
   │
   ▼
JavaScript can read response
```

---

# 8. What is the `Origin` header?

When a browser makes certain cross-origin requests, it can include:

```http
Origin: https://myapp.com
```

The server can use this information when applying its CORS policy.

For example:

```http
Origin: https://myapp.com
```

The server might respond:

```http
Access-Control-Allow-Origin: https://myapp.com
```

This tells the browser:

> "This origin is allowed."

---

# 9. CORS is a conversation between browser and server

Think of it like this:

```text
Browser:

"I am making this request from
https://myapp.com."

             │
             ▼

Server:

"Okay. My policy allows
https://myapp.com."

             │
             ▼

Browser:

"Then I'll allow the webpage
to access the response."
```

The browser is the component enforcing the browser-side restriction.

That's why CORS makes much more sense when you think about:

```text
Browser + Origin + Server response
```

rather than thinking:

```text
CORS = server firewall
```

---

# 10. What exactly is an origin?

Let's practice.

### Example 1

```text
https://example.com
https://example.com
```

Same origin.

---

### Example 2

```text
http://example.com
https://example.com
```

Different origin.

Why?

```text
http
vs
https
```

Different scheme.

---

### Example 3

```text
https://example.com
https://api.example.com
```

Different origin.

Why?

```text
example.com
vs
api.example.com
```

Different host.

---

### Example 4

```text
http://localhost:3000
http://localhost:5000
```

Different origin.

Why?

```text
port 3000
vs
port 5000
```

---

# 11. Origin vs URL

This distinction can be confusing.

A URL can contain:

```text
scheme
host
port
path
query
fragment
```

For example:

```text
https://example.com:443/users?page=10
```

The origin is only:

```text
https://example.com:443
```

It does **not** include:

```text
/users?page=10
```

So these:

```text
https://example.com/users
https://example.com/products
```

have the same origin.

But:

```text
https://api.example.com/users
```

has a different origin.

---

# 12. Why MERN developers encounter CORS constantly

During development you often have:

```text
React
localhost:5173
```

and:

```text
Express
localhost:5000
```

Your frontend code:

```js
fetch("http://localhost:5000/api/v1/todos");
```

comes from:

```text
http://localhost:5173
```

while the API is:

```text
http://localhost:5000
```

Different origin.

So the browser applies cross-origin rules.

This is why you often see errors such as:

```text
Access to fetch at ...
from origin ...
has been blocked by CORS policy
```

This isn't necessarily an Express error.

It can be the **browser refusing to expose the response to your frontend JavaScript** because the server's CORS policy doesn't allow the origin.

---

# 13. What happens without CORS?

Imagine:

```text
Frontend
http://localhost:5173
```

requests:

```text
Backend
http://localhost:5000
```

but the backend doesn't provide the necessary CORS permission.

Conceptually:

```text
Browser
   │
   │ cross-origin request
   ▼
Backend
   │
   │ response
   ▼
Browser
   │
   X
   │
   └── JavaScript cannot access
       the response as allowed
```

The exact browser behavior depends on the request type and CORS situation, but the important idea is:

> **The browser enforces the cross-origin policy.**

---

# 14. CORS does not mean "block the request"

This is another subtle but important point.

Many beginners think:

```text
CORS rejects request
```

That's an oversimplification.

For some requests, the server may receive and process the request, while the browser prevents frontend JavaScript from reading the response if the CORS policy isn't satisfied.

For example:

```text
Browser
   │
   │ request
   ▼
Server
   │
   │ processes request
   ▼
Response
   │
   ▼
Browser
   │
   └── may block JS from reading it
```

This becomes especially important for certain state-changing requests.

So don't think of CORS as:

> "A server-side authorization system."

Think:

> **"A browser-enforced cross-origin access policy based on server-provided CORS headers."**

---

# 15. CORS and credentials

Now things become more interesting.

Suppose your application uses cookies:

```text
access token
refresh token
session cookie
```

The browser may need to send credentials with a cross-origin request.

For example:

```js
fetch("https://api.example.com/profile", {
    credentials: "include"
});
```

The server then needs an appropriate CORS configuration.

Conceptually:

```text
Browser
   │
   │ credentials
   ▼
Backend
   │
   │ CORS policy
   ▼
Browser
```

Credentialed CORS has stricter requirements.

We'll study the practical configuration later when we build the middleware.

For now, remember:

```text
Cross-origin + credentials
```

requires extra care.

---

# 16. Why `origin: "*"` can be dangerous

You may see:

```js
cors({
    origin: "*"
});
```

This means:

> Allow requests from any origin for the CORS policy.

That might be okay for some genuinely public APIs.

But you should not blindly use it for applications involving sensitive user data or credentialed requests.

For example:

```text
Private user dashboard
       ↓
Personal data
       ↓
Authentication cookies
       ↓
"Allow everyone"
```

is a very different situation from:

```text
Public weather API
       ↓
Public data
       ↓
No credentials
       ↓
Broad CORS policy
```

Security configuration depends on the application's threat model.

---

# 17. CORS is not CSRF protection

Another important distinction.

CORS and CSRF are related to browser security, but they are **not the same thing**.

### CORS

Controls whether browser JavaScript can access cross-origin responses according to the server's policy.

### CSRF

Concerns unwanted state-changing requests made using a victim's authenticated browser context.

For example:

```text
Victim logged into bank.com
       ↓
Visits malicious site
       ↓
Malicious site attempts action
       ↓
Victim's credentials/cookies may be involved
```

CSRF defenses can involve:

```text
SameSite cookies
CSRF tokens
Origin/Referer validation
```

CORS configuration alone should not be treated as a complete CSRF defense.

We'll revisit this when we go deeper into authentication and security engineering.

---

# 18. CORS vs authentication

Let's compare them.

### CORS asks:

```text
"Which browser origins are allowed
to access this response?"
```

### Authentication asks:

```text
"Who is making this request?"
```

Example:

```text
Origin:
https://myfrontend.com
```

doesn't prove:

```text
User:
Rahul
```

Similarly:

```text
Authorization: Bearer <token>
```

doesn't mean:

```text
Origin is allowed by CORS
```

They solve different problems.

---

# 19. CORS vs authorization

Suppose:

```text
https://myfrontend.com
```

is allowed by CORS.

Does that mean every user of that frontend can:

```http
DELETE /api/v1/users/123
```

No.

Authorization still needs to decide:

```text
Is this authenticated user allowed
to delete this resource?
```

So:

```text
CORS
   ↓
Browser origin policy

Authorization
   ↓
User/resource permission
```

---

# 20. CORS vs rate limiting

Suppose an attacker uses:

```text
curl
```

to send:

```text
100,000 requests
```

CORS doesn't solve that.

Rate limiting does.

So:

```text
CORS
   ↓
Cross-origin browser access

Rate limiting
   ↓
Request volume / abuse
```

Again:

> **One security control should not be expected to solve another security problem.**

---

# 21. CORS request flow

Here's the basic flow you should remember:

```text
                Browser
                   │
                   │
          Origin: myapp.com
                   │
                   ▼
               Backend
                   │
                   │
         CORS policy checks
                   │
                   ▼
              HTTP response
                   │
                   │
     Access-Control-Allow-Origin
                   │
                   ▼
                Browser
                   │
                   ▼
        Allow / block browser
        JavaScript access
```

This is the core idea.

---

# 22. Common CORS response headers

You will encounter headers such as:

```http
Access-Control-Allow-Origin
```

This specifies allowed origin(s).

Example:

```http
Access-Control-Allow-Origin: https://myapp.com
```

---

You may also encounter:

```http
Access-Control-Allow-Methods
```

Example:

```http
Access-Control-Allow-Methods: GET,POST,PATCH,DELETE
```

This tells the browser which methods are allowed under the CORS policy.

---

And:

```http
Access-Control-Allow-Headers
```

Example:

```http
Access-Control-Allow-Headers: Content-Type, Authorization
```

This is relevant when the request wants to send particular headers.

---

For credentials:

```http
Access-Control-Allow-Credentials: true
```

This is used in credentialed CORS scenarios and comes with important restrictions.

We'll examine these headers more deeply in **10.6 and 10.7**.

This package helps your Express application produce the appropriate CORS behavior and headers.

But don't memorize:

```js
cors()
```

```text

   ↓

   ↓

   ↓

   ↓

```

Then the code becomes much easier.

# 24. A better production mindset

Don't blindly copy:

```js
app.use(cors());
```

from a tutorial.

Ask:

```text
Which frontend origins should be allowed?

Should credentials be allowed?

Which methods are needed?

Which request headers are needed?

Is this API public or private?

Are cookies involved?

What environments exist?
```

For example:

```text
Development:
http://localhost:5173

Production:
https://app.example.com
```

You might want a policy that allows those specific application origins rather than every possible origin.

---

# 25. Multiple frontend origins

Your application might have:

```text
Web app:
https://app.example.com

Admin app:
https://admin.example.com

Development:
http://localhost:5173
```

You may therefore need an allow-list:

```js
const allowedOrigins = [
    "https://app.example.com",
    "https://admin.example.com",
    "http://localhost:5173"
];
```

Then your CORS logic can determine whether the request origin is allowed.

This idea connects directly to our future lesson:

**10.19 — Origin Validation**

---

# 26. Dynamic CORS

Sometimes you need to check the origin dynamically.

Conceptually:

```js
const allowedOrigins = [
    "https://app.example.com",
    "https://admin.example.com"
];

function isAllowedOrigin(origin) {
    return allowedOrigins.includes(origin);
}
```

Then:

```text
Request origin
      │
      ▼
Is origin in allow-list?
      │
   ┌──┴──┐
   │     │
  YES    NO
   │     │
   ▼     ▼
Allow   Reject/
        don't allow
```

This is more secure than blindly trusting:

```js
origin: true
```

in sensitive applications.

---

# 27. Don't use naive substring checks

A common bad idea is:

```js
if (origin.includes("example.com")) {
    allow();
}
```

Why can this be dangerous?

Consider:

```text
https://example.com.attacker.com
```

It contains:

```text
example.com
```

but it is **not**:

```text
https://example.com
```

So origin validation should compare actual origins rather than using careless substring matching.

Better:

```text
Exact allow-list
```

or carefully parsed origin validation.

We'll discuss this much more in **10.19**.

# 28. CORS and your MERN architecture

Your eventual application might look like:

```text
                  React
             localhost:5173
                    │
                    │ HTTP
                    ▼
             ┌──────────────┐
             │   Express    │
             └──────┬───────┘
                    │
              CORS middleware
                    │
                    ▼
            Other middleware
                    │
                    ▼
              Controllers
                    │
                    ▼
               Services
                    │
                    ▼
              Repositories
                    │
                    ▼
                MongoDB
```

CORS belongs near the **HTTP/security boundary**.

It isn't something that belongs inside:

```text
service
repository
database
```

because those layers don't need to know which browser origin made the request.

# 29. Why CORS should usually be early

Consider:

```text
Request
   ↓
CORS
   ↓
Rate limiting
   ↓
Parsing
   ↓
Sanitization
   ↓
Routes
```

CORS is concerned with the request's origin and browser cross-origin policy.

So it generally belongs in the application's HTTP middleware layer rather than deep inside business logic.

# 30. CORS doesn't protect your database

Suppose your backend has:

```text
MongoDB
```

CORS doesn't protect:

```text
MongoDB injection
```

It doesn't protect:

```text
Unauthorized database queries
```

It doesn't protect:

```text
Broken authorization
```

It doesn't protect:

```text
Leaked MongoDB credentials
```

Those require other security controls.

This is why security is layered.

# 31. One complete example

Imagine:

```text
React:
https://app.example.com

API:
https://api.example.com
```

The React application sends:

```http
GET /api/v1/profile
Origin: https://app.example.com
Authorization: Bearer <token>
```

Now there are **two different security questions**.

### Question 1 — CORS

```text
Is https://app.example.com
allowed to access this response?
```

CORS handles this browser-origin question.

### Question 2 — Authentication

```text
Is this token valid?
Who is the user?
```

Authentication handles this.

### Question 3 — Authorization

```text
Can this authenticated user
access /profile?
```

Authorization handles this.

So:

```text
                    REQUEST
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      CORS      Authentication   Authorization
        │              │              │
     Origin           Who?          Allowed?
```

Three different questions.

# 33. The biggest CORS misconception

Let's lock this into your memory:

### Wrong:

> "CORS prevents unauthorized users from calling my API."

### Correct:

> **CORS controls browser-based cross-origin access to responses according to the server's policy.**

Authentication and authorization are still required to protect your API.

Think:

```text
CORS
   ↓
Can this browser origin access the response?

Authentication
   ↓
Who is this requester?

Authorization
   ↓
Can this requester perform this action?
```
