# Lesson 10.7 — Preflight `OPTIONS` Requests

In **10.6**, we learned that the browser can check CORS before allowing frontend JavaScript to access a cross-origin response.

Now we'll understand one of the most confusing things you'll see in your MERN backend:

```http
OPTIONS /api/users
```

You might wonder:

> "I never sent an `OPTIONS` request. Why is the browser sending this?"

The answer is:

> **The browser may send a CORS preflight request before sending the actual request.**

---

# 1. What is a preflight request?

A **preflight request** is a request the browser sends to the server **before the actual cross-origin request** to ask:

> "Am I allowed to make this kind of request?"

It uses the HTTP method:

```http
OPTIONS
```

So the basic flow becomes:

```text
Browser
   │
   │ OPTIONS
   │ "Can I send this request?"
   ▼
Server
   │
   │ "Yes, that's allowed."
   ▼
Browser
   │
   │ POST / PATCH / DELETE
   ▼
Server
```

This preliminary `OPTIONS` request is called the **preflight**.

---

# 2. Why does the browser need preflight?

Imagine your React application wants to send:

```http
PATCH /api/users/123
```

with:

```http
Content-Type: application/json
Authorization: Bearer <token>
```

This is a more powerful request than a basic:

```http
GET /products
```

The browser wants to make sure the target server explicitly allows this type of cross-origin operation.

So it asks first:

```text
"Server, do you allow this?"
```

Only after getting an acceptable CORS response does it send the actual request.

---

# 3. Simple mental model

Think of preflight like entering a building.

Instead of:

```text
You → Enter building
```

the browser does:

```text
You
 ↓
Security desk
 ↓
"Are you allowed to enter?"
 ↓
YES
 ↓
Enter
```

In HTTP:

```text
Browser
   ↓
OPTIONS
   ↓
Server
   ↓
CORS permission
   ↓
Actual request
```

---

# 4. A real MERN example

Suppose:

```text
React:
http://localhost:5173
```

and:

```text
Express:
http://localhost:5000
```

Your React code:

```js
await fetch("http://localhost:5000/api/users/123", {
    method: "PATCH",
    headers: {
        "Content-Type": "application/json",
        "Authorization": `Bearer ${token}`
    },
    body: JSON.stringify({
        name: "Rahul"
    })
});
```

The browser may not immediately send:

```http
PATCH /api/users/123
```

Instead:

```text
1. Browser
      ↓
2. OPTIONS /api/users/123
      ↓
3. Server responds with CORS permissions
      ↓
4. Browser checks response
      ↓
5. Browser sends PATCH
```

---

# 5. What does the preflight request look like?

A simplified preflight request could look like:

```http
OPTIONS /api/users/123 HTTP/1.1
Host: localhost:5000
Origin: http://localhost:5173
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: authorization, content-type
```

There are three extremely important headers here.

### 1. `Origin`

```http
Origin: http://localhost:5173
```

It tells the server:

> "The request is coming from this origin."

---

### 2. `Access-Control-Request-Method`

```http
Access-Control-Request-Method: PATCH
```

It tells the server:

> "I want to send a PATCH request."

---

### 3. `Access-Control-Request-Headers`

```http
Access-Control-Request-Headers: authorization, content-type
```

It tells the server:

> "I want to send these headers."

So the browser is effectively asking:

```text
Origin:
http://localhost:5173

Method:
PATCH

Headers:
Authorization
Content-Type

Is this allowed?
```

---

# 6. What does the server send back?

The Express server can respond with CORS headers such as:

```http
HTTP/1.1 204 No Content

Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET,POST,PATCH,DELETE
Access-Control-Allow-Headers: Authorization,Content-Type
```

Now the browser can evaluate:

```text
Requested origin:
http://localhost:5173

Allowed origin:
http://localhost:5173

        ↓

MATCH
```

and:

```text
Requested method:
PATCH

Allowed methods:
GET, POST, PATCH, DELETE

        ↓

PATCH allowed
```

and:

```text
Requested headers:
Authorization
Content-Type

Allowed headers:
Authorization
Content-Type

        ↓

Headers allowed
```

The browser can then proceed with the actual request.

---

# 7. Complete preflight flow

This is worth memorizing:

```text
                    Browser
                       │
                       │
                       │ Wants:
                       │ PATCH
                       │ Authorization
                       │ Content-Type
                       ▼
              OPTIONS /api/users/123
                       │
                       │
                       │ Origin:
                       │ localhost:5173
                       │
                       │ Access-Control-Request-Method:
                       │ PATCH
                       │
                       │ Access-Control-Request-Headers:
                       │ authorization, content-type
                       ▼
                    Express
                       │
                       │ CORS middleware
                       ▼
              CORS response headers
                       │
                       ▼
                    Browser
                       │
                 CORS check
                       │
                ┌──────┴──────┐
                │             │
              Allowed       Denied
                │             │
                ▼             ▼
          Actual request    Browser
             PATCH          blocks it
                │
                ▼
              Express
```

This is the most important diagram in this lesson.

---

# 8. Why is the method called `OPTIONS`?

HTTP has several methods:

```text
GET
POST
PUT
PATCH
DELETE
OPTIONS
HEAD
```

`OPTIONS` is used to ask about the communication options supported by a resource/server.

CORS uses it for preflight.

So:

```http
OPTIONS /api/users
```

doesn't mean:

> "Create something."

or:

> "Update something."

It's basically the browser asking:

> "What am I allowed to do here?"

---

# 9. Preflight is not the actual request

This distinction is very important.

Suppose you want:

```http
DELETE /api/users/123
```

You may see:

```text
OPTIONS /api/users/123
DELETE /api/users/123
```

The first request:

```http
OPTIONS
```

is the **preflight**.

The second:

```http
DELETE
```

is the **actual request**.

So:

```text
OPTIONS
   ↓
Permission check

DELETE
   ↓
Actual operation
```

---

# 10. Does every cross-origin request cause preflight?

**No.**

This is another important concept.

Browsers have a category commonly called a **simple request**.

Some cross-origin requests can be sent without a preflight.

For example, a basic request such as:

```http
GET /api/products
```

with simple request characteristics may go directly to the server.

But a request involving things such as:

```text
PATCH
DELETE
Authorization
application/json
```

can cause a preflight.

Don't memorize a simplistic rule like:

> "POST always causes preflight."

That's not correct.

Whether a request is preflighted depends on the request's method, headers, and other CORS conditions.

---

# 11. Example: simple GET

Suppose:

```js
fetch("https://api.example.com/products");
```

The browser may do:

```text
GET
 ↓
Server
 ↓
Response
 ↓
Browser CORS check
```

No `OPTIONS` is necessarily required first.

---

# 12. Example: JSON POST

Now:

```js
fetch("https://api.example.com/users", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify({
        name: "Rahul"
    })
});
```

Because of the request characteristics, the browser may perform:

```text
OPTIONS
   ↓
POST
```

So in DevTools you might see:

```text
OPTIONS /users
POST /users
```

---

# 13. Example: PATCH

```js
fetch("https://api.example.com/users/123", {
    method: "PATCH",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify({
        name: "Rahul"
    })
});
```

You may see:

```text
OPTIONS /users/123
PATCH /users/123
```

---

# 14. Example: Authorization header

Suppose:

```js
fetch("https://api.example.com/profile", {
    headers: {
        Authorization: `Bearer ${token}`
    }
});
```

The browser may need to perform a preflight because of the requested header.

You could see:

```text
OPTIONS /profile
GET /profile
```

This is why authentication and CORS often meet each other in MERN applications.

---

# 15. What does `Access-Control-Request-Method` mean?

This header appears in the **preflight request**.

Example:

```http
Access-Control-Request-Method: DELETE
```

It means:

> "If you allow me to proceed, I want to send a DELETE request."

The server can respond with:

```http
Access-Control-Allow-Methods: GET,POST,PATCH,DELETE
```

Now the browser sees:

```text
Requested:
DELETE

Allowed:
GET, POST, PATCH, DELETE

        ↓

YES
```

---

# 16. What does `Access-Control-Request-Headers` mean?

Suppose your actual request needs:

```http
Authorization
Content-Type
```

The browser can tell the server during preflight:

```http
Access-Control-Request-Headers: authorization, content-type
```

The server can respond:

```http
Access-Control-Allow-Headers: Authorization, Content-Type
```

The browser checks whether the requested headers are allowed.

---

# 17. Request headers vs response headers

This is a very useful distinction.

### Browser → Server

The browser sends:

```http
Origin
Access-Control-Request-Method
Access-Control-Request-Headers
```

during preflight.

### Server → Browser

The server responds with:

```http
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
```

Think:

```text
Browser asks:
"Can I?"

Server answers:
"Yes, you can."
```

---

# 18. Why do I sometimes see `OPTIONS 204`?

When using Express CORS middleware, you may see something like:

```text
OPTIONS /api/users 204
```

This is often completely normal.

`204` means:

```text
No Content
```

The server doesn't need to send a normal application response body for the preflight.

It mainly needs to provide the appropriate CORS headers.

So:

```text
OPTIONS
204
```

isn't automatically an error.

---

# 19. Why does my controller not run for `OPTIONS`?

Suppose you have:

```js
router.patch(
    "/users/:id",
    updateUser
);
```

and the browser sends:

```http
OPTIONS /users/123
```

You might wonder:

> "Why isn't `updateUser()` running?"

Because:

```text
OPTIONS
```

and:

```text
PATCH
```

are different HTTP methods.

Your PATCH controller is supposed to handle:

```http
PATCH /users/123
```

not:

```http
OPTIONS /users/123
```

The CORS middleware can handle the preflight before the request reaches your actual route.

---

# 20. Express middleware flow

Your application might eventually look like:

```js
app.use(cors(corsOptions));

app.use(express.json());

app.use("/api/users", userRouter);
```

The browser sends:

```http
OPTIONS /api/users/123
```

Express processes middleware.

Conceptually:

```text
OPTIONS
   ↓
CORS middleware
   ↓
CORS response
   ↓
Browser
```

Then, if allowed:

```text
PATCH
   ↓
CORS middleware
   ↓
express.json()
   ↓
router
   ↓
controller
   ↓
service
   ↓
repository
```

This is one reason **middleware ordering** matters.

We'll study the complete ordering in **10.20**.

---

# 21. What if the preflight fails?

Suppose the browser asks:

```http
Access-Control-Request-Method: PATCH
```

but the server responds:

```http
Access-Control-Allow-Methods: GET,POST
```

`PATCH` isn't included.

The browser can reject the cross-origin operation.

So the actual:

```http
PATCH
```

may never be sent.

This is different from the earlier situation where the server may have already received the actual request.

With a failed preflight:

```text
OPTIONS
   ↓
Denied
   ↓
Actual request is not sent
```

This is one of the major purposes of preflight.

---

# 22. What if the origin fails?

Browser:

```http
Origin: http://localhost:5173
```

Server:

```http
Access-Control-Allow-Origin: https://app.example.com
```

They don't match.

The browser rejects the CORS permission.

Conceptually:

```text
Requested:
localhost:5173

Allowed:
app.example.com

        ↓

      MISMATCH

        ↓

      DENIED
```

---

# 23. What if the requested header isn't allowed?

Browser:

```http
Access-Control-Request-Headers:
authorization
```

Server:

```http
Access-Control-Allow-Headers:
Content-Type
```

`Authorization` isn't allowed.

Therefore the preflight can fail.

This is a very common source of errors when developers add JWT authentication.

---

# 24. A very common MERN debugging situation

You write:

```js
fetch("http://localhost:5000/api/profile", {
    headers: {
        Authorization: `Bearer ${token}`
    }
});
```

The browser sends:

```http
OPTIONS /api/profile
```

Your server doesn't properly handle CORS.

Then you see:

```text
CORS policy error
```

You inspect Network:

```text
OPTIONS /api/profile
```

and think:

> "Why is my browser calling OPTIONS?"

Now you know.

It is probably asking:

```text
Can I make this cross-origin request
with these headers?
```

---

# 25. Preflight and authentication

Here's an important security point.

The preflight isn't equivalent to:

```text
"Is the user authenticated?"
```

It is asking:

```text
"Is this cross-origin request allowed?"
```

For example:

```text
OPTIONS
   ↓
CORS permission

GET /profile
   ↓
Authentication

GET /admin
   ↓
Authorization
```

These are separate layers.

---

# 26. Don't put business logic in preflight

Your preflight handler shouldn't do things like:

```text
Create user
Update database
Send email
Delete account
```

It should mainly answer the browser's CORS negotiation.

Think:

```text
OPTIONS
   ↓
Infrastructure/security concern
```

while:

```text
POST /users
PATCH /users/:id
DELETE /users/:id
```

handle actual business operations.

---

# 27. Preflight and rate limiting

This creates another interesting security consideration.

Your application may receive many:

```http
OPTIONS
```

requests.

A rate limiter should be designed thoughtfully so legitimate browsers aren't accidentally blocked simply because they perform CORS preflights.

This is one reason we don't blindly put every middleware everywhere.

Later, when we build:

```text
10.11 Rate limiting
10.12 Global rate limiting
```

we'll consider this kind of middleware interaction.

---

# 28. Preflight caching

Browsers can cache successful preflight results for some period.

The server can communicate a desired cache duration with:

```http
Access-Control-Max-Age
```

For example:

```http
Access-Control-Max-Age: 600
```

Conceptually:

```text
First request
   ↓
OPTIONS
   ↓
Server says "allowed"
   ↓
Browser remembers
   ↓
Future matching requests
   ↓
May avoid another preflight
```

This can reduce unnecessary `OPTIONS` requests.

However, don't worry about optimizing this yet.

First understand the basic flow.

---

# 29. The `OPTIONS` request can look strange in DevTools

You may see:

```text
Name                Method       Status

users               OPTIONS      204
users               POST         201
```

Don't interpret this as:

```text
"Why did my API run twice?"
```

It means:

```text
OPTIONS
   ↓
CORS negotiation

POST
   ↓
Actual operation
```

So your browser may make **two HTTP requests for one frontend operation**.

That's completely normal when preflight is required.

# 30. The complete real-world example

Let's walk through one.

Frontend:

```text
http://localhost:5173
```

Backend:

```text
http://localhost:5000
```

React:

```js
await fetch(
    "http://localhost:5000/api/users/123",
    {
        method: "PATCH",
        headers: {
            "Content-Type": "application/json",
            "Authorization": `Bearer ${token}`
        },
        body: JSON.stringify({
            name: "Rahul"
        })
    }
);
```

### Step 1 — Browser detects cross-origin request

```text
5173
  ↓
5000

Different origin
```

### Step 2 — Browser performs preflight

```http
OPTIONS /api/users/123
Origin: http://localhost:5173
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: authorization, content-type
```

### Step 3 — Server responds

```http
204 No Content
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET,POST,PATCH,DELETE
Access-Control-Allow-Headers: Authorization,Content-Type
```

### Step 4 — Browser checks

```text
Origin?       ✓
Method?       ✓
Headers?      ✓
```

### Step 5 — Browser sends actual request

```http
PATCH /api/users/123
Origin: http://localhost:5173
Authorization: Bearer ...
Content-Type: application/json
```

### Step 6 — Express handles actual request

```text
CORS
 ↓
JSON parser
 ↓
Authentication
 ↓
Authorization
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
MongoDB
```

That's a realistic MERN request lifecycle.

# 31. Why this matters for your starter project

Your starter eventually contains something conceptually like:

```js
app.use(middleware.security.cors);
```

Now you should understand that this middleware isn't simply:

```text
"Allow frontend."
```

It participates in a browser protocol involving:

```text
Origin
OPTIONS
Access-Control-Request-Method
Access-Control-Request-Headers
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
```

That's why we'll build it carefully rather than blindly copying:

```js
cors()
```

# 32. A compact cheat sheet

|Header|Direction|Meaning|
|---|---|---|
|`Origin`|Browser → Server|Where the request came from|
|`Access-Control-Request-Method`|Browser → Server|Method the browser wants to use|
|`Access-Control-Request-Headers`|Browser → Server|Headers the browser wants to send|
|`Access-Control-Allow-Origin`|Server → Browser|Which origin is allowed|
|`Access-Control-Allow-Methods`|Server → Browser|Which methods are allowed|
|`Access-Control-Allow-Headers`|Server → Browser|Which request headers are allowed|
|`Access-Control-Allow-Credentials`|Server → Browser|Whether credentials are allowed|
|`Access-Control-Max-Age`|Server → Browser|How long preflight permission may be cached|

You don't need to memorize all of these yet.

Understand the direction:

```text
Browser asks
     ↓
Access-Control-Request-*

Server answers
     ↓
Access-Control-Allow-*
```

That's the pattern.

# 33. Common beginner mistakes

### Mistake 1

Thinking:

```text
OPTIONS = error
```

No.

```text
OPTIONS = potentially a CORS preflight
```

---

### Mistake 2

Thinking:

```text
OPTIONS = actual API operation
```

No.

It's usually a permission/communication check.

---

### Mistake 3

Thinking:

```text
POST always requires preflight
```

Not necessarily.

It depends on the request characteristics.

---

### Mistake 4

Thinking:

```text
CORS = authentication
```

No.

```text
CORS → browser cross-origin policy
Authentication → identity
Authorization → permissions
```

---

### Mistake 5

Seeing:

```text
OPTIONS
POST
```

and thinking your frontend submitted the form twice.

Not necessarily.

The first may simply be the browser's preflight.
