# Lesson 10.8 — Building CORS Middleware

Now we move from **understanding CORS → actually writing CORS middleware**.

Your starter eventually needs something like:

```js
app.use(middleware.security.cors);
```

The goal of this lesson is that you should understand **what that middleware is doing and why each option exists**, instead of simply writing:

```js
app.use(cors());
```

Your starter's Phase 10 specifically lists **CORS** as one of the security middleware components.

---

# 1. First: what are we building?

Our goal is:

```text
Browser
   ↓
Origin
   ↓
CORS middleware
   ↓
Allowed?
   ├── YES → continue
   └── NO  → browser cannot access response
```

For a MERN application, imagine:

```text
React
http://localhost:5173

        ↓

Express API
http://localhost:5000
```

We want the backend to explicitly know:

```text
Allowed frontend:
http://localhost:5173
```

---

# 2. Install the CORS package

If you haven't already:

```bash
npm install cors
```

The package provides Express middleware for handling CORS.

Your starter roadmap also identifies `cors` as one of the core backend dependencies.

---

# 3. The simplest possible version

You could write:

```js
import cors from "cors";

app.use(cors());
```

This is useful for learning, but **don't stop here**.

Why?

Because a production application should have an intentional CORS policy.

We want to answer:

```text
Which origins?
Which methods?
Which headers?
Credentials?
```

---

# 4. Start with an allowed origin

Let's say your React frontend runs at:

```text
http://localhost:5173
```

We can configure:

```js
import cors from "cors";

app.use(
    cors({
        origin: "http://localhost:5173"
    })
);
```

Now the CORS middleware knows the allowed frontend origin.

Conceptually:

```text
Request
   │
   │ Origin:
   │ http://localhost:5173
   ▼
cors()
   │
   ▼
Allowed
```

---

# 5. Why shouldn't we hard-code this?

This is okay for learning:

```js
origin: "http://localhost:5173"
```

But eventually you'll have different environments:

```text
Development
http://localhost:5173

Production
https://app.example.com
```

Your uploaded starter's architecture also uses environment configuration such as:

```text
FRONTEND_URL=http://localhost:5173
```

rather than hard-coding application configuration everywhere.

So eventually we want:

```js
origin: env.frontendUrl
```

rather than:

```js
origin: "http://localhost:5173"
```

---

# 6. Create an environment variable

In `.env`:

```env
FRONTEND_URL=http://localhost:5173
```

Then your configuration layer can expose it:

```js
const env = {
    frontendUrl: process.env.FRONTEND_URL
};
```

Then:

```js
cors({
    origin: env.frontendUrl
});
```

Now the flow is:

```text
.env
 ↓
env.js
 ↓
CORS middleware
 ↓
Browser
```

This is much cleaner.

Your starter architecture separates security middleware under:

The broader starter architecture explicitly includes security middleware such as:

```text

   ↓

```

This keeps security-related HTTP behavior together.

# 8. Create `cors.middleware.js`

Let's start simple.

```js
import cors from "cors";

export const corsMiddleware = cors({
    origin: "http://localhost:5173"
});
```

Now `corsMiddleware` itself is an Express middleware function.

You can use it:

```js
app.use(corsMiddleware);
```

Or, following your starter's style:

```js
app.use(middleware.security.cors);
```

---

# 9. Why export the middleware?

You might ask:

> "Why not just call `cors()` directly inside `app.js`?"

You can.

But your architecture is trying to keep responsibilities separated.

Instead of:

```js
// app.js

app.use(
    cors({
        origin: "http://localhost:5173"
    })
);
```

you can have:

```text
middlewares/
└── security/
    └── cors.middleware.js
```

and:

```js
// app.js

app.use(middleware.security.cors);
```

Now `app.js` is primarily assembling the application.

Your starter's overall architecture follows this idea: `app.js` is where Express is assembled, with security middleware, CORS, parsers, logging, routes, 404 handling, and error handling.

# 10. Add methods

You can explicitly configure allowed HTTP methods:

```js
const corsMiddleware = cors({
    origin: env.frontendUrl,

    methods: [
        "GET",
        "POST",
        "PUT",
        "PATCH",
        "DELETE",
        "OPTIONS"
    ]
});
```

This communicates your API's intended CORS methods.

For example:

```text
GET       ✓
POST      ✓
PUT       ✓
PATCH     ✓
DELETE    ✓
OPTIONS   ✓
```

---

# 11. Why is `OPTIONS` included?

You learned this in **10.7**.

The browser can send:

```http
OPTIONS /api/users
```

as a preflight request.

So CORS configuration needs to properly handle preflight.

Conceptually:

```text
Browser
   ↓
OPTIONS
   ↓
CORS middleware
   ↓
"PATCH is allowed"
   ↓
Browser
   ↓
PATCH
```

This is why `OPTIONS` isn't some random extra method.

It's part of the CORS protocol.

---

# 12. Configure allowed headers

Suppose your frontend sends:

```http
Authorization: Bearer ...
Content-Type: application/json
```

You can configure:

```js
const corsMiddleware = cors({
    origin: env.frontendUrl,

    methods: [
        "GET",
        "POST",
        "PUT",
        "PATCH",
        "DELETE",
        "OPTIONS"
    ],

    allowedHeaders: [
        "Content-Type",
        "Authorization"
    ]
});
```

Now your CORS policy explicitly describes the headers your frontend needs.

---

# 13. Why `Authorization` matters

Later, your authentication middleware may expect:

```http
Authorization: Bearer <access-token>
```

The request might be:

```text
React
  ↓
fetch()
  ↓
Authorization header
  ↓
API
```

For cross-origin browser requests, CORS must allow the browser to use that header where preflight applies.

So these two concepts connect:

```text
CORS
   ↓
Allows browser request characteristics

Authentication
   ↓
Reads Authorization header
```

They are separate responsibilities.

---

# 14. `credentials`

Now let's talk about one of the most important CORS options:

```js
credentials: true
```

This is relevant when the browser needs to send credentials such as cookies in a cross-origin request.

For example:

```js
fetch("https://api.example.com/me", {
    credentials: "include"
});
```

The server can configure:

```js
cors({
    origin: "https://app.example.com",
    credentials: true
});
```

Conceptually:

```text
Browser
   │
   │ cross-origin request
   │ + credentials
   ▼
API
   │
   │ CORS allows credentials
   ▼
Browser
```

---

# 15. Important: credentials and `*`

A very important rule:

You should **not** combine credentialed CORS with:

```js
origin: "*"
```

For example, don't build:

```js
cors({
    origin: "*",
    credentials: true
});
```

For credentialed browser requests, the server needs to identify an allowed origin rather than using the wildcard.

This is one reason an explicit origin configuration is safer for applications using authentication cookies.

---

# 16. When do you need `credentials: true`?

Don't automatically add it.

Ask:

> "Does my frontend need to send browser credentials cross-origin?"

For example, if authentication uses cookies:

```text
Browser
   ↓
Cookie
   ↓
API
```

then credentialed CORS may be required.

If you're using a bearer token in:

```http
Authorization: Bearer ...
```

the situation is different: you're explicitly sending an authorization header rather than relying on browser cookies.

So don't blindly add:

```js
credentials: true
```

to every project.

# 19. Multiple allowed origins

Real applications often have more than one frontend.

For example:

```text
http://localhost:5173
https://app.example.com
https://admin.example.com
```

You can maintain an allow-list:

```js
const allowedOrigins = [
    "http://localhost:5173",
    "https://app.example.com",
    "https://admin.example.com"
];
```

Then determine whether the incoming origin is allowed.

Conceptually:

```text
Incoming origin
      │
      ▼
┌──────────────────────────┐
│ Is it in allowedOrigins? │
└────────────┬─────────────┘
             │
       ┌─────┴─────┐
       ▼           ▼
      YES          NO
       │           │
       ▼           ▼
     Allow       Reject
```

This leads directly into **10.19 — Origin Validation**.

# 20. Dynamic origin function

The `cors` package can accept a function for `origin`.

For example:

```js
const allowedOrigins = [
    "http://localhost:5173",
    "https://app.example.com"
];

const corsMiddleware = cors({
    origin(origin, callback) {
        if (!origin || allowedOrigins.includes(origin)) {
            callback(null, true);
            return;
        }

        callback(new Error("Origin not allowed"));
    }
});
```

Let's understand the pieces.

### `origin`

```js
origin
```

is the origin supplied by the browser.

For example:

```text
http://localhost:5173
```

---

### `allowedOrigins`

```js
allowedOrigins.includes(origin)
```

asks:

> "Is this origin on my allow-list?"

---

### `callback(null, true)`

Means:

```text
Allow this origin
```

---

### `callback(new Error(...))`

Means:

```text
This origin isn't allowed
```

We'll build a cleaner production version when we reach **10.19**.

For now, understand the idea.

---

# 21. Why `!origin`?

You may have noticed:

```js
if (!origin || allowedOrigins.includes(origin))
```

Why allow requests without an origin?

Because not every HTTP client behaves like a browser.

For example:

```text
curl
Postman
server-to-server request
```

may not provide an `Origin` header.

Remember:

> CORS is primarily a browser mechanism.

So the absence of an `Origin` header isn't automatically proof of an attack.

However, whether you want to allow such requests is an **application-specific security decision**.

Don't treat this line as a universal rule.

# 22. CORS middleware vs origin middleware

Your starter mentions both:

```text
CORS
Origin checking
```

These are related but can have different responsibilities.

### CORS middleware

Handles browser CORS behavior:

```text
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
...
```

### Origin validation middleware

Can perform application-level validation such as:

```text
Is this request origin trusted?
```

You can therefore have:

```text
Request
   ↓
Origin validation
   ↓
CORS
   ↓
Other security middleware
```

or another carefully designed ordering depending on the architecture.

We'll study the complete ordering in **10.20**.

# 30. Common mistake: `origin: true`

You may encounter:

```js
cors({
    origin: true
});
```

Be careful.

This can dynamically reflect the request origin rather than restricting it to your known frontend origins.

That may be appropriate in some situations, but you shouldn't use it just because:

> "It fixed my CORS error."

Security configuration should be based on your application's trust model.

---

# 31. Common mistake: wildcard everywhere

Another beginner solution:

```js
cors({
    origin: "*"
});
```

This essentially says:

```text
Any origin
```

For a public API serving public data, that may be reasonable.

For a private application with user data and credentialed browser access, blindly doing this is usually a poor security choice.

Prefer:

```text
Known frontend origins
```

when your architecture permits it.

---

# 32. Common mistake: putting CORS inside controllers

Don't do:

```js
export const getUser = (req, res) => {
    // CORS logic here
};
```

That's the wrong layer.

CORS is an **HTTP middleware concern**.

Keep it at:

```text
Middleware layer
```

not:

```text
Controller
Service
Repository
Model
```

# 40. Interview questions

Try answering these without looking back.

### Q1. What does the `cors` package do?

**Answer:** It provides Express middleware that handles CORS behavior and sets the appropriate CORS response headers.

---

### Q2. Why should CORS configuration usually be middleware?

Because CORS is an HTTP-level concern that should be handled centrally rather than duplicated across controllers.

---

### Q3. What does this mean?

```js
origin: "http://localhost:5173"
```

It specifies that this browser origin is allowed by the CORS policy.

---

### Q4. What is `allowedHeaders`?

It specifies request headers that the CORS policy permits the browser to use for cross-origin requests.

---

### Q5. Why is `OPTIONS` included?

Because browsers may use `OPTIONS` for CORS preflight requests.

---

### Q6. Is CORS authentication?

No.

```text
CORS
→ browser cross-origin access

Authentication
→ who are you?
```

---

### Q7. Should every application use `origin: "*"`?

No. The correct policy depends on the application's architecture and security requirements.
