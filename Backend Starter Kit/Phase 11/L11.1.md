# Lesson 11.1 — What is a Controller?

In the previous phases, you learned that a request travels through middleware before reaching the actual application logic.

Now we're going to learn the **Controller**.

The simplest definition is:

> **A controller is the part of your backend that handles an HTTP request and prepares an HTTP response.**

Your starter architecture places controllers between middleware/routes and the deeper application layers, which is exactly the structure we're going to learn.

---

## 1. First, forget the folder

Don't think:

```text
controllers/
```

Think about the **job**.

Suppose the frontend sends:

```http
GET /api/v1/users/me
```

Something needs to answer:

```text
What should happen with this HTTP request?
```

That's where the controller comes in.

A simplified flow is:

```text
                HTTP REQUEST
                     │
                     ▼
                   ROUTE
                     │
                     ▼
                MIDDLEWARE
                     │
                     ▼
                CONTROLLER
                     │
                     ▼
                 RESPONSE
```

For now, don't worry about Services or Repositories. We'll add those later.

---

# 2. Real-world analogy

Imagine a restaurant.

```text
Customer
   ↓
Reception
   ↓
Waiter
   ↓
Kitchen
```

The waiter receives your request:

> "I want a pizza."

The waiter doesn't personally grow wheat, make cheese, or manufacture the oven.

The waiter:

1. receives the customer's request
    
2. understands what the customer wants
    
3. sends the request to the kitchen
    
4. receives the result
    
5. gives the result back to the customer
    

A controller is somewhat similar.

```text
Frontend
   ↓
Controller
   ↓
Application logic
   ↓
Controller
   ↓
Frontend
```

The controller is the **HTTP-facing part of your application**.

---

# 3. A controller is a function

At the simplest level:

```js
const helloController = (req, res) => {
    res.json({
        message: "Hello"
    });
};
```

That's a controller.

Nothing magical is happening.

It's simply a function that receives:

```js
req
```

and:

```js
res
```

and produces an HTTP response.

---

# 4. What are `req` and `res`?

You already saw these while learning Express.

### `req`

Means:

```text
request
```

It contains information coming **from the client**.

For example:

```js
req.body
req.params
req.query
req.headers
req.cookies
```

We'll study these carefully in later lessons.

---

### `res`

Means:

```text
response
```

It's what your server uses to answer the client.

For example:

```js
res.json(...)
```

or:

```js
res.status(201).json(...)
```

---

# 5. Your first controller

Create:

```text
controllers/
└── hello.controller.js
```

Put:

```js
export const hello = (req, res) => {
    res.json({
        success: true,
        message: "Hello from controller"
    });
};
```

Notice something important.

The controller doesn't know anything about:

```text
MongoDB
JWT
bcrypt
Docker
React
```

It simply handles the HTTP request and creates the response.

---

# 6. Connect it to a route

Now create:

```text
routes/
└── hello.routes.js
```

```js
import express from "express";
import { hello } from "../controllers/hello.controller.js";

const router = express.Router();

router.get("/hello", hello);

export default router;
```

Then your application might have:

```js
app.use("/api/v1", helloRoutes);
```

The complete flow becomes:

```text
GET /api/v1/hello
        │
        ▼
hello.routes.js
        │
        ▼
hello controller
        │
        ▼
res.json(...)
        │
        ▼
Frontend
```

---

# 7. What exactly did the controller do?

The client sent:

```http
GET /api/v1/hello
```

The route determined:

> "This request should go to `hello`."

Then:

```js
hello
```

was executed.

The controller returned:

```json
{
    "success": true,
    "message": "Hello from controller"
}
```

That's it.

---

# 8. Why not put this directly inside the route?

You could technically write:

```js
router.get("/hello", (req, res) => {
    res.json({
        success: true,
        message: "Hello"
    });
});
```

And for a tiny application, this works.

But imagine your application grows.

You might eventually have:

```text
50 routes
100 routes
200 routes
```

If every route contains application logic, your route files become huge.

Instead:

```js
router.get("/hello", hello);
```

is much cleaner.

The route answers:

> **Which function handles this request?**

The controller answers:

> **What HTTP response should this request produce?**

# 10. Controller's main responsibilities

A controller generally handles things related to **HTTP**.

For example:

### Reading request information

```js
req.body
req.params
req.query
req.user
```

### Calling application logic

Later:

```js
const user = await userService.getUser(userId);
```

### Choosing the HTTP status

```js
res.status(200)
```

### Sending the response

```js
res.json(...)
```

So:

```text
Controller
=
HTTP boundary
```

This is a very useful mental model.

---

# 11. What should a controller NOT do?

This is where things become important.

Suppose you're creating a user.

A beginner might write:

```js
export const createUser = async (req, res) => {

    const { email, password } = req.body;

    const existingUser = await User.findOne({ email });

    if (existingUser) {
        return res.status(409).json({
            message: "User already exists"
        });
    }

    const hashedPassword = await bcrypt.hash(password, 12);

    const user = await User.create({
        email,
        password: hashedPassword
    });

    const token = jwt.sign(
        { userId: user._id },
        process.env.JWT_SECRET
    );

    res.status(201).json({
        user,
        token
    });
};
```

It works.

But look at how much responsibility the controller has:

```text
HTTP
 +
database
 +
business rules
 +
password hashing
 +
JWT
```

That's a **fat controller**.

We'll learn how to fix this later.

---

# 12. The controller should become thin

Eventually:

```js
export const createUser = asyncHandler(async (req, res) => {

    const user = await userService.createUser(req.body);

    res.status(201).json({
        success: true,
        data: user
    });
});
```

Much cleaner.

The controller handles:

```text
HTTP request
     ↓
service call
     ↓
HTTP response
```

The Service will handle the business logic.

We'll study that deeply in Phase 12.

---

# 13. Controller vs Route

This distinction is important.

### Route

Answers:

> **Where does this request go?**

Example:

```js
router.post("/users", createUser);
```

### Controller

Answers:

> **What should happen when this request arrives?**

Example:

```js
export const createUser = async (req, res) => {
    // handle request
};
```

So:

```text
Route
    ↓
maps URL → controller
```

while:

```text
Controller
    ↓
handles HTTP operation
```

---

# 14. Controller vs Middleware

You already learned middleware.

Middleware:

```text
Can this request continue?
```

Controller:

```text
What should this request do?
```

For example:

```text
POST /todos
      │
      ▼
authMiddleware
      │
      │ Is user authenticated?
      │
      ▼
validationMiddleware
      │
      │ Is input valid?
      │
      ▼
createTodoController
      │
      │ Create todo
      ▼
response
```

This distinction is extremely important.

Whenever you're confused, use this:

```text
ROUTE
"Where?"

MIDDLEWARE

"What business decision?"

REPOSITORY
"How do I access data?"

MODEL
"What does the data look like?"
```

We'll build the remaining pieces in the upcoming phases.

# 16. Why controllers are useful

Imagine you have:

```text
POST /users
GET /users
GET /users/:id
PATCH /users/:id
DELETE /users/:id
```

You can organize them as:

```text
controllers/
└── user.controller.js
```

```js
export const createUser = ...
export const getUsers = ...
export const getUser = ...
export const updateUser = ...
export const deleteUser = ...
```

And routes:

```text
routes/
└── user.routes.js
```

```js
router.post("/", createUser);
router.get("/", getUsers);
router.get("/:id", getUser);
router.patch("/:id", updateUser);
router.delete("/:id", deleteUser);
```

This creates a clean relationship:

```text
user.routes.js
       │
       ├── createUser
       ├── getUsers
       ├── getUser
       ├── updateUser
       └── deleteUser
              │
              ▼
       user.controller.js
```
