# Lesson 11.10 — Sending HTTP Responses

Now we move to the **second half of the Controller's job**.

So far, we've learned how a Controller **reads the incoming request**:

```text
req.params
req.query
req.body
req.user
```

Now we need to learn how it **sends the result back to the client**.

The basic idea is:

```text
HTTP Request
     ↓
Controller
     ↓
Service
     ↓
Controller
     ↓
HTTP Response
```

---

# 1. The `res` object

Express gives every Controller two important objects:

```js
(req, res)
```

We've already spent several lessons learning `req`.

Now we're focusing on:

```js
res
```

`res` means:

> **Response**

It gives your Controller methods for sending something back to the client.

For example:

```js
res.json(...)
```

or:

```js
res.status(...)
```

---

# 2. The simplest response

You can send text:

```js
export const hello = (req, res) => {
    return res.send("Hello World");
};
```

Request:

```http
GET /hello
```

Response:

```text
Hello World
```

The browser, React application, Postman, or another API client receives that response.

---

# 3. Sending JSON

For APIs, you'll normally use:

```js
res.json(...)
```

Example:

```js
export const getUser = (req, res) => {
    return res.json({
        name: "Rahul",
        role: "student"
    });
};
```

Response:

```json
{
    "name": "Rahul",
    "role": "student"
}
```

This is one of the most common things you'll write in Controllers.

---

# 4. Why `return res.json()`?

You'll often see:

```js
return res.json({
    success: true
});
```

rather than:

```js
res.json({
    success: true
});
```

Both can work.

The `return` is useful because it immediately exits the Controller function.

For example:

```js
if (!user) {
    return res.status(404).json({
        success: false,
        message: "User not found"
    });
}
```

Once the response is sent, you don't want the function to continue executing.

---

# 5. Setting the HTTP status code

Every HTTP response has a status code.

For example:

```text
200
201
400
401
403
404
500
```

You can set the status with:

```js
res.status(200)
```

Then send JSON:

```js
res.status(200).json({
    success: true
});
```

---

# 6. `200 OK`

`200` generally means:

> The request succeeded.

Example:

```js
export const getProfile = async (req, res) => {
    const profile = await userService.getProfile(req.user.id);

    return res.status(200).json({
        success: true,
        data: profile
    });
};
```

Response:

```http
200 OK
```

with:

```json
{
    "success": true,
    "data": {
        "id": "123",
        "name": "Rahul"
    }
}
```

---

# 7. You don't always have to write `200`

This:

```js
return res.status(200).json({
    success: true
});
```

and:

```js
return res.json({
    success: true
});
```

will normally produce a successful `200` response.

So why explicitly write:

```js
.status(200)
```

?

Because it makes the intended HTTP status obvious.

In a structured backend codebase, explicit status codes can make Controllers easier to read.

---

# 8. `201 Created`

When you successfully create a resource, `201` is commonly used.

For example:

```http
POST /api/v1/todos
```

Controller:

```js
export const createTodo = async (req, res) => {
    const { title } = req.body;

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

Response:

```http
201 Created
```

This tells the client:

> A new resource was successfully created.

---

# 9. `204 No Content`

Sometimes an operation succeeds but you don't need to return a response body.

For example:

```http
DELETE /api/v1/todos/123
```

You could return:

```js
return res.status(204).send();
```

This means:

```text
Operation successful
+
No response body
```

You don't normally send JSON with a `204`.

Avoid:

```js
res.status(204).json({
    success: true
});
```

A `204` response is specifically intended to have no content.

---

# 10. `400 Bad Request`

`400` generally means:

> The client sent an invalid request.

For example, suppose an API requires:

```json
{
    "title": "Learn Node"
}
```

but receives:

```json
{
    "title": ""
}
```

If your validation layer rejects it, the response might be:

```js
return res.status(400).json({
    success: false,
    message: "Invalid request"
});
```

However, in your architecture, validation errors may eventually be handled by your validation/error middleware rather than manually inside every Controller.

That's better because it keeps Controllers small.

---

# 11. `401 Unauthorized`

Despite the confusing name, `401` is generally used when authentication is missing or invalid.

For example:

```http
GET /api/v1/profile
Authorization: Bearer invalid-token
```

The authentication middleware may return:

```js
return res.status(401).json({
    success: false,
    message: "Authentication required"
});
```

This usually happens **before the Controller**.

Remember:

```text
Request
   ↓
Authentication
   ↓
401 if authentication fails
   ↓
Controller only runs if authentication succeeds
```

---

# 12. `403 Forbidden`

`403` is generally used when:

> The user is authenticated, but doesn't have permission.

For example:

```text
User:
role = student

Endpoint:
DELETE /api/v1/users/123

Required:
admin
```

Authorization middleware could return:

```js
return res.status(403).json({
    success: false,
    message: "Access denied"
});
```

Difference:

```text
401
↓
Who are you?
Authentication failed/missing.

403
↓
I know who you are,
but you're not allowed.
```

---

# 13. `404 Not Found`

Suppose:

```http
GET /api/v1/todos/999
```

and Todo `999` doesn't exist.

The Service might determine:

```text
Todo doesn't exist
```

and your error-handling architecture can eventually turn that into:

```http
404 Not Found
```

A simple Controller might look like:

```js
if (!todo) {
    return res.status(404).json({
        success: false,
        message: "Todo not found"
    });
}
```

But as your project grows, you'll want centralized error handling rather than repeating this everywhere.

---

# 14. `500 Internal Server Error`

`500` generally means:

> Something unexpected went wrong on the server.

For example:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Database error
```

Ideally, your Controller should **not** manually write:

```js
res.status(500)
```

for every unexpected exception.

That's one of the reasons you already studied **Phase 8 — Error Handling**.

Instead:

```text
Unexpected error
       ↓
throw error
       ↓
async error wrapper
       ↓
global error middleware
       ↓
500 response
```

This keeps Controllers cleaner.

---

# 15. The basic response pattern

For a successful API operation:

```js
return res.status(200).json({
    success: true,
    data: result
});
```

For creation:

```js
return res.status(201).json({
    success: true,
    data: result
});
```

For no content:

```js
return res.status(204).send();
```

This pattern will become very familiar.

---

# 16. A consistent API response

Instead of randomly returning:

```json
{
    "name": "Rahul"
}
```

from one endpoint and:

```json
{
    "user": {
        "name": "Rahul"
    }
}
```

from another, your API can establish a consistent structure.

For example:

```json
{
    "success": true,
    "data": {
        "name": "Rahul"
    }
}
```

Then another endpoint:

```json
{
    "success": true,
    "data": [
        {
            "id": "1"
        },
        {
            "id": "2"
        }
    ]
}
```

The frontend can learn:

```text
success
   ↓
Was it successful?

data
   ↓
Where is the result?
```

---

# 17. Response messages

You may also see:

```json
{
    "success": true,
    "message": "Todo created successfully",
    "data": {
        "id": "123"
    }
}
```

This can be useful.

But don't add messages everywhere just because you can.

For example, this:

```json
{
    "success": true,
    "message": "The request to retrieve the todos was successfully processed",
    "data": []
}
```

is unnecessary.

Keep API responses useful and predictable.

---

# 18. Success response example

A good simple response:

```js
return res.status(200).json({
    success: true,
    data: user
});
```

Creation:

```js
return res.status(201).json({
    success: true,
    data: todo
});
```

Deletion:

```js
return res.status(204).send();
```

---

# 19. Error response example

A simple error response:

```js
return res.status(404).json({
    success: false,
    message: "Todo not found"
});
```

Another:

```js
return res.status(403).json({
    success: false,
    message: "You do not have permission to perform this action"
});
```

The important thing is consistency.

---

# 20. `res.send()`

`res.send()` can send different kinds of data.

For example:

```js
return res.send("Hello");
```

or:

```js
return res.send({
    success: true
});
```

For a JSON API, though, prefer:

```js
res.json(...)
```

when your intention is specifically to return JSON.

---

# 21. `res.json()` vs `res.send()`

Think of it this way:

```text
res.json()
   ↓
"I am intentionally returning JSON."

res.send()
   ↓
"I am sending this response body."
```

For your MERN backend APIs, you'll probably use:

```js
res.json()
```

much more frequently.

---

# 22. `res.end()`

You may also see:

```js
res.end();
```

This ends the response without sending a response body.

For example:

```js
return res.status(204).end();
```

It's useful, but for most of your API code:

```js
res.status(204).send();
```

is easier to understand.

You don't need to use `res.end()` frequently at this stage.

---

# 23. Don't send two responses

This is a very common Express mistake.

Bad:

```js
if (!user) {
    res.status(404).json({
        message: "User not found"
    });
}

return res.status(200).json({
    data: user
});
```

If `user` doesn't exist, you've already sent:

```text
404
```

Then the Controller tries to send:

```text
200
```

again.

This can lead to:

```text
Error: Cannot set headers after they are sent to the client
```

---

# 24. Use `return`

Correct:

```js
if (!user) {
    return res.status(404).json({
        success: false,
        message: "User not found"
    });
}

return res.status(200).json({
    success: true,
    data: user
});
```

The `return` prevents the function from continuing.

This is one of the simplest and most useful Controller habits.

---

# 25. Don't mix response and business logic

Avoid:

```js
export const createTodo = async (req, res) => {
    const { title } = req.body;

    if (!title) {
        return res.status(400).json({
            message: "Title required"
        });
    }

    const existingTodo = await Todo.findOne({
        title
    });

    if (existingTodo) {
        return res.status(409).json({
            message: "Todo already exists"
        });
    }

    const todo = await Todo.create({
        title,
        userId: req.user.id
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

This Controller is doing too much.

It contains:

```text
HTTP
validation
business logic
database access
response
```

Instead:

```js
export const createTodo = async (req, res) => {
    const { title } = req.body;
    const { id: userId } = req.user;

    const todo = await todoService.createTodo({
        title,
        userId
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

Much cleaner.

---

# 26. Controller as a translator

This is probably the most important idea of today's lesson.

A Controller translates:

```text
HTTP Request
      ↓
Application Input
```

and then:

```text
Application Result
      ↓
HTTP Response
```

So:

```text
             CONTROLLER

HTTP Request ──────────────→ Service
     ↑                         │
     │                         │
     └──── HTTP Response ──────┘
```

For example:

```js
const { id } = req.user;
const { todoId } = req.params;

const todo = await todoService.getTodo({
    todoId,
    userId: id
});

return res.status(200).json({
    success: true,
    data: todo
});
```

The Controller isn't deciding **how** the Todo is retrieved.

It is translating between two worlds:

```text
Express/HTTP
      ↕
Application
```

---

# 27. Response after Service call

A very common pattern:

```js
export const getTodo = async (req, res) => {
    const { id } = req.params;

    const todo = await todoService.getTodo(id);

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

The steps are:

```text
1. Read request
      ↓
2. Call Service
      ↓
3. Receive result
      ↓
4. Choose HTTP status
      ↓
5. Send response
```

That's basically the core Controller workflow.

# 30. Delete example

A delete endpoint might be:

```js
export const deleteTodo = async (req, res) => {
    const { id: todoId } = req.params;
```

---

# 31. `res.status()` does not send the response

This is important.

This:

```js
res.status(200);
```

only sets the status.

It does **not** finish the response.

You generally follow it with:

```js
res.json(...)
```

For example:

```js
res.status(200).json({
    success: true
});
```

Think:

```text
res.status()
     ↓
set HTTP status

res.json()
     ↓
send body
```

---

# 32. Method chaining

Express allows:

```js
res
    .status(200)
    .json({
        success: true
    });
```

This is the same idea as:

```js
res.status(200).json({
    success: true
});
```

You'll probably use the second style more often because it's compact.

# 33. Choosing status codes

A useful starting table:

|Situation|Status|
|---|--:|
|Successful GET|`200`|
|Successful update|`200`|
|Successful creation|`201`|
|Successful deletion with no body|`204`|
|Invalid request|`400`|
|Not authenticated|`401`|
|Not authorized|`403`|
|Resource doesn't exist|`404`|
|Unexpected server error|`500`|

Don't try to memorize every HTTP status code.

Learn the common ones first.

# 34. RESTful CRUD mapping

For your MERN backend, a common pattern is:

```text
POST
  ↓
Create
  ↓
201

GET
  ↓
Read
  ↓
200

PATCH/PUT
  ↓
Update
  ↓
200

DELETE
  ↓
Delete
  ↓
204
```

For example:

```text
POST   /todos
GET    /todos
GET    /todos/:id
PATCH  /todos/:id
DELETE /todos/:id
```

And:

```text
POST   → 201
GET    → 200
GET    → 200
PATCH  → 200
DELETE → 204
```

This isn't an absolute rule, but it's a very good starting convention.

# 35. Response consistency

Imagine your React frontend calls:

```text
GET /todos
```

and receives:

```json
{
    "success": true,
    "data": [...]
}
```

Then:

```text
GET /users
```

returns:

```json
{
    "users": [...]
}
```

Then:

```text
GET /courses
```

returns:

```json
{
    "result": [...]
}
```

This makes frontend code unnecessarily confusing.

Instead, establish conventions.

For example:

```json
{
    "success": true,
    "data": [...]
}
```

for successful responses.

And:

```json
{
    "success": false,
    "message": "Something went wrong"
}
```

for errors.

Later, you can centralize this even further with response helpers.

# 36. Pagination response

For a paginated endpoint:

```js
return res.status(200).json({
    success: true,
    data: result.items,
    pagination: result.pagination
});
```

Response:

```json
{
    "success": true,
    "data": [
        {
            "id": "1",
            "title": "Learn Node"
        }
    ],
    "pagination": {
        "page": 2,
        "limit": 10,
        "total": 51,
        "totalPages": 6
    }
}
```

This is much more useful than returning only:

```json
[
    {
        "id": "1"
    }
]
```

because the frontend needs to know how pagination works.

# 37. Don't leak database objects blindly

Suppose MongoDB returns:

```js
{
    _id: "...",
    name: "Rahul",
    passwordHash: "...",
    refreshToken: "..."
}
```

Don't simply do:

```js
return res.json({
    data: user
});
```

if that object contains sensitive fields.

Instead, your Service/mapper/serializer layer should produce a safe representation.

For example:

```js
{
    id: user._id,
    name: user.name
}
```

Then:

```js
return res.status(200).json({
    success: true,
    data: safeUser
});
```

This becomes particularly important in production APIs.

---

# 38. Response shape vs HTTP status

Don't confuse these two:

```text
HTTP status
    ↓
200 / 201 / 404 / 500

JSON body
    ↓
{
    success: true,
    data: ...
}
```

They serve different purposes.

For example:

```http
HTTP/1.1 200 OK
```

and:

```json
{
    "success": true,
    "data": {}
}
```

The HTTP status communicates at the protocol level.

The JSON body communicates application-level information.

# 39. What about errors?

Your Controller doesn't need to manually handle every possible error.

For example:

```js
export const getTodo = async (req, res) => {
    const { id } = req.params;

    const todo = await todoService.getTodo(id);

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

Suppose:

```text
todoService.getTodo()
        ↓
Database error
        ↓
throws error
```

Your error-handling system can catch it.

That's why your previous Phase 8 knowledge matters.

The architecture becomes:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Error thrown
    ↓
Error middleware
    ↓
500 response
```

Instead of:

```text
Every Controller
    ↓
try/catch everything
    ↓
repeat error responses
```

# 40. A clean Controller

At this stage, a good Controller should start looking boring.

And that's a **good thing**.

For example:

```js
export const getTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;
    const { id: userId } = req.user;

    const todo = await todoService.getTodo({
        todoId,
        userId
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

Look at how little it does:

```text
1. Read request
2. Call Service
3. Send response
```

That's exactly what we want.

# 41. The Controller shouldn't decide everything

A beginner might think:

```text
Controller = entire backend logic
```

But our architecture is:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

Each layer has a job.

### Route

```text
Which endpoint?
```

### Middleware

```text
Authentication?
Validation?
Authorization?
```

### Controller

```text
Translate HTTP ↔ application
```

### Service

```text
Business/application logic
```

### Repository

```text
Database access
```

This separation is the foundation of the backend starter architecture you're building.

```js
};
```

### PATCH

```js
export const updateTodo = async (req, res) => {
    const { id: todoId } = req.params;
    const { title } = req.body;

    const todo = await todoService.updateTodo({
        todoId,
        userId: req.user.id,
        title
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

### DELETE

```js
export const deleteTodo = async (req, res) => {
    const { id: todoId } = req.params;

    await todoService.deleteTodo({
        todoId,
        userId: req.user.id
    });

    return res.status(204).send();
};
```

These four patterns will become your everyday tools.

# 🧠 Final Mental Model

Think about every Controller as having **two sides**:

```text
             CONTROLLER
                 │
        ┌────────┴────────┐
        │                 │
        ▼                 ▼
   READ REQUEST       SEND RESPONSE
        │                 │
        │                 │
   req.params          res.status()
   req.query           res.json()
   req.body            res.send()
   req.user            res.end()
        │                 │
        └───────┬─────────┘
                │
                ▼
             SERVICE
```

So the Controller's job is essentially:

> **Take HTTP input → give clean input to the Service → take the Service result → turn it into an HTTP response.**

That's the core Controller responsibility.

## 🔥 What you should remember from 11.10

```text
res.status(200)
    ↓
Set HTTP status

res.json(data)
    ↓
Send JSON

res.send(data)
    ↓
Send response body

res.status(204).send()
    ↓
Successful response with no body
```

Common statuses:

```text
200 → Success
201 → Created
204 → Success, no content
400 → Bad request
401 → Authentication required/failed
403 → Permission denied
404 → Resource not found
500 → Unexpected server error
```

And one very important habit:

```js
return res.status(...).json(...);
```

because it prevents the Controller from accidentally continuing after sending a response.
