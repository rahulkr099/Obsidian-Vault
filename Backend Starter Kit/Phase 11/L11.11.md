# Lesson 11.11 — HTTP Status Codes

Before moving to Controller error handling, we need to correct one small point from the previous lesson.

In the original Phase 11 roadmap, **11.11 is HTTP Status Codes**, followed by **11.12 Controller Error Handling**.

So today we'll properly learn **HTTP status codes** and how they fit into Controllers.

---

## 1. What is an HTTP status code?

Whenever your backend responds to a request, it sends a status code.

For example:

```http
HTTP/1.1 200 OK
```

The `200` tells the client what happened with the request.

Think of it as a short answer from your server:

```text
200 → "Everything worked."
201 → "I created something."
400 → "Your request is invalid."
401 → "You aren't authenticated."
403 → "You're authenticated, but not allowed."
404 → "I couldn't find it."
500 → "Something went wrong on my server."
```

---

# 2. Why status codes matter

Imagine your React frontend sends:

```http
POST /api/v1/todos
```

The server returns:

```json
{
    "success": false,
    "message": "Title is required"
}
```

Without a status code, the frontend doesn't have a standard HTTP-level indication of what happened.

But:

```http
400 Bad Request
```

immediately tells the frontend:

> The request itself was invalid.

So your API communicates using **two levels**:

```text
HTTP status code
       +
JSON response body
```

For example:

```http
HTTP/1.1 201 Created
```

```json
{
    "success": true,
    "data": {
        "id": "123",
        "title": "Learn Controllers"
    }
}
```

---

# 3. The five status-code families

HTTP status codes are grouped by their first digit:

|Range|Meaning|
|---|---|
|`1xx`|Informational|
|`2xx`|Success|
|`3xx`|Redirection|
|`4xx`|Client/request error|
|`5xx`|Server error|

For your MERN backend, you'll mostly work with:

```text
2xx
4xx
5xx
```

You don't need to memorize every HTTP status code.

---

# 4. 2xx — Success

The `2xx` family means:

> The request was successfully processed.

The most important ones for you are:

```text
200 OK
201 Created
204 No Content
```

---

# 5. `200 OK`

`200` is the most common success status.

Use it when the requested operation succeeded and you're returning a response.

### GET

```js
export const getTodo = async (req, res) => {
    const todo = await todoService.getTodo(req.params.id);

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

Response:

```http
200 OK
```

---

# 6. GET usually uses 200

For:

```http
GET /api/v1/todos
```

you might return:

```http
200 OK
```

with:

```json
{
    "success": true,
    "data": [
        {
            "id": "1",
            "title": "Learn Node"
        }
    ]
}
```

For:

```http
GET /api/v1/todos/123
```

you can also return:

```http
200 OK
```

---

# 7. `201 Created`

Use `201` when the request successfully **creates a new resource**.

Example:

```http
POST /api/v1/todos
```

Controller:

```js
export const createTodo = async (req, res) => {
    const { title } = req.body;

    const todo = await todoService.createTodo({
        title,
        userId: req.user.id
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

Response:

```http
201 Created
```

Think:

```text
POST
 ↓
New resource created
 ↓
201
```

---

# 8. `204 No Content`

`204` means:

> The operation succeeded, but there is no response body.

A common example is DELETE:

```http
DELETE /api/v1/todos/123
```

Controller:

```js
export const deleteTodo = async (req, res) => {
    const { id: todoId } = req.params;

    await todoService.deleteTodo({
        todoId,
        userId: req.user.id
    });

    return res.status(204).send();
};
```

The response contains no JSON body.

Think:

```text
Delete succeeded
      ↓
Nothing else needs to be returned
      ↓
204
```

---

# 9. 2xx summary

Remember these three:

```text
200 → Successful operation
201 → Resource created
204 → Successful, no response body
```

That's enough for most of your CRUD work.

---

# 10. 4xx — Client/request errors

A `4xx` status generally means:

> The problem is with the request or the client's permissions/authentication.

The important ones:

```text
400
401
403
404
409
422
429
```

We'll focus on the common use cases.

---

# 11. `400 Bad Request`

Use `400` when the request is invalid.

For example:

```http
POST /api/v1/todos
```

Body:

```json
{}
```

but your API requires:

```json
{
    "title": "Learn Express"
}
```

You could return:

```http
400 Bad Request
```

with:

```json
{
    "success": false,
    "message": "Title is required"
}
```

---

# 12. Validation belongs at the boundary

In your architecture, validation should generally happen before the Controller's business operation.

The flow is:

```text
Request
   ↓
Validation middleware
   ↓
Valid?
   ├── No → 400
   │
   └── Yes
         ↓
      Controller
```

Your Phase 9 architecture is specifically designed around this boundary: validate and clean input before it reaches application logic.

So don't fill every Controller with:

```js
if (!email) ...
if (!password) ...
if (!name) ...
```

when your validation middleware can handle it.

---

# 13. `401 Unauthorized`

This one causes a lot of confusion.

`401` generally means:

> The request lacks valid authentication credentials.

For example:

```http
GET /api/v1/users/me
Authorization: Bearer invalid-token
```

Authentication middleware may return:

```js
return res.status(401).json({
    success: false,
    message: "Authentication required"
});
```

Flow:

```text
Request
   ↓
Authentication middleware
   ↓
Token invalid
   ↓
401
```

The Controller never needs to run.

---

# 14. `401` vs `403`

This distinction is extremely important.

### 401

```text
You haven't successfully authenticated.
```

### 403

```text
We know who you are,
but you're not allowed to do this.
```

Example:

```text
401
 ↓
No valid login/token
```

versus:

```text
403
 ↓
Logged in as "student"
 ↓
Trying to access admin-only endpoint
```

---

# 15. `403 Forbidden`

Suppose:

```http
DELETE /api/v1/users/123
```

The user is authenticated:

```js
req.user = {
    id: "456",
    role: "student"
};
```

But the endpoint requires:

```text
admin
```

Authorization middleware can return:

```js
return res.status(403).json({
    success: false,
    message: "Access denied"
});
```

Flow:

```text
Request
   ↓
Authentication
   ↓
Authenticated ✓
   ↓
Authorization
   ↓
Role = student
   ↓
Admin required
   ↓
403
```

---

# 16. `404 Not Found`

`404` means:

> The requested resource could not be found.

Example:

```http
GET /api/v1/todos/999
```

There is no Todo `999`.

Your application can eventually produce:

```http
404 Not Found
```

with:

```json
{
    "success": false,
    "message": "Todo not found"
}
```

---

# 17. 404 can also mean route doesn't exist

Suppose your API has:

```text
GET /api/v1/todos
```

but the client requests:

```text
GET /api/v1/abc
```

There may be no route matching it.

Your global 404 handler can respond with:

```http
404 Not Found
```

So `404` can occur at two different levels:

```text
Route doesn't exist
       ↓
404

Resource doesn't exist
       ↓
404
```

---

# 18. `409 Conflict`

`409` is useful when the request conflicts with the current state of the resource.

A common example:

```http
POST /api/v1/auth/signup
```

Body:

```json
{
    "email": "rahul@example.com",
    "password": "..."
}
```

Suppose that email already belongs to a user.

Your application could respond:

```http
409 Conflict
```

```json
{
    "success": false,
    "message": "Email already registered"
}
```

Think:

```text
Request itself may be structurally valid
        ↓
But it conflicts with existing state
        ↓
409
```

---

# 19. `422 Unprocessable Content`

You may encounter `422` in APIs.

It can be used when:

> The server understands the request, but cannot process the supplied content.

Different teams use `400` and `422` differently.

For your starter, **don't obsess over choosing between them yet**.

The important thing is to establish a consistent convention across your API.

For example, your project could decide:

```text
Malformed/invalid request → 400
Validation failure         → 400
```

and use that consistently.

Or:

```text
Malformed request          → 400
Semantically invalid data  → 422
```

The exact convention matters less than consistency.

---

# 20. `429 Too Many Requests`

This one is particularly important for your security middleware.

Suppose a user sends:

```text
100 login attempts
```

in a short period.

Your rate limiter can return:

```http
429 Too Many Requests
```

Example:

```json
{
    "success": false,
    "message": "Too many requests. Please try again later."
}
```

Flow:

```text
Request
   ↓
Rate limiter
   ↓
Limit exceeded
   ↓
429
```

This is why rate limiting is not just a random security package—it directly affects HTTP responses.

---

# 21. 5xx — Server errors

Now we reach:

```text
5xx
```

These generally mean:

> The server failed while processing an otherwise valid request.

The most important:

```text
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

For your backend application, `500` is the main one to understand initially.

---

# 22. `500 Internal Server Error`

Suppose:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
MongoDB
    ↓
Unexpected database failure
```

The application may eventually return:

```http
500 Internal Server Error
```

with a safe response such as:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

Notice something important:

You generally **don't want to expose**:

```text
Mongo connection details
stack traces
database credentials
internal file paths
secret keys
```

to the client.

That's part of the error-handling architecture you'll learn next.

---

# 23. Status code ≠ error message

Don't do this:

```text
200 OK
```

with:

```json
{
    "success": false,
    "message": "Something went wrong"
}
```

for a normal error.

Technically, APIs can do unusual things, but it creates unnecessary confusion.

Prefer:

```http
400 Bad Request
```

with:

```json
{
    "success": false,
    "message": "Invalid input"
}
```

or:

```http
404 Not Found
```

with:

```json
{
    "success": false,
    "message": "Todo not found"
}
```

The HTTP status should match the outcome.

---

# 24. Don't use `200` for every response

A common beginner API does:

```js
return res.status(200).json({
    success: false,
    message: "User not found"
});
```

Avoid this.

Instead:

```js
return res.status(404).json({
    success: false,
    message: "User not found"
});
```

Why?

Because clients, proxies, monitoring systems, API tools, and other infrastructure understand HTTP status codes.

---

# 25. Don't invent a custom status code

You might be tempted to write:

```js
res.status(999)
```

Don't.

HTTP defines standardized status codes.

Use an appropriate standard status.

---

# 26. CRUD status-code cheat sheet

For your MERN projects, this is a very useful starting point:

|Operation|Typical status|
|---|--:|
|Get one|`200`|
|Get many|`200`|
|Create|`201`|
|Update|`200`|
|Delete with body|`200`|
|Delete without body|`204`|
|Invalid input|`400`|
|Not authenticated|`401`|
|Not allowed|`403`|
|Resource missing|`404`|
|Duplicate/conflict|`409`|
|Rate limit exceeded|`429`|
|Unexpected server error|`500`|

You don't have to use these blindly. Context matters.

# 28. What happens when the resource doesn't exist?

Suppose:

```http
GET /todos/999
```

Service determines:

```text
Todo doesn't exist
```

Eventually:

```http
404 Not Found
```

The important architecture is:

```text
Controller
     ↓
Service
     ↓
"No Todo found"
     ↓
Error
     ↓
Error middleware
     ↓
404
```

This leads directly into **11.12 Controller Error Handling**.

---

# 29. Don't put every status code directly into every layer

A useful architectural rule:

### Repository

Usually shouldn't care about HTTP:

```js
repository.findTodo(...)
```

It shouldn't normally do:

```js
return res.status(404)
```

because the Repository isn't an HTTP layer.

### Service

Should generally work with application concepts/errors.

For example:

```text
TodoNotFoundError
```

rather than:

```text
res.status(404)
```

### Controller

Understands HTTP:

```js
res.status(200)
```

### Error middleware

Converts application errors into HTTP responses.

This separation is very important.

---

# 30. Why this architecture is better

Imagine your Service contains:

```js
return res.status(404).json(...)
```

Now the Service needs to know:

```text
Express
res
HTTP
JSON
status codes
```

That's bad coupling.

Instead:

```text
Repository
     ↓
Service
     ↓
throws application error
     ↓
Controller/error middleware
     ↓
HTTP 404
```

The lower layers don't need to know about Express.

---

# 31. Think in layers

Your backend should look like:

```text
                  HTTP
                   │
                   ▼
              Controller
                   │
             HTTP concepts
                   │
                   ▼
                Service
                   │
          Application concepts
                   │
                   ▼
              Repository
                   │
            Database concepts
                   │
                   ▼
                MongoDB
```

Status codes belong primarily at the **HTTP boundary**.

This is a very important architectural principle.

# 32. A realistic example

Suppose:

```http
GET /api/v1/users/me
```

Authentication middleware:

```text
No token
```

Response:

```http
401 Unauthorized
```

Authentication succeeds:

```text
req.user = { id: "123" }
```

Controller calls:

```js
userService.getProfile("123");
```

Service can't find user:

```text
UserNotFoundError
```

Error middleware converts it to:

```http
404 Not Found
```

Service succeeds:

```text
User object
```

Controller sends:

```http
200 OK
```

So one endpoint can naturally produce different status codes:

```text
GET /users/me

401 → authentication failed
404 → user not found
200 → successful
500 → unexpected server error
```

# 33. Status code decision tree

When you're unsure what status to use, think:

```text
Did the operation succeed?
       │
       ├── YES
       │    │
       │    ├── Created something?
       │    │      └── 201
       │    │
       │    ├── No response body?
       │    │      └── 204
       │    │
       │    └── Otherwise
       │           └── 200
       │
       └── NO
            │
            ├── Authentication problem?
            │      └── 401
            │
            ├── Permission problem?
            │      └── 403
            │
            ├── Resource missing?
            │      └── 404
            │
            ├── Request invalid?
            │      └── 400
            │
            ├── State conflict?
            │      └── 409
            │
            ├── Too many requests?
            │      └── 429
            │
            └── Unexpected server failure?
                   └── 500
```

This is much easier than memorizing a giant list.

# 34. A practical Controller

Here's a clean example:

```js
export const createTodo = asyncHandler(async (req, res) => {
    const { title } = req.body;
    const { id: userId } = req.user;

    const todo = await todoService.createTodo({
        title,
        userId
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
});
```

Notice:

```text
Validation
   ↓
Middleware

Authentication
   ↓
Middleware

Business logic
   ↓
Service

HTTP response
   ↓
Controller
```

That's the architecture we're aiming for.

# 35. Your starter's error architecture

Your uploaded starter roadmap explicitly describes the error flow as:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
      ↓
JSON response
```

This is important because **11.11 is the foundation for 11.12**.

You don't want:

```js
controller
   ↓
try/catch
   ↓
res.status(500)
```

everywhere.

Instead, you'll eventually have:

```text
Controller
   ↓
Service
   ↓
error thrown
   ↓
asyncHandler
   ↓
global error middleware
   ↓
correct HTTP status
```

# 37. One important distinction

Don't think:

```text
4xx = frontend's fault
5xx = backend developer's fault
```

It's more useful to think:

```text
4xx
↓
The request cannot be successfully fulfilled
because of the request/authentication/authorization/state.

5xx
↓
The server failed while processing the request.
```

This is a more practical mental model.

# 38. What you should memorize

Don't memorize 60 HTTP codes.

For your MERN backend, start with these:

```text
200 → OK
201 → Created
204 → No Content

400 → Bad Request
401 → Unauthenticated
403 → Forbidden
404 → Not Found
409 → Conflict
429 → Too Many Requests

500 → Internal Server Error
```

And remember:

```text
401 ≠ 403
```

This distinction will become extremely important when we build authentication and authorization.

# 🧠 Final Mental Model

When your Controller finishes successfully:

```text
Service result
     ↓
Controller
     ↓
Choose status
     ↓
Send JSON
```

Example:

```js
return res.status(200).json({
    success: true,
    data: result
});
```

When something goes wrong:

```text
Error
  ↓
Error architecture
  ↓
Choose appropriate HTTP status
  ↓
JSON error response
```

The key architectural rule is:

> **HTTP status codes belong to the HTTP boundary. Your Service and Repository should not become dependent on Express.**

Your starter's architecture follows this separation by routing controller errors through `asyncHandler` and the global error middleware.
