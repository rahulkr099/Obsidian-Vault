# Lesson 11.12 — Controller Error Handling

Now we are connecting **Phase 11 Controllers** with the **Phase 8 Error Handling architecture** you already studied.

Your starter specifically expects this flow:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
      ↓
JSON response
```

The goal is simple:

> **Controllers should focus on HTTP, not become giant `try/catch` blocks.**

---

# 1. The problem with normal async Controllers

Imagine this Controller:

```js
export const getUser = async (req, res) => {
    const user = await userService.getUser(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Looks great.

But what happens if:

```js
userService.getUser()
```

throws an error?

For example:

```text
MongoDB error
Database connection error
UserNotFoundError
Unexpected programming error
```

The error needs to reach Express's error-handling system.

---

# 2. The beginner solution: `try/catch`

You might write:

```js
export const getUser = async (req, res) => {
    try {
        const user = await userService.getUser(req.params.id);

        return res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        return res.status(500).json({
            success: false,
            message: "Something went wrong"
        });
    }
};
```

This works.

But imagine having **30 Controllers**.

You could end up with:

```js
try {
    ...
} catch (error) {
    ...
}
```

everywhere.

That's repetitive.

Worse, every Controller might handle errors differently.

---

# 3. The architecture we want

Your starter's architecture instead uses:

```text
Controller
     ↓
throws/rejects
     ↓
asyncHandler
     ↓
next(error)
     ↓
error.middleware
     ↓
HTTP response
```

This gives you one centralized place for error responses.

The Controller can remain small.

---

# 4. What does `asyncHandler` do?

Conceptually, `asyncHandler` is a wrapper around an asynchronous Controller.

It says:

> "Run this async function, and if it fails, pass the error to Express."

A simple version:

```js
export const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};
```

This tiny utility solves a big problem.

---

# 5. Understanding the important line

Look at:

```js
.catch(next);
```

You can think of it as:

```js
.catch((error) => {
    next(error);
});
```

So:

```js
.catch(next);
```

is basically shorthand for:

```js
.catch((error) => next(error));
```

---

# 6. What is `next(error)`?

You learned `next()` back in the middleware phase.

Normally:

```js
next();
```

means:

> Continue to the next middleware.

But:

```js
next(error);
```

means:

> Something went wrong. Send this error into Express's error-handling pipeline.

So:

```text
next()
   ↓
Continue normally

next(error)
   ↓
Enter error handling
```

This distinction is extremely important.

---

# 7. The complete flow

Suppose we have:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Now suppose:

```js
userService.getUser()
```

throws:

```js
throw new Error("Database failed");
```

The flow becomes:

```text
getUser Controller
       ↓
Service throws
       ↓
Promise rejects
       ↓
asyncHandler
       ↓
catch(error)
       ↓
next(error)
       ↓
Express error middleware
       ↓
JSON response
```

That's the architecture you should remember.

# 8. Why the Controller doesn't need `try/catch`

Instead of:

```js
export const getUser = async (req, res) => {
    try {
        const user = await userService.getUser(req.params.id);

        return res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        return res.status(500).json({
            success: false,
            message: "Something went wrong"
        });
    }
};
```

you write:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Much cleaner.

---

# 9. But where does the error response happen?

Not inside the Controller.

It happens in:

```text
middlewares/error.middleware.js
```

Your starter architecture explicitly includes:

```text
utils/AppError.js
utils/asyncHandler.js
middlewares/error.middleware.js
```

for this purpose.

So the responsibilities are separated:

```text
asyncHandler
    ↓
catches rejected async operations

AppError
    ↓
represents expected application errors

error.middleware
    ↓
converts errors into HTTP responses
```

---

# 10. Understanding `AppError`

Suppose a user doesn't exist.

This is not necessarily an unexpected programming error.

It's an expected application condition:

```text
User doesn't exist
```

You can represent that using a custom error:

```js
export class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;
    }
}
```

Then:

```js
throw new AppError("User not found", 404);
```

Now the error contains useful information:

```text
message
   ↓
User not found

statusCode
   ↓
404

isOperational
   ↓
true
```

---

# 11. Why not just use `Error`?

You could write:

```js
throw new Error("User not found");
```

But then the error doesn't naturally tell your HTTP layer:

```text
What status should I return?
```

With:

```js
throw new AppError("User not found", 404);
```

the error carries that information.

The architecture becomes:

```text
Service
   ↓
AppError("User not found", 404)
   ↓
error.middleware
   ↓
404 response
```

# 12. Example: User not found

Service:

```js
export const getUser = async (userId) => {
    const user = await userRepository.findById(userId);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    return user;
};
```

Controller:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Notice something beautiful:

The Controller doesn't need:

```js
if (!user) ...
```

The Service understands the application rule:

> A requested user must exist.

# 13. Error middleware

A basic Express error middleware looks like:

```js
export const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    return res.status(statusCode).json({
        success: false,
        message: err.message || "Internal server error"
    });
};
```

Notice the four arguments:

```js
(err, req, res, next)
```

That tells Express:

> This is an error-handling middleware.

---

# 14. Why four arguments?

Normal middleware:

```js
(req, res, next)
```

Error middleware:

```js
(err, req, res, next)
```

The first parameter is the error.

So:

```text
Normal middleware
(req, res, next)

Error middleware
(err, req, res, next)
```

Express uses this signature to identify error-handling middleware.

---

# 15. Where should error middleware be registered?

Usually near the end of your Express application:

```js
app.use(routes);

app.use(notFoundMiddleware);

app.use(errorMiddleware);
```

Think:

```text
Request
   ↓
Middleware
   ↓
Routes
   ↓
Controller
   ↓
Service
   ↓
Error?
   ↓
errorMiddleware
```

Your uploaded starter describes `app.js` as the place where Express is assembled, including routes, the 404 handler, and the error handler.

# 18. Expected vs unexpected errors

This distinction is important.

### Expected / operational error

Something the application knows can happen.

Examples:

```text
User not found
Email already exists
Invalid token
Permission denied
Resource already exists
```

These can have intentional HTTP statuses:

```text
404
409
401
403
```

---

### Unexpected/programming error

Something went wrong unexpectedly.

Examples:

```text
undefined variable
broken database connection
unexpected library failure
programming bug
```

These generally become:

```text
500 Internal Server Error
```

Your Phase 8 roadmap specifically separates **operational vs programming errors** and covers hiding sensitive errors in production.

---

# 19. Why this distinction matters

Imagine:

```js
throw new AppError("Email already registered", 409);
```

This is safe to show the user.

But suppose:

```js
ReferenceError: userRepositry is not defined
```

You probably don't want to send:

```json
{
    "message": "ReferenceError: userRepositry is not defined"
}
```

to your production client.

Instead:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

while the actual technical details go into your logs.

---

# 20. Never expose stack traces in production

Development:

```json
{
    "success": false,
    "message": "Something went wrong",
    "stack": "..."
}
```

can sometimes be useful for debugging.

Production:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

is much safer.

Your starter roadmap explicitly includes **hiding sensitive errors in production** as part of the error architecture.

---

# 21. Controller should not decide every error

Bad:

```js
export const getUser = async (req, res) => {
    try {
        const user = await userService.getUser(req.params.id);

        if (!user) {
            return res.status(404).json({
                success: false,
                message: "User not found"
            });
        }

        return res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        return res.status(500).json({
            success: false,
            message: "Something went wrong"
        });
    }
};
```

This Controller knows too much.

Better:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

The Service and error system handle the rest.

---

# 22. Don't catch and rethrow unnecessarily

Avoid this:

```js
export const getUser = asyncHandler(async (req, res) => {
    try {
        const user = await userService.getUser(req.params.id);

        return res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        throw error;
    }
});
```

This adds no value.

The `asyncHandler` already handles rejected Promises.

Just write:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

---

# 23. What if the Controller itself detects an error?

Sometimes the Controller may need to reject something related directly to HTTP input.

For example:

```js
if (!req.params.id) {
    throw new AppError("User ID is required", 400);
}
```

Then:

```text
Controller
   ↓
throw AppError
   ↓
asyncHandler
   ↓
error middleware
   ↓
400
```

However, if this is ordinary request validation, your **validation middleware** should normally handle it before the Controller.

That's the cleaner architecture.

---

# 24. Error handling vs validation

Remember:

```text
Validation
    ↓
"Is this input acceptable?"
```

Error handling:

```text
Error handling
    ↓
"What should happen when something fails?"
```

For example:

```text
POST /users

Body:
{
    "email": "hello"
}
```

Validation might say:

```text
Invalid email
↓
400
```

But:

```text
MongoDB suddenly unavailable
```

is not a validation problem.

That's:

```text
Unexpected server/database error
↓
500
```

---

# 25. Error handling vs authentication

Similarly:

```text
Invalid/expired JWT
```

is an authentication problem:

```text
401
```

while:

```text
Database crashes while loading user
```

is a server error:

```text
500
```

The error architecture helps route each error to the correct response.

---

# 26. Error handling vs authorization

Suppose:

```text
User is authenticated
Role = user
Endpoint requires admin
```

That's:

```text
403 Forbidden
```

Not:

```text
500
```

And not:

```text
401
```

Again, the important thing is understanding what actually happened.


# 32. Your mental model for `asyncHandler`

Don't think of `asyncHandler` as magic.

Think:

> **It is a bridge between Promise errors and Express's `next(error)` system.**

Conceptually:

```text
async function
     ↓
Promise
     ↓
rejected Promise
     ↓
.catch(next)
     ↓
Express error middleware
```

That's all it is.

---

# 33. Your mental model for `AppError`

Don't think:

> "AppError is some special Express thing."

It's simply a custom JavaScript error that carries extra application information.

For example:

```js
new AppError(
    "Todo not found",
    404
);
```

means:

```text
Error message
+
HTTP/application status
+
possibly other metadata
```

The HTTP layer can then use that information.

---

# 34. Your mental model for `error.middleware`

Think:

> **The final translator from errors → HTTP responses.**

Normal path:

```text
Application result
       ↓
Controller
       ↓
HTTP response
```

Error path:

```text
Application error
       ↓
Error middleware
       ↓
HTTP error response
```

So Controllers translate normal application results into HTTP, while the error middleware translates failures into HTTP.

# 35. The complete pattern

Your Controller should eventually look like this:

```js
import { asyncHandler } from "../utils/asyncHandler.js";
import { userService } from "../services/user.service.js";

export const getUser = asyncHandler(async (req, res) => {
    const { id } = req.params;

    const user = await userService.getUser(id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Notice how clean it is.

The Controller has only three jobs:

```text
1. Read HTTP input
2. Call application logic
3. Send HTTP response
```

If something fails:

```text
asyncHandler
    ↓
error.middleware
```

handles it.
