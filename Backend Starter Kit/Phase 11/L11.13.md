# Lesson 11.13 — Controller Naming Conventions

Now that we understand **what a Controller does** and **how it handles errors**, we need to learn how to name Controllers properly.

This may look like a small topic, but in a real backend project it becomes very important.

When you have:

```text
10 Controllers
20 Controllers
50 Controllers
100+ Controllers
```

good naming makes the project easy to understand.

---

# 1. Why naming matters

Imagine opening a backend project and seeing:

```text
controllers/
├── controller1.js
├── controller2.js
├── test.js
├── userStuff.js
├── todoFunctions.js
├── auth.js
└── finalController.js
```

You have no idea what belongs where.

Now compare:

```text
controllers/
├── auth.controller.js
├── user.controller.js
├── todo.controller.js
├── course.controller.js
└── payment.controller.js
```

Immediately you understand the project.

That's the goal.

> **A good name should tell you what the file is responsible for without opening it.**

---

# 2. The basic Controller filename

A very common convention is:

```text
<resource>.controller.js
```

Examples:

```text
user.controller.js
todo.controller.js
auth.controller.js
course.controller.js
product.controller.js
order.controller.js
```

So:

```text
todo.controller.js
```

contains Controller functions related to Todos.

---

# 3. Why `.controller.js`?

You could name a file:

```text
todo.js
```

But this becomes confusing when your project has:

```text
models/todo.js
services/todo.js
repositories/todo.js
routes/todo.js
controllers/todo.js
```

Instead:

```text
todo.model.js
todo.service.js
todo.repository.js
todo.route.js
todo.controller.js
```

Now the role of each file is immediately visible.

---

# 4. Think in resource + layer

Your backend architecture can use the same naming idea across layers:

```text
Todo

todo.model.js
todo.repository.js
todo.service.js
todo.controller.js
todo.route.js
```

You can visually see:

```text
todo
  │
  ├── model
  ├── repository
  ├── service
  ├── controller
  └── route
```

This becomes extremely useful as your project grows.

---

# 5. Controller functions should describe actions

Inside:

```text
todo.controller.js
```

you might have:

```js
export const createTodo = ...
export const getTodos = ...
export const getTodo = ...
export const updateTodo = ...
export const deleteTodo = ...
```

These names are clear.

You can understand what each function does immediately.

---

# 6. Avoid vague names

Don't write:

```js
export const todo = ...
```

What does `todo` mean?

Is it:

```text
create?
read?
update?
delete?
```

Instead:

```js
createTodo
getTodo
updateTodo
deleteTodo
```

The action is visible.

---

# 7. CRUD naming convention

For CRUD Controllers, a very useful pattern is:

```text
create<Resource>
get<Resource>
get<Resources>
update<Resource>
delete<Resource>
```

For Todo:

```js
createTodo
getTodo
getTodos
updateTodo
deleteTodo
```

For User:

```js
createUser
getUser
getUsers
updateUser
deleteUser
```

For Product:

```js
createProduct
getProduct
getProducts
updateProduct
deleteProduct
```

It's simple and predictable.

---

# 8. Singular vs plural

This small distinction is important.

### One resource

```js
getTodo
```

means:

```text
Get one Todo
```

### Multiple resources

```js
getTodos
```

means:

```text
Get multiple Todos
```

For example:

```http
GET /api/v1/todos
```

would usually call:

```js
getTodos
```

while:

```http
GET /api/v1/todos/:id
```

would usually call:

```js
getTodo
```

---

# 9. Example

```js
export const getTodos = asyncHandler(async (req, res) => {
    const todos = await todoService.getTodos();

    return res.status(200).json({
        success: true,
        data: todos
    });
});
```

Versus:

```js
export const getTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.getTodo(req.params.id);

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

The naming communicates the difference.

---

# 10. Don't use HTTP verbs in function names unnecessarily

You might see:

```js
postTodo
getTodo
putTodo
deleteTodo
```

This isn't terrible, but it's usually less descriptive.

Prefer:

```js
createTodo
getTodo
updateTodo
deleteTodo
```

Why?

Because the function describes the **application action**, not merely the HTTP method.

For example:

```text
POST
```

doesn't always mean exactly the same business operation.

But:

```text
createTodo
```

is explicit.

---

# 11. HTTP method belongs to the route

The route already tells us the HTTP method:

```js
router.post("/", createTodo);
```

So we don't need:

```js
postTodo
```

The route says:

```text
POST
```

and the Controller says:

```text
createTodo
```

Together:

```text
POST /todos
      ↓
createTodo
```

Very readable.

---

# 12. Authentication Controller naming

Authentication is slightly different because it's not always simple CRUD.

Inside:

```text
auth.controller.js
```

you might have:

```js
register
login
logout
refreshToken
forgotPassword
resetPassword
verifyEmail
```

These are much clearer than:

```js
auth1
auth2
auth3
```

or:

```js
handleLogin
handleRegister
```

unless your project has a specific naming convention.

---

# 13. Example `auth.controller.js`

```js
export const register = asyncHandler(async (req, res) => {
    const user = await authService.register(req.body);

    return res.status(201).json({
        success: true,
        data: user
    });
});
```

```js
export const login = asyncHandler(async (req, res) => {
    const result = await authService.login(req.body);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

```js
export const logout = asyncHandler(async (req, res) => {
    await authService.logout(req.user.id);

    return res.status(204).send();
});
```

The names are directly connected to the use cases.

---

# 14. User Controller

A typical:

```text
user.controller.js
```

could contain:

```js
createUser
getUser
getUsers
updateUser
deleteUser
getProfile
updateProfile
```

Notice that:

```text
getProfile
```

is not necessarily:

```text
getUser
```

because they represent different API use cases.

---

# 15. Don't force everything into CRUD

This is important.

Real applications aren't only:

```text
Create
Read
Update
Delete
```

You might have:

```text
publishCourse
approveOrder
cancelOrder
completePayment
verifyEmail
refreshToken
sendInvitation
resetPassword
```

Don't try to force these into weird CRUD names.

For example, don't call:

```js
updateOrder
```

if the actual business action is:

```js
cancelOrder
```

The business action is much clearer.

---

# 16. Naming should describe intent

Compare:

```js
updateOrder()
```

with:

```js
cancelOrder()
```

If the operation means:

```text
Change status from "pending" to "cancelled"
```

then:

```js
cancelOrder()
```

communicates the intention much better.

The Controller name should help another developer understand:

> What does this endpoint actually do?

---

# 17. Resource-specific naming

Suppose your application has:

```text
courses
```

You might have:

```js
createCourse
getCourse
getCourses
updateCourse
deleteCourse
publishCourse
unpublishCourse
```

Notice:

```text
CRUD operations
+
domain-specific actions
```

That's perfectly normal.

---

# 18. Controller filename and function names work together

Suppose we have:

```text
controllers/
└── course.controller.js
```

Inside:

```js
createCourse
getCourse
getCourses
updateCourse
deleteCourse
publishCourse
```

Now when you see:

```js
router.patch("/:id/publish", publishCourse);
```

everything is immediately understandable:

```text
PATCH /courses/:id/publish
                 ↓
          publishCourse
                 ↓
     course.controller.js
```

This is good naming.

---

# 19. Avoid generic `handle...` names everywhere

You might see:

```js
handleCreateTodo
handleGetTodo
handleDeleteTodo
```

This isn't wrong.

But in a backend Controller layer, it's often unnecessary.

Prefer:

```js
createTodo
getTodo
deleteTodo
```

The fact that the function handles an HTTP request is already obvious from its location.

---

# 20. Avoid unnecessary abbreviations

Don't write:

```js
crtTodo
getTds
updTodo
delTodo
```

Even though they're shorter, they're harder to read.

Prefer:

```js
createTodo
getTodos
updateTodo
deleteTodo
```

Code is read much more often than it is typed.

---

# 21. File names should also be predictable

Prefer:

```text
user.controller.js
todo.controller.js
course.controller.js
order.controller.js
```

Avoid:

```text
usersController.js
TodoController.js
todoControllerFile.js
todo-handler.js
```

The most important thing isn't the exact convention.

It's **consistency**.

---

# 22. Consistency beats personal preference

Suppose your project uses:

```text
user.controller.js
```

Don't suddenly create:

```text
ProductController.js
```

Use:

```text
product.controller.js
```

If you decide:

```text
<resource>.<layer>.js
```

then follow that pattern everywhere.

For example:

```text
user.controller.js
user.service.js
user.repository.js
user.route.js
user.model.js
```

---

# 23. Keep Controller files focused

Don't create:

```text
main.controller.js
```

containing:

```text
users
todos
courses
orders
payments
auth
notifications
```

This becomes a huge file.

Instead:

```text
controllers/
├── auth.controller.js
├── user.controller.js
├── todo.controller.js
├── course.controller.js
├── order.controller.js
└── notification.controller.js
```

Each file has a clear responsibility.

---

# 24. When should you split a Controller?

Suppose:

```text
user.controller.js
```

has become:

```text
createUser
getUser
getUsers
updateUser
deleteUser
getProfile
updateProfile
changePassword
verifyEmail
uploadAvatar
sendInvitation
...
```

You might eventually separate some responsibilities.

For example:

```text
controllers/
├── user.controller.js
├── profile.controller.js
└── user-auth.controller.js
```

But don't split files too early.

Start simple.

Split when the file becomes difficult to understand.

---

# 25. Resource-based organization

For a medium-sized project:

```text
src/
├── controllers/
│   ├── auth.controller.js
│   ├── user.controller.js
│   ├── todo.controller.js
│   └── course.controller.js
│
├── services/
│   ├── auth.service.js
│   ├── user.service.js
│   ├── todo.service.js
│   └── course.service.js
│
├── repositories/
│   ├── user.repository.js
│   ├── todo.repository.js
│   └── course.repository.js
```

This makes it easy to find the corresponding layer.

---

# 26. Another organization style

As applications become very large, you may eventually organize by feature:

```text
modules/
├── users/
│   ├── user.controller.js
│   ├── user.service.js
│   ├── user.repository.js
│   ├── user.route.js
│   └── user.model.js
│
├── todos/
│   ├── todo.controller.js
│   ├── todo.service.js
│   ├── todo.repository.js
│   ├── todo.route.js
│   └── todo.model.js
```

This is called **feature/module-based organization**.

For your current starter architecture, don't worry about switching to it immediately.

First become comfortable with the layer-based architecture.

---

# 27. Naming route handlers

Consider:

```js
router.get("/", getTodos);
router.get("/:id", getTodo);
router.post("/", createTodo);
router.patch("/:id", updateTodo);
router.delete("/:id", deleteTodo);
```

This is very readable.

You can almost read it as English:

```text
GET all → getTodos
GET one → getTodo
POST → createTodo
PATCH → updateTodo
DELETE → deleteTodo
```

That's exactly what we want.

---

# 28. Naming Service calls

The Controller and Service should generally use matching concepts.

Controller:

```js
const todo = await todoService.getTodo(todoId);
```

Service:

```js
export const getTodo = async (todoId) => {
    ...
};
```

Repository:

```js
const todo = await todoRepository.findById(todoId);
```

Notice the vocabulary changes slightly at each layer:

```text
Controller
getTodo()

Service
getTodo()

Repository
findById()
```

That's intentional.

The Repository describes **data access**.

The Service describes **application behavior**.

---

# 29. A useful naming vocabulary

### Controller

Use application/HTTP action words:

```text
create
get
update
delete
publish
cancel
approve
login
logout
```

### Service

Use business/application action words:

```text
createUser
authenticateUser
calculateOrderTotal
publishCourse
cancelOrder
```

### Repository

Use persistence/data-access words:

```text
findById
findByEmail
findMany
create
updateById
deleteById
```

This distinction becomes very useful as your backend gets more advanced.

---

# 30. Example of good naming across layers

Let's say we're creating a course.

### Route

```js
router.post("/", createCourse);
```

### Controller

```js
createCourse
```

### Service

```js
courseService.createCourse(...)
```

### Repository

```js
courseRepository.create(...)
```

The flow is:

```text
POST /courses
      ↓
createCourse Controller
      ↓
courseService.createCourse()
      ↓
courseRepository.create()
      ↓
MongoDB
```

Each layer has a clear name.

---

# 31. Naming errors

Your custom errors should also be descriptive.

For example:

```js
UserNotFoundError
TodoNotFoundError
UnauthorizedError
ForbiddenError
ValidationError
DuplicateEmailError
```

Or, if your project uses a general `AppError`, you can use:

```js
new AppError("User not found", 404)
```

The important thing is that error names/messages communicate **what happened**.

---

# 32. Naming variables inside Controllers

Good:

```js
const { id: userId } = req.params;
const user = await userService.getUser(userId);
```

Bad:

```js
const x = req.params.id;
const y = await userService.getUser(x);
```

Your Controller is small, so variable names should be very readable.

Prefer:

```text
userId
todoId
courseId
orderId
```

over:

```text
id1
id2
x
data
result1
```

---

# 33. Don't call everything `data`

This:

```js
const data = await todoService.getTodo(id);
```

works, but:

```js
const todo = await todoService.getTodo(id);
```

is better.

Likewise:

```js
const user = ...
const course = ...
const order = ...
const todos = ...
```

The variable should communicate what it contains.

---

# 34. Naming response variables

Prefer:

```js
const todo = await todoService.getTodo(id);

return res.status(200).json({
    success: true,
    data: todo
});
```

rather than:

```js
const result = await todoService.getTodo(id);

return res.status(200).json({
    success: true,
    data: result
});
```

`result` isn't wrong, but `todo` is more meaningful.

For complex operations:

```js
const result = await paymentService.processPayment(...);
```

can be perfectly reasonable if the result genuinely contains multiple things.

---

# 35. Naming Controllers for special operations

Suppose you have:

```http
PATCH /courses/:id/publish
```

Controller:

```js
publishCourse
```

Suppose:

```http
PATCH /orders/:id/cancel
```

Controller:

```js
cancelOrder
```

Suppose:

```http
POST /users/:id/invite
```

Controller:

```js
inviteUser
```

This is much better than generic:

```js
updateCourse
updateOrder
updateUser
```

when the actual business intention is more specific.

---

# 36. Avoid overly long function names

Don't create:

```js
createNewTodoForAuthenticatedUserWithValidationAndNotification
```

That's describing the entire implementation.

Prefer:

```js
createTodo
```

The Controller's surrounding architecture already tells us that authentication, validation, services, notifications, etc. exist elsewhere.

Good names should be:

> **specific enough to understand, short enough to read.**

---

# 37. Naming convention for async Controllers

You don't need to put `Async` into the name.

Avoid:

```js
getUserAsync
createTodoAsync
```

Just use:

```js
getUser
createTodo
```

Whether the function is asynchronous is an implementation detail.

---

# 38. Naming convention for middleware-wrapped Controllers

This:

```js
export const getTodo = asyncHandler(async (req, res) => {
    ...
});
```

is perfectly clear.

You don't need:

```js
export const asyncGetTodo = ...
```

or:

```js
export const getTodoHandler = ...
```

unless your project has a specific reason.

---

# 39. Don't overthink naming

The goal isn't to create the world's perfect naming system.

The goal is:

```text
Clear
Predictable
Consistent
Readable
```

If another developer can open:

```text
todo.controller.js
```

and immediately understand:

```text
createTodo
getTodos
getTodo
updateTodo
deleteTodo
```

your naming is doing its job.

---

For the backend starter you're learning, I'd recommend:

### Files

```text

```

### CRUD functions

```text
createUser
getUsers
getUser
updateUser

```

### Domain actions

```text
publishCourse

approveApplication
verifyEmail

```

### Variables

```text
user
```

# 41. A complete example

Let's create:

```text
controllers/todo.controller.js
```

```js
import { asyncHandler } from "../utils/asyncHandler.js";
import { todoService } from "../services/todo.service.js";

export const createTodo = asyncHandler(async (req, res) => {
    const { title } = req.body;
    const { id: userId } = req.user;

    const todo = await todoService.createTodo({
        title,
        userId
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
});

export const getTodos = asyncHandler(async (req, res) => {
    const { id: userId } = req.user;

    const todos = await todoService.getTodos(userId);

    return res.status(200).json({
        success: true,
        data: todos
    });
});

export const getTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;
    const { id: userId } = req.user;

    const todo = await todoService.getTodo({
        todoId,
        userId
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});

export const updateTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;
    const { title } = req.body;
    const { id: userId } = req.user;

    const todo = await todoService.updateTodo({
        todoId,
        userId,
        title
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});

export const deleteTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;
    const { id: userId } = req.user;

    await todoService.deleteTodo({
        todoId,
        userId
    });

    return res.status(204).send();
});
```

Even without reading the implementation, you can understand the file.

That's the power of good naming.

# 42. Matching routes

Then:

```js
import {
    createTodo,
    getTodos,
    getTodo,
    updateTodo,
    deleteTodo
} from "../controllers/todo.controller.js";

router.post("/", createTodo);
router.get("/", getTodos);
router.get("/:id", getTodo);
router.patch("/:id", updateTodo);
router.delete("/:id", deleteTodo);
```

Now the entire API is easy to scan.

```text
POST   /todos       → createTodo
GET    /todos       → getTodos
GET    /todos/:id   → getTodo
PATCH  /todos/:id   → updateTodo
DELETE /todos/:id   → deleteTodo
```

---

# 43. The bigger lesson

Naming isn't just about aesthetics.

Good naming reduces **mental load**.

When you see:

```js
const todo = await todoService.getTodo(todoId);
```

your brain immediately knows:

```text
todoId
   ↓
find Todo
   ↓
return todo
```

When you see:

```js
const x = await service.get(y);
```

your brain has to stop and investigate.

As your codebase gets bigger, those tiny differences matter a lot.

---

# 🧠 Final Mental Model

Use this simple rule:

```text
FILE
↓
<resource>.<layer>.js

FUNCTION
↓
<action><Resource>()

VARIABLE
↓
meaningfulName

ROUTE
↓
HTTP method + path + action
```

Example:

```text
todo.controller.js
        ↓
createTodo()
        ↓
POST /todos
```

and:

```text
todo.controller.js
        ↓
getTodo()
        ↓
GET /todos/:id
```

For non-CRUD operations:

```text
publishCourse()
cancelOrder()
approveUser()
refreshToken()
verifyEmail()
```

### 🔥 Remember

> **Name things according to what they represent, not according to how they are implemented.**

So prefer:

```text
createTodo
```

over:

```text
postTodo
```

and:

```text
publishCourse
```

over:

```text
updateCourseStatus
```

when publishing is the actual business action.

This will make the Controllers, Services, Routes, and Repositories much easier to understand as your MERN backend grows.
