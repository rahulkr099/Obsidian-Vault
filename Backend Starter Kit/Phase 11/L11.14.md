# Lesson 11.14 — One Controller Action = One Responsibility

This lesson is the **core principle of Controller design** in your Phase 11.

Your roadmap defines 11.14 exactly as:

> **One controller action = one responsibility**.

And this fits the larger architecture you've been learning:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

The Controller's job is to act as an **HTTP translator**: HTTP → application and application → HTTP.

---

# 1. What does "one responsibility" mean?

Suppose you have:

```http
POST /api/v1/auth/login
```

The Controller should mainly do:

```text
1. Read request data
2. Call the service
3. Send HTTP response
```

For example:

```js
export const login = asyncHandler(async (req, res) => {
    const result = await authService.login(req.body);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

That's a focused Controller action.

It doesn't:

```text
❌ query MongoDB
❌ hash passwords
❌ generate JWTs
❌ send emails
❌ contain complex business rules
❌ manually handle every error
```

Those responsibilities belong elsewhere.

---

# 2. Think of a Controller as a translator

Imagine a person speaks English and another person speaks Hindi.

The translator doesn't perform the actual work.

They translate:

```text
Person A
   ↓
Translator
   ↓
Person B
```

Similarly:

```text
HTTP Client
     ↓
Controller
     ↓
Application
```

The Controller translates things like:

```js
req.body
req.params
req.query
req.user
```

into something your application can use.

Then it translates the application's result into:

```js
res.status(...)
res.json(...)
```

---

# 3. What belongs inside a Controller?

A Controller normally handles **HTTP-specific work**.

For example:

```js
export const getTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.getTodo(todoId);

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

Notice the three main jobs:

### 1. Read HTTP input

```js
req.params
```

### 2. Call application logic

```js
todoService.getTodo(todoId)
```

### 3. Create HTTP output

```js
res.status(200).json(...)
```

That's it.

---

# 4. What should NOT belong in the Controller?

Consider this:

```js
export const login = asyncHandler(async (req, res) => {
    const { email, password } = req.body;

    const user = await User.findOne({ email });

    if (!user) {
        return res.status(401).json({
            message: "Invalid credentials"
        });
    }

    const isPasswordValid = await bcrypt.compare(
        password,
        user.password
    );

    if (!isPasswordValid) {
        return res.status(401).json({
            message: "Invalid credentials"
        });
    }

    const accessToken = jwt.sign(
        { userId: user._id },
        process.env.ACCESS_TOKEN_SECRET
    );

    await User.updateOne(
        { _id: user._id },
        { refreshToken: refreshTokenHash }
    );

    await sendEmail(...);

    return res.status(200).json({
        accessToken
    });
});
```

It works, but this Controller is doing **far too much**.

It knows about:

```text
MongoDB
password hashing
JWT
refresh tokens
email
business rules
HTTP
```

This is what we call a **fat controller**.

---

# 5. The professional version

Instead:

```js
export const login = asyncHandler(async (req, res) => {
    const result = await authService.login(req.body);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

Now:

```text
Controller
    ↓
authService.login()
```

And the Service can handle:

```text
Find user
    ↓
Check password
    ↓
Generate tokens
    ↓
Store refresh-token hash
    ↓
Return authentication result
```

This is exactly the architecture your roadmap is trying to teach before you move deeper into Services and Repositories.

# 6. One endpoint → one Controller action

A useful mental model is:

```text
Endpoint
   ↓
Controller action
   ↓
One HTTP responsibility
```

For example:

```text
POST /todos
    ↓
createTodo

GET /todos
    ↓
getTodos

GET /todos/:id
    ↓
getTodo

PATCH /todos/:id
    ↓
updateTodo

DELETE /todos/:id
    ↓
deleteTodo
```

This gives you a predictable structure.

```js

    const todo = await todoService.createTodo({
        ...req.body,
        userId: req.user.id
```

```js

    const { id: todoId } = req.params;
```

Again:

```text

    ↓
Call service
    ↓

```

Very focused.

# 9. One responsibility does NOT mean one line

This is important.

"One responsibility" does **not** mean:

```js
export const getTodo = () => {
    ...
};
```

must contain only one statement.

This is perfectly fine:

```js
export const getTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.getTodo({
        todoId,
        userId: req.user.id
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

There are several lines, but they all belong to **one responsibility**:

> Handle the HTTP request for retrieving one Todo.

# 10. What is a responsibility?

A responsibility means:

> **A single meaningful job that the code is responsible for performing.**

For a Controller:

```text
HTTP request → application → HTTP response
```

For a Service:

```text
Business operation
```

For a Repository:

```text
Database/data access
```

For middleware:

```text
Request processing/check
```

This is why your architecture has separate layers.

The starter's roadmap explicitly describes the Repository as the database-access layer and the Service as the place for application/business logic.

# 11. Controller vs Service

This is where beginners often get confused.

Suppose we have:

```http
POST /api/v1/users
```

Controller:

```js
export const createUser = asyncHandler(async (req, res) => {
    const user = await userService.createUser(req.body);

    return res.status(201).json({
        success: true,
        data: user
    });
});
```

Service:

```js
export const createUser = async (userData) => {
    // business logic
};
```

The distinction is:

### Controller

> How do I handle this HTTP request?

### Service

> What should happen when a user is created?

---

# 12. Example of business logic

Suppose the rule is:

> A user cannot register with an email that already exists.

That's business/application logic.

It belongs in the Service:

```js
export const createUser = async (userData) => {
    const existingUser = await userRepository.findByEmail(
        userData.email
    );

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    // continue...
};
```

The Controller doesn't need to know **why** the email is checked.

It simply calls:

```js
userService.createUser(...)
```

# 13. Controller should not query MongoDB

Avoid:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await User.findById(req.params.id);

    ...
});
```

This makes the Controller responsible for database access.

Instead:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Then:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Model
   ↓
MongoDB
```

Your roadmap specifically teaches this progression: Controller → Service → Repository → Model → MongoDB.

---

# 14. Controller should not hash passwords

Avoid:

```js
const hashedPassword = await bcrypt.hash(password, 12);
```

inside:

```text
user.controller.js
```

Why?

Because password hashing is not an HTTP responsibility.

It belongs in your application/authentication layer.

Your starter's authentication design specifically places password hashing in the authentication flow rather than making it a Controller concern.

---

# 15. Controller should not generate JWTs

Avoid:

```js
const token = jwt.sign(...);
```

inside:

```text
auth.controller.js
```

Instead:

```js
const result = await authService.login(req.body);
```

The Service handles the authentication process.

The Controller handles the HTTP boundary.

---

# 16. Controller should not send emails

Avoid:

```js
await sendVerificationEmail(user.email);
```

inside every Controller.

Your architecture has a separate email layer:

```text
mail/
├── mailSender.js
├── renderTemplate.js
└── templates/
```

The roadmap explicitly places email architecture outside Controllers and later covers email services and background processing.

---

# 17. Controller should not contain complex validation

Basic extraction is fine:

```js
const { email, password } = req.body;
```

But don't turn the Controller into:

```js
if (!email) ...
if (!email.includes("@")) ...
if (password.length < 8) ...
if (!/[A-Z]/.test(password)) ...
```

That's validation logic.

Your architecture already has:

```text
validations/
middlewares/security/validate.middleware.js
```

for this job.

The flow becomes:

```text
Request
   ↓
Validation middleware
   ↓
Controller
```

---

# 18. Controller should not contain authorization rules everywhere

Avoid:

```js
if (req.user.role !== "admin") {
    return res.status(403).json(...);
}
```

everywhere.

For simple route protection, use authorization middleware.

For resource ownership/business authorization, the appropriate application layer can enforce it.

Your broader architecture explicitly distinguishes:

```text
Authentication
+
Authorization
+
Resource ownership
```

and later covers RBAC and ownership.

---

# 19. Controller should not manually handle every error

We already learned this in Lesson 11.12.

Avoid:

```js
try {
    ...
} catch (error) {
    ...
}
```

in every Controller.

Instead:

```js
export const getTodo = asyncHandler(async (req, res) => {
    ...
});
```

Then:

```text
Controller throws
      ↓
asyncHandler
      ↓
next(error)
      ↓
error.middleware
      ↓
JSON response
```

This is the exact error flow defined in your starter architecture.

# 20. What SHOULD the Controller do?

Let's create a checklist.

A Controller can:

```text
✓ Read req.body
✓ Read req.params
✓ Read req.query
✓ Read req.user
✓ Call a service
✓ Choose HTTP status
✓ Build HTTP response
✓ Set cookies/headers when appropriate
✓ Pass errors to centralized handling
```

A Controller generally should NOT:

```text
✗ Query MongoDB directly
✗ Implement complicated business rules
✗ Hash passwords
✗ Generate JWTs directly
✗ Send emails directly
✗ Perform complicated validation
✗ Become a giant try/catch block
```

---

# 21. A very useful test

Whenever you're unsure whether something belongs in a Controller, ask:

> **"Is this specifically about HTTP?"**

If yes, it probably belongs in the Controller.

For example:

```js

```

HTTP-specific?

**Yes.**

Controller.

---

```js

```

HTTP-specific?

**Yes.**

Controller.

---

```js
bcrypt.compare(...)
```

HTTP-specific?

**No.**

Service/auth utility.

---

```js
User.findOne(...)
```

HTTP-specific?

**No.**

Repository.

---

```js
email already exists
```

Business rule?

**Yes.**

Service.

# 22. Think in three questions

When writing a Controller, ask:

### Question 1

> What information came from HTTP?

```js
req.body
req.params
req.query
req.user
```

### Question 2

> What application operation should happen?

```js
userService.createUser(...)
```

### Question 3

> What HTTP response should I return?

```js
res.status(...).json(...)
```

That's almost the entire Controller pattern.

# 26. One action can call one or more services

"One responsibility" doesn't mean:

> A Controller can call exactly one function.

For example:

```js
export const createOrder = asyncHandler(async (req, res) => {
    const order = await orderService.createOrder({
        userId: req.user.id,
        items: req.body.items
    });

    return res.status(201).json({
        success: true,
        data: order
    });
});
```

The Service might internally coordinate:

```text
Order service
   ↓
Product repository
   ↓
Payment service
   ↓
Order repository
   ↓
Email service
```

The Controller doesn't need to know about those details.

---

# 27. Don't turn the Controller into an orchestrator

This is a common mistake:

```js
export const createOrder = asyncHandler(async (req, res) => {
    const user = await userService.getUser(...);

    const products = await productService.getProducts(...);

    const total = calculateTotal(products);

    const payment = await paymentService.charge(...);

    const order = await orderRepository.create(...);

    await emailService.send(...);

    return res.status(201).json(...);
});
```

This Controller has become the entire application.

Bad.

Instead:

```js
export const createOrder = asyncHandler(async (req, res) => {
    const order = await orderService.createOrder({
        userId: req.user.id,
        items: req.body.items
    });

    return res.status(201).json({
        success: true,
        data: order
    });
});
```

Now:

```text
Controller
    ↓
orderService.createOrder()
```

The Service orchestrates the business operation.

# 29. How thin is "thin"?

There is no magical number like:

> "Controller must contain exactly 7 lines."

Don't optimize for line count.

This:

```js
export const createTodo = asyncHandler(async (req, res) => {
    const { title, description } = req.body;

    const todo = await todoService.createTodo({
        title,
        description,
        userId: req.user.id
    });

    return res.status(201).json({
        success: true,
        message: "Todo created successfully",
        data: todo
    });
});
```

is completely fine.

It's still thin because every operation is related to the HTTP boundary.

# 30. A powerful refactoring question

Whenever your Controller becomes large, ask:

> **"Can this code exist without Express?"**

Suppose you have:

```js

    throw new AppError("User not found", 404);

```

Could this logic exist without:

```js

res

```

?

Yes.

Therefore, it probably doesn't belong in the Controller.

Move it into the Service/Repository architecture.

# 36. Exercise — Find the responsibility problems

Look at this:

```js
export const register = asyncHandler(async (req, res) => {
    const { email, password } = req.body;

    if (!email || !email.includes("@")) {
        return res.status(400).json({
            message: "Invalid email"
        });
    }

    const existingUser = await User.findOne({ email });

    if (existingUser) {
        return res.status(409).json({
            message: "Email already exists"
        });
    }

    const hashedPassword = await bcrypt.hash(password, 12);

    const user = await User.create({
        email,
        password: hashedPassword
    });

    const token = jwt.sign(
        { userId: user._id },
        process.env.JWT_SECRET
    );

    return res.status(201).json({
        user,
        token
    });
});
```

This Controller is responsible for:

```text
❌ validation
❌ database querying
❌ business rules
❌ password hashing
❌ user creation
❌ JWT generation
✓ HTTP response
```

That's a **fat Controller**.
