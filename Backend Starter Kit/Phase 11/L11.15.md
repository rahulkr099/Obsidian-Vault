# Lesson 11.15 — Building an Auth Controller

Now we move from **Controller theory → actually building one**.

The goal of this lesson is to understand how an `auth.controller.js` should be designed, rather than memorizing code.

Our Auth Controller will handle these HTTP actions:

```text
register
login
refresh
logout
status
```

The important idea from the previous lesson remains:

> **The Controller handles HTTP. The Service handles authentication logic.**

---

# 1. Where does Auth Controller fit?

Our request flow is:

```text
Client
  ↓
Route
  ↓
Middleware
  ↓
Auth Controller
  ↓
Auth Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

For example:

```http
POST /api/v1/auth/login
```

becomes:

```text
POST /auth/login
       ↓
login Controller
       ↓
authService.login()
       ↓
authentication logic
```

The Controller should **not** know the details of password hashing, JWT creation, token rotation, etc.

---

# 2. Auth Controller file

Our file might be:

```text
src/
└── controllers/
    └── auth.controller.js
```

At the top:

```js
import { asyncHandler } from "../utils/asyncHandler.js";
import { authService } from "../services/auth.service.js";
```

Then we'll export our Controller actions.

---

# 3. The five actions

For this architecture, think about:

```text
register
login
refresh
logout
status
```

Their responsibilities are different.

|Action|Purpose|
|---|---|
|`register`|Create a new account|
|`login`|Authenticate user|
|`refresh`|Get a new access token|
|`logout`|End the current authentication session|
|`status`|Check current authentication state|

---

# 4. `register`

First:

```http
POST /api/v1/auth/register
```

The client sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123"
}
```

The Controller receives this through:

```js
req.body
```

---

# 5. Basic register Controller

A thin Controller can look like this:

```js
export const register = asyncHandler(async (req, res) => {
    const result = await authService.register(req.body);

    return res.status(201).json({
        success: true,
        data: result
    });
});
```

Look carefully at what happened.

### Controller does:

```text
req.body
   ↓
authService.register()
   ↓
HTTP response
```

That's it.

---

# 6. What the Service does

The Service might internally perform:

```text
Check email
     ↓
Check existing user
     ↓
Hash password
     ↓
Create user
     ↓
Create authentication/session data
     ↓
Return result
```

The Controller doesn't need to know those details.

This separation is extremely important.

---

# 7. Why not hash the password here?

Don't do:

```js
export const register = asyncHandler(async (req, res) => {
    const hashedPassword = await bcrypt.hash(
        req.body.password,
        12
    );

    ...
});
```

Why?

Because password hashing isn't an HTTP responsibility.

Instead:

```js
authService.register(req.body);
```

The Service owns the application logic.

---

# 8. `login`

Now:

```http
POST /api/v1/auth/login
```

Body:

```json
{
  "email": "rahul@example.com",
  "password": "StrongPassword123"
}
```

Controller:

```js
export const login = asyncHandler(async (req, res) => {
    const result = await authService.login(req.body);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

Again:

```text
HTTP
 ↓
Controller
 ↓
Service
 ↓
HTTP response
```

---

# 9. What happens inside `authService.login()`?

Conceptually:

```text
email + password
       ↓
find user
       ↓
compare password
       ↓
generate access token
       ↓
generate/rotate refresh token
       ↓
return authentication result
```

The Controller should not implement this.

---

# 10. Access token vs refresh token

At this stage, remember the basic idea:

### Access token

Used frequently to access protected APIs.

```text
Client
  ↓
Authorization: Bearer <access-token>
```

### Refresh token

Used to obtain a new access token.

```text
Client
  ↓
refresh request
  ↓
new access token
```

The details of token rotation and storage belong to the authentication layer, not the Controller.

---

# 11. Cookies

Your authentication architecture may use cookies for refresh tokens.

For example, the Service might return something like:

```js
{
    user,
    accessToken,
    refreshToken
}
```

The Controller may need to put a token into an HTTP cookie.

That **is** HTTP-specific work.

For example:

```js
res.cookie("refreshToken", result.refreshToken, {
    httpOnly: true,
    secure: true,
    sameSite: "strict"
});
```

This is appropriate in a Controller because cookies are part of the HTTP response.

---

# 12. Important distinction

Notice the difference:

### Controller

```js
res.cookie(...)
```

Good.

### Controller

```js
const refreshTokenHash = await bcrypt.hash(...)
```

Not good.

Why?

Because:

```text
res.cookie()
```

is HTTP.

Whereas:

```text
bcrypt.hash()
```

is authentication/application logic.

This distinction will become very important when you build production authentication.

---

# 13. `refresh`

Now:

```http
POST /api/v1/auth/refresh
```

The refresh token might come from:

```js
req.cookies.refreshToken
```

The Controller can extract it:

```js
export const refresh = asyncHandler(async (req, res) => {
    const refreshToken = req.cookies.refreshToken;

    const result = await authService.refresh(refreshToken);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

This is a good Controller responsibility.

It is reading an HTTP cookie and passing the value to the Service.

---

# 14. What should NOT happen here?

Don't do:

```js
const decoded = jwt.verify(
    refreshToken,
    process.env.REFRESH_TOKEN_SECRET
);
```

followed by:

```js
const user = await User.findById(decoded.userId);
```

and then:

```js
const newToken = jwt.sign(...);
```

inside the Controller.

That turns the Controller into the authentication system.

Instead:

```js
const result = await authService.refresh(refreshToken);
```

---

# 15. `logout`

Now:

```http
POST /api/v1/auth/logout
```

The Controller may call:

```js
export const logout = asyncHandler(async (req, res) => {
    await authService.logout(req.user?.id);

    res.clearCookie("refreshToken");

    return res.status(204).send();
});
```

Notice something interesting.

The Controller has two jobs here:

```text
1. Call the application operation
2. Manipulate the HTTP cookie
```

Both are appropriate because cookie manipulation is HTTP-specific.

---

# 16. Why `204`?

HTTP `204 No Content` means:

> The request succeeded, but there is no response body to return.

So:

```js
return res.status(204).send();
```

is appropriate when logout doesn't need to return JSON.

You could also use:

```http
200 OK
```

with a response message if that is the convention of your API.

The important thing is to be consistent.

---

# 17. `status`

Now we have:

```http
GET /api/v1/auth/status
```

Its purpose is usually:

> Tell the client whether the current authentication state is valid.

A Controller could look like:

```js
export const status = asyncHandler(async (req, res) => {
    const result = await authService.status(req.user);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

Depending on your authentication design, the middleware may already have populated:

```js
req.user
```

---

# 18. Complete Controller

Putting everything together:

```js
import { asyncHandler } from "../utils/asyncHandler.js";
import { authService } from "../services/auth.service.js";

export const register = asyncHandler(async (req, res) => {
    const result = await authService.register(req.body);

    return res.status(201).json({
        success: true,
        data: result
    });
});

export const login = asyncHandler(async (req, res) => {
    const result = await authService.login(req.body);

    return res.status(200).json({
        success: true,
        data: result
    });
});

export const refresh = asyncHandler(async (req, res) => {
    const refreshToken = req.cookies.refreshToken;

    const result = await authService.refresh(refreshToken);

    return res.status(200).json({
        success: true,
        data: result
    });
});

export const logout = asyncHandler(async (req, res) => {
    await authService.logout(req.user?.id);

    res.clearCookie("refreshToken");

    return res.status(204).send();
});

export const status = asyncHandler(async (req, res) => {
    const result = await authService.status(req.user);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

This is a **thin Auth Controller**.

---

# 19. Why this Controller is good

Look at what it doesn't contain.

```text
❌ bcrypt
❌ jwt.sign()
❌ jwt.verify()
❌ User.findOne()
❌ User.create()
❌ refresh-token database queries
❌ complicated authentication rules
❌ password rules
```

Instead:

```text
✓ req.body
✓ req.cookies
✓ req.user
✓ authService
✓ res.status()
✓ res.json()
✓ res.cookie()
✓ res.clearCookie()
```

That is exactly what we want.

---

# 20. Auth Routes

Now we connect the Controller to routes.

```js
import { Router } from "express";

import {
    register,
    login,
    refresh,
    logout,
    status
} from "../controllers/auth.controller.js";

const router = Router();

router.post("/register", register);
router.post("/login", login);
router.post("/refresh", refresh);
router.post("/logout", logout);
router.get("/status", status);

export default router;
```

Now the flow becomes:

```text
POST /auth/register
       ↓
register()

POST /auth/login
       ↓
login()

POST /auth/refresh
       ↓
refresh()

POST /auth/logout
       ↓
logout()

GET /auth/status
       ↓
status()
```

---

# 21. Authentication middleware

Some routes may require authentication.

For example:

```js
router.post(
    "/logout",
    requireAuth,
    logout
);
```

And:

```js
router.get(
    "/status",
    requireAuth,
    status
);
```

Now the flow is:

```text
Request
  ↓
requireAuth
  ↓
req.user
  ↓
Controller
  ↓
Service
```

The Controller doesn't need to verify the access token again.

---

# 22. Why middleware first?

Suppose the request has:

```http
Authorization: Bearer eyJ...
```

`requireAuth` can:

```text
Read token
   ↓
Verify token
   ↓
Find/identify user
   ↓
Attach req.user
   ↓
next()
```

Then Controller receives:

```js
req.user
```

This is much cleaner.

---

# 23. Register usually doesn't require authentication

Normally:

```http
POST /auth/register
```

is public.

So:

```js
router.post("/register", register);
```

No authentication middleware.

---

# 24. Login usually doesn't require authentication

Similarly:

```http
POST /auth/login
```

is public.

The user doesn't have a valid access token yet.

So:

```js
router.post("/login", login);
```

---

# 25. Refresh is special

Refresh authentication is different.

The client may send:

```text
refresh token
```

through an HTTP-only cookie.

The refresh Controller extracts it:

```js
const refreshToken = req.cookies.refreshToken;
```

Then:

```js
authService.refresh(refreshToken);
```

The Service handles whether the token is valid.

---

# 26. Logout is also special

Depending on your architecture, logout may require:

```text
access token
```

or:

```text
refresh token
```

or both.

Don't blindly copy one approach into every project.

The important architectural principle is:

> **The Controller handles how authentication data arrives through HTTP; the Service handles what that data means.**

---

# 27. What if the refresh token is missing?

The Controller could check:

```js
const refreshToken = req.cookies.refreshToken;

if (!refreshToken) {
    throw new AppError(
        "Refresh token is required",
        401
    );
}
```

But there's an important architectural choice here.

If your Service already handles:

```text
missing token
invalid token
expired token
revoked token
```

then you may simply pass it through:

```js
const result = await authService.refresh(
    req.cookies.refreshToken
);
```

and let the Service throw the appropriate error.

Avoid duplicating validation across layers.

---

# 28. Error flow

Suppose:

```js
authService.login()
```

throws:

```js
new AppError("Invalid credentials", 401);
```

The Controller doesn't need:

```js
try {
    ...
} catch (error) {
    ...
}
```

because we're using:

```js
asyncHandler
```

Flow:

```text
authService.login()
       ↓
throws AppError
       ↓
asyncHandler
       ↓
next(error)
       ↓
error middleware
       ↓
HTTP 401 response
```

This keeps the Auth Controller clean.

---

# 29. Don't expose sensitive information

Suppose the Service returns:

```js
{
    user,
    accessToken
}
```

Make sure `user` doesn't contain:

```text
password
passwordHash
refreshTokenHash
security secrets
```

The Controller should not blindly return a database document containing sensitive fields.

Ideally, the Service or serializer creates a safe user representation:

```js
{
    id,
    name,
    email
}
```

Then the Controller returns that.

---

# 30. Good authentication response

For example:

```json
{
  "success": true,
  "data": {
    "user": {
      "id": "123",
      "name": "Rahul",
      "email": "rahul@example.com"
    },
    "accessToken": "..."
  }
}
```

Don't return:

```json
{
  "password": "...",
  "refreshTokenHash": "..."
}
```

Security-sensitive fields should never accidentally leak through your API.

---

# 31. A useful Controller checklist

Before finishing `auth.controller.js`, ask:

### Register

```text
✓ Reads req.body
✓ Calls authService.register()
✓ Returns 201
```

### Login

```text
✓ Reads req.body
✓ Calls authService.login()
✓ Returns authentication result
```

### Refresh

```text
✓ Reads refresh token from HTTP
✓ Calls authService.refresh()
✓ Returns new authentication result
```

### Logout

```text
✓ Calls authService.logout()
✓ Clears cookie if required
✓ Returns appropriate HTTP response
```

### Status

```text
✓ Reads current authentication context
✓ Calls authService.status()
✓ Returns status
```

# 32. The biggest beginner mistake

A beginner often thinks:

> "I need to make the login endpoint."

So they write everything in:

```text
auth.controller.js
```

But an endpoint isn't the same thing as an entire feature.

Think:

```text
Endpoint
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

The Controller is only one piece.

---

# 33. The mental model to memorize

For every Auth Controller function:

```text
                    HTTP
                     │
                     ▼
              ┌─────────────┐
              │ Controller  │
              └──────┬──────┘
                     │
              Extract HTTP data
                     │
                     ▼
              ┌─────────────┐
              │   Service   │
              └──────┬──────┘
                     │
             Authentication logic
                     │
                     ▼
              ┌─────────────┐
              │ Repository  │
              └─────────────┘
```

Then the result travels back:

```text
Repository
    ↓
Service
    ↓
Controller
    ↓
HTTP Response
```

# 34. Your final Auth Controller

For your current learning architecture, remember this shape:

```js
export const register = asyncHandler(async (req, res) => {
    const result = await authService.register(req.body);

    return res.status(201).json({
        success: true,
        data: result
    });
});

export const login = asyncHandler(async (req, res) => {
    const result = await authService.login(req.body);

    return res.status(200).json({
        success: true,
        data: result
    });
});

export const refresh = asyncHandler(async (req, res) => {
    const result = await authService.refresh(
        req.cookies.refreshToken
    );

    return res.status(200).json({
        success: true,
        data: result
    });
});

export const logout = asyncHandler(async (req, res) => {
    await authService.logout(req.user?.id);

    res.clearCookie("refreshToken");

    return res.status(204).send();
});

export const status = asyncHandler(async (req, res) => {
    const result = await authService.status(req.user);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

Don't memorize this line-by-line.

Understand the pattern:

```text
register → req.body → service → 201
login    → req.body → service → 200
refresh  → cookie   → service → 200
logout   → user     → service → 204
status   → user     → service → 200
```

# 🧠 Lesson 11.15 Summary

The most important thing you should take from this lesson is:

> **An Auth Controller should translate authentication-related HTTP requests into calls to the Auth Service.**

### Controller:

```text
req.body
req.params
req.query
req.cookies
req.user
       ↓
authService
       ↓
res.status()
res.json()
res.cookie()
res.clearCookie()
```

### Service:

```text
password verification
token generation
refresh-token handling
authentication rules
database coordination
```

### Repository:

```text
database operations
```

And the complete flow:

```text
POST /auth/login
       ↓
auth route
       ↓
middleware
       ↓
login controller
       ↓
authService.login()
       ↓
repository
       ↓
MongoDB
       ↓
result
       ↓
login controller
       ↓
HTTP response
```
