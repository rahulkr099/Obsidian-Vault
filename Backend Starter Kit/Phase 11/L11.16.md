# Lesson 11.16 — Building the User Controller

In the previous lesson, we built the **Auth Controller**.

Now we'll build the **User Controller**.

The main purpose is to understand how normal user-related HTTP operations are translated into Service calls.

Our basic flow remains:

```text
HTTP Request
     ↓
Route
     ↓
Middleware
     ↓
User Controller
     ↓
User Service
     ↓
User Repository
     ↓
MongoDB
```

The key rule from Lesson 11.14 still applies:

> **One Controller action = one clear HTTP responsibility.**

---

# 1. What is a User Controller?

The User Controller handles HTTP requests related to users.

For example:

```text
GET    /users
GET    /users/:id
POST   /users
PATCH  /users/:id
DELETE /users/:id
```

These routes may connect to:

```js
getUsers
getUser
createUser
updateUser
deleteUser
```

So our file can be:

```text
src/
└── controllers/
    └── user.controller.js
```

---

# 2. User Controller vs Auth Controller

This distinction is important.

### Auth Controller

Deals with:

```text
register
login
logout
refresh
authentication status
```

### User Controller

Deals with:

```text
user data
user profile
user management
user CRUD
```

Think:

```text
AUTH
"What is my authentication state?"

USER
"What user data am I managing?"
```

Don't mix everything into `auth.controller.js`.

---

# 3. Basic User Controller imports

```js
import { asyncHandler } from "../utils/asyncHandler.js";
import { userService } from "../services/user.service.js";
```

Then we'll create our Controller actions.

# 4. CRUD operations

A typical User Controller contains:

```text
createUser
getUsers
getUser
updateUser
deleteUser
```

The mapping is:

```text
POST   /users       → createUser
GET    /users       → getUsers
GET    /users/:id   → getUser
PATCH  /users/:id   → updateUser
DELETE /users/:id   → deleteUser
```

This is the same predictable naming convention we learned in Lesson 11.13.

---

# 5. `createUser`

Let's start with:

```http
POST /api/v1/users
```

The request might contain:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

The Controller:

```js
export const createUser = asyncHandler(async (req, res) => {
    const user = await userService.createUser(req.body);

    return res.status(201).json({
        success: true,
        data: user
    });
});
```

Very simple.

The Controller:

```text
reads req.body
      ↓
calls userService
      ↓
returns 201
```

---

# 6. What shouldn't happen here?

Don't write:

```js
const existingUser = await User.findOne({
    email: req.body.email
});
```

That's database access.

Don't write:

```js
const hashedPassword = await bcrypt.hash(
    req.body.password,
    12
);
```

That's authentication/application logic.

Don't write:

```js
if (!email.includes("@")) {
    ...
}
```

if your validation layer is responsible for this.

Instead:

```js
userService.createUser(req.body);
```

export const getUsers = asyncHandler(async (req, res) => {

HTTP
 ↓

# 8. Pagination and query parameters

Real APIs often support:

```http
GET /users?page=2&limit=20
```

The Controller can read:

```js
req.query
```

For example:

```js
export const getUsers = asyncHandler(async (req, res) => {
    const users = await userService.getUsers(req.query);

    return res.status(200).json({
        success: true,
        data: users
    });
});
```

The Controller's job is simply to pass the HTTP input into the application layer.

The Service can decide how pagination, sorting, filtering, etc. should work.

---

# 9. `getUser`

Now:

```http
GET /api/v1/users/:id
```

For:

```text
GET /users/123
```

Express gives us:

```js
req.params.id
```

Controller:

```js
export const getUser = asyncHandler(async (req, res) => {
    const { id: userId } = req.params;

    const user = await userService.getUser(userId);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Notice the naming:

```js
const { id: userId } = req.params;
```

This is better than:

```js
const id = req.params.id;
```

when you want to make it obvious that the ID represents a User.

---

# 10. Why use `userId`?

Imagine later your Controller has:

```js
const userId = req.params.id;
const orderId = req.query.orderId;
const courseId = req.body.courseId;
```

Now the code is self-documenting.

Compare:

```js
const id = ...
const id2 = ...
const id3 = ...
```

Much harder to understand.

Good naming reduces mistakes.

---

# 11. `updateUser`

Now:

```http
PATCH /api/v1/users/:id
```

Request:

```json
{
  "name": "Rahul Kumar"
}
```

Controller:

```js
export const updateUser = asyncHandler(async (req, res) => {
    const { id: userId } = req.params;

    const user = await userService.updateUser(
        userId,
        req.body
    );

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Again, the Controller isn't deciding:

```text
Which fields can change?
Can email change?
Can role change?
Is this user allowed to update this user?
```

Those decisions belong in the appropriate validation, authorization, and Service layers.

---

# 12. Why shouldn't Controller decide allowed fields?

Suppose the request contains:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

Should a normal user be allowed to change:

```text
role → admin
```

?

That's an authorization/business rule.

Don't hide that rule inside:

```text
user.controller.js
```

Instead, your architecture should have proper authorization and Service-level rules.

This becomes especially important when we later deal with:

```text
RBAC
ownership
admin operations
```

---

# 13. `deleteUser`

Now:

```http
DELETE /api/v1/users/:id
```

Controller:

```js
export const deleteUser = asyncHandler(async (req, res) => {
    const { id: userId } = req.params;

    await userService.deleteUser(userId);

    return res.status(204).send();
});
```

Notice that we don't need:

```js
const deletedUser = ...
```

if the API doesn't need to return the deleted object.

---

# 14. Why `204`?

The operation succeeded:

```text
User deleted
```

but there is no response body.

So:

```js
return res.status(204).send();
```

is a clean choice.

Alternatively, your API might standardize on:

```json
{
  "success": true,
  "message": "User deleted successfully"
}
```

with:

```http
200 OK
```

The important thing is to establish one consistent API convention.

# 16. But real applications need more than CRUD

A real user system might also have:

getProfile

# 17. `getProfile`

Suppose:

```http
GET /api/v1/users/me
```

Authentication middleware has already populated:

```js
req.user
```

Controller:

```js
export const getProfile = asyncHandler(async (req, res) => {
    const user = await userService.getProfile(req.user.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Notice:

```text
req.user.id
```

came from the authentication middleware.

The Controller doesn't verify the access token itself.

---

# 18. `updateProfile`

Suppose:

```http
PATCH /api/v1/users/me
```

Controller:

```js
export const updateProfile = asyncHandler(async (req, res) => {
    const user = await userService.updateProfile(
        req.user.id,
        req.body
    );

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

This is different from:

```http
PATCH /users/:id
```

Why?

Because:

```text
/users/:id
```

means:

> Update the specified user.

While:

```text
/users/me
```

means:

> Update the currently authenticated user's profile.

This distinction is very useful in API design.

---

# 19. User Controller and authorization

Imagine:

```http
DELETE /users/123
```

Who can perform this?

Maybe:

```text
Admin
```

or perhaps:

```text
The user themselves
```

or:

```text
Admin OR account owner
```

The Controller shouldn't contain a giant authorization system.

Instead:

```text
Route
 ↓
Authentication middleware
 ↓
Authorization middleware
 ↓
Controller
 ↓
Service
```

For example:

```js
router.delete(
    "/:id",
    requireAuth,
    requireRole("admin"),
    deleteUser
);
```

Now the Controller can focus on:

```js
userService.deleteUser(userId);
```

---

# 20. Resource ownership

Suppose a normal user requests:

```http
GET /users/999
```

but `999` belongs to another user.

Should they be allowed to see it?

That's a **resource ownership** question.

Your architecture distinguishes authentication from authorization and ownership.

The Controller shouldn't blindly assume:

```js
req.params.id
```

is always allowed.

Instead, the Service or authorization layer should enforce the appropriate rule.

---

# 21. Don't trust `req.user` blindly

Authentication middleware might provide:

```js
req.user = {
    id: "...",
    role: "user"
};
```

The Controller can use it:

```js
req.user.id
```

But don't let a client send:

```json
{
  "userId": "someone-else"
}
```

and blindly trust it for sensitive operations.

For example, this is dangerous:

```js
await userService.updateProfile(
    req.body.userId,
    req.body
);
```

Better:

```js
await userService.updateProfile(
    req.user.id,
    req.body
);
```

The authenticated identity should come from the server-side authentication context.

---

# 22. Don't expose sensitive User data

This is especially important in a User Controller.

Suppose your MongoDB document contains:

```js
{
    name,
    email,
    passwordHash,
    refreshTokenHash,
    role
}
```

Don't blindly do:

```js
res.json({
    data: user
});
```

if `user` contains sensitive fields.

You want a safe representation.

For example:

```js
{
    id,
    name,
    email,
    role
}
```

depending on who is requesting the data.

---

# 23. Controller vs serializer

As your application grows, you may create a helper such as:

```text
serializers/
└── user.serializer.js
```

Then:

```js
const safeUser = serializeUser(user);
```

and:

```js
return res.status(200).json({
    success: true,
    data: safeUser
});
```

The idea is:

```text
Database document
      ↓
Serializer / DTO
      ↓
Safe API response
```

You don't necessarily need this abstraction on day one.

But it is a useful pattern to know.

# 24. User list response

Suppose:

```http
GET /users
```

returns:

```json
{
  "success": true,
  "data": [
    {
      "id": "1",
      "name": "Rahul",
      "email": "rahul@example.com"
    },
    {
      "id": "2",
      "name": "Amit",
      "email": "amit@example.com"
    }
  ]
}
```

The Controller doesn't build each user manually.

The Service can return safe user objects, or a serializer can transform them.

---

# 25. Pagination

Later, your response might look like:

```json
{
  "success": true,
  "data": [
    {}
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 120,
    "totalPages": 6
  }
}
```

Controller:

```js
export const getUsers = asyncHandler(async (req, res) => {
    const result = await userService.getUsers(req.query);

    return res.status(200).json({
        success: true,
        data: result.users,
        pagination: result.pagination
    });
});
```

The Controller formats the HTTP response.

The Service handles the actual application logic for obtaining the data.

---

# 26. Query parameters belong to HTTP

This is appropriate:

```js
const { page, limit, search } = req.query;
```

because these came from HTTP.

You can then pass them to the Service:

```js
const result = await userService.getUsers({
    page,
    limit,
    search
});
```

The Controller translates:

```text
HTTP query parameters
        ↓
application input
```

---

# 27. Don't put database filters in Controller

Avoid:

```js
const users = await User.find({
    name: { $regex: req.query.search }
});
```

Now the Controller knows MongoDB query syntax.

Instead:

```js
const users = await userService.getUsers({
    search: req.query.search
});
```

Then:

```text
Service
 ↓
Repository
 ↓
MongoDB query
```

This separation makes the architecture easier to test and change.

---

# 28. What if the user isn't found?

Suppose:

```js
await userService.getUser(userId);
```

throws:

```js
new AppError("User not found", 404);
```

The Controller doesn't need:

```js
try/catch
```

because:

```js
asyncHandler(...)
```

handles the rejected Promise and passes the error to centralized error middleware.

Flow:

```text
userService.getUser()
       ↓
UserNotFoundError
       ↓
asyncHandler
       ↓
error middleware
       ↓
404 response
```

Keep the Controller clean.

---

# 29. Route file

Now connect the User Controller.

```js
import { Router } from "express";

import {
    createUser,
    getUsers,
    getUser,
    updateUser,
    deleteUser,
    getProfile,
    updateProfile
} from "../controllers/user.controller.js";

const router = Router();

router.get("/me", requireAuth, getProfile);
router.patch("/me", requireAuth, updateProfile);

router.post("/", requireAuth, requireRole("admin"), createUser);
router.get("/", requireAuth, requireRole("admin"), getUsers);
router.get("/:id", requireAuth, getUser);
router.patch("/:id", requireAuth, updateUser);
router.delete("/:id", requireAuth, requireRole("admin"), deleteUser);

export default router;
```

The exact authorization rules depend on your application's requirements.

The important architectural idea is:

```text
Middleware
    ↓
authorization
    ↓
Controller
```

rather than putting all authorization logic inside the Controller.

---

# 30. Route ordering matters

There's a subtle Express issue here.

Consider:

```js
router.get("/:id", getUser);
router.get("/me", getProfile);
```

A request to:

```http
GET /users/me
```

could match:

```text
/:id
```

with:

```text
id = "me"
```

So generally put the specific route before the dynamic route:

```js
router.get("/me", getProfile);
router.get("/:id", getUser);
```

This is a small but very practical Express lesson.

---

# 31. Another important distinction: `/me`

You may wonder:

> Why not simply use `/users/:id`?

Because `/me` communicates something different.

```text
GET /users/:id
```

means:

> Get a specific user resource.

```text
GET /users/me
```

means:

> Get the currently authenticated user's profile.

This can make frontend code much easier:

```js
fetch("/api/v1/users/me");
```

instead of:

```js
fetch(`/api/v1/users/${currentUser.id}`);
```

# 32. User Controller should remain boring

This is actually a compliment.

A good Controller often looks boring:

```js
export const getUser = asyncHandler(async (req, res) => {
    const { id: userId } = req.params;

    const user = await userService.getUser(userId);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

That's good.

You don't want Controllers to be exciting.

You want them to be:

```text
Predictable
Small
Readable
Easy to test
Easy to replace
```

# 33. A common beginner mistake

Beginners often create:

```js
user.controller.js
```

with 500–1000 lines.

For example:

```text
createUser
getUser
getUsers
updateUser
deleteUser
login
logout
refresh
verifyEmail
resetPassword
changePassword
sendEmail
uploadAvatar
calculateStats
generateReport
...
```

Don't do this.

Authentication belongs in Auth Controller.

User management belongs in User Controller.

Other domain operations should have their own Controllers.

# 36. Spot the pattern

Every action follows:

```text
1. Extract HTTP input
2. Call Service
3. Return HTTP response
```

For example:

```js
const { id: userId } = req.params;

const user = await userService.getUser(userId);

return res.status(200).json({
    success: true,
    data: user
});
```

That's the Controller pattern.

---

# 37. The User Controller should not know MongoDB

Your Controller shouldn't care whether your Service uses:

```text
MongoDB
PostgreSQL
MySQL
Redis
external API
```

It only knows:

```js
userService.getUser(userId)
```

This gives you an important advantage.

If you later replace MongoDB with PostgreSQL:

```text
Controller
      ↓
Service
      ↓
PostgreSQL Repository
```

the Controller may not need any changes.

---

# 38. This is why layers matter

Imagine a backend without layers:

```text
Controller
   ↓
MongoDB
```

Now every Controller knows MongoDB.

But with:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

each layer has a clear responsibility.

This is the architecture you're gradually learning throughout these Phase 7–11 lessons.

# 🧠 Final Cheat Sheet

### User CRUD

```text
POST   /users       → createUser
GET    /users       → getUsers
GET    /users/:id   → getUser
PATCH  /users/:id   → updateUser
DELETE /users/:id   → deleteUser
```

### Profile

```text
GET    /users/me    → getProfile
PATCH  /users/me    → updateProfile
```

### Controller responsibilities

```text
✓ req.body
✓ req.params
✓ req.query
✓ req.user
✓ call userService
✓ choose HTTP status
✓ return HTTP response
```

### Don't put here

```text
✗ MongoDB queries
✗ complex business logic
✗ password hashing
✗ JWT generation
✗ database rules
✗ complicated authorization
✗ manual error handling
```

### The pattern

```js
export const getUser = asyncHandler(async (req, res) => {
    const { id: userId } = req.params;

    const user = await userService.getUser(userId);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

If you understand why this code is structured this way, you're no longer just learning **Controllers**—you're starting to understand **layered backend architecture**.
