# Lesson 11.17 — Building a CRUD Controller

Now we're going to go one step deeper.

In Lesson 11.16, you saw the individual User Controller methods:

```text
createUser
getUsers
getUser
updateUser
deleteUser
```

In this lesson, we'll understand the **CRUD Controller pattern** properly.

CRUD means:

```text
C → Create
R → Read
U → Update
D → Delete
```

This pattern appears everywhere in backend development:

```text
Users
Products
Courses
Posts
Orders
Comments
Todos
Categories
```

Once you understand CRUD Controllers, you'll be able to build Controllers for almost any resource.

---

# 1. What does CRUD actually mean?

Suppose we have a `Todo` resource.

A client should be able to:

```text
Create a Todo
Read Todos
Update a Todo
Delete a Todo
```

That gives us:

```text
POST   /todos
GET    /todos
GET    /todos/:id
PATCH  /todos/:id
DELETE /todos/:id
```

The Controller connects these HTTP operations to the Service.

---

# 2. The complete CRUD flow

Think of it like this:

```text
                 HTTP
                  ↓
                ROUTE
                  ↓
              MIDDLEWARE
                  ↓
             CONTROLLER
                  ↓
               SERVICE
                  ↓
             REPOSITORY
                  ↓
               DATABASE
```

For example:

```text
POST /todos
   ↓
createTodo()
   ↓
todoService.createTodo()
   ↓
todoRepository.create()
   ↓
MongoDB
```

---

# 3. Our example resource

We'll use `Todo`.

A Todo might look like:

```json
{
  "title": "Learn Express",
  "description": "Study Controllers",
  "completed": false
}
```

Our Controller file:

```text
src/
└── controllers/
    └── todo.controller.js
```

---

# 4. Import dependencies

```js
import { asyncHandler } from "../utils/asyncHandler.js";
import { todoService } from "../services/todo.service.js";
```

Then we'll create five Controller functions.

---

# 5. CREATE — `createTodo`

The HTTP request:

```http
POST /api/v1/todos
```

Body:

```json
{
  "title": "Learn Controllers",
  "description": "Understand CRUD Controllers"
}
```

Controller:

```js
export const createTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.createTodo(req.body);

    return res.status(201).json({
        success: true,
        data: todo
    });
});
```

That's the basic pattern.

---

# 6. Why `201`?

When a new resource is successfully created, HTTP commonly uses:

```http
201 Created
```

So:

```js
res.status(201)
```

makes sense.

Compare:

```text
POST /todos
     ↓
new Todo created
     ↓
201 Created
```

---

# 7. What does the Service receive?

The Controller sends:

```js
req.body
```

So the Service receives something like:

```js
{
    title: "Learn Controllers",
    description: "Understand CRUD Controllers"
}
```

The Service might then:

```text
validate business rules
      ↓
prepare data
      ↓
call repository
      ↓
return created Todo
```

The Controller doesn't need to know how that happens.

---

# 8. READ — Get all resources

Now:

```http
GET /api/v1/todos
```

Controller:

```js
export const getTodos = asyncHandler(async (req, res) => {
    const todos = await todoService.getTodos();

    return res.status(200).json({
        success: true,
        data: todos
    });
});
```

This is the **collection endpoint**.

```text
/todos
```

means:

> Give me the collection of Todos.

---

# 9. Collection vs individual resource

This distinction is very important.

### Collection

```http
GET /todos
```

means:

```text
Give me many Todos.
```

### Individual resource

```http
GET /todos/123
```

means:

```text
Give me Todo 123.
```

So:

```text
/todos       → collection
/todos/:id   → individual resource
```

---

# 10. READ — Get one resource

Now:

```http
GET /api/v1/todos/123
```

Express gives us:

```js
req.params.id
```

Controller:

```js
export const getTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.getTodo(todoId);

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

The flow:

```text
/todos/123
    ↓
req.params.id
    ↓
todoId = "123"
    ↓
todoService.getTodo(todoId)
```

---

# 11. Why rename `id` to `todoId`?

You could write:

```js
const id = req.params.id;
```

But:

```js
const { id: todoId } = req.params;
```

is clearer.

Imagine a larger Controller:

```js
const { id: todoId } = req.params;

const userId = req.user.id;

const { categoryId } = req.body;
```

Now you immediately know what each ID represents.

Good naming becomes increasingly important as applications grow.

---

# 12. What if Todo doesn't exist?

Suppose:

```http
GET /todos/999
```

and Todo `999` doesn't exist.

The Service can throw:

```js
throw new AppError(
    "Todo not found",
    404
);
```

Then:

```text
Service
   ↓
AppError
   ↓
asyncHandler
   ↓
error middleware
   ↓
404 response
```

The Controller doesn't need to manually handle this.

---

# 13. UPDATE — `updateTodo`

Now:

```http
PATCH /api/v1/todos/123
```

Body:

```json
{
  "title": "Learn Advanced Controllers"
}
```

Controller:

```js
export const updateTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.updateTodo(
        todoId,
        req.body
    );

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

Notice the Service gets **two things**:

```text
todoId
update data
```

So:

```js
todoService.updateTodo(
    todoId,
    req.body
);
```

---

# 14. Why use PATCH?

There are two common HTTP methods for updating resources:

```text
PUT
PATCH
```

A simple mental model:

### PUT

Replace the resource representation.

### PATCH

Modify part of the resource.

For example:

```http
PATCH /todos/123
```

with:

```json
{
  "completed": true
}
```

means:

> Change the completed field.

For most partial-update APIs, `PATCH` is a natural choice.

---

# 15. DELETE — `deleteTodo`

Request:

```http
DELETE /api/v1/todos/123
```

Controller:

```js
export const deleteTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    await todoService.deleteTodo(todoId);

    return res.status(204).send();
});
```

Again:

```text
HTTP
 ↓
Controller
 ↓
Service
```

The Controller doesn't perform the actual database deletion.

# 16. Complete CRUD Controller

Now put everything together:

```js
import { asyncHandler } from "../utils/asyncHandler.js";
import { todoService } from "../services/todo.service.js";

export const createTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.createTodo(req.body);

    return res.status(201).json({
        success: true,
        data: todo
    });
});

export const getTodos = asyncHandler(async (req, res) => {
    const todos = await todoService.getTodos();

    return res.status(200).json({
        success: true,
        data: todos
    });
});

export const getTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.getTodo(todoId);

    return res.status(200).json({
        success: true,
        data: todo
    });
});

export const updateTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.updateTodo(
        todoId,
        req.body
    );

    return res.status(200).json({
        success: true,
        data: todo
    });
});

export const deleteTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    await todoService.deleteTodo(todoId);

    return res.status(204).send();
});
```

This is a standard CRUD Controller.

---

# 17. The five functions have a predictable structure

You should start seeing a pattern.

### Create

```js
const result = await service.create(req.body);
```

### Get all

```js
const result = await service.getAll(req.query);
```

### Get one

```js
const result = await service.getOne(req.params.id);
```

### Update

```js
const result = await service.update(
    req.params.id,
    req.body
);
```

### Delete

```js
await service.delete(req.params.id);
```

This pattern is extremely reusable.

# 18. CRUD route file

Now connect it to Express.

```js
import { Router } from "express";

import {
    createTodo,
    getTodos,
    getTodo,
    updateTodo,
    deleteTodo
} from "../controllers/todo.controller.js";

const router = Router();

router.post("/", createTodo);

router.get("/", getTodos);

router.get("/:id", getTodo);

router.patch("/:id", updateTodo);

router.delete("/:id", deleteTodo);

export default router;
```

Now:

```text
POST   /todos       → createTodo
GET    /todos       → getTodos
GET    /todos/:id   → getTodo
PATCH  /todos/:id   → updateTodo
DELETE /todos/:id   → deleteTodo
```

---

# 19. Add authentication

In a real application, Todos probably belong to users.

So routes might become:

```js
router.post(
    "/",
    requireAuth,
    createTodo
);

router.get(
    "/",
    requireAuth,
    getTodos
);

router.get(
    "/:id",
    requireAuth,
    getTodo
);

router.patch(
    "/:id",
    requireAuth,
    updateTodo
);

router.delete(
    "/:id",
    requireAuth,
    deleteTodo
);
```

Now the request flow is:

```text
Request
   ↓
requireAuth
   ↓
req.user
   ↓
Controller
   ↓
Service
```

---

# 20. Don't trust the client for ownership

This is a very important backend security concept.

Imagine the frontend sends:

```json
{
  "title": "My Todo",
  "userId": "someone-else"
}
```

Don't simply trust:

```js
req.body.userId
```

Instead, authentication middleware gives you:

```js
req.user.id
```

Then:

```js
const todo = await todoService.createTodo({
    ...req.body,
    userId: req.user.id
});
```

Now the server determines the owner.

---

# 21. But where should ownership logic live?

There's a subtle point here.

The Controller can translate:

```text
authenticated HTTP identity
        ↓
application input
```

But the Service should enforce the actual business rule.

For example:

```js
todoService.createTodo({
    userId: req.user.id,
    title: req.body.title
});
```

Then the Service decides:

```text
Can this user create a Todo?
What fields are allowed?
What relationships must exist?
```

---

# 22. Getting a user's Todos

Instead of:

```http
GET /todos
```

returning every Todo in the database, a user-specific application might do:

```js
export const getTodos = asyncHandler(async (req, res) => {
    const todos = await todoService.getTodos({
        userId: req.user.id,
        ...req.query
    });

    return res.status(200).json({
        success: true,
        data: todos
    });
});
```

Now the Service can retrieve only the authenticated user's Todos.

This is a very common real-world pattern.

---

# 23. Ownership on `getTodo`

Suppose:

```http
GET /todos/123
```

Todo `123` belongs to Rahul.

Another user requests it.

The Service should ensure:

```text
Requested Todo
       ↓
belongs to req.user.id?
       ↓
Yes → return
No  → reject
```

For example, conceptually:

```js
todoService.getTodo({
    todoId,
    userId: req.user.id
});
```

Then the Service/repository can enforce ownership.

This is much safer than:

```js
todoService.getTodo(todoId);
```

when the resource is user-owned.

---

# 24. Resource ID alone isn't always enough

This is an important backend design lesson.

A naive implementation:

```js
Todo.findById(todoId)
```

asks:

> Does this Todo exist?

But a secure user-owned operation often needs:

```text
Does this Todo exist?
AND
Does it belong to this user?
```

Conceptually:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

The Repository can implement this query.

---

# 25. Controller responsibility is translation

Think of this:

```js
const { id: todoId } = req.params;
const userId = req.user.id;

const todo = await todoService.getTodo({
    todoId,
    userId
});
```

The Controller translated:

```text
HTTP request
     ↓
application command
```

From:

```text
req.params.id
req.user.id
```

to:

```js
{
    todoId,
    userId
}
```

This is one of the most useful ways to think about Controllers.

---

# 26. Query parameters

CRUD APIs often support:

```http
GET /todos?page=1&limit=20
```

or:

```http
GET /todos?completed=true
```

or:

```http
GET /todos?search=express
```

The Controller can pass:

```js
req.query
```

to the Service:

```js
export const getTodos = asyncHandler(async (req, res) => {
    const todos = await todoService.getTodos({
        userId: req.user.id,
        ...req.query
    });

    return res.status(200).json({
        success: true,
        data: todos
    });
});
```

---

# 27. Don't build MongoDB queries here

Avoid:

```js
const todos = await Todo.find({
    userId: req.user.id,
    completed: req.query.completed
});
```

inside the Controller.

Now your Controller knows:

```text
MongoDB
Mongoose
query syntax
database schema
```

That's not its job.

Instead:

```js
todoService.getTodos({
    userId: req.user.id,
    ...req.query
});
```

---

# 28. Filtering belongs below the Controller

Suppose the request is:

```http
GET /todos?completed=true
```

The Controller passes:

```js
{
    userId,
    completed: "true"
}
```

The Service can decide:

```text
Is "true" valid?
Should it become boolean true?
What filtering rules apply?
```

Then Repository handles:

```text
MongoDB query
```

This separation keeps your architecture clean.

---

# 29. Pagination

A production CRUD endpoint usually needs pagination.

Instead of:

```http
GET /todos
```

returning 100,000 records, use:

```http
GET /todos?page=1&limit=20
```

Controller:

```js
const result = await todoService.getTodos({
    userId: req.user.id,
    page: req.query.page,
    limit: req.query.limit
});
```

Service:

```text
validate pagination
      ↓
calculate skip
      ↓
call repository
      ↓
return records + metadata
```

---

# 30. Pagination response

For example:

```json
{
  "success": true,
  "data": [
    {
      "id": "1",
      "title": "Learn Express"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 120,
    "totalPages": 6
  }
}
```

This is much more useful than returning an enormous array.

---

# 31. Update semantics

When updating a resource, the Controller might receive:

```json
{
  "title": "New title"
}
```

The Service should determine:

```text
Can title be changed?
Can completed be changed?
Can userId be changed?
Can createdAt be changed?
```

The Controller should not contain a giant list of business rules.

---

# 32. Never allow ownership fields to be freely changed

Suppose a Todo contains:

```json
{
  "title": "Learn Node",
  "userId": "rahul123"
}
```

A malicious request could try:

```json
{
  "userId": "admin123"
}
```

Your update operation should not simply update every field from:

```js
req.body
```

The Service/validation layer should whitelist allowed fields.

For example:

```text
Allowed:
title
description
completed

Not allowed:
userId
createdAt
owner
```

This is one of the reasons blindly doing:

```js
Model.findByIdAndUpdate(id, req.body)
```

can be dangerous.

---

# 33. CRUD Controller doesn't mean CRUD-only logic

A resource can have additional operations.

For Todo:

```text
POST /todos
GET /todos
GET /todos/:id
PATCH /todos/:id
DELETE /todos/:id
```

But maybe also:

```text
PATCH /todos/:id/complete
```

or:

```text
POST /todos/:id/archive
```

These are domain operations.

Don't force everything into generic CRUD if the business operation has a clear meaning.

---

# 34. Generic CRUD vs business actions

Consider:

```http
PATCH /orders/123
```

with:

```json
{
  "status": "cancelled"
}
```

This might be technically CRUD.

But cancelling an order could involve:

```text
payment refund
inventory release
notification
audit log
```

That's not merely a generic update.

A better API could be:

```http
POST /orders/123/cancel
```

Then:

```text
cancelOrder Controller
       ↓
orderService.cancelOrder()
```

This is a very important architectural idea:

> **Use CRUD for simple resource manipulation; use explicit actions for meaningful business operations.**

---

# 35. Controller size

A good CRUD Controller might be around:

```text
5–15 lines per action
```

For example:

```js
export const getTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.getTodo(
        req.params.id
    );

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

If your Controller becomes:

```text
300 lines
500 lines
1000 lines
```

that's a warning sign.

Some logic probably belongs elsewhere.

# 36. A useful layer test

Whenever you write code, ask:

### Question 1

Does this code deal with:

```text
req
res
cookies
HTTP status
headers
```

If yes → likely **Controller**.

### Question 2

Does this code implement:

```text
business rules
workflows
application decisions
```

If yes → likely **Service**.

### Question 3

Does this code deal with:

```text
MongoDB
Mongoose
queries
database persistence
```

If yes → likely **Repository**.

This simple test will help you a lot.

# 37. CRUD Controller architecture

Here's the complete picture:

```text
                  CLIENT
                    │
                    ▼
              POST /todos
                    │
                    ▼
                  ROUTE
                    │
                    ▼
             requireAuth
                    │
                    ▼

                    │

           │                 │

                    │
                    ▼
            TODO REPOSITORY
                    │

```

Response:

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
res.status()
res.json()
   ↓
Client
```

Don't memorize the entire code.

Remember these five patterns:

### Create

```js
const result = await service.create(req.body);
```

### List

```js
const result = await service.getAll(req.query);
```

### Get one

```js
const result = await service.getOne(req.params.id);
```

### Update

```js
const result = await service.update(
    req.params.id,
    req.body
);
```

### Delete

```js
await service.delete(req.params.id);
```

Then wrap them with:

```js
asyncHandler(...)
```

and return an appropriate HTTP response.

# 39. Your CRUD Controller checklist

Before considering a CRUD Controller complete, check:

```text
□ create operation exists
□ list operation exists
□ get-one operation exists
□ update operation exists
□ delete operation exists

□ Controller doesn't access MongoDB
□ Controller doesn't contain business logic
□ Controller uses asyncHandler
□ Controller passes data to Service
□ Controller returns appropriate HTTP status
□ Sensitive data isn't exposed
□ Ownership is enforced
□ Authentication is handled by middleware
□ Authorization is enforced appropriately
```

# 40. The most important lesson

The biggest idea from this lesson isn't CRUD itself.

It's this:

> **A Controller is an adapter between HTTP and your application layer.**

For example:

```text
HTTP:

PATCH /todos/123

{
    "completed": true
}
```

Controller converts it into:

```js
todoService.updateTodo(
    "123",
    {
        completed: true
    }
);
```

The Service handles the meaning of that operation.

The Repository handles persistence.

Then the result comes back:

```text
Repository
    ↓
Service
    ↓
Controller
    ↓
HTTP 200
```

Once this mental model becomes natural, creating Controllers for:

```text
users
todos
products
courses
posts
orders
comments
```

becomes much easier.
