# Lesson 11.18 — Controller Input Transformation

In the previous lesson, we learned the CRUD Controller pattern.

Now we're going to learn something **very important in real backend development**:

> How should a Controller take raw HTTP input and convert it into clean input for the Service?

A request can contain data in several places:

```text
req.body
req.params
req.query
req.user
req.cookies
req.headers
```

The Controller sits at the HTTP boundary, so it is responsible for understanding these HTTP-specific objects.

---

# 1. Why input transformation matters

Suppose the client sends:

```http
PATCH /api/v1/todos/123?notify=true
```

with:

```json
{
  "title": "Learn Controllers"
}
```

and authentication middleware has already added:

```js
req.user = {
    id: "user123",
    role: "user"
};
```

The Controller sees:

```text
req.params.id
req.query.notify
req.body.title
req.user.id
```

But your Service shouldn't need to understand Express.

Instead of doing this:

```js
todoService.updateTodo(req, res);
```

we want:

```js
todoService.updateTodo({
    todoId,
    userId,
    title,
    notify
});
```

That's **input transformation**.

---

# 2. The Controller as a translator

Think about the Controller like a translator:

```text
                HTTP WORLD
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     params       body        query
        │           │           │
        └───────────┼───────────┘
                    ↓
               CONTROLLER
                    ↓
             Clean Service Input
                    ↓
                 SERVICE
```

The Controller translates:

```text
Express-specific request
        ↓
application-specific input
```

This is one of the most important Controller concepts.

---

# 3. `req.body`

`req.body` contains data sent in the request body.

For example:

```http
POST /api/v1/todos
```

with:

```json
{
  "title": "Learn Node.js",
  "description": "Study backend development"
}
```

Then:

```js
req.body
```

contains:

```js
{
    title: "Learn Node.js",
    description: "Study backend development"
}
```

---

# 4. Using `req.body`

A simple Controller:

```js
export const createTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.createTodo(req.body);

    return res.status(201).json({
        success: true,
        data: todo
    });
});
```

This works.

But there is a potential problem.

You're passing the **entire body** into your Service.

That may not always be desirable.

---

# 5. Why blindly passing `req.body` can be dangerous

Imagine your Todo contains:

```js
{
    title,
    description,
    completed,
    userId,
    createdAt
}
```

The client sends:

```json
{
  "title": "Learn Node",
  "userId": "someone-else",
  "completed": true
}
```

If you blindly trust:

```js
req.body
```

you could accidentally allow fields the client should never control.

This is called **mass assignment** or **over-posting** when unwanted fields are accepted into updates.

So sometimes you should explicitly select the fields you need.

---

# 6. Explicit body transformation

Instead of:

```js
const todo = await todoService.createTodo(req.body);
```

you can write:

```js
const { title, description } = req.body;

const todo = await todoService.createTodo({
    title,
    description
});
```

Now the Controller explicitly controls what enters the application layer.

The request could contain:

```json
{
  "title": "Learn Node",
  "description": "Backend",
  "userId": "attacker",
  "role": "admin"
}
```

but your Service receives only:

```js
{
    title,
    description
}
```

That's much safer.

---

# 7. But don't confuse transformation with validation

This is important.

The Controller can extract:

```js
const { title, description } = req.body;
```

But should it perform all validation?

For example:

```js
if (!title) {
    ...
}

if (title.length < 3) {
    ...
}

if (description.length > 5000) {
    ...
}
```

Usually, in the architecture we're building, validation should be handled by the **validation layer/middleware**.

So:

```text
Controller
    ↓
extract/transform

Validation
    ↓
check correctness

Service
    ↓
business rules
```

These responsibilities should remain separate.

---

# 8. `req.params`

Route:

```js
router.get("/todos/:id", getTodo);
```

Request:

```http
GET /todos/123
```

Then:

```js
req.params
```

is:

```js
{
    id: "123"
}
```

So:

```js
const { id: todoId } = req.params;
```

gives:

```js
todoId === "123";
```

---

# 9. Transforming route parameters

Don't necessarily pass the entire `req.params`:

```js
todoService.getTodo(req.params);
```

Instead:

```js
const { id: todoId } = req.params;

const todo = await todoService.getTodo(todoId);
```

Now the Service receives:

```text
"123"
```

instead of an Express-specific object.

---

# 10. Why not pass `req` to the Service?

Avoid:

```js
await todoService.getTodo(req);
```

This creates a strong dependency between your Service and Express.

Now the Service needs to know:

```text
req.params
req.body
req.user
req.query
```

That's bad separation.

Prefer:

```js
await todoService.getTodo(todoId);
```

or:

```js
await todoService.getTodo({
    todoId,
    userId
});
```

---

# 11. `req.query`

Query parameters appear after `?`.

Example:

```http
GET /todos?page=2&limit=20&completed=true
```

Then:

```js
req.query
```

looks approximately like:

```js
{
    page: "2",
    limit: "20",
    completed: "true"
}
```

Notice something important:

> Query parameters arrive as strings.

---

# 12. Why query parameters are strings

HTTP URLs are text.

So:

```http
?page=2
```

doesn't automatically mean:

```js
page === 2
```

It generally arrives as:

```js
page === "2"
```

Similarly:

```http
?completed=true
```

gives:

```js
completed === "true"
```

not:

```js
completed === true
```

This is a very common beginner mistake.

---

# 13. Transform query parameters

Suppose your Service expects:

```js
{
    page: 2,
    limit: 20,
    completed: true
}
```

The Controller can transform the raw query:

```js
const page = Number(req.query.page ?? 1);
const limit = Number(req.query.limit ?? 20);

const completed =
    req.query.completed === undefined
        ? undefined
        : req.query.completed === "true";
```

Then:

```js
const todos = await todoService.getTodos({
    page,
    limit,
    completed
});
```

Now the Service receives meaningful values.

---

# 14. But where should query validation happen?

Suppose:

```http
GET /todos?page=hello
```

Then:

```js
Number("hello")
```

becomes:

```text
NaN
```

You don't want invalid data silently flowing through your application.

That's where validation becomes important.

A good architecture might be:

```text
Request
   ↓
Validation middleware
   ↓
Controller transformation
   ↓
Service
```

or:

```text
Request
   ↓
Controller extraction
   ↓
Schema validation
   ↓
Service
```

The exact ordering depends on your architecture.

The important point is:

> **Transformation and validation are related, but they are not the same responsibility.**

---

# 15. `req.user`

This one is especially important.

`req.user` usually does **not** come directly from the client.

Authentication middleware creates it.

For example:

```js
req.user = {
    id: user.id,
    role: user.role
};
```

Then a Controller can use:

```js
req.user.id
```

---

# 16. Example: create a Todo for current user

```js
export const createTodo = asyncHandler(async (req, res) => {
    const { title, description } = req.body;

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title,
        description
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
});
```

Notice what happened.

The client sends:

```json
{
  "title": "Learn Express",
  "description": "Study middleware"
}
```

The server adds:

```js
userId: req.user.id
```

So the application input becomes:

```js
{
    userId: "authenticated-user-id",
    title: "Learn Express",
    description: "Study middleware"
}
```

---

# 17. Why is this better?

Because the server controls ownership.

Don't depend on:

```json
{
  "userId": "123"
}
```

from the client.

The client could send:

```json
{
  "userId": "456"
}
```

The server should determine identity from authentication:

```js
req.user.id
```

This is a fundamental backend security principle.

---

# 18. `req.cookies`

Cookies are another HTTP input source.

For example, suppose authentication uses:

```text
refreshToken
```

stored in an HTTP-only cookie.

Then:

```js
req.cookies.refreshToken
```

might contain the token.

A Controller could do:

```js
export const refreshToken = asyncHandler(async (req, res) => {
    const { refreshToken } = req.cookies;

    const result = await authService.refreshToken(refreshToken);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

The Controller extracts the cookie and passes it to the Service.

---

# 19. Don't make the Service depend on `req.cookies`

Avoid:

```js
authService.refreshToken(req);
```

Instead:

```js
authService.refreshToken(refreshToken);
```

Why?

Because the Service doesn't care where the token came from.

It could come from:

```text
cookie
header
mobile client
another service
test
```

The Service only needs the token.

---

# 20. `req.headers`

HTTP headers are another input source.

For example:

```http
Authorization: Bearer eyJ...
```

You might see:

```js
req.headers.authorization
```

Usually, authentication middleware handles this.

The Controller shouldn't normally parse JWT authorization headers itself.

Instead:

```text
Authorization header
        ↓
Authentication middleware
        ↓
verify token
        ↓
req.user
        ↓
Controller
```

This keeps authentication logic in the correct layer.

---

# 21. Controller should consume authentication context

Once middleware has done its job:

```js
req.user
```

might contain:

```js
{
    id: "user123",
    role: "admin"
}
```

The Controller can safely consume the context:

```js
const userId = req.user.id;
```

It shouldn't reimplement:

```text
extract token
decode token
verify token
load user
check token expiration
```

That's authentication middleware/service responsibility.

---

# 22. Combining multiple input sources

This is where Controller input transformation becomes powerful.

Suppose:

```http
PATCH /todos/123?notify=true
```

Body:

```json
{
  "title": "Learn Controllers"
}
```

Authenticated user:

```js
req.user = {
    id: "user123"
};
```

The Controller can transform all of that:

```js
export const updateTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;
    const { title } = req.body;
    const { notify } = req.query;

    const todo = await todoService.updateTodo({
        todoId,
        userId: req.user.id,
        title,
        notify: notify === "true"
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

Now look at the Service input:

```js
{
    todoId: "123",
    userId: "user123",
    title: "Learn Controllers",
    notify: true
}
```

That is much cleaner than passing Express's entire request object.

---

# 23. This is the real purpose of a Controller

The Controller is converting:

```text
HTTP representation
```

into:

```text
Application command
```

For example:

```text
PATCH /todos/123?notify=true
```

plus:

```json
{
    "title": "Learn Controllers"
}
```

becomes:

```js
{
    todoId: "123",
    userId: "user123",
    title: "Learn Controllers",
    notify: true
}
```

The Service can now work with normal JavaScript data.

---

# 24. A very useful pattern

You can explicitly create an input object:

```js
const input = {
    todoId,
    userId: req.user.id,
    title,
    notify
};
```

Then:

```js
const todo = await todoService.updateTodo(input);
```

This makes the Controller very readable.

---

# 25. Don't over-transform

There's also a danger of doing too much.

For example, don't turn your Controller into:

```js
const input = {
    title: req.body.title.trim().toLowerCase(),
    page: parseInt(req.query.page, 10),
    ...
};
```

and then perform dozens of business decisions.

You need a boundary.

A useful rule:

```text
HTTP-specific transformation
        ↓
Controller

Business transformation
        ↓
Service
```

---

# 26. Example: title normalization

Suppose your application wants:

```text
"   Learn Node   "
```

to become:

```text
"Learn Node"
```

Where should that happen?

It depends on the rule.

If it's simply an HTTP/input normalization step, you could do it before the Service.

But if:

> Every Todo title must always be normalized regardless of where it comes from

then this is a **business/application rule**, and it belongs closer to the Service/domain layer.

This distinction becomes important when you later have:

```text
HTTP API
background jobs
CLI
message queues
scheduled tasks
```

All of them may call the same Service.

---

# 27. Why this matters for future architecture

Imagine your Todo creation can happen through:

```text
REST API
     ↓
Controller
     ↓
Service

Background Job
     ↓
Service

Admin CLI
     ↓
Service
```

If the important business logic lives only in the Controller:

```text
REST API works
Background Job doesn't
CLI doesn't
```

But if the Controller only performs HTTP transformation:

```text
REST
 ↓
Controller
 ↓
Service
```

and:

```text
Background Job
 ↓
Service
```

then the business logic is reusable.

That's a major benefit of layered architecture.

---

# 28. `req.body` → command object

A very useful pattern is:

```js
const input = {
    title: req.body.title,
    description: req.body.description,
    userId: req.user.id
};
```

Then:

```js
await todoService.createTodo(input);
```

Think:

```text
req.body
   +
req.user
   +
req.params
   +
req.query
   ↓
Controller
   ↓
Command/Input Object
   ↓
Service
```

---

# 29. Example: Create User

Suppose:

```http
POST /users
```

Body:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "secret"
}
```

Controller:

```js
export const createUser = asyncHandler(async (req, res) => {
    const { name, email, password } = req.body;

    const user = await userService.createUser({
        name,
        email,
        password
    });

    return res.status(201).json({
        success: true,
        data: user
    });
});
```

Notice:

```text
req.body
```

is converted into:

```js
{
    name,
    email,
    password
}
```

The Service can then handle application logic such as password processing.

---

# 30. Example: Get user's Todos

Request:

```http
GET /todos?page=2&limit=10
```

Authenticated user:

```js
req.user.id
```

Controller:

```js
export const getTodos = asyncHandler(async (req, res) => {
    const { page = "1", limit = "10" } = req.query;

    const result = await todoService.getTodos({
        userId: req.user.id,
        page: Number(page),
        limit: Number(limit)
    });

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

The Service gets:

```js
{
    userId: "user123",
    page: 2,
    limit: 10
}
```

That's a clean application input.

---

# 31. Default values

Controllers often need reasonable defaults.

For example:

```js
const {
    page = "1",
    limit = "20"
} = req.query;
```

Then:

```js
Number(page)
Number(limit)
```

becomes:

```text
page → 1
limit → 20
```

But remember:

> Defaults are not the same as validation.

You still need to make sure:

```text
page > 0
limit > 0
limit <= maximum
```

is enforced appropriately.

---

# 32. Why maximum limits matter

A client could send:

```http
GET /todos?limit=1000000
```

If your backend blindly accepts that, it could request a huge amount of data.

So production APIs usually have a maximum:

```text
minimum limit = 1
maximum limit = 100
```

This is typically enforced by validation/service logic.

The Controller's job is to turn:

```text
"100"
```

into:

```js
100
```

and pass it onward.

---

# 33. Never trust HTTP input

Everything coming from the client should be considered untrusted:

```text
req.body
req.params
req.query
req.cookies
req.headers
```

Even:

```text
req.user
```

should only be trusted because your authentication middleware established it.

The basic security mindset is:

```text
Client input
     ↓
UNTRUSTED
     ↓
Validation / authorization / business rules
     ↓
Trusted application state
```

---

# 34. Don't return raw request data

Avoid debugging code like:

```js
return res.json(req.body);
```

in production endpoints.

The response should represent your API contract, not simply echo client input.

Prefer:

```js
return res.status(201).json({
    success: true,
    data: todo
});
```

---

# 35. Input transformation and DTOs

You may hear the term:

> DTO — Data Transfer Object

A DTO is simply a structured object used to transfer data between layers.

For example:

```js
const createTodoInput = {
    userId: req.user.id,
    title: req.body.title,
    description: req.body.description
};
```

Then:

```js
todoService.createTodo(createTodoInput);
```

You don't necessarily need a separate DTO class in a Node.js application.

A plain object is often enough.

---

# 36. Input object naming

Instead of:

```js
const data = {
    ...
};
```

you can use meaningful names:

```js
const createTodoInput = {
    ...
};
```

or:

```js
const updateTodoInput = {
    ...
};
```

This makes code easier to understand.

---

# 37. Controller with explicit transformation

Here's a strong example:

```js
export const updateTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const { title, description, completed } = req.body;

    const updateTodoInput = {
        todoId,
        userId: req.user.id,
        title,
        description,
        completed
    };

    const todo = await todoService.updateTodo(
        updateTodoInput
    );

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

This is extremely readable.

Anyone looking at it can immediately understand:

```text
What comes from URL?
What comes from body?
What comes from authentication?
What goes into Service?
```

# 38. What about `req.cookies`?

Suppose:

```http
POST /auth/refresh
```

and the refresh token is stored in:

```text
HTTP-only cookie
```

Controller:

```js
export const refreshToken = asyncHandler(async (req, res) => {
    const { refreshToken } = req.cookies;

    const tokens = await authService.refreshToken(
        refreshToken
    );

    return res.status(200).json({
        success: true,
        data: tokens
    });
});
```

The Controller knows:

```text
"The token came from a cookie."
```

The Service only knows:

```text
"Here is a refresh token."
```

That's good separation.

---

# 39. What about headers?

Suppose you have:

```http
X-Request-ID: abc123
```

A Controller might extract:

```js
const requestId = req.headers["x-request-id"];
```

and pass it to a Service if the application actually needs it.

But don't extract every header just because you can.

Only transform HTTP data that the application actually needs.

---

# 40. Avoid unnecessary transformation

Bad:

```js
const input = {
    body: req.body,
    params: req.params,
    query: req.query,
    headers: req.headers,
    cookies: req.cookies,
    user: req.user
};
```

You're basically passing the HTTP request into another object.

Instead:

```js
const input = {
    todoId: req.params.id,
    userId: req.user.id,
    title: req.body.title
};
```

Only pass what the Service needs.

---

# 41. A clean Controller boundary

Think about this rule:

> **The Service should not have to know that Express exists.**

Good:

```js
todoService.updateTodo({
    todoId,
    userId,
    title
});
```

Bad:

```js
todoService.updateTodo(req, res);
```

Good:

```js
authService.refreshToken(refreshToken);
```

Bad:

```js
authService.refreshToken(req.cookies.refreshToken);
```

inside the Service.

The latter still leaks HTTP knowledge into the Service.

---

# 42. Controller transformation pattern

The pattern is:

```text
                 EXPRESS
                    │
                    ▼
        ┌──────────────────────┐
        │      CONTROLLER      │
        │                      │
        │ req.params           │
        │ req.body             │
        │ req.query            │
        │ req.user             │
        │ req.cookies          │
        │ req.headers          │
        └──────────┬───────────┘
                   │
                   ▼
             INPUT OBJECT
                   │
                   ▼
                SERVICE
```

This is the mental model I want you to remember.

# 45. What should happen if input is missing?

Suppose:

```http
POST /todos
```

with:

```json
{}
```

The Controller might extract:

```js
const { title } = req.body;
```

and the validation layer should reject the request.

For example:

```text
Request
  ↓
Validation middleware
  ↓
400 Bad Request
```

The Controller might never even execute.

That's a good thing.

---

# 46. Why middleware should validate before Controller

Consider:

```text
POST /todos
```

Body:

```json
{
  "title": 12345
}
```

If your schema says:

```text
title must be a string
```

the validation middleware can reject it before your Controller performs application work.

Flow:

```text
Request
   ↓
Validation
   ↓
Invalid → 400
```

Only valid requests reach:

```text
Controller
   ↓
Service
```

This keeps Controllers smaller.

---

# 47. Controller should not become a validation monster

Avoid:

```js
export const createTodo = asyncHandler(async (req, res) => {
    if (!req.body.title) {
        ...
    }

    if (typeof req.body.title !== "string") {
        ...
    }

    if (req.body.title.length < 3) {
        ...
    }

    if (req.body.title.length > 100) {
        ...
    }

    // 100 more lines...
});
```

That's exactly the kind of Controller that becomes difficult to maintain.

Use validation middleware/schema validation instead.

---

# 48. Controller transformation vs sanitization

These are also different concepts.

### Transformation

```text
"2" → 2
"true" → true
req.params.id → todoId
req.user.id → userId
```

### Validation

```text
Is page a positive number?
Is title required?
Is email valid?
```

### Sanitization

```text
Remove dangerous/unwanted input
Normalize input where appropriate
```

Don't treat these three concepts as identical.

You'll see these distinctions again in your security and validation phases.

---

# 49. One more important rule: never mutate `req`

Avoid doing things like:

```js
req.body.title = req.body.title.trim();
```

inside the Controller unless your architecture explicitly uses that pattern.

Prefer:

```js
const { title } = req.body;

const input = {
    title: title.trim()
};
```

Even better, let your validation/normalization layer handle such transformations when appropriate.

Why?

Because mutating the request can make debugging and middleware behavior harder to understand.

---

# 50. Final mental model

When a request arrives, ask:

### 1. Where is the data?

```text
body?
params?
query?
user?
cookies?
headers?
```

### 2. What does my Service actually need?

```text
todoId?
userId?
title?
page?
limit?
```

### 3. Transform only that data.

```js
const input = {
    todoId,
    userId,
    title
};
```

### 4. Call the Service.

```js
const result = await todoService.updateTodo(input);
```

### 5. Return the HTTP response.

```js
return res.status(200).json({
    success: true,
    data: result
});
```

# 🧠 Lesson 11.18 Cheat Sheet

## HTTP input sources

```text
req.body
    ↓
JSON/form request body

req.params
    ↓
/users/:id

req.query
    ↓
/users?page=2

req.user
    ↓
authentication middleware

req.cookies
    ↓
browser cookies

req.headers
    ↓
HTTP headers
```

## Controller job

```text
HTTP Request
     ↓
Extract
     ↓
Transform
     ↓
Create clean input
     ↓
Service
     ↓
Result
     ↓
HTTP Response
```

## Good

```js
const input = {
    todoId: req.params.id,
    userId: req.user.id,
    title: req.body.title
};

const todo = await todoService.updateTodo(input);
```

## Bad

```js
await todoService.updateTodo(req);
```

## Remember

```text
Controller = HTTP boundary

Service = Application/business logic

Repository = Database access
```
