# Lesson 11.19 — Refactoring Fat Controllers

In the previous lessons, we learned that a Controller is an **HTTP translator**: it takes HTTP input and turns it into application input, then turns the application's result back into an HTTP response.

The Phase 11 roadmap specifically places **“Refactoring fat controllers”** at Lesson 11.19.

Today we're going to understand one of the most common problems beginners face:

> **The Controller starts doing everything.**

And then suddenly one Controller becomes 200, 400, or even 800 lines long.

---

# 1. What is a fat Controller?

A **fat Controller** is a Controller containing too much logic.

For example:

```js
export const login = asyncHandler(async (req, res) => {
    const { email, password } = req.body;

    const user = await User.findOne({ email });

    if (!user) {
        throw new AppError("Invalid credentials", 401);
    }

    const passwordMatches = await bcrypt.compare(
        password,
        user.password
    );

    if (!passwordMatches) {
        throw new AppError("Invalid credentials", 401);
    }

    const accessToken = jwt.sign(
        { userId: user._id },
        process.env.ACCESS_TOKEN_SECRET
    );

    const refreshToken = jwt.sign(
        { userId: user._id },
        process.env.REFRESH_TOKEN_SECRET
    );

    await RefreshToken.create({
        userId: user._id,
        token: refreshToken
    });

    await sendEmail(user.email, "Login notification");

    return res.status(200).json({
        success: true,
        accessToken,
        refreshToken
    });
});
```

This Controller is doing **far too much**.

It is handling:

```text
HTTP input
 ↓
database query
 ↓
password verification
 ↓
JWT generation
 ↓
database write
 ↓
email
 ↓
HTTP response
```

That's a fat Controller.

---

# 2. Why is this a problem?

At first, this may look convenient.

Everything is in one place.

But as your application grows:

```text
Controller
    ↓
50 lines
    ↓
150 lines
    ↓
300 lines
    ↓
500 lines
```

Now you have a maintenance problem.

Suppose you need to change password hashing.

You need to search through Controllers.

Suppose you change token generation.

Again, search through Controllers.

Suppose another feature needs the same logic.

You might copy-paste it.

That's how backend code becomes difficult to maintain.

---

# 3. The architecture we want

Your starter's architecture is designed around separating these responsibilities.

The roadmap explicitly describes the professional transformation as:

```text
Controller
    ↓
authService.login()
    ↓
repository
    ↓
database
```

rather than putting all login operations inside the Controller.

So instead of:

```text
Controller
 ├── database
 ├── password
 ├── JWT
 ├── business rules
 ├── email
 └── response
```

we want:

```text
Controller
     ↓
Service
     ↓
Repository
     ↓
Database
```

---

# 4. The Controller's real job

A Controller should primarily deal with:

```text
HTTP
```

That means things such as:

```js
req.body
req.params
req.query
req.user
req.cookies
```

and:

```js
res.status(...)
res.json(...)
res.cookie(...)
```

That's its natural boundary.

Remember our previous mental model:

```text
HTTP request
     ↓
Controller
     ↓
Application
     ↓
Controller
     ↓
HTTP response
```

---

# 5. What should NOT normally live in the Controller?

Avoid putting things like:

```text
MongoDB queries
Password hashing
Password comparison
JWT creation
Complex business rules
Email implementation
Large calculations
Transactions
Complex ownership rules
```

directly into the Controller.

Those responsibilities belong in other layers.

---

# 6. Refactoring example

Let's take the fat login Controller.

### Before

```js
export const login = asyncHandler(async (req, res) => {
    const { email, password } = req.body;

    const user = await User.findOne({ email });

    if (!user) {
        throw new AppError("Invalid credentials", 401);
    }

    const passwordMatches = await bcrypt.compare(
        password,
        user.password
    );

    if (!passwordMatches) {
        throw new AppError("Invalid credentials", 401);
    }

    const accessToken = generateAccessToken(user);
    const refreshToken = generateRefreshToken(user);

    await RefreshToken.create({
        userId: user._id,
        token: refreshToken
    });

    return res.status(200).json({
        success: true,
        accessToken,
        refreshToken
    });
});
```

The Controller knows too much.

---

# 7. First step — extract the input

Start by making the HTTP input clear:

```js
const { email, password } = req.body;
```

Then create an application input:

```js
const loginInput = {
    email,
    password
};
```

---

# 8. Second step — call the Service

Now:

```js
const result = await authService.login(loginInput);
```

The Controller doesn't need to know:

```text
How did login happen?
```

It only needs:

```text
"Login this user."
```

---

# 9. Refactored Controller

Now the Controller becomes:

```js
export const login = asyncHandler(async (req, res) => {
    const { email, password } = req.body;

    const result = await authService.login({
        email,
        password
    });

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

That's dramatically smaller.

And more importantly:

> **It's easier to understand.**

---

# 10. Where did the complexity go?

It didn't disappear.

We moved it to the correct layer.

```text
Controller
    ↓
authService.login()
    ↓
userRepository.findByEmail()
    ↓
passwordService.compare()
    ↓
tokenService.generate()
    ↓
repository.saveRefreshToken()
```

Now each layer has a clearer responsibility.

---

# 11. Controller vs Service

This distinction is extremely important.

### Controller

Answers:

> How does the client communicate with the application?

### Service

Answers:

> What should the application actually do?

For example:

```text
POST /auth/login
```

The Controller handles:

```text
req.body
HTTP status
HTTP response
```

The Service handles:

```text
find user
verify password
generate tokens
save refresh token
```

---

# 12. Controller vs Repository

The Repository answers:

> How do I access the database?

For example:

```js
userRepository.findByEmail(email);
```

The Controller should **not** do:

```js
User.findOne({ email });
```

The Service should coordinate the operation:

```js
const user = await userRepository.findByEmail(email);
```

So:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
MongoDB
```

This is exactly the layered architecture we're building toward in later phases. The roadmap describes the Repository as the layer through which Services request database work.

---

# 13. Controller vs validation

Another common mistake is putting validation inside the Controller.

Bad:

```js
export const createTodo = asyncHandler(async (req, res) => {

    if (!req.body.title) {
        throw new AppError("Title required", 400);
    }

    if (typeof req.body.title !== "string") {
        throw new AppError("Invalid title", 400);
    }

    if (req.body.title.length < 3) {
        throw new AppError("Title too short", 400);
    }

    // ...
});
```

This makes the Controller fat again.

Your Phase 9 architecture already establishes a separate validation boundary:

```text
req.body
   ↓
validation
   ↓
controller
```

The starter roadmap specifically calls out reusable validation middleware and validation architecture.

---

# 14. Controller vs authentication

Don't put JWT verification inside every Controller.

Bad:

```js
export const getProfile = asyncHandler(async (req, res) => {
    const token = req.headers.authorization;

    // verify JWT
    // decode JWT
    // check expiration
    // find user
    // ...

    const profile = ...
});
```

Instead:

```text
Authorization header
        ↓
auth middleware
        ↓
JWT verification
        ↓
req.user
        ↓
Controller
```

Then:

```js
export const getProfile = asyncHandler(async (req, res) => {
    const user = await userService.getProfile(req.user.id);

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

Much cleaner.

---

# 15. Controller vs authorization

Suppose only admins can delete users.

Don't build a huge check inside every Controller.

Instead:

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Controller
   ↓
Service
```

For example:

```js
router.delete(
    "/:id",
    requireAuth,
    requireRole("admin"),
    deleteUser
);
```

Then:

```js
export const deleteUser = asyncHandler(async (req, res) => {
    await userService.deleteUser(req.params.id);

    return res.status(204).send();
});
```

The Controller stays focused.

---

# 16. The "Can I move this?" question

When you see a Controller line, ask:

> **Does this line exist because of HTTP?**

If yes, it probably belongs in the Controller.

Example:

```js
const { id } = req.params;
```

Yes.

```js
res.status(200).json(...);
```

Yes.

But:

```js
await User.findOne(...);
```

No.

Move it toward Repository.

---

# 17. Another useful question

Ask:

> **Would this code still be useful if tomorrow I stopped using Express?**

For example:

```js
const { id } = req.params;
```

No.

That's Express-specific.

But:

```js
const user = await userRepository.findByEmail(email);
```

Yes.

That operation could be used by:

```text
REST API
CLI
background job
GraphQL
tests
```

That's a good sign that it belongs outside the Controller.

---

# 18. Fat Controller example — Todo

Imagine:

```js
export const updateTodo = asyncHandler(async (req, res) => {
    const { id } = req.params;

    const todo = await Todo.findById(id);

    if (!todo) {
        throw new AppError("Todo not found", 404);
    }

    if (todo.userId.toString() !== req.user.id) {
        throw new AppError("Forbidden", 403);
    }

    if (req.body.title) {
        todo.title = req.body.title.trim();
    }

    if (req.body.completed !== undefined) {
        todo.completed = req.body.completed;
    }

    await todo.save();

    await createAuditLog({
        userId: req.user.id,
        action: "TODO_UPDATED",
        resourceId: id
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

At first glance, it looks reasonable.

But it contains:

```text
database access
ownership rule
data transformation
business logic
persistence
audit logging
HTTP response
```

That's too much.

---

# 19. Refactor it

Controller:

```js
export const updateTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.updateTodo({
        todoId,
        userId: req.user.id,
        ...req.body
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

Now the Controller is tiny.

The Service can coordinate:

```text
todoService.updateTodo()
        ↓
check ownership
        ↓
validate business rules
        ↓
repository.update()
        ↓
audit service
        ↓
return Todo
```

---

# 20. But be careful with `...req.body`

We learned in Lesson 11.18 that blindly passing the entire body can be dangerous.

So a better Controller is:

```js
export const updateTodo = asyncHandler(async (req, res) => {
    const { id: todoId } = req.params;

    const {
        title,
        description,
        completed
    } = req.body;

    const todo = await todoService.updateTodo({
        todoId,
        userId: req.user.id,
        title,
        description,
        completed
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

Now the Controller explicitly controls the input boundary.

---

# 21. What about business rules?

Suppose the rule is:

> A completed Todo cannot be edited.

Don't write this in the Controller:

```js
if (todo.completed) {
    throw new AppError(
        "Completed todo cannot be edited",
        400
    );
}
```

That's a business rule.

Put it in the Service:

```js
if (todo.completed) {
    throw new AppError(
        "Completed todo cannot be edited",
        400
    );
}
```

Why?

Because another part of your application might update a Todo without going through this Controller.

You want the business rule to remain enforced.

# 22. Service becomes the application's brain

A useful mental model:

```text
Controller
   ↓
"Someone requested this operation."

Service
   ↓
"Here's what the application should do."

Repository
   ↓
"Here's how I persist/retrieve the data."
```

This is why the roadmap gives Services their own full phase.

# 23. Fat Controller smell #1 — database queries

If you see:

```js
User.findOne(...)
```

```js
Todo.findById(...)
```

```js
Todo.find(...)
```

inside a Controller, stop and ask:

> Should this be Repository work?

Usually, yes.

---

# 24. Fat Controller smell #2 — password logic

If you see:

```js
bcrypt.hash(...)
```

or:

```js
bcrypt.compare(...)
```

inside many Controllers, that's a smell.

Your architecture already has a dedicated:

```text
password.service.js
```

in the starter structure.

That is exactly the kind of responsibility that should be isolated.

---

# 25. Fat Controller smell #3 — JWT logic

If your Controller contains:

```js
jwt.sign(...)
jwt.verify(...)
```

you should question whether token logic belongs there.

Authentication-related operations should be handled through the authentication architecture rather than duplicated across Controllers.

---

# 26. Fat Controller smell #4 — email

Bad:

```js
await transporter.sendMail({
    to: user.email,
    subject: "Welcome",
    html: ...
});
```

inside:

```text
user.controller.js
```

Your starter separates mail functionality:

```text
mail/
├── mailSender.js
├── renderTemplate.js
└── templates/
```

so email should be handled through the appropriate application/service layer.

---

# 27. Fat Controller smell #5 — huge `try/catch`

This:

```js
export const createUser = async (req, res, next) => {
    try {
        // 100 lines
    } catch (error) {
        next(error);
    }
};
```

is often a sign that the Controller is doing too much.

With the `asyncHandler` architecture from your roadmap:

```js
export const createUser = asyncHandler(async (req, res) => {
    // focused controller logic
});
```

errors can flow into the global error architecture. The intended flow is:

```text
Controller throws
      ↓
asyncHandler
      ↓
next(error)
      ↓
error middleware
      ↓
JSON response
```

---

# 28. Fat Controller smell #6 — multiple business operations

Suppose:

```js
createOrder()
```

contains:

```text
check inventory
calculate price
apply coupon
charge payment
create order
send email
create audit log
```

That's a huge warning sign.

The Controller should probably be:

```js
export const createOrder = asyncHandler(async (req, res) => {
    const order = await orderService.createOrder({
        userId: req.user.id,
        ...req.body
    });

    return res.status(201).json({
        success: true,
        data: order
    });
});
```

The Service coordinates the actual business operation.

---

# 29. Don't make Services fat either

Here's an important warning.

We're not saying:

> "Move every line from the Controller into one giant Service."

That creates:

```text
Fat Controller
     ↓
Fat Service
     ↓
Everything is still messy
```

Instead, Services can use other specialized components.

For example:

```text
authService
   ├── userRepository
   ├── passwordService
   ├── tokenService
   └── refreshTokenRepository
```

This is much healthier.

---

# 30. Refactoring is about responsibility

The goal isn't:

```text
Controller = 10 lines
```

The goal is:

```text
Controller
    ↓
HTTP responsibility

Service
    ↓
Application/business responsibility

Repository
    ↓
Persistence responsibility
```

A Controller can sometimes be 30 lines.

That's not automatically bad.

The question is:

> **Does each line belong to the Controller's responsibility?**

---

# 31. A practical refactoring process

When you encounter a large Controller, don't rewrite everything at once.

Use this process.

### Step 1

Read the Controller completely.

### Step 2

Mark every line as:

```text
HTTP
VALIDATION
BUSINESS
DATABASE
AUTH
EMAIL
UTILITY
```

### Step 3

Keep HTTP-related code.

### Step 4

Move database work to Repository.

### Step 5

Move business logic to Service.

### Step 6

Move reusable specialized logic to dedicated services/utilities.

### Step 7

Keep the Controller as the HTTP adapter.

# 32. Example classification

Suppose you have:

```js
const { email, password } = req.body;
```

→ **HTTP**

```js
const user = await User.findOne({ email });
```

→ **Repository**

```js
const valid = await bcrypt.compare(password, user.password);
```

→ **Password/Auth service**

```js
if (!valid) {
    throw new AppError("Invalid credentials", 401);
}
```

→ **Authentication/business logic**

```js
return res.status(200).json(...);
```

→ **HTTP**

Now the refactoring becomes obvious.

# 34. How small should a Controller be?

Don't use an arbitrary rule like:

> "Every Controller must be exactly 10 lines."

Instead, aim for something like:

```js
export const createTodo = asyncHandler(async (req, res) => {
    const { title, description } = req.body;

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title,
        description
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
});
```

The Controller:

```text
1. extracts HTTP input
2. creates application input
3. calls Service
4. returns HTTP response
```

That's excellent.

---

# 35. A very useful test

When reviewing a Controller, try saying:

> "This Controller receives ___, gives it to ___, and returns ___."

For example:

> "This Controller receives the Todo ID and request body, gives them to the Todo Service, and returns the updated Todo."

If you can describe it in one sentence, it's probably focused.

If you need to say:

> "It finds the user, checks their password, creates a JWT, updates the database, sends an email, writes an audit log..."

your Controller is probably too fat.

# 🎯 Mini Exercise

Take this Controller:

```js
export const register = asyncHandler(async (req, res) => {
    const { name, email, password } = req.body;

    const existingUser = await User.findOne({ email });

    if (existingUser) {
        throw new AppError("Email already exists", 409);
    }

    const hashedPassword = await bcrypt.hash(password, 12);

    const user = await User.create({
        name,
        email,
        password: hashedPassword
    });

    const token = jwt.sign(
        { userId: user._id },
        process.env.ACCESS_TOKEN_SECRET
    );

    await sendWelcomeEmail(email, name);

    return res.status(201).json({
        success: true,
        data: {
            user,
            token
        }
    });
});
```

Your task is **not to rewrite it immediately**.

First identify each piece:

```text
1. HTTP input
2. Database work
3. Business logic
4. Password logic
5. Token logic
6. Email logic
7. HTTP response
```

Then ask:

```text
Which layer should own each one?
```

If you can correctly classify those seven pieces, you've understood the heart of **fat Controller refactoring**.

### The one sentence to remember

> **Don't make the Controller do the work; make the Controller tell the application what work needs to be done.**
