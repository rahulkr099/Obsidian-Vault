# 2. Our final architecture

We'll use a small `Todo` module.

The architecture is:

```text
                    CLIENT
                      │
                      ▼
                  HTTP Request
                      │
                      ▼
                    ROUTE
                      │
                      ▼
                 MIDDLEWARE
              ┌───────┼────────┐
              │       │        │
             Auth Validation  Rate Limit
              │       │        │
              └───────┼────────┘
                      ▼
                 CONTROLLER
                      │
                      ▼
                   SERVICE
                      │
                      ▼
                 REPOSITORY
                      │
                      ▼
                    MODEL
                      │
                      ▼
                   MONGODB
```

The uploaded architecture describes this same mental model: Route → Middleware → Controller → Service → Repository → Model → MongoDB, with security, validation, errors, logging and other concerns around it.

---

# 3. What exactly does the Controller do?

Our Controller has four major jobs:

```text
1. Read HTTP input
2. Transform it
3. Call the Service
4. Create HTTP response
```

That's it.

Think:

```text
HTTP
 ↓
Controller
 ↓
Application
 ↓
Controller
 ↓
HTTP
```

The Controller is an **HTTP translator**.

# 7. CREATE — `createTodo`

```http
POST /api/v1/todos
```

```json

  "title": "Learn Controllers",
  "description": "Finish Phase 11"
}
```

```js

    id: "user123"

```

```js
export const createTodo = asyncHandler(async (req, res) => {
    const {
        title,
        description
    } = req.body;

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title,
        description
    });

    return res.status(201).json({
        success: true,
        data: todo
```

```text
req.body
   ↓
Controller
   ↓
clean input object
   ↓
Service
   ↓
response
```

Perfect.

# 8. Why `userId` comes from `req.user`

Don't let the client decide ownership.

Don't do this:

```js
const {
    title,
    description,
    userId
} = req.body;
```

Instead:

```js
const {
    title,
    description
} = req.body;

const userId = req.user.id;
```

The server knows who is authenticated.

This becomes especially important when we later build ownership and authorization. The roadmap explicitly emphasizes querying resources using both resource ID and authenticated user ID.

```text
req.query
```

```js

```

# 10. Query parameters are HTTP-specific

The client sends:

```http
GET /todos?page=2&limit=10
```

Express gives:

```js
req.query
```

The Service shouldn't need to know that this came from a URL.

It receives:

```js
{
    page: "2",
    limit: "10"
}
```

or transformed values depending on your validation/processing architecture.

This is exactly why the Controller acts as a boundary.

# 11. READ ONE — `getTodo`

Endpoint:

```http
GET /api/v1/todos/:id
```

Example:

```http
GET /api/v1/todos/abc123
```

Controller:

```js
export const getTodo = asyncHandler(async (req, res) => {
    const {
        id: todoId
    } = req.params;

    const todo = await todoService.getTodo({
        todoId,
        userId: req.user.id
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

This is an important pattern.

We're not simply doing:

```js
todoService.getTodo(todoId);
```

We're giving the Service:

```js
{
    todoId,
    userId
}
```

Why?

Because this is a user-owned resource.

---

# 12. Why both IDs?

Imagine:

```text
Todo A → Rahul
Todo B → User B
```

User B requests:

```http
GET /todos/A
```

If your Repository does:

```js
Todo.findById(todoId);
```

it could return Rahul's Todo.

That's dangerous.

Instead:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

means:

> Find this Todo **only if it belongs to this authenticated user**.

The roadmap specifically highlights this ownership query as an important security concept.

# 16. Now create the routes

Create:

```text
routes/todo.routes.js
```

```js
import { Router } from "express";

import {
    createTodo,
    getTodos,
    getTodo,
    updateTodo,
    deleteTodo
} from "../controllers/todo.controller.js";

import { authMiddleware } from "../middlewares/auth.middleware.js";

const router = Router();

router.use(authMiddleware);

router.post("/", createTodo);

router.get("/", getTodos);

router.get("/:id", getTodo);

router.patch("/:id", updateTodo);

router.delete("/:id", deleteTodo);

export default router;
```

Now the relationship is:

```text
Route
 ↓
Middleware
 ↓
Controller
```

# 19. What happens when something fails?

Suppose:

```http
GET /todos/does-not-exist
```

Repository finds nothing.

Service throws:

```js
throw new AppError(
    "Todo not found",
    404
);
```

The Controller doesn't need:

```js
try/catch
```

because we have:

```js
asyncHandler(...)
```

Flow:

```text
Service throws
     ↓
asyncHandler
     ↓
next(error)
     ↓
Error middleware
     ↓
HTTP 404
```

That's the architecture established in the earlier Error Handling phase.

---

# 20. Controller should not format every error

Don't do this repeatedly:

```js
try {
    ...
} catch (error) {
    return res.status(500).json({
        success: false,
        message: error.message
    });
}
```

inside every Controller.

Instead:

```js
export const getTodo = asyncHandler(async (req, res) => {
    // ...
});
```

and allow the centralized error system to handle failures.

This keeps Controllers clean.

---

# 21. What if validation fails?

Suppose:

```http
POST /todos
```

contains:

```json
{
  "title": 12345
}
```

Your validation middleware should reject it.

Flow:

```text
Request
   ↓
Validation
   ↓
INVALID
   ↓
Error middleware
   ↓
400
```

The Controller doesn't need to know about the invalid request.

This is why validation exists as a separate layer.

---

# 22. What if authentication fails?

Suppose someone requests:

```http
GET /api/v1/todos
```

without a valid access token.

Flow:

```text
Request
   ↓
authMiddleware
   ↓
401 Unauthorized
```

The request doesn't even reach:

```text
Controller
```

That's good architecture.

---

# 23. What if authorization fails?

Suppose a user tries to access another user's Todo.

The Service/authorization layer can reject it:

```text
403 Forbidden
```

or deliberately return:

```text
404 Not Found
```

depending on your API's security design.

The important thing is:

> **The Controller shouldn't become the place where every security rule is manually implemented.**

```js
    const result = await resourceService.getAll({
```

# 29. Your Controller review checklist

Before moving to Phase 12, check every Controller.

### HTTP

```text
□ Reads req.body correctly
□ Reads req.params correctly
□ Reads req.query correctly
□ Uses req.user when needed
□ Handles cookies when needed
```

### Architecture

```text
□ Doesn't query MongoDB
□ Doesn't use Mongoose directly
□ Doesn't contain large business rules
□ Doesn't contain password logic
□ Doesn't generate JWTs unnecessarily
□ Doesn't send emails directly
□ Calls Services
```

### Errors

```text
□ Uses asyncHandler
□ Doesn't duplicate try/catch
□ Allows global error middleware to handle errors
```

### Security

```text
□ Doesn't trust client-supplied userId
□ Doesn't expose sensitive data
□ Doesn't bypass authorization
□ Doesn't blindly spread req.body
```

### Responses

```text
□ Correct status codes
□ Consistent JSON structure
□ Appropriate response data
□ 204 for successful empty deletion where appropriate
```
