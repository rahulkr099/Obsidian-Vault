# Lesson 11.3 — Route vs Controller

In **11.1**, we learned what a controller is.

In **11.2**, we learned why controllers exist.

Now we need to understand one of the most common beginner confusions:

> **What is the difference between a Route and a Controller?**

This distinction is very important because your starter architecture separates:

```text
routes/
controllers/
```

and that separation is intentional.

---

# 1. The simplest answer

Remember this:

```text
Route      → WHERE?
Controller → WHAT?
```

For example:

```http
POST /api/v1/todos
```

The **route** says:

> "A POST request to `/todos` should go here."

The **controller** says:

> "Okay, here's what we should do with this request."

So:

```text
HTTP Request
     ↓
   ROUTE
     ↓
CONTROLLER
     ↓
   Response
```

---

# 2. What is a Route?

A route connects an HTTP request to some handler.

For example:

```js
router.get("/users", getUsers);
```

This says:

```text
GET /users
      ↓
getUsers()
```

The route is basically a **mapping**.

```text
HTTP method + URL
        ↓
   Handler function
```

Examples:

```js
router.get("/users", getUsers);

router.post("/users", createUser);

router.patch("/users/:id", updateUser);

router.delete("/users/:id", deleteUser);
```

The route doesn't need to know all the details of how the user is created or updated.

It just knows:

> **Which handler should receive this request?**

---

# 3. What is a Controller?

The controller is the handler responsible for processing the HTTP operation.

Example:

```js
export const createUser = async (req, res) => {
    const user = await userService.createUser(req.body);

    res.status(201).json({
        success: true,
        data: user
    });
};
```

The controller:

1. reads information from the request
    
2. communicates with the application layer
    
3. prepares the HTTP response
    

---

# 4. Put them together

Suppose we have:

```text
POST /api/v1/users
```

Our route might be:

```js
router.post("/", createUser);
```

And our controller:

```js
export const createUser = async (req, res) => {
    const user = await userService.createUser(req.body);

    res.status(201).json({
        success: true,
        data: user
    });
};
```

The flow is:

```text
POST /api/v1/users
        │
        ▼
user.routes.js
        │
        │ router.post("/", createUser)
        ▼
createUser controller
        │
        ▼
HTTP response
```

---

# 5. Real-world analogy

Imagine a university office.

A student walks in and says:

> "I want to apply for an exam."

The **reception desk** decides:

> "Exam applications go to the examination department."

That's similar to a **Route**.

Then the examination officer handles the actual request.

That's similar to a **Controller**.

```text
Student
   ↓
Reception
   ↓
Exam Officer
```

Backend:

```text
Client
   ↓
Route
   ↓
Controller
```

The reception doesn't process the entire application.

It simply directs the request to the correct place.

---

# 6. Route's responsibility

A route is mainly concerned with:

```text
HTTP method
URL/path
middleware
handler/controller
```

For example:

```js
router.post(
    "/",
    authMiddleware,
    validateCreateUser,
    createUser
);
```

The route is saying:

```text
POST /
 ↓
authenticate
 ↓
validate
 ↓
createUser controller
```

Notice something interesting.

The route can also assemble middleware.

That's one reason route files are useful.

---

# 7. Controller's responsibility

The controller handles the HTTP operation.

For example:

```js
export const createUser = async (req, res) => {

    const user = await userService.createUser({
        name: req.body.name,
        email: req.body.email
    });

    res.status(201).json({
        success: true,
        data: user
    });
};
```

The controller understands things such as:

```text
req.body
req.params
req.query
req.user

res.status()
res.json()
```

These are HTTP/Express concerns.

---

# 8. The easiest comparison

|Route|Controller|
|---|---|
|Defines endpoint|Handles endpoint|
|Maps URL to handler|Executes request handling|
|Knows HTTP method|Works with request/response|
|Connects middleware|Uses request data|
|Usually small|Contains HTTP logic|
|`router.get()`|`getUsers()`|

Think:

```text
Route:
"Who should handle this?"

Controller:
"Here's how this HTTP request should be handled."
```

---

# 9. Example: GET users

### Route

```js
router.get("/", getUsers);
```

### Controller

```js
export const getUsers = async (req, res) => {

    const users = await userService.getUsers();

    res.status(200).json({
        success: true,
        data: users
    });
};
```

The route doesn't know:

```text
how users are retrieved
```

The controller doesn't need to know:

```text
how the URL was matched
```

Each layer has its own job.

---

# 10. Why not combine them?

You can technically do:

```js
router.get("/users", async (req, res) => {
    const users = await User.find();

    res.json(users);
});
```

There's nothing syntactically wrong with this.

For a tiny experiment, it's perfectly fine.

But as the application grows, you'll have:

```text
users
todos
products
orders
payments
notifications
```

and routes start becoming:

```text
hundreds of lines
```

Separating controllers keeps things organized.

# 11. Route file

Imagine:

```text
routes/
└── todo.routes.js
```

It might contain:

```js
import express from "express";

import {
    createTodo,
    getTodos,
    getTodo,
    updateTodo,
    deleteTodo
} from "../controllers/todo.controller.js";

const router = express.Router();

router.post("/", createTodo);
router.get("/", getTodos);
router.get("/:id", getTodo);
router.patch("/:id", updateTodo);
router.delete("/:id", deleteTodo);

export default router;
```

Look at it.

You can immediately see the API:

```text
POST   /
GET    /
GET    /:id
PATCH  /:id
DELETE /:id
```

That's a major benefit.

    // ...

Now the responsibilities are separated:

```text
todo.routes.js
        ↓

        ↓

```

# 13. Add middleware

This is where the architecture becomes more interesting.

Suppose only logged-in users can create todos.

The route can express that very clearly:

```js
router.post(
    "/",
    authMiddleware,
    createTodo
);
```

The flow becomes:

```text
POST /todos
      ↓
authMiddleware
      ↓
createTodo
```

If the user isn't authenticated:

```text
Request
   ↓
authMiddleware
   ↓
❌ 401 Unauthorized
```

The controller never runs.

That's a very clean architecture.

---

# 14. Add validation

Suppose we also need to validate the request.

Now:

```js
router.post(
    "/",
    authMiddleware,
    validateCreateTodo,
    createTodo
);
```

Flow:

```text
POST /todos
      │
      ▼
authMiddleware
      │
      ▼
validateCreateTodo
      │
      ▼
createTodo
      │
      ▼
Service
```

Now look at how readable the route is.

It tells you the entire request pipeline without containing the implementation details.

# 15. Route as a pipeline definition

You can think of the route as describing:

```text
WHO can enter?
WHAT checks happen?
WHERE does the request go?
```

For example:

```js
router.post(
    "/",
    authMiddleware,
    validateCreateTodo,
    createTodo
);
```

means:

```text
Request
  ↓
Authentication
  ↓
Validation
  ↓
Controller
```

That's a very useful mental model.

---

# 16. Controller as an HTTP adapter

Now let's make the distinction slightly deeper.

Suppose the Service eventually exposes:

```js
todoService.createTodo({
    userId,
    title
});
```

The Service doesn't care about:

```text
POST
/api/v1/todos
req
res
HTTP 201
```

The Controller translates HTTP into application data:

```js
const todo = await todoService.createTodo({
    userId: req.user.id,
    title: req.body.title
});
```

Then translates the result back into HTTP:

```js
res.status(201).json({
    success: true,
    data: todo
});
```

So:

```text
             HTTP
              │
              ▼
         CONTROLLER
          ↙       ↘
     Request       Response
        ↓             ↑
        └── SERVICE ──┘
```

---

# 17. Very important: the Route shouldn't contain business logic

Avoid this:

```js
router.post("/todos", async (req, res) => {

    if (req.user.role !== "admin") {
        return res.status(403).json({
            message: "Forbidden"
        });
    }

    // lots of business logic...

});
```

The route should primarily describe the pipeline.

Better:

```js
router.post(
    "/todos",
    authMiddleware,
    requireRole("admin"),
    createTodo
);
```

Now:

```text
Route
→ defines the pipeline

Middleware
→ performs checks

Controller
→ handles HTTP

Service
→ performs business logic
```

# 22. A common beginner misunderstanding

You might think:

> "Route and Controller are basically the same thing."

They're related, but they're not the same.

Think of it like:

```text
Route = address/signpost
Controller = worker
```

The signpost says:

> "For this request, go here."

The worker actually performs the task.

---

# 23. Another analogy: railway station

Imagine a railway system.

```text
Train number
      ↓
Platform
      ↓
Train
```

The route is like the **platform assignment**.

The controller is like the **train/service that handles the passenger's journey**.

The platform doesn't drive the train.

Similarly:

```text
Route
```

doesn't need to contain the whole application operation.

It directs the request.

---

# 24. Why your starter has separate folders

Your starter architecture uses the separation:

```text
routes/
controllers/
services/
repositories/
```

because each layer answers a different question.

The purpose is not:

> "Professional developers like many folders."

The purpose is:

> **Keep different responsibilities from becoming mixed together.**

This is a very important mindset shift.

---

# 25. When is it okay to skip a Controller?

For a tiny project or quick experiment, you can absolutely do:

```js
router.get("/hello", (req, res) => {
    res.json({
        message: "Hello"
    });
});
```

There's no law saying every Express endpoint needs a separate controller file.

But when you're building a reusable backend architecture with many modules, separating routes and controllers gives you:

```text
organization
testability
readability
maintainability
clear responsibilities
```

That's why we're using them in your starter.

# 26. Common mistakes

### ❌ Mistake 1 — Putting business logic in routes

```js
router.post("/orders", async (...) => {
    // 100 lines
});
```

### ❌ Mistake 2 — Putting database queries in routes

```js
router.get("/users", async (...) => {
    const users = await User.find();
});
```

### ❌ Mistake 3 — Making routes responsible for authentication logic

```js
router.get("/admin", async (...) => {
    // manually decode JWT
    // manually check role
});
```

Use middleware instead.

### ❌ Mistake 4 — Making the Controller perform everything

```text
Controller
├── validation
├── database
├── hashing
├── emails
├── business rules
├── JWT
└── response
```

We'll fix that through Services and Repositories.

---

# 27. The golden rule

When writing a route, ask:

> **"Am I describing the request pipeline?"**

When writing a controller, ask:

> **"Am I handling the HTTP part?"**

When writing a service, ask:

> **"Am I implementing business rules?"**

When writing a repository, ask:

> **"Am I talking to the database?"**

This simple questioning technique will help you decide where code belongs.
