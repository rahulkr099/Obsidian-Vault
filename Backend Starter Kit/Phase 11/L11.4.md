# Lesson 11.4 — Controller vs Service

This is one of the **most important lessons in the entire backend architecture**.

If you understand the difference between a **Controller** and a **Service**, you'll avoid one of the biggest problems beginners face:

> **Fat Controllers — controllers containing all the business logic.**

Your starter architecture separates Controllers and Services for exactly this reason.

---

# 1. The simple difference

Remember this:

```text
Controller → HTTP work
Service    → Business work
```

Or:

```text
Controller = "How do I communicate through HTTP?"

Service = "What should my application actually do?"
```

For example:

```text
POST /todos
    ↓
Controller
    ↓
Service
```

The Controller understands:

```text
req.body
req.params
req.user
res.status()
res.json()
```

The Service understands:

```text
create todo
update todo
delete todo
business rules
permissions/business decisions
```

---

# 2. Why do we need a Service?

Suppose you write:

```js
export const createTodo = async (req, res) => {
    const { title } = req.body;

    const todo = await Todo.create({
        title,
        userId: req.user.id
    });

    res.status(201).json({
        success: true,
        data: todo
    });
};
```

This is already better than putting it directly in the route.

But now imagine the operation becomes more complicated:

```text
Create Todo
    ↓
Check user
    ↓
Check user's plan
    ↓
Check todo limit
    ↓
Check duplicate
    ↓
Create todo
    ↓
Update user's statistics
    ↓
Create notification
    ↓
Send event
```

If we put all of this into the Controller:

```js
export const createTodo = async (req, res) => {
    // 100+ lines
};
```

we've created a **fat controller**.

That's exactly what Services help us avoid.

---

# 3. The Service is the business layer

Suppose our application has this operation:

```text
Create Todo
```

The Controller doesn't need to understand every business rule.

It can simply say:

```js
const todo = await todoService.createTodo({
    userId: req.user.id,
    title: req.body.title
});
```

The Service handles the actual operation:

```js
export const createTodo = async ({ userId, title }) => {
    // business logic
};
```

So:

```text
Controller
    ↓
"Here is the information."

Service
    ↓
"I know what the application should do with it."
```

---

# 4. Think of the Controller as a receptionist

Imagine visiting a company.

You tell the receptionist:

> "I want to open a new account."

The receptionist:

```text
receives your request
        ↓
collects required information
        ↓
sends it to the correct department
        ↓
gets the result
        ↓
gives you the response
```

The receptionist doesn't decide all company business rules.

That's similar to the Controller.

```text
Client
  ↓
Controller
  ↓
Service
```

The Controller is the **entry point for HTTP**.

The Service is where the **application work happens**.

---

# 5. Example without Service

Here's a typical beginner implementation:

```js
export const registerUser = async (req, res) => {
    const { name, email, password } = req.body;

    const existingUser = await User.findOne({ email });

    if (existingUser) {
        return res.status(409).json({
            message: "User already exists"
        });
    }

    const hashedPassword = await bcrypt.hash(password, 12);

    const user = await User.create({
        name,
        email,
        password: hashedPassword
    });

    const token = jwt.sign(
        { userId: user._id },
        process.env.JWT_SECRET
    );

    res.status(201).json({
        success: true,
        user,
        token
    });
};
```

Look at everything the Controller is doing:

```text
HTTP
 ├── req.body
 └── res.status()

Business
 ├── user already exists?
 └── registration rules

Security
 └── password hashing

Database
 └── User.findOne()
 └── User.create()

Authentication
 └── jwt.sign()
```

That's too much responsibility.

---

# 6. With a Service

Instead:

### Controller

```js
export const registerUser = async (req, res) => {
    const user = await authService.registerUser(req.body);

    res.status(201).json({
        success: true,
        data: user
    });
};
```

### Service

```js
export const registerUser = async ({ name, email, password }) => {

    // business logic

    // check existing user

    // hash password

    // create user

    // generate authentication information

    return user;
};
```

Now the responsibilities are clearer.

```text
Controller
    ↓
HTTP

Service
    ↓
Business operation
```

---

# 7. The most important question

Whenever you're writing code, ask:

> **"Does this code care about HTTP?"**

If yes, it probably belongs in the Controller.

For example:

```js
req.body
```

Controller.

```js
req.params.id
```

Controller.

```js
res.status(201)
```

Controller.

```js
res.json(...)
```

Controller.

---

Now ask:

> **"Would this logic still make sense if there were no HTTP request?"**

If yes, it's probably business logic and belongs in the Service.

For example:

```text
Can this user create another todo?
```

This has nothing inherently to do with HTTP.

It could be called from:

```text
REST API
CLI
Background job
Cron job
Message queue
GraphQL
```

That's a strong sign that the logic belongs in the Service.

---

# 8. Very important example

Suppose you have:

```js
if (user.todoCount >= user.todoLimit) {
    throw new Error("Todo limit reached");
}
```

Does this require:

```js
req
```

or:

```js
res
```

?

No.

Therefore, it shouldn't need to live in the Controller.

It is an application/business rule.

So it can live in:

```text
todo.service.js
```

---

# 9. HTTP should stop at the Controller

A very useful architecture rule is:

```text
HTTP
 ↓
Controller
 ↓
Service
```

The Service should ideally not know that Express exists.

Avoid:

```js
// ❌ Bad Service design

export const createTodo = async (req, res) => {
    ...
};
```

Why?

Because now the Service is tied to Express.

Instead:

```js
// ✅ Better

export const createTodo = async ({ userId, title }) => {
    ...
};
```

Now the Service receives normal application data.

---

# 10. Why this matters for future applications

Imagine later you want to create a CLI command:

```bash
node create-todo.js
```

If your Service is:

```js
createTodo({ userId, title })
```

you can reuse it.

```text
REST Controller
       │
       ▼
createTodo Service
```

and:

```text
CLI
       │
       ▼
createTodo Service
```

Same business logic.

That's one of the biggest benefits of separating Controllers and Services.

---

# 11. Another example: money transfer

Imagine a banking application.

The user sends:

```http
POST /api/transfers
```

with:

```json
{
    "recipientId": "123",
    "amount": 5000
}
```

The Controller might do:

```js
export const transferMoney = async (req, res) => {

    const result = await transferService.transferMoney({
        senderId: req.user.id,
        recipientId: req.body.recipientId,
        amount: req.body.amount
    });

    res.status(200).json({
        success: true,
        data: result
    });
};
```

The Service might handle:

```text
Check sender
    ↓
Check recipient
    ↓
Check balance
    ↓
Check transfer limits
    ↓
Perform transfer
    ↓
Record transaction
    ↓
Return result
```

Those are business operations.

They don't belong in the Controller.

---

# 12. Controller should be thin

Eventually, a good Controller often looks surprisingly small:

```js
export const createTodo = asyncHandler(async (req, res) => {

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title: req.body.title
    });

    res.status(201).json({
        success: true,
        data: todo
    });
});
```

That's not a problem.

In fact:

> **A small Controller is often a sign that your architecture is working well.**

The complexity hasn't disappeared.

It has moved to the correct layer.

---

# 13. Don't misunderstand "thin"

Thin Controller does **not** mean:

> "Controllers must always have 5 lines."

A Controller may legitimately need to do some HTTP-related work.

For example:

```js
const { id } = req.params;
const { page, limit } = req.query;
const userId = req.user.id;
```

Then:

```js
const result = await service.getSomething({
    id,
    userId,
    page,
    limit
});
```

Then:

```js
res.status(200).json({
    success: true,
    data: result
});
```

That's perfectly reasonable.

The goal isn't fewer lines.

The goal is:

> **Clear responsibility.**

---

# 14. Controller responsibilities

A Controller can reasonably handle:

### 1. Extracting request data

```js
const { title } = req.body;
```

### 2. Reading route parameters

```js
const { id } = req.params;
```

### 3. Reading query parameters

```js
const { page } = req.query;
```

### 4. Reading authenticated user

```js
const userId = req.user.id;
```

### 5. Calling the Service

```js
const todo = await todoService.createTodo(...);
```

### 6. Choosing HTTP status

```js
res.status(201)
```

### 7. Sending the response

```js
res.json(...)
```

These are all HTTP-facing responsibilities.

---

# 15. Service responsibilities

A Service can handle things like:

### Business rules

```text
User can create maximum 100 todos.
```

### Application operations

```text
Create user
Create order
Cancel order
Transfer money
Reset password
```

### Coordinating multiple operations

For example:

```text
Create order
    ↓
Reserve inventory
    ↓
Calculate total
    ↓
Create payment
    ↓
Create order record
```

That's a Service-level responsibility.

---

# 16. Repository responsibilities

We'll learn this deeply later.

But remember:

```text
Service
   ↓
Repository
```

The Repository handles data access.

For example:

```js
const todo = await todoRepository.create(data);
```

The Repository might eventually contain:

```js
return Todo.create(data);
```

So:

```text
Controller
→ HTTP

Service
→ Business/application logic

Repository
→ Data access
```

---

# 17. A very useful comparison

|Question|Controller|Service|
|---|---|---|
|Knows HTTP?|Yes|Ideally no|
|Uses `req`?|Yes|No|
|Uses `res`?|Yes|No|
|Reads `req.body`?|Yes|No|
|Sets status code?|Yes|No|
|Sends JSON response?|Yes|No|
|Business rules?|Minimal|Yes|
|Coordinates operations?|No/very little|Yes|
|Database directly?|Ideally no|Through Repository|
|Reusable outside HTTP?|Usually no|Yes|

The word **ideally** matters here because real projects can make reasonable variations.

We're learning a clean architecture pattern first.

# 18. A powerful test

Here's a trick you can use while coding.

Take a piece of code and ask:

> **"Could I run this code without Express?"**

### Example:

```js
res.status(201).json(data);
```

No.

It needs Express.

Therefore:

```text
Controller
```

---

Now:

```js
if (amount > balance) {
    throw new Error("Insufficient balance");
}
```

Yes.

It doesn't need Express.

Therefore:

```text
Service
```

---

Another:

```js
const user = await User.findById(id);
```

It doesn't need HTTP.

But it's specifically database access.

Therefore, in our architecture:

```text
Repository
```

# 19. Let's classify some code

### Example A

```js
const { email, password } = req.body;
```

**Controller**

Because it reads HTTP request data.

---

### Example B

```js
if (password.length < 8) {
    throw new AppError("Password too short");
}
```

Depending on your architecture, input-shape validation may be handled earlier by validation middleware, while deeper business rules belong in the Service.

For our architecture:

```text
Validation middleware
→ request validation

Service
→ business rules
```

This distinction becomes important because **not every `if` belongs in the Service**.

---

### Example C

```js
res.status(201).json({
    success: true,
    data: user
});
```

**Controller**

Definitely HTTP.

---

### Example D

```js
if (user.subscription === "free" && user.todoCount >= 10) {
    throw new AppError("Todo limit reached");
}
```

**Service**

That's a business rule.

---

### Example E

```js
return Todo.findById(id);
```

**Repository**

That's data access.

Let's build the mental model.




### Service

Performs:

```text

```

Performs:

# 21. The full architecture

```text
                    CLIENT
                       │
                       │ HTTP
                       ▼
                    ROUTE
                       │
                       ▼
                 MIDDLEWARE
                       │
                       ▼
                 CONTROLLER
                HTTP boundary
                       │
                       ▼
                   SERVICE
              Business logic
                       │
                       ▼
                 REPOSITORY
                Data access
                       │
                       ▼
                    MODEL
                       │
                       ▼
                   DATABASE
```

Notice the boundary:

```text
                HTTP
                 │
                 ▼
             CONTROLLER
                 │
          ───────┼───────
                 │
             SERVICE
```

HTTP concerns should generally stop at the Controller.

# 22. Why this makes code easier to change

Imagine six months later you change:

```text
Express REST API
```

to:

```text
GraphQL
```

If your business logic is deeply mixed with:

```text
req
res
Express
HTTP status codes
```

you have a big problem.

But if your Service is:

```js
createTodo({
    userId,
    title
});
```

you can potentially reuse the same Service.

The interface changes:

```text
REST Controller
       ↓
Service
```

could become:

```text
GraphQL Resolver
       ↓
Service
```

The business logic doesn't need to know about the transport mechanism.

That's a powerful architectural benefit.

# 23. A common mistake: Service returning HTTP responses

Avoid this:

```js
export const createTodo = async (req, res) => {
    // ❌ Service shouldn't do this
    return res.status(201).json({
        success: true
    });
};
```

Instead:

```js
// Service
export const createTodo = async ({ userId, title }) => {
    // business logic

    return todo;
};
```

Then:

```js
// Controller
export const createTodo = async (req, res) => {

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title: req.body.title
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

Much cleaner.

---

# 24. Another common mistake: Service reading `req.user`

Avoid:

```js
// ❌
todoService.createTodo(req.user.id, req.body.title);
```

This particular call from the Controller is not inherently wrong—the Controller can extract those values and pass them. The problem is when the **Service itself** starts depending on `req`:

```js
// ❌
export const createTodo = async (req) => {
    const userId = req.user.id;
};
```

Better:

```js
// ✅
export const createTodo = async ({ userId, title }) => {
};
```

The Service now receives exactly what it needs.

---

# 25. Another common mistake: Service setting status codes

Don't do:

```js
// ❌
if (!user) {
    return res.status(404).json({
        message: "User not found"
    });
}
```

The Service shouldn't need to know about HTTP.

Instead, it can signal the failure:

```js
throw new AppError("User not found", 404);
```

Then your Controller/error-handling system can turn that into the HTTP response.

You'll see this pattern become especially useful with the error-handling architecture you learned in Phase 8.

---

# 26. Controller and Service communication

Think of it as a contract.

Controller says:

```js
const result = await service.doSomething({
    userId,
    data
});
```

Service says:

```text
"Give me the application data I need."
```

Service returns:

```js
return result;
```

Controller then says:

```js
res.status(200).json({
    success: true,
    data: result
});
```

So:

```text
Controller
    ↓
plain application data
    ↓
Service
    ↓
result
    ↓
Controller
    ↓
HTTP response
```

# 28. Mini exercise

Take this code:

```js
export const purchaseProduct = async (req, res) => {

    const { productId } = req.body;

    const product = await Product.findById(productId);

    if (!product) {
        return res.status(404).json({
            message: "Product not found"
        });
    }

    if (product.stock <= 0) {
        return res.status(400).json({
            message: "Product is out of stock"
        });
    }

    if (req.user.balance < product.price) {
        return res.status(400).json({
            message: "Insufficient balance"
        });
    }

    product.stock -= 1;

    await product.save();

    res.status(200).json({
        success: true,
        message: "Purchase successful"
    });
};
```

Don't rewrite it yet.

Instead, classify each part.

### Controller

```text
req.body
req.user
res.status()
res.json()
```

### Service

```text
product is out of stock
balance is sufficient
purchase rules
```

### Repository

```text
Product.findById()
product.save()
```

This exercise is more valuable than memorizing definitions.

# 29. One subtle point: validation vs business rules

You may notice something interesting.

We previously learned validation.

Suppose:

```json
{
    "title": ""
}
```

Checking whether `title` is a string and required can be handled by **validation middleware**.

But:

```text
"This user has already created 100 todos and their plan only allows 100."
```

is a **business rule**.

So we can think:

```text
Validation middleware
→ Is the request structurally valid?

Service
→ Is this operation allowed according to business rules?
```

This distinction will become very useful as your backend becomes larger.

# 31. Final cheat sheet

Keep this near you while coding:

```text
ROUTE
  ↓
"Where?"

MIDDLEWARE
  ↓
"Can it continue?"

CONTROLLER
  ↓
"How do I handle this HTTP request?"

SERVICE
  ↓
"What should the application do?"

REPOSITORY
  ↓
"How do I access the database?"
```

And the golden rule:

> **If the code needs `req` or `res`, it is probably Controller code. If the code describes what the application should do regardless of HTTP, it is probably Service code.**

One more important rule:

```text
Controller → Service
Service    → Repository
```

not:

```text
Controller → Database
Service    → Express
```

That separation is the foundation for the next lessons. In **11.5 — Understanding `req` and `res`**, we'll slow down and deeply understand the two objects that make Controllers work: **`request` and `response`**.
