# Lesson 11.5 — Understanding `req` and `res`

In the previous lessons, we established:

```text
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
```

Now we're going to focus on the two objects that you will use constantly inside Controllers:

```js
req
res
```

They are short names for:

```text
req → request
res → response
```

If you become comfortable with these two objects, writing Express Controllers becomes much easier.

---

# 1. What is `req`?

`req` represents the **HTTP request sent by the client to your server**.

For example, your frontend sends:

```http
POST /api/v1/todos
Content-Type: application/json

{
    "title": "Learn Express"
}
```

Express gives your Controller a `req` object containing information about that request.

You can think:

```text
Client
   │
   │ HTTP Request
   ▼
 req
```

The request can contain:

```text
body
params
query
headers
cookies
user
method
url
```

We'll learn these one by one.

---

# 2. What is `res`?

`res` represents the **HTTP response that your server sends back to the client**.

For example:

```js
res.json({
    success: true,
    message: "Todo created"
});
```

The server sends something like:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
    "success": true,
    "message": "Todo created"
}
```

So:

```text
Client
   │
   │ Request
   ▼
 Server
   │
   │ Response
   ▼
Client
```

Inside the Controller:

```text
req → information coming IN
res → information going OUT
```

That's the first mental model to remember.

---

# 3. A Controller receives both

A typical Express Controller looks like:

```js
const getUsers = (req, res) => {
    // use req

    // use res
};
```

Express calls your function and provides these objects.

You don't manually create:

```js
const req = ...
const res = ...
```

Express creates and provides them for you.

---

# 4. Simple example

Let's create:

```js
export const hello = (req, res) => {
    res.json({
        success: true,
        message: "Hello"
    });
};
```

Here:

```text
req
```

is available even though we're not using it.

We're only using:

```text
res
```

to send the response.

---

# 5. `req` contains client information

Suppose the client sends:

```http
GET /api/v1/users/123
```

The request contains information such as:

```text
HTTP method → GET
URL → /api/v1/users/123
```

If the route is:

```js
router.get("/users/:id", getUser);
```

then:

```js
req.params
```

contains:

```js
{
    id: "123"
}
```

We'll study `req.params` in **11.7**.

---

# 6. `req.body`

Suppose the client sends:

```http
POST /api/v1/users
```

with:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com"
}
```

The Controller can access it using:

```js
req.body
```

For example:

```js
export const createUser = (req, res) => {
    console.log(req.body);

    res.json({
        success: true
    });
};
```

You might see:

```js
{
    name: "Rahul",
    email: "rahul@example.com"
}
```

So:

```text
req.body
=
data sent inside the request body
```

We'll study this deeply in **11.6**.

---

# 7. `req.params`

Suppose:

```http
GET /api/v1/users/123
```

and:

```js
router.get("/users/:id", getUser);
```

Then:

```js
req.params.id
```

gives:

```text
"123"
```

Example:

```js
export const getUser = (req, res) => {
    const userId = req.params.id;

    res.json({
        userId
    });
};
```

Response:

```json
{
    "userId": "123"
}
```

---

# 8. `req.query`

Now suppose the client sends:

```http
GET /api/v1/users?page=2&limit=10
```

The query parameters are available through:

```js
req.query
```

So:

```js
req.query.page
```

is:

```text
"2"
```

and:

```js
req.query.limit
```

is:

```text
"10"
```

Example:

```js
export const getUsers = (req, res) => {
    const { page, limit } = req.query;

    res.json({
        page,
        limit
    });
};
```

We'll study this in more detail in **11.8**.

---

# 9. `req.headers`

HTTP requests can contain headers.

For example:

```http
Authorization: Bearer abc123
Content-Type: application/json
```

You can access headers through:

```js
req.headers
```

For example:

```js
const contentType = req.headers["content-type"];
```

Or:

```js
const authorization = req.headers.authorization;
```

This becomes particularly important for:

```text
authentication
content negotiation
client information
security
```

You've already encountered authentication and security in previous phases, so this will connect those concepts to Controllers.

---

# 10. `req.cookies`

If your application uses cookies, Express middleware can make them available through:

```js
req.cookies
```

For example:

```js
const token = req.cookies.accessToken;
```

This is common in authentication systems.

The exact availability depends on the cookie-parsing middleware you've configured.

---

# 11. `req.user`

This one is very important for your backend architecture.

Express does not automatically give every request:

```js
req.user
```

Usually, your authentication middleware creates it.

For example:

```js
req.user = {
    id: user._id,
    role: user.role
};
```

Then your Controller can use:

```js
const userId = req.user.id;
```

So the flow can be:

```text
Request
   ↓
Authentication Middleware
   ↓
req.user added
   ↓
Controller
```

This is a perfect example of how middleware and Controllers work together.

---

# 12. `req.method`

You can access the HTTP method:

```js
req.method
```

For example:

```text
GET
POST
PATCH
DELETE
```

Example:

```js
console.log(req.method);
```

If the request was:

```http
POST /users
```

you'll get:

```text
POST
```

Usually, you don't need to check this manually inside a Controller because your route already knows which method it handles.

---

# 13. `req.url`

You can access the request URL:

```js
req.url
```

For example:

```http
GET /users?page=2
```

You can inspect the URL information through Express's request properties.

Again, you generally won't need to manually inspect the URL in normal Controllers because your routes already define the paths.

---

# 14. Important idea: `req` is not just `req.body`

Beginners often think:

```text
req = req.body
```

That's incorrect.

Think of `req` as a large object:

```text
req
├── body
├── params
├── query
├── headers
├── cookies
├── user
├── method
├── url
└── ...
```

So:

```js
req.body
```

is only **one piece** of the request.

---

# 15. Now let's understand `res`

The `res` object is how your server communicates back to the client.

The most common methods you'll use are:

```js
res.json()
res.status()
res.send()
```

There are other response methods, but these are the ones we'll focus on first.

---

# 16. `res.json()`

This is probably the method you'll use most often in an API.

Example:

```js
res.json({
    success: true,
    message: "User created"
});
```

Express sends JSON to the client.

The response might look like:

```json
{
    "success": true,
    "message": "User created"
}
```

---

# 17. `res.status()`

You can set the HTTP status code:

```js
res.status(201);
```

But normally you'll chain it with:

```js
res.status(201).json({
    success: true
});
```

For example:

```js
export const createUser = (req, res) => {
    res.status(201).json({
        success: true,
        message: "User created"
    });
};
```

This means:

```text
HTTP status = 201
Response body = JSON
```

We'll study status codes in detail in **11.11**.

---

# 18. `res.send()`

You can also use:

```js
res.send("Hello");
```

This sends a response body.

For APIs, however, you'll commonly prefer:

```js
res.json(...)
```

when your API response is JSON.

For example:

```js
res.send("Hello");
```

versus:

```js
res.json({
    message: "Hello"
});
```

For the backend architecture we're building, you'll mostly see `res.json()`.

---

# 19. `res.status().json()`

This combination is extremely common.

For successful creation:

```js
res.status(201).json({
    success: true,
    data: user
});
```

For a successful normal request:

```js
res.status(200).json({
    success: true,
    data: users
});
```

For an error:

```js
res.status(404).json({
    success: false,
    message: "User not found"
});
```

---

# 20. `return res...`

You'll often see:

```js
return res.status(404).json({
    success: false,
    message: "User not found"
});
```

Why `return`?

Because it immediately exits the Controller function.

Consider:

```js
if (!user) {
    return res.status(404).json({
        message: "User not found"
    });
}

res.json(user);
```

If the user doesn't exist:

```text
return
 ↓
Controller stops
```

Without `return`:

```js
if (!user) {
    res.status(404).json({
        message: "User not found"
    });
}

res.json(user);
```

the function could continue and attempt to send another response.

That can cause errors such as:

```text
Error: Cannot set headers after they are sent
```

We'll discuss response flow more later.

---

# 21. Request → Controller → Response

Let's put everything together.

Client sends:

```http
POST /api/v1/todos
Content-Type: application/json
Authorization: Bearer token
```

Body:

```json
{
    "title": "Learn Controllers"
}
```

Middleware authenticates the user and adds:

```js
req.user = {
    id: "123"
};
```

Controller receives:

```text
req
├── body
│   └── title
├── headers
│   └── authorization
└── user
    └── id
```

The Controller might do:

```js
export const createTodo = async (req, res) => {
    const { title } = req.body;
    const userId = req.user.id;

    const todo = await todoService.createTodo({
        title,
        userId
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

Notice how naturally `req` and `res` fit into the Controller.

---

# 22. A useful classification

When you see:

```js
req.something
```

you're **reading information coming into your server**.

When you see:

```js
res.something(...)
```

you're **creating/sending information going back to the client**.

So:

```text
REQ
↓
Input

RES
↓
Output
```

This simple idea will help you remember which object does what.

---

# 23. Request lifecycle

Let's see the complete lifecycle.

```text
                 CLIENT
                    │
                    │ HTTP Request
                    ▼
                EXPRESS
                    │
                    ▼
                MIDDLEWARE
                    │
                    │ modifies/enriches req
                    ▼
               CONTROLLER
                    │
              ┌─────┴─────┐
              │           │
            req          res
              │           │
         read input    send output
              │           │
              ▼           ▼
             SERVICE     CLIENT
```

For example:

```text
req.body
   ↓
Controller
   ↓
Service
   ↓
result
   ↓
res.json()
```

---

# 24. Why Controllers need `req` and `res`

This connects directly to our previous lesson.

We said:

> **Controller = HTTP boundary**

Now you can see why.

The Controller is the layer that directly interacts with:

```text
req
res
```

The Service doesn't need to know about them.

For example:

```js
// Controller
const todo = await todoService.createTodo({
    title: req.body.title,
    userId: req.user.id
});

res.status(201).json({
    data: todo
});
```

The Service only receives:

```js
{
    title,
    userId
}
```

That's a clean boundary.

---

# 25. What happens if the Service receives `req`?

Suppose you write:

```js
todoService.createTodo(req);
```

Then the Service might start doing:

```js
req.body
req.user
req.params
req.headers
```

Now your Service knows about HTTP.

That's exactly what we're trying to avoid.

Better:

```js
todoService.createTodo({
    title: req.body.title,
    userId: req.user.id
});
```

Now the Service receives plain data.

---

# 26. Think of `req` as an input package

Imagine the client sends:

```text
name
email
password
```

The request object is like a package containing:

```text
┌──────────────────────┐
│       REQUEST        │
├──────────────────────┤
│ body                 │
│ params               │
│ query                │
│ headers              │
│ cookies              │
│ user                 │
│ method               │
│ url                  │
└──────────────────────┘
```

The Controller opens the package and takes what it needs.

For example:

```js
const { email, password } = req.body;
```

Then passes only the required information deeper into the application.

---

# 27. Think of `res` as an output package

The Controller receives a result:

```js
const user = ...
```

Then builds the response:

```js
res.status(200).json({
    success: true,
    data: user
});
```

Think:

```text
Service result
     ↓
Controller
     ↓
HTTP Response
```

---

# 28. Don't blindly return everything from `req`

Suppose:

```js
req.body
```

contains:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "password": "secret"
}
```

Don't automatically pass everything everywhere.

Instead:

```js
const { name, email, password } = req.body;

await userService.registerUser({
    name,
    email,
    password
});
```

Later, validation and security layers will make this even safer.

The Controller should consciously decide what information enters the Service.

---

# 29. Don't blindly send database documents

Suppose the database returns:

```js
{
    id: "123",
    name: "Rahul",
    email: "rahul@example.com",
    password: "hashed-password"
}
```

You should not automatically send sensitive fields to the client:

```js
res.json(user);
```

Instead, your application should control what is exposed.

For example:

```js
res.json({
    success: true,
    data: {
        id: user.id,
        name: user.name,
        email: user.email
    }
});
```

Exactly how you handle response transformation will depend on the architecture you build later.

---

# 30. `req.user` is special

Let's revisit this because it will appear everywhere in authenticated APIs.

A request starts as:

```text
Client
  ↓
Authorization header
  ↓
Authentication middleware
```

The middleware verifies the token and may do:

```js
req.user = {
    id: user._id,
    role: user.role
};
```

Then:

```text
Middleware
     ↓
req.user
     ↓
Controller
```

Controller:

```js
const userId = req.user.id;
```

This means:

> **Middleware can enrich the request before the Controller receives it.**

That's an important Express concept.

---

# 31. Example with authentication

Route:

```js
router.post(
    "/todos",
    authenticate,
    createTodo
);
```

Authentication middleware:

```js
export const authenticate = async (req, res, next) => {
    // verify token

    req.user = {
        id: user._id
    };

    next();
};
```

Controller:

```js
export const createTodo = async (req, res) => {
    const todo = await todoService.createTodo({
        userId: req.user.id,
        title: req.body.title
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

This is a very common backend pattern.

---

# 32. `req` can be modified by middleware

This is why middleware is so powerful.

For example:

```text
Incoming Request
       ↓
auth middleware
       ↓
req.user added
       ↓
validation middleware
       ↓
validated data available
       ↓
Controller
```

The Controller gets a request that has already been processed by earlier layers.

This connects directly to the middleware concepts from **Phase 10**.

---

# 33. One important warning: `req.body` may be undefined

If you're expecting JSON:

```json
{
    "title": "Learn Express"
}
```

your Express application needs the appropriate body parser middleware.

Typically:

```js
app.use(express.json());
```

Without it, your Controller may not receive JSON request data as expected.

So:

```text
Client sends JSON
        ↓
express.json()
        ↓
req.body
        ↓
Controller
```

This is another example of middleware preparing the request before the Controller.

---

# 34. Query and params are strings

One important detail for later lessons:

Suppose the client sends:

```http
GET /users?page=2
```

Then:

```js
req.query.page
```

is generally a string:

```js
"2"
```

not:

```js
2
```

Similarly:

```http
/users/123
```

gives:

```js
req.params.id
```

as:

```js
"123"
```

This matters when performing numeric operations or validation.

We'll cover this carefully in the upcoming lessons.

---

# 35. Request data can come from different places

Suppose the endpoint is:

```http
GET /api/v1/users/123?includeTodos=true
```

The request could provide:

### URL parameter

```js
req.params.id
```

→ `"123"`

### Query parameter

```js
req.query.includeTodos
```

→ `"true"`

### Headers

```js
req.headers.authorization
```

→ authentication information

### User added by middleware

```js
req.user.id
```

→ authenticated user's ID

The Controller can combine these:

```js
const userId = req.params.id;
const includeTodos = req.query.includeTodos;
const requesterId = req.user.id;
```

---

# 36. Controller example

Here's a more realistic example:

```js
export const getUser = async (req, res) => {
    const { id } = req.params;
    const { includeTodos } = req.query;

    const user = await userService.getUser({
        id,
        includeTodos
    });

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Notice the Controller knows:

```text
HTTP
```

but the Service receives:

```js
{
    id,
    includeTodos
}
```

It doesn't receive:

```js
req
res
```

That's exactly the separation we're trying to build.

# 37. Common mistakes

## Mistake 1 — Confusing `req` and `res`

Wrong mental model:

```text
req = response
res = request
```

Correct:

```text
req = request
res = response
```

---

## Mistake 2 — Trying to send response from Service

Avoid:

```js
service.getUser(req, res);
```

Better:

```js
const user = await service.getUser(id);

res.json({
    data: user
});
```

---

## Mistake 3 — Sending multiple responses

Bad:

```js
if (!user) {
    res.status(404).json({
        message: "Not found"
    });
}

res.json(user);
```

Better:

```js
if (!user) {
    return res.status(404).json({
        message: "Not found"
    });
}

return res.json(user);
```

---

## Mistake 4 — Assuming everything is in `req.body`

Remember:

```text
Body    → req.body
Params  → req.params
Query   → req.query
Headers → req.headers
Cookies → req.cookies
User    → req.user
```

# 41. The cheat sheet

Keep this nearby:

```text
┌────────────────────────────────────┐
│              REQUEST               │
├────────────────────────────────────┤
│ req.body       → request body      │
│ req.params     → URL parameters    │
│ req.query      → query parameters  │
│ req.headers    → HTTP headers      │
│ req.cookies    → cookies           │
│ req.user       → authenticated user│
│ req.method     → HTTP method       │
└────────────────────────────────────┘
```

And:

```text
┌────────────────────────────────────┐
│             RESPONSE               │
├────────────────────────────────────┤
│ res.status()   → status code       │
│ res.json()     → JSON response     │
│ res.send()     → response body     │
└────────────────────────────────────┘
```

The most important mental model:

```text
             CLIENT
                │
                │ Request
                ▼
               req
                │
                ▼
           CONTROLLER
                │
                │
                ▼
               res
                │
                │ Response
                ▼
             CLIENT
```

### Remember:

> **`req` tells your Controller what the client sent. `res` lets your Controller tell the client what happened.**

And this is why Controllers are the **HTTP boundary** between your outside world and your application's internal Service layer.
