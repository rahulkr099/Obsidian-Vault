# Lesson 11.6 — Reading `req.body`

In the Phase 11 roadmap, **11.6 is specifically "Reading `req.body`"**. The goal is to understand exactly how data sent by a client reaches your Controller.

This is one of the most important Controller concepts because almost every `POST`, `PUT`, and `PATCH` endpoint will use request-body data.

---

# 1. What is `req.body`?

`req.body` contains data that the client sends **inside the HTTP request body**.

For example, your frontend sends:

```http
POST /api/v1/todos
Content-Type: application/json

{
  "title": "Learn Controllers",
  "priority": "high"
}
```

Your Controller can read it using:

```js
req.body
```

So:

```js
console.log(req.body);
```

would give:

```js
{
  title: "Learn Controllers",
  priority: "high"
}
```

The basic flow is:

```text
Frontend
   │
   │ JSON body
   ▼
HTTP Request
   │
   ▼
Express
   │
   ▼
req.body
   │
   ▼
Controller
```

---

# 2. `req.body` is NOT the entire request

Remember from 11.5:

```text
req
├── body
├── params
├── query
├── headers
├── cookies
├── user
└── ...
```

Therefore:

```js
req
```

is the complete request object.

While:

```js
req.body
```

is only the data contained in the request body.

---

# 3. Why do we need a request body?

Imagine creating a user.

The URL alone isn't enough:

```http
POST /api/v1/users
```

The server also needs:

```text
name
email
password
```

So the client sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "secret123"
}
```

This is the **request body**.

---

# 4. `express.json()` is extremely important

Here's something beginners often miss.

If the client sends JSON, Express needs to parse that JSON before you can conveniently access it through `req.body`.

Usually you'll have:

```js
app.use(express.json());
```

in your application setup.

The flow becomes:

```text
JSON Request
     ↓
express.json()
     ↓
req.body
     ↓
Controller
```

Your starter architecture explicitly treats `express.json()` as part of the middleware foundation.

---

# 5. What does `express.json()` actually do?

Suppose the client sends:

```json
{
  "title": "Learn Express"
}
```

Over HTTP, that arrives as request data.

`express.json()` parses the JSON so your application can work with it as a JavaScript object.

Conceptually:

```text
Raw JSON
   ↓
express.json()
   ↓
JavaScript object
   ↓
req.body
```

So:

```js
req.body.title
```

can give:

```text
"Learn Express"
```

---

# 6. Basic example

### app.js

```js
import express from "express";

const app = express();

app.use(express.json());

export default app;
```

### Controller

```js
export const createTodo = (req, res) => {
    console.log(req.body);

    return res.status(201).json({
        success: true,
        data: req.body
    });
};
```

If the client sends:

```json
{
  "title": "Learn Services"
}
```

the response could be:

```json
{
  "success": true,
  "data": {
    "title": "Learn Services"
  }
}
```

# 7. Accessing individual fields

Suppose:

```json
{
  "title": "Learn Controllers",
  "priority": "high"
}
```

You can write:

```js
const title = req.body.title;
const priority = req.body.priority;
```

Or destructure:

```js
const { title, priority } = req.body;
```

I recommend becoming comfortable with destructuring because you'll use it constantly in backend code.

---

# 8. Real Controller example

Suppose we have:

```http
POST /api/v1/todos
```

and the body:

```json
{
  "title": "Learn req.body",
  "priority": "high"
}
```

Controller:

```js
export const createTodo = async (req, res) => {
    const { title, priority } = req.body;

    const todo = await todoService.createTodo({
        title,
        priority
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

Notice something important.

The Controller doesn't pass the entire `req` to the Service.

Instead:

```js
todoService.createTodo({
    title,
    priority
});
```

That's consistent with the architecture we're building:

```text
req.body
   ↓
Controller
   ↓
extract required data
   ↓
Service
```

---

# 9. Why shouldn't we simply pass `req.body` everywhere?

You might see:

```js
todoService.createTodo(req.body);
```

This can work.

But there's an important architectural question:

> **Should the Controller decide exactly what data enters the Service?**

Usually, yes.

For example, imagine the client sends:

```json
{
  "title": "Learn Node",
  "priority": "high",
  "isAdmin": true,
  "createdBy": "someone-else"
}
```

If you blindly pass:

```js
todoService.createTodo(req.body);
```

you're allowing every submitted field to move deeper into your application.

That's risky.

Instead:

```js
const { title, priority } = req.body;

todoService.createTodo({
    title,
    priority
});
```

Now you've explicitly selected the fields your operation expects.

---

# 10. But validation should happen too

Don't misunderstand the previous section.

The Controller shouldn't become responsible for all validation.

Our architecture has a validation layer:

```text
Request
   ↓
Validation middleware
   ↓
Controller
   ↓
Service
```

The source roadmap specifically describes the desired flow as:

```text
req.body
   ↓
validate()
   ↓
clean data
   ↓
controller
```

rather than blindly trusting `req.body`.

So eventually:

```text
Client
  ↓
req.body
  ↓
Validation
  ↓
Controller
  ↓
Service
```

---

# 11. Request body vs validation

Suppose the endpoint expects:

```json
{
  "title": "Learn Node"
}
```

The client sends:

```json
{
  "title": 123
}
```

`req.body` doesn't automatically mean:

> "This data is correct."

It only means:

> "This is what the client sent."

That's a very important backend principle:

> **Client input is untrusted input.**

Validation determines whether that input satisfies your API's requirements.

# 12. `req.body` can contain different data types

For example:

### String

```json
{
  "name": "Rahul"
}
```

JavaScript:

```js
typeof req.body.name
```

→ `"string"`

### Number

```json
{
  "age": 22
}
```

→ number

### Boolean

```json
{
  "completed": true
}
```

→ boolean

### Array

```json
{
  "tags": ["node", "express", "mongodb"]
}
```

→ array

### Object

```json
{
  "profile": {
    "city": "Delhi"
  }
}
```

→ object

---

# 13. Nested request bodies

Suppose:

```json
{
  "title": "Learn Node",
  "settings": {
    "priority": "high",
    "notifications": true
  }
}
```

You can access:

```js
const title = req.body.title;

const priority = req.body.settings.priority;

const notifications = req.body.settings.notifications;
```

Or:

```js
const {
    title,
    settings: {
        priority,
        notifications
    }
} = req.body;
```

Don't worry if the second version feels complicated right now.

The first version is completely fine.

---

# 14. Request body can be an array

Depending on the endpoint, a body doesn't always have to be an object.

For example:

```json
[
  {
    "title": "Task 1"
  },
  {
    "title": "Task 2"
  }
]
```

Then:

```js
req.body
```

is an array.

You could do:

```js
for (const todo of req.body) {
    console.log(todo.title);
}
```

However, for most CRUD endpoints, you'll commonly use an object body.

---

# 15. What happens if `express.json()` is missing?

Suppose you have:

```js
app.post("/todos", (req, res) => {
    console.log(req.body);
});
```

but you haven't configured JSON parsing:

```js
app.use(express.json());
```

Then your JSON body may not be available in the way you expect.

This is why middleware order matters.

Correct:

```js
const app = express();

app.use(express.json());

app.post("/todos", controller);
```

The body parser runs **before** the Controller.

---

# 16. Middleware order matters

This:

```js
app.use(express.json());

app.use("/api/todos", todoRoutes);
```

means:

```text
Request
   ↓
express.json()
   ↓
todoRoutes
   ↓
Controller
```

But if you accidentally put things in the wrong order, the route may execute before the body parser.

The general principle is:

> **Middleware that prepares `req` must run before code that needs the prepared data.**

This connects directly to the middleware execution-order concepts from Phase 7.

# 17. `req.body` and HTTP methods

You'll commonly see request bodies with:

```text
POST
PUT
PATCH
```

For example:

### POST

```http
POST /users
```

```json
{
  "name": "Rahul"
}
```

### PUT

```http
PUT /users/123
```

```json
{
  "name": "Rahul Kumar"
}
```

### PATCH

```http
PATCH /users/123
```

```json
{
  "name": "Rahul Kumar"
}
```

`GET` requests generally use:

```text
req.params
req.query
```

rather than a request body for normal API designs.

# 18. `req.body` vs `req.params` vs `req.query`

This is worth memorizing.

Suppose:

```http
PATCH /api/v1/todos/123?notify=true
```

with:

```json
{
  "title": "Learn req.body"
}
```

Then:

### URL parameter

```js
req.params.id
```

→

```text
"123"
```

### Query parameter

```js
req.query.notify
```

→

```text
"true"
```

### Request body

```js
req.body.title
```

→

```text
"Learn req.body"
```

Think:

```text
URL
 ├── /todos/123
 │      ↓
 │   req.params
 │
 └── ?notify=true
        ↓
     req.query

Body
 ↓
req.body
```

# 19. A complete example

Let's build a realistic endpoint.

### Request

```http
POST /api/v1/todos
Content-Type: application/json
Authorization: Bearer <token>
```

Body:

```json
{
  "title": "Learn backend architecture",
  "priority": "high"
}
```

Authentication middleware might add:

```js
req.user = {
    id: "123"
};
```

Then Controller:

```js
export const createTodo = async (req, res) => {
    const { title, priority } = req.body;

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title,
        priority
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
};
```

The flow is:

```text
HTTP Request
     │
     ▼
express.json()
     │
     ▼
auth middleware
     │
     ├── req.user
     │
     ▼
validation
     │
     ▼
Controller
     │
     ├── req.body.title
     ├── req.body.priority
     └── req.user.id
     │
     ▼
Service
```

This is the architecture you are building toward.

# 20. Don't trust arbitrary fields

This is especially important when dealing with MongoDB.

Suppose your model has:

```js
{
    title,
    priority,
    ownerId,
    isDeleted
}
```

The client sends:

```json
{
  "title": "My todo",
  "priority": "high",
  "ownerId": "another-user",
  "isDeleted": false
}
```

If you blindly do:

```js
Todo.create(req.body);
```

you could accidentally allow clients to control fields they shouldn't control.

Instead, your application should determine which fields are allowed.

For example:

```js
const { title, priority } = req.body;

const todo = await todoService.createTodo({
    userId: req.user.id,
    title,
    priority
});
```

Now ownership comes from the authenticated user rather than the client.

This also connects with the security/ownership architecture described in your starter roadmap.

# 21. `req.body` and authentication

Consider:

```json
{
  "title": "My Todo",
  "userId": "123"
}
```

You might think:

```js
const { title, userId } = req.body;
```

But for an authenticated API, you normally don't want the client deciding who owns the resource.

Instead:

```js
const { title } = req.body;

const userId = req.user.id;
```

Then:

```js
todoService.createTodo({
    userId,
    title
});
```

So:

```text
Client
  ↓
title
  ↓
req.body

Authentication middleware
  ↓
userId
  ↓
req.user
```

That's much safer.

---

# 22. What if `req.body` is empty?

The client might send:

```json
{}
```

Then:

```js
req.body.title
```

is:

```text
undefined
```

This is exactly why validation exists.

For example:

```text
Request body
    ↓
Does title exist?
    ↓
Is title a string?
    ↓
Is title long enough?
    ↓
Controller
```

Don't fill your Controllers with dozens of checks.

Use the validation layer you've been learning.

---

# 23. What if the client sends malformed JSON?

Suppose the client sends invalid JSON:

```text
{
    "title": "Learn Node"
```

The JSON is incomplete.

`express.json()` may reject the body parsing.

That's not something your Controller should manually parse.

The middleware/error-handling layers should deal with parsing failures appropriately.

This is another reason the architecture has:

```text
Middleware
   ↓
Error handling
   ↓
Validation
   ↓
Controller
```

rather than making every Controller responsible for everything.

# 24. A common beginner Controller

You might initially write:

```js
export const createTodo = async (req, res) => {
    const { title } = req.body;

    if (!title) {
        return res.status(400).json({
            message: "Title required"
        });
    }

    const todo = await Todo.create({
        title
    });

    return res.status(201).json({
        data: todo
    });
};
```

This works.

But as your application grows, you'll separate responsibilities:

```text
Validation
    ↓
Controller
    ↓
Service
    ↓
Repository
```

So eventually:

```js
export const createTodo = asyncHandler(async (req, res) => {
    const { title } = req.body;

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title
    });

    return res.status(201).json({
        success: true,
        data: todo
    });
});
```

Much cleaner.

# 27. A very important distinction

Don't confuse these two statements:

### "Read the request body"

```js
const { title } = req.body;
```

This is Controller work.

### "Decide whether this title is allowed"

For example:

```text
Title must be unique for this user.
```

That's a business rule and belongs deeper in the application layer.

So:

```text
req.body
   ↓
Controller reads it

Validation
   ↓
Checks input structure

Service
   ↓
Applies business rules
```

# 31. The golden rules for `req.body`

Remember these:

### Rule 1

```js
req.body
```

contains body data sent by the client.

### Rule 2

For JSON requests, configure:

```js
app.use(express.json());
```

### Rule 3

Don't assume the body is valid.

```text
req.body
   ↓
validation
```

### Rule 4

Don't blindly pass arbitrary body fields deeper into your application.

### Rule 5

Don't allow clients to control security-sensitive ownership fields.

Use:

```js
req.user.id
```

when the authenticated identity is the source of truth.

### Rule 6

The Controller should extract request data and pass appropriate application data to the Service.
