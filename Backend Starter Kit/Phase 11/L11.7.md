# Lesson 11.7 — Reading `req.params`

In the previous lesson, we learned:

```js
req.body
```

which contains data sent **inside the request body**.

Now we'll learn:

```js
req.params
```

which contains values captured from **dynamic parts of the URL**.

This is one of the most important concepts in CRUD APIs because you'll constantly work with URLs like:

```text
/users/123
/todos/456
/products/789
/orders/abc123
```

---

# 1. What is `req.params`?

`req.params` contains **route parameters**.

Consider this route:

```js
router.get("/users/:id", getUser);
```

The `:id` is a **route parameter**.

If the client requests:

```http
GET /users/123
```

then:

```js
req.params
```

contains:

```js
{
    id: "123"
}
```

Therefore:

```js
req.params.id
```

returns:

```text
"123"
```

The basic idea is:

```text
Route:
 /users/:id
         ↑
     parameter

Request:
 /users/123
         ↑
       value

req.params.id
       ↓
     "123"
```

---

# 2. Why do we need route parameters?

Imagine you're building a Todo API.

You have 1,000 todos.

You want to retrieve one specific todo.

You could theoretically create:

```text
/todos?id=123
```

But REST-style APIs commonly represent a resource's identity directly in the path:

```text
/todos/123
```

So:

```text
/todos/:id
```

means:

> "Give me the todo identified by this ID."

---

# 3. Defining a parameter

In Express, a dynamic route segment starts with:

```text
:
```

For example:

```js
router.get("/users/:id", getUser);
```

Here:

```text
:id
```

is a parameter.

Another example:

```js
router.get("/products/:productId", getProduct);
```

Now the parameter is:

```text
productId
```

You access it using:

```js
req.params.productId
```

---

# 4. Simple example

Route:

```js
router.get("/users/:id", getUser);
```

Controller:

```js
export const getUser = (req, res) => {
    const { id } = req.params;

    return res.json({
        userId: id
    });
};
```

Request:

```http
GET /users/123
```

Response:

```json
{
    "userId": "123"
}
```

---

# 5. `req.params` is an object

Suppose:

```js
router.get("/users/:id", getUser);
```

and request:

```http
GET /users/123
```

Then:

```js
req.params
```

is:

```js
{
    id: "123"
}
```

Therefore:

```js
req.params.id
```

is:

```text
"123"
```

You can also destructure:

```js
const { id } = req.params;
```

This is probably the form you'll use most often.

---

# 6. Parameters are strings

This is an important detail.

Suppose:

```http
GET /users/123
```

You might expect:

```js
req.params.id
```

to be:

```js
123
```

But Express gives you:

```js
"123"
```

It is a **string**.

So:

```js
typeof req.params.id
```

will generally be:

```text
"string"
```

If you need a number, you must convert it:

```js
const id = Number(req.params.id);
```

However, for MongoDB/Mongoose IDs such as:

```text
ObjectId
```

you normally **don't convert them to numbers**.

---

# 7. MongoDB example

In your MERN backend, you'll commonly have:

```http
GET /api/v1/todos/64f123abc456...
```

Route:

```js
router.get("/todos/:id", getTodo);
```

Controller:

```js
export const getTodo = async (req, res) => {
    const { id } = req.params;

    const todo = await todoService.getTodo(id);

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

Notice:

```js
const { id } = req.params;
```

The Controller extracts the resource identifier.

Then:

```js
todoService.getTodo(id);
```

The Service doesn't need to know that the ID originally came from an HTTP URL.

That's a very important architectural boundary.

# 8. One parameter

The most common case:

```js
router.get("/todos/:id", getTodo);
```

Request:

```http
GET /todos/123
```

Then:

```js
req.params.id
```

→

```text
"123"
```

---

# 9. Multiple parameters

You can have multiple route parameters.

For example:

```js
router.get(
    "/users/:userId/todos/:todoId",
    getUserTodo
);
```

Request:

```http
GET /users/123/todos/456
```

Then:

```js
req.params
```

is:

```js
{
    userId: "123",
    todoId: "456"
}
```

You can extract them:

```js
const { userId, todoId } = req.params;
```

Then:

```js
console.log(userId);
console.log(todoId);
```

gives:

```text
123
456
```

---

# 10. Think about nested resources

This pattern:

```text
/users/:userId/todos/:todoId
```

represents something like:

```text
User
 └── Todo
```

For example:

```http
GET /users/123/todos/456
```

means:

> Get todo `456` belonging to user `123`.

Your Controller could be:

```js
export const getUserTodo = async (req, res) => {
    const { userId, todoId } = req.params;

    const todo = await todoService.getUserTodo({
        userId,
        todoId
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

Notice the Service receives:

```js
{
    userId,
    todoId
}
```

not:

```js
req
```

---

# 11. `req.params` vs `req.body`

This is extremely important.

Suppose:

```http
PATCH /api/v1/todos/123
```

with:

```json
{
    "title": "Learn Express"
}
```

Then:

```js
req.params.id
```

contains:

```text
"123"
```

while:

```js
req.body.title
```

contains:

```text
"Learn Express"
```

Think:

```text
URL
 ↓
/todos/123
        ↓
   req.params.id


BODY
 ↓
{
   title: "Learn Express"
}
        ↓
req.body.title
```

The URL identifies **which resource** you're talking about.

The body usually contains **what data you want to create/update**.

---

# 12. `req.params` vs `req.query`

Now consider:

```http
GET /api/v1/todos/123?includeComments=true
```

There are two different types of URL information.

### Route parameter

```js
req.params.id
```

→

```text
"123"
```

### Query parameter

```js
req.query.includeComments
```

→

```text
"true"
```

Visualize it:

```text
/api/v1/todos/123?includeComments=true
                 │
                 │
                 └── query
                 

/todos/:id
        │
        └── route parameter
```

So:

```text
req.params → identifies route resources
req.query  → modifies/filter the request
```

This isn't an absolute rule for every API design, but it's a very useful mental model.

# 13. CRUD and `req.params`

This is where `req.params` becomes extremely useful.

## Get one

```http
GET /todos/:id
```

```js
const { id } = req.params;
```

---

## Update one

```http
PATCH /todos/:id
```

```js
const { id } = req.params;
const { title } = req.body;
```

---

## Delete one

```http
DELETE /todos/:id
```

```js
const { id } = req.params;
```

So you'll repeatedly see:

```js
const { id } = req.params;
```

throughout your backend.

---

# 14. Complete CRUD example

Imagine these routes:

```js
router.get("/todos/:id", getTodo);

router.patch("/todos/:id", updateTodo);

router.delete("/todos/:id", deleteTodo);
```

### Get

```js
export const getTodo = async (req, res) => {
    const { id } = req.params;

    const todo = await todoService.getTodo(id);

    return res.json({
        success: true,
        data: todo
    });
};
```

### Update

```js
export const updateTodo = async (req, res) => {
    const { id } = req.params;
    const { title } = req.body;

    const todo = await todoService.updateTodo(id, {
        title
    });

    return res.json({
        success: true,
        data: todo
    });
};
```

### Delete

```js
export const deleteTodo = async (req, res) => {
    const { id } = req.params;

    await todoService.deleteTodo(id);

    return res.status(204).send();
};
```

See the pattern?

```text
GET
  params → identify resource

PATCH
  params → identify resource
  body   → new data

DELETE
  params → identify resource
```

# 15. Route parameter names matter

Suppose you define:

```js
router.get("/users/:userId", getUser);
```

Then this is correct:

```js
req.params.userId
```

Not:

```js
req.params.id
```

because your parameter is named:

```text
:userId
```

So:

```text
"/users/:userId"
          ↓
req.params.userId
```

The parameter name in the route becomes the property name.

---

# 16. Multiple parameters

Consider:

```js
router.get(
    "/users/:userId/posts/:postId",
    getPost
);
```

Request:

```http
GET /users/10/posts/50
```

Then:

```js
const { userId, postId } = req.params;
```

gives:

```text
userId = "10"
postId = "50"
```

You can pass these into your Service:

```js
const post = await postService.getPost({
    userId,
    postId
});
```

---

# 17. Optional route parameters

Express also supports optional route patterns depending on the version and route syntax being used, but **don't make this your first approach**.

For your current architecture, prefer explicit routes.

Instead of trying to make one complicated route handle many possibilities:

```text
/users/:id
/users
```

define clear routes:

```js
router.get("/users", getUsers);

router.get("/users/:id", getUser);
```

This is easier to understand and maintain.

---

# 18. Don't put everything into `req.params`

A common beginner mistake is trying to design URLs like:

```text
/todos/123/high/true/rahul/...
```

Just because route parameters exist doesn't mean every piece of data belongs there.

For example:

```http
GET /todos/123
```

is reasonable.

But:

```http
GET /todos/123/high/true/rahul
```

is usually a sign that you're putting too much information into the path.

Use the appropriate location:

```text
Resource identity → params
Filtering/options → query
Data being created/updated → body
Authentication identity → req.user
```

# 19. Example: updating a Todo

Request:

```http
PATCH /api/v1/todos/64abc
Content-Type: application/json
```

Body:

```json
{
    "title": "Learn Service Layer",
    "completed": true
}
```

Controller:

```js
export const updateTodo = async (req, res) => {
    const { id } = req.params;

    const {
        title,
        completed
    } = req.body;

    const updatedTodo = await todoService.updateTodo(id, {
        title,
        completed
    });

    return res.status(200).json({
        success: true,
        data: updatedTodo
    });
};
```

Here:

```text
req.params.id
        ↓
which Todo?

req.body
        ↓
what should change?
```

This distinction is fundamental.

# 20. Route parameters and authorization

Here's where things become more interesting.

Suppose:

```http
DELETE /api/v1/todos/123
```

You get:

```js
const { id } = req.params;
```

But knowing the Todo ID isn't enough.

You also need to know:

```js
req.user.id
```

Then your Service can determine whether:

```text
authenticated user
        ↓
owns Todo 123?
        ↓
yes → delete
no  → reject
```

So a secure architecture might look like:

```text
Request
   ↓
Authentication middleware
   ↓
req.user
   ↓
Controller
   ↓
req.params.id
   ↓
Service
   ↓
Ownership check
   ↓
Repository
```

This connects `req.params` directly to the authorization concepts you learned in Phase 10.

---

# 21. Never trust the parameter

Suppose the user requests:

```http
DELETE /todos/999
```

The fact that `999` came from the URL doesn't mean:

> "This Todo belongs to the current user."

It's simply:

```text
client requested resource 999
```

Your backend must still determine:

```text
Does Todo 999 exist?
Does this user have permission?
Is this operation allowed?
```

So:

```js
req.params.id
```

is **input**, not proof of authorization.

That's an important security mindset.

---

# 22. Validation of route parameters

Suppose your MongoDB ID should be a valid ObjectId.

The client requests:

```http
GET /todos/hello
```

Then:

```js
req.params.id
```

is:

```text
"hello"
```

Your validation layer can check whether it's a valid ID before the Service or Repository tries to query the database.

Conceptually:

```text
Request
   ↓
req.params.id
   ↓
Parameter validation
   ↓
valid?
 ┌─┴─┐
No  Yes
 ↓    ↓
400  Controller
      ↓
    Service
```

This is much cleaner than putting every validation check directly inside the Controller.

---

# 23. Don't assume the resource exists

Even if:

```js
req.params.id
```

contains a valid-looking ID, the resource might not exist.

For example:

```text
GET /todos/64abc...
```

The ID may be syntactically valid but the Todo may have been deleted.

So there are two separate questions:

```text
1. Is the ID valid?
2. Does a resource with this ID exist?
```

And another:

```text
3. Is the current user allowed to access it?
```

These are different concerns.

# 24. A clean architecture example

Controller:

```js
export const getTodo = async (req, res) => {
    const { id } = req.params;

    const todo = await todoService.getTodo({
        todoId: id,
        userId: req.user.id
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

Service:

```js
export const getTodo = async ({ todoId, userId }) => {
    // business rules
};
```

Repository:

```js
export const findTodoById = async (todoId) => {
    // database access
};
```

Notice the separation:

```text
Controller
  ↓
HTTP-specific data

Service
  ↓
application/business data

Repository
  ↓
database-specific operations
```

That's the architecture you're gradually building throughout Phase 11.

# 25. A subtle but important point

You might write:

```js
todoService.getTodo(req.params.id);
```

That's perfectly reasonable.

But you might eventually prefer:

```js
todoService.getTodo({
    todoId: req.params.id,
    userId: req.user.id
});
```

Why?

Because the Service might need more application context than just the ID.

For example:

```text
todoId
userId
role
organizationId
```

The Controller translates HTTP information into a meaningful application-level input.

That's one of its main responsibilities.

# 30. The three-way comparison

This is worth memorizing:

|Client data|Express property|Example|
|---|---|---|
|URL path|`req.params`|`/todos/123`|
|Query string|`req.query`|`?page=2`|
|Request body|`req.body`|`{ "title": "Learn" }`|

So:

```text
GET /todos/123?page=2

        │
        ├── 123
        │    ↓
        │ req.params.id
        │
        └── 2
             ↓
         req.query.page
```

And with:

```http
PATCH /todos/123?page=2
```

```json
{
    "title": "Learn Express"
}
```

you have:

```text
req.params.id
       ↓
     "123"

req.query.page
       ↓
      "2"

req.body.title
       ↓
"Learn Express"
```

# 31. Common mistakes

### Mistake 1

Route:

```js
router.get("/users/:id", controller);
```

Then writing:

```js
req.params.userId
```

❌ Wrong.

Use:

```js
req.params.id
```

because the parameter is named `id`.

---

### Mistake 2

Thinking the parameter is a number:

```js
req.params.id === 123
```

Usually false if `123` came from the URL.

It's:

```js
req.params.id === "123"
```

---

### Mistake 3

Assuming a valid ID means authorized access.

```js
const { id } = req.params;
```

doesn't prove ownership.

---

### Mistake 4

Doing database work directly in the Controller:

```js
const todo = await Todo.findById(req.params.id);
```

For the architecture we're building, this responsibility will eventually belong to the Service/Repository layers.

# 33. Final architecture

At this stage, your Controller mental model should be:

```text
                 HTTP REQUEST
                      │
          ┌───────────┼───────────┐
          │           │           │
       params       query       body
          │           │           │
          ▼           ▼           ▼
     req.params   req.query   req.body
          │           │           │
          └───────────┼───────────┘
                      ▼
                 CONTROLLER
                      │
              extract/translate
                      │
                      ▼
                   SERVICE
                      │
                      ▼
                 REPOSITORY
                      │
                      ▼
                   DATABASE
```

The most important sentence from this lesson is:

> **`req.params` contains values captured from dynamic segments of the route URL.**

For example:

```js
router.get("/todos/:id", getTodo);
```

and:

```http
GET /todos/123
```

gives:

```js
req.params.id
// "123"
```

Once this becomes natural, you'll find CRUD Controllers much easier to understand.
