# Lesson 11.8 — Reading `req.query`

In the previous lesson, we learned:

```js
req.params
```

which is mainly used for identifying a specific resource:

```http
GET /todos/123
```

Now we're going to learn:

```js
req.query
```

This becomes **extremely important** when building real-world APIs because query parameters are commonly used for:

- filtering
    
- searching
    
- pagination
    
- sorting
    
- selecting options
    
- controlling how much data the API returns
    

---

# 1. What is `req.query`?

`req.query` contains the parameters that appear **after `?` in the URL**.

For example:

```http
GET /api/v1/todos?page=2
```

The query string is:

```text
?page=2
```

Express makes it available through:

```js
req.query
```

So:

```js
req.query.page
```

gives:

```text
"2"
```

The basic idea:

```text
/api/v1/todos?page=2
                  │
                  ▼
              req.query
```

---

# 2. Simple example

Route:

```js
router.get("/todos", getTodos);
```

Request:

```http
GET /todos?page=2
```

Controller:

```js
export const getTodos = (req, res) => {
    console.log(req.query);

    return res.json({
        success: true,
        query: req.query
    });
};
```

The result is approximately:

```json
{
    "success": true,
    "query": {
        "page": "2"
    }
}
```

Notice that `page` is generally a **string**.

---

# 3. Query parameters are optional

This is an important difference between `req.params` and `req.query`.

A route parameter:

```js
router.get("/todos/:id", getTodo);
```

requires:

```text
/todos/123
```

But query parameters can simply be omitted:

```http
GET /todos
```

or included:

```http
GET /todos?page=2
```

or:

```http
GET /todos?page=2&limit=10
```

So query parameters are often used for **optional instructions** to the API.

---

# 4. Multiple query parameters

Suppose:

```http
GET /todos?page=2&limit=10
```

Then:

```js
req.query
```

looks like:

```js
{
    page: "2",
    limit: "10"
}
```

You can write:

```js
const { page, limit } = req.query;
```

Then:

```text
page  → "2"
limit → "10"
```

---

# 5. Query parameters are strings

This is one of the most important things to remember.

Request:

```http
GET /todos?page=2&limit=10
```

Don't assume:

```js
req.query.page
```

is:

```js
2
```

It is generally:

```js
"2"
```

So:

```js
typeof req.query.page
```

is generally:

```text
"string"
```

If you need a number:

```js
const page = Number(req.query.page);
```

But simply doing:

```js
Number(undefined)
```

would give:

```text
NaN
```

So you'll usually want defaults and validation.

---

# 6. Why do APIs use query parameters?

Imagine your application has:

```text
100,000 todos
```

The client doesn't want all 100,000 records.

It might request:

```http
GET /todos?page=1&limit=20
```

Meaning:

> "Give me the first 20 todos."

Or:

```http
GET /todos?completed=true
```

Meaning:

> "Give me completed todos."

Or:

```http
GET /todos?search=node
```

Meaning:

> "Search todos related to node."

This is where `req.query` becomes extremely useful.

---

# 7. Query parameters for filtering

Suppose you have:

```http
GET /todos?completed=true
```

Controller:

```js
export const getTodos = async (req, res) => {
    const { completed } = req.query;

    const todos = await todoService.getTodos({
        completed
    });

    return res.status(200).json({
        success: true,
        data: todos
    });
};
```

The flow:

```text
Client
  ↓
?completed=true
  ↓
req.query.completed
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

---

# 8. Filtering by multiple values

You can have:

```http
GET /todos?completed=true&priority=high
```

Then:

```js
const {
    completed,
    priority
} = req.query;
```

gives:

```text
completed → "true"
priority  → "high"
```

You can pass them to your Service:

```js
const todos = await todoService.getTodos({
    completed,
    priority
});
```

The Service can then apply the appropriate business/data-access rules.

---

# 9. Search

Query parameters are commonly used for search.

For example:

```http
GET /users?search=rahul
```

Controller:

```js
export const getUsers = async (req, res) => {
    const { search } = req.query;

    const users = await userService.getUsers({
        search
    });

    return res.status(200).json({
        success: true,
        data: users
    });
};
```

The Controller doesn't need to know how MongoDB performs the search.

It simply translates:

```text
HTTP query
   ↓
application input
```

---

# 10. Pagination

Pagination is one of the most important uses of `req.query`.

Suppose you have thousands of products.

Instead of:

```http
GET /products
```

returning everything, the client can request:

```http
GET /products?page=2&limit=20
```

Meaning:

```text
page  = 2
limit = 20
```

Controller:

```js
export const getProducts = async (req, res) => {
    const { page, limit } = req.query;

    const result = await productService.getProducts({
        page,
        limit
    });

    return res.status(200).json({
        success: true,
        data: result
    });
};
```

---

# 11. Why pagination matters

Imagine:

```text
1,000,000 products
```

Sending:

```http
GET /products
```

and returning all of them would be terrible.

Instead:

```text
Request 1:
?page=1&limit=20

Request 2:
?page=2&limit=20

Request 3:
?page=3&limit=20
```

The client gets manageable chunks.

This improves:

- response size
    
- database workload
    
- frontend performance
    
- network usage
    
- user experience
    

---

# 12. Don't trust `page` and `limit`

Suppose the client sends:

```http
GET /products?page=hello&limit=banana
```

You shouldn't blindly pass that into your database logic.

Remember:

```text
req.query
   ↓
client input
   ↓
untrusted
```

Your validation layer should check things like:

```text
page → positive integer
limit → positive integer
```

So the architecture becomes:

```text
Request
   ↓
req.query
   ↓
Validation
   ↓
Controller
   ↓
Service
```

---

# 13. Defaults

Suppose the client sends:

```http
GET /products
```

There is no:

```js
req.query.page
```

So you can establish defaults.

For example:

```js
const page = Number(req.query.page) || 1;
const limit = Number(req.query.limit) || 20;
```

This means:

```text
page  → 1 by default
limit → 20 by default
```

However, be careful with this pattern because `||` treats `0` as false.

For production code, validation/defaulting through a dedicated validation layer is cleaner.

For example, conceptually:

```text
req.query
   ↓
schema validation
   ↓
{
    page: 1,
    limit: 20
}
   ↓
Controller
```

That's the direction your starter architecture is moving toward.

---

# 14. Pagination math

A common pagination formula is:

```text
skip = (page - 1) × limit
```

For:

```text
page = 1
limit = 20
```

we get:

```text
skip = (1 - 1) × 20
     = 0
```

For:

```text
page = 2
limit = 20
```

we get:

```text
skip = (2 - 1) × 20
     = 20
```

For:

```text
page = 3
limit = 20
```

we get:

```text
skip = (3 - 1) × 20
     = 40
```

This is usually Repository/database logic rather than Controller logic.

The Controller should not become a huge database-query function.

---

# 15. Sorting

Query parameters can also control sorting.

For example:

```http
GET /products?sort=price
```

or:

```http
GET /products?sort=-price
```

A common convention is:

```text
price
```

for ascending order and:

```text
-price
```

for descending order.

Controller:

```js
const { sort } = req.query;

const products = await productService.getProducts({
    sort
});
```

Again, the Controller simply extracts the request information.

The actual database sorting belongs deeper in the architecture.

---

# 16. Multiple sorting fields

A more advanced API might support:

```http
GET /products?sort=price,-createdAt
```

meaning something like:

```text
price ascending
createdAt descending
```

But don't rush into complicated query formats.

Start with:

```text
?page=1
?limit=20
?sort=price
```

Then gradually build more advanced functionality.

```http
GET /products?page=2&limit=20&category=phone&sort=-price
```

Now:

```js
const {
```


Notice how readable this is.

The Controller doesn't build a MongoDB query.

It simply translates HTTP input into application input.

# 19. `req.query` is an object

For:

```http
GET /todos?page=2&limit=10&completed=true
```

you can think of:

```js
req.query
```

as:

```js
{
    page: "2",
    limit: "10",
    completed: "true"
}
```

Therefore:

```js
const { page, limit, completed } = req.query;
```

is very common.

---

# 20. Query parameters and boolean values

This is a common beginner mistake.

Request:

```http
GET /todos?completed=true
```

You might think:

```js
req.query.completed
```

is:

```js
true
```

But it is generally:

```js
"true"
```

That's a string.

So this:

```js
if (completed === true) {
    // ...
}
```

may not work as expected.

You need to parse/validate it.

For example:

```js
const completed = req.query.completed === "true";
```

But in your production architecture, a validation/schema layer can handle this conversion more cleanly.

---

# 21. Query parameters and numbers

Same issue with:

```http
?page=2&limit=20
```

You'll receive values like:

```js
{
    page: "2",
    limit: "20"
}
```

If your application needs numbers:

```js
const page = Number(req.query.page);
const limit = Number(req.query.limit);
```

But again:

```text
parsing + validation
```

should eventually be handled systematically rather than manually repeated throughout Controllers.

That's one of the reasons Phase 9 validation was important.

---

# 22. Query parameters are optional input

Consider:

```http
GET /products
```

There may be no query parameters.

So:

```js
req.query
```

can simply be:

```js
{}
```

Then:

```js
const { search, page, limit } = req.query;
```

may give:

```text
search → undefined
page   → undefined
limit  → undefined
```

Your validation/defaulting layer can then provide appropriate defaults.

# 23. Query parameters vs route parameters

Let's make this distinction very clear.

### Route parameter

```http
GET /products/123
```

Route:

```js
router.get("/products/:id", getProduct);
```

Access:

```js
req.params.id
```

Meaning:

> Which product?

---

### Query parameter

```http
GET /products?category=phone
```

Access:

```js
req.query.category
```

Meaning:

> How should I filter the products?

A useful mental model:

```text
/products/123
          ↑
       identity

/products?category=phone
                   ↑
                options
```

---

# 24. Route + query together

This is very common:

```http
GET /users/123/orders?page=2&limit=10
```

Route:

```js
router.get(
    "/users/:userId/orders",
    getUserOrders
);
```

Controller:

```js
export const getUserOrders = async (req, res) => {
    const { userId } = req.params;
    const { page, limit } = req.query;

    const result = await orderService.getUserOrders({
        userId,
        page,
        limit
    });

    return res.status(200).json({
        success: true,
        data: result
    });
};
```

Here:

```text
req.params.userId
        ↓
which user's orders?

req.query.page
        ↓
which page?

req.query.limit
        ↓
how many?
```

This is a very realistic Controller.

---

# 25. Query parameters don't have to be database filters

They're often used for other things too.

For example:

```http
GET /products?includeReviews=true
```

or:

```http
GET /users?includeProfile=true
```

or:

```http
GET /posts?format=summary
```

The query string can communicate optional behavior.

So don't think:

```text
req.query = database filter only
```

Instead:

> **`req.query` contains optional parameters that modify or describe how the client wants the resource.**

---

# 26. Example: `include`

Suppose:

```http
GET /products/123?includeReviews=true
```

Then:

```js
const { id } = req.params;
const { includeReviews } = req.query;
```

Your Controller might call:

```js
const product = await productService.getProduct({
    id,
    includeReviews
});
```

The Service can decide how to handle the request.

---

# 27. Query parameter naming

Use clear names.

Good:

```text
?page=2
?limit=20
?search=node
?sort=price
?category=electronics
?completed=true
```

Less clear:

```text
?p=2
?l=20
?s=node
?x=price
```

Short names may save a few characters, but descriptive names make APIs easier to understand.

---

# 28. Don't make query strings too complicated

You might eventually see APIs with:

```http
/products?
filter[category]=phone&
filter[price][gte]=500&
filter[price][lte]=1000&
sort=-price&
page=2&
limit=20
```

These are valid design approaches, but don't try to master advanced query syntax immediately.

Your learning progression should be:

```text
Basic query
    ↓
Filtering
    ↓
Pagination
    ↓
Sorting
    ↓
Search
    ↓
Combined queries
    ↓
Advanced filtering
```

You're currently building the foundation.

---

# 29. Query parsing belongs somewhere

A common beginner Controller can become messy:

```js
export const getProducts = async (req, res) => {
    let page = Number(req.query.page);

    if (!page) {
        page = 1;
    }

    let limit = Number(req.query.limit);

    if (!limit) {
        limit = 20;
    }

    if (limit > 100) {
        limit = 100;
    }

    // more validation...
    
    // database query...
    
    // response...
};
```

This quickly becomes hard to maintain.

Our architecture aims for:

```text
Request
   ↓
Validation
   ↓
Clean/validated query
   ↓
Controller
   ↓
Service
```

Then the Controller can stay small.

---

# 30. A cleaner future Controller

Eventually you want something closer to:

```js
export const getProducts = asyncHandler(async (req, res) => {
    const result = await productService.getProducts({
        ...req.query
    });

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

Or, even better, if validation has transformed the data:

```js
export const getProducts = asyncHandler(async (req, res) => {
    const result = await productService.getProducts(
        req.validatedQuery
    );

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

The exact implementation will depend on the validation architecture we'll use later.

The important idea is:

```text
Raw query
   ↓
Validation/parsing
   ↓
Clean query
   ↓
Controller
```

# 32. The Controller should not build MongoDB queries

Avoid doing this inside the Controller:

```js
const filter = {};

if (req.query.completed) {
    filter.completed = req.query.completed;
}

if (req.query.priority) {
    filter.priority = req.query.priority;
}

const todos = await Todo.find(filter)
    .skip(...)
    .limit(...)
    .sort(...);
```

Technically it can work.

But now the Controller is responsible for:

```text
HTTP
+
validation
+
business logic
+
database query construction
+
database access
```

That's exactly what our layered architecture is trying to prevent.

Instead:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
MongoDB
```

# 33. Query parameters and the Repository

Eventually, you might have:

```js
todoRepository.findMany({
    search,
    completed,
    priority,
    page,
    limit,
    sort
});
```

The Repository can translate that into a MongoDB query.

For example, conceptually:

```text
Application filters
        ↓
Repository
        ↓
MongoDB filter
```

The Controller shouldn't need to know MongoDB syntax.

# 34. A complete example

### Route

```js
router.get("/todos", getTodos);
```

### Controller

```js
export const getTodos = async (req, res) => {
    const {
        search,
        completed,
        priority,
        page,
        limit,
        sort
    } = req.query;

    const result = await todoService.getTodos({
        search,
        completed,
        priority,
        page,
        limit,
        sort
    });

    return res.status(200).json({
        success: true,
        data: result
    });
};
```

### Service

```js
export const getTodos = async (filters) => {
    return todoRepository.findMany(filters);
};
```

### Repository

```js
export const findMany = async (filters) => {
    // Build database query here
};
```

Now responsibilities are clear:

```text
Controller
→ HTTP

Service
→ application/business logic

Repository
→ database
```

# 35. Query parameters and pagination response

A good paginated API often returns metadata too.

For example:

```json
{
    "success": true,
    "data": [
        {
            "id": "1",
            "title": "Learn Node"
        },
        {
            "id": "2",
            "title": "Learn Express"
        }
    ],
    "pagination": {
        "page": 2,
        "limit": 10,
        "total": 57,
        "totalPages": 6
    }
}
```

The client can then know:

```text
Current page → 2
Items/page   → 10
Total items  → 57
Total pages  → 6
```

The exact response format should be standardized across your application rather than reinvented for every Controller.

# 41. Common mistakes

### Mistake 1 — Treating query values as numbers

```js
const page = req.query.page;

page + 1;
```

If:

```text
page = "2"
```

you may get:

```text
"21"
```

instead of:

```text
3
```

Parse/validate the value.

---

### Mistake 2 — Treating `"false"` as boolean `false`

Remember:

```js
Boolean("false")
```

is actually:

```text
true
```

because `"false"` is a non-empty string.

So don't blindly use:

```js
Boolean(req.query.completed)
```

for query booleans.

---

### Mistake 3 — Trusting arbitrary query parameters

The client can send:

```http
?isAdmin=true
```

That doesn't make the user an admin.

Query parameters are client-controlled input.

---

### Mistake 4 — Building database queries in Controllers

Keep:

```text
HTTP handling → Controller

business rules → Service

database operations → Repository
```

```text
│       ↓                             │
│   req.params                         │
│                                     │
│ ?page=2&limit=10                    │
│       ↓                             │
│   req.query                          │
│                                     │
│ { "title": "Learn Node" }           │
│       ↓                             │
│   req.body                           │
│                                     │
└─────────────────────────────────────┘
```

And the mental model:

```text
req.params
    ↓
"Which resource?"

req.query
    ↓
"How do you want the resource?"

req.body
    ↓
"What data are you sending?"
```

It's not a universal rule, but it's an excellent mental model for your CRUD APIs.

# 43. Your Controller toolbox so far

You now have:

```js
req.body
req.params
req.query
req.headers
req.user

res.status()
res.json()
res.send()
```

The next important step is learning how to use them together without turning the Controller into a huge function.

For example:

```js
export const updateTodo = async (req, res) => {
    const { id } = req.params;

    const {
        notify
    } = req.query;

    const {
        title,
        completed
    } = req.body;

    const userId = req.user.id;

    const todo = await todoService.updateTodo({
        todoId: id,
        userId,
        title,
        completed,
        notify
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

This is the direction we're heading toward.

And remember:

> **Query parameters are client-provided input. Parse, validate, and constrain them before relying on them.**

The most important architectural idea from this lesson is:

```text

    ↓
Controller
    ↓
clean application input
    ↓
Service
```
