# Lesson 11.9 — Reading `req.user`

Great. This is the **most important Controller lesson so far**, because now we're connecting the Controller phase with the **authentication system from Phase 10**.

Your Phase 11 roadmap specifically places **11.9 — Reading `req.user`** immediately after `req.body`, `req.params`, and `req.query`.

The key idea is:

> **`req.user` represents the authenticated user attached to the request by authentication middleware.**

---

## 1. First: where does `req.user` come from?

You don't normally get `req.user` automatically from Express.

Instead, your authentication middleware creates it.

Think about this request:

```http
GET /api/v1/profile
Authorization: Bearer <access-token>
```

The flow is:

```text
Client
  │
  │ Access Token
  ▼
Authentication Middleware
  │
  │ verify token
  ▼
User identified
  │
  │ req.user = user information
  ▼
Controller
```

So:

```js
req.user
```

is basically a bridge between:

```text
Authentication
      ↓
Controller
```

---

# 2. Why do we need `req.user`?

Imagine the logged-in user sends:

```http
GET /api/v1/profile
```

How does your Controller know **which user's profile** to return?

You could ask the client:

```http
GET /api/v1/users/123
```

But that creates a problem.

The client could try:

```http
GET /api/v1/users/456
```

Are they actually allowed to access user `456`?

Instead, authentication already tells us:

```text
"This request belongs to user 123."
```

That information can be attached to:

```js
req.user
```

Then your Controller can use it.

---

# 3. A simple example

Authentication middleware:

```js
const authenticate = (req, res, next) => {
    req.user = {
        id: "123",
        role: "student"
    };

    next();
};
```

Route:

```js
router.get(
    "/profile",
    authenticate,
    getProfile
);
```

Controller:

```js
export const getProfile = async (req, res) => {
    const userId = req.user.id;

    return res.status(200).json({
        success: true,
        userId
    });
};
```

Request:

```http
GET /profile
```

Response:

```json
{
    "success": true,
    "userId": "123"
}
```

---

# 4. `req.user` is normally created by middleware

This is the important architecture:

```text
Request
   │
   ▼
Authentication Middleware
   │
   ├── read token
   ├── verify token
   ├── identify user
   │
   ▼
req.user
   │
   ▼
Controller
```

So when you see:

```js
req.user
```

you should immediately think:

> "Authentication middleware must have run before this Controller."

---

# 5. What should `req.user` contain?

This depends on your application.

A simple example:

```js
req.user = {
    id: user._id,
    role: user.role
};
```

You might eventually have:

```js
req.user = {
    id: user._id,
    role: user.role,
    email: user.email
};
```

But don't put everything into `req.user`.

For example, you should **not** attach:

```js
req.user = {
    id,
    email,
    password,
    refreshToken,
    passwordResetToken
};
```

Sensitive information should not be unnecessarily carried around.

A safer mental model is:

```text
req.user
   ↓
minimal identity/context required by the request
```

---

# 6. `req.user` vs `req.params`

This distinction is extremely important.

Suppose:

```http
GET /users/456
```

and the currently authenticated user is `123`.

Then:

```js
req.params.id
```

is:

```text
"456"
```

while:

```js
req.user.id
```

is:

```text
"123"
```

Visualize it:

```text
GET /users/456
       │
       └──── req.params.id
             ↓
            456


Authorization token
       │
       └──── req.user.id
             ↓
            123
```

One is:

> **The resource being requested.**

The other is:

> **The authenticated user making the request.**

---

# 7. Why this matters for security

Suppose we have:

```http
PATCH /users/456
```

and:

```js
req.user.id === "123"
```

The user is trying to modify user `456`.

Your application needs to decide:

```text
Does user 123 have permission
to modify user 456?
```

That's an authorization question.

So:

```text
req.user
   ↓
Who are you?

req.params
   ↓
What resource are you requesting?

authorization logic
   ↓
Are you allowed?
```

This is one of the most important backend concepts you'll use.

---

# 8. `req.user` and a profile endpoint

Consider:

```http
GET /api/v1/profile
```

You don't need:

```text
/profile/123
```

because the authenticated identity already tells you who the user is.

Controller:

```js
export const getProfile = async (req, res) => {
    const { id } = req.user;

    const user = await userService.getProfile(id);

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Flow:

```text
JWT
 ↓
Authentication middleware
 ↓
req.user.id
 ↓
Controller
 ↓
userService.getProfile()
 ↓
Repository
 ↓
MongoDB
```

That's a very clean design.

---

# 9. `req.user` and the Service layer

A good Controller might look like:

```js
export const getProfile = async (req, res) => {
    const { id } = req.user;

    const user = await userService.getProfile(id);

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Notice what the Service receives:

```js
id
```

It doesn't receive the entire Express request:

```js
// Avoid this
userService.getProfile(req);
```

Instead:

```js
userService.getProfile(id);
```

This keeps your Service independent from Express.

---

# 10. Why shouldn't the Service receive `req`?

Imagine:

```js
userService.getProfile(req);
```

Now the Service knows about:

```text
Express
req
HTTP
headers
params
query
body
```

That's unnecessary coupling.

Instead:

```js
userService.getProfile(userId);
```

The Service only knows:

```text
"I need a user ID."
```

That's a much cleaner boundary.

Your Phase 11 → 12 progression is designed exactly for this separation: Controllers translate HTTP input, while Services handle application/business logic.

# 11. Example: Update current user's profile

Request:

```http
PATCH /api/v1/profile
```

Body:

```json
{
    "name": "Rahul Kumar"
}
```

Authentication middleware gives:

```js
req.user = {
    id: "123"
};
```

Controller:

```js
export const updateProfile = async (req, res) => {
    const { id } = req.user;

    const { name } = req.body;

    const user = await userService.updateProfile(id, {
        name
    });

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Notice:

```text
User identity
    ↓
req.user.id

New profile data
    ↓
req.body
```

Perfect separation.

# 12. `req.user` + `req.body`

This combination appears constantly.

Example:

```http
PATCH /api/v1/profile
```

Body:

```json
{
    "name": "Rahul",
    "bio": "Backend developer"
}
```

Controller:

```js
const { id } = req.user;

const {
    name,
    bio
} = req.body;
```

Now you have:

```text
req.user.id
     ↓
Who is changing the data?

req.body
     ↓
What data are they changing?
```

# 13. `req.user` + `req.params`

Consider:

```http
PATCH /api/v1/users/456
```

and:

```js
req.user.id === "123";
```

You have:

```js
const { id: targetUserId } = req.params;
const { id: currentUserId } = req.user;
```

Now:

```text
currentUserId = 123
targetUserId  = 456
```

Your authorization logic can determine whether the operation is allowed.

For example:

```text
123 editing 456
      ↓
Is 123 an admin?
      ↓
yes → allow
no  → reject
```

Don't put this kind of authorization decision blindly into the Controller; it will become more structured as we move into the Service/authorization lessons.

---

# 14. `req.user` + `req.query`

Suppose:

```http
GET /api/v1/my-courses?page=2&limit=10
```

Authentication middleware:

```js
req.user = {
    id: "123"
};
```

Controller:

```js
export const getMyCourses = async (req, res) => {
    const { id } = req.user;

    const {
        page,
        limit
    } = req.query;

    const result = await courseService.getMyCourses({
        userId: id,
        page,
        limit
    });

    return res.status(200).json({
        success: true,
        data: result
    });

```

Now:

```text
req.user
   ↓
which student?

req.query
   ↓
which page/how many?
```

# 15. A very realistic Controller

Let's combine everything you've learned so far.

Request:

```http
PATCH /api/v1/todos/456?notify=true
```

Body:

```json
{
    "title": "Learn Controllers"
}
```

Authentication middleware:

```js
req.user = {
    id: "123",
    role: "student"
};
```

Controller:

```js
export const updateTodo = async (req, res) => {
    const { id: todoId } = req.params;

    const { notify } = req.query;

    const { title } = req.body;

    const { id: userId } = req.user;

    const todo = await todoService.updateTodo({
        todoId,
        userId,
        title,
        notify
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
};
```

Now you can see the Controller as a **translator**:

```text
HTTP
 │
 ├── params → todoId
 ├── query  → notify
 ├── body   → title
 └── user   → userId
 │
 ▼
Service input
```

This is exactly what a thin Controller should do.

# 16. Authentication middleware example

Let's create a simplified authentication middleware just to understand where `req.user` comes from.

```js
const authenticate = (req, res, next) => {
    const token = req.headers.authorization;

    // token verification would happen here

    const user = {
        id: "123",
        role: "student"
    };

    req.user = user;

    next();
};
```

Then:

```js
router.get(
    "/profile",
    authenticate,
    getProfile
);
```

Execution:

```text
GET /profile
      ↓
authenticate()
      ↓
req.user = {...}
      ↓
next()
      ↓
getProfile()
      ↓
req.user available
```

---

# 17. What happens if authentication middleware doesn't run?

Suppose you write:

```js
router.get(
    "/profile",
    getProfile
);
```

but your Controller does:

```js
const { id } = req.user;
```

There may be no:

```js
req.user
```

So you'll get an error or unexpected behavior.

That's why protected routes normally have:

```text
authentication middleware
       ↓
controller
```

not:

```text
controller
```

by itself.

---

# 18. Middleware order matters

Correct:

```js
router.get(
    "/profile",
    authenticate,
    getProfile
);
```

Incorrect:

```js
router.get(
    "/profile",
    getProfile,
    authenticate
);
```

Why?

Because Controllers execute in order.

Correct:

```text
authenticate
    ↓
req.user created
    ↓
getProfile
    ↓
req.user available
```

Incorrect:

```text
getProfile
    ↓
req.user doesn't exist yet
    ↓
authenticate
```

This connects directly with the middleware execution-order concepts from your earlier Phase 7 lessons.

---

# 19. What should authentication middleware actually do?

A production authentication middleware typically does something conceptually like:

```text
Request
  ↓
Read Authorization header
  ↓
Extract token
  ↓
Verify token
  ↓
Extract identity
  ↓
Find/validate user if required
  ↓
Attach safe user context
  ↓
next()
```

Then:

```js
req.user
```

might contain:

```js
{
    id: "...",
    role: "student"
}
```

The Controller doesn't need to know how the token was verified.

That's another major benefit of middleware.

---

# 20. `req.user` is not necessarily the complete database user

This is a subtle but important concept.

Suppose your MongoDB User document contains:

```js
{
    _id,
    name,
    email,
    passwordHash,
    role,
    refreshToken,
    createdAt,
    updatedAt
}
```

You don't necessarily want:

```js
req.user = entireUserDocument;
```

Instead, you might use:

```js
req.user = {
    id: user._id,
    role: user.role
};
```

Why?

Because `req.user` should represent **request identity/context**, not necessarily be a copy of the entire database document.

---

# 21. Don't trust `req.user` blindly either

This may sound strange:

> "If the middleware created it, why wouldn't we trust it?"

Because security depends on the authentication middleware being correct.

For example, if authentication middleware does:

```js
req.user = {
    id: req.body.userId
};
```

that's dangerous.

The client could send:

```json
{
    "userId": "someone-else"
}
```

Authentication identity should come from a **verified authentication mechanism**, such as a validated access token/session—not from arbitrary client input.

---

# 22. `req.user` and authorization

Remember the distinction:

```text
Authentication
    ↓
Who are you?

Authorization
    ↓
What are you allowed to do?
```

`req.user` is usually the information that helps authorization answer the second question.

For example:

```js
req.user = {
    id: "123",
    role: "admin"
};
```

Then authorization middleware might check:

```text
role === "admin"?
```

and allow:

```text
next()
```

or reject:

```text
403 Forbidden
```

---

# 23. Example: role middleware

Suppose:

```js
const requireAdmin = (req, res, next) => {
    if (req.user.role !== "admin") {
        return res.status(403).json({
            success: false,
            message: "Admin access required"
        });
    }

    next();
};
```

Route:

```js
router.delete(
    "/users/:id",
    authenticate,
    requireAdmin,
    deleteUser
);
```

Flow:

```text
Request
   ↓
authenticate
   ↓
req.user
   ↓
requireAdmin
   ↓
role check
   ↓
deleteUser
```

Now you can see why `req.user` is so important.

# 24. `req.user` and ownership

Suppose students can update only their own profile.

Request:

```http
PATCH /users/456
```

Authenticated user:

```js
req.user.id === "456"
```

Then:

```text
current user = 456
target user  = 456
```

Potentially allowed.

But:

```js
req.user.id === "123"
```

and:

```text
target user = 456
```

Then:

```text
123 ≠ 456
```

The operation might be rejected unless the user has an appropriate elevated role.

This pattern is called an **ownership check**.

You'll encounter it constantly in real APIs.

# 25. `req.user` with todos

Suppose every Todo belongs to a user:

```js
{
    _id: "...",
    title: "Learn Express",
    userId: "123"
}
```

A request:

```http
DELETE /todos/456
```

gives:

```js
req.params.id
```

→ Todo `456`

and:

```js
req.user.id
```

→ current user `123`

The Service/Repository can then ensure:

```text
Todo 456
    ↓
belongs to user 123?
    ↓
yes → delete
no  → reject
```

This is much safer than:

```js
Todo.findByIdAndDelete(req.params.id);
```

because that could potentially delete another user's Todo if authorization isn't checked.

---

# 26. A better Service input

Instead of:

```js
todoService.deleteTodo(todoId);
```

you may eventually have:

```js
todoService.deleteTodo({
    todoId,
    userId
});
```

Then the Service can enforce the application rule:

```text
Delete Todo
    ↓
Does Todo exist?
    ↓
Does it belong to user?
    ↓
Does user have permission?
    ↓
Delete
```

This is one reason Services deserve their own phase.

---

# 27. Don't pass the entire `req.user` unnecessarily

You might see:

```js
todoService.deleteTodo({
    todoId,
    user: req.user
});
```

Sometimes this is useful.

But don't automatically pass the entire object everywhere.

Prefer the smallest meaningful input:

```js
todoService.deleteTodo({
    todoId,
    userId
});
```

or, when role matters:

```js
todoService.deleteTodo({
    todoId,
    userId,
    role
});
```

This makes dependencies clear.

# 28. A complete protected route

Let's put everything together.

### Middleware

```js
const authenticate = (req, res, next) => {
    // verify access token...

    req.user = {
        id: "123",
        role: "student"
    };

    next();
};
```

### Route

```js
router.patch(
    "/todos/:id",
    authenticate,
    updateTodo

```

### Controller

```js
export const updateTodo = async (req, res) => {
    const { id: todoId } = req.params;

    const todo = await todoService.updateTodo({
        todoId,
        userId,
        title
    });

    return res.status(200).json({
        success: true,
        data: todo
    });

```

Architecture:

```text
HTTP request
      ↓
authenticate
      ↓
req.user
      ↓

      │
      ├── req.params

      └── req.user

      ↓

      ↓

```

That's the architecture you are learning to build from scratch.

# 29. Common mistake — assuming `req.user` is built into Express

This:

```js
req.user
```

is not something you should assume Express automatically provides.

Usually your application creates it.

For example:

```js
req.user = {
    id,
    role
};
```

So if you see `req.user` in a project, search for where it is assigned.

A useful debugging technique:

```bash
grep -R "req.user =" .
```

From your Linux terminal, this can help you find where the application attaches the user.

---

# 30. Common mistake — using `req.body.userId` for identity

Avoid patterns like:

```js
const userId = req.body.userId;
```

for authenticated identity.

For example:

```http
POST /todos
```

Body:

```json
{
    "title": "Learn Express",
    "userId": "456"
}
```

If the authenticated user is actually:

```text
123
```

the client is attempting to say:

> "Create this Todo for user 456."

That's dangerous.

Instead:

```js
const { id: userId } = req.user;
```

The server determines the authenticated identity.

Then:

```js
const { title } = req.body;
```

So:

```text
identity → authentication context
data     → request body
```

---

# 31. Common mistake — exposing sensitive user data

Don't casually return:

```js
return res.json({
    user: req.user
});
```

unless you've deliberately designed that response.

For example, if `req.user` eventually contains sensitive/internal information, you don't want to expose it to the client.

Instead, create a response-safe representation:

```js
return res.json({
    success: true,
    data: {
        id: req.user.id,
        role: req.user.role
    }
});
```

Or better, retrieve the appropriate public profile through the Service.

---

# 32. Common mistake — putting authentication logic in Controller

Bad:

```js
export const getProfile = async (req, res) => {
    const token = req.headers.authorization;

    // verify JWT
    // decode JWT
    // check user
    // check expiry
    // ...
    
    // finally get profile
};
```

Now your Controller is doing:

```text
HTTP
+
authentication
+
business logic
+
database
```

Instead:

```text
Authentication middleware
       ↓
req.user
       ↓
Controller
       ↓
Service
```

That's much cleaner.

# 33. The Controller's job

At this point, you can now understand the Controller much better.

A Controller receives:

```text
HTTP information
```

such as:

```js
req.params
req.query
req.body
req.user
```

and converts it into:

```text
application input
```

For example:

```js
const { id: todoId } = req.params;
const { title } = req.body;
const { id: userId } = req.user;

const todo = await todoService.updateTodo({
    todoId,
    userId,
    title
});
```

Then the Service returns something.

The Controller converts it back into:

```text
HTTP response
```

This is why your starter roadmap describes a Controller as an **HTTP translator**.

# 36. One final security lesson

Never think:

```text
req.user.id
    ↓
automatically authorized
```

`req.user` tells you **who is authenticated**.

It doesn't automatically tell you:

> "This person can perform every operation."

That's authorization.

So keep these three concepts separate:

```text
Authentication
     ↓
Who are you?
     ↓
req.user


Authorization
     ↓
What are you allowed to do?
     ↓
role / permissions / ownership


Business logic
     ↓
What should the application actually do?
     ↓
Service
```

This separation will make the upcoming Service lessons much easier.
