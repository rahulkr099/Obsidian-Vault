# Lesson 12.1 — What Is Business Logic?

Welcome to **Phase 12: Services & Business Logic**.

You already learned controllers in Phase 11. Now we're going to answer a very important question:

> **What code actually belongs inside a service?**

If you understand this lesson properly, `service.js` will stop looking like an unnecessary extra file.

---

## 1. First: What Does "Business Logic" Mean?

In simple words:

> **Business logic is the code that describes what your application is supposed to do.**

It represents the **rules, decisions, and processes** of your application.

For example, imagine a Todo application.

A user wants to delete a Todo.

The application might have a rule:

> A user can delete only their own Todo.

That's business logic.

Another rule:

> A completed Todo cannot be edited.

That's business logic.

Another:

> An admin can delete any Todo.

That's also business logic.

So:

```text
Business Logic
     ↓
Rules + Decisions + Application Operations
```

---

# 2. Real-World Example

Imagine a banking application.

A user requests:

```text
Transfer ₹10,000
```

The HTTP part is easy:

```text
POST /api/v1/transfers
```

But the application has to decide:

```text
Does the sender exist?
        ↓
Is the account active?
        ↓
Is there enough balance?
        ↓
Is the receiver valid?
        ↓
Is the transfer allowed?
        ↓
Subtract ₹10,000
        ↓
Add ₹10,000
        ↓
Record transaction
```

Those decisions are **business logic**.

The controller shouldn't be responsible for all of this.

---

# 3. Business Logic Is Not the Same as HTTP Logic

This distinction is extremely important.

Suppose we have:

```js
req.body.email
```

Reading `req.body` is **HTTP/request handling**.

But:

```js
if (existingUser) {
    throw new Error("Email already registered");
}
```

is a business rule.

Similarly:

```js
res.status(201).json(...)
```

is HTTP logic.

But:

```js
const user = await createUser(...)
```

is application logic.

Think:

```text
HTTP concerns
────────────────────
req
res
status codes
headers
cookies
URLs


Business concerns
────────────────────
rules
decisions
calculations
workflows
permissions
application operations
```

---

# 4. A Simple Example

Suppose we have:

```text
POST /api/v1/todos
```

The user sends:

```json
{
    "title": "Learn backend"
}
```

A beginner might write everything inside the controller:

```js
const createTodo = async (req, res) => {

    const { title } = req.body;

    if (!title) {
        return res.status(400).json({
            message: "Title is required"
        });
    }

    if (title.length > 100) {
        return res.status(400).json({
            message: "Title is too long"
        });
    }

    const todo = await Todo.create({
        title,
        userId: req.user.id,
        completed: false
    });

    res.status(201).json({
        success: true,
        data: todo
    });
};
```

It works.

There is nothing inherently wrong with making something work this way in a tiny project.

But notice how many responsibilities this controller has.

```text
Controller
│
├── Reads HTTP input
├── Validates input
├── Applies rules
├── Creates database document
├── Decides default values
└── Creates HTTP response
```

As your application grows, this becomes difficult to maintain.

---

# 5. Let's Identify the Business Logic

Look at this:

```js
const todo = await Todo.create({
    title,
    userId: req.user.id,
    completed: false
});
```

There are some application decisions here.

For example:

```js
userId: req.user.id
```

means:

> Every Todo belongs to the authenticated user.

And:

```js
completed: false
```

means:

> A newly created Todo starts incomplete.

Those are application rules.

---

# 6. Another Example: Login

Imagine:

```text
POST /api/v1/auth/login
```

A login operation might require:

```text
Find user
      ↓
Does user exist?
      ↓
Compare password
      ↓
Is password correct?
      ↓
Generate access token
      ↓
Generate refresh token
      ↓
Store refresh token hash
      ↓
Return authentication result
```

These are business/application operations.

The controller shouldn't need to understand all the internal details.

Instead:

```text
Controller
    ↓
authService.login()
```

The service handles the actual login process.

---

# 7. A Useful Test

When you're unsure whether something is business logic, ask:

> **"If I changed Express to Fastify, would this code still be useful?"**

For example:

```js
res.status(201).json(data);
```

If you switch frameworks, this probably changes.

So it's HTTP-specific.

But:

```js
if (user.role !== "admin") {
    throw new Error("Only admins can perform this action");
}
```

The rule still exists regardless of Express, Fastify, or another framework.

Therefore:

```text
Business rule
     ↓
Framework independent
```

This is a very useful way to identify business logic.

---

# 8. Another Test

Ask:

> **"Would this rule still exist if there were no HTTP API?"**

Imagine your application eventually has:

```text
REST API
React frontend
Admin dashboard
Background worker
CLI
Scheduled job
```

All of them might need the same rule.

For example:

```text
Only admins can delete users.
```

That rule shouldn't exist only because you have:

```text
DELETE /users/:id
```

It is an application rule.

Therefore, it belongs closer to the **service/business layer**.

# 10. Business Logic vs Database Logic

This distinction will become very important in **Phase 13 — Repository Pattern**.

Suppose:

```js
const user = await User.findOne({ email });
```

This is primarily **data access logic**.

You're asking MongoDB:

> Find me a user.

But:

```js
if (!user) {
    throw new AppError("User does not exist", 404);
}
```

is application logic.

And:

```js
if (!isPasswordCorrect) {
    throw new AppError("Invalid credentials", 401);
}
```

is a business/application decision.

So eventually:

```text
Service
   ↓
"Find the user."

Repository
   ↓
"Okay, I'll query MongoDB."
```

We'll learn that separation in Phase 13.

# 11. The Three Layers

For now, remember these three responsibilities:

```text
┌──────────────────────────┐
│       Controller         │
│                          │
│ HTTP communication       │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│        Service           │
│                          │
│ Business/application     │
│ logic                    │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│         Model            │
│                          │
│ Database/data structure  │
└──────────────────────────┘
```

Later we'll insert:

```text
Repository
```

between Service and Model.

# 12. Think About the Controller as a Translator

This is a mental model I want you to remember.

The controller translates:

```text
HTTP
  ↕
Application
```

For example:

```text
req.body
   ↓
Controller
   ↓
service.createTodo(data)
```

Then:

```text
service result
   ↓
Controller
   ↓
res.status(...).json(...)
```

So the controller is basically an **HTTP translator**.

It should not become the place where the entire application lives.

---

# 13. The Service Is the Decision Maker

Think:

```text
Controller:
"User wants to create a Todo."

Service:
"Okay. Let's determine whether this operation is allowed
and what should happen."

Repository:
"I'll retrieve/save the data."

Model:
"I define what the data looks like."

Database:
"I store the data."
```

This gives us:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
    ↓
Database
```

Each layer has a job.

# 14. Before and After

### ❌ Fat Controller

```js
const deleteTodo = async (req, res) => {

    const todo = await Todo.findById(req.params.id);

    if (!todo) {
        return res.status(404).json({
            message: "Todo not found"
        });
    }

    if (todo.userId.toString() !== req.user.id) {
        return res.status(403).json({
            message: "You cannot delete this Todo"
        });
    }

    await Todo.findByIdAndDelete(req.params.id);

    res.status(200).json({
        message: "Todo deleted"
    });
};
```

This controller knows:

```text
HTTP
+
database
+
ownership rule
+
deletion process
```

Too much responsibility.

---

### ✅ Better Architecture

Controller:

```js
const deleteTodo = asyncHandler(async (req, res) => {

    await todoService.deleteTodo(
        req.params.id,
        req.user.id
    );

    res.status(200).json({
        success: true,
        message: "Todo deleted"
    });
});
```

Service:

```js
const deleteTodo = async (todoId, userId) => {

    const todo = await Todo.findById(todoId);

    if (!todo) {
        throw new AppError("Todo not found", 404);
    }

    if (todo.userId.toString() !== userId) {
        throw new AppError(
            "You cannot delete this Todo",
            403
        );
    }

    await Todo.findByIdAndDelete(todoId);
};
```

Now:

```text
Controller
    ↓
todoService.deleteTodo()
    ↓
Business decisions
    ↓
Database operation
```

This is much easier to understand.

---

# 15. Don't Move Everything Into Services

There is an important trap here.

Some beginners learn about services and then create:

```text
Controller
   ↓
Service
```

and put **literally everything** into the service.

For example:

```js
service.createTodo(req, res)
```

❌ Not ideal.

A service shouldn't normally know about:

```js
req
res
next
cookies
HTTP headers
```

Instead:

```js
service.createTodo({
    title,
    userId
});
```

The service receives **application data**, not an Express request.

---

# 16. The Service Should Not Send HTTP Responses

Avoid:

```js
const createUser = async (req, res) => {

    // ...

    return res.status(201).json(...);
};
```

inside a service.

The service should return a result:

```js
return user;
```

Then the controller decides how that result becomes HTTP:

```js
res.status(201).json({
    success: true,
    data: user
});
```

Remember:

```text
Service
   ↓
returns application result

Controller
   ↓
converts result into HTTP response
```

---

# 17. Business Logic Can Be More Than `if`

Business logic isn't only:

```js
if (...) {}
```

It can include:

### Calculations

```js
const total = price * quantity;
```

### Decisions

```js
if (user.isPremium) {
    discount = 20;
}
```

### Workflows

```text
Create order
 ↓
Reserve inventory
 ↓
Create payment
 ↓
Send confirmation
```

### Rules

```text
Only owner can update resource.
```

### State transitions

```text
PENDING
   ↓
PAID
   ↓
SHIPPED
   ↓
DELIVERED
```

All of these can be business logic.

---

# 18. A Very Important Concept: State Changes

Suppose you have an order:

```text
PENDING
```

Can it directly become:

```text
DELIVERED
```

Maybe not.

Your application might require:

```text
PENDING
   ↓
PAID
   ↓
SHIPPED
   ↓
DELIVERED
```

The rule:

> An order can only move from SHIPPED to DELIVERED.

That's business logic.

The database itself doesn't necessarily know that rule.

Your service can enforce it.

---

# 19. Why Services Become Important as Applications Grow

Imagine your application has:

```text
50 controllers
100 routes
30 models
```

If business logic is inside controllers, you'll eventually get:

```text
500-line controller
700-line controller
1000-line controller
```

And then maintenance becomes painful.

With services:

```text
controllers/
    ↓
services/
    ↓
repositories/
```

the responsibilities are separated.

You can modify business rules without rewriting your HTTP layer.

---

# 20. The Golden Rule

Remember this:

> **Controllers handle HTTP. Services handle application decisions.**

Or even shorter:

```text
Controller → "How does HTTP work?"
Service    → "What should the application do?"
```

And later:

```text
Repository → "How do I access the data?"
```

This three-question model is extremely useful.

When you see code, ask:

```text
res

cookies
status codes
```

→ **Controller**

### Does it make an application decision?



```text
Schema
```
