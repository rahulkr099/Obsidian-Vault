# Lesson 12.10 — Calling Repositories from Services

This is one of the **most important lessons in Phase 12**, because this is where the Service Layer connects to the database layer.

Your roadmap explicitly defines 12.10 as **“Calling repositories from services”**. It then moves into authentication, user services, CRUD services, transactions, and service composition.

The core architecture we are building is:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
    ↓
MongoDB
```

Your starter's intended mental model is also:

```text
Service
  ↓
"I need the user."

Repository
  ↓
"Okay, I'll query MongoDB."

Model
  ↓
"Here is the database structure."

MongoDB
  ↓
"Here is the data."
```

Let's understand **why this separation exists**, rather than just learning how to write `repository.findById()`.

---

# 1. The Problem We're Solving

Imagine you have this controller:

```js
const getUser = async (req, res) => {
    const user = await User.findById(req.params.id);

    res.json({
        success: true,
        data: user
    });
};
```

It works.

But look at what's happening:

```text
Controller
   ↓
MongoDB
```

The controller knows:

- HTTP
    
- Express
    
- MongoDB
    
- Mongoose
    
- database queries
    
- response formatting
    

That's too much responsibility.

---

# 2. Then We Introduced Services

We moved business logic out:

```text
Controller
    ↓
Service
    ↓
MongoDB
```

For example:

```js
const getUser = async ({ userId }) => {

    const user = await User.findById(userId);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    return user;
};
```

Better.

But the service still knows:

```js
User.findById(...)
```

So now the Service Layer knows about Mongoose/database implementation.

That's where the Repository Layer comes in.

---

# 3. Repository's Job

The repository answers:

> **"How do I get or modify data?"**

For example:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

The service answers:

> **"What should the application do with that data?"**

For example:

```js
const getUser = async ({ userId }) => {

    const user = await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Now the responsibilities are clear.

---

# 4. The Most Important Difference

Remember this:

### Repository

```text
HOW do I access the data?
```

### Service

```text
WHAT should the application do?
```

Example:

```text
User doesn't exist
```

Repository:

```text
"I found nothing."
```

Service:

```text
"That means this operation cannot continue."
```

That's a very important distinction.

---

# 5. Complete Flow

Suppose the request is:

```http
GET /api/v1/users/123
```

The flow becomes:

```text
HTTP Request
      ↓
Route
      ↓
Middleware
      ↓
Controller
      ↓
User Service
      ↓
User Repository
      ↓
User Model
      ↓
MongoDB
```

Then the result travels back:

```text
MongoDB
   ↓
Model
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
HTTP Response
```

So the full flow is:

```text
              REQUEST
                 ↓
              ROUTE
                 ↓
            MIDDLEWARE
                 ↓
            CONTROLLER
                 ↓
              SERVICE
                 ↓
            REPOSITORY
                 ↓
               MODEL
                 ↓
             MONGODB
                 ↓
              RESULT
                 ↓
            REPOSITORY
                 ↓
              SERVICE
                 ↓
            CONTROLLER
                 ↓
             RESPONSE
```

This is the architecture you should start seeing mentally whenever you build an endpoint.

# 7. User Model

For simplicity:

```js
import mongoose from "mongoose";

const userSchema = new mongoose.Schema({
    name: {
        type: String,
        required: true
    },

    email: {
        type: String,
        required: true,
        unique: true
    }
});

export const User = mongoose.model(
    "User",
    userSchema
);
```

The model describes the database structure.

It doesn't decide:

```text
Should this user be allowed to perform an operation?
```

That's application logic.

---

# 8. User Repository

Create:

```text
repositories/user.repository.js
```

```js
import { User } from "../models/user.model.js";

const findById = async (userId) => {
    return User.findById(userId);
};

const findByEmail = async (email) => {
    return User.findOne({ email });
};

const create = async (data) => {
    return User.create(data);
};

export default {
    findById,
    findByEmail,
    create
};
```

Notice something.

The repository knows:

```text
User
Mongoose
findById
findOne
create
```

It does **not** know:

```text
HTTP
req
res
JWT
cookies
business rules
```

That's exactly what we want.

---

# 9. User Service

Now:

```text
services/user.service.js
```

```js
import userRepository from "../repositories/user.repository.js";
import AppError from "../utils/AppError.js";

const getUserById = async ({ userId }) => {

    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};

export default {
    getUserById
};
```

Look at the difference.

The service says:

```text
I need a user.
        ↓
Repository, find it.
        ↓
No user?
        ↓
Business operation fails.
```

The service doesn't care whether the repository uses:

```text
MongoDB
PostgreSQL
Redis
some external API
```

The repository handles the data-access implementation.

---

# 10. Controller

Then:

```js
const getUser = asyncHandler(async (req, res) => {

    const user =
        await userService.getUserById({
            userId: req.params.id
        });

    res.status(200).json({
        success: true,
        data: user
    });
});
```

The controller knows:

```text
HTTP
```

The service knows:

```text
business logic
```

The repository knows:

```text
database access
```

Beautiful.

---

# 11. Why Not Just Use `User.findById()` in the Service?

You might ask:

> "This seems like extra code. Why not just do `User.findById()` directly in the service?"

For a tiny application, you absolutely can.

The Repository Pattern becomes useful when your application grows.

Your roadmap specifically separates **Services & Business Logic** from **Repository Pattern**, with Phase 13 covering why services shouldn't directly query MongoDB.

The purpose isn't:

> "More files = professional."

The purpose is:

> **Each layer should have a clear responsibility.**

---

# 12. Think About the Future

Today:

```text
MongoDB
```

Tomorrow, maybe:

```text
MongoDB + Redis
```

Or:

```text
MongoDB
    +
external service
```

Or perhaps you change part of the data storage strategy.

If your business logic is filled with:

```js
User.findOne(...)
User.findById(...)
User.updateOne(...)
```

you have database details spread throughout your application.

With a repository:

```text
Service
   ↓
Repository
   ↓
Database implementation
```

the database-specific code has a clear home.

---

# 13. Repository Is a Boundary

Think of the repository as a **database boundary**.

Outside:

```text
Service
```

Inside:

```text
Mongoose
MongoDB
queries
aggregation
indexes
database-specific operations
```

So:

```text
       APPLICATION
            │
            ▼
       ┌───────────┐
       │  SERVICE  │
       └─────┬─────┘
             │
             ▼
       ┌────────────┐
       │ REPOSITORY │ ← database boundary
       └─────┬──────┘
             │
             ▼
          MONGOOSE
             │
             ▼
          MONGODB
```

# 14. Repository Returns Data

Suppose:

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Possible result:

```js
{
    _id: "...",
    name: "Rahul",
    email: "rahul@example.com"
}
```

or:

```js
null
```

The repository doesn't necessarily decide what `null` means from a business perspective.

It simply reports the database result.

---

# 15. Service Interprets the Result

Now:

```js
const user =
    await userRepository.findByEmail(email);

if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

The service interprets:

```text
null
 ↓
user doesn't exist
 ↓
application operation fails
```

That's business/application logic.

# 16. Another Example: Login

This becomes even clearer with authentication.

Suppose:

```text
POST /auth/login
```

The controller sends:

```js
authService.login({
    email,
    password
});
```

The service:

```text
login()
   ↓
repository.findByEmail()
   ↓
user
   ↓
passwordService.compare()
   ↓
generate tokens
   ↓
return authentication result
```

Notice the repository's job:

```text
Find the user.
```

The service's job:

```text
Perform login.
```

These are not the same responsibility.

# 17. Login Example

Repository:

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Service:

```js
const login = async ({
    email,
    password
}) => {

    const user =
        await userRepository.findByEmail(email);

    if (!user) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const valid =
        await passwordService.compare(
            password,
            user.password
        );

    if (!valid) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    // generate tokens...

    return {
        user
    };
};
```

Notice:

```text
Repository
→ Find user.

Password service
→ Compare password.

Auth service
→ Coordinate login.
```

That's service composition.

# 18. Don't Put Business Rules in Repository

Bad:

```js
const findById = async (userId) => {

    const user = await User.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    if (user.isBlocked) {
        throw new AppError(
            "User is blocked",
            403
        );
    }

    return user;
};
```

Why is this problematic?

The repository now knows:

```text
business rules
```

Instead:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

Then service:

```js
const user =
    await userRepository.findById(userId);

if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}

if (user.isBlocked) {
    throw new AppError(
        "User is blocked",
        403
    );
}
```

Now responsibilities are clear.

---

# 19. But Repositories Can Contain Query Logic

This doesn't mean repositories should be stupid.

A repository can contain a sophisticated query.

For example:

```js
const findActiveUserById = async (userId) => {

    return User.findOne({
        _id: userId,
        isActive: true
    });
};
```

That's still data-access logic.

The repository is saying:

> "Here's how I query active users."

It isn't saying:

> "Inactive users are forbidden from doing X."

That decision belongs to the service.

---

# 20. Query vs Business Rule

This distinction is extremely useful.

### Query

```js
User.findOne({
    _id: userId,
    isActive: true
});
```

Repository.

### Business rule

```text
Only active users can create orders.
```

Service.

So:

```text
Repository
→ How can I find it?

Service
→ What does this result mean?
```

---

# 21. Ownership Query

Remember the ownership concept from your roadmap.

Suppose a user wants to retrieve a Todo.

Bad:

```js
Todo.findById(todoId);
```

Better:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

This query can live in the repository:

```js
const findByIdForUser = async ({
    todoId,
    userId
}) => {

    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

Then service:

```js
const todo =
    await todoRepository.findByIdForUser({
        todoId,
        userId
    });

if (!todo) {
    throw new AppError(
        "Todo not found",
        404
    );
}
```

That's a very clean separation.

Your roadmap specifically later emphasizes ownership queries such as querying by both resource ID and authenticated user ID.

---

# 22. Why Ownership Query Is Powerful

Suppose:

```text
User A
   ↓
Todo 123
```

User B sends:

```http
GET /todos/123
```

Repository:

```js
Todo.findOne({
    _id: "123",
    userId: "B"
});
```

Result:

```text
null
```

Service:

```text
Todo not found
```

User B cannot access User A's Todo.

This is much safer than:

```js
Todo.findById("123");
```

and checking ownership later in random places.

---

# 23. Repository Parameters Should Be Meaningful

Bad:

```js
findOne(a, b, c, d, e)
```

Hard to understand.

Better:

```js
findByIdForUser({
    todoId,
    userId
});
```

Now the intent is obvious.

This style also makes adding parameters safer.

---

# 24. Don't Pass `req` Into Repository

Avoid:

```js
userRepository.findUser(req);
```

The repository shouldn't know Express.

Instead:

```js
userRepository.findById({
    userId
});
```

The controller extracts the HTTP information first.

---

# 25. Don't Pass `req` Into Service Either

Avoid:

```js
userService.getUser(req);
```

Instead:

```js
userService.getUser({
    userId: req.params.id
});
```

This keeps the service independent from Express.

---

# 26. Service Input Should Be Application Data

Good:

```js
authService.login({
    email,
    password
});
```

Good:

```js
todoService.createTodo({
    userId,
    title,
    description
});
```

Good:

```js
userService.getProfile({
    userId
});
```

Bad:

```js
service(req, res);
```

The service should not care where the data came from.

# 27. Repository Input Should Be Query Data

Good:

```js
userRepository.findByEmail(email);
```

or:

```js

```

or:

```js

    todoId,
    userId
```

# 29. Notice Something Important

The repository can protect sensitive data.

For example:

```js
.select("-password -refreshTokenHash")
```

This is a **data-access concern**.

The service doesn't necessarily need to know how the fields are excluded.

This is one reason your roadmap later includes repository lessons about **selecting fields** and **preventing password leakage**.

---

# 30. Repository Methods Should Express Intent

Compare:

```js
repository.findOne({
    _id: todoId,
    userId
});
```

with:

```js
repository.findByIdForUser({
    todoId,
    userId
});
```

The second is often easier to understand.

The method itself documents its purpose:

```text
findByIdForUser
```

means:

> Find this resource only if it belongs to this user.

This becomes particularly useful as your application grows.

# 31. CRUD Repository

A typical repository might have:

```js
const findById = async (id) => {
    return Model.findById(id);
};

const findOne = async (filter) => {
    return Model.findOne(filter);
};

const findMany = async (filter) => {
    return Model.find(filter);
};

const create = async (data) => {
    return Model.create(data);
};

const updateById = async (id, data) => {
    return Model.findByIdAndUpdate(
        id,
        data,
        {
            new: true,
            runValidators: true
        }
    );
};

const deleteById = async (id) => {
    return Model.findByIdAndDelete(id);
};
```

These are data-access operations.

---

# 32. Service Uses Those Operations

For example:

```js
const updateTodo = async ({
    todoId,
    userId,
    title
}) => {

    const todo =
        await todoRepository.findByIdForUser({
            todoId,
            userId
        });

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.completed) {
        throw new AppError(
            "Completed Todo cannot be modified",
            400
        );
    }

    return todoRepository.updateById(
        todoId,
        { title }
    );
};
```

Notice the service is coordinating:

```text
Find
 ↓
Check business rule
 ↓
Update
```

That's exactly what the Service Layer should be doing.

---

# 33. Service = Orchestrator

This is a great mental model:

> **A service orchestrates application operations.**

Example:

```text
updateTodo()
     │
     ├── repository.find()
     │
     ├── check ownership
     │
     ├── check completed status
     │
     └── repository.update()
```

Repository doesn't orchestrate the whole operation.

It performs individual data-access operations.

---

# 34. Don't Make the Repository Orchestrate

Bad:

```js
const updateTodo = async (...) => {

    const todo = await Todo.findById(...);

    if (...) {
        ...
    }

    const user = await User.findById(...);

    if (...) {
        ...
    }

    // business decisions...
};
```

Now the repository is acting like a service.

Instead:

```text
Service
  ↓
Repository
  ↓
data
```

The service should coordinate multiple repository calls if necessary.

---

# 35. Multiple Repository Calls

A service can use several repositories.

For example:

```js
const createOrder = async ({
    userId,
    productId
}) => {

    const user =
        await userRepository.findById(userId);

    const product =
        await productRepository.findById(productId);

    // business rules...

    const order =
        await orderRepository.create({
            userId,
            productId
        });

    return order;
};
```

Now:

```text
Order Service
   │
   ├── User Repository
   ├── Product Repository
   └── Order Repository
```

This is perfectly reasonable.

---

# 36. But Transactions Are Coming

There's an important problem.

Suppose:

```text
1. Create payment
2. Create order
3. Update inventory
```

What if:

```text
Payment succeeds
Order creation succeeds
Inventory update fails
```

Now your database may be inconsistent.

That's why your next major lessons eventually include **transactions and business operations**.

We'll handle that later.

For now, remember:

> **Services can coordinate multiple repository operations, but multi-step database changes may require a transaction.**

---

# 37. Don't Catch Repository Errors Without Reason

Suppose:

```js
const user =
    await userRepository.findById(userId);
```

and MongoDB throws:

```text
MongoServerError
```

Don't automatically do:

```js
catch {
    throw new AppError(
        "User not found",
        404
    );
}
```

As we learned in 12.8, those are different failures.

```text
null
 ↓
not found

database exception
 ↓
unexpected infrastructure failure
```

Let the global error architecture handle unexpected errors unless you have a meaningful transformation.

---

# 38. Repository Error vs Service Error

Think:

### Repository error

```text
Database failed
```

### Service error

```text
Business operation isn't allowed
```

Example:

```text
Repository:
MongoDB connection failed.

Service:
User doesn't have permission.

Service:
Todo is already completed.

Service:
Email already exists.
```

This distinction is critical.

# 40. What If We Didn't Have a Repository?

Then:

```js
const updateTodo = async ({
    todoId,
    userId,
    title
}) => {

    const todo =
        await Todo.findOne({
            _id: todoId,
            userId
        });

    if (!todo) {
        throw new AppError(...);
    }

    if (todo.completed) {
        throw new AppError(...);
    }

    return Todo.findByIdAndUpdate(...);
};
```

This isn't inherently broken.

It's a valid simpler architecture.

But now your service directly depends on Mongoose.

With a repository:

```text
Service
   ↓
Repository
   ↓
Mongoose
```

the database dependency is isolated.

---

# 41. Don't Turn Repository Into a Generic Monster

Another mistake is creating one giant repository:

```text
repository.js
```

containing:

```text
findUser
findTodo
createOrder
updateProduct
deleteComment
...
```

Avoid that.

Prefer:

```text
repositories/
├── user.repository.js
├── todo.repository.js
├── order.repository.js
└── product.repository.js
```

Each repository belongs to a data/domain area.

Your roadmap similarly uses `repositories/user.repository.js` as the target architecture.

# 43. The "Database Smell" Test

Here's a useful test.

Open your service.

If you see lots of:

```js
User.find(...)
User.findOne(...)
User.findById(...)
User.create(...)
User.updateOne(...)
Todo.find(...)
Todo.findOne(...)
```

ask:

> **"Is database access becoming mixed into my business logic?"**

If yes, that's a sign the repository boundary may be useful.

# 48. Common Mistakes

## ❌ Mistake 1: Controller → Repository

```text
Controller
    ↓
Repository
```

This skips your service/business layer.

---

## ❌ Mistake 2: Service → Model everywhere

```js
User.findById(...)
```

everywhere inside services.

That's what the repository layer is intended to isolate.

---

## ❌ Mistake 3: Repository → Controller

Never:

```text
Repository
    ↓
Controller
```

---

## ❌ Mistake 4: Repository → Service

Generally avoid:

```text
Repository
    ↓
Service
```

Keep the direction:

```text
Service
    ↓
Repository
```

---

## ❌ Mistake 5: Business logic in repository

```js
if (user.role !== "admin") {
    throw ...
}
```

Usually service responsibility.

---

## ❌ Mistake 6: Passing Express objects

Avoid:

```js
userService.getUser(req)
```

and:

```js
userRepository.findUser(req)
```

Pass plain application/query data instead.

Create:

Implement:

Requirements:

### Repository

Create:

```js
findByIdForUser({
```

It should query:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

### Service

Create:

```js
getTodo({
    todoId,
    userId
});
```

It should:

```text
1. Call repository.
2. If no Todo → throw 404.
3. Return Todo.
```

### Controller

Call:

```js
todoService.getTodo({
    todoId: req.params.id,
    userId: req.user.id
});
```

Don't put:

```js
Todo.findOne(...)
```

in the controller.

# 🔑 Final Takeaway

The most important sentence from this lesson is:

> **The service decides what the application should do; the repository handles how the application gets or changes the data.**

So instead of:

```js
// service
const user = await User.findById(userId);
```

you can build:

```js
// service
const user =
    await userRepository.findById(userId);
```

and:

```js
// repository
const findById = async (userId) => {
    return User.findById(userId);
};
```

That one separation may look like extra code today, but it gives your backend a much clearer architecture as it grows.
