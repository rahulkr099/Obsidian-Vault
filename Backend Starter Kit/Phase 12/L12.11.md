# Lesson 12.11 — Authentication Service

Now we are going to build one of the most important services in your backend:

```text
services/auth.service.js
```

Your course roadmap specifically places **Authentication Service** at 12.11, after learning service dependencies and calling repositories from services.

The goal is **not** to learn JWT or bcrypt deeply yet. Those are covered later in the dedicated Authentication phase. Here, we are learning:

> **How an authentication use case is organized inside the Service Layer.**

Your source describes the intended flow as:

```text
Signup:
Request
 ↓
Validate
 ↓
Normalize email
 ↓
Check existing user
 ↓
Hash password
 ↓
Create user
 ↓
Return result
```

and login as:

```text
Email + Password
       ↓
Find user
       ↓
Compare password
       ↓
Generate access token
       ↓
Generate refresh token
       ↓
Hash refresh token
       ↓
Store hash
       ↓
Return access token
```

---

# 1. First: What Is an Authentication Service?

Authentication answers:

> **"Who is this user?"**

Examples:

```text
Signup
Login
Refresh token
Logout
Check authentication status
Password reset
Email verification
```

The authentication service contains the **application/business flow** for these operations.

So instead of putting everything into the controller:

```js
authController.login()
```

we want:

```text
Controller
    ↓
authService.login()
    ↓
repositories / password service / token utilities
```

This is exactly the architecture your roadmap is trying to teach.

---

# 2. What Should `auth.service.js` Do?

Think of it as an **orchestrator**.

For example:

```text
authService.login()
       │
       ├── Find user
       │
       ├── Compare password
       │
       ├── Generate tokens
       │
       ├── Save refresh-token hash
       │
       └── Return authentication result
```

It coordinates the operation.

It does **not** need to directly implement everything.

For example:

```text
Password hashing
      ↓
password.service.js

Database access
      ↓
user/auth repository

JWT generation
      ↓
token utility
```

That's the service dependency concept from 12.9.

---

# 3. The Authentication Architecture

A simplified architecture is:

```text
                  HTTP REQUEST
                       │
                       ▼
                 Auth Controller
                       │
                       ▼
                 Auth Service
                 /     |      \
                /      |       \
               ▼       ▼        ▼
          Repository Password   Token
                     Service    Utility
               │        │          │
               ▼        ▼          ▼
            MongoDB   bcrypt      JWT
```

This is much better than:

```text
Auth Controller
     ↓
MongoDB
     ↓
bcrypt
     ↓
JWT
     ↓
cookies
```

all inside one controller.

---

# 4. Authentication Service vs Authentication Controller

This distinction is extremely important.

### Controller

Handles HTTP:

```text
req.body
req.params
req.user
res.status()
res.json()
```

### Service

Handles the authentication operation:

```text
find user
verify password
create tokens
store token hash
return result
```

So:

```js
// controller

const result = await authService.login({
    email,
    password
});
```

The controller shouldn't know **how** login works.

Let's start with:

```text

```

Suppose the client sends:

```json
{
  "name": "Rahul",

  "password": "secret123"

```

The request eventually reaches:

```js
authService.signup({
    name,
    email,
    password

```

Now the service performs the application workflow.

# 6. Signup Step 1 — Normalize Email

The source explicitly includes:

```text
Normalize email
```

in the signup flow.

For example:

```text
" Rahul@Example.COM "
```

could be normalized to:

```text
"rahul@example.com"
```

Conceptually:

```js
const normalizedEmail =
    email.trim().toLowerCase();
```

Why?

Because these should generally not become two separate accounts:

```text
Rahul@example.com
rahul@example.com
```

Normalization gives your application a consistent representation.

```js
const existingUser =

```

# 8. What If User Already Exists?

The service makes the business decision.

```js
if (existingUser) {
    throw new AppError(
        "Email already registered",
        409
    );
}
```

Notice the difference:

### Repository

```text
"I found a user."
```

### Service

```text
"Therefore, signup cannot continue."
```

This is exactly why we separated these layers.

---

# 9. Signup Step 3 — Hash Password

Never store:

```text
secret123
```

directly in MongoDB.

The source explicitly says:

```text
password
 ↓
bcrypt
 ↓
hash
 ↓
MongoDB
```

So the service calls the password service:

```js
const passwordHash =
    await passwordService.hash(password);
```

Now:

```text
plain password
      ↓
passwordService
      ↓
bcrypt
      ↓
password hash
```

The authentication service doesn't need to know bcrypt's internal implementation.

---

# 10. Why Is Password Hashing a Separate Service?

Because authentication and password operations are different responsibilities.

```text
Auth Service
→ "Register this user."

Password Service
→ "Hash this password."
```

That gives:

```text
auth.service.js
       ↓
password.service.js
       ↓
bcrypt
```

Your starter specifically contains both:

```text
services/
├── auth.service.js
└── password.service.js
```

which is why understanding this dependency is useful.

---

# 11. Signup Step 4 — Create User

After hashing:

```js
const user =
    await userRepository.create({
        name,
        email: normalizedEmail,
        password: passwordHash
    });
```

Notice:

```text
Auth Service
      ↓
User Repository
      ↓
User Model
      ↓
MongoDB
```

The repository handles database access.

---

# 12. Signup Step 5 — Return a Safe Result

Be careful here.

The database user might contain:

```js
{
    _id,
    name,
    email,
    password,
    refreshTokenHash
}
```

You should **not** blindly return the whole document.

For example:

```js
return {
    id: user._id,
    name: user.name,
    email: user.email
};
```

The source also emphasizes preventing password leakage as part of the repository architecture.

# 14. Signup Service Example

A simplified version:

```js
const signup = async ({
    name,
    email,
    password
}) => {

    const normalizedEmail =
        email.trim().toLowerCase();

    const existingUser =
        await userRepository.findByEmail(
            normalizedEmail
        );

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const passwordHash =
        await passwordService.hash(password);

    const user =
        await userRepository.create({
            name,
            email: normalizedEmail,
            password: passwordHash
        });

    return {
        id: user._id,
        name: user.name,
        email: user.email
    };
};
```

This is the kind of code you should understand conceptually before worrying about the exact implementation in your starter.

# 16. Login Step 1 — Normalize Email

Same idea:

```js
const normalizedEmail =
    email.trim().toLowerCase();
```

Then:

```js
const user =
    await userRepository.findByEmail(
        normalizedEmail
```

# 17. Login Step 2 — Find User

The repository returns either:

```text
user
```

or:

```text
null
```

If:

```text
null
```

the login should fail.

For security, don't normally reveal whether the email exists.

Instead:

```js
throw new AppError(
    "Invalid credentials",
    401
);
```

So:

```text
Wrong email
    ↓
Invalid credentials

Correct email + wrong password
    ↓
Invalid credentials
```

This avoids giving attackers useful account-enumeration information.

---

# 18. Login Step 3 — Compare Password

Now:

```js
const passwordValid =
    await passwordService.compare(
        password,
        user.password
    );
```

The flow:

```text
Entered password
       ↓
passwordService.compare()
       ↓
Stored password hash
       ↓
bcrypt
       ↓
true / false
```

The service makes the decision:

```js
if (!passwordValid) {
    throw new AppError(
        "Invalid credentials",
        401
    );
}
```

---

# 19. Login Step 4 — Generate Access Token

Conceptually:

# 20. Login Step 5 — Generate Refresh Token

# 21. Access Token vs Refresh Token

You don't need to deeply study this yet, but remember:

```text
ACCESS TOKEN
→ short-lived
→ used to access protected APIs
```

```text
REFRESH TOKEN
→ longer-lived
→ used to obtain a new access token
```

Your source describes the intended transport as:

```text
Access Token
→ Authorization header

Refresh Token
→ HttpOnly cookie
```

We'll study the security details later.

---

# 22. Why Hash the Refresh Token?

This is an important part of your starter.

The source's login flow says:

```text
Generate refresh token
       ↓
Hash refresh token
       ↓
Store hash
```

Why?

Imagine the database contains the actual refresh token:

```text
refreshTokenHash = "actual-secret-token"
```

If an attacker gets the database value, they may be able to use it.

Instead:

```text
refresh token
      ↓
hash
      ↓
refreshTokenHash
      ↓
MongoDB
```

The server stores the hash rather than the raw refresh token.

---

# 23. Auth Service Coordinates This

This is where the Service Layer becomes really useful.

The auth service can coordinate:

```text
Find user
   ↓
Compare password
   ↓
Generate access token
   ↓
Generate refresh token
   ↓
Hash refresh token
   ↓
Store hash
   ↓
Return access token
```

No individual component needs to own the entire workflow.

---

# 24. Store Refresh Token Hash

For example:

```js
const refreshTokenHash =
    await passwordService.hash(refreshToken);
```

Then:

```js
await userRepository.updateRefreshTokenHash({
    userId: user._id,
    refreshTokenHash
});
```

Notice the architecture:

```text
Auth Service
    │
    ├── Password Service
    │        ↓
    │      bcrypt
    │
    └── User Repository
             ↓
          MongoDB
```

---

# 25. Why Hashing Refresh Token Can Reuse Password Service

This is an interesting design question.

Password service isn't necessarily only:

```text
hash password
compare password
```

It can represent:

```text
secure secret hashing/comparison
```

depending on how you design it.

But be careful with naming.

If it becomes responsible for every kind of cryptographic operation, it may become a **giant utility/service**.

Later, you might separate:

```text
password.service.js
crypto utility
token utility
```

The important thing at this stage is understanding the responsibility boundary.

# 26. Final Login Result

The service might return:

```js
return {
    user: {
        id: user._id,
        name: user.name,
        email: user.email,
        role: user.role
    },
    accessToken,
    refreshToken
};
```

However, the exact transport of the refresh token depends on your controller/cookie architecture.

Your source recommends the refresh token be placed in an HttpOnly cookie.

So conceptually:

```text
Service
   ↓
Authentication result

Controller
   ↓
HTTP response
   +
Set-Cookie
```

The controller handles HTTP transport.

---

# 27. Important: Service Shouldn't Set Cookies

Don't do this:

```js
// auth.service.js

res.cookie(...)
```

Why?

Because:

```text
res
```

belongs to Express/HTTP.

The service shouldn't depend on Express.

Instead:

```text
Auth Service
    ↓
returns authentication result
    ↓
Controller
    ↓
sets cookie
```

This preserves the layer boundary.

# 29. What About Validation?

You might ask:

> "Where do we validate email and password?"

The roadmap has already taught Validation before Services.

So ideally:

```text
Request
   ↓
Validation Middleware
   ↓
Controller
   ↓
Auth Service
```

For example:

```text

```

should normally be rejected before reaching the business operation.

The service can still protect itself against important invariants, but don't turn the service into a duplicate validation system.

# 32. Why Not Put Signup in `user.service.js`?

This is a good architecture question.

You could argue:

> "Creating a user belongs to User Service."

Sometimes that makes sense.

But signup isn't merely:

```text

```

It is an **authentication use case** involving:

```text

password hashing
account creation
authentication state
possibly email verification
```

So an `auth.service.js` can reasonably orchestrate signup.

Meanwhile:

```text

```

can handle user-specific operations such as:


This separation becomes clearer in 12.12.

# 37. Complete Simplified Example

Putting everything together:

```js
const signup = async ({
    name,
    email,
    password
}) => {

    const normalizedEmail =
        email.trim().toLowerCase();

    const existingUser =
        await userRepository.findByEmail(
            normalizedEmail
        );

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const passwordHash =
        await passwordService.hash(password);

    const user =
        await userRepository.create({
            name,
            email: normalizedEmail,
            password: passwordHash
        });

    return {
        id: user._id,
        name: user.name,
        email: user.email
    };

```

And login:

```js
const login = async ({
    email,
    password
}) => {

    const normalizedEmail =
        email.trim().toLowerCase();

    const user =
        await userRepository.findByEmail(
            normalizedEmail
        );

    if (!user) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const valid =
        await passwordService.compare(
            password,
            user.password
        );

    if (!valid) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const accessToken =
        tokenService.generateAccessToken({
            userId: user._id,
            role: user.role
        });

    const refreshToken =
        tokenService.generateRefreshToken({
            userId: user._id
        });

    const refreshTokenHash =
        await passwordService.hash(
            refreshToken
        );

    await userRepository.updateRefreshTokenHash({
        userId: user._id,
        refreshTokenHash
    });

    return {
        user: {
            id: user._id,
            name: user.name,
            email: user.email,
            role: user.role
        },
        accessToken,
        refreshToken
    };
};
```

Again, this is a **learning model**, not yet the final production implementation.

The dedicated Authentication phase will later cover the details of sessions vs tokens, bcrypt, JWT, access/refresh tokens, secure cookies, refresh-token rotation, logout, token theft, password reset, and email verification.

# 40. Your Most Important Learning Point

At this point, you should understand why this:

```js
authController.login()
```

should eventually be thin.

Instead of:

```js
const login = async (req, res) => {

    const user = await User.findOne(...);

    const valid = await bcrypt.compare(...);

    const accessToken = jwt.sign(...);

    const refreshToken = jwt.sign(...);

    const hash = await bcrypt.hash(...);

    await User.updateOne(...);

    res.cookie(...);

    res.json(...);
};
```

we want:

```js
const login = asyncHandler(async (req, res) => {

    const result =
        await authService.login({
            email: req.body.email,
            password: req.body.password
        });

    // HTTP-specific response handling
});
```

That's the transformation your entire Phase 12 is teaching.
