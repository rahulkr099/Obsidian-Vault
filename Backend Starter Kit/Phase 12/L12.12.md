# Lesson 12.12 — User Service

Now we move from the **Authentication Service** to the **User Service**.

Your roadmap defines **12.12 as “User service”**, and later the starter-building plan places `services/user.service.js` inside the complete User Module alongside the controller, repository, routes, and validation.

The main goal of this lesson is to understand:

> **What should `user.service.js` actually do, and why shouldn't the controller or repository do it?**

---

# 1. First, Understand the Difference

We now have two services:

```text
auth.service.js
user.service.js
```

They are related, but they are **not the same thing**.

### Auth Service

Concerned with:

```text
Signup
Login
Refresh
Logout
Authentication state
```

### User Service

Concerned with:

```text
User profile
User information
Updating user information
User-specific operations
User management
```

A useful mental model:

```text
AUTH
→ "Who are you?"

USER
→ "What can I do with your user information?"
```

---

# 2. Where User Service Fits

The User Module eventually looks like:

```text
routes/user.routes.js
        ↓
middlewares
        ↓
controllers/user.controller.js
        ↓
services/user.service.js
        ↓
repositories/user.repository.js
        ↓
models/user.model.js
        ↓
MongoDB
```

Your source specifically describes the first User endpoint as:

```text
GET /api/v1/users/me
```

with this flow:

```text
GET /users/me
       ↓
authMiddleware
       ↓
userController
       ↓
userService
       ↓
userRepository
       ↓
User model
       ↓
MongoDB
```

This is exactly what we're going to understand.

---

# 3. Why Do We Need a User Service?

Imagine you don't have a service.

Your controller might become:

```js
const getMe = async (req, res) => {

    const user = await User.findById(
        req.user.id
    );

    if (!user) {
        return res.status(404).json({
            message: "User not found"
        });
    }

    res.json({
        data: user
    });
};
```

It works.

But now the controller is doing:

```text
HTTP
+
database access
+
business logic
+
error handling
```

That's exactly what we are trying to avoid.

Instead:

```text
Controller
    ↓
userService.getProfile()
    ↓
userRepository.findById()
```

---

# 4. User Service Is an Orchestrator

Think of:

```js
userService.getProfile()
```

as saying:

> "I want to perform the application operation of getting this user's profile."

The service then decides:

```text
Find user
 ↓
Does user exist?
 ↓
Remove sensitive information
 ↓
Return user
```

The repository handles:

```text
How do I query MongoDB?
```

---

# 5. First User Operation: Get Profile

Let's start with:

```http
GET /api/v1/users/me
```

The authentication middleware has already done something like:

```js
req.user = {
    id: "123",
    role: "user"
};
```

So the controller can call:

```js
userService.getProfile({
    userId: req.user.id
});
```

Notice something important.

The service doesn't receive:

```js
req
```

It receives:

```js
{
    userId
}
```

That's a clean application-level input.

---

# 6. Controller

A thin controller:

```js
const getMe = asyncHandler(async (req, res) => {

    const user =
        await userService.getProfile({
            userId: req.user.id
        });

    res.status(200).json({
        success: true,
        data: user
    });
});
```

The controller handles:

```text
req
res
HTTP status
JSON response
```

That's it.

---

# 7. Service

Now:

```js
const getProfile = async ({ userId }) => {

    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Look at how simple it is.

The service is saying:

```text
I need this user.
        ↓
Repository, find them.
        ↓
No user?
        ↓
The operation fails.
```

---

# 8. Repository

The repository handles the actual database operation:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

So now:

```text
Controller
   ↓
"I need my profile."

Service
   ↓
"I'll perform the profile operation."

Repository
   ↓
"I'll query MongoDB."

Model
   ↓
"I know what a User document looks like."
```

This is the architecture we're building.

---

# 9. Why Not Just Return the Entire User?

This is where the User Service becomes important.

Suppose MongoDB returns:

```js
{
    _id: "...",
    name: "Rahul",
    email: "rahul@example.com",
    password: "$2b$12$...",
    refreshTokenHash: "...",
    role: "user"
}
```

You definitely don't want:

```json
{
  "password": "...",
  "refreshTokenHash": "..."
}
```

going to the frontend.

Your source specifically highlights **preventing password leakage** as an important repository concern.

Ideally, the data-access layer already excludes sensitive fields, and the service returns a safe representation.

---

# 10. Safe User Object

You can create a small transformation:

```js
const toPublicUser = (user) => ({
    id: user._id,
    name: user.name,
    email: user.email,
    role: user.role
});
```

Then:

```js
const getProfile = async ({ userId }) => {

    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return toPublicUser(user);
};
```

Now the service controls what the application exposes.

# 11. User Service Is Not Just CRUD

This is important.

You might think:

```text
User Service
=
find user
create user
update user
delete user
```

That's only part of it.

A service represents **application operations**.

For example:

```text
getProfile()
updateProfile()
changePassword()
deleteAccount()
getUserById()
```

These methods represent things the application wants to do.

---

# 12. `getProfile()` vs `findById()`

This distinction is subtle but important.

Repository:

```js
findById(userId)
```

means:

> Find a database record by ID.

Service:

```js
getProfile({ userId })
```

means:

> Perform the application operation of retrieving this user's profile.

The names are intentionally different because their responsibilities are different.

# 14. Controller

```js
const updateProfile = asyncHandler(
    async (req, res) => {

        const user =
            await userService.updateProfile({
                userId: req.user.id,
                updates: req.body
            });

        res.status(200).json({
            success: true,
            data: user
        });
    }
);
```

The controller doesn't decide:

```text
Can this field be changed?
```

That's service/application logic.

---

# 15. Service

A simple version:

```js
const updateProfile = async ({
    userId,
    updates
}) => {

    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return userRepository.updateById(
        userId,
        updates
    );
};
```

But there's a problem.

We're blindly accepting:

```js
updates
```

That can become dangerous.

---

# 16. Never Blindly Update User Data

Imagine the request:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

If you blindly do:

```js
User.findByIdAndUpdate(
    userId,
    req.body
);
```

the user might change their own role.

That's a serious security problem.

So the service needs to understand which fields are allowed.

---

# 17. Allow-Listed Fields

For a normal profile update:

```js
const allowedUpdates = {
    name: updates.name
};
```

Then:

```js
return userRepository.updateById(
    userId,
    allowedUpdates
);
```

Now:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

becomes effectively:

```json
{
    "name": "Rahul"
}
```

The `role` field is ignored.

This idea is called **allow-listing**.

---

# 18. Why This Matters

Your source later emphasizes authorization, ownership, and preventing privilege escalation. It specifically gives the example of ensuring a user cannot access another user's resource and stresses queries involving both resource ID and authenticated user ID.

The same mindset applies here:

> **Never let users modify fields merely because those fields exist in `req.body`.**

---

# 19. User Service and Authorization

Suppose we have:

```text
User A
User B
Admin
```

User A requests:

```http
PATCH /users/B
```

The service must not simply say:

```text
"Here's user B."
```

It needs to understand the operation's authorization requirements.

For normal self-service endpoints:

```text
/users/me
```

the authenticated user ID gives us the ownership context:

```js
userId: req.user.id
```

For admin operations:

```text
/users/:id
```

authorization can be handled through role/permission middleware and/or service-level rules.

# 21. What About Change Password?

This is a nice example of why boundaries matter.

Changing a password is a **user operation**, but it uses authentication/password functionality.

The flow could be:

```text
User Service
     ↓
Find user
     ↓
Verify current password
     ↓
Hash new password
     ↓
Update password
```

The service may depend on:

```text
User Repository
Password Service
```

So:

```text
user.service.js
      │
      ├── userRepository
      │
      └── passwordService
```

This is service composition.

We will study composition more deeply in 12.15.

---

# 22. Change Password Example

Conceptually:

```js
const changePassword = async ({
    userId,
    currentPassword,
    newPassword
}) => {

    const user =
        await userRepository.findByIdWithPassword(
            userId
        );

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    const valid =
        await passwordService.compare(
            currentPassword,
            user.password
        );

    if (!valid) {
        throw new AppError(
            "Current password is incorrect",
            401
        );
    }

    const passwordHash =
        await passwordService.hash(
            newPassword
        );

    await userRepository.updateById(
        userId,
        {
            password: passwordHash
        }
    );
};
```

Notice how several components cooperate.

---

# 23. Why Repository Needs a Special Method

Earlier we said:

```js
findById()
```

should normally avoid returning sensitive fields.

But password change requires the password hash.

So you might have:

```js
findById()
```

for normal profile operations, and:

```js
findByIdWithPassword()
```

for an internal authentication-sensitive operation.

This is an example of why repositories need meaningful methods rather than one generic:

```js
findEverything()
```

# 27. Example: Admin Changes Role

Imagine:

```http
PATCH /api/v1/users/:id/role
```

Request:

```json
{
    "role": "admin"
}
```

The flow should be:

```text
Request
   ↓
Authentication
   ↓
Authorization: admin?
   ↓
Validation
   ↓
Controller
   ↓
User Service
   ↓
Repository
```

The service:

```js
const updateRole = async ({
    userId,
    role
}) => {

    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404

    return userRepository.updateById(
        userId,

```

---

# 28. Controller Shouldn't Decide Business Rules

Avoid:

```js
const updateProfile = async (req, res) => {

    if (req.body.role) {
        return res.status(403).json(...);
    }

    if (req.body.name.length < 3) {
        return res.status(400).json(...);
    }

    const user = await User.findById(...);

    ...
};
```

Now the controller has become a giant application layer.

Instead:

```text
Validation
→ input structure

Service
→ business rules

Repository
→ database
```

---

# 29. User Service Shouldn't Build HTTP Responses

Avoid:

```js
return {
    statusCode: 200,
    message: "User found",
    data: user
};
```

unless your application deliberately uses a service-level result contract.

Generally, keep:

```js
return user;
```

and let the controller construct:

```js
res.status(200).json({
    success: true,
    data: user
});
```

This keeps the service independent from Express.

---

# 30. User Service Shouldn't Know `req`

Avoid:

```js
userService.getProfile(req);
```

Prefer:

```js
userService.getProfile({
    userId: req.user.id
});
```

Why?

Because now the service can be called from:

```text
HTTP controller
background job
CLI
test
another service
```

without needing an Express request.

---

# 31. User Service Shouldn't Know `res`

Avoid:

```js
userService.deleteUser(req, res);
```

The service should return a result or throw an error.

Then:

```text
Service
 ↓
result
 ↓
Controller
 ↓
HTTP response
```

# 42. One Important Security Rule

Never make this:

```js
const updateProfile = async ({
    userId,
    updates
}) => {

    return userRepository.updateById(
        userId,
        updates
    );
};
```

your default pattern.

Because `updates` could contain:

```json
{
    "role": "admin",
    "isVerified": true,
    "password": "..."
}
```

Instead, explicitly define what this operation allows:

```js
const updateProfile = async ({
    userId,
    name
}) => {

    return userRepository.updateById(
        userId,
        {
            name
        }
    );
};
```

That is much safer.

---

# 43. Don't Create One `updateUser()` for Everything

Avoid a giant method:

```text
updateUser()
```

that allows:

```text
name
email
password
role
status
permissions
refreshToken
verification state
```

These operations have very different security requirements.

Prefer meaningful application operations:

```text
updateProfile()
changePassword()
updateRole()
verifyEmail()
disableAccount()
```

This makes the code much easier to reason about.

# 🔑 Lesson 12.12 Summary

Your `user.service.js` is the **application/business layer for user-related operations**.

Typical operations can include:

```text
getProfile()
updateProfile()
changePassword()
deleteAccount()
getUser()
admin user operations
```

The important architecture is:

```text
Controller
    ↓
userService
    ↓
userRepository
    ↓
User Model
    ↓
MongoDB
```

And remember the most important rule:

> **Never let a normal profile update blindly pass `req.body` into a database update. Explicitly decide which fields that business operation is allowed to change.**

Your source's overall architecture is deliberately moving toward this separation: controllers handle HTTP, services contain business logic, repositories handle MongoDB access, and models define the data structure.
