# Lesson 12.13 — CRUD Service

Now we reach a very important lesson.

Your roadmap calls **12.13 “CRUD service”**.

You've already learned:

```text
12.11 → Authentication Service
12.12 → User Service
12.13 → CRUD Service
```

So now we're going to take everything you've learned and apply it to a normal resource such as:

```text
Todo
```

Your uploaded reference actually contains a Todo service example with operations such as `createTodo`, `getTodoById`, `listTodos`, `updateTodo`, and `completeTodo`.

The goal today is:

> **Understand how a service coordinates CRUD operations and business rules without becoming a giant controller or raw database layer.**

---

# 1. First: What Does CRUD Mean?

CRUD stands for:

```text
C → Create
R → Read
U → Update
D → Delete
```

For a Todo API:

```text
Create
POST /todos

Read one
GET /todos/:id

Read many
GET /todos

Update
PATCH /todos/:id

Delete
DELETE /todos/:id
```

So we can imagine:

```text
Todo Service
├── createTodo()
├── getTodoById()
├── listTodos()
├── updateTodo()
└── deleteTodo()
```

That's our CRUD service.

---

# 2. But Don't Think "CRUD = Database"

This is the most important point.

A beginner thinks:

```text
CRUD service
=
Todo.create()
Todo.findById()
Todo.update()
Todo.delete()
```

That's not enough.

A service is supposed to contain **application behavior**.

For example:

```text
Create Todo
    ↓
Create database record
    ↓
Record activity
    ↓
Return Todo
```

Your uploaded Todo example does exactly this: after creating a Todo, it creates an `Activity` record.

So:

```text
CRUD
+
business rules
+
related operations
=
Service
```

---

A Todo request should eventually look like:

```text
POST /api/v1/todos

        ▼
     Route

        ▼

        ▼
    Validation
        │
        ▼

        │
        ▼
   Todo Service
        │
        ▼
  Todo Repository
        │
        ▼

        │
        ▼

```

And possibly:

```text

      │
      └──────► Activity Repository/Model
```

for auditing.

Your reference architecture describes the general flow as:

```text

Middleware

Controller

Service

Repository

Model

Database
```

with security, validation, error handling, logging, configuration, and testing around it.

# 5. Operation #1 — Create

Endpoint:

```http
POST /api/v1/todos
```

Request:

```json
{
    "title": "Learn Services",
    "description": "Study CRUD service",
    "priority": "high"
}
```

The controller might call:

```js
todoService.createTodo({
    data: req.body,
    userId: req.user.id
});
```

Notice:

The controller gives the service **application data**, not the entire `req`.

---

# 6. Create Service

Conceptually:

```js
const createTodo = async ({ data, userId }) => {

    const todo = await todoRepository.create({
        ...data,
        userId
    });

    return todo;
};
```

Very simple.

But let's think carefully.

Why does the service add:

```js
userId
```

instead of trusting the frontend?

Because the authenticated user comes from:

```text
Authentication middleware
        ↓
req.user.id
```

The client should not decide:

```json
{
    "userId": "some-other-user"
}
```

---

# 7. Ownership Is Important

Imagine Rahul is logged in.

The request says:

```text
Create Todo
```

The server knows:

```text
authenticated user = Rahul
```

So:

```js
todoService.createTodo({
    data,
    userId: req.user.id
});
```

Then:

```js
Todo.create({
    ...data,
    userId
});
```

This establishes ownership.

Later, the repository can use:

```js
{
    _id: todoId,
    userId
}
```

to ensure Rahul only accesses Rahul's Todo.

Your roadmap specifically emphasizes ownership queries such as:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

as an important authorization/security concept.

---

# 8. Activity Logging

Your actual uploaded Todo service example does something interesting:

```js
const todo = await Todo.create(data);

await Activity.create({
    todoId: todo._id,
    action: "create",
    userId
});

return todo;
```

Why?

Because creating a Todo is not necessarily the entire business operation.

The application may also need:

```text
Todo created
+
Activity recorded
```

So the service coordinates both.

---

# 9. This Is Why Services Exist

Without a service:

```text
Controller
   ↓
Todo.create()
   ↓
Activity.create()
   ↓
Response
```

The controller now knows too much.

With a service:

```text
Controller
   ↓
todoService.createTodo()
       │
       ├── Todo Repository
       │
       └── Activity Repository
```

Much cleaner.

# 10. Operation #2 — Get One Todo

Endpoint:

```http
GET /api/v1/todos/:id
```

Controller:

```js
const todo = await todoService.getTodoById({
    todoId: req.params.id,
    userId: req.user.id
});
```

Service:

```js
const getTodoById = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

Notice the important difference from simply:

```js
Todo.findById(todoId);
```

We want:

```text
Todo ID
+
authenticated User ID
```

---

# 11. Why Should the Service Pass `userId`?

Suppose:

```text
Todo A → Rahul
Todo B → Amit
```

Rahul sends:

```http
GET /todos/B
```

If the repository only does:

```js
Todo.findById(todoId)
```

Rahul could potentially retrieve Amit's Todo.

Instead:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

returns only a Todo belonging to the authenticated user.

This is the ownership pattern emphasized in your roadmap.

---

# 12. What If Todo Doesn't Exist?

The service decides:

```js
if (!todo) {
    throw new AppError(
        "Todo not found",
        404
    );
}
```

Your uploaded reference uses exactly this pattern:

```js
if(!todo) {
    throw new AppError("Todo not found", 404)
}
```

Notice:

The service doesn't do:

```js
res.status(404).json(...)
```

because that's HTTP.

It throws an application error.

The error middleware handles the HTTP response.

# 13. Operation #3 — List Todos

Now we get:

```http
GET /api/v1/todos
```

This is more interesting.

The request might contain:

```text
?page=1
&limit=20
&status=pending
&tag=work,study
&q=express
&sortBy=-createdAt
```

Your service has to turn these query parameters into an application-level query.

Your reference Todo service already demonstrates this workflow.

---

# 14. Extract Query Parameters

Conceptually:

```js
const {
    page = 1,
    limit = 20,
    status,
    tag,
    q,
    sortBy = "-createdAt"
} = queryParams;
```

Then:

```js
const pageNum = Number(page);
const limitNum = Number(limit);
```

This is important because HTTP query parameters arrive as strings.

For example:

```text
?page=2
```

usually gives:

```js
page === "2"
```

not:

```js
page === 2
```

---

# 15. Validate Pagination

Your reference checks:

```js
if(pageNum < 1 || limitNum < 1){
    throw new AppError(
        "Invalid pagination values",
        400
    );
}
```

and also:

```js
if(limitNum > 100){
    throw new AppError(
        "Limit cannot exceed 100",
        400
    );
}
```

Why have a maximum?

Because this request:

```text
GET /todos?limit=10000000
```

could create a huge database operation.

So:

```text
limit
→ must be valid
→ must have a safety maximum
```

---

# 16. Build the Base Filter

The reference starts with:

```js
const filters = {
    softDelete: false
};
```

Then adds:

```js
if(status) {
    filters.status = status;
}
```

and:

```js
if(tag) {
    filters.tags = {
        $in: tag.split(",")
    };
}
```

So:

```text
No filter
    ↓
softDelete: false

status=pending
    ↓
softDelete: false
status: pending

tag=work,study
    ↓
softDelete: false
tags: { $in: ["work", "study"] }
```

---

# 17. Why Build Filters in the Service?

Because this represents an **application query operation**.

The service understands:

```text
User wants pending Todos
User wants work-tagged Todos
User wants active Todos
```

The repository can then receive the final query information.

In your current starter/reference, some service code directly constructs Mongoose queries. That's useful for learning the business flow, but Phase 13 will specifically teach moving database access behind repositories. The roadmap says Phase 13 exists to understand why services shouldn't directly query MongoDB.

So keep this distinction in mind:

> **12.13 teaches CRUD service behavior; Phase 13 will refactor the database operations into repositories.**

# 19. Sorting

The reference allows:

```js
const allowedSortFields = [
    "createdAt",
    "priority",
    "dueDate"
];
```

This is an important security/performance idea.

Don't blindly allow:

```text
sortBy=anything
```

Instead:

```text
Allowed:
createdAt
priority
dueDate
```

This is called **allow-listing**.

---

# 20. Why Allow-List Sort Fields?

Imagine the client sends:

```text
?sortBy=password
```

You don't want arbitrary database fields being accepted.

So:

```js
if (!allowedSortFields.includes(field)) {
    delete sort[field];
}
```

Your reference uses exactly this pattern.

Later, in the pagination/filtering phase, you'll study this more deeply.

---

# 21. Pagination Calculation

The standard formula is:

```text
skip = (page - 1) × limit
```

For:

```text
page = 1
limit = 20
```

we get:

```text
skip = 0
```

For:

```text
page = 2
limit = 20
```

we get:

```text
skip = 20
```

For:

```text
page = 3
limit = 20
```

we get:

```text
skip = 40
```

```js
return {

```

So the service result becomes:


# 23. Run Independent Queries in Parallel

Your reference does:

```js
const [items, total] = await Promise.all([
    query.exec(),
    Todo.countDocuments(filters)
]);
```

Why?

Because these operations don't depend on each other:

```text
Get page of Todos
        +
Count total Todos
```

They can run concurrently.

Conceptually:

```text
        ┌── query items ──┐
Service ┤                 ├──→ result
        └── count total ──┘
```

rather than:

```text
query items
    ↓
wait
    ↓
count total
    ↓
result
```

This is a useful performance pattern.

---

# 25. Never Blindly Update `req.body`

This is one of the most important lessons from the previous User Service lesson.

Don't do:

```js
Todo.findByIdAndUpdate(
    id,
    req.body
);
```

because the client could send:

```json
{
    "userId": "another-user",
    "softDelete": false,
    "version": 999999
}
```

or other protected fields.

Instead, validation + service logic should control what can be changed.

For example:

```js
const allowedUpdates = {
    title: updateData.title,
    description: updateData.description,
    priority: updateData.priority
};
```

---

# 26. Update and Versioning

Your uploaded example does:

```js
$inc: {
    version: 1
}
```

So:

```text
version 1
   ↓ update
version 2
   ↓ update
version 3
```

This can be useful for tracking changes or implementing optimistic concurrency later.

The important lesson for now is:

> A CRUD operation can contain business behavior beyond simply changing fields.

# 28. Operation #5 — Complete Todo

This is where CRUD becomes more interesting.

Completing a Todo isn't simply:

```text
update status
```

It is a **business operation**.

Your reference contains:

```js
export const completeTodo = async(id, userId) => {
    const updateData = {
        status: "done",
        completedAt: new Date()
    }
```

So the service defines what "complete" means.

It means:

```text
status = done
+
completedAt = current time
```

---

# 29. Why `completeTodo()` Is Better Than Generic Update

Imagine the frontend sends:

```json
{
    "status": "done"
}
```

That only says:

```text
status = done
```

But the business operation might require:

```text
status = done
completedAt = now
activity = completed
```

So:

```js
completeTodo()
```

can coordinate all of those actions.

This is a great example of:

> **Services represent business operations, not just database operations.**

# 30. Delete

Now:

```http
DELETE /api/v1/todos/:id
```

There are two common approaches.

### Hard delete

```text
Document
   ↓
MongoDB delete
   ↓
Gone
```

### Soft delete

```text
Document
   ↓
softDelete = true
   ↓
Still exists in database
```

Your reference uses:

```js
softDelete: false
```

as part of its normal Todo filters.

That strongly suggests the Todo design uses a soft-delete concept.

---

# 31. Why Soft Delete?

Suppose you delete:

```text
Todo: "Learn MongoDB"
```

Hard deletion means:

```text
Database
→ record gone
```

Soft deletion:

```js
{
    softDelete: true
}
```

means:

```text
Normal queries
→ don't show it

Database
→ record still exists
```

This can help with:

```text
recovery
auditing
history
accidental deletion
```

The exact policy depends on the application.

# 39. A Practical `todo.service.js`

A simplified version might look like:

```js
import Todo from "../models/todo.model.js";
import Activity from "../models/activity.model.js";
import { AppError } from "../utils/index.js";

export const createTodo = async (data, userId) => {

    const todo = await Todo.create({
        ...data,
        userId
    });

    await Activity.create({
        todoId: todo._id,
        action: "create",
        userId
    });

    return todo;
};
```

Get one:

```js
export const getTodoById = async (
    id,
    userId
) => {

    const todo = await Todo.findOne({
        _id: id,
        userId,
        softDelete: false
    });

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

Update:

```js
export const updateTodo = async (
    id,
    updateData,
    userId
) => {

    const todo =
        await Todo.findOneAndUpdate(
            {
                _id: id,
                userId,
                softDelete: false
            },
            {
                $set: updateData,
                $inc: {
                    version: 1
                }
            },
            {
                new: true,
                runValidators: true
            }
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    await Activity.create({
        todoId: todo._id,
        action: "update",
        userId,
        payload: updateData
    });

    return todo;
};
```

This follows the same overall pattern as the Todo service supplied in your reference.

# 40. But Notice One Improvement

In the reference:

```js
export const updateTodo = async(
    id,
    updateData,
    userId
)
```

the update query doesn't include `userId`:

```js
{
    _id: id,
    softDelete: false
}
```

For a multi-user application, you should think carefully about ownership here.

A safer ownership-aware query would conceptually be:

```js
{
    _id: id,
    userId,
    softDelete: false
}
```

This connects directly to the ownership principle in your roadmap.

However, I'm deliberately distinguishing this as **an architectural security improvement/inference**, rather than claiming your uploaded reference already does it.

A good service API is explicit.

Instead of:

```js
createTodo(req)
```

use:

```js
createTodo({
    data,
    userId
})
```

Instead of:

```js
updateTodo(req)
```

use:

```js
updateTodo({
    todoId,
    userId,
    updateData
})
```

This makes the function easy to understand and test.

---

# 42. Service Output Design

The service should return application data.

For example:

```js
return todo;
```

or:

```js
return {
    items,
    meta
};
```

It generally shouldn't return:

```js
res
```

or:

```js
res.status(...)
```

because those belong to the controller.

# 44. CRUD Service and Validation

Suppose:

```json
{
    "title": ""
}
```

Input validation should catch obvious schema problems.

But the service can still enforce business rules.

For example:

```text
A completed Todo cannot be edited
```

That's not merely a string validation rule.

It's a business rule.

So:

```js
if (todo.status === "done") {
    throw new AppError(
        "Completed todos cannot be edited",
        409
    );
}
```

That's service-level logic.

---

# 45. A Useful Classification

When building CRUD features, classify rules into three levels.

### Input validation

```text
title required
title max 200 chars
priority must be high/medium/low
```

→ Validation layer

### Business rules

```text
completed Todo cannot be edited
only owner can update
deleted Todo cannot be completed
```

→ Service/application layer

### Database operations

```text
findOne
find
create
findOneAndUpdate
delete
```

→ Repository/data-access layer

This separation is one of the biggest lessons of your architecture course.

# 🧠 49. The Most Important Lesson

A CRUD service is **not simply a wrapper around Mongoose**.

Bad mental model:

```text
Service
 ↓
Todo.create()
Todo.find()
Todo.update()
Todo.delete()
```

Better mental model:

```text
Service
 ↓
Understand the application operation
 ↓
Apply business rules
 ↓
Coordinate related operations
 ↓
Ask data-access layer for persistence
 ↓
Return application result
```

Your reference Todo service demonstrates this with:

```text
Create Todo
+
Activity log
```

and:

```text
Update Todo
+
Version increment
+
Activity log
```

and:

```text
Complete Todo
+
completedAt
```

That is the real meaning of **business logic**.
