# Lesson 12.14 — Transactions and Business Operations

This lesson is where the idea of a **service** becomes much more powerful.

Your roadmap places:

```text
12.13 CRUD Service
        ↓
12.14 Transactions and Business Operations
        ↓
12.15 Service Composition
```

The key question today is:

> **What happens when one business operation requires multiple database changes, and one of those changes fails?**

---

# 1. The Problem

Let's use the Todo example from your starter/reference.

When a Todo is created, the application may need to do:

```text
Create Todo
    ↓
Create Activity Log
```

Your reference service does exactly this:

```js
const todo = await Todo.create(data);

await Activity.create({
    todoId: todo._id,
    action: "create",
    userId
});
```

At first glance, this looks fine.

But imagine:

```text
Todo.create()
      ↓
SUCCESS ✅

Activity.create()
      ↓
FAIL ❌
```

Now MongoDB contains:

```text
Todo exists
Activity doesn't exist
```

Your application is in a **partially completed state**.

That's the problem transactions solve.

---

# 2. What Is a Business Operation?

A business operation is a complete action from the application's point of view.

For example:

```text
Create Todo
```

might actually mean:

```text
1. Create Todo
2. Record activity
3. Update some related data
4. Send/queue a notification
```

The user thinks:

> "I created a Todo."

They don't think:

> "Step 1 succeeded but step 2 failed."

So the backend needs to decide what must happen **together**.

---

# 3. Atomicity

A transaction gives us the idea:

```text
ALL
or
NOTHING
```

For example:

```text
BEGIN TRANSACTION

Create Todo
Create Activity

COMMIT
```

If everything succeeds:

```text
COMMIT
```

Both changes remain.

If something fails:

```text
ROLLBACK
```

Both changes are undone.

Conceptually:

```text
              TRANSACTION
                   │
          ┌────────┴────────┐
          ▼                 ▼
     Create Todo       Create Activity
          │                 │
          └────────┬────────┘
                   ▼
             Everything OK?
              /          \
            YES           NO
             ↓             ↓
          COMMIT        ROLLBACK
```

---

# 4. Without a Transaction

Imagine:

```js
const todo = await Todo.create(data);

await Activity.create({
    todoId: todo._id,
    action: "create",
    userId
});
```

Possible result:

```text
Todo      → SUCCESS
Activity  → FAILURE
```

Database:

```text
Todos
├── Todo A
└── Todo B   ← newly created

Activities
└── no activity for Todo B
```

That's inconsistent.

---

# 5. With a Transaction

The idea becomes:

```text
Start session
    ↓
Start transaction
    ↓
Create Todo
    ↓
Create Activity
    ↓
Everything successful?
    ↓
YES → commit
NO  → abort
```

So:

```text
SUCCESS
→ both exist

FAILURE
→ neither exists
```

That's much safer when both operations are supposed to be one atomic business action.

---

# 6. MongoDB Transactions

Because your backend uses MongoDB/Mongoose, transactions are commonly implemented using a Mongoose session.

Conceptually:

```js
const session = await mongoose.startSession();

session.startTransaction();

try {

    // database operations

    await session.commitTransaction();

} catch (error) {

    await session.abortTransaction();

    throw error;

} finally {

    await session.endSession();

}
```

The important parts are:

```text
startSession()
startTransaction()
commitTransaction()
abortTransaction()
endSession()
```

---

# 7. Simple Example

Let's build:

```text
createTodo()
```

with an activity log.

```js
import mongoose from "mongoose";
import Todo from "../models/todo.model.js";
import Activity from "../models/activity.model.js";

export const createTodo = async ({
    data,
    userId
}) => {

    const session = await mongoose.startSession();

    try {

        session.startTransaction();

        const [todo] = await Todo.create(
            [
                {
                    ...data,
                    userId
                }
            ],
            { session }
        );

        await Activity.create(
            [
                {
                    todoId: todo._id,
                    action: "create",
                    userId
                }
            ],
            { session }
        );

        await session.commitTransaction();

        return todo;

    } catch (error) {

        await session.abortTransaction();

        throw error;

    } finally {

        await session.endSession();

    }
};
```

Don't worry about memorizing this code yet.

Understand the **idea first**.

---

# 8. Why `session` Is Passed to Both Operations

This is extremely important.

We have:

```js
Todo.create(..., { session })
```

and:

```js
Activity.create(..., { session })
```

Both operations participate in the same transaction.

Think:

```text
Session A
   │
   ├── Todo.create()
   │
   └── Activity.create()
```

Without passing the same session, they aren't part of the same transaction.

---

# 9. The Transaction Lifecycle

Let's slow this down.

### Step 1

```js
const session = await mongoose.startSession();
```

We create a database session.

---

### Step 2

```js
session.startTransaction();
```

We say:

> Start a transaction.

---

### Step 3

```js
Todo.create(..., { session });
```

Todo creation belongs to the transaction.

---

### Step 4

```js
Activity.create(..., { session });
```

Activity creation also belongs to the same transaction.

---

### Step 5

```js
await session.commitTransaction();
```

Everything succeeds.

MongoDB commits the changes.

---

### Step 6 — Failure

If something throws:

```js
await session.abortTransaction();
```

MongoDB rolls back the transaction.

---

### Step 7

```js
await session.endSession();
```

We clean up the session.

---

# 10. What Does Rollback Mean?

Suppose:

```text
Initial database

Todo count = 10
Activity count = 50
```

We start:

```text
Create Todo
```

Temporary state:

```text
Todo count = 11
```

Then:

```text
Create Activity
```

fails.

Without transaction:

```text
Todo count = 11
Activity count = 50
```

With rollback:

```text
Todo count = 10
Activity count = 50
```

The Todo creation is undone.

---

# 11. Why This Belongs in the Service

Notice who knows that:

```text
Create Todo
+
Create Activity
```

are one business operation?

Not the controller.

Not the route.

Not the model.

The **service** knows.

That's why transactions often live around service-level business operations.

The service says:

> "Creating a Todo includes these related database changes."

---

# 12. Controller Shouldn't Manage the Transaction

Avoid:

```js
const createTodo = async (req, res) => {

    const session = await mongoose.startSession();

    session.startTransaction();

    // database operations...

    await session.commitTransaction();

    res.json(...);
};
```

Now your controller understands:

```text
HTTP
+
business operation
+
database transaction
```

That's too much responsibility.

Instead:

```text
Controller
    ↓
todoService.createTodo()
    ↓
transaction
    ↓
repositories
    ↓
database
```

The controller remains thin.

---

# 13. Transaction Boundary

This is an important concept.

A **transaction boundary** defines:

> Which operations must succeed or fail together?

For example:

```text
Create Order
    │
    ├── Create Order
    ├── Create Order Items
    └── Update Inventory
```

Maybe these three must be atomic:

```text
ALL SUCCESS
    ↓
COMMIT
```

or:

```text
ANY FAILURE
    ↓
ROLLBACK
```

That's a transaction boundary.

---

# 14. Another Example: Money Transfer

This is an even clearer example.

Suppose:

```text
Account A
₹10,000

Account B
₹5,000
```

Transfer:

```text
₹2,000
```

The operation requires:

```text
1. Subtract ₹2,000 from A
2. Add ₹2,000 to B
```

Without a transaction:

```text
A → -₹2,000 SUCCESS
B → +₹2,000 FAILURE
```

Now:

```text
₹2,000 disappeared
```

That's unacceptable.

With a transaction:

```text
BEGIN

A -= 2000
B += 2000

COMMIT
```

If step 2 fails:

```text
ROLLBACK
```

Account A gets its ₹2,000 back.

# 15. Business Operation vs CRUD

This is the deeper lesson.

A simple CRUD operation:

```text
Update Todo
```

may only require:

```text
UPDATE todo
```

But a business operation:

```text
Complete Todo
```

might mean:

```text
Update Todo status
+
Set completedAt
+
Create Activity
+
Update statistics
```

Now you have a **business operation**.

That's why the service layer is more than a CRUD wrapper.

# 16. `completeTodo()` Example

Your reference already defines:

```js
const updateData = {
    status: "done",
    completedAt: new Date()
};
```

then updates the Todo and creates an Activity record.

Conceptually:

```text
completeTodo()
      │
      ├── update Todo
      │
      └── create Activity
```

If the application requires both to remain consistent, this is a good candidate for a transaction.

---

# 17. Transaction Version

Conceptually:

```js
const completeTodo = async ({
    todoId,
    userId
}) => {

    const session = await mongoose.startSession();

    try {

        session.startTransaction();

        const todo =
            await todoRepository.complete(
                {
                    todoId,
                    userId,
                    session
                }
            );

        if (!todo) {
            throw new AppError(
                "Todo not found",
                404
            );
        }

        await activityRepository.create(
            {
                todoId: todo._id,
                action: "complete",
                userId
            },
            session
        );

        await session.commitTransaction();

        return todo;

    } catch (error) {

        await session.abortTransaction();

        throw error;

    } finally {

        await session.endSession();

    }
};
```

This is closer to the architecture you'll eventually build after Phase 13.

---

# 18. A Very Important Detail: Not Everything Needs a Transaction

Don't think:

> "Every database operation should use a transaction."

That's not the goal.

Transactions add overhead and complexity.

You should ask:

> **Do these operations need to succeed or fail together?**

If:

```text
Update Todo
```

is completely independent:

```text
Todo.update()
```

may be enough.

But:

```text
Update Todo
+
Create required Activity
```

may need atomicity depending on your application's consistency requirements.

---

# 19. Example That Doesn't Need a Transaction

Suppose:

```text
GET /todos/:id
```

The operation is:

```text
Read Todo
```

There is no multi-step write operation.

You normally don't need:

```text
startTransaction()
```

for a simple read.

---

# 20. Another Example

Suppose:

```text
PATCH /users/me
```

changes only:

```text
name
```

One database write:

```text
User.update()
```

A transaction is probably unnecessary.

But:

```text
Delete Account
```

might involve:

```text
Delete User
Delete Sessions
Delete Private Data
Create Audit Record
```

Now you should consider whether those operations need to be atomic.

# 21. Transaction Doesn't Mean "Make Everything Safe"

This is another common misunderstanding.

A transaction protects **database consistency**.

It doesn't automatically solve:

```text
Authentication
Authorization
Input validation
Rate limiting
XSS
CSRF
JWT theft
Business authorization
```

For example:

```text
User A
    ↓
Update User B's Todo
```

A transaction won't stop that.

You still need:

```text
Authentication
+
Authorization/ownership
```

The roadmap later explicitly teaches ownership and authorization.

---

# 22. Transaction vs Validation

Suppose the client sends:

```json
{
    "priority": "super-important"
}
```

Validation should reject that.

You don't need:

```text
Transaction
```

to solve it.

Think:

```text
Validation
→ Is the input structurally valid?

Service
→ Is the operation allowed?

Transaction
→ Must multiple database changes succeed together?
```

---

# 23. Transaction vs Authorization

Suppose:

```text
Rahul owns Todo A
Amit owns Todo B
```

Rahul requests:

```text
PATCH /todos/B
```

Authorization should reject it.

A transaction doesn't decide ownership.

So:

```text
Authorization
→ "Can Rahul do this?"

Transaction
→ "If we do this, do all required database changes succeed together?"
```

Two completely different responsibilities.

---

# 24. Transaction vs Error Handling

Transactions also don't replace error handling.

You still need:

```js
try {
    ...
} catch (error) {
    await session.abortTransaction();
    throw error;
}
```

The service throws the error.

Then your global error middleware eventually turns it into the HTTP response.

The architecture remains:

```text
Database error
      ↓
Service
      ↓
throw
      ↓
asyncHandler
      ↓
Error Middleware
      ↓
HTTP response
```

---

# 25. What Happens If `commitTransaction()` Fails?

This is a more advanced point.

You shouldn't assume:

```js
commitTransaction()
```

can never fail.

Real database systems can encounter:

```text
network issues
write conflicts
transient errors
transaction limits
```

Production-grade transaction handling may need retry strategies for specific transient failures.

For your current learning stage, remember:

```text
transaction
→ commit
→ if failure, handle/retry according to the database error
```

Don't build complex retry logic into every service yet.

# 26. Transactions and Repository Pattern

This lesson also prepares you for Phase 13.

Right now you may write:

```js
Todo.findOneAndUpdate(...)
Activity.create(...)
```

directly in the service.

Later:

```text
Service
    ↓
Todo Repository
    ↓
Todo Model

Service
    ↓
Activity Repository
    ↓
Activity Model
```

The transaction still belongs to the **business operation**, while repositories receive the session/context needed to participate in it.

Conceptually:

```text
Service
  │
  │ transaction session
  │
  ├── Todo Repository
  │
  └── Activity Repository
```

---

# 27. Don't Put Business Decisions in the Repository

Bad:

```js
const updateTodo = async (...) => {

    if (todo.status === "done") {
        // business decision
    }

    // database operation
};
```

The repository shouldn't decide:

> "A completed Todo cannot be changed."

That's a business rule.

Instead:

```text
Service
→ decide whether operation is allowed

Repository
→ perform database operation
```

# 28. Transaction Helper

As your application grows, you'll notice repetitive code:

```js
const session = await mongoose.startSession();

try {
    session.startTransaction();

    // ...

    await session.commitTransaction();
} catch (error) {
    await session.abortTransaction();
    throw error;
} finally {
    await session.endSession();
}
```

You can eventually create a helper such as:

```js
export const withTransaction = async (
    callback
) => {

    const session =
        await mongoose.startSession();

    try {

        session.startTransaction();

        const result =
            await callback(session);

        await session.commitTransaction();

        return result;

    } catch (error) {

        await session.abortTransaction();

        throw error;

    } finally {

        await session.endSession();

    }
};
```

Then:

```js
const todo = await withTransaction(
    async (session) => {

        const todo =
            await todoRepository.create(
                data,
                session
            );

        await activityRepository.create(
            activity,
            session
        );

        return todo;
    }
);
```

This can make services cleaner.

But don't rush to build this abstraction until you understand transactions themselves.

# 32. The "All or Nothing" Test

Whenever you're writing a service, ask:

> **If step 2 fails, am I okay with step 1 remaining?**

### Example

```text
Create Todo
+
Create Activity
```

If activity creation fails:

```text
Should Todo remain?
```

If the answer is:

```text
NO
```

you likely need atomicity.

---

### Another example

```text
Update profile
+
Send analytics event
```

If analytics fails:

```text
Should profile update be rolled back?
```

Usually:

```text
NO
```

So you probably shouldn't make the analytics operation part of the database transaction.

This is an important distinction.

---

# 33. Database Transaction vs External Service

Here's a subtle but important concept.

Suppose:

```text
Create Order
+
Send Email
```

You cannot simply assume:

```text
MongoDB transaction
```

can roll back:

```text
Gmail / SMTP / external email provider
```

A database transaction controls the database operations participating in that transaction.

It cannot magically undo:

```text
email already sent
API request already made
payment already charged
```

So external side effects require other patterns, which you'll encounter later when learning background jobs/outbox-style architectures.

For now:

```text
Database operations
→ transaction can provide atomicity

External side effects
→ need separate reliability patterns
```

# 37. What You Should Know Before Moving On

You should now be able to explain:

### What is a transaction?

> A group of database operations treated as one atomic unit.

### What is atomicity?

> Either all required operations succeed, or the transaction is rolled back.

### Why does a service care about transactions?

> Because the service represents the business operation and knows which database changes belong together.

### Does every CRUD operation need a transaction?

> No.

### Does a transaction provide authorization?

> No.

### Can a database transaction automatically undo an email?

> No.

### Why use a transaction with Todo + Activity?

> If the application's consistency requirement says the Todo and its required activity record must be created/updated together.
