# Lesson 12.15 — Service Composition

We now build directly on **12.14 — Transactions and Business Operations**.

Your roadmap defines this lesson as:

```text
12.14 → Transactions and Business Operations
12.15 → Service Composition
12.16 → Avoiding Giant Services
```

The main idea is:

> **Sometimes one business operation needs several pieces of application logic. How do we combine them without putting everything into one huge service?**

---

# 1. What Is Service Composition?

Suppose we have:

```text
TodoService
```

and completing a Todo requires:

```text
Todo logic
+
Notification logic
+
Activity logging
```

Instead of putting all of this into one enormous file:

```text
todo.service.js
```

we can compose smaller services:

```text
TodoService
    │
    ├── ActivityService
    │
    └── NotificationService
```

So:

> **Service composition means combining multiple focused services to complete one larger business operation.**

---

# 2. Why Do We Need It?

Imagine `todo.service.js` becomes:

```js
createTodo()
getTodo()
listTodos()
updateTodo()
deleteTodo()
completeTodo()
restoreTodo()
sendNotification()
createActivity()
sendEmail()
hashSomething()
generateToken()
calculateStatistics()
...
```

Soon you have:

```text
todo.service.js
→ 1,500 lines
```

😵

That's exactly the problem your next lesson, **12.16 Avoiding Giant Services**, is going to address.

Instead, separate responsibilities:

```text
TodoService
ActivityService
NotificationService
EmailService
```

Then compose them where necessary.

---

# 3. A Simple Example

Suppose:

```text
completeTodo()
```

requires:

```text
1. Complete Todo
2. Record activity
3. Notify user
```

We can design:

```text
TodoService
     │
     ├── TodoRepository
     │
     ├── ActivityService
     │
     └── NotificationService
```

The operation becomes:

```text
completeTodo()
      │
      ├── update Todo
      │
      ├── record activity
      │
      └── send notification
```

That's composition.

---

# 4. First Understand "Responsibility"

Before composing services, each service should have a clear responsibility.

For example:

### Todo Service

```text
Todo-related business operations
```

### Activity Service

```text
Activity/audit-related operations
```

### Notification Service

```text
Notification-related operations
```

### Email Service

```text
Email delivery-related operations
```

So:

```text
TodoService
    ❌ shouldn't become EmailService

ActivityService
    ❌ shouldn't become TodoService
```

---

# 5. Service Composition in Your Architecture

Your overall architecture is:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
    ↓
MongoDB
```

With composition:

```text
                  Controller
                      │
                      ▼
                 TodoService
                 /    |     \
                /     |      \
               ▼      ▼       ▼
            TodoRepo Activity Notification
               │        │        │
               ▼        ▼        ▼
             Model    Model    Provider
```

The main service coordinates the operation.

---

# 6. Controller Doesn't Compose Services

Don't do this:

```js
const completeTodo = async (req, res) => {

    await todoService.completeTodo();

    await activityService.createActivity();

    await notificationService.notify();

    res.json(...);
};
```

Now the controller is deciding the business workflow.

Instead:

```js
const completeTodo = asyncHandler(
    async (req, res) => {

        const todo =
            await todoService.completeTodo({
                todoId: req.params.id,
                userId: req.user.id
            });

        res.status(200).json({
            success: true,
            data: todo
        });
    }
);
```

The controller only says:

> "Perform the complete-Todo operation."

The service decides **how** that operation happens.

---

# 7. A Better `TodoService`

Conceptually:

```js
const completeTodo = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.complete({
            todoId,
            userId
        });

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    await activityService.record({
        userId,
        action: "TODO_COMPLETED",
        resourceId: todo._id
    });

    await notificationService.send({
        userId,
        type: "TODO_COMPLETED",
        todoId: todo._id
    });

    return todo;
};
```

Now:

```text
TodoService
→ coordinates

ActivityService
→ knows activity rules

NotificationService
→ knows notification rules
```

That's much cleaner.

# 8. What Does "Composition" Actually Mean?

Think about a restaurant.

You order:

> "Make me a pizza."

The pizza chef doesn't personally:

```text
grow wheat
make flour
mine salt
manufacture cheese
build the oven
```

They coordinate specialized pieces.

Similarly:

```text
TodoService
```

doesn't need to know every detail of:

```text
Activity
Email
Notification
```

It asks specialized services to perform those operations.

# 9. Service-to-Service Dependency

For example:

```text
todo.service.js
```

could import:

```js
import activityService
    from "./activity.service.js";

import notificationService
    from "./notification.service.js";
```

Then:

```js
await activityService.record(...);

await notificationService.send(...);
```

This is a service dependency.

---

# 10. But Be Careful

This can become dangerous:

```text
TodoService
   ↓
ActivityService
   ↓
NotificationService
   ↓
TodoService
```

Now we have a circular dependency.

```text
A → B → C → A
```

This is one of the major things you need to learn to avoid.

---

# 11. Circular Dependency Example

Suppose:

```text
todo.service.js
```

imports:

```text
activity.service.js
```

And then:

```text
activity.service.js
```

imports:

```text
todo.service.js
```

You get:

```text
TodoService
    ↓
ActivityService
    ↓
TodoService
    ↓
ActivityService
    ↓
...
```

This is a design smell.

The problem isn't merely JavaScript imports.

The deeper problem is:

> **The responsibilities are probably too tightly coupled.**

---

# 12. How Do We Avoid Circular Dependencies?

One useful strategy is to introduce an **orchestrator**.

Instead of:

```text
TodoService
    ↔
ActivityService
```

we can have:

```text
TodoWorkflow
   │
   ├── TodoService
   └── ActivityService
```

Now:

```text
TodoWorkflow
      │
      ├── TodoService
      │
      └── ActivityService
```

Neither service needs to call the other.

---

# 13. What Is an Orchestrator?

An orchestrator coordinates a larger business workflow.

For example:

```text
TodoCompletionService
```

could do:

```text
Complete Todo
     ↓
Record activity
     ↓
Send notification
```

while the individual services remain focused.

Think:

```text
Specialized Service
→ performs one responsibility

Orchestrator
→ coordinates several responsibilities
```

---

# 14. Example Architecture

```text
Controller
    ↓
TodoWorkflowService
    │
    ├── TodoService
    │      ↓
    │   TodoRepository
    │
    ├── ActivityService
    │      ↓
    │   ActivityRepository
    │
    └── NotificationService
           ↓
       Notification provider
```

This is a clean form of composition.

---

# 15. Do We Always Need an Orchestrator?

No.

For simple applications:

```text
TodoService
    ↓
ActivityService
```

may be perfectly reasonable.

Don't create:

```text
TodoWorkflowService
TodoCoordinatorService
TodoApplicationService
TodoBusinessOrchestrator
```

for every two-line operation.

That's over-engineering.

Start simple.

Introduce an orchestration layer when the workflow genuinely becomes complex.

---

# 16. Composition vs Transactions

This is an important connection to 12.14.

Suppose:

```text
completeTodo()
```

does:

```text
1. Update Todo
2. Record Activity
```

You might have:

```text
TodoService
     │
     └── ActivityService
```

But if both operations need to be atomic:

```text
Todo update
+
Activity creation
```

they need to participate in the **same transaction**.

Conceptually:

```text
              Transaction
                  │
          ┌───────┴────────┐
          ▼                ▼
     TodoService      ActivityService
          │                │
          ▼                ▼
      TodoRepo         ActivityRepo
```

The transaction boundary belongs to the overall business operation.

---

# 17. Important Transaction Design

Don't accidentally do:

```js
await todoService.completeTodo();

await activityService.record();
```

where `todoService.completeTodo()` internally commits its own transaction.

Then:

```text
Transaction A
→ Todo update
→ COMMIT

Transaction B
→ Activity
→ FAIL
```

You still have inconsistency.

If the operations must be atomic, they should share the same transaction context.

---

# 18. Passing Transaction Context

Conceptually:

```js
await todoService.completeTodo({
    todoId,
    userId,
    session
});

await activityService.record({
    userId,
    action: "TODO_COMPLETED",
    resourceId: todoId,
    session
});
```

Both repositories then use:

```js
{ session }
```

with their database operations.

The exact implementation will become much cleaner once you reach the repository phase, because your roadmap explicitly teaches repositories after Phase 12.

---

# 19. Don't Pass `req` Between Services

Avoid:

```js
todoService.completeTodo(req);
```

and:

```js
activityService.record(req);
```

Instead pass application data:

```js
todoService.completeTodo({
    todoId,
    userId
});
```

This keeps services independent of Express.

---

# 20. Don't Pass `res`

Never:

```js
notificationService.send(req, res);
```

Services should not know about:

```text
Express
HTTP response
status codes
headers
```

unless you intentionally design a very different architecture.

Keep:

```text
HTTP
→ Controller

Business operation
→ Service

Database
→ Repository
```

# 22. But External Email Changes the Transaction Problem

Remember the previous lesson.

A database transaction can control:

```text
User creation
Verification token
Activity
```

but not:

```text
Email already sent
```

So you should not think:

```text
MongoDB transaction
+
email
=
everything atomic
```

It doesn't work that way.

Instead:

```text
Database transaction
        ↓
Commit
        ↓
Queue/send email
```

or use a reliable event/outbox pattern later.

This is an advanced architecture topic, so for now just understand the boundary.


For example:


# 27. Composition Doesn't Mean Every Service Can Call Every Other Service

This is an important design rule.

Avoid:

```text
UserService
 ↕
AuthService
 ↕
TodoService
 ↕
ActivityService
 ↕
NotificationService
 ↕
UserService
```

That becomes a dependency web:

```text
      A
    ↗   ↘
   B     C
    ↘   ↗
      D
```

Hard to understand.

Hard to test.

Hard to modify.

---

# 28. Prefer One-Way Dependency Flow

A cleaner design:

```text
Workflow / Orchestrator
       │
 ┌─────┼─────┐
 ▼     ▼     ▼
A      B      C
```

instead of:

```text
A ↔ B ↔ C
```

For example:

```text
CheckoutService
    │
    ├── PaymentService
    ├── InventoryService
    └── OrderService
```

The dependencies have a clear direction.

# 29. Another Useful Technique: Shared Domain Service

Sometimes multiple services need the same logic.

Suppose:

```text
OrderService
UserService
AdminService
```

all need:

```text
calculateDiscount()
```

Don't duplicate:

```js
// OrderService
calculateDiscount()

// UserService
calculateDiscount()

// AdminService
calculateDiscount()
```

Create:

```text
PricingService
```

Then:

```text
OrderService ──┐
UserService ───┼──→ PricingService
AdminService ──┘
```

Now there's one source of truth.

# 30. But Avoid "Utils" for Everything

A common beginner reaction is:

> "I'll put everything shared into `utils.js`."

Then:

```text
utils.js
→ 2,000 lines
```

😂

Instead, ask:

> **What responsibility does this logic belong to?**

For example:

```text
calculatePrice()
→ PricingService

sendEmail()
→ EmailService

generateToken()
→ Token utility/service

formatDate()
→ utility
```

Not everything belongs in one generic utility file.

# 31. Service Composition and Dependency Injection

Now we're approaching a professional concept.

Instead of hardcoding dependencies:

```js
import activityService from "./activity.service.js";
import notificationService from "./notification.service.js";
```

you can inject them:

```js
const createTodoService = ({
    todoRepository,
    activityService,
    notificationService
}) => {

    return {
        async completeTodo(...) {
            ...
        }
    };
};
```

Then:

```js
const todoService = createTodoService({
    todoRepository,
    activityService,
    notificationService
});
```

This is **dependency injection**.

You don't need a DI framework for this.

JavaScript functions are enough.

---

# 32. Why Dependency Injection Helps

Testing becomes easier.

Suppose your real notification service sends emails.

For a unit test, you don't want to send real emails.

You can inject:

```js
const fakeNotificationService = {
    send: async () => {}
};
```

Then:

```text
TodoService
     ↓
FakeNotificationService
```

instead of:

```text
TodoService
     ↓
Real Email Provider
```

This is extremely useful for testing.

Your roadmap later includes **12.19 Testing Services**, so this becomes important.

---

# 33. Dependency Injection Without a Framework

You can write:

```js
const createTodoService = ({
    todoRepository,
    activityService
}) => {

    const createTodo = async ({
        data,
        userId
    }) => {

        const todo =
            await todoRepository.create({
                ...data,
                userId
            });

        await activityService.record({
            userId,
            action: "TODO_CREATED",
            resourceId: todo._id
        });

        return todo;
    };

    return {
        createTodo
    };
};

export default createTodoService;
```

Then:

```js
const todoService = createTodoService({
    todoRepository,
    activityService
});
```

This is a very clean pattern.

# 37. When Should You Create Another Service?

Ask these questions.

### Question 1

Does this logic have a distinct responsibility?

If yes:

```text
Maybe a separate service.
```

### Question 2

Will multiple features use this logic?

If yes:

```text
A shared service may make sense.
```

### Question 3

Is the current service becoming difficult to understand?

If yes:

```text
Consider extracting responsibilities.
```

### Question 4

Will extraction create circular dependencies?

If yes:

```text
Consider an orchestrator.
```

---

# 38. When Should You NOT Create Another Service?

Don't create:

```text
UserNameService
TodoTitleService
TodoStatusService
TodoIdService
```

just because each operation is technically separate.

That's over-engineering.

A service should represent a meaningful responsibility or domain capability.

---

# 39. Service Composition vs Repository Composition

Don't confuse these.

### Service composition

```text
TodoService
   ↓
ActivityService
```

This is application/business logic.

### Repository composition

```text
TodoRepository
   ↓
Todo Model
```

This is data access.

Your roadmap deliberately separates these layers:

```text
Controller
→ Service
→ Repository
→ Model
```

---

# 40. Service Composition vs Middleware Composition

Also different.

Middleware composition:

```text
authMiddleware
      ↓
validationMiddleware
      ↓
rateLimitMiddleware
      ↓
controller
```

Service composition:

```text
TodoService
      ↓
ActivityService
      ↓
NotificationService
```

Middleware answers:

> **Can the request continue?**

Services answer:

> **What should the application do?**

# 41. A Complete Example

Let's imagine:

```text
POST /todos/:id/complete
```

### Route

```js
router.post(
    "/:id/complete",
    authMiddleware,
    todoController.complete
);
```

### Controller

```js
const complete = asyncHandler(
    async (req, res) => {

        const todo =
            await todoService.completeTodo({
                todoId: req.params.id,
                userId: req.user.id
            });

        res.status(200).json({
            success: true,
            data: todo
        });
    }
);
```

### Service

```js
const completeTodo = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.complete({
            todoId,
            userId
        });

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

        userId,
        action: "TODO_COMPLETED",
        resourceId: todo._id

        userId,

        resourceId: todo._id
    });

};
```

Now you can clearly see:

```text
Controller
→ HTTP

TodoService
→ business workflow

TodoRepository
→ Todo database operation

ActivityService
→ activity responsibility

NotificationService
→ notification responsibility
```

That's a mature separation.

# 42. One Important Improvement

Suppose notification fails:

```text
Todo update       ✅
Activity record   ✅
Notification      ❌
```

Should the Todo be rolled back?

Probably not necessarily.

Why?

Because notification is often a **side effect**, not core database state.

You might instead:

```text
Complete Todo
     ↓
Commit database transaction
     ↓
Queue notification
     ↓
Background worker sends notification
```

This is more reliable than making the user's Todo operation depend on an external notification provider.

We'll study background work much later in your roadmap.

---

# 43. Core Operation vs Side Effect

This distinction is extremely useful.

### Core operation

```text
Complete Todo
```

### Related database state

```text
Activity record
```

### Side effect

```text
Send email
Send push notification
Send webhook
```

Often:

```text
Core operation
+
required database changes
→ transaction
```

while:

```text
External side effects
→ queue/background processing
```

This isn't an absolute rule, but it's a very useful architecture guideline.

# 44. Your Service Dependency Graph

For a small backend:

```text
AuthService
    ↓
UserRepository

UserService
    ↓
UserRepository

TodoService
    ↓
TodoRepository
```

As it grows:

```text
TodoService
    ├── TodoRepository
    ├── ActivityService
    └── NotificationService

ActivityService
    └── ActivityRepository

NotificationService
    └── NotificationProvider
```

Notice the direction:

```text
Business workflow
       ↓
Focused services
       ↓
Repositories/providers
```

Not the other way around.

# 45. The Golden Rule

Remember this:

> **Compose services to coordinate business capabilities, not to move code around just for the sake of having more files.**

If:

```text
TodoService
```

needs activity functionality:

```text
use ActivityService
```

If:

```text
TodoService
```

needs notification functionality:

```text
use NotificationService
```

If these dependencies start forming a circle:

```text
A → B → A
```

stop and reconsider the architecture.

Maybe you need:

```text
Orchestrator
```

or:

```text
Shared domain service
```

or:

```text
a clearer responsibility boundary
```

### Good

```text
CheckoutService
 ├── PaymentService
 ├── InventoryService
 └── OrderService
```

### Bad

```text
PaymentService
 ↔ OrderService
 ↔ InventoryService
 ↔ PaymentService
```

### Transaction

If several **database changes** must succeed together:

```text
Shared transaction
```

### External side effect

If something like email/notification is involved:

```text
Don't assume database transaction
can roll it back.
```
