# Lesson 12.16 — Avoiding Giant Services

This lesson is very important because you're moving from:

```text
"I know how to create a service."
```

to:

```text
"I know how to design a service properly."
```

The goal is **not** to make many files just for the sake of it.

The goal is:

> **Keep each service focused enough that you can understand, test, and change it without fear.**

---

# 1. What Is a Giant Service?

Imagine you have:

```text
services/
└── user.service.js
```

At first it looks fine:

```js
createUser()
getUser()
updateUser()
deleteUser()
```

Then the application grows.

You add:

```js
registerUser()
loginUser()
logoutUser()
refreshToken()
changePassword()
forgotPassword()
resetPassword()
verifyEmail()
resendVerification()
uploadAvatar()
deleteAvatar()
updateProfile()
changeEmail()
deleteAccount()
banUser()
unbanUser()
createAdmin()
removeAdmin()
sendWelcomeEmail()
sendPasswordResetEmail()
createActivity()
generateReport()
```

Eventually:

```text
user.service.js
→ 2,000 lines
```

That's a **giant service**.

---

# 2. Why Giant Services Are Bad

A giant service creates several problems.

### Problem 1 — Hard to understand

You open:

```text
user.service.js
```

and see hundreds of functions.

You don't know:

```text
Which code handles authentication?
Which code handles profile?
Which code handles admin?
Which code handles passwords?
```

---

### Problem 2 — Hard to test

Suppose you want to test:

```text
changePassword()
```

but the same file contains:

```text
authentication
email
admin
profile
avatar
permissions
```

The test setup becomes complicated.

---

### Problem 3 — Hard to modify

You change:

```text
password logic
```

and accidentally break:

```text
login
reset password
email verification
```

because everything is tightly connected.

---

### Problem 4 — Merge conflicts

Imagine two developers work on:

```text
user.service.js
```

Developer A:

```text
authentication
```

Developer B:

```text
profile
```

Both modify the same giant file.

Git conflicts become much more likely.

---

# 3. The Real Question

Don't ask:

> "How many functions should a service contain?"

Ask:

> **"What responsibility does this service own?"**

That's a much better architectural question.

---

# 4. One Service ≠ One Function

This is important.

You don't want:

```text
create-user.service.js
get-user.service.js
update-user.service.js
delete-user.service.js
```

That's too fragmented.

Instead:

```text
user.service.js
```

can reasonably contain:

```text
createUser()
getUser()
updateUser()
deleteUser()
```

because these operations belong to the same responsibility.

The goal is **cohesion**, not tiny files.

---

# 5. What Is Cohesion?

Cohesion means:

> **How closely related the responsibilities inside a module are.**

High cohesion:

```text
password.service.js

hashPassword()
comparePassword()
validatePassword()
```

These operations are closely related.

Good.

Low cohesion:

```text
user.service.js

createUser()
sendEmail()
processPayment()
generateReport()
uploadImage()
calculateTax()
```

These responsibilities are unrelated.

Bad.

---

# 6. A Useful Rule

Think:

```text
High cohesion
    ↓
Good service

Unrelated responsibilities
    ↓
Consider splitting
```

For example:

```text
AuthService
PasswordService
UserService
NotificationService
```

is usually more understandable than:

```text
EverythingService
```

😂

---

# 7. Your Starter Already Shows This Idea

Your starter structure separates authentication and password responsibilities:

```text
services/
├── auth.service.js
└── password.service.js
```

This is a good example of separating related but distinct responsibilities.

Instead of putting:

```text
login
register
hash password
compare password
refresh token
```

all inside one enormous service, password-specific logic can have its own focused boundary.

---

# 8. Example: Authentication

A beginner might create:

```text
auth.service.js
```

containing:

```js
register()
login()
logout()
refreshToken()
hashPassword()
comparePassword()
resetPassword()
verifyEmail()
```

This can become too much.

A better conceptual split could be:

```text
AuthService
    ↓
authentication workflows

PasswordService
    ↓
password-specific logic

TokenService
    ↓
token-specific logic

EmailVerificationService
    ↓
verification workflow
```

Now responsibilities are clearer.

---

# 9. But Don't Split Everything Immediately

This is where beginners often go too far.

You might think:

```text
login()
→ LoginService

logout()
→ LogoutService

refreshToken()
→ RefreshTokenService
```

Now you have:

```text
services/
├── login.service.js
├── logout.service.js
├── refresh-token.service.js
├── register.service.js
├── password.service.js
...
```

This can actually make the project **harder** to understand.

So remember:

> **Split by responsibility, not by function count.**

---

# 10. A Practical Example

Suppose you have:

```text
user.service.js
```

with:

```js
createUser()
getUserById()
updateUser()
deleteUser()
changePassword()
sendVerificationEmail()
banUser()
unbanUser()
```

Ask:

### User CRUD

```text
createUser()
getUserById()
updateUser()
deleteUser()
```

Clearly related.

### Password

```text
changePassword()
```

Could belong to:

```text
PasswordService
```

### Email verification

```text
sendVerificationEmail()
```

Could belong to:

```text
VerificationService
```

### Moderation

```text
banUser()
unbanUser()
```

Could eventually belong to:

```text
UserModerationService
```

depending on the size of your application.

---

# 11. Think in Capabilities

Another useful approach is to think about **capabilities**.

A user module might have:

```text
User
├── Profile
├── Authentication
├── Password
├── Verification
└── Administration
```

These are different capabilities.

So your application might evolve into:

```text
services/
├── user.service.js
├── auth.service.js
├── password.service.js
├── verification.service.js
└── admin-user.service.js
```

Not every project needs all five.

You introduce them when the responsibilities actually become meaningful.

# 12. Giant Todo Service

Now let's apply this to your project.

Imagine:

```text
todo.service.js
```

starts with:

```js
createTodo()
getTodo()
listTodos()
updateTodo()
deleteTodo()
completeTodo()
restoreTodo()
```

That's completely reasonable.

But later you add:

```js
shareTodo()
assignTodo()
inviteCollaborator()
sendReminder()
scheduleReminder()
generateTodoReport()
exportTodos()
importTodos()
archiveTodo()
bulkDelete()
bulkComplete()
```

Now things are getting crowded.

---

# 13. How Could We Split It?

Potentially:

```text
TodoService
    ↓
Core Todo operations

TodoCollaborationService
    ↓
Sharing/assignment

TodoReminderService
    ↓
Reminders

TodoExportService
    ↓
Export/import

TodoReportService
    ↓
Reports
```

Again:

**Don't create these just because they sound nice.**

Create them when those responsibilities become substantial.

---

# 14. The "Change Together" Principle

Here's one of the most useful rules.

Ask:

> **Do these functions usually change together?**

Suppose:

```text
createTodo()
updateTodo()
deleteTodo()
```

all depend on the Todo model.

They probably change together.

Keep them together.

But:

```text
sendReminder()
```

may involve:

```text
scheduler
notification provider
queue
email
```

It may evolve independently.

That suggests a separate service.

---

# 15. Another Important Question

Ask:

> **Would I want to test these things together?**

For example:

```text
hashPassword()
comparePassword()
```

Yes.

They are tightly related.

So:

```text
password.service.js
```

makes sense.

But:

```text
hashPassword()
generateMonthlyRevenueReport()
```

No.

They don't belong together.

---

# 16. Business Boundary

A good service often represents a meaningful **business boundary**.

For example:

```text
PaymentService
```

could own:

```text
createPayment()
capturePayment()
refundPayment()
getPaymentStatus()
```

These operations are related.

Another:

```text
NotificationService
```

could own:

```text
sendEmail()
sendPush()
sendInAppNotification()
```

depending on your architecture.

---

# 17. Avoid the "God Service"

A **God Service** is a service that knows and does almost everything.

For example:

```text
app.service.js
```

containing:

```text
users
auth
todos
payments
emails
notifications
reports
files
analytics
```

This is the service-layer version of a God object.

Avoid it.

A healthy architecture looks more like:

```text
                 Application
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
    AuthService   TodoService   UserService
       │             │             │
       ▼             ▼             ▼
   repositories   repositories  repositories
```

---

# 18. But Don't Make Services Too Small

The opposite problem is **over-fragmentation**.

For example:

```text
TodoCreateService
TodoReadService
TodoUpdateService
TodoDeleteService
TodoCompleteService
TodoRestoreService
```

For a small application, this could be unnecessary.

Instead:

```text
TodoService
```

can own the core Todo lifecycle.

---

# 19. The Sweet Spot

Think of service size like this:

```text
Too small
   ↓
Many tiny services
   ↓
Hard to navigate

GOOD
   ↓
Focused, cohesive services
   ↓
Easy to understand

Too large
   ↓
God/Giant service
   ↓
Hard to maintain
```

Your goal is the middle.

---

# 20. Service Splitting Is an Evolution

You don't need to predict your entire architecture on day one.

Start:

```text
todo.service.js
```

Then as the project grows:

```text
todo.service.js
todo-reminder.service.js
todo-collaboration.service.js
```

This is normal.

Good architecture is often **evolved**, not designed perfectly upfront.

---

# 21. Refactoring Example

Imagine you start with:

```js
// user.service.js

export const createUser = ...
export const updateUser = ...
export const changePassword = ...
export const verifyEmail = ...
export const sendVerificationEmail = ...
```

At first this may be acceptable.

Later you notice:

```text
Password code = 200 lines
Verification code = 300 lines
User CRUD = 150 lines
```

Now refactor.

Before:

```text
UserService
├── CRUD
├── Password
└── Verification
```

After:

```text
UserService
├── CRUD

PasswordService
├── password operations

VerificationService
├── verification operations
```

---

# 22. Don't Duplicate Business Logic During Refactoring

A common mistake:

Before:

```js
userService.changePassword()
```

After creating:

```js
passwordService.changePassword()
```

but leaving the old implementation too.

Now:

```text
userService
+
passwordService
```

both contain password logic.

That's dangerous.

You want one source of truth.

```text
UserService
      │
      └── PasswordService
```

or move the capability entirely to:

```text
PasswordService
```

and update callers.

---

# 23. Composition Helps Splitting

This connects directly to Lesson 12.15.

Suppose:

```text
UserService
```

is getting too large because of password logic.

You extract:

```text
PasswordService
```

Then:

```text
UserService
      │
      └── PasswordService
```

You didn't lose functionality.

You simply moved responsibility to a focused service.

That's the power of service composition.

---

# 24. Service Extraction Process

When a service becomes too large, use this process.

### Step 1 — Identify responsibilities

Write:

```text
UserService currently handles:

1. User CRUD
2. Password
3. Verification
4. Notifications
5. Admin actions
```

---

### Step 2 — Group related operations

```text
User
→ CRUD

Password
→ password operations

Verification
→ verification

Admin
→ moderation
```

---

### Step 3 — Find the strongest boundary

Maybe:

```text
PasswordService
VerificationService
```

---

### Step 4 — Move one responsibility

Don't refactor 1,000 lines at once.

Move:

```text
password logic
```

first.

---

### Step 5 — Update callers

```text
UserService
    ↓
PasswordService
```

---

### Step 6 — Test

Make sure:

```text
UserService tests
PasswordService tests
```

still pass.

Suppose:

```js
todo.service.js
```

imports:

```js

Activity
User
Notification
Email
Payment
File
Analytics

```

That's a warning sign.

Not automatically wrong.

But ask:

> Why does TodoService know about all of these?

Maybe you've created a giant service.

If you're using dependency injection and you have:

```js
createTodoService({
    todoRepository,
    userRepository,
    activityService,
    notificationService,
    emailService,
    paymentService,
    analyticsService,
    fileService,
    queueService,
    redisService,
    ...
})
```

that's a strong signal.

Maybe the service has too many responsibilities.

---

# 27. Another Smell: Huge Function

Suppose:

```js
completeTodo()
```

becomes:

```text
200 lines
```

and does:

```text
validate user
check permissions
update todo
create activity
calculate statistics
send email
send push notification
update analytics
write audit log
```

That's probably not a simple Todo operation anymore.

You may need:

```text
TodoService
+
ActivityService
+
NotificationService
+
AnalyticsService
```

and perhaps a workflow/orchestrator.

---

# 28. Another Smell: "If Statement Forest"

Example:

```js
if (user.isAdmin) {
    ...
}

if (user.isPremium) {
    ...
}

if (user.isEnterprise) {
    ...
}

if (todo.isArchived) {
    ...
}

if (notificationEnabled) {
    ...
}

if (paymentRequired) {
    ...
}
```

When business logic starts branching everywhere, it's worth asking whether responsibilities have become mixed.

---

# 29. Don't Split Based Only on File Length

A 500-line service isn't automatically bad.

A 100-line service isn't automatically good.

For example:

```text
500 lines
→ 15 highly related functions
```

could be fine.

While:

```text
100 lines
→ authentication + payments + emails
```

could be terrible.

Measure **responsibility**, not lines.

---

# 30. Cohesion > Line Count

Remember:

```text
Service quality
≠
number of lines
```

More useful:

```text
Service quality
≈
clear responsibility
+
high cohesion
+
low unnecessary coupling
+
testability
```

---

# 31. Coupling

We should also understand **coupling**.

Coupling means:

> How strongly one part of the system depends on another part.

For example:

```text
TodoService
    ↓
TodoRepository
```

This is expected coupling.

But:

```text
TodoService
 ↕
UserService
 ↕
PaymentService
 ↕
NotificationService
 ↕
TodoService
```

is excessive coupling.

---

# 32. High Cohesion + Low Coupling

This is one of the biggest design goals.

### High cohesion

Related things stay together.

```text
PasswordService
→ password-related operations
```

### Low coupling

Unrelated services don't depend heavily on one another.

```text
PasswordService
→ doesn't know about TodoService
```

So:

```text
GOOD ARCHITECTURE

High Cohesion
       +
Low Coupling
```

---

# 33. Example

Bad:

```text
UserService
├── user CRUD
├── todo creation
├── payment processing
├── email sending
└── analytics
```

Better:

```text
UserService
├── user operations

TodoService
├── todo operations

PaymentService
├── payment operations

NotificationService
├── notifications

AnalyticsService
├── analytics
```

And an appropriate workflow can coordinate them.

---

# 34. Don't Create Circular Architecture

After splitting, check:

```text
UserService → AuthService
AuthService → UserService
```

If both depend on each other, you may have simply moved the giant-service problem into multiple files.

The goal isn't:

```text
many files
```

The goal is:

```text
clear dependency direction
```

---

# 35. One-Way Dependency Example

Better:

```text
AuthWorkflow
     │
     ├── UserService
     ├── PasswordService
     └── TokenService
```

rather than:

```text
UserService ↔ AuthService
```

The workflow coordinates them.

---

# 36. Service Ownership

A very useful question is:

> **Who owns this business rule?**

Suppose:

```text
Password must contain 8 characters.
```

This belongs around:

```text
PasswordService / validation
```

Not:

```text
TodoService
```

Suppose:

```text
A completed Todo cannot be completed again.
```

That belongs around:

```text
Todo business logic
```

Not:

```text
PasswordService
```

Service boundaries become much easier when you think about ownership.

---

# 37. Business Rule Duplication

Suppose two services contain:

```js
if (todo.status === "done") {
    throw new AppError(
        "Todo already completed"
    );
}
```

You now have duplicated business rules.

Later one changes:

```text
"done" → "completed"
```

and one service gets updated but another doesn't.

That's dangerous.

Ask:

> **Which service owns this rule?**

Then centralize it.

# 40. The Refactoring Rule

When a service gets large, don't ask:

> "What functions can I move somewhere?"

Ask:

> **"What responsibility doesn't belong here?"**

That's a much stronger way to refactor.

---

# 41. Practical Decision Tree

When you see a large service:

```text
Is everything related?
        │
       YES
        │
   Keep together
        │
       NO
        ↓
What responsibilities exist?
        │
        ├── Password
        ├── Notification
        ├── Verification
        └── Core domain
```

Then:

```text
Does each responsibility have enough complexity?
        │
   ┌────┴────┐
  NO         YES
  │           │
Keep         Extract
together     service
```

That's a very practical rule.

# 🧠 Final Mental Model

Remember these **5 rules**:

```text
1. Split by responsibility, not by function count.

2. Keep related operations together.

3. Avoid services that know too many unrelated things.

4. Prefer high cohesion and low unnecessary coupling.

5. Refactor when complexity appears; don't over-engineer early.
```

And the most important one:

> **A service should be large enough to represent a meaningful business capability, but small enough that you can clearly explain what it owns.**
