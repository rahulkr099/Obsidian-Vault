# Lesson 12.17 — Service Naming Conventions

According to your Phase 12 roadmap, **12.17 is “Service naming conventions”**—not business rules. The source explicitly lists 12.17 that way, so we'll follow that structure.

This lesson looks simple, but good naming becomes very important when your backend grows.

---

## 1. Why Service Names Matter

Imagine opening a project and seeing:

```text
services/
├── service.js
├── helper.js
├── userStuff.js
├── logic.js
└── manager.js
```

You immediately have questions:

> What does `logic.js` do?

> Is `manager.js` a service?

> What does `userStuff.js` contain?

Good architecture should make the purpose obvious.

Compare that with:

```text
services/
├── auth.service.js
├── password.service.js
├── user.service.js
├── todo.service.js
└── notification.service.js
```

You can understand the architecture just by reading the filenames.

Your starter already follows this pattern with `auth.service.js` and `password.service.js`.

---

# 2. The Basic Convention

For your project, use:

```text
<responsibility>.service.js
```

Examples:

```text
auth.service.js
user.service.js
todo.service.js
password.service.js
notification.service.js
```

This gives us:

```text
auth
  +
service
  +
JavaScript
```

---

# 3. Why `.service.js`?

You could technically write:

```text
auth.js
user.js
todo.js
```

But:

```text
auth.service.js
```

immediately tells you:

> This file belongs to the service layer.

This becomes useful when your project contains:

```text
controllers/
services/
repositories/
models/
middlewares/
utils/
```

For example:

```text
auth.controller.js
auth.service.js
auth.repository.js
auth.validation.js
auth.routes.js
```

You can immediately see the layers.

---

# 4. Naming Should Describe Responsibility

Bad:

```text
common.service.js
misc.service.js
helper.service.js
logic.service.js
manager.service.js
```

These names don't tell you what the service owns.

Better:

```text
password.service.js
notification.service.js
payment.service.js
todo.service.js
```

The name should answer:

> **"What capability does this service handle?"**

---

# 5. `auth.service.js`

A reasonable authentication service:

```text
auth.service.js
```

could contain:

```js
register()
login()
logout()
refreshSession()
```

The name `auth` communicates the responsibility.

---

# 6. `password.service.js`

Your starter specifically has:

```text
password.service.js
```

A password service could contain:

```js
hashPassword()
comparePassword()
changePassword()
```

These operations are related to passwords.

So:

```text
password.service.js
```

is better than:

```text
security.service.js
```

if the file specifically handles password operations.

---

# 7. `user.service.js`

For users:

```text
user.service.js
```

could contain:

```js
getUserById()
getUserByEmail()
updateUser()
deleteUser()
```

The service owns user-related application operations.

---

# 8. `todo.service.js`

For your Todo feature:

```text
todo.service.js
```

could contain:

```js
createTodo()
getTodoById()
listTodos()
updateTodo()
deleteTodo()
completeTodo()
restoreTodo()
```

This is a good example of the principle from **12.16**:

> Don't split every CRUD operation into its own service.

Keep related Todo operations together.

---

# 9. Verb-Based Names vs Domain-Based Names

You might be tempted to create:

```text
createTodo.service.js
updateTodo.service.js
deleteTodo.service.js
```

Don't do this for your current architecture.

Prefer:

```text
todo.service.js
```

because the service represents the **Todo capability**, while its methods represent individual operations:

```text
todo.service.js
     │
     ├── createTodo()
     ├── updateTodo()
     ├── deleteTodo()
     └── completeTodo()
```

---

# 10. When a Verb-Based Service Can Make Sense

There are cases where a workflow itself is a meaningful capability.

For example:

```text
checkout.service.js
```

could contain:

```js
checkout()
```

because checkout is a meaningful business workflow.

Similarly:

```text
payment.service.js
```

could contain:

```js
capturePayment()
refundPayment()
getPaymentStatus()
```

The point isn't:

> Never use verbs.

The point is:

> **Name the service around the responsibility it owns.**

---

# 11. Service Names Should Match the Domain

Suppose your application has:

```text
courses
lessons
enrollments
payments
```

You could have:

```text
course.service.js
lesson.service.js
enrollment.service.js
payment.service.js
```

This is easy to understand.

Your application becomes almost self-documenting.

---

# 12. Avoid Generic "Manager"

A common naming mistake is:

```text
user.manager.js
todo.manager.js
application.manager.js
```

What does "manager" mean?

It could mean:

```text
CRUD
business logic
coordination
database access
caching
```

The name is vague.

Prefer:

```text
user.service.js
```

or, if it genuinely coordinates a workflow:

```text
checkout.service.js
```

---

# 13. Avoid Generic "Helper"

Don't create:

```text
service-helper.js
```

and put:

```js
createUser()
sendEmail()
generateToken()
calculatePrice()
```

inside it.

These operations don't share a meaningful responsibility.

Instead:

```text
user.service.js
email.service.js
token.service.js
pricing.service.js
```

if those boundaries are actually needed.

---

# 14. Singular or Plural?

For services, I recommend **singular domain names**:

```text
user.service.js
todo.service.js
payment.service.js
notification.service.js
```

rather than:

```text
users.service.js
todos.service.js
payments.service.js
notifications.service.js
```

Why?

Because you're naming the **domain capability**, not a collection.

Your repository convention can follow the same style:

```text
user.repository.js
todo.repository.js
```

Your starter already demonstrates the singular style with `user.repository.js`.

---

# 15. Match Controller and Service Names

This is extremely convenient.

Use:

```text
controllers/
└── todo.controller.js

services/
└── todo.service.js

repositories/
└── todo.repository.js

models/
└── todo.model.js

validations/
└── todo.validation.js

routes/
└── todo.routes.js
```

Now you have a consistent Todo module.

Think:

```text
todo
 │
 ├── route
 ├── controller
 ├── service
 ├── repository
 ├── model
 └── validation
```

This is much easier to navigate.

---

# 16. Naming Methods

Use clear verbs.

Good:

```js
createUser()
getUserById()
getUserByEmail()
updateUser()
deleteUser()
```

Bad:

```js
doUser()
processUser()
handleUser()
manageUser()
```

The good names tell you what the function does.

---

# 17. `get` vs `find`

Both can be valid, but consistency matters.

For example:

```js
getUserById()
getUserByEmail()
```

or:

```js
findUserById()
findUserByEmail()
```

Don't randomly mix:

```js
getUserById()
findUserByEmail()
fetchUser()
retrieveUser()
```

Pick a convention.

For your learning project, I'd recommend:

```text
get...
```

for service methods.

---

# 18. Service Method Names Should Describe the Business Operation

Compare:

```js
update()
```

with:

```js
updateUserProfile()
```

The second is more descriptive.

For Todo:

```js
completeTodo()
```

is better than:

```js
updateStatus()
```

because:

```text
completeTodo()
```

communicates the business operation.

This becomes especially important when business rules are involved.

---

# 19. CRUD Naming Convention

For a typical resource:

```js
createTodo()
getTodoById()
listTodos()
updateTodo()
deleteTodo()
```

This gives you a predictable pattern.

Think:

```text
CREATE → create
ONE    → get...ById
MANY   → list
UPDATE → update
DELETE → delete
```

---

# 20. Special Business Operations

Don't force everything into CRUD.

Suppose:

```text
Todo
```

can be completed.

Use:

```js
completeTodo()
```

instead of:

```js
updateTodo({
    status: "done"
})
```

Why?

Because completing a Todo may eventually involve:

```text
status change
completedAt
activity log
notification
statistics
```

So:

```text
completeTodo()
```

represents a meaningful business operation.

This connects directly to your earlier lessons on business operations and service composition.

---

# 21. Example: Order

Don't necessarily write:

```js
updateOrder({
    status: "paid"
});
```

if "paying an order" is a business operation.

Prefer something like:

```js
payOrder()
```

or:

```js
capturePayment()
```

depending on where payment responsibility belongs.

The method name should communicate the business meaning.

---

# 22. Example: User

Instead of:

```js
updateUser({
    verified: true
});
```

you might have:

```js
verifyUser()
```

if verification is a meaningful workflow.

Similarly:

```js
deactivateUser()
activateUser()
banUser()
unbanUser()
```

These are much clearer than generic:

```js
updateUser()
```

for every possible state transition.

---

# 23. Don't Put HTTP in Service Names

Avoid:

```js
getUserFromRequest()
sendUserResponse()
handleUserRequest()
processHttpUser()
```

Services aren't HTTP handlers.

Remember the architecture:

```text
Controller
   ↓
Service
```

The controller handles:

```text
req
res
HTTP status
HTTP headers
```

The service handles:

```text
business operation
```

Your source describes the controller as the HTTP translator and the service as the business-logic layer.

---

# 24. Don't Put Database Details in Service Names

Avoid:

```js
findUserFromMongo()
saveUserToMongo()
queryTodoCollection()
```

The service shouldn't care about the underlying database implementation.

Prefer:

```js
getUserById()
createTodo()
```

Then the repository handles:

```text
MongoDB
Mongoose
queries
```

This matches the intended architecture:

```text
Service
 ↓
Repository
 ↓
Model
 ↓
MongoDB
```

---

# 25. Naming the Service vs Naming Its Dependencies

Suppose:

```text
todo.service.js
```

uses:

```text
todo.repository.js
activity.service.js
notification.service.js
```

That's fine.

The Todo service is named after its **primary responsibility**, not every dependency.

```text
todo.service.js
    │
    ├── todo.repository
    ├── activity.service
    └── notification.service
```

---

# 26. Workflow Services

Sometimes you will have a workflow that crosses multiple domains.

For example:

```text
checkout.service.js
```

could coordinate:

```text
cart
inventory
payment
order
notification
```

That's a valid service name because **checkout** is itself a business capability.

So:

```text
services/
├── cart.service.js
├── inventory.service.js
├── payment.service.js
├── order.service.js
└── checkout.service.js
```

Here:

```text
checkout.service.js
```

may act as the orchestrator.

This connects directly with our previous lesson on service composition.

---

# 27. Don't Call Every Orchestrator "manager"

Instead of:

```text
order.manager.js
```

if it specifically coordinates order placement, use something meaningful:

```text
order-placement.service.js
```

or:

```text
checkout.service.js
```

depending on the actual business domain.

The name should tell another developer **why the service exists**.

---

# 28. File Names vs Function Names

Think about this distinction:

### File

```text
todo.service.js
```

answers:

> What responsibility does this module own?

### Function

```js
completeTodo()
```

answers:

> What operation does this module perform?

Together:

```text
todo.service.js
     │
     └── completeTodo()
```

This is a very clean mental model.

---

# 29. Consistency Is More Important Than the Exact Convention

There isn't one universal naming convention that every company uses.

For example, one team may use:

```text
user.service.js
```

Another:

```text
UserService.js
```

Another:

```text
userService.js
```

What matters is:

```text
consistent
predictable
understandable
```

For **your starter**, we'll use:

```text
lowercase
+
dot-separated role
+
.js
```

Example:

```text
auth.service.js
```

# 31. Feature-Based Structure Later

As your application grows, you may eventually prefer:

```text
modules/
└── user/
    ├── user.controller.js
    ├── user.service.js
    ├── user.repository.js
    ├── user.model.js
    ├── user.routes.js
    └── user.validation.js
```

Then:

```text
modules/
├── auth/
├── user/
├── todo/
└── notification/
```

This is a more scalable organization.

But **don't worry about restructuring your starter right now**.

First become comfortable with the layer-based structure.

---

# 32. A Naming Mistake to Avoid

Don't use the same name for unrelated responsibilities.

For example:

```text
services/user.service.js
services/user-manager.service.js
services/user-helper.service.js
```

Ask:

> Why are there three user services?

If the answer isn't immediately obvious, the architecture probably needs clarification.

---

# 33. Another Mistake: `business.service.js`

Avoid:

```text
business.service.js
```

This is almost meaningless.

Everything inside the service layer is related to business/application logic.

Instead:

```text
todo.service.js
payment.service.js
subscription.service.js
```

Tell the reader **which business capability**.

---

# 34. Naming and IDE Search

Good naming also makes your development workflow faster.

Suppose you want to find Todo business logic.

You can search:

```bash
find . -name '*todo.service.js'
```

Or in Vim:

```vim
:Telescope live_grep
```

and search:

```text
completeTodo
```

You'll quickly find:

```text
services/todo.service.js
```

Predictable naming saves time.

---

# 35. Naming and Git

Good names also make Git changes easier to understand.

Example commit:

```text
feat(todo): add completeTodo service
```

instead of:

```text
feat: update logic
```

You know exactly what changed.

---

# 36. Naming Checklist

Before creating:

```text
something.service.js
```

ask:

### 1. What does it own?

```text
Todo
Payment
Authentication
Password
```

### 2. Is the name specific?

```text
payment.service.js
```

rather than:

```text
manager.service.js
```

### 3. Is it consistent?

```text
todo.service.js
```

rather than:

```text
TodoService.js
```

if the rest of your project uses lowercase.

### 4. Does the name match the domain?

```text
password.service.js
```

for password functionality.

### 5. Would another developer understand it immediately?

If yes, the name is probably good.

# 37. Recommended Naming Table

|Layer|Convention|Example|
|---|---|---|
|Controller|`<domain>.controller.js`|`todo.controller.js`|
|Service|`<domain>.service.js`|`todo.service.js`|
|Repository|`<domain>.repository.js`|`todo.repository.js`|
|Model|`<domain>.model.js`|`todo.model.js`|
|Routes|`<domain>.routes.js`|`todo.routes.js`|
|Validation|`<domain>.validation.js`|`todo.validation.js`|
|Middleware|`<purpose>.middleware.js`|`auth.middleware.js`|
|Utility|`<purpose>.js`|`parseSort.js`|

Your starter architecture follows this general separation between controllers, services, repositories, models, routes, and validation.

├── manager.js
├── helper.js
├── auth.js

Try to rename them based on responsibility.

For example:

```text

    ↓
todo.service.js

manager.js
    ↓
payment.service.js

helper.js
    ↓
password.service.js

auth.js
    ↓
auth.service.js

userStuff.js
    ↓

```

But remember:

> **Don't rename based only on the filename. First inspect what the file actually does.**

# 🧠 What to Remember

The five rules I want you to remember from 12.17:

```text
1. Use <responsibility>.service.js

2. Name services after meaningful capabilities/domains.

3. Use clear verbs for service methods.

4. Don't use vague names like:
   manager
   helper
   logic
   misc

5. Keep naming consistent across the whole project.
```

Most importantly:

> **A good service name should tell you what the service owns without opening the file.**
