# 1. Mistake #1 — Putting HTTP Logic Inside a Service

This is probably the most common beginner mistake.

### ❌ Bad

```js
const login = async (req, res) => {
    const user = await User.findOne({
        email: req.body.email
    });

    if (!user) {
        return res.status(404).json({
            message: "User not found"
        });
    }

    return res.status(200).json({
        user
    });
};
```

This service knows about:

```text
req
res
HTTP status codes
JSON response
```

That's controller responsibility.

---

### ✅ Better

Controller:

```js
const login = asyncHandler(async (req, res) => {
    const result = await authService.login({
        email: req.body.email,
        password: req.body.password
    });

    res.status(200).json({
        success: true,
        data: result
    });
});
```

Service:

```js
const login = async ({ email, password }) => {
    // business logic
};
```

The architecture becomes:

```text
HTTP
 ↓
Controller
 ↓
Service
```

Your starter's architecture explicitly treats the controller as the **HTTP translator** and the service as the business-logic layer.

---

# 2. Mistake #2 — Returning `res.json()` From a Service

Never do this:

```js
const createTodo = async (...) => {
    const todo = await ...;

    return res.status(201).json({
        data: todo
    });
};
```

Why?

Because now your service depends on Express.

Tomorrow you might want to use that service from:

```text
REST API
CLI
background job
cron job
WebSocket
GraphQL
tests
```

But your service expects:

```text
res
```

That's unnecessary coupling.

---

### ✅ Better

```js
const createTodo = async (data) => {
    return todoRepository.create(data);
};
```

Controller:

```js
const todo = await todoService.createTodo(data);

res.status(201).json({
    success: true,
    data: todo
});
```

---

# 3. Mistake #3 — Direct MongoDB Queries Everywhere

Suppose your service contains:

```js
const getUser = async (userId) => {
    return User.findById(userId);
};
```

If your architecture uses the repository pattern, this bypasses the intended boundary.

Your roadmap specifically teaches:

```text
Service
 ↓
Repository
 ↓
Model
 ↓
MongoDB
```

as the data-access flow.

So prefer:

```js
const getUser = async (userId) => {
    return userRepository.findById(userId);
};
```

Then:

```js
// user.repository.js

const findById = (userId) => {
    return User.findById(userId);
};
```

The separation becomes:

```text
Service
→ "I need a user."

Repository
→ "I'll query MongoDB."
```

This is exactly the mental model your roadmap gives for Phase 13.

---

# 4. Mistake #4 — Putting Business Logic in the Repository

The opposite mistake also happens.

### ❌ Bad

```js
const completeTodo = async (todoId, userId) => {

    const todo = await Todo.findOne({
        _id: todoId,
        userId
    });

    if (todo.status === "completed") {
        throw new Error("Already completed");
    }

    todo.status = "completed";
    todo.completedAt = new Date();

    return todo.save();
};
```

The repository is now deciding:

```text
Can this Todo be completed?
What does "completed" mean?
What business rule applies?
```

That's service-level logic.

---

### Better

Repository:

```js
const findByIdForUser = (todoId, userId) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

Service:

```js
const completeTodo = async ({ todoId, userId }) => {

    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.status === "completed") {
        throw new AppError(
            "Todo is already completed",
            409
        );
    }

    todo.status = "completed";

    return todoRepository.save(todo);
};
```

Now:

```text
Repository
→ data access

Service
→ business decision
```

# 5. Mistake #5 — Putting Validation Everywhere

You might end up with:

```text
route validation
controller validation
service validation
repository validation
model validation
```

all checking the same thing.

That's messy.

You need to distinguish different types of validation.

---

## Input validation

Example:

```text
title must be a string
title must not be empty
email must be valid
```

This can happen at the request boundary.

```text
Request
 ↓
Validation middleware
```

Your roadmap specifically teaches validation as a separate layer before reaching services.

---

## Business validation

Example:

```text
A completed Todo cannot be completed again.
```

That's not merely input validation.

That's a **business rule**.

It belongs in the service/domain logic.

```text
Controller
 ↓
Service
   ↓
"Is this operation allowed?"
```

---

# 6. Mistake #6 — Trusting the Controller

A beginner might think:

```js
// controller

if (todo.status === "completed") {
    return res.status(409).json(...);
}

await todoService.completeTodo(...);
```

But then another caller can call the service directly and bypass the rule.

Instead:

```text
Controller
→ receives HTTP request

Service
→ protects business rules
```

The service should be the reliable boundary for the business operation.

---

# 7. Mistake #7 — Passing `req` Into Services

### ❌ Bad

```js
await todoService.createTodo(req);
```

Now the service needs to understand Express.

---

### ❌ Also bad

```js
await todoService.createTodo(
    req.body,
    req.user,
    req.params
);
```

This is better than passing `req`, but still not ideal if the service is receiving random HTTP-shaped data.

---

### ✅ Better

Create an explicit input:

```js
await todoService.createTodo({
    title: req.body.title,
    description: req.body.description,
    userId: req.user.id
});
```

Now the service receives exactly what it needs.

---

# 8. Mistake #8 — Passing `res` Into Services

Never:

```js
await todoService.createTodo(
    data,
    res
);
```

The service should return data or throw an error.

```text
Service
 ↓
return result
```

or:

```text
Service
 ↓
throw AppError
```

Then:

```text
Controller
 ↓
HTTP response
```

---

# 9. Mistake #9 — Catching Every Error Inside the Service

This is a very common pattern:

```js
const createTodo = async (data) => {
    try {
        return await todoRepository.create(data);
    } catch (error) {
        console.log(error);
        return null;
    }
};
```

This is dangerous.

Why?

Because you just swallowed the error.

The caller receives:

```js
null
```

instead of knowing:

```text
database failed
```

---

# 10. Let Unexpected Errors Propagate

Usually:

```js
const createTodo = async (data) => {
    return todoRepository.create(data);
};
```

If MongoDB fails:

```text
Repository
 ↓
throws
 ↓
Service doesn't swallow it
 ↓
Controller/asyncHandler
 ↓
Global error middleware
```

Your Phase 8 architecture is designed around this flow:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
      ↓
JSON response
```

---

# 11. When Should a Service Catch an Error?

Sometimes you **should** catch an error.

For example, when you want to translate a low-level error into a meaningful application error.

Example:

```js
try {
    return await userRepository.create(data);
} catch (error) {
    if (error.code === 11000) {
        throw new AppError(
            "Email already exists",
            409
        );
    }

    throw error;
}
```

Notice the important part:

```js
throw error;
```

Unknown errors are still allowed to propagate.

---

# 12. Mistake #10 — Returning `null` for Every Problem

Bad:

```js
const user = await userRepository.findById(id);

if (!user) {
    return null;
}
```

Maybe that's fine for a lower-level repository operation.

But the service should decide what that means.

For example:

```js
const user = await userRepository.findById(id);

if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

Now the business operation has a meaningful outcome.

---

# 13. Mistake #11 — Mixing Authentication and Authorization

These are different.

### Authentication

> Who are you?

```text
JWT
 ↓
user identity
```

### Authorization

> Are you allowed to do this?

```text
user
 ↓
permission
```

Don't create confusing service logic like:

```js
loginAndCheckAdminAndUpdateTodo()
```

Separate responsibilities.

For example:

```text
AuthService
→ authentication

Authorization logic
→ permissions/roles/ownership

TodoService
→ Todo business operations
```

---

# 14. Mistake #12 — Making Services Aware of Middleware

Don't do:

```js
todoService.completeTodo(
    req,
    authMiddleware
);
```

The service shouldn't know:

```text
auth.middleware.js
role.middleware.js
rateLimiter.middleware.js
```

Middleware protects the HTTP pipeline.

Services handle application behavior.

Your roadmap intentionally teaches these as separate architectural layers.

---

# 15. Mistake #13 — Making Services Call Controllers

This is backwards.

### ❌

```text
Service
 ↓
Controller
```

You should have:

```text
Controller
 ↓
Service
```

The controller is the outer layer.

The service is deeper inside the application.

Think:

```text
HTTP
 ↓
Application
 ↓
Data
```

not:

```text
Application
 ↓
HTTP
```

---

# 16. Mistake #14 — Circular Service Dependencies

Suppose:

```text
UserService
 ↓
AuthService
 ↓
UserService
```

That's a warning sign.

Or:

```text
TodoService
 ↓
ActivityService
 ↓
TodoService
```

You learned about this in **12.15 Service Composition**.

Possible solutions:

```text
Workflow/Orchestrator
```

or:

```text
Shared focused service
```

or simply:

```text
Redesign the responsibility boundary
```

Don't solve every circular dependency with clever import tricks.

Fix the architecture.

# 17. Mistake #15 — One Giant Service

You learned this in 12.16.

Bad:

```text
user.service.js

register
login
logout
password
email
payments
todos
notifications
admin
analytics
```

If everything lives here, you've created a **God Service**.

Instead:

```text
AuthService
PasswordService
UserService
NotificationService
PaymentService
TodoService
```

with appropriate composition.

---

# 18. Mistake #16 — Too Many Tiny Services

The opposite is also bad.

Don't do:

```text
create-user.service.js
get-user.service.js
update-user.service.js
delete-user.service.js
```

for a simple application.

Remember:

> **Split by responsibility, not by function.**

A cohesive:

```text
user.service.js
```

is perfectly fine.

---

# 19. Mistake #17 — Putting Utility Functions Into Services

Suppose you have:

```js
const capitalize = (value) => ...
```

and:

```js
const formatDate = (date) => ...
```

and:

```js
const generateSlug = (title) => ...
```

Don't automatically put all of them into:

```text
todo.service.js
```

Some generic reusable functions belong in:

```text
utils/
```

while domain-specific logic belongs in services.

For example:

```text
generateSlug()
```

could be a utility if it's generic.

But:

```text
calculateTodoCompletionScore()
```

might be domain logic.

---

# 20. Mistake #18 — Services Doing Presentation Formatting

Bad:

```js
return {
    message: "Todo created successfully",
    color: "green",
    buttonText: "View Todo",
    data: todo
};
```

This is presentation/UI thinking.

The service should return application data:

```js
return todo;
```

The controller/API layer decides the HTTP response format.

---

# 21. Mistake #19 — Returning Database Internals Blindly

Suppose your User document contains:

```js
{
    email,
    name,
    passwordHash,
    refreshTokenHash
}
```

Don't blindly return the entire document.

Bad:

```js
return user;
```

if that object eventually reaches the client.

Instead, deliberately select what the API should expose.

For example:

```js
return {
    id: user._id,
    email: user.email,
    name: user.name
};
```

Or use repository-level field selection where appropriate.

Your Phase 13 roadmap specifically includes **selecting fields** and **preventing password leakage**.

---

# 22. Mistake #20 — Business Logic in the Model Just Because Mongoose Allows It

Mongoose lets you define:

```js
schema.methods.someFunction = ...
```

That's useful in certain designs.

But don't automatically put all business workflows inside the model.

For example, don't make the User model responsible for:

```text
send email
create session
update audit log
charge payment
```

A model primarily represents:

```text
data structure
database behavior
```

while the service coordinates application-level business operations.

Your intended architecture keeps:

```text
Service
 ↓
Repository
 ↓
Model
```

separate.

---

# 23. Mistake #21 — Making the Service a Second Controller

Sometimes beginners remove `res` but still write HTTP-style logic:

```js
if (...) {
    return {
        status: 404,
        message: "Not found"
    };
}
```

Then the controller does:

```js
res.status(result.status).json(result);
```

Now your service is basically producing HTTP responses.

That's usually unnecessary.

Prefer:

```js
throw new AppError(
    "Todo not found",
    404
);
```

Then the controller/error middleware handles HTTP.

---

# 24. Mistake #22 — Inconsistent Service Return Values

Imagine:

```js
createTodo()
→ Todo object

updateTodo()
→ { success: true, todo }

deleteTodo()
→ "deleted"

completeTodo()
→ true
```

This becomes annoying.

Try to establish predictable contracts.

For example:

```text
create → created resource
get → resource
list → array + metadata
update → updated resource
delete → deleted resource / confirmation
```

The exact contract depends on your application, but consistency matters.

---

# 25. Mistake #23 — Services With Hidden Side Effects

Consider:

```js
const updateUser = async (data) => {

    const user = await userRepository.update(data);

    await emailService.send(...);

    await analyticsService.track(...);

    await notificationService.send(...);

    return user;
};
```

Calling:

```text
updateUser()
```

now secretly does four different things.

That isn't necessarily wrong, but you need to know the consequences.

Ask:

```text
What happens if email fails?
What happens if notification fails?
What happens if analytics fails?
Which operations are transactional?
```

This is exactly where service composition and transaction design become important.

---

# 26. Mistake #24 — Treating External Services Like MongoDB Transactions

Suppose:

```text
Update database
+
Send email
```

You cannot assume:

```text
MongoDB transaction
```

will roll back:

```text
email already sent
```

Your earlier transaction lesson matters here.

Think:

```text
Database state
→ transaction

External side effect
→ separate reliability strategy
```

Potentially:

```text
DB transaction
 ↓
commit
 ↓
queue job
 ↓
email worker
```

You don't need to implement queues yet. Just understand the boundary.

# 27. Mistake #25 — No Explicit Service Contract

A service should make it reasonably clear:

```text
Input
 ↓
Operation
 ↓
Output / Error
```

Example:

```js
const completeTodo = async ({
    todoId,
    userId
}) => {
    // ...
    return updatedTodo;
};
```

You can immediately understand:

### Input

```text
todoId
userId
```

### Output

```text
updatedTodo
```

### Failure

```text
AppError
```

That's a good service contract.

---

# 28. Mistake #26 — Passing Huge Objects

Avoid:

```js
await todoService.createTodo({
    req,
    user,
    session,
    response,
    config,
    application,
    database,
    ...
});
```

That's a sign the boundary isn't clear.

Prefer:

```js
await todoService.createTodo({
    title,
    description,
    userId
});
```

And if a transaction context is required:

```js
await todoService.createTodo({
    title,
    description,
    userId,
    session
});
```

Only pass what the service genuinely needs.

---

# 29. Mistake #27 — Services Knowing Too Much About the Database

Bad:

```js
const todo = await Todo.findOne({
    userId
}).sort({
    createdAt: -1
}).skip(
    (page - 1) * limit
).limit(limit);
```

Now the service knows all the MongoDB query mechanics.

With a repository:

```js
const todos = await todoRepository.findMany({
    userId,
    page,
    limit,
    sort
});
```

The service communicates **what it needs**, while the repository determines **how MongoDB should retrieve it**.

That's the separation your Phase 13 is designed to teach.

---

# 30. Mistake #28 — No Ownership Check

This is especially important for your Todo API.

### ❌ Dangerous

```js
const todo =
    await todoRepository.findById(todoId);
```

Then:

```js
todoService.updateTodo(todoId);
```

What if:

```text
Rahul
 ↓
requests User B's Todo
```

The service must ensure ownership/authorization is respected.

Better repository query:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Your roadmap explicitly highlights ownership queries and secure ownership architecture later.

---

# 31. Mistake #29 — Trusting `userId` From `req.body`

Never do:

```json
{
    "title": "My Todo",
    "userId": "someone-else"
}
```

and then:

```js
await todoService.createTodo(req.body);
```

For authenticated operations, identity should normally come from the authenticated context:

```js
await todoService.createTodo({
    title: req.body.title,
    userId: req.user.id
});
```

The client shouldn't decide:

> "I want this Todo to belong to user X."

The server decides the owner.

# 32. Mistake #30 — Testing Only Through the Controller

If your only test is:

```text
POST /todos
```

you aren't testing the service in isolation.

Your next lesson is **12.19 Testing Services**, and this is why we separated the service layer.

You should eventually be able to test:

```text
TodoService
    ↓
Fake TodoRepository
```

without needing:

```text
Express
HTTP
MongoDB
```

That is one of the biggest benefits of a clean service boundary.

# 34. A Good Service Example

Let's put everything together.

```js
const completeTodo = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.status === "completed") {
        throw new AppError(
            "Todo is already completed",
            409
        );
    }

    const updatedTodo =
        await todoRepository.markCompleted(
            todoId
        );

    await activityService.record({
        userId,
        action: "TODO_COMPLETED",
        resourceId: todoId
    });

    return updatedTodo;
};
```

Notice what it **doesn't** contain:

```text
❌ req
❌ res
❌ res.json()
❌ MongoDB query syntax
❌ HTTP response formatting
❌ Express middleware
```

It contains:

```text
✅ business operation
✅ business rules
✅ service composition
✅ repository calls
✅ application errors
```

That's what we want.

# 35. Service Layer Checklist

Before you finish a service, ask:

```text
[ ] Does it know about Express req/res?
[ ] Does it send HTTP responses?
[ ] Does it contain direct MongoDB queries?
[ ] Does it contain business rules?
[ ] Does it call the correct repository?
[ ] Does it have clear inputs?
[ ] Does it have clear outputs?
[ ] Does it throw meaningful errors?
[ ] Does it swallow unexpected errors?
[ ] Does it have too many dependencies?
[ ] Does it have circular dependencies?
[ ] Does it expose sensitive data?
[ ] Does it enforce ownership where needed?
[ ] Is it too large?
[ ] Is it unnecessarily split?
[ ] Can I unit-test it independently?
```

If most answers look good, your service is probably in a healthy state.

# 🧠 The 10 Rules I Want You to Remember

If you forget everything else from 12.18, remember these:

```text
1. Services should not know about req/res.

2. Services should not send HTTP responses.

3. Services should not bypass the repository layer
   when your architecture uses repositories.

4. Business rules belong in the service/application layer.

5. Don't swallow unexpected errors.

6. Don't create circular service dependencies.

7. Don't create giant services.

8. Don't create hundreds of tiny services.

9. Don't trust client-controlled ownership information.

10. Design services so they can be tested independently.
```

The overall target remains:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

Your starter/roadmap intentionally builds these layers separately so that, by the time you reach the repository and authentication phases, each layer has a clear job.
