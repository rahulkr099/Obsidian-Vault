# Lesson 12.19 — Testing Services

Your Phase 12 roadmap defines **12.19 as “Testing services”**, immediately before the final lesson, **12.20 Build a complete service layer**.

The main goal today is to understand:

> **How can we test business logic without starting Express, sending HTTP requests, or connecting to MongoDB?**

That's where service testing becomes powerful.

---

# 1. Why Test a Service Separately?

Suppose we have:

```text
POST /api/v1/todos/:id/complete
```

A full request might travel through:

```text
HTTP request
    ↓
Route
    ↓
Middleware
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
MongoDB
```

If the test fails, you have many possible causes.

Maybe:

```text
route is wrong
middleware is wrong
controller is wrong
service is wrong
repository is wrong
database is wrong
```

That's not ideal when you're trying to test **business logic**.

Instead, we can test:

```text
TodoService
     ↓
Fake Repository
```

Now if the test fails, we know the problem is probably in the service.

This is one reason your roadmap separates **unit testing** from later integration testing.

---

# 2. What Are We Actually Testing?

Consider this service:

```js
const completeTodo = async ({ todoId, userId }) => {
    const todo = await todoRepository.findByIdForUser(
        todoId,
        userId
    );

    if (!todo) {
        throw new AppError("Todo not found", 404);
    }

    if (todo.status === "completed") {
        throw new AppError(
            "Todo is already completed",
            409
        );
    }

    return todoRepository.markCompleted(todoId);
};
```

There are several things we want to test.

### Case 1

Todo exists and is pending:

```text
→ Todo gets completed
```

### Case 2

Todo doesn't exist:

```text
→ 404 error
```

### Case 3

Todo is already completed:

```text
→ 409 error
```

### Case 4

Repository fails:

```text
→ error propagates
```

Notice something important:

We don't need MongoDB to test these rules.

---

# 3. Service Testing Means Testing Behavior

Don't think:

> "I need to test every line."

Think:

> **"I need to prove that the service behaves correctly."**

For example:

```text
Input
 ↓
Service
 ↓
Expected behavior
```

A good test might say:

```text
Given a pending Todo,
when completeTodo() is called,
the repository should mark it completed.
```

That's much more meaningful than:

> "Line 18 executed."

---

# 4. The Service's Dependencies Are the Key

Remember the architecture:

```text
Service
   ↓
Repository
```

Our service depends on:

```js
todoRepository
```

But when testing the service, we don't necessarily want the real repository.

Instead:

```text
Real world

TodoService
    ↓
TodoRepository
    ↓
MongoDB
```

Testing:

```text
Test

TodoService
    ↓
Fake TodoRepository
```

This is called **mocking/stubbing a dependency**.

Your broader testing roadmap explicitly includes mocking as a separate concept.

---

# 5. Why Not Use the Real Database?

You could.

But then you're no longer doing a pure service unit test.

Imagine:

```text
test
 ↓
MongoDB
 ↓
insert Todo
 ↓
run service
 ↓
update Todo
 ↓
clean database
```

Now the test can fail because:

```text
MongoDB isn't running
database connection failed
test data wasn't cleaned
network problem
database state is wrong
```

For unit testing the service, that's unnecessary.

We want:

```text
Service
+
controlled dependency
```

# 6. A Simple Service

Let's create:

```js
// todo.service.js

const createTodo = async ({
    title,
    userId
}) => {

    return todoRepository.create({
        title,
        userId
    });
};

module.exports = {
    createTodo
};
```

The service depends on:

```text
todoRepository
```

Our test can provide a fake version.

# 7. Think About the Test Like This

Suppose:

```js
todoRepository.create()
```

returns:

```js
{
    id: "123",
    title: "Learn testing",
    userId: "user1"
}
```

We want to prove:

```text
createTodo()
 ↓
calls repository
 ↓
with correct data
 ↓
returns repository result
```

That's the service contract.

# 8. Jest Basics

Your roadmap later introduces **Jest fundamentals** as part of backend testing.

A basic Jest test looks like:

```js
describe("todoService", () => {

    test("creates a todo", async () => {

        // test

    });

});
```

Think of:

```js
describe()
```

as:

> "These tests belong to this thing."

And:

```js
test()
```

as:

> "This is one specific behavior I want to verify."

---

# 9. `expect()`

Jest uses:

```js
expect()
```

to express what you expect.

Example:

```js
expect(result.title).toBe("Learn testing");
```

Meaning:

> I expect `result.title` to equal `"Learn testing"`.

Another example:

```js
expect(result).toEqual(expectedTodo);
```

---

# 10. First Service Test

Suppose:

```js
const todoRepository = {
    create: jest.fn()
};
```

We tell our fake repository:

```js
todoRepository.create.mockResolvedValue({
    id: "123",
    title: "Learn testing",
    userId: "user1"
});
```

Then:

```js
const result = await todoService.createTodo({
    title: "Learn testing",
    userId: "user1"
});
```

Now we can test:

```js
expect(result).toEqual({
    id: "123",
    title: "Learn testing",
    userId: "user1"
});
```

---

# 11. Testing That the Repository Was Called

We also want to make sure the service called the repository correctly.

```js
expect(todoRepository.create).toHaveBeenCalledWith({
    title: "Learn testing",
    userId: "user1"
});
```

This is extremely useful.

We're testing:

```text
Service
 ↓
Did it call the correct dependency?
```

---

# 12. What Is `jest.fn()`?

This:

```js
jest.fn()
```

creates a mock function.

For example:

```js
const repository = {
    create: jest.fn()
};
```

Now:

```js
repository.create()
```

isn't a real database function.

It's a controlled test function.

We can inspect:

```js
repository.create.mock.calls
```

to see how it was called.

---

# 13. `mockResolvedValue()`

Services often use:

```js
await repository.create()
```

So our fake function needs to behave asynchronously.

Use:

```js
repository.create.mockResolvedValue(todo);
```

This means approximately:

```js
repository.create()
```

will behave like:

```js
Promise.resolve(todo)
```

So:

```js
const result =
    await repository.create();
```

works normally.

---

# 14. Testing the "Not Found" Rule

Now consider:

```js
const completeTodo = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todoRepository.markCompleted(todoId);
};
```

We can configure:

```js
todoRepository.findByIdForUser
    .mockResolvedValue(null);
```

Then:

```js
await expect(
    todoService.completeTodo({
        todoId: "123",
        userId: "user1"
    })
).rejects.toThrow("Todo not found");
```

We're testing an important business rule.

---

# 15. Testing Error Status

If `AppError` contains a status code:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);
        this.statusCode = statusCode;
    }
}
```

we can do:

```js
try {
    await todoService.completeTodo({
        todoId: "123",
        userId: "user1"
    });

    throw new Error("Expected error");
} catch (error) {
    expect(error.statusCode).toBe(404);
}
```

Now we're testing:

```text
Missing Todo
 ↓
AppError
 ↓
404
```

---

# 16. Testing Business Rules

This is where service tests become especially valuable.

Suppose:

```js
if (todo.status === "completed") {
    throw new AppError(
        "Todo is already completed",
        409
    );
}
```

Test it:

```js
todoRepository.findByIdForUser
    .mockResolvedValue({
        id: "123",
        status: "completed"
    });
```

Then:

```js
await expect(
    todoService.completeTodo({
        todoId: "123",
        userId: "user1"
    })
).rejects.toThrow(
    "Todo is already completed"
);
```

Now your test proves the business rule exists.

---

# 17. Testing the Happy Path

We also need the successful case.

Fake repository:

```js
todoRepository.findByIdForUser
    .mockResolvedValue({
        id: "123",
        status: "pending"
    });

todoRepository.markCompleted
    .mockResolvedValue({
        id: "123",
        status: "completed"
    });
```

Call:

```js
const result =
    await todoService.completeTodo({
        todoId: "123",
        userId: "user1"
    });
```

Then:

```js
expect(result.status).toBe("completed");
```

And:

```js
expect(
    todoRepository.markCompleted
).toHaveBeenCalledWith("123");
```

---

# 18. The Three Most Important Service Tests

For most service methods, start thinking in three categories:

```text
1. Happy path
2. Business-rule failure
3. Dependency failure
```

For example:

```text
completeTodo()

1. pending Todo
   → succeeds

2. already completed
   → 409

3. repository/database failure
   → error propagates
```

That's an excellent starting point.

---

# 19. Testing Dependency Failure

Suppose:

```js
todoRepository.findByIdForUser
    .mockRejectedValue(
        new Error("Database unavailable")
    );
```

Then:

```js
await expect(
    todoService.completeTodo({
        todoId: "123",
        userId: "user1"
    })
).rejects.toThrow(
    "Database unavailable"
);
```

This confirms that the service doesn't silently swallow unexpected failures.

That connects directly to the mistake we discussed in **12.18**.

---

# 20. Resetting Mocks

Imagine we have several tests:

```text
test 1
test 2
test 3
```

The mock could remember calls from previous tests.

So we generally reset mocks between tests.

For example:

```js
beforeEach(() => {
    jest.clearAllMocks();
});
```

This keeps each test independent.

---

# 21. Test Isolation

Suppose test A creates:

```text
Todo A
```

and test B expects no Todo.

If test B depends on test A, your tests aren't isolated.

Good:

```text
Test A
  ↓
clean state

Test B
  ↓
clean state

Test C
  ↓
clean state
```

This principle becomes even more important later when you test repositories and databases. Your broader roadmap explicitly includes **test isolation**.

---

# 22. Don't Test the Repository Again

Suppose your service test contains:

```js
expect(
    todoRepository.create
).toHaveBeenCalledWith(...);
```

Good.

But don't test MongoDB behavior here:

```js
expect(
    MongoDB.collection("todos")
        .insertOne(...)
).toHaveBeenCalled();
```

That's repository testing.

Keep the layers separate.

---

# 23. Service Test vs Repository Test

This distinction is important.

### Service test

Asks:

> Did the application make the correct business decision?

```text
TodoService
 ↓
Fake Repository
```

### Repository test

Asks:

> Did we correctly interact with MongoDB?

```text
TodoRepository
 ↓
Test Database
```

Your roadmap explicitly separates **testing services** and **testing repositories**.

---

# 24. Service Test vs Controller Test

Similarly:

### Service

```text
business behavior
```

### Controller

```text
HTTP behavior
```

A service test shouldn't care about:

```js
res.status(201)
```

A controller test should.

This separation keeps tests focused.

---

# 25. Don't Test Implementation Details Too Much

Imagine:

```js
const createTodo = async (data) => {
    const normalizedTitle =
        data.title.trim();

    return todoRepository.create({
        ...data,
        title: normalizedTitle
    });
};
```

Don't write a test that depends on every internal variable.

Prefer testing behavior:

```text
Given title "  Learn Testing  "
→ repository receives "Learn Testing"
```

The test should protect useful behavior, not make refactoring painful.

# 27. A Complete Small Example

Let's imagine:

### `todo.service.js`

```js
const createTodo = async ({
    title,
    userId
}) => {

    if (!title.trim()) {
        throw new AppError(
            "Title is required",
            400
        );
    }

    return todoRepository.create({
        title: title.trim(),
        userId
    });
};
```

Now test it.

### Test 1 — Success

```js
todoRepository.create.mockResolvedValue({
    id: "1",
    title: "Learn Jest",
    userId: "user1"
});

const result =
    await todoService.createTodo({
        title: " Learn Jest ",
        userId: "user1"
    });

expect(result.title).toBe("Learn Jest");
```

And:

```js
expect(
    todoRepository.create
).toHaveBeenCalledWith({
    title: "Learn Jest",
    userId: "user1"
});
```

---

### Test 2 — Empty title

```js
await expect(
    todoService.createTodo({
        title: "   ",
        userId: "user1"
    })
).rejects.toThrow(
    "Title is required"
);
```

Notice:

**The repository isn't even called.**

We can verify:

```js
expect(
    todoRepository.create
).not.toHaveBeenCalled();
```

That's useful because the service should reject invalid business input before data access.

# 28. What Should You Test in Every Service?

Use this checklist:

```text
Input
 ↓
Does the service accept valid input?

Business rules
 ↓
Are the rules enforced?

Dependencies
 ↓
Are repositories/services called correctly?

Output
 ↓
Does the service return the expected result?

Errors
 ↓
Are expected errors translated correctly?

Unexpected failures
 ↓
Are unknown errors propagated?

Side effects
 ↓
Are required secondary services called?
```

# 33. Unit Tests vs Integration Tests

This distinction is critical.

### Unit

```text
TodoService
    ↓
Mock Repository
```

Fast.

Focused.

No real database.

### Integration

```text
HTTP
 ↓
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Test Database
```

Slower.

Tests that multiple components work together.

Your roadmap deliberately introduces unit testing and integration testing as separate concepts.

# 34. A Good Mental Model

Whenever you're testing a service, imagine:

```text
                 SERVICE TEST
                     │
         ┌───────────┴───────────┐
         │                       │
         ▼                       ▼
      INPUT                  MOCK DEPENDENCY
         │                       │
         └───────────┬───────────┘
                     ▼
                  SERVICE
                     │
                     ▼
                  OUTPUT
                     │
                     ▼
                  ASSERT
```

You're controlling the world around the service.

That's why service tests can be very fast.

---

# 35. One Important Rule

**Don't mock everything blindly.**

If your service uses:

```text
TodoRepository
PasswordService
NotificationService
```

you may mock these dependencies when you're testing the service's own behavior.

But don't turn your tests into:

```text
mock
mock
mock
mock
mock
```

with no meaningful behavior.

The purpose is:

> **Control dependencies so you can verify the service's behavior.**

Not:

> "Mock every function because that's what unit tests do."

    ↓

    ↓

    ↓

# 🧠 12.19 Summary

Remember these:

```text
1. A service should be testable independently.

2. Service unit tests focus on business behavior.

3. Mock repositories and other dependencies when appropriate.

4. Test happy paths.

5. Test business-rule failures.

6. Test dependency failures.

7. Verify dependencies were called correctly.

8. Keep tests isolated.

9. Don't test MongoDB behavior inside service tests.

10. Don't test HTTP behavior inside service tests.
```

The architecture you're building is now becoming very powerful:

```text
             HTTP
              ↓
           Controller
              ↓
            Service
              ↓
          Repository
              ↓
            Model
              ↓
           MongoDB
```

And the testing strategy mirrors it:

```text
Service Test
     ↓
Mock Repository

Repository Test
     ↓
Test Database

Controller Test
     ↓
Mock Service

Integration Test
     ↓
Entire request flow
```

That's exactly why we spent the previous lessons learning **service boundaries, dependencies, inputs/outputs, error handling, composition, and common mistakes** before testing them.
