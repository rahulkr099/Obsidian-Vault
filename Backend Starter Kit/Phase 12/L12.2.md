# Lesson 12.2 — Why Controllers Shouldn't Contain Business Logic

In Lesson 12.1, we learned:

> **Controller handles HTTP. Service handles business/application logic.**

Now let's understand **why we separate them**.

This is not just about having a cleaner folder structure. It solves real problems that appear when your application becomes larger.

---

# 1. What Is a "Fat Controller"?

A **fat controller** is a controller that tries to do everything.

For example:

```js
const createOrder = async (req, res) => {
    const { productId, quantity } = req.body;

    // validation
    if (!productId) {
        return res.status(400).json({
            message: "Product ID is required"
        });
    }

    if (quantity <= 0) {
        return res.status(400).json({
            message: "Quantity must be greater than 0"
        });
    }

    // database query
    const product = await Product.findById(productId);

    if (!product) {
        return res.status(404).json({
            message: "Product not found"
        });
    }

    // business rule
    if (product.stock < quantity) {
        return res.status(400).json({
            message: "Not enough stock"
        });
    }

    // business calculation
    let total = product.price * quantity;

    if (req.user.isPremium) {
        total = total * 0.9;
    }

    // database operation
    const order = await Order.create({
        userId: req.user.id,
        productId,
        quantity,
        total,
        status: "PENDING"
    });

    // HTTP response
    return res.status(201).json({
        success: true,
        data: order
    });
};
```

This may work.

But look at what this one function is doing:

```text
Controller
│
├── Reads request
├── Validates data
├── Queries database
├── Checks product
├── Checks stock
├── Calculates price
├── Applies discount
├── Creates order
└── Sends HTTP response
```

That's a lot.

---

# 2. Why Is This a Problem?

At first:

```text
100 lines
```

doesn't feel terrible.

But imagine your application grows.

You eventually have:

```text
Orders
Payments
Users
Products
Subscriptions
Notifications
Reviews
Coupons
Shipping
```

Now controllers start becoming:

```text
500 lines
700 lines
1000 lines
```

And worse:

> The same business rules start getting copied into different controllers.

That's where problems begin.

---

# 3. Problem #1 — Controllers Become Difficult to Read

Imagine this:

```js
const createOrder = async (req, res) => {

    // 15 lines validation

    // 20 lines product logic

    // 30 lines pricing logic

    // 25 lines inventory logic

    // 15 lines payment logic

    // 20 lines database operations

    // 10 lines response
};
```

When you open the file, you can't quickly answer:

> **What does this endpoint do?**

The actual HTTP operation is hidden inside hundreds of lines.

A thin controller makes the intention obvious:

```js
const createOrder = asyncHandler(async (req, res) => {

    const order = await orderService.createOrder({
        userId: req.user.id,
        productId: req.body.productId,
        quantity: req.body.quantity
    });

    res.status(201).json({
        success: true,
        data: order
    });
});
```

Now you immediately understand:

```text
Receive request
      ↓
Ask service to create order
      ↓
Return response
```

Much easier.

---

# 4. Problem #2 — Business Logic Gets Repeated

This is one of the biggest problems.

Suppose you have:

```text
POST /orders
```

and:

```text
POST /admin/orders
```

Both need to calculate the order price.

Without a service, you might write:

```js
// order.controller.js

const total = product.price * quantity;

if (req.user.isPremium) {
    total *= 0.9;
}
```

And somewhere else:

```js
// adminOrder.controller.js

const total = product.price * quantity;

if (user.isPremium) {
    total *= 0.9;
}
```

Now you have duplicated business logic.

```text
Controller A
    ↓
Price calculation

Controller B
    ↓
Same price calculation
```

What happens if the discount changes from:

```text
10%
```

to:

```text
15%
```

You have to remember every location where the calculation exists.

That's dangerous.

---

# 5. The Service Solves This

Create:

```text
order.service.js
```

Then:

```js
const calculateOrderTotal = (product, quantity, user) => {

    let total = product.price * quantity;

    if (user.isPremium) {
        total *= 0.9;
    }

    return total;
};
```

Now both controllers can use the same application logic through the service.

```text
Controller A
       │
       ├──────┐
       │      │
       ▼      ▼
       Order Service
       │
       ▼
 calculateOrderTotal()
```

One rule.

One place.

Much safer.

---

# 6. Problem #3 — Controllers Become Hard to Test

Suppose you want to test:

> Premium users receive a 10% discount.

If the calculation is buried inside an Express controller, your test may need to construct:

```text
req
res
user
body
database
Express behavior
```

just to test a simple calculation.

That's unnecessary complexity.

Instead, the service can contain:

```js
const calculateOrderTotal = (...) => {
    // business logic
};
```

Then you can test the logic independently.

```text
Test
 ↓
Service
 ↓
Business rule
```

No HTTP required.

---

# 7. Problem #4 — Business Logic Becomes Coupled to Express

This is an important architectural problem.

Imagine this:

```js
const createOrder = async (req, res) => {
    // business logic
};
```

The logic depends on:

```text
req
res
Express
HTTP
```

Now imagine six months later you want to run the same order process from:

```text
REST API
Admin dashboard
Background job
CLI
Scheduled task
```

You don't want every one of those systems to pretend to be an Express request.

Instead:

```js
orderService.createOrder({
    userId,
    productId,
    quantity
});
```

Now the service doesn't care where the request came from.

---

# 8. Think About Your Future AI Backend

This is especially useful for the kind of backend architecture you're building.

Imagine later you have:

```text
React frontend
      │
      ▼
REST API
      │
      ▼
Order Service
```

But also:

```text
AI Agent
      │
      ▼
Order Service
```

And:

```text
Background Worker
      │
      ▼
Order Service
```

You want:

```text
REST API ────────┐
                 │
AI Agent ────────┼──→ Order Service
                 │
Worker ──────────┘
```

rather than:

```text
REST API
   ↓
Express Controller
   ↓
Business Logic
```

The service layer creates a reusable application core.

---

# 9. Problem #5 — Controllers Mix Different Types of Logic

Consider this:

```js
const createOrder = async (req, res) => {

    const { productId, quantity } = req.body;

    // HTTP
    ...

    // validation
    ...

    // database
    ...

    // business rules
    ...

    // calculations
    ...

    // response
    ...
};
```

There are several different responsibilities.

A cleaner architecture separates them.

```text
Request
   ↓
Middleware
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Each layer has a smaller responsibility.

---

# 10. Let's Refactor the Fat Controller

Let's take our previous example and improve it.

### Step 1 — Controller

```js
const createOrder = asyncHandler(async (req, res) => {

    const order = await orderService.createOrder({
        userId: req.user.id,
        productId: req.body.productId,
        quantity: req.body.quantity
    });

    res.status(201).json({
        success: true,
        data: order
    });
});
```

The controller now handles:

```text
HTTP input
    ↓
service call
    ↓
HTTP response
```

That's it.

---

# 11. Step 2 — Move Business Logic to Service

Now:

```js
const createOrder = async ({
    userId,
    productId,
    quantity
}) => {

    const product = await Product.findById(productId);

    if (!product) {
        throw new AppError(
            "Product not found",
            404
        );
    }

    if (product.stock < quantity) {
        throw new AppError(
            "Not enough stock",
            400
        );
    }

    let total = product.price * quantity;

    if (user.isPremium) {
        total *= 0.9;
    }

    const order = await Order.create({
        userId,
        productId,
        quantity,
        total,
        status: "PENDING"
    });

    return order;
};
```

Now the service is responsible for:

```text
Product exists?
Stock available?
Calculate price
Apply discount
Create order
```

Those are application decisions.

---

# 12. But There's Still Something Wrong

You might notice:

```js
Product.findById()
```

and:

```js
Order.create()
```

are still inside the service.

That's okay **for now**.

Why?

Because we're learning the layers gradually.

In **Phase 13**, we'll introduce:

```text
Repository
```

Then this:

```js
Product.findById(...)
```

will eventually move toward:

```js
productRepository.findById(...)
```

and:

```js
Order.create(...)
```

will eventually become something like:

```js
orderRepository.create(...)
```

So our final architecture will be:

```text
Controller
      ↓
Service
      ↓
Repository
      ↓
Model
      ↓
MongoDB
```

Don't try to solve Phase 13 today.

---

# 13. What Should Stay in the Controller?

A controller commonly handles:

### Request data

```js
req.body
req.params
req.query
req.user
```

### Calling the service

```js
orderService.createOrder(...)
```

### HTTP status

```js
res.status(201)
```

### HTTP response

```js
res.json(...)
```

### Sometimes HTTP-specific headers/cookies

For example:

```js
res.cookie(...)
```

That's controller territory.

---

# 14. What Should Move to the Service?

Business/application decisions such as:

```text
Does this operation make sense?
Is this user allowed according to business rules?
Should a discount apply?
Can this state change happen?
What records need to be created?
What workflow should happen?
What calculations are required?
Which business operation should happen next?
```

For example:

```js
if (order.status !== "PENDING") {
    throw new AppError(
        "Only pending orders can be cancelled",
        400
    );
}
```

That's a business rule.

---

# 15. What Should NOT Be in a Service?

Avoid this:

```js
const createOrder = async (req, res) => {
```

A service shouldn't normally receive Express objects.

Avoid:

```js
res.status(400).json(...)
```

The service shouldn't construct HTTP responses.

Avoid:

```js
req.cookies.refreshToken
```

The service shouldn't know how Express stores cookies.

Instead:

```js
orderService.createOrder({
    userId,
    productId,
    quantity
});
```

The service receives the **information it needs**, not the entire HTTP request.

---

# 16. The "HTTP Boundary" Concept

This is a very useful concept.

Think of your controller as the boundary between:

```text
Internet / HTTP
        │
        │
        ▼
┌───────────────────────┐
│      Controller       │
└───────────────────────┘
        │
        │ clean application data
        ▼
┌───────────────────────┐
│       Service         │
└───────────────────────┘
```

The controller should transform:

```js
req.body
```

into something meaningful:

```js
{
    userId,
    productId,
    quantity
}
```

Then pass that into the service.

---

# 17. A Great Mental Model

Imagine the controller says:

> "The HTTP client wants to create an order for product X with quantity 3."

The service says:

> "Okay. I'll determine whether that operation is allowed and what needs to happen."

The repository says:

> "I'll handle retrieving and saving the data."

The database says:

> "I'll store it."

So:

```text
Controller
"What was requested?"

Service
"What should happen?"

Repository
"How do I access the data?"

Database
"Where is the data?"
```

This is one of the most useful mental models for your backend journey.

---

# 18. What About Validation?

You might ask:

> "Didn't we just put validation into middleware?"

Yes.

There are actually different kinds of validation/rules.

### Input validation

```text
Is email actually an email?
Is quantity a number?
Is title too long?
```

Usually handled by:

```text
Validation layer
```

### Business validation

```text
Does this product have enough stock?
Can this order be cancelled?
Can this user perform this operation?
```

Usually belongs in:

```text
Service
```

That's an important distinction.

---

# 19. Input Validation vs Business Rules

Example:

```text
quantity = -5
```

This is invalid input.

```text
quantity = 5
but stock = 2
```

The input is valid.

But the **business operation is not allowed**.

Therefore:

```text
quantity = -5
       ↓
Validation

quantity = 5
stock = 2
       ↓
Service/business rule
```

This distinction will become very useful as your architecture grows.

# 20. What Happens When a Service Becomes Huge?

We'll cover this more deeply later, but consider:

```text
auth.service.js
```

If it becomes:

```text
1500 lines
```

we have another problem.

A service shouldn't become a dumping ground.

Instead, we can separate responsibilities:

```text
services/
├── auth.service.js
├── password.service.js
├── token.service.js
└── email.service.js
```

Your starter already follows this general idea by separating authentication and password-related operations.

We'll learn how to decide when to split services in **12.16**.

---

# 21. One Important Principle: Single Responsibility

A controller should have a relatively narrow responsibility:

> Handle the HTTP operation.

A service should have a relatively narrow responsibility:

> Handle a related application/business operation.

For example:

```text
user.service.js
```

could handle:

```text
createUser
getUser
updateUser
deleteUser
```

while:

```text
password.service.js
```

could handle:

```text
changePassword
createResetToken
resetPassword
```

The exact organization depends on the application.

Let's practice.

Suppose you have:

```text
POST /api/v1/users/:id/change-password
```

The operation does this:

```text
1. Read user ID from URL
2. Read old password from request
3. Read new password
4. Verify old password
5. Check new password isn't same as old password
6. Hash new password
7. Save new password
8. Clear refresh tokens
9. Return HTTP 200
```

Classify them.

### Controller

Which operations belong here?

### Service

Which operations belong here?

### Repository

Which operations will eventually belong here?

### Validation

Which operations belong here?

Take a minute and classify them before looking at the answer.

---

## ✅ Suggested answer

```text
Controller
──────────
1. Read user ID from URL
2. Read request data
3. Return HTTP 200


Validation
──────────
Validate new password format
Validate required fields


Service
───────
4. Verify old password
5. Check new password isn't same
6. Hash new password
7. Clear refresh tokens
```

And eventually:

```text
Repository
──────────
7. Save new password
8. Update/clear refresh token data
```

Notice that **one business operation can use multiple repositories**.

For example:

```text
Password Service
       │
       ├── User Repository
       │
       └── Token Repository
```

That's perfectly normal.

Memorize this:

```text
                    REQUEST
                       │
                       ▼
                 CONTROLLER
                       │
              "What was requested?"
                       │
                       ▼
                   SERVICE
                       │
              "What should happen?"
                       │
                       ▼
                REPOSITORY
                       │
              "How do I get/save it?"
                       │
                       ▼
                    MODEL
                       │

                   DATABASE
```

And one golden rule:

> **Don't make the controller smart. Make the application architecture smart.**

A thin controller is not about writing fewer lines for the sake of fewer lines. It's about keeping **HTTP concerns separate from business decisions**, so the same business operation can be reused, tested, and changed without touching your HTTP layer.
