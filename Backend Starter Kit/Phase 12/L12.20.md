# 1. What Does "Complete Service Layer" Mean?

It does **not** mean:

> Create 50 service files.

It means you can take a feature and correctly move its business logic into services.

The architecture you're aiming for is:

```text
                    HTTP Request
                         │
                         ▼
                       Route
                         │
                         ▼
                    Middleware
                         │
                         ▼
                     Controller
                         │
                  clean application input
                         │
                         ▼
                      SERVICE
                         │
               business decisions
                         │
                         ▼
                    Repository
                         │
                         ▼
                       Model
                         │
                         ▼
                      MongoDB
```

Your source roadmap describes this as the important transformation from a controller containing everything to a controller calling something such as `authService.login()`.

# 3. First — Define the Business Operations

Before writing code, list what the application can do.

```text
Todo
│
├── create
├── getOne
├── getMany
├── update
├── complete
└── delete
```

This is important.

Don't start by thinking:

> "What functions should I write?"

Start with:

> **"What operations does my application support?"**

Then turn those operations into service methods.

# 5. Start With the Repository

Remember:

> The service should decide **what the application should do**.  
> The repository should handle **how data is accessed**.

For example:

```js
const findByIdForUser = async (todoId, userId) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

The repository knows MongoDB.

The service doesn't need to know that this is:

```js
Todo.findOne()
```

# 8. Controller

The controller might be:

```js
const createTodo = asyncHandler(async (req, res) => {

    const todo = await todoService.createTodo({
        title: req.body.title,
        description: req.body.description,
        userId: req.user.id
    });

    res.status(201).json({
        success: true,
        data: todo
    });
});
```

Look at what the controller **doesn't** do.

```text
❌ MongoDB query
❌ business rules
❌ password logic
❌ database update
❌ Todo ownership logic
```

It translates HTTP into an application call.

That's exactly the "HTTP translator" role established in your controller phase.

# 9. Get One Todo

Service:

```js
const getTodo = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

This contains an important business/security decision:

```text
Does this Todo belong to this user?
```

The repository performs the ownership-aware query.

The service determines what a missing result means:

```text
No Todo
   ↓
404
```

# 10. Why `userId` Matters

Never blindly do:

```js
Todo.findById(todoId);
```

for a protected Todo operation.

Instead:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Conceptually:

```text
Todo ID
+
Authenticated User ID
        ↓
Correct resource
```

Your roadmap specifically calls out ownership queries as an important security boundary.

# 12. Update Todo

Now things become more interesting.

Suppose the user wants:

```text
title → "Learn Backend"
```

Service:

```js
const updateTodo = async ({
    todoId,
    userId,
    data
}) => {

    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.status === "completed") {
        throw new AppError(
            "Completed todos cannot be edited",
            409
        );
    }

    return todoRepository.updateByIdForUser(
        todoId,
        userId,
        data
    );
};
```

Now we have actual business logic:

```text
Does Todo exist?
        ↓
Does user own it?
        ↓
Is it already completed?
        ↓
If allowed → update
```

That's exactly why the service layer exists.

# 13. Complete Todo

This is a perfect example of a business operation.

```js
const completeTodo = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.status === "completed") {
        throw new AppError(
            "Todo is already completed",
            409
        );
    }

    return todoRepository.markCompleted(
        todoId,
        userId
    );

```

The service answers:

> **Is completing this Todo currently allowed?**

The repository answers:

> **How do I update MongoDB?**

That's the separation you should now be comfortable with.


# 21. Authentication Controller

The controller doesn't implement login.

Instead:

```js

    const result =
        await authService.login({
            email: req.body.email,
            password: req.body.password
        });

    res.status(200).json({
        success: true,
        data: result
    });
});
```

That's it.

# 22. Authentication Service

Conceptually:

```js
const login = async ({
    email,
    password
}) => {

    const user =
        await userRepository.findByEmail(email);

    if (!user) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const valid =
        await passwordService.compare(
            password,
            user.passwordHash
        );

    if (!valid) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const accessToken =
        generateAccessToken(user);

    const refreshToken =
        generateRefreshToken(user);

    const refreshTokenHash =
        await passwordService.hash(
            refreshToken
        );

    await userRepository.updateRefreshTokenHash(
        user.id,
        refreshTokenHash
    );

    return {
        user,
        accessToken,
        refreshToken
    };
};
```

The important part isn't the exact implementation.

It's the responsibility:

```text
AuthService
=
authentication workflow
```

# 23. Service Composition

Suppose registration requires:

```text
User creation
+
Welcome email
+
Activity log
```

Don't create:

```text
UserService
→ directly implement email internals
→ directly implement logging internals
```

Instead:

```text
RegistrationService
       │
       ├── UserRepository
       ├── EmailService
       └── ActivityService
```

This is service composition.

Your Phase 12 explicitly includes service composition because larger workflows often need multiple focused services.

---

# 24. Don't Build This

Avoid:

```text
SuperService
│
├── auth
├── users
├── todos
├── email
├── payments
├── analytics
├── notifications
├── admin
└── everything else
```

Instead:

```text
AuthService
UserService
TodoService
EmailService
NotificationService
PaymentService
```

and compose them where necessary.

That's the balance between **giant services** and **unnecessarily tiny services**.

---

# 25. Service Dependencies

A service may depend on:

```text
TodoService
 ├── TodoRepository
 └── ActivityService
```

while:

```text
AuthService
 ├── UserRepository
 ├── PasswordService
 └── TokenService
```

This is completely normal.

But watch for:

```text
TodoService
 ↓
ActivityService
 ↓
TodoService
```

That's a circular dependency.

If you encounter it, reconsider the architecture instead of simply trying to hide the problem.

---

# 26. Transactions

Suppose:

```text
Create order
+
Decrease inventory
```

Both database operations must succeed together.

A service can coordinate the business transaction:

```text
OrderService
      │
      ▼
   Transaction
      │
      ├── create order
      │
      └── decrease inventory
```

The repository performs database operations using the transaction/session context.

This is why transactions belong in your service-layer understanding: the service coordinates the **business operation**, while repositories perform the actual data operations. Your roadmap explicitly places transactions in 12.14.
