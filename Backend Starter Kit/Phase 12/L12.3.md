# Lesson 12.3 — What Is a Service?

In the previous lesson, we learned **why controllers shouldn't contain business logic**.

Now we answer the next question:

> **If the controller shouldn't contain business logic, where does that logic go?**

The answer is:

> **The Service Layer.**

Your starter pack also follows this idea with a dedicated `services/` layer, including files such as `auth.service.js` and `password.service.js`.

---

# 1. What Is a Service?

In simple words:

> **A service is a piece of application code responsible for performing a specific business operation.**

For example:

```text
User Service
    ↓
User-related operations

Auth Service
    ↓
Authentication operations

Password Service
    ↓
Password-related operations

Todo Service
    ↓
Todo-related operations
```

So a service answers:

> **"What should my application do?"**

---

# 2. The Request Flow

Let's say the frontend sends:

```http
POST /api/v1/users
```

with:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

The flow becomes:

```text
Frontend
   ↓
HTTP Request
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
User Service
   ↓
Database
   ↓
User Service
   ↓
Controller
   ↓
HTTP Response
```

The important part is:

```text
Controller
     ↓
User Service
```

The controller says:

> "Someone wants to create a user."

The service says:

> "Okay, I'll perform the user-creation operation."

---

# 3. Why Do We Need a Service?

You might be thinking:

> "Why can't the controller just do it?"

Technically, it can.

For a tiny application:

```js
const createUser = async (req, res) => {
    const user = await User.create(req.body);

    res.status(201).json(user);
};
```

This works.

But real applications usually have rules.

For example:

```text
Create User
    ↓
Check email
    ↓
Does user already exist?
    ↓
Hash password
    ↓
Create user
    ↓
Create verification token
    ↓
Send verification email
    ↓
Return user
```

Now the controller becomes complicated.

A service gives that process a home:

```text
User Controller
      ↓
User Service
      ↓
User creation workflow
```

---

# 4. Service = Application Operation

A useful way to think about a service is:

> **One service method represents an application operation.**

For example:

```js
userService.createUser()
```

means:

> "Perform the operation of creating a user."

Similarly:

```js
authService.login()
```

means:

> "Perform the login operation."

And:

```js
todoService.deleteTodo()
```

means:

> "Perform the operation of deleting a Todo."

So you can think of:

```text
Service Method
      ↓
Application Operation
```

---

# 5. First Simple Service

Let's create:

```text
services/
└── user.service.js
```

Start with something very simple:

```js
const createUser = async (userData) => {
    const user = await User.create(userData);

    return user;
};

export {
    createUser
};
```

And the controller:

```js
const createUser = asyncHandler(async (req, res) => {

    const user = await userService.createUser(req.body);

    res.status(201).json({
        success: true,
        data: user
    });
});
```

Now look at the separation:

```text
Controller
    ↓
Receives HTTP request
    ↓
Calls service
    ↓
Returns HTTP response
```

while:

```text
Service
    ↓
Creates user
    ↓
Returns user
```

---

# 6. But Our Service Is Too Simple

Right now:

```js
const createUser = async (userData) => {
    return User.create(userData);
};
```

doesn't look very impressive.

You might ask:

> "Why do I need a service for one database call?"

Excellent question.

**You might not need one for such a trivial operation.**

The value becomes much clearer when business rules appear.

For example:

```js
const createUser = async (userData) => {

    const existingUser = await User.findOne({
        email: userData.email
    });

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const hashedPassword = await bcrypt.hash(
        userData.password,
        12
    );

    const user = await User.create({
        ...userData,
        password: hashedPassword
    });

    return user;
};
```

Now the service has a real purpose.

It contains the workflow:

```text
Create User
    ↓
Check duplicate
    ↓
Hash password
    ↓
Create user
    ↓
Return user
```

---

# 7. Service Does Not Mean "Database Wrapper"

This is a very common beginner mistake.

Some developers create:

```js
const getUser = async (id) => {
    return User.findById(id);
};
```

for every single database operation.

Then their service becomes:

```text
Service
    ↓
Database
```

with no business logic.

That isn't necessarily wrong, but it doesn't demonstrate the main reason for a service layer.

A service should represent an **application operation**, not simply rename:

```js
User.findById()
```

to:

```js
userService.getUser()
```

We'll improve this further when we learn repositories.

---

# 8. Service vs Controller

Let's make this crystal clear.

## Controller

Concerned with:

```text
HTTP
```

It knows about:

```js
req
res
params
query
body
headers
cookies
HTTP status codes
```

Example:

```js
const getUser = asyncHandler(async (req, res) => {

    const user = await userService.getUser(
        req.params.id
    );

    res.status(200).json({
        success: true,
        data: user
    });
});
```

---

## Service

Concerned with:

```text
Application behavior
```

Example:

```js
const getUser = async (userId) => {

    const user = await User.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Notice:

```text
Controller
→ req.params.id

Service
→ userId
```

The service doesn't need to know that `userId` came from a URL.

It only needs the ID.

---

# 9. A Service Should Receive Data, Not Express Objects

Compare these.

### ❌ Bad coupling

```js
userService.createUser(req, res);
```

The service now knows about Express.

That's not what we want.

---

### ❌ Still unnecessarily coupled

```js
userService.createUser(req.body);
```

This is better, but the service is still being handed HTTP-derived structure directly.

---

### ✅ Cleaner

```js
userService.createUser({
    name: req.body.name,
    email: req.body.email,
    password: req.body.password
});
```

The controller translates HTTP input into application data.

The service receives:

```js
{
    name,
    email,
    password
}
```

It doesn't care whether that data came from:

```text
REST API
GraphQL
CLI
background job
AI agent
test
```

---

# 10. Service Return Values

A service should generally **return application results**.

For example:

```js
const user = await userService.createUser(data);

return user;
```

The service doesn't normally do:

```js
res.status(201).json(...)
```

Instead:

```text
Service
   ↓
returns user
   ↓
Controller
   ↓
HTTP response
```

This keeps the HTTP layer separate.

---

# 11. Service Errors

Suppose a user already exists.

The service can say:

```js
if (existingUser) {
    throw new AppError(
        "Email already registered",
        409
    );
}
```

The service doesn't need to do:

```js
res.status(409).json(...)
```

Instead:

```text
Service
   ↓
throws AppError
   ↓
asyncHandler
   ↓
Global Error Middleware
   ↓
HTTP response
```

This connects directly to what you learned in **Phase 8 — Error Handling**.

# 12. Service Example: Password Change

Consider:

```text
POST /api/v1/users/change-password
```

The controller might be:

```js
const changePassword = asyncHandler(async (req, res) => {

    await passwordService.changePassword({
        userId: req.user.id,
        currentPassword: req.body.currentPassword,
        newPassword: req.body.newPassword
    });

    res.status(200).json({
        success: true,
        message: "Password changed successfully"
    });
});
```

The service:

```js
const changePassword = async ({
    userId,
    currentPassword,
    newPassword
}) => {

    const user = await User.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    const isValid = await bcrypt.compare(
        currentPassword,
        user.password
    );

    if (!isValid) {
        throw new AppError(
            "Current password is incorrect",
            401
        );
    }

    if (currentPassword === newPassword) {
        throw new AppError(
            "New password must be different",
            400
        );
    }

    const hashedPassword = await bcrypt.hash(
        newPassword,
        12
    );

    user.password = hashedPassword;

    await user.save();
};
```

Notice how much cleaner the architecture is.

---

# 13. The Service Contains the Workflow

Look at the password example:

```text
Change Password
       │
       ▼
Find user
       │
       ▼
Verify current password
       │
       ▼
Check new password
       │
       ▼
Hash password
       │
       ▼
Save password
```

That's a **workflow**.

The service coordinates that workflow.

This is one of the most important responsibilities of a service.

---

# 14. Service as an Orchestrator

The word **orchestrator** sounds complicated, but the idea is simple.

It means:

> **The service coordinates multiple operations to complete one business task.**

For example:

```text
Register User
       │
       ├── Check user
       │
       ├── Hash password
       │
       ├── Create user
       │
       ├── Generate verification token
       │
       └── Send email
```

The service coordinates these pieces:

```text
authService.register()
       │
       ├── userRepository
       ├── password utility
       ├── token utility
       └── mail service
```

This is much closer to the architecture you'll eventually see in your starter.

---

# 15. Service Dependencies

A service can depend on other application components.

For example:

```js
import userRepository from "../repositories/user.repository.js";
import passwordService from "./password.service.js";
import mailService from "../mail/mail.service.js";
```

Then:

```text
Auth Service
   │
   ├── User Repository
   │
   ├── Password Service
   │
   └── Mail Service
```

Don't worry about implementing this architecture yet.

We're learning the idea first.

---

# 16. Service Naming

Use names that describe **what the application does**.

Good:

```text
createUser()
login()
registerUser()
changePassword()
resetPassword()
deleteTodo()
createOrder()
cancelOrder()
```

Less useful:

```text
process()
handle()
execute()
doSomething()
```

A service method should communicate its purpose.

For example:

```js
authService.login()
```

is immediately understandable.

---

# 17. One Service vs Many Services

You don't need:

```text
services/
├── createUser.service.js
├── getUser.service.js
├── updateUser.service.js
├── deleteUser.service.js
```

That would often be excessive.

Instead, related operations can live together:

```text
services/
└── user.service.js
```

containing:

```js
createUser()
getUser()
updateUser()
deleteUser()
```

But authentication may deserve its own service:

```text
services/
├── user.service.js
├── auth.service.js
└── password.service.js
```

Why?

Because these represent different areas of application behavior.

# 19. Service vs Utility

Another common confusion.

Suppose you have:

```js
hashPassword(password)
```

That is usually a **utility/helper operation**.

It performs a focused technical operation:

```text
password
   ↓
hash
```

But:

```js
changePassword(userId, oldPassword, newPassword)
```

is an application operation.

It may:

```text
Find user
 ↓
Verify old password
 ↓
Hash new password
 ↓
Save password
 ↓
Invalidate tokens
```

That's a service operation.

So:

```text
Utility
→ Performs a focused technical task.

Service
→ Coordinates an application operation.
```

This distinction will become important later.

# 20. Service vs Repository

We haven't officially learned repositories yet, but you should start recognizing the difference.

Imagine:

```js
await userRepository.findById(userId);
```

The repository answers:

> "How do I retrieve the user?"

The service answers:

> "What should I do with that user?"

For example:

```text
Service
   ↓
Get user
   ↓
Check whether account is active
   ↓
Check permission
   ↓
Perform operation
```

The repository doesn't make those application decisions.

Phase 13 will go deeply into this.

# 21. The Service Boundary

Here's another diagram worth remembering:

```text
                 HTTP WORLD
                     │
                     ▼
               ┌───────────┐
               │ Controller│
               └─────┬─────┘
                     │
          Clean application data
                     │
                     ▼
              ┌─────────────┐
              │   SERVICE   │
              │             │
              │ Business    │
              │ Logic       │
              │ Workflows   │
              │ Decisions   │
              └──────┬──────┘
                     │
                     ▼
               DATA WORLD
```

The service sits between the outside world and your data/application infrastructure.

# 22. A Practical Example

Let's design a Todo service.

Requirements:

```text
Create Todo
Get Todo
Update Todo
Delete Todo
```

We might eventually have:

```js
todoService.createTodo()
todoService.getTodo()
todoService.updateTodo()
todoService.deleteTodo()
```

For example:

```js
const updateTodo = async ({
    todoId,
    userId,
    title
}) => {

    const todo = await Todo.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.userId.toString() !== userId) {
        throw new AppError(
            "You cannot update this Todo",
            403
        );
    }

    if (todo.completed) {
        throw new AppError(
            "Completed Todo cannot be edited",
            400
        );
    }

    todo.title = title;

    await todo.save();

    return todo;
};
```

Notice the business rules:

```text
Todo exists?
       ↓
Does user own it?
       ↓
Is it already completed?
       ↓
Can it be edited?
       ↓
Update
```

That's exactly why the service exists.

# 23. The Most Important Question

Whenever you create a service method, ask:

> **"What business operation does this method represent?"**

For example:

```js
createUser()
```

→ Create a user.

```js
login()
```

→ Authenticate a user.

```js
changePassword()
```

→ Change a user's password according to application rules.

```js
cancelOrder()
```

→ Cancel an order according to cancellation rules.

```js
deleteTodo()
```

→ Delete a Todo if the operation is allowed.

If you can't explain what the method represents, you may be putting unrelated logic into the service.

# 🧠 What You Should Remember From 12.3

### A service is:

> **A layer that performs application/business operations.**

### A service should:

```text
✔ Receive application data
✔ Apply business rules
✔ Coordinate workflows
✔ Call repositories/utilities/other services
✔ Return application results
✔ Throw application errors
```

### A service should generally NOT:

```text
❌ Read req directly
❌ Write res directly
❌ Know Express
❌ Decide HTTP status codes
❌ Contain random unrelated operations
```
