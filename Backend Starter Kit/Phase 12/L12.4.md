# Lesson 12.4 — Controller vs Service

This is one of the **most important lessons in Phase 12**.

You now know:

> **Controller handles HTTP.**  
> **Service handles application/business logic.**

But when you're actually writing code, the difficult question is:

> **"This line of code — should it be in the controller or service?"**

Today we'll learn a practical method to answer that.

---

# 1. The Basic Difference

Keep this simple:

```text
Controller
    ↓
HTTP-related work

Service
    ↓
Application/business-related work
```

Or:

```text
Controller → "How do I communicate through HTTP?"
Service    → "What should the application do?"
```

---

# 2. Controller Responsibilities

A controller usually handles things like:

```js
req.body
req.params
req.query
req.user
```

It calls the service:

```js
userService.createUser(...)
```

And creates the HTTP response:

```js
res.status(201).json(...)
```

So a controller often looks like:

```js
const createUser = asyncHandler(async (req, res) => {

    const user = await userService.createUser({
        name: req.body.name,
        email: req.body.email,
        password: req.body.password
    });

    res.status(201).json({
        success: true,
        data: user
    });
});
```

Notice the controller is relatively small.

---

# 3. Service Responsibilities

The service performs the actual application operation.

For example:

```js
const createUser = async ({
    name,
    email,
    password
}) => {

    const existingUser = await User.findOne({
        email
    });

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const hashedPassword = await bcrypt.hash(
        password,
        12
    );

    const user = await User.create({
        name,
        email,
        password: hashedPassword
    });

    return user;
};
```

The service knows:

```text
Does the user already exist?
How should the password be stored?
What should happen when registration succeeds?
```

Those are application decisions.

---

# 4. A Very Useful Question

When deciding where code belongs, ask:

> **"Does this code need to know that an HTTP request exists?"**

If yes:

```text
→ Controller
```

If no:

```text
→ Probably Service or another application layer
```

For example:

```js
req.params.id
```

needs HTTP.

Therefore:

```text
Controller
```

But:

```js
if (!user) {
    throw new AppError("User not found");
}
```

doesn't need HTTP.

Therefore:

```text
Service
```

---

# 5. Another Useful Question

Ask:

> **"Would this code still make sense if I called the application from a CLI, background job, or another API?"**

Consider:

```js
res.status(201).json(user);
```

No.

That's specifically HTTP.

So:

```text
Controller
```

Now:

```js
if (user.isPremium) {
    discount = 0.1;
}
```

Yes.

The rule still makes sense regardless of how the operation was triggered.

So:

```text
Service
```

---

# 6. Let's Analyze a Real Controller

Here's a deliberately messy controller:

```js
const createUser = async (req, res) => {

    const { name, email, password } = req.body;

    if (!name || !email || !password) {
        return res.status(400).json({
            message: "All fields are required"
        });
    }

    const existingUser = await User.findOne({
        email
    });

    if (existingUser) {
        return res.status(409).json({
            message: "Email already registered"
        });
    }

    const hashedPassword = await bcrypt.hash(
        password,
        12
    );

    const user = await User.create({
        name,
        email,
        password: hashedPassword
    });

    res.status(201).json({
        success: true,
        data: user
    });
};
```

Let's go line by line.

---

# 7. Line 1

```js
const createUser = async (req, res) => {
```

### Controller

Why?

Because:

```text
req
res
```

are HTTP objects.

---

# 8. Reading Request Body

```js
const { name, email, password } = req.body;
```

### Controller

Why?

Because the controller is responsible for extracting information from the HTTP request.

The service shouldn't need to know:

```js
req.body
```

It should receive:

```js
{
    name,
    email,
    password
}
```

---

# 9. Required Field Check

```js
if (!name || !email || !password) {
    return res.status(400).json({
        message: "All fields are required"
    });
}
```

This is interesting.

There are actually **two different responsibilities** here.

The rule:

```text
name is required
email is required
password is required
```

is validation.

The:

```js
res.status(400).json(...)
```

part is HTTP.

In the architecture you're learning, input validation can be handled by the **validation layer/middleware**, while the controller remains responsible for the HTTP response flow.

So ideally:

```text
Validation
    ↓
"Are the fields valid?"
```

and:

```text
Controller
    ↓
"How do I turn this into an HTTP response?"
```

The exact placement can vary by project, but don't confuse validation with business logic.

---

# 10. Find Existing User

```js
const existingUser = await User.findOne({
    email
});
```

This is **database/data-access work**.

For now, you might see this inside the service:

```text
Controller
    ↓
Service
    ↓
Model
```

Later, when we learn repositories:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
```

So this line should **not remain in the controller**.

---

# 11. Duplicate User Rule

```js
if (existingUser) {
    return res.status(409).json({
        message: "Email already registered"
    });
}
```

The rule:

> A user cannot register with an email that is already registered.

That's application/business logic.

Therefore:

```text
Service
```

But again, the:

```js
res.status(...)
```

part belongs to HTTP handling.

The cleaner approach is:

```js
if (existingUser) {
    throw new AppError(
        "Email already registered",
        409
    );
}
```

Then your existing global error-handling architecture can turn that error into an HTTP response.

---

# 12. Password Hashing

```js
const hashedPassword = await bcrypt.hash(
    password,
    12
);
```

This is not HTTP.

It's part of the user-registration workflow.

So it belongs outside the controller.

Depending on your architecture, password hashing itself may eventually be handled by a password utility/service, while the registration service coordinates the operation.

For example:

```text
Auth/User Service
      ↓
Password Service
      ↓
bcrypt
```

Your starter pack's separate password service is a good example of this separation.

---

# 13. Create User

```js
const user = await User.create({
    name,
    email,
    password: hashedPassword
});
```

This is database access.

It should eventually be:

```text
Service
    ↓
Repository
    ↓
Model
```

rather than directly living in the controller.

---

# 14. HTTP Response

Finally:

```js
res.status(201).json({
    success: true,
    data: user
});
```

### Controller

Absolutely.

Why?

Because the service shouldn't know:

```text
HTTP 201
JSON response
Express res object
```

The service simply returns:

```js
return user;
```

Then the controller decides how to represent that result over HTTP.

---

# 15. Let's Refactor It

Our original controller:

```js
const createUser = async (req, res) => {

        return res.status(400).json({
            message: "All fields are required"
        });
    }

    if (existingUser) {
        return res.status(409).json({

        12

        name,
        email,
        password: hashedPassword
    });

    res.status(201).json({
        success: true,

    });

```

Becomes:

### Controller

```js
const createUser = asyncHandler(async (req, res) => {

    const user = await userService.createUser({

        email: req.body.email,
        password: req.body.password

```

### Service

```js
const createUser = async ({
    name,
    email,
    password

    const existingUser = await User.findOne({
        email
    });

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409

    }

    const hashedPassword = await bcrypt.hash(

```

Now we have:

```text
Controller
    ↓
HTTP

Service
    ↓
Application operation
```

Much cleaner.

# 16. The Most Important Difference

Look at these two functions.

### Controller

```js
const createUser = asyncHandler(async (req, res) => {

    const user = await userService.createUser({
        name: req.body.name,
        email: req.body.email,
        password: req.body.password
    });

    res.status(201).json({
        success: true,
        data: user
    });
});
```

### Service

```js
const createUser = async ({
    name,
    email,
    password
}) => {

    // business logic

    return user;
};
```

Notice:

```text
Controller knows:
    req
    res
    HTTP

Service knows:
    user data
    business rules
    application workflow
```

That separation is the entire point.

---

# 17. Controller Is an Adapter

A very useful mental model:

> **A controller adapts HTTP requests into service calls and service results into HTTP responses.**

Think:

```text
HTTP Request
     │
     ▼
 Controller
     │
     │ converts HTTP data
     ▼
 Service
     │
     │ returns application result
     ▼
 Controller
     │
     │ converts result to HTTP
     ▼
HTTP Response
```

So:

```text
Controller = Adapter between HTTP and application
```

This is a powerful concept.

---

# 18. Example: Get User

Suppose:

```http
GET /api/v1/users/123
```

Controller:

```js
const getUser = asyncHandler(async (req, res) => {

    const user = await userService.getUser(
        req.params.id
    );

    res.status(200).json({
        success: true,
        data: user
    });
});
```

Service:

```js
const getUser = async (userId) => {

    const user = await User.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

The controller knows:

```text
"user ID came from URL."
```

The service knows:

```text
"Given a user ID, find the user or fail."
```

That's a clean boundary.

---

# 19. Example: Delete User

Controller:

```js
const deleteUser = asyncHandler(async (req, res) => {

    await userService.deleteUser(
        req.params.id,
        req.user.id
    );

    res.status(204).send();
});
```

Service:

```js
const deleteUser = async (userId, requesterId) => {

    const user = await User.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    if (userId !== requesterId) {
        throw new AppError(
            "You cannot delete this user",
            403
        );
    }

    await User.findByIdAndDelete(userId);
};
```

The service contains the important decision:

```text
Can requester delete this user?
```

The controller handles:

```text
HTTP 204
```

---

# 20. What About `req.user`?

This is an important question.

You might wonder:

> "Authentication middleware puts `req.user` there. Should the service use `req.user`?"

No.

Instead:

```js
userService.deleteUser(
    req.params.id,
    req.user.id
);
```

The controller extracts the necessary data.

The service receives:

```text
userId
requesterId
```

So the service doesn't know:

```js
req.user
```

It simply knows:

```text
Someone with ID X wants to modify user Y.
```

That's cleaner.

# 21. Controller vs Service Cheat Sheet

|Task|Controller|Service|
|---|--:|--:|
|Read `req.body`|✅|❌|
|Read `req.params`|✅|❌|
|Read `req.query`|✅|❌|
|Read `req.user`|✅|❌|
|Set HTTP status|✅|❌|
|Send JSON response|✅|❌|
|Set HTTP cookies|✅|❌|
|Business rules|❌|✅|
|Application workflow|❌|✅|
|Business calculations|❌|✅|
|Permission/business decisions|❌|✅|
|Coordinate multiple operations|❌|✅|
|Database access|Eventually no|Eventually via repository|
|Throw application errors|Usually service|✅|

The exact boundaries can vary slightly by architecture, but this is the model we'll use for your starter.

# 22. A Practical Classification Technique

When you see a controller with 100 lines, don't immediately rewrite it.

Instead, mark every line:

```text
H = HTTP
B = Business
D = Data
V = Validation
```

For example:

```js
const createUser = async (req, res) => {     // H

    const { email } = req.body;              // H

    if (!email) {                            // V
        ...
    }

    const user = await User.findOne({        // D
        email
    });

    if (user) {                              // B
        ...
    }

    const passwordHash = await hash(...);   // B/utility

    await User.create(...);                  // D

    res.status(201).json(...);               // H
};
```

Then separate the layers.

This technique is extremely useful when you start working with unfamiliar codebases.

# 23. Don't Obsess Over "Perfect" Separation

One warning.

You might eventually encounter code where you think:

> "Is this line controller or service?"

Sometimes there isn't one universal answer.

Real architectures have judgment calls.

For example:

```text
Validation
```

could be:

```text
middleware
controller
service
schema layer
```

depending on the project.

The goal isn't:

> "Follow arbitrary rules."

The goal is:

> **Keep related responsibilities together and unrelated responsibilities separated.**

For your starter architecture, we'll use the separation we've established consistently.

---

# 24. The Biggest Beginner Mistake

Don't do this:

```js
const createUser = async (req, res) => {

    const data = await userService.createUser(req, res);

};
```

That's basically moving the controller into another file.

❌ Bad:

```text
Controller
   ↓
Service(req, res)
```

Better:

```text
Controller
   ↓
Service(data)
```

For example:

```js
userService.createUser({
    name,
    email,
    password
});
```

The service should operate on **application data**, not HTTP objects.

# ✅ One Possible Refactoring

### Controller

```js
const updateTodo = asyncHandler(async (req, res) => {

    const todo = await todoService.updateTodo({
        todoId: req.params.id,
        userId: req.user.id,
        title: req.body.title
    });

    res.status(200).json({
        success: true,
        data: todo
    });
});
```

### Service

```js
const updateTodo = async ({
    todoId,
    userId,
    title
}) => {

    const todo = await Todo.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.userId.toString() !== userId) {
        throw new AppError(
            "You don't own this Todo",
            403
        );
    }

    if (todo.completed) {
        throw new AppError(

            400
        );
    }

    todo.title = title;

    await todo.save();

    return todo;
};
```

Now the architecture is:

```text
HTTP
 │
 ▼
Controller
 │
 │ todoId
 │ userId
 │ title

Service

```

That's exactly the separation we're trying to build.

# 🧠 Final Takeaway

If you remember only **four things** from Lesson 12.4, remember these:

### 1.

> **Controller receives and responds to HTTP.**

### 2.

> **Service performs application/business operations.**

### 3.

> **Don't pass `req` and `res` into services.**

Instead:

```js
service.doSomething({
    userId,
    resourceId,
    data
});
```

### 4.

> **When a controller starts making business decisions, it is probably becoming too smart.**

The ideal flow is:

```text
                 HTTP
                  │
                  ▼
             CONTROLLER
                  │
          application data
                  │
                  ▼
               SERVICE
                  │
          business decisions
                  │
                  ▼
             REPOSITORY
                  │
             data access
                  │
                  ▼
                MODEL
                  │
                  ▼
              MongoDB
```

Whenever you're unsure where a line belongs, ask:

```text
"Does this line care about HTTP?"
          │
       YES ──────→ Controller
          │
        NO
          │
          ▼
"Does this line represent an
 application/business decision?"
          │
       YES ──────→ Service
          │
        NO
          │
          ▼
"Does this line access data?"
          │
       YES ──────→ Repository
```
