# Lesson 12.5 — Identifying Business Rules

This lesson is extremely important because **business rules are the main reason the Service Layer exists**.

So far we've learned:

```text
Controller
    ↓
HTTP handling

Service
    ↓
Application/business logic
```

But now we need to answer:

> **What exactly is "business logic"?**

The easiest way to understand it is through **business rules**.

---

# 1. What Is a Business Rule?

A business rule is a rule that defines:

> **What your application is allowed to do, not allowed to do, or required to do.**

For example:

```text
A user can only edit their own Todo.
```

That's a business rule.

Another:

```text
A completed Todo cannot be edited.
```

That's a business rule.

Another:

```text
Premium users receive a 10% discount.
```

That's a business rule.

Another:

```text
An order cannot be cancelled after it has been shipped.
```

That's a business rule.

Notice something important:

None of these rules are specifically about HTTP.

They would still exist if the operation came from:

```text
REST API
CLI
Background job
Admin panel
AI agent
```

That's why they belong in the application/service layer.

---

# 2. Business Rule vs Normal Code

Not every line of code is a business rule.

For example:

```js
const userId = req.params.id;
```

This is not a business rule.

It's HTTP handling.

---

This:

```js
const user = await User.findById(userId);
```

is data access.

---

But this:

```js
if (user.role !== "admin") {
    throw new AppError(
        "Only admins can perform this operation",
        403
    );
}
```

is a business/authorization rule.

So:

```text
req.params
    ↓
HTTP

User.findById()
    ↓
Data access

user.role !== "admin"
    ↓
Business/authorization rule
```

---

# 3. The Most Useful Question

Whenever you see an `if` statement, ask:

> **"Why does this condition exist?"**

For example:

```js
if (todo.completed) {
    throw new AppError(
        "Completed Todo cannot be edited",
        400
    );
}
```

Why does this condition exist?

Because the application has a rule:

> Completed Todos cannot be edited.

That's business logic.

---

Now:

```js
if (!email) {
    throw new AppError(
        "Email is required",
        400
    );
}
```

Why?

Because the input must contain an email.

That's input validation.

So not every `if` belongs to the service.

---

# 4. Four Different Types of Rules

When designing a backend, you'll frequently encounter these:

```text
1. Input Validation
2. Authentication
3. Authorization
4. Business Rules
```

They can look similar in code, but they solve different problems.

Let's understand each one.

---

# 5. Input Validation

Input validation asks:

> **"Is the data structurally valid?"**

Example:

```json
{
  "email": "hello",
  "password": ""
}
```

Potential rules:

```text
Email must be valid.
Password must not be empty.
Password must have minimum 8 characters.
```

For example:

```js
email: z.string().email()
```

or:

```js
if (!email) {
    ...
}
```

This is generally handled by your:

```text
validators/
```

or validation middleware.

---

# 6. Authentication

Authentication asks:

> **"Who are you?"**

For example:

```text
JWT
Session
Access token
Cookie
```

Authentication middleware might determine:

```js
req.user = {
    id: "123",
    role: "user"
};
```

So:

```text
Authentication
      ↓
Identify the user
```

---

# 7. Authorization

Authorization asks:

> **"Are you allowed to perform this action?"**

For example:

```text
Only admins can delete users.
```

Or:

```text
Users can only edit their own Todos.
```

Or:

```text
Only the owner of an order can cancel it.
```

Authorization can be handled partly by middleware and partly by services, depending on the rule.

This distinction is important.

---

# 8. Business Rules

Business rules ask:

> **"What should happen according to the application's rules?"**

Examples:

```text
Premium users receive 10% discount.

A completed Todo cannot be edited.

An order cannot be cancelled after shipment.

A user cannot reuse their current password.

A coupon cannot be used after expiration.

A product cannot be purchased if stock is insufficient.
```

These are classic service-layer responsibilities.

---

# 9. Let's Study a Real Example

Imagine your application has:

```text
Todo
```

Requirement:

> "A user can update their own Todo, but completed Todos cannot be modified."

Let's break it down.

---

### Step 1 — Is the user authenticated?

```text
Authentication
```

Middleware can handle this.

```text
authenticate
    ↓
req.user
```

---

### Step 2 — Is the Todo ID valid?

For example:

```text
ObjectId format
```

That's input validation.

---

### Step 3 — Does the Todo exist?

```js
const todo = await todoRepository.findById(todoId);
```

That's data access.

---

### Step 4 — Does the Todo belong to the user?

```js
if (todo.userId.toString() !== userId) {
    throw new AppError(
        "You don't own this Todo",
        403
    );
}
```

That's authorization/business logic.

---

### Step 5 — Is the Todo completed?

```js
if (todo.completed) {
    throw new AppError(
        "Completed Todo cannot be edited",
        400
    );
}
```

That's a business rule.

---

### Step 6 — Update the Todo

```js
todo.title = title;
```

That's application/data operation.

Eventually:

```text
Service
   ↓
Repository
   ↓
Database
```

---

# 10. Look at the Complete Flow

```text
Request
   │
   ▼
Authentication
   │
   ▼
Validation
   │
   ▼
Controller
   │
   │ todoId
   │ userId
   │ title
   ▼
Todo Service
   │
   ├── Find Todo
   │
   ├── Check ownership
   │
   ├── Check completed status
   │
   └── Update Todo
   │
   ▼
Repository
   │
   ▼
Database
```

Now the architecture starts making sense.

---

# 11. Business Rules Usually Sound Like Sentences

This is a very useful trick.

When reading requirements, look for sentences like:

> "Users can only..."

> "Users cannot..."

> "Only admins can..."

> "An order must..."

> "A product cannot..."

> "If X happens, then Y..."

These are often business rules.

For example:

### Requirement

> Users cannot delete a Todo that has already been completed.

Business rule:

```text
completed Todo → cannot delete
```

Service:

```js
if (todo.completed) {
    throw new AppError(
        "Completed Todo cannot be deleted",
        400
    );
}
```

---

# 12. Example: E-Commerce

Imagine you're building an e-commerce backend.

Requirement:

> "A customer cannot purchase more items than are currently available."

Business rule:

```text
requestedQuantity <= stock
```

Service:

```js
if (product.stock < quantity) {
    throw new AppError(
        "Insufficient stock",
        400
    );
}
```

That's not validation.

Why?

Because:

```text
quantity = 5
```

could be perfectly valid input.

But:

```text
stock = 2
```

means the operation isn't allowed.

So:

```text
Input valid
     ↓
Business rule fails
```

That's a key distinction.

---

# 13. Validation vs Business Rule

Compare these:

### Validation

```text
quantity must be an integer
quantity must be greater than 0
```

### Business rule

```text
quantity cannot exceed available stock
```

Why?

Because:

```text
quantity = 5
```

is structurally valid.

But:

```text
stock = 2
```

makes the operation invalid according to the application's rules.

---

# 14. Another Example: Password Change

Requirement:

> "A user must provide their current password before changing it."

That's a business/security rule.

Service:

```js
const isValid = await bcrypt.compare(
    currentPassword,
    user.password
);

if (!isValid) {
    throw new AppError(
        "Current password is incorrect",
        401
    );
}
```

Then:

> "The new password must be at least 8 characters."

That's input validation.

So:

```text
Current password correct?
        ↓
Business/security rule

New password has valid format?
        ↓
Validation
```

---

# 15. Another Example: Order Cancellation

Requirement:

> "A customer can cancel an order only while it is pending."

Business rule:

```text
PENDING → can cancel
SHIPPED → cannot cancel
DELIVERED → cannot cancel
```

Service:

```js
if (order.status !== "PENDING") {
    throw new AppError(
        "Only pending orders can be cancelled",
        400
    );
}
```

This is a classic service-layer rule.

The controller should not contain it.

---

# 16. State-Based Business Rules

A lot of real-world business logic involves **state**.

For example:

```text
Order
```

may have:

```text
PENDING
PAID
SHIPPED
DELIVERED
CANCELLED
```

Then the application might define:

```text
PENDING → PAID
PAID → SHIPPED
SHIPPED → DELIVERED
```

But:

```text
DELIVERED → PENDING
```

may not be allowed.

That's business logic.

You might eventually write:

```js
if (order.status !== "PAID") {
    throw new AppError(
        "Only paid orders can be shipped",
        400
    );
}
```

This type of logic becomes very important in larger systems.

---

# 17. Business Rules Can Involve Multiple Models

This is where services become especially useful.

Suppose:

> "A user can purchase a product only if the product is in stock and the user's account is active."

The service may need:

```text
User
Product
Order
```

Flow:

```text
Purchase Service
      │
      ├── Get User
      │
      ├── Check account status
      │
      ├── Get Product
      │
      ├── Check stock
      │
      └── Create Order
```

The controller shouldn't coordinate all of this.

The service can.

---

# 18. Business Rules Can Involve Calculations

For example:

> Premium customers receive 10% discount.

Service:

```js
let total = price * quantity;

if (user.isPremium) {
    total *= 0.9;
}
```

Another rule:

> Orders above ₹5,000 receive free shipping.

```js
let shippingCost = 100;

if (total >= 5000) {
    shippingCost = 0;
}
```

The important part isn't the arithmetic.

The important part is:

```text
"Why is shipping free above ₹5,000?"
```

Because that's an application rule.

---

# 19. Business Rules Can Trigger Other Actions

Suppose:

> "When a payment succeeds, mark the order as paid and send a confirmation email."

The service might coordinate:

```text
Payment successful
      │
      ├── Mark payment successful
      │
      ├── Update order
      │
      └── Send confirmation
```

This is a workflow.

The service acts as the coordinator.

Later, you'll learn better patterns for events, queues, and background jobs.

---

# 20. Business Rules Should Be Centralized

Imagine this rule:

> "Premium users receive 10% discount."

Bad architecture:

```text
Order Controller
      ↓
10% discount

Admin Controller
      ↓
10% discount

Checkout Controller
      ↓
10% discount
```

Now there are three copies.

Better:

```text
             Discount Rule
                  │
                  ▼
            Order Service
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    Checkout    Admin      API
```

One source of truth.

---

# 21. What Happens When the Rule Changes?

Today:

```text
Premium discount = 10%
```

Tomorrow:

```text
Premium discount = 15%
```

If centralized:

```js
if (user.isPremium) {
    total *= 0.85;
}
```

One change.

If duplicated:

```text
Controller A → 10%
Controller B → 10%
Controller C → 10%
Worker → 10%
```

You might forget one.

That's how inconsistent business behavior happens.

---

# 22. Business Rules vs Authorization

These can overlap, so let's carefully distinguish them.

Consider:

> "Only the owner can edit a Todo."

That's authorization.

```js
if (todo.userId !== userId) {
    throw new AppError(
        "Forbidden",
        403
    );
}
```

Now:

> "Completed Todos cannot be edited, even by their owner."

That's a business rule.

```js
if (todo.completed) {
    throw new AppError(
        "Completed Todo cannot be edited",
        400
    );
}
```

Both might live inside a service because both affect whether the operation can happen.

But conceptually:

```text
Ownership
    ↓
Authorization

Completed state
    ↓
Business rule
```

This distinction becomes very useful when designing permissions.

---

# 23. Business Rules vs Authentication

Consider:

> "User must be logged in to create a Todo."

That's authentication.

```text
No valid token
      ↓
401 Unauthorized
```

But:

> "A user can create at most 100 active Todos."

That's a business rule.

```js
if (activeTodoCount >= 100) {
    throw new AppError(
        "Todo limit reached",
        400
    );
}
```

So:

```text
Who are you?
     ↓
Authentication

Are you allowed?
     ↓
Authorization

What is the application allowed to do?
     ↓
Business rules
```

---

# 24. Business Rules vs Database Constraints

Another important distinction.

Suppose you have:

```text
Email must be unique.
```

You may enforce this at the database level:

```js
email: {
    type: String,
    unique: true
}
```

But your application might also need to handle the resulting duplicate-key error cleanly.

Database constraints protect your data.

Business logic decides application behavior.

Ideally:

```text
Application rule
        +
Database constraint
        ↓
Strong protection
```

Never rely on application checks alone for critical uniqueness constraints.

For example:

```js
const existingUser = await User.findOne({ email });

if (existingUser) {
    throw ...
}
```

is useful for a friendly error, but concurrent requests can still race.

The database constraint should remain the final safety net.

# 25. A Real-World Example: Coupon

Requirement:

> "A coupon can only be used once per user and expires after 30 days."

Let's identify the rules.

### Validation

```text
Coupon code must be a string.
```

### Data access

```text
Find coupon.
Find user's coupon usage.
```

### Business rules

```text
Coupon must exist.
Coupon must not be expired.
Coupon must be active.
User must not have used it before.
```

Service:

```text
applyCoupon()
    │
    ├── Find coupon
    ├── Check expiration
    ├── Check active status
    ├── Check previous usage
    └── Apply discount
```

That's a perfect service operation.

# 26. Turning Requirements Into Services

This is a very valuable developer skill.

Suppose a product owner gives you:

> "A user can submit a support ticket. The ticket must contain a title and description. A user can only close their own ticket. A closed ticket cannot be reopened."

Don't immediately start coding.

First identify:

### Operations

```text
createTicket()
closeTicket()
reopenTicket()
```

### Validation

```text
title required
description required
```

### Authorization

```text
user can only close own ticket
```

### Business rules

```text
closed ticket cannot be reopened
```

Now you know what the service layer needs to handle.

This is how professional backend development starts to feel easier.

Then:


That's much more powerful.

Imagine you're building a shopping cart.

Requirements:

```text
1. A user must be logged in to use a cart.
2. Product ID must be valid.
3. Quantity must be greater than 0.
4. Product must exist.
5. Product must be active.
6. Quantity cannot exceed stock.
7. Premium users get free shipping.

```

Let's classify them.

---

### Authentication

```text
1. User must be logged in.
```

---

### Validation

```text
2. Product ID must be valid.
3. Quantity must be greater than 0.
```

---

### Data Access

```text
4. Find product.
5. Save cart.
```

---

### Business Rules

```text
5. Product must be active.
6. Quantity cannot exceed stock.
7. Premium users get free shipping.
8. Cart total cannot exceed ₹1,00,000.
```

Excellent.

That's exactly how you should begin analyzing backend requirements.

# 29. Service Design From This Example

You might create:

```js
cartService.addItem(...)
```

Inside:

```text
Get product
     ↓
Product exists?
     ↓
Product active?
     ↓
Enough stock?
     ↓
Calculate cart total
     ↓
Check maximum cart value
     ↓
Calculate shipping
     ↓
Save cart
     ↓
Return cart
```

The controller remains tiny:

```js
const addItem = asyncHandler(async (req, res) => {

    const cart = await cartService.addItem({
        userId: req.user.id,
        productId: req.body.productId,
        quantity: req.body.quantity
    });

    res.status(200).json({
        success: true,
        data: cart
    });
});
```

# 30. A Very Important Rule

Don't move **everything** into services.

For example, don't write:

```js
const createUser = async (req, res) => {
    return userService.createUser(req, res);
};
```

That's not separation.

You've just moved code around.

Good architecture means:

```text
Controller
    ↓
translates HTTP
    ↓
Service
    ↓
performs application operation
```

# 31. The "Would It Still Exist?" Test

Here's my favorite test for identifying business rules.

Ask:

> **"If I completely removed HTTP from my application, would this rule still exist?"**

Example:

```text
Premium users get 10% discount.
```

Yes.

Therefore:

```text
Business rule
```

---

Example:

```text
Return HTTP 201.
```

No.

Therefore:

```text
HTTP concern
```

---

Example:

```text
Completed Todo cannot be edited.
```

Yes.

Therefore:

```text
Business rule
```

---

Example:

```text
Read `req.params.id`.
```

No.

Therefore:

```text
Controller concern
```

This test is incredibly useful.

# 32. Another Mental Model

Think about your application as a **machine**.

The controller is the **door**.

```text
HTTP
 ↓
Door
 ↓
Application
```

The service is the **brain**.

```text
Request
 ↓
Controller
 ↓
Service
 ↓
Decision
 ↓
Action
```

The repository is the **data worker**.

```text
Service
 ↓
Repository
 ↓
Database
```

So:

```text
Controller → communication
Service    → decisions
Repository → data
```

# 33. What You Should Look For in Existing Code

When you open an unfamiliar backend project and see:

```js
if (...)
```

don't immediately assume:

```text
service
```

Instead ask:

```text
What kind of rule is this?
```

### Is it:

```text
Input format?
     ↓
Validation

Who is the user?
     ↓
Authentication

Can they perform this action?
     ↓
Authorization

What should the application allow?
     ↓
Business rule

How do we retrieve/save data?
     ↓
Repository
```

This mindset will help you understand large codebases much faster.

# 🧪 Final Exercise

Consider this function:

```js
const cancelOrder = async (req, res) => {

    const orderId = req.params.id;

    const order = await Order.findById(orderId);

    if (!order) {
        return res.status(404).json({
            message: "Order not found"
        });
    }

    if (order.userId.toString() !== req.user.id) {
        return res.status(403).json({
            message: "You don't own this order"
        });
    }

    if (order.status !== "PENDING") {
        return res.status(400).json({
            message: "Only pending orders can be cancelled"
        });
    }

    order.status = "CANCELLED";

    await order.save();

    res.status(200).json({
        success: true,
        data: order
    });
};
```

Classify:

```text
orderId = req.params.id
```

→ ?

```text
Order.findById()
```

→ ?

```text
order.userId !== req.user.id
```

→ ?

```text
order.status !== "PENDING"
```

→ ?

```text
order.status = "CANCELLED"
```

→ ?

```text
order.save()
```

→ ?

```text
res.status(200).json()
```

→ ?

### Answer

```text
req.params.id
        ↓
Controller / HTTP extraction

Order.findById()
        ↓
Data access
        ↓
Eventually Repository

Ownership check
        ↓
Authorization / business rule
        ↓
Service

Status check
        ↓
Business rule
        ↓
Service

status = CANCELLED
        ↓
Application operation
        ↓
Service

order.save()
        ↓
Data access
        ↓
Eventually Repository

res.status().json()
        ↓
Controller
```

So the architecture becomes:

```text
                cancelOrder()
                     │
                     ▼
                Controller
                     │
                orderId
                userId
                     │
                     ▼
              Order Service
                     │
             ┌───────┼────────┐
             ▼       ▼        ▼
          Exists?  Owner?   Pending?
             │       │        │
             └───────┼────────┘
                     │
                     ▼
                Cancel Order
                     │
                     ▼
                Repository
                     │
                     ▼
                  MongoDB
```

# 🧠 Lesson 12.5 Summary

Remember these distinctions:

```text
Validation
→ Is the input shaped correctly?

Authentication
→ Who is the user?

Authorization
→ Is the user allowed?

Business Rule
→ What does the application allow or require?

Repository
→ How do we access the data?

Controller
→ How do we communicate through HTTP?
```

And the most important idea:

> **Business rules are usually the sentences in your requirements that say what the system can, cannot, must, or should do.**

Once you learn to identify those sentences, designing your service layer becomes much easier.
