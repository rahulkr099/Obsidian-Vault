# Lesson 12.6 — Designing Service Methods

In the last lesson, we learned how to **identify business rules**.

Now we move one step further:

> **How do we turn those business rules into good service methods?**

This is where the Service Layer starts becoming practical.

---

# 1. What Is a Service Method?

A service method is a function that represents **one meaningful application operation**.

For example:

```js
userService.createUser()
userService.getUser()
userService.updateUser()
userService.deleteUser()

authService.register()
authService.login()
authService.logout()

passwordService.changePassword()
passwordService.resetPassword()
```

Think of each method as:

```text
One method
    ↓
One application operation
    ↓
A small workflow
    ↓
Business rules
    ↓
Data access
```

---

# 2. Don't Think "One Method = One Database Query"

This is a very important point.

A beginner might create:

```js
const getUser = () => User.findById(...);

const createUser = () => User.create(...);

const findUserByEmail = () => User.findOne(...);
```

These are basically database operations.

That's not necessarily wrong, but **service methods should usually represent what the application is trying to accomplish**, not merely what MongoDB needs to do.

Compare:

```js
userRepository.findByEmail()
```

with:

```js
authService.login()
```

The first means:

> "Find a user."

The second means:

> "Authenticate this user."

The second is a much bigger application operation.

---

# 3. Service Method = Use Case

A very useful concept is:

> **A service method can be thought of as a use case.**

For example:

```text
Use case:
"User changes password."
```

Service method:

```js
passwordService.changePassword()
```

Another:

```text
Use case:
"User places an order."
```

Service method:

```js
orderService.placeOrder()
```

Another:

```text
Use case:
"Admin suspends a user."
```

Service method:

```js
adminService.suspendUser()
```

So:

```text
Requirement
    ↓
Use Case
    ↓
Service Method
```

This is one of the most useful ways to design services.

---

# 4. Start With the Requirement

Suppose the requirement is:

> "A user can update their profile. They can change their name and profile picture, but they cannot change their email through this endpoint."

Don't immediately write code.

First identify the operation:

```text
Update Profile
```

Then create:

```js
userService.updateProfile()
```

Now identify the inputs:

```text
userId
name
profileImage
```

So:

```js
userService.updateProfile({
    userId,
    name,
    profileImage
});
```

This is already giving us a clean design.

---

# 5. Good Service Method Inputs

Prefer passing a clear object:

```js
await userService.updateProfile({
    userId,
    name,
    profileImage
});
```

instead of:

```js
await userService.updateProfile(
    userId,
    name,
    profileImage,
    undefined,
    undefined,
    ...
);
```

Why?

Because objects make the method easier to understand and extend.

For example:

```js
await userService.updateProfile({
    userId,
    name,
    profileImage,
    bio
});
```

Much easier.

---

# 6. Avoid Passing `req`

Bad:

```js
await userService.updateProfile(req);
```

Why is this bad?

Because the service now knows about Express.

It has to do:

```js
req.body
req.params
req.user
```

That's exactly what we're trying to avoid.

Instead:

```js
await userService.updateProfile({
    userId: req.user.id,
    name: req.body.name,
    profileImage: req.body.profileImage
});
```

Now the service doesn't care where the data came from.

---

# 7. Avoid Passing `res`

Never design your service around:

```js
userService.updateProfile(req, res);
```

Then the service might start doing:

```js
res.status(...)
res.json(...)
res.cookie(...)
```

Now you've basically moved the controller into the service.

Instead:

```text
Controller
    ↓
Service
    ↓
returns result
    ↓
Controller
    ↓
HTTP response
```

---

# 8. What Should a Service Method Do?

A good service method usually follows a pattern like:

```text
1. Receive application data
2. Retrieve required data
3. Apply business rules
4. Perform the operation
5. Persist changes
6. Return result
```

For example:

```js
const updateProfile = async ({
    userId,
    name,
    profileImage
}) => {

    const user = await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    if (name !== undefined) {
        user.name = name;
    }

    if (profileImage !== undefined) {
        user.profileImage = profileImage;
    }

    await userRepository.save(user);

    return user;
};
```

We'll later replace direct model access with repositories.

---

# 9. A Service Method Is a Workflow

Consider:

```js
passwordService.changePassword()
```

The method might perform:

```text
Find user
   ↓
Verify current password
   ↓
Check new password
   ↓
Hash new password
   ↓
Save password
   ↓
Invalidate old sessions
   ↓
Return success
```

That's one operation:

> **Change password**

Even though it contains several steps.

This is why a service method is better thought of as a **workflow**, not a single query.

---

# 10. How Much Responsibility Should One Method Have?

This is where things get interesting.

Suppose you create:

```js
userService.doEverything()
```

Inside:

```text
Create user
Update user
Delete user
Login user
Send email
Create order
Generate invoice
...
```

Obviously bad.

One method has too many responsibilities.

Instead:

```text
userService.createUser()
userService.updateUser()
userService.deleteUser()

authService.login()
authService.register()

orderService.createOrder()
orderService.cancelOrder()
```

Each method represents a meaningful operation.

---

# 11. The "One Business Operation" Rule

A good starting rule is:

> **One service method should represent one business operation.**

For example:

```text
createUser()
```

One operation.

```text
changePassword()
```

One operation.

```text
cancelOrder()
```

One operation.

```text
completeTodo()
```

One operation.

This does **not** mean the method can only contain one line or one database query.

It can contain many steps.

---

# 12. Example: `cancelOrder()`

Suppose:

```text
Cancel Order
```

Requirements:

```text
1. Order must exist.
2. User must own the order.
3. Order must be pending.
4. Refund must be created.
5. Order must become cancelled.
```

A service method:

```js
const cancelOrder = async ({
    orderId,
    userId
}) => {

    const order = await orderRepository.findById(orderId);

    if (!order) {
        throw new AppError(
            "Order not found",
            404
        );
    }

    if (order.userId.toString() !== userId) {
        throw new AppError(
            "You cannot cancel this order",
            403
        );
    }

    if (order.status !== "PENDING") {
        throw new AppError(
            "Only pending orders can be cancelled",
            400
        );
    }

    await refundService.createRefund(order);

    order.status = "CANCELLED";

    await orderRepository.save(order);

    return order;
};
```

This is still one operation:

```text
cancelOrder()
```

Even though it has multiple steps.

---

# 13. Don't Split Too Early

A common beginner mistake is over-engineering.

They see:

```js
const cancelOrder = async (...) => {
    // 30 lines
};
```

and think:

> "30 lines! I need 10 services."

Not necessarily.

A method can reasonably contain a workflow.

Don't split code simply because it has several lines.

Split when a piece represents:

- a reusable operation
    
- a separate responsibility
    
- a meaningful domain concept
    
- a complex independent workflow
    

---

# 14. Example of Bad Splitting

Imagine:

```js
validateOrder()
findOrder()
checkOwner()
checkStatus()
updateStatus()
saveOrder()
```

and then:

```text
orderService.js
orderValidationService.js
orderLookupService.js
orderOwnershipService.js
orderStatusService.js
orderUpdateService.js
orderPersistenceService.js
```

That's probably too much.

You may end up with:

```text
Service → Service → Service → Service → Repository
```

for something simple.

Keep the architecture understandable.

---

# 15. When Should You Extract a Helper?

Suppose you have:

```js
const calculateOrderTotal = (...) => {
    // 40 lines of pricing logic
};
```

And this calculation is used by:

```text
createOrder()
updateOrder()
checkout()
```

Now extraction makes sense:

```js
pricingService.calculateOrderTotal()
```

because it represents a meaningful reusable operation.

So:

```text
Repeated + meaningful + independent
        ↓
Consider extracting
```

---

# 16. Service Dependencies

A service can call another service when that represents a genuine application relationship.

For example:

```text
Auth Service
    ↓
Password Service
```

Suppose registration needs:

```text
Hash password
Create user
Send verification email
```

The auth service might coordinate:

```js
const register = async (data) => {

    const passwordHash =
        await passwordService.hash(data.password);

    const user =
        await userRepository.create({
            ...data,
            password: passwordHash
        });

    await emailService.sendVerification(user);

    return user;
};
```

The auth service is orchestrating the registration workflow.

---

# 17. Don't Create Circular Dependencies

Be careful with:

```text
Auth Service
    ↓
User Service
    ↓
Auth Service
```

This can create circular dependencies.

For example:

```js
authService → userService
userService → authService
```

That can become difficult to understand and maintain.

If you see this happening frequently, it may mean your service boundaries aren't designed well.

---

# 18. Return the Right Thing

Suppose:

```js
userService.createUser()
```

creates a user.

Should it return:

```js
return user;
```

Usually yes, if the caller needs the user.

But don't automatically return everything.

For example, don't return:

```js
{
    user,
    password,
    internalToken,
    secretKey,
    databaseMetadata
}
```

The service should return an appropriate application result.

---

# 19. Never Return Sensitive Data Accidentally

Suppose the database user contains:

```js
{
    name: "Rahul",
    email: "rahul@example.com",
    password: "$2b$12$...",
    refreshToken: "...",
    resetToken: "..."
}
```

You shouldn't blindly return the entire document to the controller.

Instead, later you'll learn patterns such as:

```js
const userResponse = {
    id: user.id,
    name: user.name,
    email: user.email
};
```

Or configure sensitive fields to be excluded.

This is part of good service/API design.

---

# 20. Service Method Naming

Good names:

```text
createUser()
updateProfile()
changePassword()
resetPassword()
login()
logout()
createTodo()
completeTodo()
deleteTodo()
placeOrder()
cancelOrder()
applyCoupon()
```

These tell you what happens.

Avoid vague names:

```text
process()
handleData()
execute()
perform()
manage()
doTask()
```

For example:

```js
orderService.process()
```

What does that mean?

Nobody knows.

But:

```js
orderService.cancelOrder()
```

is immediately understandable.

---

# 21. Verb + Noun Is Often Useful

A simple naming pattern:

```text
verb + noun
```

Examples:

```text
createUser
updateUser
deleteUser
createOrder
cancelOrder
applyCoupon
generateInvoice
verifyEmail
changePassword
```

Authentication actions:

```text
login
logout
register
refreshToken
```

This makes service APIs easy to read.

---

# 22. Don't Put HTTP Names in Service Methods

Avoid:

```text
getUserResponse()
sendUser()
handleRequest()
sendLoginResponse()
```

These sound like controller responsibilities.

Prefer:

```text
getUser()
login()
createUser()
```

Because the service shouldn't care about HTTP.

---

# 23. Service Methods Should Be Testable

A major benefit of this architecture is testing.

Imagine:

```js
await orderService.cancelOrder({
    orderId,
    userId
});
```

You can test it without starting Express.

For example:

```text
Given:
    Order exists
    User owns order
    Status = PENDING

When:
    cancelOrder()

Then:
    Order status = CANCELLED
```

That's a clean unit/integration test target.

---

# 24. Compare With a Controller Test

Controller testing involves:

```text
HTTP request
    ↓
Express
    ↓
Middleware
    ↓
Controller
    ↓
Response
```

Service testing can focus directly on:

```text
Input
  ↓
Service
  ↓
Result
```

This is another reason we separate them.

# 25. Designing `createUser()`

Let's design one carefully.

Requirement:

> Register a new user.

Rules:

```text
1. Email must not already exist.
2. Password must be hashed.
3. User must be created.
4. Password must never be returned.
```

Service signature:

```js
userService.createUser({
    name,
    email,
    password
});
```

Workflow:

```text
Input
 ↓
Find existing user
 ↓
Already exists?
 ↓
Hash password
 ↓
Create user
 ↓
Remove sensitive fields
 ↓
Return safe user
```

That's a well-defined service method.

---

# 26. Designing `login()`

Requirement:

> Authenticate a user and return authentication information.

Inputs:

```js
authService.login({
    email,
    password
});
```

Workflow:

```text
Find user
   ↓
User exists?
   ↓
Compare password
   ↓
Account allowed?
   ↓
Generate tokens
   ↓
Return authentication result
```

Potential result:

```js
{
    user,
    accessToken,
    refreshToken
}
```

The controller can then decide how those tokens should be sent:

```text
JSON
Cookie
Header
```

The service doesn't need to care about HTTP.

# 30. Service Method Template

You can use this mental template:

```js
const operation = async ({
    requiredInput
}) => {

    // 1. Retrieve required data

    // 2. Check business rules

    // 3. Perform operation

    // 4. Persist changes

    // 5. Return result
};
```

For example:

```js
const completeTodo = async ({
    todoId,
    userId
}) => {

    const todo = await todoRepository.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.userId.toString() !== userId) {
        throw new AppError(
            "You don't own this Todo",
            403
        );
    }

    if (todo.completed) {
        throw new AppError(
            "Todo is already completed",
            400
        );
    }

    todo.completed = true;

    await todoRepository.save(todo);

    return todo;
};
```

---

# 31. Service Method and Repository

Notice something:

```js
const todo = await todoRepository.findById(todoId);
```

The service says:

> "I need the Todo."

The repository says:

> "I'll figure out how to retrieve it."

Then:

```js
await todoRepository.save(todo);
```

The service says:

> "Save these changes."

The repository handles the actual data access.

This gives us:

```text
Service
  ↓
"What should happen?"

Repository
  ↓
"How do I access the data?"
```

We'll study this deeply later.

---

# 32. Keep the Service Focused on the Use Case

Suppose:

```js
orderService.placeOrder()
```

starts doing:

```text
Create order
 ↓
Send email
 ↓
Generate PDF
 ↓
Upload PDF
 ↓
Resize product images
 ↓
Send SMS
 ↓
Calculate analytics
 ↓
Update dashboard
```

This might become too much.

Some operations may be better delegated:

```text
Order Service
   ├── Payment Service
   ├── Email Service
   ├── Invoice Service
   └── Notification Service
```

The order service can orchestrate them without implementing every detail itself.

---

# 33. Orchestration vs Implementation

This is an important architectural idea.

Suppose:

```text
Place Order
```

requires:

```text
Payment
Inventory
Order
Email
```

The order service may coordinate:

```text
Order Service
     │
     ├── Payment Service
     ├── Inventory Service
     ├── Order Repository
     └── Email Service
```

But it doesn't need to know:

```text
How bcrypt works
How email SMTP works
How MongoDB queries work
How JWT is cryptographically generated
```

Those details belong elsewhere.

So:

> **A service should coordinate what needs to happen, while specialized components handle their own technical details.**

---

# 34. A Warning About "God Services"

Just like we can have a God Controller, we can have a **God Service**.

Example:

```text
application.service.js
```

containing:

```text
users
auth
orders
payments
emails
notifications
products
todos
reports
analytics
```

That's a warning sign.

Instead, organize services around meaningful areas:

```text
services/
├── user.service.js
├── auth.service.js
├── password.service.js
├── todo.service.js
├── order.service.js
└── payment.service.js
```

Your starter pack's separation of authentication and password responsibilities follows this general idea.

# 35. A Practical Design Exercise

Requirement:

> "A user can deactivate their account. They must provide their password. An already deactivated account cannot be deactivated again."

Design the service.

### Step 1 — Name

```text
?
```

Answer:

```js
userService.deactivateAccount()
```

### Step 2 — Inputs

```text
userId
password
```

So:

```js
userService.deactivateAccount({
    userId,
    password
});
```

### Step 3 — Workflow

```text
Find user
   ↓
Does user exist?
   ↓
Already deactivated?
   ↓
Verify password
   ↓
Deactivate account
   ↓
Save
   ↓
Return result
```

### Step 4 — Business rules

```text
User must exist.
Account must be active.
Password must be correct.
```

That's a complete service design before you've written the implementation.

# 36. Another Exercise: Password Reset

Requirement:

> "A user can reset their password using a valid reset token. The token expires after 15 minutes. The new password must be different from the old password."

Potential method:

```js
passwordService.resetPassword({
    token,
    newPassword
});
```

Workflow:

```text
Find reset token
       ↓
Token exists?
       ↓
Token expired?
       ↓
Find user
       ↓
New password different?
       ↓
Hash password
       ↓
Update password
       ↓
Invalidate reset token
```

Notice how many operations are involved.

But the whole thing is still one use case:

> **Reset Password**

That's a good service method.

---

# 37. Don't Make Services Too Thin

This:

```js
const createUser = async (data) => {
    return userRepository.create(data);
};
```

might be perfectly fine **if there genuinely are no application rules at that point**.

But don't create a service layer just to rename repository methods:

```text
Repository:
create()

Service:
create()
```

The service becomes useful when it represents an application operation and coordinates rules/workflows.

---

# 38. Don't Make Services Too Fat

At the same time, don't put every technical detail into one service.

Bad:

```js
orderService.placeOrder()
```

containing:

```text
JWT generation
bcrypt hashing
Mongo queries
SMTP implementation
PDF generation
file compression
payment API HTTP calls
```

Better:

```text
Order Service
     ↓
Payment Service
     ↓
Email Service
     ↓
Invoice Service
     ↓
Repository
```

The service coordinates rather than becoming a dumping ground.

---

# 39. A Simple Balance

Think:

```text
Too thin
   ↓
Just forwards repository calls

       ✅
       │
       │
       ▼
Good service
   ↓
Represents a use case
   ↓
Contains/coordinates business rules
   ↓
Uses repositories/services

       │
       ▼
Too fat
   ↓
Everything in the application
```

Your goal is the middle.

# 40. The Service Design Checklist

Before creating a service method, ask:

### 1. What is the operation?

```text
createUser?
login?
cancelOrder?
```

### 2. What inputs does it need?

```text
userId?
orderId?
password?
```

### 3. What data does it need?

```text
User?
Order?
Product?
```

### 4. What business rules apply?

```text
Owner?
Status?
Limits?
Permissions?
```

### 5. What operation happens?

```text
Create?
Update?
Delete?
Calculate?
Transition?
```

### 6. What other services are needed?

```text
Payment?
Email?
Password?
Notification?
```

### 7. What should it return?

```text
User?
Order?
Boolean?
Result object?
```

If you can answer these questions, you're ready to implement the method.

# 🧠 The Most Important Concept of 12.6

Don't start with:

> "Which function should I write?"

Start with:

> **"What use case am I implementing?"**

Then:

```text
Use case
   ↓
Inputs
   ↓
Required data
   ↓
Business rules
   ↓
Workflow
   ↓
Service method
   ↓
Repository/services
   ↓
Result
```

For example:

```text
"Cancel an order"
       ↓
cancelOrder()
       ↓
orderId + userId
       ↓
find order
       ↓
check ownership
       ↓
check status
       ↓
cancel
       ↓
save
       ↓
return order
```

That's how you design a service method instead of randomly moving controller code into another file.
