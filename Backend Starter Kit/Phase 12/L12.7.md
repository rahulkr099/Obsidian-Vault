# Lesson 12.7 — Service Inputs and Outputs

According to the roadmap you gave me, **Lesson 12.7 is "Service Inputs and Outputs"**; **service error handling is 12.8**.

This lesson is important because once you understand what should **enter** and **leave** a service, your Controller → Service boundary becomes much cleaner.

---

# 1. The Basic Idea

Remember our architecture:

```text
HTTP Request
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Database
```

The controller deals with HTTP.

The service deals with the application's operation.

So we want:

```text
Controller
    ↓
clean application input
    ↓
Service
    ↓
application result
    ↓
Controller
    ↓
HTTP response
```

The service should **not need to understand Express**.

---

# 2. What Is a Service Input?

A service input is the information required to perform an application operation.

For example:

```js
userService.getUser({
    userId
});
```

The input is:

```text
userId
```

Another:

```js
authService.login({
    email,
    password
});
```

Inputs:

```text
email
password
```

Another:

```js
todoService.updateTodo({
    todoId,
    userId,
    title
});
```

Inputs:

```text
todoId
userId
title
```

---

# 3. Controller Knows Where the Data Came From

Suppose the request is:

```http
PATCH /api/v1/todos/123
```

with:

```json
{
    "title": "Learn Docker"
}
```

and authentication middleware has created:

```js
req.user = {
    id: "456"
};
```

The controller knows:

```text
todoId → req.params.id
title  → req.body.title
userId → req.user.id
```

So the controller converts HTTP data into application data:

```js
const todo = await todoService.updateTodo({
    todoId: req.params.id,
    userId: req.user.id,
    title: req.body.title
});
```

The service doesn't need to know that these values came from:

```text
req.params
req.body
req.user
```

---

# 4. Why Passing `req` Is Bad

Avoid:

```js
await todoService.updateTodo(req);
```

Now your service has to know:

```js
req.params.id
req.body.title
req.user.id
```

That creates coupling:

```text
Service
   ↓
Express
```

We want:

```text
Controller
   ↓
plain JavaScript data
   ↓
Service
```

This makes the service independent from HTTP.

---

# 5. The Better Pattern

Instead of:

```js
await todoService.updateTodo(req);
```

use:

```js
await todoService.updateTodo({
    todoId: req.params.id,
    userId: req.user.id,
    title: req.body.title
});
```

Now the service sees:

```js
{
    todoId,
    userId,
    title
}
```

That's much cleaner.

---

# 6. Why Objects Are Better Than Many Arguments

You could write:

```js
await todoService.updateTodo(
    req.params.id,
    req.user.id,
    req.body.title
);
```

This works.

But I recommend the object form:

```js
await todoService.updateTodo({
    todoId: req.params.id,
    userId: req.user.id,
    title: req.body.title
});
```

Why?

Because the meaning of each value is obvious.

Compare:

```js
updateTodo("123", "456", "Learn Docker");
```

with:

```js
updateTodo({
    todoId: "123",
    userId: "456",
    title: "Learn Docker"
});
```

The second is much easier to read.

---

# 7. Adding More Inputs Later

Suppose tomorrow you add:

```text
description
priority
dueDate
```

With positional arguments:

```js
updateTodo(
    todoId,
    userId,
    title,
    description,
    priority,
    dueDate
);
```

This becomes difficult to read.

With an object:

```js
updateTodo({
    todoId,
    userId,
    title,
    description,
    priority,
    dueDate
});
```

Much better.

---

# 8. Service Input Should Represent the Use Case

Remember Lesson 12.6:

> A service method represents an application operation/use case.

So the inputs should be based on what that operation actually needs.

For:

```text
Change Password
```

we might need:

```js
passwordService.changePassword({
    userId,
    currentPassword,
    newPassword
});
```

Not:

```js
passwordService.changePassword({
    req,
    res,
    next,
    userId,
    randomThing,
    headers
});
```

The first represents the use case.

The second represents HTTP implementation details.

---

# 9. Service Output

Now the other side.

After the service finishes, it should return an **application result**.

Example:

```js
const user = await userService.getUser({
    userId
});

return user;
```

The controller then decides how that result becomes HTTP:

```js
res.status(200).json({
    success: true,
    data: user
});
```

So:

```text
Service
   ↓
returns data

Controller
   ↓
turns data into HTTP response
```

---

# 10. Service Should Not Send HTTP Responses

Avoid this:

```js
const getUser = async (req, res) => {
    const user = await User.findById(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

This isn't really a service.

It's another controller.

Instead:

```js
const getUser = async ({ userId }) => {
    const user = await userRepository.findById(userId);

    return user;
};
```

Then:

```js
const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser({
        userId: req.params.id
    });

    res.status(200).json({
        success: true,
        data: user
    });
});
```

---

# 11. The Boundary

This is the boundary you should remember:

```text
┌──────────────────────────┐
│       Controller         │
│                          │
│ req.body                 │
│ req.params               │
│ req.query                │
│ req.user                 │
│ res.status()             │
│ res.json()               │
└────────────┬─────────────┘
             │
             │ plain application data
             ▼
┌──────────────────────────┐
│         Service          │
│                          │
│ business rules           │
│ workflows                │
│ application decisions    │
└────────────┬─────────────┘
             │
             │ repository calls
             ▼
┌──────────────────────────┐
│       Repository         │
└──────────────────────────┘
```

The line between Controller and Service is extremely important.

# 12. Example: Creating a Todo

Suppose the request is:

```http
POST /api/v1/todos
```

Body:

```json
{
    "title": "Learn Redis"
}
```

Authentication gives:

```js
req.user.id
```

### Controller

```js
const createTodo = asyncHandler(async (req, res) => {

    const todo = await todoService.createTodo({
        userId: req.user.id,
        title: req.body.title
    });

    res.status(201).json({
        success: true,
        data: todo
    });
});
```

### Service

```js
const createTodo = async ({
    userId,
    title
}) => {

    const todo = await todoRepository.create({
        userId,
        title
    });

    return todo;
};
```

Notice:

The service never sees:

```js
req
res
```

That's exactly what we want.

---

# 13. Example: Login

Controller:

```js
const login = asyncHandler(async (req, res) => {

    const result = await authService.login({
        email: req.body.email,
        password: req.body.password
    });

    res.status(200).json({
        success: true,
        data: result
    });
});
```

Service:

```js
const login = async ({
    email,
    password
}) => {

    const user =
        await userRepository.findByEmail(email);

    // authentication logic...

    return {
        user,
        accessToken,
        refreshToken
    };
};
```

The service returns:

```js
{
    user,
    accessToken,
    refreshToken
}
```

It doesn't decide:

```text
Should tokens be cookies?
Should they be JSON?
What HTTP status?
What headers?
```

Those are HTTP/API concerns.

---

# 14. Service Output Doesn't Have to Be a Database Document

This is important.

A service can return:

### A user

```js
return user;
```

### An order

```js
return order;
```

### A boolean

```js
return true;
```

### A result object

```js
return {
    user,
    accessToken
};
```

### A calculated result

```js
return {
    subtotal,
    discount,
    total
};
```

The output should represent the result of the operation.

---

# 15. Example: Calculate Cart Total

Imagine:

```js
cartService.calculateTotal({
    userId,
    cartId
});
```

It might return:

```js
{
    subtotal: 5000,
    discount: 500,
    shipping: 0,
    total: 4500
}
```

The controller can send:

```js
res.status(200).json({
    success: true,
    data: result
});
```

Again:

```text
Service
→ application result

Controller
→ HTTP response
```

---

# 16. Don't Return `res`

Never:

```js
return res.status(200).json(...);
```

from a service.

That means:

```text
Service
   ↓
Express
```

Instead:

```js
return {
    success: true,
    data: user
};
```

Then the controller handles the response.

---

# 17. Don't Return `req`

Similarly, a service shouldn't return or manipulate the request object.

Bad:

```js
req.user.lastLogin = new Date();
return req;
```

Instead, work with application data:

```js
return updatedUser;
```

---

# 18. What About Cookies?

This is a common question with authentication.

Suppose login generates:

```js
{
    accessToken,
    refreshToken
}
```

Who should set the cookie?

Usually the HTTP-facing layer should handle the HTTP cookie:

```js
res.cookie("refreshToken", result.refreshToken, {
    httpOnly: true,
    secure: true,
    sameSite: "strict"
});
```

The service can generate/return the token.

So:

```text
Service
    ↓
generates authentication result
    ↓
Controller
    ↓
sets HTTP cookie
```

This keeps the service independent of Express.

---

# 19. What About Status Codes?

The service generally shouldn't do:

```js
throw new Error(201);
```

or:

```js
return {
    statusCode: 201,
    data: user
};
```

just because HTTP is involved.

The service should focus on the operation.

For example:

```js
return user;
```

Then the controller knows:

```js
res.status(201).json({
    success: true,
    data: user
});
```

We'll discuss service errors in **12.8**.

---

# 20. What About "Not Found"?

Suppose:

```js
const user = await userRepository.findById(userId);
```

returns `null`.

The service understands:

> The requested user doesn't exist.

So the service can signal that condition.

For example:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

Then the global error system can eventually convert that into HTTP.

That's an important boundary:

```text
Service
→ identifies application failure

Error architecture
→ converts it to HTTP response
```

We'll explore this properly in 12.8.

---

# 21. Input Validation Still Has a Boundary

Suppose:

```js
title = ""
```

Should the service trust it?

No.

Your validation middleware should normally reject structurally invalid input before the controller calls the service.

Flow:

```text
Request
   ↓
Validation
   ↓
Controller
   ↓
Service
```

However, **business rules still belong in the service**.

For example:

```text
Validation:
title must be a non-empty string.

Business rule:
A user cannot have more than 100 active Todos.
```

So:

```text
Validation
→ Is this input structurally valid?

Service
→ Is this operation allowed?
```

# 22. A Complete Example

Let's build:

```text
todoService.updateTodo()
```

### Input

```js
{
    todoId,
    userId,
    title
}
```

### Service

```js
const updateTodo = async ({
    todoId,
    userId,
    title
}) => {

    const todo =
        await todoRepository.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.userId.toString() !== userId) {
        throw new AppError(
            "You don't own this Todo",
            403
        );
    }

    if (todo.completed) {
        throw new AppError(
            "Completed Todo cannot be edited",
            400
        );
    }

    todo.title = title;

    await todoRepository.save(todo);

    return todo;
};
```

The service has:

```text
Input
 ↓
Business decisions
 ↓
Repository
 ↓
Result
```

No:

```text
req
res
next
HTTP status response
JSON response
```

# 23. Controller Around It

```js
const updateTodo = asyncHandler(async (req, res) => {

    const todo = await todoService.updateTodo({
        todoId: req.params.id,
        userId: req.user.id,
        title: req.body.title
    });

    res.status(200).json({
        success: true,
        data: todo
    });
});
```

Look at how small the controller is.

That's the goal.

# 24. Why This Makes Testing Easier

Because the service accepts plain data:

```js
await todoService.updateTodo({
    todoId: "123",
    userId: "456",
    title: "Learn Docker"
});
```

You don't need to construct an entire Express request:

```js
{
    params: {},
    body: {},
    query: {},
    headers: {},
    user: {},
    ...
}
```

You can test the actual application operation directly.

This becomes very useful in Phase 21 when you test services. Your roadmap explicitly includes **testing services** as part of the backend testing architecture.

```text
    ↓

```

Tomorrow:

```text

    ↓

```

```text

    ↓

```

```text
    ↓
```

```text
    ↓
```

# 26. This Is Why Service Independence Matters

Imagine:

```text
REST API
    ──────┐
          │
CLI ──────┼──→ Todo Service → Repository
          │
Job ──────┤
          │
AI Agent ─┘
```

The business logic is reusable.

Without a service layer:

```text
REST Controller
    ↓
Business logic

CLI
    ↓
Different business logic

Job
    ↓
Different business logic
```

Now your rules can become inconsistent.

---

# 27. Service Result Should Be Stable

Try to make the service output meaningful and predictable.

For example:

```js
authService.login()
```

always returns something like:

```js
{
    user,
    accessToken,
    refreshToken
}
```

rather than sometimes:

```js
user
```

and sometimes:

```js
{
    user,
    token
}
```

and sometimes:

```js
null
```

unless those differences are intentional.

Predictable service contracts make the rest of your application easier to build.

# 28. Service Contract

You can think of a service method as having a contract:

```text
┌─────────────────────────────────┐
│        Service Contract         │
├─────────────────────────────────┤
│                                 │
│ Input                           │
│   ↓                             │
│ { userId, todoId, title }       │
│                                 │
│ Operation                       │
│   ↓                             │
│ updateTodo                      │
│                                 │
│ Success                         │
│   ↓                             │
│ updated Todo                    │
│                                 │
│ Failure                         │
│   ↓                             │
│ application error               │
│                                 │
└─────────────────────────────────┘
```

This is a powerful mental model.

# 29. Think of Services Like Functions

A clean service method should feel almost like a normal JavaScript function:

```js
const result = await service.operation(input);
```

For example:

```js
const user = await userService.getUser({
    userId
});
```

```js
const order = await orderService.placeOrder({
    userId,
    items
});
```

```js
const result = await authService.login({
    email,
    password
});
```

You don't need to know the internals.

That's abstraction.

---

Controller only knows:

# 32. A Simple Rule to Memorize

Whenever you're writing a service method, ask:

### Input

> **"What does this operation need?"**

### Output

> **"What result does this operation produce?"**

### Don't ask

> "What does Express give me?"

That's the controller's job.

# 33. Before vs After

### ❌ Poor architecture

```js
const updateTodo = async (req, res) => {

    const todo = await Todo.findById(req.params.id);

    if (todo.userId !== req.user.id) {
        return res.status(403).json(...);
    }

    todo.title = req.body.title;

    await todo.save();

    return res.status(200).json({
        data: todo
    });
};
```

Everything is mixed together:

```text
HTTP
Data access
Business rules
Response
```

---

### ✅ Better architecture

```js
// Controller

const updateTodo = asyncHandler(async (req, res) => {

    const todo = await todoService.updateTodo({
        todoId: req.params.id,
        userId: req.user.id,
        title: req.body.title
    });

    res.status(200).json({
        success: true,
        data: todo
    });
});
```

Service:

```js
const updateTodo = async ({
    todoId,
    userId,
    title
}) => {

    const todo =
        await todoRepository.findById(todoId);

    // business rules...

    todo.title = title;

    await todoRepository.save(todo);

    return todo;
};
```

Much cleaner.

# 🧠 Lesson 12.7 Summary

Remember this diagram:

```text
             HTTP
              │
              ▼
         ┌──────────┐
         │Controller│
         └────┬─────┘
              │
              │ application input
              ▼
         ┌──────────┐
         │ Service  │
         └────┬─────┘
              │
              │ application result
              ▼
         ┌──────────┐
         │Controller│
         └────┬─────┘
              │
              ▼
             HTTP
```

### Controller receives:

```js
req.body
req.params
req.query
req.user
```

and converts them into:

```js
{
    userId,
    todoId,
    title
}
```

### Service receives:

```js
{
    userId,
    todoId,
    title
}
```

and performs the application operation.

### Service returns:

```js
todo
```

or:

```js
{
    user,
    accessToken
}
```

or another meaningful application result.

### Service should generally NOT:

```text
❌ receive req
❌ receive res
❌ call res.json()
❌ call res.status()
❌ know Express
❌ decide HTTP response formatting
```

The key idea:

> **A service should look like a normal application function: give it the data required for a use case, let it perform the operation, and get back the result.**

And this clean input/output boundary is what will make **Lesson 12.8 — Service Error Handling** much easier: we'll see how a service communicates **failure** without directly sending an HTTP error response.
