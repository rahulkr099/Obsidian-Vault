# Lesson 12.8 — Service Error Handling

This lesson is exactly where the pieces from **Phase 8 — Error Handling** and **Phase 12 — Services** meet.

Your roadmap defines **12.8 as Service Error Handling**, followed by service dependencies in 12.9.

The goal is to understand:

> **When something goes wrong inside a service, how should the service communicate that failure without becoming responsible for the HTTP response?**

---

# 1. First: Where Does an Error Go?

Let's start with the complete flow:

```text
HTTP Request
     ↓
Route
     ↓
Middleware
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Database
```

Suppose the user asks for a Todo that doesn't exist.

The repository might return:

```js
null
```

The service discovers:

```text
Todo doesn't exist
```

The service should then communicate:

> "This operation cannot continue because the Todo doesn't exist."

But it should **not** do:

```js
res.status(404).json(...)
```

Instead:

```text
Service
   ↓
throw error
   ↓
Controller/asyncHandler
   ↓
Global error middleware
   ↓
HTTP 404 response
```

This is the key idea of this lesson.

---

# 2. Why Should the Service Throw an Error?

Imagine:

```js
const todo = await todoRepository.findById(todoId);

if (!todo) {
    throw new AppError("Todo not found", 404);
}
```

The service is saying:

> "The requested business operation cannot be completed."

It isn't saying:

> "Send an HTTP 404 response immediately."

That's an important separation.

---

# 3. HTTP Is Not the Service's Main Responsibility

Remember our previous lesson.

The service should accept:

```js
{
    todoId,
    userId
}
```

and return:

```text
success
```

or:

```text
failure
```

It shouldn't need:

```js
req
res
next
```

Similarly, it shouldn't directly handle:

```js
res.status(404)
res.json(...)
```

The service deals with the **application problem**.

The HTTP layer deals with the **HTTP representation of that problem**.

---

# 4. A Simple Example

Suppose:

```js
const getTodo = async ({ todoId, userId }) => {

    const todo = await todoRepository.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

Notice:

```text
Todo doesn't exist
       ↓
throw AppError
```

The service doesn't return:

```js
res.status(404)
```

---

# 5. What Happens After `throw`?

Suppose the controller calls:

```js
const todo = await todoService.getTodo({
    todoId: req.params.id,
    userId: req.user.id
});
```

If the service throws:

```js
throw new AppError("Todo not found", 404);
```

the normal execution stops.

The controller doesn't continue to:

```js
res.status(200).json(...)
```

Instead, the error travels upward.

Conceptually:

```text
Service
   │
   │ throw
   ▼
Controller
   │
   │ error propagation
   ▼
asyncHandler
   │
   ▼
error.middleware
   │
   ▼
HTTP response
```

This builds directly on the error architecture from Phase 8, where the roadmap describes the flow as controller → `asyncHandler` → `next(error)` → `error.middleware` → JSON response.

---

# 6. Why `AppError` Exists

You could technically write:

```js
throw new Error("Todo not found");
```

But then your error doesn't clearly contain the HTTP/application information your global handler may need.

Instead, you can have a custom error:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;
    }
}
```

Then:

```js
throw new AppError(
    "Todo not found",
    404
);
```

Now the error contains:

```text
message
    ↓
"Todo not found"

statusCode
    ↓
404

isOperational
    ↓
true
```

---

# 7. What Does `isOperational` Mean?

This is an important backend concept.

An **operational error** is an expected problem that the application knows how to handle.

Examples:

```text
User not found
Todo not found
Invalid credentials
Email already exists
Permission denied
Token expired
```

These aren't necessarily bugs in your code.

They're situations that can naturally happen during normal application usage.

---

# 8. Operational Error Example

Suppose:

```js
const user = await userRepository.findByEmail(email);

if (!user) {
    throw new AppError(
        "Invalid credentials",
        401
    );
}
```

A user entering the wrong email/password isn't necessarily a programming bug.

It's an expected application condition.

So:

```text
Invalid credentials
       ↓
Operational error
```

---

# 9. Programming Error

Now imagine:

```js
const user = await userRepository.findByEmail(email);

console.log(user.profile.name.first);
```

But:

```js
user.profile
```

is `undefined`.

That could be a programming bug.

You didn't intentionally design:

```text
"User profile is missing"
```

as a normal application condition.

So there's a difference:

```text
Operational error
→ expected application problem

Programming error
→ something is wrong in the code/system
```

Your Phase 8 roadmap specifically includes **operational vs programming errors** as a dedicated topic.

---

# 10. Don't Catch Every Error Inside the Service

This is a very common beginner mistake.

You might write:

```js
const getTodo = async ({ todoId }) => {

    try {
        const todo =
            await todoRepository.findById(todoId);

        if (!todo) {
            throw new AppError(
                "Todo not found",
                404
            );
        }

        return todo;

    } catch (error) {
        console.log(error);
        throw error;
    }
};
```

This usually adds no value.

You're catching the error only to immediately throw it again.

Instead:

```js
const getTodo = async ({ todoId }) => {

    const todo =
        await todoRepository.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

Let the error architecture handle propagation.

---

# 11. When Should You Catch an Error?

Catch an error when you can **meaningfully handle or transform it**.

For example:

```js
try {
    await paymentService.charge(...);
} catch (error) {
    // convert known payment failure
}
```

Maybe the external payment provider gives:

```text
PAYMENT_DECLINED
```

and your application wants:

```text
Payment could not be completed
```

That's a meaningful transformation.

---

# 12. Bad Catching

Avoid:

```js
try {
    ...
} catch (error) {
    throw new AppError(
        "Something went wrong",
        500
    );
}
```

for every error.

Why?

Because you might hide useful information.

For example:

```text
MongoDB connection error
```

becomes:

```text
Something went wrong
```

Now debugging becomes harder.

---

# 13. Preserve the Original Error

If you intentionally transform an error, preserve the original cause when useful.

Modern JavaScript allows:

```js
throw new AppError(
    "Unable to process payment",
    502,
    {
        cause: error
    }
);
```

The exact implementation depends on your error class.

The important idea is:

> **Don't destroy useful debugging information unnecessarily.**

---

# 14. Service Errors Should Be Meaningful

Bad:

```js
throw new Error("Error");
```

Not useful.

Better:

```js
throw new AppError(
    "Todo not found",
    404
);
```

Better still, depending on your API design:

```js
throw new AppError(
    "You don't have permission to access this Todo",
    403
);
```

The error should describe the actual application problem.

---

# 15. Common Service Errors

For a Todo service:

### Todo doesn't exist

```js
throw new AppError(
    "Todo not found",
    404
);
```

### User doesn't own it

```js
throw new AppError(
    "You don't have permission to modify this Todo",
    403
);
```

### Todo already completed

```js
throw new AppError(
    "Completed Todo cannot be modified",
    400
);
```

### Duplicate resource

```js
throw new AppError(
    "Todo with this title already exists",
    409
);
```

The exact status code depends on the API contract you choose.

---

# 16. Service Errors vs Validation Errors

This distinction is important.

Suppose the request contains:

```json
{
    "title": ""
}
```

A validation layer might reject this before the service:

```text
Request
   ↓
Validation
   ↓
❌ Invalid title
```

But suppose:

```json
{
    "title": "Learn Docker"
}
```

is structurally valid, but the user has already reached their maximum number of active Todos.

That's a business rule:

```text
Validation
   ↓
Valid
   ↓
Controller
   ↓
Service
   ↓
❌ User has reached Todo limit
```

So:

```text
Validation
→ Is the input structurally valid?

Service
→ Is this operation allowed?
```

---

# 17. Example: Todo Limit

Suppose your business rule is:

> A free user can have at most 100 active Todos.

Service:

```js
const createTodo = async ({
    userId,
    title
}) => {

    const count =
        await todoRepository.countActiveByUser(userId);

    if (count >= 100) {
        throw new AppError(
            "You have reached the maximum number of active Todos",
            403
        );
    }

    return todoRepository.create({
        userId,
        title
    });
};
```

This is a service-level error because it's a **business rule**.

---

# 18. Repository Errors

What if MongoDB itself fails?

For example:

```text
Database connection problem
```

The repository might throw an error.

The service doesn't always need to catch it.

For example:

```js
const getTodo = async ({ todoId }) => {

    const todo =
        await todoRepository.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

If MongoDB throws unexpectedly:

```text
Repository
    ↓
MongoDB error
    ↓
Service
    ↓
asyncHandler
    ↓
global error middleware
```

The error can propagate naturally.

---

# 19. Don't Convert Every Database Error to 404

This is a dangerous mistake.

Suppose:

```js
const todo = await repository.findById(todoId);
```

throws:

```text
MongoNetworkError
```

That does **not** mean:

```text
Todo not found
```

So don't do:

```js
try {
    ...
} catch {
    throw new AppError(
        "Todo not found",
        404
    );
}
```

You would be lying about what happened.

---

# 20. Distinguish "Not Found" From "Database Failed"

These are completely different:

```text
findById()
    │
    ├── returns null
    │      ↓
    │   Todo doesn't exist
    │      ↓
    │   404
    │
    └── throws MongoDB error
           ↓
        Infrastructure/system problem
           ↓
        usually 500/appropriate server error
```

This distinction is extremely important.

---

# 21. Service Error Flow

Let's visualize a successful request:

```text
POST /todos
    ↓
Validation
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
    ↓
Todo created
    ↓
Service returns Todo
    ↓
Controller
    ↓
201 Created
```

Now failure:

```text
POST /todos
    ↓
Validation
    ↓
Controller
    ↓
Service
    ↓
Business rule fails
    ↓
throw AppError
    ↓
asyncHandler
    ↓
error.middleware
    ↓
400/403/404/etc.
```

---

# 22. The Global Error Middleware

Conceptually:

```js
const errorMiddleware = (
    err,
    req,
    res,
    next
) => {

    const statusCode =
        err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message: err.message
    });
};
```

Then:

```js
throw new AppError(
    "Todo not found",
    404
);
```

eventually becomes:

```json
{
    "success": false,
    "message": "Todo not found"
}
```

with HTTP:

```text
404 Not Found
```

The service never called `res.status()`.

---

# 23. Why This Architecture Is Powerful

Imagine your service is used by:

```text
REST API
   ↓
Service

Background Job
   ↓
Service

CLI
   ↓
Service

Admin Tool
   ↓
Service
```

If the service directly returned:

```js
res.status(404)
```

it would only work with Express.

But if it throws:

```js
throw new AppError("Todo not found", 404);
```

any caller can decide how to represent that failure.

That's a much cleaner architecture.

---

# 24. The Controller Becomes Tiny

Controller:

```js
const getTodo = asyncHandler(async (req, res) => {

    const todo = await todoService.getTodo({
        todoId: req.params.id,
        userId: req.user.id
    });

    res.status(200).json({
        success: true,
        data: todo
    });
});
```

No:

```js
try/catch
```

needed if your `asyncHandler` handles rejected promises.

No:

```js
if (!todo)
```

needed if the service already defines that business behavior.

No:

```js
res.status(404)
```

needed inside the service.

This is what a **thin controller** looks like.

---

# 25. `asyncHandler` Does the Plumbing

You may have something like:

```js
const asyncHandler = (fn) => {
    return (req, res, next) => {
        Promise
            .resolve(fn(req, res, next))
            .catch(next);
    };
};
```

So:

```js
const controller = asyncHandler(async (req, res) => {
    const result = await service.operation();
});
```

If:

```js
service.operation()
```

throws:

```js
AppError
```

then:

```text
Promise rejection
      ↓
.catch(next)
      ↓
error middleware
```

That's why the controller doesn't need repetitive error handling.

---

# 26. Don't Swallow Errors

Never do this:

```js
try {
    await something();
} catch (error) {
    console.log(error);
}
```

Now the application may continue as if everything succeeded.

You have effectively swallowed the error.

If you catch it, either:

```js
throw error;
```

or meaningfully handle it.

---

# 27. Another Bad Pattern

Avoid:

```js
catch (error) {
    return null;
}
```

Now callers can't distinguish:

```text
No data
```

from:

```text
Something failed
```

For example:

```js
const user = await userService.getUser(...);

if (!user) {
    // Is user actually missing?
    // Or did database access fail?
}
```

You just destroyed that distinction.

---

# 28. Error Contract

A useful mental model:

```text
Service operation
       │
       ├── Success
       │      ↓
       │   return result
       │
       └── Expected failure
              ↓
          throw AppError
```

And unexpected errors:

```text
Unexpected failure
       ↓
propagate
       ↓
global error handler
```

This gives you a predictable contract.

---

# 29. Example: `changePassword()`

Let's put everything together.

```js
const changePassword = async ({
    userId,
    currentPassword,
    newPassword
}) => {

    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    const matches =
        await passwordService.compare(
            currentPassword,
            user.password
        );

    if (!matches) {
        throw new AppError(
            "Current password is incorrect",
            400
        );
    }

    if (currentPassword === newPassword) {
        throw new AppError(
            "New password must be different",
            400
        );
    }

    const passwordHash =
        await passwordService.hash(newPassword);

    user.password = passwordHash;

    await userRepository.save(user);

    return {
        success: true
    };
};
```

The service handles business failures.

It doesn't send:

```js
res.status(...)
```

---

# 30. Don't Leak Internal Errors

Suppose MongoDB produces:

```text
MongoServerError: E11000 duplicate key error collection...
```

You generally don't want to expose the entire internal database error to a user.

Bad response:

```json
{
    "success": false,
    "message": "MongoServerError: E11000 duplicate key..."
}
```

A better application-level response might be:

```json
{
    "success": false,
    "message": "Email is already registered"
}
```

This conversion is often handled by the error architecture rather than scattered throughout every service.

Your roadmap explicitly calls out **handling MongoDB errors, validation errors, JWT errors, and hiding sensitive errors in production** as part of the earlier error-handling phase.

---

# 31. Development vs Production

In development, you may want:

```text
stack trace
error name
debug information
```

In production, you usually don't want to expose:

```text
database connection details
file paths
stack traces
internal library information
secrets
```

For example:

### Development

```json
{
    "success": false,
    "message": "Something went wrong",
    "stack": "..."
}
```

### Production

```json
{
    "success": false,
    "message": "Something went wrong",
    "requestId": "abc123"
}
```

The user gets a safe message.

Your logs can contain the technical details.

---

# 32. Request IDs Help Here

Suppose the user receives:

```json
{
    "success": false,
    "message": "Something went wrong",
    "requestId": "req_123"
}
```

Your server logs:

```text
req_123
MongoNetworkError
database connection failed
stack trace...
```

Now support/debugging becomes much easier.

Instead of exposing internal details:

```text
User → requestId
Developer → logs
```

This connects your Service/Error architecture to the observability work you'll learn later.

---

# 33. Don't Put Logging Everywhere

You don't need:

```js
console.log("ERROR");
```

inside every service.

Centralized error middleware can log unexpected errors.

For example:

```text
Service
   ↓
throw
   ↓
Global error middleware
   ↓
Logger
   ↓
Safe HTTP response
```

This is much easier to maintain.

---

# 34. Practical Example: `deleteTodo()`

Let's build one.

### Requirement

> Delete a Todo owned by the current user.

Rules:

```text
1. Todo must exist.
2. User must own it.
3. Completed Todo cannot be deleted.
```

Service:

```js
const deleteTodo = async ({
    todoId,
    userId
}) => {

    const todo =
        await todoRepository.findById(todoId);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    if (todo.userId.toString() !== userId) {
        throw new AppError(
            "You don't have permission to delete this Todo",
            403
        );
    }

    if (todo.completed) {
        throw new AppError(
            "Completed Todo cannot be deleted",
            400
        );
    }

    await todoRepository.delete(todoId);

    return {
        deleted: true
    };
};
```

The service has three possible business failures:

```text
Todo missing
   → 404

Not owner
   → 403

Already completed
   → 400
```

And one success:

```text
deleted: true
```

---

# 35. Controller

```js
const deleteTodo = asyncHandler(async (req, res) => {

    const result = await todoService.deleteTodo({
        todoId: req.params.id,
        userId: req.user.id
    });

    res.status(200).json({
        success: true,
        data: result
    });
});
```

That's it.

The controller doesn't need:

```js
if (!todo)
if (!owner)
if (todo.completed)
```

because those decisions belong to the service.

---

# 36. The Golden Rule

Here's the rule I want you to remember:

> **Services decide whether an application operation can succeed; controllers decide how the result is represented over HTTP.**

So:

```text
Service:
"Todo doesn't exist."

Controller:
"Okay, the HTTP representation is 404."

Error middleware:
"Let's send the standard error response."
```

### ❌ Mistake 1 — Service sends response

```js

```

**Don't.**

### ❌ Mistake 2 — Service catches everything

```js

   throw new AppError("Something went wrong", 500);

```

**Don't do this blindly.**

### ❌ Mistake 3 — Swallowing errors

```js

    console.log(error);
}
```

**Don't.**

---

### ❌ Mistake 4 — Converting every error to 404

```js
catch {
```

### ❌ Mistake 5 — Exposing internal errors


# 🧠 40. The Three Layers of Failure

You should now distinguish these three:

### Validation failure

```text
"Title must be a string"
```

Usually caught at the validation boundary.

### Business failure

```text
"Completed Todo cannot be deleted"
```

Usually identified by the service.

### Unexpected/system failure

```text
MongoDB connection crashed
```

Usually allowed to propagate to the global error handler.

So:

```text
Input problem
     ↓
Validation

Business problem
     ↓
Service

Unexpected system problem
     ↓
Global error handling
```

This separation will save you a lot of confusion later.
