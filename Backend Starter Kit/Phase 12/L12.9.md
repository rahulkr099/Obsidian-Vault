# Lesson 12.9 — Service Dependencies

Now we reach an important part of the Service Layer:

> **What should happen when one service needs functionality from another service?**

Your roadmap explicitly places **Service Dependencies** here, before we learn how services call repositories.

This is especially important because your starter has multiple services, such as:

```text
services/
├── auth.service.js
└── password.service.js
```

So we need to understand **why one service might use another** and, more importantly, how to avoid creating a tangled dependency mess.

---

# 1. What Is a Service Dependency?

Suppose we have:

```text
Auth Service
Password Service
```

During registration, the authentication process needs to hash a password.

Instead of putting password hashing directly into `auth.service.js`, we can have:

```text
Auth Service
     ↓
Password Service
     ↓
hash password
```

So:

> **A service dependency means one service needs another service to complete its operation.**

For example:

```js
authService.register()
        ↓
passwordService.hash()
```

---

# 2. Why Not Put Everything Inside Auth Service?

A beginner might write:

```js
const register = async ({
    email,
    password
}) => {

    const hashedPassword =
        await bcrypt.hash(password, 12);

    // create user...

};
```

This works.

But now `auth.service.js` knows about:

```text
bcrypt
hashing algorithm
salt rounds
password implementation
```

Instead, we can have:

```js
const register = async ({
    email,
    password
}) => {

    const passwordHash =
        await passwordService.hash(password);

    // create user...
};
```

Now:

```text
Auth Service
→ "I need a password hash."

Password Service
→ "I'll handle password hashing."
```

That's a cleaner separation.

---

# 3. Think in Responsibilities

Imagine an application with:

```text
Auth
Users
Passwords
Email
Payments
Orders
Notifications
```

We don't want:

```text
auth.service.js
```

to contain everything.

Instead:

```text
Auth Service
   │
   ├── Password Service
   ├── User Service
   └── Email Service
```

Potentially:

```text
Order Service
   │
   ├── Payment Service
   ├── Inventory Service
   └── Notification Service
```

Each service owns a meaningful responsibility.

---

# 4. A Service Dependency Is Not Automatically Bad

You might hear:

> "Services shouldn't depend on other services."

That's too extreme.

Service-to-service dependencies can be perfectly reasonable.

For example:

```text
Auth Service
      ↓
Password Service
```

is natural.

The problem is **uncontrolled dependencies**.

For example:

```text
Auth
 ↓
User
 ↓
Order
 ↓
Payment
 ↓
Notification
 ↓
Auth
```

Now we have a dependency cycle.

That's where things become dangerous.

---

# 5. Good Dependency

Consider password handling.

```text
auth.service.js
        ↓
password.service.js
```

Why?

Because authentication needs password operations.

The direction makes sense:

```text
Authentication
    depends on
Password operations
```

---

# 6. Bad Circular Dependency

Imagine:

```text
auth.service.js
       ↓
user.service.js
       ↓
auth.service.js
```

Now:

```text
Auth → User
User → Auth
```

This is a **circular dependency**.

It can create confusing initialization problems and, more importantly, usually indicates unclear responsibilities.

---

# 7. What Does a Circular Dependency Look Like?

Imagine:

### `auth.service.js`

```js
import userService from "./user.service.js";
```

And:

### `user.service.js`

```js
import authService from "./auth.service.js";
```

You now have:

```text
auth.service.js
       ↕
user.service.js
```

Both depend on each other.

That's something you should generally avoid.

---

# 8. Why Circular Dependencies Are Dangerous

They make the architecture harder to understand.

You might eventually get:

```text
Auth
 ↓
User
 ↓
Auth
 ↓
User
```

And debugging becomes difficult.

It also makes it harder to answer:

> "Which service owns this business rule?"

That's the real problem.

---

# 9. A Better Solution: Find the Shared Responsibility

Suppose:

```text
Auth Service
    ↕
User Service
```

both need:

```text
User lookup
```

Instead of making them depend on each other, ask:

> "Can this responsibility belong somewhere else?"

For example:

```text
Auth Service
      ↓
User Repository

User Service
      ↓
User Repository
```

Now:

```text
Auth ──────┐
           ├──→ User Repository
User ──────┘
```

No circular dependency.

This is one reason the Repository Layer is useful.

---

# 10. Another Example

Suppose:

```text
Order Service
```

needs to find a user.

You could do:

```text
Order Service
      ↓
User Service
      ↓
User Repository
```

That may be reasonable if the user service contains meaningful user-related business logic.

But if all you need is:

> "Find this user's database record."

then perhaps:

```text
Order Service
      ↓
User Repository
```

is enough.

Don't introduce a service dependency just because another service exists.

---

# 11. Ask This Question

Whenever Service A wants to call Service B, ask:

> **"Does A actually need B's business operation, or does A merely need B's data?"**

This is a very useful design question.

### Needs business operation

Use another service:

```text
Auth
 ↓
Password Service
```

because:

```text
compare password
hash password
```

are meaningful password operations.

### Needs only data

Possibly use a repository:

```text
Order Service
 ↓
User Repository
```

if it only needs user data.

---

# 12. Service vs Repository Dependency

This gives us an important distinction:

```text
Service
→ business operation

Repository
→ data access
```

Suppose:

```text
Order Service
```

needs to know whether a user exists.

It could ask:

```js
await userRepository.existsById(userId);
```

That's a data-access question.

But suppose it needs:

> "Can this user purchase this restricted product?"

That's a business decision.

That may belong in a service/domain-level operation.

---

# 13. Example: Authentication

Let's design:

```text
authService.login()
```

It needs:

```text
1. Find user
2. Compare password
3. Generate tokens
```

Potential architecture:

```text
authService
    │
    ├── userRepository
    │
    ├── passwordService
    │
    └── tokenService
```

Conceptually:

```text
                authService.login()
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
   userRepository passwordService tokenService
          │            │            │
       MongoDB       bcrypt        JWT
```

This is much easier to understand than putting all three technical implementations directly inside `auth.service.js`.

---

# 14. `passwordService`

For example:

```js
const hash = async (password) => {
    return bcrypt.hash(password, 12);
};

const compare = async (password, hash) => {
    return bcrypt.compare(password, hash);
};

export default {
    hash,
    compare
};
```

Then authentication can say:

```js
const passwordHash =
    await passwordService.hash(password);
```

or:

```js
const valid =
    await passwordService.compare(
        password,
        user.password
    );
```

Auth doesn't need to know how bcrypt works.

---

# 15. This Is Abstraction

The auth service knows:

```text
"I can hash a password."
```

It doesn't need to know:

```text
"bcrypt uses this particular algorithm and these salt rounds."
```

So:

```text
Auth Service
      ↓
Password Service
      ↓
bcrypt
```

The implementation is hidden behind the service interface.

---

# 16. Another Example: Email

Suppose registration needs an email verification message.

Don't do:

```js
const register = async (...) => {

    // create user

    await nodemailer.createTransport(...);

    // send email
};
```

Now your auth service knows SMTP details.

Instead:

```text
Auth Service
      ↓
Email Service
      ↓
Mail Sender
      ↓
SMTP provider
```

The auth service can simply say:

```js
await emailService.sendVerificationEmail({
    user
});
```

That's much cleaner.

---

# 17. Service Dependencies Should Follow Meaning

Think about the sentence:

> "To perform X, I need Y."

For example:

> "To register a user, I need password hashing."

So:

```text
Auth → Password
```

Another:

> "To send a verification email, I need the email service."

So:

```text
Auth → Email
```

Another:

> "To create an order, I need payment processing."

So:

```text
Order → Payment
```

These are understandable dependencies.

---

# 18. Avoid Dependency Chains Just for Convenience

Bad architecture:

```text
Todo Service
    ↓
User Service
    ↓
Auth Service
    ↓
Password Service
```

Maybe Todo Service only wanted:

```text
userId
```

There was no reason to involve three services.

Every dependency adds complexity.

So:

> **Only introduce a dependency when the dependent service genuinely needs the other service's responsibility.**

---

# 19. Dependency Graph

It's useful to imagine your services as a graph.

Good:

```text
Auth ─────────→ Password
  │
  └───────────→ User Repository

Order ────────→ Payment
  │
  └───────────→ Order Repository
```

Bad:

```text
Auth ─────→ User
 ↑          │
 │          ↓
 └────── Payment
```

Even worse:

```text
Auth → User → Order → Payment → Auth
```

Your goal is to keep dependencies mostly flowing in one direction.

---

# 20. A Practical Rule: Dependencies Point Downward

A useful architecture might look like:

```text
Controller
    ↓
Service
    ↓
Service / Repository
    ↓
Infrastructure
```

For example:

```text
authController
       ↓
authService
       ├── passwordService
       ├── tokenService
       └── userRepository
```

The lower-level components shouldn't suddenly call the higher-level orchestration service.

Avoid:

```text
Repository
   ↓
Auth Service
```

That's usually backwards.

---

# 21. Repository Should Not Call Service

Imagine:

```js
userRepository.findByEmail()
```

inside the repository, and then:

```js
userService.checkSomething()
```

inside the repository.

That's a bad direction.

Repository should focus on:

```text
database access
```

not business orchestration.

Keep:

```text
Service
 ↓
Repository
```

not:

```text
Repository
 ↓
Service
```

---

# 22. Controller Should Not Become a Service Dependency

Similarly:

```text
Service
 ↓
Controller
```

is generally wrong.

A service should never need:

```js
userController.getUser()
```

The direction should remain:

```text
Controller
 ↓
Service
```

---

# 23. Example: Registration

Let's design a realistic flow.

User sends:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "password": "secret"
}
```

Controller:

```js
const result = await authService.register({
    name: req.body.name,
    email: req.body.email,
    password: req.body.password
});
```

Auth service:

```text
register()
   │
   ├── userRepository.findByEmail()
   │
   ├── passwordService.hash()
   │
   ├── userRepository.create()
   │
   └── emailService.sendVerificationEmail()
```

Architecture:

```text
                 Controller
                     │
                     ▼
              authService.register()
                     │
          ┌──────────┼───────────┐
          ▼          ▼           ▼
      User Repo   Password    Email Service
                     │
                   bcrypt
```

This is a clean example of service composition.

---

# 24. What Is Service Composition?

Service composition means:

> **One service coordinates multiple specialized operations to complete one use case.**

For example:

```text
Register User
      │
      ├── Check existing user
      ├── Hash password
      ├── Create user
      └── Send verification email
```

The authentication service is the **orchestrator**.

It doesn't necessarily implement every operation itself.

---

# 25. Orchestration Is Different From Ownership

Suppose:

```text
authService.register()
```

calls:

```js
passwordService.hash()
```

Who owns password hashing?

```text
Password Service
```

Who coordinates registration?

```text
Auth Service
```

So:

```text
Auth
→ orchestrates registration

Password
→ owns password operations
```

This distinction is very useful.

---

# 26. Example: Order Processing

Imagine:

```text
orderService.placeOrder()
```

needs:

```text
Payment
Inventory
Notification
```

Flow:

```text
placeOrder()
      │
      ├── check inventory
      │
      ├── charge payment
      │
      ├── create order
      │
      └── send notification
```

Potential architecture:

```text
Order Service
    │
    ├── Inventory Service
    ├── Payment Service
    ├── Order Repository
    └── Notification Service
```

The order service coordinates the business workflow.

---

# 27. But Be Careful With Long Chains

This can become:

```text
Order
 ↓
Payment
 ↓
User
 ↓
Notification
 ↓
Email
 ↓
Template
```

A chain like this isn't automatically wrong, but if every service calls another service, debugging becomes difficult.

Ask:

> "Can the top-level service directly use the needed dependency?"

For example:

```text
Order
 ├── Payment
 ├── Notification
 └── Repository
```

may be easier than:

```text
Order
 ↓
Payment
 ↓
Notification
```

when Notification isn't actually part of Payment's responsibility.

---

# 28. Don't Use Services as Utility Functions

You might eventually see:

```text
passwordService
tokenService
emailService
```

These are service-like components, but some are really **domain/infrastructure utilities**.

For example:

```js
tokenService.generateAccessToken()
```

might simply wrap JWT.

That's okay, but don't create:

```text
stringService
dateService
objectService
arrayService
numberService
```

for every tiny helper.

Use services for meaningful responsibilities.

# 30. Dependency Injection — The Next Idea

Now let's introduce a powerful concept.

Instead of importing dependencies directly:

```js
import passwordService from "./password.service.js";

const login = async (...) => {
    await passwordService.compare(...);
};
```

we can eventually inject the dependency:

```js
const createAuthService = ({
    userRepository,
    passwordService,
    tokenService
}) => {

    const login = async ({
        email,
        password
    }) => {

        const user =
            await userRepository.findByEmail(email);

        const valid =
            await passwordService.compare(
                password,
                user.password
            );

        // ...

    };

    return {
        login
    };
};
```

Then:

```js
const authService = createAuthService({
    userRepository,
    passwordService,
    tokenService
});
```

This is **dependency injection**.

---

# 31. Why Dependency Injection?

It makes dependencies explicit.

Without DI:

```js
authService
```

might secretly depend on:

```text
User Repository
Password Service
JWT Utility
Email Service
Redis
...
```

With DI:

```js
createAuthService({
    userRepository,
    passwordService,
    tokenService
});
```

you can immediately see:

> "These are the things Auth Service requires."

That's valuable.

---

# 32. Dependency Injection Also Helps Testing

Suppose you want to test:

```js
authService.login()
```

You don't necessarily want to use real:

```text
MongoDB
bcrypt
JWT
```

You can provide fake dependencies:

```js
const fakePasswordService = {
    compare: async () => true
};
```

and:

```js
const fakeUserRepository = {
    findByEmail: async () => ({
        id: "123",
        email: "test@example.com",
        password: "hash"
    })
};
```

Then:

```js
const authService = createAuthService({
    userRepository: fakeUserRepository,
    passwordService: fakePasswordService,
    tokenService: fakeTokenService
});
```

Now you can test the business logic in isolation.

This connects directly to your roadmap's later **12.19 Testing Services** lesson.

This is important for you.

You don't need a huge dependency injection framework just to build a small Express application.

You can start with:


The concept matters more than adding a library.

# 34. Composition Root

There's another useful concept:

> **Create your dependencies in one place.**

For example:

```text
app/
└── container.js
```

Conceptually:

```js
const userRepository = createUserRepository(...);
const passwordService = createPasswordService(...);
const tokenService = createTokenService(...);

const authService = createAuthService({
    userRepository,
    passwordService,
    tokenService
});
```

Now dependency wiring is centralized.

This becomes useful in larger applications.

```text
container

   ↓
factory
```

```text
authService
```

```text
Maximum abstraction
```

# 37. Example: `auth.service.js`

A simplified version:

```js
import userRepository from "../repositories/user.repository.js";
import passwordService from "./password.service.js";
import tokenService from "../utils/token.service.js";

const register = async ({
    name,
    email,
    password
}) => {

    const existingUser =
        await userRepository.findByEmail(email);

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const passwordHash =
        await passwordService.hash(password);

    const user =
        await userRepository.create({
            name,
            email,
            password: passwordHash
        });

    return user;
};
```

Notice the dependencies:

```text
auth.service
   │
   ├── userRepository
   └── passwordService
```

The auth service coordinates them.

---

# 38. What Shouldn't `passwordService` Do?

It shouldn't suddenly do:

```js
userRepository.create()
```

because that's not its responsibility.

Password service should focus on:

```text
hash
compare
possibly password-specific operations
```

So:

```text
Auth Service
    ↓
Password Service
```

not:

```text
Password Service
    ↓
Auth Service
```

---

# 39. Example of a Bad Dependency

Imagine:

```js
const hash = async (password) => {

    const user =
        await authService.getCurrentUser();

    return bcrypt.hash(password, 12);
};
```

Why would password hashing need authentication?

It shouldn't.

This creates:

```text
Password → Auth
```

for no good reason.

Dependencies should represent real responsibility relationships.

---

# 40. Dependency Direction Test

Whenever you create:

```text
A → B
```

ask:

### Question 1

> Does A genuinely need B's responsibility?

### Question 2

> Could A use a repository/utility instead?

### Question 3

> Would B ever need A?

If yes:

```text
A → B
B → A
```

you may have a design problem.

### Question 4

> Is there a shared responsibility that should be extracted?

These questions will prevent many architecture problems.

---

# 41. Common Service Dependency Mistakes

## Mistake 1 — Circular dependencies

```text
Auth → User → Auth
```

Avoid.

---

## Mistake 2 — Service calls controller

```text
Service → Controller
```

Don't.

---

## Mistake 3 — Repository calls service

```text
Repository → Service
```

Usually avoid.

---

## Mistake 4 — Giant dependency graph

```text
A → B → C → D → E → F
```

Keep workflows understandable.

---

## Mistake 5 — Calling another service unnecessarily

If you only need:

```text
userRepository.findById()
```

don't automatically call:

```text
userService.getUser()
```

unless you actually need the user service's business logic.

---

## Mistake 6 — Creating a service for every function

Don't create:

```text
HashStringService
FormatEmailService
GetDateService
```

just because the code is a function.

# 43. The Most Important Distinction

Here's the distinction I really want you to remember:

### Service dependency

```text
"I need another business operation."
```

Example:

```text
Auth
 ↓
Password Service
```

### Repository dependency

```text
"I need database data."
```

Example:

```text
Auth
 ↓
User Repository
```

### Utility dependency

```text
"I need a small technical operation."
```

Example:

```text
Auth
 ↓
Token utility
```

When you see:

```js
authService.login()
```

think:

```text
                   login()
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
 User Repository  Password       Token
                  Service        Utility
        │             │             │
```

# 45. A Very Important Design Principle

> **Depend on responsibilities, not files.**

Don't think:

> "I have `password.service.js`, so I should call it."

Instead think:

> "My authentication use case needs password comparison. Which component should own that responsibility?"

Then:

```text
Password Service
```

makes sense.

This prevents your architecture from becoming a collection of random folders.

```text
orderService

    ├── ?
```

# 🧠 47. Final Mental Model

When designing dependencies:

```text
              CONTROLLER
                   │
                   ▼
                SERVICE
             ┌─────┼─────┐
             │     │     │
             ▼     ▼     ▼
          SERVICE  REPO  UTILITY
             │     │
             ▼     ▼
       business   data
       operation  access
```

Ask:

```text
Does this component own the responsibility?
             │
             ├── Yes → depend on it
             │
             └── No → find the correct owner
```

And always watch for:

```text
A → B → A
```

because that often means your responsibilities aren't separated correctly.

