# Phase 13 — Repository Pattern & Data Access

## Lesson 13.1 — What is the Repository Pattern?

This is one of the most important lessons in your backend architecture.

You have already learned:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
```

Now we're adding:

```text
Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

The goal of today's lesson is **not** to memorize repository code.

The goal is to understand:

> **Why do we put database operations inside a Repository instead of directly writing them inside Services?**

Your starter architecture includes a repository layer such as `user.repository.js`, so this lesson is the foundation for understanding why that layer exists.

---

# 1. First: What Problem Are We Solving?

Imagine we're building a user login system.

A beginner might write:

```js
export const login = async (email, password) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new Error("User not found");
    }

    // password checking...
};
```

At first, this looks completely fine.

We're using Mongoose:

```js
User.findOne()
```

and getting our user.

But now imagine your application becomes large.

You have:

```text
Auth Service
User Service
Admin Service
Password Service
Notification Service
```

And all of them directly use:

```js
User.findOne()
User.findById()
User.create()
User.findByIdAndUpdate()
User.findByIdAndDelete()
```

Your application slowly becomes filled with database queries.

```text
auth.service.js
       ↓
    MongoDB

user.service.js
       ↓
    MongoDB

admin.service.js
       ↓
    MongoDB

password.service.js
       ↓
    MongoDB
```

This creates a problem.

---

# 2. The Repository Pattern

The Repository Pattern gives database access its own layer.

Instead of:

```text
Service
   ↓
MongoDB
```

we create:

```text
Service
   ↓
Repository
   ↓
MongoDB
```

For example:

```js
const user = await userRepository.findByEmail(email);
```

The service doesn't need to know how the database query works.

The repository handles it:

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

So:

```text
Service
  │
  │ "Find this user"
  ▼
Repository
  │
  │ User.findOne(...)
  ▼
Mongoose
  │
  ▼
MongoDB
```

That's the basic idea.

---

# 3. Real-World Analogy

Imagine a restaurant.

You are the customer.

You don't walk into the kitchen and say:

> "Give me this exact ingredient from shelf number 4."

Instead:

```text
Customer
   ↓
Waiter
   ↓
Kitchen
   ↓
Storage
```

The waiter acts as an abstraction.

You simply say:

> "I want a pizza."

You don't care:

```text
where ingredients are stored
how they're retrieved
which shelf they're on
how the kitchen accesses them
```

Similarly:

```text
Service
   ↓
Repository
   ↓
Database
```

The service says:

> "I need the user with this email."

The repository knows:

> "I'll use Mongoose to find that user."

---

# 4. Repository = Data Access Layer

A repository is responsible for **data access**.

Think:

> Repository = the part of the application that knows how to communicate with the database.

For MongoDB + Mongoose, that might mean:

```js
User.findOne()
User.findById()
User.create()
User.findOneAndUpdate()
User.deleteOne()
```

The repository wraps these operations.

For example:

```text
repositories/
└── user.repository.js
```

Inside:

```js
export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

The rest of the application doesn't need to know that `findByEmail()` internally uses:

```js
User.findOne()
```

---

# 5. Why Not Just Use the Model?

This is a very common question.

You might say:

> "We already have a User model. Why do we need a repository?"

Excellent question.

Let's compare them.

### Model

The model describes the **data structure and database behavior**.

For example:

```js
const userSchema = new mongoose.Schema({
    name: String,
    email: String,
    password: String
});
```

Then:

```js
const User = mongoose.model("User", userSchema);
```

The model gives us:

```js
User.findOne()
User.findById()
User.create()
```

### Repository

The repository provides **application-specific data-access functions**.

For example:

```js
userRepository.findByEmail(email);
```

or:

```js
userRepository.findActiveUsers();
```

or:

```js
userRepository.findByIdWithSafeFields(id);
```

So:

```text
Model
 ↓
Database representation

Repository
 ↓
Application's data-access interface
```

---

# 6. Model vs Repository

Remember this distinction:

```text
MODEL

"What is a User?"

        ↓

REPOSITORY

"How does our application retrieve Users?"
```

For example:

### Model

```js
User.findOne({
    email
});
```

is a Mongoose database operation.

### Repository

```js
userRepository.findByEmail(email);
```

is an application-level operation.

The repository hides the implementation.

---

# 7. Why Is That Useful?

Suppose today we use MongoDB.

Our repository:

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Later, perhaps we change how data is accessed.

Maybe we introduce:

```text
MongoDB
+
Redis cache
```

We could change:

```js
findByEmail()
```

internally.

The service can still use:

```js
userRepository.findByEmail(email);
```

The service doesn't need to know what changed.

This is called **separation of concerns**.

---

# 8. Separation of Concerns

This is the main idea behind the Repository Pattern.

Each layer has a different responsibility.

```text
Controller
    ↓
HTTP responsibility

Service
    ↓
Business responsibility

Repository
    ↓
Data-access responsibility

Model
    ↓
Database structure

MongoDB
    ↓
Data storage
```

Let's make this concrete.

Suppose we have:

```text
POST /api/v1/auth/login
```

### Controller

Handles HTTP:

```js
req.body
res.status(...)
```

### Service

Handles business logic:

```text
Does the user exist?
Is the password correct?
Should we create tokens?
```

### Repository

Handles data:

```text
Find user by email
Save refresh-token hash
```

### Model

Defines:

```text
User fields
schema
indexes
Mongoose behavior
```

---

# 9. The Complete Flow

Imagine Rahul sends:

```http
POST /api/v1/auth/login
```

with:

```json
{
    "email": "rahul@example.com",
    "password": "secret"
}
```

The flow is:

```text
                 HTTP Request
                      │
                      ▼
                    Route
                      │
                      ▼
                 Controller
                      │
                      ▼
              authService.login()
                      │
                      ▼
          userRepository.findByEmail()
                      │
                      ▼
                 User Model
                      │
                      ▼
                   MongoDB
                      │
                      ▼
                  User data
                      │
                      ▼
                Repository
                      │
                      ▼
                  Service
                      │
                      ▼
                Controller
                      │
                      ▼
                 HTTP Response
```

This is the architecture you need to start seeing mentally.

---

# 10. Without Repository

Here's the architecture without Repository:

```text
Controller
    ↓
Service
    ↓
Mongoose Model
    ↓
MongoDB
```

This isn't automatically bad.

For a **small application**, it can be perfectly reasonable.

For example:

```js
const user = await User.findById(userId);
```

inside a service may be totally fine.

This is important:

> **Repository Pattern is an architectural choice, not a law of backend development.**

Don't use an abstraction just because someone says "professional developers do this."

Use it when it gives your application a useful boundary.

---

# 11. With Repository

Now:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
    ↓
MongoDB
```

Example:

```js
const user = await userRepository.findById(userId);
```

The service doesn't care whether the repository uses:

```js
User.findById()
```

or:

```js
User.findOne()
```

or some more complex query.

---

# 12. A Very Simple Repository

Let's create one.

Suppose we have:

```text
models/
└── user.model.js
```

and:

```text
repositories/
└── user.repository.js
```

Our repository could start very simply:

```js
import User from "../models/user.model.js";

export const findById = async (userId) => {
    return User.findById(userId);
};
```

Then:

```js
export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

And:

```js
export const create = async (userData) => {
    return User.create(userData);
};
```

Now the repository has a small interface:

```text
findById()
findByEmail()
create()
```

---

# 13. The Service Uses the Repository

Instead of:

```js
import User from "../models/user.model.js";

const login = async (email, password) => {
    const user = await User.findOne({ email });

    // business logic...
};
```

we do:

```js
import * as userRepository from "../repositories/user.repository.js";

const login = async (email, password) => {
    const user = await userRepository.findByEmail(email);

    // business logic...
};
```

Notice the difference.

The service knows:

```text
I need a user by email.
```

It doesn't need to know:

```text
MongoDB
Mongoose
findOne()
```

That's the abstraction.

---

# 14. What Should NOT Go Into a Repository?

This is extremely important.

A repository should **not** become a second service.

Don't do this:

```js
const loginUser = async (email, password) => {
    // find user
    // compare password
    // generate JWT
    // send email
};
```

That's business logic.

It belongs in the service.

Repository:

```text
Data access
```

Service:

```text
Business logic
```

---

# 15. Bad Repository

Avoid:

```js
const loginUser = async (email, password) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new Error("User not found");
    }

    const valid = await bcrypt.compare(password, user.password);

    if (!valid) {
        throw new Error("Invalid password");
    }

    return generateToken(user);
};
```

Why?

Because this repository now knows about:

```text
passwords
bcrypt
authentication
JWT
business rules
```

That's too much.

---

# 16. Better Architecture

Instead:

### Repository

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

### Service

```js
const login = async (email, password) => {
    const user = await userRepository.findByEmail(email);

    // validate user
    // compare password
    // generate tokens

    return result;
};
```

Now responsibilities are clear.

---

# 17. Another Important Benefit: Testing

Repositories also make testing cleaner.

Imagine your service does:

```js
const user = await userRepository.findByEmail(email);
```

During a unit test, you can replace the repository behavior.

Conceptually:

```text
Service Test
     ↓
Fake Repository
     ↓
Fake User
```

instead of needing MongoDB for every service unit test.

Later, we'll study this properly in the testing phase.

---

# 18. Repository as an Interface

This is a useful way to think about it.

Your service sees:

```text
User Repository
────────────────────
findById()
findByEmail()
create()
update()
delete()
```

The service doesn't need to know the internal implementation.

So the repository becomes a **contract**.

For example:

```js
userRepository.findByEmail(email)
```

means:

> "Give me the user associated with this email."

The service doesn't care how that happens.

---

# 19. A Small Example

Let's imagine a Notes application.

### Repository

```js
const findById = async (noteId) => {
    return Note.findById(noteId);
};
```

### Service

```js
const getNote = async (noteId, userId) => {
    const note = await noteRepository.findById(noteId);

    if (!note) {
        throw new AppError("Note not found", 404);
    }

    if (note.userId.toString() !== userId) {
        throw new AppError("Forbidden", 403);
    }

    return note;
};
```

Notice something important.

The repository retrieved the data.

The service decided:

```text
Does this user have permission?
```

That's a **business/security decision**, so it belongs in the service or authorization layer—not simply in a generic database method.

We'll go much deeper into ownership queries in Lesson 13.15.

# 20. Your Mental Model

When you see:

```js
userRepository.findByEmail(email)
```

think:

```text
"I need some data."
        ↓
"I ask the repository."
        ↓
"The repository knows how to get it."
        ↓
"Mongoose talks to MongoDB."
```

Don't think:

> "Repository is just another folder."

It is a **boundary**.

# 21. The Architecture We Are Building

By the end of Phase 13:

```text
                    REQUEST
                       │
                       ▼
                    ROUTE
                       │
                       ▼
                  MIDDLEWARE
                       │
                       ▼
                  CONTROLLER
                       │
                       ▼
                    SERVICE
                       │
                       ▼
                 REPOSITORY
                       │
                       ▼
                    MODEL
                       │
                       ▼
                   MONGODB
```

Each layer answers a different question:

|Layer|Question|
|---|---|
|Route|Which endpoint?|
|Middleware|Can this request continue?|
|Controller|How do I handle HTTP?|
|Service|What should the application do?|
|Repository|How do I access the data?|
|Model|What does the data look like?|
|MongoDB|Where is the data stored?|

---

# 22. One Important Warning

Don't fall into this trap:

```text
Controller
 ↓
Service
 ↓
Repository
 ↓
Model
```

and assume:

> "Every function must pass through every layer."

Not necessarily.

Architecture should serve the application.

For a very simple operation, adding five layers can create unnecessary complexity.

The goal is not:

```text
MORE FILES = MORE PROFESSIONAL
```

The goal is:

```text
CLEAR RESPONSIBILITIES
+
LOW COUPLING
+
EASY TESTING
+
EASY MAINTENANCE
```

That's the real reason we're learning this pattern.

---

# 23. Interview Question

### Q: What is the Repository Pattern?

A good answer:

> **The Repository Pattern separates data-access logic from business logic. A repository provides methods for retrieving and modifying data, while the service layer uses those methods without needing to know the details of the underlying database implementation.**

In simpler words:

> **Service decides what the application should do; Repository handles how the application gets or saves the data.**
