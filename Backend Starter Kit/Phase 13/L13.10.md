# Phase 13 — Repository Pattern & Data Access

## Lesson 13.10 — `delete()`

In **13.8**, we learned `create()`.

In **13.9**, we learned `update()`.

Now we complete the basic CRUD operations with:

```text
DELETE
   ↓
delete()
```

Your Phase 13 roadmap explicitly defines **13.10 as `delete`**.

The main idea is:

> **The Service decides whether something should be deleted; the Repository performs the database deletion.**

---

# 1. What Does `delete()` Mean?

Suppose MongoDB contains:

```text
Todo
────────────────────────
_id: 123
title: "Learn Repository"
userId: 456
```

The user wants to delete it.

The Service might call:

```js
await todoRepository.delete(todoId);
```

The Repository then performs the database operation:

```text
Service
   ↓
repository.delete(id)
   ↓
MongoDB
   ↓
Document removed
```

Simple.

But just like `update()`, **the important part isn't the Mongoose method itself**.

The important part is understanding:

- who decides deletion is allowed,
    
- how ownership is checked,
    
- what the Repository should return,
    
- and why blindly deleting by ID can become dangerous.
    

---

# 2. Basic Mongoose Delete

Mongoose provides several deletion methods.

One common method is:

```js
Model.findByIdAndDelete(id);
```

So a basic Repository could be:

```js
const deleteById = async (id) => {
    return Todo.findByIdAndDelete(id);
};
```

Conceptually:

```text
id
 ↓
find document by _id
 ↓
delete document
```

---

# 3. Why Call It `deleteById()`?

You might wonder why we're writing:

```js
deleteById()
```

instead of:

```js
delete()
```

Because the name tells us **how the document is located**.

Compare:

```js
deleteById(todoId);
```

with:

```js
deleteOne({
    _id: todoId
});
```

The first is immediately understandable.

For a Repository API, explicit names can be useful:

```text
create()
findOne()
findById()
updateById()
deleteById()
```

Your roadmap calls the lesson simply **`delete`**, but this implementation detail is worth understanding.

---

# 4. The Basic Repository

For a Todo Repository:

```js
import Todo from "../models/todo.model.js";

export const deleteById = async (todoId) => {
    return Todo.findByIdAndDelete(todoId);
};
```

That's enough to perform the database operation.

But don't stop here.

The dangerous question is:

> **Who is allowed to delete that Todo?**

---

# 5. The Security Problem

Imagine:

```text
User A
   ↓
Todo A
   ↓
ID = 123
```

User B somehow discovers:

```text
123
```

and sends:

```http
DELETE /api/v1/todos/123
```

If your code does:

```js
Todo.findByIdAndDelete("123");
```

MongoDB doesn't know:

```text
"Is User B the owner?"
```

It only knows:

```text
"Does Todo 123 exist?"
```

If it exists:

```text
DELETE
```

That's a serious authorization problem.

---

# 6. Never Confuse ID With Permission

This is one of the most important lessons from today's topic.

```js
Todo.findByIdAndDelete(todoId);
```

means:

> Find this document by ID and delete it.

It does **not** mean:

> Verify that the current user is allowed to delete this document.

These are completely different concerns.

---

# 7. Ownership-Aware Delete

For a user-owned Todo, we may want:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

Now the database query says:

```text
Find Todo where:

_id    = requested Todo
AND
userId = authenticated user
```

Only then delete it.

Conceptually:

```text
DELETE /todos/123
        │
        ▼
     todoId
        +
 authenticated userId
        │
        ▼
   Repository
        │
        ▼
findOneAndDelete({
    _id: todoId,
    userId
})
```

Your starter roadmap specifically points toward ownership-aware queries later in Phase 13 and deeper authorization/ownership work afterward.

---

# 8. Where Does `userId` Come From?

The client should **not** tell us:

```json
{
    "userId": "456"
}
```

Instead, authentication middleware establishes the current user.

For example:

```text
Authorization header
       ↓
authMiddleware
       ↓
req.user
```

Then:

```js
req.user.id
```

might represent the authenticated user.

The Controller can call:

```js
todoService.deleteTodo(
    req.user.id,
    req.params.todoId
);
```

---

# 9. Controller

The Controller handles HTTP.

```js
export const deleteTodo = async (req, res) => {
    await todoService.deleteTodo(
        req.user.id,
        req.params.todoId
    );

    res.status(204).send();
};
```

Notice:

The Controller doesn't do:

```js
Todo.findOneAndDelete();
```

That's Repository responsibility.

---

# 10. Service

The Service handles the business decision.

Conceptually:

```js
const deleteTodo = async (userId, todoId) => {
    const deletedTodo =
        await todoRepository.deleteByOwner(
            todoId,
            userId
        );

    if (!deletedTodo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return deletedTodo;
};
```

The Service says:

> "Delete this Todo belonging to this authenticated user."

The Repository handles the actual database query.

---

# 11. Repository

Now the Repository could be:

```js
const deleteByOwner = async (todoId, userId) => {
    return Todo.findOneAndDelete({
        _id: todoId,
        userId
    });
};
```

Now look at the separation:

```text
Service
→ decides what operation is allowed

Repository
→ constructs database query

MongoDB
→ performs deletion
```

This is exactly the kind of separation we're building throughout Phase 13.

---

# 12. Why Is `findOneAndDelete()` Useful?

Because it allows us to provide a filter.

For example:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

means:

```text
Find one Todo
where:
    _id = todoId
    AND
    userId = userId

Then delete it.
```

This is much more useful for ownership than:

```js
Todo.findByIdAndDelete(todoId);
```

---

# 13. `findByIdAndDelete()` vs `findOneAndDelete()`

### `findByIdAndDelete()`

```js
Todo.findByIdAndDelete(todoId);
```

Best mental model:

```text
delete where _id = todoId
```

---

### `findOneAndDelete()`

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

Best mental model:

```text
delete where filter matches
```

Therefore:

```text
Simple ID deletion
        ↓
findByIdAndDelete()

Ownership-aware deletion
        ↓
findOneAndDelete()
```

---

# 14. What Does the Delete Operation Return?

This is important.

An operation such as:

```js
const deletedTodo =
    await Todo.findByIdAndDelete(todoId);
```

can give you the document that was deleted.

So you may receive something like:

```json
{
    "_id": "123",
    "title": "Learn Repository",
    "userId": "456"
}
```

If nothing matched, you can get:

```js
null
```

That gives the Service useful information.

---

# 15. Why Does `null` Matter?

Suppose:

```js
const deletedTodo =
    await todoRepository.deleteById(todoId);
```

If:

```js
deletedTodo === null
```

then the document wasn't found.

The Service can decide:

```js
if (!deletedTodo) {
    throw new AppError(
        "Todo not found",
        404
    );
}
```

This is another example of:

```text
Repository
→ database result

Service
→ application meaning
```

---

# 16. Don't Put HTTP Status Codes in Repository

Avoid:

```js
const deleteById = async (id) => {
    const todo = await Todo.findByIdAndDelete(id);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

This isn't necessarily catastrophic, but it mixes responsibilities.

The Repository shouldn't need to understand:

```text
HTTP 404
HTTP 403
HTTP 500
```

Those are application/API concerns.

A cleaner approach:

```text
Repository
→ returns null

Service
→ interprets null as "not found"

Controller
→ converts result/error into HTTP response
```

Let's build the complete flow.

```text
DELETE /api/v1/todos/:todoId
             │
             ▼
       Authentication
             │
             ▼
          Controller
             │
             ▼
           Service
             │

             │
```

# 18. What About Authorization?

Suppose only admins can delete users.

The Service might receive:

```js
userId
```

and then check:

```text
Is this user an administrator?
```

or authorization middleware may already establish the role.

Then:

```text
Authorized?
   │
   ├── NO → reject
   │
   └── YES
          ↓
       Repository
          ↓
        delete
```

The Repository should not generally become the place where every business authorization rule lives.

---

# 19. Different Delete Use Cases

"Delete" isn't always one operation.

You might have:

```text
deleteTodo()
deleteUser()
deleteComment()
deleteOrder()
```

And even within users:

```text
deleteOwnAccount()
adminDeleteUser()
deactivateUser()
```

These can have completely different business rules.

But they may eventually use Repository operations such as:

```js
deleteById()
```

or:

```js
deleteOne(filter)
```

---

# 20. Hard Delete

A **hard delete** means the document is actually removed.

Example:

```text
Before:

MongoDB
──────────────
Todo A
Todo B
Todo C

        ↓ delete Todo B

After:

MongoDB
──────────────
Todo A
Todo C
```

Todo B is gone from the collection.

This is what methods like:

```js
findByIdAndDelete()
```

perform.

---

# 21. Soft Delete

There is another approach:

> Don't actually remove the document.

Instead:

```js
{
    deletedAt: new Date()
}
```

For example:

```text
Before:

{
    title: "Learn Repository",
    deletedAt: null
}

        ↓ soft delete

After:

{
    title: "Learn Repository",
    deletedAt: "2026-08-26T..."
}
```

The document still exists.

Later, queries can exclude deleted documents.

Your Phase 17 roadmap specifically includes **soft delete and restore**, so we'll study this properly there rather than mixing it into today's basic `delete()` lesson.

---

# 22. Why Use Soft Delete?

Soft deletion can be useful when you need:

```text
Restore
Audit history
Accidental deletion recovery
Business records
Compliance/history
```

For example:

```text
DELETE
 ↓
deletedAt = now
```

Then:

```text
RESTORE
 ↓
deletedAt = null
```

This is a different business design from hard deletion.

---

# 23. Don't Automatically Use Soft Delete Everywhere

Soft delete isn't always better.

It introduces extra complexity.

For example, every query might need:

```js
{
    deletedAt: null
}
```

Otherwise deleted records may appear.

So:

```text
Hard delete
→ simpler

Soft delete
→ recoverable but more complex
```

Choose based on the application's requirements.

---

# 24. Example: Todo Hard Delete

### Repository

```js
const deleteByOwner = async (todoId, userId) => {
    return Todo.findOneAndDelete({
        _id: todoId,

```

### Service

```js

        throw new AppError(

    return deletedTodo;

```

### Controller


# 25. Why Return `204`?

For a successful DELETE request, a common API choice is:

```http
204 No Content
```

Meaning:

> The operation succeeded and there is no response body.

So:

```js
res.status(204).send();
```

is a common pattern.

You could also choose:

```http
200 OK
```

with a response body such as:

```json
{
    "success": true,
    "message": "Todo deleted successfully"
}
```

The important thing is consistency across your API.

---

# 26. Don't Return the Deleted Document Unless Needed

Suppose:

```js
const deletedTodo =
    await todoRepository.deleteByOwner(...);
```

The Service receives it.

Do we always need to return it?

No.

If your endpoint uses:

```http
204 No Content
```

there is no need to send the deleted document to the client.

The Repository may need to return it so the Service can distinguish:

```text
deleted successfully
```

from:

```text
nothing matched
```

But the Controller doesn't necessarily need the deleted document.

---

# 27. Important Security Scenario

Imagine this:

```text
User A owns Todo 123

User B sends:
DELETE /todos/123
```

Bad implementation:

```js
Todo.findByIdAndDelete(123);
```

Result:

```text
Todo deleted ❌
```

Secure ownership-aware implementation:

```js
Todo.findOneAndDelete({
    _id: 123,
    userId: userB
});
```

Result:

```text
No matching Todo
```

The Todo remains.

This is exactly why ownership-aware repository queries matter.

The source roadmap later highlights:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

as a key pattern for preventing users from accessing another user's resource.

---

# 28. A Subtle Point: 404 vs 403

Suppose User B tries to delete User A's Todo.

Should you return:

```http
403 Forbidden
```

or:

```http
404 Not Found
```

There are different API/security designs.

An ownership query:

```js
{
    _id: todoId,
    userId
}
```

returns no match.

The Service might therefore return:

```text
404 Not Found
```

This can also avoid revealing whether the resource exists.

The exact policy belongs to your application's authorization design.

The important lesson today is:

> **The Repository can enforce the ownership condition in the query, while the Service decides how the result should be interpreted.**

# 29. Common Mistake #1 — Delete Directly From Controller

❌

```js
export const deleteTodo = async (req, res) => {
    await Todo.findByIdAndDelete(
        req.params.todoId
    );

    res.status(204).send();
};
```

Now the Controller knows about MongoDB.

Better:

```text
Controller
 ↓
Service
 ↓
Repository
 ↓
Model
```

---

# 30. Common Mistake #2 — Blind `findByIdAndDelete()`

❌

```js
Todo.findByIdAndDelete(todoId);
```

for a user-owned resource.

This doesn't check ownership.

Better:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

when ownership is part of the operation.

---

# 31. Common Mistake #3 — Passing User ID From Client

Never depend on:

```json
{
    "userId": "123"
}
```

for ownership.

Instead:

```text
JWT
 ↓
auth middleware
 ↓
req.user.id
 ↓
Service
 ↓
Repository
```

The authenticated identity should come from your trusted authentication mechanism.

---

# 32. Common Mistake #4 — Returning `true` Without Information

You might write:

```js
const deleteById = async (id) => {
    await Todo.findByIdAndDelete(id);
    return true;
};
```

Now what happens if the Todo didn't exist?

You still return:

```js
true
```

That's not useful.

Better:

```js
return Todo.findByIdAndDelete(id);
```

Then the caller can distinguish:

```text
document
   ↓
deleted

null
   ↓
nothing found
```

---

# 33. Common Mistake #5 — Catching Everything

Avoid:

```js
const deleteById = async (id) => {
    try {
        return await Todo.findByIdAndDelete(id);
    } catch {
        return null;
    }
};
```

Now:

```text
Not found
```

and:

```text
Database failure
```

could both become:

```js
null
```

Those are completely different situations.

We'll cover proper Repository error handling in **13.19**, according to your roadmap.

# 38. Interview Questions

### Q1. What is the purpose of `delete()` in a Repository?

> It encapsulates the database operation used to remove a document.

### Q2. Does `findByIdAndDelete()` check authorization?

> No. It only finds the document by ID and deletes it. Authorization or ownership must be handled separately.

### Q3. How can you make deletion ownership-aware?

Use a filter containing both identifiers:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

### Q4. What happens if no document matches?

The operation can return:

```js
null
```

The Service can then decide how the application should respond.

### Q5. What is hard delete?

> Permanently removing the document from the collection.

### Q6. What is soft delete?

> Keeping the document but marking it as deleted, commonly with something such as `deletedAt`.

# ⭐ Final Mental Model

When you see:

```js
await todoRepository.deleteByOwner(
    todoId,
    userId
);
```

think:

```text
"Service has decided that deletion
should happen."

          ↓

     Repository

          ↓

"Find this resource AND make sure
it belongs to this user."

          ↓

     MongoDB

          ↓

     Delete it
```

### The one sentence to remember:

> **`delete()` is a data-access operation; the Service decides whether deletion is allowed, and an ownership-aware Repository query can ensure the database operation targets the correct user's resource.**

And keep this security pattern in mind:

```text
❌ DELETE BY ID ONLY

Todo.findByIdAndDelete(todoId)


✅ DELETE BY ID + OWNER

Todo.findOneAndDelete({
    _id: todoId,
    userId
})
```

That small difference is one of the foundations of building a secure multi-user backend.
