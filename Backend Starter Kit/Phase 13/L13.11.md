# Phase 13 — Repository Pattern & Data Access

## Lesson 13.11 — Returning Documents

In **13.9**, we learned `update()`.

In **13.10**, we learned `delete()`.

Now we focus on an important Repository question:

> **After a database operation, what should the Repository return to the Service?**

Your Phase 13 roadmap places **13.11 — Returning documents** immediately after update/delete, before selecting fields and preventing password leakage.

---

# 1. Why Returning Documents Matters

Consider:

```js
const user = await userRepository.update(
    userId,
    updateData
);
```

What is `user`?

Is it:

```text
old user?
```

or:

```text
updated user?
```

Similarly:

```js
const deletedUser =
    await userRepository.deleteById(userId);
```

What should `deletedUser` contain?

Understanding this is important because the **Service needs useful information from the Repository**.

---

# 2. Repository Is Not Just "Do Something"

A beginner may think:

```js
await userRepository.update(...);
```

means:

```text
Database updated.
Done.
```

But a Repository usually has a useful contract:

```text
Input
  ↓
Repository
  ↓
Database operation
  ↓
Useful result
  ↓
Service
```

For example:

```js
const updatedUser =
    await userRepository.update(userId, data);
```

The Repository can return the updated document.

---

# 3. `findByIdAndUpdate()` and the Returned Document

Suppose we have:

```js
const updatedUser =
    await User.findByIdAndUpdate(
        userId,
        {
            firstName: "Rahul"
        }
    );
```

One important option is:

```js
{
    new: true
}
```

So:

```js
const updatedUser =
    await User.findByIdAndUpdate(
        userId,
        {
            firstName: "Rahul"
        },
        {
            new: true
        }
    );
```

Now the result represents the updated document.

---

# 4. Why `new: true` Is Important

Imagine the database contains:

```json
{
    "_id": "123",
    "firstName": "Rahul",
    "lastName": "Kumar"
}
```

We update:

```js
{
    firstName: "Rahul Singh"
}
```

Without requesting the new document, the returned result can represent the document **before** the update.

With:

```js
{
    new: true
}
```

we want:

```json
{
    "_id": "123",
    "firstName": "Rahul Singh",
    "lastName": "Kumar"
}
```

So remember:

```text
findByIdAndUpdate()
       +
new: true
       ↓
return updated document
```

---

# 5. Repository Example

Our Repository can therefore have:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data,
        {
            new: true,
            runValidators: true
        }
    );
};
```

Now:

```js
const updatedUser =
    await userRepository.update(
        userId,
        updateData
    );
```

gives the Service the updated document.

---

# 6. Why Should the Service Receive It?

Suppose your API needs to return the updated profile.

Flow:

```text
PATCH /users/me
       ↓
Controller
       ↓
Service
       ↓
Repository
       ↓
MongoDB
       ↓
updated document
       ↓
Service
       ↓
Controller
       ↓
JSON response
```

The Service can receive:

```js
const updatedUser =
    await userRepository.update(
        userId,
        updateData
    );
```

and then return it.

---

# 7. Complete Example

### Repository

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data,
        {
            new: true,
            runValidators: true
        }
    );
};
```

### Service

```js
const updateProfile = async (userId, input) => {
    const updateData = {
        firstName: input.firstName,
        lastName: input.lastName
    };

    const updatedUser =
        await userRepository.update(
            userId,
            updateData
        );

    return updatedUser;
};
```

### Controller

```js
const updateProfile = async (req, res) => {
    const user =
        await userService.updateProfile(
            req.user.id,
            req.body
        );

    res.status(200).json({
        success: true,
        data: user
    });
};
```

The updated document travels back up the layers.

---

# 8. What If the Document Doesn't Exist?

Suppose:

```js
const updatedUser =
    await userRepository.update(
        "does-not-exist",
        data
    );
```

The Repository may return:

```js
null
```

Then the Service can decide what that means:

```js
if (!updatedUser) {
    throw new AppError(
        "User not found",
        404
    );
}
```

This is an important separation:

```text
Repository
→ returns null

Service
→ interprets null

Controller
→ produces HTTP response
```

---

# 9. Same Idea With Delete

In Lesson 13.10, we saw:

```js
const deletedTodo =
    await Todo.findByIdAndDelete(todoId);
```

The result can be:

```text
deleted document
```

or:

```text
null
```

So:

```js
const deletedTodo =
    await todoRepository.deleteById(todoId);

if (!deletedTodo) {
    throw new AppError(
        "Todo not found",
        404
    );
}
```

Again:

```text
Database operation
       ↓
Repository result
       ↓
Service decision
```

---

# 10. Returning a Document vs Returning `true`

Consider this Repository:

```js
const update = async (id, data) => {
    await User.findByIdAndUpdate(id, data);

    return true;
};
```

You only know:

```text
true
```

But you don't have the updated user.

Compare that with:

```js
const update = async (id, data) => {
    return User.findByIdAndUpdate(
        id,
        data,
        {
            new: true
        }
    );
};
```

Now the Service gets:

```text
updated document
```

This is generally more useful.

---

# 11. But Should We Always Return the Entire Document?

**No.**

This leads directly toward the next lessons:

```text
13.12 Selecting fields
13.13 Preventing password leakage
```

Suppose your User document contains:

```text
_id
firstName
lastName
email
password
refreshTokenHash
role
```

Returning the entire document could expose sensitive fields.

For example:

```json
{
    "_id": "123",
    "firstName": "Rahul",
    "email": "rahul@example.com",
    "password": "..."
}
```

That's obviously something we don't want in an API response.

So:

> **Returning a document from the Repository does not automatically mean returning the entire database document to the client.**

---

# 12. Database Result vs API Response

This distinction is extremely important.

```text
MongoDB Document
       ↓
Repository
       ↓
Service
       ↓
Response-safe data
       ↓
Controller
       ↓
Client
```

The database document and API response don't have to be identical.

For example, the database might contain:

```json
{
    "_id": "123",
    "firstName": "Rahul",
    "email": "rahul@example.com",
    "password": "HASH",
    "role": "user"
}
```

The API might return:

```json
{
    "_id": "123",
    "firstName": "Rahul",
    "email": "rahul@example.com"
}
```

The sensitive fields stay internal.

---

# 13. Returning Documents Is a Contract

A Repository method should have a predictable contract.

For example:

```js
userRepository.findById(id)
```

might mean:

```text
Returns:
    User document
or
    null
```

And:

```js
userRepository.update(id, data)
```

might mean:

```text
Returns:
    updated User document
or
    null
```

And:

```js
userRepository.deleteById(id)
```

might mean:

```text
Returns:
    deleted User document
or
    null
```

Having clear expectations makes the Service layer much easier to write.

---

# 14. A Simple Repository Contract

Think about this:

```text
findById(id)
      ↓
User | null

update(id, data)
      ↓
Updated User | null

deleteById(id)
      ↓
Deleted User | null
```

This is a clean mental model.

The exact implementation can change later.

For example, we may add:

```text
projection
pagination
filters
sorting
lean()
transactions
```

without changing the basic idea.

---

# 15. What About `create()`?

Create operations naturally return the created document.

For example:

```js
const user = await User.create(data);
```

`user` is the newly created document.

So:

```text
create()
   ↓
created document
```

This gives us a consistent pattern:

```text
CREATE
   ↓
created document

UPDATE
   ↓
updated document

DELETE
   ↓
deleted document
```

---

# 16. Read Operations Already Return Documents

Consider:

```js
const user =
    await User.findById(userId);
```

This naturally returns:

```text
User document
```

or:

```text
null
```

So Repository operations often follow:

```text
Database operation
       ↓
Document result
```

---

# 17. The Four CRUD Results

A useful table:

|Operation|Repository method|Typical result|
|---|---|---|
|Create|`create()`|Created document|
|Read|`findById()`|Document or `null`|
|Update|`update()`|Updated document or `null`|
|Delete|`deleteById()`|Deleted document or `null`|

This is a very useful mental model for your MERN backend.

---

# 18. Why `null` Is Better Than Fake Success

Suppose:

```js
const update = async (id, data) => {
    await User.findByIdAndUpdate(id, data);

    return true;
};
```

If the user doesn't exist, you might still get:

```text
true
```

That's misleading.

Instead:

```js
const update = async (id, data) => {
    return User.findByIdAndUpdate(
        id,
        data,
        {
            new: true
        }
    );
};
```

Now:

```text
document
    ↓
successful update

null
    ↓
nothing matched
```

This gives the Service enough information to make the correct decision.

---

# 19. Returning Documents and Service Logic

Suppose:

```js
const updatedUser =
    await userRepository.update(
        userId,
        updateData
    );
```

The Service can do:

```js
if (!updatedUser) {
    throw new AppError(
        "User not found",
        404
    );
}

return updatedUser;
```

So the Service doesn't need to perform another query:

```js
// unnecessary in this case
const user =
    await userRepository.findById(userId);
```

The update already gave us the document.

This can avoid an extra database round trip.

---

# 20. Avoid Unnecessary Queries

Bad:

```js
await userRepository.update(
    userId,
    updateData
);

const user =
    await userRepository.findById(userId);

return user;
```

This can mean:

```text
UPDATE
  ↓
MongoDB

then

SELECT
  ↓
MongoDB
```

Two database operations.

If the update operation can return the updated document:

```js
const user =
    await userRepository.update(
        userId,
        updateData
    );

return user;
```

you can get what you need in one operation.

---

# 21. Important: Don't Optimize Blindly

This doesn't mean:

> "Always return documents."

The correct choice depends on what the use case needs.

If you only need to know whether an operation succeeded, you may not need the entire document.

For example:

```text
Delete operation
   ↓
204 No Content
```

The API may not need the deleted document.

The Repository contract should be designed around the application's needs.

---

# 22. Returning Documents and Ownership

Consider:

```js
const todo =
    await todoRepository.deleteByOwner(
        todoId,
        userId
    );
```

If it returns:

```text
Todo document
```

the Service knows:

```text
The matching owned Todo existed
and was deleted.
```

If it returns:

```js
null
```

then:

```text
No Todo matched
```

This makes ownership-aware operations easier to reason about.

---

# 23. Don't Return Mongoose Internals Everywhere

A Repository might return a Mongoose document.

That's okay internally.

But your architecture shouldn't make every upper layer depend heavily on Mongoose-specific behavior.

For example, avoid designing your entire application around things like:

```js
user.$isModified(...)
```

or:

```js
user.populate(...)
```

in every Service.

The Repository is the boundary around database access.

As the project grows, keeping that boundary clean makes it easier to change the data-access implementation.

---

# 24. Document vs Plain JavaScript Object

Mongoose can return a Mongoose Document.

Conceptually:

```text
Mongoose Document
    +
Mongoose methods
    +
document data
```

A plain object is simply:

```js
{
    id: "...",
    name: "Rahul"
}
```

Later, we'll discuss techniques such as:

```js
.lean()
```

when reading documents.

For now, the key point is:

> **A database result can be more than just a plain object; know what your Repository contract returns.**

# 25. Example With `findById()`

Repository:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

Service:

```js
const getProfile = async (userId) => {
    const user =
        await userRepository.findById(userId);

    if (!user) {

            404
```

Controller:

```js
const getProfile = async (req, res) => {

        data: user

```

The document flows:

```text
MongoDB
 ↓
Repository
 ↓
Service
 ↓
Controller
 ↓

```

But before the client receives it, we must think carefully about sensitive fields.

# 27. Practical Repository Example

Here's a clean version for now:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data,
        {
            new: true,
            runValidators: true
        }
    );
};

const deleteById = async (userId) => {
    return User.findByIdAndDelete(userId);
};
```

Then:

```js
const updatedUser =
    await userRepository.update(
        userId,
        updateData
    );

if (!updatedUser) {
    throw new AppError(
        "User not found",
        404
    );
}
```

The Repository returns the result.

The Service interprets it.

---

# 28. Common Mistake #1 — Forgetting `new: true`

You write:

```js
return User.findByIdAndUpdate(
    userId,
    data
);
```

and then:

```js
const user =
    await userRepository.update(...);
```

You expect:

```text
updated user
```

but the returned document may represent the previous state.

When you need the updated document, use:

```js
{
    new: true
}
```

---

# 29. Common Mistake #2 — Querying Again Unnecessarily

❌

```js
await userRepository.update(id, data);

return userRepository.findById(id);
```

If the update operation can return the updated document:

✅

```js
return userRepository.update(
    id,
    data
);
```

One operation can be enough.

---

# 30. Common Mistake #3 — Returning Sensitive Data

Even if the Repository returns:

```json
{
    "_id": "123",
    "email": "rahul@example.com",
    "password": "HASH"
}
```

that doesn't mean the Controller should send it.

You need a safe response shape.

We'll handle this properly in **13.12 and 13.13**.

---

# 31. Common Mistake #4 — Treating `null` as an Error in Repository

Don't automatically do:

```js
if (!user) {
    throw new Error("User not found");
}
```

inside every Repository method.

A missing document is often a normal database result.

The Service can decide:

```text
null
 ↓
business meaning
 ↓
Not found
```

This keeps Repository and Service responsibilities cleaner.

---

# 32. Common Mistake #5 — Assuming Every Operation Needs a Document

Don't force:

```text
Every Repository method
       ↓
return entire document
```

Instead ask:

```text
What does the caller need?
```

For example:

```text
Create
→ probably created document

Get profile
→ document

Update profile
→ updated document

Delete with 204
→ perhaps only success/not-found information
```

The Repository contract should be intentional.

---

# 33. Interview Questions

### Q1. What does `new: true` do?

It makes `findOneAndUpdate()` / `findByIdAndUpdate()` return the updated document.

---

### Q2. Why should a Repository return database results?

So the Service can use the result of the database operation rather than performing unnecessary additional queries.

---

### Q3. What can an update Repository method return?

Typically:

```text
Updated document
or
null
```

depending on whether a matching document exists.

---

### Q4. What can a delete Repository method return?

It can return the deleted document or `null` if nothing matched.

---

### Q5. Should the entire database document always be sent to the client?

**No.**

Sensitive fields should be excluded before producing the API response.

---

# ⭐ Final Mental Model

Think of the Repository as a **database boundary**:

```text
             Service
                │
                │
        "Update this user"
                │
                ▼
           Repository
                │
                ▼
       findByIdAndUpdate()
                │
                ▼
             MongoDB
                │
                ▼
        Updated document
                │
                ▼
           Repository
                │
                ▼
             Service
```

The most important pattern is:

```js
const updatedUser =
    await userRepository.update(
        userId,
        updateData
    );

if (!updatedUser) {
    // Service decides what "not found" means
}
```

And remember:

> **Returning a document from the Repository gives the Service useful database results, but that does not mean the complete database document should automatically be exposed to the client.**
