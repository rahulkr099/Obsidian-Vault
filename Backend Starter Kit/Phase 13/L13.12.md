# Phase 13 — Repository Pattern & Data Access

## Lesson 13.12 — Selecting Fields

This lesson is the bridge between:

- **13.11 — Returning Documents**
    
- **13.13 — Preventing Password Leakage**
    

The main idea is simple:

> **Don't retrieve or return more database fields than the current operation actually needs.**

---

# 1. The Problem

Suppose our `User` document contains:

```js
{
    _id,
    firstName,
    lastName,
    email,
    password,
    role,
    refreshTokenHash,
    resetTokenHash,
    resetTokenExpires,
    createdAt,
    updatedAt
}
```

Now suppose we only need:

```text
firstName
lastName
email
```

Why should we retrieve everything?

We don't need:

```text
password
refreshTokenHash
resetTokenHash
resetTokenExpires
```

So we should select only the fields we need.

---

# 2. What Is Field Selection?

Field selection is also called **projection**.

Instead of:

```js
const user = await User.findById(userId);
```

we can do:

```js
const user = await User.findById(userId)
    .select("firstName lastName email");
```

Now the query is asking for:

```text
firstName
lastName
email
```

rather than the entire document.

---

# 3. Why Is This Important?

There are several reasons.

### 1. Security

Sensitive fields don't need to enter the application layer.

### 2. Performance

You transfer less data from MongoDB.

### 3. Clarity

The Repository clearly communicates what data the operation needs.

### 4. Maintainability

If your User model gains more fields later, they don't automatically become part of every query's result.

---

# 4. Selecting Fields With Mongoose

The common syntax is:

```js
.select("field1 field2 field3")
```

For example:

```js
const user = await User.findById(userId)
    .select("firstName lastName email");
```

Conceptually:

```text
MongoDB document
──────────────────────
_id
firstName       ✓
lastName        ✓
email           ✓
password        ✗
role            ✗
refreshToken    ✗
```

---

# 5. `_id` Is Special

There's an interesting detail.

Suppose:

```js
const user = await User.findById(userId)
    .select("firstName email");
```

Mongoose normally still includes:

```text
_id
```

So you may get:

```js
{
    _id: "...",
    firstName: "Rahul",
    email: "rahul@example.com"
}
```

If you explicitly don't want `_id`:

```js
.select("firstName email -_id");
```

The `-` means exclude.

---

# 6. Include vs Exclude

There are two basic approaches.

### Include fields

```js
.select("firstName lastName email");
```

Meaning:

```text
Give me these fields.
```

### Exclude fields

```js
.select("-password -refreshTokenHash");
```

Meaning:

```text
Give me the normal fields,
but remove these.
```

---

# 7. Which Approach Is Better?

For security-sensitive data, **explicit inclusion** is often easier to reason about.

Instead of:

```js
.select("-password -refreshTokenHash -resetTokenHash")
```

you can say:

```js
.select("firstName lastName email role");
```

This creates an allowlist.

Think:

```text
Only these fields are allowed.
```

That's safer when your schema grows.

---

# 8. Why an Allowlist Is Powerful

Imagine today your User model has:

```text
firstName
lastName
email
password
role
```

You write:

```js
.select("-password");
```

Everything looks fine.

Six months later, another developer adds:

```text
refreshTokenHash
```

Your query may now return it because you never excluded it.

But with:

```js
.select("firstName lastName email role");
```

the new field doesn't automatically appear.

This is one reason explicit field selection is a strong practice.

---

# 9. Repository Example

Instead of:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

we can create a profile-specific method:

```js
const findProfileById = async (userId) => {
    return User.findById(userId)
        .select(
            "firstName lastName email role"
        );
};
```

Now the method itself communicates its purpose:

```text
findProfileById()
        ↓
profile fields
```

---

# 10. Repository Methods Should Have Clear Intent

Compare these:

```js
findById(id)
```

and:

```js
findProfileById(id)
```

The second one tells us:

> "This query is for a profile."

That allows us to make the field selection intentional.

You could have:

```text
findProfileById()
findByEmailForLogin()
findByIdForAdmin()
```

Each can select a different set of fields.

---

# 11. Example: Profile

Suppose the client needs:

```json
{
    "id": "123",
    "firstName": "Rahul",
    "lastName": "Kumar",
    "email": "rahul@example.com"
}
```

Repository:

```js
const findProfileById = async (userId) => {
    return User.findById(userId)
        .select(
            "firstName lastName email"
        );
};
```

The database layer doesn't need to return:

```text
password
refreshTokenHash
resetTokenHash
```

---

# 12. Example: Admin User List

An admin endpoint might need:

```text
_id
firstName
lastName
email
role
createdAt
```

So:

```js
const findUsersForAdmin = async () => {
    return User.find()
        .select(
            "firstName lastName email role createdAt"
        );
};
```

Different use case → different projection.

---

# 13. Example: Login

Login is different.

Authentication needs the password hash.

If your schema uses:

```js
password: {
    type: String,
    select: false
}
```

you can explicitly request it:

```js
const findByEmailForLogin = async (email) => {
    return User.findOne({ email })
        .select("+password");
};
```

This is an important distinction:

```text
Profile query
→ password NOT needed

Login query
→ password hash needed internally
```

---

# 14. Field Selection Is Not Only About Security

It also reduces unnecessary data.

Imagine a document contains:

```text
20 fields
```

but your endpoint needs:

```text
4 fields
```

There is no reason for your application layer to work with all 20.

You can request:

```js
.select("fieldA fieldB fieldC fieldD");
```

This makes the data flow cleaner.

---

# 15. Think About Data Flow

Without selection:

```text
MongoDB
   ↓
20 fields
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
Client
```

With selection:

```text
MongoDB
   ↓
only required fields
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
Client
```

The second flow is much easier to control.

---

# 16. Selecting Fields During Updates

Field selection isn't limited to `find()`.

For example:

```js
const user = await User.findByIdAndUpdate(
    userId,
    updateData,
    {
        new: true
    }
).select(
    "firstName lastName email role"
);
```

Now the updated document returned to the Service is restricted.

This is useful because **13.11 taught us that update operations can return documents**.

Now we're saying:

> "Return the updated document, but only the fields this use case needs."

---

# 17. Combining 13.11 + 13.12

Previously:

```js
const updatedUser =
    await User.findByIdAndUpdate(
        userId,
        updateData,
        {
            new: true
        }
    );
```

Now:

```js
const updatedUser =
    await User.findByIdAndUpdate(
        userId,
        updateData,
        {
            new: true
        }
    ).select(
        "firstName lastName email role"
    );
```

So we have:

```text
13.11
Return updated document
        +
13.12
Select only required fields
```

This combination is much safer.

---

# 18. Excluding Fields

Sometimes you specifically want to exclude something.

For example:

```js
const user = await User.findById(userId)
    .select("-password");
```

You can exclude multiple fields:

```js
const user = await User.findById(userId)
    .select(
        "-password -refreshTokenHash -resetTokenHash"
    );
```

This is useful, but remember the allowlist idea.

---

# 19. Include and Exclude Rules

Be careful when mixing inclusion and exclusion.

Generally, MongoDB projection rules don't let you arbitrarily mix:

```text
include field A
exclude field B
include field C
exclude field D
```

The major exception is `_id`.

For example, this is valid:

```js
.select("firstName email -_id");
```

But don't build complicated projections by mixing inclusion and exclusion without understanding MongoDB's projection rules.

For your application, simple allowlists are usually easier.

---

# 20. Don't Select Sensitive Fields "Just in Case"

Avoid this thinking:

```js
.select(
    "firstName lastName email password role refreshTokenHash"
);
```

because:

> "Maybe we'll need them later."

No.

Retrieve sensitive fields only when the operation genuinely needs them.

This is the principle of **least privilege** applied to data.

---

# 21. Principle of Least Data

A useful rule:

> **Give each operation only the data it needs to do its job.**

For example:

### Profile

```text
firstName
lastName
email
```

### Login

```text
email
password hash
```

### Admin dashboard

```text
firstName
lastName
email
role
createdAt
```

### Password change

```text
password hash
```

Different operations should not automatically receive the same User document.

---

# 22. This Makes Repository Design Better

A Repository shouldn't become:

```js
findUserWithEverything()
```

Instead:

```text
UserRepository

├── findProfileById()
├── findByEmailForLogin()
├── findByIdForAdmin()
├── findForPasswordChange()
└── ...
```

Each method can have a specific data contract.

This becomes especially useful as your backend grows.

---

# 23. Common Mistake #1

❌

```js
const user = await User.findById(id);
```

when the endpoint only needs:

```text
name
email
```

Better:

```js
const user = await User.findById(id)
    .select("firstName lastName email");
```

---

# 24. Common Mistake #2

❌

```js
.select("-password");
```

and assuming you're finished.

There may be other sensitive fields:

```text
refreshTokenHash
resetTokenHash
resetTokenExpires
```

Explicit allowlists are often safer:

```js
.select("firstName lastName email role");
```

---

# 25. Common Mistake #3

❌

```js
const user = await User.findOne({ email })
    .select("email password");

return user;
```

If that `user` is returned from an API endpoint, the password hash can leak.

The query might be correct for authentication, but the **response must still be safe**.

---

# 26. Common Mistake #4

❌ One Repository method for everything:

```js
findUser(id, {
    includePassword: true,
    includeTokens: true,
    includeEverything: true
});
```

This can become difficult to secure.

Prefer clear, purpose-specific Repository methods.

---

# 27. Common Mistake #5

❌ Assuming the Database Schema Equals API Schema

Your MongoDB document may have:

```text
password
refreshTokenHash
resetTokenHash
```

Your public API doesn't need those fields.

Remember:

```text
Database model
       ≠
API response model
```

---

# 28. Practical Pattern for Your Backend

A good pattern to carry forward is:

### Repository

```js
const findProfileById = async (userId) => {
    return User.findById(userId)
        .select(
            "firstName lastName email role"
        );
};
```

### Service

```js
const getProfile = async (userId) => {
    const user =
        await userRepository.findProfileById(
            userId
        );

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return {
        id: user._id,
        firstName: user.firstName,
        lastName: user.lastName,
        email: user.email,
        role: user.role
    };
};
```

### Controller

```js
const getProfile = async (req, res) => {
    const user =
        await userService.getProfile(
            req.user.id
        );

    res.status(200).json({
        success: true,
        data: user
    });
};
```

Notice how each layer has a clear job.

---

# 29. Repository → Service → Controller

Keep this mental model:

```text
Repository
    ↓
"What data should I get?"

Service
    ↓
"What data should this use case return?"

Controller
    ↓
"How should this become an HTTP response?"
```

This is much cleaner than allowing the Controller to directly decide database projections everywhere.

Selecting only specific fields from a MongoDB document instead of retrieving the entire document.

It improves:
