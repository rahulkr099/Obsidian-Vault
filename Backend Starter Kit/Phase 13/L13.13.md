# Phase 13 — Repository Pattern & Data Access

## Lesson 13.13 — Preventing Password Leakage

This lesson is extremely important because we just learned in **13.11** that Repository methods can return complete database documents.

Now we have a problem:

```text
MongoDB User Document
        ↓
Repository
        ↓
Service
        ↓
Controller
        ↓
JSON Response
```

What if the User document contains:

```text
password
refreshTokenHash
resetTokenHash
```

We **must not accidentally send those fields to the frontend**.

Your Phase 13 roadmap specifically places **13.13 — Preventing password leakage** immediately after **13.12 — Selecting fields**.

---

# 1. The Problem

Imagine your MongoDB User document looks like:

```js
{
    _id: "123",
    firstName: "Rahul",
    lastName: "Kumar",
    email: "rahul@example.com",

    password: "$2b$12$....",

    role: "user",

    refreshTokenHash: "...",
    resetTokenHash: "...",
    resetTokenExpires: "..."
}
```

Now imagine this:

```js
const user = await userRepository.findById(userId);

res.json({
    success: true,
    data: user
});
```

If `user` contains the password hash, you may accidentally send:

```json
{
    "success": true,
    "data": {
        "_id": "123",
        "firstName": "Rahul",
        "email": "rahul@example.com",
        "password": "$2b$12$...",
        "role": "user"
    }
}
```

That's **password leakage**.

Even though it's a hash rather than the original password, it is still sensitive information and should not be exposed.

---

# 2. Very Important Rule

Remember this:

> **A password hash is not a password, but it is still sensitive and must be protected.**

Never think:

```text
"Nobody can see the original password,
so it's okay to send the hash."
```

No.

The hash belongs on the server side.

---

# 3. What Should the Client Receive?

Instead of:

```json
{
    "_id": "123",
    "firstName": "Rahul",
    "email": "rahul@example.com",
    "password": "$2b$12$...",
    "refreshTokenHash": "...",
    "resetTokenHash": "..."
}
```

we want something like:

```json
{
    "_id": "123",
    "firstName": "Rahul",
    "lastName": "Kumar",
    "email": "rahul@example.com",
    "role": "user"
}
```

So:

```text
Database representation
        ≠
API representation
```

This is a very important backend concept.

---

# 4. The First Defense — Select Only Needed Fields

This connects directly to Lesson 13.12.

Instead of retrieving everything:

```js
User.findById(userId);
```

we can select specific fields.

For example:

```js
User.findById(userId).select(
    "firstName lastName email role"
);
```

Now MongoDB/Mongoose gives us only the fields we actually want.

Conceptually:

```text
User document
────────────────────────
_id
firstName       ✓
lastName        ✓
email           ✓
password        ✗
role            ✓
refreshToken    ✗
resetToken      ✗
```

This is called **field projection/selection**.

---

# 5. Why Selecting Fields Is Powerful

Suppose the model contains:

```text
_id
firstName
lastName
email
password
role
refreshTokenHash
resetTokenHash
resetTokenExpires
createdAt
updatedAt
```

But the profile endpoint only needs:

```text
firstName
lastName
email
```

Then don't retrieve everything and clean it afterward if you can simply select what you need.

For example:

```js
const findProfileById = async (userId) => {
    return User.findById(userId)
        .select("firstName lastName email");
};
```

Now the Repository has a very clear purpose:

> "For this query, return only profile fields."

---

# 6. But There's a Problem With "Always Select These Fields"

Authentication sometimes **needs the password hash**.

For example, during login:

```text
Email + password
       ↓
Find user
       ↓
Get password hash
       ↓
bcrypt.compare()
       ↓
Login success/failure
```

So you can't globally say:

```text
"Never retrieve password."
```

The server sometimes needs it.

The correct rule is:

> **Never expose sensitive fields to the client, but retrieve them internally when a trusted server-side operation actually needs them.**

This distinction is extremely important.

---

# 7. Login Example

Suppose the user submits:

```json
{
    "email": "rahul@example.com",
    "password": "mypassword"
}
```

The Service needs to compare:

```text
submitted password
        ↓
bcrypt.compare()
        ↓
stored password hash
```

So the Repository may intentionally return:

```js
{
    email,
    password
}
```

to the **authentication Service**.

But that doesn't mean the Controller should return that same object.

---

# 8. Two Different Uses of the Same User

Think about these two operations.

### Login

```text
Service needs:
email
password hash
role
_id
```

### Get Profile

```text
Client needs:
_id
firstName
lastName
email
role
```

Different use cases need different fields.

Therefore:

```text
Repository query
       ↓
purpose-specific fields
```

is a much better approach.

---

# 9. Bad Architecture

Avoid this:

```js
const user = await userRepository.findById(id);

return user;
```

and then everywhere assume:

```text
"Someone else will remove password later."
```

That's fragile.

Imagine one new endpoint:

```js
res.json(user);
```

Now the password hash leaks.

---

# 10. Defense in Depth

A stronger architecture uses multiple protections:

```text
             User Data
                 │
                 ▼
          Repository Query
                 │
          Select safe fields
                 │
                 ▼
              Service
                 │
          Build safe output
                 │
                 ▼
            Controller
                 │
                 ▼
              Client
```

So even if one layer changes, there are additional protections.

---

# 11. Mongoose Schema-Level Protection

Mongoose also allows you to configure fields so they aren't selected by default.

For example:

```js
password: {
    type: String,
    required: true,
    select: false
}
```

Now:

```js
User.findById(userId);
```

will normally exclude the password.

This is a powerful default.

---

# 12. What Does `select: false` Mean?

Consider:

```js
const userSchema = new Schema({
    email: {
        type: String,
        required: true,
        unique: true
    },

    password: {
        type: String,
        required: true,
        select: false
    }
});
```

Normally:

```js
User.findOne({
    email
});
```

will not include:

```text
password
```

This creates a secure default.

---

# 13. How Do We Get the Password for Login Then?

If the password is:

```js
select: false
```

authentication can explicitly request it.

Conceptually:

```js
User.findOne({
    email
}).select("+password");
```

The `+` means:

> Explicitly include this normally excluded field.

So:

```text
Normal user query
        ↓
password excluded

Authentication query
        ↓
explicitly request password
```

This is an excellent pattern.

---

# 14. Why This Is Safer

Imagine six developers are working on the project.

One writes:

```js
const user = await User.findById(id);
```

Because the schema says:

```js
select: false
```

the password doesn't automatically appear.

That's much safer than depending on every developer remembering:

```js
.select("-password")
```

every single time.

---

# 15. Default Deny Is Better

Think about security like this:

### Dangerous default

```text
Return everything
 ↓
Developer must remember to remove secrets
```

### Safer default

```text
Hide secrets
 ↓
Developer must explicitly request them
```

This is called a **secure-by-default mindset**.

---

# 16. Which Fields Should Be Protected?

For your architecture, sensitive User fields can include things such as:

```text
password
refreshTokenHash
resetTokenHash
resetTokenExpires
```

Depending on the application, other fields may also be sensitive.

Your source's User model planning explicitly includes:

```text
password
refreshTokenHash
resetTokenHash
resetTokenExpires
```

which is why these should be treated carefully.

---

# 17. Password vs Refresh Token Hash

Don't make the mistake of protecting only:

```text
password
```

You might remember:

```js
password: {
    select: false
}
```

but forget:

```text
refreshTokenHash
```

Then you could accidentally return:

```json
{
    "email": "rahul@example.com",
    "refreshTokenHash": "..."
}
```

That's also sensitive.

---

# 18. Example Secure User Schema

Conceptually:

```js
const userSchema = new Schema({
    firstName: {
        type: String,
        required: true
    },

    lastName: {
        type: String,
        required: true
    },

    email: {
        type: String,
        required: true,
        unique: true
    },

    password: {
        type: String,
        required: true,
        select: false
    },

    role: {
        type: String,
        required: true
    },

    refreshTokenHash: {
        type: String,
        select: false
    },

    resetTokenHash: {
        type: String,
        select: false
    },

    resetTokenExpires: {
        type: Date,
        select: false
    }
});
```

Now sensitive fields are excluded from normal queries.

---

# 19. Why This Is Better Than Only Cleaning the Response

Suppose you do:

```js
const user = await User.findById(id);

delete user.password;

res.json(user);
```

This is not ideal.

Why?

Because you've already retrieved the sensitive data.

And developers may forget to remove:

```text
refreshTokenHash
resetTokenHash
resetTokenExpires
```

It's better to prevent unnecessary selection in the first place.

---

# 20. But Don't Rely Only on `select: false`

`select: false` is a strong safety mechanism, but it isn't the only layer.

You should still think about:

```text
field selection
response DTOs
serialization
Service output
Controller response
```

For example:

```js
return {
    id: user._id,
    firstName: user.firstName,
    lastName: user.lastName,
    email: user.email
};
```

Now your API response is explicitly defined.

---

# 21. Database Document vs DTO

A useful professional concept is **DTO**:

> Data Transfer Object

Suppose MongoDB gives:

```js
user = {
    _id,
    firstName,
    lastName,
    email,
    role
};
```

The Service can construct:

```js
const userResponse = {
    id: user._id,
    firstName: user.firstName,
    lastName: user.lastName,
    email: user.email
};
```

Then:

```text
MongoDB document
       ↓
Repository
       ↓
Service
       ↓
DTO / response object
       ↓
Controller
       ↓
Client
```

This gives you explicit control.

---

# 22. Why Not Just Send the Mongoose Document?

Because your database schema is an internal implementation detail.

Your API should define its own contract.

For example, your database might eventually change:

```text
firstName
lastName
```

into:

```text
profile: {
    firstName,
    lastName
}
```

You don't necessarily want the frontend API contract to change.

A Service/DTO layer can hide those database changes.

---

# 23. A Safe Profile Service

For example:

```js
const getProfile = async (userId) => {
    const user =
        await userRepository.findProfileById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return {
        id: user._id,
        firstName: user.firstName,
        lastName: user.lastName,
        email: user.email,
        role: user.role
    };
};
```

Now the Service returns only what the API needs.

---

# 24. Repository

The Repository can make the query even safer:

```js
const findProfileById = async (userId) => {
    return User.findById(userId)
        .select(
            "firstName lastName email role"
        );
};
```

Now:

```text
Repository
→ only safe fields

Service
→ explicit response shape

Controller
→ HTTP response
```

This is excellent defense in depth.

---

# 25. Authentication Repository

But login needs something different:

```js
const findByEmailForLogin = async (email) => {
    return User.findOne({ email })
        .select(
            "+password email role"
        );
};
```

Notice the method name:

```text
findByEmailForLogin()
```

instead of:

```text
findByEmail()
```

This communicates the purpose.

The Repository knows:

> This query is specifically for authentication.

---

# 26. Why Purpose-Specific Methods Are Useful

Compare:

```js
userRepository.findById(id);
```

with:

```js
userRepository.findByIdForProfile(id);
```

and:

```js
userRepository.findByEmailForLogin(email);
```

Different operations have different data requirements.

This is often safer than having one giant method:

```js
findUser({
    includePassword: true,
    includeTokens: true,
    includeEverything: true
});
```

That kind of flexible API can become dangerous.

---

# 27. A Useful Pattern

Think:

```text
USER REPOSITORY
│
├── findById()
│     ↓
│   safe fields
│
├── findByEmailForLogin()
│     ↓
│   password + required auth fields
│
├── findProfileById()
│     ↓
│   profile fields
│
└── updatePassword()
      ↓
    password-related operation
```

Each method has a clear purpose.

---

# 28. Don't Return Password After Login

Suppose login succeeds.

The Service does:

```text
email
 +
password
 ↓
find user
 ↓
get password hash
 ↓
bcrypt.compare()
 ↓
generate tokens
```

After comparison, the password hash is **not needed in the response**.

Don't do:

```js
return user;
```

if `user` contains:

```text
password
```

Instead:

```js
return {
    user: {
        id: user._id,
        email: user.email,
        role: user.role
    },
    accessToken
};
```

---

# 29. Login Response

A safer response might look like:

```json
{
    "success": true,
    "data": {
        "user": {
            "id": "123",
            "email": "rahul@example.com",
            "role": "user"
        },
        "accessToken": "..."
    }
}
```

Not:

```json
{
    "user": {
        "_id": "123",
        "email": "rahul@example.com",
        "password": "$2b$...",
        "refreshTokenHash": "..."
    }
}
```

---

# 30. Password Hash Should Stay Server-Side

Think of this boundary:

```text
                 SERVER
────────────────────────────────
password
   ↓
bcrypt
   ↓
password hash
   ↓
MongoDB

                 ❌
          NEVER CROSS THIS
             BOUNDARY
                 ❌

                 CLIENT
```

The client doesn't need the hash.

The client doesn't need the stored refresh token hash.

The client doesn't need password-reset token hashes.

---

# 31. Another Important Issue: Logs

Password leakage isn't only about API responses.

You can accidentally leak secrets through logs.

Bad:

```js
console.log("User:", user);
```

If `user` contains:

```text
password
refreshTokenHash
resetTokenHash
```

your logs now contain sensitive information.

So:

> **Never log complete User documents blindly.**

This connects with the observability architecture in your roadmap, where sensitive data in logs is specifically part of the logging phase.

---

# 32. Error Messages Can Also Leak Information

Be careful with authentication.

Avoid unnecessarily revealing:

```text
"Email exists but password is wrong."
```

versus:

```text
"Email doesn't exist."
```

Depending on your authentication design, a generic message such as:

```text
"Invalid email or password."
```

can reduce account-enumeration risk.

This is broader authentication/security design, but it's another example of:

```text
Don't expose internal information unnecessarily.
```

---

# 33. Password Leakage Can Happen in Debugging

Imagine:

```js
console.log(req.body);
```

during signup.

Request:

```json
{
    "email": "rahul@example.com",
    "password": "mypassword"
}
```

Now your logs contain the user's **plain password**.

That's even worse.

So be careful with:

```text
req.body
user
req.headers
cookies
tokens
```

when logging.

Bad:


# 45. Interview Questions

### Q1. Why shouldn't a password hash be returned to the client?

Because it is sensitive authentication data and provides no legitimate client-side benefit.

---

### Q2. What does `select: false` do?

It prevents a Mongoose field from being included in normal query results unless it is explicitly selected.

---

### Q3. How can authentication retrieve a password field marked `select: false`?

Explicitly request it, for example:

```js
.select("+password")
```

---

### Q4. Should the password ever be sent in an API response?

**No.**

---

### Q5. Should only the password be protected?

No. Other sensitive authentication fields, such as refresh-token and password-reset hashes, should also be protected.

---

### Q6. Why shouldn't we return the complete Mongoose User document?

Because the database document may contain internal or sensitive fields that aren't part of the API's public contract.

# ⭐ Final Mental Model

There are **three different concepts** you should keep separate:

```text
1. What is stored?
        ↓
MongoDB document

2. What does the server need?
        ↓
Repository projection

3. What does the client need?
        ↓
Safe API response
```

So:

```text
MongoDB
   │
   │  Full document
   ▼
Repository
   │
   │  Only required fields
   ▼
Service
   │
   │  Safe response object
   ▼
Controller
   │
   ▼
Client
```

### The rule to remember:

> **Sensitive fields should be hidden by default, explicitly retrieved only when the server needs them, and never included in client-facing responses.**

For your User model, think especially about:

```text
password
refreshTokenHash
resetTokenHash
resetTokenExpires
```

Your starter's planned authentication architecture relies on storing password/token hashes server-side, not exposing them to the client.
