# Phase 13 — Repository Pattern & Data Access

## Lesson 13.14 — Repository Parameters

We have now covered:

```text
13.11 → Returning documents
13.12 → Selecting fields
13.13 → Preventing password leakage
13.14 → Repository parameters
```

The next question is:

> **How should we pass information into Repository methods?**

This sounds simple, but good parameter design makes a Repository much easier to use, test, and maintain.

Your roadmap explicitly lists **13.14 Repository parameters** before moving into ownership queries, pagination, filtering, and sorting.

---

# 1. What Are Repository Parameters?

Consider:

```js
const user = await userRepository.findById(userId);
```

Here:

```text
findById()
    ↑
    │
 userId
```

`userId` is a **parameter**.

Another example:

```js
await userRepository.update(userId, updateData);
```

There are two parameters:

```text
userId
updateData
```

So:

```text
Repository method
       ↓
accepts parameters
       ↓
uses them to build database query
```

---

# 2. The Repository's Job

Remember the boundary:

```text
Service
   ↓
"I need this data."

Repository
   ↓
"I need these parameters to query MongoDB."

MongoDB
   ↓
"Here is the result."
```

The Service shouldn't need to know the exact MongoDB query.

For example, Service:

```js
const user =
    await userRepository.findById(userId);
```

Repository:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

The Service only knows:

```text
findById(userId)
```

It doesn't care whether the Repository uses:

```js
User.findById(userId)
```

or:

```js
User.findOne({
    _id: userId
})
```

---

# 3. Simple Parameters Are Good

A basic Repository method can be:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

This is easy to understand.

Input:

```text
userId
```

Output:

```text
User | null
```

That's a clean contract.

---

# 4. Multiple Parameters

Suppose we need to update a user:

```js
const update = async (userId, updateData) => {
    return User.findByIdAndUpdate(
        userId,
        updateData,
        {
            new: true
        }
    );
};
```

Now:

```text
update(
    userId,
    updateData
)
```

means:

```text
Which document?
      ↓
   userId

What changes?
      ↓
 updateData
```

This is perfectly reasonable.

---

# 5. Another Example: Create

Create doesn't need an ID:

```js
const create = async (userData) => {
    return User.create(userData);
};
```

Service:

```js
const user =
    await userRepository.create({
        firstName,
        lastName,
        email,
        password
    });
```

Repository:

```text
userData
   ↓
User.create()
```

Again, simple.

---

# 6. The Problem With Too Many Parameters

Imagine this:

```js
const findUsers = async (
    page,
    limit,
    sortBy,
    sortOrder,
    search,
    role,
    status,
    createdAfter,
    createdBefore
) => {
    // ...
};
```

Now calling it becomes ugly:

```js
await userRepository.findUsers(
    1,
    20,
    "createdAt",
    "desc",
    "rahul",
    "user",
    "active",
    startDate,
    endDate
);
```

It's difficult to remember which value belongs to which parameter.

This is where an **options object** becomes useful.

---

# 7. Use an Options Object for Complex Queries

Instead:

```js
const findUsers = async ({
    page,
    limit,
    sortBy,
    sortOrder,
    search,
    role,
    status
}) => {
    // ...
};
```

Then:

```js
await userRepository.findUsers({
    page: 1,
    limit: 20,
    sortBy: "createdAt",
    sortOrder: "desc",
    search: "rahul",
    role: "user",
    status: "active"
});
```

Much easier to read.

---

# 8. Simple Rule

Use:

### Individual parameters

When the method is simple:

```js
findById(userId)
```

```js
deleteById(todoId)
```

```js
findByEmail(email)
```

### Options object

When the method has several optional or related parameters:

```js
findMany({
    page,
    limit,
    filter,
    sort,
    fields
})
```

This is a very useful convention.

---

# 9. Don't Pass `req` Into the Repository

This is a common architectural mistake.

❌ Don't do:

```js
userRepository.findUser(req);
```

Why?

Because the Repository should not know about Express.

`req` belongs to the HTTP layer.

Remember:

```text
Controller
    ↓
HTTP concepts

Service
    ↓
Business concepts

Repository
    ↓
Data-access concepts
```

Passing `req` deep into the application mixes these layers.

---

# 10. Don't Pass `res` Either

Avoid:

```js
userRepository.createUser(req, res);
```

The Repository should never be responsible for:

```text
HTTP response
status codes
cookies
headers
Express request
```

It should focus on data access.

---

# 11. Don't Pass the Entire Request When You Need One Value

Suppose you need the authenticated user's ID.

Bad:

```js
await todoRepository.findById(req);
```

Better:

```js
await todoRepository.findById(
    req.user.id
);
```

Now the Repository receives exactly what it needs:

```text
userId
```

This is called **passing the minimum required data**.

---

# 12. Service Extracts the Information

Suppose the request is:

```text
GET /todos/:todoId
```

The Controller might receive:

```js
req.params.todoId
req.user.id
```

The Service can do:

```js
const getTodo = async (todoId, userId) => {
    return todoRepository.findByIdAndOwner(
        todoId,
        userId
    );
};
```

The Repository receives:

```text
todoId
userId
```

Not:

```text
req
```

---

# 13. This Becomes Important in Ownership Queries

Your roadmap's next lesson is:

```text
13.15 Ownership queries
```

So we're preparing for something like:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

The Repository might be:

```js
const findByIdAndOwner = async (
    todoId,
    userId
) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

Notice the parameters:

```text
todoId
userId
```

These are **domain/data values**, not HTTP objects.

---

# 14. Why This Is Better

Controller:

```text
HTTP
 ↓
req.params.todoId
req.user.id
```

Service:

```text
todoId
userId
```

Repository:

```text
todoId
userId
 ↓
MongoDB query
```

Each layer receives the type of information it actually needs.

---

# 15. Repository Parameters Should Be Database-Relevant

A good parameter:

```js
findByEmail(email)
```

A good parameter:

```js
findById(userId)
```

A good parameter:

```js
findByIdAndOwner(todoId, userId)
```

A good parameter:

```js
update(todoId, updateData)
```

These describe data-access operations.

---

# 16. Avoid Business Decisions Inside Parameters

Suppose the Service has:

```js
const canEdit =
    user.role === "admin" ||
    todo.userId === user.id;
```

Don't turn the Repository into:

```js
findTodo(
    todoId,
    user,
    "maybe-admin",
    "some-business-rule"
);
```

Instead, the Repository should receive the actual data needed to enforce the query.

For example:

```js
findByIdAndOwner(todoId, userId)
```

Authorization decisions belong primarily to the Service/authorization layer.

The Repository can enforce ownership through the query.

---

# 17. Avoid Passing Domain Objects Unnecessarily

Suppose:

```js
const user = await userRepository.findById(userId);
```

Then you want to find todos.

You might be tempted to do:

```js
todoRepository.findByUser(user);
```

But if the Repository only needs the ID:

```js
todoRepository.findByUserId(user._id);
```

is clearer.

Instead of:

```text
User object
   ↓
Repository
```

we pass:

```text
userId
   ↓
Repository
```

Again:

> **Pass the minimum required data.**

---

# 18. What About Update Data?

For updates, an object makes sense:

```js
const update = async (userId, updateData) => {
    return User.findByIdAndUpdate(
        userId,
        updateData,
        {
            new: true
        }
    );
};
```

Here:

```text
userId
    ↓
Which record?

updateData
    ↓
What should change?
```

That's a clean parameter contract.

---

# 19. Don't Pass the Entire `User` Object to Update

Instead of:

```js
userRepository.update(user);
```

prefer:

```js
userRepository.update(
    userId,
    updateData
);
```

Why?

Because:

```text
User object
```

may contain fields that shouldn't be updated:

```text
password
role
refreshTokenHash
createdAt
```

An explicit `updateData` object is safer.

---

# 20. Even Better: Build Update Data in the Service

Suppose the user sends:

```json
{
    "firstName": "Rahul",
    "role": "admin"
}
```

The Service should decide what is allowed:

```js
const updateData = {
    firstName: input.firstName
};
```

Then:

```js
await userRepository.update(
    userId,
    updateData
);
```

So:

```text
Client input
    ↓
Validation
    ↓
Service decides allowed fields
    ↓
updateData
    ↓
Repository
```

This prevents clients from controlling arbitrary database fields.

---

# 21. Repository Shouldn't Trust Raw Client Input

This is important.

Don't do:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data
    );
};
```

and blindly pass:

```js
req.body
```

from the Controller.

Instead:

```text
req.body
   ↓
validation
   ↓
service
   ↓
allowed updateData
   ↓
repository
```

The Repository receives already-prepared data.

---

# 22. Options Objects Become Important Later

We're going to reach:

```text
13.16 Pagination repositories
13.17 Filtering repositories
13.18 Sorting repositories
```

At that point, parameters can become complex.

For example:

```js
findMany({
    page,
    limit,
    filter,
    sort
});
```

This is much cleaner than:

```js
findMany(
    page,
    limit,
    search,
    role,
    status,
    sortBy,
    sortOrder
);
```

So learn this pattern now.

---

# 23. Example: Pagination Parameters

Eventually:

```js
const findMany = async ({
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    return User.find()
        .skip(skip)
        .limit(limit);
};
```

Call:

```js
await userRepository.findMany({
    page: 2,
    limit: 20
});
```

This is easy to extend later.

---

# 24. Example: Filtering

Later we might have:

```js
await userRepository.findMany({
    page: 1,
    limit: 20,
    filter: {
        role: "user",
        status: "active"
    }
});
```

Repository:

```js
const findMany = async ({
    page = 1,
    limit = 20,
    filter = {}
}) => {
    // query
};
```

Now the method can grow without adding a dozen positional parameters.

---

# 25. Example: Sorting

Eventually:

```js
await userRepository.findMany({
    page: 1,
    limit: 20,
    sort: {
        field: "createdAt",
        order: "desc"
    }
});
```

Again:

```text
options object
      ↓
easy to extend
```

This is why you'll see this style frequently in mature backend codebases.

---

# 26. But Don't Use Options Objects Everywhere

Don't write:

```js
findById({
    userId
});
```

when the method only needs one value.

This:

```js
findById(userId);
```

is simpler.

You don't want unnecessary abstraction.

A good principle:

> **Use the simplest parameter structure that clearly expresses the operation.**

---

# 27. Good Examples

### One parameter

```js
findById(userId)
```

### Two meaningful parameters

```js
update(userId, updateData)
```

### Ownership query

```js
findByIdAndOwner(todoId, userId)
```

### Complex query

```js
findMany({
    page,
    limit,
    filter,
    sort
})
```

This is a very practical pattern.

---

# 28. Parameter Naming Matters

Prefer:

```js
userId
todoId
email
updateData
filter
sort
page
limit
```

Avoid vague names:

```js
id
data
obj
value
thing
params
```

unless the context genuinely makes them obvious.

For example:

```js
update(userId, updateData)
```

is much clearer than:

```js
update(id, data)
```

especially in a large codebase.

---

# 29. Parameters Should Describe Their Meaning

Compare:

```js
findById(id)
```

with:

```js
findById(userId)
```

If this Repository is specifically a User Repository, both can work.

But:

```js
findById(userId)
```

communicates the domain meaning.

Similarly:

```js
findByIdAndOwner(todoId, userId)
```

is immediately understandable.

---

# 30. Don't Mutate Parameters

Avoid doing something like:

```js
const findMany = async (options) => {
    options.page = Number(options.page);
    options.limit = Number(options.limit);

    // ...
};
```

Ideally, validation and normalization should happen before the Repository.

For example:

```text
Request
 ↓
Validation
 ↓
Normalization
 ↓
Service
 ↓
Repository
```

The Repository should receive clean values.

---

# 31. Repository Parameters Should Be Predictable

If you call:

```js
userRepository.findById(userId)
```

you should know:

```text
Input:
userId

Output:
User | null
```

If you call:

```js
userRepository.update(userId, updateData)
```

you should know:

```text
Input:
userId
updateData

Output:
Updated User | null
```

Clear contracts make testing much easier.

---

# 32. Testing Becomes Easier

Consider:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

A test can easily say:

```text
Given userId
    ↓
Repository queries that ID
```

But if your method accepts:

```js
findById(req, res, next, options, context)
```

testing becomes unnecessarily complicated.

Simple parameters create simple tests.

---

# 33. Repository Parameters vs Service Parameters

This distinction is important.

Service:

```js
userService.updateProfile(
    userId,
    input
);
```

Repository:

```js
userRepository.update(
    userId,
    updateData
);
```

They don't necessarily have to be identical.

The Service can transform:

```text
input
```

into:

```text
updateData
```

before calling the Repository.

---

# 34. Example of the Transformation

Client:

```json
{
    "firstName": "Rahul",
    "role": "admin",
    "password": "..."
}
```

Service:

```js
const updateData = {
    firstName: input.firstName
};
```

Repository:

```js
await userRepository.update(
    userId,
    updateData
);
```

Notice:

```text
Client input
     ↓
Service filters business-allowed fields
     ↓
Repository receives safe update data
```

This is exactly the separation we want.

---

# 35. Common Mistake #1 — Passing `req`

❌

```js
userRepository.findById(req);
```

✅

```js
userRepository.findById(
    req.user.id
);
```

---

# 36. Common Mistake #2 — Passing `req.body` Directly

❌

```js
userRepository.update(
    req.params.id,
    req.body
);
```

This gives the client too much control.

Better:

```js
const updateData = {
    firstName: req.body.firstName,
    lastName: req.body.lastName
};

await userRepository.update(
    userId,
    updateData
);
```

In your architecture, the Service should normally prepare the data.

---

# 37. Common Mistake #3 — Too Many Positional Arguments

❌

```js
findMany(
    page,
    limit,
    search,
    role,
    status,
    sortBy,
    sortOrder,
    startDate,
    endDate
);
```

Better:

```js
findMany({
    page,
    limit,
    search,
    role,
    status,
    sortBy,
    sortOrder,
    startDate,
    endDate
});
```

---

# 38. Common Mistake #4 — Options Object for Everything

❌

```js
findById({
    userId
});
```

when this is all you need:

```js
findById(userId);
```

Don't create complexity where none is needed.

---

# 39. Common Mistake #5 — Passing Business Objects Everywhere

Avoid:

```js
repository.update(user);
```

when the Repository only needs:

```text
userId
updateData
```

Keep the boundary explicit.

# 40. A Clean Repository API

For your User Repository, imagine:

```js
const findById = async (userId) => {};

const findByEmail = async (email) => {};

const create = async (userData) => {};

const update = async (
    userId,
    updateData
) => {};

const deleteById = async (userId) => {};
```

Very easy to understand.

For Todo:

```js
const findByIdAndOwner = async (
    todoId,
    userId
) => {};

const create = async (todoData) => {};

const update = async (
    todoId,
    userId,
    updateData
) => {};
```

Now ownership is already part of the data-access contract.

# ⭐ Final Mental Model

Think of Repository parameters as a **clean contract**:

```text
                 SERVICE
                    │
                    │
             userId, updateData
                    │
                    ▼
               REPOSITORY
                    │
              translates
                    │
                    ▼
              MongoDB query
```

### Simple operation:

```js
findById(userId)
```

### Multiple required values:

```js
update(userId, updateData)
```

### Ownership:

```js
findByIdAndOwner(todoId, userId)
```

### Complex optional query:

```js
findMany({
    page,
    limit,
    filter,
    sort
})
```

And the most important rule:

> **A Repository should receive clean, meaningful data-access parameters—not Express `req`/`res`, raw HTTP objects, or unnecessary domain objects.**

This gives us a clean transition into **Lesson 13.15 — Ownership Queries**.
