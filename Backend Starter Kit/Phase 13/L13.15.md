# Phase 13 — Repository Pattern & Data Access

## Lesson 13.15 — Ownership Queries

This is one of the **most important Repository lessons** because it connects data access with **authorization and data isolation**.

We just learned in **13.14** that Repository methods should receive clean parameters such as:

```js
todoId
userId
```

Now we're going to use those parameters to answer an important question:

> **Does this record actually belong to this user?**

---

# 1. The Problem

Imagine our application has:

```text
User A
 ├── Todo 1
 ├── Todo 2
 └── Todo 3

User B
 ├── Todo 4
 └── Todo 5
```

Suppose User A sends:

```http
GET /todos/4
```

Todo `4` belongs to User B.

Should User A be allowed to receive it?

**No.**

But this query is dangerous:

```js
Todo.findById(todoId);
```

It checks only:

```text
Does Todo 4 exist?
```

It does **not** check:

```text
Does Todo 4 belong to User A?
```

That's the problem ownership queries solve.

---

# 2. The Basic Ownership Query

Instead of:

```js
Todo.findById(todoId);
```

use:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Now MongoDB must satisfy **both conditions**:

```text
_id === todoId
AND
userId === currentUserId
```

So:

```text
Todo exists?
        +
Belongs to this user?
        ↓
       Yes
        ↓
     Return it
```

---

# 3. Why This Is Better

Suppose:

```text
todoId = 100
userId = A
```

Database:

```text
Todo 100 → owner A
```

Query:

```js
Todo.findOne({
    _id: 100,
    userId: A
});
```

Result:

```text
Todo 100
```

Now:

```text
todoId = 100
userId = B
```

Query:

```js
Todo.findOne({
    _id: 100,
    userId: B
});
```

Result:

```text
null
```

Even though Todo `100` exists, it doesn't belong to User B.

That's exactly what we want.

---

# 4. Ownership Is a Data-Access Rule

This is a very important architectural idea.

Suppose the Service says:

```js
const todo = await todoRepository.findById(todoId);
```

and later:

```js
if (todo.userId !== req.user.id) {
    throw new AppError("Forbidden", 403);
}
```

This can work, but we're first retrieving the document.

A stronger pattern is:

```js
const todo =
    await todoRepository.findByIdAndOwner(
        todoId,
        userId
    );
```

Repository:

```js
const findByIdAndOwner = async (
    todoId,
    userId
) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

Now ownership is part of the query itself.

---

# 5. Repository Method

A clean method could be:

```js
const findByIdAndOwner = async (
    todoId,
    userId
) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

The parameters have clear meaning:

```text
todoId
   ↓
Which Todo?

userId
   ↓
Which owner?
```

This directly builds on Lesson 13.14.

---

# 6. Controller → Service → Repository

Imagine:

```http
GET /todos/:todoId
```

The Controller has access to:

```js
req.params.todoId
req.user.id
```

The Controller should pass the necessary values to the Service:

```js
const todo = await todoService.getTodo(
    req.params.todoId,
    req.user.id
);
```

Service:

```js
const getTodo = async (
    todoId,
    userId
) => {
    const todo =
        await todoRepository.findByIdAndOwner(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

Repository:

```js
const findByIdAndOwner = async (
    todoId,
    userId
) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

The flow is:

```text
HTTP request
     ↓
Controller
     ↓
todoId + userId
     ↓
Service
     ↓
todoId + userId
     ↓
Repository
     ↓
MongoDB
```

---

# 7. Why Not Only Check Ownership in the Service?

You might ask:

> "Why can't I just query by ID and then check the owner?"

For example:

```js
const todo =
    await Todo.findById(todoId);

if (todo.userId !== userId) {
    throw new AppError(
        "Forbidden",
        403
    );
}
```

This is not always wrong.

But an ownership-aware query is often cleaner:

```js
const todo =
    await Todo.findOne({
        _id: todoId,
        userId
    });
```

The database itself now answers:

> "Give me this record only if it belongs to this user."

---

# 8. Ownership Queries Prevent Accidental Exposure

Imagine an endpoint:

```http
GET /todos/123
```

If the Repository does:

```js
Todo.findById(123);
```

then the Service receives the Todo regardless of ownership.

Someone could accidentally forget the authorization check.

But:

```js
Todo.findOne({
    _id: 123,
    userId
});
```

makes the safe behavior part of the data-access operation.

This is a form of **defense in depth**.

---

# 9. Ownership for Updates

This is even more important.

Suppose User A sends:

```http
PATCH /todos/200
```

Todo `200` belongs to User B.

Dangerous:

```js
Todo.findByIdAndUpdate(
    todoId,
    updateData,
    { new: true }
);
```

That query doesn't check ownership.

A safer query is:

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData,
    {
        new: true
    }
);
```

Now the update happens only if:

```text
Todo ID matches
AND
Owner matches
```

---

# 10. This Is Extremely Important

Compare:

### Dangerous

```js
Todo.findByIdAndUpdate(
    todoId,
    updateData
);
```

### Ownership-aware

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData
);
```

The second version protects the update itself.

This is much better than:

```text
find
 ↓
check ownership
 ↓
update
```

when you can safely express the condition in the database operation.

---

# 11. Ownership for Delete

Same idea.

Dangerous:

```js
Todo.findByIdAndDelete(todoId);
```

A malicious user could potentially delete another user's Todo if the endpoint doesn't properly verify ownership.

Better:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

Now:

```text
Delete Todo
only when
Todo belongs to user
```

---

# 12. Ownership for List Queries

Ownership isn't only for one document.

Suppose:

```http
GET /todos
```

You don't want:

```js
Todo.find();
```

because that could return **everyone's Todos**.

Instead:

```js
Todo.find({
    userId
});
```

Now:

```text
User A
 ↓
Todo.find({ userId: A })
 ↓
Only User A's Todos
```

This is one of the most common ownership queries you'll write.

---

# 13. Repository Example

```js
const findAllByOwner = async (userId) => {
    return Todo.find({
        userId
    });
};
```

Service:

```js
const getMyTodos = async (userId) => {
    return todoRepository.findAllByOwner(
        userId
    );
};
```

Controller:

```js
const getMyTodos = async (req, res) => {
    const todos =
        await todoService.getMyTodos(
            req.user.id
        );

    res.status(200).json({
        success: true,
        data: todos
    });
};
```

---

# 14. Ownership Should Be Part of the Query

This is the central lesson:

> **If a resource belongs to a user, include the owner's identity in the database query whenever appropriate.**

For example:

```js
{
    _id: todoId,
    userId
}
```

instead of:

```js
{
    _id: todoId
}
```

---

# 15. Why This Is Called an Ownership Query

Because we're querying based on:

```text
resource ID
+
owner ID
```

Examples:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

```js
Todo.find({
    userId
});
```

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData
);
```

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

These are all ownership-aware queries.

---

# 16. The Data Model Matters

Usually the Todo document contains something like:

```js
{
    title: "Learn MongoDB",
    completed: false,
    userId: ObjectId("...")
}
```

The important field is:

```text
userId
```

It establishes:

```text
Todo
  ↓
belongs to
  ↓
User
```

So when querying Todos, we can use:

```js
userId
```

to isolate each user's data.

---

# 17. Ownership Is Different From Role

Don't confuse:

```text
ownership
```

with:

```text
role
```

Suppose:

```text
User A
role = user

User B
role = admin
```

Ownership asks:

> Who owns this specific Todo?

Role asks:

> What permissions does this user have?

For example:

```text
Todo 10 → owned by User A
```

User B might be an admin and have permission to view it.

So:

```text
Ownership ≠ Authorization
```

But ownership queries are an important tool for implementing authorization correctly.

---

# 18. Example: Normal User

User A requests:

```http
GET /todos/10
```

Repository:

```js
Todo.findOne({
    _id: 10,
    userId: A
});
```

If Todo 10 belongs to A:

```text
return Todo
```

If it belongs to B:

```text
return null
```

---

# 19. Example: Admin

An admin might have a different use case.

Instead of:

```js
findByIdAndOwner(todoId, adminId)
```

the admin might legitimately use:

```js
findById(todoId)
```

because their authorization rules allow access across users.

This is why Repository methods should describe their purpose.

For example:

```text
findByIdAndOwner()
```

means:

> "Ownership is required."

While:

```text
findById()
```

means:

> "Ownership is not part of this query."

The Service/authorization layer decides **which operation is appropriate**.

---

# 20. Don't Add Ownership to Every Query Automatically

For example, suppose you're building:

```text
Admin: List all users
```

You obviously don't want:

```js
User.find({
    userId
});
```

because that doesn't make sense.

Ownership queries are appropriate when the resource is user-owned.

Examples:

```text
User's Todos
User's Posts
User's Orders
User's Notes
User's Files
```

---

# 21. Ownership and Multi-Tenant Systems

The same idea becomes even more powerful in multi-tenant applications.

Instead of:

```js
{
    userId
}
```

you might have:

```js
{
    organizationId
}
```

Then:

```js
Project.find({
    organizationId
});
```

means:

> Only return projects belonging to this organization.

You can even have both:

```js
Project.find({
    organizationId,
    ownerId
});
```

This creates strong data isolation.

---

# 22. Ownership Query + Field Selection

Now combine **13.12** and **13.15**.

Suppose we want the user's Todo:

```js
const findByIdAndOwner = async (
    todoId,
    userId
) => {
    return Todo.findOne({
        _id: todoId,
        userId
    }).select(
        "title completed createdAt"
    );
};
```

Now the Repository is doing two useful things:

```text
1. Ownership filtering
2. Field selection
```

Very clean.

---

# 23. Ownership Query + Update

Combine ownership with an update:

```js
const updateByIdAndOwner = async (
    todoId,
    userId,
    updateData
) => {
    return Todo.findOneAndUpdate(
        {
            _id: todoId,
            userId
        },
        updateData,
        {
            new: true
        }
    ).select(
        "title completed createdAt updatedAt"
    );
};
```

This is a very realistic Repository method.

It says:

> Update this Todo only if it belongs to this user, and return only the fields the application needs.

---

# 24. Ownership Query + Delete

```js
const deleteByIdAndOwner = async (
    todoId,
    userId
) => {
    return Todo.findOneAndDelete({
        _id: todoId,
        userId
    });
};
```

Then:

```js
const deletedTodo =
    await todoRepository.deleteByIdAndOwner(
        todoId,
        userId
    );
```

If:

```text
deletedTodo === null
```

then the matching owned resource wasn't found.

---

# 25. Not Found vs Forbidden

This is a subtle design question.

Suppose User A requests:

```text
Todo 100
```

but Todo 100 belongs to User B.

Your ownership query:

```js
Todo.findOne({
    _id: 100,
    userId: A
});
```

returns:

```text
null
```

You now need to decide what the API should return.

Often, APIs intentionally return:

```http
404 Not Found
```

because from the user's perspective:

> "There is no Todo with this ID that you are allowed to access."

This can also avoid revealing whether another user's resource exists.

Your exact policy should be consistent across the application.

---

# 26. Don't Leak Resource Existence

Suppose User A asks:

```http
GET /todos/999
```

and Todo 999 belongs to User B.

If the server says:

```text
403 Forbidden
```

the user learns:

> Todo 999 exists, but I don't own it.

Sometimes that's undesirable.

An ownership query that simply returns no matching document lets the application respond:

```text
404 Not Found
```

without revealing ownership information.

This is a useful security property.

---

# 27. Common Mistake #1

❌

```js
const todo =
    await Todo.findById(todoId);

return todo;
```

No ownership check.

---

# 28. Common Mistake #2

❌

```js
Todo.find({
    userId: req.user.id
});
```

inside the Repository.

Why?

Because the Repository now depends on Express.

Better:

Controller/Service:

```js
const userId = req.user.id;
```

Repository:

```js
Todo.find({
    userId
});
```

---

# 29. Common Mistake #3

❌

```js
Todo.findOneAndUpdate(
    { _id: todoId },
    updateData
);
```

and then hoping the Service checked ownership.

Better when appropriate:

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData
);
```

---

# 30. Common Mistake #4

❌

```js
Todo.findOneAndDelete({
    _id: todoId
});
```

for a user-owned resource.

Better:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

---

# 31. Common Mistake #5 — Trusting Client-Supplied `userId`

Never blindly trust:

```json
{
    "userId": "someone-else"
}
```

from the request body to determine ownership.

The authenticated identity should come from your authentication system:

```js
req.user.id
```

Then:

```text
authenticated identity
        ↓
Service
        ↓
Repository
        ↓
userId filter
```

The client should not be allowed to simply say:

> "I am User B."

# 32. Ownership and Authentication

Authentication tells us:

```text
Who are you?
```

For example:

```text
req.user.id = 123
```

Ownership tells us:

```text
Does this resource belong to you?
```

Query:

```js
{
    _id: todoId,
    userId: 123
}
```

Authorization tells us:

```text
Are you allowed to perform this action?
```

These concepts work together:

```text
Authentication
      ↓
Who?
      ↓
userId
      ↓
Ownership query
      ↓
Which resource?
      ↓
Authorization
      ↓
What can they do?
```

---

# 33. A Very Important Pattern

For a user-owned resource:

```text
Request
  ↓
Authenticated user
  ↓
userId
  ↓
Repository ownership query
  ↓
Resource
```

For example:

```js
const todo =
    await todoRepository.findByIdAndOwner(
        todoId,
        req.user.id
    );
```

Although, as we discussed in 13.14, preferably the Controller passes clean values into the Service rather than making the Repository know about `req`.

---

# 34. Better Complete Architecture

```text
Controller
    │
    │ req.params.todoId
    │ req.user.id
    ▼
Service
    │
    │ todoId
    │ userId
    ▼
Repository
    │
    │ {_id: todoId, userId}
    ▼
MongoDB
```

This is exactly the separation we want.

# 36. The Pattern

### Read one

```js
findOne({
    _id,
    userId
});
```

### Update one

```js
findOneAndUpdate(
    {
        _id,
        userId
    },
    updateData

```

```js
findOneAndDelete({
    _id,
    userId
});
```

```js

```

# 37. What About Nested Ownership?

Sometimes ownership isn't direct.

For example:

```text
Comment
   ↓
Post
   ↓
User
```

A Comment may not have:

```js
userId
```

directly.

Then ownership might need a different strategy.

For example:

```text
Comment
  postId
    ↓
Post
  userId
    ↓
User
```

This becomes more complex and may require:

- aggregation
    
- multiple queries
    
- denormalized ownership fields
    
- carefully designed data models
    

So direct ownership:

```js
userId
```

is often very convenient.

---

# 38. Ownership Fields Should Be Indexed

This is a useful performance consideration.

If you frequently query:

```js
Todo.find({
    userId
});
```

you will often want an index involving:

```text
userId
```

And if you frequently query:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

MongoDB's `_id` index already helps with the `_id` lookup, while your broader list queries may benefit from a `userId` index.

Index design will become more important as we move deeper into Repository performance.

# 39. Interview Questions

### Q1. What is an ownership query?

A query that retrieves or modifies a resource only when it belongs to a specific user or tenant.

Example:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

---

### Q2. Why is `findById()` sometimes insufficient?

Because it checks only the resource ID and doesn't verify ownership.

---

### Q3. How do you update only a user's own Todo?

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData,
    {
        new: true
    }
);
```

---

### Q4. How do you delete only a user's own Todo?

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

---

### Q5. Should the Repository receive `req.user.id` directly?

No.

Pass the extracted `userId`:

```js
todoRepository.findByIdAndOwner(
    todoId,
    userId
);
```

The Repository should not depend on Express.

# ⭐ Final Mental Model

Remember this:

```text
             AUTHENTICATION
                   │
                   ▼
              userId = A
                   │
                   ▼
             SERVICE
                   │
             todoId + userId
                   │
                   ▼
            REPOSITORY
                   │
                   ▼
       {_id: todoId, userId: A}
                   │
                   ▼
               MongoDB
                   │
          ┌────────┴────────┐
          │                 │
      Owner A           Owner B
          │                 │
        MATCH             NO MATCH
          │                 │
          ▼                 ▼
       return             null
```

### The golden rule:

> **For user-owned resources, don't query by resource ID alone when ownership matters. Include the authenticated user's ID in the data-access query.**

The four patterns worth remembering are:

```js
// List
Todo.find({ userId });

// Read
Todo.findOne({
    _id: todoId,
    userId
});

// Update
Todo.findOneAndUpdate(
    { _id: todoId, userId },
    updateData
);

// Delete
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

This gives you a strong foundation for the next three lessons:

```text
13.15 → Ownership queries       ← today
13.16 → Pagination repositories
13.17 → Filtering repositories
13.18 → Sorting repositories
```

Once pagination, filtering, and sorting are added, we'll start building a Repository API that looks much closer to what you'll see in real production MERN applications.
