# Phase 13 — Repository Pattern & Data Access

## Lesson 13.16 — Pagination Repositories

We now move from **ownership** to **pagination**.

Your Phase 13 roadmap places **13.16 Pagination repositories** immediately after ownership queries and before filtering and sorting.

And this topic will later connect directly to your broader pagination/filtering/sorting phase, where the roadmap expects you to understand `page`, `limit`, `skip`, `sort`, and `filter`.

---

# 1. The Problem

Imagine your application has:

```text
10 users
```

Returning all users is fine:

```js
const users = await User.find();
```

But imagine:

```text
1,000,000 users
```

Now doing:

```js
const users = await User.find();
```

is a bad idea.

You're asking the database to return a huge amount of data.

Instead, we want:

```text
Page 1 → 20 users
Page 2 → next 20 users
Page 3 → next 20 users
...
```

This is **pagination**.

---

# 2. What Is Pagination?

Pagination means:

> **Splitting a large result set into smaller pages.**

For example:

```text
Total records = 100

limit = 10
```

Then:

```text
Page 1 → records 1–10
Page 2 → records 11–20
Page 3 → records 21–30
...
Page 10 → records 91–100
```

Instead of sending all 100 records at once.

---

# 3. Why Do We Need Pagination?

Pagination gives us several benefits.

### Performance

The server doesn't process huge result sets.

### Network efficiency

The client receives less data.

### Database efficiency

The application requests only the current page.

### Better UI

Frontend applications can display:

```text
Previous | 1 | 2 | 3 | 4 | Next
```

### Scalability

A query that works with:

```text
1,000 records
```

should ideally still have a reasonable strategy when you have:

```text
1,000,000 records
```

---

# 4. The Two Main Parameters

For traditional MongoDB pagination, you'll commonly see:

```text
page
limit
```

For example:

```text
?page=2&limit=20
```

Meaning:

```text
Page = 2
Records per page = 20
```

---

# 5. What Is `limit`?

`limit` tells MongoDB:

> **How many documents should I return?**

Example:

```js
User.find()
    .limit(20);
```

This means:

```text
Return at most 20 documents.
```

---

# 6. What Is `skip`?

`skip` tells MongoDB:

> **How many documents should I ignore before returning results?**

Example:

```js
User.find()
    .skip(20)
    .limit(20);
```

Conceptually:

```text
Records:

1  2  3  ... 20  21  22 ... 40
|-------------|  |-------------|
     skip             return
```

So:

```text
skip = 20
limit = 20
```

returns approximately records:

```text
21–40
```

assuming a stable sort/order.

---

# 7. Page → Skip Formula

This is the formula you should remember:

```text
skip = (page - 1) × limit
```

Examples:

### Page 1

```text
page = 1
limit = 20

skip = (1 - 1) × 20
     = 0
```

### Page 2

```text
page = 2
limit = 20

skip = (2 - 1) × 20
     = 20
```

### Page 3

```text
page = 3
limit = 20

skip = (3 - 1) × 20
     = 40
```

So:

```text
Page 1 → skip 0
Page 2 → skip 20
Page 3 → skip 40
Page 4 → skip 60
```

---

# 8. Basic Repository Pagination

Let's create:

```js
const findMany = async ({
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    return User.find()
        .skip(skip)
        .limit(limit);
};
```

This is our first pagination Repository.

---

# 9. Calling the Repository

The Service can call:

```js
const users = await userRepository.findMany({
    page: 2,
    limit: 20
});
```

Repository:

```text
page = 2
limit = 20
```

calculates:

```text
skip = 20
```

Then:

```js
User.find()
    .skip(20)
    .limit(20);
```

---

# 10. Why Use an Options Object?

Remember Lesson 13.14.

We could theoretically write:

```js
findMany(page, limit)
```

That's okay for two parameters.

But pagination will soon need more:

```text
page
limit
filter
sort
search
```

So this is more scalable:

```js
findMany({
    page,
    limit,
    filter,
    sort
});
```

The Repository API remains readable.

---

# 11. Pagination Flow

The complete flow looks like:

```text
GET /users?page=2&limit=20
             │
             ▼
         Controller
             │
             ▼
         Validation
             │
             ▼
          Service
             │
       page = 2
       limit = 20
             │
             ▼
        Repository
             │
     skip = 20
             │
             ▼
          MongoDB
             │
             ▼
       20 documents
```

This is the architecture we want.

---

# 12. Controller Shouldn't Calculate Database Logic

A Controller might receive:

```js
req.query.page
req.query.limit
```

But don't fill the Controller with:

```js
const skip = (page - 1) * limit;

const users = await User.find()
    .skip(skip)
    .limit(limit);
```

That would put database logic inside the Controller.

Instead:

```text
Controller
   ↓
Service
   ↓
Repository
```

The Repository handles:

```text
MongoDB
skip
limit
query
```

# 13. Service Example

```js
const getUsers = async ({
    page,
    limit
}) => {
    return userRepository.findMany({
        page,
        limit
    });
};
```

Controller:

```js
const getUsers = async (req, res) => {
    const users =
        await userService.getUsers({
            page: Number(req.query.page),
            limit: Number(req.query.limit)
        });

    res.status(200).json({
        success: true,
        data: users
    });
};
```

Repository:

```js
const findMany = async ({
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    return User.find()
        .skip(skip)
        .limit(limit);
};
```

---

# 14. But There Is a Problem

Suppose we return:

```json
{
  "success": true,
  "data": [
    "...20 users..."
  ]
}
```

How does the frontend know:

```text
How many pages exist?
How many records exist?
Is this the last page?
```

It doesn't.

That's why pagination usually needs **metadata**.

We'll cover pagination metadata more deeply later, but let's understand the basic idea now.

---

# 15. Pagination Metadata

A useful response can contain:

```json
{
  "success": true,
  "data": [],
  "pagination": {
    "page": 2,
    "limit": 20,
    "total": 100,
    "totalPages": 5
  }
}
```

Now React knows:

```text
Current page = 2
Records/page = 20
Total = 100
Pages = 5
```

---

# 16. Calculating Total Pages

Formula:

```text
totalPages = ceil(total / limit)
```

Example:

```text
total = 100
limit = 20

totalPages = ceil(100 / 20)
           = 5
```

Another example:

```text
total = 101
limit = 20

totalPages = ceil(101 / 20)
           = 6
```

The `ceil()` is important because even one extra record requires another page.

---

# 17. Getting Total Records

MongoDB can give us the number of matching documents.

For example:

```js
const total = await User.countDocuments();
```

Then:

```js
const users = await User.find()
    .skip(skip)
    .limit(limit);
```

So we have:

```text
countDocuments()
      ↓
total

find()
      ↓
current page
```

---

# 18. A Better Repository Result

Instead of returning only:

```js
return users;
```

the Repository can return:

```js
return {
    users,
    total
};
```

For example:

```js
const findMany = async ({
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    const [users, total] =
        await Promise.all([
            User.find()
                .skip(skip)
                .limit(limit),
            User.countDocuments()
        ]);

    return {
        users,
        total
    };
};
```

This is a useful pattern.

---

# 19. Why `Promise.all()`?

We have two independent database operations:

```text
Get current page
Get total count
```

They don't depend on each other.

So:

```js
await Promise.all([
    query1,
    query2
]);
```

allows them to run concurrently rather than waiting for one to finish before starting the other.

Conceptually:

```text
             ┌── find()
             │
Repository ──┤
             │
             └── countDocuments()

                ↓

          both complete

                ↓

             result
```

---

# 20. Ownership + Pagination

Now things become more interesting.

Suppose we want:

> "Give me User A's Todos, 20 at a time."

We don't want:

```js
Todo.find()
```

We want:

```js
Todo.find({
    userId
})
```

plus:

```js
.skip(skip)
.limit(limit)
```

So:

```js
const findManyByOwner = async ({
    userId,
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    return Todo.find({
        userId
    })
        .skip(skip)
        .limit(limit);
};
```

This combines:

```text
13.15 Ownership
+
13.16 Pagination
```

---

# 21. Ownership + Total Count

For a complete result:

```js
const findManyByOwner = async ({
    userId,
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    const filter = {
        userId
    };

    const [todos, total] =
        await Promise.all([
            Todo.find(filter)
                .skip(skip)
                .limit(limit),
            Todo.countDocuments(filter)
        ]);

    return {
        todos,
        total
    };
};
```

Notice something very important:

Both queries use the **same filter**.

```js
const filter = {
    userId
};
```

Then:

```js
Todo.find(filter)
```

and:

```js
Todo.countDocuments(filter)
```

This ensures the count represents the same dataset.

---

# 22. Why This Matters

Suppose User A owns:

```text
75 Todos
```

We request:

```text
page = 2
limit = 20
```

Then:

```text
skip = 20
```

MongoDB returns:

```text
Todos 21–40
```

And:

```text
total = 75
```

So:

```text
totalPages = ceil(75 / 20)
           = 4
```

Frontend can show:

```text
Page 2 of 4
```

# 23. Add Sorting

There is an important practical detail.

Pagination without a stable order can produce confusing results.

For example:

```js
Todo.find({
    userId
})
.skip(skip)
.limit(limit);
```

It's better to eventually define a consistent sort:

```js
Todo.find({
    userId
})
.sort({
    createdAt: -1
})
.skip(skip)
.limit(limit);
```

Meaning:

```text
Newest first
```

Sorting itself is the topic of **13.18**, so don't worry about mastering it yet.

For now, understand:

> **Pagination works best with a predictable ordering.**

---

# 24. The `limit` Must Be Controlled

Never blindly trust:

```text
?limit=999999999
```

A malicious or careless client could request a huge amount of data.

Instead, define a maximum.

For example:

```js
const MAX_LIMIT = 100;
```

Then normalize:

```js
const limit = Math.min(
    requestedLimit,
    MAX_LIMIT
);
```

Or validate the query before it reaches the Repository.

This is important because:

```text
Pagination
+
Security
+
Performance
```

are connected.

---

# 25. Default Values

Your Repository should have sensible defaults.

For example:

```js
const findMany = async ({
    page = 1,
    limit = 20
}) => {
    // ...
};
```

If the caller provides:

```js
{}
```

then:

```text
page = 1
limit = 20
```

This prevents every caller from having to specify defaults.

---

# 26. Validate Page

`page` should normally be:

```text
positive integer
```

Valid:

```text
1
2
3
100
```

Invalid:

```text
0
-1
1.5
abc
```

This validation should happen before the Repository.

The Repository ideally receives:

```js
{
    page: 2,
    limit: 20
}
```

not raw:

```text
"2"
"20"
```

from the URL.

---

# 27. Query Parameters Are Strings

This is an important Express detail.

If the request is:

```http
GET /users?page=2&limit=20
```

then:

```js
req.query.page
```

is generally a string:

```js
"2"
```

not:

```js
2
```

So your validation/normalization layer should convert it.

For example:

```js
const page = Number(req.query.page);
const limit = Number(req.query.limit);
```

Or better, use your validation system to validate and convert it.

Then the Repository receives numbers.

---

# 28. Repository Shouldn't Parse HTTP Query Strings

Avoid:

```js
const findMany = async (query) => {
    const page = Number(query.page);
    const limit = Number(query.limit);

    // ...
};
```

if `query` means `req.query`.

That's an HTTP concern.

Prefer:

```js
const findMany = async ({
    page,
    limit
}) => {
    // ...
};
```

The Service/application layer passes normalized values.

---

# 29. A Clean Architecture

```text
HTTP
 │
 │ ?page=2&limit=20
 ▼
Controller
 │
 │ raw query
 ▼
Validation / normalization
 │
 │ page: 2
 │ limit: 20
 ▼
Service
 │
 │ page + limit
 ▼
Repository
 │
 │ skip + limit

```

This keeps responsibilities separate.

A clean Repository method might be:


# 31. Service Builds Pagination Metadata

I prefer keeping the Repository focused on data access.

So Repository returns:

```js
{
    todos,
    total
}
```

Then Service can calculate:

```js
const totalPages =
    Math.ceil(total / limit);
```

and return:

```js
return {
    data: todos,
    pagination: {
        page,
        limit,
        total,
        totalPages

```

This keeps the separation clean:

```text
Repository
    ↓
Database result

Service
    ↓
Application-level result
```

```js
const getMyTodos = async ({
```

# 37. A Common Mistake

❌

```js
const skip = page * limit;
```

This is wrong for page numbering starting at `1`.

If:

```text
page = 1
limit = 20
```

you would get:

```text
skip = 20
```

and accidentally skip the first page.

Correct:

```js
const skip = (page - 1) * limit;
```

---

# 38. Another Common Mistake

❌

```js
Todo.find({
    userId
}).limit(20);
```

and calling that "pagination."

That's only a **limit**.

Real page-based pagination needs:

```text
page
limit
skip
```

---

# 39. Another Common Mistake

❌ Returning all records to calculate the total:

```js
const todos = await Todo.find({
    userId
});

const total = todos.length;
```

This defeats the purpose of pagination.

You don't want to retrieve 100,000 documents just to count them.

Instead:

```js
const total =
    await Todo.countDocuments({
        userId
    });
```

---

# 40. Another Common Mistake

❌ Different filters for data and count:

```js
const todos = await Todo.find({
    userId
});

const total = await Todo.countDocuments();
```

The first query is:

```text
User A's Todos
```

but the second counts:

```text
Everyone's Todos
```

Wrong.

Use the same filter:

```js
const filter = {
    userId
};

const todos = await Todo.find(filter);
const total = await Todo.countDocuments(filter);
```

This pattern is worth remembering.

---

# 41. Another Common Mistake

❌ Allowing:

```text
limit=1000000
```

without a maximum.

Better:

```text
Default limit = 20
Maximum limit = 100
```

Then the API remains predictable.

---

# 42. `skip()` Has a Scalability Limitation

Traditional pagination uses:

```js
.skip(skip)
.limit(limit)
```

It's simple and very useful.

But for extremely large datasets, very high offsets can become inefficient because MongoDB may need to work through many earlier records.

For example:

```text
page = 50,000
```

with:

```text
limit = 20
```

means:

```text
skip = 999,980
```

That's a huge offset.

This is one reason large-scale systems sometimes use **cursor-based pagination**.

You don't need to implement cursor pagination today.

Just remember:

```text
Page pagination
    ↓
simple
easy for UIs
uses skip/limit

Cursor pagination
    ↓
better for certain large/changing datasets
uses a cursor instead of huge offsets
```

The roadmap specifically calls out **page vs cursor pagination** later in Phase 18.

---

# 43. Page Pagination Is Still Extremely Useful

Don't think:

> "`skip()` is bad, so never use it."

That's not correct.

For many normal CRUD applications:

```text
users
products
posts
admin tables
orders
todos
```

page + limit + skip is simple and perfectly practical.

The important thing is understanding its tradeoffs.

# 47. Interview Questions

### Q1. What is pagination?

Pagination divides a large result set into smaller pages.

---

### Q2. What are `skip()` and `limit()`?

```text
skip()
→ number of documents to skip

limit()
→ maximum number of documents to return
```

---

### Q3. What is the page-to-skip formula?

```text
skip = (page - 1) × limit
```

---

### Q4. How do you get total documents?

```js
await Model.countDocuments(filter);
```

---

### Q5. Why should the same filter be used for `find()` and `countDocuments()`?

So the total count represents the same dataset as the returned page.

---

### Q6. Why should `limit` have a maximum?

To prevent huge queries and protect database/server performance.

---

### Q7. What is one limitation of `skip` pagination?

Very large offsets can become inefficient, which is why cursor-based pagination can be useful for some large datasets.

```text
│                             │
│  WHICH PAGE?                 │
│  page                        │
│                             │
│  HOW MANY?                   │
│  limit                       │
│                             │
│  WHERE TO START?             │
│  skip = (page - 1) × limit   │
│                             │
└─────────────────────────────┘
```

The basic Repository pattern:

```js
const findManyByOwner = async ({
    userId,
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    const filter = {
        userId
    };

    const [items, total] =
        await Promise.all([
            Todo.find(filter)
                .skip(skip)
                .limit(limit),
            Todo.countDocuments(filter)
        ]);

    return {
        items,
        total
    };
};
```
