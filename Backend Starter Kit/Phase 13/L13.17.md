# Phase 13 — Repository Pattern & Data Access

## Lesson 13.17 — Filtering Repositories

In **13.15**, we learned how to filter by ownership.

In **13.16**, we learned how to paginate.

Now we combine those ideas with **general filtering**.

The goal is to build repositories that can answer questions like:

> "Give me page 2 of Rahul's completed Todos."

or:

> "Give me active users whose role is `admin`."

or:

> "Give me products in the `laptop` category."

---

# 1. What Is Filtering?

Filtering means:

> **Returning only documents that match specific conditions.**

Suppose the database contains:

```text
Todo 1 → completed: true
Todo 2 → completed: false
Todo 3 → completed: true
Todo 4 → completed: false
```

If we want only completed Todos:

```js
Todo.find({
    completed: true
});
```

MongoDB returns:

```text
Todo 1
Todo 3
```

That's filtering.

---

# 2. Why Filtering Belongs in the Repository

Remember our architecture:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
MongoDB
```

Filtering is directly related to the database query.

Therefore, the Repository is responsible for translating application-level filters into MongoDB queries.

For example:

```js
const filter = {
    completed: true
};

Todo.find(filter);
```

The Service shouldn't contain lots of MongoDB syntax.

---

# 3. Simple Filtering

Suppose our Todo model looks like:

```js
{
    title: "Learn MongoDB",
    completed: false,
    userId: ObjectId("...")
}
```

We can filter:

### Completed

```js
Todo.find({
    completed: true
});
```

### Incomplete

```js
Todo.find({
    completed: false
});
```

### By owner

```js
Todo.find({
    userId
});
```

### By owner + status

```js
Todo.find({
    userId,
    completed: true
});
```

This last one is especially useful.

# 4. Ownership + Filtering

From Lesson 13.15:

```js
{
    userId
}
```

Now add:

```js
{
    completed: true
}
```

Together:

```js
Todo.find({
    userId,
    completed: true
});
```

This means:

> "Find completed Todos belonging to this user."

Notice how MongoDB treats the properties as **AND conditions**.

Conceptually:

```text
userId = Rahul
    AND
completed = true
```

# 5. Filtering + Pagination

Now combine 13.15, 13.16, and 13.17.

Suppose:

```text
userId = A
completed = true
page = 2
limit = 20
```

Repository:

```js
const filter = {
    userId,
    completed: true
};

const skip = (page - 1) * limit;

const todos = await Todo.find(filter)
    .skip(skip)
    .limit(limit);
```

Now we're saying:

```text
1. Only User A's Todos
2. Only completed Todos
3. Give me page 2
4. Give me 20 records
```

That's already a very realistic production query.

---

# 6. Don't Create One Method for Every Filter

A beginner might create:

```js
findCompletedTodos()
findIncompleteTodos()
findActiveTodos()
findCompletedTodosByUser()
findIncompleteTodosByUser()
findCompletedTodosByUserPaginated()
```

This quickly becomes messy.

Instead, create a flexible method:

```js
findMany({
    filter,
    page,
    limit
});
```

Then the caller can provide different filters.

---

# 7. Basic Flexible Repository

```js
const findMany = async ({
    filter = {},
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    return Todo.find(filter)
        .skip(skip)
        .limit(limit);
};
```

Now:

### All Todos

```js
findMany({
    filter: {}
});
```

### Completed Todos

```js
findMany({
    filter: {
        completed: true
    }
});
```

### User's Todos

```js
findMany({
    filter: {
        userId
    }
});
```

### User's completed Todos

```js
findMany({
    filter: {
        userId,
        completed: true
    }
});
```

Much cleaner.

---

# 8. But There Is an Important Security Problem

Be careful with this:

```js
findMany({
    filter: req.query
});
```

You should **not blindly pass client input directly into MongoDB**.

For example, a client might send unexpected fields or MongoDB operators.

Instead, the application should first validate and normalize allowed filters.

For example, allow:

```text
completed
priority
category
```

but don't blindly accept every arbitrary query parameter.

---

# 9. Whitelist Your Filters

Suppose your API supports:

```http
GET /todos?completed=true&priority=high
```

You can explicitly create:

```js
const filter = {};

if (completed !== undefined) {
    filter.completed = completed;
}

if (priority !== undefined) {
    filter.priority = priority;
}
```

Now only supported filters enter the Repository.

This is called a **whitelist approach**.

---

# 10. Why Whitelisting Is Better

Suppose the client sends:

```text
?completed=true
```

You expect:

```js
{
    completed: true
}
```

But if you blindly use:

```js
const filter = req.query;
```

the client controls the shape of your MongoDB query.

That's not a good boundary.

Instead:

```text
HTTP query
    ↓
Validation
    ↓
Allowed filter object
    ↓
Service
    ↓
Repository
```

This gives you control.

---

# 11. Repository Should Receive a Clean Filter

The Repository doesn't need to know:

```text
req.query
Express
HTTP
URL parameters
```

It should receive:

```js
{
    userId,
    completed: true,
    priority: "high"
}
```

Then:

```js
Todo.find(filter);
```

This is another example of the clean Repository boundary we've been building throughout Phase 13.

# 14. Filtering by Multiple Values

Suppose we want:

```text
status = active OR pending
```

MongoDB provides `$in`:

```js
User.find({
    status: {
        $in: ["active", "pending"]
    }
});
```

This means:

```text
status is active
OR
status is pending
```

# 15. Example: Product Categories

Suppose:

```text
category = laptop

category = tablet
```

We want:

```text
laptop OR tablet
```

Query:

```js
Product.find({
    category: {
        $in: ["laptop", "tablet"]
    }

```

This is a useful Repository-level filter.

# 16. Filtering by Numeric Range

Suppose products have:

```js
price: 50000
```

We want:

```text
price >= 20000
AND
price <= 80000
```

MongoDB:

```js
Product.find({
    price: {
        $gte: 20000,
        $lte: 80000
    }
});
```

Meaning:

```text
$gte → greater than or equal
$lte → less than or equal
```

---

# 17. Common Comparison Operators

You'll frequently see:

```text
$gt
$gte
$lt
$lte
$in
$nin
```

Meaning:

|Operator|Meaning|
|---|---|
|`$gt`|greater than|
|`$gte`|greater than or equal|
|`$lt`|less than|
|`$lte`|less than or equal|
|`$in`|matches one of the values|
|`$nin`|doesn't match listed values|

Examples:

```js
{
    price: {
        $gt: 1000
    }
}
```

means:

```text
price > 1000
```

# 20. The Important Design Question

Should the Repository construct the entire filter?

There are two common approaches.

### Approach A — Service constructs filter

```js
const filter = {
    userId,
    completed
};

repository.findMany({
    filter,
    page,
    limit
});
```

### Approach B — Repository accepts domain-specific options

```js
repository.findManyTodos({
    userId,
    completed,
    page,
    limit
});
```

Both can work.

For our architecture, a good general-purpose Repository can accept a clean `filter` object, while the Service is responsible for deciding **what the user is allowed to filter by**.

---

# 21. Don't Let the Client Decide Ownership

This is extremely important.

Suppose the client sends:

```http
GET /todos?userId=someoneElse
```

Don't blindly use:

```js
const filter = {
    userId: req.query.userId
};
```

For a "my Todos" endpoint, ownership should come from authentication:

```js
const filter = {
    userId: req.user.id
};
```

The client should control things like:

```text
completed
priority
page
limit
```

but not override:

```text
authenticated owner
```

unless the endpoint is specifically designed for admins.

---

# 22. Building Filters Safely

A clean Service might do:

```js
const getMyTodos = async ({
    userId,
    completed,
    priority,
    page,
    limit
}) => {
    const filter = {
        userId
    };

    if (completed !== undefined) {
        filter.completed = completed;
    }

    if (priority !== undefined) {
        filter.priority = priority;
    }

    return todoRepository.findMany({
        filter,
        page,
        limit
    });
};
```

Notice:

```text
userId
```

is always controlled by the application.

But:

```text
completed
priority
```

are optional filters.

That's a good pattern.

---

# 23. Why `undefined` Matters

Consider:

```js
if (completed !== undefined) {
    filter.completed = completed;
}
```

Why not:

```js
if (completed) {
    filter.completed = completed;
}
```

Because:

```js
completed = false
```

is a valid filter.

This:

```js
if (completed)
```

would not execute for `false`.

So use:

```js
completed !== undefined
```

when a boolean filter can legitimately be either `true` or `false`.

---

# 24. A Common Bug

❌

```js
const filter = {};

if (completed) {
    filter.completed = completed;
}
```

If the user asks:

```text
completed=false
```

the filter isn't added.

Then you accidentally return:

```text
both completed and incomplete Todos
```

Correct:

```js
if (completed !== undefined) {
    filter.completed = completed;
}
```

# 25. Filter Object as a Repository Boundary

I want you to remember this pattern:

```js
repository.findMany({
    filter,
    page,
    limit
});
```

The Repository receives:

```text
filter → what records?
page   → which page?
limit  → how many?
```

Later we'll add:

```text
sort
projection
search
cursor
```

So the Repository becomes a reusable data-access interface.

# 26. Filtering + Count

Remember our pagination lesson.

If we're filtering:

```js
const filter = {
    userId,
    completed: true
};
```

then:

```js
const [todos, total] =
    await Promise.all([
        Todo.find(filter)
            .skip(skip)
            .limit(limit),

        Todo.countDocuments(filter)
    ]);
```

Both operations must use the same filter.

Otherwise:

```text
page data
```

and:

```text
total count
```

would represent different datasets.

---

# 27. Complete Filtering Repository

A useful implementation:

```js
const findMany = async ({
    filter = {},
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    const [items, total] =
        await Promise.all([
            Todo.find(filter)
                .skip(skip)
                .limit(limit),

            Todo.countDocuments(filter)
        ]);

    return {
        items,
        total
    };
};
```

This Repository doesn't care whether the filter is:

```js
{
    userId
}
```

or:

```js
{
    completed: true
}
```

or:

```js
{
    userId,
    completed: true,
    priority: "high"
}
```

It simply performs data access.

---

# 28. Service Example

```js
const getMyTodos = async ({
    userId,
    completed,
    priority,
    page,
    limit
}) => {
    const filter = {
        userId
    };

    if (completed !== undefined) {
        filter.completed = completed;
    }

    if (priority !== undefined) {
        filter.priority = priority;
    }

    const result =
        await todoRepository.findMany({
            filter,
            page,
            limit
        });

    return {
        data: result.items,
        pagination: {
            page,
            limit,
            total: result.total,
            totalPages: Math.ceil(
                result.total / limit
            )
        }
    };
};
```

This is getting very close to a production-style Service + Repository implementation.

# 31. Filtering Should Be Explicit

Don't create magical behavior like:

```js
Todo.find(req.query);
```

Instead, explicitly support filters.

For example:

```js
const allowedFilters = {
    completed,
    priority,
    category
};
```

Then construct only valid fields.

This makes your API:

```text
predictable
secure
maintainable
```

# 32. Filtering vs Searching

These are related but different.

### Filtering

Exact or structured conditions:

```js
{
    completed: true
}
```

### Searching

Usually means matching text:

```text
"javascript"
```

against fields such as:

```text
title
description
```

For example, MongoDB text/regex/search features can be used.

We'll treat search as a separate concern rather than mixing it into basic filtering.

---

# 33. Filtering vs Sorting

Filtering answers:

> **Which documents?**

Sorting answers:

> **In what order?**

Example:

```text
Filter:
completed = true

Sort:
createdAt descending
```

So:

```text
Filtering → WHERE
Sorting   → ORDER BY
```

If you've used SQL, this mental model is useful.

---

# 34. Filtering vs Pagination

Pagination answers:

> **Which slice of the matching results?**

So these concepts work together:

```text
Filter
   ↓
Which records?

Sort
   ↓
What order?

Pagination
   ↓
Which portion?
```

For example:

```text
All Todos
   ↓
User A's Todos
   ↓
Completed Todos
   ↓
Newest first
   ↓
Page 2
   ↓
20 records
```

This is the exact kind of query our Repository layer is preparing to support.

---

# 35. A Powerful Mental Model

Think of a Repository query as a pipeline:

```text
                   DATABASE QUERY
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
     FILTER            SORT           PAGINATION
        │                │                │
    Which data?       What order?     Which page?
```

For example:

```text
Filter:
userId = A
completed = true

Sort:
createdAt DESC

Pagination:
page = 2
limit = 20
```
