# Phase 13 — Repository Pattern & Data Access

## Lesson 13.18 — Sorting Repositories

In **13.17**, we learned filtering:

> **Which records do I want?**

Now we add sorting:

> **In what order should those records come back?**

Your roadmap explicitly places **13.18 Sorting repositories** after pagination and filtering.

This is also directly connected to the starter code you uploaded. Your existing Todo implementation already accepts `sortBy`, parses it with `parseSort()`, restricts sorting to `createdAt`, `priority`, and `dueDate`, and then applies `.sort(sort)`.

So this lesson will explain **why that code exists**, rather than treating it as magic.

---

# 1. What Is Sorting?

Sorting means:

> **Arranging database results according to a field and direction.**

Suppose we have:

```text
Todo A → createdAt: Jan 1
Todo B → createdAt: Jan 5
Todo C → createdAt: Jan 3
```

Without sorting, you shouldn't rely on the returned order.

We can explicitly request:

```js
Todo.find()
    .sort({
        createdAt: -1
    });
```

Result:

```text
Todo B → Jan 5
Todo C → Jan 3
Todo A → Jan 1
```

That's sorting in descending order.

---

# 2. Ascending vs Descending

MongoDB uses:

```text
1  → ascending
-1 → descending
```

For example:

```js
.sort({
    priority: 1
});
```

means:

```text
low → high
```

And:

```js
.sort({
    priority: -1
});
```

means:

```text
high → low
```

For dates:

```js
.sort({
    createdAt: -1
});
```

usually means:

```text
newest → oldest
```

while:

```js
.sort({
    createdAt: 1
});
```

means:

```text
oldest → newest
```

---

# 3. Why Sorting Matters for Pagination

This is **very important**.

Imagine:

```text
page = 1
limit = 20
```

and:

```js
Todo.find()
    .skip(0)
    .limit(20);
```

Then page 2:

```js
Todo.find()
    .skip(20)
    .limit(20);
```

What determines which documents are considered the first 20?

The ordering.

If you don't have a predictable sort, pagination can become confusing.

So a common pattern is:

```js
Todo.find(filter)
    .sort({
        createdAt: -1
    })
    .skip(skip)
    .limit(limit);
```

Now we have:

```text
FILTER
   ↓
SORT
   ↓
PAGINATION
```

# 5. Basic Repository Sorting

A simple Repository can receive:

```js
{
    filter,
    sort,
    page,
    limit
}
```

Example:

```js
const findMany = async ({
    filter = {},
    sort = { createdAt: -1 },
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    return Todo.find(filter)
        .sort(sort)
        .skip(skip)
        .limit(limit);
};
```

This is clean because the Repository doesn't care why the caller chose that sort.

# 8. What Should `sortBy` Look Like?

Your API might support:

```text

```

for ascending:

```text

```

and:

```text
?sortBy=-createdAt
```

for descending:

```text

```

```js

```

```js

```

# 9. Understanding `parseSort()`

Suppose:

```text
sortBy = "-createdAt"
```

A helper such as:

```js
parseSort("-createdAt")
```

can produce:

```js
{
    createdAt: -1
}
```

And:

```text
sortBy = "createdAt"
```

can become:

```js
{
    createdAt: 1
}
```

So:

```text
API-friendly string
        ↓
   parseSort()
        ↓
MongoDB sort object
```

This is a nice separation.

---

# 10. Why Use a Helper?

Without a helper, you might repeatedly write:

```js
if (sortBy.startsWith("-")) {
    // ...
}
```

in different places.

Instead:

```js
const sort = parseSort(sortBy);
```

centralizes the conversion.

Then the Repository can work with:

```js
{
    createdAt: -1
}
```

which is directly usable by MongoDB.

# 11. Multiple Sort Fields

MongoDB can sort by multiple fields.

Example:

```js
.sort({
    priority: -1,
    createdAt: -1
});
```

This means:

> Sort by priority descending. If two documents have the same priority, sort those by `createdAt` descending.

Conceptually:

```text
Priority
  ↓
same priority?
  ↓
CreatedAt
```

For example:

```text
High   Jan 10
High   Jan 5
Medium Jan 8
Medium Jan 2
Low    Jan 9
```

---

# 12. Why Multiple Sort Fields Are Useful

Imagine:

```text
Todo A → priority: high
Todo B → priority: high
```

If we only sort:

```js
{
    priority: -1
}
```

their relative order isn't something you should rely on.

Add:

```js
{
    priority: -1,
    createdAt: -1
}
```

Now newer high-priority Todos come first.

This creates a more predictable ordering.

# 15. Complete Repository Method

A clean version:

```js
const findMany = async ({
    filter = {},
    sort = { createdAt: -1 },
    page = 1,
    limit = 20
}) => {
    const skip = (page - 1) * limit;

    const [items, total] =
        await Promise.all([
            Todo.find(filter)
                .sort(sort)
                .skip(skip)
                .limit(limit),

            Todo.countDocuments(filter)
        ]);

    return {
        items,
        total
    };
};
```

Now our Repository supports:

```text

sort
pagination
total count
```

# 16. The Security Problem With Sorting

Here's something very important.

Suppose the Todo document contains:

```text
title
description
priority
createdAt
dueDate
password
internalNotes
secretToken
```

You shouldn't allow the client to sort by every field.

For example:

```http
GET /todos?sortBy=secretToken
```

should not automatically become:

```js
.sort({
    secretToken: 1
});
```

Instead, define allowed fields.

---

# 17. Sort Whitelist

Your uploaded starter does exactly this.

It defines:

```js
const allowedSortFields = [
    "createdAt",
    "priority",
    "dueDate"
];
```

Then it parses the requested sort and removes fields that aren't allowed.

Conceptually:

```text
Client says:
sortBy=password

        ↓

parseSort()

        ↓

{ password: 1 }

        ↓

allowed fields?

        ↓

NO

        ↓

remove it
```

This is a **sort whitelist**.

---

# 18. Why Whitelisting Is Better

You explicitly decide:

```text
These fields are safe and useful to sort by.
```

For example:

```js
const allowedSortFields = [
    "createdAt",
    "priority",
    "dueDate"
];
```

Now:

```text
createdAt → allowed
priority  → allowed
dueDate   → allowed
password  → rejected
internal  → rejected
secret    → rejected
```

This makes the API predictable.

---

# 19. Reproducing the Starter's Pattern

Your uploaded code does essentially:

```js
const allowedSortFields = [
    "createdAt",
    "priority",
    "dueDate"
];

const sort = parseSort(sortBy);

Object.keys(sort).forEach((field) => {
    if (!allowedSortFields.includes(field)) {
        delete sort[field];
    }
});
```

Then:

```js
query = query
    .sort(sort)
    .skip((pageNum - 1) * limitNum)
    .limit(limitNum)
    .lean();
```

Now you can understand every part:

```text
parseSort()
    ↓
Convert API string

allowedSortFields
    ↓
Security / API contract

.sort()
    ↓
MongoDB ordering

.skip()
    ↓
Pagination

.limit()
    ↓
Page size

.lean()
    ↓
Read optimization
```

# 20. Why `sortBy=password` Should Not Work

Suppose:

```http
GET /todos?sortBy=password
```

Your API should not blindly execute:

```js
.sort({
    password: 1
});
```

The allowed list prevents this.

This doesn't mean sorting by a field is automatically a major security vulnerability in every application, but unrestricted query capabilities are a poor API boundary and can expose internal fields or create unnecessary database work.

---

# 21. A Better Pattern: Map API Names

An even cleaner approach is to expose friendly API names.

For example:

```text
?sortBy=newest
?sortBy=oldest
?sortBy=priority
```

Then map them:

```js
const sortMap = {
    newest: {
        createdAt: -1
    },

    oldest: {
        createdAt: 1
    },

    priority: {
        priority: -1
    }
};
```

Then:

```js
const sort = sortMap[sortBy]
    ?? sortMap.newest;
```

Now clients never directly specify database field names.

This is a useful design for larger APIs.

# 28. Stable Sorting

Here's an advanced but important idea.

Suppose:

```text
Todo A → createdAt = Jan 1
Todo B → createdAt = Jan 1
Todo C → createdAt = Jan 1
```

If you sort only:

```js
{
    createdAt: -1
}
```

these records have equal values.

For more deterministic pagination, you can add a unique tie-breaker:

```js
{
    createdAt: -1,
    _id: -1
}
```

Now if two Todos have the same `createdAt`, `_id` gives the database another ordering criterion.

Conceptually:

```text
createdAt DESC
      ↓
tie?
      ↓
_id DESC
```

This becomes especially useful when paginating changing datasets.

---

# 29. Why `_id` Is a Useful Tie-Breaker

MongoDB's `_id` is unique.

So:

```js
{
    createdAt: -1,
    _id: -1
}
```

gives us:

```text
primary ordering:
createdAt

secondary ordering:
_id
```

This helps make ordering deterministic.

Don't memorize this as a rule that every query must use `_id`; understand it as a useful technique when you need stable ordering.

---

# 30. Sorting + `lean()`

Your starter uses:

```js
.lean()
```

after:

```js
.sort()
.skip()
.limit()
```

For read-only queries, `lean()` tells Mongoose to return plain JavaScript objects instead of full Mongoose documents.

So:

```js
Todo.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit)
    .lean();
```

is a common read-query pattern.

The key point for today's lesson:

> `lean()` doesn't perform sorting; `.sort()` does.

# 32. Don't Mix HTTP Parsing With MongoDB Logic

Avoid a Repository method like:

```js
const findMany = async (req) => {
    const { sortBy } = req.query;

    // parse HTTP
    // validate HTTP
    // build Mongo query
    // execute database
};
```

That's mixing layers.

Better:

```text
Controller
    ↓
sortBy = "-createdAt"
    ↓
Validation / parsing
    ↓
Service
    ↓
sort = { createdAt: -1 }
    ↓
Repository
```

The Repository should focus on data access.

```text
                       ▼
                   Repository
                       │
                       ▼
                 MongoDB query
                       │
                       ▼
                    Results
```

The important Repository query is:

```js
const skip = (page - 1) * limit;

Todo.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit);
```

And the **security-conscious** version of sorting is:

```js
const allowedSortFields = [
    "createdAt",
    "priority",
    "dueDate"
];

const sort = parseSort(sortBy);

Object.keys(sort).forEach((field) => {
    if (!allowedSortFields.includes(field)) {
        delete sort[field];
    }
});
```

That exact pattern is already present in your starter's Todo implementation.

### 🔑 Remember this sequence

```text
FILTER
  ↓
Which records?

SORT
  ↓
What order?

SKIP
  ↓
Where does this page start?

LIMIT
  ↓
How many records?
```

So the complete mental sentence is:

> **"Find these records, put them in this order, skip these records, and give me this many."**

That's the core of **sorting repositories**.
