# Phase 13 — Repository Pattern & Data Access

## Lesson 13.19 — Repository Errors

In the previous lessons, we've learned how a Repository performs database operations:

```text
13.15 → Ownership
13.16 → Pagination
13.17 → Filtering
13.18 → Sorting
13.19 → Errors ← TODAY
```

Your roadmap specifically places **Repository Errors** after sorting and before Repository testing.

The key idea today is:

> **A Repository should deal with database failures, but it should not contain business decisions that belong to the Service.**

---

# 1. Why Do Repositories Need Error Handling?

A Repository talks directly to MongoDB.

That means many things can go wrong:

```text
MongoDB unavailable
        ↓
Connection failure

Invalid ObjectId
        ↓
Query failure

Duplicate unique field
        ↓
Duplicate key error

Database timeout
        ↓
Operation failure

Unexpected MongoDB error
        ↓
Unknown failure
```

For example:

```js
const user = await User.findById(userId);
```

This can throw.

So this:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

doesn't mean:

> "Nothing can go wrong."

It means:

> "If something goes wrong, the rejected Promise moves upward."

---

# 2. Where Should the Error Go?

Remember our architecture:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
MongoDB
```

Suppose MongoDB fails:

```text
MongoDB
   X
   │
   ▼
Repository
   │
   ▼
Service
   │
   ▼
Controller
   │
   ▼
Global Error Middleware
   │
   ▼
HTTP Response
```

The Repository doesn't usually send an HTTP response.

It reports the failure upward.

---

# 3. Repository Is Not the HTTP Layer

This is extremely important.

Don't do this:

```js
const findById = async (id, res) => {
    try {
        return await User.findById(id);
    } catch (error) {
        return res.status(500).json({
            message: "Database error"
        });
    }
};
```

Why is this bad?

Because now the Repository knows about:

```text
Express
res
HTTP status codes
JSON responses
```

But the Repository should only know about:

```text
database
queries
data
database errors
```

---

# 4. Better Architecture

Repository:

```js
const findById = async (id) => {
    return User.findById(id);
};
```

Service:

```js
const getUser = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Controller:

```js
const getUser = async (req, res) => {
    const user =
        await userService.getUser(req.user.id);

    res.status(200).json({
        success: true,
        data: user
    });
};
```

Global error middleware handles unexpected errors.

This maintains:

```text
Repository
    ↓
data access

Service
    ↓
business decisions

Controller
    ↓
HTTP
```

---

# 5. Important Distinction: Not Found vs Database Error

This is one of the most important concepts in today's lesson.

Suppose:

```js
const user = await User.findById(id);
```

returns:

```js
null
```

That usually means:

> MongoDB successfully executed the query, but no matching document exists.

That's **not necessarily a database failure**.

Compare:

### Case A

```js
user === null
```

Meaning:

```text
Query worked
        ↓
No document found
```

### Case B

```js
await User.findById(id)
```

throws an error.

Meaning:

```text
Query failed
```

These are different situations.

---

# 6. Repository Should Usually Return `null`

For a `findById` method:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

If the user doesn't exist:

```js
null
```

comes back.

The Service decides what that means.

For example:

```js
const user = await userRepository.findById(userId);

if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

The Service is making the business/API decision.

---

# 7. Why Not Throw `404` Inside Repository?

You might think:

```js
const findById = async (id) => {
    const user = await User.findById(id);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Sometimes this can be acceptable in a very specific architecture.

But generally, a reusable Repository shouldn't assume:

> "Not found always means HTTP 404."

A Repository isn't an HTTP layer.

Another caller might want:

```text
null
```

instead of:

```text
404
```

For example:

```text
background job
admin report
internal service
```

So a clean separation is:

```text
Repository
    ↓
null

Service
    ↓
decides what null means
```

---

# 8. Database Errors Are Different

Suppose MongoDB isn't available:

```text
MongoDB
   X
```

Then:

```js
await User.findById(id);
```

could reject.

The Repository doesn't need to convert that into:

```text
HTTP 500
```

Instead:

```text
Repository
    ↓
throw/reject
    ↓
Service
    ↓
global error handler
```

The HTTP layer handles the final response.

---

# 9. Do We Need `try/catch` Everywhere?

Usually:

**No.**

This is unnecessary:

```js
const findById = async (id) => {
    try {
        return await User.findById(id);
    } catch (error) {
        throw error;
    }
};
```

You're catching the error only to immediately throw the same error.

This:

```js
const findById = async (id) => {
    return User.findById(id);
};
```

already allows the rejection to propagate.

---

# 10. When `try/catch` Is Useful

`try/catch` becomes useful when you need to:

```text
transform an error
add context
perform cleanup
handle a specific error
```

For example:

```js
const createUser = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        if (error.code === 11000) {
            throw new DuplicateUserError();
        }

        throw error;
    }
};
```

Now the `catch` has a purpose.

We're translating a database-specific error into an application-level error.

---

# 11. Duplicate Key Errors

This is a very common Repository error.

Suppose your User model has:

```js
email: {
    type: String,
    unique: true
}
```

You already have:

```text
rahul@example.com
```

Then someone tries:

```js
User.create({
    email: "rahul@example.com"
});
```

MongoDB can produce a duplicate key error.

Typically:

```text
error.code === 11000
```

This is an important MongoDB error code to recognize.

---

# 12. What Should Happen?

You don't want the frontend to receive something ugly like:

```json
{
    "error": "E11000 duplicate key error collection..."
}
```

Instead, your application should eventually produce something meaningful, such as:

```json
{
    "success": false,
    "message": "Email already exists"
}
```

The exact conversion can happen in your error architecture.

The important separation is:

```text
MongoDB error
       ↓
application error meaning
       ↓
HTTP response
```

---

# 13. Repository-Level Error Translation

One possible pattern:

```js
const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        if (error.code === 11000) {
            throw new DuplicateKeyError(
                "User already exists"
            );
        }

        throw error;
    }
};
```

Now the Repository is saying:

> "MongoDB reported a duplicate key. I'm translating that database-specific condition into something the application understands."

That's reasonable.

---

# 14. But Don't Over-Translate

Don't write:

```js
catch (error) {
    throw new AppError(
        "Something went wrong",
        500
    );
}
```

for every error.

Why?

Because you've destroyed useful information.

You can't distinguish:

```text
duplicate
validation
timeout
connection
programming bug
```

Everything becomes:

```text
500 Something went wrong
```

That's poor error handling.

---

# 15. Preserve Unknown Errors

A better pattern:

```js
try {
    return await User.create(data);
} catch (error) {
    if (error.code === 11000) {
        throw new DuplicateKeyError(
            "Email already exists"
        );
    }

    throw error;
}
```

Notice:

```js
throw error;
```

Unknown errors continue upward.

This is important.

---

# 16. Don't Hide Programming Errors

Imagine you accidentally write:

```js
User.finfById(id);
```

instead of:

```js
User.findById(id);
```

If you do:

```js
catch (error) {
    throw new AppError(
        "Database error",
        500
    );
}
```

you've hidden the actual programming problem.

During development, you want the original error and stack trace.

So:

```text
Known database condition
        ↓
translate

Unknown error
        ↓
preserve
```

is a useful rule.

# 18. Invalid ObjectId

Suppose:

```http
GET /users/abc
```

but your code expects a MongoDB ObjectId.

You may encounter a casting error when calling:

```js
User.findById("abc");
```

The Repository/database layer may produce a Mongoose cast error.

Your application can translate this into a client-friendly response.

For example:

```text
400 Bad Request
```

rather than an ugly internal stack trace.

---

# 19. Where Should Invalid IDs Be Checked?

There are several options.

### Validation layer

Validate:

```text
userId
todoId
```

before reaching the Repository.

### Repository

Mongoose may reject an invalid ID.

### Service

The Service can interpret the resulting error.

The important lesson is:

> **Don't assume every database error means the database is broken.**

Some errors represent invalid client input.

# 20. Repository vs Service Error Responsibilities

A useful mental model:

### Repository

Understands:

```text
MongoDB
Mongoose
duplicate keys
database queries
database failures
```

### Service

Understands:

```text
business rules
resource existence
what the application should do
```

### Controller

Understands:

```text
HTTP
status codes
response format
```

For example:

```text
MongoDB
  ↓
duplicate key
  ↓
Repository
  ↓
DuplicateEmailError
  ↓
Service
  ↓
Controller / Error Middleware
  ↓
409 Conflict
```

---

# 21. Why `409 Conflict`?

A duplicate resource is often represented by:

```text
409 Conflict
```

For example:

```text
POST /users
email = rahul@example.com
```

if that email already exists.

Conceptually:

```text
400 → invalid request
404 → resource not found
409 → request conflicts with existing state
500 → unexpected server failure
```

The exact API contract can vary, but this is a common design.

---

# 22. Repository Should Not Return HTTP Status Codes

Avoid:

```js
return {
    statusCode: 404,
    message: "User not found"
};
```

inside Repository code.

Why?

Because Repository doesn't know whether the caller is:

```text
HTTP API
CLI
background job
test
internal service
```

Instead:

```js
return null;
```

or:

```js
throw error;
```

Then higher layers decide what to do.

---

# 23. Example: `findByEmail`

Repository:

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

If no user exists:

```js
null
```

Service:

```js
const login = async ({ email, password }) => {
    const user =
        await userRepository.findByEmail(email);

    if (!user) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    // continue...
};
```

Notice something interesting:

The Repository says:

```text
No user.
```

The Service decides:

```text
For login, that means invalid credentials.
```

That's exactly why this separation is useful.

---

# 24. Same Repository, Different Meaning

Imagine another Service:

```js
const getUserProfile = async (userId) => {
    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Same Repository result:

```js
null
```

Different Service interpretation:

```text
Login
    ↓
Invalid credentials

Profile
    ↓
User not found
```

Excellent example of why the Repository shouldn't decide business meaning.

            new: true

Possible result:

```text
document
```

or:

```text

```

Again:

```text
null ≠ database failure

```

# 26. Delete Errors

Same concept:

```js
const remove = async (id) => {
    return User.findByIdAndDelete(id);
};
```

If nothing exists:

```js
null
```

Then:

```js
const deleted =
    await userRepository.remove(id);

if (!deleted) {
    throw new AppError(
        "User not found",
        404
    );
}
```

Again:

```text
Repository → data result
Service → meaning
```

# 27. Don't Catch Everything in Repository

Avoid this:

```js
const findById = async (id) => {
    try {
        return await User.findById(id);
    } catch (error) {
        console.log(error);

        throw new Error(
            "Repository failed"
        );
    }
};
```

Problems:

1. Original error information can be lost.
    
2. Stack trace can become less useful.
    
3. Error classification disappears.
    
4. Service cannot distinguish failures.
    
5. Debugging becomes harder.
    

Only catch when you have something useful to do.

---

# 28. Logging Repository Errors

Should Repository errors be logged?

Sometimes.

But be careful about duplicate logging.

For example:

```text
Repository logs error
       ↓
Service logs error
       ↓
Global middleware logs error
```

Now one failure produces:

```text
three log entries
```

This can become noisy.

A common approach is:

```text
Repository
    ↓
throw

Global error handler
    ↓
centralized logging
```

This works especially well with your broader architecture because your roadmap later includes logging and observability.

---

# 29. Error Context

Sometimes adding context is useful.

For example:

```js
try {
    return await User.create(data);
} catch (error) {
    error.operation = "User.create";
    throw error;
}
```

But don't blindly mutate errors everywhere.

A better long-term approach is often structured error handling where the error contains useful context.

For now, remember:

> Preserve enough information to diagnose the database operation that failed.

---

# 30. Repository Error Wrapper

You might eventually create a helper:

```js
const executeRepositoryOperation = async (
    operation,
    context
) => {
    try {
        return await operation();
    } catch (error) {
        // classify or attach context
        throw error;
    }
};
```

Then:

```js
const findById = async (id) => {
    return executeRepositoryOperation(
        () => User.findById(id),
        "User.findById"
    );
};
```

But don't introduce this abstraction too early.

For your learning stage:

```js
return User.findById(id);
```

is often better.

Understand the simple version first.

# 36. Don't Leak MongoDB Internals

Never return raw database errors directly to clients:

```js
res.json(error);
```

A raw error could expose:

```text
database name
collection name
query details
schema information
stack traces
internal paths
```

Instead:

```text
Internal error
      ↓
log detailed information
      ↓
client receives safe message
```

Your roadmap explicitly calls for hiding sensitive errors in production.

---

# 37. Development vs Production

During development, you may want:

```json
{
    "success": false,
    "message": "Cast to ObjectId failed...",
    "stack": "..."
}
```

to debug quickly.

Production should generally expose something much safer:

```json
{
    "success": false,
    "message": "Invalid user ID",
    "requestId": "abc123"
}
```

while your server logs contain the detailed error.

This is why:

```text
developer information
```

and:

```text
client information
```

should be treated differently.

# 39. The Repository Should Be Boring

This is actually a compliment.

Good Repository code often looks boring:

```js
const findById = async (id) => {
    return User.findById(id);
};

    return User.findOne({ email });
};

    return User.create(data);

```

You don't want:

```text

HTTP responses
JWT generation
emails
authorization
password comparison
```

inside it.

The Repository should mostly say:

> "Here's how I talk to the database."

# 40. What About `try/catch`?

Use this:

```js
const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        if (error.code === 11000) {
            throw new DuplicateKeyError(
                "User already exists"
            );
        }

        throw error;
    }
};
```

when you need to classify a known database condition.

But this:

```js
const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        throw error;
    }
};
```

adds no value.

# 41. A Good Rule

Ask yourself:

> **"Why am I catching this error?"**

If your answer is:

> "I need to transform it."

Good.

If:

> "I need to add useful context."

Potentially good.

If:

> "I don't know, but every function needs try/catch."

No.

That's a common beginner mistake.

|Concern|Repository|Service|
|---|---|---|

|`findById()`|✅|❌|

# 49. Interview Questions

### Q1. Should a Repository return HTTP status codes?

**No.**

The Repository is a data-access layer, not an HTTP layer.

---

### Q2. What should `findById()` return when nothing is found?

Usually:

```js
null
```

The Service can decide what that means.

---

### Q3. Is `null` the same as a database failure?

No.

```text
null
→ query succeeded, no matching document

exception
→ operation failed
```

---

### Q4. Should every Repository method have `try/catch`?

No.

Only catch when you need to handle, translate, enrich, or recover from an error.

---

### Q5. What is MongoDB duplicate key error code?

Commonly:

```text
11000
```

---

### Q6. Why shouldn't unknown errors be converted into generic errors?

Because doing so can destroy useful debugging information and stack traces.

# 51. The Code You Should Remember

### Simple Repository

```js
const findById = async (id) => {
    return User.findById(id);
};
```

### Known error translation

```js
const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        if (error.code === 11000) {
            throw new DuplicateKeyError(
                "User already exists"
            );
        }

        throw error;
    }
};
```

### Service interprets absence

```js
const getUser = async (id) => {
    const user =
        await userRepository.findById(id);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

This is the separation I want you to understand.

# ⭐ Final Mental Model

Don't think:

```text
Repository = error handler
```

Think:

```text
Repository
    ↓
Database interaction
    ↓
Known DB problem?
    ├── Yes → optionally translate it
    └── No  → let it propagate
```

Then:

```text
Service
    ↓
"What does this result mean
 for my application?"
```

Then:

```text
Controller / Error Middleware
    ↓
"What HTTP response should the client receive?"
```

So the complete architecture is:

```text
                 HTTP REQUEST
                      │
                      ▼
                  Controller
                      │
                      ▼
                   Service
                      │
                      ▼
                 Repository
                      │
                      ▼
                  MongoDB
                      │
              ┌───────┴───────┐
              │               │
           Success          Error
              │               │
              ▼               ▼
        document/null     known?
                              │
                         ┌────┴────┐
                         │         │
                        YES        NO
                         │         │
                         ▼         ▼
                     translate   rethrow
                         │         │
                         └────┬────┘
                              ▼
                           Service
                              │
                              ▼
                     Global Error Handler
                              │
                              ▼
                         HTTP Response
```

### 🔑 One sentence to remember

> **Repository handles database interaction; Service decides what the database result means; the HTTP layer decides how that meaning is communicated to the client.**

That separation will make **Lesson 13.20 — Testing Repositories** much easier, because we'll be able to test the Repository's database behavior independently from the Service and Controller.
