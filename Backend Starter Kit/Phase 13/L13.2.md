# Phase 13 — Repository Pattern & Data Access

## Lesson 13.2 — Why Services Shouldn't Directly Query MongoDB

In **13.1**, we learned the basic idea:

```text
Service
   ↓
Repository
   ↓
Model
   ↓
MongoDB
```

Today we answer the important question:

> **Why not simply let the Service call the Mongoose Model directly?**

The short answer is:

> **Because business logic and database-access logic are different responsibilities.**

Your starter-pack roadmap specifically separates the service layer from the repository layer, so this lesson is about understanding the reason behind that separation.

---

# 1. First, Let's Look at the Problem

Suppose we're building authentication.

We create:

```text
services/
└── auth.service.js
```

A beginner might write:

```js
import User from "../models/user.model.js";
import bcrypt from "bcrypt";

export const login = async (email, password) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new Error("Invalid credentials");
    }

    const isPasswordValid = await bcrypt.compare(
        password,
        user.password
    );

    if (!isPasswordValid) {
        throw new Error("Invalid credentials");
    }

    return user;
};
```

At first glance:

**What's wrong with this?**

Technically, nothing is immediately broken.

It works.

The problem appears as your application grows.

---

# 2. What Is Inside This Service?

Look carefully.

```js
const user = await User.findOne({ email });
```

This is:

> **Database access logic**

Then:

```js
bcrypt.compare(password, user.password);
```

This is:

> **Business/authentication logic**

So one function is doing two different jobs:

```text
login()
 ├── Database access
 └── Business logic
```

That's the problem.

---

# 3. Separate the Responsibilities

We want:

```text
Service
    ↓
Business logic

Repository
    ↓
Database access
```

So instead of:

```js
User.findOne({ email });
```

inside the service, we create:

```js
userRepository.findByEmail(email);
```

Now the service becomes:

```js
export const login = async (email, password) => {
    const user = await userRepository.findByEmail(email);

    if (!user) {
        throw new Error("Invalid credentials");
    }

    const isPasswordValid = await bcrypt.compare(
        password,
        user.password
    );

    if (!isPasswordValid) {
        throw new Error("Invalid credentials");
    }

    return user;
};
```

Much cleaner.

The service says:

> "I need the user associated with this email."

It doesn't say:

> "Use MongoDB's `findOne()` operation with this exact query."

---

# 4. Think About a Restaurant Again

Imagine you're running a restaurant.

The **service** is like the chef.

The chef decides:

```text
What should we prepare?
What ingredients are needed?
What recipe should be followed?
What should happen if an ingredient is unavailable?
```

The chef shouldn't need to know:

```text
Which storage shelf?
Which refrigerator?
Which supplier?
Which warehouse?
```

That's another responsibility.

Similarly:

```text
Service
 ↓
Business decisions
```

while:

```text
Repository
 ↓
Data retrieval/storage
```

---

# 5. The Service Should Speak in Business Terms

This is a very useful concept.

Compare these two:

### Database language

```js
User.findOne({ email });
```

### Application language

```js
userRepository.findByEmail(email);
```

The second one communicates intent more clearly.

It says:

> "Find a user by email."

The service doesn't care that MongoDB happens to be the current database.

---

# 6. Before Repository

Our architecture is:

```text
Controller
     ↓
Auth Service
     ↓
Mongoose Model
     ↓
MongoDB
```

The service knows about:

```text
Mongoose
MongoDB
User Model
MongoDB query syntax
```

So the dependency looks like:

```text
Auth Service
     │
     ├── Mongoose
     ├── User Model
     └── MongoDB query
```

That's fairly tightly coupled.

---

# 7. After Repository

Now:

```text
Controller
     ↓
Auth Service
     ↓
User Repository
     ↓
User Model
     ↓
MongoDB
```

The dependency becomes:

```text
Auth Service
     ↓
User Repository
```

The repository handles:

```text
Mongoose
MongoDB
queries
database-specific details
```

This reduces coupling between business logic and data-access implementation.

---

# 8. What Does "Coupling" Mean?

**Coupling** simply means:

> How strongly one piece of code depends on another piece of code.

High coupling:

```text
Service
 ↓
Mongoose
 ↓
MongoDB-specific code
```

The service knows many implementation details.

Lower coupling:

```text
Service
 ↓
Repository interface
```

The service only needs to know what the repository can do.

For example:

```js
userRepository.findByEmail(email);
```

---

# 9. A Real Refactoring

Let's start with a bad-ish architecture.

### `auth.service.js`

```js
import User from "../models/user.model.js";
import bcrypt from "bcrypt";

export const login = async (email, password) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new Error("Invalid credentials");
    }

    const validPassword = await bcrypt.compare(
        password,
        user.password
    );

    if (!validPassword) {
        throw new Error("Invalid credentials");
    }

    return user;
};
```

We want to move:

```js
User.findOne({ email })
```

out of the service.

---

# 10. Step 1 — Create Repository

Create:

```text
repositories/
└── user.repository.js
```

Then:

```js
import User from "../models/user.model.js";

export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Now MongoDB-related code lives here.

---

# 11. Step 2 — Use Repository in Service

Now modify the service:

```js
import * as userRepository from "../repositories/user.repository.js";
import bcrypt from "bcrypt";

export const login = async (email, password) => {
    const user = await userRepository.findByEmail(email);

    if (!user) {
        throw new Error("Invalid credentials");
    }

    const validPassword = await bcrypt.compare(
        password,
        user.password
    );

    if (!validPassword) {
        throw new Error("Invalid credentials");
    }

    return user;
};
```

Now look at the responsibilities.

### Repository

```js
findByEmail()
```

does:

```text
Database access
```

### Service

```js
login()
```

does:

```text
Authentication business logic
```

Much better.

---

# 12. Why Is This Better?

Imagine we add another authentication operation:

```text
refreshToken()
```

It needs a user.

Instead of writing:

```js
User.findById(...)
```

we can use:

```js
userRepository.findById(...)
```

Then:

```text
auth.service.js
      │
      ├── findByEmail()
      ├── findById()
      └── updateRefreshToken()
             │
             ▼
      user.repository.js
             │
             ▼
          User Model
```

The database operations stay in one place.

---

# 13. Centralizing Database Access

Suppose ten services need users.

Without a repository:

```text
auth.service
   ↓
User.findOne()

admin.service
   ↓
User.findOne()

profile.service
   ↓
User.findOne()

password.service
   ↓
User.findOne()

notification.service
   ↓
User.findOne()
```

Now imagine you need to change how users are retrieved.

You potentially have to inspect many services.

With a repository:

```text
auth.service ─────┐
admin.service ────┤
profile.service ──┤
password.service ┤
notification ─────┘
                   ↓
          user.repository
                   ↓
              User Model
```

The database-access boundary is centralized.

---

# 14. But Don't Put Everything in the Repository

This is where beginners can go too far.

Suppose you have:

```js
userRepository.loginUser()
```

and inside:

```js
const user = await User.findOne({ email });

const valid = await bcrypt.compare(
    password,
    user.password
);

const token = jwt.sign(...);
```

That's bad separation.

Why?

Because now the repository knows:

```text
Authentication
Password hashing
JWT
Business rules
```

The repository should remain focused on data access.

---

# 15. What Belongs in the Repository?

Good repository responsibilities:

```text
Find data
Create data
Update data
Delete data
Query data
Count data
Paginate data
Select fields
Apply database-specific operations
```

Examples:

```js
findById()
findByEmail()
create()
updateById()
deleteById()
count()
findMany()
```

---

# 16. What Belongs in the Service?

Good service responsibilities:

```text
Business rules
Decisions
Workflows
Combining operations
Permission decisions
Password verification
Token generation
Calling email services
Calling repositories
Transactions/business operations
```

For example:

```js
const login = async (email, password) => {
    const user = await userRepository.findByEmail(email);

    if (!user) {
        throw new AppError("Invalid credentials", 401);
    }

    const valid = await bcrypt.compare(
        password,
        user.password
    );

    if (!valid) {
        throw new AppError("Invalid credentials", 401);
    }

    const accessToken = generateAccessToken(user);

    return {
        user,
        accessToken
    };
};
```

That's clearly business/application logic.

---

# 17. What About the Model?

The model is responsible for the database representation.

For example:

```js
const userSchema = new mongoose.Schema({
    email: {
        type: String,
        required: true,
        unique: true
    },

    password: {
        type: String,
        required: true
    }
});
```

The model describes:

```text
What fields exist?
What types do they have?
What database constraints apply?
What indexes exist?
```

So we have:

```text
Service
→ business logic

Repository
→ data access

Model
→ database structure
```

---

# 18. The Three-Layer Rule

Memorize this:

```text
┌─────────────────────────┐
│        SERVICE          │
│                         │
│ What should happen?     │
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│       REPOSITORY        │
│                         │
│ How do I access data?   │
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│          MODEL          │
│                         │
│ What does data look     │
│ like?                   │
└─────────────────────────┘
```

This is one of the most useful mental models in this phase.

---

# 19. What Happens If We Change Database Technology?

This is one reason people use repositories.

Suppose your service currently uses:

```text
MongoDB
```

and your repository internally uses:

```js
User.findOne(...)
```

Later, your application architecture changes.

Maybe you move some data to another persistence system.

Your service ideally still says:

```js
userRepository.findByEmail(email);
```

The repository implementation can change.

This is called **decoupling**.

However, don't misunderstand this:

> A repository does **not** magically make switching MongoDB to PostgreSQL easy.

Your data model, queries, transactions, indexes, and behavior may all need changes.

The repository simply gives you a cleaner boundary for those changes.

# 20. Testing Becomes Easier

Consider this service:

```js
const login = async (email, password) => {
    const user = await userRepository.findByEmail(email);

    // business logic
};
```

When unit testing the service, we can conceptually provide:

```text
Fake Repository
       ↓
fake user
```

So the test can focus on:

```text
Does login correctly handle
valid password?
invalid password?
missing user?
etc.
```

It doesn't necessarily need to perform a real MongoDB query for every service unit test.

We'll explore mocking and dependency replacement much more in Phase 21.

# 21. One Important Nuance

The statement:

> "Services should never directly query MongoDB."

is a **design guideline**, not a universal law.

For a tiny Express project:

```text
Controller
 ↓
Service
 ↓
Model
```

might be completely reasonable.

For example:

```js
const getHealthInfo = async () => {
    return HealthCheck.findOne();
};
```

Creating a repository only for one tiny query could be unnecessary complexity.

As your application grows, though, a repository layer can provide a useful boundary.

So your mindset should be:

```text
Don't add abstractions because they look professional.

Add abstractions when they solve a real architectural problem.
```

That's an important professional habit.

---

# 22. A Practical Rule for Your MERN Projects

When you're deciding whether a database operation belongs directly in a service, ask:

### Question 1

> Is this code about MongoDB/Mongoose?

If yes, it probably belongs in the repository.

### Question 2

> Is this code deciding what the application should do?

If yes, it probably belongs in the service.

### Question 3

> Is this code describing the database structure?

If yes, it belongs in the model.

# 23. Example: Create User

Let's trace a signup request.

```text
POST /api/v1/auth/signup
```

### Controller

```js
const signup = async (req, res) => {
    const result = await authService.signup(req.body);

    res.status(201).json(result);
};
```

Controller handles:

```text
HTTP
```

---

### Service

```js
const signup = async ({ email, password }) => {
    const existingUser =
        await userRepository.findByEmail(email);

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const hashedPassword =
        await bcrypt.hash(password, 12);

    return userRepository.create({
        email,
        password: hashedPassword
    });
};
```

Service handles:

```text
Business decisions
```

---

### Repository

```js
const create = async (userData) => {
    return User.create(userData);
};
```

Repository handles:

```text
Database access
```

---

### Model

```js
const userSchema = new mongoose.Schema({
    email: String,
    password: String
});
```

Model handles:

```text
Database structure
```

# 24. Notice the Direction

The dependency direction is important:

```text
Controller
     ↓
Service
     ↓
Repository
     ↓
Model
     ↓
Database
```

Don't casually reverse it.

For example, you don't want:

```text
Repository
    ↓
Service
```

because then your data-access layer starts depending on business logic.

Keep the responsibilities flowing downward.

---

# 25. A Common Beginner Mistake

Someone learns Repository Pattern and creates:

```text
user.repository.js
```

Then copies every Model method into it:

```js
find()
findOne()
findById()
findOneAndUpdate()
findOneAndDelete()
findByIdAndUpdate()
findByIdAndDelete()
aggregate()
exists()
countDocuments()
estimatedDocumentCount()
...
```

Don't do that blindly.

Your repository should expose **meaningful operations your application actually needs**.

For example:

```js
findByEmail(email)
findById(id)
create(data)
updateProfile(id, data)
```

rather than exposing every possible Mongoose method.

This makes your repository interface easier to understand.

---

# 26. The Key Transformation

Remember this transformation.

### Before

```js
const user = await User.findOne({
    email
});
```

### After

```js
const user =
    await userRepository.findByEmail(email);
```

The first version talks in **database language**.

The second version talks in **application/data-access language**.

That's the real value.

# 28. Interview Question

### Why shouldn't a service directly query MongoDB?

A strong answer:

> **A service should primarily contain application and business logic. Direct database queries mix business logic with data-access concerns and tightly couple the service to the persistence layer. A repository provides a separate data-access boundary, making the code easier to maintain, test, and change.**

Simpler version:

> **Service decides what to do. Repository handles how to access the data.**
