# Phase 13 — Repository Pattern & Data Access

## Lesson 13.20 — Testing Repositories

🎯 **Goal:** Learn how to test the Repository layer separately from Controllers and Services.

This is the final lesson of Phase 13.

Your roadmap places **13.20 — Testing Repositories** here, after Repository errors. The phase then moves into **Phase 14 — Security Engineering**.

---

# 1. Why Test the Repository?

Our architecture is:

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

Each layer has a different responsibility.

So we should be able to test:

```text
Controller tests
       ↓
HTTP behavior

Service tests
       ↓
Business rules

Repository tests
       ↓
Database/data-access behavior
```

The Repository should answer questions such as:

> Did we actually query the correct collection?

> Did filtering work?

> Did sorting work?

> Did pagination work?

> Does `findById()` return `null` when nothing exists?

> Does the Repository correctly handle database errors?

---

# 2. What Are We Testing?

Remember what we built during Phase 13.

Our Repository may support:

```text
create
findById
findOne
findMany
update
delete
count
filter
sort
pagination
ownership
```

So our tests should verify those behaviors.

For example:

```text
findById()
    ↓
existing document → document

findById()
    ↓
missing document → null
```

And:

```text
findMany()
    ↓
filter
    ↓
sort
    ↓
pagination
    ↓
correct results
```

---

# 3. Repository Tests Should Be Focused

Suppose we have:

```js
const todoRepository = {
    findById,
    findMany,
    create,
    update,
    remove
};
```

Don't write one giant test:

```text
"Todo Repository works"
```

Instead:

```text
findById returns Todo
findById returns null
findMany filters by owner
findMany sorts correctly
findMany paginates correctly
create creates Todo
update updates Todo
remove deletes Todo
```

Each test should answer one clear question.

---

# 4. Unit Test vs Integration Test

This distinction is very important.

### Unit test

Tests code in isolation.

```text
Repository
   ↓
mock MongoDB
```

### Integration test

Tests the Repository against an actual test database.

```text
Repository
   ↓
real MongoDB test database
```

For a Repository layer, **integration tests are especially valuable** because the Repository's main job is communicating with the database.

---

# 5. Why Repository Tests Often Need a Database

Imagine this Repository:

```js
const findMany = async ({
    filter,
    sort,
    skip,
    limit
}) => {
    return Todo.find(filter)
        .sort(sort)
        .skip(skip)
        .limit(limit);
};
```

A mock can tell you:

```text
".find() was called"
```

But it doesn't necessarily prove:

```text
MongoDB actually filtered correctly
MongoDB actually sorted correctly
MongoDB actually paginated correctly
```

That's why integration testing is useful.

---

# 6. The Test Database

Never run Repository tests against your normal development database.

Don't do this:

```text
Your production DB
       ↓
Tests
       ↓
DELETE
CREATE
UPDATE
```

😨 That's dangerous.

Instead:

```text
Application DB
       ↓
normal application

Test DB
       ↓
automated tests
```

For example:

```text
myapp
myapp_test
```

---

# 7. Test Database Isolation

A good test should not depend on another test.

Bad:

```text
Test 1 creates Todo A

Test 2 expects Todo A

Test 3 modifies Todo A
```

Now if Test 1 fails:

```text
Test 2 fails
Test 3 fails
```

even though their own code might be correct.

Better:

```text
Test 1
  ↓
clean database
  ↓
run test

Test 2
  ↓
clean database
  ↓
run test
```

Each test gets a predictable environment.

---

# 8. Basic Test Lifecycle

A typical Repository integration test has:

```text
beforeAll
    ↓
connect to test DB

beforeEach
    ↓
clean/reset data

test
    ↓
execute Repository

afterAll
    ↓
disconnect
```

Conceptually:

```js
beforeAll(async () => {
    await connectTestDatabase();
});

beforeEach(async () => {
    await clearDatabase();
});

afterAll(async () => {
    await disconnectTestDatabase();
});
```

The exact testing framework can vary.

# 9. First Test: `findById()`

Suppose:

```js
const todo = await todoRepository.findById(todoId);
```

We want to test:

> If the Todo exists, does the Repository return it?

Setup:

```js
const todo = await Todo.create({
    title: "Learn Repository Testing",
    userId
});
```

Then:

```js
const result =
    await todoRepository.findById(todo._id);
```

Assertions:

```js
expect(result).not.toBeNull();
expect(result.title)
    .toBe("Learn Repository Testing");
```

---

# 10. Test the Missing Case

Now test:

> What happens when the Todo doesn't exist?

```js
const result =
    await todoRepository.findById(
        new ObjectId()
    );
```

Expected:

```js
expect(result).toBeNull();
```

This is important because we learned in Lesson 13.19:

```text
not found
    ↓
usually null
```

not:

```text
database failure
```

---

# 11. Test `create()`

Suppose:

```js
const todo = await todoRepository.create({
    title: "Learn testing",
    userId
});
```

We can verify:

```js
expect(todo.title)
    .toBe("Learn testing");

expect(todo.userId)
    .toEqual(userId);
```

But don't stop there.

We should verify that the record actually exists in the database:

```js
const saved =
    await Todo.findById(todo._id);

expect(saved).not.toBeNull();
```

This tests the actual Repository/database interaction.

---

# 12. Why This Is Better

Imagine your Repository accidentally becomes:

```js
const create = async (data) => {
    return {
        ...data,
        fake: true
    };
};
```

A weak unit test might pass if it only checks the returned object.

An integration test checks:

```text
Did MongoDB actually receive the document?
```

and catches the problem.

Suppose the Repository supports:

```js
findMany({
    filter: {
        userId
    }

```

Create:

```text
User A
 ├── Todo A
 ├── Todo B

User B
 └── Todo C
```

Then:

```js
const result =
    await todoRepository.findMany({
        filter: {
            userId: userA._id

```

Expected:

```text
Todo A
Todo B
```

and **not**:

```text
Todo C
```

# 14. Ownership Test

This connects directly to Lesson 13.15.

Suppose:

```text
User A
    ↓
Todo A

User B
    ↓
Todo B
```

Repository query:

```js
findMany({
    filter: {
        userId: userA._id
    }
});
```

Test:

```js
expect(result).toHaveLength(1);
expect(
    result[0].userId.toString()
).toBe(userA._id.toString());
```

This verifies that the Repository query respects the ownership filter supplied to it.

---

# 15. Important Architecture Point

The Repository doesn't necessarily decide:

> "The current logged-in user is User A."

The Service may build:

```js
const filter = {
    userId: currentUserId
};
```

Then Repository executes it.

So Repository testing verifies:

```text
Given this filter
       ↓
Does the Repository query correctly?
```

Service testing separately verifies:

```text
Did the Service create the correct filter?
```

This separation is extremely useful.

# 16. Testing Sorting

We learned in 13.18:

```js
.sort({
    createdAt: -1
});
```

means:

```text
newest → oldest
```

Create three Todos:

```text
Todo A → older
Todo B → newest
Todo C → middle
```

Then:

```js
const result =
    await todoRepository.findMany({
        sort: {
            createdAt: -1
        }
    });
```

Expected:

```text
Todo B
Todo C
Todo A
```

---

# 17. Sorting Test

A simple assertion:

```js
expect(result[0].title)
    .toBe("Todo B");

expect(result[1].title)
    .toBe("Todo C");

expect(result[2].title)
    .toBe("Todo A");
```

Now you're not just testing:

```text
".sort() was called"
```

You're testing:

> **Did sorting actually produce the expected database result?**

That's much stronger.

# 18. Testing Pagination

Suppose:

```text
10 Todos
```

and:

```text
limit = 3
page = 2
```

Then:

```text
skip = (2 - 1) × 3
     = 3
```

Expected results:

```text
Todo 4
Todo 5
Todo 6
```

Your test:

```js
const result =
    await todoRepository.findMany({
        sort: {
            createdAt: 1
        },
        page: 2,
        limit: 3
    });
```

Then:

```js
expect(result.items)
    .toHaveLength(3);
```

and verify the expected records.

---

# 19. Pagination + Sorting Test

This is especially important.

Don't only test:

```text
pagination works
```

and:

```text
sorting works
```

individually.

Also test:

```text
sorting + pagination
```

because that's a common source of bugs.

Example:

```text
10 records
sort newest first
page 2
limit 3
```

Expected:

```text
4th newest
5th newest
6th newest
```

---

# 20. Testing Total Count

Your Repository may return:

```js
{
    items,
    total
}
```

For:

```text
100 Todos
limit = 10
```

page 3 should return:

```text
items → 10
total → 100
```

Not:

```text
total → 10
```

The `total` represents the number of matching documents **before pagination**.

Test this explicitly.

---

# 21. Why `total` Matters

Frontend pagination needs:

```text
total = 100
limit = 10
```

to calculate:

```text
10 pages
```

If Repository accidentally counts after `.skip()` or `.limit()`, your frontend pagination becomes wrong.

So:

```js
expect(result.total)
    .toBe(100);
```

is an important Repository test.

Suppose:

```js
const result =
```

```text
 ↓
```

# 25. Testing Delete

Create:

```js
const todo = await Todo.create({
    title: "Delete me",
    userId
});
```

Then:

```js
const deleted =
    await todoRepository.remove(todo._id);
```

Verify:

```js

```

```js
const found =
    await Todo.findById(todo._id);

expect(found).toBeNull();
```

Now we know the document was actually removed.

# 26. Testing Delete of Missing Document

```js
const result =
    await todoRepository.remove(
        new ObjectId()
    );
```

Expected:

```js
expect(result).toBeNull();
```

Again, this isn't necessarily an error.

The Service decides whether:

```text
null → 404
```

or whether deletion should be idempotent.

# 27. Testing Repository Errors

We also learned about database errors.

We should test important known error conditions.

For example, suppose:

```js
email
```

is unique.

Try creating:

```text
user@example.com
```

twice.

First:

```js
await userRepository.create({
    email: "user@example.com"
});
```

Second:

```js
await userRepository.create({
    email: "user@example.com"
});
```

Expected:

```text
DuplicateKeyError
```

if your Repository translates the MongoDB duplicate-key error.

---

# 28. Why Test Error Translation?

Because this code:

```js
if (error.code === 11000) {
    throw new DuplicateKeyError(...);
}
```

is business/application infrastructure.

It can break.

For example, someone might accidentally write:

```js
if (error.code === 1100) {
```

Now duplicate errors aren't translated.

A test catches that regression.

---

# 29. Don't Test MongoDB Internals

You don't need tests like:

```text
"MongoDB supports sort()"
```

You're testing **your Repository code**, not MongoDB itself.

Bad test:

```text
Does MongoDB understand $text?
```

Better:

```text
Does our Repository correctly construct
and execute the search query?
```

---

# 30. What Should a Repository Test Prove?

Think:

```text
Input
  ↓
Repository
  ↓
Database
  ↓
Output
```

For example:

```text
filter
sort
page
limit
  ↓
Repository
  ↓
correct records
```

The test should prove that relationship.

# 31. Arrange → Act → Assert

A very useful testing pattern is:

```text
Arrange
   ↓
Act
   ↓
Assert
```

### Arrange

Prepare database state.

```js
await Todo.create({
    title: "Learn testing"
});
```

### Act

Call Repository.

```js
const result =
    await todoRepository.findMany();
```

### Assert

Verify result.

```js
expect(result.items).toHaveLength(1);
```

---

# 32. Example

```js
it("returns todos for the requested user", async () => {
    // Arrange
    const todo = await Todo.create({
        title: "User A Todo",
        userId: userA._id
    });

    await Todo.create({
        title: "User B Todo",
        userId: userB._id
    });

    // Act
    const result =
        await todoRepository.findMany({
            filter: {
                userId: userA._id
            }
        });

    // Assert
    expect(result.items).toHaveLength(1);

    expect(result.items[0].title)
        .toBe("User A Todo");
});
```

This is a clean Repository test.

---

# 33. Test Names Matter

Bad:

```js
it("works", ...)
```

Good:

```js
it("returns only todos belonging to the requested user", ...)
```

Good:

```js
it("returns todos sorted by createdAt descending", ...)
```

Good:

```js
it("returns null when the todo does not exist", ...)
```

A test name should explain the behavior being protected.

---

# 34. Test One Behavior

Avoid:

```js
it("tests everything", async () => {
    // create
    // update
    // delete
    // filter
    // sort
    // pagination
});
```

If it fails, you don't immediately know what broke.

Prefer:

```text
create creates Todo

findById returns Todo

findById returns null

findMany filters

findMany sorts

findMany paginates

update updates Todo

remove deletes Todo
```

Small tests are easier to debug.

---

# 35. Repository Test Structure

A clean structure could be:

```text
tests/
└── repositories/
    ├── user.repository.test.js
    └── todo.repository.test.js
```

Or colocated:

```text
src/
└── modules/
    └── todos/
        ├── todo.repository.js
        └── todo.repository.test.js
```

Both approaches can work.

For a larger modular backend, keeping tests close to their module can be convenient.

# 43. Testing Limits

Your Repository may normalize:

```text
limit
```

to a safe range.

For example:

```text
limit = 1000
```

might become:

```text
limit = 100
```

if the application has a maximum.

If that logic exists in your Repository, test it.

However, if the Service/validation layer owns this rule, test it there instead.

Again:

> Test the layer that owns the behavior.

---

# 44. Don't Duplicate Service Tests

Suppose the Service says:

```js
if (!todo) {
    throw new AppError(
        "Todo not found",
        404
    );
}
```

The Repository test shouldn't test:

```text
Does this become 404?
```

That's a Service/API concern.

Repository test:

```text
Does findById return null?
```

Service test:

```text
Does null become TodoNotFoundError?
```

Controller/error middleware test:

```text
Does TodoNotFoundError become HTTP 404?
```

That's layered testing.

---

# 45. Testing the Layers Separately

Imagine:

```text
Repository
    ↓
null
```

Test 1:

```text
Repository returns null
```

Then:

```text
Service
    ↓
TodoNotFoundError
```

Test 2:

```text
Service converts null into domain error
```

Then:

```text
Controller
    ↓
404
```

Test 3:

```text
HTTP layer returns 404
```

Each test has a single responsibility.

# 46. Mocking the Repository in Service Tests

This is where mocks become useful.

Suppose Service:

```js
const getTodo = async (id) => {
    const todo =
        await todoRepository.findById(id);

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todo;
};
```

Service test can mock:

```js
todoRepository.findById
```

to return:

```js
null
```

Then verify:

```text
Service throws 404 error
```

You don't need MongoDB for that Service test.

This gives us:

```text
Repository integration test
        ↓
real test DB

Service unit test
        ↓
mock Repository
```

Excellent separation.

---

# 47. Repository Tests vs Service Tests

|Test|Database?|Main goal|
|---|--:|---|
|Repository integration|Usually yes|Query/data behavior|
|Service unit|Usually no|Business rules|
|Controller unit|Usually no|HTTP behavior|
|API integration|Yes|Full request flow|

This layered strategy keeps tests fast and meaningful.

---

# 48. What About Transactions?

Your Repository layer may eventually use:

```js
session
```

and MongoDB transactions.

Then tests should verify:

```text
transaction starts
       ↓
operations execute
       ↓
commit
```

and failure:

```text
operation fails
       ↓
rollback
```

You don't need to implement that for today's lesson unless your current Repository uses transactions.

The important principle is:

> Test the data-access behavior your Repository actually owns.

---

# 49. What About Mocks?

Mocks can still be useful.

For example, you might mock:

```js
Todo.find
```

and verify:

```js
expect(Todo.find)
    .toHaveBeenCalledWith(filter);
```

This is useful for a **unit test**.

But it doesn't prove MongoDB actually behaves as expected.

So don't make mocks your only Repository testing strategy.

---

# 50. Best Strategy

For Repository code:

```text
Integration tests
       +
small number of focused unit tests
```

is often more valuable than mocking everything.

Why?

Because Repository code is fundamentally about:

```text
database ↔ application
```

and integration tests exercise that boundary.

---

# 51. A Practical Test Pyramid

Think:

```text
                E2E
               /  \
              /    \
         API tests
            /  \
           /    \
      Service tests
         /      \
        /        \
 Repository integration
────────────────────────
```

You generally want:

```text
many fast unit tests
some integration tests
fewer expensive end-to-end tests
```

But the Repository layer deserves real database coverage.

---

# 52. What If Tests Are Slow?

A common solution is:

```text
Test suite starts
      ↓
one MongoDB test instance
      ↓
reuse connection
      ↓
clear collections between tests
```

instead of:

```text
connect
disconnect
connect
disconnect
```

for every single test.

That can make the suite much faster.

---

# 53. Test Data Factories

As your application grows, manually creating data becomes repetitive.

Instead of:

```js
await Todo.create({
    title: "Todo 1",
    userId,
    priority: "high",
    ...
});
```

everywhere, create a factory/helper:

```js
const createTodo = (overrides = {}) => {
    return Todo.create({
        title: "Test Todo",
        userId,
        priority: "medium",
        ...overrides
    });
};
```

Then:

```js
await createTodo({
    title: "Important Todo",
    priority: "high"
});
```

This makes Repository tests shorter.

---

# 54. Test Fixtures

Another approach:

```text
fixtures/
    users
    todos
```

But don't create huge static fixtures for everything.

Prefer small, readable test data.

A test should make it obvious:

```text
why this data exists
```

---

# 55. Avoid Overusing Fixtures

Bad:

```text
100-line JSON fixture
```

for a test that only needs:

```text
title
userId
```

Better:

```js
await createTodo({
    title: "Test Todo",
    userId
});
```

Keep the test focused.

# 56. Testing Time-Based Sorting

This can be tricky.

If you create:

```js
await Todo.create({ title: "A" });
await Todo.create({ title: "B" });
```

and immediately sort by:

```js
createdAt
```

the timestamps may be extremely close.

Better test data can explicitly define dates:

```js
createdAt: new Date("2026-01-01")
```

and:

```js
createdAt: new Date("2026-01-05")
```

Now your test is deterministic.

# 57. Deterministic Tests

A good test should give the same result every time.

Avoid depending on:

```text
current time
random data
network
external APIs
existing database records
test execution order
```

unless the test specifically needs them.

For Repository tests:

```text
known data
+
known database
=
known result
```

# 60. Example Full Test

Here's a compact example:

```js
describe("TodoRepository.findMany", () => {
    it("filters, sorts and paginates todos", async () => {
        await Todo.create({
            title: "Old Todo",
            userId,
            createdAt: new Date("2026-01-01")
        });

        await Todo.create({
            title: "New Todo",
            userId,
            createdAt: new Date("2026-01-05")
        });

        const result =
            await todoRepository.findMany({
                filter: {
                    userId
                },
                sort: {
                    createdAt: -1
                },
                page: 1,
                limit: 1
            });

        expect(result.items)
            .toHaveLength(1);

        expect(result.items[0].title)
            .toBe("New Todo");

        expect(result.total)
            .toBe(2);
    });
});
```

This one test protects several important Repository behaviors.

However, in a real suite, I'd still keep separate tests for filtering, sorting, and pagination so failures are easier to identify.

Example:

```js
it("translates duplicate email errors", async () => {
    await userRepository.create({

        userRepository.create({
            email: "test@example.com"
```

The exact assertion depends on your error classes and testing framework.

The important concept is:

```text

       ↓
expected application error
```

# 62. Testing Unexpected Errors

If your Repository wraps errors, make sure unknown errors aren't silently swallowed.

For example, if your abstraction does something like:

```js
catch (error) {
    if (error.code === 11000) {
        throw new DuplicateKeyError();
    }

    throw error;
}
```

you should have confidence that:

```text
unknown error
    ↓
same error continues upward
```

This protects debugging and error handling.

---

# 63. Test the Contract, Not the Implementation

This is a very important testing principle.

Suppose today your Repository uses:

```js
Todo.find()
```

and tomorrow you change it to:

```js
Todo.aggregate()
```

If the behavior remains:

```text
same filter
same sort
same pagination
same output
```

your tests should still pass.

That's good.

Don't make tests unnecessarily depend on internal implementation details.

Test:

> **What the Repository promises.**

Not:

> **Exactly which Mongoose method it calls.**

---

# 64. Example of Bad Testing

```js
expect(Todo.find)
    .toHaveBeenCalledTimes(1);

expect(Todo.find)
    .toHaveBeenCalledWith(filter);
```

This can be useful in a unit test, but if that's your **only** test, you haven't proven the actual database behavior.

A stronger test checks:

```js
const result =
    await todoRepository.findMany(...);

expect(result.items)
    .toEqual(expected);
```

with a real test database.

# 69. Final Interview Questions

### Q1. Why should Repository tests often use a real test database?

Because the Repository's responsibility is database interaction, and a real database verifies that queries, filters, sorting, pagination, and persistence actually work.

### Q2. Should Repository tests use mocks?

They can, especially for unit tests, but mocks shouldn't be the only testing strategy for database-access code.

### Q3. What should happen when `findById()` doesn't find a document?

Usually return:

```js
null
```

and let the Service decide the business meaning.

### Q4. What should happen when MongoDB throws an unexpected error?

Allow it to propagate rather than hiding the original error.

### Q5. Why isolate the test database?

To prevent tests from modifying development/production data and to make tests deterministic.

### Q6. Why test sorting + pagination together?

Because pagination depends on ordering. A bug in ordering can change which records appear on each page.
