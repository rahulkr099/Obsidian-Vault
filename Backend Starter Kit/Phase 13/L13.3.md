# Phase 13 — Repository Pattern & Data Access

## Lesson 13.3 — Repository vs Model

This is one of the **most important distinctions in Phase 13**.

A common beginner question is:

> "If my Mongoose Model already gives me `findById()`, `findOne()`, `create()`, etc., then why do I need a Repository?"

Excellent question.

The answer is:

> **The Model represents the database structure and provides database capabilities. The Repository defines how your application accesses that data.**

Your starter-pack architecture separates repositories from models, so understanding this distinction is important before we build the actual repository layer.

---

# 1. First, Let's Look at a Mongoose Model

Suppose we have a User.

```js
import mongoose from "mongoose";

const userSchema = new mongoose.Schema(
    {
        name: {
            type: String,
            required: true
        },

        email: {
            type: String,
            required: true,
            unique: true
        },

        password: {
            type: String,
            required: true
        }
    },
    {
        timestamps: true
    }
);

const User = mongoose.model("User", userSchema);

export default User;
```

This creates our:

```text
User Model
```

The model gives us methods like:

```js
User.findById()
User.findOne()
User.find()
User.create()
User.findByIdAndUpdate()
User.findByIdAndDelete()
```

So you might think:

> "We already have everything."

Technically, yes.

But there is an important architectural difference.

---

# 2. What Is the Model?

Think of the Model as the **database-facing representation of an entity**.

For example:

```text
User Model
```

represents:

```text
User
├── name
├── email
├── password
├── createdAt
└── updatedAt
```

The Model knows about things such as:

```text
Schema
Types
Required fields
Indexes
Validation rules
Mongoose middleware/hooks
Database operations
```

So the Model is closely connected to:

```text
MongoDB
+
Mongoose
```

---

# 3. What Is the Repository?

The Repository sits above the Model.

```text
Service
   ↓
Repository
   ↓
Model
   ↓
MongoDB
```

The repository gives your application a cleaner interface for accessing the model.

For example:

```js
userRepository.findByEmail(email);
```

Internally:

```js
User.findOne({ email });
```

The service doesn't need to know that.

---

# 4. The Simplest Difference

Remember this:

```text
MODEL
↓
"What does a User look like?"

REPOSITORY
↓
"How does our application access Users?"
```

That's the heart of today's lesson.

---

# 5. Model Example

Suppose:

```js
const User = mongoose.model("User", userSchema);
```

You can write:

```js
const user = await User.findOne({
    email: "rahul@example.com"
});
```

This is directly using the Model.

The Model gives you a general database API.

---

# 6. Repository Example

Instead, we create:

```text
repositories/
└── user.repository.js
```

And:

```js
import User from "../models/user.model.js";

export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Now we can write:

```js
const user =
    await userRepository.findByEmail(email);
```

The difference might look small:

```text
User.findOne(...)
```

versus:

```text
userRepository.findByEmail(...)
```

But architecturally, they're quite different.

---

# 7. Model Gives Generic Database Operations

Mongoose gives us generic operations:

```js
User.find()
User.findOne()
User.findById()
User.create()
User.updateOne()
User.deleteOne()
```

These operations are database-oriented.

They answer:

> "What can I do with this MongoDB collection?"

---

# 8. Repository Gives Application-Oriented Operations

Your repository can provide operations such as:

```js
userRepository.findByEmail(email);
userRepository.findActiveUserById(userId);
userRepository.createUser(data);
userRepository.updateProfile(userId, data);
```

These answer:

> "What data operations does my application actually need?"

That's a much more meaningful interface.

---

# 9. Compare the Two

### Model

```js
User.findOne({
    email
});
```

The caller needs to know:

```text
User
findOne
MongoDB query
email field
```

### Repository

```js
userRepository.findByEmail(email);
```

The caller only needs to know:

```text
findByEmail
```

The repository hides the implementation.

---

# 10. Think of the Repository as a Translator

This is a useful analogy.

The Service speaks:

```text
Application language
```

The Model speaks:

```text
Database/Mongoose language
```

The Repository translates between them.

```text
Service
  │
  │ "Find user by email"
  ▼
Repository
  │
  │ User.findOne({ email })
  ▼
Model
  │
  ▼
MongoDB
```

So:

> **Repository = data-access translator/boundary**

---

# 11. Why Not Put `findByEmail()` Directly on the Model?

Another good question.

You could create a Mongoose static:

```js
userSchema.statics.findByEmail = function (email) {
    return this.findOne({ email });
};
```

Then:

```js
User.findByEmail(email);
```

That's possible.

But now `findByEmail()` becomes part of the **database model API**.

Your application still depends directly on the Mongoose Model.

With a repository:

```text
Service
   ↓
Repository
   ↓
Mongoose Model
```

the service has an additional abstraction boundary.

---

# 12. The Model Is Not the Repository

Don't think:

```text
Model = Repository
```

They are related, but they're not the same thing.

A Model is typically responsible for:

```text
Schema
Database representation
Mongoose behavior
Database operations
Indexes
Hooks
```

A Repository is responsible for:

```text
Application data-access operations
Queries needed by the application
Database-access abstraction
Query composition
Data retrieval patterns
```

---

# 13. Example: Finding an Active User

Imagine your User model has:

```js
isActive: {
    type: Boolean,
    default: true
}
```

The Model gives you:

```js
User.findOne(...)
```

Your application may repeatedly need:

> "Find the active user by ID."

Instead of repeating:

```js
User.findOne({
    _id: userId,
    isActive: true
});
```

in multiple services, create:

```js
userRepository.findActiveById(userId);
```

Repository:

```js
export const findActiveById = async (userId) => {
    return User.findOne({
        _id: userId,
        isActive: true
    });
};
```

Now the query is centralized.

---

# 14. Another Example: Safe User Lookup

Suppose you don't want to return:

```text
password
refreshTokenHash
resetTokenHash
```

to the application.

You might have:

```js
userRepository.findPublicById(userId);
```

Internally:

```js
return User.findById(userId).select(
    "name email createdAt"
);
```

The service can simply say:

```js
const user =
    await userRepository.findPublicById(userId);
```

This is a useful application-level operation.

---

# 15. Repository Can Hide Query Complexity

Imagine a more complicated query:

```js
User.findOne({
    _id: userId,
    isActive: true,
    deletedAt: null
})
.select("name email role")
.populate("profile");
```

If every service writes this:

```text
auth.service
admin.service
profile.service
notification.service
```

you get duplicated database logic.

Instead:

```js
userRepository.findActiveUserWithProfile(userId);
```

The complexity stays inside the repository.

---

# 16. This Is Where Repositories Become Valuable

The value isn't:

```text
User.findById()
```

becoming:

```text
userRepository.findById()
```

for no reason.

The value becomes much clearer when your application has:

```text
Complex queries
Repeated queries
Ownership queries
Filtering
Pagination
Sorting
Field selection
Population
Transactions
Database-specific behavior
```

Then the repository becomes a useful boundary.

---

# 17. Model vs Repository — Side-by-Side

|Model|Repository|
|---|---|
|Represents database entity|Represents application data access|
|Defines schema|Defines useful data operations|
|Mongoose-specific|Can hide Mongoose details|
|Knows database structure|Knows application query needs|
|Provides generic DB operations|Provides meaningful application operations|
|Closely tied to MongoDB|Acts as a boundary above the Model|

Think:

```text
Model = database representation

Repository = database access interface
```

# 18. Where Does Business Logic Go?

This is where the three layers become very clear.

Suppose we are logging in.

### Controller

```text
HTTP
```

### Service

```text
Business logic
```

### Repository

```text
Data access
```

### Model

```text
Database structure
```

So:

```text
                    LOGIN
                      │
                      ▼
                  Controller
                      │
                      ▼
                    Service
                 "Is login valid?"
                      │
                      ▼
                  Repository
                "Find the user."
                      │
                      ▼
                    Model
                "User structure"
                      │
                      ▼
                  MongoDB
```

# 19. A Complete Example

Let's build a tiny architecture.

## Model

```js
// user.model.js

const userSchema = new mongoose.Schema({
    name: String,
    email: String,
    password: String
});

const User = mongoose.model("User", userSchema);

export default User;
```

---

## Repository

```js
// user.repository.js

import User from "../models/user.model.js";

export const findByEmail = async (email) => {
    return User.findOne({ email });
};

export const findById = async (userId) => {
    return User.findById(userId);
};

export const create = async (data) => {
    return User.create(data);
};
```

---

## Service

```js
// user.service.js

import * as userRepository
    from "../repositories/user.repository.js";

export const getUserByEmail = async (email) => {
    const user =
        await userRepository.findByEmail(email);

    if (!user) {
        throw new Error("User not found");
    }

    return user;
};
```

Notice:

The Service doesn't write:

```js
User.findOne(...)
```

It says:

```js
userRepository.findByEmail(...)
```

---

# 20. What If We Don't Use Repository?

Then:

```js
import User from "../models/user.model.js";

export const getUserByEmail = async (email) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new Error("User not found");
    }

    return user;
};
```

Again:

**This isn't automatically wrong.**

This is an important professional distinction.

Repository architecture is useful when the complexity and size of your application justify the boundary.

---

# 21. Don't Over-Engineer

Imagine a tiny application:

```text
GET /health
```

and you create:

```text
HealthController
HealthService
HealthRepository
HealthModel
HealthFactory
HealthAdapter
HealthProvider
```

That's ridiculous.

You have created more architecture than the feature needs.

Good engineering means:

> **Use enough abstraction to keep responsibilities clear, but not so much that the architecture becomes harder than the problem.**

---

# 22. When Should You Consider a Repository?

Repositories become especially useful when you have:

### 1. Many database queries

```text
findByEmail
findById
findActive
findByRole
findPaginated
```

### 2. Multiple services using the same data

```text
Auth
User
Admin
Notification
```

### 3. Complex queries

```text
filter
sort
pagination
populate
aggregation
```

### 4. Strong testing requirements

You may want to test business logic without depending on a real database.

### 5. A larger codebase

The repository creates a clear data-access boundary.

---

# 23. Repository Does Not Mean "No MongoDB Knowledge"

This is another subtle point.

Your repository **can absolutely know MongoDB/Mongoose**.

In fact, that's usually where that knowledge belongs.

For example:

```js
User.findOne({
    email,
    isActive: true
});
```

That's perfectly reasonable inside the repository.

The important thing is that the **Service doesn't need to know those implementation details**.

---

# 24. A Better Mental Model

Don't memorize:

```text
Model
Repository
Service
```

as three random layers.

Think:

```text
MODEL
"What is the data?"

        ↓

REPOSITORY
"How do I access the data?"

        ↓

SERVICE
"What should I do with the data?"
```

Actually, in request flow:

```text
Service
   ↓
Repository
   ↓
Model
```

So when reading code, move downward.

# 28. Interview Question

### Q: What's the difference between a Mongoose Model and a Repository?

A strong answer:

> **A Mongoose Model represents a database entity and provides database-specific capabilities such as querying and persistence. A Repository sits above the Model and exposes application-specific data-access operations, hiding database implementation details from the service layer.**

Simpler:

> **Model talks in database/Mongoose terms. Repository talks in application data-access terms.**
