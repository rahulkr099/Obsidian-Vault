# Phase 13 — Repository Pattern & Data Access

## Lesson 13.4 — Repository vs Service

This is the lesson where the boundary between **Service** and **Repository** should become very clear.

The biggest question is:

> **When I'm writing backend code, how do I decide whether something belongs in the Service or the Repository?**

We'll learn a simple decision system that you can use while building your MERN projects.

---

# 1. The Basic Difference

Remember:

```text
SERVICE
↓
What should the application do?

REPOSITORY
↓
How should the application access the data?
```

For example:

```js
const user = await userRepository.findByEmail(email);
```

The Repository answers:

> "How do I find this user?"

Then the Service decides:

```js
if (!user) {
    throw new AppError("Invalid credentials", 401);
}
```

The Service answers:

> "What should happen if the user doesn't exist?"

---

# 2. Think of Them as Two Different Questions

Whenever you're unsure, ask:

### Question A

> **Is this about getting/saving/querying data?**

If yes → **Repository**

### Question B

> **Is this about deciding what the application should do?**

If yes → **Service**

This simple rule will solve a large number of architectural decisions.

---

# 3. Example: Login

Suppose we have:

```js
const login = async (email, password) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new AppError("Invalid credentials", 401);
    }

    const valid = await bcrypt.compare(
        password,
        user.password
    );

    if (!valid) {
        throw new AppError("Invalid credentials", 401);
    }

    return generateAccessToken(user);
};
```

There are several different responsibilities here.

Let's identify them.

---

# 4. `User.findOne()`

```js
const user = await User.findOne({ email });
```

This is:

```text
Database access
```

Therefore:

```text
Repository
```

We move it to:

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

---

# 5. Checking Whether User Exists

```js
if (!user) {
    throw new AppError("Invalid credentials", 401);
}
```

This is an application decision.

The application is deciding:

> "A login cannot continue without a valid user."

Therefore:

```text
Service
```

---

# 6. Comparing Password

```js
const valid = await bcrypt.compare(
    password,
    user.password
);
```

This is part of authentication/business logic.

Therefore:

```text
Service
```

Not Repository.

The Repository should not know:

```text
Why are we checking the password?
What is login?
What does authentication mean?
```

It should only handle data access.

---

# 7. Generating the Token

```js
const token = generateAccessToken(user);
```

Again:

```text
Authentication/business operation
```

Therefore:

```text
Service
```

---

# 8. Final Architecture

We end up with:

### Repository

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

### Service

```js
const login = async (email, password) => {
    const user = await userRepository.findByEmail(email);

    if (!user) {
        throw new AppError("Invalid credentials", 401);
    }

    const valid = await bcrypt.compare(
        password,
        user.password
    );

    if (!valid) {
        throw new AppError("Invalid credentials", 401);
    }

    return generateAccessToken(user);
};
```

Now the boundary is clear.

---

# 9. Repository = Data Operations

Typical Repository responsibilities:

```text
CREATE
READ
UPDATE
DELETE
QUERY
COUNT
PAGINATE
SORT
FILTER
```

For example:

```js
userRepository.create(data);

userRepository.findById(id);

userRepository.findByEmail(email);

userRepository.updateById(id, data);

userRepository.deleteById(id);
```

These operations are about **data**.

---

# 10. Service = Business Operations

Typical Service responsibilities:

```text
Register user
Login user
Change password
Deactivate account
Place order
Cancel order
Approve application
Process payment
Send verification workflow
```

Notice something interesting.

These are **business concepts**, not database concepts.

For example:

```js
authService.login(email, password);
```

is meaningful to the application.

But:

```js
userRepository.findByEmail(email);
```

is meaningful to the data layer.

---

# 11. Compare the Names

This is a useful trick.

### Repository names often sound like:

```text
findById()
findByEmail()
findMany()
create()
update()
delete()
count()
exists()
```

They describe **data operations**.

### Service names often sound like:

```text
login()
register()
verifyEmail()
changePassword()
resetPassword()
activateAccount()
deactivateAccount()
```

They describe **business operations**.

This isn't a strict rule, but it's a very useful signal.

---

# 12. Example: Registration

Suppose a user registers.

The workflow might be:

```text
1. Check whether email exists
2. Hash password
3. Create user
4. Generate verification token
5. Send verification email
```

Let's divide this.

### Step 1

```js
userRepository.findByEmail(email);
```

Repository.

### Step 2

```js
bcrypt.hash(password, 12);
```

Service.

### Step 3

```js
userRepository.create(userData);
```

Repository.

### Step 4

```js
verificationService.createToken(user);
```

Service/application logic.

### Step 5

```js
emailService.sendVerificationEmail(...);
```

Service/application workflow.

So:

```text
SERVICE
   │
   ├── Repository
   ├── Password hashing
   ├── Token service
   └── Email service
```

The Service orchestrates the workflow.

---

# 13. The Service Is an Orchestrator

This is one of the best ways to understand the Service layer.

The Service often **coordinates multiple operations**.

For example:

```text
register()
    │
    ├── check user
    │       ↓
    │   Repository
    │
    ├── hash password
    │
    ├── create user
    │       ↓
    │   Repository
    │
    ├── create verification token
    │
    └── send email
```

The Service decides the sequence.

The Repository doesn't.

---

# 14. Repository Shouldn't Orchestrate Business Workflows

Bad:

```js
const registerUser = async (data) => {
    const existing = await User.findOne(...);

    if (existing) {
        throw new Error("Already exists");
    }

    const hashedPassword = await bcrypt.hash(...);

    const user = await User.create(...);

    await sendVerificationEmail(user);

    return user;
};
```

This repository is doing:

```text
Database
+
Business rules
+
Password hashing
+
Email
+
Registration workflow
```

That's too much responsibility.

---

# 15. Better

### Repository

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};

const create = async (data) => {
    return User.create(data);
};
```

### Service

```js
const register = async ({ email, password }) => {
    const existing =
        await userRepository.findByEmail(email);

    if (existing) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const hashedPassword =
        await bcrypt.hash(password, 12);

    const user =
        await userRepository.create({
            email,
            password: hashedPassword
        });

    // verification workflow...

    return user;
};
```

Now the responsibilities are clean.

---

# 16. What About Validation?

This can be confusing because there are multiple kinds of validation.

Suppose:

```text
email must be valid
password must be at least 8 characters
```

Request/input validation:

```text
Validation layer / middleware
```

Business validation:

```text
Service
```

Database validation:

```text
Model
```

For example:

### Request validation

```js
email: z.string().email()
```

### Business rule

```js
if (existingUser) {
    throw new AppError("Email already registered", 409);
}
```

### Database constraint

```js
email: {
    type: String,
    unique: true
}
```

These are different responsibilities.

---

# 17. What About Ownership?

Suppose we have:

```text
User
Note
```

A note belongs to a user.

We might write:

```js
const note = await noteRepository.findById(noteId);

if (note.userId.toString() !== userId) {
    throw new AppError("Forbidden", 403);
}
```

Here:

```js
noteRepository.findById()
```

→ Repository.

But:

```js
note.userId !== userId
```

→ authorization/business decision.

Therefore:

```text
Service
```

---

# 18. But Could the Repository Query Ownership?

Yes.

And this is where things become more interesting.

Instead of:

```js
const note = await noteRepository.findById(noteId);

if (note.userId.toString() !== userId) {
    throw ...
}
```

we could have:

```js
const note =
    await noteRepository.findByIdForUser(
        noteId,
        userId
    );
```

Repository:

```js
const findByIdForUser = async (noteId, userId) => {
    return Note.findOne({
        _id: noteId,
        userId
    });
};
```

This is still data access.

The repository is simply performing a more specific query.

The **decision about what to do when no note is found** still belongs to the Service.

We'll explore this carefully in **13.15 — Ownership Queries**.

---

# 19. Repository Can Contain Query Rules

Don't confuse:

```text
query logic
```

with:

```text
business logic
```

A repository can absolutely contain:

```js
const findActiveByEmail = async (email) => {
    return User.findOne({
        email,
        isActive: true
    });
};
```

That's query logic.

But something like:

```js
if (!user) {
    throw new AppError("You cannot login");
}
```

is an application decision.

That's service logic.

---

# 20. A Very Useful Test

When you're unsure where code belongs, ask:

> **"If I changed MongoDB to PostgreSQL, would this piece of code need to change?"**

If the answer is **yes because the code uses database-specific querying**, it's likely Repository/Model territory.

Example:

```js
User.findOne({ email });
```

Definitely database-specific.

---

Now ask:

> **"If the business requirement changes, would this code need to change?"**

For example:

```js
if (user.isSuspended) {
    throw new AppError(
        "Account suspended",
        403
    );
}
```

That's a business rule.

So it belongs in the Service.

This two-question test is extremely useful.

---

# 21. Another Practical Test

Ask:

> **Can I describe this function without mentioning the database?**

### Repository

```js
findByEmail(email)
```

Yes.

It means:

> Find a user by email.

### Service

```js
login(email, password)
```

Yes.

It means:

> Perform the login process.

### Database-specific implementation

```js
User.findOne({ email })
```

No.

It explicitly mentions Mongoose/database behavior.

That's repository territory.

---

# 22. Service Should Not Know Query Syntax

Avoid this:

```js
const user = await User.findOne({
    email,
    isActive: true,
    deletedAt: null
})
.select("name email role")
.populate("profile");
```

inside a service.

The service shouldn't need to understand:

```text
findOne()
select()
populate()
MongoDB query objects
```

Instead:

```js
const user =
    await userRepository.findActiveUserProfile(userId);
```

Now the service communicates intent.

---

# 23. Repository Should Not Know Why Data Is Needed

This is equally important.

Suppose:

```js
userRepository.findByEmail(email);
```

The repository shouldn't care whether the user is being retrieved for:

```text
login
password reset
admin lookup
profile page
notification
```

Its job is simply:

> Retrieve the requested data.

The Service knows **why** it needs it.

---

# 24. A Powerful Rule

Here's a rule worth writing in your notes:

> **The Repository knows "how". The Service knows "why".**

Example:

```text
Why do we need the user?
→ Login
→ Service

How do we find the user?
→ Query by email
→ Repository
```

Another example:

```text
Why do we update the order?
→ Customer cancelled it
→ Service

How do we update it?
→ Order.findByIdAndUpdate(...)
→ Repository
```

This distinction is incredibly useful.

# 25. Repository vs Service Example

Let's build an order cancellation workflow.

User requests:

```text
POST /orders/123/cancel
```

### Controller

```js
await orderService.cancelOrder(
    orderId,
    userId
);
```

### Service

```js
const cancelOrder = async (orderId, userId) => {
    const order =
        await orderRepository.findByIdForUser(
            orderId,
            userId
        );

    if (!order) {
        throw new AppError(
            "Order not found",
            404
        );
    }

    if (order.status === "shipped") {
        throw new AppError(
            "Shipped orders cannot be cancelled",
            409
        );
    }

    return orderRepository.updateStatus(
        orderId,
        "cancelled"
    );
};
```

### Repository

```js
const findByIdForUser = async (
    orderId,
    userId
) => {
    return Order.findOne({
        _id: orderId,
        userId
    });
};

const updateStatus = async (
    orderId,
    status
) => {
    return Order.findByIdAndUpdate(
        orderId,
        { status },
        { new: true }
    );
};
```

Look at the separation.

---

# 26. Repository

Handles:

```text
Find order
Update order
```

### Service

Handles:

```text
Does the order exist?
Does the user own it?
Can a shipped order be cancelled?
What should the new status be?
```

This is exactly the boundary we want.

---

# 27. The "Why" vs "How" Rule

Let's reinforce it.

### Repository

```text
HOW?
```

Examples:

```text
How do I find the user?
How do I update the order?
How do I delete the note?
How do I paginate products?
```

### Service

```text
WHY?
```

Examples:

```text
Why are we finding this user?
Why are we updating this order?
Why are we deleting this note?
Why should this workflow continue?
```

This is a simplified rule, but extremely effective.

---

# 28. Common Mistake #1

Putting business rules into Repository:

```js
const cancelOrder = async (orderId) => {
    const order = await Order.findById(orderId);

    if (order.status === "shipped") {
        throw new Error("Cannot cancel");
    }

    return Order.findByIdAndUpdate(...);
};
```

The repository now knows:

> "Shipped orders cannot be cancelled."

That's a business rule.

Move it to Service.

---

# 29. Common Mistake #2

Putting database queries into Service:

```js
const cancelOrder = async (...) => {
    const order = await Order.findOne({
        _id: orderId,
        userId
    });

    // ...
};
```

Now the Service knows MongoDB query details.

Move the query to Repository:

```js
orderRepository.findByIdForUser(
    orderId,
    userId
);
```

---

# 30. Common Mistake #3

Putting HTTP logic into Service

Bad:

```js
const login = async (req, res) => {
    // ...
    return res.status(200).json(...);
};
```

The Service shouldn't know:

```text
req
res
status()
json()
HTTP headers
```

That's Controller territory.

---

# 31. Three-Layer Decision Table

|Code|Layer|
|---|---|
|`req.body`|Controller|
|`res.status()`|Controller|
|`bcrypt.compare()`|Service|
|`generateAccessToken()`|Service|
|`userRepository.findByEmail()`|Service calling Repository|
|`User.findOne()`|Repository|
|`User.findByIdAndUpdate()`|Repository|
|`mongoose.Schema()`|Model|
|`unique: true`|Model|
|"User cannot cancel shipped order"|Service|
|"Find order belonging to user"|Repository query|

This table is worth remembering.

# 32. One Subtle Point: Repository Return Values

Suppose:

```js
const user = await userRepository.findByEmail(email);
```

The Repository should generally return data:

```js
return User.findOne({ email });
```

It doesn't usually decide:

```js
if (!user) {
    throw new AppError(...);
}
```

Why?

Because different services might have different requirements.

One service might say:

```text
Missing user = 404
```

Another might say:

```text
Missing user = create a new user
```

Another might say:

```text
Missing user = return null
```

The Repository shouldn't blindly impose business behavior.

---

# 33. Repository Should Be Predictable

A good repository method has a clear contract.

For example:

```js
findByEmail(email)
```

could mean:

> Return the matching user or `null` if no user exists.

Then the Service decides what to do with `null`.

This makes the repository reusable.

---

# 34. Don't Make Repositories Too Smart

Avoid a repository like:

```js
const findUserForLogin = async (email, password) => {
    // find user
    // compare password
    // check suspension
    // check email verification
    // generate token
};
```

This is not really a data-access method anymore.

It's a business workflow.

Better:

```js
findByEmail(email)
```

and let the Service handle:

```text
password
suspension
verification
token
```

---

# 35. The Service Can Call Multiple Repositories

This is another major advantage.

Suppose registration needs:

```text
User
Profile
VerificationToken
```

Service:

```js
const register = async (data) => {
    const existing =
        await userRepository.findByEmail(data.email);

    if (existing) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const user =
        await userRepository.create(data);

    await profileRepository.create({
        userId: user._id
    });

    await verificationRepository.create({
        userId: user._id
    });

    return user;
};
```

The Service coordinates:

```text
User Repository
Profile Repository
Verification Repository
```

The repositories don't coordinate the business workflow.

# 37. A Practical Coding Workflow

When implementing a feature, try this order:

### Step 1 — Describe the business operation

Example:

```text
"User changes their password."
```

That's Service territory.

### Step 2 — Identify required data

```text
Need user
Need current password
Need new password
```

### Step 3 — Define repository operations

```text
findById()
updatePassword()
```

### Step 4 — Implement the Repository

```js
User.findById(...)
User.findByIdAndUpdate(...)
```

### Step 5 — Implement Service logic

```text
Check user
Check old password
Hash new password
Update password
```

This workflow keeps the architecture clean.

# 38. The Biggest Mental Shift

Don't think:

> "Where should I put this file?"

Think:

> **"What responsibility does this piece of code have?"**

That's a much better software-engineering question.

For example:

```js
User.findOne(...)
```

Don't ask:

> "Should this be in user.service.js?"

Ask:

> "What responsibility does this code have?"

Answer:

> Database access.

Therefore:

> Repository.

# 40. Interview Question

### Q: What is the difference between a Service and a Repository?

A strong answer:

> **A Service contains application and business logic and coordinates workflows. A Repository handles data-access operations and hides database-specific query details from the Service.**

Even simpler:

> **Service decides what should happen. Repository handles how data is accessed.**

And the rule to remember:

```text
SERVICE     → WHY?
REPOSITORY  → HOW?
MODEL       → WHAT?
CONTROLLER  → HTTP?
```
