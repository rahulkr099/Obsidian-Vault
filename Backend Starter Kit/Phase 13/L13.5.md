# Phase 13 — Repository Pattern & Data Access

## Lesson 13.5 — CRUD Repository Operations

Now we move from **understanding repositories** to actually **building them**.

So far:

```text
13.1 → What is Repository Pattern?
13.2 → Why separate database access?
13.3 → Repository vs Model
13.4 → Repository vs Service
```

Today:

> **How do we design the basic CRUD operations inside a Repository?**

CRUD means:

```text
C → Create
R → Read
U → Update
D → Delete
```

These four operations form the foundation of most repository implementations.

---

# 1. First, What Does CRUD Mean?

Suppose we have:

```text
User
```

CRUD operations are:

|Operation|Meaning|Example|
|---|---|---|
|Create|Add data|Create user|
|Read|Get data|Find user|
|Update|Modify data|Change user name|
|Delete|Remove data|Delete user|

In MongoDB/Mongoose, these might correspond to:

```js
User.create()
User.find()
User.findOne()
User.findById()

User.findByIdAndUpdate()

User.findByIdAndDelete()
```

But remember:

> **These Mongoose methods belong inside the Repository when we're using the Repository architecture.**

---

# 2. Our Architecture

We currently have:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
    ↓
MongoDB
```

For CRUD:

```text
Service
   ↓
userRepository.create()
   ↓
User.create()
   ↓
MongoDB
```

or:

```text
Service
   ↓
userRepository.findById()
   ↓
User.findById()
   ↓
MongoDB
```

---

# 3. Why Not Just Expose Mongoose Directly?

We could write:

```js
User.findById(id);
```

But our Service would now depend directly on Mongoose.

Instead:

```js
userRepository.findById(id);
```

The Repository hides:

```js
User.findById(id);
```

This gives us a cleaner boundary.

---

# 4. Our First Repository

Let's imagine this structure:

```text
src/
├── models/
│   └── user.model.js
│
├── repositories/
│   └── user.repository.js
│
├── services/
│   └── user.service.js
│
└── controllers/
    └── user.controller.js
```

We'll start with:

```js
// user.repository.js

import User from "../models/user.model.js";
```

Now we can build our CRUD methods.

---

# 5. CREATE

The first operation is:

```text
Create a new document.
```

Mongoose provides:

```js
User.create(data);
```

Our repository wraps it:

```js
export const create = async (data) => {
    return User.create(data);
};
```

Now the Service uses:

```js
const user = await userRepository.create(data);
```

Notice the separation:

```text
Service
    ↓
create(data)
    ↓
Repository
    ↓
User.create(data)
```

---

# 6. Why Call It `create()`?

We could name it:

```js
createUser()
```

or:

```js
insertUserIntoMongoDB()
```

But usually:

```js
create()
```

is enough when the repository is already clearly named:

```js
userRepository.create()
```

So:

```js
userRepository.create(data);
```

naturally means:

> Create a User.

---

# 7. CREATE Is Still Data Access

Important:

```js
User.create(data);
```

belongs to Repository.

But things like:

```js
if (emailAlreadyExists) {
    throw new AppError(...);
}
```

belong to Service.

So:

```text
Repository
→ save data

Service
→ decide whether data should be saved
```

---

# 8. Example: User Registration

Suppose:

```js
const register = async (data) => {
    const existingUser =
        await userRepository.findByEmail(data.email);

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const user =
        await userRepository.create(data);

    return user;
};
```

The Service decides:

> Should we create this user?

The Repository performs:

> Create this user in MongoDB.

---

# 9. READ

Read operations are slightly broader because there are many ways to read data.

For example:

```text
Find one
Find by ID
Find many
Find by email
Find active users
Find users by role
```

Let's start with the basic one.

---

# 10. `findById()`

Repository:

```js
export const findById = async (userId) => {
    return User.findById(userId);
};
```

Service:

```js
const user = await userRepository.findById(userId);
```

Again:

```text
Service
    ↓
findById(userId)
    ↓
Repository
    ↓
User.findById(userId)
```

---

# 11. `findByEmail()`

This is another common operation.

Repository:

```js
export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Service:

```js
const user =
    await userRepository.findByEmail(email);
```

Notice something important.

The Repository method:

```js
findByEmail()
```

is more meaningful than forcing the Service to know:

```js
User.findOne({ email });
```

The Repository hides the query implementation.

---

# 12. `findMany()`

Suppose we want many users.

Repository:

```js
export const findMany = async () => {
    return User.find();
};
```

Service:

```js
const users =
    await userRepository.findMany();
```

This is the basic version.

Later we'll improve it with:

```text
filtering
sorting
pagination
field selection
```

---

# 13. READ Is Not Always `find()`

Don't think:

```text
READ = find()
```

Read means retrieving data.

Depending on the requirement, we may use:

```js
User.findById()
User.findOne()
User.find()
```

The Repository chooses the appropriate database operation.

For example:

```js
userRepository.findByEmail(email);
```

could internally use:

```js
User.findOne({ email });
```

---

# 14. UPDATE

Now we need to modify existing data.

For example:

```text
Change user name.
```

Mongoose provides several methods.

One common option:

```js
User.findByIdAndUpdate()
```

Repository:

```js
export const updateById = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data,
        { new: true }
    );
};
```

---

# 15. Why `{ new: true }`?

This is important.

Suppose the existing user is:

```json
{
    "_id": "123",
    "name": "Rahul"
}
```

We update:

```js
{
    name: "Rahul Kumar"
}
```

Without:

```js
{ new: true }
```

Mongoose's update method may return the **old document**.

With:

```js
{ new: true }
```

we ask for the updated document.

So:

```js
return User.findByIdAndUpdate(
    userId,
    data,
    { new: true }
);
```

means:

> Find this user, update it, and return the updated version.

---

# 16. UPDATE Example

Service:

```js
const updateProfile = async (userId, data) => {
    const user =
        await userRepository.updateById(
            userId,
            data
        );

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Repository:

```js
const updateById = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data,
        { new: true }
    );
};
```

Again:

```text
Repository
→ performs update

Service
→ decides what missing user means
```

---

# 17. DELETE

Finally:

```text
Delete a document.
```

Repository:

```js
export const deleteById = async (userId) => {
    return User.findByIdAndDelete(userId);
};
```

Service:

```js
const deleteUser = async (userId) => {
    const deletedUser =
        await userRepository.deleteById(userId);

    if (!deletedUser) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return deletedUser;
};
```

Again, the Repository performs the database operation.

---

# 18. Our Basic CRUD Repository

We now have:

```js
import User from "../models/user.model.js";

export const create = async (data) => {
    return User.create(data);
};

export const findById = async (userId) => {
    return User.findById(userId);
};

export const findByEmail = async (email) => {
    return User.findOne({ email });
};

export const findMany = async () => {
    return User.find();
};

export const updateById = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data,
        { new: true }
    );
};

export const deleteById = async (userId) => {
    return User.findByIdAndDelete(userId);
};
```

This is already a useful starting point.

---

# 19. But We Need to Be Careful

This repository is simple, but there's a problem with blindly exposing:

```js
updateById(userId, data)
```

Imagine the Service sends:

```js
{
    role: "admin"
}
```

Now the user might accidentally become an admin.

So:

```js
updateById(id, data)
```

is powerful.

In production code, we often create more specific operations.

For example:

```js
updateProfile()
```

instead of allowing arbitrary fields.

We'll learn more about this later.

---

# 20. Generic vs Specific Repository Methods

Compare:

### Generic

```js
updateById(id, data);
```

### Specific

```js
updateProfile(id, profileData);
```

The generic method is flexible.

The specific method gives stronger control.

For example:

```js
export const updateProfile = async (
    userId,
    data
) => {
    return User.findByIdAndUpdate(
        userId,
        {
            name: data.name,
            bio: data.bio
        },
        { new: true }
    );
};
```

Now only allowed fields are updated.

This is a pattern we'll revisit during security and validation.

---

# 21. CRUD Does Not Mean One Method Only

A repository might eventually contain:

```text
CREATE
├── create()

READ
├── findById()
├── findByEmail()
├── findMany()
├── findActive()
└── findByRole()

UPDATE
├── updateById()
├── updateProfile()
└── updatePassword()

DELETE
├── deleteById()
└── softDelete()
```

That's normal.

CRUD is a category, not a fixed four-function API.

---

# 22. Hard Delete vs Soft Delete

This is an important future concept.

### Hard delete

```js
User.findByIdAndDelete(id);
```

The document is actually removed.

### Soft delete

Instead of removing it:

```js
User.findByIdAndUpdate(
    id,
    {
        deletedAt: new Date()
    },
    { new: true }
);
```

The document remains in the database.

The Repository might expose:

```js
userRepository.softDelete(userId);
```

The Service doesn't need to know how soft deletion is implemented.

---

# 23. Repository Methods Should Have Clear Names

Good:

```text
findById()
findByEmail()
findActiveById()
create()
updateProfile()
deleteById()
```

Less clear:

```text
getData()
process()
handle()
doQuery()
execute()
```

A repository method name should communicate **what data operation is being performed**.

---

# 24. Avoid Mongoose Names Everywhere

Suppose you expose:

```js
userRepository.findOne({
    email
});
```

Now your Service still needs to know Mongoose-style query objects.

That's not ideal.

Better:

```js
userRepository.findByEmail(email);
```

The Repository should provide a useful interface rather than simply forwarding every Mongoose API.

---

# 25. Repository Is Not Just a Wrapper

This is an important point.

At first, it may look like:

```js
User.findById(id);
```

becomes:

```js
userRepository.findById(id);
```

and that's all.

But eventually the Repository can encapsulate:

```text
complex queries
filters
sorting
pagination
field selection
population
transactions
database-specific optimizations
```

For example:

```js
userRepository.findActiveUsers({
    page,
    limit,
    sort
});
```

might internally construct a much more complicated Mongoose query.

The Service remains clean.

---

# 26. CRUD and Business Logic

Let's take:

```js
const deleteUser = async (userId) => {
    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    if (user.role === "superadmin") {
        throw new AppError(
            "Superadmin cannot be deleted",
            403
        );
    }

    return userRepository.deleteById(userId);
};
```

Where is everything?

### Repository

```js
findById()
deleteById()
```

### Service

```js
if (!user)
```

and:

```js
if (user.role === "superadmin")
```

Those are application decisions.

This distinction should now feel natural.

---

# 27. What Does the Repository Return?

A Repository commonly returns:

### Create

```text
Created document
```

### Find one

```text
Document
or null
```

### Find many

```text
Array
```

### Update

Depending on the method/options:

```text
Updated document
or null
```

### Delete

Often:

```text
Deleted document
or null
```

The Service then decides how to interpret those results.

---

# 28. Why Return `null` Instead of Throwing?

Suppose:

```js
const user = await userRepository.findById(id);
```

If the user doesn't exist:

```js
null
```

The Service can decide:

```js
if (!user) {
    throw new AppError("User not found", 404);
}
```

This keeps the Repository generic.

But there are exceptions: a repository may translate certain **database-specific failures** into application-level errors if your architecture defines that contract. We'll discuss error handling for repositories in **13.19**.

const User = mongoose.model(

# 31. CRUD Doesn't Mean Controller → Repository

Don't do:

```text
Controller
   ↓
Repository
```

and skip the Service for business operations.

Usually:

```text
Controller
   ↓
Service
   ↓
Repository
```

The Controller should not be responsible for deciding database operations.

For example, avoid:

```js
export const createUser = async (req, res) => {
    const user =
        await userRepository.create(req.body);

    res.json(user);
};
```

In our architecture, prefer:

```js
const user =
    await userService.createUser(req.body);
```

Then Service decides what should happen.

---

# 32. Why CRUD Repository Design Matters

A well-designed repository gives you:

### Clear code

```js
userRepository.findByEmail(email);
```

### Less database coupling

Service doesn't directly use Mongoose.

### Reusable queries

Multiple services can use:

```js
findByEmail()
```

### Easier testing

Repositories can be replaced/mocked.

### Easier maintenance

Database query changes stay mostly within the Repository boundary.

---

# 33. A Small Design Improvement

Instead of exporting an object:

```js
export const findById = ...
export const create = ...
```

you could also create:

```js
const userRepository = {
    findById,
    findByEmail,
    create,
    updateById,
    deleteById
};

export default userRepository;
```

Then:

```js
userRepository.findById(id);
```

Both styles can work.

The important thing is consistency across your project.

---

# 34. Don't Create Duplicate Methods

Avoid this:

```text
findById()
getById()
fetchById()
retrieveById()
findUserById()
```

all doing the same thing.

Choose one clear naming convention.

For example:

```text
findById()
findByEmail()
findMany()
create()
updateById()
deleteById()
```

Consistency is more valuable than clever naming.

# 36. One Important Security Reminder

Never blindly pass:

```js
req.body
```

into:

```js
userRepository.create(req.body);
```

without proper validation and field control.

For example, a malicious request might contain:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

if your application isn't designed to allow the user to choose their role.

A Service should decide which fields are allowed:

```js
const userData = {
    name: input.name,
    email: input.email,
    password: hashedPassword
};

const user =
    await userRepository.create(userData);
```

This is one reason the Repository should not become a completely unrestricted database gateway.

# 37. Professional Mental Model

When you implement CRUD, think:

```text
CREATE
"Store this valid data."

READ
"Retrieve this data."

UPDATE
"Change this data."

DELETE
"Remove this data."
```

The Repository knows **how to perform those operations**.

The Service knows **when and why they should happen**.

# 38. Interview Question

### What is CRUD?

> CRUD stands for Create, Read, Update, and Delete. These are the four fundamental operations used to manage persistent data.

### How does CRUD relate to a Repository?

> A Repository encapsulates the application's data-access operations, such as creating, retrieving, updating, and deleting documents, while keeping database-specific implementation details away from the Service layer.
