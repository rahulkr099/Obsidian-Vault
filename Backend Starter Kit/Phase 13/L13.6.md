# Phase 13 — Repository Pattern & Data Access

## Lesson 13.6 — `findOne()`

In the previous lesson, we built the basic CRUD repository:

```text
create()
findById()
findByEmail()
findMany()
updateById()
deleteById()
```

The official Phase 13 roadmap specifically places **`findOne` before `findById`**, because `findOne()` is the general-purpose MongoDB/Mongoose operation from which many repository queries are built.

Today we'll understand:

- What `findOne()` does
    
- `findOne()` vs `findById()`
    
- How to build a repository `findOne()`
    
- Why Services shouldn't construct MongoDB queries
    
- How to handle `null`
    
- When `findOne()` is useful
    
- Common mistakes
    

---

# 1. What Is `findOne()`?

Mongoose provides:

```js
Model.findOne(filter)
```

It means:

> **Find one document matching the given conditions.**

For example:

```js
const user = await User.findOne({
    email: "rahul@example.com"
});
```

MongoDB searches the `users` collection for a document whose:

```text
email
 ↓
rahul@example.com
```

matches.

---

# 2. What Does `findOne()` Return?

There are two important possibilities.

### User exists

```js
{
    _id: "...",
    name: "Rahul",
    email: "rahul@example.com"
}
```

### User doesn't exist

```js
null
```

So:

```js
const user = await User.findOne({
    email
});
```

might produce:

```text
User document
```

or:

```text
null
```

This is extremely important for your Service layer.

---

# 3. `findOne()` Is a Read Operation

Remember CRUD:

```text
CREATE
READ
UPDATE
DELETE
```

`findOne()` belongs to:

```text
READ
```

So:

```text
Service
   ↓
Repository
   ↓
findOne()
   ↓
Model
   ↓
MongoDB
```

---

# 4. Basic Repository Method

Suppose:

```text
repositories/
└── user.repository.js
```

We could write:

```js
import User from "../models/user.model.js";

export const findOne = async (filter) => {
    return User.findOne(filter);
};
```

Now the Service can call:

```js
const user = await userRepository.findOne({
    email
});
```

This works.

But there's an important design question:

> **Should we expose a completely generic `findOne(filter)` to the Service?**

We'll get to that.

---

# 5. First Understand the Query

Suppose:

```js
User.findOne({
    email
});
```

The query has two parts:

```text
Model
+
Filter
```

Model:

```js
User
```

Filter:

```js
{
    email
}
```

So:

```js
User.findOne({
    email
});
```

means:

> Search the User collection and return one document whose email matches.

---

# 6. Multiple Conditions

`findOne()` can use multiple conditions.

For example:

```js
const user = await User.findOne({
    email,
    isActive: true
});
```

Now the query means:

```text
email matches
AND
isActive is true
```

Conceptually:

```text
User
 │
 ├── email = requested email
 │
 └── isActive = true
```

Only a matching document is returned.

---

# 7. Another Example

Suppose we have:

```text
Todo
```

We can write:

```js
const todo = await Todo.findOne({
    _id: todoId,
    userId
});
```

This means:

> Find one Todo whose ID matches **and** whose owner is this user.

This ownership pattern is explicitly part of the architecture roadmap and becomes important later for authorization.

We'll study ownership queries deeply in **Lesson 13.15**.

---

# 8. Why Is `findOne()` Powerful?

Because it isn't restricted to IDs.

You can search using:

```text
email
username
phone
slug
status
token
multiple fields
ownership
etc.
```

Examples:

```js
User.findOne({ email });

User.findOne({ username });

User.findOne({ phone });

User.findOne({ resetTokenHash });

Todo.findOne({
    _id: todoId,
    userId
});
```

That's why `findOne()` is such an important repository operation.

---

# 9. `findOne()` vs `find()`

This distinction is very important.

### `findOne()`

Returns:

```text
one document
```

or:

```text
null
```

Example:

```js
const user = await User.findOne({
    email
});
```

---

### `find()`

Returns:

```text
array
```

Example:

```js
const users = await User.find({
    isActive: true
});
```

Possible result:

```js
[
    { name: "Rahul" },
    { name: "Aman" },
    { name: "Priya" }
]
```

So:

```text
findOne()
→ one document / null

find()
→ array
```

---

# 10. `findOne()` vs `findById()`

This is the most important comparison for today's lesson.

### `findById()`

Designed specifically for:

```text
_id
```

Example:

```js
User.findById(userId);
```

---

### `findOne()`

Can search using arbitrary conditions:

```js
User.findOne({
    email
});
```

or:

```js
User.findOne({
    email,
    isActive: true
});
```

or:

```js
User.findOne({
    username
});
```

So:

```text
findById()
→ specifically searches by _id

findOne()
→ searches using a filter
```

---

# 11. Why Not Use `findOne()` for Everything?

You technically could:

```js
User.findOne({
    _id: userId
});
```

But Mongoose already provides:

```js
User.findById(userId);
```

which communicates intent more clearly.

Compare:

```js
User.findOne({ _id: userId });
```

with:

```js
User.findById(userId);
```

The second one immediately tells another developer:

> "We're looking this document up by ID."

Clear code matters.

---

# 12. Repository Naming

Instead of making the Service write:

```js
userRepository.findOne({
    email
});
```

we can create:

```js
userRepository.findByEmail(email);
```

Repository:

```js
export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Now the Service doesn't need to know the query.

This is one of the main benefits of the Repository Pattern.

---

# 13. Why `findByEmail()` Can Be Better

Compare:

### Generic

```js
userRepository.findOne({
    email
});
```

### Specific

```js
userRepository.findByEmail(email);
```

The second one is more expressive.

It says:

> I need a user identified by email.

The Service doesn't need to know:

```text
MongoDB
Mongoose
findOne()
email field
query object
```

The Repository handles those details.

---

# 14. The Repository Boundary

Think:

```text
SERVICE
"I need the user with this email."

        ↓

REPOSITORY
"Okay, I'll translate that into a database query."

        ↓

MODEL
User.findOne({ email })

        ↓

MongoDB
```

This follows the source architecture's core mental model:

```text
Service
  ↓
"I need the user."

Repository
  ↓
"Okay, I'll query MongoDB."

Model
  ↓
"Here is the database structure."

MongoDB
  ↓
"Here is the data."
```

---

# 15. What Should Happen When Nothing Is Found?

Suppose:

```js
const user =
    await userRepository.findByEmail(email);
```

No user exists.

Repository returns:

```js
null
```

Then the Service decides what to do.

For example:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

The Repository shouldn't automatically decide:

```text
"No user = 404"
```

because that is an application-level decision.

---

# 16. Why Return `null`?

Imagine two different Services.

### Service A — Login

```js
const user =
    await userRepository.findByEmail(email);

if (!user) {
    throw new AppError(
        "Invalid credentials",
        401
    );
}
```

### Service B — Registration

```js
const user =
    await userRepository.findByEmail(email);

if (user) {
    throw new AppError(
        "Email already registered",
        409
    );
}
```

Same repository operation:

```js
findByEmail()
```

But completely different business meanings.

That's why the Repository should generally return:

```text
document
or
null
```

and let the Service decide what that means.

---

# 17. Example: Login

Repository:

```js
export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Service:

```js
export const login = async (email, password) => {
    const user =
        await userRepository.findByEmail(email);

    if (!user) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    // password verification...
    // token generation...

    return user;
};
```

Notice:

```text
Repository
→ Find user

Service
→ Decide what missing user means
→ Check password
→ Generate tokens
```

Clean separation.

---

# 18. Example: Password Reset

Suppose we store:

```text
resetTokenHash
resetTokenExpires
```

We might need:

```js
const user = await User.findOne({
    resetTokenHash: tokenHash,
    resetTokenExpires: {
        $gt: new Date()
    }
});
```

That's a database query.

So it belongs in the Repository.

We might expose:

```js
userRepository.findByValidResetToken(tokenHash);
```

Repository:

```js
export const findByValidResetToken = async (
    tokenHash
) => {
    return User.findOne({
        resetTokenHash: tokenHash,
        resetTokenExpires: {
            $gt: new Date()
        }
    });
};
```

The Service can then say:

```js
const user =
    await userRepository.findByValidResetToken(
        tokenHash
    );

if (!user) {
    throw new AppError(
        "Invalid or expired reset token",
        400
    );
}
```

Again:

```text
Repository
→ Query

Service
→ Business decision
```

---

# 19. `findOne()` Can Also Use Operators

MongoDB filters aren't limited to:

```js
{
    field: value
}
```

You can use operators.

Example:

```js
{
    resetTokenExpires: {
        $gt: new Date()
    }
}
```

Meaning:

```text
resetTokenExpires
>
current time
```

This allows queries like:

```js
User.findOne({
    resetTokenHash: tokenHash,
    resetTokenExpires: {
        $gt: new Date()
    }
});
```

This is a perfect example of why database query knowledge belongs in the Repository.

The Service shouldn't need to understand `$gt`.

---

# 20. Another Example: Active User

Repository:

```js
export const findActiveByEmail = async (email) => {
    return User.findOne({
        email,
        isActive: true
    });
};
```

Service:

```js
const user =
    await userRepository.findActiveByEmail(email);

if (!user) {
    throw new AppError(
        "Invalid credentials",
        401
    );
}
```

The Service doesn't know how "active" is represented in MongoDB.

It only knows:

```text
find active user
```

# 21. Don't Put Business Decisions in `findOne()`

Avoid:

```js
export const findByEmail = async (email) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Why?

Because now the Repository has imposed a business rule.

A different Service might want:

```text
null
```

instead.

Prefer:

```js
export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

Then:

```js
const user =
    await userRepository.findByEmail(email);

if (!user) {
    // business decision
}
```

---

# 22. Generic `findOne(filter)` — Good or Bad?

There isn't one universal answer.

You might have:

```js
export const findOne = async (filter) => {
    return User.findOne(filter);
};
```

This can be useful internally.

But exposing it everywhere:

```js
userRepository.findOne({
    email,
    isActive: true,
    deletedAt: null
});
```

can start leaking database/query concepts into Services.

So a good practical approach is:

### Keep generic methods when useful internally

```js
findOne(filter)
```

### Expose meaningful methods for application use

```js
findByEmail(email)
findActiveByEmail(email)
findByValidResetToken(tokenHash)
```

This gives you a cleaner interface.

---

# 23. Think of Repository Methods as an API

Your Repository itself has an API.

For example:

```text
UserRepository API

findById(id)
findByEmail(email)
findActiveByEmail(email)
create(data)
updateById(id, data)
deleteById(id)
```

The Service consumes this API.

It doesn't need to know:

```text
Mongoose
MongoDB
findOne
findById
findByIdAndUpdate
```

That's implementation detail.

---

# 24. A Useful Rule

Ask yourself:

> **Would a Service developer need to understand MongoDB to use this Repository method?**

If yes, your Repository interface may be too low-level.

For example:

```js
userRepository.findOne({
    email,
    isActive: true
});
```

requires some understanding of query filters.

But:

```js
userRepository.findActiveByEmail(email);
```

is self-explanatory.

# 25. `findOne()` and Uniqueness

Suppose:

```text
email
```

should be unique.

We might have:

```js
email: {
    type: String,
    required: true,
    unique: true
}
```

Then:

```js
User.findOne({ email });
```

is commonly used to check whether a user exists.

For registration:

```js
const existingUser =
    await userRepository.findByEmail(email);

if (existingUser) {
    throw new AppError(
        "Email already registered",
        409
    );
}
```

But remember:

> **A `findOne()` existence check alone is not a replacement for a database uniqueness constraint.**

Two requests can race:

```text
Request A → findByEmail() → nothing
Request B → findByEmail() → nothing
Request A → create
Request B → create
```

The database's unique constraint is what provides the final guarantee.

We'll revisit this when we discuss repository errors and robust data access.

# 26. `findOne()` and Ownership

Suppose:

```text
User A
 └── Todo A

User B
 └── Todo B
```

If User A requests Todo A:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

This is safer than:

```js
Todo.findById(todoId);
```

because the query includes the owner.

So:

```text
findOne()
+
multiple conditions
```

becomes very useful for authorization-related data access.

The roadmap specifically highlights this pattern later in the Ownership phase.

# 27. A Real Repository Example

Let's create:

```text
repositories/user.repository.js
```

```js
import User from "../models/user.model.js";

const findOne = async (filter) => {
    return User.findOne(filter);
};

const findByEmail = async (email) => {
    return User.findOne({ email });

    return User.findOne({
        email,
        isActive: true

    findOne,
    findByEmail,
    findActiveByEmail
};
```

Now the Service can use:

```js
import * as userRepository
    from "../repositories/user.repository.js";
```

and:

```js

    await userRepository.findByEmail(email);
```

# 28. What About `.exec()`?

You may see:

```js
return User.findOne({
    email
}).exec();
```

instead of:

```js
return User.findOne({
    email
});
```

Both can be used with `await`.

For example:

```js
const user = await User.findOne({
    email
});
```

Mongoose queries are then awaited.

Using `.exec()` explicitly can make it clear that you're executing the query:

```js
const user = await User.findOne({
    email
}).exec();
```

For our repository architecture, either style can work. The important thing is to choose a consistent project convention.

---

# 29. What About `lean()`?

Later, you may see:

```js
return User.findOne({
    email
}).lean();
```

This tells Mongoose to return a plain JavaScript object instead of a full Mongoose document.

For read-heavy operations, this can sometimes be useful.

But don't add `lean()` everywhere just because you've seen it.

First understand:

```text
Document
vs
Plain Object
```

We'll cover this properly when we reach **Lesson 13.11 — Returning Documents**.

# 30. What About `select()`?

You might also see:

```js
User.findOne({
    email
}).select("name email role");
```

This controls which fields are returned.

This becomes especially important for:

```text
password

resetTokenHash
```

because you don't want sensitive fields unnecessarily flowing through the application.

# 32. Don't Confuse `findOne()` With Business Logic

This:

```js
User.findOne({
    email
});
```

is:

```text
Database query
```

This:

```js
if (!user) {
    throw new AppError(
        "Invalid credentials",
        401
    );
}
```

is:

```text
Business/application decision
```

This:

```js
bcrypt.compare(password, user.password);
```

is:

```text
Authentication logic
```

This:

```js
res.status(401).json(...);
```

is:

```text
HTTP response
```

Keep these separate.

# 33. Common Mistake #1

Putting the query directly in the Service:

```js
const login = async (email, password) => {
    const user = await User.findOne({
        email
    });

    // ...
};
```

In our architecture, prefer:

```js
const login = async (email, password) => {
    const user =
        await userRepository.findByEmail(email);

    // ...
};
```

# 34. Common Mistake #2

Making the Repository perform business decisions:

```js
const findByEmail = async (email) => {
    const user = await User.findOne({ email });

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Prefer:

```js
const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

---

# 35. Common Mistake #3

Using `findOne()` when `findById()` communicates the intention better.

Instead of:

```js
User.findOne({
    _id: userId
});
```

prefer:

```js
User.findById(userId);
```

The second is clearer.

# 36. Common Mistake #4

Assuming `findOne()` always finds something.

Never do:

```js
const user =
    await userRepository.findByEmail(email);

console.log(user.name);
```

without considering:

```text
user === null
```

Instead:

```js
if (!user) {
    // handle missing user
}
```

The Service should know what that absence means.

# 37. Common Mistake #5

Building giant generic repositories

For example:

```js
repository.findOne({
    $or: [...],
    $and: [...],
    ...
});
```

everywhere in your Services.

This starts making the Repository almost pointless.

Better application-facing methods:

```js
findByEmail()
findActiveByEmail()
findByValidResetToken()
```

Use meaningful operations where they improve clarity.

# 38. Interview Question

### What is `findOne()`?

> `findOne()` is a Mongoose query method that searches for a single document matching a specified filter and returns the document or `null` when no matching document exists.

### `findOne()` vs `findById()`?

> `findOne()` accepts a general filter and can match multiple fields, while `findById()` is specifically designed to find a document by its `_id`.

### Where should it be used in Repository Architecture?

> The Mongoose `findOne()` operation should normally be inside the Repository, while the Service uses a meaningful repository method such as `findByEmail()` and decides what to do when no document is found.
