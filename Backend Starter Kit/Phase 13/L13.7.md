# Phase 13 — Repository Pattern & Data Access

## Lesson 13.7 — `findById()`

According to our Phase 13 roadmap, **13.7 is `findById`**, immediately after `findOne`.

In Lesson 13.6, we learned:

```js
User.findOne({ email });
```

Today we'll learn the more specific operation:

```js
User.findById(userId);
```

The key idea is simple:

> **`findById()` is used when you already have a document's MongoDB `_id` and want that document.**

---

# 1. What Is `findById()`?

Mongoose provides:

```js
Model.findById(id)
```

For a User:

```js
const user = await User.findById(userId);
```

This means:

> Find the User document whose `_id` matches `userId`.

For example:

```text
userId
   ↓
"68a123..."
   ↓
User collection
   ↓
document with _id = "68a123..."
```

---

# 2. Why Do We Need `findById()`?

Imagine the frontend sends:

```http
GET /api/v1/users/68a123
```

The route gives us:

```js
req.params.id
```

So the Controller might pass:

```js
"68a123"
```

to the Service:

```js
userService.getUserById("68a123");
```

The Service asks the Repository:

```js
userRepository.findById("68a123");
```

The Repository performs:

```js
User.findById("68a123");
```

The flow is:

```text
HTTP
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
User.findById()
 ↓
MongoDB
```

This matches the architecture we're building: the Service asks for data, while the Repository handles the MongoDB access.

---

# 3. Basic Repository Implementation

Our repository can contain:

```js
import User from "../models/user.model.js";

export const findById = async (userId) => {
    return User.findById(userId);
};
```

That's it.

The Repository's responsibility here is simply:

```text
Input:
userId

↓

Database query:
User.findById(userId)

↓

Output:
User document / null
```

---

# 4. `findById()` vs `findOne()`

This is the most important concept today.

### `findById()`

```js
User.findById(userId);
```

Specifically searches:

```text
_id
```

### `findOne()`

```js
User.findOne({
    email
});
```

Searches using a general filter.

So:

```text
findById()
    ↓
_id

findOne()
    ↓
any filter
```

---

# 5. These Two Are Related

Conceptually:

```js
User.findById(userId);
```

is similar to:

```js
User.findOne({
    _id: userId
});
```

But don't normally write the second version when you simply want an ID lookup.

Use:

```js
User.findById(userId);
```

because it communicates your intention much more clearly.

---

# 6. Why Clear Intent Matters

Compare:

```js
User.findOne({
    _id: userId
});
```

with:

```js
User.findById(userId);
```

When another developer reads:

```js
findById()
```

they immediately understand:

> We're looking for a document by its ID.

This becomes especially valuable when your Repository contains many queries.

---

# 7. What Does `findById()` Return?

There are two normal possibilities.

### Document exists

```js
{
    _id: "68a123",
    name: "Rahul",
    email: "rahul@example.com"
}
```

### Document doesn't exist

```js
null
```

So this:

```js
const user =
    await userRepository.findById(userId);
```

does **not** guarantee that `user` exists.

Always remember:

```text
findById()
    ↓
User document OR null
```

---

# 8. The Service Decides What `null` Means

Suppose:

```js
const user =
    await userRepository.findById(userId);
```

returns:

```js
null
```

The Repository doesn't necessarily need to say:

```text
404 Not Found
```

That's an application decision.

The Service can do:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

So:

```text
Repository
→ "I couldn't find it."

Service
→ "That means this operation should return 404."
```

---

# 9. Complete Example

### Repository

```js
export const findById = async (userId) => {
    return User.findById(userId);
};
```

### Service

```js
export const getUserById = async (userId) => {
    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

### Controller

```js
export const getUser = async (req, res) => {
    const user =
        await userService.getUserById(
            req.params.id
        );

    res.status(200).json({
        success: true,
        data: user
    });
};
```

Notice how each layer has a different responsibility.

---

# 10. Controller Responsibility

The Controller knows about:

```js
req.params.id
```

because that's HTTP.

So:

```js
const userId = req.params.id;
```

is perfectly appropriate inside the Controller.

Then:

```js
userService.getUserById(userId);
```

The Controller doesn't need:

```js
User.findById()
```

---

# 11. Service Responsibility

The Service receives:

```js
userId
```

and decides:

```text
What should happen?
```

For example:

```js
const user =
    await userRepository.findById(userId);

if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

It doesn't need to know whether the Repository uses:

```text
Mongoose
MongoDB driver
another database
```

---

# 12. Repository Responsibility

The Repository knows:

```js
User.findById(userId);
```

That's database access.

So:

```text
Controller
→ HTTP

Service
→ Business logic

Repository
→ Database access
```

This separation is the foundation of our Phase 13 architecture.

# 15. `findById()` Is Common Everywhere

You'll use this pattern constantly.

### User

```js
userRepository.findById(userId);
```

### Todo

```js
todoRepository.findById(todoId);
```

### Product

```js
productRepository.findById(productId);
```

### Order

```js
orderRepository.findById(orderId);
```

### Comment

```js
commentRepository.findById(commentId);
```

It's one of the most common repository methods.

---

# 16. But Here's an Important Security Problem

Suppose:

```text
User A
   ↓
Todo A
```

and:

```text
User B
   ↓
Todo B
```

User B sends:

```http
GET /todos/<Todo-A-ID>
```

If your Repository only does:

```js
Todo.findById(todoId);
```

it might return Todo A.

That's potentially a security problem.

Why?

Because you're checking:

```text
Does this Todo exist?
```

but not:

```text
Does this Todo belong to this user?
```

---

# 17. Ownership Requires a Different Query

For ownership, we might later use:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Notice:

```text
findById()
```

became:

```text
findOne()
```

because we now need **two conditions**:

```text
_id
+
userId
```

This exact ownership pattern is highlighted in the roadmap and will be studied deeply in **13.15 Ownership Queries**.

---

# 18. This Gives Us a Useful Rule

Use:

```js
findById(id)
```

when your requirement is simply:

> Give me the document with this ID.

Use:

```js
findOne(filter)
```

when your requirement is:

> Give me the document matching these conditions.

For example:

```js
findById(todoId)
```

versus:

```js
findOne({
    _id: todoId,
    userId
})
```

---

# 19. Another Example: Updating a User

Suppose:

```http
PATCH /api/v1/users/64f8abc
```

The Controller gets:

```js
const userId = req.params.id;
```

The Service might first check:

```js
const user =
    await userRepository.findById(userId);
```

Then:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

Then perform the update.

This is a very common use of `findById()`.

---

# 20. `findById()` Before Update

For example:

```js
export const updateUser = async (
    userId,
    data
) => {
    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return userRepository.updateById(
        userId,
        data
    );
};
```

Here the Service is using two repository operations:

```text
findById()
     ↓
check existence
     ↓
updateById()
```

This is a simple example of **service orchestration**.

---

# 21. Does `findById()` Validate the ID?

Be careful here.

Suppose someone sends:

```text
GET /users/not-a-valid-object-id
```

Depending on your Mongoose setup/version and the value, the query may result in a cast error rather than simply returning `null`.

So don't assume:

```text
invalid ID
=
not found
```

There are actually different situations:

```text
Invalid ID format
        ↓
Validation / cast problem

Valid ID but no document
        ↓
null / not found

Valid ID and document exists
        ↓
document
```

This distinction becomes important when your validation and error-handling layers are fully connected.

---

# 22. Where Should ID Validation Happen?

In our architecture, request validation can happen before the Service.

For example:

```text
Request
 ↓
Validation
 ↓
Controller
 ↓
Service
 ↓
Repository
```

The validation layer can ensure:

```text
userId has expected format
```

Then the Repository can focus on database access.

However, the Repository still needs to be robust because not every call necessarily comes from HTTP.

---

# 23. Don't Put `req.params` in Repository

Bad:

```js
const findById = async (req) => {
    return User.findById(req.params.id);
};
```

Why is this bad?

Because now Repository knows about Express.

Instead:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

Now it can be called from anywhere.

For example:

```js
userRepository.findById(userId);
```

The Repository doesn't care where `userId` came from.

It could come from:

```text
HTTP request
background job
CLI
test
another service
```

---

# 24. Don't Put `req.user` in Repository

Similarly, avoid:

```js
Todo.findById(req.user.id);
```

The Repository should receive plain data:

```js
todoRepository.findById(todoId);
```

or, for ownership:

```js
todoRepository.findOwnedById(
    todoId,
    userId
);
```

The Repository should not know about Express's `req`.

---

# 25. A Better Ownership Method

Later, we can write:

```js
const findOwnedById = async (
    todoId,
    userId
) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

Then the Service says:

```js
const todo =
    await todoRepository.findOwnedById(
        todoId,
        userId
    );
```

This is much cleaner than:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

inside the Service.

We'll build this properly in **13.15**.

After Lessons 13.5–13.7, our repository might look like:

# 27. Generic vs Specific Methods

This is a useful architecture question.

You could expose:

```js
findOne(filter)
```

and use:

```js
userRepository.findOne({
    _id: userId
});
```

But:

```js
userRepository.findById(userId);
```

is clearer.

Similarly:

```js
userRepository.findOne({
    email
});
```

is less expressive than:

```js
userRepository.findByEmail(email);
```

So a Repository can have both:

```text
Generic methods
+
Meaningful specific methods
```

depending on your architecture.

---

# 28. Don't Overcomplicate `findById()`

A beginner mistake is to turn:

```js
findById(userId)
```

into a huge method:

```js
const findById = async (
    userId,
    options,
    populate,
    fields,
    includeDeleted,
    includeInactive,
    ...
) => {
    // giant query
};
```

Don't do this yet.

Today's method can remain simple:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

Later lessons will introduce:

```text
field selection
population
parameters
filtering
sorting
pagination
```

one at a time.

Without Repository:

```text
Controller
    ↓
Service
    ↓
User.findById()
    ↓
MongoDB
```

With Repository:

```text

    ↓

    ↓

    ↓

    ↓
MongoDB
```

The additional layer isn't there just to make the project bigger.

```text

     │

     ▼
```

That's the important architectural benefit.

# 33. Common Mistake #1 — Calling Model From Service

Avoid:

```js
const getUser = async (userId) => {
    return User.findById(userId);
};
```

If we're following our Repository architecture, use:

```js
const getUser = async (userId) => {
    return userRepository.findById(userId);
};
```

---

# 34. Common Mistake #2 — Repository Returning HTTP Errors

Avoid:

```js
const findById = async (userId) => {
    const user = await User.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Prefer:

```js
const findById = async (userId) => {
    return User.findById(userId);
};
```

Then Service decides:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

---

# 35. Common Mistake #3 — Returning HTTP Responses

Never make the Repository do:

```js
return res.status(200).json(user);
```

The Repository shouldn't know:

```text
res
HTTP
status codes
JSON responses
Express
```

Its job is data access.

---

# 36. Common Mistake #4 — Mixing Ownership Into Basic `findById()`

Don't make:

```js
findById(todoId, userId)
```

secretly perform:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

unless the method is explicitly designed for ownership.

Keep:

```js
findById(todoId)
```

meaning:

> Find by ID.

And later:

```js
findOwnedById(todoId, userId)
```

meaning:

> Find this resource only if it belongs to this user.

That makes your Repository API much easier to understand.

# 37. Interview Questions

### What does `findById()` do?

> `findById()` retrieves a single MongoDB/Mongoose document using its `_id`.

### What does it return if nothing is found?

> Normally, it returns `null`.

### Difference between `findOne()` and `findById()`?

> `findOne()` accepts a general filter, while `findById()` is specifically intended for finding a document by `_id`.

### Should the Service directly call `User.findById()`?

> In our Repository architecture, no. The Service should call something like `userRepository.findById()`, while the Repository performs the Mongoose operation.
