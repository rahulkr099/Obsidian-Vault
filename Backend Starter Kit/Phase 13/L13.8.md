# Phase 13 — Repository Pattern & Data Access

## Lesson 13.8 — `create()`

In **13.5**, we introduced CRUD and saw:

```text
CREATE → create()
READ   → findOne(), findById()
UPDATE → updateById()
DELETE → deleteById()
```

Today we're going deeper into **Create**.

The roadmap defines **13.8 as `create`**, after `findOne` and `findById`.

The main idea:

> **The Service decides what should be created; the Repository knows how to store it in the database.**

---

# 1. What Does `create()` Mean?

Suppose we want to create a user.

We have data:

```js
{
    firstName: "Rahul",
    lastName: "Kumar",
    email: "rahul@example.com",
    password: "hashed-password"
}
```

The Repository can use:

```js
User.create(data);
```

Mongoose then creates a document in MongoDB.

So:

```text
Service
   ↓
repository.create(data)
   ↓
User.create(data)
   ↓
MongoDB
```

---

# 2. Basic Repository Implementation

Our repository:

```text
repositories/
└── user.repository.js
```

can contain:

```js
import User from "../models/user.model.js";

export const create = async (data) => {
    return User.create(data);
};
```

That's the basic implementation.

The Repository doesn't need to know:

```text
Who created the user?
Why are we creating the user?
Is this signup?
Is this an admin operation?
```

It only knows:

> **Given valid data, create the database document.**

This matches the architecture from your starter roadmap: the Repository's responsibility is **how to access or modify data**, while business logic belongs in the Service.

---

# 3. What Does `User.create()` Do?

When we write:

```js
User.create(data);
```

Mongoose roughly performs the following process:

```text
data
 ↓
Mongoose Model
 ↓
Schema processing
 ↓
Validation
 ↓
Document creation
 ↓
MongoDB
```

For example:

```js
const user = await User.create({
    firstName: "Rahul",
    email: "rahul@example.com"
});
```

MongoDB might store:

```json
{
    "_id": "68abc123...",
    "firstName": "Rahul",
    "email": "rahul@example.com",
    "createdAt": "...",
    "updatedAt": "..."
}
```

The exact fields depend on your schema.

---

# 4. Repository `create()` Is Simple

A clean Repository method can be:

```js
const create = async (data) => {
    return User.create(data);
};
```

Don't feel that a Repository has to contain complicated code.

Sometimes the Repository is intentionally very thin.

That's okay.

Its value comes from creating a **boundary around database access**.

---

# 5. Who Decides What Goes Into `data`?

This is extremely important.

Suppose the client sends:

```json
{
    "firstName": "Rahul",
    "email": "rahul@example.com",
    "password": "123456",
    "role": "admin"
}
```

Should the Repository blindly do:

```js
User.create(req.body);
```

**No.**

The Service should determine what data is allowed to reach the Repository.

Your source architecture explicitly separates:

```text
Service
→ business logic

Repository
→ data access
```

---

# 6. The Service Prepares the Data

Imagine signup.

The client gives:

```js
{
    firstName,
    email,
    password
}
```

The Service might do:

```text
Request
 ↓
Validate input
 ↓
Normalize email
 ↓
Check existing user
 ↓
Hash password
 ↓
Prepare user data
 ↓
Repository.create()
```

This is exactly the architecture described in your starter material for signup.

---

# 7. Example Service

```js
const signup = async (input) => {
    const existingUser =
        await userRepository.findByEmail(input.email);

    if (existingUser) {
        throw new AppError(
            "Email already registered",
            409
        );
    }

    const hashedPassword =
        await hashPassword(input.password);

    const userData = {
        firstName: input.firstName,
        email: input.email,
        password: hashedPassword
    };

    return userRepository.create(userData);
};
```

Look carefully at the flow.

The Service decides:

```js
const userData = {
    firstName: input.firstName,
    email: input.email,
    password: hashedPassword
};
```

The Repository simply receives:

```js
userData
```

and stores it.

---

# 8. Why Not Hash the Password in the Repository?

You might be tempted to write:

```js
const create = async (data) => {
    data.password = await bcrypt.hash(
        data.password,
        12
    );

    return User.create(data);
};
```

This mixes responsibilities.

The Repository's job is:

```text
Database access
```

Password hashing is:

```text
Application/security logic
```

So the cleaner architecture is:

```text
Service
 ↓
hash password
 ↓
Repository
 ↓
save hash
```

Your starter roadmap explicitly places password hashing and signup logic in the authentication/service architecture rather than the Repository.

---

# 9. Very Important: Never Store Plain Passwords

The correct flow is:

```text
Plain password
      ↓
bcrypt
      ↓
Password hash
      ↓
Repository
      ↓
MongoDB
```

Not:

```text
Plain password
      ↓
Repository
      ↓
MongoDB
```

Your source specifically states:

> Never store plain password.

Instead:

```text
password
 ↓
bcrypt
 ↓
hash
 ↓
MongoDB
```

---

# 10. The Repository Doesn't Need to Know It's a Password

Suppose the Service produces:

```js
{
    firstName: "Rahul",
    email: "rahul@example.com",
    password: "$2b$12$..."
}
```

The Repository sees:

```js
create(data)
```

and does:

```js
User.create(data);
```

It doesn't need to know:

```text
This is a password hash.
```

That's a useful separation.

---

# 11. Think of `create()` as a Contract

Our Repository exposes:

```js
create(data)
```

The contract is basically:

```text
Input:
valid User data

Output:
created User document
```

The Service doesn't care whether the Repository internally uses:

```text
User.create()
```

or:

```text
new User(data)
user.save()
```

The Repository hides that implementation detail.

---

# 12. Two Ways to Create With Mongoose

You may see both approaches.

### Approach 1

```js
const user = await User.create(data);
```

### Approach 2

```js
const user = new User(data);

await user.save();
```

Both can create a MongoDB document.

For our Repository:

```js
const create = async (data) => {
    return User.create(data);
};
```

is perfectly reasonable and concise.

# 13. Why Have a Repository If It's Just One Line?

This is a very common beginner question.

You might think:

```js
User.create(data);
```

became:

```js
userRepository.create(data);
```

So:

> "Why did we add another layer?"

Because the Repository creates a boundary.

Today:

```text
Repository
 ↓
Mongoose
```

Tomorrow, your Repository might contain:

```text
query construction
transactions
indexes
population
field selection
database-specific optimization
soft-delete rules
```

The Service still talks to:

```js
userRepository.create(data);
```

That's the architectural benefit.

# 14. Repository vs Service

Let's compare them directly.

### Repository

```js
const create = async (data) => {
    return User.create(data);
};
```

Its question is:

> **How do I store this?**

---

### Service

```js
const signup = async (input) => {
    // check duplicate
    // hash password
    // prepare data

    return userRepository.create(userData);
};
```

Its question is:

> **Should I create this, and what should be created?**

This distinction is extremely important.

---

# 15. Service Controls the Data

Suppose the User model contains:

```text
firstName
lastName
email
password
role
refreshTokenHash
```

A normal signup shouldn't necessarily allow:

```js
{
    role: "admin",
    refreshTokenHash: "something"
}
```

from the client.

Instead:

```js
const userData = {
    firstName: input.firstName,
    lastName: input.lastName,
    email: input.email,
    password: hashedPassword
};
```

Then:

```js
await userRepository.create(userData);
```

This is a powerful security boundary.

---

# 16. Don't Pass `req.body` Directly

Avoid:

```js
await userRepository.create(req.body);
```

Why?

Because the request body is **untrusted input**.

Imagine:

```json
{
    "firstName": "Rahul",
    "email": "rahul@example.com",
    "password": "secret",
    "role": "admin"
}
```

If you blindly pass it through:

```text
HTTP
 ↓
req.body
 ↓
Repository
 ↓
MongoDB
```

you have given the client too much control.

Instead:

```text
HTTP
 ↓
Validation
 ↓
Controller
 ↓
Service
 ↓
Allowed fields
 ↓
Repository
 ↓
MongoDB
```

---

# 17. Validation Is Still Important

Don't misunderstand this.

We shouldn't rely only on the Service's field selection.

A good architecture has multiple layers:

```text
Request
 ↓
Validation
 ↓
Service
 ↓
Repository
 ↓
Model
 ↓
Database
```

Validation answers:

> Is the input structurally valid?

Service answers:

> Is this operation allowed and what data should we create?

Repository answers:

> How do I store it?

Model/database constraints provide another layer of protection.

# 20. Why Should the Service Add `userId`?

Suppose the authenticated user is:

```text
User A
```

The request contains:

```json
{
    "title": "My Todo"
}
```

The backend knows:

```text
req.user.id = User A
```

So the Service constructs:

```js
{
    userId: authenticatedUserId,
    title: input.title
}
```

This prevents the client from simply saying:

```json
{
    "userId": "someone-else"
}
```

and creating a Todo belonging to another user.

This connects directly to the ownership architecture in your source material.

---

# 21. `create()` Doesn't Decide Ownership

This is subtle but important.

Repository:

```js
const create = async (data) => {
    return Todo.create(data);
};
```

Service:

```js
const createTodo = async (userId, input) => {
    const data = {
        userId,
        title: input.title
    };

    return todoRepository.create(data);
};
```

So:

```text
Service
→ decides owner

Repository
→ stores owner
```

# 26. A Very Important Rule

### Repository should not decide:

```text
Should we create this user?
```

### Service should decide:

```text
Yes, this operation is valid.
```

Then Repository says:

```text
Okay, I'll save it.
```

In other words:

```text
Service
→ WHY + WHAT

Repository
→ HOW
```

That's one of the most useful ways to remember the difference.

# 27. What If MongoDB Rejects the Create?

For example, suppose email has a unique constraint:

```text
email = rahul@example.com
```

already exists.

Two requests might race:

```text
Request A
 ↓
check email
 ↓
not found

Request B
 ↓
check email
 ↓
not found

Request A
 ↓
create

Request B
 ↓
create
```

The database uniqueness constraint should still protect the data.

So:

> **An existence check is useful for business behavior, but the database constraint is the final guarantee.**

We'll later discuss how Repository errors should be handled in **13.19**.

---

# 28. Don't Hide Database Errors Completely

Avoid this:

```js
const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        return null;
    }
};
```

Why?

Because now you've destroyed useful information.

The Service may need to know:

```text
duplicate key
validation failure
database unavailable
connection problem
```

Don't turn every database failure into:

```js
null
```

We'll learn proper Repository error handling later.

---

# 29. Don't Put HTTP Status Codes in `create()`

Avoid:

```js
const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        throw new AppError(
            "Could not create user",
            500
        );
    }
};
```

This mixes database access with HTTP/application concerns.

The Repository should stay focused.

❌

```js

    → bcrypt.hash()
```

# 38. Common Mistake #3 — Adding HTTP Logic

❌

```js
repository.create()
    → res.status(...)
```

Never.

# 39. Common Mistake #4 — Returning a Custom HTTP Response

❌

```js

    status: 201,
    message: "Created",

};
```

# 40. Common Mistake #5 — Allowing Sensitive Fields

Avoid:

```js
repository.create({
    ...req.body
});
```

because the user might send:

```json
{
    "role": "admin",
    "refreshTokenHash": "fake",
    "resetTokenHash": "fake"
}
```

Instead, explicitly construct the allowed data:

```js
const userData = {
    firstName: input.firstName,
    lastName: input.lastName,
    email: normalizedEmail,
    password: hashedPassword
};
```

This is a much safer habit.

# 41. Interview Question

### What is the responsibility of a Repository `create()` method?

> Its responsibility is to persist prepared data using the data-access layer, such as a Mongoose model. It should not contain business decisions, HTTP logic, or authentication workflows.

### Should a Repository hash passwords?

> Generally, no. Password hashing belongs to the authentication/application logic, typically in the Service layer. The Repository should persist the resulting hash.

### Should we pass `req.body` directly to `create()`?

> No. Request data is untrusted. Validation and Service-level field selection should determine what data reaches the Repository.
