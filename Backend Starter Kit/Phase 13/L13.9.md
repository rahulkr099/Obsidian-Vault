# Phase 13 — Repository Pattern & Data Access

## Lesson 13.9 — `update()`

In the previous lesson, we learned:

```js
userRepository.create(data);
```

That was **CREATE**.

Now we're moving to **UPDATE**.

The roadmap defines **13.9 as `update`**, after `findOne`, `findById`, and `create`.

The core idea is:

> **The Service decides what should change; the Repository performs the database update.**

---

# 1. What Does `update()` Mean?

Suppose we already have:

```text
User
_id: 123
name: Rahul
email: rahul@example.com
```

Now Rahul wants to change his name:

```text
Rahul
   ↓
Rahul Kumar
```

The Service can ask:

```js
userRepository.update(userId, {
    name: "Rahul Kumar"
});
```

The Repository handles the database operation.

Conceptually:

```text
Service
   ↓
repository.update(id, data)
   ↓
User.update...
   ↓
MongoDB
```

---

# 2. Basic Mongoose Update

Mongoose provides several update methods.

One common option is:

```js
User.findByIdAndUpdate(
    userId,
    data
);
```

So our Repository could start with:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data
    );
};
```

This is the basic idea.

---

# 3. But There Is an Important Problem

Look at this:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data
    );
};
```

What exactly is inside `data`?

Suppose the frontend sends:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

If we blindly pass it:

```js
userRepository.update(
    userId,
    req.body
);
```

we could accidentally allow the user to modify fields they should never control.

This is why **Repository `update()` must not be confused with permission to update anything**.

The Service decides what is allowed.

---

# 4. The Correct Flow

A safer architecture looks like:

```text
HTTP Request
     ↓
Validation
     ↓
Controller
     ↓
Service
     ↓
Choose allowed fields
     ↓
Repository.update()
     ↓
Mongoose
     ↓
MongoDB
```

The Repository performs the operation.

The Service controls the business rules.

This follows the architecture in your source: Services contain business logic, while Repositories handle data access.

---

# 5. Example: Update User Profile

Suppose the client sends:

```json
{
    "firstName": "Rahul",
    "lastName": "Kumar"
}
```

Controller:

```js
const user = await userService.updateProfile(
    req.user.id,
    req.body
);
```

Service:

```js
const updateProfile = async (userId, input) => {
    const updateData = {
        firstName: input.firstName,
        lastName: input.lastName
    };

    return userRepository.update(
        userId,
        updateData
    );
};
```

Repository:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data
    );
};
```

Now each layer has a clear responsibility.

---

# 6. Controller

The Controller deals with HTTP:

```js
export const updateProfile = async (req, res) => {
    const user = await userService.updateProfile(
        req.user.id,
        req.body
    );

    res.status(200).json({
        success: true,
        data: user
    });
};
```

The Controller doesn't directly call:

```js
User.findByIdAndUpdate();
```

because database access belongs to the Repository.

---

# 7. Service

The Service decides:

```text
Which fields can change?
Should this user be allowed to change them?
Does the user exist?
Does another business rule apply?
```

Example:

```js
const updateProfile = async (userId, input) => {
    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    const updateData = {
        firstName: input.firstName,
        lastName: input.lastName
    };

    return userRepository.update(
        userId,
        updateData
    );
};
```

---

# 8. Repository

The Repository knows how to perform the database operation:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data
    );
};
```

Its job is essentially:

> "Here is an ID and prepared update data. I'll perform the database update."

---

# 9. Why Use `findByIdAndUpdate()`?

Because we already have the document ID.

For example:

```js
User.findByIdAndUpdate(
    userId,
    updateData
);
```

means:

```text
Find document
where _id = userId

        ↓

Apply updateData
```

It's a convenient operation for ID-based updates.

---

# 10. `findByIdAndUpdate()` vs `findOneAndUpdate()`

These are closely related.

### By ID

```js
User.findByIdAndUpdate(
    userId,
    data
);
```

### By arbitrary filter

```js
User.findOneAndUpdate(
    filter,
    data
);
```

Conceptually:

```text
findByIdAndUpdate()
        ↓
_id lookup

findOneAndUpdate()
        ↓
custom filter
```

For example:

```js
User.findOneAndUpdate(
    { email },
    data
);
```

---

# 11. Ownership Again

This becomes very important with resources such as Todos.

Imagine:

```text
Todo A
ownerId = User A
```

User B somehow knows Todo A's ID.

If the Repository does:

```js
Todo.findByIdAndUpdate(
    todoId,
    data
);
```

it only checks:

```text
Does this Todo ID exist?
```

It doesn't establish:

```text
Does this Todo belong to this user?
```

That's why ownership-aware updates often need a filter like:

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    data
);
```

The roadmap later dedicates **13.15 to Ownership Queries**, so we're not going to go too deep into that today.

---

# 12. The Big Security Lesson

Never think:

```js
updateById(id, data)
```

automatically means:

> "This user is allowed to update this document."

It only means:

> "Try to update this document."

Authorization and ownership are separate concerns.

So:

```text
Authentication
→ Who is this?

Authorization
→ Are they allowed?

Ownership
→ Does this resource belong to them?

Repository
→ How do we perform the database operation?
```

---

# 13. Partial Update vs Full Replacement

This is another important concept.

Suppose the existing document is:

```json
{
    "firstName": "Rahul",
    "lastName": "Kumar",
    "email": "rahul@example.com"
}
```

The client sends:

```json
{
    "firstName": "Rahul Singh"
}
```

For a partial update, we want:

```json
{
    "firstName": "Rahul Singh",
    "lastName": "Kumar",
    "email": "rahul@example.com"
}
```

We don't want:

```json
{
    "firstName": "Rahul Singh"
}
```

to destroy everything else.

That's why update semantics matter.

---

# 14. `PATCH` and Partial Updates

A common API design is:

```http
PATCH /api/v1/users/:id
```

Meaning:

> Update only the fields provided.

For example:

```json
{
    "firstName": "Rahul Singh"
}
```

The Repository applies only that change.

This is different from a conceptual full replacement.

For our backend architecture, you'll commonly encounter partial updates.

---

# 15. `PUT` vs `PATCH`

A useful simplified mental model:

### PUT

```text
Replace the resource representation.
```

### PATCH

```text
Modify part of the resource.
```

So:

```text
PUT
 ↓
replacement semantics

PATCH
 ↓
partial modification
```

The exact API contract is your application's responsibility.

---

# 16. Why `update()` Shouldn't Decide Business Rules

Don't put things like this inside the Repository:

```js
if (user.role !== "admin") {
    throw ...
}
```

The Repository shouldn't become your authorization layer.

Instead:

```text
Service
 ↓
authorization/business decision
 ↓
Repository
 ↓
database update
```

This separation keeps the architecture understandable.

---

# 17. A Better Repository API

Instead of exposing MongoDB details everywhere:

```js
User.findByIdAndUpdate(...)
```

the Service uses:

```js
userRepository.update(
    userId,
    updateData
);
```

The Repository hides:

```text
Mongoose
MongoDB
query implementation
```

The Service sees a clean API.

---

# 18. What Should `update()` Return?

This is where things get interesting.

Consider:

```js
const user =
    await User.findByIdAndUpdate(
        userId,
        data
    );
```

You need to understand what document you're getting back and whether you want:

```text
old document
```

or:

```text
updated document
```

Mongoose update operations have options that control this behavior.

For example:

```js
{
    new: true
}
```

can be used so the returned document is the updated version.

So you may see:

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        data,
        {
            new: true
        }
    );
};
```

We'll study **returning documents** specifically in Lesson **13.11**, so for now remember only the concept.

---

# 19. What About Validation?

Mongoose update operations have their own behavior around validation.

You may encounter:

```js
{
    new: true,
    runValidators: true
}
```

For example:

```js
return User.findByIdAndUpdate(
    userId,
    data,
    {
        new: true,
        runValidators: true
    }
);
```

This asks Mongoose to run schema validators for the update.

This is useful, but remember:

> **Request validation and database/schema validation are different layers.**

Your architecture already treats validation as a separate concern.

---

# 20. Why Multiple Validation Layers?

Imagine:

```text
Client
 ↓
Request validation
 ↓
Service
 ↓
Repository
 ↓
Mongoose validation
 ↓
MongoDB
```

Each layer has a different purpose.

### Request validation

```text
Is this input structurally valid?
```

### Service

```text
Is this operation allowed?
```

### Model

```text
Does this data satisfy the schema?
```

### Database

```text
Can the data satisfy database constraints?
```

This is defense in depth.

# 21. Example: Updating Email

Email changes are more complicated than changing a name.

Suppose:

```json
{
    "email": "new@example.com"
}
```

The Service might need to:

```text
Check email format
      ↓
Normalize email
      ↓
Check if another account uses it
      ↓
Possibly require verification
      ↓
Build update data
      ↓
Repository.update()
```

The Repository shouldn't decide all of that.

It simply receives:

```js
{
    email: "new@example.com"
}
```

and persists it.

---

# 22. Example: Updating Password

Password updates are even more important.

Client sends:

```json
{
    "password": "new-password"
}
```

The Service should:

```text
Validate password
      ↓
Hash password
      ↓
Build updateData
      ↓
Repository.update()
```

Repository:

```js
User.findByIdAndUpdate(
    userId,
    updateData
);
```

So MongoDB receives:

```text
hashed password
```

not:

```text
new-password
```

---

# 23. Never Do This

❌

```js
const update = async (userId, data) => {
    return User.findByIdAndUpdate(
        userId,
        {
            ...data,
            password: await bcrypt.hash(data.password, 12)
        }
    );
};
```

Now the Repository knows about authentication logic.

Instead:

```text
Service
 ↓
hash password
 ↓
Repository.update()
```

---

# 24. Update Data Should Be Explicit

Avoid:

```js
const updateData = {
    ...req.body
};
```

Prefer:

```js
const updateData = {};

if (input.firstName !== undefined) {
    updateData.firstName = input.firstName;
}

if (input.lastName !== undefined) {
    updateData.lastName = input.lastName;
}
```

This makes allowed fields explicit.

---

# 25. Why This Matters for Security

Imagine your User model contains:

```text
firstName
lastName
email
password
role
isVerified
refreshTokenHash
```

If you allow:

```js
{
    ...req.body
}
```

the client may attempt:

```json
{
    "role": "admin",
    "isVerified": true
}
```

That's dangerous.

Instead, the Service should define what this particular operation allows:

```js
const updateData = {
    firstName: input.firstName,
    lastName: input.lastName
};
```

The Repository then updates only those fields.

Imagine:


This:


For user profiles, the Service might obtain the authenticated user's own ID.

# 37. Interview Questions

### What is the purpose of a Repository `update()` method?

> It encapsulates the database operation required to modify an existing document.

### Should the Repository decide which fields a user is allowed to update?

> Generally no. The Service should enforce business rules and prepare the allowed update data.

### Why shouldn't we pass `req.body` directly to the Repository?

> Because request data is untrusted and may contain fields the user should not be allowed to modify.

### What is `findByIdAndUpdate()`?

> A Mongoose operation that finds a document by its `_id` and applies an update.

### What does `{ new: true }` do?

> It makes the update operation return the updated document rather than the previous version.
