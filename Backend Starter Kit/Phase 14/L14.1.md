# Lesson 14.1 — What Is Authentication?

Welcome to **Phase 14: Authentication**. 🔐

You've already learned:

```text
Middleware
Error Handling
Validation
Security
Controllers
Services
Repositories
```

Now we're going to use those pieces to build something real:

> **How does our backend know who is making a request?**

That is the core problem authentication solves.

---

## 1. What does Authentication mean?

**Authentication = verifying identity.**

In simple words:

> Authentication answers: **"Who are you?"**

Suppose you open a website and enter:

```text
Email: rahul@example.com
Password: ********
```

The backend checks those credentials.

If they're correct:

```text
"Yes, this is Rahul."
```

The backend has authenticated you.

---

## 2. Authentication vs Authorization

This distinction is extremely important.

### Authentication

```text
Who are you?
```

### Authorization

```text
What are you allowed to do?
```

Example:

```text
Rahul logs in
     ↓
Authentication
     ↓
"Rahul is a valid user."
     ↓
Authorization
     ↓
"Rahul can read his own todos."
```

Another example:

```text
Admin logs in
     ↓
Authentication
     ↓
"User = Admin"
     ↓
Authorization
     ↓
"Admin can delete users."
```

So:

```text
Authentication → Identity
Authorization  → Permission
```

We'll study authorization deeply in **Phase 15**.

---

# 3. Why does our backend need authentication?

Imagine your Todo API has:

```http
GET /api/v1/todos
```

Without authentication, how would the backend know whose todos to return?

Suppose MongoDB contains:

```text
User A
 ├── Todo 1
 ├── Todo 2

User B
 ├── Todo 3
 ├── Todo 4
```

User A makes:

```http
GET /api/v1/todos
```

The backend needs to know:

```text
Who is making this request?
        ↓
User A
        ↓
Return User A's todos
```

Authentication provides that identity.

---

# 4. The problem with simply sending `userId`

A beginner might think:

```http
GET /api/v1/todos
X-User-Id: 123
```

or:

```json
{
  "userId": "123"
}
```

Then the backend says:

```js
const userId = req.body.userId;
```

This is **not authentication**.

Why?

Because a malicious user could simply change:

```text
123
```

to:

```text
456
```

and pretend to be another user.

For example:

```text
Actual user:
    Rahul

Request says:
    userId = Amit
```

The server needs a way to verify that the identity belongs to the person making the request.

That's the fundamental problem authentication solves.

---

# 5. Authentication starts with credentials

A user needs some way to prove their identity.

Common examples:

### Something you know

```text
Password
PIN
```

### Something you have

```text
Phone
Security key
Authenticator device
```

### Something you are

```text
Fingerprint
Face
```

For our MERN backend, we'll primarily work with:

```text
Email + Password
```

Later we'll discuss things such as email verification and password reset.

# 6. Basic login flow

Imagine:

```text
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "mypassword"
}
```

The request enters our backend:

```text
React
  ↓
POST /auth/login
  ↓
Route
  ↓
Validation
  ↓
Controller
  ↓
Auth Service
  ↓
User Repository
  ↓
MongoDB
```

The database contains something like:

```text
User
────────────────────────────
_id: 123
email: rahul@example.com
password: <password hash>
role: user
```

The backend verifies the supplied password.

If everything is correct:

```text
Authentication successful
```

Now the important question becomes:

> **How does the backend remember that this user has already authenticated on the next request?**

That's where our next authentication concepts come in.

---

# 7. Authentication isn't just Login

This is a common misunderstanding.

Authentication is not simply:

```text
Login page
```

A complete authentication system usually involves:

```text
Signup
   ↓
Login
   ↓
Authenticated state
   ↓
Access protected resources
   ↓
Refresh authentication
   ↓
Logout
```

And often:

```text
Email verification
Password reset
Password change
Session/token management
```

So we're going to build authentication as a **system**, not as a single endpoint.

---

# 8. What happens after login?

Let's say login succeeds.

The backend knows:

```text
User ID = 123
Email = rahul@example.com
```

But the browser will later make another request:

```http
GET /api/v1/users/me
```

How does the server know that this request also belongs to User 123?

We need some kind of **authentication credential** that can travel with subsequent requests.

Conceptually:

```text
LOGIN
  ↓
Verify credentials
  ↓
Create authentication credential
  ↓
Client stores/sends credential
  ↓
Next request
  ↓
Backend verifies credential
  ↓
User identified
```

There are different ways to implement this.

The two major approaches you'll learn are:

```text
Session-based authentication
```

and:

```text
Token-based authentication
```

We'll study those in **14.8**.

---

# 9. The important mental model

Don't think:

> "JWT is authentication."

That's too narrow.

Instead:

```text
Authentication
       │
       ├── Session-based
       │
       └── Token-based
              │
              └── JWT is one technology
```

JWT is a **token format**, not the entire concept of authentication.

We'll spend time on this distinction because it prevents a lot of confusion later.

---

# 10. Authentication in our architecture

Remember our architecture:

```text
Request
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Model
   ↓
MongoDB
```

Authentication will use several of these layers.

For example, login:

```text
POST /auth/login
       ↓
Auth Route
       ↓
Validation Middleware
       ↓
Auth Controller
       ↓
Auth Service
       ↓
User Repository
       ↓
User Model
       ↓
MongoDB
```

Then a protected endpoint:

```text
GET /users/me
       ↓
Auth Route
       ↓
Authentication Middleware
       ↓
User Controller
       ↓
User Service
       ↓
User Repository
       ↓
MongoDB
```

Notice something important:

### Login

The user is **proving identity**.

### Protected request

The user is **presenting proof of previous authentication**.

That's a major concept.

# 11. What does `req.user` mean?

You'll eventually see code like:

```js
req.user
```

For example:

```js
export const getMe = asyncHandler(async (req, res) => {
    console.log(req.user);
});
```

You might wonder:

> Where did `req.user` come from?

It comes from authentication middleware.

Conceptually:

```text
Request
   ↓
Auth Middleware
   ↓
Verify authentication credential
   ↓
Identify user
   ↓
req.user = user information
   ↓
next()
   ↓
Controller
```

So:

```js
req.user
```

means something like:

> "The authenticated identity associated with this request."

We'll build this ourselves in later lessons.

# 12. Authentication boundary

Think about your API as having a boundary.

Public endpoint:

```text
GET /healthz
```

Anyone can access it.

```text
Internet
   ↓
/healthz
   ↓
Response
```

Protected endpoint:

```text
GET /api/v1/users/me
```

requires authentication.

```text
Internet
   ↓
Authentication Check
   ↓
   ├── ❌ Not authenticated → 401
   │
   └── ✅ Authenticated
             ↓
          Controller
```

This authentication middleware becomes a **gateway**.

---

# 13. What does `401 Unauthorized` mean?

You'll frequently encounter:

```http
401 Unauthorized
```

when authentication fails or is missing.

For example:

```text
No token
   ↓
401
```

or:

```text
Invalid token
   ↓
401
```

or:

```text
Expired authentication credential
   ↓
401
```

Later we'll distinguish this carefully from:

```http
403 Forbidden
```

which is primarily an authorization problem.

For now remember:

```text
401 → "I don't accept your identity/authentication."
403 → "I know who you are, but you aren't allowed."
```

# 14. Authentication and MongoDB

Our MongoDB `User` document might eventually look approximately like:

```js
{
    _id: "...",
    email: "rahul@example.com",
    password: "<hash>",
    role: "user"
}
```

Notice:

```text
password
```

should **not** be stored as:

```text
mypassword123
```

Instead:

```text
mypassword123
       ↓
    bcrypt
       ↓
password hash
       ↓
    MongoDB
```

We'll learn password hashing properly in **14.4 and 14.5**.

# 17. Key things to remember

If you remember only these points from today's lesson, that's enough:

### 1. Authentication means identity verification

```text
Authentication = Who are you?
```

### 2. Authorization is different

```text
Authorization = What are you allowed to do?
```

### 3. Login is only one part of authentication

Authentication is a complete system.

### 4. Never trust a client-provided `userId`

```text
❌ req.body.userId
```

cannot prove identity.

### 5. Authentication must survive future requests

That's why we need sessions or tokens.

### 6. JWT is not synonymous with authentication

JWT is a token technology we'll use as part of our authentication architecture.

### 7. `req.user` is created by authentication middleware

Conceptually:

```js
req.user = authenticatedUser;
```

### 8. Protected routes need an authentication boundary

```text
Request
  ↓
Authentication
  ↓
Controller
```
