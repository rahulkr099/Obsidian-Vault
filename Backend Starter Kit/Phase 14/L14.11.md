# Lesson 14.11 — Dependency & Supply-Chain Security

Your Phase 14 roadmap defines **14.11 as Dependency & Supply-Chain Security**. It specifically includes `npm audit`, dependency updates, lockfiles, vulnerable packages, typosquatting, malicious dependencies, the software supply chain, and Docker image security.

This lesson is important because your backend is not only **your code**.

A large part of your application is code written by other people.

```text
Your application
      │
      ├── Express
      ├── Mongoose
      ├── Zod
      ├── JWT library
      ├── bcrypt
      ├── Redis client
      ├── AI SDK
      └── many transitive dependencies
```

So security has to include the **software you depend on**.

---

# 1. What is a dependency?

A dependency is a package your application uses.

For example:

```bash
npm install express
```

Now your project depends on Express.

Your `package.json` might contain:

```json
{
  "dependencies": {
    "express": "^5.1.0"
  }
}
```

Your application code:

```js
import express from "express";
```

depends on that package.

---

# 2. But your dependency has dependencies

This is where things become interesting.

Imagine:

```text
Your application
      ↓
    Express
      ↓
 ┌────┼────┐
 ↓    ↓    ↓
 A    B    C
      ↓
      D
      ↓
      E
```

You installed:

```bash
npm install express
```

But npm may install many additional packages required by Express.

These are called:

> **Transitive dependencies**

So your real dependency tree can be much larger than your `package.json` suggests.

---

# 3. Your supply chain

Think about the complete chain:

```text
Developer
    ↓
npm package
    ↓
Package maintainer
    ↓
Package registry
    ↓
Your npm install
    ↓
Your application
    ↓
Production server
```

Every step introduces potential risk.

This is your:

> **Software supply chain**

---

# 4. Why supply-chain security matters

Suppose your application is perfectly written:

```text
Your code
    ↓
100% secure
```

But you install a malicious package:

```text
Your code
    +
malicious dependency
    ↓
compromised application
```

Your application can still be compromised.

So:

> **Secure application code is not enough if your dependencies are compromised.**

Imagine you're building a house.

You carefully build:

```text
Foundation
Walls
Doors
Windows
```

But you purchase:

```text

electrical components
```

from unknown suppliers.

If one supplier gives you defective or malicious material, your house can still have a problem.

Software dependencies work similarly.

```text

Third-party packages

Complete application
```

# 6. `package.json` vs `package-lock.json`

This is one of the most important concepts.

You normally have:

```text
package.json
package-lock.json
```

They have different purposes.

### `package.json`

Describes your project's dependencies and acceptable version ranges.

For example:

```json
{
  "dependencies": {
    "express": "^5.1.0"
  }
}
```

### `package-lock.json`

Records the exact dependency tree that npm resolved.

Conceptually:

```text
package.json
     ↓
Allowed dependency ranges

package-lock.json
     ↓
Exact resolved versions
```

---

# 7. Why lockfiles matter

Suppose:

```text
package.json
express = ^5.1.0
```

The `^` allows compatible updates.

Today npm might install:

```text
5.1.2
```

Later:

```text
5.1.5
```

Without a lockfile, different installations could potentially resolve different dependency versions.

With:

```text
package-lock.json
```

the project records the resolved dependency tree.

This makes installations much more reproducible.

---

# 8. Never casually delete `package-lock.json`

A beginner sometimes sees:

```text
package-lock.json
```

and thinks:

> "It's generated. I can delete it."

Don't do that casually.

The lockfile is valuable for:

```text
Reproducible installs
CI/CD consistency
Security auditing
Dependency tracking
Debugging
```

For an application repository, normally commit it to Git.

```bash
git add package.json package-lock.json
```

---

# 9. `npm install` vs `npm ci`

This distinction is important for production and CI.

### Development

You commonly use:

```bash
npm install
```

It can update the lockfile when dependency resolution changes.

### CI / reproducible installation

You commonly use:

```bash
npm ci
```

`npm ci` is designed around the existing lockfile.

Conceptually:

```text
package-lock.json
       ↓
npm ci
       ↓
exact dependency tree
```

This is useful for CI/CD.

---

# 10. Why `npm ci` is useful

Imagine your GitHub Actions pipeline:

```text
git push
   ↓
CI
   ↓
npm ci
   ↓
npm test
   ↓
npm run build
```

You want CI to install the dependency tree represented by your committed lockfile.

That makes builds more predictable.

# 11. What is a vulnerable dependency?

Imagine you have:

```text
your application
      ↓
some-package
      ↓
vulnerable-package
```

A security vulnerability may exist in that package.

For example, conceptually:

```text
vulnerable-package
version 1.2.3
      ↓
known security vulnerability
```

Your application may therefore inherit the risk even if **you never directly wrote code using that vulnerable package**.

---

# 12. `npm audit`

npm provides:

```bash
npm audit
```

This checks your dependency tree against known vulnerability information.

Run it from your project:

```bash
npm audit
```

You may see categories such as:

```text
low
moderate
high
critical
```

The exact output depends on your dependency tree and current vulnerability database.

---

# 13. Don't blindly run `npm audit fix`

You may see:

```bash
npm audit fix
```

This can automatically update dependencies where npm determines a compatible fix is available.

But don't develop the habit:

```text
audit
 ↓
audit fix
 ↓
done
```

That's not proper security engineering.

A dependency update can introduce:

```text
Breaking changes
Behavior changes
New bugs
Compatibility issues
```

So after updates:

```text
Update
 ↓
Test
 ↓
Review
 ↓
Build
 ↓
Security check
```

---

# 14. Audit results require understanding

Suppose npm says:

```text
some-package
Severity: high
```

Don't immediately panic.

Ask:

```text
Which package?
Direct or transitive?
Which version?
What vulnerability?
Is our application affected?
Is there a fixed version?
Will updating cause breaking changes?
```

Security alerts require context.

# 15. Direct vs transitive dependency

Suppose:

```json
{
  "dependencies": {
    "express": "..."
  }
}
```

Express is your:

```text
Direct dependency
```

But Express may depend on:

```text
package-a
package-b
package-c
```

Those are:

```text
Transitive dependencies
```

So:

```text
Your project
│
├── express        ← direct
│    ├── package-a ← transitive
│    └── package-b ← transitive
│
└── mongoose       ← direct
     └── package-c ← transitive
```

---

# 16. Why transitive dependencies matter

You may say:

> "I never installed package-a."

That doesn't necessarily mean you're safe.

Your dependency tree may still contain it.

This is why:

```bash
npm audit
```

looks beyond just your direct dependencies.

# 17. Dependency tree

You can inspect your dependency tree using:

```bash
npm ls
```

For example:

```bash
npm ls express
```

This helps you understand where a package came from.

Conceptually:

```text
my-backend
 └── express
      └── dependency-x
           └── vulnerable-package
```

Now you know the path through the supply chain.

You should not leave dependencies untouched forever.

Why?

Because updates can include:

```text
Security patches
Bug fixes
Performance improvements
Compatibility fixes
New features
```

But don't update everything randomly every day.

A better process:

```text
Review
 ↓
Update intentionally
 ↓
Run tests
 ↓
Review changelog
 ↓
Run security checks
 ↓
Commit
```

# 19. A practical update workflow

Suppose you want to update a package.

Start:

```bash
npm outdated
```

This can show packages where newer versions exist.

Then inspect:

```text
Current
Wanted
Latest
```

Don't blindly jump to `latest`.

Understand what changed.

---

# 20. Semantic versioning

You'll often see:

```text
1.4.2
```

This represents:

```text
MAJOR.MINOR.PATCH
```

For example:

```text
1.4.2
│ │ │
│ │ └── patch
│ └──── minor
└────── major
```

Generally:

### Patch

```text
1.4.2 → 1.4.3
```

Bug/security fixes.

### Minor

```text
1.4.2 → 1.5.0
```

New functionality while maintaining compatibility according to semver expectations.

### Major

```text
1.4.2 → 2.0.0
```

Potential breaking changes.

This is why major dependency upgrades deserve more attention.

---

# 21. Why `^` matters

You might see:

```json
{
  "express": "^5.1.0"
}
```

The `^` means npm can resolve compatible versions within the specified semver range.

But remember:

```text
package.json
```

expresses the acceptable range, while:

```text
package-lock.json
```

records the actual resolution for the project.

---

# 22. The danger of random version ranges

Imagine someone writes:

```json
{
  "some-package": "*"
}
```

This is generally a poor practice for production applications.

You're essentially saying:

```text
Give me whatever version fits.
```

You lose control.

Prefer intentional version constraints and commit your lockfile.

---

# 23. Typosquatting

This is one of the most interesting supply-chain attacks.

Suppose the real package is:

```text
express
```

An attacker might publish a malicious package with a similar name:

```text
expresss
```

or:

```text
express-js
```

A developer accidentally runs:

```bash
npm install expresss
```

instead of:

```bash
npm install express
```

Now:

```text
Developer typo
      ↓
Malicious package
      ↓
Installed locally
      ↓
Potential compromise
```

This is called:

> **Typosquatting**

---

# 24. Why typosquatting works

Developers install packages quickly.

For example:

```bash
npm install some-package
```

They may not carefully check:

```text
package name
publisher
download source
repository
version
```

An attacker takes advantage of that.

---

# 25. Don't blindly copy npm commands

Suppose a random website tells you:

```bash
npm install super-secret-helper
```

Don't immediately run it.

First investigate:

```text
Who maintains it?
Is it the official package?
Is the repository legitimate?
How many users?
How old is it?
Does the package actually need these permissions?
Are there suspicious install scripts?
```

Your terminal is a powerful environment.

Running:

```bash
npm install
```

can execute package lifecycle scripts.

---

# 26. Malicious package lifecycle scripts

Some npm packages can execute scripts during installation.

For example, packages can define lifecycle hooks in `package.json`.

Conceptually:

```json
{
  "scripts": {
    "postinstall": "..."
  }
}
```

This means installing a package can potentially execute code.

Therefore:

> **Installing a package is a trust decision.**

Don't treat it like downloading a passive text file.

---

# 27. Supply-chain attack example

Imagine:

```text
You
 ↓
Install package A
 ↓
Package A depends on B
 ↓
B gets compromised
 ↓
New malicious version published
 ↓
Your build installs B
 ↓
Malicious code executes
```

Your application code may not have changed at all.

The supply chain changed underneath it.

---

# 28. Dependency confusion

Another supply-chain problem is **dependency confusion**.

Conceptually:

```text
Your organization
      ↓
Uses internal package:
@company/auth-utils
```

An attacker might try to publish a package with a confusingly similar name to a public registry.

If your tooling is misconfigured, the build may accidentally retrieve the attacker's package.

The lesson:

> Package names and package sources must be controlled carefully, especially in organizations with private packages.

---

# 29. Keep dependencies minimal

One of the simplest security strategies is:

> **Don't install packages you don't need.**

Bad:

```text
Project
 ├── 150 dependencies
 ├── 300 dependencies
 └── many unused packages
```

Better:

```text
Project
 ├── Express
 ├── Mongoose
 ├── Zod
 ├── JWT
 └── only what the application actually needs
```

Every additional dependency increases:

```text
Attack surface
Maintenance
Upgrade work
Dependency tree size
Potential vulnerabilities
```

---

# 30. Don't install a package for tiny functionality

Suppose you need to capitalize a string:

```js
const result =
    name.charAt(0).toUpperCase() + name.slice(1);
```

Don't necessarily install:

```bash
npm install capitalize-everything
```

for a tiny task.

Ask:

> Is this dependency worth introducing into the supply chain?

Sometimes yes.

Often no.

---

# 31. Review package permissions

When evaluating a package, think about what it can access.

A package running inside your Node process potentially operates with the privileges available to that process.

If your backend can access:

```text
Database
Environment variables
Filesystem
Network
Cloud credentials
```

then malicious code inside the application process may potentially interact with those resources.

This is why dependency security is serious.

---

# 32. Environment variables make supply-chain attacks dangerous

Your production backend may have:

```text
MONGODB_URI
JWT_SECRET
REDIS_URL
OPENAI_API_KEY
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

If malicious code executes inside your application process, secrets could potentially become a target.

That's another reason to:

```text
Minimize dependencies
+
Review packages
+
Protect secrets
+
Use least privilege
```

---

# 33. Never commit secrets to Git

Supply-chain security connects with secret security.

Don't put:

```env
OPENAI_API_KEY=sk-...
JWT_SECRET=...
DATABASE_URL=...
```

into Git.

Use:

```text
.env
```

and:

```text
.gitignore
```

for local secrets, plus a proper secrets-management solution in production.

# 38. Why `latest` can be problematic

Consider:

```dockerfile
FROM node:latest
```

Today:

```text
node:latest
 ↓
Version A
```

Later:

```text
node:latest
 ↓
Version B
```

Your build may change even though your Dockerfile didn't.

This can make builds less predictable.

Prefer intentional image versions/tags appropriate to your deployment strategy.

# 39. Docker image layers

A Docker image can conceptually contain:

```text
Base OS
   ↓
Node runtime
   ↓
System packages
   ↓
npm dependencies
   ↓
Application code
```

Every layer contributes to the attack surface.

Therefore:

```text
Smaller image
+
Fewer unnecessary packages
+
Updated base image
=
Better security posture
```

---

# 40. Don't run unnecessary software in your image

If your Node application doesn't need:

```text
curl
vim
gcc
python
```

don't automatically include them in your production image.

A minimal runtime image reduces unnecessary components.

This is the principle of:

> **Minimize the attack surface.**

---

# 41. Multi-stage Docker builds

A useful production pattern is:

```text
Build stage
    ↓
Install dependencies
Compile/build
    ↓
Runtime stage
    ↓
Only what is needed to run
```

Conceptually:

```dockerfile
FROM node:... AS build

# install/build
...

FROM node:... AS production

# copy only runtime artifacts
...
```

The final image doesn't need every build tool.

This can improve both:

```text
Image size
Security
```

# 45. Dependency pinning

For highly controlled environments, teams may pin versions more strictly.

For example:

```json
{
  "dependencies": {
    "some-package": "1.4.2"
  }
}
```

instead of:

```json
{
  "dependencies": {
    "some-package": "^1.4.2"
  }
}
```

The tradeoff is:

```text
More control
      vs
More maintenance
```

Your lockfile already gives your project substantial reproducibility, so don't change version strategy without understanding why.



# 🎯 Your Developer Mental Model

From now on, whenever you type:

```bash
npm install some-package
```

don't think:

> "I need this package."

Think:

> **"I'm adding another piece of software into my application's trusted computing environment."**

Then ask:

```text
Do I need it?
       ↓
Is it the correct package?
       ↓
Is it maintained?
       ↓
Does it have known vulnerabilities?
       ↓
What dependencies does it bring?
       ↓
What permissions does my application have?
       ↓
Can I keep the dependency tree small?
```

That's the difference between **"I know npm"** and **"I understand software supply-chain security."**

And this fits your overall Phase 14 goal: security isn't something added at the very end. Your roadmap explicitly treats security as a cross-cutting concern while Phase 14 provides the deeper security pass.
