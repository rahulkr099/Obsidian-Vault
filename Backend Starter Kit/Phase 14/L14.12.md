# Lesson 14.12 — Security Testing & Final Audit

Before we start, one important clarification from your uploaded roadmap:

Your **current Phase 14 is Authentication**, while **Security Testing is formally Phase 22** in the original starter-pack roadmap.

However, in the **Phase 14 Security Engineering roadmap we've been following**, 14.12 is our security-testing/final-audit lesson. So we'll treat today's lesson as a **security audit checkpoint** using everything you've learned so far.

The goal is not:

> "Learn another security package."

The goal is:

> **Try to break your backend before an attacker does.**

---

# 1. What is security testing?

Normal testing asks:

> "Does my application work?"

Security testing asks:

> **"Can someone make my application do something it shouldn't?"**

For example:

Normal test:

```text
User A creates Todo
       ↓
201 Created
```

Security test:

```text
User A creates Todo
       ↓
Can User B access it?
       ↓
Must be NO
```

That's a completely different mindset.

---

# 2. Functional testing vs security testing

Imagine:

```http
GET /api/v1/todos/123
```

Functional test:

```text
Valid user
+
Todo exists
=
200 OK
```

Security tests:

```text
No token
     ↓
401

Invalid token
     ↓
401

Expired token
     ↓
401

User B requests User A's todo
     ↓
403/404

Malformed ID
     ↓
400
```

We're testing the **security boundaries**, not only the happy path.

# 5. Security boundary

Suppose:

```text
User A
   ↓
GET /courses/123
```

The server should determine:

```text
Who is User A?
       ↓
Authenticated?
       ↓
Authorized for course 123?
       ↓
Allowed?
```

The client should **never be the final authority**.

For example, this is not security:

```js
if (req.body.isAdmin) {
    // allow admin operation
}
```

Because the user controls:

```json
{
  "isAdmin": true
}
```

# 6. Authentication testing

First attack your authentication system.

Suppose:

```http
POST /api/v1/auth/login
```

Test:

```text
Correct email
Correct password
        ↓
200
```

Then:

```text
Correct email
Wrong password
        ↓
401
```

Then:

```text
Unknown email
Any password
        ↓
401
```

Then:

```text
No email
No password
        ↓
400
```

Your authentication endpoint should behave predictably.

# 7. Test missing authentication

Suppose:

```http
GET /api/v1/profile
```

requires authentication.

Send:

```http
GET /api/v1/profile
```

without:

```http
Authorization: Bearer ...
```

Expected:

```text
401 Unauthorized
```

If you receive:

```text
200 OK
```

you've found a serious security bug.

# 8. Test malformed JWTs

Try:

```http
Authorization: Bearer abc
```

or:

```http
Authorization: Bearer random-data
```

The server should reject it.

Expected:

```text
401 Unauthorized
```

It should **not crash**.

---

# 9. Test expired JWTs

Suppose a token expires after:

```text
15 minutes
```

Use an expired token.

Expected:

```text
401 Unauthorized
```

You should never have:

```text
expired token
     ↓
server accepts
     ↓
protected resource
```

---

# 10. Test token tampering

Imagine your JWT payload contains:

```json
{
  "userId": "123",
  "role": "user"
}
```

An attacker might try changing:

```json
{
  "userId": "123",
  "role": "admin"
}
```

without possessing the signing secret.

The server must reject the modified token.

Why?

Because JWT verification checks the signature.

Conceptually:

```text
Token
 ↓
Verify signature
 ↓
Valid?
 ├── YES → trust claims within limits
 └── NO  → reject
```

---

# 11. Important JWT rule

Never test security by simply decoding a JWT.

Remember:

```text
Decode
    ≠
Verify
```

Anyone can decode a JWT payload.

Security comes from:

```text
Signature verification
+
Expiration validation
+
Issuer/audience validation where appropriate
+
Application authorization
```

---

# 12. Authentication ≠ authorization

This is one of the most important security-testing concepts.

Suppose User A is logged in.

Authentication says:

```text
"This is User A."
```

Authorization asks:

```text
"Can User A perform this action?"
```

So:

```text
Authenticated
    ≠
Authorized
```

---

# 13. Test IDOR

One of the most important API security tests is **IDOR** — Insecure Direct Object Reference.

Suppose:

```http
GET /api/v1/users/101
```

belongs to User A.

User B changes:

```text
101
```

to:

```text
100
```

and gets User A's private data.

That's a security vulnerability.

---

# 14. IDOR example with your LMS

Imagine:

```text
GET /api/v1/courses/123/materials/456
```

Material `456` belongs to:

```text
Course 123
Instructor 10
```

A student changes the URL:

```text
/materials/457
```

and gets another course's private document.

That's an authorization failure.

# 15. The secure database query

A dangerous pattern:

```js
Material.findById(materialId);
```

This only asks:

> Does this material exist?

A stronger ownership-aware query might conceptually be:

```js
Material.findOne({
    _id: materialId,
    courseId: authorizedCourseId
});
```

Now you're asking:

> Does this material exist **and does it belong to the resource this user is authorized to access?**

This is why your earlier Repository Pattern lessons matter.

---

# 16. Test horizontal privilege escalation

Horizontal escalation means:

```text
User A
  ↓
accesses User B's resources
```

Both users have the same role:

```text
USER
```

Example:

```text
User A
GET /users/B/profile
```

Expected:

```text
403 or 404
```

not:

```text
200 OK
```

---

# 17. Test vertical privilege escalation

Vertical escalation means:

```text
USER
 ↓
tries ADMIN operation
```

For example:

```http
DELETE /api/v1/users/123
```

A normal user should not be able to perform an admin-only operation.

Test:

```text
Regular user
     ↓
Admin endpoint
     ↓
403 Forbidden
```

---

# 18. Test role manipulation

Suppose signup accepts:

```json
{
  "email": "rahul@example.com",
  "password": "..."
}
```

An attacker may try:

```json
{
  "email": "attacker@example.com",
  "password": "...",
  "role": "admin"
}
```

If your server creates:

```text
role = admin
```

you have a privilege-escalation vulnerability.

This connects directly to the validation and mass-assignment concepts in your roadmap.

---

# 19. Test mass assignment

Suppose your model contains:

```text
name
email
role
isVerified
isAdmin
```

Your update endpoint accepts:

```json
{
  "name": "Rahul"
}
```

But an attacker sends:

```json
{
  "name": "Rahul",
  "role": "admin",
  "isVerified": true
}
```

If your update code blindly passes the entire object into MongoDB:

```js
User.findByIdAndUpdate(id, req.body);
```

you could accidentally allow sensitive fields to be modified.

---

# 20. Safer update design

Instead of:

```js
User.findByIdAndUpdate(id, req.body);
```

define explicitly what users can update:

```js
const allowedUpdates = {
    name: req.body.name,
    bio: req.body.bio
};
```

Then:

```text
Client input
     ↓
Allowed fields only
     ↓
Service
     ↓
Repository
```

This is **allowlisting**.

# 21. Test injection

Your backend accepts user-controlled data.

Examples:

```text
email
search
sort
filter
IDs
query parameters
JSON body
```

Try malicious inputs against your validation layer.

For example:

```text
unexpected object
unexpected array
special operators
very long strings
malformed IDs
unexpected nested objects
```

The goal isn't merely:

> "Can I make MongoDB execute something?"

The broader question is:

> **Can attacker-controlled data change the meaning of my database query?**

# 23. Test unexpected fields

Suppose:

```json
{
  "name": "Rahul",
  "isAdmin": true
}
```

Your validator should either:

```text
Reject unknown field
```

or:

```text
Strip unknown field
```

What you don't want is:

```text

      ↓

```

without deliberate handling.

# 24. Rate-limit testing

Your login endpoint is especially sensitive.

Imagine:

```text
POST /auth/login
```

An attacker sends:

```text
1000 requests
```

very quickly.

Your rate limiter should eventually respond with something like:

```text
429 Too Many Requests
```

The security test is:

```text
Repeated requests
       ↓
Rate limiter
       ↓
429
```

---

# 25. Don't test only from one IP

In real security testing, think about how your rate limiter identifies clients.

Possible keys:

```text
IP
User ID
Email
IP + account
API key
```

If your strategy is only:

```text
IP → 100 requests
```

an attacker might distribute requests across multiple IP addresses.

The correct strategy depends on the endpoint and threat model.

---

# 26. Test login abuse

For example:

```text
100 wrong passwords
       ↓
same account
```

Ask:

```text
Does the account receive protection?
Does the endpoint slow down?
Is the IP rate-limited?
Is suspicious activity logged?
```

This is more meaningful than simply checking whether a rate-limiter package exists.

---

# 27. Refresh-token testing

Suppose:

```text
POST /auth/refresh
```

uses refresh-token rotation.

A test should be:

```text
Refresh token A
     ↓
refresh
     ↓
Token B issued
```

Then try:

```text
Refresh token A again
```

Expected:

```text
Rejected
```

if your rotation design invalidates the previous token.

This helps detect refresh-token replay.

---

# 28. Logout testing

After:

```http
POST /auth/logout
```

test the old credentials/tokens according to your architecture.

For example:

```text
Logout
 ↓
Refresh token invalidated
 ↓
Old refresh token
 ↓
Rejected
```

Don't assume "logout endpoint returned 200" means logout security works.

# 29. Cookie security testing

If authentication uses cookies, inspect:

```text
HttpOnly
Secure
SameSite
Domain
Path
Expiration
```

For example, production authentication cookies should generally be configured carefully so JavaScript cannot unnecessarily access sensitive tokens.

Test whether:

```text
document.cookie
```

can access a sensitive authentication cookie.

If it can, your `HttpOnly` strategy may not be working as intended.

# 30. CORS testing

Suppose your API allows:

```text
https://your-frontend.com
```

Test an unexpected origin:

```text
https://evil-example.com
```

Ask:

```text
Does the server incorrectly allow it?
```

Your CORS policy should be deliberate.

Don't use:

```js
origin: "*"
```

as a lazy solution for an authenticated private API.

---

# 31. CSRF testing

If you're using cookie-based authentication, think about CSRF.

The threat is roughly:

```text
Victim logged into your site
        ↓
Attacker-controlled website
        ↓
Browser automatically sends cookies
        ↓
Unwanted request to your API
```

Your defense depends on your architecture and can involve:

```text
SameSite cookies
CSRF tokens
Origin checking
appropriate CORS configuration
```

The important thing is to understand the threat before choosing a defense.

# 34. Test error responses

Send malformed requests.

For example:

```text
invalid ObjectId
missing field
invalid JSON
database failure
unknown route
expired token
```

Ask:

> Does the server reveal internal implementation details?

Bad:

```json
{
  "error": "/home/rahul/project/src/repositories/user.repository.js:47"
}
```

or:

```text
MongoDB connection string...
```

Better:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc123"
}
```

And the detailed information stays in controlled server logs.

# 40. Security test matrix

A useful way to think is:

|Area|Attack|Expected|
|---|---|---|
|Auth|No JWT|`401`|
|Auth|Expired JWT|`401`|
|Auth|Modified JWT|`401`|
|Auth|Wrong password|`401`|
|Authorization|User B → User A data|`403/404`|
|RBAC|User → admin endpoint|`403`|
|Validation|Invalid body|`400`|
|Rate limit|Too many requests|`429`|
|CORS|Unauthorized origin|Blocked|
|Upload|Oversized file|Rejected|
|Upload|Unauthorized download|`403/404`|
|Injection|Malicious query input|Rejected/safely handled|
|Secrets|Sensitive data in response|Must not appear|
|RAG|Unauthorized course retrieval|No results|

The exact status code can depend on your API contract; the important part is the **security outcome**.

# 42. Example: IDOR security test

Conceptually:

```js
it("should prevent user B from accessing user A's todo", async () => {
    const userA = await createUser();
    const userB = await createUser();

    const todo = await createTodo({
        userId: userA.id
    });

    const response = await request(app)
        .get(`/api/v1/todos/${todo.id}`)
        .set("Authorization", `Bearer ${userB.token}`);

    expect(response.status).toBe(403);
});
```

The important part isn't the exact Jest/Supertest syntax.

It's the security rule:

```text
Owner ≠ requester
        ↓
Access denied
```

---

# 43. Example: role escalation test

```js
it("should not allow a normal user to become admin", async () => {
    const response = await request(app)
        .post("/api/v1/auth/signup")
        .send({
            email: "attacker@example.com",
            password: "StrongPassword123!",
            role: "admin"
        });

    // Verify the created user is NOT admin.
});
```

The exact assertion depends on your signup design.

The security principle is:

> **Privileged fields must not be controlled by untrusted clients.**

---

# 44. Example: expired token test

Conceptually:

```js
it("rejects an expired access token", async () => {
    const expiredToken = createExpiredToken();

    const response = await request(app)
        .get("/api/v1/profile")
        .set("Authorization", `Bearer ${expiredToken}`);

    expect(response.status).toBe(401);
});
```

This converts your security assumption into an automated guarantee.

# 46. Your final security review questions

Before calling your backend production-ready, ask:

### Identity

> Can an attacker become another user?

### Authorization

> Can a user access another user's resource?

### Privilege

> Can a normal user become an admin?

### Input

> Can malicious data change application behavior?

### Abuse

> Can an attacker automate requests without meaningful limits?

### Secrets

> Can secrets appear in logs, responses, Git, or errors?

### Files

> Can attackers upload or download files they shouldn't?

### Dependencies

> Are vulnerable or untrusted packages present?

### AI

> Can untrusted content manipulate the AI system?

### Infrastructure

> Can a compromised component gain more access than it needs?

If you can answer these systematically, you're thinking like a security engineer.

# 48. The golden rule

Suppose you discover:

> "User A can access User B's todo."

Don't simply fix the query.

Do this:

```text
Bug discovered
     ↓
Understand why
     ↓
Fix authorization
     ↓
Write security test
     ↓
Run test
     ↓
Commit
```

Now the vulnerability is much less likely to return later.

```text

```

asks:

> **"Does that protection actually work?"**

So don't think:

```text

✓

JWT middleware installed
✓

✓
```

Instead think:

```text

Can I access another user's data?
Can I inject unexpected fields?

```
