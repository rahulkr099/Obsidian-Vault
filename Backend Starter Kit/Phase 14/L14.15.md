We've now moved from:

```text

```

The natural next step is:

> **How do we know that something suspicious is happening in production?**

So today we're learning the **security side** of that topic.

---

# 1. Prevention is not enough

Imagine your backend has:

```text
Authentication ✓
Authorization ✓
Validation ✓
Rate limiting ✓
Security tests ✓
```

Great.

But an attacker might still find a way through.

What happens then?

If you have no monitoring:

```text
Attacker
   ↓
Successful attack
   ↓
Nobody notices
```

With monitoring:

```text
Attacker
   ↓
Suspicious activity
   ↓
Logs
   ↓
Detection
   ↓
Alert
   ↓
Investigation
```

This is why security needs **visibility**.

---

# 2. Three different concepts

Don't mix these three:

### Logging

> Record what happened.

### Monitoring

> Continuously observe what's happening.

### Alerting

> Tell someone when something important happens.

Think:

```text
Application
    ↓
Logs
    ↓
Monitoring
    ↓
Alerts
```

---

# 3. Example

Suppose someone attempts 500 logins.

Your application might produce:

```text
LOGIN_FAILED
LOGIN_FAILED
LOGIN_FAILED
...
```

Logging records them.

Monitoring notices:

```text
500 failed logins from one source
```

Alerting says:

```text
🚨 Possible brute-force attack
```

Each layer has a different job.

---

# 4. What should security logging capture?

For important security events, useful information includes:

```text
Who?
What?
When?
Which resource?
Success or failure?
Request ID?
```

For example:

```json
{
  "event": "login.failed",
  "userId": "123",
  "requestId": "req_abc",
  "timestamp": "..."
}
```

But don't log sensitive secrets.

---

# 5. What should NEVER be logged?

Be extremely careful with:

```text
Passwords
Access tokens
Refresh tokens
API keys
Database passwords
Session secrets
Encryption keys
Password-reset tokens
```

Bad:

```js
logger.info({
    password: req.body.password
});
```

Never do this.

---

# 6. Why logs themselves are sensitive

Your logs may contain:

```text
User IDs
Emails
IP addresses
URLs
Error information
Security events
```

An attacker who gets access to your logging system may learn a lot.

Therefore:

> **Logs need security too.**

Think:

```text
Application data
      ↓
Protected

Logs
      ↓
Also protected
```

---

# 7. Security events vs normal events

Not every event deserves the same attention.

Normal:

```text
GET /courses
```

Security-sensitive:

```text
LOGIN_FAILED
PASSWORD_CHANGED
ROLE_CHANGED
REFRESH_TOKEN_REUSED
ACCESS_DENIED
ADMIN_ACTION
```

These events deserve stronger auditing.

---

# 8. Authentication events

You should be able to identify events such as:

```text
LOGIN_SUCCESS
LOGIN_FAILED
LOGOUT
TOKEN_REFRESH
TOKEN_REFRESH_FAILED
PASSWORD_CHANGED
PASSWORD_RESET_REQUESTED
PASSWORD_RESET_COMPLETED
EMAIL_VERIFIED
```

This doesn't mean you must literally use these exact names.

The idea is:

> **Important identity events should be observable.**

---

# 9. Authorization events

Also monitor:

```text
ACCESS_DENIED
ROLE_CHANGED
PERMISSION_CHANGED
UNAUTHORIZED_RESOURCE_ACCESS
```

For example:

```text
User B
   ↓
GET /todos/123
   ↓
Todo belongs to User A
   ↓
403
   ↓
Audit event
```

You now have evidence that an authorization boundary was triggered.

---

# 10. Suspicious patterns

One failed authorization attempt may be normal.

But:

```text
User B
 ↓
403
 ↓
403
 ↓
403
 ↓
403
 ↓
403
```

could indicate enumeration or an attack.

Monitoring looks for **patterns**, not just individual events.

---

# 11. Enumeration attacks

Suppose an attacker tries:

```text
/users/1
/users/2
/users/3
/users/4
...
/users/10000
```

Individually, each request might look normal.

Together:

```text
10,000 resource requests
```

is suspicious.

This is why metrics and aggregated monitoring matter.

---

# 12. Brute-force detection

Imagine:

```text
100 failed logins
```

within a few minutes.

A useful security signal might be:

```text
failed_login_count > threshold
```

Then:

```text
Monitor
   ↓
Threshold exceeded
   ↓
Alert
```

This can trigger additional protection such as rate limiting or temporary blocking, depending on your architecture.

---

# 13. Impossible behavior

Monitoring should also help identify strange patterns.

For example:

```text
User normally:
10 API requests/hour

Suddenly:
50,000 requests/hour
```

Or:

```text
Normal:
read courses

Suddenly:
delete users
change roles
```

This doesn't automatically prove compromise.

But it's a signal worth investigating.

---

# 14. Audit logging

Audit logging is slightly different from ordinary application logging.

Normal log:

```text
Request completed
```

Audit log:

```text
Admin changed User 123's role
```

Audit logs answer:

> **Who performed an important action, on what resource, and when?**

---

# 15. Example audit event

Imagine an admin changes:

```text
USER
student
   ↓
instructor
```

An audit event could contain:

```json
{
  "event": "user.role_changed",
  "actorId": "admin123",
  "targetUserId": "user456",
  "oldRole": "student",
  "newRole": "instructor",
  "requestId": "req789"
}
```

Notice the important distinction:

```text
actorId
```

means:

> Who performed the action?

while:

```text
targetUserId
```

means:

> Who was affected?

This distinction becomes extremely useful during investigations.

---

# 16. Actor vs target

Always think:

```text
Actor
  ↓
performs action
  ↓
Target
```

Example:

```text
Admin
  ↓
changes role
  ↓
Student
```

So:

```text
actor = admin
target = student
```

This makes audit logs much more useful.

---

# 17. Request IDs

Your starter roadmap specifically includes **request IDs** as part of observability.

Suppose:

```text
requestId = req_123
```

Then you can connect:

```text
HTTP request
      ↓
Authentication
      ↓
Authorization
      ↓
Controller
      ↓
Service
      ↓
Repository
      ↓
Audit event
```

using the same identifier.

---

# 18. Why request IDs matter during incidents

Suppose a user says:

> "Something went wrong when I deleted my course."

They provide:

```text
requestId: req_123
```

You can search your logs:

```text
req_123
```

and reconstruct the request path.

Without request IDs, investigation can become much harder.

---

# 19. Structured logging

Avoid relying only on:

```js
console.log("user logged in");
```

Structured logging gives you machine-readable information:

```js
logger.info({
    event: "login.success",
    userId,
    requestId
});
```

Now logging systems can search and aggregate fields.

Your roadmap later explicitly introduces **structured logging**, log levels, request IDs, user context, and Pino.

---

# 20. Log levels

Common levels include:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

A simple mental model:

### DEBUG

Detailed development information.

### INFO

Normal important application events.

### WARN

Something unusual happened.

### ERROR

An operation failed.

### FATAL

A serious failure affecting the application.

The exact levels and semantics depend on the logger you're using.

---

# 21. Security events and log levels

For example:

```text
Successful login
→ INFO
```

```text
Repeated failed login
→ WARN
```

```text
Unexpected authentication failure
→ WARN/ERROR
```

```text
Database unavailable
→ ERROR
```

```text
Application cannot start safely
→ FATAL
```

Don't make every event `ERROR`.

If everything is an error:

```text
ERROR
ERROR
ERROR
ERROR
ERROR
```

then real problems become difficult to notice.

---

# 22. Security metrics

Logs tell you individual events.

Metrics help you see trends.

For example:

```text
login_failures_total
login_success_total
authorization_denied_total
password_reset_requests_total
api_requests_total
```

Then you can observe:

```text
Failed logins:
10 → 20 → 30 → 40 → 10,000
```

That spike is meaningful.

---

# 23. Metrics vs logs

Think:

```text
LOG
=
"What happened in this particular event?"

METRIC
=
"How often is this happening?"
```

Example:

### Log

```text
User 123 failed login at 10:31:04
```

### Metric

```text
login_failures = 8,423
```

Both are useful.

# 25. Alerting

Not every event needs an alert.

If you alert on:

```text
every failed login
```

you'll probably create alert fatigue.

Instead, alert on meaningful patterns.

For example:

```text
50 failed logins
within 1 minute
from one source
```

might deserve an alert.

---

# 26. Alert fatigue

This is a real production problem.

Imagine:

```text
Monday:
100 alerts

Tuesday:
200 alerts

Wednesday:
300 alerts
```

Eventually developers stop paying attention.

That's dangerous.

A good alert should mean:

> **Someone should probably investigate this now.**

---

# 27. Detection rules

A simple detection rule could be:

```text
IF
failed_logins > 50
AND
time_window < 5 minutes

THEN
alert
```

Another:

```text
IF
admin_role_changes > normal_threshold

THEN
alert
```

Another:

```text
IF
authorization_denied spikes dramatically

THEN
investigate
```

These rules depend on your system and normal traffic.

---

# 28. Security monitoring flow

Your production architecture eventually looks like:

```text
                 REQUEST
                    │
                    ▼
               APPLICATION
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
        LOGS                METRICS
```

# 29. Audit logs should be trustworthy

Here's a subtle security problem.

Suppose a normal user can modify:

```text
audit_logs
```

Then an attacker could:

```text
Perform attack
   ↓
Delete audit evidence
```

That's bad.

Audit logs should have stronger access controls than ordinary application data.

---

# 30. Don't let application users delete security evidence

For example, avoid giving:

```text
DELETE /audit-logs/:id
```

to ordinary application users.

In many systems, audit records should be:

```text
append-only
```

or otherwise protected against unauthorized modification.

---

# 31. Audit log retention

Logs don't need to live forever.

You need a policy.

Think about:

```text
How long?
Who can access them?
Where are they stored?
When are they archived?
When are they deleted?
```

Retention depends on your application's requirements and applicable policies/laws.

---

# 32. Clock synchronization

Imagine:

```text
Server A:
10:02:01

Server B:
09:58:41
```

If clocks are badly out of sync, incident investigation becomes confusing.

Production systems therefore need reliable time synchronization.

This becomes increasingly important when you have:

```text
multiple servers
containers
queues
databases
external services
```

---

# 33. Don't log secrets for debugging

A very common beginner mistake:

```js
console.log("JWT:", token);
```

or:

```js
console.log("password:", password);
```

because:

> "I'm debugging."

But logs can remain long after debugging.

Better:

```js
logger.debug({
    userId,
    requestId,
    event: "token.created"
});
```

No actual secret.

---

# 34. Redaction

Sometimes you genuinely need to log an object.

Instead of:

```js
logger.info(req.headers);
```

which might include:

```text
Authorization: Bearer ...
Cookie: ...
```

you should redact sensitive fields.

Conceptually:

```text
Request
 ↓
Remove sensitive fields
 ↓
Log safe representation
```

This is an important part of production logging.

---

# 35. Security monitoring for authentication

For your LMS, monitor patterns like:

```text
Failed login spikes
Password reset spikes
Refresh-token reuse
Many accounts from same source
Many sources attacking one account
Repeated invalid JWTs
Unusual admin logins
```

This helps detect:

```text
credential stuffing
brute force
token abuse
account takeover
```

---

# 36. Security monitoring for authorization

Monitor:

```text
Repeated 403 responses
Access attempts across many resource IDs
Large numbers of denied requests
Unexpected admin operations
Sudden role changes
```

For example:

```text
GET /courses/1 → 403
GET /courses/2 → 403
GET /courses/3 → 403
...
GET /courses/1000 → 403
```

That pattern is more suspicious than one isolated `403`.

---

# 37. Security monitoring for file uploads

Monitor:

```text
Large upload spikes
Repeated rejected file types
Many uploads from one account
Many download attempts
Unexpected file access patterns
```

For your future LMS:

```text
Student
  ↓
uploads 50,000 documents
```

should probably trigger investigation.

---

# 38. Security monitoring for AI

Your AI LMS will need additional signals.

For example:

```text
AI requests/user
Tokens/user
Cost/user
Tool calls
Retrieval failures
Unauthorized retrieval attempts
Prompt-injection detection signals
```

Suppose:

```text
Normal student:
20 AI requests/day
```

Suddenly:

```text
Student:
50,000 AI requests/hour
```

That's both:

```text
Security problem
+
Cost problem
```

Monitoring helps detect it.

---

# 39. Security monitoring for RAG

Monitor:

```text
Which user?
Which course?
Which documents retrieved?
How many chunks?
Was authorization applied?
```

This can help detect:

```text
Cross-course retrieval
Unexpected document access
Mass document enumeration
```

You don't necessarily need to log the full document content.

In fact, you generally should avoid doing so unnecessarily.

---

# 40. Privacy-aware monitoring

Security logging must balance:

```text
Visibility
     +
Privacy
```

You want enough information to investigate.

But not:

```text
Every request
+
Every password
+
Every token
+
Every document
+
Every AI conversation
```

That would create another security and privacy risk.

---

# 41. The principle of minimum logging

Ask:

> **What is the minimum information needed to investigate this event?**

For example:

Instead of:

```text
password = "secret123"
```

log:

```text
login_failed
userId = 123
requestId = abc
```

You know what happened without storing the secret.

---

# 42. Security monitoring and least privilege

Your monitoring infrastructure also needs least privilege.

For example:

```text
Application
   ↓
Can write logs

Application
   X
Cannot delete audit history
```

Monitoring service:

```text
Can read relevant metrics
```

Security team:

```text
Can investigate audit records
```

This limits damage if one component is compromised.

---

# 43. A practical audit event model

For your backend, a conceptual audit record might be:

```js
{
    event: "user.role_changed",

    actorId: "admin123",

    targetId: "user456",

    action: "ROLE_CHANGED",

    metadata: {
        oldRole: "student",
        newRole: "instructor"
    },

    requestId: "req789",

    timestamp: new Date()
}
```

Notice:

```text
actor
target
action
context
requestId
time
```

These are powerful investigation fields.

---

# 44. Don't put business logic inside logging

Bad:

```js
if (user.role === "admin") {
    logSomething();
    // authorization logic...
}
```

Logging should observe what happened.

It shouldn't secretly become your authorization system.

Better:

```text
Authorization
     ↓
decision
     ↓
Audit logging
```

---

# 45. Security event pipeline

A clean architecture can be:

```text
Controller/Service
        │
        │ important action
        ▼
   Audit Service
        │
        ▼
   Audit Repository
        │
        ▼
 Audit Store
```

Meanwhile ordinary application logs can go through:

```text
Application
     ↓
Logger
     ↓
Log system
```

These serve slightly different purposes.

---

# 46. Audit log vs application log

|Application Log|Audit Log|
|---|---|
|Debugging/operations|Security/accountability|
|Technical events|Important user actions|
|High volume|More selective|
|Developers/operators|Security/admin investigators|
|May rotate frequently|Often stronger retention/integrity|

There can be overlap, but don't treat them as identical.

---

# 47. Example: deleting a course

Application logs:

```text
DELETE /courses/123
status=204
duration=42ms
```

Audit log:

```text
actorId=admin123
action=COURSE_DELETED
targetId=123
requestId=req456
```

Now:

```text
Application log
=
technical behavior
```

```text
Audit log
=
accountability
```

---

# 48. What happens during an incident?

Suppose an instructor's account is compromised.

You can search:

```text
actorId = instructor123
```

and find:

```text
09:01 LOGIN_SUCCESS
09:02 COURSE_UPDATED
09:03 COURSE_DELETED
09:04 ROLE_CHANGED
09:05 DOCUMENT_DOWNLOADED
```

Now you have a timeline.

Without audit logging:

```text
"Something happened."
```

With audit logging:

```text
"We can see exactly which important actions occurred."
```
