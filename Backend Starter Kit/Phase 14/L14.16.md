# Lesson 14.16 — Threat Modeling for Your Backend

We've reached another natural extension of Phase 14.


The goal today is to learn how to **think like an attacker before you write the code**.

---

# 1. What is threat modeling?

Threat modeling means systematically asking:

> **"How could someone misuse or attack this system?"**

Instead of building first and discovering problems later:

```text
Build
  ↓
Deploy
  ↓
Attack discovered
  ↓
Fix
```

we try to do:

```text
Design
  ↓
Think about threats
  ↓
Add security controls
  ↓
Build
  ↓
Test
```

This is much cheaper.

---

# 2. A simple example

Imagine your LMS has:

```text
Student
   ↓
Login
   ↓
Dashboard
   ↓
Course
   ↓
PDF
```

A beginner may think:

> "I need a login page and course API."

A security-minded developer asks:

```text
Can someone access another student's course?

Can someone download a private PDF?

Can someone change their role?

Can someone bypass login?

Can someone guess resource IDs?

Can someone abuse the AI endpoint?
```

That's threat modeling.

---

# 3. Threat modeling isn't just for security experts

You don't need to be a penetration tester.

As a backend developer, you can start with four questions:

```text
1. What are we protecting?
2. Who could attack or misuse it?
3. How could they do it?
4. What controls can stop them?
```

That's already a useful threat-modeling habit.

---

# 6. Who are we protecting against?

Threat modeling requires thinking about different actors.

For example:

```text
Anonymous attacker
Authenticated user
Malicious student
Compromised instructor
Compromised admin
Automated bot
Insider
Compromised third-party service
```

Don't assume:

> "The attacker is always an anonymous hacker."

An authenticated user can be dangerous too.

---

# 7. The important distinction

Authentication does not mean:

> "This user is trusted."

It means:

> **"We know which account is making this request."**

That account could itself be compromised or malicious.

Therefore:

```text
Authenticated user
        ≠
Trusted user
```

This is one of the most important backend security concepts.

# 9. Trust boundaries

Now ask:

> **Where does data move from a less-trusted environment into a more-trusted environment?**

For example:

```text

   │
   │ untrusted input
   ▼
API
   │
   │ validated data
   ▼
Service
   │
   ▼
Database
```

The boundary between:

```text
Browser → Backend
```

is extremely important.

# 11. Threat modeling your login system

Suppose:

```text
POST /api/v1/auth/login
```

You should ask:

```text
Can attackers brute-force it?

Can they enumerate users?

Can they steal credentials?

Can they reuse old tokens?

Can they bypass validation?

Can they abuse password reset?
```

Then add controls.

---

# 12. Threat → control

This is the core of threat modeling.

|Threat|Possible control|
|---|---|
|Brute force|Rate limiting|
|Credential theft|Secure password hashing|
|Token theft|Short expiry / rotation|
|User enumeration|Generic responses|
|Password reset abuse|Secure single-use tokens|
|Session abuse|Revocation/rotation|
|Input attacks|Validation + sanitization|

You don't just identify threats.

You connect them to **controls**.

---

# 13. Threat modeling authorization

Suppose:

```http
GET /api/v1/courses/:courseId
```

Ask:

```text
Can any authenticated user access it?

Only enrolled students?

Only instructors?

Only the course owner?

Can an instructor access another instructor's course?

Can an admin access everything?
```

Now you've discovered the authorization policy before implementation.

---

# 14. Threat modeling an IDOR

Suppose:

```text
GET /todos/123
```

Potential threat:

```text
User B changes:

/todos/123
      ↓
/todos/124
      ↓
/todos/125
```

and discovers another user's resources.

Threat:

> **Insecure Direct Object Reference / broken object-level authorization**

Control:

```text
Authenticated user
       ↓
Resource ownership check
       ↓
Database query scoped to user
```

And then:

```text
Security regression test
```

# 17. Threat modeling RAG

Imagine:

```text

 └── Private document A.pdf

Course B
```

# 23. STRIDE

A popular threat-modeling framework is **STRIDE**.

It represents:

```text
S → Spoofing
T → Tampering
R → Repudiation
I → Information Disclosure
D → Denial of Service
E → Elevation of Privilege
```

You don't need to memorize the framework immediately.

But knowing these six categories is useful.

---

# 24. S — Spoofing

Question:

> Can someone pretend to be another user?

Examples:

```text
Stolen credentials
Stolen session
Forged token
Account takeover
```

Controls:

```text
Strong authentication
Secure sessions
Token validation
MFA where appropriate
```

---

# 25. T — Tampering

Question:

> Can someone modify data they shouldn't?

Examples:

```text
Change another user's profile
Modify course content
Change role
Modify grades
```

Controls:

```text
Authorization
Validation
Database constraints
Audit logs
```

---

# 26. R — Repudiation

Question:

> Can someone perform an important action and later deny that it happened because we have no reliable record?

Example:

```text
Admin deletes course
```

Without audit logs:

```text
Who did it?
Unknown.
```

With audit logging:

```text
actorId
action
target
timestamp
requestId
```

much easier to investigate.

---

# 27. I — Information Disclosure

Question:

> Can someone access information they shouldn't?

Examples:

```text
User A sees User B's data
Student sees instructor documents
API returns passwordHash
AI retrieves private document
```

Controls:

```text
Authorization
Data filtering
Safe serialization
Encryption
Access controls
```

---

# 28. D — Denial of Service

Question:

> Can someone make the system unavailable or too expensive?

Examples:

```text
Brute-force requests
Huge file uploads
Expensive AI requests
Database-heavy queries
Request flooding
```

Controls:

```text
Rate limiting
Request limits
File limits
Query limits
Timeouts
Caching
Resource quotas
```

---

# 29. E — Elevation of Privilege

Question:

> Can a low-privilege user become more powerful?

Example:

```text
Student
   ↓
role=admin
```

Controls:

```text
Server-side authorization
Protected role changes
Input filtering
Audit logging
Regression tests
```

This is one of the most dangerous API vulnerabilities.

---

# 30. STRIDE applied to your LMS

Imagine:

```text
Student → API → Course → AI
```

You might identify:

|STRIDE|LMS example|
|---|---|
|Spoofing|Stolen student session|
|Tampering|Modify course progress|
|Repudiation|No record of admin action|
|Information Disclosure|Private course data leaked|
|Denial of Service|AI request flooding|
|Elevation|Student becomes admin|

Now you've got a basic threat model.

# 31. Threat prioritization

Not every threat deserves equal engineering effort.

Consider:

```text
Likelihood
     ×
Impact
     =
Risk
```

For example:

```text
Low likelihood + low impact
        ↓
Low priority
```

But:

```text
High likelihood + high impact
        ↓
Critical priority
```

---

# 32. Example risk matrix

|Threat|Likelihood|Impact|Priority|
|---|---|---|---|
|Brute-force login|High|Medium|High|
|IDOR|Medium|High|High|
|Database credential leak|Low|Critical|Critical|
|Minor UI issue|High|Low|Low|
|AI cost abuse|Medium|Medium/High|High|

These are examples, not fixed ratings.

Your actual application determines the risk.

# 33. Threat model before coding

Suppose you're about to implement:

```text
Course certificate download
```

Before coding, ask:

```text
Who can download it?
Can another user guess the ID?
Can the URL be shared?
Does it expire?
Can a deleted user still access it?
Can an instructor access it?
Can an admin access it?
```

Now your security requirements are clearer.

---

# 34. Threat model during code review

A pull request says:

```text

```

Don't review only:

```text
Does it work?
```

Also ask:

```text
Who can call it?
What can they access?
Can IDs be guessed?
Can files leak?
Is authorization enforced?
Are logs safe?
Is rate limiting needed?
```

That's security-minded code review.

# 41. The most important question

Whenever you design an endpoint, ask:

> **"If I were a malicious user, what would I try here?"**

For:

```http
POST /users
```

maybe:

```text
Can I create an admin?
```

For:

```http
GET /courses/:id
```

maybe:

```text
Can I access someone else's private course?
```

For:

```http
POST /ai/chat
```

maybe:

```text
Can I make the AI reveal protected information?
```

For:

```http
DELETE /users/:id
```

maybe:

```text
Can I delete another account?
```

This simple habit is extremely valuable.

---

# 42. Your security design mindset

Don't think:

```text
"How do I make this endpoint work?"
```

Think:

```text
"How do I make this endpoint work
for legitimate users
while preventing unauthorized behavior?"
```

That is a major step toward professional backend engineering.

# 🎯 Final Mental Model

Threat modeling gives us the **map**.

```text
                 SYSTEM
                    │
             ┌──────┴──────┐
             ▼             ▼
           Assets         Actors
             │             │
             └──────┬──────┘
                    ▼
                 Threats
                    │
                    ▼
                  Risks
                    │
                    ▼
                Controls
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        Tests    Monitoring  Response
```

And this is the bigger Phase 14 security loop we've built:

```text
Threat Modeling
      ↓
Security Controls
      ↓
Security Testing
      ↓
Regression Testing
      ↓
Monitoring & Audit
      ↓
Incident Response
      ↓
Lessons Learned
      ↓
Threat Model Updated
      ↓
      ↺
```

**The key lesson:** don't wait for an attacker to teach you how your system can fail. **Use threat modeling to think about the attack paths before they become vulnerabilities.**
