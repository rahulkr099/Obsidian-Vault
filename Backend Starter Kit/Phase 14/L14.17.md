# 2. Security is a system

A beginner may think:

```text
Security = JWT
```

That's incorrect.

Another beginner might think:

```text
Security = Helmet + CORS
```

Also incorrect.

A production backend needs multiple layers:

```text
                SECURITY
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
   Identity     Input       Access
       │           │           │
       ▼           ▼           ▼
Authentication Validation Authorization
       │           │           │
       └──────┬────┴─────┬─────┘
              ▼          ▼
          Protection   Monitoring
              │          │
              └────┬─────┘
                   ▼
              Response
```

# 3. Defense in depth

The main idea is:

> **Don't depend on one security control.**

Imagine:

```text
Attacker
   ↓
Rate limit
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Business rules
   ↓
Database access control
   ↓
Audit logging
```

If one layer fails, another layer may still prevent or detect the attack.

That's **defense in depth**.

# 5. Authentication answers one question

Authentication asks:

> **Who are you?**

Example:

```text
JWT
 ↓
verify
 ↓
userId = 123
```

Now your application knows:

```text
req.user.id = 123
```

But that does **not** mean the user can do everything.

---

# 6. Authorization answers another question

Authorization asks:

> **Are you allowed to perform this operation?**

Example:

```text
User 123
   ↓
DELETE Course 456
```

You need to determine:

```text
Is User 123:
    owner?
    instructor?
    admin?
    enrolled student?
```

Authentication:

```text
Who?
```

Authorization:

```text
Allowed?
```

Keep those separate.

---

# 7. Validation answers another question

Suppose:

```http
PATCH /users/123
```

contains:

```json
{
  "role": "admin"
}
```

Authentication says:

```text
Yes, this is User 123.
```

Authorization says:

```text
User 123 isn't allowed to change roles.
```

Validation additionally says:

```text
Is "role" even an allowed input field for this endpoint?
```

These controls solve different problems.

---

# 8. Why validation alone isn't security

Suppose you validate:

```json
{
  "title": "Learn Node.js"
}
```

Great.

But an attacker may still ask:

```text
GET /todos/another-users-id
```

The input might be perfectly valid.

The problem is authorization.

So:

```text
Valid input
    ≠
Authorized action
```

Very important.

---

# 9. Why authentication alone isn't security

Imagine:

```text
User A logs in successfully.
```

Then they request:

```text
GET /users/B
```

Authentication succeeds.

But authorization should fail.

Therefore:

```text
Authenticated
    ≠
Authorized
```

# 10. Middleware responsibility

Your middleware layer can handle cross-cutting security concerns.

For example:

```text
middlewares/
│
├── auth.middleware.js
├── requestId.middleware.js
├── logger.middleware.js
│
└── security/
    ├── cors.middleware.js
    ├── rateLimiter.middleware.js
    ├── sanitize.middleware.js
    └── validate.middleware.js
```

Your uploaded starter roadmap specifically uses middleware for security, validation, authentication, request IDs, and logging.

---

# 11. But don't put everything in middleware

This is a common architectural mistake.

Bad:

```text
auth.middleware.js
   ↓
authentication
   ↓
database query
   ↓
business rules
   ↓
send email
   ↓
modify user
```

Now your middleware has become a giant application layer.

Instead:

```text
Middleware
    ↓
basic request/security boundary
    ↓
Controller
    ↓
Service
    ↓
Repository
```

Each layer has a clear job.

---

# 12. Controller security responsibility

Controllers should remain relatively thin.

Example:

```js
const deleteCourse = async (req, res) => {
    await courseService.deleteCourse({
        courseId: req.params.courseId,
        userId: req.user.id
    });

    return res.status(204).send();
};
```

Notice:

The controller receives:

```text
courseId
userId
```

and passes them to the service.

The controller shouldn't contain 100 lines of authorization logic.

---

# 13. Service security responsibility

The service contains business rules.

For example:

```text
deleteCourse(courseId, userId)
```

might mean:

```text
Find course
   ↓
Does it exist?
   ↓
Does user own it?
   ↓
Is user allowed to delete it?
   ↓
Delete
```

This is business logic.

Your Phase 12 roadmap explicitly places business rules inside the service layer rather than controllers.

---

# 14. Repository security responsibility

The repository should make data access precise.

Instead of:

```js
Course.findById(courseId);
```

you might need:

```js
Course.findOne({
    _id: courseId,
    ownerId: userId
});
```

Now the database query itself reflects the ownership boundary.

This is especially powerful against IDOR.

---

# 15. The secure ownership pattern

Compare:

### Dangerous

```js
findById(courseId)
```

followed by some later assumption.

### Stronger

```js
findOne({
    _id: courseId,
    ownerId: userId
})
```

The second approach says:

> **Only retrieve the resource if it belongs to this user.**

Your uploaded roadmap specifically highlights this ownership-query idea in its authorization architecture.

---

# 16. Security should follow the data

Think about:

```text
User
 ↓
Course
 ↓
Document
 ↓
AI retrieval
```

At every step ask:

```text
Who owns this?
Who can access this?
What relationship exists?
```

For example:

```text
Student
 ↓
Enrollment
 ↓
Course
 ↓
Document
```

Authorization may depend on the enrollment relationship.

---

# 17. Security boundary around MongoDB

Your application should never assume:

```text
"Because the controller checked ownership, the database query can be unrestricted."
```

A safer mindset is:

```text
Service
   ↓
authorized context
   ↓
Repository
   ↓
scoped query
   ↓
MongoDB
```

This reduces the chance that another caller accidentally retrieves unauthorized data.

---

# 18. Security boundary around AI

For your future LMS:

```text
User
 ↓
AI API
 ↓
Service
 ↓
Authorization
 ↓
RAG retrieval
 ↓
Allowed documents
 ↓
LLM
```

The important part is:

```text
Authorization
       ↓
BEFORE sensitive retrieval
```

not:

```text
Retrieve everything
       ↓
Ask AI not to reveal it
```

The latter is a dangerous design.

---

# 19. Never make the model your authorization system

Suppose the user asks:

> "Show me another student's private document."

Don't rely on:

```text
LLM:
"I should not reveal this."
```

Instead:

```text
Application
   ↓
Authorization
   ↓
Private document excluded
   ↓
LLM never receives it
```

Security should happen **before sensitive information reaches the model**.

---

# 20. Secrets belong outside the request path

Imagine:

```text
OPENAI_API_KEY
MONGO_URI
JWT_SECRET
```

These should never be:

```text
req.body
```

or:

```text
frontend JavaScript
```

or:

```text
logs
```

The browser should never receive server-side secrets.

---

# 21. Security configuration

Your application should have a clear configuration boundary:

```text
config/
├── env.js
├── database.js
└── ...
```

Conceptually:

```text
Environment
     ↓
Config
     ↓
Application
```

not:

```text
Random process.env.X
Random process.env.Y
Random process.env.Z
```

everywhere.

Centralized configuration makes security review easier.

---

# 22. Rate limiting belongs near the edge

For example:

```text
Internet
   ↓
Rate limiter
   ↓
Application
```

Why?

You want abusive traffic stopped as early as reasonably possible.

For sensitive endpoints, use stricter policies:

```text
Login
Password reset
OTP
AI requests
File uploads
```

than ordinary read operations.

---

# 23. But rate limiting isn't authorization

This:

```text
100 requests/minute
```

doesn't answer:

> Is this user allowed to access Course 123?

Rate limiting controls:

```text
How much?
```

Authorization controls:

```text
Who can do what?
```

Again, different security boundaries.

---

# 24. Logging shouldn't replace prevention

Suppose you have:

```text
Authorization failure → audit log
```

That's useful.

But this is not enough:

```text
Allow unauthorized request
       ↓
Log it
```

Logging is detection/accountability.

Authorization is prevention.

You want:

```text
Authorization
    ↓
Block
    ↓
Log
```

---

# 25. Security architecture should produce evidence

When an important operation occurs:

```text
Admin changes role
```

you want:

```text
Authorization decision
       ↓
Operation
       ↓
Audit event
```

So later you can answer:

```text
Who?
What?
When?
Which resource?
Was it successful?
```

That's operational security.

---

# 26. Error handling is part of security

Suppose MongoDB throws:

```text
MongoServerError:
duplicate key index users_email_unique
```

Don't necessarily expose that raw error to the user.

Instead:

```json
{
  "success": false,
  "message": "Email is already registered",
  "requestId": "req_123"
}
```

Your roadmap explicitly includes hiding sensitive errors in production and consistent error responses.

---

# 27. Security headers are another layer

A security middleware stack may include:

```text
Helmet
CORS
HPP
Input sanitization
Rate limiting
```

These help reduce certain classes of attacks.

But don't think:

```text
Helmet = secure backend
```

It's only one layer.

# 29. Security architecture isn't just code

There are four major parts:

```text
                SECURITY
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
    Code        Process       People
      │            │            │
      ▼            ▼            ▼
 Controls       Reviews       Awareness
 Tests          Incidents     Access
```

For a solo developer, "people" may simply mean:

> **Your own development habits.**

---

# 30. Secure-by-default

One of the strongest principles is:

> **Make the secure behavior the default behavior.**

Bad:

```text
findUser(id)
```

and developers must remember to add authorization.

Better architecture may encourage:

```text
findUserForActor(id, actorId)
```

when appropriate.

Similarly:

```text
public endpoint
```

should be explicit rather than accidentally public.

---

# 31. Fail closed

Another important principle:

> **When security information is missing or invalid, deny access.**

For example:

```text
No user
 ↓
DENY
```

rather than:

```text
No user
 ↓
Maybe allow
```

Similarly:

```text
Unknown role
 ↓
DENY
```

not:

```text
Unknown role
 ↓
Treat as admin
```

---

# 32. Least privilege

Give each actor only what they need.

Example:

```text
Student
 ├── read enrolled courses
 ├── update own progress
 └── use allowed AI features
```

Not:

```text
Student
 └── access everything
```

Similarly, your application database account shouldn't necessarily have unrestricted database privileges if a more limited role can work.

---

# 33. Minimize attack surface

Every feature adds potential attack surface.

For example:

```text
File upload
   ↓
New risks
```

```text
Admin API
   ↓
New risks
```

```text
AI tools
   ↓
New risks
```

So ask:

> **Do we actually need this capability?**

If yes:

> **Can we expose less of it?**

This is attack-surface reduction.

# 34. Security review checklist

Before considering an endpoint complete:

```text
[ ] Authentication required?
[ ] Correct authorization?
[ ] Input validated?
[ ] Unknown fields rejected?
[ ] Rate limit needed?
[ ] Sensitive data exposed?
[ ] Errors safe?
[ ] Logs safe?
[ ] Audit event needed?
[ ] Ownership enforced?
[ ] Tests added?
[ ] Abuse scenario considered?
```

This is a practical checklist you can reuse.

```

```

# 38. What you should NOT memorize

Don't try to memorize:

```text
50 security headers
100 attack names
every OWASP acronym
every security library
```

Those can be looked up.

Instead, memorize the reasoning:

```text
Who is this?
What are they allowed to do?
What data can they access?
What input can they control?
What happens if they abuse it?
How will we detect it?
How will we recover?
```

Those questions stay useful for years.
