# Lesson 14.18 — Logout

According to your actual Phase 14 roadmap, **14.18 is Logout**.

This lesson is important because logout is often misunderstood as simply:

```text
"Delete the JWT from the browser."
```

For a proper authentication system, logout is more than that.

---

# 1. What does logout actually mean?

When a user logs out, we want to make their authentication session unusable.

A simplified flow is:

```text
User
 ↓
Logout
 ↓
Invalidate refresh token
 ↓
Clear refresh-token cookie
 ↓
Session can no longer be refreshed
```

The key idea:

> **Logout should prevent the user from obtaining new access tokens from their existing refresh token.**

---

# 2. Why is logout tricky with JWT?

Remember our two-token architecture:

```text
ACCESS TOKEN
Short-lived
     ↓
API requests
```

and:

```text
REFRESH TOKEN
Long-lived
     ↓
Get new access token
```

Suppose:

```text
Access Token
expires in 15 minutes

Refresh Token
expires in 7 days
```

The user clicks:

```text
Logout
```

What happens?

If you only delete the access token:

```text
Access token ❌
Refresh token ✅
```

the refresh token could potentially still be used to obtain another access token.

That's why refresh-token invalidation matters.

---

# 3. Our authentication architecture

From the previous lessons:

```text
LOGIN
  │
  ├── Access Token
  │
  └── Refresh Token
          │
          ▼
    Hash refresh token
          │
          ▼
       MongoDB
```

For example:

```text
users
└── Rahul
    ├── passwordHash
    └── refreshTokenHash
```

The database does **not** need to store the raw refresh token.

---

# 4. What happens during logout?

Conceptually:

```text
POST /api/v1/auth/logout
            │
            ▼
      Authentication
            │
            ▼
       Auth Service
            │
            ▼
 Clear refreshTokenHash
            │
            ▼
 Clear refresh-token cookie
            │
            ▼
          204
```

The important operations are:

```text
1. Invalidate server-side refresh-token state
2. Remove client-side refresh-token cookie
```

---

# 5. Logout route

A typical endpoint could be:

```http
POST /api/v1/auth/logout
```

Why `POST`?

Because logout represents an action that changes authentication/session state.

We're not simply retrieving information.

---

# 6. Why should logout usually be POST?

Compare:

```http
GET /auth/logout
```

with:

```http
POST /auth/logout
```

GET should generally be safe and not perform state-changing operations.

Logout changes authentication state.

Therefore:

```text
POST /auth/logout
```

is a better API design.

---

# 7. Do we need authentication middleware?

There are multiple possible designs.

One common design:

```text
POST /logout
       ↓
auth middleware
       ↓
controller
```

But there's an important question:

> What if the access token has already expired?

The user may still have a valid refresh-token cookie.

If logout requires a valid access token, logout may fail simply because the access token expired.

Therefore, logout design depends on how your refresh-token/session architecture works.

---

# 8. A practical design

For our learning architecture, think of logout as primarily invalidating the refresh-token session.

Conceptually:

```text
Logout request
     ↓
Read refresh token/session
     ↓
Invalidate server-side session
     ↓
Clear cookie
```

This is often more useful than requiring a still-valid access token.

---

# 9. The refresh token is the important part

Suppose:

```text
Access token:
AT-123

Refresh token:
RT-456
```

Database stores:

```text
hash(RT-456)
```

After logout:

```text
refreshTokenHash = null
```

So:

```text
RT-456
   ↓
hash
   ↓
Compare with database
   ↓
No matching active token
   ↓
REJECT
```

Now the refresh token cannot create a new access token.

---

# 10. Why not store the raw refresh token?

Don't do:

```text
refreshToken: "eyJhbGciOi..."
```

Instead:

```text
refreshTokenHash:
"$2b$12$..."
```

If the database is leaked, storing raw refresh tokens would make the situation much worse.

This follows the same principle we learned with passwords:

```text
Password
   ↓
Hash
   ↓
Database
```

and:

```text
Refresh Token
   ↓
Hash
   ↓
Database
```

Your starter roadmap explicitly includes **14.16 Refresh Token Hashing** immediately before rotation and logout.

---

# 11. Clearing the cookie

Suppose the refresh token is stored in:

```text
HttpOnly cookie
```

Logout should also remove it.

Conceptually:

```js
res.clearCookie("refreshToken");
```

But there's an important detail.

The cookie options used when clearing it should match the relevant cookie configuration.

For example:

```js
res.clearCookie("refreshToken", {
    httpOnly: true,
    secure: true,
    sameSite: "strict"
});
```

The exact production configuration depends on your deployment architecture.

---

# 12. Why clear both sides?

Think of two locations:

```text
CLIENT
refreshToken cookie
       │
       │
       ▼
SERVER
refreshTokenHash
```

Logout should clean both:

```text
CLIENT
   ↓
clear cookie

SERVER
   ↓
invalidate stored token
```

So:

```text
Client state + Server state
```

both become logged out.

---

# 13. What if we only clear the cookie?

Suppose:

```text
Browser
 ↓
refreshToken cookie deleted
```

but:

```text
Database
 ↓
refreshTokenHash still valid
```

The current browser is logged out.

But if the refresh token had been copied somewhere else, that token may potentially remain usable.

Therefore:

> **Client-side deletion alone is not enough for strong server-side session invalidation.**

---

# 14. What if we only delete the database token?

Suppose:

```text
Database
 ↓
refreshTokenHash = null
```

but the browser still contains:

```text
refreshToken cookie
```

The browser keeps sending a token that the server rejects.

That's not ideal UX.

Therefore:

```text
Invalidate server state
+
Clear client state
```

is the better design.

---

# 15. Logout service

Following our architecture:

```text
Route
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
MongoDB
```

The controller should remain thin.

For example:

```js
const logout = async (req, res) => {
    await authService.logout(req);

    res.clearCookie("refreshToken");

    return res.status(204).send();
};
```

The exact implementation will depend on whether your service receives the refresh token, user ID, or a session identifier.

---

# 16. What should the service do?

The service contains the authentication business logic.

Conceptually:

```text
authService.logout()
        ↓
identify session
        ↓
invalidate refresh token
        ↓
return
```

It should not contain HTTP-specific code such as:

```text
res.cookie()
res.status()
res.json()
```

Those belong to the controller/HTTP layer.

---

# 17. Repository responsibility

The repository handles database operations.

For example:

```text
authRepository.clearRefreshToken(userId)
```

Conceptually:

```js
User.updateOne(
    { _id: userId },
    {
        $unset: {
            refreshTokenHash: 1
        }
    }
);
```

Now the responsibilities are clean:

```text
Controller
 → HTTP

Service
 → authentication logic

Repository
 → MongoDB
```

---

# 18. Complete logout architecture

Think:

```text
                 POST /logout
                       │
                       ▼
                  Controller
                       │
                       ▼
                 Auth Service
                       │
                       ▼
              Auth Repository
                       │
                       ▼
                    MongoDB
                       │
                       ▼
            refreshTokenHash removed
                       │
                       ▼
                 Clear Cookie
                       │
                       ▼
                  HTTP 204
```

This is exactly the architecture you're learning throughout Phases 11–14.

---

# 19. Why return 204?

Logout doesn't necessarily need to return a JSON body.

You could return:

```http
204 No Content
```

meaning:

> The operation succeeded and there's no response body to return.

For example:

```http
POST /api/v1/auth/logout

HTTP/1.1 204 No Content
```

That's clean.

---

# 20. What about the access token?

Here's a subtle but very important point.

Suppose the user logs out:

```text
Access token
still valid for 10 minutes
```

If your API uses stateless JWT access tokens, the server may not automatically know that this particular access token should now be rejected.

Therefore:

```text
Logout
 ≠
Instantly invalidate every already-issued access token
```

unless you introduce some server-side revocation mechanism.

---

# 21. Why short-lived access tokens help

This is one reason we use:

```text
Short-lived access token
+
Longer-lived refresh token
```

For example:

```text
Access token
15 minutes

Refresh token
7 days
```

If logout invalidates the refresh token:

```text
New access token
       ↓
cannot be obtained
```

The existing access token naturally expires soon.

This reduces the need to maintain a huge access-token blacklist.

---

# 22. Token lifecycle

Let's visualize it.

### Login

```text
Login
 ↓
Access Token ───────→ API
 │
 └── expires soon

Refresh Token ──────→ Refresh endpoint
 │
 └── stored securely
```

### Refresh

```text
Refresh Token
     ↓
verify
     ↓
rotate
     ↓
new Access Token
```

### Logout

```text
Refresh Token
     ↓
invalidate
     ↓
clear cookie
```

That's the lifecycle.

---

# 23. Logout + refresh rotation

Remember Lesson 14.17:

```text
Refresh Token Rotation
```

Now combine it with logout.

```text
Login
 ↓
RT1

Refresh
 ↓
RT1 invalidated
 ↓
RT2 issued

Refresh
 ↓
RT2 invalidated
 ↓
RT3 issued

Logout
 ↓
RT3 invalidated
 ↓
cookie cleared
```

This creates a much stronger session lifecycle.

---

# 24. What if an attacker stole RT2?

Imagine:

```text
User:
RT2

Attacker:
RT2
```

User refreshes:

```text
RT2
 ↓
RT3
```

RT2 is now invalid.

If the attacker later tries:

```text
RT2
 ↓
REJECT
```

Depending on your implementation, reuse of an old refresh token can also become a signal for **token theft/reuse detection**.

We'll explore that more deeply in the token-theft lesson.

---

# 25. Logout doesn't mean deleting the user

This sounds obvious, but it's worth separating concepts.

Logout:

```text
Invalidate authentication session
```

Account deletion:

```text
Delete user account/data
```

They are completely different operations.

---

# 26. Logout vs session expiration

These are also different.

### Logout

User intentionally says:

```text
"I want to leave."
```

### Expiration

The system says:

```text
"Your authentication is no longer valid."
```

For example:

```text
Refresh token expired
        ↓
Login required
```

---

# 27. Logout vs password change

Suppose the user changes their password.

Depending on your session architecture, you may want to invalidate existing sessions too.

For example:

```text
Password changed
       ↓
Invalidate refresh sessions
       ↓
Require login again
```

This is especially useful if you suspect account compromise.

The exact policy depends on whether you support multiple concurrent sessions/devices.

---

# 28. Multiple devices make logout harder

Imagine:

```text
Laptop
 └── RT-A

Phone
 └── RT-B

Tablet
 └── RT-C
```

What should:

```text
Logout on Laptop
```

do?

Possibility 1:

```text
Invalidate RT-A only
```

Result:

```text
Laptop ❌
Phone ✅
Tablet ✅
```

Possibility 2:

```text
Invalidate all sessions
```

Result:

```text
Laptop ❌
Phone ❌
Tablet ❌
```

A mature authentication system often needs to distinguish:

```text
Logout current session
```

from:

```text
Logout all sessions
```

---

# 29. Session model

If you want multiple devices, eventually you may move from:

```text
User
 └── refreshTokenHash
```

to:

```text
User
   │
   ├── Session A
   ├── Session B
   └── Session C
```

For example:

```text
sessions
├── userId
├── tokenHash
├── expiresAt
├── createdAt
├── lastUsedAt
└── revokedAt
```

Then logout can revoke one session.

This is a useful future improvement for your backend architecture.

---

# 30. Security considerations

Logout should not leak sensitive information.

Avoid responses such as:

```json
{
  "refreshToken": "...",
  "sessionId": "..."
}
```

Instead:

```json
{
  "success": true,
  "message": "Logged out successfully"
}
```

or simply:

```http
204 No Content
```

---

# 31. Should logout fail if the token is already invalid?

Usually, logout should be **idempotent from the user's perspective**.

Meaning:

```text
Already logged out
        +
Logout again
        ↓
Still logged out
```

You generally don't want:

```text
Logout
 ↓
500 Internal Server Error
```

just because the session was already gone.

A clean logout endpoint can safely converge to:

```text
"Session is not active."
```

without exposing unnecessary details.

---

# 32. Logout and audit logging

Logout can be useful to log.

For example:

```text
AUTH_LOGOUT
```

with:

```text
userId
sessionId
timestamp
requestId
```

But be careful:

```text
❌ raw refresh token
❌ access token
❌ cookies
```

should never be logged.

---

# 33. Logout and security monitoring

Suppose you see:

```text
User logs out
 ↓
Refresh request
 ↓
Old token
 ↓
REJECT
```

This may be normal.

But repeated refresh-token reuse from unusual locations can become a security signal.

So:

```text
Authentication events
        ↓
Logs
        ↓
Monitoring
```

becomes useful.

# 36. Common beginner mistake #1

### Mistake

```js
const logout = (req, res) => {
    res.clearCookie("refreshToken");

    res.json({
        message: "Logged out"
    });
};
```

Problem:

Only the browser-side cookie is removed.

The server may still consider the refresh token valid.

---

# 37. Common beginner mistake #2

Clearing only the database value:

```text
refreshTokenHash = null
```

but forgetting:

```text
clearCookie()
```

Result:

```text
Browser
 ↓
keeps sending useless refresh token
```

Not a catastrophic security failure, but poor session cleanup and potentially confusing behavior.

---

# 38. Common beginner mistake #3

Trying to blacklist every access token

You might think:

```text
Logout
 ↓
Find access token
 ↓
Add to blacklist
```

This can work, but introduces state and cleanup complexity.

If access tokens are short-lived, a common architecture is simpler:

```text
Short-lived access token
+
Revocable refresh token
```

There are cases where access-token revocation is necessary, but don't add complexity without a requirement.

---

# 39. Common beginner mistake #4

Putting logout logic inside the repository

For example:

```text
repository.logout()
```

with:

```text
clear cookie
generate response
```

That's mixing layers.

Better:

```text
Controller
 └── clear cookie

Service
 └── authentication/session logic

Repository
 └── database update
```

---

# 40. Common beginner mistake #5

Logging the token

Never do:

```js
console.log("Refresh token:", refreshToken);
```

Even during development, get into the habit of treating tokens like passwords.

Log:

```text
userId
sessionId
event
requestId
```

not credentials.

# 41. Complete example architecture

Conceptually:

### Route

```js
router.post(
    "/logout",
    authController.logout
);
```

### Controller

```js
const logout = asyncHandler(async (req, res) => {
    await authService.logout(req);

    res.clearCookie("refreshToken");

    return res.status(204).send();
});
```

### Service

```js
const logout = async (req) => {
    const refreshToken = req.cookies.refreshToken;

    if (!refreshToken) {
        return;
    }

    // Identify/revoke the session.
    // Exact implementation depends
    // on the session design.
};
```

### Repository

```js
const revokeSession = async (sessionId) => {
    // Database operation
};
```

Don't copy this blindly into your starter yet. The important thing is understanding the **responsibility of each layer**.

Keep this diagram:

```text
                LOGOUT
                  │
                  ▼
          Read refresh session
                  │
                  ▼
        Identify current session
                  │
                  ▼
        Revoke/invalidate session
                  │
                  ▼
       Remove refresh-token cookie
                  │
                  ▼

```

Then:

```text
Old refresh token
       │
       ▼
 /refresh
       │
       ▼
   Rejected
```

That's the security property we want.

# 43. What happens to the access token?

Remember:

```text
Access token → short-lived
Refresh token → long-lived
```

After logout:

```text
Refresh token
      ↓
INVALID
```

Existing access token:

```text
Still potentially valid
until its expiration
```

Therefore, a typical architecture relies on the short access-token lifetime.

If your application requires **immediate access-token revocation**, you need an additional server-side mechanism such as session/version checks or a revocation strategy.

Don't introduce that complexity unless your requirements justify it.

---

# 44. Final mental model

Think of authentication as a door:

```text
                LOGIN
                  │
                  ▼
            Access Token
                  │
             short life
                  │
                  ▼
               API
```

Refresh token is the mechanism that gives you another temporary key:

```text
Refresh Token
      │
      ▼
New Access Token
```

Logout removes the ability to get another key:

```text
                 LOGOUT
                   │
                   ▼
        Refresh Session Revoked
                   │
                   ▼
          Cookie Removed
                   │
                   ▼
        Cannot Refresh Again
```

That's the real purpose of logout.
