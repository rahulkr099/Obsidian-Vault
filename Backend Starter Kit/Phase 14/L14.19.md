# Lesson 14.19 — Token Theft

This lesson builds directly on **refresh-token rotation, refresh-token hashing, and logout**.

The main question is:

> **What happens if an attacker steals a user's refresh token?**

---

## 1. The basic attack

Suppose Rahul logs in:

```text
Login
  ↓
Access Token  → AT1
Refresh Token → RT1
```

The refresh token is stored securely in an `HttpOnly` cookie.

But imagine an attacker somehow obtains:

```text
RT1
```

Now we have:

```text
Legitimate User
    ↓
    RT1

Attacker
    ↓
    RT1
```

This is **refresh-token theft**.

---

# 2. Why is a stolen refresh token dangerous?

An access token might expire quickly:

```text
Access Token
    ↓
15 minutes
    ↓
Expired
```

But a refresh token might live much longer:

```text
Refresh Token
    ↓
Days
    ↓
Can obtain new access tokens
```

So an attacker possessing a valid refresh token may be able to do:

```text
RT1
 ↓
/refresh
 ↓
New Access Token
 ↓
Access account
```

That's why protecting refresh tokens is extremely important.

---

# 3. Four layers protect us

Our architecture uses several defenses:

```text
              Refresh Token Security
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
     HTTPS          Hashing         Rotation
       │               │               │
       └───────────────┬───────────────┘
                       ▼
                    Revocation
```

In practice:

```text
HTTPS
+
HttpOnly cookie
+
Refresh-token hashing
+
Refresh-token rotation
+
Reuse detection
+
Revocation
```

No single mechanism is perfect.

---

# 4. Layer 1 — HTTPS

Never send authentication credentials over plain HTTP in production.

Bad:

```text
http://example.com
```

Better:

```text
https://example.com
```

HTTPS protects the connection against network-level interception.

But remember:

> HTTPS protects the token **while it travels**, not after the token has already been stolen from another source.

---

# 5. Layer 2 — HttpOnly cookie

A common approach is:

```text
Refresh Token
      ↓
HttpOnly Cookie
```

JavaScript cannot directly read an `HttpOnly` cookie.

So this:

```js
document.cookie
```

doesn't expose the refresh token.

This reduces the impact of many client-side token-theft scenarios.

But:

> HttpOnly does not make a token impossible to steal.

For example, malware, compromised infrastructure, browser compromise, or server-side leakage can still create risks.

---

# 6. Layer 3 — Hash the refresh token

Suppose the raw token is:

```text
RT1
```

Don't store:

```text
refreshToken = RT1
```

Store:

```text
refreshTokenHash = hash(RT1)
```

Then:

```text
RT1
 ↓
hash()
 ↓
H1
```

Database:

```text
H1
```

---

# 7. Why hashing matters after a database breach

Imagine an attacker obtains your database:

```text
users
 ├── email
 ├── passwordHash
 └── refreshTokenHash
```

They shouldn't immediately have:

```text
RT1
```

Instead they have:

```text
H1
```

The attacker still has a serious security problem to exploit, but you've avoided storing the actual authentication credential in plaintext.

---

# 8. Layer 4 — Refresh-token rotation

This is one of the most important defenses.

Without rotation:

```text
RT1
 ↓
Refresh
 ↓
AT2

RT1
 ↓
Refresh
 ↓
AT3

RT1
 ↓
Refresh
 ↓
AT4
```

The same refresh token remains usable repeatedly.

With rotation:

```text
RT1
 ↓
Refresh
 ↓
RT2
```

and:

```text
RT1 → invalid
RT2 → valid
```

Then:

```text
RT2
 ↓
Refresh
 ↓
RT3
```

Now:

```text
RT2 → invalid
RT3 → valid
```

This creates a moving authentication credential.

---

# 9. The stolen-token scenario

Here's where rotation becomes powerful.

Suppose:

```text
User has:
RT1
```

Attacker steals:

```text
RT1
```

The attacker hasn't used it yet.

Database/session state:

```text
RT1 → valid
```

Now the legitimate user refreshes.

```text
RT1
 ↓
refresh
 ↓
RT2 issued
```

Now:

```text
RT1 → invalid
RT2 → valid
```

The attacker still has:

```text
RT1
```

If they now attempt:

```text
RT1
 ↓
refresh
```

the server should reject it.

---

# 10. Token reuse is suspicious

This is an important security signal.

Suppose:

```text
RT1
```

has already been rotated.

Then somebody sends:

```text
RT1
```

again.

That means:

> **Someone is attempting to use an old refresh token.**

Possible explanation:

```text
User's old token
```

or:

```text
Attacker has stolen token
```

The application can treat this as a possible **refresh-token reuse attack**.

---

# 11. The family concept

A useful way to understand rotation is with a token family.

Imagine:

```text
RT1
 │
 └── RT2
       │
       └── RT3
             │
             └── RT4
```

These tokens belong to the same authentication session/family.

If:

```text
RT3
```

creates:

```text
RT4
```

then RT3 becomes invalid.

Now if someone later presents RT3:

```text
RT3
 ↓
Already used
 ↓
Suspicious reuse
```

The server can respond by revoking the relevant session/token family.

---

# 12. Why revoke the whole family?

Suppose:

```text
RT1 → RT2 → RT3 → RT4
```

The attacker possesses:

```text
RT2
```

The legitimate user possesses:

```text
RT4
```

Then an old RT2 appears again.

We don't know exactly who possesses which token.

A conservative security response can be:

```text
Detected reuse
      ↓
Revoke session family
      ↓
User must authenticate again
```

This prioritizes security over convenience.

---

# 13. The important tradeoff

This can cause:

```text
User
 ↓
Suddenly logged out
```

even if the legitimate user wasn't the attacker.

That's intentional.

When authentication credentials appear compromised:

> **It's safer to force re-authentication than to keep a potentially compromised session alive.**

---

# 14. Example attack timeline

Let's make this concrete.

### Step 1

User logs in:

```text
RT1
```

### Step 2

Attacker steals:

```text
RT1
```

### Step 3

User refreshes:

```text
RT1 → RT2
```

Now:

```text
RT1 ❌
RT2 ✅
```

### Step 4

Attacker uses stolen RT1:

```text
RT1 → /refresh
```

Server sees:

```text
RT1 already rotated
```

### Step 5

Security response:

```text
Reuse detected
      ↓
Revoke session
      ↓
Require login
```

This is the core idea.

---

# 15. Why hashing + rotation work together

These two solve different problems.

### Hashing

Protects the token **at rest**.

```text
Database breach
      ↓
Token isn't stored directly
```

### Rotation

Limits token **reuse**.

```text
Token used once
      ↓
Old token becomes invalid
```

Together:

```text
Hashing
  +
Rotation
  +
Reuse detection
  +
Revocation
```

provide much stronger protection.

---

# 16. What about access-token theft?

Refresh-token theft and access-token theft are different.

### Access token

Usually:

```text
Short-lived
```

So:

```text
Stolen AT
 ↓
Limited lifetime
```

### Refresh token

Usually:

```text
Longer-lived
```

So:

```text
Stolen RT
 ↓
Potentially much more dangerous
```

That's why refresh-token security receives extra attention.

---

# 17. Should we store access tokens in the database?

Usually, no.

One reason for JWT access tokens is that the server can validate them without storing every token.

Instead:

```text
JWT
 ↓
verify signature
 ↓
check expiration
 ↓
check claims
```

Refresh sessions can remain stateful:

```text
Refresh token
 ↓
database/session store
 ↓
revocable
```

This gives us a useful balance:

```text
Access tokens → mostly stateless
Refresh sessions → stateful + revocable
```

---

# 18. What if the attacker refreshes first?

This is an interesting case.

Suppose both have RT1:

```text
User      → RT1
Attacker  → RT1
```

Attacker acts first:

```text
RT1
 ↓
/refresh
 ↓
RT2
```

Now:

```text
RT1 ❌
RT2 ✅
```

The legitimate user later sends:

```text
RT1
```

The server detects:

```text
RT1 already used
```

This can trigger reuse detection.

Again:

```text
possible compromise
 ↓
revoke session
 ↓
force login
```

---

# 19. The race-condition problem

Now we encounter a deeper backend problem.

Suppose two requests arrive almost simultaneously:

```text
Request A → RT1
Request B → RT1
```

Both might check:

```text
RT1 is valid
```

before either request invalidates it.

Then both could potentially succeed.

This is a **concurrency/race-condition** problem.

---

# 20. Why atomic operations matter

The backend needs to make token rotation atomic.

Conceptually:

```text
Check RT1
+
Invalidate RT1
+
Issue RT2
```

should behave like one controlled operation.

You don't want:

```text
Request A:
check → valid

Request B:
check → valid

Request A:
invalidate

Request B:
invalidate
```

Both requests may incorrectly succeed.

---

# 21. Database-level thinking

A secure implementation often uses an atomic database operation or transaction strategy appropriate to the session model.

Conceptually:

```text
Find valid RT1
       +
Atomically mark RT1 as used/revoked
       ↓
Only one request succeeds
```

Then:

```text
Request A → success
Request B → reuse detected
```

This is an important production-level concept.

---

# 22. Why this matters in Node.js

You might think:

> "Node.js is single-threaded, so race conditions don't happen."

That's incorrect.

Your Node.js process can have many asynchronous requests:

```text
Request A
Request B
Request C
Request D
```

Database operations happen asynchronously and can interleave.

Therefore:

```text
Node.js
≠
No concurrency problems
```

---

# 23. Token theft from logs

One surprisingly common danger is accidental logging.

Bad:

```js
console.log(req.cookies.refreshToken);
```

or:

```js
logger.info({
    refreshToken
});
```

Now your logs contain a credential.

If an attacker gains access to logs:

```text
Logs
 ↓
Refresh Token
 ↓
Account compromise
```

So:

> **Never log authentication tokens.**

---

# 24. Token theft from URLs

Don't put refresh tokens into URLs.

Bad:

```text
https://example.com/refresh?token=RT1
```

Why?

URLs can leak through:

```text
browser history
logs
proxy logs
analytics
referrer information
```

Prefer secure cookies or appropriately protected request bodies/headers according to your architecture.

---

# 25. Token theft from frontend storage

A common approach is:

```text
localStorage
 └── refreshToken
```

This can expose the token to JavaScript running in the page.

For browser applications, an `HttpOnly` cookie is often preferable for refresh credentials because JavaScript cannot directly read it.

But cookies introduce their own considerations, especially around CSRF, `SameSite`, CORS, and cookie scope.

Security is about balancing these risks.

---

# 26. Cookie security

A refresh-token cookie should typically consider:

```text
HttpOnly
Secure
SameSite
Path
Domain
Max-Age / Expires
```

For example:

```text
HttpOnly
    ↓
JavaScript can't read it

Secure
    ↓
HTTPS only

SameSite
    ↓
Helps control cross-site sending
```

The exact values depend on your frontend/backend deployment setup.

---

# 27. Don't confuse CSRF and token theft

These are related but different problems.

### Token theft

```text
Attacker obtains the credential.
```

### CSRF

```text
Attacker tricks a browser into sending an authenticated request.
```

Cookie-based authentication requires you to think about both.

For example:

```text
HttpOnly
```

helps protect against JavaScript reading the cookie.

But it does **not automatically eliminate CSRF**.

---

# 28. Reuse detection flow

Let's build the security flow:

```text
Refresh Request
      │
      ▼
Extract refresh token
      │
      ▼
Hash token
      │
      ▼
Find matching session
      │
      ├── Not found
      │      ↓
      │    Reject
      │
      └── Found
             │
             ▼
       Is token active?
          │        │
         NO       YES
          │        │
          ▼        ▼
       Reuse?    Rotate
          │        │
          ▼        ▼
      Revoke      RT2
       family
```

This is the mental model to remember.

---

# 29. What should happen after reuse detection?

A strong response might be:

```text
Old refresh token detected
        ↓
Revoke current session/token family
        ↓
Invalidate refresh credentials
        ↓
Require fresh login
        ↓
Record security event
```

Depending on your security requirements, you might also notify the user.

For example:

```text
"We signed you out because we detected suspicious session activity."
```

Don't expose unnecessary technical details to the attacker.

---

# 30. Security event

Record something like:

```text
REFRESH_TOKEN_REUSE_DETECTED
```

Potential metadata:

```text
userId
sessionId
timestamp
requestId
IP metadata
user-agent metadata
```

Avoid:

```text
refreshToken
accessToken
password
```

---

# 31. Don't trust IP address alone

You might be tempted to say:

```text
Different IP
 ↓
Attacker
```

That's unreliable.

Users can legitimately change networks:

```text
Wi-Fi
 ↓
Mobile data
 ↓
Office
 ↓
VPN
```

So IP address can be a **signal**, not proof.

Similarly, user-agent changes aren't automatically malicious.

Security decisions should use multiple signals.

---

# 32. What if the attacker has the latest token?

Suppose the attacker steals:

```text
RT4
```

after it has become the current token.

Rotation can't detect theft **until the token is used in a suspicious way**.

That's an important limitation.

Therefore:

```text
Rotation
≠
Magic stolen-token prevention
```

It reduces the usefulness of previously used tokens and helps detect reuse.

It doesn't make a currently valid stolen token harmless.

---

# 33. This is why token protection still matters

You still need:

```text
HTTPS
HttpOnly
Secure cookie
Short token lifetime
Hashing
Rotation
Revocation
Monitoring
```

Because defense in depth matters.

# 35. Token theft and password change

Suppose the user reports:

> "Someone accessed my account."

A strong response can be:

```text
Password change
      ↓
Revoke sessions
      ↓
Re-authenticate
```

This is why session management should be designed as a first-class system rather than just a JWT helper.

# 36. A better session model

For a serious application, consider:

```text
User
 │
 ├── Session 1
 │     ├── tokenHash
 │     ├── createdAt
 │     ├── lastUsedAt
 │     ├── expiresAt
 │     └── revokedAt
 │
 ├── Session 2
 │     └── ...
 │
 └── Session 3
       └── ...
```

Now you can implement:

```text
Logout current device
Logout all devices
Revoke one session
Revoke all sessions
Show active sessions
```

This becomes much more powerful than one `refreshTokenHash` field on the user.


# 39. Common mistakes

### ❌ Store raw refresh tokens

```text
refreshToken
```

### ❌ Never rotate tokens

```text
RT1
 ↓
RT1
 ↓
RT1
```

### ❌ Ignore reuse

```text
Old RT
 ↓
Just reject
```

without considering whether the event indicates compromise.

### ❌ Log tokens

```text
console.log(token)
```

### ❌ Put tokens in URLs

```text
?token=...
```

### ❌ Assume HttpOnly solves everything

It doesn't.

### ❌ Assume JWT means "no server state"

Refresh sessions often need server-side state for revocation and security controls.
