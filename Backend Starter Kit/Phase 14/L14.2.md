# Lesson 14.2 — Authentication vs Authorization

This is one of the **most important distinctions in backend development**.

If you understand this clearly, later concepts like:

```text
JWT
Middleware
RBAC
Roles
Permissions
Ownership
403
401
```

will become much easier.

---

# 1. The simplest definition

Remember these two questions:

```text
Authentication
    ↓
WHO are you?
```

```text
Authorization
    ↓
WHAT are you allowed to do?
```

That's the entire difference.

A useful shortcut:

> **AuthN = Authentication → Identity**

> **AuthZ = Authorization → Permission**

---

# 2. Real-world example

Imagine you're entering your college.

At the entrance, a security guard asks:

```text
"Show me your college ID."
```

You show your ID.

The guard checks:

```text
Is this ID valid?
```

If yes:

```text
Authentication successful
```

The guard now knows:

```text
You are Rahul.
```

But that doesn't mean you can enter every room.

Suppose you try to enter:

```text
Principal's office
```

The guard checks:

```text
Is Rahul allowed to enter this room?
```

That's:

```text
Authorization
```

So:

```text
ID verification
     ↓
Authentication
     ↓
"Who are you?"
```

Then:

```text
Permission check
     ↓
Authorization
     ↓
"What can you access?"
```

---

# 3. Web application example

Suppose our application has:

```text
User
Admin
```

Rahul logs in:

```http
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "password123"
}
```

The backend verifies the credentials.

It determines:

```text
User ID: 123
Role: user
```

This is **authentication**.

The server has established:

```text
"I know who this person is."
```

---

# 4. Now Rahul wants to delete another user

Suppose we have:

```http
DELETE /api/v1/users/456
```

Rahul is already authenticated.

So:

```text
Authentication
        ↓
SUCCESS
```

But Rahul has:

```text
role = user
```

and deleting users requires:

```text
role = admin
```

Therefore:

```text
Authorization
        ↓
FAIL
```

The server responds:

```http
403 Forbidden
```

So this is a very important situation:

> A user can be **authenticated but not authorized**.

---

# 5. The complete flow

Think about a protected request:

```text
Client
  │
  │ Request
  ▼
Authentication
  │
  ├── ❌ Failed
  │      ↓
  │     401
  │
  └── ✅ Successful
          │
          ▼
      Authorization
          │
          ├── ❌ Failed
          │      ↓
          │     403
          │
          └── ✅ Successful
                  │
                  ▼
              Controller
```

This is the basic architecture we'll eventually implement.

# 6. Example: Todo application

Suppose:

```text
Rahul
 ├── Todo A
 └── Todo B

Amit
 ├── Todo C
 └── Todo D
```

Rahul makes:

```http
GET /api/v1/todos/A
```

First:

```text
Authentication
```

The server asks:

> Who is requesting this?

Answer:

```text
Rahul
```

Authentication succeeds.

Then authorization asks:

> Is Rahul allowed to access Todo A?

Suppose Todo A belongs to Rahul.

```text
Authorization
      ↓
YES
```

Request continues.

---

# 7. Now suppose Rahul requests Todo C

```http
GET /api/v1/todos/C
```

Authentication:

```text
Who is requesting?
        ↓
Rahul
        ↓
Authenticated ✅
```

Authorization:

```text
Does Rahul own Todo C?
        ↓
No ❌
```

Therefore:

```text
403 Forbidden
```

This is called an **ownership check**.

We'll study this deeply in Phase 15.

---

# 8. Authentication doesn't automatically give permission

This is a common beginner mistake.

You might think:

```text
User logged in
     ↓
User can access everything
```

No.

Correct:

```text
User logged in
     ↓
Identity established
     ↓
Check permissions
     ↓
Allow specific operation
```

For example:

```text
Authenticated user
       │
       ├── GET own profile       ✅
       ├── UPDATE own profile    ✅
       ├── GET own todos         ✅
       ├── DELETE another user   ❌
       └── Create admin          ❌
```

Authentication only establishes identity.

---

# 9. Authentication happens before authorization

Usually:

```text
Authentication
      ↓
Authorization
```

Why?

Because you can't properly ask:

> "Is this person allowed to do X?"

until you know:

> "Who is this person?"

For example:

```text
Request
   ↓
Who are you?
   ↓
Rahul
   ↓
What is Rahul allowed to do?
   ↓
User permissions
```

---

# 10. Where does authentication happen?

In our backend architecture, authentication will primarily happen in:

```text
middlewares/auth.middleware.js
```

Conceptually:

```js
const authMiddleware = (req, res, next) => {
    // verify authentication credential

    req.user = authenticatedUser;

    next();
};
```

So:

```text
Request
   ↓
authMiddleware
   ↓
req.user
   ↓
Controller
```

The controller can now work with the authenticated identity.

---

# 11. Where does authorization happen?

Authorization can happen in several places depending on the type of rule.

For simple role-based authorization, we might have:

```text
middlewares/role.middleware.js
```

For example:

```js
requireRole("admin")
```

Conceptually:

```text
Request
   ↓
Authentication
   ↓
req.user
   ↓
Role check
   ↓
Controller
```

Example:

```text
DELETE /users/:id
        ↓
authMiddleware
        ↓
requireRole("admin")
        ↓
controller
```

---

# 12. Authentication middleware

Imagine:

```text
GET /api/v1/users/me
```

The route might eventually look like:

```js
router.get(
    "/me",
    authMiddleware,
    userController.getMe
);
```

Flow:

```text
GET /me
  ↓
authMiddleware
  ↓
Is authentication valid?
  │
  ├── NO → 401
  │
  └── YES
        ↓
    req.user
        ↓
    getMe()
```

---

# 13. Authorization middleware

Now imagine:

```text
DELETE /api/v1/users/:id
```

Only admins can perform this operation.

Conceptually:

```js
router.delete(
    "/:id",
    authMiddleware,
    requireRole("admin"),
    userController.deleteUser
);
```

Flow:

```text
DELETE /users/123
        ↓
authMiddleware
        ↓
Who are you?
        ↓
Rahul
        ↓
requireRole("admin")
        ↓
Is Rahul an admin?
        │
        ├── NO → 403
        │
        └── YES
              ↓
          Controller
```

Notice how clean this is.

Each middleware has one job.

---

# 14. 401 vs 403

This is a very useful distinction for interviews and real development.

## `401 Unauthorized`

Think:

> **Authentication failed or is missing.**

Examples:

```text
No access token
Invalid token
Expired token
Invalid credentials
```

Flow:

```text
Request
  ↓
Authentication
  ↓
❌
  ↓
401
```

---

## `403 Forbidden`

Think:

> **Authentication succeeded, but access is not allowed.**

Examples:

```text
Normal user accessing admin endpoint
User accessing another user's resource
Insufficient permissions
```

Flow:

```text
Request
  ↓
Authentication
  ↓
✅ Rahul
  ↓
Authorization
  ↓
❌ Not allowed
  ↓
403
```

---

# 15. Very important example

Consider:

```http
DELETE /api/v1/users/123
```

### Case 1 — No token

```text
No authentication
        ↓
401
```

### Case 2 — Invalid token

```text
Token invalid
        ↓
401
```

### Case 3 — Valid token, normal user

```text
Authentication
      ↓
Rahul
      ↓
Authorization
      ↓
Not admin
      ↓
403
```

### Case 4 — Valid admin

```text
Authentication
      ↓
Admin
      ↓
Authorization
      ↓
Allowed
      ↓
Controller
```

This distinction should become automatic in your mind.

# 17. Three types of authorization we'll learn

Authorization is bigger than just roles.

We'll eventually study three important patterns.

### 1. Role-based

```text
role = admin
```

Example:

```text
Admin → delete users
User  → cannot delete users
```

---

### 2. Permission-based

Instead of:

```text
role = admin
```

we might have:

```text
permissions:
[
    "user:read",
    "user:create",
    "user:delete"
]
```

Then:

```text
requirePermission("user:delete")
```

---

### 3. Resource ownership

Example:

```text
Todo belongs to Rahul
```

Rahul:

```text
GET Todo A → ✅
UPDATE Todo A → ✅
DELETE Todo A → ✅
```

Amit:

```text
GET Todo A → ❌
UPDATE Todo A → ❌
DELETE Todo A → ❌
```

This is extremely important for APIs.

---

# 18. Why ownership is especially important

Suppose we have:

```http
GET /api/v1/todos/123
```

The developer writes:

```js
Todo.findById(req.params.id);
```

This only checks:

```text
Does Todo 123 exist?
```

It doesn't check:

```text
Does this Todo belong to the authenticated user?
```

A safer query is conceptually:

```js
Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

Now the database query itself enforces ownership.

We'll explore this carefully in Phase 15.

---

# 19. Authentication + Authorization are complementary

Think of them like two doors.

```text
Door 1
Authentication
     ↓
"Identify yourself."
```

Then:

```text
Door 2
Authorization
     ↓
"Are you allowed inside?"
```

Both are needed.

A secure API doesn't say:

```text
"You're logged in, so you can do anything."
```

Instead:

```text
Who are you?
    ↓
What are you allowed to access?
    ↓
What operation are you allowed to perform?
```

# 20. React + Express example

Imagine your React frontend has:

```text
Dashboard
Admin Panel
User Profile
```

Rahul logs in.

The backend authenticates him:

```text
User ID: 123
Role: user
```

React can show:

```text
Dashboard
Profile
Todos
```

But the important security rule is:

> **Hiding the Admin button in React is not authorization.**

For example, this is only UI behavior:

```jsx
{user.role === "admin" && (
    <button>Delete User</button>
)}
```

A malicious user can still manually call:

```http
DELETE /api/v1/users/456
```

Therefore the backend must enforce authorization.

```text
Frontend authorization
        ↓
UX convenience

Backend authorization
        ↓
Actual security boundary
```

This is a very important professional habit.

---

# 21. The golden rule

Remember this:

> **Never rely on the frontend for authorization.**

The frontend can decide:

```text
"Should I show this button?"
```

The backend must decide:

```text
"Is this operation actually allowed?"
```

So:

```text
React
 ↓
UX
```

while:

```text
Express backend
 ↓
Security enforcement
```

# 22. A complete example

Suppose Rahul wants to delete Todo `100`.

Request:

```http
DELETE /api/v1/todos/100
```

### Step 1 — Authentication

```text
Access credential
       ↓
Verify
       ↓
User = Rahul
```

Now:

```js
req.user = {
    id: "rahul-id",
    role: "user"
};
```

### Step 2 — Authorization

Service/repository checks:

```text
Todo 100
     ↓
owner = Rahul?
```

If yes:

```text
Authorization successful
```

If no:

```text
403 Forbidden
```

### Step 3 — Business operation

Only after authorization:

```text
Delete Todo
```

The complete flow:

```text
DELETE /todos/100
       ↓
Authentication
       ↓
req.user = Rahul
       ↓
Authorization
       ↓
Does Rahul own Todo 100?
       ↓
YES
       ↓
Controller
       ↓
Service
       ↓
Repository
       ↓
MongoDB
```

# 23. Common beginner mistakes

### Mistake 1

Thinking:

```text
Login = Authentication
```

Not exactly.

Login is one authentication operation.

---

### Mistake 2

Thinking:

```text
JWT = Authentication
```

No.

JWT is a token format/technology that can be used as part of an authentication system.

---

### Mistake 3

Thinking:

```text
Logged in = can access everything
```

Wrong.

Authentication doesn't grant unlimited permissions.

---

### Mistake 4

Only protecting the frontend:

```jsx
if (user.role === "admin") {
    showAdminPanel();
}
```

That's not sufficient security.

---

### Mistake 5

Checking only the resource ID:

```js
Todo.findById(todoId);
```

without checking ownership.

---

### Mistake 6

Returning `403` when the user isn't authenticated.

Generally:

```text
Not authenticated → 401
Authenticated but not allowed → 403
```
