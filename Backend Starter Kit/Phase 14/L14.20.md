# Lesson 14.20 — Password Reset

Your actual Phase 14 roadmap has **14.20 = Password reset**, followed by **14.21 = Email verification** and **14.22 = Authentication architecture**.

This is an important authentication feature because password reset is essentially a **temporary authentication mechanism**.

The user has forgotten their password, so we need a secure way to prove:

> "This person has access to the email/account recovery channel, so allow them to choose a new password."

---

# 1. The password-reset problem

Imagine:

```text
User
 ↓
"I forgot my password."
```

They can't log in:

```text
email + password
       ↓
    ❌ password unknown
```

So we need another flow:

```text
Forgot password
      ↓
Enter email
      ↓
Receive reset email
      ↓
Open reset link
      ↓
Choose new password
      ↓
Password changed
      ↓
Login again
```

---

# 2. The complete architecture

Think of password reset as two separate operations:

```text
        FORGOT PASSWORD
              │
              ▼
       Generate reset token
              │
              ▼
       Store token securely
              │
              ▼
         Send email
              │
              ▼
       User opens link
              │
              ▼
        RESET PASSWORD
              │
              ▼
       Verify reset token
              │
              ▼
       Hash new password
              │
              ▼
       Save new password
              │
              ▼
       Invalidate reset token
```

This separation is very important.

---

# 3. Never send a password

A common beginner mistake is thinking:

```text
Forgot password
 ↓
Send old password by email
```

Never do this.

Passwords should be stored as hashes:

```text
password
   ↓
bcrypt
   ↓
passwordHash
```

You cannot safely "recover" the original password.

Instead:

```text
Forgot password
 ↓
Create temporary reset credential
 ↓
User proves possession
 ↓
Choose NEW password
```

---

# 4. Two endpoints

A clean API might have:

```http
POST /api/v1/auth/forgot-password
```

and:

```http
POST /api/v1/auth/reset-password
```

The first starts the process.

The second completes it.

---

# 5. Forgot-password request

The user sends:

```json
{
  "email": "rahul@example.com"
}
```

Request flow:

```text
POST /forgot-password
        ↓
Validation
        ↓
Find user
        ↓
Generate reset token
        ↓
Store token securely
        ↓
Send reset email
        ↓
Return response
```

---

# 6. Don't reveal whether the email exists

This is a very important security concept.

Suppose the attacker tries:

```text
POST /forgot-password

{
  "email": "admin@example.com"
}
```

If your API says:

```json
{
  "message": "User exists"
}
```

the attacker can discover valid accounts.

They can then test:

```text
admin@example.com
user1@example.com
ceo@example.com
...
```

This is called **account enumeration**.

---

# 7. Use a generic response

A safer response is something like:

```json
{
  "success": true,
  "message": "If an account exists, a password reset link has been sent."
}
```

Notice:

The response doesn't tell the attacker whether the account exists.

Conceptually:

```text
Existing email
      ↓
Send email
      ↓
Generic response

Unknown email
      ↓
Don't send email
      ↓
Same generic response
```

This keeps the external behavior similar.

---

# 8. Generate a random reset token

Don't use something predictable like:

```text
123456
```

or:

```text
userId + timestamp
```

or:

```text
Math.random()
```

Use a cryptographically secure random value.

Conceptually:

```text
Secure Random Generator
        ↓
Reset Token
```

For example:

```text
RANDOM_LONG_SECRET
```

The actual token should have enough entropy to make guessing impractical.

---

# 9. Reset token vs JWT

This is an important design decision.

You might think:

> "We're using JWT everywhere, so why not make the password reset token a JWT?"

You can, but a random opaque reset token stored server-side is often simpler for password reset.

Think:

```text
Access token
 → JWT
 → API authentication
```

while:

```text
Password reset token
 → random secret
 → one-time recovery credential
```

They solve different problems.

---

# 10. Store the reset token securely

Your starter roadmap's user model includes fields such as:

```text
resetTokenHash
resetTokenExpires
```

The important pattern is:

```text
Raw reset token
      ↓
Hash
      ↓
Database
```

Not:

```text
Raw reset token
      ↓
Database
```

---

# 11. Why hash the reset token?

Suppose:

```text
Reset Token:

RANDOM_SECRET_ABC
```

The database stores:

```text
resetTokenHash:

HASH_VALUE
```

If your database is leaked, the attacker shouldn't immediately have a usable password-reset credential.

This is the same security principle we've already seen with refresh tokens.

```text
Password
    ↓
Hash

Refresh token
    ↓
Hash

Reset token
    ↓
Hash
```

---

# 12. Token lifecycle

Let's visualize it:

```text
Generate
   ↓
RT_RAW
   ↓
Hash
   ↓
Store HASH
   ↓
Send RAW token to user
```

The user receives:

```text
https://example.com/reset-password?token=RT_RAW
```

The server stores only:

```text
HASH(RT_RAW)
```

When the user submits the token:

```text
RT_RAW
  ↓
Hash
  ↓
Compare with stored hash
```

If they match:

```text
✅ valid
```

---

# 13. Never log the reset token

Don't do:

```js
console.log("Reset token:", resetToken);
```

That's dangerous.

Your logs might later be accessed by:

```text
developers
servers
log aggregation systems
monitoring tools
third-party services
```

Instead log something like:

```text
PASSWORD_RESET_REQUESTED
userId
requestId
timestamp
```

without the credential itself.

---

# 14. Token expiration

Reset tokens must be temporary.

For example:

```text
Reset token
   ↓
valid for limited period
   ↓
expires
```

Your database can store:

```text
resetTokenExpires
```

Conceptually:

```text
Now < expiresAt
    ↓
valid

Now >= expiresAt
    ↓
invalid
```

---

# 15. Why expiration matters

Imagine a reset link never expires:

```text
2026
 ↓
Reset link created

2030
 ↓
Still works
```

That's dangerous.

If someone obtains an old reset link years later, they could potentially use it.

Temporary credentials should have limited lifetimes.

---

# 16. The reset email

The email might contain:

```text
You requested a password reset.

Click here to choose a new password:

https://frontend.example.com/reset-password?token=...
```

Notice something important:

The frontend receives the **raw token** through the link.

The backend stores only:

```text
hash(token)
```

---

# 17. Why send the token to the frontend?

Your architecture might be:

```text
Email
 ↓
Frontend reset page
 ↓
POST /auth/reset-password
 ↓
Backend
```

The frontend doesn't need to know the user's existing password.

It only needs:

```text
resetToken
newPassword
```

---

# 18. Reset-password request

The frontend might send:

```json
{
  "token": "RANDOM_SECRET",
  "password": "NewStrongPassword123!"
}
```

Backend:

```text
token
  ↓
hash token
  ↓
find matching user
  ↓
check expiration
  ↓
validate new password
  ↓
hash new password
  ↓
save password
```

---

# 19. The critical comparison

Suppose database contains:

```text
resetTokenHash = H1
```

User sends:

```text
resetToken = RT1
```

Backend calculates:

```text
hash(RT1) = H1
```

Then:

```text
H1 === stored H1
```

Therefore:

```text
Token valid
```

If:

```text
hash(RT1) !== stored H1
```

then:

```text
Invalid reset token
```

---

# 20. Password validation still applies

Don't bypass normal password validation just because this is a reset flow.

You still need:

```text
new password
      ↓
validation
      ↓
strong enough?
```

For example:

```text
minimum length
allowed characters
password policy
```

The exact policy should match your authentication architecture.

---

# 21. Hash the new password

Once the reset token is valid:

```text
New password
     ↓
bcrypt
     ↓
passwordHash
     ↓
MongoDB
```

Never:

```text
new password
     ↓
MongoDB
```

---

# 22. What happens to the reset token afterward?

This is extremely important.

After successful password reset:

```text
resetTokenHash = null
resetTokenExpires = null
```

Conceptually:

```text
Before:

resetTokenHash = H1
resetTokenExpires = future


After:

resetTokenHash = null
resetTokenExpires = null
```

Why?

Because the reset token should be **one-time use**.

---

# 23. Prevent reset-token reuse

Imagine:

```text
Reset Token RT1
       ↓
Password changed
```

An attacker tries:

```text
RT1
 ↓
reset password again
```

The server should reject it.

Why?

Because:

```text
RT1
 ↓
already consumed
```

So:

> **A successful password reset should invalidate the reset credential.**

# 26. Password reset service

Conceptually:

```js
async function forgotPassword(email) {
    const user = await userRepository.findByEmail(email);

    if (!user) {
        return;
    }

    const resetToken = generateSecureToken();

    const resetTokenHash = hash(resetToken);

    await userRepository.setResetToken(
        user.id,
        resetTokenHash,
        expiresAt
    );

    await mailService.sendPasswordResetEmail(
        user.email,
        resetToken
    );
}
```

Notice:

The service doesn't do:

```text
res.json()
res.status()
```

That's the controller's job.

---

# 27. Reset service

Conceptually:

```js
async function resetPassword(token, newPassword) {
    const tokenHash = hash(token);

    const user = await userRepository.findByResetToken(
        tokenHash
    );

    if (!user) {
        throw invalidResetTokenError();
    }

    if (user.resetTokenExpires < new Date()) {
        throw expiredResetTokenError();
    }

    const passwordHash = await bcrypt.hash(
        newPassword,
        12
    );

    await userRepository.updatePasswordAndClearResetToken(
        user.id,
        passwordHash
    );
}
```

This is simplified architecture, not something you should blindly paste into your starter.

---

# 28. Atomicity matters

Notice this operation:

```text
Update password
+
Invalidate reset token
```

should ideally happen as one controlled database operation/transaction where appropriate.

You don't want:

```text
Password updated
 ↓
Application crashes
 ↓
Reset token remains valid
```

That could create an unwanted security state.

A good design ensures the successful reset leaves the account in a consistent state.

---

# 29. Should we log the user out after password reset?

This depends on your session architecture.

But from a security perspective, password reset is a strong signal that existing authentication sessions may need attention.

A mature approach can:

```text
Password reset
      ↓
Invalidate existing refresh sessions
      ↓
Require login again
```

This is particularly useful if the reset happened because the user forgot their password or suspects compromise.

---

# 30. Why invalidate existing sessions?

Imagine an attacker already has:

```text
Refresh Token
```

The legitimate user resets their password.

If you only change:

```text
passwordHash
```

the stolen refresh token might remain valid.

That would be bad.

A stronger flow is:

```text
Password Reset
      ↓
Change password
      ↓
Revoke existing refresh sessions
      ↓
Require fresh login
```

Now the old authentication sessions are shut down.

This connects today's lesson directly to **14.19 Token Theft**.

---

# 31. Password reset is not login

A reset token proves something different.

Login:

```text
email + password
```

Password reset:

```text
reset credential
+
new password
```

Don't mix the two mechanisms.

The reset token should be:

```text
temporary
single-use
random
securely stored
```

---

# 32. Rate limiting password reset

This endpoint is sensitive:

```http
POST /forgot-password
```

An attacker could spam it:

```text
1,000 requests
10,000 requests
100,000 requests
```

Possible consequences:

```text
email spam
resource exhaustion
user annoyance
email-provider costs
account enumeration attempts
```

Therefore password-reset requests should have appropriate rate limits.

---

# 33. Rate-limit by more than one dimension

Depending on your architecture, consider:

```text
IP-based limit
+
email/account-based limit
```

Why?

If you only limit IP:

```text
Attacker changes IP
 ↓
continues attacking
```

If you only limit email:

```text
Attacker targets thousands of emails
```

Layered rate limiting is stronger.

---

# 34. Don't make rate limiting reveal account existence

Be careful with:

```text
Existing account
 → "Reset email sent"

Nonexistent account
 → "No account found"
```

This leaks information.

Similarly, differences in response timing can sometimes reveal whether an account exists.

Aim for a consistent external response.

---

# 35. Reset-token errors

Don't expose unnecessary details.

Avoid:

```json
{
  "error": "No user with resetTokenHash abc123 exists"
}
```

Instead:

```json
{
  "success": false,
  "message": "Invalid or expired reset link"
}
```

The attacker doesn't need your database structure.

---

# 36. What if the token is expired?

Example:

```text
Reset token
created: 10:00

expires: 11:00

user clicks: 12:30
```

Result:

```text
❌ Invalid or expired reset link
```

The user can simply request another reset.

---

# 37. What if the user requests two resets?

Suppose:

```text
Request 1
 ↓
RT1

Request 2
 ↓
RT2
```

You need a clear policy.

A simple design can make the latest reset token replace the previous one:

```text
RT1 → invalid
RT2 → valid
```

This prevents multiple active reset credentials for the same account.

# 39. Password reset and email security

Your reset link itself is sensitive.

So think carefully about:

```text
HTTPS
```

and:

```text
frontend URL
```

Avoid sending credentials through insecure channels.

Also avoid putting sensitive information besides the necessary reset credential into the URL.

# 40. Common mistake #1 — predictable token

Bad:

```js
const token = `${user.id}-${Date.now()}`;
```

An attacker may be able to predict or narrow the search space.

Use a cryptographically secure random generator instead.

---

# 41. Common mistake #2 — storing raw token

Bad:

```text
resetToken = "abc123"
```

in MongoDB.

Better:

```text
resetTokenHash = hash("abc123")
```

---

# 42. Common mistake #3 — no expiration

Bad:

```text
reset token
 ↓
valid forever
```

Better:

```text
reset token
 ↓
short validity window
```

---

# 43. Common mistake #4 — reusable reset token

Bad:

```text
RT1
 ↓
password reset
 ↓
RT1
 ↓
another password reset
```

Better:

```text
RT1
 ↓
password reset
 ↓
RT1 invalid
```

---

# 44. Common mistake #5 — not revoking sessions

Suppose:

```text
Attacker
 ↓
stolen refresh token
```

User resets password:

```text
password changed
```

but:

```text
refresh token
 ↓
still valid
```

That's a dangerous design.

Password reset should be considered when designing session revocation.

---

# 45. Common mistake #6 — revealing account existence

Bad:

```text
"Email does not exist."
```

Better:

```text
"If an account exists, we sent a reset link."
```

---

# 46. Common mistake #7 — logging reset credentials

Bad:

```js
logger.info({
    email,
    resetToken
});
```

Better:

```js
logger.info({
    event: "PASSWORD_RESET_REQUESTED",
    userId,
    requestId
});
```
