# Lesson 14.21 — Email Verification

According to your roadmap, **14.21 is Email Verification**, immediately after Password Reset and before the complete Authentication Architecture.

The goal is to understand how a backend verifies that:

> **The user actually has access to the email address they registered with.**

---

# 1. Why do we need email verification?

Imagine someone creates an account:

```text
POST /auth/signup

email:
rahul@example.com

password:
********
```

The account is created.

But how do we know:

```text
rahul@example.com
```

actually belongs to that person?

We don't.

The user could have typed:

```text
someone-else@example.com
```

or:

```text
fake@example.com
```

Email verification adds another proof.

```text
Signup
   ↓
Account created
   ↓
Verification email
   ↓
User clicks link
   ↓
Email verified
```

---

# 2. Authentication vs email verification

Don't confuse these.

### Authentication

Answers:

> Who are you?

For example:

```text
email + password
       ↓
login
```

### Email verification

Answers:

> Do you control this email address?

For example:

```text
verification link
       ↓
email account
       ↓
user clicks
```

So:

```text
Authentication
    +
Email Verification
```

are two different concepts.

---

# 3. The complete flow

Think of the system like this:

```text
                SIGNUP
                  │
                  ▼
             Create User
                  │
                  ▼
        emailVerified = false
                  │
                  ▼
       Generate verification token
                  │
                  ▼
          Hash verification token
                  │
                  ▼
             Store hash
                  │
                  ▼
          Send verification email
                  │
                  ▼
                USER
                  │
                  ▼
          Click verification link
                  │
                  ▼
       POST /auth/verify-email
                  │
                  ▼
         Hash supplied token
                  │
                  ▼
       Find matching verification hash
                  │
                  ▼
             Check expiry
                  │
                  ▼
        emailVerified = true
                  │
                  ▼
        Invalidate verification token
```

That's the core architecture.

---

# 4. User model

Your starter-pack roadmap already includes authentication-related user state such as token fields, and the verification flow naturally needs corresponding email-verification state.

Conceptually, your user might contain:

```js
{
    email: "rahul@example.com",

    passwordHash: "...",

    emailVerified: false,

    verificationTokenHash: "...",

    verificationTokenExpires: "..."
}
```

The important field is:

```text
emailVerified
```

Initially:

```text
false
```

After successful verification:

```text
true
```

---

# 5. Why not just store `emailVerified`?

Because:

```text
emailVerified: false
```

doesn't tell us **how to verify it**.

We need a temporary credential.

So we have:

```text
emailVerified
        +
verification token
```

The token proves that the person received the verification email.

---

# 6. Generate a random verification token

Just like password reset, don't create predictable tokens.

Bad:

```js
const token = `${userId}-${Date.now()}`;
```

Also don't use:

```js
Math.random();
```

Instead:

```text
Cryptographically secure random generator
                 ↓
         Verification Token
```

Conceptually:

```text
VERIFY_TOKEN_ABC123...
```

The real token should have enough randomness that guessing it is impractical.

---

# 7. Don't store the raw token

Suppose the generated token is:

```text
VT1
```

Don't store:

```text
verificationToken = VT1
```

Instead:

```text
VT1
 ↓
hash()
 ↓
H1
```

Store:

```text
verificationTokenHash = H1
```

This is the same principle you learned in:

- refresh-token hashing
    
- password reset
    

---

# 8. Send the raw token

There's an important difference.

The user needs:

```text
VT1
```

The database stores:

```text
H1
```

So:

```text
              VT1
             /   \
            /     \
           ▼       ▼
       Email      hash()
                    │
                    ▼
                   H1
                    │
                    ▼
                 Database
```

The email contains the usable credential.

The database does not.

# 11. Backend verification flow

The backend receives:

```text
VT1
```

Then:

```text
VT1
 ↓
hash()
 ↓
H1
```

Database:

```text
verificationTokenHash = H1
```

Comparison:

```text
H1 === stored H1
```

If yes:

```text
Token is valid
```

---

# 12. Check expiration

Verification tokens should not live forever.

You can have:

```text
verificationTokenExpires
```

Then:

```text
currentTime < expiresAt
```

means:

```text
✅ valid
```

while:

```text
currentTime >= expiresAt
```

means:

```text
❌ expired
```

---

# 13. Why expiration matters

Imagine:

```text
2026
 ↓
Verification email sent
```

and the link works forever:

```text
2030
 ↓
Old verification link
 ↓
Still valid
```

That's unnecessary security exposure.

Temporary credentials should have a limited lifetime.

---

# 14. Successful verification

Suppose:

```text
emailVerified = false
```

and the token is valid.

The service performs:

```text
emailVerified = true
```

Then:

```text
verificationTokenHash = null
verificationTokenExpires = null
```

So the final state becomes:

```js
{
    emailVerified: true,

    verificationTokenHash: null,

    verificationTokenExpires: null
}
```

---

# 15. Why clear the token?

Because the verification token should be **single-use**.

Before:

```text
VT1 → valid
```

User verifies:

```text
VT1
 ↓
emailVerified = true
```

After:

```text
VT1 → invalid
```

If someone tries to reuse the same token:

```text
VT1
 ↓
verify
```

the backend rejects it.

# 17. Should unverified users be allowed to log in?

This is a **business-rule decision**.

You could allow:

```text
Signup
 ↓
Login
 ↓
Limited access
 ↓
Verify email
```

Or require:

```text
Signup
 ↓
Verify email
 ↓
Login
```

For some applications, unverified users can access basic features but cannot perform sensitive actions.

For example:

```text
Unverified
    ↓
Can browse

Verified
    ↓
Can create content
    ↓
Can perform sensitive operations
```

The important lesson is:

> **Email verification is not automatically authorization.**

Your application decides what verified status allows.

```text

```

# 19. Email verification middleware?

You could eventually create something like:


```text

   ↓
```

# 20. Don't put verification logic in the controller

Avoid a giant controller:

```js
async function verifyEmail(req, res) {
    // find user
    // hash token
    // check expiry
    // update database
    // clear token
    // send email
    // etc.
}
```

Instead:

```text
Controller
    ↓
authService.verifyEmail()
    ↓
Repository
```

Your roadmap deliberately separates controllers, services, and repositories.

---

# 21. Controller responsibility

The controller should mostly deal with HTTP:

```text
Request
 ↓
Read token
 ↓
Call service
 ↓
Return response
```

Conceptually:

```js
async function verifyEmail(req, res) {
    await authService.verifyEmail(req.body.token);

    return res.status(200).json({
        success: true,
        message: "Email verified successfully"
    });
}
```

The actual security logic belongs in the service.

# 23. Repository responsibility

# 26. What if email sending fails?

This is an important production problem.

Suppose:

```text
User created
      ↓
Database success
      ↓
Email sending fails
```

Now:

```text
User exists
emailVerified = false
```

That's okay if your architecture allows the user to request another verification email.

You don't necessarily want to delete the user just because SMTP failed.

Instead:

```text
Signup succeeds
      ↓
Verification email fails
      ↓
User can request resend
```

# 27. Resend verification email

You'll usually want another endpoint:

```http
POST /api/v1/auth/resend-verification
```

Flow:

```text
User
 ↓
"Resend verification"
 ↓
Backend
 ↓
Generate new token
 ↓
Invalidate old token
 ↓
Store new hash
 ↓
Send new email
```

---

# 28. Why invalidate the old token?

Suppose:

```text
Request 1 → VT1
Request 2 → VT2
```

If both remain valid:

```text
VT1 → valid
VT2 → valid
```

you have multiple active verification credentials.

A simpler security model is:

```text
VT1 → invalid
VT2 → valid
```

So the latest verification request wins.

---

# 29. Rate-limit resend

Imagine someone repeatedly clicks:

```text
Resend
Resend
Resend
Resend
Resend
...
```

You could accidentally send hundreds of emails.

So:

```text
resend-verification
        ↓
rate limiter
        ↓
service
```

is important.

You can rate-limit by:

```text
IP
+
account/email
```

depending on your architecture.

# 30. Don't reveal account existence

Just like password reset, be careful with:

```http
POST /resend-verification
```

Don't necessarily respond:

```text
"This email does not belong to an account."
```

because attackers can use this to enumerate accounts.

A safer external response can be generic.

For example:

```json
{
    "success": true,
    "message": "If verification is required, a new email has been sent."
}
```

Your exact wording can vary.

Example:


# 37. What if the user is already verified?

Suppose:

```text
emailVerified = true
```

and they submit another verification token.

You can simply treat the account as already verified or return an appropriate response.

The important thing is that verification should be **idempotent in behavior where practical**:

```text
Already verified
    ↓
Don't accidentally break the account
```

# 38. Verification link security

The verification link is a credential.

Therefore:

```text
HTTPS
```

is essential.

You should also avoid putting unnecessary sensitive data into the link.

Keep it focused:

```text
/reset-password?token=...
```

or:

```text
/verify-email?token=...
```

rather than adding unnecessary account information.

```text

```

```text
 ↓
```

# 40. Don't trust frontend state

Bad security design:

```js
if (localStorage.getItem("emailVerified")) {
    // allow sensitive operation
}
```

An attacker controls the browser.

They can change:

```text
localStorage
```

or:

```text
request payload
```

The backend must check the actual user state.

```text
Client says:
emailVerified = true

Backend:
Let's check MongoDB.
```

This is another example of:

> **Never trust client-controlled security state.**

# 41. Email verification and JWT claims

Suppose your access token contains:

```json
{
    "sub": "user123",
    "emailVerified": false
}
```

Later the user verifies their email.

The old JWT still contains:

```text
emailVerified: false
```

until it expires.

This creates an important architectural consideration.

One solution is:

```text
JWT
 ↓
user ID
 ↓
fetch current user state
```

for operations where current verification status matters.

Or you can design your token/session strategy around short-lived access tokens and appropriate claims.

The important lesson:

> **JWT claims are snapshots, not automatically live database state.**


# 43. Email verification and session management

Suppose a user signs up:

```text
emailVerified = false
```

Then verifies:

```text
emailVerified = true
```

If your access token was created before verification, it might not reflect the new state.

A clean architecture could simply issue a fresh authentication state after verification.

For example:

```text
Verify email
     ↓
Success
     ↓
Login / refresh authentication
```

The exact behavior depends on your authentication UX.

# 55. The reusable pattern

This is perhaps the most valuable thing to take from today's lesson.

You have now seen three temporary credentials:

```text
Refresh Token
Password Reset Token
Email Verification Token
```

They have different purposes, but many security principles are the same:

```text
                 TEMPORARY CREDENTIAL
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
           Random      Hashed    Expiring
              │          │          │
              └──────────┼──────────┘
                         ▼
                     Single-use
                         │
                         ▼
                    Rate-limited
```

Once you understand this pattern, many authentication systems become much easier to reason about.
