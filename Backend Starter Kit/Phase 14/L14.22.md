# 9. Access token vs refresh token

This distinction should now be automatic in your mind.

### Access token

```text
Short-lived
 ↓
Used to access APIs
```

### Refresh token

```text
Long-lived
 ↓
Used to obtain new access token
```

Your roadmap specifically describes the recommended split as:

```text
Login
  │
  ├── Access Token
  │       ↓
  │   Authorization header
  │
  └── Refresh Token
          ↓
      HttpOnly cookie
```

---

# 10. Why two tokens?

Suppose access tokens lived for:

```text
30 days
```

If stolen:

```text
Attacker
 ↓
stolen access token
 ↓
30 days of access
```

That's undesirable.

Instead:

```text
Access token
 ↓
short lifetime
```

and:

```text
Refresh token
 ↓
longer lifetime
 ↓
protected carefully
```

Now stolen access credentials have a smaller blast radius.

---

# 11. Where should the tokens live?

A common architecture is:

```text
Access token
 ↓
Authorization header

Refresh token
 ↓
HttpOnly Secure cookie
```

So requests might look conceptually like:

```http
Authorization: Bearer ACCESS_TOKEN
```

while the browser automatically sends:

```text
refresh_token cookie
```

The refresh token isn't directly readable by ordinary JavaScript when the cookie is `HttpOnly`.

---

# 12. Why protect the refresh token more?

Because the refresh token has a different power.

An access token:

```text
API access
```

A refresh token:

```text
Can potentially create new access tokens
```

Therefore:

```text
Refresh token
     ↓
Higher-value credential
     ↓
Stronger protection
```

# 13. Refresh-token hashing

This was one of the most important concepts in your earlier lessons.

Suppose:

```text
RT1 = refresh token
```

Don't store:

```text
refreshToken = RT1
```

Store:

```text
hash(RT1)
```

So:

```text
Raw refresh token
       │
       ▼
      hash
       │
       ▼
MongoDB
```

Your roadmap explicitly highlights this architecture.

---

# 14. Why hash a JWT?

This question often confuses beginners.

A JWT can be:

```text
cryptographically signed
```

but that doesn't mean:

```text
safe to store as plaintext
```

If someone gets database access and you stored:

```text
refreshToken = actual-token
```

they may be able to use it.

Hashing changes the database into:

```text
refreshTokenHash
```

So:

```text
Database leak
 ↓
attacker gets hash
 ↓
doesn't immediately get usable refresh credential
```


# 16. Refresh-token rotation

Suppose:

```text
RT1
```

is currently valid.

User refreshes:

```text
RT1
 ↓
RT2
```

Then:

```text
RT1 → invalid
RT2 → valid
```

This is rotation.

The security advantage is that the same refresh token shouldn't remain indefinitely reusable.

---

# 17. Token theft scenario

Suppose attacker steals:

```text
RT1
```

User legitimately uses it first:

```text
RT1
 ↓
RT2
```

Now:

```text
RT1 → invalid
```

Attacker later tries:

```text
RT1
 ↓
❌ rejected
```

This is why refresh-token rotation is such an important part of authentication architecture.

# 18. Logout

Now:

```http
POST /api/v1/auth/logout
```

The server should invalidate the refresh session/token according to your session design.

Conceptually:

```text
Refresh token
 ↓
Revoke / invalidate
 ↓
Clear cookie
```

After logout:

```text
Old refresh token
       ↓
      ❌
```

This is why logout isn't merely:

```js
res.clearCookie(...)
```

Clearing the browser cookie is useful, but server-side invalidation matters too when you maintain server-side refresh-token state.

# 21. Authentication middleware

After login, the user calls:

```http
GET /api/v1/users/me
```

with:

```http
Authorization: Bearer ACCESS_TOKEN
```

Middleware:

```text
Request
 ↓
Extract Bearer token
 ↓
Verify JWT
 ↓
Read claims
 ↓
Set req.user
 ↓
next()
```

Your roadmap describes this architecture as:

```text
Authorization Header
       ↓
Extract Bearer token
       ↓
Verify JWT
       ↓
Find user information
       ↓
req.user = ...
       ↓
next()
```

---

# 22. What should `req.user` contain?

Keep it minimal.

For example:

```js
req.user = {
    id: userId
};
```

You might have other trusted claims depending on your design.

But don't blindly put sensitive information into the request context.

Especially don't do:

```js
req.user = entireUserDocument;
```

unless there is a good reason.

---

# 23. Why not put the password in `req.user`?

Obviously:

```text
❌ password
❌ passwordHash
```

should not be needed for normal request authentication.

Your authentication middleware should work with the minimum identity information required.

---

# 24. Authentication middleware ≠ authorization

This distinction is extremely important.

Authentication asks:

> **Who is this?**

```text
JWT
 ↓
userId
```

Authorization asks:

> **Can this user do this?**

For example:

```text
userId = 123
role = user
```

might mean:

```text
GET /todos
   ↓
✅ allowed

DELETE /admin/users/456
   ↓
❌ not allowed
```

Authorization becomes the focus of Phase 15.

# 26. Authentication database state

Your user/session data might conceptually look like:

```text

│
├── id
├── email
├── passwordHash
├── emailVerified
├── role
│

```

But in a more mature multi-device system, refresh sessions are often better modeled separately:

```text

```

```text

```

# 27. One refresh token per user vs sessions

A beginner design might have:

```text
User
 └── refreshTokenHash
```

This is simple.

But imagine:

```text
Laptop → RT1
Phone  → RT2
```

If you only have one field:

```text
refreshTokenHash
```

then managing multiple devices becomes awkward.

A more scalable design is:

```text
User
  │
  ├── Session A
  │     └── refreshTokenHash
  │
  ├── Session B
  │     └── refreshTokenHash
  │
  └── Session C
        └── refreshTokenHash
```

Now you can:

```text
Logout current device
Revoke phone
Revoke all sessions
```

This is an important forward-looking improvement.

# 29. Token utilities

Token creation should be separated into utilities.

For example:

```text
utils/
└── token.js
```

Conceptually:

```text
generateAccessToken()
generateRefreshToken()
verifyAccessToken()
verifyRefreshToken()
```

Why?

Because token mechanics aren't business logic.

The service says:

```text
"Generate an access token."
```

The utility knows:

```text
"How exactly do I sign this JWT?"
```

That's separation of responsibility.

---

# 30. Password utility

Similarly:

```text
utils/
└── password.js
```

could conceptually contain:

```text
hashPassword()
comparePassword()
```

Then your service doesn't need to care about bcrypt's API.

It simply says:

```text
hash password
compare password
```

You don't need to over-engineer your first implementation, but understanding this direction will help you design better systems.
