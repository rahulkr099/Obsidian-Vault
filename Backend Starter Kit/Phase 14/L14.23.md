# Lesson 14.23 — Build Authentication From Scratch

This is the **final practical lesson of Phase 14**.

Your roadmap explicitly defines 14.23 as **“Build authentication from scratch”**. The intended flow is the one we've been building toward:

```text
login
 ↓
service
 ↓
generateAccessToken()
 ↓
generateRefreshToken()
 ↓
bcrypt.hash(refreshToken)
 ↓
repository
 ↓
MongoDB
```

Today we'll turn the architecture from 14.22 into a **real implementation plan**.

---

# 1. What are we building?

We're going to build authentication as a complete feature:

```text
                    AUTH MODULE
                        │
       ┌────────────────┼────────────────┐
       ▼                ▼                ▼
     Signup            Login          Refresh
       │                │                │
       ▼                ▼                ▼
 Email verification   Tokens          Rotation
       │                │
       ▼                ▼
   Verified user       Logout
```

And later:

```text
Forgot Password
       ↓
Reset Password
```

The important part is that we're not creating random files.

We're creating a **request flow**.

---

Before writing code, decide what the authentication API looks like.

We'll use:

```text

POST /api/v1/auth/login

POST /api/v1/auth/reset-password

POST /api/v1/auth/verify-email
POST /api/v1/auth/resend-verification
```

Your roadmap specifically calls out signup, login, refresh, logout and later password-reset functionality.

# 5. Step 1 — User model

Authentication starts with the user.

Conceptually:

```js
User {
    firstName,
    lastName,
    email,
    passwordHash,
    role,
    emailVerified,

    refreshTokenHash,

    resetTokenHash,
    resetTokenExpires,

    verificationTokenHash,
    verificationTokenExpires,

    timestamps
}
```

The starter roadmap similarly identifies the user model as containing authentication-related fields such as password, role, refresh-token and reset-token state.

---

# 6. Very important: never store the password

Never:

```js
password: "Rahul123"
```

Instead:

```text
password
   ↓
bcrypt
   ↓
passwordHash
   ↓
MongoDB
```

So MongoDB contains something like:

```text
passwordHash:
$2b$...
```

not the original password.

---

# 7. Step 2 — Password utility

Don't spread bcrypt code everywhere.

Create a small abstraction:

```js
hashPassword(password)
comparePassword(password, passwordHash)
```

Conceptually:

```text
authService
     │
     ├── hashPassword()
     │
     └── comparePassword()
```

Now the authentication service doesn't need to care about bcrypt's API.

---

# 8. Step 3 — Token utility

Similarly, token creation belongs in a token utility.

Conceptually:

```js
generateAccessToken(user)
generateRefreshToken(user)
verifyAccessToken(token)
verifyRefreshToken(token)
```

Your roadmap specifically separates access and refresh tokens.

---

# 9. Access token

The access token is:

```text
SHORT-LIVED
```

and is used for API authorization.

Example:

```text
Client
  ↓
Authorization: Bearer <access-token>
  ↓
auth.middleware
  ↓
verify JWT
  ↓
req.user
```

---

# 10. Refresh token

The refresh token is:

```text
LONGER-LIVED
```

and is used to obtain a new access token.

Your roadmap recommends the basic arrangement:

```text
Access token
    ↓
Authorization header

Refresh token
    ↓
HttpOnly cookie
```

---

# 11. Step 4 — Authentication repository

Now we need database operations.

The repository should answer questions like:

```text
findUserByEmail()
findUserById()
createUser()
updateRefreshToken()
clearRefreshToken()
```

Notice what is missing:

```text
❌ JWT logic
❌ bcrypt logic
❌ HTTP response
❌ cookie logic
```

That's because the repository is responsible for **data access**, not business logic.

Your roadmap describes this exact separation: repository = how data is retrieved/modified; service = business logic.

# 14. Signup — Step 1: normalize email

The service should normalize the email before looking it up.

Conceptually:

```text
" Rahul@Example.com "
          ↓
"rahul@example.com"
```

Why?

Otherwise these could accidentally become different database values:

```text
Rahul@example.com
rahul@example.com
```

Email normalization should be done consistently throughout the authentication system.

---

# 15. Signup — Step 2: check existing user

Service asks repository:

```text
findUserByEmail(email)
```

If found:

```text
User already exists
```

If not:

```text
continue
```

The repository performs the database query.

The service decides what the result means.

---

# 16. Signup — Step 3: hash password

Raw password:

```text
StrongPassword123!
```

becomes:

```text

   ↓
passwordHash
```

Then:

```text

   ↓
createUser()
```

# 17. Signup — Step 4: create user

Initial state:

```text
emailVerified = false
```

because the user hasn't proved email ownership yet.

So:

```text
Create User
   ↓

```

# 18. Signup — Step 5: verification token

Generate:

```text

```

Then:

```text

       ↓

       ↓
verificationTokenHash
```

Store the hash.

Send the raw token through the verification email.

This follows exactly the temporary-token pattern from Lesson 14.21.

# 21. Login — find the user

Service calls:

```text
findUserByEmail(email)
```

If the user doesn't exist:

```text

```

Don't expose unnecessary information about whether an account exists.

# 22. Login — compare password

We have:

```text
User input
    ↓
password
```

and:

```text
Database
    ↓
passwordHash
```

Use:

```text
comparePassword(password, passwordHash)
```

If false:

```text
❌ Authentication failed
```

If true:

```text
✅ Continue
```

---

# 23. Login — generate access token

Now:

```text
User
 ↓
generateAccessToken()
 ↓
accessToken
```

The access token should contain only the claims your application actually needs.

For example:

```json
{
  "sub": "user-id"
}
```

Don't put sensitive data into the JWT unnecessarily.

---

# 24. Login — generate refresh token

Then:

```text
User
 ↓
generateRefreshToken()
 ↓
refreshToken
```

Now we have:

```text
accessToken
+
refreshToken
```

---

# 25. The important part: hash refresh token

This is the part your starter was designed to teach you.

Suppose:

```text
refreshToken = RT1
```

Don't save:

```text
RT1
```

Save:

```text
hash(RT1)
```

So:

```text
generateRefreshToken()
          ↓
         RT1
          ↓
      bcrypt.hash()
          ↓
          H1
          ↓
       MongoDB
```

The roadmap explicitly highlights this flow.

---

# 26. Why is this different from access tokens?

Because the refresh token is a valuable long-lived credential.

```text
Access token
 ↓
short-lived
```

while:

```text
Refresh token
 ↓
long-lived
 ↓
can obtain new access tokens
```

Therefore we want stronger protection around its server-side representation.

---

# 27. Login — store refresh state

The repository updates the user/session:

```text
refreshTokenHash = H1
```

If you later move to a multi-device session model, this can instead live in a separate session collection.

For the first implementation, keep the architecture understandable.

# 31. Refresh-token rotation

Suppose:

```text
Current:
RT1
```

User refreshes.

Server generates:

```text
RT2
```

Then:

```text
RT1 → invalid
RT2 → valid
```

Database becomes:

```text
hash(RT2)
```

instead of:

```text
hash(RT1)
```

This is rotation.

---

# 32. Why rotation matters

Imagine an attacker steals:

```text
RT1
```

The legitimate user refreshes first:

```text
RT1
 ↓
RT2
```

Now the attacker tries:

```text
RT1
 ↓
❌ invalid
```

That's a major security improvement.

---

# 33. Build logout

Request:

```http
POST /api/v1/auth/logout
```

Flow:

```text
Request
 ↓

 ↓
Service
 ↓
Revoke refresh session
 ↓
Clear cookie
```

Two things happen:

```text
Server:
invalidate refresh state

Browser:
remove refresh cookie
```

Don't rely only on deleting the browser cookie.

# 42. Why this architecture is powerful

Imagine tomorrow you change:

```text
bcrypt
```

to another password-hashing implementation.

If password logic is isolated:

```text
password.js
```

you don't need to rewrite:

```text
controller
service
routes
```

Similarly, if you change:

```text
JWT library
```

your authentication service can continue using:

```text
generateAccessToken()
```

without caring about the library underneath.

That's abstraction.

---

# 43. Don't create unnecessary abstraction

There's also a trap.

Don't make:

```text
TokenManagerFactoryProviderService
TokenRepositoryManager
AuthTokenAdapterFactory
```

just because architecture sounds professional.

Start with:

```text
controller
service
repository
utility
```

Add abstractions when there is a real reason.

**Clean architecture is not "more files."**

It's **clear responsibilities**.

# 54. A very important testing mindset

Don't only test:

```text
"Does login work?"
```

Also test:

```text
What if password is wrong?
What if user doesn't exist?
What if token is expired?
What if token is invalid?
What if token is reused?
What if refresh token was revoked?
What if email isn't verified?
What if request is repeated too quickly?
What if cookie is missing?
```

Security features are defined as much by their **failure behavior** as their success behavior.

> **Build authentication as a set of secure use cases—signup, login, refresh, logout, verification and recovery—where the controller handles HTTP, the service handles decisions, the repository handles data, and tokens/passwords are protected according to their purpose.**
