# Lesson 14.24 — Authentication Security Review & Hardening

Think of this lesson as:

> **“We built authentication. Now let's try to break it.”**

This is a very useful bridge between Phase 14 Authentication and Phase 15 Authorization.

---

## 1. Why do we need a security review?

A working login system is not automatically a secure login system.

For example:

```text
POST /login
     ↓
password correct?
     ↓
JWT generated
     ↓
200 OK
```

Technically, it works.

But we still need to ask:

```text
Can someone brute-force login?

Can someone steal a refresh token?

Can an expired token be reused?

Can a reset token be reused?

Can a user manipulate their role?

Can sensitive information leak in errors?

Can cookies be stolen?

Can sessions remain active after password reset?
```

Security review answers these questions.

---

# 2. Authentication security checklist

Your authentication system should now have these major protections:

```text
                    AUTH SECURITY
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
 Password             Tokens            Sessions
       │                 │                 │
       ▼                 ▼                 ▼
    Hashing          Expiration         Revocation
    bcrypt           Rotation           Logout
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ▼
                 Account Recovery
                         │
                ┌────────┴────────┐
                ▼                 ▼
          Email Verify       Password Reset
```

---

# 3. Password security

Never store:

```js
{
  password: "Rahul123"
}
```

Instead:

```text
password
   ↓
bcrypt
   ↓
passwordHash
   ↓
MongoDB
```

And when logging in:

```text
password
   +
passwordHash
   ↓
bcrypt.compare()
```

Never try to decrypt the password.

Passwords are **hashed**, not encrypted.

---

# 4. Never log passwords

This is a surprisingly common mistake.

Never do:

```js
logger.info({
  email,
  password
});
```

Also avoid:

```js
console.log(req.body);
```

inside authentication endpoints.

Because `req.body` could contain:

```json
{
  "email": "rahul@example.com",
  "password": "..."
}
```

Your logs can become a security leak.

---

# 5. Access-token security

Access tokens should generally be:

```text
short-lived
```

Conceptually:

```text
Login
 ↓
Access Token
 ↓
short lifetime
```

For example, an application might choose something like:

```text
15 minutes
```

The exact lifetime depends on your application's risk profile.

Don't blindly copy a number.

The principle is:

> **The more valuable the credential, the shorter its useful lifetime should generally be.**

---

# 6. Refresh-token security

Refresh tokens are different:

```text
longer-lived
+
higher-value
```

Therefore:

```text
Refresh token
      ↓
HttpOnly cookie
      ↓
Secure
      ↓
SameSite policy
      ↓
Server-side session state
```

And the server should store a protected representation such as:

```text
hash(refreshToken)
```

rather than the raw token.

---

# 7. Refresh-token rotation

Your secure refresh flow should look like:

```text
RT1
 ↓
refresh
 ↓
RT1 invalidated
 ↓
RT2 created
 ↓
RT2 stored
```

So:

```text
RT1 → ❌
RT2 → ✅
```

This prevents indefinite reuse of the same refresh credential.

---

# 8. Detect token reuse

Now let's go one step further.

Suppose:

```text
RT1
```

was issued.

An attacker steals it.

The legitimate user refreshes:

```text
RT1
 ↓
RT2
```

Now the attacker later sends:

```text
RT1
```

That should be suspicious.

Conceptually:

```text
Old refresh token used
        ↓
Token reuse detected
        ↓
Invalidate session
        ↓
Possibly revoke related sessions
        ↓
Require login again
```

This is a powerful production-level improvement.

---

# 9. Logout security

Logout should not merely mean:

```js
res.clearCookie("refreshToken");
```

Think:

```text
Logout
  │
  ├── Clear cookie
  │
  └── Revoke server-side session
```

Otherwise, an already-issued refresh credential might remain valid depending on your session design.

---

# 10. Password-reset security

A reset token should be:

```text
temporary
+
single-use
+
hard to guess
```

Architecture:

```text
Forgot password
      ↓
Generate random token
      ↓
Hash token
      ↓
Store hash + expiry
      ↓
Send raw token by email
```

When used:

```text
raw token
    ↓
hash
    ↓
compare
    ↓
valid?
```

After successful reset:

```text
resetTokenHash = null
resetTokenExpires = null
```

The token cannot be reused.

---

# 11. Password reset should affect sessions

Imagine:

```text
Laptop ─── logged in
Phone  ─── logged in
Tablet ─── logged in
```

Someone compromises the user's password.

The user performs:

```text
Password reset
```

A stronger security design can do:

```text
Password reset
      ↓
Change password
      ↓
Revoke existing sessions
      ↓
User logs in again
```

Now the old sessions aren't trusted indefinitely.

---

# 12. Email verification security

Verification tokens should also be:

```text
temporary
+
single-use
+
stored safely
```

Flow:

```text
Signup
 ↓
Generate token
 ↓
Hash token
 ↓
Store hash
 ↓
Email raw token
```

Then:

```text
Verify
 ↓
Hash received token
 ↓
Compare
 ↓
Check expiry
 ↓
emailVerified = true
 ↓
Delete token
```

---

# 13. Don't trust client-controlled fields

Suppose signup sends:

```json
{
  "email": "rahul@example.com",
  "password": "StrongPassword123!",
  "role": "admin"
}
```

Your backend should **not** simply save:

```js
role: req.body.role
```

Instead:

```text
Signup
 ↓
Server chooses default role
 ↓
role = USER
```

For example:

```js
role: ROLES.USER
```

Authorization will build on this in Phase 15.

---

# 14. Don't trust `emailVerified` from the client

This is also dangerous:

```json
{
  "email": "rahul@example.com",
  "emailVerified": true
}
```

The server should determine:

```text
emailVerified
```

from its own verification process.

Never allow:

```text
Client
 ↓
"I am verified."
```

to become trusted application state.

---

# 15. Avoid user-enumeration leaks

Be careful with responses like:

```text
Email doesn't exist.
```

during password recovery.

An attacker could send:

```text
100,000 email addresses
```

and discover which accounts exist.

A safer pattern is often a generic response:

```text
If an account exists, a reset email has been sent.
```

The exact UX/security balance depends on your application.

---

# 16. Login brute-force protection

Consider:

```text
Attacker
   ↓
/login
   ↓
password attempt
   ↓
password attempt
   ↓
password attempt
   ↓
...
```

You need rate limiting.

For example:

```text
/login
   ↓
Authentication rate limiter
   ↓
login service
```

This connects Phase 10 Security Middleware with Phase 14 Authentication.

---

# 17. Don't use only IP-based thinking

A sophisticated attacker may distribute requests across:

```text
IP 1
IP 2
IP 3
IP 4
...
```

So authentication protection can consider multiple signals:

```text
IP
+
account/email
+
device/session context
+
request frequency
```

Don't build an extremely complicated system immediately, but understand the direction.

---

# 18. Generic authentication errors

Avoid unnecessarily revealing:

```text
User does not exist
```

versus:

```text
Password incorrect
```

A generic response can be:

```text
Invalid email or password.
```

Internally, however, your logs can contain enough safe diagnostic information to investigate failures.

---

# 19. JWT secrets must be protected

Never:

```js
const SECRET = "my-secret";
```

inside source code.

Instead:

```text
Environment
   ↓
JWT_ACCESS_SECRET
JWT_REFRESH_SECRET
```

and:

```text
process.env.JWT_ACCESS_SECRET
```

Your `.env` should never be committed.

---

# 20. Use separate secrets where appropriate

Instead of:

```text
one secret for everything
```

you can use:

```text
ACCESS_TOKEN_SECRET
REFRESH_TOKEN_SECRET
```

This provides separation.

Then:

```text
Access JWT
   ↓
Access secret

Refresh JWT
   ↓
Refresh secret
```

If one credential system needs to be rotated, you have more control.

---

# 21. Don't put sensitive information inside JWT payloads

Avoid:

```json
{
  "userId": "123",
  "password": "...",
  "creditCard": "...",
  "secret": "..."
}
```

Remember:

> **JWT payloads are encoded, not encrypted by default.**

Put only the information the backend actually needs.

Usually something like:

```json
{
  "sub": "123"
}
```

is enough for basic identity.

---

# 22. Authentication middleware should fail safely

Suppose:

```text
Authorization header missing
```

Result:

```text
401 Unauthorized
```

Suppose:

```text
JWT malformed
```

Result:

```text
401 Unauthorized
```

Suppose:

```text
JWT expired
```

Result:

```text
401 Unauthorized
```

Don't expose internal JWT-library errors directly to clients.

---

# 23. Cookie security

Your refresh cookie should be configured intentionally.

Important properties:

```text
HttpOnly
Secure
SameSite
```

Conceptually:

```text
                    REFRESH COOKIE
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       HttpOnly        Secure        SameSite
          │              │              │
       JS can't       HTTPS only     Cross-site
       read it                        control
```

The correct `SameSite` setting depends on your frontend/backend deployment architecture.

Don't blindly choose one without understanding your deployment.

---

# 24. CORS + cookies

This becomes important when frontend and backend are separated.

For example:

```text
Frontend
https://app.example.com

Backend
https://api.example.com
```

If refresh tokens are cookies, you need your CORS and cookie configuration to agree.

Conceptually:

```text
Browser
  │
  ├── CORS policy
  │
  └── Cookie policy
          │
          ▼
       Backend
```

This is one reason authentication cannot be treated as "just JWT."

---

# 25. CSRF consideration

If authentication credentials are automatically sent by the browser as cookies, you must consider CSRF.

The key question is:

> Can another website cause the browser to send an authenticated request to my API?

Your protections can involve combinations of:

```text
SameSite cookies
+
CSRF defenses where required
+
Origin checks
+
proper CORS configuration
```

The exact design depends on how your application uses cookies and cross-site requests.

---

# 26. Authentication should have audit events

Important events include:

```text
LOGIN_SUCCESS
LOGIN_FAILURE
LOGOUT
REFRESH
REFRESH_REUSE_DETECTED
PASSWORD_RESET_REQUESTED
PASSWORD_RESET_COMPLETED
EMAIL_VERIFIED
SESSION_REVOKED
```

Don't log sensitive credentials.

Instead log useful metadata such as:

```text
event
userId
requestId
timestamp
```

and other non-sensitive context appropriate for your environment.

# 28. Authentication threat model

Think like an attacker.

```text
                    ATTACKER
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Login          Token           Account
      attack         theft           recovery
        │              │              │
        ▼              ▼              ▼
    Brute force    JWT theft       Reset abuse
    Credential     Cookie theft    Email abuse
    stuffing       Replay          Token reuse
```

Then your defenses:

```text
Brute force
    ↓
Rate limiting

Token theft
    ↓
Short expiry + rotation + secure storage

Reset abuse
    ↓
Short-lived single-use tokens

Cookie theft
    ↓
HttpOnly + Secure + SameSite + HTTPS
```
