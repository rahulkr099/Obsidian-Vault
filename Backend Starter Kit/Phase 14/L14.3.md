# Lesson 14.3 — How Login Actually Works

Now we move from **what authentication means** to **what actually happens when a user logs in**.

This lesson is very important because later, when we write:

```js
authService.login()
```

you should already understand everything happening behind that function.

---

# 1. The login problem

Suppose our React frontend has a login form:

```text
Email:
rahul@example.com

Password:
********
```

The user clicks:

```text
Login
```

React sends:

```http
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "mypassword"
}
```

Now the backend has one main job:

> **Verify that these credentials belong to a real user.**

If they are valid:

```text
Authentication successful
```

If they aren't:

```text
Authentication failed
```

But there are several steps between the request and that result.

---

# 2. The complete login flow

At a high level:

```text
React
  │
  │ email + password
  ▼
POST /api/v1/auth/login
  │
  ▼
Route
  │
  ▼
Validation Middleware
  │
  ▼
Controller
  │
  ▼
Auth Service
  │
  ▼
User Repository
  │
  ▼
MongoDB
  │
  ▼
Find User
  │
  ▼
Verify Password
  │
  ▼
Generate Authentication Credentials
  │
  ▼
Response
  │
  ▼
React
```

This is the architecture you should visualize whenever you hear:

> "Login request."

---

# 3. Step 1 — User submits login form

React might have:

```js
const response = await fetch("/api/v1/auth/login", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify({
        email,
        password
    })
});
```

The browser sends something conceptually like:

```http
POST /api/v1/auth/login
Content-Type: application/json
```

Body:

```json
{
  "email": "rahul@example.com",
  "password": "mypassword"
}
```

Now the request enters Express.

---

# 4. Step 2 — Route receives the request

We might eventually have:

```js
router.post(
    "/login",
    validate(loginSchema),
    authController.login
);
```

Notice something important.

The route itself doesn't perform login.

It connects different pieces:

```text
/login
   ↓
validation
   ↓
controller
```

So the route is essentially saying:

> "For a login request, first validate it, then send it to the login controller."

---

# 5. Step 3 — Validation

Before touching MongoDB, validate the input.

For example:

```text
Email
 ↓
Is it present?
 ↓
Is it a valid email?
```

Password:

```text
Password
 ↓
Is it present?
```

Potentially:

```text
Is it a string?
Does it meet our input requirements?
```

So:

```text
POST /login
      ↓
Validation
      │
      ├── Invalid → 400
      │
      └── Valid
            ↓
        Controller
```

Why validate first?

Because there's no reason to query MongoDB for obviously invalid input.

For example:

```json
{
  "email": "hello",
  "password": ""
}
```

We already know this isn't a valid login request.

---

# 6. Step 4 — Controller receives validated input

Now our controller might conceptually look like:

```js
export const login = asyncHandler(async (req, res) => {
    const { email, password } = req.body;

    const result = await authService.login({
        email,
        password
    });

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

Notice what the controller is doing.

It is mostly handling:

```text
HTTP
```

It gets:

```text
req.body
```

and eventually creates:

```text
HTTP response
```

It isn't responsible for:

```text
Finding the user
Checking password
Generating tokens
Updating refresh tokens
```

Those belong in deeper layers.

---

# 7. Step 5 — Controller calls the Service

The controller says:

```js
authService.login({
    email,
    password
});
```

Now we're entering the **business logic layer**.

The service asks:

> "What does our application need to do to authenticate this user?"

Conceptually:

```text
authService.login()
       │
       ├── Find user
       ├── Verify password
       ├── Generate credentials
       └── Return authentication result
```

This is why the service layer is so useful.

---

# 8. Step 6 — Service asks Repository for the user

The service shouldn't directly write:

```js
User.findOne(...)
```

if we're following the repository architecture we've been learning.

Instead:

```js
const user = await userRepository.findByEmail(email);
```

Now:

```text
Service
   ↓
Repository
```

The service says:

> "I need the user associated with this email."

The repository knows how to talk to MongoDB.

---

# 9. Step 7 — Repository queries MongoDB

The repository might eventually contain something like:

```js
export const findByEmail = async (email) => {
    return User.findOne({ email });
};
```

So the architecture becomes:

```text
Auth Service
      ↓
User Repository
      ↓
User Model
      ↓
MongoDB
```

MongoDB might contain:

```text
{
    _id: "123",
    email: "rahul@example.com",
    password: "$2b$12$....",
    role: "user"
}
```

The repository returns the user to the service.

---

# 10. Step 8 — What if the user doesn't exist?

Suppose the email isn't found.

```text
Repository
    ↓
null
```

The service now knows:

```text
No matching user
```

Authentication fails.

The service should not continue to:

```text
Generate access token
Generate refresh token
```

Instead, it should produce an authentication failure.

Conceptually:

```text
Email
 ↓
Find user
 ↓
No user
 ↓
Authentication failed
```

The API might return:

```http
401 Unauthorized
```

with a safe message such as:

```json
{
  "success": false,
  "message": "Invalid credentials"
}
```

We'll discuss why generic authentication errors are useful when we study security more deeply.

---

# 11. Step 9 — User exists

Suppose MongoDB returns:

```text
User
├── id: 123
├── email: rahul@example.com
├── password: <hash>
└── role: user
```

Now comes the critical question:

> Does the supplied password match the stored password hash?

This is where password hashing enters our authentication system.

---

# 12. The password is NOT compared directly

Suppose the user entered:

```text
mypassword
```

The database should **not** contain:

```text
password: "mypassword"
```

Instead it contains something like:

```text
password:
$2b$12$................................
```

That's a bcrypt hash.

The backend doesn't simply do:

```js
password === user.password
```

because:

```text
mypassword
```

is not equal to:

```text
$2b$12$...
```

Instead, bcrypt provides a comparison operation:

```text
supplied password
       +
stored hash
       ↓
bcrypt.compare()
       ↓
true / false
```

We'll learn this properly in **14.4 and 14.5**.

---

# 13. Step 10 — Password verification

Conceptually:

```js
const passwordCorrect = await bcrypt.compare(
    password,
    user.password
);
```

Suppose:

```text
passwordCorrect = true
```

Then:

```text
Authentication successful
```

If:

```text
passwordCorrect = false
```

then:

```text
Authentication failed
```

So:

```text
Find user
   ↓
Compare password
   │
   ├── false → authentication failure
   │
   └── true
          ↓
      authenticated
```

---

# 14. What happens after successful authentication?

Now the server knows:

```text
User = 123
Email = rahul@example.com
Role = user
```

But we still have a problem.

The request is finished.

Later React will make:

```http
GET /api/v1/users/me
```

How will the backend know that the new request is from User 123?

We need to give the client some form of authentication credential.

This is where **sessions and tokens** come in.

We'll study the different approaches later, but our architecture will eventually use:

```text
Access Token
+
Refresh Token
```

---

# 15. Step 11 — Generate an access token

After successful password verification:

```text
User verified
    ↓
Generate access token
```

Conceptually:

```text
User ID
Role
Other required claims
       ↓
JWT signing
       ↓
Access Token
```

For example, the token might encode information representing:

```text
userId = 123
role = user
```

The actual token will look like a long encoded string.

We don't manually create that string.

A JWT library does it for us.

We'll study JWT deeply in **14.9 and 14.10**.

---

# 16. Step 12 — Generate refresh token

Modern authentication often uses two credentials:

```text
Access Token
Refresh Token
```

Why two?

Because we want:

```text
Access Token
→ short-lived
```

and:

```text
Refresh Token
→ longer-lived
```

Conceptually:

```text
Login
 │
 ├── Access Token
 │       ↓
 │   API requests
 │
 └── Refresh Token
         ↓
     Get new access token
```

We'll spend several lessons understanding why this design is useful.

---

# 17. Why not make the access token last for 30 days?

Suppose you create:

```text
Access token
expires in 30 days
```

If that token gets stolen:

```text
Attacker
   ↓
stolen token
   ↓
API
   ↓
access for potentially 30 days
```

That's undesirable.

Instead, we can make the access token short-lived:

```text
Access Token
15 minutes
```

and use a refresh mechanism to obtain a new one.

For example:

```text
Access Token
   ↓
expires
   ↓
Refresh Token
   ↓
new Access Token
```

We'll examine the security trade-offs later.

---

# 18. Step 13 — Store refresh-token information

Our starter architecture includes the idea of storing a **hash** of the refresh token rather than simply keeping the raw refresh token.

Conceptually:

```text
Refresh Token
      ↓
Hash
      ↓
MongoDB
```

Why?

If your database were compromised, you don't want the database itself to contain reusable authentication credentials in plaintext.

So:

```text
Raw refresh token
      ↓
Client
```

while:

```text
Hash(refresh token)
      ↓
Database
```

This is an important security design.

We'll study it properly in **14.17**.

---

# 19. Step 14 — Send authentication credentials to the client

After successful login, the server needs to give the client what it needs for future authentication.

A simplified architecture could look like:

```text
Response
   │
   ├── Access Token
   │
   └── Refresh Token
```

In a browser-based application, the refresh token is commonly handled using an:

```text
HttpOnly Cookie
```

while the access token can be used for API authorization.

We'll carefully discuss cookie storage and token handling in later lessons.

---

# 20. Step 15 — Login response

The response might conceptually look like:

```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "user": {
      "id": "123",
      "email": "rahul@example.com",
      "role": "user"
    },
    "accessToken": "..."
  }
}
```

The exact response contract is a design decision.

Our goal is consistency.

For example:

```text
success
message
data
```

will eventually connect with the API response architecture we study later.

---

# 21. The complete login architecture

Now let's put everything together.

```text
                   React
                     │
                     │
                     │ email + password
                     ▼
          POST /api/v1/auth/login
                     │
                     ▼
                  Route
                     │
                     ▼
              Validation
                     │
                     ▼
                Controller
                     │
                     ▼
               Auth Service
                     │
                     ▼
             User Repository
                     │
                     ▼
                User Model
                     │
                     ▼
                 MongoDB
                     │
                     │ User
                     ▼
               Auth Service
                     │
                     ▼
            Verify Password
                     │
              ┌──────┴──────┐
              │             │
            FAIL          SUCCESS
              │             │
              ▼             ▼
             401       Generate Tokens
                            │
                    ┌───────┴────────┐
                    ▼                ▼
              Access Token      Refresh Token
                                       │
                                       ▼
                              Store token hash
                                       │
                                       ▼
                                   Response
                                       │
                                       ▼
                                    React
```

This is the architecture I want you to understand—not memorize individual files.

Let's make the responsibilities very clear.




---

```text

```

```text

```

For example:

```text

```




# 23. Why this separation matters

Imagine putting everything inside the controller:

```js
loginController()
```

It might become:

```text
Read request
 ↓
Validate
 ↓
Find user
 ↓
Check password
 ↓
Generate JWT
 ↓
Generate refresh token
 ↓
Hash refresh token
 ↓
Update database
 ↓
Set cookie
 ↓
Create response
 ↓
Handle errors
```

That's too much responsibility.

Instead:

```text
Controller
    ↓
Auth Service
    ↓
Repository
```

This makes the code easier to:

```text
Understand
Test
Change
Maintain
Reuse
```

---

# 24. What happens on a wrong password?

Suppose:

```text
Email exists
Password is wrong
```

Flow:

```text
Login
 ↓
Validation ✅
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
User found
 ↓
bcrypt.compare()
 ↓
false
 ↓
Authentication failure
 ↓
401
```

No tokens should be generated.

---

# 25. What happens with an unknown email?

```text
Login
 ↓
Validation ✅
 ↓
Repository
 ↓
User not found
 ↓
Authentication failure
 ↓
401
```

Again:

```text
No access token
No refresh token
```

should be issued.

---

# 26. Why shouldn't we tell the attacker exactly what failed?

Imagine an API returns:

```text
"Email does not exist."
```

An attacker can potentially test millions of email addresses and discover which accounts exist.

Better authentication responses generally avoid unnecessarily revealing whether:

```text
Email exists
```

or:

```text
Password was wrong
```

Instead:

```text
Invalid credentials
```

This reduces information leakage.

We'll revisit this when we study authentication security.

---

# 27. Login isn't finished when the response is sent

This is a subtle but important point.

Many beginners think:

```text
Login
 ↓
JWT
 ↓
Done
```

But authentication continues on future requests.

For example:

```text
LOGIN
 ↓
Access token
 ↓
GET /users/me
 ↓
Verify access token
 ↓
req.user
 ↓
Controller
```

Then:

```text
Access token expires
 ↓
Refresh
 ↓
New access token
```

Then:

```text
Logout
 ↓
Invalidate refresh credential
```

So authentication is a **lifecycle**, not one request.

---

# 28. Authentication lifecycle

Think of it as:

```text
                SIGNUP
                   │
                   ▼
             User created
                   │
                   ▼
                 LOGIN
                   │
                   ▼
          Verify credentials
                   │
                   ▼
          Authentication success
                   │
                   ▼
             Access token
                   │
                   ▼
         Protected API requests
                   │
                   ▼
          Access token expires
                   │
                   ▼
               REFRESH
                   │
                   ▼
          New access token
                   │
                   ▼
                LOGOUT
                   │
                   ▼
      Refresh credential invalidated
```

Later we'll add:

```text
Email verification
Password reset
Password change
Refresh token rotation
```

# 29. A professional mental model

Whenever you see:

```http
POST /auth/login
```

your brain should think:

```text

        ↓
2. Find user
        ↓
3. Verify password
        ↓
4. Establish authenticated identity
        ↓
5. Issue authentication credentials
        ↓
6. Store required server-side credential state
        ↓
7. Return appropriate response
```

And the architecture:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓

 ↓

```

# 30. One important distinction

There are two different things here:

### Authentication during login

```text
Email + Password
       ↓
"Are these credentials valid?"
```

### Authentication during future requests

```text
Access credential
       ↓
"Does this request belong to an authenticated user?"
```

So:

```text
LOGIN
→ Establish authentication
```

while:

```text
PROTECTED REQUEST
→ Verify existing authentication
```

That's a very important distinction.
