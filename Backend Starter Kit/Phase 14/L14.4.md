# Lesson 14.4 — Password Hashing Fundamentals 🔐

> **Source note:** Your project roadmap lists **14.3 as Password hashing** and **14.4 as bcrypt**. Since we're following the lesson numbering already established in our conversation, today's lesson is **14.4 — Password Hashing Fundamentals**, and we'll keep the actual `bcrypt` API for the next lesson.

This is one of the most important authentication concepts.

The question is:

> **If we must never store a user's real password in MongoDB, how can we later check whether the password they entered is correct?**

Let's build the answer from the ground up.

---

# 1. The dangerous approach: storing passwords directly

Imagine a user signs up:

```json
{
  "email": "rahul@example.com",
  "password": "Rahul@123"
}
```

A beginner might store:

```js
{
    email: "rahul@example.com",
    password: "Rahul@123"
}
```

This is called storing a **plaintext password**.

It is a serious security problem.

---

# 2. Why plaintext passwords are dangerous

Imagine your MongoDB contains:

```text
Users
──────────────────────────────
Rahul
email: rahul@example.com
password: Rahul@123

Amit
email: amit@example.com
password: Amit@456

Priya
email: priya@example.com
password: Priya@789
```

Now imagine an attacker gets access to your database.

They immediately have:

```text
Email + Password
Email + Password
Email + Password
```

The attacker doesn't need to crack anything.

The passwords are already there.

Even worse, people often reuse passwords across websites.

So a database leak could potentially compromise accounts elsewhere too.

---

# 3. The correct idea: hashing

Instead of storing:

```text
Rahul@123
```

we transform it into a **password hash**.

Conceptually:

```text
Password
   │
   ▼
Hashing algorithm
   │
   ▼
Password Hash
```

For example:

```text
Rahul@123
    ↓
hash function
    ↓
$2b$12$................................
```

We store:

```js
{
    email: "rahul@example.com",
    password: "$2b$12$................................"
}
```

not:

```js
{
    email: "rahul@example.com",
    password: "Rahul@123"
}
```

Your project roadmap explicitly follows this principle: plain passwords should never be stored; passwords are hashed before going into MongoDB.

---

# 4. What is hashing?

Hashing is a one-way transformation.

Conceptually:

```text
Input
  ↓
Hash function
  ↓
Hash
```

For example:

```text
hello
 ↓
HASH
 ↓
some-long-result
```

The important property is:

```text
Password
   ↓
Hash
```

should be easy to perform, while:

```text
Hash
   ↓
Original password
```

should not be practically reversible.

That's why we don't call password hashing **encryption**.

---

# 5. Hashing vs Encryption

This distinction is extremely important.

### Encryption

Encryption is designed to be reversible if you possess the appropriate key.

```text
Plaintext
   ↓
Encryption + Key
   ↓
Ciphertext
   ↓
Decryption + Key
   ↓
Plaintext
```

### Hashing

Hashing is designed as a one-way transformation:

```text
Password
   ↓
Hash
```

You don't normally do:

```text
Hash
 ↓
"Give me the original password"
```

There is no normal "decrypt password hash" operation.

---

# 6. Why do we need one-way hashing?

Suppose the database is compromised.

If we store:

```text
password = Rahul@123
```

the attacker immediately knows the password.

If we store:

```text
password = $2b$12$....
```

the attacker doesn't immediately have the original password.

They now have to attempt to guess passwords and see whether the resulting hashes match.

That's much better.

But there's another problem.

---

# 7. Why not use a normal hash like SHA-256?

You might think:

```text
password
   ↓
SHA-256
   ↓
hash
```

Problem:

**Password hashing needs to be deliberately expensive.**

General-purpose cryptographic hashes such as SHA-256 are designed to be extremely fast.

That's great for many cryptographic tasks.

It's not ideal for password storage.

Imagine an attacker has powerful hardware and can test enormous numbers of guesses per second.

If password hashing is extremely fast:

```text
guess
 ↓
SHA-256
 ↓
compare
```

can be repeated very quickly.

Password hashing algorithms are designed differently.

---

# 8. Password hashing should be slow

For passwords, we want something more like:

```text
Password
   ↓
Expensive password hashing
   ↓
Hash
```

The goal is to make each password guess more expensive.

So an attacker can't cheaply test billions of guesses.

This gives us an important principle:

> **Password hashing should be intentionally computationally expensive.**

---

# 9. Salts

Now we reach another extremely important concept:

> **The same password should not always produce the same stored hash.**

Suppose Rahul and Amit both use:

```text
password123
```

If hashing worked like:

```text
password123
    ↓
HASH
    ↓
ABC123
```

then both users would have:

```text
ABC123
```

An attacker could identify users sharing passwords.

More importantly, precomputed password-hash lookup attacks become much more useful.

This is why password hashing uses a **salt**.

---

# 10. What is a salt?

A salt is additional random data incorporated into the password hashing process.

Conceptually:

```text
Password
   +
Random Salt
   ↓
Password Hashing Algorithm
   ↓
Hash
```

So:

```text
password123 + randomSaltA
       ↓
       hashA
```

while another user:

```text
password123 + randomSaltB
       ↓
       hashB
```

The resulting hashes can therefore be different even though the passwords are identical.

---

# 11. Important distinction: salt vs password

Don't confuse:

```text
Password
```

with:

```text
Salt
```

The password is secret.

The salt is not treated as a secret key.

The salt's purpose is to make each password hash unique and make precomputed attacks much harder.

Modern password-hashing libraries such as bcrypt handle the salt as part of the password-hashing process.

That's one reason we don't want to manually invent our own password-storage algorithm.

---

# 12. What does a password hash actually contain?

When you eventually see something like:

```text
$2b$12$................................................
```

don't think:

> "That's just the encrypted password."

It isn't.

A bcrypt password string encodes information needed for password verification, including the algorithm/version information, cost factor, salt, and resulting hash.

Conceptually:

```text
bcrypt stored value
│
├── algorithm/version information
├── cost
├── salt
└── derived hash
```

This is why you can store **one string** in MongoDB and later give that string to bcrypt for verification.

---

# 13. How can login work if we don't know the original password?

This is the beautiful part.

Suppose signup:

```text
User enters:
Rahul@123

       ↓

Password hashing

       ↓

Stored hash:
$2b$12$................
```

Later the user logs in:

```text
User enters:
Rahul@123
```

The server doesn't say:

```text
"Let's decrypt the database hash."
```

Instead it says:

```text
"Let's verify whether this password produces
the same result according to the stored hash."
```

Conceptually:

```text
Login password
      +
Stored hash
      ↓
Password verification
      ↓
true / false
```

# 14. Signup flow

Let's look at signup.

User sends:

```json
{
  "email": "rahul@example.com",
  "password": "Rahul@123"
}
```

Backend:

```text
Receive password
      ↓
Validate password
      ↓
Hash password
      ↓
Store hash
      ↓
MongoDB
```

Database:

```js
{
    email: "rahul@example.com",
    password: "<password hash>"
}
```

The plaintext password should not be stored.

# 15. Login flow

Later:

```json
{
  "email": "rahul@example.com",
  "password": "Rahul@123"
}
```

Backend:

```text
Receive password
      ↓
Find user
      ↓
Get stored password hash
      ↓
Verify supplied password
      ↓
true?
```

If true:

```text
Authentication successful
```

If false:

```text
Authentication failed
```

This connects directly to the login architecture from Lesson 14.3.

# 17. Hashing is not just "run a function"

This is an important professional mindset.

Don't think:

```js
const hash = hash(password);
```

and move on.

A secure password-storage system involves decisions about:

```text
Algorithm
Salt
Cost/work factor
Password verification
Upgrade strategy
Error handling
Password policies
Credential lifecycle
```

We'll start simple, but eventually you'll understand the whole system.

---

# 18. What is a work factor?

Remember that password hashing should be intentionally expensive.

Many password-hashing algorithms therefore have a configurable **work factor** or **cost**.

Conceptually:

```text
Low cost
   ↓
Fast hashing
   ↓
Less protection against guessing
```

versus:

```text
Higher cost
   ↓
Slower hashing
   ↓
More expensive attacks
```

But you don't simply choose the highest possible value.

Your application needs a sensible balance between:

```text
Security
      +
Server performance
      +
User experience
```

We'll discuss the bcrypt cost factor specifically in **14.5**.

---

# 19. Why hashing doesn't mean passwords are magically safe

Password hashing dramatically improves security, but it doesn't eliminate all password risks.

For example, if a user chooses:

```text
123456
```

an attacker can still guess it.

The hash protects the stored representation, but it can't make a weak password strong.

Think:

```text
Weak password
      +
Excellent hashing
      ↓
Still a weak password
```

So authentication security needs multiple layers:

```text
Strong password policy
       +
Secure password hashing
       +
Rate limiting
       +
Account protection
       +
Secure authentication tokens
```

We'll build these across the authentication and security phases.

---

# 20. Hashing vs encoding

Another common beginner confusion.

### Encoding

Example:

```text
"hello"
   ↓
Base64
   ↓
"aGVsbG8="
```

This is not security.

Anyone can decode it.

### Hashing

```text
password
   ↓
password hashing algorithm
   ↓
derived hash
```

Designed to be one-way.

### Encryption

```text
data
 ↓
encryption
 ↓
encrypted data
 ↓
decryption
 ↓
data
```

Designed to be reversible with the proper key.

So:

```text
Encoding     → representation
Hashing      → one-way transformation
Encryption   → reversible protection
```

# 21. Why shouldn't we invent our own hashing system?

Suppose someone says:

```js
function myPasswordHash(password) {
    return password + "SECRET123";
}
```

This is not secure password hashing.

Or:

```js
password.split("").reverse().join("")
```

Obviously not secure.

Or:

```js
sha256(password)
```

Even though SHA-256 is a cryptographic hash, it isn't designed specifically for password storage.

Security-sensitive primitives should come from well-established libraries and algorithms.

For this project, we'll use **bcrypt**.

# 23. Password hashing in your architecture

Remember the layers we learned earlier.

Signup:

```text
POST /auth/signup
       ↓
Validation
       ↓
Controller
       ↓
Auth Service
       ↓
Password hashing
       ↓
Repository
       ↓
MongoDB
```

Notice:

**Password hashing belongs to authentication/business logic, not to the controller.**

You don't want:

```js
// controller
bcrypt.hash(...)
```

mixed into HTTP handling.

Instead, conceptually:

```text
Controller
    ↓
authService.signup()
    ↓
hash password
    ↓
repository.createUser()
```

This keeps your architecture clean.

# 24. A subtle but important rule

### Never log passwords.

Don't do this:

```js
console.log(req.body.password);
```

Don't do this:

```js
logger.info({
    email,
    password
});
```

And don't include passwords in error messages.

Your logs should never become another place where credentials leak.

# 25. What should be stored?

A user document might look like:

```js
{
    _id: "...",
    email: "rahul@example.com",
    password: "$2b$12$....................",
    role: "user"
}
```

Not:

```js
{
    email: "rahul@example.com",
    password: "Rahul@123"
}
```

And when returning user information from your API, we generally don't want:

```json
{
  "email": "rahul@example.com",
  "password": "$2b$12$..."
}
```

Even though the hash isn't the plaintext password, it is still sensitive credential data and should normally be excluded from normal user responses.

# 27. A common misconception

You may hear:

> "We hash the password and then compare the two hashes."

That's an oversimplification.

With modern password hashing systems such as bcrypt, verification uses the stored hash's parameters and salt to process the supplied password and determine whether it matches.

Conceptually:

```text
Supplied password
       +
Stored password hash
       ↓
bcrypt verification
       ↓
true / false
```

You don't manually extract a salt and implement the comparison yourself.

The library handles it.

# 29. What happens if MongoDB is leaked?

Let's compare.

### Bad design

```text
MongoDB leaked
      ↓
Plain passwords
      ↓
Game over
```

### Better design

```text
MongoDB leaked
      ↓
Password hashes
      ↓
Attacker must attempt password guesses
```

That's a **huge improvement**, although not a guarantee of safety.

Strong password hashing is specifically designed to make those guessing attacks more expensive.

# 🔑 Five rules to remember

### Rule 1

**Never store plaintext passwords.**

```text
❌ password: "Rahul@123"
```

---

### Rule 2

**Use a password-hashing algorithm designed for passwords.**

```text
✅ bcrypt
```

---

### Rule 3

**Password hashing is not encryption.**

```text
Hashing      → one-way
Encryption   → reversible with key
```

---

### Rule 4

**Use salts.**

They ensure identical passwords don't simply result in identical stored hashes.

---

### Rule 5

**Never log or return passwords.**

Even during debugging.
