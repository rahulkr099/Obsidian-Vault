# Lesson 14.5 — bcrypt: Password Hashing in Node.js 🔐

In Lesson 14.4, we learned **why** passwords must be hashed.

Now we'll learn **how bcrypt actually fits into our Node.js backend**.

Our goal is not just to memorize:

```js
bcrypt.hash()
bcrypt.compare()
```

We want to understand what these functions are doing and **where they belong in our architecture**.

---

# 1. What is bcrypt?

**bcrypt is a password-hashing algorithm/library designed specifically for storing passwords securely.**

Our basic flow is:

```text
Plain Password
      ↓
    bcrypt
      ↓
Password Hash
      ↓
   MongoDB
```

During login:

```text
Entered Password
      +
Stored Password Hash
      ↓
bcrypt.compare()
      ↓
true / false
```

So bcrypt gives us two important operations:

```js
bcrypt.hash()
```

and:

```js
bcrypt.compare()
```

---

# 2. Install bcrypt

In our Node.js backend:

```bash
npm install bcrypt
```

Then:

```js
import bcrypt from "bcrypt";
```

Depending on your project configuration, you may use CommonJS instead:

```js
const bcrypt = require("bcrypt");
```

Since our backend uses modern JavaScript modules, we'll generally use:

```js
import bcrypt from "bcrypt";
```

---

# 3. `bcrypt.hash()`

Suppose the user enters:

```text
Rahul@123
```

We don't want:

```js
password: "Rahul@123"
```

in MongoDB.

Instead:

```js
const passwordHash = await bcrypt.hash(password, 12);
```

Conceptually:

```text
"Rahul@123"
      ↓
bcrypt.hash()
      ↓
"$2b$12$................"
```

Then store:

```js
{
    email,
    password: passwordHash
}
```

---

# 4. What is the `12`?

You may see:

```js
bcrypt.hash(password, 12);
```

The second argument is the **cost factor**, also called the work factor.

Conceptually:

```text
bcrypt.hash(password, cost)
```

For example:

```js
bcrypt.hash(password, 10);
bcrypt.hash(password, 12);
bcrypt.hash(password, 14);
```

Higher cost generally means:

```text
More computation
      ↓
Slower hashing
      ↓
More expensive password guessing
```

But higher isn't automatically better.

You need a reasonable balance between:

```text
Security
   +
Server performance
```

For our learning project, you'll commonly see a value such as:

```js
12
```

The exact production value should be chosen based on current security guidance and measured server performance.

---

# 5. Why bcrypt should be slow

Imagine an attacker has stolen your database.

They see:

```text
$2b$12$........................
```

They don't know the original password.

They might try:

```text
123456
password
password123
rahul123
qwerty
...
```

For every guess:

```text
Guess
 ↓
bcrypt
 ↓
Compare
```

If bcrypt is deliberately computationally expensive, the attacker can't test guesses as cheaply as they could with a fast general-purpose hash.

That's the basic security idea.

---

# 6. What does bcrypt actually do with the password?

Conceptually:

```text
Password
   +
Random Salt
   +
Cost Factor
   ↓
bcrypt algorithm
   ↓
Derived Password Hash
```

The salt is generated as part of the bcrypt process.

That's why you normally don't need to manually create:

```js
const salt = ...
```

for basic bcrypt usage.

Let the library handle it.

---

# 7. You don't manually store the salt separately

A beginner might think:

```js
const salt = generateSalt();

const hash = bcrypt.hash(password, salt);
```

For normal bcrypt usage, you don't need to build this yourself.

Instead:

```js
const hash = await bcrypt.hash(password, 12);
```

The resulting bcrypt string contains the information needed for later verification, including the salt and cost parameters.

So MongoDB stores something like:

```text
$2b$12$................................................
```

as one value.

---

# 8. `bcrypt.compare()`

Now imagine the user logs in.

They enter:

```text
Rahul@123
```

MongoDB contains:

```text
$2b$12$................................................
```

We do:

```js
const isMatch = await bcrypt.compare(
    password,
    user.password
);
```

where:

```text
password
    ↓
user-entered password

user.password
    ↓
stored bcrypt hash
```

The result is:

```js
true
```

or:

```js
false
```

---

# 9. Very important: we don't decrypt the hash

This:

```js
bcrypt.compare(password, user.password);
```

does **not** mean:

```text
Decrypt stored password
       ↓
Get original password
```

Instead, bcrypt uses the information in the stored hash to process the supplied password and determine whether it matches.

Think:

```text
Entered Password
      +
Stored Hash
      ↓
bcrypt verification
      ↓
true / false
```

# 10. Signup example

Let's create a simple signup example.

```js
import bcrypt from "bcrypt";

const password = "Rahul@123";

const passwordHash = await bcrypt.hash(password, 12);

console.log(passwordHash);
```

The result will look roughly like:

```text
$2b$12$................................................
```

We then store:

```js
const user = {
    email: "rahul@example.com",
    password: passwordHash
};
```

Not:

```js
const user = {
    email: "rahul@example.com",
    password: password
};
```

# 11. Login example

Later:

```js
const password = "Rahul@123";

const user = await userRepository.findByEmail(email);

const isMatch = await bcrypt.compare(
    password,
    user.password
);
```

Then:

```js
if (!isMatch) {
    throw new UnauthorizedError("Invalid credentials");
}
```

If it matches:

```text
Authentication successful
```

and we can continue with token generation.

# 12. Complete signup flow

Our architecture:

```text
POST /auth/signup
        ↓
Validation
        ↓
Controller
        ↓
Auth Service
        ↓
bcrypt.hash()
        ↓
User Repository
        ↓
MongoDB
```

Inside the service, conceptually:

```js
async function signup({ email, password }) {
    const existingUser =
        await userRepository.findByEmail(email);

    if (existingUser) {
        throw new ConflictError("User already exists");
    }

    const passwordHash =
        await bcrypt.hash(password, 12);

    return userRepository.create({
        email,
        password: passwordHash
    });
}
```

Notice the important sequence:

```text
Receive password
      ↓
Validate
      ↓
Hash
      ↓
Store hash
```

# 13. Complete login flow

Login:

```text
POST /auth/login
        ↓
Validation
        ↓
Controller
        ↓
Auth Service
        ↓
Find User
        ↓
bcrypt.compare()
        ↓
     ┌──┴──┐
     │     │
   false  true
     │     │
    401    ↓
        Generate tokens
```

Conceptually:

```js
async function login({ email, password }) {
    const user =
        await userRepository.findByEmail(email);

    if (!user) {
        throw new UnauthorizedError("Invalid credentials");
    }

    const isMatch =
        await bcrypt.compare(password, user.password);

    if (!isMatch) {
        throw new UnauthorizedError("Invalid credentials");
    }

    // Generate authentication credentials...
}
```

This is the core of password-based authentication.

---

# 14. Why `await`?

You'll notice:

```js
await bcrypt.hash(...)
```

and:

```js
await bcrypt.compare(...)
```

bcrypt operations are computationally expensive.

In a Node.js server, we don't want password operations to unnecessarily block the event loop.

So we use the asynchronous API:

```js
await bcrypt.hash(...)
```

instead of relying on synchronous password hashing in request handling.

---

# 15. Avoid synchronous bcrypt methods in request handlers

You may encounter:

```js
bcrypt.hashSync(password, 12);
```

and:

```js
bcrypt.compareSync(password, hash);
```

These are synchronous.

For normal web request handling, prefer:

```js
await bcrypt.hash(password, 12);
```

and:

```js
await bcrypt.compare(password, hash);
```

because password hashing is intentionally expensive.

A synchronous operation can block Node.js from processing other work.

---

# 16. Why blocking matters

Imagine your Express server is handling:

```text
Request A
Request B
Request C
Request D
```

If you perform a long synchronous operation:

```text
Request A
   ↓
bcrypt.hashSync()
   ↓
BLOCK
```

other JavaScript work may have to wait.

With asynchronous APIs:

```text
Request A
   ↓
bcrypt.hash()
   ↓
await
   ↓
Node can continue handling other work
```

The exact underlying execution details are more nuanced, but the practical rule is:

> **Use the asynchronous bcrypt APIs in normal backend request flows.**

---

# 17. What if `user` doesn't exist?

Be careful here.

This would be dangerous:

```js
const isMatch = await bcrypt.compare(
    password,
    user.password
);
```

if:

```js
user === null
```

because:

```js
user.password
```

would fail.

Instead:

```js
const user = await userRepository.findByEmail(email);

if (!user) {
    throw new UnauthorizedError("Invalid credentials");
}

const isMatch = await bcrypt.compare(
    password,
    user.password
);
```

This is both cleaner and safer.

---

# 18. Why use the same error for email and password failures?

Consider:

```text
Email doesn't exist
        ↓
"Email does not exist"
```

versus:

```text
Email exists but password is wrong
        ↓
"Wrong password"
```

That can reveal information about registered accounts.

Instead:

```text
Invalid credentials
```

for both cases.

Conceptually:

```text
Unknown email
     ↓
401 Invalid credentials

Wrong password
     ↓
401 Invalid credentials
```

This reduces unnecessary account-enumeration information.

---

# 19. bcrypt and password leakage

Imagine your API returns:

```json
{
  "id": "123",
  "email": "rahul@example.com",
  "password": "$2b$12$..."
}
```

Don't do this.

Even though the value is hashed, your normal user response should not expose password credential data.

Better:

```json
{
  "id": "123",
  "email": "rahul@example.com"
}
```

This is another reason your repository/model layer should be careful about selecting password fields.

# 20. A useful User model design

You might eventually have:

```js
const userSchema = new Schema({
    email: {
        type: String,
        required: true,
        unique: true
    },

    password: {
        type: String,
        required: true,
        select: false
    },

    role: {
        type: String,
        default: "user"
    }
});
```

The idea behind:

```js
select: false
```

is that normal user queries don't automatically return the password hash.

Then when login specifically needs it, you can explicitly request it.

Conceptually:

```js
User.findOne({ email }).select("+password");
```

The exact implementation depends on how we structure your project.

The important architectural idea is:

> **The password hash should be available to authentication logic when needed, but shouldn't casually leak into normal application code or API responses.**

# 21. Where should bcrypt live?

A clean structure could be:

```text
src/
├── controllers/
│   └── auth.controller.js
│
├── services/
│   └── auth.service.js
│
├── repositories/
│   └── user.repository.js
│
├── models/
│   └── user.model.js
│
└── utils/
    └── password.js
```

We could create a password utility:

```js
export const hashPassword = async (password) => {
    return bcrypt.hash(password, 12);
};

export const verifyPassword = async (
    password,
    passwordHash
) => {
    return bcrypt.compare(password, passwordHash);
};
```

Then the service becomes cleaner:

```js
const passwordHash = await hashPassword(password);
```

and:

```js
const isMatch = await verifyPassword(
    password,
    user.password
);
```

This is especially useful as your project grows.

---

# 22. Should bcrypt be inside the repository?

Usually, no.

Don't think:

```text
Repository
   ↓
Hash password
```

The repository's primary responsibility is persistence.

For example:

```text
Repository
   ↓
Create user
Find user
Update user
Delete user
```

Password hashing is authentication/domain logic.

So a cleaner separation is:

```text
Auth Service
   ↓
Password Utility
   ↓
bcrypt
```

then:

```text
Auth Service
   ↓
User Repository
```

# 24. Cost factor: don't blindly increase it

You might think:

```text
12 is secure
Therefore:
20 must be more secure
Therefore:
Use 20
```

Not necessarily.

Increasing the cost means each password operation becomes more expensive.

That affects:

```text
Signup
Login
Password reset
Password change
```

If the cost is unnecessarily high:

```text
High CPU usage
       ↓
Higher latency
       ↓
Lower throughput
```

So production systems should benchmark their chosen configuration.

The principle is:

> **Choose a strong work factor that is expensive enough to slow attackers without unnecessarily hurting your application's normal authentication traffic.**

# 25. Why bcrypt is still useful

bcrypt has several important properties for password storage:

```text
✓ Designed for passwords
✓ Salt handled by the algorithm
✓ Configurable work factor
✓ Built-in verification
✓ Widely supported
✓ Well understood
```

Other password-hashing algorithms also exist, such as:

```text
Argon2
scrypt
```

We'll eventually discuss why algorithm choice matters.

For our current MERN starter project, however, bcrypt gives us a simple and well-understood foundation.

---

# 26. Don't build password hashing yourself

Never do something like:

```js
const myHash = password =>
    crypto
        .createHash("sha256")
        .update(password + "my-secret")
        .digest("hex");
```

Even though this uses a real cryptographic hash, you've now created your own password-storage scheme.

That's not what we want.

Instead:

```js
const hash = await bcrypt.hash(password, 12);
```

Use a purpose-built, well-reviewed password-hashing implementation.

---

# 27. bcrypt doesn't solve everything

This is important.

Using bcrypt doesn't automatically protect your authentication system from:

```text
Brute-force attacks
Credential stuffing
Phishing
Stolen sessions
Token theft
Password reset attacks
Account enumeration
Weak passwords
```

bcrypt solves a specific problem:

> **How should we securely store and verify passwords?**

Other authentication security mechanisms solve other problems.

# 28. Password hashing vs token security

After login:

```text

   ↓

   ↓
Authentication succeeds
   ↓

```

Now there are **two different security areas**.

### Password security

```text
Password
 ↓

```

### Token security

```text

Cookies

```

We'll handle those separately.

Don't mix them together.

# 29. A realistic `auth.service.js`

A simplified version could look like:

```js
import {
    hashPassword,
    verifyPassword
} from "../utils/password.js";

export const signup = async ({ email, password }) => {
    const existingUser =
        await userRepository.findByEmail(email);

    if (existingUser) {
        throw new ConflictError("User already exists");
    }

    const passwordHash =
        await hashPassword(password);

    const user = await userRepository.create({
        email,
        password: passwordHash
    });

    return user;
};

export const login = async ({ email, password }) => {
    const user =
        await userRepository.findByEmailWithPassword(email);

    if (!user) {
        throw new UnauthorizedError("Invalid credentials");
    }

    const isMatch =
        await verifyPassword(
            password,
            user.password
        );

    if (!isMatch) {
        throw new UnauthorizedError("Invalid credentials");
    }

    // Token generation comes later.
};
```

Notice how readable this is:

```text
Find user
 ↓
Verify password
 ↓
Continue authentication
```

Token generation will be added in later lessons.

# 31. Signup vs Login

Let's compare them.

|Operation|What bcrypt does|
|---|---|
|Signup|`bcrypt.hash()`|
|Login|`bcrypt.compare()`|
|Password change|`bcrypt.hash()`|
|Password reset|`bcrypt.hash()`|

So:

```text
Creating/replacing password
        ↓
bcrypt.hash()
```

while:

```text
Checking password
        ↓
bcrypt.compare()
```

This is an excellent rule to remember.

### Hash

```js
const hash = await bcrypt.hash(password, 12);
```

### Verify

```js
const isValid = await bcrypt.compare(
```
