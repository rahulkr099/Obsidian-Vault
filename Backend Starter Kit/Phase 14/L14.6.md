# Lesson 14.6 — Signup Architecture

We now move from the **bcrypt implementation** to designing the complete **signup flow**.

One correction from the earlier lesson: your project roadmap defines **14.5 = Signup architecture** and **14.6 = Login architecture**.

So, following your roadmap, **today's lesson is actually Login Architecture**. The previous lesson covered bcrypt, which is the foundation for this flow.

---

# 1. What are we trying to build?

Our authentication API eventually needs:

```text
POST /api/v1/auth/signup
POST /api/v1/auth/login
POST /api/v1/auth/refresh
POST /api/v1/auth/logout
GET  /api/v1/auth/status
```

The starter roadmap explicitly puts authentication after middleware, validation, controllers, services, and repositories because those layers are supposed to work together.

Today we're focusing on:

```text
POST /api/v1/auth/login
```

The important question is:

> **How should a login request travel through our architecture?**

---

# 2. Start with the user's request

Imagine React sends:

```http
POST /api/v1/auth/login
Content-Type: application/json
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "Rahul@123"
}
```

The request enters our backend.

Our architecture should be:

```text
Request
   ↓
Route
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
   ↓
Service
   ↓
Token generation
   ↓
Controller
   ↓
Response
```

# 3. Why login needs several layers

A beginner might write:

```js
router.post("/login", async (req, res) => {
    const user = await User.findOne({
        email: req.body.email
    });

    const valid = await bcrypt.compare(
        req.body.password,
        user.password
    );

    const token = jwt.sign(...);

    res.json({ token });
});
```

It may work.

But we've put everything into one place:

```text
HTTP
Database
Password verification
JWT
Business logic
Response
```

That's exactly the kind of **fat controller** our architecture is trying to avoid.

Instead:

```text
Controller
     ↓
authService.login()
     ↓
repository
```

The project roadmap describes the same professional separation: the controller should delegate to `authService.login()` rather than directly performing database and authentication operations.

---

# 4. Login begins at the route

We might have:

```js
router.post(
    "/login",
    validate(loginSchema),
    authController.login
);
```

The route answers:

> "Which code handles `POST /login`?"

It doesn't answer:

> "How do we authenticate the user?"

That's the service's job.

---

# 5. Validation happens first

Before authentication logic:

```text
Request
   ↓
Validation
```

Suppose the client sends:

```json
{
  "email": "hello",
  "password": ""
}
```

The validation layer should reject this.

```text
Invalid request
       ↓
400 Bad Request
```

We shouldn't unnecessarily query MongoDB.

So:

```text
                    LOGIN
                      │
                      ▼
                  Validation
                      │
               ┌──────┴──────┐
               ▼             ▼
             Invalid        Valid
               │             │
              400            ▼
                         Controller
```

This follows the trust-boundary architecture you've already learned in Phase 9.

---

# 6. Controller

After validation:

```js
export const login = asyncHandler(async (req, res) => {
    const { email, password } = req.body;

    const result = await authService.login({
        email,
        password
    });

    return res.status(200).json({
        success: true,
        message: "Login successful",
        data: result
    });
});
```

Notice how small the controller is.

It does four things:

```text
1. Read HTTP input
2. Call service
3. Receive result
4. Send HTTP response
```

That's it.

---

# 7. Controller → Service

The controller calls:

```js
authService.login({
    email,
    password
});
```

Now the service owns the authentication workflow.

The service needs to answer:

```text
Does this user exist?
       ↓
Does the password match?
       ↓
Should authentication succeed?
       ↓
What credentials should be issued?
```

---

# 8. The login service

Conceptually:

```js
export const login = async ({ email, password }) => {
    const user =
        await userRepository.findByEmailWithPassword(email);

    if (!user) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    const passwordValid =
        await verifyPassword(
            password,
            user.password
        );

    if (!passwordValid) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    // Token generation comes next.

    return {
        user
    };
};
```

The important thing is the order.

```text
Find user
   ↓
Verify password
   ↓
Authentication successful
```

---

# 9. Why does the repository need the password?

Earlier we discussed:

```js
password: {
    select: false
}
```

This is a useful protection because normal queries shouldn't casually return password hashes.

But login specifically needs the password hash.

So our repository can have a dedicated method:

```js
findByEmailWithPassword(email)
```

Conceptually:

```text
Normal user query
     ↓
password excluded

Authentication query
     ↓
password explicitly included
```

This is a great example of the repository pattern helping security.

---

# 10. Repository

Conceptually:

```js
export const findByEmailWithPassword = async (email) => {
    return User
        .findOne({ email })
        .select("+password");
};
```

Now the repository is responsible for:

```text
"How do I retrieve this user from MongoDB?"
```

It isn't responsible for:

```text
bcrypt
JWT
HTTP
cookies
login rules
```

---

# 11. MongoDB returns the user

Suppose MongoDB contains:

```json
{
  "_id": "123",
  "email": "rahul@example.com",
  "password": "$2b$12$...................",
  "role": "user"
}
```

The repository returns that user to the service.

Now:

```text
Repository
    ↓
User
    ↓
Service
```

---

# 12. First authentication check: user exists

The service checks:

```js
if (!user) {
    throw new UnauthorizedError(
        "Invalid credentials"
    );
}
```

Why `401`?

Because the request hasn't successfully authenticated.

Conceptually:

```text
Unknown user
     ↓
Authentication failed
     ↓
401 Unauthorized
```

---

# 13. Second authentication check: password

Now:

```js
const passwordValid = await bcrypt.compare(
    password,
    user.password
);
```

Remember:

```text
User enters:
Rahul@123

Stored:
$2b$12$...................

             ↓

bcrypt.compare()

             ↓

         true / false
```

If:

```js
passwordValid === false
```

then:

```js
throw new UnauthorizedError(
    "Invalid credentials"
);
```

---

# 14. Why use the same error?

Don't do:

```text
Email doesn't exist
```

for one case and:

```text
Wrong password
```

for the other.

Instead:

```text
Invalid credentials
```

for both.

So:

```text
Unknown email
    ↓
Invalid credentials

Wrong password
    ↓
Invalid credentials
```

This prevents unnecessary account-enumeration information.

---

# 15. Successful authentication

Now suppose:

```js
passwordValid === true
```

The service has established:

```text
This user knows the correct password.
```

So:

```text
Authentication successful
```

But we're not finished.

The user needs a way to prove authentication on **future requests**.

That's where tokens enter.

---

# 16. The next stage: credentials

Our roadmap eventually wants:

```text
generateAccessToken()
generateRefreshToken()
```

and then:

```text
bcrypt.hash(refreshToken)
```

before storing the refresh-token hash in MongoDB.

So successful login eventually becomes:

```text
Verify password
      ↓
Generate access token
      ↓
Generate refresh token
      ↓
Hash refresh token
      ↓
Store hash
      ↓
Return authentication result
```

We'll study each piece separately in the next lessons.

---

# 17. Why don't we generate tokens before checking the password?

Never do this:

```text
Find user
   ↓
Generate JWT
   ↓
Check password
```

Instead:

```text
Find user
   ↓
Verify password
   ↓
Authentication successful
   ↓
Generate credentials
```

Because issuing an authentication credential means:

> "This person has successfully authenticated."

Therefore token creation must come **after** successful credential verification.

# 20. What should the client receive?

After successful authentication, we don't want to return the entire MongoDB document.

For example, don't return:

```json
{
  "_id": "123",
  "email": "rahul@example.com",
  "password": "$2b$12$...",
  "role": "user"
}
```

Instead, return a safe public representation:

```json
{
  "id": "123",
  "email": "rahul@example.com",
  "role": "user"
}
```

Then authentication credentials are handled separately.

For example, conceptually:

```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "user": {
      "id": "123",
      "email": "rahul@example.com",
      "role": "user"
    },
    "accessToken": "..."
  }
}
```

The refresh-token handling will be discussed when we reach refresh tokens and cookies.

---

# 21. What should NEVER be returned?

Never return:

```text
Plain password
```

Obviously.

But also avoid returning:

```text
Password hash
Refresh token
Refresh token hash
Reset token
Internal security fields
```

unless there is a very specific reason.

A good rule:

> **Return only the information the frontend actually needs.**

# 22. Login service before tokens

At this stage, our service can look like:

```js
export const login = async ({ email, password }) => {
    const user =
        await userRepository.findByEmailWithPassword(email);

    if (!user) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    const passwordValid =
        await verifyPassword(
            password,
            user.password
        );

    if (!passwordValid) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    return {
        user: {
            id: user._id,
            email: user.email,
            role: user.role
        }
    };
};
```

Notice:

```text
No HTTP
No res.json()
No req.body
No MongoDB query
No JWT implementation
```

That's a clean service.

# 23. Why normalize email?

Suppose one person signs up with:

```text
Rahul@Example.com
```

and later tries:

```text
rahul@example.com
```

Depending on your application's rules, you may want emails normalized consistently.

For example:

```text
Input
 ↓
Trim whitespace
 ↓
Normalize case
 ↓
Database
```

Conceptually:

```js
const normalizedEmail = email
    .trim()
    .toLowerCase();
```

Then use the normalized value consistently.

This should be part of your input/business rules rather than something randomly repeated throughout controllers.

# 25. What if the account is disabled?

Real applications often need account state.

For example:

```text

├── email
├── password
├── role
└── status
```

Possible statuses:

```text

```

Then login might eventually become:

```text
Find user
   ↓
Does user exist?
   ↓
Is account active?
   ↓
Verify password
   ↓
Generate credentials
```

This is business logic, which belongs in the service layer.

```text

   ↓
Check account status
   ↓
```

```text
     │
```

# 30. The important difference between signup and login

### Signup

The password is **new**.

Therefore:

```text
Password
 ↓
bcrypt.hash()
 ↓
Store hash
```

### Login

The password already exists in the database as a hash.

Therefore:

```text
Password
 +
Stored hash
 ↓
bcrypt.compare()
 ↓
true / false
```

Remember:

```text
CREATE PASSWORD → hash
VERIFY PASSWORD → compare
```
