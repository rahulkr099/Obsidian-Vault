# Lesson 14.7 — JWT Fundamentals 🔑

Now we reach one of the most important parts of authentication.

In the previous lessons, we solved this problem:

> **How do we verify that the password is correct?**

With bcrypt:

```text
Email + Password
       ↓
Find User
       ↓
bcrypt.compare()
       ↓
Password correct
```

But there's a new problem:

> **How does the server know that the user is authenticated on the next request?**

That's where **JWTs** come in.

---

# 1. The problem after login

Imagine Rahul logs in:

```http
POST /api/v1/auth/login
```

```json
{
  "email": "rahul@example.com",
  "password": "Rahul@123"
}
```

The server verifies:

```text
Password
   ↓
bcrypt.compare()
   ↓
true
```

Great.

But now Rahul makes another request:

```http
GET /api/v1/users/me
```

How does the server know:

```text
"This request belongs to Rahul."
```

HTTP itself doesn't remember previous requests.

Each request is independent.

```text
Request 1 → Login
Request 2 → Get profile
Request 3 → Update profile
Request 4 → Get courses
```

The server needs some kind of **authentication credential** that the client can send with future requests.

---

# 2. What is JWT?

JWT stands for:

> **JSON Web Token**

A JWT is a compact token that can carry claims about a user/session and can be cryptographically signed.

Conceptually:

```text
Login successful
      ↓
Create JWT
      ↓
Send JWT to client
      ↓
Client sends JWT with future requests
      ↓
Server verifies JWT
      ↓
Request is authenticated
```

So:

```text
Password
   ↓
bcrypt
   ↓
Authentication
   ↓
JWT
   ↓
Future requests
```

---

# 3. JWT is not a password hash

This distinction is extremely important.

We have:

```text
Password
   ↓
bcrypt
   ↓
Password Hash
```

And:

```text
Authenticated User
   ↓
JWT
   ↓
Authentication Credential
```

These solve different problems.

### bcrypt

Protects the stored password.

### JWT

Can represent an authenticated session/request credential.

Don't mix these concepts.

---

# 4. Basic authentication flow

The overall flow becomes:

```text
                    LOGIN
                      │
                      ▼
               Email + Password
                      │
                      ▼
                 Find User
                      │
                      ▼
              bcrypt.compare()
                      │
                      ▼
                 Password OK
                      │
                      ▼
                Create JWT
                      │
                      ▼
                  Client
```

Then:

```text
                   NEXT REQUEST
                       │
                       ▼
                  Send JWT
                       │
                       ▼
                  Server
                       │
                       ▼
                Verify JWT
                       │
                       ▼
              Identify User
                       │
                       ▼
               Allow Request
```

That's the basic idea.

---

# 5. A JWT looks strange

A JWT often looks something like:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiIxMjMiLCJyb2xlIjoidXNlciJ9
.
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

There are **three parts**:

```text
HEADER.PAYLOAD.SIGNATURE
```

This is extremely important.

---

# 6. JWT structure

A JWT has:

```text
┌────────────┐
│   Header   │
├────────────┤
│  Payload   │
├────────────┤
│ Signature  │
└────────────┘
```

Written as:

```text
HEADER.PAYLOAD.SIGNATURE
```

For example:

```text
eyJhbGciOiJIUzI1NiJ9
.
eyJzdWIiOiIxMjMifQ
.
abc123...
```

Let's understand each part.

---

# 7. Header

The header contains information about the token.

Conceptually:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

`alg` tells us which signing algorithm is being used.

`typ` tells us this is a JWT.

So:

```text
Header
  ↓
How should this token be interpreted?
```

---

# 8. Payload

The payload contains **claims**.

For example:

```json
{
  "sub": "user123",
  "role": "user"
}
```

You might also have:

```json
{
  "sub": "user123",
  "role": "admin",
  "iat": 1750000000,
  "exp": 1750003600
}
```

The payload is information about the token/user/session.

---

# 9. Very important: JWT payload is NOT secret

This is one of the biggest JWT misconceptions.

A normal signed JWT is **not encrypted**.

That means someone who possesses the token can generally decode the header and payload.

For example, if your JWT contains:

```json
{
  "sub": "123",
  "email": "rahul@example.com"
}
```

don't assume:

> "Nobody can see this."

They potentially can.

Therefore:

### Never put secrets in a JWT payload.

Don't put:

```json
{
  "password": "Rahul@123"
}
```

Absolutely not.

Also avoid putting unnecessary sensitive information into tokens.

---

# 10. Then why is JWT secure?

The important part is the **signature**.

A signed JWT allows the server to detect whether the token has been modified.

Conceptually:

```text
Header
   +
Payload
   +
Secret/key
   ↓
Signing algorithm
   ↓
Signature
```

The server can later verify:

```text
Header
   +
Payload
   +
Signature
   ↓
Verification
   ↓
Valid / Invalid
```

So JWT's signature provides **integrity/authenticity**, not confidentiality.

This distinction is extremely important:

```text
JWT signing
    ↓
Detect modification

JWT encryption
    ↓
Hide contents
```

A normal JWT is generally about the first one.

---

# 11. Example of tampering

Suppose the original payload says:

```json
{
  "sub": "123",
  "role": "user"
}
```

An attacker tries to change it to:

```json
{
  "sub": "123",
  "role": "admin"
}
```

The signature no longer matches the modified payload.

The server verifies:

```text
Modified payload
      +
Original signature
      ↓
Verification fails
```

Therefore:

```text
401 Unauthorized
```

assuming your authentication middleware handles it that way.

---

# 12. The signature is the important security boundary

Conceptually:

```text
                    JWT
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
     Header        Payload      Signature
                                    │
                                    ▼
                              Server verifies
```

An attacker may be able to **read** the payload.

But without the appropriate signing key, they shouldn't be able to create a valid modified token.

---

# 13. JWT and stateless authentication

One reason JWTs are popular is that the server can verify a token without necessarily looking up a session record for every request.

For example:

```text
Request
   ↓
JWT
   ↓
Verify signature
   ↓
Read claims
   ↓
Authenticated
```

This is often called **stateless authentication**.

But be careful:

> JWT does not automatically make your entire authentication system stateless.

Once you introduce refresh-token storage, revocation, rotation, logout state, sessions, etc., you may have server-side authentication state too.

Your roadmap intentionally introduces refresh-token persistence later.

---

# 14. What is a claim?

A **claim** is a piece of information carried by the JWT.

For example:

```json
{
  "sub": "user123"
}
```

means:

```text
sub = subject
```

Usually, the subject identifies the entity associated with the token.

You may also see registered claims such as:

```text
iss
sub
aud
exp
nbf
iat
jti
```

Don't try to memorize all of them yet.

The important ones for our authentication system will include:

```text
sub
iat
exp
jti
```

---

# 15. `sub`

`sub` means:

> **Subject**

For an access token, it can identify the user.

Example:

```json
{
  "sub": "66c123abc..."
}
```

Then authentication middleware can conceptually do:

```text
JWT
 ↓
sub = user ID
 ↓
req.user = ...
```

This is one of the most common JWT patterns.

---

# 16. `iat`

`iat` means:

> **Issued At**

It represents when the token was issued.

Conceptually:

```json
{
  "iat": 1750000000
}
```

The JWT library can often generate this automatically.

You don't always need to manually add it.

---

# 17. `exp`

`exp` means:

> **Expiration Time**

Example:

```json
{
  "sub": "123",
  "exp": 1750003600
}
```

After the expiration time:

```text
JWT
 ↓
Expired
 ↓
Authentication rejected
```

This is very important because authentication credentials shouldn't normally live forever.

---

# 18. Why expiration matters

Imagine a token that never expires:

```text
Login
 ↓
Token
 ↓
Valid forever
```

If someone steals it:

```text
Token stolen
 ↓
Attacker
 ↓
Potentially authenticated indefinitely
```

Instead:

```text
Login
 ↓
Short-lived access token
 ↓
Expires
```

Then the application can use a refresh-token mechanism to obtain new access tokens.

We'll learn that later.

---

# 19. `jti`

`jti` means:

> **JWT ID**

It can uniquely identify a particular token.

For example:

```json
{
  "sub": "123",
  "jti": "a9f3..."
}
```

This becomes useful in more advanced token-management scenarios such as:

```text
Token tracking
Revocation
Auditing
Refresh-token management
```

We won't need to use it everywhere.

---

# 20. What should our access-token payload contain?

For our starter project, keep the payload small.

Conceptually:

```json
{
  "sub": "userId",
  "role": "user"
}
```

Possibly with:

```text
iat
exp
```

generated by the JWT library.

Avoid stuffing the entire user document into the token.

Don't do:

```json
{
  "id": "123",
  "email": "rahul@example.com",
  "password": "...",
  "address": "...",
  "phone": "...",
  "preferences": "...",
  "everything": "..."
}
```

JWTs should contain only the claims needed for authentication/authorization.

---

# 21. JWT is not a database

A JWT should not become:

```text
"Let's put our entire user database inside the token."
```

Instead:

```text
JWT
 ↓
Small authentication claims
```

For example:

```json
{
  "sub": "123",
  "role": "user"
}
```

Then, if the application needs more user information:

```text
JWT
 ↓
user ID
 ↓
Repository
 ↓
MongoDB
 ↓
User information
```

Whether you need that database lookup depends on the operation.

---

# 22. Creating a JWT

In Node.js, a common library is `jsonwebtoken`.

Install:

```bash
npm install jsonwebtoken
```

Then:

```js
import jwt from "jsonwebtoken";
```

A basic example:

```js
const token = jwt.sign(
    {
        sub: user.id
    },
    process.env.JWT_ACCESS_SECRET,
    {
        expiresIn: "15m"
    }
);
```

Conceptually:

```text
User ID
  +
Secret
  +
Expiration
  ↓
jwt.sign()
  ↓
Access Token
```

---

# 23. Never hardcode the secret

Do NOT do:

```js
const token = jwt.sign(
    { sub: user.id },
    "my-secret-password"
);
```

Instead:

```js
const token = jwt.sign(
    { sub: user.id },
    process.env.JWT_ACCESS_SECRET,
    {
        expiresIn: "15m"
    }
);
```

The secret belongs in your environment/configuration management.

For example:

```env
JWT_ACCESS_SECRET=very-long-random-secret
```

And your `.env` file should not be committed to Git.

This connects directly to the secrets-management topics in Phase 14.

---

# 24. Don't use the same secret everywhere

Later we'll have:

```text
Access token
Refresh token
```

Don't casually use one generic secret like:

```env
JWT_SECRET=...
```

for everything.

A better architecture can separate signing keys/secrets according to the credential type and algorithm design.

For example:

```env
JWT_ACCESS_SECRET=...
JWT_REFRESH_SECRET=...
```

We'll discuss the exact setup later.

---

# 25. Creating the access token

A utility might eventually look like:

```js
import jwt from "jsonwebtoken";

export const generateAccessToken = (user) => {
    return jwt.sign(
        {
            sub: user.id,
            role: user.role
        },
        process.env.JWT_ACCESS_SECRET,
        {
            expiresIn: "15m"
        }
    );
};
```

Then:

```js
const accessToken = generateAccessToken(user);
```

This keeps token-generation details out of your controller.

---

# 26. Why use a utility?

Without a utility, you might repeat:

```js
jwt.sign(...)
```

in several places.

For example:

```text
auth.service.js
admin.service.js
refresh.service.js
```

Instead:

```text
Token Utility
     │
     ├── generateAccessToken()
     └── generateRefreshToken()
```

Then your service simply says:

```js
const accessToken = generateAccessToken(user);
```

The project roadmap explicitly includes dedicated JWT utility work.

# 27. Login flow now becomes clearer

We've learned:

```text
Email + Password
       ↓
Find User
       ↓
bcrypt.compare()
       ↓
Password correct
       ↓
generateAccessToken()
       ↓
Access Token
```

So the service might eventually look like:

```js
export const login = async ({ email, password }) => {
    const user =
        await userRepository.findByEmailWithPassword(email);

    if (!user) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    const valid = await verifyPassword(
        password,
        user.password
    );

    if (!valid) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    const accessToken =
        generateAccessToken(user);

    return {
        accessToken,
        user: sanitizeUser(user)
    };
};
```

We'll improve this further when refresh tokens enter the picture.

# 28. How does the next request work?

Suppose login returns:

```json
{
  "accessToken": "eyJhbGciOi..."
}
```

The frontend then calls:

```http
GET /api/v1/users/me
Authorization: Bearer eyJhbGciOi...
```

Now the server receives:

```text
Authorization
      ↓
Bearer token
      ↓
Extract JWT
      ↓
Verify JWT
      ↓
Read user identity
      ↓
Continue request
```

This is the foundation of **authentication middleware**.

---

# 29. Bearer token

You will commonly see:

```http
Authorization: Bearer <token>
```

Why "Bearer"?

The basic meaning is:

> Whoever bears/presents this credential is presenting it as their authentication credential.

So:

```http
Authorization: Bearer eyJ...
```

means:

```text
Authorization scheme = Bearer
Credential = JWT
```

Your middleware can extract the token after `Bearer`.

---

# 30. JWT verification

On a protected route:

```text
GET /api/v1/users/me
```

middleware might eventually do:

```js
const token = extractBearerToken(req);

const payload = jwt.verify(
    token,
    process.env.JWT_ACCESS_SECRET
);
```

If valid:

```text
JWT valid
 ↓
payload available
 ↓
Authenticated request
```

If invalid:

```text
JWT invalid
 ↓
401 Unauthorized
```

---

# 31. `jwt.decode()` vs `jwt.verify()`

This is a very important distinction.

You might see:

```js
jwt.decode(token);
```

and:

```js
jwt.verify(token, secret);
```

They are **not equivalent**.

### `decode()`

Essentially:

```text
Read token contents
```

It doesn't prove that the token is authentic.

### `verify()`

Checks the signature and relevant token constraints.

So for authentication:

```text
❌ jwt.decode()
```

is not enough.

Use:

```text
✅ jwt.verify()
```

when you need to authenticate the token.

---

# 32. Why decoding alone is dangerous

Imagine an attacker changes:

```json
{
  "sub": "123",
  "role": "user"
}
```

to:

```json
{
  "sub": "123",
  "role": "admin"
}
```

If your middleware only does:

```js
jwt.decode(token)
```

it could blindly trust the modified payload.

That's terrible.

Verification is essential:

```js
jwt.verify(token, secret);
```

---

# 33. Signature verification

Conceptually:

```text
Received JWT
      │
      ▼
Split:
Header.Payload.Signature
      │
      ▼
Verify signature
      │
   ┌──┴──┐
   ▼     ▼
Valid   Invalid
   │       │
   ▼       ▼
Continue   401
```

This is the core job of authentication middleware.

---

# 34. JWT doesn't automatically mean authorization

This distinction is also important.

### Authentication

> Who are you?

JWT can help answer:

```text
User ID = 123
```

### Authorization

> Are you allowed to do this?

For example:

```text
role = user
```

trying:

```http
DELETE /api/v1/admin/users/123
```

The JWT may be valid, but the user may not have permission.

So:

```text
Valid JWT
   ≠
Permission to perform every action
```

Authentication and authorization are different.

---

# 35. Access token vs refresh token

Don't worry about implementation yet, but understand the conceptual difference.

### Access token

Used frequently:

```text
API request
 ↓
Access token
 ↓
Protected resource
```

Usually short-lived.

For example:

```text
15 minutes
```

### Refresh token

Used to obtain a new access token:

```text
Refresh token
      ↓
New access token
```

Usually longer-lived and protected more carefully.

Your roadmap explicitly separates access-token and refresh-token design.

---

# 36. Why short-lived access tokens?

Suppose:

```text
Access token lifetime = 15 minutes
```

If stolen:

```text
Attacker
 ↓
Stolen token
 ↓
Limited validity window
```

That's better than:

```text
Access token
 ↓
Valid for 30 days
```

The shorter lifetime reduces the window in which a stolen access token can be abused.

But short expiration creates another problem:

> Users shouldn't have to log in every 15 minutes.

That's why refresh tokens exist.

# 37. The authentication system we're building

Eventually:

```text
                       LOGIN
                         │
                         ▼
                   Verify password
                         │
                         ▼
                ┌────────┴────────┐
                ▼                 ▼
          Access Token       Refresh Token
          short-lived        long-lived
                │                 │
                │                 ▼
                │          Stored/managed
                │            securely
                │
                ▼
          API Requests
                │
                ▼
        Authentication
```

Then:

```text
Access token expires
       ↓
Refresh token
       ↓

```

We'll build this gradually.

# 38. JWT payload should be minimal

A good payload might be:

```js
{
    sub: user.id,
    role: user.role
}
```

A bad payload:

```js
{
    sub: user.id,
    email: user.email,
    password: user.password,
    address: user.address,
    phone: user.phone,
    creditCard: user.creditCard
}
```

The second design creates unnecessary exposure.

Remember:

> **A signed JWT is readable by whoever possesses it.**

---

# 39. JWT is not a session database

Don't think:

```text
JWT = user record
```

Think:

```text
JWT = signed authentication credential
```

The database remains the source of persistent application state.

For example:

```text
MongoDB
 ├── user
 ├── role
 ├── account status
 └── refresh-token state
```

JWT:

```text
sub
role
iat
exp
...
```

These serve different purposes.

---

# 40. A useful analogy

Imagine entering an office.

### Password

Your password is like proving your identity at the reception desk.

```text
Password
 ↓
Verification
 ↓
You're authenticated
```

### Access token

Reception gives you a temporary access badge:

```text
Authenticated
 ↓
Temporary badge
```

You use the badge to enter rooms:

```text
API requests
 ↓
Access token
 ↓
Protected resources
```

### Refresh token

A longer-lived credential lets you obtain a new temporary badge when the old one expires.

```text
Old badge expired
       ↓
Refresh credential
       ↓
New badge
```

This is the mental model we'll use.

Our architecture now looks like:

  ├── Repository

# 42. Don't put JWT logic in the repository

The repository should not do:

```js
jwt.sign(...)
```

The repository is for persistence.

Similarly, don't make the controller responsible for:

```js
bcrypt.compare(...)
jwt.sign(...)
User.findOne(...)
```

Instead:

```text
Controller
   ↓
Service
   ├── bcrypt
   ├── repository
   └── token utility
```

---

# 43. JWT secret security

The signing key is extremely sensitive.

If an attacker obtains the signing secret, they may be able to create valid tokens.

That's why:

```env
JWT_ACCESS_SECRET=...
```

must be protected.

Don't:

```js
const secret = "hello123";
```

Don't commit:

```text
.env
```

to Git.

Don't put secrets in:

```text
Frontend JavaScript
JWT payload
Public GitHub repository
Logs
Error messages
```

---

# 44. Environment variables aren't magic security

One subtle point:

```env
JWT_ACCESS_SECRET=abc123
```

being in `.env` doesn't automatically make it secure.

You still need:

```text
Strong random secret
+
Secure secret storage
+
Correct permissions
+
No accidental logging
+
No Git commits
```

Later in Phase 14 we'll cover proper secret management.

---

# 45. What if the JWT is expired?

`jwt.verify()` can detect expiration if the token contains an `exp` claim.

Conceptually:

```text
Token
 ↓
Signature valid?
 ↓
Expiration valid?
 ↓
Yes → continue
No  → reject
```

So:

```text
Expired JWT
    ↓
401 Unauthorized
```

The client can then use its refresh mechanism.

---

# 46. What if the JWT signature is invalid?

For example:

```text
Attacker modifies payload
        ↓
Signature no longer matches
        ↓
jwt.verify()
        ↓
FAIL
        ↓
401
```

This is why we verify the signature rather than simply decoding the token.

# 50. One important future improvement

As we progress, we should avoid scattering strings like:

```js
"15m"
```

throughout the codebase.

Instead, centralized configuration can eventually contain:

```js
auth: {
    accessTokenExpiresIn: "15m",
    refreshTokenExpiresIn: "7d"
}
```

Then:

```js
generateAccessToken(user)
```

uses configuration.

This makes changing security policy much easier.

# 🔑 Today's core mental model

Don't think:

> **"JWT is an encrypted user object."**

Think:

> **"JWT is a signed authentication credential containing a small set of claims."**

The complete idea is:

```text
                 LOGIN
                   │
                   ▼
             Verify password
                   │
                   ▼
            Generate JWT
                   │
                   ▼
              Access Token
                   │
                   ▼
             Future Request
                   │
                   ▼
            jwt.verify()
                   │
                   ▼
             Identify User
                   │
                   ▼
          Protected Resource
```

And remember these three words:

```text
JWT = Header + Payload + Signature
```
