# Lesson 14.9 — Access Tokens 🔐

In **14.7**, we learned what JWT is.  
In **14.8**, we learned about the JWT payload and claims.

Now we answer a practical question:

> **What exactly is an access token, and how does our backend use it to protect API routes?**

Your roadmap places **Access Tokens** immediately after JWT fundamentals and payload, before refresh tokens, expiration, authorization headers, and cookies.

---

# 1. What is an access token?

An **access token** is a credential that the client presents to the backend when accessing protected resources.

Simple flow:

```text
Login
  ↓
Credentials verified
  ↓
Access token generated
  ↓
Client receives token
  ↓
Client requests protected API
  ↓
Client sends access token
  ↓
Server verifies token
  ↓
Request allowed
```

Think of it as a **temporary API access pass**.

---

# 2. Access token vs JWT

These terms are related, but they aren't exactly the same thing.

### JWT

Describes a **token format**.

```text
Header.Payload.Signature
```

### Access token

Describes the **purpose of a token**.

```text
Used to access protected resources
```

Therefore:

> A JWT can be used as an access token.

In our backend, that's exactly what we're building.

```text
JWT
 ↓
Used as
 ↓
Access Token
```

# 3. The complete login flow

Let's imagine Rahul sends:

```http
POST /api/v1/auth/login
```

with:

```json
{
  "email": "rahul@example.com",
  "password": "Rahul@123"
}
```

Our architecture:

```text
Request
   ↓
Route
   ↓
Validation
   ↓
Controller
   ↓
authService.login()
   ↓
Repository
   ↓
MongoDB
```

The user is found.

Then:

```text
Password
   ↓
bcrypt.compare()
   ↓
Valid
```

Then:

```text
User authenticated
       ↓
Generate access token
       ↓
Return token
```

# 4. Access token generation

Conceptually:

```js
const accessToken = generateAccessToken(user);
```

The token utility might eventually do:

```js
jwt.sign(
    {
        sub: user.id,
        role: user.role
    },
    process.env.JWT_ACCESS_SECRET,
    {
        expiresIn: "15m"
    }
);
```

So:

```text
user
 ↓
generateAccessToken()
 ↓
JWT
 ↓
accessToken
```

---

# 5. What should an access token contain?

Keep it small.

For our application, a simple payload could be:

```json
{
  "sub": "user123",
  "role": "user"
}
```

And the JWT system can include:

```text
iat
exp
```

as appropriate.

So conceptually:

```text
ACCESS TOKEN
│
├── sub
├── role
├── iat
└── exp
```

Don't put the entire user object inside it.

---

# 6. Why is the access token short-lived?

An access token is usually designed to have a relatively short lifetime.

For example:

```text
15 minutes
```

Why?

Because the access token is sent frequently.

```text
GET /users/me
GET /todos
POST /todos
PATCH /todos/123
DELETE /todos/123
```

If somebody steals the token, we want to limit how long it remains useful.

```text
Stolen access token
       ↓
Limited lifetime
       ↓
Eventually expires
```

We'll study expiration in detail in **14.11**.

---

# 7. Access token lifecycle

Think of the access token as having a lifecycle:

```text
              CREATE
                │
                ▼
             ACTIVE
                │
          API requests
                │
                ▼
             EXPIRE
                │
                ▼
             INVALID
```

More realistically:

```text
Login
  ↓
Access Token
  ↓
Use for API requests
  ↓
Expires
  ↓
Refresh mechanism
  ↓
New Access Token
```

The refresh-token part comes in **14.10**.

---

# 8. What happens after login?

Suppose the server responds:

```json
{
  "success": true,
  "data": {
    "accessToken": "eyJhbGciOi..."
  }
}
```

The frontend now has an access token.

For future protected API requests, it needs to present that credential.

This leads us to:

```text
Authorization: Bearer <access-token>
```

We'll study the Authorization header formally in **14.12**.

---

# 9. Protected API example

Suppose we have:

```http
GET /api/v1/users/me
```

This route requires authentication.

The request can eventually look like:

```http
GET /api/v1/users/me
Authorization: Bearer eyJhbGciOi...
```

The backend receives:

```text
Request
  ↓
Authorization header
  ↓
Bearer token
  ↓
Extract token
  ↓
Verify token
  ↓
Authenticated
```

---

# 10. Access token is not authorization by itself

This is an important distinction.

Suppose a user has a valid access token.

That proves:

```text
Authentication
```

It does **not automatically mean**:

```text
User can perform every operation
```

For example:

```text
Valid access token
       ↓
User = Rahul
       ↓
Role = user
       ↓
DELETE /admin/users/123
       ↓
Not authorized
```

So:

```text
Authentication
=
Who are you?

Authorization
=
What are you allowed to do?
```

We'll study authorization in Phase 15.

---

# 11. Access token and `req.user`

Eventually, our authentication middleware will do something like:

```text
Authorization header
        ↓
Extract JWT
        ↓
Verify JWT
        ↓
Read payload
        ↓
Create authenticated user context
        ↓
req.user
```

For example:

```js
req.user = {
    id: payload.sub,
    role: payload.role
};
```

Then your controller can use:

```js
req.user.id
```

instead of trying to decode the token itself.

---

# 12. Why middleware should handle the access token

Imagine every controller had this:

```js
const token = extractToken(req);

const payload = jwt.verify(
    token,
    process.env.JWT_ACCESS_SECRET
);
```

Then:

```text
user.controller.js
todo.controller.js
course.controller.js
admin.controller.js
```

would all duplicate authentication logic.

Bad architecture.

Instead:

```text
Request
   ↓
authMiddleware
   ↓
Controller
```

The controller receives an already-authenticated request.

Your starter's planned authentication middleware follows exactly this idea: extract the Bearer token, verify JWT, establish user information, and continue with `next()`.

---

# 13. The middleware boundary

This is a very useful architectural boundary:

```text
                    HTTP REQUEST
                         │
                         ▼
                ┌────────────────┐
                │ authMiddleware │
                └───────┬────────┘
                        │
                  JWT verified
                        │
                        ▼
                   req.user
                        │
                        ▼
                   Controller
```

The controller doesn't need to know:

```text
How was the JWT extracted?
How was the signature verified?
Which secret was used?
Was the token expired?
```

Authentication middleware handles that.

---

# 14. Access token and database

A JWT access token can be verified cryptographically without necessarily querying MongoDB for every request.

For example:

```text
Request
 ↓
JWT
 ↓
Signature verification
 ↓
Claims
 ↓
Authenticated
```

This is one reason JWT-based authentication is often called **stateless authentication**.

But don't overgeneralize this.

Our overall authentication system will eventually have persistent refresh-token state in MongoDB.

The roadmap specifically describes storing a hashed refresh token and updating/clearing it through the repository layer.

---

# 15. Why not store access tokens in MongoDB?

A beginner might think:

```text
Login
 ↓
Create JWT
 ↓
Store JWT in MongoDB
```

For a simple JWT access-token design, this usually defeats much of the point of using a stateless access token.

Instead:

```text
Login
 ↓
Generate access token
 ↓
Send to client
```

The server verifies its signature later.

The refresh-token system is where persistent server-side state becomes much more important.

---

# 16. Access token vs refresh token

This distinction is fundamental.

|Access Token|Refresh Token|
|---|---|
|Short-lived|Long-lived|
|Used for API requests|Used to obtain new access token|
|Sent frequently|Used less frequently|
|Needs quick verification|Needs stronger lifecycle management|
|Usually JWT in our design|Can be an opaque/random token or JWT depending on design|
|Limited lifetime|Longer lifetime|

Our roadmap explicitly recommends:

```text
Access Token
    ↓
Authorization header

Refresh Token
    ↓
HttpOnly cookie
```

Don't worry about the cookie side yet; that comes later.

---

# 17. Why not make the access token last 7 days?

Imagine:

```text
Access token = 7 days
```

Then:

```text
Attacker steals token
       ↓
Token remains useful
       ↓
Potentially for days
```

Instead:

```text
Access token = 15 minutes
```

Then:

```text
Attacker steals token
       ↓
Smaller validity window
```

This is one of the reasons we separate access and refresh tokens.

---

# 18. Why not make it 10 seconds?

You could theoretically make the access token extremely short-lived.

But then:

```text
Token expires
   ↓
Refresh
   ↓
New token
   ↓
Token expires
   ↓
Refresh
```

would happen constantly.

That creates unnecessary complexity and traffic.

So token lifetime is a balance between:

```text
Security
     +
Usability
     +
Operational cost
```

We'll discuss this tradeoff in 14.11.

---

# 19. What if the access token is stolen?

This is an important security scenario.

Suppose:

```text
Rahul
 ↓
Access token
 ↓
Attacker gets a copy
```

The attacker may be able to use it while it remains valid.

That's why we use multiple defenses:

```text
Short expiration
        +
HTTPS
        +
Secure token handling
        +
Refresh-token protection
        +
Good browser storage strategy
        +
Token rotation/revocation strategy
```

Later lessons will cover token theft, cookies, refresh-token hashing, rotation, and logout.

---

# 20. Access token does not automatically support logout

This is a subtle but very important point.

Suppose:

```text
Access token
expires in 15 minutes
```

User clicks:

```text
Logout
```

If the server has no state tracking that access token, the token may technically remain cryptographically valid until it expires.

That's why logout and token revocation require careful design.

The roadmap has a dedicated:

```text
14.18 Logout
14.19 Token theft
```

section.

So don't assume:

```text
logout()
=
JWT magically becomes invalid
```

It doesn't automatically work that way.

---

# 21. Access token should not contain the refresh token

Never do:

```json
{
  "sub": "123",
  "refreshToken": "very-long-secret-token"
}
```

Why?

Because you're placing a more sensitive credential inside another credential.

Instead, keep their responsibilities separate:

```text
Access token
 ↓
API access

Refresh token
 ↓
Obtain new access token
```

---

# 22. Access token should not contain passwords

Again:

```json
{
  "sub": "123",
  "password": "..."
}
```

❌ Never.

Also:

```json
{
  "sub": "123",
  "passwordHash": "$2b$..."
}
```

❌ Never.

JWT payloads should contain only the minimum information needed for the token's purpose.

---

# 23. Access token and user deletion

Imagine:

```text
User = 123
Access token = valid
```

Then an administrator deletes the user.

What happens?

The JWT itself doesn't know that MongoDB deleted the user.

This demonstrates an important limitation:

```text
JWT
 ↓
Self-contained credential
```

versus:

```text
Database
 ↓
Current application state
```

Depending on your security requirements, your authentication middleware or downstream service may need to check current user state.

For example:

```text
JWT valid
 ↓
User exists?
 ↓
Account active?
 ↓
Continue
```

The exact choice depends on the application's security and performance requirements.

---

# 24. Access token and account disabling

Similarly:

```text
Monday:
User active

Tuesday:
Admin disables account
```

An old JWT may still be cryptographically valid.

Therefore, a production authentication design needs to think about:

```text
Token validity
+
Current account state
+
Revocation
+
Expiration
```

Don't confuse:

> **"JWT signature is valid."**

with:

> **"This user is currently allowed to access the application."**

Those are related but different checks.

---

# 25. The access-token utility

A clean architecture can eventually have:

```text
utils/
├── generateAccessToken.js
└── generateRefreshToken.js
```

For example:

```js
import jwt from "jsonwebtoken";

export const generateAccessToken = (user) => {
    return jwt.sign(
        {
            sub: user.id,
            role: user.role
        },
        process.env.JWT_ACCESS_SECRET,
        {
            expiresIn: "15m"
        }
    );
};
```

Notice:

```text
Controller
    ↓
Service
    ↓
generateAccessToken()
```

Not:

```text
Controller
    ↓
jwt.sign()
```

---

# 26. Why token generation belongs outside the controller

Your controller should primarily translate HTTP into application operations.

For example:

```js
export const login = asyncHandler(async (req, res) => {
    const result = await authService.login(req.body);

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

The controller doesn't need to know:

```text
JWT algorithm
secret
expiration
claims
```

The service/token utility handles that.

This keeps the architecture consistent with the controller → service → repository pattern you've already learned.

---

# 27. Login service

Conceptually:

```js
export const login = async ({ email, password }) => {
    const user =
        await authRepository.findUserByEmail(email);

    if (!user) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    const valid = await verifyPassword(
        password,
        user.password
    );

    if (!valid) {
        throw new UnauthorizedError(
            "Invalid credentials"
        );
    }

    const accessToken =
        generateAccessToken(user);

    return {
        accessToken
    };
};
```

Later we'll add:

```text
refresh token
hashing
storage
cookies
rotation
```

Don't add all of that at once.

# 29. A useful distinction: authentication credential vs user data

The access token tells us something like:

```text
"Here is a credential associated with user 123."
```

It does **not** necessarily provide:

```text
User's complete profile
User's current settings
User's latest database state
```

Those are application data.

So:

```text
Access Token
      ↓
Identity/authentication context

Database
      ↓
Application state
```

Keeping these separate makes your system easier to reason about.

---

# 30. Access token security checklist

For our backend, remember:

```text
[✓] Short-lived
[✓] Signed
[✓] Small payload
[✓] Strong signing secret/key
[✓] Never contain password
[✓] Never contain refresh token
[✓] Verify before trusting
[✓] Send through protected transport
[✓] Don't log tokens
```

That last one is very important.

---

# 31. Never log the access token

Don't do:

```js
console.log("Access token:", accessToken);
```

Especially not in production.

Why?

Your logs may be accessible to:

```text
Developers
Operations
Monitoring systems
Log aggregation systems
Third-party platforms
```

A leaked token in logs can become an authentication incident.

So instead:

```js
console.log("Access token generated");
```

if you genuinely need diagnostic information.

Better yet, avoid unnecessary token logging entirely.

---

# 32. Don't return tokens in error messages

Avoid:

```json
{
  "error": "Invalid token: eyJhbGciOi..."
}
```

Instead:

```json
{
  "success": false,
  "message": "Invalid or expired access token"
}
```

Never expose the credential while reporting an authentication failure.

---

# 33. Access token and HTTPS

A good JWT implementation can still be undermined if the network connection isn't protected.

Imagine:

```text
Client
   ↓
HTTP
   ↓
Attacker intercepts token
```

That's a disaster.

We want:

```text
Client
   ↓
HTTPS/TLS
   ↓
Server
```

so credentials are protected in transit.

Production HTTPS and cookie security will be covered later in the roadmap.

---

# 34. Where the access token goes

The roadmap's recommended design is:

```text
Access Token
    ↓
Authorization header
```

and:

```text
Refresh Token
    ↓
HttpOnly cookie
```

That means we should conceptually separate their storage/transmission responsibilities.

We'll study the Authorization header in **14.12** and cookies in **14.13–14.15**.

---

# 35. Why this separation is useful

Imagine:

```text
Access Token
 ↓
Short lifetime
 ↓
API authorization
```

while:

```text
Refresh Token
 ↓
Longer lifetime
 ↓
Protected from JavaScript
 ↓
Used to obtain new access token
```

This creates a layered authentication design instead of relying on one permanent credential.
