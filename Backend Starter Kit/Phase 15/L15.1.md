# Lesson 15.1 — Authentication vs Authorization

This is the **first and most important concept of Phase 15**.

You already studied authentication in Phase 14. Now we need to clearly separate it from authorization.

Your backend will use both:

```text
Authentication
      ↓
"Who are you?"
      ↓
Authorization
      ↓
"What are you allowed to do?"
```

This separation is fundamental to secure backend development.

---

## 1. Authentication

**Authentication = proving your identity.**

Suppose you have:

```http
POST /api/v1/auth/login
```

You send:

```json
{
  "email": "rahul@example.com",
  "password": "password123"
}
```

The backend checks:

```text
Email exists?
      ↓
Password correct?
      ↓
YES
      ↓
Generate token
```

Now the server knows:

> This request belongs to Rahul.

That's authentication.

### Simple question

Authentication answers:

> **Who are you?**

---

# 2. Authorization

After authentication, the backend needs another answer:

> **What is Rahul allowed to do?**

Suppose your application has two users:

```text
Rahul
role = user

Admin
role = admin
```

Both successfully log in.

Therefore:

```text
Rahul → authenticated
Admin → authenticated
```

But perhaps only the admin can:

```http
DELETE /api/v1/users/123
```

So:

```text
Rahul
  ↓
Authenticated ✅
  ↓
Admin permission? ❌
  ↓
403 Forbidden
```

Whereas:

```text
Admin
  ↓
Authenticated ✅
  ↓
Admin permission? ✅
  ↓
Controller
```

That's authorization.

---

# 3. The Most Important Difference

Remember this:

|Authentication|Authorization|
|---|---|
|Who are you?|What can you do?|
|Identity|Permission|
|Login|Access control|
|JWT/session verification|Role/permission/ownership check|
|Usually happens first|Happens after identity is known|

Think:

```text
AUTHENTICATION
       ↓
      WHO?
       ↓
   Rahul

AUTHORIZATION
       ↓
      WHAT?
       ↓
Can Rahul delete this user?
```

---

# 4. Real-World Example

Imagine a college building.

You arrive at the gate.

### Step 1 — Identity

Security asks:

> "Show me your ID card."

You show your student ID.

They confirm:

```text
Name: Rahul
ID: 12345
```

This is:

```text
Authentication
```

They now know who you are.

---

### Step 2 — Permission

You want to enter the professor's office.

Security checks:

```text
Is Rahul allowed inside the professor's office?
```

If not:

```text
ACCESS DENIED
```

That's:

```text
Authorization
```

You can be a real student and still **not have permission** to enter that room.

---

# 5. Authentication Does NOT Mean Full Access

This is a very common beginner mistake.

You might think:

```text
Valid JWT
   ↓
User can access everything
```

❌ Wrong.

The correct flow is:

```text
Valid JWT
    ↓
User identified
    ↓
Check permission
    ↓
Allowed?
   / \
 YES  NO
  ↓    ↓
Allow  403
```

A valid JWT only tells you:

> "This identity has been authenticated."

It doesn't automatically mean:

> "This identity can perform every operation."

---

# 6. Example in Your MERN Backend

Suppose you have:

```http
GET /api/v1/admin/users
```

The request contains:

```http
Authorization: Bearer <access-token>
```

Your backend might process it like this:

```text
Request
   ↓
authMiddleware
   ↓
Verify JWT
   ↓
req.user = {
    id: "...",
    role: "user"
}
   ↓
Authorization middleware
   ↓
Is role === "admin"?
   ↓
NO
   ↓
403 Forbidden
```

Notice the two separate jobs:

### Authentication middleware

```text
"Is this JWT valid?"
```

### Authorization middleware

```text
"Does this authenticated user have permission?"
```

---

# 7. Authentication Middleware

Conceptually:

```js
const authenticate = (req, res, next) => {
    const token = getToken(req);

    const payload = verifyToken(token);

    req.user = payload;

    next();
};
```

Its job is to establish:

```js
req.user
```

For example:

```js
req.user = {
    id: "abc123",
    role: "user"
};
```

After this middleware runs, later middleware/controllers can know who made the request.

---

# 8. Authorization Middleware

Now imagine:

```js
const requireAdmin = (req, res, next) => {
    if (req.user.role !== "admin") {
        return res.status(403).json({
            success: false,
            message: "Admin access required"
        });
    }

    next();
};
```

The important thing is:

```text
authenticate
     ↓
creates req.user
     ↓
requireAdmin
     ↓
reads req.user.role
```

Therefore the order matters.

---

# 9. Middleware Order

Correct:

```js
router.delete(
    "/users/:id",
    authenticate,
    requireAdmin,
    deleteUser
);
```

Flow:

```text
Request
   ↓
authenticate
   ↓
req.user
   ↓
requireAdmin
   ↓
deleteUser
```

Incorrect:

```js
router.delete(
    "/users/:id",
    requireAdmin,
    authenticate,
    deleteUser
);
```

Why?

Because `requireAdmin` tries to use:

```js
req.user.role
```

before authentication has established:

```js
req.user
```

This is why **middleware ordering** from Phase 7 becomes important here.

---

# 10. 401 vs 403

This distinction is extremely important.

## `401 Unauthorized`

Usually means:

> The request has not been successfully authenticated.

Examples:

```text
No token
Invalid token
Expired token
Malformed token
```

Conceptually:

```text
Who are you?
    ↓
I don't know.
    ↓
401
```

---

## `403 Forbidden`

Means:

> The server knows who you are, but you don't have permission.

Example:

```text
JWT valid
   ↓
User = Rahul
   ↓
Role = user
   ↓
Admin resource
   ↓
403
```

Think:

```text
401 → "I don't know who you are."

403 → "I know who you are, but you're not allowed."
```

This distinction will become very useful when we build RBAC.

---

# 11. Authentication + Authorization Together

A protected admin endpoint might look like:

```js
router.delete(
    "/users/:id",
    authenticate,
    requireAdmin,
    userController.deleteUser
);
```

Think of it as two security gates:

```text
                 REQUEST
                    │
                    ▼
          ┌──────────────────┐
          │ Authentication   │
          │                  │
          │ Is identity      │
          │ valid?           │
          └────────┬─────────┘
                   │
                  YES
                   │
                   ▼
          ┌──────────────────┐
          │ Authorization    │
          │                  │
          │ Is user allowed? │
          └────────┬─────────┘
                   │
                  YES
                   │
                   ▼
              CONTROLLER
```

If authentication fails:

```text
→ 401
```

If authorization fails:

```text
→ 403
```

---

# 12. Authorization Isn't Only Roles

This is a very important preview for the later lessons.

Authorization can be based on:

### Role

```text
admin
user
moderator
```

### Permission

```text
users:read
users:create
users:delete
```

### Ownership

```text
Can Rahul modify THIS todo?
```

### Resource state

For example:

```text
Can this order be cancelled?
```

### Organization/team

```text
Does Rahul belong to this company?
```

So authorization is much bigger than:

```js
if (role === "admin")
```

We'll explore these throughout Phase 15.

# 13. A Critical Example: Todo Application

Suppose:

```text
User A → Todo A
User B → Todo B
```

Both users are authenticated.

User A sends:

```http
DELETE /api/v1/todos/todoB
```

Authentication says:

```text
JWT valid?
YES
```

So:

```text
User A is authenticated.
```

But authorization says:

```text
Does Todo B belong to User A?
NO
```

Therefore:

```text
403 Forbidden
```

This is why **authentication alone cannot secure your application**.

# 14. Think in Security Questions

Whenever you create a protected endpoint, ask two questions:

### Question 1

```text
WHO is making this request?
```

Authentication.

### Question 2

```text
IS this person allowed to perform this action?
```

Authorization.

For example:

```text
DELETE /todos/123
```

Your brain should automatically think:

```text
WHO?
 ↓
JWT
 ↓
req.user

ALLOWED?
 ↓
Does this todo belong to req.user?
 ↓
YES → continue
NO  → reject
```

That's the mindset we're building.

# 15. Where They Fit in Your Architecture

Your backend architecture becomes:

```text
                    REQUEST
                       │
                       ▼
                    ROUTE
                       │
                       ▼
               Authentication
                       │
                       ▼
               Authorization
                       │
                       ▼
                  Validation
                       │
                       ▼
                  Controller
                       │
                       ▼
                   Service
                       │
                       ▼
                 Repository
                       │
                       ▼
                   Database
```

There can be variations in the exact ordering depending on what a particular middleware needs, but the conceptual security boundary is:

```text
Authentication
      ↓
Authorization
      ↓
Application logic
```

# 16. Common Beginner Mistakes

### Mistake 1

Thinking:

> "If JWT is valid, user can access everything."

❌ No.

JWT establishes identity. Authorization decides access.

---

### Mistake 2

Using only frontend authorization.

For example:

```js
if (user.role === "admin") {
    showDeleteButton();
}
```

This is useful for UI.

But it is **not security**.

A malicious user can directly send:

```http
DELETE /api/v1/users/123
```

Your backend must enforce authorization.

---

### Mistake 3

Confusing 401 and 403.

Remember:

```text
401 → authentication problem
403 → authorization problem
```

---

### Mistake 4

Checking role without authenticating first.

Bad:

```text
requireAdmin
    ↓
authenticate
```

Usually:

```text
authenticate
    ↓
requireAdmin
```

---

### Mistake 5

Only checking roles.

A normal user might not be an admin, but two normal users can still have access to different resources.

That's why we need:

```text
Role
+
Permission
+
Ownership
```

depending on the application.

# 18. What You Should Remember

Don't memorize a lot of code from this lesson.

Remember these **four statements**:

```text
1. Authentication identifies the user.

2. Authorization decides what the user can do.

3. Authentication usually happens before authorization.

4. A valid JWT does NOT mean unlimited access.
```

And:

```text
401 → Not successfully authenticated

403 → Authenticated but not allowed
```
