# Lesson 15.11 — Vertical Privilege Escalation

According to your Phase 15 roadmap, **15.11 is Vertical Privilege Escalation**, followed by Admin Routes and protecting sensitive operations.

In the previous lesson, we studied:

```text
User A
   ↓
User B's resource
```

That was **horizontal privilege escalation**.

Now we're going **upward**:

```text
Normal User
     ↓
Admin functionality
```

That is **vertical privilege escalation**.

---

# 1. What Does "Vertical" Mean?

Imagine your application has different privilege levels:

```text
        ADMIN
          ▲
          │
        USER
```

A normal user should stay at the `USER` level.

An admin has more authority:

```text
Admin
 ├── manage users
 ├── change roles
 ├── delete accounts
 ├── view system information
 └── perform sensitive operations
```

If a normal user manages to perform one of those admin-only operations:

> **Vertical privilege escalation has occurred.**

---

# 2. Horizontal vs Vertical

Let's make this extremely clear.

### Horizontal

```text
User A
  ↓
User B's Todo
```

Same privilege level.

### Vertical

```text
Normal User
  ↓
Admin functionality
```

Higher privilege level.

Visual:

```text
                  ADMIN
                    ▲
                    │
             VERTICAL ESCALATION
                    │
                  USER
                 ↙    ↘
             User A   User B
                 HORIZONTAL
                 ESCALATION
```

---

# 3. Simple Example

Suppose your database has:

```js
{
    name: "Rahul",
    role: "user"
}
```

And an admin:

```js
{
    name: "Admin",
    role: "admin"
}
```

Your application has:

```http
DELETE /api/v1/users/:id
```

Only admins should be able to delete users.

But if your route is:

```js
router.delete(
    "/users/:id",
    authMiddleware,
    userController.deleteUser
);
```

you have only checked:

```text
Is the person logged in?
```

You haven't checked:

```text
Is the person an admin?
```

That's dangerous.

---

# 4. Authentication Is Not Authorization

This is one of the most important concepts in your entire backend journey.

Suppose:

```text
User logs in
     ↓
JWT is valid
     ↓
Authentication succeeds
```

That only tells you:

> "I know who this user is."

It does **not** tell you:

> "This user is allowed to perform every operation."

So:

```text
Authentication
    =
Who are you?

Authorization
    =
What are you allowed to do?
```

---

# 5. The Vulnerable Flow

Imagine:

```text
DELETE /api/v1/users/202
        ↓
authMiddleware
        ↓
JWT valid
        ↓
req.user = User A
        ↓
deleteUser()
        ↓
User B deleted
```

The attacker is authenticated.

But they shouldn't have permission.

So:

```text
Authentication → ✅
Authorization  → ❌
```

---

# 6. The Secure Flow

Instead:

```text
DELETE /api/v1/users/202
        ↓
authMiddleware
        ↓
req.user
        ↓
requireRole("admin")
        ↓
Is user an admin?
       / \
     YES  NO
      ↓    ↓
 Controller 403
```

Now:

```text
Normal user → DENY
Admin       → ALLOW
```

# 7. Role-Based Authorization

Your Phase 15 roadmap introduces roles before permissions:

A simple role check might conceptually look like:

```js
if (req.user.role !== "admin") {
    return res.status(403).json({
        success: false,
        message: "Forbidden"
    });
}
```

This is the basic idea behind:

```text

```

---

# 8. Why `403`?

There are two important status codes here:

```text
401 Unauthorized
403 Forbidden
```

In practical API usage:

### 401

The user isn't properly authenticated.

Example:

```text
No token
Invalid token
Expired token
```

### 403

The user is authenticated but doesn't have permission.

Example:

```text
Logged-in normal user
        ↓
tries admin operation
        ↓
403 Forbidden
```

So:

```text
401 → "I don't know who you are."

403 → "I know who you are, but you're not allowed."
```

# 9. Example: Admin Dashboard

Suppose you have:

```http
GET /api/v1/admin/dashboard
```

A normal user sends:

```http
Authorization: Bearer <valid-user-token>
```

Authentication succeeds:

```text
req.user.id = 101
req.user.role = "user"
```

But authorization checks:

```text
role === "admin"?
```

Result:

```text
NO
```

Response:

```http
403 Forbidden
```

The user cannot access the dashboard.

---

# 10. Route-Level Protection

A clean route can look conceptually like:

```js
router.get(
    "/admin/dashboard",
    authMiddleware,
    requireRole("admin"),
    adminController.getDashboard
);
```

Notice the order:

```text
Request
   ↓
authMiddleware
   ↓
requireRole("admin")
   ↓
controller
```

Why?

Because `requireRole()` needs to know:

```js
req.user
```

And `req.user` is normally created by authentication middleware.

---

# 11. Middleware Order Matters

This would be wrong:

```js
router.get(
    "/admin/dashboard",
    requireRole("admin"),
    authMiddleware,
    controller
);
```

Why?

Because `requireRole()` runs before authentication.

There may be no:

```js
req.user
```

yet.

Correct:

```text
authMiddleware
      ↓
creates req.user
      ↓
requireRole
      ↓
checks req.user.role
```

This is another reason middleware ordering matters.

---

# 12. The Role Middleware

Conceptually:

```js
const requireRole = (requiredRole) => {
    return (req, res, next) => {
        if (req.user.role !== requiredRole) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Then:

```js
router.delete(
    "/users/:id",
    authMiddleware,
    requireRole("admin"),
    userController.deleteUser
);
```

Now the controller doesn't need to repeatedly ask:

```js
if (req.user.role !== "admin")
```

The middleware handles that boundary.

# 15. Changing Your Own Role

This is one of the most important examples.

Suppose your User model contains:

```js
{
    name: "Rahul",
    role: "user"
}
```

And you have:

```http
PATCH /api/v1/users/me
```

with:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

If the backend blindly accepts `req.body`, you have a serious vulnerability.

The user has effectively said:

> "Make me an admin."

And the server said:

> "Sure."

---

# 16. This Is Why Field Whitelisting Matters

Never blindly do:

```js
User.findByIdAndUpdate(
    req.user.id,
    req.body
);
```

Because the request may contain:

```json
{
    "name": "Rahul",
    "role": "admin",
    "isVerified": true
}
```

The user might modify fields they should never control.

Instead, explicitly choose allowed fields:

```js
const updateData = {
    name: req.body.name,
    avatar: req.body.avatar
};
```

Then:

```js
User.findByIdAndUpdate(
    req.user.id,
    updateData
);
```

Now:

```text
role
passwordHash
permissions
isAdmin
```

aren't accepted from this endpoint.

---

# 17. This Connects to Mass Assignment

You will later study mass assignment in the security-testing phase.

The dangerous pattern is:

```js
Model.findByIdAndUpdate(
    id,
    req.body
);
```

because the developer may intend to allow:

```text
name
avatar
bio
```

but accidentally allow:

```text
role
permissions
isAdmin
accountStatus
```

So:

```text
Client input
     ↓
Whitelist allowed fields
     ↓
Business logic
     ↓
Database
```

is much safer.

---

# 18. Never Trust `isAdmin` From the Client

This is obviously dangerous:

```json
{
    "isAdmin": true
}
```

if the server accepts it.

The server should determine privilege from a trusted server-side source.

For example:

```text
Database
   ↓
User role
   ↓
req.user.role
```

not:

```text
req.body.isAdmin
```

---

# 19. What About `req.user.role`?

Suppose authentication middleware verifies a JWT containing:

```json
{
    "sub": "101",
    "role": "user"
}
```

You need to think carefully about how current authorization state is established.

If roles can change, relying forever on an old token's role can create stale authorization decisions.

A safer architecture may be:

```text
JWT
 ↓
identify user
 ↓
load current user / authorization state
 ↓
req.user
 ↓
authorization
```

The exact design depends on your token strategy and how quickly role changes must take effect.

The important lesson:

> **Authorization decisions should be based on trustworthy, current authorization state.**

# 20. Why Admin Operations Need Extra Protection

Consider:

```http
DELETE /api/v1/users/202
```

This is much more sensitive than:

```http
PATCH /api/v1/users/me
```

Admin operations often affect:

```text
other users
permissions
system configuration
financial data
security settings
```

Therefore you should treat them as high-risk operations.

Conceptually:

```text
Normal operation
      ↓
authentication
      ↓
permission
```

Sensitive admin operation:

```text
authentication
      ↓
role/permission
      ↓
resource scope
      ↓
possibly additional safeguards
      ↓
operation
```

# 22. Hidden Admin Routes Are Not Security

A developer might think:

> "Nobody knows `/api/v1/admin/users`."

That's not security.

Attackers can discover endpoints through:

```text
frontend JavaScript
API documentation
error messages
network requests
guessing
source code leaks
```

Therefore:

```text
Hidden route
≠
Protected route
```

You must enforce authorization on the backend.

---

# 23. Frontend Route Protection Is Also Not Enough

Your React app might do:

```text
if (user.role !== "admin") {
    hideAdminPage();
}
```

That's useful for the user experience.

But it does not secure your API.

An attacker can directly call:

```http
DELETE /api/v1/users/202
```

using Postman or curl.

Therefore:

```text
Frontend authorization
        ↓
UX

Backend authorization
        ↓
REAL SECURITY
```

# 24. Role Middleware vs Permission Middleware

You already studied both concepts earlier in Phase 15.

A role check:

```text
requireRole("admin")
```

asks:

> Is this user an admin?

A permission check:

```text
requirePermission("users:delete")
```

asks:

> Does this user have the permission to delete users?

Permission-based authorization is often more flexible.

For example:

```text
admin
 ├── users:read
 ├── users:update
 ├── users:delete
 └── courses:delete
```

while:

```text
moderator
 ├── users:read
 └── courses:delete
```

Roles can map to permissions.

---

# 25. Why Permissions Can Be Better

Suppose you have:

```text
admin
moderator
instructor
student
```

A role check can become:

```js
if (
    role !== "admin" &&
    role !== "moderator"
) {
    deny();
}
```

As the application grows, this becomes messy.

Permission-based:

```text
requirePermission("courses:delete")
```

is more expressive.

You can then configure:

```text
admin      → courses:delete
moderator  → courses:delete
instructor → courses:delete
student    → no
```

This is why your roadmap includes:

```text
15.6 RBAC fundamentals
15.7 Permission-based authorization
```

before the privilege-escalation lessons.

---

# 26. Vertical Escalation Through Permissions

Suppose:

```text
Student
permissions:
    courses:read
    quizzes:take
```

Attacker sends:

```http
DELETE /courses/123
```

If the server only checks:

```text
authenticated?
```

then:

```text
Student
   ↓
courses:delete
   ↓
should be DENIED
```

If allowed:

```text
Student
   ↓
Instructor/Admin capability
```

That's vertical privilege escalation.

---

# 27. Role Hierarchy Can Be Dangerous

Suppose you define:

```text
superadmin
admin
moderator
user
```

and assume:

```text
superadmin > admin > moderator > user
```

Be careful with automatically treating higher roles as having every lower-level capability.

Sometimes that is correct.

Sometimes it isn't.

For example:

```text
billing_admin
content_admin
security_admin
```

may have completely different responsibilities.

A more precise permission system can avoid accidental privilege inheritance.

---

# 28. Sensitive Role Changes

One of the most sensitive operations is:

```http
PATCH /users/:id/role
```

Who should be allowed?

Possibly:

```text
admin
```

But maybe only:

```text
superadmin
```

And perhaps:

```text
admin cannot promote themselves
admin cannot create superadmin
```

These are **business authorization rules**.

This is where authorization becomes more than simply:

```js
role === "admin"
```

---

# 29. Example: Admin Promotes User

Suppose:

```text
User A = admin
User B = user
```

User A sends:

```http
PATCH /users/202/role
```

```json
{
    "role": "instructor"
}
```

Maybe that's allowed.

But:

```http
PATCH /users/202/role
```

```json
{
    "role": "superadmin"
}
```

might not be allowed.

So the service could enforce:

```text
Admin
  ↓
Can assign user/instructor
  ↓
Cannot assign superadmin
```

This is why we don't want all authorization logic buried inside a simple role middleware.

---

# 30. Middleware vs Service Authorization

A useful division is:

### Middleware

Good for broad access:

```text
Is authenticated?
Is admin?
Has permission?
```

### Service

Good for contextual business rules:

```text
Can this admin promote this user?
Can this instructor modify this course?
Can this user cancel this order?
Can this user delete this resource?
```

So:

```text
Middleware
   ↓
Coarse authorization

Service
   ↓
Contextual authorization
```

This becomes especially important in the next lessons.

# 31. Example Architecture

Imagine:

```js
router.patch(
    "/users/:id/role",
    authMiddleware,
    requirePermission("users:role:update"),
    userController.updateRole
);
```

Then:

```text
Controller
    ↓
userService.updateRole()
```

Service:

```text
1. Find target user
2. Check current admin's authorization
3. Check target role
4. Apply business rules
5. Update role
6. Create audit event
```

Repository:

```text
Perform database operation
```

This is a clean architecture.

# 34. Secure Version

The profile update endpoint should only allow:

```text
name
avatar
bio
```

For example:

```js
const updateData = {
    name: req.body.name,
    avatar: req.body.avatar,
    bio: req.body.bio
};
```

Then:

```js
userRepository.updateProfile(
    req.user.id,
    updateData
);
```

The `role` field is not accepted.

If role changes are allowed, create a dedicated operation:

```http
PATCH /api/v1/admin/users/:id/role
```

and protect it:

```text
auth
 ↓
permission
 ↓
service business rules
 ↓
repository
```

This is much safer.

# 35. Separate Sensitive Operations

Don't make one giant endpoint:

```http
PATCH /users/:id
```

that can change:

```text
name
email
password
role
permissions
status
```

That's difficult to secure.

Instead, consider separate operations:

```text
PATCH /users/:id/profile
PATCH /users/:id/password
PATCH /users/:id/role
PATCH /users/:id/status
```

Now each operation has a clear security policy.

This is a very useful API-design principle.

---

# 36. Principle of Least Privilege

Vertical privilege escalation prevention is closely related to:

> **Principle of least privilege**

Give users only the permissions they actually need.

For example:

```text
Student
  ↓
courses:read
quizzes:take
```

Don't give:

```text
users:delete
users:role:update
system:configure
```

"Just in case."

Less privilege means:

```text
smaller attack surface
```

---

# 37. Don't Give Admin to Everything

Sometimes developers solve authorization like this:

```text
If something doesn't work:
    make user admin
```

That's a bad habit.

Instead ask:

```text
What exact capability is needed?
```

Then create:

```text
permission
```

for that capability.

For example:

```text
courses:create
courses:update
courses:delete
users:read
users:suspend
users:role:update
```

This is much more scalable.

# 40. Vertical Escalation Can Happen Without Changing Roles

This is another subtle point.

An attacker doesn't have to literally change:

```text
role=user
```

to:

```text
role=admin
```

They might simply access an admin capability.

For example:

```text
role remains user
```

but they can call:

```http
POST /admin/backups
```

or:

```http
DELETE /users/202
```

or:

```http
GET /admin/analytics
```

That's still vertical privilege escalation.

The problem is:

```text
User
 ↓
higher-level capability
```

not necessarily:

```text
User
 ↓
role changed
```

                       ▼

# 44. The Golden Rule

When building any sensitive endpoint, ask:

> **"What is the highest privilege this operation requires?"**

Then enforce it explicitly.

For example:

```text
GET /todos
    → authenticated user

DELETE /todos/:id
    → authenticated + owner

DELETE /users/:id
    → users:delete permission

PATCH /users/:id/role
    → users:role:update permission
      + additional business rules

POST /system/backup
    → system:backup permission
```

This makes your authorization model much easier to reason about.
