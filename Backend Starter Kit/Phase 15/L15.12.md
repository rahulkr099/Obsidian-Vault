# Phase 15.12 — Admin Routes

Your roadmap places **15.12 Admin Routes** immediately after vertical privilege escalation and before protecting sensitive operations.

The goal of this lesson is simple:

> **Learn how to design and protect routes that only privileged users should be able to access.**

---

## 1. What Is an Admin Route?

An admin route is an API endpoint that performs an operation requiring elevated privileges.

For example:

```text
GET    /api/v1/admin/dashboard
GET    /api/v1/admin/users
PATCH  /api/v1/admin/users/:id/status
PATCH  /api/v1/admin/users/:id/role
DELETE /api/v1/admin/users/:id
```

These are different from normal user routes:

```text
GET   /api/v1/users/me
PATCH /api/v1/users/me
GET   /api/v1/todos
POST  /api/v1/todos
```

The important difference is **not the `/admin` URL itself**.

The important difference is the **authorization policy behind the route**.

---

# 2. `/admin` Does NOT Make a Route Secure

This is a common beginner mistake:

```text
/admin/users
```

looks protected because it contains `admin`.

But the URL is just a string.

An attacker can still request:

```http
GET /api/v1/admin/users
```

So this:

```text
/admin
```

does **not** mean:

```text
admin-only
```

You need actual authorization middleware.

---

# 3. The Correct Flow

Your admin request should conceptually travel like this:

```text
Request
   ↓
Admin Route
   ↓
Authentication
   ↓
Authorization
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

More specifically:

```text
GET /api/v1/admin/users
             ↓
       authMiddleware
             ↓
     requirePermission()
             ↓
     adminController
             ↓
       adminService
             ↓
       repository
             ↓
          MongoDB
```

This fits the architecture you've already learned through Controllers → Services → Repositories.

---

# 4. Authentication Comes First

Suppose someone requests:

```http
GET /api/v1/admin/users
```

First question:

> Who is this person?

That's authentication.

```text
Authorization header
        ↓
JWT
        ↓
verify token
        ↓
req.user
```

Now you might have:

```js
req.user = {
    id: "123",
    role: "user"
};
```

Only after this can authorization happen.

---

# 5. Then Authorization

Now ask:

> Is this authenticated user allowed to access this route?

For a simple admin route:

```text
req.user.role === "admin"
```

If:

```text
role = user
```

then:

```text
403 Forbidden
```

If:

```text
role = admin
```

then:

```text
continue
```

So:

```text
Authentication
     ↓
Who are you?
     ↓
Authorization
     ↓
What can you do?
```

---

# 6. Basic Admin Route

Conceptually:

```js
router.get(
    "/admin/users",
    authMiddleware,
    requireRole("admin"),
    adminController.getUsers
);
```

The order is important:

```text
authMiddleware
       ↓
req.user created
       ↓
requireRole("admin")
       ↓
controller
```

Don't reverse them.

---

# 7. Why Separate Admin Routes?

You could theoretically put everything under:

```text
/users
```

and check authorization individually.

But separating administrative functionality can make your API easier to understand.

For example:

```text
/api/v1/users
```

represents normal user functionality.

While:

```text
/api/v1/admin/users
```

clearly represents administrative operations.

This gives developers a clear mental boundary:

```text
Normal API
     ↓
Normal user capabilities

Admin API
     ↓
Elevated capabilities
```

But remember:

> The URL is for organization. Middleware is for security.

---

# 8. Example Route Structure

You might have:

```text
routes/
├── auth.routes.js
├── user.routes.js
├── todo.routes.js
└── admin.routes.js
```

Then:

```text
auth.routes.js
    ↓
/api/v1/auth

user.routes.js
    ↓
/api/v1/users

todo.routes.js
    ↓
/api/v1/todos

admin.routes.js
    ↓
/api/v1/admin
```

This is clean and easy to navigate.

---

# 9. Admin Router

Conceptually:

```js
const router = Router();

router.use(
    authMiddleware,
    requireRole("admin")
);

router.get(
    "/users",
    adminController.getUsers
);

router.patch(
    "/users/:id/status",
    adminController.updateUserStatus
);

router.delete(
    "/users/:id",
    adminController.deleteUser
);

export default router;
```

Notice something useful:

```js
router.use(
    authMiddleware,
    requireRole("admin")
);
```

This protects the whole router.

So you don't have to repeat:

```js
authMiddleware,
requireRole("admin")
```

on every route.

---

# 10. Router-Level Protection

Think of it like a security gate:

```text
/api/v1/admin
        │
        ▼
 ┌─────────────────┐
 │ Authentication  │
 │       +         │
 │ Admin AuthZ     │
 └────────┬────────┘
          │
     ┌────┴────┐
     ↓         ↓
 /users    /dashboard
     ↓         ↓
 controller  controller
```

Every route underneath the admin router passes through the gate.

This reduces the chance of accidentally forgetting authorization on one route.

---

# 11. But Be Careful With Router-Level Authorization

Suppose you have:

```text
/api/v1/admin
```

and all routes are protected by:

```text
requireRole("admin")
```

Later you add:

```text
GET /api/v1/admin/public-info
```

which you intended to be accessible to everyone.

It will still be admin-only.

So router-level middleware is powerful, but you need to understand its scope.

---

# 12. Role-Based Admin Routes

A simple architecture might be:

```text
Admin
 ↓
requireRole("admin")
```

Example:

```js
router.get(
    "/dashboard",
    authMiddleware,
    requireRole("admin"),
    adminController.dashboard
);
```

This is perfectly reasonable for simple applications.

But your roadmap also teaches permission-based authorization, so eventually you can make this more precise.

---

# 13. Permission-Based Admin Routes

Instead of:

```js
requireRole("admin")
```

you might use:

```js
requirePermission("users:read")
```

For example:

```js
router.get(
    "/users",
    authMiddleware,
    requirePermission("users:read"),
    adminController.getUsers
);
```

Then:

```text
admin
    ↓
users:read
```

might be allowed.

But perhaps:

```text
moderator
    ↓
users:read
```

could also be allowed.

You don't have to make every permission depend directly on the word `admin`.

---

# 14. Admin Does Not Mean "Can Do Everything"

This is a very important design improvement.

Avoid thinking:

```text
admin
 ↓
everything
```

Instead think:

```text
admin
 ↓
set of permissions
```

For example:

```text
users:read
users:update
users:suspend
users:role:update

courses:read
courses:update
courses:delete

reports:read
```

Now your system is much more flexible.

---

# 15. Admin Route + Permission

A realistic route could be:

```js
router.delete(
    "/users/:id",
    authMiddleware,
    requirePermission("users:delete"),
    adminController.deleteUser
);
```

The request flow becomes:

```text
Request
  ↓
Is authenticated?
  ↓
Does user have users:delete?
  ↓
Controller
```

This is stronger than simply saying:

```text
role === admin
```

because the permission describes the actual operation.

---

# 16. Admin Routes and Resource Ownership

Here's an important distinction.

Normal user:

```text
PATCH /users/me
```

might operate on:

```text
their own profile
```

An admin:

```text
PATCH /admin/users/:id/status
```

might operate on:

```text
another user's account
```

So admin routes often intentionally bypass ordinary ownership restrictions.

For example:

```text
Normal user
   ↓
only own resource

Admin
   ↓
authorized resources across users
```

But that does **not** mean the admin should automatically have unlimited access.

The operation still needs authorization.

---

# 17. Example: Suspend a User

Suppose:

```http
PATCH /api/v1/admin/users/202/status
```

Body:

```json
{
  "status": "suspended"
}
```

The security flow:

```text
User A
 ↓
authenticated?
 ↓
has users:suspend?
 ↓
YES
 ↓
find User B
 ↓
apply business rules
 ↓
update status
```

The controller shouldn't just blindly execute:

```js
User.findByIdAndUpdate(...)
```

The service should own the operation's business logic.

---

# 18. Admin Controller

Remember your Phase 11 controller lesson.

Controller's job:

> **Translate HTTP into application calls and application results back into HTTP.**

So:

```js
const updateUserStatus = asyncHandler(async (req, res) => {
    const { id } = req.params;
    const { status } = req.body;

    const user = await adminService.updateUserStatus(
        id,
        status
    );

    return res.status(200).json({
        success: true,
        data: user
    });
});
```

The controller shouldn't contain all the authorization/business rules.

---

# 19. Admin Service

The service might handle:

```text
1. Find target user
2. Check whether operation is allowed
3. Validate target state
4. Perform business operation
5. Record audit event
6. Return result
```

Conceptually:

```text
adminController
      ↓
adminService.updateUserStatus()
      ↓
userRepository
      ↓
MongoDB
```

This follows the architecture you've already built in Phases 11–13.

---

# 20. Admin Repository

The repository should focus on database access.

For example:

```text
findUserById()
updateUserStatus()
findUsers()
deleteUser()
```

It shouldn't decide:

```text
"Is this person an admin?"
```

That is authorization/business logic.

The repository's job is:

> "Given a valid operation, how do I perform the database interaction?"

---

# 21. Don't Put Authorization Only in the Controller

This is tempting:

```js
if (req.user.role !== "admin") {
    return res.status(403).json(...);
}
```

inside every controller.

It works, but it becomes repetitive:

```text
Controller A → admin check
Controller B → admin check
Controller C → admin check
Controller D → admin check
```

Better:

```text
Route
 ↓
authMiddleware
 ↓
authorization middleware
 ↓
controller
```

Then complex business authorization can still happen inside the service.

---

# 22. Two Levels of Protection

A strong architecture can look like:

```text
                    REQUEST
                       ↓
               Authentication
                       ↓
                Permission check
                       ↓
                  Controller
                       ↓
                    Service
                       ↓
          Contextual business authorization
                       ↓
                  Repository
```

This gives you:

### Middleware

Broad permission:

```text
Can this type of user perform this operation?
```

### Service

Contextual decision:

```text
Can this exact operation happen
with this exact target?
```

---

# 23. Example: Delete User

Route:

```js
router.delete(
    "/users/:id",
    authMiddleware,
    requirePermission("users:delete"),
    adminController.deleteUser
);
```

Service:

```text
Is target user protected?
Is actor trying to delete themselves?
Is target a superadmin?
Is deletion allowed by business rules?
```

Then repository:

```text
deleteUserById()
```

This separation is powerful.

---

# 24. Prevent Self-Destructive Admin Actions

Imagine:

```text
Admin A
```

calls:

```http
DELETE /admin/users/A
```

Should admins be allowed to delete themselves?

Maybe.

Maybe not.

That's a business rule.

You might decide:

```text
Admin cannot delete own account
```

Then:

```text
actorId === targetId
        ↓
DENY
```

This is a good example of why authorization isn't always just a role check.

---

# 25. Protect Higher-Level Admins

Suppose you have:

```text
user
instructor
admin
superadmin
```

An admin might be allowed to:

```text
suspend user
```

but not:

```text
delete superadmin
```

So:

```text
Admin
 ↓
delete Superadmin
 ↓
DENY
```

even though the actor is an admin.

This is **contextual authorization**.

---

# 26. Admin Route Naming

A clean naming scheme could be:

```text
/api/v1/admin/users
/api/v1/admin/users/:id
/api/v1/admin/users/:id/status
/api/v1/admin/users/:id/role
/api/v1/admin/courses
```

But don't create an admin route for something that doesn't actually need admin privileges.

For example:

```text
GET /api/v1/users/me
```

doesn't need:

```text
/admin
```

because it is already scoped to the authenticated user.

---

# 27. Avoid "Admin Everything"

Don't create:

```text
/api/v1/admin/all
```

with dozens of unrelated operations.

Prefer resources:

```text
/admin/users
/admin/courses
/admin/reports
/admin/settings
```

This gives each area a clear authorization policy.

---

# 28. Admin Routes in Your LMS

For your LMS, imagine:

```text
/api/v1/admin/users
/api/v1/admin/courses
/api/v1/admin/reports
```

Possible operations:

```text
GET    /admin/users
PATCH  /admin/users/:id/status
PATCH  /admin/users/:id/role

GET    /admin/courses
DELETE /admin/courses/:id

GET    /admin/reports
```

The permission model could be:

```text
users:read
users:suspend
users:role:update

courses:read
courses:delete

reports:read
```

Now the API is much easier to reason about.

---

# 29. Admin Routes Should Still Validate Input

Authorization does not replace validation.

For:

```http
PATCH /admin/users/202/status
```

you still need to validate:

```json
{
  "status": "suspended"
}
```

Maybe only these values are allowed:

```text
active
suspended
disabled
```

So:

```text
Request
 ↓
Authentication
 ↓
Authorization
 ↓
Validation
 ↓
Controller
 ↓
Service
```

The exact middleware order can vary based on your architecture, but **all of these concerns still need to be handled**.

---

# 30. Admin Routes Should Still Have Rate Limits

Sensitive endpoints can be attractive targets.

For example:

```http
PATCH /admin/users/:id/role
```

shouldn't necessarily be treated like an ordinary public endpoint.

You may want:

```text
Authentication
+
Authorization
+
Rate limiting
+
Validation
+
Audit logging
```

The security middleware phase in your starter explicitly treats middleware as security checkpoints.

---

# 31. Audit Admin Actions

Admin operations are particularly useful to audit.

For example:

```text
ADMIN_USER_ROLE_CHANGED
ADMIN_USER_SUSPENDED
ADMIN_USER_DELETED
ADMIN_COURSE_DELETED
```

Record:

```text
actorId
action
targetId
timestamp
requestId
```

Example:

```text
actorId: 101
action: USER_ROLE_CHANGED
targetId: 202
oldRole: user
newRole: instructor
requestId: abc123
```

Then you can investigate:

> "Who changed this user's role?"

---

# 32. Don't Log Sensitive Data

Audit logging doesn't mean:

```text
password
access token
refresh token
```

should be logged.

Never turn your security logs into a new data-leak source.

Prefer:

```text
actorId
action
targetId
timestamp
requestId
```

rather than secrets.

---

# 33. What Happens When Authorization Fails?

Suppose:

```text
Normal User
    ↓
GET /api/v1/admin/users
```

Authentication succeeds.

Authorization fails.

Return:

```http
403 Forbidden
```

Conceptually:

```json
{
  "success": false,
  "message": "Forbidden"
}
```

Don't continue to the controller.

The flow stops:

```text
authMiddleware
      ↓
requirePermission()
      ↓
      ❌
      ↓
    403
```

---

# 34. Don't Let the Controller "Hope" Authorization Happened

A dangerous architecture is:

```text
Route
 ↓
Controller
 ↓
"Maybe the user is admin?"
```

Instead:

```text
Route
 ↓
Authentication
 ↓
Authorization
 ↓
Controller
```

The controller receives an already-authorized request.

This makes your code easier to reason about.

---

# 35. Admin Route Security Checklist

For every admin route, ask:

```text
[ ] Is authentication required?
[ ] Is authorization required?
[ ] Which permission is required?
[ ] Is input validated?
[ ] Is resource scope checked?
[ ] Are business rules checked?
[ ] Is sensitive data minimized?
[ ] Is the operation audited?
[ ] Is rate limiting appropriate?
[ ] Does failure return the correct status?
```

This is the mindset you want to develop.

# 37. The Big Lesson

An admin route is **not** simply:

```text
URL contains /admin
```

It is:

```text
Admin route
    =
Protected endpoint
    +
Authentication
    +
Authorization
    +
Validation
    +
Business rules
    +
Appropriate data access
```

And for sensitive operations, potentially:

```text
+
Audit logging
+
Rate limiting
```

When you see:

```text

```

your brain should immediately think:

```text
Request
  ↓
Route
  ↓
Authentication
  ↓
Permission
  ↓

  ↓

  ↓
Service
  ↓

  ↓
```

```text

  ↓

  ↓
```
