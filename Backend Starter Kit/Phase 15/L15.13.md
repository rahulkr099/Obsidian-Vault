# Lesson 15.13 — Protecting Sensitive Operations

Your Phase 15 roadmap defines **15.13 as “Protecting sensitive operations”**, after Admin Routes and before authorization inside services and repositories.

This lesson is important because **being an admin is not the end of authorization**.

A sensitive operation may need additional checks even when the user is already authenticated and authorized.

---

## 1. What Is a Sensitive Operation?

A sensitive operation is an action that can cause significant damage if abused.

Examples:

```text
Change someone's role
Delete a user
Suspend an account
Reset another user's password
Change email
Change security settings
Delete important data
Access sensitive reports
Change system configuration
```

Compare:

```text
GET /api/v1/courses
```

with:

```text
DELETE /api/v1/admin/users/123
```

The second operation has a much higher security impact.

So we shouldn't treat both requests exactly the same.

---

# 2. Authentication Is Not Enough

Imagine:

```text
Admin
  ↓
DELETE /admin/users/123
```

The admin is authenticated.

They have permission:

```text
users:delete
```

Does that automatically mean the operation should happen?

**Not necessarily.**

There may be additional rules:

```text
Is the target user protected?
Is the admin deleting themselves?
Is the target another administrator?
Is deletion actually allowed?
Does this require confirmation?
Should the action be audited?
```

So authorization can have multiple layers.

---

# 3. Think in Security Layers

A sensitive operation can look like:

```text
                    REQUEST
                       ↓
                Authentication
                       ↓
                 Authorization
                       ↓
                  Validation
                       ↓
             Business authorization
                       ↓
              Sensitive operation
                       ↓
                  Audit event
```

Each layer answers a different question.

### Authentication

```text
Who are you?
```

### Authorization

```text
Are you allowed to perform this kind of operation?
```

### Business authorization

```text
Are you allowed to perform this exact operation
on this exact resource under these exact conditions?
```

### Audit

```text
What happened, and who did it?
```

---

# 4. Example: Delete User

Suppose:

```http
DELETE /api/v1/admin/users/202
```

The actor is:

```text
User 101
role = admin
```

First:

```text
Authentication
      ↓
valid
```

Then:

```text
users:delete
      ↓
allowed
```

But now the service should consider:

```text
Target user = 202
Actor       = 101
```

Questions:

```text
Is user 202 a superadmin?
Is user 202 protected?
Is user 101 trying to delete themselves?
Does the application permit permanent deletion?
```

Only after these checks should the database operation happen.

---

# 5. Why This Should Not All Live in Middleware

You might be tempted to create:

```js
requirePermission("users:delete")
```

and think you're done.

That middleware can answer:

> Does this user have the `users:delete` capability?

But it doesn't necessarily know the entire business context.

For example:

```text
Admin A
    ↓
delete
    ↓
User B
```

The middleware may know:

```text
Admin A has users:delete
```

But the service can know:

```text
User B is the only superadmin
```

or:

```text
Admin A is trying to delete themselves
```

or:

```text
User B has an active legal/financial record
```

Those are business rules.

---

# 6. Middleware vs Service

This distinction is extremely important.

### Middleware

Good for:

```text
Authentication
Role checks
Permission checks
Rate limiting
General request policies
```

### Service

Good for:

```text
Business rules
Resource-specific authorization
State-dependent authorization
Sensitive-operation rules
Transactions
Side effects
```

Think:

```text
Middleware
   ↓
"Can you perform this type of operation?"

Service
   ↓
"Can you perform this exact operation?"
```

---

# 7. Example

Route:

```js
router.delete(
    "/users/:id",
    authMiddleware,
    requirePermission("users:delete"),
    adminController.deleteUser
);
```

This says:

```text
Must be authenticated
        +
Must have users:delete
```

Then:

```js
adminController.deleteUser()
```

calls:

```js
adminService.deleteUser(
    req.user.id,
    req.params.id
);
```

The service can now perform contextual checks.

---

# 8. Contextual Authorization

This is one of the most useful concepts in backend development.

Imagine:

```text
Actor:
admin A

Target:
admin B
```

The permission:

```text
users:delete
```

might exist.

But your business rules may say:

```text
Admin cannot delete another admin.
```

Therefore:

```text
Permission
   ↓
YES
   ↓
Business rule
   ↓
NO
   ↓
403 Forbidden
```

This is why:

> **Having a permission does not always mean every possible use of that permission is valid.**

---

# 9. Another Example: Changing Roles

Endpoint:

```http
PATCH /api/v1/admin/users/202/role
```

Body:

```json
{
  "role": "instructor"
}
```

The actor might have:

```text
users:role:update
```

But suppose the target is:

```text
superadmin
```

and the new role is:

```text
user
```

Maybe ordinary admins aren't allowed to demote superadmins.

So:

```text
Permission → YES
Business rule → NO
```

Result:

```http
403 Forbidden
```

---

# 10. Sensitive Operations Need Narrow APIs

Avoid a giant endpoint like:

```http
PATCH /api/v1/admin/users/202
```

that accepts:

```json
{
  "name": "...",
  "email": "...",
  "role": "admin",
  "status": "suspended",
  "password": "...",
  "permissions": []
}
```

That's difficult to secure.

Instead, separate sensitive operations:

```text
PATCH /admin/users/:id/profile
PATCH /admin/users/:id/status
PATCH /admin/users/:id/role
PATCH /admin/users/:id/permissions
```

Each endpoint can have a specific policy.

---

# 11. Why Narrow Endpoints Are Safer

Suppose you have:

```text
PATCH /admin/users/:id/role
```

The service expects:

```json
{
  "role": "instructor"
}
```

Its security boundary is clear.

But with:

```text
PATCH /admin/users/:id
```

you may accidentally allow fields you didn't intend to expose.

This connects directly to the **mass-assignment** problem you'll later test in security testing.

---

# 12. Never Trust Sensitive Fields From the Client

Suppose a normal user sends:

```json
{
  "role": "admin"
}
```

or:

```json
{
  "permissions": [
    "users:delete"
  ]
}
```

The server must not assume those values are legitimate.

Client input is:

```text
UNTRUSTED
```

Always.

So:

```text
Client
  ↓
untrusted input
  ↓
validation
  ↓
authorization
  ↓
business logic
```

---

# 13. Example: Password Change

Password changes are sensitive.

Imagine:

```http
PATCH /api/v1/users/me/password
```

You shouldn't simply do:

```js
User.findByIdAndUpdate(
    req.user.id,
    {
        password: req.body.password
    }
);
```

The service may need to:

```text
1. Validate new password
2. Verify current password
3. Hash new password
4. Update password
5. Invalidate existing sessions/tokens if required
6. Record security event
```

This is a sensitive business operation.

---

# 14. Example: Email Change

Changing an email address can also be sensitive.

A safer flow could be:

```text
User requests email change
        ↓
Verify current authentication
        ↓
Validate new email
        ↓
Check email uniqueness
        ↓
Send verification email
        ↓
User confirms
        ↓
Change email
```

Notice:

```text
authenticated
≠
automatically allowed to change everything immediately
```

Sensitive operations often require an additional step.

---

# 15. Step-Up Authentication

For particularly sensitive operations, you can require the user to prove their identity again.

This is sometimes called:

> **Step-up authentication**

Example:

```text
User is already logged in
        ↓
tries to change password
        ↓
application asks for current password
        ↓
operation continues
```

Or:

```text
Logged-in user
      ↓
Enable MFA
      ↓
additional verification
      ↓
sensitive action
```

The exact mechanism depends on your application.

The core idea is:

```text
Normal authentication
       ↓
Sensitive operation
       ↓
Stronger verification
```

---

# 16. Why Step-Up Authentication Helps

Imagine someone steals an active session.

If the application allows:

```text
stolen session
   ↓
change email
   ↓
change password
   ↓
take over account
```

that's dangerous.

Additional verification can make the attack harder.

For example:

```text
stolen session
      ↓
change password
      ↓
current password required
      ↓
attacker blocked
```

---

# 17. Confirmation Is Not Authorization

A UI confirmation like:

```text
"Are you sure you want to delete this user?"
```

is useful.

But it is **not security**.

An attacker can simply call the API directly.

So:

```text
Frontend confirmation
       ↓
UX
```

while:

```text
Backend authorization
       ↓
Security
```

The backend must enforce the rule.

---

# 18. Soft Delete for Sensitive Data

For some operations, permanent deletion may be unnecessarily dangerous.

Instead of:

```text
DELETE
   ↓
MongoDB document permanently removed
```

you could use:

```text
deletedAt: Date
```

Then:

```text
User
 ↓
soft delete
 ↓
deletedAt = current time
```

This gives you the ability to:

```text
restore
audit
investigate
recover
```

when appropriate.

Whether you should use soft deletion depends on the domain.

---

# 19. Sensitive Operations and Transactions

Some sensitive operations affect multiple pieces of data.

For example:

```text
Delete user
    ↓
delete account
    ↓
remove sessions
    ↓
remove permissions
    ↓
update related records
    ↓
write audit event
```

If one step succeeds and another fails, you could end up with inconsistent state.

That's where database transactions can become useful.

Conceptually:

```text
BEGIN
 ↓
Operation A
 ↓
Operation B
 ↓
Operation C
 ↓
COMMIT
```

or:

```text
ROLLBACK
```

if something fails.

Your earlier Services phase included transactions and business operations for exactly this reason.

---

# 20. Audit Sensitive Operations

For sensitive actions, you often want an audit trail.

Example:

```text
Actor:
101

Action:
USER_ROLE_CHANGED

Target:
202

Old role:
user

New role:
instructor

Timestamp:
...
```

This helps answer:

```text
Who did this?
What did they do?
When did they do it?
What resource was affected?
```

---

# 21. Audit ≠ Normal Logging

Normal application log:

```text
GET /api/v1/users/202
200
```

Audit event:

```text
ADMIN_CHANGED_USER_ROLE
actorId=101
targetId=202
oldRole=user
newRole=instructor
```

Audit logs are focused on:

> **security-relevant actions and accountability.**

---

# 22. Don't Log Secrets

When auditing sensitive operations, never casually record:

```text
password
JWT
refresh token
API key
session cookie
```

Bad:

```json
{
  "action": "PASSWORD_CHANGED",
  "password": "Rahul123"
}
```

Good:

```json
{
  "action": "PASSWORD_CHANGED",
  "actorId": "101",
  "targetId": "101"
}
```

Remember:

> **Logs are data too, and logs can leak.**

---

# 23. Rate Limiting Sensitive Operations

Sensitive endpoints can also benefit from stricter rate limits.

For example:

```text
POST /auth/login
```

already deserves rate limiting.

But consider:

```text
POST /admin/users/:id/reset-password
```

or:

```text
PATCH /users/me/email
```

These may deserve additional protection depending on the application.

Conceptually:

```text
Sensitive endpoint
       ↓
authentication
       ↓
authorization
       ↓
rate limit
       ↓
operation
```

The exact middleware order depends on your implementation, but the security controls should all be considered.

---

# 24. Prevent Abuse of Admin Accounts

Admins are high-value accounts.

If an attacker compromises an admin:

```text
attacker
   ↓
admin account
   ↓
delete users
change roles
access sensitive information
```

So for administrative systems, consider stronger protections such as:

```text
MFA
shorter sessions
step-up authentication
audit logs
IP/network controls where appropriate
stricter rate limits
alerting
```

Not every application needs every control, but the risk should be considered.

---

# 25. Sensitive Operation Matrix

A useful design technique is to create a table before implementing an endpoint.

For example:

|Operation|Authentication|Permission|Extra Rule|Audit|
|---|---|---|---|---|
|View profile|Yes|`profile:read`|Own profile|Optional|
|Change password|Yes|`profile:password:update`|Current password|Yes|
|Delete user|Yes|`users:delete`|Target rules|Yes|
|Change role|Yes|`users:role:update`|Role hierarchy|Yes|
|Suspend user|Yes|`users:suspend`|Protected accounts|Yes|

This forces you to think about security **before writing code**.

# 26. Example Architecture

Let's build:

```http
PATCH /api/v1/admin/users/:id/role
```

### Route

```js
router.patch(
    "/users/:id/role",
    authMiddleware,
    requirePermission("users:role:update"),
    validate(updateRoleSchema),
    adminController.updateUserRole
);
```

Then:

```text
Request
  ↓
Authentication
  ↓
Permission
  ↓
Input validation
  ↓
Controller
  ↓
Service
```

---

# 27. Controller

The controller stays thin:

```js
const updateUserRole = asyncHandler(async (req, res) => {
    const result = await adminService.updateUserRole({
        actorId: req.user.id,
        targetUserId: req.params.id,
        newRole: req.body.role
    });

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

Notice what the controller does **not** do:

```text
❌ database query
❌ role hierarchy logic
❌ audit logic
❌ complex business rules
```

---

# 28. Service

The service can reason about the sensitive operation:

```text
actor
  ↓
target
  ↓
current target role
  ↓
new role
  ↓
authorization rules
  ↓
update
  ↓
audit
```

Conceptually:

```js
async function updateUserRole({
    actorId,
    targetUserId,
    newRole
}) {
    // find actor
    // find target
    // check business rules
    // update role
    // create audit event
}
```

This is exactly where sensitive-operation logic becomes valuable.

---

# 29. Example Business Rules

Suppose:

```text
Admin can:
    user → instructor
    user → moderator

Admin cannot:
    admin → superadmin
    superadmin → anything
    themselves → superadmin
```

Your service can enforce these rules.

So even if an attacker somehow gets:

```text
users:role:update
```

they still don't automatically get unlimited authority.

That's **defense in depth**.

---

# 30. Defense in Depth

This is a major security principle.

Don't depend on one check.

Instead:

```text
Authentication
      +
Permission
      +
Validation
      +
Business rules
      +
Ownership/scope
      +
Audit
      +
Rate limiting
```

Each layer reduces risk.

If one layer has a mistake, another layer may still prevent damage.

---

# 31. Sensitive Operation ≠ Admin Operation

Important distinction.

Some sensitive operations are admin-only:

```text
Delete another user
Change another user's role
```

But some sensitive operations are available to normal users:

```text
Change own password
Change own email
Delete own account
Create API key
Enable MFA
```

So don't think:

```text
sensitive = admin
```

Instead:

```text
sensitive
   ↓
requires stronger security thinking
```

# 33. Course Publishing Example

Suppose:

```http
POST /api/v1/courses/123/publish
```

The user is an instructor.

Authentication:

```text
YES
```

Permission:

```text
courses:publish
YES
```

Is that enough?

Maybe not.

The service should check:

```text
Does course 123 exist?
Does instructor own course 123?
Is the course complete?
Does it have required lessons?
Does it have a valid thumbnail?
Does it meet publishing rules?
```

Then:

```text
Permission → YES
Ownership → YES
Business rules → YES
       ↓
    PUBLISH
```

This example combines almost everything you've learned in Phase 15.

# 34. This Connects Back to Ownership

You learned:

```text
15.8 Resource ownership
15.9 User A vs User B
15.10 Horizontal escalation
```

Now combine that with sensitive operations.

Suppose Instructor A requests:

```http
POST /courses/course-B/publish
```

The instructor has:

```text
courses:publish
```

But:

```text
course-B.ownerId !== instructorId
```

So:

```text
Permission → YES
Ownership → NO
       ↓
403 Forbidden
```

This prevents horizontal privilege escalation **and** protects a sensitive operation.

# 35. The Three Questions

For every sensitive endpoint, ask:

### Question 1

```text
Who is making this request?
```

Authentication.

### Question 2

```text
Does this user have this capability?
```

Authorization.

### Question 3

```text
Can this exact action happen to this exact resource right now?
```

Business authorization.

That's an excellent mental model.

# 37. Common Mistakes

### Mistake 1: "They're admin, so allow everything."

Wrong.

```text
admin
≠
unlimited authority
```

---

### Mistake 2: Only protecting the frontend

Wrong.

```text
Hide button
≠
API security
```

---

### Mistake 3: Checking only the role

Sometimes insufficient.

```text
role === "admin"
```

doesn't answer every business rule.

---

### Mistake 4: Accepting sensitive fields blindly

Dangerous:

```js
Model.findByIdAndUpdate(id, req.body)
```

Especially for fields like:

```text
role
permissions
status
password
security settings
```

---

### Mistake 5: No audit trail

For high-impact administrative operations, this makes investigation much harder.

---

### Mistake 6: Putting everything in middleware

Middleware shouldn't become a giant business-logic engine.

Keep contextual rules in the service.

---

# 38. A Practical Rule for Your Backend

When you're implementing an operation, classify it:

```text
LOW RISK
    ↓
Normal authorization

MEDIUM RISK
    ↓
Authorization + validation + business rules

HIGH RISK
    ↓
Authorization
+ validation
+ business rules
+ audit
+ possibly step-up authentication
+ possibly stricter rate limits
```

This isn't a rigid universal formula, but it's a very useful design mindset.
