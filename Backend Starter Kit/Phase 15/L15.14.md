# Lesson 15.14 — Authorization Inside Services

Your Phase 15 roadmap explicitly places **15.14 — Authorization inside services** immediately after protecting sensitive operations. The goal is to understand why authorization sometimes cannot stop at middleware and must be enforced inside the business-logic layer.

This lesson is one of the most important ones in the entire **Controller → Service → Repository** architecture you've been building.

---

## 1. The Problem

Suppose we have:

```text
PATCH /api/v1/courses/:id/publish
```

The route has:

```text
authMiddleware
      ↓
requirePermission("courses:publish")
      ↓
controller
```

Looks secure, right?

Not completely.

Imagine:

```text
Instructor A
    ↓
has courses:publish
```

Now Instructor A sends:

```http
PATCH /api/v1/courses/999/publish
```

But course `999` belongs to:

```text
Instructor B
```

The middleware knows:

```text
A has courses:publish
```

But it may not know:

```text
course 999 belongs to B
```

That's a **service-level authorization problem**.

---

# 2. Middleware Cannot Know Everything

Middleware is excellent for broad authorization:

```text
Is authenticated?
Does user have this permission?
```

But business logic often requires:

```text
Does this user own this resource?
Can this instructor modify this particular course?
Can this admin modify this particular user?
Is this resource in a state where the operation is allowed?
```

That information usually belongs closer to the business operation.

So:

```text
Middleware
   ↓
Broad authorization

Service
   ↓
Contextual authorization
```

---

# 3. The Core Idea

Remember this:

> **Middleware asks: "Can you perform this kind of operation?"**

> **Service asks: "Can you perform this exact operation on this exact data?"**

For example:

```text
Middleware:

Can Rahul publish courses?

        YES
```

Then service:

```text
Can Rahul publish THIS course?

        NO
```

because:

```text
course.ownerId !== Rahul.id
```

---

# 4. Example Without Service Authorization

Imagine this route:

```js
router.patch(
    "/courses/:id/publish",
    authMiddleware,
    requirePermission("courses:publish"),
    courseController.publish
);
```

Controller:

```js
const publish = asyncHandler(async (req, res) => {
    const course = await courseRepository.publish(
        req.params.id
    );

    res.json({
        success: true,
        data: course
    });
});
```

What's missing?

We never checked:

```text
Who owns this course?
```

That's dangerous.

---

# 5. The Vulnerable Flow

Imagine:

```text
Instructor A
    ↓
courses:publish
    ↓
PATCH /courses/B/publish
    ↓
Repository
    ↓
Course B published
```

Result:

```text
Instructor A
      ↓
Instructor B's course
      ↓
UNAUTHORIZED ACCESS
```

This can become a form of **horizontal privilege escalation**.

---

# 6. Correct Architecture

Instead:

```text
Request
   ↓
Authentication
   ↓
Permission
   ↓
Controller
   ↓
Service
   ↓
Ownership / business authorization
   ↓
Repository
   ↓
Database
```

Now the service can make the contextual decision.

---

# 7. Service Receives the Actor

A very useful pattern is to explicitly pass the actor.

For example:

```js
courseService.publishCourse({
    actorId: req.user.id,
    courseId: req.params.id
});
```

Now the service knows:

```text
actorId
courseId
```

It can reason about the relationship.

---

# 8. Example Service

Conceptually:

```js
async function publishCourse({
    actorId,
    courseId
}) {
    const course = await courseRepository.findById(courseId);

    if (!course) {
        throw new NotFoundError("Course not found");
    }

    if (course.ownerId.toString() !== actorId) {
        throw new ForbiddenError(
            "You cannot publish this course"
        );
    }

    return courseRepository.publish(courseId);
}
```

Notice the sequence:

```text
Find resource
     ↓
Does it exist?
     ↓
Who owns it?
     ↓
Is actor allowed?
     ↓
Perform operation
```

---

# 9. Why Not Put This in the Controller?

You could technically write:

```js
if (course.ownerId !== req.user.id) {
    return res.status(403).json(...);
}
```

inside the controller.

But then the controller becomes responsible for business rules.

Imagine another entry point:

```text
HTTP Controller
       ↓
courseService.publishCourse()

Admin tool
       ↓
courseService.publishCourse()

Background job
       ↓
courseService.publishCourse()
```

If authorization exists only in the HTTP controller:

```text
HTTP request → protected
background job → maybe not
```

That's inconsistent.

Putting the core rule in the service gives you a central business boundary.

---

# 10. Services Are Not Just "Database Helpers"

This is important given everything you've learned in Phase 12.

A service is where the application decides:

```text
What should happen?
```

For example:

```text
publish course
cancel order
change role
delete account
reset password
transfer ownership
```

These are business operations.

Therefore service-level authorization naturally belongs there when authorization depends on business context.

---

# 11. Example: User Updating Their Profile

Consider:

```http
PATCH /api/v1/users/202
```

Suppose:

```text
Rahul's ID = 101
Target ID = 202
```

Rahul shouldn't be allowed to modify User 202's profile.

Service receives:

```js
userService.updateProfile({
    actorId: 101,
    targetUserId: 202,
    data
});
```

Then:

```text
actorId === targetUserId?
```

Result:

```text
101 !== 202
      ↓
403 Forbidden
```

That's service-level authorization.

---

# 12. Ownership Authorization

A common rule is:

```text
User can modify resource
ONLY IF
resource.ownerId === user.id
```

For example:

```js
if (todo.userId.toString() !== actorId) {
    throw new ForbiddenError("Forbidden");
}
```

This is directly connected to your roadmap's resource ownership lessons.

The roadmap specifically highlights why a query such as:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

is important.

---

# 13. Service Authorization vs Repository Authorization

This distinction will become even more important in **15.15**, so don't mix them up.

### Service

Knows:

```text
business rules
authorization decisions
operation meaning
```

### Repository

Knows:

```text
how to query MongoDB
```

So:

```text
Service
 ↓
"User can modify this Todo."
 ↓
Repository
 ↓
"Okay, I'll query/update the Todo."
```

---

# 14. But There Is a Security Problem

Suppose the service does:

```js
const todo = await todoRepository.findById(todoId);

if (todo.userId !== actorId) {
    throw new ForbiddenError();
}

await todoRepository.update(todoId, data);
```

This is logically correct.

But there is another approach that can be even stronger:

```js
Todo.findOneAndUpdate({
    _id: todoId,
    userId: actorId
}, data);
```

Now the ownership condition is part of the database query.

That's the subject of your next lesson:

> **15.15 Authorization inside repositories.**

For now, understand why both layers can matter.

---

# 15. Service-Level Authorization Is About Meaning

Consider:

```text
DELETE /todos/123
```

The service can decide:

```text
Can this user delete this Todo?
```

But the repository doesn't need to understand the concept of "delete permission."

It can simply receive:

```text
todoId
actorId
```

and perform the constrained database operation.

This gives us separation:

```text
Service
    ↓
business decision

Repository
    ↓
data enforcement
```

---

# 16. Example: Role Change

Suppose:

```http
PATCH /admin/users/202/role
```

Actor:

```text
Admin A
```

Target:

```text
User B
```

Middleware:

```text
users:role:update
      ↓
YES
```

Service then checks:

```text
Is target a superadmin?
Can actor modify that role?
Is actor trying to promote themselves?
Is new role valid?
Is this role transition allowed?
```

This is service-level authorization.

---

# 17. Role Hierarchy Example

Suppose:

```text
user
instructor
moderator
admin
superadmin
```

You could define rules such as:

```text
admin
  ↓
can modify user
can modify instructor
can modify moderator

admin
  ↓
cannot modify superadmin
```

So:

```text
actor.role = admin
target.role = superadmin
```

Even though:

```text
users:role:update = YES
```

the service can reject the operation.

---

# 18. Permission ≠ Business Permission

This is subtle.

Suppose the user has:

```text
users:delete
```

That is a **system permission**.

But the application may still have:

```text
"You cannot delete the last administrator."
```

That's a **business rule**.

Therefore:

```text
System permission
        +
Business authorization
        ↓
Allowed operation
```

Both may be required.

---

# 19. Another Example: Course Ownership

Imagine:

```text
Course A
ownerId = 101
```

Instructor:

```text
actorId = 101
```

Request:

```text
publish Course A
```

Service:

```text
101 === 101
     ↓
Allowed
```

Now:

```text
Course B
ownerId = 202
```

Same instructor:

```text
actorId = 101
```

Request:

```text
publish Course B
```

Service:

```text
101 !== 202
     ↓
Forbidden
```

This is exactly the kind of contextual authorization that a generic:

```text
requireRole("instructor")
```

cannot solve.

---

# 20. Service-Level Authorization Is Not Always Ownership

Don't think:

```text
service authorization = ownership check
```

It can also include:

### State

```text
Can this course be published?
```

### Role relationship

```text
Can this admin modify this other admin?
```

### Account state

```text
Can a suspended user perform this action?
```

### Resource status

```text
Can a completed order be cancelled?
```

### Business restrictions

```text
Can the last administrator be deleted?
```

So service-level authorization is broader than ownership.

---

# 21. Authorization Depends on State

Imagine:

```text
Order
status = delivered
```

User requests:

```http
POST /orders/123/cancel
```

The user might own the order.

They might have:

```text
orders:cancel
```

But:

```text
delivered
```

means cancellation isn't allowed.

Therefore:

```text
Authentication → YES
Permission → YES
Ownership → YES
Business state → NO
```

Final:

```text
403 Forbidden
```

That's service-level business authorization.

---

# 22. Authorization Can Depend on Relationships

Suppose an LMS has:

```text
Instructor
Course
Students
```

Maybe an instructor can access:

```text
their own course
```

but not:

```text
another instructor's course
```

Or perhaps:

```text
moderator
```

can moderate any course.

Now authorization depends on relationships:

```text
actor
 ↓
relationship
 ↓
resource
```

This is why simple role checks eventually become insufficient.

---

# 23. A Useful Service Input Pattern

Instead of:

```js
courseService.publishCourse(
    req.params.id
);
```

prefer something explicit:

```js
courseService.publishCourse({
    actorId: req.user.id,
    courseId: req.params.id
});
```

Why?

Because authorization needs the actor.

It makes the service contract obvious:

```text
actorId
courseId
```

rather than hiding authorization information somewhere inside a global object.

---

# 24. Don't Pass the Entire `req`

Avoid:

```js
courseService.publishCourse(req);
```

This tightly couples your service to Express.

Your service should not need to know about:

```text
req.body
req.params
req.query
res
cookies
HTTP headers
```

Instead:

```js
courseService.publishCourse({
    actorId,
    courseId
});
```

This keeps the service independent of HTTP.

---

# 25. Good Architecture

Prefer:

```text
Controller
    ↓
extract HTTP data
    ↓
Service
    ↓
business authorization
    ↓
Repository
```

For example:

```js
const publish = asyncHandler(async (req, res) => {
    const result = await courseService.publishCourse({
        actorId: req.user.id,
        courseId: req.params.id
    });

    return res.status(200).json({
        success: true,
        data: result
    });
});
```

The service doesn't know that the actor came from:

```text
req.user
```

It just knows:

```text
actorId
```

---

# 26. What Should the Service Return?

If authorization fails:

```text
ForbiddenError
```

If resource doesn't exist:

```text
NotFoundError
```

If state is invalid:

```text
ConflictError
```

For example:

```text
Course doesn't exist
        ↓
404

Course belongs to another instructor
        ↓
403

Course already published
        ↓
409
```

Your global error architecture can then convert these into HTTP responses.

---

# 27. Don't Leak Too Much Information

There is an interesting security decision here.

Suppose:

```http
GET /todos/999
```

The Todo exists but belongs to another user.

Should you return:

```text
403 Forbidden
```

or:

```text
404 Not Found
```

There isn't one universal answer.

Sometimes returning `404` can avoid revealing that a resource exists.

For example:

```text
User requests another user's private document
        ↓
404
```

instead of:

```text
403
```

which might reveal:

> "Yes, that document exists, but you're forbidden."

This is a security/design decision based on your API.

---

# 28. Service Authorization Should Be Consistent

Suppose you have:

```text
updateTodo()
deleteTodo()
completeTodo()
shareTodo()
```

All of them should have a clear authorization policy.

For example:

```text
updateTodo
    ↓
owner

deleteTodo
    ↓
owner

completeTodo
    ↓
owner

shareTodo
    ↓
owner
```

Don't accidentally protect only `updateTodo()` and forget `deleteTodo()`.

---

# 29. Centralize Repeated Authorization Rules

Suppose many service methods need:

```text
assertTodoOwner()
```

You could create a helper:

```js
function assertTodoOwner(todo, actorId) {
    if (todo.userId.toString() !== actorId) {
        throw new ForbiddenError("Forbidden");
    }
}
```

Then:

```js
async function updateTodo(...) {
    const todo = await repository.findById(todoId);

    assertTodoOwner(todo, actorId);

    ...
}
```

And:

```js
async function deleteTodo(...) {
    const todo = await repository.findById(todoId);

    assertTodoOwner(todo, actorId);

    ...
}
```

This reduces duplicated security logic.

---

# 30. But Don't Build a Giant `AuthorizationService`

Avoid something like:

```text
authorization.service.js
```

with:

```text
checkUser()
checkTodo()
checkCourse()
checkOrder()
checkAdmin()
checkInstructor()
checkEverything()
```

Eventually it becomes a giant ball of business logic.

Prefer authorization rules close to the domain they protect.

For example:

```text
todo.service.js
   ↓
Todo authorization

course.service.js
   ↓
Course authorization

user.service.js
   ↓
User-management authorization
```

This keeps the system understandable.

# 33. Why This Matters Even If Middleware Exists

You might ask:

> "If middleware already checks permission, why do we need another authorization check?"

Because authorization isn't always a single yes/no question.

Middleware may know:

```text
User has permission X.
```

Service knows:

```text
Given permission X,
is operation Y allowed on resource Z
under state S?
```

So:

```text
Middleware
    ↓
Capability

Service
    ↓
Context
```

---

# 34. Service Authorization and Background Jobs

Here's another advantage.

Suppose tomorrow your application has:

```text
HTTP API
    ↓
courseService.publishCourse()
```

But you also create:

```text
Background job
    ↓
courseService.publishCourse()
```

The service can still enforce important business rules.

However, **don't blindly apply end-user authorization to trusted internal jobs**. The service contract may need an explicit actor/system identity or a different trusted-operation path.

The key is:

> Don't accidentally bypass business invariants just because the caller isn't HTTP.

---

# 35. A Better Mental Model

Think of the service as a **business security boundary**.

```text
Internet
   ↓
HTTP security
   ↓
Controller
   ↓
BUSINESS SECURITY
   ↓
Repository
   ↓
Database
```

The service doesn't replace middleware.

It adds another layer.

---

# 36. Service Authorization vs Authentication

Don't mix these up.

Authentication:

```text
Who is actorId 101?
```

Usually middleware handles this.

Service authorization:

```text
Is actorId 101 allowed to perform this business operation?
```

Service handles contextual decisions.

# 37. The Golden Pattern

For many protected operations, think:

```text
actor
  ↓
permission
  ↓
resource
  ↓
relationship
  ↓
state
  ↓
business rule
  ↓
operation
```

For example:

```text
Actor:
Instructor A

Permission:
courses:publish

Resource:
Course 123

Relationship:
Instructor A owns Course 123

State:
Course is complete

Business rule:
Complete courses can be published

Result:
ALLOW
```

Change any one of those:

```text
Course belongs to Instructor B
```

and:

```text
DENY
```

# 38. What Not to Do

### ❌ Don't rely only on frontend

```text
React hides button
        ↓
API still vulnerable
```

### ❌ Don't rely only on role

```text
role = instructor
        ↓
therefore can modify every course
```

Wrong.

### ❌ Don't put all business authorization in controllers

```text
controller
   ↓
100 lines of business rules
```

Bad architecture.

### ❌ Don't pass `req` into services

```js
service.doSomething(req)
```

This couples your service to Express.

### ❌ Don't let repository decide business policy

```text
MongoDB query
   ↓
"Is this instructor allowed?"
```

The repository should remain focused on data access, with security-enforcing query constraints becoming especially important in the next lesson.

# 40. A Practical Example

Let's build the logic conceptually.

### Request

```http
PATCH /api/v1/todos/123
```

### User

```text

```

### Todo

```text
id = 123

```

```js
async function updateTodo({
    actorId,
    todoId,
    data
}) {

```

The important thing isn't the exact code.

```text
Find
 ↓
Authorize
 ↓
Modify
```

### 1. Middleware is not enough

```text

≠

```

### 2. Services understand business context

```text
actor
+
resource
+
state
+
business rules
```



```text
      ↓
Repository query constraints
      ↓
```
