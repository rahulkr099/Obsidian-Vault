# Lesson 15.15 — Authorization Inside Repositories

Your roadmap defines **15.15 as “Authorization inside repositories”** and specifically highlights the importance of ownership-constrained queries such as:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

This lesson builds directly on 15.14. In 15.14, we learned **why the service must make contextual authorization decisions**. Now we're going one level deeper:

> **How can the repository make the database query itself respect the authorization boundary?**

---

# 1. The Problem With `findById()`

Imagine we have two users:

```text
User A
id = 101

User B
id = 202
```

And:

```text
Todo A
id = 500
userId = 101
```

User B sends:

```http
GET /api/v1/todos/500
```

If your repository does:

```js
Todo.findById(todoId);
```

MongoDB says:

```text
Todo 500 exists
       ↓
return Todo 500
```

It doesn't care that:

```text
requesting user = 202
todo owner = 101
```

That's the security problem.

---

# 2. The Secure Query

Instead of:

```js
Todo.findById(todoId);
```

use:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Now the query means:

> Find this Todo **AND** make sure it belongs to this user.

So:

```text
User B
id = 202

Todo
id = 500
userId = 101
```

Query:

```js
{
    _id: 500,
    userId: 202
}
```

Result:

```text
No document
```

The database itself refuses to return User A's Todo.

This is the central idea of **15.15**.

---

# 3. Why This Is Powerful

Compare the two approaches.

### Unsafe-ish approach

```text
Find resource
      ↓
Get resource
      ↓
Check ownership
```

### Ownership-constrained query

```text
Find resource
     +
Check ownership
     ↓
Database query
```

The second approach makes it much harder to accidentally fetch data outside the user's scope.

---

# 4. Service Authorization vs Repository Authorization

This distinction is extremely important.

### Service

The service asks:

> **Is this operation allowed?**

### Repository

The repository can enforce:

> **Only retrieve/modify records inside the actor's allowed data scope.**

Think:

```text
                 Service
                    │
             Business decision
                    │
                    ▼
               Repository
                    │
          Constrained database query
                    │
                    ▼
                 MongoDB
```

They complement each other.

---

# 5. Example

Service:

```js
async function getTodo({ actorId, todoId }) {
    return todoRepository.findOwnedByUser({
        todoId,
        userId: actorId
    });
}
```

Repository:

```js
async function findOwnedByUser({ todoId, userId }) {
    return Todo.findOne({
        _id: todoId,
        userId
    });
}
```

Notice the service doesn't say:

```js
Todo.findOne(...)
```

It asks the repository:

```text
"Give me this user's Todo."
```

The repository knows how to express that requirement in MongoDB.

---

# 6. Why `findOne()` Matters

You might have:

```js
Todo.findById(todoId);
```

But ownership requires multiple conditions:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Conceptually:

```text
_id = requested resource
       AND
userId = authenticated actor
```

Both must match.

---

# 7. This Prevents Horizontal Privilege Escalation

Remember 15.10?

Horizontal privilege escalation happens when:

```text
User A
   ↓
accesses
   ↓
User B's resource
```

For example:

```http
GET /api/v1/todos/500
```

User A shouldn't be able to change the URL to:

```http
GET /api/v1/todos/501
```

and suddenly see User B's data.

Ownership-constrained queries directly help prevent this.

---

# 8. The Dangerous Pattern

Imagine:

```js
async function getTodo(todoId) {
    return Todo.findById(todoId);
}
```

Then controller:

```js
const todo = await todoService.getTodo(req.params.id);

if (todo.userId !== req.user.id) {
    throw new ForbiddenError();
}
```

This looks protected.

But notice what already happened:

```text
MongoDB
   ↓
returned User B's document
   ↓
application memory
   ↓
authorization check
```

You've already retrieved data outside the actor's scope.

Sometimes that's acceptable depending on the architecture, but it creates a larger security boundary than necessary.

---

# 9. Better Pattern

Instead:

```js
async function getTodo({ todoId, actorId }) {
    const todo = await todoRepository.findOwnedByUser({
        todoId,
        userId: actorId
    });

    if (!todo) {
        throw new NotFoundError("Todo not found");
    }

    return todo;
}
```

Now:

```text
User ID
    +
Todo ID
    ↓
Repository
    ↓
MongoDB
    ↓
Only matching document
```

Much safer.

---

# 10. The Query Is the Security Boundary

This is the key idea I want you to remember.

Instead of:

```js
Todo.findById(todoId);
```

think:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

The query itself says:

> **This operation is scoped to this user.**

That's why your roadmap specifically emphasizes this query.

---

# 11. Apply It to Update

Suppose:

```http
PATCH /api/v1/todos/500
```

Unsafe:

```js
Todo.findByIdAndUpdate(
    todoId,
    updateData
);
```

The database only knows:

```text
_id = 500
```

It doesn't know who is allowed to update it.

Instead:

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData,
    {
        new: true
    }
);
```

Now the update requires:

```text
Todo ID matches
AND
owner matches
```

---

# 12. Apply It to Delete

Unsafe:

```js
Todo.findByIdAndDelete(todoId);
```

Secure ownership-scoped version:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

Now:

```text
User A
   ↓
delete Todo B
   ↓
query requires userId = A
   ↓
Todo B has userId = B
   ↓
no match
   ↓
nothing deleted
```

That's excellent defense in depth.

---

# 13. Apply It to Update

The same principle applies everywhere.

### Read

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

### Update

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData
);
```

### Delete

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

The ownership condition stays consistent.

---

# 14. Create Is Different

Creating a Todo doesn't require finding an existing Todo.

Instead:

```js
Todo.create({
    title,
    userId
});
```

The important part is:

> **The server determines `userId`.**

Don't trust:

```json
{
    "title": "Learn MongoDB",
    "userId": "202"
}
```

from the client.

Instead:

```js
Todo.create({
    title: req.body.title,
    userId: req.user.id
});
```

The authenticated identity determines ownership.

---

# 15. Never Trust `userId` From the Client

This is a classic mistake.

Bad:

```js
const todo = await Todo.create(req.body);
```

Client could send:

```json
{
    "title": "My Todo",
    "userId": "another-user-id"
}
```

Now the client is attempting to choose the owner.

Better:

```js
const todo = await Todo.create({
    title: data.title,
    userId: actorId
});
```

The server owns the security-sensitive field.

---

# 16. Repository Method Naming

Instead of generic methods:

```js
findById()
```

you can create explicit methods:

```js
findById()
findOwnedByUser()
updateOwnedByUser()
deleteOwnedByUser()
```

For example:

```js
async function findOwnedByUser({
    todoId,
    userId
}) {
    return Todo.findOne({
        _id: todoId,
        userId
    });
}
```

The method name communicates its security expectation.

---

# 17. Why This Is Better Than Generic Queries

Consider:

```js
todoRepository.findById(todoId);
```

The caller must remember:

```text
"Wait... I need to check ownership!"
```

But:

```js
todoRepository.findOwnedByUser({
    todoId,
    userId
});
```

makes the security scope explicit.

It becomes harder to accidentally use the wrong method.

---

# 18. Repository API as a Security Contract

Your repository can effectively expose:

```text
findOwnedByUser()
updateOwnedByUser()
deleteOwnedByUser()
```

instead of forcing every service to manually build:

```js
{
    _id,
    userId
}
```

This creates a clear contract:

```text
Service
   ↓
"I want the Todo belonging to this user."

Repository
   ↓
"I will enforce that ownership in the query."
```

---

# 19. Example Repository

A simple repository could look like:

```js
const findOwnedByUser = async ({
    todoId,
    userId
}) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};

const updateOwnedByUser = async ({
    todoId,
    userId,
    data
}) => {
    return Todo.findOneAndUpdate(
        {
            _id: todoId,
            userId
        },
        data,
        {
            new: true
        }
    );
};

const deleteOwnedByUser = async ({
    todoId,
    userId
}) => {
    return Todo.findOneAndDelete({
        _id: todoId,
        userId
    });
};
```

This is a very useful repository pattern for user-owned resources.

---

# 20. What Happens When Nothing Matches?

Suppose:

```text
Todo 500
owner = 101
```

Actor:

```text
202
```

Repository:

```js
Todo.findOne({
    _id: 500,
    userId: 202
});
```

MongoDB returns:

```text
null
```

The service then decides what that means.

Possibilities:

```text
404 Not Found
```

or, depending on your API's security policy:

```text
403 Forbidden
```

Often `404` is useful because it avoids confirming that another user's resource exists.

The repository's job is generally:

```text
"No matching authorized-scope document exists."
```

The service decides how to interpret that result for the business operation.

---

# 21. Don't Leak Ownership Information

Imagine User A requests:

```http
GET /todos/500
```

where Todo 500 belongs to User B.

You could return:

```json
{
    "message": "Todo 500 exists but belongs to another user"
}
```

That's potentially unnecessary information.

Better:

```json
{
    "message": "Todo not found"
}
```

The attacker doesn't learn whether:

```text
Todo 500
```

actually exists.

This is another reason ownership-constrained queries are useful.

# 22. Service + Repository Together

Let's combine 15.14 and 15.15.

### Controller

```js
const getTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.getTodo({
        actorId: req.user.id,
        todoId: req.params.id
    });

    res.json({
        success: true,
        data: todo
    });
});
```

### Service

```js
async function getTodo({
    actorId,
    todoId
}) {
    const todo = await todoRepository.findOwnedByUser({
        todoId,
        userId: actorId
    });

    if (!todo) {
        throw new NotFoundError("Todo not found");
    }

    return todo;
}
```

### Repository

```js
async function findOwnedByUser({
    todoId,
    userId
}) {
    return Todo.findOne({
        _id: todoId,
        userId
    });
}
```

Now we have:

```text
Controller
    ↓
passes actor
    ↓
Service
    ↓
defines business operation
    ↓
Repository
    ↓
enforces ownership in query
    ↓
MongoDB
```

That's the architecture you should understand.

# 23. What If the Resource Has a Different Owner Field?

Not every resource uses:

```text
userId
```

You might have:

```text
ownerId
```

Then:

```js
Model.findOne({
    _id: resourceId,
    ownerId: actorId
});
```

Or:

```text
createdBy
```

Then:

```js
Model.findOne({
    _id: resourceId,
    createdBy: actorId
});
```

The principle is the same:

```text
resource identifier
+
authorization scope
```

---

# 24. Multi-Tenant Applications

This idea becomes even more important in multi-tenant systems.

Imagine:

```text
Company A
  users
  projects

Company B
  users
  projects
```

A repository query might need:

```js
Project.findOne({
    _id: projectId,
    organizationId
});
```

Now the security boundary isn't:

```text
userId
```

but:

```text
organizationId
```

The principle remains:

> **Every data-access operation should be scoped to the actor's permitted tenant/resource boundary.**

---

# 25. Example Multi-Tenant Query

Unsafe:

```js
Project.findById(projectId);
```

Safer:

```js
Project.findOne({
    _id: projectId,
    organizationId
});
```

Now:

```text
Company A
    ↓
projectId
    +
organizationId A
```

cannot accidentally retrieve:

```text
Company B's project
```

---

# 26. Nested Resources

Suppose your API is:

```http
GET /users/:userId/todos/:todoId
```

You might be tempted to trust:

```text
:userId
```

from the URL.

Don't.

The authenticated identity should still be used.

For example:

```js
Todo.findOne({
    _id: todoId,
    userId: actorId
});
```

not:

```js
Todo.findOne({
    _id: todoId,
    userId: req.params.userId
});
```

The client controls the URL.

---

# 27. Client-Controlled IDs Are Untrusted

Remember:

```text
req.params
req.query
req.body
```

are all user-controlled.

So:

```js
req.params.userId
```

shouldn't automatically become the security identity.

Instead:

```js
req.user.id
```

comes from your authentication process.

Then:

```text
authenticated identity
+
requested resource
```

creates the secure query.

---

# 28. Bulk Operations

Now things become more interesting.

Suppose:

```http
DELETE /todos
```

with:

```json
{
    "ids": ["1", "2", "3"]
}
```

Don't do:

```js
Todo.deleteMany({
    _id: {
        $in: ids
    }
});
```

because that could delete other users' Todos.

Instead:

```js
Todo.deleteMany({
    _id: {
        $in: ids
    },
    userId
});
```

Now every deletion is scoped.

This is an important real-world security consideration.

---

# 29. Search Queries Need Scope Too

Suppose:

```http
GET /todos?search=database
```

Unsafe:

```js
Todo.find({
    title: {
        $regex: search
    }
});
```

This could search across every user's Todos.

Instead:

```js
Todo.find({
    userId,
    title: {
        $regex: search
    }
});
```

Now:

```text
search
+
ownership
```

are both enforced.

---

# 30. Pagination Must Preserve Authorization

Suppose:

```http
GET /todos?page=2&limit=20
```

Your repository should not do:

```js
Todo.find({})
    .skip(...)
    .limit(...);
```

It should do:

```js
Todo.find({
    userId
})
.skip(...)
.limit(...);
```

Otherwise you could accidentally paginate through another user's data.

So authorization scope belongs in:

```text
find
filter
search
sort
pagination
update
delete
```

whenever those operations access user-scoped resources.

---

# 31. Sorting Does Not Remove Authorization

For:

```http
GET /todos?sort=-createdAt
```

you still need:

```js
Todo.find({
    userId
})
.sort({
    createdAt: -1
});
```

The authorization filter remains.

---

# 32. Counting Also Needs Scope

This is a common mistake.

Suppose you want:

```text
total = number of user's Todos
```

Don't do:

```js
Todo.countDocuments({});
```

That gives:

```text
all users' Todos
```

Instead:

```js
Todo.countDocuments({
    userId
});
```

Otherwise your pagination metadata can leak information.

---

# 33. Aggregation Needs Scope Too

Suppose you use MongoDB aggregation:

```js
Todo.aggregate([
    ...
]);
```

The authorization boundary must still be included.

For example, begin with a `$match`:

```js
Todo.aggregate([
    {
        $match: {
            userId
        }
    },
    // other stages
]);
```

Otherwise an aggregation can accidentally cross user boundaries.

This is an important point:

> **Authorization isn't only for `findOne()`.**

It applies to every data-access path.

---

# 34. Populate Can Also Be Dangerous

Suppose:

```js
Todo.findOne({
    _id: todoId,
    userId
}).populate("someReference");
```

The Todo itself is scoped correctly.

But you still need to think about whether the populated resource is allowed to be exposed.

Security isn't automatically solved just because the first query is constrained.

This becomes especially important with:

```text
populate
aggregation
nested documents
references
```

---

# 35. Repository Security Is Defense in Depth

You might already have:

```text
authMiddleware
```

and:

```text
service authorization
```

Why add repository-level constraints?

Because multiple layers provide defense in depth:

```text
Authentication
       ↓
Permission
       ↓
Service business authorization
       ↓
Repository scope
       ↓
Database
```

If someone accidentally removes a service check later, a scoped repository method can still reduce the blast radius.

---

# 36. But Don't Put All Authorization in Repositories

This is equally important.

Don't write:

```js
todoRepository.updateTodo(...)
```

and make the repository understand:

```text
roles
permissions
business states
admin hierarchy
course publishing rules
```

That's not its job.

Repository should understand:

```text
How do I query the data?
What data scope is being requested?
```

Service should understand:

```text
Why is this operation allowed?
```

---

# 37. Good Responsibility Split

Think of it like this:

### Middleware

```text
Is the request authenticated?
Does the actor have the required broad permission?
```

### Service

```text
Is this business operation allowed?
```

### Repository

```text
Can I make the database operation constrained
to the permitted resource scope?
```

### Database

```text
Store and retrieve the data.
```

# 38. A Very Useful Pattern

For owned resources:

```text
findOwnedByUser()
updateOwnedByUser()
deleteOwnedByUser()
```

For tenant resources:

```text
findByOrganization()
updateByOrganization()
deleteByOrganization()
```

For admin-controlled resources:

```text
findById()
updateById()
deleteById()
```

depending on the actual security model.

The repository API should reflect the scope required by the domain.

# 39. Example: Secure Todo Repository

A clean repository might look conceptually like:

```js
const todoRepository = {
    create(data) {
        return Todo.create(data);
    },

    findOwnedByUser({ todoId, userId }) {
        return Todo.findOne({
            _id: todoId,
            userId
        });
    },

    findManyOwnedByUser({ userId, filter }) {
        return Todo.find({
            userId,
            ...filter
        });
    },

    updateOwnedByUser({ todoId, userId, data }) {
        return Todo.findOneAndUpdate(
            {
                _id: todoId,
                userId
            },
            data,
            {
                new: true
            }
        );
    },

    deleteOwnedByUser({ todoId, userId }) {
        return Todo.findOneAndDelete({
            _id: todoId,
            userId
        });
    }
};
```

This is a strong foundation.

# 40. One Important Security Rule

When you see:

```js
Model.findById(id)
```

for a user-owned resource, pause and ask:

> **"Should this query also include the authenticated user's scope?"**

For example:

```js
Model.findOne({
    _id: id,
    userId
});
```

That simple question can prevent a huge class of authorization bugs.

# 42. The Golden Pattern

For a user-owned resource:

```text
                 AUTHENTICATED USER
                         │
                         │ userId
                         ▼
                      SERVICE
                         │
                         │ resourceId + userId
                         ▼
                    REPOSITORY
                         │
                         ▼
               ┌──────────────────┐
               │ MongoDB Query    │
               │                  │
               │ _id: resourceId  │
               │ userId: userId   │
               └────────┬─────────┘
                        │
                        ▼
                    MongoDB
```

This is what you should visualize.

# 43. 15.14 vs 15.15

Let's make the difference crystal clear.

|Layer|Main Question|
|---|---|
|Authentication|Who is the user?|
|Middleware authorization|Does the user have the capability?|
|**Service authorization**|Is this business operation allowed?|
|**Repository authorization/scope**|Is the database operation constrained to the allowed resource scope?|
|Database|How is the data stored?|

Example:

```text
Instructor A
     ↓
has courses:edit
     ↓
Service
     ↓
Can A edit Course 123?
     ↓
YES
     ↓
Repository
     ↓
findOneAndUpdate({
    _id: 123,
    instructorId: A
})
```

Now the entire chain respects the authorization boundary.
