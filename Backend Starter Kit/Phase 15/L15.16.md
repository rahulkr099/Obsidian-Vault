# Lesson 15.16 — Designing Secure Ownership Queries

This lesson is the natural continuation of **15.14 Authorization inside services** and **15.15 Authorization inside repositories**.

Your roadmap specifically names **15.16 “Designing secure ownership queries”** and says the key Phase 15 idea is understanding why an ownership-constrained query such as this is so important:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

The goal today is not just to memorize that query.

The goal is to learn **how to design secure queries for an entire resource**, so you don't accidentally create an authorization vulnerability in `find`, `update`, `delete`, search, pagination, or bulk operations.

---

# 1. What Is an Ownership Query?

Suppose we have:

```text
User A
id = 101

User B
id = 202
```

And:

```text
Todo 1 → userId = 101
Todo 2 → userId = 202
```

User A asks for:

```http
GET /api/v1/todos/1
```

We want:

```text
Todo ID = 1
AND
Owner = User A
```

So the query becomes:

```js
Todo.findOne({
    _id: todoId,
    userId: actorId
});
```

This is an **ownership-constrained query**.

---

# 2. The Dangerous Mental Model

A beginner often thinks:

```text
"I have the Todo ID.
I'll find the Todo.
Then I'll check who owns it."
```

That produces:

```js
const todo = await Todo.findById(todoId);

if (todo.userId !== actorId) {
    throw new ForbiddenError();
}
```

This can work logically, but you're separating:

```text
resource lookup
```

from:

```text
authorization scope
```

A stronger design is:

```js
const todo = await Todo.findOne({
    _id: todoId,
    userId: actorId
});
```

Now the database lookup itself is scoped.

---

# 3. Think in Terms of Scope

This is the most important concept of this lesson.

Don't think:

```text
Find Todo 123.
```

Think:

```text
Find Todo 123
WITHIN MY AUTHORIZED SCOPE.
```

For a normal user:

```text
authorized scope = userId
```

For a multi-tenant application:

```text
authorized scope = organizationId
```

For some systems:

```text
authorized scope = teamId
```

So the general pattern is:

```text
resource identifier
+
authorization scope
```

---

# 4. Basic Pattern

For user-owned data:

```js
Model.findOne({
    _id: resourceId,
    userId: actorId
});
```

For organization-owned data:

```js
Model.findOne({
    _id: resourceId,
    organizationId: organizationId
});
```

For instructor-owned courses:

```js
Course.findOne({
    _id: courseId,
    instructorId: instructorId
});
```

Same idea every time.

---

# 5. Why `_id` Alone Isn't Enough

Consider:

```js
Todo.findById(todoId);
```

The only condition is:

```text
_id = todoId
```

MongoDB doesn't know:

```text
Who is requesting this?
```

So if User B knows User A's Todo ID:

```text
User B
   ↓
Todo A's ID
   ↓
findById()
   ↓
Todo A returned
```

That's exactly the kind of situation that can cause **horizontal privilege escalation**, which you studied earlier in Phase 15.

---

# 6. Add the Owner

Now:

```js
Todo.findOne({
    _id: todoId,
    userId: actorId
});
```

The query means:

```text
_id matches
     AND
userId matches
```

Both conditions must be true.

So:

```text
User B
actorId = 202

Todo A
_id = 500
userId = 101
```

Query:

```js
{
    _id: 500,
    userId: 202
}
```

Result:

```text
null
```

User B doesn't get User A's Todo.

---

# 7. Design the Query From the Security Requirement

This is a very useful professional habit.

Don't start with:

> "Which Mongoose method should I use?"

Start with:

> **"What data is this actor allowed to access?"**

Example:

```text
Requirement:
User can access only their own Todos.
```

Translate it:

```text
Todo must belong to actor.
```

Translate that into data:

```text
Todo.userId === actorId
```

Translate that into MongoDB:

```js
{
    userId: actorId
}
```

Then add the resource identifier:

```js
{
    _id: todoId,
    userId: actorId
}
```

That's query design.

---

# 8. Secure Read-One Query

### Requirement

> User can read their own Todo.

### Query

```js
const todo = await Todo.findOne({
    _id: todoId,
    userId: actorId
});
```

This is the basic pattern.

---

# 9. Secure Read-Many Query

Now suppose:

```http
GET /api/v1/todos
```

Don't do:

```js
Todo.find({});
```

because that means:

```text
Give me everybody's Todos.
```

Instead:

```js
Todo.find({
    userId: actorId
});
```

Now:

```text
User A
   ↓
only User A's Todos
```

---

# 10. Secure Search Query

Suppose:

```http
GET /api/v1/todos?search=docker
```

A dangerous query:

```js
Todo.find({
    title: {
        $regex: search
    }
});
```

That searches everyone's Todos.

Instead:

```js
Todo.find({
    userId: actorId,
    title: {
        $regex: search
    }
});
```

Now:

```text
ownership scope
      +
search condition
```

Both are enforced.

---

# 11. Secure Filtering

Suppose the API supports:

```http
GET /todos?completed=true
```

Don't do:

```js
Todo.find({
    completed: true
});
```

Instead:

```js
Todo.find({
    userId: actorId,
    completed: true
});
```

The general rule:

> **Every query condition is added to an already-authorized scope.**

Think:

```text
Authorized scope
       +
User filters
       +
Search
       +
Sorting
       +
Pagination
```

---

# 12. Secure Update Query

This is where things become very important.

Unsafe:

```js
Todo.findByIdAndUpdate(
    todoId,
    updateData
);
```

A user who knows another user's Todo ID could potentially modify it.

Instead:

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId: actorId
    },
    updateData,
    {
        new: true
    }
);
```

Now the update is allowed only if:

```text
Todo exists
AND
Todo belongs to actor
```

---

# 13. Secure Delete Query

Unsafe:

```js
Todo.findByIdAndDelete(todoId);
```

Secure ownership-scoped version:

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId: actorId
});
```

Again:

```text
resource ID
+
owner ID
```

---

# 14. Secure Bulk Delete

This is a place beginners often forget.

Suppose:

```http
DELETE /api/v1/todos
```

with:

```json
{
    "ids": ["1", "2", "3"]
}
```

Dangerous:

```js
Todo.deleteMany({
    _id: {
        $in: ids
    }
});
```

That says:

> Delete these IDs, regardless of ownership.

Instead:

```js
Todo.deleteMany({
    _id: {
        $in: ids
    },
    userId: actorId
});
```

Now only the actor's matching Todos can be deleted.

---

# 15. Secure Count Query

Suppose the frontend needs:

```text
Total Todos: 42
```

Don't do:

```js
Todo.countDocuments({});
```

because that gives:

```text
all users' Todos
```

Instead:

```js
Todo.countDocuments({
    userId: actorId
});
```

Now the count belongs to the current user's scope.

---

# 16. Secure Pagination

Suppose:

```http
GET /todos?page=2&limit=20
```

The query must start with:

```js
Todo.find({
    userId: actorId
})
.skip(skip)
.limit(limit);
```

Not:

```js
Todo.find({})
    .skip(skip)
    .limit(limit);
```

Otherwise you're paginating across everybody's data.

The authorization scope must remain present regardless of pagination.

---

# 17. Secure Aggregation

Suppose you calculate:

```text
number of completed Todos
```

A dangerous aggregation could process the entire collection.

Instead, establish the scope first:

```js
Todo.aggregate([
    {
        $match: {
            userId: actorId
        }
    },
    {
        $match: {
            completed: true
        }
    }
]);
```

Or combine them:

```js
Todo.aggregate([
    {
        $match: {
            userId: actorId,
            completed: true
        }
    }
]);
```

The important idea is:

```text
Scope first
then business filtering.
```

---

# 18. The "Scope First" Rule

I want you to remember this phrase:

> **Scope first, operation second.**

For example:

```text
Scope:
userId = actorId

Operation:
completed = true
```

Together:

```js
{
    userId: actorId,
    completed: true
}
```

For an organization:

```text
Scope:
organizationId = organizationId

Operation:
status = "active"
```

Together:

```js
{
    organizationId,
    status: "active"
}
```

This is an excellent way to think about secure query construction.

---

# 19. Don't Trust the Client's Scope

Suppose the request is:

```http
GET /todos?userId=202
```

The user is authenticated as:

```text
actorId = 101
```

Do not simply do:

```js
Todo.find({
    userId: req.query.userId
});
```

The client is trying to choose the scope.

Instead:

```js
Todo.find({
    userId: actorId
});
```

The authenticated identity should determine the ownership boundary.

---

# 20. The Same Problem With Route Parameters

Suppose:

```http
GET /users/202/todos
```

and the current user is:

```text
101
```

Don't blindly assume:

```js
const userId = req.params.userId;
```

means:

```text
authenticated user
```

It means:

```text
user ID requested by the client
```

Those are different things.

Your security identity should come from your authentication layer:

```js
req.user.id
```

Then authorization determines whether the actor can access the requested user's resources.

---

# 21. Owner ID Should Come From the Server

When creating a resource:

Bad:

```js
Todo.create(req.body);
```

If the client sends:

```json
{
    "title": "Learn security",
    "userId": "202"
}
```

you've allowed the client to choose ownership.

Instead:

```js
Todo.create({
    title: data.title,
    userId: actorId
});
```

The server decides:

```text
authenticated actor
       ↓
resource owner
```

---

# 22. Mass Assignment Connection

This connects directly to another security idea.

Suppose your model contains:

```text
title
completed
userId
role
```

and you do:

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId: actorId
    },
    req.body
);
```

The query is scoped correctly.

But what if the client sends:

```json
{
    "title": "Updated",
    "userId": "202"
}
```

Now you've created a different problem:

```text
ownership query = secure
update fields = unsafe
```

So you need **both**:

```text
secure query
+
safe update fields
```

For example:

```js
const updateData = {
    title: body.title,
    completed: body.completed
};
```

Then:

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId: actorId
    },
    updateData
);
```

This is defense in depth.

---

# 23. Ownership Is Not Always `userId`

Don't blindly copy:

```js
userId
```

into every project.

Your domain may use:

```text
ownerId
```

or:

```text
instructorId
```

or:

```text
organizationId
```

or:

```text
tenantId
```

For example, your LMS Course could be:

```text
Course
├── _id
├── title
├── instructorId
└── status
```

Then:

```js
Course.findOne({
    _id: courseId,
    instructorId: actorId
});
```

---

# 24. Ownership vs Membership

This is a subtle but important distinction.

Imagine:

```text
Project
```

A project might have:

```text
ownerId
members[]
```

User A may not be the owner but may still be allowed to access it.

So:

```text
ownerId === actorId
```

would be too restrictive.

You might need:

```js
Project.findOne({
    _id: projectId,
    members: actorId
});
```

or a more complex authorization model.

So always ask:

> **What relationship gives this actor access to the resource?**

It isn't always ownership.

---

# 25. Organization-Based Scope

Imagine your LMS becomes multi-tenant:

```text
Organization A
   ├── Instructor 1
   ├── Instructor 2
   └── Courses

Organization B
   ├── Instructor 3
   └── Courses
```

Now a user may access only their organization's data.

A secure query could be:

```js
Course.findOne({
    _id: courseId,
    organizationId: actor.organizationId
});
```

The critical security boundary becomes:

```text
organizationId
```

rather than just:

```text
userId
```

---

# 26. Multiple Scope Conditions

Sometimes you need more than one boundary.

For example:

```js
Course.findOne({
    _id: courseId,
    organizationId: actor.organizationId,
    instructorId: actor.id
});
```

Now all three conditions must match.

This can be useful when:

```text
organization
+
ownership
+
resource ID
```

all matter.

---

# 27. Role-Based Scope

Admins may have a different scope.

For example:

```text
normal user:
    own resources only

instructor:
    own courses

admin:
    organization resources

superadmin:
    all resources
```

Your repository methods might therefore differ.

For a normal user:

```js
findOwnedByUser()
```

For an organization admin:

```js
findByOrganization()
```

For a trusted system operation:

```js
findById()
```

The important thing is that **the wider scope must be intentional**, not accidental.

---

# 28. Avoid a Dangerous Generic Repository

Imagine you expose:

```js
todoRepository.findById(todoId);
```

everywhere.

A developer may later write:

```js
const todo = await todoRepository.findById(todoId);
```

without thinking about ownership.

A more secure repository API can make scope obvious:

```js
todoRepository.findOwnedByUser({
    todoId,
    userId
});
```

This makes the safe path easy to use.

---

# 29. Repository Methods Should Express Intent

Compare:

```js
findById(id)
```

with:

```js
findOwnedByUser({
    todoId,
    userId
})
```

The second one tells you:

```text
This query has an ownership boundary.
```

Similarly:

```js
updateOwnedByUser()
deleteOwnedByUser()
findManyOwnedByUser()
```

This is a useful architecture pattern.

# 30. Service + Secure Repository

Let's put everything together.

### Controller

```js
const updateTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.updateTodo({
        actorId: req.user.id,
        todoId: req.params.id,
        data: {
            title: req.body.title,
            completed: req.body.completed
        }
    });

    return res.status(200).json({
        success: true,
        data: todo
    });
});
```

### Service

```js
async function updateTodo({
    actorId,
    todoId,
    data
}) {
    const todo = await todoRepository.updateOwnedByUser({
        todoId,
        userId: actorId,
        data
    });

    if (!todo) {
        throw new NotFoundError("Todo not found");
    }

    return todo;
}
```

### Repository

```js
async function updateOwnedByUser({
    todoId,
    userId,
    data
}) {
    return Todo.findOneAndUpdate(
        {
            _id: todoId,
            userId
        },
        data,
        {
            new: true
        }
    );
}
```

Notice how every layer has a clear responsibility.

# 32. Common Vulnerability Pattern

A vulnerable API often looks like this:

```text
GET /todos/:id
     ↓
findById(id)
     ↓
return document
```

The attacker discovers:

```text
Todo 100
Todo 101
Todo 102
Todo 103
```

and changes:

```text
/todos/100
```

to:

```text
/todos/101
```

If Todo 101 belongs to another user, they've accessed someone else's data.

This is commonly associated with **IDOR/BOLA-style authorization failures**, which your roadmap later covers in the Security Testing phase.

---

# 33. Secure Version

Instead:

```text
GET /todos/:id
     ↓
authenticated actor
     ↓
findOne({
    _id: id,
    userId: actorId
})
     ↓
return only matching document
```

Now changing the ID doesn't bypass the ownership boundary.

# 34. Don't Forget Relationships

Suppose:

```text
Course
  ↓
Lessons
```

A user requests:

```http
GET /courses/123/lessons/456
```

Don't only check:

```js
Lesson.findOne({
    _id: lessonId
});
```

You may need to ensure the lesson belongs to:

```text
Course 123
```

and the actor can access:

```text
Course 123
```

For example, conceptually:

```js
Lesson.findOne({
    _id: lessonId,
    courseId: courseId
});
```

and the service separately establishes that the actor can access that course.

This gives you:

```text
actor
 ↓
course access
 ↓
lesson relationship
 ↓
lesson
```

# 35. Secure Nested Data Access

This is a useful mental model:

```text
Actor
  ↓
Parent resource authorization
  ↓
Child resource relationship
  ↓
Child resource
```

For example:

```text
User
 ↓
Course
 ↓
Lesson
```

Don't assume that knowing a Lesson ID is enough.

# 36. The Database Query Should Be Narrow

A secure query should retrieve:

> **The smallest set of data necessary for the operation.**

Instead of:

```js
Todo.findById(todoId);
```

use:

```js
Todo.findOne({
    _id: todoId,
    userId: actorId
});
```

Instead of:

```js
Todo.find({});
```

use:

```js
Todo.find({
    userId: actorId
});
```

This reduces the blast radius of mistakes.

# 38. Think Like an Attacker

For every endpoint, ask:

> "What happens if I replace this ID with somebody else's ID?"

For:

```text
GET /todos/:id
PATCH /todos/:id
DELETE /todos/:id
```

try:

```text
my ID
↓
someone else's ID
```

If the operation still succeeds:

```text
🚨 Authorization vulnerability
```

If the query is:

```js
{
    _id: resourceId,
    userId: actorId
}
```

the attack should fail.

# 40. What About Admins?

Suppose admins can modify any course.

Don't simply remove ownership checks everywhere.

Instead, make the broader scope explicit.

For example, the service can determine:

```text
actor.role === ADMIN
```

and intentionally call a repository method with a broader scope.

Conceptually:

```text
Instructor
   ↓
findOwnedByInstructor()

Admin
   ↓
findById()
```

The important point:

> **A broader query should be the result of an intentional authorization decision.**

It shouldn't happen because somebody forgot the ownership filter.

# 41. Secure Query Design Checklist

Whenever you build a repository method, ask:

### 1. What resource am I accessing?

```text
Todo
Course
User
Order
```

### 2. Who is requesting it?

```text
actorId
```

### 3. What scope does the actor have?

```text
user
organization
team
role
membership
```

### 4. What operation is being performed?

```text
read
create
update
delete
search
```

### 5. Is the scope included in the query?

```text
YES / NO
```

### 6. Can the client control the scope?

```text
If yes → 🚨 inspect carefully
```

### 7. Does bulk/search/count/aggregation also preserve the scope?

```text
YES / NO
```

This checklist will save you many bugs.

# 43. The Most Important Rule of 15.16

Write this in your notes:

> ### **Never design a query only around the resource ID. Design it around the resource ID + the actor's authorized scope.**

Instead of:

```js
findById(resourceId)
```

think:

```js
findOne({
    _id: resourceId,
    userId: actorId
});
```

Or:

```js
findOne({
    _id: resourceId,
    organizationId: actor.organizationId
});
```

Or:

```js
findOne({
    _id: resourceId,
    instructorId: actor.id
});
```

The exact field changes.

The security principle doesn't.
