# Lesson 15.17 — Testing Authorization

Your Phase 15 roadmap has **15.17 — Testing authorization** immediately before **15.18 — Build RBAC architecture**.

This lesson is extremely important because authorization code can **look correct while still being vulnerable**.

The goal is:

> **Don't just test that authorized users can do something. Test that unauthorized users definitely cannot.**

---

# 1. Why Authorization Needs Special Testing

Imagine you wrote:

```js
Todo.findOne({
    _id: todoId,
    userId: actorId
});
```

Looks secure.

But what if:

```text
DELETE /todos/:id
```

still uses:

```js
Todo.findByIdAndDelete(todoId);
```

Your GET endpoint is protected, but DELETE is vulnerable.

That's why we test authorization **operation by operation**.

---

# 2. The Most Important Authorization Test

Your first question should always be:

> **Can User A access User B's resource?**

For example:

```text
User A
id = 101

User B
id = 202
```

User B owns:

```text
Todo B
id = 500
userId = 202
```

Now User A tries:

```http
GET /api/v1/todos/500
Authorization: Bearer <user-A-token>
```

Expected:

```text
❌ Access denied
```

This is one of the most important security tests in your backend.

---

# 3. Positive and Negative Tests

Authorization testing needs both.

### Positive test

```text
User owns resource
       ↓
operation succeeds
```

### Negative test

```text
User does NOT own resource
       ↓
operation fails
```

For example:

```text
User A → Todo A → 200
User A → Todo B → 403/404
```

Both tests matter.

---

# 4. Don't Test Only the Happy Path

A weak test suite might contain:

```js
it("gets todo", async () => {
    ...
});
```

But what does that prove?

Only:

```text
Someone can get a Todo.
```

It doesn't prove:

```text
Only authorized users can get it.
```

A security-focused suite asks:

```text
Can owner access?
Can another user access?
Can unauthenticated user access?
Can wrong role access?
Can wrong permission access?
```

---

# 5. Build Two Users in Tests

A very useful pattern is to create:

```text
userA
userB
```

Then create:

```text
todoA → owned by userA
todoB → owned by userB
```

Now your tests can simulate real authorization boundaries.

Conceptually:

```js
const userA = await createTestUser();
const userB = await createTestUser();

const todoA = await createTodo({
    userId: userA.id
});

const todoB = await createTodo({
    userId: userB.id
});
```

Now we can attack our own API.

---

# 6. Test: Owner Can Read

Scenario:

```text
User A
   ↓
Todo A
```

Request:

```http
GET /todos/A
```

Expected:

```text
200 OK
```

Test idea:

```js
it("allows owner to read their todo", async () => {
    const response = await request(app)
        .get(`/api/v1/todos/${todoA.id}`)
        .set("Authorization", `Bearer ${tokenA}`);

    expect(response.status).toBe(200);
});
```

The exact implementation depends on your test architecture, but the idea is simple.

---

# 7. Test: Another User Cannot Read

Now:

```text
User B
   ↓
tries to read
   ↓
Todo A
```

Expected:

```text
403
```

or:

```text
404
```

depending on your API's chosen information-disclosure policy.

Example:

```js
it("does not allow another user to read the todo", async () => {
    const response = await request(app)
        .get(`/api/v1/todos/${todoA.id}`)
        .set("Authorization", `Bearer ${tokenB}`);

    expect([403, 404]).toContain(response.status);
});
```

This test is much more valuable than simply testing a successful GET.

---

# 8. Test Update Authorization

Don't stop at GET.

Try:

```text
User B
   ↓
PATCH /todos/A
```

Expected:

```text
DENIED
```

Test:

```js
it("does not allow another user to update the todo", async () => {
    const response = await request(app)
        .patch(`/api/v1/todos/${todoA.id}`)
        .set("Authorization", `Bearer ${tokenB}`)
        .send({
            title: "Hacked title"
        });

    expect([403, 404]).toContain(response.status);
});
```

Then verify the database:

```text
Todo A title
       ↓
still unchanged
```

This second check is important.

---

# 9. Test Delete Authorization

This is even more important.

User B:

```text
DELETE /todos/A
```

Expected:

```text
DENIED
```

Then verify:

```text
Todo A still exists
```

Because an endpoint could return:

```text
403
```

while accidentally deleting the resource due to a bug elsewhere.

Security tests should verify the **side effect**, not just the HTTP status.

---

# 10. Authorization Test Matrix

For a user-owned Todo, think in a matrix:

|Actor|Resource|Read|Update|Delete|
|---|---|--:|--:|--:|
|Owner|Own Todo|✅|✅|✅|
|Other user|Owner's Todo|❌|❌|❌|
|Unauthenticated|Any Todo|❌|❌|❌|
|Admin*|Other user's Todo|Depends on policy|Depends|Depends|

`*` Admin behavior should be explicitly defined by your application.

This matrix is an excellent way to discover missing tests.

---

# 11. Test Authentication Separately

Before authorization, test authentication.

For example:

```text
No token
    ↓
401 Unauthorized
```

Invalid token:

```text
Invalid JWT
    ↓
401
```

Expired token:

```text
Expired JWT
    ↓
401
```

Then authorization:

```text
Valid token
+
insufficient permission
    ↓
403
```

This gives you the important distinction:

```text
401 = authentication problem
403 = authorization problem
```

---

# 12. Test Role Authorization

Suppose:

```text
USER
ADMIN
```

Endpoint:

```http
DELETE /admin/users/:id
```

Test:

```text
Admin → allowed
User  → denied
```

For example:

```js
it("allows admin to delete users", async () => {
    ...
    expect(response.status).toBe(200);
});
```

And:

```js
it("does not allow normal user to delete users", async () => {
    ...
    expect(response.status).toBe(403);
});
```

Both are required.

---

# 13. Test Permission Authorization

Suppose you move from simple roles to permissions:

```text
users:read
users:create
users:update
users:delete
```

A user might have:

```text
users:read
```

but not:

```text
users:delete
```

Test:

```text
Permission exists
    ↓
operation succeeds
```

and:

```text
Permission missing
    ↓
operation fails
```

This becomes especially important when you build the RBAC architecture in **15.18**.

---

# 14. Test Horizontal Privilege Escalation

You studied this in 15.10.

The test is:

```text
User A
  ↓
tries User B's resource
```

Examples:

```text
GET /users/B/profile
PATCH /todos/B
DELETE /documents/B
GET /courses/B
```

Every resource should have a corresponding negative authorization test.

A good security test suite intentionally tries to cross the user boundary.

---

# 15. Test Vertical Privilege Escalation

You also studied this in 15.11.

Example:

```text
USER
  ↓
tries admin endpoint
```

For:

```http
DELETE /admin/users/202
```

test:

```text
Normal user → 403
Admin → success
```

Don't assume role middleware works simply because you've tested it once.

Test every sensitive route group.

---

# 16. Test ID Manipulation

This is a very practical security test.

Suppose User A owns:

```text
Todo ID = 100
```

User B owns:

```text
Todo ID = 200
```

User A normally calls:

```http
GET /todos/100
```

Then deliberately change it:

```http
GET /todos/200
```

Expected:

```text
DENIED
```

This directly tests for IDOR/BOLA-style vulnerabilities.

Your roadmap's security-testing section explicitly includes **IDOR** and **broken authorization** as later security-testing topics.

---

# 17. Test Update With Another User's ID

Don't test only GET.

Try:

```http
PATCH /todos/200
```

with User A's token.

Then:

```text
database should remain unchanged
```

This is important because developers sometimes secure:

```text
GET
```

but forget:

```text
PATCH
DELETE
```

---

# 18. Test Delete With Another User's ID

This should be one of your strongest tests.

```text
User A
   ↓
DELETE User B's Todo
```

Expected:

```text
request rejected
+
Todo B still exists
```

That's a complete authorization test.

---

# 19. Test Bulk Authorization

Suppose User A sends:

```json
{
    "ids": [
        "todoA",
        "todoB"
    ]
}
```

where:

```text
todoA → User A
todoB → User B
```

Now ask:

> What should happen?

You need an explicit policy.

Possible behavior:

### Option 1

Only modify User A's Todo.

```text
todoA → deleted
todoB → untouched
```

### Option 2

Reject the entire request.

```text
403
```

The important thing is:

> **The behavior must be intentional and tested.**

---

# 20. Test Search Authorization

Suppose User A searches:

```http
GET /todos?search=password
```

The response must contain only:

```text
User A's Todos
```

not:

```text
User B's matching Todos
```

This is a very good integration test because a developer might accidentally write:

```js
Todo.find({
    title: /password/i
});
```

instead of:

```js
Todo.find({
    userId: actorId,
    title: /password/i
});
```

---

# 21. Test Pagination Authorization

Suppose:

```text
User A has 10 Todos
User B has 100 Todos
```

User A requests:

```http
GET /todos?page=1&limit=20
```

Expected:

```text
10 or fewer records
```

and:

```text
total = 10
```

not:

```text
total = 110
```

This verifies that your count and data queries both use the authorization scope.

---

# 22. Test Aggregation Authorization

If you have:

```text
GET /todos/stats
```

User A should receive:

```text
User A's statistics
```

not:

```text
all users' statistics
```

For example:

```text
User A:
completed = 5

User B:
completed = 50
```

User A should not receive:

```text
completed = 55
```

This tests whether your aggregation has the proper `$match` scope.

---

# 23. Test Resource State Authorization

Remember from 15.14:

```text
permission
+
ownership
+
business state
```

Suppose:

```text
Course status = published
```

and:

```text
published course cannot be edited
```

Test:

```text
Owner + draft course
    ↓
allowed

Owner + published course
    ↓
denied
```

This ensures your service-level business authorization is actually working.

---

# 24. Test Admin Boundaries

Suppose:

```text
admin
superadmin
```

You might have:

```text
admin → can modify normal users
admin → cannot modify superadmin
```

Test both:

```text
Admin → User → allowed
Admin → Superadmin → denied
```

This is exactly the kind of contextual authorization that simple:

```js
requireRole("admin")
```

cannot test by itself.

---

# 25. Test Self-Protection Rules

Suppose:

```text
Admin cannot delete themselves.
```

Test:

```text
Admin A
    ↓
DELETE Admin A
```

Expected:

```text
DENIED
```

Then:

```text
Admin A
    ↓
DELETE User B
```

Expected:

```text
ALLOWED
```

assuming your policy allows it.

These business authorization rules are easy to forget, so they deserve tests.

---

# 26. Test the Database After Sensitive Operations

Don't only write:

```js
expect(response.status).toBe(403);
```

Also check:

```js
const todo = await Todo.findById(todoB.id);

expect(todo.title).toBe(originalTitle);
```

For delete:

```js
const todo = await Todo.findById(todoB.id);

expect(todo).not.toBeNull();
```

This verifies that authorization failure actually prevented the side effect.

---

# 27. Test at the API Level

For important authorization rules, integration tests are extremely useful.

Your roadmap already separates:

```text
unit tests
integration tests
```

and specifically includes:

```text
Testing authentication
Testing authorization
Testing CRUD
```

in the backend-testing phase.

A complete request test looks like:

```text
Supertest
   ↓
HTTP
   ↓
Route
   ↓
Auth middleware
   ↓
Authorization
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓

```

This is much stronger than testing one function in isolation.

---

# 28. Unit Test the Authorization Logic Too

Integration tests aren't the only tool.

Suppose your service contains:

```js
if (todo.userId !== actorId) {
    throw new ForbiddenError();
}
```

You can unit test:

```text
owner → allowed
different user → rejected
```

This makes failures easier to diagnose.

So ideally:

```text
Unit tests
+
Integration tests
```

---

# 29. Mocking Authorization Dependencies

For a service unit test, you might mock:

```js
todoRepository.findOwnedByUser
```

Example concept:

```text
Service
  ↓
mock repository
```

Then test:

```text
repository returns owned Todo
    ↓
service allows operation
```

and:

```text
repository returns null
    ↓
service rejects operation
```

This isolates business logic.

---

# 30. But Don't Mock Everything

If you mock the entire authorization system:

```text
mock auth
mock middleware
mock service
mock repository
mock database
```

you may end up testing almost nothing real.

For security-sensitive behavior, keep integration tests that exercise the actual chain:

```text
HTTP
 ↓
authentication
 ↓
authorization
 ↓
service
 ↓
repository
 ↓
database
```

That's where many real bugs occur.

---

# 31. Test Every Sensitive Endpoint

Make a table.

For example:

|Endpoint|Auth|Role|Ownership|
|---|---|---|---|
|`GET /todos`|✅|—|User|
|`GET /todos/:id`|✅|—|User|
|`POST /todos`|✅|—|Actor|
|`PATCH /todos/:id`|✅|—|Owner|
|`DELETE /todos/:id`|✅|—|Owner|
|`GET /admin/users`|✅|Admin|—|
|`DELETE /admin/users/:id`|✅|Admin|Business rules|

Then create tests from this table.

This is a very practical technique.

---

# 32. Authorization Test Naming

Good test names should explain the security rule.

Weak:

```js
it("works", ...)
```

Better:

```js
it("allows a user to update their own todo", ...)
```

Even better:

```js
it("rejects a user attempting to update another user's todo", ...)
```

When the test fails six months later, you'll immediately understand the security rule.

---

# 33. Test Both Sides of Every Rule

For every authorization rule:

```text
ALLOW
DENY
```

For example:

### Rule

> Only course instructors can update their course.

Tests:

```text
Instructor + own course → ALLOW
Instructor + another course → DENY
Student + course → DENY
Unauthenticated + course → DENY
```

That's much stronger than one test.

---

# 34. Test Role Changes

Suppose a user's role changes:

```text
USER → ADMIN
```

After the change:

```text
admin endpoint → allowed
```

If:

```text
ADMIN → USER
```

then:

```text
admin endpoint → denied
```

This becomes especially important if your authorization information is stored inside JWTs.

You need to understand whether your architecture uses:

```text
fresh database role
```

or:

```text
role embedded in token
```

because that affects when permission changes take effect.

---

# 35. Test Token-Based Authorization Carefully

Suppose JWT contains:

```json
{
    "sub": "101",
    "role": "user"
}
```

Don't assume that changing the database role automatically changes the already-issued token's authorization behavior.

Your tests should reflect your chosen architecture.

This is a good example of why authentication and authorization tests must be connected.

---

# 36. Test Expired Authentication

Try:

```text
expired access token
       ↓
protected endpoint
```

Expected:

```text
401
```

Then test:

```text
valid token
+
insufficient role
```

Expected:

```text
403
```

This confirms that your layers are behaving correctly.

---

# 37. Test Missing Permission

Suppose:

```text
User permissions:
[
    "todos:read"
]
```

Request:

```http
DELETE /todos/123
```

Required:

```text
todos:delete
```

Expected:

```text
403
```

This is permission-based authorization testing.

---

# 38. Test Permission Combinations

Suppose an endpoint requires:

```text
todos:read
AND
todos:private
```

or perhaps:

```text
todos:read
OR
todos:admin
```

Don't assume your authorization middleware handles logical combinations correctly.

Write explicit tests:

```text
permission A only
permission B only
both
neither
```

This becomes useful as your RBAC system grows.

---

# 39. Test "Confused Deputy" Scenarios

This is a more advanced idea.

Suppose an admin endpoint performs an operation on behalf of a user.

You need to ensure:

```text
the caller's authorization
```

isn't accidentally replaced by:

```text
the target user's identity
```

For example:

```text
Admin A
   ↓
modify User B's Todo
```

The system should intentionally determine:

```text
Is Admin A allowed to do this?
```

not:

```text
Does Todo belong to User B?
→ therefore allowed
```

This is where explicit actor/target modeling helps.

---

# 40. Test Authorization Bypass Attempts

Think like an attacker.

Try changing:

```text
resource ID
user ID
role
permission
HTTP method
query parameters
body fields
```

Examples:

```text
/todos/123
→ /todos/124

?userId=A
→ ?userId=B

role=user
→ role=admin

ownerId=A
→ ownerId=B
```

Your server should never trust client-controlled authorization fields.

---

# 41. Test Mass Assignment + Authorization Together

Suppose:

```http
PATCH /todos/123
```

attacker sends:

```json
{
    "title": "Hacked",
    "userId": "attacker-id"
}
```

You need to verify:

```text
ownership cannot be changed
```

Even if:

```text
the attacker owns the Todo
```

they shouldn't necessarily be able to modify:

```text
userId
```

This combines:

```text
authorization
+
input control
+
mass-assignment protection
```

# 42. Test That Sensitive Fields Stay Protected

For a User:

```json
{
    "role": "admin"
}
```

A normal user shouldn't be able to send:

```http
PATCH /users/me
```

and become admin.

Test:

```js
expect(updatedUser.role).toBe("user");
```

even when the request contains:

```json
{
    "role": "admin"
}
```

This is a very important authorization/security test.

---

# 43. Test Error Consistency

Your tests should also verify that authorization failures produce consistent responses.

For example:

```json
{
    "success": false,
    "message": "Forbidden"
}
```

or your chosen format.

Don't allow one endpoint to return:

```text
403
```

another:

```text
401
```

and another:

```text
500
```

for the same authorization problem.

Consistent errors make your frontend and security monitoring much easier.

---

# 44. Don't Reveal Too Much in Tests

If your API intentionally returns:

```text
404
```

instead of:

```text
403
```

for resources belonging to other users, test that behavior.

For example:

```js
expect(response.status).toBe(404);
```

This confirms your API isn't accidentally leaking:

> "That resource exists, but you don't have permission."

The exact choice is application-specific.

# 45. A Practical Authorization Test Structure

You could organize your tests like:

```text
tests/
└── integration/
    ├── auth/
    │   ├── login.test.js
    │   └── token.test.js
    │
    ├── authorization/
    │   ├── roles.test.js
    │   ├── permissions.test.js
    │   ├── ownership.test.js
```

You don't have to copy this exact structure, but organizing security tests separately can make them much easier to find.

# 46. The Most Important Ownership Test Suite

For a Todo resource, I would want at least:

```text
✓ owner can create Todo
✓ owner can read Todo
✓ owner can update Todo
✓ owner can delete Todo

✓ another user cannot read Todo
✓ another user cannot update Todo
✓ another user cannot delete Todo

✓ unauthenticated user cannot read Todo
✓ unauthenticated user cannot update Todo
✓ unauthenticated user cannot delete Todo
```

Then:

```text
✓ user cannot change Todo owner
✓ user cannot access another user's search results
✓ user cannot access another user's pagination
✓ user cannot delete another user's Todo in bulk
```

That's a serious authorization baseline.

# 47. Think in Security Invariants

This is an advanced but very useful way to test.

Instead of only testing endpoints, define invariants.

For example:

> **Invariant: A user can never modify a Todo they don't own.**

Now test this invariant across:

```text
PATCH
PUT
DELETE
bulk update
bulk delete
```

Another:

> **Invariant: A normal user can never assign themselves an admin role.**

Test:

```text
POST
PATCH
PUT
signup
profile update
```

This mindset is much stronger than testing individual routes randomly.

# 🧠 The Most Important Lesson

Don't ask only:

> **"Does my authorization code work?"**

Ask:

> **"Can I prove that an attacker cannot cross my authorization boundary?"**

For example:

```text
User A
  │
  ├── Own Todo
  │      └── ✅ allowed
  │
  └── User B's Todo
         └── ❌ denied
```

And then test it through:

```text
GET
PATCH
DELETE
SEARCH
BULK
PAGINATION
```

That's how authorization becomes something you can **trust**, rather than something you merely hope works.
