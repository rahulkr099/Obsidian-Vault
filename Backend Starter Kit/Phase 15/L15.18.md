# 1. First: What Does RBAC Actually Mean?

RBAC means:

> **Role-Based Access Control**

Instead of asking every time:

```js
if (user.email === "admin@example.com")
```

we define roles.

For example:

```text
USER
INSTRUCTOR
ADMIN
```

Then each role has permissions.

Think:

```text
USER
 ├── todos:read
 ├── todos:create
 ├── todos:update-own
 └── todos:delete-own

INSTRUCTOR
 ├── courses:read
 ├── courses:create
 ├── courses:update-own
 └── courses:publish

ADMIN
 ├── users:read
 ├── users:update
 ├── users:delete
 ├── courses:read
 ├── courses:update
 └── courses:delete
```

The exact roles and permissions depend on your application.

But remember:

> **RBAC doesn't replace ownership checks.**

This is extremely important.

# 3. Role ≠ Permission ≠ Ownership

These three concepts are different.

### Role

```text
ADMIN
INSTRUCTOR
USER
```

### Permission

```text
users:delete
courses:publish
todos:create
```

### Ownership

```text
todo.userId === actor.id
```

So a request may require:

```text
Authenticated
+
Correct role
+
Correct permission
+
Correct ownership
+
Valid resource state
```

This is why your previous lessons were necessary.

# 8. Why Use Permissions?

Imagine you have 30 endpoints.

If every route says:

```js
requireRole("admin")
```

you eventually get a problem.

Maybe you want:

```text
Instructor → courses:create
Admin → courses:create
```

Both roles should have the same permission.

If your application is based only on roles, you might write:

```text
requireRole("admin", "instructor")
```

everywhere.

That becomes messy.

Permissions solve this.

You can say:

```js
requirePermission(PERMISSIONS.COURSES_CREATE)
```

Now you don't care which role grants it.

# 10. Permission Middleware

Conceptually:

```js
const requirePermission = (permission) => {
    return (req, res, next) => {
        if (!req.user) {
            return next(new UnauthorizedError());
        }

        if (!hasPermission(req.user, permission)) {
            return next(new ForbiddenError());
        }

        next();
    };
};
```

Then:

```js
router.post(
    "/courses",
    authMiddleware,
    requirePermission(PERMISSIONS.COURSES_CREATE),
    courseController.create
);
```

The route now clearly communicates:

```text
Authentication required
+
courses:create permission required
```

---

# 11. `requireRole()` Still Has a Place

You don't have to remove role middleware.

For example:

```js
router.get(
    "/admin/dashboard",
    authMiddleware,
    requireRole(ROLES.ADMIN),
    adminController.dashboard
);
```

Role checks are useful when:

> **The entire endpoint is fundamentally restricted to a role.**

Permission checks are useful when:

> **The operation itself is the important security requirement.**

---

# 12. Role-Based vs Permission-Based

Compare:

### Role

```js
requireRole(ROLES.ADMIN)
```

Meaning:

```text
Only administrators.
```

### Permission

```js
requirePermission(PERMISSIONS.USERS_DELETE)
```

Meaning:

```text
Anyone with users:delete.
```

The second is more flexible.

# 14. But Don't Put Everything in Middleware

This is one of the most important architectural lessons.

Suppose:

```text
PUT /courses/123
```

requires:

```text
courses:update
```

Middleware can check:

```text
Does actor have courses:update?
```

But middleware may not know:

```text
Does Course 123 belong to this instructor?
```

That requires resource data.

So:

```text
Middleware
    ↓
Broad permission
```

and:

```text
Service
    ↓
Resource-specific authorization
```

This matches the architecture you've been learning in 15.14 and 15.15.

# 20. Policy Layer

As applications grow, you may introduce:

```text
policies/
├── course.policy.js
├── user.policy.js
└── todo.policy.js
```

For example:

```js
function canUpdateCourse(actor, course) {
    if (actor.role === ROLES.ADMIN) {
        return true;
    }

    if (actor.role === ROLES.INSTRUCTOR) {
        return course.instructorId === actor.id;
    }

    return false;
}
```

Then service:

```js
if (!canUpdateCourse(actor, course)) {
    throw new ForbiddenError();
}
```

This is one possible architecture.

You don't necessarily need a policy directory for every project, but the concept becomes valuable as authorization grows.

# 34. Don't Put `role` in Every Repository Query

This is a subtle design point.

Avoid things like:

```js
Todo.findOne({
    _id: todoId,
    role: "admin"
});
```

The database generally stores:

```text
Todo
 ↓
userId
```

not:

```text
Todo
 ↓
userRole
```

Role is an attribute of the actor.

Authorization determines:

```text
What scope does this actor get?
```

Then the repository receives the appropriate scope.

---

# 35. Better Service Input

Instead of:

```js

```

use something closer to:

```js
updateCourse({
    actor,
    courseId,
    data
});
```

Now the service has the information required to make an authorization decision.

For example:

```js
async function updateCourse({
```

# 36. Don't Pass `req` Into Services

Avoid:

```js

```

The service shouldn't know about Express.

Instead:

```js
courseService.updateCourse({
    actor: req.user,
    courseId: req.params.id,
    data
});
```

Now your service remains independent of HTTP.

This fits the controller/service separation you've already studied.

# 38. Example Authorization Middleware

A simple permission checker:

```js
const requirePermission = (permission) => {
    return (req, res, next) => {
        const user = req.user;

        if (!user) {
            return next(new UnauthorizedError());
        }

        const permissions =
            ROLE_PERMISSIONS[user.role] ?? [];

        if (!permissions.includes(permission)) {
            return next(new ForbiddenError());
        }

        next();
    };
};
```

Then:

```js
router.post(
    "/courses",
    authMiddleware,
    requirePermission(PERMISSIONS.COURSES_CREATE),
    courseController.create
);
```

This is the **route-level** part.

# 42. Default Deny

One of the best security principles:

> **If permission isn't explicitly granted, deny access.**

So:

```js
const permissions =
    ROLE_PERMISSIONS[user.role] ?? [];
```

If the role isn't known:

```text
[]
```

not:

```text
all permissions
```

This is called **fail closed**.

---

# 43. What Happens When a New Role Appears?

Suppose someone changes:

```text
user.role = "manager"
```

but you haven't defined:

```text
manager → permissions
```

Your system should say:

```text
no permissions
```

not:

```text
manager gets everything
```

That's another reason for:

```js
ROLE_PERMISSIONS[user.role] ?? []
```

---

# 44. Don't Trust Client-Supplied Roles

Never do:

```js
const role = req.body.role;
```

for authorization.

An attacker could send:

```json
{
    "role": "admin"
}
```

The authoritative role should come from your trusted authentication/user data.

For example:

```js
req.user.role
```

after authentication.

---

# 45. Don't Let Users Change Their Own Role

Bad:

```js
User.findByIdAndUpdate(
    userId,
    req.body
);
```

because:

```json
{
    "role": "admin"
}
```

could become a privilege escalation.

Instead, whitelist fields:

```js
const updateData = {
    firstName: body.firstName,
    lastName: body.lastName
};
```

Role changes should be handled by a separate privileged operation.

---

# 46. Dedicated Role-Change Operation

For example:

```http
PATCH /api/v1/admin/users/:id/role
```

with:

```json

```

Then authorization:

```text

    ↓

    ↓

```

This is much safer than allowing arbitrary user updates to contain `role`.
