# Lesson 15.2 — What Is a Role?

In the previous lesson, we learned:

```text
Authentication
    ↓
Who are you?

Authorization
    ↓
What are you allowed to do?
```

Now we need to understand one of the simplest ways to implement authorization:

> **Roles**

This is the foundation of **RBAC — Role-Based Access Control**.

---

# 1. What Is a Role?

A **role** is a label that represents a user's level of responsibility or access inside an application.

For example:

```text
user
admin
moderator
```

A user might have:

```js
{
    id: "123",
    email: "rahul@example.com",
    role: "user"
}
```

An administrator might have:

```js
{
    id: "456",
    email: "admin@example.com",
    role: "admin"
}
```

The role can then be used when making authorization decisions.

---

# 2. Real-World Analogy

Think about a company.

There might be:

```text
Employee
Manager
HR
Administrator
```

Everyone can enter the company.

But they don't have the same permissions.

For example:

```text
Employee
    ↓
Can view their profile

Manager
    ↓
Can view team information

HR
    ↓
Can manage employee records

Administrator
    ↓
Can manage the entire system
```

The person's **role** helps the system determine what they're allowed to do.

---

# 3. Role Is Not the Same as Identity

This is important.

Suppose:

```text
Rahul
```

is a user.

His identity is:

```text
userId = 123
```

His role is:

```text
role = "user"
```

These answer different questions:

```text
Who?
    ↓
userId = 123

What type of access?
    ↓
role = user
```

So don't confuse:

```text
User ID
```

with:

```text
Role
```

---

# 4. Where Does the Role Come From?

Typically, the role is stored with the user.

For example, your User document might contain:

```js
{
    _id: "...",
    firstName: "Rahul",
    email: "rahul@example.com",
    password: "...",
    role: "user"
}
```

Another user:

```js
{
    _id: "...",
    firstName: "Amit",
    email: "amit@example.com",
    password: "...",
    role: "admin"
}
```

So MongoDB stores information about the user's access level.

---

# 5. Why Do We Need Roles?

Imagine you have:

```text
1000 users
```

and:

```text
5 administrators
```

You don't want to write:

```js
if (user.id === "123") {
   ...
}
```

for every administrator.

Instead, you can say:

```js
if (user.role === "admin") {
   ...
}
```

Now the authorization rule is based on the **type of user**, rather than a specific person's ID.

---

# 6. Basic Role-Based Access

Imagine these rules:

```text
user
    ↓
Can create todos

admin
    ↓
Can create todos
Can delete users
Can view system statistics
```

Then your application might conceptually have:

```text
                    USER
                     │
              ┌──────┴──────┐
              │             │
          User APIs      Todo APIs


                   ADMIN
                     │
          ┌──────────┼──────────┐
          │          │          │
       User APIs  Todo APIs  Admin APIs
```

The admin has a larger access area.

---

# 7. Roles in a JWT

You may remember from Phase 14 that JWTs contain a payload.

A simplified payload could be:

```js
{
    sub: "123",
    role: "user"
}
```

After verifying the JWT:

```js
const payload = jwt.verify(token, secret);
```

you might have:

```js
req.user = payload;
```

So:

```js
req.user.role
```

could return:

```text
"user"
```

Then authorization middleware can use that information.

---

# 8. But Be Careful: JWT Role Data

There is an important security consideration here.

Suppose a user is currently:

```text
role = user
```

and their access token contains:

```json
{
    "sub": "123",
    "role": "user"
}
```

Later, an administrator changes their database role to:

```text
admin
```

The existing access token may still contain:

```text
role = user
```

until that token expires or is otherwise replaced.

The reverse situation is more concerning.

Suppose:

```text
admin
```

is changed to:

```text
user
```

but an old token still says:

```text
role = admin
```

If your authorization system blindly trusts stale role information from the JWT, you could accidentally allow access longer than intended.

This is one reason token lifetime and authorization design matter.

We'll return to this later.

---

# 9. Common Role Names

A small application might have:

```text
user
admin
```

A larger application might have:

```text
user
moderator
admin
superadmin
```

For example:

```text
user
    ↓
Normal application features

moderator
    ↓
Moderate user-generated content

admin
    ↓
Manage users and application settings

superadmin
    ↓
Manage administrators/system-level settings
```

But don't create roles just because you can.

---

# 10. Don't Create Too Many Roles

Imagine creating:

```text
user
admin
manager
editor
moderator
support
developer
senior-developer
junior-developer
finance
marketing
sales
...
```

You can quickly end up with a complicated authorization system.

A better question is:

> **What access rules does my application actually need?**

Start simple.

For example:

```text
user
admin
```

might be enough.

Later, if your requirements become more complex, you can move toward permissions.

---

# 11. Roles vs Permissions

This distinction is very important.

### Role

Describes a category of user:

```text
admin
```

### Permission

Describes a specific capability:

```text
users:read
users:create
users:update
users:delete
```

So:

```text
Role
 ↓
admin
```

could have:

```text
Permissions
 ↓
users:read
users:create
users:update
users:delete
```

This gives us:

```text
Role
   ↓
Permissions
   ↓
Actions
```

We'll study permission-based authorization later in **15.7**.

For now, focus on roles.

---

# 12. A Simple Role Model

For your backend, we could define:

```js
const ROLES = {
    USER: "user",
    ADMIN: "admin"
};
```

Then:

```js
user.role === ROLES.ADMIN
```

instead of repeatedly writing:

```js
user.role === "admin"
```

Why is this useful?

Because constants give you a single source of truth.

---

# 13. Why Constants Matter

Imagine your application accidentally contains:

```js
"admin"
"Admin"
"administrator"
"ADMIN"
```

These are different strings.

You could accidentally create authorization bugs.

Instead:

```js
export const ROLES = {
    USER: "user",
    ADMIN: "admin"
};
```

Then use:

```js
ROLES.USER
ROLES.ADMIN
```

throughout the application.

Your architecture already has a `constants` area for exactly this kind of shared value.

---

# 14. Role and Authentication Flow

Let's put everything together.

Suppose Rahul logs in.

### Step 1 — Authentication

```text
Email + Password
       ↓
Verify credentials
       ↓
User found
       ↓
JWT generated
```

The user has:

```js
{
    id: "123",
    role: "user"
}
```

---

### Step 2 — Request

Rahul requests:

```http
GET /api/v1/admin/users
```

---

### Step 3 — Authentication

```text
JWT
 ↓
verify
 ↓
req.user
```

Now:

```js
req.user.role
```

is available.

---

### Step 4 — Authorization

Check:

```js
req.user.role === ROLES.ADMIN
```

Rahul is:

```text
user
```

So:

```text
❌ Access denied
```

---

# 15. Role Middleware Preview

Later we'll create something like:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        if (req.user.role !== role) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Then:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    adminController.getUsers
);
```

The flow becomes:

```text
Request
   ↓
authenticate
   ↓
Who is this?
   ↓
req.user
   ↓
requireRole(ADMIN)
   ↓
Is user admin?
   │
   ├── NO → 403
   │
   └── YES
         ↓
      Controller
```

Don't worry about fully implementing this yet. That's coming in **15.4 and 15.5**.

---

# 16. Role Hierarchy Is Not Automatic

This is another important point.

Suppose you have:

```text
user
moderator
admin
```

Don't automatically assume:

```text
admin > moderator > user
```

unless you explicitly design it that way.

For example, perhaps:

```text
moderator
    ↓
Can moderate comments

admin
    ↓
Can manage users
```

The admin doesn't necessarily need to inherit every moderator permission unless your system says so.

Roles are simply an authorization design.

---

# 17. Role-Based Authorization Example

Imagine a blogging application.

### User

Can:

```text
Create post
Edit own post
Delete own post
Comment
```

### Moderator

Can:

```text
Everything relevant to moderation
Delete inappropriate comments
Hide reported posts
```

### Admin

Can:

```text
Manage users
Manage roles
View system statistics
Manage application settings
```

The role provides a convenient way to group these access rules.

---

# 18. Role vs Ownership

This is where authorization gets interesting.

Suppose Rahul is:

```text
role = user
```

and owns:

```text
Todo #123
```

Rahul should be allowed to:

```text
UPDATE Todo #123
```

But not:

```text
UPDATE Todo #456
```

if Todo #456 belongs to another user.

The decision isn't based only on:

```text
role = user
```

It also depends on:

```text
ownership
```

So authorization can be:

```text
Role
+
Ownership
```

We'll study this deeply later.

---

# 19. Why Admin Is Different

An administrator often has broad privileges.

For example:

```text
DELETE /users/:id
```

might be:

```text
authenticate
    ↓
requireRole(admin)
    ↓
controller
```

But a normal user might only access:

```text
GET /users/me
```

So the route architecture might look like:

```text
/user routes
    ↓
authenticate

/admin routes
    ↓
authenticate
    ↓
requireRole(admin)
```

This is a very common backend pattern.

---

# 20. Never Trust the Client's Role

This is extremely important.

Suppose React sends:

```json
{
    "role": "admin"
}
```

You should **not** say:

```js
const role = req.body.role;
```

and then trust it for authorization.

A malicious client can simply send:

```json
{
    "role": "admin"
}
```

Your backend should determine the user's role from a trusted server-side source, such as your authenticated identity/database state.

Remember:

```text
Frontend
    ↓
UNTRUSTED
    ↓
Backend
    ↓
Security decision
```

The client is allowed to **request** an action.

The server decides whether the action is allowed.

---

# 21. A Very Important Rule

Never think:

```text
"User says they are admin."
```

Think:

```text
"Backend has verified that this identity has admin privileges."
```

That's the security mindset we want.

---

# 22. Role Assignment

Another sensitive operation is:

```text
Who can change someone's role?
```

For example:

```http
PATCH /api/v1/users/123/role
```

You definitely don't want:

```text
Normal user
    ↓
Changes own role
    ↓
admin
```

That would be a serious authorization problem.

A safer design might be:

```text
Normal user
    ↓
Cannot modify roles

Admin
    ↓
May modify certain roles
```

We'll revisit this when we study **vertical privilege escalation**.

---

# 23. Mental Model

Keep this picture in your head:

```text
                  USER
                   │
                   ▼
             Authentication
                   │
                   ▼
             Identity known
                   │
                   ▼
                ROLE
                   │
          ┌────────┼────────┐
          │        │        │
         user   moderator  admin
          │        │        │
          ▼        ▼        ▼
       Allowed  Allowed   Allowed
       actions  actions   actions
```

The role doesn't authenticate the user.

Instead:

```text
Authentication
    ↓
establishes identity

Role
    ↓
helps determine authorization
```

---

# 24. What You Should Remember

If you remember only these points from 15.2, you're good:

```text
1. A role is a category that helps determine access.

2. Roles are part of authorization, not authentication.

3. A role can be stored with the user.

4. Common roles include user, moderator and admin.

5. Don't trust role information sent by the client.

6. Use constants for roles.

7. Roles are only one authorization strategy;
   ownership and permissions are also important.
```

And the core relationship:

```text
Authentication
      ↓
Who is this?
      ↓
User
      ↓
What role/access does this user have?
      ↓
Authorization
```
