# Lesson 15.3 — User vs Admin

In **15.2**, we learned that a role is a way to group access.

Now we'll build the most common starting authorization model:

```text
USER
  ↓
Normal application access

ADMIN
  ↓
Privileged application access
```

This looks simple, but there are several important security decisions hidden inside it.

Your starter architecture already has the idea of roles such as `user` and `admin`, so this lesson is about understanding the design rather than blindly adding a role check.

---

# 1. What Is a Normal User?

A normal user is someone who uses the application's regular features.

For example, in a Todo application:

```text
User
 ├── Create own todo
 ├── Read own todos
 ├── Update own todo
 └── Delete own todo
```

The important word is:

> **own**

A normal user should generally have access to their own resources, not everybody else's.

So:

```text
Rahul
  ↓
Todo A
```

Rahul can:

```text
GET Todo A
UPDATE Todo A
DELETE Todo A
```

But:

```text
Amit
  ↓
Todo B
```

Rahul should not automatically be able to modify Todo B.

We'll study this more deeply in **15.9 — User A vs User B**.

---

# 2. What Is an Admin?

An administrator is a privileged user who can perform operations that ordinary users cannot.

For example:

```text
Admin
 ├── View users
 ├── Disable users
 ├── Manage roles
 ├── View system information
 └── Perform administrative operations
```

So:

```text
user
   ↓
normal application operations

admin
   ↓
normal operations
+
administrative operations
```

But be careful:

> **Admin should not mean "can do absolutely anything."**

That's an important production-security principle.

---

# 3. User vs Admin

Let's make the difference concrete.

Suppose your application has:

```text
GET /api/v1/users/me
GET /api/v1/admin/users
DELETE /api/v1/users/:id
POST /api/v1/todos
```

A simple authorization design might be:

|Endpoint|User|Admin|
|---|--:|--:|
|`GET /users/me`|✅|✅|
|`GET /admin/users`|❌|✅|
|`POST /todos`|✅|✅|
|Delete own todo|✅|✅|
|Delete another user's todo|❌|Depends on policy|
|Change user role|❌|✅|

Notice something important:

**Being an admin doesn't automatically define every permission.**

You still need to decide what administrators are allowed to do.

---

# 4. The First Important Rule

A normal user should not be able to simply change:

```json
{
  "role": "admin"
}
```

For example, imagine:

```http
PATCH /api/v1/users/me
```

with:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

If your backend accepts that blindly:

```text
User
 ↓
changes own role
 ↓
admin
```

you've created a serious authorization vulnerability.

The backend must control sensitive fields such as roles.

---

# 5. Never Trust the Client

This is worth repeating because it is one of the biggest security lessons.

Suppose React sends:

```json
{
  "role": "admin"
}
```

The backend must **not** think:

> "The client says this user is admin, so they must be admin."

The client is controlled by the user.

A malicious user can directly send HTTP requests without using your React application at all.

For example:

```text
Browser
   ↓
React UI
   ↓
Backend
```

is only one possibility.

An attacker can instead do:

```text
Custom script
   ↓
Backend
```

Therefore:

```text
Frontend authorization
        ≠
Backend authorization
```

Frontend checks are for user experience.

Backend checks are for security.

---

# 6. The Admin Route

Suppose we have:

```http
GET /api/v1/admin/users
```

We want:

```text
User
 ↓
❌ 403

Admin
 ↓
✅ Continue
```

The request flow becomes:

```text
Request
   ↓
Authentication
   ↓
Identify user
   ↓
Authorization
   ↓
Check role
   ↓
Controller
```

For example:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    adminController.getUsers
);
```

We'll build `requireRole()` properly in **15.5**.

For now, focus on the architecture.

---

# 7. Why Authentication Comes First

Remember:

```text
authenticate
```

answers:

> Who is making this request?

Then:

```text
requireRole(ROLES.ADMIN)
```

answers:

> Is this user an administrator?

Therefore:

```text
authenticate
      ↓
req.user
      ↓
requireRole()
      ↓
req.user.role
```

Without authentication, authorization doesn't have a reliable identity to evaluate.

---

# 8. What Happens to a Normal User?

Suppose Rahul has:

```js
req.user = {
    id: "123",
    role: "user"
};
```

He requests:

```http
GET /api/v1/admin/users
```

Authentication succeeds:

```text
JWT valid
 ↓
Rahul identified
```

Authorization then checks:

```js
req.user.role === "admin"
```

Result:

```text
"user" === "admin"
```

❌ False.

Therefore:

```http
403 Forbidden
```

The controller should never execute.

That's important.

---

# 9. What Happens to an Admin?

Suppose Amit has:

```js
req.user = {
    id: "456",
    role: "admin"
};
```

Request:

```http
GET /api/v1/admin/users
```

Flow:

```text
JWT
 ↓
Authentication ✅
 ↓
req.user
 ↓
role = admin
 ↓
Authorization ✅
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
```

The admin operation is allowed.

---

# 10. Don't Put Authorization Only Inside the Controller

A beginner might write:

```js
const getUsers = async (req, res) => {

    if (req.user.role !== "admin") {
        return res.status(403).json({
            message: "Forbidden"
        });
    }

    // actual logic...
};
```

This can work, but as your application grows, it becomes repetitive.

You might have:

```text
getUsers()
deleteUser()
disableUser()
viewReports()
changeRole()
viewAuditLogs()
```

and every controller starts repeating:

```js
if (req.user.role !== "admin")
```

That's one reason middleware is useful.

Instead:

```text
Route
 ↓
Authentication
 ↓
Authorization middleware
 ↓
Controller
```

The controller can focus on the HTTP operation.

---

# 11. Admin Routes as a Boundary

A useful architecture is:

```text
/api/v1/users/*
```

for regular user operations.

And:

```text
/api/v1/admin/*
```

for administrative operations.

For example:

```text
/api/v1/users/me

/api/v1/admin/users
/api/v1/admin/users/:id
/api/v1/admin/reports
```

This isn't mandatory, but it can make your API easier to understand.

You can visually see:

```text
users
 ↓
regular user features

admin
 ↓
administrative features
```

---

# 12. But URL Doesn't Provide Security

This is a subtle but important point.

Just because an endpoint is:

```text
/api/v1/admin/users
```

does **not** make it an admin endpoint securely.

An attacker can still request it.

The backend must enforce:

```text
authenticate
+
authorization
```

So this:

```text
/admin/users
```

is organization.

This:

```text
requireRole(admin)
```

is security enforcement.

---

# 13. User Access to Their Own Profile

Consider:

```http
GET /api/v1/users/me
```

A normal user should be able to access their own profile.

The flow:

```text
Request
 ↓
authenticate
 ↓
req.user.id
 ↓
user service
 ↓
repository
 ↓
find user
```

No admin role is necessary.

So:

```text
user → /users/me → ✅
admin → /users/me → ✅
```

An admin is still a user of the system and may need normal user functionality too.

---

# 14. Admin Access to User Data

Now:

```http
GET /api/v1/admin/users
```

This is different.

The purpose isn't:

> "Show me my profile."

It's:

> "Give me access to user-management data."

Therefore:

```text
user → ❌
admin → ✅
```

This is a **privileged operation**.

---

# 15. Should Admin Automatically Own Everything?

Not necessarily.

Suppose:

```text
Todo A → Rahul
Todo B → Amit
```

A request:

```http
DELETE /todos/B
```

might be allowed only if:

```text
request.user.id === todo.userId
```

But perhaps your product requirements say:

> Administrators can remove any inappropriate todo.

Then the authorization rule could be:

```text
User:
    can delete own todo

Admin:
    can delete any todo
```

This is a business/security decision.

Don't assume it automatically.

---

# 16. Two Different Authorization Rules

This gives us an important distinction.

### Role-based

```text
Is user an admin?
```

Example:

```text
/admin/users
```

### Resource-based

```text
Does this resource belong to this user?
```

Example:

```text
/todos/:id
```

So a real application often needs:

```text
Authentication
      ↓
Role authorization
      +
Resource authorization
```

This becomes one of the most important parts of Phase 15.

---

# 17. Admin Should Be a Protected Role

Who creates an admin?

This is an important design question.

You should **not** generally allow:

```text
Signup
 ↓
role = admin
```

For example, don't expose a public signup API where the client can submit:

```json
{
  "email": "attacker@example.com",
  "password": "password",
  "role": "admin"
}
```

Instead, a normal public signup might create:

```text
role = user
```

automatically.

Then a trusted administrative process can promote a user.

For example:

```text
Existing admin
       ↓
Role management
       ↓
User becomes admin
```

Exactly how you bootstrap the first admin depends on the application and deployment architecture.

---

# 18. Role Assignment Is a Sensitive Operation

Suppose:

```http
PATCH /api/v1/admin/users/:id/role
```

That endpoint itself needs authorization.

You don't want:

```text
User
 ↓
PATCH role
 ↓
admin
```

Instead:

```text
User
 ↓
PATCH role
 ↓
403
```

while:

```text
Admin
 ↓
PATCH role
 ↓
Allowed according to policy
```

This is called **protecting the privilege-management operation itself**.

We'll return to this later.

---

# 19. What If Someone Changes Their Own Database Role?

Suppose the database contains:

```js
{
    email: "rahul@example.com",
    role: "user"
}
```

An attacker somehow attempts:

```text
UPDATE users
SET role = "admin"
```

Your application must ensure users don't have arbitrary access to modify privileged fields.

This is why authorization isn't just a route-level problem.

It also affects:

```text
validation
service logic
repository operations
database permissions
```

We'll explore this later.

---

# 20. Don't Create a "God Mode" Admin

A common beginner design is:

```text
admin = can do absolutely everything
```

That might be acceptable for a tiny personal project, but production systems often use more controlled permissions.

For example:

```text
superadmin
admin
moderator
support
```

or:

```text
admin
+
specific permissions
```

Why?

Because if every administrator can:

```text
delete users
change roles
access financial data
view security logs
change system configuration
```

then compromising one admin account becomes extremely dangerous.

We'll eventually move from:

```text
role-only authorization
```

toward:

```text
role
+
permissions
+
resource ownership
```

---

# 21. User vs Admin — Complete Example

Imagine this application:

```text
Roles:

USER
ADMIN
```

Resources:

```text
Users
Todos
Reports
```

Authorization design:

```text
                    USER             ADMIN
---------------------------------------------------
Own profile          ✅                ✅
Own todos            ✅                ✅
Other users' data    ❌                policy
Admin dashboard      ❌                ✅
System reports       ❌                ✅
Change roles         ❌                policy
```

The word **policy** is important.

Authorization isn't simply:

```text
admin = yes
user = no
```

Every sensitive action should have an intentional rule.

---

# 22. A Better Way to Design Authorization

For every endpoint, ask:

### Question 1

Who needs to be authenticated?

```text
Public?
Authenticated?
```

### Question 2

Which roles can access it?

```text
user?
admin?
moderator?
```

### Question 3

Does ownership matter?

```text
own resource?
any resource?
```

### Question 4

Are there additional conditions?

For example:

```text
Is the resource active?
Is the user part of the organization?
Is the order still cancellable?
```

This is how you move from simple RBAC toward proper authorization design.

---

# 23. Example Design Exercise

Let's design a Todo API.

```text
POST   /todos
GET    /todos
GET    /todos/:id
PATCH  /todos/:id
DELETE /todos/:id
GET    /admin/users
DELETE /admin/users/:id
```

A reasonable starting policy:

```text
POST /todos
    → authenticated users

GET /todos
    → authenticated users
    → only their own todos

GET /todos/:id
    → authenticated
    → own todo

PATCH /todos/:id
    → authenticated
    → own todo

DELETE /todos/:id
    → authenticated
    → own todo

GET /admin/users
    → authenticated admin

DELETE /admin/users/:id
    → authenticated admin
```

Notice that only two endpoints are strictly role-based:

```text
/admin/users
/admin/users/:id
```

The Todo endpoints mainly depend on **ownership**.

This is an important realization:

> **Not every authorization problem should be solved with roles.**

# 25. Common Mistakes

### ❌ Mistake 1 — Trusting the frontend

```js
if (frontendSaysAdmin) {
    allow();
}
```

Never do this.

---

### ❌ Mistake 2 — Allowing role in public signup

```json
{
    "email": "...",
    "password": "...",
    "role": "admin"
}
```

Don't let an untrusted client choose privileged roles.

---

### ❌ Mistake 3 — Assuming admin automatically owns every resource

Admin access should be explicitly designed.

---

### ❌ Mistake 4 — Only protecting the UI

Hiding an "Admin" button isn't authorization.

The API must enforce it.

---

### ❌ Mistake 5 — Checking only role for resource access

For:

```text
/todos/:id
```

you often need ownership:

```text
userId === authenticatedUserId
```

---

# 26. The Most Important Mental Model

When you build an endpoint, don't ask only:

> "Is the user logged in?"

Ask:

```text
1. Is the request authenticated?
       ↓
2. What user is making it?
       ↓
3. What role does the user have?
       ↓
4. What resource are they accessing?
       ↓
5. Do they own it?
       ↓
6. Are there additional business rules?
       ↓
7. Allow or deny?
```

That's real authorization thinking.

---

# 27. What You Should Remember

Keep these points from 15.3:

```text
1. Normal users get regular application access.

2. Admins get explicitly defined privileged access.

3. Never trust a role supplied by the client.

4. Public signup should not allow arbitrary privileged roles.

5. Admin routes still need authentication + authorization.

6. Admin does not automatically mean "can do everything."

7. Resource ownership is separate from role-based access.

8. Every sensitive operation should have an explicit authorization rule.
```

The key architecture:

```text
Authentication
      ↓
Who is the user?
      ↓
Role
      ↓
What category of access?
      ↓
Ownership / permissions
      ↓
What exact resource/action is allowed?
```
