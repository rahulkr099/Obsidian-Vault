# Lesson 15.4 — Role Middleware

In **15.3**, we designed the difference between normal users and admins.

Now we turn that idea into actual Express middleware.

The goal of this lesson is to understand how to build:

```js
requireRole(...)
```

so that we can write routes like:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole("admin"),
    adminController.getUsers
);
```

---

# 1. Why Do We Need Role Middleware?

Imagine you have 10 admin-only endpoints:

```text
GET    /admin/users
GET    /admin/reports
DELETE /admin/users/:id
PATCH  /admin/users/:id
GET    /admin/logs
...
```

Without middleware, you might repeat this in every controller:

```js
if (req.user.role !== "admin") {
    return res.status(403).json({
        success: false,
        message: "Forbidden"
    });
}
```

That becomes repetitive.

Instead, we create one reusable middleware:

```text
authenticate
      ↓
requireRole
      ↓
controller
```

Now the authorization rule is reusable.

---

# 2. First Understand Normal Middleware

A basic Express middleware looks like:

```js
const middleware = (req, res, next) => {
    // do something

    next();
};
```

Remember:

```text
req
 ↓
middleware
 ↓
next()
 ↓
next middleware/controller
```

If middleware doesn't call `next()` and doesn't send a response, the request can get stuck.

---

# 3. Our Authentication Middleware

From Phase 14, conceptually we have something like:

```js
const authenticate = (req, res, next) => {
    // verify token

    req.user = decodedUser;

    next();
};
```

After authentication:

```js
req.user
```

might contain:

```js
{
    id: "123",
    role: "user"
}
```

This is the information our role middleware needs.

---

# 4. Basic Role Middleware

The simplest version is:

```js
const requireAdmin = (req, res, next) => {
    if (req.user.role !== "admin") {
        return res.status(403).json({
            success: false,
            message: "Forbidden"
        });
    }

    next();
};
```

Then:

```js
router.get(
    "/admin/users",
    authenticate,
    requireAdmin,
    adminController.getUsers
);
```

Flow:

```text
Request
   ↓
authenticate
   ↓
req.user
   ↓
requireAdmin
   ↓
Is role admin?
   │
   ├── NO → 403
   │
   └── YES
        ↓
    Controller
```

This works.

But there's a problem.

---

# 5. The Problem With `requireAdmin`

Suppose tomorrow you need:

```text
moderator
admin
superadmin
```

You could create:

```js
requireAdmin()
requireModerator()
requireSuperAdmin()
```

But now you're creating lots of almost-identical middleware.

A better approach is to create a **middleware factory**.

---

# 6. Middleware Factory

Instead of:

```js
requireAdmin
```

we create:

```js
requireRole("admin")
```

Think of:

```js
requireRole("admin")
```

as:

> "Create a middleware that requires the admin role."

For example:

```js
const requireRole = (requiredRole) => {
    return (req, res, next) => {
        if (req.user.role !== requiredRole) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Notice something interesting.

The outer function:

```js
requireRole
```

receives the configuration:

```text
"admin"
```

and returns another function:

```js
(req, res, next) => {}
```

That returned function is the actual Express middleware.

---

# 7. Understand the Two Functions

This can look confusing at first:

```js
const requireRole = (requiredRole) => {
    return (req, res, next) => {
        // ...
    };
};
```

There are two functions.

### Outer function

```js
requireRole("admin")
```

Its job:

> Configure the middleware.

### Inner function

```js
(req, res, next) => {}
```

Its job:

> Handle the actual request.

So:

```text
requireRole("admin")
        ↓
creates
        ↓
(req, res, next) => {...}
        ↓
Express executes it
```

---

# 8. Why Is This Called a Factory?

Because:

```js
requireRole("admin")
```

**creates** middleware.

For example:

```js
const requireAdmin = requireRole("admin");
```

Now:

```text
requireAdmin
```

is a middleware function.

Similarly:

```js
const requireModerator = requireRole("moderator");
```

creates another middleware.

So:

```text
requireRole()
     │
     ├── "admin"      → admin middleware
     │
     ├── "moderator"  → moderator middleware
     │
     └── "user"       → user middleware
```

One function gives you many authorization middlewares.

---

# 9. Using It in Routes

Now we can write:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole("admin"),
    adminController.getUsers
);
```

Another route:

```js
router.get(
    "/moderation/reports",
    authenticate,
    requireRole("moderator"),
    moderationController.getReports
);
```

Another:

```js
router.get(
    "/profile",
    authenticate,
    requireRole("user"),
    userController.getProfile
);
```

Same middleware factory.

Different configuration.

---

# 10. Use Role Constants

Earlier we discussed avoiding random strings.

Instead of:

```js
requireRole("admin")
```

we can eventually use:

```js
requireRole(ROLES.ADMIN)
```

For example:

```js
export const ROLES = {
    USER: "user",
    ADMIN: "admin",
    MODERATOR: "moderator"
};
```

Then:

```js
requireRole(ROLES.ADMIN)
```

This is safer and easier to maintain.

---

# 11. A Better Implementation

Let's build a cleaner version.

```js
const requireRole = (requiredRole) => {
    return (req, res, next) => {
        if (req.user.role !== requiredRole) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

There are three important parts:

### 1. Receive required role

```js
(requiredRole)
```

### 2. Check authenticated user's role

```js
req.user.role
```

### 3. Continue only if allowed

```js
next();
```

---

# 12. Why `authenticate` Must Come First

This is critical.

Correct:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    adminController.getUsers
);
```

Why?

Because:

```js
authenticate
```

creates:

```js
req.user
```

Then:

```js
requireRole()
```

reads:

```js
req.user.role
```

The flow is:

```text
authenticate
     ↓
req.user = {
    id: "...",
    role: "admin"
}
     ↓
requireRole(ADMIN)
     ↓
req.user.role
```

---

# 13. What Happens If We Reverse Them?

Suppose:

```js
router.get(
    "/admin/users",
    requireRole(ROLES.ADMIN),
    authenticate,
    adminController.getUsers
);
```

Now `requireRole()` may execute before `authenticate()`.

Then:

```js
req.user
```

might not exist.

Trying:

```js
req.user.role
```

could result in an error.

So the conceptual rule is:

```text
Authentication
      ↓
Authorization
```

Identity must be established before authorization can evaluate it.

---

# 14. What If There Is No User?

A robust authorization middleware should also consider this.

Suppose someone accidentally uses:

```js
requireRole(ROLES.ADMIN)
```

without authentication.

Then:

```js
req.user
```

could be undefined.

Instead of causing:

```text
Cannot read properties of undefined
```

we can safely handle it:

```js
const requireRole = (requiredRole) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (req.user.role !== requiredRole) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Now we have:

```text
No identity
    ↓
401

Identity exists
    ↓
Wrong role
    ↓
403

Correct role
    ↓
next()
```

---

# 15. 401 vs 403 Again

Our middleware demonstrates the difference perfectly.

### No authenticated user

```js
if (!req.user) {
    return res.status(401)
}
```

Meaning:

> We don't have a valid authenticated identity.

### Authenticated but wrong role

```js
if (req.user.role !== requiredRole) {
    return res.status(403)
}
```

Meaning:

> We know who you are, but you don't have this role.

---

# 16. Supporting Multiple Roles

Our current middleware accepts one role:

```js
requireRole(ROLES.ADMIN)
```

But sometimes a route should allow:

```text
admin OR moderator
```

For example:

```text
GET /reports
```

could be accessible to both.

We can design:

```js
requireRole(
    ROLES.ADMIN,
    ROLES.MODERATOR
)
```

The middleware then checks whether the current role is one of the allowed roles.

Conceptually:

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Now:

```js
requireRole(ROLES.ADMIN)
```

means:

```text
admin only
```

while:

```js
requireRole(
    ROLES.ADMIN,
    ROLES.MODERATOR
)
```

means:

```text
admin OR moderator
```

---

# 17. Understanding the Rest Parameter

This:

```js
const requireRole = (...allowedRoles) => {
```

uses JavaScript's **rest parameter**.

If we call:

```js
requireRole("admin", "moderator");
```

then:

```js
allowedRoles
```

becomes:

```js
[
    "admin",
    "moderator"
]
```

Then:

```js
allowedRoles.includes(req.user.role)
```

checks whether the current user's role exists in that array.

For example:

```text
allowedRoles:
[
    "admin",
    "moderator"
]

req.user.role:
"moderator"

includes?
YES
```

So:

```text
next()
```

is called.

---

# 18. Why `includes()` Is Useful

Instead of:

```js
if (
    req.user.role !== "admin" &&
    req.user.role !== "moderator"
) {
    // reject
}
```

we can write:

```js
if (!allowedRoles.includes(req.user.role)) {
    // reject
}
```

This is cleaner and scales better.

---

# 19. Complete Role Middleware

A good conceptual version is:

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Then:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    adminController.getUsers
);
```

And:

```js
router.get(
    "/reports",
    authenticate,
    requireRole(
        ROLES.ADMIN,
        ROLES.MODERATOR
    ),
    reportController.getReports
);
```

---

# 20. Where Should This Middleware Live?

In a clean backend architecture, authorization middleware should live in the middleware/security layer rather than inside controllers.

For example:

```text
src/
├── controllers/
├── services/
├── repositories/
├── middleware/
│   ├── auth.middleware.js
│   ├── role.middleware.js
│   └── ...
├── constants/
│   └── roles.js
└── routes/
```

The exact filenames can vary, but the responsibility should remain clear:

```text
middleware
    ↓
request-level access control
```

---

# 21. Route-Level Authorization

This is one of the biggest benefits.

Instead of:

```js
const getUsers = async (req, res) => {
    if (req.user.role !== ROLES.ADMIN) {
        ...
    }

    // controller logic
};
```

we can say:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    getUsers
);
```

Now the controller can concentrate on:

```text
HTTP request
    ↓
service call
    ↓
HTTP response
```

while authorization remains in middleware.

This keeps responsibilities cleaner.

---

# 22. But Role Middleware Isn't Everything

Very important:

```text
requireRole()
```

solves:

> **Does this user have an allowed role?**

It does **not** solve:

> Does this particular resource belong to this user?

For example:

```http
PATCH /todos/123
```

Suppose:

```text
Rahul
role = user
```

and:

```text
Todo 123
owner = Amit
```

Role middleware says:

```text
Rahul has role "user"
```

That doesn't tell us whether Rahul owns Todo 123.

So:

```text
Role authorization
        +
Resource authorization
```

are different problems.

We'll deal with ownership later.

---

# 23. Another Important Limitation

Suppose:

```text
admin
```

can access:

```text
/admin/users
```

That doesn't necessarily mean the admin should be able to:

```text
delete every user
change every role
view every sensitive record
```

Role middleware gives us a **coarse access boundary**.

Later we can add:

```text
permissions
ownership
resource policies
business rules
```

This is why we're building Phase 15 progressively.

# 24. Request Flow

Let's visualize our current architecture.

```text
                 HTTP Request
                       │
                       ▼
                     Route
                       │
                       ▼
                authenticate
                       │
                       ▼
                  req.user
                       │
                       ▼
                 requireRole()
                       │
             ┌─────────┴─────────┐
             │                   │
          allowed             denied
             │                   │
             ▼                   ▼
          next()                403
             │
             ▼

             │
             ▼
          Service
             │
             ▼

```

This is the pattern you should understand, not just memorize.

# 25. Common Mistakes

### Mistake 1 — Calling the factory incorrectly

Wrong:

```js
requireRole
```

when the route expects configured middleware.

Usually:

```js
requireRole(ROLES.ADMIN)
```

because the function needs to know which roles are allowed.

---

### Mistake 2 — Forgetting authentication

Wrong:

```js
router.get(
    "/admin/users",
    requireRole(ROLES.ADMIN),
    controller
);
```

Better:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    controller
);
```

---

### Mistake 3 — Checking `req.body.role`

Never do:

```js
req.body.role
```

for authorization.

Use trusted server-side identity information.

---

### Mistake 4 — Returning `401` for wrong role

If the user is authenticated but lacks the required role:

```text
403
```

---

### Mistake 5 — Thinking middleware replaces ownership checks

It doesn't.

```text
requireRole()
```

answers:

> "Does your role qualify?"

Ownership logic answers:

> "Are you allowed to access this particular resource?"

---

# 28. Key Takeaways

Remember these:

```text
1. Role middleware is authorization middleware.

2. Authentication should establish req.user first.

3. requireRole() can be implemented as a middleware factory.

4. Multiple roles can be supported with ...allowedRoles.

5. Wrong/missing authentication → 401.

6. Authenticated but wrong role → 403.

7. Never trust role information from the client.

8. Role middleware doesn't replace ownership checks.

9. Authorization should be enforced on the backend.

10. Middleware keeps repetitive role checks out of controllers.
```

The basic pattern is:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    controller
);
```

And the conceptual implementation is:

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```
