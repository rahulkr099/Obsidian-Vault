# Lesson 15.5 — `requireRole()` in Detail

In **15.4**, we built the basic idea of:

```js
requireRole(ROLES.ADMIN)
```

Now let's understand it deeply enough that you can confidently implement and use it in a real Express backend.

The goal isn't just to memorize this:

```js
if (!allowedRoles.includes(req.user.role))
```

The goal is to understand **why every part exists**.

---

# 1. The Problem We're Solving

Suppose your application has:

```text
user
admin
moderator
```

And these routes:

```text
/admin/users
/admin/reports
/moderation/comments
```

We need rules like:

```text
/admin/users
    → admin only

/admin/reports
    → admin only

/moderation/comments
    → moderator or admin
```

Without reusable middleware, we'd repeatedly write:

```js
if (req.user.role !== "admin") {
    ...
}
```

That's exactly what `requireRole()` helps us avoid.

---

# 2. Our Desired API

We want to write:

```js
requireRole(ROLES.ADMIN)
```

or:

```js
requireRole(
    ROLES.ADMIN,
    ROLES.MODERATOR
)
```

This should produce an Express middleware.

So conceptually:

```text
requireRole(...)
       ↓
creates middleware
       ↓
Express executes middleware
       ↓
checks req.user.role
       ↓
allow / deny
```

---

# 3. Understanding the Function Shape

Start with:

```js
const requireRole = (...allowedRoles) => {
    // ...
};
```

The `...allowedRoles` part is important.

Suppose we call:

```js
requireRole("admin");
```

Then:

```js
allowedRoles
```

becomes:

```js
["admin"]
```

If we call:

```js
requireRole("admin", "moderator");
```

then:

```js
allowedRoles
```

becomes:

```js
[
    "admin",
    "moderator"
]
```

So our middleware doesn't need separate implementations for one role or multiple roles.

---

# 4. Returning Middleware

Now:

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        // authorization logic
    };
};
```

This is a **higher-order function / middleware factory**.

The outer function:

```js
requireRole(...)
```

runs when you configure your route.

The returned function:

```js
(req, res, next) => {}
```

runs when an actual HTTP request arrives.

Think:

```text
Application startup
       ↓
requireRole(ADMIN)
       ↓
middleware created

Later...

HTTP request
       ↓
middleware executes
```

This distinction is very important.

---

# 5. First Security Check — Is the User Authenticated?

Our middleware can begin with:

```js
if (!req.user) {
    return res.status(401).json({
        success: false,
        message: "Authentication required"
    });
}
```

Why?

Because `requireRole()` depends on:

```js
req.user
```

If there is no authenticated user, there is no trustworthy identity whose role we can evaluate.

So:

```text
req.user missing
      ↓
Cannot perform role authorization
      ↓
401
```

---

# 6. Second Security Check — Is the Role Allowed?

Now:

```js
if (!allowedRoles.includes(req.user.role)) {
    return res.status(403).json({
        success: false,
        message: "Forbidden"
    });
}
```

Suppose:

```js
allowedRoles = ["admin"];
```

and:

```js
req.user.role = "user";
```

Then:

```js
allowedRoles.includes("user")
```

returns:

```text
false
```

Therefore:

```text
403 Forbidden
```

---

# 7. Third Step — Continue

If the role is allowed:

```js
next();
```

That's all the middleware needs to do.

So the complete decision is:

```text
                req.user?
                   │
             ┌─────┴─────┐
            NO           YES
            │             │
           401            │
                          ▼
                     role allowed?
                          │
                    ┌─────┴─────┐
                   NO           YES
                   │             │
                  403          next()
```

---

# 8. Complete Middleware

Our current implementation becomes:

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

This is a good starting point.

But let's make sure you understand the behavior before making it more sophisticated.

---

# 9. Example: Admin Only

Route:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    adminController.getUsers
);
```

Suppose:

```js
req.user = {
    id: "123",
    role: "admin"
};
```

Then:

```js
allowedRoles = ["admin"];
```

Check:

```js
["admin"].includes("admin")
```

Result:

```text
true
```

So:

```js
next();
```

Controller executes.

---

# 10. Example: Normal User

Now:

```js
req.user = {
    id: "123",
    role: "user"
};
```

Check:

```js
["admin"].includes("user")
```

Result:

```text
false
```

Therefore:

```http
403 Forbidden
```

And importantly:

```text
Controller ❌
Service ❌
Repository ❌
Database ❌
```

The request stops at the authorization boundary.

---

# 11. Example: Multiple Roles

Suppose:

```js
router.get(
    "/reports",
    authenticate,
    requireRole(
        ROLES.ADMIN,
        ROLES.MODERATOR
    ),
    reportController.getReports
);
```

Then:

```js
allowedRoles = [
    "admin",
    "moderator"
];
```

For an admin:

```js
["admin", "moderator"].includes("admin")
```

→ `true`

For a moderator:

```js
["admin", "moderator"].includes("moderator")
```

→ `true`

For a normal user:

```js
["admin", "moderator"].includes("user")
```

→ `false`

So:

```text
admin      → ✅
moderator  → ✅
user       → ❌
```

---

# 12. Why `return res...`?

Notice this:

```js
return res.status(403).json({
    success: false,
    message: "Forbidden"
});
```

Why `return`?

Because once we've rejected the request, we don't want execution to continue.

Without `return`, you could accidentally write:

```js
if (!allowedRoles.includes(req.user.role)) {
    res.status(403).json({
        success: false,
        message: "Forbidden"
    });
}

next();
```

Now even after sending the 403 response, `next()` could execute.

That's a bug.

The safe pattern is:

```js
if (condition) {
    return res.status(...).json(...);
}

next();
```

Meaning:

```text
Reject → stop execution
Allow → next()
```

---

# 13. Why Not `next()` After 403?

Never do this:

```js
if (!allowed) {
    res.status(403).json(...);
    next();
}
```

You've just said:

```text
Access denied
       ↓
but continue anyway
```

That's logically contradictory.

Authorization middleware should have a very clear contract:

```text
Allowed → next()
Denied  → response + stop
```

---

# 14. Empty Roles

Consider:

```js
requireRole()
```

Then:

```js
allowedRoles = [];
```

For any user:

```js
[].includes(req.user.role)
```

returns:

```text
false
```

Therefore everyone gets:

```text
403
```

This might be acceptable, but a more defensive implementation could reject invalid configuration early.

For example:

```js
const requireRole = (...allowedRoles) => {
    if (allowedRoles.length === 0) {
        throw new Error("At least one role is required");
    }

    return (req, res, next) => {
        // ...
    };
};
```

Whether you want this depends on your project's error-handling and configuration philosophy.

The important lesson is:

> **Authorization middleware should fail safely when incorrectly configured.**

---

# 15. Role Comparison Is Exact

Suppose:

```js
req.user.role = "Admin";
```

and:

```js
allowedRoles = ["admin"];
```

Then:

```js
["admin"].includes("Admin")
```

is:

```text
false
```

JavaScript string comparisons are case-sensitive.

That's another reason to centralize roles:

```js
const ROLES = {
    USER: "user",
    ADMIN: "admin",
    MODERATOR: "moderator"
};
```

Then you don't randomly write:

```text
Admin
admin
ADMIN
administrator
```

throughout your application.

---

# 16. Using Constants

Instead of:

```js
requireRole("admin")
```

prefer:

```js
requireRole(ROLES.ADMIN)
```

For example:

```js
export const ROLES = {
    USER: "user",
    ADMIN: "admin",
    MODERATOR: "moderator"
};
```

Then:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    adminController.getUsers
);
```

This creates a clear source of truth.

---

# 17. Where Should Role Values Come From?

This is a security question.

The role should come from a **trusted authentication process**, not directly from the request body.

Bad:

```js
const role = req.body.role;
```

Then:

```js
if (role === ROLES.ADMIN) {
    // allow
}
```

An attacker can simply send:

```json
{
    "role": "admin"
}
```

The authorization system should instead evaluate trusted identity information established by your authentication system.

Conceptually:

```text
Request
   ↓
JWT/session
   ↓
Authentication
   ↓
Trusted user identity
   ↓
Authorization
```

---

# 18. JWT Role vs Database Role

Now we reach an important production design question.

Suppose the access token contains:

```json
{
    "sub": "123",
    "role": "admin"
}
```

Your middleware might use:

```js
req.user.role
```

That's convenient.

But consider this:

```text
10:00 AM
User role = admin
       ↓
JWT issued

10:05 AM
Admin changes user role → user

10:06 AM
Old JWT still says → admin
```

Depending on your token strategy, the old access token may continue to carry the old role until it expires.

This means authorization design must consider **token lifetime and revocation**.

We already touched on this in Phase 14 authentication.

For now, understand the tradeoff:

```text
JWT role
    ↓
Fast
Stateless
Convenient

Database role
    ↓
More current
Can reflect role changes immediately
Potential extra DB lookup
```

There isn't one universal answer for every application.

---

# 19. Don't Make Every Authorization Check a Database Query

A beginner may react to the previous point by doing:

```text
Every request
   ↓
Verify JWT
   ↓
Query user
   ↓
Get role
   ↓
Check role
```

That can be valid, but it adds database work to every protected request.

A typical design might instead use:

```text
Short-lived access token
        ↓
Role/identity claims
        ↓
Authorization
```

and have a strategy for handling role changes, token expiry, revocation, or reauthentication.

The correct design depends on your security requirements.

---

# 20. `requireRole()` Does Not Check Ownership

This is probably the most important limitation to understand.

Suppose:

```text
Rahul
role = user
```

and:

```text
Todo #100
owner = Amit
```

Rahul requests:

```http
PATCH /todos/100
```

If you use:

```js
requireRole(ROLES.USER)
```

the middleware says:

```text
Rahul is a user
        ↓
user role allowed
        ↓
next()
```

But Rahul still shouldn't necessarily be allowed to modify Amit's Todo.

Therefore:

```text
Role authorization
        ≠
Resource authorization
```

We'll build ownership checks later.

---

# 21. Role Middleware Should Be Simple

One design principle:

> Don't put business logic into `requireRole()`.

Avoid:

```js
const requireRole = (...roles) => {
    return async (req, res, next) => {
        // query database
        // load order
        // check payment
        // check organization
        // check subscription
        // check ownership
        // check role
        // ...
    };
};
```

Now your "role middleware" is doing everything.

Instead, keep it focused:

```text
requireRole()
    ↓
role-based access decision
```

Other authorization concerns can have their own mechanisms.

---

# 22. Separation of Responsibilities

A clean architecture might look like:

```text
authenticate
    ↓
Who is this user?

requireRole
    ↓
Does their role qualify?

ownership / policy check
    ↓
Can they access this resource?

controller
    ↓
Handle HTTP

service
    ↓
Business logic

repository
    ↓
Database access
```

This separation makes your application easier to understand and test.

# 24. Should Authorization Be Checked Again in the Service?

This is a more advanced design question.

Suppose your route has:

```js
authenticate,
requireRole(ROLES.ADMIN)
```

Should the service also check:

```js
if (user.role !== "admin")
```

There isn't one universal answer.

For route-specific access control, middleware is useful.

But **critical business authorization rules** may also need to be enforced deeper in the application depending on how the service can be invoked.

For example, if your service can be called from:

```text
HTTP controller
background job
CLI
internal worker
another service
```

then relying only on HTTP middleware may not be enough.

This is why defense-in-depth matters.

We'll revisit this as Phase 15 becomes more advanced.

---

# 25. A Useful Pattern

One useful approach is to make authorization explicit in the service API.

For example:

```js
await userService.deleteUser({
    actor: req.user,
    targetUserId: req.params.id
});
```

Then the service can enforce important business rules.

For example:

```text
actor
  ↓
Who is performing the action?

targetUserId
  ↓
Who is being affected?
```

This becomes especially important for:

```text
user management
role changes
ownership
financial operations
sensitive data
```

---

# 26. Don't Overcomplicate It Yet

At this point, don't build:

```text
Policy Engine
Permission Engine
ABAC
RBAC hierarchy
Organization-level authorization
Dynamic policy evaluation
```

We're building the system progressively.

For now:

```text
Authentication
      ↓
Role middleware
      ↓
Controller
```

is enough.

Then we'll add complexity only when there is a real authorization problem that requires it.

# 27. Testing `requireRole()`

Authorization middleware must be tested.

At minimum, test:

### Case 1 — No authenticated user

```text
req.user = undefined
```

Expected:

```text
401
```

### Case 2 — Wrong role

```text
req.user.role = "user"
required = "admin"
```

Expected:

```text
403
```

### Case 3 — Correct role

```text
req.user.role = "admin"
required = "admin"
```

Expected:

```text
next()
```

### Case 4 — Multiple roles

```text
allowed = ["admin", "moderator"]
user role = "moderator"
```

Expected:

```text
next()
```

### Case 5 — Multiple roles but unauthorized

```text
allowed = ["admin", "moderator"]
user role = "user"
```

Expected:

```text
403
```

These tests give us confidence that the security boundary actually works.

# 28. A Simple Test Table

|User|Allowed roles|Result|
|---|---|---|
|No user|`admin`|`401`|
|`user`|`admin`|`403`|
|`moderator`|`admin`|`403`|
|`admin`|`admin`|`next()`|

# 29. Production Mindset

When you're building security middleware, ask:

```text
What happens when...
```

Not only:

```text
What happens when everything is correct?
```

Test:

```text
No token
Invalid token
Expired token
No req.user
Missing role
Wrong role
Unexpected role
Multiple allowed roles
Malformed user object
Misconfigured middleware
```

Security code should be designed around **failure cases**.

# 30. Final Implementation

A clean basic implementation:

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};

export default requireRole;
```

And usage:

```js
router.get(
    "/admin/users",
    authenticate,
    requireRole(ROLES.ADMIN),
    adminController.getUsers
);
```

For multiple roles:

```js
router.get(
    "/reports",
    authenticate,
    requireRole(
        ROLES.ADMIN,
        ROLES.MODERATOR
    ),
    reportController.getReports
);
```
