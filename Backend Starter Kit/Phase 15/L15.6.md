# Lesson 15.6 — RBAC Fundamentals

The official Phase 15 roadmap places **15.6 as “RBAC fundamentals”**, after we have already learned authentication, roles, `requireRole()`, and the difference between users and admins.

Now we connect all of those pieces into one proper authorization model.

---

## 1. What Does RBAC Mean?

**RBAC = Role-Based Access Control**

The idea is simple:

> A user's permissions are determined by their role.

For example:

```text
User
  ↓
normal permissions

Admin
  ↓
administrative permissions

Moderator
  ↓
moderation permissions
```

Instead of asking:

```text
"Is Rahul allowed to access this endpoint?"
```

we can define:

```text
"What role does Rahul have?"
        ↓
"What can that role do?"
```

---

# 2. The Basic RBAC Model

The basic relationship is:

```text
USER
 ↓
ROLE
 ↓
PERMISSIONS
```

For example:

```text
Rahul
  ↓
user
  ↓
read_own_profile
create_todo
read_own_todo
update_own_todo
```

Another user:

```text
Amit
  ↓
admin
  ↓
read_users
delete_users
manage_roles
view_reports
```

So RBAC separates the **person** from the **access rules**.

---

# 3. Why Not Put Permissions Directly on Users?

Imagine 10,000 users.

Without roles, you might have to maintain permissions individually:

```text
Rahul → can_read, can_create, can_update
Amit  → can_read, can_create, can_delete
Priya → can_read, can_create, can_update
...
```

This becomes difficult.

With RBAC:

```text
Rahul → user
Amit  → admin
Priya → user
```

Then define:

```text
user
 ↓
standard permissions

admin
 ↓
administrative permissions
```

Now changing the rules for a role changes them for everyone assigned to that role.

---

# 4. The Three Main Concepts

For basic RBAC, remember:

```text
User
Role
Permission
```

### User

The actual person/account:

```js
{
    id: "123",
    email: "rahul@example.com",
    role: "user"
}
```

### Role

A named access category:

```text
user
admin
moderator
```

### Permission

A specific capability:

```text
users:read
users:delete
roles:update
todos:create
todos:read
```

So:

```text
User
 ↓
Role
 ↓
Permissions
```

---

# 5. Role Is Not the Same as Permission

This distinction is extremely important.

A role might be:

```text
admin
```

A permission might be:

```text
users:delete
```

Therefore:

```text
admin
   ↓
users:read
users:delete
users:update
roles:update
reports:read
```

The role is a **grouping mechanism**.

The permissions describe **what actions are allowed**.

---

# 6. Why Did We Start With `requireRole()`?

Because role-based authorization is the simplest form of RBAC.

We already have:

```js
requireRole(ROLES.ADMIN)
```

This asks:

```text
Does this user have the admin role?
```

If yes:

```text
allow
```

If no:

```text
403 Forbidden
```

This is role-level authorization.

---

# 7. Basic RBAC Example

Suppose we have:

```text
Roles:

USER
ADMIN
MODERATOR
```

And permissions:

```text
USER
 ├── todos:create
 ├── todos:read
 ├── todos:update
 └── todos:delete

MODERATOR
 ├── todos:read
 ├── todos:delete
 └── reports:read

ADMIN
 ├── users:read
 ├── users:update
 ├── users:delete
 ├── roles:update
 └── reports:read
```

Now:

```text
Rahul → USER
```

gets the permissions assigned to `USER`.

And:

```text
Amit → ADMIN
```

gets the permissions assigned to `ADMIN`.

---

# 8. Role Hierarchy Is Not Automatic

Be careful with this assumption:

```text
admin
  >
moderator
  >
user
```

RBAC does **not automatically mean hierarchy**.

You might decide:

```text
admin can do everything
```

But that's a separate policy decision.

For example:

```text
user
moderator
admin
```

could have completely independent permissions.

Or you might explicitly define:

```text
admin
  ↓
inherits moderator
  ↓
inherits user
```

But don't assume inheritance unless your system defines it.

---

# 9. RBAC in Your Express Application

The request flow becomes:

```text
Request
   ↓
Authentication
   ↓
req.user
   ↓
Role
   ↓
RBAC authorization
   ↓
Allowed?
   ├── NO → 403
   │
   └── YES
         ↓
      Controller
```

For basic role checks:

```js
requireRole(ROLES.ADMIN)
```

is enough.

Later we can make authorization more permission-oriented.

---

# 10. Role-Based vs Permission-Based Authorization

This distinction is the next important step.

### Role-based

```js
requireRole(ROLES.ADMIN)
```

Meaning:

> Only admins can access this.

### Permission-based

Conceptually:

```js
requirePermission(PERMISSIONS.USERS_DELETE)
```

Meaning:

> Anyone who has the `users:delete` permission can access this.

This is more flexible.

---

# 11. Why Permissions Become Useful

Suppose you have:

```text
admin
support
moderator
```

Maybe all three need:

```text
users:read
```

But only:

```text
admin
```

needs:

```text
roles:update
```

And only:

```text
moderator
```

needs:

```text
comments:delete
```

If you rely only on role checks:

```text
requireRole("admin")
```

you may create too many role-specific rules.

Permissions allow you to say:

```text
users:read
```

instead of:

```text
admin OR support OR moderator
```

This becomes easier to scale.

---

# 12. RBAC Example

Let's define:

```js
const ROLES = {
    USER: "user",
    MODERATOR: "moderator",
    ADMIN: "admin"
};
```

And:

```js
const PERMISSIONS = {
    USERS_READ: "users:read",
    USERS_DELETE: "users:delete",
    ROLES_UPDATE: "roles:update",
    REPORTS_READ: "reports:read"
};
```

Then define which permissions each role has:

```js
const ROLE_PERMISSIONS = {
    user: [
        "todos:create",
        "todos:read",
        "todos:update"
    ],

    moderator: [
        "todos:read",
        "todos:delete",
        "reports:read"
    ],

    admin: [
        "users:read",
        "users:delete",
        "roles:update",
        "reports:read"
    ]
};
```

Now the architecture becomes:

```text
User
 ↓
role = admin
 ↓
ROLE_PERMISSIONS.admin
 ↓
allowed permissions
```

# 15. RBAC Is About Access Control

The most useful definition to remember:

> **RBAC controls access by assigning users to roles and associating those roles with allowed capabilities.**

In simple terms:

```text
Who are you?
    ↓
What role do you have?
    ↓
What can that role do?
```

---

# 16. Real-World Example

Think about a college application.

Roles:

```text
STUDENT
TEACHER
ADMIN
```

Permissions might be:

```text
students:read
students:update
courses:create
courses:update
grades:update
users:delete
```

Possible mapping:

```text
STUDENT
 ├── courses:read
 └── grades:read

TEACHER
 ├── students:read
 ├── courses:create
 ├── courses:update
 └── grades:update

ADMIN
 ├── students:read
 ├── students:update
 ├── courses:create
 ├── courses:update
 └── users:delete
```

Now authorization becomes understandable.

---

# 17. RBAC Reduces Repetition

Without RBAC:

```js
if (user.email === "admin@example.com") {
    ...
}
```

This is terrible.

Or:

```js
if (
    user.id === "123" ||
    user.id === "456" ||
    user.id === "789"
) {
    ...
}
```

Also terrible.

Instead:

```text
user
 ↓
role
 ↓
permissions
```

This makes access control based on **responsibility**, not individual identities.

---

# 18. Never Use Email as a Role System

Don't do:

```js
if (req.user.email === "rahul@example.com") {
    // admin
}
```

Why?

Because your authorization system should not depend on specific users.

Use:

```js
req.user.role === ROLES.ADMIN
```

or eventually:

```js
hasPermission(req.user, PERMISSIONS.USERS_DELETE)
```

This scales.

---

# 19. Where Should Roles Be Stored?

Typically, the user's role is part of their trusted account data.

For example:

```js
{
    _id: "...",
    email: "rahul@example.com",
    password: "...",
    role: "user"
}
```

Your authentication process can establish the user's identity and role.

Then authorization can use that trusted information.

The important rule is:

```text
Client
   ↓
cannot decide its own privileges
```

---

# 20. Mass Assignment and RBAC

Here's an important security connection.

Suppose you have:

```http
PATCH /api/v1/users/me
```

and accept:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

If your update logic blindly does:

```js
User.findByIdAndUpdate(
    req.user.id,
    req.body
);
```

you could accidentally allow privilege escalation.

This is one reason input validation and authorization must work together.

A safer design explicitly controls which fields the user can modify:

```text
name
email
avatar
```

while sensitive fields such as:

```text
role
permissions
isActive
```

require separate authorization rules.

This connects Phase 9 validation and Phase 15 authorization.

# 21. RBAC Doesn't Solve Everything

This is the biggest thing to understand.

Suppose:

```text
Rahul
role = user
```

and:

```text
Todo 100
owner = Amit
```

RBAC says:

```text
Rahul has role user
```

But the real question is:

```text
Can Rahul access Todo 100?
```

Role alone cannot answer that.

You need:

```text
ownership
```

That's why the roadmap moves from:

```text
15.6 RBAC fundamentals
        ↓
15.7 Permission-based authorization
        ↓
15.8 Resource ownership
```

# 22. Four Layers to Keep Separate

As we progress through Phase 15, think of authorization as:

```text
                 AUTHORIZATION
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Role        Permission      Ownership
        │              │              │
     "Who are      "What can      "Which resource
      you?"         you do?"        can you access?"
```

And eventually there may be:

```text
Business rules
```

such as:

```text
Can cancel this order?
Is the subscription active?
Is this organization allowed?
Is the resource locked?
```

# 23. RBAC vs Authentication

Don't mix these up.

### Authentication

```text
Who are you?
```

Example:

```text
Rahul
user ID = 123
```

### Authorization

```text
What are you allowed to do?
```

Example:

```text
Rahul
role = user
```

Therefore:

```text
Authentication
      ↓
Identity

Authorization
      ↓
Access
```

The uploaded roadmap intentionally places Authorization/RBAC after Authentication for exactly this reason.

# 24. RBAC vs `requireRole()`

They're related, but not identical.

### RBAC

The **overall access-control model**:

```text
Users
 ↓
Roles
 ↓
Permissions
```

### `requireRole()`

One **implementation mechanism**:

```js
requireRole(ROLES.ADMIN)
```

So:

```text
RBAC
 ↓
concept / architecture

requireRole()
 ↓
Express implementation
```

# 27. What RBAC Is Good At

RBAC is excellent for broad application boundaries:

```text
/admin/*
```

```text
/moderation/*
```

```text
/staff/*
```

For example:

```js
requireRole(ROLES.ADMIN)
```

is very clear.

It tells the reader:

> This endpoint requires administrative access.

---

# 28. What RBAC Is Not Good At

RBAC alone isn't enough for:

```text
"My own profile"

"My own todo"

"My organization's documents"

"This particular invoice"

"This particular project"
```

These require more context.

For example:

```text
user role
+
resource owner
+
organization membership
```

That's why mature authorization systems often combine several authorization techniques.

# 29. A Small Design Exercise

Suppose we have:

```text
Roles:

user
moderator
admin
```

And endpoints:

```text
GET /profile
POST /todos
DELETE /todos/:id
GET /admin/users
DELETE /admin/users/:id
GET /moderation/reports
```

A reasonable first RBAC design:

```text
GET /profile
    authenticated

POST /todos
    user/admin

DELETE /todos/:id
    role isn't enough → ownership needed

GET /admin/users
    admin

DELETE /admin/users/:id
    admin

GET /moderation/reports
    moderator/admin
```

Notice how RBAC helps with some endpoints, while other endpoints require additional authorization logic.

That's exactly how you should think when designing a real API.

# 30. Common RBAC Mistakes

### ❌ Mistake 1: "Admin means everything"

Not necessarily.

Define actual privileges.

---

### ❌ Mistake 2: Using roles as individual identities

Don't do:

```js
if (user.id === "123")
```

for general authorization.

---

### ❌ Mistake 3: Trusting the frontend

A hidden admin button isn't security.

The backend must enforce access.

---

### ❌ Mistake 4: Allowing users to modify their role

Don't allow:

```json
{
    "role": "admin"
}
```

through ordinary profile updates.

---

### ❌ Mistake 5: Using RBAC for ownership

```text
role = user
```

doesn't mean:

```text
can access every user's resources
```

# 31. What You Should Remember From 15.6

The core model:

```text
USER
  ↓
ROLE
  ↓
PERMISSIONS
```

Authentication answers:

```text
Who are you?
```

RBAC helps answer:

```text
What access does your role provide?
```

Permission-based authorization answers more specifically:

```text
What action can you perform?
```

Ownership answers:

```text
Which resource can you perform it on?
```

So eventually:

```text
Authentication
      ↓
Role
      ↓
Permission
      ↓
Resource ownership
      ↓
Business rules
      ↓
ALLOW / DENY
```
