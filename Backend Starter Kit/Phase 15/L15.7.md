# Lesson 15.7 — Permission-Based Authorization

In **15.6**, we learned RBAC:

```text
User
 ↓
Role
 ↓
Permissions
```

Now we move one level deeper.

Instead of asking only:

```text
"Is this user an admin?"
```

we can ask:

> **"Does this user have permission to perform this exact action?"**

This is **permission-based authorization**.

---

# 1. Role vs Permission

Let's make the difference very clear.

A **role** is broad:

```text
admin
moderator
user
```

A **permission** is specific:

```text
users:read
users:update
users:delete
roles:update
reports:read
todos:create
todos:delete
```

So:

```text
Role
 ↓
Group of permissions
```

For example:

```text
ADMIN
 ↓
users:read
users:update
users:delete
roles:update
reports:read
```

---

# 2. Why Do We Need Permissions?

Imagine your application has these roles:

```text
admin
moderator
support
```

Suppose:

```text
admin      → users:read, users:delete, roles:update
moderator  → users:read, reports:read
support    → users:read, reports:read
```

Now you want:

```text
GET /users
```

to be accessible by:

```text
admin
moderator
support
```

With role-based middleware, you might write:

```js
requireRole(
    ROLES.ADMIN,
    ROLES.MODERATOR,
    ROLES.SUPPORT
)
```

That works.

But as the application grows, this becomes harder to maintain.

Permission-based authorization lets you write:

```js
requirePermission(PERMISSIONS.USERS_READ)
```

Now the route doesn't care which roles provide that permission.

It only cares about the capability.

---

# 3. The Core Idea

Think of the system like this:

```text
                 USER
                   │
                   ▼
                  ROLE
                   │
                   ▼
             PERMISSIONS
                   │
                   ▼
             AUTHORIZATION
                   │
              ┌────┴────┐
              │         │
           allowed    denied
              │         │
              ▼         ▼
           next()      403
```

For example:

```text
Rahul
 ↓
moderator
 ↓
reports:read
 ↓
GET /reports
 ↓
ALLOW
```

---

# 4. Define Permissions Centrally

Don't scatter strings everywhere.

Instead:

```js
const PERMISSIONS = {
    USERS_READ: "users:read",
    USERS_CREATE: "users:create",
    USERS_UPDATE: "users:update",
    USERS_DELETE: "users:delete",

    ROLES_UPDATE: "roles:update",

    REPORTS_READ: "reports:read",

    TODOS_CREATE: "todos:create",
    TODOS_READ: "todos:read",
    TODOS_UPDATE: "todos:update",
    TODOS_DELETE: "todos:delete"
};
```

Now routes can use:

```js
requirePermission(PERMISSIONS.USERS_DELETE)
```

instead of:

```js
requirePermission("users:delete")
```

This gives you one source of truth.

---

# 5. Role-to-Permission Mapping

Now we need to connect roles to permissions.

For example:

```js
const ROLE_PERMISSIONS = {
    user: [
        PERMISSIONS.TODOS_CREATE,
        PERMISSIONS.TODOS_READ,
        PERMISSIONS.TODOS_UPDATE,
        PERMISSIONS.TODOS_DELETE
    ],

    moderator: [
        PERMISSIONS.TODOS_READ,
        PERMISSIONS.REPORTS_READ
    ],

    admin: [
        PERMISSIONS.USERS_READ,
        PERMISSIONS.USERS_CREATE,
        PERMISSIONS.USERS_UPDATE,
        PERMISSIONS.USERS_DELETE,
        PERMISSIONS.ROLES_UPDATE,
        PERMISSIONS.REPORTS_READ
    ]
};
```

Now:

```text
user
 ↓
todo permissions

moderator
 ↓
moderation/report permissions

admin
 ↓
administrative permissions
```

---

# 6. How Authorization Works

Suppose:

```js
req.user.role = "admin";
```

And we have:

```js
ROLE_PERMISSIONS.admin
```

which contains:

```text
users:read
users:create
users:update
users:delete
roles:update
reports:read
```

Then:

```js
requirePermission(PERMISSIONS.USERS_DELETE)
```

asks:

```text
Does admin have users:delete?
```

Yes.

Therefore:

```text
ALLOW
```

---

# 7. The Permission Middleware

Conceptually:

```js
const requirePermission = (requiredPermission) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        const permissions =
            ROLE_PERMISSIONS[req.user.role] || [];

        if (!permissions.includes(requiredPermission)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Notice how similar this is to `requireRole()`.

The difference is what we're checking.

### `requireRole()`

```js
req.user.role
```

### `requirePermission()`

```js
ROLE_PERMISSIONS[req.user.role]
```

and then:

```js
permissions.includes(requiredPermission)
```

---

# 8. Example Route

Suppose:

```http
DELETE /api/v1/users/:id
```

requires:

```text
users:delete
```

The route becomes:

```js
router.delete(
    "/users/:id",
    authenticate,
    requirePermission(PERMISSIONS.USERS_DELETE),
    userController.deleteUser
);
```

Now the route is saying:

> Any authenticated user whose role grants `users:delete` may pass.

That's more flexible than:

```js
requireRole(ROLES.ADMIN)
```

---

# 9. Role-Based vs Permission-Based

Let's compare them.

### Role-based

```js
requireRole(ROLES.ADMIN)
```

Meaning:

```text
Only admin.
```

### Permission-based

```js
requirePermission(PERMISSIONS.USERS_DELETE)
```

Meaning:

```text
Anyone with users:delete.
```

This distinction becomes very useful as your application grows.

---

# 10. Why Permission-Based Authorization Scales Better

Imagine five roles:

```text
admin
moderator
support
manager
auditor
```

And twenty permissions.

If you protect routes using roles, you might eventually write:

```js
requireRole(
    ROLES.ADMIN,
    ROLES.SUPPORT,
    ROLES.MANAGER
)
```

Then another route:

```js
requireRole(
    ROLES.ADMIN,
    ROLES.MODERATOR,
    ROLES.MANAGER
)
```

And another:

```js
requireRole(
    ROLES.ADMIN,
    ROLES.SUPPORT,
    ROLES.AUDITOR
)
```

The routes become tightly coupled to your role structure.

With permissions:

```js
requirePermission(PERMISSIONS.REPORTS_READ)
```

the route only cares about the capability.

You can change which roles receive that permission without rewriting every route.

---

# 11. A Very Important Design Principle

The endpoint should ideally describe the **required capability**, not the organizational title.

Compare:

```js
requireRole(ROLES.ADMIN)
```

with:

```js
requirePermission(PERMISSIONS.USERS_DELETE)
```

The second one communicates the business requirement more precisely:

> This operation requires the ability to delete users.

That's often easier to reason about.

---

# 12. But Don't Throw Away Roles

Permissions don't make roles useless.

A common model is still:

```text
User
 ↓
Role
 ↓
Permissions
```

For example:

```text
Rahul
 ↓
moderator
 ↓
[
  "todos:read",
  "reports:read"
]
```

So roles remain a convenient way to group permissions.

Think:

```text
Role = convenient bundle
Permission = actual capability
```

---

# 13. A Simple Example

Suppose:

```js
const ROLE_PERMISSIONS = {
    user: [
        "todos:create",
        "todos:read"
    ],

    moderator: [
        "todos:create",
        "todos:read",
        "todos:delete",
        "reports:read"
    ],

    admin: [
        "todos:create",
        "todos:read",
        "todos:delete",
        "reports:read",
        "users:delete",
        "roles:update"
    ]

```

Now:

```text
USER
 ├── todos:create
 └── todos:read

MODERATOR
 ├── todos:create
 ├── todos:read
 ├── todos:delete
 └── reports:read

ADMIN
 ├── todos:create
 ├── todos:read
 ├── todos:delete
 ├── reports:read
 ├── users:delete
 └── roles:update
```

# 14. Permission Check Example

Suppose:

```js
req.user.role = "moderator";
```

And:

```js
requiredPermission = "reports:read";
```

We get:

```js
const permissions =
    ROLE_PERMISSIONS["moderator"];
```

Result:

```js
[
    "todos:create",
    "todos:read",
    "todos:delete",
    "reports:read"
]
```

Then:

```js
permissions.includes("reports:read")
```

returns:

```text
true
```

So:

```js
next();
```

---

# 15. Unauthorized Permission

Now suppose:

```js
requiredPermission = "users:delete";
```

But moderator has:

```text
todos:create
todos:read
todos:delete
reports:read
```

No:

```text
users:delete
```

Therefore:

```js
permissions.includes("users:delete")
```

returns:

```text
false
```

Result:

```http
403 Forbidden
```

---

# 16. The Important Difference From Ownership

Suppose:

```text
Rahul
role = user
```

and:

```text
Rahul
permissions = [
    "todos:read",
    "todos:update"
]
```

Now Rahul has:

```text
todos:update
```

Does that mean Rahul can update:

```text
Todo #123
```

belonging to Amit?

**Not necessarily.**

Permission says:

```text
"What action can Rahul perform?"
```

Ownership says:

```text
"Which resource can Rahul perform it on?"
```

So:

```text
Permission
   +
Ownership
```

may both be required.

This becomes the next major concept in **15.8 — Resource Ownership**.

---

# 17. Example: Permission + Ownership

Suppose:

```text
Permission:
todos:update
```

And:

```text
Todo 123
ownerId = Amit
```

Rahul requests:

```http
PATCH /todos/123
```

Authorization might evaluate:

```text
Does Rahul have todos:update?
        ↓
       YES

Does Todo 123 belong to Rahul?
        ↓
       NO

Final decision:
       DENY
```

So:

```text
Permission alone ≠ authorization decision
```

It is one part of the decision.

---

# 18. Don't Confuse Permission With Authentication

Remember:

```text
Authentication
    ↓
Who is Rahul?
```

Then:

```text
Authorization
    ↓
What can Rahul do?
```

And permission-based authorization answers:

```text
Does Rahul have capability X?
```

For example:

```text
Authentication:
Rahul, user ID 123

Authorization:
todos:update = yes
```

---

# 19. Where Does the Permission Come From?

There are several possible designs.

### Option A — Derive from role

```text
JWT
 ↓
role = admin
 ↓
ROLE_PERMISSIONS.admin
 ↓
permissions
```

Simple and often sufficient for smaller applications.

---

### Option B — Store permissions directly

The user might have:

```js
{
    role: "user",
    permissions: [
        "reports:read"
    ]
}
```

This is more flexible, but also more complex.

---

### Option C — Database-driven RBAC

You might have database tables/collections such as:

```text
users
roles
permissions
role_permissions
user_roles
```

Then:

```text
User
 ↓
Role
 ↓
Role Permissions
```

This is useful for systems where administrators need to dynamically manage roles and permissions.

Don't build this complexity unless your application actually needs it.

---

# 20. A Practical Starter-Kit Approach

For your backend starter project, a sensible progression is:

```text
Phase 15.6
    ↓
Understand roles

Phase 15.7
    ↓
Understand permissions

Phase 15.8
    ↓
Understand ownership

Later
    ↓
Combine them
```

Don't jump immediately into a huge database-driven permission engine.

You want to understand the security model first.

---

# 21. Permission Naming

A clean naming convention helps.

A common pattern is:

```text
resource:action
```

Examples:

```text
users:read
users:create
users:update
users:delete

todos:read
todos:create
todos:update
todos:delete

reports:read

roles:read
roles:update
```

This is easy to read.

For example:

```js
PERMISSIONS.USERS_DELETE
```

maps to:

```text
users:delete
```

---

# 22. Avoid Vague Permissions

Avoid things like:

```text
manage
access
admin
full_access
```

These don't tell you enough.

Prefer:

```text
users:read
users:update
users:delete
roles:update
reports:read
```

The more specific the permission, the easier it is to reason about authorization.

---

# 23. Avoid Overly Fine-Grained Permissions Too Early

But don't go to the other extreme.

You don't necessarily need:

```text
users:read:first-name
users:read:last-name
users:read:email
users:read:phone
users:read:avatar
```

That can become unnecessarily complicated.

Start with meaningful business capabilities.

For example:

```text
users:read
```

and later introduce field-level restrictions only if there is a real requirement.

# 24. Permission Middleware Flow

Our middleware architecture now becomes:

```text
                  REQUEST
                     │
                     ▼
              authenticate
                     │
                     ▼
                  req.user
                     │
                     ▼
          requirePermission(...)
                     │
             ┌───────┴───────┐
             │               │
          allowed          denied
             │               │
             ▼               ▼
          next()            403
             │
             ▼
        Controller
```

Internally:

```text
req.user.role
      ↓
ROLE_PERMISSIONS
      ↓
permissions[]
      ↓
includes(requiredPermission)
```

---

# 25. Example Complete Flow

Let's say:

```js
router.delete(
    "/users/:id",
    authenticate,
    requirePermission(PERMISSIONS.USERS_DELETE),
    userController.deleteUser
);
```

Rahul:

```text
role = user
```

Permissions:

```text
todos:create
todos:read
todos:update
```

Request:

```http
DELETE /users/123
```

Flow:

```text
Authentication
    ↓
Rahul identified
    ↓
Role = user
    ↓
Permissions loaded
    ↓
Need users:delete
    ↓
Permission missing
    ↓
403
```

The controller never runs.

---

# 26. Why `403`?

Because Rahul is authenticated.

We know:

```text
Who is Rahul?
```

Yes.

But:

```text
Does Rahul have users:delete?
```

No.

Therefore:

```text
401 → identity problem
403 → permission problem
```

This distinction should now feel natural.

---

# 27. Don't Put Permission Checks in the Frontend Only

You might have:

```js
if (user.permissions.includes("users:delete")) {
    showDeleteButton();
}
```

That's useful for UI.

But it isn't security.

An attacker can hide the UI check and send:

```http
DELETE /api/v1/users/123
```

directly.

Therefore:

```text
Frontend permission check
       ↓
UX

Backend permission check
       ↓
Security
```

You need the backend check.

---

# 28. Permission Revocation

Here's another production concern.

Suppose:

```text
10:00
Amit = admin
```

At 10:01:

```text
Amit loses users:delete
```

But an old JWT may still contain:

```text
role = admin
```

If permissions are derived entirely from the token, the old token may continue to authorize the action until it expires.

This is why privileged access needs careful consideration around:

```text
token lifetime
revocation
session invalidation
role changes
permission changes
```

You don't need to solve all of this today.

The important thing is to recognize the problem.

---

# 29. Security Principle: Least Privilege

Permission-based authorization helps implement a very important security principle:

> **Give users only the access they actually need.**

For example:

A support employee may need:

```text
users:read
```

but not:

```text
users:delete
roles:update
```

So don't give them:

```text
admin
```

just because it's convenient.

Instead:

```text
support
 ↓
users:read
tickets:read
tickets:update
```

This reduces the damage if the account is compromised.

# 31. Permission Middleware vs Role Middleware

Keep this comparison:

||`requireRole()`|`requirePermission()`|
|---|---|---|
|Checks|Role|Permission|
|Example|`admin`|`users:delete`|
|Granularity|Coarser|More specific|
|Easy to start|✅|✅|
|Scales with many roles|Less flexible|More flexible|
|Ownership-aware|❌|❌|

The last row is important.

Neither one automatically solves ownership.

# 32. The Authorization Stack We're Building

At this point, your mental model should be:

```text
                    REQUEST
                       │
                       ▼
                Authentication
                       │
                       ▼
                    User
                       │
                       ▼
                     Role
                       │
                       ▼
                  Permission
                       │
                       ▼
                  Ownership
                       │
                       ▼
                Business Rules
                       │
                       ▼
                ALLOW / DENY
```

Not every endpoint needs every layer.

For example:

```text
GET /public-courses
```

might require none.

While:

```text
DELETE /admin/users/:id
```

might require:

```text
authentication
+
permission
+
additional business rules
```

And:

```text
PATCH /todos/:id
```

might require:

```text
authentication
+
permission
+
ownership
```

# 33. The Most Important Lesson

Don't think:

```text
"Admin can access this endpoint."
```

Think:

```text
"This operation requires the users:delete capability."
```

Then ask:

```text
Which roles have users:delete?
```

This separates:

```text
business capability
```

from:

```text
organizational role
```

That separation becomes very valuable as your application grows.
