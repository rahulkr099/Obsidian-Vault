# Lesson 15.8 — Resource Ownership

The official Phase 15 sequence puts **Resource Ownership** immediately after RBAC and permission-based authorization. The roadmap specifically highlights why a query like this is important:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

because authorization sometimes depends not only on **who the user is**, but also on **which resource they are trying to access**.

This is one of the most important backend security concepts in the entire phase.

---

# 1. The Problem

Imagine two users:

```text
Rahul
userId = A
```

and:

```text
Amit
userId = B
```

Rahul owns:

```text
Todo 101
ownerId = A
```

Amit owns:

```text
Todo 202
ownerId = B
```

Now Rahul sends:

```http
GET /api/v1/todos/202
```

The server receives:

```text
todoId = 202
userId = A
```

The important question is:

> Should Rahul be allowed to see Todo 202?

Obviously:

```text
NO
```

Even if Rahul is authenticated.

Even if Rahul has:

```text
todos:read
```

This is where **resource ownership** comes in.

---

# 2. Authentication Isn't Enough

We learned:

```text
Authentication
    ↓
Who is this user?
```

For Rahul:

```text
userId = A
```

Good.

Then we learned permissions:

```text
Does Rahul have todos:read?
```

Suppose:

```text
YES
```

Still, Rahul should not necessarily be able to access **every Todo**.

We need another question:

```text
Does this Todo belong to Rahul?
```

So:

```text
Authentication
      ↓
Who are you?

Permission
      ↓
What can you do?

Ownership
      ↓
Which resource can you do it to?
```

---

# 3. The Most Important Query

Suppose you have:

```js
const todo = await Todo.findById(todoId);
```

This asks:

> Find Todo 202.

It does **not** ask:

> Find Todo 202 belonging to Rahul.

That's a security problem when the endpoint is supposed to be user-scoped.

Instead:

```js
const todo = await Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

Now the database query itself enforces:

```text
Todo ID
+
Authenticated User ID
```

This is extremely powerful.

---

# 4. Why the Database Query Matters

Suppose:

```text
Todo 202
ownerId = B
```

Rahul:

```text
userId = A
```

Query:

```js
Todo.findOne({
    _id: "202",
    userId: "A"
});
```

MongoDB effectively asks:

```text
Does Todo 202 exist?
        AND
Does it belong to user A?
```

Result:

```text
No document
```

So Rahul cannot access it.

---

# 5. The Dangerous Version

Imagine this controller:

```js
const getTodo = async (req, res, next) => {
    try {
        const todo = await Todo.findById(req.params.id);

        if (!todo) {
            return res.status(404).json({
                success: false,
                message: "Todo not found"
            });
        }

        res.json({
            success: true,
            data: todo
        });
    } catch (error) {
        next(error);
    }
};
```

Looks completely normal.

But imagine:

```text
Todo 202 belongs to Amit.
```

Rahul sends:

```http
GET /todos/202
```

`findById()` finds it.

Then the server returns Amit's Todo to Rahul.

That's a broken access-control vulnerability.

---

# 6. The Safer Version

Instead:

```js
const todo = await Todo.findOne({
    _id: req.params.id,
    userId: req.user.id
});
```

Now:

```text
Rahul requests Todo 202
        ↓
Find Todo 202
        +
Check owner = Rahul
        ↓
No match
        ↓
Not accessible
```

This is the core idea of resource ownership.

---

# 7. Ownership Is a Relationship

Think of a resource like:

```text
Todo
```

with:

```js
{
    _id: "...",
    title: "Learn Express",
    userId: "123"
}
```

The:

```js
userId
```

creates a relationship:

```text
User 123
   │
   └──── owns ────> Todo ABC
```

Another Todo:

```text
User 456
   │
   └──── owns ────> Todo XYZ
```

So the database isn't just storing a Todo.

It's storing:

```text
resource
+
owner relationship
```

---

# 8. Ownership Doesn't Have to Be Called `userId`

You might see:

```js
userId
```

or:

```js
ownerId
```

or:

```js
createdBy
```

or:

```js
authorId
```

The naming depends on the domain.

For example:

### Todo

```js
userId
```

### Blog post

```js
authorId
```

### Uploaded document

```js
ownerId
```

### Course

```js
instructorId
```

The concept is the same:

```text
resource → responsible/owning identity
```

---

# 9. Ownership in an LMS

This becomes especially important for your LMS.

Suppose:

```text
Instructor A
    ↓
Course A
```

and:

```text
Instructor B
    ↓
Course B
```

Instructor A sends:

```http
PATCH /api/v1/courses/course-B
```

Changing the URL is easy.

The backend must ask:

```text
Does Course B belong to Instructor A?
```

If not:

```text
DENY
```

The fact that Instructor A is an instructor doesn't automatically give them access to every course.

---

# 10. Role + Ownership

This is where our previous lessons connect.

Suppose:

```text
Instructor A
role = instructor
```

and:

```text
Course B
instructorId = B
```

Request:

```http
PATCH /courses/B
```

Authorization might be:

```text
Is user authenticated?
       ↓
      YES

Does user have courses:update?
       ↓
      YES

Does this course belong to user?
       ↓
      NO

DENY
```

So:

```text
Role
+
Permission
+
Ownership
```

can form the authorization decision.

---

# 11. Ownership Is Not Always Required

Not every resource belongs to one user.

For example:

```text
GET /api/v1/courses
```

might be public.

Or:

```text
GET /api/v1/admin/reports
```

might be admin-only.

There may be no ownership requirement.

So don't blindly add:

```js
userId
```

to every query.

Ask:

> Is this resource user-scoped?

If yes, ownership may matter.

---

# 12. User-Scoped vs Global Resources

### User-scoped

```text
Todo
Personal profile
Private notes
Private documents
```

Usually:

```text
user
 ↓
resource
```

### Global/shared

```text
Public courses
Countries
Categories
System configuration
```

These may not belong to a particular user.

So:

```text
Todo → ownership likely
Country → ownership usually irrelevant
```

---

# 13. Ownership for Create

Ownership also matters during creation.

Suppose Rahul sends:

```http
POST /todos
```

with:

```json
{
    "title": "Learn MongoDB",
    "userId": "Amit"
}
```

Should we trust:

```js
req.body.userId
```

?

**No.**

The authenticated identity should determine ownership.

Instead:

```js
const todo = await Todo.create({
    title: req.body.title,
    userId: req.user.id
});
```

Now:

```text
Authenticated user
       ↓
ownership assigned by server
```

The client doesn't get to choose the owner.

---

# 14. Very Important: Never Trust Client Ownership

Bad:

```js
const todo = await Todo.create({
    title: req.body.title,
    userId: req.body.userId
});
```

An attacker could send:

```json
{
    "title": "Secret",
    "userId": "some-other-user"
}
```

Now they might create a resource under another user's identity.

Instead:

```js
const todo = await Todo.create({
    title: req.body.title,
    userId: req.user.id
});
```

The server decides ownership.

---

# 15. Ownership During Update

Suppose:

```http
PATCH /todos/123
```

Bad:

```js
Todo.findByIdAndUpdate(
    req.params.id,
    req.body
);
```

The query identifies only:

```text
Todo ID
```

It doesn't establish:

```text
Current user owns Todo
```

Safer:

```js
Todo.findOneAndUpdate(
    {
        _id: req.params.id,
        userId: req.user.id
    },
    {
        $set: {
            title: req.body.title
        }
    },
    {
        new: true
    }
);
```

Now the update happens only if both conditions match.

---

# 16. Ownership During Delete

Same idea.

Dangerous:

```js
Todo.findByIdAndDelete(req.params.id);
```

Safer:

```js
Todo.findOneAndDelete({
    _id: req.params.id,
    userId: req.user.id
});
```

The database operation itself becomes user-scoped.

---

# 17. Ownership During List Queries

This is another common mistake.

Suppose:

```http
GET /api/v1/todos
```

Bad:

```js
Todo.find({});
```

This could return every user's Todos.

Instead:

```js
Todo.find({
    userId: req.user.id
});
```

Now Rahul gets:

```text
Rahul's Todos
```

not:

```text
Everyone's Todos
```

This is especially important for list endpoints.

---

# 18. The Four Basic CRUD Queries

For a user-owned resource:

### Create

```js
Todo.create({
    ...data,
    userId
});
```

### Read one

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

### Update

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId
    },
    updateData
);
```

### Delete

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId
});
```

Notice the repeated pattern:

```text
resource ID
+
user ID
```

That pattern is the foundation of secure ownership queries.

---

# 19. Why This Is Better Than "Find Then Check"

You might think:

```js
const todo = await Todo.findById(todoId);

if (todo.userId !== req.user.id) {
    return res.status(403).json(...);
}
```

This can work.

But there are advantages to querying with ownership directly:

```js
Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

The database is asked for only a resource that the current user is allowed to access.

Conceptually:

```text
❌ Find resource
   ↓
   Then ask if allowed

✅ Ask database for allowed resource
```

This becomes especially valuable in repository design.

---

# 20. Not Found vs Forbidden

Here's an interesting security design decision.

Suppose Rahul requests Amit's Todo:

```http
GET /todos/202
```

Our query:

```js
Todo.findOne({
    _id: "202",
    userId: "Rahul"
});
```

returns:

```text
null
```

What should the API return?

One option:

```http
404 Not Found
```

Another:

```http
403 Forbidden
```

For many user-owned resources, returning:

```http
404
```

is useful because it doesn't reveal whether another user's resource exists.

In other words:

```text
"Todo 202 doesn't exist for you"
```

can be safer than:

```text
"Todo 202 exists, but you're not allowed to access it."
```

This can reduce information leakage.

We'll go deeper into this when we study privilege escalation and testing.

---

# 21. Ownership Is a Security Boundary

Think of:

```js
userId
```

not merely as a database field.

It's part of your security boundary.

For example:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

is doing two jobs:

```text
Database lookup
+
Authorization enforcement
```

This is why the roadmap specifically highlights this pattern.

---

# 22. Repository Layer Is a Great Place for This

Remember our architecture:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

The controller might receive:

```js
req.params.id
req.user.id
```

The service can make the business decision:

```text
"User can operate on their own Todo."
```

Then the repository can perform:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

This keeps database access centralized.

---

# 23. Example Repository

```js
const findTodoByIdAndUser = async (todoId, userId) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

Then:

```js
const updateTodo = async (
    todoId,
    userId,
    updateData
) => {
    return Todo.findOneAndUpdate(
        {
            _id: todoId,
            userId
        },
        {
            $set: updateData
        },
        {
            new: true
        }
    );
};
```

The repository now naturally enforces the ownership boundary.

---

# 24. Service Layer

The service might do:

```js
const updateTodo = async ({
    todoId,
    userId,
    data
}) => {
    const todo = await todoRepository.updateTodo(
        todoId,
        userId,
        data
    );

    if (!todo) {
        throw new NotFoundError(
            "Todo not found"
        );
    }

    return todo;
};
```

Notice:

```text
Controller
    ↓
passes identity
    ↓
Service
    ↓
Repository
    ↓
ownership query
```

---

# 25. Controller

The controller should stay relatively thin:

```js
const updateTodo = async (req, res, next) => {
    try {
        const todo = await todoService.updateTodo({
            todoId: req.params.id,
            userId: req.user.id,
            data: req.body
        });

        res.json({
            success: true,
            data: todo
        });
    } catch (error) {
        next(error);
    }
};
```

The controller doesn't need to manually perform the MongoDB query.

---

# 26. Why `req.user.id` Matters

Where does:

```js
req.user.id
```

come from?

From authentication middleware.

Conceptually:

```text
JWT
 ↓
verify token
 ↓
identify user
 ↓
req.user
```

Then:

```text
req.user.id
```

becomes the trusted identity used by authorization.

So the full chain is:

```text
Token
 ↓
Authentication
 ↓
req.user.id
 ↓
Ownership query
 ↓
Resource access
```

---

# 27. Never Take the Current User ID From the URL

Suppose you have:

```http
GET /users/A/todos/123
```

It might be tempting to use:

```js
req.params.userId
```

as the identity.

But a client can change:

```text
/users/A/
```

to:

```text
/users/B/
```

The server should determine the current authenticated user from the authentication context:

```js
req.user.id
```

not trust an arbitrary identity supplied by the client.

---

# 28. A Classic Vulnerability

Suppose the endpoint is:

```http
GET /api/v1/users/:userId/todos/:todoId
```

and the server does:

```js
Todo.findOne({
    _id: req.params.todoId,
    userId: req.params.userId
});
```

Attacker:

```text
/user/B/todos/202
```

They've changed:

```text
userId
```

to someone else's ID.

If the server doesn't verify that:

```js
req.params.userId === req.user.id
```

then the attacker may access another user's data.

This is exactly why client-controlled identifiers must not automatically be treated as trusted identity.

---

# 29. Resource Ownership and IDOR

You'll study **IDOR** and **horizontal privilege escalation** later in:

```text
15.9 User A vs User B
15.10 Horizontal privilege escalation
```

The connection is:

```text
Attacker
 ↓
changes resource ID
 ↓
server retrieves resource
 ↓
ownership isn't checked
 ↓
attacker sees/changes another user's resource
```

That's a classic broken access-control problem.

The roadmap explicitly puts User A vs User B and horizontal privilege escalation immediately after ownership for this reason.

---

# 30. Horizontal vs Vertical

Don't worry about mastering these yet, but understand the direction.

### Horizontal

```text
User A
  ↓
accesses User B's resource
```

Same privilege level.

### Vertical

```text
User
  ↓
accesses admin functionality
```

Higher privilege.

Ownership is particularly important for preventing:

```text
User A → User B's resources
```

We'll study that directly in 15.9 and 15.10.

---

# 31. Ownership Isn't Always One-to-One

Consider an LMS course.

It might have:

```text
course
 ├── instructorId
 └── students[]
```

Now ownership may be more complicated.

Perhaps:

```text
Instructor
    ↓
can edit course
```

while:

```text
Student
    ↓
can read/enroll
```

So we shouldn't blindly think:

```text
one resource = one owner
```

Instead:

> **Ownership is one possible relationship used to determine authorization.**

---

# 32. Organization-Based Ownership

Imagine a SaaS application:

```text
Organization A
 ├── Rahul
 ├── Amit
 └── Priya
```

Resources:

```text
Organization A
 ├── Project 1
 ├── Project 2
 └── Project 3
```

Rahul might not individually own Project 1.

Instead:

```text
Rahul
 ↓
member of Organization A
 ↓
has access to Organization A resources
```

So the authorization query might involve:

```text
organizationId
+
user membership
```

rather than simply:

```text
userId
```

We'll encounter these more advanced patterns later.

---

# 33. Ownership Can Be Based on Relationships

Examples:

```text
Todo
 → userId

Course
 → instructorId

Comment
 → authorId

Order
 → customerId

Document
 → organizationId

Project
 → teamId
```

Authorization depends on the domain relationship.

The important question is:

> **What relationship connects the authenticated user to this resource?**

---

# 34. A Secure Mental Model

For every protected resource, ask these questions:

```text
1. Who is making the request?
        ↓
2. What are they allowed to do?
        ↓
3. What resource are they targeting?
        ↓
4. What relationship do they have with it?
        ↓
5. Is that relationship sufficient?
```

For a Todo:

```text
Rahul
 ↓
todos:update
 ↓
Todo 123
 ↓
ownerId = Rahul
 ↓
ALLOW
```

For Amit's Todo:

```text
Rahul
 ↓
todos:update
 ↓
Todo 456
 ↓
ownerId = Amit
 ↓
DENY
```

---

# 35. The Pattern You Should Memorize

For user-owned MongoDB resources:

```js
{
    _id: resourceId,
    userId: req.user.id
}
```

For example:

```js
const todo = await Todo.findOne({
    _id: req.params.id,
    userId: req.user.id
});
```

This is much better than:

```js
const todo = await Todo.findById(
    req.params.id
);
```

when the resource is supposed to be accessible only by its owner.

---

# 36. But Don't Blindly Add `userId`

This is also important.

Suppose an admin should be able to view **all users' Todos**.

If you always do:

```js
Todo.find({
    userId: req.user.id
});
```

then the admin can only see their own Todos.

That's incorrect.

You might instead have separate authorization behavior:

```text
Normal user
    ↓
own resources

Admin
    ↓
all resources
```

So ownership rules depend on the user's role and the operation.

---

# 37. Combining Role + Ownership

For example:

```text
Normal user:
    can update own Todo

Admin:
    can update any Todo
```

The authorization policy becomes:

```text
Is admin?
   ↓
YES → allow

NO
   ↓
Does Todo belong to user?
   ↓
YES → allow
NO  → deny
```

This is more realistic than simply:

```text
user → allowed
admin → allowed
```

---

# 38. Least Privilege

Ownership also supports the principle of:

> **Least privilege**

If Rahul only needs access to:

```text
Rahul's Todos
```

don't give him:

```text
All Todos
```

The query itself can enforce the narrow boundary:

```js
Todo.find({
    userId: req.user.id
});
```

This reduces accidental exposure.

---

# 39. Important Security Rule

Never trust:

```text
req.body.userId
req.query.userId
req.params.userId
```

as proof of the current user's identity.

Use:

```js
req.user.id
```

from the authenticated security context.

Client-provided IDs can identify a **target resource**.

They should not automatically define **who the requester is**.

---

# 40. Final Architecture

For a user-owned Todo:

```text
                     REQUEST
                        │
                        ▼
                 Authentication
                        │
                        ▼
                    req.user
                        │
                        ▼
                  Permission check
                        │
                        ▼
                   Controller
                        │
                        ▼
                     Service
                        │
                        ▼
                   Repository
                        │
                        ▼
              ┌──────────────────┐
              │ _id = todoId     │
              │ userId = userId  │
              └────────┬─────────┘
                       │
                       ▼
                    MongoDB
                       │
                ┌──────┴──────┐
                │             │
             Match          No match
                │             │
                ▼             ▼
             Resource       Not found
```

This is the architecture you should have in your head.
