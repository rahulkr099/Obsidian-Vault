# Lesson 15.9 — User A vs User B

This lesson takes the **resource ownership** concept from 15.8 and turns it into a real security scenario.

The Phase 15 roadmap places **User A vs User B** directly after Resource Ownership, before horizontal privilege escalation.

The main question is:

> **Can User A access or modify User B's resource?**

If the answer is yes when it shouldn't be, you have a serious authorization problem.

---

# 1. The Basic Scenario

Let's create two users:

```text
User A
userId = 101

User B
userId = 202
```

And two Todos:

```text
Todo 1
ownerId = 101

Todo 2
ownerId = 202
```

So:

```text
User A
  │
  └── Todo 1


User B
  │
  └── Todo 2
```

Everything is fine.

---

# 2. User A Requests Their Own Todo

User A sends:

```http
GET /api/v1/todos/1
```

Server knows:

```text
req.user.id = 101
```

Database query:

```js
Todo.findOne({
    _id: 1,
    userId: 101
});
```

Result:

```text
Todo 1
```

Allowed.

```text
User A
  ↓
Todo 1
  ↓
OWNER
  ↓
ALLOW
```

---

# 3. Now User A Requests User B's Todo

User A changes the URL:

```http
GET /api/v1/todos/2
```

The attacker is essentially saying:

> "I want Todo 2."

The server must **not** assume that because the ID is valid, access is allowed.

The secure query is:

```js
Todo.findOne({
    _id: 2,
    userId: 101
});
```

But Todo 2 actually contains:

```text
ownerId = 202
```

Therefore:

```text
_id = 2
      +
userId = 101

        ↓

NO MATCH
```

Access denied.

---

# 4. The Dangerous Implementation

Consider this:

```js
const getTodo = async (req, res, next) => {
    try {
        const todo = await Todo.findById(req.params.id);

        if (!todo) {
            return res.status(404).json({
                success: false,
                message: "Todo not found"
            });
        }

        res.json({
            success: true,
            data: todo
        });
    } catch (error) {
        next(error);
    }
};
```

At first glance, this looks perfectly normal.

But there's a security problem.

The query only checks:

```text
Todo ID
```

It doesn't check:

```text
Who owns the Todo?
```

---

# 5. How the Attack Works

Database:

```text
Todo 1 → owner 101
Todo 2 → owner 202
Todo 3 → owner 303
```

User A:

```text
userId = 101
```

User A knows or guesses:

```text
Todo ID = 2
```

They send:

```http
GET /todos/2
```

Server executes:

```js
Todo.findById(2);
```

MongoDB returns:

```text
Todo 2
ownerId = 202
```

And the server sends it back.

Now:

```text
User A
  │
  │ requests Todo 2
  ▼
Server
  │
  │ findById(2)
  ▼
Todo 2
  │
  │ belongs to User B
  ▼
User A receives it
```

That's a security failure.

---

# 6. The Secure Implementation

Instead:

```js
const todo = await Todo.findOne({
    _id: req.params.id,
    userId: req.user.id
});
```

Now the database query contains two conditions:

```text
1. Is this the requested Todo?
2. Does it belong to the authenticated user?
```

For User A requesting Todo 2:

```js
{
    _id: 2,
    userId: 101
}
```

But the actual document is:

```js
{
    _id: 2,
    userId: 202
}
```

No match.

Therefore:

```text
DENIED
```

---

# 7. Why This Is So Powerful

Notice something interesting.

We're not doing:

```js
const todo = await Todo.findById(id);

if (todo.userId !== req.user.id) {
    // deny
}
```

Instead:

```js
const todo = await Todo.findOne({
    _id: id,
    userId: req.user.id
});
```

The database query itself represents the security boundary.

Think:

```text
❌ Find everything, then remember to check access

✅ Ask only for something the current user is allowed to access
```

This is one of the most useful patterns you'll carry into real backend development.

---

# 8. The Same Problem Exists With Update

Suppose User A sends:

```http
PATCH /api/v1/todos/2
```

with:

```json
{
  "title": "Hacked Todo"
}
```

Dangerous:

```js
Todo.findByIdAndUpdate(
    req.params.id,
    req.body
);
```

This says:

> Update whatever Todo has this ID.

It doesn't say:

> Update this Todo only if it belongs to the current user.

---

# 9. Secure Update

Instead:

```js
Todo.findOneAndUpdate(
    {
        _id: req.params.id,
        userId: req.user.id
    },
    {
        $set: {
            title: req.body.title
        }
    },
    {
        new: true
    }
);
```

Now User A cannot update User B's Todo.

The query:

```js
{
    _id: 2,
    userId: 101
}
```

doesn't match:

```js
{
    _id: 2,
    userId: 202
}
```

Therefore no update occurs.

---

# 10. Same Problem With Delete

Dangerous:

```js
Todo.findByIdAndDelete(req.params.id);
```

User A could potentially delete:

```text
Todo 2 → User B
```

Secure:

```js
Todo.findOneAndDelete({
    _id: req.params.id,
    userId: req.user.id
});
```

Now:

```text
User A
   ↓
Todo 2
   ↓
Does Todo 2 belong to A?
   ↓
NO
   ↓
No deletion
```

---

# 11. Same Problem With List Endpoints

This mistake is even easier to make.

Suppose:

```http
GET /api/v1/todos
```

Dangerous:

```js
const todos = await Todo.find({});
```

This returns:

```text
User A's Todos
User B's Todos
User C's Todos
...
```

If this endpoint is intended to show the current user's Todos, that's a major problem.

Instead:

```js
const todos = await Todo.find({
    userId: req.user.id
});
```

Now:

```text
User A
 ↓
only User A's Todos
```

---

# 12. The Four CRUD Rules

For a user-owned resource, remember this pattern.

### CREATE

```js
Todo.create({
    ...data,
    userId: req.user.id
});
```

### READ

```js
Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

### UPDATE

```js
Todo.findOneAndUpdate(
    {
        _id: todoId,
        userId: req.user.id
    },
    updateData
);
```

### DELETE

```js
Todo.findOneAndDelete({
    _id: todoId,
    userId: req.user.id
});
```

The important part is:

```text
resource ID
+
authenticated user ID
```

---

# 13. Never Trust `userId` From the Request

This is extremely important.

Imagine the client sends:

```json
{
    "title": "Learn MongoDB",
    "userId": "202"
}
```

Should the server create the Todo for User B?

**No.**

The authenticated user is:

```text
req.user.id = 101
```

Therefore:

```js
Todo.create({
    title: req.body.title,
    userId: req.user.id
});
```

The server determines ownership.

Not the client.

---

# 14. Why `req.user.id` Is Trusted

Remember the authentication flow:

```text
Authorization: Bearer <JWT>
            ↓
       JWT verification
            ↓
        authenticated
            ↓
          req.user
```

So:

```js
req.user.id
```

comes from the authenticated identity established by the backend.

But:

```js
req.body.userId
```

comes from the client.

Those are fundamentally different trust levels.

---

# 15. URL Parameters Are Not Identity

Suppose your route is:

```http
GET /users/:userId/todos/:todoId
```

It may be tempting to do:

```js
Todo.findOne({
    _id: req.params.todoId,
    userId: req.params.userId
});
```

But `userId` is client-controlled.

User A could send:

```http
GET /users/202/todos/2
```

even though:

```text
req.user.id = 101
```

Therefore:

```text
URL userId = 202
```

doesn't prove:

```text
current user = 202
```

The authenticated identity must come from:

```js
req.user.id
```

---

# 16. User A vs User B

Let's make the security boundary very explicit.

```text
                 APPLICATION
                      │
          ┌───────────┴───────────┐
          │                       │
       User A                  User B
       101                     202
          │                       │
          ▼                       ▼
       Todo 1                  Todo 2
```

User A should normally have:

```text
Todo 1 → YES
Todo 2 → NO
```

User B should have:

```text
Todo 1 → NO
Todo 2 → YES
```

This is **horizontal authorization**.

Both users may have the same role:

```text
user
```

but each is restricted to their own resources.

---

# 17. Same Role Does Not Mean Same Resources

This is an important concept.

Suppose:

```text
User A → role=user
User B → role=user
```

Both have:

```text
todos:read
todos:update
```

Does User A have access to User B's Todos?

No.

Because:

```text
Permission
    ↓
What operation can you perform?

Ownership
    ↓
Which resources can you perform it on?
```

So:

```text
User A
 ├── todos:read
 └── owns Todo 1

User B
 ├── todos:read
 └── owns Todo 2
```

Same permissions.

Different resources.

---

# 18. This Is Why RBAC Alone Isn't Enough

Imagine:

```text
Role:
user
```

and:

```text
Permissions:
todos:read
todos:update
todos:delete
```

RBAC tells us:

```text
User A can read Todos.
```

But it doesn't answer:

```text
Can User A read Todo 2?
```

That's a resource-level question.

So:

```text
RBAC
+
Resource ownership
```

gives us a much stronger authorization model.

---

# 19. Ownership and Services

Remember our architecture:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
MongoDB
```

Suppose:

```http
PATCH /todos/2
```

Controller:

```js
const updateTodo = async (req, res, next) => {
    try {
        const todo = await todoService.updateTodo({
            todoId: req.params.id,
            userId: req.user.id,
            data: req.body
        });

        res.json({
            success: true,
            data: todo
        });
    } catch (error) {
        next(error);
    }
};
```

The controller extracts:

```text
todoId
userId
data
```

and passes them to the service.

---

# 20. Service

The service might do:

```js
const updateTodo = async ({
    todoId,
    userId,
    data
}) => {
    const todo = await todoRepository.updateOwnedTodo(
        todoId,
        userId,
        data
    );

    if (!todo) {
        throw new NotFoundError(
            "Todo not found"
        );
    }

    return todo;
};
```

The service knows the operation requires:

```text
todoId
+
userId
```

---

# 21. Repository

Then:

```js
const updateOwnedTodo = async (
    todoId,
    userId,
    data
) => {
    return Todo.findOneAndUpdate(
        {
            _id: todoId,
            userId
        },
        {
            $set: data
        },
        {
            new: true
        }
    );
};
```

Now the repository performs the actual ownership-aware query.

This fits beautifully with the repository architecture you studied in Phase 13.

---

# 22. What Happens When User B Tries?

User B:

```text
userId = 202
```

requests:

```text
Todo 1
```

Repository:

```js
Todo.findOneAndUpdate({
    _id: 1,
    userId: 202
});
```

But:

```text
Todo 1 → ownerId = 101
```

So:

```text
No match
```

The service receives:

```js
null
```

and returns an appropriate error.

The important thing:

> **The update never happens.**

---

# 23. Why This Is Better Than Checking Only in the Controller

You could write:

```text
Controller
 ↓
find Todo
 ↓
check owner
 ↓
update Todo
```

But now every controller needs to remember the same security rule.

That creates opportunities for mistakes.

Instead, having repository methods such as:

```text
findOwnedTodo()
updateOwnedTodo()
deleteOwnedTodo()
```

makes the ownership requirement explicit.

For example:

```js
todoRepository.updateOwnedTodo(
    todoId,
    userId,
    data
);
```

The method name itself communicates:

> This operation is ownership-aware.

---

# 24. But Don't Put Everything Into the Repository

There is an important boundary.

Repository:

```text
How do I query the database?
```

Service:

```text
Is this operation allowed according to business rules?
```

For example:

```text
Repository:
find Todo where _id=X and userId=Y
```

Service:

```text
A normal user can update only their own Todo.
Admin can update any Todo.
Completed Todos cannot be edited.
```

The service can decide which repository operation is appropriate.

---

# 25. Admin Exception

Now let's make it realistic.

Suppose:

```text
user
```

can update:

```text
own Todos
```

but:

```text
admin
```

can update:

```text
any Todo
```

Then the service could conceptually do:

```text
if admin
    ↓
update by ID

else
    ↓
update by ID + userId
```

So:

```text
ADMIN
 ↓
Todo.findByIdAndUpdate()

USER
 ↓
Todo.findOneAndUpdate({
    _id,
    userId
})
```

The authorization policy determines the appropriate data access.

---

# 26. Be Careful With This Pattern

Don't make your repository silently decide:

```text
"If admin, ignore ownership."
```

That mixes authorization policy into the data layer.

A cleaner design is:

```text
Service
 ↓
decides what operation is allowed
 ↓
Repository
 ↓
executes appropriate query
```

This separation becomes important when your authorization rules become more complex.

---

# 27. What If the ID Doesn't Exist?

User A requests:

```text
Todo 999
```

and it doesn't exist.

Result:

```text
null
```

What if Todo 999 exists but belongs to User B?

Our ownership-aware query also returns:

```text
null
```

This can intentionally produce the same external response:

```http
404 Not Found
```

That means an attacker doesn't easily learn:

```text
"Does Todo 999 belong to another user?"
```

This is a useful information-leakage defense.

---

# 28. The Security Boundary

Here's the key mental model:

```text
                REQUEST
                   │
                   ▼
             Authentication
                   │
                   ▼
              User A (101)
                   │
                   ▼
             Permission
             todos:update
                   │
                   ▼
             Target Todo 2
                   │
                   ▼
        ┌─────────────────────┐
        │ ownerId === 101 ?   │
        └──────────┬──────────┘
                   │
              ┌────┴────┐
              │         │
             YES        NO
              │         │
              ▼         ▼
            ALLOW      DENY
```

That's the exact decision we're learning to make.

---

# 29. A Real-World Example

Imagine a banking application.

```text
User A
accountId = 1001

User B
accountId = 2002
```

User A sends:

```http
GET /accounts/2002
```

If the server does:

```js
Account.findById(req.params.accountId);
```

User A might see User B's account.

That's obviously unacceptable.

A secure query might be conceptually:

```js
Account.findOne({
    _id: req.params.accountId,
    ownerId: req.user.id
});
```

The same principle applies to:

```text
bank accounts
orders
documents
messages
todos
profiles
private files
invoices
```

---

# 30. Another Example: Orders

Suppose:

```text
Order A → customerId = 101
Order B → customerId = 202
```

User A:

```http
GET /orders/B
```

The backend must ensure:

```text
order.customerId === req.user.id
```

Otherwise User A could potentially see:

```text
User B's address
User B's order items
User B's payment information
```

That becomes a serious sensitive-data exposure issue.

---

# 31. Another Example: Private Documents

```text
Document A
ownerId = 101
```

Attacker:

```http
GET /documents/A
```

If document IDs are predictable, they may try:

```http
GET /documents/B
GET /documents/C
GET /documents/D
```

Therefore:

```text
authentication
+
permission
+
ownership
```

must be evaluated.

---

# 32. Predictable IDs Are Not the Real Defense

You might think:

> "I'll use UUIDs/ObjectIds so attackers can't guess IDs."

That's useful, but **not sufficient**.

Even if IDs are difficult to guess:

```text
authorization must still be enforced
```

Security should never depend on:

```text
"Nobody will know the ID."
```

Instead:

```text
They may know the ID.
Can they access it?
```

That is the correct security question.

---

# 33. What About MongoDB ObjectIds?

MongoDB ObjectIds are not designed to be authorization mechanisms.

Even if:

```text
ObjectId = difficult-to-guess
```

you should still enforce:

```js
{
    _id: resourceId,
    userId: authenticatedUserId
}
```

Security comes from authorization.

Not obscurity.

---

# 34. User A vs User B Test

This gives you a very useful security test.

Create:

```text
User A
Todo A
```

and:

```text
User B
Todo B
```

Authenticate as User A.

Test:

```text
GET Todo A
```

Expected:

```text
200
```

Then:

```text
GET Todo B
```

Expected:

```text
404/403
```

depending on your API design.

Then:

```text
PATCH Todo B
```

Expected:

```text
DENIED
```

Then:

```text
DELETE Todo B
```

Expected:

```text
DENIED
```

This is the beginning of authorization testing.

---

# 35. Don't Test Only the GET Endpoint

A common mistake is testing:

```text
GET /todos/:id
```

and stopping.

You should test every operation:

```text
GET
POST
PATCH
PUT
DELETE
```

because authorization bugs can exist in one operation but not another.

For example:

```text
GET → protected correctly
PATCH → forgot ownership check
DELETE → protected correctly
```

The application is still vulnerable.

---

# 36. The CRUD Security Matrix

For a user-owned Todo:

|Operation|User A on Todo A|User A on Todo B|
|---|--:|--:|
|Create|✅|N/A|
|Read|✅|❌|
|Update|✅|❌|
|Delete|✅|❌|

This simple table is incredibly useful when designing authorization.

---

# 37. A More Complete Authorization Model

Now combine what we've learned:

```text
User A
   │
   ├── Authentication
   │
   ├── Role
   │
   ├── Permissions
   │
   └── Ownership
```

For example:

```text
User A
role = user
permissions = [
    todos:read,
    todos:update
]
```

Target:

```text
Todo 123
ownerId = User A
```

Decision:

```text
Authenticated?     YES
Has todos:update?  YES
Owns Todo 123?     YES

                    ↓

                  ALLOW
```

Change ownership:

```text
Todo 123
ownerId = User B
```

Decision:

```text
Authenticated?     YES
Has todos:update?  YES
Owns Todo 123?     NO

                    ↓

                  DENY
```

---

# 38. The Big Lesson

Don't think:

> "User A is logged in, so User A can access the resource."

Instead ask:

```text
Who?
 ↓
User A

What can they do?
 ↓
todos:update

To what?
 ↓
Todo 123

What relationship do they have?
 ↓
owner

Does that satisfy the authorization policy?
 ↓
YES / NO
```

That's the foundation of proper authorization.

---

# 🧠 What You Should Remember From 15.9

The most important pattern is:

```js
Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

Not:

```js
Todo.findById(todoId);
```

when the resource is user-owned.

And:

```text
User A having a permission
        ≠
User A having access to every resource
```

Instead:

```text
Permission
    +
Resource relationship
    =
Authorization decision
```

The Phase 15 roadmap intentionally follows this lesson with **15.10 Horizontal Privilege Escalation**, because User A accessing User B's resource is exactly the security problem we need to understand next.
