# Phase 16 — API Response Architecture

## Lesson 16.10 — Consistent API Contracts

This is a **gold-level backend interview topic**.

At this point, you've learned:

- response envelopes
    
- HTTP status codes
    
- validation errors
    
- request IDs
    
- error handling
    

Now we combine them into one idea:

> **An API contract defines the predictable structure and behavior that clients can rely on when communicating with your backend.**

A good backend isn't just "returning JSON."

It returns JSON in a way that remains understandable and stable as the application grows.

---

# 1. What Is an API Contract?

Suppose your frontend calls:

```http
GET /api/v1/todos
```

It needs to know:

```text
What does success look like?
What does failure look like?
Where is the data?
How are errors represented?
What status codes are used?
How is pagination represented?
Can the response change later?
```

These expectations form the **API contract**.

Think of it as an agreement:

```text
Frontend
   ↕
 API Contract
   ↕
Backend
```

The frontend shouldn't need to inspect your controller implementation.

It should simply know:

> "If I call this endpoint, I know what kind of response I'll receive."

---

# 2. Why Consistency Matters

Imagine these three endpoints:

### Endpoint A

```json
{
  "success": true,
  "data": {
    "id": "123"
  }
}
```

### Endpoint B

```json
{
  "status": "ok",
  "user": {
    "id": "456"
  }
}
```

### Endpoint C

```json
{
  "result": [
    {
      "id": "789"
    }
  ]
}
```

All three might work.

But the frontend now needs three different patterns.

That's unnecessary complexity.

A better API establishes conventions.

For example:

```json
{
  "success": true,
  "data": {}
}
```

and:

```json
{
  "success": false,
  "error": {}
}
```

Now clients know what to expect.

---

# 3. Contract Is More Than JSON Shape

This is important for interviews.

An API contract includes more than:

```text
JSON structure
```

It can include:

```text
HTTP method
URL
request parameters
request body
authentication requirements
status codes
response structure
error format
pagination
headers
caching behavior
versioning
```

For example:

```http
POST /api/v1/todos
```

might have a contract:

```text
Request:
    title: string
    description?: string

Success:
    201 Created

Failure:
    400 Validation Error
    401 Unauthorized
    409 Conflict

Response:
    standard success envelope
```

That's a real API contract.

---

# 4. Our API Contract

For our backend architecture, we can establish:

### Success

```json
{
  "success": true,
  "data": {}
}
```

### Error

```json
{
  "success": false,
  "code": "SOME_ERROR",
  "message": "Something went wrong",
  "requestId": "req_123"
}
```

For validation:

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "Validation failed",
  "errors": [
    {
      "field": "email",
      "message": "Invalid email address"
    }
  ],
  "requestId": "req_123"
}
```

This gives the frontend a predictable structure.

---

# 5. The Success Contract

Suppose:

```http
GET /api/v1/todos/123
```

returns:

```json
{
  "success": true,
  "data": {
    "id": "123",
    "title": "Learn backend",
    "completed": false
  }
}
```

The client knows:

```text
success === true
       ↓
look at data
```

That's simple.

---

# 6. Collection Response

Suppose:

```http
GET /api/v1/todos
```

returns multiple todos:

```json
{
  "success": true,
  "data": [
    {
      "id": "1",
      "title": "Learn Express"
    },
    {
      "id": "2",
      "title": "Learn MongoDB"
    }
  ]
}
```

That's fine.

But once pagination enters the picture, you'll want more structure.

---

# 7. Paginated Response

For example:

```json
{
  "success": true,
  "data": [
    {
      "id": "1",
      "title": "Learn Express"
    },
    {
      "id": "2",
      "title": "Learn MongoDB"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 10,
    "totalItems": 42,
    "totalPages": 5
  }
}
```

Now the contract tells the frontend:

```text
data
  ↓
actual records

pagination
  ↓
information about the collection
```

---

# 8. Don't Mix Metadata With Data

Avoid this:

```json
{
  "success": true,
  "data": [
    {
      "id": "1"
    }
  ],
  "page": 1,
  "limit": 10,
  "total": 42
}
```

It can work, but as the API grows, response structure becomes harder to organize.

Prefer:

```json
{
  "success": true,
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 10,
    "totalItems": 42
  }
}
```

Now the structure communicates meaning.

---

# 9. Single Resource vs Collection

This distinction should be clear.

### Single resource

```text
GET /todos/123
```

```json
{
  "success": true,
  "data": {
    "id": "123",
    "title": "Learn APIs"
  }
}
```

### Collection

```text
GET /todos
```

```json
{
  "success": true,
  "data": [
    {
      "id": "123"
    },
    {
      "id": "456"
    }
  ]
}
```

Same contract:

```text
success
  ↓
data
```

Different data type:

```text
object
vs
array
```

# 10. Error Contract

Now consider:

```http
GET /api/v1/todos/999
```

The todo doesn't exist.

Return:

```http
404 Not Found
```

with:

```json
{
  "success": false,
  "code": "TODO_NOT_FOUND",
  "message": "Todo not found",
  "requestId": "req_abc123"
}
```

The frontend now knows:

```text
success === false
       ↓
error response
       ↓
code
       ↓
message
       ↓
requestId
```

---

# 11. Why Have an Error Code?

You might ask:

> Why not let the frontend check the message?

Bad:

```js
if (message === "Todo not found") {
    ...
}
```

Messages are for humans.

Codes are for machines.

Better:

```js
if (error.code === "TODO_NOT_FOUND") {
    ...
}
```

Because you can change:

```text
"Todo not found"
```

to:

```text
"The requested todo could not be found"
```

without breaking the frontend.

The machine-readable contract remains:

```text
TODO_NOT_FOUND
```

---

# 12. Message vs Code

This distinction is worth remembering:

```text
code
 ↓
machine-readable

message
 ↓
human-readable
```

Example:

```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "Email or password is incorrect"
}
```

The frontend can use:

```js
error.code
```

while the user sees:

```text
Email or password is incorrect
```

---

# 13. HTTP Status vs Error Code

Now we have two levels:

```text
HTTP status
+
application error code
```

Example:

```http
401 Unauthorized
```

```json
{
  "success": false,
  "code": "INVALID_CREDENTIALS",
  "message": "Email or password is incorrect"
}
```

The HTTP status communicates the broad HTTP meaning.

The application code communicates the specific application condition.

Think:

```text
401
 ↓
HTTP-level meaning

INVALID_CREDENTIALS
 ↓
application-level meaning
```

---

# 14. Why Not Put Everything in HTTP Status?

HTTP has a limited set of standardized semantics.

Suppose your application has:

```text
INVALID_CREDENTIALS
ACCOUNT_LOCKED
EMAIL_NOT_VERIFIED
TOKEN_EXPIRED
```

You don't want to invent random HTTP status codes for every application condition.

Instead:

```text
401
 ├── INVALID_CREDENTIALS
 └── TOKEN_EXPIRED
```

and perhaps:

```text
403
 └── ACCOUNT_DISABLED
```

depending on the semantics of your authentication design.

This gives you a clean hierarchy.

---

# 15. Validation Error Contract

Validation deserves special treatment.

Request:

```json
{
  "email": "hello",
  "password": ""
}
```

Response:

```http
400 Bad Request
```

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "Validation failed",
  "errors": [
    {
      "field": "email",
      "message": "Invalid email address"
    },
    {
      "field": "password",
      "message": "Password is required"
    }
  ],
  "requestId": "req_123"
}
```

This is much better than:

```json
{
  "error": "Invalid input"
}
```

because the frontend knows exactly what went wrong.

---

# 16. Why `errors` Should Be Structured

Imagine:

```text
email
password
username
age
```

all fail validation.

The frontend can map:

```js
errors.forEach(...)
```

or build field-level messages.

For example:

```text
email → Invalid email
password → Required
username → Already taken
```

This is especially useful for forms.

---

# 17. Should `errors` Always Exist?

No.

Don't return:

```json
{
  "success": false,
  "code": "TODO_NOT_FOUND",
  "message": "Todo not found",
  "errors": []
}
```

unless your contract explicitly requires it.

If there are no field-level errors, simply omit the property.

This keeps responses meaningful.

---

# 18. Optional Fields Should Have Meaning

Good contract:

```json
{
  "success": false,
  "code": "TODO_NOT_FOUND",
  "message": "Todo not found",
  "requestId": "req_123"
}
```

Validation:

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "Validation failed",
  "errors": [...],
  "requestId": "req_123"
}
```

The presence of:

```text
errors
```

means:

> There are structured field-level validation errors.

That's useful semantic design.

---

# 19. Empty Data

Another contract decision.

Suppose:

```http
GET /api/v1/todos
```

has no todos.

I recommend:

```json
{
  "success": true,
  "data": []
}
```

not:

```json
{
  "success": true,
  "data": null
}
```

because a collection endpoint represents a collection.

No records means:

```text
[]
```

not:

```text
null
```

This reduces frontend checks.

---

# 20. Null vs Missing vs Empty Array

These are not automatically equivalent.

### Missing

```json
{}
```

means:

> property isn't present.

### Null

```json
{
  "data": null
}
```

means:

> property exists but has no value.

### Empty array

```json
{
  "data": []
}
```

means:

> collection exists but contains zero elements.

A good API contract should use these intentionally.

---

# 21. Don't Change Types Randomly

Bad API:

```text
Response 1:
data = object

Response 2:
data = array

Response 3:
data = null
```

for the same endpoint depending on conditions.

Clients become complicated.

Instead, define the type.

For:

```text
GET /todos
```

always:

```text
data → array
```

For:

```text
GET /todos/:id
```

always:

```text
data → object
```

except when there is an error.

---

# 22. Consistency Across Endpoints

Suppose you have:

```text
GET /users
GET /todos
GET /posts
GET /comments
```

Don't make each controller invent its own format.

Instead:

```text
All successful endpoints
        ↓
{
  success: true,
  data: ...
}
```

and:

```text
All errors
        ↓
{
  success: false,
  code: ...,
  message: ...,
  requestId: ...
}
```

This is the essence of consistent API design.

---

# 23. Centralize Response Creation

Don't repeatedly write:

```js
res.status(200).json({
    success: true,
    data: todo
});
```

in 100 places if your architecture can centralize this.

You might create a helper:

```js
const successResponse = ({
    data,
    message
}) => ({
    success: true,
    ...(message ? { message } : {}),
    data
});
```

Then:

```js
res.status(200).json(
    successResponse({
        data: todo
    })
);
```

This reduces accidental inconsistency.

---

# 24. Error Response Helper

Similarly:

```js
const errorResponse = ({
    code,
    message,
    requestId,
    errors
}) => ({
    success: false,
    code,
    message,
    ...(errors ? { errors } : {}),
    requestId
});
```

Then:

```js
res.status(400).json(
    errorResponse({
        code: "VALIDATION_ERROR",
        message: "Validation failed",
        errors,
        requestId: req.requestId
    })
);
```

Now the contract is centralized.

---

# 25. But Don't Over-Abstraction

Be careful.

Don't create:

```text
response/
  universal/
    generic/
      response/
        builder/
          factory/
            ...
```

just to return:

```json
{
  "success": true
}
```

😂

Your abstraction should solve a real problem.

A simple helper is often enough.

---

# 26. Controller Responsibility

Your controller should generally decide:

```text
HTTP status
response shape
```

while the service handles:

```text
business logic
```

For example:

```js
const todo = await todoService.getTodo(id);

return res.status(200).json(
    successResponse({
        data: todo
    })
);
```

The service shouldn't normally know about:

```text
res.status()
res.json()
HTTP headers
```

This separation keeps your architecture clean.

---

# 27. Service Should Not Return HTTP Responses

Avoid:

```js
async function getTodo(id) {
    if (!todo) {
        return {
            status: 404,
            body: {
                success: false
            }
        };
    }
}
```

Now your service is coupled to HTTP.

Better:

```js
async function getTodo(id) {
    const todo = await repository.findById(id);

    if (!todo) {
        throw new TodoNotFoundError();
    }

    return todo;
}
```

Controller/error middleware translates that into HTTP.

This connects directly with the service architecture from your earlier phases.

---

# 28. Repository Should Know Even Less

Repository:

```js
async function findById(id) {
    return Todo.findById(id);
}
```

It shouldn't return:

```js
{
    success: false,
    statusCode: 404
}
```

because that's HTTP/application response logic.

Think:

```text
Repository
    ↓
data access

Service
    ↓
business rules

Controller
    ↓
HTTP response

Error middleware
    ↓
error → HTTP contract
```

This separation is very important.

---

# 29. API Contract and Versioning

Now we reach an important production question.

Suppose your API currently returns:

```json
{
  "success": true,
  "data": {
    "name": "Rahul"
  }
}
```

Later you want:

```json
{
  "success": true,
  "data": {
    "fullName": "Rahul Kumar"
  }
}
```

If you simply change it, old clients may break.

This is why API contracts connect to:

```text
versioning
backward compatibility
deprecation
```

We'll study these later in Phase 16.

---

# 30. Backward Compatibility

A good API tries to avoid unexpectedly breaking clients.

For example, adding:

```json
{
  "success": true,
  "data": {...},
  "metadata": {...}
}
```

is often safer than removing an existing field.

Generally:

```text
Adding optional fields
        ↓
often backward compatible

Removing fields
        ↓
potentially breaking

Changing field type
        ↓
potentially breaking

Changing meaning
        ↓
potentially breaking
```

This is a key API-design mindset.

---

# 31. Contract Evolution

Imagine version 1:

```json
{
  "id": "123",
  "name": "Rahul"
}
```

You want:

```json
{
  "id": "123",
  "fullName": "Rahul Kumar"
}
```

Instead of suddenly removing `name`, you might temporarily support:

```json
{
  "id": "123",
  "name": "Rahul",
  "fullName": "Rahul Kumar"
}
```

Then:

```text
old clients → continue working
new clients → use fullName
```

Eventually:

```text
deprecate name
```

and later remove it in a planned breaking release/version.

---

# 32. What Does "Stable Contract" Mean?

It does **not** mean:

> The API can never change.

It means:

> Changes should be deliberate, predictable, documented, and preferably backward compatible.

That's much more realistic.

# 34. TypeScript and API Contracts

If you're using TypeScript on the frontend/backend, you can define types such as:

```ts
type SuccessResponse<T> = {
    success: true;
    data: T;
};
```

and:

```ts
type ErrorResponse = {
    success: false;
    code: string;
    message: string;
    requestId: string;
    errors?: ValidationError[];
};
```

Then:

```ts
type TodoResponse =
    SuccessResponse<Todo>;
```

This can make contracts easier to reason about.

Even if your current starter project uses JavaScript, understanding this is valuable.

---

# 35. Generic Response Types

Conceptually:

```ts
SuccessResponse<T>
```

means:

```text
T = Todo
```

then:

```text
SuccessResponse<Todo>
```

or:

```text
T = Todo[]
```

then:

```text
SuccessResponse<Todo[]>
```

The envelope stays the same.

Only the data changes.

This is one of the reasons generic response contracts are powerful.

# 36. API Contract Testing

Another production-level idea:

> Don't just document the contract. Test it.

Suppose you expect:

```json
{
  "success": true,
  "data": {}
}
```

Your tests should verify that.

For example:

```text
GET /todos/:id
        ↓
200
        ↓
success === true
        ↓
data exists
```

And:

```text
GET /todos/unknown
        ↓
404
        ↓
success === false
        ↓
code === TODO_NOT_FOUND
        ↓
requestId exists
```

This prevents accidental contract changes.

# 37. Contract Tests Protect the Frontend

Imagine someone changes:

```json
"data"
```

to:

```json
"result"
```

and everything still works on the backend.

But the frontend breaks.

Contract tests can catch:

```text
expected:
data

received:
result
```

before deployment.

This becomes increasingly important as teams grow.

# 40. One Important Design Decision

You may notice that our success response has:

```json
{
  "success": true,
  "data": {}
}
```

while the error response has:

```json
{
  "success": false,
  "code": "...",
  "message": "...",
  "requestId": "..."
}
```

You might ask:

> "Why not always have `data`?"

You could.

For example:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "TODO_NOT_FOUND"
  }
}
```

That's also possible.

There is no universal perfect response envelope.

The important thing is:

> **Choose a coherent convention and use it consistently.**

---

# 41. Don't Become Dogmatic

This is important for interviews.

Don't say:

> "Every professional API must use exactly this response format."

That's false.

Instead say:

> "I'd establish a consistent response contract appropriate for the project. For example, I might use a success envelope containing `data` and a standardized error envelope containing a machine-readable error code, human-readable message, and request ID."

That's a much stronger engineering answer.

---

# 42. Interview Question

### "How would you design a consistent API response format?"

A strong answer:

> "I'd define a standard success and error envelope and enforce it across controllers and error middleware. Successful responses would contain a predictable `data` field, while errors would include an HTTP status, machine-readable error code, human-readable message, and request ID. Validation errors would additionally contain structured field-level errors. I'd also document and test the contract so changes don't accidentally break clients."

That's **interview gold**.

---

# 43. Interview Question

### "Why use an error code instead of relying on the error message?"

Answer:

> "Messages are intended for humans and may change. Error codes provide stable machine-readable semantics that frontend clients can safely use for conditional behavior."

---

# 44. Interview Question

### "Should services return HTTP responses?"

Answer:

> "Generally no. Services should contain business logic and return domain results or throw domain/application errors. Controllers and error middleware should translate those results into HTTP responses. This keeps the service layer independent of the HTTP transport."

Excellent.

---

# 45. Interview Question

### "What happens if your API contract changes?"

Answer:

> "I would first determine whether the change is backward compatible. Adding optional fields is usually safer than removing or changing existing fields. For breaking changes, I'd use a planned versioning or deprecation strategy and communicate the migration path to clients."

---

# 46. Interview Question

### "How do you prevent accidental API contract changes?"

Answer:

> "I'd use automated integration or contract tests that verify status codes, response schemas, error formats, and important fields. For larger systems, I'd also maintain an OpenAPI specification and use it as part of the development and testing process."

---

# 🧠 Remember These 8 Things

If you revise this lesson before an interview, remember:

1. **API contract = agreement between client and server.**
    
2. **Consistency is more important than one magical response format.**
    
3. **Success responses should have a predictable structure.**
    
4. **Errors should have stable machine-readable codes.**
    
5. **Messages are for humans; codes are for machines.**
    
6. **Validation errors should identify individual fields.**
    
7. **Request IDs connect client errors to server logs.**
    
8. **Contracts must be documented, tested, and evolved carefully.**
