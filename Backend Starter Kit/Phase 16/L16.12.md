# Phase 16 — API Response Architecture

## Lesson 16.12 — Filtering, Sorting & Search Contracts

This is another **gold-level backend interview lesson**.

In the previous lesson, we learned:

```text
Pagination
    ↓
Which portion of the collection?
```

Now we add:

```text
Filtering
    ↓
Which records?

Sorting
    ↓
In what order?

Search
    ↓
Which records match this text/query?
```

A production collection API often combines all of them:

```http
GET /api/v1/todos
    ?status=completed
    &priority=high
    &sort=createdAt
    &order=desc
    &limit=20
    &page=1
```

The goal of this lesson is not just learning how to read query parameters.

The real goal is:

> **Design a predictable, safe, scalable query contract without turning your controller into a giant `if/else` block.**

---

# 1. The Collection API Problem

Imagine your Todo API.

A frontend may need:

```text
all todos
completed todos
high-priority todos
recent todos
oldest todos
todos containing "backend"
```

A naive developer might create separate endpoints:

```http
GET /todos
GET /completed-todos
GET /high-priority-todos
GET /recent-todos
GET /search-todos
```

This quickly becomes messy.

A better approach is often one collection endpoint:

```http
GET /api/v1/todos
```

with query parameters:

```http
?status=completed
&priority=high
&sort=createdAt
&order=desc
&search=backend
&page=1
&limit=20
```

Now the endpoint has a **query contract**.

---

# 2. Query Parameters Are Part of Your API Contract

This connects directly to Lesson 16.10.

If your API supports:

```http
GET /todos?status=completed&limit=20
```

then you should define:

```text
status
    allowed values?

priority
    allowed values?

sort
    allowed fields?

order
    allowed directions?

search
    what does it search?

page
    minimum?

limit
    maximum?
```

Don't leave these behaviors undefined.

---

# 3. A Good Query Contract

For example:

```text
GET /api/v1/todos
```

Supported parameters:

|Parameter|Type|Example|
|---|---|---|
|`status`|enum|`completed`|
|`priority`|enum|`high`|
|`search`|string|`backend`|
|`sort`|enum|`createdAt`|
|`order`|enum|`desc`|
|`page`|integer|`1`|
|`limit`|integer|`20`|

The important word is:

> **enum**

The client should not be allowed to send arbitrary values for everything.

---

# 4. Filtering

Filtering means:

> Return only records satisfying specific conditions.

Example:

```http
GET /api/v1/todos?status=completed
```

Conceptually:

```js
{
    status: "completed"
}
```

MongoDB might execute:

```js
Todo.find({
    status: "completed"
});
```

Simple.

---

# 5. Multiple Filters

Suppose:

```http
GET /api/v1/todos
    ?status=completed
    &priority=high
```

The intended meaning is usually:

```text
status = completed
AND
priority = high
```

MongoDB:

```js
Todo.find({
    status: "completed",
    priority: "high"
});
```

Only documents satisfying both conditions are returned.

---

# 6. Filtering Is Not Search

This distinction is important.

Filtering:

```http
?status=completed
```

asks:

> Does this structured field equal a specific value?

Search:

```http
?search=backend
```

asks:

> Does this text match my search criteria?

These are different operations.

---

# 7. Structured Filtering

Examples:

```http
?status=completed
?priority=high
?userId=123
?category=backend
```

These generally map to structured database fields.

For example:

```js
{
    status: "completed",
    priority: "high"
}
```

---

# 8. Search

Suppose your Todo has:

```json
{
  "title": "Learn Node.js backend architecture",
  "description": "Build production APIs"
}
```

The user searches:

```http
GET /todos?search=backend
```

Now your backend needs to decide:

```text
Search which fields?
title?
description?
both?
case-sensitive?
partial match?
exact match?
full-text?
```

This is why **search must be part of the contract**.

---

# 9. Never Let the Search Behavior Be Ambiguous

Bad documentation:

```text
search
    Search todos
```

Better:

```text
search
    Searches title and description using case-insensitive
    partial matching.
```

Even better, if using a dedicated search engine:

```text
search
    Full-text search over title and description.
```

The client should know what to expect.

---

# 10. Sorting

Now:

```http
GET /api/v1/todos?sort=createdAt&order=desc
```

means:

```text
sort by createdAt
descending
```

MongoDB:

```js
Todo.find(...)
    .sort({
        createdAt: -1
    });
```

Ascending:

```text
asc → 1
```

Descending:

```text
desc → -1
```

---

# 11. Never Trust Arbitrary Sort Fields

This is an important production rule.

Don't blindly do something like:

```js
const sortField = req.query.sort;

Todo.find().sort({
    [sortField]: -1
});
```

Why?

Because now the client controls the database query structure.

Even if this isn't automatically a security vulnerability in every database/driver configuration, it creates a serious **query-control and performance problem**.

The client might request:

```text
sort=someHugeOrUnindexedField
```

or:

```text
sort=internalField
```

or something your API never intended to expose.

---

# 12. Whitelist Sort Fields

Instead:

```js
const allowedSortFields = {
    createdAt: "createdAt",
    updatedAt: "updatedAt",
    title: "title"
};
```

Then:

```js
const sortField =
    allowedSortFields[req.query.sort]
    ?? "createdAt";
```

Now:

```text
sort=createdAt
    ↓
allowed

sort=title
    ↓
allowed

sort=passwordHash
    ↓
not allowed
```

This is called **allowlisting**.

---

# 13. Allowlisting Is Better Than Blocklisting

Blocklist:

```text
Allow everything
except passwordHash
except internalNotes
except secretField
...
```

This is dangerous because new fields can be added later.

Allowlist:

```text
Only these fields are allowed:
createdAt
updatedAt
title
```

Much safer.

Think:

> **Only expose what the API intentionally supports.**

---

# 14. Whitelist Filter Values Too

Suppose:

```http
GET /todos?status=anything
```

Don't blindly accept it.

If your valid statuses are:

```text
pending
in_progress
completed
cancelled
```

define that explicitly.

For example:

```js
const allowedStatuses = [
    "pending",
    "in_progress",
    "completed",
    "cancelled"
];
```

Then validate:

```js
if (
    status &&
    !allowedStatuses.includes(status)
) {
    throw new ValidationError(
        "Invalid status"
    );
}
```

Now the API contract is predictable.

---

# 15. Why Not Silently Ignore Invalid Filters?

Suppose:

```http
GET /todos?status=banana
```

If you silently ignore it and return all todos, the frontend may think:

```text
"banana" is a valid filter
```

but receive unrelated data.

That's confusing.

Usually it's better to clearly reject invalid query values:

```http
400 Bad Request
```

with:

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "Invalid query parameters",
  "errors": [
    {
      "field": "status",
      "message": "Invalid status"
    }
  ]
}
```

This connects directly to the response contract from Lesson 16.10.

---

# 16. Boolean Filters

Suppose:

```http
GET /todos?completed=true
```

Remember:

> Query parameters arrive as strings.

So:

```js
req.query.completed
```

is:

```text
"true"
```

not:

```js
true
```

Don't do:

```js
if (req.query.completed) {
    // ...
}
```

because:

```text
"false"
```

is still a truthy JavaScript string.

---

# 17. The `"false"` Trap

This is a classic interview/production bug.

```js
const completed = req.query.completed;

if (completed) {
    // runs even when completed === "false"
}
```

Because:

```js
Boolean("false")
```

is:

```text
true
```

You need explicit parsing:

```js
function parseBoolean(value) {
    if (value === "true") return true;
    if (value === "false") return false;

    return undefined;
}
```

Now:

```text
"true"  → true
"false" → false
missing → undefined
```

This is a small but important detail.

---

# 18. Numeric Filters

Suppose:

```http
GET /todos?priority=5
```

If `priority` is numeric:

```js
const priority = Number(req.query.priority);
```

But you should validate:

```text
Is it actually a number?
Is it within an allowed range?
Is decimal allowed?
Is negative allowed?
```

For example:

```text
priority = 5   ✅
priority = -20 ❌
priority = abc ❌
```

Again:

> Query parameters are untrusted input.

---

# 19. Date Filters

Real APIs often support:

```http
GET /todos?createdAfter=2026-08-01
```

or:

```http
GET /todos?from=2026-08-01&to=2026-08-26
```

You need to define:

```text
What timezone?
Is the date inclusive?
What date format?
Can from > to?
```

For example:

```text
from = 2026-08-01T00:00:00Z
to   = 2026-08-27T00:00:00Z
```

can represent a half-open interval:

```text
[from, to)
```

This avoids many end-of-day problems.

---

# 20. Query Parsing Should Be Its Own Responsibility

Don't let your controller become:

```js
if (req.query.status) ...
if (req.query.priority) ...
if (req.query.search) ...
if (req.query.sort) ...
if (req.query.order) ...
if (req.query.page) ...
if (req.query.limit) ...
if (req.query.from) ...
if (req.query.to) ...
```

and then 300 lines later:

```js
Todo.find(...)
```

😂

That's exactly the kind of controller we want to avoid.

---

# 21. Better Architecture

Think:

```text
HTTP query
    ↓
Query validation/parsing
    ↓
Normalized query object
    ↓
Service
    ↓
Repository
    ↓
Database
```

For example:

```js
const query = parseTodoQuery(req.query);
```

returns:

```js
{
    filters: {
        status: "completed",
        priority: "high"
    },

    search: "backend",

    sort: {
        field: "createdAt",
        direction: "desc"
    },

    pagination: {
        page: 1,
        limit: 20
    }
}
```

Now the rest of your application doesn't need to understand raw HTTP query strings.

---

# 22. Raw Query vs Normalized Query

Raw:

```js
req.query
```

might be:

```js
{
    status: "completed",
    priority: "high",
    sort: "createdAt",
    order: "desc",
    page: "1",
    limit: "20"
}
```

Normalized:

```js
{
    filters: {
        status: "completed",
        priority: "high"
    },
    sort: {
        field: "createdAt",
        direction: "desc"
    },
    pagination: {
        page: 1,
        limit: 20
    }
}
```

Notice:

```text
"1"
```

became:

```text
1
```

and:

```text
HTTP-specific query
```

became:

```text
application-level query
```

That's a cleaner architecture.

---

# 23. Example Query Parser

Conceptually:

```js
function parseTodoQuery(query) {
    const page = parsePage(query.page);
    const limit = parseLimit(query.limit);

    const status = parseStatus(query.status);
    const priority = parsePriority(query.priority);

    const sort = parseSort(
        query.sort,
        query.order
    );

    return {
        filters: {
            ...(status && { status }),
            ...(priority && { priority })
        },

        search: query.search?.trim(),

        sort,

        pagination: {
            page,
            limit
        }
    };
}
```

The exact implementation can evolve.

The architecture is what matters.

---

# 24. Repository Should Receive Structured Query

Instead of:

```js
todoRepository.findTodos(
    req.query
);
```

prefer:

```js
todoRepository.findMany({
    filters,
    search,
    sort,
    pagination
});
```

The repository receives a known structure.

That makes it easier to test.

---

# 25. But Don't Leak MongoDB Into the Service

Avoid:

```js
todoService.findTodos({
    $regex: ...
});
```

because now your service knows MongoDB syntax.

Prefer:

```js
todoService.findTodos({
    search: "backend",
    filters: {
        status: "completed"
    }
});
```

Then repository infrastructure translates the application query into MongoDB operations.

This fits nicely with the **Repository Pattern** you studied in Phase 13.

---

# 26. Query Object Architecture

Think:

```text
HTTP
 │
 │ ?status=completed&sort=createdAt
 ▼
Controller
 │
 ▼
Query Parser
 │
 ▼
Application Query
 │
 ├── filters
 ├── search
 ├── sort
 └── pagination
 │
 ▼
Service
 │
 ▼
Repository
 │
 ▼
MongoDB
```

This is a very scalable pattern.

---

# 27. Search Using Regex

A beginner MongoDB implementation might use:

```js
{
    title: {
        $regex: search,
        $options: "i"
    }
}
```

This can be useful for small/simple applications.

But don't immediately assume:

> "Regex search is production-grade search."

It depends on:

```text
dataset size
query pattern
indexes
prefix vs substring
performance requirements
```

---

# 28. Prefix vs Contains Search

These are very different.

### Prefix:

```text
"node"
```

matches:

```text
Node.js
Node backend
Node architecture
```

### Contains:

```text
"node"
```

might match:

```text
Learn Node.js
Backend with Node
Understanding Node
```

A substring regex can be much harder for a database to optimize than a prefix query.

So search behavior must be deliberate.

---

# 29. Search vs Full-Text Search

For serious search requirements, you might use:

```text
MongoDB text search
Atlas Search
Elasticsearch/OpenSearch
dedicated search engine
```

depending on the system.

The key architectural lesson:

> **Search is a separate concern from ordinary structured filtering.**

Don't build an enormous regex query and call it a search system.

---

# 30. Search Contract Example

You could define:

```text
search
- Searches title and description
- Case-insensitive
- Minimum length: 2
- Maximum length: 100
```

Now:

```http
GET /todos?search=backend
```

has predictable semantics.

You could later replace the implementation with a search engine without changing the public contract.

That's excellent abstraction.

---

# 31. Don't Expose Database Query Syntax

This is a major API-design rule.

Don't design your API like:

```http
GET /todos?filter[status][$eq]=completed
```

unless there is a strong reason.

And definitely don't expose arbitrary MongoDB operators such as:

```text
$where
$regex
$ne
$gt
```

directly to clients.

Why?

Because now the client effectively controls your database query language.

Instead:

```http
GET /todos?status=completed
```

is much cleaner.

Your API owns the translation.

---

# 32. API Contract vs Database Contract

Frontend knows:

```text
status=completed
```

Backend translates:

```text
status
   ↓
MongoDB field
```

The frontend should not need to know:

```text
MongoDB
SQL
PostgreSQL
Elasticsearch
```

That's one of the benefits of a clean API contract.

---

# 33. Prevent Query Explosion

Imagine supporting:

```text
status
priority
category
owner
createdAfter
createdBefore
updatedAfter
updatedBefore
completed
archived
search
sort
order
page
limit
```

Now combinations explode.

You could have thousands of query combinations.

Don't manually write:

```js
if (status && priority && category) ...
if (status && priority) ...
if (status && category) ...
```

Instead, construct a structured query dynamically from validated pieces.

---

# 34. Query Builder

A repository might internally build:

```js
const filter = {};

if (query.filters.status) {
    filter.status = query.filters.status;
}

if (query.filters.priority) {
    filter.priority = query.filters.priority;
}
```

This is okay.

The important difference is:

```text
validated application query
          ↓
database filter
```

rather than:

```text
raw HTTP input
          ↓
database filter
```

---

# 35. Filtering + Pagination

Suppose:

```http
GET /todos
    ?status=completed
    &page=2
    &limit=20
```

The logical order is:

```text
filter
    ↓
sort
    ↓
paginate
```

Conceptually:

```text
all todos
   ↓
completed only
   ↓
sort
   ↓
page 2
   ↓
20 records
```

You don't want:

```text
page first
   ↓
then filter
```

because that changes the meaning.

---

# 36. Filtering + Cursor Pagination

Same principle:

```text
filter
   ↓
stable sort
   ↓
cursor position
   ↓
limit
```

The cursor belongs to a particular ordered/filtering context.

This leads to an important issue.

---

# 37. Cursor + Filter Changes

Suppose the client gets:

```text
cursor=abc123
```

for:

```text
status=completed
```

Then sends:

```http
GET /todos?status=pending&cursor=abc123
```

That cursor may no longer make sense.

A robust cursor implementation should either:

```text
reject the cursor
```

or:

```text
ensure cursor context matches the query
```

This is one reason production cursors may contain/safeguard information about the query context.

---

# 38. Cursor Context

A cursor might conceptually represent:

```json
{
  "position": {
    "createdAt": "...",
    "id": "..."
  },
  "filterHash": "abc123"
}
```

Then the server can verify:

```text
cursor filter
      =
current request filter
```

If not:

```text
400 INVALID_CURSOR
```

You don't always need this complexity for a small app.

But knowing the problem is valuable at interview level.

---

# 39. Sorting + Cursor

Suppose:

```http
GET /todos?sort=createdAt&order=desc
```

returns:

```text
cursor=abc
```

Then the next request changes:

```http
GET /todos?sort=title&order=asc&cursor=abc
```

The cursor represents the old ordering.

Therefore:

> **A cursor is tied to the ordering that produced it.**

A robust API should not blindly accept mismatched cursors.

---

# 40. Sort Defaults

Don't require the frontend to always specify:

```http
sort=createdAt&order=desc
```

You can define a default:

```text
sort = createdAt
order = desc
```

Then:

```http
GET /todos
```

has deterministic behavior.

That's important.

Never leave default ordering ambiguous.

---

# 41. Why Default Ordering Matters

Without a stable default:

```http
GET /todos
```

could potentially return records in an order the client shouldn't rely on.

With:

```text
createdAt DESC
_id DESC
```

you have an explicit contract.

This also helps pagination.

---

# 42. Secondary Sort Key

Suppose:

```text
createdAt
```

is not unique.

Use:

```text
createdAt DESC
_id DESC
```

Think:

```text
Primary ordering:
createdAt

Tie-breaker:
_id
```

This gives you deterministic results.

---

# 43. Sorting Is a Product Decision Too

Don't expose every sortable field just because the database supports it.

Maybe your API allows:

```text
createdAt
updatedAt
title
priority
```

but not:

```text
internalScore
passwordHash
securityToken
```

The API contract defines what the product supports.

---

# 44. Filtering and Authorization

This is a critical security point.

Suppose:

```http
GET /todos?userId=999
```

Your user is user `123`.

Don't assume:

```text
userId=999
```

means the requester is allowed to see user 999's todos.

Authorization must still apply.

For example, your service/repository query might enforce:

```text
currentUserId = 123
AND
requested filters
```

So:

```text
authorization scope
       +
user filters
       +
other filters
```

This prevents data leakage.

---

# 45. Never Let Filters Bypass Authorization

Bad:

```js
Todo.find({
    userId: req.query.userId
});
```

if the endpoint is supposed to show only the current user's todos.

A malicious user could simply request:

```http
?userId=another-user
```

Instead, derive security-sensitive constraints from authenticated context:

```js
Todo.find({
    userId: req.user.id,
    status: requestedStatus
});
```

This distinction is extremely important.

---

# 46. Filtering and Multi-Tenant Systems

This becomes even more important in multi-tenant applications.

Suppose:

```text
tenant A
tenant B
tenant C
```

A query might include:

```text
tenantId
```

But the client should not normally be trusted to choose:

```http
?tenantId=B
```

The backend should derive tenant scope from the authenticated identity/session/token.

Conceptually:

```text
authenticated tenant
        ↓
authorization scope
        +
user filters
        ↓
database query
```

This prevents cross-tenant data leakage.

---

# 47. Filtering and Database Indexes

Suppose your API frequently uses:

```http
?status=completed
```

and:

```http
?status=completed&sort=createdAt
```

Your database indexing strategy should consider that workload.

For example:

```js
TodoSchema.index({
    status: 1,
    createdAt: -1,
    _id: -1
});
```

Again, don't memorize this exact index.

Understand the principle:

> **Indexes should support your real filter + sort + pagination query patterns.**

---

# 48. Don't Add Indexes Randomly

More indexes are not always better.

Indexes:

```text
speed up some reads
```

but also:

```text
consume storage
increase write cost
increase maintenance
```

So index design is a tradeoff.

A production engineer asks:

```text
What queries are common?
How selective are the filters?
What sort is used?
How large is the collection?
What is the read/write ratio?
```

---

# 49. Query Performance

When designing filtering/sorting/search APIs, think:

```text
Correctness
     +
Security
     +
Performance
     +
Usability
```

A query that returns the correct result but takes:

```text
8 seconds
```

is not a good production API.

---

# 50. Avoid N+1 Queries

Suppose:

```http
GET /todos
```

returns 20 todos.

Then for each todo, you separately query its user:

```text
Todo 1 → User query
Todo 2 → User query
Todo 3 → User query
...
Todo 20 → User query
```

You may have:

```text
1 + 20 = 21 queries
```

This is the **N+1 query problem**.

When filtering/sorting endpoints grow more complex, watch for this.

The exact solution depends on your architecture:

```text
populate
aggregation
joins
batch loading
projection
```

We'll cover query optimization more deeply later.

---

# 51. Projection

Suppose the Todo document contains:

```text
title
description
internalNotes
auditData
largeMetadata
```

But the collection endpoint only needs:

```text
id
title
status
createdAt
```

Don't necessarily return everything.

Use projection/select fields.

MongoDB conceptually:

```js
Todo.find(filter)
    .select({
        title: 1,
        status: 1,
        createdAt: 1
    });
```

This can reduce:

```text
database data
serialization cost
network payload
```

It also helps avoid accidentally exposing sensitive fields.

---

# 52. Filtering + Projection

A good collection API might therefore perform:

```text
Authorization
       ↓
Filtering
       ↓
Sorting
       ↓
Pagination
       ↓
Projection
       ↓
Response mapping
```

Though the actual database execution order can differ internally.

The conceptual API pipeline is useful.

---

# 53. Query Contract Example

Let's design:

```http
GET /api/v1/todos
```

Supported query:

```http
?status=completed
&priority=high
&search=node
&sort=createdAt
&order=desc
&page=1
&limit=20
```

Contract:

```text
status:
    pending | in_progress | completed | cancelled

priority:
    low | medium | high

search:
    string
    max 100 characters

sort:
    createdAt | updatedAt | title

order:
    asc | desc

page:
    integer >= 1

limit:
    integer 1-100
```

That's already a professional API contract.

---

# 54. Response

```json
{
  "success": true,
  "data": [
    {
      "id": "123",
      "title": "Learn Node.js",
      "status": "completed",
      "priority": "high",

    }
  ],
  "pagination": {
    "page": 1,

  }
}
```

Notice something important:

The response doesn't expose:

```text
MongoDB document
```

It exposes:

```text
API representation
```

That's another important architectural boundary.

# 55. Query DTO

At the service boundary, we can think in terms of a query DTO:

```js
{
    filters: {
        status: "completed",
        priority: "high"
    },

    search: {
        term: "node"
    },

    sort: {
        field: "createdAt",
        direction: "desc"
    },

    pagination: {
        page: 1,
        limit: 20
    }
}
```

This is much cleaner than passing:

```js
req.query
```

through the entire application.

# 56. Controller

Conceptually:

```js
async function listTodos(req, res) {
    const query = parseTodoQuery(req.query);

    const result = await todoService.listTodos({
        userId: req.user.id,
        query
    });

    return res.status(200).json(
        successResponse(result)
    );
}
```

Notice the controller isn't doing database logic.

It:

```text
receives HTTP
      ↓
parses/validates query
      ↓
calls service
      ↓
returns response
```

That's exactly what we want.

---

# 57. Service

Conceptually:

```js
async function listTodos({
    userId,
    query
}) {
    return todoRepository.findMany({
        ownerId: userId,
        ...query
    });
}
```

The service can enforce business rules.

For example:

```text
only active todos
certain user permissions
tenant scope
business-specific filters
```

---

# 58. Repository

The repository translates:

```js
{
    filters,
    search,
    sort,
    pagination
}
```

into MongoDB operations.

Conceptually:

```js
Todo.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit);
```

The MongoDB details remain in the repository.

# 60. Common Beginner Mistake #1

Putting everything in the controller:

```js
async function getTodos(req, res) {
    // validate status
    // validate priority
    // validate sort
    // parse dates
    // build MongoDB filter
    // build regex
    // build sort
    // calculate pagination
    // query database
    // count database
    // map response
    // handle errors
}
```

This becomes difficult to:

```text
test
maintain
reuse
debug
extend
```

---

# 61. Common Mistake #2

Passing raw query parameters everywhere:

```js
service.getTodos(req.query);
```

then:

```js
repository.getTodos(req.query);
```

Now your repository knows:

```text
HTTP parameter names
```

and potentially accepts unvalidated input.

Better:

```text
HTTP query
   ↓
validated application query
   ↓
service
   ↓
repository
```

---

# 62. Common Mistake #3

Allowing arbitrary sort:

```js
.sort({
    [req.query.sort]: req.query.order
});
```

Use:

```text
allowlist
```

instead.

---

# 63. Common Mistake #4

Building giant regex searches for everything.

```text
search everything
using regex
across millions of records
```

This can become extremely slow.

For serious search:

```text
database-native search
or
dedicated search engine
```

may be more appropriate.

---

# 64. Common Mistake #5

Forgetting Authorization

A developer implements:

```http
GET /todos?userId=123
```

but doesn't enforce:

```text
current user
```

Now users can query other users' records.

Never treat filtering as authorization.

They are separate concerns.

---

# 65. Common Mistake #6

No Stable Default Sort

If:

```http
GET /todos
```

doesn't have a deterministic ordering, pagination can behave unpredictably.

Define:

```text
createdAt DESC
_id DESC
```

or another appropriate stable order.

---

# 66. Common Mistake #7

No Maximum Limit

This:

```http
GET /todos?limit=1000000
```

shouldn't be able to casually force a million-record response.

Set a maximum.

For example:

```text
default = 20
maximum = 100
```

---

# 67. Common Mistake #8

Returning the Entire Database Document

Don't automatically return:

```js
res.json(todo);
```

if the document contains:

```text
internal fields
security fields
audit fields
private data
```

Use a response mapper/DTO.

For example:

```js
function toTodoResponse(todo) {
    return {
        id: todo._id,
        title: todo.title,
        status: todo.status,
        priority: todo.priority,
        createdAt: todo.createdAt
    };
}
```

Now your public contract is controlled.

---

# 68. Search Input Length

Don't accept:

```http
?search=<10MB string>
```

Set reasonable limits.

For example:

```text
minimum: 2
maximum: 100
```

depending on your application.

This protects:

```text
memory
CPU
database workload
logs
```

and gives predictable behavior.

---

# 69. Empty Search

What should this mean?

```http
GET /todos?search=
```

You need a defined behavior.

Usually:

```text
empty search
   ↓
treat as no search filter
```

rather than:

```text
database search for empty string
```

Again, contract matters.

---

# 70. Case Sensitivity

Suppose:

```http
?search=Node
```

Should it match:

```text
node
Node
NODE
```

Your API should define this.

For user-facing search, case-insensitive behavior is often expected.

But implementation details matter for performance.

---

# 71. Exact Match vs Partial Match

Suppose:

```http
?status=completed
```

This should probably be:

```text
exact match
```

while:

```http
?search=backend
```

might be:

```text
partial/full-text match
```

Don't apply one search mechanism to every parameter.

Different query types have different semantics.

---

# 72. Filter Operators

Eventually you may need:

```text
price >= 100
createdAt > date
priority != low
```

You could design:

```http
?minPrice=100
&maxPrice=500
```

This is often easier and safer than exposing generic operators.

For example:

```text
minPrice
maxPrice
createdAfter
createdBefore
```

are clearer API contracts than:

```text
price[$gte]=100
price[$lte]=500
```

unless you intentionally want a generic query language.

---

# 73. Why Explicit Parameters Are Often Better

Compare:

```http
?createdAfter=2026-08-01
&createdBefore=2026-08-26
```

with:

```http
?createdAt[$gte]=...
&createdAt[$lte]=...
```

The first is:

```text
easy to document
easy to validate
easy to understand
easy to secure
```

The second is more generic but introduces:

```text
complexity
operator exposure
query-language design
```

For your starter backend, I'd strongly favor explicit parameters.

# 74. Query Contract and Versioning

Suppose version 1 supports:

```text
sort=createdAt
```

Later you want to change:

```text
sort=createdAt
```

to:

```text
sort=created_at
```

That's an API contract change.

Even query parameter names are part of the public API.

So:

```text
URL
query parameters
request body
headers
response
errors
```

all form part of the API contract.

# 76. Interview Question

### "How would you design filtering and sorting for a REST API?"

Strong answer:

> "I'd define a documented query contract with explicitly supported filters and sortable fields. I'd validate and normalize query parameters at the HTTP boundary, use allowlists for enum values and sort fields, and pass a structured query object into the service layer. The repository would translate that object into database-specific filters and sorting. I'd also design indexes around the common filter and sort patterns."

That's a **gold-level answer**.

---

# 77. Interview Question

### "Why shouldn't you directly pass `req.query` to MongoDB?"

Strong answer:

> "Because `req.query` is untrusted HTTP input and contains strings and arbitrary client-controlled fields. Passing it directly can expose unintended query behavior, make validation inconsistent, couple the repository to HTTP semantics, and create security and performance problems. I'd first validate and normalize it into an application-level query object."

Excellent.

---

# 78. Interview Question

### "Why whitelist sortable fields?"

Answer:

> "Because sorting affects database execution and should be limited to fields the API intentionally supports. An allowlist prevents clients from requesting arbitrary internal fields and lets us design indexes for known query patterns."

---

# 79. Interview Question

### "What is the difference between filtering and search?"

Answer:

> "Filtering usually operates on structured fields with well-defined values, such as status or priority. Search is generally text-oriented and may involve partial matching, full-text search, ranking, tokenization, or a dedicated search engine. I would define them separately in the API contract."

---

# 80. Interview Question

### "Where should query parsing happen?"

A strong architecture answer:

> "HTTP-specific parsing and validation should happen near the controller boundary. I'd normalize raw query parameters into a structured application-level query object. The service should work with that normalized representation, while the repository translates it into database-specific query syntax."

Very strong.

# 🧠 Your 12-Point Revision

Remember these:

1. **Query parameters are part of the API contract.**
    
2. Filtering handles structured conditions.
    
3. Search is a separate concern from filtering.
    
4. Sorting should use an **allowlist**.
    
5. Query parameters arrive as strings.
    
6. `"false"` is a truthy JavaScript string — parse booleans explicitly.
    
7. Never pass raw `req.query` directly into database queries.
    
8. Normalize HTTP input into an application-level query object.
    
9. Filtering, sorting, and pagination should be designed together.
    
10. Stable sorting is essential for reliable pagination.
    
11. Authorization must never depend on client-provided filters.
    
12. Database indexes should match your real filter + sort + pagination patterns.
