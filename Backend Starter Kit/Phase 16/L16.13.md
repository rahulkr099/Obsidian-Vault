# Phase 16 — API Architecture & Production Contracts

## Lesson 16.13 — API Versioning & Backward Compatibility

This is an **important gold-level interview topic**.

So far we've built APIs that are:

```text
consistent
validated
secure
paginated
filterable
sortable
```

But there is one problem:

> **What happens when your API needs to change?**

Imagine you have 10,000 frontend users using:

```http
GET /api/v1/users
```

and you suddenly change the response from:

```json
{
  "id": "123",
  "name": "Rahul"
}
```

to:

```json
{
  "userId": "123",
  "fullName": "Rahul"
}
```

Your new frontend may work.

But the old frontend can break immediately.

This is where **API versioning and backward compatibility** become critical.

---

# 1. What Is API Versioning?

API versioning means:

> Providing a controlled way to evolve an API while managing compatibility with existing clients.

For example:

```http
/api/v1/users
```

and later:

```http
/api/v2/users
```

The versions represent different API contracts.

Think:

```text
v1
 │
 ├── old clients
 └── old contract

v2
 │
 ├── new clients
 └── new contract
```

---

# 2. Why Do We Need Versioning?

Because APIs are contracts.

Suppose frontend expects:

```json
{
  "data": {
    "name": "Rahul"
  }
}
```

and backend changes it to:

```json
{
  "data": {
    "fullName": "Rahul"
  }
}
```

Frontend code:

```js
user.name
```

now becomes:

```text
undefined
```

This is a **breaking change**.

Versioning gives you a way to introduce the new contract without immediately destroying the old one.

---

# 3. API Clients Can Be Independent of Your Deployment

This is a very important production concept.

Imagine:

```text
Backend v2 deployed today
```

but:

```text
Mobile App v1
```

cannot be updated immediately.

You cannot assume:

```text
backend changes
      ↓
all clients instantly update
```

Real systems may have:

```text
web frontend
mobile app
third-party integrations
internal services
partner APIs
old applications
```

all using different versions.

Therefore:

> **API evolution must account for independently deployed clients.**

This is one of the most important ideas in backend architecture.

---

# 4. What Is a Breaking Change?

A breaking change is a change that can cause an existing valid client to stop working correctly.

Examples:

### Removing a field

Before:

```json
{
  "id": "123",
  "name": "Rahul"
}
```

After:

```json
{
  "id": "123"
}
```

Breaking.

---

### Renaming a field

```text
name
↓
fullName
```

Breaking.

---

### Changing a field's type

Before:

```json
{
  "age": 25
}
```

After:

```json
{
  "age": "25"
}
```

Potentially breaking.

---

### Changing enum values

Before:

```text
status:
pending
completed
```

After:

```text
status:
pending
done
```

Existing clients expecting:

```text
completed
```

may fail.

---

### Changing endpoint behavior

Suppose:

```http
GET /users
```

previously returned:

```text
all users
```

but now returns:

```text
only active users
```

Even though the endpoint and response shape look the same, its semantics changed.

That can also be breaking.

---

# 5. Non-Breaking Changes

Some changes are generally backward-compatible.

For example, adding an optional response field:

Before:

```json
{
  "id": "123",
  "name": "Rahul"
}
```

After:

```json
{
  "id": "123",
  "name": "Rahul",
  "createdAt": "..."
}
```

Existing clients that ignore unknown fields can continue working.

But notice:

> "Generally" does not mean "always."

Poorly written clients may make assumptions such as:

```js
Object.keys(user).length === 2
```

So compatibility depends partly on client behavior.

---

# 6. Backward Compatibility

Backward compatibility means:

> Existing clients continue to work when the server changes.

Suppose:

```text
Client A
   ↓
API v1
```

You deploy:

```text
Backend release 2
```

Client A should still function correctly.

That's backward compatibility.

---

# 7. Forward Compatibility

Forward compatibility is the reverse direction.

It means a system can tolerate certain changes introduced by newer versions.

For example, a client may safely ignore unknown response fields.

```json
{
  "id": "123",
  "name": "Rahul",
  "createdAt": "...",
  "newField": "..."
}
```

A tolerant client continues working.

This is why API clients should generally avoid assuming:

```text
"These are the only fields that will ever exist."
```

---

# 8. The Most Common Versioning Strategy

A common approach is URL versioning:

```http
/api/v1/users
/api/v2/users
```

For example:

```http
GET /api/v1/orders
```

and:

```http
GET /api/v2/orders
```

This is easy to understand.

---

# 9. Express Route Structure

You might organize your backend like:

```text
src/
├── routes/
│   ├── v1/
│   │   └── user.routes.js
│   │
│   └── v2/
│       └── user.routes.js
│
├── controllers/
│   ├── v1/
│   └── v2/
│
└── services/
```

Then:

```js
app.use(
    "/api/v1/users",
    userV1Routes
);

app.use(
    "/api/v2/users",
    userV2Routes
);
```

But there's an important architectural question:

> Should the entire implementation be duplicated?

Usually:

**No.**

---

# 10. Don't Duplicate Everything

Bad:

```text
v1 service
    ↓
completely separate logic

v2 service
    ↓
completely separate logic
```

Now you have:

```text
same business rules
duplicated twice
```

Eventually:

```text
v1 bug fixed
v2 bug remains
```

or:

```text
v2 behavior changed
v1 behavior accidentally changed
```

Instead, try to isolate the actual contract differences.

---

# 11. Separate API Contract From Business Logic

For example:

```text
v1 response
    ↓
response mapper v1
    ↓
shared service
    ↓
repository
```

and:

```text
v2 response
    ↓
response mapper v2
    ↓
shared service
    ↓
repository
```

Conceptually:

```text
                 ┌── v1 Controller ── v1 Mapper
                 │
Request ─────────┤
                 │
                 └── v2 Controller ── v2 Mapper
                           │
                           ▼
                     Shared Service
                           │
                           ▼
                       Repository
```

This prevents unnecessary duplication.

---

# 12. Example: Field Rename

Suppose v1 returns:

```json
{
  "name": "Rahul"
}
```

v2 wants:

```json
{
  "fullName": "Rahul"
}
```

Internally your domain object can remain:

```js
{
    name: "Rahul"
}
```

Then:

### v1 mapper

```js
function toV1User(user) {
    return {
        id: user.id,
        name: user.name
    };
}
```

### v2 mapper

```js
function toV2User(user) {
    return {
        id: user.id,
        fullName: user.name
    };
}
```

The business logic doesn't need to be duplicated.

---

# 13. This Is Why Response DTOs Matter

Earlier we discussed response mapping.

Now you can see another benefit.

Without a response mapper:

```text
database model
      ↓
directly exposed
      ↓
API contract
```

Changing the API becomes dangerous.

With DTO/mapping:

```text
database model
      ↓
domain/service
      ↓
version-specific response mapper
      ↓
API contract
```

Now the public API can evolve independently from the internal model.

This is a **very strong architectural pattern**.

---

# 14. URL Versioning Is Not the Only Strategy

There are several approaches.

### 1. URL versioning

```http
/api/v1/users
/api/v2/users
```

### 2. Header versioning

For example:

```http
Accept: application/vnd.example.v2+json
```

### 3. Query parameter

```http
/api/users?version=2
```

### 4. Content negotiation

Version is represented through HTTP media types/headers.

Each approach has tradeoffs.

---

# 15. URL Versioning

Example:

```http
/api/v1/products
```

Advantages:

```text
easy to understand
easy to test
easy to document
easy to route
easy to observe in logs
```

Disadvantages:

```text
URLs contain version information
multiple route trees may exist
```

For the kind of backend starter architecture you're building, URL versioning is a very practical approach.

---

# 16. Header Versioning

Example:

```http
GET /api/users

Accept: application/vnd.myapi.v2+json
```

The URL remains:

```text
/api/users
```

The version is represented through headers.

Advantages:

```text
clean resource URL
version represents representation
```

Disadvantages:

```text
less obvious
harder to test manually
less visible in simple logs
```

---

# 17. Query Parameter Versioning

Example:

```http
GET /api/users?version=2
```

Very easy technically.

But it can become awkward because:

```text
version becomes another query parameter
```

and query parameters are usually better suited for:

```text
filtering
sorting
pagination
search
```

rather than defining fundamentally different API contracts.

---

# 18. Which Versioning Strategy Should You Use?

For your MERN backend starter:

I'd recommend learning URL versioning first:

```text
/api/v1
/api/v2
```

Why?

Because it gives you a very clear mental model:

```text
v1 = contract A
v2 = contract B
```

Then learn header/content-negotiation versioning as an architectural alternative.

In an interview, don't say:

> "URL versioning is always the best."

Instead say:

> "I'd choose the strategy based on the API's consumers, operational requirements, documentation approach, and organizational conventions. URL versioning is often simple and explicit, while header-based versioning can keep resource URLs stable."

That is a much stronger answer.

---

# 19. When Should You Create v2?

This is one of the most important questions.

Don't create:

```text
v2
```

for every tiny change.

For example:

```text
add optional field
```

usually doesn't require v2.

But:

```text
rename required field
change response semantics
remove field
change endpoint behavior
change authentication contract
```

may justify a new version.

Think:

```text
Is the existing contract still valid?
```

If yes:

```text
probably no new version
```

If no:

```text
consider a new version
```

---

# 20. Example

Current:

```json
{
  "id": "123",
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

You want:

```json
{
  "id": "123",
  "profile": {
    "fullName": "Rahul",
    "email": "rahul@example.com"
  }
}
```

That's a substantial response restructuring.

Rather than silently changing:

```http
/api/v1/users
```

you might introduce:

```http
/api/v2/users
```

---

# 21. Don't Version for Internal Changes

Suppose you change:

```text
MongoDB collection design
```

but the API response stays exactly the same.

You usually don't need:

```text
v2
```

The client doesn't care.

This illustrates a key principle:

> **API versions are about public contracts, not internal implementation versions.**

---

# 22. Database Version ≠ API Version

You might have:

```text
API v1
    ↓
MongoDB schema v7
```

and:

```text
API v2
    ↓
MongoDB schema v7
```

Or:

```text
API v1
    ↓
schema v7

API v2
    ↓
schema v9
```

These versions are independent concepts.

Don't confuse:

```text
API contract
```

with:

```text
database schema
```

---

# 23. The Dangerous Migration

Suppose your database currently stores:

```json
{
  "firstName": "Rahul",
  "lastName": "Kumar"
}
```

v2 wants:

```json
{
  "fullName": "Rahul Kumar"
}
```

A naive migration might:

```text
delete firstName
delete lastName
add fullName
```

immediately.

But what if v1 is still running?

```text
v1 expects firstName
v2 expects fullName
```

Now v1 breaks.

This is why API evolution often requires **expand-and-contract migrations**.

---

# 24. Expand-and-Contract

This is a **gold-level production concept**.

Suppose you want:

```text
firstName + lastName
```

to become:

```text
fullName
```

### Step 1 — Expand

Add support for:

```text
fullName
```

without removing the old fields.

Database can temporarily support:

```json
{
  "firstName": "Rahul",
  "lastName": "Kumar",
  "fullName": "Rahul Kumar"
}
```

---

# 25. Step 2 — Migrate

Update existing records:

```text
old records
    ↓
populate fullName
```

During this period:

```text
old clients
    ↓
still work

new clients
    ↓
can use fullName
```

---

# 26. Step 3 — Switch Consumers

Move clients from:

```text
v1
```

to:

```text
v2
```

Gradually.

For example:

```text
10% clients
50% clients
90% clients
100% clients
```

depending on your deployment strategy.

---

# 27. Step 4 — Contract

After all old consumers have migrated:

```text
remove old fields
remove old API version
remove compatibility code
```

Now the system becomes simpler again.

So:

```text
EXPAND
   ↓
MIGRATE
   ↓
SWITCH
   ↓
CONTRACT
```

This pattern is extremely useful in production systems.

---

# 28. Why This Pattern Is Powerful

Because you avoid:

```text
big bang migration
```

Instead:

```text
old + new coexist temporarily
```

This gives you:

```text
safer deployments
rollback options
gradual migration
less downtime
independent deployments
```

---

# 29. API Deprecation

Suppose:

```text
v1
```

is old and:

```text
v2
```

is now recommended.

Don't necessarily kill v1 immediately.

You can mark it:

```text
DEPRECATED
```

Then communicate:

```text
v1 will be retired on DATE
```

This gives consumers time to migrate.

---

# 30. Deprecation Is a Process

A mature API lifecycle might look like:

```text
v1
 ↓
stable
 ↓
v2 released
 ↓
v1 deprecated
 ↓
migration period
 ↓
v1 sunset
 ↓
v1 removed
```

Don't think:

```text
v2 released
↓
v1 immediately deleted
```

unless you completely control all clients.

---

# 31. Deprecation Communication

A professional organization might provide:

```text
migration guide
release notes
documentation
deadline
examples
support
```

For example:

```text
v1:
deprecated

Sunset:
2027-01-01

Replacement:
v2
```

The exact mechanism depends on your API platform.

The important concept is:

> **Consumers need a predictable migration path.**

---

# 32. Sunset Headers

Some APIs use HTTP headers to communicate deprecation/sunset information.

Conceptually:

```http
Deprecation: true
```

and possibly a sunset date through an appropriate mechanism.

The exact header conventions and tooling depend on your API infrastructure.

For interviews, the important point is:

> **APIs can communicate that an endpoint/version is approaching retirement.**

---

# 33. Don't Hide Breaking Changes

Bad:

```text
v1 endpoint
   ↓
silently changes behavior
```

Good:

```text
v1
 ↓
stable old behavior

v2
 ↓
new behavior
```

or:

```text
v1
 ↓
backward-compatible evolution
```

depending on the change.

Predictability is more valuable than surprise.

---

# 34. Compatibility Is More Than JSON Shape

An API can break clients through:

### Request changes

```text
required field added
field renamed
type changed
```

### Response changes

```text
field removed
field renamed
type changed
```

### Behavior changes

```text
different filtering semantics
different sorting
different authorization behavior
```

### Error changes

```text
status code changed
error code removed
error format changed
```

### Authentication changes

```text
token format changed
authentication mechanism changed
```

All of these can affect clients.

---

# 35. Error Contracts Must Be Versioned Carefully

Suppose v1 returns:

```json
{
  "success": false,
  "message": "Invalid email"
}
```

and suddenly v1 returns:

```json
{
  "error": {
    "code": "INVALID_EMAIL",
    "details": []
  }
}
```

A frontend doing:

```js
error.message
```

can break.

So your error response is also part of the API contract.

This connects directly to the response architecture we've been building.

---

# 36. Don't Change HTTP Semantics Casually

Suppose:

```text
POST /users
```

previously returns:

```http
201 Created
```

and you change it to:

```http
200 OK
```

Some clients may depend on:

```js
if (response.status === 201)
```

Therefore:

> HTTP status codes are part of your API contract too.

---

# 37. API Compatibility Matrix

For a real project, you can maintain something like:

|Change|Usually Breaking?|
|---|---|
|Add optional response field|No|
|Add optional request field|No|
|Remove response field|Yes|
|Rename response field|Yes|
|Change field type|Yes|
|Add required request field|Yes|
|Change enum semantics|Potentially|
|Change status code|Potentially/Yes|
|Change authentication behavior|Yes|
|Improve internal DB implementation|No|
|Add new endpoint|No|

This is a useful interview revision table.

---

# 38. Adding a Required Request Field

Current:

```http
POST /users
```

```json
{
  "name": "Rahul"
}
```

Later you require:

```json
{
  "name": "Rahul",
  "country": "India"
}
```

Old clients don't send:

```text
country
```

Therefore:

```text
old client
   ↓
400
```

That's breaking.

---

# 39. Safer Alternative

Initially make the new field optional:

```text
country?
```

Deploy support.

Then migrate clients.

Later, if necessary, enforce it under a new contract/version.

This is another example of:

```text
expand
↓
migrate
↓
contract
```

---

# 40. Consumer-Driven Thinking

Before changing an API, ask:

```text
Who consumes this API?
```

Potential consumers:

```text
web app
mobile app
admin dashboard
internal service
third-party partner
CLI
automation
```

The more consumers you have, the more carefully you need to evolve the contract.

---

# 41. Internal APIs vs Public APIs

An internal API may have:

```text
10 known consumers
```

and you control all of them.

A public API might have:

```text
thousands of unknown consumers
```

Public APIs usually need much stronger compatibility guarantees.

You can't simply say:

> "I'll update the frontend tomorrow."

because you don't control the consumers.

---

# 42. Microservices Make This Harder

Suppose:

```text
Order Service
     ↓
Payment Service
```

Order Service sends:

```json
{
  "amount": 100
}
```

Payment Service expects:

```json
{
  "amount": 100
}
```

Now Payment Service changes:

```text
amount
↓
amountInPaise
```

If Order Service hasn't been updated, communication breaks.

This is why API compatibility matters between services too.

---

# 43. Tolerant Reader Principle

A useful distributed-systems idea is:

> Consumers should generally be tolerant of additions they don't understand.

For example, if a service receives:

```json
{
  "id": "123",
  "name": "Rahul",
  "newField": "something"
}
```

it shouldn't necessarily fail just because `newField` exists.

This helps systems evolve independently.

But tolerance should not mean:

```text
accept absolutely anything
```

Validation still matters.

---

# 44. Contract Testing

This is where automated API contract tests become powerful.

You can verify:

```text
Provider
    ↓
still satisfies
    ↓
Consumer expectations
```

For example:

```text
GET /api/v1/users
```

must continue returning:

```text
id
name
email
```

with expected types and semantics.

This helps prevent accidental breaking changes.

---

# 45. Schema-Based Contract Testing

You might define a schema:

```json
{
  "type": "object",
  "required": ["id", "name"],
  "properties": {
    "id": {
      "type": "string"
    },
    "name": {
      "type": "string"
    }
  }
}
```

Then tests can verify that responses still conform.

Tools can automate this through:

```text
OpenAPI
JSON Schema
contract-testing frameworks
```

The architecture matters more than memorizing a specific tool.

---

# 46. OpenAPI Helps Here

Your API specification can define:

```text
v1 endpoints
request schemas
response schemas
errors
parameters
authentication
```

Then:

```text
implementation
      ↔
contract
```

can be tested and documented.

This makes API evolution safer.

---

# 47. API Versioning and Documentation

When you have:

```text
v1
v2
```

your documentation should clearly explain:

```text
which version to use
what changed
migration steps
deprecated endpoints
```

For example:

```text
API v1
    Legacy
    Supported until DATE

API v2
    Recommended
```

Don't make users discover compatibility issues through runtime errors.

---

# 48. Versioning Doesn't Mean "Never Change Anything"

A common beginner misunderstanding:

> "If I use API versioning, I need v2 for every change."

No.

Instead:

```text
Backward-compatible change
    ↓
keep current version

Breaking change
    ↓
consider new version
```

Versioning is a tool for managing **contract changes**, not a release-numbering system for every deployment.

---

# 49. API Version ≠ Application Version

Your application might be:

```text
backend release 2.37.4
```

while the public API is:

```text
v1
```

That's completely normal.

You might deploy 100 backend releases without changing:

```text
/api/v1
```

The API version changes only when the public contract needs a different compatibility boundary.

---

# 50. Semantic Versioning vs API Versioning

These are also different.

Semantic versioning:

```text
1.4.2
```

usually describes software releases:

```text
MAJOR.MINOR.PATCH
```

API versioning:

```text
v1
v2
```

describes public API contract generations.

Don't assume:

```text
backend 2.0.0
=
API v2
```

They are independent.

---

# 51. Interview Question

### "When would you introduce API v2?"

Strong answer:

> "I would introduce a new API version when I need a breaking change that cannot be safely introduced while preserving the existing contract. Examples include removing or renaming fields, changing response semantics, changing required request fields, or substantially changing endpoint behavior. For backward-compatible changes, I'd generally keep the existing version."

---

# 52. Interview Question

### "How would you migrate from v1 to v2 without downtime?"

Excellent answer:

> "I'd use a gradual migration. First I'd introduce the v2 contract while keeping v1 available. If the database schema also needs to change, I'd use an expand-and-contract migration so both versions can operate during the transition. Then I'd migrate consumers gradually, monitor errors and usage, deprecate v1, and only remove it after the supported migration window."

That's a **very strong production answer**.

---

# 53. Interview Question

### "Would you duplicate the entire v1 codebase for v2?"

Answer:

> "Usually no. I'd isolate version-specific concerns such as request validation and response mapping while keeping shared domain and business logic where the semantics are still the same. If the business behavior genuinely differs, I would separate that logic rather than forcing both versions through an abstraction that becomes difficult to maintain."

That's better than blindly saying:

> "Always reuse everything."

---

# 54. Interview Question

### "Is adding a field always backward-compatible?"

A nuanced answer:

> "Usually adding an optional response field is considered backward-compatible for tolerant clients, but compatibility depends on client behavior. Some clients may incorrectly assume an exact schema. So I'd still verify consumer expectations through contract tests and documentation."

That nuance is what separates a stronger engineer from someone memorizing definitions.

---

# 55. Interview Question

### "What is expand-and-contract migration?"

Answer:

> "It's a migration strategy where we first expand the system to support both old and new representations, migrate data and consumers gradually, and only then remove the old representation. It avoids requiring all components to switch simultaneously and reduces deployment and rollback risk."

Memorize this concept.

---

# 56. A Real Example

Suppose v1:

```http
GET /api/v1/profile
```

returns:

```json
{
  "name": "Rahul",
  "phone": "1234567890"
}
```

v2 wants:

```json
{
  "profile": {
    "fullName": "Rahul",
    "phoneNumber": "1234567890"
  }
}
```

Architecture:

```text
                 User Domain
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
     v1 response            v2 response
       mapper                 mapper
          │                     │
          ▼                     ▼
       /v1/profile           /v2/profile
```

Same underlying business object.

Different public contracts.

                         API

             ┌────────────┴────────────┐
             ▼                         ▼
            v1                         v2
             │                         │
       Request DTO                Request DTO

# 58. Your Gold-Level Mental Model

When someone says:

> **"We need to change our API."**

Don't immediately think:

```text
edit controller
```

Think:

```text
What is changing?
       ↓
Is it breaking?
       ↓
Can it be backward-compatible?
       ↓
Who consumes it?
       ↓
Do we need a new API version?
       ↓
Does the database need migration?
       ↓
Can old + new coexist?
       ↓
How do we migrate consumers?
       ↓
How do we test compatibility?
       ↓
When can the old version be removed?
```

That is the production mindset.

# 🧠 Lesson 16.13 — Revision Sheet

Remember these **15 points**:

1. **API versioning manages changes to public API contracts.**
    
2. `/api/v1` and `/api/v2` can represent different contracts.
    
3. Breaking changes can break existing clients.
    
4. Removing/renaming fields is generally breaking.
    
5. Adding optional response fields is generally non-breaking.
    
6. API versioning is about **public contracts**, not internal deployments.
    
7. Database version and API version are separate concepts.
    
8. URL versioning is explicit and easy to understand.
    
9. Don't create a new version for every small change.
    
10. Keep shared business logic where semantics remain the same.
    
11. Use version-specific request/response mapping where necessary.
    
12. Deprecation should provide consumers a migration path.
    
13. **Expand → Migrate → Switch → Contract** is a powerful migration strategy.
    
14. Contract testing helps prevent accidental breaking changes.
    
15. API compatibility includes **data shape, types, status codes, errors, authentication, and behavior**.

# 🎯 Interview Challenge

Imagine you're asked:

> **"Your company has `/api/v1/orders`. You need to rename `customerName` to `customer.fullName`, remove `phone`, and change the order status from `completed` to `delivered`. Thousands of mobile users still use v1. How would you implement this?"**

Your answer should contain these ideas:

```text
1. Identify breaking changes
2. Keep v1 stable
3. Introduce v2
4. Create v2 DTO/response mapper
5. Keep shared business logic where possible
6. Handle database migration safely
7. Use expand-and-contract if schema changes
8. Migrate clients gradually
9. Monitor v1/v2 usage and errors
10. Deprecate v1
11. Give consumers a migration window
12. Remove v1 only after migration
```

If you can explain that naturally in an interview, you're moving well beyond **"MERN developer who knows Express"** toward **backend engineer who understands production API design**.
