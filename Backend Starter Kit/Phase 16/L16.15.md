# Phase 16 — API Architecture & Production Contracts

## Lesson 16.15 — Distributed Transactions, Atomicity & Partial Failure

This is where we move from **"how do I build an API?"** to:

> **"How do I keep a distributed system correct when something fails halfway through?"**

This is one of the most valuable backend interview topics in the whole roadmap.

Your uploaded roadmap places Phase 16 around API architecture and treats the backend as layered through **routes → middleware → controllers → services → repositories → models**, with later phases covering observability, background jobs, testing, Docker, and production hardening.

For this lesson, we're extending that architecture into distributed operations.

---

# 1. The Problem

Imagine an e-commerce checkout:

```text
POST /api/v1/orders
```

The backend needs to:

```text
1. Create order
2. Reserve inventory
3. Charge payment
4. Send confirmation email
```

Looks simple:

```text
Create Order
     ↓
Reserve Inventory
     ↓
Charge Payment
     ↓
Send Email
```

But what happens here?

```text
Create Order       ✅
Reserve Inventory  ✅
Charge Payment     ❌
```

Now what is the state?

You have:

```text
Order exists
Inventory reserved
Payment failed
```

Or even worse:

```text
Order created       ✅
Inventory reserved  ✅
Payment succeeded   ✅
Email failed        ❌
```

Should you cancel the payment?

Should you delete the order?

Should you release inventory?

These are **distributed consistency problems**.

---

# 2. Atomicity

Atomicity means:

> An operation is treated as an indivisible unit: either the required changes happen, or they don't.

Classic database transaction:

```text
Transaction
   │
   ├── Operation A
   ├── Operation B
   └── Operation C
        │
        ▼
     COMMIT
```

If something fails:

```text
ROLLBACK
```

Conceptually:

```text
A ✅
B ✅
C ❌
 ↓
ROLLBACK
 ↓
A ❌
B ❌
C ❌
```

That's atomicity.

---

# 3. MongoDB Transaction Example

Suppose we have:

```text
orders
inventory
```

We want:

```text
Create order
+
decrease inventory
```

inside one database transaction.

Conceptually:

```js
const session = await mongoose.startSession();

try {
    session.startTransaction();

    await Order.create(
        [orderData],
        { session }
    );

    await Product.updateOne(
        { _id: productId },
        { $inc: { stock: -quantity } },
        { session }
    );

    await session.commitTransaction();
} catch (error) {
    await session.abortTransaction();
    throw error;
} finally {
    await session.endSession();
}
```

The exact implementation will depend on your repository/service architecture.

The important idea is:

```text
Same database
+
Same transaction
=
Atomic operation
```

---

# 4. But Transactions Have a Boundary

Here's the critical part.

Suppose:

```text
MongoDB
   ↓
create order
   ↓
commit
```

Then:

```text
Payment Provider
   ↓
charge ₹1,000
```

MongoDB cannot automatically roll back:

```text
external payment
```

if something later fails.

You don't have:

```text
MongoDB transaction
       +
Stripe/Razorpay/Bank transaction
```

as one magical atomic transaction.

This is where distributed transactions become difficult.

---

# 5. Local Transaction vs Distributed Transaction

### Local transaction

Everything happens inside one transactional system:

```text
MongoDB
 ├── Order
 ├── Inventory
 └── PaymentRecord
```

You may be able to use:

```text
MongoDB transaction
```

to make these changes atomic.

---

### Distributed operation

Now:

```text
Order Service
     ↓
MongoDB

Payment Service
     ↓
Payment Provider

Email Service
     ↓
Email Provider
```

Different systems.

Different failure boundaries.

Now a single database transaction isn't enough.

---

# 6. The Partial Failure Problem

This is the concept I want you to remember.

Suppose:

```text
Step 1 → SUCCESS
Step 2 → SUCCESS
Step 3 → SUCCESS
Step 4 → FAILURE
```

You don't have a simple:

```text
ROLLBACK EVERYTHING
```

button.

Why?

Because the previous systems may already have committed their changes.

This is called:

> **Partial failure**

---

# 7. Example: Order Checkout

Let's build a realistic example.

```text
Client
  │
  ▼
Order API
  │
  ├── Create order
  │
  ├── Reserve inventory
  │
  ├── Charge payment
  │
  └── Send confirmation
```

Suppose:

```text
Create order       ✅
Reserve inventory  ✅
Charge payment     ✅
Send email         ❌
```

Should the order be cancelled?

Probably not.

An email failure doesn't necessarily mean the order failed.

This teaches an important lesson:

> **Not every failure should cause the entire business operation to roll back.**

---

# 8. Business Criticality Matters

Classify operations.

### Critical

```text
Payment
Inventory reservation
Order creation
```

### Non-critical

```text
Email
Analytics event
Notification
Logging event
```

If email fails:

```text
Order
  ↓
still successful
```

You can retry the email asynchronously.

If payment fails:

```text
Order
  ↓
probably cannot become "paid"
```

The business state needs different handling.

---

# 9. State Machines

One of the best ways to manage these workflows is to model explicit states.

Instead of:

```text
order exists
```

use:

```text
PENDING
CONFIRMED
PAID
PROCESSING
SHIPPED
CANCELLED
FAILED
```

For example:

```text
PENDING
   ↓
PAYMENT_PENDING
   ↓
PAID
   ↓
CONFIRMED
   ↓
SHIPPED
```

If payment fails:

```text
PAYMENT_PENDING
       ↓
PAYMENT_FAILED
```

Now the system knows what happened.

---

# 10. Don't Use a Boolean

A beginner might create:

```json
{
  "paid": true
}
```

But production workflows often need more information.

Better:

```json
{
  "paymentStatus": "pending"
}
```

Possible values:

```text
pending
processing
succeeded
failed
refunded
```

The same idea applies to:

```text
orderStatus
inventoryStatus
emailStatus
```

State machines make distributed workflows much easier to reason about.

---

# 11. Compensating Actions

Suppose:

```text
Create Order       ✅
Reserve Inventory  ✅
Payment            ❌
```

You may want to undo:

```text
Reserve Inventory
```

So:

```text
reserve inventory
       ↓
payment fails
       ↓
release inventory
```

This is called a:

> **Compensating action**

Notice the difference:

```text
Database rollback
```

versus:

```text
Compensating action
```

A rollback automatically restores a transactional database state.

A compensating action is a **new business operation that reverses the effect of a previous operation**.

---

# 12. Example

Original action:

```text
reserveInventory()
```

Compensation:

```text
releaseInventory()
```

Original:

```text
capturePayment()
```

Compensation might be:

```text
refundPayment()
```

Original:

```text
createShipment()
```

Compensation might be:

```text
cancelShipment()
```

These aren't database rollbacks.

They're new operations.

---

# 13. Why Compensation Isn't Perfect

Suppose:

```text
Charge payment
      ↓
₹1,000 successfully charged
```

Then you decide:

```text
refund ₹1,000
```

But refund itself fails.

Now:

```text
Payment succeeded
Refund failed
```

So compensation can itself fail.

This means you need:

```text
retry
monitoring
state tracking
reconciliation
```

This is why distributed workflows are hard.

---

# 14. Saga Pattern

The **Saga pattern** is one of the most important concepts here.

A saga breaks one large distributed operation into:

```text
multiple local transactions
```

with:

```text
compensating actions
```

For example:

```text
Create Order
     ↓
Reserve Inventory
     ↓
Charge Payment
     ↓
Confirm Order
```

Each step commits independently.

If something fails:

```text
run compensating actions
```

---

# 15. Saga Example

Forward actions:

```text
T1: Create Order
T2: Reserve Inventory
T3: Charge Payment
T4: Confirm Order
```

Compensations:

```text
C1: Cancel Order
C2: Release Inventory
C3: Refund Payment
```

Conceptually:

```text
T1 → T2 → T3 → T4
          ❌
          ↓
        C2 / C1
```

The exact compensation depends on which steps succeeded.

---

# 16. Two Main Saga Styles

There are two important approaches.

### Choreography

Services react to events.

```text
Order Created
     ↓
Inventory Service
     ↓
Inventory Reserved
     ↓
Payment Service
     ↓
Payment Succeeded
```

No central controller coordinates every step.

---

### Orchestration

A central orchestrator coordinates the workflow.

```text
             Order Saga
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
    Inventory  Payment  Shipping
```

The orchestrator says:

```text
reserve inventory
charge payment
create shipment
```

and decides what happens when something fails.

---

# 17. Choreography

Example:

```text
Order Service
    │
    │ OrderCreated
    ▼
Message Broker
    │
    ▼
Inventory Service
    │
    │ InventoryReserved
    ▼
Message Broker
    │
    ▼
Payment Service
```

Advantages:

```text
loosely coupled
event-driven
services react independently
```

Disadvantages:

```text
workflow can become difficult to understand
debugging becomes harder
event dependencies can become complicated
```

---

# 18. Orchestration

Example:

```text
              Order Saga Orchestrator
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
     Inventory   Payment   Shipping
```

The orchestrator knows:

```text
Step 1
Step 2
Step 3
```

and what to do after failures.

Advantages:

```text
centralized workflow
easier to understand
easier to track business process
```

Disadvantages:

```text
orchestrator becomes important infrastructure
can become too complex
services depend on workflow commands
```

---

# 19. Which One Should You Use?

Don't say:

> "Saga orchestration is always better."

A strong interview answer is:

> "I'd choose based on workflow complexity and coupling. Choreography can work well for loosely coupled event-driven flows, while orchestration is often easier to reason about for complex business workflows with many steps and compensations."

That's the kind of answer interviewers like.

# 20. Eventual Consistency

With distributed systems, you may not have:

```text
everything becomes consistent immediately
```

Instead:

```text
State A
  ↓
event
  ↓
State B
  ↓
event
  ↓
State C
```

There can be a short period where different services have different views.

This is:

> **Eventual consistency**

---

# 21. Example

Immediately after placing an order:

```text
Order Service:
PAID
```

But:

```text
Analytics Service:
not updated yet
```

A moment later:

```text
Analytics Service:
updated
```

The system becomes consistent over time.

This is often acceptable for:

```text
analytics
notifications
search indexes
recommendations
reporting
```

But may not be acceptable for some critical decisions.

---

# 22. Strong vs Eventual Consistency

### Strong consistency

You expect readers to immediately see the latest committed state.

Useful when correctness is critical.

Examples may include:

```text
financial balance
inventory allocation
authorization state
```

depending on the system design.

---

### Eventual consistency

Updates propagate asynchronously.

Useful for:

```text
analytics
emails
search
notifications
recommendations
```

The key question is:

> **Does this part of the system require immediate consistency?**

# 23. The Outbox Pattern

Now we're reaching another **gold-level interview topic**.

Suppose you do:

```text
Create Order
   ↓
Publish OrderCreated event
```

What if:

```text
Create Order = SUCCESS
Publish event = FAILURE
```

Now your database says:

```text
Order exists
```

but other services never received:

```text
OrderCreated
```

You have inconsistency.

---

# 24. The Dual-Write Problem

This is called the:

> **Dual-write problem**

You're trying to write to two systems:

```text
Database
+
Message Broker
```

Example:

```text
DB write       ✅
Kafka publish  ❌
```

or:

```text
DB write       ❌
Kafka publish  ✅
```

You cannot easily make both atomic using a normal database transaction.

---

# 25. Outbox Pattern

Instead of:

```text
Database
   +
Message Broker
```

directly, write the event into the same database transaction.

```text
Transaction
   │
   ├── Create Order
   │
   └── Create Outbox Event
          ↓
       COMMIT
```

Now both are inside the same database transaction.

---

# 26. Outbox Table/Collection

You might have:

```text
outbox_events
```

with:

```text
id
type
aggregateId
payload
status
createdAt
processedAt
```

For example:

```json
{
  "type": "ORDER_CREATED",
  "aggregateId": "order_123",
  "payload": {
    "orderId": "order_123"
  },
  "status": "pending"
}
```

---

# 27. Outbox Flow

```text
Application
    │
    ▼
Database Transaction
    │
    ├── Order
    │
    └── Outbox Event
            │
            ▼
          COMMIT
            │
            ▼
      Outbox Worker
            │
            ▼
      Message Broker
            │
            ▼
        Consumers
```

Now the critical data and event record are committed together.

# 28. What If the Worker Crashes?

Suppose:

```text
Outbox Worker
    ↓
reads event
    ↓
publishes event
    ↓
CRASH
```

before marking:

```text
processed
```

The worker may publish it again later.

Therefore consumers should often be:

> **Idempotent**

This connects directly to Lesson 16.14.

# 29. The Beautiful Connection

Lesson 16.14:

```text
Idempotency
```

Lesson 16.15:

```text
Distributed transactions
```

They are connected.

Because distributed systems often provide:

```text
at-least-once delivery
```

meaning:

> A message may be delivered more than once.

Therefore:

```text
Producer
   ↓

   ↓

```

---

# 30. At-Least-Once Delivery

Imagine:

```text
Message M
   ↓
Consumer processes M
   ↓
Consumer crashes before ACK
```

Broker thinks:

```text
M was not successfully processed
```

So it delivers:

```text
M again
```

Now:

```text
M
M
```

The consumer must safely handle duplicates.

---

# 31. At-Most-Once Delivery

The opposite approach:

```text
send message
   ↓
mark processed
   ↓
don't retry
```

Potentially means:

```text
message lost
```

So:

```text
at-most-once
=
possible loss
```

while:

```text
at-least-once
=
possible duplicates
```

Neither automatically gives exactly-once business effects.

---

# 32. Exactly-Once Is Tricky

You may hear:

> "We need exactly-once processing."

Be careful.

At the distributed-system level, exactly-once semantics are difficult.

Even if infrastructure offers some form of exactly-once processing, your **business side effects** still need careful design.

For example:

```text
send email
charge payment
update external service
```

may have their own failure boundaries.

A better practical mindset is:

> **Design important consumers to tolerate duplicate delivery.**

---

# 33. Idempotent Consumer

Suppose an event arrives:

```json
{
  "eventId": "evt_123",
  "type": "ORDER_CREATED"
}
```

Consumer stores:

```text
processed_events
```

with:

```text
eventId
```

Before processing:

```text
Does evt_123 already exist?
```

If yes:

```text
ignore duplicate
```

If no:

```text
process
record eventId
```

Again, the check must be designed safely against races.

---

# 34. Unique Constraints Help Again

Suppose:

```text
processed_events
```

has:

```text
UNIQUE(eventId)
```

Then duplicate processing attempts can be prevented at the database level.

This is the same defense-in-depth principle we discussed with idempotency keys.

# 38. Order State Machine

A good design might be:

```text
PENDING
   │
   ▼
PAYMENT_PROCESSING
   │
   ├──── failure ────> PAYMENT_FAILED
   │
   ▼
PAID
   │
   ▼
CONFIRMED
   │
   ▼
SHIPPED
```

If payment fails:

```text
PAYMENT_FAILED
```

Then a retry may transition:

```text
PAYMENT_FAILED
      ↓
PAYMENT_PROCESSING
      ↓
PAID
```

Now your system isn't relying on one synchronous request surviving perfectly.

# 40. Synchronous vs Asynchronous

Synchronous:

```text
Create order
Validate payment
```

Potentially asynchronous:

```text

Update search index

```

A useful mental model:

> **Do only what the user needs immediately inside the request.**

Move non-critical work to background processing where appropriate.

# 41. Failure Handling Matrix

For a production checkout, think like this:

|Step|Failure|Possible response|
|---|---|---|
|Create order|DB failure|fail request|
|Reserve inventory|failure|order remains pending/failed|
|Payment|failure|release inventory|
|Payment|timeout|query/retry idempotently|
|Email|failure|retry asynchronously|
|Analytics|failure|retry asynchronously|
|Notification|failure|retry asynchronously|

There isn't one universal rollback rule.

You need **business-specific failure semantics**.

# 42. Retry vs Compensation

This distinction is very important.

### Retry

Means:

> "The operation may not have succeeded; try the same operation again."

Example:

```text
Send email
   ↓
timeout
   ↓
retry
```

---

### Compensation

Means:

> "The previous operation succeeded, but we now need another operation to reverse its business effect."

Example:

```text
Reserve inventory
      ↓
Payment fails
      ↓
Release inventory
```

Different concepts.

---

# 43. Compensation vs Rollback

Remember:

```text
ROLLBACK
```

usually means:

```text
undo uncommitted work within a transaction
```

while:

```text
COMPENSATION
```

means:

```text
perform another business operation to counteract an already committed action
```

This distinction is a favorite interview question.

---

# 44. Interview Question

### "Why can't you simply use a MongoDB transaction for payment + order?"

Strong answer:

> "A MongoDB transaction can provide atomicity for operations within the transactional MongoDB boundary, but an external payment provider is outside that transaction. If the payment succeeds and the database later fails, MongoDB cannot roll back the external charge. For that kind of workflow I'd use explicit states, idempotency, retries, provider status checks, and potentially compensating actions or a saga."

Excellent answer.

---

# 45. Interview Question

### "What is a Saga?"

Answer:

> "A saga breaks a distributed business transaction into a sequence of local transactions. Each step commits independently, and if a later step fails, previously completed steps can be reversed using compensating actions. A saga can be coordinated through orchestration or choreography."

---

# 46. Interview Question

### "What is the Outbox Pattern?"

Answer:

> "The outbox pattern solves the dual-write problem by storing the business change and its corresponding event in the same database transaction. A separate worker later publishes the outbox event to the message broker. This prevents a successful database write from being silently separated from its event publication."

---

# 47. Interview Question

### "What happens if the outbox worker publishes an event twice?"

Strong answer:

> "The consumer should be designed to handle duplicate delivery. I'd give events a unique event ID and use idempotent processing, potentially backed by a unique constraint or processed-event record. At-least-once delivery plus idempotent consumers is usually a practical approach."

---

# 48. Interview Question

### "What is eventual consistency?"

Answer:

> "Eventual consistency means different components may temporarily have different states, but assuming successful propagation and no permanent failure, they converge toward a consistent state. It's often useful for asynchronous concerns such as notifications, analytics, and search indexes."

---

# 49. Interview Question

### "Would you use a distributed transaction everywhere?"

Absolutely not.

A strong answer:

> "No. Distributed transaction coordination adds complexity and operational cost. I'd first see whether the operation can be kept within one transactional boundary. For cross-service workflows, I'd generally prefer explicit state machines, idempotency, asynchronous events, sagas, and compensating actions where appropriate."

# 🧠 Lesson 16.15 — Revision Sheet

Remember these **18 points**:

1. **Atomicity** means a transactional operation succeeds as a unit or rolls back.
    
2. Database transactions only cover their transactional boundary.
    
3. External services cannot normally participate in your MongoDB transaction automatically.
    
4. **Partial failure** happens when some steps succeed and others fail.
    
5. Model important workflows using explicit **states**.
    
6. A compensating action is a new operation that reverses a previous committed business effect.
    
7. **Saga** = sequence of local transactions + compensating actions.
    
8. Saga can use **orchestration** or **choreography**.
    
9. Distributed systems commonly use **eventual consistency**.
    
10. The **dual-write problem** occurs when you must update a database and publish an event.
    
11. The **Outbox Pattern** stores the business change and event together in one DB transaction.
    
12. A worker publishes outbox events asynchronously.
    
13. Outbox consumers should generally tolerate duplicate events.
    
14. **At-least-once delivery** can produce duplicates.
    
15. Idempotent consumers protect against duplicate processing.
    
16. Retry and compensation are different mechanisms.
    
17. Not every failure should roll back the entire business workflow.
    
18. Good distributed architecture is about **explicit states, failure recovery, idempotency, observability, and controlled consistency**.

### In one sentence each:

**Transaction**

> "Make multiple operations atomic within one transactional boundary."

**Saga**

> "Coordinate multiple local transactions and compensate when later steps fail."

**Outbox**

> "Atomically save the business change and event, then publish the event asynchronously."

**Idempotency**

> "Make retries of the same logical operation safe."
