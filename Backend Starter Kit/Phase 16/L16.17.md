# Phase 16 — API Architecture & Production Contracts

## Lesson 16.17 — REST vs RPC vs GraphQL

This is a **very important interview lesson** because interviewers often ask:

> **"Why did you choose REST instead of GraphQL?"**

or:

> **"When would you use RPC?"**

A weak answer memorizes definitions.

A strong backend engineer understands the **trade-offs and chooses based on requirements**.

---

# 1. The Three API Styles

At a high level:

```text
REST
 ↓
Resources

RPC
 ↓
Actions / Operations

GraphQL
 ↓
Client-defined data queries
```

Examples:

### REST

```http
GET /api/v1/users/123
POST /api/v1/orders
PATCH /api/v1/orders/123
DELETE /api/v1/orders/123
```

### RPC

```http
POST /api/v1/orders/123/cancel
POST /api/v1/payments/123/refund
POST /api/v1/users/123/reset-password
```

### GraphQL

```graphql
query {
  user(id: "123") {
    name
    email
    orders {
      id
      total
    }
  }
}
```

The fundamental difference is:

> **REST organizes around resources, RPC around operations, and GraphQL around client-specified data requirements.**

---

# 2. REST

REST stands for:

> **Representational State Transfer**

It is an architectural style based around resources and standard HTTP semantics.

For example:

```text
User
Order
Product
Payment
```

become resources.

---

# 3. REST Example

Suppose you have an e-commerce API.

```http
GET /api/v1/products
```

Get products.

```http
GET /api/v1/products/123
```

Get one product.

```http
POST /api/v1/products
```

Create a product.

```http
PATCH /api/v1/products/123
```

Update it.

```http
DELETE /api/v1/products/123
```

Delete it.

The API naturally maps HTTP methods to resource operations.

---

# 4. REST's Biggest Strength

REST works extremely well with the existing HTTP ecosystem.

You get:

```text
HTTP methods
status codes
headers
caching
proxies
CDNs
authentication mechanisms
browser tooling
observability tooling
```

For many public APIs and CRUD-heavy applications, that's a huge advantage.

---

# 5. REST's Weakness

Suppose your mobile dashboard needs:

```text
User
+
latest 5 orders
+
unread notifications
+
profile image
```

You might need:

```text
GET /users/123
GET /users/123/orders?limit=5
GET /users/123/notifications?status=unread
```

Potentially:

```text
3 HTTP requests
```

This can become inconvenient for clients.

---

# 6. Over-Fetching

Suppose:

```http
GET /users/123
```

returns:

```json
{
  "id": "123",
  "name": "Rahul",
  "email": "...",
  "phone": "...",
  "address": {...},
  "preferences": {...},
  "orders": [...],
  "notifications": [...]
}
```

But the mobile screen only needs:

```text
name
profile image
```

The client receives more data than necessary.

This is called:

> **Over-fetching**

---

# 7. Under-Fetching

The opposite problem:

```text
GET /users/123
```

returns only user data.

Then the client needs:

```text
orders
notifications
preferences
```

So it makes additional requests.

This is:

> **Under-fetching**

GraphQL was designed in part to address these kinds of client data-fetching problems.

---

# 8. RPC

RPC means:

> **Remote Procedure Call**

The API is designed around actions or procedures.

Instead of thinking:

```text
"What resource am I manipulating?"
```

you think:

```text
"What operation do I want to perform?"
```

For example:

```http
POST /api/v1/orders/123/cancel
```

The operation is:

```text
cancelOrder()
```

---

# 9. RPC Examples

Consider authentication.

REST-style:

```http
PATCH /users/123
```

```json
{
  "status": "disabled"
}
```

RPC-style:

```http
POST /users/123/disable
```

Or:

```http
POST /users/123/reset-password
```

Another:

```http
POST /payments/123/refund
```

The endpoint directly represents the business action.

---

# 10. Why RPC Can Be Excellent

Some business operations aren't naturally CRUD.

Consider:

```text
capturePayment()
refundPayment()
approveLoan()
cancelSubscription()
generateInvoice()
sendVerificationEmail()
rotateApiKey()
```

Trying to represent every operation as:

```text
PATCH /resource
```

can become awkward.

RPC makes the business intent explicit.

---

# 11. REST vs RPC Example

Imagine:

```text
Cancel order
```

REST-ish:

```http
PATCH /orders/123
```

```json
{
  "status": "cancelled"
}
```

RPC:

```http
POST /orders/123/cancel
```

The RPC endpoint clearly communicates:

> "Execute the cancellation operation."

That's especially useful when cancellation involves:

```text
refund payment
release inventory
cancel shipment
send notification
```

It's more than simply changing a database field.

---

# 12. RPC Isn't Automatically Non-RESTful

This is an important interview nuance.

People sometimes say:

> "RPC and REST are completely opposite."

That's too simplistic.

HTTP APIs can contain action-oriented endpoints while still using HTTP semantics sensibly.

The more useful distinction is:

```text
REST
resource-oriented design

RPC
operation-oriented design
```

Think of them as different design emphases.

---

# 13. GraphQL

GraphQL is different.

Instead of the server deciding exactly what representation each endpoint returns, the client sends a query describing what it needs.

For example:

```graphql
query {
  user(id: "123") {
    name
    email
  }
}
```

The server returns:

```json
{
  "data": {
    "user": {
      "name": "Rahul",
      "email": "..."
    }
  }
}
```

---

# 14. GraphQL's Core Idea

Think:

```text
REST
Server decides response shape

GraphQL
Client specifies response shape
```

That's the fundamental difference.

---

# 15. GraphQL Query Example

Suppose the client wants:

```text
User
 ├── name
 ├── email
 └── orders
      ├── id
      └── total
```

GraphQL:

```graphql
query {
  user(id: "123") {
    name
    email
    orders {
      id
      total
    }
  }
}
```

The client doesn't need separate endpoints for each piece of related data.

---

# 16. GraphQL Can Reduce Over-Fetching

Suppose the server has:

```text
User
 ├── id
 ├── name
 ├── email
 ├── phone
 ├── address
 ├── preferences
 └── ...
```

Client only requests:

```graphql
{
  user {
    name
  }
}
```

The response contains only:

```json
{
  "data": {
    "user": {
      "name": "Rahul"
    }
  }
}
```

That's powerful for clients with different data requirements.

---

# 17. GraphQL Can Reduce Under-Fetching

Instead of:

```text
GET /users/123
GET /users/123/orders
GET /users/123/notifications
```

you can query:

```graphql
query {
  user(id: "123") {
    name
    orders {
      id
    }
    notifications {
      id
    }
  }
}
```

One logical query.

But this does **not** mean:

> GraphQL always means one network request and REST always means many.

That's too simplistic.

REST APIs can also provide aggregation endpoints, and GraphQL queries can be internally expensive.

---

# 18. GraphQL's Major Advantage

GraphQL is particularly attractive when:

```text
many different clients
different UI requirements
deeply related data
rapid frontend development
mobile bandwidth concerns
```

For example:

```text
Web
Mobile
Tablet
Admin Dashboard
```

may all need different subsets of the same domain data.

---

# 19. GraphQL's Major Complexity

The client can ask for complicated queries.

For example:

```graphql
user {
  orders {
    products {
      reviews {
        author {
          orders {
            ...
          }
        }
      }
    }
  }
}
```

If the backend doesn't control query complexity, this can become expensive.

Therefore GraphQL often requires:

```text
query depth limits
query complexity analysis
pagination
timeouts
rate limiting
field-level authorization
careful resolver design
```

---

# 20. The N+1 Problem in GraphQL

This is one of the most important GraphQL interview topics.

Suppose:

```graphql
query {
  users {
    id
    orders {
      id
    }
  }
}
```

There are:

```text
100 users
```

A naive resolver might execute:

```text
1 query → users

100 queries → orders for each user
```

Total:

```text
101 database queries
```

That's the:

> **N+1 problem**

---

# 21. DataLoader

A common solution is batching.

Instead of:

```text
User 1 → query orders
User 2 → query orders
User 3 → query orders
...
```

batch them:

```text
Users
  ↓
collect IDs
  ↓
one query
  ↓
orders for all users
```

Conceptually:

```text
100 individual queries
        ↓
1 batched query
```

Tools such as DataLoader are commonly used for this pattern.

The important interview point isn't the library.

It's:

> **GraphQL's flexible nested queries require careful resolver/data-access design to avoid N+1 problems.**

---

# 22. REST Caching Advantage

HTTP caching is one of REST's major strengths.

You can have:

```http
GET /products/123
```

with headers such as:

```http
Cache-Control: ...
ETag: ...
```

CDNs and HTTP caches understand these concepts.

This makes standard HTTP caching relatively natural.

---

# 23. GraphQL Caching Is More Complicated

GraphQL often uses:

```http
POST /graphql
```

and the actual data requirements live inside the request body.

Traditional HTTP caching becomes less straightforward.

You can still build sophisticated caching strategies, but:

```text
cache key
query shape
variables
authorization
field-level data
```

can make caching more complex.

So:

> **GraphQL's flexibility can come at the cost of simpler HTTP caching semantics.**

---

# 24. REST and CDN

REST is particularly convenient for:

```text
GET /products
GET /products/123
GET /images/123
```

because CDNs understand URLs naturally.

For public or semi-public read-heavy data, this can be very useful.

---

# 25. GraphQL and Authorization

REST often has authorization at the endpoint level:

```text
GET /users/123
```

Maybe:

```text
user:read
```

GraphQL can require authorization deeper inside the query.

For example:

```graphql
user {
  name
  salary
  privateNotes
}
```

You may need:

```text
Can user access user?
       ↓
Can user access salary?
       ↓
Can user access privateNotes?
```

This can become more complex.

---

# 26. REST Error Handling

REST naturally uses HTTP status codes:

```text
200 OK
201 Created
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests
500 Internal Server Error
```

Clients can reason about these using standard HTTP semantics.

---

# 27. GraphQL Error Model

GraphQL commonly returns a structure such as:

```json
{
  "data": {
    "user": null
  },
  "errors": [
    {
      "message": "..."
    }
  ]
}
```

Notice something important:

The HTTP request itself can succeed while the GraphQL response contains application-level errors.

This is a different mental model from traditional REST APIs.

---

# 28. Partial Data

GraphQL can return:

```json
{
  "data": {
    "user": {
      "name": "Rahul",
      "orders": null
    }
  },
  "errors": [
    {
      "message": "Orders service unavailable"
    }
  ]
}
```

You can potentially receive:

```text
some data
+
some errors
```

This can be powerful.

But clients need to understand the semantics properly.

---

# 29. Versioning

REST APIs often use:

```text
/api/v1
/api/v2
```

or another versioning strategy.

GraphQL usually emphasizes evolving a schema while maintaining compatibility.

You might:

```text
add fields
deprecate old fields
```

rather than creating:

```text
/graphql/v2
```

for every schema change.

This can reduce explicit versioning pressure.

But GraphQL doesn't magically eliminate compatibility concerns.

---

# 30. GraphQL Deprecation

A field can be marked as deprecated.

Conceptually:

```graphql
type User {
  name: String
  oldName: String @deprecated(reason: "Use name")
}
```

Clients can migrate gradually.

That's a useful advantage for evolving APIs with many consumers.

---

# 31. REST's Simplicity

For a typical MERN application:

```text
Users
Products
Orders
Posts
Comments
```

REST is often a very sensible choice.

Example:

```text
GET /users
GET /users/:id

GET /products
GET /products/:id

GET /orders
GET /orders/:id

POST /orders
PATCH /orders/:id
```

Simple.

Easy to:

```text
test
debug
document
monitor
understand
```

Don't choose GraphQL just because it's more advanced.

---

# 32. RPC's Strength in Internal Services

RPC can be particularly attractive for internal service-to-service communication.

For example:

```text
Order Service
      ↓
Payment Service
```

Operations might be:

```text
AuthorizePayment
CapturePayment
RefundPayment
GetPaymentStatus
```

These are naturally actions.

Protocols such as gRPC are commonly used for this kind of communication.

---

# 33. REST vs RPC for Internal APIs

Imagine:

```text
Order Service
```

needs:

```text
reserveInventory()
```

RPC:

```text
ReserveInventory(...)
```

is very natural.

REST might be:

```http
POST /inventory/reservations
```

Both can work.

The choice depends on:

```text
service architecture
language ecosystem
performance
tooling
team familiarity
contract requirements
```

---

# 34. gRPC

gRPC is an RPC framework commonly associated with:

```text
Protocol Buffers
HTTP/2
strongly typed contracts
code generation
streaming
```

Example conceptual service:

```proto
service PaymentService {
  rpc CapturePayment(CapturePaymentRequest)
      returns (CapturePaymentResponse);
}
```

This gives you a strongly typed contract between services.

---

# 35. Why gRPC Can Be Attractive

For internal services:

```text
strong typing
generated clients
compact binary serialization
streaming support
clear service contracts
```

can be very useful.

Especially when:

```text
service-to-service traffic
high throughput
polyglot services
strong contracts
```

matter.

---

# 36. Why gRPC Isn't Always Ideal for Public APIs

Public APIs often need:

```text
browser compatibility
easy debugging
simple HTTP tooling
human-readable requests
wide client support
```

REST/JSON can be easier for these cases.

gRPC-Web and other technologies exist, but they add more considerations.

Again:

> **Choose based on consumers.**

---

# 37. REST vs GraphQL vs RPC

Here's the high-level comparison:

|Feature|REST|RPC|GraphQL|
|---|---|---|---|
|Main abstraction|Resources|Operations|Data/query graph|
|Typical style|HTTP|Procedure calls|Query language|
|Client controls fields|Limited|Usually limited|Strong|
|HTTP semantics|Strong|Can be strong|Less central to data semantics|
|CRUD|Excellent|Possible|Excellent|
|Business actions|Good|Excellent|Possible|
|Flexible nested data|Moderate|Depends|Excellent|
|HTTP caching|Excellent fit|Depends|More complex|
|Typed contract|OpenAPI/etc.|Often strong|Strong schema|
|Learning curve|Low|Moderate|Moderate/high|
|Query complexity risk|Lower|Depends|Higher|
|N+1 risk|Possible|Possible|Common concern|
|Browser friendliness|Excellent|Depends|Excellent|
|Internal services|Good|Excellent|Possible|
|Public APIs|Excellent|Possible|Excellent in suitable cases|

Don't memorize the table blindly.

Understand **why** the differences exist.

---

# 38. When I'd Choose REST

I'd strongly consider REST when:

```text
CRUD dominates
public API
simple clients
HTTP caching matters
CDN usage matters
easy debugging matters
resources map naturally to domain
```

For example:

```text
e-commerce API
blog API
student management API
inventory CRUD API
```

---

# 39. When I'd Choose RPC

I'd consider RPC when:

```text
operation-oriented domain
internal services
strongly typed contracts
high-performance service communication
streaming
generated clients
```

Examples:

```text
payment service
inventory service
machine-learning inference service
internal platform APIs
```

---

# 40. When I'd Choose GraphQL

I'd consider GraphQL when:

```text
many clients
different UI data requirements
deeply related data
frontend needs flexible field selection

rapid schema evolution
```

For example:

```text
large product
multiple frontend clients
complex dashboards
social application
```

---

# 41. Can You Use More Than One?

Absolutely.

A mature architecture may use:

```text
                    API Gateway
                        │
              ┌─────────┼─────────┐
              ▼         ▼         ▼
            REST      GraphQL    BFF
              │         │
              └────┬────┘
                   ▼
             Internal Services
                   │
                  RPC
```

For example:

```text
Public API → REST
Frontend aggregation → GraphQL
Internal service communication → gRPC
```

This can be a very reasonable architecture.

---

Don't design:

```text

+

+

```

just because you can.

Every technology adds:


# 47. Interview Scenario

Interviewer:

> "Your MERN application currently uses REST. Why wouldn't you immediately migrate it to GraphQL?"

Strong answer:

> "Because GraphQL solves specific client data-fetching problems; it isn't automatically an improvement over REST. If our current REST APIs are simple, cacheable, easy to consume, and meeting client requirements, migration would add unnecessary complexity. I'd consider GraphQL if we have significant over-fetching, under-fetching, multiple clients with very different data requirements, or complex nested data needs."

Excellent.

---

# 48. Interview Scenario

Interviewer:

> "Would you use REST or gRPC between microservices?"

Strong answer:

> "I'd consider gRPC when strong contracts, generated clients, efficient service-to-service communication, or streaming are important. REST can still be a good choice when simplicity, HTTP compatibility, easier debugging, or broad tooling matter. I wouldn't choose solely based on performance benchmarks; operational complexity and team needs matter too."

---

# 49. Interview Scenario

Interviewer:

> "Why not use GraphQL everywhere?"

Answer:

> "GraphQL gives clients powerful query flexibility, but that also introduces query-complexity, authorization, caching, resolver performance, and N+1 concerns. For straightforward CRUD APIs, REST may be simpler and easier to operate. I'd use GraphQL where its flexible data-fetching model provides enough value to justify those costs."

---

# 🧠 Lesson 16.17 — Revision Sheet

Remember these **18 points**:

1. **REST** is primarily resource-oriented.
    
2. **RPC** is primarily operation-oriented.
    
3. **GraphQL** lets clients specify the data they need.
    
4. REST works naturally with HTTP semantics.
    
5. REST is often excellent for CRUD and public APIs.
    
6. RPC is especially natural for business commands and internal service communication.
    
7. GraphQL is useful when clients have different and complex data requirements.
    
8. REST can suffer from over-fetching and under-fetching.
    
9. GraphQL reduces these problems but introduces query-complexity concerns.
    
10. GraphQL has a common **N+1 resolver problem**.
    
11. DataLoader/batching is a common solution to N+1.
    
12. HTTP caching is generally more straightforward with REST.
    
13. GraphQL caching can be more complicated because queries determine the requested data.
    
14. REST commonly uses HTTP status codes as part of its error contract.
    
15. GraphQL commonly represents errors in its response structure and can return partial data.
    
16. gRPC/RPC can provide strongly typed, generated service contracts.
    
17. You can use **REST + GraphQL + RPC together** when there is a real architectural reason.
    
18. **Never choose an API style because it is fashionable—choose it because its trade-offs fit the requirements.**
    

---

# 🔥 The Gold Interview Answer

If an interviewer asks:

> **"REST, GraphQL, or RPC—which one is best?"**

Your answer should be:

> **"There isn't a universally best option. I'd choose based on the consumers and the communication pattern. REST is a strong default for resource-oriented public APIs and HTTP caching. GraphQL is attractive when clients need flexible, nested data and different clients have different requirements. RPC is useful for operation-oriented or internal service-to-service communication where strong contracts and efficient communication are important. I would also consider operational complexity, authorization, caching, observability, and team expertise before choosing."**

That's the answer I want you to be able to give naturally in an interview.
