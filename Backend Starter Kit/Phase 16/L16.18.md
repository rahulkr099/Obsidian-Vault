# Phase 16 — API Architecture & Production Contracts

## Lesson 16.18 — API Rate Limiting & Quotas

This is a **gold-level backend interview topic** because rate limiting sits at the intersection of:

```text
API Design
   ↓
Security
   ↓
Performance
   ↓
Redis
   ↓
Distributed Systems
   ↓
Reliability
```

An interviewer may start with:

> "What is rate limiting?"

and quickly move to:

> "How would you implement it across multiple Node.js servers?"

That's where this lesson becomes important.

---

# 1. What Is Rate Limiting?

**Rate limiting controls how many requests a client can make during a given period.**

For example:

```text
100 requests / minute / user
```

or:

```text
10 login attempts / minute / IP
```

or:

```text
10,000 API requests / day / API key
```

The purpose is to prevent one client from consuming an unreasonable amount of system resources.

---

# 2. Why Do We Need Rate Limiting?

Without rate limiting:

```text
Client
  │
  │ 10,000 requests/sec
  ▼
API Server
  │
  ▼
Database
```

The client may consume:

```text
CPU
memory
database connections
network bandwidth
external API quota
```

Eventually:

```text
normal users
     ↓
get slower
     ↓
timeouts
     ↓
service outage
```

Rate limiting protects the system.

---

# 3. Rate Limiting Is Not Just Security

People often think:

> "Rate limiting is only for preventing attackers."

Not true.

It provides several benefits:

### Security

Helps reduce:

```text
brute-force attempts
credential attacks
API abuse
automated scraping
```

### Reliability

Protects backend resources from overload.

### Fairness

Prevents one client from monopolizing resources.

### Cost control

Important when your backend calls paid APIs.

For example:

```text
Your API
   ↓
OpenAI / payment / maps / email provider
```

If one user causes 1 million requests, your external bill could increase dramatically.

---

# 4. Basic Example

Suppose:

```text
100 requests / minute
```

A client makes:

```text
1
2
3
...
100
```

Request 101:

```http
429 Too Many Requests
```

The client should understand:

> "You have exceeded your allowed request rate."

---

# 5. HTTP 429

The standard HTTP status code is:

```http
429 Too Many Requests
```

Example:

```http
HTTP/1.1 429 Too Many Requests
```

Response:

```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Too many requests"
  }
}
```

---

# 6. Retry-After

You can also tell the client when it should retry.

Example:

```http
Retry-After: 30
```

Meaning approximately:

> Retry after 30 seconds.

This is extremely useful for well-behaved clients.

---

# 7. Rate Limit vs Quota

These concepts are related but not identical.

### Rate limit

Controls **how quickly** requests can happen.

Example:

```text
100 requests / minute
```

### Quota

Controls **how much total usage** is allowed over a longer period.

Example:

```text
10,000 requests / day
```

Think:

```text
Rate limit
→ speed

Quota
→ total allowance
```

---

# 8. Example

Suppose an API key has:

```text
100 requests/minute
10,000 requests/day
```

The client could hit:

```text
101 requests in one minute
```

and receive:

```text
429
```

Even though the daily quota hasn't been exhausted.

Later, it could make:

```text
10,000 requests throughout the day
```

and reach its daily quota.

These are separate controls.

This is an important design decision.

Possible identifiers:

```text

Access token

```

Sometimes you need multiple dimensions.

For example:


---

# 10. IP-Based Rate Limiting

Example:

```text
100 requests/minute/IP
```

Advantages:

```text
simple
works before authentication
useful against anonymous abuse
```

But IP addresses aren't perfect identities.

---

# 11. Why IP Isn't a Perfect Identifier

Multiple users may share one public IP.

For example:

```text
College Wi-Fi
     │
     ├── Student A
     ├── Student B
     ├── Student C
     └── Student D
```

If you enforce:

```text
100 requests/minute/IP
```

all four users share the same bucket.

One aggressive user could affect everyone.

---

# 12. NAT

This happens because many devices can appear to the internet using one public IP address.

Therefore:

> **IP-based limits should be used carefully.**

They're useful, but they shouldn't automatically be treated as the user's true identity.

---

# 13. User-Based Rate Limiting

For authenticated users:

```text
1000 requests/hour/user
```

You might use:

```text
userId
```

as the rate-limit key.

Example:

```text
user:123
```

Advantages:

```text
better fairness
works across changing IPs
natural for authenticated APIs
```

---

# 14. API-Key-Based Limiting

For developer APIs:

```text
api_key:abc123
```

might have:

```text
10,000 requests/day
```

This is often more appropriate than IP-based limiting.

For example:

```text
Free plan
→ 1,000 requests/day

Pro
→ 100,000 requests/day

Enterprise
→ custom
```

Now rate limiting becomes part of the API's business model.

---

# 15. Endpoint-Specific Limits

Not all endpoints cost the same.

Consider:

```text
GET /products
```

versus:

```text
POST /auth/login
```

versus:

```text
POST /reports/generate
```

They should not necessarily have the same limit.

---

# 16. Different Cost Profiles

For example:

```text
GET /products
→ 1000/minute

GET /users/:id
→ 500/minute

POST /auth/login
→ 10/minute

POST /reports/generate
→ 5/minute
```

Why?

Because:

```text
report generation
```

might consume significantly more resources.

---

# 17. Authentication Rate Limiting

Login endpoints deserve special treatment.

Imagine an attacker tries:

```text
password1
password2
password3
...
password100000
```

This is a brute-force attack.

Rate limiting can reduce the attack speed:

```text
5 login attempts / minute
```

But don't rely on rate limiting alone.

You may also use:

```text
account lockout strategy
progressive delays
MFA
bot detection
IP reputation
credential breach detection
```

---

# 18. Important Security Principle

Don't create a rule like:

```text
5 failed attempts
→ permanently lock account
```

without considering denial-of-service abuse.

An attacker could intentionally fail someone else's login repeatedly and lock them out.

Security controls themselves can sometimes become attack vectors.

This is why rate-limit design needs careful thought.

---

# 19. The Simplest Algorithm: Fixed Window

Suppose:

```text
100 requests / minute
```

Divide time into fixed windows:

```text
12:00:00 ───── 12:00:59
12:01:00 ───── 12:01:59
```

Maintain:

```text
counter
```

For example:

```text
12:00 window
count = 75
```

Request:

```text
count = 76
```

Once the window expires:

```text
count = 0
```

---

# 20. Fixed Window Example

Suppose limit:

```text
100 requests/minute
```

A client sends:

```text
100 requests at 12:00:59
```

Then:

```text
100 requests at 12:01:00
```

Technically:

```text
200 requests
```

arrived within roughly:

```text
2 seconds
```

This is called the:

> **Boundary burst problem**

---

# 21. Fixed Window Advantages

```text
simple
cheap
easy to understand
easy to implement
easy to distribute with Redis
```

For many applications, it can be good enough.

---

# 22. Fixed Window Disadvantages

Main problem:

```text
traffic can spike around boundaries
```

For high-value APIs, this may be undesirable.

---

# 23. Sliding Window

Instead of fixed blocks:

```text
12:00:00–12:00:59
```

we look at the previous rolling period.

For every request at:

```text
12:01:20
```

we ask:

> How many requests did this client make during the previous 60 seconds?

This is a:

> **Sliding Window**

---

# 24. Sliding Window Example

At:

```text
12:01:20
```

consider:

```text
12:00:20 → 12:01:20
```

If:

```text
requests = 100
```

reject the next request.

When older requests leave the window, capacity becomes available.

This gives smoother behavior.

---

# 25. Sliding Window Advantage

Compared with fixed windows:

```text
less boundary bursting
more accurate rate control
```

But it generally requires more state and computation.

---

# 26. Sliding Window Log

One straightforward implementation stores timestamps:

```text
user:123
[
  12:00:21,
  12:00:24,
  12:00:28,
  ...
]
```

For a new request:

```text
remove timestamps older than 60 sec
count remaining
```

If:

```text
count < 100
```

allow.

Otherwise:

```text
429
```

---

# 27. Problem With Sliding Window Log

Suppose a busy client makes:

```text
10,000 requests
```

You may have to store many timestamps.

Memory usage can become expensive.

So implementations often use more efficient algorithms.

---

# 28. Token Bucket

This is one of the most important algorithms to understand.

Imagine a bucket containing tokens.

```text
Bucket
┌─────────────┐
│ ● ● ● ● ●   │
│ ● ● ●       │
└─────────────┘
```

Every request consumes:

```text
1 token
```

Tokens are replenished at a fixed rate.

---

# 29. Token Bucket Example

Suppose:

```text
bucket capacity = 100 tokens
refill rate = 10 tokens/sec
```

A client can immediately make:

```text
100 requests
```

if the bucket is full.

Then tokens are consumed.

Afterward:

```text
10 tokens/sec
```

become available.

This allows controlled bursts.

---

# 30. Why Token Bucket Is Powerful

It supports:

```text
controlled bursts
+
long-term rate control
```

For example:

```text
capacity = 100
refill = 10/sec
```

means:

> The client can burst up to 100 requests, but sustained traffic is limited around 10 requests/sec.

That's often more useful than a rigid fixed window.

---

# 31. Token Bucket Mental Model

Think:

```text
                refill
                  ↓
             ┌─────────┐
             │ TOKENS   │
             │ ● ● ● ●  │
             └────┬────┘
                  │
                  ▼
               Request
                  │
            consume token
                  │
          ┌───────┴───────┐
          ▼               ▼
       token exists    no token
          │               │
       allow             429
```

---

# 32. Leaky Bucket

Another algorithm is:

> **Leaky Bucket**

Imagine requests entering a queue:

```text
Requests
   ↓
┌────────────┐
│ █ █ █ █ █  │
└─────┬──────┘
      │
      ▼
 fixed output rate
```

Requests leave at a controlled rate.

This smooths traffic.

---

# 33. Token Bucket vs Leaky Bucket

### Token Bucket

Good for:

```text
controlled bursts
```

### Leaky Bucket

Good for:

```text
smooth output
```

Mental model:

```text
Token bucket
→ "You can burst if you have tokens."

Leaky bucket
→ "I'll process traffic at a controlled rate."
```

---

# 34. Which Algorithm Should You Choose?

There is no universal answer.

### Fixed window

Choose when:

```text
simplicity matters
requirements are modest
```

### Sliding window

Choose when:

```text
more accurate rolling limits matter
```

### Token bucket

Choose when:

```text
bursts are acceptable
but sustained rate must be controlled
```

### Leaky bucket

Choose when:

```text
smooth processing/output is important
```

---

# 35. Interview Question

> "Which rate-limiting algorithm would you use?"

Don't say:

> "Token bucket because it's best."

Say:

> "I'd choose based on the traffic pattern. For an API where short bursts are acceptable but sustained traffic needs to be controlled, token bucket is a strong option. For a simpler API, fixed-window limiting may be sufficient. If precise rolling-window behavior is important, I'd consider a sliding-window approach."

Excellent.

```js
app.use(rateLimiter);
```

```text
 ┌─┴──────┐

 ↓         ↓

```

# 37. The Critical Question

Where do you store the counters?

If you have one Node.js server:

```text
memory
```

might work.

For example:

```js
const limits = new Map();
```

But this becomes a problem in production.

---

# 38. Why In-Memory Rate Limiting Fails at Scale

Suppose:

```text
              Load Balancer
               /         \
              /           \
        Server A          Server B
```

Server A has:

```text
user123 → 90 requests
```

Server B has:

```text
user123 → 90 requests
```

The user can potentially make:

```text
180 requests
```

even though the intended limit was:

```text
100
```

Each server has its own counter.

---

# 39. Distributed Rate Limiting

For multiple application servers:

```text
              Load Balancer
              /           \
             ▼             ▼
         Node A          Node B
             \             /
              \           /
                Redis
```

Now all servers share rate-limit state.

For example:

```text
user:123 → 87
```

is stored centrally.

This is why Redis is commonly used.

---

# 40. Why Redis?

Redis is useful because it provides:

```text
fast reads/writes
atomic operations
TTL/expiration
shared state
high throughput
```

These are exactly the properties a rate limiter needs.

---

# 41. Basic Redis Fixed-Window Idea

Conceptually:

```text
INCR rate:user123
EXPIRE rate:user123 60
```

First request:

```text
count = 1
```

Second:

```text
count = 2
```

Eventually:

```text
count = 100
```

Next request:

```text
count = 101
```

→ reject.

---

# 42. But There's a Race Condition

Consider:

```text
INCR
EXPIRE
```

as separate operations.

Multiple servers could interact with the key at nearly the same time.

You need to think carefully about:

```text
atomicity
expiration
concurrency
```

Redis Lua scripts or appropriate atomic commands/transactions can help make the operation reliable.

This is a very good interview detail.

---

# 43. Redis Atomicity

The important idea isn't:

> "Use Redis."

The important idea is:

> **The decision to increment/check the limit should be consistent under concurrency.**

Otherwise:

```text
Server A checks
Server B checks
Server A increments
Server B increments
```

can produce unexpected results.

Distributed rate limiting is fundamentally a concurrency problem.

---

# 44. Redis Key Design

You might use:

```text
rate:user:123
```

or:

```text
rate:ip:192.0.2.1
```

or:

```text
rate:apikey:abc123
```

For endpoint-specific limits:

```text
rate:user:123:login
```

or:

```text
rate:user:123:report-generation
```

The key should reflect the identity and scope of the limit.

Conceptually:

```text
  │
  ├── IP limit ───────┐
```

# 46. Hierarchical Rate Limiting

You might have:

```text

  ↓

  ↓
```

For example:

```text

1000 requests/hour
```

This is much closer to how production API platforms can work.

# 47. Fairness

Imagine one organization has:

```text
10,000 users
```

and another has:

```text
1 user
```

If both receive:

```text
1000 requests/minute
```

you might not be allocating resources fairly.

Instead you could have:

```text
Free plan
→ 10 req/sec

Pro
→ 100 req/sec

Enterprise
→ custom
```

Rate limiting can therefore become part of **resource allocation**.

# 48. Rate Limit Headers

You can expose information to clients.

For example:

```http
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 42
X-RateLimit-Reset: 1720000000
```

The exact header conventions can vary by API design.

The idea is:

```text
Limit
Remaining
Reset time
```

This helps clients behave intelligently.

---

# 49. Why Expose Remaining Capacity?

Suppose a frontend knows:

```text
remaining = 2
```

It can avoid making unnecessary requests.

Similarly, SDKs can implement:

```text
backoff
retry scheduling
request batching
```

instead of blindly hammering the API.

---

# 50. Retry Strategy

When clients receive:

```http
429 Too Many Requests
```

they shouldn't immediately retry thousands of times.

That creates:

```text
request
 ↓
429
 ↓
retry
 ↓
429
 ↓
retry
 ↓
429
```

This can make the situation worse.

---

# 51. Exponential Backoff

A common strategy:

```text
retry after:
1 sec
2 sec
4 sec
8 sec
16 sec
```

with some random jitter.

Conceptually:

```text
delay = base * 2^attempt
```

Then add randomness:

```text
delay + jitter
```

This prevents many clients from retrying at exactly the same moment.

---

# 52. Retry Storm

Imagine 10,000 clients all receive:

```text
Retry-After: 10
```

and all retry exactly at:

```text
10 seconds
```

You could get:

```text
                retry storm
                    ↓
10,000 requests simultaneously
                    ↓
                  server
                    ↓
                  overload
```

Jitter helps spread them out.

---

# 53. Rate Limiting vs DDoS Protection

Important distinction.

Rate limiting:

```text
application-level control
```

DDoS protection:

```text
network/infrastructure-level defense
```

Your Express middleware cannot magically stop a massive volumetric attack that overwhelms your network before traffic reaches your server.

For large attacks you may need:

```text
CDN
WAF
cloud edge protection
load balancer
network-level mitigation
```

Rate limiting is one layer.

# 55. Rate Limiting and Authentication

Where should rate limiting happen?

Potentially:

```text
Before authentication
```

for:

```text
IP protection
```

and:

```text
After authentication
```

for:

```text
user/API-key limits
```

Often you want both.

---

# 56. Important Login Design

For:

```http
POST /auth/login
```

you might consider:

```text
IP-based limit
+
account/user-based protection
+
failed-attempt tracking
+
progressive delays
```

Why both?

Because:

```text
IP-only
```

can be bypassed through many IPs.

And:

```text
user-only
```

can allow attackers to target many accounts.

Layered controls are stronger.

---

# 57. Rate Limiting and Proxies

Here's a common Node.js production problem.

Your application may receive:

```text
req.ip
```

from a reverse proxy.

If your proxy configuration is wrong, every request might appear to come from:

```text
127.0.0.1
```

Then your IP-based limiter thinks:

```text
everyone = same IP
```

That's disastrous.

You need correct proxy/trust configuration and careful handling of forwarded IP information.

---

# 58. Never Blindly Trust Client Headers

A malicious client may send:

```http
X-Forwarded-For: fake-ip
```

If your infrastructure doesn't establish the trusted proxy chain correctly, using this header blindly can allow attackers to bypass IP-based rate limits.

Important principle:

> **Only trust proxy-provided identity information when your infrastructure is configured to establish that trust.**

Think about expensive operations:

```text

```

You might define:

```text

20 requests/minute

10 requests/hour

```

The limit should reflect **cost and abuse potential**.

# 60. Cost-Based Rate Limiting

An advanced approach assigns different costs.

For example:

```text
GET /products
cost = 1

GET /analytics
cost = 10

POST /generate-report
cost = 50
```

A user may receive:

```text
1000 tokens
```

instead of simply:

```text
1000 requests
```

Then:

```text
cheap operation
→ consumes 1

expensive operation
→ consumes 50
```

This is more expressive for APIs with very different endpoint costs.

---

# 61. Rate Limiting for AI APIs

This is especially useful in modern backend systems.

Suppose:

```text
POST /ai/generate
```

may consume:

```text
tokens
GPU time
external API credits
```

A simple:

```text
100 requests/minute
```

may not accurately represent cost.

You could instead limit:

```text

```

or:

```text

```

This is an excellent system-design discussion point.

A production response might be:

```http

```

```json

  "error": {
```

# 63. What Happens When Redis Is Down?

This is a **gold interview question**.

Suppose:

```text
Application
     ↓
Redis
     X
   DOWN
```

What do you do?

Possible policies:

### Fail open

Allow requests.

```text
Redis unavailable
→ don't enforce rate limit
```

Advantages:

```text
availability
```

Risk:

```text
abuse can increase
```

### Fail closed

Reject requests.

```text
Redis unavailable
→ reject
```

Advantages:

```text
strong protection
```

Risk:

```text
entire API may become unavailable
```

---

# 64. Which One Should You Choose?

Depends on endpoint.

For:

```text
login
OTP
password reset
expensive AI operation
```

you may prefer stronger protection.

For:

```text
low-risk public product reads
```

availability may matter more.

The correct interview answer is:

> **"I'd choose fail-open or fail-closed based on the endpoint's risk and availability requirements rather than applying one global policy."**

Excellent.

# 65. Local + Distributed Rate Limiting

You can combine:

```text
Node process local limiter
+
Redis distributed limiter
```

Why?

Local limiting can reject obvious bursts without making a Redis call for every request.

Then Redis provides the shared global limit.

Conceptually:

```text
Request
   ↓
Local check
   ↓
Redis check
   ↓
Application
```

This can improve efficiency, but introduces additional complexity.

# 69. Rate Limiting as a Dependency Protection Mechanism

Imagine:

```text
Your API
   ↓
Payment Provider
```

Provider allows:

```text
100 requests/sec
```

Your API has:

```text
10,000 clients
```

Without protection:

```text
10,000 clients
      ↓

      ↓
429 / failure
```

Your API should respect the downstream provider's limits.

This is sometimes called:

> **Backpressure / dependency protection**

### Rate limiter


```text

```

For example:

```text

 ↓

 ↓
Order Service
 ↓

 ↓

```

Both can be valuable.

# 71. A Production Architecture

# 74. Interview Design Question

### Interviewer:

> "How would you implement rate limiting for a Node.js API running on 10 servers?"

A strong answer:

> "I wouldn't keep the counters only in Node.js memory because each server would have its own state. I'd use a shared store such as Redis for distributed rate-limit state. The middleware would derive a key based on the appropriate identity, such as user ID, API key, or trusted client IP, then perform an atomic rate-limit operation with expiration. I'd return 429 with appropriate retry information when the limit is exceeded. For expensive endpoints I'd use separate policies, and for a high-scale system I'd consider enforcing limits at the gateway or edge as well."

That's a very good interview answer.

---

# 75. Interview Follow-Up

Interviewer:

> "Why Redis?"

Answer:

> "Because rate limiting requires fast shared state with atomic operations and expiration. Redis provides those primitives and allows multiple application instances to enforce a common limit."

---

# 76. Interview Follow-Up

> "What if Redis goes down?"

Answer:

> "I'd define the failure policy based on the endpoint. For low-risk endpoints, failing open may preserve availability. For sensitive or expensive operations, failing closed or using a local fallback may provide better protection. The important part is making this an explicit availability-versus-abuse trade-off."

Excellent.

---

# 77. Interview Follow-Up

> "Which algorithm would you choose?"

Answer:

> "For a typical API where controlled bursts are acceptable, I'd consider token bucket. For a simple application, fixed window can be sufficient. If precise rolling-window semantics are important, I'd consider sliding-window approaches. The choice depends on traffic patterns, fairness requirements, memory cost, and implementation complexity."

---

# 78. Interview Follow-Up

> "Can rate limiting stop DDoS?"

Answer:

> "Application-level rate limiting helps control abusive request rates that reach the application, but it isn't a complete DDoS solution. Volumetric attacks need protection at the edge or network layer using CDN, WAF, load-balancing, and cloud DDoS mitigation."

Very important.

Creates inconsistent limits.

Ignores endpoint cost.

Can create retry storms.

False.

Can enable denial-of-service against users.

# 🧠 Lesson 16.18 — Interview Revision

Remember these **20 points**:

1. Rate limiting controls request frequency.
    
2. Quotas control total usage over a larger period.
    
3. `429 Too Many Requests` is the standard response for exceeded rate limits.
    
4. `Retry-After` can tell clients when to retry.
    
5. Rate limiting protects security, reliability, fairness, and cost.
    
6. Limits can be based on IP, user, API key, organization, or endpoint.
    
7. IP isn't always a reliable identity because of NAT/shared networks.
    
8. Authenticated APIs often benefit from user/API-key limits.
    
9. Different endpoints may require different limits.
    
10. Fixed window is simple but has boundary-burst problems.
    
11. Sliding window provides more precise rolling behavior.
    
12. Token bucket supports controlled bursts plus sustained rate control.
    
13. Leaky bucket is useful for smoothing output.
    
14. In-memory limiting doesn't provide a shared limit across multiple servers.
    
15. Redis is commonly used for distributed rate-limit state.
    
16. Distributed counters need careful atomicity/concurrency handling.
    
17. Exponential backoff + jitter helps prevent retry storms.
    
18. Rate limiting is not the same as DDoS protection.
    
19. Redis failure requires an explicit fail-open vs fail-closed policy.
    
20. **Production rate limiting is a policy + identity + algorithm + shared-state + failure-handling problem.**
