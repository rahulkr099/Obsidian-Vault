# Phase 16 — API Architecture & Production Contracts

## Lesson 16.19 — API Caching & Cache-Control

This is another **gold-level backend interview topic**.

A common interview question is:

> **"Your API suddenly receives 10× more read traffic. How would you reduce database load?"**

A strong answer often starts with:

> **Caching.**

But an interviewer may immediately ask:

- Where would you cache?
    
- What data should be cached?
    
- How long?
    
- What happens when data changes?
    
- What is an ETag?
    
- What does `304 Not Modified` mean?
    
- What is a cache stampede?
    
- Redis or CDN?
    
- How do you invalidate cached data?
    

Let's build this from fundamentals to production architecture.

---

# 1. What Is Caching?

Caching means:

> **Store frequently needed data somewhere faster so we don't have to recompute or retrieve it every time.**

Without caching:

```text
Client
  ↓
API
  ↓
Database
  ↓
Response
```

Every request hits the database.

With caching:

```text
Client
  ↓
API
  ↓
Cache
  │
  ├── HIT  → Response
  │
  └── MISS
       ↓
    Database
       ↓
     Cache
       ↓
    Response
```

The goal is:

```text
less database work
+
lower latency
+
higher throughput
```

---

# 2. Simple Example

Suppose:

```http
GET /api/v1/products
```

returns a product catalog.

Imagine:

```text
100,000 requests/minute
```

but the product list changes only:

```text
every 10 minutes
```

Without caching:

```text
100,000 DB reads/minute
```

With caching:

```text
1 DB read
+
99,999 cache responses
```

The difference can be enormous.

---

# 3. What Makes Good Cache Data?

Good candidates usually have:

```text
high read frequency
+
relatively low change frequency
+
expensive computation/database access
```

Examples:

```text
product catalog
public configuration
popular posts
category lists
permissions/configuration
expensive analytics
```

Poor candidates may include:

```text
highly personalized rapidly changing data
```

although even those can sometimes be cached with careful design.

---

# 4. Cache Is Not a Database

This distinction is extremely important.

Database:

```text
source of truth
```

Cache:

```text
temporary copy
```

Think:

```text
Database
   ↓
Source of Truth

Cache
   ↓
Performance Layer
```

If Redis disappears, your application should ideally be able to reconstruct the cache from the database.

---

# 5. Cache Hit

Suppose:

```text
GET /products
```

The cache contains:

```text
products:list
```

The request finds it.

That's a:

> **Cache hit**

```text
Request
   ↓
Cache
   ↓
FOUND
   ↓
Response
```

No database query is necessary.

---

# 6. Cache Miss

If:

```text
products:list
```

doesn't exist:

```text
Request
   ↓
Cache
   ↓
NOT FOUND
   ↓
Database
```

The application retrieves the data and often stores it in the cache.

```text
Database
   ↓
Cache
   ↓
Response
```

That's a:

> **Cache miss**

---

# 7. Cache Hit Ratio

One important metric:

```text
cache hit ratio =
cache hits / total cache requests
```

Suppose:

```text
1,000 requests
900 hits
100 misses
```

Then:

```text
hit ratio = 90%
```

A high hit ratio generally means the cache is doing useful work.

But:

> **A high cache hit ratio isn't automatically good if you're caching the wrong data.**

---

# 8. Where Can We Cache?

There are multiple layers.

```text
Client
  ↓
Browser Cache
  ↓
CDN
  ↓
Reverse Proxy
  ↓
Application Cache
  ↓
Redis
  ↓
Database
```

Each layer has different responsibilities.

---

# 9. Browser Cache

The browser can cache HTTP responses based on headers.

For example:

```http
Cache-Control: max-age=3600
```

means approximately:

> This response can be considered fresh for 3600 seconds.

This can eliminate a network request entirely while the cached response is fresh.

That's extremely powerful.

---

# 10. CDN Cache

A CDN can cache content closer to users.

Architecture:

```text
                    Origin
                      │
                      ▼
                 Your Server
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       CDN Edge    CDN Edge    CDN Edge
        India       Europe       US
```

A user can receive cached content from a nearby edge location.

This reduces:

```text
latency
origin traffic
database traffic
```

---

# 11. Redis Cache

Redis is commonly used as an application-level cache.

Architecture:

```text
Client
  ↓
Node.js
  ↓
Redis
  ↓
MongoDB
```

For your MERN stack, this is especially useful because:

```text
Node.js
+
Redis
+
MongoDB
```

is a very common production combination.

---

# 12. Three Different Caches

Don't think:

> "Caching means Redis."

There are different layers.

### HTTP/browser cache

```text
client-side
```

### CDN cache

```text
edge-side
```

### Redis/application cache

```text
server-side
```

A mature system may use all three.

---

# 13. Cache-Control

One of the most important HTTP headers:

```http
Cache-Control
```

Example:

```http
Cache-Control: max-age=3600
```

This tells caches how long the response can be considered fresh.

---

# 14. `max-age`

Example:

```http
Cache-Control: max-age=600
```

Means:

```text
fresh for 600 seconds
```

or:

```text
10 minutes
```

After that, the cache may need to revalidate or fetch a fresh response depending on the caching directives.

---

# 15. `public`

Example:

```http
Cache-Control: public, max-age=3600
```

This indicates the response may be stored by shared caches.

Useful for data that is safe to share among users.

For example:

```text
public product catalog
```

---

# 16. `private`

Example:

```http
Cache-Control: private, max-age=300
```

This tells shared caches not to store the response.

Useful for user-specific data.

For example:

```text
GET /me/profile
```

You generally don't want a CDN serving Rahul's profile to another user.

---

# 17. `no-store`

This is stronger:

```http
Cache-Control: no-store
```

It means:

> Don't store this response.

Useful for sensitive responses where caching is inappropriate.

For example, depending on your application:

```text
highly sensitive account information
security-sensitive responses
```

---

# 18. `no-cache`

This one causes confusion.

Many developers incorrectly think:

```http
Cache-Control: no-cache
```

means:

> "Don't cache this."

Not exactly.

`no-cache` generally means:

> **The cached response must be revalidated before being reused.**

Compare:

```text
no-store
→ don't store

no-cache
→ may store, but must revalidate before reuse
```

This distinction is a classic interview question.

---

# 19. Cache-Control Summary

|Directive|Meaning|
|---|---|
|`max-age=3600`|Fresh for 1 hour|
|`public`|Shared caches may store|
|`private`|Shared caches shouldn't store|
|`no-store`|Don't store|
|`no-cache`|Revalidate before reuse|
|`must-revalidate`|Must follow freshness/revalidation rules|

---

# 20. Example Express Response

You might send:

```js
res.set(
  "Cache-Control",
  "public, max-age=300"
);

res.json(products);
```

Meaning:

```text
public
+
cache for 5 minutes
```

This is an HTTP-level caching strategy.

---

# 21. ETag

Now we reach another important concept.

An:

> **ETag**

is a validator representing a particular version of a resource.

Example:

```http
ETag: "abc123"
```

The client caches the response.

Later it asks:

```http
If-None-Match: "abc123"
```

The server checks:

> Has the resource changed?

---

# 22. If Nothing Changed

Suppose the resource still has:

```text
ETag: "abc123"
```

The server can respond:

```http
304 Not Modified
```

No full response body is necessary.

This saves bandwidth.

---

# 23. ETag Flow

```text
First request
    ↓
GET /products
    ↓
200 OK
ETag: "abc123"
    ↓
Client caches response

Later:
    ↓
GET /products
If-None-Match: "abc123"
    ↓
Server checks resource
    ↓
unchanged
    ↓
304 Not Modified
```

The client can reuse its cached body.

---

# 24. Why 304 Is Powerful

Imagine the response is:

```text
5 MB
```

If nothing changed, sending the entire 5 MB again is wasteful.

Instead:

```http
304 Not Modified
```

can tell the client:

> Use your existing cached copy.

This saves:

```text
bandwidth
latency
server response work
```

---

# 25. ETag vs Cache-Control

They solve related but different problems.

### Cache-Control

Answers:

> **How long can I use this cached response without asking the server?**

### ETag

Answers:

> **Has this cached representation changed?**

Together:

```text
Cache-Control
      ↓
freshness

ETag
      ↓
validation
```

---

# 26. Last-Modified

Another validator is:

```http
Last-Modified
```

Example:

```http
Last-Modified: Wed, 26 Aug 2026 10:00:00 GMT
```

Client can later send:

```http
If-Modified-Since: Wed, 26 Aug 2026 10:00:00 GMT
```

If nothing changed:

```http
304 Not Modified
```

---

# 27. ETag vs Last-Modified

ETag can identify a specific representation/version more precisely.

`Last-Modified` relies on modification time.

For example:

```text
ETag
→ "version/hash"

Last-Modified
→ timestamp
```

ETags are often preferable when precise validation matters.

---

# 28. Redis Cache Pattern

Now let's move from HTTP caching to backend caching.

Suppose:

```http
GET /api/v1/products/123
```

Application logic:

```text
Request
  ↓
Redis GET product:123
  ↓
Found?
 ┌──────┴──────┐
yes            no
 ↓              ↓
return       MongoDB
                ↓
              Redis SET
                ↓
              return
```

This is commonly called:

> **Cache-aside**

---

# 29. Cache-Aside Pattern

The application controls the cache.

Pseudo-flow:

```js
const cached = await redis.get(key);

if (cached) {
  return JSON.parse(cached);
}

const product = await Product.findById(id);

await redis.set(key, JSON.stringify(product), {
  EX: 300
});

return product;
```

The important idea:

```text
read cache first
↓
miss
↓
read database
↓
populate cache
```

---

# 30. Why Cache-Aside Is Popular

Because it is relatively simple.

The database remains:

```text
source of truth
```

and Redis becomes:

```text
performance optimization
```

If Redis disappears:

```text
application
   ↓
MongoDB
```

still works, although more slowly.

---

# 31. Write Strategies

Caching gets more interesting when data changes.

Suppose:

```text
Product price = ₹100
```

Cache contains:

```text
₹100
```

Database is updated:

```text
₹120
```

What does Redis contain?

Potentially:

```text
₹100
```

Now you have:

> **Stale cache data**

---

# 32. Cache Invalidation

This is one of the hardest caching problems.

When data changes:

```text
Database
  ↓
new value
```

you need to decide what happens to:

```text
Cache
```

This is called:

> **Cache invalidation**

---

# 33. Cache-Aside Invalidation

Suppose:

```http
PATCH /products/123
```

updates the product.

After successful database update:

```text
MongoDB
   ↓
update successful
   ↓
Redis DEL product:123
```

Then the next read:

```text
GET /products/123
```

causes:

```text
cache miss
↓
MongoDB
↓
new value
↓
Redis
```

Simple and reliable.

---

# 34. Why Delete Instead of Update?

You could do:

```text
DB update
↓
Redis update
```

But now you have to keep two copies perfectly synchronized.

If:

```text
DB update succeeds
Redis update fails
```

you have inconsistency.

With cache-aside:

```text
DB update
↓
invalidate cache
```

the next read reconstructs the cache.

This is often simpler.

---

# 35. But Cache Invalidation Has Problems

Imagine:

```text
Request A
→ reads old data

Request B
→ updates database

Request A
→ writes old data into cache
```

Now your cache may contain stale information again.

This is why production caching can become complicated under concurrency.

---

# 36. TTL

A common safety mechanism is:

> **Time To Live**

Example:

```text
product:123
TTL = 300 seconds
```

After 5 minutes:

```text
key expires
```

Then the next request reloads the database.

TTL limits how long stale data can survive.

---

# 37. TTL Does Not Solve Everything

Suppose:

```text
TTL = 1 hour
```

and the product price changes after:

```text
5 minutes
```

The cache could still contain stale data for:

```text
55 minutes
```

Therefore:

> **TTL is a safety mechanism, not a complete invalidation strategy.**

For important data, explicit invalidation may still be needed.

---

# 38. Cache Stampede

This is a major interview topic.

Suppose:

```text
popular product
```

has cache entry:

```text
expires at 12:00
```

At 12:00:

```text
10,000 requests
```

arrive simultaneously.

All see:

```text
CACHE MISS
```

Then all hit MongoDB:

```text
10,000 DB queries
```

Your cache just expired and accidentally created a database spike.

This is:

> **Cache stampede**

also called:

> **Thundering herd**

---

# 39. Cache Stampede Diagram

```text
              10,000 requests
                    │
                    ▼
               Cache MISS
          ┌────┬────┬────┬────┐
          ▼    ▼    ▼    ▼    ▼
         DB   DB   DB   DB   DB
          └────┴────┴────┴────┘
                    │
                    ▼
                DB overload
```

This is a classic system-design problem.

---

# 40. Solution: Request Coalescing / Locking

Instead of allowing every request to query the database:

```text
First request
→ fetch database
```

Others wait.

Conceptually:

```text
Request 1
→ acquire lock
→ DB

Requests 2–9999
→ wait

DB result
→ populate cache

all requests
→ receive result
```

Only one request rebuilds the cache.

---

# 41. Redis Distributed Lock

In a multi-server architecture:

```text
Node A
Node B
Node C
```

you can use a Redis-based coordination mechanism so that only one instance refreshes a particular cache key at a time.

Conceptually:

```text
lock:product:123
```

Only one process should own the refresh lock.

Be careful, though: distributed locking has its own correctness and failure considerations.

Don't casually claim:

> "Redis lock solves everything."

---

# 42. Jittered TTL

Another technique:

Instead of:

```text
TTL = 300 sec
```

for thousands of keys simultaneously, use:

```text
TTL = 300 + random(0,60)
```

This spreads expirations.

Instead of:

```text
100,000 keys
↓
expire at exactly 12:00
```

you get:

```text
some expire at 12:00
some 12:01
some 12:02
...
```

This reduces synchronized cache misses.

---

# 43. Cache Avalanche

A cache avalanche happens when many cache entries become unavailable around the same time.

For example:

```text
100,000 keys
      ↓
same TTL
      ↓
expire simultaneously
      ↓
massive DB traffic
```

Jittered expiration is one mitigation.

Other options:

```text
staggered TTLs
warming
multi-level caching
request coalescing
```

---

# 44. Cache Penetration

Another problem:

A client requests data that doesn't exist:

```http
GET /products/nonexistent123
```

The cache misses.

Then:

```text
MongoDB
→ not found
```

If the attacker repeatedly requests random nonexistent IDs:

```text
abc1
abc2
abc3
abc4
...
```

every request may hit MongoDB.

That's:

> **Cache penetration**

---

# 45. Negative Caching

One solution is to temporarily cache "not found."

For example:

```text
product:abc123
→ NOT_FOUND
TTL = 30 seconds
```

Then repeated requests don't hit MongoDB.

But use a short TTL and be careful with semantics because an object could be created during that period.

---

# 46. Bloom Filters

At larger scale, a:

> **Bloom filter**

can help identify keys that definitely don't exist.

Conceptually:

```text
Request
   ↓
Bloom Filter
   │
   ├── definitely absent → reject early
   │
   └── possibly exists → continue
```

A Bloom filter can say:

```text
definitely not present
```

or:

```text
possibly present
```

It can have false positives but not false negatives under normal assumptions.

This is an advanced interview topic.

---

# 47. Cache Avalanche vs Stampede vs Penetration

Remember:

### Cache Stampede

```text
one key expires
↓
many requests miss
↓
many DB queries
```

### Cache Avalanche

```text
many keys expire/fail together
↓
massive DB load
```

### Cache Penetration

```text
requests repeatedly ask for nonexistent data
↓
cache can't help
↓
DB gets hammered
```

These three are often confused.

---

# 48. Cache-Aside vs Write-Through

Now let's discuss write strategies.

### Cache-aside

```text
Application
   ↓
Database
   ↓
invalidate cache
```

Reads populate cache.

### Write-through

```text
Application
   ↓
Cache
   ↓
Database
```

Writes update the cache and database as part of the caching layer's workflow.

The exact implementation varies.

---

# 49. Write-Through

Suppose:

```text
price = ₹100
```

Client updates:

```text
price = ₹120
```

Write-through concept:

```text
Application
   ↓
Cache
   ↓
Database
```

The cache is updated as part of the write path.

Advantage:

```text
cache stays warm
```

But:

```text
more complexity
```

and consistency/error handling become important.

---

# 50. Write-Back

Another pattern:

```text
Application
   ↓
Cache
   ↓
later → Database
```

The cache becomes the immediate write target.

This can improve write performance but introduces greater durability and consistency risks.

For many ordinary web APIs, you should **not casually use write-back caching** for important persistent data.

---

# 51. Read-Through

Conceptually:

```text
Application
   ↓
Cache
   ↓
Database
```

The cache layer itself knows how to retrieve missing data.

This differs from cache-aside because the application doesn't manually implement every cache miss lookup.

Again, the naming can vary across systems, so focus on the data flow rather than memorizing terminology.

---

# 52. Cache Consistency

This is one of the hardest questions:

> **"How do you guarantee cache consistency?"**

The honest answer:

> **Perfect strong consistency between an external cache and the database can be difficult and expensive.**

Instead, define what your application needs:

```text
strong consistency?
eventual consistency?
acceptable stale period?
```

Then design accordingly.

---

# 53. Strong vs Eventual Consistency

Suppose:

```text
Product price = ₹100
```

Database changes:

```text
₹120
```

If cache temporarily says:

```text
₹100
```

that's eventual consistency.

If your business requires checkout to always use:

```text
₹120
```

then the cache should not be treated as authoritative for that critical decision.

This is extremely important.

---

# 54. Never Trust Cache for Critical Writes

For example:

```text
Payment amount
Inventory availability
Account balance
```

You should carefully determine whether cached values are safe to use.

A stale cache might say:

```text
inventory = 10
```

while the database says:

```text
inventory = 0
```

If you sell based only on cached inventory, you could oversell.

Cache is primarily a performance mechanism—not automatically a source of truth.

---

# 55. Cache Keys

Good cache key design matters.

Bad:

```text
product
```

Better:

```text
product:123
```

For a user's profile:

```text
user:123:profile
```

For paginated products:

```text
products:page:2:limit:20
```

For filtered data:

```text
products:category:phones:page:2
```

Keys should capture every input that changes the response.

---

# 56. Cache Key Bug

Suppose:

```http
GET /products?category=phones
```

and:

```http
GET /products?category=laptops
```

both use:

```text
products:list
```

Then the second request could receive the first request's data.

That's a serious correctness bug.

Your cache key must represent the response's relevant parameters.

---

# 57. User-Specific Cache Keys

Suppose:

```http
GET /me/dashboard
```

You cannot simply cache:

```text
dashboard
```

because:

```text
Rahul → Rahul's dashboard
Amit  → Rahul's dashboard
```

would be catastrophic.

Use something like:

```text
dashboard:user:123
```

and ensure authorization boundaries are respected.

---

# 58. Cache Security

Caching can accidentally leak private data.

Example:

```text
User A
GET /profile
```

response gets cached publicly.

Then:

```text
User B
GET /profile
```

receives User A's response.

This is why:

```http
Cache-Control: private
```

or:

```http
Cache-Control: no-store
```

may be appropriate for sensitive user-specific responses.

---

# 59. CDN Cache Security

A CDN can be especially dangerous if you incorrectly mark authenticated responses as public.

Be careful with:

```text
Authorization
cookies
personalized content
tenant-specific data
```

Never assume:

```text
"GET = safe to cache publicly"
```

A GET response can absolutely contain sensitive information.

---

# 60. Multi-Tenant Applications

Imagine:

```text
Company A
Company B
```

Both use:

```http
GET /dashboard
```

If your cache key is:

```text
dashboard
```

you could leak:

```text
Company A data → Company B
```

Use tenant-aware keys:

```text
tenant:A:dashboard
tenant:B:dashboard
```

This is a very strong production detail.

---

# 61. Cache Warming

Suppose you know:

```text
products
homepage
popular categories
```

are requested heavily.

You can preload them:

```text
Application starts
     ↓
Load popular data
     ↓
Redis
```

This is:

> **Cache warming**

It reduces cold-start cache misses.

---

# 62. Cache Warming Example

Before a major sale:

```text
Black Friday
```

you might prepopulate:

```text
homepage
popular products
categories
campaign data
```

into the cache.

Then traffic arrives:

```text
Cache HIT
```

instead of causing a huge initial database spike.

---

# 63. Cache Invalidation Strategies

Common approaches:

### TTL

```text
expire automatically
```

### Explicit invalidation

```text
update DB
↓
delete cache
```

### Event-driven invalidation

```text
DB change
↓
event
↓
cache invalidation
```

### Versioned keys

```text
product:v2:123
```

These can be combined.

---

# 64. Event-Driven Invalidation

Imagine:

```text
Product Service
     ↓
ProductUpdated event
     ↓
Message broker
     ↓
Cache consumer
     ↓
invalidate product:123
```

This can be useful in distributed systems.

But it introduces:

```text
message delivery
ordering
duplicates
eventual consistency
failure recovery
```

So don't introduce it unless the architecture needs it.

---

# 65. Cache Versioning

Instead of deleting:

```text
product:123
```

you can use versioned keys:

```text
product:v1:123
product:v2:123
```

When the schema or representation changes:

```text
v1
→ v2
```

This can prevent old cached representations from conflicting with new application logic.

---

# 66. CDN vs Redis

Interviewers often ask:

> "Why Redis if you already have a CDN?"

Because they solve different problems.

### CDN

Great for:

```text
HTTP responses
static assets
public/cacheable content
edge delivery
```

### Redis

Great for:

```text
application state
database query results
sessions
counters
distributed coordination
internal caching
```

You can use both.

---

# 67. Example Architecture

```text
                    Client
                      │
                      ▼
                     CDN
                      │
               cacheable response?
                 /          \
               HIT          MISS
                │             │
                │             ▼
                │          Node.js
                │             │
                │          Redis
                │          /    \
                │       HIT      MISS
                │        │         │
                │        │      MongoDB
                │        │         │
                │        └────┬────┘
                │             ▼
                └──────── Response
```

This is a powerful multi-layer caching architecture.

---

# 68. What If Cache Is Wrong?

Suppose:

```text
MongoDB:
price = ₹120

Redis:
price = ₹100
```

What should you do?

Possible strategy:

```text
invalidate Redis
```

Then:

```text
next request
↓
MongoDB
↓
₹120
↓
Redis
```

The key principle:

> **The database remains authoritative.**

# 69. Cache Observability

A production cache needs monitoring.

Track:

```text
cache hit rate
cache miss rate
cache latency
Redis memory
eviction count
key expiration rate
hot keys
cache errors
stampede events
```

For example:

```text
Hit rate: 94%
Miss rate: 6%
Redis p95 latency: 2ms
```

Now you can determine whether caching is actually helping.

# 70. Hot Keys

Suppose:

```text
product:iphone-17
```

receives:

```text
1 million requests
```

while other keys receive almost nothing.

That key is a:

> **Hot key**

Even Redis can become stressed if one key receives extreme traffic.

Possible mitigations include:

```text
local caching
CDN caching
replication/read scaling
request coalescing
precomputation
```

---

# 71. Cache Eviction

Redis has limited memory.

Eventually:

```text
memory full
```

Redis may need to evict keys depending on its configured eviction policy.

Possible strategies include:

```text
LRU
LFU
TTL-based policies
```

You don't need to memorize every Redis configuration for interviews, but understand:

> **A cache has finite capacity and therefore needs an eviction strategy.**

---

# 72. LRU

LRU means:

> **Least Recently Used**

The system removes items that haven't been accessed recently.

Conceptually:

```text
A → accessed recently
B → accessed recently
C → old
D → old
```

Evict:

```text
C / D
```

depending on the exact policy.

Useful when recently accessed data is likely to be accessed again.

---

# 73. LFU

LFU means:

> **Least Frequently Used**

It considers access frequency.

If:

```text
A → 10,000 accesses
B → 8,000
C → 2
```

C is a stronger eviction candidate.

This can be useful for workloads with stable popularity patterns.

---

# 74. Cache Invalidation Is the Hard Part

There's a famous saying:

> "There are only two hard things in Computer Science: cache invalidation and naming things."

The exact wording isn't important for interviews.

The lesson is:

```text
Caching data
→ easy

Keeping cached data correct
→ much harder
```

That's why production cache design needs careful thought.

---

# 75. Interview Scenario

### Interviewer:

> "Your `/products` endpoint is getting 100,000 requests per minute. MongoDB is overloaded. What would you do?"

A strong answer:

> "First I'd check whether the endpoint is suitable for caching. If product data is mostly public and doesn't change frequently, I'd use HTTP caching and potentially CDN caching for public responses. On the application side, I'd consider Redis using a cache-aside strategy to reduce database reads. I'd define an appropriate TTL and explicitly invalidate relevant keys when products change. I'd also monitor cache hit ratio, Redis latency, and database load."

That's a strong practical answer.

---

# 76. Interview Follow-Up

> "What if 10,000 requests arrive when the cache expires?"

Answer:

> "I'd consider request coalescing or a distributed lock so only one request refreshes the cache while the others reuse the result once available. Jittered TTLs can also reduce synchronized expirations."

Excellent.

---

# 77. Interview Follow-Up

> "What if the cache has stale product data?"

Answer:

> "I'd treat MongoDB as the source of truth. For mutable data, I'd invalidate the relevant cache after a successful write and use TTL as a safety mechanism. For operations where stale data is unacceptable, I wouldn't rely solely on the cache."

---

# 78. Interview Follow-Up

> "Should we cache user profiles?"

Good answer:

> "Potentially, but I wouldn't make them publicly cacheable. I'd use user- or tenant-specific keys and appropriate private caching rules. I'd also consider whether stale profile information is acceptable and invalidate the cache when important fields change."

---

# 79. Interview Follow-Up

> "Is Redis always necessary?"

Answer:

> "No. For public HTTP responses, browser and CDN caching may already provide significant benefits. Redis becomes useful when the application needs shared server-side caching or other fast distributed state. I'd add Redis when the workload justifies its operational complexity."

Very good.

# 80. Gold-Level Cache Architecture

For a serious production API:

```text
                         Client
                           │
                           ▼
                    Browser Cache
                           │
                           ▼
                         CDN
                           │
                    cacheable request?
                      /           \
                    HIT           MISS
                     │              │
                     │              ▼
                     │          API Gateway
                     │              │
                     │              ▼
                     │          Node.js
                     │              │
                     │           Redis
                     │          /     \
                     │       HIT       MISS
                     │        │          │
                     │        │       MongoDB
                     │        │          │
                     │        └────┬─────┘
                     │             │
                     └─────────────┘
                           Response
```

Then for writes:

```text
PATCH /products/123
        │
        ▼
     MongoDB
        │
        ▼
 invalidate product:123
        │
        ▼
      Redis
```

This is a strong production mental model.

# 81. The Most Important Rule

Never start with:

> "Let's add Redis."

Start with:

> **"What problem are we solving?"**

For example:

```text
Database too slow?
→ caching may help

High network latency?
→ CDN/HTTP caching may help

Repeated expensive computation?
→ application cache may help

External API expensive?
→ cache results where safe

Personalized data?
→ carefully scoped server-side caching
```

Architecture follows the bottleneck.

# 🧠 Lesson 16.19 — Gold Revision Sheet

Remember these **25 points**:

1. Caching stores reusable data closer to the consumer.
    
2. The database should generally remain the source of truth.
    
3. Cache hits avoid expensive work.
    
4. Cache misses require the underlying data source.
    
5. Cache hit ratio measures cache effectiveness.
    
6. Browser caching operates at the client/HTTP layer.
    
7. CDN caching operates near users at the edge.
    
8. Redis can provide shared application-level caching.
    
9. `Cache-Control` controls HTTP caching behavior.
    
10. `max-age` defines freshness duration.
    
11. `public` allows shared caches to store a response.
    
12. `private` prevents shared caches from storing a response.
    
13. `no-store` means don't store the response.
    
14. `no-cache` means cached data must be revalidated before reuse.
    
15. ETags provide a representation validator.
    
16. `304 Not Modified` avoids retransmitting an unchanged response body.
    
17. Cache-aside is a common server-side caching pattern.
    
18. TTL limits how long cached data survives.
    
19. Cache invalidation is critical for mutable data.
    
20. Cache stampede happens when many requests simultaneously rebuild an expired cache entry.
    
21. Cache avalanche happens when many cached entries become unavailable together.
    
22. Cache penetration happens when repeated requests for nonexistent data bypass the cache.
    
23. Request coalescing, locking, negative caching, TTL jitter, and Bloom filters can mitigate different cache problems.
    
24. Never expose one user's or tenant's cached data to another user or tenant.
    
25. **The right cache depends on data freshness, access frequency, consistency requirements, cost, and where the bottleneck actually exists.**

# 🔥 Gold Interview Answer

If an interviewer asks:

> **"How would you reduce database load for a high-traffic API?"**

A strong answer would be:

> **"I'd first identify which reads are responsible for the load. For public or relatively stable responses, I'd use HTTP caching and potentially CDN caching. For server-side repeated queries, I'd consider Redis with a cache-aside strategy. I'd use appropriate TTLs and invalidate affected cache keys after successful writes. I'd also protect against cache stampedes with request coalescing or controlled refreshes, and monitor hit rate, Redis latency, and database load. For sensitive or personalized data, I'd carefully scope cache keys and use private caching rules so data isn't leaked between users or tenants."**

That's a **production-level answer**, not just:

> "Use Redis."
