# Lesson 16.2 — HTTP Status Codes

In **Lesson 16.1**, we learned that an API is a contract between the frontend and backend.

Now we learn one of the most important parts of that contract:

> **HTTP status codes tell the client what happened to its request.**

If React sends:

```http
POST /api/v1/todos
```

the response shouldn't just contain JSON.

It should also have an appropriate HTTP status:

```http
201 Created
```

That status itself carries meaning.

---

# 1. What Is an HTTP Status Code?

Every HTTP response contains a status code.

For example:

```http
HTTP/1.1 200 OK
```

Here:

```text
200
```

is the status code.

And:

```text
OK
```

is its standard reason phrase.

Think of the status code as a **short answer from the server**:

```text
200 → It worked.

201 → It worked and created something.

400 → Your request was invalid.

401 → You need to authenticate.

403 → You're authenticated, but not allowed.

404 → I couldn't find that resource.

500 → Something went wrong on the server.
```

---

# 2. The Five Status Code Families

HTTP status codes are grouped into five categories:

```text
1xx → Informational
2xx → Success
3xx → Redirection
4xx → Client-side/request errors
5xx → Server-side errors
```

For backend development, you'll mostly work with:

```text
2xx
4xx
5xx
```

---

# 3. The Most Important Ones for Your MERN Backend

You don't need to memorize every HTTP status code.

For our backend starter, these are the important ones:

```text
200 OK
201 Created
204 No Content

400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests

500 Internal Server Error
503 Service Unavailable
```

We'll understand each one.

---

# 4. `200 OK`

Use:

```http
200 OK
```

when the request succeeded and you're returning a response body.

For example:

```http
GET /api/v1/todos/123
```

If the todo exists:

```http
200 OK
```

```json
{
  "success": true,
  "data": {
    "id": "123",
    "title": "Learn Node.js"
  }
}
```

Another example:

```http
PATCH /api/v1/todos/123
```

If the update succeeds and you're returning the updated todo:

```http
200 OK
```

---

# 5. `201 Created`

Use:

```http
201 Created
```

when the request successfully **creates a new resource**.

Example:

```http
POST /api/v1/todos
```

Request:

```json
{
  "title": "Learn API Design"
}
```

Response:

```http
201 Created
```

```json
{
  "success": true,
  "message": "Todo created successfully",
  "data": {
    "id": "123",
    "title": "Learn API Design"
  }
}
```

This is better than returning:

```http
200 OK
```

because `201` communicates something more specific:

> **A new resource was created.**

---

# 6. `200` vs `201`

This is a very common interview question.

### `200`

The operation succeeded.

```text
GET → 200
PATCH → 200
```

when returning a result.

### `201`

A new resource was created.

```text
POST /todos → 201
```

Think:

```text
200 = succeeded

201 = succeeded + created
```

---

# 7. `204 No Content`

`204` means:

> The operation succeeded, but there is no response body.

A common example:

```http
DELETE /api/v1/todos/123
```

If the todo was successfully deleted:

```http
204 No Content
```

There is no need to return:

```json
{
  "success": true,
  "message": "Todo deleted"
}
```

You _can_ choose a different API convention, such as returning `200` with a JSON message. But if you're using `204`, the response should contain no body.

So:

```text
DELETE
   ↓
successful
   ↓
204
   ↓
no response body
```

---

# 8. `400 Bad Request`

Now we enter the `4xx` family.

`400` generally means:

> **The server cannot process the request because the request itself is invalid.**

For example:

```http
POST /api/v1/todos
```

with malformed or invalid request data.

Example:

```json
{
  "title": ""
}
```

If your API considers this invalid:

```http
400 Bad Request
```

```json
{
  "success": false,
  "message": "Invalid request"
}
```

---

# 9. `400` Is About the Request

Think:

```text
Client
  ↓
Bad/invalid request
  ↓
Server
  ↓
400
```

Examples can include:

```text
Malformed JSON
Invalid request structure
Invalid parameters
Invalid request syntax
```

The exact boundary between `400` and other 4xx statuses depends on your API design.

We'll establish a consistent convention for our starter.

---

# 10. `401 Unauthorized`

This one causes **a lot of confusion**.

In API authentication terminology:

```http
401 Unauthorized
```

generally means:

> **The request lacks valid authentication credentials.**

For example:

```http
GET /api/v1/users/me
```

without an access token.

```text
Request
   ↓
No valid authentication
   ↓
401 Unauthorized
```

Response:

```json
{
  "success": false,
  "message": "Authentication required"
}
```

---

# 11. Example of `401`

Suppose our protected route is:

```http
GET /api/v1/todos
Authorization: Bearer <token>
```

If the token is:

```text
missing
```

or:

```text
invalid
```

or:

```text
expired
```

your authentication layer may reject the request with:

```http
401 Unauthorized
```

The important concept is:

> **The server doesn't accept the caller's authentication.**

---

# 12. `401` vs `403`

This is one of the most important distinctions in backend development.

### `401`

```text
Who are you?
```

Authentication problem.

### `403`

```text
I know who you are,
but you're not allowed to do this.
```

Authorization problem.

Think:

```text
401 → Authentication
403 → Authorization
```

You learned this distinction deeply in Phase 15.

---

# 13. `403 Forbidden`

Suppose:

```text
Rahul = normal user
Admin route = /api/v1/admin/users
```

Rahul is authenticated:

```text
JWT valid
```

but doesn't have the required role.

Then:

```http
403 Forbidden
```

Example:

```text
Request
   ↓
JWT valid
   ↓
User authenticated
   ↓
Role = USER
   ↓
Required role = ADMIN
   ↓
403
```

Response:

```json
{
  "success": false,
  "message": "You do not have permission to perform this action"
}
```

---

# 14. `401` and `403` in One Diagram

Remember this:

```text
                 REQUEST
                    │
                    ▼
             Is authentication
                  valid?
                /       \
              NO         YES
              │           │
             401          ▼
                    Is authorization
                       allowed?
                       /     \
                     NO       YES
                     │         │
                    403        Continue
```

This is directly connected to your authentication and authorization phases.

---

# 15. `404 Not Found`

Use:

```http
404 Not Found
```

when the requested resource doesn't exist.

Example:

```http
GET /api/v1/todos/999999
```

Suppose that todo doesn't exist.

Return:

```http
404 Not Found
```

```json
{
  "success": false,
  "message": "Todo not found"
}
```

---

# 16. `404` Is Not Only for URLs

It can mean a resource wasn't found.

For example:

```http
GET /api/v1/users/123
```

If user `123` doesn't exist:

```text
404
```

Likewise:

```http
GET /api/v1/todos/abc
```

if that todo doesn't exist:

```text
404
```

So think:

> **The requested resource cannot be found.**

---

# 17. `409 Conflict`

`409` is useful when the request conflicts with the current state of the resource.

A common example:

```text
User signup
```

Suppose:

```text
email = rahul@example.com
```

already exists.

The request is structurally valid.

But creating another account with that unique email conflicts with the current state.

So:

```http
409 Conflict
```

```json
{
  "success": false,
  "message": "Email is already registered"
}
```

This is much more meaningful than:

```http
500 Internal Server Error
```

---

# 18. Why Duplicate Email Shouldn't Be `500`

Imagine:

```text
POST /api/v1/auth/signup
```

with an email that already exists.

That's not really an unexpected server failure.

The server is working correctly.

The problem is:

```text
The requested operation conflicts
with existing application state.
```

Therefore:

```text
409 Conflict
```

is a useful choice.

---

# 19. `422 Unprocessable Content`

You may also encounter:

```http
422 Unprocessable Content
```

This is commonly used when:

> The request is syntactically valid, but the submitted data doesn't satisfy the application's validation rules.

For example:

```json
{
  "email": "hello",
  "password": "123"
}
```

The JSON itself is valid.

But the values may violate your application's validation rules.

Some APIs use:

```text
400
```

for validation failures.

Others use:

```text
422
```

The important thing is **consistency**.

For our starter, we'll establish a deliberate convention rather than randomly mixing them.

---

# 20. `429 Too Many Requests`

This one is especially relevant to the security work you've already completed.

Suppose a client repeatedly calls:

```http
POST /api/v1/auth/login
```

hundreds of times.

Your rate limiter may respond:

```http
429 Too Many Requests
```

Meaning:

> Slow down. You've exceeded the allowed request rate.

Example:

```json
{
  "success": false,
  "message": "Too many requests. Please try again later."
}
```

Flow:

```text
Request
   ↓
Rate limiter
   ↓
Limit exceeded
   ↓
429
```

---

# 21. `500 Internal Server Error`

Now the `5xx` family.

```http
500 Internal Server Error
```

means:

> Something went wrong on the server while processing the request.

For example:

```text
Unexpected programming error
Unexpected database failure
Unhandled exception
```

Your backend should generally **not expose internal details**.

Bad:

```json
{
  "error": "TypeError: Cannot read properties of undefined..."
}
```

Better:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "req_123"
}
```

The detailed error belongs in your server logs, not in the production response.

---

# 22. `503 Service Unavailable`

`503` generally means:

> The service is temporarily unable to handle the request.

For example, your application might be alive but a required dependency isn't ready.

Imagine:

```text
Node application
       ↓
MongoDB
       ↓
MongoDB unavailable
```

Your readiness endpoint might report:

```http
503 Service Unavailable
```

This becomes especially useful in:

```text
Docker
Kubernetes
load balancers
deployment systems
health checks
```

We'll revisit this in the production phases.

---

# 23. Don't Use `500` for Everything

This is a beginner mistake.

Bad API:

```text
Invalid email       → 500
Not logged in       → 500
Not authorized      → 500
Todo not found      → 500
Duplicate email     → 500
Database unexpected → 500
```

Now the frontend can't understand what happened.

Better:

```text
Invalid input       → 400/422
Not authenticated   → 401
Not authorized      → 403
Not found           → 404
Conflict            → 409
Rate limited        → 429
Unexpected server   → 500
Unavailable service → 503
```

This makes your API much easier to consume.

---

# 24. Status Codes Are Part of Your API Contract

Remember Lesson 16.1?

> API = contract.

Now we can make that more concrete.

For:

```http
POST /api/v1/todos
```

your contract might be:

```text
201 → Todo created
400 → Invalid request
401 → Not authenticated
409 → Conflict
500 → Unexpected server error
```

For:

```http
GET /api/v1/todos/:id
```

you might have:

```text
200 → Todo returned
401 → Not authenticated
404 → Todo not found
500 → Unexpected server error
```

The frontend can now react appropriately.

---

# 25. Frontend Can Use Status Codes

For example:

```js
const response = await fetch("/api/v1/todos/123");
```

Suppose:

```js
response.status === 401
```

React can understand:

```text
User's session may have expired
        ↓
Try refresh-token flow
        ↓
If refresh fails
        ↓
Send user to login
```

If:

```js
response.status === 404
```

the frontend might show:

```text
"Todo not found"
```

If:

```js
response.status === 500
```

it might show:

```text
"Something went wrong. Please try again."
```

This is why status codes aren't just backend decoration.

# 27. Express Example

Here's a simple example:

```js
router.post(
    "/todos",
    authMiddleware,
    validate(createTodoSchema),
    todoController.create
);
```

Inside the controller:

```js
export const create = asyncHandler(async (req, res) => {
    const todo = await todoService.create(req.user.id, req.body);

    return res.status(201).json({
        success: true,
        message: "Todo created successfully",
        data: todo
    });
});
```

Notice:

```js
res.status(201)
```

We're explicitly telling the client:

> A new resource was created.

---

# 28. Another Example — Not Found

Service:

```js
const todo = await todoRepository.findById(id);

if (!todo) {
    throw new AppError(
        "Todo not found",
        404
    );
}
```

Then your global error middleware eventually produces:

```http
404 Not Found
```

The controller doesn't need:

```js
try/catch
```

because your async/error architecture already handles it.

This shows how the lessons we've studied are connecting:

```text
Repository
   ↓
No document
   ↓
Service
   ↓
AppError(404)
   ↓
Global error middleware
   ↓
HTTP 404
```

# 29. One Important Correction: `401 Unauthorized`

You'll sometimes hear:

> "`401` means unauthorized and `403` means forbidden."

That's a useful shortcut, but don't rely on the English words alone.

For API authentication:

```text
401
→ authentication credentials are missing/invalid

403
→ authentication is known/accepted,
  but access is forbidden
```

For example:

```text
No JWT
    ↓
401
```

versus:

```text
Valid JWT
    ↓
role = user
    ↓
admin-only endpoint
    ↓
403
```

Remember the **authentication vs authorization** distinction from Phase 15.

# 30. The Status Code Cheat Sheet

Keep this mental table:

|Status|Meaning|Typical MERN use|
|---|---|---|
|**200**|Success|GET, PATCH|
|**201**|Created|POST/create|
|**204**|Success, no body|DELETE|
|**400**|Bad request|Invalid request|
|**401**|Authentication required/invalid|Missing/invalid JWT|
|**403**|Forbidden|Insufficient permission|
|**404**|Not found|Resource doesn't exist|
|**409**|Conflict|Duplicate/competing state|
|**422**|Validation/domain input issue|Depending on API convention|
|**429**|Too many requests|Rate limiting|
|**500**|Server error|Unexpected failure|
|**503**|Service unavailable|Dependency/readiness issue|

# 31. The Mental Model

When you're designing an endpoint, ask:

```text
                    REQUEST
                       │
                       ▼
             Did the request succeed?
                       │
          ┌────────────┼─────────────┐
          │            │             │
          ▼            ▼             ▼
       Success     Client issue   Server issue
          │            │             │
          ▼            ▼             ▼
        2xx          4xx            5xx
```

Then become more specific:

```text
2xx
 ├── 200 → Success + response
 ├── 201 → Created
 └── 204 → Success + no body

4xx
 ├── 400 → Bad request
 ├── 401 → Authentication problem
 ├── 403 → Authorization problem
 ├── 404 → Resource missing
 ├── 409 → Conflict
 ├── 422 → Validation/content problem
 └── 429 → Rate limit

5xx
 ├── 500 → Unexpected server failure
 └── 503 → Temporarily unavailable
```

## 🎯 Key takeaway

Don't think:

> "`201` is the code for POST."

That's too simplistic.

Instead think:

> **The status code describes the result of the operation.**

For example:

```text
POST
 ├── created → 201
 ├── invalid → 400/422
 ├── unauthenticated → 401
 ├── forbidden → 403
 ├── conflict → 409
 ├── rate limited → 429
 └── unexpected failure → 500
```

That's the professional way to think about HTTP status codes.
