# Phase 16 — API Architecture

## Lesson 16.20 — Pagination, Filtering & Sorting

This is a **very important gold-level interview lesson** because pagination is not just an API feature.

It connects:

```text
API Design
   ↓
Query Parameters
   ↓
Repository
   ↓
MongoDB
   ↓
Indexes
   ↓
Database Performance
   ↓
Scalability
```

Your uploaded roadmap treats pagination/filtering/sorting as a dedicated part of the backend architecture path.

---

# 1. Why Do We Need Pagination?

Imagine your database contains:

```text
10,000,000 users
```

And someone requests:

```http
GET /api/v1/users
```

If your backend returns all 10 million:

```text
MongoDB
   ↓
10 million documents
   ↓
Node.js
   ↓
Huge memory usage
   ↓
Huge response
   ↓
Slow client
```

That's obviously bad.

Instead:

```http
GET /api/v1/users?page=1&limit=20
```

means:

> "Give me only 20 users."

So pagination controls how much data is returned per request.

---

# 2. Basic Pagination

The simplest model is:

```text
page
limit
```

Example:

```http
GET /todos?page=1&limit=20
```

Meaning:

```text
page = 1
limit = 20
```

Then:

```text
page 1 → records 1–20
page 2 → records 21–40
page 3 → records 41–60
```

---

# 3. The `limit`

`limit` answers:

> **How many records should I return?**

Example:

```http
GET /todos?limit=10
```

returns at most:

```text
10 records
```

But don't blindly trust the client.

This is dangerous:

```http
GET /todos?limit=100000000
```

Your API should enforce a maximum.

For example:

```text
default limit = 20
maximum limit = 100
```

So:

```text
?limit=5000
```

might become:

```text
limit = 100
```

or return a validation error.

---

# 4. The `page`

`page` answers:

> **Which page do I want?**

For:

```text
limit = 20
```

we have:

```text
page 1 → 1–20
page 2 → 21–40
page 3 → 41–60
```

---

# 5. Calculating `skip`

For offset/page pagination:

```text
skip = (page - 1) × limit
```

Example:

```text
page = 1
limit = 20

skip = (1 - 1) × 20
     = 0
```

Page 2:

```text
skip = (2 - 1) × 20
     = 20
```

Page 3:

```text
skip = (3 - 1) × 20
     = 40
```

Therefore:

```text
page 1 → skip 0
page 2 → skip 20
page 3 → skip 40
```

---

# 6. MongoDB Example

Conceptually:

```js
const users = await User.find()
    .skip(skip)
    .limit(limit);
```

For:

```text
page = 3
limit = 20
```

this becomes:

```js
User.find()
    .skip(40)
    .limit(20);
```

---

# 7. But There Is a Problem

Offset pagination looks simple.

But imagine:

```text
10,000,000 records
```

and someone asks:

```http
?page=500000&limit=20
```

Then:

```text
skip = 9,999,980
```

The database may have to process a huge offset before returning the desired records.

This is one reason deep offset pagination can become inefficient.

---

# 8. The Bigger Problem: Data Changes

Imagine page 1 contains:

```text
A
B
C
D
E
```

Then someone inserts:

```text
X
```

at the beginning.

Now page boundaries can shift.

You may get:

```text
Page 1
A B C D E

Page 2
E F G H I
```

You could see:

```text
E
```

twice.

Or records could be skipped.

This is why pagination needs **stable ordering**.

---

# 9. Always Think About Ordering

Bad:

```js
User.find()
    .skip(skip)
    .limit(limit);
```

Better:

```js
User.find()
    .sort({ createdAt: -1 })
    .skip(skip)
    .limit(limit);
```

Now you have an explicit ordering.

But even that can have edge cases if many records share the same `createdAt`.

---

# 10. Stable Sorting

Suppose:

```text
User A → createdAt = 10:00
User B → createdAt = 10:00
User C → createdAt = 10:00
```

Sorting only by:

```text
createdAt
```

doesn't fully establish a deterministic order among equal timestamps.

A stronger ordering could be:

```js
.sort({
    createdAt: -1,
    _id: -1
});
```

Now:

```text
createdAt
+
_id
```

forms a more stable ordering.

This becomes especially important for cursor/keyset pagination.

---

# 11. Pagination Response

Don't just return:

```json
[
  {},
  {},
  {}
]
```

A frontend often needs pagination information.

A useful response might be:

```json
{
  "success": true,
  "data": {
    "items": [],
    "pagination": {
      "page": 1,
      "limit": 20,
      "total": 125,
      "totalPages": 7,
      "hasNextPage": true,
      "hasPreviousPage": false
    }
  }
}
```

Your roadmap explicitly includes pagination responses as part of API response architecture.

---

# 12. What Does `total` Mean?

Suppose:

```text
total = 125
limit = 20
```

Then:

```text
totalPages = ceil(125 / 20)
           = 7
```

So:

```text
page 1 → 20
page 2 → 20
page 3 → 20
page 4 → 20
page 5 → 20
page 6 → 20
page 7 → 5
```

---

# 13. Do We Always Need `total`?

Not necessarily.

This is a subtle production-level point.

To calculate:

```text
total = 125
```

you may need an additional database count:

```js
User.countDocuments(filter);
```

For a very large dataset, repeatedly calculating exact totals can add database work.

Sometimes you only need:

```text
hasNextPage
```

rather than:

```text
totalPages
```

---

# 14. A Useful Trick

Request:

```text
limit = 20
```

Internally fetch:

```text
limit + 1
```

So:

```text
21 records
```

If you receive:

```text
21
```

you know:

```text
hasNextPage = true
```

Then return only:

```text
20
```

This can avoid an expensive total count in some APIs.

---

# 15. Offset Pagination

The model we've discussed is:

> **Offset pagination**

Example:

```http
GET /todos?page=3&limit=20
```

Internally:

```text
skip = 40
limit = 20
```

Advantages:

```text
simple
easy to understand
easy for frontend pagination
easy to jump to page 10
```

Disadvantages:

```text
deep offsets can become expensive
data changes can shift page boundaries
```

---

# 16. Cursor Pagination

A more scalable approach is:

```http
GET /todos?limit=20&cursor=abc123
```

Instead of saying:

> "Skip the first 40 records."

we say:

> "Give me records after this particular position."

Conceptually:

```text
Record A
Record B
Record C
Record D
Record E
     ↑
   cursor
```

Next request:

```text
cursor = E
```

Then:

```text
F
G
H
I
J
```

---

# 17. Why Cursor Pagination Is Powerful

Imagine:

```text
10 million records
```

Offset:

```text
skip 9,000,000
```

can become expensive.

Cursor pagination can instead use an indexed condition such as:

```text
createdAt < lastCreatedAt
```

or:

```text
_id < lastId
```

Then MongoDB can use an index efficiently.

---

# 18. Keyset Pagination

You'll often hear:

> **Keyset pagination**

This is closely related to cursor pagination.

Instead of:

```text
skip = 9000000
```

you query based on the last known sort key.

For example:

```js
Todo.find({
    createdAt: {
        $lt: lastCreatedAt
    }
})
.sort({
    createdAt: -1
})
.limit(20);
```

This can scale much better for large datasets when the query and index are designed correctly.

---

# 19. Cursor vs Offset

|Feature|Offset|Cursor/Keyset|
|---|---|---|
|Simple|✅|Moderate|
|Jump to page 50|✅|Usually not|
|Deep pagination|Can be expensive|Better|
|Stable under inserts|Weaker|Better|
|Infinite scrolling|Okay|Excellent|
|Large datasets|Can struggle|Usually better|
|Frontend page numbers|Excellent|Less natural|

---

# 20. Interview Question

### Interviewer:

> "Would you use offset or cursor pagination?"

Don't answer:

> "Cursor is always better."

Instead:

> **"It depends on the use case. Offset pagination is simple and works well for moderate datasets where users need page numbers. For large or frequently changing datasets, especially feeds or infinite scrolling, I'd prefer cursor/keyset pagination because it avoids deep offsets and gives more stable traversal."**

That's a much stronger answer.

---

# 21. Filtering

Pagination isn't enough.

Suppose:

```http
GET /todos
```

returns every todo.

We may want:

```http
GET /todos?status=completed
```

Now the API filters results.

Possible query parameters:

```text
status
priority
category
userId
createdAfter
createdBefore
```

But don't allow arbitrary database queries from users.

---

# 22. Filter Allow-List

Bad idea:

```js
Todo.find(req.query);
```

Why?

Because you're giving the client too much control over your database query.

Instead:

```js
const filter = {};

if (status) {
    filter.status = status;
}

if (priority) {
    filter.priority = priority;
}
```

Only explicitly supported fields are accepted.

This is both an architecture and security principle.

---

# 23. Example

Request:

```http
GET /todos?status=completed&priority=high
```

Could become:

```js
{
    status: "completed",
    priority: "high"
}
```

Then:

```js
Todo.find(filter);
```

The important thing is that **you constructed the filter**, rather than blindly trusting the query object.

---

# 24. Filtering + Ownership

This becomes extremely important after your authorization lessons.

Suppose:

```text
GET /todos
```

A logged-in user should only see their own todos.

So the service/repository should effectively combine:

```js
{
    userId: authenticatedUserId,
    status: "completed"
}
```

Not:

```js
{
    status: "completed"
}
```

Otherwise users could potentially retrieve other users' records.

Your architecture roadmap specifically emphasizes ownership-aware repository queries.

---

# 25. Sorting

Users may want:

```http
GET /todos?sort=createdAt
```

or:

```http
GET /todos?sort=-createdAt
```

where:

```text
createdAt
```

means ascending, while:

```text
-createdAt
```

means descending.

But again:

> **Never blindly allow arbitrary database fields for sorting.**

---

# 26. Sort Allow-List

Define:

```js
const allowedSortFields = [
    "createdAt",
    "updatedAt",
    "title"
];
```

Then:

```text
sort=createdAt
```

is accepted.

But:

```text
sort=password
```

should not be.

This gives you a controlled API contract.

---

# 27. Why Sort Fields Matter for Performance

Suppose you frequently query:

```text
status = completed
sort = createdAt descending
```

MongoDB may benefit from an appropriate compound index.

Conceptually:

```text
status + createdAt
```

This connects:

```text
API query
   ↓
Repository
   ↓
MongoDB query
   ↓
Index design
```

This is why pagination/filtering/sorting isn't just an API topic.

It's also a database-performance topic.

---

# 28. Compound Index

Suppose your common query is:

```js
Todo.find({
    userId,
    status
})
.sort({
    createdAt: -1
});
```

A suitable compound index might involve:

```text
userId
status
createdAt
```

The exact index order should be based on your actual query patterns and MongoDB's query planner.

Don't create indexes randomly.

---

# 29. Search

Now:

```http
GET /todos?search=javascript
```

might search titles.

But "search" can mean many things:

```text
exact match
prefix search
regex
text search
full-text search
MongoDB text indexes
external search engine
```

For a small application, simple search may be enough.

For a large search-heavy system, you might eventually consider a dedicated search system.

---

# 30. Don't Confuse Filtering and Search

Filtering:

```text
status=completed
```

means:

> Exact structured condition.

Search:

```text
search=javascript
```

means:

> Find records matching some textual relevance/pattern.

They have different performance characteristics and may require different indexes.

# 31. Query Parameters Need Validation

Suppose:

```http
GET /todos?page=abc
```

Bad.

Or:

```http
GET /todos?limit=-50
```

Bad.

Or:

```http
GET /todos?page=0
```

depending on your API contract, probably invalid.

Or:

```http

```

Not allowed.

Therefore:

```text
Query string
   ↓
Validation
   ↓
Normalized query object
   ↓
Service
```

Your roadmap explicitly places query validation before pagination/filtering work.

---

# 32. Normalize Query Parameters

The HTTP query string contains strings:

```text
?page=2&limit=20
```

You should turn them into appropriate types:

```js
{
    page: 2,
    limit: 20
}
```

Then your service doesn't have to repeatedly worry about:

```text
"20"
```

versus:

```text
20
```

---

# 33. Recommended Query Object

A clean architecture could produce:

```js
{
    page: 1,
    limit: 20,
    sort: {
        createdAt: -1
    },
    filter: {
        status: "completed"
    }
}
```

Then:

```text
Controller
    ↓
normalized query
    ↓
Service
    ↓
Repository
```

The repository receives structured information rather than raw HTTP query strings.

---

# 34. Don't Put Query Parsing in Repository

Avoid:

```js
repository.getTodos(req.query);
```

The repository shouldn't know about Express.

Better:

```text
Controller
 ↓
parse/validate query
 ↓
Service
 ↓
Repository
```

So the repository can work independently of HTTP.

# 36. Repository Responsibility

The repository should handle the database details:

```js
findTodos({
    userId,
    filter,
    sort,
    skip,
    limit
});
```

It can translate those inputs into:

```js
Todo.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit);
```

The service shouldn't need to know the exact MongoDB API.

---

# 37. Service Responsibility

The service can decide:

```text
What does this request mean?
```

For example:

```text
Is this user allowed?
What filters are allowed?
What business rules apply?
Should deleted records be included?
```

Then it asks the repository for the data.

---

The controller handles HTTP.

It receives:


Then:

```text

   ↓

```

Remember your earlier architecture principle:

```text

HTTP translator
```

The source roadmap explicitly defines the controller this way.

# 40. Offset Pagination Example

Suppose:

```text
page = 3
limit = 10
```

Then:

```text
skip = (3 - 1) × 10
     = 20
```

MongoDB conceptually:

```js
Todo.find(filter)
    .sort({ createdAt: -1, _id: -1 })
    .skip(20)
    .limit(10);
```

---

# 41. Cursor Pagination Example

Suppose the last item on the current page has:

```text
createdAt = 2026-08-26T10:00:00Z
_id = abc123
```

The next request can carry a cursor representing that position.

Conceptually:

```text
GET /todos?limit=20&cursor=...
```

The server decodes the cursor and queries for records **after that position**, according to the chosen ordering.

The cursor should generally be treated as an opaque value by the client.

---

# 42. Why Opaque Cursors?

Don't force the frontend to understand:

```text
createdAt
_id
sort direction
```

Instead give it:

```text
nextCursor: "eyJjcmVhdGVkQXQi..."
```

The frontend simply says:

```http
GET /todos?cursor=eyJ...
```

The backend owns the cursor format.

This gives you freedom to change its internal representation later.

---

# 43. Cursor Security

Don't put sensitive information directly into an easily readable cursor.

Remember:

> **A cursor is not automatically secret just because it's encoded.**

Base64 is encoding, not encryption.

If the cursor contains internal information, consider signing or otherwise protecting it appropriately.

---

# 44. Pagination and Authorization

This is a subtle but important interview point.

Imagine:

```text
User A
```

requests:

```http
GET /todos?page=1
```

The query must effectively be scoped to:

```text
userId = User A
```

**before pagination is applied.**

Conceptually:

```text
filter by ownership
      ↓
sort
      ↓
paginate
```

Not:

```text
paginate all users' records
      ↓
try to filter afterward
```

That would be both incorrect and potentially dangerous.

---

# 45. Filtering Order

A useful mental model:

```text
Authorization scope
        ↓
Business filters
        ↓
Sorting
        ↓
Pagination
```

For example:

```text
userId = currentUser
status = completed
priority = high
sort = newest
limit = 20
```

This produces the final dataset.

---

# 46. Maximum Limits

A production API should usually have something like:

```text
default:
20

maximum:
100
```

Why?

Without limits, someone could request:

```http
?limit=1000000
```

and potentially cause:

```text
large DB query
large Node memory usage
large JSON serialization
large network response
```

This is both a performance and availability concern.

---

# 47. Maximum Page Depth

For offset pagination, you might also consider restricting extremely deep pages.

For example:

```text
page <= 1000
```

Whether this is appropriate depends on the application.

For huge datasets, cursor pagination is usually a better long-term solution than allowing enormous offsets.

---

# 48. Infinite Scrolling

Cursor pagination is especially useful for:

```text
social feeds
notifications
activity feeds
chat history
large timelines
```

Example:

```text
Initial:
GET /feed?limit=20

Response:
items: [...]
nextCursor: "abc"

Next:
GET /feed?limit=20&cursor=abc

Response:
items: [...]
nextCursor: "def"
```

This is a natural fit for frontend infinite scrolling.

---

# 49. Admin Tables

Offset pagination can be better for:

```text
admin dashboard
user management
reports
data tables
```

because the UI might need:

```text
Page 1
Page 2
Page 3
...
Page 50
```

Users often expect direct page navigation there.

---

# 50. Interview Question: "What Is the Best Pagination Strategy?"

There is no universal best strategy.

A strong answer:

> **"For simple administrative tables and moderate datasets, offset pagination is straightforward and provides page-number navigation. For large, frequently changing datasets such as feeds, I'd prefer cursor or keyset pagination because it avoids deep offsets and provides more stable traversal."**

That answer demonstrates engineering judgment.

# 53. Interview Scenario

### Interviewer:

> "You have 50 million orders. Your API currently uses `skip()` and `limit()`. Users complain that page 100,000 is slow. What would you do?"

Strong answer:

> "I'd investigate the query plan and indexes first. If the use case doesn't require arbitrary page jumps, I'd move toward cursor/keyset pagination using a stable indexed sort key, such as `createdAt` combined with `_id`. That avoids walking through a huge offset. I'd also make sure the filtering and ordering match an appropriate compound index."

That's a **gold-level answer**.

---

# 54. Interview Scenario — Data Changes

> "What happens if new records are inserted while someone is paginating?"

Answer:

> "Offset pagination can produce duplicates or skipped records because page boundaries can shift. Cursor/keyset pagination is generally more stable because the next query starts from a known position in the ordered dataset."

Excellent.

---

# 55. Interview Scenario — `total`

> "Would you always return total pages?"

Answer:

> "Not necessarily. Exact totals can require an additional count operation, which may be expensive at scale. If the frontend only needs to know whether more records exist, I can fetch `limit + 1` records and derive `hasNextPage` without calculating the exact total."

That's the kind of detail interviewers like.

---

# 56. Interview Scenario — Redis

Connecting this lesson to **16.19 caching**:

> "Would you cache paginated results?"

Possible answer:

> "Potentially, if the query is frequently repeated and the data is suitable for caching. But I'd carefully design the cache key to include the relevant filters, sort order, pagination position, and authorization/tenant scope. I'd also consider cache invalidation because paginated collections can become stale."

For example, a key might conceptually include:

```text
todos:
user:123:
status:completed:
sort:createdAt_desc:
page:2:
limit:20
```

For cursor pagination, the cursor also becomes part of the cache key if you choose to cache that exact request.

11. Cursor/keyset pagination is usually better for large feeds.
    
12. Offset pagination is convenient for page-number UIs.
    
13. Don't blindly use `req.query` as a MongoDB filter.
    
14. Allow-list filter fields.
    
15. Allow-list sort fields.
    
16. Validate and normalize query parameters.
    
17. Apply authorization/ownership scope before pagination.
    
18. Proper indexes are essential for high-performance filtering and sorting.
    
19. Exact `total` counts can add database work.
    
20. `limit + 1` can help determine `hasNextPage` without an exact count.
    
21. Cursor values should generally be opaque to clients.
    
22. Pagination, filtering, sorting, and indexing must be designed together.
    
23. Cache keys for paginated APIs must include all relevant query dimensions.
    
24. Choose pagination strategy based on the product's actual navigation needs.
    
25. **There is no universally "best" pagination method.**
