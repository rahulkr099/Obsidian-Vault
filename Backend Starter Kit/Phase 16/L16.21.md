# Phase 16 — API Architecture

## Lesson 16.21 — API Query Builder Architecture

This is an important **gold-level backend architecture lesson**.

In the previous lesson, we learned:

```text
pagination
filtering
sorting
search
```

Now we need to answer a practical production question:

> **Where should all this query logic live, and how do we keep it reusable without creating a giant repository?**

The goal is to move from:

```text
One endpoint
   ↓
one giant query implementation
```

to:

```text
HTTP Query
    ↓
Validation
    ↓
Normalization
    ↓
Reusable Query Object
    ↓
Repository
    ↓
Database
```

---

# 1. The Problem We Are Solving

Imagine you have:

```text
GET /users
GET /todos
GET /posts
GET /comments
GET /orders
GET /products
```

Almost every endpoint needs some combination of:

```text
page
limit
sort
filter
search
projection
```

If you implement everything independently, you may end up with:

```text
users.controller.js
    pagination logic
    sorting logic
    filtering logic

todos.controller.js
    pagination logic
    sorting logic
    filtering logic

posts.controller.js
    pagination logic
    sorting logic
    filtering logic
```

That's duplication.

---

# 2. The Wrong Architecture

A controller like this becomes problematic:

```js
async function getUsers(req, res) {
    const {
        page = 1,
        limit = 20,
        sort = "-createdAt",
        search,
        status,
        role
    } = req.query;

    // validate page

    // validate limit

    // calculate skip

    // build search

    // build filters

    // build sort

    // query database

    // calculate pagination

    // format response
}
```

This controller is doing too much.

Remember our architecture principle:

```text
Controller = HTTP translator
```

Not:

```text
Controller = query engine
```

---

# 3. The Better Architecture

Think in layers:

```text
Request
   ↓
Controller
   ↓
Query Parser / Validator
   ↓
Normalized Query
   ↓
Service
   ↓
Repository
   ↓
Database
```

For example:

```js
{
    pagination: {
        page: 2,
        limit: 20
    },

    sort: {
        createdAt: -1
    },

    filters: {
        status: "completed"
    },

    search: {
        term: "javascript"
    }
}
```

Now each layer has a clear responsibility.

---

# 4. What Is a Query Builder?

A query builder is a component that transforms something like:

```text
req.query
```

into a structured query description.

Example:

```http
GET /todos?page=2&limit=20&status=completed&sort=-createdAt
```

becomes:

```js
{
    pagination: {
        page: 2,
        limit: 20
    },

    filters: {
        status: "completed"
    },

    sort: {
        createdAt: -1
    }
}
```

The database layer can then use this structure.

---

# 5. Why Not Pass `req.query` Directly?

Because `req.query` belongs to HTTP.

Your repository shouldn't know anything about Express.

Bad:

```js
todoRepository.findAll(req.query);
```

Now your repository depends on the shape of an HTTP request.

Better:

```js
todoRepository.findAll({
    filters,
    sort,
    pagination
});
```

This creates a clean boundary.

---

# 6. Think of Query Building as Translation

You can think of it like this:

```text
HTTP language
     ↓
Query Builder
     ↓
Application Query language
     ↓
Repository
     ↓
Database language
```

For example:

```text
?page=2&limit=20
```

becomes:

```js
{
    offset: 20,
    limit: 20
}
```

Then the repository translates that into:

```js
.skip(20)
.limit(20)
```

---

# 7. Separate Parsing From Database Querying

This is extremely important.

Don't create one giant function:

```js
buildMongoQuery(req.query)
```

that does everything.

Instead think:

```text
parsePagination()
parseSorting()
parseFilters()
parseSearch()
buildQuery()
```

This makes each part easier to test.

---

# 8. Pagination Parser

Conceptually:

```js
function parsePagination(query) {
    const page = ...
    const limit = ...

    return {
        page,
        limit,
        skip: (page - 1) * limit
    };
}
```

Input:

```text
?page=3&limit=20
```

Output:

```js
{
    page: 3,
    limit: 20,
    skip: 40
}
```

The important thing is that this function does **not** query MongoDB.

---

# 9. Sorting Parser

Input:

```text
?sort=-createdAt
```

Output:

```js
{
    createdAt: -1
}
```

Input:

```text
?sort=title
```

Output:

```js
{
    title: 1
}
```

But only if those fields are allowed.

---

# 10. Filter Parser

Suppose your API supports:

```text
status
priority
category
```

Input:

```http
?status=completed&priority=high
```

Output:

```js
{
    status: "completed",
    priority: "high"
}
```

Again:

> Only explicitly supported filters should be converted into database conditions.

---

# 11. Search Parser

Input:

```text
?search=javascript
```

could become:

```js
{
    term: "javascript"
}
```

Then the repository or a specialized search layer decides how that term should be queried.

This separation is useful because your search implementation may eventually change.

For example:

```text
MongoDB text search
        ↓
Atlas Search
        ↓
External search engine
```

Your HTTP API doesn't necessarily need to change.

---

# 12. Projection

Another useful query feature is **field selection**.

For example:

```http
GET /users?fields=name,email
```

could mean:

```json
{
    "name": "Rahul",
    "email": "..."
}
```

instead of returning:

```text
name
email
passwordHash
tokens
internal fields
metadata
...
```

But projection must be carefully controlled.

Never let users arbitrarily access sensitive fields.

---

# 13. Allow-Listing Projection

Suppose:

```js
const allowedFields = [
    "name",
    "email",
    "avatar"
];
```

Then:

```text
?fields=name,email
```

is valid.

But:

```text
?fields=passwordHash
```

should be rejected or ignored.

This is another example of:

```text
Client input
    ↓
Allow-list
    ↓
Application query
```

---

# 14. A Complete Query Object

A mature query object could look like:

```js
{
    filters: {
        status: "completed",
        priority: "high"
    },

    search: {
        term: "javascript"
    },

    sort: {
        createdAt: -1,
        _id: -1
    },

    pagination: {
        page: 2,
        limit: 20,
        skip: 20
    },

    projection: [
        "title",
        "status",
        "createdAt"
    ]
}
```

This is much cleaner than passing raw HTTP parameters everywhere.

---

# 15. But There Is a Critical Question

Should this query object be **generic for every resource**?

Not completely.

This is where many developers make a mistake.

You might create:

```text
UniversalQueryBuilder
```

that tries to support:

```text
every possible filter
every possible operator
every possible field
every possible search
every possible database feature
```

Eventually it becomes a monster.

---

# 16. Generic Infrastructure vs Resource-Specific Rules

A better approach is:

```text
Generic infrastructure
        +
Resource-specific configuration
```

For example:

```js
const todoQueryConfig = {
    filterFields: [
        "status",
        "priority"
    ],

    sortFields: [
        "createdAt",
        "updatedAt",
        "title"
    ],

    searchableFields: [
        "title",
        "description"
    ]
};
```

The query infrastructure remains reusable.

The Todo module decides what is allowed.

---

# 17. This Is Configuration-Driven Architecture

Instead of hardcoding everything into your generic query builder:

```text
QueryBuilder
```

give it configuration:

```text
QueryBuilder
     +
TodoQueryConfig
```

For users:

```text
QueryBuilder
     +
UserQueryConfig
```

For products:

```text
QueryBuilder
     +
ProductQueryConfig
```

This gives you reuse without losing control.

---

# 18. Example

Conceptually:

```js
const config = {
    filterFields: ["status", "priority"],
    sortFields: ["createdAt", "title"]
};

const query = queryBuilder.parse(req.query, config);
```

The query builder doesn't need to know what a Todo is.

It simply follows the configuration.

---

# 19. Why This Is Better

You now have:

```text
Reusable query infrastructure
             +
Resource-specific rules
```

Benefits:

```text
less duplication
better consistency
easier testing
better security
easier maintenance
clear API contracts
```

---

# 20. Avoid the "Magic Query Builder"

Here's an important interview-level warning.

Don't build something like:

```http
?status[in]=completed,pending
&createdAt[gte]=2026-01-01
&createdAt[lte]=2026-08-01
&sort=-createdAt
&fields=name,email
&search=abc
&page=2
&limit=20
```

and automatically translate every operator into MongoDB:

```js
req.query
   ↓
Object.keys()
   ↓
MongoDB operators
```

This may look clever.

But it can create:

```text
security risks
complex validation
unclear API contracts
hard debugging
database coupling
```

A production API should be **explicit**, not magical.

---

# 21. API Contract Matters

Suppose your API officially supports:

```text
status
priority
sort
page
limit
search
```

Document exactly that.

Then:

```text
?randomMongoOperator=...
```

is not part of the API.

This makes your API predictable.

---

# 22. Query Builder vs Repository

This distinction is important.

### Query Builder

Answers:

> What does this API query mean?

### Repository

Answers:

> How do I execute this query against the database?

For example:

```text
Query Builder
      ↓
{
  filters,
  sort,
  pagination
}
      ↓
Repository
      ↓
MongoDB
```

---

# 23. Query Builder vs Service

Another important distinction.

### Query Builder

Handles:

```text
query syntax
normalization
allowed fields
pagination
sorting
filter parsing
```

### Service

Handles:

```text
business rules
authorization
ownership
workflow
domain decisions
```

Don't put:

```js
if (user.role === "admin")
```

inside a generic query parser.

That's business/application logic.

---

# 24. Query Builder vs Controller

### Controller:

```text
HTTP
```

### Query Builder:

```text
query interpretation
```

### Service:

```text
business logic
```

### Repository:

```text
persistence
```

This gives:

```text
Controller
    ↓
Query Builder
    ↓
Service
    ↓
Repository
```

---

# 25. A Clean Module Structure

For your MERN backend, you could eventually have:

```text
src/
├── modules/
│   └── todo/
│       ├── todo.controller.js
│       ├── todo.service.js
│       ├── todo.repository.js
│       ├── todo.query.js
│       └── todo.validation.js
│
└── common/
    └── query/
        ├── pagination.js
        ├── sorting.js
        ├── filtering.js
        └── query-builder.js
```

Notice the distinction:

```text
common/query/
```

contains reusable infrastructure.

While:

```text
todo/todo.query.js
```

contains Todo-specific query rules.

---

# 26. Example Responsibility

Imagine:

```text
GET /todos?status=completed&limit=20
```

### Validation

Checks:

```text
status is valid
limit is integer
limit <= 100
```

### Query Builder

Produces:

```js
{
    filters: {
        status: "completed"
    },

    pagination: {
        limit: 20
    }
}
```

### Service

Adds:

```js
userId: currentUser.id
```

### Repository

Executes:

```js
Todo.find({
    userId,
    status: "completed"
})
.limit(20);
```

That's a clean flow.

---

# 27. Important: Authorization Scope

Never let the generic query builder decide ownership.

For example, don't let:

```text
?userId=someoneElse
```

automatically determine which user's data is returned.

Instead:

```text
Authentication
      ↓
Current user
      ↓
Authorization
      ↓
Ownership scope
      ↓
Query
```

For a normal user:

```js
{
    userId: currentUserId
}
```

For an authorized admin:

```js
{
    // potentially broader scope
}
```

The service decides this.

---

# 28. Query Composition

One powerful design is to build query pieces separately.

Conceptually:

```js
const filters = buildFilters(query, config);

const search = buildSearch(query, config);

const sort = buildSort(query, config);

const pagination = buildPagination(query);
```

Then:

```js
const parsedQuery = {
    filters,
    search,
    sort,
    pagination
};
```

This is **composition**.

Each piece has one responsibility.

---

# 29. Why Composition Beats One Giant Function

Bad:

```js
buildEverything(query, config)
```

with 500 lines.

Better:

```text
buildFilters()
buildSearch()
buildSort()
buildPagination()
buildProjection()
```

Each can be independently tested.

For example:

```text
pagination.test.js
sorting.test.js
filtering.test.js
projection.test.js
```

This becomes especially valuable as your backend grows.

---

# 30. Validation Belongs Before Query Construction

Consider:

```text
limit = "abc"
```

Don't let your query builder try to make sense of everything.

Better:

```text
HTTP query
    ↓
Schema validation
    ↓
Normalized data
    ↓
Query builder
```

Then the query builder can assume:

```text
page is a positive integer
limit is a positive integer
sort is allowed
```

This reduces complexity.

---

# 31. Query Normalization

Suppose clients send:

```text
?limit=20
```

After validation:

```js
{
    limit: 20
}
```

Then your internal code works with:

```js
20
```

not:

```js
"20"
```

This is an important boundary.

---

# 32. Default Values

Your query system should define defaults.

For example:

```text
page:
1

limit:
20

sort:
-createdAt
```

Then:

```http
GET /todos
```

still produces a predictable query.

---

# 33. Maximum Values

Similarly:

```text
maximum limit:
100
```

This should be enforced centrally rather than repeatedly throughout every controller.

---

# 34. Sorting Multiple Fields

You may eventually support:

```text
?sort=-createdAt,title
```

which could become:

```js
{
    createdAt: -1,
    title: 1
}
```

But don't automatically allow every field.

Configuration still controls:

```text
allowed sort fields
```

---

# 35. Stable Multi-Field Sorting

Suppose:

```text
sort = createdAt DESC
```

Multiple records may have identical timestamps.

A useful strategy is:

```text
createdAt DESC
_id DESC
```

This gives you a deterministic tie-breaker.

This is particularly important for keyset/cursor pagination.

---

# 36. Filter Operators

Eventually you may need:

```text
price >= 100
createdAt < date
status = completed
```

You might be tempted to expose:

```text
?price[gte]=100
```

This can be useful in some APIs, but it requires careful validation.

An explicit API might instead define:

```text
?minPrice=100
```

which is easier to understand and control.

The important architectural principle:

> **Choose an API query language intentionally. Don't accidentally expose your database query language.**

---

# 37. Database Independence

Here's another gold-level concept.

If your query object looks like:

```js
{
    filters,
    sort,
    pagination
}
```

it's relatively database-neutral.

But if your application layer contains:

```js
{
    $gte: 100,
    $in: [...]
}
```

everywhere, your business logic starts speaking MongoDB.

That creates stronger database coupling.

---

# 38. Keep MongoDB Operators Near the Repository

Prefer:

```text
Application Query
      ↓
Repository
      ↓
MongoDB Query
```

rather than:

```text
Service
   ↓
MongoDB operators
   ↓
Repository
```

This helps keep persistence details inside the repository layer.

---

# 39. Query Object as a Boundary

Think of:

```js
{
    filters,
    sort,
    pagination
}
```

as a boundary between:

```text
application concerns
```

and:

```text
database concerns
```

That is a powerful architectural idea.

---

# 40. Query Builder Testing

A query builder is excellent for unit testing.

Test:

```text
?page=2&limit=20
```

Expected:

```js
{
    page: 2,
    limit: 20,
    skip: 20
}
```

Test:

```text
?limit=1000
```

Expected:

```text
validation error
```

Test:

```text
?sort=password
```

Expected:

```text
invalid sort field
```

Test:

```text
?status=completed
```

Expected:

```js
{
    status: "completed"
}
```

These tests don't require MongoDB.

That's a major advantage.

---

# 41. Query Builder Is Pure-ish Infrastructure

A good query parser can often be close to a pure function:

```text
input
  ↓
output
```

For example:

```text
Input:
?page=3&limit=10

Output:
{
  page: 3,
  limit: 10,
  skip: 20
}
```

No:

```text
database
network
Express response
```

This makes it fast and easy to test.

---

# 42. Query Builder and Caching

Remember our previous lesson about caching.

A normalized query object is useful for generating cache keys.

For example:

```js
{
    filters: {
        status: "completed"
    },
    sort: {
        createdAt: -1
    },
    pagination: {
        page: 2,
        limit: 20
    }
}
```

can be serialized into a stable cache-key representation.

This is much safer than blindly using:

```text
JSON.stringify(req.query)
```

because different parameter orderings can represent the same logical query.

---

# 43. Example

These requests:

```http
GET /todos?status=completed&limit=20
```

and:

```http
GET /todos?limit=20&status=completed
```

mean the same thing.

A normalized query can make them produce the same logical cache key.

That's a subtle but valuable design benefit.

---

# 44. Query Builder and Observability

A normalized query also makes logging easier.

Instead of logging raw:

```text
req.query
```

you can log structured information such as:

```text
resource: todos
filters: status=completed
sort: createdAt desc
pagination: limit=20
```

while avoiding sensitive information.

This helps debugging production issues.

---

# 45. Don't Log Everything

Query parameters may contain:

```text
search terms
emails
IDs
sensitive values
```

So observability should still follow your security/privacy rules.

Structured logging doesn't mean:

> Log every input.

It means:

> Log useful, safe information consistently.

---

# 46. Interview Question

### "Why create a query builder instead of querying MongoDB directly in the controller?"

Strong answer:

> **"It separates HTTP query parsing from persistence concerns. The controller shouldn't know how pagination, sorting, or MongoDB queries work. A query builder can validate and normalize the API query into a structured representation, while the repository translates that representation into the database-specific query. This improves reuse, testing, maintainability, and database independence."**

Excellent answer.

---

# 47. Interview Question

### "Should the query builder know about authorization?"

Answer:

> **"Generally, no. It can validate which query fields are allowed, but authorization and ownership rules belong to the application/service layer. Otherwise a generic query component becomes coupled to business rules and security policy."**

Very strong.

---

# 48. Interview Question

### "Should every resource use the exact same query builder?"

Answer:

> **"I'd share generic infrastructure for common concerns such as pagination and sorting, but resource-specific configuration should define allowed filters, sort fields, searchable fields, and projections. I would avoid a universal query builder that tries to model every possible resource and database operation."**

That's the architectural judgment interviewers want.

---

# 49. Interview Question

### "How would you prevent query injection?"

Don't simply say:

> "Use MongoDB sanitization."

A better answer:

> **"I would validate and allow-list query fields and operators, avoid passing raw request query objects directly into MongoDB, normalize values through schemas, and keep database-specific query construction inside the repository. I would also apply appropriate MongoDB/operator injection protections."**

---


# 🧠 Gold-Level Takeaways

Remember these:

1. **Don't pass raw `req.query` through your entire application.**
    
2. Validate query parameters at the boundary.
    
3. Normalize them into application-friendly types.
    
4. A query builder translates API query syntax into a structured query.
    
5. Keep pagination, filtering, sorting, and search composable.
    
6. Use generic infrastructure for common behavior.
    
7. Use resource-specific configuration for allowed fields.
    
8. Don't create a magical universal query builder.
    
9. Controllers should not construct database queries.
    
10. Services should own business rules and authorization decisions.
    
11. Repositories should translate application queries into database queries.
    
12. Keep MongoDB-specific operators close to the repository.
    
13. Allow-list filter fields.
    
14. Allow-list sort fields.
    
15. Allow-list projection fields.
    
16. Don't accidentally expose your database query language as your API language.
    
17. Stable sorting matters for pagination.
    
18. Normalized queries are useful for caching.
    
19. Query builders are highly unit-testable.
    
20. **Good query architecture is about controlled flexibility, not maximum flexibility.**
    

---

## 🎯 One interview sentence to remember

> **"I prefer to treat API query handling as a translation pipeline: validate and normalize the HTTP query at the boundary, convert it into a structured application query, apply authorization and business rules in the service layer, and let the repository translate that query into an optimized database-specific operation."**

That one sentence demonstrates a **much deeper understanding of backend architecture** than simply knowing how to write `.find().sort().skip().limit()`.
