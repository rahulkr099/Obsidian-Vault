# Phase 16 — API Architecture

## Lesson 16.22 — API Performance Architecture

This is another **gold-level interview lesson**.

So far we've built the API architecture:

```text
Request
  ↓
Validation
  ↓
Query Builder
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

Now the important question is:

> **What happens when this API becomes slow?**

A strong backend developer doesn't just know how to build an API. They know **how to find where the performance problem is and fix the correct layer**.

---

# 1. Performance Is a System Problem

Suppose:

```http
GET /api/v1/orders
```

takes:

```text
2.8 seconds
```

Don't immediately say:

> "MongoDB is slow."

The request could be spending time in:

```text
Network
   ↓
Middleware
   ↓
Authentication
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
   ↓
Serialization
   ↓
Network response
```

The first rule is:

> **Measure before optimizing.**

---

# 2. Think in Latency

Suppose your API has:

```text
Authentication: 20 ms
Service:        15 ms
MongoDB:       700 ms
Serialization:  50 ms
Network:       100 ms
```

Total:

```text
885 ms
```

Optimizing the controller from:

```text
15 ms → 5 ms
```

only saves:

```text
10 ms
```

But improving the database query from:

```text
700 ms → 100 ms
```

saves:

```text
600 ms
```

This is why performance optimization should be evidence-driven.

---

# 3. First Golden Rule

> **Don't optimize what you haven't measured.**

Before changing code, determine:

```text
Where is the time going?
```

You might measure:

```text
request duration
database duration
external API duration
serialization duration
cache duration
```

Then optimize the actual bottleneck.

---

# 4. The N+1 Query Problem

This is one of the most important backend interview topics.

Imagine:

```text
GET /posts
```

returns:

```text
10 posts
```

Then your code does:

```text
Get posts
   ↓
For each post:
   get author
```

You now have:

```text
1 query for posts
+
10 queries for authors
=
11 database queries
```

That's the **N+1 query problem**.

---

# 5. Example

Bad pattern:

```js
const posts = await Post.find();

for (const post of posts) {
    post.author = await User.findById(post.authorId);
}
```

If there are:

```text
100 posts
```

you could execute:

```text
1 + 100 = 101 queries
```

This can become extremely expensive.

---

# 6. Why N+1 Is Dangerous

Imagine:

```text
100 posts
```

and:

```text
average query = 10 ms
```

You might think:

```text
100 × 10 ms = 1000 ms
```

But real systems are more complicated because of:

```text
network round trips
connection pool usage
database contention
serialization
concurrency
```

The important point is:

> **Repeated database round trips can become a major bottleneck.**

---

# 7. Better Approach — Batch

Instead of:

```text
post 1 → user query
post 2 → user query
post 3 → user query
...
```

collect the IDs:

```text
authorIds:
A
B
C
D
```

Then perform one batch query:

```js
User.find({
    _id: {
        $in: authorIds
    }
});
```

Conceptually:

```text
100 posts
   ↓
collect 100 author IDs
   ↓
one user query
   ↓
map users back to posts
```

Now:

```text
1 post query
+
1 user query
=
2 queries
```

instead of:

```text
101 queries
```

---

# 8. N+1 Isn't Only a MongoDB Problem

You can encounter N+1 with:

```text
MongoDB
PostgreSQL
MySQL
REST APIs
GraphQL
microservices
external APIs
```

For example:

```text
Get 100 orders
   ↓
For every order:
   call payment service
```

That's also an N+1-style architecture problem.

---

# 9. Another Example

Suppose:

```text
GET /users
```

returns:

```text
50 users
```

Then you separately request:

```text
50 profile queries
50 subscription queries
50 organization queries
```

You could accidentally create:

```text
1 + 50 + 50 + 50
=
151 operations
```

This is why API performance requires thinking about **data access patterns**, not just individual queries.

---

# 10. Projection

Suppose your user document contains:

```text
_id
name
email
passwordHash
avatar
address
preferences
tokens
metadata
createdAt
updatedAt
```

But your endpoint only needs:

```text
name
avatar
```

Why retrieve everything?

Use projection.

Conceptually:

```js
User.find()
    .select("name avatar");
```

Now the database/application handles less data.

---

# 11. Why Projection Helps

Projection can reduce:

```text
database data read
network transfer
Node.js memory usage
serialization work
response size
```

It's particularly useful for large documents.

---

# 12. Security Benefit of Projection

Projection isn't only about performance.

Suppose you accidentally return:

```text
passwordHash
refreshToken
internalMetadata
```

That's a security problem.

A safer design is to explicitly select the fields required by the API.

Think:

```text
Database document
      ↓
Allowed fields
      ↓
API representation
```

---

# 13. `lean()` in Mongoose

If you're using Mongoose, you'll often encounter:

```js
User.find().lean();
```

Conceptually, `lean()` tells Mongoose:

> Return plain JavaScript objects instead of full Mongoose documents.

For read-heavy endpoints where you don't need document methods, this can reduce overhead.

For example:

```js
const users = await User.find()
    .select("name email")
    .lean();
```

This can be useful for APIs that primarily read data.

---

# 14. But Don't Use `lean()` Blindly

A gold-level answer isn't:

> "`lean()` always makes MongoDB faster."

That's too simplistic.

`lean()` changes the kind of objects returned by Mongoose.

You may lose behavior associated with hydrated Mongoose documents, depending on your setup and usage.

So ask:

```text
Do I need a Mongoose document?
```

If the answer is:

```text
No, I'm only reading and serializing data.
```

then `lean()` can be a good fit.

---

# 15. Hydration

Without `lean()`:

```text
MongoDB document
      ↓
Mongoose hydration
      ↓
Mongoose document object
```

With:

```js
.lean()
```

you can conceptually get:

```text
MongoDB document
      ↓
Plain JavaScript object
```

Less application-layer work may be needed.

---

# 16. Database Round Trips

Suppose your service does:

```text
Query A
   ↓
wait
Query B
   ↓
wait
Query C
```

This creates multiple round trips.

If some queries are independent, you may be able to run them concurrently.

For example:

```js
const [users, categories] = await Promise.all([
    getUsers(),
    getCategories()
]);
```

Instead of:

```js
const users = await getUsers();
const categories = await getCategories();
```

If they are independent, concurrency can reduce overall waiting time.

---

# 17. But `Promise.all()` Isn't Magic

Don't do this:

```js
await Promise.all(
    Array.from({ length: 1000 }, () => expensiveQuery())
);
```

You may overwhelm:

```text
database
connection pool
external service
CPU
memory
```

So concurrency needs limits.

The gold-level idea is:

> **Parallelize independent work carefully, not blindly.**

---

# 18. Connection Pool

Your Node.js application doesn't normally open a brand-new database connection for every query.

It uses a connection pool.

Conceptually:

```text
Node.js
 ├── connection
 ├── connection
 ├── connection
 ├── connection
 └── connection
        ↓
     MongoDB
```

If your application creates too much concurrent database work, the pool can become a bottleneck.

That's another reason N+1 queries are dangerous.

---

# 19. Database Indexes

Suppose you frequently query:

```js
Todo.find({
    userId,
    status
});
```

Without an appropriate index, MongoDB may need to examine many documents.

With an appropriate index:

```text
userId
status
```

the database may be able to locate matching documents much more efficiently.

But:

> **An index is not automatically good just because it exists.**

---

# 20. Index Trade-Off

Indexes improve reads.

But they also have costs:

```text
additional storage
write overhead
index maintenance
memory usage
```

So don't create:

```text
50 indexes
```

just because you can.

Indexes should follow actual query patterns.

---

# 21. Query Shape

Suppose your API commonly performs:

```js
Todo.find({
    userId,
    status
})
.sort({
    createdAt: -1
})
.limit(20);
```

The important query shape is:

```text
filter:
userId
status

sort:
createdAt
```

This query shape should influence your index design.

This is where:

```text
API architecture
        ↓
repository queries
        ↓
database indexes
```

becomes one connected system.

---

# 22. Query Planner

When investigating a slow MongoDB query, don't guess.

Inspect the query plan.

Conceptually:

```js
query.explain(...)
```

The goal is to understand:

```text
How is MongoDB executing this query?
```

You want to investigate things like:

```text
collection scan
index scan
documents examined
keys examined
execution time
```

A large gap between:

```text
documents examined
```

and:

```text
documents returned
```

can be a clue that the query isn't efficiently targeting the data.

---

# 23. Collection Scan

A collection scan means the database examines documents across the collection rather than efficiently using an appropriate index.

Conceptually:

```text
10 million documents
      ↓
inspect many/all
      ↓
find matching 20
```

That can become expensive.

With an effective index:

```text
index
 ↓
locate matching range
 ↓
fetch needed documents
```

can be much more efficient.

---

# 24. But Don't Worship Indexes

Suppose:

```text
collection = 50 documents
```

and:

```text
query = very simple
```

A collection scan might be perfectly fine.

Performance engineering is contextual.

You should ask:

```text
How large is the data?
How frequent is the query?
How selective is the filter?
What does the query plan show?
What is the latency requirement?
```

---

# 25. Response Size

Suppose your endpoint returns:

```text
10,000 records
```

Even if MongoDB returns them quickly, your API still has to:

```text
serialize JSON
send data
```

and the client has to:

```text
receive
parse
render
```

So API performance isn't only database performance.

---

# 26. API Payload Optimization

Use:

```text
pagination
projection
compact response representations
```

For example:

Bad:

```json
{
  "user": {
    "...": "huge object"
  }
}
```

when the frontend only needs:

```json
{
  "id": "...",
  "name": "Rahul"
}
```

Send what the client actually needs.

---

# 27. Compression

For sufficiently large responses, HTTP compression can reduce network transfer size.

Conceptually:

```text
JSON
 ↓
compression
 ↓
network
 ↓
decompression
 ↓
client
```

But compression also costs CPU.

So again:

> Measure the trade-off.

---

# 28. Serialization Cost

Your API might retrieve data quickly but still be slow because of:

```text
large objects
nested objects
transformations
JSON serialization
```

For example:

```text
MongoDB:       80 ms
Service:       20 ms
Serialization: 300 ms
Network:       100 ms
```

In that case, optimizing MongoDB from:

```text
80 → 60 ms
```

is not your biggest opportunity.

---

# 29. External API Calls

Imagine:

```text
GET /dashboard
```

requires:

```text
MongoDB
Payment API
Analytics API
Notification service
```

If done sequentially:

```text
MongoDB
   ↓
Payment API
   ↓
Analytics API
   ↓
Notification API
```

latency can accumulate.

If some calls are independent:

```text
           ┌→ MongoDB
Request ───┼→ Payment
           ├→ Analytics
           └→ Notifications
```

you may be able to run them concurrently.

Again:

> Only where dependencies allow it.

---

# 30. The Critical Path

Imagine:

```text
MongoDB: 100 ms
Payment: 200 ms
Analytics: 150 ms
```

Sequential:

```text
100 + 200 + 150
=
450 ms
```

If independent and safely parallelized:

```text
max(100, 200, 150)
=
200 ms
```

plus overhead.

This is the **critical-path** idea.

The longest dependency chain often determines request latency.

---

# 31. Caching

We discussed caching earlier.

Caching can transform:

```text
Request
  ↓
Database
  ↓
Response
```

into:

```text
Request
  ↓
Cache HIT
  ↓
Response
```

But caching is not a replacement for fixing a terrible query.

If your query is:

```text
slow
incorrect
unindexed
over-fetching
```

you should understand and fix the underlying problem.

---

# 32. Cache the Right Things

Good candidates may include:

```text
rarely changing configuration
popular read-heavy data
expensive computed results
frequently requested reference data
```

Be careful with:

```text
highly personalized data
rapidly changing data
authorization-sensitive data
large combinations of query parameters
```

---

# 33. Cache Stampede

Suppose:

```text
cache expires
```

and suddenly:

```text
10,000 requests
```

arrive.

All 10,000 miss the cache:

```text
10,000 requests
      ↓
10,000 DB queries
```

The cache can actually cause a sudden load spike.

This is called a **cache stampede** or **thundering herd** problem.

Mitigation strategies include:

```text
request coalescing
locking
stale-while-revalidate
jittered expiration
```

You don't need to implement all of these immediately, but you should know the concept.

---

# 34. Rate Limiting and Performance

A public endpoint can receive:

```text
100 requests/sec
```

or:

```text
100,000 requests/sec
```

If each request triggers expensive work, the system can collapse.

Rate limiting helps protect:

```text
CPU
database
external APIs
memory
```

So performance and security are connected.

---

# 35. Backpressure

Suppose your API can safely process:

```text
100 expensive operations/sec
```

but traffic sends:

```text
10,000/sec
```

You need some way to prevent the system from endlessly accepting work.

Possible mechanisms include:

```text
rate limits
queues
bounded concurrency
timeouts
load shedding
circuit breakers
```

This is a more advanced scalability concept.

---

# 36. Timeouts

Never assume external operations will always respond.

Bad:

```text
API → external service
```

with no timeout.

If the external service hangs:

```text
request
   ↓
waiting
   ↓
waiting
   ↓
waiting
```

your resources can remain occupied.

Production systems should define appropriate timeouts.

---

# 37. Avoid Hidden Sequential Work

A common mistake:

```js
for (const item of items) {
    await process(item);
}
```

This is sequential.

Sometimes that's intentional.

But if the operations are independent, you might use controlled concurrency.

For example:

```text
10 items
   ↓
process 5 at a time
```

rather than:

```text
process 1
wait
process 1
wait
...
```

The correct concurrency level depends on the workload.

---

# 38. Don't Optimize With `Promise.all()` Everywhere

This deserves repetition because it's a common junior mistake.

Suppose you have:

```text
1000 independent database operations
```

Doing:

```js
await Promise.all(operations);
```

can generate a huge burst.

Better architecture may use:

```text
batching
controlled concurrency
bulk operations
```

---

# 39. Bulk Operations

Suppose you need to update:

```text
1000 records
```

Bad approach:

```text
update record 1
update record 2
update record 3
...
```

Depending on the operation, a bulk database operation can dramatically reduce round trips.

For MongoDB, concepts such as:

```text
bulkWrite
```

can be useful.

Again:

> The exact operation depends on the data and business rules.

---

# 40. Avoid Over-Fetching

Suppose:

```text
GET /users
```

returns:

```text
users
permissions
roles
organizations
preferences
activity
notifications
```

when the UI only needs:

```text
id
name
avatar
```

That's over-fetching.

A better endpoint representation is intentionally designed around the client's use case.

---

# 41. Avoid Under-Fetching

The opposite problem:

```text
GET /user
GET /user/preferences
GET /user/avatar
GET /user/organization
GET /user/permissions
```

might cause many requests.

So the goal isn't:

> "Always return less data."

The goal is:

> **Return the right amount of data for the use case.**

---

# 42. API Performance Is About Round Trips

A useful mental model:

```text
Performance
=
database work
+
network round trips
+
application work
+
serialization
+
external dependencies
```

Reducing unnecessary round trips can often produce large improvements.

---

# 43. Performance Budget

For an important endpoint, you might define a target such as:

```text
p95 latency < 300 ms
```

The important concept is **p95**, not only average latency.

Why?

Suppose:

```text
99 requests = 50 ms
1 request   = 10 seconds
```

The average can hide a bad tail.

---

# 44. Percentiles

Common metrics:

```text
p50
p90
p95
p99
```

Meaning approximately:

```text
p50 → median
p95 → 95% of requests are at or below this latency
p99 → 99% are at or below this latency
```

For production APIs, tail latency matters.

---

# 45. Why p99 Matters

Imagine:

```text
p50 = 80 ms
p95 = 200 ms
p99 = 2 sec
```

Most users are fast.

But a meaningful minority experience very slow requests.

This can indicate:

```text
database contention
cache misses
GC pauses
external API delays
large payloads
resource saturation
```

---

# 46. Observability

To diagnose performance, you need measurements.

Useful metrics:

```text
request count
latency
error rate
database latency
cache hit rate
CPU
memory
connection pool usage
external API latency
```

This is why logging, metrics, and tracing become important in production backend architecture.

---

# 47. Structured Performance Logging

Instead of:

```text
"Something took too long"
```

log structured information:

```json
{
  "requestId": "...",
  "route": "/api/v1/orders",
  "durationMs": 412,
  "dbDurationMs": 290,
  "statusCode": 200
}
```

This makes investigation much easier.

Be careful not to log sensitive data.

---

# 48. Request IDs

A request ID helps connect:

```text
API request
   ↓
service logs
   ↓
database logs
   ↓
external service logs
```

For example:

```text
requestId = abc123
```

Then you can search logs for:

```text
abc123
```

and reconstruct what happened.

This becomes very valuable in production debugging.

---

# 49. Distributed Tracing

In a larger architecture:

```text
API Gateway
    ↓
Backend
    ↓
Payment Service
    ↓
Database
```

a distributed trace can show:

```text
Request
├── backend: 100ms
├── database: 30ms
├── payment: 500ms
└── serialization: 20ms
```

Now you immediately see:

```text
payment service
```

is the bottleneck.

---

# 50. Performance Diagnosis Flow

When an endpoint is slow:

```text
1. Reproduce
      ↓
2. Measure latency
      ↓
3. Identify bottleneck
      ↓
4. Inspect query/external dependency
      ↓
5. Check indexes
      ↓
6. Check payload size
      ↓
7. Check N+1
      ↓
8. Optimize
      ↓
9. Measure again
```

This is much better than randomly changing code.

---

# 51. Gold Interview Scenario

### Interviewer:

> "Your endpoint takes 2 seconds. What would you do?"

Don't say:

> "I'll add Redis."

Instead:

> **"First I'd measure where the latency is coming from. I'd break down request, application, database, cache, and external-service timings. Then I'd inspect the slow database queries and query plans, check for N+1 operations, unnecessary round trips, over-fetching, missing indexes, and external dependency latency. I'd optimize the actual bottleneck and verify the improvement using latency metrics."**

That's a much stronger engineering answer.

---

# 52. Gold Interview Scenario — N+1

### Interviewer:

> "What is N+1?"

Answer:

> **"It's when retrieving a collection requires one query for the collection plus one additional query for each item. For example, fetching 100 posts and then querying the author separately for each post results in 101 queries. I'd typically solve it through batching, joins/population where appropriate, aggregation, or redesigning the data access pattern."**

---

# 53. Gold Interview Scenario — `lean()`

### Interviewer:

> "Why use `.lean()`?"

Answer:

> **"For read-only Mongoose queries where I don't need full Mongoose document behavior, `lean()` can return plain JavaScript objects and avoid document hydration overhead. I wouldn't use it blindly because it changes the returned object behavior and isn't appropriate when document-specific features are required."**

---

# 54. Gold Interview Scenario — Index

### Interviewer:

> "Should we create an index for every query?"

Answer:

> **"No. Indexes improve certain reads but add storage and write-maintenance costs. I'd examine actual query patterns, frequency, selectivity, and query plans before deciding which indexes are valuable."**

---

# 55. Gold Interview Scenario — `Promise.all()`

### Interviewer:

> "How would you optimize three independent API calls?"

Answer:

> **"If they're truly independent, I can execute them concurrently rather than sequentially, potentially reducing the critical path to roughly the slowest operation instead of the sum. But I'd control concurrency and consider downstream limits rather than blindly creating unlimited parallel requests."**

---

# 56. Performance Architecture

Your architecture should now look like:

```text
                       REQUEST
                          │
                          ▼
                    VALIDATION
                          │
                          ▼
                     CONTROLLER
                          │
                          ▼
                       SERVICE
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
           Cache       Repository   External APIs
             │            │            │
             │            ▼            │
             │         MongoDB         │
             │            │            │
             └────────────┼────────────┘
                          ▼
                    RESPONSE BUILD
                          │
                          ▼
                    SERIALIZATION
                          │
                          ▼
                       CLIENT
```

And around the entire system:

```text
        ┌────────────────────────────┐
        │       OBSERVABILITY        │
        │                            │
        │ logs / metrics / tracing   │
        └────────────────────────────┘
```

# 57. The Performance Checklist

When reviewing an API, ask:

### Database

```text
Is the query indexed?
Is the query plan healthy?
Are we fetching unnecessary documents?
Are we using projection?
Are we doing N+1 queries?
```

### Application

```text
Are we doing unnecessary computation?
Are independent operations sequential?
Are we creating excessive concurrency?
Are we serializing huge objects?
```

### Network

```text
Is the payload too large?
Are there unnecessary API round trips?
Can compression help?
```

### External services

```text
Are there unnecessary calls?
Can independent calls run concurrently?
Are timeouts configured?
Are retries controlled?
```

### Cache

```text
Is caching actually useful?
What's the hit rate?
Could stale data cause problems?
Could cache stampede occur?
```

### Observability

```text
Do we know where latency occurs?
Do we have p95/p99?
Can we trace a request?
```

# 🧠 Gold-Level Revision Sheet

Memorize these:

1. **Measure before optimizing.**
    
2. API latency is a system-level problem.
    
3. Don't automatically blame MongoDB.
    
4. N+1 means one query plus one query per returned item.
    
5. Solve N+1 with batching, aggregation, population/joins where appropriate, or better data access patterns.
    
6. Avoid unnecessary database round trips.
    
7. Use projection to avoid fetching unnecessary fields.
    
8. Projection can also prevent accidental exposure of sensitive fields.
    
9. `lean()` can reduce Mongoose hydration overhead for suitable read-only operations.
    
10. `lean()` isn't universally appropriate.
    
11. Use indexes based on real query patterns.
    
12. Inspect query plans instead of guessing.
    
13. `Promise.all()` can reduce latency for independent operations.
    
14. Unlimited concurrency can overload dependencies.
    
15. Use bulk operations where appropriate.
    
16. Avoid over-fetching.
    
17. Avoid unnecessary under-fetching and excessive client round trips.
    
18. Caching is useful for appropriate read-heavy workloads, but doesn't replace fixing bad queries.
    
19. Cache stampedes can create sudden database load.
    
20. Use timeouts for external dependencies.
    
21. Think about the critical path.
    
22. Measure p50, p95, and p99 latency.
    
23. Structured logs help diagnose performance.
    
24. Request IDs help trace individual requests.
    
25. Distributed tracing helps locate cross-service bottlenecks.

```text
                  │
                  ▼
               CACHE
                  │
             hit / miss
             invalidation
                  │
                  ▼
             MEASURE AGAIN
```

The most important lesson is not **"how to make an API fast."**

It's:

> **"How to systematically identify the bottleneck and improve the correct part of the system."**

That is the difference between knowing backend code and thinking like a backend engineer.
