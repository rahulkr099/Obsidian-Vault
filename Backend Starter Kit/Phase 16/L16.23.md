# Phase 16 — API Architecture

## Lesson 16.23 — API Reliability Architecture

We have covered **query architecture** and **performance architecture**.

Now we move into another area interviewers care about heavily:

> **What happens when something goes wrong?**

A beginner thinks:

```text
Request → Controller → Database → Response
```

A production backend engineer thinks:

```text
Request
   ↓
What if DB is down?
What if Redis is down?
What if another API is slow?
What if the client retries?
What if the request is duplicated?
What if traffic suddenly increases?
What if a dependency returns an error?
What if our server crashes halfway through an operation?
```

That's **reliability engineering**.

---

# 1. What Is API Reliability?

API reliability means your API behaves correctly and predictably even when parts of the system fail.

It does **not** mean:

> "The API never fails."

That's impossible.

Instead:

> **A reliable system fails in controlled, observable, and recoverable ways.**

For example:

```text
Payment service unavailable
        ↓
Your API
        ↓
controlled failure
        ↓
useful error response
        ↓
system remains healthy
```

rather than:

```text
Payment service unavailable
        ↓
requests hang
        ↓
connections exhausted
        ↓
CPU increases
        ↓
database overloaded
        ↓
entire API crashes
```

---

# 2. Failure Is Normal

In production, failures happen.

Examples:

```text
Database temporarily unavailable
Redis timeout
Network failure
DNS failure
External API outage
Server restart
Container crash
Deployment problem
Traffic spike
Malformed request
Dependency overload
```

Good architecture assumes failures will happen.

---

# 3. The Reliability Mindset

Instead of asking:

> "How do I prevent every failure?"

ask:

> **"How does my system behave when this component fails?"**

For every dependency, ask:

```text
What happens if it is:
    slow?
    unavailable?
    returning errors?
    returning invalid data?
```

This is a powerful interview mindset.

---

# 4. Timeouts

One of the most important reliability mechanisms is a timeout.

Imagine:

```text
API
 ↓
Payment Service
```

and the payment service stops responding.

Without a timeout:

```text
Request
   ↓
waiting...
   ↓
waiting...
   ↓
waiting...
```

Your server resources remain occupied.

With a timeout:

```text
Request
   ↓
Payment Service
   ↓
timeout
   ↓
controlled failure
```

The request can terminate.

---

# 5. Why Infinite Waiting Is Dangerous

Suppose your server has capacity for:

```text
1000 concurrent requests
```

Now an external service hangs.

If:

```text
1000 requests
```

are waiting for that service, your application can run out of available resources.

Then even healthy requests may start failing.

One slow dependency can therefore cause a **cascading failure**.

---

# 6. Cascading Failure

This is an important interview concept.

Imagine:

```text
API
 ↓
Payment Service
```

Payment becomes slow.

Then:

```text
API requests wait longer
        ↓
more requests remain active
        ↓
connection/resource usage increases
        ↓
API becomes slower
        ↓
more requests accumulate
        ↓
API becomes overloaded
```

Eventually:

```text
Payment problem
      ↓
API problem
      ↓
Database problem
      ↓
system-wide failure
```

That's a cascading failure.

---

# 7. Timeouts Limit the Damage

Timeouts don't fix the dependency.

They protect your system from waiting indefinitely.

Conceptually:

```text
Dependency request
       │
       ├── succeeds → continue
       │
       └── timeout → fail fast
```

This gives your system a boundary.

---

# 8. Timeout Types

In a real system, there can be multiple timeout layers:

```text
Client timeout
    ↓
Load balancer timeout
    ↓
API server timeout
    ↓
HTTP client timeout
    ↓
Database timeout
```

Each layer should be designed intentionally.

You don't want:

```text
client timeout = 2 seconds
server timeout = 30 seconds
```

if the client will always give up first.

Timeouts should make sense across the request chain.

---

# 9. Retry

Sometimes failures are temporary.

For example:

```text
Request → external API
              ↓
         temporary network failure
```

A retry might succeed.

Conceptually:

```text
Attempt 1 → failure
Attempt 2 → success
```

Retries can be useful.

But:

> **Retries can also make an outage worse.**

---

# 10. Retry Storm

Suppose an external service is already overloaded.

Your system receives:

```text
10,000 requests
```

and each request retries 3 times.

You might create:

```text
30,000 dependency requests
```

instead of:

```text
10,000
```

You just increased the load on an already failing service.

This can create a **retry storm**.

---

# 11. Exponential Backoff

Instead of retrying immediately:

```text
retry
retry
retry
```

use increasing delays.

Conceptually:

```text
Attempt 1
   ↓
small delay
   ↓
Attempt 2
   ↓
larger delay
   ↓
Attempt 3
```

For example:

```text
100 ms
200 ms
400 ms
800 ms
```

The exact values depend on the system.

---

# 12. Jitter

If 10,000 requests all fail at the same time and all use:

```text
100 ms
200 ms
400 ms
```

they may retry at almost exactly the same moments.

That creates synchronized retry spikes.

**Jitter** adds randomness to retry delays.

Conceptually:

```text
100ms + random amount
200ms + random amount
400ms + random amount
```

This spreads retry traffic.

---

# 13. Retry Only When Appropriate

Not every error should be retried.

For example:

```text
401 Unauthorized
```

retrying immediately usually doesn't solve anything.

Similarly:

```text
400 Bad Request
```

shouldn't normally be retried.

But a temporary network failure may be retryable.

The key question is:

> **Is this failure likely to succeed if attempted again?**

---

# 14. Idempotency

This is one of the **most important concepts in API reliability**.

Suppose the client sends:

```http
POST /payments
```

The server processes the payment.

But before the response reaches the client:

```text
network failure
```

The client thinks:

```text
"I don't know whether the payment succeeded."
```

So it retries:

```http
POST /payments
```

Now you might accidentally charge the customer twice.

---

# 15. Idempotency Keys

A common solution is an idempotency key.

Client sends:

```http
POST /payments
Idempotency-Key: abc123
```

Server records:

```text
abc123 → payment result
```

If the client retries:

```http
POST /payments
Idempotency-Key: abc123
```

the server recognizes:

```text
"This is the same operation."
```

and avoids creating another payment.

---

# 16. Idempotency Is Not Just for Payments

It can be useful for operations such as:

```text
Create order
Create subscription
Send important command
Create invoice
Process webhook
Submit job
```

Especially when clients may retry.

---

# 17. Idempotent vs Non-Idempotent

An operation is idempotent when repeating it produces the same intended result.

For example:

```http
PUT /users/123
```

with:

```json
{
  "name": "Rahul"
}
```

repeating it should leave the user in the same state.

But:

```http
POST /payments
```

could create a new transaction each time.

Therefore, POST operations often need special consideration when retries are possible.

---

# 18. Exactly-Once Is Difficult

A common interview trap:

> "Can you guarantee exactly-once processing?"

In distributed systems, exactly-once behavior across multiple systems is difficult.

For example:

```text
API
 ↓
Database
 ↓
Payment provider
```

What if:

```text
payment succeeds
↓
server crashes
↓
database update never happens
```

You now have a consistency problem.

This is why reliable systems often use:

```text
idempotency
durable state
transactions where appropriate
reconciliation
event processing
```

rather than assuming exactly-once execution is trivial.

---

# 19. Circuit Breaker

Another important reliability pattern is the **circuit breaker**.

Imagine:

```text
Your API
   ↓
External Service
```

The external service is failing repeatedly.

Instead of continuing:

```text
request → failure
request → failure
request → failure
request → failure
```

the circuit breaker can open:

```text
Your API
   ↓
CIRCUIT OPEN
   ↓
fail quickly
```

Your system stops repeatedly hitting the unhealthy dependency.

---

# 20. Circuit Breaker States

A simplified circuit breaker has three states:

```text
CLOSED
   ↓
failures increase
   ↓
OPEN
   ↓
wait
   ↓
HALF-OPEN
   ↓
test request
```

If the test succeeds:

```text
HALF-OPEN → CLOSED
```

If it fails:

```text
HALF-OPEN → OPEN
```

---

# 21. Why Circuit Breakers Help

Without a circuit breaker:

```text
Dependency failing
      ↓
keep calling it
      ↓
waste resources
      ↓
increase latency
```

With one:

```text
Dependency failing
      ↓
circuit opens
      ↓
fail fast
      ↓
protect application
```

This is especially useful for expensive external dependencies.

---

# 22. Circuit Breaker vs Timeout

They solve different problems.

### Timeout

Answers:

> "How long should I wait?"

### Circuit breaker

Answers:

> "Should I even attempt this dependency right now?"

They often work together:

```text
request
 ↓
circuit breaker
 ↓
external call
 ↓
timeout
```

---

# 23. Graceful Degradation

A highly useful production concept.

Suppose:

```text
GET /dashboard
```

depends on:

```text
User data
Recommendations
Analytics
Notifications
```

What if recommendations fail?

Do you necessarily fail the entire dashboard?

Maybe not.

You could return:

```json
{
  "user": {...},
  "notifications": [...],
  "recommendations": []
}
```

with an indication that recommendations are temporarily unavailable.

This is **graceful degradation**.

---

# 24. Not Everything Is Equally Important

Imagine an e-commerce page:

```text
Product information      critical
Price                    critical
Inventory                 critical
Recommendations          optional
Analytics                 optional
```

If analytics fails:

```text
Don't necessarily fail checkout.
```

This is reliability through **dependency prioritization**.

---

# 25. Fail Open vs Fail Closed

This is an important security/reliability concept.

Suppose a permission-checking service is unavailable.

Should you allow access?

Usually for authorization:

```text
dependency unavailable
       ↓
deny access
```

This is **fail closed**.

For some non-security features:

```text
recommendation service unavailable
       ↓
show no recommendations
```

could be a form of **fail open/degraded behavior**.

The correct choice depends on the function.

---

# 26. Never Fail Open for Security-Critical Decisions Without a Very Strong Reason

Consider:

```text
Authorization service
       ↓
unavailable
```

If your fallback is:

```text
"Assume user is authorized."
```

you may create a serious security vulnerability.

Security-sensitive decisions should generally prefer safe denial.

---

# 27. Bulkheads

Another useful reliability pattern is the **bulkhead pattern**.

Imagine one external service consumes all your resources.

For example:

```text
Payment requests
Recommendation requests
Email requests
```

all share the same worker pool.

If recommendations suddenly become extremely slow:

```text
recommendation requests
        ↓
consume all workers
        ↓
payment requests can't run
```

That's bad.

Bulkheads isolate resources:

```text
Payment workers
Recommendation workers
Email workers
```

Now one workload is less likely to destroy another.

---

# 28. Resource Isolation

Bulkheads can be implemented through things such as:

```text
separate queues
bounded concurrency
separate worker pools
connection limits
resource quotas
```

The exact mechanism depends on the architecture.

---

# 29. Queue-Based Reliability

Suppose a request needs to perform expensive work:

```text
Generate report
```

Instead of:

```text
HTTP request
   ↓
generate report
   ↓
wait 30 seconds
   ↓
response
```

you can use:

```text
HTTP request
   ↓
create job
   ↓
queue
   ↓
202 Accepted
```

Then:

```text
Worker
   ↓
process job
   ↓
store result
```

The client can later retrieve the result.

---

# 30. Why Queues Improve Reliability

Queues provide:

```text
buffering
controlled processing
retry capability
asynchronous work
load smoothing
```

Suppose traffic suddenly increases:

```text
10 jobs/sec
   ↓
1000 jobs/sec
```

Instead of immediately overwhelming the worker:

```text
requests
   ↓
queue
   ↓
workers process at safe speed
```

The queue absorbs some of the burst.

---

# 31. But Queues Don't Magically Fix Capacity

If you receive:

```text
1000 jobs/sec
```

but process:

```text
100 jobs/sec
```

the queue grows.

Eventually:

```text
queue size
   ↑
   ↑
   ↑
```

So queue systems need:

```text
monitoring
capacity planning
dead-letter handling
backpressure
```

---

# 32. Dead-Letter Queue

Suppose a job repeatedly fails:

```text
Job
 ↓
attempt 1 → fail
 ↓
attempt 2 → fail
 ↓
attempt 3 → fail
```

Instead of retrying forever:

```text
Job
 ↓
Dead Letter Queue
```

This allows engineers to inspect and recover problematic messages.

---

# 33. Poison Messages

A **poison message** is a job/message that repeatedly fails processing.

For example:

```text
invalid data
```

If you retry forever:

```text
retry
retry
retry
retry
...
```

you waste resources.

Dead-letter mechanisms prevent infinite retry loops.

---

# 34. Error Classification

A reliable API distinguishes between different errors.

For example:

```text
400 → client sent invalid request
401 → authentication required/invalid
403 → not authorized
404 → resource not found
409 → conflict
429 → rate limited
500 → internal server error
502/503 → dependency/service problem
504 → timeout
```

The exact semantics depend on the API design, but the principle is:

> **Errors should communicate useful meaning.**

---

# 35. Don't Leak Internal Errors

Bad:

```json
{
  "error": "MongoServerError: E11000 duplicate key collection users index ..."
}
```

This exposes internal implementation details.

Better:

```json
{
  "error": {
    "code": "USER_EMAIL_EXISTS",
    "message": "A user with this email already exists."
  }
}
```

Internally, you can log the technical error.

Externally, return a safe representation.

---

# 36. Error Response Consistency

Your APIs should have a predictable structure.

For example:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request.",
    "details": [...]
  }
}
```

Then clients don't have to guess how errors work across endpoints.

---

# 37. Error Codes vs Messages

Messages can change.

Codes should be more stable.

For example:

```text
USER_NOT_FOUND
EMAIL_ALREADY_EXISTS
INVALID_TOKEN
RATE_LIMITED
PAYMENT_FAILED
```

Frontend code can react to:

```text
PAYMENT_FAILED
```

instead of parsing:

```text
"Something went wrong while processing your payment."
```

---

# 38. Health Checks

A production API should often expose health information.

Conceptually:

```http
GET /health
```

But there's an important distinction.

---

# 39. Liveness

Liveness asks:

> **Is the application process alive?**

For example:

```text
GET /health/live
```

might simply indicate:

```json
{
  "status": "ok"
}
```

It should generally be lightweight.

---

# 40. Readiness

Readiness asks:

> **Is this instance ready to receive traffic?**

For example:

```text
GET /health/ready
```

might verify necessary dependencies.

Conceptually:

```text
Application running?
        ↓
Database connection ready?
        ↓
Required dependencies ready?
        ↓
Ready for traffic?
```

This distinction is especially useful with containers and orchestration systems.

---

# 41. Don't Make Liveness Too Expensive

A common mistake is:

```text
/health
   ↓
query database
   ↓
query Redis
   ↓
call every external service
```

on every health check.

Now your health-check system itself creates load.

Keep health checks purposeful.

---

# 42. Graceful Shutdown

Suppose your server is being restarted.

You don't want:

```text
server receives request
      ↓
process killed
      ↓
operation interrupted
```

Instead:

```text
Shutdown signal
      ↓
stop accepting new traffic
      ↓
finish existing requests
      ↓
close resources
      ↓
exit
```

This is graceful shutdown.

---

# 43. Why Graceful Shutdown Matters

Without graceful shutdown:

```text
in-flight requests
database operations
queue processing
external calls
```

may be interrupted.

This can cause:

```text
failed requests
partial work
duplicate retries
inconsistent states
```

Graceful shutdown reduces these problems.

---

# 44. Reliability and Deployment

Suppose you deploy a new version:

```text
v1 → v2
```

If all servers are replaced simultaneously:

```text
100% v1
    ↓
100% v2
```

a deployment bug can cause a large outage.

Safer strategies include:

```text
rolling deployment
blue-green deployment
canary deployment
```

We'll study deployment architecture more deeply later.

---

# 45. SLO / SLA / SLI

These are useful interview concepts.

### SLI

**Service Level Indicator**

A measurement.

Example:

```text
request success rate
p95 latency
```

### SLO

**Service Level Objective**

A target.

Example:

```text
99.9% successful requests
p95 latency < 300 ms
```

### SLA

**Service Level Agreement**

A formal commitment, often involving customers/business consequences.

---

# 46. Reliability Is More Than Uptime

A service can be "up" but terrible.

For example:

```text
HTTP 200
```

but:

```text
response takes 30 seconds
```

Technically available, practically unusable.

That's why reliability should consider:

```text
availability
latency
correctness
error rate
```

---

# 47. Error Budget

Suppose your SLO is:

```text
99.9% availability
```

That means you have a small amount of allowed failure.

This becomes an **error budget**.

Teams can use this concept to balance:

```text
feature development
```

against:

```text
reliability work
```

If the system is burning the error budget too quickly, reliability work becomes more urgent.

---

# 48. Reliability Doesn't Mean "Never Return Errors"

This is a subtle but important point.

Imagine the database is unavailable.

A reliable API may return:

```http
503 Service Unavailable
```

quickly.

An unreliable API may:

```text
hang for 60 seconds
```

and eventually crash.

The first system is actually more reliable because it fails **predictably and safely**.

---

# 49. Gold Interview Question

### "How would you prevent one failing dependency from taking down your API?"

A strong answer:

> **"I'd isolate the dependency with timeouts, bounded concurrency, and potentially a circuit breaker. I'd use retries only for transient failures with exponential backoff and jitter. For non-critical functionality I'd consider graceful degradation, while security-critical decisions should fail safely. I'd also monitor dependency latency and error rates so we can detect the failure early."**

Excellent.

---

# 50. Gold Interview Question

### "What happens if a client retries a POST request?"

Strong answer:

> **"It depends on whether the operation is safely repeatable. For operations such as payments or order creation, I'd use an idempotency key or another deduplication mechanism so a retry doesn't create duplicate side effects. I'd also consider transaction boundaries and how failures between external systems and our database are reconciled."**

---

# 51. Gold Interview Question

### "Why are retries dangerous?"

Answer:

> **"Retries can amplify load during an outage. If many clients retry immediately, they can create a retry storm and make the dependency even less healthy. I'd retry only appropriate transient failures, use exponential backoff and jitter, and impose a maximum number of attempts."**

---

# 52. Gold Interview Question

### "What is a circuit breaker?"

Answer:

> **"A circuit breaker prevents repeatedly calling a dependency that is currently failing. After enough failures it opens and fails requests quickly, then periodically allows a test request in a half-open state. If the dependency recovers, the circuit closes again."**

---

# 53. Gold Interview Question

### "What is graceful degradation?"

Answer:

> **"It means keeping the core functionality available when a non-critical dependency fails. For example, a dashboard might still return user data and notifications while omitting recommendations if the recommendation service is unavailable."**

---

# 54. Gold Interview Question

### "What is the difference between liveness and readiness?"

Answer:

> **"Liveness tells us whether the process is alive and should generally remain lightweight. Readiness tells us whether the instance is capable of serving traffic, which can include checking required dependencies. They're useful for orchestration and traffic management."**

---

Your mental model should now look like:

```text
                           ▼
                    ┌─────────────┐
```

Around the system:

```text
metrics
```

# 🧠 Gold-Level Revision Sheet

Remember these concepts:

1. **Reliability means controlled failure, not zero failure.**
    
2. Assume dependencies can fail.
    
3. Use timeouts to prevent indefinite waiting.
    
4. One slow dependency can cause cascading failures.
    
5. Retries can help transient failures.
    
6. Retries can also create retry storms.
    
7. Use exponential backoff.
    
8. Add jitter to prevent synchronized retries.
    
9. Don't retry permanent client errors blindly.
    
10. Idempotency protects against duplicate side effects.
    
11. Idempotency keys are especially useful for payment/order-like operations.
    
12. Exactly-once processing is difficult in distributed systems.
    
13. Circuit breakers protect unhealthy dependencies.
    
14. Timeouts and circuit breakers solve different problems.
    
15. Graceful degradation keeps core functionality alive when optional dependencies fail.
    
16. Security-sensitive decisions generally should fail closed.
    
17. Bulkheads isolate resource consumption.
    
18. Queues can buffer expensive asynchronous work.
    
19. Dead-letter queues prevent endlessly retrying poison messages.
    
20. Health checks distinguish liveness from readiness.
    
21. Graceful shutdown protects in-flight work.
    
22. Consistent error responses improve API reliability and client behavior.
    
23. Request IDs help trace failures.
    
24. SLI = measurement.
    
25. SLO = target.
    
26. SLA = formal commitment.
    
27. Error budgets help balance reliability and feature velocity.
    
28. **A reliable API should fail fast, fail safely, recover when possible, and remain observable.**

## 🎯 The Interview Mental Model

When an interviewer asks:

> **"How would you design a reliable API?"**

Think:

```text
                 RELIABLE API
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
    PREVENT         CONTAIN        RECOVER
       │              │              │
   validation       timeout         retry
   rate limit       circuit         backoff
   idempotency      breaker         queue
                    bulkhead        DLQ
       │              │              │
       └──────────────┼──────────────┘
                      ▼
                 OBSERVABILITY
                      │
             logs / metrics / traces
                      │
                      ▼
                  IMPROVE
```

The key principle to remember is:

> **Don't design only for the happy path. Design the API around what happens when dependencies are slow, unavailable, duplicated, overloaded, or partially failed.**

That is one of the biggest differences between a **CRUD developer** and a **production backend engineer**.
