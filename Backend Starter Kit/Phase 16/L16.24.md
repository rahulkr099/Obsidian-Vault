# Phase 16 — API Architecture

## Lesson 16.24 — API Resilience: Retries, Idempotency & Failure Recovery

We already covered reliability at a high level in **16.23**. Now we're going one level deeper.

This lesson is especially important for interviews because it tests whether you understand what happens when **requests fail halfway through real-world operations**.

---

# 1. The Real Problem: Partial Failure

Consider:

```text
POST /orders
```

Your server performs:

```text
1. Create order
2. Charge payment
3. Send confirmation email
```

Now imagine:

```text
Create order     ✅
Charge payment   ✅
Send email       ❌
```

Should the entire order be considered failed?

No.

The order and payment may already exist.

This is called **partial failure**.

---

# 2. Another Example

Imagine:

```text
POST /orders
```

The server:

```text
Create order
   ↓
Charge payment
   ↓
Return response
```

Payment succeeds:

```text
Payment provider → SUCCESS
```

But before your server sends the response:

```text
Server crashes
```

The client receives:

```text
No response
```

The client thinks:

> "Maybe the request failed."

So it retries.

Now:

```text
POST /orders
```

again.

Potential result:

```text
Order #1
Payment #1 ✅

Order #2
Payment #2 ❌
```

or worse:

```text
Payment #1
Payment #2
```

The user has been charged twice.

---

# 3. This Is Why Reliability Is Hard

The difficult question isn't:

> "What happens when an operation succeeds?"

It's:

> **"What happens when the system doesn't know whether an operation succeeded?"**

This state is extremely important.

You can have:

```text
SUCCESS
FAILURE
UNKNOWN
```

The **UNKNOWN** state is where distributed-system problems become interesting.

---

# 4. The Three Outcomes

Suppose your API calls a payment service.

### Success

```text
API → Payment
       ↓
    SUCCESS
```

Easy.

### Failure

```text
API → Payment
       ↓
     FAIL
```

Potentially manageable.

### Unknown

```text
API → Payment
       ↓
     SUCCESS
       ↓
Network failure
       ↓
API doesn't know result
```

Now the API cannot safely assume:

```text
"Payment failed."
```

because payment might actually have succeeded.

---

# 5. Never Treat Network Failure as Business Failure

This is a very important principle.

Suppose:

```text
Payment API
   ↓
request
   ↓
network timeout
```

You cannot automatically conclude:

```text
payment = failed
```

It might mean:

```text
request never reached provider
```

or:

```text
provider rejected request
```

or:

```text
provider processed request but response was lost
```

These are very different situations.

---

# 6. Idempotency Solves One Major Problem

Use an idempotency key:

```http
POST /payments
Idempotency-Key: 7f3a...
```

The client intends:

```text
"Perform this logical payment operation."
```

The key identifies that operation.

If the request is retried:

```http
POST /payments
Idempotency-Key: 7f3a...
```

the server can recognize:

```text
"This operation was already processed."
```

---

# 7. Idempotency Is About the Operation, Not the Request

This distinction is important.

You may have:

```text
Request #1
Request #2
Request #3
```

but all three represent:

```text
ONE logical operation
```

because they use:

```text
Idempotency-Key: abc123
```

Therefore:

```text
3 HTTP requests
        ↓
1 logical operation
```

That's the goal.

---

# 8. Basic Idempotency Flow

Conceptually:

```text
Client
  │
  │ Idempotency-Key: abc123
  ▼
API
  │
  ├── Has abc123 been processed?
  │
  ├── NO → process operation
  │
  └── YES → return stored result
```

The server needs durable storage for the idempotency record.

For example:

```text
idempotency_key
status
response
created_at
```

---

# 9. Why Memory Isn't Enough

Don't store:

```js
const processedKeys = new Set();
```

in production.

Why?

Because:

```text
server restart
```

would erase it.

Also:

```text
multiple server instances
```

would each have different memory.

You could have:

```text
Request 1 → Server A
Request 2 → Server B
```

Server A knows:

```text
abc123 already processed
```

Server B doesn't.

That's dangerous.

---

# 10. Use Shared Durable Storage

Depending on the architecture, idempotency state might be stored in:

```text
database
Redis
dedicated idempotency store
```

The important requirement is:

> **All relevant application instances must be able to see the same state.**

---

# 11. Idempotency Record

Conceptually:

```json
{
  "key": "abc123",
  "status": "completed",
  "response": {
    "orderId": "order_123"
  },
  "createdAt": "..."
}
```

Then:

```text
Retry
 ↓
lookup abc123
 ↓
completed
 ↓
return stored response
```

No duplicate business operation.

---

# 12. What If Two Requests Arrive at the Same Time?

This is where things become more interesting.

Suppose:

```text
Request A → idempotency key abc123
Request B → idempotency key abc123
```

both arrive simultaneously.

Both might check:

```text
"Does abc123 exist?"
```

Both get:

```text
NO
```

Then both process the operation.

You still have duplication.

---

# 13. Check-Then-Act Race Condition

This is the classic problem:

```text
if (!exists(key)) {
    createOperation();
}
```

Two processes can execute this concurrently.

Timeline:

```text
Request A          Request B

check → missing
                   check → missing

process
                   process
```

Now:

```text
duplicate operation
```

---

# 14. Atomicity

You need an atomic mechanism.

Conceptually:

```text
CREATE idempotency key
        ↓
    atomic operation
```

Only one request should win.

For example:

```text
abc123 → CREATED
```

The second request sees:

```text
abc123 already exists
```

and knows another request owns that operation.

This is where:

```text
unique constraints
atomic inserts
distributed locks
```

can become useful.

---

# 15. Database Unique Constraint

One simple pattern is:

```text
idempotency_key UNIQUE
```

Then:

```text
Request A → insert abc123 → success
Request B → insert abc123 → duplicate key
```

Now only one request can establish ownership.

The exact implementation depends on your database.

---

# 16. But Don't Just Return "Duplicate"

Suppose Request B arrives while Request A is still processing.

You might have:

```text
abc123
status = PROCESSING
```

Request B should not necessarily receive:

```text
"duplicate"
```

Instead, the API needs a defined policy.

Possibilities:

```text
wait for original result
return conflict/in-progress
poll
return the existing operation status
```

The correct choice depends on the API contract.

---

# 17. Idempotency State Machine

A useful model:

```text
             ┌──────────────┐
             │   ABSENT     │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │  PROCESSING  │
             └──────┬───────┘
                    │
             ┌──────┴──────┐
             ▼             ▼
        COMPLETED        FAILED
```

Potentially:

```text
PROCESSING
    ↓
TIMEOUT / UNKNOWN
```

can require special handling.

---

# 18. The UNKNOWN State Again

Imagine:

```text
API
 ↓
Payment provider
 ↓
payment succeeds
 ↓
response lost
```

Your local state might say:

```text
PROCESSING
```

But payment provider says:

```text
SUCCESS
```

Now you need a way to reconcile the state.

---

# 19. Reconciliation

A mature payment system may have:

```text
payment status
provider transaction ID
webhooks
periodic reconciliation
```

For example:

```text
Our DB:
payment = processing

Provider:
payment = succeeded
```

A reconciliation process can detect:

```text
inconsistent state
```

and repair it.

---

# 20. Webhooks

Many external systems use webhooks to communicate state changes.

For example:

```text
Our API
   ↓
Payment Provider
```

Later:

```text
Payment Provider
   ↓
Webhook
   ↓
Our API
```

The webhook may say:

```text
payment.succeeded
```

Your system updates:

```text
payment = succeeded
```

---

# 21. But Webhooks Can Also Be Duplicated

A provider may send:

```text
Webhook #1
payment.succeeded

Webhook #2
payment.succeeded
```

This can happen because webhook delivery is commonly designed around retryable delivery.

Therefore:

> **Webhook handlers should also be idempotent.**

---

# 22. Webhook Idempotency

Suppose the webhook contains:

```text
eventId = evt_123
```

Store:

```text
evt_123 → processed
```

If the same event arrives again:

```text
evt_123
```

your system recognizes it.

So:

```text
same event
    ↓
same effect
```

instead of:

```text
same event
    ↓
duplicate side effect
```

---

# 23. Idempotency at Multiple Boundaries

A reliable system may need idempotency at several levels:

```text
Client → API
API → payment provider
Provider → webhook
Queue → worker
```

Each boundary may have different failure behavior.

This is a powerful interview point.

---

# 24. Queue Job Idempotency

Suppose:

```text
Queue
 ↓
Worker
```

Worker receives:

```text
job_123
```

It starts processing.

Then:

```text
worker crashes
```

The queue retries:

```text
job_123
```

Now the worker must determine:

```text
"Was this job already applied?"
```

If the operation isn't idempotent, you can create duplicate effects.

---

# 25. Example

Suppose a worker sends:

```text
Welcome email
```

If the job runs twice:

```text
Email #1
Email #2
```

The user gets two emails.

A system could use:

```text
event ID
deduplication key
processed-events table
```

to avoid duplicate processing.

---

# 26. At-Least-Once Delivery

Many message systems effectively provide:

> **At-least-once delivery**

Meaning:

```text
message should be delivered
```

but:

```text
message may be delivered more than once
```

Therefore:

> **Consumers should often be idempotent.**

This is one of the most important distributed-systems concepts to understand.

---

# 27. Exactly-Once Processing

People often say:

> "We need exactly-once processing."

But exactly-once behavior across multiple systems is difficult.

For example:

```text
Queue
 ↓
Worker
 ↓
Database
 ↓
External API
```

There are multiple failure points.

A more practical architecture is often:

```text
at-least-once delivery
+
idempotent processing
+
deduplication
+
reconciliation
```

This produces **effectively-once business behavior** for the operations that matter.

---

# 28. Transaction vs Idempotency

These are different.

### Transaction

Helps maintain atomicity within a transaction boundary.

Example:

```text
Database operation A
+
Database operation B
```

either both succeed or both roll back.

### Idempotency

Helps safely handle repeated attempts.

Example:

```text
same HTTP request
retry
retry
```

without creating duplicate effects.

You may need both.

---

# 29. Database Transaction Example

Suppose:

```text
Create order
Decrease inventory
```

If both happen in the same database transaction:

```text
BEGIN
  create order
  decrease inventory
COMMIT
```

then a database failure can roll back the transaction.

But suppose:

```text
Database
+
External Payment API
```

are involved.

A database transaction cannot automatically roll back an external payment.

That's where distributed consistency becomes difficult.

---

# 30. Distributed Transaction Problem

Imagine:

```text
BEGIN DB TRANSACTION

create order

call payment provider
     ↓
     SUCCESS

DB crashes

ROLLBACK
```

The database may roll back:

```text
order
```

but the payment provider cannot magically roll back.

Now:

```text
Payment = successful
Order = doesn't exist
```

That's a consistency problem.

---

# 31. Saga Pattern

For workflows involving multiple systems, you may eventually use a **Saga** style approach.

Instead of one global transaction:

```text
Step 1
Step 2
Step 3
```

you define:

```text
Step
 ↓
compensating action if needed
```

For example:

```text
Create order
   ↓
Charge payment
   ↓
Reserve inventory
```

If inventory reservation fails:

```text
refund payment
cancel order
```

Conceptually:

```text
Forward actions
      ↓
Compensating actions
```

---

# 32. Saga Is Not a Magic Rollback

This is an important interview distinction.

A database rollback:

```text
ROLLBACK
```

can restore transactional state inside that transaction.

A Saga uses:

```text
business-level compensating actions
```

Example:

```text
charge payment
```

compensates with:

```text
refund payment
```

That's not the same as a database rollback.

---

# 33. When Should You Use a Saga?

Don't introduce a Saga just because you have two function calls.

It's useful when you have:

```text
multiple services
long-running workflows
distributed state changes
business-level compensation
```

For a simple single-database operation, a normal database transaction may be enough.

---

# 34. Outbox Pattern

Another gold-level concept.

Suppose your service needs to:

```text
1. Update database
2. Publish event
```

You might write:

```text
DB update → SUCCESS
Event publish → FAILURE
```

Now the database changed, but the event wasn't published.

Your system is inconsistent.

---

# 35. Transactional Outbox

The Outbox Pattern solves this by storing the event in the same database transaction.

Conceptually:

```text
BEGIN TRANSACTION

update order

insert event into outbox

COMMIT
```

Now both are committed together.

Later:

```text
Outbox worker
    ↓
read event
    ↓
publish event
    ↓
mark processed
```

This creates a reliable bridge between:

```text
database state
```

and:

```text
event publishing
```

---

# 36. Why Outbox Is Powerful

Without outbox:

```text
DB update
   ↓
event publish
```

has a failure gap.

With outbox:

```text
DB transaction
 ├── business change
 └── outbox event
        ↓
      commit
        ↓
   background publisher
```

The event is durably recorded.

---

# 37. Outbox Still Needs Idempotency

Suppose:

```text
Outbox worker
 ↓
publish event
 ↓
provider receives event
 ↓
worker crashes before marking it processed
```

Worker retries:

```text
publish event again
```

So consumers should often handle duplicate events.

Again:

```text
At-least-once delivery
+
idempotent consumer
```

is a common reliability strategy.

---

# 38. Retry Taxonomy

Not all retries are equal.

### Network retry

```text
connection reset
timeout
temporary DNS issue
```

Potentially retryable.

### HTTP retry

Some status codes may indicate temporary conditions.

For example:

```text
429
503
```

may be retryable depending on the API contract.

### Business failure

Example:

```text
insufficient funds
```

Usually not useful to retry immediately.

---

# 39. Retry Policy

A mature retry policy should answer:

```text
What errors are retryable?
How many attempts?
How long between attempts?
Is backoff used?
Is jitter used?
What is the total retry deadline?
What happens after retries are exhausted?
```

Don't simply write:

```js
for (let i = 0; i < 10; i++) {
    tryAgain();
}
```

That's not a reliability strategy.

---

# 40. Retry Budget

Retries consume resources.

Suppose:

```text
original traffic = 1000 req/sec
```

and each request can retry twice.

Worst-case dependency traffic could approach:

```text
3000 attempts/sec
```

Therefore retries should have a budget.

The idea is:

> **Retries must not become a larger source of load than the original traffic.**

---

# 41. Total Deadline

Imagine:

```text
API timeout = 2 seconds
```

You shouldn't do:

```text
retry 1 → wait 2 sec
retry 2 → wait 2 sec
retry 3 → wait 2 sec
```

because now the operation can take:

```text
6+ seconds
```

even though the original request's deadline was 2 seconds.

A better design considers the **total operation deadline**.

---

# 42. Retry With Idempotency

These two concepts often work together:

```text
retry
+
idempotency
```

For example:

```text
POST /payments
Idempotency-Key: abc123
```

If the network times out:

```text
retry
```

The payment service receives the same logical operation:

```text
abc123
```

and can safely return the original result rather than charging again.

---

# 43. Retry + Circuit Breaker

These also work together.

Imagine:

```text
Dependency failing
```

Retries alone:

```text
request
retry
retry
retry
```

can increase load.

Circuit breaker:

```text
failures increase
 ↓
circuit opens
 ↓
stop attempts
```

So:

```text
retry
+
backoff
+
jitter
+
circuit breaker
```

can provide much safer failure behavior.

---

# 44. Retry + Queue

For asynchronous work:

```text
Queue
 ↓
Worker
 ↓
temporary failure
```

the job can be retried later.

But again:

```text
maximum attempts
backoff
deduplication
dead-letter queue
```

should be considered.

---

# 45. Failure Recovery Hierarchy

Think of recovery like this:

```text
Temporary failure
       ↓
Retry
       ↓
Still failing?
       ↓
Backoff
       ↓
Still failing?
       ↓
Circuit breaker / stop calling
       ↓
Can operation be degraded?
       ↓
Graceful degradation
       ↓
Can it be retried later?
       ↓
Queue / background processing
       ↓
Still failing?
       ↓
Dead-letter / manual recovery
```

This is a very useful mental model.

---

# 46. Don't Retry Everything

Suppose:

```http
POST /users
```

returns:

```text
409 Conflict
```

because:

```text
email already exists
```

Retrying:

```text
POST
POST
POST
```

doesn't help.

Likewise:

```text
400 invalid input
```

should usually be fixed by the client.

Reliability means knowing **when not to retry**.

---

# 47. Error Classification Table

A simplified mental model:

|Failure|Usually retry?|Why|
|---|--:|---|
|Invalid input|❌|Request must change|
|Authentication failure|❌|Credentials/token issue|
|Authorization failure|❌|Permission issue|
|Duplicate/conflict|Usually ❌|State must change|
|Temporary network failure|✅|May recover|
|Timeout|Sometimes|Depends on operation|
|Rate limit|Sometimes|Respect retry guidance|
|Service unavailable|Sometimes|Temporary condition|
|Permanent business failure|❌|Retry won't change state|

The exact behavior depends on the API contract.

---

# 48. Reliability and HTTP Methods

HTTP semantics matter.

Generally:

```text
GET
PUT
DELETE
```

are intended to have idempotent semantics.

But:

```text
POST
```

is commonly non-idempotent.

However:

> HTTP method semantics alone do not automatically make your implementation safe under retries.

You still need to design the actual operation correctly.

---

# 49. A Common Interview Trap

Interviewer:

> "Is PUT idempotent?"

Don't simply answer:

> "Yes, always."

Better:

> **"PUT is defined with idempotent semantics when the same request is repeated, meaning the intended resource state should be the same. But the actual server implementation still needs to respect those semantics. HTTP method semantics don't automatically make arbitrary side effects idempotent."**

Much stronger.

---

# 50. API Reliability Contract

A mature API should define:

```text
What can be retried?
What cannot?
What does timeout mean?
What does 503 mean?
What does 429 mean?
Are requests idempotent?
How are duplicate requests handled?
```

These aren't just implementation details.

They're part of your API contract.

# 51. Example: Reliable Order API

Imagine:

```http

Idempotency-Key: order-abc
```

Flow:

```text

  ↓
API
  ↓
validate request
  ↓
check idempotency key
  ↓
create order
  ↓
publish/order workflow
  ↓
return result
```

If payment is external:

```text

  ↓
```

# 52. What If Payment Times Out?

Don't immediately do:

```text
payment = failed
```

Instead:

```text
payment = pending/unknown
```

Then:

```text
provider status check
       OR
webhook
       OR
reconciliation job
```

can eventually establish the final state.

This is much safer than guessing.

---

# 53. State Machines

For workflows like payments/orders, explicit state machines can help.

Example:

```text
ORDER_CREATED
      ↓
PAYMENT_PENDING
      ↓
PAYMENT_CONFIRMED
      ↓
FULFILLMENT_PENDING
      ↓
FULFILLED
```

Failure paths:

```text
PAYMENT_PENDING
      ↓
PAYMENT_FAILED
```

or:

```text
PAYMENT_PENDING
      ↓
PAYMENT_UNKNOWN
      ↓
RECONCILIATION
      ↓
PAYMENT_CONFIRMED
```

This makes complex workflows easier to reason about.

---

# 54. Don't Hide State Transitions

Bad:

```text
status = "something"
```

scattered throughout dozens of files.

Better:

```text
well-defined states
well-defined transitions
well-defined allowed actions
```

This becomes particularly important for:

```text
payments
orders
subscriptions
jobs
verification workflows
```

Test:

# 57. Chaos Engineering

At larger scale, teams may intentionally introduce failures.

For example:

```text
kill service
add latency
drop network traffic
restart instances
```

Then observe:

```text
Does the system recover?
```

This is broadly known as **chaos engineering**.

You don't need chaos engineering for a small MERN project, but understanding the philosophy is valuable.

---

# 58. Interview Scenario

### Interviewer:

> "Your payment API timed out. Would you retry?"

Weak answer:

> "Yes."

Strong answer:

> **"It depends on whether the operation is safely retryable. A timeout doesn't tell us whether the payment was processed. For a payment operation I'd use an idempotency key and a provider-supported status/reconciliation mechanism. If the provider documents the timeout as safely retryable, I'd retry with bounded exponential backoff and jitter. Otherwise I'd preserve an unknown/pending state rather than assuming failure."**

That is a **gold-level answer**.

---

# 59. Interview Scenario

### "What happens if your webhook is delivered twice?"

Answer:

> **"I assume duplicate delivery is possible. I'd identify the event using a stable event ID, store or atomically record processed events, and make the handler idempotent. The second delivery should produce no additional business side effect."**

---

# 60. Interview Scenario

### "Why not use a database transaction for everything?"

Answer:

> **"Transactions are excellent for maintaining atomicity within their supported transaction boundary, but they don't automatically make external service calls atomic. If a workflow spans multiple systems, I may need idempotency, an outbox, compensation/Saga-style workflows, and reconciliation."**

Excellent.

---

# 61. Interview Scenario

### "What happens if your server crashes after the database update but before publishing an event?"

Answer:

> **"That creates a dual-write problem. I'd consider a transactional outbox where the business update and the event record are committed in the same database transaction. A background publisher then publishes the outbox event, with idempotent processing on the consumer side."**

This is a very strong backend interview answer.

---

# 62. The Architecture

Put everything together:

```text
                         CLIENT
                            │
                            ▼
                       API REQUEST
                            │
                    ┌───────┴────────┐
                    │                │
              Validation        Idempotency
                    │                │
                    └───────┬────────┘
                            ▼
                         SERVICE
                            │
              ┌─────────────┼─────────────┐
              │             │             │
              ▼             ▼             ▼
           Database       Queue       External API
              │             │             │
              │             │        Timeout
              │             │        Retry
              │             │        Backoff
              │             │        Circuit Breaker
              │             │             │
              ▼             ▼             ▼
           Transaction    Worker      Provider
                            │
                         Retry
                            │
                         DLQ
```

And for database → event reliability:

```text
              DATABASE
                  │
          ┌───────┴────────┐
          │                │
     Business Data      Outbox Event
          │                │
          └───────┬────────┘
                  │
               COMMIT
                  │
                  ▼
             OUTBOX WORKER
                  │
                  ▼
             EVENT SYSTEM
                  │
                  ▼
            IDEMPOTENT CONSUMER
```

# 🧠 Gold-Level Revision Sheet

Remember these:

1. **Network failure does not necessarily mean business failure.**
    
2. Distributed systems can produce an **unknown outcome**.
    
3. Idempotency makes retries safer.
    
4. Idempotency keys identify a logical operation.
    
5. Idempotency state must be shared/durable in multi-instance systems.
    
6. Check-then-act can create race conditions.
    
7. Use atomic creation/unique constraints where appropriate.
    
8. Concurrent duplicate requests need an explicit policy.
    
9. Webhooks can be delivered more than once.
    
10. Webhook consumers should generally be idempotent.
    
11. Queue delivery can be at-least-once.
    
12. At-least-once delivery requires idempotent consumers or deduplication.
    
13. Exactly-once behavior across distributed systems is difficult.
    
14. Database transactions and idempotency solve different problems.
    
15. A Saga uses business-level compensating actions.
    
16. An Outbox Pattern helps solve the database + event dual-write problem.
    
17. Retries should be bounded.
    
18. Use exponential backoff.
    
19. Add jitter to avoid synchronized retry storms.
    
20. Respect total operation deadlines.
    
21. Circuit breakers prevent repeatedly hitting unhealthy dependencies.
    
22. Timeouts and circuit breakers are complementary.
    
23. Use queues for asynchronous, durable work.
    
24. Dead-letter queues handle repeatedly failing jobs.
    
25. Explicit workflow states make recovery easier.
    
26. Reconciliation helps resolve unknown/partial states.
    
27. **Design for at-least-once execution and make important side effects idempotent.**
