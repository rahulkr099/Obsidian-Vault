# Phase 16 — API Design & Response Architecture

## Lesson 16.4 — Error Responses

Your roadmap explicitly places **16.4 Error Responses** immediately after success responses.

This lesson is extremely important for interviews because a professional backend isn't judged only by how it handles successful requests. A large part of backend engineering is:

> **How predictably and safely does the system communicate failures?**

Your earlier architecture already established the foundation:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
      ↓
JSON response
```

That's the error flow your starter is designed around.

Now let's understand **why** it works.

---

# 1. What Is an Error Response?

Suppose React sends:

```http
GET /api/v1/todos/123
```

but Todo `123` doesn't exist.

Your backend shouldn't simply crash.

It should communicate:

```http
404 Not Found
```

with a predictable response:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

So:

```text
Error
  ↓
HTTP status
  +
JSON representation
  ↓
Error response
```

---

# 2. Why Error Responses Matter So Much

Imagine an API that returns random responses.

### Endpoint A

```json
{
  "error": "User not found"
}
```

### Endpoint B

```json
{
  "message": "Todo doesn't exist"
}
```

### Endpoint C

```json
{
  "success": false,
  "errorMessage": "Product missing"
}
```

### Endpoint D

```text
Internal Server Error
```

The frontend now has to understand four different formats.

That's bad API design.

Your goal is:

```text
Every error
    ↓
predictable structure
    ↓
frontend knows how to handle it
```

---

# 3. Error Response Is Part of the API Contract

Remember our central idea from 16.1:

> **An API is a contract.**

That contract includes failures.

For example:

```http
GET /api/v1/todos/123
```

might have this contract:

```text
200 → Todo returned
401 → Authentication required
403 → Not allowed
404 → Todo doesn't exist
500 → Unexpected server error
```

The frontend can build its behavior around this.

---

# 4. The Basic Error Envelope

For our starter architecture, a useful structure is:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

For validation errors, we may eventually expand it:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [...]
}
```

And later, with request tracing:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "req_123"
}
```

Notice the progression:

```text
Simple error
     ↓
Structured error
     ↓
Debuggable production error
```

We'll study validation errors and request IDs separately in **16.8** and **16.9**.

---

# 5. HTTP Status + Error Body

A professional error response usually has **two layers**.

### Protocol layer

```http
404 Not Found
```

### Application layer

```json
{
  "success": false,
  "message": "Todo not found"
}
```

Think:

```text
HTTP
 ↓
"What kind of failure is this?"

JSON
 ↓
"What specifically happened?"
```

# 6. Example: Resource Not Found

Request:

```http
GET /api/v1/todos/123
```

Suppose the repository can't find it.

Your service can throw:

```js
throw new AppError("Todo not found", 404);
```

Then:

```text
AppError
   ↓
error middleware
   ↓
404
```

Final response:

```http
404 Not Found
```

```json
{
  "success": false,
  "message": "Todo not found"
}
```

This is much better than allowing MongoDB or JavaScript errors to leak to the client.

---

# 7. What Is `AppError`?

Your starter architecture explicitly uses:

```text
utils/AppError.js
```

The purpose is to represent an **expected application error** in a controlled way.

Conceptually:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
    }
}
```

Then:

```js
throw new AppError(
    "Todo not found",
    404
);
```

The important idea isn't the exact class syntax.

It's this:

```text
Normal Error
    ↓
"What went wrong?"

AppError
    ↓
"What went wrong?"
+
"How should the API communicate it?"
```

---

# 8. Why Not Just Use `Error`?

You could do:

```js
throw new Error("Todo not found");
```

But then the error itself doesn't necessarily tell your API layer:

```text
HTTP status = 404
```

You'd have to infer it somewhere else.

With:

```js
new AppError("Todo not found", 404)
```

you explicitly carry application-level information.

Conceptually:

```text
AppError
├── message
├── statusCode
└── other metadata
```

That makes centralized error handling possible.

---

# 9. Expected Errors vs Unexpected Errors

This distinction is **very important for interviews**.

Consider:

### Case A

User requests a Todo that doesn't exist.

```text
Todo not found
```

This is an expected application condition.

```text
404
```

### Case B

Your code accidentally does:

```js
user.profile.name.toUpperCase()
```

when:

```js
user.profile === undefined
```

That's an unexpected programming error.

Usually:

```text
500
```

So:

```text
Expected application error
        ↓
controlled response

Unexpected programming error
        ↓
generic server response
        +
detailed server log
```

---

# 10. Never Expose Internal Errors in Production

Suppose this happens:

```js
const name = user.profile.name;
```

and `profile` is undefined.

Node might produce:

```text
TypeError:
Cannot read properties of undefined
(reading 'name')
```

Do **not** send that directly to the client.

Bad:

```json
{
  "success": false,
  "message": "Cannot read properties of undefined (reading 'name')"
}
```

Why?

Because internal errors can reveal:

```text
implementation details
database structure
libraries
file paths
stack traces
internal assumptions
```

Instead:

```http
500 Internal Server Error
```

```json
{
  "success": false,
  "message": "Internal server error"
}
```

And the actual error goes into your logs.

---

# 11. Client Response vs Server Log

This is one of the most important production concepts.

```text
                 ERROR
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
       CLIENT              SERVER
          │                 │
          ▼                 ▼
   Safe information     Detailed information
          │                 │
          ▼                 ▼
   "Internal error"     stack trace
                        error type
                        request ID
                        context
```

The user needs:

```text
Something went wrong.
```

The developer needs:

```text
TypeError
file
line
stack
requestId
user context
```

Those are **different audiences**.

---

# 12. Error Middleware Is the Central Router for Errors

Instead of doing this in every controller:

```js
try {
    ...
} catch (error) {
    res.status(...).json(...);
}
```

your architecture centralizes it.

Your starter's intended flow is:

```text
Controller
    ↓
throw
    ↓
asyncHandler
    ↓
next(error)
    ↓
error.middleware
    ↓
response
```

This is specifically the architecture described in your roadmap.

---

# 13. Why Centralized Error Handling Is Better

Imagine 30 controllers.

Without centralized handling:

```text
Controller 1 → try/catch
Controller 2 → try/catch
Controller 3 → try/catch
...
Controller 30 → try/catch
```

Problems:

- duplicated code
    
- inconsistent responses
    
- different status handling
    
- different logging
    
- easy to forget something
    

With centralized handling:

```text
Controller
   ↓
throw
   ↓
Global error middleware
   ↓
one response policy
```

Much easier to maintain.

---

# 14. `asyncHandler` Solves Another Problem

Remember your asynchronous controllers.

For example:

```js
export const getTodo = async (req, res) => {
    const todo = await todoService.getById(req.params.id);

    res.json({
        success: true,
        data: todo
    });
};
```

What if:

```js
todoService.getById()
```

rejects?

We need that error to reach Express's error middleware.

That's where your:

```text
utils/asyncHandler.js
```

comes in.

Conceptually:

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};
```

Now:

```text
Promise rejection
       ↓
.catch(next)
       ↓
Express error middleware
```

# 20. Don't Return Stack Traces

Never do this in production:

```js
res.status(500).json({
    success: false,
    error: error.stack
});
```

This can expose:

```text
/server/src/services/user.service.js
/server/node_modules/...
database details
implementation details
```

Instead:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

And log:

```text
ERROR
requestId=req_123
TypeError: ...
stack: ...
```

---

# 21. Don't Leak Database Errors

Imagine MongoDB produces some internal error.

Don't automatically do:

```js
res.status(500).json({
    error: error
});
```

Because the error may contain information that should never leave the server.

Instead:

```text
Database error
      ↓
log detailed error
      ↓
client receives safe message
```

This is especially important because your security roadmap includes **sensitive data exposure** and production hardening later.

---

# 22. Error Messages Should Be Useful

Bad:

```json
{
  "message": "Error"
}
```

Not useful.

Better:

```json
{
  "message": "Todo not found"
}
```

Better for validation:

```json
{
  "message": "Validation failed",
  "errors": [...]
}
```

Better for production server errors:

```json
{
  "message": "Internal server error",
  "requestId": "req_123"
}
```

The client gets enough information to respond appropriately without getting your internals.

---

# 23. Don't Put Sensitive Information in Error Messages

Avoid:

```json
{
  "message": "Password for user rahul@example.com is incorrect"
}
```

Depending on the authentication flow, overly specific errors can help attackers enumerate accounts.

Prefer carefully designed messages such as:

```json
{
  "message": "Invalid credentials"
}
```

This is an example of how:

```text
API design
+
security
```

work together.

# 24. Error Codes vs Error Messages

Here's an important improvement.

Suppose you return:

```json
{
  "message": "Email is already registered"
}
```

The message is for humans.

But a frontend may benefit from a stable machine-readable code:

```json
{
  "success": false,
  "code": "EMAIL_ALREADY_EXISTS",
  "message": "Email is already registered"
}
```

Now:

```text
code
 ↓
machine-readable

message
 ↓
human-readable
```

This is often better than making frontend logic depend on the exact wording.

We can introduce this carefully as your response architecture becomes more mature.

# 27. Error Categories

You should start thinking of errors by category.

```text
                 ERROR
                   │
       ┌───────────┼────────────┐
       │           │            │
       ▼           ▼            ▼
    Client       Auth        Server
       │           │            │
       ▼           ▼            ▼
    400/404     401/403       500/503
    409/422
    429
```

More specifically:

```text
400 → malformed/invalid request
401 → authentication problem
403 → authorization problem
404 → resource not found
409 → state conflict
422 → validation/content convention
429 → rate limit
500 → unexpected server error
503 → service unavailable
```

# 28. Error Handling Should Be Centralized, But Error Creation Isn't

This is subtle.

You **don't** want every controller constructing HTTP responses.

But different layers may discover different errors.

For example:

### Repository

```text
database problem
```

### Service

```text
email already exists
```

### Authentication middleware

```text
invalid token
```

### Authorization middleware

```text
insufficient permission
```

They can all create/throw appropriate application errors.

Then:

```text
one global error middleware
```

decides how to turn them into HTTP responses.

So:

```text
Error detection
     ↓
can happen at different layers

Error presentation
     ↓
centralized
```

That's a very strong architectural principle.

---

# 29. What Should the Controller Do?

A controller should generally not have this:

```js
try {
    ...
} catch (error) {

    if (error.code === "...") {
        ...
    }

    if (error.name === "...") {
        ...
    }

    ...
}
```

Instead:

```js
export const createTodo = asyncHandler(async (req, res) => {
    const todo = await todoService.create(
        req.user.id,
        req.body
    );

    return res.status(201).json({
        success: true,
        data: todo
    });
});
```

If service throws:

```text
AppError
```

the global error layer handles it.

That's a **thin controller**.

# 30. Error Middleware Concept

Express error middleware has this shape:

```js
const errorMiddleware = (
    err,
    req,
    res,
    next
) => {
    // central error handling
};
```

The four parameters matter:

```text
err
req
res
next
```

The presence of `err` as the first argument tells Express:

> This is an error-handling middleware.

Your Phase 8 roadmap already taught this concept because your starter depends on `error.middleware.js`.

---

# 31. A Basic Implementation

A simple version:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message:
            err.statusCode
                ? err.message
                : "Internal server error"
    });
};
```

Conceptually:

```text
Known AppError
    ↓
use its status/message

Unknown error
    ↓
500
+
safe generic message
```

This is the beginning.

Later we'll make it production-grade.

---

# 32. Why `err.statusCode || 500`?

Suppose:

```js
throw new AppError(
    "Todo not found",
    404
);
```

Then:

```js
err.statusCode
```

is:

```text
404
```

So the response becomes:

```text
404
```

But suppose some unexpected error occurs:

```js
throw new Error("Something weird happened");
```

There may be no:

```js
err.statusCode
```

Therefore:

```js
err.statusCode || 500
```

becomes:

```text
500
```

This gives you a safe default.

---

# 33. But Don't Trust Every Error's Message

This is where production security matters.

Imagine:

```js
throw new Error(
    "MongoDB connection string contains secret..."
);
```

If your middleware blindly does:

```js
message: err.message
```

you may expose internal information.

Instead, conceptually:

```text
Operational error?
    ↓
safe known message

Unknown programming error?
    ↓
generic client message
    ↓
detailed server log
```

This distinction is extremely important.

# 34. Production Error Flow

A mature system looks like:

```text
                  ERROR
                    │
                    ▼
            Is it expected?
              /          \
            YES           NO
             │             │
             ▼             ▼
```

This is the kind of architecture interviewers want you to understand.

# 35. Interview Question — What Is Global Error Handling?

### Weak answer:

> "It's middleware that handles errors."

### Strong answer:

> Global error handling centralizes the conversion of application and unexpected errors into consistent HTTP responses. Controllers and services can throw errors without duplicating response logic, while the global error middleware determines the status code, safe client-facing message, logging behavior, and eventually request-tracing information.

That's a much stronger answer.

---

# 36. Interview Question — Why Use `AppError`?

A good answer:

> `AppError` provides a controlled representation for expected application errors, such as resource-not-found or authorization failures. It can carry information such as an HTTP status code and safe message, allowing centralized error middleware to convert it into a predictable API response.

---

# 37. Interview Question — Operational vs Programming Errors

This one is worth knowing.

### Operational error

An expected condition that the application knows how to handle.

Examples:

```text
User not found
Invalid credentials
Insufficient permissions
Duplicate email
Validation failure
```

### Programming error

A bug or unexpected condition.

Examples:

```text
undefined property access
incorrect function assumption
unexpected null
logic bug
```

Conceptually:

```text
Operational
    ↓
handle gracefully

Programming
    ↓
log
    +
investigate/fix
```

This distinction is a classic backend interview topic.

---

# 38. Interview Question — Should Every Error Return `500`?

Absolutely not.

A strong answer:

> No. Expected client or application errors should use appropriate 4xx status codes, while 5xx responses represent server-side failures. Returning 500 for every error prevents clients from distinguishing invalid requests, authentication failures, missing resources, conflicts, and actual server failures.

---

# 39. Interview Question — Why Not Handle Errors in Every Controller?

Strong answer:

> Per-controller error handling creates duplication and makes response formats inconsistent. Centralized error middleware provides one place to define response formatting, status mapping, logging, security rules, and eventually request tracing.
