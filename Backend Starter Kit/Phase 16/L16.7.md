# Phase 16 — API Design & Response Architecture

## Lesson 16.7 — Pagination Responses

Your roadmap explicitly places **16.7 Pagination Responses** here, before validation errors and request IDs.

This lesson is especially important for interviews because pagination looks simple at first:

```text
?page=1&limit=20
```

but good pagination involves **API design, database performance, consistency, and scalability**.

Your roadmap later has a dedicated Phase 18 for deeper pagination/filtering/sorting, including page vs cursor pagination, `limit`, `skip`, metadata, indexes, and performance.

So in **16.7**, we'll learn how pagination should appear in an API response. We'll go deeper into database/query optimization in Phase 18.

---

# 1. The Problem

Imagine your application has:

```text
1,000,000 todos
```

A frontend requests:

```http
GET /api/v1/todos
```

If the backend returns all one million:

```json
{
  "success": true,
  "data": [
    "... 1,000,000 records ..."
  ]
}
```

That's terrible.

You have problems with:

```text
memory
network bandwidth
database load
response time
frontend performance
```

Instead, return a small portion:

```text
20 records
```

This is **pagination**.

---

# 2. What Is Pagination?

Pagination means:

> **Returning a large collection in smaller chunks.**

For example:

```text
100 todos
```

with:

```text
limit = 10
```

becomes:

```text
Page 1 → todos 1–10
Page 2 → todos 11–20
Page 3 → todos 21–30
...
Page 10 → todos 91–100
```

Conceptually:

```text
All records
──────────────────────────────────────────
│ 1 │ 2 │ 3 │ ... │ 100 │
──────────────────────────────────────────
        ↓
       page
        ↓
┌───────────┐
│ 1 ... 10  │
└───────────┘
```

---

# 3. The Basic API

A common API design is:

```http
GET /api/v1/todos?page=1&limit=20
```

Two query parameters:

```text
page
limit
```

### `page`

Which page do you want?

```text
page=1
page=2
page=3
```

### `limit`

How many records per page?

```text
limit=10
limit=20
limit=50
```

So:

```text
?page=2&limit=20
```

means:

> Give me the second page, with up to 20 records.

---

# 4. Why Pagination Belongs in the API Contract

The frontend needs more than just:

```json
{
  "data": [...]
}
```

Suppose it receives 20 records.

How does React know:

```text
Am I on page 1?
Is there another page?
How many records exist?
How many pages are there?
```

Therefore pagination metadata is useful.

A response can look like:

```json
{
  "success": true,
  "message": "Todos fetched successfully",
  "data": [
    {
      "id": "101",
      "title": "Learn Node.js"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 87,
    "totalPages": 5
  }
}
```

Now the frontend has everything it needs.

---

# 5. Understand `data` vs `pagination`

This separation is extremely important.

```json
{
  "data": [...],
  "pagination": {...}
}
```

### `data`

Contains:

> **The actual resources requested.**

### `pagination`

Contains:

> **Information about the collection/result set.**

Think:

```text
data
 ↓
"What did I receive?"

pagination
 ↓
"Where am I in the larger collection?"
```

---

# 6. Example

Suppose the database has:

```text
87 todos
```

Request:

```http
GET /api/v1/todos?page=2&limit=20
```

Then:

```text
page = 2
limit = 20
total = 87
```

The backend calculates:

```text
totalPages = ceil(87 / 20)
```

which gives:

```text
5
```

So:

```json
{
  "success": true,
  "message": "Todos fetched successfully",
  "data": [
    "... up to 20 todos ..."
  ],
  "pagination": {
    "page": 2,
    "limit": 20,
    "total": 87,
    "totalPages": 5
  }
}
```

---

# 7. Why `totalPages` Matters

Without:

```json
"totalPages": 5
```

the frontend may have to calculate:

```js
Math.ceil(total / limit)
```

It could do that.

But if your backend owns pagination semantics, providing the metadata makes the API easier to consume.

For example:

```js
const hasNextPage =
    pagination.page < pagination.totalPages;
```

Then:

```text
page 1 → has next
page 2 → has next
page 3 → has next
page 4 → has next
page 5 → no next
```

---

# 8. `hasNextPage` and `hasPreviousPage`

We can make the response even easier for clients:

```json
{
  "pagination": {
    "page": 3,
    "limit": 20,
    "total": 87,
    "totalPages": 5,
    "hasNextPage": true,
    "hasPreviousPage": true
  }
}
```

This is convenient.

But remember:

> Don't add metadata just because you can.

You should choose the contract that your clients actually need.

# 10. Last Page

Request:

```http
GET /todos?page=5&limit=20
```

Response:

```json
{
  "pagination": {
    "page": 5,
    "limit": 20,

    "hasNextPage": false,
```


```text

```

That's completely normal.

# 11. Empty Result

Suppose there are no todos.

Request:

```http
GET /todos?page=1&limit=20
```

Response:

```json
{
  "success": true,
  "message": "Todos fetched successfully",
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 0,
    "totalPages": 0
  }
}
```

This is still a successful request.

Remember from 16.5:

```text
successful collection
+
zero records
=
data: []
```

Not:

```text
404
```

# 12. What If Page Is Too Large?

Suppose:

```text
total = 87
```

and the client asks:

```http
GET /todos?page=100&limit=20
```

There are several valid API policies.

### Option A — Return empty data

```json
{
  "success": true,
  "data": [],
  "pagination": {
    "page": 100,
    "limit": 20,
    "total": 87,
    "totalPages": 5
  }
}
```

### Option B — Return a validation error

```http
400 Bad Request
```

with:

```json
{
  "success": false,
  "message": "Page exceeds available pages"
}
```

Neither is universally correct.

The important thing is to **choose a policy and keep it consistent**.

---

# 13. Never Trust `limit`

This is a security and performance issue.

A client could send:

```http
GET /todos?limit=1000000
```

If you blindly accept it:

```text
database
   ↓
1,000,000 records
   ↓
memory
   ↓
network
```

That's dangerous.

Instead, enforce a maximum:

```text
minimum = 1
maximum = 100
```

For example:

```text
limit=20  → valid
limit=100 → valid
limit=500 → reject or cap
```

The exact maximum depends on the application.

---

# 14. Validate Pagination Parameters

This connects directly to Phase 9's validation architecture.

Your query:

```http
GET /todos?page=abc&limit=hello
```

is invalid.

You should validate:

```text
page
limit
```

before passing them deeper into your application.

Flow:

```text
Request
   ↓
req.query
   ↓
Validation
   ↓
Clean pagination parameters
   ↓
Controller
   ↓
Service
   ↓
Repository
```

This is much safer than letting every layer interpret raw strings.

---

# 15. Remember: Query Parameters Are Strings

This is a subtle but important Node/Express point.

Request:

```http
GET /todos?page=2&limit=20
```

Express gives you values conceptually like:

```js
req.query.page
req.query.limit
```

which originate from the URL as strings.

So don't assume:

```js
req.query.page === 2
```

is automatically true.

Validation/normalization should turn them into the types your application expects.

Conceptually:

```text
"2"
 ↓
validate
 ↓
2
```

# 17. Where Should Pagination Logic Live?

This is an excellent architecture question.

Suppose the controller does:

```js
const page = Number(req.query.page);
const limit = Number(req.query.limit);
const skip = (page - 1) * limit;
```

Some simple query parsing is okay.

But don't let your controller become:

```text
parse pagination
calculate filters
build Mongo query
calculate sorting
execute query
calculate totals
format response
```

That's too much.

A better separation is:

```text
Controller
    ↓
receive validated pagination parameters

Service
    ↓
apply business rules

Repository
    ↓
execute database pagination
```

---

# 18. Page vs Skip

Offset/page pagination often translates to:

```text
skip = (page - 1) × limit
```

For:

```text
page = 1
limit = 20
```

we get:

```text
skip = (1 - 1) × 20
     = 0
```

Page 2:

```text
skip = (2 - 1) × 20
     = 20
```

Page 3:

```text
skip = (3 - 1) × 20
     = 40
```

So:

```text
page 1 → skip 0
page 2 → skip 20
page 3 → skip 40
page 4 → skip 60
```

This is the basic mathematics behind page-based pagination.

---

# 19. MongoDB Example

A repository might eventually do something conceptually like:

```js
Todo.find(filter)
    .sort({ createdAt: -1 })
    .skip(skip)
    .limit(limit);
```

Don't worry about building the complete repository implementation yet.

The important thing is understanding:

```text
filter
 ↓
sort
 ↓
skip
 ↓
limit
```

These become database concerns.

---

# 20. Why Sorting Matters With Pagination

This is extremely important.

Imagine your API returns:

```text
page 1
```

and then:

```text
page 2
```

What determines which records belong to each page?

You need a predictable ordering.

For example:

```text
createdAt DESC
```

means:

```text
newest → oldest
```

Without deterministic ordering, records can move between pages as the database returns results in different orders.

So good pagination usually goes with:

```text
pagination
+
stable sorting
```

Phase 18 will go deeper into this.

---

# 21. A Dangerous Example

Imagine:

```text
Page 1
──────────────
A
B
C
D
E
```

Then a new record is inserted:

```text
X
```

If you're sorting newest-first:

```text
X
A
B
C
D
E
```

Now page boundaries shift.

A client requesting page 2 may see records that were previously on page 1.

This is one reason traditional page/offset pagination can become tricky for rapidly changing datasets.

---

# 22. Offset Pagination

What we've discussed so far is generally called:

> **Offset-based pagination**

Conceptually:

```text
page
limit
skip
```

Example:

```http
GET /todos?page=10&limit=20
```

becomes approximately:

```text
skip = 180
limit = 20
```

It's easy to understand and works very well for many applications.

---

# 23. Advantages of Offset Pagination

It's popular because it's simple.

```text
?page=1&limit=20
```

is easy for:

```text
frontend
backend
SQL
MongoDB
admin dashboards
tables
```

It also makes it easy to jump directly:

```text
page 1
page 10
page 100
```

That's useful for traditional UIs.

---

# 24. Problems With Offset Pagination

At very large offsets, databases may have to do more work to reach the desired position.

For example:

```text
skip = 1,000,000
```

can become expensive depending on the database/query/index design.

There is also the changing-data problem we just discussed.

This is why large-scale systems sometimes use:

> **Cursor-based pagination**

We'll study this more deeply in Phase 18.

---

# 25. Cursor Pagination

Instead of:

```http
GET /todos?page=2&limit=20
```

you might have:

```http
GET /todos?limit=20&cursor=abc123
```

The cursor represents a position in the result set.

Conceptually:

```text
First request
     ↓
20 records
     ↓
nextCursor
     ↓
client requests next page
```

Response:

```json
{
  "success": true,
  "data": [
    "... 20 records ..."
  ],
  "pagination": {
    "nextCursor": "abc123",
    "hasNextPage": true
  }
}
```

Then:

```http
GET /todos?limit=20&cursor=abc123
```

---

# 26. Offset vs Cursor

Think about the difference.

### Offset

```text
"Give me records 41–60."
```

### Cursor

```text
"Give me the next 20 records after this position."
```

Diagram:

```text
OFFSET

1  2  3  ... 40 | 41 42 ... 60
                  ↑
                skip


CURSOR

A B C D E F G H I J
          ↑
        cursor
          │
          ▼
        next 20
```

---

# 27. When Offset Pagination Is Good

Use page/offset pagination when:

```text
dataset isn't enormous
users need page numbers
users jump between pages
admin dashboards
data changes slowly
```

For your Todo application:

```text
?page=1&limit=20
```

is completely reasonable.

Don't over-engineer it.

---

# 28. When Cursor Pagination Is Better

Cursor pagination becomes attractive when:

```text
very large datasets
infinite scrolling
social feeds
highly changing data
activity streams
real-time-ish feeds
```

For example:

```text
Twitter/X-style feed
Instagram-style feed
notifications
messages
event streams
```

The client often wants:

> "Give me the next batch."

rather than:

> "Give me page 437."


# 31. Don't Mix Pagination Strategies Accidentally

Avoid an API that sometimes expects:

```text
page
```

and sometimes:

```text
cursor
```

without a clear contract.

For a given endpoint, define the strategy.

For example:

```text
/admin/users
    ↓
offset pagination

/feed
    ↓
cursor pagination
```

That's perfectly reasonable.

# 35. Common Pagination Mistakes

### ❌ No limit

```http
GET /todos
```

returns everything.

---

### ❌ Unlimited `limit`

```http
GET /todos?limit=999999999
```

Potential performance problem.

---

### ❌ No validation

```http
?page=-100&limit=abc
```

---

### ❌ Unstable ordering

```text
page 1
page 2
```

without deterministic sorting.

---

### ❌ Exposing database details

```json
{
  "skip": 4000,
  "mongoQuery": "..."
}
```

Don't.

---

### ❌ Counting everything unnecessarily

Depending on the use case, exact:

```text
total
```

may be expensive.

Cursor APIs often avoid requiring it.

---

### ❌ Assuming offset is always bad

It isn't.

For many applications:

```text
page + limit
```

is perfectly good.

Use the simplest strategy that satisfies the requirements.

# 36. Interview Question — What Is Pagination?

A strong answer:

> Pagination is a technique for returning a large collection in smaller result sets rather than sending every record at once. Common approaches include offset/page-based pagination and cursor-based pagination.

---

# 37. Interview Question — Offset vs Cursor?

Strong answer:

> Offset pagination uses values such as page, limit, and skip to identify a result range. It's simple and supports jumping to arbitrary pages, but large offsets can become inefficient and changing datasets can cause inconsistent page boundaries. Cursor pagination instead uses a position or cursor from the previous result set and is often better for large, frequently changing datasets or infinite-scroll interfaces.

That's an excellent interview answer.

---

# 38. Interview Question — Why Is Sorting Important?

Strong answer:

> Pagination depends on a predictable ordering of records. Without deterministic sorting, records can move between pages or appear inconsistently, especially when data changes between requests. Therefore pagination should generally use an appropriate stable sort, often supported by an index.

That final phrase is particularly good for a backend interview.

---

# 39. Interview Question — Should the Backend Return `total`?

A mature answer:

> It depends on the API's requirements. `total` and `totalPages` are useful for page-based UIs, but calculating exact totals can add database work. Cursor-based APIs often don't need exact totals and can instead return information such as `nextCursor` and `hasNextPage`.

Excellent.

---

# 40. Interview Question — Where Does Pagination Logic Belong?

Strong answer:

> Query parameters should be validated at the input boundary. The controller should orchestrate the request, the service can apply business-level rules, and the repository should handle database-specific pagination such as skip, limit, cursor conditions, and indexes.

This connects your:

```text
Validation
Controller
Service
Repository
```

architecture together.

# 🧠 One Very Important Interview Insight

If an interviewer asks:

> **"How would you implement pagination?"**

Don't immediately say:

```js
.skip((page - 1) * limit)
.limit(limit)
```

That's only the implementation detail.

Start with:

> "It depends on the use case. For a normal administrative or CRUD listing, I'd probably use validated page/limit pagination with a deterministic sort and a maximum page size. For a very large or frequently changing feed, I'd consider cursor pagination. I'd also make sure the relevant sort/filter fields are indexed."

That answer demonstrates **design judgment**.

Then, if they ask for implementation, show:

```js
const skip = (page - 1) * limit;
```

Now you're answering at both the architectural and coding levels.

## ⭐ Gold Interview Challenge

Imagine the interviewer says:

> **"You have 50 million records in MongoDB. The frontend needs infinite scrolling. Would you use `page` and `skip`?"**

Don't automatically say yes.

A strong answer would begin:

> "I'd probably consider cursor-based pagination rather than large offset pagination. For infinite scrolling over a very large and frequently changing dataset, a cursor based on a stable indexed sort key can avoid large offsets and provide more consistent continuation between requests. I'd return the records plus a next cursor and whether another page exists."

Then the interviewer may ask:

> **"What would your cursor be based on?"**

That's where we'll eventually discuss:

and why **cursor design and indexes must be considered together**.
