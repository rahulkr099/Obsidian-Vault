# Lesson 17.1 — What Is CRUD Architecture?

Welcome back, Rahul. 🚀

In Phase 16, we focused on **API design** — how an API should look from the outside.

Now in Phase 17, we're going one level deeper:

> **How do we internally build a CRUD feature so that it remains clean, secure, testable, and easy to extend?**

Your starter architecture is built around this separation of responsibilities.

---

# 1. First: What is CRUD?

CRUD stands for:

```text
C → Create
R → Read
U → Update
D → Delete
```

Almost every backend application has resources that need these operations.

For example, imagine a Notes application.

A user might want to:

```text
Create a note
Read a note
Update a note
Delete a note
```

That gives us:

```text
CREATE
POST /api/v1/notes

READ
GET /api/v1/notes
GET /api/v1/notes/:noteId

UPDATE
PATCH /api/v1/notes/:noteId

DELETE
DELETE /api/v1/notes/:noteId
```

That's CRUD.

But **CRUD itself is not architecture**.

---

# 2. CRUD Operation vs CRUD Architecture

This distinction is extremely important.

Suppose we write:

```js
app.post("/notes", async (req, res) => {
    const note = await Note.create(req.body);

    res.json(note);
});
```

This technically performs a CRUD operation.

But we have a problem.

The route is now doing:

```text
Routing
+
Database access
+
Business logic
+
HTTP response
```

Everything is mixed together.

As the application grows, this becomes difficult to maintain.

---

# 3. The Problem With "Everything in One Place"

Imagine this:

```js
app.post("/notes", async (req, res) => {
    // validate data

    // check authentication

    // check ownership

    // check duplicate note

    // apply business rules

    // save to MongoDB

    // send email

    // create audit log

    // return response
});
```

At first:

```text
20 lines
```

Maybe that's manageable.

But eventually:

```text
100 lines
200 lines
500 lines
```

Now one endpoint is responsible for almost everything.

This is commonly called a **fat route/controller** problem.

---

# 4. So What Is CRUD Architecture?

CRUD architecture means:

> **Separating the different responsibilities involved in performing a CRUD operation.**

Instead of:

```text
Request
   ↓
Everything
   ↓
Database
```

we create layers:

```text
Request
   ↓
Route
   ↓
Middleware
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Model
   ↓
Database
```

Each layer has a specific responsibility.

---

# 5. Let's Take "Create Note"

Suppose the frontend sends:

```http
POST /api/v1/notes
```

with:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today"
}
```

The request should travel through our architecture.

```text
Frontend
   │
   ▼
POST /api/v1/notes
   │
   ▼
Route
   │
   ▼
Middleware
   │
   ▼
Validation
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Model
   │
   ▼
MongoDB
```

This is **CRUD architecture**.

---

# 6. What Does Each Layer Do?

Let's understand the responsibility of each layer.

## Route

The route answers:

> **Where should this request go?**

Example:

```js
router.post(
    "/",
    authMiddleware,
    validate(createNoteSchema),
    noteController.createNote
);
```

The route is basically wiring.

It connects:

```text
URL
 ↓
Middleware
 ↓
Controller
```

It shouldn't contain your business logic.

---

# 7. Middleware

Middleware answers:

> **Can this request continue?**

For example:

```text
Authentication
Validation
Rate limiting
Request ID
Logging
```

For our note:

```text
POST /notes
      ↓
Is user authenticated?
      ↓
Is request valid?
      ↓
Continue
```

If something fails:

```text
Request
   ↓
Middleware
   ↓
❌ Error
```

The request never reaches the controller.

---

# 8. Controller

The controller answers:

> **What HTTP operation is being performed?**

For example:

```js
const createNote = asyncHandler(async (req, res) => {
    const note = await noteService.createNote({
        userId: req.user.id,
        title: req.body.title,
        content: req.body.content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

Notice something important.

The controller doesn't know **how MongoDB works**.

It simply says:

```text
"I received an HTTP request.
I need a note created.
I'll ask the service."
```

---

# 9. Service

The service answers:

> **What should the application actually do?**

For example:

```js
const createNote = async ({ userId, title, content }) => {
    // business rules

    // maybe check something

    // then create the note
};
```

Imagine your application has this rule:

> A user cannot create more than 100 active notes.

That's a **business rule**.

It belongs in the service layer.

Conceptually:

```text
Controller
     ↓
Service
     ↓
"Does this user have permission?"
     ↓
"Has the user reached the limit?"
     ↓
"Okay, create the note."
```

---

# 10. Repository

The repository answers:

> **How do we access the database?**

For example:

```js
const create = async (data) => {
    return Note.create(data);
};
```

The service doesn't need to know:

```text
Mongoose
MongoDB
findOne()
create()
findById()
```

It simply asks:

```text
noteRepository.create(...)
```

The repository handles the database interaction.

---

# 11. Model

The model answers:

> **What does a Note look like in the database?**

For example:

```js
const noteSchema = new mongoose.Schema({
    userId: {
        type: mongoose.Schema.Types.ObjectId,
        required: true
    },

    title: {
        type: String,
        required: true
    },

    content: {
        type: String,
        required: true
    }
});
```

The model describes the data structure and database-level behavior.

---

# 12. MongoDB

Finally:

```text
Repository
     ↓
Model
     ↓
MongoDB
```

MongoDB stores:

```json
{
  "_id": "...",
  "userId": "...",
  "title": "Learn MongoDB",
  "content": "Study indexes today"
}
```

---

# 13. Put Everything Together

Now look at the entire process:

```text
                POST /api/v1/notes
                         │
                         ▼
                       ROUTE
                         │
                         ▼
                    MIDDLEWARE
                    /          \
              Authentication   Validation
                    \          /
                         │
                         ▼
                    CONTROLLER
                         │
                         ▼
                      SERVICE
                         │
                   Business Rules
                         │
                         ▼
                    REPOSITORY
                         │
                  Database Access
                         │
                         ▼
                       MODEL
                         │
                         ▼
                      MongoDB
```

And the result comes back:

```text
MongoDB
   ↓
Model
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
HTTP Response
   ↓
Frontend
```

---

# 14. Why Do We Need So Many Layers?

You might be thinking:

> "Rahul, this seems like a lot of files for simply creating a note."

That's a very good question.

For a tiny application, this can absolutely feel like overengineering.

But consider a real application.

You may eventually have:

```text
Users
Notes
Comments
Posts
Products
Orders
Payments
Notifications
Subscriptions
```

And each resource might have:

```text
Create
Read
Update
Delete
Search
Filtering
Authorization
Validation
Auditing
Notifications
```

Without separation, your code becomes difficult to manage.

With separation:

```text
notes/
users/
orders/
products/
```

can each follow the same architecture.

---

# 15. Reusability

Suppose you understand:

```text
Note
 ↓
Controller
 ↓
Service
 ↓
Repository
```

Now you need to build:

```text
Product
```

The architecture is almost identical:

```text
Product Route
      ↓
Product Controller
      ↓
Product Service
      ↓
Product Repository
      ↓
Product Model
      ↓
MongoDB
```

Then:

```text
Order
```

becomes:

```text
Order Route
      ↓
Order Controller
      ↓
Order Service
      ↓
Order Repository
      ↓
Order Model
      ↓
MongoDB
```

You're learning a **repeatable engineering pattern**, not a one-time implementation.

---

# 16. Separation of Responsibilities

This is the heart of the lesson.

Remember this:

```text
Route
→ Where?

Middleware
→ Can it continue?

Validation
→ Is the input acceptable?

Controller
→ What HTTP operation?

Service
→ What should the application do?

Repository
→ How do I access data?

Model
→ What does the data look like?

Database
→ Where is the data stored?
```

If you ever become confused about where code belongs, ask:

> **"Which question is this code answering?"**

That usually tells you the correct layer.

---

# 17. A Very Important Example

Suppose you have:

```js
if (user.role !== "admin") {
    throw new AppError("Admin only", 403);
}
```

Where does this belong?

Potentially:

```text
Authorization middleware
```

because it's checking whether the request can continue.

Now imagine:

```js
if (user.activeNotes >= 100) {
    throw new AppError(
        "Maximum number of notes reached",
        400
    );
}
```

That's a **business rule**.

So it belongs in:

```text
Service
```

Now:

```js
Note.findOne({
    _id: noteId,
    userId
});
```

That's a database query.

So it belongs in:

```text
Repository
```

This ability to **place logic in the correct layer** is one of the main skills we're developing in Phase 17.

---

# 18. CRUD Architecture Is Not About More Files

This is another important point.

Don't think:

> "Professional backend = many folders."

Wrong.

The real goal is:

> **Professional backend = clear responsibilities.**

You could technically put everything in one file and create a working API.

But maintaining it becomes difficult.

The architecture exists to reduce **coupling**.

---

# 19. What Is Coupling?

Imagine:

```text
Controller
   ↓
Direct MongoDB query
   ↓
Business rule
   ↓
Email
   ↓
Authentication
```

Everything depends on everything else.

That's high coupling.

Instead:

```text
Controller
   ↓
Service
   ↓
Repository
```

creates clearer boundaries.

For example:

```text
Controller doesn't need to know MongoDB details.
```

And:

```text
Repository doesn't need to know HTTP details.
```

That's the idea.

---

# 20. CRUD Architecture and Testing

This separation also makes testing easier.

Imagine you want to test:

```text
"Can a user create a note?"
```

You can test the service separately.

You don't necessarily need:

```text
Browser
 ↓
HTTP
 ↓
Express
 ↓
MongoDB
```

for every test.

You can test:

```text
Service
 ↓
Mock repository
```

Similarly, repository tests can focus on:

```text
Repository
 ↓
Database
```

This gives you smaller, more focused tests.

We'll study this deeply later in the testing phase.

---

# 21. CRUD Architecture and Security

Architecture also helps security.

Consider:

```text
PATCH /notes/:noteId
```

We don't want:

```text
User A
   ↓
PATCH
   ↓
User B's note
   ↓
❌ SUCCESS
```

Instead:

```text
Request
   ↓
Authentication
   ↓
User identity
   ↓
Service
   ↓
Repository
   ↓
Find note WHERE:
    noteId = requested ID
    AND userId = authenticated user
```

We'll study this properly in **17.15 — Resource Ownership** and **17.16 — Preventing IDOR**.

Imagine this request:

Body:

```json

  "title": "Updated title"

```

Don't write code yet.

Instead, mentally trace it:

```text
PATCH /notes/123
       ↓
Route
       ↓
Authentication
       ↓
Validation
       ↓
Controller
       ↓
Service
       ↓
Repository
       ↓
MongoDB
```

Now ask yourself:

### Route

Where does this request go?

### Middleware

Who is making the request?

### Validation

Is `"title"` valid?

### Controller

What HTTP operation is being requested?

### Service

Is this user allowed to update this note?

### Repository

How do we find and update the note?

### Model

What fields does a Note contain?

That's CRUD architecture.

# 24. The Golden Rule

Keep this rule with you throughout Phase 17:

> **Don't put code where it is convenient. Put code where its responsibility belongs.**

For example:

```text
❌ Database query inside controller

❌ Business rules inside route

❌ HTTP response inside repository

❌ JWT verification inside repository

❌ MongoDB logic inside service
```

Instead:

```text
Route
   → routing

Middleware
   → request checks

Controller
   → HTTP

Service
   → business logic

Repository
   → database access

Model
   → data structure
```
