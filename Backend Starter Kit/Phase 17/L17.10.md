# Lesson 17.10 — Validation

In the Phase 17 roadmap, **17.10 is Validation**. The goal is to make sure the CRUD resource receives valid input before that input reaches our application logic and database.

We've already built the important security idea in **17.9 — Ownership**:

```text
authenticated user
        ↓
ownership
        ↓
correct resource
```

Now we add another boundary:

```text
Client
  ↓
Validation
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

The core idea is:

> **Never trust data just because it came from your frontend.**

---

# 1. Why Do We Need Validation?

Imagine our API:

```http
POST /api/v1/notes
```

expects:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes."
}
```

But the client sends:

```json
{
  "title": 123,
  "content": true
}
```

Or:

```json
{
  "title": ""
}
```

Or:

```json
{
  "randomField": "something"
}
```

Or:

```json
{
  "title": "<something unexpected>"
}
```

Our backend must decide:

```text
Is this input acceptable?
```

That's validation.

---

# 2. Client Validation Is Not Enough

Your React frontend might have:

```js
if (!title) {
    showError("Title required");
}
```

That's useful for the user experience.

But it is **not security**.

A malicious user doesn't need to use your React application.

They can directly send:

```bash
curl ...
```

or use:

```text
Postman
Insomnia
browser DevTools
custom script
```

So:

```text
Frontend validation
        ↓
Good UX

Backend validation
        ↓
Security + correctness
```

Your starter roadmap describes validation as an **input boundary**: request data should be validated and cleaned before reaching the controller.

---

# 3. The Trust Boundary

Think of the internet as untrusted.

```text
                UNTRUSTED
                   │
                   ▼
              HTTP Request
                   │
                   ▼
              VALIDATION
                   │
                   ▼
                TRUSTED
                   │
                   ▼
              Application
```

The validation layer is one of the boundaries between:

```text
external input
```

and:

```text
internal application logic
```

This is why validation belongs early in the request pipeline.

---

# 4. What Should We Validate?

For our Note resource:

```text
title
content
```

We might define:

```text
title:
  required
  string
  minimum length
  maximum length

content:
  required
  string
  maximum length
```

For example:

```text
title: 1–100 characters
content: 1–10,000 characters
```

These are examples; your actual application requirements may differ.

---

# 5. Validation vs Sanitization

These are related but different.

### Validation

Asks:

> **Is this value acceptable?**

Example:

```text
title = ""
```

Result:

```text
❌ invalid
```

### Sanitization / normalization

Asks:

> **Can we safely clean or normalize this value?**

Example:

```text
"   Learn MongoDB   "
```

might become:

```text
"Learn MongoDB"
```

So:

```text
Validation
   ↓
Is it valid?

Normalization
   ↓
Can we put it into a consistent form?
```

Your earlier Phase 9 roadmap explicitly separates validation from sanitization and normalization.

---

# 6. Validation Should Happen Before the Controller

Our request flow should look like:

```text
POST /notes
      ↓
Route
      ↓
Authentication
      ↓
Validation
      ↓
Controller
      ↓
Service
      ↓
Repository
      ↓
MongoDB
```

Why before the controller?

Because the controller shouldn't have to repeatedly check:

```js
if (!title) ...
if (typeof title !== "string") ...
if (title.length > 100) ...
```

Instead:

```text
Validation middleware
       ↓
clean, validated input
       ↓
Controller
```

---

# 7. Our Note Validation Schema

Suppose we use Joi, which is part of the architecture described in the starter roadmap.

Conceptually:

```js
const createNoteSchema = Joi.object({
    title: Joi.string()
        .trim()
        .min(1)
        .max(100)
        .required(),

    content: Joi.string()
        .trim()
        .min(1)
        .max(10000)
        .required()
});
```

This describes our input contract.

---

# 8. What Does This Schema Say?

Let's break it down.

```js
Joi.string()
```

means:

> This value must be a string.

Then:

```js
.min(1)
```

means:

> At least one character.

Then:

```js
.max(100)
```

means:

> Maximum 100 characters.

Then:

```js
.required()
```

means:

> The field must exist.

And:

```js
.trim()
```

means:

> Remove surrounding whitespace during validation/normalization.

---

# 9. Valid Request

This passes:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes."
}
```

Because:

```text
title
 ├── exists        ✅
 ├── string        ✅
 ├── non-empty     ✅
 └── <= 100 chars  ✅

content
 ├── exists        ✅
 ├── string        ✅
 ├── non-empty     ✅
 └── <= 10000      ✅
```

---

# 10. Invalid Request

This:

```json
{
  "title": 123,
  "content": "Study MongoDB"
}
```

fails:

```text
title
 ↓
number
 ↓
expected string
 ↓
400 Bad Request
```

The request shouldn't reach:

```text
Service
Repository
MongoDB
```

---

# 11. Another Invalid Request

```json
{
  "title": "",
  "content": "Study MongoDB"
}
```

fails:

```text
title
 ↓
minimum 1 character
 ↓
invalid
```

Again:

```text
Validation
   ↓
❌
```

The controller doesn't run.

---

# 12. Another Invalid Request

```json
{
  "content": "Study MongoDB"
}
```

fails because:

```text
title
 ↓
required
 ↓
missing
```

So:

```text
400 Bad Request
```

---

# 13. What About Extra Fields?

Suppose the client sends:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes.",
  "role": "admin"
}
```

That's suspicious.

Why is the client trying to send:

```text
role
```

to a Note endpoint?

This is where **allow-listing fields** becomes important.

The server should explicitly define what fields are accepted.

For our Note creation:

```text
Allowed:
title
content
```

Not:

```text
userId
role
isAdmin
createdAt
updatedAt
```

---

# 14. Never Let the Client Choose Ownership

This connects directly to 17.9.

Bad:

```json
{
  "title": "My Note",
  "content": "Hello",
  "userId": "another-user"
}
```

Don't trust:

```js
req.body.userId
```

Instead:

```js
const userId = req.user.id;
```

The server assigns ownership.

So validation should **not** turn this into a valid request merely because `userId` has the correct format.

Ownership is controlled by the authenticated identity.

---

# 15. Mass Assignment Problem

Imagine your model has:

```text
userId
role
isAdmin
isDeleted
```

and you do:

```js
Note.create(req.body);
```

The client might send:

```json
{
  "title": "Hack",
  "content": "Something",
  "isDeleted": false
}
```

or potentially other fields your application never intended the client to control.

This is why we use explicit input schemas and construct application data intentionally.

Prefer:

```js
const data = {
    userId: req.user.id,
    title: validatedData.title,
    content: validatedData.content
};
```

This is much safer.

---

# 16. Validation Does Not Replace Authorization

This is extremely important.

Suppose:

```json
{
  "title": "Hello",
  "content": "World"
}
```

is perfectly valid.

That doesn't mean the user is authorized to perform the operation.

So:

```text
Validation
    ↓
"Is the input valid?"

Authorization
    ↓
"Is this user allowed to do this?"
```

They solve different problems.

---

# 17. Validation Does Not Replace Database Constraints

Similarly, validation doesn't replace database-level guarantees.

Suppose you validate:

```text
email must be unique
```

Two requests could still arrive simultaneously:

```text
Request A ─┐
           ├── both check "email available"
Request B ─┘
```

Both may pass the application-level check.

A database unique index provides a stronger integrity guarantee.

So:

```text
Validation
+
Business rules
+
Database constraints
```

work together.

---

# 18. Validation Error

Suppose the client sends:

```json
{
  "title": 123
}
```

We shouldn't return:

```json
{
  "error": "Something went wrong"
}
```

That's not useful.

Instead, a consistent API can return something like:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    {
      "field": "title",
      "message": "Title must be a string"
    }
  ]
}
```

The exact response format should follow the API response architecture you established in Phase 16.

---

# 19. Why Consistent Validation Errors Matter

Your React frontend can then easily do:

```text
errors.title
errors.content
```

and show messages next to the correct fields.

Without consistency, every endpoint might return:

```text
"Invalid input"
```

in a different format.

That creates unnecessary frontend complexity.

---

# 20. Validation Middleware

We can create reusable middleware conceptually like:

```js
const validate = (schema) => {
    return (req, res, next) => {
        // validate request data
        // reject invalid data
        // attach validated data
        // next()
    };
};
```

Then a route can say:

```js
router.post(
    "/notes",
    authMiddleware,
    validate(createNoteSchema),
    noteController.create
);
```

Now validation becomes reusable.

---

# 21. Middleware Factory

Notice:

```js
validate(createNoteSchema)
```

isn't middleware itself yet.

It's a function that **creates middleware**.

Conceptually:

```text
validate(schema)
      ↓
returns middleware
      ↓
Express executes middleware
```

This is called a **middleware factory**.

You already studied middleware factories earlier in the roadmap.

# 23. Parameter Validation

Now consider:

```http
GET /notes/abc123
```

We have:

```text
req.params.id
```

That can also require validation.

For example, if you're using MongoDB ObjectIds, you might validate that:

```text
id
 ↓
valid ObjectId format
```

before the repository queries MongoDB.

This prevents malformed IDs from reaching the database layer.

For:

```http
GET /notes?page=1&limit=20
```

we can validate:

```text

```

For example:

```text
page → positive integer

```

# 25. Three Different Input Locations

Remember:

```text
req.body
req.params
req.query
```

They can all require validation.

### Body

```http
POST /notes
```

```json
{
  "title": "...",
  "content": "..."
}
```

### Params

```http
GET /notes/:id
```

```text
req.params.id
```

### Query

```http
GET /notes?page=1&limit=20
```

```text
req.query.page
req.query.limit
```

```text
 Authentication
```

---

# 27. Validated Data vs Raw Data

This is an important design idea.

Raw:

```js
req.body
```

should be treated as:

```text
UNTRUSTED
```

After validation:

```js
validatedData
```

can be treated as:

```text
VALIDATED INPUT
```

So conceptually:

```text
req.body
   ↓
validate
   ↓
validatedData
   ↓
controller
```

Don't keep using raw `req.body` after validation if the validation library has already produced a cleaned/validated result.

---

# 28. Don't Duplicate Validation Everywhere

Bad:

```js
// middleware
if (!title) ...

// controller
if (!title) ...

// service
if (!title) ...

// repository
if (!title) ...
```

Now the same rule exists four times.

Instead:

```text
Validation middleware
        ↓
one clear input contract
        ↓
Service
        ↓
business rules
```

Keep responsibilities separate.

---

# 29. Validation vs Business Rules

This distinction is critical.

### Validation

```text
title must be a string
title <= 100 characters
content is required
```

### Business rule

```text
User cannot have more than 100 active Notes.
```

The first asks:

> Is the input structurally acceptable?

The second asks:

> Is the requested operation allowed under application rules?

Therefore:

```text
Validation → Validation layer
Business rules → Service layer
```

---

# 30. Example: Note Limit

Suppose the user sends:

```json
{
  "title": "Note",
  "content": "Hello"
}
```

Validation says:

```text
Valid input
```

Then the Service says:

```text
User already has 100 active Notes
        ↓
Business rule violated
        ↓
Reject
```

So:

```text
Validation
    ↓
PASS
    ↓
Service
    ↓
FAIL
```

This is perfectly normal.

---

# 31. Validation + Ownership

Another useful example:

```json
{
  "title": "My Note",
  "content": "Hello",
  "userId": "userB"
}
```

Validation might say:

```text
userId is a string
```

But we should **not accept that field as ownership**.

Instead:

```text
Authenticated user
       ↓
req.user.id = userA

Create:
userId = userA
```

So validation and ownership work together but solve different problems.

---

# 32. Validation + Soft Delete

Suppose:

```http
PATCH /notes/:id/restore
```

There may not even be a request body.

We still validate:

```text
req.params.id
```

Then:

```text
Service
   ↓
Can this Note be restored?
```

Repository:

```text
_id = noteId
userId = authenticated user
isDeleted = true
```

Again, different layers solve different problems.

---

# 33. What Should Validation Middleware Return?

A good validation middleware can put the validated data somewhere predictable.

For example:

```js
req.validated = result.value;
```

Then:

```js
const { title, content } = req.validated;
```

This has an advantage:

```text
req.body
   ↓
raw input

req.validated
   ↓
validated/normalized input
```

The exact property name is an architectural choice; the important thing is to establish one consistent convention.

# 35. Validation Error vs Authentication Error

Don't mix them.

### No/invalid authentication

```text
401 Unauthorized
```

### Authenticated but not allowed

```text
403 Forbidden
```

### Invalid input

```text
400 Bad Request
```

These are different failure categories.

Your Phase 16 response architecture is where the API contract for these errors is standardized.

---

# 36. Validation and Database Errors

Suppose validation passes:

```text
title valid
content valid
```

but MongoDB rejects the operation because of a database constraint.

That's not a validation error anymore.

The flow might be:

```text
Validation
   ↓
PASS
   ↓
Service
   ↓
Repository
   ↓
Database constraint fails
```

The error handling layer should translate the database failure appropriately.

Don't incorrectly call every database failure a "validation error."

---

# 37. Don't Validate Only in Mongoose

Mongoose schemas provide some validation.

For example:

```js
title: {
    type: String,
    required: true
}
```

That's useful.

But application-level request validation still matters.

Why?

Because you want to reject bad requests **before they reach the database**.

So:

```text
HTTP validation
       ↓
Application validation
       ↓
Mongoose validation
       ↓
Database constraints
```

These layers can complement each other.

---

# 38. Defense in Depth

A production backend often uses multiple layers of protection:

```text
Client validation
       ↓
Server request validation
       ↓
Business rules
       ↓
Database schema validation
       ↓
Database constraints
```

Don't think:

> "I already validated it once, so nothing else matters."

Each layer protects against different failures.

Our Note API now looks like:

```text
                  REQUEST
                     │
                     ▼
                   ROUTE
                     │

              AUTHENTICATION
                     │
                     ▼
                VALIDATION
                     │
             ┌───────┴───────┐
             │               │

             │               │

            400          CONTROLLER
                             │

                             │
```

# 40. What Validation Does NOT Do

Don't turn validation into a giant layer that tries to do everything.

Validation should not normally:

```text
❌ Generate JWT
❌ Check password
❌ Decide ownership
❌ Create database records
❌ Send emails
❌ Decide user permissions
❌ Perform business workflows
```

Its job is primarily:

```text
Input
 ↓
Is it acceptable?
 ↓
Normalize/clean where appropriate
 ↓
Pass it onward
```

---

# 41. The Three Most Important Rules

### Rule 1

> **Never trust frontend validation.**

Always validate on the backend.

### Rule 2

> **Don't trust client-controlled ownership fields.**

Use:

```js
req.user.id
```

for the authenticated owner.

### Rule 3

> **Don't confuse validation with business logic.**

```text
Validation → Is the input valid?

Service → Is the operation allowed?
```

# 43. The Mental Model

At this point, our CRUD request has four major questions:

```text
Authentication
    ↓
WHO are you?

Ownership / Authorization
    ↓

    ↓
```

```text

    ↓
HOW do we persist/read the data?
```

This is an excellent mental model for backend development.
