# 1. What Is Service Logic?

Remember:

```text
Controller
    ↓
Service
    ↓
Repository
```

The Service answers:

> **What should happen when this CRUD operation is requested?**

The Repository answers:

> **How do I talk to MongoDB?**

For example:

```text
GET /notes/:id
       ↓
Controller
       ↓
noteService.getById()
       ↓
noteRepository.findByIdForUser()
       ↓
MongoDB
```

The Service sits between HTTP and database operations.

---

# 2. Why Do We Need a Service for CRUD?

A beginner might write:

```js
const getNote = async (req, res) => {
    const note = await Note.findById(req.params.id);

    res.json(note);
};
```

Everything is inside the controller.

That's exactly what we're trying to avoid.

Instead:

```text
Controller
   ↓
"Get this Note."
   ↓
Service
   ↓
"Here are the business rules."
   ↓
Repository
   ↓
"Here's the database query."
```

Your Phase 12 material describes the professional transformation as:

```text
Controller
    ↓
authService.login()
    ↓
repository
    ↓
database
```

rather than putting database and business operations directly into the controller.

# 3. Our Note Service

Let's imagine:

```text
services/
└── note.service.js
```

It might eventually contain:

```js
create()

```

So:

```text

       │
       ├── create
       ├── getById
       ├── getMany
       ├── update
       ├── delete
       └── restore
```

Each function represents an **application operation**.

---

# 4. Service ≠ Database

This distinction is extremely important.

Don't think:

```text
note.service.js
    ↓
MongoDB code
```

Instead:

```text
note.service.js
    ↓
Business/application decisions
    ↓
note.repository.js
    ↓
MongoDB
```

For example, this belongs more naturally in the Repository:

```js
Note.findOne({
    _id: noteId,
    userId
});
```

The Service shouldn't need to know every MongoDB detail.

---

# 5. Service Dependencies

The Note Service needs access to the Note Repository.

Conceptually:

```js
import noteRepository from "../repositories/note.repository.js";
```

Then:

```js
const getById = async (noteId, userId) => {
    return noteRepository.findByIdForUser(
        noteId,
        userId
    );
};
```

The flow is:

```text
Controller
    ↓
noteService.getById()
    ↓
noteRepository.findByIdForUser()
```

# 6. Create Service

Let's start with:

```text
create()
```

The controller might give the Service:

```js
{
    userId,
    title,
    content
}
```

The Service could look conceptually like:

```js
const create = async ({ userId, title, content }) => {
    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

Simple.

But here's the important question:

> Why not just call the repository directly from the controller?

Because business rules will eventually live here.

---

# 7. Where Business Logic Enters

Suppose our application has a rule:

> A user can have at most 100 active Notes.

Now:

```text
POST /notes
      ↓
Controller
      ↓
Service
      ↓
Does user have 100 active Notes?
      │
      ├── YES → reject
      │
      └── NO
           ↓
        Repository
           ↓
        Create
```

This is clearly Service logic.

The Repository should not decide:

> "Should this user be allowed to create another Note?"

That's an application rule.

---

# 8. Service Logic vs Repository Logic

Let's compare.

### Service

```text
Should this operation happen?
```

### Repository

```text
How do I query the database?
```

Example:

### Service

```js
if (activeCount >= 100) {
    throw new AppError(
        "Note limit reached",
        400
    );
}
```

### Repository

```js
Note.countDocuments({
    userId,
    isDeleted: false
});
```

Notice the difference.

The Repository knows **how to count**.

The Service knows **why the count matters**.

# 10. What Should the Service Receive?

A good Service API should receive the information it actually needs.

For example:

```js
noteService.create({
    userId: req.user.id,
    title: validatedData.title,
    content: validatedData.content
});
```

Not:

```js
noteService.create(req);
```

and not:

```js
noteService.create(req, res);
```

The Service shouldn't know about Express.

---

# 11. Keep Express Out of the Service

Avoid:

```js
const create = async (req, res) => {
    ...
};
```

inside the Service.

That's Controller responsibility.

Instead:

```js
const create = async ({
    userId,
    title,
    content
}) => {
    ...
};
```

This makes the Service independent of HTTP.

---

# 12. Why Is That Useful?

Because the same Service could eventually be called by:

```text
REST API
   ↓
noteService.create()

Background Job
   ↓
noteService.create()

CLI
   ↓
noteService.create()

GraphQL
   ↓
noteService.create()
```

The Service doesn't care where the request came from.

It just receives application data.

# 13. Get One

Now:

```js
getById(noteId, userId)
```

The Service might do:

```js
const getById = async (noteId, userId) => {
    const note =
        await noteRepository.findByIdForUser(
            noteId,
            userId
        );

    if (!note) {
        throw new AppError(
            "Note not found",
            404
        );
    }

    return note;
};
```

Notice something important.

The Repository returns:

```text
null
```

The Service turns that into:

```text
404 Not Found
```

This is a good separation.

---

# 14. Why Does the Service Handle This?

The Repository shouldn't necessarily decide:

```text
HTTP 404
```

because the Repository isn't an HTTP layer.

It knows:

```text
"Document wasn't found."
```

The Service understands:

```text
"For this application operation, that means Note not found."
```

Then the Controller/error architecture converts that into an HTTP response.

---

# 15. Ownership in the Service

Our previous lesson taught:

```js
{
    _id: noteId,
    userId
}
```

The Service should ensure the operation receives the authenticated user's identity.

For example:

```js
getById(noteId, userId)
```

not:

```js
getById(noteId)
```

for a user-owned resource.

So the flow becomes:

```text
JWT
 ↓
req.user.id
 ↓
Controller
 ↓
Service(noteId, userId)
 ↓
Repository(noteId, userId)
```

# 16. Get Many

Now:

```js
getMany(userId, options)
```

For example:

```js
const getMany = async (userId, options) => {
    return noteRepository.findManyByUser(
        userId,
        options
    );
};
```

Later `options` might contain:

```js
{
    page,
    limit,
    search,
    sort
}
```

Phase 18 will expand this significantly.

---

# 17. Why Use an `options` Object?

Instead of:

```js
getMany(
    userId,
    page,
    limit,
    search,
    sort,
    status
);
```

prefer:

```js
getMany(userId, {
    page,
    limit,
    search,
    sort,
    status
});
```

Why?

Because function calls with many positional arguments become difficult to understand.

Compare:

```js
getMany(userId, 1, 20, "javascript", "createdAt", "active");
```

with:

```js
getMany(userId, {
    page: 1,
    limit: 20,
    search: "javascript",
    sort: "createdAt",
    status: "active"
});
```

The second is much clearer.

# 18. Update Service

Update might look like:

```js
const update = async (
    noteId,
    userId,
    data

    const note =
        await noteRepository.updateByIdForUser(
            noteId,
            userId,
            data
        );

    if (!note) {
        throw new AppError(
            "Note not found",
            404
        );
    }

    return note;
};
```

Again:

```text
Service
 ↓
operation rules
 ↓
Repository
```

---

# 19. Should the Service Validate Data?

Remember Lesson 17.10.

We already have:

```text
Validation middleware
```

So basic structural validation should happen before the Service.

For example:

```text
title must be string
title max 100 chars
content required
```

belongs to validation.

But the Service can still enforce **business rules**.

Example:

```text
❌ title empty
```

→ validation problem.

But:

```text
❌ user has reached maximum number of active Notes
```

→ business rule.

---

# 20. Service-Level Business Validation

Consider:

```text
User has 100 Notes.
```

Request:

```text
Create another Note.
```

Input itself is valid:

```json
{
  "title": "Learn Redis",
  "content": "Study caching."
}
```

But the operation isn't allowed.

Therefore:

```text
Validation
    ↓
PASS

Service business rule
    ↓
FAIL
```

That's exactly why we need both layers.

# 21. Delete Service

For soft delete:

```js
const remove = async (noteId, userId) => {
    const note =
        await noteRepository.softDeleteForUser(
            noteId,
            userId
        );

    if (!note) {
        throw new AppError(
            "Note not found",
            404
        );
    }

    return note;
};
```

The Service doesn't write:

```js
Note.findOneAndUpdate(...)
```

That's Repository work.

---

# 22. Restore Service

Similarly:

```js
const restore = async (noteId, userId) => {
    const note =
        await noteRepository.restoreForUser(
            noteId,
            userId
        );

    if (!note) {
        throw new AppError(
            "Deleted Note not found",
            404
        );
    }

    return note;
};
```

Notice the Service understands the application operation:

```text
restore
```

while the Repository handles the MongoDB query.

# 24. What the Service Should NOT Do

Avoid putting these inside the Service:

```text
❌ req.body
❌ req.params
❌ req.query
❌ res.status()
❌ res.json()
❌ res.cookie()
```

Those belong to HTTP/controller concerns.

Also avoid direct database operations when a Repository abstraction is part of your architecture:

```text
❌ Note.find(...)
❌ Note.findOne(...)
❌ Note.create(...)
```

inside the Service.

Instead:

```text
Service
   ↓
Repository
```

---

# 25. What the Service SHOULD Do

The Service can:

```text
✅ coordinate operations
✅ apply business rules
✅ call repositories
✅ combine multiple repositories
✅ decide when an operation should fail
✅ transform application-level results
✅ enforce use-case rules
```

For example:

```text
Create Note
    ↓
Check user exists
    ↓
Check user hasn't reached limit
    ↓
Create Note
    ↓
Return Note
```

That's Service logic.

---

# 26. Service Composition

Sometimes one operation needs multiple repositories.

For example:

```text
Create Note
     │
     ├── User Repository
     │       ↓
     │   Find user
     │
     └── Note Repository
             ↓
         Create note
```

The Service coordinates both.

```text
noteService
     │
     ├── userRepository
     └── noteRepository
```

This is one reason Services are valuable.

# 27. Example: User Limit

Imagine:

```text
Business rule:

User can create maximum 100 active Notes.
```

Service:

```js
const create = async ({ userId, title, content }) => {
    const count =
        await noteRepository.countActiveByUser(userId);

    if (count >= 100) {
        throw new AppError(
            "Maximum active notes reached",
            400
        );
    }

    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

Repository:

```js
const countActiveByUser = async (userId) => {
    return Note.countDocuments({
        userId,
        isDeleted: false
    });
};
```

Perfect separation.

# 28. Another Example: Update Restrictions

Suppose deleted Notes cannot be edited.

The Service could enforce:

```text
Update request
    ↓
Is Note active?
    │
    ├── NO → reject
    │
    └── YES → update
```

The Repository could make the query:

```js
{
    _id: noteId,
    userId,
    isDeleted: false
}
```

So the Service expresses the operation:

```text
"Update an active Note."
```

and the Repository implements the data access.

# 29. Service Errors

A Service can throw application-level errors:

```js
throw new AppError(
    "Note not found",
    404
);
```

or:

```js
throw new AppError(
    "You cannot create more than 100 active notes",
    400
);
```

The global error architecture handles the final HTTP response.

So:

```text
Service
   ↓
throw AppError
   ↓
asyncHandler
   ↓
error middleware
   ↓
JSON response
```

This connects directly to your Phase 8 error architecture.

# 30. Service Doesn't Know About HTTP

This is one of the best tests for whether you've designed your Service correctly.

Ask:

> **Could I call this Service from a test without Express?**

If yes:

```text
Good.
```

If the Service requires:

```js
req
res
next
```

then you've mixed layers.

# 31. Unit Testing Becomes Easier

Suppose:

```js
noteService.getById(noteId, userId)
```

You can test:

```text
Given Note exists
    ↓
returns Note

Given Note doesn't exist
    ↓
throws Not Found
```

You don't need to start the entire HTTP server to test the business logic.

This is one of the major benefits of separating Services.

# 35. The Most Important Principle

Don't make the Service a second Controller.

Bad:

```js
noteService.create = async (req, res) => {
    ...
};
```

Don't make the Service a second Repository either.

Bad:

```js
noteService.create = async () => {
    await Note.create(...);
};
```

when your architecture has a Repository layer.

Instead:

```text
Controller
   ↓
Service
   ↓
Repository
```

Each layer has one clear job.

# 36. A Practical Note Service

A simplified version might look like:

```js
const create = async ({ userId, title, content }) => {
```

# 37. A Better Mental Model

When you write a Service function, ask four questions:

```text
1. What operation is this?

2. What business rules apply?

3. What data do I need?

4. Which repository operations do I need?
```

For example:

### `updateNote`

```text
Operation:
Update Note

Business rules:
Only owner can update
Deleted Notes cannot be updated

Data:
noteId
userId
validated update data

Repository:
updateByIdForUser()
```

That's Service design.

# 38. CRUD Service Table

|Operation|Service Responsibility|
|---|---|
|Create|Apply creation rules|
|Read one|Check result / application rules|
|Read many|Coordinate filters/options|
|Update|Apply update rules|
|Delete|Apply deletion rules|
|Restore|Apply restore rules|

And Repository:

|Operation|Repository Responsibility|
|---|---|
|Create|Insert document|
|Read one|Query document|
|Read many|Query collection|
|Update|Update document|
|Delete|Soft/hard delete|
|Restore|Restore document|
