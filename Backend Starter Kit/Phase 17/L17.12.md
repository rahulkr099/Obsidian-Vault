# Lesson 17.12 — Repository Queries

Now we move to the next layer of our CRUD architecture:

```text
17.11 Service Logic
        ↓
17.12 Repository Queries
        ↓
17.13 Controller Design
```

The key idea for this lesson is:

> **The Repository is responsible for talking to the database.**

The Service decides **what should happen**.  
The Repository decides **how to retrieve or modify the data**.

---

# 1. Where Repository Fits

Our complete flow is now:

```text
Client
  ↓
Route
  ↓
Authentication
  ↓
Validation
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

For a Note:

```text
note.controller
       ↓
note.service
       ↓
note.repository
       ↓
Note model
       ↓
MongoDB
```

This separation is one of the main purposes of Phase 17.

---

# 2. What Is a Repository Query?

A Repository contains database operations such as:

```text
create
findById
findMany
update
softDelete
restore
count
```

For example:

```js
const findById = async (noteId) => {
    return Note.findById(noteId);
};
```

The Service doesn't need to know that we're using:

```js
Note.findById()
```

It simply asks:

```js
noteRepository.findById(noteId);
```

---

# 3. Repository Should Know MongoDB

Unlike the Service, the Repository **can** know about MongoDB.

For example:

```js
const findByIdForUser = async (noteId, userId) => {
    return Note.findOne({
        _id: noteId,
        userId
    });
};
```

That's exactly what the Repository is for.

It understands:

```text
MongoDB
Mongoose
queries
filters
updates
indexes
```

The Service shouldn't need to understand all these details.

---

# 4. Our Note Repository

We might have:

```text
repositories/
└── note.repository.js
```

Inside:

```text
note.repository.js
│
├── create()
├── findByIdForUser()
├── findManyByUser()
├── updateByIdForUser()
├── softDeleteForUser()
├── restoreForUser()
└── countActiveByUser()
```

These are **data-access operations**.

---

# 5. Create Query

Our first operation:

```js
const create = async (data) => {
    return Note.create(data);
};
```

The Service calls:

```js
return noteRepository.create({
    userId,
    title,
    content
});
```

The Repository handles:

```js
Note.create(...)
```

So:

```text
Service
  ↓
create(data)
  ↓
Repository
  ↓
Note.create(data)
  ↓
MongoDB
```

---

# 6. Why Not Put `Note.create()` in the Service?

You could technically do it.

For example:

```js
const create = async (data) => {
    return Note.create(data);
};
```

But now the Service is directly coupled to MongoDB/Mongoose.

If your architecture has a Repository layer, you want:

```text
Service
   ↓
Repository
   ↓
Database
```

This gives each layer a clear responsibility.

---

# 7. Find One Note

A basic query:

```js
const findById = async (noteId) => {
    return Note.findById(noteId);
};
```

But because our Notes are user-owned, we usually need more than the ID.

We need:

```text
noteId
+
userId
```

So a better repository method is:

```js
const findByIdForUser = async (noteId, userId) => {
    return Note.findOne({
        _id: noteId,
        userId
    });
};
```

This is an important pattern.

---

# 8. Why Include `userId` in the Query?

Imagine:

```text
User A
 └── Note A

User B
 └── Note B
```

User A requests:

```http
GET /notes/<note-B-id>
```

If your Repository does:

```js
Note.findById(noteId);
```

it may return User B's Note.

That's dangerous.

Instead:

```js
Note.findOne({
    _id: noteId,
    userId
});
```

means:

> Find this Note **only if it belongs to this user**.

So ownership becomes part of the data-access query.

---

# 9. Ownership Query Pattern

This is a pattern worth remembering:

```js
{
    _id: resourceId,
    userId: authenticatedUserId
}
```

For example:

```js
const note = await Note.findOne({
    _id: noteId,
    userId
});
```

This gives us:

```text
Resource ID
     +
Owner ID
     ↓
Correct resource
```

It is much safer than:

```js
Note.findById(noteId);
```

for a user-owned resource.

---

# 10. Get Many Notes

Now suppose:

```http
GET /api/v1/notes
```

We need:

> Get Notes belonging to this user.

Repository:

```js
const findManyByUser = async (userId) => {
    return Note.find({
        userId
    });
};
```

Notice the Repository doesn't need to know:

```text
Who is the logged-in user?
```

The Service/controller provides the `userId`.

---

# 11. Soft Delete

From our earlier CRUD lessons, we aren't necessarily physically deleting the document.

Instead:

```js
isDeleted: true
```

Repository:

```js
const softDeleteForUser = async (noteId, userId) => {
    return Note.findOneAndUpdate(
        {
            _id: noteId,
            userId,
            isDeleted: false
        },
        {
            $set: {
                isDeleted: true
            }
        },
        {
            new: true
        }
    );
};
```

Notice three filters:

```text
_id
userId
isDeleted: false
```

That's a very useful query.

---

# 12. Why `isDeleted: false`?

Suppose the Note is already deleted.

Request:

```http
DELETE /notes/123
```

The query:

```js
{
    _id: noteId,
    userId,
    isDeleted: false
}
```

won't find it.

Therefore:

```text
already deleted
      ↓
query returns null
      ↓
Service handles "not found"
```

This keeps the Repository query precise.

---

# 13. Restore Query

Restore is basically the opposite:

```js
const restoreForUser = async (noteId, userId) => {
    return Note.findOneAndUpdate(
        {
            _id: noteId,
            userId,
            isDeleted: true
        },
        {
            $set: {
                isDeleted: false
            }
        },
        {
            new: true
        }
    );
};
```

Notice:

```text
Delete:
isDeleted: false → true

Restore:
isDeleted: true → false
```

---

# 14. Update Query

Update:

```js
const updateByIdForUser = async (
    noteId,
    userId,
    data
) => {
    return Note.findOneAndUpdate(
        {
            _id: noteId,
            userId,
            isDeleted: false
        },
        {
            $set: data
        },
        {
            new: true,
            runValidators: true
        }
    );
};
```

The important filter is:

```js
{
    _id: noteId,
    userId,
    isDeleted: false
}
```

So the operation means:

> Update this active Note only if it belongs to this user.

---

# 15. Why `runValidators`?

When using update operations with Mongoose, you may want schema validators to run during updates.

For example:

```js
{
    title: {
        type: String,
        required: true,
        maxlength: 100
    }
}
```

Using:

```js
runValidators: true
```

helps ensure the update respects the Mongoose schema validation rules.

Remember:

```text
Request validation
       ↓
Application boundary

Mongoose validation
       ↓
Model/database boundary
```

They're complementary.

---

# 16. Active Notes Query

Suppose the Service needs to know:

> How many active Notes does this user have?

Repository:

```js
const countActiveByUser = async (userId) => {
    return Note.countDocuments({
        userId,
        isDeleted: false
    });
};
```

The Repository knows:

```text
how to count documents
```

The Service knows:

```text
why the count matters
```

For example:

```js
const count = await noteRepository.countActiveByUser(userId);

if (count >= 100) {
    throw new AppError(
        "Maximum active notes reached",
        400
    );
}
```

Perfect separation.

---

# 17. Repository Should Return Data

Generally, the Repository should return:

```text
document
documents
count
null
```

For example:

```js
return Note.findOne(...);
```

or:

```js
return Note.find(...);
```

or:

```js
return Note.countDocuments(...);
```

The Service decides what those results mean for the application.

---

# 18. Repository Shouldn't Send HTTP Responses

Never do:

```js
res.status(404).json(...)
```

inside the Repository.

Why?

Because Repository shouldn't know about:

```text
Express
HTTP
status codes
res
req
```

Its job is database access.

---

# 19. Repository Shouldn't Throw HTTP Errors Unnecessarily

Avoid making your Repository heavily dependent on:

```js
new AppError("Not found", 404)
```

Instead:

```js
const note = await Note.findOne(...);

return note;
```

If:

```text
note === null
```

the Service can decide:

```text
"Note not found"
```

This keeps the Repository reusable.

---

# 20. Service + Repository

Now compare the two.

### Service

```js
const getById = async (noteId, userId) => {
    const note =
        await noteRepository.findByIdForUser(
            noteId,
            userId
        );

    if (!note) {
        throw new AppError(
            "Note not found",
            404
        );
    }

    return note;
};
```

### Repository

```js
const findByIdForUser = async (
    noteId,
    userId
) => {
    return Note.findOne({
        _id: noteId,
        userId,
        isDeleted: false
    });
};
```

This is clean.

---

# 21. Repository Naming

Good Repository method names should describe the data operation.

Examples:

```text
findById
findByIdForUser
findManyByUser
countActiveByUser
create
updateByIdForUser
softDeleteForUser
restoreForUser
```

Avoid vague names such as:

```text
getData()
doQuery()
databaseOperation()
handleNote()
```

Good names make the architecture self-documenting.

---

# 22. Repository Methods Should Match Use Cases

Instead of exposing every possible MongoDB operation:

```text
find()
findOne()
findOneAndUpdate()
updateMany()
deleteMany()
aggregate()
...
```

your Repository can expose meaningful application data operations.

For example:

```js
findByIdForUser(noteId, userId)
```

is much clearer than making the Service construct:

```js
findOne({
    _id: noteId,
    userId
})
```

The Repository owns that query detail.

---

# 23. Avoid Generic Repository Abuse

You might eventually see something like:

```js
repository.find({
    filter,
    projection,
    sort,
    populate,
    options
});
```

A generic Repository can sometimes be useful, but don't force everything into one giant method.

For example:

```js
noteRepository.find(...)
```

doesn't tell us much.

Compare:

```js
noteRepository.findByIdForUser(...)
```

The second communicates intent much better.

---

# 24. Query Composition

For a more complex list endpoint, the Repository may receive structured options:

```js
{
    userId,
    page,
    limit,
    search,
    sort
}
```

Then it builds the database query.

For example:

```js
const findManyByUser = async ({
    userId,
    skip,
    limit,
    search
}) => {
    const filter = {
        userId,
        isDeleted: false
    };

    // add search conditions if needed

    return Note.find(filter)
        .skip(skip)
        .limit(limit);
};
```

The Service can calculate:

```text
page → skip
limit → limit
```

while the Repository handles MongoDB query construction.

---

# 25. Filtering and Business Logic

Suppose the client sends:

```http
GET /notes?status=deleted
```

The Service might decide:

```text
Is this user allowed to request deleted Notes?
```

Then the Repository receives a well-defined query option.

This is another example of:

```text
Service
 ↓
decides what data is needed
 ↓
Repository
 ↓
builds database query
```

---

# 26. Pagination

Later, we may have:

```text
page = 2
limit = 20
```

The Service can calculate:

```js
const skip = (page - 1) * limit;
```

Then Repository:

```js
Note.find(filter)
    .skip(skip)
    .limit(limit);
```

So:

```text
Service
  ↓
pagination rules
  ↓
Repository
  ↓
MongoDB skip/limit
```

Phase 18 will take this further.

---

# 27. Projection

Suppose we don't need every field.

Repository can use projection:

```js
Note.find(
    filter,
    {
        title: 1,
        content: 1
    }
);
```

Again, this is database/query knowledge.

Therefore it belongs naturally in the Repository.

---

# 28. Sorting

Repository can also handle database sorting:

```js
Note.find(filter)
    .sort({
        createdAt: -1
    });
```

The Service might decide:

```text
default sort = newest first
```

The Repository implements:

```js
.sort({ createdAt: -1 })
```

---

# 29. Important Separation

Think:

```text
Service:
"What data should the application operation retrieve?"

Repository:
"How do I write the MongoDB query to retrieve it?"
```

Example:

```text
Service:
"Get the user's active Notes, newest first."

Repository:
Note.find({
    userId,
    isDeleted: false
}).sort({
    createdAt: -1
});
```

---

# 30. Repository and Transactions

Repositories become especially useful when an operation involves multiple database actions.

For example:

```text
Create Note
   ↓
Create audit record
   ↓
Update user statistics
```

You may eventually need a transaction.

The Repository layer can encapsulate the database operations and transaction/session handling.

The Service can coordinate the overall business operation.

Conceptually:

```text
Service
   ↓
"Perform this business operation"
   ↓
Repositories + transaction
   ↓
Database
```

We'll build more advanced versions of this idea later.

---

# 31. Don't Overcomplicate the Repository

For our current Notes API, we don't need:

```text
50 abstraction layers
generic query builders
complex ORM wrappers
```

Start with simple methods:

```js
create()
findByIdForUser()
findManyByUser()
updateByIdForUser()
softDeleteForUser()
restoreForUser()
```

Clean and understandable is better.

# 32. Complete Note Repository

A simplified Repository could look like:

```js
const create = async (data) => {
    return Note.create(data);
};

const findByIdForUser = async (noteId, userId) => {
    return Note.findOne({
        _id: noteId,
        userId,
        isDeleted: false
    });
};

const findManyByUser = async (userId) => {
    return Note.find({
        userId,
        isDeleted: false
    });
};

const updateByIdForUser = async (
    noteId,
    userId,
    data
) => {
    return Note.findOneAndUpdate(
        {
            _id: noteId,
            userId,
            isDeleted: false
        },
        {
            $set: data
        },
        {
            new: true,
            runValidators: true
        }
    );
};

const softDeleteForUser = async (
    noteId,
    userId
) => {
    return Note.findOneAndUpdate(
        {
            _id: noteId,
            userId,
            isDeleted: false
        },
        {
            $set: {
                isDeleted: true
            }
        },
        {
            new: true
        }
    );
};

const restoreForUser = async (
    noteId,
    userId
) => {
    return Note.findOneAndUpdate(
        {
            _id: noteId,
            userId,
            isDeleted: true
        },
        {
            $set: {
                isDeleted: false
            }
        },
        {
            new: true
        }
    );
};

export default {
    create,
    findByIdForUser,
    findManyByUser,
    updateByIdForUser,
    softDeleteForUser,
    restoreForUser
};
```

This is the kind of Repository we'll use as the foundation for the rest of Phase 17.

# 33. Notice Something Important

Look at every user-owned query:

```js
{
    userId
}
```

or:

```js
{
    _id: noteId,
    userId
}
```

This is not accidental.

We learned in **17.9 Ownership** that a resource should be scoped to the authenticated user.

So our Repository becomes one of the places where that ownership boundary is enforced.

---

# 34. But Don't Rely Only on Repository Ownership

Still keep the architecture clear.

```text
Authentication
   ↓
Who is this?

Authorization/ownership
   ↓
Is this user allowed?

Repository query
   ↓
Only retrieve matching user's resource
```

Defense in depth is valuable.

# 36. Final Architecture After 17.12

We now have:

```text
                   HTTP
                    │
                    ▼
                  Route
                    │
                    ▼
             Authentication
                    │
                    ▼
               Validation
                    │
                    ▼
               Controller
                    │
                    ▼
                 Service
              business rules
                    │
                    ▼
               Repository
                DB queries
                    │
                    ▼
                 Model
                    │
                    ▼
```

|Layer|Main responsibility|
|---|---|
