# Lesson 17.13 — Controller Design

We now have:

```text
17.10 Validation
       ↓
17.11 Service Logic
       ↓
17.12 Repository Queries
       ↓
17.13 Controller Design
```

Your Phase 17 source explicitly puts **Controller Design** after Service Logic and Repository Queries, as part of building the reusable CRUD feature around a `Notes` resource.

You already studied Controllers deeply in Phase 11. So here we're going to apply that knowledge to our **Notes CRUD architecture**.

---

# 1. What Is the Controller's Job?

The easiest definition is:

> **A Controller is the HTTP translator between the request and your application logic.**

Your earlier architecture defines the Controller as translating:

```text
HTTP → application
```

and:

```text
application → HTTP
```

So the Controller deals with things like:

```text
req
res
req.body
req.params
req.query
req.user
HTTP status codes
HTTP response
```

But it should **not** contain your business logic or database queries.

---

# 2. Our Note Request Flow

For example:

```http
POST /api/v1/notes
```

The request travels:

```text
Client
  ↓
Route
  ↓
Authentication
  ↓
Validation
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
MongoDB
```

And the response travels back:

```text
MongoDB
  ↓
Repository
  ↓
Service
  ↓
Controller
  ↓
HTTP Response
  ↓
Client
```

The Controller is basically the **bridge**.

---

# 3. What the Controller Should Do

For a `POST /notes` request, the Controller should roughly:

```text
1. Read authenticated user
2. Read validated input
3. Call Service
4. Receive result
5. Send HTTP response
```

That's it.

Conceptually:

```js
const createNote = asyncHandler(async (req, res) => {
    const note = await noteService.create({
        userId: req.user.id,
        title: req.validated.title,
        content: req.validated.content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

Notice how small it is.

---

# 4. Why Is This Controller "Thin"?

Because it doesn't contain:

```text
❌ MongoDB query
❌ business rules
❌ password logic
❌ ownership query
❌ complex validation
❌ database update
```

Instead:

```text
Controller
   ↓
collect input
   ↓
call Service
   ↓
send response
```

This is what we mean by a **thin controller**.

---

# 5. The Controller Does NOT Create the Note

This is an important distinction.

Don't do:

```js
const createNote = async (req, res) => {
    const note = await Note.create({
        userId: req.user.id,
        title: req.body.title,
        content: req.body.content
    });

    res.status(201).json(note);
};
```

Why is this bad?

Because the Controller now knows:

```text
HTTP
+
business operation
+
MongoDB
```

We've already separated those responsibilities.

Instead:

```text
Controller
    ↓
noteService.create()
    ↓
noteRepository.create()
```

---

# 6. Controller Dependencies

Our Controller will usually depend on the Service:

```js
import noteService from "../services/note.service.js";
```

Not directly on the Model:

```js
// Avoid this in the controller
import Note from "../models/note.model.js";
```

The intended architecture is:

```text
Controller
     ↓
Service
     ↓
Repository
     ↓
Model
```

---

# 7. Create Controller

Let's build our first CRUD Controller.

```js
const create = asyncHandler(async (req, res) => {
    const note = await noteService.create({
        userId: req.user.id,
        title: req.validated.title,
        content: req.validated.content
    });

    res.status(201).json({
        success: true,
        message: "Note created successfully",
        data: note
    });
});
```

Let's understand every line.

---

# 8. `asyncHandler`

We use:

```js
asyncHandler(async (req, res) => {
```

instead of:

```js
try {
   ...
} catch(error) {
   next(error);
}
```

because your backend architecture already has centralized async/error handling.

The flow becomes:

```text
Controller
   ↓
throws error
   ↓
asyncHandler
   ↓
error middleware
   ↓
standard error response
```

This matches the error architecture established earlier in your starter roadmap.

---

# 9. Reading `req.user`

Authentication middleware gives us:

```js
req.user
```

For example:

```js
req.user.id
```

So:

```js
userId: req.user.id
```

means:

> Create this Note for the authenticated user.

We should **not** get ownership from:

```js
req.body.userId
```

because the client shouldn't control ownership.

---

# 10. Reading Validated Data

From Lesson 17.10, we don't want to blindly trust:

```js
req.body
```

Instead, our validation middleware can produce validated data:

```js
req.validated
```

So:

```js
title: req.validated.title,
content: req.validated.content
```

means:

```text
raw request
    ↓
validation
    ↓
validated input
    ↓
controller
```

The exact property name can vary by project; the important thing is to establish one consistent convention.

---

# 11. Controller Calls Service

The important line is:

```js
const note = await noteService.create({
    userId: req.user.id,
    title: req.validated.title,
    content: req.validated.content
});
```

The Controller is saying:

> "Service, please create this Note."

It isn't saying:

> "Here is how MongoDB should create the Note."

That's the Repository's job.

---

# 12. Controller Sends Response

After the Service returns:

```js
note
```

the Controller converts it into HTTP:

```js
res.status(201).json({
    success: true,
    message: "Note created successfully",
    data: note
});
```

So:

```text
Application result
       ↓
Controller
       ↓
HTTP response
```

This is exactly why we call it an HTTP translator.

---

# 13. Why `201 Created`?

For a successful creation:

```http
201 Created
```

is appropriate.

Compare:

```text
GET successful       → 200
POST creates         → 201
PUT/PATCH successful → 200 or 204
DELETE successful    → 200 or 204
```

You studied status codes in Phase 16, so here we're applying them to CRUD.

---

# 14. Read One Controller

Now:

```http
GET /api/v1/notes/:id
```

Controller:

```js
const getById = asyncHandler(async (req, res) => {
    const note = await noteService.getById(
        req.params.id,
        req.user.id
    );

    res.status(200).json({
        success: true,
        data: note
    });
});
```

Notice:

```js
req.params.id
```

comes from:

```text
/notes/:id
```

And:

```js
req.user.id
```

comes from authentication.

The Controller passes both to the Service.

---

# 15. Why Pass `userId`?

Because this is a user-owned resource.

We want:

```text
GET /notes/123
```

to mean:

> Give me Note `123` **if it belongs to me**.

Not:

> Give me Note `123` regardless of its owner.

So:

```js
noteService.getById(
    req.params.id,
    req.user.id
);
```

is important.

---

# 16. Read Many Controller

Now:

```http
GET /api/v1/notes
```

Controller:

```js
const getMany = asyncHandler(async (req, res) => {
    const notes = await noteService.getMany(
        req.user.id,
        req.validatedQuery
    );

    res.status(200).json({
        success: true,
        data: notes
    });
});
```

Now we have:

```text
req.user.id
        ↓
ownership

req.validatedQuery
        ↓
pagination/filter/sort options
```

The Controller simply passes them onward.

---

# 17. Why Not Parse Pagination in the Controller?

You might eventually have:

```http
GET /notes?page=2&limit=20
```

You could write:

```js
const page = Number(req.query.page);
const limit = Number(req.query.limit);
```

But remember our layered architecture.

A cleaner flow is:

```text
req.query
   ↓
validation
   ↓
validatedQuery
   ↓
controller
   ↓
service
```

The Controller shouldn't become a giant query-processing layer.

Phase 18 will expand pagination, filtering, and sorting.

---

# 18. Update Controller

```http

const update = asyncHandler(async (req, res) => {

    res.status(200).json({
        success: true,
        message: "Note updated successfully",
        data: note
    });
});
```

Very small.

The Controller handles:

```text
params
user
validated body
response
```

The Service handles:

```text
update rules
```

The Repository handles:

```text
MongoDB update
```

---

# 19. Delete Controller

For:

```http
DELETE /api/v1/notes/:id
```

we can write:

```js
const remove = asyncHandler(async (req, res) => {
    await noteService.remove(
        req.params.id,
        req.user.id
    );

    res.status(200).json({

    });

```

Notice that the Controller doesn't care whether the Service performs:

```text
soft delete
```

or:

```text
hard delete
```

That's an implementation detail of the lower layers.

# 21. Complete Controller

Our Controller might eventually look like:

```js
import asyncHandler from "../utils/asyncHandler.js";
import noteService from "../services/note.service.js";

const create = asyncHandler(async (req, res) => {
    const note = await noteService.create({
        userId: req.user.id,
        title: req.validated.title,
        content: req.validated.content
    });

    res.status(201).json({
        success: true,
        message: "Note created successfully",
        data: note
    });
});

const getById = asyncHandler(async (req, res) => {
    const note = await noteService.getById(
        req.params.id,
        req.user.id
    );

    res.status(200).json({
        success: true,
        data: note
    });
});

const getMany = asyncHandler(async (req, res) => {
    const notes = await noteService.getMany(
        req.user.id,
        req.validatedQuery
    );

    res.status(200).json({
        success: true,
        data: notes
    });
});

const update = asyncHandler(async (req, res) => {
    const note = await noteService.update(
        req.params.id,
        req.user.id,
        req.validated
    );

    res.status(200).json({
        success: true,
        message: "Note updated successfully",
        data: note
    });
});

const remove = asyncHandler(async (req, res) => {
    await noteService.remove(
        req.params.id,
        req.user.id
    );

    res.status(200).json({
        success: true,
        message: "Note deleted successfully"
    });
});

const restore = asyncHandler(async (req, res) => {
    const note = await noteService.restore(

    create,

```

That's a very reasonable CRUD Controller.

# 22. Look at How Thin It Is

The Controller contains almost no complicated logic.

```text
create()
   ↓
read input
   ↓
call service
   ↓
send response
```

```text
getById()
   ↓
read params/user
   ↓
call service
   ↓
send response
```

```text
update()
   ↓
read params/user/body
   ↓
call service
   ↓
send response
```

That's what we want.

---

# 23. The Controller Should Not Know the Repository

This:

```js
noteRepository.findByIdForUser(...)
```

should **not** appear in your Controller.

Why?

Because then:

```text
Controller
   ↓
Repository
```

would bypass:

```text
Service
```

You lose the business-logic boundary.

Keep:

```text
Controller
   ↓
Service
   ↓
Repository
```

---

# 24. The Controller Should Not Know MongoDB

Avoid:

```js
Note.find(...)
Note.findOne(...)
Note.create(...)
Note.findOneAndUpdate(...)
```

inside the Controller.

The Controller should not care whether your database is:

```text
MongoDB
PostgreSQL
MySQL
```

The lower layers handle that.

---

# 25. The Controller Should Not Repeat Validation

Avoid:

```js
if (!req.body.title) {
    ...
}

if (typeof req.body.title !== "string") {
    ...
}

if (req.body.title.length > 100) {
    ...
}
```

when you already have validation middleware.

The intended flow is:

```text
Request
  ↓
Validation middleware
  ↓
Controller
```

This keeps the Controller clean.

---

# 26. The Controller Should Not Implement Business Rules

Avoid:

```js
if (activeNotes >= 100) {
    return res.status(400)...
}
```

That belongs in the Service.

Why?

Because:

```text
"Maximum 100 Notes"
```

is a business rule, not an HTTP concern.

Instead:

```text
Controller
   ↓
noteService.create()
   ↓
Service checks limit
```

---

# 27. Controller as an Adapter

A useful mental model:

```text
HTTP world
     │
     ▼
Controller
     │
     ▼
Application world
```

For example:

```text
HTTP:
req.params.id
req.user.id
req.validated

        ↓

Application:
noteService.getById(
    noteId,
    userId
)
```

And back:

```text
Application result
        ↓
Controller
        ↓
HTTP JSON
```

---

# 28. What If Service Throws an Error?

Suppose:

```js
noteService.getById(...)
```

doesn't find the Note.

The Service may throw:

```js
throw new AppError(
    "Note not found",
    404
);
```

The Controller doesn't need:

```js
try/catch
```

if `asyncHandler` handles rejected promises.

Flow:

```text
Service
   ↓
throw AppError
   ↓
asyncHandler
   ↓
error middleware
   ↓
404 JSON response
```

This keeps every Controller small.

---

# 29. Controller and Response Architecture

Since you've already completed Phase 16, the Controller should follow your established response contract.

For example:

```json
{
  "success": true,
  "message": "Note created successfully",
  "data": {
    "_id": "...",
    "title": "Learn MongoDB"
  }
}
```

The exact envelope depends on the response architecture you established in Phase 16.

The important point is:

> **Controllers should consistently convert Service results into your API response format.**

# 30. Don't Over-Abstract Controllers

There's another mistake:

Trying to create something like:

```js
genericCrudController(...)
```

before you understand your actual use cases.

For learning, explicit functions are better:

```text
create
getById
getMany
update
remove
restore
```

You can recognize the operation immediately.

Abstraction should solve a real duplication problem.

# 32. Why `remove` Instead of `delete`?

You may see:

```js
delete
```

as a function name.

But JavaScript has the `delete` operator.

Using:

```js
remove
```

is often cleaner:

```js
const remove = asyncHandler(...)
```

Then:

```text
Controller.remove()
Service.remove()
Repository.softDeleteForUser()
```

Notice the Repository is more explicit because it describes the actual database operation.

# 33. Controller Input Map

A useful table:

|Input|Comes from|Controller uses|
|---|---|---|
|`userId`|`req.user`|Ownership|
|`noteId`|`req.params`|Resource ID|
|`title`|validated body|Create/update|
|`content`|validated body|Create/update|
|`page`|validated query|Listing|
|`limit`|validated query|Listing|
|`search`|validated query|Listing|

This is basically the Controller's job:

> Collect the right input and hand it to the right application operation.

# 35. Controller → Service → Repository

Let's trace one complete request.

### Request

```http
PATCH /api/v1/notes/123
```

Body:

```json
{
  "title": "Updated title"
}
```

### Authentication

```text
req.user.id = user123
```

### Validation

```text
req.validated = {
    title: "Updated title"
}
```

### Controller

```js
noteService.update(
    "123",
    "user123",
    {
        title: "Updated title"
    }
);
```

### Service

```text
Apply business rules
       ↓
Repository
```

### Repository

```js
Note.findOneAndUpdate(
    {
        _id: "123",
        userId: "user123",
        isDeleted: false
    },
    {
        $set: {
            title: "Updated title"
        }
    }
);
```

### Response

```text
Repository
   ↓
Service
   ↓
Controller
   ↓
200 JSON
```

That is the entire architecture working together.

# 36. A Powerful Test for Controllers

When reviewing a Controller, ask:

> **Can I explain every line as HTTP handling or Service invocation?**

If yes:

```text
✅ probably a thin Controller
```

If you see:

```text
MongoDB queries
large loops
business rules
complex calculations
permission rules
password hashing
```

then you've probably put too much into the Controller.

---

# 37. Controller Responsibilities — Final Version

A CRUD Controller should generally:

```text
✅ Receive HTTP request
✅ Read req.params
✅ Read req.query
✅ Read req.user
✅ Read validated body
✅ Call Service
✅ Choose HTTP status
✅ Build API response
```

It should generally NOT:

```text
❌ Query MongoDB
❌ Access Repository directly
❌ Implement business rules
❌ Perform complex validation
❌ Decide ownership using client input
❌ Contain large workflows
```
