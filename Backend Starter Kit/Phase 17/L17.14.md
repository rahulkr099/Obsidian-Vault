
The goal is simple:

---

# 1. What Is a Route?

A route answers:

> **Which URL + HTTP method should execute which Controller?**

For example:

```http
POST /api/v1/notes
```

might execute:

```js
noteController.create
```

So:

```text
POST /api/v1/notes
        ↓
noteController.create
```

That's the basic job of a route.

---

# 2. Route vs Controller

This distinction is extremely important.

### Route

Answers:

> **Where does this request go?**

### Controller

Answers:

> **What HTTP operation should happen?**

For example:

```js
router.post("/", noteController.create);
```

The Route says:

```text
POST /
   ↓
create controller
```

The Controller then does:

```text
request
 ↓
service
 ↓
response
```

---

# 3. Route Should Not Contain Business Logic

Avoid this:

```js
router.post("/notes", async (req, res) => {
    const user = await User.findById(req.user.id);

    if (user.notesCount >= 100) {
        return res.status(400).json({
            message: "Limit reached"
        });
    }

    const note = await Note.create({
        userId: req.user.id,
        title: req.body.title
    });

    res.status(201).json(note);
});
```

This route now contains:

```text
❌ database queries
❌ business rules
❌ validation
❌ HTTP handling
```

It becomes difficult to maintain.

Instead:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
```

---

# 4. Our Notes Route

Let's create:

```text
routes/
└── note.routes.js
```

Basic version:

```js
import { Router } from "express";
import noteController from "../controllers/note.controller.js";

const router = Router();

router.post("/", noteController.create);
router.get("/", noteController.getMany);
router.get("/:id", noteController.getById);
router.patch("/:id", noteController.update);
router.delete("/:id", noteController.remove);

export default router;
```

This is already much cleaner.

---

# 5. Mounting the Route

Our `app.js` might have:

```js
import noteRoutes from "./routes/note.routes.js";

app.use("/api/v1/notes", noteRoutes);
```

Now combine the two pieces.

Inside the router:

```js
router.post("/", noteController.create);
```

Mounted at:

```js
app.use("/api/v1/notes", noteRoutes);
```

Therefore the final endpoint is:

```http
POST /api/v1/notes
```

---

# 6. How Express Combines Paths

Think of it like:

```text
app.use()
     +
router.post()
     =
final endpoint
```

Example:

```js
app.use("/api/v1/notes", noteRoutes);
```

and:

```js
router.get("/:id", noteController.getById);
```

becomes:

```http
GET /api/v1/notes/:id
```

This is one of the most important things to understand about Express route organization.

# 7. Our Complete CRUD Routes

Our Notes API could look like:

```text

GET    /api/v1/notes/:id
PATCH  /api/v1/notes/:id
DELETE /api/v1/notes/:id
PATCH  /api/v1/notes/:id/restore
```

Mapping:

|Method|Endpoint|Controller|
|---|---|---|
|POST|`/notes`|`create`|
|GET|`/notes`|`getMany`|
|GET|`/notes/:id`|`getById`|
|PATCH|`/notes/:id`|`update`|
|DELETE|`/notes/:id`|`remove`|
|PATCH|`/notes/:id/restore`|`restore`|

This is our CRUD API surface.

# 8. Why HTTP Methods Matter

We shouldn't make everything:

```http
POST /api/v1/notes/create
POST /api/v1/notes/get
POST /api/v1/notes/update
POST /api/v1/notes/delete
```

Instead, HTTP methods communicate the operation.

```text
POST
 ↓
Create

GET
 ↓
Read

PATCH
 ↓
Partially update

DELETE
 ↓
Delete
```

So:

```http
POST /notes
```

means:

> Create a Note.

And:

```http
GET /notes
```

means:

> Retrieve Notes.

# 15. Middleware Belongs in Routes

This is where Route Design becomes more interesting.

Our route shouldn't simply be:

```js
router.post("/", noteController.create);
```

For a protected Notes API, we might need:

```text
Authentication
Validation
Controller
```

So:

```js
router.post(
    "/",
    authMiddleware,
    validate(createNoteSchema),
    noteController.create
);
```

Now the route describes the complete request pipeline.

---

# 16. Readable Route Structure

A good route should make the pipeline easy to see:

```js
router.post(

    validate(createNoteSchema),
    noteController.create
);
```

Read it from top to bottom:

```text
POST /
 ↓
Authenticate
 ↓
Validate
 ↓
Create
```

That's excellent route design.

# 22. Authentication on Routes

A protected route might look like:

```js
router.get(
    "/",
    requireAuth,
    noteController.getMany
);
```

Why put authentication here?

Because not every route needs authentication.

For example:

```http
GET /healthz
```

should normally be public.

But:

```http
GET /api/v1/notes
```

requires a logged-in user.

So route-level middleware gives us control.

---

# 23. Route-Level vs Global Middleware

### Global middleware

```js
app.use(requestId);
```

Applies broadly.

### Route-level middleware

```js
router.get(
    "/",
    requireAuth,
    noteController.getMany
);
```

Applies only to this route.

This is why middleware composition is so useful.

---

# 24. Middleware Order Matters

Consider:

```js
router.post(
    "/",
    requireAuth,
    validate(createNoteSchema),
    noteController.create
);
```

The order is:

```text
1. requireAuth
2. validation
3. controller
```

If authentication fails:

```text
requireAuth
   ↓
STOP
```

Validation doesn't need to run.

If validation fails:

```text
requireAuth
   ↓
validation
   ↓
STOP
```

Controller doesn't execute.

Only if everything succeeds:

```text
requireAuth
   ↓
validation
   ↓
controller
```

---

# 25. Why Not Put Authentication Inside Controller?

You could technically write:

```js
const create = asyncHandler(async (req, res) => {
    if (!req.user) {
        return res.status(401)...
    }

    ...
});
```

But authentication is a middleware concern.

Routes make the protection obvious:

```js
router.post(
    "/",
    requireAuth,
    noteController.create
);
```

Anyone reading the route immediately sees:

> This endpoint is protected.

---

# 26. Route Design and Authorization

Authentication isn't the same as authorization.

Suppose:

```text
DELETE /api/v1/admin/users/:id
```

might require:

```js
requireAuth,
requireRole("admin"),
```

So:

```js
router.delete(
    "/:id",
    requireAuth,
    requireRole("admin"),
    userController.remove
);
```

The route describes the security boundary.

For Notes, however, ownership may be handled inside Service/Repository rather than a generic role middleware.

That matches the architecture you've already studied in Phase 15.

---

# 27. Don't Put Ownership in the URL

Avoid designing:

```http
GET /api/v1/users/:userId/notes/:noteId
```

for every user-owned operation unless your API genuinely needs that hierarchy.

For our current Notes API:

```http
GET /api/v1/notes/:id
```

is enough because:

```text
req.user.id
      +
noteId
```

can determine ownership.

Repository:

```js
Note.findOne({
    _id: noteId,
    userId
});
```

This follows the ownership approach you've already learned.

# 28. Route Naming

Good:

```text
/api/v1/notes
/api/v1/notes/:id
/api/v1/notes/:id/restore
```

Less ideal:

```text
/api/v1/createNote
/api/v1/getAllNotes
/api/v1/updateNote
/api/v1/deleteNote
```

The HTTP method already tells us the operation.

So:

```text
POST /notes
```

is cleaner than:

```text
POST /createNote
```

---

# 29. Plural Resource Names

Prefer:

```text
/notes
/users
/products
/orders
```

rather than:

```text
/note
/user
/product
/order
```

The collection is represented by the plural noun.

Then:

```text
/notes
```

means the collection.

```text
/notes/123
```

means one resource.

---

# 30. Route Parameter vs Query Parameter

This distinction is important.

### Path parameter

```http
GET /notes/123
```

`123` identifies a specific resource.

```js
req.params.id
```

### Query parameter

```http
GET /notes?page=2&limit=20
```

These control how the collection is retrieved.

```js
req.query.page
req.query.limit
```

So:

```text
/notes/123
    ↓
Which Note?

/notes?page=2
    ↓
How should I retrieve Notes?
```

---

# 31. Query Parameters for Filtering

Later, in Phase 18, we will have:

```http
GET /api/v1/notes?search=javascript
```

or:

```http
GET /api/v1/notes?sort=-createdAt
```

or:

```http
GET /api/v1/notes?page=2&limit=20
```

The Route itself doesn't need to change.

It remains:

```js
router.get(
    "/",
    requireAuth,
    validateQuery(noteListSchema),
    noteController.getMany
);
```

That's another benefit of good API design.

# 32. Avoid Route Explosion

Don't create:

```text
/notes/search
/notes/filter
/notes/sort
/notes/page
/notes/by-date
```

when query parameters can express these collection operations.

Instead:

```http
GET /notes?search=react
GET /notes?sort=-createdAt
GET /notes?page=2
```

We'll study this deeply in Phase 18.

# 33. Route Ordering Matters

Here's an important Express detail.

Suppose you have:

```js
router.get("/:id", noteController.getById);

router.patch("/:id/restore", noteController.restore);
```

These use different HTTP methods, so there's no conflict here.

But if you had:

```js
router.get("/:id", ...);
router.get("/stats", ...);
```

you should generally put the specific static route before the dynamic route:

```js
router.get("/stats", noteController.stats);
router.get("/:id", noteController.getById);
```

Why?

Because:

```text
/stats
```

can otherwise match:

```text
/:id
```

with:

```js
req.params.id === "stats"
```

So route order matters.

# 39. Route Design Rule

Here's a very useful rule:

> **Routes should describe the request pipeline, not implement the application.**

Good:

```js
router.post(
    "/",
    requireAuth,
    validate(createNoteSchema),
    noteController.create
);
```

Bad:

```js
router.post("/", async (req, res) => {
    // 100 lines of business logic
});
```

# 40. Route Design Checklist

When creating a new endpoint, ask:

```text
[ ] What HTTP method?
[ ] What resource?
[ ] What URL?
[ ] Does it require authentication?
[ ] Does it require authorization?
[ ] Does the body need validation?
[ ] Do params need validation?
[ ] Do query parameters need validation?
[ ] Which Controller handles it?
```

Example:

```text
Create Note

POST

URL:
/api/v1/notes

Authentication:
Yes

Validation:
createNoteSchema

Controller:
noteController.create
```

Then:

```js
router.post(
    "/",
    requireAuth,
    validate(createNoteSchema),
    noteController.create
);
```

Done.
