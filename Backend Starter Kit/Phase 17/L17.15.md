# 2. Why Test CRUD?

Imagine your code looks perfect:

```text
Route       ✅
Controller  ✅
Service     ✅
Repository  ✅
Model       ✅
```

But when you actually send:

```http
POST /api/v1/notes
```

you get:

```http
500 Internal Server Error
```

Something somewhere is broken.

Testing helps us answer:

> **Does the complete request flow actually work?**

---

For Phase 17, we're getting our first practical experience with that idea.

# 4. Two Types of Testing

For our CRUD feature, think about two levels.

## Unit testing

Test one piece:

```text
Service
Repository
Controller
Utility
```

For example:

```text
Does noteService.create()
return the expected result?
```

## Integration testing

Test multiple layers together:

```text
HTTP
 ↓
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
```

For example:

```text
POST /api/v1/notes
```

should actually create a Note.

---

# 5. Why Integration Testing Is Important Here

Suppose your Controller says:

```js
await noteService.create(...)
```

and the Service says:

```js
await noteRepository.create(...)
```

and Repository says:

```js
Note.create(...)
```

Every individual function could look correct.

But perhaps:

```js
noteService.create(...)
```

expects:

```js
{
    userId,
    title,
    content
}
```

while the Controller sends:

```js
{
    userId,
    name,
    body
}
```

Unit tests might miss this integration problem.

An integration test can catch it.

# 9. Create Test

A conceptual test:

```js
it("creates a note", async () => {
    const response = await request(app)
        .post("/api/v1/notes")
        .set("Authorization", `Bearer ${token}`)
        .send({
            title: "Learn Backend",
            content: "Study CRUD architecture"
        });

    expect(response.status).toBe(201);

    expect(response.body.success).toBe(true);

    expect(response.body.data.title)
        .toBe("Learn Backend");
});
```

Don't worry yet about making the entire test infrastructure perfect.

The important part is understanding what we're proving.

# 14. Important Read-Many Test

Suppose we have:

```text
User A
 ├── Note A1
 └── Note A2

User B
 └── Note B1
```

When User A requests:

```http
GET /api/v1/notes
```

the result should contain:

```text
Note A1
Note A2
```

but NOT:

```text
Note B1
```

This connects directly to the **ownership** lesson from Phase 17.

The roadmap specifically includes Ownership before Validation, Service Logic, Repository Queries, and CRUD Testing.

# 17. Test Ownership

This is one of the **most important CRUD tests**.

Suppose:

```text
User A owns Note 123
```

User B tries:

```http
GET /api/v1/notes/123
```

Expected:

```text
User B
   ↓
Note 123
   ↓
NOT accessible
```

Depending on your chosen security contract, this may be represented as `404 Not Found` to avoid revealing resource existence.

The important thing is:

```text
❌ User B must NOT receive User A's Note.
```

---

# 18. Why This Test Is So Important

Consider a bad Repository:

```js
Note.findById(noteId);
```

User B could potentially access:

```text
User A's Note
```

But a secure ownership query is conceptually:

```js
Note.findOne({
    _id: noteId,
    userId
});
```

So the test verifies that the architecture you learned in Phase 15 and Phase 17 actually protects the resource.

# 32. Test Response Contract

Remember Phase 16.

Every successful response should follow your established API response architecture.

For example:

```json
{
  "success": true,
  "message": "Note created successfully",
  "data": {}
}
```

Your test should verify the contract.

For example:

```js
expect(response.body).toHaveProperty("success");
expect(response.body).toHaveProperty("data");
```

The exact response shape should remain consistent with the response architecture you established earlier.

---

# 33. Test Error Contract

Likewise, errors should follow your standard format.

For example:

```json
{
  "success": false,
  "message": "Note not found"
}
```

Then:

```js
expect(response.body.success).toBe(false);
expect(response.body.message).toBeDefined();
```

This prevents one endpoint from returning:

```json
{
  "error": "..."
}
```

while another returns:

```json
{
  "message": "..."
}
```

---

# 34. Don't Test Implementation Details

This is a very important testing principle.

Avoid writing a CRUD integration test that cares about:

```text
"Did Controller call Service exactly once?"
```

unless you're specifically writing a unit test for that Controller.

For an integration test, care about:

```text
Request
 ↓
Correct behavior
 ↓
Correct response
 ↓
Correct database state
```

In other words:

> **Test what the system does, not how every internal function happens to be implemented.**

# 37. Test Isolation

Imagine:

```text

```

Then Test B starts.

If Note 1 is still there, Test B might accidentally pass because of Test A.

That's bad.

We want:

```text
Test A
  ↓
isolated

Test B
  ↓
isolated

Test C
  ↓
isolated
```

Each test should have predictable starting conditions.

# 42. Supertest

When testing Express HTTP endpoints, a tool like **Supertest** is very useful.

Conceptually:

```js

```

Then:


Don't think:

> **"I tested my Controller, so my CRUD feature works."**

> **"I sent a real request and verified the final behavior and database state."**

That's the mindset behind integration testing:

```text
REAL REQUEST
     ↓
REAL PIPELINE
     ↓
REAL DATABASE
     ↓
EXPECTED RESULT
```

And that is exactly what prepares us for the next step: **17.16 — Build Notes API**, where we'll assemble the complete CRUD resource instead of studying each layer separately.
