# 4. Step One — Define the Note

Before writing routes, we need to know what a Note is.

Conceptually:

```js
{
    _id,
    userId,
    title,
    content,
    isDeleted,
    createdAt,
    updatedAt
}
```

The important fields are:

```text
userId
title
content
isDeleted
```

---

# 5. Why `userId` Matters

Our Notes are user-owned resources.

So:

```text
User A
 ├── Note A
 └── Note B

User B
 ├── Note C
 └── Note D
```

When User A asks:

```http
GET /api/v1/notes
```

they should receive:

```text
Note A
Note B
```

not:

```text
Note C
Note D
```

Ownership is therefore part of the feature, not an optional extra.

---

# 6. Step Two — Repository

The Repository owns database operations.

Conceptually:

```js
class NoteRepository {

    async create(data) {}

    async findMany(filter) {}

    async findById(id, userId) {}

    async updateById(id, userId, data) {}

    async softDelete(id, userId) {}

    async restore(id, userId) {}
}
```

Notice something important.

The Repository doesn't know about:

```text
HTTP
req
res
status codes
```

It only cares about data access.

---

# 7. Create Repository

Conceptually:

```js
async create(data) {
    return Note.create(data);
}
```

The Service will provide:

```js
{
    userId,
    title,
    content
}
```

The Repository persists it.

---

# 8. Find Many Repository

We need active Notes belonging to the current user.

Conceptually:

```js
async findMany(userId) {
    return Note.find({
        userId,
        isDeleted: false
    });
}
```

This query contains two important rules:

```text
userId
+
isDeleted: false
```

So it protects both:

```text
ownership
```

and:

```text
soft-delete behavior
```

---

# 9. Find One Repository

Conceptually:

```js
async findById(id, userId) {
    return Note.findOne({
        _id: id,
        userId,
        isDeleted: false
    });
}
```

This is much safer than:

```js
Note.findById(id);
```

because the second version ignores ownership.

---

# 10. Update Repository

Conceptually:

```js
async updateById(id, userId, data) {
    return Note.findOneAndUpdate(
        {
            _id: id,
            userId,
            isDeleted: false
        },
        data,
        {
            new: true
        }
    );
}
```

Again:

```text
id
+
userId
+
isDeleted: false
```

are part of the resource boundary.

---

# 11. Soft Delete Repository

Instead of:

```js
Note.deleteOne(...)
```

we can do:

```js
async softDelete(id, userId) {
    return Note.findOneAndUpdate(
        {
            _id: id,
            userId,
            isDeleted: false
        },
        {
            isDeleted: true
        },
        {
            new: true
        }
    );
}
```

The document remains in the database.

Its state changes:

```text
false → true
```

---

# 12. Restore Repository

Restore reverses the state:

```js
async restore(id, userId) {
    return Note.findOneAndUpdate(
        {
            _id: id,
            userId,
            isDeleted: true
        },
        {
            isDeleted: false
        },
        {
            new: true
        }
    );
}
```

So:

```text
DELETE
   ↓
isDeleted = true

RESTORE
   ↓
isDeleted = false
```

---

# 13. Step Three — Service

The Service contains application/business logic.

Conceptually:

```js
class NoteService {

    async create(userId, data) {}

    async getMany(userId, query) {}

    async getById(userId, id) {}

    async update(userId, id, data) {}

    async remove(userId, id) {}

    async restore(userId, id) {}
}
```

---

# 14. Create Service

The Controller shouldn't directly create database records.

Instead:

```js
async create(userId, data) {
    return noteRepository.create({
        userId,
        title: data.title,
        content: data.content
    });
}
```

Notice:

```text
userId
```

comes from authentication.

Not from the request body.

---

# 15. Very Important Security Rule

Don't trust this:

```json
{
  "userId": "someone-else"
}
```

The client should not decide ownership.

Instead:

```text
Authenticated user
       ↓
req.user.id
       ↓
Service
       ↓
userId
```

So the server determines ownership.

---

# 16. Create Service Flow

```text
POST /notes
     │
     ▼
req.user.id
     │
     +
req.body
     │
     ▼
NoteService.create()
     │
     ▼
Repository.create()
```

This is a very important backend pattern.

---

# 17. Get Many Service

Conceptually:

```js
async getMany(userId) {
    return noteRepository.findMany(userId);

```

```js
async getMany(userId, query) {
    // pagination

    // filtering
}
```

That's coming in Phase 18.

For now, keep it simple.

# 18. Get One Service

```js
async getById(userId, id) {
    const note = await noteRepository.findById(
        id,
        userId
    );

    if (!note) {
        throw new AppError(
            "Note not found",
            404
        );
    }

    return note;
}
```

This is where the Service can translate:

```text
Repository returned null
```

into:

```text
Application error: 404
```

---

# 19. Update Service

```js
async update(userId, id, data) {
    const note = await noteRepository.updateById(
        id,
        userId,
        data
    );

    if (!note) {
        throw new AppError(
            "Note not found",
            404
        );
    }

    return note;
}
```

Again:

```text
Repository
    ↓
null
    ↓
Service
    ↓
404
```

---

# 20. Delete Service

```js
async remove(userId, id) {
    const note = await noteRepository.softDelete(
        id,
        userId
    );

    if (!note) {
        throw new AppError(
            "Note not found",
            404
        );
    }

    return note;
}
```

The Service doesn't execute:

```js
res.status(...)
```

That's Controller responsibility.

---

# 21. Restore Service

```js
async restore(userId, id) {
    const note = await noteRepository.restore(
        id,
        userId
    );

    if (!note) {
        throw new AppError(
            "Deleted note not found",
            404
        );
    }

    return note;
}
```

The Repository handles the database state.

The Service handles the application meaning.

---

# 22. Step Four — Controller

Now we translate HTTP into Service calls.

Conceptually:

```js
const create = asyncHandler(async (req, res) => {
    const note = await noteService.create(
        req.user.id,
        req.body
    );

    res.status(201).json({
        success: true,
        data: note
    });
});
```

Notice what the Controller does:

```text
req
 ↓
extract information
 ↓
call Service
 ↓
send response
```

That's it.

---

# 23. Get Many Controller

```js
const getMany = asyncHandler(async (req, res) => {
    const notes = await noteService.getMany(
        req.user.id,
        req.query
    );

    res.status(200).json({
        success: true,
        data: notes
    });
});
```

Later `req.query` becomes important for:

```text

sorting
filtering

```

# 24. Get One Controller

```js
const getById = asyncHandler(async (req, res) => {

        req.user.id,
        req.params.id

    res.status(200).json({
        success: true,
        data: note
    });

```

The Controller extracts:

```text
req.user.id
req.params.id
```

and passes them to the Service.

# 25. Update Controller

# 28. Step Five — Routes

Now connect everything.

```js
router.post(
    "/",
    requireAuth,
    validate(createNoteSchema),
    noteController.create
);

router.get(
    "/",
    requireAuth,
    noteController.getMany
);

router.get(
    "/:id",
    requireAuth,
    validate(noteIdSchema),
    noteController.getById
);

router.patch(
    "/:id",
    requireAuth,
    validate(updateNoteSchema),
    noteController.update
);

router.delete(
    "/:id",
    requireAuth,
    validate(noteIdSchema),
    noteController.remove
);

router.patch(
    "/:id/restore",
    requireAuth,
    validate(noteIdSchema),
    noteController.restore
);
```

Now our feature has a complete HTTP interface.

# 31. What Happens at Authentication?

Authentication middleware determines:

```js
req.user = {
    id: "USER_ID"
};
```

Now the Controller can access:

```js
req.user.id
```

This is how the Note gets associated with the correct user.

---

# 32. What Happens at Validation?

Validation checks:

```text
title
content
```

For example:

```text
title must be string
title must not be empty
content must be string
```

If validation fails:

```text
Request
   ↓
Validation
   ↓
❌
400
```

The Service never runs.


