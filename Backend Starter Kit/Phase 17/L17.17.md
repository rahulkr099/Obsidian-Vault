|---|---|---|
|POST|`/api/v1/notes`|Create Note|
|GET|`/api/v1/notes`|Get user's Notes|

```text

```

# Part 5 — Ownership

This is your most important exercise.

Imagine:

```text
User A
 └── Note 123

User B
 └── Note 456
```

User B must not be able to do:

```http
GET /api/v1/notes/123
```

and receive User A's Note.

Your Repository query should conceptually enforce:

```js
{
    _id: noteId,
    userId: currentUserId
}
```

not merely:

```js
{
    _id: noteId
}
```

Your earlier authorization material specifically emphasizes resource ownership and secure ownership queries.

---

# Part 6 — Soft Delete

Your DELETE operation should **not necessarily physically remove** the document.

Instead:

```text
isDeleted: false
```

becomes:

```text
isDeleted: true
```

So:

```text
DELETE
   ↓
isDeleted = true
```

Then:

```text
GET /notes
```

should normally exclude deleted Notes.

---

# Part 7 — Restore

Restore reverses it:

```text
isDeleted: true
        ↓
isDeleted: false
```

So your complete lifecycle becomes:

```text
CREATE
  ↓
ACTIVE
  ↓
DELETE
  ↓
DELETED
  ↓
RESTORE
  ↓
ACTIVE
```

---

# Part 8 — Controller Design

Your Controllers should be **thin**.

For example, mentally design:

```js
create(req, res)
```

as:

```text
req.user.id
      +
req.body
      ↓
noteService.create()
      ↓
response
```

Not:

```text
Controller
 ├── validate
 ├── query MongoDB
 ├── check ownership
 ├── perform business logic
 ├── update document
 └── send response
```

The architecture you're learning deliberately separates these responsibilities.

# Part 10 — Validation

Your Note creation request:

```json
{
  "title": "Learn Backend",
  "content": "Study CRUD architecture"
}
```

Think about what should happen with:

```json
{}
```

```json
{
  "title": ""
}
```

```json
{
  "title": 123
}
```

```json
{
  "title": "Hello",
  "content": 123
}
```

You should reject invalid data **before it reaches your business logic**.

---

# Part 11 — Authentication

The client should **not** send:

```json
{
  "userId": "..."
}
```

and expect the server to trust it.

Instead:

```text
JWT
 ↓
auth middleware
 ↓
req.user
 ↓
controller
 ↓
service
```

The authenticated identity becomes the source of ownership.

This is the same architectural principle used throughout your authentication and authorization phases.

---

# Part 12 — Response Design

Use the API response architecture you've already learned.

For success, something conceptually like:

```json
{
  "success": true,
  "message": "Note created successfully",
  "data": {}
}
```

For failure:

```json
{
  "success": false,
  "message": "Note not found"
}
```

Keep the structure consistent.
