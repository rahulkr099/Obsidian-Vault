# Lesson 17.2 — Designing a Resource

In **17.1**, we learned that CRUD architecture is not just about writing `create()`, `find()`, `update()`, and `delete()`.

Before writing any code, we need to answer:

> **What exactly are we building?**

That's what **resource design** means.

For this phase, we'll use a **Note** resource.

---

# 1. What Is a Resource?

In an API, a **resource** is a type of thing that your application manages.

Examples:

```text
User
Note
Todo
Post
Comment
Product
Order
Payment
```

For our example:

```text
Resource = Note
```

Our API will manage notes belonging to users.

---

# 2. Don't Start With the Database

A common beginner approach is:

> "Let me create a Mongoose schema first."

Instead, start with the real-world object.

Ask:

```text
What is a Note?
Who owns it?
What information does it contain?
What can users do with it?
What rules apply to it?
```

Only after answering those questions should we create the model.

---

# 3. Define Our Note

Let's start simple.

A Note might contain:

```text
Note
├── title
├── content
├── userId
└── timestamps
```

So conceptually:

```text
Note
│
├── title
├── content
├── userId
├── createdAt
└── updatedAt
```

This is our **resource definition**.

---

# 4. What Is `userId`?

This is extremely important.

Suppose two users exist:

```text
Rahul
User B
```

Rahul creates:

```text
Note A
```

User B creates:

```text
Note B
```

We need to know which user owns which note.

So:

```text
Note A
   ↓
userId = Rahul
```

and:

```text
Note B
   ↓
userId = User B
```

Conceptually:

```text
User
 │
 ├──── Note
 │
 ├──── Note
 │
 └──── Note
```

This is called **resource ownership**.

We'll study ownership much more deeply later in:

```text
17.15 Resource Ownership
17.16 Preventing IDOR
```

---

# 5. Why Ownership Must Be Designed Early

Imagine our API has:

```http
GET /api/v1/notes/abc
```

The frontend gives us:

```text
noteId = abc
```

If our database query is:

```js
Note.findById(noteId);
```

we might accidentally return another user's note.

That's dangerous.

Instead, eventually we want something conceptually like:

```js
Note.findOne({
    _id: noteId,
    userId: authenticatedUserId
});
```

So our resource design already needs to consider:

```text
Note
 ├── _id
 ├── userId
 ├── title
 └── content
```

Security isn't something we should bolt on at the very end.

---

# 6. Define the Fields

Now let's think about every field.

## `title`

The note needs a title.

Example:

```json
{
  "title": "Learn MongoDB"
}
```

Potential rules:

```text
Required
String
Minimum length
Maximum length
```

For example:

```text
min: 1
max: 200
```

The exact limits can be adjusted later.

---

## `content`

The actual note:

```json
{
  "content": "Learn MongoDB indexes."
}
```

Potential rules:

```text
Required
String
Maximum length
```

Again, the exact limit is a design decision.

---

## `userId`

This identifies the owner.

Important:

> **The client should not normally decide which user owns the resource.**

For example, don't trust:

```json
{
  "title": "My note",
  "content": "Hello",
  "userId": "some-user-id"
}
```

Instead:

```text
Authenticated request
        ↓
req.user.id
        ↓
Service
        ↓
userId
        ↓
Database
```

The server determines ownership.

This is a very important security principle.

---

# 7. `createdAt` and `updatedAt`

These are timestamps.

We want to know:

```text
When was this note created?
When was it last changed?
```

So:

```text
createdAt
updatedAt
```

are useful.

Mongoose can manage these automatically with:

```js
timestamps: true
```

Conceptually:

```text
Note
├── title
├── content
├── userId
├── createdAt
└── updatedAt
```

---

# 8. What About `_id`?

MongoDB automatically gives documents an identifier.

For example:

```text
_id = 64f...
```

So our complete resource becomes:

```text
Note
├── _id
├── userId
├── title
├── content
├── createdAt
└── updatedAt
```

---

# 9. Resource Design vs Validation

This distinction matters.

When we say:

```text
title
  required
  max 200
```

we're thinking about the **rules of the resource**.

But there are different places where those rules can be enforced.

For example:

```text
Request validation
        ↓
Database schema
```

The request might be validated using Joi:

```text
"Is this request acceptable?"
```

The Mongoose schema provides another protection:

```text
"Can this data be stored according to our model?"
```

We'll study validation properly in later lessons.

For now, just understand:

> **Resource design comes before implementation of validation.**

---

# 10. Define What Users Can Do

A resource isn't just its fields.

We should also define its operations.

For `Note`:

```text
Create
Read
Update
Delete
```

So:

```text
Note
│
├── Create
├── Read
├── Update
└── Delete
```

But we should ask more questions.

Can users:

```text
Create notes?        Yes
Read their notes?    Yes
Update their notes?  Yes
Delete their notes?  Yes
```

Can users:

```text
Read another user's note?   No
Update another user's note? No
Delete another user's note? No
```

Now we're already thinking about authorization.

---

# 11. Define Ownership Rules

Let's write our initial rules.

### Rule 1

A user can create a note.

```text
User → Create Note
```

### Rule 2

A user can read their own notes.

```text
User → Read own Note
```

### Rule 3

A user can update their own notes.

```text
User → Update own Note
```

### Rule 4

A user can delete their own notes.

```text
User → Delete own Note
```

### Rule 5

A user cannot access another user's note.

```text
User A
   X
User B's Note
```

This is a fundamental resource rule.

---

# 12. What About Admins?

We could later introduce:

```text
USER
ADMIN
```

Then perhaps:

```text
User
→ manage own notes

Admin
→ manage all notes
```

But don't add unnecessary complexity yet.

Our first design can simply be:

```text
Authenticated user
       ↓
Own notes only
```

Later, Phase 15's authorization concepts can extend this.

---

# 13. What Should the Client Send?

For creation:

```http
POST /api/v1/notes
```

The client sends:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today."
}
```

Notice:

```text
userId
```

is missing.

That's intentional.

The server gets it from authentication:

```text
JWT
 ↓
auth middleware
 ↓
req.user
 ↓
userId
```

This is much safer.

---

# 14. What Should the Client NOT Send?

Avoid trusting fields such as:

```json
{
  "userId": "another-user",
  "role": "admin",
  "createdAt": "some-date"
}
```

The client should not be allowed to arbitrarily control server-managed fields.

Think of the request as:

```text
Client-controlled data
        +
Server-controlled data
```

For example:

```text
Client:
title
content

Server:
userId
createdAt
updatedAt
_id
```

This distinction becomes very important when we study **mass assignment** and security testing later.

---

# 15. Resource Lifecycle

Think about a Note's lifecycle:

```text
                 CREATE
                   │
                   ▼
                ACTIVE
               /      \
          UPDATE       DELETE
            │            │
            ▼            ▼
          ACTIVE       DELETED
```

If we later support soft deletion:

```text
ACTIVE
  │
  ▼
DELETED
  │
  ▼
RESTORED
  │
  ▼
ACTIVE
```

We'll discuss this properly in **17.13 and 17.14**.

---

# 16. Resource Design Document

Before writing code, we can describe our Note like this:

```text
Resource: Note

Owner:
  Authenticated User

Fields:
  _id
  userId
  title
  content
  createdAt
  updatedAt

Client-controlled:
  title
  content

Server-controlled:
  _id
  userId
  createdAt
  updatedAt

Operations:
  Create
  Read
  Update
  Delete

Ownership:
  Users can access their own notes.

Authentication:
  Required for all Note operations.

Authorization:
  User can only modify/access owned notes.
```

This is already a useful design specification.

---

# 17. From Resource to Database Model

Now we can translate our design into a Mongoose schema.

Conceptually:

```js
const noteSchema = new mongoose.Schema(
    {
        userId: {
            type: mongoose.Schema.Types.ObjectId,
            ref: "User",
            required: true
        },

        title: {
            type: String,
            required: true,
            trim: true,
            maxlength: 200
        },

        content: {
            type: String,
            required: true
        }
    },
    {
        timestamps: true
    }
);
```

Don't worry about memorizing this yet.

We're going to build models properly when we implement the feature.

The important thing right now is understanding **why these fields exist**.

---

# 18. Why `ref: "User"`?

This:

```js
ref: "User"
```

tells Mongoose that the ObjectId refers to a `User` document.

Conceptually:

```text
Note
 │
 └── userId
       │
       ▼
     User
```

This creates a logical relationship:

```text
User 1 ──────── * Notes
```

One user can have many notes.

---

# 19. Think in Relationships

Our application currently has:

```text
User
  │
  │ 1
  │
  │
  │ *
  ▼
Note
```

This is a:

> **One-to-Many relationship**

Meaning:

```text
One User
    ↓
Many Notes
```

Example:

```text
Rahul
 │
 ├── Note 1
 ├── Note 2
 ├── Note 3
 └── Note 4
```

This relationship will become important when we build repository queries.

---

# 20. Resource Design Before Endpoint Design

Notice the order we're following.

We didn't immediately start writing:

```text
POST /notes
```

Instead:

```text
What is a Note?
       ↓
What fields does it have?
       ↓
Who owns it?
       ↓
What can users do?
       ↓
What rules apply?
       ↓
Now design endpoints
```

That's a much stronger development process.

---

# 21. A Real-World Example

Imagine you're asked:

> Build an e-commerce Product API.

Don't immediately create:

```text
product.model.js
product.controller.js
```

First ask:

```text
What is a Product?

Who owns it?

Who can create it?

Who can modify it?

Who can read it?

Which fields are client-controlled?

Which fields are server-controlled?

Can it be deleted?

Should deletion be permanent?

Does it have categories?

Does it have inventory?

Does it have a price?

Who can change the price?
```

These questions determine the architecture.

---

# 22. The Important Design Principle

Here's a principle I want you to remember:

> **Don't design the database first. Design the resource and its behavior first.**

Then:

```text
Resource
   ↓
Rules
   ↓
API
   ↓
Application logic
   ↓
Database model
```

Of course, in real projects this can be iterative. But starting from the resource's behavior helps prevent database-driven architecture.
