# Lesson 17.3 — CRUD Endpoint Design

In **17.2**, we designed our `Note` resource:

```text
Note
├── _id
├── userId
├── title
├── content
├── createdAt
└── updatedAt
```

Now we need to answer:

> **How should the outside world interact with this resource?**

That's where **endpoint design** comes in.

---

# 1. What Is an Endpoint?

An endpoint is a combination of:

```text
HTTP Method + URL
```

For example:

```http
GET /api/v1/notes
```

Here:

```text
Method = GET
URL    = /api/v1/notes
```

Together they represent an API operation.

---

# 2. CRUD → HTTP Methods

The basic mapping is:

|CRUD|HTTP Method|
|---|---|
|Create|POST|
|Read|GET|
|Update|PATCH / PUT|
|Delete|DELETE|

For our `Note` resource:

```text
Create → POST
Read   → GET
Update → PATCH
Delete → DELETE
```

So we can start designing:

```text
POST   /api/v1/notes
GET    /api/v1/notes
GET    /api/v1/notes/:noteId
PATCH  /api/v1/notes/:noteId
DELETE /api/v1/notes/:noteId
```

This is our initial CRUD API.

---

# 3. Why `/notes`?

Notice that we're using:

```http
/notes
```

instead of:

```http
/createNote
/getNotes
/updateNote
/deleteNote
```

This is an important REST design principle.

The **URL represents the resource**.

The **HTTP method represents the action**.

So:

```http
POST /notes
```

means:

> Create a Note.

While:

```http
GET /notes
```

means:

> Retrieve Notes.

The URL stays focused on the resource.

---

# 4. Avoid Action-Based URLs

A beginner might design:

```text
POST /create-note
GET /get-notes
POST /update-note
POST /delete-note
```

This works technically, but it isn't a clean REST-style design.

Prefer:

```text
POST   /notes
GET    /notes
PATCH  /notes/:noteId
DELETE /notes/:noteId
```

The HTTP method already tells us the operation.

---

# 5. Our Complete Endpoint Set

For now:

```text
┌────────┬─────────────────────────────┬─────────────────┐
│ Method │ Endpoint                    │ Purpose         │
├────────┼─────────────────────────────┼─────────────────┤
│ POST   │ /api/v1/notes               │ Create note     │
│ GET    │ /api/v1/notes               │ List notes      │
│ GET    │ /api/v1/notes/:noteId       │ Get one note    │
│ PATCH  │ /api/v1/notes/:noteId       │ Update note     │
│ DELETE │ /api/v1/notes/:noteId       │ Delete note     │
└────────┴─────────────────────────────┴─────────────────┘
```

That's enough for basic CRUD.

---

# 6. Why Do We Have Two GET Endpoints?

We have:

```http
GET /api/v1/notes
```

and:

```http
GET /api/v1/notes/:noteId
```

because they represent two different operations.

### Collection

```http
GET /notes
```

means:

> Give me a collection of notes.

### Individual resource

```http
GET /notes/123
```

means:

> Give me the specific note whose ID is `123`.

Think:

```text
/notes
   ↓
Collection

/notes/123
   ↓
Individual resource
```

---

# 7. Collection vs Individual Resource

This distinction is extremely important.

### Collection

```http
/api/v1/notes
```

Represents:

```text
All notes accessible to the current user
```

### Individual resource

```http
/api/v1/notes/:noteId
```

Represents:

```text
One specific note
```

Therefore:

```text
POST /notes
```

creates a new member of the collection.

And:

```text
GET /notes/123
```

retrieves one member.

---

# 8. `:noteId` Is a Route Parameter

Look at:

```http
GET /api/v1/notes/:noteId
```

The `:noteId` part is a **route parameter**.

For example:

```http
GET /api/v1/notes/65abc123
```

Express can access it through:

```js
req.params.noteId
```

Conceptually:

```text
URL
 │
 └── /notes/65abc123
             │
             ▼
       req.params.noteId
```

This is how the server knows which resource the client wants.

---

# 9. Route Parameters vs Query Parameters

This is an important distinction.

### Route parameter

```http
GET /notes/123
```

Here:

```text
123
```

identifies the specific resource.

Access it with:

```js
req.params.noteId
```

---

### Query parameter

```http
GET /notes?page=2&limit=20
```

Here:

```text
page=2
limit=20
```

are options for the request.

Access them with:

```js
req.query.page
req.query.limit
```

So:

```text
/notes/123
       ↑
    params

/notes?page=2
      ↑
    query
```

We'll study pagination and filtering later.

---

# 10. Create Endpoint

Our create endpoint:

```http
POST /api/v1/notes
```

The client sends:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today."
}
```

Notice again:

```text
userId
```

isn't supplied by the client.

The server gets it from authentication.

Flow:

```text
POST /notes
     ↓
Authentication
     ↓
req.user.id
     ↓
Service
     ↓
Create Note
```

---

# 11. Create Response

After successfully creating the note, we should normally return:

```http
201 Created
```

For example:

```json
{
  "success": true,
  "message": "Note created successfully",
  "data": {
    "id": "65abc123",
    "title": "Learn MongoDB",
    "content": "Study indexes today."
  }
}
```

The exact response envelope will be refined using the API response architecture we learned in Phase 16.

The important point here is the status code:

```text
POST successful creation
        ↓
201 Created
```

---

# 12. List Endpoint

Now:

```http
GET /api/v1/notes
```

The server should return notes that the current user is allowed to access.

For our current design:

```text
Authenticated User
        ↓
Own notes
```

Not:

```text
All notes in MongoDB
```

This distinction is critical.

Eventually the repository query should conceptually enforce:

```text
userId = authenticatedUserId
```

---

# 13. List Response

For example:

```json
{
  "success": true,
  "data": [
    {
      "id": "123",
      "title": "Learn MongoDB",
      "content": "Study indexes."
    },
    {
      "id": "456",
      "title": "Learn Redis",
      "content": "Study caching."
    }
  ]
}
```

Later, when we introduce pagination, we'll change this to include metadata.

For now, keep it simple.

---

# 14. Get One Note

Endpoint:

```http
GET /api/v1/notes/:noteId
```

Example:

```http
GET /api/v1/notes/123
```

Flow:

```text
Request
   ↓
Authenticate user
   ↓
Get noteId
   ↓
Find note belonging to user
   ↓
Return note
```

A very important detail:

Don't simply think:

```js
Note.findById(noteId)
```

Think:

```text
Find:
    noteId
    +
    authenticated user
```

We'll implement the secure version later.

---

# 15. What If the Note Doesn't Exist?

Suppose:

```http
GET /api/v1/notes/999
```

and the note doesn't exist.

We should return an appropriate error, commonly:

```http
404 Not Found
```

For example:

```json
{
  "success": false,
  "message": "Note not found"
}
```

Notice we're not returning:

```http
200 OK
```

with:

```json
{
  "data": null
}
```

for a resource that was requested by ID but doesn't exist.

The API should communicate the actual HTTP meaning.

---

# 16. Update Endpoint

Our update endpoint:

```http
PATCH /api/v1/notes/:noteId
```

Example:

```http
PATCH /api/v1/notes/123
```

Body:

```json
{
  "title": "Learn MongoDB Properly"
}
```

Notice something important:

The client doesn't need to send:

```json
{
  "title": "Learn MongoDB Properly",
  "content": "Study indexes today."
}
```

if only the title changed.

That's one reason `PATCH` is useful.

---

# 17. Why PATCH?

`PATCH` generally means:

> Partially modify an existing resource.

For example:

Current resource:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes."
}
```

Request:

```json
{
  "title": "Learn MongoDB Properly"
}
```

Result:

```json
{
  "title": "Learn MongoDB Properly",
  "content": "Study indexes."
}
```

Only the title changed.

---

# 18. PATCH vs PUT

You should know the conceptual difference.

### PATCH

Partial modification:

```text
PATCH /notes/123

{
  "title": "New title"
}
```

### PUT

Typically represents replacement of the resource:

```text
PUT /notes/123

{
  "title": "New title",
  "content": "New content"
}
```

For our Notes API, we'll use:

```text
PATCH
```

because partial updates are convenient and fit our use case.

We'll discuss the differences more deeply in **17.11**.

---

# 19. Delete Endpoint

Our delete endpoint:

```http
DELETE /api/v1/notes/:noteId
```

Example:

```http
DELETE /api/v1/notes/123
```

Flow:

```text
DELETE request
      ↓
Authentication
      ↓
Find owned note
      ↓
Delete
      ↓
Response
```

The client shouldn't be able to delete another user's note.

Again:

```text
noteId
+
authenticated user ID
```

must be considered.

---

# 20. Delete Response

A successful deletion can commonly return:

```http
204 No Content
```

with no response body.

Or the API may return:

```http
200 OK
```

with a response body.

For our learning architecture, we'll discuss both choices later.

The important thing is:

> Pick a consistent convention and use it throughout your API.

---

# 21. Authentication on Every Endpoint

Our current Note design says:

```text
Authentication required
```

Therefore:

```text
POST /notes       → Auth required
GET /notes        → Auth required
GET /notes/:id    → Auth required
PATCH /notes/:id  → Auth required
DELETE /notes/:id → Auth required
```

Conceptually:

```text
                    /notes
                       │
                 authMiddleware
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        POST          GET          ...
```

This prevents unauthenticated users from interacting with private notes.

---

# 22. Our Route File

Eventually our route file could look conceptually like:

```js
router.post(
    "/",
    authMiddleware,
    validate(createNoteSchema),
    noteController.create
);

router.get(
    "/",
    authMiddleware,
    noteController.getAll
);

router.get(
    "/:noteId",
    authMiddleware,
    validate(noteIdSchema),
    noteController.getOne
);

router.patch(
    "/:noteId",
    authMiddleware,
    validate(updateNoteSchema),
    noteController.update
);

router.delete(
    "/:noteId",
    authMiddleware,
    validate(noteIdSchema),
    noteController.remove
);
```

Don't worry about implementing this yet.

We're designing the contract first.

---

# 23. Endpoint → Responsibility

Let's map everything:

|Endpoint|Responsibility|
|---|---|
|`POST /notes`|Create|
|`GET /notes`|List|
|`GET /notes/:noteId`|Get one|
|`PATCH /notes/:noteId`|Update|
|`DELETE /notes/:noteId`|Delete|

And:

```text
Authentication
     ↓
All endpoints

Ownership
     ↓
All resource-specific operations
```

---

# 24. What About `/my-notes`?

You might wonder:

> Why not use `GET /api/v1/my-notes`?

Because the authenticated user's identity already comes from the authentication context.

Prefer:

```http
GET /api/v1/notes
```

and internally:

```text
authenticated user
        ↓
their accessible notes
```

rather than creating unnecessary URLs such as:

```http
GET /my-notes
GET /my-profile
GET /my-orders
```

That said, specialized endpoints can be useful when the resource semantics genuinely require them. Don't create them just because the word "my" feels explicit.

---

# 25. What About `/users/:userId/notes`?

This is another valid API design in some applications:

```http
GET /api/v1/users/:userId/notes
```

This expresses:

```text
User
  └── Notes
```

But for our current private Notes API, it creates an unnecessary opportunity for users to request another user's ID.

Our simpler design:

```http
GET /api/v1/notes
```

lets the server derive the owner from authentication.

So for our project:

```text
GET /notes
```

is the better starting point.

---

# 26. Think About Endpoint Semantics

Don't just memorize:

```text
POST = create
GET = read
```

Ask what the endpoint **means**.

For example:

```http
GET /api/v1/notes
```

means:

> Give me the collection of Notes that I am authorized to access.

While:

```http
GET /api/v1/notes/123
```

means:

> Give me this specific Note, if I am authorized to access it.

That is much closer to professional API thinking.

---

# 27. Endpoint Design Table

Let's create our first complete contract.

|Method|Endpoint|Auth|Purpose|Success|
|---|---|---|---|---|
|POST|`/api/v1/notes`|Yes|Create note|`201`|
|GET|`/api/v1/notes`|Yes|List own notes|`200`|
|GET|`/api/v1/notes/:noteId`|Yes|Get own note|`200`|
|PATCH|`/api/v1/notes/:noteId`|Yes|Update own note|`200`|
|DELETE|`/api/v1/notes/:noteId`|Yes|Delete own note|`204` or chosen convention|

This is our initial API contract.

---

# 28. Endpoint Design Is a Contract

This is one of the most important concepts from this lesson.

Suppose the frontend developer builds:

```http
PATCH /api/v1/notes/123
```

and expects:

```json
{
  "title": "Updated"
}
```

Your backend shouldn't randomly change it to:

```http
POST /api/v1/update-note/123
```

without a reason.

The API is a **contract between client and server**.

That's why endpoint design should happen deliberately.

---

# 29. Think About Errors Too

Endpoint design isn't only about success.

For:

```http
PATCH /api/v1/notes/123
```

possible outcomes include:

```text
200 → Updated successfully
400 → Invalid input
401 → Not authenticated
403 → Not authorized
404 → Note not found
429 → Too many requests
500 → Unexpected server error
```

We'll handle these systematically as we implement the CRUD flow.

# 32. Common Beginner Mistakes

### ❌ Mistake 1

```http
POST /api/v1/create-note
```

Prefer:

```http
POST /api/v1/notes
```

---

### ❌ Mistake 2

```http
POST /api/v1/delete-note/123
```

Prefer:

```http
DELETE /api/v1/notes/123
```

---

### ❌ Mistake 3

Using query parameters to identify the resource:

```http
GET /notes?id=123
```

when the intent is to retrieve a specific resource.

Prefer:

```http
GET /notes/123
```

---

### ❌ Mistake 4

Letting the client specify ownership:

```json
{
  "userId": "123"
}
```

Don't trust this for ownership.

---

### ❌ Mistake 5

Mixing actions into URLs unnecessarily:

```text
/notes/getAll
/notes/create
/notes/update
```

Use HTTP semantics instead.
