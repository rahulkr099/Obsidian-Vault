# Lesson 17.4 — Create Resource: Request Flow

In **17.3**, we designed:

```http
POST /api/v1/notes
```

Now we're going to understand exactly what happens when a user sends that request.

The goal of this lesson is **not to write the complete implementation yet**.

The goal is to build the mental model:

> **How does a Create request travel through our backend architecture?**

---

# 1. The Request

Suppose the frontend sends:

```http
POST /api/v1/notes
Content-Type: application/json
Authorization: Bearer <token>
```

with:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today."
}
```

Our backend needs to turn this request into a database document.

The complete flow is:

```text
Client
  ↓
POST /api/v1/notes
  ↓
Route
  ↓
Authentication
  ↓
Validation
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

Then the result travels back:

```text
MongoDB
  ↓
Repository
  ↓
Service
  ↓
Controller
  ↓
HTTP Response
  ↓
Client
```

This request/response journey is what we're studying.

---

# 2. Start at the Route

Our route might eventually look like:

```js
router.post(
    "/",
    authenticate,
    validate(createNoteSchema),
    noteController.create
);
```

When the client sends:

```http
POST /api/v1/notes
```

Express matches the route.

Conceptually:

```text
POST /api/v1/notes
        ↓
notes router
        ↓
POST /
```

The route's job is mainly **wiring**.

It says:

> "For this HTTP request, run these middlewares and then call the controller."

---

# 3. Authentication Runs First

The request contains:

```http
Authorization: Bearer <token>
```

Our authentication middleware checks the token.

Conceptually:

```text
Request
   ↓
JWT
   ↓
Verify token
   ↓
Extract user identity
```

If successful:

```text
req.user
```

might contain something like:

```js
{
    id: "user123"
}
```

Now the request has an authenticated identity.

---

# 4. Why Authentication Comes Before Creation

Remember our resource design.

A Note belongs to a user:

```text
User
  │
  ├── Note
  ├── Note
  └── Note
```

Therefore, when creating a Note, we need to know:

> **Who is creating it?**

We don't want the client to tell us:

```json
{
  "userId": "user123"
}
```

Instead:

```text
JWT
 ↓
Authentication middleware
 ↓
req.user.id
 ↓
Service
 ↓
userId
```

The server determines ownership.

---

# 5. What If Authentication Fails?

Suppose the request doesn't contain a token:

```http
POST /api/v1/notes
```

No authentication.

The middleware should stop the request:

```text
Request
   ↓
Authentication
   ↓
❌ 401 Unauthorized
```

The request should **not** reach:

```text
Controller
Service
Repository
Database
```

That's an important architectural benefit of middleware.

---

# 6. Validation Comes Next

Suppose authentication succeeds.

Now we validate the request body:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today."
}
```

We might have rules such as:

```text
title
 ├── required
 ├── string
 └── max 200 characters

content
 ├── required
 └── string
```

So:

```text
Request
   ↓
Authentication ✓
   ↓
Validation
```

---

# 7. Invalid Request

Suppose the client sends:

```json
{
  "title": "",
  "content": 123
}
```

Validation should reject it.

Flow:

```text
Request
   ↓
Authentication ✓
   ↓
Validation
   ↓
❌ 400 Bad Request
```

Again, the request doesn't reach the service or database.

This prevents bad data from moving deeper into the application.

---

# 8. Why Validate Before the Service?

Imagine the service receives:

```js
{
    title: 123,
    content: null
}
```

Now the service has to worry about basic input correctness.

That's not ideal.

Instead:

```text
HTTP layer
   ↓
Validate input
   ↓
Service receives valid-shaped data
```

This gives the service a cleaner responsibility:

> **Handle application/business logic.**

Not:

> "Is `title` even a string?"

---

# 9. Controller Receives the Request

After authentication and validation succeed:

```text
Request
   ↓
Authentication ✓
   ↓
Validation ✓
   ↓
Controller
```

The controller receives:

```text
req
res
```

and extracts the information it needs.

For example:

```js
const create = asyncHandler(async (req, res) => {
    const { title, content } = req.body;

    const note = await noteService.create({
        userId: req.user.id,
        title,
        content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

Don't worry about the exact code yet.

Focus on what the controller is doing.

---

# 10. What Does the Controller Actually Know?

The controller knows about:

```text
HTTP
Request
Response
Status codes
Request body
Authenticated request
```

For example:

```text
req.body
req.params
req.query
req.user
res.status()
res.json()
```

That's HTTP/application-interface knowledge.

But the controller should **not** need to know how MongoDB works.

---

# 11. Controller Calls the Service

The controller says:

```text
"I need a Note created."
```

So it calls:

```js
noteService.create(...)
```

Conceptually:

```text
Controller
    ↓
noteService.create()
```

This is an important boundary.

The controller doesn't say:

```js
Note.create(...)
```

Instead:

```text
Controller
    ↓
Service
```

---

# 12. What Does the Controller Pass?

Our client sent:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today."
}
```

Authentication gave us:

```text
req.user.id
```

So the controller can combine them:

```js
{
    userId: req.user.id,
    title: req.body.title,
    content: req.body.content
}
```

Conceptually:

```text
Client data
     +
Authenticated identity
     ↓
Service input
```

This is an important step.

---

# 13. Service Receives the Data

Now we're inside the service layer.

Conceptually:

```js
noteService.create({
    userId,
    title,
    content
});
```

The service asks:

> **What business rules need to happen before creating this Note?**

This is where our architecture starts becoming powerful.

---

# 14. Example Business Rule

Imagine our application has a rule:

> A user cannot have more than 100 active notes.

The service could perform:

```text
Create Note
    ↓
Check active note count
    ↓
Is count >= 100?
   /       \
 Yes       No
 ↓          ↓
Error     Continue
```

This is **business logic**.

It shouldn't live in:

```text
Route ❌
Controller ❌
Repository ❌
```

It belongs conceptually in:

```text
Service ✓
```

---

# 15. Service Shouldn't Know HTTP

Suppose the user has reached the limit.

The service should not need to think:

```js
res.status(400)
```

Why?

Because the service shouldn't be tied to Express's HTTP response object.

Instead, it can throw an application error:

```js
throw new AppError(
    "Maximum number of notes reached",
    400
);
```

Then our global error-handling system can turn that into the HTTP response.

This keeps the service independent from HTTP.

---

# 16. Service Calls Repository

After business rules pass:

```text
Service
   ↓
Repository
```

The service might call:

```js
noteRepository.create({
    userId,
    title,
    content
});
```

Now we're entering the data-access layer.

---

# 17. What Does the Repository Do?

The repository answers:

> **How do I save this data?**

For example:

```js
return Note.create(data);
```

The repository knows:

```text
Mongoose
MongoDB
Queries
Database operations
```

The service doesn't need to know those details.

---

# 18. Why Not Call `Note.create()` Directly From Service?

You might ask:

> "Why not simply write `Note.create()` in the service?"

For a small application, you certainly could.

But our architecture intentionally separates:

```text
Business logic
```

from:

```text
Data access
```

So:

```text
Service
 ↓
"Create this note"

Repository
 ↓
"I know how to create it in MongoDB"
```

This becomes particularly useful when the application grows.

---

# 19. Repository Calls the Model

The repository might execute:

```js
Note.create({
    userId,
    title,
    content
});
```

The model defines the structure:

```text
Note
├── userId
├── title
├── content
├── createdAt
└── updatedAt
```

Mongoose then sends the database operation to MongoDB.

---

# 20. MongoDB Creates the Document

The final document might look conceptually like:

```json
{
  "_id": "65abc123",
  "userId": "user123",
  "title": "Learn MongoDB",
  "content": "Study indexes today.",
  "createdAt": "2026-08-26T...",
  "updatedAt": "2026-08-26T..."
}
```

Notice something important.

The client didn't provide:

```text
_id
userId
createdAt
updatedAt
```

The server/database layer handles them.

---

# 21. The Result Travels Back

MongoDB returns the created document.

Then:

```text
MongoDB
   ↓
Model
   ↓
Repository
   ↓
Service
   ↓
Controller
```

The repository returns the created Note to the service.

The service returns it to the controller.

The controller prepares the HTTP response.

---

# 22. Controller Sends the Response

The controller might eventually send:

```http
201 Created
```

with:

```json
{
  "success": true,
  "message": "Note created successfully",
  "data": {
    "id": "65abc123",
    "title": "Learn MongoDB",
    "content": "Study indexes today."
  }
}
```

The frontend receives it.

Complete.

---

# 23. Complete Create Flow

Now look at everything together:

```text
                    CLIENT
                       │
                       │ POST /api/v1/notes
                       ▼
                     ROUTE
                       │
                       ▼
                AUTHENTICATION
                       │
                       ▼
                  VALIDATION
                       │
                       ▼
                  CONTROLLER
                       │
                       │ userId
                       │ title
                       │ content
                       ▼
                    SERVICE
                       │
                       │ business rules
                       ▼
                  REPOSITORY
                       │
                       │ database operation
                       ▼
                     MODEL
                       │
                       ▼
                    MongoDB
                       │
                       ▼
                  CREATED NOTE
                       │
                       ▼
                  REPOSITORY
                       │
                       ▼
                    SERVICE
                       │
                       ▼
                  CONTROLLER
                       │
                       ▼
                  201 Created
                       │
                       ▼
                     CLIENT
```

This diagram is worth remembering.

---

# 24. Where Does Each Piece Belong?

Let's make this extremely clear.

### Route

```text
POST /notes
```

### Authentication

```text
Who is the user?
```

### Validation

```text
Is the input valid?
```

### Controller

```text
Handle HTTP request/response.
```

### Service

```text
Apply business rules.
```

### Repository

```text
Perform database operations.
```

### Model

```text
Define database document structure.
```

### MongoDB

```text
Persist the data.
```

---

# 25. What Happens When Something Fails?

This is equally important.

Imagine MongoDB fails.

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
   ↓
❌ Database error
```

The error travels back:

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
Error Handler
   ↓
HTTP Response
```

The controller doesn't need to manually handle every possible database failure.

Our global error handling architecture can handle unexpected errors consistently.

---

# 26. Another Failure: Business Rule

Suppose:

```text
User has 100 notes
```

and our application says:

```text
Maximum = 100
```

The service rejects creation:

```text
Controller
   ↓
Service
   ↓
Business Rule
   ↓
❌ AppError
   ↓
Error Handler
   ↓
400 Bad Request
```

MongoDB is never called.

That's exactly what we want.

---

# 27. Another Failure: Validation

Suppose:

```json
{
  "title": "",
  "content": 123
}
```

Then:

```text
Route
   ↓
Authentication ✓
   ↓
Validation
   ↓
❌ Invalid
```

The request stops there.

No:

```text
Controller
Service
Repository
MongoDB
```

This is efficient and safer.

---

# 28. Another Failure: Authentication

No token:

```text
Request
   ↓
Authentication
   ↓
❌ 401
```

The request never reaches the business logic.

This illustrates a key architectural idea:

> **Fail as early as possible when the request cannot be processed.**

---

# 29. The Three Main Layers

You can simplify the architecture mentally into three major areas:

```text
HTTP Layer
    ↓
Controller

Business Layer
    ↓
Service

Data Layer
    ↓
Repository
```

Around those we have:

```text
Route
Middleware
Validation
Model
Database
```

So:

```text
HTTP
 ↓
Business
 ↓
Data
```

is the core idea.

---

# 30. Why This Architecture Scales

Imagine tomorrow we replace MongoDB with PostgreSQL.

If database access is isolated:

```text
Service
   ↓
Repository
```

we can potentially replace the repository implementation without rewriting the entire controller/business layer.

For example:

```text
MongoRepository
```

could become:

```text
PostgresRepository
```

The service's responsibility remains:

```text
Create Note
```

rather than:

```text
Create Note using MongoDB specifically
```

This is one reason abstraction boundaries matter.

---

# 31. But Don't Over-Abstract

There's an important warning.

Don't create:

```text
NoteRepositoryFactory
DatabaseProviderFactory
CrudRepositoryAdapter
RepositoryStrategyFactory
```

just because architecture diagrams look professional.

😂

For our project, keep it practical:

```text
Controller
Service
Repository
Model
```

Add abstraction only when it solves a real problem.

Good architecture is:

> **Simple boundaries with clear responsibilities.**

Not:

> **Maximum number of files.**

---

# 32. Create Flow in One Sentence

If someone asks you in an interview:

> "Explain the flow of creating a resource in your backend."

A strong answer would be:

> "The request enters through the route, authentication and validation middleware process it, the controller handles the HTTP layer, the service applies business rules, the repository performs database access through the model, and the result is returned through the service and controller as an HTTP response."

That's a professional answer.

---

Don't think:
