# Lesson 17.5 — Create Resource: Controller

In **17.4**, we traced the complete create flow:

```text
Request
   ↓
Route
   ↓
Authentication
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Model
   ↓
MongoDB
```

Now we're focusing on **one layer only**:

> **What exactly should the Controller do when creating a Note?**

This is an important lesson because controllers are one of the easiest places to accidentally put too much logic.

---

# 1. What Is a Controller?

A controller is the layer that handles the **HTTP interaction**.

It receives:

```text
Request
```

and produces:

```text
Response
```

So a simple mental model is:

```text
HTTP Request
      ↓
  Controller
      ↓
HTTP Response
```

For our Note creation:

```http
POST /api/v1/notes
```

the controller's job is to coordinate the request.

---

# 2. What Should the Controller Know?

The controller can know about things like:

```text
req.body
req.params
req.query
req.user
res.status()
res.json()
```

These are HTTP/application-interface concerns.

For example:

```js
const create = asyncHandler(async (req, res) => {
    const { title, content } = req.body;

    const userId = req.user.id;

    // ...
});
```

That's reasonable controller code.

---

# 3. What Should the Controller NOT Know?

The controller shouldn't know the details of:

```text
MongoDB queries
Mongoose implementation
Database indexes
Business rules
Password hashing
Transaction implementation
```

For example, avoid:

```js
const create = asyncHandler(async (req, res) => {
    const existingNotes = await Note.countDocuments({
        userId: req.user.id
    });

    if (existingNotes >= 100) {
        throw new AppError("Note limit reached", 400);
    }

    const note = await Note.create({
        userId: req.user.id,
        title: req.body.title,
        content: req.body.content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

This controller is now doing:

```text
HTTP
+
Business logic
+
Database access
```

That's exactly what we're trying to avoid.

---

# 4. The Controller's Main Job

Think of the controller as a **translator**.

The client speaks:

```text
HTTP
```

The service speaks:

```text
Application operations
```

The controller translates between them.

```text
Client
  │
  │ HTTP
  ▼
Controller
  │
  │ Application operation
  ▼
Service
```

For example:

```text
HTTP:
POST /api/v1/notes

        ↓

Application:
createNote({
    userId,
    title,
    content
})
```

Then the result goes back:

```text
Service result
      ↓
Controller
      ↓
HTTP response
```

---

# 5. Our Controller

Let's start with a simple version:

```js
const create = asyncHandler(async (req, res) => {
    const { title, content } = req.body;

    const note = await noteService.create({
        userId: req.user.id,
        title,
        content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

This is a good starting point.

Let's understand every part.

---

# 6. `asyncHandler`

You may already have an async error-handling wrapper in your starter architecture.

Conceptually:

```js
asyncHandler(async (req, res) => {
    // controller logic
});
```

Why?

Because controllers frequently perform asynchronous operations:

```text
Service
 ↓
Repository
 ↓
Database
```

If something throws, we want the error to reach the application's centralized error-handling system.

So instead of repeating:

```js
try {
    // ...
} catch (error) {
    next(error);
}
```

everywhere, an `asyncHandler` can standardize this.

The important idea:

```text
Controller
   ↓
async operation
   ↓
Error
   ↓
Central error handler
```

---

# 7. Extracting the Request Body

Our request is:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today."
}
```

So:

```js
const { title, content } = req.body;
```

gives us:

```text
title
content
```

The controller can extract the data it needs.

But remember:

> **Validation should already have happened before this point.**

So the controller shouldn't become a second validation system.

---

# 8. Getting the Authenticated User

Authentication middleware might have populated:

```js
req.user
```

For example:

```js
req.user = {
    id: "user123"
};
```

The controller can then use:

```js
req.user.id
```

to identify the owner.

So:

```js
const userId = req.user.id;
```

Conceptually:

```text
JWT
 ↓
Authentication middleware
 ↓
req.user.id
 ↓
Controller
 ↓
Service
```

---

# 9. Combining Client Data and Server Identity

The client sends:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes."
}
```

The server knows:

```text
userId = authenticated user
```

The controller creates the service input:

```js
{
    userId,
    title,
    content
}
```

So the controller is performing a useful transformation:

```text
HTTP Request
     ↓
Service Input
```

---

# 10. Controller Calls Service

Now:

```js
const note = await noteService.create({
    userId: req.user.id,
    title,
    content
});
```

This line is extremely important.

The controller says:

> "Service, please create this Note."

It doesn't say:

> "MongoDB, please insert this document."

That's the separation we're after.

---

# 11. Why Is This Better?

Imagine tomorrow the Note creation process becomes more complicated.

Maybe we add:

```text
Check user's subscription
Check note limit
Create note
Create audit log
Send notification
Update usage statistics
```

The controller can still remain:

```js
const note = await noteService.create({
    userId,
    title,
    content
});
```

The complexity lives in the service.

That's a huge benefit.

---

# 12. The Controller Should Be Boring

This is actually a good thing.

A professional controller often looks almost boring:

```js
const create = asyncHandler(async (req, res) => {
    const note = await noteService.create({
        userId: req.user.id,
        title: req.body.title,
        content: req.body.content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

That's okay.

You don't want your controller to contain 200 lines of business logic.

A useful principle:

> **Controllers should coordinate, not decide.**

---

# 13. What Does "Coordinate" Mean?

The controller coordinates:

```text
Request
  ↓
Extract information
  ↓
Call service
  ↓
Format response
```

It doesn't decide complex application rules.

For example:

```text
"Can the user create this note?"
```

is a business decision.

That belongs in the service/authorization layer depending on the exact rule.

The controller should not contain:

```js
if (user.subscription === "free" && noteCount >= 100) {
    // ...
}
```

---

# 14. Response Status Code

After successful creation:

```js
res.status(201)
```

Why `201`?

Because:

```text
201 Created
```

communicates:

> A new resource was successfully created.

This is more meaningful than simply:

```text
200 OK
```

for a creation operation.

---

# 15. Response Body

We might return:

```js
res.status(201).json({
    success: true,
    data: note
});
```

The response could look like:

```json
{
  "success": true,
  "data": {
    "id": "65abc123",
    "title": "Learn MongoDB",
    "content": "Study indexes today."
  }
}
```

Depending on the response architecture established in your project, we may later use a standard response helper rather than writing this object manually.

The important idea is:

> **The controller converts the service result into the API's response format.**

---

# 16. Controller vs Service

This is probably the most important comparison in today's lesson.

|Controller|Service|
|---|---|
|HTTP-focused|Business-focused|
|Reads `req`|Receives application data|
|Uses `res`|Shouldn't depend on `res`|
|Handles status codes|Handles business rules|
|Formats response|Performs application operation|
|Calls service|Calls repository|

Think:

```text
Controller
= HTTP coordinator

Service
= Business operation
```

---

# 17. Controller vs Repository

Another important distinction:

|Controller|Repository|
|---|---|
|HTTP|Database|
|`req`|Queries|
|`res`|Mongoose|
|status codes|persistence|
|response format|data access|

So this is wrong:

```js
// Controller
await Note.create(...)
```

because the controller is now directly coupled to the database.

Instead:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
```

---

# 18. What About Validation?

Suppose we have:

```json
{
  "title": "",
  "content": 123
}
```

The controller shouldn't normally do:

```js
if (!title) {
    return res.status(400).json(...);
}

if (typeof content !== "string") {
    return res.status(400).json(...);
}
```

Instead:

```text
Request
   ↓
Validation middleware
   ↓
Controller
```

So the controller can assume:

> "The request has passed the input validation boundary."

That keeps it cleaner.

---

# 19. What About Authentication?

Similarly, don't make the controller manually verify the JWT:

```js
jwt.verify(...)
```

Authentication middleware should do that.

Then the controller gets:

```js
req.user
```

So:

```text
Authentication
       ↓
req.user
       ↓
Controller
```

Again, one responsibility per layer.

---

# 20. What About Authorization?

This one is slightly more nuanced.

Authentication answers:

> **Who are you?**

Authorization answers:

> **Are you allowed to perform this operation?**

For our Note:

```text
Authentication:
User = Rahul

Authorization:
Does Rahul own this Note?
```

Some authorization checks can happen in dedicated middleware.

Other resource-specific business authorization may happen inside the service.

The key point is:

> **Don't automatically dump every authorization rule into the controller.**

We'll study this carefully in later lessons.

---

# 21. A Better Controller Design

Let's make our controller slightly cleaner.

```js
const create = asyncHandler(async (req, res) => {
    const noteData = {
        userId: req.user.id,
        title: req.body.title,
        content: req.body.content
    };

    const note = await noteService.create(noteData);

    res.status(201).json({
        success: true,
        data: note
    });
});
```

This makes the boundary very obvious:

```text
HTTP request
     ↓
noteData
     ↓
Service
     ↓
HTTP response
```

---

# 22. Don't Pass the Entire `req` to the Service

Avoid:

```js
await noteService.create(req);
```

This creates a bad dependency.

Now your service knows about:

```text
Express request
headers
body
params
query
user
```

That's unnecessary.

Prefer:

```js
await noteService.create({
    userId: req.user.id,
    title: req.body.title,
    content: req.body.content
});
```

Now the service receives exactly what it needs.

This is a very important architectural habit.

---

# 23. Don't Pass `res` to the Service

Similarly, don't do:

```js
await noteService.create(req.body, res);
```

Then the service becomes coupled to HTTP.

Bad:

```text
Service
 ↓
Express Response
```

Better:

```text
Service
 ↓
Return result
 ↓
Controller
 ↓
HTTP response
```

---

# 24. Service Return Value

Suppose:

```js
const note = await noteService.create(noteData);
```

The service returns:

```js
{
    id: "123",
    title: "Learn MongoDB",
    content: "Study indexes."
}
```

The controller then decides:

```text
201
```

and:

```json
{
  "success": true,
  "data": {}
}
```

This separation is useful because the service doesn't need to know whether the client is using:

```text
REST API
GraphQL
CLI
Background job
```

The service just performs the application operation.

---

# 25. A Very Useful Thought Experiment

Suppose tomorrow we call the same service from a background job:

```text
Daily import job
     ↓
noteService.create()
```

There is no:

```text
req
res
```

If your service requires:

```js
noteService.create(req, res)
```

it won't work.

But if your service accepts:

```js
noteService.create({
    userId,
    title,
    content
});
```

it can potentially be reused.

That's the power of keeping the service independent from HTTP.

---

# 26. Controller as an Adapter

You can think of the controller as an adapter:

```text
              HTTP WORLD
                  │
                  ▼
             Controller
                  │
                  ▼
          APPLICATION WORLD
                  │
                  ▼
              Service
                  │
                  ▼
              Repository
                  │
                  ▼
             DATABASE WORLD
```

The controller adapts HTTP concepts into application concepts.

# 28. What If the Service Throws an Error?

Suppose:

```js
await noteService.create(noteData);
```

throws:

```text
Note limit exceeded
```

The controller doesn't need:

```js
try {
    ...
} catch (error) {
    ...
}
```

if your `asyncHandler` and global error middleware already handle rejected promises.

The conceptual flow is:

```text
Service
   ↓
throws AppError
   ↓
asyncHandler
   ↓
Global Error Handler
   ↓
HTTP response
```

This keeps controllers clean.

---

# 29. What Should NOT Be Inside Our Create Controller?

Let's create a checklist.

### ❌ Don't put MongoDB queries

```js
Note.find(...)
Note.create(...)
```

### ❌ Don't put business rules

```js
if (noteCount >= 100) ...
```

### ❌ Don't verify JWT manually

```js
jwt.verify(...)
```

### ❌ Don't perform password hashing

Not relevant to Note creation.

### ❌ Don't contain complex authorization logic unnecessarily

Keep resource/business authorization in the appropriate layer.

### ❌ Don't pass `req` to service

```js
service.create(req)
```

### ❌ Don't pass `res` to service

```js
service.create(data, res)
```

---

# 30. What SHOULD Be Inside?

A good create controller generally does something like:

```text
1. Extract request data
2. Get authenticated identity
3. Build service input
4. Call service
5. Return HTTP response
```

That's it.

In pseudocode:

```text
CREATE CONTROLLER

input:
    request

extract:
    title
    content
    authenticated user

call:
    noteService.create(...)

output:
    HTTP 201 response
```

---

# 31. Controller Complexity Test

Here's a useful rule.

If your controller starts becoming:

```text
20 lines
30 lines
50 lines
100 lines
```

stop and ask:

> **"Am I putting business or data-access logic here?"**

A controller can legitimately be longer in complex endpoints, but unexpected growth is often a sign that responsibilities are leaking into it.

---

# 32. One More Important Detail: DTO Thinking

You may hear the term:

> **DTO — Data Transfer Object**

You don't need a huge DTO system right now.

But we're already doing a simple version of DTO thinking:

```js
const noteData = {
    userId: req.user.id,
    title: req.body.title,
    content: req.body.content
};
```

This object is the data we intentionally transfer from:

```text
Controller → Service
```

Instead of passing the entire HTTP request.

This is a good habit.

---

# 33. Before and After

### ❌ Bad

```js
router.post("/notes", async (req, res) => {
    const user = jwt.verify(req.headers.authorization);

    const count = await Note.countDocuments({
        userId: user.id
    });

    if (count >= 100) {
        return res.status(400).json({
            message: "Limit reached"
        });
    }

    const note = await Note.create({
        userId: user.id,
        title: req.body.title,
        content: req.body.content
    });

    res.status(201).json(note);
});
```

Everything is mixed together.

---

### ✅ Better

```js
router.post(
    "/",
    authenticate,
    validate(createNoteSchema),
    noteController.create
);
```

Controller:

```js
const create = asyncHandler(async (req, res) => {
    const note = await noteService.create({
        userId: req.user.id,
        title: req.body.title,
        content: req.body.content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

Then:

```text
Service
   ↓
Business rules

Repository
   ↓
Database access
```

Much cleaner.

---

# 34. The Golden Rule for Controllers

Remember this sentence:

> **A controller should translate HTTP input into an application operation and translate the result back into an HTTP response.**

That's the essence of controller design.

```text
HTTP → Controller → Application
Application → Controller → HTTP
```
