# Lesson 17.6 — Create Resource: Service

In **17.5**, we learned that the controller should stay thin:

```text
HTTP Request
     ↓
Controller
     ↓
Service
```

Now we move into the **Service layer**.

The key idea of this lesson is:

> **The Service layer represents what the application is trying to accomplish.**

For our example:

```text
noteService.create()
```

means:

> "Create a Note according to the application's rules."

---

# 1. Where the Service Fits

Our complete architecture is:

```text
Client
  ↓
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

The controller handles:

```text
HTTP
```

The service handles:

```text
Application/business logic
```

The repository handles:

```text
Data access
```

So:

```text
Controller
   ↓
"What did the HTTP client ask?"

Service
   ↓
"What should the application do?"

Repository
   ↓
"How do I access the data?"
```

---

# 2. Our Create Operation

We have:

```http
POST /api/v1/notes
```

with:

```json
{
  "title": "Learn MongoDB",
  "content": "Study indexes today."
}
```

Authentication gives us:

```text
userId = authenticated user
```

The controller passes:

```js
{
    userId,
    title,
    content
}
```

to:

```js
noteService.create()
```

Now the service takes over.

---

# 3. What Should the Service Do?

A basic Note creation service might do:

```text
1. Receive validated application data
2. Apply business rules
3. Prepare data if necessary
4. Ask repository to create the Note
5. Return the created Note
```

Conceptually:

```text
noteService.create()
        ↓
Business rules
        ↓
Repository
        ↓
Created Note
```

---

# 4. Start With the Simplest Service

A simple implementation could be:

```js
const create = async ({ userId, title, content }) => {
    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

That's it.

Don't be surprised that it looks small.

A service doesn't need to contain artificial complexity.

---

# 5. Why Does This Service Exist?

You might ask:

> "If the service only calls the repository, why not call the repository directly from the controller?"

For our current simple example, technically you could.

But the service creates a **business boundary**.

Today:

```text
Controller
   ↓
Repository
```

might seem fine.

Tomorrow:

```text
Controller
   ↓
Service
   ├── Check limits
   ├── Check subscription
   ├── Normalize data
   ├── Create note
   ├── Create audit record
   └── Send event
```

Now the service has a clear place for that logic.

---

# 6. Service Is Not "Extra Code"

A common beginner thought is:

> "Service is just another file."

That's not the right way to think about it.

Think of it as an **application operation**.

For example:

```text
noteService.create()
noteService.update()
noteService.delete()
```

These describe things the application can do.

This is much more meaningful than thinking only in terms of database queries.

---

# 7. Service Input Should Be Explicit

Our service should receive:

```js
{
    userId,
    title,
    content
}
```

rather than:

```js
create(req)
```

or:

```js
create(req.body)
```

Why?

Because the service should receive **application data**, not HTTP objects.

Good:

```js
noteService.create({
    userId,
    title,
    content
});
```

Bad:

```js
noteService.create(req);
```

---

# 8. The Service Should Not Know About Express

Our service should not contain:

```js
req.body
req.params
req.query
req.user
res.status()
res.json()
```

Those belong to the HTTP layer.

The service should be usable without Express.

For example:

```js
await noteService.create({
    userId: "123",
    title: "Learn Redis",
    content: "Study caching."
});
```

That could theoretically be called by:

```text
REST API
Background Job
CLI
GraphQL Resolver
Message Consumer
```

That's a strong architectural boundary.

---

# 9. The Service Should Not Know About MongoDB

Similarly, avoid:

```js
const create = async (data) => {
    return Note.create(data);
};
```

inside the service if we're deliberately using the Repository Pattern.

Instead:

```js
const create = async (data) => {
    return noteRepository.create(data);
};
```

So:

```text
Service
  ↓
Repository
  ↓
Mongoose
  ↓
MongoDB
```

The service doesn't need to know how persistence works.

---

# 10. Business Rules Belong Here

Now we reach the important part.

Suppose our application says:

> A user can have at most 100 active Notes.

The service can enforce this rule.

Conceptually:

```js
const create = async ({ userId, title, content }) => {
    const count = await noteRepository.countByUser(userId);

    if (count >= 100) {
        throw new AppError(
            "Maximum number of notes reached",
            400
        );
    }

    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

Now the service is doing something meaningful.

---

# 11. Service Decision-Making

Notice the difference.

Repository:

```text
"How many Notes does this user have?"
```

Service:

```text
"Is the user allowed to create another Note?"
```

That's a very useful distinction.

```text
Repository
     ↓
Data fact

Service
     ↓
Business decision
```

For example:

```text
Repository:
User has 100 notes.

Service:
100 is the maximum → reject creation.
```

---

# 12. Don't Put This Rule in the Repository

Avoid:

```js
noteRepository.create = async (data) => {
    const count = await Note.countDocuments({
        userId: data.userId
    });

    if (count >= 100) {
        throw new Error("Limit reached");
    }

    return Note.create(data);
};
```

Why?

Because now the repository is making a **business decision**.

The repository should primarily answer:

> "How do I interact with the database?"

The service should answer:

> "What should the application allow?"

---

# 13. Business Rule vs Database Constraint

There's another important distinction.

Suppose we have:

```text
title must not be empty
```

This is primarily an **input validation** rule.

Suppose:

```text
user cannot create more than 100 active notes
```

This is an **application/business rule**.

Suppose:

```text
userId must reference an existing user
```

This may involve **data integrity/database-level concerns**.

These are different types of rules.

Don't throw every rule into the service.

---

# 14. Validation Has Already Happened

Remember our request flow:

```text
Route
 ↓
Authentication
 ↓
Validation
 ↓
Controller
 ↓
Service
```

So by the time the service receives:

```js
{
    userId,
    title,
    content
}
```

the basic HTTP input should already have been validated.

For example:

```text
title exists
title is a string
title length is acceptable
content is a string
```

The service shouldn't duplicate all of that.

---

# 15. But Services Can Still Defend Important Invariants

There's a subtle point here.

A service shouldn't blindly trust every caller forever.

Suppose the service is later called from:

```text
REST API
Background job
CLI
```

The service may need to protect important application invariants.

For example:

```text
Cannot create a Note for a suspended user.
```

That's not merely HTTP validation.

That's a business rule.

So:

```text
Validation
    ↓
Input shape

Service
    ↓
Business correctness
```

---

# 16. Example: Suspended User

Suppose our application has:

```text
User.status
```

with:

```text
active
suspended
```

Business rule:

> Suspended users cannot create Notes.

Service:

```js
const user = await userRepository.findById(userId);

if (user.status === "suspended") {
    throw new AppError(
        "Suspended users cannot create notes",
        403
    );
}
```

Then:

```text
Controller
   ↓
Service
   ↓
Check business rule
   ↓
❌ Reject
```

Again, the controller doesn't need to know this rule.

---

# 17. Service as a Use Case

This is a powerful way to think about services.

Instead of:

```text
"NoteService is a file."
```

think:

```text
"Create Note is an application use case."
```

So:

```text
Create Note
     ↓
noteService.create()
```

The service represents the application's operation.

Other examples:

```text
Register User
Login User
Create Order
Cancel Order
Publish Post
Create Note
Delete Note
```

These are **use cases**.

---

# 18. Service Should Return Data

Suppose the repository creates:

```json
{
  "_id": "123",
  "userId": "user1",
  "title": "Learn Redis",
  "content": "Study caching."
}
```

The service can return that result:

```js
const note = await noteRepository.create(data);

return note;
```

The controller receives it:

```js
const note = await noteService.create(data);
```

and converts it into an HTTP response.

---

# 19. Service Should Not Send HTTP Responses

Don't do this:

```js
const create = async (data, res) => {
    const note = await noteRepository.create(data);

    return res.status(201).json({
        success: true,
        data: note
    });
};
```

That's wrong for our architecture.

Now:

```text
Service
 ↓
Express Response
```

The service has become HTTP-dependent.

Instead:

```text
Service
 ↓
return note

Controller
 ↓
res.status(201).json(...)
```

---

# 20. Error Handling in the Service

Suppose a business rule fails:

```js
if (count >= 100) {
    throw new AppError(
        "Maximum number of notes reached",
        400
    );
}
```

The service can throw an application-level error.

Then:

```text
Service
   ↓
throw AppError
   ↓
asyncHandler
   ↓
Global Error Handler
   ↓
HTTP Response
```

This gives us centralized error formatting.

---

# 21. Don't Return `res.status()` From Service

Avoid:

```js
return res.status(400).json({
    message: "Limit reached"
});
```

Instead:

```js
throw new AppError("Maximum number of notes reached", 400);
```

Then the HTTP layer decides how that error is represented.

This keeps the service independent.

---

# 22. Service and Authorization

Authorization deserves special attention.

Suppose we have:

```text
PATCH /notes/123
```

and the Note belongs to:

```text
userA
```

but the authenticated user is:

```text
userB
```

Should the update be allowed?

Obviously not.

Where should that rule be enforced?

There isn't one universal answer.

Depending on the application, it may be handled through:

```text
Authorization middleware
Service
Repository query
```

or a combination.

For our architecture, resource-specific ownership checks will be handled carefully as we build the CRUD operations.

The important lesson:

> **Authorization is a business/security concern, not simply an HTTP concern.**

---

# 23. Ownership Can Be Part of the Data Operation

For example, instead of:

```js
findById(noteId)
```

then:

```js
if (note.userId !== userId)
```

we can eventually use a repository operation conceptually like:

```js
findByIdForUser(noteId, userId)
```

The database query can enforce:

```text
noteId = requested note
AND
userId = authenticated user
```

This becomes especially useful for update and delete.

We'll build that carefully in upcoming lessons.

---

# 24. Simple Service First

Don't over-engineer our first version.

Start with:

```js
const create = async ({ userId, title, content }) => {
    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

Then add real business rules when they actually exist.

This is important:

> **Don't invent business logic just to make the service look complicated.**

A service with five meaningful lines is better than a service with 100 meaningless lines.

---

# 25. Service File Structure

A simple structure could be:

```text
src/
├── controllers/
│   └── note.controller.js
│
├── services/
│   └── note.service.js
│
├── repositories/
│   └── note.repository.js
│
├── models/
│   └── note.model.js
│
└── routes/
    └── note.routes.js
```

Our service:

```text
services/
└── note.service.js
```

might look like:

```js
const noteRepository = require("../repositories/note.repository");

const create = async ({ userId, title, content }) => {
    return noteRepository.create({
        userId,
        title,
        content
    });
};

module.exports = {
    create
};
```

The exact module syntax depends on how your starter project is configured.

The architectural idea matters more than the syntax here.

---

# 26. Controller + Service Together

Now we can see the boundary clearly.

### Controller

```js
const create = asyncHandler(async (req, res) => {
    const note = await noteService.create({
        userId: req.user.id,
        title: req.body.title,
        content: req.body.content
    });

    res.status(201).json({
        success: true,
        data: note
    });
});
```

### Service

```js
const create = async ({ userId, title, content }) => {
    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

Notice:

```text
Controller
knows req/res

Service
doesn't
```

And:

```text
Service
knows business operation

Controller
doesn't
```

---

# 27. Add a Business Rule

Now imagine:

```text
Maximum 100 Notes per user
```

Service becomes:

```js
const create = async ({ userId, title, content }) => {
    const count = await noteRepository.countByUser(userId);

    if (count >= 100) {
        throw new AppError(
            "Maximum number of notes reached",
            400
        );
    }

    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

The controller doesn't change.

That's exactly what we want.

```text
Controller
      │
      │ unchanged
      ▼
Service
      │
      ├── business rule
      │
      ▼
Repository
```

---

# 28. This Is Why the Service Boundary Matters

Imagine we didn't have a service.

Controller:

```text
HTTP
 ↓
Validation
 ↓
Business rules
 ↓
Database
 ↓
Response
```

It would become large quickly.

With the service:

```text
Controller
 ↓
"Create this Note."

Service
 ↓
"Is creation allowed?"
"Apply business rules."
"Create it."

Repository
 ↓
"Save it."
```

Each layer has a much clearer responsibility.

---

# 29. Service Naming

Use names that describe application operations.

Good:

```text
create()
update()
delete()
getById()
list()
```

Or, in larger systems:

```text
createNote()
updateNote()
deleteNote()
```

Both can work.

The important thing is consistency.

For a resource-specific service:

```text
noteService.create()
```

is clean.

---

# 30. Avoid Generic "Do Everything" Services

Avoid creating:

```text
CommonService
UtilityService
DatabaseService
HelperService
MainService
```

with hundreds of unrelated functions.

Prefer domain-oriented services:

```text
note.service.js
user.service.js
order.service.js
payment.service.js
```

This keeps the application easier to understand.

---

# 31. What Happens When Repository Fails?

Suppose:

```text
MongoDB unavailable
```

Repository throws:

```text
Database error
```

The service generally doesn't need to turn that into:

```text
res.status(500)
```

It can let the error propagate:

```text
Repository
   ↓
Service
   ↓
Controller/async handler
   ↓
Global error handler
```

Centralized error handling decides the final HTTP representation.

---

# 32. Service Flow Diagram

Remember this:

```text
noteService.create()
       │
       ├── receive application data
       │
       ├── check business rules
       │
       ├── prepare application operation
       │
       ├── call repository
       │
       └── return result
```

Not:

```text
noteService.create()
       │
       ├── req.body ❌
       ├── res.json() ❌
       ├── JWT verification ❌
       ├── MongoDB query directly ❌
       └── HTTP status codes ❌
```

---

# 33. The Golden Rule

Here's the sentence I want you to remember from **17.6**:

> **The service should express what the application wants to accomplish, not how HTTP or MongoDB works.**

For our example:

```text
Create Note
```

becomes:

```js
noteService.create(data)
```

The service can then coordinate:

```text
Business rules
      ↓
Repository
      ↓
Result
```
