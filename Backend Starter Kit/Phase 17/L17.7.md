# Lesson 17.7 — Create Resource: Repository

In **17.6**, we built the Service layer:

```text
Controller
    ↓
Service
    ↓
Repository
```

The Service answers:

> **What should the application do?**

The Repository answers:

> **How should the application access the data?**

For our Note creation flow, we're now going to build:

```js
noteRepository.create()
```

---

# 1. Where Repository Fits

Our complete flow is:

```text
POST /api/v1/notes
        ↓
      Route
        ↓
 Authentication
        ↓
    Validation
        ↓
    Controller
        ↓
      Service
        ↓
    Repository
        ↓
      Model
        ↓
    MongoDB
```

We've already discussed the first parts.

Now we're focusing on:

```text
Service
   ↓
Repository
   ↓
Database
```

---

# 2. What Is a Repository?

A repository is an abstraction around **data access**.

Instead of allowing the entire application to write:

```js
Note.create(...)
Note.find(...)
Note.findById(...)
Note.deleteOne(...)
```

everywhere, we provide dedicated repository methods.

For example:

```js
noteRepository.create()
noteRepository.findById()
noteRepository.findByUserId()
noteRepository.update()
noteRepository.delete()
```

So the rest of the application can say:

```text
"Create this Note."
```

without worrying about the exact database query.

---

# 3. Repository vs Model

This distinction is important.

### Model

The Model represents the database structure:

```js
Note
```

and knows about:

```text
Schema
Fields
Indexes
Mongoose behavior
```

### Repository

The Repository represents application-facing **data-access operations**:

```text
create
find
update
delete
```

Think:

```text
Repository
    ↓
uses
    ↓
Model
    ↓
MongoDB
```

---

# 4. Our First Repository Method

We need:

```js
noteRepository.create()
```

A simple implementation could be:

```js
const create = async (data) => {
    return Note.create(data);
};
```

This looks tiny.

But the important thing is **where this code lives**.

It belongs in:

```text
repositories/
└── note.repository.js
```

rather than inside the controller or service.

---

# 5. Repository File

Conceptually:

```js
const Note = require("../models/note.model");

const create = async (data) => {
    return Note.create(data);
};

module.exports = {
    create
};
```

Now our layers are:

```text
Controller
    ↓
noteService.create()
    ↓
noteRepository.create()
    ↓
Note.create()
```

That's the separation we want.

---

# 6. Why Not Just Call `Note.create()` Everywhere?

Imagine we have:

```text
note.controller.js
note.service.js
comment.service.js
admin.service.js
background-job.js
```

Without a repository, multiple places might directly use:

```js
Note.create()
Note.find()
Note.findById()
Note.updateOne()
```

Now database logic is spread everywhere.

```text
Service A ──→ Mongoose
Service B ──→ Mongoose
Controller ──→ Mongoose
Job ─────────→ Mongoose
```

That's difficult to maintain.

With a repository:

```text
Service A ──┐
Service B ──┤
Job ────────┤
             ▼
        Repository
             ↓
          Mongoose
```

Database access has a clear boundary.

---

# 7. Repository as a Data Access Boundary

Think of the repository as a door:

```text
             APPLICATION
                  │
                  ▼
          ┌──────────────┐
          │  Repository  │
          └──────────────┘
                  │
                  ▼
              Mongoose
                  │
                  ▼
              MongoDB
```

The application doesn't need to know what's behind the door.

It only needs to know:

```text
create()
findById()
update()
delete()
```

---

# 8. What Should `create()` Receive?

Our service currently calls:

```js
return noteRepository.create({
    userId,
    title,
    content
});
```

So the repository receives:

```js
{
    userId,
    title,
    content
}
```

It should not receive:

```js
req
res
```

The repository should have no idea that HTTP exists.

---

# 9. Repository Should Not Know About HTTP

Never do this:

```js
const create = async (req, res) => {
    // ...
};
```

That's completely wrong for a repository.

The repository should not know about:

```text
Express
HTTP
Request
Response
Status codes
JWT
```

Its world is:

```text
Data
Database
Queries
Persistence
```

---

# 10. Repository Should Not Make Business Decisions

This is another important boundary.

Avoid:

```js
const create = async (data) => {
    const count = await Note.countDocuments({
        userId: data.userId
    });

    if (count >= 100) {
        throw new Error("User has reached the note limit");
    }

    return Note.create(data);
};
```

The repository is now deciding:

> "Is the user allowed to create another Note?"

That's business logic.

Instead:

```text
Service
  ↓
Check note limit
  ↓
Repository
  ↓
Create Note
```

The repository should focus on the data operation.

---

# 11. Service vs Repository

This is one of the most important comparisons in this phase.

|Service|Repository|
|---|---|
|Business logic|Data access|
|Application rules|Database operations|
|Decides whether operation is allowed|Executes operation|
|Coordinates use case|Queries database|
|Doesn't need MongoDB details|Knows database details|

Example:

```text
Service:
"User can create this Note."

Repository:
"Okay, I'll save it."
```

---

# 12. The Create Flow

Let's follow the actual operation.

### Controller

```js
const note = await noteService.create({
    userId: req.user.id,
    title: req.body.title,
    content: req.body.content
});
```

↓

### Service

```js
const create = async ({ userId, title, content }) => {
    return noteRepository.create({
        userId,
        title,
        content
    });
};
```

↓

### Repository

```js
const create = async (data) => {
    return Note.create(data);
};
```

↓

### Model

```text
Note schema
```

↓

### MongoDB

```text
Document inserted
```

That's our complete create path.

---

# 13. Why Does the Service Call the Repository?

The service shouldn't care whether the data is stored in:

```text
MongoDB
PostgreSQL
MySQL
Redis
External API
```

The service says:

```text
"Create this Note."
```

The repository handles:

```text
"Here's how we create it in our current database."
```

This is the abstraction.

---

# 14. Repository Method Naming

Good repository names describe **data operations**.

For example:

```js
create()
findById()
findByUserId()
updateById()
deleteById()
countByUserId()
exists()
```

These names describe what data operation is being performed.

Compare that with:

```text
canUserCreateNote()
shouldAllowCreation()
processNoteCreation()
```

Those sound more like business operations.

Those belong closer to the service layer.

---

# 15. `create()` Is a Persistence Operation

Our repository method:

```js
create(data)
```

means:

> Persist this Note.

It doesn't mean:

> Decide whether the user should be allowed to create a Note.

That's the service's responsibility.

This distinction will become increasingly important when our application gets more complex.

---

# 16. Repository Should Return the Result

When:

```js
Note.create(data)
```

finishes, Mongoose returns the created document.

The repository can simply return it:

```js
const create = async (data) => {
    return Note.create(data);
};
```

Then:

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
```

The created Note travels back up.

---

# 17. What Does the Repository Return?

Suppose MongoDB creates:

```json
{
  "_id": "65abc123",
  "userId": "user123",
  "title": "Learn MongoDB",
  "content": "Study indexes.",
  "createdAt": "2026-08-26T...",
  "updatedAt": "2026-08-26T..."
}
```

The repository can return the Mongoose document.

The service can then decide whether it needs to:

```text
return it directly
transform it
remove sensitive fields
combine it with other data
```

Then the controller formats the HTTP response.

---

# 18. Repository Does Not Format API Responses

Don't do this:

```js
const create = async (data) => {
    const note = await Note.create(data);

    return {
        success: true,
        message: "Note created",
        data: note
    };
};
```

That response structure is an **API concern**.

The repository should return data, not HTTP response envelopes.

Prefer:

```js
const create = async (data) => {
    return Note.create(data);
};
```

Then the controller handles:

```js
res.status(201).json({
    success: true,
    data: note
});
```

---

# 19. Repository and Mongoose

Since we're using MongoDB with Mongoose, the repository will naturally contain Mongoose operations.

For example:

```js
Note.create(data);
```

Later:

```js
Note.find(...)
Note.findOne(...)
Note.findById(...)
Note.updateOne(...)
Note.findByIdAndUpdate(...)
Note.deleteOne(...)
```

This is exactly where those database-specific details belong.

---

# 20. Why This Helps With Testing

Imagine testing the service.

Without a repository:

```text
Service
   ↓
MongoDB
```

Your test might need a real database.

With a repository boundary:

```text
Service
   ↓
Repository
```

you can replace/mock the repository.

Conceptually:

```text
Fake Repository
       ↓
Service
```

and test business rules without needing MongoDB for every test.

This is one of the practical benefits of the pattern.

---

# 21. Example Service Test

Imagine our business rule is:

```text
A user cannot create more than 100 notes.
```

We can test the service conceptually:

```js
repository.countByUser = async () => 100;

await expect(
    noteService.create({
        userId: "123",
        title: "Test",
        content: "Test"
    })
).rejects.toThrow();
```

The service test doesn't need to care how MongoDB works.

The repository is a separate concern.

---

# 22. Repository Testing

The repository itself can have database-focused tests.

For example:

```text
Repository test
    ↓
create()
    ↓
MongoDB test database
```

So we can separate our tests:

```text
Service tests
    ↓
Business rules

Repository tests
    ↓
Database behavior
```

That's much easier to reason about.

---

# 23. Don't Make the Repository Too Generic

A common mistake is creating something like:

```js
GenericRepository
```

with:

```js
create()
find()
update()
delete()
```

and then trying to force every model into it.

Generic repositories can sometimes be useful, but don't assume they're automatically better.

For our learning project, a domain-specific repository is easier to understand:

```text
note.repository.js
user.repository.js
order.repository.js
```

Each can expose exactly the operations its domain needs.

---

# 24. Why Domain-Specific Repositories Are Useful

Suppose Notes need:

```text
findByUserId()
countByUserId()
findRecentByUserId()
```

while Orders need:

```text
findPending()
findByCustomerId()
calculateTotal()
```

A generic repository becomes awkward.

Domain-specific repositories can express exactly what the application needs.

```text
NoteRepository
    ├── create
    ├── findById
    ├── findByUserId
    └── countByUserId

OrderRepository
    ├── create
    ├── findPending
    ├── findByCustomerId
    └── ...
```

This is clearer.

---

# 25. Repository as an Interface

Even if we're using JavaScript, it's useful to think of:

```text
NoteRepository
```

as an interface between the application and database.

The service expects:

```text
create(data)
```

It doesn't necessarily care how that operation is implemented.

Today:

```text
MongoNoteRepository
```

Tomorrow, hypothetically:

```text
PostgresNoteRepository
```

The service contract could remain similar.

---

# 26. But Don't Switch Databases Just for the Pattern

A warning:

Don't think:

> "We're using repositories, so we'll definitely switch from MongoDB later."

No.

The repository pattern isn't valuable only because of database switching.

It helps with:

```text
Separation of concerns
Testing
Maintainability
Readable services
Centralized data access
```

Those benefits are useful even if MongoDB stays forever.

---

# 27. Repository Error Handling

Suppose MongoDB fails:

```text
MongoDB
   ↓
Connection error
```

Mongoose throws an error.

The repository generally shouldn't turn it into:

```js
res.status(500)
```

Instead:

```text
MongoDB error
    ↓
Repository
    ↓
throws
    ↓
Service
    ↓
Controller/async handler
    ↓
Global error handler
```

This keeps error handling centralized.

---

# 28. Should the Repository Catch Errors?

Not every repository method needs:

```js
try {
    return await Note.create(data);
} catch (error) {
    throw error;
}
```

That's pointless.

If you're simply catching an error and immediately throwing the same error, you've added no value.

Instead, catch errors when you need to:

```text
Translate them
Add context
Handle a specific database condition
```

Otherwise, let them propagate.

---

# 29. Example: Duplicate Key Error

Suppose the database has a unique constraint.

MongoDB could return a duplicate-key error.

The repository might eventually translate a database-specific error into a domain/application error if that makes the architecture cleaner.

For example:

```text
MongoDB duplicate key
        ↓
Repository
        ↓
"Resource already exists"
        ↓
Service
        ↓
Error handler
```

But don't add this complexity until the actual requirement exists.

# 33. A Very Important Boundary

Look at this:

```js
Note.create(data);
```

Where should it live?

```text
❌ Controller
❌ Service
✅ Repository
```

Why?

Because:

```text
Note.create()
```

is a **database/data-access operation**.

And the Repository owns data access.

---

# 34. Another Boundary

Where should this live?

```js
if (noteCount >= 100) {
    throw new AppError(...);
}
```

Answer:

```text
❌ Controller
❌ Repository
✅ Service
```

Because:

```text
"Can the user create another Note?"
```

is a business decision.

---

# 35. Another Boundary

Where should this live?

```js
res.status(201).json(...)
```

Answer:

```text
✅ Controller
❌ Service
❌ Repository
```

Because it's an HTTP response.

---

# 36. The Three-Layer Rule

Keep this table in your notes:

|Code|Layer|
|---|---|
|`req.body`|Controller|
|`req.user`|Controller|
|`res.status()`|Controller|
|Business rules|Service|
|Application use case|Service|
|`Note.create()`|Repository|
|`Note.find()`|Repository|
|MongoDB queries|Repository|
|Schema definition|Model|

This table will save you from a lot of architectural confusion.
