# Lesson 17.8 — Restore a Soft-Deleted Resource

In **17.7**, we introduced **soft delete**.

Instead of permanently removing a Note:

```js
await noteRepository.deleteById(noteId);
```

we change its state:

```text
isDeleted = true
```

So the document remains in MongoDB.

Now we have an important question:

> **What if the user wants that Note back?**

That's what **restore** does.

---

# 1. What Is Restore?

Suppose the Note originally looks like:

```json
{
  "_id": "note123",
  "title": "Learn MongoDB",
  "content": "Study indexes",
  "isDeleted": false
}
```

After soft delete:

```json
{
  "_id": "note123",
  "title": "Learn MongoDB",
  "content": "Study indexes",
  "isDeleted": true
}
```

Restore changes it back:

```json
{
  "_id": "note123",
  "title": "Learn MongoDB",
  "content": "Study indexes",
  "isDeleted": false
}
```

So:

```text
ACTIVE
  ↓
SOFT DELETE
  ↓
DELETED
  ↓
RESTORE
  ↓
ACTIVE
```

---

# 2. Why Restore Is Useful

Soft delete is useful because we don't immediately destroy data.

For example:

```text
User deletes Note
       ↓
isDeleted = true
       ↓
Note disappears from normal list
       ↓
User changes their mind
       ↓
Restore
       ↓
isDeleted = false
```

This gives your application an **undo-like capability**.

It can also be useful for:

- accidental deletion
    
- recycle-bin functionality
    
- administrative recovery
    
- auditing
    
- data retention
    

---

# 3. Restore Is a Different Operation From Update

This is important.

Normal update:

```text
PATCH /notes/:id
```

might change:

```json
{
  "title": "New title"
}
```

Restore changes the resource's lifecycle state:

```text
isDeleted: true
        ↓
isDeleted: false
```

So restore deserves its own application operation.

Conceptually:

```text
noteService.update()
```

and:

```text
noteService.restore()
```

are different use cases.

---

# 4. Possible API Design

One simple API design is:

```http
PATCH /api/v1/notes/:id/restore
```

For example:

```http
PATCH /api/v1/notes/123/restore
```

Another possible design is:

```http
POST /api/v1/notes/123/restore
```

There isn't one universal answer.

For our learning architecture, we'll use:

```text
PATCH /notes/:id/restore
```

because we're changing the resource's state.

---

# 5. The Complete Restore Flow

Our architecture becomes:

```text
PATCH /api/v1/notes/:id/restore
                ↓
              Route
                ↓
        Authentication
                ↓
           Validation
                ↓
           Controller
                ↓
             Service
                ↓
           Repository
                ↓
             Model
                ↓
            MongoDB
```

Notice something important:

> Restore still travels through the same architectural layers.

That's exactly why the layered architecture is useful.

---

# 6. Controller

The controller receives:

```text
req.params.id
```

For:

```http
PATCH /notes/123/restore
```

we get:

```js
req.params.id
```

which is:

```text
123
```

The controller can then call:

```js
await noteService.restore(req.params.id, req.user.id);
```

Conceptually:

```js
const restore = asyncHandler(async (req, res) => {
    const note = await noteService.restore(
        req.params.id,
        req.user.id
    );

    res.status(200).json({
        success: true,
        data: note
    });
});
```

The exact response helper will depend on the response architecture we've been building.

---

# 7. Why Pass `userId`?

This is extremely important.

Don't simply do:

```js
noteService.restore(noteId);
```

if Notes belong to users.

Instead:

```js
noteService.restore(noteId, userId);
```

Why?

Because:

```text
User A
   ↓
Note A

User B
   ↓
Note B
```

User A should not be able to restore User B's deleted Note.

So the operation should conceptually mean:

> Restore **this Note belonging to this authenticated user**.

This connects directly to the ownership phase that comes next.

---

# 8. Service

The service represents the use case:

```text
Restore Note
```

A simple version:

```js
const restore = async (noteId, userId) => {
    return noteRepository.restoreById(noteId, userId);
};
```

At first this looks almost too simple.

That's okay.

Later, the service may contain business rules.

For example:

```text
Can this user restore the Note?
Is restoration allowed?
Has the retention period expired?
Is the Note already permanently deleted?
```

Those are application decisions.

---

# 9. Repository

The repository performs the database operation.

Conceptually:

```js
const restoreById = async (noteId, userId) => {
    return Note.findOneAndUpdate(
        {
            _id: noteId,
            userId,
            isDeleted: true
        },
        {
            $set: {
                isDeleted: false
            }
        },
        {
            new: true
        }
    );
};
```

This is a very important query.

Let's break it down.

---

# 10. The Filter

We're searching for:

```js
{
    _id: noteId,
    userId,
    isDeleted: true
}
```

That means:

```text
Note ID matches
      AND
User owns Note
      AND
Note is currently deleted
```

Only when **all three conditions** are true can the restore happen.

---

# 11. Why `isDeleted: true`?

Because we're restoring a deleted Note.

If the Note is already active:

```text
isDeleted = false
```

then there is nothing to restore.

Our query:

```js
isDeleted: true
```

prevents the operation from unnecessarily modifying active Notes.

---

# 12. The Update

We're changing:

```js
{
    $set: {
        isDeleted: false
    }
}
```

So:

```text
true
 ↓
false
```

That's the entire persistence operation.

---

# 13. What Does `new: true` Do?

Mongoose's `findOneAndUpdate()` normally has behavior where the returned document may be the document **before** the update.

Using:

```js
{
    new: true
}
```

asks Mongoose to return the **updated document**.

So:

```js
const note = await Note.findOneAndUpdate(
    filter,
    update,
    { new: true }
);
```

gives us the restored Note.

Conceptually:

```text
Before:
isDeleted = true

Database update

After:
isDeleted = false

Returned document:
isDeleted = false
```

---

# 14. What If the Note Doesn't Exist?

Suppose:

```js
findOneAndUpdate(...)
```

returns:

```text
null
```

That can mean several things:

```text
Note doesn't exist
OR
Note belongs to another user
OR
Note isn't deleted
```

From a security perspective, this is interesting.

We don't necessarily want to tell the requester:

> "The Note exists but belongs to another user."

That could leak information.

A service can turn the result into an appropriate application error.

For example:

```js
const note = await noteRepository.restoreById(
    noteId,
    userId
);

if (!note) {
    throw new AppError("Note not found", 404);
}

return note;
```

Now:

```text
No matching owned deleted Note
          ↓
404 Not Found
```

This is a clean boundary.

---

# 15. Why the Repository Should Combine Ownership

Compare:

### Less safe approach

```js
const note = await Note.findById(noteId);

if (note.userId !== userId) {
    throw ...
}
```

with:

### Better data-access operation

```js
Note.findOneAndUpdate({
    _id: noteId,
    userId,
    isDeleted: true
});
```

The second approach makes the ownership requirement part of the database query itself.

Your source roadmap specifically emphasizes this ownership model later:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

rather than simply:

```js
Todo.findById(todoId);
```

because ownership checks are important for preventing horizontal privilege escalation.

We'll study that deeply in **17.9**.

# 16. What About a Trash/Recycle Bin?

Soft delete naturally allows us to build:

```http
GET /notes/trash
```

The repository could query:

```js
{
    userId,
    isDeleted: true
}
```

while the normal list uses:

```js
{
    userId,
    isDeleted: false
}
```

So we effectively have:

```text
Normal Notes
    ↓
isDeleted = false

Trash
    ↓
isDeleted = true
```

This is a very practical pattern.

---

# 17. Normal Read After Soft Delete

Suppose:

```text
Note A → isDeleted = false
Note B → isDeleted = true
Note C → isDeleted = false
```

A normal list should return:

```text
A
C
```

not:

```text
A
B
C
```

So normal repository queries need to account for:

```js
isDeleted: false
```

That's one of the most important consequences of adopting soft deletion.

---

# 18. Restore Makes the Note Visible Again

Before restore:

```text
Database:

A → false
B → true
C → false
```

Normal list:

```text
A
C
```

After restoring B:

```text
Database:

A → false
B → false
C → false
```

Normal list:

```text
A
B
C
```

That's the user-visible effect of restore.

---

# 19. What If the Note Is Permanently Deleted?

Soft delete and permanent delete are different.

```text
Soft delete
    ↓
isDeleted = true
```

Permanent delete:

```text
document removed from MongoDB
```

If the document has been permanently deleted:

```text
Note.findOneAndUpdate(...)
```

can't restore it.

So:

```text
SOFT DELETE
    ↓
RESTORE possible

HARD DELETE
    ↓
RESTORE impossible
```

This is one reason applications often delay permanent deletion.

---

# 20. Retention Policies

A production application may eventually have:

```text
Deleted at:
2026-08-26
```

Then a policy might say:

```text
Keep deleted Notes for 30 days.
```

Flow:

```text
Delete
 ↓
deletedAt = now
 ↓
30 days
 ↓
Permanent deletion
```

Then restore is allowed only during those 30 days.

The service could enforce:

```text
If retention period expired
    ↓
Reject restore
```

That's a **business rule**, so it belongs in the Service layer.

---

# 21. `deletedAt` Is Often Better Than Only `isDeleted`

Instead of:

```js
isDeleted: Boolean
```

we can eventually have:

```js
isDeleted: Boolean,
deletedAt: Date
```

When deleting:

```text
isDeleted = true
deletedAt = current time
```

When restoring:

```text
isDeleted = false
deletedAt = null
```

This gives us more information.

Example:

```json
{
  "isDeleted": true,
  "deletedAt": "2026-08-26T10:30:00Z"
}
```

Now we know **when** it was deleted.

---

# 22. Why `deletedAt` Is Useful

It can support:

```text
Trash UI
Retention policies
Audit information
Cleanup jobs
Analytics
Recovery rules
```

For example:

```text
Delete:
August 26

Permanent cleanup:
September 25
```

A background job can find:

```js
{
    isDeleted: true,
    deletedAt: {
        $lt: thirtyDaysAgo
    }
}
```

and permanently remove old documents.

That's an example of how today's CRUD architecture can later connect to background jobs.

---

# 23. Restore With `deletedAt`

A better restore update could be:

```js
{
    $set: {
        isDeleted: false,
        deletedAt: null
    }
}
```

So the state transition is:

### Active

```json
{
  "isDeleted": false,
  "deletedAt": null
}
```

### Deleted

```json
{
  "isDeleted": true,
  "deletedAt": "2026-08-26T10:30:00Z"
}
```

### Restored

```json
{
  "isDeleted": false,
  "deletedAt": null
}
```

This creates a clean state model.

# 27. What If Restore Is Called on an Active Note?

Suppose:

```text
isDeleted = false
```

Then our repository filter:

```js
isDeleted: true
```

doesn't match.

Result:

```text
null
```

The service can return:

```text
404 Note not found
```

or, depending on the API contract, potentially:

```text
409 Note is already active
```

Which one is better depends on your API design.

The important thing is to define the behavior consistently.

---

# 28. Should Restore Be Idempotent?

This is a useful API-design question.

An operation is **idempotent** if repeating it produces the same final state.

Restore:

```text
Deleted
 ↓
Restore
 ↓
Active
```

Calling restore again:

```text
Active
 ↓
Restore
 ↓
Active
```

The final state doesn't change.

But the HTTP/API semantics and response can still be designed differently.

For our learning architecture, it's perfectly reasonable to require:

```text
isDeleted = true
```

for a successful restore operation.

---

# 29. Security Consideration

Imagine User A knows:

```text
noteId = 123
```

and User B owns it.

If your repository does:

```js
Note.findOneAndUpdate(
    { _id: noteId },
    { $set: { isDeleted: false } }
);
```

then User A could potentially restore User B's Note.

That's a security bug.

Instead:

```js
Note.findOneAndUpdate(
    {
        _id: noteId,
        userId,
        isDeleted: true
    },
    ...
);
```

The authenticated identity becomes part of the data-access condition.

This is a pattern you'll use repeatedly.

```text

```

Restore is our first simple example of **state transition design**.
