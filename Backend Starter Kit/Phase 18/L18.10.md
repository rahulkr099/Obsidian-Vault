# Lesson 18.10 — Query Validation

We are now at:

```text
18.6 Filtering
18.7 Search
18.8 Sorting
18.9 Allow-listing sort fields
18.10 Query validation ← TODAY
```

Your roadmap defines **18.10 as Query Validation**, within Phase 18: Pagination, Filtering & Sorting.

The main goal today is to stop treating `req.query` as trusted input.

---

# 1. The problem with `req.query`

Suppose the frontend sends:

```http
GET /api/v1/todos?page=2&limit=20&sort=-created&status=pending
```

Express gives us:

```js
req.query
```

which might look like:

```js
{
  page: "2",
  limit: "20",
  sort: "-created",
  status: "pending"
}
```

Notice something important:

> **Everything coming from a URL query string is initially just input from the client.**

Even:

```text
page
limit
sort
status
search
```

must be treated as untrusted.

---

# 2. Query validation vs body validation

You already learned validation for:

```http
POST /todos
```

where data might come from:

```js
req.body
```

For example:

```json
{
  "title": "Learn MongoDB"
}
```

But GET requests commonly use:

```js
req.query
```

Example:

```http
GET /todos?page=2&limit=20
```

So we need to validate **query parameters** too.

Your source roadmap explicitly includes query parameter validation in the earlier validation phase as well.

---

# 3. Query parameters are strings

This is one of the most important things to understand.

The client sends:

```http
?page=2
```

You may think:

```js
page === 2
```

But Express generally gives:

```js
page === "2"
```

So:

```js
typeof req.query.page
```

is typically:

```text
"string"
```

not:

```text
"number"
```

---

# 4. Why this matters

Suppose:

```js
const page = req.query.page;
```

You might then do:

```js
const skip = (page - 1) * limit;
```

JavaScript may coerce strings into numbers here.

But relying on implicit conversion is not a good API design.

Instead:

```text
raw input
   ↓
validation
   ↓
conversion
   ↓
trusted application value
```

For example:

```js
page = 2
```

as an actual number.

---

# 5. What should we validate?

Our Todo query might support:

```text
search
status
sort
page
limit
```

So we need rules.

For example:

```text
page
→ positive integer

limit
→ positive integer
→ maximum 100

status
→ pending | completed

sort
→ created | -created | updated | -updated

search
→ string
→ maximum length
```

Now our API has an explicit contract.

---

# 6. Think of validation as a gate

The architecture should be:

```text
                CLIENT
                   │
                   ▼
              req.query
                   │
                   ▼
            QUERY VALIDATION
                   │
          ┌────────┴────────┐
          │                 │
        INVALID            VALID
          │                 │
          ▼                 ▼
        400             CLEAN DATA
                            │
                            ▼
                         SERVICE
```

This is the same trust-boundary idea you learned earlier.

---

# 7. Why validate before the service?

Imagine the service receives:

```js
{
  page: "hello",
  limit: "-500",
  sort: "password",
  status: "whatever"
}
```

If the service has to deal with all of these possibilities, it becomes messy.

Instead:

```text
Controller boundary
       ↓
Validation
       ↓
Service receives trusted values
```

Now the service can focus on business logic.

---

# 8. Example query schema

Using Joi, conceptually:

```js
const querySchema = Joi.object({
  page: Joi.number()
    .integer()
    .min(1)
    .default(1),

  limit: Joi.number()
    .integer()
    .min(1)
    .max(100)
    .default(20),

  status: Joi.string()
    .valid("pending", "completed"),

  search: Joi.string()
    .trim()
    .max(100),

  sort: Joi.string()
});
```

This is already much safer.

---

# 9. `page`

We don't want:

```text
?page=-5
```

or:

```text
?page=hello
```

or:

```text
?page=1.5
```

We want:

```text
?page=1
?page=2
?page=3
```

So:

```js
Joi.number()
  .integer()
  .min(1)
```

means:

```text
number
+
integer
+
minimum 1
```

---

# 10. `limit`

This one is especially important.

A client could request:

```http
GET /todos?limit=1000000
```

If you blindly accept it, the API might attempt to return an enormous number of documents.

Instead:

```js
limit: Joi.number()
  .integer()
  .min(1)
  .max(100)
```

Now:

```text
limit=20     ✅
limit=100    ✅
limit=101    ❌
limit=100000 ❌
```

This is both **validation and resource protection**.

---

# 11. Why maximum limits matter

Imagine your database contains:

```text
5,000,000 todos
```

Someone sends:

```http
GET /todos?limit=5000000
```

You don't want your server trying to process that request.

A reasonable API might enforce:

```text
1 ≤ limit ≤ 100
```

or perhaps:

```text
1 ≤ limit ≤ 50
```

depending on the endpoint.

The exact number is an API design decision.

---

# 12. `status`

Suppose your Todo statuses are:

```text
pending
completed
```

Then:

```js
status: Joi.string()
  .valid("pending", "completed")
```

allows:

```text
status=pending       ✅
status=completed     ✅
```

but rejects:

```text
status=random        ❌
status=admin         ❌
status=123           ❌
```

This is an example of **enumeration validation**.

---

# 13. `search`

Suppose:

```http
GET /todos?search=mongodb
```

We can validate:

```js
search: Joi.string()
  .trim()
  .max(100)
```

Now:

```text
search=mongodb
```

is okay.

But an extremely large search string can be rejected.

This gives your endpoint a clear boundary.

---

# 14. `sort`

We already learned allow-listing in 18.9.

So don't just do:

```js
sort: Joi.string()
```

and call it finished.

Instead, we want:

```text
created
-created
updated
-updated
title
-title
```

depending on what the API supports.

For example:

```js
sort: Joi.string()
  .valid(
    "created",
    "-created",
    "updated",
    "-updated",
    "title",
    "-title"
  )
```

Now validation and allow-listing work together.

---

# 15. Validation vs allow-listing

These concepts are related but slightly different.

### Validation asks:

> Is this input structurally valid?

Example:

```text
page=hello
```

❌ Not a valid integer.

### Allow-listing asks:

> Is this particular value supported by our API?

Example:

```text
sort=password
```

❌ Not an allowed sort option.

So:

```text
Validation
+
Allow-listing
```

gives you a much stronger boundary.

---

# 16. The validated result should be normalized

Suppose the client sends:

```http
?page=2&limit=20
```

Raw:

```js
{
  page: "2",
  limit: "20"
}
```

After validation/conversion:

```js
{
  page: 2,
  limit: 20
}
```

This is important.

The service should ideally receive:

```js
page: 2
```

not:

```js
page: "2"
```

---

# 17. Defaults

One of the useful features of validation libraries is defaults.

Suppose the client sends:

```http
GET /todos
```

No:

```text
page
limit
```

We can define:

```js
page: Joi.number()
  .integer()
  .min(1)
  .default(1),

limit: Joi.number()
  .integer()
  .min(1)
  .max(100)
  .default(20)
```

Then the validated result becomes:

```js
{
  page: 1,
  limit: 20
}
```

So your service doesn't have to repeatedly write:

```js
const page = req.query.page || 1;
const limit = req.query.limit || 20;
```

---

# 18. A better query object

After validation, we want something like:

```js
{
  page: 2,
  limit: 20,
  status: "pending",
  search: "mongo",
  sort: "-created"
}
```

Then we can pass it deeper into the application.

# 19. Query validation middleware

You can create reusable middleware:

```js
function validateQuery(schema) {
  return (req, res, next) => {
    const { error, value } = schema.validate(req.query);

    if (error) {
      return next(error);
    }

    req.query = value;

    next();
  };
}
```

Conceptually:

```text
req.query
   ↓
Joi schema
   ↓
error?
   ├── yes → next(error)
   │
   └── no
        ↓
   req.query = validated value
        ↓
      next()
```

Now controllers don't need to manually validate every query parameter.

---

# 20. Route usage

For example:

```js
router.get(
  "/",
  validateQuery(todoQuerySchema),
  todoController.getTodos
);
```

The request flow becomes:

```text
GET /todos?page=2&limit=20
          │
          ▼
validateQuery()
          │
          ▼
todoController.getTodos()
```

Very clean.

# 21. Why middleware is a good place

Remember the Phase 9 architecture:

```text
Request
 ↓
Validation middleware
 ↓
Valid?
 │
 ├── NO → 400
 │
 └── YES
       ↓
    Controller
```

That's exactly what we're doing here.

The validation layer acts as the boundary between:

```text
untrusted HTTP input
```

and:

```text
trusted application data
```

---

# 22. Don't put all validation inside the controller

Avoid:

```js
async function getTodos(req, res) {

  if (!req.query.page) {
     ...
  }

  if (req.query.limit < 1) {
     ...
  }

  if (!["pending", "completed"].includes(req.query.status)) {
     ...
  }

  // actual controller logic...
}
```

The controller becomes cluttered.

Instead:

```text
Route
 ↓
Query validation middleware
 ↓
Controller
```

Now the controller can focus on HTTP handling.

---

# 23. Query validation is different from business validation

This distinction is important.

Suppose:

```text
limit=20
```

is valid.

That's **query validation**.

But suppose the user requests:

```text
GET /todos
```

and they aren't allowed to see a particular Todo.

That's **authorization/business logic**.

So:

```text
Query validation
    ↓
"Is this input acceptable?"

Authorization
    ↓
"Is this user allowed?"

Business logic
    ↓
"What should happen?"
```

Don't mix these responsibilities.

---

# 24. Query validation is also different from sanitization

Another important distinction.

### Validation

Checks whether input is acceptable.

```text
limit=20
```

→ valid.

### Normalization

Converts input into a consistent form.

```text
"  mongo  "
```

→

```text
"mongo"
```

### Sanitization

Removes or transforms potentially dangerous content according to your security policy.

These are related but not identical concepts.

Your roadmap treats **validation vs sanitization** as separate concepts in Phase 9.

# 25. Unknown query parameters

Suppose your API supports:

```text
page
limit
status
search
sort
```

But the client sends:

```http
GET /todos?page=2&limit=20&secretMode=true
```

What should happen?

One strong approach is to reject unknown fields.

For example, with Joi:

```js
Joi.object({
  page: ...,
  limit: ...,
  status: ...,
  search: ...,
  sort: ...
}).unknown(false)
```

Then:

```text
secretMode
```

is rejected.

This is another form of allow-listing.

---

# 26. Why reject unknown query fields?

Because it makes your API contract explicit.

Without this:

```http
GET /todos?foo=bar&hello=world&abc=123
```

might silently work.

That makes typos harder to find.

For example:

```http
GET /todos?limt=20
```

instead of:

```text
limit=20
```

If unknown fields are rejected, you catch the typo immediately.

That's useful.

---

# 27. But should every API reject unknown fields?

Not necessarily.

There are two reasonable approaches:

### Strict

```text
Unknown field → 400
```

Pros:

- clear contract
    
- catches typos
    
- easier debugging
    

### Permissive

```text
Unknown field → ignored
```

Pros:

- more flexible
    
- sometimes useful for backward compatibility
    

For our architecture, strict validation is a good learning default.

---

# 28. Validation error response

Suppose:

```http
GET /todos?page=hello
```

The validator detects:

```text
page must be a number
```

Your API could return:

```json
{
  "success": false,
  "message": "Invalid query parameters",
  "errors": [
    {
      "field": "page",
      "message": "page must be a number"
    }
  ]
}
```

This connects with the API response architecture you learned in Phase 16.

# 29. Don't expose raw validation errors blindly

A validation library might produce internal details.

Your API should format them into a consistent structure.

For example:

```text
Joi error
   ↓
validation middleware
   ↓
AppError / validation error
   ↓
global error middleware
   ↓
API error response
```

This keeps your error handling consistent.

# 33. An important improvement: don't pass `req.query` everywhere

Avoid:

```js
todoService.getTodos(req.query);
```

if `req.query` still contains raw HTTP data.

Better:

```js
const query = validateAndParseTodoQuery(req.query);

todoService.getTodos({
  userId: req.user.id,
  query
});
```

Or even better, let middleware produce the trusted object.

For example:

```js
req.validatedQuery
```

Then:

```js
todoController.getTodos = async (req, res) => {
  const result = await todoService.getTodos({
    userId: req.user.id,
    query: req.validatedQuery
  });

  ...
};
```

This makes the distinction very clear:

```text
req.query
       ↓
untrusted

req.validatedQuery
       ↓
validated/normalized
```

---

# 34. Is `req.validatedQuery` necessary?

Not always.

You could overwrite:

```js
req.query = value;
```

But having:

```js
req.validatedQuery
```

can make your architecture more explicit.

For learning and larger applications, I like the distinction:

```text
req.query
        → raw input

req.validatedQuery
        → trusted application input
```

It makes the trust boundary visible.

# 35. Example middleware

Conceptually:

```js
function validateQuery(schema) {
  return (req, res, next) => {
    const { error, value } = schema.validate(req.query, {
      abortEarly: false,
      stripUnknown: true
    });

    if (error) {
      return next(
        new AppError(
          "Invalid query parameters",
          400
        )
      );
    }

    req.validatedQuery = value;

    next();
  };
}
```

The exact error implementation will depend on the error architecture you've already built.

The important flow is:

```text
raw query
 ↓
schema
 ↓
validated value
 ↓
req.validatedQuery
```

---

# 36. `abortEarly: false`

Imagine the client sends:

```http
?page=hello&limit=-50&status=unknown
```

There are three problems.

If validation stops at the first error, the client may only see:

```text
page is invalid
```

With:

```js
abortEarly: false
```

the validator can report multiple problems.

Conceptually:

```json
{
  "errors": [
    {
      "field": "page",
      "message": "must be a number"
    },
    {
      "field": "limit",
      "message": "must be greater than or equal to 1"
    },
    {
      "field": "status",
      "message": "must be one of pending or completed"
    }
  ]
}
```

This is much nicer for frontend development.

---

# 37. `stripUnknown`

Suppose:

```http
GET /todos?page=2&limit=20&random=hello
```

If your policy is to strip unknown fields:

```js
stripUnknown: true
```

then:

```js
{
  page: 2,
  limit: 20
}
```

reaches your application.

But remember:

> **Strip vs reject is an API design decision.**

For public APIs, strict rejection can often be easier to reason about.

Don't blindly enable every option without understanding its effect.

For example:

```text

limit
min: 1
max: 100

max length: 100

status
allowed values only

allowed values only
```

This turns vague input into a predictable contract.

# 39. Query validation + pagination

Let's build the full example.

```http

```

Beautiful separation.

# 44. What validation does NOT do

This is very important.

Query validation does **not** mean:

> "The user is allowed to access these records."

For example:

```http
GET /todos?userId=anotherUser
```

Even if:

```text
userId
```

is a valid MongoDB ObjectId, that doesn't mean the user is allowed to query that user's data.

That's authorization/ownership.

Your previous Phase 15 work is what handles this.

---

# 45. Validation does not replace authorization

Think:

```text
Validation
    ↓
"Is userId structurally valid?"

Authorization
    ↓
"Is this user allowed to access that user's records?"
```

Both are necessary.

---

# 46. Validation does not replace security middleware

Similarly:

```text
Validation
    ↓
Is the input acceptable?

Authentication
    ↓
Who is this user?

Authorization
    ↓
What can this user access?

Security middleware
    ↓
How do we defend the application?
```

These layers solve different problems.

# 48. A professional query object

Eventually, instead of letting your service understand HTTP syntax:

```js
{
  page: 2,
  limit: 20,
  sort: "-created"
}
```

you can give it a more application-oriented structure:

```js
{
  pagination: {
    page: 2,
    limit: 20
  },

  filter: {
    status: "pending"
  },

  search: "mongo",

  sort: {
    createdAt: -1,
    _id: -1
  }
}
```

Now the service doesn't care about:

```text
?page=2
&limit=20
&sort=-created
```

That's just HTTP syntax.

This is an important architectural improvement.

# 50. Common mistakes

## Mistake 1 — Trusting query values

```js
const limit = req.query.limit;
```

and immediately querying MongoDB.

❌ Don't.

---

## Mistake 2 — No maximum limit

```text
limit=100000000
```

❌ Dangerous for resources.

---

## Mistake 3 — Only validating the request body

```text
POST body → validated
GET query → ignored
```

❌ Query parameters also need validation.

---

## Mistake 4 — Mixing validation and business logic

```js
if (!status) ...
if (!authorized) ...
if (!todoExists) ...
```

all inside one controller.

❌ Responsibilities become mixed.

---

## Mistake 5 — Passing raw `req.query` everywhere

```js
service.getTodos(req.query);
```

❌ Keeps HTTP concerns inside deeper layers.

---

## Mistake 6 — Allowing arbitrary sort fields

```text
sort=passwordHash
```

❌ Use an allow-list.

## 🧪 Practice Task

Before moving to **18.11**, try designing a Joi schema for:

```http
GET /api/v1/products
    ?page=2
    &limit=20
    &category=electronics
    &minPrice=500
    &maxPrice=50000
    &sort=-price
    &search=laptop
```

Your rules should be roughly:

```text
page
→ integer, minimum 1

limit
→ integer, 1–100

category
→ string

minPrice
→ number, >= 0

maxPrice
→ number, >= 0

sort
→ only allowed values

search
→ string, trimmed, reasonable maximum length
```

The key challenge is to make the **validated output useful to the service**, rather than simply checking whether the input "looks okay."
