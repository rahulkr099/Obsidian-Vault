# 1. First: Why do indexes exist?

Imagine your MongoDB collection contains:

```text
todos
├── Todo 1
├── Todo 2
├── Todo 3
├── ...
└── Todo 1,000,000
```

Now the user requests:

```http
GET /todos?status=pending
```

MongoDB needs to find documents where:

```js
{
  status: "pending"
}
```

Without a suitable index, MongoDB may need to examine a huge number of documents.

Conceptually:

```text
No index

MongoDB
   ↓
Todo 1       check
Todo 2       check
Todo 3       check
Todo 4       check
...
Todo 1,000,000
```

That's expensive.

An index gives MongoDB a faster structure for finding matching documents.

```text
With index

status index
     ↓
pending ─────────→ matching documents
completed ───────→ matching documents
```

The key idea:

> **An index is an additional data structure that helps MongoDB find documents more efficiently.**

# 3. Collection scan vs index scan

MongoDB can execute a query using different strategies.

### Collection scan

Conceptually:

```text
COLLSCAN
```

MongoDB examines documents in the collection.

### Index scan

Conceptually:

```text
IXSCAN
```

MongoDB uses an index to locate relevant documents.

You should remember:

```text
COLLSCAN
    ↓
potentially examine many documents

IXSCAN
    ↓
use index to narrow the search
```

But don't make the mistake of thinking:

> "IXSCAN always means fast."

It doesn't.

An index can still be poorly designed or ineffective for a particular query.

We'll get deeper into that in **18.13 Performance Considerations**.

# 4. A simple MongoDB index

Suppose your Todo schema contains:

```js
{
  title: "Learn MongoDB",
  status: "pending",
  userId: "...",
  createdAt: ...
}
```

You frequently query:

```js
Todo.find({
  status: "pending"
});
```

You could create:

```js
todoSchema.index({
  status: 1
});
```

Here:

```text
1
```

means ascending index order.

You may also see:

```js
todoSchema.index({
  status: -1
});
```

where:

```text
-1
```

means descending order.

For a simple equality query on `status`, the direction often isn't the important part. Direction becomes more important when sorting and when designing compound indexes.

---

# 5. Why not index every field?

This is one of the most important lessons.

You might think:

```text
"Indexes make queries faster."

Therefore:

"Put an index on everything."
```

❌ Wrong.

Indexes have costs.

When you insert:

```js
Todo.create(...)
```

MongoDB has to maintain the relevant indexes too.

So:

```text
More indexes
     ↓
More index storage
     ↓
More write/maintenance cost
```

Therefore:

> **Indexes should support real query patterns, not be added randomly.**

---

# 6. Indexes are a trade-off

Think:

```text
                INDEX
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
      Benefits             Costs
        │                   │
        ├─ faster reads     ├─ storage
        ├─ faster sorting   ├─ write overhead
        └─ better lookup    └─ maintenance
```

So database design is about balance.

# 11. Sorting and indexes

Now consider:

```http
GET /todos?sort=-created
```

which becomes something like:

```js
Todo.find(...)
    .sort({
      createdAt: -1
    });
```

An index can also help with sorting.

For example:

```js
todoSchema.index({
  createdAt: -1
});
```

Now MongoDB has an ordered structure based on `createdAt`.

This can reduce the amount of work required for certain sorted queries.

```text
    userId

    status
```

A single-field index on:

```js

```

might not fully support the entire query efficiently.

# 14. Index declaration in Mongoose

You can define an index at schema level:

```js
const todoSchema = new mongoose.Schema(
  {
    title: String,
    status: String,
    userId: mongoose.Schema.Types.ObjectId
  },
  {
    timestamps: true
  }
);

todoSchema.index({
  userId: 1
});
```

Now the schema declares:

```text
Todo
 ↓
userId index
```

Mongoose can use the schema's index definitions when indexes are created/synchronized according to your MongoDB/Mongoose deployment configuration.

---

# 15. Index vs field

An index doesn't change your document.

Your document remains:

```js
{
  _id: "...",
  title: "Learn MongoDB",
  status: "pending",
  userId: "...",
  createdAt: "..."
}
```

The index is a separate structure associated with the collection.

Think:

```text
Collection
│
├── Documents
│
└── Indexes
      ├── _id index
      ├── userId index
      └── createdAt index
```

---

# 16. MongoDB already creates an `_id` index

This is important.

MongoDB automatically maintains an index on:

```text
_id
```

So:

```js
Todo.findById(todoId)
```

can efficiently use the `_id` index.

You don't need to manually create:

```js
todoSchema.index({
  _id: 1
});
```

just for the normal `_id` index.

---

# 17. Unique indexes

Indexes can also enforce uniqueness.

For example:

```js
const userSchema = new mongoose.Schema({
  email: {
    type: String,
    unique: true
  }
});
```

This creates a unique index for the email field when indexes are properly created.

Conceptually:

```text
email
 ↓
unique index
```

Then:

```text
rahul@example.com
```

can exist once.

Trying to insert another document with the same unique value results in a duplicate-key error.

---

# 18. Unique is not just validation

This is a subtle but important point.

Many beginners think:

```js
email: {
  unique: true
}
```

means:

> "Mongoose validation will check uniqueness."

That's not the right mental model.

`unique` is fundamentally a database index constraint.

So you should still design your application to handle duplicate-key errors.

For example:

```text
Signup
  ↓
User service
  ↓
Repository
  ↓
MongoDB
  ↓
duplicate key
  ↓
error handling
  ↓
409 Conflict
```

This connects nicely with the consistent API error architecture from Phase 16.

# 19. Indexing search fields

Now let's revisit **18.7 Search**.

Suppose we do:

```js
Todo.find({
  title: {
    $regex: "mongo",
    $options: "i"
  }
});
```

A beginner might say:

> "Let's add an index on title."

But that doesn't automatically mean the regex query becomes efficient.

Especially with:

```text
contains search
```

such as:

```text
%mongo%
```

or regex patterns that don't have a useful prefix.

So:

> **Indexing is query-pattern dependent.**

Don't assume:

```text
index(field)
=
every query involving field becomes fast
```

It doesn't.

---

# 20. Prefix search vs contains search

Consider:

```text
"mongo..."
```

versus:

```text
"...mongo..."
```

A B-tree-style index can be much more useful for certain prefix patterns than arbitrary substring searches.

For example, a query conceptually equivalent to:

```text
starts with "mon"
```

is very different from:

```text
contains "mon" anywhere
```

That's one reason search requirements sometimes need different database/search strategies.

Don't try to solve every search problem by adding ordinary indexes.

# 21. Indexing status

Suppose your Todo API frequently does:

```js
Todo.find({
  status: "pending"
});
```

You might create:

```js
todoSchema.index({
  status: 1
});
```

This can be useful.

But now imagine:

```text
90% of todos = pending
10% = completed
```

The index may be less selective than if the values were distributed differently.

This introduces another important database concept:

> **Selectivity.**

---

# 22. What is selectivity?

Very simply:

> How much does a field narrow down the possible documents?

Suppose you have:

```text
1,000,000 documents
```

Query:

```text
status = "pending"
```

and:

```text
900,000 documents are pending
```

The field doesn't narrow the dataset very much.

But:

```text
userId = one specific user
```

might return:

```text
500 documents
```

That is much more selective.

So:

```text
userId
```

may be a much more useful query field in your application than:

```text
status
```

depending on the query pattern.

---

# 23. Indexes don't magically fix bad queries

Suppose you write:

```js
Todo.find({
  userId
})
```

and then retrieve:

```text
500,000 documents
```

An index can help MongoDB locate them, but you are still asking the database for 500,000 documents.

The better solution might involve:

```text
pagination
+
projection
+
appropriate indexes
+
reasonable limits
```

This is why Phase 18 is being taught in this order.

# 24. Pagination + indexes

You learned:

```http
GET /todos?page=2&limit=20
```

which becomes:

```js
skip(20)
.limit(20)
```

But here's an important performance warning:

> Large `skip()` values can become expensive.

For example:

```text
page=1
skip=0

page=10
skip=180

page=1000
skip=19980

page=100000
skip=1999980
```

At very large offsets, MongoDB may still need to walk past many records.

That's one reason cursor pagination can be preferable for certain large datasets.

You already learned the conceptual difference in **18.2**.

# 25. Indexes and cursor pagination

Suppose your cursor is based on:

```text
createdAt
_id
```

An appropriate index can make this pattern very efficient.

For example:

```js
{
  userId: 1,
  createdAt: -1,
  _id: -1
}
```

This is already moving into **compound indexes**, so we'll study the exact design in 18.12.

For now remember:

```text
Cursor pagination
       +

       ↓
Potentially excellent performance
```

# 26. How do we know whether MongoDB uses an index?

This is where:

```text
explain()
```

becomes important.

For example:

```js
Todo.find({
  userId: someUserId
}).explain("executionStats");
```

MongoDB can provide information about how it executed the query.

You might see stages such as:

```text
COLLSCAN
```

or:

```text
IXSCAN
```

---

# 27. `COLLSCAN`

Conceptually:

```text
COLLSCAN
```

means MongoDB scanned the collection.

Example:

```text
Query
 ↓
Collection
 ↓
Document 1
Document 2
Document 3
...
```

This doesn't automatically mean:

> "Your query is bad."

For a tiny collection, a collection scan might be perfectly reasonable.

That's another important lesson:

> **Performance decisions depend on workload and data size.**

---

# 28. `IXSCAN`

Conceptually:

```text
IXSCAN
```

means MongoDB is scanning an index.

For example:

```text
userId index
     ↓
requested userId
     ↓
matching records
```

This can avoid examining unrelated documents.

But again:

```text
IXSCAN ≠ automatically optimal
```

You need to examine the actual execution plan.

---

# 29. `executionStats`

One useful mode is:

```js
.explain("executionStats")
```

This can help you understand things such as:

```text
How many documents were examined?
How many documents were returned?
How many index keys were examined?
Which execution stage was used?
```

One especially useful comparison is:

```text
docs examined
vs
docs returned
```

Suppose:

```text
Documents returned: 20
Documents examined: 500,000
```

That's a warning sign.

If instead:

```text
Documents returned: 20
Documents examined: 25
```

that's much more promising.

---

# 30. A simple performance mental model

Think:

```text
Query
 ↓
How many documents must MongoDB examine?
 ↓
How many does it return?
```

For:

```text
20 results
```

examining:

```text
20–100 documents
```

may be reasonable.

Examining:

```text
1,000,000 documents
```

is much more concerning.

This is not an absolute rule, but it's a useful intuition.

# 31. Don't create indexes based on guesses

A common beginner approach:

```text
"This field is queried."

→ create index
```

A better engineering approach:

```text
1. Identify important query patterns
2. Measure them
3. Inspect explain()
4. Design index
5. Measure again
6. Keep only useful indexes
```

That's a much more professional workflow.

# 34. Indexes and writes

Let's say you have:

```text
1 million todos
```

and:

```text
8 indexes
```

Every insert/update that affects indexed fields may require index maintenance.

So:

```text
INSERT
  ↓
Document written
  +
Relevant indexes updated
```

More indexes mean more work.

This matters for high-write applications.

---

# 35. Read-heavy vs write-heavy systems

Different applications have different priorities.

### Read-heavy

For example:

```text
content platform
catalog
news website
```

You may invest heavily in read optimization.

### Write-heavy

For example:

```text
event ingestion
telemetry
logging system
```

Too many indexes can become expensive.

So index design depends on workload.

# 36. Index storage matters

Indexes consume disk/memory resources.

Conceptually:

```text
MongoDB
├── Documents
└── Indexes
    ├── _id
    ├── userId
    ├── createdAt
    └── ...
```

As indexes increase:

```text
Storage ↑
Memory pressure ↑
Write maintenance ↑
```

Therefore:

> **An index is not free.**


# 41. Indexes and security

Indexes themselves aren't an authorization mechanism.

Never think:

```text
"I indexed userId, therefore users are isolated."
```

No.

Security still comes from the query:

```js
Todo.findOne({
  _id: todoId,
  userId: authenticatedUserId
});
```

The index merely helps execute the query efficiently.

Remember:

```text
Authorization
→ correctness/security

Index
→ performance
```

Different responsibilities.

# 45. A simple index checklist

Before adding an index, ask:

### 1. Is this field frequently queried?

```text
userId
```

### 2. Is it selective enough?

Does it narrow down the data?

### 3. Is sorting involved?

```text
createdAt
```

### 4. Are multiple fields involved?

```text
userId + status + createdAt
```

→ maybe compound index.

### 5. Is the query actually slow?

Measure first.

### 6. What does `explain()` say?

Don't guess.

### 7. Is the write overhead acceptable?

Every index has a cost.

# 48. Interview-style questions

### Q1. What is a MongoDB index?

An additional data structure that helps MongoDB locate and/or order documents more efficiently for supported query patterns.

### Q2. Does an index always make queries faster?

No.

An index has overhead and may not help a particular query.

### Q3. What is `COLLSCAN`?

A collection scan where MongoDB examines documents in the collection.

### Q4. What is `IXSCAN`?

An execution stage indicating that MongoDB is scanning an index.

### Q5. Why not index every field?

Indexes consume storage and add write/maintenance overhead.

### Q6. How do you investigate whether an index helps?

Use query plans such as:

```js
.explain("executionStats")
```

and examine what MongoDB actually does.

### Q7. Why is `_id` special?

MongoDB automatically creates an index for `_id`.
