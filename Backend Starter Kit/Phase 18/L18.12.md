# Lesson 18.12 — Compound Indexes

Now we move from **single-field indexes** to one of the most important MongoDB performance concepts:

> **Compound indexes = one index built using multiple fields.**

Your Phase 18 roadmap puts this immediately after MongoDB indexes:

```text

18.13 Performance considerations

```

---

# 1. Why do we need compound indexes?

In the previous lesson, we had a query like:

```js
Todo.find({
  userId,
  status: "pending"
})
.sort({
  createdAt: -1
})
.limit(20);
```

Notice that this query uses **three fields**:

```text
Filter:
    userId
    status

Sort:
    createdAt
```

A single-field index such as:

```js
{
  userId: 1
}
```

only focuses on:

```text
userId
```

But our query has a larger pattern:

```text
userId
+
status
+
createdAt
```

That's where a compound index can help.

---

# 2. What is a compound index?

A compound index contains multiple fields.

For example:

```js
todoSchema.index({
  userId: 1,
  status: 1,
  createdAt: -1
});
```

This is one index containing:

```text
userId
status
createdAt
```

in that **specific order**.

That last part is extremely important.

---

# 3. Field order matters

These two indexes are not the same:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

and:

```js
{
  status: 1,
  userId: 1,
  createdAt: -1
}
```

The order changes how MongoDB can use the index.

Think of a compound index as a sorted structure:

```text
userId
   ↓
status
   ↓
createdAt
```

MongoDB can efficiently navigate this structure according to the index ordering.

So:

> **Don't randomly choose the order of fields in a compound index.**

---

# 4. Real-world analogy

Imagine a library catalog sorted by:

```text
Country → City → Author → Book
```

If you ask:

```text
Country = India
```

the catalog can quickly narrow down to India.

Then:

```text
Country = India
City = Delhi
```

narrows it further.

Then:

```text
Country = India
City = Delhi
Author = XYZ
```

narrows it even further.

But if you only know:

```text
Author = XYZ
```

the catalog isn't necessarily organized primarily around authors.

That's similar to the idea behind compound indexes.

---

# 5. The prefix idea

Suppose we have:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

The important prefix is:

```text
userId
```

Then:

```text
userId + status
```

Then:

```text
userId + status + createdAt
```

These are progressively longer prefixes.

Conceptually:

```text
[userId]
[userId, status]
[userId, status, createdAt]
```

This is why index order matters so much.

---

# 6. Query using the first field

Index:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

Query:

```js
Todo.find({
  userId
});
```

This is a good match for the index prefix:

```text
userId
```

---

# 7. Query using first two fields

Query:

```js
Todo.find({
  userId,
  status
});
```

This matches:

```text
userId
+
status
```

which is the first two fields of the index.

Good.

---

# 8. Query using all three

Query:

```js
Todo.find({
  userId,
  status
})
.sort({
  createdAt: -1
});
```

Now we're using:

```text
userId
status
createdAt
```

which aligns with the full compound index:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

This is exactly the type of query pattern we want to optimize.

---

# 9. What about only `status`?

Suppose we have:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

and query:

```js
Todo.find({
  status: "pending"
});
```

Notice:

```text
Index starts with:
userId

Query starts with:
status
```

The query does not match the index's leading prefix in the same useful way.

This is the reason you should remember:

> **A compound index is not simply "an index containing these fields." Field order defines how the index can be used.**

---

# 10. The leftmost-prefix rule

You'll hear this concept often:

> **Compound indexes are generally most useful when queries use the index's leftmost fields.**

For:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

the leftmost prefixes are:

```text
userId
userId + status
userId + status + createdAt
```

Think:

```text
[userId]
      ↓
[userId, status]
      ↓
[userId, status, createdAt]
```

The first field is the leftmost field.

---

# 11. Why does this matter for our Todo API?

Our Todo API is user-scoped.

A common query might be:

```js
Todo.find({
  userId
})
.sort({
  createdAt: -1
})
.limit(20);
```

Another:

```js
Todo.find({
  userId,
  status: "pending"
})
.sort({
  createdAt: -1
})
.limit(20);
```

So an index like:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

is worth considering.

But don't immediately assume it's the perfect index.

You must consider your **actual workload**.

That's the performance lesson coming next.

---

# 12. Equality fields vs sorting fields

A very useful starting heuristic for compound indexes is:

```text
Equality filters
        ↓
Sort fields
        ↓
Range fields
```

For example:

```js
Todo.find({
  userId,
  status: "pending"
})
.sort({
  createdAt: -1
});
```

We have:

```text
Equality:
userId
status

Sort:
createdAt
```

So a natural candidate is:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

This is a useful rule of thumb, not a universal law.

---

# 13. Why equality fields usually come first

Suppose:

```text
userId = Rahul
status = pending
```

These conditions narrow the dataset.

Then:

```text
createdAt DESC
```

organizes the matching results.

Conceptually:

```text
All Todos
   ↓
userId = X
   ↓
status = pending
   ↓
createdAt descending
   ↓
first 20
```

This can be an efficient access pattern.

---

# 14. Equality + sorting example

Consider:

```js
Todo.find({
  userId: "U1",
  status: "pending"
})
.sort({
  createdAt: -1
})
.limit(20);
```

Candidate index:

```js
todoSchema.index({
  userId: 1,
  status: 1,
  createdAt: -1
});
```

Conceptually:

```text
INDEX
────────────────────────────
userId
  └── status
        └── createdAt DESC
```

MongoDB can navigate the structure based on the query.

---

# 15. Why `_id` sometimes appears in the sort

Suppose many Todos have exactly the same:

```text
createdAt
```

Then:

```js
.sort({
  createdAt: -1
})
```

doesn't give a fully deterministic ordering for equal timestamps.

A common technique is:

```js
.sort({
  createdAt: -1,
  _id: -1
});
```

Then the index might be:

```js
{
  userId: 1,
  createdAt: -1,
  _id: -1
}
```

This gives us a stable tie-breaker.

This becomes especially useful with cursor pagination.

---

# 16. Connection to cursor pagination

Remember your earlier pagination lessons.

Suppose we use a cursor:

```text
createdAt
+
_id
```

We might query for records after a particular position.

A suitable compound index can make this pattern much more efficient.

Conceptually:

```text
userId
   ↓
createdAt DESC
   ↓
_id DESC
```

Then:

```text
user's todos
     ↓
newest first
     ↓
continue from cursor
```

This is one reason compound indexes become extremely important in real-world APIs.

---

# 17. Compound indexes aren't only for filtering

A compound index can help with:

```text
Filtering
+
Sorting
```

It can also support:

```text
Filtering
+
Filtering
+
Sorting
```

or:

```text
Equality
+
Range
+
Sorting
```

depending on the query and index structure.

So don't think:

```text
compound index = multiple filters
```

It's broader than that.

---

# 18. A common mistake

Suppose your query is:

```js
Todo.find({
  userId,
  status
})
.sort({
  createdAt: -1
});
```

A beginner may create three separate indexes:

```js
{
  userId: 1
}

{
  status: 1
}

{
  createdAt: -1
}
```

That might help some queries, but it is not automatically equivalent to:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

Why?

Because the compound index represents the **combined query pattern**.

---

# 19. Three single-field indexes vs one compound index

Imagine:

```text
Index A
userId

Index B
status

Index C
createdAt
```

versus:

```text
Index D
userId + status + createdAt
```

They provide different capabilities.

The compound index can represent the relationship/order:

```text
userId
  → status
      → createdAt
```

That's why compound indexes should be designed around actual queries.

---

# 20. Should we delete all single-field indexes?

No.

For example, maybe you frequently have:

```js
Todo.find({
  userId
});
```

and:

```js
Todo.find({
  status
});
```

and:

```js
Todo.find({
  userId,
  status
})
.sort({
  createdAt: -1
});
```

You may need different indexes depending on workload.

The goal isn't:

> "Use as few indexes as possible."

The goal is:

> **Use the smallest useful set of indexes that supports your important queries without unnecessary write/storage cost.**

---

# 21. Index design is workload-driven

Imagine these are your top queries:

```text
Q1:
userId → newest todos

Q2:
userId + status → newest todos

Q3:
status → newest todos
```

One index may not perfectly support all three.

You need to evaluate:

```text
frequency
+
data size
+
selectivity
+
latency
+
write cost
```

This is real backend/database engineering.

---

# 22. Index field direction

You can write:

```js
{
  userId: 1,
  createdAt: -1
}
```

The directions mean:

```text
userId → ascending
createdAt → descending
```

For equality fields such as:

```text
userId = X
```

the direction often doesn't matter much.

For sort fields, direction becomes important.

---

# 23. Sort direction and compound indexes

Suppose:

```js
{
  userId: 1,
  createdAt: -1
}
```

and:

```js
.sort({
  createdAt: -1
});
```

This aligns naturally.

If you request:

```js
.sort({
  createdAt: 1
});
```

MongoDB may still be able to use the index by scanning it in the opposite direction in some cases.

So don't reduce the concept to:

```text
index -1
→ only supports sort -1
```

The actual behavior is more nuanced.

The key is that compound sort patterns and index ordering need to be compatible.

---

# 24. The ESR idea

You may encounter a useful MongoDB index-design guideline called **ESR**:

```text
E = Equality
S = Sort
R = Range
```

A common starting pattern is:

```text
Equality
   ↓
Sort
   ↓
Range
```

For example:

```js
Todo.find({
  userId,
  status,
  createdAt: {
    $lt: someDate
  }
})
.sort({
  title: 1
});
```

The exact optimal index requires deeper analysis, but ESR gives you a useful starting point.

---

# 25. Equality example

```js
{
  userId: "U1",
  status: "pending"
}
```

These are equality conditions:

```text
userId = U1
status = pending
```

Candidate beginning:

```js
{
  userId: 1,
  status: 1
}
```

---

# 26. Range example

Now:

```js
{
  createdAt: {
    $gte: startDate,
    $lt: endDate
  }
}
```

is a range condition.

So:

```text
createdAt >= X
createdAt < Y
```

is different from:

```text
createdAt = X
```

This distinction matters when designing compound indexes.

---

# 27. Why range position matters

Suppose:

```js
{
  userId: 1,
  status: 1,
  createdAt: 1
}
```

and query:

```js
{
  userId,
  status,
  createdAt: {
    $gte: startDate
  }
}
```

This can be a strong index pattern because:

```text
Equality
Equality
Range
```

aligns naturally with the index.

But once you introduce a range field, later index fields may not be used in exactly the same way for narrowing/sorting.

This is one reason index design becomes more advanced as queries become complex.

# 28. Example: Product API

Let's move beyond Todos.

Suppose:

```text
GET /products
?category=electronics
&minPrice=500
&maxPrice=50000
&sort=-price
```

The query might become:

```js
Product.find({
  category: "electronics",

    $gte: 500,
    $lte: 50000
  }

.sort({
  price: -1
});
```

Fields:

```text
Equality:
category

Range:
price

Sort:
price
```

Now index design becomes a real engineering decision.

This is exactly why you shouldn't memorize one fixed index pattern.

# 29. Index design starts from query shape

This phrase is worth remembering:

> **Design indexes around query shapes, not individual fields.**

Query shape:

```text
filter fields
+
sort
+
range
+
projection
+
limit
```

For example:

```text
userId equality
status equality
createdAt sort
limit 20
```

is a query shape.

You want your indexes to support important query shapes.

Suppose your query only needs:


In some situations, MongoDB may be able to satisfy the query largely from the index itself.

This is related to **covered queries**.

For now, don't go too deep into it.

Just remember:

```text
Index
+

+
```

# 33. Which index should come first?

Suppose we have:

```text
Query A:
userId + createdAt

Query B:
userId + status + createdAt
```

You might wonder whether to use:

```js
{
  userId: 1,
  createdAt: -1
}
```

or:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

The answer depends on workload.

If Query A is extremely common and Query B is rare, a smaller index might be better.

If Query B dominates your workload, the second index may be more useful.

There is no universal:

```text
"best index"
```

without knowing the workload.

# 35. What happens if you add too many compound indexes?

Suppose:

```text
Index 1:
userId + createdAt

Index 2:
userId + status + createdAt

Index 3:
status + createdAt

Index 4:
category + price

Index 5:
userId + title

Index 6:
userId + updatedAt
```

Now you have a lot of structures to maintain.

Writes become more expensive.

Storage increases.

Index management becomes harder.

So don't create an index for every possible query combination.

Instead:

```text
Most important queries
        ↓
Measure
        ↓
Design indexes
```

---

# 36. The "index explosion" problem

Suppose you have:

```text
10 filterable fields
5 sortable fields
```

You cannot realistically create an index for every combination.

The number of combinations grows rapidly.

Therefore your API should also be designed thoughtfully.

For example, don't allow users to arbitrarily combine:

```text
10 filters
+
20 sorts
+
10 ranges
```

unless you have a strong reason.

This connects back to **query validation and allow-listing**.

# 37. API design influences database complexity

This is a powerful backend idea.

If your API supports:

```text

sort by anything
search anything
```

your database optimization problem becomes much harder.

But if your API intentionally supports:

```text

createdAt
```

you can design indexes around known query patterns.

So:

> **Good API constraints can make database performance easier to control.**

# 39. Indexing and allow-listed sorting

Suppose you allow:

```text

sort=-updated
```


# 43. What you should remember for interviews

### What is a compound index?

An index containing multiple fields in a specified order.

Example:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

### Why does order matter?

Because MongoDB uses the index according to its ordered structure, and the leading fields determine which query patterns can efficiently use it.

### What is the leftmost-prefix idea?

For:

```js
{
  userId: 1,
  status: 1,
  createdAt: -1
}
```

important prefixes are:

```text
userId
userId + status
userId + status + createdAt
```

### How should you initially think about compound index ordering?

A useful starting heuristic is:

```text
Equality
   ↓
Sort
   ↓
Range
```

but always verify against the actual workload.

### Should you create an index for every possible query?

No.

Indexes have storage and write-maintenance costs.
