# Lesson 18.13 — Performance Considerations

Today we answer the question:

> **"I created an index. How do I know whether it actually makes my query better?"**

Your Phase 18 roadmap defines **18.13 as Performance considerations**, immediately after indexes and compound indexes.

The biggest mistake here is **guessing**.

Professional backend development uses **measurement**.

---

# 1. The basic performance problem

Imagine:

```text
1,000,000 Todos
```

Your API asks:

```js
Todo.find({
  userId
});
```

Suppose the response contains:

```text
20 Todos
```

That sounds good.

But what if MongoDB had to examine:

```text
500,000 documents
```

to find those 20?

Then:

```text
20 returned
500,000 examined
```

is a warning sign.

This is why response size alone doesn't tell you whether a query is efficient.

---

# 2. The important numbers

When analyzing MongoDB query performance, pay attention to:

```text
documents examined
documents returned
index keys examined
execution time
execution stages
```

Conceptually:

```text
Query
  │
  ├── How many index entries did I inspect?
  ├── How many documents did I inspect?
  ├── How many documents did I return?
  └── How long did it take?
```

---

# 3. `explain()`

MongoDB provides:

```js
.explain()
```

to inspect how a query is executed.

For example:

```js
const result = await Todo.find({
  userId
}).explain("executionStats");
```

The important part is:

```text
executionStats
```

because we want actual execution information.

---

# 4. Why `executionStats`?

There are different explain modes.

For learning and performance investigation, you'll commonly use:

```js
.explain("executionStats")
```

It tells MongoDB:

> "Actually analyze the execution and give me statistics."

That gives you much more useful information than simply looking at the query.

---

# 5. Example

Suppose:

```js
Todo.find({
  userId
})
  .sort({
    createdAt: -1
  })
  .limit(20)
  .explain("executionStats");
```

You may see information conceptually like:

```text
executionStats
├── nReturned
├── executionTimeMillis
├── totalKeysExamined
├── totalDocsExamined
└── executionStages
```

Don't worry about memorizing every field yet.

The most important ones are:

```text
nReturned
totalDocsExamined
totalKeysExamined
executionTimeMillis
```

---

# 6. `nReturned`

Suppose:

```text
nReturned: 20
```

That means:

> The query ultimately returned 20 documents.

For pagination:

```js
.limit(20)
```

you'll often expect something around:

```text
nReturned: 20
```

unless fewer matching documents exist.

---

# 7. `totalDocsExamined`

Suppose:

```text
totalDocsExamined: 500000
```

while:

```text
nReturned: 20
```

That's potentially terrible.

You asked for:

```text
20
```

but MongoDB examined:

```text
500,000
```

documents.

Compare that with:

```text
nReturned: 20
totalDocsExamined: 22
```

That's much more promising.

---

# 8. A useful ratio

A simple mental model is:

```text
documents examined
-------------------
documents returned
```

Example:

```text
500,000 / 20
= 25,000
```

versus:

```text
22 / 20
= 1.1
```

The second query is clearly doing much less unnecessary document examination.

This isn't a formal performance metric you should blindly optimize for, but it's a great learning tool.

---

# 9. `totalKeysExamined`

When MongoDB uses an index, it examines index entries.

For example:

```text
totalKeysExamined: 25
```

means MongoDB examined 25 index keys.

Then:

```text
totalDocsExamined: 20
```

means it examined 20 actual documents.

So you can think:

```text
Index
 ↓
keys examined
 ↓
documents examined
 ↓
results returned
```

---

# 10. `COLLSCAN`

One of the most important things you'll see is:

```text
COLLSCAN
```

This means:

> MongoDB scanned the collection.

Conceptually:

```text
Collection
│
├── Document 1 → check
├── Document 2 → check
├── Document 3 → check
├── Document 4 → check
├── ...
└── Document 1,000,000 → check
```

This can be expensive for large collections.

---

# 11. `IXSCAN`

Another important stage is:

```text
IXSCAN
```

This means MongoDB is scanning an index.

Conceptually:

```text
Index
│
├── matching key
├── matching key
├── matching key
└── ...
```

Then MongoDB can fetch the associated documents.

So the rough difference is:

```text
COLLSCAN
    ↓
Collection → documents

IXSCAN
    ↓
Index → matching documents
```

---

# 12. But don't panic when you see `COLLSCAN`

This is important.

Seeing:

```text
COLLSCAN
```

doesn't automatically mean:

> "Something is broken."

Suppose your collection contains:

```text
50 documents
```

A collection scan may be perfectly fine.

MongoDB's query planner may decide:

> "The collection is tiny. Scanning it is cheaper than using an index."

That's reasonable.

---

# 13. Performance depends on scale

Consider:

### Development

```text
100 documents
```

A collection scan:

```text
very cheap
```

### Production

```text
10,000,000 documents
```

The same collection scan:

```text
potentially expensive
```

So always think:

```text
query
+
data size
+
workload
+
frequency
```

not just:

```text
"Does this query work?"
```

---

# 14. Query correctness vs query performance

These are different questions.

### Correctness

Does this:

```js
Todo.find({
  userId
});
```

return the correct user's Todos?

### Performance

Does MongoDB retrieve them efficiently?

You need both.

```text
Correct
   +
Efficient
   =
Good database query
```

---

# 15. The security connection

Remember authorization.

We want:

```js
Todo.find({
  _id: todoId,
  userId
});
```

The:

```text
userId
```

condition is there for **security/correctness**.

An index may then help this query execute efficiently.

So:

```text
userId filter
    ↓
Authorization boundary
    +
Database query optimization
```

One query can serve both purposes, but the responsibilities are different.

---

# 16. Example: bad vs better

Suppose:

```js
Todo.find({
  status: "pending"
});
```

returns:

```text
900,000 documents
```

from:

```text
1,000,000 documents
```

Even if you have:

```js
{
  status: 1
}
```

the query may not become dramatically better.

Why?

Because almost the entire collection matches.

This is where **selectivity** matters.

---

# 17. Selectivity again

Remember from 18.11:

> Selectivity means how effectively a condition narrows the dataset.

Suppose:

```text
1,000,000 Todos
```

### Query A

```text
status = pending
```

matches:

```text
900,000
```

Low selectivity.

### Query B

```text
userId = U123
```

matches:

```text
200
```

Much higher selectivity.

So `userId` can be a much more useful index field for that workload.

---

# 18. High-cardinality fields

Another useful idea is **cardinality**.

Suppose:

```text
status
```

has only:

```text
pending
completed
cancelled
```

That's low cardinality.

But:

```text
userId
```

might contain:

```text
100,000 different values
```

That's much higher cardinality.

High-cardinality fields can often be more selective.

Again:

> This doesn't mean "always index high-cardinality fields."

It means cardinality is one factor to consider.

---

# 19. Indexes don't fix returning huge datasets

Suppose you write:

```js
Todo.find({
  userId
});
```

and the user owns:

```text
500,000 Todos
```

An index can help locate those records.

But you are still asking your API to return 500,000 records.

That's an API design problem too.

Instead:

```js
Todo.find({
  userId
})
.limit(20);
```

and use pagination.

This is why your Phase 18 topics work together:

```text
Pagination
+
Filtering
+
Sorting
+
Indexes
```

---

# 20. `limit()` matters

Suppose:

```js
Todo.find({
  userId
})
.sort({
  createdAt: -1
})
.limit(20);
```

The application only needs:

```text
20
```

documents.

This is much better than:

```js
Todo.find({
  userId
});
```

followed by:

```js
results.slice(0, 20);
```

The latter potentially retrieves far more data than necessary.

Always try to push useful work down to the database.

---

# 21. Database pagination vs application pagination

### Bad pattern

```js
const todos = await Todo.find({
  userId
});

const page = todos.slice(0, 20);
```

Potential problem:

```text
MongoDB
 ↓
500,000 documents
 ↓
Node.js
 ↓
500,000 documents in memory
 ↓
take 20
```

### Better

```js
const todos = await Todo.find({
  userId
})
.limit(20);
```

Now:

```text
MongoDB
 ↓
20 relevant documents
 ↓
Node.js
```

Much better.

---

# 22. `skip()` performance

You've already learned:

```text
page
limit
skip
```

Suppose:

```js
.skip(20)
.limit(20)
```

That's usually fine.

But consider:

```js
.skip(1_000_000)
.limit(20)
```

MongoDB may still need to walk past a large number of matching records before reaching the desired position.

Conceptually:

```text
records
 ↓
skip 1,000,000
 ↓
return 20
```

This can become expensive.

---

# 23. Large offset pagination

Imagine:

```text
Page 1
skip 0

Page 100
skip 1,980

Page 10,000
skip 199,980

Page 100,000
skip 1,999,980
```

As the offset grows:

```text
skip ↑
work can ↑
```

This is one reason cursor-based pagination is useful for large datasets.

---

# 24. Cursor pagination

Instead of saying:

```text
"Skip 1,000,000 records."
```

we can say:

```text
"Start after this specific record."
```

For example:

```text
cursor:
createdAt = ...
_id = ...
```

Then the database can continue from a known position.

Conceptually:

```text
Page 1
 ↓
last record
 ↓
cursor
 ↓
Page 2
 ↓
last record
 ↓
cursor
 ↓
Page 3
```

This can scale better for large datasets.

---

# 25. Cursor pagination + compound index

Now everything we've learned connects.

Suppose:

```js
Todo.find({
  userId
})
.sort({
  createdAt: -1,
  _id: -1
})
.limit(20);
```

A candidate index:

```js
todoSchema.index({
  userId: 1,
  createdAt: -1,
  _id: -1
});
```

Now:

```text
Cursor pagination
        +
Compound index
        ↓
Efficient large dataset traversal
```

This is one of the most useful production patterns from this phase.

---

# 26. Sorting can become expensive

Suppose you query:

```js
Todo.find({
  userId
})
.sort({
  createdAt: -1
});
```

If MongoDB cannot use an appropriate index for the filtering/sorting pattern, it may need to perform additional sorting work.

Conceptually:

```text
Find matching documents
        ↓
Load results
        ↓
Sort them
        ↓
Return
```

With a suitable index:

```text
Index already ordered
        ↓
Traverse in desired order
        ↓
Return
```

That's one reason indexes can help sorting.

---

# 27. In-memory sorting

When the database can't efficiently use an index for the requested sort, it may need to perform a sort operation.

This can require memory and processing.

For large result sets, this can become expensive.

So if your API frequently does:

```text
filter X
+
sort Y
```

you should investigate whether your index supports that query shape.

---

# 28. Don't forget projection

Suppose your frontend only needs:

```text
title
createdAt
status
```

but your document contains:

```text
title
description
status
userId
metadata
attachments
history
...
```

You don't necessarily need to send everything.

You can use projection:

```js
Todo.find({
  userId
})
.select("title status createdAt");
```

Now:

```text
Database
 ↓
Only needed fields
 ↓
Node.js
 ↓
API
```

This can reduce data transfer and processing.

---

# 29. Smaller responses are better

Suppose:

```text
Todo document = 50 KB
```

and you return:

```text
100 documents
```

That's potentially:

```text
5 MB
```

for one request before considering JSON overhead and other factors.

If the frontend only needs:

```text
title
status
createdAt
```

don't blindly return the entire document.

Performance optimization happens at multiple levels:

```text
Database
 ↓
Query
 ↓
Projection
 ↓
API response
 ↓
Network
 ↓
Frontend
```

---

# 30. Indexes have write costs

Now the important trade-off.

Suppose you have:

```text
10 indexes
```

and execute:

```js
Todo.create(...)
```

MongoDB needs to maintain the relevant indexes.

Conceptually:

```text
INSERT
  │
  ├── document storage
  ├── index 1 update
  ├── index 2 update
  ├── index 3 update
  └── ...
```

Therefore:

```text
More indexes
    ↓
Potentially faster reads
    +
Potentially slower writes
    +
More storage
```

---

# 31. Read-heavy applications

Suppose you have:

```text
Product catalog
```

with:

```text
10 million products
```

and users constantly search and browse.

You might accept more indexes because:

```text
reads >>> writes
```

Optimizing reads can be very valuable.

---

# 32. Write-heavy applications

Now imagine:

```text
Telemetry ingestion
```

receiving:

```text
100,000 writes/sec
```

You need to be much more careful with indexes.

Because:

```text
writes ↑
indexes ↑
maintenance work ↑
```

The optimal design can be very different.

---

# 33. Don't optimize for milliseconds blindly

Suppose Query A:

```text
10 ms
```

and after optimization:

```text
7 ms
```

Is that worth:

```text
3 additional indexes?
```

Maybe not.

You should ask:

```text
How frequently is the query executed?
How much traffic does it receive?
How much storage does the index use?
What write cost does it introduce?
Does it affect user experience?
```

Optimization should solve a meaningful problem.

---

# 34. Measure before and after

This is the professional workflow.

### Before

```text
Query
 ↓
explain("executionStats")
 ↓
record:
docs examined
keys examined
execution time
```

### Add/improve index

```text
Index
 ↓
repeat query
 ↓
explain("executionStats")
```

### Compare

```text
Before              After
─────────────────────────────
docs examined       ↓
keys examined       ↓
execution time      ↓
```

If it doesn't improve the actual workload:

> Don't keep the index just because it looks good on paper.

---

# 35. Query planner

MongoDB has a query planner that considers possible execution strategies.

For a query, conceptually:

```text
Query
 ↓
Possible plans
 ├── COLLSCAN
 ├── Index A
 ├── Index B
 └── Index C
       ↓
Query planner
       ↓
Chosen plan
```

You don't manually tell MongoDB:

```text
"Always use Index B."
```

Normally MongoDB chooses a plan based on its internal planning mechanisms.

---

# 36. Why indexes can still be ignored

You may create:

```js
{
  status: 1
}
```

and MongoDB may still choose:

```text
COLLSCAN
```

Possible reasons include:

```text
collection is small
query isn't selective
index isn't useful for the sort
another plan is cheaper
query shape doesn't match the index well
```

So don't conclude:

> "MongoDB ignored my index, therefore MongoDB is broken."

Investigate the plan.

---

# 37. `hint()` — use carefully

MongoDB can be told to prefer a specific index using `hint()`.

Conceptually:

```js
Todo.find({
  userId
}).hint({
  userId: 1
});
```

But don't use `hint()` as your first solution.

It is generally better to:

```text
understand the query
+
understand the indexes
+
inspect explain()
```

before forcing a plan.

A forced hint can become problematic if the workload changes.

---

# 38. The performance investigation workflow

This is worth memorizing:

```text
1. Identify slow query
        ↓
2. Reproduce it
        ↓
3. Run explain("executionStats")
        ↓
4. Inspect:
   - execution stage
   - docs examined
   - keys examined
   - returned documents
   - execution time
        ↓
5. Identify bottleneck
        ↓
6. Design/change index
        ↓
7. Run explain() again
        ↓
8. Compare
        ↓
9. Keep the change only if useful
```

That's real database performance work.

# 39. Example: Todo query

Let's say:

```js
Todo.find({
  userId,
  status: "pending"
})
.sort({
  createdAt: -1
})
.limit(20);
```

Current execution:

```text
nReturned: 20
totalDocsExamined: 800000
totalKeysExamined: 0
```

This strongly suggests:

```text
COLLSCAN
```

or at least no useful index scan.

We might investigate a compound index:

```js
todoSchema.index({
  userId: 1,
  status: 1,
  createdAt: -1
});
```

Then test again.

---

# 40. After indexing

Suppose we get:

```text
nReturned: 20
totalDocsExamined: 20
totalKeysExamined: 21
```

That's much more promising.

Conceptually:

```text
Before

800,000 docs
      ↓
     20 results


After

~20 docs
      ↓
     20 results
```

That's the kind of improvement we're looking for.

These numbers are illustrative; don't treat them as a guaranteed result for every dataset.

---

# 41. Don't forget cache effects

Performance testing can also be affected by:

```text
memory
cache
database state
system load
network
concurrent requests
```

A query might be:

```text
first run: 30ms
later: 5ms
```

because data/index pages may already be cached.

So don't make major production decisions from one local timing measurement.

---

# 42. Development performance vs production performance

Your local environment:

```text
Linux Mint
localhost
small MongoDB dataset
one developer
```

doesn't represent:

```text
Production
 ↓
multiple application instances
 ↓
many concurrent users
 ↓
large database
 ↓
network latency
 ↓
real traffic
```

Therefore:

> Local testing is useful, but production-like workloads are much more valuable for serious optimization.

---

# 43. Avoid N+1 database queries

Another major performance issue isn't always solved by indexes.

Suppose you fetch:

```text
100 Todos
```

and then for each Todo:

```js
await User.findById(todo.userId);
```

You might accidentally create:

```text
1 query for Todos
+
100 user queries
=
101 queries
```

This is the classic **N+1 query problem**.

Indexes may make each individual query fast, but:

```text
101 queries
```

can still be expensive.

So performance isn't just:

```text
indexes
```

It's also:

```text
query count
+
query shape
+
data volume
+
indexes
```

---

# 44. Keep database calls intentional

Your service/repository architecture helps here.

Instead of:

```text
Controller
 ↓
loop
 ↓
query
 ↓
query
 ↓
query
 ↓
query
```

think carefully about:

```text
What data do I actually need?
Can I retrieve it efficiently?
Can I batch the operation?
Can I avoid unnecessary queries?
```

This is another benefit of the repository pattern you learned in Phase 13.

# 45. Don't blindly use `populate()`

In Mongoose, you may eventually use:

```js
.populate("user");
```

This can be convenient.

But don't assume:

```text
populate = free
```

It introduces additional database work.

For every relationship, ask:

```text
Do I actually need this data?
Can I select only needed fields?
How many records am I populating?
Is this endpoint frequently called?
```

Again:

```text
Convenience
vs
Performance
```

needs to be balanced.

# 46. Performance layers

For your backend, think about performance at several levels:

```text
                  PERFORMANCE
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      API            Database        Network
        │              │              │
      limit         indexes         response size
      pagination    query shape     compression
      validation    projections     payload
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                  Application
                       │
                 query count
                 business logic
                 caching
```

Indexes are only **one part** of performance.

---

# 47. Caching

Sometimes the correct optimization isn't an index.

Suppose you repeatedly request:

```text
GET /categories
```

and the categories rarely change.

You might use caching:

```text
Request
 ↓
Cache
 ├── HIT → return
 │
 └── MISS
       ↓
    MongoDB
       ↓
     Cache
       ↓
    Response
```

Then:

```text
Database load ↓
Response latency ↓
```

Caching is a separate topic, but keep it in your performance toolbox.

---

# 48. Database indexes vs caching

Use an index when:

```text
The database query itself needs to be efficient.
```

Use caching when:

```text
The same result is requested repeatedly
and can safely be reused.
```

They solve different problems.

---

# 49. A practical Todo performance strategy

For your Todo API, a sensible progression is:

### Step 1

Don't return everything.

```js
.limit(20)
```

### Step 2

Support pagination.

```text
page / cursor
```

### Step 3

Allow controlled filtering.

```text
status
```

### Step 4

Allow controlled sorting.

```text
createdAt
```

### Step 5

Create indexes based on real query patterns.

```text
userId
userId + status + createdAt
```

### Step 6

Use `explain()`.

### Step 7

Optimize based on evidence.

That's a much healthier approach than prematurely creating dozens of indexes.

# 52. Interview questions

### Q1. What is `COLLSCAN`?

A collection scan where MongoDB examines documents in the collection.

### Q2. What is `IXSCAN`?

An execution stage where MongoDB scans an index.

### Q3. What does `nReturned` tell you?

How many documents the query returned.

### Q4. What does `totalDocsExamined` tell you?

How many documents MongoDB examined while executing the query.

### Q5. What does `totalKeysExamined` tell you?

How many index keys MongoDB examined.

### Q6. Why can `skip()` become expensive?

Large offsets may require MongoDB to walk past many records before reaching the requested page.

### Q7. Why not create indexes on every field?

Indexes consume storage and increase write/maintenance overhead.

### Q8. How do you verify whether an index helps?

Use:

```js
.explain("executionStats")
```

and compare execution statistics before and after the index change.
