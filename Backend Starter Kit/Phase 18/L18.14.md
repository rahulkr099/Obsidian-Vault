# Lesson 18.14 — Build Reusable Query Utilities

In the previous lessons, we built the individual pieces:

```text
18.7  Pagination
18.8  Filtering
18.9  Search
18.10 Query validation
18.11 Indexes
18.12 Compound indexes
18.13 Performance
```

Now we solve a practical backend problem:

> **How do we avoid rewriting the same pagination, filtering, sorting, and search logic in every repository?**

The answer is **reusable query utilities**.

---

# 1. The problem: duplicated query logic

Imagine we have:

```text
TodoRepository
UserRepository
ProductRepository
OrderRepository
PostRepository
```

Without reusable utilities, you might repeatedly write:

```js
const page = Number(query.page) || 1;
const limit = Number(query.limit) || 20;
const skip = (page - 1) * limit;
```

Then again:

```js
const sort = query.sort || "-createdAt";
```

Then again:

```js
if (query.status) {
  filter.status = query.status;
}
```

And again for another repository.

This creates duplication.

---

# 2. Why duplication is dangerous

Suppose you have this code in five repositories:

```js
const limit = Math.min(
  Number(query.limit) || 20,
  100
);
```

Later you decide:

```text
maximum limit = 50
```

Now you have to remember to change it in five places.

You might change:

```text
TodoRepository
ProductRepository
OrderRepository
```

but forget:

```text
PostRepository
```

Now your API behaves differently depending on the resource.

That's a maintenance problem.

---

# 3. The goal

Instead of:

```text
TodoRepository
 ├── pagination logic
 ├── sorting logic
 └── filtering logic

ProductRepository
 ├── pagination logic
 ├── sorting logic
 └── filtering logic

OrderRepository
 ├── pagination logic
 ├── sorting logic
 └── filtering logic
```

we want:

```text
                  Query Utilities
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   Pagination       Sorting        Filtering
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                  Repositories
```

Now repositories can focus on:

> **What data should this resource query?**

while utilities handle:

> **How should query parameters be interpreted?**

---

# 4. Important architectural rule

Don't turn the utility into a giant "do everything" function.

Bad:

```js
buildEverything(query, model, user, permissions, search, pagination)
```

This becomes difficult to understand.

Instead, use small focused utilities:

```text
parsePagination()
parseSort()
parseFilters()
parseSearch()
```

Then compose them.

---

# 5. A useful folder structure

For our backend starter architecture, something like this works well:

```text
src/
├── controllers/
├── services/
├── repositories/
├── models/
├── middlewares/
├── utils/
│   └── query/
│       ├── pagination.js
│       ├── sorting.js
│       ├── filtering.js
│       ├── search.js
│       └── index.js
└── ...
```

The exact folder structure can vary.

The important idea is **separation of responsibilities**.

# 6. First utility: pagination

Let's create:

```text
utils/query/pagination.js
```

A simple utility:

```js
export function parsePagination(query) {
  const page = Math.max(
    Number(query.page) || 1,
    1
  );

  const limit = Math.min(
    Math.max(Number(query.limit) || 20, 1),
    100
  );

  const skip = (page - 1) * limit;

  return {
    page,
    limit,
    skip
  };
}
```

Now every repository doesn't need to repeat this logic.

---

# 7. Using it

Repository:

```js
import { parsePagination } from "../utils/query/pagination.js";

async function findTodos(query) {
  const { page, limit, skip } =
    parsePagination(query);

  return Todo.find()
    .skip(skip)
    .limit(limit);
}
```

Much cleaner.

---

# 8. But there is an important improvement

Should the repository trust:

```js
query.page
query.limit
```

directly?

No.

Remember our previous lesson:

> **Query parameters are untrusted input.**

Ideally:

```text
Request
   ↓
Validation
   ↓
Normalized query
   ↓
Repository
```

So the utility should not become an excuse to skip validation.

---

# 9. Validation vs parsing

These are related but different.

### Validation asks:

```text
Is this value allowed?
```

For example:

```text
limit = 20
```

is allowed.

But:

```text
limit = -100
```

isn't.

### Parsing asks:

```text
What JavaScript value should I use?
```

For example:

```text
"20"
```

becomes:

```js
20
```

So:

```text
Validation
+
Parsing
```

work together.

# 10. Second utility: sorting

Create:

```text
utils/query/sorting.js
```

We don't want to accept arbitrary sort fields.

Bad:

```js
const sort = query.sort;
```

because the client could request:

```text
sort=password
```

or any other field.

Instead, use an allow-list.

```js
const allowedSortFields = [
  "createdAt",
  "updatedAt",
  "title"
];
```

---

# 11. Parsing a sort parameter

Suppose the API accepts:

```text
?sort=-createdAt
```

We can parse it:

```js
export function parseSort(
  value,
  allowedFields
) {
  if (!value) {
    return {
      createdAt: -1
    };
  }

  const descending = value.startsWith("-");
  const field = descending
    ? value.slice(1)
    : value;

  if (!allowedFields.includes(field)) {
    return {
      createdAt: -1
    };
  }

  return {
    [field]: descending ? -1 : 1
  };
}
```

Now:

```text
-createdAt
```

becomes:

```js
{
  createdAt: -1
}
```

while:

```text
createdAt
```

becomes:

```js
{
  createdAt: 1
}
```

---

# 12. Why allow-listing matters

Imagine this request:

```text
GET /todos?sort=password
```

You don't want your API to blindly accept it.

Instead:

```js
const allowedSortFields = [
  "createdAt",
  "updatedAt"
];
```

Now only approved fields can be sorted.

This gives you:

```text
Security
+
Predictability
+
Performance control
```

Remember Lesson 18.12.


# 14. Third utility: filtering

Suppose our Todo API allows:

```text
?status=pending
```

We can build:

```js
export function parseTodoFilters(query) {
  const filter = {};

  if (query.status) {
    filter.status = query.status;
  }

  return filter;
}
```

Now repository code becomes:

```js
const filter = parseTodoFilters(query);

return Todo.find(filter);
```

---

# 15. Resource-specific filtering

Notice something important.

Pagination is generic:

```js
parsePagination()
```

Sorting can be mostly generic:

```js
parseSort()
```

But filtering is often **resource-specific**.

Todo might have:

```text
status
priority
completed
```

Product might have:

```text
category
price
brand
```

Order might have:

```text
status
paymentStatus
createdAt
```

So don't force every filter into one enormous generic function.

# 16. Generic vs domain-specific utilities

A useful rule:

### Generic

```text
pagination
sorting mechanics

```

### Domain-specific

```text
Todo filters
Product filters
Order filters
```

So:

```text
utils/query/
```

might contain:

```text
pagination.js
sorting.js
```

while:

```text
repositories/
```

or:

```text
features/todos/
```

contains:

```text
todoFilters.js
```

depending on your architecture.

# 17. Fourth utility: search

Suppose Todo supports:

```text
?q=learn
```

Maybe we want to search:

```text
title
description
```

We could create:

```js
export function buildTextSearch(
  search,
  fields
) {
  if (!search) {
    return {};
  }

  return {
    $or: fields.map((field) => ({
      [field]: {
        $regex: search,
        $options: "i"
      }
    }))
  };
}
```

Then:

```js
buildTextSearch(
  query.q,
  ["title", "description"]
);
```

could produce:

```js
{
  $or: [
    {
      title: {
        $regex: "learn",
        $options: "i"
      }
    },
    {
      description: {
        $regex: "learn",
        $options: "i"
      }
    }
  ]
}
```

---

# 18. But be careful with regex search

This is a very important production point.

A naive regex search such as:

```js
{
  title: {
    $regex: search,
    $options: "i"
  }
}
```

can become expensive for large datasets.

Especially:

```text
contains search
```

patterns.

So don't think:

```text
Reusable search utility
=
Fast search
```

It only gives you reusable **query construction**.

For serious search requirements, you may eventually use:

```text
MongoDB text indexes
Atlas Search
dedicated search systems
```

depending on the application.

---

# 19. Don't hide database behavior

A utility should make code easier to use without hiding important behavior.

Bad abstraction:

```js
queryTodos(query);
```

and nobody knows whether it:

```text
searches
filters
sorts
populates
joins
caches
paginates
```

Good abstraction:

```js
const pagination = parsePagination(query);

const sort = parseSort(
  query.sort,
  allowedSortFields
);

const filter = buildTodoFilters(query);
```

The repository can still clearly show what is happening.

---

# 20. Composing the utilities

Now let's put them together.

```js
async function findTodos(query) {
  const {
    page,
    limit,
    skip
  } = parsePagination(query);

  const filter = parseTodoFilters(query);

  const sort = parseSort(
    query.sort,
    ["createdAt", "updatedAt"]
  );

  return Todo.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit);
}
```

This is much easier to read.

The repository says:

```text
Build pagination
Build filter
Build sort
Execute query
```

instead of containing 50 lines of parsing logic.

---

# 21. Adding search

Now:

```js
async function findTodos(query) {
  const {
    page,
    limit,
    skip
  } = parsePagination(query);

  const filter = {
    ...parseTodoFilters(query),
    ...buildTextSearch(
      query.q,
      ["title", "description"]
    )
  };

  const sort = parseSort(
    query.sort,
    ["createdAt", "updatedAt"]
  );

  return Todo.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit);
}
```

The repository remains readable.

---

# 22. But there is a subtle problem

This:

```js
{
  ...parseTodoFilters(query),
  ...buildTextSearch(...)
}
```

looks simple.

But MongoDB query objects can become more complicated.

For example:

```js
{
  status: "pending",
  $or: [...]
}
```

is fine.

But as your query grows, blindly merging objects can create conflicts or unexpected behavior.

So reusable utilities need good boundaries.

---

# 23. Don't create a "God utility"

Avoid this:

```js
buildQuery({
  pagination,
  filters,
  search,
  sorting,
  population,
  permissions,
  authorization,
  projection,
  caching,
  aggregation
});
```

Eventually nobody understands what it does.

Instead:

```text
parsePagination()
parseSort()
buildTodoFilter()
buildSearch()
buildProjection()
```

Small utilities are easier to:

```text
test
debug
replace
reuse
understand
```

# 24. A query builder object

As your application grows, you can also introduce a small query-builder abstraction.

For example:

```js
class QueryBuilder {
  constructor(model, query) {
    this.model = model;
    this.query = query;
  }

  filter(filter) {
    this.model = this.model.find(filter);
    return this;
  }

  sort(sort) {
    this.model = this.model.sort(sort);
    return this;
  }

  paginate(skip, limit) {
    this.model = this.model
      .skip(skip)
      .limit(limit);

    return this;
  }

  exec() {
    return this.model.exec();
  }
}
```

Then:

```js
const result = await new QueryBuilder(
  Todo,
  query
)
  .filter(filter)
  .sort(sort)
  .paginate(skip, limit)
  .exec();
```

This is one possible abstraction.

But don't add it just because you can.

---

# 25. Abstraction has a cost

Compare:

### Simple

```js
Todo.find(filter)
  .sort(sort)
  .skip(skip)
  .limit(limit);
```

### Abstraction

```js
new QueryBuilder(Todo, query)
  .filter(filter)
  .sort(sort)
  .paginate(skip, limit)
  .exec();
```

The second can be useful when:

```text
many repositories
same query behavior
same conventions
```

But if your application is small:

```text
simple Mongoose queries
```

may actually be easier.

Remember:

> **Don't abstract code merely because it can be abstracted. Abstract repeated behavior that has a stable meaning.**

---

# 26. Reusable query options

A nice middle ground is a reusable function that returns query options.

For example:

```js
function buildPagination(query) {
  const page = Math.max(
    Number(query.page) || 1,
    1
  );

  const limit = Math.min(
    Number(query.limit) || 20,
    100
  );

  return {
    page,
    limit,
    skip: (page - 1) * limit
  };
}
```

Then:

```js
const { skip, limit } =
  buildPagination(query);
```

This is simple and explicit.

# 28. Parsing vs database execution

A good separation is:

```text
Query utility
     ↓
understands request parameters

Repository
     ↓
understands database

Service
     ↓
understands business rules
```

For example:

```js
const pagination =
  parsePagination(req.query);
```

Then:

```js
repository.findMany({
  filter,
  sort,
  pagination
});
```

The repository knows how to translate that into Mongoose.

---

# 29. A clean repository API

Instead of:

```js
repository.findTodos(req.query);
```

you can eventually use:

```js
repository.findMany({
  filter,
  sort,
  pagination
});
```

For example:

```js
const todos = await todoRepository.findMany({
  filter: {
    userId,
    status: "pending"
  },

  sort: {
    createdAt: -1
  },

  pagination: {
    skip: 0,
    limit: 20
  }
});
```

This is much cleaner architecturally.

---

# 30. Why this fits your Repository Pattern

You studied Repository Pattern in Phase 13.

The repository should abstract:

```text
database operations
```

So the service shouldn't need to know:

```text
Mongoose syntax
```

For example, service:

```js
const todos =
  await todoRepository.findMany({
    filter,
    sort,
    pagination
  });
```

Repository:

```js
async findMany({
  filter,
  sort,
  pagination
}) {
  return Todo.find(filter)
    .sort(sort)
    .skip(pagination.skip)
    .limit(pagination.limit);
}
```

This is a clean separation.

# 31. Service vs query utility

Don't confuse them.

### Query utility

```text
"How do I parse ?page=2&limit=20?"
```

### Service

```text
"Is this user allowed to retrieve these Todos?"
```

### Repository

```text
"How do I query MongoDB?"
```

So:

```text
Request
 ↓
Validation
 ↓
Query utilities
 ↓
Service
 ↓
Repository
 ↓
MongoDB
```

The exact placement can vary depending on your architecture, but the responsibilities should remain clear.

# 33. Centralize constants

Reusable utilities become even better when constants are centralized.

For example:

```js
export const PAGINATION_DEFAULTS = {
  page: 1,
  limit: 20,
  maxLimit: 100

```

Then:

```js
parsePagination()
```

uses those values.

Now you don't have:

```text
20

20
100
100
100
```

scattered throughout the project.

# 34. Don't over-centralize business rules

This is the opposite mistake.

Suppose Todo has:

```text
status:
pending
completed
archived
```

Don't put:

```js
TODO_ALLOWED_STATUSES
```

into a global generic query utility if only Todo understands those values.

Keep domain rules near the domain.

Think:

```text
Global behavior
     ↓
utils

Todo behavior
     ↓
Todo module
```

# 35. Type-safe / schema-safe query utilities

As your project becomes larger, validation schemas become valuable.

For example:

```text
query:
{
  page,
  limit,
  sort,
  status,
  q
}
```

can be validated before reaching your query builder.

Then your query utility can assume:

```text
page = valid integer
limit = valid integer
sort = approved value
status = approved value
```

This makes the utility simpler and safer.

---

# 36. Never let query utilities become security boundaries

This is important.

Suppose:

```js
parseFilters(query)
```

returns:

```js
{
  userId: query.userId
}
```

That may be dangerous.

A normal user shouldn't necessarily be able to say:

```text
GET /todos?userId=someoneElse
```

and retrieve another user's records.

Authorization should determine ownership.

For example:

```js
const filter = {
  userId: currentUser.id,
  ...safeTodoFilters
};
```

The server should control the ownership constraint.

---

# 37. User-controlled filters vs server-controlled filters

This distinction is excellent to remember.

### User-controlled

```text
status
priority
search
sort
```

### Server-controlled

```text
userId
tenantId
organizationId
permission boundaries
```

Don't let clients override server-controlled constraints.

For example, avoid:

```js
const filter = {
  userId: req.query.userId
};
```

when the endpoint is supposed to operate on the authenticated user's Todos.

Prefer:

```js
const filter = {
  userId: req.user.id
};
```

and then add safe user filters.

---

# 38. Reusable utilities should be boring

This sounds strange, but it's a good engineering principle.

A good utility should be:

```text
small
predictable
easy to test
easy to understand
```

For example:

```js
parsePagination(query)
```

should not:

```text
query MongoDB
check authorization
send HTTP responses
log users
modify documents
```

It should just:

```text
parse pagination
```

# 39. Unit testing utilities

Reusable utilities are excellent candidates for unit tests.

For example:

```js
describe("parsePagination", () => {
  it("uses defaults", () => {
    expect(
      parsePagination({})
    ).toEqual({
      page: 1,
      limit: 20,
      skip: 0
    });
  });
});
```

Then:

```js
it("calculates skip", () => {
  expect(
    parsePagination({
      page: 3,
      limit: 20
    }).skip
  ).toBe(40);
});
```

This is a major benefit of extracting logic.

# 41. Query utilities and performance

Remember Lesson 18.13.

If your utility allows:

```text
100 different sorts
50 different filters
20 search fields
```

you've potentially created many query shapes.

So reusable utilities should be designed with performance in mind.

For example:

```js
const allowedSortFields = [
  "createdAt",
  "updatedAt"
];
```

is much better than:

```js
const allowedSortFields =
  Object.keys(Todo.schema.paths);
```

because you explicitly control the supported query patterns.



```js
return Todo.find(filter)
  .sort(sort)
  .skip(pagination.skip)
  .limit(pagination.limit);
```

This is a very clean flow.

Imagine six months from now.

Your project has:

```text
30 repositories

100 query combinations
```

If query logic is duplicated everywhere:

```text
maintenance becomes painful
```

If common behavior is centralized:

```text
change once

```

That's the real value.

# 45. But don't abstract too early

There is an important balance.

If you only have:

```text
1 repository
1 endpoint
```

creating:

```text
12 query abstraction classes
```

is unnecessary.

Start simple.

When repetition becomes obvious:

```text
extract
```

This is often called:

> **Rule of Three**

If you see the same logic once:

```text
keep it simple
```

Twice:

```text
notice it
```

Three times:

```text
consider extracting it
```

It's not a strict law, but it's a useful guideline.

```js
  sort,
  pagination,
  projection
}) {
  return Todo.find(
    filter,
    projection
  )
    .sort(sort)
    .skip(pagination.skip)
    .limit(pagination.limit);
}
```

Then service can decide what fields are needed.

But again:

> Don't add every possible option until the application actually needs it.

Keep the interface focused.

# 48. What not to do

Avoid this:

```js
async findMany(options = {}) {
  // 300 lines of logic
}
```

with:

```text
filter
sort
pagination
search
populate
projection
aggregation
authorization
caching
transactions
logging
permissions
```

That's no longer a simple repository method.

Instead, keep responsibilities separated.

# 50. Interview questions

### Q1. Why create reusable query utilities?

To avoid duplicating common query parsing and construction logic across repositories/endpoints.

### Q2. Should query utilities handle authorization?

Generally, no. Authorization should remain an explicit application/business/security concern.

### Q3. Should all filtering be generic?

No. Generic utilities work well for common mechanics, while domain-specific filters should remain close to their resource/domain.

### Q4. Why allow-list sort fields?

To prevent uncontrolled query behavior and keep supported query shapes predictable.

### Q5. Should we create a query builder immediately?

No. Use one when repeated query composition justifies the abstraction.

### Q6. What is the benefit of small utilities?

They are easier to:

```text
understand
test
reuse
maintain
```
