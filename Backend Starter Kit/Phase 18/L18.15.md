# 1. The problem we're solving

Imagine your Todo API receives:

```http
GET /api/v1/todos
    ?page=2
    &limit=20
    &status=pending
    &sort=-createdAt
    &q=learn
```

We need to turn this:

```text
HTTP query parameters
```

into something the repository can understand:

```js
{
  filter: {
    userId: "...",
    status: "pending",
    $or: [...]
  },

  sort: {
    createdAt: -1
  },

  pagination: {
    skip: 20,
    limit: 20
  }
}
```

The question is:

> **Where should this transformation happen, and how should we design it so it stays clean?**

That's what a query builder can help with.

---

# 2. What is a Query Builder?

A query builder is an abstraction that helps construct a database query from smaller pieces.

Think:

```text
Request
   ↓
Query Builder
   ↓
Filter + Search + Sort + Pagination
   ↓
Repository
   ↓
MongoDB
```

Instead of writing:

```js
Todo.find(...)
  .sort(...)
  .skip(...)
  .limit(...);
```

in many places, we can have a structured way of building the query.

---

# 3. But don't confuse two things

There are actually two different ideas.

### Query parameter parser

Converts:

```text
?page=2&limit=20
```

into:

```js
{
  page: 2,
  limit: 20
}
```

### Database query builder

Converts:

```js
{
  filter,
  sort,
  pagination
}
```

into an actual Mongoose query.

These are different responsibilities.

A clean architecture keeps them separate.

---

# 4. Our architecture

A good flow is:

```text
HTTP Request
     ↓
Validation
     ↓
Query Parser
     ↓
Normalized Query
     ↓
Service
     ↓
Repository
     ↓
Query Builder
     ↓
Mongoose
     ↓
MongoDB
```

Notice something important:

**The query builder is not responsible for authentication or authorization.**

---

# 5. Why not put everything into the controller?

Bad:

```js
async getTodos(req, res) {
  const page = ...
  const limit = ...
  const status = ...
  const search = ...
  const sort = ...

  const todos = await Todo.find({
    userId: req.user.id,
    ...
  })
    .sort(...)
    .skip(...)
    .limit(...);

  res.json(...);
}
```

Now the controller knows:

```text
HTTP
+
query parsing
+
business rules
+
database syntax
```

That's exactly what we've been trying to avoid throughout Phases 11–18.

---

# 6. Better separation

Controller:

```js
async getTodos(req, res) {
  const result =
    await todoService.getTodos({
      userId: req.user.id,
      query: req.query
    });

  res.json(result);
}
```

Service:

```js
async getTodos({ userId, query }) {
  // prepare business-level query
}
```

Repository:

```js
async findMany(options) {
  // database query
}
```

Now each layer has a clear responsibility.

---

# 7. A simple query options object

One clean design is:

```js
{
  filter: {},
  sort: {},
  pagination: {
    skip: 0,
    limit: 20
  },
  projection: null
}
```

For example:

```js
const options = {
  filter: {
    userId,
    status: "pending"
  },

  sort: {
    createdAt: -1
  },

  pagination: {
    skip: 20,
    limit: 20
  }
};
```

Then the repository can consume this structure.

---

# 8. Repository

```js
async function findMany({
  filter = {},
  sort = {},
  pagination = {}
}) {
  const {
    skip = 0,
    limit = 20
  } = pagination;

  return Todo.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit);
}
```

This is already a very useful abstraction.

Notice:

The repository doesn't care whether:

```text
?page=2
```

was used.

It only understands:

```js
skip: 20
```

That's good separation.

---

# 9. Where the Query Builder comes in

Now suppose many repositories repeat:

```js
Model.find(filter)
  .sort(sort)
  .skip(skip)
  .limit(limit);
```

You might create:

```js
class QueryBuilder {
  constructor(query) {
    this.query = query;
  }

  filter(filter) {
    this.query = this.query.find(filter);
    return this;
  }

  sort(sort) {
    this.query = this.query.sort(sort);
    return this;
  }

  paginate(skip, limit) {
    this.query = this.query
      .skip(skip)
      .limit(limit);

    return this;
  }

  exec() {
    return this.query.exec();
  }
}
```

---

# 10. Using the builder

```js
const query = new QueryBuilder(
  Todo.find()
);

const todos = await query
  .filter({
    userId,
    status: "pending"
  })
  .sort({
    createdAt: -1
  })
  .paginate(20, 20)
  .exec();
```

The API becomes:

```text
filter()
   ↓
sort()
   ↓
paginate()
   ↓
exec()
```

This is called a **fluent interface**.

---

# 11. Why return `this`?

Look at:

```js
filter(filter) {
  this.query = this.query.find(filter);
  return this;
}
```

The important part is:

```js
return this;
```

Because of that, we can write:

```js
query
  .filter(...)
  .sort(...)
  .paginate(...);
```

instead of:

```js
query.filter(...);

query.sort(...);

query.paginate(...);
```

This is called **method chaining**.

---

# 12. But do we actually need this?

This is the key question.

We could simply write:

```js
return Todo.find(filter)
  .sort(sort)
  .skip(skip)
  .limit(limit);
```

That's already very readable.

So introducing:

```js
QueryBuilder
```

adds another abstraction layer.

Therefore:

> **A query builder should solve real repetition, not merely make the code look more sophisticated.**

---

# 13. The danger of overengineering

You might create:

```text
QueryBuilder
QueryParser
QueryFactory
QueryManager
QueryService
QueryRepository
QueryTransformer
QueryStrategy
```

for:

```text
Todo.find()
```

That's too much.

Your architecture becomes:

```text
GET /todos
 ↓
Controller
 ↓
Service
 ↓
QueryFactory
 ↓
QueryManager
 ↓
QueryBuilder
 ↓
QueryTransformer
 ↓
Repository
 ↓
Model
 ↓
MongoDB
```

😵

This is exactly what we don't want.

---

# 14. The simpler approach

For your MERN starter, I'd prefer this initially:

```text
Controller
    ↓
Service
    ↓
Query utilities
    ↓
Repository
    ↓
Mongoose
```

For example:

```js
const pagination = parsePagination(req.query);

const sort = parseSort(
  req.query.sort,
  ["createdAt", "updatedAt"]
);

const filter = buildTodoFilter(req.query);
```

Then:

```js
todoRepository.findMany({
  filter,
  sort,
  pagination
});
```

This is already clean.

---

# 15. When should you introduce a QueryBuilder?

Consider it when you repeatedly have:

```js
Model.find(filter)
  .sort(sort)
  .skip(skip)
  .limit(limit)
  .select(...)
  .populate(...);
```

across many repositories.

For example:

```text
TodoRepository
ProductRepository
OrderRepository
PostRepository
CommentRepository
```

all doing nearly identical query composition.

Then a shared abstraction can make sense.

---

# 16. Generic query builder

A more useful version might support:

```js
class QueryBuilder {
  constructor(query) {
    this.query = query;
  }

  filter(filter) {
    this.query = this.query.find(filter);
    return this;
  }

  sort(sort) {
    this.query = this.query.sort(sort);
    return this;
  }

  select(fields) {
    this.query = this.query.select(fields);
    return this;
  }

  paginate(skip, limit) {
    this.query = this.query
      .skip(skip)
      .limit(limit);

    return this;
  }

  populate(path) {
    this.query = this.query.populate(path);
    return this;
  }

  exec() {
    return this.query.exec();
  }
}
```

Now it can support common database mechanics.

But again:

**Only add operations that your application actually needs.**

---

# 17. Query Builder should not build authorization

Don't do:

```js
queryBuilder
  .filter(req.query)
  .authorize(req.user)
```

That's a bad boundary.

Authorization belongs to the service/business layer.

For example:

```js
const filter = {
  userId: currentUser.id,
  ...safeFilters
};
```

Then:

```js
repository.findMany({
  filter,
  sort,
  pagination
});
```

This is much safer.

---

# 18. Server-controlled filters

This is extremely important for your Todo application.

The client sends:

```http
GET /todos?status=pending
```

The server adds:

```js
userId: req.user.id
```

So the final filter is:

```js
{
  userId: req.user.id,
  status: "pending"
}
```

The client controls:

```text
status
```

The server controls:

```text
userId
```

This protects resource ownership.

---

# 19. Query Builder should not trust raw query parameters

Don't do:

```js
new QueryBuilder(Todo.find())
  .filter(req.query);
```

because `req.query` is untrusted input.

Instead:

```text
req.query
   ↓
validation
   ↓
normalization
   ↓
safe filter
   ↓
query builder/repository
```

This distinction is very important.

---

# 20. Example: safe Todo query

Request:

```http
GET /todos?status=pending&sort=-createdAt&page=2&limit=20
```

Controller:

```js
const result =
  await todoService.getTodos({
    userId: req.user.id,
    query: req.query
  });
```

Service:

```js
const pagination =
  parsePagination(query);

const sort =
  parseSort(
    query.sort,
    ["createdAt", "updatedAt"]
  );

const filter = {
  userId,
  ...buildTodoFilters(query)
};

return todoRepository.findMany({
  filter,
  sort,
  pagination
});
```

Repository:

```js
return Todo.find(filter)
  .sort(sort)
  .skip(pagination.skip)
  .limit(pagination.limit);
```

This is already production-friendly architecture.

# 21. Query Builder vs Repository

This distinction is important.

### Repository

Answers:

> **What database operation does this resource support?**

Example:

```js
todoRepository.findMany()
todoRepository.findById()
todoRepository.create()
todoRepository.update()
```

### Query Builder

Answers:

> **How can we compose database query operations cleanly?**

Example:

```js
filter()
sort()
paginate()
select()
```

So:

```text
Repository
   ↓
uses
   ↓
Query Builder
```

if your architecture actually benefits from one.

---

# 22. Query Builder vs Service

### Service

```text
Business rules
```

Example:

```text
User can only see their own Todo.
Archived Todo cannot be edited.
```

### Query Builder

```text
Database query composition
```

Example:

```text
WHERE userId = ...
SORT createdAt DESC
LIMIT 20
```

Never mix these concepts.

---

# 23. Query Builder vs Query Parser

This is another common interview question.

### Parser

```text
?page=2&limit=20
```

becomes:

```js
{
  page: 2,
  limit: 20
}
```

### Builder

```js
{
  filter,
  sort,
  pagination
}
```

becomes:

```text
Mongoose query
```

So:

```text
HTTP query
     ↓
Parser
     ↓
Normalized options
     ↓
Builder
     ↓
Database query
```

# 24. A better mental model

Think of the builder like a **query construction machine**.

Input:

```text
filter
sort
pagination
projection
```

Machine:

```text
┌──────────────────────────┐
│      Query Builder       │
│                          │
│ filter()                 │
│ sort()                   │
│ paginate()               │
│ select()                 │
└────────────┬─────────────┘
             ↓
       Mongoose Query
```

It doesn't decide:

```text
"Is Rahul allowed to see this?"
```

The service decides that.

---

# 25. Pagination metadata

A reusable builder can also eventually support:

```js
const [data, total] =
  await Promise.all([
    query.exec(),
    Model.countDocuments(filter)
  ]);
```

Then:

```js
{
  data,
  pagination: {
    page,
    limit,
    total,
    totalPages
  }
}
```

But be careful.

A generic builder that automatically performs:

```text
countDocuments()
```

for every query may add unnecessary database work.

Again:

> **Abstraction should not hide performance costs.**

---

# 26. Performance awareness

Imagine:

```js
const result =
  await queryBuilder
    .filter(filter)
    .sort(sort)
    .paginate(skip, limit)
    .withTotal()
    .exec();
```

`withTotal()` might secretly execute another query.

That's important.

Your developer should be able to understand:

```text
1 query
```

versus:

```text
2 queries
```

without opening five abstraction layers.

---

# 27. Keep database behavior visible

This is why I prefer a relatively small repository API.

For example:

```js
async findMany({
  filter,
  sort,
  pagination
}) {
  return Todo.find(filter)
    .sort(sort)
    .skip(pagination.skip)
    .limit(pagination.limit);
}
```

A future developer immediately understands:

```text
filter
sort
skip
limit
```

No mystery.


# 29. `lean()` and QueryBuilder

For read-only queries, Mongoose often provides:

```js
.lean()
```

which returns plain JavaScript objects instead of full Mongoose documents.

Example:

```js
Todo.find(filter)
  .lean();
```

This can be useful for read-heavy endpoints.

A query builder might eventually support:

```js
lean() {
  this.query = this.query.lean();
  return this;
}
```

But again:

> Don't automatically add `lean()` everywhere without understanding whether the caller needs Mongoose document behavior.

# 30. Projection

Suppose the endpoint only needs:

```text
title
status
createdAt
```

The repository could support:

```js
.select("title status createdAt");
```

or:

```js
.select({
  title: 1,
  status: 1,
  createdAt: 1
});
```

This can reduce unnecessary data transfer.

# 31. Query Builder design principle #1

> **Keep it composable.**

Good:

```js
query
  .filter(...)
  .sort(...)
  .paginate(...);
```

Each operation does one thing.

---

# 32. Design principle #2

> **Keep it predictable.**

If:

```js
.sort(...)
```

also changes:

```text
filter
pagination
projection
```

that's surprising.

One method should have one clear responsibility.

---

# 33. Design principle #3

> **Don't hide expensive operations.**

If:

```js
paginate()
```

runs three database queries, that's bad abstraction.

A method name should make its cost reasonably understandable.

---

# 34. Design principle #4

> **Don't allow arbitrary database operations from HTTP input.**

Never expose something like:

```http
GET /todos?operator=$where
```

or allow clients to directly construct MongoDB operators.

Instead, define a controlled API:

```text
status=pending
priority=high
sort=-createdAt
```

and translate those into safe database operations.

---

# 35. Design principle #5

> **Keep authorization outside the generic builder.**

This is one of the most important rules for your backend.

Bad:

```js
QueryBuilder.authorize(...)
```

Better:

```text
Service
  ↓
build secure filter
  ↓
Repository
  ↓
Query Builder
```

# 39. Interview questions

### Q1. What is a query builder?

A reusable abstraction for composing database queries from operations such as filtering, sorting, pagination, and projection.

### Q2. Is a query builder mandatory?

No.

### Q3. Query builder vs repository?

Repository defines resource-level data access operations; a query builder can help compose the underlying database query.

### Q4. Should a query builder handle authorization?

Generally no.

### Q5. Why shouldn't raw `req.query` go directly into MongoDB?

Because request input is untrusted and should be validated and translated into controlled query operations.

### Q6. Why can over-abstraction hurt performance?

Because abstractions can hide extra database operations, additional queries, or expensive processing.
