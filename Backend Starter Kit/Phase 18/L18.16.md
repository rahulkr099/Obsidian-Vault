## Lesson 18.16 — Query Builder vs Query Utilities: When to Abstract

First, one correction from the official roadmap: **Phase 18 officially ends at 18.14 — “Build reusable query utilities.”** There is no official 18.15 or 18.16 in your uploaded roadmap.

Since we already continued with 18.15, I'll treat **18.16 as an optional extension**, not as an official roadmap lesson.

The important topic now is:

> **How do you decide whether you need a Query Builder at all?**

---

# 1. Start with the simplest architecture

From 18.14, we already have:

```text
Request
   ↓
Validate query
   ↓
Parse query
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

For example:

```js
const pagination = parsePagination(req.query);

const sort = parseSort(
  req.query.sort,
  ["createdAt", "updatedAt"]
);

const filter = buildTodoFilters(req.query);
```

Then:

```js
await todoRepository.findMany({
  filter,
  sort,
  pagination
});
```

This is already good architecture.

**You do not automatically need a QueryBuilder.**

---

# 2. Why developers create QueryBuilders

Suppose you have five repositories:

```text
TodoRepository
PostRepository
ProductRepository
OrderRepository
CommentRepository
```

And all of them repeatedly do:

```js
Model.find(filter)
  .sort(sort)
  .skip(skip)
  .limit(limit);
```

Then you notice:

> "I'm repeating the same database-query composition everywhere."

That's when abstraction becomes reasonable.

---

# 3. Three levels of abstraction

Think of your backend query architecture as three levels.

### Level 1 — Direct Mongoose

```js
Todo.find(filter)
  .sort(sort)
  .skip(skip)
  .limit(limit);
```

### Level 2 — Query utilities

```js
const filter = buildTodoFilters(query);
const sort = parseSort(query.sort);
const pagination = parsePagination(query);
```

### Level 3 — Query Builder

```js
new QueryBuilder(Todo.find())
  .filter(filter)
  .sort(sort)
  .paginate(skip, limit)
  .exec();
```

Don't jump to Level 3 just because it looks "professional."

---

# 4. Level 1 is completely valid

For a small project:

```js
async findMany({ filter, sort, pagination }) {
  return Todo.find(filter)
    .sort(sort)
    .skip(pagination.skip)
    .limit(pagination.limit);
}
```

This is:

- readable
    
- easy to debug
    
- easy to understand
    
- easy for a beginner
    
- close to the actual database operation
    

That's a **good thing**.

---

# 5. Level 2 is what I recommend for your starter

Your current architecture should mainly use:

```text
utils/query/
├── pagination.js
├── sorting.js
└── search.js
```

Then domain-specific filtering:

```text
todo/
└── todo.query.js
```

For example:

```js
const pagination = parsePagination(query);

const sort = parseSort(
  query.sort,
  ["createdAt", "updatedAt"]
);

const filter = buildTodoFilters(query);
```

Then:

```js
todoRepository.findMany({
  filter,
  sort,
  pagination
});
```

This gives you most of the benefits without overengineering.

---

# 6. Level 3 is optional

A QueryBuilder becomes useful when you have a **stable repeated pattern**.

For example:

```text
Every repository supports:

filter
sort
pagination
projection
lean
populate
```

Then you might create:

```js
class QueryBuilder {
  constructor(query) {
    this.query = query;
  }

  filter(filter) {
    this.query = this.query.find(filter);
    return this;
  }

  sort(sort) {
    this.query = this.query.sort(sort);
    return this;
  }

  paginate(skip, limit) {
    this.query = this.query
      .skip(skip)
      .limit(limit);

    return this;
  }

  select(fields) {
    this.query = this.query.select(fields);
    return this;
  }

  lean() {
    this.query = this.query.lean();
    return this;
  }

  exec() {
    return this.query.exec();
  }
}
```

---

# 7. Using it

Now:

```js
const todos = await new QueryBuilder(
  Todo.find()
)
  .filter({
    userId,
    status: "pending"
  })
  .sort({
    createdAt: -1
  })
  .paginate(20, 20)
  .lean()
  .exec();
```

This is neat.

But compare it with:

```js
const todos = await Todo.find({
  userId,
  status: "pending"
})
  .sort({ createdAt: -1 })
  .skip(20)
  .limit(20)
  .lean();
```

The second version is arguably easier to understand.

That's why abstraction needs justification.

---

# 8. The abstraction test

Before creating a QueryBuilder, ask:

### Question 1

Is the same logic repeated?

```text
Yes → maybe abstract
No → don't abstract
```

### Question 2

Is the repeated behavior stable?

If today every repository needs:

```text
filter
sort
pagination
```

but tomorrow you're not sure what the pattern will look like, wait.

### Question 3

Does abstraction make the code easier to understand?

If:

```js
QueryBuilder(...)
```

requires reading another 300-line class just to understand:

```js
findMany()
```

you probably made things worse.

---

# 9. The "five lines" rule

Suppose your repository has:

```js
return Todo.find(filter)
  .sort(sort)
  .skip(skip)
  .limit(limit);
```

That's only four lines.

Creating:

```text
QueryBuilder
QueryBuilderFactory
QueryBuilderConfig
QueryBuilderOptions
```

to remove those four lines is usually not worth it.

---

# 10. Abstraction should remove complexity

Good abstraction:

```text
50 repeated lines
       ↓
10 reusable lines
```

Bad abstraction:

```text
4 simple lines
       ↓
100 lines of abstraction
```

Always remember:

> **An abstraction is successful when it reduces total complexity, not when it reduces the number of lines in one file.**

---

# 11. Don't create generic filters for everything

Suppose Todo supports:

```text
status
priority
completed
```

Product supports:

```text
category
brand
price
```

Order supports:

```text
paymentStatus
deliveryStatus
```

Don't create:

```js
buildUniversalFilter()
```

like:

```js
buildUniversalFilter({
  status,
  priority,
  completed,
  category,
  brand,
  price,
  paymentStatus,
  deliveryStatus
});
```

That's a **God utility**.

Instead:

```text
Todo
 └── buildTodoFilters()

Product
 └── buildProductFilters()

Order
 └── buildOrderFilters()
```

---

# 12. What should be generic?

Good candidates:

```text
pagination parsing
sort parsing
search parsing
query normalization
```

For example:

```js
parsePagination()
```

doesn't care whether you're querying:

```text
Todo
Product
Order
Post
```

That's genuinely generic behavior.

---

# 13. What should remain domain-specific?

Things like:

```js
buildTodoFilters()
```

should know about:

```text
Todo.status
Todo.priority
Todo.completed
```

Similarly:

```js
buildProductFilters()
```

knows about:

```text
Product.category
Product.price
Product.brand
```

This keeps domain logic close to the domain.

---

# 14. Query Builder shouldn't know business rules

This is a major architectural boundary.

Don't write:

```js
queryBuilder
  .onlyOwnedBy(user)
  .onlyVisibleTo(user)
  .checkPermission(user);
```

That sounds convenient, but now the generic database utility understands application authorization.

Bad separation.

Instead:

```js
const filter = {
  userId: user.id,
  status: "pending"
};
```

Then:

```js
repository.findMany({
  filter,
  sort,
  pagination
});
```

The service decides **what the user is allowed to access**.

---

# 15. Security boundary

Consider:

```http
GET /todos?userId=abc
```

A dangerous implementation:

```js
const filter = {
  userId: req.query.userId
};
```

The client can select another user's ID.

Instead:

```js
const filter = {
  userId: req.user.id
};
```

Then the client can control only safe filters:

```js
{
  userId: req.user.id,
  status: req.query.status
}
```

This is exactly the ownership pattern emphasized in your roadmap.

---

# 16. Query Builder shouldn't accept raw HTTP input

Never design:

```js
new QueryBuilder(Todo.find())
  .filter(req.query);
```

That's dangerous.

Use:

```text
req.query
   ↓
validation
   ↓
normalization
   ↓
safe query object
   ↓
repository
```

The QueryBuilder should receive **trusted, controlled application-level values**, not arbitrary HTTP input.

---

# 17. Example of a safe flow

Request:

```http
GET /api/v1/todos?status=pending&sort=-createdAt&page=2&limit=20
```

### Step 1 — Validate

```text
status → pending ✓
sort → -createdAt ✓
page → 2 ✓
limit → 20 ✓
```

### Step 2 — Parse

```js
{
  page: 2,
  limit: 20,
  sort: {
    createdAt: -1
  }
}
```

### Step 3 — Service adds ownership

```js
{
  userId: req.user.id,
  status: "pending"
}
```

### Step 4 — Repository

```js
todoRepository.findMany({
  filter,
  sort,
  pagination
});
```

### Step 5 — Database

```js
Todo.find(filter)
  .sort(sort)
  .skip(20)
  .limit(20);
```

Beautifully separated.

---

# 18. A useful interface

Your repository can expose:

```js
findMany({
  filter,
  sort,
  pagination,
  projection
})
```

instead of:

```js
findMany(req.query)
```

That's a very important distinction.

### Bad

```text
Repository ← HTTP
```

### Good

```text
HTTP
 ↓
Application-level options
 ↓
Repository
```

The repository shouldn't know HTTP exists.

---

# 19. This makes repositories reusable

Imagine tomorrow you call your service from:

```text
REST API
GraphQL
CLI
Background job
Admin script
```

If your repository accepts:

```js
{
  filter,
  sort,
  pagination
}
```

it doesn't care where those options came from.

That's excellent architecture.

---

# 20. Query Builder can sit below the Repository

If you eventually need one:

```text
Service
   ↓
Repository
   ↓
QueryBuilder
   ↓
Mongoose
   ↓
MongoDB
```

For example:

```js
async findMany({
  filter,
  sort,
  pagination
}) {
  return new QueryBuilder(
    Todo.find()
  )
    .filter(filter)
    .sort(sort)
    .paginate(
      pagination.skip,
      pagination.limit
    )
    .exec();
}
```

The service doesn't know the QueryBuilder exists.

That's a good abstraction boundary.

---

# 21. Why this is better

Suppose you later replace:

```text
Mongoose
```

with another database access approach.

If the service only knows:

```js
repository.findMany(...)
```

then the service doesn't need to change.

That's the main value of the Repository Pattern you've already studied.

The QueryBuilder is an **implementation detail** underneath it.

---

# 22. Query Builder should not become another Repository

Don't create:

```text
QueryBuilder.findTodo()
QueryBuilder.createTodo()
QueryBuilder.deleteTodo()
```

That's wrong.

A QueryBuilder should compose queries.

The Repository should define resource operations.

### QueryBuilder

```text
filter
sort
paginate
select
lean
populate
```

### Repository

```text
findMany
findById
create
update
delete
```

---

# 23. Think in responsibilities

Here's a very useful table:

|Component|Responsibility|
|---|---|
|Controller|HTTP|
|Validator|Input validity|
|Query utilities|Query parameter parsing|
|Service|Business rules|
|Repository|Data access|
|QueryBuilder|Query composition|
|Model|Data schema|
|MongoDB|Data storage|

If you remember this table, you'll avoid a lot of architectural mistakes.

---

# 24. Query Builder and pagination

A builder can make pagination look nice:

```js
query.paginate({
  page: 2,
  limit: 20
});
```

Internally:

```js
const skip = (page - 1) * limit;
```

But there's a question:

> Should `paginate()` accept `page` and `limit`, or `skip` and `limit`?

I prefer:

### Query utility

```js
parsePagination()
```

produces:

```js
{
  page: 2,
  limit: 20,
  skip: 20
}
```

### Repository / builder

uses:

```js
skip: 20
limit: 20
```

Why?

Because `page` is an **HTTP/API concept**, while `skip` is a **database query concept**.

That's a subtle but useful separation.

---

# 25. Same idea with sorting

HTTP:

```text
?sort=-createdAt
```

Query utility converts it to:

```js
{
  createdAt: -1
}
```

Repository receives:

```js
sort: {
  createdAt: -1
}
```

Now the database layer doesn't care about:

```text
"-createdAt"
```

That's clean.

---

# 26. This is what "translation between layers" means

You are gradually transforming data:

```text
HTTP language
    ↓
Application language
    ↓
Database language
```

For example:

```text
?page=2
```

becomes:

```js
{
  page: 2
}
```

then:

```js
{
  skip: 20,
  limit: 20
}
```

This is one of the most useful architectural ideas to understand.

---

# 27. Don't leak Mongoose everywhere

Bad:

```js
service.getTodos()
```

returns a Mongoose query object.

Then controller:

```js
const query = service.getTodos();

query.populate(...);
query.sort(...);
```

Now the controller knows Mongoose.

That's leakage.

Prefer:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Mongoose
```

The database technology stays below the Repository boundary.

---

# 28. Don't return query builders to services

Avoid:

```js
const query =
  repository.buildQuery(...);

return query;
```

Then the service starts manipulating:

```js
query.sort()
query.populate()
query.limit()
```

Now your service is database-aware.

Instead:

```js
const result =
  await repository.findMany(...);
```

The repository completes the database operation.

---

# 29. A strong repository contract

For example:

```js
todoRepository.findMany({
  filter,
  sort,
  pagination,
  projection
});
```

The service says:

> "Give me Todos matching these application-level conditions."

The repository says:

> "I'll translate that into Mongoose."

That's a strong boundary.

---

# 30. Query Builder as an implementation detail

Your architecture can therefore look like:

```text
             Service
                │
                ▼
        TodoRepository
                │
                ▼
          QueryBuilder
                │
                ▼
            Mongoose
                │
                ▼
            MongoDB
```

But your service doesn't need to know:

```text
QueryBuilder exists.
```

That is good encapsulation.

---

# 31. When NOT to use QueryBuilder

Don't use one if:

```text
you have only a few repositories
queries are simple
Mongoose syntax is already readable
there is little repetition
the team is unfamiliar with the abstraction
```

Use direct Mongoose.

---

# 32. When to consider one

Consider one if:

```text
many repositories repeat query composition
query behavior is standardized
the abstraction is well-tested
the team understands it
it actually reduces complexity
```

That's the right threshold.

---

# 33. The YAGNI principle

You will hear this in professional development:

> **YAGNI — You Aren't Gonna Need It.**

Meaning:

Don't build:

```text
advanced query engine
```

because you _might_ need it someday.

Build it when you **actually need it**.

This is particularly important for your starter project.

Your starter should be:

```text
simple enough to understand
```

but:

```text
structured enough to scale
```

That's the sweet spot.

# 36. Interview perspective

If an interviewer asks:

> "Would you create a generic QueryBuilder?"

A strong answer isn't:

> "Yes, because clean architecture."

Instead:

> "It depends on the amount of repeated query composition. I would first keep query parsing in reusable utilities and keep repositories explicit. If multiple repositories develop the same stable Mongoose query-composition behavior, I would extract a small QueryBuilder while keeping authorization and business rules outside it."

That's a much more mature answer.

# 🧪 Practice

Take this request:

```http
GET /api/v1/todos?page=3&limit=10&sort=-createdAt&status=pending
```

Design the transformation:

### HTTP

```text
page=3
limit=10
sort=-createdAt
status=pending
```

↓

### Normalized query

```js
{
  pagination: {
    page: 3,
    limit: 10,
    skip: 20
  },

  sort: {
    createdAt: -1
  },

  filters: {
    status: "pending"
  }
}
```

↓

### Service adds ownership

```js
{
  userId: currentUserId,
  status: "pending"
}
```

↓

### Repository

```js
todoRepository.findMany({
  filter,
  sort,
  pagination
});
```

↓

### Database

```js
Todo.find(filter)
  .sort(sort)
  .skip(20)
  .limit(10);
```

If you can trace this flow without confusion, you've understood the important part of **18.16**.

## 🔑 One sentence

> **Start with simple repositories and reusable query utilities; introduce a QueryBuilder only when repeated database-query composition creates real complexity.**

And for your actual starter, **I would not add a QueryBuilder yet**. Your existing Repository + reusable query utilities architecture is the better learning and maintenance choice.
