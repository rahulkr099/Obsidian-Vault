# Lesson 18.5 — Pagination Metadata

In the previous lessons, we learned:

```text
page
limit
skip
```

We can now retrieve a portion of a large dataset.

But there is a new problem.

Suppose the frontend requests:

```http
GET /api/v1/todos?page=2&limit=20
```

The backend returns 20 todos.

The frontend now knows:

> "I received 20 todos."

But it **doesn't know**:

- How many todos exist in total?
    
- Is this the last page?
    
- Is there another page?
    
- What page am I currently on?
    
- How many pages are available?
    

That's the purpose of **pagination metadata**.

Your roadmap explicitly includes pagination as part of the API response architecture, so we're now connecting the query mechanism to a useful frontend-facing response contract.

---

# 1. The problem

Imagine there are:

```text
147 todos
```

and:

```text
limit = 20
```

The frontend requests:

```http
GET /todos?page=1&limit=20
```

The backend returns:

```json
{
  "success": true,
  "data": [
    "...20 todos..."
  ]
}
```

The frontend knows:

```text
20 todos received
```

But does it know:

```text
147 total?
8 pages?
page 1?
next page exists?
```

No.

So the frontend can't reliably build:

```text
← Previous    1  2  3  4  5  6  7  8    Next →
```

We need additional information.

---

# 2. What is pagination metadata?

Pagination metadata is information **about the paginated result**, rather than the actual records.

For example:

```json
{
  "page": 2,
  "limit": 20,
  "totalItems": 147,
  "totalPages": 8,
  "hasNextPage": true,
  "hasPreviousPage": true
}
```

Notice the separation:

```text
data
 ↓
actual todos

pagination
 ↓
information about the result
```

This is a very useful API design pattern.

---

# 3. The complete response

A good response might look like:

```json
{
  "success": true,
  "message": "Todos fetched successfully",
  "data": [
    {
      "_id": "abc123",
      "title": "Learn pagination"
    },
    {
      "_id": "def456",
      "title": "Practice MongoDB"
    }
  ],
  "pagination": {
    "page": 2,
    "limit": 20,
    "totalItems": 147,
    "totalPages": 8,
    "hasNextPage": true,
    "hasPreviousPage": true
  }
}
```

Now the frontend has everything it needs.

---

# 4. `page`

This tells the frontend:

> Which page did the server return?

For:

```http
GET /todos?page=3&limit=20
```

metadata contains:

```json
{
  "page": 3
}
```

Simple.

---

# 5. `limit`

This tells the frontend:

> What page size was used?

For:

```http
GET /todos?page=3&limit=20
```

we return:

```json
{
  "limit": 20
}
```

This is useful because the server may apply a default or maximum.

For example:

```http
GET /todos
```

could internally become:

```text
page = 1
limit = 20
```

The response can make that explicit.

---

# 6. `totalItems`

This is one of the most important pieces.

Suppose the database contains:

```text
147 todos
```

Then:

```json
{
  "totalItems": 147
}
```

means:

> There are 147 matching records in total.

Notice the word **matching**.

If you're filtering:

```http
GET /todos?status=completed
```

then:

```text
totalItems
```

should represent the number of **completed todos**, not necessarily every todo in the database.

We'll see why this matters when we reach filtering.

---

# 7. `totalPages`

Now we can calculate how many pages are available.

Formula:

```text
totalPages = ceil(totalItems / limit)
```

Suppose:

```text
totalItems = 147
limit = 20
```

Then:

```text
147 / 20
= 7.35
```

We can't have:

```text
7.35 pages
```

So we round **up**:

```text
ceil(7.35)
= 8
```

Therefore:

```json
{
  "totalPages": 8
}
```

---

# 8. Why `Math.ceil()`?

In JavaScript:

```js
Math.ceil(147 / 20);
```

gives:

```text
8
```

Compare:

```js
Math.floor(147 / 20);
```

which gives:

```text
7
```

That would be wrong.

Why?

Because page 8 still contains:

```text
records 141–147
```

There are 7 records on the final page.

So we need:

```text
ceil()
```

not:

```text
floor()
```

---

# 9. Example: 100 records

Suppose:

```text
totalItems = 100
limit = 20
```

Then:

```text
100 / 20 = 5
```

So:

```text
totalPages = 5
```

Pages:

```text
Page 1 → 1–20
Page 2 → 21–40
Page 3 → 41–60
Page 4 → 61–80
Page 5 → 81–100
```

Perfect.

---

# 10. Example: 101 records

Now:

```text
totalItems = 101
limit = 20
```

Calculate:

```text
101 / 20
= 5.05
```

Then:

```text
ceil(5.05)
= 6
```

So:

```text
totalPages = 6
```

The pages are:

```text
Page 1 → 1–20
Page 2 → 21–40
Page 3 → 41–60
Page 4 → 61–80
Page 5 → 81–100
Page 6 → 101
```

The last page contains only one record.

---

# 11. `hasNextPage`

Now we can tell the frontend:

> Does another page exist?

Suppose:

```text
page = 2
totalPages = 8
```

Then:

```text
hasNextPage = true
```

Because:

```text
2 < 8
```

The frontend can show:

```text
Next →
```

---

# 12. Last page

Suppose:

```text
page = 8
totalPages = 8
```

Then:

```text
hasNextPage = false
```

Because:

```text
8 < 8
```

is false.

So the frontend can disable:

```text
Next →
```

---

# 13. `hasPreviousPage`

Similarly:

```text
hasPreviousPage = page > 1
```

Therefore:

### Page 1

```text
page = 1

hasPreviousPage = false
```

### Page 2

```text
page = 2

hasPreviousPage = true
```

### Page 8

```text
page = 8

hasPreviousPage = true
```

Simple.

---

# 14. Complete calculation

Let's say:

```text
totalItems = 147
page = 4
limit = 20
```

First:

```text
totalPages = ceil(147 / 20)
            = 8
```

Then:

```text
hasNextPage = 4 < 8
             = true
```

And:

```text
hasPreviousPage = 4 > 1
                = true
```

So:

```json
{
  "page": 4,
  "limit": 20,
  "totalItems": 147,
  "totalPages": 8,
  "hasNextPage": true,
  "hasPreviousPage": true
}
```

---

# 15. What happens on page 1?

For:

```text
page = 1
totalPages = 8
```

we get:

```json
{
  "page": 1,
  "limit": 20,
  "totalItems": 147,
  "totalPages": 8,
  "hasNextPage": true,
  "hasPreviousPage": false
}
```

---

# 16. What happens on the last page?

For:

```text
page = 8
totalPages = 8
```

we get:

```json
{
  "page": 8,
  "limit": 20,
  "totalItems": 147,
  "totalPages": 8,
  "hasNextPage": false,
  "hasPreviousPage": true
}
```

This makes frontend pagination very easy.

---

# 17. Where does `totalItems` come from?

This is the interesting part.

We need to count the matching documents.

With Mongoose, conceptually:

```js
const totalItems = await Todo.countDocuments();
```

And separately:

```js
const todos = await Todo.find()
    .skip(skip)
    .limit(limit);
```

So we have two pieces of information:

```text
countDocuments()
        ↓
totalItems

find()
  ↓
current page data
```

---

# 18. Filtering changes the count

Suppose we have:

```text
500 total todos
```

But the user requests:

```http
GET /todos?status=completed&page=1&limit=20
```

Suppose only:

```text
123 completed todos
```

Then:

```text
totalItems = 123
```

not:

```text
500
```

So conceptually:

```js
const filter = {
    status: "completed"
};

const totalItems = await Todo.countDocuments(filter);

const todos = await Todo.find(filter)
    .skip(skip)
    .limit(limit);
```

Both operations use the **same filter**.

That's extremely important.

---

# 19. Why must the count and query use the same filter?

Imagine:

```text
500 total todos
123 completed todos
```

If you accidentally do:

```js
const totalItems = await Todo.countDocuments();
```

you get:

```text
500
```

but:

```js
const todos = await Todo.find({
    status: "completed"
});
```

returns only completed todos.

Now your API says:

```json
{
  "totalItems": 500
}
```

while the actual dataset being paginated contains only:

```text
123
```

That's incorrect pagination metadata.

The rule is:

> **Count the same dataset that you are paginating.**

---

# 20. The two-query mental model

For basic page-based pagination, think:

```text
             FILTER
                │
       ┌────────┴────────┐
       │                 │
       ▼                 ▼
 countDocuments()      find()
       │                 │
       ▼                 ▼
 totalItems          page data
                         │
                    skip + limit
                         │
                         ▼
                     current page
```

Then combine:

```text
data
+
pagination metadata
```

into one API response.

---

# 21. But isn't counting expensive?

It can be.

For a large collection, calculating:

```js
countDocuments()
```

also requires database work.

So pagination isn't completely free.

We're trading:

```text
return 1,000,000 documents
```

for:

```text
count matching documents
+
return 20 documents
```

Usually this is much more useful, but the count itself can become expensive for complex queries.

Later, when we study:

```text
indexes
performance
cursor pagination
```

we'll discuss these trade-offs.

---

# 22. A practical controller response

A simplified controller might eventually produce:

```js
const totalItems = await todoRepository.count(filter);

const todos = await todoRepository.findMany({
    filter,
    skip,
    limit
});

const totalPages = Math.ceil(totalItems / limit);

res.json({
    success: true,
    data: todos,
    pagination: {
        page,
        limit,
        totalItems,
        totalPages,
        hasNextPage: page < totalPages,
        hasPreviousPage: page > 1
    }
});
```

This is useful for understanding the idea.

However, in our architecture, we don't want controllers becoming responsible for every database operation.

We'll improve the placement of this logic later.

---

# 23. A better architecture

Eventually our flow should look something like:

```text
Controller
    │
    │ page, limit, filters
    ▼
Service
    │
    │ pagination rules
    ▼
Repository
    │
    ├── count matching documents
    │
    └── fetch current page
    ▼
MongoDB
```

Then the service can produce a structured result:

```js
{
    data,
    pagination
}
```

The controller simply converts that into the HTTP response.

This follows the architecture you've been learning since the service and repository phases. Your source describes the repository as the data-access layer and the service as the business-logic layer.

---

# 24. Should pagination metadata be inside `data`?

I recommend keeping them separate.

### Less clean

```json
{
  "data": {
    "items": [],
    "page": 1,
    "limit": 20,
    "totalItems": 147
  }
}
```

### Cleaner

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 20,
    "totalItems": 147,
    "totalPages": 8
  }
}
```

Why?

Because:

```text
data
```

represents the actual resources.

While:

```text
pagination
```

represents information about how those resources were retrieved.

This separation becomes especially useful for React clients.

---

# 25. Frontend becomes simple

Suppose React receives:

```json
{
  "data": [],
  "pagination": {
    "page": 3,
    "limit": 20,
    "totalItems": 147,
    "totalPages": 8,
    "hasNextPage": true,
    "hasPreviousPage": true
  }
}
```

The UI can simply do:

```text
page = 3

```

and display:

```text
← Previous

Page 3 of 8

Next →
```

No database knowledge is required.

---

# 26. Why `totalPages` is useful

Without:

```text
totalPages
```

the frontend would have to keep requesting pages:

```text
page 1
page 2
page 3
page 4
...
```

until it receives:

```json
{
  "data": []
}
```

That's wasteful.

With:

```json
{
  "totalPages": 8
}
```

the frontend already knows:

```text
Page 8 is the last page.
```

---

# 27. What if there are zero records?

Suppose:

```text
totalItems = 0
limit = 20
```

Mathematically:

```text
Math.ceil(0 / 20)
= 0
```

So:

```text
totalPages = 0
```

The response might be:

```json
{
  "success": true,
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 20,
    "totalItems": 0,
    "totalPages": 0,
    "hasNextPage": false,
    "hasPreviousPage": false
  }
}
```

There are no results.

---

# 28. A small design decision: `totalPages = 0` or `1`

Different APIs may choose different conventions for an empty dataset.

You might see:

```text
totalItems = 0
totalPages = 0
```

or:

```text
totalItems = 0
totalPages = 1
```

I generally prefer:

```text
totalItems = 0
totalPages = 0
```

because there are literally zero pages containing data.

But the important thing is **consistency**.

Your frontend and backend should agree on the contract.

---

# 29. Metadata should describe the actual query

Suppose the request is:

```http
GET /todos
    ?page=2
    &limit=20
    &status=completed
    &sort=-createdAt
```

Then metadata should describe the result of:

```text
filter = completed
sort = newest first
page = 2
limit = 20
```

For example:

```json
{
  "pagination": {
    "page": 2,
    "limit": 20,
    "totalItems": 73,
    "totalPages": 4,
    "hasNextPage": true,
    "hasPreviousPage": true
  }
}
```

This is why pagination, filtering, and sorting eventually become one combined query system.

---

# 30. Don't expose unnecessary internal information

Your pagination metadata should normally contain useful client-facing information:

```text
page
limit
totalItems
totalPages
hasNextPage
hasPreviousPage
```

You don't need to expose internal database details such as:

```text
MongoDB execution time
query planner
internal cursor state
database server information
```

unless there is a specific reason.

API responses should expose what the client needs—not your internal implementation.

---

# 31. A reusable pagination object

As your application grows, you'll have:

```text
/users
/todos
/products
/orders
/comments
/posts
```

All of them may need pagination.

So instead of inventing different metadata every time:

```json
{
  "page": 1,
  "total": 100
}
```

then:

```json
{
  "currentPage": 1,
  "count": 100
}
```

then:

```json
{
  "pageNumber": 1,
  "records": 100
}
```

choose one consistent contract.

For example:

```json
{
  "page": 1,
  "limit": 20,
  "totalItems": 147,
  "totalPages": 8,
  "hasNextPage": true,
  "hasPreviousPage": false
}
```

Consistency is extremely valuable in API design.

Your roadmap specifically emphasizes **consistent API contracts** and pagination responses as part of API response architecture.

# 32. Complete example

Let's put everything together.

Suppose:

```text
Total matching todos = 147
page = 3
limit = 20
```

### Step 1 — Calculate skip

```text
skip = (3 - 1) × 20
     = 40
```

### Step 2 — Fetch data

```text
skip 40
limit 20
```

So we retrieve approximately:

```text
41–60
```

### Step 3 — Calculate pages

```text
totalPages = ceil(147 / 20)
            = 8
```

### Step 4 — Determine navigation

```text
hasNextPage = 3 < 8
            = true

hasPreviousPage = 3 > 1
                = true
```

### Step 5 — Response

```json
{
  "success": true,
  "data": [
    "...20 todos..."
  ],
  "pagination": {
    "page": 3,
    "limit": 20,
    "totalItems": 147,
    "totalPages": 8,
    "hasNextPage": true,
    "hasPreviousPage": true
  }
}
```

That's a complete paginated response.

# 🧠 What you should remember

There are **six important pieces**:

```text
page
limit
totalItems
totalPages
hasNextPage
hasPreviousPage
```

And the formulas:

```text
skip = (page - 1) × limit
```

```text
totalPages = Math.ceil(totalItems / limit)
```

```text
hasNextPage = page < totalPages
```

```text
hasPreviousPage = page > 1
```

The most important conceptual distinction is:

```text
data
 ↓
"What did I receive?"

pagination
 ↓
"Where am I in the complete dataset?"
```
