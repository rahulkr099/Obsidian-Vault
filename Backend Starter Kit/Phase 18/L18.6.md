# Lesson 18.6 — Filtering

According to the Phase 18 roadmap, **18.6 is Filtering**.

So far we have learned:

```text
18.1 → Why pagination matters
18.2 → Page vs cursor pagination
18.3 → limit
18.4 → skip
18.5 → Pagination metadata
18.6 → Filtering  ← today
```

Now we're going to make our API more useful.

Instead of:

```http
GET /api/v1/todos
```

we should be able to ask:

```http
GET /api/v1/todos?status=completed
```

or:

```http
GET /api/v1/todos?priority=high
```

or:

```http
GET /api/v1/todos?status=pending&priority=high
```

This is **filtering**.

---

# 1. What is filtering?

Filtering means:

> **Return only the records that match specific conditions.**

Suppose our database contains:

```text
Todo A → completed
Todo B → pending
Todo C → completed
Todo D → pending
Todo E → pending
```

Without filtering:

```http
GET /todos
```

returns:

```text
A
B
C
D
E
```

With:

```http
GET /todos?status=completed
```

we want:

```text
A
C
```

The database query becomes conceptually:

```js
Todo.find({
    status: "completed"
});
```

---

# 2. Filtering vs pagination

These are different concepts.

### Pagination

```text
"Which portion of the results do I want?"
```

### Filtering

```text
"Which records should be included at all?"
```

For example:

```http
GET /todos?page=2&limit=20&status=completed
```

means:

```text
status=completed
        ↓
Choose only completed todos
        ↓
page=2
        ↓
Take second page
        ↓
limit=20
        ↓
Return up to 20
```

So the overall flow becomes:

```text
Request
   ↓
Filter
   ↓
Sort
   ↓
Pagination
   ↓
Response
```

We'll refine that ordering later when we study sorting and query construction.

---

# 3. A simple MongoDB filter

Suppose our Todo model looks roughly like:

```js
{
    title: "Learn MongoDB",
    status: "pending",
    priority: "high"
}
```

We can query:

```js
Todo.find({
    status: "pending"
});
```

MongoDB will return documents where:

```text
status === "pending"
```

Similarly:

```js
Todo.find({
    priority: "high"
});
```

returns high-priority todos.

---

# 4. Filtering through an HTTP query parameter

The frontend might send:

```http
GET /api/v1/todos?status=completed
```

Express gives us:

```js
req.query.status
```

which is approximately:

```js
"completed"
```

So a basic implementation could be:

```js
const filter = {};

if (req.query.status) {
    filter.status = req.query.status;
}

const todos = await Todo.find(filter);
```

If the request is:

```http
GET /todos?status=completed
```

then:

```js
filter
```

becomes:

```js
{
    status: "completed"
}
```

---

# 5. Multiple filters

This becomes more interesting.

Suppose the client sends:

```http
GET /todos?status=pending&priority=high
```

We can construct:

```js
const filter = {};

if (req.query.status) {
    filter.status = req.query.status;
}

if (req.query.priority) {
    filter.priority = req.query.priority;
}
```

The resulting filter is:

```js
{
    status: "pending",
    priority: "high"
}
```

Then:

```js
Todo.find(filter);
```

means:

> Find todos that are pending **AND** have high priority.

---

# 6. AND behavior

When MongoDB receives:

```js
{
    status: "pending",
    priority: "high"
}
```

both conditions need to match.

Imagine:

```text
Todo A
status   = pending
priority = high
```

✅ Matches

```text
Todo B
status   = pending
priority = low
```

❌ Doesn't match

```text
Todo C
status   = completed
priority = high
```

❌ Doesn't match

So:

```text
status=pending
+
priority=high
```

means:

```text
pending AND high priority
```

---

# 7. Filtering is not searching

This distinction is very important.

### Filtering

Usually asks:

> "Does this field have this value?"

Example:

```http
GET /todos?status=completed
```

### Searching

Usually asks:

> "Does this text appear in this field?"

Example:

```http
GET /todos?search=mongo
```

Search might match:

```text
"Learn MongoDB"
"MongoDB indexing"
"MongoDB pagination"
```

even though the exact value isn't `"mongo"`.

According to our roadmap:

```text
18.6 → Filtering
18.7 → Search
```

So **don't mix these concepts yet**.

---

# 8. Filtering by enum-like values

Suppose Todo status can only be:

```text
pending
completed
cancelled
```

Then:

```http
GET /todos?status=pending
```

is reasonable.

But:

```http
GET /todos?status=banana
```

should probably not silently become:

```js
{
    status: "banana"
}
```

because `banana` isn't a valid status.

This is where validation becomes important.

The API should eventually enforce:

```text
status ∈ {
    pending,
    completed,
    cancelled
}
```

We'll cover query validation in **18.10**.

---

# 9. Never blindly trust query parameters

A beginner might write:

```js
const filter = req.query;
```

and then:

```js
Todo.find(filter);
```

This looks convenient.

But it's a bad general design.

Why?

Because the client controls:

```text
req.query
```

That means the client can send arbitrary fields.

For example:

```http
GET /todos?password=...
```

or unexpected query structures.

You don't want your API to automatically turn every client-provided query parameter into a database query.

Instead, use an **allow-list**.

---

# 10. Allow-list filtering

Suppose your API officially supports:

```text
status
priority
```

Then explicitly read those:

```js
const filter = {};

if (req.query.status) {
    filter.status = req.query.status;
}

if (req.query.priority) {
    filter.priority = req.query.priority;
}
```

This means:

```text
Supported:
status
priority

Everything else:
ignored or rejected
```

This is much safer and more predictable.

---

# 11. Why allow-listing is important

Imagine your database document contains:

```js
{
    title,
    status,
    priority,
    userId,
    internalFlag,
    createdAt,
    updatedAt
}
```

You probably don't want clients deciding:

```http
GET /todos?internalFlag=true
```

or:

```http
GET /todos?userId=someoneElse
```

unless you've intentionally designed those filters.

Your API should define:

> These are the fields clients are allowed to filter by.

That's API design.

---

# 12. Filtering and authorization are different

This is a very important security point.

Suppose:

```http
GET /todos?userId=USER_B
```

If Rahul is logged in as User A, allowing:

```js
Todo.find({
    userId: req.query.userId
});
```

could let User A request User B's data.

Instead, ownership should normally come from trusted authentication context:

```js
{
    userId: req.user.id
}
```

not from arbitrary client input.

Conceptually:

```text
Client-controlled:
status
priority
search

Server-controlled:
userId
tenantId
authorization scope
```

The exact rules depend on your application, but the principle is extremely important.

You learned this idea earlier in authorization: ownership queries should constrain the resource to the authenticated user, rather than simply finding by resource ID.

---

# 13. Filtering + ownership

Suppose User A requests:

```http
GET /todos?status=pending
```

The service/repository might conceptually construct:

```js
{
    userId: req.user.id,
    status: "pending"
}
```

Now the database query means:

> Give me pending todos belonging to this authenticated user.

This is much safer than:

```js
{
    status: "pending"
}
```

if the endpoint is supposed to be user-specific.

# 14. Filtering + pagination

Now let's combine what we've learned.

Request:

```http
GET /api/v1/todos
    ?status=pending
    &page=2
    &limit=20
```

Conceptually:

```text
status=pending
       ↓
Filter matching todos
       ↓
page=2
       ↓
skip first 20
       ↓
limit 20
       ↓
return results
```

Repository query:

```js
Todo.find({
    status: "pending"
})
.skip(20)
.limit(20);
```

But remember:

**production code should also use a deterministic sort**, which we'll cover in Lesson 18.8.

---

# 15. Pagination metadata must use the filtered dataset

This connects directly to Lesson 18.5.

Suppose:

```text
All todos = 500
Completed todos = 123
```

Request:

```http
GET /todos?status=completed&limit=20
```

The correct count is:

```js
Todo.countDocuments({
    status: "completed"
});
```

Result:

```text
123
```

Then:

```text
totalItems = 123
totalPages = ceil(123 / 20)
           = 7
```

Not:

```text
totalItems = 500
```

because we're not paginating all 500 records.

We're paginating the filtered dataset.

Now we can visualize:

```text

    ├── status=pending
```

```text

      │
```

# 17. Common filter types

Not all filters are simple equality checks.

We can have:

### Exact value

```http
?status=completed
```

### Multiple exact values

```http
?status=completed&priority=high
```

### Boolean

```http
?archived=true
```

### Numeric comparison

For example:

```http
?priceMin=100&priceMax=500
```

Conceptually:

```js
{
    price: {
        $gte: 100,
        $lte: 500
    }
}
```

### Date range

For example:

```http
?from=2026-01-01&to=2026-08-01
```

Conceptually:

```js
{
    createdAt: {
        $gte: from,
        $lte: to
    }
}
```

These are more advanced filters.

We'll build toward them rather than putting everything into one giant query function.

---

# 18. Filtering numbers

Suppose products have:

```js
{
    price: 499
}
```

A request might be:

```http
GET /products?minPrice=200
```

The filter could become:

```js
{
    price: {
        $gte: 200
    }
}
```

Or:

```http
GET /products?maxPrice=1000
```

could become:

```js
{
    price: {
        $lte: 1000
    }
}
```

Together:

```http
GET /products?minPrice=200&maxPrice=1000
```

could become:

```js
{
    price: {
        $gte: 200,
        $lte: 1000
    }
}
```

This is much more powerful than simple equality filtering.

---

# 19. But query values arrive as strings

This is another important backend concept.

HTTP:

```http
GET /products?minPrice=200
```

gives you something like:

```js
req.query.minPrice
```

which is:

```text
"200"
```

not:

```text
200
```

So your application needs to parse and validate it.

Conceptually:

```js
const minPrice = Number(req.query.minPrice);
```

But again:

```js
Number("hello")
```

becomes:

```text
NaN
```

So simply converting isn't enough.

We need validation.

---

# 20. Don't build MongoDB operators directly from the URL

Avoid designs like:

```http
GET /products?price[$gte]=100
```

and then blindly passing:

```js
req.query
```

into MongoDB.

The API should define its own clean contract:

```http
GET /products?minPrice=100
```

and internally translate:

```text
minPrice
   ↓
$gte
```

This creates a clear boundary between:

```text
HTTP API
```

and:

```text
MongoDB query language
```

That's a strong backend design principle.

---

# 21. Filtering belongs across layers

Let's use our architecture:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
MongoDB
```

Where should filtering happen?

### Controller

Extract the HTTP query parameters:

```text
status
priority
page
limit
```

### Validation

Check:

```text
Is status valid?
Is priority valid?
Is page valid?
Is limit valid?
```

### Service

Apply application/business rules.

For example:

```text
"Users may only query their own todos."
```

### Repository

Convert the trusted filter into a MongoDB query:

```js
Todo.find(filter)
```

This separation is important.

---

# 22. Don't make the controller build MongoDB queries

Avoid:

```js
const filter = {
    status: req.query.status,
    priority: req.query.priority,
    userId: req.user.id
};

const todos = await Todo.find(filter);
```

inside the controller.

Why?

Because now the controller knows:

```text
HTTP
+
business rules
+
MongoDB
```

Instead, the controller should remain relatively thin.

Conceptually:

```text
Controller
    ↓
service.getTodos({
    userId,
    filters,
    pagination
})
```

Then:

```text
Service
    ↓
Repository
```

and the repository handles MongoDB details.

This follows the layered architecture we've been building throughout the course.

# 23. A clean query object

One useful pattern is to convert the request into a structured object.

Request:

```http
GET /todos?status=pending&priority=high&page=2&limit=20
```

After validation:

```js
{
    filters: {
        status: "pending",
        priority: "high"
    },
    pagination: {
        page: 2,
        limit: 20
    }
}
```

The service can then work with this clean structure.

Repository might receive:

```js
todoRepository.findMany({
    userId,
    filters,
    pagination
});
```

This becomes extremely useful as our query system grows.

# 26. Filtering and response metadata

Suppose:

```text
All todos: 500
Pending high-priority todos: 63
limit: 20
page: 2
```

Then:

```text
totalItems = 63
totalPages = ceil(63 / 20)
           = 4
```

Metadata:

```json
{
  "page": 2,
  "limit": 20,
  "totalItems": 63,
  "totalPages": 4,
  "hasNextPage": true,
  "hasPreviousPage": true
}
```

Notice how filtering directly affects pagination.

That's why these features can't really be designed independently.

# 27. Filtering and indexes

Filtering also introduces a performance question.

Suppose we frequently run:

```js
Todo.find({
    status: "completed"
});
```

and there are:

```text
10 million todos
```

MongoDB may need an efficient way to locate:

```text
status = completed
```

That's where **indexes** come in.

We'll reach:

```text
18.11 MongoDB indexes
18.12 Compound indexes
```

later.

For now, remember:

> **A filter describes what you want; an index can help the database find it efficiently.**

---

# 28. Filtering does not mean changing the data

This sounds obvious, but it's worth making explicit.

```js
Todo.find({
    status: "completed"
});
```

doesn't modify anything.

It only selects documents.

Filtering is a **read operation**.

It doesn't:

```text
❌ update
❌ delete
❌ modify
```

the matching documents.

# 29. Common beginner mistakes

### Mistake 1 — Passing all query parameters to MongoDB

```js
Todo.find(req.query);
```

❌ Avoid this as a general API design.

---

### Mistake 2 — Trusting filter values

```js
status = req.query.status;
```

without validation.

❌ The client controls it.

---

### Mistake 3 — Allowing ownership to come from the client

```js
{
    userId: req.query.userId
}
```

❌ Dangerous for user-owned resources.

Use authenticated identity and authorization rules.

---

### Mistake 4 — Counting the wrong dataset

```js

```

```js

```

❌ Metadata becomes incorrect.

---

### Mistake 5 — Mixing search with filtering

```text

```

and:

```text

```

are not necessarily the same thing.

# 🧠 What you should remember

The core idea of filtering is:

> **Filtering reduces the dataset before pagination is applied.**

For example:

```http
GET /todos?status=completed&page=2&limit=20
```

means:

```text
All todos
    ↓
completed only
    ↓
page 2
    ↓
skip 20
    ↓
limit 20
```

The most important rules:

```text
1. Don't blindly pass req.query to MongoDB.
2. Allow-list supported filters.
3. Validate filter values.
4. Keep authorization/ownership separate from client-controlled filters.
5. Count the filtered dataset for pagination metadata.
6. Keep MongoDB query construction in the repository layer.
```

And our evolving API architecture is:

```text
Filtering
    +
Search
    +
Sorting
    +
Pagination
    ↓
Reusable query system
```

That is exactly where Phase 18 is heading.

## 🧪 Mini Exercise

Suppose your Todo API supports:

```text
status = pending | completed
priority = low | medium | high
```

A client sends:

```http
GET /api/v1/todos?status=pending&priority=high&page=3&limit=10
```

Try to answer:

1. What is the filter object?
    
2. What is `skip`?
    
3. What does `totalItems` represent?
    
4. Should `userId` come from `req.query.userId` or authenticated user information?
    
5. Should `search` be treated as the same thing as `status`?
    

### Answers

```js
filter = {
    status: "pending",
    priority: "high"
};
```

```text
skip = (3 - 1) × 10
     = 20
```

`totalItems` means:

> Number of todos matching the applicable filter/ownership scope.

For a user-owned Todo API, ownership should come from the authenticated user context, **not** an arbitrary `userId` supplied by the client.

And:

```text
status=pending
```

is filtering, while:

```text
search=learn
```

is a text-search concept.
