# Lesson 18.7 — Search

In **18.6**, we learned filtering:

```http
GET /api/v1/todos?status=completed
```

Filtering asks:

> **Which exact category/value should I include?**

Now we move to **search**.

Search asks:

> **Does this text match what the user is looking for?**

For example:

```http
GET /api/v1/todos?search=mongo
```

could find:

```text
Learn MongoDB
MongoDB indexing
MongoDB pagination
Understanding Mongo queries
```

This is different from:

```http
GET /api/v1/todos?status=completed
```

because `status` is an exact filter, while `search` usually performs text matching.

---

# 1. Search vs filtering

Let's make the distinction very clear.

### Filtering

```http
GET /todos?status=completed
```

Means:

```text
status exactly matches "completed"
```

### Search

```http
GET /todos?search=mongo
```

Means something closer to:

```text
Find relevant text containing/matching "mongo"
```

So:

```text
Filtering → structured data
Search    → text
```

---

# 2. Simple search example

Suppose our database contains:

```text
Learn MongoDB
Learn Express
Learn React
MongoDB indexing
Node.js authentication
```

Request:

```http
GET /todos?search=mongo
```

We might want:

```text
Learn MongoDB
MongoDB indexing
```

The search term doesn't need to equal the entire title.

That's the key difference.

---

# 3. Using MongoDB regex

One basic way to implement text search is with a regular expression.

Conceptually:

```js
const filter = {
    title: {
        $regex: search
    }
};
```

For:

```text
search = "mongo"
```

MongoDB can look for text matching:

```text
mongo
```

inside the title.

---

# 4. Case sensitivity

Suppose we have:

```text
MongoDB
mongodb
MONGODB
```

A user searching:

```http
GET /todos?search=mongo
```

probably expects all of them.

We can make regex matching case-insensitive using the `i` option:

```js
const filter = {
    title: {
        $regex: search,
        $options: "i"
    }
};
```

Now:

```text
mongo
Mongo
MONGO
MoNgO
```

can match.

This is much more user-friendly.

```text
Learn MongoDB

```

Request:

```http
GET /todos?search=mongo
```

Conceptually:

```js
{

        $regex: "mongo",
        $options: "i"
    }
}
```

Possible result:

```text
Learn MongoDB
MongoDB indexing
```

# 6. Searching multiple fields

Real applications often need:

```text
title
description
```

Suppose:

```js
{
    title: "Learn database indexing",
    description: "Understand MongoDB indexes"
}
```

A search for:

```text
mongo
```

should potentially find it because `description` contains MongoDB.

We can use `$or`:

```js
const filter = {
    $or: [
        {
            title: {
                $regex: search,
                $options: "i"
            }
        },
        {
            description: {
                $regex: search,
                $options: "i"
            }
        }
    ]
};
```

Now the query means:

```text
title matches
OR
description matches
```

---

# 7. Understanding `$or`

Suppose:

```js
{
    $or: [
        { title: ... },
        { description: ... }
    ]
}
```

means:

```text
        SEARCH
          │
       ┌──┴──┐
       ▼     ▼
     title description
       │     │
       └──┬──┘
          │
          ▼
       MATCH
```

If either field matches, the document can be returned.

---

# 8. Search + filtering

Now things become interesting.

Suppose the request is:

```http
GET /todos?search=mongo&status=completed
```

We want:

```text
search matches
AND
status = completed
```

Conceptually:

```js
{
    status: "completed",

    $or: [
        {
            title: {
                $regex: "mongo",
                $options: "i"
            }
        },
        {
            description: {
                $regex: "mongo",
                $options: "i"
            }
        }
    ]
}
```

The logic is:

```text
status = completed
        AND
(
    title contains mongo
    OR
    description contains mongo
)
```

That's a very common API pattern.

---

# 9. Search + pagination

We can combine search with pagination too.

Example:

```http
GET /todos?search=mongo&page=2&limit=20
```

The conceptual pipeline is:

```text
search=mongo
      ↓
Find matching records
      ↓
Sort
      ↓
skip
      ↓
limit
      ↓
return page
```

And the pagination count must represent:

```text
number of records matching search=mongo
```

not the total number of todos.

---

# 10. Search + filter + pagination

Now we have:

```http
GET /todos
    ?search=mongo
    &status=completed
    &page=2
    &limit=20
```

Conceptually:

```text
                 TODOS
                   │
                   ▼
        status = completed
                   │
                   ▼
          search "mongo"
                   │
                   ▼
                 SORT
                   │
                   ▼
                PAGE 2
                   │
                   ▼
               LIMIT 20
                   │
                   ▼
                RESULT
```

This is becoming a real-world API query.

---

# 11. Search input is user-controlled

This is extremely important.

Suppose:

```js
const search = req.query.search;
```

The user controls:

```text
search
```

So you shouldn't blindly build complicated database expressions from it.

At minimum, you should validate things like:

```text
Is it a string?
Is it too long?
Is it empty?
Does it exceed our maximum search length?
```

For example:

```text
search = "mongo"
```

is reasonable.

But:

```text
search = "a very very very very very ... long string"
```

may be undesirable.

---

# 12. Empty search

What should this request mean?

```http
GET /todos?search=
```

Usually:

```text
search=""
```

should behave like:

```http
GET /todos
```

rather than generating a strange regex query.

So you might normalize:

```js
const search = req.query.search?.trim();
```

Then:

```js
if (search) {
    // apply search
}
```

Otherwise:

```text
No search filter
```

---

# 13. Trimming search input

Suppose the user enters:

```text
"   mongo   "
```

You probably want:

```text
"mongo"
```

not:

```text
"   mongo   "
```

So:

```js
const search = req.query.search?.trim();
```

is a simple useful normalization step.

---

# 14. Search length

A good API should generally put a reasonable limit on search input.

For example:

```text
maximum = 100 characters
```

The exact number depends on the application.

Why?

Because search queries can become expensive.

You don't want a client sending extremely large input and forcing expensive database work.

---

# 15. Regex search has performance concerns

This is one of the most important lessons.

A query such as:

```js
{
    title: {
        $regex: "mongo",
        $options: "i"
    }
}
```

is convenient.

But regex searching can become expensive, especially when:

```text
large collection
+
many documents
+
unoptimized regex
```

are involved.

For a small project:

```text
10,000 documents
```

you might not notice.

For:

```text
10 million documents
```

you absolutely need to think about search architecture.

---

# 16. Why search can be expensive

Imagine:

```text
10,000,000 documents
```

and you ask:

```text
Find documents where title contains "mongo"
```

The database may need to inspect a large number of titles.

That's very different from an indexed equality lookup like:

```js
{
    status: "completed"
}
```

with a suitable index.

So:

```text
Filtering
```

and:

```text
Text search
```

have different performance characteristics.

---

# 17. Prefix vs contains search

Consider:

```text
MongoDB tutorial
```

Search:

```text
mongo
```

This is a prefix-like match.

Search:

```text
ongo
```

is a substring match.

Search:

```text
DB tut
```

is more complicated.

These different search patterns can have very different performance characteristics.

That's one reason production applications often use proper search indexes or dedicated search systems rather than relying only on regex.

---

# 18. MongoDB text indexes

MongoDB also provides text-search capabilities through text indexes.

Conceptually:

```js
todoSchema.index({
    title: "text",
    description: "text"
});
```

Then MongoDB can support text-search queries using its text-search functionality.

This is a different approach from:

```js
$regex
```

and can be much more appropriate for actual text-search requirements.

But text indexes also have their own behavior and limitations.

The important lesson right now is:

> **Don't automatically assume regex is the best production search solution.**

---

# 19. Regex vs text search

Think of them like this:

|Approach|Good for|
|---|---|
|Exact filter|`status=completed`|
|Regex|Simple partial matching|
|Text index|Basic full-text search|
|Dedicated search engine|Advanced search|

For our learning project, regex helps us understand the concept.

For a serious production application, we choose based on:

```text
dataset size
search requirements
ranking
performance
language support
fuzzy matching
autocomplete
```

---

# 20. Search ranking

Suppose the user searches:

```text
mongo
```

and we have:

```text
MongoDB
Learn MongoDB
MongoDB indexing
Building APIs with MongoDB
```

Which result should appear first?

That's a **ranking** problem.

Simple regex doesn't naturally give you sophisticated relevance ranking.

Real search systems may consider:

```text
exact match
word frequency
field importance
relevance
recency
```

For example:

```text
MongoDB
```

might rank higher than:

```text
Building APIs with MongoDB
```

This is one reason search becomes a separate engineering problem.

---

# 21. Search is not just "add regex"

A beginner may think:

```text
Search = $regex
```

But production search involves:

```text
Search
├── input validation
├── normalization
├── matching
├── indexing
├── performance
├── relevance
├── pagination
└── security
```

That's why we're treating search as its own lesson.

# 22. Searching one field

For a simple Todo API:

```js
const filter = {};

if (search) {
    filter.title = {
        $regex: search,
        $options: "i"
    };
}
```

Conceptually this is enough to understand the basic mechanism.

# 23. Searching multiple fields

For:

```text
title
description
```

we can use:

```js
if (search) {
    filter.$or = [
        {
            title: {
                $regex: search,

            description: {
```

```text

```

can match either field.

# 24. Combining `$or` with other filters

Suppose:

```text
status = pending
search = mongo
```

The query conceptually becomes:

```js
{
    status: "pending",

    $or: [
        {
            title: {
                $regex: "mongo",
                $options: "i"
            }
        },
        {
            description: {
                $regex: "mongo",
                $options: "i"
            }
        }
    ]
}
```

Remember the logic:

```text
status = pending

AND

(
    title matches mongo
    OR
    description matches mongo
)
```

This is an important MongoDB query-building pattern.

---

# 25. Search input should not become arbitrary MongoDB syntax

A clean API might expose:

```http
GET /todos?search=mongo
```

The client shouldn't need to know that internally you're using:

```text
$regex
$or
$options
```

That's your implementation detail.

Your API contract should remain simple.

```text
HTTP API
   ↓
search=mongo
   ↓
Application query
   ↓
MongoDB query
```

This separation makes it easier to change your database/search implementation later.

---

# 26. Search and authorization

Search must still respect authorization.

Suppose a user owns:

```text
100 todos
```

and another user owns:

```text
100 todos
```

User A sends:

```http
GET /todos?search=password
```

The query must search **User A's accessible todos**, not everyone's todos.

Conceptually:

```js
{
    userId: authenticatedUserId,

    $or: [
        { title: searchCondition },
        { description: searchCondition }
    ]
}
```

The search term does not replace authorization.

It is only another condition.

---

# 27. Search + ownership + filter

A realistic query could therefore be:

```js
{
    userId: authenticatedUserId,
    status: "pending",

    $or: [
        {
            title: {
                $regex: search,
                $options: "i"
            }
        },
        {
            description: {
                $regex: search,
                $options: "i"
            }
        }
    ]
}
```

This means:

```text
                    Accessible todos
                          │
                          ▼
                  status = pending
                          │
                          ▼
                 search "mongo"
                          │
                          ▼
                       results
```

That's a realistic backend query.

---

# 28. Search and pagination metadata

Suppose:

```text
All user todos = 1,000
Search matches = 73
limit = 20
```

Then:

```text
totalItems = 73
```

and:

```text
totalPages = ceil(73 / 20)
           = 4
```

Not:

```text
totalItems = 1,000
```

Again:

> **Pagination metadata describes the filtered/search result set.**

This principle from Lesson 18.5 continues to apply.

---

# 29. Search normalization

A useful search pipeline can be:

```text
Raw query
   ↓
Trim
   ↓
Validate
   ↓
Normalize
   ↓
Build search condition
   ↓
Execute
```

For example:

```text
"   MongoDB   "
       ↓
"MongoDB"
       ↓
validated
       ↓
search condition
```

Later, normalization could also include things such as:

```text
lowercase
Unicode normalization
special character handling
```

depending on your requirements.

---

# 30. Don't over-engineer too early

For our starter backend, don't immediately build:

```text
Elasticsearch
OpenSearch
MongoDB Atlas Search
vector search
fuzzy ranking
autocomplete
```

unless the project actually needs them.

Start with:

```text
simple search contract
        ↓
validated input
        ↓
appropriate MongoDB search
        ↓
pagination
```

Then upgrade when requirements justify it.

This is a good engineering habit:

> **Build the simplest solution that meets the current requirement, but keep the architecture replaceable.**

Using our architecture:

```text

  ↓
Controller
  ↓
Service
  ↓

  ↓
```

### Controller

Extract:

```text

```

### Validation


Decide:

```text

```

### Repository

Translate:



## 🧪 Mini Exercise

Suppose the API receives:

```http
GET /api/v1/todos?search=react&status=pending&page=2&limit=10
```

Answer these:

**1.** What is the search term?

**2.** What is the exact filter?

**3.** What is the `skip` value?

**4.** If 37 todos match the search + filter, what is `totalPages`?

**5.** Should the search query be allowed to search todos belonging to other users?

### Answers

```text
1. search = "react"

2. status = "pending"

3. skip = (2 - 1) × 10
        = 10

4. totalPages = ceil(37 / 10)
              = 4

5. No.
   Search must remain inside the user's authorized dataset.
```

So conceptually:

```text
authenticated user's todos
          ↓
status = pending
          ↓
search = react
          ↓
sort
          ↓
skip 10
          ↓
limit 10
          ↓
response + pagination metadata
```

That is the search pipeline we want to understand before moving on.
