---

# 1. What is sorting?

Sorting means deciding **the order in which records are returned**.

Suppose we have:

```text
Todo A → createdAt: Jan 1
Todo B → createdAt: Jan 5
Todo C → createdAt: Jan 3
```

Without explicit sorting, we shouldn't assume the database will always return:

```text
A
C
B
```

or:

```text
B
C
A
```

Instead, our API should explicitly tell the database:

> Sort these records by `createdAt`.

For example:

```js
Todo.find().sort({
    createdAt: -1
});
```

`-1` means descending.

So:

```text
Jan 5
Jan 3
Jan 1
```

---

# 2. Ascending vs descending

MongoDB uses:

```text
1
```

for ascending order:

```text
A → B → C
```

and:

```text
-1
```

for descending order:

```text
C → B → A
```

For numbers:

```text
1 → 10 → 20 → 30
```

is ascending.

And:

```text
30 → 20 → 10 → 1
```

is descending.

---

# 3. Simple Mongoose sorting

Suppose:

```js
Todo.find().sort({
    createdAt: -1
});
```

This means:

```text
Find todos
     ↓
Sort by createdAt
     ↓
Newest first
```

For oldest first:

```js
Todo.find().sort({
    createdAt: 1
});
```

---

# 4. API query parameters

A frontend might send:

```http
GET /api/v1/todos?sort=createdAt
```

meaning:

```text
oldest → newest
```

Or:

```http
GET /api/v1/todos?sort=-createdAt
```

meaning:

```text
newest → oldest
```

This `-field` convention is common and convenient.

So:

```text
createdAt
```

means ascending.

```text
-createdAt
```

means descending.

---

# 5. Why not just pass `req.query.sort` directly?

You might be tempted to write:

```js
const sort = req.query.sort;

Todo.find().sort(sort);
```

For example:

```http
GET /todos?sort=createdAt
```

This might appear convenient.

But there is an important problem:

> **The client controls the value.**

A production API should not blindly accept arbitrary database field names.

That's why the next lesson is specifically:

```text
18.9 Allow-listing sort fields
```

Your roadmap deliberately puts allow-listing immediately after sorting.

For now, understand the basic sorting mechanism.

---

# 6. Why sorting matters so much for pagination

This is probably the most important idea in this lesson.

Imagine you request:

```http
GET /todos?page=1&limit=20
```

and then:

```http
GET /todos?page=2&limit=20
```

What determines which records belong to page 1 and page 2?

The **ordering**.

If the ordering changes between requests, pagination can become unreliable.

---

# 7. The unstable pagination problem

Suppose you have:

```text
100 todos
```

and request:

```text
page = 1
limit = 20
```

The database returns:

```text
Todo 1
Todo 2
...
Todo 20
```

Then a new todo is inserted.

Now the database has:

```text
101 todos
```

You request:

```text
page = 2
limit = 20
```

If you're sorting by newest first, the dataset has shifted.

You might now see:

```text
Todo 20
Todo 21
...
```

or miss/duplicate records depending on the ordering and timing.

This is one reason pagination needs a **stable, deterministic sort**.

---

# 8. Always think about the ordering

When building:

```http
GET /todos?page=2&limit=20
```

ask:

> In what order are these todos?

For example:

```text
Newest first
```

could mean:

```js
.sort({
    createdAt: -1
});
```

Now page boundaries have a defined ordering.

---

# 9. The ideal default sort

For many APIs, a good default is:

```js
{
    createdAt: -1
}
```

meaning:

```text
Newest first
```

For example:

```text
Today
Yesterday
2 days ago
3 days ago
...
```

This is often useful for:

```text
posts
notifications
todos
orders
messages
activities
```

But it's not a universal rule.

The correct default depends on the resource.

---

# 10. Sorting by updated time

Sometimes you want:

```http
GET /todos?sort=-updatedAt
```

This means:

```text
Recently modified first
```

Useful for:

```text
documents
notes
projects
tickets
```

Example:

```text
Note A → updated 5 minutes ago
Note B → updated yesterday
Note C → updated 7 days ago
```

Result:

```text
A
B
C
```

---

# 11. Sorting by priority

Suppose:

```text
high
medium
low
```

You might want:

```text
high
medium
low
```

But here's an interesting problem:

MongoDB doesn't automatically know that:

```text
high > medium > low
```

because these are strings.

Alphabetically:

```text
high
low
medium
```

would be a different order.

So sorting by business priority can require a special design.

This is a good example of why:

> **Database sorting and business sorting are not always the same thing.**

---

# 12. Sorting by numeric fields

For a product API:

```js
{
    price: 499
}
```

You can do:

```js
Product.find().sort({
    price: 1
});
```

Result:

```text
₹99
₹199
₹499
₹999
```

Or:

```js
Product.find().sort({
    price: -1
});
```

Result:

```text
₹999
₹499
₹199
₹99
```

Very straightforward.

---

# 13. Multiple sort fields

Sorting can use more than one field.

Suppose:

```text
createdAt
_id
```

We could do:

```js
Todo.find().sort({
    createdAt: -1,
    _id: -1
});
```

This is extremely important.

Why?

Because two documents can have the same:

```text
createdAt
```

value.

Then `_id` gives us a deterministic tie-breaker.

---

# 14. What is a tie-breaker?

Suppose:

```text
Todo A
createdAt = 10:00:00

Todo B
createdAt = 10:00:00

Todo C
createdAt = 09:59:00
```

If we only sort by:

```js
{
    createdAt: -1
}
```

then:

```text
A/B
C
```

are ordered, but A vs B may not have a meaningful deterministic order.

Add:

```js
{
    createdAt: -1,
    _id: -1
}
```

Now:

```text
createdAt
    ↓
if equal
    ↓
_id
```

This creates a more deterministic order.

---

# 15. Deterministic sorting

This term is worth remembering:

> **Deterministic sorting means that the database has a well-defined way to order records, including ties.**

For example:

```js
{
    createdAt: -1,
    _id: -1
}
```

is more deterministic than:

```js
{
    createdAt: -1
}
```

when multiple records can have the same timestamp.

This becomes especially valuable for pagination.

---

# 16. Why `_id` is useful as a tie-breaker

MongoDB ObjectIds have ordering properties that can often be useful for deterministic ordering.

So:

```js
{
    createdAt: -1,
    _id: -1
}
```

is a common pattern.

But remember:

> `_id` is a tie-breaker, not necessarily your business ordering.

If your application has a dedicated sequence/order field, that may be more appropriate.

---

# 17. Sorting + pagination

Now combine everything.

Request:

```http
GET /todos?page=2&limit=20&sort=-createdAt
```

Conceptually:

```text
Todos
  ↓
Sort by createdAt DESC
  ↓
Skip 20
  ↓
Take 20
  ↓
Return page 2
```

In Mongoose:

```js
Todo.find()
    .sort({
        createdAt: -1
    })
    .skip(20)
    .limit(20);
```

This is the basic pattern.

# 21. Query execution order

At the API-design level, think:

```text
Request
   ↓
Validate query
   ↓
Build filters
   ↓
Build search
   ↓
Build sort
   ↓
Build pagination
   ↓
Repository
   ↓
MongoDB
```

You don't necessarily have to think of MongoDB literally executing every operation in that exact textual order.

The important thing is that your **query construction** has clear stages.

# 22. Sort syntax

A simple API convention is:

```text
sort=createdAt
```

for ascending.

And:

```text
sort=-createdAt
```

for descending.

Another API might use:

```text
sortBy=createdAt&order=desc
```

Both are valid designs.

For our learning architecture, the first style is concise:

```text
sort=-createdAt
```

---

# 23. Multiple sort fields from the client

Later you might want:

```http
GET /todos?sort=-priority,createdAt
```

meaning:

```text
priority DESC
then
createdAt ASC
```

But this becomes more complicated because now the API has to parse:

```text
-priority,createdAt
```

into:

```js
{
    priority: -1,
    createdAt: 1
}
```

This is useful, but **don't implement arbitrary sort fields yet**.

Why?

Because Lesson 18.9 specifically teaches us how to safely allow-list sorting fields.

---

# 24. Why allow-list sorting fields?

Suppose your document contains:

```js
{
    title,
    status,
    priority,
    userId,
    passwordHash,
    internalNotes,
    createdAt
}
```

You might only want users to sort by:

```text
createdAt
updatedAt
title
```

You probably don't want:

```text
passwordHash
```

or:

```text
internalNotes
```

to become public sort options.

So your API should define:

```text
Allowed sort fields:
createdAt
updatedAt
title
```

That's an **allow-list**.

---

# 25. Sorting and security

Allow-listing isn't only about performance.

It also makes your API contract predictable.

Instead of:

```text
"Give me any database field you know."
```

the API says:

```text
"You may sort by these specific fields."
```

This is much better API design.

---

# 26. Sorting and database indexes

Sorting can also affect performance.

Suppose you frequently run:

```js
Todo.find({
    userId
}).sort({
    createdAt: -1
});
```

An appropriate index can make this much more efficient.

For example, conceptually:

```js
todoSchema.index({
    userId: 1,
    createdAt: -1
});
```

This is a **compound index**.

We'll study indexes in:

```text
18.11 MongoDB indexes
18.12 Compound indexes
```

according to your roadmap.

For now, just understand:

> **Filtering and sorting together often influence which indexes you need.**

# 27. A practical Todo repository

Eventually your repository might contain something conceptually like:

```js
async function findMany({
    filter,
    sort,
    skip,
    limit
}) {
    return Todo.find(filter)
        .sort(sort)
        .skip(skip)
        .limit(limit);
}
```

Notice what the repository receives:

```text
filter
sort
skip
limit
```

It doesn't need to know about:

```text
req.query
Express
HTTP
URLs
```

That's good separation.

---

# 28. Controller responsibility

The controller can extract the query:

```js
const {
    sort,
    page,
    limit,
    status,
    search
} = req.query;
```

Then pass structured information into the service.

Conceptually:

```js
todoService.getTodos({
    userId: req.user.id,
    filters: {
        status
    },
    search,
    sort,
    pagination: {
        page,
        limit
    }
});
```

The service can then apply business rules and pass the appropriate query information to the repository.

---

# 29. Why this separation matters

Imagine six months from now.

You decide:

```text
MongoDB → another database/search system
```

If your controller contains:

```js
Todo.find()
    .sort(...)
    .skip(...)
    .limit(...);
```

you have MongoDB details spread through your HTTP layer.

That's difficult to change.

But if you have:

```text
Controller
   ↓
Service
   ↓
Repository
```

then the database-specific implementation is concentrated in the repository.

This is exactly the architecture we've been building since Phase 13.

# 30. Default sorting

What should happen when the client doesn't provide:

```text
sort
```

For example:

```http
GET /todos
```

You should usually have a default.

For example:

```js
const sort = {
    createdAt: -1
};
```

Then:

```text
GET /todos
```

means:

```text
newest first
```

while:

```text
GET /todos?sort=title
```

could mean:

```text
title ascending
```

after validation and allow-listing.

---

# 31. Why a default is important

Without a deliberate default:

```text
GET /todos
```

may rely on database behavior that your API doesn't explicitly promise.

That's not a good contract.

Instead:

```text
API contract
     ↓
default sort
     ↓
predictable response
```

This is especially useful for pagination.

---

# 32. Sorting after data retrieval is usually a bad idea

Don't do:

```js
const todos = await Todo.find(filter);

todos.sort(...);
```

for large datasets.

Why?

Because you've already fetched the documents from MongoDB.

Imagine:

```text
1,000,000 documents
```

You don't want:

```text
MongoDB
   ↓
1,000,000 documents
   ↓
Node.js memory
   ↓
JavaScript sorting
```

Instead, let the database perform the query and sorting:

```text
MongoDB
   ↓
filter
   ↓
sort
   ↓
pagination
   ↓
20 documents
   ↓
Node.js
```

Much better.

---

# 33. The database should do database work

This is an important backend principle.

Bad:

```text
Database → huge dataset → Node.js → filter/sort → response
```

Better:

```text
Database
   ↓
filter
   ↓
sort
   ↓
pagination
   ↓
small result
   ↓
Node.js
```

The database is designed to efficiently perform data operations.

Don't unnecessarily move large datasets into your application server.

# 34. Sorting strings

Suppose:

```text
title
```

contains:

```text
Apple
Banana
Mango
```

Sorting:

```js
{
    title: 1
}
```

can produce alphabetical ordering.

But real-world string sorting can become more complicated because of:

```text
case
locale
Unicode
collation
```

For example:

```text
apple
Apple
APPLE
```

may not behave exactly how a user expects depending on database/collation configuration.

So string sorting has its own considerations.

You don't need to solve all of them today.

# 35. Sorting dates

Dates are usually a very useful sort field.

For example:

```js
{
    createdAt: -1
}
```

means:

```text
latest → oldest
```

And:

```js
{
    createdAt: 1
}
```

means:

```text
oldest → latest
```

This is one of the most common API sorting patterns.

---

# 36. Sorting and timestamps

One subtle issue:

Two records can have very similar timestamps.

Suppose:

```text
A → 2026-08-26T10:00:00.000Z
B → 2026-08-26T10:00:00.000Z
```

Then:

```js
{
    createdAt: -1
}
```

doesn't fully distinguish them.

So:

```js
{
    createdAt: -1,
    _id: -1
}
```

gives you a stronger ordering.

Remember this pattern.

It becomes especially important when we later discuss **cursor pagination** and performance.

---

# 37. Offset pagination + stable sorting

With our current page-based pagination:

```text
page
limit
skip
```

a good mental model is:

```text
stable sort
     +
skip
     +
limit
```

For example:

```js
Todo.find(filter)
    .sort({
        createdAt: -1,
        _id: -1
    })
    .skip(skip)
    .limit(limit);
```

This is much more reliable than:

```js
Todo.find(filter)
    .skip(skip)
    .limit(limit);
```

with no deliberate ordering.

---

# 38. Why this matters in real applications

Imagine a social feed.

You request:

```text
page 1
```

and receive:

```text
Post A
Post B
Post C
...
```

While you're browsing, new posts arrive.

If your ordering isn't properly defined, page boundaries can become confusing.

That's why production feeds often move beyond simple offset pagination and use cursor-based approaches.

You already learned about page vs cursor pagination in 18.2.

Sorting is one of the foundations that makes cursor pagination possible.

# 39. Sorting and cursor pagination

Cursor pagination typically needs something like:

```text
createdAt
+
_id
```

to define an ordered sequence.

For example:

```text
Newest
  ↓
Post A
Post B
Post C
Post D
...
```

The cursor says:

> Continue after this position in the ordered dataset.

So sorting isn't just a UI feature.

It's part of the underlying pagination architecture.

```text
3. MongoDB

4. To provide a deterministic tie-breaker
   when multiple products have the same price.

5. No.
   We should allow-list supported sort fields.
```

So the practical pattern we're moving toward is:

```js
Todo.find(filter)
    .sort({
        createdAt: -1,
        _id: -1
    })
    .skip(skip)
    .limit(limit);
```
