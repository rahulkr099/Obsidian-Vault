# Lesson 18.9 — Allow-Listing Sort Fields

In **18.8**, we learned how sorting works:

```http
GET /api/v1/todos?sort=-createdAt
```

and we saw why we **shouldn't blindly trust** a client-provided sort field.

Your Phase 18 roadmap explicitly places **18.9 — Allow-listing sort fields** immediately after sorting.

Today we'll solve that problem properly.

---

# 1. The problem

Imagine your API receives:

```http
GET /api/v1/todos?sort=createdAt
```

You might write:

```js
const sort = req.query.sort;

Todo.find().sort(sort);
```

It looks convenient.

But the client controls:

```text
req.query.sort
```

So the client can request arbitrary fields:

```http
GET /todos?sort=password
```

```http
GET /todos?sort=internalNotes
```

```http
GET /todos?sort=someInternalField
```

Even if these don't immediately create a security vulnerability, this is **poor API design**.

Your API should explicitly decide:

> Which fields are allowed to be used for sorting?

---

# 2. What is an allow-list?

An **allow-list** is simply a list of values that you explicitly permit.

For example:

```js
const allowedSortFields = [
    "createdAt",
    "updatedAt",
    "title"
];
```

Then:

```text
createdAt → allowed
updatedAt → allowed
title     → allowed

password  → rejected
internal  → rejected
anything  → rejected
```

Think:

```text
Client
  │
  ▼
"Can I sort by X?"
  │
  ▼
Allow-list
  │
  ├── YES → continue
  │
  └── NO  → reject
```

---

# 3. Why this is better

Instead of allowing:

```text
sort = ANY_DATABASE_FIELD
```

your API contract becomes:

```text
sort = one of the supported fields
```

For example:

```text
createdAt
updatedAt
title
```

This gives you:

- predictable API behavior
    
- better security boundaries
    
- easier documentation
    
- easier testing
    
- easier indexing decisions
    
- less accidental database coupling
    

---

# 4. Public API names vs database field names

Here's a useful improvement.

You don't have to expose your actual database field names.

Suppose MongoDB has:

```js
{
    createdAt,
    updatedAt,
    title
}
```

You could expose:

```http
GET /todos?sort=created
```

instead of:

```http
GET /todos?sort=createdAt
```

Then map it internally:

```js
const sortFields = {
    created: "createdAt",
    updated: "updatedAt",
    title: "title"
};
```

Now:

```text
Client
  │
  │ sort=created
  ▼
API mapping
  │
  │ createdAt
  ▼
MongoDB
```

This is even cleaner.

---

# 5. Why mapping is powerful

Imagine later you change your database field:

```text
createdAt
```

to:

```text
created_at
```

If your frontend directly sends:

```text
createdAt
```

you have coupled the frontend to your database schema.

But if the frontend sends:

```text
created
```

your API can internally change:

```js
created: "created_at"
```

without changing the frontend contract.

That's a powerful architectural idea:

> **Your API contract doesn't have to expose your database structure.**

# 6. Simple allow-list

Let's start with the simplest version.

```js
const allowedSortFields = [
    "createdAt",
    "updatedAt",
    "title"
];
```

Then:

```js
if (!allowedSortFields.includes(sortField)) {
    throw new Error("Invalid sort field");
}
```

Conceptually:

```text
sort=createdAt
      ↓
allowedSortFields.includes()
      ↓
     true
      ↓
   continue
```

But:

```text
sort=password
      ↓
allowedSortFields.includes()
      ↓
     false
      ↓
    reject
```

---

# 7. Supporting descending order

We previously used:

```http
GET /todos?sort=-createdAt
```

So our allow-list needs to understand:

```text
createdAt
```

and:

```text
-createdAt
```

as the same field with different directions.

We can parse the `-`.

Conceptually:

```js
const descending = sort.startsWith("-");

const field = descending
    ? sort.slice(1)
    : sort;
```

For:

```text
createdAt
```

we get:

```text
field = createdAt
descending = false
```

For:

```text
-createdAt
```

we get:

```text
field = createdAt
descending = true
```

---

# 8. Then validate the field

Now:

```js
const allowedSortFields = [
    "createdAt",
    "updatedAt",
    "title"
];

if (!allowedSortFields.includes(field)) {
    throw new Error("Invalid sort field");
}
```

This is the important part.

We validate:

```text
createdAt
```

not:

```text
-createdAt
```

because `-` is a direction indicator.

---

# 9. Convert it to MongoDB sort syntax

Once validated:

```js
const direction = descending ? -1 : 1;
```

Then:

```js
const sort = {
    [field]: direction
};
```

For:

```text
sort=createdAt
```

we get:

```js
{
    createdAt: 1
}
```

For:

```text
sort=-createdAt
```

we get:

```js
{
    createdAt: -1
}
```

---

# 10. Complete basic implementation

Conceptually:

```js
const allowedSortFields = [
    "createdAt",
    "updatedAt",
    "title"
];

function parseSort(sort) {
    const descending = sort.startsWith("-");

    const field = descending
        ? sort.slice(1)
        : sort;

    if (!allowedSortFields.includes(field)) {
        throw new Error("Invalid sort field");
    }

    return {
        [field]: descending ? -1 : 1
    };
}
```

Then:

```js
const sort = parseSort(req.query.sort);
```

and:

```js
Todo.find(filter).sort(sort);
```

Now your database only receives validated sort fields.

---

# 11. What happens with an invalid field?

Request:

```http
GET /todos?sort=password
```

Pipeline:

```text
sort=password
      ↓
field=password
      ↓
allow-list
      ↓
NOT FOUND
      ↓
reject
```

You could return:

```http
400 Bad Request
```

with:

```json
{
  "success": false,
  "message": "Invalid sort field"
}
```

This is much better than blindly passing it to MongoDB.

---

# 12. What about `-password`?

Request:

```http
GET /todos?sort=-password
```

We first remove the direction:

```text
-password
   ↓
password
```

Then validate:

```text
password ∈ allowed fields?
```

No.

Therefore:

```text
400 Bad Request
```

Good.

---

# 13. Use a mapping object

For a production-style API, I prefer a mapping object over just an array.

For example:

```js
const sortFieldMap = {
    created: "createdAt",
    updated: "updatedAt",
    title: "title"
};
```

Now the public API becomes:

```http
GET /todos?sort=created
```

and internally:

```text
created
   ↓
createdAt
```

---

# 14. Complete mapping approach

Conceptually:

```js
const sortFieldMap = {
    created: "createdAt",
    updated: "updatedAt",
    title: "title"
};

function parseSort(sort) {
    const descending = sort.startsWith("-");

    const publicField = descending
        ? sort.slice(1)
        : sort;

    const databaseField = sortFieldMap[publicField];

    if (!databaseField) {
        throw new Error("Invalid sort field");
    }

    return {
        [databaseField]: descending ? -1 : 1
    };
}
```

Now:

```text
sort=created
```

becomes:

```js
{
    createdAt: 1
}
```

And:

```text
sort=-created
```

becomes:

```js
{
    createdAt: -1
}
```

---

# 15. Why I like the mapping approach

Imagine your database contains:

```js
{
    createdAt,
    updatedAt,
    internalPriority,
    passwordHash,
    refreshTokenHash
}
```

Your public API can expose only:

```text
created
updated
```

The API doesn't reveal:

```text
internalPriority
passwordHash
refreshTokenHash
```

This is a clean abstraction boundary.

# 16. Default sort

What happens when the user doesn't send:

```text
sort
```

For example:

```http
GET /todos
```

You should have a default.

For example:

```js
const sort = {
    createdAt: -1,
    _id: -1
};
```

Meaning:

```text
newest first
```

with `_id` as a tie-breaker.

---

# 17. Default sort with mapping

We can define:

```js
const sortFieldMap = {
    created: "createdAt",
    updated: "updatedAt",
    title: "title"
};
```

Then:

```js
const requestedSort = req.query.sort;

if (!requestedSort) {
    return {
        createdAt: -1,
        _id: -1
    };
}
```

Otherwise parse the requested field.

This gives the API predictable behavior.

---

# 18. Why should the default be deterministic?

Suppose:

```text
100 todos
```

and:

```http
GET /todos?page=1&limit=20
```

If you don't define an ordering, you're leaving page boundaries less predictable.

Instead:

```js
{
    createdAt: -1,
    _id: -1
}
```

gives:

```text
newest → oldest
```

with a tie-breaker.

This connects directly to what we learned in 18.8.

---

# 19. Multiple sort fields

Suppose you want:

```http
GET /todos?sort=-created,title
```

This means:

```text
createdAt DESC
then
title ASC
```

You could support this eventually.

The parser would:

```text
-created,title
       ↓
split by comma
       ↓
-created
title
       ↓
validate each
       ↓
convert each
```

Result:

```js
{
    createdAt: -1,
    title: 1
}
```

But there's a reason I wouldn't start here.

---

# 20. Don't overcomplicate the API

For our starter architecture, begin with:

```text
sort=created
sort=-created
sort=title
sort=-title
```

Once that is stable, you can add:

```text
sort=-created,title
```

if your application needs it.

This follows a good principle:

> **Add flexibility when there is a real requirement for it.**

Don't make the query parser unnecessarily complicated from day one.

Suppose your API supports:


Your API documentation can simply say:

# 22. Allow-listing and frontend development

Imagine your React frontend has a dropdown:


This makes the frontend/backend contract very clear.

The repository shouldn't receive:


Instead:

```text
 ↓

 ↓

 ↓
```

The repository should receive something more trusted:

```js

    createdAt: -1
}
```

rather than:

```text

```

# 26. A reusable `parseSort`

Conceptually:

```js
function parseSort(sort, fieldMap, defaultSort) {
    if (!sort) {
        return defaultSort;
    }

    const descending = sort.startsWith("-");

    const publicField = descending
        ? sort.slice(1)
        : sort;

    const databaseField = fieldMap[publicField];

    if (!databaseField) {
        throw new Error("Invalid sort field");
    }

    return {
        [databaseField]: descending ? -1 : 1
    };
}
```

Then each resource can provide its own mapping.

# 30. What about invalid direction syntax?

Suppose the client sends:

```http
GET /todos?sort=--created
```

Our simple parser does:

```text
--created
   ↓
remove first "-"
   ↓
-created
```

Then:

```text
-created
```

is not in the allow-list.

So:

```text
400 Bad Request
```

Good.

# 31. What about an empty value?

```http
GET /todos?sort=
```

Depending on your query parser, you may receive:

```text
sort = ""
```

You can treat that as:

```text
no sort specified
```

and use the default.

For example:

```js
if (!sort?.trim()) {
    return defaultSort;
}
```

This is a small but useful normalization.

---

# 32. What about whitespace?

A client might send:

```text
sort = "  -created  "
```

Normalize:

```js
const normalizedSort = sort.trim();
```

Then process:

```text
"-created"
```

instead of:

```text
"  -created  "
```

Again:

```text
raw input
   ↓
normalize
   ↓
validate
   ↓
transform
```

This pattern will appear repeatedly throughout backend development.

# 33. Don't expose MongoDB syntax to the client

Your frontend should not send:

```text
sort={"createdAt":-1}
```

or:

```text
sort[$createdAt]=-1
```

or some other database-specific structure.

Keep the public API simple:

```text
sort=-created
```

Then your backend translates it into:

```js
{
    createdAt: -1
}
```

This is another important abstraction boundary.

# 34. Allow-listing isn't just about security

Let's be precise.

Allow-listing helps with:

### Security

Clients cannot arbitrarily request internal fields.

### Performance

You control which fields can be sorted and can prepare indexes accordingly.

### API design

The API has a clear contract.

### Maintainability

Database schema changes don't necessarily break clients.

### Documentation

The supported options are easy to describe.

So allow-listing is both a **security and architecture practice**.

Don't create one giant global list:

```js

    "createdAt",
    "updatedAt",
    "title",
    "price",
    "email",
```

Instead:

```text
Todo
  ↓

Product
  ↓
productSortFields

User
  ↓

```

Each resource knows what makes sense for itself.

# 40. Don't let the repository decide public API rules

Bad architecture:

```text
Controller
    ↓
Repository
    ↓
"Is -created allowed?"
```

Better:

```text
Controller/query layer
    ↓
validate + translate
    ↓
Service
    ↓
Repository
```

The repository is concerned with:

> How do I execute the database query?

The API/query layer is concerned with:

> What does the client request mean?

Different responsibilities.

# 41. Common mistakes

### Mistake 1

```js
.sort(req.query.sort)
```

❌ Blindly trusting the client.

---

### Mistake 2

Allowing every field:

```js
const allowed = Object.keys(Todo.schema.paths);
```

This might seem clever, but it's usually not what you want.

Your database schema and public API contract are different things.

---

### Mistake 3

Allowing database-specific syntax from clients.

❌ Don't make clients understand MongoDB.

---

### Mistake 4

No default sort.

❌ Makes ordering less predictable.

---

### Mistake 5

Duplicating sort parsing in every controller.

❌ Create a reusable query utility.

---

### Mistake 6

Allowing fields that don't make sense.

For example:

```text
sort=passwordHash
```

Even if technically possible, it's not a meaningful public API feature.

# 42. A professional mental model

Don't think:

> "I need to block bad sort values."

Think:

> **"I define the sorting capabilities my API supports."**

That's a much stronger way to design APIs.

For example:

```js
const todoSortFields = {
    created: "createdAt",
    updated: "updatedAt",
    title: "title"
};
```

This says:

> "The Todo API supports these three public sorting concepts."

Everything else is outside the API contract.
