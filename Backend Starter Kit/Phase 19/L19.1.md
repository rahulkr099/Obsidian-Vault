# Lesson 19.1 — What Is Logging?

We are now starting **Phase 19: Logging & Observability**.

You already know how a request moves through:

```text
Request
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
   ↓
Response
```

But there is a problem.

### How do you know what actually happened?

Suppose a user reports:

> "My request failed."

You cannot simply look at your code and know what happened during that particular request.

This is where **logging** comes in.

---

# 1. What is Logging?

**Logging means recording useful information about what is happening inside your application.**

For example:

```js
console.log("User logged in");
```

This is technically a log.

Another example:

```js
console.log("POST /api/v1/auth/login");
```

Again, that's logging.

But professional backend logging goes much further.

You might record:

```text
INFO
method: POST
path: /api/v1/auth/login
userId: 123
statusCode: 200
duration: 84ms
```

So, in simple words:

> **Logging is your backend keeping a record of important events and activities.**

---

# 2. Why Do We Need Logging?

Imagine your backend is running on a production server.

A user sends:

```http
POST /api/v1/todos
```

Something goes wrong.

The frontend only receives:

```json
{
  "success": false,
  "message": "Something went wrong"
}
```

That's good for security because we don't want to expose internal errors.

But now **you**, the developer, need to know:

- What request was sent?
    
- Which endpoint was called?
    
- Which user made the request?
    
- When did it happen?
    
- How long did it take?
    
- Which database operation failed?
    
- What error occurred?
    

Without logs, debugging becomes much harder.

---

# 3. Logging Is Like a Flight Recorder

Think about an airplane.

A pilot doesn't manually remember everything that happened during a flight.

The aircraft has systems that record important events.

For example:

```text
Engine started
Altitude changed
Speed changed
Warning detected
System failure
```

Later, if something goes wrong, engineers can inspect those records.

Your backend needs something similar.

```text
Server started
Request received
Authentication succeeded
Todo created
Database query failed
Request completed
```

Logs give you a history of what happened.

---

# 4. `console.log()` Is Logging

At the beginning, you may write:

```js
console.log("Server started");
```

Then:

```js
console.log("Creating user");
```

Then:

```js
console.log("User created");
```

This is useful while learning.

For example:

```js
app.post("/users", (req, res) => {
    console.log("POST /users");

    // ...
});
```

You might see:

```text
POST /users
```

in your terminal.

That's logging.

But there is a problem.

---

# 5. Why `console.log()` Isn't Enough

Imagine your production application receives thousands of requests.

Your terminal might contain:

```text
User created
POST /users
Something happened
GET /todos
User created
Error
POST /login
Todo created
GET /todos
Something happened
```

This becomes difficult to understand.

You don't know:

```text
Which user?
Which request?
Which time?
Which request ID?
Which status code?
How long did it take?
What exactly failed?
```

Professional logging solves these problems using **structured logs** and **log levels**.

We'll learn those later.

For now, understand:

```text
console.log()
      ↓
basic logging
```

but:

```text
structured logger
      ↓
professional application logging
```

---

# 6. What Should We Log?

A backend can produce many different events.

For example:

### Server events

```text
Server started
Database connected
Database disconnected
Application shutting down
```

### Request events

```text
GET /api/v1/users
POST /api/v1/todos
DELETE /api/v1/todos/123
```

### Authentication events

```text
Login successful
Login failed
Token refreshed
Logout
```

### Business events

```text
Todo created
Todo updated
Todo deleted
Password changed
```

### Error events

```text
Database error
Validation error
Unexpected exception
External API failure
```

The important idea is:

> **Logs should tell us what is happening in our application.**

---

# 7. What Should We NOT Log?

This is extremely important.

Logging can become a **security problem** if you blindly record everything.

For example, don't do:

```js
console.log(req.body);
```

for an authentication request.

Why?

Because `req.body` might contain:

```json
{
  "email": "user@example.com",
  "password": "SuperSecretPassword"
}
```

Now you've accidentally put a user's password into your logs.

That's dangerous.

Never casually log:

```text
Passwords
Access tokens
Refresh tokens
Session secrets
API keys
Credit card information
Sensitive personal data
```

We'll study this more deeply in **Lesson 19.30 — Sensitive Data in Logs**.

---

# 8. Logging vs Error Handling

These are different concepts.

### Error handling

Answers:

> **What should the application do when something goes wrong?**

For example:

```text
Database error
      ↓
Error middleware
      ↓
HTTP 500 response
```

### Logging

Answers:

> **What happened, and how can developers investigate it later?**

For example:

```text
Database error
      ↓
Error middleware
      ↓
Logger
      ↓
Record error details
      ↓
HTTP 500 response
```

So they work together.

```text
             ERROR
               │
       ┌───────┴────────┐
       ▼                ▼
Error Handler         Logger
       │                │
       ▼                ▼
HTTP Response       Error Record
```

---

# 9. Logging vs Database Storage

Another important distinction.

You might think:

> "Why don't we just store every event in MongoDB?"

Because logs and application data have different purposes.

Your MongoDB might contain:

```text
Users
Todos
Orders
Products
```

Those are **application data**.

Logs contain:

```text
Requests
Errors
Server events
Performance information
Debugging information
```

Those are **operational data**.

You generally don't want your application database becoming a giant dumping ground for logs.

Later, you'll learn about dedicated logging systems.

---

# 10. A Simple Request Log

Let's imagine this endpoint:

```js
app.get("/api/v1/todos", (req, res) => {
    res.json({
        success: true,
        data: []
    });
});
```

We could add:

```js
app.get("/api/v1/todos", (req, res) => {
    console.log("GET /api/v1/todos");

    res.json({
        success: true,
        data: []
    });
});
```

Now whenever the endpoint is called:

```text
GET /api/v1/todos
```

appears in the terminal.

This gives us basic visibility.

---

# 11. But We Want More Information

Instead of:

```text
GET /api/v1/todos
```

a professional system eventually wants something closer to:

```text
{
    "level": "info",
    "method": "GET",
    "path": "/api/v1/todos",
    "statusCode": 200,
    "duration": 42,
    "requestId": "abc123"
}
```

Now we can answer much more:

```text
What happened?
    GET request

Where?
    /api/v1/todos

What was the result?
    200

How long?
    42ms

Which request?
    abc123
```

This is why Phase 19 is more than simply learning `console.log()`.

---

# 12. Logging Across Your Architecture

Remember your architecture:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

Logging can give us visibility across these layers.

For example:

```text
Request received
       ↓
Authentication successful
       ↓
Controller started
       ↓
Todo service called
       ↓
Repository queried
       ↓
Todo created
       ↓
Response 201
```

Now imagine something fails:

```text
Request received
       ↓
Authentication successful
       ↓
Controller started
       ↓
Todo service called
       ↓
Repository queried
       ↓
Database timeout ❌
       ↓
Error handler
       ↓
Response 500
```

That's incredibly useful for debugging.

---

# 13. Logging Is Not Just For Errors

This is a common beginner mistake.

They think:

```text
logging = errors
```

Not true.

Logging can record **normal events** too.

For example:

```text
INFO  Server started
INFO  Database connected
INFO  Request received
INFO  User authenticated
INFO  Todo created
```

And:

```text
WARN  Login attempt failed
WARN  Rate limit approaching
```

And:

```text
ERROR Database connection failed
ERROR Unexpected exception
```

Later we'll organize these using **log levels**.

---

# 14. A Good Mental Model

Think of your application as a person working in an office.

Without logging:

```text
Manager:
"What happened yesterday?"

Developer:
"I don't know."
```

With logging:

```text
Manager:
"What happened yesterday?"

Developer:
"Let me check the records."
```

That's essentially what logs provide.

---

# 15. Logging in Development vs Production

During development, you might see:

```text
Server started on port 5000
Database connected
GET /todos
POST /todos
```

In production, you need much more useful information:

```text
timestamp
level
requestId
method
path
statusCode
duration
userId
error
```

And logs should generally be:

- structured
    
- searchable
    
- safe
    
- useful for debugging
    
- suitable for automated systems
    

We'll build toward this throughout Phase 19.

# 16. Your First Practical Exercise

Create a small Express application or use your current Phase 18 project.

Add:

```js
const requestLogger = (req, res, next) => {
    console.log(req.method, req.originalUrl);
    next();
};
```

Then:

```js
app.use(requestLogger);
```

Now visit:

```text
GET /healthz
```

and:

```text
GET /api/v1/todos
```

You should see something like:

```text
GET /healthz
GET /api/v1/todos
```

### Understand what happened

```text
Browser/Postman
      ↓
Express
      ↓
requestLogger
      ↓
console.log()
      ↓
next()
      ↓
Route
      ↓
Response
```

Don't worry about Pino yet.

---

# 17. One Important Rule

A log should answer a useful question.

Bad:

```js
console.log("hello");
```

Better:

```js
console.log("Database connected");
```

Even better:

```text
Database connected successfully
```

And eventually:

```json
{
  "level": "info",
  "event": "database.connected"
}
```

The goal is to make logs **useful to a human and a machine**.

Remember these five things:

### 1. Logging

> Recording important events happening inside your application.

### 2. Logs

> The records produced by your application.

### 3. `console.log()`
