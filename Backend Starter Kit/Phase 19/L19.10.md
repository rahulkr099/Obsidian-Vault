# Lesson 19.10 — Log Formatting

Now that you understand **Pino**, you have probably noticed something:

```json
{"level":30,"time":1756200000000,"pid":1234,"hostname":"linux","event":"server.started","port":5000}
```

This is excellent for machines, but while developing, it's not very pleasant for humans to read.

So today's lesson is about:

> **How do we keep structured JSON logs for production while making logs comfortable to read during development?**

---

# 1. The Problem

Our Pino logger currently produces JSON:

```js
logger.info({
    event: "server.started",
    port: 5000
});
```

Output:

```text
{"level":30,"time":1756200000000,"pid":1234,"hostname":"linux","event":"server.started","port":5000}
```

Technically this is great.

But when you're sitting in your terminal debugging your MERN backend, you'd probably prefer something like:

```text
INFO  server.started  port=5000
```

or:

```text
INFO  todo.created  userId=42 todoId=123
```

That's what **log formatting** is about.

---

# 2. Formatting vs Logging

This distinction is extremely important.

### Logging

Determines:

```text
What information should be recorded?
```

For example:

```js
logger.info({
    event: "todo.created",
    userId: "42",
    todoId: "123"
});
```

### Formatting

Determines:

```text
How should that information be displayed?
```

For example:

```text
INFO todo.created userId=42 todoId=123
```

So:

```text
Logging
   ↓
Structured event
   ↓
Formatting
   ↓
Human-readable output
```

---

# 3. Don't Destroy Structured Logging

A common beginner mistake is:

> "I want pretty logs, so I'll go back to `console.log()`."

Don't.

You want:

```text
Application
     ↓
Structured Pino log
     ↓
Formatter
     ↓
Terminal
```

not:

```text
Application
     ↓
console.log("random text")
```

The structured data should remain the source of truth.

---

# 4. Development vs Production

This is one of the most useful ideas from today's lesson.

### Development

Humans are reading the logs:

```text
INFO  server.started
INFO  todo.created userId=42 todoId=123
WARN  auth.login.failed reason=invalid_credentials
```

Readable formatting is useful.

### Production

Machines and log aggregation systems are often consuming logs:

```json
{
  "level": 30,
  "time": 1756200000000,
  "event": "todo.created",
  "userId": "42",
  "todoId": "123"
}
```

Structured JSON is usually preferable.

So:

```text
Development → readable
Production  → structured
```

---

# 5. Why Not Pretty-Print Production Logs?

Because production logs may be consumed by:

```text
Log management systems
Monitoring systems
Search systems
Alerting systems
SIEM systems
Analytics tools
```

These systems benefit from structured fields.

For example:

```json
{
  "event": "todo.created",
  "userId": "42"
}
```

can be queried directly.

But this:

```text
INFO Todo 123 was created by user 42
```

requires text parsing.

---

# 6. Pino Pretty

Pino's ecosystem provides a tool commonly used for development-friendly output:

```text
pino-pretty
```

Install it as a development dependency:

```bash
npm install -D pino-pretty
```

The important idea is:

```text
Pino
  ↓
structured JSON
  ↓
pino-pretty
  ↓
readable terminal output
```

---

# 7. Basic Development Setup

You can configure Pino with a transport:

```js
import pino from "pino";

const logger = pino({
    level: process.env.LOG_LEVEL || "info",
    transport: {
        target: "pino-pretty"
    }
});

export default logger;
```

Now instead of ugly JSON, development output can look more like:

```text
INFO server.started port=5000
```

The exact appearance depends on the Pino Pretty configuration.

---

# 8. Why `pino-pretty` Should Usually Be Development-Only

This is important.

You generally don't want:

```js
transport: {
    target: "pino-pretty"
}
```

blindly enabled in every environment.

Instead, think:

```text
NODE_ENV=development
        ↓
pino-pretty

NODE_ENV=production
        ↓
JSON
```

Conceptually:

```js
const isDevelopment =
    process.env.NODE_ENV === "development";

const logger = pino({
    level: process.env.LOG_LEVEL || "info",

    transport: isDevelopment
        ? {
              target: "pino-pretty"
          }
        : undefined
});
```

Now:

```text
Development → pretty
Production  → JSON
```

---

# 9. Why This Architecture Is Better

Your application code remains:

```js
logger.info({
    event: "todo.created",
    userId: user.id,
    todoId: todo.id
});
```

You don't change this depending on the environment.

Only the output layer changes.

```text
             logger.info()
                  │
                  ▼
              Pino event
                  │
          ┌───────┴────────┐
          │                │
      Development       Production
          │                │
          ▼                ▼
    pino-pretty           JSON
          │                │
       Terminal       Log platform
```

This is a clean architecture.

---

# 10. Message Fields

Pino supports a `msg` field.

For example:

```js
logger.info({
    event: "server.started",
    port: 5000
}, "Server started");
```

You now have both:

```text
Structured fields
       +
Human-readable message
```

Conceptually:

```json
{
  "event": "server.started",
  "port": 5000,
  "msg": "Server started"
}
```

Whether you use `msg`, an `event` field, or both depends on your logging conventions.

For the backend you're building, I recommend making **event names** a consistent part of your logging design.

---

# 11. Event Name vs Message

Consider:

```js
logger.info({
    event: "todo.created"
}, "Todo created successfully");
```

Here:

```text
event
    ↓
machine-friendly identifier

message
    ↓
human-friendly description
```

This gives you both.

---

# 12. Example

```js
logger.info(
    {
        event: "user.login.success",
        userId: user.id
    },
    "User login successful"
);
```

Possible structured data:

```json
{
  "level": 30,
  "event": "user.login.success",
  "userId": "42",
  "msg": "User login successful"
}
```

A pretty formatter might display:

```text
INFO User login successful
    event=user.login.success
    userId=42
```

Again, the exact visual format depends on the formatter.

---

# 13. Formatting Does Not Mean Changing the Data

This is the core concept.

Suppose your event is:

```js
{
    event: "todo.created",
    userId: "42",
    todoId: "123"
}
```

You can represent it as:

### JSON

```json
{
  "event": "todo.created",
  "userId": "42",
  "todoId": "123"
}
```

### Pretty terminal

```text
INFO todo.created userId=42 todoId=123
```

### Another logging system

```text
2026-08-26 INFO todo.created userId=42 todoId=123
```

Same underlying event.

Different representation.

---

# 14. Formatting Should Be a Presentation Concern

This is similar to web development.

Your backend might produce:

```js
{
    userId: 42,
    name: "Rahul"
}
```

Your frontend decides how to display it.

Similarly:

```text
Pino event
    ↓
Formatter decides presentation
```

The application should not be filled with formatting strings.

---

# 15. Avoid Manual Formatting

Don't write:

```js
logger.info(
    `[INFO] ${new Date().toISOString()} ` +
    `Todo ${todo.id} created by user ${user.id}`
);
```

Why?

Because now you're manually handling:

```text
timestamp
level
format
fields
message
```

Pino already handles these things.

Instead:

```js
logger.info(
    {
        event: "todo.created",
        userId: user.id,
        todoId: todo.id
    },
    "Todo created"
);
```

Much cleaner.

---

# 16. Pretty Logs Are for Humans

Imagine you're debugging:

```text
POST /api/v1/todos
```

and you see:

```text
INFO todo.create.started requestId=req_123 userId=42
INFO todo.created requestId=req_123 userId=42 todoId=todo_123
INFO request.completed requestId=req_123 statusCode=201 duration=48
```

This is very easy to follow.

You can visually trace the request.

---

# 17. Structured Logs Are for Machines

The same events in JSON:

```json
{
  "event": "todo.create.started",
  "requestId": "req_123",
  "userId": "42"
}
```

```json
{
  "event": "todo.created",
  "requestId": "req_123",
  "userId": "42",
  "todoId": "todo_123"
}
```

```json
{
  "event": "request.completed",
  "requestId": "req_123",
  "statusCode": 201,
  "duration": 48
}
```

Now a monitoring system can search:

```text
requestId = req_123
```

and reconstruct the whole request.

---

# 18. Development Logging Example

Your logger might eventually look like:

```js
import pino from "pino";

const isDevelopment =
    process.env.NODE_ENV === "development";

const logger = pino({
    level: process.env.LOG_LEVEL || "info",

    transport: isDevelopment
        ? {
              target: "pino-pretty",
              options: {
                  colorize: true
              }
          }
        : undefined
});

export default logger;
```

Then:

```js
logger.info(
    {
        event: "server.started",
        port: 5000
    },
    "Server started"
);
```

Development:

```text
INFO Server started
    event=server.started
    port=5000
```

Production:

```json
{
  "level": 30,
  "event": "server.started",
  "port": 5000,
  "msg": "Server started"
}
```

This is the architecture you want.

---

# 19. Be Careful With Colors

Pretty logs often use colors:

```text
INFO
WARN
ERROR
```

This can be great in a terminal.

But don't make your application depend on color formatting.

For example:

```text
Production log storage
        ↓
No need for terminal colors
```

Colors are presentation.

Structured fields are data.

---

# 20. `pino-pretty` Is Not a Production Monitoring System

This distinction matters.

`pino-pretty`:

```text
Makes logs easier to read.
```

It does **not** provide:

```text
❌ Log storage
❌ Alerting
❌ Dashboards
❌ Long-term observability
❌ Incident management
```

Those belong to your production logging/observability infrastructure.

We'll get there later.

---

# 21. Log Formatting and Log Transports

You may hear the word:

> **Transport**

A transport determines where or how logs are sent.

Conceptually:

```text
Application
     ↓
Pino
     ↓
Transport
 ┌───┴────┐
 ▼        ▼
Terminal  File/System
```

For development:

```text
Pino → pino-pretty → terminal
```

For production:

```text
Pino → JSON → log collector
```

The exact production infrastructure depends on where your application runs.

---

# 22. Don't Write Logs Directly to Random Files

A beginner might do:

```js
fs.appendFileSync(
    "app.log",
    "Todo created\n"
);
```

Avoid building your own logging system like this.

You then have to solve:

```text
rotation
formatting
concurrency
errors
retention
storage
permissions
shipping
```

A logging library and production logging platform solve these problems more appropriately.

---

# 23. Log Rotation

You may eventually hear:

> **Log rotation**

Suppose your application generates:

```text
app.log
```

and it grows:

```text
100 MB
500 MB
2 GB
10 GB
```

You don't want one infinite file.

Rotation means something like:

```text
app.log
app-2026-08-25.log
app-2026-08-26.log
```

This is a production concern.

Don't confuse it with formatting.

---

# 24. Formatting vs Rotation

### Formatting

```text
How does the log look?
```

### Rotation

```text
How are log files managed over time?
```

### Shipping

```text
Where do logs go?
```

### Retention

```text
How long do we keep them?
```

These are separate concerns.

---

# 25. Formatting vs Redaction

These are also different.

### Formatting

```text
JSON
   ↓
Pretty terminal
```

### Redaction

```text
password=secret
   ↓
password=[REDACTED]
```

Don't confuse:

```text
pretty
```

with:

```text
secure
```

A pretty log can still leak a password.

A JSON log can still leak a password.

Security comes from **what you log and what you redact**, not how pretty it looks.

---

# 26. Example of a Dangerous Pretty Log

Imagine:

```text
INFO login
    email=rahul@example.com
    password=secret123
```

It looks beautiful.

It's still a security vulnerability.

So remember:

> **Readable ≠ safe.**

---

# 27. Example of a Good Pretty Log

```text
INFO auth.login.success
    userId=42
    requestId=req_123
```

Useful.

Readable.

No secret.

That's what you want.

Development:


Production:


```js
const isDevelopment =
```

---

# 29. What Happens to `debug` Logs?

Suppose:

```env
LOG_LEVEL=info
```

Then:

```js
logger.debug({
    event: "database.query.started"
});
```

will generally not appear.

But:

```js
logger.info({
    event: "database.connected"
});
```

will.

If:

```env
LOG_LEVEL=debug
```

then debug logs become visible.

This is why log levels and formatting work together.

# 30. A Good Development Configuration

For learning and development:

```js
import pino from "pino";

const isDevelopment =
    process.env.NODE_ENV === "development";

const logger = pino({
    level: process.env.LOG_LEVEL || "debug",

    transport: isDevelopment
        ? {
              target: "pino-pretty",
              options: {
                  colorize: true,
                  translateTime: "SYS:standard"
              }
          }
        : undefined
});

export default logger;
```

The exact formatting options can be adjusted later.

The important architecture is:

```text
development
    ↓
pino-pretty

production
    ↓
structured JSON
```

---

# 31. Why `translateTime`?

Pino internally uses timestamps that are efficient for machines.

You might see:

```text
1756200000000
```

A human prefers:

```text
2026-08-26 11:20:31
```

A pretty formatter can translate timestamps into something easier to read.

Again:

```text
Internal structured timestamp
        ↓
Human-readable presentation
```

The underlying event remains structured.

---

# 32. Do Not Format Timestamps Yourself

Avoid:

```js
logger.info({
    time: new Date().toISOString()
});
```

everywhere.

Pino already provides timestamp handling.

Your application should focus on meaningful application fields.

```js
logger.info(

        event: "todo.created",
```

Development:


```json
  "userId": "42",
  "todoId": "todo_456",
```

**Same application event.**

Different presentation.

---

# 34. This Is an Important Architectural Principle

Your application should produce:

```text
DATA
```

not:

```text
DISPLAY FORMAT
```

The logger/transport decides:

```text
How that data is presented or transported.
```

This is a very reusable software engineering principle.

You'll see the same concept in:

```text
API responses
Database serialization
Message queues
Metrics
Tracing
```

---

# 35. How This Connects to Observability

Eventually:

```text
Logs
Metrics
Traces
```

will work together.

For example:

```text
requestId=req_123
```

could appear in logs.

Then metrics tell you:

```text
500 requests/minute
```

and tracing tells you:

```text
request → controller → service → database
```

Formatting is only one small part of this bigger system.

# 37. Common Mistakes

### ❌ Mistake 1

Using `pino-pretty` everywhere.

Better:

```text
development → pretty
production → JSON
```

---

### ❌ Mistake 2

Manually formatting every log.

Don't:

```js
logger.info(`[INFO] ${Date.now()} ...`);
```

---

### ❌ Mistake 3

Thinking pretty logs are safer.

They're not.

---

### ❌ Mistake 4

Logging entire objects because the pretty output looks nice.

Still dangerous:

```js
logger.info({
    user: req.user
});
```

if `req.user` contains sensitive fields.

---

### ❌ Mistake 5

Using different log formats in application code.

Keep application logging structured.
