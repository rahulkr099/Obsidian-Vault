# Lesson 19.11 — Production Logging

In **19.9**, we learned Pino.

In **19.10**, we learned how to make logs readable during development.

Now we answer the production question:

> **What should happen to our logs when the backend is running for real users?**

Your Phase 19 roadmap places **Production Logging** immediately after Pino and log formatting, before health checks and metrics.

---

# 1. Development Logging vs Production Logging

During development, you might see:

```text
INFO  Server started
INFO  Todo created
WARN  Login failed
ERROR Database connection failed
```

That's useful because **you are looking at the terminal**.

In production, your application might be running:

```text
Server
  ↓
Docker container
  ↓
Cloud / VPS
  ↓
1000 requests
  ↓
Thousands of logs
```

You cannot sit there watching:

```bash
docker logs ...
```

all day.

Production logging needs a proper strategy.

---

# 2. What Production Logging Should Give You

A production logging system should help you answer:

```text
What happened?
When did it happen?
Which request caused it?
Which user was involved?
Which endpoint?
What was the result?
How long did it take?
Did an error occur?
```

For example:

```json
{
  "level": 30,
  "event": "todo.created",
  "requestId": "req_abc123",
  "userId": "user_42",
  "todoId": "todo_99",
  "duration": 42
}
```

Now you have useful operational information.

---

# 3. Production Logs Should Be Structured

This is one of the biggest lessons from 19.9 and 19.10.

Development:

```text
INFO Todo created userId=42 todoId=99
```

Production:

```json
{
  "level": 30,
  "event": "todo.created",
  "userId": "42",
  "todoId": "99"
}
```

Generally, **don't turn production logs into pretty terminal text just because it looks nicer**.

The production logging pipeline should preserve structured data.

---

# 4. Where Do Production Logs Go?

A simple mental model:

```text
Your Node.js Application
          │
          ▼
         Pino
          │
          ▼
     JSON log output
          │
          ▼
   Logging infrastructure
          │
    ┌─────┼─────┐
    ▼     ▼     ▼
 Storage Search Alerts
```

The important point:

> **Your application generates logs; your infrastructure manages them.**

---

# 5. Don't Think "Log File" First

A beginner often thinks:

```text
Node.js
  ↓
app.log
```

and starts building:

```text
logs/app.log
```

That can work in some environments, but modern deployments often treat application logs as a stream that gets collected by the platform.

For example:

```text
Node
 ↓
stdout
 ↓
container runtime
 ↓
logging system
```

This is especially useful with Docker.

---

# 6. Why `stdout` and `stderr` Matter

Your Node application can write logs to:

```text
stdout
stderr
```

Conceptually:

```text
INFO/WARN
   ↓
stdout

ERROR
   ↓
stderr
```

The surrounding platform can then collect those streams.

For example:

```text
Node application
      ↓
Docker
      ↓
container logs
      ↓
log collector
```

This means your application doesn't necessarily need to manage log files itself.

---

# 7. The Container Mental Model

Later, when you study Docker, imagine:

```text
┌─────────────────────────┐
│       Node Container    │
│                         │
│   Express + Pino        │
│          │              │
│          ▼              │
│      JSON logs          │
└──────────┬──────────────┘
           │
           ▼
     Docker runtime
           │
           ▼
    Log collection
```

This is one reason **structured stdout logging** is such a useful production pattern.

Your roadmap eventually covers Docker and production architecture, so this connection will become even clearer there.

---

# 8. Don't Build Your Own Log Storage

Avoid turning your application into a log-management system.

For example, don't immediately build:

```text
Node
 ↓
MongoDB
 ↓
logs collection
```

for every application log.

You'd now have to solve:

```text
log storage
log retention
log indexing
log rotation
log cleanup
log querying
log scaling
```

That's infrastructure work.

Your normal application database should generally be used for **business data**, not as your default dumping ground for operational logs.

---

# 9. Application Logs vs Audit Logs

There is an important distinction.

### Application/operational logs

Things like:

```text
server.started
request.completed
database.query.failed
todo.created
email.send.failed
```

These help you operate and debug the system.

### Audit logs

Things like:

```text
user.changed.password
admin.changed.user.role
user.deleted.account
```

These can be business/security records that you may intentionally persist.

So don't assume:

> "Every log should go into MongoDB."

They have different purposes.

---

# 10. Production Log Levels

In production, you don't necessarily want:

```text
trace
debug
info
warn
error
fatal
```

all enabled.

For example:

```env
LOG_LEVEL=info
```

could be a sensible starting point.

Then:

```text
debug
   ↓
filtered

info
   ↓
logged

warn
   ↓
logged

error
   ↓
logged
```

The exact level depends on the application's needs.

---

# 11. Why Not Always Use `debug`?

Imagine a busy application.

One request produces:

```text
debug request.started
debug middleware.auth.started
debug middleware.auth.finished
debug service.started
debug repository.started
debug repository.finished
debug service.finished
debug controller.finished
```

Now multiply that by:

```text
10,000 requests
```

Your logs become enormous.

So production logging needs a balance:

```text
Useful information
       +
Reasonable volume
```

---

# 12. But Don't Hide Important Errors

A production configuration like:

```env
LOG_LEVEL=error
```

may be too aggressive for many applications.

You might lose useful:

```text
info
warn
```

events.

For example:

```text
authorization.denied
rate_limit.exceeded
database.connection.recovered
```

may be operationally useful even though they're not application crashes.

So choose levels based on what you need to operate the system.

---

# 13. Production Logging Configuration

A simple logger:

```js
import pino from "pino";

const isDevelopment =
    process.env.NODE_ENV === "development";

const logger = pino({
    level: process.env.LOG_LEVEL || "info",

    transport: isDevelopment
        ? {
              target: "pino-pretty"
          }
        : undefined
});

export default logger;
```

This gives:

```text
Development
    ↓
pretty logs

Production
    ↓
JSON logs
```

That's a good foundation.

---

# 14. Production Should Prefer JSON

Suppose your application produces:

```js
logger.info({
    event: "request.completed",
    requestId,
    method: req.method,
    path: req.originalUrl,
    statusCode: res.statusCode,
    duration
});
```

Production can output:

```json
{
  "level": 30,
  "event": "request.completed",
  "requestId": "req_123",
  "method": "GET",
  "path": "/api/v1/todos",
  "statusCode": 200,
  "duration": 31
}
```

A log platform can now index:

```text
event
requestId
method
path
statusCode
duration
```

---

# 15. Request IDs Become Extremely Important

You learned about request IDs earlier in Phase 19.

Imagine a user reports:

> "My request failed."

You have:

```text
requestId=req_abc123
```

Now you can search production logs:

```text
requestId = req_abc123
```

and find:

```text
request.received
auth.success
todo.create.started
database.query.failed
request.completed
```

That's incredibly useful.

---

# 16. Production Logging Is About Correlation

Think:

```text
Request A
requestId=A
   │
   ├── auth
   ├── service
   ├── database
   └── response

Request B
requestId=B
   │
   ├── auth
   ├── service
   └── response
```

Without request IDs:

```text
auth success
todo created
database error
request completed
```

Which request did they belong to?

You don't know.

With request IDs:

```text
req=A → auth
req=A → todo
req=A → database

req=B → auth
req=B → response
```

Now you can reconstruct the story.

---

# 17. User Context

You also learned in **19.7** about user context.

A production log might contain:

```json
{
  "event": "authorization.denied",
  "requestId": "req_123",
  "userId": "user_42",
  "requiredRole": "admin"
}
```

Now you know:

```text
Which request?
Which user?
What happened?
Why?
```

But remember:

> **User context does not mean dumping the entire user object into logs.**

Only log the fields you actually need.

---

# 18. Sensitive Data Is Still Dangerous

Production logs are often retained and accessible to more systems and people.

So this is especially dangerous:

```js
logger.info({
    email,
    password,
    accessToken,
    refreshToken
});
```

Never do this.

Your earlier lesson **19.8 — Sensitive Data in Logs** is directly connected to today's production architecture.

---

# 19. Production Logs Can Become a Security Problem

Imagine:

```text
Application
 ↓
Logs
 ↓
Cloud storage
 ↓
Multiple engineers
 ↓
Monitoring platform
 ↓
Backups
```

One accidental secret in a log can spread much farther than you expected.

Therefore:

```text
Production logging
        ↓
Security requirement
```

not just a debugging feature.

---

# 20. Log Redaction

Pino can help redact known sensitive fields.

For example:

```js
const logger = pino({
    level: process.env.LOG_LEVEL || "info",

    redact: [
        "req.headers.authorization",
        "req.headers.cookie"
    ]
});
```

Then sensitive values can be replaced rather than emitted.

But remember:

> **Redaction is a safety net, not permission to log sensitive data.**

Your first rule should still be:

```text
Don't log secrets unnecessarily.
```

---

# 21. Log Retention

Now let's discuss another production concept:

> **How long should logs be kept?**

Suppose:

```text
Day 1 → 1 GB
Day 2 → 1 GB
Day 3 → 1 GB
...
```

After 100 days:

```text
100 GB
```

You don't necessarily need every log forever.

So production systems often have a retention policy.

For example:

```text
Recent operational logs
       ↓
kept longer

Old logs
       ↓
deleted/archived
```

The exact retention period depends on your application, operational needs, and legal/security requirements.

---

# 22. Log Rotation

If you're using files, you may need **log rotation**.

Conceptually:

```text
app.log
   ↓
reaches size/time limit
   ↓
rotate
   ↓
app-2026-08-25.log
app-2026-08-26.log
```

This prevents one file from growing forever.

But if your deployment platform already collects stdout/stderr, the platform may handle storage and rotation instead.

That's why you should understand your deployment environment before designing file-based logging.

---

# 23. Log Shipping

Another production term:

> **Log shipping**

Means:

```text
Application
    ↓
Logs
    ↓
Collector
    ↓
Central log system
```

For example:

```text
Node
 ↓
stdout
 ↓
container runtime
 ↓
collector
 ↓
central storage
```

Now your application logs from multiple servers can be searched in one place.

---

# 24. Why Centralized Logging Matters

Imagine:

```text
Server A
Server B
Server C
Server D
```

Each produces:

```text
logs
```

If you SSH into every server individually:

```text
ssh server-a
grep ...

ssh server-b
grep ...

ssh server-c
grep ...
```

that's painful.

Centralized logging gives:

```text
                Central Log System
                  /     |      \
                 /      |       \
            Server A Server B Server C
```

Now you search one place.

---

# 25. Search Is the Real Power

Imagine production reports:

> "Todo creation is failing."

You can search:

```text
event = todo.create.failed
```

Then filter:

```text
statusCode >= 500
```

Then:

```text
userId = 42
```

Then:

```text
requestId = req_123
```

This is why structured logging is so powerful.

---

# 26. Logging and Alerting

Logs can also feed alerts.

For example:

```text
database.connection.failed
```

occurs many times.

Your infrastructure might detect:

```text
100 database errors in 5 minutes
```

and alert:

```text
🚨 Database failure rate increased
```

Notice something important:

> **Pino generates the event; the monitoring/alerting system decides what to do with it.**

---

# 27. Don't Turn Every Log Into an Alert

This would be terrible:

```text
INFO → alert
WARN → alert
ERROR → alert
```

Your team would get:

```text
1000 alerts/day
```

and eventually ignore all of them.

Instead, alerts should focus on meaningful operational problems.

For example:

```text
5xx rate suddenly high
database unavailable
service unavailable
authentication failure spike
```

---

# 28. Production Logging and Performance

Logging isn't free.

Every log requires work:

```text
Create log object
 ↓
Serialize
 ↓
Write
 ↓
Transport
 ↓
Store
```

Therefore:

```text
Too little logging
    ↓
hard to debug

Too much logging
    ↓
cost + noise + performance
```

The goal is:

> **High-value, structured logs.**

---

# 29. Avoid Logging Huge Objects

Don't do:

```js
logger.info({
    req,
    res,
    user,
    body
});
```

This can cause:

```text
Huge logs
Sensitive data
Slow serialization
Storage explosion
Hard-to-read output
```

Instead:

```js
logger.info({
    event: "request.completed",
    requestId,
    method: req.method,
    path: req.originalUrl,
    statusCode: res.statusCode,
    duration
});
```

Small.

Useful.

Structured.

---

# 30. Don't Log Entire Database Documents

Avoid:

```js
logger.info({
    event: "user.loaded",
    user
});
```

The user object might eventually contain:

```text
passwordHash
refreshTokenHash
resetTokenHash
internal fields
```

Instead:

```js
logger.info({
    event: "user.loaded",
    userId: user.id
});
```

Log identifiers and useful metadata, not entire objects.

---

# 31. Production Logging and Error Logging

For an unexpected error:

```js
logger.error({
    event: "todo.create.failed",
    requestId,
    userId,
    err: error
});
```

This is much better than:

```js
console.error(error);
```

because the structured log can contain:

```text
event
requestId
userId
error name
error message
stack
timestamp
```

depending on configuration.

---

# 32. Production Logging and Global Error Handling

Your architecture should eventually look like:

```text
Request
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Error
   ↓
Global Error Handler
   ├── Log error
   └── Send safe API response
```

For example:

```text
Internal error
      │
      ├── Logger
      │      ↓
      │   detailed stack
      │
      └── Client
             ↓
       safe error message
```

This distinction is extremely important.

---

# 33. Never Return Your Logs to the Client

Suppose an error occurs:

```text
MongoServerError
```

Don't send:

```json
{
  "error": "...full stack trace..."
}
```

to the user.

Instead:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "req_123"
}
```

Meanwhile your production logs contain the detailed error.

This is a very useful pattern:

```text
Client
  ↓
Safe information

Logs
  ↓
Diagnostic information
```

That's a professional production workflow.

Avoid:

```text

access tokens
refresh tokens
cookie secrets
API keys

```

Your logging strategy should be intentionally minimal.

# 39. A Good Logger for Your Starter

For the architecture you're building, a reasonable foundation is:

```js
// utils/logger.js

import pino from "pino";

const isDevelopment =
    process.env.NODE_ENV === "development";

const logger = pino({
    level: process.env.LOG_LEVEL || "info",

    redact: [
        "req.headers.authorization",
        "req.headers.cookie"
    ],

    transport: isDevelopment
        ? {
              target: "pino-pretty",
              options: {
                  colorize: true
              }
          }
        : undefined
});

export default logger;
```

Notice what we're doing:

```text
Development
    ↓
pretty logs

Production
    ↓
JSON logs

All environments
    ↓
appropriate log level
    ↓
redaction
```

This is a good starting architecture—not the final production deployment configuration.

# 41. The Three Big Observability Signals

We're approaching a bigger concept:

```text
             Observability
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
       Logs     Metrics    Traces
```

### Logs

Tell you:

> **What happened?**

### Metrics

Tell you:

> **How much/how often?**

# 42. Production Logging vs Metrics

Suppose you have:


```text

```

Logs can tell you:

```text

```

So:

```text
Metrics → pattern
Logs    → details
```

This distinction becomes important in **19.14 Metrics Fundamentals**.
