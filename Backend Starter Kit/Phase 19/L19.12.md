# 1. What Is a Health Check?

A health check is a small endpoint that answers:

> **"Is this application process alive and able to respond?"**

For example:

```http
GET /healthz
```

Response:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

That's it.

It sounds simple, but this tiny endpoint becomes very useful when your application is deployed.

---

# 2. Why Do We Need `/healthz`?

Imagine your backend is running on a server:

```text
Internet
   ↓
Node.js
   ↓
Express
```

Something goes wrong.

Maybe:

```text
Node crashed
Process became stuck
Container failed
Application isn't accepting requests
```

How does another system know?

It can call:

```http
GET /healthz
```

If it gets:

```http
200 OK
```

the application is alive.

If it gets:

```text
connection refused
timeout
5xx
```

something is wrong.

---

# 3. Health Check Is an Operational Tool

This isn't primarily a feature for your React frontend.

You generally don't build:

```text
React
 ↓
"Hey backend, are you healthy?"
```

The main consumers can be:

```text
Docker
Kubernetes
Load balancer
Deployment platform
Monitoring system
Operations team
```

Think:

```text
Application
    ↑
"Are you alive?"
    │
Monitoring / infrastructure
```

---

# 4. Health vs Readiness

This distinction is **very important** because your next lesson is readiness checks.

Your starter documentation explicitly defines:

```text
/healthz
    ↓
Is Node alive?

/readyz
    ↓
Is Node + MongoDB + required services ready?
```

So:

### `/healthz`

asks:

> **Am I alive?**

### `/readyz`

asks:

> **Am I ready to receive real traffic?**

We'll build `/readyz` in **19.13**.

For today's lesson, focus only on `/healthz`.

---

# 5. The Simplest Health Check

In Express:

```js
app.get("/healthz", (req, res) => {
    res.status(200).json({
        success: true,
        message: "Server is healthy"
    });
});
```

Now:

```bash
curl http://localhost:5000/healthz
```

Response:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

You've just created a health endpoint.

---

# 6. What Does It Actually Prove?

This endpoint proves:

```text
HTTP request
      ↓
Node process
      ↓
Express
      ↓
Routing
      ↓
Response
```

is working.

It does **not necessarily prove**:

```text
MongoDB works
Redis works
Email works
External APIs work
```

That's exactly why readiness checks are separate.

---

# 7. Why Not Check MongoDB Here?

You might think:

```js
app.get("/healthz", async (req, res) => {
    await mongoose.connection.db.command({
        ping: 1
    });

    res.json({
        success: true
    });
});
```

That changes the meaning of `/healthz`.

Now your endpoint isn't merely asking:

> "Is the application alive?"

It's asking:

> "Is the application and database healthy?"

That's closer to a **readiness/dependency check**.

We want to keep the concepts clear.

---

# 8. Health Check Should Be Cheap

A health endpoint may be called frequently.

Imagine:

```text
Every 5 seconds
      ↓
/healthz
```

That's:

```text
12 requests/minute
720 requests/hour
17,280 requests/day
```

per monitoring source.

If you have multiple infrastructure systems checking it, the number can grow.

So `/healthz` should be:

```text
Fast
Simple
Predictable
Low-cost
```

---

# 9. Don't Put Heavy Logic in `/healthz`

Avoid:

```js
app.get("/healthz", async (req, res) => {
    await expensiveDatabaseQuery();
    await checkExternalAPI();
    await sendTestEmail();
    await runComplexCalculation();

    res.json({
        success: true
    });
});
```

That's not a good basic liveness endpoint.

Why?

Because now the health check itself can become a source of load and failure.

---

# 10. Health Check Should Not Require Authentication

Don't do:

```js
router.get(
    "/healthz",
    authMiddleware,
    healthController
);
```

Generally, infrastructure needs to be able to check the application **without a user JWT**.

So:

```text
GET /healthz
     ↓
No authentication
     ↓
Health response
```

Your starter's architecture also illustrates that `/healthz` should not require authentication, while protected application routes should.

---

# 11. Health Check Should Usually Be Public

For infrastructure to check:

```http
GET /healthz
```

it shouldn't need:

```http
Authorization: Bearer ...
```

This makes deployment and monitoring much simpler.

However, "public" doesn't mean:

> expose internal information.

Don't return:

```json
{
  "mongodbPassword": "...",
  "jwtSecret": "...",
  "databaseUri": "..."
}
```

Obviously never.

---

# 12. What Should `/healthz` Return?

Keep it simple.

Your starter reference suggests:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

You could eventually include minimal operational information such as:

```json
{
  "success": true,
  "status": "ok"
}
```

The important part is consistency and simplicity.

---

# 13. Should We Return the Version?

You might see health endpoints like:

```json
{
  "status": "ok",
  "version": "1.2.3"
}
```

This can be useful in some systems.

But don't expose unnecessary information.

For your starter, keep the first version simple.

Later, when we discuss production architecture, you can decide what operational metadata is actually useful.

---

# 14. HTTP Status Code

A healthy application should normally return:

```http
200 OK
```

For example:

```js
res.status(200).json({
    success: true,
    message: "Server is healthy"
});
```

You could omit `.status(200)` because Express defaults successful responses to 200, but explicitly writing it can make the intention clear.

---

# 15. What If the Application Is Not Alive?

Here's the important part.

If Node itself crashes:

```text
Node process
     ↓
💥 crashed
```

then:

```http
GET /healthz
```

can't return anything.

The request might receive:

```text
Connection refused
```

or:

```text
Timeout
```

That's useful.

Your infrastructure can recognize:

```text
Health check failed
        ↓
Application unhealthy
```

and potentially restart or stop routing traffic to it.

# 17. Health Checks and Load Balancers

Imagine:

```text
                 Load Balancer
                /      |      \
               /       |       \
           Server A Server B Server C
```

Suppose:

```text
Server B
   ↓
broken
```

The load balancer can check:

```http
GET /healthz
```

on each server.

If:

```text
A → 200
B → failed
C → 200
```

it can avoid sending traffic to B, depending on the platform/configuration.

This is one of the main real-world reasons health endpoints exist.

# 19. Health Check vs Monitoring

Don't confuse these.

### Health check

```text
"Are you alive?"
```

### Monitoring

```text
"How is the system behaving?"
```

Monitoring may track:

```text
CPU
Memory
Request rate
Error rate
Latency
Database connections
```

That's why your roadmap later moves from:

```text
Health checks
 ↓
Readiness checks
 ↓
Metrics
```

---

# 20. Health Check vs Logging

Logging:

```text
event = database.query.failed
requestId = req_123
```

tells you:

> **What happened?**

Health check:

```http
GET /healthz
```

tells infrastructure:

> **Is the application alive right now?**

They're different signals.

```text
Logs
 ↓
Historical events

Health
 ↓
Current liveness state
```

---

# 21. Health Check vs Metrics

Metrics might say:

```text
HTTP 5xx rate = 7%
```

Health check might say:

```text
200 OK
```

Notice something interesting:

> A service can be technically alive while still behaving badly.

For example:

```text
Node process → alive
/healthz     → 200
500 errors   → 30%
```

That's why health checks alone aren't observability.

You need:

```text
Logs
+
Health
+
Readiness
+
Metrics
+
Eventually traces
```

# 27. Should Health Checks Be Logged?

This is a subtle production issue.

Suppose:

```text
Monitoring
   ↓
/healthz
   ↓
every 5 seconds
```

If you log every request:

```text
INFO GET /healthz
INFO GET /healthz
INFO GET /healthz
INFO GET /healthz
...
```

your logs can become noisy.

So you may eventually choose to:

```text
health check
   ↓
not log at normal request level
```

or filter/handle health requests specially.

This is an excellent example of how:

```text
Health checks
+
Logging
```

interact.

---

# 28. Don't Log Sensitive Health Information

Bad:

```json
{
  "status": "ok",
  "databaseUri": "mongodb://username:password@..."
}
```

Absolutely not.

A health endpoint should not become an information leak.

Good:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

---

# 29. Health Check Failure

What should happen if your application itself cannot respond?

You don't need to manually return:

```http
503
```

for a completely dead Node process.

There is no process to respond.

The infrastructure sees:

```text
timeout
connection refused
```

and considers the check failed.

This is another reason a health endpoint is useful.

---

# 30. But What About a Broken Database?

Suppose:

```text
Node       → working
Express    → working
MongoDB    → down
```

Then:

```text
/healthz
```

could still return:

```http
200 OK
```

because the application process itself is alive.

That is **not necessarily wrong**.

The database dependency belongs in the readiness/dependency check.

That's the next lesson.

# 32. Health Checks in Your Startup Architecture

Your starter reference already establishes an important startup principle:

```text
Application starts
       ↓
Load environment
       ↓
Connect MongoDB
       ↓
Connection successful?
       │
       ├── NO → exit
       │
       └── YES
             ↓
        Start Express
```

This means your application shouldn't casually start accepting normal traffic if its required startup dependency isn't available.

But once the process is running, `/healthz` answers the simpler liveness question.

---

# 33. Health Check Is Not a Substitute for Graceful Startup

Don't think:

> "I'll start Express first and health check MongoDB later."

Your startup architecture should still deliberately establish required dependencies.

Conceptually:

```text
server.js

load config
   ↓
connect DB
   ↓
start server
```

Then:

```text
/healthz
```

is available once the application is running.

---

# 34. Health Check Is Not a Substitute for Graceful Shutdown

Similarly, if you're shutting down:

```text
SIGTERM
   ↓
stop accepting new traffic
   ↓
finish existing requests
   ↓
close database
   ↓
close server
   ↓
exit
```

A health/readiness strategy can help infrastructure understand that the instance should no longer receive traffic.

Graceful shutdown will be covered later in your Docker/production phases. Your roadmap explicitly includes it in Phase 23 and Phase 24.

# 38. Should `/healthz` Use Rate Limiting?

Usually you don't want to apply your normal user-facing rate limiter blindly to infrastructure health checks.

Imagine:

```text
Load balancer
   ↓
/healthz
```

If your general rate limiter blocks it:

```text
429 Too Many Requests
```

your infrastructure might incorrectly conclude:

> "The service is unhealthy."

This is another reason health endpoints need to be treated as operational endpoints.

# 39. Health Checks and Security

Public doesn't mean careless.

A good health endpoint:

```text
✓ Doesn't require authentication
✓ Is fast
✓ Returns minimal information
✓ Doesn't expose secrets
✓ Doesn't run expensive queries
✓ Doesn't perform mutations
✓ Is predictable
```

That's a nice checklist.

```text

```

---

### ❌ Mistake 3 — Returning secrets

Never.

---

### ❌ Mistake 4 — Expensive database queries

Health checks should be cheap.

---

### ❌ Mistake 6 — Treating health as monitoring

Health checks are only one signal.

# ⭐ Final Takeaway

A health check is deliberately **boring**.

That's good.

Your first implementation can be as simple as:

```js
app.get("/healthz", (req, res) => {
    res.status(200).json({
        success: true,
        message: "Server is healthy"
    });
});
```

Its purpose is not to tell you everything about your system.

Its purpose is to answer one simple operational question:

> **"Is this application alive and able to respond?"**

Keep this distinction firmly in your mind:

```text
/healthz
   ↓
Liveness
   ↓
"Am I alive?"

/readyz
   ↓
Readiness
   ↓
"Can I safely receive traffic?"
```

Your starter architecture intentionally separates these two endpoints, and that separation will become especially important once you reach Docker and deployment.
