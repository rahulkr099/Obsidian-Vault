# Lesson 19.13 — Readiness Checks

In **19.12**, we learned:

```text
/healthz
   ↓
"Is my application alive?"
```

Now we go one level deeper:

```text
/readyz
   ↓
"Is my application ready to serve real traffic?"
```

Your course source explicitly defines the distinction as:

```text
/healthz
    ↓
Is Node alive?

/readyz
    ↓
Is Node + MongoDB + required services ready?
```

and says this becomes important during deployment.

Your Phase 19 roadmap has **19.13 Readiness checks** immediately after health checks.

---

# 1. Why Do We Need Readiness?

Imagine your backend:

```text
Node.js
   │
   ├── Express       ✅
   │
   └── MongoDB       ❌
```

The Node process is alive.

Therefore:

```text
/healthz
   ↓
200 OK
```

But can the application actually handle:

```http
POST /api/v1/todos
```

Probably not.

The application is **alive but not ready**.

That's exactly the problem `/readyz` solves.

---

# 2. The Most Important Difference

Remember this:

```text
┌──────────────────────────────────┐
│            /healthz              │
│                                  │
│       "Are you alive?"           │
└──────────────────────────────────┘

                vs

┌──────────────────────────────────┐
│            /readyz               │
│                                  │
│    "Can you serve traffic?"      │
└──────────────────────────────────┘
```

Or even shorter:

```text
healthz = alive
readyz  = ready
```

---

# 3. Real-World Analogy

Imagine a restaurant.

The restaurant building is open:

```text
Lights ON
Doors OPEN
Staff present
```

So:

```text
Health = healthy
```

But suppose:

```text
Kitchen equipment broken
No ingredients
No chef
```

Can it serve customers?

```text
NO
```

So:

```text
Alive ≠ Ready
```

Your backend is the same.

Suppose your backend starts:

```text

    ↓

    ↓
MongoDB connection still establishing
```

At this exact moment:


```text

Application → ready
```

```text

/readyz  → 200
```

# 5. Why Infrastructure Cares

Imagine you have three backend instances:

```text
             Load Balancer
              /    |    \
             /     |     \
            A      B      C
```

Their state:

```text
A → healthy + ready
B → healthy + NOT ready
C → healthy + ready
```

The load balancer should ideally send normal traffic to:

```text
A
C
```

and avoid:

```text
B
```

This prevents users from being sent to an instance that technically exists but cannot actually serve requests.

---

# 6. Readiness Is About Dependencies

Your source specifically gives:

```text
Node + MongoDB + required services
```

as the readiness concept.

So readiness can consider things like:

```text
Node.js
MongoDB
Redis
Required internal services
```

depending on what your application actually requires.

The important word is:

> **required**

Don't automatically check every external service your application has ever heard of.

---

# 7. What Is a Dependency?

A dependency is something your application needs to perform its job.

For your backend:

```text
Backend
   │
   └── MongoDB
```

MongoDB is a required dependency if your API needs MongoDB for normal operation.

Later you might have:

```text
Backend
   ├── MongoDB
   ├── Redis
   └── Email service
```

But whether all three belong in readiness depends on how your application works.

---

# 8. Simple Readiness Check

A basic idea:

```js
app.get("/readyz", (req, res) => {
    const databaseReady =
        mongoose.connection.readyState === 1;

    if (!databaseReady) {
        return res.status(503).json({
            success: false,
            message: "Server is not ready"
        });
    }

    return res.status(200).json({
        success: true,
        message: "Server is ready"
    });
});
```

The important part is:

```js
mongoose.connection.readyState === 1
```

We're asking:

> "Is the MongoDB connection currently connected?"

---

# 9. Why `503`?

When the application is alive but not currently ready to serve traffic, a common HTTP status is:

```http
503 Service Unavailable
```

So:

### Ready

```http
200 OK
```

### Not ready

```http
503 Service Unavailable
```

Conceptually:

```text
/readyz
   │
   ├── dependencies ready → 200
   │
   └── dependencies unavailable → 503
```

---

# 10. Why Not Return `500`?

You might wonder:

```text
Why 503 instead of 500?
```

Because they're communicating different ideas.

### 500

Generally means:

> The server encountered an unexpected internal error while processing the request.

### 503

Communicates:

> The service is currently unavailable to serve this request.

For readiness:

```text
MongoDB unavailable
        ↓
service temporarily not ready
        ↓
503
```

is a natural fit.

---

# 11. Readiness Is Usually More Expensive Than Liveness

Compare:

### `/healthz`

```text
Receive request
      ↓
Return 200
```

Very cheap.

### `/readyz`

```text
Receive request
      ↓
Check MongoDB
      ↓
Check required dependencies
      ↓
Return status
```

Potentially more work.

Therefore:

```text
healthz
   ↓
very cheap

readyz
   ↓
dependency checks
```

---

# 12. But Don't Make `/readyz` Too Heavy

Don't turn it into:

```text
/readyz
 ↓
MongoDB ping
 ↓
Redis ping
 ↓
External API request
 ↓
Email provider request
 ↓
Payment provider request
 ↓
Huge database query
 ↓
Complex business calculation
```

That can become problematic.

Your readiness check should answer:

> **Are the dependencies required for normal operation available?**

not:

> **Can I run my entire application successfully right now?**

---

# 13. Readiness Does Not Mean Every Request Will Succeed

Suppose:

```text
MongoDB → healthy
Node → healthy
```

Then:

```text
/readyz → 200
```

But a particular request can still fail:

```text
POST /todos
     ↓
validation error
     ↓
400
```

That's normal.

Readiness doesn't mean:

> "Every request will succeed."

It means:

> "This instance is capable of receiving normal traffic."

# 14. Startup Sequence

Your uploaded architecture says the application should connect to MongoDB before starting the HTTP server:

```text
Application starts
       ↓
Load environment
       ↓
Connect MongoDB
       ↓
Connection successful?
       │
       ├── NO → exit
       │
       └── YES
             ↓
        Start Express
```

This means your initial startup flow already provides an important guarantee:

```text

     ↓

```

So why do we still need `/readyz`?

Because production systems can experience dependency failures **after startup**.

# 16. The State Model

Think about your server as having states:

```text
           STARTING
              │
              ▼
        dependencies ready?
          /          \
        NO            YES
        │              │
        ▼              ▼
     NOT READY       READY
                       │
                       ▼
                 serving traffic
```

And later:

```text
READY
  │
  ▼
dependency fails
  │
  ▼
NOT READY
```

The application can still be alive while moving between these states.

# 18. What Should `/readyz` Return?

For your starter, keep it simple.

### Ready

```json
{
  "success": true,
  "message": "Server is ready"
}
```

### Not ready

```json
{
  "success": false,
  "message": "Server is not ready"
}
```

You don't need to expose:

```text
MongoDB hostname
connection string
credentials
internal IP
```

Keep operational information minimal.

---

# 19. Should We Tell the Client MongoDB Is Down?

You could technically return:

```json
{
  "database": "disconnected"
}
```

but think carefully.

A public endpoint should not expose unnecessary infrastructure details.

Prefer:

```json
{
  "success": false,
  "message": "Server is not ready"
}
```

while your logs contain the detailed diagnostic information.

This follows the same principle we learned in production logging:

```text
Client
 ↓
safe information

Logs
 ↓
diagnostic information
```

# 20. Logging Readiness Failures

This is where your previous lesson connects directly.

Suppose MongoDB becomes unavailable.

Your readiness endpoint might return:

```text
503
```

but your logger could record:

```json
{
  "event": "readiness.failed",
  "dependency": "mongodb"
}
```

Now infrastructure knows:

```text
/readyz → 503
```

and developers/operators can investigate:

```text

```

---

# 21. Don't Log Every Successful Readiness Request

Remember our lesson about health-check log noise.

If infrastructure calls:

```text
/readyz
```

every five seconds:

```text
INFO /readyz
INFO /readyz
INFO /readyz
INFO /readyz
...
```

you may create a lot of useless logs.

A better approach can be:

```text
Ready
 ↓
minimal/no normal log

Readiness failure
 ↓
meaningful log
```

The exact strategy depends on your logging middleware.

# 22. Readiness and Authentication

Like `/healthz`, `/readyz` normally should not require a user's JWT.

Don't do:

```text
/readyz
 ↓
JWT
 ↓
user authentication
```

Infrastructure needs to call it before normal application traffic.

So:

```text
GET /readyz
     ↓
No user authentication
     ↓
Dependency check
```

---

# 23. Readiness and Rate Limiting

Similarly, don't blindly apply your normal user-facing rate limiter.

Imagine your infrastructure checks:

```text
/readyz
```

frequently.

If your rate limiter responds:

```http
429 Too Many Requests
```

the infrastructure might interpret that as:

```text
"Server isn't ready."
```

when the actual problem is simply your rate-limit configuration.

Operational endpoints need thoughtful middleware treatment.

# 26. Readiness During Shutdown

Here's another powerful idea.

Suppose your server receives:

```text
SIGTERM
```

because it's being stopped.

You don't want new traffic to keep arriving while shutdown is happening.

Conceptually:

```text
READY
  ↓
shutdown begins
  ↓
NOT READY
  ↓
stop receiving new traffic
  ↓
finish existing requests
  ↓
close resources
  ↓
exit
```

So readiness isn't only about startup.

It can also help during **shutdown**.

You'll study graceful shutdown more deeply later in your Docker and production phases. Your source explicitly lists graceful shutdown as part of the later production architecture.

# 27. Readiness State in Code

Instead of always calculating everything from scratch, your application can maintain an internal readiness state.

Conceptually:

```js
let isReady = false;
```

During startup:

```text
Start
 ↓
isReady = false
 ↓
Connect MongoDB
 ↓
Success
 ↓
isReady = true
 ↓
Ready
```

Then:

```js
app.get("/readyz", (req, res) => {
    if (!isReady) {
        return res.status(503).json({
            success: false,
            message: "Server is not ready"
        });
    }

    return res.status(200).json({
        success: true,
        message: "Server is ready"
    });
});
```

This is one possible architecture.

---

# 28. State vs Live Dependency Check

There are two broad approaches.

### Approach A — Check dependency on every request

```text
/readyz
 ↓
check MongoDB
 ↓
return result
```

### Approach B — Maintain application readiness state

```text
MongoDB connection event
       ↓
update readiness state
       ↓
/readyz reads state
```

Neither should be treated as universally correct.

For your learning, understand the difference first.

---

# 29. Why State Can Be Useful

Suppose:

```text
/readyz
```

is called 20 times per second.

You don't necessarily want:

```text
20 MongoDB checks/second
```

Instead:

```text
MongoDB connection state
       ↓
application readiness state
       ↓
many cheap /readyz responses
```

This can reduce unnecessary work.

---

# 30. Why Live Checks Can Be Useful

On the other hand, a direct dependency check can detect:

```text
MongoDB unavailable
```

at the moment the readiness endpoint is called.

So:

```text
State-based
   ↓
cheap

Live dependency check
   ↓
fresh
```

There is a tradeoff.

For a small MERN starter, don't overengineer this yet.

# 32. A Small Implementation

For your current learning architecture:

### `health.controller.js`

```js
import mongoose from "mongoose";

export const healthCheck = (req, res) => {
    return res.status(200).json({
        success: true,
        message: "Server is healthy"
    });

        return res.status(503).json({
            success: false,
            message: "Server is not ready"
        });
    }

    return res.status(200).json({
        success: true,
        message: "Server is ready"
    });
};
```

And:

```js
router.get("/healthz", healthCheck);
router.get("/readyz", readinessCheck);
```

```text

/readyz
```

# 36. Common Mistake: Making Health and Readiness Identical

Bad architecture:

```js
app.get("/healthz", checkMongo);
app.get("/readyz", checkMongo);
```

Now both endpoints mean basically the same thing.

You've lost the distinction.

Instead:

```text
/healthz
    ↓
process/liveness

/readyz
    ↓
service readiness
```

---

# 37. Common Mistake: Checking Too Many Things

Suppose your app uses an email provider.

If email is temporarily down:

```text
MongoDB → ✅
Node → ✅
Email → ❌
```

Does that necessarily mean the whole API cannot receive traffic?

Maybe not.

If email is only used asynchronously for:

```text
welcome email
```

then your API may still be perfectly capable of handling:

```text
GET /todos
POST /todos
PATCH /todos
```

So don't automatically make:

```text
email failure → entire application not ready
```

The correct readiness dependencies depend on your architecture.

---

# 38. Required vs Optional Dependencies

This distinction is extremely useful.

### Required dependency

Without it, normal service operation is impossible.

Example:

```text
MongoDB
```

for a database-driven API.

### Optional/deferred dependency

Failure doesn't prevent the core API from serving traffic.

Example:

```text
Email provider
```

if email is processed asynchronously.

So:

```text
Required
   ↓
readiness candidate

Optional
   ↓
usually don't block readiness
```
