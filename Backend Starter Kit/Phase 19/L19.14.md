# Lesson 19.14 — Metrics Fundamentals

We've now learned three important observability signals:

```text
Logs
  ↓
What happened?

Health
  ↓
Is the application alive?

Readiness
  ↓
Can the application serve traffic?
```

Now we add **metrics**:

```text
Metrics
  ↓
How is the system behaving over time?
```

Your Phase 19 source places **Metrics fundamentals** directly after health and readiness checks, followed by building the complete backend observability layer.

---

# 1. What Is a Metric?

A metric is a **numeric measurement** about your system.

Examples:

```text
Requests = 12,450
Errors = 320
Average latency = 180 ms
CPU = 62%
Memory = 71%
Active users = 84
```

Unlike a log, a metric is usually a number that can be measured repeatedly over time.

Think:

```text
Log
 ↓
"I received POST /todos from user 123"

Metric
 ↓
"POST /todos was called 8,421 times"
```

---

# 2. Why Do We Need Metrics?

Imagine your API is slow.

A log might tell you:

```text
GET /todos took 3.2 seconds
```

That's useful for one request.

But what if you want to know:

> "Has my API been getting slower during the last 24 hours?"

Metrics are much better for this.

You might see:

```text
10:00 → 120 ms
11:00 → 140 ms
12:00 → 180 ms
13:00 → 250 ms
14:00 → 420 ms
```

Now you can see a **trend**.

That's one of the biggest differences between logs and metrics.

---

# 3. Logs vs Metrics

Keep this table in your head:

|Signal|Main question|
|---|---|
|Logs|What happened?|
|Health|Is it alive?|
|Readiness|Can it serve traffic?|
|Metrics|How is it behaving?|

For example:

### Log

```text
User 123 created Todo abc
```

### Health

```text
/healthz → 200
```

### Readiness

```text
/readyz → 200
```

### Metric

```text
todo_create_requests_total = 4,283
```

Each tells you something different.

---

# 4. Metrics Are Time-Oriented

This is extremely important.

A metric becomes much more useful when you observe it over time.

For example:

```text
Requests per minute

10:00  → 120
10:01  → 135
10:02  → 142
10:03  → 198
10:04  → 350
```

You can now identify:

```text
traffic increasing
```

or:

```text
traffic suddenly dropped
```

That's much harder to understand from isolated logs.

---

# 5. The Four Metrics You Should Learn First

For a backend API, start with:

```text
1. Request count
2. Error count
3. Latency
4. Resource usage
```

These four already tell you a lot.

---

# 6. Request Count

Request count answers:

> **How much traffic are we receiving?**

Suppose:

```text
GET /todos
```

receives:

```text
5,000 requests/hour
```

You could track:

```text
http_requests_total = 5000
```

Or break it down:

```text
GET /todos      → 4,000
POST /todos     → 700
PATCH /todos/:id → 200
DELETE /todos/:id → 100
```

Now you know which endpoints are being used.

---

# 7. Why Request Count Matters

Suppose your server suddenly gets:

```text
100 requests/minute
```

and then:

```text
20,000 requests/minute
```

That's a huge change.

Possible explanations:

```text
Traffic spike
Marketing campaign
Frontend bug
Bot
Attack
Retry storm
```

Metrics can make the change immediately visible.

---

# 8. Error Count

Now measure:

```text
HTTP 5xx responses
```

For example:

```text
500 → 120
502 → 20
503 → 80
```

You might create a metric such as:

```text
http_errors_total = 220
```

This helps answer:

> **Is the application failing?**

---

# 9. Error Rate Is More Useful Than Error Count

Suppose:

```text
Requests = 100
Errors = 10
```

Error rate:

```text
10 / 100 = 10%
```

But:

```text
Requests = 100,000
Errors = 500
```

Error rate:

```text
500 / 100000 = 0.5%
```

The second system has more errors in absolute numbers but is actually much healthier relative to traffic.

So we often care about:

```text
Error rate
=
errors / total requests
```

---

# 10. Latency

Latency means:

> **How long does a request take?**

Example:

```text
GET /todos
```

takes:

```text
150 ms
```

Another:

```text
POST /todos
```

takes:

```text
420 ms
```

You can track request duration as a metric.

---

# 11. Average Latency Isn't Enough

Suppose you have 100 requests:

```text
99 requests → 50 ms
1 request   → 10 seconds
```

Average latency may hide the problem.

That's why production systems often care about **percentiles**.

You'll commonly hear:

```text
p50
p90
p95
p99
```

---

# 12. What Is p50?

p50 is approximately the median.

If:

```text
p50 = 100 ms
```

it means roughly half of requests are at or below that latency.

Think:

```text
50% of requests
      ↓
≤ 100 ms
```

It's useful for understanding the typical request.

---

# 13. What Is p95?

If:

```text
p95 = 500 ms
```

roughly:

```text
95% of requests
      ↓
≤ 500 ms
```

and the slowest:

```text
5%
```

are above that.

This helps you see the slower side of your application.

---

# 14. What Is p99?

If:

```text
p99 = 2 seconds
```

roughly:

```text
99% of requests
      ↓
≤ 2 seconds
```

while the slowest:

```text
1%
```

take longer.

This is useful because users experiencing those slow requests still matter.

---

# 15. Why Percentiles Matter

Imagine:

```text
Average latency = 120 ms
```

Looks great.

But:

```text
p99 = 8 seconds
```

That's a very different story.

Your average is hiding a serious tail-latency problem.

So production monitoring often looks at:

```text
p50
p95
p99
```

rather than only average latency.

# 20. A Metric Has a Name

Conceptually:

```text
http_requests_total
```

could represent:

> Total number of HTTP requests.

Another:

```text
http_request_duration
```

could represent:

> Request processing duration.

Another:

```text
http_errors_total
```

could represent:

> Number of failed HTTP requests.

The naming convention depends on the metrics system you use.

---

# 21. A Metric Can Have Dimensions

Suppose you only have:

```text
http_requests_total = 10000
```

That's useful, but limited.

You might want to know:

```text
GET
POST
PATCH
DELETE
```

or:

```text
/todos
/users
/auth/login
```

So metrics can have labels/dimensions conceptually like:

```text
http_requests_total
    method = GET
    route = /todos
    status = 200
```

Then you can analyze requests by these dimensions.

---

# 22. Be Careful With Labels

This is a very important production lesson.

Don't use highly unique values as metric labels.

Bad:

```text
userId = 938475938475
```

or:

```text
requestId = abc123...
```

Why?

Because every unique value can create a new metric time series.

That can explode your monitoring system's cardinality.

Prefer controlled values:

```text
method = GET
route = /todos
status = 200
```

These have a relatively small number of possible values.

---

# 23. What Is Cardinality?

Cardinality basically means:

> **How many unique combinations of label values exist?**

Imagine:

```text
method:
GET
POST

status:
200
201
400
404
500

route:
10 routes
```

That's manageable.

But:

```text
userId:
1,000,000 users
```

can create a huge number of combinations.

So:

```text
Low/controlled cardinality
        ↓
Good

Unbounded unique IDs
        ↓
Dangerous
```

This is an important professional habit.

---

# 24. Route vs Raw URL

Suppose users request:

```text
/users/123
/users/456
/users/789
```

Don't necessarily create metric labels like:

```text
path=/users/123
path=/users/456
path=/users/789
```

Instead normalize to:

```text
route=/users/:id
```

Now you have one logical route.

This keeps metrics much more useful.

---

# 25. Counters

One common metric type is a **counter**.

A counter generally increases:

```text
0
1
2
3
4
5
```

Examples:

```text
requests_total
errors_total
login_attempts_total
emails_sent_total
```

You don't normally decrease a counter.

When the application restarts, the counter can reset depending on the metrics implementation.

---

# 26. Gauges

Another concept is a **gauge**.

A gauge can move up and down:

```text
20
25
31
28
15
18
```

Examples:

```text
active_connections
memory_usage
queue_size
```

So:

```text
Counter
 ↓
usually increases

Gauge
 ↓
can increase or decrease
```

---

# 27. Histograms

Histograms are particularly useful for latency.

Instead of only saying:

```text
average = 250 ms
```

a histogram helps capture the distribution of observations.

For example:

```text
0–100 ms    → 800 requests
100–200 ms  → 1,500
200–500 ms  → 600
500–1000 ms → 90
>1000 ms    → 10
```

From distributions like this, systems can calculate useful percentiles.

# 29. Metrics Are Not Logs

Don't try to turn every log into a metric.

For example:

```text
User 123 created Todo abc
```

is a log/event.

You might separately maintain:

```text
todos_created_total = 12500
```

The metric gives you an aggregate view.

The log gives you detailed context.

So:

```text
Metric
 ↓
"How many?"

Log
 ↓
"Which one? Who? When? What exactly happened?"
```

---

# 30. Metrics Are Not Traces

You haven't reached distributed tracing yet, but understand the distinction.

Metrics:

```text
API latency = 300 ms
```

Trace:

```text
HTTP request
 ↓ 20 ms
controller
 ↓ 30 ms
service
 ↓ 240 ms
MongoDB
 ↓ 10 ms
response
```

Metrics give you the big picture.

Traces help you follow an individual request across components.

# 35. Metrics and Alerts

Metrics become especially powerful when you create alerts.

For example:

```text
IF error_rate > 5%
FOR 5 minutes
THEN alert
```

or:

```text
IF p95_latency > 1 second
FOR 10 minutes
THEN alert
```

Or:

```text
IF readiness failures increase
THEN investigate deployment/dependency
```

You don't need to build the alerting system in this lesson.

Just understand the relationship:

```text
Metric
 ↓
Threshold/condition
 ↓
Alert
```

# 38. What Is Saturation?

Saturation means:

> **How close are we to running out of capacity?**

Examples:

```text
CPU → 95%
Memory → 92%
Database connections → 98%
Queue → 99% full
```

Your system might still be healthy right now, but it is getting dangerously close to its limits.

That's why saturation is important.

# 41. Don't Put Metrics Logic Everywhere

Avoid this:

```js
controller() {
    metrics.increment(...);

    service();

    metrics.increment(...);

    metrics.record(...);
}
```

everywhere in your codebase.

That quickly becomes messy.

Instead, look for reusable instrumentation points:

```text
HTTP middleware
Database layer
Background job system
```

This keeps observability more centralized.

---

# 42. HTTP Metrics Middleware

Conceptually:

```js
app.use((req, res, next) => {
    const start = Date.now();

    res.on("finish", () => {
        const duration = Date.now() - start;

        // record:
        // method
        // route
        // status
        // duration
    });

    next();
});
```

This can observe:

```text
method
route
status
duration
```

for every request.

You don't need to implement the full metrics system yet.

We're learning the architecture first.

---

# 43. Metrics Should Use Meaningful Dimensions

A useful HTTP metric could conceptually contain:

```text
method = GET
route = /api/v1/todos
status = 200
```

Then you can ask:

```text
How many GET /todos requests succeeded?
```

or:

```text
How many POST /todos requests failed?
```

or:

```text
What's the latency of GET /todos?
```

That's far more useful than one giant:

```text
requests = 1,000,000
```

---

# 44. Don't Add Every Possible Dimension

This is the balance:

```text
Too little information
        ↓
metric isn't useful

Too many unique labels
        ↓
cardinality explosion
```

Good:

```text
method
route
status
```

Potentially dangerous:

```text
userId
requestId
email
IP address
```

because these can have huge numbers of unique values.

---

# 45. Metrics and Privacy

Another important point:

Don't put sensitive personal information into metrics.

For example:

```text
email
phone number
access token
password
```

should never become metric labels.

Metrics are operational data, not a dumping ground for application data.
