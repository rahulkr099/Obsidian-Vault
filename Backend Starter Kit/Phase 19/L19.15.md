# 3. Logs — "What Happened?"

Suppose a request fails:

```http

```

Your logs might tell you:

```text
requestId = req_abc123
method = POST
route = /api/v1/todos
status = 500
duration = 245ms
userId = user_123
```

This gives you **details about a specific event**.

Your roadmap specifically emphasizes request IDs, request logging, error logging, user context, sensitive-data handling, Pino, and production logging before reaching this final build lesson.

# 12. Logger

Your logger's responsibility:

```text
Application event
       ↓
Logger
       ↓
Structured log
```

For example:

```js
logger.info({
    requestId,
    userId,
    route,
    statusCode
}, "Request completed");
```

With Pino, the important idea is that logs are structured data rather than random strings.

---

# 13. Request Logging

At the HTTP layer:

```text
Request starts
     ↓
record start time
     ↓
request continues
     ↓
response finishes
     ↓
calculate duration
     ↓
log result
```

Conceptually:

```js
const start = Date.now();

res.on("finish", () => {
    const duration = Date.now() - start;

    logger.info({
        method: req.method,
        path: req.originalUrl,
        statusCode: res.statusCode,
        duration,
        requestId: req.id
    }, "Request completed");
});
```

Now every request produces useful operational information.

---

# 14. Error Logging

Normal requests:

```text
INFO
```

Failures:

```text
ERROR
```

For example:

```js
logger.error({
    err,
    requestId: req.id
}, "Request failed");
```

The important thing is that your error log contains enough context to investigate the failure.

---

# 15. Don't Log Everything

This is important.

Bad:

```js
logger.info(req);
logger.info(req.body);
logger.info(req.headers);
logger.info(req.cookies);
```

You may accidentally log:

```text
passwords
tokens
cookies
authorization headers
personal information
```

Your roadmap explicitly includes **Sensitive data in logs** before Pino and production logging.

So observability must be designed with security in mind.

       ↓

       ↓

For example:

Then:

```js

```

# 17. Return the Request ID to the Client

This makes support and debugging much easier.

# 20. Health Module

Keep `/healthz` simple.

Conceptually:

```js
export function healthCheck(req, res) {
    return res.status(200).json({
        success: true,
        message: "Server is healthy"
    });
}
```

No database query.

No expensive calculation.

No authentication.

Just:

```text
"Can I respond?"
```

# 21. Readiness Module

Readiness can check required dependencies.

For your MongoDB backend:

```text
/readyz
   ↓
MongoDB connection state
   ↓
ready?
```

If ready:

```http
200 OK
```

If not:

```http
503 Service Unavailable
```

This separates:

```text
alive
```

from:

```text
ready
```

---

# 22. Why This Separation Is Powerful

Imagine:

```text
Node.js      ✅
Express      ✅
MongoDB      ❌
```

Then:

```text
/healthz → 200
/readyz  → 503
```

This tells infrastructure:

```text
The process exists,
but don't send normal traffic here.
```

That becomes particularly valuable during deployment and container orchestration.

Your starter's architecture explicitly calls out health/readiness for deployment.

# 25. Don't Expose Internal Errors

Bad API response:

```json
{
  "error": "MongoServerSelectionError: connection refused at 192.168..."
}
```

That's not appropriate for a production client.

Instead:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc123"
}
```

Then developers search:

```text
abc123
```

in logs.

This gives you both:

```text
Security
+
Debuggability
```

# 29. What Should You Alert On?

Don't alert on everything.

Good candidates include:

```text
High error rate
High p95 latency
Repeated readiness failures
Database connection failures
Very high CPU
Very high memory
```

For example:

```text
error rate > 5%
for 5 minutes
```

could trigger an alert.

The exact thresholds depend on the application.

# 31. Observability Should Be Designed Into the Architecture

Don't add observability only after production breaks.

Your architecture should naturally support it:

```text
Request
 ↓
Request ID
 ↓
Logging
 ↓
Business logic
 ↓
Metrics
 ↓
Response
```

This means observability becomes a **cross-cutting concern**.

It isn't owned by one controller or one service.

---

# 32. Don't Mix Business Logic With Observability

Bad:

```js
async function createTodo(data) {
    logger.info("Creating todo");

    const todo = await Todo.create(data);

    logger.info("Todo created");

    metrics.increment(...);

    return todo;
}
```

everywhere, manually.

This becomes noisy and repetitive.

Prefer centralized instrumentation where possible.

For example:

```text
HTTP middleware
      ↓
request metrics

Logger middleware
      ↓
request logging

Error middleware
      ↓
error logging

Repository/database instrumentation
      ↓
database metrics
```

Then business logic stays focused on business logic.

---

# 33. What Should Stay in Business Code?

Your service should focus on:

```text
Validate business rule
Create todo
Update todo
Delete todo
```

Not:

```text
Format log
Generate request ID
Calculate HTTP latency
Write access log
```

Those are infrastructure concerns.

# 35. What About Audit Logs?

Don't confuse normal observability logs with audit logs.

### Observability log

```text
GET /todos
status=200
duration=120ms
```

### Audit event

```text
User 123 deleted Todo 456
```

Audit logging is about recording important business/security actions.

Your source separately discusses activity/audit logging in the broader starter architecture.

You don't need to mix audit events with every HTTP access log.

---

# 36. Sensitive Data

Your observability system should follow the same security principles as the rest of your backend.

Never casually log:

```text
password
access token
refresh token
JWT
session cookie
credit card data
secrets
```

Even if logging makes debugging easier.

Remember:

```text
Logs are data.
```

And production logs often live outside your application server.
