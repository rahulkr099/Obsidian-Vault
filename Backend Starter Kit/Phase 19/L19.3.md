# Lesson 19.3 — `console.log()` vs Structured Logging

In the previous lessons, we learned:

- **19.1:** What logging is.
    
- **19.2:** Why backend logging matters.
    

Now we need to understand an important transition:

```text
console.log()
    ↓
Basic logging
```

versus:

```text
Structured logger
    ↓
Professional application logging
```

This distinction will become important when we introduce **Pino** later in this phase.

---

# 1. Start With `console.log()`

You've probably written:

```js
console.log("Server started");
```

Or:

```js
console.log("User created");
```

Or:

```js
console.log(req.method, req.originalUrl);
```

This is completely valid JavaScript.

And during development, it is very useful.

For example:

```js
app.get("/healthz", (req, res) => {
    console.log("Health check received");

    res.json({
        success: true
    });
});
```

You might see:

```text
Health check received
```

in your terminal.

Nothing wrong with that.

The problem starts when your application becomes larger.

---

# 2. The Problem With Plain Text

Suppose you write:

```js
console.log("User login successful");
```

You know what happened.

But a machine sees only a string:

```text
User login successful
```

What information does it contain?

Maybe:

```text
event = login
result = success
```

But that's not explicitly structured.

Now imagine:

```js
console.log(
    "User login successful",
    user.id,
    req.ip
);
```

You might get:

```text
User login successful 42 192.168.1.10
```

A human can understand it.

But a logging system has to guess:

```text
Which value is user ID?
Which value is IP?
What is the event?
What is the status?
```

That's where **structured logging** helps.

---

# 3. What Is Structured Logging?

Structured logging means:

> **Store log information as structured fields instead of putting everything into one plain-text sentence.**

For example:

```js
logger.info({
    event: "user.login.success",
    userId: user.id
});
```

Conceptually, the resulting log might look like:

```json
{
  "level": "info",
  "event": "user.login.success",
  "userId": "42"
}
```

Now each piece of information has a clear meaning.

```text
level
  ↓
info

event
  ↓
user.login.success

userId
  ↓
42
```

That's much easier for software to process.

---

# 4. Plain Text vs Structured Data

Compare these.

### Plain text

```text
User 42 logged in successfully
```

### Structured

```json
{
  "event": "user.login.success",
  "userId": "42"
}
```

The second one is much easier to search and analyze.

For example, a logging system can ask:

```text
Find all logs where:
event = user.login.success
```

or:

```text
Find all logs where:
userId = 42
```

That's much harder to do reliably with arbitrary sentences.

---

# 5. Another Example

Suppose a Todo is created.

With `console.log()`:

```js
console.log(
    `Todo ${todo.id} created by user ${user.id}`
);
```

Output:

```text
Todo abc123 created by user 42
```

Looks fine.

But structured logging:

```js
logger.info({
    event: "todo.created",
    todoId: todo.id,
    userId: user.id
});
```

Conceptually:

```json
{
  "level": "info",
  "event": "todo.created",
  "todoId": "abc123",
  "userId": "42"
}
```

Now every value has a name.

---

# 6. Why This Matters in Production

Imagine you have:

```text
100,000 logs
```

You want:

> Find every failed login.

With structured logs:

```text
event = "user.login.failed"
```

Easy.

You want:

> Find all requests made by user 42.

Search:

```text
userId = 42
```

You want:

> Find requests taking longer than 1 second.

Search:

```text
duration > 1000
```

You want:

> Find all HTTP 500 responses.

Search:

```text
statusCode = 500
```

This is one of the biggest advantages of structured logging.

---

# 7. `console.log()` Can Still Print Objects

You might say:

> "But JavaScript's `console.log()` can already print objects."

Correct.

For example:

```js
console.log({
    event: "todo.created",
    todoId: todo.id,
    userId: user.id
});
```

You may get something like:

```text
{
  event: 'todo.created',
  todoId: 'abc123',
  userId: '42'
}
```

So is that structured logging?

**Conceptually, you're moving toward structured logging.**

But a production logging system provides much more:

```text
Structured fields
Log levels
Timestamps
Serialization
Error handling
Request context
Redaction
Output destinations
Performance features
Production configuration
```

That's why we eventually use a dedicated logger such as **Pino**.

---

# 8. Think of `console.log()` as a Basic Tool

A useful mental model:

```text
console.log()
     ↓
"I want to quickly see something."
```

A structured logger:

```text
logger.info()
logger.warn()
logger.error()
     ↓
"I want this event to become
a useful operational record."
```

Both have their place.

---

# 9. Example: Request Logging

Suppose we want to log:

```text
GET /api/v1/todos
200
42ms
```

With `console.log()`:

```js
console.log(
    req.method,
    req.originalUrl,
    res.statusCode,
    duration
);
```

Output might be:

```text
GET /api/v1/todos 200 42
```

A developer can understand it.

But structured logging could represent it as:

```js
logger.info({
    event: "request.completed",
    method: req.method,
    path: req.originalUrl,
    statusCode: res.statusCode,
    duration
});
```

Conceptually:

```json
{
  "level": "info",
  "event": "request.completed",
  "method": "GET",
  "path": "/api/v1/todos",
  "statusCode": 200,
  "duration": 42
}
```

Much better.

---

# 10. Timestamps

Another advantage of a proper logger is that logs can consistently include timestamps.

You might want:

```json
{
  "timestamp": "2026-08-26T10:30:15.321Z",
  "level": "info",
  "event": "request.completed",
  "statusCode": 200
}
```

Now you know exactly when the event happened.

With raw `console.log()`, you don't necessarily design a consistent timestamp format yourself.

---

# 11. Log Levels

Structured logging systems usually support different levels.

For example:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

We'll study these deeply in **19.4 and 19.5**.

For now, understand the idea.

### INFO

Normal application event:

```text
Database connected
```

### WARN

Something unusual:

```text
Rate limit nearly reached
```

### ERROR

Something failed:

```text
Database query failed
```

### DEBUG

Detailed information useful during development.

This is another major difference between:

```text
console.log("something")
```

and:

```text
logger.info(...)
logger.warn(...)
logger.error(...)
logger.debug(...)
```

---

# 12. Errors Are Another Big Difference

Suppose you have:

```js
try {
    await createTodo();
} catch (error) {
    console.log(error);
}
```

This works.

But a proper logger can record an error in a structured way:

```js
logger.error({
    event: "todo.create.failed",
    error
});
```

The logger can serialize useful error information consistently.

Later, when we integrate logging with your **global error middleware**, this becomes particularly useful.

---

# 13. Searching Logs

Imagine your production system has:

```text
1 million logs
```

You want:

> Show me all failed requests for `/api/v1/todos`.

With structured data, you can conceptually filter:

```text
path = "/api/v1/todos"
statusCode >= 500
```

You could also search:

```text
userId = 42
```

or:

```text
requestId = "abc123"
```

This is much more reliable than searching arbitrary sentences.

---

# 14. Structured Logs Are Machine-Friendly

This is the key phrase to remember:

> **Structured logs are designed to be useful to both humans and machines.**

Humans can read:

```json
{
  "event": "todo.created",
  "userId": "42",
  "todoId": "abc123"
}
```

A logging platform can also process:

```text
event
userId
todoId
```

and create:

```text
filters
dashboards
alerts
searches
aggregations
```

That's where logging starts becoming part of **observability**.

---

# 15. Don't Confuse Structured Logging With JSON Alone

You'll often see structured logs represented as JSON:

```json
{
  "level": "info",
  "event": "todo.created"
}
```

That's common because JSON is easy for machines to process.

But the important concept is not:

> "Logging must be JSON."

The important concept is:

> **The information has clearly defined fields.**

JSON is simply a very common format for representing those fields.

---

# 16. What About Development?

You don't necessarily want ugly JSON flooding your terminal while developing.

A logger can often be configured differently for development and production.

### Development

You might prefer:

```text
INFO: Todo created
```

### Production

You might use structured JSON:

```json
{
  "level": "info",
  "event": "todo.created",
  "todoId": "abc123"
}
```

The underlying logging concept remains the same.

The output can be adapted to the environment.

# 19. One Important Warning: Don't Log Everything

Structured logging doesn't mean:

```js
logger.info({
    req,
    res,
    user,
    body,
    headers
});
```

**Don't do this blindly.**

You might accidentally log:

```text
password
authorization header
access token
refresh token
cookies
personal information
```

Structured logging makes information easier to search — which means accidentally exposing secrets can become even worse.

We'll later learn **redaction**.

---

# 20. A Practical Comparison

|Basic `console.log()`|Structured logging|
|---|---|
|Simple|More systematic|
|Great for quick debugging|Designed for applications|
|Usually plain text|Structured fields|
|Limited context|Rich context|
|Basic levels|Log levels|
|Harder to search reliably|Easy to filter/search|
|Manual consistency|Centralized configuration|
|Fine for learning|Better for production|

Don't interpret this as:

> "`console.log()` is bad."

Instead:

> **`console.log()` is a simple tool; structured logging is an application architecture.**

Take this:


Convert it mentally into structured data:

```js

```

Another one:

```js
console.log(
    `GET ${req.originalUrl} returned ${res.statusCode}`
```

```js

    statusCode: res.statusCode
}
```

Notice what happened.

We moved from:

```text
Sentence
```

to:

```text
Data
```

**That's the core idea of structured logging.**
