# Lesson 19.4 — Log Levels

In **19.3**, we learned that structured logging turns logs into meaningful data.

Now we need to answer:

> **How do we tell how important a log message is?**

That's what **log levels** are for.

Your backend might produce thousands or millions of log events. Not every event has the same importance.

For example:

```text
Server started
```

is normal.

But:

```text
Database connection failed
```

is serious.

And:

```text
Application crashed
```

is even more serious.

Log levels give us a way to classify these events.

---

# 1. What Is a Log Level?

A **log level** tells us the importance or severity of a log event.

Think:

```text
How serious is this event?
```

A typical logging hierarchy looks like:

```text
DEBUG
  ↓
INFO
  ↓
WARN
  ↓
ERROR
  ↓
FATAL
```

As you move downward:

```text
importance/severity ↑
```

So:

```text
DEBUG
```

is generally less serious than:

```text
ERROR
```

---

# 2. Why Do We Need Levels?

Imagine your backend produces:

```text
10,000 logs
```

You don't want to read every single one.

Maybe you only care about errors:

```text
ERROR
```

Or perhaps you are investigating a bug and want detailed information:

```text
DEBUG
```

Log levels allow you to control what you care about.

For example:

```text
Development
→ DEBUG + INFO + WARN + ERROR

Production
→ INFO + WARN + ERROR
```

The exact configuration depends on the application.

---

# 3. The Five Levels We'll Learn

For this course, we'll use:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

Let's understand them one by one.

---

# 4. DEBUG

`DEBUG` is for detailed information useful when investigating how the application works.

Example:

```text
DEBUG database query started
DEBUG validation completed
DEBUG repository.findUserByEmail called
```

These messages can be very useful while developing or troubleshooting.

For example:

```js
logger.debug({
    event: "user.lookup.started",
    email: normalizedEmail
});
```

**Important:** Be careful with sensitive values. You should not log passwords or secrets just because you're using `DEBUG`.

---

# 5. INFO

`INFO` means:

> **Something normal and useful happened.**

Examples:

```text
Server started
Database connected
User created
Todo created
Request completed
```

For example:

```js
logger.info({
    event: "server.started",
    port: 5000
});
```

Or:

```js
logger.info({
    event: "todo.created",
    todoId: todo.id,
    userId: user.id
});
```

This is probably the most common level for normal application events.

---

# 6. WARN

`WARN` means:

> **Something unusual happened, but the application can continue working.**

For example:

```text
Rate limit almost reached
Deprecated API used
Repeated failed login attempts
External service responding slowly
```

Example:

```js
logger.warn({
    event: "rate_limit.near_limit",
    userId: user.id
});
```

The important idea:

```text
WARN ≠ application failure
```

Something deserves attention, but the system isn't necessarily broken.

---

# 7. ERROR

`ERROR` means:

> **Something failed and needs attention.**

Examples:

```text
Database query failed
External API request failed
Unexpected exception
File operation failed
```

For example:

```js
logger.error({
    event: "todo.create.failed",
    error
});
```

A request could then result in:

```text
ERROR
requestId=abc123
event=todo.create.failed
statusCode=500
```

This is something you would normally investigate.

---

# 8. FATAL

`FATAL` represents a very serious failure where the application or an important subsystem cannot continue safely.

For example:

```text
Application cannot start
Required configuration missing
Critical database initialization failed
```

Conceptually:

```text
FATAL
   ↓
Application cannot operate normally
```

For example:

```js
logger.fatal({
    event: "application.startup.failed",
    error
});
```

Depending on the logger and application architecture, the process may then terminate.

---

# 9. A Simple Analogy

Imagine a hospital.

### DEBUG

```text
Doctor checking patient's temperature
```

Useful detail.

### INFO

```text
Patient admitted
```

Normal event.

### WARN

```text
Patient's temperature is slightly high
```

Needs attention.

### ERROR

```text
Important medical equipment failed
```

Serious problem.

### FATAL

```text
Critical hospital system is completely unavailable
```

Extremely serious.

The exact meaning depends on your system, but the idea is:

> **The level communicates severity.**

---

# 10. Log Levels Are Not HTTP Status Codes

This is important.

Don't confuse:

```text
INFO
WARN
ERROR
```

with:

```text
200
400
404
500
```

They represent different things.

### HTTP status

Describes the result of an HTTP request.

```text
200 OK
404 Not Found
500 Internal Server Error
```

### Log level

Describes the importance/severity of a logged event.

```text
INFO
WARN
ERROR
```

They can work together.

For example:

```text
HTTP 404
```

might be logged as:

```text
INFO
```

or:

```text
WARN
```

depending on the situation.

A normal "resource not found" response isn't automatically a system error.

---

# 11. Example: Login

Let's think about authentication.

### Successful login

```text
INFO
event=user.login.success
```

Normal event.

### Invalid credentials

```text
WARN
event=user.login.failed
reason=invalid_credentials
```

Potentially suspicious, but not necessarily a system failure.

### Database failure during login

```text
ERROR
event=user.login.failed
reason=database_error
```

Now the application itself encountered a problem.

This example shows why log levels require **context**.

---

# 12. Example: Todo Creation

Suppose:

```text
POST /api/v1/todos
```

Everything works:

```text
INFO todo.create.completed
```

Validation fails:

```text
WARN todo.create.validation_failed
```

Database operation fails:

```text
ERROR todo.create.database_failed
```

Application cannot initialize the database at startup:

```text
FATAL database.initialization_failed
```

Same feature, different severity.

---

# 13. The Hierarchy

Think about it like this:

```text
                  FATAL
                    ▲
                    │
                  ERROR
                    ▲
                    │
                   WARN
                    ▲
                    │
                   INFO
                    ▲
                    │
                  DEBUG
```

But don't interpret this as:

> "DEBUG is unimportant."

DEBUG can be extremely valuable during troubleshooting.

It simply means:

> **DEBUG is usually more detailed and less operationally severe.**

---

# 14. Production Filtering

Suppose your application generates:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

You might configure production to show:

```text
INFO
WARN
ERROR
FATAL
```

while hiding DEBUG logs.

Conceptually:

```text
DEBUG ────────────────┐
                      │
INFO ────────┐        │
WARN         │        │
ERROR        ├──→ Production logs
FATAL ───────┘
```

This reduces noise.

During development, you might want:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

because you're actively investigating your application.

---

# 15. Why Filtering Matters

Imagine your production application creates:

```text
1,000,000 DEBUG logs
```

If you don't need them, that's just noise.

It can lead to:

```text
More storage
More processing
More network traffic
Harder searches
Higher logging costs
```

Instead, you might keep detailed DEBUG logging available when needed and use a more focused level in normal production operation.

---

# 16. Log Levels and Observability

Eventually you might have a monitoring system that says:

```text
ERROR logs increased by 300%
```

That could trigger an alert.

For example:

```text
Normal:
ERROR = 5/min

Suddenly:
ERROR = 500/min
```

That's a strong signal that something is wrong.

So log levels aren't just labels.

They can become useful for:

```text
Filtering
Searching
Dashboards
Alerts
Incident investigation
```

---

# 17. Don't Abuse ERROR

This is a very common mistake.

A beginner might write:

```js
logger.error("User entered invalid email");
```

But validation failure isn't necessarily a server error.

Instead, depending on your logging policy:

```text
WARN
```

might be more appropriate.

Another example:

```text
404 /users/123
```

doesn't automatically mean:

```text
ERROR
```

Maybe the user simply requested something that doesn't exist.

The correct level depends on what the event means operationally.

---

# 18. Don't Abuse WARN Either

Similarly, if everything becomes:

```text
WARN
```

then warnings lose their meaning.

For example:

```text
INFO request.completed
```

shouldn't become:

```text
WARN request.completed
```

just because you're trying to make the logs "important."

The purpose of levels is to provide useful **signal**.

---

# 19. A Practical Decision Process

When deciding the level, ask:

### Question 1

Is this normal application behavior?

```text
YES → INFO
```

### Question 2

Is it detailed diagnostic information?

```text
YES → DEBUG
```

### Question 3

Is something unusual happening, but the system can continue?

```text
YES → WARN
```

### Question 4

Did an operation fail?

```text
YES → ERROR
```

### Question 5

Can the application no longer operate safely?

```text
YES → FATAL
```

This isn't an absolute law, but it's a good starting point.


Notice how the logs tell a story.

# 23. Important Security Note

Never think:

> "I'll use DEBUG for sensitive information because DEBUG is hidden in production."

That's unsafe.

Someone may enable DEBUG during an incident.

For example, this is dangerous:

```js
logger.debug({
    password: req.body.password
});
```

Or:

```js
logger.debug({
    authorization: req.headers.authorization
});
```

Sensitive information should be protected regardless of the log level.

---

# 27. What You Should Remember

Don't memorize hundreds of logging rules.

Remember these five meanings:

```text
DEBUG
→ Tell me detailed diagnostic information.

INFO
→ Tell me something normal happened.

WARN
→ Tell me something unusual happened.

ERROR
→ Tell me something failed.

FATAL
→ Tell me the application cannot safely continue.
```

And one very important distinction:

> **Log level describes the severity of the event; HTTP status code describes the result of the HTTP request.**
