# Lesson 19.5 — DEBUG / INFO / WARN / ERROR / FATAL in Real Backend Scenarios

In **19.4**, we learned the basic meaning of the five log levels.

Now let's make them practical.

The goal of this lesson is that when you see a backend event, you should be able to think:

> **"What level should this event have, and why?"**

The five levels we'll use are:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

---

# 1. First, Don't Think of Levels as "Good vs Bad"

A common beginner mistake is:

```text
INFO  = good
WARN  = bad
ERROR = very bad
```

That's too simple.

A better way to think is:

```text
DEBUG → diagnostic detail
INFO  → normal important event
WARN  → unusual situation
ERROR → failed operation
FATAL → system cannot safely continue
```

For example:

```text
HTTP 404
```

doesn't automatically mean `ERROR`.

And:

```text
Login failed
```

doesn't automatically mean `ERROR`.

**Context matters.**

---

# 2. DEBUG — Detailed Diagnostic Information

Use `DEBUG` when you want information that helps a developer understand **how the application is working internally**.

For example:

```text
DEBUG validation.started
DEBUG authentication.started
DEBUG repository.findUser.started
DEBUG database.query.started
```

Imagine your service:

```js
async function createTodo(data, userId) {
    // ...
}
```

During debugging, you might want to know:

```text
DEBUG todo.create.started
DEBUG validation.completed
DEBUG user.lookup.completed
DEBUG repository.create.started
```

These aren't necessarily important operational events.

They're **diagnostic breadcrumbs**.

---

# 3. DEBUG Example — Repository

Imagine:

```text
Service
   ↓
Repository
   ↓
MongoDB
```

You might log:

```js
logger.debug({
    event: "todo.repository.create.started"
});
```

Then:

```js
logger.debug({
    event: "todo.repository.create.completed"
});
```

This can help answer:

> Did the repository method actually execute?

---

# 4. When DEBUG Is Useful

Imagine a user reports:

> "Sometimes creating a Todo takes a long time."

You can investigate with detailed logs:

```text
DEBUG todo.create.started
DEBUG validation.completed
DEBUG user.lookup.completed
DEBUG repository.create.started
DEBUG repository.create.completed
```

Now you can see where the delay happened.

For example:

```text
DEBUG validation.completed       2ms
DEBUG user.lookup.completed     15ms
DEBUG repository.create.started
DEBUG repository.create.completed 3200ms
```

You immediately know:

> The repository/database operation may be the slow part.

---

# 5. INFO — Normal Important Events

`INFO` is for events that are normal and useful to know about.

Examples:

```text
INFO server.started
INFO database.connected
INFO user.created
INFO todo.created
INFO request.completed
```

For example:

```js
logger.info({
    event: "database.connected"
});
```

Or:

```js
logger.info({
    event: "todo.created",
    todoId: todo.id,
    userId: user.id
});
```

These are normal application events.

---

# 6. INFO Doesn't Mean "Everything"

You don't need:

```text
INFO variable.x = 1
INFO entered function
INFO loop started
INFO loop ended
```

That creates noise.

Instead, use INFO for events that are useful from an operational perspective.

For example:

```text
INFO server.started
```

is useful.

```text
INFO todo.created
```

can be useful.

```text
INFO variable.x=1
```

usually isn't.

That's where `DEBUG` may be more appropriate.

---

# 7. WARN — Something Is Unusual

`WARN` means:

> Something deserves attention, but the system is still functioning.

Examples:

```text
WARN authentication.failed
WARN rate_limit.near_limit
WARN deprecated_endpoint.used
WARN external_service.slow
```

Let's look at some realistic examples.

---

# 8. WARN Example — Invalid Login

A user enters the wrong password.

```text
POST /api/v1/auth/login
```

Result:

```text
401 Unauthorized
```

You might log:

```text
WARN user.login.failed
reason=invalid_credentials
```

Why not `ERROR`?

Because your application didn't necessarily fail.

The user simply provided incorrect credentials.

The authentication system worked exactly as designed.

---

# 9. WARN Example — Repeated Login Failures

Suppose:

```text
5 failed attempts
```

You might log:

```text
WARN authentication.repeated_failures
```

If it becomes:

```text
1000 failed attempts
```

you might want stronger security monitoring or alerting.

The important point is:

```text
WARN
```

can highlight suspicious or unusual behavior without claiming that your application itself has failed.

---

# 10. WARN Example — Slow External Service

Suppose your backend calls:

```text
Payment Service
```

Normally:

```text
100ms
```

Today:

```text
2500ms
```

The request still succeeds.

You might log:

```text
WARN payment_service.slow
duration=2500ms
```

The system is working, but something unusual is happening.

---

# 11. ERROR — An Operation Failed

Now suppose the payment service returns an error.

```text
Payment Service
      ↓
500
```

Your application couldn't complete the operation.

That is a good candidate for:

```text
ERROR payment_service.request_failed
```

Similarly:

```text
ERROR database.query.failed
ERROR email.send.failed
ERROR file.upload.failed
ERROR todo.create.failed
```

---

# 12. ERROR Example — Database Failure

Imagine:

```js
try {
    await todoRepository.create(data);
} catch (error) {
    logger.error({
        event: "todo.create.failed",
        error
    });

    throw error;
}
```

The important point is:

```text
Operation failed
       ↓
ERROR
```

The application might still be running normally.

One request failed, not necessarily the entire application.

---

# 13. ERROR Does Not Mean the Server Crashed

This distinction is very important.

Suppose:

```text
Request A → database operation fails
Request B → works
Request C → works
```

You may have:

```text
ERROR request.failed
```

But your server is still alive.

```text
Node.js process
      │
      ├── Request A ❌
      ├── Request B ✅
      └── Request C ✅
```

So:

```text
ERROR ≠ application is dead
```

It means an important operation failed.

---

# 14. FATAL — Critical System Failure

`FATAL` is for situations where the application cannot safely continue.

Imagine your application requires an environment variable:

```text
DATABASE_URL
```

But it doesn't exist.

At startup:

```text
Application
    ↓
Database initialization
    ↓
DATABASE_URL missing
    ↓
Cannot start safely
```

A possible log:

```text
FATAL application.startup.failed
reason=DATABASE_URL_missing
```

The process may terminate.

---

# 15. FATAL Example — Required Dependency

Suppose your application absolutely requires MongoDB.

Startup:

```text
Node.js
  ↓
MongoDB connection
  ↓
Connection impossible
```

If your architecture cannot function without the database, you might treat this as:

```text
FATAL database.initialization.failed
```

The application shouldn't pretend everything is fine.

---

# 16. Another FATAL Example

Imagine your application requires an essential security configuration.

For example:

```text
JWT signing configuration missing
```

If the application cannot securely authenticate users without it, you may consider startup failure:

```text
FATAL authentication.configuration.invalid
```

The exact policy depends on your application.

---

# 17. A Full Example: Server Startup

Imagine your backend starts.

### Step 1

```text
DEBUG configuration.validation.started
```

### Step 2

```text
INFO configuration.validated
```

### Step 3

```text
INFO database.connected
```

### Step 4

```text
INFO server.started
port=5000
```

Everything is good.

---

# 18. Startup Failure

Now imagine:

```text
DEBUG configuration.validation.started
```

Then:

```text
ERROR database.connection.failed
```

But perhaps the application has a retry mechanism.

It tries again.

```text
WARN database.connection.retry
attempt=2
```

Then succeeds:

```text
INFO database.connected
```

The application continues.

This is a nice example of why context matters.

---

# 19. What If It Never Recovers?

Suppose:

```text
ERROR database.connection.failed
WARN database.connection.retry
ERROR database.connection.failed
WARN database.connection.retry
ERROR database.connection.failed
```

Eventually the application decides:

> "I cannot operate safely."

Then:

```text
FATAL database.initialization.failed
```

The progression might look like:

```text
ERROR
  ↓
WARN retry
  ↓
ERROR
  ↓
WARN retry
  ↓
FATAL
```

This is a realistic operational pattern.

---

# 20. HTTP Requests and Log Levels

Let's examine common HTTP situations.

### Successful request

```text
GET /todos
200
```

Potentially:

```text
INFO request.completed
```

### Invalid request

```text
POST /todos
400
```

Potentially:

```text
WARN request.validation_failed
```

### Authentication failure

```text
POST /auth/login
401
```

Potentially:

```text
WARN authentication.failed
```

### Server-side database failure

```text
POST /todos
500
```

Potentially:

```text
ERROR request.failed
```

Again:

> These are examples, not universal rules.

Your logging policy should define what your application considers important.

---

# 21. 404 Is a Great Example of Context

Suppose:

```text
GET /todos/999999
```

Todo doesn't exist.

Response:

```text
404 Not Found
```

Should that be:

```text
ERROR
```

Not necessarily.

It might be:

```text
INFO
```

because it's normal application behavior.

Or:

```text
WARN
```

if repeated missing-resource requests are unusual.

The HTTP status alone doesn't determine the log level.

---

# 22. 401 Is Also Context-Dependent

Suppose a user enters the wrong password:

```text
401
```

That's expected behavior.

You might use:

```text
WARN user.login.failed
```

But if your application has millions of these failures, you may need to aggregate them rather than producing a huge amount of logs.

This brings us back to an important principle:

> **Good logging is about useful signal, not maximum volume.**

---

# 23. Example: File Upload

Suppose a user uploads a file.

### Upload starts

```text
DEBUG file.upload.started
```

### Upload succeeds

```text
INFO file.upload.completed
```

### File is rejected because it violates an expected validation rule

```text
WARN file.upload.rejected
reason=file_type_not_allowed
```

### Storage service fails

```text
ERROR file.upload.storage_failed
```

### Required storage system is completely unavailable during startup

Potentially:

```text
FATAL storage.initialization.failed
```

Again, severity depends on context.

---

# 24. Example: Background Job

Imagine your backend has:

```text
Email Queue
```

A job starts:

```text
DEBUG email.job.started
```

It succeeds:

```text
INFO email.job.completed
```

It encounters a temporary issue:

```text
WARN email.job.retrying
```

It finally fails:

```text
ERROR email.job.failed
```

If the entire queue system cannot initialize:

```text
FATAL email_queue.initialization.failed
```

---

# 25. The Five Levels in One Scenario

Let's create one complete example.

A user creates a Todo.

```text
DEBUG
todo.create.started
```

Validation finishes:

```text
DEBUG
todo.validation.completed
```

Todo is successfully created:

```text
INFO
todo.created
```

But perhaps the request contains a suspicious pattern:

```text
WARN
todo.request.suspicious
```

Then the database operation fails:

```text
ERROR
todo.create.database_failed
```

If the entire database becomes unavailable and the application cannot operate:

```text
FATAL
database.unavailable
```

Notice the progression.

---

# 26. A Useful Decision Tree

When you're unsure which level to use, ask:

```text
                 What happened?
                       │
             ┌─────────┴─────────┐
             │                   │
       Just details?          Normal event?
             │                   │
           DEBUG                INFO
                                 │
                                 ▼
                         Something unusual?
                                 │
                                WARN
                                 │
                                 ▼
                          Operation failed?
                                 │
                                ERROR
                                 │
                                 ▼
                       System cannot continue?
                                 │
                               FATAL
```

It's not a strict mathematical rule, but it's a very useful mental model.

# 27. Common Beginner Mistakes

## Mistake 1 — Everything is ERROR

```text
ERROR server started
ERROR user logged in
ERROR todo created
ERROR validation failed
ERROR database failed
```

Now `ERROR` has no meaning.

---

## Mistake 2 — Everything is INFO

```text
INFO database failed
INFO application crashed
INFO invalid configuration
```

Now serious problems can easily get buried.

---

## Mistake 3 — DEBUG Contains Secrets

```text
DEBUG password=...
DEBUG token=...
```

Never do this.

---

## Mistake 4 — WARN Means "Error"

Not necessarily.

A warning can simply mean:

```text
Something unusual happened.
```

---

## Mistake 5 — FATAL For Every Startup Error

Not every startup problem means the whole system is unrecoverable.

For example, if the application can retry a temporary dependency failure, you might log the failure/retry rather than immediately treating it as fatal.

---

# 28. Real-World Thinking

Imagine you're on-call at 2 AM.

Your logging system shows:

```text
INFO  request.completed
INFO  request.completed
INFO  request.completed
WARN  external_service.slow
WARN  external_service.slow
ERROR payment.request.failed
ERROR payment.request.failed
ERROR payment.request.failed
FATAL payment_service.unavailable
```

You immediately know:

> Something serious is happening with the payment dependency.

Compare that with:

```text
ERROR
ERROR
INFO
ERROR
WARN
ERROR
INFO
ERROR
INFO
```

without meaningful events or context.

The second system is much harder to understand.

---

# 29. Structured Log Example

Eventually, instead of:

```text
ERROR database failed
```

you want something closer to:

```json
{
  "level": "error",
  "event": "todo.create.database_failed",
  "requestId": "req_123",
  "userId": "user_42",
  "duration": 842,
  "error": {
    "name": "MongoServerError"
  }
}
```

Now you know:

```text
Severity → error
Event    → todo.create.database_failed
Request  → req_123
User     → user_42
Duration → 842ms
Error    → MongoServerError
```

That's the direction we're heading toward.

# 30. Quick Classification Exercise

Classify these:

|Event|Suggested level|
|---|---|
|Server successfully started|`INFO`|
|Repository method started|`DEBUG`|
|User entered invalid credentials|`WARN`|
|Database query failed|`ERROR`|
|Required configuration prevents startup|`FATAL`|
|Todo successfully created|`INFO`|
|External API is unusually slow|`WARN`|
|Detailed query diagnostic|`DEBUG`|
|Email sending operation failed|`ERROR`|
|Critical required service cannot initialize|`FATAL`|

Remember: **"suggested"** is important. Different teams can define their own logging policy.

# 32. Final Mental Model

Keep this in your head:

```text
DEBUG
│
├── Detailed internal information
│
INFO
│
├── Normal useful application events
│
WARN
│
├── Something unusual needs attention
│
ERROR
│
├── An operation failed
│
FATAL
│
└── The system cannot safely continue
```

And the most important principle:

> **Choose a log level based on the operational meaning of the event, not simply based on whether the event "looks bad."**
