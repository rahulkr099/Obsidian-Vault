# Lesson 19.6 — What Should You Log?

In the previous lessons, we learned:

```text
19.1 → What is logging?
19.2 → Why logging matters
19.3 → console.log vs structured logging
19.4 → Log levels
19.5 → Using log levels in real situations
```

Now we reach a very practical question:

> **What should your backend actually record?**

Your roadmap places **19.6 as Error Logging**, so we'll focus especially on **what useful error information should be logged**, while also connecting it to request and application context. The uploaded roadmap explicitly lists Phase 19 as: logging → console vs structured logging → log levels → request IDs → request logging → error logging → user context → sensitive data → Pino → production logging.

---

# 1. The Golden Rule

Don't think:

> "I should log everything."

Think:

> **"I should log enough information to understand what happened."**

For example, this is weak:

```js
logger.error("Something went wrong");
```

What went wrong?

We don't know.

Where?

We don't know.

For which request?

We don't know.

Which user?

We don't know.

A much more useful error log might contain:

```text
level: error
event: todo.create.failed
requestId: req_123
userId: user_42
error: MongoServerError
duration: 842ms
```

Now we have evidence.

---

# 2. What Is an Error Log?

An **error log records an operation that failed or an unexpected application problem that needs investigation.**

For example:

```text
Database query failed
```

```text
External API request failed
```

```text
Email sending failed
```

```text
Unexpected exception
```

```text
File processing failed
```

These are good candidates for `ERROR`.

---

# 3. What Information Should an Error Log Contain?

A useful error log commonly contains several categories.

Think:

```text
ERROR
 │
 ├── What happened?
 ├── Where did it happen?
 ├── Which request?
 ├── Which user?
 ├── What error?
 └── When/how long?
```

Let's examine them.

---

# 4. 1 — The Event

First, describe **what operation failed**.

Bad:

```text
error: "Something went wrong"
```

Better:

```text
event: "todo.create.failed"
```

Or:

```text
event: "database.query.failed"
```

Or:

```text
event: "email.send.failed"
```

The event name should tell you what happened.

A useful convention is:

```text
resource.operation.result
```

For example:

```text
todo.create.failed
user.login.failed
email.send.failed
database.query.failed
```

This makes logs easier to search.

---

# 5. 2 — Request ID

You have already learned about **request IDs in Phase 16**, and they become extremely valuable here.

Imagine:

```text
requestId = req_abc123
```

Your error log can contain:

```text
{
    "level": "error",
    "event": "todo.create.failed",
    "requestId": "req_abc123"
}
```

Now if someone reports:

> "My request failed."

you can search:

```text
req_abc123
```

and find all related logs.

This is exactly why your roadmap puts request IDs before error logging.

---

# 6. 3 — User Context

If the request is authenticated, you may want useful user context.

For example:

```text
userId: 42
```

Then:

```json
{
  "level": "error",
  "event": "todo.create.failed",
  "requestId": "req_abc123",
  "userId": "42"
}
```

Now you can investigate:

> Which user's request failed?

But there is an important distinction:

### Good

```text
userId: 42
```

### Dangerous

```text
password: "..."
accessToken: "..."
refreshToken: "..."
```

We'll have a dedicated lesson for sensitive data later.

---

# 7. 4 — The Error Itself

You need to know what actually failed.

For example:

```text
error.name
error.message
```

Conceptually:

```json
{
  "error": {
    "name": "MongoServerError",
    "message": "..."
  }
}
```

But be careful.

The raw error may contain information you don't want to expose or store.

For production systems, you often want controlled error serialization.

---

# 8. 5 — Where Did It Fail?

Suppose:

```text
POST /api/v1/todos
```

failed.

That's useful.

But we can be even more specific:

```text
controller → service → repository → database
```

Maybe the actual failure occurred at:

```text
repository
```

So an event like:

```text
todo.repository.create.failed
```

can provide useful context.

However, don't create hundreds of meaningless layer-specific logs.

The goal is to make investigation easier, not generate noise.

---

# 9. 6 — HTTP Information

For request-related errors, useful information includes:

```text
method
path
statusCode
```

For example:

```json
{
  "level": "error",
  "event": "request.failed",
  "method": "POST",
  "path": "/api/v1/todos",
  "statusCode": 500
}
```

Now you know:

```text
POST
   ↓
/api/v1/todos
   ↓
500
```

That's much more useful than:

```text
ERROR failed
```

---

# 10. 7 — Duration

Suppose a database query failed after:

```text
5000ms
```

That information matters.

Maybe the real problem is a timeout.

So you might have:

```text
duration: 5000
```

Example:

```json
{
  "level": "error",
  "event": "todo.create.failed",
  "duration": 5000
}
```

Now you can investigate performance and failure together.

---

# 11. Example: Weak Error Logging

Imagine your controller:

```js
try {
    await todoService.createTodo(data);
} catch (error) {
    console.error("Todo creation failed");
}
```

Output:

```text
Todo creation failed
```

Problems:

```text
❌ Which request?
❌ Which user?
❌ Which Todo?
❌ What error?
❌ What endpoint?
❌ When?
❌ How long?
```

This doesn't give you enough evidence.

---

# 12. Better Error Logging

Conceptually:

```js
logger.error({
    event: "todo.create.failed",
    requestId: req.id,
    userId: req.user?.id,
    method: req.method,
    path: req.originalUrl,
    statusCode: 500,
    error
});
```

Now the log has context.

Conceptually:

```json
{
  "level": "error",
  "event": "todo.create.failed",
  "requestId": "req_abc123",
  "userId": "42",
  "method": "POST",
  "path": "/api/v1/todos",
  "statusCode": 500
}
```

---

# 13. Error Logging in Your Architecture

Remember your architecture:

```text
Request
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

Suppose MongoDB fails.

The flow might be:

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
Error middleware
```

Logging can capture the failure:

```text
ERROR database.query.failed
```

and then your global error handler can produce the HTTP response.

This connects logging with the error-handling architecture you've already learned.

---

# 14. Logging vs Returning the Error

This is important.

Suppose MongoDB produces:

```text
MongoServerError: ...
```

You generally don't want to simply send the raw internal error to the client.

Instead:

```text
Database error
      │
      ├──────────────→ Logger
      │                 │
      │                 ▼
      │              Detailed
      │              internal info
      │
      ▼
Global Error Handler
      │
      ▼
Safe API response
```

The client might receive:

```json
{
  "success": false,
  "message": "Something went wrong",
  "requestId": "req_abc123"
}
```

while your internal logs contain the details needed for debugging.

This is a very important production pattern.

---

# 15. The Request ID Connects Both Sides

Suppose the user receives:

```json
{
  "success": false,
  "message": "Something went wrong",
  "requestId": "req_abc123"
}
```

They can report:

> "My request ID is `req_abc123`."

You search your logs:

```text
req_abc123
```

and find:

```text
request.received
auth.success
todo.create.started
database.query.failed
request.completed
```

Now you can reconstruct the request.

This is one of the strongest reasons request IDs matter.

---

# 16. Don't Log Only the Final Error

Suppose you have:

```text
ERROR request.failed
```

That's useful.

But imagine you can also see:

```text
request.received
auth.success
todo.create.started
repository.create.started
database.query.failed
request.completed
```

Now you understand the **journey** of the request.

This is much more powerful than one isolated error message.

---

# 17. But Don't Duplicate Errors Everywhere

There's another side to this.

You might accidentally do:

```text
Repository:
ERROR database failed

Service:
ERROR todo failed

Controller:
ERROR request failed

Error middleware:
ERROR request failed
```

Now one failure generates four error logs.

That's noisy.

You need to design your logging responsibility carefully.

A useful principle:

> **Log an error where you have meaningful context, but avoid repeatedly logging the same error as it bubbles upward.**

We'll refine this when we build the complete logging architecture.

---

# 18. Operational Errors vs Programming Errors

This connects to your earlier error-handling lessons.

### Operational error

Something expected can fail during normal operation.

Examples:

```text
Database timeout
External service unavailable
Invalid user input
Resource not found
```

These can often be handled safely.

### Programming error

Something is wrong in your code.

For example:

```js
const user = null;

user.profile.name;
```

This might cause:

```text
TypeError
```

An unexpected programming error deserves serious investigation.

Your logger should preserve enough information to diagnose it.

---

# 19. Stack Traces

For unexpected errors, stack traces can be extremely useful.

Example:

```text
TypeError: Cannot read properties of undefined
    at createTodo (...)
    at processRequest (...)
    ...
```

The stack trace can tell you **where the error originated**.

A professional logger should be able to capture error objects properly.

This is one of the reasons we'll eventually use Pino rather than manually formatting every error.

---

# 20. Error Logging and Sensitive Information

Here's a subtle problem.

Suppose:

```js
logger.error({
    error
});
```

Sounds fine.

But what if the error object contains:

```text
database connection string
authorization data
request headers
personal information
```

You could accidentally put sensitive information into logs.

So:

> **Never assume an error object is automatically safe to log.**

We'll study redaction and sensitive-data protection later.

---

# 21. What Should NOT Be Logged?

For error logging, avoid blindly logging:

```text
❌ Passwords
❌ Access tokens
❌ Refresh tokens
❌ Authorization headers
❌ Session secrets
❌ API keys
❌ Full cookies
❌ Sensitive personal information
```

For example, don't do:

```js
logger.error({
    body: req.body,
    headers: req.headers,
    error
});
```

without carefully controlling what gets recorded.

That can become a security vulnerability.

---

# 22. Error Logging During Authentication

Suppose login fails.

You might record:

```text
WARN user.login.failed
reason=invalid_credentials
```

But don't record:

```text
password=wrongPassword
```

For a token refresh failure:

```text
WARN token.refresh.failed
```

Don't record:

```text
refreshToken=eyJ...
```

You want enough information to investigate **without recording secrets**.

---

# 23. Error Logging During Authorization

Suppose User A attempts to access User B's Todo.

Your authorization layer might reject the request:

```text
403 Forbidden
```

You could record something like:

```text
WARN authorization.denied
userId=42
resourceId=todo123
resource=todo
```

This can be useful for security investigation.

But again:

> Don't dump the entire request into your logs.

---

# 24. Error Logging During Validation

Suppose:

```http
POST /api/v1/todos
```

contains invalid data.

For example:

```json
{
  "title": ""
}
```

The API returns:

```http
400 Bad Request
```

You might log:

```text
WARN todo.validation.failed
requestId=req_123
```

Do you necessarily need to log the entire body?

**No.**

Maybe you only need:

```text
field=title
reason=required
```

depending on your logging policy.

---

# 25. A Good Error Log

Here's a good conceptual example:

```json
{
  "level": "error",
  "event": "todo.create.failed",
  "requestId": "req_123",
  "userId": "42",
  "method": "POST",
  "path": "/api/v1/todos",
  "statusCode": 500,
  "duration": 842,
  "error": {
    "name": "MongoServerError"
  }
}
```

Notice what is **not** there:

```text
❌ password
❌ JWT
❌ refresh token
❌ complete request body
❌ authorization header
```

That's the mindset we want.

---

# 26. A Useful Error Logging Checklist

When an important error happens, ask:

```text
[ ] What operation failed?
[ ] Which request caused it?
[ ] Which endpoint?
[ ] Which HTTP method?
[ ] Which user, if relevant?
[ ] What status code resulted?
[ ] How long did it take?
[ ] What type of error occurred?
[ ] Do we need the stack trace?
[ ] Are we accidentally logging secrets?
```

This is a very good checklist to remember.

# 30. The Mental Model

When something fails:

```text
                  ERROR
                    │
                    ▼
             What happened?
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    Operation    Request       Error
       info        info        info
        │           │           │
        └───────────┼───────────┘
                    ▼
                  LOGGER
                    │
                    ▼
              Internal logs
                    │
                    ▼
             Safe API response
```

The client gets a safe response.

The developer gets enough information to investigate.

# ⭐ Key Takeaway

The goal of error logging isn't:

> **"Print the error."**

It's:

> **"Record enough safe context to understand, investigate, and reproduce what went wrong."**

A strong error log answers:

```text
What failed?
Which request?
Which user?
Where?
When?
How long?
What error?
```

while avoiding:

```text
passwords
tokens
secrets
unnecessary sensitive data
```

Your next lesson is **19.7 — User Context in Logs**, where we'll carefully answer:

> **When should `userId` be included in a log, what user information is useful, and how do we avoid turning logging into a privacy/security problem?**
