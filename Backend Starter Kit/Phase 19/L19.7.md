# Lesson 19.7 — User Context in Logs

In **19.6**, we learned what useful error logs should contain.

Now we add another important piece of context:

> **Who was involved in this event?**

For an authenticated backend request, the answer is often:

```text
userId
```

This is called **user context**.

---

# 1. Why User Context Matters

Imagine your logs contain:

```text
ERROR todo.create.failed
```

That's not enough.

You know:

```text
Something failed.
```

But you don't know:

```text
Which user?
```

Now imagine:

```text
ERROR todo.create.failed
userId=42
```

Much better.

You can now investigate:

```text
User 42
   ↓
Request
   ↓
Todo creation
   ↓
Database failure
```

This can be extremely useful when debugging production problems.

---

# 2. User Context Doesn't Mean "Log Everything About the User"

This is very important.

When we say:

```text
user context
```

we don't mean:

```text
name
email
phone
address
password
tokens
cookies
```

A good default is often simply:

```text
userId
```

For example:

```json
{
  "event": "todo.create.failed",
  "userId": "42"
}
```

The goal is **identification for investigation**, not collecting unnecessary personal data.

---

# 3. User ID vs User Data

Compare these.

### Usually useful

```text
userId=42
```

### Potentially unnecessary

```text
email=rahul@example.com
name=Rahul
phone=...
```

If your database already lets you find the user from:

```text
userId=42
```

then logging the email or phone may add unnecessary privacy risk.

A good principle is:

> **Log the smallest amount of user information needed to understand the event.**

---

# 4. Where Does `userId` Come From?

In an authenticated application, authentication middleware normally identifies the user.

Conceptually:

```text
Request
   ↓
Authentication middleware
   ↓
Verify token/session
   ↓
Identify user
   ↓
req.user
```

For example:

```js
req.user = {
    id: "42",
    role: "user"
};
```

Then later:

```text
Controller
   ↓
Service
   ↓
Logger
```

can use:

```js
req.user.id
```

or whatever user context your application attaches to the request.

---

# 5. Example

Suppose:

```http
POST /api/v1/todos
```

comes from:

```text
userId=42
```

The service creates the Todo.

You could produce:

```json
{
  "level": "info",
  "event": "todo.created",
  "userId": "42",
  "todoId": "todo_123"
}
```

Now you can search logs for:

```text
userId=42
```

and investigate that user's activity.

---

# 6. User Context + Request ID

This becomes even more useful when combined with the request ID from earlier lessons.

You might have:

```json
{
  "level": "error",
  "event": "todo.create.failed",
  "requestId": "req_abc123",
  "userId": "42"
}
```

Now you have two powerful identifiers:

```text
requestId
   ↓
Which request?

userId
   ↓
Which user?
```

This gives you two different ways to investigate an incident.

---

# 7. Request ID and User ID Are Not the Same

Don't confuse them.

### Request ID

Identifies:

```text
ONE REQUEST
```

Example:

```text
req_abc123
```

### User ID

Identifies:

```text
ONE USER
```

Example:

```text
user_42
```

A user can generate many requests:

```text
user_42
   ├── req_001
   ├── req_002
   ├── req_003
   └── req_004
```

So:

```text
requestId → request-level context
userId    → user-level context
```

---

# 8. Example: One User, Multiple Requests

Suppose User 42 does:

```text
GET /todos
POST /todos
PATCH /todos/123
DELETE /todos/123
```

Logs might look like:

```text
INFO todo.list.completed
userId=42
requestId=req_001

INFO todo.created
userId=42
requestId=req_002

INFO todo.updated
userId=42
requestId=req_003

INFO todo.deleted
userId=42
requestId=req_004
```

Now you can search:

```text
userId=42
```

to understand activity associated with that user.

---

# 9. User Context Is Especially Useful for Errors

Imagine your production logs contain:

```text
ERROR todo.create.failed
```

You investigate and discover:

```text
userId=42
```

Then you can search:

```text
requestId=req_abc123
```

and find:

```text
request.received
authentication.success
todo.create.started
repository.create.started
database.query.failed
todo.create.failed
```

This creates a much clearer picture.

---

# 10. User Context in Authorization

This is another very important use case.

Suppose:

```text
User A → tries to access User B's Todo
```

Authorization rejects it:

```text
403 Forbidden
```

You might record:

```json
{
  "level": "warn",
  "event": "authorization.denied",
  "userId": "42",
  "resource": "todo",
  "resourceId": "todo_123"
}
```

This tells you:

```text
Who attempted the action?
What resource?
Which resource?
```

That can be valuable for security investigations.

---

# 11. User Context in Authentication

Suppose a logged-in user tries to refresh a token and it fails.

You might have:

```text
WARN token.refresh.failed
userId=42
requestId=req_456
```

But be careful:

```text
userId=42
```

may be useful.

This is **not** a reason to log:

```text
refreshToken=eyJ...
```

Never confuse user context with credential logging.

---

# 12. Login Is a Special Case

Here's an interesting situation.

Suppose login fails because the user entered the wrong password.

At that point, you may not have an authenticated user yet.

So:

```text
req.user
```

might not exist.

You may have:

```text
userId = undefined
```

That's okay.

You can still log:

```text
WARN user.login.failed
requestId=req_123
reason=invalid_credentials
```

without inventing a user ID.

---

# 13. Don't Guess the User

Never do something like:

```js
const userId = req.user?.id || "unknown";
```

and then treat `"unknown"` as a real user.

It's okay to represent missing context:

```text
userId: null
```

or omit the field according to your logging format.

The important thing is:

> **Never fabricate context.**

---

# 14. Anonymous Requests

Not every endpoint requires authentication.

For example:

```text
GET /api/v1/health
```

might be public.

There is no user:

```text
userId = null
```

That's completely normal.

Your logs could be:

```json
{
  "level": "info",
  "event": "health.check.completed",
  "requestId": "req_123"
}
```

No `userId` is necessary.

---

# 15. System Actions Are Different

Not every operation is performed by a human user.

For example:

```text
Cron job
Background worker
Queue consumer
Scheduled cleanup
System migration
```

A background worker might create a record.

There may be:

```text
userId = null
```

Instead, you might have:

```text
actorType=system
```

or:

```text
jobName=cleanupExpiredSessions
```

Conceptually:

```json
{
  "event": "session.cleanup.completed",
  "actorType": "system",
  "jobName": "cleanupExpiredSessions"
}
```

This is more meaningful than pretending a user performed the action.

---

# 16. Actor vs User

This leads to a useful concept:

> **Who caused the event?**

That person or system is the **actor**.

The actor could be:

```text
USER
ADMIN
SYSTEM
WORKER
SERVICE
```

For example:

```text
userId=42
actorType=user
```

or:

```text
actorType=system
jobName=cleanup
```

You don't always need an elaborate actor model, but the concept is useful when designing production logging.

---

# 17. Admin Actions

Suppose an administrator deletes a user's account.

You might want stronger context:

```json
{
  "level": "info",
  "event": "user.deleted",
  "actorUserId": "admin_7",
  "targetUserId": "user_42"
}
```

This is different from:

```text
userId=42
```

because there are **two users**:

```text
Actor
  ↓
admin_7

Target
  ↓
user_42
```

This distinction becomes very important for auditing.

---

# 18. Don't Put Sensitive User Information in Every Log

Suppose your user has:

```text
name
email
phone
address
password
```

You probably don't want:

```json
{
  "user": {
    "name": "...",
    "email": "...",
    "phone": "...",
    "address": "..."
  }
}
```

in every log event.

That's excessive.

Instead:

```json
{
  "userId": "42"
}
```

may be enough.

Then, if you genuinely need more information for a particular audit or business requirement, add only what is justified.

---

# 19. Why This Matters for Privacy

Logs can live for a long time.

They may be:

```text
Stored
Backed up
Copied
Sent to log management systems
Accessible by developers
Used for debugging
```

So if you put unnecessary personal data into logs, you're creating another place where that data exists.

Think:

```text
Application DB
      +
Logs
      +
Backups
      +
Monitoring system
```

The more places data exists, the greater the security and privacy responsibility.

---

# 20. User Context Should Be Intentional

Before adding a user field, ask:

> **Why do I need this information?**

Good reason:

```text
I need to identify which user's request failed.
```

Potentially unnecessary:

```text
I'll just log the entire user object.
```

Don't do the second one.

---

# 21. Never Log the Entire `req.user`

This is a common beginner shortcut:

```js
logger.info({
    user: req.user
});
```

It may look convenient.

But imagine `req.user` contains:

```js
{
    id: "42",
    email: "user@example.com",
    role: "admin",
    passwordHash: "...",
    refreshToken: "...",
    ...
}
```

Now you've potentially leaked sensitive information into your logs.

Instead, select exactly what you need:

```js
logger.info({
    userId: req.user.id
});
```

This is much safer.

---

# 22. User Context Middleware

Later, we can centralize logging context.

Conceptually:

```text
Request
   ↓
Request ID middleware
   ↓
Authentication
   ↓
User context
   ↓
Logger
```

Then your logger can consistently know:

```text
requestId
userId
```

without every developer manually constructing these fields.

This reduces mistakes.

---

# 23. Example: Request Lifecycle

Imagine:

```http
POST /api/v1/todos
```

User:

```text
userId=42
```

Request:

```text
requestId=req_abc
```

Logs:

```text
INFO request.received
requestId=req_abc
userId=42
```

Then:

```text
DEBUG todo.create.started
requestId=req_abc
userId=42
```

Success:

```text
INFO todo.created
requestId=req_abc
userId=42
todoId=todo_123
```

Completed:

```text
INFO request.completed
requestId=req_abc
userId=42
statusCode=201
```

This is excellent context.

---

# 24. What If the Request Fails?

Suppose:

```text
database query
     ↓
failure
```

You might have:

```text
ERROR todo.create.failed
requestId=req_abc
userId=42
```

Then:

```text
500
```

is returned.

The client receives a safe response:

```json
{
  "success": false,
  "message": "Something went wrong",
  "requestId": "req_abc"
}
```

Now the user can give support:

```text
"My request ID is req_abc."
```

And you can find:

```text
userId=42
```

and the entire request trail.

---

# 25. What About Multiple Users?

Imagine a group operation:

```text
Admin updates 50 users.
```

Don't force:

```text
userId=???
```

to represent everything.

Instead, depending on your architecture:

```text
actorUserId=admin_7
affectedCount=50
```

or an audit event that records the appropriate target information.

The concept is:

```text
Who performed it?
Who/what was affected?
```

---

# 26. User Context vs Audit Logs

This is an important distinction.

### Application logs

Help you understand:

```text
What happened inside the application?
```

### Audit logs

Help answer:

```text
Who performed an important action?
What did they do?
What resource was affected?
When?
```

For example:

```text
Application log:
ERROR database.query.failed
```

Audit event:

```text
ADMIN deleted USER
actorUserId=admin_7
targetUserId=user_42
```

We'll study audit logging more deeply later in Phase 19.

---

# 27. A Practical Field Design

For many authenticated backend events, a useful baseline might be:

```text
requestId
userId
event
level
timestamp
```

For HTTP events:

```text
method
path
statusCode
duration
```

For errors:

```text
error.name
error.message
stack
```

But remember:

> **Only include fields that are actually useful and safe.**

---

# 28. Example of Good Structured Context

```json
{
  "timestamp": "2026-08-26T10:30:00Z",
  "level": "error",
  "event": "todo.create.failed",
  "requestId": "req_abc123",
  "userId": "42",
  "method": "POST",
  "path": "/api/v1/todos",
  "statusCode": 500,
  "error": {
    "name": "MongoServerError"
  }
}
```

This gives you:

```text
When?       timestamp
Severity?   error
What?       todo.create.failed
Which req?  req_abc123
Which user? 42
Endpoint?   POST /api/v1/todos
Result?     500
Failure?    MongoServerError
```

That's strong operational context.

---

# 29. Common Mistakes

### Mistake 1

Logging the entire user:

```js
logger.info({ user: req.user });
```

❌ Avoid.

---

### Mistake 2

Logging passwords:

```js
logger.debug({ password });
```

❌ Never.

---

### Mistake 3

Logging tokens:

```js
logger.debug({ token });
```

❌ Never.

---

### Mistake 4

Assuming every request has a user:

```js
const userId = req.user.id;
```

❌ Can crash on public routes.

Use appropriate optional handling or centralized context.

---

### Mistake 5

Using email as the primary identifier everywhere.

```text
email=user@example.com
```

A stable internal ID is often a better correlation field:

```text
userId=42
```

Whether you need both depends on the specific use case.

---

# 30. Mini Exercise

Suppose you have:

```js
req.user = {
    id: "42",
    email: "rahul@example.com",
    role: "admin",
    passwordHash: "...",
    refreshToken: "..."
};
```

Which would you prefer?

### A

```js
logger.info({
    user: req.user
});
```

### B

```js
logger.info({
    userId: req.user.id
});
```

### C

```js
logger.info({
    passwordHash: req.user.passwordHash,
    refreshToken: req.user.refreshToken
});
```

Correct answer:

**B.**

Because you're logging the minimum useful identity context.

# 34. Final Mental Model

Think of your backend log context like this:

```text
                    LOG EVENT
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   requestId        userId         event
        │              │              │
   Which request?  Which user?   What happened?
```

For administrative operations:

```text
                 ACTION
                   │
          ┌────────┴────────┐
          ▼                 ▼
     actorUserId       targetUserId
          │                 │
     Who did it?       Who was affected?
```

And always remember:

```text
Useful context
      +
Minimum necessary data
      +
No secrets
```

---

## ⭐ Key Takeaway

**User context helps you answer "who was involved?" without dumping the user's private data into your logs.**

For most authenticated application logs, start with:

```text
requestId
userId
event
```

and add other context only when there's a real reason.
