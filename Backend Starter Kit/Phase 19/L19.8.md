# Lesson 19.8 — Sensitive Data in Logs

This is one of the **most important security lessons** in Phase 19.

A backend can be perfectly secure in its API responses and database, but still have a serious vulnerability because it writes secrets into logs.

The core rule is:

> **Logs are data. Protect them like you protect your database.**

---

# 1. Why Logging Sensitive Data Is Dangerous

Imagine your login endpoint receives:

```json
{
  "email": "rahul@example.com",
  "password": "MySecretPassword"
}
```

And someone writes:

```js
logger.info({
    event: "login.request",
    body: req.body
});
```

Your log now contains:

```text
email=rahul@example.com
password=MySecretPassword
```

That's a security problem.

Why?

Because logs can be:

```text
Application
    ↓
Log file
    ↓
Log collector
    ↓
Cloud storage
    ↓
Backups
    ↓
Monitoring dashboard
```

You've now created multiple places where the password exists.

---

# 2. The Most Important Things You Should Never Log

As a strong default, **never log secrets such as:**

```text
❌ Passwords
❌ Password hashes
❌ Access tokens
❌ Refresh tokens
❌ JWTs
❌ API keys
❌ Database passwords
❌ Encryption keys
❌ Session secrets
❌ Private keys
❌ Authorization headers
❌ Full cookies
```

For example, don't do:

```js
logger.debug({
    password: req.body.password
});
```

Never.

---

# 3. Passwords Are Especially Dangerous

Imagine:

```js
const { email, password } = req.body;
```

Never do:

```js
logger.info({
    email,
    password
});
```

Even in development.

Because developers frequently copy development logging patterns into production.

A better log:

```js
logger.info({
    event: "auth.login.attempt",
    email
});
```

Even then, consider whether you actually need the email in logs.

Often:

```js
logger.info({
    event: "auth.login.attempt"
});
```

may be enough.

---

# 4. Password Hashes Are Also Sensitive

You might think:

> "I'm not logging the password. I'm logging the hash."

Still dangerous.

Don't do:

```js
logger.debug({
    passwordHash: user.password
});
```

Password hashes are security-sensitive authentication data.

If attackers obtain them, they may attempt offline password cracking.

So:

```text
password
passwordHash
```

should both be treated as sensitive.

---

# 5. JWTs Should Never Be Logged

Suppose:

```http
Authorization: Bearer eyJhbGciOi...
```

Don't log:

```js
logger.info({
    authorization: req.headers.authorization
});
```

That could expose an access token.

If an attacker gets a still-valid token, they may be able to impersonate the user.

Instead, you might log:

```json
{
  "event": "auth.request.authenticated",
  "userId": "42"
}
```

You need the **identity**, not the credential.

---

# 6. Refresh Tokens Are Even More Dangerous

Don't log:

```text
refreshToken=...
```

Not even:

```text
DEBUG refresh token received
```

if the actual token is included.

If you need to identify a token/session during debugging, use a safe identifier.

For example:

```text
sessionId
tokenId
```

depending on your architecture.

The principle:

```text
Credential → NEVER log
Identifier  → MAY be logged
```

---

# 7. Authorization Headers

This is a very common accidental leak.

Don't do:

```js
logger.info({
    headers: req.headers
});
```

because headers can contain:

```text
authorization
cookie
x-api-key
```

For example:

```http
Authorization: Bearer eyJ...
```

could end up in your logs.

If you need request headers for debugging, explicitly select safe fields.

For example:

```js
logger.debug({
    contentType: req.headers["content-type"]
});
```

instead of dumping everything.

---

# 8. Cookies

Cookies can contain:

```text
session identifiers
authentication tokens
refresh tokens
tracking information
```

So this is dangerous:

```js
logger.debug({
    cookies: req.cookies
});
```

Don't blindly log cookies.

---

# 9. API Keys

Suppose your backend calls an external service:

```text
X-API-Key: sk_live_...
```

Don't log:

```js
logger.debug({
    apiKey
});
```

And don't log:

```js
logger.debug({
    requestHeaders
});
```

if those headers contain the API key.

Instead:

```text
external_service.request.started
service=payment
```

is usually enough.

---

# 10. Database Connection Strings

This is another major one.

Your environment might contain:

```text
DATABASE_URL=mongodb+srv://user:password@cluster...
```

Never log:

```js
logger.info({
    databaseUrl: process.env.DATABASE_URL
});
```

You could expose:

```text
username
password
hostname
database
credentials
```

Instead:

```js
logger.info({
    event: "database.connected",
    database: "application"
});
```

or another safe identifier.

---

# 11. Environment Variables

Be careful with:

```js
console.log(process.env);
```

This is extremely dangerous.

Environment variables frequently contain:

```text
JWT_SECRET
DATABASE_URL
API_KEY
SMTP_PASSWORD
AWS_SECRET
ENCRYPTION_KEY
```

A single log statement could expose your entire application's secrets.

Never dump the complete environment in production.

---

# 12. Request Bodies

Request bodies are another major source of accidental data leaks.

Consider:

```js
logger.debug({
    body: req.body
});
```

This looks harmless.

But your endpoint could receive:

```json
{
  "email": "rahul@example.com",
  "password": "secret",
  "phone": "...",
  "address": "...",
  "creditCard": "..."
}
```

Now everything gets logged.

Instead, log only the fields that are useful.

For example:

```js
logger.debug({
    event: "todo.create.started",
    titleLength: req.body.title?.length
});
```

Or simply:

```js
logger.debug({
    event: "todo.create.started"
});
```

---

# 13. PII — Personally Identifiable Information

Another category is **PII**.

Examples can include:

```text
Name
Email address
Phone number
Home address
Government identifiers
```

Whether a particular piece of information is appropriate to log depends on your application, legal requirements, and purpose.

The safe engineering mindset is:

> **Don't log personal information just because you can.**

Ask:

```text
Do I actually need this?
```

---

# 14. PII Is Not the Same as a Secret

This distinction is useful.

### Secret

Something that can directly provide access or security capability.

Examples:

```text
Password
JWT
API key
Private key
Refresh token
```

### PII

Information that identifies or describes a person.

Examples:

```text
Email
Phone
Address
Name
```

Both require care, but for different reasons.

---

# 15. A Useful Data Classification

You can mentally divide data into:

```text
PUBLIC
   ↓
INTERNAL
   ↓
PERSONAL
   ↓
SENSITIVE
   ↓
SECRET
```

The exact classification system depends on the organization.

But for your backend, you can start with:

```text
Safe operational metadata
        ↓
User context
        ↓
Personal data
        ↓
Secrets
```

As sensitivity increases, logging should become more restricted.

---

# 16. The Golden Rule for Request Logging

Never start with:

```js
logger.info({
    req
});
```

or:

```js
logger.info({
    body: req.body,
    headers: req.headers,
    cookies: req.cookies
});
```

Instead, define exactly what your logger needs.

For example:

```js
logger.info({
    event: "request.completed",
    requestId: req.id,
    method: req.method,
    path: req.originalUrl,
    statusCode: res.statusCode
});
```

That's much safer.

---

# 17. Logging an Error Object Can Also Be Dangerous

Earlier we discussed:

```js
logger.error({
    error
});
```

This can be useful.

But you shouldn't assume every error object is safe.

Imagine an error contains:

```text
connection string
request headers
API response
user information
```

If you serialize everything blindly, you may leak sensitive data.

So production logging should use **controlled error serialization** and redaction.

We'll see how Pino helps with this later.

---

# 18. Redaction

One of the most important concepts in secure logging is:

> **Redaction**

Redaction means replacing sensitive information before it reaches the logs.

For example:

```text
password=MySecret123
```

becomes:

```text
password=[REDACTED]
```

Or:

```text
authorization=Bearer eyJ...
```

becomes:

```text
authorization=[REDACTED]
```

---

# 19. Example

Input:

```json
{
  "email": "rahul@example.com",
  "password": "secret123",
  "accessToken": "eyJ...",
  "role": "user"
}
```

After redaction:

```json
{
  "email": "rahul@example.com",
  "password": "[REDACTED]",
  "accessToken": "[REDACTED]",
  "role": "user"
}
```

But remember:

> **Redaction is a safety mechanism, not an excuse to log everything.**

It's still better to avoid unnecessary data entirely.

---

# 20. Redaction vs Not Logging

Which is better?

### Option A

Don't log:

```text
password
```

### Option B

Log:

```text
password=[REDACTED]
```

**Option A is generally better.**

Why?

Because the safest secret is the one that never enters the logging pipeline.

Redaction is your second line of defense.

---

# 21. Defense in Depth

A strong logging security strategy looks like:

```text
                Application
                     │
                     ▼
          Don't log unnecessary data
                     │
                     ▼
              Redaction rules
                     │
                     ▼
             Secure transport
                     │
                     ▼
             Access controls
                     │
                     ▼
               Log storage
                     │
                     ▼
              Retention policy
```

Security shouldn't depend on only one layer.

---

# 22. Example: Authentication Logging

Bad:

```js
logger.info({
    event: "login",
    email: req.body.email,
    password: req.body.password,
    authorization: req.headers.authorization
});
```

This is a security disaster.

Better:

```js
logger.info({
    event: "auth.login.attempt"
});
```

On success:

```js
logger.info({
    event: "auth.login.success",
    userId: user.id
});
```

On failure:

```js
logger.warn({
    event: "auth.login.failed",
    reason: "invalid_credentials"
});
```

Much better.

---

# 23. Example: Todo API

Suppose:

```http
POST /api/v1/todos
```

Request:

```json
{
  "title": "Learn logging",
  "description": "Study secure logging"
}
```

You don't necessarily need:

```js
logger.debug({
    body: req.body
});
```

Instead:

```js
logger.debug({
    event: "todo.create.started"
});
```

If the Todo is created:

```js
logger.info({
    event: "todo.created",
    userId: req.user.id,
    todoId: todo.id
});
```

Now the log contains useful context without unnecessary request data.

---

# 24. Example: Payment API

Imagine:

```json
{
  "cardNumber": "4111111111111111",
  "cvv": "123",
  "amount": 500
}
```

Never do:

```js
logger.info({
    paymentRequest: req.body
});
```

Even if you're debugging.

Instead:

```js
logger.info({
    event: "payment.started",
    amount: 500
});
```

And ideally use payment-provider tokens or safe identifiers rather than card credentials.

---

# 25. Example: File Upload

Suppose users upload:

```text
profile.jpg
```

You might log:

```text
INFO file.upload.completed
userId=42
fileType=image/jpeg
fileSize=245KB
```

That's useful.

You don't need:

```text
entire file content
```

inside the logs.

Obviously.

But the same principle applies to any large or sensitive payload:

> **Log metadata, not the entire payload.**

---

# 26. Don't Log Secrets During Debugging

This deserves special emphasis.

A developer might think:

> "It's okay because I'm only debugging locally."

Be careful.

Local logs can end up in:

```text
terminal history
log files
screenshots
GitHub issues
screen recordings
shared debugging sessions
```

So the rule should be:

> **Never create a habit of logging secrets.**

Development code often becomes production code.

---

# 27. Git Is Another Risk

Suppose you accidentally write:

```js
logger.debug({
    jwtSecret: process.env.JWT_SECRET
});
```

and commit the code.

Even after removing it later, the secret may have existed in Git history.

This is why secrets should never be casually printed.

---

# 28. What About Emails?

Email addresses aren't authentication secrets.

But they can still be personal information.

Instead of automatically logging:

```text
email=rahul@example.com
```

consider whether you need it.

If your support workflow genuinely needs it, you might use controlled logging or masking according to your policy.

For example:

```text
r***@example.com
```

But don't invent a masking strategy without understanding your operational requirements.

---

# 29. What About IP Addresses?

IP addresses are another example where context matters.

They can be useful for:

```text
security monitoring
rate limiting investigation
abuse detection
```

But they're also potentially sensitive data depending on the context and applicable privacy rules.

So don't automatically log everything available from:

```js
req.ip
```

just because it's easy.

Ask:

> Why do we need this?

---

# 30. What About User Agents?

A User-Agent may be useful for:

```text
browser debugging
device compatibility
security investigation
```

But again:

```text
Useful ≠ always necessary
```

Log it when it serves a real operational purpose.

---

# 31. What About Database Queries?

Be careful here too.

You might want:

```text
DEBUG database.query.started
```

but don't necessarily log:

```text
full SQL query
full MongoDB query
sensitive query parameters
```

For example, a query might contain:

```text
email
phone
internal identifiers
tokens
```

Use structured metadata and carefully control query logging.

---

# 32. Sensitive Data Can Hide in URLs

This is a surprisingly common problem.

Suppose someone designs:

```text
GET /reset-password?token=abc123
```

and your request logger records:

```text
GET /reset-password?token=abc123
```

Congratulations — you've logged a password reset token.

This is why URL/query-string logging must also be considered carefully.

Prefer:

```text
/reset-password
```

or sanitize sensitive query parameters.

Better still, sensitive credentials generally shouldn't be placed in URLs in the first place.

---

# 33. Headers Can Hide Secrets

Potentially sensitive headers include:

```text
Authorization
Cookie
X-API-Key
```

So this:

```js
logger.info({
    headers: req.headers
});
```

is dangerous.

A safer strategy is explicit selection:

```js
logger.info({
    contentType: req.headers["content-type"],
    userAgent: req.headers["user-agent"]
});
```

Only if those fields are useful for your application.

---

# 34. A Safe Request Log

A reasonable request log could look like:

```json
{
  "level": "info",
  "event": "request.completed",
  "requestId": "req_123",
  "method": "POST",
  "path": "/api/v1/todos",
  "statusCode": 201,
  "duration": 48,
  "userId": "42"
}
```

Notice:

```text
✓ request ID
✓ route
✓ method
✓ status
✓ duration
✓ user ID
```

And:

```text
✗ password
✗ token
✗ cookies
✗ authorization header
✗ full body
```

This is a good production mindset.

---

# 35. What Should You Log Instead?

Instead of logging sensitive **values**, log safe **metadata**.

### Bad

```text
token=eyJ...
```

### Better

```text
authentication=success
```

---

### Bad

```text
password=secret
```

### Better

```text
authentication=attempt
```

---

### Bad

```text
creditCard=411111...
```

### Better

```text
payment.provider_request_id=pay_123
```

---

### Bad

```text
entire request body
```

### Better

```text
resource=todo
operation=create
```

This is a powerful pattern:

> **Log what happened, not the secrets that made it happen.**

# 37. A Security Checklist

Before shipping your logger, ask:

```text
[ ] Are passwords excluded?
[ ] Are password hashes excluded?
[ ] Are access tokens excluded?
[ ] Are refresh tokens excluded?
[ ] Are API keys excluded?
[ ] Are secrets excluded?
[ ] Are authorization headers excluded?
[ ] Are cookies excluded?
[ ] Are sensitive query parameters excluded?
[ ] Are request bodies avoided or filtered?
[ ] Are error objects safely serialized?
[ ] Is unnecessary PII avoided?
[ ] Are redaction rules configured?
```

This checklist will save you from many production mistakes.

---

# 38. The Most Important Architecture Rule

Think about your logging system like this:

```text
                  Application
                       │
                       ▼
                Logging Layer
                       │
              ┌────────┴────────┐
              │                 │
         Useful context      Secrets
              │                 │
              ▼                 ▼
             KEEP            REMOVE
                                │
                                ▼
                           REDACT/DROP
```

Your logging layer should be designed to prevent accidental leaks.

Don't rely on every developer remembering every sensitive field.

---

# 39. Why Centralized Logging Helps

Suppose you have:

```text
Controller A
Controller B
Controller C
Service A
Service B
Repository A
```

If every developer manually decides:

```js
console.log(...)
```

you'll eventually get inconsistent and unsafe logs.

A centralized logger gives you one place to enforce:

```text
format
levels
request IDs
redaction
serialization
environment configuration
```

This is one reason we're moving toward **Pino** later in Phase 19.

# 41. Defense in Depth Again

A strong production setup can have:

```text
Layer 1
Don't log sensitive data
        ↓
Layer 2
Logger redaction
        ↓
Layer 3
Access-controlled log storage
        ↓
Layer 4

        ↓

```

If one layer fails, other layers still provide protection.

---

# 42. The Three Questions You Should Ask

Before logging a field:

### Question 1

> **Do I need it?**

If no:

```text
Don't log it.
```

### Question 2

> **Is it sensitive?**

If yes:

```text
Don't log it, or apply carefully designed redaction.
```

### Question 3

> **Could it contain secrets unexpectedly?**

If yes:

```text
Don't dump it blindly.
```

This simple process will prevent many mistakes.
