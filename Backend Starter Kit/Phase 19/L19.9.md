# Lesson 19.9 — Pino Logger

Now we move from **logging theory to a real Node.js logger**.

Your roadmap explicitly defines **19.9 as Pino**, after learning log levels, request IDs, request logging, error logging, user context, and sensitive-data protection.

The important thing is that we're **not starting with Pino syntax**. First understand **why Pino exists**.

---

# 1. The Problem With `console.log()`

You've probably written:

```js
console.log("User created");
```

This works.

But as your application grows:

```text
console.log()
console.error()
console.warn()
```

everywhere becomes difficult to manage.

Imagine production logs like:

```text
Server started
User created
Todo created
Database failed
Request failed
User logged in
Something went wrong
```

Problems:

```text
❌ No consistent structure
❌ Difficult to search
❌ Difficult to filter
❌ Difficult to analyze automatically
❌ Hard to attach requestId/userId
❌ Hard to redact sensitive fields
❌ Hard to configure production behavior
```

This is where a logging library becomes useful.

---

# 2. What Is Pino?

**Pino is a fast structured logger for Node.js.**

Instead of:

```js
console.log("Todo created");
```

you can write:

```js
logger.info({
    event: "todo.created",
    todoId: todo.id
});
```

And Pino produces structured output.

Conceptually:

```json
{
  "level": 30,
  "time": 1756200000000,
  "event": "todo.created",
  "todoId": "123"
}
```

Now the log is machine-readable.

---

# 3. Pino's Main Job

Think of Pino as:

```text
Your application
       ↓
      Pino
       ↓
Structured logs
       ↓
Log storage / monitoring
```

Your application doesn't need to worry about manually formatting every log line.

---

# 4. Why Pino?

Your roadmap specifically includes Pino because we're now moving toward production logging.

The important advantages are:

```text
Pino
 ├── Structured logging
 ├── Log levels
 ├── JSON output
 ├── Good performance
 ├── Child loggers
 ├── Error serialization
 └── Redaction support
```

We'll learn each of these gradually.

# 7. Basic Pino Logger

With ES modules:

```js
import pino from "pino";

const logger = pino();

export default logger;
```

That's enough to create a basic Pino logger.

Now another file can use:

```js
import logger from "./utils/logger.js";

logger.info("Server started");
```



At first this may look ugly.

But notice something important:

```json
{

  "pid": 12345,
  "hostname": "linux",
  "msg": "Server started"

```

This is **structured data**.

# 9. Why JSON?

Because machines love structured data.

Imagine you have:

```text
100,000 logs
```

A monitoring system can easily search:

```text
level = error
```

or:

```text
event = todo.created
```

or:

```text
userId = 42
```

This is much harder with random text.

---

# 10. Pino Is Not Just `console.log()` With Better Formatting

This distinction matters.

You might think:

```text
console.log()
      ↓
Pino
```

is simply:

> "Pino prints nicer logs."

Not really.

Pino gives you a **logging system**.

You can build consistent structured events:

```js
logger.info({
    event: "todo.created",
    userId: "42",
    todoId: "123"
});
```

The application is producing **structured operational data**.

---

# 11. Structured Logging With Pino

Compare:

### Console

```js
console.log(
    "Todo created by user 42 with id 123"
);
```

### Pino

```js
logger.info({
    event: "todo.created",
    userId: "42",
    todoId: "123"
});
```

The second one is much easier to process.

A machine can directly understand:

```text
event
userId
todoId
```

without parsing English text.

# 14. Pino Supports Structured Fields

You can attach arbitrary structured data:

```js
logger.info({
    event: "todo.created",
    userId: "42",
    todoId: "todo_123",
    duration: 35
});
```

Conceptually:

```json
{
  "level": 30,
  "event": "todo.created",
  "userId": "42",
  "todoId": "todo_123",
  "duration": 35
}
```

This is exactly what we learned in the previous lessons.

---

# 15. Don't Put Everything Into `msg`

A beginner might do:

```js
logger.info(
    `Todo ${todo.id} created by user ${user.id} in ${duration}ms`
);
```

It works.

But now a monitoring system has to parse the text.

Instead:

```js
logger.info({
    event: "todo.created",
    todoId: todo.id,
    userId: user.id,
    duration
});
```

Now every value has its own field.

---

# 16. A Better Logger Configuration

We can configure Pino:

```js
import pino from "pino";

const logger = pino({
    level: "info"
});

export default logger;
```

This means:

```text
info
warn
error
fatal
```

are generally emitted, while lower-priority logs such as `debug` are filtered out.

---

# 17. Why Log-Level Filtering Matters

Imagine your application produces:

```text
1000 debug logs
100 info logs
10 warn logs
2 error logs
```

In production you might not want all the debug information.

So:

```text
Development
    ↓
debug
info
warn
error

Production
    ↓
info
warn
error
```

This reduces noise and logging overhead.

---

# 18. Environment-Based Logging

A useful configuration is:

```js
const logger = pino({
    level: process.env.LOG_LEVEL || "info"
});
```

Then:

```env
LOG_LEVEL=debug
```

during development.

And:

```env
LOG_LEVEL=info
```

in production.

Now you can control logging without changing application code.

---

# 19. Don't Hard-Code Production Behavior

Avoid:

```js
const logger = pino({
    level: "debug"
});
```

and then forgetting about it.

Instead:

```js
level: process.env.LOG_LEVEL || "info"
```

This makes the logger configurable.

---

# 20. Pino and Errors

Pino can log errors in a structured way.

For example:

```js
try {
    await createTodo();
} catch (error) {
    logger.error(error);
}
```

But for your architecture, we usually want context too.

For example:

```js
logger.error({
    event: "todo.create.failed",
    requestId,
    userId,
    err: error
});
```

Now you have:

```text
What happened?
      +
Which request?
      +
Which user?
      +
What error?
```

---

# 21. Why `err` Matters

Pino has special handling for error objects when using the expected error field.

For example:

```js
logger.error({
    err: error,
    event: "todo.create.failed"
});
```

This lets the logger serialize useful error information such as:

```text
name
message
stack
```

without you manually doing:

```js
error.message
error.stack
error.name
```

every time.

---

# 22. Don't Do This

Avoid:

```js
logger.error({
    error: JSON.stringify(error)
});
```

Why?

You can lose useful error structure.

Instead, use the error object directly through Pino's error serialization support:

```js
logger.error({
    err: error
});
```

This becomes especially useful for unexpected errors.

---

# 23. Pino Child Loggers

One powerful Pino feature is the **child logger**.

Suppose you have:

```text
requestId=req_123
userId=42
```

You don't want to repeatedly write:

```js
logger.info({
    requestId: "req_123",
    userId: "42",
    event: "..."
});
```

for every event.

A child logger lets you attach context.

Conceptually:

```js
const requestLogger = logger.child({
    requestId: "req_123",
    userId: "42"
});
```

Then:

```js
requestLogger.info({
    event: "todo.create.started"
});
```

and:

```js
requestLogger.info({
    event: "todo.created"
});
```

Both logs inherit:

```text
requestId
userId
```

---

# 24. Why Child Loggers Are Powerful

Think:

```text
Global Logger
     │
     ├── requestId
     └── userId
          │
          ▼
     Child Logger
          │
     ┌────┼────┐
     ▼    ▼    ▼
   log1  log2  log3
```

This is perfect for request-scoped logging.

We'll eventually connect this with your request ID middleware.

# 30. Don't Mix Formatting With Logging Logic

A useful architecture is:

```text
Application
     ↓
Pino
     ↓
Structured event
     ↓
Formatter / transport
     ↓
Terminal / log system
```

Your application should primarily care about:

```js

    event: "todo.created"

```

not:


# 31. Pino and Redaction

You learned in **19.8** that secrets should not enter logs.

Pino can also help with **redaction**.

Conceptually:

```js
const logger = pino({
    redact: [
        "req.headers.authorization",
        "req.headers.cookie"
    ]
});
```

Then if something tries to log those fields, Pino can redact them.

The exact configuration will become more important when we build request logging.

The important idea for today is:

```text
Application
    ↓
Pino
    ↓
Redaction
    ↓
Logs
```

This is another reason to use a centralized logger.

---

# 32. Pino Doesn't Make Unsafe Logging Safe

This is extremely important.

Installing Pino does **not** mean:

> "Now I can log anything."

This is still dangerous:

```js
logger.info({
    password: req.body.password
});
```

Pino is a logging tool.

It doesn't magically know what information your application should never log.

Your first defense is still:

```text
Don't log secrets.
```

Redaction is the backup.

# 35. Example: Service Logging

Imagine:

```js
export async function createTodo(data) {
    logger.debug({
        event: "todo.create.started"
    });

    const todo = await repository.create(data);

    logger.info({
        event: "todo.created",
        todoId: todo.id
    });

    return todo;
}
```

Now your service produces meaningful events.

But don't over-log every line of code.

You don't need:

```js
logger.debug("entered function");
logger.debug("variable created");
logger.debug("if condition passed");
logger.debug("returning");
```

That's noise.

Log **meaningful application events**.

These describe meaningful application events.

# ⭐ Key Takeaway

Pino is not simply:

> **"A replacement for `console.log()`."**

Think of it as:

> **A centralized, structured logging system for your Node.js application.**

Your basic implementation is:

```js
import pino from "pino";

const logger = pino({
    level: process.env.LOG_LEVEL || "info"
});

export default logger;
```

And your application events should look like:

```js
logger.info({
    event: "todo.created",
    userId: "42",
    todoId: "todo_123"
});
```

while errors should look like:

```js
logger.error({
    event: "todo.create.failed",
    requestId: "req_123",
    userId: "42",
    err: error
});
```

The architecture is now:

```text
console.log()
     ↓
   Pino
     ↓
structured events
     ↓
request/user context
     ↓
redaction
     ↓
production logging
```

That progression is exactly what we're building through Phase 19.
