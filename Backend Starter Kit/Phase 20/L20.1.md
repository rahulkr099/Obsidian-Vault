# Lesson 20.1 — Why Email Belongs Outside Controllers

This is the first lesson of Phase 20, and it is an **architecture lesson**.

Before we learn SMTP, Nodemailer, templates, queues, or workers, we need to understand one simple question:

> **Why shouldn't my controller directly send emails?**

---

## 1. First, remember what a controller does

From Phase 11, our mental model is:

```text
HTTP Request
     ↓
   Route
     ↓
 Middleware
     ↓
 Controller
     ↓
 HTTP Response
```

A controller is mainly responsible for translating between:

```text
HTTP world
    ↕
Application world
```

For example:

```js
export const getProfile = async (req, res) => {
    const user = await userService.getProfile(req.user.id);

    res.status(200).json({
        success: true,
        data: user
    });
};
```

The controller:

1. reads the request
    
2. calls the appropriate application logic
    
3. chooses the HTTP status
    
4. sends the HTTP response
    

That's its job.

---

# 2. The beginner approach to email

Imagine we're building signup.

A beginner might write:

```js
export const signup = async (req, res) => {
    const user = await userService.signup(req.body);

    await sendEmail({
        to: user.email,
        subject: "Welcome!",
        html: "<h1>Welcome to our application</h1>"
    });

    res.status(201).json({
        success: true,
        data: user
    });
};
```

At first glance, this looks perfectly fine.

But look carefully.

The controller is now responsible for:

```text
HTTP
 │
 ├── User signup
 │
 ├── Email decision
 │
 ├── Email content
 │
 ├── Email provider
 │
 └── Email failure
```

That's too much responsibility.

---

# 3. The controller becomes "fat"

We call this a **fat controller**.

For example:

```js
export const signup = async (req, res) => {

    // Validate

    // Check user

    // Hash password

    // Create user

    // Generate token

    // Build email HTML

    // Send email

    // Handle email failure

    // Create response

};
```

Now imagine this controller becomes 200–300 lines.

That's a problem.

The controller should not know all these implementation details.

---

# 4. What should the controller actually do?

Ideally:

```js
export const signup = async (req, res) => {

    const result = await authService.signup(req.body);

    res.status(201).json({
        success: true,
        data: result
    });
};
```

Much cleaner.

The controller says:

> "Someone wants to sign up. Auth service, please handle the application operation."

It doesn't need to know:

```text
How password is hashed
How user is created
How verification token is generated
How email is rendered
How email is sent
Which SMTP server is used
```

Those responsibilities belong elsewhere.

---

# 5. Where should email logic go?

We can create an email service:

```text
services/
└── email.service.js
```

Then:

```text
Controller
    ↓
Auth Service
    ↓
Email Service
```

Conceptually:

```js
await emailService.sendVerificationEmail(user);
```

The authentication service knows:

> "After signup, this user needs a verification email."

The email service knows:

> "Here's how to send a verification email."

That's a much cleaner separation.

---

# 6. Important distinction: "When" vs "How"

This is one of the most useful ideas from this lesson.

### Auth service decides **when**

```text
User registered successfully
        ↓
User needs verification email
```

### Email service decides **how**

```text
Get user data
     ↓
Generate email data
     ↓
Render template
     ↓
Send through mail provider
```

So:

```text
AUTH SERVICE
"What should happen?"
       │
       ▼
EMAIL SERVICE
"How should the email be sent?"
```

This separation becomes extremely valuable as the application grows.

---

# 7. Think about a real application

Suppose your application eventually sends:

```text
Verification email
Password reset email
Welcome email
Password changed email
Login alert
Order confirmation
Payment receipt
Admin notification
Weekly report
```

If all of that is inside controllers, you'll eventually have:

```text
auth.controller.js
user.controller.js
order.controller.js
payment.controller.js
admin.controller.js
```

all containing email implementation code.

That's bad architecture.

Instead:

```text
services/
└── email.service.js
```

can become the central application interface for email.

---

# 8. Example architecture

A cleaner architecture could look like:

```text
routes
  ↓
controller
  ↓
service
  ├───────────────┐
  ↓               ↓
repository    email.service
  ↓               ↓
MongoDB         mailSender
                  ↓
                 SMTP
```

Notice something important.

The controller doesn't directly touch:

```text
MongoDB
SMTP
Email templates
JWT
```

It works through the appropriate application layer.

---

# 9. Why this matters for testing

Suppose we want to test signup.

If the controller directly sends email:

```text
Signup test
   ↓
Database
   ↓
SMTP
   ↓
External email server
```

Now our test depends on an external service.

That's annoying.

But if we separate email:

```text
Signup test
   ↓
Auth Service
   ↓
Mock Email Service
```

we can test signup without actually sending an email.

For example:

```js
emailService.sendVerificationEmail = jest.fn();
```

Then:

```text
Was signup successful?
Was email requested?
```

can be tested independently.

---

# 10. Why this matters for failures

Now imagine:

```text
User signup
     ↓
Database succeeds
     ↓
Email server is down
```

If email is directly inside the controller:

```text
Signup
 ↓
Database ✓
 ↓
Email ✗
 ↓
Controller throws
 ↓
500 response
```

Now the user might receive:

```text
500 Internal Server Error
```

even though their account was successfully created.

That's not necessarily what we want.

Later in this phase we'll learn how to handle this much better using:

```text
Email service
     ↓
Background job
     ↓
Queue
     ↓
Worker
```

Then:

```text
Signup
   ↓
Create user ✓
   ↓
Queue email ✓
   ↓
201 Created
```

and email can be processed separately.

---

# 11. Why this matters for performance

Sending email can involve network communication.

Imagine:

```text
API request
    ↓
Database: 50ms
    ↓
SMTP: 800ms
    ↓
Response
```

The user has to wait for the email operation.

With background processing:

```text
API request
    ↓
Database: 50ms
    ↓
Create email job: 5ms
    ↓
Response
```

Then separately:

```text
Queue
  ↓
Worker
  ↓
SMTP
```

The API becomes faster and more reliable.

We'll study this deeply in lessons **20.11–20.14**.

---

# 12. Another important reason: reusability

Suppose tomorrow you switch email providers.

Today:

```text
SMTP Provider A
```

Tomorrow:

```text
Provider B
```

If controllers directly contain provider-specific code, you'll need to modify many controllers.

But with:

```text
mailSender.js
```

you can isolate the provider-specific implementation.

Conceptually:

```text
Application
    ↓
Email Service
    ↓
Mail Sender
    ↓
Provider
```

Change the provider:

```text
Mail Sender
    ↓
New Provider
```

The rest of your application doesn't need to care.

---

# 13. Your starter's architecture

This is exactly why the starter separates the `mail/` area from the controllers/services that use it. The uploaded starter pack includes a mail layer with `mailSender.js`, `renderTemplate.js`, and email templates.

The idea is roughly:

```text
Application logic
       ↓
Email service
       ↓
mailSender
       ↓
Template renderer
       ↓
SMTP / provider
```

We're going to understand each piece individually during Phase 20.

---

# 14. Don't overcorrect

There's one important point.

We're **not** saying:

> "Controllers should never cause an email to be sent."

That's not true.

The controller can indirectly trigger email.

For example:

```text
Controller
    ↓
Auth Service
    ↓
Email Service
```

The problem is not **that an email is triggered**.

The problem is:

> **The controller shouldn't contain the email implementation details.**

That's the distinction.

Imagine a restaurant.

### Customer

```text
HTTP Request
```

### Waiter

```text
Controller
```

### Kitchen manager

```text
Service
```

### Database/storage worker

```text
Repository
```

### Delivery department

```text
Email Service
```

The waiter shouldn't personally:

```text

```

Similarly:

```text

```

shouldn't personally:

```text

```

It should coordinate the HTTP interaction.

# 17. Common mistakes

### ❌ Mistake 1 — Sending email directly from controller

```js
controller → transporter.sendMail()
```

Avoid this.

---

### ❌ Mistake 2 — Putting email HTML in controller

```js
const html = `
    <html>
       ...
    </html>
`;
```

Keep presentation separate.

---

### ❌ Mistake 3 — Putting SMTP credentials in controller

Never:

```js
const password = "my-smtp-password";
```

Use configuration.

---

### ❌ Mistake 4 — Making email service responsible for business decisions

Don't make:

```js
emailService.sendEmailIfUserIsAdmin(...)
```

The application/service layer should decide **whether** the email is needed.

The email layer should focus on **sending/rendering** it.

---

### ❌ Mistake 5 — Making every email synchronous

For some applications, this is acceptable initially.

But as your system grows, long-running or unreliable external operations should usually move toward background processing.

We'll learn when that is appropriate.

---

# 18. The three-layer distinction

Memorize this:

```text
CONTROLLER
"What HTTP request did I receive?"

SERVICE
"What should my application do?"

EMAIL SERVICE
"How should this email operation happen?"
```

And eventually:

```text
MAIL SENDER
"How do I communicate with the email provider?"
```

So:

```text
Controller
    ↓
Service
    ↓
Email Service
    ↓
Mail Sender
    ↓
SMTP
```

Each layer has a clear responsibility.

# 20. Final mental model

If you remember only one thing from **20.1**, remember this:

```text
             SIGNUP REQUEST
                    │
                    ▼
               CONTROLLER
              "HTTP handling"
                    │
                    ▼
               AUTH SERVICE
              "Business logic"
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      Repository         Email Service
          │                   │
          ▼                   ▼
       MongoDB            Mail Sender
                              │
                              ▼
                             SMTP
```

And later:

```text
Email Service
      │
      ▼
    Queue
      │
      ▼
   Worker
      │
      ▼
 Mail Sender
```

### The key principle

> **Controllers should coordinate HTTP, services should handle application/business logic, and email infrastructure should handle email.**

Once you understand this separation, the `mail/`, `services/`, and eventually `jobs/` folders in your starter stop looking like random folders and start becoming logical pieces of one system.
