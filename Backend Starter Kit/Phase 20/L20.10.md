Now we'll use that architecture for a **welcome email**.

---

## 1. What is a welcome email?

A welcome email is sent after a user successfully creates an account.

A simple flow is:

```text
User signs up
     ↓
Account created
     ↓
Signup succeeds
     ↓
Welcome email
     ↓
User's inbox
```

Example:

```text
Subject: Welcome to MyApp!

Hello Rahul,

Welcome to MyApp.

Your account has been created successfully.

We're happy to have you here.
```

It sounds simple, but there's an important architectural question:

> **When exactly should the welcome email be sent?**

That's where things become interesting.

---

# 2. Welcome email vs verification email

Don't confuse these two.

### Verification email

Purpose:

```text
Prove that the user controls the email address
```

Flow:

```text
Signup
 ↓
Verification token
 ↓
Verification email
 ↓
User clicks
 ↓
Email verified
```

### Welcome email

Purpose:

```text
Welcome the user and introduce the application
```

Flow:

```text
Signup
 ↓
Account created
 ↓
Welcome email
```

They can happen at different points.

---

# 3. When should we send the welcome email?

There are several possible designs.

### Option A — Immediately after signup

```text
Signup
 ↓
Create account
 ↓
Send welcome email
```

This is simple.

But the email address may not yet be verified.

---

### Option B — After email verification

```text
Signup
 ↓
Verification email
 ↓
User verifies
 ↓
Welcome email
```

This confirms the user actually controls the email address before sending the welcome message.

---

### Option C — Both

You can have:

```text
Signup
 ↓
Verification email
```

Then after verification:

```text
Email verified
 ↓
Welcome email
```

This can produce a nicer onboarding flow.

The correct choice depends on your product requirements.

---

# 4. Why does this matter architecturally?

Because email sending is a **side effect**.

Imagine:

```text
Create User
+
Send Welcome Email
```

If the database operation succeeds but email fails:

```text
User created ✅
Email failed ❌
```

What should happen?

Should signup fail?

Should the user still exist?

Should we retry the email?

These questions lead directly into the next Phase 20 lessons:

```text
20.11 Email failures
20.12 Async email processing
20.13 Background jobs
20.14 Queue fundamentals
```

Your roadmap intentionally places those topics immediately after welcome emails.

# 6. Welcome email template

We can create:

```text
mail/templates/welcome.ejs
```

A simple template:

```ejs
<!DOCTYPE html>
<html>
<head>
    <meta charset="UTF-8">
    <title>Welcome</title>
</head>

<body>

    <h1>Welcome, <%= name %>!</h1>

    <p>
        Thanks for creating an account with us.
    </p>

    <p>
        We're happy to have you here.
    </p>

    <p>
        You can now start using the application.
    </p>

</body>
</html>
```

Notice:

```ejs
<%= name %>
```

is still using the escaped EJS output syntax we learned earlier.

---

# 7. What data does the template need?

Keep it minimal.

For example:

```js
{
    name: user.firstName
}
```

You don't need to pass:

```js
{
    user,
    password,
    passwordHash,
    refreshToken,
    resetToken,
    ...
}
```

The template should receive only the information it actually needs.

---

# 8. Why minimal template data?

Suppose you do:

```js
renderTemplate("welcome", user);
```

Now the template technically has access to everything in the user object.

That's unnecessary.

Instead:

```js
renderTemplate("welcome", {
    name: user.firstName
});
```

is much clearer.

Think:

```text
User object
    ↓
Select required data
    ↓
Template data
    ↓
EJS
```

This reduces accidental exposure and makes the template contract easier to understand.

# 9. Email Service

Now create the email-specific operation:

```js
async function sendWelcomeEmail({
    email,
    name
}) {
    const html = await renderTemplate(
        "welcome",
        {
            name
        }
    );

    await mailSender.sendMail({
        to: email,
        subject: "Welcome to MyApp!",
        html
    });
}
```

The Email Service now knows:

```text
Which template?
Which subject?
Which template data?
```

It does not know:

```text
How the user was created
How MongoDB works
How passwords are hashed
How authentication works
```

---

# 10. Where should the welcome email be triggered?

This is an important architectural decision.

You might initially write:

```js
async function signup(data) {
    const user = await createUser(data);

    await sendWelcomeEmail({
        email: user.email,
        name: user.firstName
    });

    return user;
}
```

Conceptually:

```text
Auth Service
     ↓
Create user
     ↓
Send welcome email
```

This is okay for learning the architecture.

But there is a problem.

---

# 11. The side-effect problem

Suppose:

```text
createUser()
```

succeeds.

Then:

```text
sendWelcomeEmail()
```

fails.

Now:

```text
Database:
User exists ✅

Email:
Failed ❌
```

You cannot simply "roll back" an SMTP email operation like a normal database transaction.

This is one of the reasons email should eventually become asynchronous.

---

# 12. Don't delete the user just because email failed

A beginner might think:

```text
Email failed
 ↓
Delete user
```

Usually, that's not a good general solution.

Why?

The account creation itself may have succeeded correctly.

Instead, a better architecture can be:

```text
User created
 ↓
Email task created
 ↓
Background worker
 ↓
Send email
```

If email fails:

```text
Retry
```

We'll study this properly in 20.11–20.14.

---

# 13. Welcome email is a side effect

This is the important concept:

```text
Primary operation:
Create account

Secondary operation:
Send welcome email
```

So:

```text
Account creation
        ↓
Primary business operation

Welcome email
        ↓
Side effect
```

Other examples of side effects:

```text
Send email
Send notification
Publish event
Write audit record
Update analytics
```

Recognizing side effects is an important backend architecture skill.

# 16. A useful design

For many applications, a simple design is:

```text
Signup
 ↓
Create account
 ↓
Send verification email
```

Then:

```text
Successful verification
 ↓
Mark emailVerified = true
 ↓
Send welcome email
```

This gives the welcome email a meaningful trigger:

> **The user has successfully verified their account.**

---

# 17. But beware of duplicate welcome emails

Suppose the user clicks the verification link twice.

You don't want:

```text
Verification
 ↓
Welcome email #1

Verification again
 ↓
Welcome email #2
```

So the system should make the welcome action idempotent or otherwise track whether it has already been sent.

For example, conceptually:

```text
welcomeEmailSent
```

or an event/idempotency mechanism.

You don't necessarily need to add this field right now; the key lesson is:

> **Important side effects should not accidentally happen multiple times.**

---

# 18. What is idempotency?

An operation is idempotent when repeating it doesn't keep producing additional unwanted effects.

For example:

```text
Set:
emailVerified = true
```

can safely happen again.

But:

```text
Send welcome email
```

is not naturally idempotent.

Calling it twice:

```text
sendWelcomeEmail()
sendWelcomeEmail()
```

produces:

```text
Email #1
Email #2
```

Therefore, email workflows need special thinking around duplicates.

---

# 19. Welcome email should not contain secrets

This is extremely important.

Don't send:

```text
Your password is: abc123
```

or:

```text
Your refresh token is: ...
```

or:

```text
Your reset token is: ...
```

A welcome email should contain normal onboarding information.

For example:

```text
Welcome Rahul!

Your account has been created.

Start using the application:
[Open App]
```

---

# 20. Welcome email can contain a CTA

CTA means:

> **Call to Action**

For example:

```text
[ Open Dashboard ]
```

The template could receive:

```js
{
    name,
    dashboardUrl
}
```

Then:

```ejs
<a href="<%= dashboardUrl %>">
    Open Dashboard
</a>
```

Again, the URL should come from trusted application configuration rather than arbitrary user input.

---

# 21. Don't build URLs randomly inside EJS

Avoid putting business logic into the template.

Bad:

```ejs
<a href="https://<%= domain %>/users/<%= id %>/dashboard">
```

when the URL construction itself is complex.

Better:

```js
const dashboardUrl = buildDashboardUrl(user);
```

then:

```js
renderTemplate("welcome", {
    name: user.firstName,
    dashboardUrl
});
```

The template simply presents the result.

---

# 22. Template vs business logic

Remember:

```text
Service:
"Where should this user go?"

Template:
"How should that link look?"
```

So:

```text
Service
   ↓
dashboardUrl
   ↓
Template
   ↓
<a href="...">
```

This keeps EJS simple.

# 26. Welcome email data contract

Think of:

```text
sendWelcomeEmail()
```

as having a contract.

Input:

```text
email
name
optional dashboardUrl
```

Output:

```text
Email delivery requested
```

So:

```text
sendWelcomeEmail({
    email,
    name,
    dashboardUrl
});
```

This is much cleaner than:

```text
sendWelcomeEmail(user)
```

when the whole user object isn't needed.

# 30. What should happen after a failure?

There are several possibilities:

### Retry immediately

```text

 ↓

 ↓
Retry
```

### Queue for later

```text

 ↓
Queue
 ↓
Worker
 ↓
SMTP
```

### Retry with backoff

```text
Attempt 1
 ↓
wait
 ↓
Attempt 2
 ↓
wait longer
 ↓
Attempt 3
```

# 36. Interview questions

### What is a welcome email?

An email sent as part of user onboarding, usually after account creation or verification.

### Is a welcome email the same as verification?

No.

Verification establishes email ownership; a welcome email is primarily an onboarding communication.

### Should a welcome email contain a password?

Never.

### Should we pass the whole user object to EJS?

No. Pass only the data the template requires.

### Why can welcome emails create architectural problems?

Because email sending is an external side effect that can fail independently of database operations.

### Why might we eventually use a queue?

To prevent email delivery from slowing down the main request and to allow retries when delivery fails.

### What is duplicate email delivery?

When the same logical event causes the same email to be sent multiple times.

### How can duplicate welcome emails be prevented?

Use idempotency/state tracking or a reliable event/job-processing design.

# 37. The important architecture lesson

At this point, you should see something bigger.

We have three types of operations:

### Primary operation

```text
Create user
```

### Security operation

```text
Generate verification/reset credential
```

### Side effect

```text
Send email
```

These don't necessarily belong in one function.

A clean architecture separates them:

```text
                REQUEST
                   │
                   ▼
             Auth Service
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
    Database work       Email request
                            │
                            ▼
                       Email Service
                            │
                            ▼
                         SMTP
```

This separation becomes extremely valuable as the application grows.
