# Lesson 20.11 — Email Failures

Your Phase 20 roadmap places **20.11 Email Failures** immediately after verification, password-reset, and welcome emails. The next lessons then move into async processing, background jobs, and queues.

This lesson answers a very important production question:

> **What happens when the application works correctly, but sending the email fails?**

---

# 1. Email is an external dependency

Your backend controls:

```text
Node.js
Express
MongoDB
Your services
Your controllers
```

But it does **not** control:

```text
SMTP server
Email provider
Internet connection
Recipient's mail server
DNS
```

So:

```text
Your backend
     │
     ▼
Email provider
     │
     ▼
Recipient mail server
     │
     ▼
User
```

Every arrow can potentially fail.

---

# 2. A simple example

Suppose a user signs up:

```text
POST /api/v1/auth/signup
```

Your application does:

```text
Validate user
    ↓
Create user in MongoDB
    ↓
Send welcome email
```

MongoDB succeeds:

```text
User created ✅
```

But SMTP fails:

```text
Email failed ❌
```

Now you have:

```text
Database:
User exists

Email:
Not delivered
```

This is a **partial success**.

---

# 3. Why this is difficult

The database and email server are two different systems.

MongoDB might say:

```text
SUCCESS
```

while SMTP says:

```text
FAILURE
```

There is no normal database transaction that can magically undo an external email.

You cannot reliably do:

```text
MongoDB transaction
+
SMTP transaction
```

as one atomic operation.

So we need to design for failure.

---

# 4. The first mistake: treating email like database work

A beginner might write:

```js
const user = await userRepository.createUser(data);

await emailService.sendWelcomeEmail(user);

return user;
```

This works when everything is healthy.

But imagine:

```text
createUser()
     ↓
SUCCESS
     ↓
sendWelcomeEmail()
     ↓
FAIL
     ↓
throw error
```

Now your API might return:

```http
500 Internal Server Error
```

even though:

```text
User was successfully created.
```

That's confusing for the frontend.

The user might click **Sign Up** again.

Then:

```text
User already exists
```

and now you have another problem.

---

# 5. Don't automatically roll back the user

One tempting solution is:

```text
Create user
 ↓
Email fails
 ↓
Delete user
```

Generally, don't make this your default design.

Why?

Because the account creation and email delivery are separate concerns.

The user may already have a valid account even though the email provider temporarily failed.

A better mental model is:

```text
Account creation
      ↓
Successful business operation

Email delivery
      ↓
Independent side effect
```

---

# 6. Types of email failures

Not every failure means the same thing.

We can broadly think about:

```text
1. Temporary failures
2. Permanent failures
3. Application failures
4. Configuration failures
5. Provider failures
```

Let's understand each.

---

# 7. Temporary failure

A temporary failure may happen because:

```text
SMTP server temporarily unavailable
Network timeout
Connection reset
Provider overloaded
Temporary rate limit
```

Example:

```text
Backend
 ↓
SMTP
 ↓
"Connection timeout"
```

This doesn't necessarily mean the email can never be sent.

It may succeed a few seconds later.

Therefore:

```text
Temporary failure
      ↓
Retry may help
```

---

# 8. Permanent failure

Some failures shouldn't simply be retried again and again.

For example:

```text
Invalid recipient address
```

or potentially:

```text
Rejected recipient
```

If the email address itself is invalid, retrying:

```text
1
2
3
4
5
...
```

doesn't fix it.

So:

```text
Permanent failure
      ↓
Don't endlessly retry
```

---

# 9. Application failure

Your own code can fail before SMTP is even contacted.

For example:

```text
Template rendering
       ↓
ERROR
```

Maybe:

```text
welcome.ejs
```

has an invalid variable:

```ejs
<%= userName %>
```

but the service passes:

```js
{
    name: "Rahul"
}
```

The email isn't sent because the template rendering failed.

---

# 10. Configuration failure

Suppose your environment contains:

```env
SMTP_HOST=
SMTP_PORT=
SMTP_USER=
SMTP_PASSWORD=
```

and something is wrong.

Then:

```text
Application
    ↓
mailSender
    ↓
SMTP configuration
    ↓
FAIL
```

This isn't a user problem.

It's an application/deployment configuration problem.

---

# 11. Provider failure

Your email provider might have an outage.

For example:

```text
Your application
       ↓
Email provider
       ↓
Provider unavailable
```

Your application can be perfectly healthy.

The external dependency isn't.

This is why observability matters.

---

# 12. Network timeout

One very common failure:

```text
await transporter.sendMail(...)
```

takes too long.

Instead of waiting forever:

```text
Request
 ↓
SMTP
 ↓
..................
 ↓
Timeout
```

your mail sender should have appropriate timeout behavior.

The exact timeout settings depend on the mail library/provider you're using.

The principle is:

> **Never allow an external dependency to hang your application indefinitely.**

---

# 13. Email failure should be observable

Remember Phase 19.

You need useful logs.

For example:

```text
event: email_send_failed
emailType: welcome
recipient: rahul@example.com
errorType: SMTP_TIMEOUT
requestId: abc123
```

But be careful.

Don't log:

```text
password
reset token
access token
refresh token
SMTP password
```

Your Phase 19 logging architecture specifically emphasizes sensitive-data handling.

---

# 14. Log useful information

Good:

```text
emailType
recipient
provider
error code
requestId
duration
attempt number
```

Potentially useful:

```text
messageId
```

if your provider gives one.

Avoid:

```text
email HTML
reset URL
verification token
credentials
```

---

# 15. Don't expose SMTP errors to users

Suppose SMTP returns:

```text
ECONNREFUSED smtp.example.com:587
```

Don't return this:

```json
{
  "success": false,
  "message": "ECONNREFUSED smtp.example.com:587"
}
```

to the frontend.

That's an internal implementation detail.

Instead:

```json
{
  "success": false,
  "message": "Unable to send email at this time."
}
```

or, depending on the workflow:

```json
{
  "success": true,
  "message": "If the account exists, a reset email will be sent."
}
```

The client shouldn't need to know your SMTP infrastructure.

---

# 16. Error classification

A useful mental model:

```text
                    Email Error
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
      Temporary      Permanent       Internal
          │              │              │
          ▼              ▼              ▼
        Retry         Don't retry    Fix code/config
```

For example:

```text
Temporary:
timeout

Permanent:
invalid recipient

Internal:
template rendering bug
```

The exact classification depends on the provider and error information.

---

# 17. Should we retry?

Sometimes yes.

For example:

```text
Attempt 1
   ↓
timeout
   ↓
Retry
```

But don't do:

```text
while (true) {
    sendEmail();
}
```

That would be dangerous.

---

# 18. Why infinite retries are bad

Imagine SMTP is down.

Your server keeps doing:

```text
retry
retry
retry
retry
retry
...
```

Now you can create:

```text
CPU usage
Connection exhaustion
Memory pressure
Provider abuse
Duplicate emails
```

So retries must be controlled.

---

# 19. Maximum retry attempts

Conceptually:

```text
Attempt 1
 ↓
fail
 ↓
Attempt 2
 ↓
fail
 ↓
Attempt 3
 ↓
fail
 ↓
Stop
```

For example:

```text
maxAttempts = 3
```

The exact number should depend on your application.

The principle is:

> **Retries must have a limit.**

---

# 20. Exponential backoff

Suppose an email fails.

Don't necessarily retry immediately:

```text
0s
0s
0s
```

Instead:

```text
Attempt 1
 ↓
wait 1s
 ↓
Attempt 2
 ↓
wait 2s
 ↓
Attempt 3
 ↓
wait 4s
 ↓
Attempt 4
```

This is called **exponential backoff**.

Conceptually:

```text
delay = base × 2^attempt
```

You don't need to memorize the exact formula yet.

Remember:

> **Wait longer between repeated failures.**

---

# 21. Add jitter

If thousands of jobs fail simultaneously and all retry at exactly:

```text
1 second
2 seconds
4 seconds
```

they may all hit the provider at the same moment.

That's called a **thundering herd** problem.

So production systems often add random variation:

```text
1.2 sec
2.7 sec
4.1 sec
```

This is called **jitter**.

You don't need to implement it yet, but understand why it exists.

---

# 22. Synchronous retry vs background retry

This distinction is very important.

### Synchronous

```text
HTTP Request
    ↓
Send email
    ↓
Fail
    ↓
Retry
    ↓
Retry
    ↓
HTTP Response
```

The user waits.

### Asynchronous

```text
HTTP Request
    ↓
Create email job
    ↓
HTTP Response
```

Then:

```text
Worker
   ↓
Send email
   ↓
Fail
   ↓
Retry later
```

This is much better for many production workflows.

And this leads directly into **20.12 Async Email Processing**.

---

# 23. What should signup return?

Consider:

```text
User created
Email failed
```

You have several choices.

### Choice A

Return failure:

```text
500
```

This tells the frontend signup failed.

Problem:

```text
User actually exists.
```

---

### Choice B

Return success:

```text
201
```

and handle email separately.

This often gives a better user experience when email is a secondary side effect.

For example:

```json
{
  "success": true,
  "message": "Account created successfully."
}
```

Then email delivery can happen independently.

The exact contract depends on your product requirements.

---

# 24. Password reset is different

Remember:

```text
POST /forgot-password
```

should generally return a generic response.

For example:

```text
"If an account exists for this email,
a reset email has been sent."
```

Even if:

```text
SMTP temporarily fails
```

you need to carefully decide how much information to expose.

Don't accidentally turn email infrastructure behavior into an account-enumeration signal.

---

# 25. Verification email failure

Suppose:

```text
Signup
 ↓
User created
 ↓
Verification email fails
```

The account may still exist:

```text
emailVerified = false
```

The user can potentially request verification again.

This is another reason verification email sending should not be treated as identical to user creation.

---

# 26. Welcome email failure

Suppose:

```text
User verified
 ↓
Welcome email fails
```

The user is still verified.

Don't undo:

```text
emailVerified = true
```

just because the welcome email failed.

Think:

```text
Verification
    ↓
Primary account state

Welcome email
    ↓
Communication side effect
```

---

# 27. Separate business state from delivery state

This is a powerful architecture concept.

Instead of thinking:

```text
User = email sent
```

think:

```text
User
├── account state
└── email-related events/jobs
```

For example:

```text
User verified
      ↓
Welcome email requested
      ↓
Delivery succeeds/fails
```

The account's state doesn't have to become invalid just because delivery failed.

---

# 28. Email status

For more advanced systems, you might track something like:

```text
PENDING
SENT
FAILED
```

Conceptually:

```text
Email Job
   │
   ├── PENDING
   │
   ├── SENT
   │
   └── FAILED
```

You could also have:

```text
RETRYING
```

or provider-specific states.

Don't add a complicated email-status database model just because we're studying the concept. First understand **why** delivery state may need to exist separately.

---

# 29. Dead-letter concept

Suppose:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
```

and the job still cannot be delivered.

You don't want it to disappear silently.

A production queue system may eventually move it to a:

```text
Dead Letter Queue
```

or failure store.

Conceptually:

```text
Email Job
   ↓
Retry
   ↓
Retry
   ↓
Retry
   ↓
Still failing
   ↓
Dead Letter Queue
```

We'll study queues later in Phase 20.14.

---

# 30. Alerting

Some email failures are expected.

But if suddenly:

```text
1% failure
```

becomes:

```text
70% failure
```

something is wrong.

Observability can detect:

```text
Email failure rate ↑
```

and trigger an alert.

So the architecture becomes:

```text
Email Service
      ↓
Logs + Metrics
      ↓
Monitoring
      ↓
Alert
```

This connects Phase 19 and Phase 20.

---

# 31. Metrics

Useful email metrics include:

```text
emails_requested
emails_sent
emails_failed
emails_retried
email_duration
```

For example:

```text
Email success rate = sent / requested
```

You can also measure by email type:

```text
verification
password-reset
welcome
```

This helps you discover:

```text
"Password reset emails are failing more than welcome emails."
```

---

# 32. Don't count "accepted by SMTP" as "delivered"

This is an important distinction.

Your application might receive:

```text
SMTP accepted message
```

That doesn't necessarily mean:

```text
User opened email
```

or even:

```text
Email reached inbox
```

There are multiple stages:

```text
Application
    ↓
SMTP accepted
    ↓
Provider processing
    ↓
Recipient server
    ↓
Inbox / spam / rejection
```

Your `sendMail()` success usually tells you something about the submission step, not the entire delivery journey.

---

# 33. Email delivery vs email submission

Think:

```text
sendMail()
```

means roughly:

> "I successfully handed the message to the configured mail transport."

It doesn't automatically mean:

> "Rahul definitely saw this email in his inbox."

This distinction becomes important when using real email providers.

# 34. A useful error-handling architecture

Eventually we want something like:

```text
                   EMAIL REQUEST
                        │
                        ▼
                  Email Service
                        │
                        ▼
                   Mail Sender
                        │
                ┌───────┴───────┐
                │               │
             SUCCESS          FAILURE
                │               │
                ▼               ▼
              SENT        Classify error
                                │
                    ┌───────────┴──────────┐
                    │                      │
                Temporary              Permanent
                    │                      │
                    ▼                      ▼
                  Retry                Record failure
                    │
                    ▼
                Success?
                    │
              ┌─────┴─────┐
              │           │
             YES          NO
              │           │
              ▼           ▼
             SENT      Retry limit
                           │
                           ▼
                       Failed/DLQ
```

This is the architecture we're building toward.

---

# 35. Where should error handling live?

Don't put everything inside the controller.

Bad:

```js
try {
    await sendEmail();
} catch (error) {
    // 100 lines of retry logic
}
```

Your controller should not know SMTP internals.

Instead:

```text
Controller
   ↓
Application Service
   ↓
Email Service
   ↓
Mail Sender
```

Each layer handles its responsibility.

---

# 36. Mail Sender responsibility

The `mailSender` should be responsible for communicating with the transport.

Conceptually:

```js
await mailSender.sendMail({
    to,
    subject,
    html
});
```

If SMTP fails:

```text
mailSender
    ↓
throws/returns error
```

It should not decide:

```text
Should the user be deleted?
Should password reset be revoked?
Should signup fail?
```

Those are application-level decisions.

---

# 37. Email Service responsibility

The Email Service understands:

```text
verification email
password reset email
welcome email
```

For example:

```text
sendVerificationEmail()
sendPasswordResetEmail()
sendWelcomeEmail()
```

It can handle:

```text
template
subject
recipient
template data
```

But it shouldn't become a giant retry engine.

---

# 38. Job/queue responsibility

Later, when we introduce background jobs:

```text
Email Job
   ↓
Worker
   ↓
Email Service
   ↓
Mail Sender
```

The job system can handle things like:

```text
retry
delay
backoff
attempt count
failed jobs
dead-letter handling
```

This separation is much cleaner.

# 39. A real-world mental model

Think about an online store.

User places an order:

```text
Order created
```

Then several side effects happen:

```text
Send order confirmation
Send notification
Update analytics
Start fulfillment
```

If the email provider fails:

```text
Order should still exist.
```

You don't want:

```text
Email failed
 ↓
Delete order
```

Instead:

```text
Order created
 ↓
Email job created
 ↓
Worker tries email
 ↓
Retry if needed
```

This is the same architecture we're learning.

# 40. Failure doesn't always mean the main operation failed

This is perhaps the most important lesson.

Suppose:

```text
Create user = SUCCESS
Send email = FAILURE
```

The result is not simply:

```text
SUCCESS
```

or:

```text
FAILURE
```

It's:

```text
Primary operation:
SUCCESS

Side effect:
FAILURE
```

Backend engineers need to be comfortable designing systems around these partial outcomes.

What happens if:


Don't automatically assume:

```text
Entire signup must be rolled back.
```

# 43. Interview questions

### What happens if SMTP fails after user creation?

The user can still exist; email delivery should be treated as a separate side effect and handled/retried appropriately.

### Should email failure automatically roll back a database transaction?

Not generally. Email is an external system and isn't normally part of the same atomic database transaction.

### What is a transient email failure?

A temporary failure that may succeed if retried later.

### What is exponential backoff?

Increasing the delay between retry attempts.

### Why add jitter?

To prevent many clients/jobs from retrying at exactly the same time.

### Why shouldn't we retry forever?

It can overload your application/provider and waste resources.

### What is a dead-letter queue?

A place where jobs that repeatedly fail can be stored for investigation or later handling.

### Should SMTP errors be returned directly to the frontend?

No. Return a safe application-level message and log the internal details appropriately.

### Should a failed welcome email invalidate a verified user?

Normally no. Account state and email delivery are separate concerns.

Memorize this:

```text
             PRIMARY OPERATION
                    │
                    ▼
              Create/Update
                    │
                 SUCCESS
                    │
                    ▼
              SIDE EFFECT
                    │
                    ▼
                Send Email
                    │
             ┌──────┴──────┐
             │             │
          SUCCESS        FAILURE
             │             │
             ▼             ▼
            SENT      Classify error

                    │             │
                 Temporary     Permanent
                    │             │
                    ▼             ▼
                  Retry       Record/stop
```

### The key rule:

> **Never design your application as if email delivery is guaranteed.**

Email is an external dependency. It can be slow, unavailable, rejected, or temporarily broken.

Your job as a backend developer is to make sure that **a failure in email doesn't unnecessarily destroy the correctness of the main business operation**.
