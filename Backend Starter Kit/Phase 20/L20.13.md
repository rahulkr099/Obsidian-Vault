# Lesson 20.13 — Background Jobs

In the Phase 20 sequence, we have reached **Background Jobs** after learning why email should be processed asynchronously. The goal now is to understand exactly what a **job** is, what a **worker** does, and how work moves from the main application to background processing.

---

## 1. What is a background job?

A **background job** is a piece of work that your application asks another process to perform **outside the current HTTP request**.

For example:

```text
User signs up
     ↓
Create account
     ↓
Create "send welcome email" job
     ↓
Return response
```

Later:

```text
Worker
  ↓
Pick up job
  ↓
Send welcome email
```

So a job is basically:

> **A description of work that needs to be performed later or independently.**

---

# 2. Why do we need background jobs?

Some operations are not ideal for the HTTP request lifecycle.

Examples:

```text
Send email
Generate PDF
Resize image
Generate report
Process uploaded video
Send notification
Export large dataset
Process webhook
```

Imagine:

```text
POST /generate-report
```

and generating the report takes:

```text
30 seconds
```

You don't want:

```text
Browser
   ↓
HTTP request
   ↓
30 seconds waiting
   ↓
Response
```

Instead:

```text
Browser
   ↓
Request report
   ↓
Create background job
   ↓
Response: "Report is being generated"
```

Then:

```text
Worker
   ↓
Generate report
   ↓
Store report
```

---

# 3. Job vs function

This is important.

A normal function:

```js
await sendWelcomeEmail();
```

means:

> Execute this function now.

A background job means:

```js
await queue.add({
    type: "WELCOME_EMAIL",
    ...
});
```

means:

> Record this work so it can be processed separately.

So:

```text
Function
    ↓
Execute now

Job
    ↓
Execute later/independently
```

---

# 4. A job contains instructions

Think of a job as a small package of information.

For example:

```js
{
    type: "WELCOME_EMAIL",
    data: {
        email: "rahul@example.com",
        name: "Rahul"
    }
}
```

It tells the worker:

```text
WHAT:
Send welcome email

TO:
rahul@example.com

DATA:
Rahul
```

---

# 5. Job payload

The information inside the job is called the **payload**.

Example:

```js
{
    type: "WELCOME_EMAIL",
    data: {
        email: "rahul@example.com",
        name: "Rahul"
    }
}
```

Here:

```text
type
 ↓
Job type

data
 ↓
Job payload
```

You can think of:

```text
Job
├── type
└── data
```

---

# 6. Why should job payloads be small?

Suppose your user document contains:

```js
{
    _id,
    email,
    firstName,
    passwordHash,
    refreshToken,
    role,
    createdAt,
    updatedAt,
    ...
}
```

Don't blindly put the whole document into the job:

```js
// ❌
{
    type: "WELCOME_EMAIL",
    user: entireUser
}
```

Instead:

```js
// ✅
{
    type: "WELCOME_EMAIL",
    data: {
        email: user.email,
        name: user.firstName
    }
}
```

Smaller payloads are:

- easier to understand
    
- safer
    
- easier to serialize
    
- easier to debug
    
- less expensive to store

# 7. The worker

A **worker** is a process that takes background jobs and performs the actual work.

Think:

```text
Queue
   ↓
Worker
   ↓
Job
   ↓
Execute
```

For an email:

```text
Queue
   ↓
Worker
   ↓
Email Service
   ↓
Mail Sender
   ↓
SMTP
```

The worker's job is basically:

> **Take pending work and execute it.**

---

# 8. Producer → Queue → Worker

This is the fundamental background-job architecture:

```text
             PRODUCER
                 │
                 ▼
              QUEUE
                 │
                 ▼
              WORKER
                 │
                 ▼
             JOB HANDLER
                 │
                 ▼
             Actual work
```

For email:

```text
Auth Service
     │
     ▼
Email Job
     │
     ▼
Queue
     │
     ▼
Worker
     │
     ▼
Email Service
     │
     ▼
SMTP
```

---

# 9. Who is the producer?

The **producer** creates the job.

For example:

```text
Signup Service
     ↓
Create welcome-email job
```

So:

```text
Signup Service = Producer
```

Another example:

```text
Order Service
     ↓
Create invoice-generation job
```

Here:

```text
Order Service = Producer
```

---

# 10. Who is the consumer?

The **consumer** processes the job.

For example:

```text
Email Worker
     ↓
Processes welcome-email job
```

So:

```text
Worker = Consumer
```

The basic relationship is:

```text
Producer
   ↓
Job
   ↓
Consumer
```

---

# 11. Job handler

A worker usually needs to know:

> "What should I do for this job type?"

Conceptually:

```js
async function processJob(job) {

    switch (job.type) {

        case "WELCOME_EMAIL":
            return sendWelcomeEmail(job.data);

        case "VERIFICATION_EMAIL":
            return sendVerificationEmail(job.data);

        case "PASSWORD_RESET_EMAIL":
            return sendPasswordResetEmail(job.data);

        default:
            throw new Error("Unknown job type");
    }
}
```

This is a simple conceptual example.

In a larger system, you may separate handlers more cleanly.

---

# 12. Why separate handlers?

Instead of one giant function:

```text
processEverything()
```

you can have:

```text
welcomeEmailHandler
verificationEmailHandler
passwordResetHandler
invoiceHandler
reportHandler
```

For example:

```text
Worker
  │
  ├── Welcome Email Handler
  ├── Verification Handler
  ├── Password Reset Handler
  └── Report Handler
```

This keeps background processing easier to maintain.

---

# 13. Job lifecycle

A background job usually goes through several states.

Conceptually:

```text
CREATED
   ↓
QUEUED
   ↓
PROCESSING
   ↓
COMPLETED
```

If something goes wrong:

```text
QUEUED
   ↓
PROCESSING
   ↓
FAILED
   ↓
RETRY
   ↓
PROCESSING
```

Eventually:

```text
COMPLETED
```

or:

```text
PERMANENTLY FAILED
```

---

# 14. Pending jobs

Suppose your application creates:

```text
Job #101
Job #102
Job #103
```

The queue might look like:

```text
┌─────────┐
│ Job 101 │
├─────────┤
│ Job 102 │
├─────────┤
│ Job 103 │
└─────────┘
```

The worker takes one:

```text
Queue
 ├── Job 102
 └── Job 103

Worker
 └── Job 101
```

Then processes it.

---

# 15. Multiple workers

Suppose there are many jobs:

```text
Queue
 │
 ├── Job 101
 ├── Job 102
 ├── Job 103
 ├── Job 104
 └── Job 105
```

You can have:

```text
          Queue
        /   |   \
       /    |    \
      ▼     ▼     ▼
 Worker1 Worker2 Worker3
```

Now jobs can be processed concurrently.

This is one of the major scalability benefits of background jobs.

---

# 16. But more workers aren't always better

Suppose your email provider allows only a certain amount of traffic.

If you start:

```text
100 workers
```

you could overwhelm:

```text
SMTP provider
```

So you need to consider:

```text
Workers
+
Concurrency
+
Provider limits
+
Rate limiting
```

Scaling workers blindly can make the system worse.

---

# 17. Worker is separate from the API server

You can run your backend like:

```text
API Server
    │
    └── Handles HTTP requests
```

and separately:

```text
Worker Process
    │
    └── Handles background jobs
```

For example:

```text
                Application
              /             \
             /               \
            ▼                 ▼
       API Server          Worker
            │                 │
       HTTP Requests       Jobs
```

This separation is very useful.

---

# 18. Why separate processes?

Imagine email processing becomes heavy.

You don't want:

```text
Email processing
     ↓
Consumes CPU/memory
     ↓
API becomes slow
```

With separate workers:

```text
API Process
   ↓
HTTP requests

Worker Process
   ↓
Background jobs
```

They can scale independently.

For example:

```text
2 API instances
+
5 workers
```

depending on workload.

---

# 19. Background jobs survive HTTP requests

This is one of their biggest advantages.

Suppose:

```text
POST /signup
```

returns:

```text
201 Created
```

Then the browser closes.

The email job can still continue:

```text
Browser closed
     │
     X
     
Queue
     ↓
Worker
     ↓
Email
```

The job isn't tied to the browser connection.

That's a major difference from doing the work directly inside the request.

---

# 20. Job execution is independent

Suppose:

```text
User
 ↓
Signup
 ↓
Email Job
 ↓
Response
```

The worker can execute the job even after the HTTP request is finished.

This is exactly what we mean by:

> **Background processing.**

---

# 21. What if the worker crashes?

Suppose:

```text
Worker
 ↓
Job #101
 ↓
Processing
 ↓
Worker crashes
```

A robust job system should avoid simply losing Job #101.

Depending on the queue system, the job may become:

```text
available again
```

and another worker can process it.

Conceptually:

```text
Worker 1
   ↓
Job #101
   ↓
CRASH

              ↓

Worker 2
   ↓
Job #101
```

This is why proper queues are important.

---

# 22. Job acknowledgement

After successfully processing a job:

```text
Worker
   ↓
Process job
   ↓
SUCCESS
   ↓
ACK
```

ACK means roughly:

> **I successfully handled this job.**

Then the queue can consider the job completed.

---

# 23. What if ACK fails?

This is where distributed systems become interesting.

Suppose:

```text
Worker
 ↓
Send email
 ↓
SUCCESS
 ↓
Worker crashes
```

before the job is acknowledged.

The queue may think:

```text
Job wasn't completed
```

and retry it.

Result:

```text
Email sent #1
Email sent #2
```

Potential duplicate.

That's why:

```text
Background jobs
+
Idempotency
```

are closely connected.

---

# 24. At-least-once processing

Many job systems effectively aim for:

> **The job should be processed at least once.**

That means:

```text
1 execution
```

is normal, but in failure scenarios:

```text
2 executions
```

can happen.

Therefore:

```text
Don't assume:
"One job = exactly one execution."
```

Instead:

```text
Design important operations to tolerate retries.
```

---

# 25. Email is not perfectly idempotent

Consider:

```js
sendWelcomeEmail();
```

If called twice:

```text
Email #1
Email #2
```

The user receives two emails.

So if duplicate processing matters, you may need:

```text
Idempotency key
+
Delivery tracking
+
Duplicate detection
```

The exact solution depends on your email provider and architecture.

---

# 26. Job ID

A job can have an identifier:

```text
jobId = 12345
```

Then you can track:

```text
Job 12345
type: WELCOME_EMAIL
status: COMPLETED
attempts: 2
```

This becomes very useful for debugging.

Imagine a support issue:

> "I received two welcome emails."

You can investigate:

```text
jobId
attempt count
worker logs
email provider response
```

---

# 27. Attempt count

A job can track:

```text
attempts = 1
```

Then:

```text
attempts = 2
```

Then:

```text
attempts = 3
```

This allows retry policies such as:

```text
maximum attempts = 3
```

After that:

```text
FAILED
```

or:

```text
DEAD_LETTER
```

# 28. Delayed jobs

Background jobs don't always need to run immediately.

For example:

> Send a reminder 24 hours after signup.

You can create:

```text
Reminder Job
     ↓
Wait 24 hours
     ↓
Worker
     ↓
Send reminder
```

Other examples:

```text
Retry after 30 seconds
Retry after 5 minutes
Send reminder tomorrow
Generate report at midnight
```

This is another major advantage of job systems.

---

# 29. Scheduled jobs vs background jobs

They're related but not identical.

### Background job

```text
Do this work outside the request.
```

### Delayed job

```text
Do this work later.
```

### Scheduled job

```text
Do this work at a defined time or interval.
```

For example:

```text
Every day at 2 AM
 ↓
Generate reports
```

That's scheduled work.

---

# 30. Job priority

Some jobs may be more important than others.

For example:

```text
PASSWORD_RESET_EMAIL
```

might deserve higher priority than:

```text
MARKETING_EMAIL
```

Conceptually:

```text
HIGH
  ↓
Password reset

MEDIUM
  ↓
Verification

LOW
  ↓
Marketing
```

A queue system can sometimes support priorities.

Don't over-engineer this in your starter backend, but understand the concept.

---

# 31. Background jobs can fail independently

Suppose:

```text
User signup
 ↓
User created ✅
 ↓
Welcome job created ✅
 ↓
Worker tries email
 ↓
SMTP fails ❌
```

The main operation remains successful.

The background job can:

```text
Retry
```

without making the user repeat signup.

This is one of the biggest reasons we introduced background jobs.

# 32. Logging background jobs

Because jobs happen outside HTTP requests, you need good logs.

For example:

```text
jobId=12345
jobType=WELCOME_EMAIL
attempt=2
status=started
```

Then:

```text
jobId=12345
jobType=WELCOME_EMAIL
attempt=2
status=completed
```

Or:

```text
jobId=12345
jobType=WELCOME_EMAIL
attempt=2
status=failed
error=SMTP_TIMEOUT
```

This makes debugging much easier.

# 33. Correlation between request and job

A very useful production pattern is to carry a correlation/request ID.

For example:

```text

```

Then:

```text
Signup request
    ↓
Email job
    ↓
Worker
```

can retain the relationship:

```text
requestId = req_abc123

```

Now you can investigate:

```text
What happened to this signup?
```

```text

 → database operation

```

This connects directly with the structured logging concepts from Phase 19.

# 34. Job payload and security

Remember that jobs can be persisted.

Therefore, don't put secrets inside them.

Bad:

```js
{
    type: "PASSWORD_RESET",
    password: "secret"
}
```

Bad:

```js
{
    type: "AUTH",
    refreshToken: "..."
}
```

Be especially careful with:

```text
Passwords
Tokens
API keys
Credentials
Private data
```

Use the smallest payload necessary.

---

# 35. What should the worker know?

The worker should know:

```text
How to execute background work.
```

It should not need to know:

```text
HTTP request details
Express req/res
Browser information
```

For example:

```text
Worker
  ↓
processWelcomeEmail(job)
```

not:

```text
Worker
  ↓
req.body.email
```

The worker is not handling an HTTP request.

---

# 36. Worker should call services

A clean architecture:

```text
Worker
   ↓
Job Handler
   ↓
Application/Domain Service
   ↓
Email Service
   ↓
Mail Sender
```

For example:

```text
WelcomeEmailJobHandler
          ↓
sendWelcomeEmail()
          ↓
render template
          ↓
send through mail sender
```

This allows the same Email Service to be reused.

---

# 37. Don't duplicate business logic

Bad:

```text
HTTP signup
  ↓
Custom email logic

Worker
  ↓
Another custom email logic
```

Now you have two implementations.

Better:

```text
HTTP/Application
        │
        └──► create email job
                    │
                    ▼
                  Worker
                    │
                    ▼
              Email Service
```

One Email Service owns email-specific behavior.

# 44. Interview questions

### What is a background job?

A unit of work executed outside the main request lifecycle.

### What is a worker?

A process that retrieves and executes background jobs.

### What is a producer?

The component that creates/submits jobs.

### What is a consumer?

The component that processes jobs.

### What is a job payload?

The data required to perform the job.

### Why shouldn't jobs contain secrets?

Jobs may be persisted, logged, inspected, or transported through infrastructure.

### Why can a job execute more than once?

Failures can happen after work completes but before the system records the completion/acknowledgement.

### What is at-least-once processing?

The system tries to ensure the job is processed, but the same job may execute more than once in failure scenarios.

### Why use separate worker processes?

To isolate background workloads from HTTP traffic and scale them independently.

### Can a background job be delayed?

Yes. Job systems can support delayed execution.

# 45. The most important distinction

Keep this in your mind:

```text
async function
      ≠
background job
      ≠
queue
```

### `async/await`

Programming-language mechanism:

```js
await something();
```

### Background job

A unit of work processed outside the current request.

### Queue

Infrastructure that stores/manages jobs between producers and workers.

So:

```text
async/await
       ↓
JavaScript behavior

background job
       ↓
Application architecture

queue
       ↓
Infrastructure
```
