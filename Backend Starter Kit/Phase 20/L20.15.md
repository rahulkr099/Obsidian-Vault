# Lesson 20.15 — Build Email Architecture

This is the **final lesson of Phase 20**. The roadmap defines 20.15 specifically as **“Build email architecture”**, after covering SMTP, `mailSender`, templates, verification/reset/welcome emails, failures, async processing, background jobs, and queue fundamentals.

Now we connect everything into **one clean production-style flow**.

---

# 1. What are we building?

The final architecture is:

```text
                    HTTP REQUEST
                         │
                         ▼
                    Controller
                         │
                         ▼
                     Service
                         │
                  Create Email Job
                         │
                         ▼
                  ┌─────────────┐
                  │    QUEUE    │
                  └──────┬──────┘
                         │
                         ▼
                       WORKER
                         │
                         ▼
                  Email Job Handler
                         │
                         ▼
                   Email Service
                    /         \
                   /           \
                  ▼             ▼
        renderTemplate()    mailSender
                                │
                                ▼
                               SMTP
```

The important thing is that **the controller never directly sends the email**.

---

# 2. Why this architecture?

Your starter already separates mail-related functionality into:

```text
mail/
├── mailSender.js
├── renderTemplate.js
└── templates/
```

The roadmap specifically says that we should understand this existing architecture instead of treating it as mysterious.

We're now extending that idea with background processing:

```text
mail/
jobs/
services/
```

The goal is separation of responsibility.

---

# 3. The responsibilities

Let's define each part very clearly.

## Controller

Responsible for:

```text
HTTP
```

It should understand:

```text
req
res
status codes
```

It should **not** understand SMTP.

---

## Service

Responsible for:

```text
Business logic
```

For example:

```text
User registered
     ↓
Need welcome email
```

The service decides that an email job should be created.

---

## Queue producer

Responsible for:

```text
Creating/enqueuing email work
```

Example:

```text
WELCOME_EMAIL
```

---

## Queue

Responsible for:

```text
Holding jobs
```

---

## Worker

Responsible for:

```text
Taking jobs from the queue
```

---

## Job handler

Responsible for:

```text
Understanding what a particular job means
```

For example:

```text
WELCOME_EMAIL
       ↓
processWelcomeEmail()
```

---

## Email service

Responsible for:

```text
Preparing the email
```

It can coordinate:

```text
template
+
subject
+
recipient
+
mail sender
```

---

## Template renderer

Responsible for:

```text
Data
 ↓
HTML
```

---

## Mail sender

Responsible for:

```text
Actually sending the email
```

---

## SMTP

Responsible for:

```text
Transporting the email
```

# 4. The most important rule

Remember this:

> **Each layer should know only what it needs to know.**

For example:

```text
Controller
    ↓
doesn't know SMTP
```

```text
Queue
    ↓
doesn't know HTML templates
```

```text
Template renderer
    ↓
doesn't know HTTP
```

```text
SMTP sender
    ↓
doesn't know user registration
```

This is what makes the architecture maintainable.

# 7. Don't send email inside signup service

A beginner might write:

```js
async function signup(data) {
    const user = await createUser(data);

    await sendWelcomeEmail(user.email);

    return user;
}
```

This works technically.

But now signup is waiting for:

```text
SMTP
```

That's exactly the problem we studied in 20.12.

Instead:

```js
async function signup(data) {
    const user = await createUser(data);

    await emailQueue.add({
        type: "WELCOME_EMAIL",
        data: {
            userId: user.id,
            email: user.email,
            name: user.firstName
        }
    });

    return user;
}
```

Now:

```text
Signup
 ↓
Create user
 ↓
Create email job
 ↓
Return
```

The worker handles the email later.

---

# 8. Why put `userId` in the job?

You might wonder:

> "Why do we need `userId` if we already have email?"

Because a job often benefits from having an application-level reference.

For example:

```json
{
  "type": "WELCOME_EMAIL",
  "data": {
    "userId": "123",
    "email": "rahul@example.com",
    "name": "Rahul"
  }
}
```

Now logs can say:

```text
jobId: 5001
userId: 123
type: WELCOME_EMAIL
```

That makes debugging much easier.

---

# 9. Don't put sensitive information in the job

Avoid:

```json
{
  "password": "myPassword"
}
```

Never put:

```text
passwords
private keys
API secrets
unnecessary tokens
```

inside job payloads.

Keep the payload minimal.

For example:

```json
{
  "userId": "123",
  "email": "rahul@example.com",
  "name": "Rahul"
}
```

is much better.

# 13. Job handler

Conceptually:

```js
async function handleWelcomeEmail(job) {
    const { email, name } = job.data;

    await emailService.sendWelcomeEmail({
        email,
        name
    });
}
```

Notice what it doesn't do:

```text
❌ req.body
❌ res.status()
❌ Express
```

The worker isn't an HTTP controller.

# 14. Email service

Now:

```text
sendWelcomeEmail()
```

can coordinate the actual email preparation.

Conceptually:

```js
async function sendWelcomeEmail({ email, name }) {

    const html = await renderTemplate(
        "welcome",
        { name }
    );

    await mailSender.send({
        to: email,
        subject: "Welcome!",
        html
    });
}
```

Now our responsibilities are nicely separated.

# 21. Don't create a separate email system for every email

You don't want:

```text
welcomeMailer.js
verificationMailer.js
resetMailer.js
```

each implementing SMTP independently.

Instead:

```text
Email Service
├── sendWelcomeEmail()
├── sendVerificationEmail()
└── sendPasswordResetEmail()
```

and underneath:

```text
              Email Service
              /     |      \
             /      |       \
            ▼       ▼        ▼
       Welcome  Verify     Reset
            \      |       /
             \     |      /
              ▼    ▼     ▼
              mailSender
                   │
                   ▼
                  SMTP
```

This gives you one transport layer.

# 23. Email service vs mail sender

This distinction is extremely important.

### Email Service

Knows:

```text
What email are we sending?
Which template?
What subject?
What data?
```

### Mail Sender

Knows:

```text
How do we transport the email?
```

For example:

```text
Email Service
   ↓
"Send password reset email"
```

while:

```text
mailSender
   ↓
"Send this HTML through SMTP"
```

---

# 24. Why this separation is powerful

Suppose today you use:

```text
SMTP Provider A
```

and later switch to:

```text
Provider B
```

If your application directly uses SMTP everywhere:

```text
Signup → SMTP
Reset → SMTP
Verification → SMTP
Welcome → SMTP
```

you have lots of code to change.

With:

```text
Email Service
      ↓
mailSender
      ↓
SMTP
```

you can change the transport implementation while keeping the higher-level email operations mostly unchanged.

# 25. Failure handling

Now let's use what we learned in 20.11 and 20.14.

Suppose:

```text
Worker
 ↓
Email Service
 ↓
mailSender
 ↓
SMTP
 ↓
TIMEOUT ❌
```

The worker should report failure.

Then:

```text
Job
 ↓
Retry
```

For example:

```text
Attempt 1 ❌
    ↓
Backoff
    ↓
Attempt 2 ❌
    ↓
Backoff
    ↓
Attempt 3 ✅
```

If it still fails:

```text
Dead Letter Queue
```

The roadmap explicitly places email failures before async/background processing because the architecture needs to account for these failure modes.

---

# 26. Important: don't retry every error

Suppose:

```text
SMTP timeout
```

Retry may make sense.

But suppose:

```text
Invalid email address
```

Retrying won't necessarily fix anything.

So conceptually:

```text
Temporary failure
      ↓
Retry

Permanent failure
      ↓
Fail / investigate
```

Your job handler and queue strategy should eventually account for this.

---

# 27. Idempotency problem

Remember our previous lesson:

```text
A job can potentially execute more than once.
```

Imagine:

```text
Worker
 ↓
mailSender
 ↓
SMTP accepts email
 ↓
Worker crashes before ACK
```

The queue might retry:

```text
Worker 2
 ↓
Same job
 ↓
Send email again
```

Now:

```text
Email #1
Email #2
```

That's why production email architecture should consider duplicate processing.

# 31. What belongs in `jobs/producers/`?

The producer creates jobs.

For example:

```text
jobs/
└── producers/
    └── email.producer.js
```

Conceptually:

```js
createWelcomeEmailJob(...)
createVerificationEmailJob(...)
createPasswordResetEmailJob(...)
```

The producer should not actually send the email.

It only says:

> "Please process this work."

---

# 32. What belongs in `jobs/workers/`?

Workers consume jobs.

Conceptually:

```text
jobs/
└── workers/
    └── email.worker.js
```

Its responsibility:

```text
Listen for email jobs
        ↓
Receive job
        ↓
Send to appropriate handler
```

---

# 33. What belongs in `jobs/handlers/`?

Handlers contain job-specific processing.

For example:

```text
jobs/
└── handlers/
    ├── welcomeEmail.handler.js
    ├── verificationEmail.handler.js
    └── passwordResetEmail.handler.js
```

Conceptually:

```text
Worker
  ↓
Job type
  ↓
Correct handler
```

This prevents one giant worker file from becoming messy.

```text

 ↓

 ↓

 ↓

```

Better:

```text

 ↓

```

The two paths are loosely coupled.

# 37. What happens if the worker is down?

This is a very useful scenario.

Suppose:

```text
API Server       ✅
Queue            ✅
Worker           ❌
```

User signs up.

The API can still:

```text
Create user
Create email job
Return response
```

The job waits:

```text
Queue
 └── WELCOME_EMAIL
```

When the worker comes back:

```text
Worker
 ↓
Queue
 ↓
WELCOME_EMAIL
 ↓
Send
```

That's one of the biggest advantages of separating queue and worker processing.

---

# 38. What happens if SMTP is down?

Suppose:

```text
API          ✅
Queue        ✅
Worker       ✅
SMTP         ❌
```

Then:

```text
Worker
 ↓
Email
 ↓
SMTP ❌
 ↓
Retry
```

The signup itself doesn't necessarily have to fail.

That's exactly the resilience we wanted.

---

# 39. What happens if the queue is down?

This is a more serious case.

Suppose:

```text
API
 ↓
Queue ❌
```

Now the application cannot reliably enqueue the email job.

You need to decide what your application should do.

Possible strategies include:

```text
Fail the operation
+
Retry queue submission
+
Use an outbox pattern
```

This introduces a very important future concept:

> **Transactional Outbox**

We won't turn that into another Phase 20 lesson because it isn't specified in the roadmap, but it is a valuable production architecture topic to learn later.

---

# 40. The database + queue consistency problem

Consider:

```text
Create User
     ↓
SUCCESS
     ↓
Create Email Job
     ↓
FAIL ❌
```

Now:

```text
User exists
Email job doesn't
```

The user may never receive the email.

This is a classic distributed consistency problem.

For simple projects, you may accept some operational tradeoffs.

For more critical workflows, patterns such as an **outbox** can make event/job publication more reliable.

That's a major architectural win.

# 43. Email producer

The producer abstracts the queue.

Instead of:

```js

```

being scattered everywhere, you can have:

```js

Then your business logic says:

> "I want a welcome email."

rather than:

> "I know exactly which queue library and queue configuration to use."

This is a useful abstraction.

# 48. What you should be able to explain now

If an interviewer asks:

> **"How would you design email sending in a Node.js backend?"**

You should be able to answer:

> "I wouldn't send emails directly from the controller. The controller calls the service. After the relevant business operation succeeds, the service creates an email background job. The job is placed into a queue. A separate worker consumes the job and calls the appropriate email handler. The handler uses an email service, which renders the appropriate template and delegates transport to a mail sender using SMTP. Failed jobs can be retried with backoff, and permanently failing jobs can be moved to a dead-letter queue."

That is a **much stronger backend answer** than simply saying:

> "I use Nodemailer."

                 "process email"
                       │
                       ▼
                 EMAIL SERVICE
                       │
              ┌────────┴────────┐
              ▼                 ▼
          TEMPLATE          MAIL SENDER
              │                 │
              └────────┬────────┘
                       ▼
                      SMTP
```

And remember the reason:

> **The request path should be fast and focused on the business operation. Email is moved to background processing so slow or temporarily failing external email infrastructure doesn't unnecessarily block the user's request.**
