# Lesson 20.3 — Email Service Architecture

In **20.1**, we learned why email shouldn't be implemented directly inside controllers.

In **20.2**, we learned how SMTP works underneath the application.

Now we connect those two ideas:

> **Where exactly should email logic live inside our backend, and what should each part be responsible for?**

Your starter pack has a dedicated `mail/` layer with `mailSender.js`, `renderTemplate.js`, and templates.

The important thing is to understand **why those pieces are separated**.

---

# 1. The problem we're solving

Suppose we have:

```text
POST /api/v1/auth/signup
```

A user signs up.

We need to:

```text
1. Validate user
2. Create user
3. Generate verification token
4. Create verification URL
5. Create email
6. Render HTML
7. Connect to SMTP
8. Send email
```

If we put everything into the controller:

```js
export const signup = async (req, res) => {
    // validation
    // create user
    // token generation
    // email HTML
    // SMTP connection
    // send email
    // response
};
```

we've created a **giant responsibility problem**.

Instead, we'll divide the work.

---

# 2. The architecture

Our target architecture is:

```text
                   HTTP REQUEST
                        │
                        ▼
                    CONTROLLER
                        │
                        ▼
                    AUTH SERVICE
                        │
                        ▼
                  EMAIL SERVICE
                        │
                        ▼
                   MAIL SENDER
                        │
                        ▼
                       SMTP
```

But there is another branch:

```text
AUTH SERVICE
     │
     ├──────────────► USER REPOSITORY
     │                     │
     │                     ▼
     │                  MongoDB
     │
     └──────────────► EMAIL SERVICE
```

So the complete picture is:

```text
                  Controller
                      │
                      ▼
                 Auth Service
                 /          \
                /            \
               ▼              ▼
        User Repository   Email Service
               │              │
               ▼              ▼
            MongoDB       Mail Sender
                              │
                              ▼
                             SMTP
```

Each layer has a different responsibility.

---

# 3. Four important layers

For email, we'll mainly work with:

```text
Email Service
Mail Sender
Template Renderer
Templates
```

Think:

```text
Email Service
      ↓
"What email should happen?"

Template Renderer
      ↓
"Turn data into HTML"

Mail Sender
      ↓
"How do I deliver it?"

SMTP
      ↓
"Transport the message"
```

---

# 4. Email Service

Let's start with the most important layer.

Create:

```text
services/
└── email.service.js
```

The email service is the **application-facing interface for email operations**.

For example:

```js
emailService.sendVerificationEmail(user);
```

or:

```js
emailService.sendPasswordResetEmail(user, resetToken);
```

The caller doesn't need to know:

```text
SMTP host
SMTP port
SMTP credentials
HTML rendering
Transporter
```

That's the whole point.

---

# 5. What should Email Service know?

The email service can understand **application-level email concepts**.

For example:

```text
Verification Email
Password Reset Email
Welcome Email
Password Changed Email
```

So it can expose methods like:

```js
sendVerificationEmail()
sendPasswordResetEmail()
sendWelcomeEmail()
sendPasswordChangedEmail()
```

This is much nicer than exposing low-level SMTP details everywhere.

---

# 6. What should Email Service NOT know?

Ideally, the caller shouldn't need to provide:

```js
{
    host: "...",
    port: 587,
    username: "...",
    password: "...",
    secure: true
}
```

That's infrastructure configuration.

The email service should not make every application feature understand SMTP.

Instead:

```text
Application
     ↓
Email Service
     ↓
Mail Sender
     ↓
SMTP
```

---

# 7. "What" vs "How"

This distinction is worth repeating.

Suppose the application says:

```js
emailService.sendVerificationEmail(user);
```

The application is saying:

> **What should happen?**

Answer:

> Send a verification email.

Then the email service handles the application-level email operation.

The mail sender handles:

> **How should it be transported?**

That's:

```text
What?
 ↓
Email Service

How?
 ↓
Mail Sender
```

---

# 8. Mail Sender

Your starter pack has:

```text
mail/
└── mailSender.js
```

This is the lower-level transport layer.

Its responsibility is basically:

```text
Receive email message
        ↓
Send it through configured transport
```

For example, conceptually:

```js
await mailSender.send({
    from,
    to,
    subject,
    html
});
```

The mail sender knows how to communicate with the configured SMTP transport.

---

# 9. Why not call `mailSender` everywhere?

Imagine your auth service does:

```js
mailSender.send(...)
```

Your payment service also does:

```js
mailSender.send(...)
```

Your notification service does:

```js
mailSender.send(...)
```

Now every service has to understand the low-level email structure.

For example:

```js
{
    from,
    to,
    subject,
    html
}
```

That's not ideal.

Instead:

```text
Auth Service
    ↓
Email Service
    ↓
Mail Sender
```

and:

```text
Payment Service
    ↓
Email Service
    ↓
Mail Sender
```

This gives us one application-level email boundary.

---

# 10. Template Renderer

Your starter also contains:

```text
mail/
└── renderTemplate.js
```

This has another responsibility.

Suppose we have:

```text
templates/
└── verification.ejs
```

and data:

```js
{
    name: "Rahul",
    verificationUrl: "https://..."
}
```

The renderer does:

```text
Template
   +
Data
   ↓
Rendered HTML
```

For example:

```text
Template:

Hello <%= name %>

[Verify Email]
```

becomes:

```html
Hello Rahul

<a href="...">Verify Email</a>
```

---

# 11. Templates are presentation

This is another separation we want.

Don't put:

```html
<h1>Welcome Rahul</h1>
```

inside your service logic.

Instead:

```text
Email Service
     ↓
Select verification template
     ↓
Template Renderer
     ↓
HTML
```

The template owns the presentation.

---

# 12. The complete email pipeline

Now we can understand the whole system:

```text
Auth Service
     │
     │ sendVerificationEmail()
     ▼
Email Service
     │
     │ choose template + prepare data
     ▼
Template Renderer
     │
     │ rendered HTML
     ▼
Mail Sender
     │
     │ SMTP transport
     ▼
SMTP Server
```

This is a clean pipeline.

---

# 13. Example: Verification email

Imagine:

```js
await emailService.sendVerificationEmail(user);
```

Internally, conceptually:

```text
emailService
     │
     ├── Get user email
     ├── Get user name
     ├── Create verification URL
     ├── Select verification template
     │
     ▼
renderTemplate()
     │
     ▼
HTML
     │
     ▼
mailSender.send()
     │
     ▼
SMTP
```

The controller doesn't see any of this.

---

# 14. What belongs in Auth Service?

This is a very important boundary.

Consider:

```text
User signs up
```

The Auth Service can handle:

```text
Create user
Generate verification token
Store verification information
Request verification email
```

For example:

```js
const user = await userRepository.create(data);

await emailService.sendVerificationEmail(user);
```

The Auth Service knows:

> A newly registered user needs verification.

That's business/application logic.

---

# 15. What belongs in Email Service?

The Email Service handles:

```text
Verification email
Password reset email
Welcome email
```

It can determine:

```text
Which email type?
Which template?
Which email data?
Which subject?
```

For example:

```js
sendVerificationEmail(user)
```

could internally decide:

```text
Template:
verification.ejs

Subject:
Verify your email

Data:
name
verificationUrl
```

---

# 16. What belongs in Mail Sender?

The Mail Sender handles low-level delivery.

Conceptually:

```text
from
to
subject
html
```

and then:

```text
SMTP transport
```

It shouldn't care whether the email is:

```text
verification
welcome
password reset
payment receipt
```

It just receives a message and sends it.

---

# 17. Responsibility table

Keep this table in your notes:

|Component|Responsibility|
|---|---|
|Controller|HTTP request/response|
|Auth Service|Signup/login business logic|
|Email Service|Application-level email operations|
|Template Renderer|Convert template + data → HTML|
|Template|Email presentation|
|Mail Sender|Send email through transport|
|SMTP|Email transport protocol|

This is the architecture you should understand.

---

# 18. Why this makes testing easier

Suppose we test:

```text
Auth Service
```

We don't actually want our unit test to send a real email.

We can replace:

```text
Email Service
```

with a mock.

Conceptually:

```text
Auth Service
     │
     ▼
Mock Email Service
```

Then we can verify:

```text
Was verification email requested?
```

without contacting SMTP.

Similarly, we can test:

```text
Email Service
```

separately.

And:

```text
Mail Sender
```

separately.

This is one major benefit of separating responsibilities.

---

# 19. Why this makes provider changes easier

Imagine you initially use:

```text
SMTP Provider A
```

Later you move to:

```text
Provider B
```

If SMTP logic is spread throughout your controllers:

```text
auth.controller
user.controller
payment.controller
...
```

changing providers becomes painful.

But with:

```text
mailSender.js
```

you have an infrastructure boundary:

```text
Email Service
      ↓
Mail Sender
      ↓
Provider A
```

Later:

```text
Email Service
      ↓
Mail Sender
      ↓
Provider B
```

Most of the application remains unchanged.

---

# 20. Why this makes background jobs easier

This architecture becomes especially powerful when we introduce queues.

Currently:

```text
Auth Service
     ↓
Email Service
     ↓
Mail Sender
```

Later:

```text
Auth Service
     ↓
Email Job
     ↓
Queue
     ↓
Worker
     ↓
Email Service
     ↓
Mail Sender
```

Notice something:

**The Email Service doesn't need to become responsible for the queue.**

We can change how the work gets executed without completely rewriting email functionality.

That's good architecture.

# 23. Don't create an "Email God Service"

There's another architectural mistake.

Don't create one giant file:

```text
email.service.js
```

with:

```text
1000 lines
```

containing:

```text
SMTP configuration
templates
database queries
user creation
password reset logic
queue management
email rendering
```

That's just another form of bad architecture.

Separation should remain meaningful.

---

For our starter, the conceptual structure is:

Let's imagine:

```js
await emailService.sendVerificationEmail(user);
```

### Step 1 — Email Service

```text
sendVerificationEmail(user)
```

decides:

```text
subject = "Verify your email"

```

### Step 2 — Template Renderer

```text
verification.ejs
       +
user data
       ↓

```



# 26. Important boundary: email vs business logic

Consider password reset.

The **Auth Service** should decide:

```text
Does this user need a reset token?
Is the token valid?
Should the password be changed?
```

The **Email Service** should handle:

```text
How do we create/send the password reset email?
```

The **template** should handle:

```text
How does the email look?
```

The **Mail Sender** should handle:

```text
How does it get transported?
```

This gives us:

```text
Business
   ↓
Email operation
   ↓
Presentation
   ↓
Transport
```

---

# 27. Think in terms of dependencies

Our dependency direction should look like:

```text
Controller
    ↓
Application Service
    ↓
Email Service
    ↓
Mail Sender
    ↓
SMTP
```

Not:

```text
SMTP
    ↓
Controller
    ↓
Business logic
```

The lower-level infrastructure should not control the application's business flow.

---

# 28. Common mistakes

### ❌ Mistake 1

```text
Controller → SMTP
```

Too tightly coupled.

### ❌ Mistake 2

```text
Controller → HTML template
```

Presentation logic in the controller.

### ❌ Mistake 3

```text
Repository → Email Service
```

Repositories should primarily deal with data access.

### ❌ Mistake 4

```text
Email Service → MongoDB
```

Usually unnecessary coupling.

If the email needs user data, the application service can provide the required data.

### ❌ Mistake 5

```text
Mail Sender → decide business rules
```

The transport layer shouldn't decide:

> "Should this user receive a verification email?"

That's application logic.
