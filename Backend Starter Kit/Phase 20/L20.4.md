# Lesson 20.4 — Building `mailSender.js`

In the previous lesson, we designed this architecture:

```text
Controller
    ↓
Service
    ↓
Email Service
    ↓
Mail Sender
    ↓
SMTP
```

Now we focus on one specific component:

> **What should `mailSender.js` actually do?**

Your starter pack already contains a `mail/` layer with `mailSender.js`, so this lesson connects the architecture to that existing structure.

---

# 1. What is `mailSender.js`?

`mailSender.js` is our **email transport layer**.

Its job is intentionally small:

```text
Receive email message
        ↓
Send through configured mail transport
```

It should **not**:

- create users
    
- generate password-reset business logic
    
- decide whether a user needs an email
    
- contain controller logic
    
- contain large HTML templates
    

Its main responsibility is:

> **Take a prepared email and send it.**

---

# 2. Where does it sit?

Our architecture:

```text
                    APPLICATION
                         │
                         ▼
                    Auth Service
                         │
                         ▼
                    Email Service
                         │
                         ▼
                    Mail Sender
                         │
                         ▼
                  SMTP Transport
                         │
                         ▼
                    SMTP Server
```

The Mail Sender is near the bottom because it deals with infrastructure.

---

# 3. What information does it need?

A mail sender generally needs four important pieces of information:

```text
From
To
Subject
Body
```

For an HTML email:

```js
{
    from: "noreply@example.com",
    to: "rahul@example.com",
    subject: "Verify your email",
    html: "<h1>Verify your email</h1>"
}
```

The important thing is that `mailSender` receives a **prepared message**.

It doesn't need to understand why the message exists.

---

# 4. The mail sender should be generic

Suppose we have:

```js
mailSender.send({
    to: "rahul@example.com",
    subject: "Verify your email",
    html: "<h1>Verify your email</h1>"
});
```

The mail sender shouldn't care whether this is:

```text
Verification email
```

or:

```text
Password reset email
```

or:

```text
Welcome email
```

It simply sends it.

So:

```text
Email Service
    ↓
"What type of email is this?"
```

while:

```text
Mail Sender
    ↓
"Here is the message. I'll send it."
```

---

# 5. Why use a transporter?

In Node.js, we'll normally use a mail library to communicate with SMTP.

A common choice is **Nodemailer**.

The architecture becomes:

```text
mailSender.js
     │
     ▼
Nodemailer Transporter
     │
     ▼
SMTP Server
```

The transporter is basically a configured object that knows:

```text
SMTP host
SMTP port
Authentication
TLS/security settings
```

---

# 6. Conceptual implementation

Before writing the real implementation, understand the structure.

It might conceptually look like:

```js
const transporter = createTransport({
    host: SMTP_HOST,
    port: SMTP_PORT,
    auth: {
        user: SMTP_USER,
        pass: SMTP_PASSWORD
    }
});
```

Then:

```js
const send = async (mail) => {
    return transporter.sendMail(mail);
};
```

That's the basic idea.

Notice how small the actual transport layer can be.

---

# 7. Configuration should come from environment variables

We learned this in 20.2.

Don't do:

```js
const transporter = createTransport({
    host: "smtp.example.com",
    auth: {
        user: "my-email",
        pass: "my-password"
    }
});
```

Instead:

```env
SMTP_HOST=...
SMTP_PORT=...
SMTP_USER=...
SMTP_PASSWORD=...
MAIL_FROM=...
```

Then your configuration layer provides those values.

Conceptually:

```text
.env
 ↓
Configuration
 ↓
mailSender
 ↓
SMTP
```

---

# 8. Why `MAIL_FROM` is useful

Suppose all application emails should come from:

```text
noreply@example.com
```

Instead of repeating:

```js
from: "noreply@example.com"
```

everywhere, define:

```env
MAIL_FROM=noreply@example.com
```

Then:

```js
{
    from: MAIL_FROM,
    to,
    subject,
    html
}
```

This gives us centralized configuration.

---

# 9. A clean `mailSender` interface

I recommend keeping the public interface simple.

For example:

```js
export const sendMail = async ({
    to,
    subject,
    html,
    text
}) => {
    // send through transporter
};
```

Then the caller only needs to know:

```js
await sendMail({
    to: user.email,
    subject: "Verify your email",
    html
});
```

It doesn't need to know anything about:

```text
SMTP
Nodemailer
TLS
ports
transporters
```

That's abstraction.

---

# 10. Why accept `text` as well as `html`?

You may wonder why we don't only use:

```js
html
```

A good email can provide both:

```text
HTML version
+
Plain-text version
```

For example:

```js
{
    to: user.email,
    subject: "Verify your email",
    text: "Please verify your email using this link: ...",
    html: "<h1>Please verify your email</h1>"
}
```

This gives email clients an alternative representation.

The exact behavior depends on the recipient's mail client.

---

# 11. Don't put template logic here

This is a very important boundary.

Don't do this:

```js
const sendVerificationEmail = async (user) => {
    const html = `
        <h1>Hello ${user.name}</h1>
        <a href="${user.url}">
            Verify
        </a>
    `;

    await transporter.sendMail({
        ...
    });
};
```

Why?

Because now `mailSender` knows about:

```text
Verification
User
HTML
Business meaning
SMTP
```

That's too much.

Instead:

```text
Email Service
      ↓
Prepare email
      ↓
Render template
      ↓
Mail Sender
      ↓
SMTP
```

---

# 12. `mailSender` should be boring

This is actually a good thing.

A well-designed infrastructure component should often be boring.

We want:

```text
mailSender
    ↓
validate required message fields
    ↓
call transporter
    ↓
return result / throw error
```

Not:

```text
mailSender
    ↓
check user
    ↓
query database
    ↓
generate token
    ↓
render HTML
    ↓
decide business rules
    ↓
send
```

Keep the responsibility narrow.

---

# 13. What happens when `sendMail()` succeeds?

The mail library will normally return information about the send operation.

Conceptually:

```js
const result = await transporter.sendMail(mail);
```

We can then:

```js
return result;
```

or return only the useful parts through our own abstraction.

For example:

```js
return {
    messageId: result.messageId
};
```

The exact result depends on the mail library and provider.

---

# 14. What happens when sending fails?

This is extremely important.

Suppose:

```js
await transporter.sendMail(mail);
```

fails.

We shouldn't silently ignore it:

```js
try {
    await transporter.sendMail(mail);
} catch (error) {
    // nothing
}
```

That creates hidden failures.

Instead, the error should be:

```text
captured
      ↓
logged appropriately
      ↓
handled by the caller/worker
```

For example:

```js
try {
    return await transporter.sendMail(mail);
} catch (error) {
    throw new EmailSendError(
        "Failed to send email",
        { cause: error }
    );
}
```

We don't necessarily need a custom error on day one, but the important principle is:

> **Don't swallow infrastructure failures.**

---

# 15. Why throwing the error matters

Imagine:

```text
Email Service
      ↓
Mail Sender
      ↓
SMTP ❌
```

If `mailSender` swallows the error:

```text
SMTP failed
   ↓
mailSender says nothing
   ↓
Email Service thinks success happened
```

Now your system believes:

```text
Email sent ✓
```

when it actually failed.

That's dangerous.

Instead:

```text
SMTP failed
   ↓
mailSender throws
   ↓
Email Service knows
   ↓
Worker can retry later
```

This becomes extremely important once we introduce queues.

---

# 16. Error propagation

Think about the flow:

```text
SMTP
 ↓
Mail Sender
 ↓
Email Service
 ↓
Worker
```

If SMTP fails:

```text
SMTP
 ↓
throws error
 ↓
Mail Sender
 ↓
throws error
 ↓
Email Service
 ↓
throws error
 ↓
Worker
 ↓
retry
```

This is much better than silently hiding the failure.

---

# 17. What about logging?

We don't want `mailSender` dumping secrets into logs.

Never log:

```text
SMTP_PASSWORD
```

or sensitive authentication credentials.

Be careful even with email content.

A safe operational log might say:

```text
Email send failed
to=user@example.com
type=verification
error=connection timeout
```

rather than:

```text
password=...
smtp_password=...
full reset token=...
```

We'll connect this with the logging architecture from Phase 19.

---

# 18. The `mailSender` dependency

A clean dependency structure is:

```text
mailSender
   │
   ├── configuration
   │
   └── mail transport library
```

Not:

```text
mailSender
   │
   ├── User Model
   ├── Auth Service
   ├── Controller
   ├── Repository
   └── Database
```

The lower-level mail component shouldn't depend on unrelated application layers.

# 19. Testing `mailSender`

We also want to test this layer.

There are two useful kinds of testing.

### Unit testing

Mock the transporter:

```text
mailSender
    ↓
Mock transporter
```

Verify:

```text
Was sendMail called?
Were the correct fields passed?
```

### Integration testing

Use a controlled SMTP/test provider and verify that the actual transport works.

So:

```text
Unit Test
    ↓
No real email

Integration Test
    ↓
Controlled email environment
```

This separation is useful in real projects.

# 23. A practical implementation shape

A clean implementation could eventually look approximately like this:

```js
// mailSender.js

import nodemailer from "nodemailer";

const transporter = nodemailer.createTransport({
    host: config.smtp.host,
    port: config.smtp.port,
    secure: config.smtp.secure,
    auth: {
        user: config.smtp.user,
        pass: config.smtp.password
    }
});

export const sendMail = async ({
    to,
    subject,
    html,
    text
}) => {
    return transporter.sendMail({
        from: config.mail.from,
        to,
        subject,
        html,
        text
    });
};
```

**Important:** this is the architectural shape, not something you should blindly paste into the starter yet. We still need to decide how your project's configuration and error-handling layers are structured.

# 24. Why create the transporter once?

A common mistake is creating a new transporter every time:

```js
sendMail() {
    const transporter = createTransport(...);
    transporter.sendMail(...);
}
```

Conceptually, we generally want the configured transport to be created once and reused.

```text
Application starts
      ↓
Create transporter
      ↓
Reuse transporter
      ↓
Send mail
      ↓
Send mail
      ↓
Send mail
```

This avoids unnecessary setup work.

The exact connection pooling behavior depends on the transport configuration.

---

# 25. One transporter vs multiple providers

Later, a production application might need:

```text
Primary Email Provider
        │
        ▼
      Failure
        │
        ▼
Backup Provider
```

Or separate transports for different purposes.

But don't build that complexity now.

Start with:

```text
One mail sender
      ↓
One configured transport
```

Then evolve when there is a real requirement.

# 26. Common mistakes

### ❌ Mistake 1

Creating the transporter inside every request.

### ❌ Mistake 2

Hard-coding SMTP credentials.

### ❌ Mistake 3

Putting HTML templates inside `mailSender.js`.

### ❌ Mistake 4

Making `mailSender` query the database.

### ❌ Mistake 5

Swallowing SMTP errors.

### ❌ Mistake 6

Logging passwords or reset tokens.

### ❌ Mistake 7

Making every controller know how SMTP works.

---

# 27. Interview questions

### What is the responsibility of `mailSender.js`?

To provide the low-level mechanism for sending a prepared email through the configured mail transport.

### Should `mailSender.js` decide whether a verification email should be sent?

No.

### Should it generate password-reset tokens?

No.

### Should it contain email HTML?

Preferably no; templates/rendering should be separated.

### Why shouldn't SMTP configuration be hard-coded?

Because credentials and environment-specific configuration should be managed securely outside source code.

### Why should mail errors propagate?

Because higher layers or background workers need to know when delivery failed so they can handle, log, or retry it.
