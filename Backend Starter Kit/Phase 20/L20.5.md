In **20.4**, we built the mental model for `mailSender.js`:

```text

      ↓

      ↓

      ↓
SMTP
```

Now we're going to focus on the **template** part.

Your starter pack explicitly defines Phase 20 as **Email Architecture**, with:

```text
mail/
├── mailSender.js
├── renderTemplate.js
└── templates/
```

and the roadmap places **Email Templates** before the dedicated EJS and rendering lessons.

So today's goal is not yet to deeply learn EJS syntax. That's **20.6**.

Today's goal is:

> **Understand why email templates exist, what belongs inside them, and how they fit into the architecture.**

---

# 1. What is an email template?

An email template is a reusable structure that defines **how an email should look**.

For example, instead of putting this directly inside JavaScript:

```js
const html = `
    <html>
        <body>
            <h1>Hello Rahul</h1>
            <p>Please verify your email.</p>
        </body>
    </html>
`;
```

we create a separate template:

```text
mail/
└── templates/
    └── verification.ejs
```

Then JavaScript provides the data:

```text
name
verificationUrl
```

The template uses that data to produce the final HTML.

---

# 2. Why not write HTML inside JavaScript?

Imagine you have five email types:

```text
Verification
Password Reset
Welcome
Password Changed
Notification
```

If every email is written inside JavaScript:

```text
email.service.js
    ↓
HTML
HTML
HTML
HTML
HTML
```

the service becomes difficult to maintain.

You end up mixing:

```text
Business logic
+
Email logic
+
Presentation
```

That's exactly what we're trying to avoid.

---

# 3. Separate logic from presentation

This is the main lesson.

We want:

```text
Application logic
       ↓
Email Service
       ↓
Template
       ↓
HTML
```

The email template is responsible for:

> **How the email looks.**

The service is responsible for:

> **Why and when the email is being sent.**

---

# 4. Think about a website

You already know frontend development.

Imagine React.

You wouldn't normally put your entire page UI inside:

```js
handleSubmit()
```

You would separate:

```text
Component
    ↓
UI
```

Email templates follow a similar idea:

```text
Email Service
    ↓
Email Template
```

The service provides the data.

The template controls presentation.

---

# 5. Example: Verification email

Suppose a user registers.

The application has:

```js
{
    name: "Rahul",
    verificationUrl: "https://example.com/verify?token=..."
}
```

The template might conceptually look like:

```html
<h1>Hello {{name}}</h1>

<p>
    Please verify your email address.
</p>

<a href="{{verificationUrl}}">
    Verify Email
</a>
```

After rendering:

```html
<h1>Hello Rahul</h1>

<p>
    Please verify your email address.
</p>

<a href="https://example.com/verify?token=...">
    Verify Email
</a>
```

The template is therefore:

```text
Structure
+
Dynamic placeholders
```

---

# 6. Static vs dynamic content

An email usually contains both.

### Static content

Things that don't change:

```text
Verify your email
Please click the button below.
Thanks for joining us.
```

### Dynamic content

Things that change for each recipient:

```text
User name
Verification URL
Reset URL
Order number
Expiration time
```

So:

```text
Template
   +
Dynamic data
   ↓
Final email
```

This is the fundamental idea behind templating.

---

# 7. Why templates are reusable

Suppose 10,000 users receive verification emails.

We don't create 10,000 different HTML files.

We have:

```text
verification.ejs
```

and render it 10,000 times with different data.

For Rahul:

```text
name = Rahul
```

For another user:

```text
name = Priya
```

Same template:

```text
verification.ejs
```

Different data.

# 10. Template vs Email Service

This distinction is extremely important.

Suppose the user signs up.

The **Email Service** might say:

```text
Send verification email.
```

It decides:

```text
Email type = verification
```

Then it selects:

```text
verification.ejs
```

The template doesn't decide:

> "Should this user receive a verification email?"

That's not its job.

---

# 11. Responsibility of the template

The template should mainly answer:

> **How should this email be presented?**

For example:

```text
┌─────────────────────────────┐
│        My Application       │
│                             │
│ Hello Rahul                 │
│                             │
│ Please verify your email.   │
│                             │
│       [Verify Email]        │
│                             │
│ Thanks,                     │
│ My Application Team         │
└─────────────────────────────┘
```

That's presentation.

---

# 12. What should NOT be inside the template?

Don't put database queries in a template:

```js
// ❌ Bad idea
const user = await User.findById(...);
```

Don't put authentication logic:

```js
// ❌ Bad
if (user.role === "admin") {
   ...
}
```

Don't generate security tokens inside the HTML template.

Don't decide business operations.

The template should receive the data it needs.

---

# 13. Data should come from outside

A better flow:

```text
Auth Service
     ↓
Generate verification data
     ↓
Email Service
     ↓
Prepare template data
     ↓
Template Renderer
     ↓
Template
```

For example:

```js
{
    name: user.firstName,
    verificationUrl
}
```

Then the template consumes it.

---

# 14. Don't expose your database document directly

This is an important design improvement.

Avoid doing:

```js
renderTemplate("verification", user);
```

if `user` is your entire database document.

Why?

Because the template may now have access to things it doesn't need:

```text
password hash
refresh token hash
reset token
internal fields
timestamps
```

Instead, prepare a small template-data object:

```js
const templateData = {
    name: user.firstName,
    verificationUrl
};
```

Then:

```text
Template
   ↓
Only receives what it needs
```

This follows the principle of **least privilege / minimum necessary data**.

---

# 15. Template data as an interface

You can think of template data as a small contract.

For example:

```text
verification.ejs
expects:

name
verificationUrl
```

So the Email Service should provide exactly that:

```js
{
    name,
    verificationUrl
}
```

This is much cleaner than giving the template the entire application state.

---

# 16. Email templates can have different layouts

You may eventually want a common structure:

```text
Header
   ↓
Content
   ↓
Button
   ↓
Footer
```

For example:

```text
┌─────────────────────────────┐
│        MY APP LOGO          │
├─────────────────────────────┤
│                             │
│     Email-specific content  │
│                             │
├─────────────────────────────┤
│        Footer               │
└─────────────────────────────┘
```

Then multiple emails can share a consistent design.

We don't need to implement reusable layouts yet; first understand the basic template concept.

---

# 17. HTML email is different from a web page

This is an important practical point.

Email clients aren't browsers in the normal application-development sense.

Different clients have different HTML/CSS support.

Therefore, email HTML often needs to be more conservative than your React frontend.

For example, email design frequently relies heavily on:

```text
simple HTML
inline styles
tables for layout
limited CSS
```

You shouldn't assume:

```text
"Whatever works in Chrome will work exactly the same in every email client."
```

It won't.

---

# 18. Why email templates should be simple

A verification email doesn't need a huge frontend application.

Usually:

```text
Logo
 ↓
Short message
 ↓
Button
 ↓
Fallback link
 ↓
Footer
```

For example:

```text
Hello Rahul,

Thanks for creating your account.

[ Verify Email ]

If the button doesn't work, use this link:
https://...

This link expires after a limited period.

Thanks,
My Application
```

Simple is often better.

---

# 19. Always consider a fallback link

A good email shouldn't depend only on a button.

Imagine:

```text
[Verify Email]
```

doesn't render properly.

You can also provide:

```text
If the button doesn't work, copy and paste this URL:

https://example.com/verify?token=...
```

This improves usability.

---

# 20. HTML + plain text

As we discussed in 20.4, an email can have:

```text
HTML
+
Plain text
```

Your template system might eventually produce the HTML version while you separately prepare the plain-text version.

Conceptually:

```text
Template data
      │
      ├──────────────► HTML template
      │
      └──────────────► Plain text content
```

This makes the email more accessible across different clients and configurations.

---

# 21. Template naming

Use names that describe the email's purpose.

Good:

```text
verification.ejs
password-reset.ejs
welcome.ejs
password-changed.ejs
```

Less useful:

```text
email1.ejs
template2.ejs
newmail.ejs
test.ejs
```

The filename should tell another developer what the template represents.

---

# 22. Don't duplicate templates unnecessarily

Suppose:

```text
verification.ejs
verification-copy.ejs
verification-final.ejs
verification-final-new.ejs
```

This quickly becomes messy.

Instead, establish a clear template structure and update the appropriate template.

If multiple emails share common visual elements, later introduce reusable layouts/partials rather than copying hundreds of lines.

# 23. Template rendering flow

Now connect today's lesson with 20.4.

We have:

```text
Email Service
      │
      │ template + data
      ▼
renderTemplate()
      │
      ▼
verification.ejs
      │
      ▼
HTML
      │
      ▼

      │
      ▼

```

So:

```text

    = design

Renderer
    = turns design + data into HTML

Mail Sender
    = sends the result
```

This separation is extremely important.

# 25. Why use a template engine?

Without a template engine, you might manually build strings:

```js
const html =
    "<h1>Hello " +
    user.name +
    "</h1>";
```

This becomes ugly quickly.

A template engine lets you write something much closer to the final HTML:

```html
<h1>Hello <%= name %></h1>
```

and provide:

```js
{
    name: user.name
}
```

That's easier to read and maintain.

---

# 26. Template injection vs data

This is a security concept worth understanding early.

There is a big difference between:

```text
Template code
```

and:

```text
User data
```

For example:

```text
Template:
Hello <%= name %>
```

and:

```text
name:
Rahul
```

The user should provide **data**, not executable template code.

You should not dynamically treat arbitrary user input as a new template.

Bad conceptual design:

```text
User input
   ↓
Create template code
   ↓
Execute template
```

Better:

```text
Trusted template
   +
Untrusted data
   ↓
Rendered output
```

We'll discuss this more when we study EJS and rendering.

---

# 27. Template escaping

Another important security concept:

Suppose a user's name is:

```text
<script>...</script>
```

You don't want that to become executable HTML inside the email.

Template engines generally provide escaping mechanisms.

This is one reason we should understand the difference between:

```text
escaped output
```

and:

```text
raw/unescaped output
```

before using template syntax.

We'll study this carefully in **20.6**.

---

# 28. Email templates and security links

Verification and password-reset emails often contain URLs.

For example:

```text
https://frontend.example.com/reset?token=...
```

The URL is dynamic data.

The template should **display/use the provided URL**, not generate the security token itself.

The flow should be:

```text
Auth Service
     ↓
Generate token
     ↓
Create URL
     ↓
Email Service
     ↓
Template
```

Not:

```text
Template
     ↓
Generate password-reset token
```

Again, business/security logic stays outside presentation.

---

# 29. A good template-data boundary

Imagine:

```js
const emailData = {
    name: user.firstName,
    verificationUrl,
    supportEmail: config.mail.supportEmail
};
```

Then:

```text
verification.ejs
```

can use:

```text

```

Nothing more.

This gives us a clear interface.

# 31. Common mistakes

## ❌ Mistake 1 — HTML inside controller

```js
const html = `<h1>...</h1>`;
```

Avoid this for reusable production email templates.

---

## ❌ Mistake 2 — Database queries inside templates

```text
template → MongoDB
```

Don't do this.

---

## ❌ Mistake 3 — Business logic inside templates

For example:

```text
template decides whether user is authorized
```

No.

---

## ❌ Mistake 4 — Giving the entire user object to the template

Prefer:

```js
{
    name,
    verificationUrl
}
```

over:

```js
user
```

when only a few fields are needed.

---

## ❌ Mistake 5 — Treating user input as template code

User data should remain data.

Don't dynamically compile arbitrary user-provided template content.

---

## ❌ Mistake 6 — Assuming browser CSS works everywhere

Email clients have different capabilities.

Keep email HTML relatively conservative.
