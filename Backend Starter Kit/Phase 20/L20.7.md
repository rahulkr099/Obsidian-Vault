# Lesson 20.7 — Template Rendering

In **20.6**, we learned EJS syntax.

Now we connect EJS to the actual backend architecture.

The key question is:

> **Who takes an EJS template + data and turns it into final HTML?**

That is the job of:

```text
mail/renderTemplate.js
```

Your starter pack already separates `renderTemplate.js` from `mailSender.js` and the `templates/` directory.

---

# 1. The basic idea

We have:

```text
EJS Template
     +
Data
     ↓
Template Renderer
     ↓
HTML
```

For example:

```text
verification.ejs
        +
{
    name: "Rahul",
    verificationUrl: "..."
}
        ↓
renderTemplate()
        ↓
HTML
```

Then that HTML goes to the mail sender.

---

# 2. Why do we need `renderTemplate.js`?

You might wonder:

> Why not render the EJS template directly inside the Email Service?

You could technically do that.

But it would mix responsibilities.

Without a renderer:

```text
Email Service
   ├── decide email
   ├── find template
   ├── read file
   ├── compile EJS
   ├── render HTML
   └── send email
```

That's too much.

With a renderer:

```text
Email Service
   ↓
renderTemplate()
   ↓
Mail Sender
```

Much cleaner.

---

# 3. Three separate responsibilities

We now have three important components:

### Email Service

```text
"What email should be sent?"
```

### Template Renderer

```text
"Turn this template + data into HTML."
```

### Mail Sender

```text
"Send this HTML through SMTP."
```

This is the separation we want.

---

# 4. Complete flow

Suppose a user signs up.

```text
User
 ↓
Signup Controller
 ↓
Auth Service
 ↓
Email Service
 ↓
renderTemplate()
 ↓
verification.ejs
 ↓
HTML
 ↓
mailSender.sendMail()
 ↓
SMTP
```

Each layer has one clear job.

---

# 5. What does `renderTemplate()` need?

At minimum, it needs two things:

```text
Template
Data
```

For example:

```js
await renderTemplate(
    "verification",
    {
        name: user.firstName,
        verificationUrl
    }
);
```

Conceptually:

```text
"verification"
      +
templateData
      ↓
renderTemplate()
      ↓
HTML string
```

---

# 6. What is the template name?

We don't want callers to write:

```js
"/home/rahul/project/src/mail/templates/verification.ejs"
```

every time.

Instead, we can use:

```js
"verification"
```

The renderer knows where templates live.

For example:

```text
"verification"
      ↓
mail/templates/verification.ejs
```

This keeps callers simple.

---

# 7. Why centralize the template directory?

Imagine:

```text
Email Service
```

needs to know:

```text
mail/templates/verification.ejs
mail/templates/reset.ejs
mail/templates/welcome.ejs
```

Now the Email Service becomes tightly coupled to your filesystem.

Instead:

```text
Email Service
      ↓
renderTemplate("verification", data)
```

The renderer handles:

```text
template directory
template filename
EJS rendering
```

This is abstraction.

---

# 8. What happens internally?

Conceptually, `renderTemplate()` performs these steps:

```text
1. Receive template name
        ↓
2. Build template path
        ↓
3. Read template
        ↓
4. Pass data to EJS
        ↓
5. Generate HTML
        ↓
6. Return HTML
```

That's the entire responsibility.

---

# 9. Step 1 — receive template name

Example:

```js
renderTemplate("verification", data);
```

The renderer receives:

```text
templateName = "verification"
```

and:

```text
data = {
    name,
    verificationUrl
}
```

---

# 10. Step 2 — build template path

The renderer needs to locate:

```text
mail/templates/verification.ejs
```

A production-friendly approach is to build paths using Node's path utilities rather than manually concatenating strings.

Conceptually:

```js
const templatePath = path.join(
    templatesDirectory,
    `${templateName}.ejs`
);
```

This is safer and more portable than:

```js
const templatePath =
    "mail/templates/" + templateName + ".ejs";
```

---

# 11. Why `path.join()`?

Your application may run on:

```text
Linux
Windows
macOS
Docker
CI environment
```

Path separators can differ.

Using Node's path utilities lets Node handle the platform-specific details.

So prefer:

```js
path.join(...)
```

over manually constructing filesystem paths.

---

# 12. Step 3 — read the template

The renderer now needs the actual EJS file.

Conceptually:

```js
const template = await fs.readFile(
    templatePath,
    "utf8"
);
```

Now:

```text
templatePath
      ↓
verification.ejs
      ↓
template source
```

The result is a string containing the EJS markup.

For example:

```ejs
<h1>Hello <%= name %></h1>

<a href="<%= verificationUrl %>">
    Verify Email
</a>
```

---

# 13. Step 4 — give the template to EJS

Now EJS receives:

```text
Template source
+
Data
```

For example:

```js
ejs.render(template, data);
```

Conceptually:

```text
<h1>Hello <%= name %></h1>
             +
{name: "Rahul"}
             ↓
<h1>Hello Rahul</h1>
```

That's the actual rendering step.

---

# 14. Step 5 — return HTML

After EJS renders the template:

```js
const html = ejs.render(template, data);
```

we get:

```html
<h1>Hello Rahul</h1>

<a href="https://example.com/verify/...">
    Verify Email
</a>
```

The renderer returns it:

```js
return html;
```

---

# 15. The entire renderer concept

So the mental model is:

```js
async function renderTemplate(templateName, data) {
    const templatePath = ...;

    const template = await readFile(
        templatePath,
        "utf8"
    );

    return ejs.render(template, data);
}
```

This is the core idea.

The exact implementation in your project may use a slightly different approach, but the responsibility remains the same.

---

# 16. Why return a string?

Because the next layer needs the HTML.

```text
renderTemplate()
      ↓
HTML string
      ↓
mailSender
```

So:

```js
const html = await renderTemplate(
    "verification",
    data
);
```

Then:

```js
await sendMail({
    to,
    subject,
    html
});
```

This creates a very clean boundary.

# 18. Then the mail sender takes over

Now:

```js
await mailSender.sendMail({
    to: user.email,
    subject: "Verify your email",
    html
});
```

So the two components have very different jobs:

```text
renderTemplate()
    ↓
HTML generation

mailSender.sendMail()
    ↓
Email delivery
```

Don't mix them.

---

# 19. Why not make `renderTemplate()` send email?

Avoid this:

```js
renderTemplateAndSendEmail(...)
```

because then one function does:

```text
filesystem
+
EJS
+
email transport
```

That's too much responsibility.

Instead:

```text
renderTemplate()
```

only renders.

And:

```text
sendMail()
```

only sends.

---

# 20. Error handling

Rendering can fail.

For example:

```text
Template doesn't exist
```

or:

```text
Invalid EJS syntax
```

or:

```text
Template expects a variable that wasn't provided
```

These errors should not silently disappear.

Bad:

```js
try {
    return ejs.render(...);
} catch {
    return "";
}
```

This is dangerous.

Now the application could send an empty email and think everything worked.

---

# 21. Better error flow

Instead:

```text
Template error
      ↓
renderTemplate throws
      ↓
Email Service receives error
      ↓
caller/worker handles it
```

For example:

```js
try {
    const html = await renderTemplate(
        "verification",
        data
    );
} catch (error) {
    // handle or propagate
}
```

The exact logging strategy belongs to the broader application architecture.

---

# 22. Missing template

Imagine:

```js
renderTemplate("verificaton", data);
```

Notice the typo:

```text
verificaton
```

instead of:

```text
verification
```

The renderer will try to find:

```text
verification? No.

verificaton.ejs
```

If that file doesn't exist, rendering fails.

This is actually good.

We want the application to know:

```text
Template not found
```

rather than silently continuing.

---

# 23. Missing template data

Suppose the template contains:

```ejs
<h1>Hello <%= name %></h1>
```

but the service passes:

```js
{}
```

Depending on the EJS configuration and expression, this can result in missing/undefined output or an error.

The larger lesson is:

> **Template data should have a clear contract.**

If `verification.ejs` requires:

```text
name
verificationUrl
```

the caller should provide them.

---

# 24. Template contract

Think of this:

```text
verification.ejs
```

as having an informal interface:

```text
Input:
    name: string
    verificationUrl: string

Output:
    HTML string
```

That's very similar to a function.

For example:

```text
renderVerificationEmail(data)
```

Conceptually:

```text
data
 ↓
template
 ↓
HTML
```

This mental model makes template architecture much easier.

---

# 25. Should we validate template data?

There are two levels.

### Simple projects

The service constructs the correct data object.

```js
{
    name,
    verificationUrl
}
```

That's often enough.

### Larger systems

You may explicitly validate the template data:

```text
name → required string
verificationUrl → required URL
```

This can be useful when there are many templates or multiple callers.

We don't need to over-engineer this immediately.

---

# 26. Security: template path handling

There's an important security concern here.

Suppose the renderer accepts:

```js
renderTemplate(templateName, data);
```

and someone somehow controls:

```text
templateName = "../../some-sensitive-file"
```

You don't want your renderer blindly reading arbitrary files.

So the renderer should treat the template name as a **controlled internal identifier**, not arbitrary user input.

Good:

```js
renderTemplate("verification", data);
```

Bad:

```js
renderTemplate(req.body.template, data);
```

unless you have strict validation/allowlisting.

---

# 27. Allowlisting template names

For a larger production system, you can make the allowed templates explicit:

```js
const templates = {
    verification: "verification.ejs",
    passwordReset: "password-reset.ejs",
    welcome: "welcome.ejs"
};
```

Then:

```text
verification
     ↓
allowed
     ↓
verification.ejs
```

while:

```text
../../etc/passwd
     ↓
rejected
```

This is a strong security pattern.

---

# 28. Why this matters

A template renderer deals with:

```text
filesystem
+
template compilation
```

Those are powerful capabilities.

We should therefore keep its input controlled.

The ideal flow is:

```text
Application code
      ↓
Known template identifier
      ↓
Renderer
      ↓
Known template directory
```

not:

```text
HTTP user input
      ↓
arbitrary filesystem path
```

---

# 29. Async vs synchronous file reading

You might see:

```js
fs.readFile(...)
```

or:

```js
fs.readFileSync(...)
```

For server-side applications, asynchronous filesystem operations are generally preferred for request-sensitive paths because they don't block the Node.js event loop while waiting for I/O.

So conceptually:

```js
await fs.readFile(...)
```

is a good pattern.

However, EJS and filesystem caching can change the optimal implementation, especially once we discuss production optimization.

---

# 30. Should we read the template on every email?

Conceptually, the simplest implementation does:

```text
Every email
    ↓
Read file
    ↓
Render
```

But if your application sends lots of emails, repeatedly reading the same template can be wasteful.

Later we can consider:

```text
Application startup / first use
        ↓
Load template
        ↓
Cache
        ↓
Reuse
```

This is one of the optimizations that becomes more interesting in production.

---

# 31. Development vs production

During development:

```text
Template changes frequently
```

You may prefer behavior that reads the latest template.

In production:

```text
Templates rarely change while process is running
```

Caching can be beneficial.

So don't blindly optimize too early.

First:

```text
Correctness
```

Then:

```text
Performance
```

---

# 32. Template rendering vs template compilation

These terms are related but not exactly identical.

### Template

```text
verification.ejs
```

contains:

```ejs
Hello <%= name %>
```

### Compilation

EJS can turn the template into executable rendering logic.

### Rendering

That compiled/template logic is applied to:

```js
{name: "Rahul"}
```

to produce:

```html
Hello Rahul
```

Conceptually:

```text
Template
   ↓
Compile
   ↓
Rendering function
   ↓
Data
   ↓
HTML
```

You don't need to manually manage compilation yet, but understanding the distinction helps when we later discuss caching.

And:

```text

        │
```

That's a clean infrastructure boundary.

---

# 34. Example `renderTemplate.js` shape

A simplified implementation could look like:

```js
import fs from "node:fs/promises";
import path from "node:path";
import ejs from "ejs";

const templatesDirectory = path.resolve(
    "src/mail/templates"
);

export async function renderTemplate(
    templateName,
    data
) {
    const templatePath = path.join(
        templatesDirectory,
        `${templateName}.ejs`
    );

    const template = await fs.readFile(
        templatePath,
        "utf8"
    );

    return ejs.render(template, data);
}
```

Again, this is the **conceptual implementation shape**.

In the actual project, we should align the path resolution and configuration with your existing source structure rather than blindly copying this path.

---

# 35. A production improvement: `ejs.renderFile()`

EJS also provides a mechanism that can render a file directly.

Conceptually:

```js
ejs.renderFile(
    templatePath,
    data
);
```

This can simplify the implementation because we don't have to manually:

```text
read file
   ↓
pass string to ejs
```

The important thing isn't memorizing one API.

The important thing is understanding:

```text
template path
+
data
↓
EJS
↓
HTML
```

# 36. Should `renderTemplate()` know about users?

No.

Bad:

```js
renderTemplate("verification", userId);
```

and then:

```text
renderTemplate
    ↓
Database
    ↓
User
    ↓
Generate URL
    ↓
Render
```

That couples rendering to the database.

Better:

```js
renderTemplate("verification", {
    name,
    verificationUrl
});
```

Now the renderer is completely independent of your database.

---

Imagine testing:

```js
renderTemplate("verification", {
    name: "Rahul",
    verificationUrl: "https://example.com/verify/test"
});
```

You don't need:

```text
MongoDB
User model
Authentication
JWT
HTTP request
```

You only need:

```text
Template
+
Data
```

That's a huge testing advantage.

# 38. Unit testing the renderer

A basic test might verify:

```text
Given:
name = Rahul

When:
verification template is rendered

Then:
output contains "Rahul"
```

Another:

```text
Given:
verificationUrl = test URL

Then:
output contains the expected URL
```

Another:

```text
Given:
invalid template

Then:
renderer throws an error
```

This gives us confidence in the infrastructure layer.

# 39. Testing escaping

Because we learned EJS security in 20.6, we should also test escaping behavior.

Suppose:

```js
name = "<script>attack</script>"
```

The rendered output should not treat that as trusted HTML when using:

```ejs
<%= name %>
```

This is a very useful security-focused test.

# 40. Common mistakes

### ❌ Mistake 1

Putting SMTP code inside `renderTemplate.js`.

No.

```text
renderTemplate → HTML
mailSender → SMTP
```

---

### ❌ Mistake 2

Putting database queries in the renderer.

No.

---

### ❌ Mistake 3

Accepting arbitrary filesystem paths.

Avoid.

---

### ❌ Mistake 4

Swallowing template errors.

Don't.

---

### ❌ Mistake 5

Passing the entire database object.

Pass only required data.

---

### ❌ Mistake 6

Hardcoding template paths everywhere.

Centralize template-directory handling.
