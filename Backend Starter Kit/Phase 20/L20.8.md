---

# 1. What is a verification email?

When a user creates an account, we usually don't want to immediately assume that the email address is valid.

Instead:

```text
User Signup
    ↓
Create account
    ↓
Generate verification token
    ↓
Create verification URL
    ↓
Send verification email
    ↓
User clicks link
    ↓
Backend verifies token
    ↓
Email marked as verified
```

The important point is:

> **Email verification connects authentication, security, email architecture, and token handling.**

---

# 2. Why do we verify email addresses?

Suppose someone creates:

```text
email = someone@example.com
```

How do we know they actually control that email address?

We don't.

The verification process proves that the person can access the mailbox.

So verification can help prevent:

```text
Fake email addresses
Mistyped email addresses
Some forms of account abuse
Accounts created using someone else's address
```

It also allows your application to safely use email for things like:

```text
Password reset
Important notifications
Account recovery
```

---

# 3. Verification is NOT just an email feature

This is important.

The email itself is only the **delivery mechanism**.

The actual security flow is:

```text
Authentication system
        ↓
Verification token
        ↓
Verification URL
        ↓
Email
        ↓
User clicks
        ↓
Verification endpoint
```

So don't think:

```text
"Verification = EJS template"
```

Think:

```text
Verification
    =
Security flow
    +
Token
    +
Email delivery
    +
Verification endpoint
```

# 5. Verification token

We need some value that proves:

> "This person received the verification email."

Conceptually:

```text
verification token
        ↓
verification URL
        ↓
email
```

For example:

```text
https://example.com/verify-email?token=abc123
```

The exact token-generation design will depend on the authentication architecture you're building.

The important thing is:

> **The token must be unpredictable.**

Don't create something like:

```text
token = userId
```

or:

```text
token = email
```

Those aren't secrets.

---

# 6. Don't use predictable verification tokens

Bad:

```text
https://example.com/verify?token=12345
```

if the token can easily be guessed.

Also bad:

```text
https://example.com/verify?token=user123
```

A verification token should be generated using a cryptographically secure mechanism.

Think:

```text
Secure random value
        ↓
Verification token
```

---

# 7. Token vs user ID

This distinction is very important.

Suppose:

```text
userId = 64abc...
```

That's an identifier.

It isn't necessarily a secret.

A verification token should be:

```text
random
unpredictable
single-purpose
time-limited
```

So:

```text
userId
≠
verification token
```

---

# 8. Where should the token be stored?

There are several possible designs.

A common secure architecture is:

```text
Generate verification token
        ↓
Store a hash of the token
        ↓
Send the original token in email
```

Conceptually:

```text
Original token
      │
      ├──────────────► Email URL
      │
      ▼
   Hash token
      │
      ▼
   Database
```

Then when the user clicks the link:

```text
Token from URL
      ↓
Hash it
      ↓
Compare with stored hash
```

This means the database doesn't need to contain the raw verification secret.

---

# 9. Why hash the verification token?

Imagine your database contains:

```text
verificationToken = abc123
```

If someone obtains that database value, they may be able to construct:

```text
/verify?token=abc123
```

and verify the account.

If instead you store:

```text
hash(abc123)
```

the database contains a derived value rather than the original secret.

This follows the same security thinking we learned for refresh tokens.

---

# 10. Verification token expiration

Verification links shouldn't necessarily work forever.

For example:

```text
Token created
      ↓
Valid for limited period
      ↓
Expires
```

The exact expiration duration is an application decision.

The important architectural idea is:

```text
token
+
expiration
```

For example, conceptually:

```js
{
    verificationTokenHash,
    verificationTokenExpiresAt
}
```

---

# 11. Why expiration matters

Suppose someone receives an email containing a verification link and never clicks it.

If that link worked forever:

```text
Old verification link
       ↓
Still valid months later
```

That's undesirable.

Instead:

```text
Verification link
       ↓
Expires
       ↓
User requests a new one
```

This limits the lifetime of the credential.

# 17. Generate verification URL

Suppose we generate:

```text
randomToken
```

Then create:

```text
verificationUrl
```

Conceptually:

```text
https://frontend.example.com/verify-email?token=<token>
```

Notice something important:

> The URL doesn't have to point directly to your backend.

It can point to your frontend, which then calls the backend verification endpoint.

The exact architecture depends on your application.

---

# 18. Two common verification flows

### Flow A — Backend URL

```text
Email
 ↓
GET /api/v1/auth/verify-email?token=...
 ↓
Backend verifies
 ↓
Redirect to frontend
```

### Flow B — Frontend URL

```text
Email
 ↓
Frontend /verify-email?token=...
 ↓
Frontend sends token to backend
 ↓
Backend verifies
 ↓
Frontend shows result
```

Both can work.

For a MERN application, the second approach is often convenient because the frontend controls the user experience.

# 19. Email Service

After generating the URL:

```text
Auth Service
     ↓
Email Service
```

The Email Service shouldn't generate the authentication token itself.

Instead, give it the information it needs:

```js
await emailService.sendVerificationEmail({
    email: user.email,
    name: user.firstName,
    verificationUrl
});
```

This is clean separation.

---

# 20. Why shouldn't Email Service generate the token?

Because:

```text
Token generation
```

belongs to the authentication/security domain.

While:

```text
Email formatting + sending
```

belongs to the email domain.

So:

```text
Auth Service
    ↓
creates security data

Email Service
    ↓
delivers security data
```

This separation makes the system easier to reason about.

---

# 21. Email Service implementation concept

Conceptually:

```js
async function sendVerificationEmail({
    email,
    name,
    verificationUrl
}) {
    const html = await renderTemplate(
        "verification",
        {
            name,
            verificationUrl
        }
    );

    await mailSender.sendMail({
        to: email,
        subject: "Verify your email",
        html
    });
}
```

Notice the responsibility:

```text
Email Service
    ↓
Choose template
    ↓
Prepare template data
    ↓
Render
    ↓
Send
```

It doesn't:

```text
❌ query MongoDB
❌ hash password
❌ generate JWT
❌ authenticate user
```

# 23. Verification endpoint

Eventually we need something like:

```http
GET /api/v1/auth/verify-email?token=...
```

or:

```http
POST /api/v1/auth/verify-email
```

depending on your API design.

The endpoint receives the token.

Then:

```text
Token
 ↓
Hash token
 ↓
Find matching user
 ↓
Check expiration
 ↓
Mark email verified
 ↓
Remove verification token
```

---

# 24. Why remove the token?

Verification should normally be a **one-time action**.

Before verification:

```text
emailVerified = false
verificationTokenHash = ...
```

After successful verification:

```text
emailVerified = true
verificationTokenHash = null
verificationTokenExpiresAt = null
```

Conceptually:

```text
Unused token
    ↓
Successful verification
    ↓
Token invalidated
```

This prevents reuse.

# 26. What happens if the token is invalid?

Suppose someone sends:

```text
/verify-email?token=randomFakeValue
```

The backend should not verify the account.

Conceptually:

```text
Token
 ↓
Hash
 ↓
Database lookup
 ↓
No matching token
 ↓
Verification fails
```

Return an appropriate error response.

Don't reveal unnecessary information about internal authentication state.

---

# 27. What if the token expired?

Flow:

```text
Token
 ↓
Find user
 ↓
Check expiration
 ↓
Expired
 ↓
Reject
```

The user can then request a new verification email.

# 28. Resend verification email

A useful feature is:

```http
POST /api/v1/auth/resend-verification
```

Flow:

```text
User
 ↓
Request resend
 ↓
Find account
 ↓
Generate new token
 ↓
Invalidate old token
 ↓
Store new hash
 ↓
Send new email
```

The old verification link should no longer be usable.

---

# 29. Don't allow unlimited resend requests

Imagine someone repeatedly requests:

```text
/resend-verification
```

1000 times.

That could cause:

```text
Email spam
SMTP usage
Application abuse
Rate-limit problems
```

So combine verification with your existing security architecture:

```text
Request
 ↓
Rate limiter
 ↓
Validation
 ↓
Auth Service
```

This connects Phase 20 with the security work you've already studied.

---

# 30. What should the response say?

Be careful with account enumeration.

For example, an attacker could try:

```text
Does rahul@example.com have an account?
Does priya@example.com have an account?
Does amit@example.com have an account?
```

If your endpoint responds differently for existing vs nonexistent accounts, it may reveal information.

A safer design can use a generic response such as:

```text
"If the account exists, a verification email has been sent."
```

The exact response strategy depends on your application's threat model.

# 31. Verification and authentication

Should an unverified user be allowed to log in?

There isn't one universal answer.

Possible policies:

### Policy A

```text
Signup
 ↓
Account created
 ↓
Cannot access application until verified
```

### Policy B

```text
Signup
 ↓
Account created
 ↓
Can log in
 ↓
Restricted until email verified
```

### Policy C

```text
Signup
 ↓
Account created
 ↓
Normal access
 ↓
Verification requested for sensitive operations
```

For most applications, you should explicitly decide what your product requires instead of accidentally allowing everything.

# 33. Authentication vs email verification

Authentication answers:

> **Who are you?**

Email verification answers:

> **Do you control this email address?**

Authorization answers:

> **What are you allowed to do?**

So:

```text
Authentication
      +
Email Verification
      +
Authorization
```

are separate concepts.

# 34. Security considerations

Verification links contain a credential.

Treat the token as sensitive.

Avoid:

```text
Logging the full verification URL
```

For example, don't casually log:

```text
verificationUrl=https://...token=abc123
```

because logs may be accessible to developers, monitoring systems, or third parties.

Instead, log something like:

```text
verification email generated
userId=...
```

without the secret token.

This connects directly to the logging/security principles you covered in Phase 19.

---

# 35. Don't put the token in unnecessary places

The token should appear where it needs to:

```text
Email URL
```

and temporarily exist in the relevant authentication flow.

Avoid storing it in:

```text
logs
analytics
error messages
unrelated database fields
```

The less exposure, the better.

# 42. Interview questions

### 1. Why do we verify email addresses?

To establish that the user controls the email address associated with the account.

### 2. Is email verification authentication?

No.

### 3. Should a verification token be predictable?

No. It should be generated using a secure random mechanism.

### 4. Should verification tokens expire?

Yes, normally they should have a limited lifetime.

### 5. Should the raw token be stored in the database?

A stronger design is to store a hash of the token rather than the raw token.

### 6. Should EJS generate the verification token?

No. Token generation belongs to the authentication/security layer.

### 7. What happens after successful verification?

The account is marked verified and the verification credential should be invalidated.
