# Lesson 20.9 — Password Reset Emails

Your Phase 20 roadmap defines **20.9 as Password Reset Emails**, immediately after verification emails and before welcome emails.

This lesson is important because password reset is one of the most security-sensitive email flows in a backend.

---

## 1. What is a password reset email?

Suppose a user forgets their password.

They click:

```text
Forgot Password?
```

Then:

```text
User
 ↓
Enter email
 ↓
Backend generates reset token
 ↓
Reset email sent
 ↓
User clicks reset link
 ↓
Backend validates token
 ↓
User chooses new password
 ↓
Password is hashed
 ↓
Password updated
```

The key idea:

> **The email doesn't reset the password. It gives the user a temporary credential that allows the password-reset flow to continue.**

---

# 2. Password reset vs email verification

They look similar:

```text
Verification:
Signup
 ↓
Token
 ↓
Email
 ↓
Verify account
```

Password reset:

```text
Forgot password
 ↓
Token
 ↓
Email
 ↓
Set new password
```

But password reset has an important difference:

> **A successful password reset changes a user's authentication credential.**

Therefore, we need to be especially careful with:

- token security
    
- expiration
    
- token reuse
    
- account enumeration
    
- password hashing
    
- session/token invalidation
    

---

# 4. Step 1 — Forgot Password endpoint

A typical endpoint might be:

```http
POST /api/v1/auth/forgot-password
```

Request:

```json
{
  "email": "rahul@example.com"
}
```

The backend receives the email.

---

# 5. Don't immediately say "email doesn't exist"

This is a very important security concept.

Imagine an attacker sends:

```text
POST /forgot-password
email=alice@example.com
```

and gets:

```text
Account exists.
```

Then:

```text
email=bob@example.com
```

gets:

```text
Account does not exist.
```

The attacker can now discover which email addresses have accounts.

This is called **account enumeration**.

So a safer response is something like:

```text
"If an account exists for this email,
a password reset link has been sent."
```

Same response whether the account exists or not.

---

# 6. The flow when the account exists

Suppose:

```text
rahul@example.com
```

belongs to a user.

The service does:

```text
Find user
 ↓
Generate secure random token
 ↓
Hash token
 ↓
Store hash + expiration
 ↓
Create reset URL
 ↓
Send email
```

---

# 7. Generate a reset token

The reset token should be:

```text
Random
Unpredictable
High entropy
Time-limited
Single-purpose
```

Conceptually:

```text
randomToken
```

might look like:

```text
x8K2...very-long-random-value...
```

Don't use:

```text
userId
```

or:

```text
email
```

as the reset token.

Those are identifiers, not secure secrets.

---

# 8. Hash the reset token

A strong architecture is:

```text
Original token
       │
       ├───────────────► Reset URL
       │
       ▼
     Hash
       │
       ▼
   Database
```

For example:

```text
Database:

resetTokenHash = hash(token)
resetTokenExpiresAt = ...
```

The user receives the original token.

The database stores the derived hash.

---

# 9. Why not store the raw token?

Imagine your database contains:

```text
resetToken = ABC123
```

If someone obtains the database data, they potentially have a usable password-reset credential.

Instead:

```text
resetTokenHash = hash(ABC123)
```

The raw reset credential isn't sitting in the database.

This follows the same principle we discussed with verification tokens.

---

# 10. Reset token expiration

A reset link should be temporary.

Conceptually:

```text
Token created
     ↓
Valid
     ↓
Expiration time reached
     ↓
Invalid
```

For example, your application might choose a relatively short reset window.

The exact duration should be decided by your security/product requirements.

The important thing is:

> **A password-reset token should not remain valid indefinitely.**

---

# 11. Create the reset URL

After generating the token:

```text
resetToken
```

we create something like:

```text
https://frontend.example.com/reset-password?token=...
```

The frontend can then show:

```text
New Password
Confirm Password
```

---

# 12. Why put the token in the URL?

Because the user needs a way to prove:

> "I received the reset email."

The token travels from:

```text
Backend
 ↓
Email
 ↓
User's browser
 ↓
Reset endpoint
```

So the token acts as a temporary credential.

---

# 13. Password reset email template

Our EJS template could be:

```text
mail/templates/password-reset.ejs
```

Example:

```ejs
<!DOCTYPE html>
<html>
<head>
    <meta charset="UTF-8">
    <title>Reset your password</title>
</head>

<body>

    <h1>Hello <%= name %></h1>

    <p>
        We received a request to reset your password.
    </p>

    <p>
        Click the button below to choose a new password.
    </p>

    <p>
        <a href="<%= resetUrl %>">
            Reset Password
        </a>
    </p>

    <p>
        If you didn't request a password reset,
        you can safely ignore this email.
    </p>

</body>
</html>
```

Notice the same architecture from 20.8:

```ejs
<%= name %>
```

and:

```ejs
<%= resetUrl %>
```

# 14. Email Service

The Email Service can expose something like:

```js
async function sendPasswordResetEmail({
    email,
    name,
    resetUrl
}) {
    const html = await renderTemplate(
        "password-reset",
        {
            name,
            resetUrl
        }
    );

    await mailSender.sendMail({
        to: email,
        subject: "Reset your password",
        html
    });
}
```

Notice what it **doesn't** do:

```text
❌ Generate reset token
❌ Query MongoDB
❌ Update password
❌ Verify the token
```

It handles the email side.

---

# 15. Why should Auth Service generate the token?

Because reset tokens are authentication/security credentials.

So:

```text
Auth Service
    ↓
Generate reset credential
```

while:

```text
Email Service
    ↓
Deliver reset credential
```

This is a clean separation.

---

# 16. Database state

Conceptually, a user could have fields like:

```text
User
├── email
├── passwordHash
├── resetTokenHash
└── resetTokenExpiresAt
```

Before requesting reset:

```text
resetTokenHash = null
resetTokenExpiresAt = null
```

After requesting reset:

```text
resetTokenHash = hashed token
resetTokenExpiresAt = future time
```

After successful reset:

```text
resetTokenHash = null
resetTokenExpiresAt = null
```

The exact schema belongs to your implementation; the roadmap itself only establishes password reset as part of authentication/email architecture.

# 17. User clicks the email

The user receives:

```text
[ Reset Password ]
```

and clicks it.

They arrive at something like:

```text
/reset-password?token=abc123
```

Now the frontend has the token.

# 18. Reset password endpoint

The frontend can send the token and new password to something like:

```http
POST /api/v1/auth/reset-password
```

Body:

```json
{
  "token": "abc123",
  "password": "NewStrongPassword123!"
}
```

The backend now performs the sensitive part.

---

# 19. Validate the token

The backend does:

```text
Token from request
        ↓
Hash token
        ↓
Find matching stored hash
        ↓
Check expiration
```

If no matching record exists:

```text
Invalid reset token
```

If expired:

```text
Reset token expired
```

Otherwise:

```text
Token valid
```

---

# 20. Hash the new password

This is extremely important.

Never do:

```js
user.password = newPassword;
```

Instead:

```text
New password
     ↓
bcrypt
     ↓
Password hash
     ↓
MongoDB
```

So your database stores:

```text
passwordHash
```

not:

```text
MyPassword123
```

---

# 21. Password reset is not password storage

Separate these concepts:

```text
RESET TOKEN
    ↓
Temporary credential
    ↓
Used to prove reset authorization
```

and:

```text
PASSWORD
    ↓
Long-term user credential
    ↓
Must be securely hashed
```

Don't confuse them.

---

# 22. Invalidate the reset token

After successful password reset:

```text
resetTokenHash = null
resetTokenExpiresAt = null
```

Why?

Because the reset token should be **one-time use**.

Without invalidation:

```text
Token
 ↓
Reset password
 ↓
Token still works
 ↓
Reset again
```

That's unnecessary risk.

Instead:

```text
Token
 ↓
Reset password
 ↓
Token destroyed
```

```text
        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓
```

# 24. What about existing login sessions?

This is a very important production question.

Suppose an attacker somehow has an old access token.

Then the legitimate user resets their password.

Should that old session remain valid?

Often, a secure application should consider invalidating existing authentication sessions/tokens after a password reset.

For example:

```text
Password reset
      ↓
Invalidate refresh tokens/sessions
      ↓
User must authenticate again
```

The exact mechanism depends on your authentication architecture.

Since you've already studied refresh-token rotation, this is where those concepts become useful.

---

# 25. Password reset + refresh tokens

Suppose the user has:

```text
Access token
Refresh token
```

and then resets their password.

A strong design can invalidate the refresh-token state:

```text
Password reset
      ↓
Clear/revoke refresh-token records
      ↓
Old session cannot continue refreshing
```

This reduces the damage if an old refresh credential was compromised.

---

# 26. Don't log the reset token

Avoid:

```text
console.log(resetToken);
```

and especially:

```text
console.log(resetUrl);
```

because the URL contains the secret.

Remember your Phase 19 logging lesson:

```text
Sensitive credential
        ↓
DO NOT put it in logs
```

---

# 27. Password reset endpoint should be public

Notice something interesting.

You can't require normal authentication for:

```text
POST /forgot-password
```

because the user has forgotten their password.

Similarly:

```text
POST /reset-password
```

must be accessible without a normal access token.

Instead, the reset token itself is the temporary credential.

So:

```text
Normal API
 ↓
Access token
```

while:

```text
Password reset
 ↓
Reset token
```

---

# 28. But public doesn't mean unprotected

This is a common mistake.

Someone might think:

```text
No JWT
=
No security
```

Wrong.

Password-reset endpoints should have protections such as:

```text
Validation
Rate limiting
Generic responses
Secure token generation
Token expiration
Token invalidation
Password strength requirements
```

So:

```text
Public endpoint
≠
Unsecured endpoint
```

---

# 29. Rate-limit forgot-password

An attacker could repeatedly request:

```text
POST /forgot-password
```

for the same address.

That could cause:

```text
Email flooding
SMTP costs
User annoyance
Abuse
```

So apply rate limiting.

For example, conceptually:

```text
IP-based limit
+
Email/account-based limit
```

The exact implementation belongs to your security/rate-limiting architecture.

---

# 30. Don't reveal whether the email exists

Good:

```text
"If an account exists,
a reset email has been sent."
```

Riskier:

```text
"No account found with that email."
```

The first response reduces account enumeration.

---

# 31. What if the email doesn't exist?

A good flow can simply:

```text
Receive email
 ↓
Look up account
 ↓
If account doesn't exist:
    don't send anything
 ↓
Return generic response
```

The attacker shouldn't be able to tell from the response.

A useful message:


# 35. Verification vs reset token

Both use a temporary token:

```text
Verification token
      ↓
Proves email ownership
```

```text
Reset token
      ↓
Authorizes password change
```

But their consequences differ.

Verification:

```text
emailVerified = true
```

Reset:

```text
passwordHash = newHash
```

Therefore password reset is generally more sensitive.

# 36. Common mistakes

### ❌ Mistake 1 — Put the password in the URL

Never.

Bad:

```text
/reset?password=MyPassword123
```

The URL should contain only the temporary reset credential.

---

### ❌ Mistake 2 — Store the new password directly

Bad:

```js
user.password = password;
```

Use password hashing.

---

### ❌ Mistake 3 — Store raw reset token

Prefer storing a hash.

---

### ❌ Mistake 4 — Never expire reset tokens

Don't allow permanent reset links.

---

### ❌ Mistake 5 — Reuse reset token

Invalidate after successful reset.

---

### ❌ Mistake 6 — Reveal nonexistent accounts

Avoid account enumeration.

---

### ❌ Mistake 7 — Log reset URLs

They contain credentials.

---

### ❌ Mistake 8 — No rate limiting

Password reset is an abuse-sensitive endpoint.

---

### ❌ Mistake 9 — Let Email Service modify passwords

Wrong layer.

```text
Email Service
    ↓
send email

Auth Service
    ↓
change password
```

# 39. Interview questions

### What is a password reset token?

A temporary credential that allows a user to authorize a password-reset operation.

### Should reset tokens expire?

Yes.

### Should reset tokens be reusable?

Normally no.

### Should the raw reset token be stored?

A stronger design stores a hash of the token.

### Why shouldn't the API reveal whether an email exists?

To reduce account enumeration.

### Should the reset endpoint require a JWT?

No. The reset token itself provides the temporary authorization needed for the reset flow.

### Should the new password be stored directly?

No. It must be securely hashed.

### Should reset tokens be logged?

No. Treat them as secrets.
