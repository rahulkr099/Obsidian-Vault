# Lesson 21.10 — Testing Routes

We now move one step above controllers.

So far:

```text
21.7 → Testing Services
21.8 → Testing Repositories
21.9 → Testing Controllers
21.10 → Testing Routes ← You are here
```

The route layer is small, but it is extremely important because it connects the **HTTP endpoint** to the correct middleware and controller.

Your architecture separates routes from controllers and middleware, so routes should mainly define **how a request travels through the application**, rather than containing business logic.

---

# 1. What Is a Route?

Consider:

```js
router.get(
    "/users/:id",
    authenticate,
    getUser
);
```

This line defines:

```text
GET /users/:id
      ↓
authenticate
      ↓
getUser
```

The route is essentially a pipeline definition.

It answers:

> **When this HTTP request arrives, which middleware and controller should handle it?**

---

# 2. What Should a Route Test Verify?

A route test should mainly verify:

```text
✓ HTTP method
✓ URL/path
✓ route parameters
✓ middleware attached
✓ middleware order
✓ controller attached
✓ protected/public behavior
```

It should generally **not** test:

```text
✗ database queries
✗ business logic
✗ password hashing
✗ controller response formatting
```

Those belong to other tests.

---

# 3. Example Route

Suppose:

```js
router.get(
    "/users/:id",
    authenticate,
    getUser
);
```

We can visualize it as:

```text
GET /users/:id
       │
       ▼
authenticate
       │
       ▼
getUser
```

If someone accidentally changes it to:

```js
router.post(
    "/users/:id",
    authenticate,
    getUser
);
```

your frontend's:

```text
GET /users/123
```

will no longer work.

A route test can catch this.

---

# 4. Why Test Routes Separately?

It might initially seem unnecessary.

After all, you could use Supertest:

```text
GET /users/123
```

and see whether the endpoint works.

But a route-level test can give very focused feedback:

```text
❌ Wrong HTTP method
❌ Missing authentication middleware
❌ Wrong controller
❌ Wrong path
❌ Wrong middleware order
```

instead of simply:

```text
❌ API test failed
```

The smaller the test, the easier it is to identify the problem.

---

# 5. Route Testing vs API Testing

This distinction matters.

### Route unit test

You test the route configuration itself.

```text
router
 ↓
middleware/controller references
```

### API integration test

You send an actual HTTP request:

```text
HTTP
 ↓
Express
 ↓
router
 ↓
middleware
 ↓
controller
 ↓
service
 ↓
repository
```

We'll get into the second approach later.

---

# 6. A Typical Route File

For example:

```js
import { Router } from "express";

import {
    getUser,
    createUser
} from "../controllers/user.controller.js";

import {
    authenticate
} from "../middlewares/auth.middleware.js";

const router = Router();

router.get(
    "/:id",
    authenticate,
    getUser
);

router.post(
    "/",
    authenticate,
    createUser
);

export default router;
```

We want to make sure the route definitions are correct.

---

# 7. Route Testing Can Be Tricky

Express doesn't expose a simple API like:

```js
router.getRoutes()
```

that you can always use directly.

Internally, Express stores route information in its routing stack.

That means there are a few approaches to testing routes.

The most useful ones are:

```text
1. Inspect router configuration
2. Test through a minimal Express app
3. Test through Supertest
```

Each has a different purpose.

---

# 8. Approach 1 — Inspect the Router

For simple route registration, you can inspect Express's internal stack.

For example, depending on Express version:

```js
router.stack
```

may contain route layers.

You can inspect:

```js
router.stack.map(layer => layer.route);
```

This can expose information such as:

```text
path
methods
handlers
```

But there is an important warning.

---

# 9. Express Internals Are Implementation Details

Code like:

```js
router.stack
```

depends on Express internals.

That means a test relying heavily on internal structures can become brittle.

So don't automatically write huge tests against:

```text
router.stack
layer.handle
layer.route.stack
```

just because you can.

Use this technique carefully.

---

# 10. Better Question

Instead of asking:

> "Can I inspect Express internals?"

ask:

> **"What behavior do I actually need confidence in?"**

For most applications, the most valuable answer is:

```text
GET /users/123
```

actually reaches the expected middleware/controller.

That's why integration tests become increasingly useful.

---

# 11. Testing the Route With a Minimal Express App

You can mount the router:

```js
const app = express();

app.use(express.json());

app.use("/users", userRouter);
```

Then send a request with Supertest:

```js
await request(app)
    .get("/users/user-123");
```

This tests:

```text
Express
 ↓
Router
 ↓
Middleware
 ↓
Controller
```

This is already more realistic than inspecting `router.stack`.

---

# 12. But We Haven't Reached Supertest Yet

Don't worry.

We're going to study Supertest in detail in the upcoming lessons.

For now, understand the architecture.

Route testing asks:

```text
Did the request enter the correct pipeline?
```

Supertest will later let us ask:

```text
What happens when a real HTTP request enters that pipeline?
```

---

# 13. Route Method Testing

Suppose:

```js
router.get("/:id", getUser);
```

You want:

```text
GET /users/123
```

to work.

But:

```text
POST /users/123
```

should not accidentally invoke `getUser`.

That's a route contract.

---

# 14. Why HTTP Method Matters

These are different endpoints:

```text
GET    /users/:id
POST   /users
PATCH  /users/:id
DELETE /users/:id
```

Even if they use the same resource:

```text
/users
```

their semantics are different.

A route mistake can cause:

```text
frontend request
      ↓
404
```

or worse:

```text
frontend request
      ↓
wrong controller
```

---

# 15. Testing Route Parameters

Suppose:

```js
router.get(
    "/:id",
    getUser
);
```

The route parameter:

```text
:id
```

must become:

```js
req.params.id
```

The route itself doesn't extract it.

Express does that before the controller runs.

So:

```text
/users/123
     ↓
:id = "123"
     ↓
req.params.id
```

Your controller tests verify what happens after this point.

Route/API tests verify the entire path.

---

# 16. Nested Routes

Your backend may eventually have routes like:

```text
/users/:userId/todos
```

For example:

```js
router.get(
    "/users/:userId/todos",
    authenticate,
    listUserTodos
);
```

Now the route has:

```text
:userId
```

and the controller receives:

```js
req.params.userId
```

A route test should make sure the path is actually:

```text
/users/:userId/todos
```

and not accidentally:

```text
/users/todos/:userId
```

---

# 17. Route Mounting Matters

Suppose your application has:

```js
app.use("/api/v1/users", userRouter);
```

and inside:

```js
router.get("/:id", getUser);
```

The final endpoint is:

```text
GET /api/v1/users/:id
```

not:

```text
GET /users/:id
```

Think in two pieces:

```text
Application mount
       +
Router path
       =
Final API path
```

---

# 18. Example

Application:

```js
app.use(
    "/api/v1/users",
    userRouter
);
```

Router:

```js
router.get(
    "/:id",
    authenticate,
    getUser
);
```

Final route:

```text
GET /api/v1/users/:id
```

This is why route testing at the application level is often more useful than testing an isolated router.

---

# 19. Middleware Order

This is one of the most important parts of route testing.

Suppose:

```js
router.get(
    "/:id",
    authenticate,
    authorize("admin"),
    getUser
);
```

The intended pipeline is:

```text
Request
  ↓
authenticate
  ↓
authorize
  ↓
getUser
```

If someone accidentally writes:

```js
router.get(
    "/:id",
    getUser,
    authenticate,
    authorize("admin")
);
```

the controller executes first.

That's a serious security problem.

---

# 20. Why Middleware Order Matters

Express executes handlers in the order they are registered.

So:

```js
router.get(
    "/",
    middlewareA,
    middlewareB,
    controller
);
```

means:

```text
A
 ↓
B
 ↓
controller
```

not:

```text
controller
 ↓
A
 ↓
B
```

Route tests can help protect this pipeline.

---

# 21. Protected Routes

Suppose:

```js
router.delete(
    "/:id",
    authenticate,
    authorize("admin"),
    deleteUser
);
```

The route contract is:

```text
DELETE /users/:id

authentication required
        ↓
authorization required
        ↓
controller
```

A good test strategy should verify that this route is not accidentally registered as:

```js
router.delete(
    "/:id",
    deleteUser
);
```

because that would bypass your protection.

---

# 22. Public Routes

Not every route needs authentication.

For example:

```js
router.post(
    "/login",
    login
);
```

Expected:

```text
POST /login
   ↓
login controller
```

No authentication middleware.

If someone accidentally adds:

```js
authenticate
```

then nobody could log in without already being authenticated.

So route configuration itself matters.

---

# 23. Route Groups

You may have:

```text
Public
├── POST /auth/login
├── POST /auth/register
└── POST /auth/refresh

Protected
├── GET /users/me
├── PATCH /users/me
└── DELETE /users/me
```

This gives you an architectural test idea:

```text
Public routes
    ↓
must not require authentication

Protected routes
    ↓
must require authentication
```

This becomes particularly useful as your application grows.

---

# 24. Route Tests Should Not Duplicate Middleware Tests

Suppose `authenticate` already has its own tests.

You don't need to test JWT validation again in the route test.

Instead, route test:

```text
Is authenticate attached?
```

Middleware test:

```text
Does authenticate validate the token correctly?
```

This keeps responsibilities separate.

---

# 25. Route Tests Should Not Duplicate Controller Tests

Similarly:

### Route test

```text
GET /users/:id
 ↓
getUser controller attached?
```

### Controller test

```text
getUser()
 ↓
service called correctly?
 ↓
response correct?
```

Don't make both tests responsible for the same thing.

---

# 26. Route Test With Mock Handlers

One possible strategy is to replace handlers with identifiable functions.

Conceptually:

```js
const authenticate = jest.fn(
    (req, res, next) => next()
);

const getUser = jest.fn(
    (req, res) => res.send("getUser")
);
```

Then mount them:

```js
router.get(
    "/:id",
    authenticate,
    getUser
);
```

When a request is made:

```text
GET /users/123
```

you can verify:

```js
expect(authenticate)
    .toHaveBeenCalled();

expect(getUser)
    .toHaveBeenCalled();
```

This is more behavior-oriented than inspecting internal Express objects.

---

# 27. But Be Careful

If you replace every real middleware and controller with mocks, you aren't testing:

```text
real middleware
+
real controller
```

You're testing:

```text
route configuration
```

That is okay **if that is your intention**.

Remember:

> A test should have a clear scope.

---

# 28. Route Test Scope

Think:

```text
Route Unit Test
```

tests:

```text
method
path
handler ordering
handler presence
```

while:

```text
API Integration Test
```

tests:

```text
method
path
middleware
controller
service
repository
database
```

Neither is "better".

They answer different questions.

---

# 29. Route Ordering

Here's another subtle problem.

Suppose:

```js
router.get(
    "/:id",
    getUser
);

router.get(
    "/me",
    getCurrentUser
);
```

Depending on how the routes are registered, `/me` can potentially be captured by:

```text
/:id
```

because:

```text
:id = "me"
```

This is a classic routing issue.

A safer order is often:

```js
router.get(
    "/me",
    getCurrentUser
);

router.get(
    "/:id",
    getUser
);
```

Now:

```text
/me
```

matches the specific route first.

---

# 30. This Is Why Route Order Matters

Think:

```text
Specific route
      ↓
Generic route
```

rather than:

```text
Generic route
      ↓
Specific route
```

For example:

```text
/users/me
/users/:id
```

Usually:

```text
/users/me
```

should be registered before:

```text
/users/:id
```

if both live in the same router.

---

# 31. Testing Route Ordering

This is better tested with an actual request.

Suppose:

```js
router.get("/me", getCurrentUser);
router.get("/:id", getUser);
```

Then:

```text
GET /users/me
```

should invoke:

```text
getCurrentUser
```

not:

```text
getUser
```

This is an excellent example of where integration-style route testing provides more confidence than inspecting router internals.

---

# 32. 404 Routes

What happens when:

```text
GET /api/v1/users/does-not-exist-route
```

doesn't match anything?

Express eventually reaches your 404 handling.

Your architecture has centralized error handling, so route/API tests should eventually verify that unmatched endpoints produce your expected 404 response.

We'll test this more naturally through Supertest.

---

# 33. Route Prefixes

Large APIs often use:

```text
/api/v1
```

For example:

```js
app.use(
    "/api/v1/users",
    userRoutes
);

app.use(
    "/api/v1/todos",
    todoRoutes
);
```

Now the final endpoints become:

```text
GET /api/v1/users/:id

GET /api/v1/todos/:id
```

Testing the mounted application helps ensure these prefixes haven't accidentally changed.

---

# 34. API Versioning and Routes

Suppose you later introduce:

```text
/api/v1/users
/api/v2/users
```

You might have:

```text
routes/
├── v1/
│   └── user.routes.js
└── v2/
    └── user.routes.js
```

Route tests become useful because they can verify:

```text
v1 endpoint
    ↓
v1 controller

v2 endpoint
    ↓
v2 controller
```

rather than accidentally pointing both versions to the same implementation.

---

# 35. Route Testing Checklist

For every important route, ask:

```text
[ ] Correct HTTP method?
[ ] Correct path?
[ ] Correct mount prefix?
[ ] Correct path parameters?
[ ] Correct middleware?
[ ] Correct middleware order?
[ ] Correct controller?
[ ] Public/protected status correct?
[ ] Specific routes before generic routes?
```

That's a very practical checklist.

|PATCH|`/users/:id`|`authenticate`|`updateUser`|

This table is almost a test plan by itself.

# 38. Route Tests and Security

Routes are part of your security boundary.

Consider:

```js
router.delete(
    "/:id",
    deleteUser
);
```

If the endpoint should be protected, this is a vulnerability.

You want:

```js
router.delete(
    "/:id",
    authenticate,
    authorize,
    deleteUser
);
```

This means route tests shouldn't be treated as "just plumbing".

A missing middleware can completely change the security of an endpoint.

---

# 39. A Useful Security Test

For a protected endpoint, define the expected pipeline:

```text
DELETE /users/:id
        ↓
authenticate
        ↓
authorize
        ↓
deleteUser
```

Then make sure a future developer can't accidentally simplify it to:

```text
DELETE /users/:id
        ↓
deleteUser
```

This is particularly useful when your application has many routes.

---

# 40. Route Naming Consistency

You should also keep an eye on route conventions.

For example:

```text
GET    /users
GET    /users/:id
POST   /users
PATCH  /users/:id
DELETE /users/:id
```

This is predictable.

Avoid random patterns such as:

```text
GET  /getUsers
POST /createUser
POST /deleteUser
```

when you're building a REST-style API.

Your API design phase already established the importance of consistent resource-oriented routes.

---

# 41. Routes Should Be Boring

This is actually a compliment.

A good route file often looks like:

```js
router.get(
    "/:id",
    authenticate,
    getUser
);

router.post(
    "/",
    authenticate,
    createUser
);

router.patch(
    "/:id",
    authenticate,
    updateUser
);

router.delete(
    "/:id",
    authenticate,
    deleteUser
);
```

No:

```text
database queries
if/else business rules
password hashing
JWT generation
```

Just:

```text
method
path
middleware
controller
```

Boring routes are easier to maintain.

---

# 42. Don't Put Logic in Routes

Bad:

```js
router.get("/users/:id", async (req, res) => {
    const user = await User.findById(req.params.id);

    if (!user) {
        return res.status(404).json(...);
    }

    res.json(user);
});
```

Now your route file contains:

```text
HTTP
+
database
+
business logic
+
response handling
```

That's exactly what we're trying to avoid.

Better:

```js
router.get(
    "/users/:id",
    authenticate,
    getUser
);
```

# 45. Route Tests vs Supertest

This is the transition point.

### Route-focused test

```text
"Is GET /users/:id configured correctly?"
```

### Supertest

```text
"What actually happens when I send
GET /users/123?"
```

The second question is much closer to how a real client interacts with your API.

---

# 46. What Supertest Will Give You

With Supertest, you'll be able to write something conceptually like:

```js
const response = await request(app)
    .get("/api/v1/users/user-123");
```

Then inspect:

```js
response.status
response.body
response.headers
```

Now you are testing actual HTTP behavior.

We'll study this carefully rather than jumping straight into it.

# 50. Final Takeaway

The most important lesson from 21.10:

> **Routes define the request pipeline; they should not contain application logic.**

Test that:

```text
correct method
      ↓
correct path
      ↓
correct middleware
      ↓
correct middleware order
      ↓
correct controller
```

And remember the distinction:

```text
Route test
    ↓
"Is the pipeline configured correctly?"

Controller test
    ↓
"Does HTTP input/output translate correctly?"

API test
    ↓
"Does the complete endpoint actually work?"
```
