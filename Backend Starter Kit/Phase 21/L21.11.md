# Lesson 21.11 — Supertest Fundamentals

Now we enter one of the most useful parts of backend testing.

So far, we've mostly tested individual pieces:

```text
Utility
Middleware
Repository
Service
Controller
Route
```

Now we're going to test the application **through HTTP**.

That means instead of doing:

```js
await controller(req, res, next);
```

we'll do:

```js
await request(app)
    .get("/api/v1/users");
```

This is much closer to how your frontend, mobile app, or another service actually uses your backend.

---

# 1. What Is Supertest?

[Supertest on npm](https://www.npmjs.com/package/supertest?utm_source=chatgpt.com) is a Node.js testing library commonly used to make HTTP requests against applications such as Express.

The basic idea is:

```text
Test
  │
  │ HTTP request
  ▼
Express App
  │
  ├── Middleware
  ├── Routes
  ├── Controllers
  ├── Services
  └── Repositories
```

Then the test receives:

```text
HTTP response
```

and makes assertions about it.

---

# 2. Why Supertest Is Important

Imagine your API has:

```text
POST /api/v1/auth/login
```

A unit test might test:

```text
loginController()
```

But a real client doesn't call your controller directly.

It sends:

```http
POST /api/v1/auth/login
Content-Type: application/json

{
  "email": "...",
  "password": "..."
}
```

Supertest lets your test behave much more like that client.

---

# 3. Unit Test vs Supertest

### Controller unit test

```text
fake req
fake res
mock service
     ↓
controller()
```

### Supertest

```text
HTTP request
     ↓
Express
     ↓
Router
     ↓
Middleware
     ↓
Controller
     ↓
Service
     ↓
...
     ↓
HTTP response
```

This gives you confidence that the pieces are wired together correctly.

# 5. The Most Important Concept

You don't normally want your test to start the production server with:

```js
app.listen(PORT);
```

Instead, export the Express application:

```js
export default app;
```

Then your test can use:

```js
request(app)
```

This is a very important architectural distinction.

---

# 6. Separate `app` From `server`

A clean structure is:

```text
src/
├── app.js
└── server.js
```

### `app.js`

```js
import express from "express";

const app = express();

app.use(express.json());

// routes...

export default app;
```

### `server.js`

```js
import app from "./app.js";

app.listen(
    process.env.PORT,
    () => {
        console.log("Server started");
    }
);
```

Now:

```text
app.js
    ↓
Express configuration

server.js
    ↓
Actually opens network port
```

---

# 7. Why This Separation Matters

Your tests can do:

```js
request(app)
```

without starting:

```text
localhost:5000
```

That means:

```text
No manually started server
No port conflicts
No server cleanup problems
Cleaner tests
```

This is a very good backend architecture pattern.

# 8. Your First Supertest

Suppose:

```js
GET /api/v1/health
```

returns:

```json
{
  "success": true,
  "message": "API is running"
}
```

Test:

```js
import request from "supertest";
import app from "../../src/app.js";

describe("GET /api/v1/health", () => {
    test("returns health status", async () => {
        const response = await request(app)
            .get("/api/v1/health");

        expect(response.status)
            .toBe(200);

        expect(response.body)
            .toEqual({
                success: true,
                message: "API is running"
            });
    });
});
```

That's your first real HTTP integration test.

---

# 9. Read This Test Carefully

This:

```js
request(app)
```

means:

> "Create a Supertest client for this Express application."

Then:

```js
.get("/api/v1/health")
```

means:

> "Send a GET request to this path."

Then:

```js
const response = await ...
```

gives you the HTTP response.

Then:

```js
response.status
```

gives:

```text
200
```

and:

```js
response.body
```

gives the parsed JSON.

---

# 10. The Basic Pattern

Memorize this pattern:

```js
const response = await request(app)
    .get("/some/path");

expect(response.status)
    .toBe(200);

expect(response.body)
    .toEqual(expectedBody);
```

This pattern will appear throughout your integration tests.

# 12. POST Requests

For:

```text
POST /api/v1/users
```

use:

```js
const response = await request(app)
    .post("/api/v1/users");
```

To send JSON:

```js
const response = await request(app)
    .post("/api/v1/users")
    .send({
        name: "Rahul",
        email: "rahul@example.com"
    });
```

Supertest will send the request body.

---

# 13. JSON Content Type

You can explicitly specify:

```js
.set(
    "Content-Type",
    "application/json"
)
```

but with `.send({...})`, Supertest commonly handles the JSON request setup for you.

So this is usually enough:

```js
const response = await request(app)
    .post("/api/v1/users")
    .send({
        name: "Rahul",
        email: "rahul@example.com"
    });
```

---

# 14. Testing POST Response

Suppose the API responds:

```http
201 Created
```

with:

```json
{
  "success": true,
  "data": {
    "name": "Rahul"
  }
}
```

Test:

```js
expect(response.status)
    .toBe(201);

expect(response.body.success)
    .toBe(true);

expect(response.body.data.name)
    .toBe("Rahul");
```

---

# 15. `response.body`

If the server returns JSON:

```json
{
  "success": true
}
```

Supertest gives:

```js
response.body
```

as a JavaScript object.

So:

```js
expect(response.body.success)
    .toBe(true);
```

works.

You can also:

```js
expect(response.body)
    .toEqual({
        success: true
    });
```

# 18. Testing Headers

Suppose the server returns:

```http
Content-Type: application/json
```

You can inspect:

```js
response.headers["content-type"]
```

For example:

```js
expect(response.headers["content-type"])
    .toMatch(/json/);
```

This is useful for verifying API behavior.

# 19. Testing Custom Headers

Suppose:

```http
X-Request-ID: abc123
```

Then:

```js
expect(response.headers["x-request-id"])
    .toBeDefined();
```

or:

```js
expect(response.headers["x-request-id"])
    .toBe("abc123");
```

This becomes especially useful once you test your logging/request-ID architecture.

# 20. Sending Request Headers

Supertest also lets you send headers.

For example:

```js
const response = await request(app)
    .get("/api/v1/users/me")
    .set(
        "Authorization",
        "Bearer test-token"
    );
```

This is essential for authenticated APIs.

---

# 21. Authentication Testing

Suppose your middleware expects:

```http
Authorization: Bearer <access-token>
```

Then:

```js
const response = await request(app)
    .get("/api/v1/users/me")
    .set(
        "Authorization",
        `Bearer ${accessToken}`
    );
```

Now the request travels through:

```text
Supertest
   ↓
Express
   ↓
authenticate middleware
   ↓
controller
```

This is much closer to a real frontend request.

---

# 22. Don't Hardcode Real Tokens

Avoid putting a production token into tests.

Bad:

```js
.set(
    "Authorization",
    "Bearer eyJhbGciOi..."
);
```

Instead, generate a test token or use your authentication test helper.

For example:

```js
const token = createTestAccessToken({
    userId: user.id
});
```

Then:

```js
.set(
    "Authorization",
    `Bearer ${token}`
);
```

We'll build a cleaner strategy for this in later lessons.

---

# 23. Testing Cookies

Supertest can also work with cookies.

For example:

```js
.set(
    "Cookie",
    `refreshToken=${refreshToken}`
);
```

You can inspect response cookies through headers:

```js
response.headers["set-cookie"]
```

This becomes important when testing refresh-token authentication.

```js
const loginResponse = await request(app)
```

# 25. Testing Validation

Suppose:

```text
POST /api/v1/users
```

requires:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"

```

Send an invalid request:

# 26. Testing 404

Try an endpoint that doesn't exist:

```js

    .get("/api/v1/does-not-exist");
```

Then:

```js
expect(response.status)
    .toBe(404);
```

You can also test your standardized error body:

```js
expect(response.body)
    .toMatchObject({
        success: false
    });
```

# 27. Testing 401

Suppose:

```text
GET /api/v1/users/me
```

requires authentication.

Don't send a token:

```js
const response = await request(app)
    .get("/api/v1/users/me");
```

Then:

```js
expect(response.status)
    .toBe(401);
```

This verifies that:

```text
route
 ↓
authentication middleware
 ↓
request rejected
```

is actually connected correctly.

# 28. Testing 403

Now send a valid authenticated user who doesn't have enough permission.

For example:

```js
const response = await request(app)
    .delete("/api/v1/admin/users/user-123")
    .set(
        "Authorization",
        `Bearer ${regularUserToken}`
    );
```

Then:

```js
expect(response.status)
    .toBe(403);
```

This tests a larger part of the security pipeline:

```text
Authentication
      ↓
Authorization
      ↓
Controller
```

---

# 29. Testing 404 Resource Not Found

Don't confuse:

```text
404 route doesn't exist
```

with:

```text
404 user doesn't exist
```

These can both use HTTP 404, but happen at different layers.

### Route doesn't exist

```text
GET /api/v1/random
```

### Resource doesn't exist

```text
GET /api/v1/users/does-not-exist
```

The first is a routing problem.

The second is usually a service/repository/application problem.

Your tests should distinguish them.

# 30. Supertest Doesn't Need a Running Server

This is one of its best features.

You can do:

```js
request(app)
```

without:

```bash
npm start
```

and without:

```js
app.listen(...)
```

That's why separating:

```text
app
```

from:

```text
server
```

is so useful.

---

# 31. Don't Do This in Integration Tests

Avoid:

```js
beforeAll(() => {
    app.listen(5000);
});
```

for normal Supertest usage.

It creates unnecessary problems:

```text
Port conflicts
Open handles
Cleanup complexity
Parallel test issues
```

Instead:

```js
request(app)
```

directly.

# 33. Database Is the Next Problem

At this point you might notice something.

Suppose:

```js
const response = await request(app)
    .get("/api/v1/users");
```

and the route calls:

```text
service
 ↓
repository
 ↓
MongoDB
```

Now your test requires a database.

That's not necessarily bad.

But we need to decide what kind of integration test we're writing.

---

# 34. Three Testing Levels

This is important.

### Level 1 — Unit

```text
Controller
 ↓
mock service
```

### Level 2 — Integration with mocked dependencies

```text
HTTP
 ↓
Express
 ↓
Controller
 ↓
mock service
```

### Level 3 — Full integration

```text
HTTP
 ↓
Express
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Test database
```

We'll gradually build toward Level 3.

---

# 35. Supertest Does Not Automatically Mean Database

Supertest only cares about HTTP.

It doesn't decide whether you use:

```text
real database
mock repository
in-memory database
test database
```

That's your testing architecture.

This is an important distinction.

Suppose:

```js
userService.getUser = jest.fn()
    .mockResolvedValue({
        id: "123",
        name: "Rahul"
    });
```

Then:

```js
const response = await request(app)
```

```text

 ↓
Express
 ↓
Route
 ↓
Middleware
 ↓
```

# 37. Why This Is Useful

Imagine a route suddenly returns:

```text
404
```

Your unit controller test passes.

Your service test passes.

But your Supertest test fails.

That might reveal:

```text
Wrong route path
Missing router mounting
Middleware problem
Controller not attached
Request parameter problem
```

That's exactly the kind of wiring issue unit tests can't always catch.

```text

             ▲
             │
       HTTP Integration

             ▲
```

# 41. Test Query Parameters

Suppose:

```text
GET /api/v1/users?page=2&limit=10
```

You can write:

```js
const response = await request(app)
    .get("/api/v1/users")
    .query({
        page: 2,
        limit: 10
    });
```

This is cleaner than manually constructing:

```js
.get("/api/v1/users?page=2&limit=10")
```

Both can work, but `.query()` is easier to maintain.

# 42. Example

```js
const response = await request(app)
    .get("/api/v1/users")
    .query({
        page: 2,
        limit: 20,
        search: "Rahul"
    });
```

The server receives:

```text
req.query
```

roughly as:

```js
{
    page: "2",
    limit: "20",
    search: "Rahul"
}
```

Remember that query parameters arrive as strings unless your application transforms them.

# 48. Don't Over-Assert Everything

This is important.

You might be tempted to write:

```js
expect(response.status).toBe(200);

expect(response.headers).toEqual(...);

expect(response.body).toEqual(...);

expect(response.text).toBe(...);

expect(response.headers["date"]).toBe(...);
```

That's often too much.

Test what your API contract actually promises.

Good:

```text
status
important response fields
important headers
```

Avoid testing random framework-generated details.

---

# 49. Exact vs Partial Body Assertions

Exact:

```js
expect(response.body)
    .toEqual({
        success: true,
        data: {
            id: "123",
            name: "Rahul"
        }
    });
```

Useful when the complete response structure is part of your contract.

Partial:

```js
expect(response.body)
    .toMatchObject({
        success: true
    });
```

Useful when the response contains dynamic fields.

For example:

```json
{
  "success": true,
  "data": {},
  "requestId": "dynamic-value"
}
```

You probably don't want to hardcode the request ID.

---

# 50. Dynamic Values

Suppose your API returns:

```json
{
  "id": "generated-id"
}
```

Don't do:

```js
expect(response.body.data.id)
    .toBe("abc123");
```

unless `"abc123"` is deliberately fixed.

Instead:

```js
expect(response.body.data.id)
    .toBeDefined();
```

or:

```js
expect(typeof response.body.data.id)
    .toBe("string");
```

Tests should verify contracts, not accidental values.

---

# 51. Testing Status Codes First

A useful habit:

```js
expect(response.status)
    .toBe(200);
```

before deeply inspecting the body.

Why?

If you expected:

```text
200
```

but got:

```text
500
```

then the response body may be an error response entirely.

The status code immediately tells you what kind of result you received.

Once health works, create simple tests for your API:

```text

POST
PATCH

```

The syntax pattern is:

```js

request(app).post(path)
request(app).patch(path)
```

For POST/PATCH:

```js
.send(body)
```

For query parameters:

```js
.query(params)
```

For headers:

```js
.set(name, value)
```
