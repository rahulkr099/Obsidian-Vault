# Lesson 21.12 — Testing Authorization

Before we begin, one small numbering correction from the previous lesson: the uploaded Phase 21 roadmap defines **21.10 as Supertest, 21.11 as Testing Authentication, and 21.12 as Testing Authorization**.

So today we'll follow the actual roadmap:

> **21.12 — Testing Authorization**

Authorization is especially important because your backend must not only know **who the user is**, but also **what that user is allowed to do**.

---

# 1. Authentication vs Authorization

First, keep this distinction very clear.

### Authentication

> **Who are you?**

```text
Request
   ↓
JWT
   ↓
User identified
   ↓
req.user
```

### Authorization

> **Are you allowed to perform this action?**

```text
Request
   ↓
Authentication
   ↓
req.user
   ↓
Authorization
   ↓
Allowed?
```

Your roadmap explicitly separates authentication from authorization/RBAC, including roles, permissions, ownership, horizontal privilege escalation, and authorization testing.

---

# 2. Why Authorization Testing Matters

Imagine:

```text
User A
   ↓
Todo A
```

and:

```text
User B
   ↓
Todo B
```

User A requests:

```http
DELETE /api/v1/todos/B
```

Authentication succeeds.

User A is a valid user.

But the operation should still fail.

```text
Authentication → ✓
Authorization  → ❌
```

Expected:

```http
403 Forbidden
```

or, depending on your resource-ownership design, sometimes `404 Not Found`.

This is one of the most important security tests in a backend.

---

# 3. Authorization Pipeline

Think about a protected endpoint:

```text
DELETE /api/v1/todos/:id
              │
              ▼
        authenticate
              │
              ▼
         req.user
              │
              ▼
       authorization
              │
        ┌─────┴─────┐
        │           │
       YES          NO
        │           │
        ▼           ▼
   Controller      403
```

Your integration test should verify this entire behavior.

---

# 4. Role-Based Authorization

Suppose your application has:

```js
const ROLES = {
    USER: "user",
    INSTRUCTOR: "instructor",
    ADMIN: "admin"
};
```

Imagine:

```text
POST /api/v1/courses
```

is allowed only for:

```text
instructor
admin
```

A normal student should receive:

```http
403 Forbidden
```

---

# 5. The Important Test Cases

For a role-protected endpoint, don't test only:

```text
admin → success
```

Test the boundaries.

```text
Unauthenticated → 401
Student          → 403
Instructor       → 200/201
Admin            → 200/201
```

For example:

|User|Authenticated?|Role|Expected|
|---|--:|---|--:|
|Anonymous|❌|—|`401`|
|Student|✅|student|`403`|
|Instructor|✅|instructor|success|
|Admin|✅|admin|success|

This is much stronger than testing only the happy path.

---

# 6. Example Route

Suppose:

```js
router.post(
    "/courses",
    authenticate,
    requireRole("instructor", "admin"),
    createCourse
);
```

The pipeline is:

```text
POST /courses
      ↓
authenticate
      ↓
requireRole()
      ↓
createCourse
```

Now our tests need to verify that each category of user gets the correct result.

---

# 7. Unauthenticated Request

First:

```js
const response = await request(app)
    .post("/api/v1/courses")
    .send({
        title: "Node.js"
    });
```

No authorization header.

Expected:

```js
expect(response.status)
    .toBe(401);
```

This verifies that an unauthenticated user cannot bypass the first security layer.

---

# 8. Authenticated but Unauthorized

Now imagine we have a student token:

```js
const studentToken = createTestToken({
    userId: student.id,
    role: "student"
});
```

Send it:

```js
const response = await request(app)
    .post("/api/v1/courses")
    .set(
        "Authorization",
        `Bearer ${studentToken}`
    )
    .send({
        title: "Node.js"
    });
```

Expected:

```js
expect(response.status)
    .toBe(403);
```

This is a critical test.

The user is authenticated.

But they don't have permission.

---

# 9. Authorized User

Now create an instructor token:

```js
const instructorToken = createTestToken({
    userId: instructor.id,
    role: "instructor"
});
```

Then:

```js
const response = await request(app)
    .post("/api/v1/courses")
    .set(
        "Authorization",
        `Bearer ${instructorToken}`
    )
    .send({
        title: "Node.js"
    });
```

Expected:

```js
expect(response.status)
    .toBe(201);
```

Now we've tested the positive authorization case.

---

# 10. Why Testing Only Admin Is Not Enough

A common mistake:

```text
admin → success ✓
```

and assuming authorization works.

It doesn't prove that:

```text
student → rejected
```

because your middleware might accidentally allow everyone.

For example, a broken middleware could do:

```js
return next();
```

for every request.

Admin would still pass.

Your test suite would falsely look healthy.

That's why **negative authorization tests are extremely important**.

---

# 11. Testing Role Middleware

Suppose you have:

```js
requireRole("admin")
```

Your tests should verify:

```text
admin      → allowed
user       → rejected
instructor → rejected
anonymous  → rejected before role check
```

The expected behavior is:

```text
anonymous
   ↓
401

authenticated user
   ↓
wrong role
   ↓
403

correct role
   ↓
controller
```

---

# 12. Testing Resource Ownership

RBAC isn't the only form of authorization.

Consider:

```text
GET /api/v1/todos/:id
```

Maybe every authenticated user can read **their own** todo.

But not another user's todo.

Your repository should enforce ownership.

The architecture material explicitly highlights this pattern:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

rather than simply finding by the todo ID.

---

# 13. Ownership Test

Create:

```text
User A
  ↓
Todo A
```

and:

```text
User B
  ↓
Todo B
```

Then authenticate as User A:

```js
const response = await request(app)
    .get(`/api/v1/todos/${todoB.id}`)
    .set(
        "Authorization",
        `Bearer ${userAToken}`
    );
```

The request should **not** return Todo B.

Depending on your API design:

```text
404
```

may be appropriate to avoid revealing whether the resource exists.

Or:

```text
403
```

may be used when the API intentionally exposes the authorization distinction.

The important thing is that your API has a deliberate contract and your test protects it.

---

# 14. Horizontal Privilege Escalation

This attack is:

> A normal user accesses another normal user's resource.

Example:

```text
User A
   ↓
GET /todos/B
```

where `B` belongs to User B.

This is commonly called an ownership/IDOR-style authorization problem.

Your test should explicitly model it:

```text
User A
   ↓
attempts User B's resource
   ↓
must fail
```

This is one of the highest-value authorization tests you can write.

---

# 15. Vertical Privilege Escalation

This is different.

Here:

```text
student
   ↓
admin operation
```

For example:

```http
DELETE /api/v1/users/123
```

A normal student tries to access an admin-only operation.

Expected:

```http
403 Forbidden
```

So:

```text
Horizontal
User A → User B resource

Vertical
Normal user → Admin capability
```

Both should have dedicated tests.

---

# 16. Testing Ownership With Update

Suppose:

```http
PATCH /api/v1/todos/:id
```

User A owns Todo A.

Test:

```js
const response = await request(app)
    .patch(`/api/v1/todos/${todoA.id}`)
    .set(
        "Authorization",
        `Bearer ${userAToken}`
    )
    .send({
        title: "Updated"
    });

expect(response.status)
    .toBe(200);
```

Then:

```text
User B
   ↓
PATCH Todo A
```

should fail.

---

# 17. Testing Ownership With Delete

This is even more important.

```text
User A
   ↓
DELETE User B's Todo
```

must never succeed.

Test:

```js
const response = await request(app)
    .delete(`/api/v1/todos/${todoB.id}`)
    .set(
        "Authorization",
        `Bearer ${userAToken}`
    );

expect(response.status)
    .toBe(403); // or 404, based on your contract
```

Then verify:

```text
Todo B still exists
```

This last assertion is important.

---

# 18. Don't Only Test the HTTP Status

Imagine the API returns:

```http
403
```

but accidentally deleted the resource first.

That would be a serious bug.

So for destructive operations, verify the state too:

```text
Request
   ↓
Unauthorized
   ↓
403
   ↓
Database unchanged
```

For example:

```js
expect(response.status)
    .toBe(403);

const todoStillExists =
    await Todo.findById(todoB.id);

expect(todoStillExists)
    .not
    .toBeNull();
```

Now your test protects both the HTTP contract and the data.

---

# 19. Authorization Test Structure

A good test file might look like:

```text
authorization.test.js

describe("Course authorization", () => {

    test("rejects anonymous users");

    test("rejects students");

    test("allows instructors");

    test("allows admins");

});

describe("Todo ownership", () => {

    test("allows owner");

    test("rejects another user");

});
```

This makes the security rules obvious.

---

# 20. Test the Rule, Not the Implementation

Avoid tests like:

```js
expect(requireRole)
    .toHaveBeenCalled();
```

That tells you the middleware ran.

But the real question is:

> Did the endpoint actually protect the resource?

A stronger test is:

```text
student
  ↓
POST /courses
  ↓
403
```

You're testing behavior rather than implementation details.

---

# 21. Authorization Tests Should Use Real HTTP

This is where Supertest becomes powerful.

Instead of:

```js
requireRole(req, res, next);
```

test:

```js
await request(app)
    .post("/api/v1/courses")
    .set("Authorization", `Bearer ${token}`)
    .send(...);
```

Then you're verifying:

```text
HTTP
 ↓
Route
 ↓
Authentication
 ↓
Authorization
 ↓
Controller
```

That's exactly the integration-testing goal described in your roadmap.

---

# 22. Test Middleware Order

Consider:

```js
router.delete(
    "/:id",
    authenticate,
    requireRole("admin"),
    deleteUser
);
```

You want:

```text
authenticate
      ↓
requireRole
      ↓
deleteUser
```

not:

```text
deleteUser
      ↓
authenticate
```

A real HTTP test can expose this.

For example, an unauthenticated request:

```js
const response = await request(app)
    .delete("/api/v1/users/123");
```

must never execute the deletion.

Expected:

```js
expect(response.status)
    .toBe(401);
```

and:

```text
Database
   ↓
unchanged
```

---

# 23. A Powerful Security Test

For every destructive protected endpoint:

```text
DELETE
PATCH
POST sensitive operation
```

test:

```text
Anonymous
   ↓
blocked

Wrong role
   ↓
blocked

Wrong owner
   ↓
blocked

Correct owner
   ↓
allowed

Admin
   ↓
allowed when appropriate
```

This gives you a strong authorization matrix.

---

# 24. Authorization Matrix

Suppose:

```text
Resource: Todo
```

Rules:

|Action|Owner|Other User|Admin|
|---|--:|--:|--:|
|Read|✓|❌|✓|
|Update|✓|❌|✓|
|Delete|✓|❌|✓|

Your tests should reflect this matrix.

This is much easier to reason about than writing random authorization tests.

---

# 25. Course Example

For your LMS architecture, you could eventually have:

|Action|Student|Instructor|Admin|
|---|--:|--:|--:|
|View course|✓|✓|✓|
|Create course|❌|✓|✓|
|Update own course|❌|✓|✓|
|Update another instructor's course|❌|❌|✓|
|Delete course|❌|maybe|✓|

The exact rules depend on your application design.

The important part is:

> **Write the authorization matrix before writing the tests.**

---

# 26. Why This Is Better

Without a matrix:

```text
"Does this route work?"
```

With a matrix:

```text
"Who is allowed to perform this operation?"
```

That turns authorization into an explicit system.

---

# 27. Testing `req.user`

Authentication middleware usually creates:

```js
req.user
```

Authorization then uses:

```js
req.user.role
req.user.id
```

For example:

```js
if (req.user.role !== "admin") {
    throw new ForbiddenError();
}
```

Integration tests verify that the entire chain correctly produces the expected behavior.

---

# 28. Don't Trust the Client's User ID

This is critical.

A malicious client can send:

```json
{
    "userId": "someone-elses-id"
}
```

Your backend should not use that as the source of authorization.

Instead:

```text
JWT
 ↓
authenticate
 ↓
req.user.id
```

Then ownership queries should use:

```js
{
    userId: req.user.id
}
```

Your uploaded architecture specifically emphasizes authenticated-user ownership queries for preventing horizontal privilege escalation.

---

# 29. Example Attack

Suppose:

```http
PATCH /api/v1/todos/todo-A
```

Body:

```json
{
    "userId": "user-B",
    "title": "Hacked"
}
```

Your backend must not suddenly transfer ownership.

Bad:

```js
Todo.findByIdAndUpdate(
    todoId,
    req.body
);
```

Better architecture:

```text
authenticated user
       ↓
service
       ↓
ownership check
       ↓
allowed fields
       ↓
repository
```

Authorization testing should attempt these kinds of attacks.

---

# 30. Mass Assignment Connection

Authorization testing also connects to another security problem:

```text
Mass assignment
```

Suppose users are allowed to update:

```json
{
    "name": "Rahul"
}
```

but not:

```json
{
    "role": "admin"
}
```

A malicious request might send:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

Your test should make sure:

```text
role remains unchanged
```

This is a very valuable security test.

---

# 31. Example

```js
const response = await request(app)
    .patch("/api/v1/users/me")
    .set(
        "Authorization",
        `Bearer ${userToken}`
    )
    .send({
        name: "Rahul",
        role: "admin"
    });
```

Then verify:

```text
name → updated
role → unchanged
```

The endpoint should only update fields the user is allowed to modify.

---

# 32. Admin Authorization

Suppose:

```http
PATCH /api/v1/users/:id/role
```

is admin-only.

Test:

```text
anonymous → 401
student   → 403
instructor → 403
admin     → success
```

Then verify the database:

```text
student cannot become admin
```

This protects against vertical privilege escalation.

---

# 33. Authorization Failure Should Not Leak Data

Suppose User A requests User B's private resource.

Don't return:

```json
{
    "success": false,
    "message": "User B owns this resource"
}
```

That can reveal information.

Depending on your API's security design, you may return:

```json
{
    "success": false,
    "message": "Resource not found"
}
```

with:

```http
404
```

This is one reason authorization and information disclosure are closely related.

---

# 34. Testing Error Contracts

If your application standardizes errors, test the structure too.

For example:

```js
expect(response.status)
    .toBe(403);

expect(response.body)
    .toMatchObject({
        success: false
    });
```

If your contract has:

```json
{
    "success": false,
    "error": {
        "code": "FORBIDDEN"
    }
}
```

then test that contract:

```js
expect(response.body.error.code)
    .toBe("FORBIDDEN");
```

---

# 35. Don't Test Implementation Details

Avoid making your authorization integration tests depend heavily on:

```text
specific middleware function calls
private variables
Express internals
repository implementation
```

Instead test:

```text
given user
+
given resource
+
given action
=
expected authorization result
```

That's much more stable.

---

# 36. Authorization Test Pyramid

You can test authorization at several levels.

### Middleware unit test

```text
requireRole("admin")
        ↓
role = admin → next()
role = user  → error
```

### Service test

```text
user A
+
todo B
        ↓
service rejects
```

### Integration test

```text
HTTP
 ↓
Auth
 ↓
Authorization
 ↓
Controller
 ↓
Service
```

Use all three when appropriate.

---

# 37. The Most Valuable Integration Tests

If time is limited, prioritize:

```text
1. Anonymous access to protected route
2. Wrong role
3. Wrong owner
4. Correct owner
5. Admin access
6. Attempted privilege escalation
7. Database remains unchanged after rejection
```

These catch real security mistakes.

---

# 38. Example Complete Test

Conceptually:

```js
describe("DELETE /api/v1/todos/:id", () => {

    test("rejects unauthenticated user", async () => {
        const response = await request(app)
            .delete(`/api/v1/todos/${todo.id}`);

        expect(response.status)
            .toBe(401);
    });

    test("rejects another user's todo", async () => {
        const response = await request(app)
            .delete(`/api/v1/todos/${todo.id}`)
            .set(
                "Authorization",
                `Bearer ${otherUserToken}`
            );

        expect(response.status)
            .toBe(403);
    });

    test("allows owner", async () => {
        const response = await request(app)
            .delete(`/api/v1/todos/${todo.id}`)
            .set(
                "Authorization",
                `Bearer ${ownerToken}`
            );

        expect(response.status)
            .toBe(204);
    });
});
```

This is the kind of test that gives you real confidence.

---

# 39. A Better Way to Think About Authorization Tests

Don't ask:

> "Did my `requireRole()` middleware run?"

Ask:

> **"Can an unauthorized person actually perform the operation?"**

That's the mindset of security testing.

---

# 40. Your Authorization Checklist

For each protected endpoint, write:

```text
[ ] Anonymous request
[ ] Authenticated normal user
[ ] Wrong role
[ ] Correct role
[ ] Wrong resource owner
[ ] Correct resource owner
[ ] Admin
[ ] Privilege escalation attempt
[ ] Mass-assignment attempt where relevant
[ ] Database remains unchanged after rejection
```

You don't need every case for every endpoint, but this checklist helps you decide what matters.

# 43. The Key Lesson

The most important thing to remember from **21.12** is:

> **Authorization tests should prove that users cannot perform actions outside their permissions or ownership.**

Not merely:

```text
"authorization middleware was called"
```

but:

```text
User A
   ↓
tries User B's resource
   ↓
REJECTED
   ↓
database unchanged
```

And:

```text
Student
   ↓
tries admin operation
   ↓
REJECTED
```

while:

```text
Admin
   ↓
same operation
   ↓
ALLOWED
```

Your Phase 15 authorization curriculum specifically builds toward RBAC, permissions, resource ownership, horizontal/vertical privilege escalation, and secure ownership queries.
