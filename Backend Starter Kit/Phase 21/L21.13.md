# Lesson 21.13 — Testing CRUD

The Phase 21 roadmap places **21.13 specifically as “Testing CRUD”**, after Supertest, authentication testing, and authorization testing. The goal of this phase is to test the complete behavior of a CRUD resource through HTTP.

This lesson is where the previous lessons start connecting together.

---

# 1. What Are We Testing?

CRUD means:

```text
C → Create
R → Read
U → Update
D → Delete
```

For a resource such as `todos`:

```text
POST   /api/v1/todos
GET    /api/v1/todos
GET    /api/v1/todos/:id
PATCH  /api/v1/todos/:id
DELETE /api/v1/todos/:id
```

Our test shouldn't simply check that each controller function works.

We want to test the actual request flow:

```text
HTTP Request
     ↓
Route
     ↓
Middleware
     ↓
Authentication
     ↓
Authorization
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Database
     ↓
HTTP Response
```

That's the integration-testing model described in your architecture material.

---

# 2. Why CRUD Testing Is Different

Imagine your `createTodo()` controller has a passing unit test.

That tells us:

```text
Controller logic → probably works
```

But it doesn't tell us whether:

```text
POST /api/v1/todos
```

actually reaches that controller.

Maybe the route was accidentally registered as:

```text
POST /api/v1/todo
```

instead.

The controller test can still pass.

A CRUD integration test catches this.

---

# 3. Our Test Resource

We'll use a Todo API:

```text
Todo
├── _id
├── title
├── completed
└── userId
```

Suppose our API supports:

```text
POST   /api/v1/todos
GET    /api/v1/todos
GET    /api/v1/todos/:id
PATCH  /api/v1/todos/:id
DELETE /api/v1/todos/:id
```

And ownership works like:

```text
User A
  ├── Todo A
  └── Todo B

User B
  └── Todo C
```

A user should only manipulate their own todos unless they have elevated permissions.

---

# 4. CRUD Test Strategy

Don't think:

```text
"Let's write five tests."
```

Think in **behavioral scenarios**.

For Create:

```text
authenticated + valid input → 201
authenticated + invalid input → 400
unauthenticated → 401
```

For Read:

```text
authenticated → 200
resource exists → returned
resource doesn't exist → 404
other user's resource → rejected
```

For Update:

```text
owner + valid input → 200
invalid input → 400
other owner → rejected
```

For Delete:

```text
owner → success
other user → rejected
resource doesn't exist → 404
```

This produces much stronger tests.

```http
POST /api/v1/todos
```

```json
  "title": "Learn backend testing"

```

```json
  }

```

# 6. Create — Happy Path

Assume we already have:

```js
const userToken = ...
```

Then:

```js
const response = await request(app)
    .post("/api/v1/todos")
    .set(
        "Authorization",
        `Bearer ${userToken}`
    )
    .send({
        title: "Learn backend testing"
    });

expect(response.status)
    .toBe(201);
```

Then verify the response:

```js
expect(response.body.success)
    .toBe(true);
```

And:

```js
expect(response.body.data.title)
    .toBe("Learn backend testing");
```

---

# 7. Don't Stop at the HTTP Response

This is extremely important for CRUD tests.

Suppose the API returns:

```http
201
```

but the database didn't actually save anything.

Your test could incorrectly pass.

So after creating:

```js
const todo = await Todo.findById(
    response.body.data.id
);

expect(todo)
    .not
    .toBeNull();
```

Now we've tested:

```text
HTTP response
+
Database state
```

That's much stronger.

---

# 8. Create Test Flow

Think:

```text
POST /todos
      ↓
201
      ↓
Response contains ID
      ↓
Database lookup
      ↓
Todo exists
```

This is one of the most useful patterns in integration testing.

# 9. Create — Validation Failure

Now send:

```js
const response = await request(app)
    .post("/api/v1/todos")
    .set(
        "Authorization",
        `Bearer ${userToken}`
    )
    .send({});
```

If `title` is required:

```js
expect(response.status)
    .toBe(400);
```

And verify:

```js
expect(response.body.success)
    .toBe(false);
```

This tests:

```text
HTTP
 ↓
validation middleware
 ↓
rejected
```

without reaching the database.

---

# 10. Create — Unauthenticated

Don't send a token:

```js
const response = await request(app)
    .post("/api/v1/todos")
    .send({
        title: "Should fail"
    });
```

Expected:

```js
expect(response.status)
    .toBe(401);
```

This protects your authentication boundary.

---

# 11. Create — Database State Should Not Change

For rejected requests, it's useful to make sure nothing was created.

For example:

```js
const before = await Todo.countDocuments();

const response = await request(app)
    .post("/api/v1/todos")
    .send({});

expect(response.status)
    .toBe(400);

const after = await Todo.countDocuments();

expect(after)
    .toBe(before);
```

Now you know:

```text
Invalid request
    ↓
Rejected
    ↓
No database mutation
```

# 12. Read All

Endpoint:

```http
GET /api/v1/todos
```

Test:

```js
const response = await request(app)
    .get("/api/v1/todos")
    .set(
        "Authorization",
        `Bearer ${userToken}`
    );

expect(response.status)
    .toBe(200);
```

Then:

```js
expect(response.body.success)
    .toBe(true);
```

And:

```js
expect(
    Array.isArray(response.body.data)
).toBe(true);
```

# 13. Test Ownership on Read

Suppose:

```text
User A
 └── Todo A

User B
 └── Todo B
```

User A requests:

```http
GET /api/v1/todos
```

The response should contain:

```text
Todo A
```

but not:

```text
Todo B
```

This is a very important authorization test.

For example:

```js
expect(
    response.body.data.some(
        todo => todo.id === todoB.id
    )
).toBe(false);
```

You are verifying that your repository/service ownership filtering works correctly.

---

# 14. Why This Test Is Important

A dangerous implementation might accidentally do:

```js
Todo.find({})
```

instead of:

```js
Todo.find({
    userId
});
```

The endpoint would still return `200`.

A normal happy-path test might pass.

But the ownership test catches the security bug.

Your architecture material specifically emphasizes ownership-aware queries such as:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

as an important authorization pattern.

```js
const response = await request(app)
```

# 16. Read One — Missing Resource

Create a fake/nonexistent ID.

For example:

```js
const response = await request(app)
    .get("/api/v1/todos/507f1f77bcf86cd799439011")
    .set(
        "Authorization",
        `Bearer ${userToken}`

```

Expected:

```js
expect(response.status)
    .toBe(404);
```

Your test should protect the API contract:

```text
Resource doesn't exist
        ↓
404
```

# 17. Read One — Wrong Owner

User A:

```text
GET /todos/todo-B
```

where Todo B belongs to User B.

```js
const response = await request(app)
    .get(`/api/v1/todos/${todoB.id}`)
    .set(
        "Authorization",
        `Bearer ${userAToken}`
    );
```

Depending on your API contract:

```js
expect(response.status)
    .toBe(403);
```

or:

```js
expect(response.status)
    .toBe(404);
```

The important thing is that:

```text
User A must not receive Todo B.
```

# 20. Update — Invalid Data

Try:

```js
const response = await request(app)
    .patch(`/api/v1/todos/${todo.id}`)

        `Bearer ${userToken}`

```

# 21. Update — Wrong Owner

User A attempts:

```text
PATCH Todo B
```

```js
const response = await request(app)
    .patch(`/api/v1/todos/${todoB.id}`)
    .set(
        "Authorization",
        `Bearer ${userAToken}`
    )
    .send({
        title: "Hacked"
    });
```

Expected:

```js
expect([403, 404])
    .toContain(response.status);
```

Then:

```js
const unchangedTodo =
    await Todo.findById(todoB.id);

expect(unchangedTodo.title)
    .not
    .toBe("Hacked");
```

This is a **very strong security test**.

# 25. CRUD Test Matrix

You can create a simple matrix before writing tests:

|Operation|Scenario|Expected|
|---|---|--:|
|Create|valid user|`201`|
|Create|invalid input|`400`|
|Create|anonymous|`401`|
|Read all|own resources|`200`|
|Read all|other user's resources hidden|`200`|
|Read one|existing own resource|`200`|
|Read one|missing|`404`|
|Read one|another user's resource|`403/404`|
|Update|owner + valid data|`200`|
|Update|invalid data|`400`|
|Update|wrong owner|`403/404`|
|Delete|owner|`204`|
|Delete|wrong owner|`403/404`|
|Delete|missing|`404`|

This becomes your CRUD testing blueprint.

---

# 26. Don't Create Tests in Random Order

A useful order is:

```text
Create
  ↓
Read
  ↓
Update
  ↓
Delete
```

Because later operations depend on resources created during setup.

But there's an important rule:

> **Don't make tests depend on each other.**

Never do:

```text
test 1 creates todo
       ↓
test 2 expects todo from test 1
       ↓
test 3 updates it
```

We'll deal with proper isolation in **21.15**.

For now, understand the problem.

# 28. CRUD Tests Are Contract Tests Too

Remember your API response architecture.

For example, your starter architecture expects consistent responses such as:

```json
{
  "success": true,
  "message": "Todo created successfully",
  "data": {}
}
```

and errors such as:

```json
{
  "success": false,
  "message": "Todo not found",
  "requestId": "..."
}
```

Your CRUD integration tests should verify these contracts where they matter.

For example:

```js
expect(response.body)
    .toMatchObject({
        success: true
    });
```

# 29. Don't Over-Test the Same Thing

Suppose you already have a unit test proving:

```js
todoService.createTodo()
```

correctly handles a particular business rule.

Your integration test doesn't need to reproduce every internal assertion.

Instead, focus on:

```text
HTTP input
      ↓
correct system behavior
      ↓
HTTP output
      ↓
important database state
```

This keeps integration tests useful and maintainable.

# 31. A Complete CRUD Test File

A simplified structure:

```js
import request from "supertest";
import app from "../../src/app.js";

describe("Todo CRUD API", () => {

    describe("POST /api/v1/todos", () => {
        test("creates a todo", async () => {
            // ...
        });

        test("rejects invalid input", async () => {
            // ...
        });

        test("rejects unauthenticated user", async () => {
            // ...
        });
    });

    describe("GET /api/v1/todos", () => {
        test("returns user's todos", async () => {
            // ...
        });
    });

    describe("GET /api/v1/todos/:id", () => {
        test("returns todo", async () => {
            // ...
        });

        test("returns 404 for missing todo", async () => {
            // ...
        });

        test("does not expose another user's todo", async () => {
            // ...
        });
    });

    describe("PATCH /api/v1/todos/:id", () => {
        test("updates todo", async () => {
            // ...
        });

        test("rejects another user's todo", async () => {
            // ...
        });
    });

    describe("DELETE /api/v1/todos/:id", () => {
        test("deletes todo", async () => {
            // ...
        });

        test("rejects another user's todo", async () => {
            // ...
        });
    });
});
```

This is a good organizational pattern.

```text

│   ├── success

│   └── authentication
│
```

# 33. Test the Complete CRUD Lifecycle

A very useful mental model:

```text
CREATE
  │
  ▼
resource exists
  │
  ▼
READ
  │
  ▼
resource returned
  │
  ▼
UPDATE
  │
  ▼
resource changed
  │
  ▼
READ again
  │
  ▼
new data returned
  │
  ▼
DELETE
  │
  ▼
resource removed
```

This represents the complete lifecycle of a resource.

---

# 34. But Don't Put the Whole Lifecycle in One Test

Avoid:

```js
test("complete CRUD", async () => {
    // create
    // read
    // update
    // delete
});
```

Why?

If it fails at update, you don't immediately know whether:

```text
create
read
```

also work independently.

Better:

```text
test create
test read
test update
test delete
```

with isolated setup.

---

# 35. One Test = One Behavior

Good:

```js
test("owner can update todo", ...)
```

Good:

```js
test("another user cannot update todo", ...)
```

Good:

```js
test("missing todo returns 404", ...)
```

Less useful:

```js
test("todo API works", ...)
```

Specific names make your test suite almost read like documentation.

# 36. A Very Important Security Test

Let's say User A owns:

```text
todo-A
```

User B sends:

```http
PATCH /api/v1/todos/todo-A
Authorization: Bearer user-B
```

with:

```json
{
  "title": "Hacked"
}
```

Your test should verify **three things**:

### 1. HTTP request rejected

```js
expect(response.status)
    .toBe(403);
```

### 2. Original resource remains unchanged

```js
expect(todo.title)
    .toBe(originalTitle);
```

### 3. User B didn't gain access

This turns a basic authorization test into a real security test.

# 37. Another Important Test: Mass Assignment

Suppose users cannot modify their own role.

Send:

```js
.send({
    name: "Rahul",
    role: "admin"
});
```

Then:

```js
expect(response.status)
    .toBe(200);
```

might still be correct.

But after fetching the user:

```js
expect(user.role)
    .not
    .toBe("admin");
```

The allowed field changed:

```text
name → changed
```

The forbidden field stayed:

```text
role → unchanged
```

This connects your CRUD tests with the security testing you'll study in Phase 22.

# 43. Final Checklist

Before considering a CRUD endpoint properly tested, ask:

```text
CREATE
✓ Can a valid user create?
✓ Does invalid input fail?
✓ Does unauthenticated access fail?
✓ Is the database changed correctly?

READ
✓ Can the owner read?
✓ Are other users' resources protected?
✓ Does missing data return the correct response?

UPDATE
✓ Can the owner update?
✓ Is invalid data rejected?
✓ Is another user's resource protected?
✓ Is the database actually updated?

DELETE
✓ Can the owner delete?
✓ Is another user's resource protected?
✓ Is missing data handled?
✓ Is the resource actually deleted?

RESPONSE
✓ Correct status?
✓ Correct response structure?
✓ Correct error structure?

SECURITY
✓ No ownership bypass?
✓ No privilege escalation?
✓ No unauthorized database mutation?
```
