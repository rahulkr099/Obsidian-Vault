# Lesson 21.14 — Test Database

This lesson is the natural next step after **21.13 Testing CRUD**.

Your Phase 21 roadmap explicitly places the lessons in this order:

```text
21.13 Testing CRUD
21.14 Test database
21.15 Test isolation
21.16 Mocking
21.17 Fixtures
21.18 Coverage
21.19 Build backend test architecture
```

The main question today is:

> **Where should our integration tests store their data?**

---

# 1. Why Do We Need a Test Database?

Imagine your development database is:

```text
MongoDB
└── myapp
    ├── users
    ├── todos
    ├── courses
    └── orders
```

Now you run:

```bash
npm test
```

Your tests create:

```text
User A
User B
Todo A
Todo B
```

If those tests use your normal development database, you're mixing:

```text
Development data
+
Test data
```

That's dangerous.

A test might accidentally:

- delete your development data
    
- modify real records
    
- depend on old records
    
- leave thousands of test documents
    
- produce different results on different machines
    

So we want:

```text
Development
     ↓
myapp

Testing
     ↓
myapp_test
```

Separate environments.

---

# 2. The Core Principle

Your test database should be:

> **Disposable, isolated, predictable, and safe.**

Think:

```text
Production DB
    ❌ Never touch

Development DB
    ❌ Don't use for automated tests

Test DB
    ✅ Specifically created for tests
```

This becomes especially important once your CRUD integration tests interact with MongoDB.

---

# 3. Why Mocking MongoDB Isn't Always Enough

You might think:

> "Why don't we just mock MongoDB?"

Because then you aren't testing the real database behavior.

For example:

```text
POST /todos
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Mock MongoDB
```

You aren't proving that:

```text
Repository
    ↓
Mongoose
    ↓
MongoDB
```

actually works.

For repository and CRUD integration tests, a real test database gives you much more confidence.

Your roadmap specifically separates **integration testing**, **repository testing**, **CRUD testing**, and later **mocking**, which is a good distinction.

---

# 4. The Three Database Environments

Eventually your backend may have:

```text
development
test
production
```

For example:

```text
NODE_ENV=development
```

uses:

```text
mongodb://localhost:27017/myapp
```

while:

```text
NODE_ENV=test
```

uses:

```text
mongodb://localhost:27017/myapp_test
```

and production uses a completely different connection.

Conceptually:

```text
NODE_ENV
   │
   ├── development → development DB
   │
   ├── test        → test DB
   │
   └── production  → production DB
```

---

# 5. Never Hard-Code the Test Database Everywhere

Avoid:

```js
mongoose.connect(
    "mongodb://localhost:27017/myapp_test"
);
```

inside your test files.

That makes your tests tightly coupled to the database configuration.

Instead:

```text
Environment
    ↓
Config
    ↓
Database connection
    ↓
Application
```

Your existing starter architecture already emphasizes centralized environment configuration rather than scattering `process.env` throughout the application.

---

# 6. Test Environment Variables

You might have:

```text
.env
.env.example
.env.test
```

For example:

```env
NODE_ENV=test
MONGO_URI=mongodb://127.0.0.1:27017/myapp_test
```

The exact environment-loading strategy can vary, but the important principle is:

> **Tests must explicitly know that they are running against a test database.**

---

# 7. Why `NODE_ENV=test` Matters

When you execute:

```bash
npm test
```

you want:

```text
NODE_ENV=test
```

Then your application knows:

```text
I'm running tests.
```

This lets you change behavior safely.

For example:

```js
if (env.nodeEnv === "test") {
    // test-specific behavior
}
```

But be careful.

Don't create a huge number of:

```js
if (NODE_ENV === "test")
```

branches.

The test environment should mostly change **configuration**, not your business logic.

A clean architecture looks like:

```text
tests
  │
  ▼

  │
  ▼

  │
  ▼

  │
  ▼

```

Then:

```text

   ↓

   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Test MongoDB
```

This is a real integration test.

---

# 9. What Should Happen Before Tests?

Before running integration tests:

```text
Start test database
        ↓
Connect Mongoose
        ↓
Run tests
```

For example:

```text
npm test
   ↓
MongoDB available
   ↓
Connect
   ↓
Jest starts
   ↓
Tests execute
```

If the database isn't available:

```text
Tests should fail clearly.
```

You don't want mysterious errors like:

```text
Cannot read properties of undefined
```

when the real problem is:

```text
MongoDB isn't running.
```

---

# 10. A Simple Database Helper

You can create:

```text
tests/
└── helpers/
    └── database.js
```

Conceptually:

```js
export async function connectTestDatabase() {
    // connect to test MongoDB
}

export async function disconnectTestDatabase() {
    // close connection
}

export async function clearTestDatabase() {
    // remove test data
}
```

Then your tests don't need to know the connection details.

---

# 11. Why Put This in a Helper?

Without a helper:

```js
beforeAll(async () => {
    await mongoose.connect(...);
});

afterAll(async () => {
    await mongoose.disconnect();
});
```

repeated across multiple files.

That becomes messy.

Instead:

```js
beforeAll(connectTestDatabase);

afterAll(disconnectTestDatabase);
```

Much cleaner.

---

# 12. `beforeAll`

Jest provides:

```js
beforeAll()
```

It runs once before all tests in a test scope.

Example:

```js
beforeAll(async () => {
    await connectTestDatabase();
});
```

Conceptually:

```text
beforeAll
    ↓
Connect DB
    ↓
Test 1
Test 2
Test 3
Test 4
    ↓
afterAll
```

---

# 13. `afterAll`

After all tests:

```js
afterAll(async () => {
    await disconnectTestDatabase();
});
```

This is important because MongoDB connections are open resources.

If you forget to close them, Jest may complain:

```text
Jest did not exit one second after the test run has completed.
```

The underlying reason can be an open database connection.

---

# 14. Basic Structure

Your integration test might look like:

```js
describe("Todo API", () => {

    beforeAll(async () => {
        await connectTestDatabase();
    });

    afterAll(async () => {
        await disconnectTestDatabase();
    });

    test("creates a todo", async () => {
        // ...
    });

    test("gets todos", async () => {
        // ...
    });
});
```

This is the basic pattern.

---

# 15. But There's a Problem

Suppose Test 1 creates:

```text
Todo A
```

Then Test 2 asks:

```text
GET /todos
```

It might receive:

```text
Todo A
```

But perhaps Test 2 was supposed to start with **zero todos**.

Now Test 2 depends on Test 1.

That's bad.

This brings us to the next lesson:

> **21.15 Test Isolation**

But we need to understand the database setup first.

---

# 16. Clearing the Database

One simple strategy is:

```text
before each test
      ↓
clear database
      ↓
create required test data
      ↓
run test
```

Conceptually:

```js
beforeEach(async () => {
    await clearTestDatabase();
});
```

Then:

```text
Test 1
  ↓
empty DB
  ↓
setup data
  ↓
test

Test 2
  ↓
empty DB
  ↓
setup data
  ↓
test
```

This creates predictable tests.

The deeper isolation strategy is the subject of **21.15**, so don't worry about optimizing this yet.

---

# 17. What Does "Clear Database" Mean?

For a simple MongoDB test database, you might remove documents from each collection.

Conceptually:

```js
const collections =
    mongoose.connection.collections;

for (const key of Object.keys(collections)) {
    await collections[key].deleteMany({});
}
```

This means:

```text
users     → empty
todos     → empty
courses   → empty
```

The database itself remains.

You're clearing its contents.

---

# 18. Don't Drop Your Development Database

This is where environment separation becomes extremely important.

Imagine:

```js
await mongoose.connection.dropDatabase();
```

This is powerful.

If your connection accidentally points to:

```text
myapp
```

instead of:

```text
myapp_test
```

you could destroy your development database.

That's why you should make test database protection explicit.

---

# 19. Add a Safety Check

Before destructive test setup, verify:

```js
if (env.nodeEnv !== "test") {
    throw new Error(
        "Refusing to clear non-test database"
    );
}
```

Then:

```text
NODE_ENV=test
      ↓
allowed

NODE_ENV=development
      ↓
STOP
```

This is a fantastic safety habit.

---

# 20. Test Database Naming

A simple convention:

```text
myapp
myapp_test
```

or:

```text
myapp_development
myapp_test
myapp_production
```

For local MongoDB:

```text
mongodb://127.0.0.1:27017/myapp_test
```

The important thing is that the database name makes its purpose obvious.

---

# 21. Test Database Should Never Contain Real Data

Your test database should contain:

```text
fake users
fake todos
fake courses
fake tokens
```

Not:

```text
real customer
real password
real payment information
real production records
```

Automated tests should use synthetic data.

---

# 22. Test Database and Passwords

Suppose your user model stores:

```text
passwordHash
```

Your test users should still use the real hashing flow if you're testing authentication integration.

For example:

```text
test password
      ↓
bcrypt
      ↓
passwordHash
      ↓
test database
```

Don't manually insert:

```text
password: "123456"
```

into a field that expects a hash.

Otherwise your tests don't represent real application behavior.

---

```text
   ↓
```

Now you're testing:


That's much more realistic.

# 26. Don't Change Business Logic for Tests

A bad approach:

```js

    return fakeTodo;
}
```

Now you're not testing the real application.

Better:

```text

    +

```

So:

```text

       ≈

```

with the main difference being infrastructure/configuration.

# 30. One Important Question

You might ask:

> Should every test file connect to MongoDB separately?

Usually, no.

You generally want a controlled test setup.

For example:

```text
Jest

 ├── test setup
 │      ↓
 │   connect DB
 │
 ├── auth tests
 ├── todo tests
 ├── user tests

 └── cleanup
        ↓
     disconnect
```

The exact setup depends on your Jest configuration and whether tests run in parallel.

That last part becomes important when we discuss **test isolation**.

# 33. The Test Lifecycle

Remember this:

```text
             TEST LIFECYCLE

        beforeAll
            │
            ▼
      Connect DB
            │
            ▼
       beforeEach
            │
            ▼
       Clear DB
            │
            ▼
        Test runs
            │
            ▼
       afterEach
            │
            ▼
        Next test
            │
            ▼
       afterAll
            │
            ▼

```

You don't necessarily need all four hooks in every file.

But understand what each one means.

---

# 34. `beforeAll` vs `beforeEach`

This distinction is very important.

### `beforeAll`

Runs once:

```text
beforeAll
   ↓
Test 1
Test 2
Test 3
Test 4
```

Good for:

```text
database connection
server setup
expensive shared infrastructure
```

### `beforeEach`

Runs before every test:

```text
beforeEach → Test 1
beforeEach → Test 2
beforeEach → Test 3
beforeEach → Test 4
```

Good for:

```text
clearing data
creating test-specific records
resetting state
```

---

# 35. `afterAll`

Use it for:

```text
closing DB
closing server resources
stopping test infrastructure
```

Example:

```js
afterAll(async () => {
    await mongoose.disconnect();
});
```

---

# 36. What About `afterEach`?

You can use:

```js
afterEach(...)
```

for cleanup that needs to happen after every test.

For example:

```text
Test
 ↓
temporary resource
 ↓
afterEach
 ↓
cleanup
```

But don't blindly clean everything in both:

```text
beforeEach
+
afterEach
```

unless there's a reason.

Keep your lifecycle simple.

---

# 37. Test Database Errors

What if MongoDB isn't running?

Your test setup should fail early.

For example:

```text
npm test
   ↓
connectTestDatabase()
   ↓
connection fails
   ↓
tests stop
```

That's much better than running 50 tests that all fail with unrelated-looking errors.

---

# 38. Test Database Connection Timeout

A test database connection should not hang forever.

Your MongoDB client/configuration can use sensible timeouts.

Conceptually:

```text
connect
 ↓
database unavailable
 ↓
timeout
 ↓
clear error
```

You want:

```text
"Cannot connect to test database"
```

rather than:

```text
Test timed out after 5 minutes.
```

# 39. In-Memory MongoDB

There is another approach:

> **Run MongoDB in memory for tests.**

A commonly used ecosystem option is an in-memory MongoDB server.

Conceptually:

```text
Jest
 ↓
Start temporary MongoDB
 ↓
Run tests
 ↓
Stop MongoDB
 ↓
Everything disappears
```

Advantages:

```text
No permanent test data
Easy cleanup
Isolated environment
Good CI experience
```

But there are tradeoffs.

---

# 40. Real MongoDB vs In-Memory MongoDB

### Real test MongoDB

```text
MongoDB process
     ↓
myapp_test
```

Pros:

- very close to your normal environment
    
- useful for realistic MongoDB behavior
    
- straightforward if MongoDB already runs locally/CI
    

Cons:

- requires MongoDB infrastructure
    
- cleanup required
    
- CI setup can be more involved
    

### In-memory MongoDB

```text
Test process
     ↓
temporary MongoDB
```

Pros:

- isolated
    
- disposable
    
- convenient for tests
    

Cons:

- additional setup/dependency
    
- may differ from production infrastructure
    
- memory/resource considerations
    

The important lesson isn't "always use one."

It's:

> **Use a database environment specifically designed for tests.**

# 43. A Critical Safety Rule

Never let:

```text
npm test
```

automatically connect to:

```text
production
```

Your configuration should make this practically impossible.

For example, you can enforce:

```js
if (
    env.nodeEnv === "test" &&
    !env.mongoUri.includes("test")
) {
    throw new Error(
        "Test environment must use test database"
    );
}
```

The exact check can vary.

The principle is excellent:

> **Fail closed.**

If the test database configuration looks dangerous, stop.

---

# 44. Database Reset Strategy

There are several ways to reset test state.

### Option 1 — Delete documents

```text
deleteMany({})
```

Simple and clear.

### Option 2 — Drop collections

```text
drop collection
```

Useful but more destructive.

### Option 3 — Drop database

```text
dropDatabase()
```

Very destructive, so only use it when you have strong environment safeguards.

### Option 4 — Transaction rollback

Some test architectures use database transactions:

```text
begin transaction
     ↓
run test
     ↓
rollback
```

This can be very fast, but it depends on your database architecture and the operations you're testing.

You don't need this complexity yet.

# 46. Practical Example

Imagine:

```text
tests/integration/todo.test.js
```

We can conceptually write:

```js
describe("Todo API", () => {

    beforeAll(async () => {
        await connectTestDatabase();
    });

    beforeEach(async () => {
        await clearTestDatabase();
    });

    afterAll(async () => {
        await disconnectTestDatabase();
    });

    test("creates todo", async () => {
        const user = await createTestUser();

        const response = await request(app)
            .post("/api/v1/todos")
            .set(
                "Authorization",
                `Bearer ${user.token}`
            )
            .send({
                title: "Learn testing"
            });

        expect(response.status)
            .toBe(201);
    });
});
```

Notice the architecture:

```text
Jest
 │
 ├── beforeAll
 │      └── Test DB
 │
 ├── beforeEach
 │      └── Clean state
 │
 ├── Supertest
 │      ↓
 │    Express
 │      ↓
 │    Backend
 │      ↓
 │    MongoDB
 │
 └── afterAll
        └── Disconnect
```
