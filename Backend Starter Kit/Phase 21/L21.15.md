# Lesson 21.15 — Test Isolation

This is one of the most important lessons in backend testing.

You now have:

```text
21.13 → Testing CRUD
21.14 → Test Database
21.15 → Test Isolation  ← YOU ARE HERE
21.16 → Mocking
21.17 → Fixtures
21.18 → Coverage
21.19 → Build Backend Test Architecture
```

The purpose of test isolation is simple:

> **Every test should be able to run independently and produce the same result regardless of what other tests ran before it.**

---

# 1. The Problem

Imagine these tests:

```js
test("creates a todo", async () => {
    // creates Todo A
});

test("returns empty todo list", async () => {
    // expects []
});
```

If the first test runs first:

```text
Test 1
  ↓
creates Todo A
  ↓
Test 2
  ↓
GET /todos
  ↓
[Todo A]
```

Test 2 fails.

But if Test 2 runs first:

```text
Test 2
  ↓
[]
  ↓
Test 1
  ↓
creates Todo A
```

Test 2 passes.

That means the test suite has **order-dependent tests**.

That's bad.

---

# 2. What Does Isolation Mean?

A properly isolated test looks like:

```text
Test A
  ↓
setup
  ↓
run
  ↓
cleanup
  ↓
finished

Test B
  ↓
setup
  ↓
run
  ↓
cleanup
  ↓
finished
```

Test B doesn't care what Test A did.

---

# 3. The Golden Rule

Remember this:

> **A test should own the state it depends on.**

If a test needs:

```text
User A
Todo A
```

the test should create or obtain that state through controlled setup.

Don't depend on:

```text
"That user was created by another test."
```

---

# 4. Bad Test Dependency

This is bad:

```js
let todoId;

test("creates todo", async () => {
    const response = await createTodo();

    todoId = response.body.data.id;
});

test("updates todo", async () => {
    await request(app)
        .patch(`/todos/${todoId}`);
});
```

The second test depends on the first.

If you run:

```bash
npx jest -t "updates todo"
```

the second test fails.

That's a clear sign of poor isolation.

---

# 5. Better Approach

Each test creates what it needs:

```js
test("updates todo", async () => {
    const todo = await createTestTodo();

    const response = await request(app)
        .patch(`/todos/${todo.id}`)
        .send({
            title: "Updated"
        });

    expect(response.status).toBe(200);
});
```

Now:

```text
Run only this test
        ↓
works
```

That's isolation.

---

# 6. `beforeEach()`

One of your most useful tools is:

```js
beforeEach()
```

Example:

```js
beforeEach(async () => {
    await clearTestDatabase();
});
```

Then:

```text
beforeEach
   ↓
Test 1

beforeEach
   ↓
Test 2

beforeEach
   ↓
Test 3
```

Each test starts from a known database state.

---

# 7. Why `beforeAll()` Isn't Enough

You might have:

```js
beforeAll(async () => {
    await clearTestDatabase();
});
```

Then:

```text
beforeAll
   ↓
empty DB

Test 1
   ↓
creates Todo A

Test 2
   ↓
Todo A still exists
```

So `beforeAll()` doesn't isolate individual tests.

It only prepares the test suite once.

---

# 8. `beforeEach()` Gives You a Fresh Start

Instead:

```js
beforeEach(async () => {
    await clearTestDatabase();
});
```

Now:

```text
beforeEach
   ↓
empty DB
   ↓
Test 1
   ↓
data created

beforeEach
   ↓
empty DB
   ↓
Test 2
```

Much safer.

---

# 9. Database Isolation

For MongoDB, a simple strategy is:

```js
async function clearTestDatabase() {
    const collections =
        mongoose.connection.collections;

    for (const key of Object.keys(collections)) {
        await collections[key].deleteMany({});
    }
}
```

Then:

```js
beforeEach(async () => {
    await clearTestDatabase();
});
```

Conceptually:

```text
users      → []
todos      → []
courses    → []
sessions   → []
```

before each test.

---

# 10. But Don't Blindly Delete Everything

Suppose your tests eventually involve:

```text
users
roles
permissions
organizations
courses
lessons
todos
orders
payments
```

Deleting everything before every test can become expensive.

So isolation has multiple strategies.

We'll start simple, then optimize when necessary.

---

# 11. Isolation Strategy #1 — Clear Database

The easiest:

```text
Before test
    ↓
Delete all documents
    ↓
Create required data
    ↓
Run test
```

Advantages:

```text
✓ Very simple
✓ Easy to understand
✓ Highly predictable
✓ Good for learning
```

Disadvantages:

```text
✗ Can become slow
✗ More database operations
```

For your current backend learning project, this is an excellent starting point.

---

# 12. Isolation Strategy #2 — Clear Specific Collections

Suppose you're testing todos.

You could clear only:

```js
await Todo.deleteMany({});
```

instead of everything.

For example:

```text
users       → preserved
todos       → cleared
```

This can be faster.

But now you're responsible for understanding dependencies.

---

# 13. The Hidden Problem

Suppose:

```text
Todo
  ↓
references User
```

If you clear:

```text
todos
```

but preserve:

```text
users
```

that's fine.

But if you clear:

```text
users
```

and leave:

```text
todos
```

you may create invalid references.

So cleanup strategy must understand your data relationships.

---

# 14. Isolation Strategy #3 — Unique Data

Another strategy is to generate unique values.

Instead of:

```js
{
    email: "test@example.com"
}
```

use something like:

```js
{
    email: `test-${crypto.randomUUID()}@example.com`
}
```

Now different tests can create:

```text
test-a@example.com
test-b@example.com
test-c@example.com
```

without collisions.

But unique data **does not replace cleanup**.

It solves:

```text
duplicate-value collisions
```

not:

```text
shared state
```

---

# 15. Isolation Strategy #4 — Transactions

A more advanced technique is:

```text
BEGIN TRANSACTION
       ↓
run test
       ↓
ROLLBACK
```

Example:

```text
Database
   │
   ├── existing state
   │
   └── transaction
          │
          ├── create user
          ├── create todo
          └── update todo
               │
               ▼
            rollback
               │
               ▼
          original state
```

This can be very fast.

But it introduces complexity, especially when your application uses multiple connections, background jobs, or operations outside the transaction.

For your MongoDB backend, don't make this your first isolation strategy.

---

# 16. Isolation Strategy #5 — Separate Database Per Test

You can theoretically do:

```text
Test 1 → myapp_test_1
Test 2 → myapp_test_2
Test 3 → myapp_test_3
```

This gives excellent isolation.

But it's usually unnecessary for a normal backend test suite.

It becomes more interesting when tests run in parallel or when you need very strong isolation.

---

# 17. Test Isolation Is More Than Database Isolation

This is important.

Even if the database is clean, your test may still share:

```text
global variables
environment variables
mock state
caches
files
queues
Redis
sessions
timers
event listeners
```

So:

> **Test isolation means isolating all mutable state, not just MongoDB.**

---

# 18. Global Variables

Bad:

```js
let currentUser;

test("creates user", async () => {
    currentUser = await createUser();
});

test("gets user", async () => {
    expect(currentUser).toBeDefined();
});
```

The second test depends on the first.

Better:

```js
test("gets user", async () => {
    const currentUser = await createUser();

    // test
});
```

Keep state as local as possible.

---

# 19. Environment Variables

Suppose one test changes:

```js
process.env.NODE_ENV = "production";
```

Then another test may accidentally run with:

```text
NODE_ENV=production
```

That's shared global state.

If you need to modify environment variables temporarily, restore them afterward.

Conceptually:

```js
const original = process.env.SOME_VALUE;

process.env.SOME_VALUE = "test";

// test

process.env.SOME_VALUE = original;
```

---

# 20. Mock State

We'll study mocking in **21.16**, but you should understand the isolation problem now.

Suppose:

```js
jest.mock(...)
```

changes behavior for one test.

If that mock remains active, another test might receive the mocked behavior.

So mocks need cleanup/reset too.

Think:

```text
Test A
 ↓
mock
 ↓
reset
 ↓
Test B
```

not:

```text
Test A
 ↓
mock
 ↓
Test B
 ↓
still mocked
```

---

# 21. Cache State

Imagine your application has:

```js
cache.set("user:123", user);
```

Test A creates the cache entry.

Test B expects:

```text
cache is empty
```

But it isn't.

Database cleanup won't fix this.

You need:

```js
cache.clear();
```

or an appropriate test-specific reset.

---

# 22. Redis Isolation

Later your backend may use Redis for:

```text
sessions
rate limiting
caching
queues
```

Then you have another shared state problem.

You don't want:

```text
Development Redis
      ↑
     tests
```

Instead:

```text
Development
   ↓
Redis DB 0

Testing
   ↓
Redis DB 1
```

or a completely separate Redis instance.

The same principle applies:

> **Never let automated tests modify shared development infrastructure.**

---

# 23. File System Isolation

Suppose a test generates:

```text
/uploads/profile.png
```

If another test expects the directory to be empty, you've created shared state.

Use temporary directories:

```text
tests/tmp/
```

and clean them.

Or generate unique paths:

```text
/tmp/test-<uuid>/
```

---

# 24. Port Isolation

This becomes important when testing servers.

Suppose your development server uses:

```text
localhost:5000
```

Don't start your tests on the same port if you don't need to.

With Supertest, you can generally test the Express app directly:

```js
request(app)
```

without manually opening a network port.

That's one reason Supertest is convenient.

---

# 25. Queue Isolation

Imagine your application sends:

```text
sendWelcomeEmail()
```

through a queue.

Test A creates a user.

The queue receives:

```text
welcome-email
```

Then Test B starts.

If the queue isn't reset, Test B may encounter Test A's job.

You need to isolate or clean:

```text
queue
workers
jobs
```

when testing these systems.

This becomes especially relevant to the email architecture you studied in Phase 20.

---

# 26. Test Isolation and Async Code

This is a common source of bugs.

Bad:

```js
test("creates todo", async () => {
    createTodo(); // forgot await
});
```

The test may finish before the operation completes.

Then the next test starts while the previous operation is still running.

Now you have:

```text
Test A
   ↓
async operation still running
   ↓
Test A finishes
   ↓
cleanup
   ↓
Test B
   ↓
Test A's operation completes
```

Chaos.

Always properly await asynchronous work:

```js
await createTodo();
```

---

# 27. Background Jobs

This gets even more important with:

```text
emails
queues
cron jobs
events
workers
```

Imagine:

```text
Test A
 ↓
create user
 ↓
event emitted
 ↓
background worker
 ↓
email job
```

If the test ends while the worker is still processing:

```text
cleanup
 ↓
worker continues
 ↓
unexpected DB operation
```

That can cause extremely confusing failures.

The solution is controlled lifecycle management.

---

# 28. Test Isolation and Events

Suppose:

```js
eventBus.emit("user.created", user);
```

If your test registers a listener:

```js
eventBus.on("user.created", handler);
```

and never removes it, the next test might receive the event too.

You can end up with:

```text
Test 1 → listener A
Test 2 → listener A + listener B
Test 3 → listener A + listener B + listener C
```

This creates memory leaks and duplicated behavior.

Clean up listeners.

---

# 29. Why Tests Sometimes Pass Individually but Fail Together

This is a classic symptom.

Run:

```bash
npx jest todo.test.js
```

Everything passes.

Run:

```bash
npm test
```

Some tests fail.

Often this means:

```text
shared state
```

or:

```text
test order dependency
```

or:

```text
parallel execution conflict
```

This is one of the main reasons test isolation matters.

---

# 30. Order Independence

A strong test suite should behave approximately like:

```text
A → B → C
```

and:

```text
C → A → B
```

and:

```text
B → C → A
```

The results should remain the same.

You shouldn't need to know:

> "Run authentication tests before todo tests."

If you do, your test architecture has shared state.

---

# 31. Parallel Tests

Modern test runners can execute tests concurrently.

Imagine:

```text
Test A ────────────────┐
                       │
Test B ────────────────┼──→ same DB
                       │
Test C ────────────────┘
```

Now imagine:

```text
Test A
deleteMany()

Test B
create user

Test C
query users
```

If these happen simultaneously:

```text
Test B creates user
       ↓
Test A deletes users
       ↓
Test C finds nothing
```

Now you've created a race condition.

---

# 32. Parallelism Changes the Rules

A test that is safe sequentially:

```text
A
↓
B
↓
C
```

may fail when executed:

```text
A ────────┐
          │
B ────────┼── concurrent
          │
C ────────┘
```

This is why database-wide cleanup such as:

```js
deleteMany({})
```

can be dangerous if multiple test suites share the same database concurrently.

---

# 33. Practical Solution for Now

While learning:

```text
Run integration tests sequentially
```

and use:

```text
beforeEach
+
clean test DB
+
test-specific data
```

This gives you a simple, predictable system.

Later, when your test suite grows, you can design proper parallel isolation.

---

# 34. Don't Over-Optimize Too Early

You might hear:

> "Deleting the database before every test is slow!"

True.

But if your suite has:

```text
20 tests
```

you don't need an extremely sophisticated isolation system.

Start with:

```text
simple
predictable
correct
```

Then optimize when you have evidence that performance is a problem.

---

# 35. Isolation Through Factories

Suppose you have:

```js
createTestUser()
createTestTodo()
```

A test can do:

```js
test("user can update todo", async () => {
    const user = await createTestUser();

    const todo = await createTestTodo({
        userId: user.id
    });

    // test
});
```

Now the test completely describes its own state.

This is the beginning of **test fixtures/factories**, which you'll study in 21.17.

---

# 36. A Powerful Pattern

Think:

```text
Arrange
   ↓
Act
   ↓
Assert
```

For example:

### Arrange

```js
const user = await createTestUser();

const todo = await createTestTodo({
    userId: user.id
});
```

### Act

```js
const response = await request(app)
    .patch(`/todos/${todo.id}`)
    .set("Authorization", `Bearer ${user.token}`)
    .send({
        title: "Updated"
    });
```

### Assert

```js
expect(response.status).toBe(200);
```

Each test owns its Arrange phase.

That naturally improves isolation.

---

# 37. Avoid Giant Shared `beforeEach`

You might be tempted to do:

```js
beforeEach(async () => {
    user = await createTestUser();
    todo = await createTestTodo();
    course = await createCourse();
    order = await createOrder();
    payment = await createPayment();
});
```

for every test.

That's not ideal.

A test about todos shouldn't necessarily create:

```text
course
order
payment
```

unless required.

Keep setup close to the test's needs.

---

# 38. Good Setup

```js
describe("Todo API", () => {
    beforeEach(async () => {
        await clearTestDatabase();
    });

    test("creates todo", async () => {
        const user = await createTestUser();

        // ...
    });

    test("deletes todo", async () => {
        const user = await createTestUser();
        const todo = await createTestTodo({
            userId: user.id
        });

        // ...
    });
});
```

The setup is easy to understand.

---

# 39. Bad Setup

```js
beforeEach(async () => {
    user = await createUser();
    todo = await createTodo();
    admin = await createAdmin();
    course = await createCourse();
    lesson = await createLesson();
    order = await createOrder();
    payment = await createPayment();
});
```

Now every test carries a huge hidden dependency.

This makes tests:

```text
slow
hard to understand
hard to debug
hard to maintain
```

---

# 40. Isolation and Deterministic Data

Suppose your test says:

```js
expect(users.length).toBe(1);
```

This is deterministic only if you know the database starts empty.

If your test database contains:

```text
User A
User B
```

the same test could return:

```text
3 users
```

So isolation gives you:

```text
known initial state
        ↓
predictable result
```

That's what we mean by **deterministic tests**.

---

# 41. Deterministic vs Flaky

### Deterministic

```text
Run 1 → pass
Run 2 → pass
Run 3 → pass
Run 4 → pass
```

### Flaky

```text
Run 1 → pass
Run 2 → fail
Run 3 → pass
Run 4 → fail
```

Flaky tests destroy confidence in a test suite.

One of the biggest causes:

```text
shared state
```

---

# 42. Test Isolation Checklist

For every integration test, ask:

```text
Does this test depend on another test?

Does it depend on database records created elsewhere?

Does it modify global variables?

Does it modify environment variables?

Does it leave mocks behind?

Does it leave event listeners behind?

Does it leave cache data?

Does it leave files behind?

Does it leave queue jobs behind?

Does it start background work that survives the test?

Can I run this test alone?

Can I run it repeatedly?
```

If the answer to the last two is **yes**, you're in a good place.

---

# 43. The Most Useful Rule

When writing a test, ask:

> **"If I delete every other test in this project, will this test still work?"**

If yes:

```text
✅ Strong isolation
```

If no:

```text
❌ Hidden dependency
```

This is one of the best testing habits you can develop.

# 46. A Simple Example

Here's the pattern I want you to remember:

```js
describe("Todo CRUD", () => {
    beforeAll(async () => {
        await connectTestDatabase();
    });

    beforeEach(async () => {
        await clearTestDatabase();
    });

    afterAll(async () => {
        await disconnectTestDatabase();
    });

    test("creates a todo", async () => {
        const user = await createTestUser();

        const response = await request(app)
            .post("/api/v1/todos")
            .set(
                "Authorization",
                `Bearer ${user.token}`
            )
            .send({
                title: "Learn testing"
            });

        expect(response.status).toBe(201);
    });

    test("returns empty list when no todos exist", async () => {
        const user = await createTestUser();

        const response = await request(app)
            .get("/api/v1/todos")
            .set(
                "Authorization",
                `Bearer ${user.token}`
            );

        expect(response.status).toBe(200);
        expect(response.body.data).toHaveLength(0);
    });
});
```

The second test passes because:

```text
beforeEach
   ↓
database cleared
   ↓
user created
   ↓
GET todos
   ↓
[]
```

It doesn't matter whether the create test runs before it.

---

# 47. One Subtle Point

Notice that we **still create the user** in the second test.

Why?

Because the test needs an authenticated user.

But we don't reuse the user from another test.

That's the difference between:

```text
shared dependency ❌
```

and:

```text
controlled setup ✅
```

---

# 48. What Isolation Does NOT Mean

Isolation does **not** mean:

> Every test must create everything from scratch manually.

That's too much work.

Instead, we'll eventually create reusable factories:

```js
const user = await createTestUser();
const todo = await createTestTodo({
    userId: user.id
});
```

This gives us:

```text
Isolation
+
Reusable setup
```

without repetitive code.

That's exactly why **21.17 Fixtures** comes later.

## 🔑 Final Mental Model

Remember these three rules:

### Rule 1

> **Tests must never depend on your development or production database.**

### Rule 2

> **A test should create the state it needs.**

### Rule 3

> **One test should not care what another test did.**

If you follow those three rules, you'll avoid a huge percentage of testing problems later.
