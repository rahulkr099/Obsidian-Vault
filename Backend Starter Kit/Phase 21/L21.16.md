# Lesson 21.16 — Mocking

Now we move from **test isolation** to **mocking**.

Your Phase 21 roadmap places **Mocking immediately after Test Database and Test Isolation**, followed by Fixtures.

The key question is:

> **When should a test use the real dependency, and when should we replace that dependency with a fake one?**

---

# 1. What Is Mocking?

Suppose your service does this:

```text
signup()
   ↓
User Repository
   ↓
MongoDB

   +
Email Service
   ↓
Email Provider
```

If you test signup, do you really want every test to:

```text
connect MongoDB
+
call an email provider
+
actually send an email
```

Usually, no.

Instead, we can replace the email provider during a unit test:

```text
signup()
   ↓
User Repository
   ↓
mock

Email Service
   ↓
mock
```

The test controls those dependencies.

That's **mocking**.

---

# 2. Why Do We Need Mocking?

Imagine:

```js
async function sendWelcomeEmail(user) {
    await emailProvider.send({
        to: user.email,
        subject: "Welcome"
    });
}
```

Testing this function against the real email provider could:

- send real emails
    
- require API credentials
    
- cost money
    
- depend on the internet
    
- be slow
    
- fail because the provider is unavailable
    

Instead:

```text
Real email provider
        ↓
     replaced
        ↓
Mock email provider
```

Now the test can ask:

> "Was `send()` called?"

without actually sending anything.

---

# 3. Mocking Does NOT Mean "Don't Test the Dependency"

This distinction is extremely important.

Suppose you have:

```text
signupService
     ↓
emailService
     ↓
emailProvider
```

A unit test for `signupService` can mock:

```text
emailService
```

But you should separately test:

```text
emailService
```

and, where appropriate, integration-test the real provider boundary.

So:

```text
Unit test
   ↓
mock dependency

Integration test
   ↓
real application components

External integration
   ↓
controlled environment/provider
```

---

# 4. Mocking vs Test Database

You learned in 21.14:

```text
Integration test
      ↓
real test database
```

Now compare:

### Integration test

```text
HTTP
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Test MongoDB
```

### Unit test

```text
Service
 ↓
Mock Repository
```

The unit test doesn't need MongoDB.

This makes it:

```text
faster
smaller
more focused
```

# 5. The Main Idea

A unit test asks:

> **Does this piece of code behave correctly when its dependencies behave in a known way?**

For example:

```text
auth.service.js
```

depends on:

```text
userRepository
password utility
token utility
```

We can control those dependencies.

---

# 6. Example: User Service

Imagine:

```js
export async function getUserProfile(userId) {
    const user = await userRepository.findById(userId);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    return user;
}
```

We don't necessarily need MongoDB to test this.

We can mock:

```js
userRepository.findById
```

---

# 7. Successful Case

We tell the mock:

```text
findById("123")
     ↓
return fake user
```

Then:

```js
const user = await getUserProfile("123");
```

We expect:

```text
fake user
```

The database never runs.

---

# 8. Failure Case

We can instead configure:

```text
findById("123")
     ↓
return null
```

Then:

```js
await getUserProfile("123");
```

should throw:

```text
User not found
```

This gives us a very focused test.

---

# 9. What Is a Mock?

A mock is a controlled replacement for something your code depends on.

For example:

```text
Real Repository
       ↓
      ❌

Mock Repository
       ↓
      ✅
```

The mock might return:

```js
{
    id: "123",
    name: "Test User"
}
```

instead of querying MongoDB.

---

# 10. What Is a Stub?

You'll hear the word **stub** too.

A stub mainly provides predetermined behavior.

For example:

```text
getUser()
   ↓
always returns
   ↓
Test User
```

You don't necessarily care whether it was called.

You care about:

```text
"What value did it return?"
```

---

# 11. What Is a Spy?

A spy observes a function.

For example:

```text
sendEmail()
```

The spy can tell you:

```text
Was it called?
How many times?
What arguments were passed?
```

Example expectation:

```js
expect(sendEmail).toHaveBeenCalledWith(
    "test@example.com"
);
```

---

# 12. Mock vs Stub vs Spy

A simple mental model:

```text
Mock
 ↓
Replace behavior + inspect calls

Stub
 ↓
Provide controlled behavior

Spy
 ↓
Observe calls
```

In practice, testing libraries blur these terms somewhat.

Don't get stuck on terminology.

The important thing is:

> **Control and observe dependencies without using their real implementation.**

---

# 13. Jest Mocks

Since Phase 21 is built around Jest, you'll commonly see:

```js
jest.fn()
```

For example:

```js
const sendEmail = jest.fn();
```

Now:

```js
await sendEmail("hello@example.com");
```

doesn't send anything.

But Jest records the call.

You can test:

```js
expect(sendEmail).toHaveBeenCalled();
```

---

# 14. Mock Return Value

You can tell a mock what to return:

```js
const findUser = jest.fn();

findUser.mockResolvedValue({
    id: "123",
    name: "Rahul"
});
```

Then:

```js
const user = await findUser("123");
```

returns:

```js
{
    id: "123",
    name: "Rahul"
}
```

No database.

---

# 15. Mock Rejected Promise

You can also simulate failures:

```js
findUser.mockRejectedValue(
    new Error("Database unavailable")
);
```

Then:

```js
await findUser("123");
```

behaves as though the dependency failed.

This is extremely useful.

You can test:

```text
database failure
email failure
payment failure
API failure
```

without actually causing those failures.

---

# 16. Why This Is Powerful

Imagine your service:

```text
createOrder()
     ↓
Payment Gateway
```

What happens if payment fails?

With a real payment provider, reproducing the exact failure can be difficult.

With a mock:

```text
paymentGateway.charge()
       ↓
mockRejectedValue(...)
```

You can simulate:

```text
payment declined
timeout
network error
provider unavailable
```

instantly.

---

# 17. Mocking External APIs

Suppose:

```text
Your backend
     ↓
OpenAI API
```

or:

```text
Your backend
     ↓
Stripe
```

or:

```text
Your backend
     ↓
Cloud storage
```

You generally don't want every unit test calling those real services.

Instead:

```text
Your backend
     ↓
Mock external client
```

Then you can test your business logic safely.

---

# 18. But Don't Mock Everything

This is one of the biggest mistakes beginners make.

They see mocking and think:

```text
Mock MongoDB
Mock Express
Mock service
Mock repository
Mock everything
```

Now the test may not test anything meaningful.

For example:

```text
Controller
 ↓
mock service
 ↓
mock repository
 ↓
mock database
```

If every layer is mocked, you're basically testing:

```text
"Does my mock return what I told it to return?"
```

Not useful.

---

# 19. Mock the Boundary

A very useful rule:

> **Mock external or expensive dependencies when testing your own logic.**

For example:

```text
Your Service
     ↓
External Email Provider
```

Mock the email provider.

But if you're testing:

```text
Repository
     ↓
MongoDB
```

you may want the real test database.

That's why your roadmap had:

```text
21.8 Testing repositories
21.13 Testing CRUD
21.14 Test database
21.15 Test isolation
21.16 Mocking
```

These concepts serve different testing purposes.

# 20. Unit Test Example

Suppose:

```js
async function createUser(data) {
    const existingUser =
        await userRepository.findByEmail(data.email);

    if (existingUser) {
        throw new AppError(
            "Email already exists",
            409
        );
    }

    return userRepository.create(data);
}
```

Dependencies:

```text
userRepository.findByEmail
userRepository.create
```

For a unit test, we can mock both.

---

# 21. Test Duplicate Email

Configure:

```text
findByEmail()
      ↓
existing user
```

Then:

```js
await createUser({
    email: "test@example.com"
});
```

should throw:

```text
409
Email already exists
```

We don't need MongoDB.

---

# 22. Test Successful Creation

Configure:

```text
findByEmail()
      ↓
null

create()
      ↓
new user
```

Then:

```js
const user = await createUser({
    email: "test@example.com"
});
```

should return the new user.

And we can verify:

```js
expect(userRepository.create)
    .toHaveBeenCalled();
```

---

# 23. Why This Test Is Better as a Unit Test

We're testing this rule:

```text
IF email already exists
THEN reject signup
```

That's business logic.

We don't need to prove MongoDB works here.

MongoDB should have its own repository/integration tests.

This separation makes the entire suite cleaner.

---

# 24. Mocking Dependencies

Conceptually:

```text
                  createUser()
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
 findByEmail()                  create()
     MOCK                          MOCK
```

Then the test controls:

```text
findByEmail → null
create → fake user
```

This is dependency isolation.

---

# 25. Dependency Injection Makes Mocking Easier

Consider:

```js
import userRepository from "./user.repository.js";

export async function createUser(data) {
    return userRepository.create(data);
}
```

This can be mocked through Jest's module mocking.

But another architecture is:

```js
export function createUser(userRepository) {
    return async function (data) {
        return userRepository.create(data);
    };
}
```

Now:

```text
Production
    ↓
real repository

Test
    ↓
mock repository
```

This is **dependency injection**.

You don't need to redesign your whole starter around dependency injection, but understanding it will help you write more testable code.

---

# 26. A Simple Dependency Injection Example

```js
function createUserService(userRepository) {
    return {
        async createUser(data) {
            return userRepository.create(data);
        }
    };
}
```

Production:

```js
const userService =
    createUserService(userRepository);
```

Testing:

```js
const mockRepository = {
    create: jest.fn()
};

const userService =
    createUserService(mockRepository);
```

Now the service doesn't know whether the repository is real or fake.

---

# 27. Why This Is a Good Design

Your service depends on an abstraction:

```text
"Something that can create users"
```

rather than being tightly coupled to:

```text
"MongoDB implementation"
```

This can improve:

```text
testability
maintainability
flexibility
```

But don't add abstraction just for the sake of abstraction.

---

# 28. Mocking a Repository

Suppose:

```js
const mockRepository = {
    findById: jest.fn()
};
```

Then:

```js
mockRepository.findById
    .mockResolvedValue({
        id: "123",
        name: "Test User"
    });
```

Test:

```js
const user =
    await userService.getProfile("123");

expect(user.name)
    .toBe("Test User");
```

And:

```js
expect(
    mockRepository.findById
).toHaveBeenCalledWith("123");
```

Now you've tested two things:

```text
behavior
+
dependency interaction
```

---

# 29. Don't Assert Implementation Details Too Much

Be careful with:

```js
expect(repository.findById)
    .toHaveBeenCalledTimes(1);
```

Sometimes that's useful.

But the most important assertion is:

```text
Did the service produce the correct behavior?
```

Not:

```text
Did the developer use exactly three function calls?
```

Otherwise a harmless refactor can break the test.

---

# 30. Good Mock Assertion

Suppose your service must create a user.

Useful:

```js
expect(mockRepository.create)
    .toHaveBeenCalledWith({
        email: "test@example.com"
    });
```

This verifies an important contract.

Less useful:

```js
expect(mockRepository.someInternalHelper)
    .toHaveBeenCalledTimes(1);
```

if that helper isn't part of the service's meaningful behavior.

---

# 31. Mocking Errors

This is one of my favorite uses of mocks.

Suppose:

```text
Email service
```

normally works.

You want to test:

```text
What if email provider fails?
```

Mock:

```js
sendEmail.mockRejectedValue(
    new Error("Email provider unavailable")
);
```

Then test your application's behavior.

For example:

```text
Signup
 ↓
User created
 ↓
Email fails
```

What should your application do?

Depending on your architecture:

```text
return error
```

or:

```text
queue email
```

or:

```text
create user successfully
+
log email failure
```

Mocking lets you test these paths.

# 33. Mocking Time

Time itself can be a dependency.

Suppose:

```js
if (token.expiresAt < Date.now()) {
    // expired
}
```

Testing expiration can be annoying because you have to wait.

A test framework can provide controlled time.

Conceptually:

```text
Real clock
   ↓
Mock clock
   ↓
Pretend it is tomorrow
```

Then test expiration immediately.

This is another example of controlling external state.

# 34. Mocking Randomness

Similarly:

```js
Math.random()
```

or:

```js
crypto.randomUUID()
```

can make some tests unpredictable.

If your business logic depends on randomness, controlling it can make the test deterministic.

Again:

```text
real randomness
      ↓
controlled test value
```

# 35. Mocking Environment Configuration

Suppose:

```js
if (env.emailEnabled) {
    await sendEmail();
}
```

A test can control:

```text
emailEnabled=true
```

or:

```text
emailEnabled=false
```

Then test both paths.

Be careful to restore global environment state afterward.

That's directly connected to the isolation lesson you just completed.

---

# 36. Resetting Mocks

This is extremely important.

Suppose:

```js
const sendEmail = jest.fn();
```

Test 1:

```text
called once
```

Test 2:

```text
called once
```

If you don't reset the mock, Jest may see:

```text
Test 1 → 1 call
Test 2 → 2 total calls
```

Now your assertion can become incorrect.

So mock state must be reset between tests when appropriate.

---

# 37. `mockClear()`

Conceptually:

```js
mockFn.mockClear();
```

This clears information about calls.

For example:

```text
calls
arguments
instances
```

but doesn't necessarily remove the mock implementation.

Think:

```text
Keep behavior
Clear history
```

---

# 38. `mockReset()`

`mockReset()` goes further.

Think:

```text
Clear history
+
remove mock implementation
```

So:

```text
mockResolvedValue(...)
```

can be reset.

---

# 39. `mockRestore()`

For spies on real methods, you may need:

```js
mockRestore();
```

This restores the original implementation.

Mental model:

```text
Real function
      ↓
Spy/mock
      ↓
Test
      ↓
Restore original
```

This is important when modifying existing objects/modules.

---

# 40. Three Terms to Remember

You don't need to memorize every Jest API today.

Remember:

```text
clear
 ↓
remove call history

reset
 ↓
remove call history + implementation

restore
 ↓
bring back original function
```

We'll use these concepts repeatedly.

# 41. Mocking and Test Isolation Are Connected

You just learned:

> Tests shouldn't affect each other.

Now consider:

```text
Test A
 ↓
mock email service
 ↓
doesn't reset it

Test B
 ↓
email service still mocked
```

That's a violation of isolation.

So:

```text
Test isolation
     +
Mock cleanup
     =
Reliable tests
```

# 42. Mocking and Integration Tests

Here's a useful spectrum:

```text
               MORE REAL
                   ↑
                   │
        End-to-end test
                   │
        Integration test
                   │
             Service test
                   │
              Unit test
                   │
                   ↓
               MORE MOCKS
```

A unit test might mock:

```text
repository
email
payment
external API
```

An integration test might use:

```text
real repository
real test database
```

while mocking only external providers.

An end-to-end test may involve much more of the actual infrastructure.

---

For your MERN backend, a practical starting point is:

### Usually mock

```text
External HTTP APIs
Email provider
Payment provider
Cloud storage
AI APIs
SMS provider
Third-party SDKs
Time/randomness when needed
```

### Often don't mock in integration tests

```text
Express

Your services
Your repositories
Mongoose
Test MongoDB
```

Because the purpose of integration testing is to verify those components actually work together.

# 51. A Small Jest Example

Conceptually:

```js
describe("createUser", () => {
    const userRepository = {
        findByEmail: jest.fn(),
        create: jest.fn()
    };

    test("creates user when email is available", async () => {
        userRepository.findByEmail
            .mockResolvedValue(null);

        userRepository.create
            .mockResolvedValue({
                id: "123",
                email: "test@example.com"
            });

        // call service

        // assert result
        // assert repository interaction
    });
});
```

The important thing isn't the exact syntax.

The important architecture is:

```text
Service
   ↓
Mock Repository
   ↓
Controlled result
```

---

# 52. What You Should NOT Do

Avoid this:

```js
test("create user", async () => {
    jest.mock("../services/user.service.js");

    // mock everything

    expect(true).toBe(true);
});
```

This test proves almost nothing.

Instead:

```text
Choose the unit
      ↓
Identify its dependencies
      ↓
Mock only the dependencies that need isolation
      ↓
Test real logic
```

---

# 53. The Decision Rule

When deciding whether to mock something, ask:

### Question 1

> Is this dependency part of the behavior I'm currently testing?

If yes:

```text
probably keep it real
```

### Question 2

> Is it external, expensive, unpredictable, or dangerous?

If yes:

```text
probably mock it
```

### Question 3

> Would using the real dependency make this test slow or flaky?

If yes:

```text
consider mocking
```

# 54. The Best Mental Model

Think of a unit under test as:

```text
             UNIT UNDER TEST
                    │
        ┌───────────┼───────────┐
        │           │           │
        ▼           ▼           ▼
    Database      Email       API
        │           │           │
       MOCK        MOCK        MOCK
```

The unit receives predictable answers.

You then test:

```text
"If my dependencies behave this way,
does my code make the correct decision?"
```

That's the heart of mocking.
