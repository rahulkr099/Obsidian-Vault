# Lesson 21.17 — Fixtures

You have now learned:

```text
21.14 → Test Database
21.15 → Test Isolation
21.16 → Mocking
21.17 → Fixtures  ← TODAY
21.18 → Coverage
21.19 → Build Backend Test Architecture
```

Your Phase 21 roadmap explicitly places **Fixtures** after Mocking and before Coverage.

The problem Fixtures solve is:

> **How do we create test data easily, consistently, and without repeating the same setup in every test?**

---

# 1. The Problem We Have Now

Imagine you're testing your Todo API.

Every test needs a user.

You might repeatedly write:

```js
const user = await User.create({
    name: "Test User",
    email: "test@example.com",
    password: "password123"
});
```

Then another test:

```js
const user = await User.create({
    name: "Test User",
    email: "test2@example.com",
    password: "password123"
});
```

Then another:

```js
const user = await User.create({
    name: "Test User",
    email: "test3@example.com",
    password: "password123"
});
```

Soon your tests become full of setup code.

That's where **fixtures/factories** help.

---

# 2. What Is a Fixture?

A fixture is **predefined test data or test setup** that you can reuse.

For example:

```js
const userFixture = {
    name: "Test User",
    email: "test@example.com",
    password: "password123"
};
```

Then:

```js
await User.create(userFixture);
```

Instead of rewriting the object everywhere.

---

# 3. Fixtures vs Factories

These terms are often used together, but there is a useful distinction.

### Fixture

Usually means:

> A known piece of test data/setup.

Example:

```js
const adminUser = {
    role: "admin",
    email: "admin@example.com"
};
```

### Factory

Usually means:

> A function that creates test data, often with customizable defaults.

Example:

```js
function buildUser(overrides = {}) {
    return {
        name: "Test User",
        email: "test@example.com",
        role: "user",
        ...overrides
    };
}
```

Then:

```js
buildUser();
```

or:

```js
buildUser({
    role: "admin"
});
```

For a growing backend, **factories are usually more flexible than static fixtures**.

---

# 4. Why Factories Are Powerful

Suppose you need:

```text
normal user
admin
verified user
unverified user
inactive user
```

Without factories, you may create five large objects.

With a factory:

```js
buildUser({
    role: "admin"
});
```

or:

```js
buildUser({
    isVerified: false
});
```

This keeps tests short.

---

# 5. Your Test Should Read Like a Scenario

Compare this:

```js
test("admin can delete user", async () => {
    // 40 lines creating users...
    // 20 lines creating roles...
    // more setup...

    // actual test
});
```

with:

```js
test("admin can delete user", async () => {
    const admin = await createUser({
        role: "admin"
    });

    const user = await createUser();

    // actual test
});
```

The second test immediately tells you:

```text
Admin
    ↓
deletes
    ↓
Normal User
```

That's what good test architecture should do.

---

# 6. `build` vs `create`

A very useful factory pattern is to have both:

```text
buildUser()
createUser()
```

### `buildUser()`

Creates an object **in memory**.

```js
const user = buildUser();
```

It does not touch MongoDB.

### `createUser()`

Creates the object **in the test database**.

```js
const user = await createUser();
```

This distinction becomes extremely useful.

---

# 7. Example

```js
function buildUser(overrides = {}) {
    return {
        name: "Test User",
        email: `test-${crypto.randomUUID()}@example.com`,
        password: "Password123!",
        role: "user",
        isVerified: true,
        ...overrides
    };
}
```

Then:

```js
const user = buildUser();
```

gives you something like:

```js
{
    name: "Test User",
    email: "test-abc123@example.com",
    password: "Password123!",
    role: "user",
    isVerified: true
}
```

No database interaction yet.

---

# 8. Creating It in MongoDB

Now:

```js
async function createUser(overrides = {}) {
    const data = buildUser(overrides);

    return User.create(data);
}
```

Then your test can simply do:

```js
const user = await createUser();
```

Beautifully simple.

---

# 9. Why Use Random Emails?

Remember our isolation lesson.

If every test uses:

```text
test@example.com
```

you can run into:

```text
duplicate key error
```

A factory can automatically generate unique values:

```js
email: `test-${crypto.randomUUID()}@example.com`
```

Now:

```text
test-a1...@example.com
test-b7...@example.com
test-c9...@example.com
```

This reduces accidental collisions.

---

# 10. But Random Data Has a Trap

Don't make everything random.

For example:

```js
name: randomName()
role: randomRole()
status: randomStatus()
```

Now your test might become difficult to understand.

You want:

```text
predictable defaults
+
unique values where necessary
```

For example:

```js
{
    name: "Test User",
    role: "user",
    isVerified: true,
    email: uniqueEmail()
}
```

That's a good balance.

---

# 11. Overrides

The most important factory feature is:

```js
...overrides
```

Example:

```js
function buildUser(overrides = {}) {
    return {
        name: "Test User",
        role: "user",
        isVerified: true,
        ...overrides
    };
}
```

Now:

```js
buildUser({
    role: "admin"
});
```

produces:

```js
{
    name: "Test User",
    role: "admin",
    isVerified: true
}
```

This is much better than creating a completely separate admin fixture.

# 13. User Factory

A simple version:

```js
import crypto from "node:crypto";
import User from "../../models/user.model.js";

export function buildUser(overrides = {}) {
    return {
        name: "Test User",
        email: `test-${crypto.randomUUID()}@example.com`,
        password: "Password123!",
        role: "user",
        isVerified: true,
        ...overrides
    };
}

export async function createUser(overrides = {}) {
    return User.create(buildUser(overrides));
}
```

Now your test can say:

```js
const user = await createUser();
```

or:

```js
const admin = await createUser({
    role: "admin"
});
```

---

# 14. Todo Factory

Same idea:

```js
function buildTodo(overrides = {}) {
    return {
        title: "Learn backend testing",
        completed: false,
        ...overrides
    };
}
```

But a Todo probably needs a user.

So:

```js
async function createTodo(userId, overrides = {}) {
    return Todo.create({
        ...buildTodo(overrides),
        userId
    });
}
```

Now:

```js
const user = await createUser();

const todo = await createTodo(user.id);
```

This clearly expresses the relationship.

---

# 15. Factory Relationships

This is where factories become really useful.

Suppose:

```text
User
 │
 └── Todo
      │
      └── belongs to User
```

Your test can do:

```js
const user = await createUser();

const todo = await createTodo(user.id);
```

Now the test setup communicates the domain relationship.

---

# 16. A Better Factory API

You could even make:

```js
const todo = await createTodo({
    userId: user.id
});
```

Then:

```js
async function createTodo(overrides = {}) {
    return Todo.create({
        title: "Test Todo",
        completed: false,
        ...overrides
    });
}
```

This is flexible.

---

# 17. Factory Composition

You can compose factories:

```js
const user = await createUser();

const todo = await createTodo({
    userId: user.id
});

const comment = await createComment({
    userId: user.id,
    todoId: todo.id
});
```

Now:

```text
User
 ├── Todo
 │    └── Comment
```

is created in just a few lines.

Your eventual backend can have many domains:


# 19. Fixtures for Authentication

Authentication is a perfect example.

You might repeatedly need:

```text
normal user
admin
verified user
unverified user
```

Instead:

```js
const user = await createUser();

const admin = await createUser({
    role: "admin"
});

const unverifiedUser = await createUser({
    isVerified: false
});
```

Very readable.

---

# 20. Authentication Helper

You can go one step further.

Suppose many tests need an authenticated user.

Create:

```js
async function createAuthenticatedUser(overrides = {}) {
    const user = await createUser(overrides);

    const token = generateAccessToken({
        userId: user.id
    });

    return {
        user,
        token
    };
}
```

Then:

```js
const { user, token } =
    await createAuthenticatedUser();
```

Your test can immediately make authenticated requests.

---

# 21. Testing Protected Routes

For example:

```js
test("user can get own todos", async () => {
    const { user, token } =
        await createAuthenticatedUser();

    const todo = await createTodo({
        userId: user.id
    });

    const response = await request(app)
        .get("/api/v1/todos")
        .set("Authorization", `Bearer ${token}`);

    expect(response.status).toBe(200);
});
```

Look at how little setup is required.

The test is mostly about the behavior.

# 22. Fixture Data vs Production Seed Data

Don't confuse:

```text
test fixtures
```

with:

```text
database seed data
```

### Seed data

Usually exists to populate a development/demo database.

Example:

```text
Admin User
Demo Course
Demo Lessons
```

### Test fixtures

Exist specifically to support automated tests.

Example:

```text
Test User
Test Todo
Test Course
```

Their goals are different.

---

# 23. Fixtures Should Be Easy to Understand

Avoid fixtures like:

```js
const user = {
    a: "abc",
    b: true,
    c: 17,
    d: "xyz"
};
```

Your test data should look like actual domain data:

```js
{
    name: "Test User",
    email: "test@example.com",
    role: "user"
}
```

Good test data teaches you about your own domain.

---

# 24. Don't Put Business Logic in Factories

A factory should mostly create test data.

Don't turn this:

```js
createUser()
```

into a giant application workflow:

```text
create user
 ↓
send email
 ↓
generate token
 ↓
create audit log
 ↓
send notification
```

That's no longer simple test data setup.

Keep factories predictable.

---

# 25. Factory vs Service

This distinction matters.

### Service

Production application logic:

```text
signup()
login()
createCourse()
deleteTodo()
```

### Factory

Test setup:

```text
createUser()
createTodo()
createCourse()
```

They may both "create things", but they serve completely different purposes.

---

# 26. Factories Should Usually Bypass Business Workflows

Suppose production signup does:

```text
signup
 ↓
validate
 ↓
hash password
 ↓
create user
 ↓
send verification email
```

A test factory may simply do:

```js
await User.create({
    ...
});
```

Why?

Because the factory is not testing signup.

It's preparing a user.

If your test is specifically testing signup, **then use the real signup API/service**.

This is an important testing principle.

---

# 27. Don't Accidentally Test Your Factory

Suppose:

```js
createUser()
```

contains complex logic.

Then your tests depend on that logic being correct.

You might have:

```text
Test
 ↓
Factory
 ↓
Factory bug
 ↓
Test failure
```

That's why factories should remain simple.

# 29. Static Fixtures

Sometimes static fixtures are actually better.

For example, testing a complicated API response:

```js
const courseResponse = {
    id: "course-123",
    title: "Backend Architecture",
    lessons: [
        ...
    ]
};
```

If you need exactly this structure repeatedly, a static fixture is perfectly reasonable.

Factories aren't always necessary.

---

# 30. When to Use a Fixture

Use a fixture when:

```text
the data is stable
+
you need an exact known structure
```

Example:

```text
expected API response
JWT payload
sample webhook payload
sample external API response
```

---

# 31. When to Use a Factory

Use a factory when:

```text
you need many variations
+
you want sensible defaults
+
tests need customized data
```

Example:

```text
User
Todo
Course
Order
```

# 32. External API Fixtures

This is particularly useful with mocking.

Suppose Stripe returns:

```json
{
    "id": "payment_123",
    "status": "succeeded"
}
```

Instead of rebuilding this object in every test:

```js
const stripeSuccessResponse = {
    id: "payment_123",
    status: "succeeded"
};
```

You can store it as a fixture:

```text
tests/
└── fixtures/
    └── stripe/
        ├── success.js
        └── failure.js
```

Then:

```js
mockCharge.mockResolvedValue(
    stripeSuccessResponse
);
```

This is a great combination of:

```text
Mocking
+
Fixtures
```

# 33. Webhook Fixtures

Suppose your backend handles:

```text
POST /webhooks/payment
```

You can have:

```text

└── webhooks/
    ├── payment-success.js
    ├── payment-failed.js
```

Then your integration tests can use realistic payloads.

# 34. Fixture Naming

Prefer names that describe the scenario:

```text
adminUser
verifiedUser
unverifiedUser
expiredToken
successfulPayment
failedPayment
emptyTodoList
```

Avoid:

```text
data1
data2
mockData

```

Good names make tests readable.

# 35. Scenario-Oriented Fixtures

You can create:

```js
const adminUser = buildUser({
    role: "admin"
});

const regularUser = buildUser({
    role: "user"
});
```

Then:

```text
adminUser
regularUser
```

immediately communicate the scenario.

---

# 36. Don't Overuse Global Fixtures

Avoid:

```js
let user;
let admin;
let todo;
let course;
let lesson;
```

at the top of the entire test file unless there's a good reason.

Instead:

```js
test("admin can delete user", async () => {
    const admin = await createUser({
        role: "admin"
    });

    const user = await createUser();

    // ...
});
```

Local setup is easier to reason about.

This follows directly from your **test isolation** lesson.

---

# 37. Factory Defaults Should Be Valid

This is important.

If:

```js
createUser()
```

produces an invalid user, every test must override fields.

That's a bad factory.

Good:

```js
createUser()
```

should produce a **valid normal user**.

Then special cases override what they need.

```js
createUser({
    role: "admin"
});
```

---

# 38. Factory Defaults Should Be Minimal

Don't create:

```js
{
    name,
    email,
    password,
    role,
    permissions,
    avatar,
    address,
    preferences,
    subscription,
    notifications,
    ...
}
```

unless your model actually requires all of them.

Start with the minimum valid data.

Then add optional fields through overrides.

---

# 39. A Strong Pattern

Think:

```text
Factory
   ↓
valid default object
   ↓
overrides
   ↓
database
```

Example:

```js
function buildTodo(overrides = {}) {
    return {
        title: "Test Todo",
        completed: false,
        ...overrides
    };
}
```

Then:

```js
buildTodo({

```

This is simple and powerful.

# 42. Avoid Circular Dependencies

Be careful if:

```text
user.factory
   ↓
todo.factory
   ↓
user.factory
```

Don't let factories depend on each other unnecessarily.

Prefer:

```text

 ├── createUser()
 └── createTodo({ userId })
```

# 43. A Complete Example

Imagine:

```js
test("user can update own todo", async () => {
    const { user, token } =
        await createAuthenticatedUser();

    const todo = await createTodo({
        userId: user.id,
        title: "Old title"
    });

    const response = await request(app)
        .patch(`/api/v1/todos/${todo.id}`)
        .set("Authorization", `Bearer ${token}`)
        .send({
            title: "New title"
        });

    expect(response.status).toBe(200);
    expect(response.body.data.title)
        .toBe("New title");
});
```

Look at what this test communicates:

```text
Authenticated user
       ↓
owns todo
       ↓
updates todo
       ↓
gets new title
```

That's excellent test readability.

# 44. Cross-User Authorization Test

Fixtures also make security tests easy.

```js
test("user cannot update another user's todo", async () => {
    const userA = await createAuthenticatedUser();
    const userB = await createAuthenticatedUser();

    const todo = await createTodo({
        userId: userB.user.id
    });

    const response = await request(app)
        .patch(`/api/v1/todos/${todo.id}`)
        .set(
            "Authorization",
            `Bearer ${userA.token}`
        )
        .send({
            title: "Hacked"
        });

    expect(response.status).toBe(404);
});
```

This is a great example of why factories matter.

Without factories, this test would contain a lot of setup.

With factories, the **security rule** is obvious.

# 46. Fixtures + Integration Testing

Fixtures aren't limited to unit tests.

Integration tests can use factories:

```text

   ↓

   ↓

```

For example:

```js

    userId: user.id
```

Only the setup is simplified.

---

# 47. The Important Distinction

Don't think:

> "Fixtures are fake tests."

No.

A fixture is simply:

> **A convenient way to prepare known test state.**

The actual code under test can still be completely real.

# 48. Fixture Quality Checklist

A good factory should:

```text
✓ produce valid data
✓ have sensible defaults
✓ allow overrides
✓ generate unique fields when necessary
✓ stay simple
✓ avoid business workflows
✓ avoid external API calls
✓ make relationships explicit
✓ be easy to read
```

# 50. One Mistake to Avoid

Don't turn factories into a second application.

Bad:

```js

    → validation
    → hashing
    → email
    → tokens
    → events
    → audit
    → database
```

```js

    → save to test database
```

Keep the factory boring.

**Boring test infrastructure is good test infrastructure.**
