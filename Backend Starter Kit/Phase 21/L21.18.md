# Lesson 21.18 — Test Coverage

Now we move from **writing tests** to **measuring how much of our code those tests actually execute**.

So far:

```text
21.14 → Test Database
21.15 → Test Isolation
21.16 → Mocking
21.17 → Fixtures
21.18 → Coverage ← TODAY
```

The important idea is:

> **Test coverage tells you which parts of your code were executed while your tests ran. It does not tell you that your application is correct.**

---

# 1. What Is Test Coverage?

Imagine this service:

```js
async function getUser(id) {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    return user;
}
```

Suppose your test only checks the successful case:

```text
findById()
    ↓
returns user
    ↓
return user
```

The test executes:

```text
userRepository.findById()
return user
```

But it never executes:

```text
if (!user)
    ↓
throw AppError
```

Coverage tools can show you that.

---

# 2. Why Coverage Matters

Without coverage information, you might think:

> "I have 100 tests, so my code must be well tested."

Not necessarily.

You could have:

```text
100 tests
+
lots of repeated assertions
+
important code never executed
```

Coverage gives you another perspective:

```text
Which code did my tests actually reach?
```

---

# 3. Coverage Is Not Correctness

This distinction is extremely important.

Suppose:

```js
function add(a, b) {
    return a - b;
}
```

A test could be:

```js
test("add works", () => {
    add(10, 5);
});
```

The function executes.

Coverage:

```text
100%
```

But the function is wrong.

So:

```text
100% coverage
≠
100% correctness
```

---

# 4. Four Important Coverage Types

You'll commonly encounter:

```text
1. Statement coverage
2. Branch coverage
3. Function coverage
4. Line coverage
```

They measure different things.

---

# 5. Statement Coverage

Statement coverage asks:

> **Did this executable statement run?**

Example:

```js
function calculate(a, b) {
    const sum = a + b;
    return sum;
}
```

If the test calls:

```js
calculate(2, 3);
```

both statements execute.

So statement coverage is effectively:

```text
2 / 2
=
100%
```

---

# 6. Line Coverage

Line coverage asks:

> **Did this line execute?**

For simple code, line and statement coverage can look very similar.

Example:

```js
const user = await findUser(id);
return user;
```

If both lines execute:

```text
2 / 2 lines
=
100%
```

But don't assume line coverage tells the whole story.

---

# 7. Branch Coverage

Branch coverage is more interesting.

Consider:

```js
if (user.isAdmin) {
    return "admin";
}

return "user";
```

There are two paths:

```text
user.isAdmin = true
       ↓
"admin"

user.isAdmin = false
       ↓
"user"
```

A test for only an admin user doesn't exercise both branches.

You might have:

```text
Branch coverage = 50%
```

even though the relevant lines may have been executed.

---

# 8. Why Branch Coverage Is Valuable

Consider:

```js
if (user) {
    return user;
}

throw new AppError("User not found");
```

You need at least two scenarios:

```text
User exists
     ↓
return user
```

and:

```text
User doesn't exist
     ↓
throw error
```

Branch coverage helps reveal the missing scenario.

This is one reason branch coverage is often more useful than simply chasing line coverage.

---

# 9. Function Coverage

Function coverage asks:

> **Which functions were actually called?**

Suppose a module has:

```js
function createUser() {}

function deleteUser() {}

function updateUser() {}
```

If tests only call:

```text
createUser()
deleteUser()
```

then:

```text
Functions:
2 / 3
=
66.7%
```

The `updateUser()` function hasn't been exercised.

---

# 10. A Simple Example

Imagine:

```js
function getStatus(user) {
    if (!user) {
        return "missing";
    }

    if (user.isActive) {
        return "active";
    }

    return "inactive";
}
```

There are several possible paths:

```text
user doesn't exist
        ↓
     missing
```

```text
user exists
    ↓
isActive = true
    ↓
active
```

```text
user exists
    ↓
isActive = false
    ↓
inactive
```

A strong test suite should cover all three meaningful scenarios.

---

# 11. Coverage Helps Find Missing Tests

Suppose your coverage report says:

```text
Statements: 92%
Branches:   67%
Functions:  100%
Lines:      92%
```

This tells you something interesting:

```text
Most code executes
+
all functions execute
+
many branches are still untested
```

So you should investigate branch coverage.

Maybe you forgot:

```text
unauthorized user
expired token
missing resource
database failure
empty result
```

---

# 12. Coverage Reports

Jest can generate coverage information.

A common command is:

```bash
npm test -- --coverage
```

Depending on your project configuration, you may see something like:

```text
-------------------|---------|----------|---------|---------
File               | % Stmts | % Branch | % Funcs | % Lines
-------------------|---------|----------|---------|---------
user.service.js    |   92.3  |   80.0   |   100   | 92.3
todo.service.js    |   88.8  |   75.0   |   100   | 88.8
auth.service.js    |   95.0  |   90.0   |   100   | 95.0
-------------------|---------|----------|---------|---------
```

The exact output depends on your Jest configuration.

---

# 13. Reading the Report

Suppose:

```text
Statements   90%
Branches     70%
Functions   100%
Lines        90%
```

Don't immediately think:

> "I need 100%."

Instead ask:

```text
Why are branches only 70%?
```

Maybe your tests cover:

```text
happy path
```

but not:

```text
error paths
edge cases
authorization failures
empty states
```

That's much more useful.

---

# 14. Coverage Thresholds

You can configure minimum coverage.

For example, conceptually:

```js
coverageThreshold: {
    global: {
        branches: 80,
        functions: 90,
        lines: 90,
        statements: 90
    }
}
```

Now CI can fail if coverage drops below your chosen threshold.

For example:

```text
Current branch coverage: 72%
Required:                80%

❌ Test command fails
```

This prevents coverage from silently getting worse.

---

# 15. Why Thresholds Are Useful

Imagine your team has:

```text
90% coverage
```

Then someone adds a large feature without tests.

Coverage drops:

```text
90%
 ↓
81%
```

Then another feature:

```text
81%
 ↓
74%
```

Eventually, nobody knows which important areas are untested.

A threshold creates a safety net.

---

# 16. But Don't Choose 100% Blindly

This is a common beginner mistake:

```text
"100% coverage sounds good."
```

Then developers start writing meaningless tests just to increase the percentage.

For example:

```js
test("runs line 25", () => {
    someFunction();
});
```

The test technically increases coverage.

But does it verify behavior?

Maybe not.

You want:

```text
meaningful tests
```

not:

```text
coverage theater
```

---

# 17. Coverage Theater

Coverage theater means writing tests primarily to improve the number.

Example:

```js
function calculatePrice(price, discount) {
    if (discount) {
        return price * 0.9;
    }

    return price;
}
```

A weak test might simply execute both paths without meaningful assertions.

A strong test says:

```js
expect(calculatePrice(100, true))
    .toBe(90);
```

The second test validates behavior.

---

# 18. Coverage Is a Signal

Think of coverage as:

```text
                 Coverage
                    ↓
             "Where did tests go?"
                    ↓
             Investigate gaps
                    ↓
             Improve test suite
```

Not:

```text
Coverage
   ↓
Application is correct
```

Coverage is evidence, not proof.

---

# 19. High Coverage Can Still Miss Bugs

Suppose:

```js
function isAdult(age) {
    return age >= 18;
}
```

Test:

```js
expect(isAdult(20)).toBe(true);
```

Coverage might be 100%.

But you didn't test:

```text
17
18
0
negative values
NaN
undefined
```

The code might still contain bugs around boundaries.

So coverage doesn't replace **test-case design**.

---

# 20. Branch Coverage Helps, But Still Isn't Enough

Suppose:

```js
if (age >= 18) {
    return "adult";
}

return "minor";
```

Testing:

```text
age = 20
age = 10
```

gives excellent branch coverage.

But you might still miss:

```text
age = 18
age = 17
age = 0
```

So you need both:

```text
coverage
+
boundary analysis
```

---

# 21. Coverage and Edge Cases

Coverage can point you toward missing areas.

For example:

```text
Branch coverage = 60%
```

You inspect the report and find:

```js
if (!email) {
    ...
}
```

wasn't executed.

That suggests a test:

```text
missing email
```

Another branch:

```js
if (user.isVerified) {
    ...
}
```

suggests:

```text
verified
unverified
```

Coverage becomes a tool for discovering scenarios.

---

# 22. Coverage and Error Handling

Backend applications have lots of error paths:

```text
400
401
403
404
409
422
429
500
```

A happy-path-only suite might have high line coverage but poor meaningful coverage.

For example:

```text
POST /users
   ↓
success
```

You should also think about:

```text
duplicate email
invalid input
unauthorized
forbidden
database failure
```

Coverage can help identify whether those paths are actually exercised.

---

# 23. Coverage and Authorization

Your backend has authorization logic like:

```js
if (user.id !== resource.userId) {
    throw new AppError("Forbidden", 403);
}
```

A test for:

```text
owner → allowed
```

may execute only one path.

You should also test:

```text
different user → denied
```

Branch coverage can reveal that missing path.

This connects directly with the authorization work you completed earlier in the roadmap.

---

# 24. Coverage and Authentication

Consider:

```js
if (!token) {
    throw new AppError("Authentication required", 401);
}

if (tokenExpired) {
    throw new AppError("Token expired", 401);
}
```

There are multiple scenarios.

Good coverage encourages tests for:

```text
no token
invalid token
expired token
valid token
```

Again:

```text
coverage
+
security scenarios
```

work together.

---

# 25. Don't Chase Coverage in Third-Party Code

You generally don't care about:

```text
node_modules/
```

Your coverage should focus on:

```text
your application
```

not:

```text
Express
Mongoose
Jest
jsonwebtoken
```

Those libraries have their own tests.

---

# 26. Excluding Generated Code

Some files may not need meaningful coverage.

For example:

```text
generated files
configuration wrappers
type declarations
migration scripts
```

Depending on your project, you may exclude specific files from coverage.

But don't use exclusions to hide poorly tested application logic.

A good rule:

> **Exclude code because it genuinely doesn't belong in your test target, not because it's inconvenient to test.**

---

# 27. Coverage for Controllers

Suppose:

```js
async function createTodo(req, res) {
    const todo = await todoService.create(
        req.user.id,
        req.body
    );

    return res.status(201).json({
        success: true,
        data: todo
    });
}
```

Coverage tells you whether the controller executes.

But integration tests should verify:

```text
HTTP request
    ↓
controller
    ↓
service
    ↓
response
```

So don't rely on controller line coverage alone.

---

# 28. Coverage for Services

Services are often excellent candidates for high unit-test coverage.

Example:

```text
createUser()
updateUser()
deleteUser()
getUser()
```

You can test:

```text
success
not found
duplicate
invalid state
dependency failure
```

Coverage can then reveal missed branches.

---

# 29. Coverage for Repositories

Repository coverage is different.

If you have:

```text
userRepository.findById()
userRepository.findByEmail()
userRepository.create()
```

integration tests using the test database are valuable.

Coverage can tell you whether those repository functions execute.

But correctness requires checking:

```text
MongoDB interaction
query behavior
returned data
errors
constraints
```

Coverage alone can't prove those things.

---

# 30. Coverage for Middleware

Middleware is another important area.

For authentication middleware:

```text
no token
invalid token
valid token
```

For authorization:

```text
missing permission
correct permission
wrong role
```

A coverage report can help ensure these paths are actually reached.

---

# 31. Coverage for Utilities

Utilities often have small branches:

```js
function normalizeEmail(email) {
    if (!email) {
        return null;
    }

    return email.trim().toLowerCase();
}
```

Tests should include:

```text
valid email
empty value
spaces
uppercase
```

Coverage helps ensure both branches are exercised.

---

# 32. Coverage and Refactoring

Coverage is also useful during refactoring.

Suppose you change:

```text
old authentication service
```

into:

```text
new authentication service
```

You can compare coverage before and after.

If coverage suddenly drops:

```text
95%
 ↓
72%
```

you know the refactor may have left important behavior untested.

But again, don't treat the number as the only signal.

---

# 33. Coverage and CI

Eventually your GitHub workflow might do:

```text
git push
   ↓
CI
   ↓
install dependencies
   ↓
run tests
   ↓
generate coverage
   ↓
check threshold
   ↓
pass / fail
```

For example:

```text
Tests:      214 passed
Coverage:  91%
Threshold: 85%

✅ CI passes
```

This is how coverage becomes useful at team level.

---

# 34. Coverage Reports in Pull Requests

A mature setup can report:

```text
Coverage before PR: 91%
Coverage after PR:  89%
```

Or:

```text
Changed lines:
95% covered
```

This is more useful than only looking at the entire repository.

Why?

Because old untested code may already exist.

You especially want new code to come with tests.

---

# 35. Coverage Doesn't Tell You Test Quality

Consider:

```js
test("returns something", async () => {
    const result = await getUser("123");

    expect(result).toBeDefined();
});
```

This may increase coverage.

But a stronger test might be:

```js
expect(result.id).toBe("123");
expect(result.email).toBe("test@example.com");
```

Or better:

```text
assert the behavior the user actually cares about
```

Coverage measures execution.

Assertions measure what you verified.

---

# 36. Mutation Testing

There's a more advanced technique called **mutation testing**.

Imagine your code:

```js
return price * 0.9;
```

A mutation tool changes it conceptually to:

```js
return price * 0.8;
```

Then runs your tests.

If tests fail:

```text
✅ Tests detected the bug
```

If tests still pass:

```text
❌ Tests weren't strong enough
```

This demonstrates something important:

> High coverage doesn't necessarily mean strong tests.

You don't need mutation testing for your starter immediately, but understanding the idea is valuable.

---

# 37. Coverage vs Mutation Testing

Think:

```text
Coverage
   ↓
Did the test execute this code?

Mutation testing
   ↓
Would the test detect a change in this code?
```

That's a powerful distinction.

---

# 38. A Practical Coverage Target

Don't blindly choose:

```text
100%
```

A better approach is:

```text
Set a reasonable baseline
        ↓
protect it in CI
        ↓
increase it gradually
```

For example:

```text
Initial target:
80–85%

Later:
85–90%

Critical modules:
higher expectations
```

The exact percentage depends on the project.

---

# 39. Critical Code Deserves More Attention

Not all code has equal risk.

For example:

```text
Authentication
Authorization
Payments
Security
Data deletion
Permissions
```

deserve stronger testing than:

```text
simple formatting helper
```

So don't optimize only for:

```text
global coverage = 95%
```

Think about:

```text
risk × importance × complexity
```

---

# 40. Risk-Based Testing

Imagine:

```text
Payment service
coverage = 98%

Date formatting utility
coverage = 100%
```

Good.

But if:

```text
Authorization middleware
coverage = 55%
```

that's a much bigger concern.

The number alone doesn't tell you the priority.

---

# 41. Coverage Report as a Map

A very useful mental model:

```text
                 Coverage Report
                       ↓
                 map of testing
                       ↓
              ┌────────┼────────┐
              ↓        ↓        ↓
          covered   branches  untouched
              │        │        │
              ↓        ↓        ↓
           review    add tests  investigate
```

Coverage tells you where to look.

It doesn't tell you exactly what the correct test should be.

# 42. Your Backend Coverage Strategy

For your MERN backend, a sensible approach is:

```text
Utilities
    ↓
high coverage

Services
    ↓
high branch coverage

Repositories
    ↓
integration coverage

Controllers
    ↓
integration coverage

Middleware
    ↓
strong branch coverage

Authentication
    ↓
strong scenario coverage

Authorization
    ↓
strong scenario coverage

External integrations
    ↓
mocked unit tests + selected integration tests
```

This is much better than trying to maximize one global number.

> "I got 100%!"

> **"I discovered and tested a missing behavior."**

# 44. Coverage Doesn't Replace Code Review

A pull request can have:

```text
100% coverage
```

and still contain:

```text
bad architecture
security vulnerability
incorrect business rule
poor naming
unnecessary complexity
```

So your engineering quality system should be:

```text
Tests
+
Coverage
+
Code review
+
Linting
+
Type/static analysis where applicable
+
Security checks
```

No single tool is enough.

---

# 45. The Coverage Trap

Avoid this mindset:

```text
Developer:
"I need 90% coverage."

↓

Writes easy tests.

↓

Coverage = 90%.

↓

Done.
```

Better:

```text
Developer:
"What behavior is risky?"

↓

Write meaningful tests.

↓

Run coverage.

↓

Find missing branches.

↓

Add important scenarios.

↓

Protect baseline in CI.
```

That's professional testing.

# 46. Practical Exercise

Take one service from your backend.

For example:

```text
auth.service.js
```

Run:

```bash
npm test -- --coverage
```

Then inspect:

```text
Statements
Branches
Functions
Lines
```

Find the **three least-covered branches**.

For each one, ask:

```text
What scenario causes this branch?
```

Then create a test for that scenario.

This is much better practice than simply trying to raise the percentage.

# 47. Coverage Checklist

Before considering coverage useful, ask:

```text
✓ Are important branches tested?
✓ Are error paths tested?
✓ Are authorization paths tested?
✓ Are authentication failures tested?
✓ Are edge cases tested?
✓ Are critical modules sufficiently covered?
✓ Are coverage thresholds enforced in CI?
✓ Are exclusions justified?
✓ Are tests asserting behavior?
```

If the answer is yes, your coverage number becomes meaningful.
