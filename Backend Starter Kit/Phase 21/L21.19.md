# Lesson 21.19 — Build Backend Test Architecture

This is the **final lesson of Phase 21**.

Your roadmap defines Phase 21 as **Testing Backend Architecture**, ending with exactly this lesson: **21.19 Build backend test architecture**.

The goal today is not to learn another Jest function.

The goal is to answer:

> **"If I build a real MERN backend, where does every kind of test go, how is test data created, how is the database managed, and how do all these pieces work together?"**

By the end, you should have a mental architecture like this:

```text
                         TEST SUITE
                             │
              ┌──────────────┴──────────────┐
              │                             │
           UNIT TESTS                 INTEGRATION TESTS
              │                             │
      ┌───────┼────────┐             ┌──────┼──────┐
      │       │        │             │      │      │
   utils   services  middleware    routes controllers DB
      │       │        │             │      │      │
      └───────┴────────┘             └──────┴──────┘
              │                             │
            mocks                       Test DB
              │                             │
              └──────────┬──────────────────┘
                         │
                      Fixtures
                         │
                      Coverage
                         │
                         ▼
                         CI
```

# 1. Why Do We Need Test Architecture?

If you don't design your testing structure, your project can quickly become:

```text
tests/
├── test1.js
├── test2.js
├── test3.js
├── authTest.js
├── userTest.js
├── todoTest.js
├── randomTest.js
├── setup.js
├── setup2.js
└── test-final.js
```

Eventually:

- tests become hard to find
    
- setup gets duplicated
    
- database state leaks between tests
    
- mocks become confusing
    
- fixtures are scattered
    
- slow tests increase
    
- developers stop trusting the suite
    

A testing architecture prevents this.

---

# 2. First Principle: Separate Unit and Integration Tests

The foundation is:

```text
tests/
├── unit/
└── integration/
```

This matches the roadmap's broader testing architecture: **unit tests focus on individual pieces**, while integration tests exercise the complete request path.

---

# 3. Unit Tests

Unit tests focus on one piece of your application.

Examples:

```text
utility
service
validation helper
middleware logic
```

Imagine:

```text
user.service.js
```

A unit test might be:

```text
userService
     ↓
mock repository
```

No Express.

No HTTP.

No MongoDB.

No real external API.

The question is:

> **Does this piece of code behave correctly?**

---

# 4. Integration Tests

Integration tests combine multiple real components.

For an API:

```text
HTTP Request
     ↓
Route
     ↓
Middleware
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Test Database
```

This is the request flow described in your architecture roadmap.

The question becomes:

> **Do these components actually work together?**

---

# 5. Don't Make Everything a Unit Test

A common mistake is:

```text
Everything mocked
Everything isolated
100% unit tests
```

Then you might discover:

```text
Controller → Service
```

works in unit tests,

but:

```text
Controller → Service → Repository → MongoDB
```

doesn't actually work.

Integration tests catch those problems.

---

# 6. Don't Make Everything an Integration Test Either

The opposite mistake is:

```text
Every test
   ↓
HTTP
   ↓
MongoDB
```

Now a simple service test might take hundreds of milliseconds.

Multiply that by thousands of tests.

Your suite becomes slow.

So use both:

```text
Unit tests
   +
Integration tests
```

---

# 7. A Practical Testing Pyramid

For your backend:

```text
                    /\
                   /  \
                  / E2E\
                 /------\
                / Integr.\
               /----------\
              / Unit Tests \
             /______________\
```

Think:

```text
Many unit tests
Some integration tests
Few full end-to-end tests
```

You don't need to follow the pyramid mathematically.

It's a design principle.

# 11. What Goes Inside `helpers/`?

Helpers contain reusable testing utilities.

For example:

```text
tests/helpers/
├── database.js
├── auth.js
└── request.js
```

Potential responsibilities:

```text
database.js
    → connect / cleanup test DB

auth.js
    → create authenticated test users

request.js
    → reusable request helpers
```

Keep helpers focused.

---

# 12. What Goes Inside `factories/`?

Factories create test data.

For example:

```text
tests/factories/
├── user.factory.js
├── todo.factory.js
└── course.factory.js
```

Usage:

```js
const user = await createUser();

const todo = await createTodo({
    userId: user.id
});
```

This came directly from the previous lesson.

---

# 13. What Goes Inside `fixtures/`?

Fixtures are predefined data.

For example:

```text
tests/fixtures/
├── api/
├── webhooks/
└── external-services/
```

You might have:

```text
payment-success.json
payment-failed.json
ai-response.json
email-webhook.json
```

Fixtures are especially useful for testing external integrations.

---

# 14. What Goes Inside `mocks/`?

Reusable mocks can live here.

For example:

```text
tests/mocks/
├── mailer.mock.js
├── payment.mock.js
└── ai.mock.js
```

But don't create a mock file for everything.

If a mock is only used in one test file, keeping it there can be cleaner.

---

# 15. Global Test Setup

Some setup should happen before the entire test suite.

For example:

```text
tests/setup/
└── jest.setup.js
```

Potential responsibilities:

```text
environment setup
global matchers
test configuration
shared initialization
```

But database setup can be handled separately depending on your chosen test-database strategy.

---

# 16. Test Database Architecture

Integration tests should use a **test database**, not your development database.

Think:

```text
Development
    ↓
myapp

Testing
    ↓
myapp_test
```

Never do:

```text
npm test
    ↓
production database
```

Obviously.

But also avoid:

```text
npm test
    ↓
development database
```

because tests can destroy your development data.

---

# 17. Database Lifecycle

Your integration test lifecycle should look roughly like:

```text
Test process starts
       ↓
Connect test database
       ↓
Run test
       ↓
Clean state
       ↓
Next test
       ↓
Clean state
       ↓
...
       ↓
Test process ends
       ↓
Disconnect database
```

This connects directly with the **Test Database** and **Test Isolation** lessons.

---

# 18. Isolation Is Non-Negotiable

Suppose:

```text
Test A
creates user
```

Then:

```text
Test B
expects no users
```

If Test B sees Test A's user:

```text
❌ Test B becomes dependent on Test A
```

That's a bad test.

Instead:

```text
Test A
   ↓
isolated state

Test B
   ↓
fresh state
```

---

# 19. Cleanup Strategies

There are several ways to clean the test database.

### Clear collections

```text
User.deleteMany({})
Todo.deleteMany({})
```

### Drop database

```text
drop test database
```

### Transactions

```text
begin transaction
     ↓
run test
     ↓
rollback
```

Each approach has trade-offs.

For your learning architecture, the key principle is:

> **Every test should start from a known state.**

# 20. Test Data Flow

Now combine database + factory:

```text
Test
 ↓
Factory
 ↓
Test Database
 ↓
API Request
 ↓
Application
 ↓
Test Database
 ↓
Assertion
```

Example:

```js

    userId: user.id

    .get("/api/v1/todos")
```

# 25. Authorization Test Architecture

Suppose:

```text
User A owns Todo A
User B owns Todo B
```

Test:

```text
User A → Todo A
```

should work.

But:

```text
User A → Todo B
```

should fail.

You can build this easily with factories:

```js
const userA = await createUser();
const userB = await createUser();

const todo = await createTodo({
    userId: userB.id
});
```

Then authenticate as User A.

This makes your security tests very readable.

# 30. Testing Error Handling

Your test architecture should verify that errors eventually become consistent HTTP responses.

For example:

```text

 ↓

 ↓
Global error middleware
 ↓
HTTP 404
```


# 31. Testing Middleware

For middleware, ask:

```text
Does it allow valid requests?
Does it reject invalid requests?
Does it attach expected information?
Does it produce the correct status?
```

For auth middleware:

```text
no token → 401
invalid token → 401
expired token → 401
valid token → next()
```

For authorization:

```text
correct role → allowed
wrong role → 403
```

# 32. Testing Repositories

Repositories interact with MongoDB.

So repository tests are often best as integration tests.

Example:

```text
userRepository.findByEmail()
       ↓
MongoDB
```

Test:

```text
existing email
missing email
duplicate constraints
returned document
```

This verifies that your actual query works.

# 33. Testing Services

Services are excellent unit-test candidates.

Example:

```text

```

Mock:

```text

mailSender
```

Then test business rules:

```text

```

This makes service tests fast.

# 34. Testing Controllers

Controllers can be tested in two ways.

### Unit-style

Mock the service:

```text

   ↓
mock service
```

### Integration-style

Use:

```text
HTTP
 ↓
route
 ↓
controller
 ↓
real service
```

For your starter, integration tests through **Supertest** will often give more useful confidence for controllers.

You learned Supertest in 21.10.

# 36. Separate `app` From `server`

This is especially important for testing.

Good architecture:

```text
app.js
    ↓
creates Express app

server.js
    ↓

    ↓
starts HTTP server
```

Then tests can import:

```js
import app from "../../app.js";
```

without necessarily starting:

```text

```

This makes integration testing much cleaner.

# 45. Example: Complete Todo Test

Let's put everything together.

```js
test("user can update own todo", async () => {
    const { user, token } =
        await createAuthenticatedUser();

    const todo = await createTodo({
        userId: user.id,
        title: "Old title"
    });

    const response = await request(app)
        .patch(`/api/v1/todos/${todo.id}`)
        .set("Authorization", `Bearer ${token}`)
        .send({
            title: "New title"
        });

    expect(response.status).toBe(200);
    expect(response.body.data.title)
        .toBe("New title");
});
```

Look at the architecture behind this tiny test:

```text
createAuthenticatedUser()
        ↓
Factory
        ↓
Test DB

createTodo()
        ↓
Factory
        ↓
Test DB

request()
        ↓
Supertest
        ↓
Route
        ↓
Auth middleware
        ↓
Validation
        ↓
Controller
        ↓
Service
        ↓
Repository
        ↓
Test DB

Assertions
        ↓
Result
```

That is a **real integration test**.

# 46. Example: Complete Service Unit Test

Now compare:

```js
test("throws conflict when email exists", async () => {
    userRepository.findByEmail.mockResolvedValue({
        id: "123"
    });

    await expect(
        userService.createUser({
            email: "test@example.com"
        })
    ).rejects.toThrow("Email already exists");
});
```

Architecture:

```text
Service
  ↓
Mock Repository
  ↓
Controlled result
```

No HTTP.

No MongoDB.

Fast and focused.

Here's the most important table of the lesson:

|Backend Layer|Main Test Type|Typical Dependencies|
|---|---|---|

# 50. What NOT to Put in Your Test Architecture

Avoid:

```text
tests/
└── everything.test.js
```

Also avoid:

```text
tests/
├── mockEverything.js
├── helperEverything.js
├── fixtureEverything.js
```

And especially avoid:

```text
test
 ↓
mock service
 ↓
mock repository
 ↓
mock database
 ↓
assert mock
```

That gives you very little confidence.

# 51. Your Testing Decision Tree

When you want to test something, ask:

### "What am I testing?"

If it's:

```text
pure logic
```

→ **Unit test**

If it's:

```text
service business logic
```

→ **Unit test + selected integration test**

If it's:

```text
MongoDB query
```

→ **Integration test**

If it's:

```text
HTTP endpoint
```

→ **Integration test**

If it's:

```text
external provider behavior
```

→ **Mock + dedicated integration test**

If it's:

```text
complete user workflow
```

→ **E2E/integration test**

This decision tree will save you a lot of confusion.

# 56. The One Diagram I Want You to Remember

Don't memorize the directory tree.

Memorize this:

```text
                    TEST
                     │
          ┌──────────┴──────────┐
          │                     │
        UNIT               INTEGRATION
          │                     │
    isolated logic         real request
          │                     │
        mocks              real application
          │                     │
          │                test database
          │                     │
          └──────────┬──────────┘
                     │
                  fixtures
                     │
                  isolation
                     │
                  coverage
                     │
                     ▼
                    CI
```

And underneath it:

```text
Unit tests
    → "Does this piece work?"

Integration tests
    → "Do these pieces work together?"

Fixtures
    → "How do I create known state?"

Mocks
    → "How do I control dependencies?"

Isolation
    → "How do tests stay independent?"

Coverage
    → "What code did my tests actually execute?"
```

That is the real **Backend Test Architecture**.
