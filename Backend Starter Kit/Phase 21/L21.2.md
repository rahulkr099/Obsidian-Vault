# Lesson 21.2 — Testing Pyramid

In **Lesson 21.1**, we learned _why_ testing matters.

Now we answer the next important question:

> **What kinds of tests should we write?**

You could test your entire backend through HTTP for every single case. But that would become slow, difficult to maintain, and expensive to run.

That's why we use the **Testing Pyramid**.

---

# 1. The Testing Pyramid

A simple version looks like this:

```text
                 /\
                /  \
               / E2E\
              /------\
             /        \
            /Integration\
           /------------\
          /              \
         /   Unit Tests   \
        /__________________\
```

Think:

```text
        Fewer
          ↑
          │
       E2E/API
          │
    Integration
          │
        Unit
          │
          ↓
        More
```

The basic idea is:

> **Have many small, fast tests, some larger integration tests, and fewer expensive full-system tests.**

---

# 2. Why a Pyramid?

Imagine your backend has:

```text
100 unit tests
20 integration tests
5 API/E2E tests
```

That's reasonable.

But imagine the opposite:

```text
5 unit tests
20 integration tests
100 API/E2E tests
```

Now every small change could require running hundreds of expensive full API tests.

That's usually unnecessary.

---

# 3. Unit Tests

At the bottom are **unit tests**.

A unit test focuses on a small piece of code.

For example:

```js
function calculateTotal(price, quantity) {
    return price * quantity;
}
```

We can test:

```text
calculateTotal(100, 2)
        ↓
Expected: 200
```

There is no:

```text
Express
MongoDB
HTTP
network
```

Just the function.

---

# 4. Unit Test in Your Backend

Suppose you have:

```text
utils/
└── generateToken.js
```

You can test:

```text
generateToken()
      ↓
valid token?
      ↓
PASS
```

Or:

```text
services/
└── auth.service.js
```

You might test:

```text
correct password
      ↓
login succeeds
```

while replacing the repository with a mock.

We'll learn exactly how to do that later.

---

# 5. Why Unit Tests Are Fast

Imagine this:

```text
Unit test

Function
  ↓
Result
```

That's very little work.

Compare that to:

```text
API test

HTTP
 ↓
Express
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
MongoDB
 ↓
Response
```

Obviously the second one requires much more work.

So unit tests are usually:

```text
Fast
Cheap
Easy to run
Easy to repeat
```

---

# 6. What Unit Tests Are Good At

Unit tests are excellent for:

```text
Business rules
Utilities
Helpers
Validation logic
Token utilities
Data transformations
Small pieces of logic
```

For example:

```text
Password policy
Token expiration calculation
Pagination calculation
Input transformation
Permission calculation
```

---

# 7. But Unit Tests Have a Weakness

Here's the problem.

Suppose you test:

```text
authService
```

and mock:

```text
userRepository
```

Your test can say:

```text
authService works with the repository
```

But what if the actual repository is broken?

For example:

```text
Service expects:

repository.findUserByEmail()

Actual repository:

repository.findByEmail()
```

Your mocked test might still pass because the mock was configured exactly how the service expects.

But the real application could fail.

That's why we need the next layer.

---

# 8. Integration Tests

Integration tests check that **multiple components work together**.

For example:

```text
Service
   ↓
Repository
   ↓
Database
```

Instead of replacing everything with mocks, we allow some real components to interact.

Example:

```text
authService
     ↓
userRepository
     ↓
test MongoDB
```

Now we can catch problems between layers.

---

# 9. Why Integration Tests Matter

Imagine:

```text
Service
   ↓
Repository
```

The service passes:

```js
{
    email: "rahul@example.com"
}
```

But the repository expects:

```js
{
    userEmail: "rahul@example.com"
}
```

Both pieces might pass their individual unit tests.

But together:

```text
Service + Repository
       ↓
      FAIL
```

An integration test can catch this.

---

# 10. Integration Testing in Your Architecture

Your backend architecture looks like:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
    ↓
MongoDB
```

An integration test might test:

```text
Service
   ↓
Repository
   ↓
MongoDB
```

while leaving the HTTP layer out.

Another integration test could include:

```text
Express
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
```

The exact boundary depends on what you're testing.

---

# 11. API / End-to-End Tests

At the top we have larger tests.

For your backend, these can look like:

```text
POST /api/v1/auth/login
```

Then the request goes through the actual application:

```text
HTTP
 ↓
Express
 ↓
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
 ↓
Response
```

This tests the system from the outside.

---

# 12. Why We Need API Tests

Suppose every individual component works:

```text
Route ✅
Middleware ✅
Controller ✅
Service ✅
Repository ✅
```

But someone accidentally registers the route incorrectly:

```js
app.use("/api/v2/auth", authRoutes);
```

while your frontend calls:

```text
/api/v1/auth/login
```

Every unit test could pass.

But the real API is broken.

An API test catches that:

```text
POST /api/v1/auth/login
       ↓
404 ❌
```

That's why full request tests are valuable.

---

# 13. The Three Levels

Let's simplify everything:

### Unit

```text
"Does this piece work?"
```

### Integration

```text
"Do these pieces work together?"
```

### API/E2E

```text
"Does the application work from the user's perspective?"
```

Remember those three questions.

---

# 14. Testing Pyramid for Your MERN Backend

For your project, think of it like this:

```text
                         ┌─────────────┐
                         │ API / E2E   │
                         │             │
                         │ Login       │
                         │ Signup      │
                         │ CRUD        │
                         └──────┬──────┘
                                │
                    ┌───────────┴───────────┐
                    │                       │
                    │    Integration        │
                    │                       │
                    │ Service + Repository  │
                    │ Repository + DB       │
                    │                       │
                    └───────────┬───────────┘
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
              │             Unit                  │
              │                                   │
              │ Utils                             │
              │ Services                          │
              │ Middleware                        │
              │ Validation                        │
              │ Helpers                           │
              │                                   │
              └───────────────────────────────────┘
```

---

# 15. Why Not Just Use API Tests?

This is an important interview question.

Suppose you have:

```text
100 business rules
```

If you test all 100 through HTTP:

```text
HTTP
 ↓
Express
 ↓
Middleware
 ↓
Service
 ↓
Database
```

every time, that's expensive.

But with unit tests:

```text
function
 ↓
result
```

you can test those rules much faster.

So:

```text
Unit tests
→ fast feedback

Integration tests
→ verify connections between components

API tests
→ verify real application behavior
```

---

# 16. Speed Matters

Imagine:

```text
Unit test:
5 ms

Integration test:
100 ms

API test:
500 ms
```

These numbers are just illustrative, but the idea is important.

If you have:

```text
1000 unit tests
100 integration tests
20 API tests
```

your test suite can still be practical.

But if you have:

```text
20 unit tests
100 integration tests
1000 API tests
```

your feedback loop can become painful.

And developers start doing something dangerous:

> **They stop running the tests.**

A test suite that nobody runs isn't useful.

---

# 17. The Pyramid Is a Guideline, Not a Law

Don't take the pyramid too literally.

Real projects don't always look exactly like:

```text
100 unit
20 integration
5 E2E
```

Some applications need more integration testing.

Some frontend-heavy applications use many end-to-end tests.

Some backend systems may intentionally use fewer unit tests and more integration tests.

The important principle is:

> **Use the cheapest test that gives you enough confidence for the behavior you're testing.**

That's a much better rule.

---

# 18. Example: Testing Login

Suppose:

```text
authService.login()
```

contains:

```text
Find user
 ↓
Compare password
 ↓
Generate token
 ↓
Save refresh token
```

We can test it at multiple levels.

### Unit

```text
authService
    ↓
mock repository
```

Check:

```text
correct password → success
wrong password → failure
```

### Integration

```text
authService
    ↓
real repository
    ↓
test database
```

Check:

```text
real user
 ↓
real password hash
 ↓
real database interaction
```

### API

```text
POST /api/v1/auth/login
```

Check:

```text
HTTP request
 ↓
actual backend
 ↓
actual response
```

Each test provides a different kind of confidence.

---

# 19. Don't Duplicate Everything

Suppose you test:

```text
wrong password
```

in a service unit test.

Then you don't necessarily need 15 identical API tests that only prove the exact same business rule.

Instead:

```text
Unit test
→ detailed business logic

Integration test
→ layer interaction

API test
→ important user-facing flows
```

This reduces duplication.

---

# 20. A Practical Distribution

For your starter project, I would aim for something conceptually like:

```text
                 API / E2E
                    ▲
                   / \
                  /   \
                 /     \
          Integration  \
               ▲        \
              / \        \
             /   \        \
            /     \        \
           /       \        \
          /  Unit   \       \
         /___________\_______\
```

And roughly:

```text
Lots of:
    Unit tests

Moderate:
    Integration tests

Focused:
    API tests
```

Don't obsess over percentages.

Focus on **coverage of important behavior**.

# 21. A Real Example: Todo Ownership

This is especially relevant to your backend.

Requirement:

> A user can only update their own Todo.

We could test it at different levels.

### Unit

Test the ownership/business rule:

```text
userId === todo.userId
      ↓
allowed
```

and:

```text
userId !== todo.userId
      ↓
denied
```

### Integration

Test the real repository query:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

### API

Actually send:

```http
PATCH /api/v1/todos/TODO_B
Authorization: Bearer USER_A_TOKEN
```

Expected:

```text
403 / 404
```

Now we've tested the same security boundary from multiple useful angles.

# 24. The Most Important Comparison

Keep this table in your notes:

|Type|Tests|Speed|Dependencies|
|---|---|---|---|
|Unit|Small piece|⚡ Fast|Usually mocked|
|Integration|Multiple layers|Medium|Some real|
|API/E2E|Whole flow|Slowest|Mostly real|

The question each one answers:

```text
Unit
→ Does this piece work?

Integration
→ Do these pieces work together?

API/E2E
→ Does the application work as a real user/API client sees it?
```

# 26. Common Beginner Mistakes

### Mistake 1 — Only testing success

```text
login works ✅
```

but never testing:

```text
wrong password
expired token
missing token
```

---

### Mistake 2 — Testing everything through HTTP

This makes the suite slow and difficult to maintain.

---

### Mistake 3 — Mocking everything

If you mock every dependency, you can accidentally create tests that prove only that your mocks work.

---

### Mistake 4 — No integration tests

Then you may never discover that two individually correct components don't work together.

---

### Mistake 5 — Too many E2E tests

Full-stack tests are valuable, but they are expensive.

---

# 27. Interview Question

**Q: Why is the testing pyramid useful?**

A good answer:

> The testing pyramid encourages having many fast unit tests, fewer integration tests, and a smaller number of full API or end-to-end tests. Unit tests provide fast feedback, integration tests verify that components work together, and API/E2E tests verify important real-world flows.

That's enough for now.

```text

```
