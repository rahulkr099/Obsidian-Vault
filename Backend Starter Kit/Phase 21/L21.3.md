# Lesson 21.3 — Jest Fundamentals

In **21.1**, we learned why testing matters.

In **21.2**, we learned the testing pyramid.

Now we start writing actual tests.

Our tool for this phase is **Jest**.

Your starter roadmap specifically uses Jest for backend testing, so we'll learn Jest as a tool for testing the architecture we've been building.

---

# 1. What is Jest?

Jest is a **JavaScript testing framework**.

It gives us tools to:

```text
Write tests
   ↓
Run tests
   ↓
Compare expected vs actual results
   ↓
Show PASS / FAIL
```

For example:

```text
2 + 3
  ↓
5
  ↓
Expected: 5
Actual:   5
  ↓
PASS ✅
```

---

# 2. Jest Is Not Your Application

This distinction is important.

Your backend might use:

```text
Node.js
Express
Mongoose
MongoDB
```

Jest doesn't replace any of them.

Instead:

```text
Your application
       ↑
       │
     Jest
       │
       ↓
Tests
```

Jest is the tool that **runs and evaluates your tests**.

---

# 3. Installing Jest

If you haven't already installed it in your backend:

```bash
npm install -D jest
```

Why `-D`?

Because Jest is a **development dependency**.

You need it while developing/testing your application, but your production server doesn't normally need Jest to handle requests.

Your `package.json` will contain something conceptually like:

```json
{
  "devDependencies": {
    "jest": "..."
  }
}
```

---

# 4. Why `--save-dev`?

These two commands:

```bash
npm install jest
```

and:

```bash
npm install -D jest
```

have different purposes.

### Production dependency

```bash
npm install express
```

Express is required to run your backend.

### Development dependency

```bash
npm install -D jest
```

Jest is required to test your backend during development/CI.

Think:

```text
dependencies
    ↓
Application needs them

devDependencies
    ↓
Developer needs them
```

# 5. Our First Test

Let's start with something extremely simple.

Create:

```text
tests/
└── math.test.js
```

Put:

```js
function add(a, b) {
    return a + b;
}

test("adds two numbers", () => {
    expect(add(2, 3)).toBe(5);
});
```

Don't worry about the syntax yet.

We'll break it down.

---

# 6. `test()`

This part:

```js
test("adds two numbers", () => {
    // test code
});
```

defines a test.

The first argument:

```js
"adds two numbers"
```

is the test's description.

The second argument:

```js
() => {
    ...
}
```

contains the test itself.

Think:

```text
test(
    "What am I testing?",
    "How do I test it?"
)
```

---

# 7. `expect()`

Now look at:

```js
expect(add(2, 3))
```

`expect()` tells Jest:

> "I want to make an assertion about this value."

Our function returns:

```js
add(2, 3)
```

which is:

```text
5
```

So:

```js
expect(add(2, 3))
```

means:

```text
I expect the result of add(2, 3) to satisfy something.
```

---

# 8. `.toBe()`

Then:

```js
.toBe(5)
```

means:

> "I expect the value to be 5."

So the whole line:

```js
expect(add(2, 3)).toBe(5);
```

means:

```text
Run add(2, 3)
       ↓
Get actual result
       ↓
Compare with 5
       ↓
PASS / FAIL
```

---

# 9. Running Jest

You can run:

```bash
npx jest
```

Jest searches for test files and runs them.

You'll see output similar to:

```text
PASS  tests/math.test.js

✓ adds two numbers

Test Suites: 1 passed
Tests:       1 passed
```

The exact formatting/version output can differ.

The important thing is:

```text
PASS ✅
```

# 10. Add a Test Script

Instead of typing:


```json

    "test": "jest"
  }
}
```

Now run:

```bash

```

Much easier.

# 13. Multiple Tests

You can have multiple tests in one file:

```js
test("adds two numbers", () => {
    expect(2 + 3).toBe(5);
});

test("subtracts two numbers", () => {
    expect(5 - 3).toBe(2);
});

test("multiplies two numbers", () => {
    expect(4 * 3).toBe(12);
});
```

Running:

```bash
npm test
```

might show:

```text
✓ adds two numbers
✓ subtracts two numbers
✓ multiplies two numbers
```

Now you have three independent tests.

---

# 14. `describe()`

When your project gets larger, you want to group related tests.

That's where `describe()` comes in.

```js
describe("Math operations", () => {
    test("adds two numbers", () => {
        expect(2 + 3).toBe(5);
    });

    test("subtracts two numbers", () => {
        expect(5 - 3).toBe(2);
    });
});
```

Think:

```text
describe
   ↓
Group of related tests
```

For your backend:

```js
describe("Auth Service", () => {
    test("logs in with valid credentials", () => {
        // ...
    });

    test("rejects invalid password", () => {
        // ...
    });
});
```

This becomes much easier to read.

---

# 15. `test()` vs `it()`

Jest also provides:

```js
it()
```

So these are equivalent in meaning:

```js
test("adds numbers", () => {
    // ...
});
```

and:

```js
it("adds numbers", () => {
    // ...
});
```

You'll often see:

```js
describe("Auth Service", () => {
    it("logs in with valid credentials", () => {
        // ...
    });
});
```

or:

```js
describe("Auth Service", () => {
    test("logs in with valid credentials", () => {
        // ...
    });
});
```

For this course, we'll primarily use `test()`.

# 16. A Better Backend Example

Let's imagine this function:

```js
function isAdult(age) {
    return age >= 18;
}
```

We could test:

```js
describe("isAdult", () => {
    test("returns true for an adult", () => {
        expect(isAdult(20)).toBe(true);
    });

    test("returns false for a minor", () => {
        expect(isAdult(15)).toBe(false);
    });
});
```

Notice something important.

We're testing **behavior**.

```text
Input
  ↓
Function
  ↓
Expected output
```

That's the foundation of unit testing.

# 17. Common Matchers

Jest provides different matchers for different situations.

### Exact value

```js
expect(5).toBe(5);
```

### Objects

```js
expect({ name: "Rahul" }).toEqual({
    name: "Rahul"
});
```

### Truthiness

```js
expect(true).toBeTruthy();
```

### False

```js
expect(false).toBeFalsy();
```

### Arrays

```js
expect(["a", "b"]).toContain("a");
```

We'll study matchers properly in **Lesson 21.4**.

For now, just understand the idea:

```text
expect(actual)
      ↓
matcher
      ↓
expected
```

# 18. `toBe()` vs `toEqual()`

This is a common beginner question.

For primitive values:

```js
expect(5).toBe(5);
```

works perfectly.

For objects, you'll generally use:

```js
expect(user).toEqual({
    name: "Rahul"
});
```

For example:

```js
const user = {
    name: "Rahul"
};

expect(user).toEqual({
    name: "Rahul"
});
```

The important thing for now is:

```text
toBe()
→ exact value/reference comparison

toEqual()
→ compares object/array contents
```

We'll go deeper in 21.4.

# 19. Testing Errors

Backend applications fail all the time.

We need to test failures too.

Suppose:

```js
function divide(a, b) {
    if (b === 0) {
        throw new Error("Cannot divide by zero");
    }

    return a / b;
}
```

We can test:

```js
test("throws when dividing by zero", () => {
    expect(() => divide(10, 0))
        .toThrow("Cannot divide by zero");
});
```

Notice this:

```js
() => divide(10, 0)
```

We're passing a function to `expect()`.

Why?

Because we want Jest to **execute it and observe the thrown error**.

If we wrote:

```js
expect(divide(10, 0))
```

the error would happen before Jest gets the value to inspect.

This pattern will become very useful when testing:

```text
AppError
validation
services
authorization
```

# 20. Async Tests

Backend code is usually asynchronous.

For example:

```js
async function getUser() {
    return {
        id: 1,
        name: "Rahul"
    };
}
```

We can test it with:

```js
test("gets a user", async () => {
    const user = await getUser();

    expect(user.name).toBe("Rahul");
});
```

Notice:

```js
test(..., async () => {
```

and:

```js
await getUser();
```

This tells Jest:

> Wait for the asynchronous operation before deciding whether the test passed.

This is extremely important for backend testing.

---

# 21. Testing Rejected Promises

Suppose:

```js
async function getUser() {
    throw new Error("User not found");
}
```

We can eventually write:

```js
test("throws when user is missing", async () => {
    await expect(getUser())
        .rejects
        .toThrow("User not found");
});
```

Don't worry if this syntax looks strange.

Break it down:

```text
getUser()
   ↓
Promise rejects
   ↓
rejects
   ↓
toThrow()
```

We'll use this kind of pattern frequently when testing services.

# 22. Test Naming Matters

Compare:

```js
test("test1", () => {
    // ...
});
```

with:

```js
test("rejects login when password is incorrect", () => {
    // ...
});
```

The second one is much better.

When CI tells you:

```text

```

you immediately know:

```text
❌ rejects login when password is incorrect
```

Good test names are part of good engineering.

# 23. Arrange → Act → Assert

You'll use this pattern constantly.

Suppose we're testing:

```text
login
```

### Arrange

Prepare the test:

```text
Create test user
Prepare password
Prepare repository mock
```

### Act

Perform the action:

```text
Call authService.login()
```

### Assert

Check result:

```text
Login succeeded
Token returned
```

So:

```text
ARRANGE
   ↓
ACT
   ↓
ASSERT
```

We'll use this throughout Phase 21.

# 29. What Happens When a Test Fails?

Suppose:

```js
test("adds two numbers", () => {
    expect(2 + 3).toBe(6);
});
```

Actual:

```text
5
```

Expected:

```text
6
```

Jest reports:

```text
FAIL ❌
```

This is not a bad thing.

A failed test means:

> **Our assumption and the application's behavior don't match.**

Then we investigate.

Maybe:

```text
Test is wrong
```

or:

```text
Application is wrong
```

or:

```text
Requirement changed
```

A failed test is information.

---

# 30. Your First Real Backend Testing Habit

From now on, whenever you build a feature, think:

```text
Build
 ↓
Manually verify
 ↓
Write tests
 ↓
Refactor
 ↓
Run tests
```

Don't wait until the entire project is finished.

For example:

```text
Build login
 ↓
Test login
 ↓
Build refresh token
 ↓
Test refresh token
 ↓
Build logout
 ↓
Test logout
```

This produces much better confidence.

# The Mental Model

Keep this simple model in your head:

```text
             TEST
              │
              ▼
        Run some code
              │
              ▼
       Get actual result
              │
              ▼
       Compare with expected
              │
          ┌───┴───┐
          ▼       ▼
        PASS     FAIL
          │       │
          ▼       ▼
       Good     Investigate
```

And the syntax:

```js

    expect(actual).toBe(expected);
});
```

That's the fundamental Jest pattern.
