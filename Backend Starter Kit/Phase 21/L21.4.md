# Lesson 21.4 — Test Structure & Assertions

In **21.3**, we learned the basic Jest structure:

```js
test("description", () => {
    expect(actual).toBe(expected);
});
```

Now we'll make that much more useful.

The two things we'll focus on are:

1. **How to structure tests clearly**
    
2. **How to choose the correct Jest assertion**
    

This becomes especially important when testing real backend data such as users, API responses, errors, arrays, objects, and database results.

---

# 1. The Three-Part Test Structure

A good test usually follows:

```text
Arrange
   ↓
Act
   ↓
Assert
```

This is one of the most useful patterns you'll use throughout Phase 21.

---

## Arrange

Prepare everything required for the test.

```js
const user = {
    name: "Rahul",
    role: "user"
};
```

---

## Act

Perform the operation you're testing.

```js
const result = getUserRole(user);
```

---

## Assert

Check the result.

```js
expect(result).toBe("user");
```

Together:

```js
test("returns the user's role", () => {
    // Arrange
    const user = {
        name: "Rahul",
        role: "user"
    };

    // Act
    const result = getUserRole(user);

    // Assert
    expect(result).toBe("user");
});
```

This structure makes tests much easier to understand.

---

# 2. Why Arrange → Act → Assert Matters

Imagine a large test:

```js
test("creates user", async () => {
    // 30 lines preparing data

    // 10 lines calling functions

    // 20 lines checking results
});
```

Without structure, it's difficult to understand.

With:

```text
ARRANGE
  ↓
ACT
  ↓
ASSERT
```

you can quickly identify:

```text
What was prepared?
What happened?
What was expected?
```

We'll use this structure throughout the course.

---

# 3. `expect()` Is the Beginning of an Assertion

Suppose:

```js
const result = 10;
```

You write:

```js
expect(result)
```

At this point you're saying:

> "I want to make a statement about `result`."

Then you choose a matcher:

```js
expect(result).toBe(10);
```

So think:

```text
expect()
   ↓
matcher
   ↓
expected value
```

---

# 4. `toBe()`

Use `toBe()` for exact primitive values.

```js
expect(10).toBe(10);
```

Examples:

```js
expect("hello").toBe("hello");

expect(true).toBe(true);

expect(false).toBe(false);

expect(5).toBe(5);
```

It's very useful for:

```text
strings
numbers
booleans
null
undefined
```

---

# 5. Example: HTTP Status Code

This is a very common backend use case.

Suppose:

```js
const statusCode = 200;
```

Test:

```js
expect(statusCode).toBe(200);
```

Another:

```js
expect(statusCode).toBe(401);
```

This is exactly the kind of assertion we'll use later with API tests.

---

# 6. `toEqual()`

Now suppose you have an object:

```js
const user = {
    name: "Rahul",
    role: "user"
};
```

You can write:

```js
expect(user).toEqual({
    name: "Rahul",
    role: "user"
});
```

`toEqual()` compares the contents of objects and arrays.

---

# 7. `toBe()` vs `toEqual()`

This is an important distinction.

Consider:

```js
const user = {
    name: "Rahul"
};
```

This:

```js
expect(user).toBe({
    name: "Rahul"
});
```

will not behave the way a beginner might expect.

Why?

Because objects are reference values.

Instead use:

```js
expect(user).toEqual({
    name: "Rahul"
});
```

Think:

```text
toBe()
   ↓
same exact value/reference

toEqual()
   ↓
same contents
```

For backend JSON objects, `toEqual()` is usually what you want.

---

# 8. Example: API Response

Suppose your controller returns:

```js
const response = {
    success: true,
    message: "User created"
};
```

Test:

```js
expect(response).toEqual({
    success: true,
    message: "User created"
});
```

This is much more useful than checking the whole object with `toBe()`.

---

# 9. `toStrictEqual()`

Jest also provides:

```js
toStrictEqual()
```

It's stricter than `toEqual()`.

For example, it pays more attention to things such as:

```text
undefined properties
object types
array/object structure
```

For most normal API JSON testing:

```js
toEqual()
```

is enough.

Use:

```js
toStrictEqual()
```

when you specifically care about stricter structural equality.

---

# 10. `toContain()`

Suppose:

```js
const roles = ["user", "admin", "moderator"];
```

You can check:

```js
expect(roles).toContain("admin");
```

This means:

> The array should contain `"admin"`.

Very useful for:

```text
roles
permissions
IDs
tags
emails
```

---

# 11. Example: Permissions

Suppose:

```js
const permissions = [
    "user:read",
    "user:update"
];
```

Test:

```js
expect(permissions).toContain("user:read");
```

And:

```js
expect(permissions).not.toContain("admin:delete");
```

Notice:

```js
.not
```

This reverses the expectation.

---

# 12. `not`

Jest lets you negate assertions.

For example:

```js
expect(5).not.toBe(10);
```

Means:

```text
5 should NOT be 10
```

Another example:

```js
expect(["user"]).not.toContain("admin");
```

This is extremely useful for security testing later.

For example:

```js
expect(user.permissions).not.toContain("admin:delete");
```

---

# 13. `toHaveLength()`

Suppose:

```js
const users = [
    { name: "A" },
    { name: "B" },
    { name: "C" }
];
```

You can write:

```js
expect(users).toHaveLength(3);
```

Useful for:

```text
query results
pagination
arrays
strings
```

For example:

```js
expect(results).toHaveLength(10);
```

This can become useful when testing pagination in later phases.

---

# 14. `toBeTruthy()`

Checks whether a value is truthy.

```js
expect("hello").toBeTruthy();
```

Also:

```js
expect(123).toBeTruthy();
expect(true).toBeTruthy();
```

But be careful.

Truthy/falsy tests can sometimes be less precise than testing the exact expected value.

For example, if you expect:

```js
true
```

prefer:

```js
expect(result).toBe(true);
```

rather than:

```js
expect(result).toBeTruthy();
```

when the exact boolean matters.

---

# 15. `toBeFalsy()`

The opposite:

```js
expect(false).toBeFalsy();
```

For example:

```js
const isAdmin = false;

expect(isAdmin).toBeFalsy();
```

Again, use exact assertions when possible.

---

# 16. `toBeNull()`

Suppose:

```js
const user = null;
```

You can test:

```js
expect(user).toBeNull();
```

Very useful for repository operations:

```text
findById()
    ↓
user not found
    ↓
null
```

Then:

```js
expect(user).toBeNull();
```

---

# 17. `toBeUndefined()`

For:

```js
const value = undefined;
```

use:

```js
expect(value).toBeUndefined();
```

Useful when testing optional values.

---

# 18. `toBeDefined()`

Opposite:

```js
expect(value).toBeDefined();
```

For example:

```js
const token = "abc123";

expect(token).toBeDefined();
```

But again, if you know exactly what the value should be, prefer checking that exact value.

---

# 19. `toBeGreaterThan()`

Useful for numeric values.

```js
expect(10).toBeGreaterThan(5);
```

Also:

```js
expect(10).toBeGreaterThanOrEqual(10);
```

This can be useful for:

```text
pagination
limits
timestamps
counts
scores
```

---

# 20. `toBeLessThan()`

Similarly:

```js
expect(5).toBeLessThan(10);
```

And:

```js
expect(10).toBeLessThanOrEqual(10);
```

---

# 21. `toMatch()`

Useful for strings and regular expressions.

For example:

```js
const email = "rahul@example.com";

expect(email).toMatch(/@/);
```

Or:

```js
expect(message).toMatch(/invalid/i);
```

This can be useful when the exact error message isn't important but the presence of a particular phrase is.

---

# 22. `toHaveProperty()`

This is extremely useful for backend objects.

Suppose:

```js
const user = {
    id: "123",
    email: "rahul@example.com",
    role: "user"
};
```

You can test:

```js
expect(user).toHaveProperty("email");
```

Or:

```js
expect(user).toHaveProperty("role", "user");
```

This is useful when you don't want to compare the entire object.

---

# 23. Why Partial Assertions Are Useful

Suppose your API returns:

```js
{
    id: "123",
    email: "rahul@example.com",
    name: "Rahul",
    createdAt: "...",
    updatedAt: "...",
    ...
}
```

You may only care that:

```text
id exists
email is correct
```

Instead of checking every property:

```js
expect(response).toEqual({
    // huge object
});
```

you can use:

```js
expect(response).toHaveProperty("id");
expect(response.email).toBe("rahul@example.com");
```

This can make tests less fragile.

---

# 24. `objectContaining()`

Jest also provides:

```js
expect.objectContaining()
```

For example:

```js
expect(user).toEqual(
    expect.objectContaining({
        email: "rahul@example.com",
        role: "user"
    })
);
```

This means:

> The object should contain these properties and values, even if it has additional properties.

Very useful for API responses.

---

# 25. `arrayContaining()`

Similarly:

```js
expect.arrayContaining()
```

Example:

```js
const permissions = [
    "user:read",
    "user:update",
    "user:delete"
];

expect(permissions).toEqual(
    expect.arrayContaining([
        "user:read",
        "user:update"
    ])
);
```

This says:

> The array must contain these values.

It doesn't require the array to contain only those values.

---

# 26. Testing Functions

Jest can also check whether a function was called.

We'll learn this more deeply when we reach mocking, but conceptually:

```js
expect(mockFunction).toHaveBeenCalled();
```

And:

```js
expect(mockFunction).toHaveBeenCalledWith("Rahul");
```

This becomes extremely useful when testing:

```text
Controller
   ↓
Service
```

or:

```text
Service
   ↓
Repository
```

We'll revisit this in **21.9 — Mocking Dependencies**.

---

# 27. Testing Errors

Backend applications have many error paths.

For synchronous functions:

```js
expect(() => someFunction())
    .toThrow();
```

You can also check the message:

```js
expect(() => someFunction())
    .toThrow("Unauthorized");
```

This is useful for:

```text
validation errors
business errors
authorization errors
AppError
```

---

# 28. Async Errors

For promises:

```js
await expect(someAsyncFunction())
    .rejects
    .toThrow("Unauthorized");
```

Notice the difference:

```text
Synchronous
    ↓
toThrow()

Promise rejection
    ↓
rejects.toThrow()
```

This distinction is very important in Node.js backends.

---

# 29. Example: Testing a Service Error

Imagine:

```js
async function getUser(userId) {
    const user = await repository.findById(userId);

    if (!user) {
        throw new Error("User not found");
    }

    return user;
}
```

Test:

```js
test("throws when user does not exist", async () => {
    await expect(getUser("invalid-id"))
        .rejects
        .toThrow("User not found");
});
```

This is exactly the kind of test we'll build later.

---

# 30. Testing Multiple Expectations

A single test can contain multiple assertions:

```js
test("returns user information", () => {
    const user = {
        name: "Rahul",
        role: "user"
    };

    expect(user.name).toBe("Rahul");
    expect(user.role).toBe("user");
});
```

That's valid.

But don't put unrelated behaviors into one test.

Bad:

```text
Test user creation
+ login
+ logout
+ pagination
+ authorization
```

That's too much.

Better:

```text
Test user creation
Test login
Test logout
Test pagination
Test authorization
```

Each test should have a clear purpose.

---

# 31. One Behavior Per Test

This doesn't mean:

> "Only one `expect()` is allowed."

That's not the rule.

Instead think:

> **One logical behavior per test.**

This is perfectly reasonable:

```js
test("returns the created user", () => {
    expect(user.name).toBe("Rahul");
    expect(user.role).toBe("user");
    expect(user.email).toBe("rahul@example.com");
});
```

All three assertions describe the same behavior.

---

# 32. Good vs Bad Test Structure

### ❌ Bad

```js
test("user stuff", async () => {
    // create user

    // login

    // update user

    // delete user

    // pagination

    // logout
});
```

If it fails, what actually broke?

Hard to know.

---

### ✅ Better

```js
test("creates a user", () => {
    // ...
});

test("logs in a user", () => {
    // ...
});

test("updates a user", () => {
    // ...
});

test("deletes a user", () => {
    // ...
});
```

Now failures are much easier to understand.

---

# 33. Test Descriptions Should Explain Behavior

Compare:

```js
test("test 1", ...)
```

with:

```js
test("rejects duplicate email addresses", ...)
```

The second is far more valuable.

For backend tests, good descriptions often start with:

```text
returns...
creates...
updates...
deletes...
rejects...
throws...
allows...
denies...
```

For example:

```js
test("denies access when the user does not own the resource", () => {
    // ...
});
```

That's excellent documentation.

---

# 34. Nested `describe()`

You can organize tests hierarchically:

```js
describe("Auth Service", () => {

    describe("login", () => {

        test("logs in with valid credentials", () => {
            // ...
        });

        test("rejects incorrect password", () => {
            // ...
        });

    });

    describe("logout", () => {

        test("invalidates refresh token", () => {
            // ...
        });

    });

});
```

This produces a logical structure:

```text
Auth Service
├── login
│   ├── valid credentials
│   └── incorrect password
│
└── logout
    └── invalidates refresh token
```

This becomes very useful when your backend grows.

---

# 35. A Real Backend Test Structure

Eventually, you might have:

```text
tests/
└── unit/
    └── services/
        └── auth.service.test.js
```

Inside:

```js
describe("AuthService", () => {

    describe("login", () => {

        test("logs in with valid credentials", async () => {
            // Arrange
            // Act
            // Assert
        });

        test("rejects incorrect password", async () => {
            // Arrange
            // Act
            // Assert
        });

        test("rejects inactive user", async () => {
            // Arrange
            // Act
            // Assert
        });

    });

});
```

This is the style I want you to become comfortable with.

---

# 36. Choosing the Right Assertion

Here's a practical cheat sheet:

|Situation|Matcher|
|---|---|
|Exact number/string/boolean|`toBe()`|
|Object/array contents|`toEqual()`|
|Very strict structure|`toStrictEqual()`|
|Array contains value|`toContain()`|
|Array/string length|`toHaveLength()`|
|Property exists|`toHaveProperty()`|
|Truthy value|`toBeTruthy()`|
|Falsy value|`toBeFalsy()`|
|`null`|`toBeNull()`|
|`undefined`|`toBeUndefined()`|
|Value exists|`toBeDefined()`|
|Greater than|`toBeGreaterThan()`|
|Less than|`toBeLessThan()`|
|String pattern|`toMatch()`|
|Function throws|`toThrow()`|
|Promise rejects|`rejects.toThrow()`|

Don't try to memorize everything.

You'll naturally learn the commonly used ones through practice.

# 37. Backend Example: User Repository

Imagine:

```js
const user = await userRepository.findById(userId);
```

Different outcomes require different assertions.

### User found

```js
expect(user).toEqual({
    id: userId,
    email: "rahul@example.com"
});
```

### User missing

```js
expect(user).toBeNull();
```

### User has email

```js
expect(user).toHaveProperty("email");
```

### User has correct role

```js
expect(user).toHaveProperty("role", "user");
```

This is why choosing the right matcher matters.

---

# 38. Backend Example: Pagination

Suppose:

```js
const result = {
    data: [...],
    page: 2,
    limit: 10,
    total: 50
};
```

We could test:

```js
expect(result).toHaveProperty("data");
expect(result.page).toBe(2);
expect(result.limit).toBe(10);
expect(result.total).toBe(50);
expect(result.data).toHaveLength(10);
```

Notice how the assertions describe the API contract.

---

# 39. Backend Example: Authorization

Suppose:

```js
const allowed = canAccess(user, resource);
```

We can write:

```js
expect(allowed).toBe(true);
```

and:

```js
expect(canAccess(otherUser, resource))
    .toBe(false);
```

Later, these simple assertions become part of our security tests.

---

# 40. Don't Over-Assert

There's another common mistake.

Suppose your test only needs:

```text
status = 201
```

But you check:

```text
every header
every response field
every database-generated timestamp
every internal property
```

Now your test becomes fragile.

A good test checks what matters.

Think:

> **What behavior am I actually trying to guarantee?**

Then assert that.

---

# 41. Don't Under-Assert Either

The opposite problem:

```js
test("login works", async () => {
    await login();
});
```

There's no assertion.

The test might pass even if the result is completely wrong.

A useful test should verify something meaningful:

```js
expect(result.accessToken).toBeDefined();
expect(result.user.id).toBe(userId);
```

---

# 42. A Useful Rule

When writing an assertion, ask:

> **If this assertion failed, would I care?**

If yes:

```text
Keep it.
```

If no:

```text
Maybe remove it.
```

This helps prevent both over-testing and meaningless tests.

# 43. Mini Exercise 🧠

Imagine this response:

```js
const response = {
    success: true,
    message: "User created",
    data: {
        id: "123",
        email: "rahul@example.com",
        role: "user"
    }
};
```

Write assertions for:

### A

Check that `success` is `true`.

### B

Check that the message is `"User created"`.

### C

Check that `data` contains an `id`.

### D

Check that the role is `"user"`.

### E

Check that `data` contains the expected email.

A good solution would be:

```js
expect(response.success).toBe(true);

expect(response.message)
    .toBe("User created");

expect(response.data)
    .toHaveProperty("id");

expect(response.data.role)
    .toBe("user");

expect(response.data.email)
    .toBe("rahul@example.com");
```

# 44. Another Exercise

Given:

```js
const users = [
    { id: 1, role: "user" },
    { id: 2, role: "admin" },
    { id: 3, role: "user" }
];
```

Write assertions to check:

```text
1. There are 3 users.
2. There is an admin.
3. There is a user with id 1.
4. The array does not contain id 99.
```

Possible approach:

```js
expect(users).toHaveLength(3);

expect(users).toEqual(
    expect.arrayContaining([
        expect.objectContaining({
            role: "admin"
        })
    ])
);

expect(users).toEqual(
    expect.arrayContaining([
        expect.objectContaining({
            id: 1
        })
    ])
);

expect(users).not.toEqual(
    expect.arrayContaining([
        expect.objectContaining({
            id: 99
        })
    ])
);
```

Notice that the last two use **partial matching** rather than requiring the entire object to match.

# 45. The Big Picture

Your test structure should now look like:

```text
describe()
   │
   ├── describe()
   │      │
   │      ├── test()
   │      │      ├── Arrange
   │      │      ├── Act
   │      │      └── Assert
   │      │
   │      └── test()
   │
   └── describe()
          │
          └── test()
```

And assertions:

```text
expect(actual)
      │
      ├── toBe()
      ├── toEqual()
      ├── toContain()
      ├── toHaveProperty()
      ├── toHaveLength()
      ├── toThrow()
      └── ...
```

---

# 46. What You Should Remember

Don't try to memorize every Jest matcher.

For now, remember these **core ones**:

```text
toBe()
toEqual()
toContain()
toHaveLength()
toHaveProperty()
toBeTruthy()
toBeFalsy()
toBeNull()
toBeUndefined()
toThrow()
```

And remember the test structure:

```text
Arrange
   ↓
Act
   ↓
Assert
```

Most importantly:

> **Choose assertions based on the behavior you want to guarantee, not based on how much code you can assert.**
