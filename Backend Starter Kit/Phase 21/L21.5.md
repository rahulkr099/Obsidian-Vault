# 1. What Is a Utility?

A utility is a small reusable piece of code that performs a specific task.

For example:

```text
utils/
├── AppError.js
├── ApiResponse.js
├── generateToken.js
├── pagination.js
└── password.js
```

The exact files in your starter may differ, but the idea is:

```text
Utility
   ↓
small reusable operation
```

Examples:

```js
generateToken()
hashPassword()
comparePassword()
calculatePagination()
formatResponse()
```

These are excellent candidates for **unit testing**.

Why?

Because they usually have:

```text
Input
  ↓
Utility
  ↓
Output
```

There is often no need to start Express or MongoDB.

---

# 2. Why Test Utilities First?

Utilities are usually:

```text
small
isolated
deterministic
fast
```

So they're perfect for learning unit testing.

For example:

```js
function calculateTotal(price, quantity) {
    return price * quantity;
}
```

We don't need:

```text
Express
MongoDB
HTTP
JWT
```

We simply test:

```text
100 × 3
  ↓
300
```

That's exactly what unit testing is supposed to do.

---

# 3. Our First Real Utility

Let's imagine we have:

```text
utils/pagination.js
```

with:

```js
export function calculateSkip(page, limit) {
    return (page - 1) * limit;
}
```

The purpose is simple.

For:

```text
page = 1
limit = 10
```

we get:

```text
(1 - 1) × 10
= 0
```

For:

```text
page = 2
limit = 10
```

we get:

```text
(2 - 1) × 10
= 10
```

For:

```text
page = 3
limit = 10
```

we get:

```text
20
```

---

# 4. Write the Unit Test

Create:

```text
tests/
└── unit/
    └── utils/
        └── pagination.test.js
```

Then:

```js
import { calculateSkip } from "../../../utils/pagination.js";

describe("calculateSkip", () => {
    test("returns 0 for the first page", () => {
        expect(calculateSkip(1, 10)).toBe(0);
    });

    test("returns 10 for the second page", () => {
        expect(calculateSkip(2, 10)).toBe(10);
    });

    test("returns 20 for the third page", () => {
        expect(calculateSkip(3, 10)).toBe(20);
    });
});
```

Now we're testing our **actual backend utility**, not a random mathematical function.

---

# 5. Arrange → Act → Assert

Let's look at one test:

```js
test("returns 10 for the second page", () => {
    expect(calculateSkip(2, 10)).toBe(10);
});
```

We can mentally divide it into:

### Arrange

```text
page = 2
limit = 10
```

### Act

```text
calculateSkip(2, 10)
```

### Assert

```text
expected = 10
```

For a tiny utility, we don't always need comments.

But the mental model remains:

```text
Arrange
   ↓
Act
   ↓
Assert
```

---

# 6. Test the Boundary Cases

This is where testing becomes more professional.

Don't test only:

```text
page 1
page 2
page 3
```

Think:

> What can go wrong?

For pagination:

```text
page = 0
page = -1
limit = 0
limit = -10
```

Should those values be accepted?

That's a **design decision**.

The test should reflect the expected behavior.

For example, if the utility is supposed to reject invalid values:

```js
test("rejects an invalid page", () => {
    expect(() => calculateSkip(0, 10))
        .toThrow();
});
```

But **don't add this test unless the utility is actually designed to throw**.

This is important:

> Tests should describe the application's intended behavior, not invent behavior.

---

# 7. Utility Testing Is Specification

Consider:

```js
calculateSkip(3, 20)
```

Expected:

```text
40
```

The test:

```js
expect(calculateSkip(3, 20)).toBe(40);
```

does more than check code.

It documents the rule:

```text
skip = (page - 1) × limit
```

So tests become a form of executable documentation.

# 8. Testing a Password Utility

A backend often has password-related utilities.

Conceptually:

```text
utils/password.js
```

might expose:

```js
hashPassword()
comparePassword()
```

Suppose:

```js
async function comparePassword(password, hash) {
    // ...
}
```

We want to test behavior like:

```text
correct password
      ↓
true
```

and:

```text
wrong password
      ↓
false
```

The test isn't interested in the internal implementation.

It asks:

> Does this utility behave correctly?

---

# 9. Example

Conceptually:

```js
test("returns true for the correct password", async () => {
    const password = "StrongPassword123!";
    const hash = await hashPassword(password);

    const result = await comparePassword(
        password,
        hash
    );

    expect(result).toBe(true);
});
```

And:

```js
test("returns false for the wrong password", async () => {
    const password = "StrongPassword123!";
    const wrongPassword = "WrongPassword123!";

    const hash = await hashPassword(password);

    const result = await comparePassword(
        wrongPassword,
        hash
    );

    expect(result).toBe(false);
});
```

Notice something important:

```text
hashPassword()
        ↓
comparePassword()
        ↓
real result
```

We're not mocking anything yet.

That comes later in the roadmap under **21.16 Mocking**.

---

# 10. Testing Token Utilities

Suppose your backend has:

```text
utils/token.js
```

with:

```js
generateAccessToken(user)
verifyAccessToken(token)
```

A useful test could verify:

```text
Generate token
      ↓
Verify token
      ↓
Expected user information
```

For example:

```js
test("generates a token containing the user id", () => {
    const user = {
        id: "user-123"
    };

    const token = generateAccessToken(user);

    const payload = verifyAccessToken(token);

    expect(payload.userId).toBe("user-123");
});
```

The exact payload depends on your implementation.

The principle is what matters:

> Test the contract of the utility.

---

# 11. Don't Test JWT Internals

Suppose your utility internally uses:

```js
jwt.sign(...)
```

You generally don't need a test saying:

```text
"jsonwebtoken.sign() was called"
```

for a basic unit test.

That's implementation detail.

Instead test:

```text
generateAccessToken(user)
        ↓
valid token
        ↓
expected payload
```

You care about what **your utility promises**.

---

# 12. Testing `AppError`

Your starter architecture uses an `AppError` concept, and the overall project architecture includes centralized error handling.

Suppose:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);
        this.statusCode = statusCode;
    }
}
```

We can test:

```js
test("creates an error with the correct message", () => {
    const error = new AppError(
        "User not found",
        404
    );

    expect(error.message).toBe("User not found");
});
```

And:

```js
test("stores the HTTP status code", () => {
    const error = new AppError(
        "User not found",
        404
    );

    expect(error.statusCode).toBe(404);
});
```

Now our tests guarantee the error object contains the information our error middleware expects.

---

# 13. Testing `ApiResponse`

Your backend architecture also includes a consistent API response layer.

Imagine:

```js
class ApiResponse {
    constructor(statusCode, data, message) {
        this.statusCode = statusCode;
        this.data = data;
        this.message = message;
        this.success = statusCode < 400;
    }
}
```

We can test:

```js
test("creates a successful response", () => {
    const response = new ApiResponse(
        200,
        { id: "123" },
        "User fetched"
    );

    expect(response.success).toBe(true);
});
```

And:

```js
test("stores response data", () => {
    const data = { id: "123" };

    const response = new ApiResponse(
        200,
        data,
        "User fetched"
    );

    expect(response.data).toEqual(data);
});
```

Again:

```text
Utility
   ↓
Expected contract
   ↓
Test
```

---

# 14. Testing Date Utilities

Suppose:

```js
function isExpired(expiresAt) {
    return Date.now() > expiresAt;
}
```

A test might be:

```js
test("returns true when the expiration time has passed", () => {
    const past = Date.now() - 1000;

    expect(isExpired(past)).toBe(true);
});
```

And:

```js
test("returns false when expiration is in the future", () => {
    const future = Date.now() + 10000;

    expect(isExpired(future)).toBe(false);
});
```

This teaches an important testing concept:

> **Test both sides of a condition.**

---

# 15. Testing Data Transformation Utilities

Suppose:

```js
function normalizeEmail(email) {
    return email.trim().toLowerCase();
}
```

Tests:

```js
describe("normalizeEmail", () => {
    test("converts email to lowercase", () => {
        expect(
            normalizeEmail("RAHUL@EXAMPLE.COM")
        ).toBe("rahul@example.com");
    });

    test("removes surrounding spaces", () => {
        expect(
            normalizeEmail("  rahul@example.com  ")
        ).toBe("rahul@example.com");
    });
});
```

This is a great utility to unit test because it has no external dependencies.

---

# 16. Think in Input → Output

For utilities, this is your strongest mental model:

```text
┌──────────────┐
│    INPUT     │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│   UTILITY    │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│    OUTPUT    │
└──────────────┘
```

Example:

```text
"  RAHUL@EMAIL.COM  "
          ↓
    normalizeEmail()
          ↓
"rahul@email.com"
```

Test exactly that.

---

# 17. Test What the User of the Utility Sees

Suppose:

```js
function formatUser(user) {
    return {
        id: user._id,
        name: user.name
    };
}
```

Don't care about the internal temporary variables.

Test:

```js
const result = formatUser({
    _id: "123",
    name: "Rahul",
    password: "secret"
});

expect(result).toEqual({
    id: "123",
    name: "Rahul"
});
```

This also catches a potentially serious mistake:

```text
password accidentally returned
```

If your expected object doesn't contain it, a strict enough assertion can help expose that behavior.

---

# 18. Test Security-Sensitive Utilities Carefully

Some utilities are especially important:

```text
password hashing
token generation
token verification
input sanitization
permission calculation
data filtering
```

For these, test:

```text
normal case
invalid input
boundary cases
security-sensitive failure cases
```

For example, a token utility should have tests around:

```text
valid token
invalid token
expired token
wrong secret
malformed token
```

Some of these may fit better into later authentication/security testing. Don't force everything into one utility test file.

---

# 19. Don't Make Tests Dependent on Each Other

Bad:

```js
test("creates user", () => {
    // creates global user
});

test("gets user", () => {
    // assumes previous test created user
});
```

Now:

```text
Test 1 fails
      ↓
Test 2 may fail
```

That's dangerous.

Better:

```text
Test 1
  ↓
creates its own required data

Test 2
  ↓
creates its own required data
```

We'll study proper isolation later in **21.15 Test Isolation**.

---

# 20. Don't Use the Database for Every Utility Test

Suppose you're testing:

```js
calculateSkip()
```

Don't do:

```text
Test
 ↓
Express
 ↓
MongoDB
 ↓
calculateSkip()
```

That's unnecessary.

Just:

```text
Test
 ↓
calculateSkip()
 ↓
result
```

This is the entire purpose of the lower part of the testing pyramid.

# 21. A Useful Utility Test Folder

As your backend grows, you can organize tests like:

```text
tests/
└── unit/
    └── utils/
        ├── pagination.test.js
        ├── password.test.js
        ├── token.test.js
        ├── response.test.js
        └── date.test.js
```

The exact filenames should follow your actual utilities.

Don't create files for utilities that don't exist.

# 22. Test Naming

Compare:

```js
test("works", () => {});
```

with:

```js
test("normalizes uppercase email to lowercase", () => {});
```

The second tells you exactly what behavior is guaranteed.

A good pattern is:

```text
does X when Y
```

Examples:

```text
returns zero for the first page
rejects invalid token
returns false for incorrect password
normalizes uppercase email
creates an error with the provided status code
```

---

# 23. Positive + Negative Testing

For every utility, ask:

### Positive

```text
What should work?
```

### Negative

```text
What should fail?
```

Example:

```text
comparePassword()
```

Positive:

```text
correct password → true
```

Negative:

```text
wrong password → false
```

Example:

```text
verifyToken()
```

Positive:

```text
valid token → payload
```

Negative:

```text
invalid token → error
```

This simple habit will improve your testing significantly.

# 24. Boundary Testing

Now ask:

> What happens at the edge?

For:

```js
calculateSkip(page, limit)
```

consider:

```text
page = 1
page = 2
limit = 1
limit = 100
```

If the function has rules around:

```text
0
negative numbers
maximum limit
```

test those too.

This becomes particularly important for:

```text
pagination
validation
rate limits
token expiration
password rules
```

---

# 25. Don't Over-Test Implementation Details

Suppose:

```js
function normalizeEmail(email) {
    const trimmed = email.trim();
    return trimmed.toLowerCase();
}
```

Don't write a test like:

```text
"trim() must be called"
```

unless that is specifically the behavior you're testing.

Instead:

```js
expect(
    normalizeEmail("  RAHUL@EXAMPLE.COM ")
).toBe("rahul@example.com");
```

This is a **behavior-focused test**.

---

# 26. Refactoring Should Not Break Behavior

This is one of the biggest benefits of unit tests.

Initial implementation:

```js
function normalizeEmail(email) {
    return email.trim().toLowerCase();
}
```

Later you refactor it:

```js
function normalizeEmail(email) {
    return email
        .trim()
        .toLocaleLowerCase("en-US");
}
```

If the behavior remains correct:

```text
Tests
 ↓
PASS
```

You can refactor with much more confidence.

That's one of the major reasons we test utilities early.

---

# 27. A Complete Example

Let's put everything together.

Utility:

```js
export function normalizeEmail(email) {
    return email.trim().toLowerCase();
}
```

Test:

```js
import { normalizeEmail } from "../../../utils/email.js";

describe("normalizeEmail", () => {
    test("converts email to lowercase", () => {
        const result = normalizeEmail(
            "RAHUL@EXAMPLE.COM"
        );

        expect(result).toBe(
            "rahul@example.com"
        );
    });

    test("removes surrounding spaces", () => {
        const result = normalizeEmail(
            "  rahul@example.com  "
        );

        expect(result).toBe(
            "rahul@example.com"
        );
    });
});
```

Structure:

```text
Arrange
  ↓
Input

Act
  ↓
normalizeEmail()

Assert
  ↓
Expected normalized email
```

Very simple.

Very powerful.

# 28. What About Complex Utilities?

Some utilities aren't this simple.

For example:

```text
JWT utilities
Password utilities
Encryption utilities
Pagination builders
Query builders
```

The same principle applies.

Break the behavior into cases:

```text
Input
 ↓
Expected behavior
```

Then test each meaningful case.

Don't try to test 100 internal lines.

---

# 29. Utility Testing Checklist

When testing a utility, ask:

```text
[ ] What does this utility promise?
[ ] What is the normal input?
[ ] What is the expected output?
[ ] What happens with invalid input?
[ ] What are the boundary cases?
[ ] What happens when an operation fails?
[ ] Is the test independent?
[ ] Am I testing behavior rather than implementation?
```

This is a very good checklist to keep.

# 30. Your First Practical Task

Take **3 utilities from your actual backend** and write tests for them.

For each one:

### Step 1

Identify the contract:

```text
Input → Output
```

### Step 2

Write the happy-path test.

### Step 3

Write at least one failure/edge-case test if applicable.

### Step 4

Run:

```bash
npm test
```

### Step 5

Intentionally break the utility.

For example:

```js
return email;
```

instead of:

```js
return email.trim().toLowerCase();
```

Then run:

```bash
npm test
```

You should see:

```text
FAIL ❌
```

Then restore the implementation.

That exercise is important because it proves that your test is actually capable of catching a bug.

---

# 31. The Most Important Lesson

Don't think:

> "I am writing tests because Jest requires tests."

Think:

> **"I'm describing the contract of my backend code so future changes can't silently break it."**

For utilities:

```text
Utility
   ↓
Contract
   ↓
Tests
   ↓
Refactor safely
```

And this is exactly why utilities are a good first practical target.
