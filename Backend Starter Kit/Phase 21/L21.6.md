# Lesson 21.6 — Testing Middleware

In **21.5**, we tested small utilities.

Now we move one layer up:

```text
Utility
   ↓
Middleware
   ↓
Controller
   ↓
Service
```

Your roadmap explicitly places **21.6 — Testing middleware** here, before services, repositories, controllers, and Supertest.

The big question today is:

> **How do we test middleware when Express normally gives us `req`, `res`, and `next()`?**

---

# 1. First: What Are We Testing?

Recall the middleware flow from your backend architecture:

```text
HTTP Request
      │
      ▼
   Middleware
      │
      ▼
    next()
      │
      ▼
 Next middleware / Controller
```

A middleware usually receives:

```js
(req, res, next)
```

For example:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);
    next();
};
```

When testing this middleware directly, we don't necessarily need a real Express server.

We can provide our own:

```text
fake req
fake res
fake next
```

and see what the middleware does.

---

# 2. Why Not Start Express?

You might think:

> "Why don't we just start Express and send a request?"

We absolutely **can** do that later.

That's where **Supertest** becomes useful.

But middleware unit tests are useful because they're:

```text
Fast
↓
Focused
↓
Easy to debug
```

For example:

```text
Middleware unit test

fake req
   ↓
middleware
   ↓
fake next
```

Instead of:

```text
HTTP
 ↓
Express
 ↓
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Database
```

The second approach is useful too, but it tests a much larger part of the system.

---

# 3. The Three Things We Usually Care About

When testing middleware, ask:

### 1. Did it modify the request?

For example:

```js
req.user = user;
```

### 2. Did it call `next()`?

```js
next();
```

### 3. Did it stop the request?

For example:

```js
return res.status(401).json(...);
```

Those three questions cover a huge amount of middleware behavior.

---

# 4. Our First Middleware

Let's create:

```text
middlewares/
└── logger.middleware.js
```

Example:

```js
export const logger = (req, res, next) => {
    console.log(req.method, req.url);
    next();
};
```

What should we test?

Not the fact that `console.log()` exists.

We care about:

```text
logger middleware
       ↓
calls next()
```

---

# 5. First Middleware Test

Create:

```text
tests/
└── unit/
    └── middlewares/
        └── logger.middleware.test.js
```

Then:

```js
import { logger } from "../../../middlewares/logger.middleware.js";

describe("logger middleware", () => {
    test("calls next", () => {
        const req = {
            method: "GET",
            url: "/users"
        };

        const res = {};

        const next = jest.fn();

        logger(req, res, next);

        expect(next).toHaveBeenCalled();
    });
});
```

There is a new thing here:

```js
jest.fn()
```

Don't worry—we'll study mocking deeply in **21.16**.

For now, understand it as:

> **Create a fake function that Jest can watch.**

---

# 6. What Is `jest.fn()`?

Normally:

```js
const next = () => {
    // continue
};
```

But we don't actually need `next()` to do anything.

We only need to know:

```text
Was next() called?
```

So:

```js
const next = jest.fn();
```

creates a function that Jest can track.

Then:

```js
logger(req, res, next);
```

calls it.

Finally:

```js
expect(next).toHaveBeenCalled();
```

checks:

```text
Was next() called?
        ↓
YES ✅
```

This pattern is fundamental for middleware testing.

---

# 7. Testing `next()` Exactly Once

Calling `next()` is not enough.

We often want:

```text
exactly once
```

Use:

```js
expect(next).toHaveBeenCalledTimes(1);
```

So:

```js
test("calls next exactly once", () => {
    const req = {
        method: "GET",
        url: "/users"
    };

    const res = {};
    const next = jest.fn();

    logger(req, res, next);

    expect(next).toHaveBeenCalledTimes(1);
});
```

Why does this matter?

Because accidentally doing:

```js
next();
next();
```

could cause serious problems in an Express application.

---

# 8. Middleware Can Modify `req`

Consider authentication middleware.

Conceptually:

```js
const authMiddleware = async (req, res, next) => {
    const user = await verifyToken(req);

    req.user = user;

    next();
};
```

The important behavior is:

```text
token
 ↓
user
 ↓
req.user
 ↓
next()
```

So we should test:

```text
req.user exists
```

and:

```text
next() called
```

# 9. Example: User Middleware

Suppose we have a simplified middleware:

```js
export const attachUser = (req, res, next) => {
    req.user = {
        id: "user-123",
        role: "user"
    };

    next();
};
```

Test:

```js
test("attaches the user to the request", () => {
    const req = {};
    const res = {};
    const next = jest.fn();

    attachUser(req, res, next);

    expect(req.user).toEqual({
        id: "user-123",
        role: "user"
    });
});
```

And:

```js
test("calls next after attaching the user", () => {
    const req = {};
    const res = {};
    const next = jest.fn();

    attachUser(req, res, next);

    expect(next).toHaveBeenCalledTimes(1);
});
```

# 10. Middleware That Stops the Request

Now things get more interesting.

Authentication middleware might receive an invalid token.

Instead of:

```text
next()
```

it might do:

```js
return res.status(401).json({
    success: false,
    message: "Unauthorized"
});
```

So the flow becomes:

```text
Request
   ↓
Auth middleware
   ↓
Invalid token
   ↓
401 Response
   ↓
STOP
```

Notice:

```text
next()
```

should **not** be called.

That's something we should test.

---

# 11. Fake `res`

Express's real `res` object has hundreds of methods and properties.

We don't need all of them.

If our middleware uses:

```js
res.status(401).json(...)
```

we only need to provide those methods.

For example:

```js
const res = {
    status: jest.fn().mockReturnThis(),
    json: jest.fn()
};
```

Now:

```js
res.status(401)
```

returns `res`.

Then:

```js
.json(...)
```

can be called.

---

# 12. Why `mockReturnThis()`?

This is because Express methods are often chainable.

For example:

```js
res
    .status(401)
    .json({
        message: "Unauthorized"
    });
```

The first call:

```js
res.status(401)
```

needs to return:

```text
res
```

so `.json()` can continue.

Therefore:

```js
status: jest.fn().mockReturnThis()
```

means:

```text
status()
   ↓
return the same res object
```

This is a very common pattern in Express tests.

---

# 13. Testing a 401 Response

Imagine:

```js
const authMiddleware = (req, res, next) => {
    if (!req.token) {
        return res.status(401).json({
            success: false,
            message: "Unauthorized"
        });
    }

    next();
};
```

Test:

```js
test("returns 401 when token is missing", () => {
    const req = {};

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    authMiddleware(req, res, next);

    expect(res.status).toHaveBeenCalledWith(401);

    expect(res.json).toHaveBeenCalledWith({
        success: false,
        message: "Unauthorized"
    });

    expect(next).not.toHaveBeenCalled();
});
```

This test verifies the entire middleware decision.

---

# 14. Read the Test Like a Story

The test says:

```text
Given:
    no token

When:
    authMiddleware runs

Then:
    status should be 401
    response should contain Unauthorized
    next should NOT be called
```

That's exactly what a good unit test should communicate.

---

# 15. Testing the Successful Path

We also need the other side.

```js
test("calls next when token exists", () => {
    const req = {
        token: "valid-token"
    };

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    authMiddleware(req, res, next);

    expect(next).toHaveBeenCalledTimes(1);
    expect(res.status).not.toHaveBeenCalled();
});
```

Now we have:

```text
Missing token
    ↓
401

Valid token
    ↓
next()
```

That's a much stronger test suite.

---

# 16. The Two Main Branches

Most middleware contains decisions.

For example:

```js
if (condition) {
    return res.status(...);
}

next();
```

Your tests should usually cover both branches:

```text
             Middleware
                 │
           ┌─────┴─────┐
           ▼           ▼
       condition      else
           │           │
           ▼           ▼
        response      next()
```

This is one reason middleware testing is closely connected to coverage, which we'll study later.

# 18. Validation Middleware

Your architecture also contains validation middleware.

Conceptually:

```text
req.body
   ↓
Joi schema
   ↓
Valid?
 ┌─┴──────┐
YES      NO
 │        │
 ▼        ▼
next()   400
```

So we can test:

### Valid input

```text
valid body
   ↓
next()
```

### Invalid input

```text
invalid body
   ↓
400 response
```

---

# 19. Example Validation Middleware

Imagine:

```js
const validateBody = (schema) => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req.body);

        if (error) {
            return res.status(400).json({
                success: false,
                message: "Validation failed"
            });
        }

        req.body = value;

        next();
    };
};
```

This is a **middleware factory**.

It returns middleware.

That means our test needs to do:

```js
const middleware = validateBody(schema);
```

Then:

```js
middleware(req, res, next);
```

---

# 20. Testing Valid Input

Conceptually:

```js
test("calls next for valid input", () => {
    const req = {
        body: {
            email: "rahul@example.com"
        }
    };

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    const middleware = validateBody(schema);

    middleware(req, res, next);

    expect(next).toHaveBeenCalledTimes(1);
});
```

We can also check that the validated value was assigned:

```js
expect(req.body).toEqual({
    email: "rahul@example.com"
});
```

```js
test("returns 400 for invalid input", () => {
    const req = {
```

# 22. Request ID Middleware

Your starter architecture includes request IDs as part of observability. The earlier architecture roadmap specifically calls out `requestId` middleware.

Imagine:

```js
const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();
    next();
};
```

What should we test?

```text
req.requestId exists
next() called
```

Potentially:

```js
expect(req.requestId).toBeDefined();
expect(typeof req.requestId).toBe("string");
expect(next).toHaveBeenCalledTimes(1);
```

We don't necessarily care about the exact UUID because it's generated dynamically.

---

# 23. Don't Assert Random Values Exactly

This is a common mistake.

Bad:

```js
expect(req.requestId)
    .toBe("12345678-...");
```

Why?

Because the middleware generates a new ID every time.

Instead:

```js
expect(req.requestId).toBeDefined();
```

or:

```js
expect(req.requestId).toEqual(expect.any(String));
```

This tests the contract without depending on a random value.

# 24. Testing Middleware That Uses `req.user`

Suppose authorization middleware does:

```js
const requireAdmin = (req, res, next) => {
    if (req.user.role !== "admin") {
        return res.status(403).json({
            message: "Forbidden"
        });
    }

    next();
};
```

Test normal user:

```text
req.user.role = "user"
        ↓
403
        ↓
next NOT called
```

Test admin:

```text
req.user.role = "admin"
        ↓
next()
```

This is a perfect example of testing middleware in isolation.

---

# 25. Authorization Middleware Test

```js
describe("requireAdmin", () => {
    test("denies normal users", () => {
        const req = {
            user: {
                role: "user"
            }
        };

        const res = {
            status: jest.fn().mockReturnThis(),
            json: jest.fn()
        };

        const next = jest.fn();

        requireAdmin(req, res, next);

        expect(res.status).toHaveBeenCalledWith(403);
        expect(next).not.toHaveBeenCalled();
    });

    test("allows admins", () => {
        const req = {
            user: {
                role: "admin"
            }
        };

        const res = {
            status: jest.fn().mockReturnThis(),
            json: jest.fn()
        };

        const next = jest.fn();

        requireAdmin(req, res, next);

        expect(next).toHaveBeenCalledTimes(1);
    });
});
```

This is already giving us the foundation for the dedicated authorization testing lesson later.

# 26. Middleware Can Have Side Effects

Sometimes middleware changes:

```text
req
res
```

or external state.

For example:

```js
req.user = user;
```

or:

```js
res.locals.requestId = requestId;
```

Test those side effects.

Example:

```js
expect(req.user).toEqual(user);
```

or:

```js
expect(res.locals.requestId).toBeDefined();
```

The question is:

> What state should exist after this middleware finishes?

---

# 27. Don't Test Express Itself

Suppose your middleware does:

```js
res.status(401).json(...)
```

You don't need to test:

> "Does Express's `status()` method actually set the HTTP status?"

Express already provides that.

You're testing:

> **Does my middleware call `res.status(401)` when authentication fails?**

This distinction is very important.

---

# 28. Test Your Code, Not the Framework

Bad testing target:

```text
Does Express call middleware?
```

That's Express's responsibility.

Good testing target:

```text
Does my middleware reject missing authentication?
```

That's your responsibility.

Similarly:

```text
Don't test Joi's internal validation algorithm.
```

Test:

```text
Does my validation middleware reject invalid input?
```

---

# 29. Middleware Test Pattern

You can use this template again and again:

```js
test("describes middleware behavior", () => {
    // Arrange
    const req = {};
    
    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    // Act
    middleware(req, res, next);

    // Assert
    expect(...);
});
```

Then modify the request and expectations according to the middleware.

---

# 30. A Useful Mental Model

Think of middleware as a function:

```text
               req
                │
                ▼
        ┌──────────────┐
        │  Middleware  │
        └──────┬───────┘
               │
       ┌───────┴────────┐
       │                │
       ▼                ▼
   next()           response
       │                │
       ▼                ▼
 continue             stop
```

Our test needs to determine:

```text
Which branch did middleware take?
```

|---|---|

# 32. What About Async Middleware?

Some middleware is asynchronous:

```js
const auth = async (req, res, next) => {
    const user = await verifyToken(...);

    req.user = user;

    next();
};
```

Then the test should usually be:

```js
test("attaches user for a valid token", async () => {
    // Arrange

    // Act
    await auth(req, res, next);

    // Assert
});
```

The key difference is:

```text
sync middleware
    ↓
middleware(...)

async middleware
    ↓
await middleware(...)
```

If the middleware returns a promise, Jest needs to wait for it.

---

# 33. Async Middleware Errors

Suppose:

```js
const auth = async (req, res, next) => {
    const user = await verifyToken(req.token);

    req.user = user;

    next();
};
```

If:

```text
verifyToken()
   ↓
throws
```

then your test needs to verify the error-handling behavior your architecture expects.

Depending on your implementation, that could be:

```text
rejects
```

or:

```text
next(error)
```

or an error handler wrapper.

Don't assume one pattern blindly.

Your actual middleware architecture determines what the test should verify.

---

# 34. Testing `next(error)`

Express error middleware uses:

```js
next(error);
```

Suppose:

```js
const middleware = (req, res, next) => {
    try {
        // ...
    } catch (error) {
        next(error);
    }
};
```

You can test:

```js
const next = jest.fn();

middleware(req, res, next);

expect(next).toHaveBeenCalledWith(error);
```

This is different from:

```js
expect(next).toHaveBeenCalled();
```

Here we're verifying **what was passed to `next()`**.

---

# 35. `toHaveBeenCalledWith()`

This matcher is extremely useful for middleware.

Example:

```js
expect(next).toHaveBeenCalledWith();
```

means:

```text
next() was called without arguments
```

While:

```js
expect(next).toHaveBeenCalledWith(error);
```

means:

```text
next(error) was called
```

This distinction matters because:

```text
next()
```

means:

> Continue normally.

While:

```text
next(error)
```

means:

> Send this error into Express's error-handling pipeline.

---

# 36. Testing Error Middleware

Your architecture eventually contains:

```text
middlewares/error.middleware.js
```

Error middleware has a special Express signature:

```js
(error, req, res, next)
```

You can unit test it without starting Express.

For example:

```js
const error = new Error("Something failed");

const req = {};
const res = {
```

Then check:

This distinction is extremely important.

### Unit test

```text

     ↓

```

Tests:

```text
middleware behavior
```

```text

     ↓

```

Tests:

```text
real request flow
```

# 40. Example: Authentication

### Unit test

You might test:

```text
valid token
 ↓
middleware
 ↓
req.user
 ↓
next()
```

### API test

Later:

```http
GET /api/v1/users/me
```

# 41. Common Mistake #1 — Forgetting `next()`

Middleware:

```js
const logger = (req, res, next) => {
    console.log(req.method);
};
```

Problem:

```text
Request
 ↓
logger
 ↓
STOP ❌
```

A unit test catches this:

```js
expect(next).toHaveBeenCalled();
```

---

# 42. Common Mistake #2 — Calling `next()` After Sending Response

Bad:

```js
if (!req.user) {
    res.status(401).json({
        message: "Unauthorized"
    });

    next();
}
```

Now you've potentially both:

```text
sent response
+
continued request
```

Better:

```js
if (!req.user) {
    return res.status(401).json({
        message: "Unauthorized"
    });
}
```

Test:

```js
expect(next).not.toHaveBeenCalled();
```

This is a very useful middleware test.

---

# 43. Common Mistake #3 — Testing Only Success

Bad test suite:

```text
valid token → next()
```

But no:

```text
missing token
invalid token
expired token
```

A middleware is often most valuable when it rejects bad requests.

So test the failure paths too.

---

# 44. Common Mistake #4 — Giant Middleware Tests

Don't write:

```text
auth + validation + rate limit + role
```

inside one unit test.

Keep them focused:

```text
auth.middleware.test.js
role.middleware.test.js
validation.middleware.test.js
rateLimiter.middleware.test.js
```

Then use API tests to verify they work together.

---

# 45. Common Mistake #5 — Over-Mocking

Suppose your middleware calls:

```js
verifyToken()
```

You might mock it.

That's fine when you're testing middleware behavior.

But if you mock everything:

```text
verifyToken → mock
repository → mock
user lookup → mock
Express → fake
everything → fake
```

you might end up testing almost nothing real.

We'll learn how to choose the correct mocking boundary in **21.16**.

For now:

> **Mock only what you need to isolate the middleware.**

# 46. Practical Middleware Test Template

Keep this template:

```js
describe("middlewareName", () => {
    test("allows valid input", async () => {
        // Arrange
        const req = {};
        const res = {
            status: jest.fn().mockReturnThis(),
            json: jest.fn()
        };
        const next = jest.fn();

        // Act
        await middleware(req, res, next);

        // Assert
        expect(next).toHaveBeenCalledTimes(1);
    });

    test("rejects invalid input", async () => {
        // Arrange
        const req = {};
        const res = {
            status: jest.fn().mockReturnThis(),
            json: jest.fn()
        };
        const next = jest.fn();

        // Act
        await middleware(req, res, next);

        // Assert
        expect(res.status).toHaveBeenCalledWith(400);
        expect(next).not.toHaveBeenCalled();
    });
});
```

Adapt it to the actual middleware.

---

# 47. A Better Way to Think About Middleware Tests

Don't start by asking:

> "What lines of code should I cover?"

Start with:

> **"What decisions can this middleware make?"**

For example:

```text
Auth middleware
       │
       ├── token missing → 401
       │
       ├── token invalid → 401
       │
       └── token valid → next()
```

Then write tests for those behaviors.

This is much more effective than blindly chasing line coverage.

# 48. Mini Exercise 🧠

Suppose you have:

```js
const requireUser = (req, res, next) => {

        return res.status(401).json({
            success: false,
            message: "Authentication required"
        });
    }

    next();
};
```

Write **two tests**.

### Test 1

```text
req.user exists
    ↓
next()
```

### Test 2

```text
req.user doesn't exist
    ↓
401
    ↓
next() NOT called
```

Try writing them yourself first.

# 49. Solution

### Valid user

```js
test("calls next when user is authenticated", () => {
    const req = {
        user: {
            id: "user-123"
        }
    };

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    requireUser(req, res, next);

    expect(next).toHaveBeenCalledTimes(1);
});
```

### Missing user

```js
test("returns 401 when user is not authenticated", () => {
    const req = {};

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    requireUser(req, res, next);

    expect(res.status).toHaveBeenCalledWith(401);

    expect(res.json).toHaveBeenCalledWith({
        success: false,
        message: "Authentication required"
    });

    expect(next).not.toHaveBeenCalled();
});
```

# 52. What You Should Remember From 21.6

The most important points:

### Middleware receives:

```js
(req, res, next)
```

### For unit tests, create:

```text
fake req
fake res
fake next
```

### Test whether middleware:

```text
modifies req/res
calls next()
calls next(error)
returns an HTTP error
stops the request
```

### For `next()`:

```js
const next = jest.fn();
```

Then:

```js
expect(next).toHaveBeenCalled();
```

or:

```js
expect(next).not.toHaveBeenCalled();
```

or:

```js
expect(next).toHaveBeenCalledWith(error);
```

### For Express response methods:

```js
const res = {
    status: jest.fn().mockReturnThis(),
    json: jest.fn()
};
```

# 53. One Final Mental Model

When you see middleware like:

```js
const middleware = (req, res, next) => {
    if (somethingIsWrong) {
        return res.status(400).json({
            message: "Bad request"
        });
    }

    req.someValue = value;

    next();
};
```

Immediately think:

```text
                middleware
                    │
          ┌─────────┴─────────┐
          │                   │
    something wrong       everything OK
          │                   │
          ▼                   ▼
       response            modify req
          │                   │
          ▼                   ▼
        STOP                next()
```

And your tests should cover **both branches**.

That is the core skill of middleware testing.
