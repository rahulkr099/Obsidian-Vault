# Lesson 21.7 — Testing Services

This is one of the **most important testing lessons** in Phase 21.

Your roadmap places **service testing** immediately after middleware testing:

```text
21.5 Testing utilities
        ↓
21.6 Testing middleware
        ↓
21.7 Testing services
        ↓
21.8 Testing repositories
        ↓
21.9 Testing controllers
```

The reason is architectural: the **service layer contains business logic**, while repositories handle data access. Your starter roadmap explicitly describes services as the place for business rules and repository calls.

---

# 1. What Is a Service?

A service is where your application decides:

> **What should happen?**

For example, imagine login.

A controller should not do this:

```js
async function login(req, res) {
    const user = await User.findOne({
        email: req.body.email
    });

    const valid = await bcrypt.compare(
        req.body.password,
        user.password
    );

    const token = jwt.sign(...);

    // ...
}
```

Instead:

```text
Controller
    ↓
authService.login()
    ↓
repository
    ↓
database
```

Your roadmap describes this separation explicitly: the controller translates HTTP, while the service contains the business logic.

---

# 2. Why Services Are Excellent Testing Targets

A service usually looks like:

```text
Input
  ↓
Business rules
  ↓
Dependencies
  ↓
Result
```

For example:

```text
email + password
       ↓
find user
       ↓
check password
       ↓
generate tokens
       ↓
return authentication result
```

We can test all those **business decisions** without starting Express.

That's powerful.

---

# 3. What Should a Service Test?

For a service, focus on:

```text
✓ business rules
✓ returned values
✓ thrown errors
✓ dependency calls
✓ different branches
✓ edge cases
```

Don't focus on:

```text
✗ HTTP status codes
✗ Express req/res
✗ MongoDB internals
✗ Express routing
```

Those belong to other layers.

---

# 4. The Layer Boundary

Think about the responsibilities:

```text
┌────────────────────┐
│     Controller     │
│                    │
│ HTTP               │
│ req / res          │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│      Service       │
│                    │
│ Business logic     │
│ Decisions          │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│    Repository      │
│                    │
│ Database access    │
└────────────────────┘
```

Therefore:

### Controller test

Ask:

> Did the controller translate HTTP correctly?

### Service test

Ask:

> Did the business rule work correctly?

### Repository test

Ask:

> Did the database operation work correctly?

That's the separation we're building throughout Phase 21.

# 5. First Simple Service

Let's start with something easy.

Imagine:

```js
export function calculateDiscount(price, discount) {
    return price - (price * discount) / 100;
}
```

This could technically be a utility, but it demonstrates the idea.

Test:

```js
describe("calculateDiscount", () => {
    test("calculates a 10 percent discount", () => {
        const result = calculateDiscount(1000, 10);

        expect(result).toBe(900);
    });
});
```

But real services are usually more interesting because they depend on other components.

---

# 6. A Realistic User Service

Imagine:

```js
export const createUser = async (data) => {
    const existingUser =
        await userRepository.findByEmail(data.email);

    if (existingUser) {
        throw new Error("User already exists");
    }

    const hashedPassword =
        await passwordService.hash(data.password);

    return userRepository.create({
        ...data,
        password: hashedPassword
    });
};
```

Notice the dependencies:

```text
createUser()
    │
    ├── userRepository
    │
    └── passwordService
```

We don't want our unit test to actually hit MongoDB.

Instead, we control those dependencies.

---

# 7. Why Mock Dependencies?

Suppose your service does:

```text
Service
   ↓
Repository
   ↓
MongoDB
```

If we're testing the **service**, we don't want MongoDB involved.

Otherwise:

```text
service test
   ↓
repository
   ↓
MongoDB
   ↓
network / database
```

Now the test becomes:

- slower
    
- harder to set up
    
- harder to debug
    
- dependent on external state
    

Instead:

```text
service test
   ↓
fake repository
```

This lets us test the service's business logic independently.

---

# 8. A Mock Repository

Imagine:

```js
const userRepository = {
    findByEmail: jest.fn(),
    create: jest.fn()
};
```

Now the service can use this object instead of the real repository.

For example:

```js
userRepository.findByEmail.mockResolvedValue(null);
```

means:

> When the service asks for the user, pretend no user exists.

Then:

```js
userRepository.create.mockResolvedValue({
    id: "user-123",
    email: "rahul@example.com"
});
```

means:

> Pretend the repository successfully created the user.

---

# 9. First Service Test

Suppose:

```js
const createUser = async (data) => {
    const existingUser =
        await userRepository.findByEmail(data.email);

    if (existingUser) {
        throw new Error("User already exists");
    }

    const hashedPassword =
        await passwordService.hash(data.password);

    return userRepository.create({
        ...data,
        password: hashedPassword
    });
};
```

Test the happy path:

```js
test("creates a user when email is available", async () => {
    userRepository.findByEmail
        .mockResolvedValue(null);

    passwordService.hash
        .mockResolvedValue("hashed-password");

    userRepository.create
        .mockResolvedValue({
            id: "user-123",
            email: "rahul@example.com"
        });

    const result = await createUser({
        email: "rahul@example.com",
        password: "password123"
    });

    expect(result).toEqual({
        id: "user-123",
        email: "rahul@example.com"
    });
});
```

This test never touches MongoDB.

---

# 10. What Did We Actually Test?

Let's break it down.

### Arrange

```text
No existing user
Hash password successfully
Create user successfully
```

### Act

```text
createUser(...)
```

### Assert

```text
Expected user returned
```

So:

```text
Arrange
   ↓
Act
   ↓
Assert
```

Same pattern as before.

---

# 11. Testing the Business Rule

Now the important case:

```text
User already exists
```

Our service says:

```js
if (existingUser) {
    throw new Error("User already exists");
}
```

Test:

```js
test("rejects duplicate email", async () => {
    userRepository.findByEmail
        .mockResolvedValue({
            id: "existing-user",
            email: "rahul@example.com"
        });

    await expect(
        createUser({
            email: "rahul@example.com",
            password: "password123"
        })
    ).rejects.toThrow("User already exists");
});
```

This is a **business rule test**.

---

# 12. Why This Test Is Valuable

Imagine someone later changes:

```js
if (existingUser) {
    throw new Error("User already exists");
}
```

to:

```js
if (existingUser) {
    return existingUser;
}
```

The application might now accidentally allow duplicate signup behavior.

Our test catches it:

```text
Test
 ↓
FAIL ❌
```

That's exactly what we want.

---

# 13. Verify Dependencies Were Called Correctly

We can also test:

```js
expect(userRepository.findByEmail)
    .toHaveBeenCalledWith("rahul@example.com");
```

This verifies:

> Did the service ask the repository for the correct user?

And:

```js
expect(passwordService.hash)
    .toHaveBeenCalledWith("password123");
```

This verifies:

> Did the service hash the correct password?

And:

```js
expect(userRepository.create)
    .toHaveBeenCalledWith({
        email: "rahul@example.com",
        password: "hashed-password"
    });
```

This verifies:

> Did the service send the correct data to the repository?

---

# 14. But Be Careful

Don't turn every service test into:

```text
Was function A called?
Was function B called?
Was function C called?
Was function D called?
```

You can end up testing the implementation instead of the business behavior.

Prefer:

```text
Business result
+
Important dependency interactions
```

rather than testing every tiny internal detail.

---

# 15. A Service Is a Decision Maker

This is the mental model I want you to remember:

```text
Repository
   ↓
provides data

Service
   ↓
makes decisions

Controller
   ↓
communicates HTTP
```

For example:

```text
Repository:
"Here is a user."

Service:
"This user already exists,
so signup must be rejected."

Controller:
"Return the appropriate HTTP response."
```

Therefore service tests should heavily focus on **decisions**.

# 17. Testing Login — Happy Path

Imagine:

```js
async function login(email, password) {
    const user =
        await userRepository.findByEmail(email);

    if (!user) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const valid =
        await passwordService.compare(
            password,
            user.password
        );

    if (!valid) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const accessToken =
        generateAccessToken(user);

    return {
        user,
        accessToken
    };
}
```

The happy path is:

```text
email
 ↓
find user
 ↓
user exists
 ↓
password correct
 ↓
generate token
 ↓
return result
```

# 18. Login Test

```js
test("logs in a user with valid credentials", async () => {
    const user = {
        id: "user-123",
        email: "rahul@example.com",
        password: "hashed-password"
    };

    userRepository.findByEmail
        .mockResolvedValue(user);

    passwordService.compare
        .mockResolvedValue(true);

    tokenService.generateAccessToken
        .mockReturnValue("access-token");

    const result = await login(
        "rahul@example.com",
        "password123"
    );

    expect(result).toEqual({
        user,
        accessToken: "access-token"
    });
});
```

Again:

```text
No Express
No HTTP
No MongoDB
```

Just business logic.

# 19. Invalid Password

This is a critical branch.

```text
User exists
     ↓
Password incorrect
     ↓
Reject login
```

Test:

```js
test("rejects invalid password", async () => {
    userRepository.findByEmail
        .mockResolvedValue({
            id: "user-123",
            email: "rahul@example.com",
            password: "hashed-password"
        });

    passwordService.compare
        .mockResolvedValue(false);

    await expect(
        login(
            "rahul@example.com",
            "wrong-password"
        )
    ).rejects.toThrow("Invalid credentials");

    expect(
        tokenService.generateAccessToken
    ).not.toHaveBeenCalled();
});
```

That last assertion is useful.

We don't just want:

```text
error happened
```

We want to guarantee:

```text
invalid password
      ↓
NO TOKEN
```

---

# 20. User Not Found

Another branch:

```text
User doesn't exist
      ↓
Invalid credentials
```

Test:

```js
test("rejects login when user does not exist", async () => {
    userRepository.findByEmail
        .mockResolvedValue(null);

    await expect(
        login(
            "unknown@example.com",
            "password123"
        )
    ).rejects.toThrow("Invalid credentials");

    expect(
        passwordService.compare
    ).not.toHaveBeenCalled();
});
```

This verifies an important optimization and security behavior:

```text
No user
 ↓
don't compare password
 ↓
don't generate token
```

---

# 21. Avoid User Enumeration

Notice something interesting.

Both:

```text
unknown email
```

and:

```text
wrong password
```

return:

```text
Invalid credentials
```

instead of:

```text
User doesn't exist
```

This helps avoid revealing whether an account exists.

That is a security-sensitive business behavior.

And because the service owns login logic, the service test is a good place to protect this behavior.

# 22. Testing Password Hashing

Suppose signup does:

```text
plain password
       ↓
hash
       ↓
repository
```

A test should ensure the repository does **not** receive the plain password.

For example:

```js
passwordService.hash
    .mockResolvedValue("hashed-password");

userRepository.create
    .mockResolvedValue(user);

await createUser({
    email: "rahul@example.com",
    password: "plain-password"
});

expect(userRepository.create)
    .toHaveBeenCalledWith({
        email: "rahul@example.com",
        password: "hashed-password"
    });
```

This is an excellent test because accidentally storing plaintext passwords would be a serious security bug.

# 23. Service Error Handling

Your service may throw application errors:

```js
throw new AppError(
    "User not found",
    404
);
```

Test both:

```js
expect(error.message)
    .toBe("User not found");

expect(error.statusCode)
    .toBe(404);
```

For example:

```js
test("throws 404 when user does not exist", async () => {
    userRepository.findById
        .mockResolvedValue(null);

    await expect(
        getUser("user-123")
    ).rejects.toMatchObject({
        message: "User not found",
        statusCode: 404
    });
});
```

This checks the service's contract.

---

# 24. Service vs Controller Error Testing

This distinction is important.

Service:

```js
throw new AppError(
    "User not found",
    404
);
```

Test:

```text
Does service throw the correct application error?
```

Controller:

```text
AppError
 ↓
HTTP 404
```

Test:

```text
Does controller turn the service error into the correct HTTP response?
```

Different layers.

Different tests.

# 25. Testing Ownership Rules

This is another major service responsibility.

Suppose:

```text
User A
   ↓
Todo A
```

and:

```text
User B
   ↓
Todo B
```

A service might contain:

```js
async function updateTodo(userId, todoId, data) {
    const todo =
        await todoRepository.findByIdAndUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todoRepository.update(
        todoId,
        data
    );
}
```

The important business rule is:

> A user can only modify their own todo.

Your test should protect that.

---

# 26. Ownership Test

```js
test("prevents updating another user's todo", async () => {
    todoRepository.findByIdAndUser
        .mockResolvedValue(null);

    await expect(
        updateTodo(
            "user-A",
            "todo-B",
            {
                title: "Hacked"
            }
        )
    ).rejects.toMatchObject({
        statusCode: 404
    });

    expect(todoRepository.update)
        .not.toHaveBeenCalled();
});
```

This is a **very valuable security test**.

It verifies:

```text
Wrong owner
   ↓
No update
```

---

# 27. Why `404` Can Be Useful Here

Instead of saying:

```text
"Todo exists, but you don't own it."
```

you may choose:

```text
"Todo not found."
```

That avoids exposing whether another user's resource exists.

Your exact API design may differ, but whatever rule you choose should be tested.

# 28. Service Dependencies

A service might depend on:

```text
Repository
Password service
Token service
Email service
Payment service
Notification service
```

For example:

```text
authService
    │
    ├── userRepository
    ├── passwordService
    ├── tokenService
    └── emailService
```

For a unit test, we can replace those with controlled test doubles.

This is where **dependency injection** becomes very useful.

---

# 29. Dependency Injection

Instead of:

```js
import userRepository from "../repositories/user.repository.js";

export async function createUser(data) {
    return userRepository.create(data);
}
```

we can design:

```js
export function createUserService({
    userRepository,
    passwordService
}) {
    return {
        async createUser(data) {
            // ...
        }
    };
}
```

Then production:

```js
const userService = createUserService({
    userRepository,
    passwordService
});
```

Test:

```js
const userService = createUserService({
    userRepository: fakeRepository,
    passwordService: fakePasswordService
});
```

This makes testing much easier.

---

# 30. Do You Always Need Dependency Injection?

No.

Don't add a huge dependency-injection framework just because you're learning testing.

Simple JavaScript patterns are often enough:

```text
factory functions
parameters
module boundaries
Jest mocks
```

The goal is:

> **Make dependencies replaceable where isolation is useful.**

Not:

> "Use a dependency injection framework everywhere."

---

# 31. Service Test Structure

A good service test file often looks like:

```js
describe("createUser", () => {
    beforeEach(() => {
        jest.clearAllMocks();
    });

    test("creates a user", async () => {
        // ...
    });

    test("rejects duplicate email", async () => {
        // ...
    });

    test("hashes the password", async () => {
        // ...
    });

    test("does not create user when hashing fails", async () => {
        // ...
    });
});
```

The `beforeEach()` keeps mock call history from leaking between tests.

We'll study isolation more deeply in **21.15**.

# 32. Testing Failure of a Dependency

Imagine:

```text
Service
   ↓
Repository
   ↓
Database error
```

What should the service do?

Maybe:

```js
await repository.create(...)
```

throws.

If the service is supposed to propagate the error:

```js
await expect(
    createUser(data)
).rejects.toThrow();
```

If it is supposed to translate the error:

```text
Mongo duplicate error
       ↓
AppError("User already exists")
```

then test that translation.

The test must follow the **actual service contract**.

# 33. Don't Automatically Catch Everything

Bad service design:

```js
try {
    // everything
} catch (error) {
    throw new AppError(
        "Something went wrong",
        500
    );
}
```

Now useful errors may disappear.

For example:

```text
User not found
```

could become:

```text
Something went wrong
```

Tests can expose this problem.

Good tests force you to think:

> Which errors should this service preserve, and which should it translate?

# 34. Service Testing Is Mostly Branch Testing

Imagine:

```js
if (!user) {
    throw ...
}

if (!validPassword) {
    throw ...
}

if (user.disabled) {
    throw ...
}

return success;
```

You need tests for:

```text
user missing
password invalid
user disabled
success
```

Think of it as a decision tree:

```text
                 login()
                    │
             user exists?
              ┌────┴────┐
             NO         YES
             │           │
           error    password valid?
                       ┌─┴──┐
                      NO    YES
                      │      │
                    error   success
```

Every meaningful branch deserves consideration.

# 35. Testing Services Without HTTP

A common beginner mistake:

```text
POST /signup
    ↓
Express
    ↓
Controller
    ↓
Service
```

and then they call this a "service test."

That's actually an integration/API-style test.

A true service unit test can simply do:

```js
const result = await authService.signup(data);
```

No HTTP required.

That's what makes it fast and focused.

# 36. Testing Services Without MongoDB

Similarly:

```text
Service
   ↓
Mock repository
```

not:

```text
Service
   ↓
Repository
   ↓
MongoDB
```

The latter is useful later when we test repositories/integration behavior.

For now:


# 37. What Should You Mock?

A useful rule:

### Mock external boundaries.

Examples:

```text
Database
Email provider
Payment API
Redis
External HTTP API
Time
Random token generation
```

But be more careful about mocking:

```text
simple pure functions
your own business rules

```

Over-mocking can make tests meaningless.

# 40. Service Tests Protect Business Rules

This is probably the most important sentence in today's lesson:

> **Service tests protect your application's business rules.**

Examples:

```text
A user cannot register twice.

A wrong password cannot log in.

A disabled account cannot log in.

A user cannot modify another user's resource.

A deleted resource cannot be updated.

An order cannot be cancelled after shipping.

A payment cannot be processed twice.
```

These aren't HTTP rules.

They're **business rules**.

Therefore services are one of the most valuable layers to test thoroughly.

# 43. What Not to Test in a Service Test

Avoid testing:

```text
Does Express parse req.body?
```

That's not the service.

Avoid:

```text
Does MongoDB really save the document?
```

That's repository/integration testing.

Avoid:

```text
Does HTTP return 201?
```

That's controller/API testing.

Instead:

```text
Does signup reject duplicate email?
```

That's service testing.

```text
                   / \

            Controllers
                /     \
```

# 45. A Complete Example

Let's imagine:

```js
async function changePassword(userId, oldPassword, newPassword) {
    const user =
        await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    const valid =
        await passwordService.compare(
            oldPassword,
            user.password
        );

    if (!valid) {
        throw new AppError(
            "Current password is incorrect",
            400
        );
    }

    const hashedPassword =
        await passwordService.hash(newPassword);

    await userRepository.updatePassword(
        userId,
        hashedPassword
    );

    return {
        success: true
    };
}
```

What should we test?

---

## Test 1 — User missing

```text
findById
 ↓
null
 ↓
404
```

---

## Test 2 — Old password incorrect

```text
find user
 ↓
compare → false
 ↓
400
 ↓
don't update
```

---

## Test 3 — Successful password change

```text
find user
 ↓
compare → true
 ↓
hash new password
 ↓
update repository
 ↓
success
```

---

## Test 4 — Plain password isn't stored

```text
repository.updatePassword()
```

must receive:

```text
hashed new password
```

not:

```text
new password
```

That's a very strong test.

# 46. What Happens When a Service Changes?

Suppose six months later you refactor:

```text
authService
```

into:

```text
authService
passwordService
tokenService
sessionService
```

If your service tests are focused on behavior, you can refactor safely.

The tests should continue saying:

```text
Signup works.
Duplicate email is rejected.
Wrong password is rejected.
Valid login returns tokens.
```

They shouldn't care too much whether you have:

```text
3 functions
```

or:

```text
10 functions
```

inside the implementation.

# 47. Service Test Quality Checklist

Before considering a service well-tested, ask:

```text
[ ] Happy path tested
[ ] Important business rules tested
[ ] Failure paths tested
[ ] Edge cases considered
[ ] Dependencies isolated where appropriate
[ ] Correct dependency arguments checked
[ ] Correct return value checked
[ ] Correct errors checked
[ ] Security-sensitive behavior tested
[ ] Tests don't depend on MongoDB
[ ] Tests don't depend on Express
[ ] Tests don't depend on each other
```

# 49. One Important Warning About Password Tests

Don't write a test that expects a specific bcrypt hash like:

```js
expect(hash).toBe(
    "$2b$10$some-fixed-hash..."
);
```

Hashes include salts, so the output can differ.

Instead test properties:

```text
hash exists
hash differs from plaintext
compare(correct password, hash) → true
compare(wrong password, hash) → false
```

That's a much better behavioral test.

# 51. The One Sentence to Remember

### Middleware tests ask:

> **Should this request continue?**

### Service tests ask:

> **What should the application do?**

### Repository tests ask:

> **Did we access the data correctly?**

### Controller tests ask:

> **Did we translate the application result into HTTP correctly?**

This separation will make the next lessons much easier.
