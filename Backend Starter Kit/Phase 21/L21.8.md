# Lesson 21.8 — Testing Repositories

Now we move one layer deeper.

So far we've covered:

```text
21.5 → Utilities
21.6 → Middleware
21.7 → Services
21.8 → Repositories ← You are here
```

Your backend architecture places repositories between services and the database:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
MongoDB
```

The repository layer is responsible for **data access**, while the service layer is responsible for **business logic**.

---

# 1. What Is a Repository?

A repository is the layer that talks to your database.

For example:

```js
export const userRepository = {
    findById(id) {
        return User.findById(id);
    },

    findByEmail(email) {
        return User.findOne({ email });
    },

    create(data) {
        return User.create(data);
    },

    deleteById(id) {
        return User.findByIdAndDelete(id);
    }
};
```

The repository answers questions like:

> "How do I retrieve this data?"

It should generally **not** answer:

> "Is this user allowed to do this?"

That's a service/business-rule concern.

---

# 2. Repository vs Service

This distinction is critical.

Suppose we want to delete a todo.

### Repository

```js
todoRepository.deleteById(todoId);
```

The repository knows:

```text
How to delete from MongoDB
```

### Service

```js
const todo = await todoRepository.findById(todoId);

if (todo.userId !== userId) {
    throw new AppError("Not allowed");
}

await todoRepository.deleteById(todoId);
```

The service knows:

```text
Who is allowed to delete it
```

So:

```text
Repository
    ↓
DATA ACCESS

Service
    ↓
BUSINESS RULES
```

---

# 3. What Are We Testing?

When testing a repository, we're interested in:

```text
✓ correct database query
✓ correct filter
✓ correct data passed
✓ correct result returned
✓ correct update operation
✓ correct deletion operation
✓ database errors handled according to contract
```

We are **not** primarily testing:

```text
✗ HTTP status
✗ Express req/res
✗ business authorization
✗ password policy
```

Those belong elsewhere.

---

# 4. Two Types of Repository Testing

This is where repository testing gets interesting.

There are two major approaches:

### Approach A — Mock the database model

```text
Repository
    ↓
mocked Mongoose model
```

This is a **unit test**.

### Approach B — Use a real test database

```text
Repository
    ↓
real Mongoose
    ↓
test MongoDB
```

This is closer to an **integration test**.

Both are useful.

---

# 5. Why Mock the Model?

Suppose:

```js
export const findById = (id) => {
    return User.findById(id);
};
```

If we want to test whether the repository calls:

```js
User.findById(id)
```

correctly, we don't need MongoDB.

We can mock:

```js
User.findById
```

Then test:

```text
Repository
   ↓
Did it call User.findById correctly?
```

This makes the test very fast.

---

# 6. Simple Repository

Let's start with:

```js
export const userRepository = {
    findById(id) {
        return User.findById(id);
    }
};
```

A unit test could look like:

```js
describe("userRepository.findById", () => {
    test("finds a user by id", async () => {
        const user = {
            id: "user-123",
            email: "rahul@example.com"
        };

        User.findById = jest.fn()
            .mockResolvedValue(user);

        const result =
            await userRepository.findById("user-123");

        expect(User.findById)
            .toHaveBeenCalledWith("user-123");

        expect(result).toEqual(user);
    });
});
```

The important part:

```js
expect(User.findById)
    .toHaveBeenCalledWith("user-123");
```

We're checking the database operation the repository requested.

---

# 7. Repository Tests Are Different From Service Tests

Compare them.

### Service:

```text
createUser()
   ↓
Should duplicate emails be rejected?
```

### Repository:

```text
findByEmail()
   ↓
Does it query:
{ email: "rahul@example.com" } ?
```

The service cares about:

```text
business behavior
```

The repository cares about:

```text
data access behavior
```

# 8. `findByEmail()`

Suppose:

```js
export const findByEmail = (email) => {
    return User.findOne({ email });
};
```

Test:

```js
test("finds a user by email", async () => {
    const user = {
        id: "user-123",
        email: "rahul@example.com"
    };

    User.findOne = jest.fn()
        .mockResolvedValue(user);

    const result =
        await userRepository.findByEmail(

        );

    expect(User.findOne)
        .toHaveBeenCalledWith({
            email: "rahul@example.com"
        });

    expect(result).toEqual(user);
});
```

This test tells us:

```text
email
 ↓
correct query
 ↓
correct result
```

# 9. Testing `create()`

Suppose:

```js
export const create = (data) => {
    return User.create(data);
};
```

Test:

```js
test("creates a user with the provided data", async () => {
    const data = {
        email: "rahul@example.com",
        password: "hashed-password"
    };

    const user = {
        id: "user-123",
        ...data
    };

    User.create = jest.fn()

    expect(User.create)
        .toHaveBeenCalledWith(data);

    expect(result).toEqual(user);
});
```

Again, we're not testing MongoDB itself.

We're testing our repository's interaction with the model.

# 10. Testing Updates

Suppose:

```js
export const updateById = (id, data) => {
    return User.findByIdAndUpdate(
        id,
        data,
        { new: true }
    );
};
```

Test:

```js
test("updates a user by id", async () => {
    const data = {
        name: "Rahul"
    };

    const updatedUser = {
        id: "user-123",
        name: "Rahul"
    };

    User.findByIdAndUpdate = jest.fn()
        .mockResolvedValue(updatedUser);

    const result =
        await userRepository.updateById(
            "user-123",
            data
        );

    expect(User.findByIdAndUpdate)
        .toHaveBeenCalledWith(
            "user-123",
            data,
            { new: true }
        );

    expect(result).toEqual(updatedUser);
});
```

Notice something important:

```js
{ new: true }
```

is part of the repository's behavior.

If someone accidentally removes it:

```js
User.findByIdAndUpdate(id, data);
```

your test can catch that.

# 11. Why Query Options Matter

Mongoose operations often have options:

```text
new
upsert
projection
sort
lean
populate
timestamps
```

For example:

```js
User.findByIdAndUpdate(
    id,
    data,
    { new: true }
);
```

Your repository may depend on that option.

Testing the exact interaction helps prevent accidental regressions.

# 13. What If the Database Returns `null`?

Suppose:

```js
User.findById(id)
```

returns:

```js
null
```

Should the repository convert that to an error?

Usually, the repository can simply return:

```js
null
```

and let the service decide what it means.

For example:

```text
Repository
    ↓
null

Service
    ↓
User not found → AppError(404)
```

That's a clean separation.

---

# 14. Test the `null` Result

```js
test("returns null when user does not exist", async () => {
    User.findById = jest.fn()
        .mockResolvedValue(null);

    const result =
        await userRepository.findById(
            "missing-user"
        );

    expect(result).toBeNull();
});
```

This is useful because the service can then handle it.

---

# 15. Repository Shouldn't Become a Business Layer

Consider:

```js
export const deleteUser = async (id) => {
    const user = await User.findById(id);

    if (user.role === "admin") {
        throw new Error("Cannot delete admin");
    }

    return User.findByIdAndDelete(id);
};
```

Now the repository is making a business decision:

```text
"Admins cannot be deleted."
```

That's usually a service concern.

Better:

```text
Service
   ↓
check whether admin deletion is allowed
   ↓
Repository
   ↓
delete
```

This makes both layers easier to test.

---

# 16. Testing Ownership Queries

Your backend architecture uses ownership-based queries in places such as authorization and resource operations.

For example:

```js
export const findByIdAndUser = (todoId, userId) => {
    return Todo.findOne({
        _id: todoId,
        userId
    });
};
```

This is an important repository function.

Why?

Because the query itself enforces:

```text
todoId
+
userId
```

---

# 17. Test the Ownership Query

```js
test("finds todo belonging to the user", async () => {
    Todo.findOne = jest.fn()
        .mockResolvedValue({
            id: "todo-123",
            userId: "user-123"
        });

    const result =
        await todoRepository.findByIdAndUser(
            "todo-123",
            "user-123"
        );

    expect(Todo.findOne)
        .toHaveBeenCalledWith({
            _id: "todo-123",
            userId: "user-123"
        });

    expect(result).toBeDefined();
});
```

This is a valuable security-oriented repository test.

---

# 18. Why This Query Is Better Than Two Queries

Potentially weaker approach:

```text
find todo by ID
      ↓
check userId in service
```

Alternative:

```text
find todo where:
_id = todoId
AND
userId = currentUserId
```

The second approach can reduce the chance of accidentally operating on another user's resource.

But remember:

> Repository query design and authorization architecture should work together.

The service still owns the business decision.

# 19. Testing Query Filters

Suppose:

```js
export const findActiveUsers = () => {
    return User.find({
        isActive: true
    });

```

Test:

```js
test("finds active users only", async () => {
    User.find = jest.fn()

    expect(User.find)

            isActive: true
        });

```

This is a straightforward repository test.

# 20. Testing Sorting

Suppose:

```js
export const findLatest = () => {
    return User.find()
        .sort({ createdAt: -1 });
};
```

Now the test may need to verify the chain.

This is where Mongoose's API makes repository unit tests more complicated.

For example:

```text
User.find()
   ↓
sort()
   ↓
lean()
   ↓
exec()
```

You need to decide whether mocking this chain is worth it.

And often this is a sign that **integration testing the repository with a test database may be cleaner**.

---

# 21. This Is the Important Question

Ask yourself:

> **Am I testing my repository's logic, or am I trying to fake Mongoose?**

If you have to build a huge mock like:

```text
find()
  ↓
mock object
  ↓
sort()
  ↓
mock object
  ↓
lean()
  ↓
mock object
  ↓
exec()
```

you may be spending more effort mocking Mongoose than testing your code.

That's where integration tests become attractive.

---

# 22. Unit Testing Repositories Has Limits

Repository unit tests are useful for:

```text
✓ query construction
✓ arguments
✓ options
✓ result mapping
✓ error translation
```

But they cannot prove that:

```text
MongoDB
actually accepts the query.
```

For that, you need an integration test.

---

# 23. Repository Integration Test

The architecture becomes:

```text
Test
 ↓
Repository
 ↓
Mongoose
 ↓
Test MongoDB
```

Now the query is actually executed.

This catches issues like:

```text
wrong field name
wrong MongoDB operator
incorrect index assumptions
schema mismatch
Mongoose behavior misunderstanding
populate problems
query behavior problems
```

That's why repository integration tests are very valuable.

---

# 24. Real Database vs Production Database

Very important:

**Never run your repository tests against your production database.**

Use a dedicated test database.

For example:

```text
Development
    ↓
backend_dev

Testing
    ↓
backend_test

Production
    ↓
backend_prod
```

Keep them completely separate.

---

# 25. Test Database Isolation

Suppose test A creates:

```text
user-123
```

Then test B runs.

If test B sees:

```text
user-123
```

because test A left it behind, your tests are now coupled.

That's bad.

You want:

```text
Test A
 ↓
clean state

Test B
 ↓
clean state
```

We'll study test isolation more deeply in **21.15**.

---

# 26. In-Memory MongoDB

One popular approach is using an in-memory MongoDB environment for tests.

Conceptually:

```text
Jest
 ↓
MongoDB in memory
 ↓
Mongoose
 ↓
Repository
```

This gives you:

```text
real Mongoose behavior
+
isolated test environment
```

without relying on your normal development database.

The exact setup depends on your project and package choices, so don't add it blindly yet.

---

# 27. Unit vs Integration Repository Tests

Think of them like this:

### Unit

```text
repository
   ↓
mocked Model
```

Fast.

Focused.

Good for query construction.

### Integration

```text
repository
   ↓
real Mongoose
   ↓
test MongoDB
```

Slower.

More realistic.

Good for verifying actual database behavior.

---

# 28. Should Every Repository Have Both?

Not necessarily.

A practical strategy is:

```text
Simple repository
    ↓
integration tests may be enough

Complex repository
    ↓
unit tests
+
integration tests
```

For example:

```text
findById()
```

might be trivial.

But:

```text
searchUsers()
  ↓
filters
  ↓
sorting
  ↓
pagination
  ↓
projection
  ↓
population
```

deserves stronger integration coverage.

---

# 29. Repository + Pagination

This becomes especially relevant because you've already completed the pagination phase.

Suppose:

```js
User.find(filter)
    .sort(sort)
    .skip(skip)
    .limit(limit);
```

A repository test can verify:

```text
filter
sort
skip
limit
```

But an integration test can verify that:

```text
skip + limit
```

actually returns the expected documents.

That's a great example of where the two test levels complement each other.

---

# 30. Repository + Transactions

Later, you may have:

```text
session
 ↓
transaction
 ↓
multiple database operations
```

For example:

```text
Create order
+
Create payment record
+
Update inventory
```

Unit mocking can become complicated.

Integration tests are often much more valuable because you want to verify actual transaction behavior.

---

# 31. Repository Error Testing

Suppose:

```js
User.create(data)
```

throws a database error.

You might test:

```js
test("propagates repository errors", async () => {
    const error = new Error("Database unavailable");

    User.create = jest.fn()
        .mockRejectedValue(error);

    await expect(
        userRepository.create({
            email: "rahul@example.com"
        })
    ).rejects.toThrow("Database unavailable");
});
```

But if your repository intentionally translates the error:

```text
Mongo duplicate key
       ↓
AppError("Email already exists")
```

then test the translated error instead.

Again:

> Test the repository's actual contract.

---

# 32. Don't Duplicate Service Tests

Suppose the service says:

```js
if (!user) {
    throw new AppError("User not found", 404);
}
```

Don't repeat that business rule in repository tests.

Repository test:

```text
findById() returns null
```

Service test:

```text
null → User not found error
```

That's clean.

---

# 33. Think in Contracts

Each layer has a contract.

### Repository contract

```text
findById(id)
→ user | null
```

### Service contract

```text
getUser(id)
→ user
or
→ AppError(404)
```

### Controller contract

```text
GET /users/:id
→ HTTP 200
or
→ HTTP 404
```

Testing each contract separately keeps the architecture understandable.

# 39. What About `.lean()`?

Suppose your repository does:

```js
return User.findById(id).lean();
```

Now you might need to mock:

```js
User.findById = jest.fn().mockReturnValue({
    lean: jest.fn().mockResolvedValue(user)
});
```

Test:

```js
expect(User.findById)
    .toHaveBeenCalledWith(id);
```

This works.

But notice the growing complexity.

This is one of the reasons repository integration testing becomes attractive as query complexity increases.

---

# 40. What About `.populate()`?

Suppose:

```js
return Todo.findById(id)
    .populate("user")
    .lean();
```

A unit test now needs to mimic:

```text
findById()
   ↓
populate()
   ↓
lean()
```

You can do it.

But ask yourself:

> Is mocking this chain giving me confidence that Mongoose will actually behave correctly?

Not much.

An integration test with a real test database may give significantly more confidence.

# 41. Repository Testing Strategy

For your MERN backend, a good long-term strategy is:

```text
Simple query
   ↓
unit test if useful

Complex query
   ↓
integration test

Critical query
   ↓
unit + integration
```

Critical examples:

```text
ownership queries
authentication lookup
refresh-token lookup
financial/payment queries
transactional operations
pagination/search logic
```

---

# 42. Security-Critical Repository Queries

Your architecture has authentication and authorization layers.

For example:

```text
refresh token
   ↓
find session/token record
```

or:

```text
resource
   ↓
resource + owner ID
```

These deserve extra attention.

A small query mistake such as:

```js
Todo.findOne({
    _id: todoId
});
```

instead of:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

can create a serious authorization problem.

A repository test can catch this regression.

---

# 43. Testing Query Shape Is Valuable

Consider:

```js
expect(Todo.findOne)
    .toHaveBeenCalledWith({
        _id: todoId,
        userId
    });
```

This may look overly specific at first.

But for a security-sensitive query, it's exactly the kind of detail worth protecting.

You are asserting:

> **This query must include ownership filtering.**

# 44. Repository Tests and Indexes

Suppose your query is:

```js
User.findOne({
    email
});
```

and you have a unique index on:

```text
email
```

A unit test can verify:

```text
findOne({ email })
```

but it **cannot** prove:

```text
the index actually exists.
```

For that, an integration/database-level test or schema validation approach is more appropriate.

This is another example of unit tests having boundaries.

---

# 45. Repository Tests and Mongoose Schemas

Similarly, a unit test mocking:

```js
User.create()
```

doesn't prove that:

```text
required fields
unique constraints
timestamps
schema validation
middleware/hooks
```

actually behave correctly.

Real database integration tests are much better for these behaviors.

# 47. Repository Unit Test Checklist

For a repository function, ask:

```text
[ ] Correct model method?
[ ] Correct filter?
[ ] Correct arguments?
[ ] Correct options?
[ ] Correct returned result?
```

```text

```

# 48. Common Mistake #1 — Testing MongoDB Itself

Don't write tests like:

> "Does MongoDB support `findById`?"

That's not your code.

Test:

> "Does my repository call `User.findById(id)` correctly?"

---

# 49. Common Mistake #2 — Putting Business Logic in Repository

If repository contains:

```js
if (user.role !== "admin") {
    throw ...
}
```

you've mixed responsibilities.

Keep:

```text
Repository
→ data access

Service
→ business rules
```

Your tests will become cleaner as a result.

---

# 50. Common Mistake #3 — Only Mocking Everything

If every repository test looks like:

```text
mock find
mock sort
mock populate
mock lean
mock exec
```

you may have created a fake version of Mongoose.

At some point:

> **Stop mocking and use a real test database.**

That is not a failure of unit testing.

It's recognizing the correct test boundary.

---

# 51. Common Mistake #4 — Using Development DB

Never do:

```text
Jest
 ↓
mongodb://localhost/my-real-development-db
```

because your tests could:

```text
delete data
modify data
create junk
interfere with development
```

Use a dedicated test environment.

---

# 52. Common Mistake #5 — Tests Depending on Test Order

Bad:

```text
Test A creates user
       ↓
Test B expects user
```

Now:

```text
Test B
```

cannot run independently.

Good:

```text
Test A
 ↓
clean state

Test B
 ↓
clean state
```

Each test should create the data it needs.

We'll go deeper into this in **21.15 — Test Isolation and Database Cleanup**.

# 53. Service + Repository Together

Let's connect the previous lesson.

Suppose:

```text
authService.login()
        ↓
userRepository.findByEmail()
```

### Service unit test

```text
mock repository
      ↓
test login business rules
```

### Repository unit test

```text
mock Mongoose model
      ↓
test query construction
```

### Repository integration test

```text
real MongoDB
      ↓
test actual query
```

### API test

```text
HTTP
 ↓
controller
 ↓
service
 ↓
repository
 ↓
database
```

Now you can see why different tests exist.

# 54. One Powerful Mental Model

Think of each test as answering a different question:

|Test|Question|
|---|---|
|Utility|Does this small function calculate/transform correctly?|
|Middleware|Should the request continue?|
|Service|What should the application do?|
|Repository unit|Did we construct the data operation correctly?|
|Repository integration|Does the data operation actually work?|
|Controller|Did we translate it into HTTP correctly?|
|API/Supertest|Does the complete endpoint work?|

This is the testing architecture you're building through Phase 21.

# 56. What You Should Remember

The most important ideas from 21.8 are:

### Repository = data-access boundary

```text
Service
   ↓
Repository
   ↓
Database
```

### Unit-test repositories by mocking the model

```text
Repository
   ↓
mock Mongoose model
```

### Integration-test complex/important queries with a test database

```text
Repository
   ↓
Mongoose
   ↓
test MongoDB
```

### Don't put business rules in repositories

```text
Service → decisions
Repository → data access
```

### Don't blindly mock complex database chains

Sometimes:

```text
integration test
```

is better than:

```text
giant Mongoose mock
```

### Security-sensitive queries deserve special attention

Especially:

```text
resource + owner
```

because a missing ownership filter can become a real authorization vulnerability.

# 57. Final Architecture

At this point, your testing model should look like:

```text
                    HTTP
                     │
                     ▼
              ┌─────────────┐
              │ Controller  │
              └──────┬──────┘
                     │
                     ▼
              ┌─────────────┐
              │   Service   │
              │             │
              │ Business    │
              │ Rules       │
              └──────┬──────┘
                     │
                     ▼
              ┌─────────────┐
              │ Repository  │
              │             │
              │ Data Access │
              └──────┬──────┘
                     │
                     ▼
                 MongoDB
```

And your tests increasingly surround each layer:

```text
Utility tests
      ↓
Middleware tests
      ↓
Service tests
      ↓
Repository unit tests
      ↓
Repository integration tests
      ↓
Controller tests
      ↓
API tests
```

That's the architecture you want to internalize—not just the Jest syntax.
