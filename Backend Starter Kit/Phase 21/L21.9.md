# Lesson 21.9 — Testing Controllers

Now we move one layer upward.

So far:

```text
21.5  Testing Utilities
21.6  Testing Middleware
21.7  Testing Services
21.8  Testing Repositories
21.9  Testing Controllers  ← You are here
```

The key idea is:

> **A controller's job is to translate HTTP input into a service call and translate the service result back into an HTTP response.**

Your architecture separates controllers from services: controllers handle HTTP concerns, while services contain business logic.

---

# 1. Where Does the Controller Fit?

Think about a request:

```text
Client
  │
  │ POST /api/v1/auth/login
  ▼
Controller
  │
  │ email + password
  ▼
Service
  │
  ▼
Repository
  │
  ▼
MongoDB
```

The controller sits at the **HTTP boundary**.

It should understand things like:

```text
req.body
req.params
req.query
req.user
res.status()
res.json()
next(error)
```

It should generally **not** understand things like:

```text
MongoDB queries
password hashing
business rules
authorization decisions
token database operations
```

Those belong elsewhere.

---

# 2. A Simple Controller

Imagine:

```js
export const getUser = async (req, res, next) => {
    try {
        const user = await userService.getUser(
            req.params.id
        );

        res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

What should we test?

Not MongoDB.

Not the service's business logic.

Instead:

```text
req.params.id
      ↓
service.getUser(id)
      ↓
response
```

---

# 3. Controller Tests Are About Translation

A useful mental model:

```text
HTTP input
    ↓
Controller
    ↓
Service input
```

Then:

```text
Service result
    ↓
Controller
    ↓
HTTP output
```

So controller testing asks:

> **Did the controller translate correctly in both directions?**

---

# 4. What Should We Test?

For a controller, focus on:

```text
✓ request data extraction
✓ service call
✓ arguments passed to service
✓ response status
✓ response body
✓ next(error)
✓ correct response structure
```

Don't focus on:

```text
✗ business rules
✗ database queries
✗ password hashing
✗ complex authorization logic
```

Those should already be tested in lower layers.

---

# 5. Testing Controllers Without HTTP

You don't need to start Express for a controller unit test.

You can create fake objects:

```js
const req = {
    params: {
        id: "user-123"
    }
};

const res = {
    status: jest.fn().mockReturnThis(),
    json: jest.fn()
};

const next = jest.fn();
```

Then call:

```js
await getUser(req, res, next);
```

This is a **controller unit test**.

Later, when we reach Supertest, we'll test the controller through real HTTP.

---

# 6. Mock the Service

This is extremely important.

Suppose:

```js
userService.getUser()
```

is already tested in Lesson 21.7.

We don't want the controller test to execute the real service.

Instead:

```js
userService.getUser = jest.fn();
```

Then:

```js
userService.getUser
    .mockResolvedValue({
        id: "user-123",
        name: "Rahul"
    });
```

Now:

```text
Controller
   ↓
mock service
```

This keeps the test focused.

---

# 7. First Controller Test

Controller:

```js
export const getUser = async (req, res, next) => {
    try {
        const user = await userService.getUser(
            req.params.id
        );

        res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

Test:

```js
describe("getUser", () => {
    test("returns the user", async () => {
        const user = {
            id: "user-123",
            name: "Rahul"
        };

        userService.getUser
            .mockResolvedValue(user);

        const req = {
            params: {
                id: "user-123"
            }
        };

        const res = {
            status: jest.fn().mockReturnThis(),
            json: jest.fn()
        };

        const next = jest.fn();

        await getUser(req, res, next);

        expect(
            userService.getUser
        ).toHaveBeenCalledWith("user-123");

        expect(res.status)
            .toHaveBeenCalledWith(200);

        expect(res.json)
            .toHaveBeenCalledWith({
                success: true,
                data: user
            });

        expect(next)
            .not.toHaveBeenCalled();
    });
});
```

This is a very typical controller unit test.

# 9. Testing `req.params`

Suppose your route is:

```text
GET /users/:id
```

The controller receives:

```js
req.params.id
```

Your test should verify:

```js
expect(userService.getUser)
    .toHaveBeenCalledWith("user-123");
```

This protects against mistakes such as:

```js
userService.getUser(req.params.userId);
```

when the route actually provides:

```text
:id
```

# 10. Testing `req.query`

Suppose:

```text
GET /users?page=2&limit=20
```

Controller:

```js
export const listUsers = async (req, res, next) => {
    try {
        const result = await userService.listUsers({
            page: req.query.page,
            limit: req.query.limit
        });

        res.status(200).json({
            success: true,
            data: result
        });
    } catch (error) {
        next(error);
    }
};
```

Test:

```js
test("passes query parameters to service", async () => {
    userService.listUsers
        .mockResolvedValue({
            users: [],
            pagination: {}
        });

    const req = {
        query: {
            page: "2",
            limit: "20"
        }
    };

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    await listUsers(req, res, next);

    expect(userService.listUsers)
        .toHaveBeenCalledWith({
            page: "2",
            limit: "20"
        });
});
```

Notice that the controller doesn't implement pagination.

It simply passes the HTTP input onward.

# 12. Testing `req.user`

This becomes especially important because you've already covered authentication and authorization.

Suppose authentication middleware sets:

```js
req.user = {
    id: "user-123"
};
```

Then the controller:

```js
export const createTodo = async (req, res, next) => {
    try {
        const todo = await todoService.createTodo({
            userId: req.user.id,
            ...req.body
        });

        res.status(201).json({
            success: true,
            data: todo
        });
    } catch (error) {
        next(error);
    }
};
```

Test:

```js
test("passes authenticated user to service", async () => {
    const todo = {
        id: "todo-123",
        title: "Learn testing"
    };

    todoService.createTodo
        .mockResolvedValue(todo);

    const req = {
        user: {
            id: "user-123"
        },
        body: {
            title: "Learn testing"
        }
    };

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    await createTodo(req, res, next);

    expect(todoService.createTodo)
        .toHaveBeenCalledWith({
            userId: "user-123",
            title: "Learn testing"
        });
});
```

This protects an important security boundary:

```text
authenticated identity
        ↓
controller
        ↓
service
```

# 13. Never Trust `userId` From the Body

Suppose the request body contains:

```json
{
    "title": "My todo",
    "userId": "another-user"
}
```

If your controller does:

```js
todoService.createTodo(req.body);
```

you could accidentally trust user-controlled ownership data.

A safer architecture is:

```js
todoService.createTodo({
    userId: req.user.id,
    ...req.body
});
```

But be careful about property ordering too.

If you do:

```js
{
    userId: req.user.id,
    ...req.body
}
```

the body can overwrite it.

Prefer:

```js
{
    ...req.body,
    userId: req.user.id
}
```

Now the authenticated identity wins.

This is exactly the kind of controller behavior a test should protect.

---

# 14. Test That the Authenticated User Wins

```js
test("uses authenticated user instead of body userId", async () => {
    todoService.createTodo
        .mockResolvedValue({
            id: "todo-123"
        });

    const req = {
        user: {
            id: "real-user"
        },
        body: {
            title: "Test",
            userId: "attacker-user"
        }
    };

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    await createTodo(req, res, next);

    expect(todoService.createTodo)
        .toHaveBeenCalledWith({
            title: "Test",
            userId: "real-user"
        });
});
```

That's a very good security-focused controller test.

# 15. Testing Status Codes

Controller tests should verify the HTTP status.

For creation:

```js
expect(res.status)
    .toHaveBeenCalledWith(201);
```

For normal retrieval:

```js
expect(res.status)
    .toHaveBeenCalledWith(200);
```

For deletion:

```js
expect(res.status)
    .toHaveBeenCalledWith(204);
```

But don't assume every project uses the same status conventions.

Test **your API contract**.

---

# 16. Testing Response Bodies

Suppose:

```js
res.status(200).json({
    success: true,
    data: user
});
```

Test:

```js
expect(res.json)
    .toHaveBeenCalledWith({
        success: true,
        data: user
    });
```

This catches accidental response changes such as:

```js
res.json(user);
```

when your API contract expects:

```json
{
  "success": true,
  "data": {}
}
```

---

# 17. Response Shape Is an API Contract

This becomes increasingly important as your API grows.

For example:

```json
{
  "success": true,
  "data": {
    "id": "123"
  }
}
```

is different from:

```json
{
  "data": {
    "id": "123"
  }
}
```

A frontend may depend on that structure.

Controller tests can protect the contract.

# 18. Testing Errors

Now the important part.

Suppose the service throws:

```js
throw new AppError(
    "User not found",
    404
);
```

The controller should usually do:

```js
catch (error) {
    next(error);
}
```

rather than handling every error itself.

Test:

```js
test("passes service errors to next", async () => {
    const error = new Error("User not found");

    userService.getUser
        .mockRejectedValue(error);

    const req = {
        params: {
            id: "user-123"
        }
    };

    const res = {
        status: jest.fn().mockReturnThis(),
        json: jest.fn()
    };

    const next = jest.fn();

    await getUser(req, res, next);

    expect(next)
        .toHaveBeenCalledWith(error);

    expect(res.status)
        .not.toHaveBeenCalled();

    expect(res.json)
        .not.toHaveBeenCalled();
});
```

This is a very important controller test.

---

# 19. Why Use `next(error)`?

Your architecture has centralized error handling.

The controller should usually do:

```text
Service throws
     ↓
Controller catches
     ↓
next(error)
     ↓
Global error middleware
     ↓
HTTP response
```

Instead of every controller doing:

```js
res.status(500).json(...)
```

for every possible error.

This keeps error formatting centralized.

---

# 20. Controller Shouldn't Reimplement Error Logic

Bad:

```js
try {
    const user = await userService.getUser(id);
    res.json(user);
} catch (error) {
    if (error.message === "User not found") {
        return res.status(404).json(...);
    }

    if (error.message === "Database unavailable") {
        return res.status(503).json(...);
    }

    return res.status(500).json(...);
}
```

Now the controller contains business/error translation logic.

Better:

```js
try {
    const user = await userService.getUser(id);

    res.status(200).json({
        success: true,
        data: user
    });
} catch (error) {
    next(error);
}
```

Then:

```text
Error Middleware
```

owns the final HTTP error formatting.

---

# 21. Controller Tests Should Verify `next()`

For successful requests:

```js
expect(next)
    .not.toHaveBeenCalled();
```

For failures:

```js
expect(next)
    .toHaveBeenCalledWith(error);
```

This gives you a very clean contract.

---

# 22. Testing Service Calls

One of the most important assertions:

```js
expect(userService.getUser)
    .toHaveBeenCalledWith("user-123");
```

Why?

Because the controller might accidentally do:

```js
userService.getUser(req.body.id);
```

instead of:

```js
userService.getUser(req.params.id);
```

Both may technically execute.

Only one is correct.

---

# 23. Test Call Count

Sometimes you also want:

```js
expect(userService.getUser)
    .toHaveBeenCalledTimes(1);
```

This protects against accidental duplicate service calls:

```js
const user = await userService.getUser(id);
const again = await userService.getUser(id);
```

That could create unnecessary database work.

But don't add call-count assertions everywhere unless the count is meaningful.

---

# 24. Controller Should Stay Thin

A healthy controller often looks like:

```js
export const getUser = async (req, res, next) => {
    try {
        const user = await userService.getUser(
            req.params.id
        );

        res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

That's good.

A controller like this is a warning sign:

```js
export const getUser = async (req, res, next) => {
    // validate
    // query database
    // check ownership
    // hash password
    // generate token
    // calculate permissions
    // transform data
    // send email
    // ...
};
```

Too much responsibility.

---

# 25. Thin Controllers = Easy Tests

Compare.

### Thin controller

```text
request
 ↓
service
 ↓
response
```

Test is simple.

### Fat controller

```text
request
 ↓

 ↓
database
 ↓
business rules
 ↓
authorization
 ↓
transformation
 ↓
email
 ↓

```

Now the test becomes huge.

This is one reason good architecture naturally improves testability.

# 26. Testing `res.status().json()` Chaining

Express allows:

```js
res.status(200).json(data);
```

Your fake response needs:

```js
const res = {
    status: jest.fn().mockReturnThis(),
    json: jest.fn()
};
```

Why `mockReturnThis()`?

Because:

```js
res.status(200)
```

needs to return `res` so that:

```js
.json(...)
```

can be called.

Without it:

```js
status: jest.fn()
```

would return `undefined`.

Then:

```js
res.status(200).json(...)
```

would fail.

# 29. Testing Cookies

Suppose login does:

```js
res.cookie(
    "refreshToken",
    refreshToken,

```

```js
const res = {
```

# 31. Testing Multiple Inputs

Consider:

```text
PATCH /users/:id
```

with:

```text
req.params.id
req.body
req.user.id
```

Controller:

```js
await userService.updateUser(
    req.user.id,
    req.params.id,
```

Test all three:

```js
expect(userService.updateUser)
    .toHaveBeenCalledWith(
        "user-123",

        }

```

This is exactly what controller unit tests are good at.

# 32. Don't Test Service Logic Again

Suppose the service guarantees:

```text
User cannot update another user's profile.
```

Don't make the controller test reproduce that entire rule.

The controller test should simply verify:

```text
authenticated user ID
+
requested user ID
+
body
```

are passed correctly.

Then service tests verify what happens with those values.

# 33. Controller Test Matrix

For:

```text
GET /users/:id
```

you might have:

|Scenario|Expected|
|---|---|
|Service succeeds|200 + data|
|Service throws|`next(error)`|
|Correct `id`|Service gets correct ID|
|Service returns expected object|Same object in response|

That's usually enough for a thin controller.

# 36. Controller and Authentication Middleware

Your request pipeline may look like:

```text
Request
   ↓
authenticate
   ↓
authorize
   ↓
controller
   ↓
service
```

A controller unit test doesn't need to run the actual authentication middleware.

Instead, provide:

```js
req.user = {
    id: "user-123"
};
```

Why?

Because authentication middleware already has its own tests.

You're isolating the controller.

---

# 37. This Is Test Composition

Each layer has its own confidence.

```text
Middleware test
    ↓
"Authentication works."

Controller test
    ↓
"Controller uses req.user correctly."

Service test
    ↓
"Business rules use user identity correctly."

Repository test
    ↓
"Database query filters by user."
```

Then later an API test can verify the whole pipeline.

---

# 38. Controller Unit Test vs API Test

This distinction is very important.

### Controller unit test

```text
fake req
fake res
mock service
        ↓
controller()
```

Very fast.

### API test

```text
HTTP request
    ↓
Express
    ↓
middleware
    ↓
controller
    ↓
service
    ↓
repository
```

Much broader.

We'll use **Supertest** for that later in Phase 21.

---

# 39. When Controller Tests Become Too Detailed

You don't need to test every JavaScript line.

For example:

```js
const user = await userService.getUser(id);
```

and then:

```js
const response = {
    success: true,
    data: user
};
```

You don't need a test for every intermediate variable.

Test the observable contract:

```text
service called correctly
response correct
errors forwarded
```

---

# 40. A Good Controller Test File

A typical structure:

```js
describe("getUser", () => {
    beforeEach(() => {
        jest.clearAllMocks();
    });

    test("calls service with route param", async () => {
        // ...
    });

    test("returns 200 with user", async () => {
        // ...
    });

    test("forwards service errors", async () => {
        // ...
    });
});
```

For more complex controllers:

```text
success
validation failure
service failure
authorization-related input
response formatting
```

---

# 41. Controller Testing Checklist

For every controller, ask:

```text
[ ] Does it read the correct req property?
[ ] Does it pass the correct arguments?
[ ] Does it call the service exactly as intended?
[ ] Does success return the correct status?
[ ] Does success return the correct body?
[ ] Does failure call next(error)?
[ ] Does it avoid unnecessary business logic?
[ ] Does it correctly use req.user?
[ ] Does it correctly handle params/query/body?
```

---

# 42. A Security Checklist

For authenticated controllers:

```text
[ ] User identity comes from req.user
[ ] Client cannot override ownership identity
[ ] Correct resource ID is passed
[ ] Sensitive data isn't accidentally returned
[ ] Authentication-dependent service receives correct identity
```

This is especially important because your architecture treats authorization as a separate layer and uses authenticated identity throughout protected operations.

---

# 43. Common Mistake #1 — Testing the Real Service

Bad controller unit test:

```text
Controller
   ↓
real service
   ↓
real repository
   ↓
real database
```

Now you're no longer isolating the controller.

Instead:

```text
Controller
   ↓
mock service
```

---

# 44. Common Mistake #2 — Testing Business Rules

Bad:

```js
expect(controller)
    .toRejectDuplicateEmail();
```

The controller shouldn't know about duplicate email logic.

The service should.

Controller:

```text
"call authService.signup()"
```

Service:

```text
"reject duplicate email"
```

---

# 45. Common Mistake #3 — Returning HTTP Errors Directly Everywhere

Bad:

```js
catch (error) {
    res.status(500).json({
        message: error.message
    });
}
```

This can bypass your centralized error handling.

Prefer:

```js
catch (error) {
    next(error);
}
```

when your application architecture uses centralized error middleware.

---

# 46. Common Mistake #4 — Trusting Body Ownership

Bad:

```js
todoService.createTodo(req.body);
```

when `userId` should come from:

```js
req.user.id
```

A test should catch that.

---

# 47. Common Mistake #5 — Testing Only Status Code

This:

```js
expect(res.status)
    .toHaveBeenCalledWith(200);
```

isn't enough.

You should often also test:

```js
expect(res.json)
    .toHaveBeenCalledWith(expectedBody);
```

Otherwise your response could be completely wrong while still returning `200`.

---

# 48. The Three Assertions I Want You to Remember

For a typical successful controller:

### 1. Service call

```js
expect(service.method)
    .toHaveBeenCalledWith(expectedArgs);
```

### 2. HTTP status

```js
expect(res.status)
    .toHaveBeenCalledWith(200);
```

### 3. Response body

```js
expect(res.json)
    .toHaveBeenCalledWith(expectedBody);
```

And for failure:

### 4. Error forwarding

```js
expect(next)
    .toHaveBeenCalledWith(error);
```

Those four assertions cover a huge amount of controller behavior.

# 49. The Architecture Is Coming Together

You now have:

```text
             ┌──────────────┐
             │   Request    │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │  Middleware  │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │  Controller  │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │   Service    │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │ Repository   │
             └──────┬───────┘
                    │
                    ▼
                MongoDB
```

And tests:

```text
Middleware
    ↓
"Should request continue?"

Controller
    ↓
"Did HTTP translate correctly?"

Service
    ↓
"Did business logic work?"

Repository
    ↓
"Did data access work?"
```

That separation is the heart of maintainable backend testing.

Create:



```text
createTodo()
```

```text
req.user.id
     ↓
service
```

```text

```

# 51. What You Should Understand After 21.9

You should now have this mental model:

```text
Repository
    ↓
"How do I access data?"

Service
    ↓
"What should the application do?"

Controller
    ↓
"How do I translate HTTP into that operation?"

Middleware
    ↓
"Should this request be allowed to continue?"
```

And therefore:

> **Controller tests should be thin, focused, and mostly about input extraction, service interaction, HTTP output, and error forwarding.**
