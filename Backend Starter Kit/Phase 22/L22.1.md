# Lesson 22.1 — What Is Security Testing? 🔐

Welcome to **Phase 22**.

In Phase 21, we learned how to test whether our backend behaves correctly.

Now we change our mindset.

> **Security testing asks whether the backend can be abused, bypassed, or manipulated by an attacker.**

Your Phase 22 roadmap specifically starts with security testing before moving into threat modeling, OWASP API risks, broken authentication/authorization, IDOR, injection, JWT attacks, cookies, CORS/CSRF, and sensitive-data exposure.

---

# 1. Normal Testing vs Security Testing

Suppose we have:

```http
POST /api/v1/todos
```

A normal test might be:

```text
Send valid request
        ↓
Todo created
        ↓
201 Created
```

That's good.

But a security tester asks much more.

```text
What if JWT is missing?
What if JWT is invalid?
What if JWT belongs to another user?
What if user changes todoId?
What if user adds role=admin?
What if request contains unexpected fields?
What if user sends 10,000 requests?
What if input contains malicious operators?
What if an internal error exposes database details?
```

So:

```text
Functional testing
        ↓
"Does it work?"

Security testing
        ↓
"Can I break or abuse it?"
```

---

# 2. Security Testing Is Negative Testing

A useful way to understand security testing is:

> **We intentionally give the application bad, unexpected, or malicious input and verify that it fails safely.**

For example:

### Normal

```json
{
  "title": "Learn MongoDB"
}
```

### Unexpected

```json
{
  "title": 12345
}
```

### Malicious

```json
{
  "role": "admin"
}
```

Or an attacker may manipulate the URL:

```http
GET /api/v1/todos/USER_B_TODO
```

The application shouldn't simply say:

> "The request reached my controller, so everything is fine."

It must enforce its security rules.

---

# 3. The Three Questions of Security Testing

Whenever you test an endpoint, ask:

## Question 1 — Can an unauthorized person access it?

Example:

```text
GET /api/v1/users/me
```

No token:

```text
❌ Access denied
```

---

## Question 2 — Can an authorized person do something they shouldn't?

Example:

```text
DELETE /api/v1/users/123
```

A normal user might be authenticated but still shouldn't be allowed to delete another user.

So:

```text
Authenticated ≠ Authorized
```

---

## Question 3 — Can the request manipulate the application?

Example:

```json
{
  "title": "My Todo",
  "role": "admin"
}
```

The backend must decide which fields are actually allowed.

This is where security testing starts finding problems such as **mass assignment**.

---

# 4. Think Like an Attacker

Imagine your API:

```text
POST /api/v1/auth/login
```

A developer might think:

```text
email + password
        ↓
login
```

An attacker thinks:

```text
Can I:

• omit the password?
• send an extremely long password?
• send malformed JSON?
• send unexpected fields?
• send requests repeatedly?
• reuse old credentials?
• manipulate tokens?
• bypass rate limits?
```

That's the fundamental mindset of this phase.

---

# 5. Security Testing Doesn't Mean "Hacking Randomly"

There is a difference between:

```text
Random hacking
```

and:

```text
Structured security testing
```

We want:

```text
Threat
  ↓
Expected security behavior
  ↓
Attack input
  ↓
Application response
  ↓
Assertion
```

Example:

```text
Threat:
User A accesses User B's Todo

Expected:
Request must be rejected

Test:
Authenticate as User A
Request User B's Todo

Expected result:
403 / 404
```

That's a proper security test.

---

# 6. Example: Testing Ownership

Suppose our database contains:

```text
User A
  id = 101

Todo A
  id = 500
  userId = 101
```

and:

```text
User B
  id = 202

Todo B
  id = 600
  userId = 202
```

User A logs in.

They receive:

```text
accessToken(A)
```

Now they request:

```http
GET /api/v1/todos/600
Authorization: Bearer accessToken(A)
```

A vulnerable backend might do:

```js
Todo.findById("600");
```

and return Todo B.

Security test:

```text
Expected:
❌ User A must NOT receive Todo B
```

This is a security test even though the API itself is functioning normally.

# 8. Security Testing Has Different Levels

We can test security at different layers.

## Level 1 — Unit security tests

Test individual functions.

Example:

```text
verifyToken()
```

Test:

```text
valid token → accepted
expired token → rejected
invalid token → rejected
```

---

## Level 2 — Integration security tests

Test multiple backend components together.

```text
HTTP
 ↓
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
```

Example:

```text
User A
 ↓
GET /todos/User-B-todo
 ↓
authorization
 ↓
rejected
```

---

## Level 3 — API security testing

Treat the backend like an external attacker.

You don't care how the code works internally.

You only care about:

```text
Request
   ↓
API
   ↓
Response
```

This is extremely useful.

---

# 9. Security Testing Should Test the Boundaries

A backend has many boundaries.

For example:

```text
Internet
   ↓
Express
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

Each boundary can become an attack surface.

### Internet → Express

Test:

```text
Malformed requests
Huge requests
Unexpected methods
Rate limiting
```

### Middleware → Controller

Test:

```text
Missing authentication
Invalid authentication
Invalid input
```

### Controller → Service

Test:

```text
Unexpected values
Unauthorized operations
Mass assignment
```

### Service → Repository

Test:

```text
Ownership
Filtering
Unsafe queries
```

### Backend → Database

Test:

```text
Injection
Unsafe queries
Excessive data access
```

# 10. Security Test Example

Suppose we have:

```http
PATCH /api/v1/users/me
```

Normal test:

```json
{
  "name": "Rahul"
}
```

Expected:

```text
200 OK
```

Security tests:

### Test A — No authentication

```text
PATCH /users/me
```

Expected:

```text
401
```

### Test B — Unexpected field

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

Expected:

```text
role must not be modified
```

### Test C — Invalid input

```json
{
  "name": 12345
}
```

Expected:

```text
400
```

### Test D — Malicious input

Send specially crafted input.

Expected:

```text
Safely rejected
```

### Test E — Excessive requests

Repeated requests.

Expected:

```text
429 Too Many Requests
```

Notice how **one endpoint can have many security tests**.

---

# 11. Security Tests Should Have Security Assertions

A normal assertion might be:

```js
expect(response.status).toBe(200);
```

A security assertion might be:

```js
expect(response.status).toBe(401);
```

or:

```js
expect(response.status).toBe(403);
```

or:

```js
expect(response.body.data.role).not.toBe("admin");
```

or:

```js
expect(response.body.data.passwordHash).toBeUndefined();
```

The important thing is:

> **We assert that the attack was prevented.**

---

# 12. 401 vs 403

This becomes very important during security testing.

### `401 Unauthorized`

Usually means:

> You have not successfully authenticated.

Examples:

```text
No token
Invalid token
Expired token
```

---

### `403 Forbidden`

Usually means:

> You are authenticated, but you aren't allowed to perform this operation.

Example:

```text
Normal user
   ↓
Authenticated ✅
   ↓
Admin endpoint
   ↓
Forbidden ❌
```

So:

```text
401 → Authentication problem

403 → Authorization problem
```

We'll use this distinction heavily in later lessons.

---

# 13. What Makes a Security Test Good?

A good security test should be:

### Specific

```text
User A cannot access User B's Todo.
```

Not:

```text
Security should work.
```

### Reproducible

Another developer should be able to run the test and reproduce the result.

### Automated when possible

Instead of manually checking every release:

```text
Run test suite
    ↓
Security regression tests
    ↓
PASS / FAIL
```

### Based on a real threat

Don't create meaningless tests.

Think:

```text
Threat
 ↓
Attack
 ↓
Expected defense
```

---

# 14. Security Testing Is Also Regression Testing

This is a very important professional concept.

Imagine you fix an IDOR vulnerability today.

Your test:

```text
User A cannot access User B's Todo
```

passes.

Three months later, another developer changes the repository:

```js
Todo.findById(todoId)
```

Oops.

The vulnerability comes back.

But if your security test still exists:

```text
❌ Security test failed
```

The regression is caught before deployment.

Therefore:

> **Every important security bug should ideally become a permanent regression test.**

---

# 15. Our Security Testing Loop

From now on, use this:

```text
1. Identify asset
       ↓
2. Identify attacker
       ↓
3. Identify attack
       ↓
4. Define expected defense
       ↓
5. Write attack test
       ↓
6. Run test
       ↓
7. Fix vulnerability
       ↓
8. Keep regression test
```

For example:

```text
Asset:
User Todo

Attacker:
Authenticated User A

Attack:
Access User B's Todo

Defense:
Ownership check

Test:
GET /todos/B

Result:
403/404

Fix:
Query using userId

Regression:
Keep the test permanently
```

This pattern will become the foundation of the rest of Phase 22.

# 16. Your Backend Security Mindset

Whenever you create a new endpoint, don't stop at:

```text
What is the happy path?
```

Ask these questions:

```text
┌─────────────────────────────────────────┐
│ Security Questions                      │
├─────────────────────────────────────────┤
│ Who can access this?                    │
│ Who cannot access this?                 │
│ What if authentication is missing?      │
│ What if authentication is invalid?     │
│ What if the user changes the ID?        │
│ What fields can the user modify?        │
│ What input can be malicious?            │
│ Can this endpoint be abused repeatedly? │
│ Can sensitive information leak?         │
│ What happens when something fails?      │
└─────────────────────────────────────────┘
```

This should eventually become automatic thinking.
