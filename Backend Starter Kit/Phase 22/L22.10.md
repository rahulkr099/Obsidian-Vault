# Lesson 22.10 — Refresh-Token Attacks 🔄🔐

Your roadmap places **22.10 Refresh-token attacks** immediately after JWT attacks and before cookie attacks.

This lesson is especially important because your authentication architecture already uses:

```text
Access Token
+
Refresh Token
+
Refresh Token Hash
+
Refresh Token Rotation
```

The starter roadmap explicitly teaches refresh-token hashing and rotation as part of authentication.

---

# 1. First: Why Do We Need Refresh Tokens?

An access token should normally be short-lived.

For example:

```text
Access Token
     │
     ├── API requests
     │
     └── expires quickly
```

If it lasts only a short time, stealing it is less useful to an attacker.

But then we have a problem:

```text
Access token expires
       ↓
User would need to login again
```

That's annoying.

So we introduce:

```text
Refresh Token
```

The basic architecture is:

```text
LOGIN
  │
  ├───────────────┐
  ▼               ▼
Access Token   Refresh Token
  │               │
  │               └── HttpOnly cookie
  │
  └── API requests
```

The refresh token is used to obtain a new access token.

---

# 2. Why Refresh Tokens Are Dangerous

An access token might be useful for:

```text
15 minutes
```

while a refresh token might remain valid for:

```text
days / weeks
```

depending on your design.

Therefore:

```text
Stolen access token
      ↓
Short-lived problem

Stolen refresh token
      ↓
Potentially long-lived problem
```

That's why refresh tokens deserve stronger protection.

---

# 3. The Most Important Attack

The fundamental refresh-token attack is:

> **Token theft + replay**

Imagine:

```text
User logs in
    ↓
Refresh Token A
    ↓
Attacker steals it
```

The attacker can now send:

```http
POST /api/v1/auth/refresh
Cookie: refreshToken=A
```

If your server accepts it:

```text
Refresh Token A
      ↓
New Access Token
      ↓
Attacker is authenticated
```

That's a serious problem.

---

# 4. What Is Replay?

Replay means:

> **Using a previously valid credential again.**

Example:

```text
Refresh Token A
      ↓
legitimate refresh
      ↓
new token
```

But the attacker still has:

```text
Refresh Token A
```

and tries:

```text
Refresh Token A
      ↓
refresh again
```

If your system accepts it indefinitely:

```text
🚨 Refresh-token replay
```

---

# 5. Refresh Token Rotation

This is why your architecture includes:

```text
Refresh token rotation
```

The basic idea:

```text
Old Refresh Token
       ↓
    /refresh
       ↓
Invalidate old token
       ↓
Create new refresh token
       ↓
Create new access token
```

So:

```text
Token A
   ↓
refresh
   ↓
Token B
```

After successful rotation:

```text
Token A → ❌ invalid
Token B → ✅ valid
```

This dramatically reduces the usefulness of replaying an old refresh token.

---

# 6. Without Rotation

Imagine:

```text
Login
 ↓
Refresh Token A
```

Then:

```text
Refresh A → Access 1
Refresh A → Access 2
Refresh A → Access 3
Refresh A → Access 4
```

The same refresh token remains valid.

If an attacker steals A:

```text
Attacker
   ↓
Refresh A
   ↓
new access token
```

They may continue doing this until A expires or is revoked.

---

# 7. With Rotation

Now:

```text
Login
 ↓
Refresh A
```

Refresh:

```text
Refresh A
   ↓
invalidate A
   ↓
Refresh B
   ↓
Access B
```

Another refresh:

```text
Refresh B
   ↓
invalidate B
   ↓
Refresh C
```

So:

```text
A → B → C → D
```

Only the current token should remain usable.

---

# 8. Refresh Token Families

This leads to an important concept:

> **Token family**

Imagine a login session creates:

```text
Family F1

Refresh A
   ↓
Refresh B
   ↓
Refresh C
   ↓
Refresh D
```

These tokens are related.

The server can track that relationship.

If an old token appears again:

```text
Refresh A
```

after it has already been rotated:

```text
A → B → C
```

the server can recognize:

```text
🚨 Something is wrong.
```

---

# 9. Refresh Token Reuse Detection

This is one of the strongest defenses.

Suppose:

```text
A → B → C
```

and token A has already been consumed.

Then suddenly:

```text
Refresh A
```

appears again.

That suggests:

```text
Someone may have stolen A.
```

The server can respond by invalidating the associated token family.

Conceptually:

```text
Reuse detected
      ↓
Invalidate token family
      ↓
A ❌
B ❌
C ❌
      ↓
Require fresh authentication
```

This is much stronger than simply returning:

```text
401 Invalid token
```

and doing nothing else.

---

# 10. Why Reuse Detection Is Powerful

Consider this attack:

```text
                    Legitimate User
                         │
                         ▼
                     Token A
                         │
                         ▼
                     Token B

Attacker stole Token A
                         │
                         ▼
                    Replays A
```

The server sees:

```text
Token A was already rotated.
```

Therefore:

```text
A reuse
 ↓
Possible theft
 ↓
Invalidate session/token family
```

Now the attacker can't continue using the stolen chain.

---

# 11. Refresh Token Hashing

Your starter architecture specifically includes:

```text
refreshTokenHash
```

and teaches refresh-token hashing before rotation.

Why hash the refresh token?

Because storing the raw refresh token in MongoDB means:

```text
Database
   ↓
refreshToken = actual secret
```

If your database is compromised, attackers could potentially obtain usable refresh tokens.

Instead:

```text
Refresh Token
      ↓
Hash
      ↓
MongoDB
```

The database stores:

```text
refreshTokenHash
```

rather than the raw token.

---

# 12. Similarity to Password Storage

This is similar to passwords.

You don't store:

```text
password = "myPassword123"
```

You store:

```text
passwordHash = ...
```

Likewise:

```text
Refresh Token
      ↓
hash
      ↓
refreshTokenHash
```

The general principle:

> **Don't store long-lived authentication secrets in plaintext when you can avoid it.**

---

# 13. How Verification Works

Suppose the client sends:

```text
Refresh Token A
```

Your server can:

```text
Received token
      ↓
Hash/verify against stored hash
      ↓
Match?
```

If it doesn't match:

```text
❌ Reject
```

If it matches:

```text
✅ Continue
```

Then you rotate it.

---

# 14. Don't Store the Raw Refresh Token

Avoid:

```js
user.refreshToken = refreshToken;
```

Prefer something like:

```js
user.refreshTokenHash = hashedRefreshToken;
```

The exact implementation depends on your token-storage design.

The important security property is:

```text
MongoDB
   ↓
No raw long-lived refresh credential
```

---

# 15. Refresh Token in an HttpOnly Cookie

Your earlier authentication architecture recommends:

```text
Refresh Token
      ↓
HttpOnly cookie
```

Why?

JavaScript running in the browser cannot directly read an `HttpOnly` cookie.

So an attacker who performs:

```text
document.cookie
```

can't simply read the refresh token stored there.

Conceptually:

```text
Browser
 ├── JavaScript
 │      ❌ cannot read HttpOnly cookie
 │
 └── Browser cookie system
        ✅ sends cookie to server
```

This helps reduce token theft through some XSS scenarios.

It does **not** mean HttpOnly cookies make the application immune to XSS or CSRF.

We'll study cookie attacks in **22.11**.

---

# 16. Refresh Endpoint

A typical endpoint:

```http
POST /api/v1/auth/refresh
```

The flow should look approximately like:

```text
Request
   ↓
Read refresh cookie
   ↓
Is token present?
   │
   ├── NO → 401
   │
   ▼
Verify token
   ↓
Identify session/user
   ↓
Validate token state
   ↓
Check expiration
   ↓
Check reuse/revocation
   ↓
Rotate token
   ↓
Issue new access token
   ↓
Issue new refresh token
```

This endpoint deserves especially strong security testing.

---

# 17. Attack #1 — Missing Refresh Token

Send:

```http
POST /api/v1/auth/refresh
```

without the cookie.

Expected:

```text
401 Unauthorized
```

Not:

```text
500 Internal Server Error
```

and definitely not:

```text
200 OK
```

---

# 18. Attack #2 — Random Refresh Token

Send:

```text
refreshToken=random-garbage
```

Expected:

```text
❌ rejected
```

This tests whether your server actually validates the credential.

---

# 19. Attack #3 — Expired Refresh Token

Create/use an expired token.

Then:

```http
POST /api/v1/auth/refresh
```

Expected:

```text
401
```

An expired refresh token should not magically create a fresh session.

---

# 20. Attack #4 — Tampered Refresh Token

Modify the token.

For example:

```text
Original
A.B.C
```

becomes:

```text
A_modified.B.C
```

Expected:

```text
signature verification
        ↓
❌ reject
```

Same basic principle as access JWTs.

---

# 21. Attack #5 — Reuse an Old Token

This is the important one.

Suppose:

```text
Initial:
Refresh A
```

Then:

```text
POST /refresh with A
       ↓
A invalidated
       ↓
Refresh B created
```

Now deliberately send:

```text
POST /refresh with A
```

again.

Expected behavior:

```text
Reuse detected
      ↓
Reject
      ↓
Potentially invalidate token family
```

The exact family-invalidation strategy depends on your architecture, but the key security property is:

> **A rotated refresh token must not silently remain reusable.**

---

# 22. Attack #6 — Concurrent Refresh

This is a very interesting real-world case.

Suppose the user accidentally sends two refresh requests almost simultaneously:

```text
Request 1 → Refresh A
Request 2 → Refresh A
```

Now both arrive near the same time.

Without careful handling:

```text
Request 1 → accepts A
Request 2 → accepts A
```

You could accidentally issue:

```text
B
C
```

from the same token.

That's a race condition.

---

# 23. Why Concurrency Matters

Imagine:

```text
                Refresh A
                   │
            ┌──────┴──────┐
            ▼             ▼
        Request 1      Request 2
            │             │
            ▼             ▼
        accepts A       accepts A
            │             │
            ▼             ▼
        Refresh B      Refresh C
```

Now your token chain is inconsistent.

A secure implementation needs to consider atomicity and concurrency.

This is one reason refresh-token rotation isn't just:

```js
generateToken();
```

It's a security-sensitive state transition.

---

# 24. Atomic Token Rotation

Conceptually, you want:

```text
Find token/session
AND
verify current token state
AND
replace stored token state
```

as safely as possible.

Think:

```text
Old token is valid
      ↓
Atomically replace it
      ↓
Old token becomes invalid
      ↓
New token becomes valid
```

This becomes especially important when your backend is running multiple Node instances.

---

# 25. Multi-Server Environment

Imagine:

```text
                Load Balancer
                 /        \
                ▼          ▼
             Node A      Node B
                │          │
                └────┬─────┘
                     ▼
                  MongoDB
```

A refresh request might hit:

```text
Request 1 → Node A
Request 2 → Node B
```

Both need to understand the same refresh-token state.

That's why server-side token state is important for secure rotation.

---

# 26. Stateful Refresh Tokens

This is an important architecture distinction.

Access JWT:

```text
Mostly stateless
```

Refresh token:

```text
Can have server-side state
```

For example:

```text
User/session document
       │
       ├── refreshTokenHash
       ├── tokenFamily
       ├── expiresAt
       └── revokedAt
```

This lets your backend revoke and track refresh sessions.

---

# 27. One Refresh Token Per User?

A simple design might store:

```text
User
 └── refreshTokenHash
```

But this has a limitation.

Imagine the user logs in from:

```text
Laptop
Phone
Tablet
```

You may want:

```text
Laptop → Session A
Phone  → Session B
Tablet → Session C
```

rather than one refresh token state for the entire user.

A more scalable architecture uses a separate session/refresh-token collection.

For example:

```text
sessions
├── userId
├── tokenHash
├── familyId
├── createdAt
├── expiresAt
├── revokedAt
└── metadata
```

This is an architectural improvement you should keep in mind for real applications.

---

# 28. Session Revocation

Suppose the user clicks:

```text
Logout
```

You should invalidate the refresh session.

Then:

```text
Old refresh token
      ↓
/refresh
      ↓
❌ rejected
```

Similarly, you may want to revoke sessions when:

```text
Password changes
Password reset
Account is compromised
Admin disables account
Suspicious reuse detected
```

---

# 29. "Logout Everywhere"

A useful feature:

```text
Logout all devices
```

Conceptually:

```text
User
 ├── Session A
 ├── Session B
 ├── Session C
 └── Session D
```

Then:

```text
Logout everywhere
       ↓
revoke all sessions
```

Now:

```text
A ❌
B ❌
C ❌
D ❌
```

This is especially useful after suspected account compromise.

---

# 30. Password Change and Refresh Tokens

Suppose an attacker has:

```text
Refresh Token A
```

The legitimate user changes their password.

Should A remain valid?

Often, a security-conscious system will invalidate existing refresh sessions.

Conceptually:

```text
Password changed
      ↓
Revoke refresh sessions
      ↓
Old refresh tokens
      ↓
❌
```

Then the user logs in again.

This limits the damage from previously stolen credentials.

---

# 31. Refresh Token Theft Scenario

Let's walk through a realistic attack.

```text
User logs in
     ↓
Refresh Token A
     ↓
Attacker steals A
```

User refreshes:

```text
A → B
```

Now A should be invalid.

Attacker later sends:

```text
A → /refresh
```

Your server detects:

```text
A was already rotated
```

Therefore:

```text
🚨 Possible token theft
```

Then:

```text
revoke token family
```

This can force the legitimate user to authenticate again.

It's inconvenient, but much safer than allowing the attacker to continue.

---

# 32. Why Reuse Detection Can Log the User Out

This may seem surprising.

Suppose:

```text
User has B
Attacker has A
```

Attacker replays A.

The server can't always know with certainty:

```text
Who has A?
```

So it treats the reuse as a security signal.

Possible response:

```text
Invalidate family
```

Then:

```text
User B → ❌
Attacker A → ❌
```

The legitimate user has to log in again.

This is a deliberate security tradeoff.

---

# 33. Refresh Token Rotation Is Not Magic

Rotation helps with replay, but it doesn't solve everything.

Consider:

```text
Attacker steals newest refresh token B
```

before the user uses it.

The attacker can potentially use B normally.

Therefore you still need:

```text
Secure storage
HttpOnly cookie
HTTPS
Shorter refresh lifetime where appropriate
Rotation
Reuse detection
Revocation
Session management
```

Security is layered.

---

# 34. Refresh Token vs Access Token

Keep this table in your mind:

||Access Token|Refresh Token|
|---|---|---|
|Lifetime|Short|Longer|
|Used for|API requests|Obtain new access token|
|Sent frequently|Yes|No|
|Storage|Often memory/client mechanism|Secure cookie/session mechanism|
|Server state|Often minimal|Often useful|
|Rotation|Usually not needed each request|Important|
|Theft impact|Limited by short expiry|Potentially serious|

---

# 35. Don't Put Refresh Tokens in LocalStorage

For browser-based applications, storing long-lived refresh credentials in:

```text
localStorage
```

can expose them to JavaScript.

If malicious JavaScript executes in the page:

```js
localStorage.getItem("refreshToken")
```

could potentially expose the token.

Your roadmap instead teaches:

```text
Refresh Token
 ↓
HttpOnly cookie
```

which is a stronger browser-storage pattern.

---

# 36. But HttpOnly Does NOT Solve Everything

An HttpOnly cookie prevents JavaScript from directly reading the cookie.

But the browser can still automatically send cookies with requests.

Therefore another concern appears:

```text
CSRF
```

For example:

```text
Malicious website
      ↓
browser
      ↓
your refresh endpoint
      ↓
cookie automatically attached
```

This is why your next lessons include:

```text
22.11 Cookie attacks
22.12 CORS attacks
22.13 CSRF fundamentals
```

We'll connect these topics together.

# 38. Attack: Refresh Endpoint Without Rate Limiting

An attacker may repeatedly hit:

```http
POST /api/v1/auth/refresh
```

Even though the token is invalid.

Your server should avoid allowing unlimited expensive authentication operations.

This connects directly with:

```text
22.8 Rate-limit testing
```

The security model should therefore be:

```text
Refresh endpoint
      ↓
Rate limit
      ↓
Validate token
      ↓
Rotate
```

---

# 39. Attack: User Enumeration

Be careful with refresh/logout responses too.

Don't accidentally reveal unnecessary information such as:

```text
"This refresh token belongs to user Rahul but is expired."
```

Prefer controlled authentication errors.

Security responses should reveal only what the client needs.

---

# 40. Attack: Token Leakage in Logs

Never do this:

```js
logger.info({
    refreshToken
});
```

or:

```js
console.log(req.cookies);
```

because your logs might now contain authentication secrets.

Remember your Phase 19 security lesson:

```text
Sensitive data in logs
      ↓
🚨 security problem
```

Your roadmap explicitly includes sensitive-data handling in logging.

---

# 41. Attack: Refresh Token in Error Messages

Don't return:

```json
{
  "error": "Invalid refresh token: eyJhbGci..."
}
```

The token should never appear in:

```text
response
logs
error tracking
analytics
```

unless there is an exceptional, carefully controlled security-debugging reason.

# 49. The Key Security Principle

The most important idea from this lesson is:

> **A refresh token should be treated like a long-lived authentication credential, not like an ordinary JWT.**

Therefore:

```text
Protect it
      +
Hash stored representation
      +
Rotate it
      +
Detect reuse
      +
Revoke it
      +
Don't log it
      +
Secure its transport
```
