# Lesson 22.11 — Cookie Attacks 🍪🔐

Your Phase 22 roadmap defines **22.11 as Cookie attacks**, followed by CORS attacks and CSRF fundamentals.

This lesson connects directly with the authentication architecture you've already learned:

```text
Access Token
    ↓
Authorization header

Refresh Token
    ↓
HttpOnly cookie
```

Your starter architecture specifically recommends the refresh token in an **HttpOnly cookie**.

The goal today is to understand **how cookies can become an attack surface and how to test your implementation**.

---

# 1. First: What Is a Cookie?

A cookie is data that a server asks the browser to store.

For example:

```http
Set-Cookie: sessionId=abc123
```

The browser stores it.

Later, when appropriate, the browser automatically sends:

```http
Cookie: sessionId=abc123
```

So the important difference is:

```text
Authorization header
    ↓
Your frontend code usually attaches it

Cookie
    ↓
Browser can automatically attach it
```

That automatic behavior is extremely useful.

It is also where several security problems begin.

---

# 2. Why Do We Use Cookies for Refresh Tokens?

Your authentication design uses:

```text
Access Token
    ↓
Authorization: Bearer <token>
```

and:

```text
Refresh Token
    ↓
HttpOnly cookie
```

The reason for the cookie is mainly to make the long-lived refresh credential harder for JavaScript to steal.

For example:

```text
JavaScript
    ↓
document.cookie
    ↓
HttpOnly refresh cookie
    ↓
❌ inaccessible
```

That's good.

But:

```text
Browser
    ↓
HTTP request
    ↓
Cookie
    ↓
✅ automatically sent when cookie rules allow it
```

That's the tradeoff.

---

# 3. The Four Cookie Security Controls You Must Know

For authentication cookies, remember these:

```text
HttpOnly
Secure
SameSite
Domain / Path
```

The first three are especially important.

Think:

```text
HttpOnly → Who can read it?
Secure   → Where can it travel?
SameSite → When can it travel cross-site?
```

That's a very useful mental shortcut.

---

# 4. Attack #1 — Missing `HttpOnly`

Suppose you create:

```http
Set-Cookie: refreshToken=abc123
```

without:

```text
HttpOnly
```

Then JavaScript may be able to access it:

```js
document.cookie
```

If malicious JavaScript executes in your application:

```text
XSS
 ↓
JavaScript
 ↓
document.cookie
 ↓
refresh token
 ↓
🚨 stolen
```

That's why an authentication cookie should generally use:

```http
HttpOnly
```

---

# 5. What `HttpOnly` Actually Does

With:

```http
Set-Cookie: refreshToken=abc123; HttpOnly
```

browser JavaScript cannot directly access that cookie.

So:

```js
document.cookie
```

doesn't expose the HttpOnly cookie.

But remember:

> **HttpOnly does not prevent the browser from sending the cookie to the server.**

That's important.

It protects against **direct JavaScript cookie reading**, not every browser-based attack.

---

# 6. HttpOnly Does NOT Stop XSS

Suppose your application has XSS.

The attacker may not be able to do:

```js
document.cookie
```

to steal the refresh token.

But malicious JavaScript can potentially make requests to your application **from the victim's browser**.

For example:

```text
Malicious JS
    ↓
POST /api/v1/account/change-email
    ↓
Browser automatically includes cookies
    ↓
Server sees authenticated request
```

So:

```text
HttpOnly
    ≠
XSS protection
```

This distinction is extremely important.

---

# 7. Attack #2 — Missing `Secure`

Consider:

```http
Set-Cookie: refreshToken=abc123; HttpOnly
```

but without:

```text
Secure
```

The browser may send the cookie over a non-HTTPS connection when cookie rules allow it.

That's dangerous for sensitive authentication credentials.

With:

```http
Set-Cookie: refreshToken=abc123; HttpOnly; Secure
```

the browser restricts transmission to secure HTTPS connections.

Mental model:

```text
Secure
   ↓
HTTPS only
```

For production authentication cookies, this is an important requirement.

---

# 8. Attack #3 — Missing `SameSite`

Now we reach one of the most important cookie security concepts.

Suppose your application is:

```text
https://myapp.example
```

and an attacker controls:

```text
https://evil.example
```

The browser may have your authentication cookie stored.

The question becomes:

> Should that cookie be sent when a request originates from another site?

That's what `SameSite` helps control.

---

# 9. SameSite Values

The main values you'll encounter are:

```text
Strict
Lax
None
```

Think of them as levels of cross-site cookie behavior.

---

# 10. `SameSite=Strict`

Conceptually:

```http
SameSite=Strict
```

means:

> Be very restrictive about sending this cookie in cross-site situations.

This provides strong CSRF protection for many cookie-based flows.

But there can be usability implications depending on how your application works.

---

# 11. `SameSite=Lax`

```http
SameSite=Lax
```

allows some cross-site behavior while restricting many cross-site state-changing requests.

It's often a practical default for many cookies, but the correct setting depends on your application architecture.

Don't blindly choose it because:

> "Lax is secure."

Security configuration must match the actual application flow.

---

# 12. `SameSite=None`

This is the interesting one.

If you use:

```http
SameSite=None
```

the browser allows cross-site cookie sending under the relevant cookie rules.

But modern browsers require:

```text
Secure
```

with `SameSite=None`.

So:

```text
SameSite=None
+
Secure
```

go together.

This setting may be needed for certain cross-site architectures, but it increases your responsibility for CSRF defenses.

---

# 13. The Cookie Security Triangle

For authentication cookies, memorize:

```text
             Cookie
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
  HttpOnly    Secure    SameSite
      │         │         │
      ▼         ▼         ▼
 JS access   HTTPS     Cross-site
 protection  only      control
```

This is one of the most useful diagrams from this lesson.

---

# 14. Attack #4 — Cookie Theft Through XSS

Consider an insecure cookie:

```http
Set-Cookie: refreshToken=abc123
```

An attacker finds XSS.

They run:

```js
document.cookie
```

and potentially obtain:

```text
refreshToken=abc123
```

Now:

```text
XSS
 ↓
Cookie theft
 ↓
Refresh-token theft
 ↓
Account compromise
```

This is why **22.10 Refresh-token attacks** and **22.11 Cookie attacks** are connected.

---

# 15. Attack #5 — Cookie Injection

Cookie injection occurs when an attacker can influence cookie values or cause malicious cookies to be stored.

Conceptually:

```text
Attacker
   ↓
malicious cookie value
   ↓
Browser
   ↓
Your application
   ↓
Trusts cookie
```

This can become dangerous if your backend assumes:

```text
"Whatever value came from the cookie must be trustworthy."
```

It isn't.

A cookie is **client-controlled input**.

Even if the browser created it automatically, your server must still validate what it receives.

---

# 16. Never Trust Cookie Contents

Suppose:

```http
Cookie: role=admin
```

Your backend should never think:

```js
if (req.cookies.role === "admin") {
    allowAdmin();
}
```

🚨 Bad architecture.

The client controls cookies.

Instead, privileged identity should come from a trusted authentication mechanism:

```text
Cookie
 ↓
Refresh credential
 ↓
Server verification
 ↓
Trusted session/user
 ↓
Authorization
```

---

# 17. Attack #6 — Session Fixation

Session fixation is an important session-related attack.

The basic idea is:

```text
Attacker obtains/controls a session identifier
        ↓
Victim is tricked into using it
        ↓
Victim authenticates
        ↓
Attacker attempts to reuse that session
```

The key defense is:

> **Rotate the session identifier/token after authentication or privilege changes.**

For example:

```text
Before login:
Session A

Successful login:
Session B
```

rather than continuing with the same security identifier.

---

# 18. Why Rotation Matters

Think about:

```text
Before authentication
       ↓
anonymous session
       ↓
LOGIN
       ↓
authenticated session
```

The security identity has changed.

Therefore, keeping exactly the same session identifier can create unnecessary risk.

A secure design can rotate the identifier:

```text
Session A
   ↓
LOGIN
   ↓
Session B
```

This concept is related to the refresh-token rotation you learned in 22.10, but they are not exactly the same mechanism.

---

# 19. Attack #7 — Session Cookie Not Cleared on Logout

Suppose:

```text
Login
 ↓
Session cookie
```

Then:

```text
Logout
```

but the server doesn't invalidate the session.

The browser may still have:

```text
sessionId=abc123
```

and the server may still accept it.

That's a broken logout flow.

A secure logout should invalidate the relevant server-side session/credential and clear the cookie when appropriate.

---

# 20. Cookie Clearing

A common mistake is thinking:

```js
res.clearCookie("refreshToken");
```

alone means the session is completely gone.

Not necessarily.

You should also invalidate the corresponding server-side authentication state.

Think:

```text
Logout
 ├── Clear browser cookie
 └── Revoke/invalidate server credential
```

Both sides matter.

---

# 21. Browser Cookie vs Server Session

This is a very important distinction.

There are two pieces:

```text
Browser
    ↓
Cookie
```

and:

```text
Server
    ↓
Session / token state
```

Clearing the first doesn't automatically invalidate the second.

For example:

```text
Browser cookie removed
      ↓
Server still accepts old refresh token
      ↓
Another copy of the token can still work
```

That's why logout must revoke the actual credential/session.

---

# 22. Attack #8 — Cookie Domain Misconfiguration

Cookies can have a `Domain` attribute.

For example:

```text
Domain=example.com
```

This can affect which hosts receive the cookie.

A broader cookie scope can increase exposure.

Imagine:

```text
example.com
├── app.example.com
├── api.example.com
└── old.example.com
```

A broadly scoped cookie may be available across multiple subdomains.

If one subdomain is compromised, that can create additional risk depending on the cookie and application architecture.

---

# 23. Prefer Narrow Cookie Scope

Where possible, avoid unnecessarily broad:

```text
Domain
```

and:

```text
Path
```

configuration.

Think:

```text
Only the hosts and paths that actually need the credential
```

should receive it.

This follows the broader security principle:

> **Least privilege.**

---

# 24. Attack #9 — Cookie Path Misconfiguration

Suppose your cookie is:

```text
Path=/
```

It may be sent to many application routes.

If your refresh endpoint is:

```text
/api/v1/auth/refresh
```

you can consider whether the cookie needs to be available more broadly.

A narrower path can reduce unnecessary exposure.

For example, conceptually:

```text
Path=/api/v1/auth
```

instead of:

```text
Path=/
```

But don't blindly narrow the path without understanding your application flow.

---

# 25. Attack #10 — Sensitive Data in Cookies

Don't put arbitrary sensitive information into cookies.

Bad:

```http
Set-Cookie: password=myPassword123
```

or:

```http
Set-Cookie: creditCard=...
```

Remember:

```text
Cookie
   ↓
stored on client
   ↓
sent with requests
```

Cookies are not secure storage.

They are a browser transport/storage mechanism.

---

# 26. Cookie ≠ Encryption

This is similar to the JWT lesson.

A cookie doesn't automatically encrypt your data.

For example:

```http
Set-Cookie: userRole=admin
```

doesn't make:

```text
admin
```

secret.

And if the value itself is sensitive, you have created a data-exposure problem.

---

# 27. Attack #11 — Refresh Token Cookie Without Expiration

Suppose:

```http
Set-Cookie: refreshToken=abc123
```

with no appropriate lifetime.

Depending on the cookie type, it may become a session cookie.

That's not automatically insecure, but your authentication architecture should intentionally define:

```text
cookie lifetime
+
refresh-token lifetime
```

Don't let the browser's default behavior accidentally determine your authentication policy.

---

# 28. Cookie Lifetime vs Token Lifetime

These are related but different.

For example:

```text
Refresh token:
7 days
```

Cookie:

```text
7 days
```

The effective security behavior should be intentionally designed.

If:

```text
Cookie = 30 days
Token = 7 days
```

the cookie may still exist after the token expires, but the server should reject the expired token.

Conversely:

```text
Cookie = 2 days
Token = 7 days
```

the credential may remain valid server-side while the browser no longer sends it.

The important point:

> **Don't confuse cookie expiration with authentication-token validity.**

---

# 29. Attack #12 — Cookie Over HTTP

Imagine:

```text
http://myapp.example
```

instead of:

```text
https://myapp.example
```

A sensitive authentication cookie traveling without HTTPS can potentially be exposed in transit.

This is why production authentication should use:

```text
HTTPS
+
Secure cookies
```

Your Phase 24 roadmap separately covers HTTPS and production cookie configuration.

---

# 30. Attack #13 — Cross-Site Request With Cookies

Now let's connect cookies to CSRF.

Suppose the user is logged into:

```text
https://bank.example
```

Their browser stores:

```text
session=abc123
```

Then they visit:

```text
https://evil.example
```

If the browser sends the bank cookie with a cross-site request, the attacker may be able to cause an authenticated action.

Conceptually:

```text
evil.example
     ↓
browser
     ↓
request to bank.example
     ↓
browser attaches cookie
     ↓
bank sees authenticated request
```

That's the foundation of **CSRF**.

Your roadmap intentionally teaches CSRF in 22.13 after cookies and CORS.

---

# 31. Why HttpOnly Doesn't Stop CSRF

This is worth repeating.

`HttpOnly` prevents:

```text
JavaScript → read cookie
```

But CSRF is about:

```text
Browser → automatically send cookie
```

So:

```text
HttpOnly
    ↓
helps against cookie theft via JS

SameSite / CSRF defenses
    ↓
help against cross-site request abuse
```

Different threats.

---

# 32. Cookie Attacks vs CSRF

Think of them separately:

### Cookie theft

```text
Attacker
   ↓
gets cookie value
```

### CSRF

```text
Attacker
   ↓
causes victim browser to make request
   ↓
browser sends cookie automatically
```

The attacker may never learn the cookie value during CSRF.

That's why:

```text
Cookie security
+
CSRF protection
```

must both exist.

---

# 33. Attack #14 — Overly Broad SameSite Configuration

Suppose you use:

```text
SameSite=None
```

because your frontend/backend are on different sites.

Now cross-site cookies are allowed.

That can be correct for some architectures, but you need additional protection for state-changing requests.

For example:

```text
SameSite=None
      ↓
cross-site cookie possible
      ↓
CSRF protection becomes more important
```

Don't configure `None` casually.

---

# 34. `SameSite` and Frontend/API Architecture

You might have:

```text
Frontend:
https://app.example.com

API:
https://api.example.com
```

These are different **origins**, but they are generally the same **site** under the browser's site model.

That's why you should not confuse:

```text
origin
```

with:

```text
site
```

This distinction becomes extremely important when we study CORS in 22.12.

---

# 35. Cookie + CORS

Suppose your frontend calls:

```text
https://api.example.com
```

from:

```text
https://app.example.com
```

and uses cookies.

The frontend request may need:

```js
fetch(url, {
    credentials: "include"
});
```

And the backend needs an appropriate CORS configuration.

Conceptually:

```text
Frontend
   ↓
credentials: include
   ↓
Browser
   ↓
Cookie
   ↓
API
```

The backend must explicitly allow the trusted origin rather than blindly allowing every origin.

We'll examine this in **22.12**.

---

# 36. Dangerous CORS + Cookie Combination

A dangerous configuration is essentially:

```text
Allow every origin
+
Allow credentials
```

For credentialed browser requests, you must not build a permissive policy that effectively trusts arbitrary websites.

Think:

```text
Any website
    ↓
authenticated API
    ↓
🚨 dangerous
```

Your CORS policy should have an explicit trust boundary.

---

# 37. Attack #15 — Cookie Tossing

Cookie tossing is a more advanced cookie attack involving attackers influencing cookies, often through subdomain/domain behavior.

Imagine:

```text
attacker-controlled.example.com
```

and:

```text
api.example.com
```

If the application accepts a broadly scoped cookie:

```text
Domain=.example.com
```

an attacker-controlled subdomain may potentially interfere with cookie behavior depending on the application and browser rules.

The general lesson is:

> **Avoid unnecessarily broad cookie domain scope, especially for authentication credentials.**

---

# 38. Cookie Prefixes

Browsers support special cookie prefixes such as:

```text
__Secure-
__Host-
```

These can add useful restrictions.

For example:

```text
__Secure-refreshToken
```

requires secure transmission.

And:

```text
__Host-refreshToken
```

has stricter requirements, including:

```text
Secure
Path=/
No Domain attribute
```

These prefixes can make cookie configuration safer by enforcing browser-level constraints.

---

# 39. Why `__Host-` Can Be Useful

A `__Host-` cookie cannot be scoped to an arbitrary domain.

That helps reduce certain subdomain-related risks.

Conceptually:

```text
__Host-refreshToken
       ↓
Secure
       +
Path=/
       +
No Domain
```

This is a nice hardening technique for sensitive authentication cookies when your architecture allows it.

---

# 40. Attack #16 — Cookie Name Collisions

Suppose your application expects:

```text
refreshToken=ABC
```

but the browser sends multiple cookies with the same name under different paths/domains.

Cookie parsing behavior can become confusing.

This is another reason to avoid unnecessarily complicated cookie scopes.

Keep your authentication cookie configuration simple:

```text
one clear name
one clear scope
one clear path
```

whenever possible.

---

# 41. Don't Build Authorization From Cookies Directly

Bad:

```js
if (req.cookies.role === "admin") {
    return next();
}
```

Better:

```text
Cookie
 ↓
Authentication credential
 ↓
Verify
 ↓
Trusted identity
 ↓
Authorization
```

Cookies should carry the authentication mechanism, not become an untrusted authorization database.

---

# 42. Testing Cookie Security

Now let's turn this into actual security tests.

---

## Test 1 — HttpOnly

After login/refresh, inspect the `Set-Cookie` header.

You want something conceptually like:

```text
refreshToken=...;
HttpOnly;
Secure;
SameSite=...
```

Verify:

```text
HttpOnly → present
```

---

## Test 2 — Secure

In the appropriate production/test configuration:

```text
Secure → present
```

Be careful when testing locally over plain HTTP because development and production cookie behavior may intentionally differ.

---

## Test 3 — SameSite

Verify the cookie has the intended policy:

```text
SameSite=Strict
```

or:

```text
SameSite=Lax
```

or, where genuinely required:

```text
SameSite=None; Secure
```

Don't merely test that a value exists. Test that it matches your architecture.

---

# 43. Test 4 — Logout

Flow:

```text
Login
 ↓
Refresh cookie created
 ↓
Logout
 ↓
Cookie cleared
 ↓
Old refresh credential rejected
```

You want both:

```text
Browser-side removal
+
Server-side invalidation
```

---

# 44. Test 5 — Old Refresh Token

From the previous lesson:

```text
A → B
```

Then:

```text
A → /refresh
```

Expected:

```text
401
```

This tests the combination of:

```text
Cookie
+
Refresh-token rotation
```

---

# 45. Test 6 — Missing Cookie

Request:

```http
POST /api/v1/auth/refresh
```

without the cookie.

Expected:

```text
401
```

Not:

```text
500
```

---

# 46. Test 7 — Malicious Cookie Value

Send:

```http
Cookie: refreshToken=garbage
```

Expected:

```text
401
```

The server should never crash because a cookie contains malformed input.

---

# 47. Test 8 — Cookie Injection

Attempt to provide unexpected cookie values.

For example:

```http
Cookie: role=admin
```

Then call an admin endpoint.

Expected:

```text
403
```

if the authenticated user isn't an admin.

This verifies that authorization isn't trusting arbitrary cookies.

---

# 48. Test 9 — Cross-Site Behavior

This is more appropriate once you implement the CSRF/CORS test suite.

You want to verify:

```text
Trusted frontend
     ↓
authenticated request
     ↓
works

Untrusted website
     ↓
attempted authenticated state-changing request
     ↓
blocked
```

The exact test depends heavily on your cookie and CORS architecture.

---

# 49. Supertest Example

You can inspect cookies from a response:

```js
const response = await request(app)
    .post("/api/v1/auth/login")
    .send({
        email,
        password
    });

const cookies = response.headers["set-cookie"];
```

Then assert that your refresh cookie has the expected properties.

For example, conceptually:

```js
expect(cookies.join(";")).toMatch(/HttpOnly/i);
```

You can also test:

```text
Secure
SameSite
Path
```

depending on your environment.

---

# 50. A Better Security Test

Instead of only checking:

```js
expect(response.statusCode).toBe(200);
```

test the actual security contract:

```text
Login
 ↓
Set-Cookie
 ↓
HttpOnly?
Secure?
SameSite?
Path?
 ↓
Yes
```

That's the difference between:

```text
functional testing
```

and:

```text
security testing
```

---

# 51. Production Cookie Example

Conceptually, a sensitive refresh cookie might look like:

```http
Set-Cookie:
__Host-refreshToken=<value>;
Path=/;
HttpOnly;
Secure;
SameSite=Lax
```

Whether this exact configuration is appropriate depends on your frontend/API deployment architecture.

The important part is understanding **why each attribute exists**.

---

# 52. Security Attribute Cheat Sheet

|Attribute|Main purpose|
|---|---|
|`HttpOnly`|Prevent JavaScript from reading cookie|
|`Secure`|Send cookie only over HTTPS|
|`SameSite`|Control cross-site cookie sending|
|`Domain`|Control host scope|
|`Path`|Control path scope|
|`Max-Age`|Cookie lifetime|
|`Expires`|Cookie expiration time|

# 55. Cookie Attack Checklist

When testing your backend, ask:

```text
[ ] Is the refresh cookie HttpOnly?
[ ] Is it Secure in production?
[ ] Is SameSite intentionally configured?
[ ] Is the cookie domain as narrow as possible?
[ ] Is the cookie path appropriate?
[ ] Is the lifetime intentional?
[ ] Are cookies cleared on logout?
[ ] Is the server-side credential revoked on logout?
[ ] Can arbitrary cookie values influence authorization?
[ ] Are refresh tokens absent from logs?
[ ] Can old refresh tokens still be replayed?
[ ] Are session identifiers rotated after authentication?
[ ] Is CSRF protection appropriate for the cookie design?
[ ] Is CORS configured consistently with credentialed requests?
```

# 🧠 Final Mental Model

Remember these three words:

```text
HttpOnly
   ↓
JavaScript can't read it

Secure
   ↓
HTTPS only

SameSite
   ↓
Controls cross-site sending
```

And then remember the deeper principle:

> **A cookie is client-controlled input and an automatically transported credential—not a trusted source of authorization.**

For your refresh-token architecture:

```text
Refresh Token
      ↓
HttpOnly
      +
Secure
      +
SameSite
      +
Server-side hashing
      +
Rotation
      +
Reuse detection
      +
Revocation
      +
CSRF protection
```

That's the security chain we are building across **22.10 → 22.11 → 22.12 → 22.13**. The roadmap deliberately puts cookie attacks before CORS and CSRF because these three topics are tightly connected.
