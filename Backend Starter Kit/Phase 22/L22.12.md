# Lesson 22.12 — CORS Attacks 🌐🔐

Your Phase 22 roadmap defines **22.12 as CORS attacks**, directly after Cookie attacks and before CSRF fundamentals.

This ordering is important:

```text
22.10 Refresh-token attacks
        ↓
22.11 Cookie attacks
        ↓
22.12 CORS attacks
        ↓
22.13 CSRF fundamentals
```

These topics are closely connected because browser security controls determine **which website is allowed to communicate with your API and whether credentials such as cookies can accompany that communication**.

---

# 1. What Is CORS?

CORS means:

> **Cross-Origin Resource Sharing**

Before understanding attacks, you need to understand what problem CORS solves.

Imagine your frontend runs at:

```text
http://localhost:5173
```

and your backend runs at:

```text
http://localhost:5000
```

These are different **origins**.

Your React application wants to call:

```http
GET http://localhost:5000/api/v1/users/me
```

The browser applies its same-origin security rules.

CORS is the mechanism that allows the backend to tell the browser:

> "Requests from this particular origin are allowed."

---

# 2. What Is an Origin?

An origin consists of:

```text
scheme + host + port
```

For example:

```text
https://example.com:443
```

has:

```text
scheme = https
host   = example.com
port   = 443
```

Changing any of these can create a different origin.

---

# 3. Examples

These are different origins:

```text
https://example.com
https://api.example.com
```

because the hosts differ.

Also:

```text
http://example.com
https://example.com
```

because the schemes differ.

And:

```text
https://example.com:443
https://example.com:8443
```

because the ports differ.

---

# 4. Origin vs Site

This distinction caused a lot of confusion in the previous cookie lesson.

### Origin

```text
scheme + host + port
```

### Site

A broader browser concept used by mechanisms such as `SameSite` cookies.

So:

```text
https://app.example.com
https://api.example.com
```

are:

```text
different origins
```

but can belong to the same site.

Remember:

```text
CORS → origin
SameSite → site
```

That's an excellent mental shortcut.

---

# 5. Same-Origin Policy

Browsers have a security mechanism called the:

> **Same-Origin Policy (SOP)**

It prevents arbitrary websites from freely reading data from other origins.

Imagine:

```text
evil.example
     ↓
tries to read
     ↓
api.example
```

The browser doesn't simply say:

```text
"Sure, here's the data."
```

Instead, the browser enforces origin-based restrictions.

CORS provides a controlled way for the target server to say:

```text
"This origin is allowed."
```

---

# 6. CORS Is Primarily a Browser Security Mechanism

This is one of the most important things to understand.

CORS is primarily enforced by **browsers**.

For example:

```text
React browser app
       ↓
Browser CORS enforcement
       ↓
API
```

But:

```text
Node script
curl
Postman
server-to-server request
```

doesn't behave exactly like a browser.

Therefore, this:

```bash
curl https://api.example.com/users
```

isn't a meaningful way to prove that your CORS policy protects a browser application.

---

# 7. What Does the Server Return?

Suppose your frontend is:

```text
https://app.example.com
```

It sends:

```http
GET /api/users
Origin: https://app.example.com
```

The backend may respond with:

```http
Access-Control-Allow-Origin: https://app.example.com
```

The browser sees:

```text
Origin matches allowed origin
        ↓
✅ allow JavaScript to read response
```

---

# 8. What If the Origin Isn't Allowed?

Suppose the request comes from:

```text
https://evil.example
```

but the server only allows:

```text
https://app.example.com
```

The response doesn't grant the malicious origin access.

The browser prevents the attacker's JavaScript from reading the protected response.

Conceptually:

```text
evil.example
     ↓
API
     ↓
No permission for evil.example
     ↓
🚫 Browser blocks response access
```

---

# 9. Important: CORS Does Not Stop the Request

This is a common misconception.

CORS isn't necessarily:

```text
Request → blocked before reaching server
```

Instead, for many cross-origin requests:

```text
Browser
   ↓
Request
   ↓
Server
   ↓
Response
   ↓
Browser checks CORS
   ↓
JavaScript allowed to read?
```

So:

```text
CORS
≠
firewall
```

The server still needs authentication and authorization.

---

# 10. CORS Does Not Replace Authentication

Suppose:

```text
GET /api/v1/admin/users
```

is protected by:

```text
authMiddleware
```

You still need:

```text
Authentication
+
Authorization
```

even if your CORS policy is perfect.

Think:

```text
CORS
 ↓
Which browser origins can access the response?

Authentication
 ↓
Who is this?

Authorization
 ↓
What can they do?
```

Different questions.

---

# 11. Attack #1 — `Access-Control-Allow-Origin: *`

A common configuration is:

```http
Access-Control-Allow-Origin: *
```

This means:

```text
Any origin
```

can access non-credentialed cross-origin responses where the browser's CORS rules permit it.

For a public API, this may be perfectly reasonable.

For sensitive authenticated APIs, you need to think carefully.

---

# 12. Why `*` Becomes Dangerous With Credentials

Suppose your API uses:

```text
HttpOnly refresh cookie
```

and you configure CORS carelessly.

You might think:

```text
Allow everyone
+
Allow credentials
```

is convenient.

It isn't a safe authentication architecture.

For credentialed CORS, browsers require a specific allowed origin rather than:

```text
*
```

for `Access-Control-Allow-Origin`.

The broader principle is:

> **Don't combine broad origin trust with credentialed authentication.**

---

# 13. Credentials

Browsers can make credentialed cross-origin requests.

For example:

```js
fetch("https://api.example.com/me", {
    credentials: "include"
});
```

This tells the browser:

> Include credentials according to the browser's cookie rules.

This is important for your architecture because your refresh token is stored in an HttpOnly cookie.

---

# 14. Credentialed CORS Flow

Imagine:

```text
Frontend
https://app.example.com
```

calls:

```text
API
https://api.example.com
```

with:

```js
credentials: "include"
```

The flow becomes:

```text
React
  ↓
fetch(..., credentials: "include")
  ↓
Browser
  ↓
Cookie rules
  ↓
CORS rules
  ↓
API
```

Now multiple security systems interact:

```text
Cookies
+
SameSite
+
CORS
+
CSRF
```

This is why these lessons are taught together.

---

# 15. Attack #2 — Reflecting the `Origin`

Here's a dangerous pattern:

```js
app.use(cors({
    origin: true
}));
```

or manually:

```js
res.setHeader(
    "Access-Control-Allow-Origin",
    req.headers.origin
);
```

without validating that origin first.

Suppose:

```text
Origin: https://evil.example
```

The server responds:

```text
Access-Control-Allow-Origin: https://evil.example
```

You've effectively said:

> "Whatever origin asks, I trust."

🚨 That's not an access-control policy.

---

# 16. The Dangerous Pattern

Conceptually:

```text
Request:
Origin: evil.example

Server:
Access-Control-Allow-Origin: <whatever-request-sent>
```

Result:

```text
evil.example
     ↓
"Am I trusted?"
     ↓
Server:
"Yes."
```

That's a serious CORS misconfiguration.

---

# 17. Better: Explicit Allowlist

Instead, define:

```js
const allowedOrigins = [
    "http://localhost:5173",
    "https://app.example.com"
];
```

Then:

```text
Incoming Origin
       ↓
Is it in allowlist?
       │
   ┌───┴───┐
  YES      NO
   │        │
   ▼        ▼
 Allow    Reject
```

This follows the principle:

> **Explicit trust is better than implicit trust.**

---

# 18. Attack #3 — Weak Origin Validation

Be careful with string matching.

Suppose the legitimate origin is:

```text
https://example.com
```

and you write:

```js
origin.includes("example.com")
```

An attacker could potentially use something like:

```text
https://example.com.evil.example
```

which contains the string.

Your validation might accidentally say:

```text
"Looks like example.com!"
```

when it isn't.

---

# 19. Don't Use Naive String Matching

Avoid security checks such as:

```js
origin.includes("example.com")
```

or:

```js
origin.endsWith("example.com")
```

without carefully parsing and validating the origin.

You want to compare the actual expected origin:

```text
https://app.example.com
```

against the actual origin.

Not just a substring.

---

# 20. Attack #4 — Regex-Based Origin Mistakes

Suppose someone creates:

```js
/^https:\/\/.*example\.com/
```

This can become dangerous if the regex isn't carefully designed.

Security-sensitive origin validation should be simple and explicit whenever possible.

For example:

```js
const allowedOrigins = new Set([
    "https://app.example.com"
]);
```

Then:

```js
allowedOrigins.has(origin)
```

is much easier to reason about.

---

# 21. Attack #5 — `null` Origin

Browsers can sometimes send:

```http
Origin: null
```

in certain contexts.

Developers sometimes accidentally allow:

```text
null
```

because they want to support local or unusual development scenarios.

Don't blindly add:

```text
"null"
```

to your trusted origin list.

Understand exactly why it appears before deciding to trust it.

---

# 22. Attack #6 — Trusting All Subdomains

Suppose you allow:

```text
*.example.com
```

Conceptually:

```text
app.example.com
api.example.com
admin.example.com
old.example.com
```

This sounds convenient.

But ask:

> Do I really trust every subdomain equally?

If:

```text
old.example.com
```

is vulnerable or abandoned, broad origin trust can increase your attack surface.

This connects to the cookie domain discussion from 22.11.

---

# 23. Subdomain Takeover Scenario

Imagine:

```text
app.example.com
api.example.com
old.example.com
```

Your CORS policy trusts all of them.

But:

```text
old.example.com
```

points to a third-party service and is no longer controlled properly.

If an attacker takes control of that subdomain:

```text
Attacker
   ↓
old.example.com
   ↓
Trusted by API CORS
   ↓
Potentially dangerous
```

The general lesson:

> **Don't trust a larger origin set than your application actually needs.**

---

# 24. Attack #7 — Credentials + Wildcard

Suppose a developer tries:

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

For credentialed browser requests, this combination is not accepted by browsers as a valid way to expose the response.

But don't treat that as your security strategy.

The correct architecture is:

```text
Explicit trusted origin
+
credentials when required
```

not:

```text
*
+
hope the browser blocks it
```

---

# 25. `Access-Control-Allow-Credentials`

This response header tells the browser whether the server permits the browser to expose the response to frontend JavaScript when credentials are involved.

For example:

```http
Access-Control-Allow-Credentials: true
```

This is relevant when using:

```js
credentials: "include"
```

But remember:

```text
Allow-Credentials
```

doesn't itself authenticate the user.

It is a browser permission.

---

# 26. CORS Headers You Should Know

At minimum, understand these:

```text
Access-Control-Allow-Origin
Access-Control-Allow-Credentials
Access-Control-Allow-Methods
Access-Control-Allow-Headers
Access-Control-Expose-Headers
Access-Control-Max-Age
```

Let's break them down.

---

# 27. `Access-Control-Allow-Origin`

Defines which origin can access the response.

Example:

```http
Access-Control-Allow-Origin: https://app.example.com
```

Think:

```text
WHO?
```

---

# 28. `Access-Control-Allow-Methods`

Example:

```http
Access-Control-Allow-Methods: GET,POST,PUT,DELETE
```

Think:

```text
WHICH HTTP METHODS?
```

---

# 29. `Access-Control-Allow-Headers`

Suppose your frontend sends:

```http
Authorization: Bearer ...
Content-Type: application/json
```

The server may need to allow those headers for the relevant cross-origin request.

Example:

```http
Access-Control-Allow-Headers: Authorization, Content-Type
```

Think:

```text
WHICH REQUEST HEADERS?
```

---

# 30. `Access-Control-Allow-Credentials`

Example:

```http
Access-Control-Allow-Credentials: true
```

Think:

```text
CAN THE BROWSER USE CREDENTIALS
FOR THIS CROSS-ORIGIN REQUEST?
```

The exact browser behavior also depends on cookie settings and the request mode.

---

# 31. `Access-Control-Expose-Headers`

Some response headers aren't automatically readable by frontend JavaScript.

If your API wants JavaScript to read a custom response header:

```http
X-Request-Id: abc123
```

you may need:

```http
Access-Control-Expose-Headers: X-Request-Id
```

This becomes useful with the request-ID architecture you've already studied.

---

# 32. `Access-Control-Max-Age`

This controls how long the browser may cache certain preflight results.

For example:

```http
Access-Control-Max-Age: 600
```

means the browser can cache the relevant preflight result for a period of time.

Be careful with long caching during development because changes to your CORS policy may appear not to work immediately.

---

# 33. Simple Requests vs Preflight

Not every cross-origin request requires a preflight.

Some requests are considered **CORS-safelisted/simple** when they meet specific browser rules.

Other requests require a:

```text
OPTIONS
```

request first.

Understanding this difference is important for testing.

---

# 34. What Is a Preflight?

Imagine the browser wants to send:

```http
DELETE /api/v1/todos/123
```

with:

```http
Authorization: Bearer ...
```

The browser may first ask the server:

```http
OPTIONS /api/v1/todos/123
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: authorization
```

This is the:

> **Preflight request**

---

# 35. Preflight Response

The server might respond:

```http
HTTP/1.1 204 No Content

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET,POST,PUT,DELETE
Access-Control-Allow-Headers: Authorization,Content-Type
```

The browser checks whether the requested operation is allowed.

If the requirements are satisfied:

```text
OPTIONS
   ↓
Allowed
   ↓
Actual DELETE
```

---

# 36. Attack #8 — Broken Preflight Handling

A poorly configured API may:

```text
Allow every origin
Allow every method
Allow every header
Allow credentials
```

This creates an unnecessarily broad browser trust boundary.

Your preflight configuration should be as restrictive as your actual application requires.

---

# 37. Attack #9 — Allowing Dangerous Methods

Suppose your API only needs:

```text
GET
POST
```

but your CORS policy says:

```text
GET
POST
PUT
PATCH
DELETE
OPTIONS
```

You're advertising a larger cross-origin capability than necessary.

This isn't automatically an exploit by itself, but it violates least privilege.

Prefer:

```text
Only methods your frontend actually needs.
```

---

# 38. Attack #10 — Allowing Unnecessary Headers

Similarly, don't blindly allow:

```text
*
```

for headers if your architecture doesn't require it.

If your frontend needs:

```text
Authorization
Content-Type
```

allow those.

Think:

```text
Needed
 ↓
Allow

Not needed
 ↓
Don't expose
```

---

# 39. CORS and Authorization Header

Your access-token architecture commonly uses:

```http
Authorization: Bearer <access-token>
```

Because `Authorization` is a request header, cross-origin browser requests using it can trigger a preflight depending on the request.

So:

```text
React
 ↓
Authorization header
 ↓
Browser
 ↓
OPTIONS
 ↓
API
```

Your CORS configuration needs to understand this.

---

# 40. CORS and Refresh Cookies

Now compare:

### Access token

```text
Authorization header
```

### Refresh token

```text
HttpOnly cookie
```

Therefore:

```text
Access request
   ↓
Authorization
```

while:

```text
Refresh request
   ↓
Cookie
   ↓
credentials: include when cross-origin and needed
```

This is why your CORS configuration must be designed together with your authentication architecture.

---

# 41. A Typical MERN Architecture

Suppose:

```text
Frontend:
http://localhost:5173

Backend:
http://localhost:5000
```

Your browser frontend might use:

```js
fetch("http://localhost:5000/api/v1/users/me", {
    credentials: "include"
});
```

The backend CORS configuration might conceptually be:

```js
const allowedOrigins = [
    "http://localhost:5173"
];
```

Then:

```text
Origin
   ↓
allowedOrigins?
   │
   ├── YES → CORS headers
   │
   └── NO → don't grant access
```

---

# 42. Dangerous Express Configuration

Avoid blindly doing:

```js
app.use(cors());
```

for a production authenticated API without understanding what policy it creates.

Likewise, avoid:

```js
app.use(cors({
    origin: true,
    credentials: true
}));
```

if `origin: true` effectively trusts arbitrary origins.

Your configuration should represent your actual frontend trust boundary.

---

# 43. Better CORS Middleware

A simple architecture:

```js
const allowedOrigins = new Set([
    "http://localhost:5173",
    "https://app.example.com"
]);

const corsOptions = {
    origin(origin, callback) {
        if (!origin || allowedOrigins.has(origin)) {
            callback(null, true);
            return;
        }

        callback(new Error("Origin not allowed"));
    },

    credentials: true
};
```

The exact behavior for requests without an `Origin` should be chosen intentionally for your API architecture.

The important concept is:

```text
Incoming origin
      ↓
Explicit validation
      ↓
Allow / reject
```

---

# 44. Why `origin` May Be Missing

Not every HTTP request necessarily has an `Origin` header.

For example, some server-to-server requests or command-line tools may not send one.

So:

```js
if (!origin) {
    ...
}
```

must be a deliberate policy decision.

Don't automatically assume:

```text
No Origin = safe browser request
```

or:

```text
No Origin = malicious request
```

The context matters.

---

# 45. CORS Is Not an API Security Boundary

This is one of the biggest lessons.

Imagine:

```text
curl
   ↓
POST /api/v1/users
```

CORS won't stop it.

Therefore your API must still have:

```text
Authentication
Authorization
Validation
Rate limiting
Input security
```

CORS mainly protects browser applications from unauthorized cross-origin **reading/exposure** under browser enforcement.

---

# 46. Attack Scenario

Let's imagine your API:

```text
GET /api/v1/profile
```

requires authentication.

A malicious website:

```text
https://evil.example
```

tries:

```js
fetch("https://api.example.com/api/v1/profile", {
    credentials: "include"
});
```

If your CORS policy doesn't trust `evil.example`, the browser should not expose the protected response to that website's JavaScript.

That's useful.

But if your API has:

```text
No authentication
```

then CORS isn't going to magically make the endpoint secure.

---

# 47. CORS Misconfiguration ≠ Always Account Takeover

This is an important security-testing mindset.

Finding:

```text
Access-Control-Allow-Origin: *
```

doesn't automatically mean:

```text
🚨 Critical vulnerability
```

You need to ask:

```text
What data is exposed?
Are credentials involved?
Can the attacker read authenticated responses?
Is the endpoint sensitive?
Can state-changing requests be abused?
Is CSRF protection present?
```

Security severity depends on impact.

---

# 48. CORS Attack Chain

A meaningful attack might look like:

```text
Attacker controls evil.example
          ↓
Victim is logged into app.example.com
          ↓
Browser has authentication cookie
          ↓
evil.example sends credentialed request
          ↓
API incorrectly trusts evil.example
          ↓
Browser exposes response
          ↓
🚨 Sensitive data stolen
```

This is much more serious than merely seeing a permissive header on a public endpoint.

---

# 49. CORS + Cookies + CSRF

Now you can see why 22.13 comes next.

```text
Cookies
   ↓
Browser automatically sends credentials
   ↓
CORS controls browser cross-origin access
   ↓
CSRF controls unauthorized state-changing actions
```

But don't merge them into one concept.

They solve different problems.

---

# 50. CORS vs CSRF

### CORS

Primarily asks:

> **Which origins can browser JavaScript access the response from?**

### CSRF

Asks:

> **Can an attacker cause an authenticated browser to perform an unwanted state-changing action?**

So:

```text
CORS → cross-origin response access
CSRF → unwanted authenticated action
```

This distinction is extremely important for interviews and real development.

---

# 51. Attack #11 — Wildcard Origin on Sensitive Public Data

Suppose:

```http
Access-Control-Allow-Origin: *
```

on:

```text
GET /api/v1/public-products
```

Maybe that's completely fine.

But the same policy on:

```text
GET /api/v1/account/payment-history
```

is a very different situation if authenticated data becomes readable cross-origin.

Always evaluate:

```text
Endpoint sensitivity
+
authentication
+
credentials
+
CORS policy
```

together.

---

# 52. Attack #12 — Origin Validation Case Sensitivity / Normalization

Origin comparison should use the browser's actual origin representation and a well-defined allowlist.

Don't build a complicated homemade parser unless necessary.

Prefer:

```js
const allowedOrigins = new Set([
    "https://app.example.com"
]);
```

and compare the received origin carefully.

Simple security code is usually easier to audit.

```js
const response = await request(app)
    .get("/api/v1/users/me")
```

Then inspect:

```js
response.headers["access-control-allow-origin"];
```

Expected:

```text
https://app.example.com
```

# 54. Test an Untrusted Origin

```js
const response = await request(app)
    .get("/api/v1/users/me")
    .set("Origin", "https://evil.example");
```

Your application should not grant that origin access.

Depending on your CORS implementation, you may get:

```text
No Access-Control-Allow-Origin
```

or another controlled response behavior.

The exact HTTP status isn't the only thing you're testing.

You're testing:

> **Was the untrusted origin granted CORS permission?**

# 55. Test Credentialed CORS

For a trusted origin, verify:

```text
Access-Control-Allow-Origin:
https://app.example.com
```

and:

```text
Access-Control-Allow-Credentials:
true
```

when your architecture requires credentials.

# 56. Test Wildcard + Credentials Misconfiguration

Write a security regression test that ensures your production configuration never becomes:

```text
Access-Control-Allow-Origin: *
+
Access-Control-Allow-Credentials: true
```

for your authenticated browser API.

This is a good example of a configuration test.

---

# 57. Test Preflight

Send:

```http
OPTIONS /api/v1/todos/123
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: authorization,content-type
```

Then inspect:

```text
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
```

You're verifying that the preflight contract matches your actual API.

---

# 58. Test an Untrusted Preflight

Send:

```http
OPTIONS /api/v1/todos/123
Origin: https://evil.example
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: authorization
```

Expected:

```text
No permission granted
```

This is much more useful than simply checking:

```text
OPTIONS → 204
```

A `204` alone doesn't mean the CORS policy is secure.

---

# 59. Test Only Required Methods

Suppose your frontend only needs:

```text
GET
POST
```

Then test that your policy isn't accidentally advertising:

```text
DELETE
PATCH
PUT
```

unless they're genuinely needed cross-origin.

This keeps your CORS policy aligned with the application.

---

# 60. Test Only Required Headers

Likewise:

```text
Authorization
Content-Type
```

may be enough.

Don't automatically expose every possible header.

The security principle is:

```text
Minimum required browser capability
```

---

# 61. CORS Security Test Matrix

Build a matrix like this:

|Origin|Endpoint|Credentials|Expected|
|---|---|--:|---|
|trusted frontend|`/me`|yes|allowed|
|trusted frontend|`/todos`|yes|allowed|
|evil origin|`/me`|yes|denied|
|evil origin|`/todos`|yes|denied|
|trusted frontend|public API|no|allowed|
|unknown origin|sensitive API|yes|denied|

This makes your CORS policy much easier to reason about.


for security validation.

### ❌ Mistake 6

Thinking:

```text
CORS = authentication
```

It isn't.

Testing CORS only with Postman.

Postman doesn't enforce browser CORS behavior like a browser does.

# 63. A Good Production Architecture

For your MERN backend, think:

```text
                Browser
                   │
                   ▼
              React App
                   │
          Origin: app.example.com
                   │
                   ▼
              CORS Middleware
                   │
           ┌───────┴───────┐
           │               │
       trusted          untrusted
           │               │
           ▼               ▼
       continue         reject/no
                         CORS grant
           │
           ▼
       Auth Middleware
           │
           ▼
      Authorization
           │
           ▼
       Controller
```

CORS comes **before** your application logic because it establishes the browser-origin policy.

But it does not replace authentication or authorization.
