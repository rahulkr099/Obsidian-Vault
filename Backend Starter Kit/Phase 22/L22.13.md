# Lesson 22.13 — CSRF Fundamentals

Your roadmap places **22.13 — CSRF Fundamentals** immediately after CORS attacks.

This is the perfect point to learn CSRF because you've already covered:

```text
22.10 Refresh-token attacks
        ↓
22.11 Cookie attacks
        ↓
22.12 CORS attacks
        ↓
22.13 CSRF fundamentals
```

The main thing I want you to understand today is:

> **CSRF is possible because browsers can automatically attach authentication credentials, especially cookies, to requests.**

---

# 1. What Does CSRF Mean?

CSRF stands for:

> **Cross-Site Request Forgery**

In simple words:

> An attacker tricks a victim's browser into sending an authenticated request to your application.

The attacker doesn't necessarily need to know the victim's password.

They may not even know the victim's cookie value.

The browser can send the credential automatically.

That's the dangerous part.

---

# 2. The Core Idea

Imagine you are logged into:

```text
https://bank.example
```

Your browser has:

```text
session=abc123
```

stored as a cookie.

Now you visit:

```text
https://evil.example
```

The attacker wants your browser to perform:

```http
POST /transfer
```

against:

```text
https://bank.example
```

The browser might attach the bank's cookie according to its cookie rules.

Conceptually:

```text
Victim
  │
  ├── Logged into bank.example
  │       ↓
  │    auth cookie
  │
  └── Visits evil.example
          ↓
       malicious request
          ↓
       bank.example
          ↓
       browser attaches cookie
          ↓
       authenticated request
```

That's CSRF.

---

# 3. Why Is This Possible?

Because browsers have historically been designed to automatically send certain credentials.

For cookies:

```text
Request → matching domain
             ↓
         Cookie attached
```

JavaScript doesn't need to know the cookie value.

For example, an HttpOnly cookie cannot be read by JavaScript:

```js
document.cookie
```

may not reveal it.

But that doesn't necessarily stop the browser from sending it.

This distinction is **extremely important**.

---

# 4. HttpOnly Does NOT Automatically Prevent CSRF

Suppose:

```http
Set-Cookie: refreshToken=secret; HttpOnly
```

`HttpOnly` means JavaScript can't directly read the cookie.

Good.

But:

```text
HttpOnly
   ↓
prevents JavaScript from reading cookie
```

It does **not** mean:

```text
HttpOnly
   ↓
prevents browser from sending cookie
```

So:

```text
HttpOnly ≠ CSRF protection
```

Remember that.

---

# 5. A Simple Attack

Suppose your application has:

```http
POST /api/v1/account/email
```

and expects:

```json
{
  "email": "attacker@example.com"
}
```

The user is authenticated using a cookie.

An attacker creates a malicious page containing a form targeting your application.

Conceptually:

```html
<form action="https://app.example.com/api/v1/account/email"
      method="POST">
    <input name="email"
           value="attacker@example.com">
</form>
```

The attacker gets the victim to visit the malicious page.

The victim's browser sends the request to your application.

If the authentication cookie is attached and the server doesn't have CSRF protection:

```text
🚨 State-changing action may succeed
```

---

# 6. Why the Attacker Doesn't Need the Cookie

This is the part that surprises many beginners.

Imagine:

```text
Victim's cookie:
refreshToken=SUPER_SECRET_VALUE
```

The attacker does **not** know:

```text
SUPER_SECRET_VALUE
```

They don't necessarily need it.

They just need the victim's browser to make the request.

Think of the browser as the courier:

```text
Attacker
   ↓
"Browser, please send this request."
   ↓
Browser
   ↓
adds applicable credentials
   ↓
Server
```

The browser performs the authenticated request.

---

# 7. CSRF Is Mostly About Cookies

Traditional CSRF is especially relevant when authentication relies on credentials that browsers automatically attach.

Most importantly:

```text
Cookie-based authentication
```

For example:

```text
session cookie
refresh-token cookie
authentication cookie
```

Compare this with:

```http
Authorization: Bearer <access-token>
```

If the access token is kept somewhere JavaScript explicitly controls and the attacker cannot cause the browser to attach it automatically, the classic CSRF scenario is different.

This doesn't mean bearer-token architectures are automatically secure; they have other threats, such as XSS and token theft.

---

# 8. Your Authentication Architecture

Your roadmap has taught:

```text
Access Token
     ↓
Authorization: Bearer ...
```

and:

```text
Refresh Token
     ↓
HttpOnly Cookie
```

That means CSRF is particularly important around endpoints that use the refresh-token cookie.

For example:

```text
POST /api/v1/auth/refresh
```

may depend on:

```text
refreshToken cookie
```

The browser automatically handles that cookie according to its cookie policy.

Therefore, you need to think about:

```text
Cookie
+
SameSite
+
CSRF protection
+
Origin validation
```

---

# 9. CSRF vs CORS

You just learned CORS.

Don't confuse them.

### CORS

Deals primarily with:

```text
Can JavaScript from origin A
read a response from origin B?
```

### CSRF

Deals primarily with:

```text
Can an attacker cause a victim's browser
to perform an authenticated action?
```

So:

```text
CORS
 ↓
Response access

CSRF
 ↓
Unauthorized action
```

---

# 10. A Very Important Example

Suppose:

```text
evil.example
     ↓
POST
     ↓
api.example
```

The attacker may not care about reading the response.

They only care that the action happens.

For example:

```text
Change email
Delete account
Change password
Create payment
Transfer money
Delete resource
```

This is why:

> **Blocking the attacker from reading the response isn't necessarily enough.**

The unwanted action itself is the problem.

---

# 11. CORS Doesn't Equal CSRF Protection

This is a common mistake:

> "My CORS policy blocks evil.example, so I don't have CSRF."

Not necessarily.

CORS and CSRF solve different problems.

You should design them independently.

Think:

```text
CORS
    ↓
Browser response access policy

CSRF protection
    ↓
State-changing request protection
```

---

# 12. State-Changing Requests

CSRF is especially dangerous for operations that modify data.

Examples:

```http
POST /transfer
POST /change-password
POST /delete-account
PUT /profile
PATCH /settings
DELETE /todos/123
```

These can change application state.

Compare:

```http
GET /products
```

A GET should generally be safe and not perform a state-changing operation.

This leads to an important REST/security principle:

> **Don't use GET for destructive or state-changing actions.**

Bad:

```http
GET /delete-account
```

Better:

```http
DELETE /account
```

with appropriate authorization and CSRF defenses.

---

# 13. CSRF and GET

Suppose your backend does this:

```http
GET /api/v1/delete-user/123
```

That's dangerous architecture.

An attacker could potentially cause browsers to request that URL simply by embedding it somewhere.

For example:

```html
<img src="https://api.example.com/delete-user/123">
```

The browser may make the GET request.

If GET changes state, you've created a serious design problem.

So:

```text
GET
 ↓
Read data

POST/PUT/PATCH/DELETE
 ↓
State-changing operation
```

is a much safer design principle.

---

# 14. SameSite Cookies

One of your earlier authentication lessons covered:

```text
SameSite
```

Now you can see why it matters.

Cookie settings can restrict when browsers send cookies in cross-site situations.

Common values:

```text
Strict
Lax
None
```

---

# 15. `SameSite=Strict`

Conceptually:

```text
SameSite=Strict
```

is the strongest restriction.

The browser is very restrictive about sending the cookie in cross-site contexts.

This can significantly reduce CSRF exposure.

But there can be usability implications.

For example:

```text
External site
    ↓
User clicks link
    ↓
Your application
```

Some flows may behave differently.

Security is always about balancing:

```text
security
+
functionality
```

---

# 16. `SameSite=Lax`

`Lax` provides a useful middle ground.

It restricts many cross-site cookie sends while still allowing certain top-level navigation scenarios.

For many session-style web applications, `Lax` is a practical default when compatible with the application's authentication flow.

But don't blindly choose it.

Understand your application's cross-site requirements.

---

# 17. `SameSite=None`

This means the cookie can be used in cross-site contexts, but browsers require:

```text
Secure
```

So:

```http
SameSite=None; Secure
```

is required for cross-site cookie use in modern browsers.

This is where CSRF considerations become especially important.

If your architecture truly requires cross-site cookies:

```text
CSRF protection
```

should be taken seriously.

---

# 18. SameSite Is Not Your Entire Security Strategy

A common mistake is:

> "I'm using SameSite, therefore CSRF is solved."

SameSite is a powerful defense, but security should be layered.

Think:

```text
Cookie security
      +
SameSite
      +
CSRF token / request validation
      +
Origin checking
      +
Authentication
      +
Authorization
```

This creates defense in depth.

---

# 19. The CSRF Token

One classic defense is a:

> **CSRF token**

The server generates a value that an attacker shouldn't know.

Example:

```text
csrfToken = random-secret-value
```

The legitimate frontend submits it with a state-changing request.

For example:

```http
POST /api/v1/profile

X-CSRF-Token: random-secret-value
```

The server verifies:

```text
Token provided?
       ↓
Matches expected token?
       │
   ┌───┴───┐
  YES      NO
   │        │
   ▼        ▼
Continue   Reject
```

---

# 20. Why Does a CSRF Token Work?

The attacker can often cause the victim's browser to send:

```text
Cookie
```

But they shouldn't be able to obtain the unpredictable CSRF token from your application.

So:

```text
Attacker
   ↓
Can cause request?
Maybe

Knows CSRF token?
No

Request accepted?
❌
```

This creates a second secret requirement.

---

# 21. Synchronizer Token Pattern

A common architecture is:

```text
Server
  ↓
Generate CSRF token
  ↓
Associate with session
```

Then:

```text
Frontend
  ↓
gets CSRF token
  ↓
sends it with state-changing request
```

Server checks:

```text
request token
      ==
expected token
```

If not:

```text
403 Forbidden
```

---

# 22. Double-Submit Cookie Pattern

Another approach is:

```text
CSRF token → cookie
```

and the client also sends:

```text
X-CSRF-Token
```

in a request header.

The server compares the values.

Conceptually:

```text
Cookie:
csrfToken=ABC123

Header:
X-CSRF-Token: ABC123
```

Server:

```text
ABC123 === ABC123
       ↓
      YES
       ↓
    continue
```

The exact implementation needs careful design so attackers cannot simply control both values.

---

# 23. Why Headers Help

A malicious site can often create simple cross-site requests.

But it generally cannot freely make arbitrary cross-origin JavaScript requests with custom headers and then bypass the browser's security model.

For example:

```http
X-CSRF-Token: ABC123
```

requires the legitimate application to know the token.

This is one reason CSRF defenses often use a custom header.

---

# 24. CSRF Token + CORS

Now the previous lesson becomes useful.

Suppose:

```text
Frontend
https://app.example.com
```

and:

```text
API
https://api.example.com
```

The frontend sends:

```http
X-CSRF-Token: ABC123
```

Because this is a custom header, the browser may perform a CORS preflight.

Then your API can explicitly allow:

```http
Access-Control-Allow-Headers: X-CSRF-Token
```

for the trusted frontend.

So:

```text
CSRF token
     ↓
custom header
     ↓
CORS preflight
     ↓
trusted origin
```

Now you can see how these mechanisms work together.

---

# 25. Origin Checking

Another useful CSRF defense is checking:

```http
Origin
```

on state-changing requests.

Suppose your legitimate frontend is:

```text
https://app.example.com
```

Request:

```http
Origin: https://app.example.com
```

Good.

But:

```http
Origin: https://evil.example
```

should be rejected.

Conceptually:

```text
POST /api/v1/account/email

Origin?
   ↓
Trusted?
   │
 ┌─┴─┐
YES  NO
 │    │
 ▼    ▼
OK   403
```

---

# 26. Referer Checking

Another signal is:

```http
Referer
```

It can sometimes be used as an additional defense.

However, `Origin` is generally a more direct signal for many CSRF checks.

Also remember that headers can sometimes be absent because of browser/privacy behavior.

So don't blindly depend on a single header without understanding your environment.

---

# 27. Defense in Depth

A strong architecture can combine:

```text
SameSite cookie
       +
CSRF token
       +
Origin validation
       +
Authentication
       +
Authorization
```

For example:

```text
POST /api/v1/account/change-password
        │
        ▼
Check Origin
        │
        ▼
Check CSRF token
        │
        ▼
Authenticate user
        │
        ▼
Authorize operation
        │
        ▼
Change password
```

Each layer answers a different question.

---

# 28. CSRF Does Not Mean "Any POST Is Dangerous"

Don't reduce CSRF to:

```text
POST = dangerous
```

The important question is:

> Does this request perform a state-changing operation using credentials that the browser can automatically attach?

For example:

```text
POST /search
```

might not change anything.

Whereas:

```text
POST /transfer
```

is highly sensitive.

Security decisions should follow application behavior.

---

# 29. CSRF and Your Refresh Endpoint

Your architecture uses:

```text
refresh token
   ↓
HttpOnly cookie
```

Consider:

```http
POST /api/v1/auth/refresh
```

The browser may automatically send the refresh cookie.

Therefore, you should think about whether an attacker can cause a cross-site refresh request.

Depending on the architecture, the impact may differ.

The important lesson is:

> **Any endpoint that relies on automatically attached credentials deserves CSRF analysis.**

Don't only protect `/transfer`.

---

# 30. CSRF and Logout

What about:

```http
POST /api/v1/auth/logout
```

Could CSRF trigger logout?

Potentially.

Usually:

```text
forced logout
```

is much less severe than:

```text
money transfer
password change
account deletion
```

This is a good security-engineering lesson:

> **Not every CSRF issue has the same impact.**

Always evaluate the action.

---

# 31. CSRF vs XSS

These are also easy to confuse.

### CSRF

Attacker:

```text
causes victim's browser
to perform an action
```

### XSS

Attacker:

```text
gets malicious JavaScript
to execute in your application's
trusted browser context
```

XSS can be even more powerful because malicious JavaScript executing inside your application's origin may interact with your application in ways a cross-site attacker cannot.

So:

```text
CSRF ≠ XSS
```

But they can interact.

---

# 32. XSS Can Weaken CSRF Defenses

Imagine your application has:

```text
excellent CSRF token protection
```

but also:

```text
stored XSS
```

An attacker gets JavaScript executing inside:

```text
https://app.example.com
```

That script may be able to access application data and potentially obtain CSRF tokens depending on how they're stored/exposed.

Therefore:

```text
CSRF protection
```

doesn't mean:

```text
XSS protection unnecessary
```

Security layers depend on one another.

---

# 33. A Realistic Attack Chain

Imagine:

```text
Victim logged in
      ↓
Auth cookie exists
      ↓
Victim visits evil.example
      ↓
evil.example tries state-changing request
      ↓
Browser attaches cookie
      ↓
Server sees authenticated user
      ↓
No CSRF validation
      ↓
Action succeeds
```

With protection:

```text
Victim visits evil.example
      ↓
Malicious request
      ↓
Cookie may be attached
      ↓
CSRF token missing
      ↓
Origin invalid
      ↓
🚫 Request rejected
```

That's the goal.

---

# 34. The Security Boundary

Think of your browser like this:

```text
                    BROWSER
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
     app.example              evil.example
          │                         │
          │                         │
      trusted app               attacker
          │                         │
          └──────────┬──────────────┘
                     ▼
                   API
```

The server must distinguish:

```text
legitimate application request
```

from:

```text
attacker-controlled cross-site request
```

CSRF defenses help establish that distinction.

---

# 35. A Useful Rule for Your Backend

For every state-changing endpoint, ask:

```text
1. Does it use cookies?
2. Can another site trigger the request?
3. Is SameSite sufficient for this architecture?
4. Do we need a CSRF token?
5. Can we validate Origin?
6. Is authentication required?
7. Is authorization required?
```

This becomes a reusable security checklist.

---

# 36. Example: Secure Request

Imagine:

```http
POST /api/v1/todos
Origin: https://app.example.com
Cookie: refreshToken=...
X-CSRF-Token: abc123
Authorization: Bearer <access-token>
```

Your server might process:

```text
Origin check
      ↓
CSRF token check
      ↓
JWT authentication
      ↓
Authorization
      ↓
Validation
      ↓
Controller
      ↓
Service
```

That's a strong layered approach.

---

# 37. Example: Forged Request

Attacker sends:

```http
POST /api/v1/todos
Origin: https://evil.example
Cookie: automatically attached
```

But:

```text
X-CSRF-Token
```

is missing.

Your server:

```text
Origin invalid
      ↓
CSRF token missing
      ↓
403 Forbidden
```

The attacker doesn't get the desired state change.

---

# 38. What Status Code?

For a failed CSRF validation, a common choice is:

```http
403 Forbidden
```

because the request may be understood but isn't permitted under the application's security policy.

For example:

```json
{
  "success": false,
  "message": "CSRF validation failed"
}
```

Don't expose unnecessary security details.

# 40. Your Supertest Example

Conceptually:

```js
const response = await request(app)
    .post("/api/v1/account/email")
    .set("Origin", "https://app.example.com")
    .set("X-CSRF-Token", validToken)
    .set("Cookie", authCookie)
    .send({
        email: "new@example.com"
    });

expect(response.status).toBe(200);
```

Then:

```js
const response = await request(app)
    .post("/api/v1/account/email")
    .set("Origin", "https://app.example.com")
    .set("Cookie", authCookie)
    .send({
        email: "attacker@example.com"
    });

expect(response.status).toBe(403);
```

You're now testing the actual security boundary.

# 42. The Most Important Distinction

Memorize this table:

|Mechanism|Main purpose|
|---|---|
|`HttpOnly`|Prevent JavaScript from reading a cookie|
|`Secure`|Send cookie only over HTTPS|
|`SameSite`|Control cross-site cookie sending|
|CORS|Control browser access to cross-origin responses|
|CSRF token|Prove a state-changing request came from a legitimate application flow|
|Authentication|Identify the user|
|Authorization|Decide what the user can do|

This table will save you from a lot of confusion later.
