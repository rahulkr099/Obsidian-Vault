# Lesson 22.14 — Sensitive Data Exposure 🔐

According to your roadmap, **22.14 is Sensitive Data Exposure**, followed by the security testing checklist and then building the actual security test suite.

The goal of this lesson is simple:

> **Make sure your API never gives an attacker more information than they actually need.**

This is especially important in your MERN backend because your architecture contains users, authentication, JWTs, refresh tokens, passwords, logs, database queries, and API responses.

---

# 1. What Is Sensitive Data Exposure?

Sensitive data exposure happens when your application accidentally reveals information that should have remained protected.

Examples:

```text
Password hashes
Refresh-token hashes
JWT secrets
Database credentials
API keys
Private user information
Internal database fields
Stack traces
File paths
Internal IDs
Security tokens
Sensitive logs
```

The important point is:

> The data doesn't have to be a password to be sensitive.

For example:

```json
{
  "email": "rahul@example.com",
  "role": "admin",
  "refreshTokenHash": "...",
  "resetTokenHash": "..."
}
```

Even if the password isn't present, this response may still expose far too much.

---

# 2. The Basic Security Principle

Think:

```text
Database has 20 fields
        ↓
API needs 5 fields
        ↓
Return only those 5
```

Not:

```text
Database document
        ↓
JSON.stringify(document)
        ↓
Send everything
```

This is called:

> **Data minimization**

Only expose the information required for the current operation.

---

# 3. The Classic Mistake

Imagine your MongoDB user document:

```js
{
    _id,
    firstName,
    lastName,
    email,
    password,
    role,
    refreshTokenHash,
    resetTokenHash,
    resetTokenExpires
}
```

Then your controller does:

```js
const user = await userRepository.findById(req.user.id);

return res.json({
    success: true,
    data: user
});
```

🚨 Dangerous.

You may accidentally return:

```json
{
  "_id": "...",
  "firstName": "Rahul",
  "email": "...",
  "password": "...",
  "refreshTokenHash": "...",
  "resetTokenHash": "..."
}
```

The endpoint only needed:

```text
firstName
lastName
email
```

but returned everything.

---

# 4. Never Return Passwords

This should become automatic for you.

Never send:

```json
{
  "password": "$2b$12$..."
}
```

Even though bcrypt hashes are not plaintext passwords.

Why?

Because password hashes are still sensitive authentication data.

Your API should return:

```json
{
  "id": "123",
  "firstName": "Rahul",
  "lastName": "Kumar",
  "email": "rahul@example.com"
}
```

---

# 5. Password Hash ≠ Safe Data

A common beginner thought is:

> "It's hashed, so it's okay to expose."

No.

Suppose:

```text
password
   ↓
bcrypt
   ↓
$2b$12$...
```

The hash is designed to make password recovery difficult, but it is still a valuable target.

Attackers may:

- steal hashes
    
- perform offline guessing
    
- reuse information in attacks
    
- target your authentication infrastructure
    

Therefore:

```text
Plain password
❌ Never expose

Password hash
❌ Never expose
```

---

# 6. Refresh Token Hashes Are Sensitive Too

Your architecture hashes refresh tokens before storing them.

Conceptually:

```text
Refresh token
      ↓
bcrypt/hash
      ↓
MongoDB
```

You might have:

```js
{
    refreshTokenHash: "..."
}
```

That field should **never** appear in a normal user response.

For example:

```http
GET /api/v1/users/me
```

should not return:

```json
{
  "email": "...",
  "refreshTokenHash": "..."
}
```

The user doesn't need it.

---

# 7. Reset Token Information

Password-reset systems may contain fields like:

```js
{
    resetTokenHash,
    resetTokenExpires
}
```

These are security-sensitive.

Don't return:

```json
{
  "resetTokenHash": "...",
  "resetTokenExpires": "..."
}
```

through normal APIs.

The client typically only needs to know:

```json
{
  "message": "Password reset email sent"
}
```

---

# 8. JWT Secrets

This is even more important.

Suppose:

```env
JWT_ACCESS_SECRET=super-secret-value
JWT_REFRESH_SECRET=another-secret
```

These belong in:

```text
environment / secret manager
```

not:

```text
API response
Git repository
frontend bundle
logs
error messages
```

If an attacker gets your signing secret, they may be able to create forged tokens depending on your JWT architecture.

---

# 9. `.env` Exposure

Never commit:

```text
.env
```

containing:

```env
MONGO_URI=mongodb+srv://...
JWT_SECRET=...
SMTP_PASSWORD=...
API_KEY=...
```

Your repository should normally contain:

```text
.env.example
```

instead.

For example:

```env
PORT=
MONGO_URI=
JWT_ACCESS_SECRET=
JWT_REFRESH_SECRET=
SMTP_HOST=
SMTP_USER=
SMTP_PASSWORD=
```

But:

```text
.env
```

should contain the real values and remain outside version control.

---

# 10. Git History Matters

Here's a dangerous mistake:

```bash
git add .env
git commit -m "add env"
```

Then:

```bash
git rm .env
```

You might think:

> "It's deleted now."

But the secret may still exist in:

```text
Git history
```

So:

```text
Delete from current files
≠
Delete from history
```

If a real secret was committed, the safe response is generally:

> **Rotate the secret.**

Don't rely only on deleting the file.

---

# 11. API Responses Are a Major Attack Surface

Think about every endpoint:

```text
GET /users/me
GET /users/:id
GET /admin/users
GET /todos/:id
POST /login
POST /refresh
POST /password-reset
```

Ask:

> **Exactly which fields does the client need?**

For example:

### Bad

```json
{
  "_id": "...",
  "email": "...",
  "password": "...",
  "role": "user",
  "refreshTokenHash": "...",
  "createdAt": "...",
  "updatedAt": "..."
}
```

### Better

```json
{
  "id": "...",
  "email": "...",
  "role": "user"
}
```

---

# 12. Database Projection

This is where your repository architecture becomes useful.

Instead of:

```js
User.findById(userId);
```

you can intentionally select fields.

Conceptually:

```js
User.findById(userId)
    .select("_id firstName lastName email role");
```

Now MongoDB returns only what you need.

This is better than:

```text
Fetch everything
      ↓
Remove sensitive fields later
```

because you're reducing exposure earlier.

---

# 13. Repository-Level Protection

Your repository can have methods with clear purposes.

For example:

```text
findUserForAuthentication()
```

may need:

```text
email
password
role
```

while:

```text
findUserForProfile()
```

may only need:

```text
id
firstName
lastName
email
```

That's a great architecture.

```text
Authentication query
        ↓
Needs password hash

Profile query
        ↓
Doesn't need password hash
```

---

# 14. Never Use One Query for Everything

This is risky:

```js
getUserById()
```

that always returns:

```text
every field
```

Then different services/controllers use it everywhere.

Instead, think in terms of intent:

```text
findUserForLogin()
findUserForProfile()
findUserForPasswordReset()
findUserForAuthorization()
```

Each can select exactly what is required.

This is a very good security improvement for your repository layer.

---

# 15. Error Messages Can Leak Sensitive Information

Consider:

```json
{
  "error": "MongoServerError: E11000 duplicate key error collection users index email_1 dup key: { email: 'rahul@example.com' }"
}
```

That's too much internal information for a production client.

The client might only need:

```json
{
  "success": false,
  "message": "Email is already registered"
}
```

The detailed database error belongs in:

```text
server logs
```

not:

```text
HTTP response
```

---

# 16. Stack Traces

During development, you might see:

```text
Error: Cannot read properties of undefined
    at UserService.login (...)
    at authController (...)
    at processTicksAndRejections (...)
```

Useful for developers.

Terrible as a public production response.

Don't send:

```json
{
  "stack": "Error: ..."
}
```

to users in production.

Instead:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "req_123"
}
```

Then use the request ID to find the real error in your logs.

---

# 17. Request IDs Become Extremely Useful

You've already studied request IDs in your logging phase.

Suppose something fails:

```text
POST /api/v1/payment
```

Instead of returning:

```json
{
  "error": "MongoError at payment.service.js line 84..."
}
```

return:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "req_7f92a"
}
```

Server log:

```text
requestId=req_7f92a
error=MongoError
userId=...
route=/api/v1/payment
```

The client gets useful information without getting internal details.

---

# 18. User Enumeration

Sensitive data exposure isn't only about accidentally returning fields.

Sometimes your application reveals whether a particular account exists.

Consider login:

```text
POST /login
```

Response:

```text
"Email does not exist"
```

versus:

```text
"Incorrect password"
```

An attacker can test:

```text
alice@example.com
bob@example.com
admin@example.com
```

and determine which accounts exist.

That's called:

> **User/account enumeration**

---

# 19. Password Reset Enumeration

This is especially common.

Bad:

```text
POST /forgot-password

"User does not exist."
```

Better:

```text
" If an account exists, a password reset email has been sent."
```

Now the attacker doesn't get a reliable signal about account existence.

The application can still send an email when appropriate.

---

# 20. Login Enumeration

Instead of:

```text
Email not found
```

and:

```text
Wrong password
```

you can use a generic message:

```text
Invalid email or password
```

The backend can still log the precise reason internally.

This is a good example of:

```text
Detailed internal information
        ↓
Logs

Minimal external information
        ↓
API response
```

---

# 21. Timing Differences

Sometimes an application reveals information through response timing.

For example:

```text
Unknown user
   ↓
returns immediately

Existing user
   ↓
bcrypt.compare()
   ↓
takes longer
```

An attacker may attempt many requests and look for timing differences.

You don't need to obsess over tiny timing differences in every application, but authentication systems should avoid unnecessarily obvious distinctions.

Using a consistent authentication flow and appropriate rate limiting helps.

---

# 22. Sensitive Data in Logs

This is extremely important because you studied logging in Phase 19.

Never log things like:

```text
password
JWT
refresh token
reset token
session cookie
API key
database password
credit card number
```

Bad:

```js
logger.info({
    email,
    password
}, "Login attempt");
```

🚨 Never do this.

---

# 23. Don't Log Authorization Headers

Avoid:

```js
logger.info({
    headers: req.headers
});
```

because:

```http
Authorization: Bearer eyJ...
```

could end up in your logs.

Instead, explicitly select safe metadata:

```js
logger.info({
    method: req.method,
    path: req.path,
    requestId: req.id,
    userId: req.user?.id
});
```

---

# 24. Don't Log Cookies

Similarly, avoid:

```js
logger.info(req.headers.cookie);
```

because it may contain:

```text
refreshToken=...
session=...
```

Logging infrastructure should be treated as sensitive.

Remember:

> **Logs are another database.**

If attackers gain access to logs, anything you logged becomes potentially exposed.

---

# 25. Sensitive Data in URLs

Avoid putting secrets into URLs.

Bad:

```text
https://example.com/reset?token=SUPER_SECRET
```

URLs can end up in:

```text
browser history
proxy logs
server logs
analytics
monitoring systems
Referer headers
```

A sensitive token in a URL can therefore spread to many places.

Use safer designs where possible.

---

# 26. Query Parameters Can Leak Data

Similarly, avoid:

```text
GET /login?email=...&password=...
```

Passwords should be submitted in the request body over HTTPS, not in URLs.

Bad:

```text
GET /auth?password=myPassword
```

Good:

```http
POST /auth/login
Content-Type: application/json
```

```json
{
  "email": "user@example.com",
  "password": "..."
}
```

---

# 27. HTTPS Is Essential

Sensitive data must be protected in transit.

Without HTTPS:

```text
Browser
   ↓
Internet
   ↓
Server
```

information can potentially be observed or modified by attackers in the network path.

With HTTPS:

```text
Browser
   ↓
🔒 encrypted connection
   ↓
Server
```

For production:

```text
HTTPS
+
Secure cookies
```

should be standard.

---

# 28. Don't Send Secrets to the Frontend

Suppose your backend has:

```env
JWT_ACCESS_SECRET=...
SMTP_PASSWORD=...
MONGO_URI=...
STRIPE_SECRET_KEY=...
```

Never send:

```json
{
  "config": {
    "JWT_ACCESS_SECRET": "...",
    "MONGO_URI": "..."
  }
}
```

to React.

Remember:

> **Anything delivered to the browser should be considered visible to the user.**

Frontend code is not a secret storage mechanism.

---

# 29. Environment Variables Are Not Automatically Secret

This is an important distinction.

In Node:

```js
process.env.JWT_SECRET
```

is private to the server process.

But if you do:

```js
res.json({
    jwtSecret: process.env.JWT_SECRET
});
```

it becomes public.

Likewise, a frontend build can expose environment variables intentionally provided to client-side code.

So:

```text
Environment variable
≠ automatically safe

Server-only secret
= keep it server-side
```

---

# 30. Sensitive Data in MongoDB

Data minimization should also happen at storage level.

Ask:

> Do I actually need to store this?

For example:

```text
password
```

Yes, but only as a secure hash.

Maybe:

```text
full credit card number
```

No — use a payment provider/tokenization architecture instead.

General rule:

> **If you don't need to store sensitive data, don't store it.**

You can't leak what you don't possess.

---

# 31. Data Retention

Another security principle:

```text
Collect
   ↓
Use
   ↓
No longer needed
   ↓
Delete
```

For example, a password-reset token might have:

```text
expiration
```

After the reset:

```text
resetTokenHash = null
resetTokenExpires = null
```

Don't keep temporary secrets forever.

---

# 32. Sensitive Data in Backups

Even if your API is secure, backups can contain:

```text
users
password hashes
tokens
emails
private data
```

So:

```text
Production database
       ↓
Backup
       ↓
Also sensitive
```

Backup security matters too.

---

# 33. Sensitive Data in Error Objects

Be careful with:

```js
logger.error(error);
```

depending on what your error object contains.

A third-party error might include:

```text
request headers
request body
credentials
URLs
tokens
```

Use structured logging carefully and sanitize fields.

---

# 34. Sensitive Data in Tests

This is another place beginners forget.

Don't create fixtures like:

```js
const user = {
    email: "real-person@example.com",
    password: "RealPassword123!"
};
```

Use fake data:

```js
const user = {
    email: "test@example.com",
    password: "TestPassword123!"
};
```

And never put real production secrets into:

```text
tests/
fixtures/
README
```

---

# 35. Sensitive Data in Documentation

Your API documentation might accidentally contain:

```http
Authorization: Bearer eyJ...
```

or:

```json
{
  "password": "MyRealPassword"
}
```

Use placeholders:

```text
Bearer <access-token>
```

and:

```text
"password": "<test-password>"
```

Documentation is public-facing infrastructure.

---

# 36. API Response Design

A useful strategy is to create explicit DTO-style response objects.

Instead of:

```js
return res.json(user);
```

do:

```js
const userResponse = {
    id: user._id,
    firstName: user.firstName,
    lastName: user.lastName,
    email: user.email
};
```

Then:

```js
return res.json({
    success: true,
    data: userResponse
});
```

Now the developer has to intentionally decide what leaves the server.

That's safer.

# 37. Serialization Boundaries

Think of your architecture as:

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
Response DTO
   ↓
JSON
   ↓
Browser
```

The database object should **not automatically become the API response**.

This is a very valuable professional habit.

# 38. Admin APIs Need Extra Care

Consider:

```http
GET /api/v1/admin/users
```

An admin dashboard might legitimately need more information than a normal user.

But that doesn't mean:

```text
return entire MongoDB documents
```

Instead:

```text
Admin response
 ↓
Explicit fields
```

For example:

```json
{
  "id": "...",
  "email": "...",
  "role": "user",
  "createdAt": "..."
}
```

Still don't return:

```text
password
refreshTokenHash
resetTokenHash
```

just because the caller is an admin.

# 39. Sensitive Data Exposure Through IDOR

You studied IDOR earlier.

Suppose:

```http
GET /users/123
```

returns:

```json
{
  "email": "...",
  "phone": "...",
  "address": "...",
  "internalNotes": "..."
}
```

Even if authorization is working, the response itself may reveal too much.

So security has two questions:

```text
1. Is this user allowed to access this resource?
2. What fields should this user receive?
```

Both matter.

# 40. Field-Level Authorization

Sometimes different users need different fields.

Example:

```text
Normal user:
name

Admin:
name

```

You can implement:

```text
Authorization
      ↓
Determine allowed fields
```

```text
Security headers
```

# 44. What Should You Return After Login?

Suppose login succeeds.

Don't return:

```json
{
  "user": {
    "_id": "...",
    "password": "...",
    "refreshTokenHash": "...",
    "resetTokenHash": "..."
  },
  "accessToken": "...",
  "refreshToken": "..."
}
```

A safer architecture is:

```text
Access token
    ↓
response as needed by your architecture

Refresh token
    ↓
HttpOnly Secure cookie
```

and user information:

```json
{
  "id": "...",
  "email": "...",
  "role": "user"
}
```

The refresh token itself should not be unnecessarily exposed to frontend JavaScript if your design uses an HttpOnly cookie.

# 46. Security Review Question

For every response, ask:

> **If an attacker could read this response, what would I be worried about?**

This question is surprisingly powerful.

For example:

```text
GET /users/me
```

Response contains:

```text
email
role
```

Probably okay.

Contains:

```text
passwordHash
refreshTokenHash
```

🚨 Problem.

Contains:

```text
JWT_SECRET
```

🚨🚨 Critical.

# 49. Security Tests for Sensitive Data

Now connect this lesson with Phase 21.

Your tests should verify that sensitive fields never appear.

Example:

```js
const response = await request(app)
    .get("/api/v1/users/me")
    .set("Authorization", `Bearer ${accessToken}`);

expect(response.body.data).not.toHaveProperty("password");
expect(response.body.data).not.toHaveProperty("passwordHash");
expect(response.body.data).not.toHaveProperty("refreshTokenHash");
expect(response.body.data).not.toHaveProperty("resetTokenHash");
```

This is a **security regression test**.

If someone later changes the repository and accidentally returns the whole document:

```text
Test fails
     ↓
🚨 Security problem detected
```

---

# 50. Test Login Response

```js
const response = await request(app)
    .post("/api/v1/auth/login")
    .send({
        email,
        password
    });

expect(response.body).not.toHaveProperty("password");
expect(response.body).not.toHaveProperty("refreshTokenHash");
```

Also verify that refresh credentials are handled according to your cookie architecture rather than unnecessarily returned in the JSON body.

# 51. Test Error Responses

Create a test:

```js
const response = await request(app)
    .get("/api/v1/users/invalid");
```

Then verify you don't expose:

```text
stack
file paths
database connection strings
MongoDB errors
JWT secrets
```

For example:

```js
expect(response.body).not.toHaveProperty("stack");
expect(response.body.message).not.toMatch(/mongodb/i);
```

The exact assertions depend on your error contract.

```text

[ ] Production stack traces aren't exposed
```

# 🧠 The Most Important Mental Model

Don't think:

> "I need to hide passwords."

Think:

> **"Every piece of data leaving my backend needs a reason to be there."**

Your flow should be:

```text
Database
   ↓
Contains more information
   ↓
Repository
   ↓
Select only required fields
   ↓
Service
   ↓
Apply business rules
   ↓
Controller
   ↓
Build explicit response
   ↓
Client receives minimum required data
```

And remember this rule:

> **Never serialize database documents directly into public API responses unless you have deliberately controlled the fields being exposed.**

That habit alone will prevent a large class of sensitive-data bugs.
