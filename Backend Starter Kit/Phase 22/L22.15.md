# Lesson 22.15 — Security Testing Checklist 🛡️

Your course defines **22.15 as “Security Testing Checklist”**, immediately before **22.16 — Build Security Tests**. The purpose of this lesson is to take everything from **22.1–22.14** and turn it into a repeatable security review for your backend.

The big idea:

> **Don't just ask whether your backend works. Ask how an attacker could make it behave incorrectly.**

---

# 1. What Is a Security Testing Checklist?

A normal backend test asks:

```text
"Does login work?"
```

A security test asks:

```text
"Can someone bypass login?"
```

Normal test:

```text
Valid JWT
   ↓
GET /api/v1/profile
   ↓
200 OK
```

Security test:

```text
No JWT
   ↓
GET /api/v1/profile
   ↓
Should be rejected
```

Another:

```text
User A's JWT
   ↓
GET /api/v1/users/User-B
   ↓
Should NOT expose User B's private data
```

So security testing is essentially:

> **Testing the boundaries and failure cases of your security controls.**

# 3. The Security Testing Mindset

For every feature, ask four questions:

```text
1. Who should be allowed?
2. Who should NOT be allowed?
3. What happens with invalid input?
4. What happens when the attacker changes something?
```

For example:

```http
DELETE /api/v1/todos/123
```

Normal test:

```text
Owner + valid token
        ↓
200
```

Security tests:

```text
No token
        ↓
401

Invalid token
        ↓
401

Expired token
        ↓
401

Different user's token
        ↓
403 / 404

Malformed ID
        ↓
400
```

This mindset is much more valuable than memorizing vulnerability names.

# 5. Checklist #1 — Authentication

Start with:

```text
Can someone access protected endpoints without valid authentication?
```

Test:

### No token

```http
GET /api/v1/users/me
```

Expected:

```text
401 Unauthorized
```

---

### Invalid token

```http
Authorization: Bearer fake-token
```

Expected:

```text
401
```

---

### Malformed token

```http
Authorization: Bearer abc.def
```

Expected:

```text
401
```

---

### Expired token

Use an expired JWT.

Expected:

```text
401
```

---

### Wrong signing secret

Create a token signed with a different secret.

Expected:

```text
401
```

---

### Wrong algorithm

Attempt an algorithm-confusion style token.

Expected:

```text
401
```

The server must explicitly enforce the algorithms it accepts.

# 6. Authentication Checklist

Your test suite should eventually cover:

```text
[ ] No token rejected
[ ] Empty token rejected
[ ] Malformed token rejected
[ ] Invalid signature rejected
[ ] Expired token rejected
[ ] Wrong issuer rejected if issuer is enforced
[ ] Wrong audience rejected if audience is enforced
[ ] Unsupported algorithm rejected
[ ] Token with invalid claims rejected
[ ] Protected route cannot be accessed anonymously
```

# 7. Checklist #2 — Authorization

Authentication asks:

> **Who are you?**

Authorization asks:

> **What are you allowed to do?**

Suppose:

```text
User
Admin
```

and:

```http
DELETE /api/v1/users/123
```

Test:

```text
Anonymous
   ↓
reject

Normal user
   ↓
reject

Admin
   ↓
allow
```

---

# 8. Horizontal Privilege Escalation

This is:

> User A accessing User B's resources.

Example:

```text
User A → todo A
User B → todo B
```

Attacker:

```http
GET /api/v1/todos/B-TODO-ID
```

using User A's token.

Expected:

```text
403
```

or sometimes:

```text
404
```

depending on your API design.

The important part:

> **User A must not obtain User B's resource.**

---

# 9. Vertical Privilege Escalation

This means a lower-privileged user performs a higher-privileged action.

Example:

```text
USER
 ↓
POST /api/v1/admin/users
```

Expected:

```text
403 Forbidden
```

Test:

```text
[ ] user cannot access admin endpoint
[ ] user cannot assign admin role
[ ] user cannot delete another account if prohibited
[ ] user cannot access admin-only data
```

---

# 10. Checklist #3 — IDOR

IDOR is one of the most important tests for CRUD APIs.

Suppose:

```http
GET /api/v1/todos/123
```

Your backend should not only ask:

```text
Does todo 123 exist?
```

It should ask:

```text
Does todo 123 belong to this user?
```

Your query should conceptually be:

```js
Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

instead of:

```js
Todo.findById(todoId);
```

when ownership is required.

---

# 11. IDOR Test Matrix

For a resource:

```text
Todo A → User A
Todo B → User B
```

Test:

|Request|Expected|
|---|---|
|User A → Todo A|✅|
|User B → Todo B|✅|
|User A → Todo B|❌|
|User B → Todo A|❌|
|Anonymous → Todo A|❌|

Do this for:

```text
GET
PUT
PATCH
DELETE
```

Not just GET.

---

# 12. Checklist #4 — Mass Assignment

Suppose your API expects:

```json
{
  "title": "Learn Node"
}
```

An attacker sends:

```json
{
  "title": "Learn Node",
  "role": "admin",
  "isAdmin": true,
  "userId": "another-user"
}
```

Your backend should ignore/reject fields that aren't allowed.

Test:

```text
[ ] role cannot be injected
[ ] userId cannot be changed
[ ] ownerId cannot be changed
[ ] isAdmin cannot be injected
[ ] internal fields cannot be changed
```

---

# 13. Test Update Operations Carefully

These are especially important:

```http
PUT /users/:id
PATCH /users/:id
POST /users
```

Because attackers frequently target writable fields.

Your service should explicitly decide:

```text
Allowed:
name
bio
avatar

Not allowed:
role
ownerId
passwordHash
refreshTokenHash
```

---

# 14. Checklist #5 — Input Validation

For every input field, test:

```text
normal value
empty value
missing value
wrong type
too long
too short
unexpected field
malformed format
special characters
nested object
array instead of string
null
```

Example:

```json
{
  "title": 123
}
```

If `title` must be a string:

```text
400 Bad Request
```

---

# 15. Injection Testing

Your earlier lesson covered injection.

Test inputs containing:

```text
$ne
$gt
$regex
$or
```

and other database/query operators where relevant.

For example, don't blindly allow:

```json
{
  "email": {
    "$ne": null
  }
}
```

to become a MongoDB query.

Your validation layer should control the input shape.

---

# 16. NoSQL Injection Test

Imagine login expects:

```json
{
  "email": "user@example.com",
  "password": "secret"
}
```

Attacker tries:

```json
{
  "email": {
    "$ne": null
  },
  "password": {
    "$ne": null
  }
}
```

Your test should verify:

```text
Request
 ↓
Validation
 ↓
Rejected
```

not:

```text
Request
 ↓
MongoDB query
 ↓
Unexpected authentication
```

---

# 17. Checklist #6 — Rate Limiting

You already tested the concept in 22.8.

Now turn it into explicit checks.

Sensitive endpoints:

```text
POST /login
POST /forgot-password
POST /reset-password
POST /refresh
```

Test:

```text
Request 1 → allowed
Request 2 → allowed
...
Request N → allowed
Request N+1 → rejected
```

Expected:

```http
429 Too Many Requests
```

---

# 18. Rate-Limit Checklist

Check:

```text
[ ] Login rate limit
[ ] Password-reset rate limit
[ ] OTP/email verification rate limit
[ ] Refresh endpoint protection where appropriate
[ ] Public API rate limit
[ ] Expensive endpoint rate limit
[ ] Correct 429 response
[ ] Retry-After where appropriate
```

Also test that your limiter isn't accidentally disabled in production.

---

# 19. Checklist #7 — JWT Security

Test:

```text
[ ] Invalid signature
[ ] Expired token
[ ] Missing token
[ ] Malformed token
[ ] Wrong algorithm
[ ] Wrong issuer
[ ] Wrong audience
[ ] Missing required claims
[ ] Unexpected claims
```

Also verify that your application doesn't blindly trust claims.

For example:

```json
{
  "role": "admin"
}
```

inside a token isn't automatically proof that the user should have admin privileges if your token issuance/validation architecture doesn't guarantee that claim's integrity and freshness.

---

# 20. JWT Secret Test

One critical operational test:

```text
Can the server start without JWT secrets?
```

Your configuration should fail safely.

Bad:

```text
JWT_SECRET undefined
     ↓
application still starts
```

Better:

```text
JWT_SECRET missing
     ↓
configuration validation fails
     ↓
application doesn't start
```

This is much safer than silently running with insecure defaults.

---

# 21. Checklist #8 — Refresh Tokens

Refresh tokens need their own test group.

Test:

```text
Valid refresh token
        ↓
new access token
```

Then:

```text
Same refresh token again
        ↓
Should be rejected if rotation invalidated it
```

Also test:

```text
Expired refresh token
Invalid refresh token
Revoked refresh token
Wrong user
Malformed token
```

---

# 22. Refresh Token Rotation Test

Suppose:

```text
RT1
 ↓
/refresh
 ↓
RT2
```

After rotation:

```text
RT1
 ↓
/refresh
 ↓
❌ reject
```

while:

```text
RT2
 ↓
/refresh
 ↓
✅ accepted
```

This is a very valuable security test.

# 23. Checklist #9 — Cookies

Your tests should inspect cookie attributes.

For an authentication cookie, verify the appropriate configuration includes things such as:

```text
HttpOnly
Secure
SameSite
Path
Max-Age / Expires
```

Don't blindly test only the cookie's existence.

Test its security attributes too.

---

# 24. Cookie Security Test

Conceptually:

```js
const cookies = response.headers["set-cookie"];
```

Then verify the relevant attributes:

```text
HttpOnly ✓
Secure ✓
SameSite ✓
```

depending on your environment and intended architecture.

For local HTTP development, you may intentionally configure `Secure` differently. Your production test should verify the production configuration.

---

# 25. Checklist #10 — CORS

Test your CORS policy.

Trusted origin:

```text
https://app.example.com
```

Expected:

```text
allowed
```

Attacker origin:

```text
https://evil.example
```

Expected:

```text
not allowed
```

Also test:

```text
http://app.example.com
https://evil.example
null
unexpected subdomain
```

depending on your threat model.

---

# 26. Don't Use This as Your CORS Test

Avoid thinking:

```text
"Response doesn't contain Access-Control-Allow-Origin,
therefore the request is secure."
```

Your test should verify the actual browser-facing policy and server behavior.

Remember:

```text
CORS ≠ authentication
CORS ≠ authorization
CORS ≠ CSRF protection
```

---

# 27. Checklist #11 — CSRF

For cookie-authenticated state-changing endpoints:

```text
[ ] Missing CSRF token rejected
[ ] Invalid CSRF token rejected
[ ] Wrong Origin rejected where Origin validation is used
[ ] Valid CSRF token accepted
[ ] Valid trusted Origin accepted
[ ] SameSite configuration matches architecture
```

Test important endpoints:

```text
POST
PUT
PATCH
DELETE
```

especially those using automatically attached cookies.

---

# 28. Example CSRF Test

Valid:

```text
Cookie ✓
Origin ✓
CSRF token ✓
        ↓
200
```

Missing token:

```text
Cookie ✓
Origin ✓
CSRF token ✗
        ↓
403
```

Malicious origin:

```text
Cookie ✓
Origin = evil.example
        ↓
403
```

This is exactly the type of test you should eventually automate.

# 29. Checklist #12 — Sensitive Data Exposure

Inspect every response.

Look specifically for:

```text
[ ] password
[ ] passwordHash
[ ] refreshToken
[ ] refreshTokenHash
[ ] resetToken
[ ] resetTokenHash
[ ] JWT secrets
[ ] database credentials
[ ] API keys
[ ] internal security metadata
[ ] stack traces
[ ] database errors
```

None should accidentally leak through normal API responses.

---

# 30. Test Error Responses

Force an error.

For example:

```text
GET /api/v1/todos/invalid-id
```

or intentionally trigger an internal error in a test environment.

Verify production-style responses don't expose:

```text
MongoDB details
file paths
stack traces
environment variables
secret values
internal implementation details
```

Instead:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "req_123"
}
```

---

# 31. Checklist #13 — Account Enumeration

Test:

```text
POST /forgot-password
```

with:

```text
existing@example.com
```

and:

```text
doesnotexist@example.com
```

The external behavior should avoid unnecessarily revealing whether the account exists.

Similarly, login should avoid overly specific messages such as:

```text
"Email doesn't exist"
```

versus:

```text
"Password incorrect"
```

when account enumeration is a concern.

---

# 32. Checklist #14 — Security Headers

Check your production responses for appropriate security headers.

For example, depending on your application:

```text
Content-Security-Policy
X-Content-Type-Options
Referrer-Policy
Strict-Transport-Security
```

and other headers appropriate to your deployment.

If you're using a security middleware such as Helmet, test the resulting headers rather than assuming the middleware is configured correctly.

---

# 33. Checklist #15 — HTTP Method Abuse

Test whether sensitive operations are accessible through unexpected methods.

For example:

```http
GET /api/v1/users/delete/123
```

shouldn't perform deletion.

Test:

```text
GET
POST
PUT
PATCH
DELETE
OPTIONS
HEAD
```

where relevant.

Your API should behave according to its defined HTTP contract.

---

# 34. Checklist #16 — Resource Limits

Security isn't only about authentication.

Test oversized input.

For example:

```text
10 MB JSON body
100 MB JSON body
huge array
huge string
huge query parameter
```

Your backend should have reasonable limits.

Otherwise an attacker may consume:

```text
RAM
CPU
database resources
network bandwidth
```

---

# 35. Checklist #17 — File Uploads

If your backend supports uploads, test:

```text
wrong extension
wrong MIME type
huge file
empty file
malicious filename
path traversal filename
unexpected content
too many files
```

For example:

```text
../../some-file
```

should never allow an attacker to control filesystem paths directly.

If your current backend doesn't support uploads, mark this:

```text
N/A
```

Don't invent security features you don't need.

---

# 36. Checklist #18 — HTTP Parameter Pollution

Suppose:

```text
?role=user&role=admin
```

or:

```text
?id=123&id=456
```

How does your backend interpret duplicate parameters?

Test it.

Your validation layer should have a predictable policy.

---

# 37. Checklist #19 — Prototype Pollution

If your application merges user-controlled objects, test carefully around:

```text
__proto__
constructor
prototype
```

Especially when using generic object merge utilities.

Don't blindly merge:

```js
Object.assign(target, req.body);
```

for security-sensitive objects.

---

# 38. Checklist #20 — Logging Security

Search your logs for:

```text
password
token
authorization
cookie
secret
apiKey
```

You should not find real secrets.

A useful security test is:

```text
Perform login
 ↓
Inspect logs
 ↓
No password
No access token
No refresh token
No cookie
```

This connects directly to your Phase 19 logging architecture.

---

# 39. Checklist #21 — Database Security

Test:

```text
[ ] Database isn't publicly exposed unnecessarily
[ ] Application uses least-privileged DB credentials
[ ] Production credentials aren't hardcoded
[ ] MongoDB authentication is enabled where required
[ ] TLS is used where appropriate
[ ] Sensitive fields aren't returned unnecessarily
[ ] Indexes don't accidentally create unintended data behavior
```

Your application security doesn't end at Express.

---

# 40. Checklist #22 — Secrets Management

Search the repository:

```bash
grep -R "JWT_SECRET" .
grep -R "password" .
grep -R "api_key" .
grep -R "mongodb+srv" .
```

Then inspect the results.

Look for:

```text
.env
source code
tests
README
Dockerfile
docker-compose.yml
Git history
```

Real production secrets should not be sitting in the codebase.

# 41. Checklist #23 — Configuration

Test what happens when configuration is missing.

For example:

```text
JWT_SECRET missing
MONGO_URI missing
COOKIE configuration missing
required API key missing
```

Expected behavior:

```text
Application refuses to start safely
```

rather than:

```text
Application starts with insecure defaults
```

# 42. Checklist #24 — Error Handling

Force errors at different layers:

```text
validation
controller
service
repository
database
external service
```

Verify:

```text
No crash
No secret leakage
Consistent response
Correct status code
Request ID available
Error logged internally
```

# 43. Checklist #25 — API Abuse

Don't only test individual requests.

Test sequences.

For example:

```text
Login
 ↓
Refresh
 ↓
Refresh again
 ↓
Logout
 ↓
Refresh old token
```

Expected:

```text
old credentials rejected
```

Another:

```text
Create resource
 ↓
Delete resource
 ↓
Try to access deleted resource
```

Expected behavior should match your soft/hard-delete design.

Security bugs often appear in **sequences**, not individual requests.

# 44. Build a Security Test Matrix

This is one of the most useful things you can create.

For every endpoint:

|Endpoint|Auth|Role|Ownership|Validation|Rate Limit|CSRF|Sensitive Data|
|---|---|---|---|---|---|---|---|
|`/auth/login`|❌|—|—|✅|✅|Depends|✅|
|`/auth/refresh`|Cookie|—|—|✅|✅|Depends|✅|
|`/users/me`|✅|User|Self|✅|Maybe|Depends|✅|
|`/todos`|✅|User|Own|✅|Maybe|Depends|✅|
|`/admin/users`|✅|Admin|—|✅|Maybe|Depends|✅|

The exact requirements depend on your application, but the **matrix itself** is valuable.

It forces you to think endpoint-by-endpoint.

# 47. Example: Complete Security Review

Suppose you build:

```http
PATCH /api/v1/todos/:id
```

Your security review becomes:

### Authentication

```text
No token → 401
Invalid token → 401
Expired token → 401
```

### Authorization

```text
Normal user → allowed only for own todo
Admin → according to policy
```

### IDOR

```text
User A → User B's todo → reject
```

### Mass assignment

```json
{
  "title": "New title",
  "userId": "attacker"
}
```

Expected:

```text
userId cannot be changed
```

### Validation

```text
title = number
title = huge string
title = null
```

Expected:

```text
400
```

### Injection

```json
{
  "title": {
    "$ne": null
  }
}
```

Expected:

```text
reject
```

### Sensitive data

Response should not contain:

```text
passwordHash
refreshTokenHash
```

### Rate limit

Repeated abusive requests:

```text
429
```

That's a real security test plan.

# 48. Security Testing Is Not Just "Try Hacking It"

This is an important professional mindset.

Security testing has three stages:

```text
Threat
  ↓
Control
  ↓
Verification
```

Example:

```text
Threat:
User A accesses User B's todo

Control:
Ownership query

Verification:
Automated IDOR test
```

Another:

```text
Threat:
Brute-force login

Control:
Rate limiter

Verification:
Repeated login test
```

Another:

```text
Threat:
Refresh-token replay

Control:
Token rotation

Verification:
Reuse old token → expect rejection
```

This makes security testing systematic instead of random.
