# 2. Security Tests Are Negative Tests

A normal test often says:

```js
it("allows a valid user to create a todo", ...)
```

A security test asks:

```js
it("rejects an unauthenticated user", ...)
```

or:

```js
it("prevents User A from accessing User B's todo", ...)
```

or:

```js
it("rejects an injected MongoDB operator", ...)
```

So remember:

> **Security tests intentionally try to make your application break its security rules.**

# 4. The First Rule: Tests Must Be Independent

Never let this happen:

```text
Test A
 ↓
creates user

Test B
 ↓
assumes user from Test A exists

Test C
 ↓
assumes token from Test B
```

Instead:

```text
Test A
 ↓
setup
 ↓
test
 ↓
cleanup

Test B
 ↓
setup
 ↓
test
 ↓
cleanup
```

This is the same test-isolation principle you learned in Phase 21.

Security tests especially need isolation because authentication state can easily make a test appear secure when it isn't.

# 6. Authentication Test Suite

Start with:

```text
authentication.security.test.js
```

Your first test:

```js
it("rejects requests without authentication", async () => {
    const response = await request(app)
        .get("/api/v1/users/me");

    expect(response.status).toBe(401);
});
```

That's a simple security test.

The important thing isn't the syntax.

It's the security property:

> **Protected endpoints must reject anonymous requests.**

---

# 7. Invalid Token Test

```js
it("rejects an invalid access token", async () => {
    const response = await request(app)
        .get("/api/v1/users/me")
        .set("Authorization", "Bearer invalid-token");

    expect(response.status).toBe(401);
});
```

Your test suite should never assume that:

```text
Authorization header exists
```

means:

```text
user is authenticated
```

The token must actually be valid.

---

# 8. Malformed Token

Test:

```js
.set("Authorization", "Bearer abc.def")
```

Expected:

```text
401
```

Also consider:

```text
Bearer
Bearer null
Bearer undefined
empty header
multiple spaces
```

The exact cases depend on your authentication middleware.

---

# 9. Expired JWT Test

Create an expired token in your test helper.

Conceptually:

```js
const token = signTestToken({
    userId: userA.id,
    expiresIn: "-1s"
});
```

Then:

```js
const response = await request(app)
    .get("/api/v1/users/me")
    .set("Authorization", `Bearer ${token}`);

expect(response.status).toBe(401);
```

This verifies that your middleware actually checks expiration.

---

# 10. Wrong Secret Test

Create a token using a different secret:

```js
const forgedToken = jwt.sign(
    { userId: userA.id },
    "attacker-secret"
);
```

Then send it.

Expected:

```text
401
```

This verifies that your server isn't merely decoding JWTs.

It must **verify their signatures**.

You should eventually have:

|Scenario|Expected|
|---|--:|

# 12. Authorization Tests

Now create:

```text
authorization.security.test.js
```

Test:

```text
User
Admin
```

Suppose:

```http
DELETE /api/v1/users/123
```

is admin-only.

Test:

```js
it("rejects a normal user from an admin endpoint", async () => {
    const token = await loginAs(userA);

    const response = await request(app)
        .delete(`/api/v1/users/${userB.id}`)
        .set("Authorization", `Bearer ${token}`);

    expect(response.status).toBe(403);
});
```

Then:

```js
it("allows an admin", async () => {
    const token = await loginAs(admin);

    const response = await request(app)
        .delete(`/api/v1/users/${userB.id}`)
        .set("Authorization", `Bearer ${token}`);

    expect(response.status).not.toBe(403);
});
```

# 13. IDOR Security Test

This is one of the most important tests in your entire backend.

Create:

```text
User A
User B

Todo A → belongs to User A
Todo B → belongs to User B
```

Then:

```js
it("prevents User A from accessing User B's todo", async () => {
    const tokenA = await loginAs(userA);

    const response = await request(app)
        .get(`/api/v1/todos/${todoB.id}`)
        .set("Authorization", `Bearer ${tokenA}`);

    expect([403, 404]).toContain(response.status);
});
```

The exact status depends on your API design.

But:

```text
200 + Todo B data
```

must never happen.

---

# 14. Test IDOR on Every Operation

Don't stop at:

```text
GET
```

Test:

```text
GET    /todos/:id
PATCH  /todos/:id
PUT    /todos/:id
DELETE /todos/:id
```

For each:

```text
User A → own resource → allowed
User A → User B resource → rejected
```

This is a much stronger security suite.

---

# 15. Why One IDOR Test Isn't Enough

Imagine:

```text
GET /todos/:id
```

is secure:

```js
Todo.findOne({
    _id: id,
    userId
});
```

But your delete method does:

```js
Todo.findByIdAndDelete(id);
```

Now:

```text
GET → secure
DELETE → vulnerable
```

That's why security testing must cover the **whole CRUD surface**.

# 16. Mass Assignment Test

Suppose users can update:

```json
{
  "title": "My Todo"
}
```

The attacker sends:

```json
{
  "title": "My Todo",
  "userId": "another-user",
  "role": "admin",
  "isAdmin": true
}
```

Test:

```js
it("does not allow protected fields to be mass assigned", async () => {
    const token = await loginAs(userA);

    const response = await request(app)
        .patch(`/api/v1/todos/${todoA.id}`)
        .set("Authorization", `Bearer ${token}`)
        .send({
            title: "Updated",
            userId: userB.id,
            isAdmin: true
        });

    expect(response.status).toBe(200);

    const updatedTodo = await getTodo(todoA.id);

    expect(updatedTodo.userId).toBe(userA.id);
});
```

This tests a very important security property:

> User-controlled fields must not overwrite ownership/security fields.

# 17. Injection Tests

Create:

```text
injection.security.test.js
```

Test MongoDB operator payloads.

For example:

```js
const maliciousPayload = {
    email: {
        $ne: null
    },
    password: {
        $ne: null
    }
};
```

Send it to login.

Expected:

```text
400
```

or:

```text
401
```

but **never successful authentication**.

---

# 18. Test Query Parameters Too

Injection doesn't only happen through JSON bodies.

Test:

```text
?email[$ne]=null
```

or whatever representation your parser accepts.

Also test:

```text
?role[$in][]=admin
```

and similar operator-style input where relevant.

Your validation and sanitization layers should prevent attacker-controlled query objects from becoming database operators.

---

# 19. Rate-Limit Tests

Create:

```text
rate-limit.security.test.js
```

Suppose login allows a limited number of attempts.

```js
for (let i = 0; i < LIMIT; i++) {
    await request(app)
        .post("/api/v1/auth/login")
        .send({
            email: userA.email,
            password: "wrong-password"
        });
}
```

Then:

```js
const response = await request(app)
    .post("/api/v1/auth/login")
    .send({
        email: userA.email,
        password: "wrong-password"
    });

expect(response.status).toBe(429);
```

You have now tested an actual security control.

---

# 20. Be Careful With Rate-Limit Tests

A rate limiter can make tests flaky if:

```text
Test A
 ↓
uses same IP

Test B
 ↓
uses same IP

Test C
 ↓
gets blocked unexpectedly
```

So your test environment may need:

```text
reset limiter state
```

or a dedicated test configuration.

The principle is:

> **A security test should be deterministic.**

# 22. Refresh Token Tests

Create:

```text
refresh-token.security.test.js
```

Test the complete lifecycle:

```text
Login
 ↓
RT1
 ↓
Refresh
 ↓
RT2
 ↓
RT1 should fail
 ↓
RT2 should work
```

Example:

```js
it("rejects a rotated refresh token", async () => {
    const first = await loginAndGetRefreshToken(userA);

    const second = await refresh(first);

    const replay = await refresh(first);

    expect(replay.status).toBe(401);
});
```

This is one of the highest-value security tests if your architecture uses refresh-token rotation.

---

# 23. Logout Test

If logout revokes/invalidates refresh credentials:

```text
Login
 ↓
RT1
 ↓
Logout
 ↓
RT1
 ↓
Refresh
 ↓
❌
```

Test it.

```js
it("rejects refresh after logout", async () => {
    const session = await login(userA);

    await logout(session);

    const response = await refresh(session.refreshToken);

    expect(response.status).toBe(401);
});
```

The exact implementation depends on your cookie/token architecture.

---

# 24. Cookie Security Tests

Inspect:

```js
response.headers["set-cookie"]
```

Then verify relevant attributes.

Conceptually:

```text
HttpOnly ✓
Secure ✓
SameSite ✓
```

For production configuration.

Example:

```js
expect(cookie).toMatch(/HttpOnly/i);
expect(cookie).toMatch(/SameSite=/i);
```

If your production environment requires `Secure`:

```js
expect(cookie).toMatch(/Secure/i);
```

Don't blindly force production cookie requirements onto an HTTP-only local development test.

---

# 25. CORS Tests

Create:

```text
cors.security.test.js
```

Trusted origin:

```js
const response = await request(app)
    .get("/api/v1/users/me")
    .set("Origin", "https://app.example.com");
```

Then verify the expected CORS behavior.

Test an untrusted origin:

```js
.set("Origin", "https://evil.example");
```

The important thing is that your CORS configuration does not accidentally trust arbitrary origins.

---

# 26. CORS With Credentials

If your architecture uses cookies, this becomes especially important.

Check that your configuration doesn't accidentally produce:

```text
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

That combination is not a valid permissive credentialed CORS design.

Your test should reflect your actual trusted-origin configuration.

---

# 27. CSRF Tests

For cookie-authenticated state-changing requests:

```text
POST
PUT
PATCH
DELETE
```

test:

```text
Missing CSRF token → reject
Invalid CSRF token → reject
Malicious origin → reject
Valid token → allow
```

For example:

```js
it("rejects a state-changing request without CSRF protection", async () => {
    const response = await request(app)
        .post("/api/v1/todos")
        .send({
            title: "Attack"
        });

    expect(response.status).toBe(403);
});
```

Whether this exact test applies depends on whether your endpoint relies on cookies and how your CSRF architecture is implemented.

---

# 28. Sensitive Data Tests

Create:

```text
data-exposure.security.test.js
```

Login:

```js
const response = await login(userA);
```

Then check:

```js
expect(response.body).not.toHaveProperty("password");
expect(response.body).not.toHaveProperty("passwordHash");
expect(response.body).not.toHaveProperty("refreshTokenHash");
```

For `/me`:

```js
const response = await request(app)
    .get("/api/v1/users/me")
    .set("Authorization", `Bearer ${token}`);

expect(response.body.data).not.toHaveProperty("password");
expect(response.body.data).not.toHaveProperty("refreshTokenHash");
```

This directly verifies what you learned in **22.14**.

---

# 29. Error Exposure Tests

Force an error and inspect the response.

You want to ensure the client doesn't receive:

```text
MongoError
stack trace
filesystem path
JWT secret
database URI
environment variables
```

For example:

```js
expect(response.body).not.toHaveProperty("stack");
expect(JSON.stringify(response.body)).not.toContain(process.env.JWT_SECRET);
```

Be careful with test design around intentionally triggering internal errors.

---

# 30. Test Account Enumeration

For password reset:

```text
existing account
unknown account
```

Compare their external responses.

You want your public response to avoid revealing unnecessary account existence information.

For example:

```js
expect(existing.body.message)
    .toBe(unknown.body.message);
```

The exact contract is yours, but the security property should be explicit.

# 32. Don't Hide the Security Property

Bad:

```js
it("works", async () => {
    // 40 lines of setup
});
```

Good:

```js
it("prevents User A from accessing User B's todo", async () => {
    // setup
    // request
    // assertion
});
```

The test name should describe the **security rule**.

Examples:

```text
rejects unauthenticated access
rejects expired access tokens
prevents horizontal privilege escalation
prevents mass assignment
rejects NoSQL injection
rejects refresh-token replay
does not expose password hashes
rejects malicious CORS origin
```

This makes your test suite double as security documentation.

---

# 33. Security Tests Should Test Behavior, Not Implementation

Avoid:

```js
expect(repository.findOne).toHaveBeenCalledWith(...)
```

for an integration security test.

That's testing implementation.

Instead:

```text
User A
 ↓
requests User B's todo
 ↓
HTTP response
 ↓
403/404
```

You're testing the actual security boundary.

Unit tests can still verify repository behavior separately.

# 38. Security Regression Testing

Imagine today:

```text
IDOR test → PASS
```

Six months later, another developer changes:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

to:

```js
Todo.findById(todoId);
```

The application might still pass:

```text
normal CRUD tests
```

but:

```text
security test
   ↓
FAIL
```

That's exactly what we want.

> **Security tests protect security decisions from future code changes.**

---

# 39. Don't Aim for "100% Security"

This is important.

Passing 100 security tests does **not** prove:

```text
"The backend is secure."
```

It means:

```text
"We verified these security properties."
```

Security testing is evidence, not a mathematical proof.

You still need:

```text
Threat modeling
Code review
Dependency updates
Infrastructure security
Secrets management
Monitoring
Penetration testing when appropriate
```

But automated security tests give you a repeatable baseline.
