# Lesson 22.2 — Threat Modeling 🛡️

In **Lesson 22.1**, we learned that security testing asks:

> **“What happens if someone uses my API in a way they shouldn't?”**

Now we need to answer a more important question:

> **“What exactly should I attack, who might attack it, and what could go wrong?”**

That process is called **threat modeling**.

Your Phase 22 roadmap places threat modeling immediately after the introduction to security testing, before we move into specific API attacks such as broken authentication, authorization problems, IDOR, injection, and JWT attacks.

---

# 1. What Is Threat Modeling?

Threat modeling is a structured way of thinking about security **before or while building a system**.

In simple words:

```text
What are we protecting?
        ↓
Who might attack it?
        ↓
How could they attack it?
        ↓
What would happen?
        ↓
How do we prevent it?
        ↓
How do we test the protection?
```

So:

> **Threat modeling helps us decide what security tests we actually need.**

---

# 2. Why Do We Need It?

Imagine you have a MERN application with:

```text
React
   ↓
Express API
   ↓
MongoDB
```

Your backend contains:

```text
Users
Passwords
JWTs
Todos
Email addresses
Refresh tokens
Admin operations
```

You could randomly write hundreds of security tests.

But that's inefficient.

Instead:

```text
Threat model
     ↓
Identify important risks
     ↓
Create security tests
```

For example:

```text
Threat:
User A accesses User B's Todo

       ↓

Security control:
Ownership check

       ↓

Security test:
User A requests User B's Todo

       ↓

Expected:
Request rejected
```

That's much more systematic.

---

# 3. Threat Modeling Is Not Only for Big Companies

You might think:

> "I'm just building a small MERN project. Do I really need threat modeling?"

Yes.

You don't need a 100-page security document.

Even a small API can have:

```text
Authentication
Authorization
Personal data
Database
Admin operations
File uploads
Payments
Emails
Tokens
```

A simple threat model can prevent major mistakes.

---

# 4. Start With Assets

The first question is:

> **What are we trying to protect?**

These are called **assets**.

For our MERN backend, assets might include:

```text
Users
Passwords
Email addresses
Access tokens
Refresh tokens
User data
Todos
Admin privileges
Database
Application secrets
Email accounts
Logs
```

Think of it like:

```text
                YOUR APPLICATION
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Users          Tokens        Database
        │              │              │
        ▼              ▼              ▼
   Personal data    Access       Application data
```

Not every asset has the same importance.

---

# 5. Classify Your Assets

A useful approach is to ask:

### What happens if someone reads it?

Example:

```text
Email address
```

Potential impact:

```text
Privacy leak
```

### What happens if someone modifies it?

Example:

```text
User role
```

Potential impact:

```text
Normal user → Admin
```

That's much more serious.

### What happens if someone deletes it?

Example:

```text
Database records
```

Potential impact:

```text
Data loss
```

### What happens if someone uses it?

Example:

```text
Refresh token
```

Potential impact:

```text
Account takeover
```

So security isn't just about confidentiality.

We also care about:

```text
Confidentiality
Integrity
Availability
```

---

# 6. The CIA Triad

A simple security model is:

```text
        SECURITY
           │
     ┌─────┼─────┐
     ▼     ▼     ▼
     C     I     A
```

## C — Confidentiality

Only authorized people can see the information.

Example:

```text
User A cannot see User B's private Todo.
```

---

## I — Integrity

Unauthorized people cannot modify the information.

Example:

```text
User cannot change:

role: "user"

into:

role: "admin"
```

---

## A — Availability

The system should remain available to legitimate users.

Example:

```text
Attacker sends
100,000 requests
        ↓
Rate limiting
        ↓
Backend remains available
```

This is why rate limiting is also a security control.

---

# 7. Identify Actors

Next question:

> **Who interacts with the system?**

For our backend, we might have:

```text
Guest
User
Admin
Attacker
Third-party email service
Database
```

We can represent it like:

```text
                 API
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
     Guest       User       Admin
       │          │          │
       └──────────┼──────────┘
                  ▼
               MongoDB
```

The important thing is that **different actors have different capabilities**.

---

# 8. The Attacker Is an Actor Too

Don't think:

> "The attacker is some mysterious hacker."

For API security testing, an attacker could simply be:

```text
Unauthenticated visitor
```

or:

```text
Normal authenticated user
```

This is important.

A normal user can become an attacker against another user's data.

Example:

```text
User A
  ↓
legitimate account
  ↓
tries accessing
  ↓
User B's resource
```

That's why authorization testing is so important.

---

# 9. Identify Trust Boundaries

This is one of the most useful concepts in threat modeling.

A **trust boundary** is where data moves from one level of trust to another.

Our backend:

```text
Internet
   │
   │ UNTRUSTED
   ▼
Express
   │
   ▼
Middleware
   │
   ▼
Application
   │
   ▼
Database
```

The biggest boundary is:

```text
Internet
   ↓
Your API
```

Anything coming from the internet should be considered:

> **Untrusted until validated and authorized.**

That includes:

```text
req.body
req.params
req.query
headers
cookies
JWTs
uploaded files
```

---

# 10. Never Trust the Client

This is one of the most important backend security principles.

Suppose React sends:

```json
{
  "role": "admin"
}
```

The backend should NOT think:

> "React sent it, so it must be valid."

The browser is controlled by the user.

An attacker can completely ignore your React application and directly call:

```http
POST /api/v1/users
```

using:

```text
curl
Postman
Burp Suite
custom scripts
browser developer tools
```

Therefore:

```text
Frontend validation
        ≠
Backend security
```

The backend must enforce its own rules.

Potentially everywhere.

# 12. Mark the Attack Surfaces

An **attack surface** is a place where an attacker can interact with your system.

For an API:

```text
Routes
   │
   ├── Request body
   ├── Query parameters
   ├── URL parameters
   ├── Headers
   ├── Cookies
   ├── Authentication
   └── File uploads
```

For example:

```http
POST /api/v1/auth/login
```

Attack surfaces include:

```text
email
password
headers
cookies
IP address
request frequency
```

---

# 14. From Threat → Security Control

This is the important transition.

Don't just identify threats.

Map each threat to a defense.

|Threat|Security Control|
|---|---|
|Missing authentication|Auth middleware|
|Invalid JWT|JWT verification|
|User accesses another user's resource|Ownership check|
|Admin privilege abuse|RBAC|
|Invalid input|Validation|
|Injection|Safe queries + sanitization|
|Brute force|Rate limiting|
|Sensitive data exposure|Response filtering|
|CSRF|CSRF defenses|
|Token theft|Secure cookies/token rotation|

Then:

```text
Threat
   ↓
Control
   ↓
Security Test
```

That's the complete security engineering loop.

# 15. Example: IDOR

Let's go through one completely.

### Asset

```text
User Todo
```

### Actor

```text
Authenticated User A
```

### Threat

```text
User A changes todoId
to User B's Todo
```

### Attack

```http
GET /api/v1/todos/456
```

where `456` belongs to User B.

### Security control

Repository checks:

```js
{
    _id: todoId,
    userId: currentUserId
}
```

### Test

```text
User A
 ↓
request Todo B
 ↓
expected rejection
```

That's threat modeling.

# 16. Example: Mass Assignment

### Asset

```text
User role
```

### Actor

```text
Normal user
```

### Threat

User tries:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

### Security control

Allow-list fields:

```js
const allowedFields = [
    "name"
];
```

### Test

```text
Send role=admin
        ↓
Request accepted?
        ↓
Role must remain "user"
```

Again:

```text
Threat
 ↓
Defense
 ↓
Test
```

# 17. Threat Modeling Helps Us Prioritize

Not every threat deserves the same priority.

Consider:

```text
Minor UI information leak
```

versus:

```text
Attacker can become admin
```

Clearly the second is more dangerous.

So ask:

```text
How likely is this?
How serious is the impact?
```

A simple model:

```text
Risk = Likelihood × Impact
```

For example:

|Threat|Likelihood|Impact|Priority|
|---|--:|--:|---|
|Missing auth|High|High|🔴 Critical|
|IDOR|Medium|High|🔴 High|
|Weak rate limiting|High|Medium|🟠 High|
|Minor error detail|Medium|Low|🟡 Medium|

You don't need perfect mathematical precision.

The purpose is to decide:

> **What should we fix/test first?**

Here's the workflow I want you to remember:

```text
        FEATURE
           │
           ▼
      Identify assets
           │
           ▼
      Identify actors
           │

   Identify trust boundaries
           │
```

# 21. Threat Modeling vs Security Testing

Don't mix these up.

### Threat modeling

```text
"What could go wrong?"
```

### Security testing

```text
"Let's verify that it can't go wrong."
```

Example:

```text
Threat model:
User A might access User B's Todo.

        ↓

Security test:
Authenticate as A and request B's Todo.

        ↓

Expected:
Access denied.
```

So:

```text
Threat Modeling
      ↓
Security Testing
```
