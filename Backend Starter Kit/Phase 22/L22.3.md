# Lesson 22.3 — OWASP API Security Risks 🛡️

Now that we understand **threat modeling**, we need a common language for describing API security problems.

For this lesson, we'll use the **OWASP API Security Top 10** categories as the framework. The goal isn't to memorize ten names. The goal is to look at an API and recognize **what kind of security failure you're seeing**.

Your Phase 22 roadmap specifically places OWASP API risks here, before we study broken authentication, IDOR/BOLA, mass assignment, injection, JWT attacks, and the other attack types individually.

---

# 1. What Is OWASP?

**OWASP** stands for:

> **Open Worldwide Application Security Project**

OWASP provides security guidance, educational material, and vulnerability classifications for web applications and APIs.

For you as a backend developer, OWASP is useful because it gives you a structured way to ask:

```text
"How could this API be attacked?"
```

Instead of relying only on your own imagination.

---

# 2. What Is the OWASP API Security Top 10?

It's a list of major security risk categories affecting APIs.

Think of it as a:

```text
Security checklist
      +
Common vulnerability map
      +
Testing guide
```

For our backend, we'll repeatedly encounter these categories:

```text
1. Broken Object Level Authorization
2. Broken Authentication
3. Broken Object Property Level Authorization
4. Unrestricted Resource Consumption
5. Broken Function Level Authorization
6. Unrestricted Access to Sensitive Business Flows
7. Server-Side Request Forgery
8. Security Misconfiguration
9. Improper Inventory Management
10. Unsafe Consumption of APIs
```

The exact names matter less than understanding the **security idea behind each one**.

---

# 3. The Most Important Pattern

Look at the first few categories:

```text
Object
   ↓
Property
   ↓
Function
```

They are asking different authorization questions.

### Object

> Can you access this resource?

### Property

> Can you modify this particular field?

### Function

> Can you perform this operation?

This distinction will become extremely important in our later lessons.

---

# 4. #1 — Broken Object Level Authorization

We'll call this:

> **BOLA**

You may also hear:

> **IDOR**

The basic problem:

```text
User A
   ↓
requests
   ↓
User B's object
```

Example:

```http
GET /api/v1/todos/500
```

Suppose Todo `500` belongs to User B.

If User A can retrieve it just by knowing the ID:

```text
❌ Broken Object Level Authorization
```

A secure query should include ownership:

```js
Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

So:

```text
Object ID
   +
Current User
   ↓
Authorized?
```

This is one of the most important vulnerabilities for your future MERN APIs.

---

# 5. Why BOLA Is So Dangerous

Imagine:

```text
/users/101
/users/102
/users/103
```

An attacker might try:

```text
101
102
103
104
105
...
```

If your API only checks:

```js
User.findById(id)
```

then knowing an ID could be enough to access another user's data.

This is why:

```text
Authentication
      ≠
Object authorization
```

A user can be correctly authenticated and still be unauthorized to access a particular object.

---

# 6. #2 — Broken Authentication

This category involves weaknesses in proving or maintaining identity.

Examples:

```text
Weak login protection
Bad token validation
Improper session handling
Weak password reset
Incorrect JWT verification
```

For example:

```text
Attacker
   ↓
stolen/invalid token
   ↓
API
   ↓
accepts token
```

That's an authentication failure.

We'll study this deeply in:

```text
22.4 Broken Authentication
```

---

# 7. Authentication vs Authorization

Keep this distinction clear:

```text
Authentication
    ↓
"Who are you?"

Authorization
    ↓
"What are you allowed to do?"
```

Example:

```text
Rahul logs in
    ↓
Authentication ✅
```

But:

```text
Rahul tries to access Admin Dashboard
    ↓
Authorization ❌
```

This distinction will appear throughout Phase 22.

---

# 8. #3 — Broken Object Property Level Authorization

This is about **fields inside an object**.

Imagine:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "user"
}
```

A normal user should be able to change:

```text
name
```

But probably not:

```text
role
```

or:

```text
passwordHash
refreshTokenHash
```

A vulnerable API might do:

```js
User.findByIdAndUpdate(
    userId,
    req.body
);
```

Now the client controls every field.

An attacker could send:

```json
{
  "role": "admin"
}
```

That's a property-level authorization problem.

---

# 9. Object vs Property

This distinction is worth memorizing.

### Object-level problem

```text
Can User A access User B's Todo?
```

### Property-level problem

```text
User can access their own Todo,
but can they modify a protected field?
```

Think:

```text
Object
 ├── title
 ├── completed
 ├── userId
 └── internalStatus
```

Authorization may apply to:

```text
the entire object
```

and separately to:

```text
individual properties
```

---

# 10. #4 — Unrestricted Resource Consumption

This is about attackers consuming too many resources.

For example:

```text
CPU
Memory
Database queries
Network bandwidth
Email sending
File storage
API requests
```

Imagine:

```http
POST /api/v1/auth/forgot-password
```

If there is no protection, an attacker could repeatedly request emails:

```text
request
request
request
request
...
```

Your email provider gets flooded.

Another example:

```http
GET /api/v1/todos?limit=1000000
```

If your API accepts unlimited values:

```text
MongoDB
   ↓
1,000,000 documents
   ↓
memory/CPU/network
```

That's a resource-consumption problem.

Controls include:

```text
Rate limiting
Pagination limits
Request size limits
Query limits
Timeouts
Cost controls
```

We'll test these later.

---

# 11. #5 — Broken Function Level Authorization

This is different from object-level authorization.

Here the question is:

> **Can this user execute a function they shouldn't be allowed to execute?**

Imagine:

```text
POST /api/v1/users
```

Only admins should create users.

But a normal user can call the endpoint directly:

```text
Normal User
     ↓
POST /users
     ↓
200 OK
```

That's a function-level authorization problem.

---

# 12. Object vs Function

Compare:

### BOLA

```text
Can I access Todo #500?
```

### Function-level authorization

```text
Can I execute DELETE /users/:id?
```

### Property-level authorization

```text
Can I change the role field?
```

So:

```text
Object
   → Which resource?

Property
   → Which field?

Function
   → Which operation?
```

This three-way distinction is extremely useful.

---

# 13. #6 — Unrestricted Access to Sensitive Business Flows

This category is about legitimate application features that can be abused at scale or in unintended ways.

Example:

```text
Forgot password
```

The feature itself is valid.

But imagine an attacker can repeatedly trigger:

```text
Send password-reset email
```

Another example:

```text
Coupon redemption
```

A legitimate user should redeem a coupon once.

But if the API doesn't enforce the business rule:

```text
Redeem
Redeem
Redeem
Redeem
```

the attacker abuses a legitimate business process.

So this is not necessarily a traditional technical exploit.

It's often:

> **“The API allows a valid feature to be abused.”**

---

# 14. #7 — Server-Side Request Forgery

This is usually called:

> **SSRF**

Imagine your backend has:

```http
POST /api/v1/import
```

and accepts:

```json
{
  "url": "https://example.com/data.json"
}
```

Your server does:

```text
Backend
   ↓
fetch(url)
   ↓
external server
```

Now an attacker may try to make your server request an internal resource.

Conceptually:

```text
Attacker
   ↓
Your API
   ↓
Server makes request
   ↓
Internal service
```

The important idea:

> **The attacker controls where your server connects.**

SSRF becomes especially important when your backend:

```text
fetches URLs
downloads files
processes webhooks
imports remote data
generates previews
```

We'll cover this separately later.

---

# 15. #8 — Security Misconfiguration

This is extremely common.

Examples:

```text
Debug mode enabled
Weak CORS configuration
Missing security headers
Default credentials
Overly detailed errors
Unnecessary endpoints
Bad cookie configuration
Incorrect environment variables
Open database
```

For example:

```js
app.use(cors({
    origin: "*",
    credentials: true
}));
```

A careless configuration can create security problems.

Another example:

```text
NODE_ENV=development
```

being accidentally used in production.

Security testing should therefore inspect **configuration**, not just application logic.

---

# 16. #9 — Improper Inventory Management

This sounds complicated but is actually simple.

It means:

> **You don't properly know what APIs, endpoints, versions, or services you have.**

Imagine your application officially uses:

```text
/api/v1/users
```

But an old version still exists:

```text
/api/v0/users
```

and nobody remembers it.

That old endpoint might have:

```text
Old authentication
Old validation
Old security rules
```

An attacker finds it.

This is why API inventory matters.

You should know:

```text
What endpoints exist?
Which versions exist?
Which are public?
Which require authentication?
Which are deprecated?
```

---

# 17. #10 — Unsafe Consumption of APIs

Modern applications rarely work alone.

Your backend might call:

```text
Stripe
Resend
Cloudinary
Google APIs
GitHub
OpenAI
Another internal API
```

Example:

```text
Your backend
      ↓
Third-party API
      ↓
Response
      ↓
Your application
```

A dangerous assumption is:

> "It's an external API, so its response must be safe."

You should still:

```text
Validate
Normalize
Handle errors
Set timeouts
Limit data
Verify authentication
```

And avoid blindly trusting external data.

# 19. How This Maps to Your MERN Backend

Suppose you build:

```text
POST   /api/v1/auth/login
POST   /api/v1/auth/refresh

GET    /api/v1/todos
GET    /api/v1/todos/:id
POST   /api/v1/todos
PATCH  /api/v1/todos/:id
DELETE /api/v1/todos/:id

GET    /api/v1/admin/users
PATCH  /api/v1/admin/users/:id
```

We can immediately identify security questions.

### Authentication

```text
/api/v1/auth/*
```

Ask:

```text
Can tokens be bypassed?
Can refresh tokens be abused?
```

### Object authorization

```text
/todos/:id
```

Ask:

```text
Can User A access User B's Todo?
```

### Property authorization

```text
PATCH /users/:id
```

Ask:

```text
Can user modify role?
Can user modify internal fields?
```

### Function authorization

```text
/api/v1/admin/*
```

Ask:

```text
Can a normal user call these endpoints?
```

### Resource consumption

```text
GET /todos
```

Ask:

```text
Can limit become 1,000,000?
```

### SSRF

Any endpoint accepting URLs:

```text
/import
/preview
/webhook
```

Ask:

```text
Can the server be tricked into requesting internal resources?
```

# 20. Don't Try to Memorize the Names Alone

Instead, memorize the questions.

```text
1. Object
   → Can I access another object's data?

2. Authentication
   → Can I become/access an account improperly?

3. Property
   → Can I modify a field I shouldn't?

4. Resource
   → Can I consume too many resources?

5. Function
   → Can I execute an operation I shouldn't?

6. Business flow
   → Can I abuse a legitimate feature?

7. SSRF
   → Can I make the server request something dangerous?

8. Misconfiguration
   → Is the system configured insecurely?

9. Inventory
   → Are forgotten/old APIs exposed?

10. External APIs
   → Are we trusting external data too much?
```

That's far more useful than memorizing acronyms.
