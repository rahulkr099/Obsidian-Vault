# Lesson 22.4 — Broken Authentication 🔐

In the previous lessons:

- **22.1:** We learned what security testing is.
    
- **22.2:** We learned how to identify threats.
    
- **22.3:** We learned the OWASP API security categories.
    

Now we begin our first detailed vulnerability area:

> **Broken Authentication**

Authentication is the system that answers:

> **“Who are you?”**

If an attacker can bypass, manipulate, or abuse that process, we have an authentication vulnerability.

---

# 1. Authentication vs Authorization

This distinction must become automatic for you.

```text
Authentication
     ↓
Who are you?

Authorization
     ↓
What are you allowed to do?
```

Example:

```text
Rahul logs in
     ↓
Username + password
     ↓
Identity verified
     ↓
Authentication ✅
```

Then:

```text
Rahul
  ↓
tries to access /admin
  ↓
Is Rahul allowed?
  ↓
Authorization
```

So:

```text
Authentication → Identity
Authorization  → Permission
```

---

# 2. What Does "Broken Authentication" Mean?

Authentication is broken when an attacker can somehow gain access to an account or authenticated functionality without properly proving their identity.

Common causes include:

```text
Weak login controls
Weak password handling
Improper token validation
Accepting expired tokens
Accepting malformed tokens
Weak password-reset flows
Poor session handling
Missing brute-force protection
Incorrect JWT verification
```

Think:

```text
Attacker
   ↓
Authentication mechanism
   ↓
Can bypass/manipulate it?
   ↓
YES
   ↓
Broken Authentication
```

---

# 3. Authentication Flow in Our Backend

Let's imagine our MERN backend:

```text
POST /api/v1/auth/login
```

The normal flow is:

```text
Client
  │
  │ email + password
  ▼
Route
  │
  ▼
Validation
  │
  ▼
Auth Controller
  │
  ▼
Auth Service
  │
  ▼
Find User
  │
  ▼
Verify Password
  │
  ▼
Generate Tokens
  │
  ▼
Response
```

Security testing asks:

> **Can I make this flow succeed when I shouldn't?**

---

# 4. Test #1 — Missing Credentials

Start with the simplest attack.

Send:

```http
POST /api/v1/auth/login
Content-Type: application/json

{}
```

Expected:

```text
400 Bad Request
```

or your API's validation equivalent.

It should **not**:

```text
200 OK
```

If an empty request somehow authenticates:

```text
🚨 Critical authentication problem
```

---

# 5. Test #2 — Missing Password

Send:

```json
{
  "email": "user@example.com"
}
```

Expected:

```text
400
```

Not:

```text
200
```

---

# 6. Test #3 — Missing Email

Similarly:

```json
{
  "password": "some-password"
}
```

should fail validation.

The important principle:

> **Authentication should fail closed.**

Meaning:

```text
Unknown/invalid authentication state
             ↓
           DENY
```

Not:

```text
Unknown/invalid state
       ↓
Maybe allow
```

---

# 7. What Does "Fail Closed" Mean?

This is a very useful security concept.

### Fail open

```text
Something goes wrong
       ↓
Access granted
```

Dangerous.

### Fail closed

```text
Something goes wrong
       ↓
Access denied
```

Much safer.

For authentication:

```text
JWT verification error
       ↓
401
```

Not:

```text
JWT verification error
       ↓
Continue request
```

---

# 8. Test #4 — Wrong Password

Normal:

```text
email = user@example.com
password = correct-password
```

→ Login succeeds.

Security test:

```text
email = user@example.com
password = wrong-password
```

Expected:

```text
401 Unauthorized
```

The attacker should not receive an access token.

---

# 9. Test #5 — Nonexistent User

Try:

```text
email = doesnotexist@example.com
password = anything
```

Expected:

```text
401 Unauthorized
```

One important security principle:

> **Don't reveal unnecessary information about whether an account exists.**

Avoid responses like:

```text
"User does not exist."
```

followed by:

```text
"Incorrect password."
```

because attackers can use this to discover valid accounts.

A safer generic response is conceptually:

```text
"Invalid credentials."
```

---

# 10. User Enumeration

This attack is called:

> **User enumeration**

The attacker tries to discover which accounts exist.

For example:

```text
alice@example.com → "User exists"
bob@example.com   → "User doesn't exist"
admin@example.com → "User exists"
```

Now the attacker has learned:

```text
Valid accounts:
alice
admin
```

This information can later be used for:

```text
Password attacks
Phishing
Credential stuffing
Targeted attacks
```

So authentication testing should examine not just **whether login fails**, but **what information failure reveals**.

---

# 11. Timing Differences

There can also be timing-based enumeration.

Imagine:

```text
Existing user
    ↓
Find user
    ↓
Hash password
    ↓
Compare
```

But:

```text
Nonexistent user
    ↓
Return immediately
```

If the timing difference is large and consistent, an attacker may infer whether an account exists.

You don't need to obsess over tiny timing differences in normal applications, but the principle is important:

> **Authentication failures should avoid unnecessarily revealing internal state.**

---

# 12. Test #6 — Extremely Long Credentials

Try unusually large input.

For example:

```text
email = very-large-string
password = very-large-string
```

Why?

Because authentication endpoints are exposed to the internet and can be abused to consume:

```text
CPU
Memory
Database resources
Password-hashing resources
```

Your validation should establish reasonable limits.

Example concept:

```text
email
  ↓
reasonable maximum length

password
  ↓
reasonable maximum length
```

This connects authentication security with **resource consumption** from OWASP.

---

# 13. Test #7 — Brute Force

Suppose the attacker knows:

```text
email = admin@example.com
```

They repeatedly try passwords:

```text
password1
password2
password3
password4
...
```

Without protection:

```text
Attacker
   ↓
Login
Login
Login
Login
Login
...
```

This is a brute-force attack.

Your authentication system should have appropriate protections such as:

```text
Rate limiting
Attempt throttling
Temporary lockouts where appropriate
Monitoring
Strong passwords
MFA where appropriate
```

---

# 14. Authentication Rate Limiting

For example:

```text
Attempt 1 → 401
Attempt 2 → 401
Attempt 3 → 401
...
Too many attempts
       ↓
429 Too Many Requests
```

The exact numbers depend on your application.

The important idea is:

> **Authentication endpoints should not allow unlimited password guesses.**

We'll study rate-limit testing separately in Lesson 22.9.

---

# 15. Credential Stuffing

Brute force and credential stuffing aren't exactly the same.

### Brute force

The attacker tries many possible passwords.

```text
admin@example.com
password1
password2
password3
...
```

### Credential stuffing

The attacker uses credentials stolen from another service.

```text
email: user@example.com
password: leaked-password
```

They try the same credentials on your application.

This works because people sometimes reuse passwords.

Your backend can reduce the impact through:

```text
Rate limiting
MFA
Detection
Strong authentication policies
Breached-password protections
```

# 16. Test #8 — Invalid JWT

Suppose our protected endpoint is:

```http
GET /api/v1/users/me
Authorization: Bearer <token>
```

Now send:

```text
Authorization: Bearer garbage
```

Expected:

```text
401 Unauthorized
```

Not:

```text
500 Internal Server Error
```

And definitely not:

```text
200 OK
```

---

# 17. Test #9 — Missing JWT

Send:

```http
GET /api/v1/users/me
```

without:

```text
Authorization
```

Expected:

```text
401
```

The request must not somehow become authenticated.

---

# 18. Test #10 — Expired JWT

Suppose a token was valid yesterday.

Today:

```text
exp < current time
```

The backend must reject it.

Expected:

```text
401 Unauthorized
```

A common mistake is:

```text
Decode JWT
    ↓
Read user ID
    ↓
Trust it
```

That's not enough.

The server must **verify** the token properly.

---

# 19. Decode vs Verify

This distinction is extremely important.

A JWT has three parts:

```text
header.payload.signature
```

The payload can be decoded.

But:

```text
decode ≠ trust
```

Someone can create a token payload containing:

```json
{
  "userId": "123",
  "role": "admin"
}
```

Decoding it doesn't prove it was created by your server.

The server needs to verify:

```text
Signature
Expiration
Expected claims
Algorithm/configuration
```

Conceptually:

```text
JWT
 ↓
Verify signature
 ↓
Verify expiration
 ↓
Verify required claims
 ↓
Authenticated
```

We'll go much deeper into JWT attacks in Lesson 22.10.

---

# 20. Test #11 — Modified JWT

Imagine the original payload:

```json
{
  "userId": "123",
  "role": "user"
}
```

An attacker tries to change:

```json
{
  "userId": "123",
  "role": "admin"
}
```

The signature should no longer match.

Expected:

```text
401 Unauthorized
```

This is a classic authentication security test.

---

# 21. Test #12 — Wrong Token Type

Suppose your application has:

```text
Access token
Refresh token
```

An attacker might send a refresh token to an access-token endpoint.

For example:

```http
GET /api/v1/users/me
Authorization: Bearer <refresh-token>
```

Your backend should distinguish between token purposes.

Conceptually:

```text
Access token
   ↓
API authorization

Refresh token
   ↓
Token renewal
```

One should not automatically substitute for the other.

---

# 22. Test #13 — Refresh Token Abuse

Suppose:

```text
POST /api/v1/auth/refresh
```

The attacker sends:

```text
invalid refresh token
```

Expected:

```text
401
```

Then test:

```text
expired refresh token
```

Expected:

```text
401
```

Then:

```text
revoked refresh token
```

Expected:

```text
401
```

Later we'll examine token rotation and reuse detection in detail.

---

# 23. Password Reset Is Also Authentication

Many developers secure login but forget:

```text
Forgot password
Reset password
Email verification
Change password
Account recovery
```

These are authentication-related flows too.

Imagine:

```text
POST /api/v1/auth/forgot-password
```

and:

```text
POST /api/v1/auth/reset-password
```

An attacker might try:

```text
Predictable reset token
Expired reset token
Reused reset token
Modified reset token
Another user's reset token
Unlimited reset requests
```

A weak password-reset flow can completely bypass a strong login system.

---

# 24. Authentication Is a Chain

Don't think:

```text
LOGIN = SECURITY
```

Think:

```text
              AUTHENTICATION
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
    Login        Tokens        Recovery
      │             │             │
      ▼             ▼             ▼
 Password       Access/        Reset
 validation     Refresh         password
      │             │             │
      └─────────────┼─────────────┘
                    ▼
              Session security
```

If **any important link** is weak, attackers may still gain access.

# 26. What Should a Secure Authentication System Do?

A good authentication architecture should roughly look like:

```text
                    LOGIN
                      │
                      ▼
                  Validate
                      │
                      ▼
               Find user safely
                      │
                      ▼
              Verify password
                      │
                      ▼
             Generate credentials
                      │
             ┌────────┴────────┐
             ▼                 ▼
        Access token       Refresh token
             │                 │
             ▼                 ▼
        Short lifetime     Secure handling
             │                 │
             └────────┬────────┘
                      ▼
                Protected API
                      │
                      ▼
                Verify token
                      │
                      ▼
                Authorize user
```

Every arrow represents something we'll eventually test.

# 27. Security Testing Example with Supertest

Since Phase 21 taught us API testing, we can now combine it with security testing.

For example:

```js
describe("GET /api/v1/users/me", () => {
    it("rejects requests without authentication", async () => {
        const response = await request(app)
            .get("/api/v1/users/me");

        expect(response.statusCode).toBe(401);
    });
});
```

This is a security test.

Another:

```js
it("rejects an invalid access token", async () => {
    const response = await request(app)
        .get("/api/v1/users/me")
        .set("Authorization", "Bearer invalid-token");

    expect(response.statusCode).toBe(401);
});
```

And:

```js
it("rejects an expired access token", async () => {
    // Create/use an expired token

    const response = await request(app)
        .get("/api/v1/users/me")
        .set("Authorization", `Bearer ${expiredToken}`);

    expect(response.statusCode).toBe(401);
});
```

Notice what we're doing:

```text
Attack
  ↓
Request
  ↓
Expected security behavior
  ↓
Assertion
```

---

# 28. A Very Important Rule

Never test only:

```text
"Login works."
```

Test both:

```text
Login succeeds when it should.
```

and:

```text
Login fails when it should.
```

This is:

```text
Positive security testing
        +
Negative security testing
```

For authentication, negative testing is especially important.

# 29. Common Developer Mistakes

### Mistake 1

```text
JWT exists
    ↓
Trust user
```

Wrong.

The JWT must be verified.

---

### Mistake 2

```text
Frontend protects /admin
```

Wrong.

An attacker can call the API directly.

Authorization belongs on the backend.

---

### Mistake 3

```text
Password reset is separate
```

Wrong.

Password recovery is part of the authentication attack surface.

---

### Mistake 4

```text
Login works
    ↓
Authentication is secure
```

Wrong.

You also need to test:

```text
Tokens
Sessions
Refresh
Reset
Rate limiting
Enumeration
```

