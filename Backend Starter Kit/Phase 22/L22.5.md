# Lesson 22.5 — Broken Authorization 🔐

In **Lesson 22.4**, we learned authentication:

> **“Who are you?”**

Now we move to authorization:

> **“What are you allowed to do?”**

This is one of the most important concepts in backend security.

A user can be **properly authenticated** and still be **completely unauthorized** to perform an action.

---

# 1. Authentication vs Authorization

Keep this distinction permanently in your mind:

```text
Authentication
      ↓
Who are you?
      ↓
Identity
```

```text
Authorization
      ↓
What can you do?
      ↓
Permissions
```

Example:

```text
User logs in
    ↓
JWT verified
    ↓
Authentication ✅
```

Now:

```text
User
 ↓
DELETE /api/v1/users/123
 ↓
Are they allowed?
 ↓
Authorization
```

They may be authenticated but still receive:

```text
403 Forbidden
```

---

# 2. What Is Broken Authorization?

Broken authorization happens when the backend doesn't correctly enforce **what an authenticated user is allowed to access or perform**.

For example:

```text
Normal User
    ↓
Authenticated ✅
    ↓
GET /api/v1/admin/users
    ↓
Server returns data ❌
```

The authentication worked.

The authorization failed.

That's the vulnerability.

---

# 3. The Most Important Rule

> **Never assume that authentication automatically gives permission.**

This is dangerous:

```js
authenticateUser();
next();
```

if the endpoint requires additional authorization.

Instead, think:

```text
Request
   ↓
Authentication
   ↓
Who is this?
   ↓
Authorization
   ↓
What can they do?
   ↓
Controller
```

---

# 4. A Simple Example

Imagine:

```text
Users
├── Rahul      role=user
├── Aman       role=user
└── Admin      role=admin
```

Endpoint:

```http
GET /api/v1/admin/users
```

Expected:

```text
Rahul  → 403
Aman   → 403
Admin  → 200
```

A broken backend might do:

```text
Rahul
 ↓
valid JWT
 ↓
200 OK
```

That's broken authorization.

---

# 5. Authentication Middleware Is Not Enough

You might have:

```js
router.get(
    "/admin/users",
    authenticate,
    getUsers
);
```

This means:

```text
authenticate
    ↓
"Is the user logged in?"
```

It does **not necessarily mean**:

```text
"Is this user an admin?"
```

You may need:

```js
router.get(
    "/admin/users",
    authenticate,
    authorize("admin"),
    getUsers
);
```

Conceptually:

```text
Request
   ↓
authenticate()
   ↓
authorize()
   ↓
controller()
```

This separation is extremely useful.

---

# 6. Authentication → Authorization

Think of the request pipeline like this:

```text
                 REQUEST
                    │
                    ▼
             Is user logged in?
                    │
              ┌─────┴─────┐
             NO           YES
             │             │
             ▼             ▼
            401       What permissions?
                            │
                      ┌─────┴─────┐
                   NOT ALLOWED   ALLOWED
                       │            │
                       ▼            ▼
                      403          NEXT
```

This gives us the basic distinction:

```text
401 → authentication failed
403 → authorization failed
```

---

# 7. Roles

One common authorization model is **RBAC**.

RBAC means:

> **Role-Based Access Control**

Example:

```text
user
admin
moderator
manager
```

Each role gets different permissions.

For example:

```text
user
 ├── read own profile
 ├── update own profile
 └── manage own todos

admin
 ├── manage users
 ├── manage all todos
 └── access admin dashboard
```

---

# 8. Role-Based Authorization

A simple middleware might conceptually look like:

```js
const authorize = (...allowedRoles) => {
    return (req, res, next) => {
        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Then:

```js
router.delete(
    "/users/:id",
    authenticate,
    authorize("admin"),
    deleteUser
);
```

Flow:

```text
Request
 ↓
JWT verification
 ↓
req.user
 ↓
role === "admin"?
 ↓
yes → controller
no  → 403
```

---

# 9. Don't Trust the Client's Role

Suppose React sends:

```json
{
  "role": "admin"
}
```

That doesn't make the user an admin.

The backend should determine the user's privileges from a trusted source.

Bad idea:

```text
Frontend
   ↓
role=admin
   ↓
Backend trusts it
```

Better:

```text
JWT/session
   ↓
Verified identity
   ↓
Trusted user data / authorization policy
   ↓
Permission decision
```

The client is controlled by the user.

---

# 10. Authorization Is More Than Roles

This is extremely important.

Don't think:

```text
Authorization = roles
```

Authorization can involve:

```text
Role
Ownership
Resource state
User relationship
Organization
Subscription
Permission
Business rules
```

For example:

```text
User
 ├── owns Todo
 ├── belongs to Organization A
 └── has role=editor
```

The authorization decision might depend on **all three**.

---

# 11. Ownership Authorization

Suppose:

```text
User A
  ↓
Todo 101

User B
  ↓
Todo 202
```

User A requests:

```http
PATCH /api/v1/todos/202
```

Even if User A is authenticated:

```text
Authentication ✅
Authorization ❌
```

The backend must check:

```text
Does Todo 202 belong to User A?
```

This leads directly into the next lesson about **IDOR/BOLA**.

---

# 12. Resource-Level Authorization

A common mistake is:

```js
const todo = await Todo.findById(todoId);

return todo;
```

The backend found the object.

But it didn't ask:

> **Does this user have permission to access this object?**

Better:

```js
const todo = await Todo.findOne({
    _id: todoId,
    userId: req.user.id
});
```

Now the lookup itself enforces ownership.

This is an important security design pattern.

---

# 13. Why Authorization Should Be Close to the Resource

Consider:

```text
Controller
   ↓
Service
   ↓
Repository
```

You don't want:

```js
Todo.findById(todoId);
```

to accidentally expose another user's data.

A secure architecture makes authorization part of the operation.

Conceptually:

```text
User
 ↓
Can access Todo?
 ↓
Repository query includes owner
 ↓
Result
```

This reduces the chance of forgetting the ownership condition.

---

# 14. Horizontal vs Vertical Authorization

Two useful concepts:

## Horizontal privilege escalation

One normal user accesses another normal user's resources.

```text
User A
   ↓
User B's Todo
```

This is closely related to:

```text
BOLA / IDOR
```

---

## Vertical privilege escalation

A lower-privileged user performs a higher-privileged action.

```text
Normal User
    ↓
Admin endpoint
```

Example:

```http
DELETE /api/v1/admin/users/123
```

This is a role/function authorization problem.

So:

```text
Horizontal
→ same level, wrong user's resource

Vertical
→ higher privilege than allowed
```

---

# 15. Example: Banking Application

Imagine:

```text
Account A → Rahul
Account B → Aman
```

Rahul logs in.

He requests:

```http
GET /api/v1/accounts/B
```

If the API returns Aman's account:

```text
🚨 Horizontal privilege escalation
🚨 BOLA
```

Now suppose Rahul tries:

```http
POST /api/v1/admin/refunds
```

and succeeds.

That's:

```text
🚨 Vertical privilege escalation
🚨 Broken function-level authorization
```

---

# 16. Authorization Must Be Tested Per Operation

Don't assume:

```text
GET protected
```

means:

```text
PATCH protected
DELETE protected
```

are also secure.

Consider:

```text
GET    /todos/:id
POST   /todos
PATCH  /todos/:id
DELETE /todos/:id
```

Test each separately.

Maybe:

```text
GET    → ownership enforced ✅
PATCH  → ownership enforced ✅
DELETE → ownership forgotten ❌
```

This is a very realistic security bug.

---

# 17. 401 vs 403 in Authorization Testing

This should now be clear.

### No authentication

```http
GET /api/v1/admin/users
```

No JWT:

```text
401 Unauthorized
```

### Valid authentication, insufficient permission

```text
Normal User
    ↓
valid JWT
    ↓
admin endpoint
```

Expected:

```text
403 Forbidden
```

Mental model:

```text
401
↓
"I don't know who you are."

403
↓
"I know who you are,
but you're not allowed."
```

---

# 18. Don't Leak Authorization Information

Suppose User A requests User B's resource.

You have two common choices:

```text
403 Forbidden
```

or:

```text
404 Not Found
```

Which one is appropriate depends on your API design and whether revealing the resource's existence is itself sensitive.

For some resources:

```text
404
```

can prevent leaking:

> "This resource exists, but you aren't allowed to see it."

The important lesson:

> **Security responses should not unnecessarily reveal sensitive information.**

We'll revisit this when we discuss BOLA.

---

# 19. Authorization Testing Matrix

Suppose:

```text
Roles:
user
admin
```

and endpoint:

```http
DELETE /api/v1/users/:id
```

Your tests might be:

|Actor|Target|Expected|
|---|---|---|
|Guest|Any user|401|
|User|Own account|Depends on policy|
|User|Another user|403/404|
|User|Admin account|403/404|
|Admin|User|200|
|Admin|Admin|Depends on policy|

Notice something important:

> **Authorization tests need multiple identities.**

This is why our test setup will eventually create:

```text
User A
User B
Admin
```

---

# 20. Authorization Test Setup

For security tests, we can create:

```js
const userA = await createUser({
    role: "user"
});

const userB = await createUser({
    role: "user"
});

const admin = await createUser({
    role: "admin"
});
```

Then generate tokens:

```js
const tokenA = createAccessToken(userA);
const tokenB = createAccessToken(userB);
const adminToken = createAccessToken(admin);
```

Now we can test:

```text
A → A resource
A → B resource
B → A resource
Admin → A resource
```

This creates realistic authorization tests.

---

# 21. The Permission Matrix

A professional way to think about authorization is a permission matrix.

For example:

|Action|Guest|User|Admin|
|---|--:|--:|--:|
|View public content|✅|✅|✅|
|Create Todo|❌|✅|✅|
|Read own Todo|❌|✅|✅|
|Read another user's Todo|❌|❌|Maybe|
|Delete own Todo|❌|✅|✅|
|Delete another user's Todo|❌|❌|Maybe|
|Manage users|❌|❌|✅|

This table gives us a direct source for our security tests.

---

# 22. Authorization as a Policy

Instead of scattering logic everywhere:

```js
if (user.role === "admin") ...
```

we can eventually build explicit policies.

For example:

```js
canUpdateTodo(user, todo)
```

Conceptually:

```text
canUpdateTodo(user, todo)
        │
        ├── Is authenticated?
        ├── Is owner?
        ├── Is admin?
        └── Is resource editable?
```

Then:

```js
if (!canUpdateTodo(req.user, todo)) {
    return res.status(403).json({
        message: "Forbidden"
    });
}
```

This makes authorization rules easier to understand and test.

---

# 23. Authorization Is a Business Rule

Consider:

```text
Only the owner can edit a Todo.
```

That's not just middleware.

It's a **business rule**.

Another:

```text
Only admins can delete users.
```

Another:

```text
Only organization members can view organization resources.
```

Another:

```text
Editors can update posts but cannot publish them.
```

These are authorization policies.

So authorization belongs close to your application's business logic.

---

# 24. Common Authorization Mistakes

### Mistake 1 — Checking only authentication

```js
authenticate();
next();
```

but never checking permissions.

---

### Mistake 2 — Trusting client role

```json
{
  "role": "admin"
}
```

Never trust that just because the browser sent it.

---

### Mistake 3 — Checking only the UI

```text
Admin button visible only to admins
```

That's not security.

An attacker can call:

```http
POST /api/v1/admin/action
```

directly.

---

### Mistake 4 — Protecting GET but forgetting DELETE

Every operation needs its own authorization check.

---

### Mistake 5 — Finding a resource without checking ownership

```js
findById(id)
```

can be dangerous when `id` comes from the client.

---

### Mistake 6 — Checking authorization after performing the action

Never:

```text
perform action
   ↓
check permission
```

It must be:

```text
check permission
   ↓
perform action
```

---

# 25. A Secure Request Pipeline

Our ideal mental model:

```text
                  REQUEST
                     │
                     ▼
                Validate input
                     │
                     ▼
               Authenticate
                     │
                     ▼
            Identify the user
                     │
                     ▼
             Authorize action
                     │
             ┌───────┴───────┐
             ▼               ▼
          Denied           Allowed
             │               │
             ▼               ▼
            403          Business logic
                             │
                             ▼
                          Database
```

For ownership-sensitive resources:

```text
Authenticate
     ↓
Load/check resource
     ↓
Verify ownership/permission
     ↓
Perform operation
```

# 26. Security Test Example

Suppose:

```http
DELETE /api/v1/todos/500
```

Todo 500 belongs to User B.

User A sends:

```js
const response = await request(app)
    .delete("/api/v1/todos/500")
    .set("Authorization", `Bearer ${tokenA}`);
```

Expected:

```js
expect(response.statusCode).toBe(403);
```

or your API's chosen equivalent.

Then verify:

```text
Todo 500 still exists.
```

This second assertion is important.

A security test should not only check:

```text
"Did I get 403?"
```

It should also check:

```text
"Did the protected resource remain unchanged?"
```

---

# 27. Authorization Tests Should Check Side Effects

Imagine:

```text
User A
 ↓
PATCH User B's Todo
 ↓
403
```

Good.

But suppose the backend:

```text
updates the Todo
then
returns 403
```

That's still a vulnerability.

Therefore:

```text
Security assertion
+
State assertion
```

For example:

```js
expect(response.statusCode).toBe(403);

const todoAfter = await Todo.findById(todoId);

expect(todoAfter.title).toBe(originalTitle);
```

This is a powerful testing technique.

---

# 28. Authorization and Transactions

Later, when we discuss advanced database architecture, you'll see why authorization must happen before sensitive mutations.

For example:

```text
Request
 ↓
Authorize
 ↓
Start mutation
 ↓
Database change
```

not:

```text
Request
 ↓
Database change
 ↓
Authorization
```

The second pattern can produce serious security problems.

---

# 29. Build Authorization Tests Before You Build More Features

A great habit for your future projects:

Whenever you create an endpoint, write down:

```text
Who can call this?
Who cannot?
Whose resources can they access?
What fields can they modify?
What actions can they perform?
```

Example:

```text
PATCH /todos/:id

Guest:
❌

Authenticated user:
✅ own Todo

Authenticated user:
❌ another user's Todo

Admin:
depends on policy

Fields:
title ✅
completed ✅
userId ❌
ownerId ❌
```

Now the implementation becomes much clearer.

# 30. Authorization → BOLA

We're now ready for the next lesson.

The most common dangerous mistake is:

```text
User is authenticated
      ↓
User provides resource ID
      ↓
Backend trusts the ID
      ↓
Backend returns/updates resource
```

For example:

```http
GET /api/v1/todos/123
```

The backend must ask:

```text
Does Todo 123 belong to this user?
```

That problem is called:

> **Broken Object Level Authorization (BOLA)**

and is closely associated with the term:

> **IDOR — Insecure Direct Object Reference**

That's our next lesson.

