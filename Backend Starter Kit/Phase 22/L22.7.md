# Lesson 22.7 — Mass Assignment & Broken Object Property Level Authorization

> **Source note:** Your uploaded roadmap names **22.6 as Mass Assignment**, followed by **22.7 Injection**. Since we've been following a shifted numbering in our lessons, the topic you asked for here is **Mass Assignment / property-level authorization**, and that is the topic covered below.

In **22.6**, we learned:

> **BOLA:** “Can this user access this object?”

Now we go one level deeper:

> **“Even if the user can access this object, which fields are they allowed to change?”**

This distinction is extremely important.

---

# 1. Object Authorization vs Property Authorization

Imagine:

```json
{
  "title": "Learn Node",
  "completed": false,
  "userId": "123",
  "role": "user"
}
```

Suppose the authenticated user owns this object.

So:

```text
Object authorization
        ↓
✅ User can access Todo
```

But that doesn't mean they should be able to modify every property.

For example:

```text
title       → user can change ✅
completed   → user can change ✅
userId      → user should NOT change ❌
role        → user should NOT change ❌
```

So:

```text
BOLA
↓
Can I access this object?

Property authorization
↓
Which properties can I access/change?
```

---

# 2. What Is Mass Assignment?

Mass assignment happens when the backend blindly takes user-controlled input and applies it to a database object.

Dangerous example:

```js
await User.findByIdAndUpdate(
    userId,
    req.body
);
```

Looks convenient.

But imagine the request:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

If `role` is supposed to be controlled only by administrators, you've just created a serious vulnerability.

The attacker supplied:

```text
role = admin
```

and the backend accepted it.

---

# 3. The Dangerous Pattern

Watch for code like:

```js
Model.findByIdAndUpdate(
    id,
    req.body
);
```

or:

```js
Object.assign(user, req.body);
```

or:

```js
user.set(req.body);
```

These aren't automatically vulnerable.

The problem occurs when:

> **Untrusted client fields are allowed to modify properties without an explicit authorization decision.**

---

# 4. Realistic Attack

Suppose your user profile normally accepts:

```json
{
  "firstName": "Rahul",
  "lastName": "Kumar"
}
```

Your backend does:

```js
await User.findByIdAndUpdate(
    req.user.id,
    req.body
);
```

An attacker sends:

```json
{
  "firstName": "Rahul",
  "role": "admin"
}
```

If the backend accepts it:

```text
Attacker
   ↓
role=admin
   ↓
MongoDB
   ↓
User.role = admin
   ↓
🚨 Privilege escalation
```

This is why mass assignment can become extremely dangerous.

---

# 5. Another Example — `isAdmin`

Imagine your User model:

```js
{
    name: String,
    email: String,
    password: String,
    isAdmin: Boolean
}
```

The frontend normally sends:

```json
{
  "name": "Rahul"
}
```

But the attacker sends:

```json
{
  "name": "Rahul",
  "isAdmin": true
}
```

If your update code accepts everything:

```text
isAdmin
   ↓
true
   ↓
MongoDB
   ↓
🚨 Admin account
```

This is a classic mass-assignment scenario.

---

# 6. The Secure Pattern — Explicit Fields

Instead of:

```js
await User.findByIdAndUpdate(
    userId,
    req.body
);
```

explicitly choose what can be updated:

```js
const { firstName, lastName } = req.body;

await User.findByIdAndUpdate(
    userId,
    {
        firstName,
        lastName
    }
);
```

Now:

```text
Client sends:
firstName      → accepted
lastName       → accepted
role           → ignored
isAdmin        → ignored
passwordHash   → ignored
```

This is called **allowlisting**.

---

# 7. Allowlist vs Blocklist

Two possible approaches exist.

### Blocklist

```text
Allow everything
except:
- role
- isAdmin
- passwordHash
```

Problem:

Tomorrow you add:

```text
accountStatus
```

and forget to add it to the blocklist.

Now:

```text
accountStatus
       ↓
Client may modify it
```

---

### Allowlist

```text
Only allow:
- firstName
- lastName
- avatar
```

Everything else is rejected or ignored.

This is generally safer.

Think:

```text
❌ "What should I block?"

✅ "What should I allow?"
```

---

# 8. Property-Level Authorization

This is the deeper concept.

Suppose:

```text
User
├── firstName
├── lastName
├── email
├── role
├── isVerified
├── accountStatus
└── passwordHash
```

Different actors may have different permissions.

### Normal user

```text
firstName       ✅
lastName        ✅
avatar          ✅

role            ❌
isVerified      ❌
accountStatus   ❌
passwordHash    ❌
```

### Admin

```text
role            ✅
accountStatus   ✅
```

So authorization isn't always:

```text
"Can this user access the object?"
```

It can also be:

```text
"Can this user modify this particular property?"
```

---

# 9. BOLA + Property Authorization

Now combine Lesson 22.6 and 22.7.

Suppose User A owns:

```text
Todo 123
```

User A sends:

```json
{
  "title": "New title",
  "userId": "User B"
}
```

There are two security decisions:

```text
1. Can User A access Todo 123?
        ↓
       YES

2. Can User A modify userId?
        ↓
       NO
```

So:

```text
Object authorization
+
Property authorization
```

Both are required.

# 10. Why `req.body` Is Dangerous

Think about:

```js
const update = req.body;
```

You don't know what the client has put inside it.

Maybe:

```json
{
  "title": "Hello"
}
```

Maybe:

```json
{
  "title": "Hello",
  "role": "admin"
}
```

Maybe:

```json
{
  "title": "Hello",
  "userId": "someone-else"
}
```

Maybe:

```json
{
  "title": "Hello",
  "createdAt": "2000-01-01"
}
```

Maybe:

```json
{
  "title": "Hello",
  "internalStatus": "approved"
}
```

Therefore:

> **Never treat `req.body` as a trusted representation of your database object.**

It is merely:

```text
untrusted client input
```

---

# 11. DTO Thinking

A useful professional concept here is the **DTO**:

> Data Transfer Object

Instead of passing the entire request body into your model, construct the exact data your operation accepts.

For example:

```js
const updateUserData = {
    firstName: req.body.firstName,
    lastName: req.body.lastName
};
```

Then:

```text
HTTP request
    ↓
Validation
    ↓
Allowed fields
    ↓
DTO
    ↓
Service
    ↓
Repository
```

This creates a clear boundary.

---

# 12. Validation Isn't Enough

This is a very important distinction.

Suppose your validation schema says:

```js
const schema = Joi.object({
    firstName: Joi.string(),
    lastName: Joi.string(),
    role: Joi.string()
});
```

You may have validated that `role` is a valid string.

But that doesn't answer:

> **Should this user be allowed to modify `role`?**

Validation asks:

```text
Is this input valid?
```

Authorization asks:

```text
Is this user allowed to perform this change?
```

So:

```text
Validation
    +
Authorization
```

are different security controls.

Your uploaded roadmap also separates validation from authorization, reinforcing this layered approach.

---

# 13. Validation vs Sanitization vs Authorization

Keep these three separate.

### Validation

```text
Is the value acceptable?
```

Example:

```text
email must be valid
age must be a number
title cannot be empty
```

### Sanitization

```text
Can we safely normalize/clean the value?
```

Example:

```text
trim whitespace
normalize input
remove unwanted structures
```

### Authorization

```text
Is this user allowed to modify this field?
```

Example:

```text
role → only admin
```

So:

```text
Input
 ↓
Validation
 ↓
Sanitization
 ↓
Authorization
 ↓
Business logic
```

Not every application needs exactly this ordering for every field, but the concepts should remain distinct.

Let's create a security test.

Normal user:

```text
role = user
```

Request:


Body:

```json
{
  "firstName": "Rahul",
```

Expected:

```text
firstName → updated
```

```js
expect(updatedUser.role).toBe("user");
```

```text
HTTP 200
```

Check the database state.

# 15. Attack: Change `userId`

Suppose User A owns:

```text
Todo 123
```

User A sends:

```json
{
  "title": "My todo",
  "userId": "USER_B"
}
```

If accepted:

```text
Todo 123
    ↓
owner changes
    ↓
User B
```

Now you've potentially created:

```text
ownership manipulation
```

and possibly a future BOLA problem.

Therefore fields such as:

```text
userId
ownerId
organizationId
```

usually require special protection.

# 22. Secure Create Operations

Instead of:

```js
User.create(req.body);
```

build the object explicitly:

```js
const userData = {
    firstName: req.body.firstName,
    lastName: req.body.lastName,
    email: req.body.email,
    password: req.body.password
};

await User.create(userData);
```

Notice:

```text
role
isAdmin
isVerified
permissions
refreshTokenHash
```

aren't coming from the client.

The server controls them.

# 23. Server-Controlled Fields

A useful classification is:

### Client-controlled

```text
firstName
lastName
title
description
avatar
```

### Server-controlled

```text
userId
role
permissions
isAdmin
isVerified
createdAt
updatedAt
refreshTokenHash
internalStatus
```

This isn't universal; your business rules determine the exact list.

But the distinction is extremely useful.

Ask for every field:

> **“Who should be allowed to control this value?”**

---

# 24. Security Through Data Ownership

Your repository layer can help enforce this.

For example:

```js
async updateUserProfile(userId, data) {
    return User.findOneAndUpdate(
        {
            _id: userId
        },
        {
            $set: {
                firstName: data.firstName,
                lastName: data.lastName
            }
        },
        {
            new: true
        }
    );
}
```

The repository doesn't blindly receive arbitrary fields.

Instead:

```text
Service
 ↓
approved fields
 ↓
Repository
 ↓
database
```

This matches the layered architecture you're building throughout the roadmap.

---

# 25. Don't Rely Only on Mongoose `select: false`

You might have:

```js
password: {
    type: String,
    select: false
}
```

That's useful for preventing accidental reads.

But it doesn't mean the client cannot modify other sensitive fields.

These are different problems:

```text
Reading sensitive fields
        vs
Writing sensitive fields
```

You need separate controls.

---

# 26. Don't Assume Mongoose Schema Protects You

Suppose your schema defines:

```js
role: {
    type: String,
    enum: ["user", "admin"]
}
```

An attacker sends:

```json
{
  "role": "admin"
}
```

`admin` might be a perfectly valid enum value.

Mongoose may happily accept it.

The problem isn't:

```text
Is "admin" valid?
```

The problem is:

```text
Is THIS USER allowed to set "admin"?
```

Again:

```text
Schema validation
        ≠
Authorization
```

# 28. Field-Level Authorization

Sometimes the user can update an object but only some fields.

Example:

```text
PATCH /users/me
```

User can modify:

```text
firstName
lastName
avatar
```

but not:

```text
role
permissions
organizationId
```

This is:

> **Field-level authorization**

And it's extremely useful to think about it explicitly.

---

# 29. Different Endpoints Can Have Different Fields

You don't necessarily need one huge update endpoint.

For example:

```text
PATCH /users/me
```

allows:

```text
firstName
lastName
avatar
```

While:

```text
PATCH /admin/users/:id/role
```

allows:

```text
role
```

This is often cleaner than:

```text
PATCH /users/:id
```

accepting 30 different fields.

Specific endpoints make authorization easier to reason about.

---

# 30. Don't Put Authorization in the Frontend

Your React application might do:

```js
if (user.role === "admin") {
    showRoleEditor();
}
```

That's good for UX.

But it is **not security**.

An attacker can still manually send:

```http
PATCH /api/v1/users/123
```

with:

```json
{
  "role": "admin"
}
```

Therefore:

```text
Frontend
 → UX restriction

Backend
 → Security enforcement
```

# 31. Test Unknown Fields

Your security tests should try:

```json
{
  "firstName": "Rahul",
  "role": "admin",
  "isAdmin": true,
  "userId": "other-user",
  "permissions": ["admin"]
}
```

Then verify:

```text
firstName → changed if allowed
role → unchanged
isAdmin → unchanged
userId → unchanged
permissions → unchanged
```

This is an excellent security test.

---

# 32. Test Every Sensitive Field

Don't make one test:

```text
"rejects malicious update"
```

Make explicit tests where practical:

```text
cannot modify role
cannot modify userId
cannot modify permissions
cannot modify isVerified
cannot modify accountStatus
```

This tells future developers exactly what your security policy is.

# 33. Mass Assignment Security Test

Example:

```js
it("does not allow users to assign themselves admin role", async () => {
    const response = await request(app)
        .patch("/api/v1/users/me")
        .set("Authorization", `Bearer ${userToken}`)
        .send({
            firstName: "Rahul",
            role: "admin"
        });

    expect(response.statusCode).toBe(200);

    const user = await User.findById(userId);

    expect(user.role).toBe("user");
});
```

Notice something interesting:

The endpoint can still return:

```text
200
```

because the allowed field was updated.

The security assertion is:

```text
role remains user
```

That's a much stronger test than simply checking HTTP status.

# 34. A Better Service Design

Instead of:

```js
async updateUser(userId, data) {
    return repository.update(userId, data);
}
```

consider:

```js
async updateUserProfile(userId, data) {
    const allowedData = {
        firstName: data.firstName,
        lastName: data.lastName,
        avatar: data.avatar
    };

    return repository.update(userId, allowedData);
}
```

Now the service defines the business boundary.

---

# 35. Admin Updates

An admin may legitimately need:

```text
role
accountStatus
```

So create a separate operation:

```js
async updateUserRole(admin, userId, role) {
    // authorization
    // validation
    // business rules
    // repository update
}
```

Now:

```text
Normal user
    ↓
updateUserProfile()
    ↓
No role modification

Admin
    ↓
updateUserRole()
    ↓
Role modification allowed
```

This is much safer than allowing everyone to send:

```json
{
  "role": "..."
}
```

to one generic update endpoint.

# 38. BOLA vs Mass Assignment

Let's compare them.

### BOLA

```text

```

Attacker asks:

> Can I access another user's object?

---

### Mass Assignment

```json
{
  "title": "hello",
  "userId": "another-user"
}
```

Attacker asks:

> Can I modify a property I shouldn't control?

---

### Combined attack

An attacker might:

```text

```

That's why these vulnerabilities need to be tested together.

# 41. The Golden Rule

Never do this casually:

```js
Model.create(req.body);
```

or:

```js
Model.findByIdAndUpdate(id, req.body);
```

Instead, ask:

```text
What does the client actually need to control?
```

Then explicitly construct the data.

```js
const safeData = {
    title: req.body.title,
    description: req.body.description
};
```

Then:

```js
await repository.update(id, safeData);
```

The biggest lesson is:

```text
BOLA
↓

```

```text
Property Authorization
↓
Can I access/change this field?
```
