# Lesson 22.8 — Injection 💉

According to your uploaded roadmap, **22.7 is Injection**, and **22.8 is Rate-limit testing**. Since we've already covered the earlier lessons using a shifted numbering, I'll keep the sequence consistent with our current conversation and teach **Injection now**, while preserving the roadmap's actual topic order.

Injection is one of the most important backend security topics because it happens when:

> **Untrusted input changes the meaning of a command, query, or operation.**

For a MERN backend, MongoDB/NoSQL injection is especially relevant.

---

# 1. What Is Injection?

Imagine your backend expects:

```text
username = Rahul
```

but the attacker sends specially crafted input that changes what the backend actually does.

The basic pattern is:

```text
Attacker input
      ↓
Backend
      ↓
Input becomes part of a command/query
      ↓
Meaning changes
      ↓
🚨 Injection
```

The key problem is:

```text
Data
 ↓
mistakenly treated as
 ↓
instructions
```

---

# 2. The General Injection Family

Injection isn't one single vulnerability.

It includes things like:

```text
SQL Injection
NoSQL Injection
Command Injection
LDAP Injection
Template Injection
OS Command Injection
```

The common idea is:

```text
Untrusted input
      ↓
Interpreter
      ↓
Input changes interpreter behavior
```

In our MERN backend, we'll focus heavily on:

```text
MongoDB
Express
Node.js
```

---

# 3. Why MERN Applications Can Have NoSQL Injection

Your backend might receive:

```json
{
  "email": "user@example.com",
  "password": "secret"
}
```

Then perform:

```js
User.findOne({
    email: req.body.email
});
```

Normally:

```text
email
 ↓
string
 ↓
MongoDB query
```

But what if the backend accepts an **object** where it expected a string?

For example, conceptually:

```json
{
  "email": {
    "$ne": null
  }
}
```

Now the input isn't simply:

```text
"email"
```

It contains a MongoDB operator:

```text
$ne
```

That's where the security problem can begin.

---

# 4. MongoDB Operators

MongoDB has operators such as:

```text
$eq
$ne
$gt
$gte
$lt
$lte
$in
$nin
$exists
$regex
```

These are legitimate database features.

For example:

```js
{
    age: {
        $gte: 18
    }
}
```

means:

```text
age >= 18
```

The problem occurs when:

> **The attacker gets to inject operators into a query that was supposed to contain ordinary user data.**

---

# 5. A Vulnerable Login Example

Imagine:

```js
const user = await User.findOne({
    email: req.body.email,
    password: req.body.password
});
```

This is already a questionable authentication design because passwords should be securely hashed and compared rather than queried this way.

But from an injection perspective, imagine the attacker controls the shape of:

```text
req.body.email
req.body.password
```

If the backend expects strings but accepts arbitrary objects, MongoDB operators may enter the query.

Conceptually:

```text
Expected:

email → string

Received:

email → object containing MongoDB operator
```

That's the dangerous boundary.

---

# 6. The Important Boundary

This is the rule to remember:

```text
Expected:
string

Received:
object
```

That should immediately make you suspicious.

For example:

```json
{
  "email": {
    "$ne": null
  }
}
```

is fundamentally different from:

```json
{
  "email": "user@example.com"
}
```

Your validation layer should establish:

```text
email
 ↓
must be a string
```

not:

```text
email
 ↓
anything MongoDB accepts
```

---

# 7. Why Validation Helps

Suppose your validation schema says:

```js
email: Joi.string().email().required()
```

Then:

```json
{
  "email": {
    "$ne": null
  }
}
```

should fail validation because:

```text
object ≠ string
```

So:

```text
Attacker input
      ↓
Validation
      ↓
Reject unexpected type
      ↓
MongoDB never sees malicious structure
```

This is one reason your earlier Phase 9 validation lessons are so important.

Your uploaded roadmap specifically places validation before the security-testing phase, which gives us this defense layer.

---

# 8. Type Validation Is Security

Don't think validation is only for user experience.

This:

```js
Joi.string()
```

can be a security boundary.

Because you're saying:

```text
This field is DATA of type string.
```

rather than:

```text
This field can contain arbitrary JSON.
```

That difference can prevent injection.

---

# 9. Dangerous Query Construction

Watch for code where user input directly controls query structure.

For example:

```js
const filter = req.body;

const users = await User.find(filter);
```

This is risky.

Why?

Because the client now effectively controls:

```text
MongoDB filter
```

instead of simply providing:

```text
search criteria
```

The difference is huge.

---

# 10. Better Approach

Instead of:

```js
const users = await User.find(req.body);
```

define what the API actually accepts:

```js
const filter = {
    name: req.body.name
};
```

Or:

```js
const { name, status } = req.query;

const filter = {};

if (name) {
    filter.name = name;
}

if (status) {
    filter.status = status;
}
```

Now the backend controls the query structure.

---

# 11. Never Let the Client Build Your Mongo Query

Dangerous:

```js
Model.find(req.query);
```

Imagine:

```text
GET /users?...
```

and the entire query object becomes the MongoDB filter.

That's essentially:

```text
HTTP query
     ↓
MongoDB query
```

You want:

```text
HTTP query
     ↓
Validation
     ↓
Allowed parameters
     ↓
Application-controlled query
     ↓
MongoDB
```

This is much safer.

---

# 12. Search Endpoints

Search functionality deserves special attention.

Suppose:

```http
GET /api/v1/users?name=Rahul
```

Your backend might construct:

```js
{
    name: "Rahul"
}
```

That's fine.

But if you allow the client to provide arbitrary MongoDB operators:

```text
query
 ↓
MongoDB operator
```

you've expanded the attack surface unnecessarily.

Instead, explicitly define:

```text
Allowed filters:
name
status
createdAfter
createdBefore
```

Then validate each one.

---

# 13. `$regex` and Search

MongoDB supports:

```js
{
    name: {
        $regex: search
    }
}
```

This can be useful.

But now `search` is influencing a regular expression.

That creates another concern:

> **Regular expression denial of service / ReDoS-like resource abuse.**

So even when an operator is intentionally used, you must consider:

```text
Input validation
+
Input length
+
Regex complexity
+
Query performance
```

Security isn't simply:

```text
"Block all operators."
```

It's:

> **Only allow the operations your application actually needs, under controlled conditions.**

---

# 14. `$where`

MongoDB historically has powerful query features such as `$where`.

You generally don't want arbitrary client input controlling such functionality.

The security principle is:

```text
Never let the client decide
which database operators or
query mechanisms your backend uses.
```

Your backend should choose them.

For example:

```text
Client:
search = "Rahul"

Backend:
{
    name: {
        $regex: escapedSearch
    }
}
```

The client controls the **data**.

The backend controls the **query structure**.

---

# 15. Command Injection

Injection isn't limited to MongoDB.

Imagine Node.js code that runs an operating-system command:

```js
exec(`some-command ${userInput}`);
```

This is dangerous because:

```text
userInput
   ↓
OS command
```

The user may potentially influence the command itself.

The secure principle is:

```text
Never concatenate untrusted input
into shell commands.
```

If you genuinely need to execute a process, prefer APIs that pass arguments separately rather than constructing shell command strings.

---

# 16. Example: Image Processing

Suppose your backend receives:

```text
filename
```

and runs:

```text
image-tool filename
```

Bad architecture:

```text
filename
 ↓
string concatenation
 ↓
shell
```

Better architecture:

```text
filename
 ↓
validate
 ↓
allowlist expected format
 ↓
safe process API
 ↓
image tool
```

Again:

```text
Data
 ↓
validation
 ↓
controlled operation
```

# 17. SQL Injection vs NoSQL Injection

The concepts are similar.

### SQL

```text
User input
 ↓
SQL query
 ↓
Query structure changes
```

### NoSQL

```text
User input
 ↓
MongoDB query/object
 ↓
Query behavior changes
```

The underlying databases differ, but the security principle is the same:

> **Never allow untrusted input to control the structure of an interpreter's instructions.**

---

# 18. Injection Defense #1 — Validate Types

For example:

```js
const schema = Joi.object({
    email: Joi.string().email().required(),
    password: Joi.string().required()
});
```

This ensures:

```text
email → string
password → string
```

not:

```text
email → arbitrary object
password → arbitrary object
```

---

# 19. Injection Defense #2 — Allowlist Fields

Don't accept:

```js
req.query
```

as your complete MongoDB filter.

Instead:

```js
const filter = {};

if (req.query.status) {
    filter.status = req.query.status;
}

if (req.query.category) {
    filter.category = req.query.category;
}
```

Now you control:

```text
field names
query structure
allowed operations
```

---

# 20. Injection Defense #3 — Sanitize Mongo Operators

MongoDB sanitization middleware can help protect against keys beginning with:

```text
$
```

and potentially dangerous dotted paths.

For example, your earlier security middleware architecture may include Mongo sanitization.

Your uploaded roadmap explicitly lists MongoDB sanitization under the security middleware phase.

The important point:

> **Sanitization is an additional defense, not a replacement for validation and safe query construction.**

---

# 21. Defense in Depth

Don't rely on one magic package.

A stronger design is:

```text
             Request
                │
                ▼
            Validation
                │
                ▼
         Type enforcement
                │
                ▼
       Allowed fields only
                │
                ▼
      Safe query construction
                │
                ▼
       Mongo sanitization
                │
                ▼
             MongoDB
```

If one layer fails, another may still stop the attack.

# 22. Injection Testing

Security testing should deliberately send unexpected structures.

For a field expected to be a string:

### Normal

```json
{
  "email": "user@example.com"
}
```

### Security test

```json
{
  "email": {
    "$ne": null
  }
}
```

The important expected result is:

```text
400
```

or another safe rejection.

It should **not** cause:

```text
200 authenticated
```

---

# 23. Test Object Instead of String

For:

```text
email
```

test:

```json
{
  "email": []
}
```

Then:

```json
{
  "email": {}
}
```

Then:

```json
{
  "email": null
}
```

Then:

```json
{
  "email": {
    "$gt": ""
  }
}
```

The purpose isn't simply to try random payloads.

You're checking:

> **Does the backend enforce the expected data type and query boundary?**

---

# 24. Test Nested Operators

If an endpoint accepts something like:

```json
{
  "filter": {
    "status": "active"
  }
}
```

test whether the client can change:

```json
{
  "filter": {
    "$or": [...]
  }
}
```

or:

```json
{
  "filter": {
    "status": {
      "$ne": "disabled"
    }
  }
}
```

If the API doesn't intentionally support those operators, they should be rejected or stripped.

---

# 25. Test Query Parameters

Don't test only JSON bodies.

Also test:

```text
req.query
```

For example:

```http
GET /api/v1/users?status=active
```

Then try malformed structures where your framework/parser permits them.

The question is:

```text
Can query parameters become
arbitrary MongoDB operators?
```

---

# 26. Test URL Parameters

Suppose:

Expected:

```text
id → MongoDB ObjectId/string
```

Test:

```text

unexpected characters
```

The exact tests depend on your API contract.

Again:

```text
URL parameter
 ↓
Validate
 ↓
Use safely
```

# 27. Injection Doesn't Always Mean Authentication Bypass

This is important.

Injection can cause:

```text
Authentication bypass
Data leakage
Unauthorized modification
Unauthorized deletion
Database abuse
Resource exhaustion
Command execution
```

So don't define injection as:

> "A way to bypass login."

That's only one possible impact.

# 28. Injection and Data Leakage

Imagine:

```text
GET /users?email=...
```

A poorly designed filter could potentially allow an attacker to request much broader data than intended.

Then:

```text
Attacker
 ↓
crafted filter
 ↓
MongoDB
 ↓
many records
 ↓
🚨 data exposure
```

Therefore security testing should examine:

```text
Authorization
+
Query construction
+
Returned fields
```

---

# 29. Injection and Projection

Suppose your API allows:

```text
fields=name,email
```

A poorly designed implementation may let clients request fields that should never be exposed.

So don't simply do:

```js
User.find(filter).select(req.query.fields);
```

without controlling the fields.

Instead:

```text
Requested fields
      ↓
Allowlist
      ↓
Safe projection
```

For example:

```text
Allowed:
name
email

Forbidden:
passwordHash
refreshTokenHash
internalNotes
```

This connects injection thinking with sensitive-data exposure.

---

# 30. Injection and Sorting

Suppose:

```http
GET /users?sort=name
```

You can safely allow:

```text
name
createdAt
email
```

But don't blindly trust:

```text
sort = arbitrary database expression
```

Use:

```js
const allowedSortFields = [
    "name",
    "createdAt",
    "email"
];

if (!allowedSortFields.includes(sort)) {
    return res.status(400).json({
        message: "Invalid sort field"
    });
}
```

Now:

```text
Client
 ↓
"sort=name"
 ↓
allowlist
 ↓
Mongo query
```

This is a recurring security pattern.

---

# 31. Injection and Pagination

Even pagination can be abused.

Suppose:

```http
GET /users?limit=20
```

An attacker sends:

```text
limit=100000000
```

That's not necessarily injection, but it can become:

```text
Resource exhaustion
```

So:

```text
limit
 ↓
parse
 ↓
validate
 ↓
maximum allowed
```

For example:

```text
minimum = 1
maximum = 100
```

This leads directly into our upcoming **rate-limit/resource-abuse testing**.

# 32. Injection Test Example

Suppose:

```http
POST /api/v1/auth/login
```

Security test:

```js
it("rejects MongoDB operator injection in email", async () => {
    const response = await request(app)
        .post("/api/v1/auth/login")
        .send({
            email: {
                $ne: null
            },
            password: "anything"
        });

    expect(response.statusCode).toBe(400);
});
```

The exact expected status depends on your validation architecture.

The important security property:

```text
Operator object
      ↓
Rejected
```

# 34. A Reusable Injection Test Matrix


|---|---|
|Valid string|Accepted|
|Empty string|Validation failure|
|Number|Rejected|
|Array|Rejected|
|Object|Rejected|

### ❌ Mistake 1

```js

```

You're giving the client too much control over query structure.

### ❌ Mistake 2

```js

```

Same problem.

---

### ❌ Mistake 3

```js

```

Potential command injection.

---

### ❌ Mistake 4

Only using sanitization.

```text
sanitize()
 ↓
Everything is secure
```

No.

You still need:

```text
Validation
```


# 36. A Secure Query Architecture

A good pattern:

```text
                 REQUEST
                    │
                    ▼
              Parse input
                    │
                    ▼
                Validate
                    │
                    ▼
            Allowlist fields
                    │
                    ▼
        Construct query yourself
                    │
                    ▼
           Apply authorization
                    │
                    ▼
          Apply safe projection
                    │
                    ▼
               MongoDB
```

The key is:

> **The backend constructs the query. The client provides data used by the query.**

# 37. The Most Important Mental Model

When you see:

```js
req.body
req.query
req.params
```

ask:

> **“Can this input change the structure of an operation?”**

If yes:

```text
🚨 Injection risk
```

Then ask:

```text
Can I constrain the type?
Can I allowlist the field?
Can I construct the query myself?
Can I sanitize dangerous operators?
Can I limit input size?
Can I test malicious structures?
```

```text

        ↓
   Validate it
        ↓
   Allowlist it
        ↓
 Backend constructs query
        ↓
```

