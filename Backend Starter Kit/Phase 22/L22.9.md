# Lesson 22.9 — JWT Attacks 🔐

Your roadmap defines **22.9 as JWT attacks**, after rate-limit testing and before refresh-token attacks.

JWT is already part of your authentication architecture, so now the goal is not to learn JWT from scratch. The goal is to **attack the JWT system you've built and understand where it can fail**.

---

## 1. First: What Are We Protecting?

A typical access-token flow looks like:

```text
Login
  ↓
Validate credentials
  ↓
Create access JWT
  ↓
Client receives JWT
  ↓
Client sends:
Authorization: Bearer <token>
  ↓
Auth middleware
  ↓
Verify JWT
  ↓
req.user
  ↓
Controller
```

The security boundary is:

```text
        UNTRUSTED CLIENT
               ↓
         JWT TOKEN
               ↓
        VERIFY CORRECTLY
               ↓
        TRUST req.user
```

The dangerous part is:

> **Once your middleware accepts a JWT, the rest of your application may trust the identity and claims inside it.**

So JWT verification must be extremely strict.

---

# 2. What Can Attackers Try?

During security testing, think about:

```text
JWT
├── Modify payload
├── Change algorithm
├── Remove signature
├── Forge signature
├── Use wrong secret
├── Use expired token
├── Use malformed token
├── Use token from another environment
├── Manipulate claims
├── Replay a stolen token
└── Abuse weak secrets
```

Not every attack works against every JWT library/configuration.

Your job is to verify that your implementation **rejects them safely**.

---

# 3. JWT Has Three Parts

A JWT normally looks like:

```text
xxxxx.yyyyy.zzzzz
```

These represent:

```text
HEADER.PAYLOAD.SIGNATURE
```

For example:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

Payload:

```json
{
  "sub": "user123",
  "role": "user",
  "iat": 1750000000,
  "exp": 1750000900
}
```

Then:

```text
signature
```

protects the token's integrity.

---

# 4. Important: JWT Is Not Encryption

This is one of the most important things to remember.

A normal signed JWT does **not** hide its payload.

Someone who possesses the token can generally decode the header and payload.

So don't put:

```json
{
  "password": "secret123"
}
```

inside a JWT.

Don't put:

```json
{
  "creditCardNumber": "..."
}
```

or:

```json
{
  "refreshToken": "..."
}
```

The payload should contain only the information your application actually needs.

---

# 5. Attack #1 — Modify the Payload

Suppose your token contains:

```json
{
  "sub": "user123",
  "role": "user"
}
```

An attacker decodes it and changes:

```json
{
  "sub": "user123",
  "role": "admin"
}
```

They then send the modified token.

### Secure backend

```text
Modified payload
       ↓
Signature no longer matches
       ↓
❌ JWT rejected
```

### Vulnerable backend

If your server merely decodes the token:

```text
decode(token)
   ↓
trust payload
```

then:

```text
role = admin
```

could be accepted.

---

# 6. Decode ≠ Verify

This distinction is extremely important.

### Decode

```js
jwt.decode(token);
```

means roughly:

> "Show me what's inside."

It does **not** prove the token was created by your server.

### Verify

```js
jwt.verify(token, secret);
```

means:

> "Check the cryptographic signature and token constraints."

For authentication:

```text
❌ decode → trust

✅ verify → trust
```

Never use `decode()` as your authentication mechanism.

---

# 7. Security Test: Modified Payload

Suppose you have a valid token.

Create a modified version where:

```text
role=user
```

becomes:

```text
role=admin
```

Then call:

```http
GET /api/v1/admin/users
Authorization: Bearer <modified-token>
```

Expected:

```text
401 Unauthorized
```

or another appropriate rejection.

It must **not** become:

```text
200 OK
```

---

# 8. Attack #2 — Algorithm Confusion

JWT headers contain:

```json
{
  "alg": "HS256"
}
```

Algorithms include things such as:

```text
HS256
HS384
HS512
RS256
RS384
RS512
```

A dangerous implementation may allow the token to decide which algorithm the server should use.

The attacker might try to manipulate:

```json
{
  "alg": "..."
}
```

The important defense is:

> **The server should explicitly configure which algorithms are allowed.**

For example, conceptually:

```js
jwt.verify(token, secret, {
    algorithms: ["HS256"]
});
```

Now:

```text
HS256 → accepted
unexpected algorithm → rejected
```

---

# 9. Why Explicit Algorithms Matter

Don't think:

```text
"JWT library handles it, so I'm safe."
```

Think:

```text
What algorithm does my application expect?
```

Your authentication system should have a clear cryptographic contract:

```text
Algorithm
+
Key
+
Issuer
+
Audience
+
Expiration
```

The server should enforce the contract.

---

# 10. Symmetric vs Asymmetric JWT

Two common approaches:

### Symmetric

```text
HS256
```

Same secret:

```text
signing secret
     +
verification secret
```

Conceptually:

```text
Server
  ↓
SECRET
  ↓
sign
```

and:

```text
Server
  ↓
SECRET
  ↓
verify
```

---

### Asymmetric

```text
RS256
```

Uses:

```text
Private key → sign
Public key  → verify
```

Conceptually:

```text
Private key
    ↓
  Sign

Public key
    ↓
 Verify
```

The security-testing principles remain similar:

```text
Algorithm must be controlled
Keys must be protected
Verification must be strict
```

---

# 11. Attack #3 — `alg: none`

JWT specifications have historically included an algorithm identifier called:

```text
none
```

A poorly implemented verifier could potentially be tricked into accepting an unsigned token.

Conceptually:

```text
Original:

header.payload.signature
```

attacker attempts:

```text
header.payload.
```

with:

```json
{
  "alg": "none"
}
```

Modern JWT libraries generally protect against this when correctly configured.

But it is still a useful **security test**:

> Does your backend reject unsigned tokens?

Expected:

```text
❌ Reject
```

---

# 12. Attack #4 — Weak Secret

Suppose your server uses:

```env
JWT_SECRET=123456
```

That's a terrible secret.

Why?

Because if the attacker obtains a token and the secret is weak enough, they may be able to guess or brute-force it.

Then they can potentially generate their own valid-looking tokens.

The security model becomes:

```text
Strong secret
    ↓
Hard to forge

Weak secret
    ↓
Potentially guessable
```

---

# 13. What Makes a Good JWT Secret?

For HMAC-based JWTs:

```text
❌ password123
❌ secret
❌ myappsecret
❌ jwtsecret
```

Prefer:

```text
high-entropy random secret
```

And:

```text
Development secret
≠
Production secret
```

Never commit production secrets into Git.

---

# 14. Attack #5 — Token From Another Environment

Imagine:

```text
Development
    ↓
JWT secret A
```

Production:

```text
Production
    ↓
JWT secret B
```

A development token should not be accepted by production.

A good environment separation means:

```text
DEV token
   ↓
Production
   ↓
❌ rejected
```

This is one reason environment-specific secrets matter.

---

# 15. Attack #6 — Expired Token

Suppose:

```json
{
  "sub": "user123",
  "exp": 1750000000
}
```

The token is expired.

Attacker sends it anyway.

Expected:

```text
JWT verification
      ↓
expiration check
      ↓
❌ rejected
```

Never implement authentication as:

```js
const payload = jwt.decode(token);

if (payload.userId) {
    authenticate();
}
```

That completely misses the security purpose of expiration and signature verification.

---

# 16. `exp` Is a Security Control

JWT expiration helps limit the lifetime of a stolen access token.

For example:

```text
Access token
     ↓
15 minutes
     ↓
expires
```

If an attacker steals it:

```text
Attacker
   ↓
stolen token
   ↓
limited window
```

This doesn't eliminate token theft.

It reduces the useful lifetime.

---

# 17. Attack #7 — Missing `exp`

Security test:

Create or obtain a token that doesn't contain a meaningful expiration.

Then determine whether your application accepts it indefinitely.

For access tokens, you generally want a controlled lifetime.

The exact duration is an architecture decision.

For example:

```text
Access token → short-lived
Refresh token → longer-lived
```

We'll examine refresh-token attacks in **22.10**.

---

# 18. Attack #8 — Manipulate `sub`

The `sub` claim commonly represents:

```text
subject / user identity
```

For example:

```json
{
  "sub": "USER_A"
}
```

Attacker tries:

```json
{
  "sub": "USER_B"
}
```

If they could forge the signature, they could potentially impersonate User B.

But if signature verification works correctly:

```text
Modified sub
    ↓
Signature mismatch
    ↓
❌ rejected
```

So this demonstrates why:

> **JWT signature verification is the security boundary.**

---

# 19. Attack #9 — Manipulate `role`

Suppose:

```json
{
  "sub": "USER_A",
  "role": "user"
}
```

Attacker changes:

```json
{
  "sub": "USER_A",
  "role": "admin"
}
```

Again:

```text
Modified role
     ↓
Signature invalid
     ↓
❌ reject
```

But there's another architectural lesson:

### Don't blindly trust authorization claims forever.

For extremely sensitive operations, your application may need to consider current server-side authorization state.

For example:

```text
JWT says:
role = admin
```

but database says:

```text
accountStatus = suspended
```

Your authorization system must still enforce the current security state.

---

# 20. JWT ≠ Authorization

JWT primarily gives you:

```text
Authentication information
```

It doesn't automatically make:

```text
user.role === "admin"
```

safe.

Your authorization layer still needs to decide:

```text
Can this user perform this action?
```

So:

```text
JWT
 ↓
Who are you?

Authorization
 ↓
What are you allowed to do?
```

---

# 21. Attack #10 — Invalid Signature

This is one of the simplest security tests.

Take a valid JWT:

```text
header.payload.signature
```

Change the signature:

```text
header.payload.attackerSignature
```

Send it.

Expected:

```text
❌ 401
```

If your API accepts it:

```text
🚨 Critical authentication vulnerability
```

---

# 22. Attack #11 — Truncated Token

Test:

```text
abc.def
```

instead of:

```text
abc.def.ghi
```

Expected:

```text
❌ rejected
```

Your auth middleware should fail safely.

It shouldn't cause:

```text
500 Internal Server Error
```

if the malformed token is simply an invalid client credential.

---

# 23. Attack #12 — Garbage Token

Send:

```http
Authorization: Bearer hello
```

Expected:

```text
401 Unauthorized
```

Not:

```text
500
```

And definitely not:

```text
200
```

Security testing should include malformed input, not only sophisticated attacks.

---

# 24. Attack #13 — Missing Authorization Header

Request:

```http
GET /api/v1/users/me
```

without:

```text
Authorization
```

Expected:

```text
401 Unauthorized
```

This verifies your authentication middleware actually protects the route.

---

# 25. Attack #14 — Wrong Authentication Scheme

Send:

```http
Authorization: Basic abc
```

instead of:

```http
Authorization: Bearer <jwt>
```

Expected:

```text
401
```

Your parser should not accidentally interpret arbitrary authorization schemes as JWTs.

---

# 26. Attack #15 — Extra/Broken Authorization Data

Test malformed forms such as:

```text
Bearer
```

```text
Bearer
abc
```

```text
Bearer abc def
```

```text
Bearer <invalid-token>
```

Your middleware should:

```text
fail closed
```

That means:

> When authentication is unclear or invalid, deny access.

---

# 27. Fail Closed

This is a very important security principle.

### Dangerous

```text
Token invalid
    ↓
"Maybe allow anyway"
```

### Correct

```text
Token invalid
    ↓
❌ Access denied
```

So:

```text
Unknown
Invalid
Malformed
Expired
Missing
Untrusted

       ↓

      DENY
```

---

# 28. JWT Verification Should Be Centralized

Don't verify JWT differently in every controller.

Bad:

```js
// controller A
jwt.verify(...)

// controller B
jwt.verify(...)

// controller C
jwt.verify(...)
```

Instead:

```text
auth.middleware.js
       ↓
verify JWT
       ↓
req.user
       ↓
controllers
```

Now authentication has one consistent implementation.

This fits the middleware architecture in your starter roadmap.

---

# 29. What Should `req.user` Contain?

After successful verification, you might have:

```js
req.user = {
    id: payload.sub,
    role: payload.role
};
```

Be careful about blindly copying arbitrary JWT fields:

```js
req.user = payload;
```

A cleaner approach is to extract only what your application needs.

For example:

```js
req.user = {
    id: payload.sub,
    role: payload.role
};
```

This reduces accidental coupling to arbitrary token claims.

---

# 30. Verify More Than the Signature

A strong JWT verification policy may check:

```text
Signature
Algorithm
Expiration
Not-before
Issuer
Audience
```

For example:

```text
iss = "my-api"
aud = "my-frontend"
```

Then a token issued for another service:

```text
aud = "some-other-api"
```

can be rejected.

This prevents tokens from being casually reused across security boundaries.

---

# 31. Issuer (`iss`)

The issuer identifies who created the token.

Conceptually:

```json
{
  "iss": "my-api"
}
```

Your verifier can require:

```text
iss === expected issuer
```

So:

```text
Token from unknown issuer
       ↓
❌ rejected
```

---

# 32. Audience (`aud`)

The audience identifies who the token is intended for.

For example:

```json
{
  "aud": "my-api"
}
```

Your backend expects:

```text
my-api
```

A token intended for another service can then be rejected.

This is particularly useful in larger systems with multiple services.

---

# 33. `nbf`

`nbf` means:

```text
Not Before
```

Example:

```json
{
  "nbf": 1750001000
}
```

The token should not be accepted before that time.

A correctly configured verifier should enforce it.

---

# 34. Clock Skew

Real servers don't always have perfectly identical clocks.

JWT verification libraries often allow a small clock tolerance.

But be careful:

```text
Small tolerance
    ✅

Huge tolerance
    ❌
```

You don't want:

```text
expired token
     ↓
accepted for hours
```

just because you've configured a huge clock tolerance.

---

# 35. JWT Secret Rotation

A production system may eventually need to rotate signing keys.

Conceptually:

```text
Old key
   ↓
Old tokens

New key
   ↓
New tokens
```

A mature architecture can support:

```text
current key
+
previous key during transition
```

But don't implement complex key rotation blindly.

The important lesson for now:

> **Keys are security infrastructure, not ordinary configuration strings.**

---

# 36. Don't Put Secrets in the JWT

Never do:

```json
{
  "sub": "123",
  "password": "mypassword",
  "jwtSecret": "secret",
  "refreshToken": "..."
}
```

Remember:

```text
JWT payload
    ↓
Readable by token holder
```

Signature protects integrity.

It does not make the payload confidential.

# 38. Jest + Supertest Example

A simple integration test:

```js
it("rejects a tampered JWT", async () => {
    const response = await request(app)
        .get("/api/v1/users/me")
        .set("Authorization", `Bearer ${tamperedToken}`);

    expect(response.statusCode).toBe(401);
});
```

You can create similar tests for:

```text
expiredToken
malformedToken
wrongSignatureToken
wrongIssuerToken
wrongAudienceToken
```

This turns your security policy into executable documentation.

---

# 39. Test Authorization Too

Don't stop at:

```text
JWT valid → 200
```

Test:

```text
Valid user JWT
    ↓
Admin endpoint
    ↓
403
```

This distinguishes:

```text
Authentication
```

from:

```text
Authorization
```

For example:

```text
401 → I don't know who you are.

403 → I know who you are,
      but you aren't allowed to do this.
```

# 40. JWT Attack vs BOLA

These vulnerabilities can combine.

Imagine:

```text
Attacker
   ↓
forge/steal JWT
   ↓
impersonate User B
   ↓
GET /todos/123
   ↓
BOLA
```

So security testing should not happen in isolated boxes.

You should eventually test attack chains:

```text
Authentication
      +
Authorization
      +
Object ownership
```

# 42. Practical Auth Middleware

Conceptually, your middleware should do something like:

```text
Request
   ↓
Read Authorization header
   ↓
Is Bearer token present?
   │
   ├── NO → 401
   │
   ▼
Extract token
   ↓
Verify signature
   ↓
Verify algorithm
   ↓
Verify expiration
   ↓
Verify issuer/audience
   ↓
Extract trusted claims
   ↓
req.user
   ↓
next()
```

That is the mental model I want you to remember.

---

# 43. A Dangerous Implementation

Imagine:

```js
const token = req.headers.authorization?.split(" ")[1];

const payload = jwt.decode(token);

req.user = payload;

next();
```

🚨 Huge problem.

Why?

Because:

```text
decode()
```

doesn't prove:

```text
Who created this token?
```

You're effectively saying:

```text
Client
 ↓
JWT payload
 ↓
req.user
```

The client can potentially control the identity data.

---

# 44. A Safer Implementation Pattern

Conceptually:

```js
const payload = jwt.verify(
    token,
    env.accessTokenSecret,
    {
        algorithms: ["HS256"],
        issuer: env.jwtIssuer,
        audience: env.jwtAudience
    }
);
```

Then:

```js
req.user = {
    id: payload.sub,
    role: payload.role
};
```

Now:

```text
Client
 ↓
JWT
 ↓
Cryptographic verification
 ↓
Claim validation
 ↓
Trusted identity
```

# 45. Security Testing Checklist

Before you consider JWT authentication trustworthy, ask:

```text
[ ] Does the server verify the signature?
[ ] Does it reject modified payloads?
[ ] Does it reject invalid signatures?
[ ] Does it reject expired tokens?
[ ] Does it reject malformed tokens?
[ ] Does it reject missing tokens?
[ ] Does it enforce an expected algorithm?
[ ] Does it reject unsigned tokens?
[ ] Is the signing secret strong?
[ ] Is the secret outside source control?
[ ] Are production/dev secrets separated?
[ ] Are issuer/audience checked where appropriate?
[ ] Are sensitive claims excluded?
[ ] Is JWT verification centralized?
[ ] Are authentication and authorization separated?
[ ] Are security tests automated?
```

```text

                │
                ▼
             JWT
                │
                ▼
       ┌──────────────────┐
       │ Verify signature  │
       └────────┬─────────┘
                ▼
       Verify algorithm
                │
                ▼
       Verify expiration
                │
                ▼
       Verify issuer/audience
                │
                ▼
        Extract safe claims
                │
                ▼
             req.user
                │
                ▼
          Authorization
                │
                ▼
            Controller
```

And the golden rule:

> **Never trust what a JWT says merely because it looks valid. Trust it only after your server has cryptographically verified it and validated the claims your application relies on.**
