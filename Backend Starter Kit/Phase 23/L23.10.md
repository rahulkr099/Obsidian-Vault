# Lesson 23.10 — Docker Volumes

The Phase 23 roadmap puts **Volumes** immediately after Node + MongoDB:

```text
23.8 Docker Compose
        ↓
23.9 Node + MongoDB
        ↓
23.10 Volumes
        ↓
23.11 Networks
```

The main problem we're solving today is:

> **How do we keep MongoDB data when the MongoDB container is removed or recreated?**

---

# 1. The problem

In the previous lesson, we had:

```text
Docker Compose
     │
 ┌───┴────┐
 ▼        ▼
Node     MongoDB
```

MongoDB stores data inside its container.

For example:

```text
MongoDB container
└── /data/db
    ├── users
    ├── todos
    └── ...
```

Now imagine:

```bash
docker compose down
```

The MongoDB container is removed.

If the database data only lived inside that container, your data can disappear with it.

That's obviously unacceptable.

---

# 2. Containers are disposable

This is one of the most important Docker ideas.

A container should generally be treated as:

```text
temporary
replaceable
recreatable
```

Think:

```text
Container
   ↓
can be destroyed
   ↓
new container
   ↓
application continues
```

But databases are different.

We want:

```text
MongoDB data
   ↓
persistent
```

So we need to separate:

```text
Application runtime
```

from:

```text
Application data
```

---

# 3. Volume solves this

A Docker **volume** provides persistent storage managed by Docker.

Instead of:

```text
MongoDB
   ↓
container filesystem
```

we use:

```text
MongoDB
   ↓
/data/db
   ↓
Docker volume
```

Architecture:

```text
             MongoDB container
                   │
                   │ /data/db
                   ▼
          ┌──────────────────┐
          │ Docker volume    │
          │                  │
          │ MongoDB data     │
          └──────────────────┘
```

Now the container can disappear while the data remains.

---

# 4. The key distinction

Remember this:

```text
Container
=
runtime

Volume
=
persistent data
```

For our backend:

```text
Node container
   ↓
application runtime

MongoDB container
   ↓
database runtime

MongoDB volume
   ↓
database data
```

That's a very useful mental model.

---

# 5. MongoDB's data directory

MongoDB stores its database files in:

```text
/data/db
```

inside the official MongoDB container.

So we want:

```text
MongoDB
   ↓
/data/db
   ↓
persistent volume
```

In Compose:

```yaml
services:
  mongo:
    image: mongo:8
    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
```

This is the central configuration for today's lesson.

---

# 6. Understanding this line

Look at:

```yaml
- mongo-data:/data/db
```

There are two sides:

```text
mongo-data:/data/db
     │        │
     │        └── container path
     │
     └── volume name
```

So:

```text
mongo-data
```

is the Docker volume.

And:

```text
/data/db
```

is where MongoDB expects its data inside the container.

---

# 7. The architecture

Now we have:

```text
                         Docker
                           │
              ┌────────────┴────────────┐
              │                         │
              ▼                         ▼
       Backend container        MongoDB container
                                      │
                                      │ /data/db
                                      ▼
                               ┌──────────────┐
                               │ mongo-data   │
                               │              │
                               │ persistent   │
                               │ database     │
                               │ data         │
                               └──────────────┘
```

The important part:

```text
MongoDB container
      ≠
MongoDB data
```

The data is stored separately.

---

# 8. Named volumes

This:

```yaml
volumes:
  mongo-data:
```

creates a **named volume**.

The name is:

```text
mongo-data
```

You can call it something else:

```yaml
volumes:
  mongodb-data:
```

or:

```yaml
volumes:
  app-db-data:
```

The name is up to you.

Good naming is useful because it makes your infrastructure easier to understand.

---

# 9. Complete Compose example

Now let's combine 23.9 and 23.10:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    volumes:
      - .:/app
      - /app/node_modules

    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp

    depends_on:
      - mongo

  mongo:
    image: mongo:8

    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
```

Now we have:

```text
Backend
   ↓
MongoDB
   ↓
mongo-data volume
```

---

# 10. What happens during startup?

Run:

```bash
docker compose up -d
```

Compose sees:

```yaml
volumes:
  mongo-data:
```

and creates the volume if it doesn't already exist.

Then:

```text
Compose
  ↓
mongo-data volume
  ↓
MongoDB container
  ↓
/data/db
```

MongoDB writes its database files there.

---

# 11. What happens when the container is recreated?

Suppose MongoDB is running:

```text
MongoDB container A
       ↓
mongo-data
       ↓
users/todos/etc.
```

Now container A is removed.

Then Compose creates:

```text
MongoDB container B
       ↓
same mongo-data
       ↓
existing users/todos/etc.
```

The data survives.

That's the entire purpose of the volume.

---

# 12. Container lifecycle vs data lifecycle

This is worth remembering.

Without a volume:

```text
Container A
   ↓
Database data
   ↓
Container removed
   ↓
Data gone
```

With a volume:

```text
Container A
   ↓
Volume
   ↓
Database data

Container removed
   ↓
Volume remains

Container B
   ↓
Same volume
   ↓
Same database data
```

This separation is one of the most important Docker concepts.

---

# 13. `docker compose down`

Suppose you run:

```bash
docker compose down
```

Normally this removes the Compose-managed containers and network.

The named volume:

```text
mongo-data
```

normally remains.

So:

```text
docker compose down
```

does **not** mean:

```text
delete all database data
```

That's an important safety property.

---

# 14. But there's a dangerous command

You can explicitly remove volumes with:

```bash
docker compose down -v
```

The:

```text
-v
```

means remove associated volumes.

So:

```bash
docker compose down
```

and:

```bash
docker compose down -v
```

are very different.

### Normal down

```text
containers → removed
volumes    → retained
```

### Down with `-v`

```text
containers → removed
volumes    → removed
database   → data lost
```

So be careful with:

```bash
docker compose down -v
```

especially if you have valuable development data.

---

# 15. Inspect your volumes

You can list Docker volumes:

```bash
docker volume ls
```

You might see something like:

```text
DRIVER    VOLUME NAME
local     myproject_mongo-data
```

The exact name can depend on your Compose project.

---

# 16. Inspect a specific volume

Run:

```bash
docker volume inspect myproject_mongo-data
```

Docker will show information about the volume.

This is useful when debugging storage.

---

# 17. Why does the volume name have a project prefix?

Suppose your Compose project is:

```text
myproject
```

and you define:

```yaml
volumes:
  mongo-data:
```

Compose may create something conceptually like:

```text
myproject_mongo-data
```

This prevents different Compose projects from accidentally using the same resource names.

---

# 18. Named volume vs bind mount

You've already seen:

```yaml
- .:/app
```

That's a **bind mount**.

Now:

```yaml
- mongo-data:/data/db
```

is a **named volume**.

They are not the same thing.

---

# 19. Bind mount

This:

```yaml
- .:/app
```

means:

```text
Your computer
     │
     │ bind mount
     ▼
Container /app
```

The host directory is directly mounted.

We use this heavily during development because we want live source-code changes.

```text
Edit server.js
     ↓
Host filesystem
     ↓
/app in container
     ↓
nodemon
     ↓
restart
```

---

# 20. Named volume

This:

```yaml
- mongo-data:/data/db
```

means:

```text
Docker-managed storage
       │
       ▼
MongoDB container
       │
       ▼
/data/db
```

Docker manages the volume.

We don't need a project folder like:

```text
./mongo-data
```

on our machine.

---

# 21. Why not use a bind mount for MongoDB?

You could technically do something like:

```yaml
- ./mongo-data:/data/db
```

but for many development setups, a Docker-managed named volume is cleaner.

You get:

```text
Docker-managed persistence
```

without mixing database storage files directly into your Git project directory.

So for our starter:

```text
Source code
→ bind mount

MongoDB data
→ named volume
```

That's a clean separation.

---

# 22. The two volume patterns

Your development environment may therefore have:

```yaml
backend:
  volumes:
    - .:/app
    - /app/node_modules

mongo:
  volumes:
    - mongo-data:/data/db
```

Three different storage ideas are happening.

### Source code

```text
.:/app
```

Host → container.

### Node dependencies

```text
/app/node_modules
```

Container-managed volume.

### MongoDB data

```text
mongo-data:/data/db
```

Named persistent volume.

---

# 23. Why keep `node_modules` separate?

Recall our earlier lesson.

We have:

```yaml
- .:/app
- /app/node_modules
```

Without the second mount, the bind mount can hide the container's `/app/node_modules`.

The separate volume keeps the container's dependencies isolated.

So:

```text
Host
├── source code
└── maybe host node_modules

Container
├── source code ← bind mount
└── node_modules ← container volume
```

This is different from the MongoDB volume, but the same general Docker storage mechanism is involved.

---

# 24. Persistent doesn't mean backup

This is a **very important production distinction**.

A Docker volume gives you:

```text
persistence
```

It does **not automatically give you**:

```text
backup
```

For example:

```text
MongoDB
  ↓
Docker volume
```

protects against:

```text
container recreation
```

But it doesn't necessarily protect against:

```text
disk failure
server destruction
accidental deletion
corruption
ransomware
```

So:

```text
Volume ≠ Backup
```

In production, you need proper database backup and recovery strategies.

---

# 25. Volume ≠ database replication

Similarly:

```text
Docker volume
```

doesn't mean:

```text
high availability
```

It simply provides persistent storage.

These are different concepts:

```text
Volume
  → persistence

Backup
  → recovery

Replication
  → redundancy

High availability
  → service continuity
```

Don't mix them together.

---

# 26. A useful analogy

Think of a container as a rented room:

```text
Container
=
temporary room
```

The volume is your storage locker:

```text
Volume
=
locker
```

You can leave the room:

```text
Container deleted
```

but your belongings remain:

```text
Volume remains
```

Then you get another room:

```text
New container
```

and connect the same locker.

```text
New container
      ↓
same volume
      ↓
same data
```

This analogy is surprisingly useful.

---

# 27. What if we change the MongoDB image?

Suppose today:

```yaml
image: mongo:8
```

and later we recreate the container.

The volume can remain:

```text
mongo-data
```

and the new container mounts:

```text
/data/db
```

from the same volume.

But database version upgrades require care.

Don't assume:

```text
new MongoDB image
+
old database files
=
always safe
```

Database upgrades should follow MongoDB's supported upgrade path and compatibility rules.

The volume gives persistence; it doesn't make upgrades automatically safe.

---

# 28. Volume ownership and permissions

For MongoDB and other databases, the container process may have specific filesystem permissions.

If you manually mount host directories, you can encounter:

```text
permission denied
```

Named volumes often avoid many of these development-time host filesystem permission issues because Docker manages the storage.

This is another reason named volumes are convenient for database containers.

---

# 29. Volume lifecycle

Think of the lifecycle as:

```text
Create volume
      ↓
Attach to container
      ↓
MongoDB writes data
      ↓
Container removed
      ↓
Volume remains
      ↓
New container
      ↓
Attach same volume
      ↓
Data available
```

This is the lifecycle you should understand.

---

# 30. What happens if the volume is deleted?

If you run:

```bash
docker compose down -v
```

you may remove:

```text
mongo-data
```

Then:

```text
volume
   ↓
deleted
   ↓
MongoDB data
   ↓
gone
```

The next:

```bash
docker compose up
```

creates a new empty volume.

MongoDB starts as a fresh database.

---

# 31. This can actually be useful during development

Sometimes you **want** a clean database.

For example:

```bash
docker compose down -v
docker compose up
```

can give you a fresh database environment.

But don't run it casually if you have data you care about.

A useful mental rule:

> **`down` cleans containers; `down -v` cleans containers + persistent volumes.**

---

# 32. Check whether your data survives

This is a great exercise.

### Start

```bash
docker compose up -d
```

Create some test data.

For example, create a user or todo through your API.

Then:

```bash
docker compose down
```

Start again:

```bash
docker compose up -d
```

Check your API.

Your data should still be there.

That proves the volume is working.

---

# 33. Experiment: remove the volume

If you're comfortable losing your development data:

```bash
docker compose down -v
```

Then:

```bash
docker compose up -d
```

Now your database should be fresh.

This is a good practical demonstration of:

```text
volume exists
    ↓
data survives

volume removed
    ↓
data disappears
```

# 34. Volume configuration explained line-by-line

Let's look again:

```yaml
services:
  mongo:
    image: mongo:8

    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
```

### Part 1

```yaml
mongo:
```

MongoDB service.

### Part 2

```yaml
volumes:
```

Define mounts for this service.

### Part 3

```yaml
- mongo-data:/data/db
```

Attach volume `mongo-data` to `/data/db`.

### Part 4

```yaml
volumes:
```

Top-level Compose volume definitions.

### Part 5

```yaml
mongo-data:
```

Declare the named volume.

---

# 35. Why is `mongo-data` declared twice?

This often confuses beginners.

You see:

```yaml
services:
  mongo:
    volumes:
      - mongo-data:/data/db
```

and later:

```yaml
volumes:
  mongo-data:
```

They have different purposes.

The first says:

> Mount this volume here.

The second says:

> This volume exists as a Compose resource.

Think:

```text
service configuration
      ↓
use volume

top-level volumes
      ↓
define volume
```

---

# 36. Multiple services can share a volume

Technically, Docker volumes can be mounted by multiple containers.

For example:

```text
service A
   │
   ├──── volume
   │
service B
```

But don't automatically share database storage between unrelated applications.

Database storage has application-specific semantics.

For MongoDB, normally:

```text
MongoDB container
      ↓
its database volume
```

Keep the ownership clear.

---

# 37. Don't mount MongoDB data into your Node container

Avoid designs like:

```text
Node container
   ↓
MongoDB /data/db
```

The Node application should communicate with MongoDB through:

```text
network
```

not through MongoDB's filesystem.

Correct:

```text
Node
 │
 │ MongoDB protocol
 ▼
MongoDB
 │
 ▼
volume
```

This is an important separation:

```text
Network
=
communication

Volume
=
storage
```

---

# 38. This leads directly to the next lesson

We've now separated two concepts:

```text
Volume
  ↓
storage

Network
  ↓
communication
```

The next lesson, **23.11 Networks**, will explain exactly how:

```text
backend
   ↓
mongo
```

communicate inside Docker.

The roadmap explicitly places Networks immediately after Volumes.

# 39. Our architecture after 23.10

We now have:

```text
                       Docker Compose
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
      ┌──────────────┐             ┌──────────────┐
      │ Backend      │             │ MongoDB      │
      │ container    │             │ container    │
      │              │             │              │
      │ Node         │────────────►│ MongoDB      │
      │ Express      │  network   │              │
      └──────────────┘             └──────┬───────┘
                                         │
                                         │ /data/db
                                         ▼
                                  ┌──────────────┐
                                  │ mongo-data   │
                                  │ volume       │
                                  └──────────────┘
```

So:

```text
Backend
  ↓
network
  ↓
MongoDB
  ↓
volume
  ↓
persistent data
```

This is a very clean mental model.

# 40. Development vs production

For local development:

```text
Docker Compose
    ↓
Node container
    +
MongoDB container
    +
named volume
```

For production, you may **not** necessarily run MongoDB inside the same Compose environment.

You might instead use:

```text
Application container
       ↓
Managed MongoDB
```

For example:

```text
Cloud backend
       ↓
MongoDB Atlas / managed database
```

In that case, your application still uses:

```text
MONGO_URI
```

The database location changes, but your application architecture doesn't need to fundamentally change.

---

# 41. This is why configuration matters

Development:

```text
MONGO_URI=mongodb://mongo:27017/myapp
```

Production:

```text
MONGO_URI=<production database connection>
```

Your application still does:

```js
mongoose.connect(env.mongoUri);
```

So:

```text
Application code
      ↓
configuration
      ↓
database
```

not:

```text
Application code
      ↓
hard-coded database location
```

---

# 42. Three different kinds of persistence to remember

It's useful to distinguish:

### Container filesystem

```text
temporary
```

### Named volume

```text
persistent storage
```

### External/managed database

```text
persistent infrastructure managed outside your app containers
```

As your applications become more production-oriented, you'll use the third option more often.

---

# 43. Common mistake #1 — thinking containers are permanent

Bad mental model:

```text
MongoDB container
=
the database forever
```

Better:

```text
MongoDB container
=
MongoDB process

Volume
=
database data
```

---

# 44. Common mistake #2 — thinking volume means backup

Wrong:

```text
volume
=
backup
```

Correct:

```text
volume
=
persistent storage
```

Backups are a separate responsibility.

---

# 45. Common mistake #3 — accidentally deleting volumes

Be careful with:

```bash
docker compose down -v
```

Before running it, ask:

> Do I actually want to delete my database data?

This command is very useful for resetting development environments, but dangerous when used carelessly.

---

# 46. Common mistake #4 — putting DB files in Git

Don't do:

```text
project/
├── mongo-data/
│   ├── ...
```

and commit database files into Git.

Instead:

```text
project
   ↓
Compose
   ↓
Docker named volume
```

Database runtime files should not be treated like application source code.

---

# 47. Common mistake #5 — confusing volume with network

Remember:

```text
Volume
   ↓
Where is data stored?
```

Network:

```text
Network
   ↓
How do services communicate?
```

So:

```text
Node → MongoDB
```

uses:

```text
network
```

while:

```text
MongoDB → database files
```

uses:

```text
volume
```

# 🧠 The most important mental model

Memorize this:

```text
┌─────────────────────────────────────┐
│ Container                           │
│                                     │
│ Runs the application/process        │
└──────────────────┬──────────────────┘
                   │
                   │ mounts
                   ▼
            ┌──────────────┐
            │ Volume       │
            │              │
            │ Persistent   │
            │ data         │
            └──────────────┘
```

For MongoDB:

```text
MongoDB container
      │
      ▼
/data/db
      │
      ▼
mongo-data
      │
      ▼
persistent database
```

And separately:

```text
Backend container
      │
      │ network
      ▼
MongoDB container
```

So the golden rule is:

> **Networks move data between containers; volumes keep data beyond the life of containers.**
