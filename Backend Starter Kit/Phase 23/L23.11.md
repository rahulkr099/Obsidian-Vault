# Lesson 23.11 — Docker Networks

According to your roadmap, **23.11 is Networks**, after Docker Compose, Node + MongoDB, and Volumes.

In the previous lesson, we learned:

```text
Volume
   ↓
persistent storage
```

Today we learn:

```text
Network
   ↓
container-to-container communication
```

The main question is:

> **How does our Node container communicate with our MongoDB container?**

---

# 1. The problem

We currently have two containers:

```text
┌──────────────────┐
│ Backend          │
│ Node + Express   │
└──────────────────┘

┌──────────────────┐
│ MongoDB          │
│ MongoDB server   │
└──────────────────┘
```

Our backend needs to connect to MongoDB.

But this doesn't work:

```text
mongodb://localhost:27017/myapp
```

Why?

Because inside the backend container:

```text
localhost
```

means:

> **the backend container itself.**

It does **not** mean:

> the MongoDB container.

So we need a way for containers to communicate.

That's where Docker networking comes in.

---

# 2. Network in simple words

A Docker network is basically a private communication environment for containers.

Think of it like a private LAN:

```text
Docker Network
┌──────────────────────────────────────┐
│                                      │
│  Backend              MongoDB       │
│     │                    │           │
│     └──────── communicate ───────────┘
│                                      │
└──────────────────────────────────────┘
```

The containers can communicate using service/container names rather than hard-coded IP addresses.

---

# 3. Our architecture

After today's lesson:

```text
                         Docker
                           │
                    Docker Network
                           │
              ┌────────────┴────────────┐
              │                         │
              ▼                         ▼
       Backend container        MongoDB container
              │                         │
              │                         │
              └────── mongo:27017 ──────┘
                                        │
                                        ▼
                                  mongo-data
                                    volume
```

Notice the distinction:

```text
Network → communication
Volume  → storage
```

This distinction is extremely important.

---

# 4. Compose already creates a network

Here's something useful:

When you use Docker Compose:

```bash
docker compose up
```

Compose normally creates a default network for the project.

So with:

```yaml
services:
  backend:
    ...
  
  mongo:
    image: mongo:8
```

both services are normally connected to the same Compose network.

Conceptually:

```text
myproject_default
       │
       ├── backend
       │
       └── mongo
```

That's why this works:

```text
mongodb://mongo:27017/myapp
```

The hostname:

```text
mongo
```

comes from the Compose service name.

---

# 5. Service names become hostnames

This is one of the most important Docker concepts.

Suppose:

```yaml
services:
  mongo:
    image: mongo:8
```

Then another service on the same Compose network can use:

```text
mongo
```

as the hostname.

Therefore:

```text
mongodb://mongo:27017/myapp
```

means:

```text
Protocol: mongodb
Host:     mongo
Port:     27017
Database: myapp
```

Docker's internal DNS handles the name resolution.

---

# 6. You don't need the IP address

You might imagine:

```text
backend
   ↓
172.20.0.3
   ↓
MongoDB
```

But don't build your application around that IP.

Container IPs can change.

Instead:

```text
backend
   ↓
mongo
   ↓
MongoDB
```

The service name is the stable identifier.

---

# 7. Why container IPs can change

Imagine:

```text
mongo
  ↓
172.20.0.3
```

You remove the container.

Compose creates a new one:

```text
mongo
  ↓
172.20.0.7
```

If your code had:

```text
mongodb://172.20.0.3:27017
```

it would now fail.

But if your code uses:

```text
mongodb://mongo:27017
```

Docker resolves:

```text
mongo
   ↓
current MongoDB container IP
```

Your application doesn't need to care about the IP.

---

# 8. Think of Docker DNS

Conceptually:

```text
Node
 │
 │ "Where is mongo?"
 ▼
Docker DNS
 │
 │ "mongo = current MongoDB container"
 ▼
MongoDB
```

So:

```text
mongodb://mongo:27017
```

is essentially:

```text
Find the service called "mongo"
        ↓
Get its current network address
        ↓
Connect to port 27017
```

This is much better than manually managing IP addresses.

---

# 9. The Compose file

Our current Compose configuration can be:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    volumes:
      - .:/app
      - /app/node_modules

    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp

    depends_on:
      - mongo

  mongo:
    image: mongo:8

    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
```

Even though we haven't explicitly written:

```yaml
networks:
```

Compose creates a default network for these services.

```bash
docker compose up -d
```

```bash
docker network ls
```

You may see something similar to:

```text
NETWORK ID     NAME
abc123         myproject_default
```

# 11. Inspect the Compose network

You can run:

```bash
docker network inspect myproject_default
```

You'll get information about the network and its connected containers.

Conceptually:

```text
Network
 ├── backend
 └── mongo
```

This is a great command when debugging container communication.

---

# 12. The `ports` field is not the same thing

This is a very common beginner confusion.

We have:

```yaml
ports:
  - "5000:5000"
```

for backend.

That means:

```text
Host
  │
  │ localhost:5000
  ▼
Backend container :5000
```

It exposes the backend to your machine.

But backend → MongoDB communication doesn't require a host port mapping.

It happens through the Docker network:

```text
Backend
   │
   │ mongo:27017
   ▼
MongoDB
```

---

# 13. Internal port vs host port

Suppose MongoDB has:

```yaml
ports:
  - "27018:27017"
```

This means:

```text
Host port
27018
   │
   ▼
Container port
27017
```

From your host:

```text
localhost:27018
```

From another container on the same network:

```text
mongo:27017
```

So:

```text
Host → MongoDB
localhost:27018

Container → MongoDB
mongo:27017
```

This is one of the most important Docker networking rules.

---

# 14. Why doesn't Node use `localhost:27018`?

Because Node is inside a container.

Inside the backend container:

```text
localhost
```

means:

```text
Backend container
```

not your Linux machine.

So:

```text
mongodb://localhost:27018
```

would try to find MongoDB inside the backend container.

But MongoDB is here:

```text
mongo container
```

Therefore:

```text
mongodb://mongo:27017
```

is correct.

---

# 15. Container-to-container communication

The normal path is:

```text
Backend container
       │
       │ Docker network
       ▼
MongoDB container
```

The request never needs to leave Docker and go through your host.

This is more direct:

```text
Backend
   ↓
Docker network
   ↓
MongoDB
```

rather than:

```text
Backend
   ↓
Host
   ↓
published port
   ↓
MongoDB
```

For internal service communication, use the Docker network.

---

# 16. Default Compose network

With:

```yaml
services:
  backend:
  mongo:
```

Compose effectively gives you something like:

```text
project_default
```

and:

```text
backend ─────┐
             │
             ▼
       project_default
             ▲
             │
mongo ───────┘
```

Both services can communicate.

This is enough for many small development environments.

---

# 17. Why explicitly define networks?

As your system grows, you may want more control.

For example:

```text
frontend
backend
mongo
redis
worker
```

You might want:

```text
frontend network
backend network
database network
```

Then you can control which services can communicate with which other services.

This becomes useful for isolation and security.

---

# 18. Example: custom network

We can define:

```yaml
services:
  backend:
    networks:
      - backend-network

  mongo:
    networks:
      - backend-network

networks:
  backend-network:
```

Now:

```text
backend
   │
   └──── backend-network ──── mongo
```

Both services are attached to:

```text
backend-network
```

---

# 19. Why use a custom network?

A custom network makes your architecture explicit.

Instead of:

```text
Everything
   ↓
default network
```

you can design:

```text
                    Docker
                      │
        ┌─────────────┴─────────────┐
        │                           │
        ▼                           ▼
 frontend-network            backend-network
        │                           │
        ▼                           ▼
     frontend                   backend
                                    │
                                    ▼
                                  mongo
```

Now you can intentionally control communication boundaries.

---

# 20. Multiple networks

A service can belong to more than one network.

For example:

```yaml
services:
  backend:
    networks:
      - frontend-network
      - backend-network

  frontend:
    networks:
      - frontend-network

  mongo:
    networks:
      - backend-network

networks:
  frontend-network:
  backend-network:
```

Architecture:

```text
Frontend
   │
   │ frontend-network
   ▼
Backend
   │
   │ backend-network
   ▼
MongoDB
```

This is a powerful pattern.

---

# 21. Why is this useful?

Now MongoDB doesn't need to be directly connected to the frontend network.

```text
Frontend ✕ MongoDB
```

Instead:

```text
Frontend
   ↓
Backend
   ↓
MongoDB
```

The backend acts as the application boundary.

This is a good security and architecture principle.

---

# 22. Think in trust boundaries

Imagine:

```text
Internet
   ↓
Frontend
   ↓
Backend
   ↓
Database
```

You generally don't want:

```text
Internet
   ↓
MongoDB
```

or:

```text
Frontend
   ↓
MongoDB
```

The backend should control database access.

So networks can help reinforce your architecture:

```text
Public-facing
      ↓
Backend
      ↓
Private database
```

---

# 23. Network isolation

A network can provide a degree of isolation.

For example:

```text
frontend-network
 ├── frontend
 └── backend

database-network
 ├── backend
 └── mongo
```

MongoDB isn't attached to the frontend network.

Therefore:

```text
frontend → mongo
```

doesn't have the same direct network path.

This is much cleaner than putting every service onto one giant network.

---

# 24. But don't think Docker networks are a complete security boundary

This is important.

Networks help with isolation, but they don't replace:

```text
authentication
authorization
firewalls
TLS
database credentials
secrets management
application security
```

Your MongoDB should still require proper authentication where appropriate.

Network isolation is **defense in depth**, not your only security control.

---

# 25. Network aliases

Docker networking can also provide aliases.

Conceptually:

```yaml
networks:
  backend-network:
    aliases:
      - database
```

Then a service could potentially be reachable using:

```text
database
```

But don't add aliases unless they make your architecture clearer.

Usually the Compose service name is enough:

```text
mongo
```

Keep things simple.

---

# 26. Network naming vs service naming

These are different:

```text
Service:
mongo
```

and:

```text
Network:
backend-network
```

The service identifies:

> **Which application/container do I want to reach?**

The network identifies:

> **Which communication environment are these services attached to?**

So:

```text
backend
  ↓
backend-network
  ↓
mongo
```

---

# 27. Network and volume side-by-side

This is worth memorizing:

|Concept|Purpose|
|---|---|
|Container|Runs a process|
|Network|Connects containers|
|Volume|Persists data|
|Image|Template for a container|
|Compose|Defines/manages multiple services|

So our architecture becomes:

```text
Image
  ↓
Container
  ↓
Network ───────→ other containers

Container
  ↓
Volume
  ↓
persistent data
```

# 29. The request path

Suppose the browser sends:

```http
GET /api/v1/todos
```

The flow is:

```text
Browser
   │
   │ localhost:5000
   ▼
Backend container
   │
   │ application logic
   ▼
Repository
   │
   │ mongodb://mongo:27017
   ▼
Docker DNS
   │
   ▼
MongoDB container
   │
   ▼
mongo-data volume
```

Each layer has a different job.

---

# 30. Docker DNS is the magic

When your Node application says:

```text
mongo
```

Docker can resolve it.

Conceptually:

```text
mongo
 ↓
DNS lookup
 ↓
MongoDB container address
 ↓
connection
```

You don't need:

```text
/etc/hosts
```

You don't need to manually configure IP addresses.

You don't need to discover the IP every time the container restarts.

That's one of the reasons container orchestration becomes manageable.

---

# 31. What happens when MongoDB restarts?

Suppose:

```text
mongo
 ↓
IP A
```

MongoDB is recreated:

```text
mongo
 ↓
IP B
```

Node still uses:

```text
mongo:27017
```

Docker's service discovery handles the current destination.

Your application doesn't need to change its configuration.

This is the major advantage of using names rather than IP addresses.

---

# 32. What happens if the backend restarts?

Same idea.

```text
backend
 ↓
new container
```

It reconnects to:

```text
mongo:27017
```

The network continues to provide the service discovery.

And MongoDB's data remains in:

```text
mongo-data
```

So now we've combined:

```text
Network
+
Volume
```

to make containers replaceable.

---

# 33. This is the real Docker mindset

Instead of thinking:

```text
"This exact container must stay alive."
```

think:

```text
"This service can be recreated whenever necessary."
```

The infrastructure provides:

```text
Image
   ↓
new container

Network
   ↓
find other services

Volume
   ↓
preserve important data
```

This is the foundation of containerized architecture.

---

# 34. A production-style mental model

Eventually you might have:

```text
                 Load Balancer
                       │
              ┌────────┴────────┐
              ▼                 ▼
          Backend 1          Backend 2
              │                 │
              └───────┬─────────┘
                      │
                 Backend Network
                      │
                      ▼
                 Database
```

Both backend instances can find the database through the appropriate network/service configuration.

You don't want to design around:

```text
Backend 1 → 172.18.0.5
Backend 2 → 172.18.0.6
```

You want service-level discovery.

---

# 35. Don't expose everything

Suppose your Compose file has:

```yaml
backend:
  ports:
    - "5000:5000"

mongo:
  ports:
    - "27017:27017"
```

Now MongoDB is also accessible from your host.

But if you don't need that, you can omit MongoDB's `ports`.

Then:

```text
Host
 │
 └──► Backend :5000

Backend
 │
 └──► MongoDB :27017
```

MongoDB remains internal to Docker.

This is usually a cleaner development architecture.

---

# 36. Public vs internal services

Think:

```text
Public
   │
   ▼
Backend
   │
   ▼
Internal
MongoDB
```

The backend has:

```yaml
ports:
  - "5000:5000"
```

MongoDB doesn't necessarily need:

```yaml
ports:
  - "27017:27017"
```

because the backend reaches it through the network.

This reduces unnecessary exposure.

---

# 37. Common mistake #1 — using `localhost`

Wrong:

```env
MONGO_URI=mongodb://localhost:27017/myapp
```

inside Docker.

Correct:

```env
MONGO_URI=mongodb://mongo:27017/myapp
```

because:

```text
mongo
```

is the Compose service name.

---

# 38. Common mistake #2 — using host port internally

Suppose:

```yaml
mongo:
  ports:
    - "27018:27017"
```

Wrong:

```text
mongodb://mongo:27018
```

Correct:

```text
mongodb://mongo:27017
```

because containers communicate using the MongoDB container's listening port.

---

# 39. Common mistake #3 — hard-coding IPs

Don't do:

```text
mongodb://172.20.0.5:27017
```

Use:

```text
mongodb://mongo:27017
```

Service names are much more reliable.

---

# 40. Common mistake #4 — putting everything on every network

You might eventually have:

```text
frontend
backend
worker
redis
mongo
```

Don't automatically connect every service to every network.

Instead, ask:

> **Which services actually need to communicate?**

For example:

```text
frontend
   ↓
backend
   ↓
mongo
```

and:

```text
backend
   ↓
redis
```

Then design the networks around those communication requirements.

---

# 41. Common mistake #5 — assuming a network replaces authorization

Even if:

```text
frontend cannot directly reach mongo
```

you still need:

```text
database credentials
application authorization
authentication
input validation
security controls
```

Networking reduces the attack surface.

It doesn't make the application automatically secure.

---

# 42. A custom network version

If we want to explicitly define our architecture:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp

    networks:
      - backend-network

    depends_on:
      - mongo

  mongo:
    image: mongo:8

    volumes:
      - mongo-data:/data/db

    networks:
      - backend-network

volumes:
  mongo-data:

networks:
  backend-network:
```

Now the relationships are explicit:

```text
backend ─── backend-network ─── mongo
                                  │
                                  ▼
                             mongo-data
```

---

# 43. Should you always use custom networks?

Not necessarily.

For a small Compose application:

```yaml
services:
  backend:
  mongo:
```

the default network is often perfectly fine.

Use explicit networks when:

- you have multiple groups of services
    
- you want clearer architecture
    
- you need network isolation
    
- you have frontend/backend/database boundaries
    
- the Compose project is becoming more complex
    

Don't add complexity just because Docker allows it.

# 45. Debugging a MongoDB connection

Suppose Node reports:

```text
MongoServerSelectionError
```

Don't immediately change random configuration.

Work through the architecture:

### Step 1

Is MongoDB running?

```bash
docker compose ps
```

### Step 2

Is backend running?

```bash
docker compose ps
```

### Step 3

Is the backend using:

```text
mongo:27017
```

rather than:

```text
localhost:27017
```

### Step 4

Are both services attached to the same network?

```bash
docker network inspect <network>
```

### Step 5

Is MongoDB actually listening and ready?

Check:

```bash
docker compose logs mongo
```

This is much better than blindly changing ports.

# 46. Network architecture vs application architecture

Docker networking should not change your application layers.

Your application remains:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Model
 ↓
MongoDB
```

Docker adds infrastructure around it:

```text
Backend container
      │
      │ network
      ▼
MongoDB container
      │
      │ volume
      ▼
Persistent data
```

Your source architecture and infrastructure architecture are complementary.
