# Lesson 23.12 — Environment Variables

Your Phase 23 roadmap explicitly places **Environment Variables** after Networks and before Health Checks.

This lesson connects Docker with something you've already learned earlier: **environment configuration**.

Your starter architecture already establishes the idea:

```text
.env
 ↓
dotenv
 ↓
config/env.js
 ↓
application
```

and recommends values such as `NODE_ENV`, `PORT`, `MONGO_URI`, token secrets, token expiry, and `FRONTEND_URL`.

---

# 1. The problem

Imagine your application contains:

```js
const PORT = 5000;
const MONGO_URI = "mongodb://localhost:27017/myapp";
const JWT_SECRET = "super-secret";
```

This looks simple.

But it's a bad architecture.

Why?

Because configuration is now mixed with application code.

And some configuration is sensitive:

```text
JWT secret
database credentials
API keys
SMTP credentials
cloud credentials
```

You don't want these inside your source code or Git repository.

Instead:

```text
Application code
      ↓
Configuration
```

---

# 2. What is an environment variable?

An environment variable is a value provided to your application by its environment.

For example:

```text
PORT=5000
```

or:

```text
NODE_ENV=development
```

or:

```text
MONGO_URI=mongodb://mongo:27017/myapp
```

Your Node application can access them through:

```js
process.env.PORT
```

So:

```text
Environment
    ↓
process.env
    ↓
Application
```

---

# 3. Why do we need them?

The same application can run in different environments.

For example:

```text
Development
     ↓
localhost

Testing
     ↓
test database

Production
     ↓
production database
```

You don't want three different versions of your application code.

You want:

```text
Same application
       +
Different configuration
```

That's the key idea.

---

# 4. Example

Development:

```env
NODE_ENV=development
PORT=5000
MONGO_URI=mongodb://localhost:27017/myapp
```

Docker:

```env
NODE_ENV=development
PORT=5000
MONGO_URI=mongodb://mongo:27017/myapp
```

Production:

```env
NODE_ENV=production
PORT=5000
MONGO_URI=<production-database>
```

Notice:

```text
Application code
       ↓
doesn't need to change
```

Only configuration changes.

---

# 5. Environment variables in Docker

This becomes especially important now.

Previously we had:

```text
Backend container
       ↓
MongoDB container
```

with:

```text
MONGO_URI=mongodb://mongo:27017/myapp
```

We don't want to hard-code this inside the Dockerfile.

Instead:

```text
Docker Compose
      ↓
environment variables
      ↓
Backend container
      ↓
Node application
```

---

# 6. Docker Compose `environment`

You can provide variables directly:

```yaml
services:
  backend:
    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp
```

Inside Node:

```js
process.env.NODE_ENV
process.env.PORT
process.env.MONGO_URI
```

So the flow becomes:

```text
docker-compose.yml
       ↓
environment
       ↓
container
       ↓
process.env
```

---

# 7. Important: Docker changes the MongoDB hostname

Earlier, outside Docker, you might have:

```env
MONGO_URI=mongodb://localhost:27017/myapp
```

Inside Docker:

```env
MONGO_URI=mongodb://mongo:27017/myapp
```

Why?

Because we learned in Lesson 23.11:

```text
localhost
   ↓
current container
```

while:

```text
mongo
   ↓
MongoDB service
```

So environment variables let us change this configuration without changing application code.

---

# 8. `env_file`

Instead of writing variables directly inside Compose:

```yaml
services:
  backend:
    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp
```

you can use:

```yaml
services:
  backend:
    env_file:
      - .env
```

Then:

```text
.env
 ↓
Docker Compose
 ↓
backend container
```

This can keep your Compose file cleaner.

For local Docker development:

```env
MONGO_URI=mongodb://mongo:27017/myapp
```

Then:

```yaml

  backend:
    env_file:
      - .env
```

```text
NODE_ENV

MONGO_URI
```

---

# 10. But don't blindly put secrets in `.env`

This is important.

You might have:

```env
ACCESS_TOKEN_SECRET=very-secret-value
```

or:

```env
MONGO_PASSWORD=super-secret
```

You should generally **not commit those secrets to Git**.

Your project should have:

```text
.env
.env.example
.gitignore
```

---

# 11. `.env` vs `.env.example`

### `.env`

Contains your actual local values:

```env
NODE_ENV=development
PORT=5000
MONGO_URI=mongodb://mongo:27017/myapp
ACCESS_TOKEN_SECRET=some-real-secret
```

### `.env.example`

Contains the structure but not real secrets:

```env
NODE_ENV=development
PORT=5000
MONGO_URI=mongodb://mongo:27017/myapp

ACCESS_TOKEN_SECRET=
REFRESH_TOKEN_SECRET=

ACCESS_TOKEN_EXPIRES_IN=15m
REFRESH_TOKEN_EXPIRES_IN=7d

FRONTEND_URL=http://localhost:5173
```

Your earlier project architecture explicitly uses this `.env` / `.env.example` pattern.

---

# 12. Why `.env.example` is useful

Imagine another developer clones your project.

They don't know:

```text
Which variables are required?
What's the variable name?
Which values need to be configured?
```

`.env.example` answers those questions.

They can do:

```bash
cp .env.example .env
```

and then fill in the required values.

So:

```text
.env.example
=
configuration documentation
```

That's a very useful way to think about it.

---

# 13. `.gitignore`

Your `.gitignore` should normally include:

```gitignore
.env
```

Then:

```text
.env
   ↓
local only
   ↓
not committed
```

while:

```text
.env.example
   ↓
safe template
   ↓
committed
```

---

# 14. Never do this

Don't write:

```js
const JWT_SECRET = "my-super-secret-key";
```

Don't write:

```yaml
environment:
  ACCESS_TOKEN_SECRET: my-real-secret
```

if that Compose file is going into a public repository.

And definitely don't do:

```js
const mongoPassword = "Rahul123...";
```

in your source code.

Secrets should be supplied through an appropriate secret/configuration mechanism.

---

# 15. Environment variables aren't only for secrets

This is another important point.

Environment variables are useful for **configuration**, not just secrets.

Examples:

```text
PORT
NODE_ENV
MONGO_URI
FRONTEND_URL
LOG_LEVEL
CORS_ORIGIN
TOKEN_EXPIRY
EMAIL_HOST
EMAIL_PORT
```

Some aren't sensitive at all.

For example:

```env
PORT=5000
```

isn't a secret.

But it's still configuration.

---

# 16. Configuration vs secrets

It's useful to distinguish:

### Configuration

```text
PORT=5000
NODE_ENV=production
LOG_LEVEL=info
```

### Secret

```text
ACCESS_TOKEN_SECRET=...
DATABASE_PASSWORD=...
SMTP_PASSWORD=...
```

Both can be provided through environment variables.

But secrets often deserve stronger secret-management systems in production.

---

# 17. Don't access `process.env` everywhere

Your starter architecture already recommends centralizing environment variables through:

```text
config/env.js
```

The idea is:

```text
.env
 ↓
dotenv
 ↓
config/env.js
 ↓
application
```

Instead of:

```js
process.env.PORT
process.env.MONGO_URI
process.env.JWT_SECRET
process.env.FRONTEND_URL
```

being scattered throughout dozens of files.

Prefer something conceptually like:

```js
env.port
env.mongoUri
env.accessTokenSecret
env.frontendUrl
```

This gives you a single configuration layer.

---

# 18. Why centralization matters

Imagine 50 files contain:

```js
process.env.SOMETHING
```

Now you have configuration logic scattered everywhere.

Instead:

```text
config/env.js
      │
      ├── port
      ├── mongoUri
      ├── jwt secrets
      ├── frontend URL
      └── other configuration
             │
             ▼
       application
```

Now configuration has one clear entry point.

This makes the application easier to understand and test.

---

# 19. Environment validation

Here's where we can make this even better.

Suppose your application requires:

```text
MONGO_URI
ACCESS_TOKEN_SECRET
REFRESH_TOKEN_SECRET
```

What happens if one is missing?

Bad:

```text
Application starts
      ↓
Later request
      ↓
JWT operation
      ↓
crash/error
```

Better:

```text
Application starts
      ↓
Load environment
      ↓
Validate configuration
      ↓
Missing required variable?
      ↓
Fail immediately
```

This is called **fail-fast configuration**.

---

# 20. Example validation concept

You could have something conceptually like:

```js
if (!process.env.MONGO_URI) {
  throw new Error("MONGO_URI is required");
}
```

But as your project grows, you should use a structured configuration validation approach rather than dozens of manual checks.

For example:

```text
Environment
     ↓
Schema validation
     ↓
Valid?
 ┌───┴────┐
No       Yes
 ↓        ↓
Exit    Start
```

This is much safer.

---

# 21. Environment variable types

This is a common Node.js surprise.

Environment variables arrive as strings.

For example:

```env
PORT=5000
```

then:

```js
process.env.PORT
```

is conceptually:

```text
"5000"
```

not:

```text
5000
```

So configuration parsing matters.

For example:

```js
const port = Number(process.env.PORT);
```

Similarly:

```env
ENABLE_FEATURE=true
```

doesn't automatically become:

```js
true
```

It is essentially:

```text
"true"
```

You need to parse it.

---

# 22. Example

Don't blindly assume:

```js
if (process.env.ENABLE_FEATURE) {
  ...
}
```

Because:

```env
ENABLE_FEATURE=false
```

still produces a non-empty string:

```text
"false"
```

which is truthy in JavaScript.

This is a classic configuration bug.

You need proper parsing.

---

# 23. A better configuration object

Conceptually:

```js
const env = {
  nodeEnv: process.env.NODE_ENV || "development",

  port: Number(process.env.PORT || 5000),

  mongoUri: process.env.MONGO_URI,

  accessTokenSecret: process.env.ACCESS_TOKEN_SECRET,

  refreshTokenSecret: process.env.REFRESH_TOKEN_SECRET,

  frontendUrl: process.env.FRONTEND_URL
};
```

Then:

```js
env.port
env.mongoUri
env.accessTokenSecret
```

instead of repeatedly touching `process.env`.

---

# 24. Dockerfile `ENV` vs runtime environment

You may see:

```dockerfile
ENV NODE_ENV=production
```

This sets an environment variable in the image/container environment.

But be careful with secrets.

Don't build a production image containing:

```dockerfile
ENV ACCESS_TOKEN_SECRET=real-secret
```

because the secret becomes part of the image configuration/history.

A better pattern is to inject sensitive configuration at runtime.

Think:

```text
Docker image
=
application

Runtime environment
=
configuration
```

---

# 25. Build once, configure at runtime

This is a very useful production principle:

> **Build the application once; provide environment-specific configuration when it runs.**

Think:

```text
Source code
   ↓
Docker image
```

Same image:

```text
      ┌───────────────┐
      │ Docker image  │
      └───────┬───────┘
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
      dev    test   prod
```

Each environment provides different configuration.

This is much cleaner than building a different application image for every environment.

# 27. Docker Compose example

Let's build our current architecture.

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp

    volumes:
      - .:/app
      - /app/node_modules

    depends_on:
      - mongo

  mongo:
    image: mongo:8

    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
```

Now:

```text
Compose
  │
  ├── NODE_ENV
  ├── PORT
  └── MONGO_URI
       │
       ▼
Backend container
       │
       ▼
process.env
```

# 28. A cleaner `.env` approach

We can instead use:

```text
.env
```

with:

```env
NODE_ENV=development
PORT=5000
MONGO_URI=mongodb://mongo:27017/myapp
```

and:

```yaml
services:
  backend:
    env_file:
      - .env
```

Now Compose reads the environment configuration.

This is convenient for local development.

---

# 29. But `.env` has two different roles

This is worth understanding.

### Node's `.env`

You may use:

```text
dotenv
```

to load:

```text
.env
```

into:

```text
process.env
```

### Docker Compose `.env`

Compose itself can also use `.env` for variable interpolation and configuration.

These are related concepts but not exactly the same mechanism.

Don't assume:

```text
"Compose sees .env"
```

means:

```text
"Node automatically sees every variable"
```

The exact Compose configuration determines what is passed into the container.

---

# 30. Variable interpolation

Compose can also use variables in its YAML.

For example:

```yaml
services:
  backend:
    ports:
      - "${PORT}:5000"
```

with:

```env
PORT=5000
```

Compose resolves:

```text
${PORT}
   ↓
5000
```

giving:

```text
5000:5000
```

This is useful for configuration-driven Compose files.

---

# 31. Be careful with interpolation

Environment variables can become confusing when you have:

```text
Shell environment
+
.env
+
Compose interpolation
+
container environment
+
Node process.env
```

So always ask:

> **Where is this variable being read?**

For example:

```text
Compose
   ↓
${PORT}
```

is different from:

```text
Node
   ↓
process.env.PORT
```

Understanding this difference prevents many Docker configuration bugs.

# 34. What should go into `.env`?

Good candidates:

```text
PORT
NODE_ENV
MONGO_URI
FRONTEND_URL
JWT expiration
JWT secrets
email credentials
API keys
logging configuration
feature flags
```

But always ask:

> Is this configuration or application logic?

For example:

```text
PORT=5000
```

belongs in configuration.

But:

```js
if (user.role === "admin") {
   ...
}
```

is application logic.

Don't turn every value into an environment variable.

---

# 35. Don't overuse environment variables

This is another important lesson.

Don't do:

```env
CREATE_USER_MESSAGE=...
DELETE_USER_MESSAGE=...
MAX_TODO_TITLE_LENGTH=...
BUTTON_TEXT=...
```

just because environment variables exist.

Environment variables are best for:

```text
deployment-specific configuration
secrets
infrastructure configuration
runtime configuration
```

Business logic should generally remain in your application.

---

# 36. Secret management in production

For local development:

```text
.env
```

can be convenient.

For production, you may use a proper secret-management system provided by your hosting platform or infrastructure.

Conceptually:

```text
Secret Manager
      ↓
Production container
      ↓
process.env
```

instead of:

```text
Git repository
      ↓
production secret
```

Never put production secrets in Git.

---

# 37. What if a secret leaks?

Suppose:

```text
ACCESS_TOKEN_SECRET
```

gets committed to Git.

Don't just delete the line and assume you're safe.

The secret may exist in:

```text
Git history
logs
build artifacts
CI logs
Docker image layers
backups
```

The correct response is generally:

```text
1. Revoke/rotate the secret
2. Replace it
3. Investigate where it was exposed
4. Remove it from future usage
```

This is why secret handling matters.

---

# 38. `.env` and Docker images

Another important rule:

> **Don't bake environment-specific secrets into your Docker image.**

Bad idea:

```dockerfile
COPY .env /app/.env
```

especially for production secrets.

You want:

```text
Docker image
   ↓
generic application
```

then:

```text
runtime environment
   ↓
configuration
```

This keeps your image reusable.

# 42. Failure example

Suppose:

```env

```

Bad architecture:

```text

   ↓

   ↓

   ↓

```
