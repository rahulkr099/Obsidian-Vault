# Lesson 23.13 — Health Checks

The roadmap defines **23.13 as Health Checks**, followed by **23.14 Graceful Shutdown**.

You've already encountered health checks earlier in the roadmap, including the distinction between:

```text
/healthz
    ↓
Is Node alive?

/readyz
    ↓
Is Node + MongoDB + required services ready?
```

Now we're going to understand **why this matters in Docker and production**.

---

# 1. The problem

Suppose Docker says:

```text
backend container: Running
```

Does that guarantee your backend is actually usable?

**No.**

The process might be running while:

- MongoDB is unavailable
    
- the application hasn't finished starting
    
- a required dependency is down
    
- the application is stuck
    
- the HTTP server isn't responding
    

So:

```text
Container is running
```

is not the same as:

```text
Application is healthy
```

That's why we need health checks.

---

# 2. What is a health check?

A health check is a simple way of asking:

> **"Are you alive and working?"**

For an HTTP backend, we can create:

```http
GET /healthz
```

and return:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

The infrastructure can then periodically call:

```text
/healthz
```

and check the result.

---

# 3. The simplest architecture

```text
Docker
   │
   │ GET /healthz
   ▼
Backend
   │
   ▼
"Yes, I'm alive"
```

Response:

```text
HTTP 200
```

means:

```text
Healthy
```

A failure might produce:

```text
HTTP 500
```

or no response at all.

---

# 4. Why does Docker care?

Imagine:

```text
Backend container
       │
       ▼
Node process crashes
```

Docker might need to know:

```text
Is this container still useful?
```

A health check gives Docker an additional signal.

Conceptually:

```text
Container
   │
   ├── Running?
   │
   └── Healthy?
```

These are different states.

---

# 5. Running vs healthy

This distinction is extremely important.

### Running

```text
Node process exists
```

### Healthy

```text
Node process exists
+
application responds correctly
```

So:

```text
Running ≠ Healthy
```

---

# 6. `/healthz`

Let's start with the simplest endpoint.

```js
app.get("/healthz", (req, res) => {
  res.status(200).json({
    success: true,
    message: "Server is healthy"
  });
});
```

Now:

```text
GET /healthz
```

returns:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

This proves the HTTP application is responding.

---

# 7. What does `/healthz` actually test?

A simple health endpoint usually answers:

> **Is this application process alive enough to respond to requests?**

It doesn't necessarily prove:

```text
MongoDB works
Redis works
Email service works
Queue works
External API works
```

That's why we need to distinguish **health** from **readiness**.

---

# 8. Health vs readiness

This is one of today's most important concepts.

### Health

```text
"Am I alive?"
```

### Readiness

```text
"Am I ready to receive real traffic?"
```

So:

```text
/healthz
    ↓
Alive?

/readyz
    ↓
Ready?
```

Your roadmap explicitly uses this distinction.

---

# 9. Real-world analogy

Imagine a restaurant.

The restaurant building is open:

```text
Lights ON
Doors OPEN
```

That's like:

```text
/healthz
```

But the kitchen has no food:

```text
No ingredients
No chef
```

The restaurant isn't actually ready to serve customers.

That's:

```text
/readyz
```

So:

```text
Healthy
=
Restaurant exists

Ready
=
Restaurant can serve you
```

---

# 10. Why readiness matters

Imagine your backend starts:

```text
Node starts
   ↓
Express starts
   ↓
MongoDB still connecting
```

If your load balancer immediately sends requests:

```text
Client
  ↓
Backend
  ↓
MongoDB unavailable
  ↓
500 error
```

That's bad.

Instead:

```text
Backend starts
   ↓
MongoDB connects
   ↓
Readiness = true
   ↓
Traffic allowed
```

Much better.

---

# 11. Simple readiness endpoint

Conceptually:

```js
app.get("/readyz", (req, res) => {
  res.status(200).json({
    success: true,
    message: "Server is ready"
  });
});
```

But there's a problem.

This doesn't actually check anything.

It always says:

```text
"I'm ready!"
```

even if MongoDB is completely broken.

So we need to make readiness meaningful.

---

# 12. Readiness should check dependencies

Our backend architecture is:

```text
Backend
   │
   └── MongoDB
```

Therefore readiness might check:

```text
Node
 +
MongoDB
```

Conceptually:

```text
GET /readyz
      │
      ▼
Is application running?
      │
      ▼
Is MongoDB connected?
      │
   ┌──┴──┐
  Yes    No
   │      │
   ▼      ▼
  200    503
```

---

# 13. Why `503`?

HTTP `503 Service Unavailable` is useful when the application is temporarily unable to serve requests properly.

For example:

```text
MongoDB unavailable
       ↓
Backend not ready
       ↓
HTTP 503
```

This tells infrastructure:

> Don't send normal traffic here yet.

---

# 14. Example readiness response

Ready:

```json
{
  "success": true,
  "message": "Server is ready"
}
```

with:

```text
HTTP 200
```

Not ready:

```json
{
  "success": false,
  "message": "Server is not ready"
}
```

with:

```text
HTTP 503
```

Keep the public response simple.

Don't expose sensitive internal details.

---

# 15. Checking MongoDB state

With Mongoose, you can inspect the connection state.

Conceptually:

```js
mongoose.connection.readyState
```

The exact values represent connection states.

A common readiness check is based on whether the connection is in the connected state.

Conceptually:

```js
const isDatabaseReady =
  mongoose.connection.readyState === 1;
```

Then:

```js
if (!isDatabaseReady) {
  return res.status(503).json({
    success: false,
    message: "Server is not ready"
  });
}
```

---

# 16. A better architecture

Don't put database logic directly inside every route.

Instead:

```text
routes
  ↓
health controller
  ↓
health service / dependency check
  ↓
MongoDB state
```

For a very small application, a simple health route can be enough.

As your system grows:

```text
Health
 ├── application
 ├── database
 ├── redis
 ├── queue
 └── other critical dependencies
```

This becomes an actual observability component.

---

# 17. Health check response should be fast

This is important.

Your health endpoint may be called frequently:

```text
every few seconds
```

So don't make it perform expensive work.

Avoid:

```text
/healthz
 ↓
complex database queries
 ↓
multiple external APIs
 ↓
heavy computation
```

Keep it lightweight.

---

# 18. Don't query your entire database

Bad:

```text
GET /healthz
   ↓
SELECT everything
```

or:

```text
MongoDB
 ↓
find()
 ↓
10,000 documents
```

That's unnecessary.

Health checks should be:

```text
fast
small
predictable
cheap
```

---

# 19. Liveness vs readiness

In larger infrastructure you'll often hear:

```text
Liveness
Readiness
```

These map nicely to our concepts.

### Liveness

> Is the process alive?

```text
/healthz
```

### Readiness

> Can the process handle real traffic?

```text
/readyz
```

Mental model:

```text
              Application
                   │
          ┌────────┴────────┐
          ▼                 ▼
       Liveness          Readiness
          │                 │
       "Alive?"          "Ready?"
```

---

# 20. Why not make `/healthz` check MongoDB?

You might ask:

> Why not just make `/healthz` check everything?

Because liveness and readiness answer different questions.

Imagine MongoDB temporarily goes down.

The Node process itself is still healthy:

```text
Node ✓
MongoDB ✗
```

You might want:

```text
/healthz → 200
/readyz  → 503
```

This tells infrastructure:

```text
The application process is alive,
but don't send normal traffic yet.
```

That's much more useful.

---

# 21. Docker Compose healthcheck

Docker Compose can define a health check.

Conceptually:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    healthcheck:
      test:
        [
          "CMD",
          "curl",
          "-f",
          "http://localhost:5000/healthz"
        ]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 10s
```

The idea is:

```text
Docker
  ↓
GET /healthz
  ↓
HTTP 200?
  ↓
Healthy
```

---

# 22. What are these settings?

### `interval`

How frequently Docker performs the check.

Example:

```yaml
interval: 10s
```

means approximately:

```text
every 10 seconds
```

---

### `timeout`

How long Docker waits for the check.

```yaml
timeout: 5s
```

means:

```text
If it doesn't respond within 5 seconds,
consider that check failed.
```

---

### `retries`

How many consecutive failures are tolerated before Docker marks the container unhealthy.

```yaml
retries: 3
```

---

### `start_period`

Gives the application some startup time.

```yaml
start_period: 10s
```

This is useful because the application may need time to:

```text
start Node
load configuration
connect to MongoDB
initialize resources
```

---

# 23. Health status

Docker can then show something conceptually like:

```text
backend
Up 30 seconds (healthy)
```

instead of simply:

```text
backend
Up 30 seconds
```

That extra information is valuable.

---

# 24. Healthcheck command choices

The exact healthcheck command depends on what's installed inside your image.

For example, you might use:

```text
curl
```

or:

```text
wget
```

or a Node-based command.

Don't blindly assume every minimal Docker image includes `curl`.

This is one reason you need to understand your base image.

---

# 25. Node-based healthcheck

If your image doesn't have `curl`, you can potentially use Node itself.

Conceptually:

```yaml
healthcheck:
  test:
    [
      "CMD",
      "node",
      "-e",
      "fetch('http://localhost:5000/healthz').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"
    ]
```

The important concept isn't memorizing this exact command.

It's:

```text
Docker
 ↓
execute healthcheck
 ↓
HTTP request
 ↓
health endpoint
 ↓
exit code
```

---

# 26. Exit codes

Docker health checks ultimately care about success/failure.

Conceptually:

```text
exit 0
   ↓
success

exit non-zero
   ↓
failure
```

So:

```text
HTTP 200
   ↓
exit 0
   ↓
healthy
```

and:

```text
HTTP 500
   ↓
exit 1
   ↓
unhealthy
```

---

# 27. MongoDB health check

We can also give MongoDB its own health check.

Conceptually:

```yaml
mongo:
  image: mongo:8

  healthcheck:
    test:
      [
        "CMD",
        "mongosh",
        "--eval",
        "db.adminCommand('ping')"
      ]
    interval: 10s
    timeout: 5s
    retries: 5
```

The exact command depends on the MongoDB image/version you're using.

The idea is:

```text
Docker
   ↓
MongoDB ping
   ↓
MongoDB responds?
   ↓
healthy
```

---

# 28. Now we have two health signals

```text
Backend
   │
   └── /healthz
          ↓
       healthy?

MongoDB
   │
   └── database ping
          ↓
       healthy?
```

Then readiness can consider the dependency:

```text
Backend
   │
   ├── Node alive
   │
   └── MongoDB ready
```

---

# 29. `depends_on` is not the same as health

This is a very important Docker Compose concept.

You might have:

```yaml
depends_on:
  - mongo
```

A beginner may think:

> "That means MongoDB is ready before backend starts."

Not necessarily.

It primarily expresses a **startup dependency/order**, not that MongoDB is fully ready to accept application connections.

That's why health checks become important.

---

# 30. Combining `depends_on` with health

Compose can be configured to wait for a service to become healthy before starting a dependent service.

Conceptually:

```yaml
backend:
  depends_on:
    mongo:
      condition: service_healthy
```

while MongoDB has:

```yaml
mongo:
  healthcheck:
    ...
```

Then:

```text
MongoDB container starts
        ↓
Health check
        ↓
MongoDB healthy
        ↓
Backend starts
```

This is much better than simply assuming:

```text
container started = database ready
```

---

# 31. Important limitation

Even with:

```text
depends_on
+
healthcheck
```

your application should still handle connection failures gracefully.

Why?

Because production systems change.

A database can become unavailable **after** startup.

For example:

```text
10:00
MongoDB healthy

10:05
MongoDB crashes

10:06
Backend still running
```

Your application needs proper error handling and recovery behavior.

Health checks don't magically solve dependency failures.

---

# 32. Startup sequence

A good architecture looks like:

```text
Docker starts MongoDB
          ↓
MongoDB health check
          ↓
MongoDB healthy
          ↓
Backend starts
          ↓
Backend connects to MongoDB
          ↓
Backend /healthz → 200
          ↓
Backend /readyz → 200
```

This gives us a clear startup lifecycle.

Suppose:

```text
MongoDB
   ↓
still starting
```

Then:

```text
MongoDB health
   ↓
unhealthy
```

Backend readiness:

```text
/readyz
   ↓
503
```

Infrastructure understands:

```text
Don't send traffic yet.
```

# 34. What if MongoDB goes down later?

Suppose:

```text
Backend
   ↓
MongoDB
```

and MongoDB suddenly fails.

Then:

```text
MongoDB
   ↓
unhealthy
```

The backend may respond:

```text
/readyz → 503
```

depending on your readiness implementation.

This allows infrastructure to remove the instance from normal traffic while the application recovers.

# 35. Health checks and load balancers

Imagine two backend containers:

```text
Load Balancer
      │
 ┌────┴────┐
 ▼         ▼
Backend A Backend B
```

Suppose:

```text
Backend A → healthy
Backend B → unhealthy
```

A properly configured load balancer/orchestrator can avoid sending traffic to Backend B.

Conceptually:

```text
              Load Balancer
                 │
          ┌──────┴──────┐
          ▼             ▼
      Backend A      Backend B
       HEALTHY       UNHEALTHY
          │
          ▼
        traffic
```

That's one of the major production benefits.


# 37. Startup probe concept

Some applications take a long time to start.

For example:

```text
Application
 ↓
load large model
 ↓
initialize cache
 ↓
connect to services
 ↓
ready
```

During startup, you don't necessarily want the system to interpret temporary startup failures as a permanently unhealthy process.

That's why larger orchestration systems can distinguish:

```text
startup
liveness
readiness
```

For our current Docker setup, understanding the concept is enough.

---

# 38. What should `/healthz` return?

Keep it boring.

Something like:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

That's good.

Don't return:

```json
{
  "success": true,
  "jwtSecret": "...",
  "databasePassword": "...",
  "internalIp": "...",
  "environmentVariables": "..."
}
```

Obviously never expose secrets.

---

# 39. Don't expose too much infrastructure information

A health endpoint may be accessible without authentication.

Therefore avoid exposing sensitive information such as:

```text
database URI
API keys
secret values
internal credentials
stack traces
```

A public health endpoint should provide enough information for its purpose, not become a debugging dump.

---

# 40. Health endpoint and authentication

Usually:

```text
GET /healthz
```

should not require user authentication.

Why?

Infrastructure needs to check it before normal application authentication is relevant.

Imagine:

```text
Load balancer
    ↓
health check
    ↓
JWT authentication middleware
```

That could create unnecessary problems.

Instead, health endpoints are generally placed outside protected API routes.

---

# 41. Route ordering

Conceptually:

```js
app.get("/healthz", healthController);
app.get("/readyz", readinessController);

app.use("/api/v1", apiRoutes);
```

Then:

```text
/healthz
/readyz
```

remain simple infrastructure endpoints.

While:

```text
/api/v1/*
```

contains your actual application API.

---

# 42. Health checks are not monitoring

Another important distinction.

Health check:

```text
"Are you okay?"
```

Monitoring:

```text
"What has been happening over time?"
```

Logging:

```text
"What happened?"
```

Metrics:

```text
"How much/how often?"
```

So:

```text
Health checks
Logging
Metrics
Tracing
```

are related but different observability tools.

Your roadmap later covers broader observability concepts.

---

# 43. Health checks and logging

Don't log every health request at high severity.

Imagine:

```text
GET /healthz
GET /healthz
GET /healthz
GET /healthz
...
```

If Docker checks every 10 seconds, you'll generate a lot of repetitive logs.

Health endpoints can be handled specially by your logger.

For example:

```text
GET /healthz
```

might use lower-noise logging.

This prevents health checks from drowning out useful application logs.

---

# 44. Health checks and graceful shutdown

Today's lesson connects directly to the next one.

Imagine:

```text
Backend receives SIGTERM
```

During graceful shutdown:

```text
Stop accepting traffic
        ↓
Readiness becomes false
        ↓
Finish existing requests
        ↓
Close MongoDB
        ↓
Exit
```

That's why:

```text
23.13 Health Checks
        ↓
23.14 Graceful Shutdown
```

is a logical sequence.

The roadmap intentionally puts them next to each other.

# 46. Complete Compose example

Putting today's concepts together:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp

    depends_on:
      mongo:
        condition: service_healthy

    healthcheck:
      test:
        [
          "CMD",
          "node",
          "-e",
          "fetch('http://localhost:5000/healthz').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"

      timeout: 5s
      retries: 3
      start_period: 10s

  mongo:
    image: mongo:8

      - mongo-data:/data/db

      test:
        [
          "CMD",
          "mongosh",
          "--eval",
          "db.adminCommand('ping')"
        ]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  mongo-data:
```

The exact commands may need adjustment depending on the image and tools installed, but the **architecture** is the important part.

# 49. Common mistakes

### ❌ Mistake 1 — Thinking `docker ps` means healthy

```text
Up
```

only tells you the container is running.

---

### ❌ Mistake 2 — Making `/healthz` perform expensive work

Health checks should be lightweight.

---

### ❌ Mistake 3 — Making `/healthz` depend on every service

If an optional email service is temporarily unavailable, you may not want your entire backend marked unhealthy.

Only check dependencies that are truly critical to the endpoint's purpose.

---

### ❌ Mistake 4 — Exposing secrets

Never return:

```text
MONGO_URI
JWT_SECRET
API_KEY
```

from a health endpoint.

---

### ❌ Mistake 5 — Assuming `depends_on` guarantees readiness

Startup ordering isn't the same thing as dependency readiness.

---

### ❌ Mistake 6 — Protecting health endpoints with normal user authentication

Infrastructure needs to be able to check them independently.

---

### ❌ Mistake 7 — Logging health requests excessively

High-frequency health probes can create noisy logs.
