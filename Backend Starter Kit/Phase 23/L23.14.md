# Lesson 23.14 — Graceful Shutdown

This lesson follows **23.13 Health Checks** in your Phase 23 roadmap. The important connection is:

```text
Health Checks
     ↓
know whether the service is ready
     ↓
Graceful Shutdown
     ↓
stop the service safely
```

The goal is simple:

> **When the server is asked to stop, don't kill it immediately. Give it time to finish what it's doing and close its resources properly.**

---

# 1. The problem with normal shutdown

Imagine your backend is running:

```text
Client
  ↓
Backend
  ↓
MongoDB
```

Now Docker sends:

```text
SIGTERM
```

If your application immediately exits:

```text
Backend
   ↓
💥 EXIT
```

an active request could be interrupted.

For example:

```text
Client
  ↓
POST /api/orders
  ↓
Backend
  ↓
Database operation
```

If the container suddenly disappears:

```text
Backend
  ↓
❌ Process killed
```

the request may fail.

---

# 2. What graceful shutdown means

Instead of:

```text
SIGTERM
  ↓
EXIT IMMEDIATELY
```

we want:

```text
SIGTERM
  ↓
Stop accepting new traffic
  ↓
Finish existing requests
  ↓
Close database connections
  ↓
Close other resources
  ↓
Exit
```

That's graceful shutdown.

---

# 3. Real-world analogy

Imagine a restaurant closing.

Bad approach:

```text
10:00 PM
   ↓
"WE ARE CLOSED!"
   ↓
Turn off everything
   ↓
Customers still eating
```

Better:

```text
10:00 PM
   ↓
Stop accepting new customers
   ↓
Existing customers finish eating
   ↓
Clean kitchen
   ↓
Close restaurant
```

That's exactly what we want our backend to do.

---

# 4. Why Docker sends SIGTERM

When Docker needs to stop a container, it normally gives the application an opportunity to shut down cleanly.

Conceptually:

```text
docker stop
     ↓
SIGTERM
     ↓
Application handles signal
     ↓
Graceful shutdown
```

If the process doesn't terminate within the configured grace period, Docker can eventually forcefully stop it.

So your application should respond to `SIGTERM`.

---

# 5. The two important signals

For Node.js applications, you'll commonly encounter:

```text
SIGTERM
SIGINT
```

### SIGTERM

Usually associated with:

```text
Docker
production process managers
orchestration systems
```

It basically means:

> Please terminate gracefully.

### SIGINT

Commonly occurs when you press:

```text
Ctrl + C
```

during local development.

So we often handle both:

```js
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);
```

---

# 6. The shutdown sequence

A good backend shutdown sequence looks like:

```text
SIGTERM
   ↓
Mark application as not ready
   ↓
Stop accepting new traffic
   ↓
Wait for existing requests
   ↓
Close HTTP server
   ↓
Close MongoDB connection
   ↓
Close Redis / queues / other resources
   ↓
Exit process
```

This connects directly to the readiness lesson.

---

# 7. Why readiness should change first

Suppose your backend is shutting down:

```text
Backend
   ↓
SIGTERM
```

If `/readyz` still says:

```text
200 OK
```

a load balancer might continue sending traffic.

That's bad.

Instead:

```text
SIGTERM
   ↓
ready = false
   ↓
/readyz → 503
```

Now infrastructure knows:

> Don't send new traffic here.

We can now combine Lessons 23.13 and 23.14:

```text
Application starts
       ↓
MongoDB connects
       ↓
/healthz → 200
       ↓
/readyz → 200
       ↓
Receive traffic
       ↓
SIGTERM
       ↓
/readyz → 503
       ↓

       ↓

       ↓

       ↓

```

This is a production-friendly lifecycle.

# 9. Node's HTTP server

When you start Express, you might have:

```js
app.listen(PORT);
```

For graceful shutdown, it's better to keep a reference to the HTTP server.

For example:

```js
const server = app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});
```

Now:

```text
server
```

represents the HTTP server.

You can later call:

```js
server.close();
```

to stop accepting new connections while allowing existing connections to finish.

---

# 10. Basic shutdown handler

A simple version:

```js
const shutdown = async () => {
  server.close(async () => {
    await mongoose.connection.close();

    process.exit(0);
  });
};
```

Then:

```js
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);
```

Conceptually:

```text
SIGTERM
   ↓
server.close()
   ↓
MongoDB close
   ↓
process.exit(0)
```

This is the basic pattern.

---

# 11. Don't call `process.exit()` immediately

Avoid:

```js
process.on("SIGTERM", () => {
  process.exit(0);
});
```

because you're skipping cleanup.

You could leave behind:

```text
active requests
database connections
open sockets
queue connections
timers
other resources
```

Instead:

```text
SIGTERM
 ↓
cleanup
 ↓
exit
```

---

# 12. Closing the HTTP server

When you call:

```js
server.close();
```

the server stops accepting new connections.

Existing connections can be allowed to finish.

Conceptually:

```text
Before shutdown:

New request ───────► Backend
Existing request ──► Backend
```

After shutdown starts:

```text
New request ───────► ❌

Existing request ──► Backend → finish
```

That's exactly what we want.

---

# 13. Why closing MongoDB matters

Your application has an active connection:

```text
Node
 ↓
MongoDB
```

When shutting down:

```text
Node
 ↓
close MongoDB connection
```

This releases the database resources cleanly.

With Mongoose, conceptually:

```js
await mongoose.connection.close();
```

---

# 14. Other resources

MongoDB isn't the only thing your application might need to close.

A production backend might have:

```text
HTTP server
MongoDB
Redis
message queue
background workers
WebSocket connections
file handles
external clients
```

So graceful shutdown is really:

```text
Shutdown
   ↓
Close all important resources
```

---

# 15. Centralize shutdown logic

Don't write separate cleanup logic like:

```js
process.on("SIGTERM", ...);
process.on("SIGINT", ...);
```

with completely different behavior.

Instead:

```js
const shutdown = async (signal) => {
  console.log(`${signal} received`);

  // cleanup
};
```

Then:

```js
process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));
```

Now both signals use the same shutdown process.

---

# 16. Prevent duplicate shutdown

A process can potentially receive multiple signals.

You don't want:

```text
SIGTERM
   ↓
shutdown()
   
SIGINT
   ↓
shutdown() again
```

So you can protect the shutdown function:

```js
let isShuttingDown = false;

const shutdown = async (signal) => {
  if (isShuttingDown) return;

  isShuttingDown = true;

  console.log(`${signal} received`);
  
  // cleanup
};
```

Now shutdown runs once.

---

# 17. Why this matters

Without protection:

```text
shutdown()
 ├── close HTTP
 ├── close MongoDB
 └── exit

shutdown()
 ├── close HTTP again
 ├── close MongoDB again
 └── exit
```

This can create race conditions and confusing errors.

A simple flag makes the shutdown flow predictable.

---

# 18. Shutdown timeout

What if an active request never finishes?

For example:

```text
Request
   ↓
stuck forever
```

If you wait forever:

```text
shutdown
   ↓
waiting...
   ↓
waiting...
   ↓
waiting...
```

your container may never exit.

So graceful shutdown normally needs a maximum shutdown time.

Conceptually:

```text
SIGTERM
   ↓
Graceful shutdown
   ↓
wait
   ↓
timeout reached?
 ┌─┴─┐
No  Yes
│    │
wait force exit
```

---

# 19. Example shutdown timeout

Conceptually:

```js
const shutdownTimeout = setTimeout(() => {
  process.exit(1);
}, 10_000);
```

This gives the application:

```text
10 seconds
```

to finish cleanup.

After that:

```text
force exit
```

The exact timeout should depend on your application and deployment environment.

---

# 20. Clear the timeout

If shutdown completes successfully:

```js
clearTimeout(shutdownTimeout);
```

Otherwise, the timeout could fire after you've already finished shutting down.

So the flow is:

```text
Start timeout
      ↓
Cleanup
      ↓
Cleanup successful
      ↓
clearTimeout()
      ↓
exit 0
```

---

# 21. Graceful shutdown with readiness

Let's make the lifecycle more realistic.

We maintain:

```js
let isReady = true;
```

Then readiness:

```js
app.get("/readyz", (req, res) => {
  if (!isReady) {
    return res.status(503).json({
      success: false,
      message: "Server is shutting down"
    });
  }

  res.status(200).json({
    success: true,
    message: "Server is ready"
  });
});
```

During shutdown:

```js
isReady = false;
```

Now:

```text
Normal
/readyz → 200

Shutdown
/readyz → 503
```

---

# 22. Why wait after marking not-ready?

This is a subtle but important production idea.

Suppose:

```text
Load balancer
      ↓
Backend
```

You receive:

```text
SIGTERM
```

Immediately:

```text
isReady = false
```

The load balancer needs some time to notice:

```text
Backend is no longer ready.
```

During that period, existing requests can finish.

So conceptually:

```text
SIGTERM
   ↓
ready = false
   ↓
traffic drains
   ↓
existing requests finish
   ↓
server closes
```

This is called **connection/request draining**.

---

# 23. Don't immediately close everything

A common beginner implementation is:

```text
SIGTERM
 ↓
ready = false
 ↓
server.close()
 ↓
MongoDB.close()
 ↓
exit
```

This can work for simple applications, but in production you may need a small drain period depending on how traffic is routed.

The exact sequence should be designed around your deployment system.

---

# 24. HTTP keep-alive connections

Modern HTTP clients may keep connections alive.

For example:

```text
Client
   │
   │ connection
   ▼
Backend
   │
   │ request 1
   │ request 2
   │ request 3
```

During shutdown, you need to consider existing connections.

Node's HTTP server has mechanisms for managing these connections, but your application and deployment environment should be tested to ensure requests aren't cut off unexpectedly.

For most starter projects, `server.close()` is the correct foundation.

---

# 25. MongoDB shutdown

Suppose:

```text
server.close()
```

finishes.

Then:

```text
mongoose.connection.close()
```

can close the database connection.

So:

```text
HTTP server
   ↓
closed
   ↓
MongoDB
   ↓
closed
   ↓
process
   ↓
exit
```

The order matters.

You generally don't want to close MongoDB while active HTTP requests are still trying to use it.

---

# 26. A more complete implementation

Conceptually:

```js
let isShuttingDown = false;

const shutdown = async (signal) => {
  if (isShuttingDown) return;

  isShuttingDown = true;
  isReady = false;

  console.log(`${signal} received. Starting graceful shutdown.`);

  const forceExitTimer = setTimeout(() => {
    console.error("Graceful shutdown timed out.");
    process.exit(1);
  }, 10_000);

  try {
    await new Promise((resolve) => {
      server.close(resolve);
    });

    await mongoose.connection.close();

    clearTimeout(forceExitTimer);

    process.exit(0);
  } catch (error) {
    clearTimeout(forceExitTimer);

    console.error("Shutdown failed:", error);

    process.exit(1);
  }
};
```

Then:

```js
process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));
```

This is a much more production-oriented pattern.

---

# 27. One improvement: don't overuse `process.exit`

A good Node.js application can sometimes simply finish naturally after cleanup.

For example:

```js
await serverClose();
await databaseClose();
```

and then allow the event loop to empty.

But explicit exit codes can be useful when shutdown succeeds or fails.

The important lesson is:

> Don't call `process.exit()` before cleanup.

---

# 28. Exit codes

Generally:

```text
0
```

means:

```text
successful termination
```

while:

```text
non-zero
```

indicates an error.

So:

```js
process.exit(0);
```

means:

```text
shutdown succeeded
```

while:

```js
process.exit(1);
```

means:

```text
shutdown failed / forced termination
```

---

# 29. What if MongoDB is already disconnected?

Your shutdown code should be reasonably defensive.

For example:

```text
SIGTERM
   ↓
server closes
   ↓
MongoDB already disconnected
```

Your shutdown logic shouldn't become another source of crashes.

This is why centralized cleanup functions and careful error handling matter.

---

# 30. Cleanup order

A good general order is:

```text
1. Stop advertising readiness
2. Stop accepting new traffic
3. Let active requests finish
4. Stop background work
5. Close database connections
6. Close queues/cache connections
7. Clear timers/resources
8. Exit
```

Not every application needs every step.

But this is a useful mental model.

---

# 31. Background workers

Suppose your backend has:

```text
API server
+
email worker
+
scheduled jobs
```

During shutdown:

```text
SIGTERM
   ↓
Stop accepting API traffic
   ↓
Stop starting new jobs
   ↓
Finish current job
   ↓
Close connections
   ↓
Exit
```

Otherwise you can end up with:

```text
job started
   ↓
process killed
   ↓
job incomplete
```

This becomes especially important in your later queue/background-job architecture.

---

# 32. Graceful shutdown and transactions

Suppose an API request is doing:

```text
Start transaction
   ↓
Update order
   ↓
Update payment
   ↓
Commit
```

If the process disappears halfway through:

```text
Start transaction
   ↓
Update order
   ↓
💥 process killed
```

the database transaction behavior matters.

Proper database transaction handling and graceful shutdown work together to reduce operational problems.

Graceful shutdown doesn't replace transaction safety.

---

# 33. Graceful shutdown isn't only for Docker

Even outside Docker, you can receive:

```text
SIGTERM
SIGINT
```

Examples:

```text
Linux process manager
systemd
PM2
Kubernetes
cloud platforms
container orchestration
```

So implementing graceful shutdown in your Node application is a reusable production skill.

# 34. Docker lifecycle

The important Docker flow is:

```text
docker stop backend
       ↓
SIGTERM
       ↓
Node shutdown handler
       ↓
cleanup
       ↓
process exits
```

If your application doesn't respond properly, Docker eventually has to force termination.

That's exactly what we want to avoid during normal shutdown.

---

# 35. Why force termination is dangerous

Imagine:

```text
SIGTERM
   ↓
wait 10 seconds
   ↓
still running
   ↓
SIGKILL
```

`SIGKILL` cannot be handled by your application.

You don't get:

```text
cleanup
```

So:

```text
SIGTERM
=
"Please shut down cleanly."

SIGKILL
=
"Stop now."
```

Your goal is to finish during the graceful period.

# 36. Health + shutdown together

Now combine the last two lessons:

```text
                Backend
                   │
          ┌────────┴────────┐
          ▼                 ▼
       /healthz          /readyz
          │                 │
       "Alive?"          "Ready?"
                            │
                            ▼
                       MongoDB ready
```

During normal operation:

```text
health = true
ready = true
```

During shutdown:

```text
health = true
ready = false
```

Then eventually:

```text
process exits
```

This distinction is extremely powerful.

---

# 37. Why health may remain true during shutdown

This can feel strange.

You might think:

> If we're shutting down, shouldn't `/healthz` become false?

Not necessarily.

The process is still alive:

```text
Node ✓
```

It's simply no longer willing to receive new traffic:

```text
Ready ✗
```

Therefore:

```text
/healthz → 200
/readyz  → 503
```

can be perfectly valid during graceful shutdown.

# 39. Logging shutdown

Good shutdown logs are useful:

```text
SIGTERM received
Graceful shutdown started
HTTP server closed
MongoDB connection closed
Graceful shutdown completed
```

If something fails:

```text
SIGTERM received

MongoDB close failed
Graceful shutdown failed
```

These logs help diagnose deployment problems.

---

# 40. Don't log secrets during shutdown

Avoid:

```text
Mongo URI: mongodb://user:password@...
```

or:

```text
JWT secret: ...
```

Your shutdown logs should contain:

```text
events
states
durations
errors
```

not sensitive configuration values.

---

# 41. Measuring shutdown duration

A useful production improvement is measuring:

```text
shutdown started
       ↓
shutdown completed
```

For example:

```text
Shutdown completed in 420ms
```

This helps you identify slow cleanup.

If it consistently takes:

```text
8 seconds
```

you may have a resource that isn't closing efficiently.

---

# 42. Common mistake — only handling SIGINT

You might write:

```js
process.on("SIGINT", shutdown);
```

This works nicely with:

```text
Ctrl + C
```

but production environments commonly use:

```text
SIGTERM
```

So handle both:

```js
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);
```

---

# 43. Common mistake — closing MongoDB first

Bad sequence:

```text
SIGTERM
 ↓
MongoDB.close()
 ↓
server still accepting requests
 ↓
request tries MongoDB
 ↓
failure
```

Better:

```text
SIGTERM
 ↓
not ready
 ↓
stop new traffic
 ↓
close HTTP server
 ↓
close MongoDB
```

This is why ordering matters.

---

# 44. Common mistake — no timeout

Bad:

```text
await server.close();
await mongo.close();
```

with no fallback.

If something hangs:

```text
shutdown
 ↓
forever waiting
```

Use a bounded shutdown period.

---

# 45. Common mistake — shutdown function runs twice

Protect it:

```js
let isShuttingDown = false;
```

Then:

```js
if (isShuttingDown) return;
isShuttingDown = true;
```

Simple and useful.

---

# 46. Common mistake — treating shutdown as an error

A normal:

```text
SIGTERM
```

is not necessarily an application failure.

Your logs should distinguish:

```text
normal shutdown
```

from:

```text
unexpected crash
```

This matters for monitoring and alerting.

---

# 47. Crash vs graceful shutdown

### Graceful shutdown

```text
SIGTERM
 ↓
cleanup
 ↓
exit 0
```

Expected lifecycle event.

### Crash

```text
Unhandled exception
 ↓
process terminates
```

Potential application problem.

### Force kill

```text
SIGKILL
 ↓
immediate termination
```

Cleanup isn't possible.

These should not all be treated the same way.
