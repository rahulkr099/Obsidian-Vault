---

# 1. Development container vs production container

This distinction is extremely important.

A development container is designed for:

```text
Fast development
 ↓
Edit code
 ↓
Detect changes
 ↓
Restart
 ↓
Debug
```

A production container is designed for:

```text
Reliability
 ↓
Small image
 ↓
Predictable startup
 ↓
Security
 ↓
No unnecessary tools
 ↓
Efficient runtime
```

So:

```text
Dockerfile.dev
       ≠
Dockerfile
```

They have different jobs.

---

# 2. Development container

You might have:

```text
Dockerfile.dev
```

with:

```text
Node
+
npm
+
nodemon
+
source code
+
development dependencies
```

The workflow is:

```text
Your code
   ↓
Volume mount
   ↓
Container
   ↓
nodemon
   ↓
restart
```

That's useful during development.

---

# 3. Production container

Production should look more like:

```text
Source code
   ↓
Build image
   ↓
Install required dependencies
   ↓
Copy application
   ↓
Start Node
```

No:

```text
nodemon
tests
editor
Git
unnecessary development tools
```

unless they are genuinely required.

---

# 4. Why production images should be smaller

Imagine two images:

```text
Image A
1.2 GB
```

and:

```text
Image B
250 MB
```

The smaller image generally means:

```text
faster download
faster deployment
less storage
smaller attack surface
```

This is why production Dockerfiles should avoid unnecessary files and dependencies.

---

# 5. `npm install` vs production dependencies

Your `package.json` may contain:

```json
{
  "dependencies": {
    "express": "...",
    "mongoose": "..."
  },
  "devDependencies": {
    "jest": "...",
    "nodemon": "..."
  }
}
```

Production doesn't normally need:

```text
jest
nodemon
test tooling
development-only packages
```

So production dependency installation should exclude unnecessary development dependencies.

A common approach is:

```bash
npm ci --omit=dev
```

The important concept:

```text
Production container
        ↓
Production dependencies
        ↓
Only what runtime needs
```

---

# 6. Why `npm ci`?

For production builds, `npm ci` is usually preferable when you have a committed lockfile.

You have:

```text
package.json
package-lock.json
```

The lockfile gives you a reproducible dependency tree.

Conceptually:

```text
package.json
       +
package-lock.json
       ↓
npm ci
       ↓
same dependency versions
```

This is much better than allowing dependency resolution to change unexpectedly during each image build.

---

# 7. Why not copy everything?

A beginner might write:

```dockerfile
COPY . .
```

and move on.

But your project may contain:

```text
.git/
node_modules/
.env
coverage/
tests/
README drafts
local files
```

You don't necessarily want all of that inside your production image.

That's why `.dockerignore` matters.

---

# 8. `.dockerignore`

A production project should generally have a `.dockerignore`.

For example:

```text
node_modules
npm-debug.log
.git
.gitignore
.env
coverage
tests
Dockerfile.dev
docker-compose.yml
```

The exact list depends on your project.

The idea is:

```text
Build context
      ↓
.dockerignore
      ↓
Only useful files
      ↓
Docker build
```

---

# 9. Why exclude `.env`?

This is extremely important.

Never solve configuration by doing:

```dockerfile
COPY .env .
```

for a production image.

Your `.env` may contain:

```text
MONGO_URI
JWT secrets
API keys
SMTP credentials
```

Secrets should be supplied through your deployment environment/secrets mechanism, not baked into the image.

So:

```text
Image
   ↓
Application code
```

and:

```text
Runtime environment
   ↓
Secrets/configuration
```

remain separate.

---

# 10. Image vs container

Remember this distinction:

### Image

```text
Blueprint
```

### Container

```text
Running instance of that blueprint
```

For example:

```text
Dockerfile
   ↓
Docker image
   ↓
Container
```

You can have:

```text
Image
  ↓
Container A
Container B
Container C
```

all running from the same image.

---

# 11. Production image should be immutable

A useful production mindset is:

> **Build the image once, then run that exact image.**

Don't SSH into a container and manually modify application files.

Avoid:

```text
Container
   ↓
edit source
   ↓
install package
   ↓
restart
```

Instead:

```text
Source
   ↓
Git
   ↓
Docker build
   ↓
New image
   ↓
New container
```

This makes deployments predictable.

---

# 12. Production Dockerfile

For a Node backend without a separate compile/build step, a simple production Dockerfile can look conceptually like:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY . .

ENV NODE_ENV=production

EXPOSE 5000

CMD ["node", "server.js"]
```

Don't memorize this blindly.

Understand the sequence.

---

# 13. Line-by-line

### Base image

```dockerfile
FROM node:22-alpine
```

You need a Node runtime.

`alpine` is a lightweight Linux-based option.

---

### Working directory

```dockerfile
WORKDIR /app
```

Now commands operate inside:

```text
/app
```

---

### Copy package files first

```dockerfile
COPY package*.json ./
```

Why before the source code?

**Docker layer caching.**

We'll come back to this.

---

### Install dependencies

```dockerfile
RUN npm ci --omit=dev
```

Install production dependencies according to the lockfile.

---

### Copy source

```dockerfile
COPY . .
```

Now application code enters the image.

---

### Production mode

```dockerfile
ENV NODE_ENV=production
```

This tells the application/runtime that it is running in production.

---

### Document the port

```dockerfile
EXPOSE 5000
```

This documents the port the application listens on.

Remember:

> `EXPOSE` does not itself publish the port to your host.

---

### Start the application

```dockerfile
CMD ["node", "server.js"]
```

The container starts your production server.

---

# 14. Why copy package files first?

Suppose your Dockerfile is:

```dockerfile
COPY package*.json ./
RUN npm ci
COPY . .
```

Docker can cache the dependency installation layer.

Imagine you only change:

```text
controllers/todo.controller.js
```

Your:

```text
package.json
package-lock.json
```

haven't changed.

Therefore Docker can reuse:

```text
npm ci
```

instead of reinstalling everything.

This makes builds much faster.

---

# 15. Bad Dockerfile ordering

For example:

```dockerfile
COPY . .
RUN npm ci
```

Now a small source-code change may invalidate the layer containing the dependency installation.

That can make builds slower.

Better:

```text
package files
   ↓
npm ci
   ↓
source files
```

---

# 16. Production dependencies only

Suppose:

```text
dependencies:
    express
    mongoose
    helmet

devDependencies:
    jest
    supertest
    nodemon
```

Production needs:

```text
express
mongoose
helmet
```

It doesn't normally need:

```text
jest
supertest
nodemon
```

So:

```bash
npm ci --omit=dev
```

helps keep the runtime image cleaner.

---

# 17. But where do tests run?

This is an important architecture question.

Tests should normally run **before** you deploy the production image.

Think:

```text
Developer
   ↓
Git push
   ↓
CI
   ├── lint
   ├── tests
   ├── security checks
   └── Docker build
             ↓
        production image
```

Not:

```text
Production container
   ↓
install Jest
   ↓
run tests
```

The production container's job is to run the application.

---

# 18. Production container should have one main responsibility

For your backend:

```text
Container
   ↓
Node.js API
```

Don't turn it into:

```text
Node API
+
MongoDB
+
Redis
+
Nginx
+
worker
+
cron
```

Instead:

```text
API container
      +
MongoDB container
      +
Redis container
```

Each component has a clear responsibility.

---

# 19. MongoDB should remain separate

You already learned:

```text
backend
   │
   │ Docker network
   ▼
MongoDB
```

Production follows the same architectural principle.

Your Node container should not contain MongoDB.

Instead:

```text
┌─────────────────┐
│ Backend         │
│ Node.js         │
└────────┬────────┘
         │
         │ network
         ▼
┌─────────────────┐
│ MongoDB         │
└─────────────────┘
```

The actual production database might be managed by a cloud provider rather than another container, but the separation remains.

---

# 20. Environment variables at runtime

Your image shouldn't contain:

```text
MONGO_URI=production-secret
JWT_SECRET=production-secret
```

Instead:

```text
Docker container
      ↑
environment variables
```

For example:

```bash
docker run \
  -e NODE_ENV=production \
  -e PORT=5000 \
  -e MONGO_URI="..." \
  your-backend-image
```

In real deployments, secrets are usually provided through the platform's secret/configuration system rather than typed directly into commands.

---

# 21. Configuration flow

The architecture becomes:

```text
Deployment platform
        │
        │ environment
        ▼
     Container
        │
        ▼
   process.env
        │
        ▼
     env.js
        │
        ▼
    Application
```

This follows the configuration architecture you've already learned.

---

# 22. Don't hard-code production URLs

Bad:

```js
const mongoUri = "mongodb://production-server...";
```

Bad:

```js
const jwtSecret = "my-production-secret";
```

Better:

```js
env.mongoUri
env.accessTokenSecret
```

Then configuration changes without rebuilding your application source.

---

# 23. Health check belongs in production

You've already learned:

```text
/healthz
/readyz
```

Now connect them to your production container.

Docker can check:

```text
GET /healthz
```

while your orchestration/load-balancing layer can use readiness:

```text
GET /readyz
```

Conceptually:

```text
Container
   │
   ├── /healthz
   │      ↓
   │   alive?
   │
   └── /readyz
          ↓
       ready?
```

---

# 24. Graceful shutdown belongs here too

Production container:

```text
SIGTERM
   ↓
Node shutdown handler
   ↓
ready = false
   ↓
finish requests
   ↓
close server
   ↓
close MongoDB
   ↓
exit
```

So your production Docker architecture now uses everything from 23.13 and 23.14.

---

# 25. Production container security

Now let's discuss an important improvement.

By default, a container process may run as `root`.

That's not ideal.

If your Node application is compromised and it runs with excessive privileges, the potential impact can be larger.

So where practical, run your application as a non-root user.

---

# 26. Node's non-root user

Official Node images provide a `node` user.

Conceptually:

```dockerfile
USER node
```

Then:

```text
Container
   ↓
Node process
   ↓
non-root user
```

This follows the principle:

> **Least privilege.**

Don't give the application more operating-system privileges than it needs.

---

# 27. Important caveat

You can't blindly add:

```dockerfile
USER node
```

and assume everything works.

Your application files and directories must be accessible to that user.

For example:

```text
/app
```

needs appropriate ownership/permissions.

This is one reason production Dockerfiles sometimes include:

```dockerfile
COPY --chown=node:node ...
```

or adjust permissions before switching users.

---

# 28. Example hardened Dockerfile

A more production-oriented example:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY --chown=node:node package*.json ./

RUN npm ci --omit=dev

COPY --chown=node:node . .

ENV NODE_ENV=production

USER node

EXPOSE 5000

CMD ["node", "server.js"]
```

Again, the exact version and permissions should match your project.

The important concepts are:

```text
small base
+
reproducible dependencies
+
production dependencies
+
non-root user
+
runtime configuration
```

---

# 29. Why Alpine?

You've probably seen:

```text
node:22
node:22-slim
node:22-alpine
```

These are different base images.

Very roughly:

```text
node
   ↓
larger
   ↓
more general

node-slim
   ↓
smaller

node-alpine
   ↓
very small
```

But **smaller isn't automatically better**.

Some Node packages depend on native system libraries and can behave differently depending on the base image.

So choose based on:

```text
compatibility
security updates
build complexity
image size
runtime needs
```

not just:

> "Alpine is smaller."

---

# 30. Native dependencies matter

Suppose an npm package needs native compilation.

Then:

```text
npm ci
   ↓
compile native dependency
   ↓
needs build tools
```

Your runtime image may not need those build tools after compilation.

This leads us to one of the most useful production Docker techniques:

# Multi-stage builds

---

# 31. What is a multi-stage build?

You can have:

```text
Build stage
    ↓
compile/install/build
    ↓
Runtime stage
    ↓
only required output
```

For example:

```text
Stage 1
Node + build tools + dependencies
        ↓
        build
        ↓
Stage 2
small Node runtime
        ↓
production application
```

The final image doesn't need to contain everything from the build stage.

---

# 32. Why multi-stage builds matter

Suppose building your application requires:

```text
compiler
Python
native build tools
development dependencies
```

but running it only requires:

```text
Node
production dependencies
application
```

Then:

```text
Build image
large
```

but:

```text
Runtime image
small
```

That's exactly what multi-stage builds solve.

---

# 33. Do you need multi-stage builds for your current backend?

Not necessarily.

Your current Node backend may not have a compile step.

If your application is:

```text
JavaScript
   ↓
Node
   ↓
server.js
```

then a simple production Dockerfile can be perfectly reasonable.

Don't add complexity just because it's called "production."

---

# 34. TypeScript example

If you later move to TypeScript:

```text
src/
   ↓
tsc
   ↓
dist/
```

then multi-stage builds become more useful.

Conceptually:

```dockerfile
FROM node:22 AS build

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build


FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY --from=build /app/dist ./dist

USER node

CMD ["node", "dist/server.js"]
```

This is the general pattern.

---

# 35. Production container should not use nodemon

Avoid:

```dockerfile
CMD ["npx", "nodemon", "server.js"]
```

in production.

`nodemon` exists to watch development files and restart your process.

Production should simply run:

```dockerfile
CMD ["node", "server.js"]
```

Predictable and simple.

---

# 36. Production should not mount source code

Development often uses:

```yaml
volumes:
  - .:/app
```

This is useful because:

```text
local source
   ↓
container source
```

changes immediately.

Production should normally use the source already baked into the image:

```text
Docker image
   ↓
application code
```

This keeps the container immutable.

---

# 37. Development vs production

Here's the important comparison:

|Development|Production|
|---|---|
|Volume mount|Code inside image|
|nodemon|node|
|Dev dependencies|Production dependencies|
|Frequent rebuilds|Versioned image|
|Debugging tools|Minimal runtime|
|Local `.env`|Platform-managed configuration|
|Fast iteration|Reproducibility|
|Source mounted|Immutable image|

---

# 38. Tag your images

Don't rely only on:

```text
latest
```

A better approach is to use meaningful immutable tags.

For example:

```text
backend:1.0.0
```

or:

```text
backend:git-abc123
```

Then:

```text
Deployment
   ↓
backend:1.0.0
```

You know exactly what version is running.

---

# 39. Why `latest` can be dangerous

Imagine:

```text
backend:latest
```

today means:

```text
version A
```

and tomorrow:

```text
backend:latest
```

means:

```text
version B
```

Now if something breaks, you don't immediately know which exact image was deployed.

Immutable version tags make debugging much easier.

---

# 40. Image promotion

A professional deployment pipeline can look like:

```text
Git commit
   ↓
CI
   ↓
Tests
   ↓
Build image
   ↓
backend:abc123
   ↓
Push registry
   ↓
Deploy
```

Then the same exact image can move through environments:

```text
staging
   ↓
production
```

rather than rebuilding different images for each environment.

# 41. Container registry

Conceptually:

```text

   ↓

   ↓
Container Registry
   ↓
Production server
   ↓

```

Examples include cloud/provider registries and public registries.

The key concept is:

> **The registry stores the deployable image.**

# 43. Production architecture

A simplified production system might look like:

```text
                    Internet
                       │
                       ▼
                 Reverse Proxy
                       │
                       ▼
                Load Balancer
                       │
            ┌──────────┴──────────┐
            ▼                     ▼
       Backend #1             Backend #2
       Container              Container
            │                     │
            └──────────┬──────────┘
                       │
                       ▼
                   MongoDB
```

Both backend containers can run the **same image**.

---

# 44. Why multiple backend containers?

Suppose:

```text
Backend #1
```

crashes.

If you have:

```text
Backend #2
```

traffic can continue through it.

This is one of the major benefits of stateless application containers.

---

# 45. Stateless containers

Your backend container should ideally not depend on local container storage for important persistent application data.

Bad:

```text
Container
  ↓
important user data stored here
```

Container gets replaced:

```text
Container deleted
   ↓
data deleted
```

Better:

```text
Backend container
      ↓
MongoDB
```

Persistent state belongs in the appropriate persistent system.

---

# 46. What about uploaded files?

If users upload:

```text
profile.jpg
document.pdf
video.mp4
```

don't blindly store them inside the container filesystem.

Why?

Containers can be replaced.

Instead, use persistent storage/object storage appropriate to your architecture.

The general principle:

```text
Container
=
ephemeral

Database/object storage
=
persistent
```

# 47. Production environment variables

A production deployment may provide:

```text
NODE_ENV=production
PORT=5000
MONGO_URI=...
ACCESS_TOKEN_SECRET=...
REFRESH_TOKEN_SECRET=...
FRONTEND_URL=...
```

Your application reads them through:

```text

```

The roadmap explicitly treats environment configuration as a core part of the Docker architecture.

# 50. Add health checking

Your Docker runtime can then check:

```text
/healthz
```

Conceptually:

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD node -e "fetch('http://localhost:5000/healthz').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"
```

But there is an important consideration:

If your base image/runtime doesn't support the exact command you choose, adjust it accordingly.

The architecture is more important than memorizing one command.


# 52. The most important mindset

Don't think:

> "Docker is just a way to run my Node app."

Think:

> **Docker gives me a reproducible runtime environment for my application.**

That means:

```text
Same image
    ↓
Development/staging/production
    ↓
Predictable runtime
```

with environment-specific configuration supplied separately.
