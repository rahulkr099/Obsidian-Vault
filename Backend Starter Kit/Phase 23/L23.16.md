# Lesson 23.16 — Build and Run the Complete Backend

This is the **final lesson of Phase 23 — Docker & Production Architecture**. Your roadmap explicitly ends Phase 23 with **23.16 Build and run the complete backend**.

The purpose of this lesson is not to learn one new Docker command.

It is to connect everything you've learned:

```text
Node.js
Express
MongoDB
Environment variables
Dockerfile
Docker Compose
Networks
Volumes
Health checks
Readiness
Graceful shutdown
Production container
```

into **one complete backend system**.

By the end of this lesson, think of your application like this:

# 3. Why Docker Compose?

You could manually run:

```bash
docker run ...
```

for the backend and:

```bash
docker run ...
```

for MongoDB.

But that becomes annoying.

You have:

```text

MongoDB
Network

```

Compose lets you describe these together.

Conceptually:

```text
docker-compose.yml
        │
        ├── backend
        ├── mongodb
        ├── network
        └── volume
```

Then:

```bash
docker compose up
```

can bring the environment up.

Suppose Docker doesn't work.

```text

       +

```

Instead:

```text

```

# 7. Step 2 — Check MongoDB

Your application should be able to connect to MongoDB.

Locally, your connection might look conceptually like:

```text
mongodb://localhost:27017/backend
```

Inside Docker Compose, however, **localhost changes meaning**.

This is one of the most important Docker concepts.

---

# 8. `localhost` inside a container

Suppose:

```text
Backend container
MongoDB container
```

Inside the backend container:

```text
localhost
```

means:

> **the backend container itself**

It does NOT mean MongoDB.

So this is wrong inside the backend container:

```text
mongodb://localhost:27017/backend
```

because MongoDB is running in another container.

---

# 9. Docker service names become hostnames

Suppose your Compose file says:

```yaml
services:
  backend:
    ...
  
  mongo:
    ...
```

Then the backend can reach MongoDB using:

```text
mongo
```

as the hostname.

So:

```text
mongodb://mongo:27017/backend
```

means:

```text
backend container
       │
       │ Docker DNS
       ▼
mongo container
```

This is why Docker networking matters.

# 13. Step 4 — Production Dockerfile

For a JavaScript Node backend, your production Dockerfile can be conceptually:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY --chown=node:node package*.json ./

RUN npm ci --omit=dev

COPY --chown=node:node . .

ENV NODE_ENV=production

USER node

EXPOSE 5000

CMD ["node", "server.js"]
```

Your actual entry point might instead be:

```text
src/server.js
```

or:

```text
src/index.js
```

Use the entry point your project actually has.

# 18. Step 6 — Create Compose

A simplified Compose file:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile

    ports:
      - "5000:5000"

    environment:
      NODE_ENV: production
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/backend

    depends_on:
      mongo:
        condition: service_healthy

  mongo:
    image: mongo:8

    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
```

This is a conceptual production-style Compose setup.

Your actual MongoDB version should be chosen deliberately rather than blindly copying a version number.

---

# 19. What does this Compose file create?

It defines:

```text
backend
mongo
mongo-data
```

Docker Compose automatically creates a network for the services unless you configure otherwise.

So:

```text
backend
   │
   │ network
   ▼
mongo
```

works using:

```text
mongo
```

as the hostname.

---

# 20. Why `depends_on`?

You don't want the backend to blindly start before MongoDB is ready.

Without health-aware startup:

```text
Backend starts
   ↓
MongoDB still starting
   ↓
Mongo connection fails
```

With health-aware dependency:

```text
Mongo starts
   ↓
Mongo health check
   ↓
Mongo healthy
   ↓
Backend starts
```

This is much more reliable.

---

# 21. Important: `depends_on` isn't magic

A common misunderstanding is:

> "depends_on means MongoDB is ready."

Not necessarily.

Basic dependency ordering only tells Compose about startup relationships.

For actual readiness, use a health check and a health-aware condition where supported by your Compose implementation.

Conceptually:

```text
start order
≠
service readiness
```

This is exactly why you learned health checks earlier.

# 22. MongoDB health check

Conceptually, MongoDB can have:

```yaml

  test:
    [
      "CMD-SHELL",
      "mongosh --quiet --eval 'db.adminCommand(\"ping\").ok' | grep 1"
    ]
  interval: 10s
  timeout: 5s
  retries: 5
```

The exact command depends on the MongoDB image/version you're using.

The important concept:

```text

   ↓
Can MongoDB actually respond?
```


# 33. Volume persistence test

This is one of the most important practical tests.

First:

```text
Create data
```

Then:

```bash
docker compose down
```

Start again:

```bash
docker compose up
```

Your data should still exist because MongoDB uses:

```text
mongo-data
```

the named volume.

---

# 34. Why does the data survive?

Because:

```text
MongoDB container
      ↓
/data/db
      ↓
mongo-data volume
```

When the container is removed:

```text
MongoDB container
      ↓
❌ removed
```

the volume remains:

```text
mongo-data
      ↓
✅ remains
```

So when MongoDB starts again:

```text
new MongoDB container
      ↓
same volume
      ↓
old data
```

---

# 35. Don't accidentally delete the volume

Be careful with:

```bash
docker compose down -v
```

The `-v` tells Compose to remove associated named volumes.

That can delete your local MongoDB data.

So:

```bash
docker compose down
```

and:

```bash
docker compose down -v
```

are **not equivalent**.

```text
        ↓
```

Let's follow one real request:

```text

```

```text

 ↓
```

```text
 ↓

 ↓

 ↓

 ↓
```

# 50. What happens if MongoDB crashes?

Suppose:

```text
Backend ✓
MongoDB ❌
```

Your readiness should ideally reflect that:

```text
/healthz
   ↓
200

/readyz
   ↓
503
```

Depending on your architecture, the backend may remain alive but shouldn't advertise itself as ready if a required dependency is unavailable.

This is exactly why we separate:

```text
liveness
```

from:

```text
readiness
```

---

# 51. What happens if the backend crashes?

Suppose:

```text
Backend ❌
MongoDB ✓
```

Docker/container orchestration can detect that the backend process has exited or failed its health checks and restart/replace it according to the deployment configuration.

The MongoDB data remains because it lives outside the backend container.

---

# 52. What happens when the backend is redeployed?

Suppose:

```text
backend:1.0.0
```

is running.

You release:

```text
backend:1.1.0
```

A deployment system can:

```text
Start new container
       ↓
Health check
       ↓
Ready
       ↓
Send traffic
       ↓
Stop old container
```

This is the foundation of rolling/zero-downtime deployment strategies.

---

# 53. Why readiness matters during deployment

Imagine:

```text
Old backend
    ↓
serving traffic
```

New backend starts:

```text
New backend
    ↓
MongoDB connecting...
```

It shouldn't receive production traffic yet.

Therefore:

```text
new backend
   ↓
/readyz = 503
```

Once ready:

```text
/readyz = 200
```

Then traffic can move to it.

This is why readiness isn't just a debugging endpoint.

It's deployment infrastructure.
