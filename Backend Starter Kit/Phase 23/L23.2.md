# Lesson 23.2 — Docker Fundamentals

In **23.1**, we learned _why_ containers exist.

Now we'll understand the basic Docker vocabulary and workflow deeply enough that the commands you'll use later won't feel like magic.

Your Phase 23 roadmap specifically moves from **why containers → Docker fundamentals → Dockerfile → images → containers → Compose**.

---

# 1. First: What is Docker?

Docker is a platform/tooling ecosystem that lets you:

- build container images,
    
- create and run containers,
    
- connect containers,
    
- manage containerized applications.
    

The important thing is that Docker gives us a standard way to package and run software.

For your backend:

```text
Your Code
   ↓
Docker
   ↓
Container
   ↓
Node.js + Express
```

---

# 2. The four terms you must know

Before touching commands, understand these:

```text
Dockerfile
    ↓
Image
    ↓
Container
    ↓
Network / Volumes
```

Let's separate them.

---

## Dockerfile

A text file containing instructions for building an image.

Example:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "server.js"]
```

Don't worry about understanding every line yet.

That's **Lesson 23.3**.

For now:

> Dockerfile = instructions for creating an image.

---

# 3. Docker Image

An image is the packaged template used to create containers.

For example:

```text
Node backend image
```

could contain:

```text
Node.js
npm dependencies
application code
configuration needed at build time
startup command
```

Conceptually:

```text
┌───────────────────────────┐
│       Docker Image        │
│                           │
│ Node.js                   │
│ Express                   │
│ Mongoose                  │
│ Your application          │
│ Startup configuration     │
└───────────────────────────┘
```

An image itself isn't your running application.

It is the **blueprint/package** from which containers are created.

---

# 4. Docker Container

A container is a running instance of an image.

```text
Image
  │
  ├────► Container A
  │
  ├────► Container B
  │
  └────► Container C
```

You could theoretically run multiple backend containers from the same image.

For example:

```text
backend-image
     │
     ├── api-1
     ├── api-2
     └── api-3
```

This becomes useful when scaling applications.

---

# 5. Docker Registry

There's another term you'll encounter:

> **Registry**

A registry stores Docker images.

The most famous public registry is Docker Hub.

Conceptually:

```text
Your computer
     │
     │ docker pull
     ▼
Docker Registry
     │
     ▼
Docker Image
```

And the opposite:

```text
Your computer
     │
     │ docker push
     ▼
Docker Registry
```

In production, your CI/CD system may build an image and push it to a private registry.

Then a server can pull that image.

# 6. The complete Docker lifecycle

Now connect everything:

```text
Dockerfile
    │
    │ docker build
    ▼
Docker Image
    │
    │ docker run
    ▼

    │
```

# 7. Installing/checking Docker

On your Linux system, you can check whether Docker is installed:

```bash
docker --version
```

You may get something like:

```text
Docker version 28.x.x
```

The exact version doesn't matter for this lesson.

You can also run:

```bash
docker info
```

This gives information about the Docker installation and daemon.

# 8. Docker has a client and a daemon

This is a useful concept.

When you type:

```bash
docker ps
```

you're using the Docker CLI.

Conceptually:

```text
Terminal
   │
   ▼
Docker CLI
   │
   ▼
Docker Engine
   │
   ├── Images
   ├── Containers
   ├── Networks
   └── Volumes
```

The CLI sends commands to Docker Engine.

So when you type:

```bash
docker run ...
```

you're essentially telling Docker:

> Create and run this container for me.

# 9. Your first Docker command

Let's use a very small example rather than your backend.

Run:

```bash
docker run hello-world
```

Docker will:

```text
Look for hello-world image
        ↓
Doesn't exist locally?
        ↓
Pull image from registry
        ↓
Create container
        ↓
Run it
        ↓
Container prints message
        ↓
Container exits
```

This one command demonstrates a surprisingly large amount of Docker.

---

# 10. `docker pull`

You can explicitly download an image:

```bash
docker pull node:24
```

This means:

> Download the Node.js 24 image.

The general structure is:

```text
docker pull IMAGE
```

For example:

```bash
docker pull node:24
```

Here:

```text
node
```

is the image repository/name.

And:

```text
24
```

is the tag.

---

# 11. What is a tag?

You might see:

```text
node:24
node:22
node:20
```

The part after `:` is the tag.

```text
node:24
    │  │
    │  └── tag
    └───── image name
```

Tags commonly identify versions or variants.

This matters because you don't want your production application unexpectedly switching runtime versions.

For example, explicitly using:

```dockerfile
FROM node:24
```

is more predictable than blindly depending on a moving tag.

Later we'll discuss more precise image pinning.

---

# 12. List your images

Run:

```bash
docker images
```

or:

```bash
docker image ls
```

You'll see something conceptually like:

```text
REPOSITORY    TAG      IMAGE ID      CREATED       SIZE
node          24       abc123        ...           ...
hello-world   latest   def456        ...           ...
```

Important fields:

### Repository

```text
node
```

### Tag

```text
24
```

### Image ID

```text
abc123...
```

### Size

How large the image is.

---

# 13. Run a container

Now let's run Node itself:

```bash
docker run node:24 node --version
```

Think about what happened:

```text
node:24 image
      ↓
new container
      ↓
node --version
      ↓
prints Node version
      ↓
container exits
```

The container was created specifically to execute that command.

This is a very important idea:

> A container doesn't have to stay running forever.

It runs its main process.

When that process ends, the container can stop.

---

# 14. Container lifecycle

A container can be:

```text
Created
   ↓
Running
   ↓
Stopped
   ↓
Started again
   ↓
Stopped
   ↓
Removed
```

Conceptually:

```text
             ┌───────────┐
             │ Created   │
             └─────┬─────┘
                   │
                   ▼
             ┌───────────┐
             │ Running   │
             └─────┬─────┘
                   │
                   ▼
             ┌───────────┐
             │ Stopped   │
             └─────┬─────┘
                   │
                   ▼
             ┌───────────┐
             │ Removed   │
             └───────────┘
```

Don't confuse:

```text
Stopped container
```

with:

```text
Removed container
```

A stopped container can still exist.

---

# 15. List running containers

Run:

```bash
docker ps
```

This shows currently running containers.

For example:

```text
CONTAINER ID   IMAGE     STATUS       PORTS
abc123         node:24   Up 2 minutes ...
```

---

# 16. List all containers

Use:

```bash
docker ps -a
```

The `-a` means:

> Show all containers, including stopped ones.

So:

```bash
docker ps
```

means:

> What's running?

While:

```bash
docker ps -a
```

means:

> What containers exist?

This distinction is very useful when debugging.

---

# 17. Container names

When Docker creates a container, it gives it a name if you don't provide one.

You can explicitly provide one:

```bash
docker run --name my-node node:24 node --version
```

Now:

```text
my-node
```

is the container's name.

You can then reference it:

```bash
docker ps -a
```

and later:

```bash
docker start my-node
```

---

# 18. `docker start` vs `docker run`

This is a common beginner mistake.

### `docker run`

Creates a **new container** from an image and starts it.

```bash
docker run node:24
```

### `docker start`

Starts an **existing stopped container**.

```bash
docker start my-node
```

Think:

```text
docker run
    ↓
Image → NEW Container
```

while:

```text
docker start
    ↓
Existing Container → Running
```

---

# 19. `docker stop`

To stop a running container:

```bash
docker stop my-node
```

This sends a termination request to the container's main process.

That becomes especially important later when we learn:

> **Graceful shutdown**

in Lesson 23.14.

Your Node application should be able to respond properly when the container is being stopped.

---

# 20. `docker rm`

To remove a container:

```bash
docker rm my-node
```

This removes the container itself.

It does **not** mean:

> Delete the image.

Remember:

```text
Image
   │
   └── Container
```

Removing the container doesn't automatically mean removing the image.

---

# 21. `docker rmi`

To remove an image:

```bash
docker rmi node:24
```

This is different from:

```bash
docker rm
```

Remember:

```text
docker rm
    ↓
remove container

docker rmi
    ↓
remove image
```

---

# 22. Ports

Now we reach something very important for your Express backend.

Suppose Express listens on:

```text
PORT=5000
```

Inside the container:

```text
Node
 ↓
Port 5000
```

But your browser is outside the container.

You need to expose/map the port.

For example:

```bash
docker run -p 5000:5000 my-backend
```

The structure is:

```text
-p HOST_PORT:CONTAINER_PORT
```

So:

```text
5000:5000
```

means:

```text
Host port 5000
       │
       ▼
Container port 5000
       │
       ▼
Express
```

---

# 23. Why port mapping matters

Without port mapping:

```text
Browser
   X
Container
```

With:

```bash
-p 5000:5000
```

you get:

```text
Browser
   │
   ▼
localhost:5000
   │
   ▼
Host
   │
   ▼
Container:5000
   │
   ▼
Express
```

This is how you'll eventually access your Dockerized API.

---

# 24. Environment variables

Containers also have their own environment.

You can provide an environment variable with:

```bash
docker run -e PORT=5000 my-backend
```

Then inside the container:

```js
process.env.PORT
```

can read:

```text
5000
```

Later we'll use this for:

```text
MONGO_URI
JWT secrets
NODE_ENV
PORT
frontend URL
```

But remember:

> Secrets should not casually be baked into an image.

We'll cover proper environment handling in **23.12**.

# 25. Container filesystem

A container has its own filesystem.

For example:

```text
Container
├── app/
├── node_modules/
├── package.json
└── server.js
```

If you remove the container, changes made only inside that container may disappear.

This is why persistent data requires:

```text
Volumes
```

We'll study this properly in **23.10**.

This is particularly important for databases.

---

# 26. Why MongoDB needs persistent storage

Imagine MongoDB is running inside a container:

```text
MongoDB Container
      │
      ▼
Database files
```

Then you remove the container:

```bash
docker rm mongo
```

Without proper persistent storage, you could lose the database data.

Instead:

```text
MongoDB Container
       │
       ▼
Docker Volume
       │
       ▼
Persistent storage
```

So:

> Containers are disposable; important data should live in persistent storage.

This is one of the most important Docker principles.

---

# 27. Containers should generally be disposable

This might sound strange initially.

You don't want to think:

> "This particular container is precious."

Instead:

```text
Old container
     ↓
destroy
     ↓
new container
     ↓
same image
     ↓
same persistent data
```

This is one of the major benefits of containerized architecture.

Your application should be reproducible.

# 28. The difference between code and container state

Think about three things:

```text
Source Code
Docker Image
Container
```

### Source code

Your actual project:

```text
controllers/
services/
models/
...
```

### Image

Packaged version of that project:

```text
Node
+
dependencies
+
application
```

### Container

Running instance:

```text
Image
 ↓
Running process
```

So:

```text
Source Code
     ↓
   build
     ↓
Docker Image
     ↓
   run
     ↓
Container
```

This is the central Docker workflow.

# 31. A useful debugging mental model

When something isn't working, ask:

```text
Is the image correct?
        ↓
Is the container running?
        ↓
Is the application running inside it?
        ↓
Is the port exposed?
        ↓
Is the network correct?
        ↓
Are environment variables correct?
        ↓
Is persistent storage configured?
```

For example, if:

```text
localhost:5000
```

doesn't work, don't immediately change random code.

Check:

```bash
docker ps
```

Then:

```bash
docker logs <container>
```

Then inspect the port mapping.

This debugging mindset will save you a lot of time.
