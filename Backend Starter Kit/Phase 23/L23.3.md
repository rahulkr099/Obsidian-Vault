# Lesson 23.3 — Dockerfile

Now we're going to create the **recipe for your backend container**.

In Lesson 23.2, we established:

```text
Dockerfile
    ↓ build
Docker Image
    ↓ run
Container
```

So the Dockerfile is where we tell Docker:

> **"Start with this environment, put my backend inside it, install what it needs, and tell it how to start."**

This is the first lesson where we'll actually write Docker configuration.

---

# 1. What is a Dockerfile?

A Dockerfile is a plain text file named:

```text
Dockerfile
```

No extension.

Not:

```text
Dockerfile.txt
```

Not:

```text
dockerfile.js
```

Just:

```text
Dockerfile
```

For your backend:

```text
backend/
├── Dockerfile
├── package.json
├── package-lock.json
├── server.js
├── app.js
│
├── config/
├── controllers/
├── middlewares/
├── models/
├── repositories/
├── routes/
├── services/
└── ...
```

The Dockerfile describes how to turn this project into an image.

---

# 2. Think of it as a cooking recipe

Suppose you're making your backend container.

The recipe might say:

```text
1. Start with Node.js
2. Create /app
3. Go into /app
4. Copy package files
5. Install dependencies
6. Copy source code
7. Expose the application port
8. Start the server
```

Dockerfile:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "server.js"]
```

Don't worry if this looks unfamiliar.

We're going to understand **every instruction**.

---

# 3. `FROM`

Start with:

```dockerfile
FROM node:24
```

This is usually the first instruction in a Dockerfile.

It means:

> Start building my image from the `node:24` image.

Remember our previous lesson:

```text
Node image
     ↓
Your Dockerfile
     ↓
Your backend image
```

So we're not building Node.js ourselves.

We're using an existing Node image as our foundation.

---

# 4. Why do we need a base image?

Your backend needs Node.js.

Without Docker, your machine provides:

```text
Operating System
      ↓
Node.js
      ↓
npm
      ↓
Your application
```

With Docker, the container needs its own runtime environment.

The Node image provides the foundation:

```text
┌─────────────────────────┐
│      node:24 image      │
│                         │
│ Node.js                 │
│ npm                     │
│ OS-level environment    │
└─────────────────────────┘
```

Then we add your application on top.

---

# 5. Understanding the image layers

Conceptually:

```text
┌──────────────────────────┐
│ Your backend             │
├──────────────────────────┤
│ npm dependencies         │
├──────────────────────────┤
│ Node environment         │
├──────────────────────────┤
│ Base image               │
└──────────────────────────┘
```

This becomes important in **Lesson 23.4 — Docker Layers**.

For now, just understand:

> `FROM` establishes the starting point.

---

# 6. `WORKDIR`

Next:

```dockerfile
WORKDIR /app
```

This tells Docker:

> Use `/app` as the working directory inside the image/container.

Without it, you might end up scattering files around the container filesystem.

With it:

```text
/app
├── package.json
├── package-lock.json
├── server.js
└── ...
```

Your application lives here.

---

# 7. Why `WORKDIR` is useful

Suppose your Dockerfile says:

```dockerfile
WORKDIR /app
```

Then:

```dockerfile
COPY . .
```

means:

```text
Current directory = /app

Copy project
     ↓
/app
```

And:

```dockerfile
RUN npm ci
```

means:

```text
Run npm ci
inside /app
```

So `WORKDIR` gives Docker a consistent location to work in.

---

# 8. `COPY`

Now:

```dockerfile
COPY package*.json ./
```

This tells Docker:

> Copy the package files from my project into the current directory inside the image.

Your project has:

```text
package.json
package-lock.json
```

The pattern:

```text
package*.json
```

matches both.

Conceptually:

```text
HOST PROJECT

package.json
package-lock.json
       │
       │ COPY
       ▼
CONTAINER IMAGE

/app/
├── package.json
└── package-lock.json
```

---

# 9. Why copy package files separately?

At first you might wonder:

> Why don't we just copy the entire project?

We could write:

```dockerfile
COPY . .
```

immediately.

But there's an important optimization here.

Suppose you have:

```text
package.json
package-lock.json
controllers/
services/
routes/
models/
```

You change:

```text
controllers/user.controller.js
```

Your dependencies didn't change.

If Docker can reuse the dependency-installation layer, it doesn't need to reinstall everything unnecessarily.

That's one reason we commonly do:

```dockerfile
COPY package*.json ./

RUN npm ci

COPY . .
```

We'll understand this deeply in **23.4**.

For now remember:

> Copy dependency files first, install dependencies, then copy application code.

---

# 10. `RUN`

Now:

```dockerfile
RUN npm ci
```

`RUN` tells Docker:

> Execute this command while building the image.

This happens during:

```bash
docker build
```

not when you execute:

```bash
docker run
```

This distinction is extremely important.

### Build time

```text
Dockerfile
   ↓
RUN npm ci
   ↓
Image
```

### Runtime

```text
Image
   ↓
Container
   ↓
CMD
```

So:

```dockerfile
RUN npm ci
```

installs dependencies **into the image**.

---

# 11. Why `npm ci` instead of `npm install`?

For a project with a committed lockfile:

```text
package.json
package-lock.json
```

we generally prefer:

```bash
npm ci
```

for reproducible installs.

The basic idea:

```text
package.json
      +
package-lock.json
      ↓
npm ci
      ↓
exact locked dependency tree
```

This is especially useful for CI and production builds.

We'll discuss production dependency installation more deeply in the production Dockerfile lesson.

---

# 12. `COPY . .`

Now:

```dockerfile
COPY . .
```

This means:

> Copy the remaining project files into the current working directory.

So eventually:

```text
/app/
├── package.json
├── package-lock.json
├── server.js
├── app.js
├── config/
├── controllers/
├── middlewares/
├── models/
├── repositories/
├── routes/
├── services/
├── utils/
└── validations/
```

Now your application exists inside the image.

---

# 13. But don't blindly copy everything

There's a problem with:

```dockerfile
COPY . .
```

It can potentially copy things you don't want inside the image.

For example:

```text
node_modules/
.env
.git/
logs/
temporary files
```

That's why we'll eventually create:

```text
.dockerignore
```

For example:

```text
node_modules
.git
.env
npm-debug.log
```

Then:

```dockerfile
COPY . .
```

won't copy ignored files.

We'll study `.dockerignore` as part of the Docker build process.

---

# 14. `EXPOSE`

Next:

```dockerfile
EXPOSE 5000
```

This documents that your application expects to listen on port `5000` inside the container.

Important:

> `EXPOSE` does **not** publish the port to your host by itself.

This is a common beginner misunderstanding.

If you have:

```dockerfile
EXPOSE 5000
```

that doesn't automatically mean your browser can access:

```text
localhost:5000
```

You still need port mapping when running the container:

```bash
docker run -p 5000:5000 my-backend
```

So:

```text
EXPOSE
   ↓
Documentation/metadata about container port
```

while:

```text
-p 5000:5000
   ↓
Actual host → container port mapping
```

---

# 15. `CMD`

Finally:

```dockerfile
CMD ["node", "server.js"]
```

This tells Docker:

> When a container is started from this image, run the Node server.

So:

```text
Image
  ↓
docker run
  ↓
Container starts
  ↓
CMD
  ↓
node server.js
  ↓
Express starts
```

This is the command that keeps your backend container running.

---

# 16. Why `CMD` matters so much

Remember from Lesson 23.2:

> A container generally exists around its main process.

If you run:

```dockerfile
CMD ["node", "server.js"]
```

then:

```text
node server.js
```

becomes the main process.

If the Node process stops:

```text
Node process exits
      ↓
Container stops
```

That's why your application process and container lifecycle are closely related.

We'll return to this when we learn graceful shutdown.

---

# 17. Why the JSON form?

You'll often see:

```dockerfile
CMD ["node", "server.js"]
```

rather than:

```dockerfile
CMD node server.js
```

The first is called the **exec form**.

For your backend, prefer the exec form:

```dockerfile
CMD ["node", "server.js"]
```

It gives Docker clearer process semantics and is especially useful for proper signal handling.

This will matter later for:

```text
SIGTERM
 ↓
Node
 ↓
graceful shutdown
```

---

# 18. Complete basic Dockerfile

Putting everything together:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "server.js"]
```

Read it like English:

```text
Start with Node 24
        ↓
Work inside /app
        ↓
Copy package files
        ↓
Install dependencies
        ↓
Copy application
        ↓
Document port 5000
        ↓
Start server.js
```

That's the Dockerfile.

---

# 19. Now build the image

Suppose you're inside:

```text
backend/
```

and your Dockerfile is there.

Run:

```bash
docker build -t my-backend .
```

Break it down:

```text
docker build
```

means:

> Build an image.

```text
-t my-backend
```

means:

> Give the resulting image the name `my-backend`.

And:

```text
.
```

means:

> Use the current directory as the build context.

So:

```bash
docker build -t my-backend .
```

means:

> Build an image called `my-backend` using this directory as the build context.

---

# 20. What is the build context?

This is an important concept.

When you run:

```bash
docker build -t my-backend .
```

the final:

```text
.
```

isn't random.

It means:

> Send the current directory as the build context to Docker.

So Docker can access:

```text
Dockerfile
package.json
package-lock.json
server.js
app/
controllers/
services/
...
```

depending on `.dockerignore`.

Conceptually:

```text
backend/
     │
     │ build context
     ▼
Docker build
     │
     ▼
Image
```

---

# 21. Check your image

After building:

```bash
docker images
```

You should see something like:

```text
REPOSITORY    TAG       IMAGE ID
my-backend    latest    abc123...
```

Now you have:

```text
Dockerfile
      ↓
docker build
      ↓
my-backend image
```

---

# 22. Run your backend

Now:

```bash
docker run --name my-backend-container -p 5000:5000 my-backend
```

Let's break this down.

```text
docker run
```

Create and start a container.

```text
--name my-backend-container
```

Give the container a name.

```text
-p 5000:5000
```

Map:

```text
host 5000
    ↓
container 5000
```

Finally:

```text
my-backend
```

is the image to use.

So:

```text
my-backend image
       ↓
my-backend-container
       ↓
node server.js
       ↓
Express :5000
```

You've now learned the entire basic workflow:

                        │ docker build

                 ┌─────────────┐

# 24. What if your server uses `process.env.PORT`?

Your `server.js` might contain:

```js
const PORT = process.env.PORT || 5000;
```

That's good.

Then your Docker container can eventually receive:

```text
PORT=5000
```

from the environment.

For example:

```bash
docker run \
  --name my-backend-container \
  -p 5000:5000 \
  -e PORT=5000 \
  my-backend
```

Don't worry about formatting this command perfectly yet.

The important architecture is:

```text
Environment
     ↓
process.env.PORT
     ↓
Express
     ↓
5000
```

---

# 25. Development vs production

One important warning:

The Dockerfile we just created is intentionally **basic**.

It is not yet the final production Dockerfile.

Later you'll learn:

```text
23.6 → Production Dockerfile
23.7 → Development Dockerfile
```

Why separate them?

Development wants things like:

```text
hot reload
source mounting
nodemon
fast iteration
```

Production wants things like:

```text
small image
non-root user
production dependencies
predictable startup
security
```

So don't try to make one Dockerfile solve every problem immediately.

---

# 26. A common beginner mistake

Don't put this in your production Dockerfile:

```dockerfile
CMD ["npm", "run", "dev"]
```

if your dev script uses:

```text
nodemon
```

Development and production have different goals.

For production, you'll eventually want something closer to:

```dockerfile
CMD ["node", "server.js"]
```

We'll build the production version properly later.

---

# 27. Another common mistake — copying `.env`

Never casually do:

```text
COPY . .
```

while allowing:

```text
.env
```

to enter the image.

Why?

Your `.env` might contain:

```text
MONGO_URI=...
ACCESS_TOKEN_SECRET=...
REFRESH_TOKEN_SECRET=...
```

If those secrets become part of the image, you've created a serious secret-management problem.

So later we'll use:

```text
.dockerignore
```

and runtime environment configuration.

---

# 28. Another common mistake — running as root

A basic Node image may run the process with elevated privileges depending on how you configure it.

For production, you generally want:

```text
non-root user
```

Why?

If your application gets compromised, limiting its privileges reduces potential damage.

We'll handle this during the production Dockerfile lesson.

# 30. One important distinction: `RUN` vs `CMD`

This is probably the most important thing from today's lesson.

### `RUN`

Happens during **image building**.

```dockerfile
RUN npm ci
```

Flow:

```text
Dockerfile
   ↓
docker build
   ↓
RUN npm ci
   ↓
Image
```

### `CMD`

Defines the default command when the container **starts**.

```dockerfile
CMD ["node", "server.js"]
```

Flow:

```text
Image
   ↓
docker run
   ↓
CMD
   ↓
node server.js
```

Memorize:

> **RUN builds the image. CMD starts the application.**

---

# 31. Another important distinction: `COPY` vs `RUN`

### `COPY`

Moves files:

```dockerfile
COPY package*.json ./
```

Conceptually:

```text
Host
 ↓
Image
```

### `RUN`

Executes a command:

```dockerfile
RUN npm ci
```

Conceptually:

```text
Image environment
      ↓
execute command
```

So:

```text
COPY → files
RUN  → commands
```

# 32. Your mental model

When you look at:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "server.js"]
```

your brain should translate it into:

```text
START
  ↓
Give me Node
  ↓
Create/use /app
  ↓
Copy dependency definitions
  ↓
Install dependencies
  ↓
Copy application
  ↓
Application listens on 5000
  ↓
Start Node server
```

That's all a Dockerfile really is:

> **A sequence of instructions for constructing an image.**
