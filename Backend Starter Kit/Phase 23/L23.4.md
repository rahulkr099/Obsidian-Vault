# Lesson 23.4 — Docker Layers

In **23.3**, we created a basic Dockerfile:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "server.js"]
```

Now we answer a very important question:

> **Why does the order of these instructions matter?**

The answer is **Docker layers and build cache**.

Your roadmap explicitly places **23.4 Docker layers** immediately after Dockerfile, before building the Node application image.

---

# 1. What is a Docker layer?

Think of an image as a stack of layers.

```text
┌─────────────────────────────┐
│ Application code            │
├─────────────────────────────┤
│ npm dependencies            │
├─────────────────────────────┤
│ Working directory/config    │
├─────────────────────────────┤
│ Node.js base image          │
└─────────────────────────────┘
```

Each Dockerfile instruction can contribute a filesystem layer to the resulting image.

For example:

```dockerfile
FROM node:24
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
```

can be thought of roughly as:

```text
Layer 1 → Node base image
Layer 2 → /app setup
Layer 3 → package files
Layer 4 → node_modules
Layer 5 → application source
```

This layered design is one of Docker's most useful features.

---

# 2. Why does Docker use layers?

Imagine you build your backend:

```bash
docker build -t my-backend .
```

The first build may take some time because Docker has to:

```text
Download base image
        ↓
Install dependencies
        ↓
Copy application
```

Now you change one file:

```text
controllers/user.controller.js
```

You don't want Docker to unnecessarily redo:

```text
Download Node
        ↓
Install all npm packages again
```

Instead, Docker can reuse layers that haven't changed.

Conceptually:

```text
Old build

Node image       ✅ reuse
/app             ✅ reuse
package files    ✅ reuse
npm install      ✅ reuse
source code      ❌ rebuild
```

That's **build caching**.

---

# 3. The most important Docker optimization

Look at these two Dockerfiles.

### Good ordering

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "server.js"]
```

### Poor ordering

```dockerfile
FROM node:24

WORKDIR /app

COPY . .

RUN npm ci

CMD ["node", "server.js"]
```

They can produce the same application.

But the first one gives Docker a much better opportunity to reuse the dependency-installation layer.

---

# 4. Why does the first one work better?

Suppose your project is:

```text
backend/
├── package.json
├── package-lock.json
├── server.js
├── app.js
├── controllers/
├── services/
├── models/
└── routes/
```

You change:

```text
controllers/user.controller.js
```

In the optimized Dockerfile:

```dockerfile
COPY package*.json ./

RUN npm ci

COPY . .
```

The package files haven't changed.

Therefore Docker can potentially reuse:

```text
npm ci
```

and only rebuild the layer involving your source code.

Conceptually:

```text
FROM node:24       CACHE
      ↓
WORKDIR /app       CACHE
      ↓
package*.json      CACHE
      ↓
npm ci             CACHE
      ↓
source code        REBUILD
```

That's much faster.

---

# 5. What invalidates a cache layer?

Think of Docker as asking:

> "Has the input to this instruction changed?"

For example:

```dockerfile
COPY package*.json ./
```

depends on:

```text
package.json
package-lock.json
```

If neither changed:

```text
CACHE HIT
```

If you modify:

```text
package.json
```

then Docker needs to rebuild from that point onward.

So:

```text
package.json changed
        ↓
COPY package*.json
        ↓
cache invalidated
        ↓
npm ci runs again
        ↓
later layers rebuild
```

---

# 6. This is why `package.json` placement matters

Suppose you do this:

```dockerfile
COPY . .

RUN npm ci
```

Now Docker's dependency-installation step depends on your **entire source tree**.

Change:

```text
controllers/user.js
```

and Docker may have to reconsider the layer containing:

```text
RUN npm ci
```

That's unnecessary.

Instead:

```dockerfile
COPY package*.json ./

RUN npm ci

COPY . .
```

makes the dependency layer depend primarily on dependency definitions.

That's a much better design.

---

# 7. A simple analogy

Imagine building a house.

You have:

```text
Foundation
Walls
Plumbing
Furniture
```

You change the furniture.

Would you rebuild the foundation?

Obviously not.

Docker layers work with a similar idea:

```text
Foundation
   ↓
Node
   ↓
Dependencies
   ↓
Application code
```

If only application code changes:

```text
Node          → keep
Dependencies  → keep
Code          → rebuild
```

---

# 8. Docker layers are immutable-style building blocks

Once a layer is created, Docker doesn't normally modify that existing layer in place.

Instead, a new layer is created when the image is rebuilt.

Think:

```text
Build 1:

A
B
C
D
```

Then you change something affecting D:

```text
A  ← reused
B  ← reused
C  ← reused
D' ← new
```

So the image becomes:

```text
A
B
C
D'
```

This is one reason Docker images can be efficiently rebuilt.

---

# 9. Layers are also useful for image sharing

Suppose you have two applications:

```text
backend-api
admin-api
```

Both use:

```text
node:24
```

Docker can reuse common image layers.

Conceptually:

```text
          Node base layer
          /             \
         /               \
        ▼                 ▼
backend image        admin image
```

The common base doesn't need to conceptually become a completely separate copy for every image.

This helps with storage and image distribution.

---

# 10. Base images already contain layers

When you write:

```dockerfile
FROM node:24
```

you're not necessarily starting from one giant blob that you created yourself.

The base image itself is composed of layers.

Conceptually:

```text
Your image
│
├── Your application layer
├── Your dependency layer
│
└── node:24
     ├── Base filesystem layer
     ├── Runtime-related layers
     └── Other base layers
```

So Docker's layering system exists underneath your Dockerfile too.

---

# 11. Build context matters too

Remember this command:

```bash
docker build -t my-backend .
```

The:

```text
.
```

is the build context.

If your project contains:

```text
backend/
├── node_modules/
├── .git/
├── .env
├── logs/
├── src/
└── package.json
```

and you don't use `.dockerignore`, Docker may send unnecessary files as part of the build context.

That's bad for:

- build speed,
    
- image cleanliness,
    
- security.
    

So we eventually use:

```text
.dockerignore
```

For example:

```text
node_modules
.git
.env
logs
npm-debug.log
```

---

# 12. `.dockerignore` and layers

This is important:

`.dockerignore` doesn't simply mean:

> "These files won't exist anywhere."

It means they are excluded from the build context sent to Docker.

So:

```text
Project
   │
   ├── .git          ❌ ignored
   ├── node_modules  ❌ ignored
   ├── .env          ❌ ignored
   │
   └── source        ✅ included
          │
          ▼
     Build context
          │
          ▼
       Docker
```

This helps keep builds cleaner and safer.

---

# 13. Why `node_modules` should not normally be copied

Suppose your local project contains:

```text
node_modules/
```

You shouldn't normally do:

```dockerfile
COPY . .
```

and send your entire local `node_modules` into the image.

Why?

Because your local `node_modules` may have been installed for:

```text
your OS
your CPU architecture
your Node environment
```

Docker should generally install dependencies in its own environment:

```dockerfile
RUN npm ci
```

So:

```text
Local node_modules
        ❌
        │
        X
        │
Docker
        │
        ▼
npm ci
        ↓
Container-compatible dependencies
```

That's another reason `.dockerignore` commonly contains:

```text
node_modules
```

---

# 14. A cache example

Imagine your first build:

```text
Step 1: FROM node:24
        → build

Step 2: WORKDIR /app
        → build

Step 3: COPY package*.json
        → build

Step 4: RUN npm ci
        → build

Step 5: COPY source
        → build
```

Now you modify only:

```text
routes/todo.routes.js
```

Build again:

```text
Step 1: FROM node:24
        → CACHED

Step 2: WORKDIR /app
        → CACHED

Step 3: COPY package*.json
        → CACHED

Step 4: RUN npm ci
        → CACHED

Step 5: COPY source
        → REBUILD
```

This is exactly what we want.

---

# 15. What if `package.json` changes?

Suppose you install:

```bash
npm install bcrypt
```

Now:

```text
package.json
package-lock.json
```

change.

Build again:

```text
FROM node:24
        → CACHED

WORKDIR /app
        → CACHED

COPY package*.json
        → REBUILD

RUN npm ci
        → REBUILD

COPY source
        → REBUILD
```

This is correct.

Why?

Because your dependency tree actually changed.

Docker must reinstall dependencies.

---

# 16. The dependency layer

This gives us a very useful concept:

```text
Dependency layer
```

For your Node backend:

```dockerfile
COPY package*.json ./

RUN npm ci
```

creates the dependency portion of the image.

Conceptually:

```text
┌──────────────────────────────┐
│ Application source           │
├──────────────────────────────┤
│ node_modules                 │
├──────────────────────────────┤
│ Node.js base image           │
└──────────────────────────────┘
```

If only source code changes:

```text
node_modules → reuse
```

That's why this pattern is so common.

---

# 17. Don't think of every Dockerfile line as "one exact layer"

There's a subtle point here.

For learning purposes, it's useful to think:

```text
Instruction → layer
```

But Docker's modern build system can optimize and represent builds more intelligently than this simplified model.

So don't get stuck on:

> "Exactly one physical layer must exist for every single Dockerfile instruction."

The practical lesson is:

> **Docker builds images incrementally and can reuse cached build results when inputs haven't changed.**

That's the concept you need.

---

# 18. `RUN` creates build-time results

Consider:

```dockerfile
RUN npm ci
```

During the build:

```text
npm ci
   ↓
node_modules created
   ↓
result becomes part of image
```

So when you later run:

```bash
docker run my-backend
```

you don't need to execute:

```bash
npm ci
```

again.

The dependencies are already in the image.

This is one of the biggest differences between:

```text
docker build
```

and:

```text
docker run
```

---

# 19. Don't install dependencies during container startup

A beginner might try:

```dockerfile
CMD ["sh", "-c", "npm install && node server.js"]
```

That is generally a poor production design.

Why?

Every container startup could become:

```text
Start container
   ↓
Download/install packages
   ↓
Start application
```

Instead:

```text
docker build
   ↓
npm ci
   ↓
Image contains dependencies
   ↓
docker run
   ↓
node server.js
```

Much cleaner.

---

# 20. Build once, run many times

This gives us an important production mindset:

> **Build the image once, then run that image consistently.**

For example:

```text
Source
  ↓
Docker build
  ↓
backend:v1
  │
  ├── Development/testing
  ├── CI
  └── Production
```

The exact deployment workflow can vary, but immutable image artifacts are a powerful pattern.

---

# 21. Why this matters for CI/CD

Later, you'll have something like:

```text
Developer
    ↓
git push
    ↓
CI
    ├── tests
    ├── security checks
    └── docker build
             ↓
        backend image
             ↓
        image registry
             ↓
        production
```

Docker layers make repeated builds much more efficient because CI systems can reuse appropriate cached layers when configured to do so.

# 22. Layer ordering rule

For your Node backend, remember this rule:

> **Put things that change rarely before things that change frequently.**

For example:

```text
Rarely changes
      ↓
FROM node:24
      ↓
package.json
package-lock.json
      ↓
npm dependencies
      ↓
Application source
      ↓
Frequently changes
```

So:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "server.js"]
```

is a sensible starting structure.

---

# 23. What changes frequently?

Usually:

```text
controllers/
services/
routes/
models/
utils/
```

change more frequently than:

```text
package.json
package-lock.json
```

So we want:

```text
dependencies
      ↓
source code
```

not:

```text
source code
      ↓
dependencies
```

This simple ordering can make a big difference during development.

---

# 24. What happens when you add a dependency?

Suppose today:

```json
{
  "dependencies": {
    "express": "...",
    "mongoose": "..."
  }
}
```

Then tomorrow:

```bash
npm install pino
```

Now your lockfile changes.

Docker sees:

```text
package.json changed
package-lock.json changed
```

Therefore:

```text
Dependency cache
      ↓
INVALID
      ↓
npm ci
      ↓
New dependency layer
```

Exactly what we want.

---

# 25. What happens when you only change a controller?

Suppose:

```text
controllers/user.controller.js
```

changes.

But:

```text
package.json
package-lock.json
```

don't.

Then:

```text
Dependency cache
      ↓
VALID
      ↓
Reuse
      ↓
Copy new source
```

This is much faster than reinstalling all packages.

# 26. Layers and image size

Layers also influence image size.

If you create unnecessary files during the build and leave them inside the resulting image, your image can become larger.

For example, imagine:

```dockerfile
RUN apt-get update
RUN apt-get install something
RUN rm -rf /var/lib/apt/lists/*
```

Depending on how the build is structured, simply creating files in one layer and deleting them in a later layer doesn't necessarily mean those bytes never existed in earlier image history.

This is why production Dockerfiles need careful construction.

We'll go deeper into image size and production optimization in:

**23.5 — Node Application Image**

and especially:

**23.6 — Production Dockerfile**.

---

# 27. A common mistake

Don't do this:

```dockerfile
FROM node:24

WORKDIR /app

COPY . .

RUN npm ci
```

just because it's shorter.

It's not necessarily "wrong" for every situation, but for your backend it throws away an important caching opportunity.

Prefer:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .
```

---

# 28. Another common mistake

Don't manually delete Docker cache every time something changes.

For example, beginners sometimes think:

```bash
docker system prune
```

is required whenever they modify code.

Usually it isn't.

Docker's caching mechanism is supposed to determine what can be reused.

If you intentionally need a clean rebuild, that's different.

For example:

```bash
docker build --no-cache -t my-backend .
```

This tells Docker:

> Don't use the normal build cache for this build.

Use that intentionally, not as your default workflow.

---

# 29. `--no-cache`

This command:

```bash
docker build --no-cache -t my-backend .
```

can be useful when you suspect:

```text
stale cached build
```

But remember:

```text
normal build
    ↓
use cache when possible

--no-cache
    ↓
rebuild without normal cache reuse
```

Don't make `--no-cache` your everyday solution.

It makes builds slower.

---

# 30. Layer caching vs runtime caching

Don't confuse these two:

### Docker build cache

```text
docker build
      ↓
reuse previous build results
```

### Application/runtime cache

```text
Node application
      ↓
Redis / memory / database cache
```

They are completely different concepts.

Docker layer caching helps **builds**.

Redis, memory caches, etc. help **application runtime performance**.

# 31. Your backend image as a stack

At this stage, visualize your image like this:

```text
                 YOUR IMAGE
┌────────────────────────────────┐
│ Application source             │
├────────────────────────────────┤
│ npm dependencies               │
├────────────────────────────────┤
│ Working environment            │
├────────────────────────────────┤
│ Node.js base image             │
└────────────────────────────────┘
```

When source changes:

```text
┌────────────────────────────────┐
│ NEW Application source         │ ← rebuild
├────────────────────────────────┤
│ npm dependencies               │ ← reuse
├────────────────────────────────┤
│ Working environment            │ ← reuse
├────────────────────────────────┤
│ Node.js base image             │ ← reuse
└────────────────────────────────┘
```

When dependencies change:

```text
┌────────────────────────────────┐
│ NEW Application source         │ ← rebuild
├────────────────────────────────┤
│ NEW npm dependencies           │ ← rebuild
├────────────────────────────────┤
│ Working environment            │ ← reuse
├────────────────────────────────┤
│ Node.js base image             │ ← reuse
└────────────────────────────────┘
```

This is the core idea.

# 34. The 5 things to remember

If you remember nothing else from this lesson, remember these:

### 1. Images are built in layers

```text
Base
 ↓
Dependencies
 ↓
Application
```

### 2. Docker can reuse cached build results

```text
unchanged input
     ↓
reuse cache
```

### 3. Dependency files should usually be copied before source code

```dockerfile
COPY package*.json ./
RUN npm ci
COPY . .
```

### 4. Frequently changing files should generally come later

```text
rare changes
    ↓
frequent changes
```

### 5. Build-time dependencies belong in the image build

```text
docker build
    ↓
npm ci
    ↓
image
    ↓
docker run
    ↓
node server.js
```
