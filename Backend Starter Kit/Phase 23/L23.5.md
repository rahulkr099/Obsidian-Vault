# Lesson 23.5 — Node Application Image

In **23.3**, we learned how to write a Dockerfile.

In **23.4**, we learned why the order of instructions matters because of layers and caching.

Now we're going to apply those ideas specifically to your **Node/Express backend**.

The roadmap defines **23.5 as "Node application image"**, followed by production and development Dockerfiles.

---

# 1. What are we building?

Our goal is:

```text
Node + Express backend
          ↓
      Dockerfile
          ↓
     Docker Image
          ↓
   Backend Container
```

The image should contain everything required to **run the application**, but it should not contain unnecessary development files or secrets.

For example:

```text
┌─────────────────────────────────┐
│       Backend Docker Image      │
│                                 │
│ Node.js                         │
│ npm dependencies                │
│ Express application             │
│ Startup command                 │
└─────────────────────────────────┘
```

# 4. What should NOT normally be inside?

You don't want unnecessary files such as:

```text
.git/
.env
node_modules/        ← local copy
tests/               ← depending on image purpose
coverage/
logs/
README files
temporary files
```

Some of these may be useful in specialized build/test images, but they don't generally belong in your final runtime image.

This is where `.dockerignore` becomes important.

---

# 5. Create `.dockerignore`

At the same level as your Dockerfile:

```text
backend/
├── Dockerfile
├── .dockerignore
├── package.json
└── ...
```

Create:

```text
.dockerignore
```

A reasonable starting point:

```text
node_modules
.git
.gitignore
.env
.env.*
coverage
npm-debug.log
Dockerfile*
docker-compose*
```

Be careful with:

```text
.env.example
```

You may want to keep that file available as documentation.

So instead of blindly ignoring every `.env*`, you can use a more selective pattern depending on your project.

For example:

```text
.env
.env.local
.env.development
.env.production
```

while keeping:

```text
.env.example
```

---

# 6. Why `.dockerignore` matters

Suppose your local project contains:

```text
backend/
├── node_modules/       400 MB
├── .git/               large
├── .env                secrets
├── src/
└── package.json
```

Without `.dockerignore`:

```text
Build context
     ↓
potentially huge
     ↓
Docker
```

With `.dockerignore`:

```text
node_modules  ❌
.git          ❌
.env          ❌
coverage      ❌

source        ✅
package.json  ✅
```

So:

```text
Smaller build context
        +
Less accidental data
        +
Faster builds
```

# 7. The basic Node Dockerfile

Now let's create:

```text
Dockerfile
```

Start with:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "server.js"]
```

This is our basic Node application image.

Let's understand it specifically for your backend.

---

# 8. `FROM node:24`

```dockerfile
FROM node:24
```

Your application requires Node.js.

Instead of installing Node manually:

```text
apt install...
download...
configure...
```

we use an existing Node image.

```text
node:24
   ↓
Node runtime
   ↓
Your application
```

---

# 9. Choosing the Node image variant

You may see variants such as:

```text
node:24
node:24-bookworm
node:24-slim
node:24-alpine
```

Don't assume they're interchangeable.

They have different tradeoffs involving:

- image size,
    
- available system libraries,
    
- compatibility,
    
- debugging convenience,
    
- native Node modules.
    

For your first application image, a standard Debian-based Node image is a straightforward learning choice.

Later, when we optimize production images, we'll discuss `slim` and other variants.

---

# 10. Why not immediately use Alpine?

You'll often see tutorials saying:

```dockerfile
FROM node:24-alpine
```

because Alpine images can be small.

That's attractive.

But smaller doesn't automatically mean better.

Native dependencies can introduce compatibility issues depending on the libraries you're using.

For learning:

```dockerfile
FROM node:24
```

is easier to reason about.

Once the application works, we can optimize.

This is a good engineering principle:

> **First make the container correct; then make it smaller.**

# 13. Install dependencies

```dockerfile
RUN npm ci
```

Docker executes:

```bash
npm ci
```

inside the image build environment.

After this:

```text
/app/
├── node_modules/
├── package.json
└── package-lock.json
```

Your dependencies are now part of the image.

---

# 14. Why `npm ci` is important here

You have:

```text
package.json
package-lock.json
```

The lockfile describes the exact dependency tree expected by the project.

So:

```text
package-lock.json
       ↓
npm ci
       ↓
node_modules
```

This gives us more reproducible builds than relying on a fresh dependency resolution every time.


Your backend is now inside the image.

# 16. `EXPOSE 5000`

```dockerfile
EXPOSE 5000
```

This communicates:

> The application expects to listen on port 5000 inside the container.

But remember:

```text
EXPOSE ≠ publish port
```

To access it from your host:

```bash
docker run -p 5000:5000 my-backend
```

The flow becomes:

```text
Browser
   ↓
localhost:5000
   ↓
Host port 5000
   ↓
Container port 5000
   ↓
Express
```

---

# 17. Your Express server must listen correctly

Here's something very important when containerizing Node applications.

Suppose you have:

```js
app.listen(PORT, () => {
    console.log(`Server running on ${PORT}`);
});
```

Depending on how the server is configured, you want it reachable from outside the container.

A common safe pattern is:

```js
const server = app.listen(PORT, "0.0.0.0", () => {
    console.log(`Server running on port ${PORT}`);
});
```

Why?

Because:

```text
0.0.0.0
```

means:

> Listen on all network interfaces available to the container.

If the application only listens on a loopback interface, external connections through Docker port mapping can fail.

# 18. `CMD`

Finally:

```dockerfile
CMD ["node", "server.js"]
```

When Docker starts your container:

```text
Image
 ↓
Container
 ↓
node server.js
 ↓
Express starts
```

Your Node process becomes the main application process.

This is exactly what we want for a simple backend container.

# 25. Why containers sometimes immediately stop

Suppose you have:

```dockerfile
CMD ["node", "server.js"]
```

and `server.js` crashes:

```text
node server.js
     ↓
error
     ↓
process exits
     ↓
container stops
```

Then:

```bash
docker ps
```

may show nothing.

But:

```bash
docker ps -a
```

will show the stopped container.

Then:

```bash
docker logs my-backend-container
```

will usually reveal the actual problem.

This is a very useful debugging workflow.

---

# 26. Common mistake: wrong `CMD`

Suppose your project actually has:

```text
server.js
```

but your Dockerfile says:

```dockerfile
CMD ["node", "app.js"]
```

and `app.js` isn't the startup file.

The container may fail immediately.

Always verify:

```text
Dockerfile CMD
       ↓
actual startup file
```

For your architecture:

```text
app.js
```

usually assembles Express.

```text
server.js
```

usually starts it.

So:

```dockerfile
CMD ["node", "server.js"]
```

is the logical startup command if your project follows that structure.

---

# 27. Common mistake: wrong port

Suppose:

```env
PORT=5000
```

but Docker is run with:

```bash
docker run -p 3000:5000 my-backend
```

That's actually valid.

It means:

```text
localhost:3000
       ↓
container:5000
```

So you would access:

```text
http://localhost:3000
```

This is a useful distinction:

```text
-p HOST:CONTAINER
```

Example:

```text
-p 3000:5000
```

means:

```text
Host 3000
   ↓
Container 5000
```

# 28. Environment variables at runtime

Don't hard-code production configuration into the image.

Your application might have:

```js
const PORT = process.env.PORT || 5000;
```

Then run:

```bash
docker run \
  --name my-backend-container \
  -p 5000:5000 \
  -e PORT=5000 \
  my-backend
```

Now:

```text
Docker environment
      ↓
PORT=5000
      ↓
process.env.PORT
      ↓
Express
```

We'll study proper environment management in **23.12**.

# 30. Why one container per major service?

You might wonder:

> Why not install MongoDB inside the Node container?

You could technically build a giant container, but it's generally a poor architecture.

Instead:

```text
Node container
    ↓
Node application

MongoDB container
    ↓
MongoDB
```

Each service has a clear responsibility.

This gives us:

```text
Independent lifecycle
Independent scaling
Independent configuration
Clear networking
Easier maintenance
```

# 33. Development source code vs image source code

This is a very important distinction.

During development:

```text
Your editor
   ↓
Local source code
   ↓
Container
```

You may use bind mounts and hot reload.

During production:

```text
Git
 ↓
Build
 ↓
Docker image
 ↓
Container
```

The container should not depend on your development machine's source directory.

That's why we'll have separate:

```text
Dockerfile
Dockerfile.dev
```

later.

---

# 34. Don't rebuild for every request

Obviously:

```text
HTTP request
   ↓
docker build
```

is wrong.

The normal lifecycle is:

```text
Code changes
   ↓
docker build
   ↓
new image
   ↓
run container
   ↓
many requests
```

During development, hot reload can be used to avoid rebuilding the entire image for every code change.

We'll cover that in **23.7**.

# 36. A better version using npm scripts

Instead of:

```dockerfile
CMD ["node", "server.js"]
```

you could technically use:

```dockerfile
CMD ["npm", "start"]
```

if your `package.json` contains:

```json
{
  "scripts": {
    "start": "node server.js"
  }
}
```

Both approaches can work.

For a simple production runtime, I generally prefer making the actual process explicit:

```dockerfile
CMD ["node", "server.js"]
```

because it's immediately clear what process the container is running.

But using the npm script can be useful if your startup command is intentionally centralized in `package.json`.

The important thing is consistency.

# 37. What about `npm start`?

If you use:

```dockerfile
CMD ["npm", "start"]
```

then:

```text
Docker
 ↓
npm
 ↓
node server.js
```

If you use:

```dockerfile
CMD ["node", "server.js"]
```

then:

```text
Docker
 ↓
node server.js
```

The latter gives you a simpler process chain.

This becomes relevant when we discuss signals and graceful shutdown.

# 38. The image should be reproducible

Suppose you give the Dockerfile to another developer.

They should be able to run:

```bash
docker build -t my-backend .
```

and get essentially the same application environment.

That's the point.

Instead of:

```text
Rahul's machine
Node version X
Mongo version Y
npm state Z
```

we aim for:

```text
Dockerfile
   ↓
Known base image
   ↓
Known dependencies
   ↓
Known application
```

# 40. Useful cleanup commands

When you're experimenting:

Stop:

```bash
docker stop my-backend-container
```

Remove:

```bash
docker rm my-backend-container
```

Remove image:

```bash
docker rmi my-backend
```

Then rebuild:

```bash
docker build -t my-backend .
```

Don't blindly run cleanup commands like:

```bash
docker system prune -a
```

while learning. They can remove more Docker resources than you intended.
