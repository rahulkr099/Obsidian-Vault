# Lesson 23.6 — Production Dockerfile

The roadmap places **23.6 Production Dockerfile** immediately after the Node application image and before the development Dockerfile.

In **23.5**, we built a basic image:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "server.js"]
```

That works.

But a **production Dockerfile** has a different goal:

> Build an image that contains only what the production application needs, while improving security, reproducibility, size, and startup behavior.

---

# 1. Development image vs production image

This distinction is extremely important.

### Development

You want:

```text
Fast code changes
Hot reload
Debugging
Development dependencies
Source mounting
```

### Production

You want:

```text
Small image
Only required dependencies
No secrets
No unnecessary tools
Non-root execution
Predictable startup
Reproducible build
```

So:

```text
Development
     ↓
Dockerfile.dev

Production
     ↓
Dockerfile
```

The roadmap explicitly separates these into **23.6 Production Dockerfile** and **23.7 Development Dockerfile**.

---

# 2. What makes a Dockerfile production-oriented?

There are several important ideas:

```text
Production Dockerfile
│
├── Reproducible dependencies
├── Smaller runtime
├── Multi-stage build
├── Non-root user
├── No secrets
├── Correct signal handling
├── Minimal unnecessary files
└── Predictable startup
```

We'll build these one by one.

---

# 3. First improvement: `npm ci --omit=dev`

Your development dependencies might include:

```json
{
  "devDependencies": {
    "nodemon": "...",
    "jest": "...",
    "supertest": "..."
  }
}
```

Your production server doesn't normally need:

```text
nodemon
Jest
Supertest
```

So production can install only production dependencies:

```bash
npm ci --omit=dev
```

Instead of:

```bash
npm ci
```

Conceptually:

```text
package.json
     │
     ├── dependencies
     │      ↓
     │   production
     │
     └── devDependencies
            ↓
       development only
```

---

# 4. Why not simply use `npm install`?

For production builds, prefer:

```bash
npm ci
```

when you have a lockfile.

It is designed for clean, reproducible dependency installation.

For example:

```dockerfile
RUN npm ci --omit=dev
```

means:

> Install dependencies exactly according to the lockfile, excluding development dependencies.

---

# 5. Multi-stage builds

Now we reach one of the most useful Docker techniques:

> **Multi-stage builds.**

Instead of having one stage do everything, we can use separate stages.

For example:

```text
Stage 1
Build environment
      ↓
install dependencies
prepare application
      ↓
Stage 2
Runtime environment
      ↓
only what production needs
```

Conceptually:

```text
┌─────────────────────────┐
│      Build Stage        │
│                         │
│ Node                    │
│ npm                     │
│ dependencies            │
│ source                  │
│ build tools             │
└────────────┬────────────┘
             │
             ▼
      selected output
             │
             ▼
┌─────────────────────────┐
│      Runtime Stage      │
│                         │
│ Node                    │
│ production dependencies │
│ application             │
└─────────────────────────┘
```

This can significantly improve the final image for applications that actually have a separate build step.

---

# 6. Does our Express backend need a build stage?

Not necessarily.

This is an important engineering point.

If your backend is plain JavaScript:

```text
server.js
controllers/
services/
routes/
```

and Node executes it directly:

```bash
node server.js
```

there may be no compilation step.

You don't need to invent a complicated build process just because Docker supports multi-stage builds.

However, multi-stage builds are useful when you need to:

- compile TypeScript,
    
- build frontend assets,
    
- compile native components,
    
- install build-time tooling,
    
- separate build dependencies from runtime dependencies.
    

So don't use multi-stage builds as a ritual.

Use them when they solve a problem.

---

# 7. A production-oriented JavaScript Dockerfile

For a plain JavaScript backend, we can start with:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY . .

ENV NODE_ENV=production

EXPOSE 5000

CMD ["node", "server.js"]
```

This is already better than our basic image.

Let's examine the changes.

---

# 8. `NODE_ENV=production`

We add:

```dockerfile
ENV NODE_ENV=production
```

Now inside Node:

```js
process.env.NODE_ENV
```

will be:

```text
production
```

This lets your application distinguish environments.

For example:

```js
if (process.env.NODE_ENV === "production") {
    // production behavior
}
```

But remember:

> `NODE_ENV` is configuration, not a secret.

A secret like:

```text
JWT_SECRET
MONGO_URI
```

should **not** be baked into the image.

---

# 9. Never put secrets in the Dockerfile

Do NOT do:

```dockerfile
ENV JWT_SECRET=my-super-secret-key
```

or:

```dockerfile
ENV MONGO_URI=mongodb://user:password@...
```

Why?

Because the image becomes associated with those values.

Instead:

```text
Image
  ↓
generic application
  ↓
Runtime environment
  ↓
secrets injected
```

For example:

```bash
docker run \
  -e MONGO_URI="..." \
  -e ACCESS_TOKEN_SECRET="..." \
  my-backend
```

We'll study environment variables properly in **23.12**.

---

# 10. The production image should be environment-independent

Think:

```text
Same image
   │
   ├── staging
   │
   ├── production
   │
   └── testing
```

Configuration changes.

The application artifact doesn't need to.

For example:

```text
Image:
my-backend:1.0.0
```

Staging:

```text
MONGO_URI → staging database
```

Production:

```text
MONGO_URI → production database
```

The image remains the same.

This is a powerful deployment principle.

---

# 11. Run as a non-root user

This is one of the most important production improvements.

Containers can run processes as:

```text
root
```

or:

```text
non-root user
```

Running your application as root gives the process more privileges than it normally needs.

Instead, use a non-root user.

The official Node image provides a `node` user in its standard variants.

We can use:

```dockerfile
USER node
```

But there is an important detail.

Before switching users, make sure the application directory has appropriate ownership/permissions.

For example:

```dockerfile
FROM node:24

WORKDIR /app

COPY --chown=node:node package*.json ./

RUN npm ci --omit=dev

COPY --chown=node:node . .

ENV NODE_ENV=production

USER node

EXPOSE 5000

CMD ["node", "server.js"]
```

Now the application process isn't running as root.

---

# 12. Why `--chown=node:node`?

Consider:

```dockerfile
COPY --chown=node:node . .
```

This copies the application files and gives ownership to:

```text
node:node
```

Then:

```dockerfile
USER node
```

switches the process to that user.

So:

```text
Files
  ↓
owned by node
  ↓
Node process
  ↓
runs as node
```

This avoids many permission problems.

---

# 13. Security benefit

Imagine your application gets compromised.

If the Node process is running as root:

```text
Attacker
   ↓
compromised Node process
   ↓
root privileges
```

That's a much worse situation.

If it runs as an unprivileged user:

```text
Attacker
   ↓
compromised Node process
   ↓
limited user privileges
```

It's not a complete security solution.

But it is **defense in depth**.

This fits directly with the security engineering you've already studied.

---

# 14. Production Dockerfile version

For our current plain-JavaScript backend, a strong starting point is:

```dockerfile
FROM node:24

WORKDIR /app

COPY --chown=node:node package*.json ./

RUN npm ci --omit=dev

COPY --chown=node:node . .

ENV NODE_ENV=production

USER node

EXPOSE 5000

CMD ["node", "server.js"]
```

Let's understand the complete flow:

```text
FROM
 ↓
WORKDIR
 ↓
package files
 ↓
production dependencies
 ↓
application source
 ↓
production environment
 ↓
non-root user
 ↓
port metadata
 ↓
start Node
```

---

# 15. But there's still a problem

Look carefully.

We do:

```dockerfile
COPY --chown=node:node . .
```

That means everything not excluded by `.dockerignore` enters the image.

So your `.dockerignore` becomes very important.

A reasonable production-oriented one might contain:

```text
node_modules
.git
.env
.env.*
coverage
tests
*.log
npm-debug.log
Dockerfile*
docker-compose*
```

But don't blindly exclude something your production application actually needs.

For example, if your runtime requires email templates:

```text
mail/templates/
```

those must remain in the image.

---

# 16. Production image is not "copy only JavaScript"

Don't misunderstand minimalism.

Suppose your backend has:

```text
mail/
├── mailSender.js
├── renderTemplate.js
└── templates/
    ├── welcome.ejs
    └── reset-password.ejs
```

If your application renders those templates at runtime, they are production files.

So they need to be included.

Production means:

> **Only include what the runtime needs.**

Not:

> **Only include `.js` files.**

---

# 17. What about tests?

Your production runtime usually doesn't need:

```text
tests/
```

So you can exclude them.

But your CI pipeline may need tests **before** building the production image.

A good flow is:

```text
Git push
   ↓
Install dependencies
   ↓
Run tests
   ↓
Security checks
   ↓
Build production image
   ↓
Deploy
```

Not:

```text
Production container
   ↓
Run Jest
```

Keep responsibilities separate.

---

# 18. Production dependencies vs development dependencies

Think of your `package.json` as:

```text
dependencies
│
├── express
├── mongoose
├── jsonwebtoken
├── bcrypt
└── ...
        ↓
     runtime

devDependencies
│
├── nodemon
├── jest
├── supertest
└── ...
        ↓
 development / CI
```

So:

```dockerfile
RUN npm ci --omit=dev
```

creates a cleaner runtime.

---

# 19. Why smaller images matter

Smaller images can provide:

```text
Faster image transfer
Faster deployment
Less storage
Smaller attack surface
Less unnecessary software
```

Imagine:

```text
500 MB image
```

versus:

```text
150 MB image
```

When deploying repeatedly, transferring the smaller artifact can save time and bandwidth.

But don't sacrifice correctness just to chase an arbitrary image-size number.

---

# 20. `node:24` vs `node:24-slim`

Later you might change:

```dockerfile
FROM node:24
```

to:

```dockerfile
FROM node:24-slim
```

This can reduce the base image footprint.

But test your application.

Some Node packages depend on native system libraries.

For example, packages involving:

```text
native compilation
image processing
cryptography
database drivers
```

may have additional system requirements.

So the workflow should be:

```text
Correct image
   ↓
Measure
   ↓
Optimize
   ↓
Test
   ↓
Deploy
```

not:

```text
Smallest possible image
   ↓
hope it works
```

---

# 21. Why pinning versions matters

You currently have:

```dockerfile
FROM node:24
```

This is convenient.

But a production environment benefits from controlled versions.

You should think about:

```text
Node version
Base image version
Dependency versions
```

being reproducible.

For example, you might eventually pin a specific Node image digest:

```dockerfile
FROM node:24@sha256:<digest>
```

A digest identifies an exact image content.

This is more reproducible than a floating tag.

However, it adds maintenance because you must intentionally update the digest.

For your learning project:

```dockerfile
FROM node:24
```

is perfectly reasonable.

---

# 22. Don't run `npm install` during startup

Production:

```text
Build
 ↓
npm ci --omit=dev
 ↓
Image
 ↓
Container
 ↓
node server.js
```

Not:

```text
Container starts
 ↓
npm install
 ↓
internet
 ↓
download dependencies
 ↓
start application
```

The second design makes startup slower and less predictable.

Your production backend image should remain:

```text

+

```

MongoDB is a separate service.

# 24. Production startup

Your current command:

```dockerfile
CMD ["node", "server.js"]
```

is good because it directly launches Node.

The container lifecycle becomes:

```text
Container starts
      ↓
node server.js
      ↓
Application starts
      ↓
MongoDB connection
      ↓
HTTP server
      ↓
Requests
```

Your application should also handle shutdown properly.

That's **23.14 Graceful shutdown** later in the phase.

# 25. What about signals?

Containers need to respond properly to signals such as:

```text
SIGTERM
```

This becomes important during deployments.

For example:

```text
Old container
     ↓
SIGTERM
     ↓
stop accepting new work
     ↓
finish current work
     ↓
close database
     ↓
exit
```

That's why the actual Node process and process management matter.

We'll study this properly in 23.14 instead of trying to solve everything inside today's Dockerfile.

# 26. Multi-stage Dockerfile example

Now let's see the pattern even though our current JS backend may not require it.

Suppose later your backend becomes TypeScript:

```text
src/
   ↓
TypeScript compiler
   ↓
dist/
   ↓
Node runtime
```

Then:

```dockerfile
FROM node:24 AS build

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM node:24-slim AS production

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=build /app/dist ./dist

ENV NODE_ENV=production

USER node

EXPOSE 5000

CMD ["node", "dist/server.js"]
```

Now look at the separation:

```text
BUILD STAGE
───────────
TypeScript
Compiler
Dev dependencies
Source
    │
    ▼
  dist/
    │
    ▼
RUNTIME STAGE
─────────────
Node
Production dependencies
dist/
```

The runtime image doesn't need:

```text
TypeScript source
TypeScript compiler
Jest
other build tools
```

That's the real power of multi-stage builds.

---

# 27. Why multi-stage builds are powerful

Without multi-stage:

```text
Final image
│
├── source
├── compiler
├── build tools
├── dev dependencies
└── runtime
```

With multi-stage:

```text
Final image
│
├── runtime
├── production dependencies
└── built application
```

So:

```text
Build environment
       ≠
Runtime environment
```

This separation is a major production Docker pattern.

---

# 28. Don't blindly copy `node_modules` from another stage

You may see tutorials doing:

```dockerfile
COPY --from=build /app/node_modules ./node_modules
```

Sometimes that's valid.

But it depends on how dependencies were installed and whether native modules are compatible with the runtime image.

For example:

```text
Build image
    ↓
native dependency compiled against environment A

Runtime image
    ↓
environment B
```

can cause problems.

A safe strategy is often to install production dependencies in the runtime stage itself when appropriate:

```dockerfile
RUN npm ci --omit=dev
```

Again:

> Correctness first, optimization second.

---

# 29. Production Dockerfile with a separate build stage

For a plain JavaScript project, a multi-stage approach could still separate dependency preparation, but it isn't automatically better.

For example:

```dockerfile
FROM node:24 AS deps

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev


FROM node:24-slim AS production

WORKDIR /app

COPY --from=deps /app/node_modules ./node_modules
COPY --chown=node:node . .

ENV NODE_ENV=production

USER node

EXPOSE 5000

CMD ["node", "server.js"]
```

This can be useful, but notice the complexity.

For our current backend:

```dockerfile
FROM node:24
...
RUN npm ci --omit=dev
...
```

is easier and may be completely sufficient.

Don't optimize architecture beyond the problem you're solving.

# 32. Build it

Run:

```bash
docker build -t my-backend:production .
```

Notice we're using a more meaningful tag:

```text
my-backend:production
```

instead of just:

```text
my-backend
```

You can also use version tags:

```bash
docker build -t my-backend:1.0.0 .
```

Later you'll learn proper image versioning and registries.

# 39. The deeper lesson

The most important thing from this lesson isn't the Dockerfile itself.

It's this principle:

> **A production image should contain the smallest, safest, most reproducible environment needed to run the application.**

That leads naturally to:

```text
No secrets
     ↓
Production dependencies only
     ↓
Minimal files
     ↓
Non-root user
     ↓
Predictable startup
     ↓
Reproducible image
```

This is exactly the kind of production thinking your backend roadmap is trying to develop.
