# Lesson 23.7 — Development Dockerfile

The roadmap defines **23.7 as Development Dockerfile**, directly after the production Dockerfile. The purpose of this lesson is to understand how Docker should support **development**, rather than trying to use your production container for everything.

In **23.6**, our production-oriented setup was:

```text
Source
  ↓
Docker build
  ↓
Production image
  ↓
Container
  ↓
node server.js
```

Development has a different problem:

```text
You edit code
     ↓
You want container to see the change
     ↓
You don't want to rebuild the image every time
     ↓
Application restarts automatically
```

That is what we'll build.

---

# 1. Production vs Development

Think of them as two different environments.

### Production

```text
Code
 ↓
Build image
 ↓
Run image
 ↓
Application
```

The image is the application artifact.

### Development

```text
Your source code
      ↓
  bind mount
      ↓
Container
      ↓
nodemon
      ↓
restart application
```

The important difference is:

> **In development, your source code remains outside the image and is mounted into the container.**

---

# 2. Why not use the production Dockerfile?

Imagine you're editing:

```text
controllers/user.controller.js
```

If you use the production workflow, you'd have to:

```bash
docker build -t my-backend .
```

after every change.

Then:

```bash
docker stop ...
docker rm ...
docker run ...
```

That's terrible for development.

Instead:

```text
Edit file
   ↓
Docker volume sees change
   ↓
nodemon sees change
   ↓
Node restarts
```

Much better.

---

# 3. What does our development environment need?

We want:

```text
Node.js
npm
Development dependencies
Application source
nodemon
Source-code mounting
```

Unlike production, we **do want** development dependencies.

For example:

```json
{
  "devDependencies": {
    "nodemon": "...",
    "jest": "...",
    "supertest": "..."
  }
}
```

Production:

```bash
npm ci --omit=dev
```

Development:

```bash
npm ci
```

That's one of the biggest differences.

---

# 4. Create `Dockerfile.dev`

Your project can now contain:

```text
backend/
├── Dockerfile
├── Dockerfile.dev
├── .dockerignore
├── package.json
├── package-lock.json
└── ...
```

Where:

```text
Dockerfile
    ↓
Production

Dockerfile.dev
    ↓
Development
```

---

# 5. Basic development Dockerfile

Start with:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["npm", "run", "dev"]
```

Assuming your `package.json` contains:

```json
{
  "scripts": {
    "dev": "nodemon server.js"
  }
}
```

the flow is:

```text
Docker
 ↓
npm run dev
 ↓
nodemon server.js
 ↓
Node
 ↓
Express
```

---

# 6. Why `npm ci` instead of `npm ci --omit=dev`?

Because development needs development dependencies.

Your project may have:

```text
dependencies
├── express
├── mongoose
├── cors
└── ...

devDependencies
├── nodemon
├── jest
└── supertest
```

Development needs:

```text
dependencies
+
devDependencies
```

Therefore:

```dockerfile
RUN npm ci
```

Production needs:

```text
dependencies
```

Therefore:

```dockerfile
RUN npm ci --omit=dev
```

---

# 7. But there is a problem with this Dockerfile

Consider:

```dockerfile
COPY . .
```

During image creation, your source code is copied into the image.

That's okay.

But we don't actually want to rebuild the image every time the source changes.

Instead, we'll override the application source with a **bind mount** when the container runs.

---

# 8. What is a bind mount?

A bind mount connects a directory on your computer to a directory inside the container.

For example:

```text
Your computer
────────────────
backend/
├── server.js
├── routes/
├── controllers/
└── services/
        │
        │ bind mount
        ▼
Container
────────────────
/app/
├── server.js
├── routes/
├── controllers/
└── services/
```

Now both refer to the same source files.

So when you edit:

```text
backend/server.js
```

the container sees the change.

---

# 9. The development flow

Now imagine:

```text
You
 ↓
edit server.js
 ↓
host filesystem changes
 ↓
bind mount
 ↓
/app/server.js changes
 ↓
nodemon detects change
 ↓
Node restarts
```

No image rebuild.

That's the key idea of development Docker.

---

# 10. Run with a bind mount

You can run:

```bash
docker run \
  --name my-backend-dev \
  -p 5000:5000 \
  -v "$(pwd):/app" \
  my-backend-dev
```

The important part:

```bash
-v "$(pwd):/app"
```

means:

```text
Current directory
       ↓
     /app
```

inside the container.

---

# 11. But there's another problem: `node_modules`

This is where beginners often get confused.

Suppose your host has:

```text
backend/
├── node_modules/
├── package.json
└── server.js
```

and we mount:

```bash
-v "$(pwd):/app"
```

The host directory can hide the `/app` directory that was created in the image.

That can cause:

```text
/app/node_modules
```

from the image to become inaccessible.

Then the container might say:

```text
Cannot find module 'express'
```

even though you ran:

```dockerfile
RUN npm ci
```

during the image build.

---

# 12. Anonymous volume for `node_modules`

A common development pattern is:

```bash
docker run \
  --name my-backend-dev \
  -p 5000:5000 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  my-backend-dev
```

Now:

```text
Host source
    ↓
/app

Container-managed node_modules
    ↓
/app/node_modules
```

So:

```text
/app
├── server.js       ← host
├── controllers/    ← host
├── services/       ← host
└── node_modules/   ← container
```

This separation is very useful.

---

# 13. Why shouldn't we mount host `node_modules`?

Because native Node modules can depend on the operating environment.

For example:

```text
Host:
Linux environment

Container:
different Linux userspace/runtime
```

Or:

```text
Host:
Windows

Container:
Linux
```

A host `node_modules` directory may not be appropriate inside the container.

Better:

```text
Source code
    → host

Dependencies
    → container
```

---

# 14. A better development command

So our development container can be started with:

```bash
docker run \
  --name my-backend-dev \
  -p 5000:5000 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  my-backend-dev
```

Now:

```text
Host
│
│ source files
▼
Container /app
│
├── source
├── routes
├── controllers
├── services
└── node_modules
```

---

# 15. `nodemon` does the rest

Your package script:

```json
{
  "scripts": {
    "dev": "nodemon server.js"
  }
}
```

runs:

```text
npm run dev
     ↓
nodemon server.js
     ↓
watch files
```

Suppose you change:

```js
console.log("Hello");
```

to:

```js
console.log("Hello Docker");
```

The flow is:

```text
Save file
 ↓
Host file changes
 ↓
Bind mount
 ↓
Container sees change
 ↓
nodemon detects change
 ↓
Node restarts
```

---

# 16. This is the key development architecture

Memorize this:

```text
             YOUR MACHINE
                  │
                  │ bind mount
                  ▼
          ┌──────────────────┐
          │    CONTAINER     │
          │                  │
          │ /app             │
          │                  │
          │ source code ◄────┤
          │                  │
          │ node_modules     │
          │                  │
          │ nodemon          │
          │      ↓           │
          │ node server.js   │
          └──────────────────┘
```

This is fundamentally different from the production image.

---

# 17. Production vs development comparison

|Feature|Production|Development|
|---|---|---|
|Dockerfile|`Dockerfile`|`Dockerfile.dev`|
|Dependencies|production only|all|
|`npm ci`|`--omit=dev`|normal|
|Source|copied into image|bind mounted|
|Hot reload|usually no|yes|
|nodemon|no|yes|
|Dev tools|no|yes|
|Image rebuild on code change|normally required|no|
|Main goal|reliability|productivity|

---

# 18. Don't put `nodemon` in production

This is an important mistake.

Don't do:

```dockerfile
CMD ["npm", "run", "dev"]
```

for your production image.

Because:

```text
nodemon
```

exists to watch development files and restart your process.

Production should normally simply run:

```dockerfile
CMD ["node", "server.js"]
```

So:

```text
Development
    ↓
nodemon

Production
    ↓
node
```

---

# 19. Development Dockerfile vs production Dockerfile

### Production

```dockerfile
FROM node:24

WORKDIR /app

COPY --chown=node:node package*.json ./

RUN npm ci --omit=dev

COPY --chown=node:node . .

ENV NODE_ENV=production

USER node

EXPOSE 5000

CMD ["node", "server.js"]
```

### Development

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["npm", "run", "dev"]
```

Notice the intentional differences.

---

# 20. Why development doesn't need the non-root setup yet?

It **can** use a non-root user.

But during development, you'll often have additional filesystem and tooling concerns.

For example:

```text
bind mounts
file permissions
debugging
package installation
editor integration
```

So we can first learn the clean development workflow, then tighten it where appropriate.

Security still matters.

This isn't saying:

> "Run development containers as root forever."

It's saying:

> "Understand the development workflow first; then harden it."

---

# 21. Environment variables

Development often needs:

```text
NODE_ENV=development
PORT=5000
MONGO_URI=...
```

You can pass them at runtime:

```bash
docker run \
  -e NODE_ENV=development \
  -e PORT=5000 \
  ...
```

Or later use an environment file:

```bash
docker run --env-file .env ...
```

However:

> Don't commit your real `.env` file to Git.

You should generally have:

```text
.env
.env.example
```

where:

```text
.env
```

contains actual local values and:

```text
.env.example
```

contains placeholders.

---

# 22. Don't bake development secrets into the image

Avoid:

```dockerfile
ENV MONGO_URI="mongodb://..."
```

Instead:

```text
Image
 ↓
generic
 ↓
runtime configuration
```

This keeps configuration separate from the application artifact.

# 23. Development with MongoDB

Eventually, your development environment will become:

```text
                 Docker
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
┌─────────────────┐   ┌─────────────────┐
│ Node             │   │ MongoDB         │
│ Development      │──►│ Development     │
│ Container        │   │ Container       │
└─────────────────┘   └─────────────────┘
```

Your Node container might connect to:

```text
mongodb://mongo:27017/myapp
```

rather than:

```text
mongodb://localhost:27017/myapp
```

Why?

Because inside the Node container:

```text
localhost
```

means:

> **the Node container itself.**

It does not mean your MongoDB container.

We'll cover this properly in **23.8 Docker Compose** and **23.9 Node + MongoDB**.

---

# 24. Important `localhost` concept

This is one of the biggest Docker networking lessons.

On your host:

```text
localhost:5000
```

means your computer.

Inside the Node container:

```text
localhost:5000
```

means the Node container.

Inside the MongoDB container:

```text
localhost:27017
```

means the MongoDB container.

So:

```text
Node container
   │
   │ localhost
   ▼
Node container
```

not:

```text
Node container
   │
   │ localhost
   ▼
MongoDB container
```

Later Docker networks solve this through service/container names.

---

# 25. Development with `docker compose`

Although **23.8 is specifically Docker Compose**, you should understand why Compose becomes useful.

Without Compose:

```bash
docker run ...
docker run ...
docker network ...
docker volume ...
```

With Compose:

```bash
docker compose up
```

and it can manage:

```text
Node
MongoDB
network
volumes
environment
ports
```

So our development architecture will eventually become much cleaner.

# 26. Development workflow we want

Eventually:

```bash
docker compose up
```

Then:

```text
Node starts
MongoDB starts
Network created
Volumes created
Source mounted
nodemon starts
```

You edit:

```text
server.js
```

Then:

```text
nodemon
 ↓

```

You don't rebuild the image for every normal source change.

# 27. What happens when `package.json` changes?

This is an important exception.

Suppose you add:

```bash
npm install bcrypt
```

Now your dependency set changed.

Your existing container's `node_modules` may not automatically contain the new package.

You'll need to rebuild/reinstall dependencies.

For example:

```bash
docker build -f Dockerfile.dev -t my-backend-dev .
```

Then recreate the container.

So:

```text
Source code change
    ↓
No rebuild normally

package.json change
    ↓
Rebuild/reinstall dependencies
```

That's a very useful rule.

---

# 28. Why source changes don't require rebuilding

Because source is mounted:

```text
Host
 ↓
bind mount
 ↓
/app
```

The image doesn't need to contain the latest source.

The container directly sees your working directory.

Therefore:

```text
server.js changed
     ↓
same image
     ↓
same container
     ↓
nodemon restart
```

---

# 29. Why dependency changes often require rebuilding

Dependencies are installed during:

```dockerfile
RUN npm ci
```

which happens during image construction.

So:

```text
package.json
package-lock.json
       ↓
docker build
       ↓
node_modules
```

If the lockfile changes:

```text
new dependency graph
```

the image needs to be rebuilt or dependencies otherwise refreshed.

This connects directly to the Docker layer caching concept from **23.4**.

---

# 30. Docker layer caching helps here

Our development Dockerfile:

```dockerfile
COPY package*.json ./

RUN npm ci

COPY . .
```

means Docker can cache:

```text
package.json
package-lock.json
       ↓
npm ci
```

If you only change:

```text
controllers/todo.controller.js
```

Docker doesn't need to rerun:

```bash
npm ci
```

during a rebuild.

That's why we learned Docker layers before application images.

---

# 31. A useful development Dockerfile improvement

We can add:


So:

```dockerfile
FROM node:24

COPY package*.json ./

COPY . .

ENV NODE_ENV=development
```

Now:

```js
process.env.NODE_ENV
```

returns:

```text
development
```

# 34. Test hot reload

Now comes the important experiment.

Open:

```text
server.js
```

Change something obvious.

For example:

```js
console.log("Development container started");
```

Save the file.

Watch:

```bash
docker logs -f my-backend-dev
```

You should see nodemon notice the change and restart Node.

Conceptually:

```text
File saved
   ↓
bind mount
   ↓
container sees change
   ↓
nodemon
   ↓
Node restarts
```

If this works, you've successfully built your development Docker workflow.

---

# 35. If hot reload doesn't work

Don't immediately assume Docker is broken.

Check:

### 1. Is the volume mounted?

```bash
docker inspect my-backend-dev
```

### 2. Is nodemon running?

```bash
docker logs my-backend-dev
```

### 3. Is the file visible inside the container?

```bash
docker exec -it my-backend-dev ls
```

### 4. Is the changed file actually mounted?

```bash
docker exec -it my-backend-dev cat server.js
```

You should see your latest host changes.

---

# 36. File watching can have platform-specific issues

Depending on your host environment and filesystem setup, file-system events may not behave exactly as expected inside containers.

If nodemon doesn't detect changes, you may need polling.

For example, a development script can use:

```json
{
  "scripts": {
    "dev": "nodemon --legacy-watch server.js"
  }
}
```

But don't add this blindly.

First test normal file watching.

Use polling only if your environment actually needs it.

---

# 37. Don't confuse bind mounts with Docker volumes

There are two concepts you'll encounter:

### Bind mount

```text
-v "$(pwd):/app"
```

Connects:

```text
specific host directory
        ↓
container directory
```

Great for development source code.

### Named volume

```text
-v mongo-data:/data/db
```

Stores Docker-managed persistent data.

Great for databases.

We'll study volumes in **23.10**.

# 41. A common beginner mistake

Don't try to make one Dockerfile do everything with dozens of environment-specific conditions.

For example, avoid building a monster like:

```dockerfile
IF DEVELOPMENT...
IF PRODUCTION...
IF TEST...
IF STAGING...
```

Instead, clear artifacts can be easier to understand:

```text
Dockerfile
    → production

Dockerfile.dev
    → development
```

And later:

```text
Docker Compose
    → orchestration
```

Clarity is valuable.

---

# 42. Another common mistake

Don't use:

```bash
docker build -t my-backend .
```

and then expect:

```text
source changes
```

to automatically appear in the running container.

An image is immutable from the application's point of view.

If you want live source changes:

```text
bind mount
```

is the important mechanism.

---

# 43. Another common mistake: mounting everything blindly

This:

```bash
-v "$(pwd):/app"
```

is convenient.

But it means your host directory controls `/app`.

That's why:

```bash
-v /app/node_modules
```

is commonly added.

So your intended layout is:

```text
/app
├── source ← host
└── node_modules ← container
```

rather than:

```text
/app
├── source ← host
└── node_modules ← host
```

---

# 44. Development doesn't mean insecure

Development containers can still follow good practices:

```text
Don't commit secrets
Don't expose unnecessary ports
Use non-root where practical
Keep dependencies updated
Don't install unnecessary software
Use .dockerignore
```

The difference is that development prioritizes:

```text
developer productivity
```

while production prioritizes:

```text
reliability + security + reproducibility
```

Both need good engineering.
