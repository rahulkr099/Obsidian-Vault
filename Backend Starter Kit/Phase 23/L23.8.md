# Lesson 23.8 — Docker Compose

The roadmap places **23.8 Docker Compose** after the Production and Development Dockerfiles, followed by **23.9 Node + MongoDB**, **23.10 Volumes**, and **23.11 Networks**.

So today we are **not going to jump too deeply into MongoDB, volumes, or networking yet**. The goal is to understand **what Compose is, why it exists, and how it coordinates multiple containers**.

---

# 1. The problem Docker Compose solves

In the previous lesson, we had one development container:

```text
Your machine
    │
    ▼
Node container
    │
    ▼
Express
```

You could run it with:

```bash
docker run ...
```

But a real backend quickly needs more things:

```text
Node.js
MongoDB
Redis
Mail service
Background worker
```

Now imagine starting everything manually:

```bash
docker run ...
docker run ...
docker network create ...
docker volume create ...
docker run ...
```

That becomes annoying.

Docker Compose gives us a way to describe the whole application environment in one configuration file.

---

# 2. The basic idea

Think of Docker Compose as:

> **A tool for defining and running multiple related containers as one application.**

Instead of:

```text
docker run Node
docker run MongoDB
docker network ...
docker volume ...
```

you describe:

```text
services:
  backend
  mongo
```

and Compose handles the orchestration.

Conceptually:

```text
              Docker Compose
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     Backend              MongoDB
    container             container
          │                   │
          └────── network ────┘
                    │
                 volume
```

---

# 3. Why this matters for your MERN backend

Your final backend architecture is moving toward:

```text
React
  │
  ▼
Node / Express
  │
  ▼
MongoDB
```

During development, you can have:

```text
┌─────────────────────────────────────┐
│          Docker Compose             │
│                                     │
│  ┌──────────────┐  ┌─────────────┐ │
│  │ Backend      │  │ MongoDB     │ │
│  │              │  │             │ │
│  │ Node         │──│ MongoDB     │ │
│  │ Express      │  │             │ │
│  │ nodemon      │  │             │ │
│  └──────────────┘  └─────────────┘ │
│                                     │
└─────────────────────────────────────┘
```

Instead of manually managing each container.

---

# 4. Compose configuration

Traditionally, you'll see a file called:

```text
docker-compose.yml
```

For example:

```text
backend/
├── Dockerfile
├── Dockerfile.dev
├── docker-compose.yml
├── package.json
├── package-lock.json
└── ...
```

Modern Docker Compose also commonly uses:

```text
compose.yml
```

The important concept is not the filename.

It's the **Compose configuration**.

---

# 5. A minimal Compose file

Let's create a very simple example:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "5000:5000"
    volumes:
      - .:/app
      - /app/node_modules
```

That's already enough to understand several major Compose concepts.

---

# 6. `services`

The first important section:

```yaml
services:
```

means:

> These are the containers that make up my application.

For example:

```yaml
services:
  backend:
```

defines a service called:

```text
backend
```

Later:

```yaml
services:
  backend:
  mongo:
```

will define two services.

---

# 7. Service ≠ container

This distinction is important.

In Compose, you define a:

```text
service
```

Compose then creates and manages containers for that service.

Think:

```text
Compose configuration
        ↓
     service
        ↓
    container
```

So:

```yaml
backend:
```

is your application service.

It isn't literally the container itself.

---

# 8. `build`

We have:

```yaml
backend:
  build:
    context: .
    dockerfile: Dockerfile.dev
```

This means:

> Build the backend image using the current project directory and `Dockerfile.dev`.

The:

```yaml
context: .
```

means:

```text
current directory
```

And:

```yaml
dockerfile: Dockerfile.dev
```

means:

```text
Use Dockerfile.dev
```

---

# 9. Why use `Dockerfile.dev`?

Because this is our development environment.

We already created:

```text
Dockerfile
     ↓
production

Dockerfile.dev
     ↓
development
```

Compose can use:

```yaml
dockerfile: Dockerfile.dev
```

So the flow becomes:

```text
docker-compose.yml
       ↓
Dockerfile.dev
       ↓
Development image
       ↓
Backend container
```

---

# 10. `ports`

We can write:

```yaml
ports:
  - "5000:5000"
```

This means:

```text
HOST       CONTAINER
5000   →   5000
```

So:

```text
localhost:5000
```

on your machine reaches:

```text
backend container :5000
```

Diagram:

```text
Browser / curl
      │
      │ localhost:5000
      ▼
┌───────────────┐
│ Host :5000    │
└───────┬───────┘
        │
        ▼
┌────────────────┐
│ Container      │
│ :5000          │
│ Express        │
└────────────────┘
```

---

# 11. `volumes`

We can configure:

```yaml
volumes:
  - .:/app
  - /app/node_modules
```

The first:

```yaml
- .:/app
```

means:

```text
current host directory
        ↓
container /app
```

This is our development bind mount.

So when you edit:

```text
server.js
```

the container sees the change.

---

# 12. Why `/app/node_modules` again?

Remember our previous lesson.

We don't want:

```text
host node_modules
        ↓
container node_modules
```

because the environments may differ.

So:

```yaml
- /app/node_modules
```

creates a container-managed volume for:

```text
/app/node_modules
```

Conceptually:

```text
/app
├── source code
│      ↑
│   host mount
│
└── node_modules
       ↑
   container volume
```

---

# 13. Compose simplifies the `docker run` command

Previously we needed:

```bash
docker run \
  --name my-backend-dev \
  -p 5000:5000 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  my-backend-dev
```

That's a lot to remember.

Compose lets us describe it:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    volumes:
      - .:/app
      - /app/node_modules
```

Then:

```bash
docker compose up
```

Much easier.

---

# 14. `docker compose up`

This is one of the commands you should remember.

```bash
docker compose up
```

Compose will:

```text
Read compose file
       ↓
Build required images
       ↓
Create containers
       ↓
Create required resources
       ↓
Start services
       ↓
Show logs
```

So instead of remembering many commands:

```text
docker compose up
```

becomes your development entry point.

---

# 15. Detached mode

You can also use:

```bash
docker compose up -d
```

The:

```text
-d
```

means:

```text
detached
```

The containers run in the background.

Then:

```bash
docker compose ps
```

shows the running services.

And:

```bash
docker compose logs
```

shows logs.

---

# 16. Follow logs

For development, this is useful:

```bash
docker compose logs -f
```

The:

```text
-f
```

means follow.

You can also target one service:

```bash
docker compose logs -f backend
```

So:

```text
backend
   ↓
logs
   ↓
nodemon
   ↓
Node
```

becomes easy to inspect.

---

# 17. Stop the environment

To stop the Compose application:

```bash
docker compose down
```

This stops and removes the containers created by Compose.

Conceptually:

```text
docker compose up
       ↓
environment running
       ↓
docker compose down
       ↓
containers removed
```

We'll discuss the difference between containers and persistent data more deeply when we reach **23.10 Volumes**.

---

# 18. Compose and multiple services

Now let's add MongoDB conceptually:

```yaml
services:

  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "5000:5000"

  mongo:
    image: mongo:8
```

Now Compose manages:

```text
backend
mongo
```

Together.

The architecture becomes:

```text
             Docker Compose
                   │
          ┌────────┴────────┐
          ▼                 ▼
      backend             mongo
     container           container
          │                 │
          └──── network ────┘
```

This is the architecture we'll develop further in **23.9 Node + MongoDB**.

---

# 19. Why this is better than separate `docker run` commands

Without Compose:

```bash
docker network create my-network

docker run \
  --network my-network \
  ...

docker run \
  --network my-network \
  ...
```

You need to remember:

```text
container names
network
ports
volumes
environment
images
```

With Compose:

```yaml
services:
  backend:
  mongo:
```

and Compose handles the relationships.

---

# 20. Compose creates a network

By default, Compose creates a network for the application.

For example:

```text
project_default
```

Then:

```text
backend
   │
   │ Docker network
   ▼
mongo
```

This means services can communicate with each other.

This is why eventually your Node application can use something like:

```text
mongodb://mongo:27017/myapp
```

rather than:

```text
mongodb://localhost:27017/myapp
```

The detailed networking explanation belongs to **23.11 Networks**, so for now remember only:

> Compose gives related services a network where they can communicate.

---

# 21. Service names become useful

Suppose:

```yaml
services:
  backend:
  mongo:
```

Inside the Compose network, `mongo` can act as the hostname for the MongoDB service.

So:

```text
backend
   │
   │ hostname = mongo
   ▼
mongo
```

That's a huge improvement over manually managing IP addresses.

You should **not** hard-code container IP addresses.

---

# 22. Don't use container IP addresses

Bad idea:

```text
mongodb://172.20.0.5:27017
```

Why?

Container IPs can change.

Better:

```text
mongodb://mongo:27017
```

because:

```text
mongo
```

is the service name.

Conceptually:

```text
Service discovery
      ↓
mongo
      ↓
current MongoDB container
```

Docker handles the underlying address.

---

# 23. Compose is declarative

This is an important engineering concept.

Instead of saying:

```text
First execute this command.
Then execute this command.
Then create this network.
Then create this volume.
Then start this container.
```

you say:

> **This is the environment I want.**

For example:

```yaml
services:
  backend:
    ...
  mongo:
    ...
```

Compose figures out how to create it.

This is a **declarative configuration** style.

---

# 24. Compose file as infrastructure documentation

Your Compose file becomes a form of documentation.

Someone can open:

```text
compose.yml
```

and understand:

```text
What services exist?
How is backend built?
What ports are exposed?
What volumes exist?
What environment is required?
What services communicate?
```

That's much better than having deployment knowledge only inside your head.

# 25. Environment variables in Compose

Compose can also pass environment variables.

For example:

```yaml
services:
  backend:
    environment:
      NODE_ENV: development
      PORT: 5000
```

Inside Node:

```js
process.env.NODE_ENV
```

becomes:

```text
development
```

And:

```js
process.env.PORT
```

becomes:

```text
5000
```

We'll study environment configuration more carefully in **23.12 Environment Variables**.

---

# 26. Don't put secrets directly in Compose

Avoid:

```yaml
environment:
  MONGO_PASSWORD: super-secret-password
```

if that means committing a real secret into Git.

Remember:

```text
compose.yml
      ↓
usually committed to Git
```

Therefore:

```text
real secrets
      ↓
runtime environment / secret management
```

not:

```text
real secrets
      ↓
Git repository
```

We'll return to this later.

---

# 27. `.env` with Compose

For local development, you may use:

```text
.env
```

and reference variables.

For example:

```yaml
services:
  backend:
    environment:
      MONGO_URI: ${MONGO_URI}
```

Then:

```text
.env
   ↓
Compose
   ↓
container
   ↓
process.env.MONGO_URI
```

This keeps configuration separate from the Compose structure.

---

# 28. Build vs image

Compose gives you two common ways to define a service.

### Build your own image

```yaml
backend:
  build:
    context: .
    dockerfile: Dockerfile.dev
```

This means:

```text
your source
   ↓
Dockerfile
   ↓
your image
```

### Use an existing image

For MongoDB:

```yaml
mongo:
  image: mongo:8
```

This means:

```text
Docker registry
      ↓
MongoDB image
      ↓
container
```

So:

```text
backend
  → build

mongo
  → image
```

---

# 29. This gives us a powerful pattern

Your Compose file can combine:

```text
Your custom application
+
Official infrastructure images
```

For example:

```text
Node backend
   +
MongoDB
   +
Redis
```

Your application is built by you.

Infrastructure services can use maintained images.

# 30. Development Compose example

A simple starting point for our backend:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    volumes:
      - .:/app
      - /app/node_modules

    environment:
      NODE_ENV: development
      PORT: 5000

    depends_on:
      - mongo

  mongo:
    image: mongo:8
```

Don't worry about every line yet.

We're building the mental model.

---

# 31. What does `depends_on` mean?

We wrote:

```yaml
depends_on:
  - mongo
```

This expresses:

> The backend service depends on the MongoDB service.

It influences service startup order.

But here's an important point:

> `depends_on` does **not automatically mean MongoDB is ready to accept connections**.

This distinction becomes important later when we study health checks.

---

# 32. Startup order vs readiness

Suppose:

```text
Compose starts MongoDB
        ↓
MongoDB process begins
        ↓
Backend starts immediately
        ↓
Backend tries MongoDB
        ↓
MongoDB isn't ready yet
```

You can still get a connection failure.

So:

```text
started
```

is not necessarily:

```text
ready
```

This is exactly why the roadmap later has:

```text
23.13 Health checks
```

---

# 33. Don't solve readiness with arbitrary sleeps

You might see:

```bash
sleep 10
```

in tutorials.

For example:

```text
Start MongoDB
 ↓
sleep 10
 ↓
start backend
```

That's fragile.

What if MongoDB needs:

```text
2 seconds?
```

Or:

```text
15 seconds?
```

A fixed sleep doesn't actually tell you whether the service is ready.

A better design uses:

```text
health check
     ↓
readiness
     ↓
application startup
```

We'll learn this later.

# 34. Compose development lifecycle

Your future workflow will look something like:

```bash
docker compose up --build
```

Then:

```text
Compose
  │
  ├── build backend
  │
  ├── start MongoDB
  │
  ├── start backend
  │
  ├── create network
  │
  └── attach volumes
```

Then:

```text
You edit code
     ↓
bind mount
     ↓

     ↓
nodemon
     ↓
Node restarts
```

---

# 35. `docker compose up --build`

Normally:

```bash
docker compose up
```

will reuse an existing image if possible.

If you've changed your Dockerfile or dependencies, use:

```bash
docker compose up --build
```

This tells Compose to rebuild images before starting.

A useful distinction:

```text
Source code change
    ↓
usually no rebuild

Dockerfile change
    ↓
rebuild

package.json change
    ↓
usually rebuild dependency layer
```

# 37. Compose doesn't replace Docker

Don't think:

```text
Docker Compose = Docker replacement
```

Instead:

```text
Docker
   ↓
containers/images/volumes/networks

Docker Compose
   ↓
defines and coordinates multiple Docker resources
```

Think:

```text
Docker
=
container engine/building blocks

Compose
=
application environment coordinator
```

---

# 38. Compose doesn't magically make an application production-ready

This is also important.

Having:

```text
compose.yml
```

doesn't automatically give you:

```text
HTTPS
security
backups
monitoring
scaling
secret management
high availability
```

Compose is a tool.

Your architecture still determines whether the system is production-ready.

Your roadmap separates:

```text
Phase 23
Docker & Production Architecture
```

from:

```text
Phase 24
Production Hardening
```

for exactly this reason.
