# Lesson 23.9 — Node + MongoDB

The Phase 23 roadmap defines **23.9 as “Node + MongoDB”**, immediately after Docker Compose. The intended progression is:

```text
23.8 Docker Compose
        ↓
23.9 Node + MongoDB
        ↓
23.10 Volumes
        ↓
23.11 Networks
```

So today we'll connect the **Node/Express container** to a **MongoDB container** using Compose.

---

# 1. What are we building?

Until now:

```text
Your machine
     ↓
Node container
     ↓
Express
```

Now we'll have:

```text
                 Docker Compose
                       │
              ┌────────┴────────┐
              ▼                 ▼
       Node container      MongoDB container
              │                 │
              └──── connection ─┘
```

The complete request/data flow becomes:

```text
Client
  ↓
Node / Express
  ↓
Service
  ↓
Repository
  ↓
MongoDB
```

And both Node and MongoDB are running as containers.

---

# 2. Why put MongoDB in a container?

For development, this gives you a predictable environment.

Instead of manually installing MongoDB on your Linux machine:

```text
Linux
 ├── Node
 └── MongoDB
```

you can have:

```text
Docker
 ├── Node container
 └── MongoDB container
```

Then a new developer can clone the project and run:

```bash
docker compose up
```

and get the same basic development environment.

---

```text
└── ...
```

# 4. The first Compose configuration

Let's start simple:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    volumes:
      - .:/app
      - /app/node_modules

    environment:
      NODE_ENV: development
      PORT: 5000

    depends_on:
      - mongo

  mongo:
    image: mongo:8
```

We already saw most of this in **23.8**.

Now we'll focus on the important new relationship:

```text
backend
   ↓
mongo
```

---

# 5. Two services

We have:

```yaml
services:
  backend:
```

and:

```yaml
services:
  mongo:
```

So Compose manages two services:

```text
┌───────────────────┐
│ backend            │
│ Node + Express     │
└───────────────────┘

┌───────────────────┐
│ mongo              │
│ MongoDB            │
└───────────────────┘
```

---

# 6. MongoDB image

We use:

```yaml
mongo:
  image: mongo:8
```

This tells Docker:

> Use the MongoDB image with the `8` tag.

Unlike your backend:

```yaml
backend:
  build:
    context: .
    dockerfile: Dockerfile.dev
```

we don't build MongoDB ourselves.

We use a MongoDB image.

So:

```text
Backend
   ↓
Your Dockerfile.dev

MongoDB
   ↓
MongoDB image
```

# 7. Start the environment

Run:

```bash
docker compose up --build
```

Compose now does roughly:

```text
Read compose.yml
      ↓
Build backend image
      ↓
Pull MongoDB image if needed
      ↓
Create network
      ↓
Create containers
      ↓
Start services
```

You'll see logs from both services.

# 8. Check the containers

Open another terminal:

```bash
docker compose ps
```

You should see something conceptually like:

```text
NAME              SERVICE    STATUS
backend-...       backend    running
mongo-...         mongo      running
```

The exact container names will depend on your Compose project name.

---

# 9. The critical concept: `localhost`

This is where many Docker beginners make a mistake.

Suppose your Node application uses:

```text
mongodb://localhost:27017/myapp
```

Inside the Node container, what does:

```text
localhost
```

mean?

It means:

> **The Node container itself.**

Not MongoDB.

So this is wrong for our container-to-container connection:

```text
Node container
      ↓
localhost:27017
      ↓
Node container
```

MongoDB is somewhere else.

---

# 10. How does Node find MongoDB?

Compose gives the services a network.

Inside that network:

```text
mongo
```

can be used as the hostname of the MongoDB service.

So Node can connect using:

```text
mongodb://mongo:27017/myapp
```

The architecture is:

```text
Node
 │
 │ mongodb://mongo:27017/myapp
 │
 ▼
mongo
 │
 ▼
MongoDB
```

This is one of the most important Docker networking concepts.

---

# 11. Why `mongo`?

Because our service is named:

```yaml
services:
  mongo:
```

Therefore:

```text
mongo
```

becomes the service hostname within the Compose network.

You don't need to know MongoDB's container IP.

You don't need to manually create DNS entries.

Compose/Docker networking handles service discovery.

---

# 12. Don't use the MongoDB container IP

Avoid:

```text
mongodb://172.20.0.4:27017/myapp
```

Why?

Because container IPs are not stable application identifiers.

Today:

```text
mongo → 172.20.0.4
```

Tomorrow it might be:

```text
mongo → 172.20.0.7
```

Your application shouldn't care.

Use:

```text
mongodb://mongo:27017/myapp
```

The service name is stable.

---

# 13. Configure `MONGO_URI`

Instead of hard-coding this in your source:

```js
const mongoUri = "mongodb://mongo:27017/myapp";
```

we should use configuration.

For example:

```yaml
environment:
  NODE_ENV: development
  PORT: 5000
  MONGO_URI: mongodb://mongo:27017/myapp
```

Then your application reads:

```js
process.env.MONGO_URI
```

This follows the environment-configuration architecture you've already learned.

Your source code doesn't need to know whether MongoDB is:

```text
localhost
```

or:

```text
mongo
```

or a cloud database.

---

# 14. The configuration flow

Now we have:

```text
compose.yml
      │
      │ MONGO_URI
      ▼
Node container
      │
      ▼
process.env.MONGO_URI
      │
      ▼
config/env.js
      │
      ▼
config/db.js
      │
      ▼
MongoDB
```

This is much cleaner than spreading environment access throughout your application.

---

# 15. Example `config/env.js`

A simple version:

```js
import "dotenv/config";

const env = {
  nodeEnv: process.env.NODE_ENV || "development",
  port: Number(process.env.PORT) || 5000,
  mongoUri: process.env.MONGO_URI,
};

export default env;
```

Then:

```text
env.mongoUri
```

contains:

```text
mongodb://mongo:27017/myapp
```

inside the Docker environment.

---

# 16. Example `config/db.js`

For Mongoose:

```js
import mongoose from "mongoose";
import env from "./env.js";

export const connectDB = async () => {
  await mongoose.connect(env.mongoUri);

  console.log("MongoDB connected");
};
```

Now database configuration is separated from the application.

---

# 17. Startup flow

Your `server.js` should conceptually do:

```js
import app from "./app.js";
import env from "./config/env.js";
import { connectDB } from "./config/db.js";

const startServer = async () => {
  await connectDB();

  app.listen(env.port, () => {
    console.log(`Server running on port ${env.port}`);
  });
};

startServer();
```

The important sequence is:

```text
Node starts
   ↓
Load configuration
   ↓
Connect MongoDB
   ↓
MongoDB connection succeeds
   ↓
Start HTTP server
```

This matches the starter architecture's principle that required database connectivity should be established before accepting requests.

---

# 18. Why shouldn't we start Express first?

Imagine:

```text
Node starts
   ↓
Express starts
   ↓
Server accepts requests
   ↓
MongoDB isn't connected
```

A request arrives:

```text
GET /users/me
```

Then:

```text
Controller
 ↓
Service
 ↓
Repository
 ↓
MongoDB
 ↓
Connection unavailable
```

That's not a good startup state.

Instead:

```text
Node
 ↓
MongoDB connection
 ↓
success
 ↓
HTTP server starts
```

Now your server only starts when its required dependency is available.

---

# 19. What happens when MongoDB is unavailable?

Suppose:

```text
MongoDB
   ✕
```

Your application should not pretend everything is healthy.

A good startup flow is:

```text
connectDB()
    │
    ├── success → start server
    │
    └── failure → log error + exit
```

This is an important production principle.

We'll later improve this with **health checks and readiness** in 23.13.

---

# 20. `depends_on`

Our Compose file contains:

```yaml
depends_on:
  - mongo
```

This says:

```text
backend
   ↓
depends on
   ↓
mongo
```

It helps Compose determine startup order.

But remember:

> `depends_on` does not mean MongoDB is fully ready to accept database connections.

For example:

```text
MongoDB process starts
        ↓
MongoDB initialization
        ↓
MongoDB ready
```

There can be a delay between those states.

---

# 21. Why startup order isn't enough

Imagine:

```text
Compose
 │
 ├── start mongo
 │
 └── start backend
```

MongoDB process may technically be running.

But:

```text
MongoDB
   ↓
initializing
```

while:

```text
Backend
   ↓
mongoose.connect()
```

tries to connect.

You could get a connection failure.

That's why later we'll use health/readiness mechanisms instead of relying only on startup order.

---

# 22. The database port

MongoDB normally listens on:

```text
27017
```

Inside the Compose network, Node can reach:

```text
mongo:27017
```

Notice that we don't actually need:

```yaml
ports:
  - "27017:27017"
```

for Node to communicate with MongoDB.

Why?

Because both containers are on the same Docker network.

```text
backend
   │
   │ internal network
   ▼
mongo:27017
```

---

# 23. Do we need to expose MongoDB to the host?

Not necessarily.

If only the backend needs MongoDB:

```text
Host
  │
  ▼
Backend :5000
  │
  │ internal Docker network
  ▼
MongoDB :27017
```

You can keep MongoDB internal.

You might expose it during development when you want to connect using tools such as MongoDB Compass:

```yaml
ports:
  - "27017:27017"
```

But exposing a service isn't required for container-to-container communication.

This distinction is important:

```text
ports
  ↓
host ↔ container

network
  ↓
container ↔ container
```

We'll go deeper into this in **23.11 Networks**.

# 24. A better Compose file

For our development backend:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    volumes:
      - .:/app
      - /app/node_modules

    environment:
      NODE_ENV: development
      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp

    depends_on:
      - mongo

  mongo:
    image: mongo:8
```

Now the architecture is:

```text
                  Docker Compose
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
   ┌───────────────┐        ┌───────────────┐
   │ backend       │        │ mongo         │
   │               │        │               │
   │ Node          │───────►│ MongoDB       │
   │ Express       │        │ :27017        │
   │ nodemon       │        │               │
   └───────┬───────┘        └───────────────┘
           │
           ▼
       localhost:5000
```

---

# 25. MongoDB database name

Our URI:

```text
mongodb://mongo:27017/myapp
```

contains:

```text
mongodb://
       │
       ▼
     mongo
       │
       ▼
     27017
       │
       ▼
     myapp
```

So:

```text
Host: mongo
Port: 27017
Database: myapp
```

The database name can be whatever your project uses.

# 26. What happens when Node starts?

Let's follow the complete sequence.

### Step 1

Compose starts:

```text
mongo
```

### Step 2

Compose starts:

```text
backend
```

### Step 3

Node reads:

```text
MONGO_URI=mongodb://mongo:27017/myapp
```

### Step 4

Mongoose executes:

```js
mongoose.connect(env.mongoUri);
```

### Step 5

Docker DNS resolves:

```text
mongo
```

to the MongoDB container.

### Step 6

MongoDB accepts the connection.

### Step 7

Node starts Express:

```text
localhost:5000
```

# 28. This connects directly to your repository architecture

Remember:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Model
    ↓
MongoDB
```

Docker doesn't change this architecture.

It changes **where the processes run**.

Without Docker:

```text
Node process
   ↓
localhost MongoDB
```

With Docker:

```text
Node container
   ↓
mongo service
   ↓
MongoDB container
```

Your application layers remain the same.

That's an important architectural distinction.

---

# 29. Don't put MongoDB logic inside Docker configuration

Your Compose file should answer:

```text
Where does MongoDB run?
How is it started?
What network does it use?
What data volume does it use?
```

Your application should answer:

```text
How do I query users?
How do I create todos?
How do I perform business logic?
```

Keep those responsibilities separate.

---

# 30. MongoDB data is currently ephemeral

Here's something very important.

If you simply use:

```yaml
mongo:
  image: mongo:8
```

without a persistent volume, MongoDB's data is tied to the container's writable storage.

If you remove the container, you can lose that data.

For example:

```text
MongoDB container
      ↓
database data
      ↓
docker compose down
      ↓
container removed
      ↓
data may be gone
```

That's why the next lesson is:

> **23.10 — Volumes**

We'll solve persistent MongoDB storage there.

---

You might be tempted to immediately add:

```yaml
volumes:
  mongo-data:
```

and:

```yaml
mongo:
  volumes:
    - mongo-data:/data/db
```

That's correct architecture, but the roadmap intentionally puts **Volumes in 23.10**.

For now, focus on:

```text
Node
  ↓
MongoDB
```

and understand:

```text
mongo:27017
```

as the internal database endpoint.

Then we'll make the data persistent in the next lesson.

# 37. Common mistake #1 — `localhost`

Wrong:

```env
MONGO_URI=mongodb://localhost:27017/myapp
```

inside the backend container.

Correct:

```env
MONGO_URI=mongodb://mongo:27017/myapp
```

when `mongo` is the Compose service name.

---

# 38. Common mistake #2 — wrong service name

Suppose Compose says:

```yaml
services:
  database:
    image: mongo:8
```

Then this:

```text
mongodb://mongo:27017
```

won't match the service name.

You'd use:

```text
mongodb://database:27017
```

The hostname corresponds to the service name.

So:

```text
services:
  mongo:
```

→

```text
mongo
```

and:

```text
services:
  database:
```

→

```text
database
```

---

# 39. Common mistake #3 — using host port for internal communication

Suppose you have:

```yaml
mongo:
  ports:
    - "27018:27017"
```

From your host:

```text
localhost:27018
```

reaches MongoDB's:

```text
container:27017
```

But Node should still use:

```text
mongo:27017
```

not:

```text
mongo:27018
```

Why?

Because:

```text
27018
```

is the **host port**.

Inside the Docker network, MongoDB is listening on:

```text
27017
```

So:

```text
Host → MongoDB:
localhost:27018

Backend → MongoDB:
mongo:27017
```

This distinction is extremely important.

---

# 40. Common mistake #4 — hard-coding Docker hostnames

Your code shouldn't contain:

```js
const mongoUri = "mongodb://mongo:27017/myapp";
```

because then your local non-Docker environment becomes awkward.

Instead:

```js
env.mongoUri
```

and configure:

### Local machine

```env
MONGO_URI=mongodb://localhost:27017/myapp
```

### Docker Compose

```yaml
MONGO_URI: mongodb://mongo:27017/myapp
```

Same application code.

Different environment configuration.

This is exactly why configuration should be externalized.

---

# 41. Local vs Docker environment

This gives us a very useful model:

### Running Node directly on your machine

```text
Node
 ↓
localhost:27017
 ↓
MongoDB on host
```

### Running Node inside Docker

```text
Node container
 ↓
mongo:27017
 ↓
MongoDB container
```

The application itself doesn't change.

Only:

```text
MONGO_URI
```

changes.

---

# 42. This is why environment variables matter

The same application image/code can work in different environments:

```text
Development machine
MONGO_URI=localhost

Docker development
MONGO_URI=mongo

Staging
MONGO_URI=staging-db

Production
MONGO_URI=production-db
```

Your code still uses:

```js
mongoose.connect(env.mongoUri);
```

This is a very important production architecture principle.

# 46. Final Compose example for this lesson

For now, your development `compose.yml` can look like:

```yaml
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile.dev

    ports:
      - "5000:5000"

    volumes:
      - .:/app

      PORT: 5000
      MONGO_URI: mongodb://mongo:27017/myapp

    depends_on:
      - mongo

  mongo:
    image: mongo:8
```

And your backend configuration:

```js
// config/db.js

import mongoose from "mongoose";
import env from "./env.js";

export const connectDB = async () => {
  await mongoose.connect(env.mongoUri);

  console.log("MongoDB connected");
};
```

Your startup:

```js
// server.js

import app from "./app.js";
import env from "./config/env.js";
import { connectDB } from "./config/db.js";

const startServer = async () => {
  await connectDB();

  app.listen(env.port, () => {
    console.log(`Server running on port ${env.port}`);
  });
};

startServer();
```

The exact code can vary with the starter you're building, but the **architecture** is the important part.

```text
Node container

MongoDB container
```
