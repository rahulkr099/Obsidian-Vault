# Lesson 24.10 — Error Handling & Operational Failures

In the previous lesson, we learned how to **log failures**.

Now we need to answer the next question:

> **What should our backend actually do when something goes wrong?**

A production backend should not simply crash, expose a stack trace, or return random error formats.

The goal is:

```text
Error occurs
    ↓
Classify the error
    ↓
Log useful details
    ↓
Return a safe response
    ↓
Continue if possible
    ↓
Recover / restart if necessary
```

This is the core of **production error handling**.

---

# 1. What Is Error Handling?

Error handling is the process of deciding:

```text
What happened?
    ↓
How serious is it?
    ↓
Who should know?
    ↓
What should the client receive?
    ↓
Can the application continue?
```

For example:

```text
Invalid request
    ↓
400
    ↓
Client fixes request
```

But:

```text
MongoDB unavailable
    ↓
503
    ↓
Infrastructure must recover
```

These are completely different situations.

---

# 2. Not Every Error Is the Same

A mature backend distinguishes between different categories.

A useful model is:

```text
                    ERROR
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
    Client Error   Auth Error    Server Error
        │             │             │
       4xx           401/403        5xx
```

There can also be:

```text
Database failures
External service failures
Timeouts
Configuration failures
Unexpected programming errors
```

---

# 3. Client Errors

A client error means:

> The request is invalid or the client isn't allowed to perform the operation.

Examples:

```text
Missing required field
Invalid email
Malformed ID
Invalid query parameter
Resource not found
```

Typical statuses:

```text
400
404
409
422
```

depending on your API design.

---

# 4. Authentication Errors

Authentication answers:

> **Who are you?**

If the user isn't authenticated:

```http
401 Unauthorized
```

Example:

```json
{
  "success": false,
  "message": "Authentication required"
}
```

---

# 5. Authorization Errors

Authorization answers:

> **Are you allowed to do this?**

For example:

```text
User A
  ↓
tries to delete
  ↓
User B's resource
```

The user may be authenticated, but not authorized.

Typically:

```http
403 Forbidden
```

---

# 6. Not Found

Suppose:

```http
GET /api/v1/todos/123
```

but todo `123` doesn't exist.

Return:

```http
404 Not Found
```

For example:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

Don't turn an ordinary missing resource into:

```http
500 Internal Server Error
```

---

# 7. Conflict

A conflict occurs when the request conflicts with the current state.

Example:

```text
Register
    ↓
email already exists
```

Possible response:

```http
409 Conflict
```

For example:

```json
{
  "success": false,
  "message": "Email is already registered"
}
```

The exact status depends on your API's error contract, but the key idea is to distinguish business conflicts from server failures.

---

# 8. Server Errors

A server error means:

> The client may have sent a valid request, but the server couldn't successfully process it.

Examples:

```text
Database unavailable
Unexpected exception
Internal service failure
Infrastructure failure
```

Typical response:

```http
500 Internal Server Error
```

---

# 9. Don't Expose Internal Errors

Suppose MongoDB throws:

```text
MongoServerSelectionError:
connection refused
```

Never send the raw error to the client.

Bad:

```json
{
  "error": "MongoServerSelectionError: connection refused at ..."
}
```

This can expose:

```text
database technology
internal details
stack traces
infrastructure information
```

Instead:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc123"
}
```

The detailed error belongs in your logs.

---

# 10. Two Audiences

Every error has two audiences.

### Client

Needs:

```text
safe
clear
useful
consistent
```

### Backend team

Needs:

```text
technical details
stack trace
requestId
context
error cause
```

So:

```text
                 ERROR
                   │
          ┌────────┴────────┐
          ▼                 ▼
       Client             Logs
          │                 │
      Safe message      Full details
```

This is one of the most important production patterns.

---

# 11. Centralized Error Middleware

In Express, a common architecture is a centralized error middleware.

Conceptually:

```js
app.use(errorHandler);
```

The middleware receives errors from the application and decides:

```text
log
classify
respond
```

This prevents every controller from inventing its own error-response format.

---

# 12. Express Error Middleware

The signature is important:

```js
function errorHandler(err, req, res, next) {
  // handle error
}
```

Express recognizes it as error middleware because it has four parameters:

```text
err
req
res
next
```

The important one is:

```text
err
```

---

# 13. Basic Architecture

Your application can look like:

```text
Request
   ↓
Route
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Error
   ↓
Central Error Middleware
   ↓
Log
   ↓
Safe Response
```

This creates one central place for error handling.

---

# 14. Why Centralization Matters

Without centralized handling:

```text
Controller A
 → response format A

Controller B
 → response format B

Controller C
 → response format C
```

Clients get inconsistent responses.

With centralized handling:

```text
All errors
    ↓
Error middleware
    ↓
Consistent response
```

Much easier to maintain.

---

# 15. Custom Application Errors

You can create your own error class.

Conceptually:

```js
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
  }
}
```

Then:

```js
throw new AppError(
  "Todo not found",
  404
);
```

Your centralized handler can understand:

```text
AppError
   ↓
404
```

while unexpected errors become:

```text
500
```

---

# 16. Why Custom Errors Help

Imagine your service says:

```js
throw new AppError("Todo not found", 404);
```

The controller doesn't need:

```js
res.status(404)...
```

Instead:

```text
Service
  ↓
throws AppError
  ↓
Error middleware
  ↓
404 response
```

This keeps business logic cleaner.

---

# 17. Operational vs Programming Errors

This distinction is extremely useful.

### Operational error

Something went wrong during normal operation.

Examples:

```text
Database temporarily unavailable
External API timeout
Invalid user input
File not found
```

These can often be handled.

### Programming error

Something is wrong with the application itself.

Examples:

```text
undefined variable
unexpected TypeError
broken assumption
bug in code
```

These require investigation and often a code fix.

---

# 18. Example

Suppose:

```js
const user = await findUser(id);

console.log(user.profile.name);
```

If:

```text
user = null
```

then:

```text
TypeError
```

This isn't a normal business condition.

It could indicate a programming bug or an unhandled case.

You should log it and investigate rather than pretending it is a normal user error.

---

# 19. Don't Turn Every Error Into 400

A common beginner mistake:

```js
catch (error) {
  return res.status(400).json({
    message: error.message
  });
}
```

This is bad because:

```text
Database failure → 400
Programming bug → 400
External API failure → 400
```

The client didn't necessarily do anything wrong.

Error status codes should represent the actual failure category.

---

# 20. Don't Turn Every Error Into 500 Either

The opposite mistake is:

```text
Invalid input → 500
Not found → 500
Unauthorized → 500
```

This tells clients:

> "The server is broken."

when actually:

```text
Client needs to fix the request.
```

Good error handling means **classifying errors correctly**.

---

# 21. Error Classification

Think:

```text
Error
 │
 ├── Validation → 400 / 422
 │
 ├── Authentication → 401
 │
 ├── Authorization → 403
 │
 ├── Not found → 404
 │
 ├── Conflict → 409
 │
 ├── Rate limit → 429
 │
 └── Unexpected/server failure → 500
```

The exact API contract can vary, but the principle is stable.

---

# 22. Error Response Contract

Your API should have a predictable shape.

For example:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

For an internal error:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc123"
}
```

For validation:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    {
      "field": "title",
      "message": "Title is required"
    }
  ]
}
```

Consistency is more important than having a complicated format.

---

# 23. Request ID in Error Responses

Remember our previous lesson.

Suppose the client receives:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc123"
}
```

The user can report:

> "Request `abc123` failed."

Your team searches:

```text
requestId=abc123
```

and finds:

```text
request.received
database.connection.failed
request.failed
```

This creates a powerful debugging loop.

---

# 24. Error Handling Flow

A production request can follow:

```text
                    REQUEST
                       │
                       ▼
                 requestId
                       │
                       ▼
                 Rate limiter
                       │
                       ▼
                 Authentication
                       │
                       ▼
                 Validation
                       │
                       ▼
                   Service
                       │
                       ▼
                    Error?
                    /     \
                  No       Yes
                  │         │
                  ▼         ▼
               Response   Error Handler
                            │
                    ┌───────┴───────┐
                    ▼               ▼
                  Log          Classify
                                    │
                                    ▼
                              Safe Response
```

---

# 25. Async Errors

This is especially important with Express.

Your backend contains many asynchronous operations:

```js
await User.findById(id);
await sendEmail();
await redis.get(key);
await fetch(...);
```

Any of these can fail.

Your architecture needs a consistent strategy for propagating those errors to the centralized error handler.

Depending on your Express version and architecture, you may use native async error propagation or an async wrapper/helper.

The key concept is:

> **Don't let rejected promises disappear or become unhandled failures.**

---

# 26. Unhandled Promise Rejections

Imagine:

```js
someAsyncOperation();
```

without properly handling the returned promise.

If it rejects:

```text
Promise rejected
      ↓
Nobody handles it
```

This can lead to unstable application behavior.

Always design asynchronous code so failures have a clear path:

```text
async operation
     ↓
catch/propagate
     ↓
central handler
```

---

# 27. Uncaught Exceptions

An uncaught exception is more serious.

For example:

```text
Unexpected synchronous exception
        ↓
process-level failure
```

A production Node.js application should not simply pretend that an unknown fatal state is safe.

The process may need to terminate and be restarted by infrastructure.

This is an important production concept.

---

# 28. Should You Keep Running After an Unknown Fatal Error?

Not always.

Suppose the application reaches an unknown state:

```text
Critical invariant broken
```

Continuing to serve requests may be dangerous.

A common philosophy is:

> **Fail fast and let the process manager/container orchestrator restart the application.**

For example:

```text
Node process
     ↓
fatal error
     ↓
exit
     ↓
Docker / systemd / Kubernetes
     ↓
restart
```

This connects directly to the Docker and deployment architecture you studied in Phase 23.

---

# 29. Graceful Shutdown

If the process needs to stop, it shouldn't simply disappear.

A graceful shutdown can:

```text
Stop accepting new work
       ↓
Finish important ongoing work
       ↓
Close database connections
       ↓
Close Redis connections
       ↓
Close server
       ↓
Exit
```

This will be the focus of a later lesson in this phase.

---

# 30. Operational Failure

An operational failure is something that can happen even when your code is correct.

Examples:

```text
MongoDB temporarily unavailable
Redis unavailable
Email provider timeout
Network failure
External API unavailable
Disk full
```

Your backend should anticipate these.

---

# 31. External API Failure

Suppose:

```text
Your API
   ↓
Payment provider
```

The provider times out.

Don't let that become:

```text
5-second request
↓
Node hangs
↓
user waits forever
```

Use:

```text
Timeout
+
Error handling
+
Logging
+
Safe response
```

---

# 32. Timeouts Are Essential

Every external dependency should have sensible timeouts.

Think:

```text
Your backend
    │
    ├── MongoDB
    ├── Redis
    ├── Email provider
    ├── AI provider
    └── Payment provider
```

Without timeouts:

```text
Dependency hangs
      ↓
Your request hangs
      ↓
Connections pile up
      ↓
Resources exhausted
```

Timeouts prevent one dependency from holding your application hostage.

---

# 33. Retry Carefully

Suppose an external service fails.

You might think:

```text
Failure
 ↓
retry
 ↓
retry
 ↓
retry
```

But retries can make an outage worse.

Imagine:

```text
External API
    ↓
already overloaded
```

and 10,000 clients all retry immediately.

You create:

```text
Retry storm
```

So retries need:

```text
limited attempts
backoff
jitter
```

and should be used only when the operation is safe to retry.

---

# 34. Exponential Backoff

Conceptually:

```text
Attempt 1 → immediately
Attempt 2 → wait 100ms
Attempt 3 → wait 200ms
Attempt 4 → wait 400ms
Attempt 5 → wait 800ms
```

The exact numbers depend on the system.

The idea is:

> Give the failing dependency time to recover.

---

# 35. Idempotency and Retries

This is extremely important.

Suppose you send:

```text
POST /payment
```

and the request times out.

Did the payment fail?

Or:

```text
Payment succeeded
but response was lost?
```

If you blindly retry:

```text
POST payment
POST payment
```

you could create a duplicate transaction.

So retries should consider **idempotency**.

---

# 36. Retryable vs Non-Retryable Errors

Some errors may be temporary:

```text
network timeout
temporary 503
connection reset
```

Others aren't:

```text
invalid credentials
validation failure
permission denied
```

Retrying:

```text
400
401
403
```

usually doesn't solve the underlying problem.

---

# 37. Circuit Breaker Concept

For frequently failing external dependencies, a circuit breaker can help.

Think of an electrical circuit:

```text
Healthy
  ↓
requests allowed
```

Repeated failures:

```text
failure
failure
failure
failure
      ↓
Circuit opens
```

Now requests fail fast instead of continuously hitting the broken dependency.

Later:

```text
Wait
 ↓
Test dependency
 ↓
Healthy?
 ↓
Close circuit
```

This is an advanced resilience pattern.

---

# 38. Bulkhead Concept

Another resilience pattern is the **bulkhead**.

Imagine your application has:

```text
AI requests
Email requests
Payment requests
Normal API requests
```

If AI requests consume every available resource:

```text
AI overload
   ↓
Entire API affected
```

A bulkhead approach isolates resources:

```text
AI
 ↓
limited workers

Email
 ↓
limited workers

Normal API
 ↓
separate resources
```

This prevents one workload from sinking the entire application.

---

# 39. Error Handling + Rate Limiting

From 24.8:

```text
Too many requests
      ↓
429
```

This is not an unexpected server error.

Your error system should understand that.

For example:

```text
Rate limiter
   ↓
429
   ↓
structured response
   ↓
optional security log
```

Not:

```text
429
 ↓
ERROR: server crashed
```

# 40. Error Handling + Logging

From 24.9:

```text
Error
  ↓
Log detailed information
  ↓
Return safe information
```

For example:

### Log

```text
requestId=abc123
error=MongoServerSelectionError
stack=...
```

### Client

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc123"
```

This separation is critical.

# 41. Error Handling + Health Checks

Later you'll have:

```http
GET /health
```

Suppose MongoDB is unavailable.

A health/readiness system can detect:

```text
MongoDB ❌
```

while your error handling records the actual failure:


Together:


# 42. Error Handling + Monitoring

Suppose:

```text
500 errors ↑
```

Monitoring detects the increase.

Then logs tell you:

```text
Why?
```

For example:

```text
500 rate increased
      ↓
logs searched
      ↓
MongoDB timeout
      ↓
database incident
```

This is how production debugging works.

# 43. Error Handling + Docker

Your Node.js process may fail.

Docker can restart the container depending on your configuration.

Conceptually:

```text
Node
 ↓
Fatal failure
 ↓
Process exits
 ↓
Container stops
 ↓
Runtime restarts
 ↓
Application starts
```

This is why application-level error handling and infrastructure-level recovery work together.

---

# 44. Never Hide Errors

Bad:

```js
try {
  await saveTodo();
} catch (error) {
  // ignore
}
```

Now:

```text
Database failure
   ↓
silently ignored
```

The application may continue with inconsistent state.

If you catch an error, you should usually:

```text
handle it
OR
transform it
OR
log it
OR
rethrow it
```

Don't silently swallow important failures.

---

# 45. Don't Over-Catch

Another mistake:

```js
try {
  // entire application
} catch (error) {
  return "Something went wrong";
}
```

This can hide important details and make debugging harder.

Catch errors where you have enough context to make a meaningful decision.

Then allow the centralized error system to handle the rest.

---

# 46. Error Translation

A lower-level error may need to become a domain-level error.

For example:

```text
Mongo duplicate key error
        ↓
Repository/service
        ↓
Email already registered
        ↓
409 Conflict
```

The client shouldn't need to understand:

```text
MongoDB error code 11000
```

Your backend translates infrastructure details into application-level meaning.

---

# 47. Error Boundaries Between Layers

Think of your architecture:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

The repository understands:

```text
database errors
```

The service understands:

```text
business meaning
```

The HTTP layer understands:

```text
HTTP status codes
```

This separation prevents database-specific errors from leaking everywhere.

# 49. Error Context

Good errors carry useful context.

For example:

```text
error
  ↓
operation
  ↓
resource
  ↓
requestId
```

But avoid putting secrets into the error object.

Useful:

```text

userId
operation
requestId
```

Potentially dangerous:

```text

secret
```

# 50. Production Error Checklist

For every important error, ask:

```text
[ ] Is it classified?
[ ] Is the HTTP status correct?
[ ] Is it logged?
[ ] Is sensitive information protected?
[ ] Does the client get a safe message?
[ ] Is the requestId available?
[ ] Can the operation be retried?
[ ] Is a timeout required?
[ ] Can the application continue?
[ ] Should infrastructure restart the process?
```

This is a very strong production checklist.

# 53. Example `AppError`

A simple conceptual implementation:

```js
class AppError extends Error {
  constructor(message, statusCode, code) {
    super(message);

    this.statusCode = statusCode;
    this.code = code;
    this.isOperational = true;
  }
}
```

Then:

```js
throw new AppError(
  "Todo not found",
  404,
  "TODO_NOT_FOUND"
);
```

The error middleware can recognize:

```text
isOperational = true
```

and safely return the appropriate response.

---

# 54. Error Codes

Error codes can make your API easier for frontend clients to handle.

Instead of only:

```json
{
  "message": "Todo not found"
}
```

you can use:

```json
{
  "success": false,
  "code": "TODO_NOT_FOUND",
  "message": "Todo not found"
}
```

Frontend code can then reason about:

```js
if (error.code === "TODO_NOT_FOUND") {
  // handle it
}
```

This is often more stable than depending on human-readable messages.

---

# 55. Don't Overcomplicate Error Codes

You don't need:

```text
ERROR_001
ERROR_002
ERROR_003
```

with hundreds of arbitrary numbers.

Prefer meaningful names:

```text
AUTH_REQUIRED
FORBIDDEN
TODO_NOT_FOUND
EMAIL_ALREADY_EXISTS
RATE_LIMITED
INTERNAL_ERROR
```

This makes debugging easier.

# 🔥 Five Rules to Memorize

### Rule 1

**Centralize error handling.**

```text
Controllers
    ↓
Error middleware
```

### Rule 2

**Different errors deserve different statuses.**

```text
400 → bad request
401 → unauthenticated
403 → forbidden
404 → not found
409 → conflict
429 → rate limited
500 → unexpected server failure
```

### Rule 3

**Log detailed errors, but return safe errors.**

```text
Logs → developers
Response → client
```

### Rule 4

**Operational failures should be designed for.**

Expect:

```text
timeouts
database outages
Redis failures
external API failures
network problems
```

### Rule 5

**Unknown fatal failures may require process termination and restart.**

```text
Fatal error
    ↓
shutdown
    ↓
restart by infrastructure
```

# ⭐ Architecture Challenge

Imagine:

```text
POST /api/v1/orders
       │
       ▼
Order Service
       │
       ├── MongoDB
       │
       └── Payment Provider
```

The payment provider starts timing out.

Design the failure flow:

```text
Timeout
   ↓
?
   ↓
?
   ↓
?
   ↓
Client response
```

Your design should consider:

```text
timeout
logging
requestId
retry
idempotency
safe response
monitoring
```

If you can reason through this correctly, you're moving from **writing Express APIs** toward thinking like a **production backend engineer**.
