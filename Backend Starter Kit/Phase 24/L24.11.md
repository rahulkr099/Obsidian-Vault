# Lesson 24.11 — Health Checks & Readiness Checks

This lesson follows the Phase 24 roadmap in your starter-pack plan:

```text
24.9  Logging
24.10 Error Handling
24.11 Health Checks
24.12 Graceful Shutdown
```

The source specifically separates:

```text
/healthz
    ↓
Is Node alive?

/readyz
    ↓
Is Node + MongoDB + required services ready?
```

Let's understand **why this distinction matters in production**.

---

# 1. What Is a Health Check?

A health check is a small endpoint that answers:

> **Is this application process alive and able to respond?**

For example:

```http
GET /healthz
```

Response:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

Your starter-pack architecture introduces `/healthz` early because it gives you a simple way to prove:

```text
Node
 ↓
Express
 ↓
Route
 ↓
Response
```

is working.

---

# 2. Why Do We Need Health Checks?

Imagine your backend is running inside Docker:

```text
Docker
   ↓
Node.js
   ↓
Express
```

Something goes wrong:

```text
Node process
    ↓
Application stuck
    ↓
Container still exists
```

From the outside, the container may appear to be running.

But:

> **Running does not necessarily mean healthy.**

A health endpoint gives infrastructure something concrete to check.

---

# 3. The Two Important Questions

Production infrastructure usually needs to distinguish between:

### Question 1

> **Is the application alive?**

That's:

```text
/healthz
```

### Question 2

> **Can the application actually serve traffic?**

That's:

```text
/readyz
```

Your roadmap explicitly defines this distinction.

---

# 4. Liveness vs Readiness

The terminology is:

```text
Liveness
   ↓
Is the process alive?

Readiness
   ↓
Is the process ready to receive traffic?
```

Think:

```text
          APPLICATION
               │
       ┌───────┴────────┐
       ▼                ▼
   Liveness          Readiness
   /healthz          /readyz
       │                │
       ▼                ▼
  "I'm alive"     "I'm ready"
```

---

# 5. `/healthz`

A basic liveness endpoint can be extremely simple:

```http
GET /healthz
```

Response:

```json
{
  "success": true,
  "message": "Server is healthy"
}
```

It doesn't need to query every dependency.

Its primary purpose is:

```text
Can the application process respond?
```

---

# 6. `/readyz`

Readiness is more strict.

For example:

```text
/readyz
    ↓
Node running?
    ↓
MongoDB connected?
    ↓
Required services available?
    ↓
YES → ready
```

So:

```text
GET /readyz
```

might return:

```json
{
  "success": true,
  "message": "Server is ready"
}
```

---

# 7. Why Not Just Have One Endpoint?

You might initially think:

```text
/healthz
```

can check everything.

But consider startup.

Your application starts:

```text
Node
 ↓
Express
 ↓
MongoDB connection
```

For a few seconds:

```text
Node = alive
MongoDB = not connected
```

Then:

```text
/healthz → 200
/readyz  → not ready
```

This is useful information.

---

# 8. Startup Example

Imagine:

```text
Application starts
       │
       ▼
Node running
       │
       ▼
Express running
       │
       ▼
MongoDB connecting...
       │
       ├──────────────┐
       │              │
       ▼              ▼
  /healthz         /readyz
    200            not ready
```

After MongoDB connects:

```text
MongoDB connected
       │
       ▼
/healthz → 200
/readyz  → 200
```

This is exactly why the two concepts are useful.

---

# 9. Readiness During Failure

Suppose your application is running:

```text
Node       ✅
Express    ✅
MongoDB    ❌
```

Then:

```text
/healthz → healthy
/readyz  → not ready
```

The application process is alive.

But it shouldn't receive normal database-dependent traffic.

This distinction becomes especially useful when infrastructure manages traffic.

---

# 10. Load Balancer Example

Imagine:

```text
             Load Balancer
              /    |    \
             /     |     \
           API-A API-B API-C
```

Suppose:

```text
API-A → ready
API-B → not ready
API-C → ready
```

The load balancer/platform can avoid sending normal traffic to API-B.

Conceptually:

```text
           Load Balancer
             │
      ┌──────┼──────┐
      ▼      ▼      ▼
     A      B      C
    ✅     ❌     ✅
     │             │
     └──────┬──────┘
            ▼
        traffic
```

---

# 11. Docker Health Checks

This becomes especially relevant after your Docker phase.

A container can have a health check conceptually like:

```text
Container
    ↓
GET /healthz
    ↓
200?
```

If the check repeatedly fails:

```text
Healthy
   ↓
Unhealthy
```

Infrastructure can then react according to its configuration.

---

# 12. Kubernetes Connection

This becomes even more important with Kubernetes.

Kubernetes commonly uses concepts such as:

```text
liveness probe
readiness probe
```

The mental mapping is:

```text
/healthz
    ↓
Liveness

/readyz
    ↓
Readiness
```

So the simple endpoints you're learning now prepare you for larger production environments later.

---

# 13. What Should `/healthz` Check?

Keep liveness simple.

For example:

```text
Node process
Express
basic application state
```

You generally don't want:

```text
/healthz
    ↓
MongoDB
Redis
Email
Payment API
AI API
10 external services
```

because now a temporary dependency failure can make your process appear dead.

That's not what liveness is supposed to answer.

---

# 14. What Should `/readyz` Check?

Readiness can check dependencies required to serve traffic.

For your MERN backend:

```text
/readyz
    │
    ├── Node process
    ├── MongoDB
    └── required application dependencies
```

For example:

```text
MongoDB connected?
      │
      ├── YES → ready
      └── NO  → not ready
```

---

# 15. Health Check Status Codes

A healthy endpoint might return:

```http
200 OK
```

If readiness fails, you might return an appropriate non-success status such as:

```http
503 Service Unavailable
```

Conceptually:

```text
Ready
  ↓
200

Not ready
  ↓
503
```

This lets infrastructure understand the difference automatically.

---

# 16. Example `/healthz`

A simple Express route:

```js
router.get("/healthz", (req, res) => {
  res.status(200).json({
    success: true,
    message: "Server is healthy"
  });
});
```

This is intentionally boring.

That's good.

A health endpoint should be:

> **Simple, fast, and dependable.**

---

# 17. Example `/readyz`

Conceptually:

```js
router.get("/readyz", async (req, res) => {
  const databaseReady = checkDatabaseConnection();

  if (!databaseReady) {
    return res.status(503).json({
      success: false,
      message: "Server is not ready"
    });
  }

  return res.status(200).json({
    success: true,
    message: "Server is ready"
  });
});
```

The exact MongoDB check depends on how your database connection layer is implemented.

The important architecture is:

```text
ready?
   │
   ├── yes → 200
   │
   └── no  → 503
```

---

# 18. Don't Expose Too Much Information

A common mistake is returning:

```json
{
  "mongodb": "mongodb://admin:password@internal-server",
  "redis": "redis://...",
  "apiKey": "...",
  "databaseError": "..."
}
```

Absolutely not.

A health endpoint can become publicly accessible.

Return safe information.

For example:

```json
{
  "success": false,
  "message": "Server is not ready"
}
```

Detailed information belongs in logs.

---

# 19. Health Checks + Logging

This connects directly to Lesson 24.9.

Suppose:

```text
/readyz
   ↓
MongoDB unavailable
```

The endpoint can safely return:

```json
{
  "success": false,
  "message": "Server is not ready"
}
```

while your internal logs contain:

```text
database.connection.failed
requestId=...
error=...
```

So:

```text
Client/infrastructure
        ↓
safe health response

Operations team
        ↓
detailed logs
```

---

# 20. Health Checks + Error Handling

From Lesson 24.10:

Not every health failure should be treated as an application crash.

For example:

```text
MongoDB temporarily unavailable
```

may mean:

```text
/readyz
   ↓
503
```

while the Node process remains alive.

So:

```text
Error handling
+
Readiness
```

work together.

---

# 21. Health Checks + Startup

Your earlier architecture says:

```text
Application starts
       ↓
Load environment
       ↓
Connect MongoDB
       ↓
Connection successful?
       │
       ├── NO → exit
       │
       └── YES
             ↓
        Start Express
```

This startup sequence is important because required infrastructure should be ready before the application starts accepting normal traffic.

But readiness checks still matter because dependencies can fail **after startup**.

---

# 22. Startup vs Runtime Failure

### Startup failure

```text
Node starts
 ↓
MongoDB connection fails
 ↓
Application cannot operate
 ↓
Process exits
```

### Runtime failure

```text
Node starts
 ↓
MongoDB connected
 ↓
Application serves traffic
 ↓
MongoDB later becomes unavailable
```

In the second case:

```text
Node = alive
MongoDB = unavailable
```

Therefore:

```text
/healthz → alive
/readyz  → not ready
```

That's the power of separating the two.

---

# 23. Dependency Health

Imagine your backend eventually uses:

```text
MongoDB
Redis
Email queue
Object storage
```

You could conceptually have:

```text
READINESS
    │
    ├── MongoDB      ✅
    ├── Redis        ✅
    ├── Queue        ❌
    └── Storage      ✅
```

Then the readiness decision depends on which services are **actually required** for the application to serve traffic.

Don't automatically make every optional dependency critical.

---

# 24. Required vs Optional Dependencies

Suppose your API can work without email temporarily:

```text
MongoDB → required
Email → optional
```

Then:

```text
MongoDB ❌
→ not ready
```

But:

```text
Email ❌
→ maybe still ready
```

This is an architectural decision.

Ask:

> **Can the application safely serve its primary traffic without this dependency?**

If yes, it may not belong in the readiness gate.

---

# 25. Health Check Security

Health endpoints should not become an information leak.

Avoid exposing:

```text
database hostname
internal IP
credentials
environment variables
stack traces
dependency versions
secret configuration
```

A public endpoint should return minimal information.

---

# 26. Authentication on Health Endpoints?

Usually, infrastructure needs to reach health endpoints easily.

So you generally don't want:

```text
GET /healthz
    ↓
JWT required
```

because your infrastructure would then need authentication credentials just to determine whether the service is alive.

Instead, keep the endpoint simple and protect sensitive diagnostic information elsewhere.

---

# 27. Health vs Detailed Diagnostics

These are different concepts.

### Health

```text
/healthz
```

Answers:

```text
Am I alive?
```

### Readiness

```text
/readyz
```

Answers:

```text
Can I serve traffic?
```

### Detailed diagnostics

Could potentially provide internal information such as:

```text
database latency
memory
queue state
dependency details
```

but such endpoints should be carefully protected.

Don't turn `/healthz` into a complete debugging dashboard.

---

# 28. Health Check Performance

Health endpoints should be fast.

Bad:

```text
/healthz
   ↓
run 50 database queries
   ↓
call 10 APIs
   ↓
wait 20 seconds
```

Now the health check itself becomes a problem.

Prefer:

```text
/healthz
   ↓
minimal check
   ↓
fast response
```

For readiness:

```text
/readyz
   ↓
small set of required dependency checks
   ↓
fast response
```

---

# 29. Avoid Dependency Cascades

Suppose:

```text
Load Balancer
   ↓
/readyz
   ↓
MongoDB
   ↓
another service
   ↓
another service
```

You have created:

```text
Health check
    ↓
dependency chain
```

This can become fragile.

Your health system should itself be resilient and simple.

---

# 30. Monitoring Health Checks

Your monitoring system can periodically call:

```text
GET /healthz
GET /readyz
```

For example:

```text
Every few seconds
       ↓
/healthz
       ↓
200?
```

and:

```text
Every few seconds
       ↓
/readyz
       ↓
200?
```

Then it can detect:

```text
healthy
unhealthy
not ready
```

---

# 31. Health Checks Are Not Monitoring

Important distinction:

```text
Health check
    ↓
Current state

Monitoring
    ↓
State over time
```

For example:

```text
/readyz → 503
```

tells you:

> It isn't ready right now.

Monitoring can tell you:

```text
It has been unavailable for 8 minutes.
```

And logging can tell you:

```text
MongoDB connection started failing at 23:12.
```

So:

```text
Health
+
Logs
+
Metrics
+
Monitoring
```

give you a much better operational picture.

---

# 32. The Three-Layer Mental Model

Keep this:

```text
             APPLICATION
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
   /healthz    /readyz      logs
       │          │           │
       ▼          ▼           ▼
    alive?      ready?      why?
```

And monitoring sits above them:

```text
Health / Readiness / Logs
          ↓
      Monitoring
          ↓
        Alerts
```

---

# 33. A Real Failure Scenario

Imagine your production backend:

```text
API instances:
A ✅
B ✅
C ✅
```

MongoDB suddenly becomes unavailable.

The instances are still running:

```text
A → Node alive
B → Node alive
C → Node alive
```

So:

```text
/healthz
A → 200
B → 200
C → 200
```

But:

```text
/readyz
A → 503
B → 503
C → 503
```

Now your infrastructure understands:

> The processes are alive, but they aren't ready to serve normal database-dependent traffic.

That's a much more useful signal than simply saying:

```text
"Server is down."
```

---

# 34. Health Checks During Deployment

This is another major use.

Suppose you're deploying:

```text
Version 1
    ↓
Version 2
```

New instance starts:

```text
Node starts
 ↓
MongoDB connects
 ↓
Application initializes
 ↓
/readyz = 200
```

Only then should infrastructure consider it ready for normal traffic.

Conceptually:

```text
New instance
     ↓
Starting
     ↓
Not ready
     ↓
Initialization complete
     ↓
Ready
     ↓
Receive traffic
```

This prevents traffic from reaching an instance that isn't prepared yet.

---

# 35. Health Checks During Shutdown

This connects directly to the **next lesson: graceful shutdown**.

When an instance is shutting down:

```text
Running
   ↓
Shutdown requested
   ↓
Stop accepting traffic
   ↓
Become not ready
   ↓
Finish existing work
   ↓
Close dependencies
   ↓
Exit
```

So readiness is also useful during termination.

The sequence is roughly:

```text
READY
  ↓
NOT READY
  ↓
DRAIN
  ↓
SHUT DOWN
```

We'll explore this deeply in Lesson 24.12.

---

# 36. Where Should Health Routes Live?

A clean architecture might use:

```text
routes/
└── health.routes.js
```

and:

```text
GET /healthz
GET /readyz
```

Alternatively, very small health routes can be registered directly in `app.js`.

The important thing is to keep health functionality easy to find and independent of business features.

---

# 37. Don't Put Health Logic in Controllers

You don't need:

```text
TodoController
UserController
HealthController
```

just because every endpoint must have a controller.

Health endpoints are infrastructure endpoints.

A simple route/handler can be perfectly reasonable.

The architectural principle is:

> **Don't create abstractions just for the sake of having abstractions.**

---

# 38. A Practical Health Architecture

For your MERN starter, think:

```text
routes/
└── health.routes.js

config/
└── db.js

app.js
server.js
```

Flow:

```text
GET /healthz
      ↓
health route
      ↓
simple response
```

and:

```text
GET /readyz
      ↓
health route
      ↓
check required dependencies
      ↓
200 / 503
```

# 40. What Not to Do

Avoid this:

```json
{
  "node": "v24.x",
  "mongoHost": "internal-db.example.com",
  "mongoUser": "admin",
  "mongoPassword": "...",

```

Even if you're thinking:

> "It's useful for debugging."

# 🧠 Core Mental Model

Memorize this:

```text
                 SERVER
                   │
          ┌────────┴────────┐
          ▼                 ▼
      /healthz           /readyz
          │                 │
          ▼                 ▼
      "Am I alive?"    "Can I serve?"
          │                 │
          ▼                 ▼
       Process          Dependencies
         state              state
```

The easiest way to remember it:

> **Liveness asks "Am I alive?" Readiness asks "Am I ready?"**

---

# 🔥 Five Rules to Memorize

### Rule 1

`/healthz` should be **simple and fast**.

### Rule 2

`/readyz` checks whether required dependencies are available.

### Rule 3

A server can be:

```text
alive ✅
but not ready ❌
```

### Rule 4

Don't expose secrets or detailed infrastructure information through health endpoints.

### Rule 5

Health checks work together with:

```text
Logs
+
Metrics
+
Monitoring
+
Container orchestration
```

They are not a replacement for those systems.
