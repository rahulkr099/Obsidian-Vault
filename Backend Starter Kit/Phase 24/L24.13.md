# Lesson 24.13 — Docker

This lesson is explicitly **24.13 Docker** in your Phase 24 roadmap, after Health Checks and Graceful Shutdown, and before Reverse Proxy, Deployment Architecture, and the Production Checklist.

Your roadmap treats Docker as a production-hardening concern, while Phase 23 already introduced Docker fundamentals. So here, the goal is **not to learn Docker from zero again**. The goal is to understand how Docker fits into the production backend you've built.

---

# 1. What Problem Does Docker Solve?

Without Docker, your backend might depend on:

```text
Node.js version
npm version
MongoDB
Linux packages
environment variables
system configuration
```

Imagine:

```text
Your computer
Node 24
MongoDB 8
Linux Mint
```

But your server has:

```text
Node 22
MongoDB 7
different Linux
different packages
```

Your application might behave differently.

Docker gives us a standardized environment:

```text
Application
    +
Dependencies
    +
Runtime
    ↓
Docker Image
    ↓
Container
```

---

# 2. Image vs Container

This distinction is fundamental.

## Docker Image

An image is the **blueprint**.

```text
Dockerfile
    ↓
Docker Image
```

## Container

A container is a **running instance of that image**.

```text
Docker Image
    ↓
Container
```

Think:

```text
Class
 ↓
Object
```

Similar idea:

```text
Image
 ↓
Container
```

You can create multiple containers from the same image.

---

# 3. Your MERN Backend

Your backend might look like:

```text
backend/
├── src/
├── package.json
├── package-lock.json
├── Dockerfile
└── .dockerignore
```

Docker turns this into:

```text
backend source
      ↓
Dockerfile
      ↓
Docker image
      ↓
running container
      ↓
Node.js + Express
```

---

# 4. What Actually Goes Inside the Container?

A backend container might contain:

```text
Container
│
├── Node.js
├── npm
├── application source
├── package.json
├── installed dependencies
└── application process
```

But importantly:

> **MongoDB does not have to be inside the same container.**

A common architecture is:

```text
┌───────────────┐
│ API Container │
│ Node + Express│
└───────┬───────┘
        │
        ▼
┌───────────────┐
│ MongoDB       │
│ Container     │
└───────────────┘
```

Or MongoDB can be an external managed service.

---

# 5. One Container = One Main Responsibility

A useful production principle is:

```text
API container
     ↓
Node.js application
```

and separately:

```text
MongoDB
     ↓
Database
```

Avoid thinking:

```text
One giant container
├── Node
├── MongoDB
├── Redis
├── Nginx
└── background worker
```

That makes lifecycle management harder.

Instead:

```text
API
 │
 ├── MongoDB
 ├── Redis
 └── Worker
```

with each component having an appropriate runtime/container.

---

# 6. Dockerfile

The Dockerfile tells Docker:

> **How should I build the application image?**

A simplified Node backend Dockerfile might look like:

```dockerfile
FROM node:24-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "src/server.js"]
```

Don't memorize it yet.

Understand the sequence.

```text
Base image
    ↓
Working directory
    ↓
Dependencies
    ↓
Application
    ↓
Port metadata
    ↓
Start command
```

---

# 7. `FROM`

```dockerfile
FROM node:24-alpine
```

This says:

> Start with an image that already contains Node.js.

So instead of installing Node manually:

```text
Linux
 ↓
download Node
 ↓
configure Node
 ↓
install npm
```

Docker starts from a Node image.

Conceptually:

```text
Node Docker Image
      ↓
Your application
```

---

# 8. Why Alpine?

You may see:

```text
node:24-alpine
```

instead of:

```text
node:24
```

Alpine is a small Linux distribution commonly used for compact images.

Conceptually:

```text
node:24
    ↓
larger base

node:24-alpine
    ↓
smaller base
```

Smaller images can mean:

```text
less storage
faster transfers
smaller attack surface
```

But Alpine isn't automatically the best choice for every Node application. Native dependencies can sometimes make other Node base images simpler.

The important lesson:

> **Choose the base image deliberately.**

---

# 9. `WORKDIR`

```dockerfile
WORKDIR /app
```

This tells Docker:

> Use `/app` as the application's working directory.

Then:

```text
/app
```

becomes your project directory inside the container.

So:

```dockerfile
COPY . .
```

means roughly:

```text
local project
     ↓
/app
```

---

# 10. Copy `package.json` First

Notice:

```dockerfile
COPY package*.json ./

RUN npm ci
```

comes before:

```dockerfile
COPY . .
```

This is deliberate.

Docker builds images in layers.

If your source code changes but:

```text
package.json
package-lock.json
```

don't change, Docker can potentially reuse the dependency-installation layer.

So:

```text
package files
     ↓
npm ci
     ↓
application source
```

is generally better than blindly copying everything first.

---

# 11. Docker Layers

Think:

```text
Layer 1
FROM node

Layer 2
WORKDIR

Layer 3
package.json
package-lock.json

Layer 4
npm ci

Layer 5
application source
```

If only your controller changes:

```text
controllers/user.controller.js
```

you don't necessarily want Docker to reinstall every dependency.

That's why Dockerfile ordering matters.

---

# 12. `npm ci` vs `npm install`

For production image builds, you'll commonly see:

```dockerfile
RUN npm ci
```

instead of:

```dockerfile
RUN npm install
```

`npm ci` is designed for clean, reproducible installs using the lockfile.

Conceptually:

```text
package-lock.json
       ↓
     npm ci
       ↓
exact dependency tree
```

This is particularly useful in CI/CD and production builds.

---

# 13. Copy Application Source

After installing dependencies:

```dockerfile
COPY . .
```

Now:

```text
/app
├── node_modules
├── package.json
├── package-lock.json
└── src
```

exists inside the image.

---

# 14. `EXPOSE`

You may write:

```dockerfile
EXPOSE 5000
```

This communicates:

> The application expects to listen on port 5000.

But remember:

> `EXPOSE` does not itself publish the port to your host.

You still need runtime configuration such as:

```bash
docker run -p 5000:5000 ...
```

Conceptually:

```text
Host : 5000
     │
     ▼
Container : 5000
```

---

# 15. `CMD`

Finally:

```dockerfile
CMD ["node", "src/server.js"]
```

means:

> When the container starts, run the Node server.

So:

```text
docker run
    ↓
container starts
    ↓
node src/server.js
    ↓
Express starts
```

---

# 16. Docker Build

Once you have:

```text
Dockerfile
```

you build an image.

Conceptually:

```bash
docker build -t my-backend .
```

The flow:

```text
Dockerfile + source
        ↓
    docker build
        ↓
    Docker image
```

Now you have something like:

```text
my-backend
```

---

# 17. Docker Run

Then:

```bash
docker run -p 5000:5000 my-backend
```

The flow:

```text
Docker image
     ↓
docker run
     ↓
container
     ↓
Node
     ↓
Express
```

Your API can then be accessed through the published port.

---

# 18. Important: `localhost` Changes Meaning

This is one of the biggest Docker beginner mistakes.

Suppose your API container tries:

```text
mongodb://localhost:27017
```

Inside the API container:

```text
localhost
```

means:

> **The API container itself.**

It does **not** automatically mean:

> My host machine.

And it definitely doesn't mean:

> The MongoDB container.

---

# 19. API + MongoDB Containers

Suppose:

```text
API container
MongoDB container
```

You need them to communicate over a Docker network.

Conceptually:

```text
┌──────────────┐
│ API          │
│              │
│ Node         │
└──────┬───────┘
       │
       │ Docker network
       ▼
┌──────────────┐
│ MongoDB      │
└──────────────┘
```

Then your database hostname can be the MongoDB service/container name rather than `localhost`.

For example:

```text
mongodb://mongo:27017/myapp
```

where:

```text
mongo
```

is the Docker service name.

---

# 20. Docker Compose

This is where Docker becomes much easier for multi-container applications.

Instead of manually starting:

```text
API
MongoDB
Redis
```

you can describe them in:

```text
docker-compose.yml
```

Conceptually:

```yaml
services:
  api:
    ...
  
  mongo:
    ...
```

Then:

```text
docker compose up
```

can bring the environment up together.

Your Phase 23 roadmap explicitly includes Docker Compose and Node + MongoDB as part of the Docker architecture.

# 21. Your Development Architecture

A local Docker environment might look like:

```text
                 Docker Compose
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
     API container             Mongo container
          │                         │
          │                         │
       Node.js                  MongoDB
          │
       Express
```

Your application talks to:

```text

```

rather than:

```text

```

when MongoDB is another Compose service.

# 22. Environment Variables

Never bake secrets into the Dockerfile.

Bad:

```dockerfile
ENV MONGO_URI="mongodb://user:password@..."
```

Don't put:

```text
JWT secret
database password
API keys
SMTP password
```

into the image.

Remember your Phase 24.2:

```text
Environment secrets
```

and the roadmap's production-hardening checklist includes environment variables and secrets.

Instead:

```text
Container
    ↑
Environment variables
    ↑
Deployment platform
```

---

# 23. Image vs Configuration

This is a powerful production principle.

Your image should contain:

```text
application code
dependencies
runtime
```

But environment-specific configuration should come from outside:

```text
development
staging
production
```

So:

```text
SAME IMAGE
   │
   ├── development config
   ├── staging config
   └── production config
```

This allows the same application artifact to move between environments.

---

# 24. `.dockerignore`

Your project should generally have:

```text
.dockerignore
```

You don't want to send unnecessary files into the Docker build context.

Typical examples:

```text
node_modules
.git
.env
npm-debug.log
coverage
```

The exact list depends on your project.

Important:

> **Don't blindly copy `.env` into the image.**

Secrets should stay outside the image.

---

# 25. Why `node_modules` Should Usually Be Ignored

Your local machine might have:

```text
node_modules/
```

with thousands of files.

You don't want:

```text
local node_modules
       ↓
Docker build context
       ↓
copy into image
```

Instead:

```text
package.json
package-lock.json
       ↓
npm ci
       ↓
container node_modules
```

This is cleaner and more reproducible.

# 26. Development vs Production

Your roadmap explicitly distinguishes:

```text
23.6 Production Dockerfile
23.7 Development Dockerfile
```

Why?

Because development and production have different requirements.

### Development

You want:

```text
hot reload
source mounting
debugging
nodemon
fast iteration
```

### Production

You want:

```text
small image
deterministic dependencies
no unnecessary tools
secure configuration
stable startup
```

Don't force one environment to behave exactly like the other.

# 27. Development Docker Architecture

Conceptually:

```text
      │
      ▼

      ▼

      │
      ▼
```

# 28. Production Docker Architecture

Production is different:

```text
Source
  ↓
Docker build
  ↓
Immutable image
  ↓
Deploy image
  ↓
Container
  ↓
Node
```

You don't normally want someone manually editing:

```text
/app/src
```

inside the production container.

Instead:

> Build a new image and deploy it.

---

# 29. Immutable Deployment

This gives us a powerful concept:

```text
Version 1
   ↓
Docker image v1
```

Then:

```text
Version 2
   ↓
Docker image v2
```

Deploy:

```text
v2
```

If something goes wrong:

```text
rollback → v1
```

This is much cleaner than manually changing files on a server.

---

# 30. Multi-Stage Builds

Production Dockerfiles can use:

```text
multi-stage builds
```

Conceptually:

```text
Build stage
    ↓
install/build
    ↓
Production stage
    ↓
only required files
```

For example:

```text
Stage 1
├── dependencies
├── build
└── temporary tools

        ↓

Stage 2
├── runtime
├── production dependencies
└── application
```

The final image can therefore be smaller and cleaner.

---

# 31. Why Multi-Stage Builds Matter

Suppose your build needs:

```text
compilers
development dependencies
build tools
```

But the running application doesn't.

You don't want all of those in production.

So:

```text
BUILD ENVIRONMENT
       ↓
produce artifact
       ↓
RUNTIME ENVIRONMENT
```

This reduces unnecessary components in the final image.

---

# 32. Production Dependencies

Another production concern:

```text
devDependencies
```

may not be needed at runtime.

For example:

```text
Jest
ESLint
testing tools
development utilities
```

don't necessarily belong in the final runtime environment.

The exact approach depends on your application and build process.

This is important.

Docker doesn't magically make:

```text
bad code
```

```text
Services

```

# 37. Docker Doesn't Replace Security

A container does not automatically protect your application.

You still need:

```text
HTTPS
authentication
authorization
validation
rate limiting
secure cookies
secret management
dependency security
database security
```

Your roadmap deliberately puts Docker **after** the backend and security architecture because the container is only one part of production security.

---

# 38. Docker Doesn't Mean "Everything Is Secure"

For example:

```text
FROM node:latest
```

isn't automatically a secure production strategy.

You should think about:

```text
base image
dependencies
OS packages
user privileges
secrets
network exposure
image scanning
updates
```

Docker gives you isolation and packaging, but security still requires deliberate design.

---

# 39. Don't Run as Root Without Thinking

Containers can run processes as:

```text
root
```

by default depending on the image/configuration.

For production, you should consider using a non-root user where practical.

Conceptually:

```text
root
  ↓
too much privilege

non-root
  ↓
reduced privilege
```

This follows the security principle:

> **Least privilege.**

# 40. Port Exposure

Suppose Express listens on:

```text
5000
```

Inside the container:

```text
Node
 ↓
0.0.0.0:5000
```

You can publish it:

```text
Host:5000
    ↓
Container:5000
```

But in production, you may eventually have:

```text
Internet
   ↓
Reverse Proxy
   ↓
API container
```

which is exactly why **24.14 Reverse Proxy** comes next.

---

# 41. Why Bind to `0.0.0.0`?

Inside a container, this matters.

If Node listens only on:

```text
127.0.0.1
```

it may only accept connections from inside the container.

For containerized applications, you commonly want:

```text
0.0.0.0
```

so the application accepts connections through the container's network interface.

Conceptually:

```text
127.0.0.1
   ↓
inside container only

0.0.0.0
   ↓
container interfaces
```


are all on a Docker network.

Then:

```text

```

can communicate using service names.

Conceptually:

```text
Docker network
```

# 43. Volumes

MongoDB needs persistent data.

You don't want:

```text
MongoDB container
     ↓
container deleted
     ↓
database disappears
```

Instead:

```text
MongoDB container
       │
       ▼
Docker volume
       │
       ▼
persistent data
```

Your Phase 23 roadmap explicitly includes Docker volumes.

---

# 44. API Containers Are Usually Disposable

Your API container should generally be treated differently from your database storage.

API:

```text
container
   ↓
replaceable
```

Database data:

```text
volume / managed database
   ↓
persistent
```

So:

```text
API container → disposable
Database data → persistent
```

This is a very important production mindset.

---

# 45. Stateless API

A well-designed API should ideally be mostly stateless.

For example:

```text
API-A
API-B
API-C
```

can all serve requests.

```text
             Load Balancer
             /     |     \
            A      B      C
```

If API-A disappears:

```text
A ❌
B ✅
C ✅
```

the system can continue serving traffic.

Docker makes this pattern easier to deploy.

---

# 46. Don't Store Important Data Inside the Container

Bad:

```text
/app/uploads
```

if those files must survive container replacement.

Because:

```text
container deleted
      ↓
files potentially lost
```

For persistent user files, consider:

```text
object storage
```

or a properly managed persistent volume depending on the architecture.

---

# 47. Logging in Containers

Remember Lesson 24.9.

A containerized application should generally write logs in a way that the container runtime/platform can collect.

Conceptually:

```text
Node
 ↓
stdout/stderr
 ↓
Docker
 ↓
log collection
 ↓
monitoring
```

Don't design your production logging around:

```text
some random log file inside container
```

that disappears when the container is replaced.

# 🔥 Five Rules to Memorize

**Image = blueprint. Container = running instance.**

### Rule 2

**Dockerfile builds one application's image.**

### Rule 3

**Docker Compose coordinates multiple containers.**

### Rule 4

### Rule 5

**Treat API containers as replaceable.**
