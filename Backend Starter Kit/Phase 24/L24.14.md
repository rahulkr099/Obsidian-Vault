# Lesson 24.14 — Reverse Proxy

Your Phase 24 roadmap defines **24.14 as Reverse Proxy**, directly after Docker and Graceful Shutdown, and immediately before Deployment Architecture.

The important goal of this lesson is not just learning Nginx commands. You should understand **why a production Node.js backend normally sits behind another server**.

---

# 1. What Is a Reverse Proxy?

A reverse proxy is a server that sits **in front of your backend**.

Instead of:

```text
Browser
   ↓
Node.js
```

production often looks like:

```text
Browser
   ↓
Reverse Proxy
   ↓
Node.js
```

The reverse proxy receives the client's request and decides where to send it.

A common reverse proxy is **Nginx**.

---

# 2. Why Do We Need One?

You might ask:

> "Express can already receive HTTP requests. Why add another server?"

Because production has additional responsibilities.

A reverse proxy can handle things like:

```text
HTTPS
TLS certificates
domain routing
traffic forwarding
request limits
static files
compression
connection handling
load balancing
security boundaries
```

while Node focuses mainly on:

```text
application logic
```

---

# 3. Simple Analogy

Imagine a large office.

The client arrives at:

```text
🏢 Company
```

They don't directly walk into the employee's room.

Instead:

```text
Visitor
   ↓
Reception desk
   ↓
Correct department
   ↓
Employee
```

Reverse proxy:

```text
Client
   ↓
Nginx
   ↓
Express
```

Nginx is like the reception desk.

# 5. The Request Flow

Suppose your API endpoint is:

```text
GET https://api.example.com/api/v1/users
```

The request travels approximately like:

```text
Browser
   │
   │ HTTPS
   ▼
Nginx
   │
   │ HTTP/internal network
   ▼
Node.js
   │
   ▼
Express
   │
   ▼
Route
   │
   ▼
Controller
```

Then the response travels back:

```text
Controller
   ↓
Express
   ↓
Node
   ↓
Nginx
   ↓
HTTPS
   ↓
Browser
```

---

# 6. Reverse Proxy vs Forward Proxy

This distinction is important.

### Forward proxy

Acts on behalf of the **client**.

```text
Client
   ↓
Forward Proxy
   ↓
Internet
```

### Reverse proxy

Acts on behalf of the **server/application**.

```text
Internet
   ↓
Reverse Proxy
   ↓
Backend
```

For your backend architecture, we're interested in the second one.

---

# 7. Why Not Expose Node Directly?

You technically can:

```text
Internet
   ↓
Node : 5000
```

But production architecture often prefers:

```text
Internet
   ↓
Nginx : 443
   ↓
Node : 5000
```

Now Node doesn't need to directly handle the public HTTPS endpoint.

Nginx becomes the public-facing layer.

---

# 8. Port 443

HTTPS normally uses:

```text
443
```

So:

```text
https://api.example.com
```

typically reaches:

```text
Nginx : 443
```

Then Nginx forwards internally:

```text
Nginx : 443
     ↓
Node : 5000
```

So you can have:

```text
Public:
443

Internal:
5000
```

---

# 9. Nginx as the Traffic Entry Point

Think of Nginx as your application's **front door**.

```text
                 INTERNET
                    │
                    ▼
              ┌───────────┐
              │   NGINX   │
              │           │
              │   :443    │
              └─────┬─────┘
                    │
                    ▼
              ┌───────────┐
              │   NODE    │
              │ Express   │
              │   :5000   │
              └───────────┘
```

Only Nginx needs to be directly exposed publicly in this architecture.

# 10. Reverse Proxy Configuration

A simplified Nginx configuration looks like:

```nginx
server {
    listen 80;

    server_name api.example.com;

    location / {
        proxy_pass http://api:5000;
    }
}
```

Conceptually:

```text
Request
   ↓
api.example.com
   ↓
Nginx
   ↓
api:5000
```

Here:

```text
api
```

could be the Docker Compose service name.

# 11. Docker + Reverse Proxy

This connects directly to Lesson 24.13.

Imagine:

```text
Docker network
──────────────────────────────
│                            │
│   ┌───────────┐            │
│   │   nginx   │            │
│   │   :80     │            │
│   └─────┬─────┘            │
│         │                  │
│         ▼                  │
│   ┌───────────┐            │
│   │    api    │            │

│   └───────────┘            │
│                            │
```

```text
http://api:5000
```

rather than:

```text
http://localhost:5000
```

because `api` is the service name on the Docker network.

---

# 12. Why `localhost` Again?

Remember the Docker lesson.

Inside the Nginx container:

```text
localhost
```

means:

> Nginx container itself.

It does **not** mean the API container.

So:

```text
proxy_pass http://localhost:5000;
```

is often wrong when Nginx and Node are separate containers.

Instead:

```text
proxy_pass http://api:5000;
```

where:

```text
api
```

is the backend service.

---

# 13. HTTPS at the Reverse Proxy

This is one of the biggest reasons for using a reverse proxy.

Your architecture can become:

```text
Client
   │
   │ HTTPS
   ▼
Nginx
   │
   │ HTTP/internal
   ▼
Node
```

Nginx handles the public TLS connection.

Node can communicate over the protected internal Docker/private network.

---

# 14. TLS Termination

The process is commonly called:

> **TLS termination**

Conceptually:

```text
HTTPS
  │
  ▼
Nginx
  │
  ├── decrypt TLS
  │
  ▼
HTTP/internal request
  │
  ▼
Node
```

The reverse proxy terminates the client's TLS connection.

---

# 15. Why This Is Useful

Instead of configuring TLS separately on every Node instance:

```text
API-1 → TLS
API-2 → TLS
API-3 → TLS
```

you can have:

```text
             TLS
              ↓
            Nginx
          /   |   \
         ↓    ↓    ↓
       API1 API2 API3
```

Now the public TLS layer is centralized.

# 17. Domain Routing

A reverse proxy can route different domains.

For example:

```text
api.example.com
      ↓
API server

admin.example.com
      ↓
Admin application

example.com
      ↓
Frontend
```

Conceptually:

```text
                   Nginx
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
 api.example    admin.example   example.com
      │              │              │
      ▼              ▼              ▼
     API          Admin API       Frontend
```

This is one of the reasons reverse proxies are powerful.

---

# 18. Path-Based Routing

You can also route based on paths.

For example:

```text
/api/
```

goes to the backend.

```text
/
```

could go to the frontend.

Conceptually:

```text
example.com/
      ↓
Frontend

example.com/api/
      ↓
Backend
```

This can be useful when frontend and backend share a domain.

# 19. Reverse Proxy and CORS

This becomes interesting.

Suppose your architecture is:

```text
Frontend:
https://example.com

Backend:
https://api.example.com
```

These are different origins.

Therefore CORS still matters.

But if you use:

```text
https://example.com
```

for the frontend and:

```text
https://example.com/api
```

for the backend, the browser sees them as the same origin.

The reverse proxy can therefore help you design cleaner origin architecture.

But:

> **A reverse proxy does not magically replace CORS configuration.**

Your Express CORS policy still needs to be deliberate.

---

# 20. Reverse Proxy and Cookies

This connects to:

```text
24.5 Cookies in production
```

Suppose authentication uses:

```text
HttpOnly
Secure
SameSite
```

cookies.

The browser communicates with:

```text
https://example.com
```

while Nginx forwards the request internally.

You need to ensure proxy headers and application configuration correctly represent the original HTTPS request.

This becomes particularly important for secure cookies and Express's `trust proxy` configuration.

---

# 21. `X-Forwarded-*` Headers

When Nginx forwards a request, Node may need to know:

```text
original protocol
original client IP
original host
```

Common proxy headers include:

```text
X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host
```

Conceptually:

```text
Browser
   │
   │ client IP = 203.x.x.x
   ▼
Nginx
   │
   │ X-Forwarded-For: 203.x.x.x
   ▼
Node
```

Without these headers, your backend may see the proxy as the client.

---

# 22. Why Client IP Matters

Your backend might use client IP for:

```text
rate limiting
logging
security monitoring
audit information
```

Suppose the real client is:

```text
203.0.113.10
```

but Node sees:

```text
172.x.x.x
```

because the request came from Nginx.

You need proper proxy configuration so Express can correctly interpret forwarded client information.

---

# 23. Express `trust proxy`

When Express is behind a trusted reverse proxy, you may configure:

```js
app.set("trust proxy", 1);
```

The exact value depends on your network topology.

This tells Express that it can trust the proxy layer for certain forwarded information.

This is important for things such as:

```text
req.ip
req.protocol
secure cookies
```

But don't blindly set:

```js
app.set("trust proxy", true);
```

without understanding your deployment topology.

Trusting arbitrary proxy headers can create security problems.

# 25. Reverse Proxy and Request Size

A reverse proxy can also enforce limits on incoming requests.

For example:

```text
maximum request body size
```

This gives you another protection layer.

Your backend might have:

```js
express.json({
    limit: "1mb"
});
```

while the proxy has its own request-size controls.

Defense in depth is useful.

# 26. Reverse Proxy and Compression

A reverse proxy can potentially handle compression.

Conceptually:

```text
Node
  ↓
response
  ↓
Nginx compresses
  ↓
Browser
```

This can reduce response size.

However, don't blindly enable every optimization.

Measure your actual workload and understand where compression belongs.

# 27. Reverse Proxy and Static Files

If your application serves static assets, Nginx can serve them efficiently:

```text
GET /assets/app.js
        ↓
Nginx
        ↓
file
```

instead of:

```text
GET /assets/app.js
        ↓
Node
        ↓
file
```

For a React SPA, a common production architecture can therefore be:

```text
Nginx
├── frontend static files
└── /api → Node backend
```

# 28. Reverse Proxy and Load Balancing

This is one of the most important features.

Suppose you have:

```text
API-1
API-2
API-3
```

Nginx can distribute requests:

```text
                 Nginx
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
        API-1    API-2    API-3
```

Request 1:

```text
→ API-1
```

Request 2:

```text
→ API-2
```

Request 3:

```text
→ API-3
```

This is called **load balancing**.

---

# 29. Why Multiple API Containers?

Suppose one API instance can handle:

```text
100 requests/sec
```

and your traffic becomes:

```text
250 requests/sec
```

You could scale:

```text
1 API
```

to:

```text
3 API containers
```

Then:

```text
Nginx
  ↓
API-1
API-2
API-3
```

can distribute traffic.

This is one of the foundations of horizontal scaling.

---

# 30. Statelessness Becomes Important

Remember the architecture principle from the Docker lesson.

If you have:

```text
API-1
API-2
API-3
```

any request might go to any instance.

Therefore your API shouldn't depend on:

```text
local memory
local files
local process state
```

for important persistent information.

Instead use shared infrastructure:

```text
MongoDB
Redis
object storage
external queue
```

This is why stateless backend design matters.

---

# 31. Sticky Sessions

Some architectures use:

```text
sticky sessions
```

where the same client tends to go to the same backend instance.

But for a modern stateless API, you generally want to avoid needing this unless there is a specific reason.

A better architecture is often:

```text
Any request
   ↓
Any healthy API instance
```

This makes scaling and deployment easier.

---

# 32. Reverse Proxy Health Checks

Suppose:

```text
API-1 ❌
API-2 ✅
API-3 ✅
```

A load balancer/reverse proxy should avoid sending traffic to unhealthy instances.

This connects directly to:

```text
24.11 Health Checks
```

Your:

```text
/healthz
/readyz
```

endpoints become useful infrastructure signals.

---

# 33. Readiness Is Especially Important

Imagine:

```text
API-1
```

is starting.

The process exists:

```text
Node alive ✅
```

but MongoDB isn't ready:

```text
MongoDB ❌
```

Then:

```text
/healthz → 200
/readyz → 503
```

The reverse proxy/orchestrator should avoid sending normal traffic to it.

That's why:

> **Liveness and readiness are different concepts.**

---

# 34. Reverse Proxy + Graceful Shutdown

This is where Lesson 24.12 becomes extremely important.

Suppose:

```text
API-1
API-2
API-3
```

and API-1 needs to shut down.

The ideal flow is:

```text
API-1
  ↓
SIGTERM
  ↓
ready = false
  ↓
reverse proxy stops routing new traffic
  ↓
existing requests drain
  ↓
API-1 exits
```

Meanwhile:

```text
API-2 ✅
API-3 ✅
```

continue serving users.

This is the basis of zero/minimal-downtime deployments.

A clean architecture might expose:

```text

```

publicly.

```text

```

```text

   ↓
```

# 37. One of the Most Important Security Ideas

Ask:

> **Which services actually need to be internet-accessible?**

Usually:

```text
Nginx → YES
API → preferably internal
MongoDB → NO
Redis → NO
```

You don't want:

```text
Internet
   ↓
MongoDB:27017
```

That's a completely different security posture.

# 38. Reverse Proxy as a Security Boundary

The architecture becomes:

```text
                 INTERNET
                    │
                    ▼
             PUBLIC ENTRY
                    │
                    ▼
                 NGINX
                    │
             PRIVATE NETWORK
                    │
             ┌──────┴──────┐
             ▼             ▼
            API          other services
             │
             ▼
           MongoDB
```

The reverse proxy is therefore part of your **network boundary**.

But remember:

> It is a security layer, not your only security layer.

# 39. What Should Node Know About Nginx?

For example:

```text

 ↓
Nginx
 ↓
Express
```

Node may need:

```js
app.set("trust proxy", 1);
```

This becomes particularly important when using:

```text

```

# 40. HTTP → HTTPS Redirect

A common production pattern is:

```text
http://example.com
```

redirecting to:

```text
https://example.com
```

Conceptually:

```text
HTTP :80
   ↓
301/308
   ↓
HTTPS :443
```

Then:

```text
HTTPS :443
   ↓
Node
```

This ensures users use the encrypted connection.

---

# 41. Don't Create Redirect Loops

There is a subtle issue here.

Suppose:

```text
Browser
  ↓ HTTPS
Nginx
  ↓ HTTP
Node
```

If Node doesn't know the original request was HTTPS, it may think:

```text
request is HTTP
```

and try:

```text
redirect → HTTPS
```

again.

You can get:

```text
HTTPS
 ↓
Nginx
 ↓
HTTP
 ↓
Node
 ↓
redirect HTTPS
 ↓
Nginx
 ↓
...
```

Proper proxy headers and Express proxy configuration prevent this kind of mistake.

# 42. WebSockets

If your application eventually uses:

```text
Socket.IO
WebSockets
```

the reverse proxy must support forwarding those connections correctly.

Normal HTTP proxying:

```text

 ↓
response
```

WebSocket:

```text

```

So the proxy configuration needs to account for connection upgrades and timeouts.

# 43. Timeouts

A reverse proxy needs sensible timeouts.

Imagine:

```text
Client
 ↓
Nginx
 ↓
Node
 ↓
external service
```

If the external service takes too long, you don't want connections hanging forever.

You therefore need to think about:

```text
connect timeout
read timeout
send timeout
idle timeout
```

The correct values depend on your application.

# 48. What Nginx Should NOT Do

Don't move your business logic into Nginx.

Bad architecture:

```text
Nginx
 ↓
complicated business rules
 ↓
database logic
```

Your application logic belongs in:

```text

 ↓
Controller
 ↓
Service
 ↓
Repository
```

Nginx should primarily handle infrastructure-level concerns.

# 55. Common Mistakes

## Mistake 1 — Exposing everything

Bad:

```text
Internet
 ├── Nginx
 ├── Node:5000
 ├── MongoDB:27017
 └── Redis:6379
```

Better:

```text
Internet
    ↓
Nginx
    ↓
private network
 ├── Node
 ├── MongoDB
 └── Redis
```

---

## Mistake 2 — Trusting proxy headers blindly

Don't configure:

```js
app.set("trust proxy", true);
```

without understanding your infrastructure.

---

## Mistake 3 — Using `localhost` for another container

Wrong idea:

```text
Nginx → localhost:5000
```

when Node is another container.

Use the service/network name:

```text
Nginx → api:5000
```

---

## Mistake 4 — Forgetting readiness

A container can be:

```text
alive
```

but not:

```text
ready
```

Use:

```text
/healthz
/readyz
```

appropriately.

---

## Mistake 5 — Forgetting graceful shutdown

If a backend disappears immediately:

```text
Nginx
 ↓
dead API
```

requests can fail.

Graceful shutdown allows:

```text
not ready
 ↓
drain
 ↓
exit
```
