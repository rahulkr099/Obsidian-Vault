# Lesson 24.15 — Deployment Architecture

Your roadmap defines **24.15 as Deployment Architecture**, after Docker and Reverse Proxy and immediately before the final Production Checklist.

This lesson is where the previous production lessons finally become **one complete system**.

The goal is not to memorize a cloud provider's buttons. The goal is to understand:

> **What happens from `git push` until a real user reaches your Node.js API?**

---

# 1. What Is Deployment Architecture?

Deployment architecture describes **how your application is arranged in the real production environment**.

So far we've learned individual pieces:

```text
HTTPS
Secrets
Database security
Rate limiting
Logging
Health checks
Graceful shutdown
Docker
Reverse proxy
```

Now combine them:

```text
                    INTERNET
                       │
                       ▼
                 Reverse Proxy
                       │
                       ▼
                  API Container
                       │
              ┌────────┴────────┐
              ▼                 ▼
           MongoDB             Redis
```

But that's only the runtime architecture.

We also need to understand how code gets there:

```text
Developer
   ↓
Git
   ↓
CI/CD
   ↓
Docker Image
   ↓
Deployment
   ↓

```

# 4. Where Does Docker Fit?

Docker packages your application:

```text
Source Code
    ↓
Dockerfile
    ↓
Docker Image
```

Then production runs:

```text
Docker Image
    ↓
Container
```

So:

```text
Developer
    ↓
Build
    ↓
Image
    ↓
Registry
    ↓
Server
    ↓
Container
```

This is one of the biggest reasons Docker is useful in deployment.

---

# 5. Docker Registry

You don't normally build an image on your production server manually every time.

Instead:

```text
Developer
   ↓
CI
   ↓
Docker build
   ↓
Docker image
   ↓
Container Registry
```

The registry stores the image.

Conceptually:

```text
                 Docker Registry
                       │
              ┌────────┴────────┐
              ▼                 ▼
          backend:1.0       backend:1.1
```

Production can then pull the desired version.

---

# 6. Image Tags

You might have:

```text
backend:1.0.0
backend:1.1.0
backend:1.2.0
```

This is much better than thinking only in terms of:

```text
latest
```

Why?

Because you want to know exactly what version is running.

For example:

```text
Production
    ↓
backend:1.2.0
```

If something goes wrong:

```text
rollback
    ↓
backend:1.1.0
```

---

# 7. Avoid Depending on `latest`

You might see:

```text
backend:latest
```

It's convenient, but it can make deployments harder to reason about.

Imagine:

```text
Today:
latest → 1.2.0

Tomorrow:
latest → 1.3.0
```

What exactly is running?

A versioned image gives you:

```text
backend:1.2.0
```

which is explicit.

# 9. Why CI Before Deployment?

Imagine you changed:

```text
auth.service.js
```

and accidentally introduced:

```text
Syntax error
```

Without CI:

```text
Git push
   ↓
Production
   ↓
💥
```

With CI:

```text
Git push
   ↓
Tests
   ↓
❌ failed
   ↓
Deployment stops
```

That's a major safety improvement.


rather than:

```text

    ↓

    ↓

    ↓

```

Manual deployments can work for learning, but they don't scale well.

# 11. Production Server

At a simple level, production might be one Linux server:

```text
Linux Server
│
├── Nginx
├── API container
└── MongoDB / external DB
```

This is perfectly useful for learning deployment architecture.

But as your application grows, you may move toward:

```text
Load Balancer
     ↓
Server 1
Server 2
Server 3
```

# 12. Single Server Architecture

The simplest production architecture:

```text
                    INTERNET
                       │
                       ▼
                     Nginx
                       │
                       ▼
                 API Container
                       │
                       ▼
                Managed MongoDB
```

Advantages:

```text
simple
cheap
easy to understand
easy to deploy
```

Disadvantages:

```text
single server failure
limited scaling
manual infrastructure management
```

This is often a good starting point.

# 13. Multiple API Instances

When traffic increases:

```text
                     Nginx
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
           API-1     API-2     API-3
```

Now you can scale horizontally.

Instead of making one server increasingly powerful:

```text
2 CPU
 ↓
4 CPU
 ↓
8 CPU
```

you can add instances:

```text
1 instance
 ↓
2 instances
 ↓
3 instances
```

---

# 14. Horizontal vs Vertical Scaling

### Vertical scaling

Make one machine stronger:

```text
Server
2 CPU
 ↓
8 CPU
 ↓
16 CPU
```

### Horizontal scaling

Add more machines/containers:

```text
Server 1
Server 2
Server 3
```

For stateless APIs, horizontal scaling is often very useful.

---

# 15. Why Stateless APIs Matter

Suppose:

```text
API-1
API-2
API-3
```

A request can go anywhere:

```text
Request A → API-1
Request B → API-3
Request C → API-2
```

This works best when your API doesn't depend on local process memory for important state.

Instead:

```text
API instances
      │
      ├── MongoDB
      ├── Redis
      └── Object Storage
```

Shared external systems hold persistent state.

# 16. Database Architecture

Your API containers should not normally contain the production database itself.

Better:

```text
API Container
      │
      ▼
Managed MongoDB
```

Why?

Because the database has different requirements:

```text
persistent storage
backups
replication
recovery
monitoring
security
```

Your API container is disposable.

Your database data is not.

# 19. Firewall

Your server should have network-level restrictions.

Conceptually:

```text
Internet
   │
   ├── 80  → allowed
   ├── 443 → allowed
   ├── 22  → restricted
   └── 27017 → blocked
```

The exact rules depend on your infrastructure.

The principle is:

> **Expose the minimum necessary network surface.**

# 20. SSH

You may need SSH for server administration.

But don't think:

```text

```

is ideal.

A production server should use appropriate controls such as:

```text

firewall rules
least privilege
```

SSH is an administration channel, not an application endpoint.

# 25. Staging Environment

Staging sits between development and production.

```text
Developer
   ↓
Development
   ↓
Staging
   ↓

```

Staging should resemble production as much as practical.

Why?

Because you want to catch:

```text

```

before real users encounter them.

# 26. Health Checks in Deployment

Your API has:

```text
GET /healthz
GET /readyz
```

Now they become infrastructure tools.

Suppose:

```text
API-1 → healthy
API-2 → unhealthy
API-3 → healthy
```

The infrastructure should route traffic only to ready instances.

```text
                Load Balancer
                 /        \
                ▼          ▼
             API-1       API-3
              ✅           ✅

             API-2
               ❌
```

This connects 24.11 directly to deployment.

# 27. Graceful Shutdown During Deployment

Suppose you're deploying:

```text
API v2
```

and currently have:

```text
API v1
API v1
```

A safe deployment can introduce:

```text
API v2
```

Then:

```text
API v2
   ↓
/readyz = 200
```

Only after it's ready should traffic move toward it.

Old instance:

```text
API v1
   ↓
SIGTERM
   ↓
not ready
   ↓
finish existing requests
   ↓
exit
```

This is why **24.11 + 24.12 + 24.15** are closely connected.

# 28. Rolling Deployment

A simple rolling deployment:

```text
Before:

API-1 v1
API-2 v1
API-3 v1
```

Deploy:

```text
API-1 v2
API-2 v1
API-3 v1
```

Then:

```text
API-1 v2
API-2 v2
API-3 v1
```

Finally:

```text
API-1 v2
API-2 v2
API-3 v2
```

At no point do you necessarily have to shut everything down simultaneously.

---

# 29. Blue-Green Deployment

Another strategy is:

```text
BLUE
v1
```

and:

```text
GREEN
v2
```

Architecture:

```text
              Load Balancer
                 /       \
                ▼         ▼
             BLUE        GREEN
              v1           v2
```

Initially:

```text
100% traffic → BLUE
```

After validation:

```text
100% traffic → GREEN
```

If v2 fails:

```text
100% traffic → BLUE
```

Rollback can be very fast.

---

# 30. Canary Deployment

Another approach:

```text
v1 → 95% traffic
v2 → 5% traffic
```

If v2 looks healthy:

```text
v1 → 75%
v2 → 25%
```

Then:

```text
v1 → 0%
v2 → 100%
```

This reduces the blast radius of a bad release.

This is the deeper idea.

A deployment isn't simply:

```text
copy new code
```

It's:

```text
How can I release new code

```

That's why we have:

```text
tests
health checks
readiness
graceful shutdown
rolling deployment

```

# 32. Database Migrations

Here's a tricky production problem.

Suppose version 1 has:

```text
name
```

and version 2 expects:

```text
firstName
lastName
```

If you deploy v2 immediately, old API instances might still expect:

```text
name
```

while new instances expect:

```text
firstName
lastName
```

Now you have compatibility problems.

So production deployments must consider:

> **Application version compatibility with database schema.**

---

# 33. Expand and Contract

A safer migration strategy is:

### Step 1 — Expand

Add the new field:

```text
name
firstName
lastName
```

### Step 2 — Deploy code

New code can understand both formats.

### Step 3 — Migrate data

Move existing values.

### Step 4 — Contract

Eventually remove the old field.

Conceptually:

```text
Old
 ↓
Expand
 ↓
Compatible code
 ↓
Migrate
 ↓
Remove old
```

This becomes extremely important in zero/minimal-downtime deployments.

---

# 34. Docker Image + Database Migration

# 36. Metrics

Logs tell you:

> **What happened?**

Metrics tell you:

> **How much / how often?**

Examples:

```text

error rate
latency
CPU
memory
database connections
```

For example:

```text
HTTP 5xx rate
     ↑
  suddenly
     │
     └── deployment may be broken
```

# 37. Monitoring

A production system needs visibility.

Conceptually:

```text
Application
    │
    ├── Logs
    ├── Metrics
    └── Health
          │
          ▼
      Monitoring
          │
          ▼
        Alerts
```

You don't want to discover a production outage because a user messages you.

---

# 38. Alerts

Useful alerts might include:

```text
High 5xx rate
High latency
Container unhealthy
Database unavailable
Disk nearly full
Memory exhaustion
Certificate expiration
```

The important principle:

> Alert on conditions that require action.

Don't create hundreds of noisy alerts.

# 39. Backups

Your production database needs backups.

Think:

```text
MongoDB
   │
   ├── Backup
   ├── Backup
   └── Backup
```

But backups aren't enough.

You also need to know:

> **Can I restore one?**

A backup you've never tested is not a complete recovery strategy.

---

# 40. Disaster Recovery

Suppose your server disappears.

Can you rebuild?

Ideally:

```text
Git
 ↓
Dockerfile
 ↓
Docker image
 ↓
Infrastructure
 ↓
Database restore
 ↓
Application
```

This is why infrastructure should be reproducible.

Your application shouldn't depend on one manually configured server that nobody understands.

# 44. Production Failure Scenario

Let's say:

```text
API-2
```

crashes.

What should happen?

Ideally:

```text
API-2 ❌
```

Health/readiness detects the problem.

Then:

```text
Load Balancer
   ↓
stops routing to API-2
```

Meanwhile:

```text
API-1 ✅
API-3 ✅
```

continue serving requests.

Then infrastructure can replace API-2:

```text
New API-2
   ↓
start
   ↓
health check
   ↓
readiness
   ↓
traffic
```

That's resilient deployment architecture.

# 48. Common Beginner Mistakes

### ❌ Deploy directly from your laptop

Better:

```text
Git
 ↓
CI/CD
 ↓
Production
```

### ❌ Put secrets in Git

Use external secret configuration.

### ❌ Expose MongoDB publicly

Keep databases private.

### ❌ Deploy without health checks

You need to know whether the application is actually ready.

### ❌ Kill containers immediately

Use graceful shutdown.

### ❌ Use only `latest`

Prefer identifiable versions.

### ❌ Forget database compatibility

Application deployment and database schema changes must work together.

### ❌ No rollback plan

Every production deployment should have a recovery strategy.
