# 1. What Is a Production Checklist?

A production checklist is a final verification list.

Before deploying:

```text
Code
 ↓
Checklist
 ↓
Production
```

Instead of:

```text
Code
 ↓
"Looks good"
 ↓
Production 💥
```

The checklist forces you to verify the important areas systematically.

# 3. Environment Checklist

First:

```text
NODE_ENV
PORT
DATABASE URL
FRONTEND URL
```

Check:

```text
[ ] Production environment is explicitly configured
[ ] Development settings aren't being used accidentally
[ ] Production database is different from development
[ ] Production frontend URL is correct
[ ] Debug settings are disabled
```

You don't want:

```text
NODE_ENV=development
```

on a production deployment accidentally.

---

# 4. Secrets Checklist

Never commit secrets.

Check:

```text
[ ] JWT secrets are outside Git
[ ] Database credentials are outside Git
[ ] SMTP credentials are outside Git
[ ] API keys are outside Git
[ ] .env is ignored
[ ] .env.example contains placeholders only
```

Good:

```text
.env
.env.example
.gitignore
```

For example:

```env
JWT_SECRET=<production-secret>
```

should **not** appear in your repository.

---

# 5. Check Git History Too

There's an important trap.

You might delete:

```text
.env
```

from the current project.

But if you previously committed it:

```text
commit 1 → .env ❌
commit 2 → .env deleted
```

the secret may still exist in Git history.

So:

> **Deleting a secret from the current filesystem doesn't necessarily mean the secret is safe.**

If a real secret was exposed, rotate it.

For example:

```text
Old JWT secret
     ↓
REVOKE / ROTATE
     ↓
New JWT secret
```

---

# 6. HTTPS Checklist

Production should use HTTPS.

Check:

```text
[ ] Domain configured
[ ] TLS certificate configured
[ ] HTTP redirects to HTTPS
[ ] Secure cookies enabled where appropriate
[ ] No sensitive data sent over plain HTTP
```

The architecture should look like:

```text
Browser
   │
   │ HTTPS
   ▼
Reverse Proxy
   │
   ▼
Node
```

---

# 7. HTTP → HTTPS

You generally want:

```text
http://example.com
       ↓
redirect
       ↓
https://example.com
```

Then:

```text
HTTPS
 ↓
Nginx
 ↓
Node
```

Remember the proxy configuration from 24.14 so your application correctly understands the original protocol.

---

# 8. CORS Checklist

Don't leave production CORS as:

```js
cors({
    origin: "*"
})
```

especially when your application uses credentials/cookies.

Instead think:

```text
Frontend
    ↓
https://example.com
```

and explicitly allow the required origins.

Checklist:

```text
[ ] Production origins explicitly configured
[ ] Development origins aren't accidentally allowed
[ ] Credentials configuration is intentional
[ ] Methods are appropriate
[ ] Headers are appropriate
```

The principle is:

> **Allow what you need, not everything.**

---

# 9. Cookies Checklist

If you're using authentication cookies:

```text
[ ] HttpOnly
[ ] Secure in production
[ ] SameSite intentionally configured
[ ] Appropriate domain/path
[ ] Appropriate expiration
```

For example:

```text
HttpOnly
Secure
SameSite
```

should be chosen based on your actual authentication architecture.

Don't blindly copy cookie settings from a tutorial.

---

# 10. Authentication Checklist

Before production, ask:

```text
[ ] Passwords are hashed
[ ] Passwords are never logged
[ ] JWT secrets are strong
[ ] Access tokens expire
[ ] Refresh tokens are protected
[ ] Logout invalidates appropriate credentials
[ ] Password reset tokens expire
[ ] Email verification tokens expire
```

You already studied these concepts earlier in your roadmap.

The checklist simply asks:

> **Did I actually implement them safely?**

---

# 11. Authorization Checklist

Authentication asks:

> Who are you?

Authorization asks:

> What are you allowed to do?

Check:

```text
[ ] Protected routes require authentication
[ ] Admin routes require appropriate roles
[ ] Users cannot access other users' resources
[ ] Ownership checks exist
[ ] Sensitive operations have authorization checks
```

Remember this pattern:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

rather than blindly:

```js
Todo.findById(todoId);
```

The first includes ownership.

# 12. Database Security Checklist

Your production MongoDB should not simply be:

```text
Internet
   ↓
MongoDB
```

Instead:

```text
Internet
   ↓
Reverse Proxy
   ↓
API
   ↓
Private database connection
   ↓
MongoDB
```

Check:

```text
[ ] Database isn't publicly exposed unnecessarily
[ ] Authentication is enabled
[ ] Strong database credentials
[ ] Least-privilege database user
[ ] TLS where appropriate
[ ] Backups configured
```

---

# 13. MongoDB Index Checklist

Indexes are not only performance features.

They also affect whether your application can handle production traffic efficiently.

Check important query patterns.

For example:

```text
User lookup by email
Todo lookup by userId
CreatedAt sorting
Unique fields
```

You might need indexes such as:

```js
email: 1
```

or:

```js
userId: 1,
createdAt: -1
```

But don't create indexes randomly.

Ask:

> **Which queries does my application actually perform?**

---

# 14. Rate Limiting Checklist

Production endpoints should have appropriate protection.

Especially:

```text
/login
/signup
/password-reset
/refresh-token
```

Check:

```text
[ ] Authentication endpoints are rate limited
[ ] Expensive endpoints are protected
[ ] Rate limit is appropriate for real traffic
[ ] Proxy configuration doesn't break IP detection
[ ] Legitimate users aren't unnecessarily blocked
```

Remember:

```text
Too little
    ↓
abuse

Too much
    ↓
bad user experience
```

Rate limiting is a balancing problem.

---

# 15. Logging Checklist

You need enough logging to answer:

> **What happened?**

Check:

```text
[ ] Requests are logged
[ ] Errors are logged
[ ] Request IDs exist
[ ] Important business events are logged
[ ] Logs have appropriate levels
[ ] Logs don't contain secrets
[ ] Passwords aren't logged
[ ] Tokens aren't logged
```

A useful request log might contain:

```text
requestId
method
path
status
duration
userId
```

---

# 16. Never Log Secrets

Bad:

```js
console.log(req.headers.authorization);
```

Bad:

```js
console.log(password);
```

Bad:

```js
console.log(refreshToken);
```

Even debugging logs can become a security problem in production.

Think:

```text
Logs
 ↓
Central storage
 ↓
Many people/services may access them
```

Therefore logs should be treated as sensitive infrastructure.

---

# 17. Error Handling Checklist

Production errors should be controlled.

Check:

```text
[ ] Global error middleware exists
[ ] Async errors are handled
[ ] Unknown errors don't crash the response format
[ ] Internal stack traces aren't exposed to users
[ ] Appropriate HTTP status codes are returned
[ ] Errors have useful logs
[ ] Request IDs are included where useful
```

User should receive something like:

```json
{
  "success": false,
  "message": "Something went wrong",
  "requestId": "abc123"
}
```

rather than:

```text
MongoServerError: E11000 duplicate key error...
/home/user/project/node_modules/...
```

---

# 18. Error Disclosure

Development might show:

```text
Error
Stack trace
File path
Database details
```

Production should generally avoid exposing internal implementation details.

Think:

```text
Developer
   ↓
Detailed logs

User
   ↓
Safe error response
```

Two different audiences.

# 20. Graceful Shutdown Checklist

When the process receives:

```text
SIGTERM
```

you don't want:

```text
SIGTERM
   ↓
💥 immediate exit
```

Instead:

```text
SIGTERM
   ↓
Stop accepting new work
   ↓
Mark instance not ready
   ↓
Finish existing requests
   ↓
Close server
   ↓
Close database connections
   ↓
Exit
```

Check:

```text
[ ] SIGTERM handled
[ ] New traffic stops
[ ] Existing requests can finish
[ ] Database connection closes
[ ] Other resources are cleaned up
```

---

# 21. Docker Checklist

Your production Docker image should be deliberate.

Check:

```text
[ ] Production Dockerfile exists
[ ] Image is reasonably small
[ ] .dockerignore exists
[ ] Dependencies are installed correctly
[ ] Application runs as non-root where appropriate
[ ] Environment secrets aren't baked into image
[ ] Health checks are considered
[ ] Correct port is exposed/listened on
```

Remember:

> **Docker image ≠ secret storage.**

Never bake:

```text
JWT_SECRET
MONGO_PASSWORD
SMTP_PASSWORD
```

into the image.

# 22. Container Lifecycle

Your container should behave predictably:

```text
start
 ↓
application starts
 ↓
database connection
 ↓
ready
 ↓
receive traffic
```

And:

```text
SIGTERM
 ↓
drain
 ↓
shutdown
```

You don't want containers that only work when manually started in a particular order.

# 25. Rollback Checklist

This is one of the most forgotten items.

Ask:

> **What happens if the new deployment is broken?**

Suppose:

```text
v1.4.0 ✅
```

and you deploy:

```text
v1.5.0 ❌
```

Can you return to:

```text
v1.4.0
```

quickly?

That's why versioned images are useful:

```text
backend:1.4.0
backend:1.5.0
```

A rollback becomes conceptually:

```text
1.5.0
  ↓
❌
  ↓
1.4.0
  ↓
✅
```

---

# 26. Database Migration Checklist

Before deploying code that changes the database schema:

```text
[ ] Migration is backward compatible where necessary
[ ] Existing data is considered
[ ] Old application version won't immediately break
[ ] Migration can be tested
[ ] Backup exists
[ ] Rollback/recovery strategy exists
```

This is especially important when using:

```text
rolling deployments
```

because old and new application versions may temporarily run together.

# 28. Security Testing Checklist

Ask:

```text
Can an unauthenticated user access protected routes?

Can User A access User B's resource?

Can a normal user perform admin operations?

Can invalid JWTs pass?

Can expired tokens pass?

Can refresh tokens be reused incorrectly?

Can rate limits be bypassed?

Can malicious input reach database queries?

Can sensitive information leak through errors?
```

This is where Phase 22 becomes useful.

Production hardening shouldn't be treated as a completely separate subject from security testing.

# 29. Backup Checklist

Your database contains the actual business data.

Check:

```text
[ ] Automated backups
[ ] Backup retention policy
[ ] Restore procedure documented
[ ] Restore has been tested
[ ] Backup access is secured
```

Most importantly:

> **Test restoration.**

A backup that exists but cannot be restored is a dangerous assumption.

# 30. Monitoring Checklist

Logs answer:

> What happened?

Metrics answer:

> How much/how often?

Health checks answer:

> Is it alive/ready?

Together:

```text
Application
 ├── Logs
 ├── Metrics
 └── Health
```

Check important signals such as:

```text
[ ] Error rate
[ ] Response latency
[ ] CPU
[ ] Memory
[ ] Database health
[ ] Container health
```

---

# 31. Alerting Checklist

Don't alert on everything.

Alert when something needs attention.

For example:

```text
5xx rate ↑↑
Latency ↑↑
Database unavailable
Container unhealthy
Disk almost full
Certificate nearing expiration
```

The goal is:

```text
Problem
  ↓
Alert
  ↓
Human action
```

not:

```text
Every tiny event
  ↓
ALERT!
  ↓
ALERT!
  ↓
ALERT!
```

# 37. The Most Important Mental Model

When you're about to deploy a backend, ask five questions:

### 1. Can users reach it safely?

```text
HTTPS
Reverse proxy
CORS
Cookies
```

### 2. Can attackers abuse it?

```text
Authentication
Authorization
Rate limiting
Validation
Database security
```

### 3. Can I understand what is happening?

```text
Logs
Request IDs
Metrics
Monitoring
```

### 4. Can it survive failure?

```text
Health checks
Readiness
Graceful shutdown
Backups
Multiple instances
```

### 5. Can I safely release and recover?

```text
Tests
Docker
CI/CD
Versioned images
Rollback
Database migration strategy
```

If you can confidently answer those five questions, you're thinking like a production backend engineer.
