---

## Scenario 1 — Secret Leakage

You discover this in Git:

```env
JWT_SECRET=my-secret
MONGO_URI=mongodb://admin:password@...
```

### What should you do?

Not just:

```text
delete .env
```

You should think:

```text
Secret exposed
      ↓
Rotate/revoke secret
      ↓
Remove from repository/history
      ↓
Store new secret securely
      ↓
Deploy with new secret
```

The key lesson:

> **Once a secret is exposed, assume it is compromised.**

http://api.example.com

# 4. Scenario 3 — CORS Is `*`

You find:

```js
cors({
    origin: "*"
});
```

Ask:

> Does this match my production authentication architecture?

If your application uses credentialed cookies, a wildcard origin is not the appropriate configuration.

Instead:

```text
Frontend origin
       ↓
Explicitly allowed
       ↓
API
```

The important lesson isn't:

> "Always use this exact CORS setting."

It's:

> **CORS should reflect your actual frontend/API architecture.**

---

# 5. Scenario 4 — User A Reads User B's Todo

Request:

```text
GET /api/v1/todos/123
```

Code:

```js
Todo.findById(todoId);
```

Potential problem.

Instead, ownership should be part of the authorization/data-access logic:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Mental model:

```text
Resource ID
     +
Authenticated identity
     ↓
Authorized resource
```

---

# 6. Scenario 5 — Login Abuse

Someone sends:

```text
POST /login
```

10,000 times.

You need:

```text
Rate limiting
```

But also consider:

```text
logging
monitoring
account protection
IP/proxy handling
```

Production security is usually layered.

# 7. Scenario 6 — API Crashes

Your API throws an unexpected error.

Without proper handling:

```text
User
 ↓
500
 ↓
stack trace
```

Better:

```text
User
 ↓
safe error response

Server
 ↓
detailed structured log
```

For example:

```json
{
  "success": false,
  "message": "Something went wrong",
  "requestId": "req_123"
}
```

And the server logs the details associated with:

```text
req_123
```

---

# 8. Scenario 7 — Deployment Kills Requests

You deploy:

```text
API v2
```

and immediately terminate:

```text
API v1
```

Existing requests may fail.

Better:

```text
API v1
 ↓
SIGTERM
 ↓
not ready
 ↓
stop receiving new requests
 ↓
finish existing requests
 ↓
close resources
 ↓
exit
```

That's:

> **Graceful shutdown.**

---

# 9. Scenario 8 — Container Is Running but Database Isn't Ready

Docker says:

```text
container: running
```

But:

```text
MongoDB: unavailable
```

A simple process check isn't enough.

You need the distinction:

```text
/healthz
    ↓
Is the process alive?

/readyz
    ↓
Can this instance serve traffic?
```

This is why health and readiness shouldn't be treated as identical.

---

# 10. Scenario 9 — New Container Shouldn't Receive Traffic Yet

Suppose:

```text
API v2
```

has started but is still initializing.

Don't immediately send production traffic.

Instead:

```text
Container starts
      ↓
Health check
      ↓
Dependencies ready
      ↓
/readyz → 200
      ↓
Traffic allowed
```

This gives deployment infrastructure a reliable signal.

---

# 11. Scenario 10 — Production Server Gets Destroyed

Imagine:

```text
💥 Production server gone
```

Can you rebuild?

A good architecture should allow:

```text
Git
 ↓
Dockerfile
 ↓
Docker image
 ↓
Infrastructure
 ↓
Secrets
 ↓
Database restore
 ↓
Application
```

This is why reproducible deployments matter.

---

# 12. Scenario 11 — Database Is Deleted

Now imagine:

```text
MongoDB
   ↓
💥 data lost
```

Your answer shouldn't be:

> "We'll recreate the database."

You need:

```text
Backup
 ↓
Restore
 ↓
Verify
```

And ideally you've tested restoration **before** disaster happens.

---

# 13. Scenario 12 — New Deployment Is Broken

Current:

```text
backend:1.5.0 ✅
```

You deploy:

```text
backend:1.6.0 ❌
```

What should happen?

```text
1.6.0
 ↓
health/monitoring detects problem
 ↓
rollback
 ↓
1.5.0
```

This is why versioned images are useful.

---

# 14. Scenario 13 — Database Schema Changes

Version 1:

```text
name
```

Version 2:

```text
firstName
lastName
```

But during rolling deployment:

```text
API v1
API v1
API v2
```

are running together.

If v2 immediately removes `name`, v1 can break.

Think:

```text
Expand
 ↓
Deploy compatible code
 ↓
Migrate
 ↓
Contract
```

This is an important production deployment principle.

---

# 15. Scenario 14 — Nginx Cannot Reach Node

You have:

```text
Nginx container
API container
```

Nginx contains:

```nginx
proxy_pass http://localhost:5000;
```

Potential problem:

```text
localhost
   ↓
Nginx container
```

not:

```text
API container
```

If Docker networking is configured correctly, you might instead use:

```nginx
proxy_pass http://api:5000;
```

where `api` is the Docker service name.

---

# 16. Scenario 15 — Client IP Is Wrong

Your Node application sees:

```text
172.x.x.x
```

instead of the real client IP.

Why?

```text
Client
 ↓
Nginx
 ↓
Node
```

The application is behind a proxy.

You need to correctly configure:

```text
X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host
```

and Express's trusted-proxy behavior.

Don't blindly trust arbitrary forwarded headers.

---

# 17. Scenario 16 — Logs Contain Passwords

You find:

```text
password=Rahul123
```

in your logs.

That's a serious problem.

Logs can be:

```text
stored
backed up
searched
shared
accessed by operators
```

Therefore:

```text
❌ passwords
❌ access tokens
❌ refresh tokens
❌ API keys
❌ database credentials
```

shouldn't be casually logged.

---

# 18. Scenario 17 — You Can't Debug Production

Users report:

> "The request failed."

You have no request ID.

Bad:

```text
Error happened somewhere.
```

Better:

```text
Request
 ↓
requestId = abc123
 ↓
Nginx
 ↓
Node
 ↓
Service
 ↓
Database
```

Now you can search logs for:

```text
abc123
```

and reconstruct what happened.

---

# 19. Scenario 18 — One API Container Dies

Architecture:

```text
Nginx
 ├── API-1
 ├── API-2
 └── API-3
```

API-2 dies:

```text
API-1 ✅
API-2 ❌
API-3 ✅
```

Health/readiness should cause traffic to avoid API-2.

Then:

```text
new API-2
 ↓
health check
 ↓
ready
 ↓
traffic
```

This is where:

```text
Docker
Health checks
Reverse proxy
Graceful shutdown
```

all work together.
