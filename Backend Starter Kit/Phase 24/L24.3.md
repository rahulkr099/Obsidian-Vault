# Lesson 24.3 — Production Environment Variables

In **24.2**, we learned that the same backend code can run in development, staging, and production while using different configuration.

Now we'll focus on one of the most important pieces of that architecture:

> **Environment variables are how we provide environment-specific configuration to our application without hard-coding it into the source code.**

Your Phase 24 roadmap specifically places **Production Environment Variables** here, before secrets management, HTTPS, CORS, cookies, and the other production-hardening topics.

---

# 1. The Problem We're Solving

Imagine you write:

```js
const port = 5000;
```

That's not a big problem.

But now imagine:

```js
const mongoUri = "mongodb://...";
const jwtSecret = "...";
const frontendUrl = "https://...";
const emailPassword = "...";
```

Now we have problems.

### Problem 1 — Configuration is mixed with code

Your application logic now contains deployment information.

### Problem 2 — Secrets can leak

If you commit your code:

```bash
git add .
git commit
git push
```

you could accidentally push credentials.

### Problem 3 — Different environments need different values

Development:

```text
localhost
```

Production:

```text
real domain
```

Therefore:

```text
❌ Hard-code configuration

✅ Externalize configuration
```

---

# 2. What Is an Environment Variable?

An environment variable is a value provided to your application **from outside the application code**.

For example:

```env
PORT=5000
```

Your Node.js process can access it through:

```js
process.env.PORT
```

So the flow is:

```text
Environment
     │
     ▼
process.env
     │
     ▼
Node.js application
```

---

# 3. Simple Example

Suppose you have:

```env
PORT=5000
```

Then:

```js
console.log(process.env.PORT);
```

will give you:

```text
5000
```

But remember:

> Values from `process.env` are strings.

So:

```js
process.env.PORT
```

is:

```text
"5000"
```

not:

```text
5000
```

This matters when configuration values are numbers or booleans.

---

# 4. Why Environment Variables Matter in Production

Imagine three environments.

### Development

```env
NODE_ENV=development
PORT=5000
```

### Staging

```env
NODE_ENV=staging
PORT=5000
```

### Production

```env
NODE_ENV=production
PORT=5000
```

The application code can remain:

```js
app.listen(env.port);
```

Only the configuration changes.

So:

```text
                 SAME CODE
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
      DEV         STAGING       PROD
       │            │             │
       ▼            ▼             ▼
   Dev config   Stage config   Prod config
```

That's one of the most powerful ideas behind environment configuration.

---

# 5. Typical Backend Environment Variables

A MERN backend might eventually have variables such as:

```env
NODE_ENV=production

PORT=5000

MONGO_URI=...

ACCESS_TOKEN_SECRET=...
REFRESH_TOKEN_SECRET=...

ACCESS_TOKEN_EXPIRES_IN=15m
REFRESH_TOKEN_EXPIRES_IN=7d

FRONTEND_URL=https://app.example.com

LOG_LEVEL=info
```

And possibly:

```env
SMTP_HOST=...
SMTP_PORT=...
SMTP_USER=...
SMTP_PASSWORD=...
```

or:

```env
REDIS_URL=...
```

or:

```env
S3_BUCKET=...
AWS_REGION=...
```

depending on the application.

---

# 6. Don't Put Everything in `.env`

There's an important distinction.

Not every configuration value is equally sensitive.

For example:

```env
PORT=5000
```

is configuration.

But:

```env
JWT_SECRET=...
```

is a secret.

So think:

```text
Environment variables
        │
        ├── Configuration
        │
        └── Secrets
```

We'll study secrets more deeply in **24.4**.

---

# 7. `.env` in Development

For local development, you might have:

```text
backend/
├── src/
├── config/
├── .env
├── .env.example
├── package.json
└── ...
```

Your `.env` could contain:

```env
NODE_ENV=development
PORT=5000
MONGO_URI=mongodb://localhost:27017/myapp
FRONTEND_URL=http://localhost:5173
```

Then your application loads those values.

---

# 8. Why `.env.example` Exists

You should usually have:

```text
.env
.env.example
```

The difference is important.

### `.env`

Contains your actual local values:

```env
MONGO_URI=mongodb://localhost:27017/myapp
JWT_SECRET=actual-local-secret
```

### `.env.example`

Shows the required structure without exposing real values:

```env
NODE_ENV=
PORT=
MONGO_URI=
JWT_SECRET=
FRONTEND_URL=
```

This tells another developer:

> "These are the configuration values this application expects."

---

# 9. `.env` Should Usually Not Go Into Git

You might have:

```text
.env
```

in your project.

But you generally don't want:

```bash
git add .env
```

Instead, put it in:

```text
.gitignore
```

For example:

```gitignore
.env
```

Then:

```text
Developer machine
      │
      ├── .env
      │
      └── source code → Git
```

The actual `.env` stays outside the repository.

---

# 10. What Goes Into Git?

A good pattern is:

```text
.gitignore
.env.example
source code
```

but not:

```text
.env
```

So someone cloning the project gets:

```text
.env.example
```

and knows what they need to configure.

---

# 11. Loading Environment Variables

Node.js applications need to get environment variables from the environment.

In your architecture, you've already seen the idea of:

```text
.env
 ↓
dotenv
 ↓
process.env
```

Conceptually:

```js
import "dotenv/config";
```

or using the package explicitly:

```js
import dotenv from "dotenv";

dotenv.config();
```

After loading:

```js
process.env.PORT
```

becomes available.

---

# 12. But Don't Use `process.env` Everywhere

This is where your `config/env.js` becomes useful.

A beginner might write:

```js
const port = process.env.PORT;

const mongoUri = process.env.MONGO_URI;

const jwtSecret = process.env.JWT_SECRET;

const frontendUrl = process.env.FRONTEND_URL;
```

inside different files throughout the application.

That creates configuration scattered everywhere.

Instead:

```text
.env
 ↓
config/env.js
 ↓
application
```

---

# 13. Your Configuration Layer

Create:

```text
config/
└── env.js
```

Conceptually:

```js
export const env = {
    nodeEnv: process.env.NODE_ENV,
    port: Number(process.env.PORT),
    mongoUri: process.env.MONGO_URI,
    frontendUrl: process.env.FRONTEND_URL,
    jwtSecret: process.env.JWT_SECRET
};
```

Now your application uses:

```js
env.port
```

instead of:

```js
process.env.PORT
```

everywhere.

---

# 14. Why This Is Better

Imagine your project has:

```text
server.js
db.js
cors.js
auth.js
mailer.js
logger.js
```

Without centralized configuration:

```text
server.js → process.env.PORT
db.js     → process.env.MONGO_URI
auth.js   → process.env.JWT_SECRET
cors.js   → process.env.FRONTEND_URL
mailer.js → process.env.SMTP_HOST
logger.js → process.env.LOG_LEVEL
```

Configuration is scattered.

With a configuration layer:

```text
              .env
                │
                ▼
           config/env.js
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
    server     db       auth
       │        │        │
       └────────┼────────┘
                ▼
           application
```

Now there's one place where configuration is defined.

---

# 15. Type Conversion

Remember:

```js
process.env.PORT
```

returns:

```text
"5000"
```

So you may want:

```js
port: Number(process.env.PORT)
```

Similarly, boolean configuration needs care.

For example:

```env
COOKIE_SECURE=true
```

does **not** automatically mean:

```js
true
```

It is the string:

```text
"true"
```

So you need to parse it.

Conceptually:

```js
const cookieSecure = process.env.COOKIE_SECURE === "true";
```

This becomes important later when configuring production cookies.

---

# 16. Required Variables

One major improvement is to **fail early** when required configuration is missing.

Suppose production starts with:

```text
MONGO_URI missing
```

You don't want the server to start successfully and fail later when the first request arrives.

Instead:

```text
Application starts
       ↓
Load configuration
       ↓
Validate required variables
       ↓
Missing?
   │
   ├── YES → log error + exit
   │
   └── NO → continue
```

This is called **fail-fast configuration validation**.

---

# 17. Example

Suppose:

```env
MONGO_URI=
```

Your application should ideally detect:

```text
MONGO_URI is required
```

during startup.

Rather than:

```text
Server started
...
30 minutes later
...
Database operation fails
```

This makes deployment problems much easier to diagnose.

---

# 18. Configuration Validation

You can conceptually think of your configuration as having a schema:

```text
NODE_ENV
    required
    allowed values:
      development
      staging
      production

PORT
    required
    number

MONGO_URI
    required
    string

JWT_SECRET
    required
    string

FRONTEND_URL
    required
    URL
```

This is similar to request validation.

Earlier:

```text
HTTP request
   ↓
Validation
```

Now:

```text
Environment
   ↓
Configuration validation
```

Both protect your application from invalid input.

---

# 19. Environment Variables Are Still Input

This is a subtle but important idea.

You might think:

> "Environment variables are trusted because I control them."

Usually they're more trusted than HTTP input, but they can still be:

```text
missing
incorrect
malformed
mistyped
misconfigured
```

For example:

```env
PORT=hello
```

Your application shouldn't blindly assume that's valid.

So configuration should also be validated.

---

# 20. Production Configuration Should Be Explicit

Avoid relying on mysterious defaults.

For example, instead of:

```js
const port = Number(process.env.PORT) || 5000;
```

always silently falling back can hide configuration mistakes.

Sometimes a default is perfectly reasonable.

But for critical production settings:

```text
MONGO_URI
JWT secrets
production frontend origin
```

you often want the application to complain loudly if they're missing.

---

# 21. A Good Configuration Flow

For your starter architecture, think:

```text
                 Environment
                     │
                     ▼
                  .env
                     │
                     ▼
                  dotenv
                     │
                     ▼
               process.env
                     │
                     ▼
              config/env.js
                     │
                     ▼
          Validate + normalize
                     │
                     ▼
                Application
```

This is the architecture I want you to remember.

---

# 22. Configuration vs Business Logic

Suppose your Todo service contains:

```js
async createTodo(data) {
    ...
}
```

It shouldn't care about:

```text
where MongoDB lives
what port Express uses
which frontend domain is allowed
what the JWT secret is
```

Those belong to configuration.

So:

```text
Business Logic
      ≠
Environment Configuration
```

This separation makes your application easier to test and deploy.

# 23. Production Deployment

Here's where environment variables become especially useful.

Your Git repository might contain:

```text
Application code
Dockerfile
package.json
.env.example
```

But your deployment platform provides:

```text
MONGO_URI
JWT_SECRET
FRONTEND_URL
NODE_ENV
```

Then:

```text
Deployment platform
        │
        ▼
Environment variables
        │
        ▼
Docker container
        │
        ▼
Node.js
```

You don't need to modify the source code for every deployment.

# 24. Docker and Environment Variables

Since you just completed Phase 23, connect this with Docker.

You might build one image:

```text
backend:1.0.0
```

Then run it in different environments.

Development:

```text
backend image
+
development configuration
```

Staging:

```text
backend image
+
staging configuration
```

Production:

```text
backend image
+
production configuration
```

This is powerful.

```text
              ONE IMAGE
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
      DEV       STAGING     PROD
       │          │          │
     config     config     config
```

The application artifact can remain the same.

# 25. Why This Helps CI/CD

Imagine your pipeline:

```text
Git push
   ↓
Tests
   ↓
Build Docker image
   ↓
Deploy
```

The deployment system can provide production configuration.

Therefore:

```text
Code
 ↓
Build once
 ↓
Deploy with environment-specific configuration
```

This is much cleaner than rebuilding the application with different source code for every environment.

# 26. What About `.env` in Production?

For local development:

```text
.env
```

is convenient.

In production, depending on your hosting platform, you may use:

```text
Cloud secret manager
Environment configuration
Container secrets
Deployment platform secrets
Kubernetes secrets
Vault
```

We'll discuss this more in **24.4 — Secrets Management**.

The important distinction is:

> `.env` is a convenient configuration mechanism; it is not automatically a complete production secrets-management strategy.

# 27. A Practical `env.js`

A simple architecture might look like:

```js
const nodeEnv = process.env.NODE_ENV || "development";

const port = Number(process.env.PORT || 5000);

export const env = {
    nodeEnv,
    port,
    mongoUri: process.env.MONGO_URI,
    frontendUrl: process.env.FRONTEND_URL,
    accessTokenSecret: process.env.ACCESS_TOKEN_SECRET,
    refreshTokenSecret: process.env.REFRESH_TOKEN_SECRET,
};
```

But there's an important improvement still missing:

```text
What happens if MONGO_URI doesn't exist?
```

That's where configuration validation comes in.

---

# 28. Better Architecture

Eventually, your configuration should conceptually do:

```text
Read
 ↓
Validate
 ↓
Normalize
 ↓
Export
```

For example:

```text
process.env
    ↓
required?
    ↓
correct type?
    ↓
allowed value?
    ↓
normalized
    ↓
env object
```

So your application can safely assume:

```js
env.mongoUri
```

is actually valid.

---

# 29. Don't Put Configuration Logic Everywhere

Avoid:

```js
if (process.env.NODE_ENV === "production") {
    ...
}
```

in:

```text
controller
service
repository
model
```

unless there's a genuine reason.

Prefer:

```text
config/
    ↓
determines configuration
    ↓
application components consume it
```

For example:

```js
cors({
    origin: env.frontendUrl
});
```

rather than having the CORS middleware understand every environment itself.

---

# 30. The Complete Picture

Your production configuration architecture should eventually look like:

```text
                         ┌───────────────┐
                         │ Environment   │
                         │ Variables     │
                         └───────┬───────┘
                                 │
                                 ▼
                         ┌───────────────┐
                         │ Configuration │
                         │    Layer      │
                         └───────┬───────┘
                                 │
                       ┌─────────┼─────────┐
                       ▼         ▼         ▼
                    Database   Security   Server
                       │         │         │
                       └─────────┼─────────┘
                                 ▼
                            Application
```

This is much cleaner than:

```text
Every file
   ↓
process.env
   ↓
random configuration
```

# 🧠 The 6 Rules to Remember

### Rule 1

**Don't hard-code environment-specific configuration.**

```text
❌ const mongoUri = "..."
✅ env.mongoUri
```

### Rule 2

**Keep `.env` out of Git.**

```text
.env          → private
.env.example  → commit
```

### Rule 3

**Centralize configuration.**

```text
process.env
     ↓
config/env.js
```

### Rule 4

**Validate important configuration at startup.**

```text
Missing MONGO_URI
      ↓
Fail immediately
```

### Rule 5

**Environment variables are strings.**

```js
process.env.PORT
```

is:

```text
"5000"
```

not:

```text
5000
```

### Rule 6

**Keep the same application code across environments whenever possible.**

```text
Same Docker image
       +
Different configuration
       =
DEV / STAGING / PROD
```
