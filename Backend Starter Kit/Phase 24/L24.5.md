# Lesson 24.5 — HTTPS and TLS

In the previous lessons, we established:

```text
24.2 → Development vs Production
24.3 → Environment Variables
24.4 → Secrets Management
```

Now we move to one of the most important production requirements:

> **HTTPS protects communication between the client and your backend.**

For your MERN backend, think of the production request path as:

```text
Browser
   │
   │ HTTPS
   ▼
Internet
   │
   ▼
Reverse Proxy
   │
   ▼
Node.js API
   │
   ▼
MongoDB
```

---

# 1. HTTP vs HTTPS

Let's first understand HTTP.

When a browser sends:

```http
POST /api/v1/auth/login
```

it may contain:

```json
{
  "email": "user@example.com",
  "password": "mypassword"
}
```

With ordinary HTTP:

```text
Browser
   │
   │ HTTP
   ▼
Internet
   │
   ▼
Server
```

The communication is **not protected by TLS encryption**.

That's a serious problem for production.

---

# 2. What HTTPS Adds

HTTPS is essentially:

```text
HTTP
 +
TLS
```

So:

```text
HTTPS = HTTP over TLS
```

The simplified flow becomes:

```text
Browser
   │
   │ Encrypted HTTPS connection
   ▼
Server
```

TLS provides important security properties, especially:

```text
Confidentiality
Integrity
Authentication
```

We'll understand each one.

---

# 3. Confidentiality

Confidentiality means:

> Other parties should not be able to simply read the data being transmitted.

Suppose you send:

```json
{
  "email": "user@example.com",
  "password": "secret"
}
```

With a properly configured HTTPS connection:

```text
Browser
   │
   │ 🔒 encrypted
   ▼
Server
```

Someone observing network traffic shouldn't simply see the plaintext password.

This is extremely important for:

```text
Login credentials
Cookies
JWTs
Personal data
API requests
API responses
```

---

# 4. Integrity

HTTPS also helps protect the communication from being modified unnoticed while travelling across the network.

Think:

```text
Browser
   │
   │ "Transfer ₹100"
   ▼
Network
   │
   ▼
Server
```

You don't want an attacker to secretly modify the request into:

```text
"Transfer ₹100000"
```

TLS provides mechanisms that help detect tampering with the protected connection.

So:

```text
Confidentiality
    +
Integrity
```

are both important.

---

# 5. Authentication

This is another major part.

When your browser connects to:

```text
https://api.example.com
```

how does it know that it's really talking to the intended server?

TLS uses **digital certificates**.

Conceptually:

```text
Browser
   │
   │ "Who are you?"
   ▼
Server
   │
   ▼
TLS Certificate
   │
   ▼
Browser verifies certificate
```

The certificate helps establish the server's identity.

---

# 6. The Certificate

A TLS certificate contains information about the identity of the server/domain and is signed by a trusted certificate authority.

For example:

```text
api.example.com
```

can have a certificate associated with that domain.

The browser checks the certificate chain against trusted certificate authorities.

If everything is valid:

```text
Certificate valid
       ↓
TLS handshake continues
       ↓
Secure connection
```

If something is wrong, browsers can show warnings.

---

# 7. The TLS Handshake

You don't need to memorize every cryptographic detail, but you should understand the high-level process.

Very roughly:

```text
Client                         Server
  │                              │
  │──── ClientHello ────────────►│
  │                              │
  │◄──── ServerHello ────────────│
  │◄──── Certificate ────────────│
  │                              │
  │──── Key exchange ───────────►│
  │                              │
  │════ Encrypted connection ════│
```

After the handshake:

```text
Browser
   ═══════════════════════
      Encrypted traffic
   ═══════════════════════
Server
```

The exact TLS protocol behavior is more sophisticated, but this is the mental model you need for backend architecture.

---

# 8. Why HTTPS Matters Even More for Authentication

Your backend has authentication.

Think about this request:

```http
POST /api/v1/auth/login
```

It contains credentials.

Then consider an authenticated request:

```http
GET /api/v1/todos
Cookie: refreshToken=...
```

or:

```http
Authorization: Bearer <token>
```

Without proper transport security, sensitive authentication data can be exposed.

So:

```text
Authentication
      +
HTTPS
      ↓
Much safer authentication transport
```

HTTPS is therefore not an optional decoration around authentication.

It's part of the security architecture.

---

# 9. HTTPS and Cookies

This is especially important for the authentication architecture you've been building.

Production cookies commonly use:

```text
Secure
HttpOnly
SameSite
```

The `Secure` attribute means the browser should only send the cookie over a secure connection.

Conceptually:

```text
HTTP
  ↓
❌ Secure cookie

HTTPS
  ↓
✅ Secure cookie
```

We'll study the complete cookie configuration in **24.7**.

For now, remember:

> **Production HTTPS and secure authentication cookies are closely connected.**

---

# 10. HTTPS and Your MERN Architecture

Your production architecture might look like:

```text
                         INTERNET
                            │
                            ▼
                    HTTPS :443
                            │
                            ▼
                   ┌────────────────┐
                   │ Reverse Proxy  │
                   │ TLS termination│
                   └───────┬────────┘
                           │
                           ▼
                    Node.js :5000
                           │
                           ▼
                       MongoDB
```

Notice something interesting:

The Node.js application doesn't necessarily have to handle the public TLS connection directly.

A reverse proxy can handle it.

That's the topic we'll explore in **24.16**.

---

# 11. TLS Termination

Suppose:

```text
Browser
   │
   │ HTTPS
   ▼
Nginx
   │
   │ HTTP/internal network
   ▼
Node.js
```

Nginx can terminate the TLS connection.

This is called:

> **TLS termination**

The reverse proxy handles:

```text
HTTPS
Certificate
TLS handshake
Encryption/decryption
```

and forwards the request to your application.

Conceptually:

```text
Client
   │
   │ HTTPS
   ▼
Nginx
   │
   │ HTTP
   ▼
Node.js
```

This is common in production architectures.

---

# 12. Is HTTP Between Nginx and Node Always Unsafe?

Not necessarily.

Suppose:

```text
Browser
    │
    │ HTTPS
    ▼
Nginx
    │
    │ HTTP
    ▼
Node.js
```

If Nginx and Node are communicating over a protected private network on the same machine or trusted internal network, this can be a reasonable architecture.

But if the internal network itself is untrusted, you may need encryption there too.

The security requirement depends on your infrastructure.

So don't memorize:

```text
"HTTP is always okay internally."
```

Instead remember:

> **Protect communication across every network boundary according to the trust level of that network.**

---

# 13. Port 443

HTTPS commonly uses:

```text
443
```

while HTTP commonly uses:

```text
80
```

So a production server may expose:

```text
https://example.com
```

through:

```text
443
```

and redirect ordinary HTTP traffic:

```text
http://example.com
       │
       ▼
301/308 redirect
       │
       ▼
https://example.com
```

This ensures users end up on the secure version.

---

# 14. Why Redirect HTTP to HTTPS?

Imagine someone enters:

```text
http://app.example.com
```

You don't want the application to remain on unsecured HTTP.

Instead:

```text
HTTP
 ↓
Redirect
 ↓
HTTPS
```

This creates a consistent secure entry point.

However, the redirect itself doesn't magically encrypt the original HTTP request. That's why applications should avoid sending sensitive data over HTTP in the first place.

---

# 15. HTTPS Is Not the Same as Authentication

This distinction is important.

HTTPS does **not** mean:

```text
"Users are authenticated."
```

Instead:

```text
HTTPS
   ↓
Protects communication

Authentication
   ↓
Identifies/logs in the user
```

You need both.

For example:

```text
Browser
   │
   │ HTTPS
   ▼
API
   │
   │ Authentication
   ▼
User identity
```

---

# 16. HTTPS Is Not Authorization Either

Similarly:

```text
HTTPS
```

doesn't answer:

> "Is this user allowed to delete this todo?"

That's authorization.

You still need:

```text
HTTPS
   +
Authentication
   +
Authorization
```

Each solves a different problem.

---

# 17. HTTPS Does Not Make Your API Automatically Secure

This is a very common misunderstanding.

Suppose you have:

```text
HTTPS
   ↓
POST /api/v1/todos
```

An attacker can still send:

```json
{
  "title": "<malicious input>"
}
```

HTTPS doesn't protect against:

```text
SQL/NoSQL injection
Broken authorization
Weak passwords
Bad validation
CSRF
Rate-limit abuse
Business logic vulnerabilities
```

Those require other security controls.

Think:

```text
HTTPS
   +
Input validation
   +
Authentication
   +
Authorization
   +
Rate limiting
   +
Secure cookies
   +
Database security
   +
...
```

Production security is layered.

---

# 18. Certificates Expire

TLS certificates aren't something you configure once and forget forever.

Certificates have expiration dates.

Conceptually:

```text
Certificate
   │
   ├── issued
   │
   ├── valid
   │
   └── expires
```

If the certificate expires:

```text
Browser
   ↓
Certificate invalid/expired
   ↓
⚠️ Security warning
```

So production systems need certificate renewal.

Modern deployment setups often automate this.

---

# 19. Certificate Authorities

A certificate is trusted because it chains back to a trusted certificate authority (CA).

Simplified:

```text
Root CA
   ↓
Intermediate CA
   ↓
Your certificate
   ↓
api.example.com
```

Your browser has a trust store containing trusted root certificates.

It uses this chain to determine whether the certificate should be trusted.

You don't need to become a cryptography expert for this phase, but understand the architecture.

---

# 20. Domain Names Matter

Suppose your backend is:

```text
api.example.com
```

Your certificate should cover that hostname.

If your browser connects to:

```text
api.example.com
```

but receives a certificate intended for another domain, the browser can reject it.

So production HTTPS involves:

```text
Domain
   +
DNS
   +
Certificate
   +
Server/reverse proxy
```

---

# 21. DNS + HTTPS

Imagine:

```text
api.example.com
       │
       ▼
      DNS
       │
       ▼
Server IP
       │
       ▼
Reverse Proxy
       │
       ▼
TLS Certificate
       │
       ▼
Node.js
```

The browser first needs to find the server.

Then it establishes the secure TLS connection.

Then the request reaches your application.

---

# 22. HTTPS and Reverse Proxy

This is the production architecture we are moving toward.

Instead of:

```text
Internet
   ↓
Node.js
```

we want:

```text
Internet
   ↓
HTTPS
   ↓
Reverse Proxy
   ↓
Node.js
```

Why?

The reverse proxy can handle:

```text
TLS
Security headers
Request forwarding
Rate limiting
Connection management
Static files
Load balancing
```

depending on the architecture.

We'll study reverse proxies in detail later.

---

# 23. Local HTTPS vs Production HTTPS

You might ask:

> "Do I need HTTPS while developing locally?"

Not always.

You can usually develop using:

```text
http://localhost
```

But there are cases where local HTTPS is useful, particularly when testing browser features that require a secure context.

Production should use:

```text
https://
```

So:

```text
Development
    ↓
HTTP can be acceptable locally

Production
    ↓
HTTPS
```

Don't confuse local convenience with production requirements.

---

# 24. HTTPS and Secure Contexts

Modern browsers restrict certain powerful features to secure contexts.

Examples can include browser APIs involving:

```text
Web security
Authentication-related browser behavior
Service workers
Some advanced browser APIs
```

HTTPS establishes a secure context for normal production domains.

This is another reason modern web applications are built around HTTPS.

---

# 25. What Happens If HTTPS Is Missing?

Imagine:

```text
User
  ↓
HTTP
  ↓
API
```

Potential problems include:

```text
Sensitive traffic exposed
Secure cookies unavailable
Authentication credentials at risk
Browser security warnings/features
Poor security posture
```

For a real production application, that's unacceptable.

# 27. Important TLS Concepts

You should know these terms:

|Term|Meaning|
|---|---|
|HTTP|Application protocol for web requests|
|HTTPS|HTTP protected by TLS|
|TLS|Protocol providing secure communication|
|Certificate|Digital credential identifying a domain/server|
|CA|Certificate Authority|
|TLS handshake|Process establishing secure communication|
|Encryption|Protects confidentiality|
|Integrity|Helps detect tampering|
|TLS termination|Proxy/server ends TLS connection|
|Port 443|Conventional HTTPS port|
|Port 80|Conventional HTTP port|

# 30. What HTTPS Protects

Remember:

```text
HTTPS
 │
 ├── Confidentiality
 ├── Integrity
 └── Server authentication
```

It protects the **communication channel**.

It does not automatically protect:

```text
Application logic
Database
Authorization
User passwords at rest
Server vulnerabilities
Bad code
```

That's why production hardening needs multiple layers.
