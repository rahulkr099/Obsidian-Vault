# Lesson 24.7 — MongoDB Indexes

Now we move from **database security** to **database performance and query design**.

The key idea is:

> **An index helps MongoDB find documents efficiently instead of scanning the entire collection.**

For your MERN backend, this becomes very important as your data grows.

---

## 1. The Problem Without an Index

Imagine your `users` collection contains:

```text
1,000 users
10,000 users
100,000 users
1,000,000 users
```

And you run:

```js
User.findOne({
  email: "rahul@example.com"
});
```

MongoDB needs to find the matching document.

Without a suitable index, it may need to examine many documents.

Conceptually:

```text
users collection

Document 1   ❌
Document 2   ❌
Document 3   ❌
Document 4   ❌
...
Document 999999 ❌
Document 1000000 ✅
```

That's inefficient.

---

# 2. What Is an Index?

An index is an additional data structure that helps MongoDB locate documents faster.

Think about a book.

Without an index:

```text
Book
 ↓
Read every page
 ↓
Find "MongoDB"
```

With an index:

```text
Index
 ↓
MongoDB → page 250
 ↓
Go directly there
```

Database indexes work on the same general idea.

---

# 3. Collection vs Index

Suppose:

```text
users
```

contains:

```json
{
  "_id": "...",
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

An index might be created on:

```text
email
```

Conceptually:

```text
users
   │
   ├── documents
   │
   └── email index
          │
          └── email → document location/reference
```

MongoDB can use the index when querying by email.

---

# 4. Creating an Index with Mongoose

For a Mongoose schema:

```js
const userSchema = new mongoose.Schema({
  name: String,
  email: String
});
```

You can define:

```js
userSchema.index({
  email: 1
});
```

The `1` represents ascending index order.

For descending:

```js
userSchema.index({
  createdAt: -1
});
```

---

# 5. Indexing Email

A very common backend query is:

```js
User.findOne({
  email
});
```

For example, during login:

```text
POST /api/v1/auth/login
        │
        ▼
find user by email
        │
        ▼
MongoDB
```

Since email is frequently queried, an index can make this lookup much more efficient.

You might define:

```js
userSchema.index({
  email: 1
});
```

---

# 6. Unique Indexes

For users, email often needs to be unique.

You might define:

```js
const userSchema = new mongoose.Schema({
  email: {
    type: String,
    required: true,
    unique: true
  }
});
```

This creates a uniqueness constraint/index through Mongoose/MongoDB.

Conceptually:

```text
user@example.com
        ↓
must appear only once
```

So:

```text
User A
email = rahul@example.com
```

and:

```text
User B
email = rahul@example.com
```

should not both be accepted.

---

# 7. Important: `unique` Is Not Validation

This is a common misconception.

When you write:

```js
email: {
  type: String,
  unique: true
}
```

`unique` is primarily about creating a **unique index/constraint**, not ordinary Mongoose validation.

So you should still handle duplicate-key database errors properly.

Think:

```text
Request
   ↓
Validation
   ↓
Database
   ↓
Unique index
   ↓
Duplicate rejected
```

Your application should provide a clean API error instead of exposing the raw MongoDB error.

---

# 8. Indexes Improve Reads

Suppose your API frequently performs:

```js
Todo.find({
  userId
});
```

An index on:

```js
userId
```

can make these queries much more efficient:

```js
todoSchema.index({
  userId: 1
});
```

Then:

```text
User
 ↓
userId
 ↓
Index
 ↓
Matching todos
```

This is particularly useful for multi-user applications.

---

# 9. Indexes Also Help Sorting

Suppose your API returns:

```text
GET /api/v1/todos
```

and you sort:

```js
Todo.find({
  userId
}).sort({
  createdAt: -1
});
```

A suitable compound index may help:

```js
todoSchema.index({
  userId: 1,
  createdAt: -1
});
```

Now the index represents both:

```text
userId
+
createdAt
```

This is a **compound index**.

---

# 10. Compound Indexes

A compound index contains multiple fields.

Example:

```js
todoSchema.index({
  userId: 1,
  createdAt: -1
});
```

Think of it as:

```text
(userId, createdAt)
```

rather than two completely independent indexes.

It can be useful for queries such as:

```js
Todo.find({
  userId
}).sort({
  createdAt: -1
});
```

---

# 11. Index Field Order Matters

This is extremely important.

Consider:

```js
{
  userId: 1,
  createdAt: -1
}
```

The order matters.

It's not equivalent to:

```js
{
  createdAt: -1,
  userId: 1
}
```

when considering which queries the index can efficiently support.

You should design compound indexes based on your actual query patterns.

---

# 12. The Leftmost Prefix Idea

Suppose you have:

```js
{
  userId: 1,
  createdAt: -1
}
```

Conceptually, this index can help queries involving the leading field:

```text
userId
```

and combinations involving:

```text
userId + createdAt
```

But a query only involving:

```text
createdAt
```

doesn't get the same benefit from the index's leading structure.

So:

```text
(userId, createdAt)
       ↑
   leading field
```

matters.

---

# 13. Don't Create an Index for Every Field

This is a beginner mistake.

You might think:

```text
name → index
email → index
age → index
city → index
role → index
createdAt → index
updatedAt → index
```

More indexes ≠ automatically better performance.

Indexes have costs.

---

# 14. Indexes Consume Storage

An index is additional data.

So:

```text
Collection
   +
Indexes
   =
More storage
```

If you create unnecessary indexes:

```text
Database size ↑
```

---

# 15. Indexes Can Slow Writes

This is a very important trade-off.

Suppose you insert a document:

```js
User.create({
  name,
  email
});
```

MongoDB has to update the relevant indexes too.

So:

```text
Write
  ↓
Update collection
  +
Update indexes
```

More indexes can mean more work during:

```text
INSERT
UPDATE
DELETE
```

Therefore:

> **Indexes speed up some reads but add overhead to writes.**

---

# 16. Index Design Is a Trade-Off

Think:

```text
                INDEX
                  │
       ┌──────────┴──────────┐
       ▼                     ▼
   Faster reads          More overhead
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
                 Storage          Write cost
```

Good database design balances these.

---

# 17. Index Based on Real Queries

Don't start with:

> "Which fields should I index?"

Start with:

> **"Which queries does my application perform frequently?"**

For example:

```text
GET /todos
GET /todos/:id
GET /users/:id
POST /login
GET /orders
```

Then inspect the database operations behind them.

---

# 18. Example: Todo Application

Suppose your application frequently executes:

```js
Todo.find({
  userId
}).sort({
  createdAt: -1
});
```

A reasonable index candidate is:

```js
todoSchema.index({
  userId: 1,
  createdAt: -1
});
```

Why?

Because the query uses:

```text
userId
createdAt
```

and the index reflects that access pattern.

---

# 19. Example: User Login

Login might perform:

```js
User.findOne({
  email
});
```

Candidate:

```js
userSchema.index({
  email: 1
});
```

If email must be unique:

```js
userSchema.index(
  {
    email: 1
  },
  {
    unique: true
  }
);
```

This simultaneously supports efficient lookup and uniqueness.

---

# 20. Example: Orders

Imagine:

```js
Order.find({
  userId,
  status: "pending"
});
```

A possible compound index could be:

```js
orderSchema.index({
  userId: 1,
  status: 1
});
```

But don't blindly add it.

First ask:

```text
How frequently is this query executed?
How many documents exist?
How selective are the fields?
Are there other queries using these fields?
```

Index design should come from actual workload.

---

# 21. Selectivity

Another useful concept is **selectivity**.

Suppose you have:

```text
gender
```

with only:

```text
male
female
```

Many documents have the same value.

Now compare:

```text
email
```

where almost every user has a different value.

An index on a highly selective field can often be much more useful for equality lookups.

Conceptually:

```text
email
 ↓
very specific

gender
 ↓
many matching documents
```

This isn't a universal rule for every query, but it is an important factor when designing indexes.

---

# 22. Don't Guess — Use Query Analysis

MongoDB provides query-analysis tools such as:

```js
.explain()
```

For example:

```js
db.todos
  .find({
    userId: someUserId
  })
  .explain("executionStats");
```

This lets you investigate how MongoDB executes a query.

You can look at information such as:

```text
Documents examined
Keys examined
Execution time
Query plan
```

This is much better than blindly guessing.

---

# 23. `COLLSCAN`

When MongoDB scans the entire collection, you may see:

```text
COLLSCAN
```

Conceptually:

```text
Query
 ↓
Scan every document
 ↓
Find matches
```

For a large collection, that can become expensive.

---

# 24. `IXSCAN`

When MongoDB uses an index, you may see:

```text
IXSCAN
```

Conceptually:

```text
Query
 ↓
Index
 ↓
Matching documents
```

So:

```text
COLLSCAN
→ collection scan

IXSCAN
→ index scan
```

These are useful concepts when reading query execution plans.

---

# 25. `explain()` Is a Developer Tool

A good development workflow is:

```text
Build query
    ↓
Run explain()
    ↓
Inspect execution
    ↓
Create/adjust index
    ↓
Run explain() again
    ↓
Compare
```

This turns index design into an evidence-based process.

---

# 26. Don't Optimize Tiny Collections Too Early

Imagine:

```text
todos = 20 documents
```

A collection scan may be perfectly fine.

Now imagine:

```text
todos = 50 million documents
```

Query design becomes much more important.

Therefore:

> **Don't add indexes simply because an index sounds faster.**

Consider:

```text
Data size
Query frequency
Query shape
Read/write ratio
Latency requirements
Storage cost
```

---

# 27. Indexes and Pagination

This is especially relevant because you've already completed Phase 18 on pagination.

Suppose you're doing:

```js
Todo.find({
  userId
})
.sort({
  createdAt: -1
})
.limit(20);
```

A compound index can support the access pattern:

```js
{
  userId: 1,
  createdAt: -1
}
```

For large datasets, index design becomes very important for pagination performance.

Later, when using cursor-based pagination, the index becomes even more important.

---

# 28. Indexes and Sorting

Suppose you do:

```js
.find({
  userId
})
.sort({
  createdAt: -1
});
```

Without a suitable index, MongoDB may need additional work to produce the sorted result.

With a suitable index:

```text
(userId, createdAt)
```

the database may be able to retrieve records in the desired order more efficiently.

This is one reason query shape and index shape should be designed together.

---

# 29. Indexes and Unique Constraints

Indexes aren't only about speed.

They can enforce important data rules.

For example:

```text
email must be unique
```

can be enforced using a unique index.

Other examples can include:

```text
username unique
slug unique
externalId unique
```

This is a powerful database-level protection.

---

# 30. Database Constraints Should Not Exist Only in JavaScript

Suppose you check:

```js
const existingUser = await User.findOne({ email });

if (existingUser) {
  throw new ConflictError();
}

await User.create({ email });
```

This is useful, but there is a race condition.

Two requests could arrive almost simultaneously:

```text
Request A ── check ── no user
Request B ── check ── no user
Request A ── create
Request B ── create
```

A unique database constraint provides stronger protection.

```text
Database
   ↓
UNIQUE email
   ↓
Duplicate rejected
```

This is a great example of why the database should enforce critical invariants.

---

# 31. Indexes and Security

Indexes are mostly a performance/database-design topic, but they can also support security-related constraints.

For example:

```text
Unique email
Unique username
Unique external identifier
```

These prevent duplicate identity records.

But remember:

> **An index does not replace authorization.**

An index can enforce uniqueness.

It cannot decide:

```text
"Is Rahul allowed to delete this todo?"
```

That remains application authorization.

---

# 32. Indexes in Mongoose

You can define indexes at the field level:

```js
const userSchema = new mongoose.Schema({
  email: {
    type: String,
    unique: true
  }
});
```

Or schema level:

```js
userSchema.index({
  email: 1
});
```

For compound indexes:

```js
todoSchema.index({
  userId: 1,
  createdAt: -1
});
```

Schema-level indexes are especially useful for more complex index definitions.

---

# 33. Be Careful in Production

Creating indexes on a large production collection isn't something you should treat casually.

Imagine:

```text
100 million documents
```

and then suddenly adding several indexes.

That operation can have resource implications.

So production database changes should be planned.

Think:

```text
Schema change
   ↓
Migration strategy
   ↓
Index creation
   ↓
Monitor
   ↓
Verify
```

---

# 34. Indexes and Deployments

Your deployment process may need to manage indexes.

For example:

```text
Application version
        +
Database schema/index state
```

should remain compatible.

You don't want:

```text
New application
      ↓
expects index
      ↓
index doesn't exist
```

or:

```text
Old application
      ↓
unexpected database changes
```

Database changes should be part of your deployment thinking.

---

# 35. Don't Delete Indexes Blindly

Before removing an index, ask:

```text
Which queries use it?
Is it redundant?
Is it unused?
Does another index cover the workload?
What happens to write performance?
```

Removing an index can improve write performance and storage usage, but it can also make important queries slower.

Again:

> Measure before changing.

---

# 36. Common Index Mistakes

### Mistake 1 — Index everything

```text
❌ Every field gets an index
```

Result:

```text
More storage
More write overhead
More maintenance
```

---

### Mistake 2 — No indexes on frequent queries

```text
❌ Large collection
❌ Frequent lookup
❌ Full collection scan
```

---

### Mistake 3 — Wrong compound-index order

```text
Query pattern
     ≠
Index design
```

---

### Mistake 4 — Assuming `unique` means validation

```text
unique
≠
normal application validation
```

---

### Mistake 5 — Never checking query plans

```text
"I think this query is fast."
```

isn't as useful as:

```text
.explain("executionStats")
```

# 37. A Practical MERN Example

Suppose your Todo API supports:

```text
GET /api/v1/todos
```

The service executes:

```js
Todo.find({
  userId
})
.sort({
  createdAt: -1
})
.limit(20);
```

A possible schema:

```js
const todoSchema = new mongoose.Schema(
  {
    userId: {
      type: mongoose.Schema.Types.ObjectId,
      required: true
    },

    title: {
      type: String,
      required: true
    },

    completed: {
      type: Boolean,
      default: false
    }
  },
  {
    timestamps: true
  }
);
```

Then:

```js
todoSchema.index({
  userId: 1,
  createdAt: -1
});
```

Now the index matches an important query pattern:

```text
userId
   ↓
createdAt descending
```

# 38. Think About the Query First

Instead of:

```text
"I need an index."
```

think:

```text
"What does my application actually query?"
```

For example:

```text
Query:
Todo.find({ userId }).sort({ createdAt: -1 })
```

Then:

```text
Access pattern:
userId + createdAt descending
```

Then:

```text
Candidate index:
(userId, createdAt DESC)
```

This is the professional way to think about indexing.

# 39. Index Design Workflow

Use this process:

```text
1. Identify important query
          ↓
2. Understand filter fields
          ↓
3. Understand sort fields
          ↓
4. Understand pagination
          ↓
5. Check existing indexes
          ↓
6. Use explain()
          ↓
7. Design index
          ↓
8. Test
          ↓

```

Don't skip the measurement step.

# 🔥 Five Rules to Memorize

### Rule 1

**Indexes make many reads faster, but they have storage and write costs.**

### Rule 2

**Index frequently used query fields when the workload justifies it.**

### Rule 3

**Compound index field order matters.**

```js
{
  userId: 1,
  createdAt: -1
}
```

is not the same as:

```js
{
  createdAt: -1,
  userId: 1
}
```

### Rule 4

**Use unique indexes for database-level uniqueness guarantees.**

```text
email
username
slug
```

### Rule 5

**Measure query performance instead of guessing.**

```js
.explain("executionStats")
```
