# Lesson 24.8 — Rate Limiting

According to your Phase 24 roadmap, **24.8 is Rate Limiting**, followed by logging, error handling, health checks, graceful shutdown, Docker, reverse proxy, deployment architecture, and the final production checklist.

The main idea is simple:

> **Rate limiting controls how many requests a client can make within a certain amount of time.**

It protects your backend from excessive traffic, accidental abuse, brute-force attempts, and some forms of automated attacks.

---

# 1. The Problem Rate Limiting Solves

Imagine your API has:

```http
POST /api/v1/auth/login
```

A normal user might make:

```text
1 request
2 requests
5 requests
```

But an attacker might send:

```text
10 requests/second
100 requests/second
10,000 requests/minute
```

Your backend then has to process all of them:

```text
Attacker
   │
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   └── ...
          ↓
       Node.js
          ↓
       Database
```

Eventually:

```text
CPU ↑
Memory ↑
Database load ↑
Network usage ↑
Response time ↑
```

Rate limiting puts a control in front of your application.

---

# 2. Basic Rate Limiting

Imagine we allow:

```text
100 requests
per 15 minutes
per client
```

Then:

```text
Client
   │
   ├── Request 1  ✅
   ├── Request 2  ✅
   ├── ...
   ├── Request 100 ✅
   └── Request 101 ❌
```

The server might return:

```http
429 Too Many Requests
```

So:

```text
Rate limit exceeded
        ↓
HTTP 429
```

---

# 3. HTTP 429

The standard status code is:

```http
429 Too Many Requests
```

For example:

```json
{
  "success": false,
  "message": "Too many requests. Please try again later."
}
```

Your API should provide a clear response rather than exposing internal rate-limiter details.

---

# 4. Rate Limiting Is Not Authentication

These are different.

### Authentication

```text
"Who are you?"
```

### Authorization

```text
"What are you allowed to do?"
```

### Rate limiting

```text
"How frequently are you allowed to make requests?"
```

So:

```text
Request
   │
   ├── Authentication
   ├── Authorization
   └── Rate limiting
```

They solve different problems.

---

# 5. Why Global Rate Limiting Matters

Suppose your API has:

```text
GET /api/v1/todos
GET /api/v1/users/me
POST /api/v1/todos
POST /api/v1/auth/login
POST /api/v1/auth/forgot-password
```

You can have a general limit across the API.

For example:

```text
100 requests / 15 minutes
```

Conceptually:

```text
Internet
   │
   ▼
Rate Limiter
   │
   ├── under limit → API
   │
   └── over limit  → 429
```

This gives your backend a basic protection layer.

---

# 6. But One Global Limit Isn't Enough

Imagine:

```text
GET /api/v1/todos
```

and:

```text
POST /api/v1/auth/login
```

They have very different security requirements.

A user might reasonably request todos many times.

But login attempts should be much more restricted.

So you should think in terms of:

```text
Global limit
      +
Endpoint-specific limits
```

---

# 7. Global Rate Limit

A global limiter might conceptually say:

```text
All API requests
       ↓
100 requests / 15 minutes
```

This helps protect the entire application from excessive request volume.

But it shouldn't be your only protection.

---

# 8. Authentication Rate Limiting

Authentication endpoints deserve stricter limits.

For example:

```text
POST /auth/login
```

could have a much lower threshold.

Conceptually:

```text
Login
  ↓
5 attempts / 15 minutes
```

rather than:

```text
100 requests / 15 minutes
```

Why?

Because attackers can repeatedly attempt passwords.

---

# 9. Brute-Force Attacks

Imagine an attacker knows:

```text
email = victim@example.com
```

and tries:

```text
password123
password124
password125
...
```

Without controls:

```text
Attacker
   ↓
Login
   ↓
Login
   ↓
Login
   ↓
Login
   ↓
...
```

Rate limiting slows this down.

```text
Attacker
   ↓
Login attempt
   ↓
Login attempt
   ↓
Login attempt
   ↓
429
```

This doesn't solve authentication security by itself, but it makes automated guessing much harder.

---

# 10. Password Reset Needs Rate Limiting Too

Consider:

```http
POST /api/v1/auth/forgot-password
```

An attacker could repeatedly request password-reset emails.

Without limits:

```text
Attacker
   ↓
Forgot password
   ↓
Email
   ↓
Forgot password
   ↓
Email
   ↓
...
```

This could cause:

```text
Email spam
Email provider costs
User annoyance
Potential abuse
```

So sensitive endpoints such as:

```text
login
signup
forgot password
resend verification
OTP
```

often deserve specialized rate limits.

---

# 11. OTP Endpoints

Suppose your application has:

```http
POST /api/v1/auth/verify-otp
```

An attacker could attempt:

```text
000000
000001
000002
000003
...
```

Rate limiting reduces how quickly they can try.

You may also need:

```text
OTP expiration
Maximum attempts
Account/session controls
Token invalidation
```

So rate limiting is one layer in a larger defense.

---

# 12. Rate Limiting and DDoS

Rate limiting can help with certain abusive traffic patterns, but:

> **Application-level rate limiting is not a complete DDoS solution.**

Why?

Suppose your Node.js server receives:

```text
10 million requests
```

Your application-level limiter still needs infrastructure to receive and process those connections.

For large attacks, protection may need to happen earlier:

```text
Internet
   ↓
CDN / WAF / Load Balancer
   ↓
Reverse Proxy
   ↓
Rate Limiter
   ↓
Node.js
```

So think in layers.

---

# 13. Rate Limiting Layers

A production architecture might have:

```text
                    INTERNET
                        │
                        ▼
                    CDN / WAF
                        │
                        ▼
                  Load Balancer
                        │
                        ▼
                  Reverse Proxy
                        │
                        ▼
                Application Rate Limit
                        │
                        ▼
                    Node.js
```

Different layers solve different problems.

# 15. AI Endpoints

This is particularly important for your future MERN/AI projects.

Suppose you have:

```http
POST /api/v1/ai/chat
```

Each request may call an external AI provider.

Imagine:

```text
User
 ↓
AI request
 ↓
Your server
 ↓
LLM provider
 ↓
Tokens/cost
```

An attacker can generate:

```text
1000 AI requests
```

So AI endpoints may need:

```text

Usage tracking
Cost controls

```

Rate limiting becomes both a **security** and **cost-control** mechanism.

---

# 16. Rate Limiting by IP

The simplest strategy is:

```text
IP address
    ↓
Request count
```

For example:

```text
192.168.1.10
    ↓
80 requests
```

and:

```text
192.168.1.10
    ↓
request 101
    ↓
429
```

This is useful, but IP-based limiting has limitations.

---

# 17. Why IP Isn't Always a Perfect Identity

Many users may share one public IP.

For example:

```text
College Wi-Fi
      │
      ├── Student A
      ├── Student B
      ├── Student C
      ├── Student D
      └── Student E
              │
              ▼
        Same public IP
```

If you aggressively rate-limit by IP:

```text
One abusive user
      ↓
Everyone affected
```

So IP-based rate limiting should be designed carefully.

---

# 18. Rate Limiting by User

For authenticated users, you can also think in terms of:

```text
userId
   ↓
request count
```

For example:

```text
User 123
   ↓
100 requests / minute
```

This can be more meaningful than IP alone.

A production system may combine:

```text
IP
+
User
+
Endpoint
```

depending on the use case.

---

# 19. Anonymous vs Authenticated Users

You can have different policies.

```text
Anonymous
   ↓
strict limit

Authenticated
   ↓
higher limit
```

For example:

```text
Public API
→ 30 requests/minute

Authenticated API
→ 300 requests/minute
```

The actual numbers should come from your application's requirements and observed traffic, not arbitrary universal values.

---

# 20. Rate Limiting Should Be Per Route

Imagine:

```text
GET /todos
```

is cheap.

But:

```text
POST /ai/generate
```

is expensive.

Using the same limit for both isn't necessarily ideal.

Instead:

```text
Cheap endpoint
    ↓
Higher limit

Expensive endpoint
    ↓
Lower limit
```

This is why production systems often have multiple rate-limit policies.

---

# 21. Express Rate Limiting

Your Phase 10 security curriculum already introduced rate limiting as middleware, including global limiting, authentication limiting, and brute-force protection.

In Express, a common implementation uses a package such as `express-rate-limit`.

Conceptually:

```js
const limiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100
});
```

Then:

```js
app.use(limiter);
```

The important thing isn't memorizing the package API.

Understand what the middleware is doing:

```text
Request
   ↓
Rate limiter
   │
   ├── allowed → next()
   │
   └── exceeded → 429
```

---

# 22. Middleware Position Matters

Consider:

```js
app.use(rateLimiter);
app.use(routes);
```

The limiter runs before the routes.

Flow:

```text
Request
   ↓
Rate limiter
   ↓
CORS
   ↓
Authentication
   ↓
Validation
   ↓
Controller
```

The exact ordering depends on what you want each middleware to protect, but middleware order should always be deliberate.

---

# 23. Global vs Route-Specific Middleware

Global:

```js
app.use(globalRateLimiter);
```

Route-specific:

```js
router.post(
  "/login",
  loginRateLimiter,
  loginController
);
```

Then:

```text
Normal API
   ↓
Global limiter

Login
   ↓
Global limiter
   ↓
Login-specific limiter
```

This gives you layered protection.

---

# 24. Why Have Both?

Suppose:

```text
Global:
1000 requests/hour
```

and:

```text
Login:
5 attempts/15 minutes
```

An attacker could still hit login only five times every 15 minutes.

That's much stronger than relying on the global limit.

So:

```text
Global protection
        +
Sensitive endpoint protection
```

is a good pattern.

---

# 25. Rate Limit Response Headers

A rate limiter may communicate limit information through HTTP headers.

Conceptually:

```http
RateLimit-Limit: 100
RateLimit-Remaining: 42
RateLimit-Reset: ...
```

The exact headers depend on your implementation and configuration.

These can help clients understand their usage.

---

# 26. Don't Leak Too Much Information

Your error response should remain simple.

Good:

```json
{
  "success": false,
  "message": "Too many requests. Please try again later."
}
```

You don't need to reveal internal implementation details like:

```text
Redis key structure
internal limiter algorithm
server architecture
```

Keep the external API contract clean.

---

# 27. Fixed Window

One simple rate-limiting model is a **fixed window**.

Example:

```text
10 requests
per 1 minute
```

Window:

```text
12:00:00 → 12:00:59
```

Count:

```text
Request 1
Request 2
...
Request 10
```

Then:

```text
Request 11
   ↓
429
```

At the next window:

```text
12:01:00
```

the counter resets.

---

# 28. Sliding Window

Another approach is a **sliding window**.

Instead of thinking:

```text
12:00–12:01
```

you consider the previous period relative to the current request.

Conceptually:

```text
Current time
     │
     ├──────── previous 60 seconds ────────┤
```

This can provide smoother behavior than a simple fixed window.

---

# 29. Token Bucket

Another common algorithm is the **token bucket**.

Think of a bucket:

```text
        ┌───────────────┐
        │ 🪙 🪙 🪙 🪙 🪙 │
        │     TOKENS     │
        └───────────────┘
```

Requests consume tokens:

```text
Request
   ↓
Take token
   ↓
Allowed
```

Tokens refill over time.

If the bucket is empty:

```text
Request
   ↓
No token
   ↓
429
```

This allows controlled bursts while maintaining an overall rate.

---

# 30. You Don't Need to Implement the Algorithm Yourself

For most Express applications, you shouldn't begin by writing your own rate limiter.

Use a well-tested implementation and understand:

```text
what it limits
how the key is identified
where state is stored
how it behaves across multiple servers
```

The architecture is more important than reinventing the algorithm.

---

# 31. The Multi-Server Problem

This is one of the most important production concepts.

Imagine:

```text
Load Balancer
      │
 ┌────┴────┐
 ▼         ▼
Node A    Node B
```

Suppose Node A stores:

```text
user123 → 90 requests
```

and Node B stores:

```text
user123 → 10 requests
```

Now the user has effectively made:

```text
100 requests
```

but neither server independently sees the complete picture.

This is why distributed rate limiting needs shared state.

---

# 32. In-Memory Rate Limiting

A simple development setup might store counters in Node.js memory:

```text
Node.js
  │
  └── memory
        └── rate counters
```

This can work for:

```text
Local development
Single-process applications
Simple deployments
```

But there is a major problem in a distributed deployment.

---

# 33. Multiple Instances

Imagine:

```text
                Load Balancer
                     │
             ┌───────┴───────┐
             ▼               ▼
          Node A           Node B
             │               │
          Memory A         Memory B
```

They don't automatically share counters.

So:

```text
Rate limiter state
     ≠
Global rate limiter state
```

---

# 34. Redis for Distributed Rate Limiting

This is where Redis becomes useful.

Architecture:

```text
             Load Balancer
                  │
          ┌───────┴───────┐
          ▼               ▼
       Node A           Node B
          │               │
          └───────┬───────┘
                  ▼
                Redis
                  │
                  ▼
          Shared rate state
```

Now both Node instances can see the same counters.

This connects directly to your later Redis/background-jobs learning.

---

# 35. Why Redis Works Well Here

Redis is designed for fast operations on short-lived data.

Rate-limiting data often looks like:

```text
key
counter
expiration
```

For example:

```text
rate:user:123
```

with:

```text
count = 87
expires = 42 seconds
```

This is a good fit for Redis.

# 36. Reverse Proxy / CDN Rate Limiting

You can also limit traffic before it reaches Node.js.

For example:

```text

   ↓
CDN / WAF
   ↓
Rate limit
   ↓
Reverse Proxy
   ↓
Node.js
```

This can reduce pressure on your application.

So production rate limiting may happen at multiple levels:


# 37. Rate Limiting vs Quotas

These concepts are related but different.

### Rate limit

Controls:

```text
How fast can you make requests?
```

Example:

```text
100 requests/minute
```

### Quota

Controls:

```text
How much can you use over a larger period?
```

Example:

```text
10,000 AI tokens/day
```

So:

```text
Rate
 ↓
requests/time

Quota
 ↓
usage/time
```

For AI applications, you may want both.

---

# 38. Rate Limiting vs Concurrency Limits

Another related concept:

```text
Rate
```

means:

> How many requests are allowed over time?

Whereas:

```text
Concurrency
```

means:

> How many operations can be running at the same time?

Example:

```text
Maximum 10 simultaneous AI jobs
```

Even if the user is under the request-per-minute limit.

So a production system might have:

```text
Rate limit
+
Concurrency limit
+
Usage quota
```

---

# 39. Don't Rate Limit Everything Equally

Think about your endpoints:

```text
GET /healthz
GET /todos
POST /todos
POST /auth/login
POST /auth/forgot-password
POST /ai/generate
POST /upload
```

These have different risk/cost profiles.

A better design might be:

```text
health
 ↓
very lightweight

normal API
 ↓
normal limit

authentication
 ↓
strict limit

AI
 ↓
strict + quota

uploads
 ↓
strict + size limit
```

This is much better than blindly applying one number everywhere.


# 46. Authentication Rate Limiting Is Tricky

Suppose login is limited only by:

```text
IP
```

An attacker can distribute attempts across many IPs.

Suppose it's limited only by:

```text
email
```

an attacker might target many accounts.

A stronger strategy can combine signals:

```text
IP
+
account identifier
+
endpoint
+
time
```

But be careful not to accidentally allow attackers to cause denial-of-service against legitimate users.

Security controls should be designed to avoid making the defense itself an attack tool.

---

# 47. Rate Limiting and Account Lockout

Don't automatically assume:

```text
Too many attempts
   ↓
Permanently lock account
```

That can allow attackers to intentionally lock other users out.

A better design can use:

```text
Rate limiting
+
Temporary delays
+
Risk detection
+
Careful account controls
```

The exact authentication defense depends on your threat model.

# 50. Don't Put Rate Limiting in the Controller

Avoid:

```js
async function login(req, res) {
  // manually count requests here
}
```

Why?

Because rate limiting is infrastructure/security behavior, not login business logic.

Better:

```text
Route
 ↓
Rate-limit middleware
 ↓
Controller
```

Then the controller remains focused on the login operation.

# 51. A Simple Mental Model

Think of rate limiting as a security gate:

```text
                API
                 │
          ┌──────▼──────┐
          │ Rate Limit  │
          │   Gate      │
          └──────┬──────┘
                 │
```

The gate doesn't care about the business operation.

# 53. What Happens When a Limit Is Reached?

The flow should be:

```text
Request
   ↓
Identify rate-limit key
   ↓
Read current usage
   ↓
Under limit?
   │
   ├── YES → increment → next()
   │
   └── NO  → 429
```

Conceptually:

```js
if (limitExceeded) {
  return res.status(429).json({
    success: false,
    message: "Too many requests"
  });
}

next();
```

A production library handles the actual counting and timing.

# 🔥 Five Rules to Memorize

### Rule 1

**Rate limiting controls request frequency.**

```text
Too many requests
       ↓
429
```

### Rule 2

**Don't use one rate limit for every endpoint.**

Sensitive/expensive endpoints deserve stricter policies.

### Rule 3

**Authentication endpoints need special protection.**

Especially:

```text
login
forgot password
OTP
verification
```

### Rule 4

**In-memory rate limiting doesn't automatically work across multiple Node instances.**

For distributed systems, shared state such as Redis can be used.

### Rule 5

**Rate limiting is one security layer, not a complete DDoS solution.**

Think:

```text
CDN/WAF
  +
Reverse Proxy
  +
Application Rate Limit
  +
Endpoint Rate Limit
```

Design rate limits for this API:

Think about:

```text
Which should have the strictest limit?

Which should use user-based limiting?
Which needs a usage quota?
Which needs both rate limiting and a resource limit?
```

The goal isn't to find one "correct number."

The goal is to learn to ask:
