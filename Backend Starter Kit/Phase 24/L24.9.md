# Lesson 24.9 — Logging

This lesson is about **production logging**: recording what your backend is doing so you can debug problems, investigate security events, and understand system behavior.

The important connection with the previous lesson is:

```text
Request
   ↓
Rate Limiting
   ↓
Application
   ↓
Logging
   ↓
Monitoring / Debugging
```

A production backend should not depend on `console.log()` everywhere.

---

## 1. What Is Logging?

Logging means recording useful information about events happening inside your application.

For example:

```text
User logged in
Request received
Database query failed
Rate limit exceeded
Payment failed
Server started
```

A log might look conceptually like:

```json
{
  "level": "info",
  "message": "User logged in",
  "userId": "123",
  "requestId": "abc-789"
}
```

The goal is not to record everything.

The goal is to record **useful information**.

---

# 2. Why Logging Matters

Imagine your production API suddenly starts returning:

```http
500 Internal Server Error
```

A user reports:

> "The todo API isn't working."

Without logs:

```text
❓ What happened?
❓ Which request?
❓ Which user?
❓ Which endpoint?
❓ Which service failed?
❓ Database problem?
❓ Code problem?
```

With good logs:

```text
requestId=abc123
method=POST
route=/api/v1/todos
status=500
error=MongoServerError
```

You can investigate much faster.

---

# 3. Logging Is Not Just Debugging

Logging helps with several things:

```text
                    LOGGING
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
   Debugging       Security         Operations
       │               │                │
       ▼               ▼                ▼
   Errors          Suspicious       Traffic
   Failures        activity         behavior
```

It can help answer:

```text
What happened?
When did it happen?
Where did it happen?
Which request caused it?
How severe was it?
```

---

# 4. `console.log()` vs Production Logging

During development, this is common:

```js
console.log("User logged in");
```

It is fine for quick experimentation.

But a production system needs more structure.

Instead of:

```text
User logged in
```

you want something closer to:

```json
{
  "level": "info",
  "event": "user.login.success",
  "userId": "...",
  "requestId": "...",
  "timestamp": "..."
}
```

Structured logs are much easier to search and analyze.

---

# 5. Log Levels

A common logging system has levels such as:

```text
debug
info
warn
error
```

Some systems also use:

```text
fatal
```

Think of them as severity levels.

---

# 6. DEBUG

`debug` is for detailed information useful during development or troubleshooting.

Example:

```text
DEBUG database query started
DEBUG cache lookup completed
DEBUG service returned result
```

You generally don't want extremely verbose debug logging enabled everywhere in production.

---

# 7. INFO

`info` represents normal important application events.

Examples:

```text
Server started
User authenticated
Order created
Email queued
Job completed
```

Example:

```json
{
  "level": "info",
  "event": "order.created",
  "orderId": "123"
}
```

---

# 8. WARN

`warn` means something unusual happened, but the application may still continue normally.

Examples:

```text
Rate limit approaching
External API slow
Deprecated endpoint used
Retry required
```

Example:

```json
{
  "level": "warn",
  "event": "external_api.slow",
  "durationMs": 4200
}
```

---

# 9. ERROR

`error` means something failed.

Examples:

```text
Database query failed
Payment processing failed
External API request failed
Unexpected exception
```

Example:

```json
{
  "level": "error",
  "event": "database.query.failed",
  "requestId": "abc123"
}
```

Errors should contain enough context to investigate the problem.

---

# 10. FATAL

Some logging systems support:

```text
fatal
```

This represents a severe failure that prevents the application or major component from continuing.

For example:

```text
Application cannot connect to required database
```

Don't use `fatal` for ordinary errors.

---

# 11. Log Level Mental Model

Remember:

```text
DEBUG
  ↓
Detailed technical information

INFO
  ↓
Normal important events

WARN
  ↓
Something unusual

ERROR
  ↓
Something failed

FATAL
  ↓
Critical failure
```

---

# 12. Structured Logging

This is one of the most important concepts in modern backend development.

Instead of:

```text
User Rahul created todo 123
```

use structured data:

```json
{
  "level": "info",
  "event": "todo.created",
  "userId": "123",
  "todoId": "456"
}
```

Now a log system can easily search:

```text
event = "todo.created"
```

or:

```text
userId = "123"
```

---

# 13. Why JSON Logs Are Useful

Suppose you have:

```text
1,000,000 logs
```

Text searching becomes difficult.

Structured logs allow systems to filter:

```text
status = 500
```

or:

```text
route = "/api/v1/auth/login"
```

or:

```text
level = "error"
```

This becomes extremely valuable in production.

---

# 14. Request IDs

One of the most useful logging concepts is a **request ID**.

Imagine:

```text
Client
  ↓
Request
  ↓
Controller
  ↓
Service
  ↓
Database
```

Many operations happen for one request.

You want all related logs to contain:

```text
requestId=abc123
```

Then:

```text
requestId=abc123
  ├── request received
  ├── authentication checked
  ├── service started
  ├── database query
  ├── database completed
  └── response 200
```

Now you can trace one request through your system.

---

# 15. Request ID Flow

Conceptually:

```text
HTTP Request
     │
     ▼
Generate / accept request ID
     │
     ▼
Attach to request context
     │
     ├───────────────┐
     ▼               ▼
Controller        Logger
     │               │
     ▼               │
Service              │
     │               │
     ▼               │
Repository           │
     │               │
     └───────┬───────┘
             ▼
        Same requestId
```

This becomes even more valuable when you later have multiple services.

---

# 16. Request ID Example

A request might produce:

```json
{
  "level": "info",
  "event": "request.received",
  "requestId": "7f8c..."
}
```

Then:

```json
{
  "level": "info",
  "event": "todo.created",
  "requestId": "7f8c...",
  "todoId": "123"
}
```

Then:

```json
{
  "level": "info",
  "event": "request.completed",
  "requestId": "7f8c...",
  "statusCode": 201
}
```

All three logs can be connected.

---

# 17. Request ID vs User ID

These are different.

### Request ID

Identifies:

```text
one HTTP request
```

### User ID

Identifies:

```text
one authenticated user
```

You may have:

```text
userId = 42
```

across hundreds of requests.

But each request gets its own:

```text
requestId
```

So:

```text
User 42
 ├── request A
 ├── request B
 └── request C
```

---

# 18. Logging HTTP Requests

A useful HTTP access log can contain:

```text
HTTP method
Route
Status code
Duration
Request ID
```

For example:

```json
{
  "level": "info",
  "event": "http.request",
  "method": "GET",
  "route": "/api/v1/todos",
  "statusCode": 200,
  "durationMs": 32,
  "requestId": "abc123"
}
```

This gives you a basic picture of API behavior.

---

# 19. Don't Log Entire Requests Blindly

This is dangerous.

A request may contain:

```text
password
access token
refresh token
API key
credit-card information
personal data
```

Never blindly do:

```js
console.log(req.body);
```

in production.

You could accidentally expose sensitive information.

---

# 20. Passwords Must Never Be Logged

Never:

```json
{
  "email": "user@example.com",
  "password": "MySecretPassword123"
}
```

Instead:

```json
{
  "email": "user@example.com"
}
```

Even during debugging, be extremely careful with credentials.

---

# 21. Tokens Must Not Be Logged

Avoid:

```text
Authorization: Bearer eyJ...
```

in logs.

Also avoid logging:

```text
accessToken
refreshToken
resetToken
OTP
API keys
```

Logging infrastructure is itself a sensitive data store.

---

# 22. Logs Are Data

This is an important security mindset:

> **Your logs can contain sensitive information, so logs themselves must be protected.**

Think:

```text
Application
    ↓
Logs
    ↓
Storage
    ↓
People / systems accessing logs
```

If logs contain secrets, an attacker who gets log access may get those secrets.

Therefore:

```text
Don't log secrets
+
Restrict log access
+
Protect log storage
```

---

# 23. Error Logging

When an error occurs, you want useful context.

For example:

```json
{
  "level": "error",
  "event": "todo.create.failed",
  "requestId": "abc123",
  "error": {
    "name": "ValidationError",
    "message": "title is required"
  }
}
```

But be careful about what gets returned to the client.

---

# 24. Logs vs API Error Responses

These are different audiences.

### Log

For developers/operators:

```text
database connection timeout
MongoServerError
query details
stack trace
requestId
```

### API response

For the client:

```json
{
  "success": false,
  "message": "Something went wrong.",
  "requestId": "abc123"
}
```

Don't expose internal implementation details to clients.

---

# 25. Stack Traces

For unexpected errors, stack traces are very useful internally.

Example:

```text
Error: Database connection failed
    at ...
    at ...
    at ...
```

This helps locate where the failure originated.

But:

> **Don't send stack traces to production clients.**

Keep them in controlled logs.

---

# 26. Error Handling + Logging

Your centralized error middleware can become the place where unexpected errors are logged.

Conceptually:

```js
function errorMiddleware(err, req, res, next) {
  logger.error({
    event: "request.failed",
    requestId: req.requestId,
    error: err
  });

  res.status(500).json({
    success: false,
    message: "Internal server error",
    requestId: req.requestId
  });
}
```

This gives you:

```text
Internal error
      ↓
Log full details
      ↓
Return safe response
```

---

# 27. Don't Log the Same Error Everywhere

A common problem is duplicate logging.

For example:

```text
Service logs error
     ↓
Controller logs error
     ↓
Middleware logs error
```

One failure creates:

```text
3 identical error logs
```

This creates noise.

A cleaner architecture is to decide where errors are logged.

For unexpected HTTP failures:

```text
Centralized error middleware
```

can often be the final logging point.

---

# 28. Business Events vs Technical Errors

These are different types of logs.

### Business event

```text
order.created
user.registered
todo.completed
```

### Technical event

```text
database.connection.failed
redis.timeout
external_api.failed
```

Separating these concepts makes your logs easier to understand.

---

# 29. Security Events

Security-related events are especially important.

Examples:

```text
login.failed
login.success
rate_limit.exceeded
permission.denied
password_reset.requested
token.invalid
```

These can help detect suspicious behavior.

---

# 30. Failed Login Logs

A failed login might produce:

```json
{
  "level": "warn",
  "event": "auth.login.failed",
  "requestId": "abc123",
  "reason": "invalid_credentials"
}
```

Be careful not to log:

```text
password
full authentication token
```

Also avoid unnecessarily exposing whether a particular account exists, because that can enable account enumeration.

---

# 31. Rate-Limit Logs

From the previous lesson, when a client exceeds the limit:

```text
429
```

you may log:

```json
{
  "level": "warn",
  "event": "rate_limit.exceeded",
  "requestId": "abc123",
  "route": "/api/v1/auth/login"
}
```

This lets your security team see patterns such as:

```text
Thousands of login rate-limit events
```

which could indicate an attack or misbehaving client.

---

# 32. What Should a Log Entry Contain?

A useful structured log often has:

```text
timestamp
level
event
requestId
service
environment
message/context
```

Depending on the event:

```text
userId
route
statusCode
duration
error
```

For example:

```json
{
  "timestamp": "...",
  "level": "info",
  "service": "backend-api",
  "environment": "production",
  "event": "http.request",
  "requestId": "abc123",
  "method": "GET",
  "route": "/api/v1/todos",
  "statusCode": 200,
  "durationMs": 28
}
```

---

# 33. Timestamp

Every production log needs to answer:

> **When did this happen?**

Use a consistent machine-readable timestamp.

For example:

```text
2026-08-27T18:30:00.000Z
```

Using a consistent timezone, commonly UTC, makes distributed systems much easier to debug.

---

# 34. Environment

A log can identify:

```text
development
staging
production
```

For example:

```json
{
  "environment": "production"
}
```

This prevents confusion when multiple environments are sending logs to the same system.

---

# 35. Service Name

As your architecture grows, you may have:

```text
API
Worker
Email service
AI service
Payment service
```

A field such as:

```text
service=backend-api
```

helps identify which component produced the log.

---

# 36. Logging Performance

Logging isn't free.

If you do:

```text
10 million logs
```

you have costs:

```text
CPU
I/O
Storage
Network
Log platform cost
```

So:

> **Log useful information, not everything.**

Especially avoid huge payloads.

---

# 37. Log Sampling

For extremely high-volume events, you may use sampling.

Imagine:

```text
100,000 successful requests
```

You may not need detailed logs for every identical successful request.

But you absolutely want errors.

A system might therefore:

```text
INFO → sample
ERROR → keep
SECURITY → keep
```

The exact strategy depends on your observability requirements.

---

# 38. Log Retention

Logs shouldn't necessarily live forever.

You may define:

```text
Application logs → 30 days
Security logs → longer
Audit records → based on requirements
```

Retention depends on:

```text
Compliance
Security requirements
Storage costs
Business needs
```

---

# 39. Log Rotation

If you're storing logs locally, eventually:

```text
app.log
```

could become:

```text
100 GB
```

Log rotation solves this by creating new files periodically.

Conceptually:

```text
app.log
   ↓
app-2026-08-27.log
app-2026-08-28.log
app-2026-08-29.log
```

In containerized production environments, centralized log collection is often preferred over relying on application-local files.

---

# 40. Centralized Logging

Imagine three servers:

```text
Node A ──┐
Node B ──┼──► Central Log System
Node C ──┘
```

Now you can search all logs in one place.

Without centralized logging:

```text
Server A → logs A
Server B → logs B
Server C → logs C
```

Debugging becomes much harder.

---

# 41. Request Tracing Across Servers

Suppose:

```text
Client
  ↓
Load Balancer
  ↓
API Server
  ↓
Worker
  ↓
Email Provider
```

If you preserve a correlation/request identifier:

```text
requestId=abc123
```

you can connect related events.

This is the beginning of distributed tracing.

# 42. Logging vs Monitoring vs Tracing

These are related but different.

### Logging

Answers:

> What happened?

```text
Database query failed.
```

### Metrics/Monitoring

Answers:

> How often is it happening?

```text
5% of requests are failing.
```

### Tracing

Answers:

> Where did the request spend time?

```text
API → Service → DB → External API
```

Together:

```text
Logs
+
Metrics
+
Traces
=
Observability
```

---

# 43. Logging and Metrics

Suppose logs show:

```text
database timeout
```

Metrics can show:

```text
DB error rate
    ↑
    20%
```

Logs explain individual events.

Metrics show system-wide patterns.

# 44. Logging and Health Checks

Suppose:

```text
/health
```

reports:


Logs can tell you:

```text
when the failure started
```

# 47. A Good Logger Interface

Instead of scattering raw `console.log()` calls everywhere, create a logger abstraction.

For example:

```js
logger.info({
  event: "todo.created",
  todoId
});
```

And:

```js
logger.error({
  event: "todo.create.failed",
  error
});
```

Then your application code doesn't need to care about the underlying logging implementation.

---

# 48. Why a Logger Abstraction Helps

Today:

```text
console / local logger
```

Tomorrow:

```text
centralized log platform
```

Your business code can remain:

```js
logger.info(...)
logger.warn(...)
logger.error(...)
```

This keeps infrastructure concerns separated from business logic.

---

# 49. Event Naming

Consistent event names are useful.

For example:

```text
auth.login.success
auth.login.failed

todo.created
todo.updated
todo.deleted

rate_limit.exceeded

database.connection.failed
database.query.failed
```

Avoid random messages like:

```text
"Something happened"
"Done"
"Oops"
```

Good event names make searching easier.

---

# 50. Logging Example: Successful Request

Conceptually:

```js
logger.info({
  event: "http.request.completed",
  requestId: req.requestId,
  method: req.method,
  route: req.route?.path,
  statusCode: res.statusCode,
  durationMs
});
```

This gives you useful request-level information without dumping the whole request.

---

# 51. Logging Example: Database Error

```js
logger.error({
  event: "database.query.failed",
  requestId: req.requestId,
  error: {
    name: err.name,
    message: err.message
  }
});
```

Depending on your logger, you may also capture a stack trace internally.

---

# 52. Logging Example: Authorization Failure

Suppose a user tries to delete another user's resource.

You might log:

```json
{
  "level": "warn",
  "event": "authorization.denied",
  "requestId": "abc123",
  "resource": "todo"
}
```

Don't necessarily log every piece of sensitive request data.

The goal is to record the security event safely.

---

# 53. Audit Logs Are Different

This is an important distinction.

Application logs:

```text
request completed
database failed
service started
```

Audit logs:

```text
user changed account email
admin deleted user
permissions changed
financial record modified
```

Audit records may have stronger requirements around:

```text
Integrity
Retention
Access control
Who performed the action
What changed
When it changed
```

Don't assume ordinary application logs automatically satisfy audit requirements.

---

# 54. What Not to Log

Avoid sensitive values such as:

```text
❌ passwords
❌ access tokens
❌ refresh tokens
❌ API keys
❌ OTPs
❌ session secrets
❌ encryption keys
```

Also be careful with:

```text
personal data
payment information
private messages
large request bodies
```

Use redaction where appropriate.

---

# 55. Redaction

Suppose a request contains:

```json
{
  "email": "rahul@example.com",
  "password": "secret"
}
```

A logger can transform it into:

```json
{
  "email": "rahul@example.com",
  "password": "[REDACTED]"
}
```

The principle is:

> **Sensitive data should be removed before it reaches the logging system.**

---

# 56. Logging and Privacy

Logs can become a privacy problem if you collect unnecessary personal information.

Ask:

```text
Do I need this field?
How long should I retain it?
Who can access it?
Can I anonymize it?
```

A good production engineer treats logs as part of the application's data architecture.

```text
request.received
```
```text
      ↓

      ↓
```

# 64. The Golden Rule

Don't ask:

> "What can I log?"

Ask:

> **"What information will help me understand or investigate this event later?"**

This produces much better logs.

```text
              ┌─────┴─────┐
              ▼           ▼
           Search      Monitoring
```

And remember:

> **Logs tell you what happened; metrics tell you how often; traces tell you where time was spent.**

# 🔥 Five Rules to Memorize

### Rule 1

**Use structured logging in production.**

```json
{
  "level": "info",
  "event": "todo.created"
}
```

is better than:

```text
Todo created!
```

### Rule 2

**Use a request/correlation ID.**

It lets you follow one request through multiple layers.

### Rule 3

**Never log secrets.**

Especially:

```text
passwords
tokens
API keys
OTP
```

### Rule 4

**Separate logs from client-facing errors.**

```text
Internal log
→ detailed

API response
→ safe and simple
```

### Rule 5

**Logging is part of observability, not just debugging.**

```text
Logs
+
Metrics
+
Traces
=
Observability
```
