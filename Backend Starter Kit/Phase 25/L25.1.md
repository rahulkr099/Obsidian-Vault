# Lesson 25.1 — Create the Project

Welcome to **Phase 25**. This is where we stop learning individual backend pieces and rebuild the complete starter **from an empty directory**.

Your first task is intentionally simple:

> **Create a completely empty backend project and initialize it correctly.**

The important part is understanding **what each command does and why we're doing it**.

---

## 1. What are we building?

Eventually, our project will look roughly like this:

```text
mern-backend-starter/
│
├── config/
├── constants/
├── controllers/
├── docs/
├── mail/
├── middlewares/
├── models/
├── repositories/
├── routes/
├── services/
├── tests/
├── utils/
├── validations/
│
├── .env
├── .env.example
├── .gitignore
├── app.js
├── server.js
├── package.json
└── package-lock.json
```

But **not yet**.

Today we're starting with:

```text
mern-backend-starter/
```

and nothing else.

---

# 2. Why start completely empty?

Because copying the starter gives you this problem:

```text
"I know what the files are,
but I don't know why they exist."
```

We want:

```text
Empty folder
     ↓
Understand requirement
     ↓
Create something
     ↓
Understand why
     ↓
Test it
     ↓
Continue
```

By the end of Phase 25, you'll have built the architecture rather than memorized it.

---

# 3. Choose the project location

Go somewhere where you keep your development projects.

For example:

```bash
cd ~/Projects
```

If that directory doesn't exist:

```bash
mkdir -p ~/Projects
cd ~/Projects
```

Now check where you are:

```bash
pwd
```

You might see:

```text
/home/rahul/Projects
```

The exact path doesn't matter.

---

# 4. Create the project directory

Run:

```bash
mkdir mern-backend-starter
```

Then enter it:

```bash
cd mern-backend-starter
```

Check:

```bash
pwd
```

And:

```bash
ls -la
```

At this point, the directory should essentially be empty.

You may see:

```text
.
..
```

That's exactly what we want.

---

# 5. Why `mkdir`?

This command:

```bash
mkdir mern-backend-starter
```

means:

```text
mkdir
  ↓
make directory
```

So we're simply creating the physical directory that will contain our backend.

Nothing Node-specific has happened yet.

Nothing Express-specific has happened yet.

We just created a project workspace.

---

# 6. Initialize Git

Now run:

```bash
git init
```

You should see something similar to:

```text
Initialized empty Git repository in ...
```

Check:

```bash
git status
```

You should get something similar to:

```text
On branch main

No commits yet
```

Depending on your Git configuration, the initial branch may be named `master` instead of `main`. That's okay for now.

---

# 7. Why initialize Git this early?

Because Git should track the project **from the beginning**, not after you've already written hundreds of files.

Our development history will eventually look something like:

```text
Project created
     ↓
Node configured
     ↓
Express configured
     ↓
Database added
     ↓
Middleware added
     ↓
Authentication added
     ↓
Testing added
     ↓
Docker added
     ↓
Production-ready starter
```

Each major milestone can become a commit.

For example:

```bash
git add .
git commit -m "chore: initialize backend project"
```

But **don't make that commit yet**.

We'll make it after the initial Node setup.

---

# 8. Initialize the Node project

Now run:

```bash
npm init -y
```

This is our first Node-specific command.

Check the directory:

```bash
ls
```

You should now have:

```text
package.json
```

---

# 9. What did `npm init -y` actually do?

It created:

```text
package.json
```

This file describes our Node project.

Open it:

```bash
cat package.json
```

You'll see something similar to:

```json
{
  "name": "mern-backend-starter",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}
```

The exact contents can vary slightly depending on your npm version.

---

# 10. What is `package.json`?

Think of it as the **identity and configuration file of your Node project**.

It will eventually tell Node/npm things like:

```text
What is this project called?
What version is it?
What dependencies does it need?
How do I start it?
How do I run tests?
Is this project using ES modules?
```

Eventually we'll have something more like:

```json
{
  "name": "mern-backend-starter",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "dev": "nodemon server.js",
    "start": "node server.js",
    "test": "jest"
  }
}
```

But **don't modify all of that yet**.

We'll build it step by step.

---

# 11. Why `-y`?

Normally:

```bash
npm init
```

asks questions:

```text
package name:
version:
description:
entry point:
test command:
git repository:
keywords:
author:
license:
```

The:

```bash
-y
```

means:

> Accept the default answers.

So:

```bash
npm init -y
```

is simply a faster way to initialize the project.

Run:


Git knows that `package.json` exists but isn't tracking it yet.

We'll eventually do:


```text
.gitignore
```

That's coming shortly.

# 14. The architecture principle

There is a useful distinction here:

### Project initialization

```text
mkdir
git init
npm init
```

is about creating the **workspace**.

### Application architecture

```text
routes
controllers
services
repositories
models
```

is about creating the **application**.

Don't mix these concepts.

We're currently at:

```text
                    PROJECT
                       │
              ┌────────┴────────┐
              │                 │
             Git               Node
              │                 │
           version           package.json
           control
```

Later:

```text
                 APPLICATION
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
      Routes      Middleware     Controllers
                                      │
                                      ▼
                                   Services
                                      │
                                      ▼
                                 Repositories
                                      │
                                      ▼
                                    Models
                                      │
                                      ▼
                                  MongoDB
```

This distinction will help you understand the entire starter.

---

# 15. Don't create `backend/` inside another backend

In the earlier architecture roadmap, we sometimes used:

```text
my-project/
└── backend/
```

That's useful when your MERN project also contains:

```text
frontend/
backend/
```

But in **Phase 25**, we're specifically rebuilding the backend starter itself.

So for this phase, use:

```text
mern-backend-starter/
```

as the project root.

Later, if you use it inside a full MERN application:

```text
my-mern-app/
│
├── frontend/
└── backend/
```

you can place this backend architecture inside `backend/`.

# 17. One important habit

Whenever you're building a backend, don't blindly run commands from a tutorial.

After each command, ask:

> **What changed?**

For example:

```bash
mkdir mern-backend-starter
```

Changed:

```text
Nothing inside the project yet.
Created workspace.
```

Then:

```bash
git init
```

Changed:

```text
Created .git/
```

Then:

```bash
npm init -y
```

Changed:

```text
Created package.json
```

This habit will make you much better at debugging.

# 18. Your checkpoint

At the end of Lesson 25.1, you should have:

```text
mern-backend-starter/
│
├── .git/
│
└── package.json
```

And you should understand:

- `mkdir` creates the project directory.
    
- `git init` creates the Git repository.
    
- `npm init -y` creates `package.json`.
    
- `package.json` describes the Node project.
    
- We are deliberately **not** creating the application architecture yet.
