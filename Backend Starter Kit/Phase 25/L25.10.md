# Lesson 25.10 — Error Architecture

This lesson is important because your starter architecture has three pieces specifically for errors:

```text
utils/AppError.js
utils/asyncHandler.js
middlewares/error.middleware.js
```

The intended flow from your roadmap is:

```text
Controller
   ↓
throws error
   ↓
asyncHandler
   ↓
Express error middleware
   ↓
standard JSON response
```

The goal is to stop writing this everywhere:

```js
try {
    // ...
} catch (error) {
    // format response
}
```

Instead, errors should flow into **one central place**.

---

# 1. Why do we need error architecture?

Imagine we have:

```text
POST /api/v1/auth/signup
POST /api/v1/auth/login
GET  /api/v1/users/me
POST /api/v1/todos
PATCH /api/v1/todos/:id
DELETE /api/v1/todos/:id
```

Every endpoint can fail.

For example:

```text
User already exists
Invalid password
User not found
Invalid token
Database failure
Validation failure
Unauthorized
Forbidden
```

Without centralized handling, you might end up with:

```js
// controller 1
try {
   ...
} catch (error) {
   res.status(...).json(...);
}

// controller 2
try {
   ...
} catch (error) {
   res.status(...).json(...);
}

// controller 3
try {
   ...
} catch (error) {
   res.status(...).json(...);
}
```

That's repetitive and difficult to maintain.

---

# 2. The architecture we want

Instead:

```text
                Controller
                    │
                    ▼
              something fails
                    │
                    ▼
                 Error
                    │
                    ▼
              asyncHandler
                    │
                    ▼
               next(error)
                    │
                    ▼
          error.middleware.js
                    │
                    ▼
             JSON response
```

So the controller doesn't need to know how errors are formatted.

---

# 3. First understand Express error middleware

Normal middleware:

```js
(req, res, next)
```

Error middleware:

```js
(err, req, res, next)
```

That **fourth-argument signature** is how Express identifies error-handling middleware.

Example:

```js
const errorHandler = (err, req, res, next) => {
    console.error(err);

    res.status(500).json({
        success: false,
        message: "Internal server error",
    });
};
```

The important difference:

```text
Normal
(req, res, next)

Error
(err, req, res, next)
```

---

# 4. How does an error reach it?

Suppose a route does:

```js
app.get("/test", (req, res, next) => {
    const error = new Error("Something failed");

    next(error);
});
```

Notice:

```js
next(error);
```

instead of:

```js
next();
```

This tells Express:

> Something went wrong. Enter the error-handling pipeline.

Flow:

```text
/test
  ↓
route
  ↓
next(error)
  ↓
error middleware
  ↓
response
```

# 5. Add a temporary error handler

Before creating our reusable architecture, let's understand it directly.

In `app.js`:

```js
app.get("/test-error", (req, res, next) => {
    const error = new Error("Something went wrong");

    next(error);
});

app.use((err, req, res, next) => {
    res.status(500).json({
        success: false,
        message: err.message,
    });
});
```

Now:

```bash
curl http://localhost:5000/test-error
```

returns:

```json
{
  "success": false,
  "message": "Something went wrong"
}
```

You've just built your first centralized error flow.

# 6. But this isn't our final architecture

We don't want this giant function inside `app.js`.

Remember:

> `app.js` should compose the application, not contain every implementation.

So we'll move the error handler into:

```text
middlewares/error.middleware.js
```

And we'll create:

```text
utils/
├── AppError.js
└── asyncHandler.js
```

# 7. Create `AppError`

Create:

```text
utils/AppError.js
```

The purpose is to create **expected application errors** with useful information.

For example:

```js
new AppError("User not found", 404);
```

Instead of a generic:

```js
new Error("User not found");
```

we can attach:

```text
message
statusCode
operational status
```

---

# 8. Implement `AppError`

Create:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}

export default AppError;
```

Let's break this down carefully.

---

# 9. `extends Error`

```js
class AppError extends Error {
```

JavaScript already has a built-in:

```js
Error
```

We're creating our own specialized error.

So:

```text
Error
  ↑
  │
AppError
```

This means `AppError` behaves like a normal JavaScript error but carries extra information.

---

# 10. The constructor

```js
constructor(message, statusCode) {
```

We'll create errors like:

```js
new AppError("User not found", 404);
```

So:

```text
message
   ↓
"User not found"

statusCode
   ↓
404
```

---

# 11. Call the parent constructor

```js
super(message);
```

This passes the message to JavaScript's built-in `Error`.

So:

```js
error.message
```

becomes:

```text
User not found
```

---

# 12. Store the HTTP status

```js
this.statusCode = statusCode;
```

Now:

```js
error.statusCode
```

is:

```text
404
```

The error middleware can then use:

```js
res.status(err.statusCode)
```

---

# 13. What is `isOperational`?

We add:

```js
this.isOperational = true;
```

This gives us a way to distinguish **expected application errors** from unexpected programming/system failures.

For example:

### Operational error

```text
User doesn't exist
```

That's an expected condition.

### Programming error

```text
Cannot read properties of undefined
```

That's probably a bug.

This distinction becomes useful later when deciding how much information to expose to clients and how aggressively to log errors.

Your roadmap explicitly includes operational vs programming errors as part of the error architecture.

---

# 14. Why `captureStackTrace`?

```js
Error.captureStackTrace(this, this.constructor);
```

This gives us a useful stack trace while hiding the constructor itself from the stack.

For example, an error might eventually show:

```text
AppError: User not found
    at userService.js:42
    at ...
```

This is extremely useful during debugging.

---

Temporarily:

```js
import AppError from "./utils/AppError.js";

const error = new AppError("User not found", 404);

console.log(error.message);
console.log(error.statusCode);
console.log(error.isOperational);
```

You should get:

```text
User not found
404
true
```

Now you have a custom application error.

# 16. Create `asyncHandler`

Now comes another important problem.

Consider:

```js
app.get("/users", async (req, res) => {
    const users = await getUsers();

    res.json(users);
});
```

What happens if:

```js
getUsers()
```

rejects?

We need that error to reach Express's error middleware.

That's where `asyncHandler` comes in.

Create:

```text
utils/asyncHandler.js
```

---

# 17. Basic `asyncHandler`

```js
const asyncHandler = (fn) => {
    return (req, res, next) => {
        Promise.resolve(fn(req, res, next)).catch(next);
    };
};

export default asyncHandler;
```

This small function is extremely useful.

Let's understand it slowly.

---

# 18. What does `fn` represent?

Suppose we write:

```js
const getUsers = asyncHandler(async (req, res) => {
    // ...
});
```

Then:

```text
fn
↓
async (req, res) => {
    ...
}
```

So `asyncHandler` receives your controller function.

---

# 19. Why `Promise.resolve()`?

```js
Promise.resolve(
    fn(req, res, next)
)
```

takes whatever the function returns and treats it as a promise.

Then:

```js
.catch(next)
```

means:

> If the promise rejects, pass the error to Express.

So:

```text
async controller
      ↓
Promise rejection
      ↓
.catch(next)
      ↓
next(error)
      ↓
error middleware
```

---

# 20. The beautiful part

Without `asyncHandler`:

```js
app.get("/users", async (req, res, next) => {
    try {
        const users = await getUsers();

        res.json(users);
    } catch (error) {
        next(error);
    }
});
```

With `asyncHandler`:

```js
app.get(
    "/users",
    asyncHandler(async (req, res) => {
        const users = await getUsers();

        res.json(users);
    })
);
```

Much cleaner.

---

# 21. Why not put `try/catch` everywhere?

Because the `try/catch` doesn't usually add business value.

This:

```js
try {
    const user = await userService.getUser(id);
} catch (error) {
    next(error);
}
```

is basically saying:

> Catch this error and send it to the exact same central error handler.

If every controller does this, it's repetitive.

`asyncHandler` removes that repetition.

---

# 22. Create the error middleware

Now create:

```text
middlewares/error.middleware.js
```

Start with:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message: err.message || "Internal server error",
    });
};

export default errorMiddleware;
```

This is our central error formatter.

---

# 23. Understand the fallback

```js
const statusCode = err.statusCode || 500;
```

If we have:

```js
new AppError("User not found", 404)
```

then:

```text
statusCode = 404
```

But if we have:

```js
new Error("Database exploded")
```

there may be no `statusCode`.

Then:

```text
statusCode = 500
```

That's important.

Unknown errors should not accidentally become:

```text
200 OK
```

or some random status.

---

# 24. Standard response

Our error middleware returns:

```json
{
  "success": false,
  "message": "User not found"
}
```

This creates a consistent API contract.

Instead of one endpoint returning:

```json
{
  "error": "User not found"
}
```

and another:

```json
{
  "message": "No user"
}
```

we have one centralized format.

Later, our API response architecture can make this even more structured.

---

# 25. Connect it to `app.js`

Import:

```js
import errorMiddleware from "./middlewares/error.middleware.js";
```

Then place it **after your routes**:

```js
app.get("/test-error", (req, res, next) => {
    next(new AppError("Something went wrong", 400));
});

app.use(errorMiddleware);
```

The important ordering is:

```text
routes
   ↓
404 handler
   ↓
error handler
```

Error middleware belongs near the end of the pipeline.

# 29. Important distinction: synchronous vs asynchronous errors

Consider:

```js
app.get("/test", (req, res) => {
    throw new Error("Failure");
});
```

This is synchronous.

Express can handle it naturally.

But:

```js
app.get("/test", async (req, res) => {
    await somethingThatFails();
});
```

involves asynchronous promise rejection.

That's why our architecture uses:

```text
asyncHandler
```

to consistently forward async errors.

Your broader error-handling curriculum explicitly separates synchronous errors, asynchronous errors, Promise rejection, and `asyncHandler`.

---

# 30. Operational vs programming errors

This distinction is worth remembering.

### Operational error

Something expected can go wrong.

Examples:

```text
User not found
Invalid credentials
Email already exists
Resource not found
Permission denied
```

These can safely become client-facing responses.

For example:

```json
{
  "success": false,
  "message": "User not found"
}
```

---

### Programming error

Something unexpected happened.

For example:

```js
const user = undefined;

console.log(user.email);
```

Result:

```text
Cannot read properties of undefined
```

You don't necessarily want to expose internal details to the client.

Instead:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

while the actual error gets logged internally.

---

# 31. Never leak internal errors

Imagine MongoDB throws:

```text
MongoServerError:
E11000 duplicate key error collection...
```

You probably don't want to expose the entire internal database error to a client.

Instead, the client should receive something meaningful:

```json
{
  "success": false,
  "message": "Email already exists"
}
```

while logs contain the detailed technical information.

This is especially important in production.

---

# 32. Development vs production

During development, you may want:

```json
{
  "success": false,
  "message": "Cannot read properties of undefined",
  "stack": "..."
}
```

because you're debugging.

In production:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

The stack trace should stay on the server.

So our environment configuration matters here:

```text
NODE_ENV=development
```

versus:

```text
NODE_ENV=production
```

We'll improve this behavior later.

---

# 33. Add development stack information carefully

A more complete error middleware could eventually do:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    const response = {
        success: false,
        message: err.isOperational
            ? err.message
            : "Internal server error",
    };

    if (process.env.NODE_ENV === "development") {
        response.stack = err.stack;
    }

    res.status(statusCode).json(response);
};
```

But because we've already created centralized configuration, prefer using:

```js
env.nodeEnv
```

instead of accessing `process.env` directly.

---

# 34. Better `error.middleware.js`

Use:

```js
import env from "../config/env.js";

const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    const response = {
        success: false,
        message: err.isOperational
            ? err.message
            : "Internal server error",
    };

    if (env.nodeEnv === "development") {
        response.stack = err.stack;
    }

    res.status(statusCode).json(response);
};

export default errorMiddleware;
```

This gives us a safer production default.

# 35. Request IDs + errors

Remember our request ID middleware?

```js
req.id
```

Now error handling can use it.

Suppose:

```text
Request ID:
8c5f...
```

and something fails.

The error log can say:

```text
requestId=8c5f...
error="Database timeout"
```

The client could receive:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "8c5f..."
}
```

Then the user can report:

> Request `8c5f...` failed.

And you can find that exact request in your logs.

This connects the error architecture directly with the observability architecture in your roadmap.

---

# 36. Add request ID to errors

Update:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    const response = {
        success: false,
        message: err.isOperational
            ? err.message
            : "Internal server error",
        requestId: req.id,
    };

    if (env.nodeEnv === "development") {
        response.stack = err.stack;
    }

    res.status(statusCode).json(response);
};
```

Now your error response is traceable.

---

# 37. Don't expose too much

Avoid doing this in production:

```js
res.json({
    error: err
});
```

Why?

An error object may contain:

```text
stack traces
database information
internal file paths
implementation details
```

Instead, explicitly choose what the client gets:

```js
{
    success: false,
    message: "...",
    requestId: "..."
}
```

This is a much safer API boundary.

# 41. One subtle rule: don't call `next()` after sending a response

Avoid:

```js
res.status(404).json({
    success: false,
    message: "Not found",
});

next();
```

Once you've sent the response, the request should normally stop.

Think:

```text
Response sent
    ↓
STOP
```

Calling `next()` afterward can cause confusing behavior or:

```text
Cannot set headers after they are sent
```

---

# 42. Another common mistake

Don't do:

```js
const errorHandler = (err, req, res, next) => {
    res.status(500).json(...);

    next(err);
};
```

You've already handled the response.

Usually:

```js
res.status(...).json(...);
```

is the end of that error-handling path.

---

# 43. Another common mistake

Don't put your error middleware at the beginning:

```js
app.use(errorMiddleware);

app.use(routes);
```

Instead:

```text
routes
   ↓
404
   ↓
error handler
```

The error handler belongs at the end of the pipeline.

---

# 44. What belongs in `AppError`?

Keep it focused.

Good:

```text
message
statusCode
isOperational
stack
```

Don't turn `AppError` into:

```text
database manager
logger
email sender
response formatter
authentication system
```

Its job is simply to represent an application error.

---

# 45. What belongs in `asyncHandler`?

Only one job:

> Forward asynchronous controller errors to Express.

Don't put:

```text
logging
authentication
validation
database logic
response formatting
```

inside it.

Keep utilities focused.

---

# 46. What belongs in `error.middleware`?

Its main responsibility:

```text
Error
 ↓
log/observe
 ↓
classify
 ↓
choose status
 ↓
choose safe message
 ↓
send response
```

This is the central error boundary of your HTTP application.

And the three files have very clear jobs:

```text
AppError
   ↓
Represents an application error

asyncHandler
   ↓
Forwards async errors

error.middleware
   ↓
Turns errors into HTTP responses
```

This matches the starter architecture you are rebuilding from scratch: `AppError`, `asyncHandler`, and the global error middleware are deliberately separate responsibilities.
