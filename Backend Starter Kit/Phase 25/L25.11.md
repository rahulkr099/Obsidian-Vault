# Lesson 25.11 — Validation Architecture

This lesson is the bridge between **untrusted HTTP input** and your **application logic**.

Your roadmap explicitly places validation before security and defines the target architecture as:

```text
req.body
   ↓
validate()
   ↓
clean data
   ↓
controller
```

It also specifies that the starter should eventually contain:

```text
validations/auth.validation.js
middlewares/security/validate.middleware.js
```

So today we're going to build the idea from zero instead of treating validation middleware as magic.

---

# 1. What is validation?

Validation means:

> **Checking whether incoming data has the shape and values your application expects.**

Suppose your API has:

```http
POST /api/v1/auth/signup
```

and expects:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123"
}
```

A client could instead send:

```json
{
  "name": 123,
  "email": "hello",
  "password": ""
}
```

Your backend should **not blindly trust it**.

The boundary should be:

```text
Internet
   │
   ▼
Untrusted request
   │
   ▼
Validation
   │
   ├── Invalid → reject
   │
   └── Valid
        │
        ▼
    Application
```

---

# 2. Why backend validation is necessary

You might think:

> "But React already validates the form."

Yes.

But frontend validation is for **user experience**.

Backend validation is for **correctness and security**.

A malicious user can completely bypass your React application:

```text
React
  ↓
❌ bypassed
  ↓
curl
  ↓
Postman
  ↓
custom script
  ↓
your API
```

Therefore:

> **The backend must validate its own input.**

Your roadmap calls this a **trust boundary**.

---

# 3. Client validation vs server validation

Think of two checkpoints.

### Frontend

```text
User
 ↓
React form
 ↓
Validation
 ↓
API
```

This improves UX.

### Backend

```text
Internet
 ↓
API
 ↓
Validation
 ↓
Business logic
```

This protects the application.

You need both.

---

# 4. The trust boundary

This is one of the most important concepts in backend development.

Everything coming from:

```text
req.body
req.params
req.query
req.headers
cookies
```

should initially be considered:

> **Untrusted input.**

For example:

```js
req.body.email
```

is not automatically a valid email.

It's simply a value someone sent to your server.

So:

```text
req.body
   ↓
UNTRUSTED
   ↓
validation
   ↓
TRUSTED/EXPECTED SHAPE
```

Technically, even validated data should still be treated carefully, but validation establishes the assumptions your application is allowed to make.

# 5. Three common input locations

A backend receives input from several places.

## Body

```http
POST /users
```

```json
{
  "name": "Rahul"
}
```

Accessed with:

```js
req.body
```

---

## URL parameters

```http
GET /users/123
```

Accessed with:

```js
req.params.id
```

---

## Query parameters

```http
GET /users?page=2&limit=20
```

Accessed with:

```js
req.query.page
req.query.limit
```

So our validation architecture must eventually support all three:

```text
req.body
req.params
req.query
```

The roadmap explicitly includes body, query, and URL parameter validation.

---

# 6. What happens without validation?

Imagine:

```js
const createUser = async (req, res) => {
    const { email, age } = req.body;

    await userService.create({
        email,
        age,
    });
};
```

What's wrong?

We don't know:

```text
Is email a string?
Is email actually an email?
Is age a number?
Is age positive?
Are extra fields present?
Are required fields missing?
```

We're trusting the client.

That's dangerous.

---

# 7. Don't put validation inside controllers

You could write:

```js
const createUser = async (req, res) => {
    if (!req.body.email) {
        return res.status(400).json(...);
    }

    if (!req.body.password) {
        return res.status(400).json(...);
    }

    // ...
};
```

But now your controller is doing:

```text
HTTP handling
+
validation
+
business logic
```

It becomes harder to maintain.

Instead:

```text
Request
   ↓
Validation middleware
   ↓
Controller
```

This is the architecture we're building.

---

# 8. Our validation pipeline

The final idea is:

```text
POST /users
      │
      ▼
Route
      │
      ▼
validate(schema)
      │
      ├──── invalid ────► error middleware
      │
      ▼
validated request
      │
      ▼
Controller
      │
      ▼
Service
```

This means the controller can focus on its actual job.

# 10. What is Joi?

Joi lets you describe what valid data should look like.

For example:

```js
const schema = Joi.object({
    email: Joi.string().email().required(),
});
```

You're saying:

```text
email
 ↓
must be a string
 ↓
must have email format
 ↓
must exist
```

Think of the schema as a **contract**.

```js
    .max(128)
```

Meaning:

```text

   ↓

   ↓

   ↓

   ↓

```

# 17. Validation is not sanitization

This distinction is very important.

### Validation

Asks:

> Is this input acceptable?

Example:

```text
Is this a valid email?
```

### Sanitization / normalization

Asks:

> Can we safely transform this input into a cleaner form?

Example:

```text
" Rahul@example.com "
       ↓
"rahul@example.com"
```

These are related but different jobs.

Your roadmap explicitly separates **validation vs sanitization** and **normalizing input**.


This assumes:

```text

```

is already valid.

Instead:

```text

   ↓

   ↓
validated input
   ↓
service
```

Now the service can work with clearer assumptions.

# 19. Build `validate.middleware.js`

Create:

```text
middlewares/security/validate.middleware.js
```

First create the directory:

```bash
mkdir -p middlewares/security
```

Then:

```bash
touch middlewares/security/validate.middleware.js
```

Start with:

```js
const validate = (schema) => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req.body);

        if (error) {
            return next(error);
        }

        req.body = value;

        next();
    };
};

export default validate;
```

This is our first reusable validation middleware.

---

# 20. Why is `validate` a function?

Notice:

```js
validate(schema)
```

rather than:

```js
validate()
```

This makes it a **middleware factory**.

For example:

```js
validate(signupSchema)
```

means:

> Create middleware specifically for the signup schema.

Another route can use:

```js
validate(loginSchema)
```

Same middleware.

Different schema.

---

# 21. Middleware factory mental model

Think:

```text
signupSchema
      │
      ▼
validate(signupSchema)
      │
      ▼
signup validation middleware
```

and:

```text
loginSchema
      │
      ▼
validate(loginSchema)
      │
      ▼
login validation middleware
```

So:

```js
validate(schema)
```

creates a middleware function.

---

# 22. What does `schema.validate()` do?

This line:

```js
const { error, value } = schema.validate(req.body);
```

asks Joi:

> Check this request body against my schema.

Joi gives us two important pieces:

```text
error
value
```

### `error`

Contains validation failure information.

### `value`

Contains the validated/processed value.

So:

```text
req.body
   ↓
schema.validate()
   ↓
┌───────────────┐
│ error | value │
└───────────────┘
```

Our two lessons now connect:

```text
        │
        ▼

        ▼

```

# 25. What about `value`?

Joi can return a processed value.

So:

```js
req.body = value;
```

means:

> Replace the original request body with the validated value.

This becomes particularly useful when we configure:

```text
unknown fields
conversion
trimming
normalization
```

later.

---

# 26. But be careful with mutation

This:

```js
req.body = value;
```

is convenient.

But conceptually, we're doing:

```text
untrusted input
      ↓
validated/processed input
      ↓
replace request body
```

This should be a deliberate decision.

You could instead attach it separately:

```js
req.validatedBody = value;
```

Then:

```js
req.validatedBody
```

is clearly different from:

```js
req.body
```

Which approach is better depends on the API architecture.

For our starter, we'll keep the simpler pattern of replacing the body after validation, while making the behavior explicit.

# 30. Query validation

Validation isn't only for `req.body`.

Suppose:

```http
GET /todos?page=2&limit=20
```

We can define:

```js
const paginationSchema = Joi.object({
    page: Joi.number()
        .integer()
        .min(1)
        .default(1),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(20),
});
```

But our current middleware validates:

```js
req.body
```

So we need to make the middleware more reusable.

---

# 31. Better validation middleware

Instead of hardcoding:

```js
schema.validate(req.body)
```

we can let the caller specify the source.

For example:

```js
validate(signupSchema, "body")
```

or:

```js
validate(paginationSchema, "query")
```

or:

```js
validate(todoParamsSchema, "params")
```

Create:

```js
const validate = (schema, source = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[source]);

        if (error) {
            return next(error);
        }

        req[source] = value;

        next();
    };
};

export default validate;
```

Now the middleware is reusable across all request input locations.

Suppose we have:

```text

```

The route could eventually be:

```js
router.post(
```

```text
Request
   ↓

   ↓

   ↓

```

# 35. Validation and authorization are different

Don't confuse:

### Validation

```text
Is this request structurally valid?
```

### Authentication

```text
Who is this?
```

### Authorization

```text
Are they allowed to do this?
```

Example:

```text
POST /todos
   ↓
Authentication
"Who are you?"
   ↓
Validation
"Is this todo data valid?"
   ↓
Authorization/business rules
"Can you create this?"
   ↓
Controller
```

These are separate concerns.

---

# 36. Validation and database constraints are also different

Suppose:

```js
email: Joi.string().email().required()
```

This checks:

> Does the value look like an email?

It does **not** necessarily guarantee:

> Is this email unique in MongoDB?

That is a business/database concern.

So:

```text
Validation
   ↓
"Is this structurally acceptable?"

Service/repository/database
   ↓
"Does this operation satisfy application constraints?"
```

For example:

```text
email format → validation

email already exists → service/repository/database
```

# 37. Unknown fields

Suppose your schema accepts:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

but someone sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

Should the backend accept:

```text
role = admin
```

automatically?

Absolutely not.

This is where **whitelisting** becomes important.

Your roadmap specifically includes:

```text
9.16 Whitelisting fields
9.17 Stripping unknown fields
```

---

# 38. Why unknown fields can be dangerous

Imagine a User schema:

```text
name
email
password
role
```

Your public signup API should probably allow:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "..."
}
```

A malicious client might send:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "...",
  "role": "admin"
}
```

If your application blindly passes everything to the database, you could create an authorization problem.

This is one reason validation should define the **allowed input surface**.

---

# 39. Whitelisting mental model

Think:

```text
Client sends 10 fields
        ↓
Schema allows 3
        ↓
Only expected fields continue
```

So:

```text
Input
 ↓
Allowed fields
 ↓
Application
```

rather than:

```text
Input
 ↓
Database
```

---

# 40. Don't confuse this with authorization

Suppose the client sends:

```json
{
  "role": "admin"
}
```

There are two separate questions:

### Validation

> Is `role` even accepted as part of this request?

### Authorization

> Is this user allowed to choose their role?

For public signup, the answer to the first might simply be:

```text
No.
```

The second doesn't even need to run.

That's a strong design.

# 41. Normalization

Validation can also be combined with controlled normalization.

For example, an email might arrive as:

```text
"  Rahul@Example.COM  "
```

You may want:

```text
"rahul@example.com"
```

But be careful:

> Don't blindly transform every piece of user input.

Normalization rules should be deliberate.

The roadmap treats normalization as a separate topic for this reason.

# 42. Validation error formatting

Joi can produce detailed validation errors.

For example:

```text
"email" must be a valid email
```

or:

```text
"password" is required
```

But we don't want every route formatting these errors differently.

Remember our architecture:

```text
Validation
   ↓
next(error)
   ↓
Global error middleware
```

Eventually our error middleware can recognize validation errors and convert them into a consistent API format.

For example:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    {
      "field": "email",
      "message": "Invalid email"
    }
  ]
}
```

We'll improve this as the starter grows.

---

# 43. Why not return validation errors directly?

You might write:

```js
if (error) {
    return res.status(400).json({
        success: false,
        message: error.message,
    });
}
```

That works.

But then validation middleware owns HTTP error formatting.

Our architecture is cleaner if:

```text
Validation middleware
        ↓
detects error
        ↓
next(error)
        ↓
global error middleware
        ↓
formats response
```

This keeps one central error boundary.

# 51. Common mistakes

## ❌ Mistake 1 — Only validating on frontend

```text
React validation
   ↓
MongoDB
```

Never rely on this.

---

## ❌ Mistake 2 — Validating inside every controller

```js
if (!req.body.email) ...
if (!req.body.password) ...
```

This creates repetitive controllers.

---

## ❌ Mistake 3 — Sending `req.body` directly to MongoDB

```js
User.create(req.body);
```

This is dangerous when the request has fields the application didn't intend to accept.

## ❌ Mistake 4 — Treating validation as authentication

# 57. What you should remember

If you remember only **five things** from this lesson, remember these:

### ① Client input is untrusted

```text
req.body
req.params
req.query
```

all come from outside.

### ② Validate at the boundary

```text
Request
 ↓
Validation
 ↓
Application
```

### ③ Use schemas

```js
signupSchema
loginSchema
todoSchema
paginationSchema
```

### ④ Keep validation separate from business logic

```text
Validation → Is the data acceptable?

Service → What should the application do?

Authorization → Is this user allowed?
```

### ⑤ Reuse the global error architecture

```text
Validation fails
      ↓
next(error)
      ↓
error.middleware
      ↓
consistent response
```
