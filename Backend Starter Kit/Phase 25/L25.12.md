# Lesson 25.12 — Security Architecture

We now reach one of the most important lessons in Phase 25.

Your Phase 25 roadmap explicitly defines **25.12 Security Architecture** as the step immediately after validation and before building the User model.

The important thing is that we're **not** going to treat security as a random collection of packages such as Helmet, CORS, rate limiting, and sanitization.

We'll understand **why each security layer exists and where it belongs**.

---

# 1. What does "security architecture" mean?

Security architecture means:

> Designing the backend so that requests are checked, restricted, and processed safely from the moment they enter the application.

Think about the request pipeline:

```text
Internet
   ↓
HTTP Request
   ↓
Security
   ↓
Validation
   ↓
Authentication
   ↓
Authorization
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Security is therefore **not one middleware**.

It's a collection of protections around the application.

Your roadmap describes the overall architecture as:

```text
Security
Validation
Error Handling
Logging
Configuration
Testing
```

around the core request flow.

---

# 2. Security is not just authentication

This is one of the biggest beginner mistakes.

Many developers think:

```text
Security = JWT
```

That's wrong.

A secure backend needs to think about:

```text
CORS
HTTP headers
Rate limiting
Input sanitization
Injection
Authentication
Authorization
Cookies
Tokens
Secrets
Database access
Logging
Errors
Dependencies
```

Your earlier security phase covers these concerns separately, and Phase 22 later tests attacks such as broken authentication, IDOR, mass assignment, injection, JWT attacks, cookie attacks, CORS attacks, and sensitive-data exposure.

# 3. The security mindset

Before writing any security code, adopt this rule:

> **Never trust the client.**

The client can be:

```text
React application
Postman
curl
mobile app
browser extension
custom script
attacker
```

Your backend cannot know whether the request came from your React application.

Therefore:

```text
Client says:
"I am admin."

Backend:
"Prove it."
```

# 5. Security vs validation

We just learned validation.

Validation asks:

> "Is this data in the expected shape?"

Security asks:

> "Can this request safely interact with my application?"

For example:

```json
{
  "email": "rahul@example.com"
}
```

might be perfectly valid.

But the request might still be:

```text
unauthenticated
```

or:

```text
rate limited
```

or:

```text
from an unauthorized origin
```

So:

```text
Valid input ≠ authorized request
```

---

# 6. Security vs authentication

Authentication asks:

> **Who are you?**

Example:

```text
JWT
 ↓
userId = 123
 ↓
User identified
```

Security is broader.

```text
Security
├── CORS
├── headers
├── rate limiting
├── sanitization
├── authentication
├── authorization
├── secrets
└── data protection
```

Authentication is only one branch.

---

# 7. Security vs authorization

Authorization asks:

> **Are you allowed to perform this action?**

Imagine:

```text
Rahul
 ↓
authenticated
 ↓
userId = 123
```

He tries:

```http
DELETE /api/v1/users/456
```

Authentication says:

```text
Yes, Rahul is logged in.
```

Authorization says:

```text
No, Rahul cannot delete user 456.
```

This distinction becomes especially important in Phase 25.18 and 25.19 when we build authentication and authorization.

---

# 8. First security layer: CORS

CORS stands for:

> Cross-Origin Resource Sharing

Suppose your frontend runs at:

```text
http://localhost:5173
```

and your API runs at:

```text
http://localhost:5000
```

These are different origins.

The browser asks:

> "Is this frontend allowed to access this backend?"

CORS controls that browser behavior.

---

# 9. CORS is not authentication

This is extremely important.

If your server says:

```text
Access-Control-Allow-Origin:
http://localhost:5173
```

that does **not** mean:

```text
Only Rahul can call the API.
```

It means roughly:

> Browsers may allow JavaScript running from this origin to read responses according to the server's CORS policy.

An attacker can still call your API using:

```text
curl
Postman
server-side scripts
```

CORS does not replace authentication.

# 11. Configure CORS

Suppose your environment has:

```env
FRONTEND_URL=http://localhost:5173
```

Then:

```js
import cors from "cors";

app.use(
    cors({
        origin: env.frontendUrl,
        credentials: true,
    })
);
```

The important architectural idea is:

```text
Environment
     ↓
CORS configuration
     ↓
Allowed frontend
```

Don't hard-code production URLs everywhere.

---

# 12. Why `credentials: true`?

This becomes important when using cookies.

If your authentication architecture eventually uses:

```text
HttpOnly refresh-token cookie
```

the browser needs permission to include credentials in cross-origin requests under the appropriate CORS/cookie configuration.

So:

```js
credentials: true
```

is not something you should add blindly.

It should match your authentication design.

---

# 13. Never use this casually

Avoid production configuration like:

```js
cors({
    origin: "*"
})
```

especially when your application uses credentials/cookies.

You should have an explicit origin policy.

For example:

```text
Development
http://localhost:5173

Production
https://app.example.com
```

# 14. Second security layer: Helmet

Helmet helps configure various HTTP security headers.

Install:

```bash
npm install helmet
```

Then:

```js
import helmet from "helmet";

app.use(helmet());
```

That's simple.

But don't think:

```text
helmet()
=
backend security completed
```

It isn't.

Helmet is one layer.

# 15. What are HTTP security headers?

HTTP headers can tell browsers how they should behave.

For example, security-related policies can reduce the impact of certain browser attacks.

Conceptually:

```text
Server
  ↓
HTTP response headers
  ↓
Browser security behavior
```

Helmet helps you configure these headers.

Your earlier roadmap specifically includes:

```text
10.9 Helmet fundamentals
10.10 HTTP security headers
```

before moving deeper into rate limiting and injection protection.

# 16. Third layer: rate limiting

Imagine your login endpoint:

```http
POST /api/v1/auth/login
```

An attacker could repeatedly send:

```text
attempt 1
attempt 2
attempt 3
...
attempt 100000
```

This can cause:

```text
brute-force attempts
resource exhaustion
abuse
```

Rate limiting says:

> A client may only make a certain number of requests within a certain period.

---

# 17. Global rate limiting

Example:

```js
import rateLimit from "express-rate-limit";

const globalLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100,
});
```

Then:

```js
app.use(globalLimiter);
```

Conceptually:

```text
Client
  ↓
Request 1 ✓
Request 2 ✓
...
Request 100 ✓
Request 101 ✗
```

The exact limits should depend on your application's traffic and endpoint behavior.

---

# 18. Authentication rate limiting

Login should usually be treated differently.

For example:

```text
Global API
100 requests / 15 min

Login
much stricter limit
```

Why?

Because login is an attractive target for brute-force attacks.

Your roadmap explicitly separates:

```text
10.12 Global rate limiting
10.13 Authentication rate limiting
10.14 Brute-force protection
```

That's a very important design decision.

# 19. Fourth layer: MongoDB injection protection

Consider a query:

```js
User.findOne({
    email: req.body.email
});
```

If input is handled carelessly, specially crafted MongoDB operators can potentially alter query behavior.

For example, malicious input may attempt to introduce:

```text
$ne
$gt
$regex
```

into a query.

This is why sanitization exists.

---

Your roadmap includes:

```text

10.16 express-mongo-sanitize
```

The package helps protect against certain MongoDB operator injection patterns by sanitizing request data.

Conceptually:

```text
Request
   ↓
Mongo sanitization
   ↓
Safer input
   ↓
MongoDB query
```

But remember:

> Sanitization is not a replacement for validation.

You still need schemas.

# 21. Validation vs sanitization

We can now see the difference clearly.

### Validation

```text
"Is this email valid?"
```

### Sanitization

```text
"Can dangerous MongoDB operator syntax be removed/handled?"
```

### Normalization

```text
"Can this email be converted into our canonical form?"
```

Three related but different operations.

# 22. Fifth layer: HTTP Parameter Pollution

Suppose someone sends:

```http
/users?id=123&id=456
```

Now:

```js
req.query.id
```

might not have the simple shape your code expects.

Depending on parsing and application behavior, repeated parameters can produce unexpected values.

This is called:

> HTTP Parameter Pollution (HPP)

Your roadmap specifically includes HPP as part of the security middleware layer.

---

# 23. `hpp`

You can use:

```js
import hpp from "hpp";

app.use(hpp());
```

Again:

```text
Don't think:
hpp() = security solved

Think:
hpp() = one defensive layer
```

# 24. Sixth layer: input sanitization

Suppose a user sends:

```json
{
  "name": "<script>...</script>"
}
```

You need to think carefully about how that value will eventually be used.

For example:

```text
stored in database
        ↓
returned by API
        ↓
rendered by frontend
```

The backend should define safe input boundaries, while the frontend must also safely encode/render untrusted content.

This is why:

```text
input sanitization
```

is part of the architecture.

But don't blindly HTML-strip all user input.

A field like:

```text
description
```

might legitimately contain characters that look like HTML.

Security decisions should be based on **how the data will be consumed**.

# 25. Seventh layer: origin checking

CORS handles browser cross-origin behavior, but sometimes your application needs a stricter concept of allowed origins.

For example:

```text
Allowed:
https://app.example.com

Not allowed:
https://evil.example.com
```

Your starter architecture includes:

```text
origin.middleware.js
```

So origin checking becomes a reusable middleware rather than being scattered across routes.

---

# 26. Why separate `origin.middleware.js`?

Because CORS and application origin rules aren't always identical concepts.

You might want:

```text
CORS policy
    ↓
browser access rules

Origin middleware
    ↓
application-specific origin policy
```

This keeps the responsibility explicit.

# 28. Security middleware ordering

Now we reach one of the most important parts.

Don't just write:

```js
app.use(...)
app.use(...)
app.use(...)
```

randomly.

Middleware order matters.

A simplified architecture could look like:

```text
Request
   ↓
Request ID
   ↓
Security headers
   ↓
CORS
   ↓
Rate limiting
   ↓
Body parsing
   ↓
Sanitization
   ↓
Routes
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Controller
```

But there is an important nuance:

**Not every middleware should be global, and exact ordering depends on what the middleware needs.**

For example, route-specific validation belongs close to the route.

# 35. Don't store secrets in code

Never do:

```js
const JWT_SECRET = "rahul-secret-123";
```

Instead:

```env

JWT_REFRESH_SECRET=...
```

# 36. Don't log secrets

Your logger should never casually print:

```js
console.log(req.headers.authorization);
```

or:

```js
console.log(req.cookies);
```

because those may contain credentials or tokens.

The same applies to:

```text
passwords
refresh tokens
access tokens
API keys
database credentials
session secrets
```

Your later observability architecture explicitly includes protecting sensitive data in logs.

# 39. Don't over-sanitize

This is an important real-world lesson.

Security doesn't mean:

```text
Remove everything unusual.
```

Imagine a notes application.

A user writes:

```text
Use <User> syntax in the documentation.
```

If you blindly strip all `<...>` content, you've changed legitimate user data.

Instead:

```text
Validation
+
context-aware sanitization
+
safe output encoding
```

is better than:

```text
destroy everything that looks suspicious
```

# 40. Security is defense in depth

Suppose one security layer fails.

You still want another layer.

For example:

```text
CORS
 ↓
Authentication
 ↓
Authorization
 ↓
Validation
 ↓
Database constraints
```

If someone bypasses CORS using curl:

```text
CORS bypassed
      ↓
Authentication
      ↓
Authorization
```

Still protected.

If someone is authenticated:

```text
Authentication ✓
      ↓
Authorization
      ↓
Can't access another user's resource
```

This is **defense in depth**.

# 41. Example: protecting a Todo

Suppose:

```text
Rahul
userId = 123
```

tries:

```http
GET /api/v1/todos/999
```

A secure backend shouldn't simply do:

```js
Todo.findById(999);
```

and return the result.

The eventual repository query should include ownership:

```js
Todo.findOne({
    _id: todoId,
    userId,
});
```

Your roadmap specifically highlights this kind of ownership query in the authorization phase.

This prevents many horizontal privilege-escalation/IDOR-style problems.

# 44. A practical `app.js`

At this stage, your application composition can conceptually move toward:

```js
import express from "express";
import cors from "cors";
import helmet from "helmet";
import hpp from "hpp";
import rateLimit from "express-rate-limit";
import mongoSanitize from "express-mongo-sanitize";

const app = express();

app.use(helmet());

app.use(
    cors({
        origin: env.frontendUrl,
        credentials: true,
    })
);

app.use(
    rateLimit({
        windowMs: 15 * 60 * 1000,
        limit: 100,
    })
);

app.use(express.json());

app.use(express.urlencoded({ extended: true }));

app.use(mongoSanitize());

app.use(hpp());

// routes

app.use(errorMiddleware);

export default app;
```

**Don't copy this blindly into your final starter yet.**

We're still building the architecture lesson by lesson.

The exact middleware composition will be refined as authentication, cookies, validation, logging, and production configuration are added.

---

# 45. Why security middleware comes before routes

Consider:

```js
app.use("/api", routes);
```

If you put your security middleware after it:

```js
app.use("/api", routes);

app.use(helmet());
app.use(rateLimiter);
```

the routes may already have processed the request.

That defeats the purpose of global protections.

So broadly:

```text
Global security
      ↓
Routes
```

not:

```text
Routes
      ↓
Global security
```

---

# 46. But don't blindly put everything before everything

For example:

```text
Authentication
```

doesn't make sense globally if you have:

```text
GET /health
POST /auth/login
POST /auth/signup
```

Those routes may intentionally be public.

So:

```text
Global middleware
+
route-specific middleware
```

is the correct mental model.

# 49. Common mistakes


Using the same rate limit for every endpoint.
