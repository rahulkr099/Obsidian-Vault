# Lesson 25.13 — User Model

This lesson is directly defined in your Phase 25 sequence as **25.13 User Model**, following Security Architecture and before the Repository Layer.

The source gives us the core User structure:

```text
User
├── firstName
├── lastName
├── email
├── password
├── role
├── refreshTokenHash
├── resetTokenHash
├── resetTokenExpires
└── timestamps
```

and explicitly says that the password must **never be stored in plain text**; it should be hashed with bcrypt before being stored.

Let's understand **why** this model is designed this way.

---

# 1. What is the User Model?

The User Model defines:

> **What information about a user is stored in MongoDB, and what rules apply to that data.**

Our architecture is:

```text
User Model
    ↓
MongoDB
```

The model describes the shape of a document.

For example:

```json
{
  "firstName": "Rahul",
  "lastName": "Kumar",
  "email": "rahul@example.com",
  "password": "hashed-password",
  "role": "user"
}
```

The important thing is:

```text
password
```

is **not**:

```text
mypassword123
```

It is a cryptographic hash.

# 4. First field — `firstName`

```js
firstName: {
    type: String,
    required: true,
    trim: true,
}
```

Meaning:

```text
type
 ↓
must be a string

required
 ↓
must exist

trim
 ↓
remove unnecessary surrounding spaces
```

For example:

```text
" Rahul "
```

becomes:

```text
"Rahul"
```

---

# 5. `lastName`

Same idea:

```js
lastName: {
    type: String,
    required: true,
    trim: true,
}
```

We want predictable data.

Instead of allowing:

```text
" Rahul "
"Rahul"
"RAHUL"
```

without any thought about normalization, we establish a clear model contract.

---

# 6. Email

Email is one of the most important fields.

```js
email: {
    type: String,
    required: true,
    unique: true,
    lowercase: true,
    trim: true,
}
```

Conceptually:

```text
" Rahul@Example.COM "
        ↓
"rahul@example.com"
```

The exact normalization policy should be consistent throughout the application.

---

# 7. Why `unique: true`?

Imagine two users:

```text
User A
email = rahul@example.com

User B
email = rahul@example.com
```

For normal email/password authentication, that's a problem.

We want:

```text
one email
    ↓
one user
```

So we need uniqueness.

But here's an important MongoDB lesson:

> Don't think of `unique: true` as ordinary validation.

It creates a unique index/constraint behavior at the database level.

Your service should still handle duplicate-key errors properly.

---

# 8. Email is usually used as an identity

Our authentication flow will eventually look like:

```text
Login
 ↓
email
 ↓
find user
 ↓
compare password
 ↓
authenticate
```

The source's authentication architecture specifically includes:

```text
findUserByEmail()
findUserById()
```

in the repository layer.

So email needs to be reliably stored and queried.

# 9. Password

Now the most important field:

```js
password: {
    type: String,
    required: true,
    select: false,
}
```

The source explicitly emphasizes:

```text
Never store:
plain password

Store:
password
 ↓
bcrypt
 ↓
hash
 ↓
MongoDB
```

---

# 10. Why hash the password?

Suppose the user chooses:

```text
MyPassword123
```

We should **never** store:

```text
MyPassword123
```

Instead:

```text
MyPassword123
      ↓
   bcrypt
      ↓
$2b$12$...
      ↓
MongoDB
```

If someone gets database access, they shouldn't immediately see everyone's actual passwords.

---

# 11. Hashing vs encryption

This distinction is important.

### Encryption

```text
data
 ↓
encrypt
 ↓
encrypted data
 ↓
decrypt
 ↓
original data
```

### Password hashing

```text
password
 ↓
hash
 ↓
hash
```

You don't normally decrypt a password hash.

During login:

```text
entered password
       ↓
bcrypt.compare()
       ↓
stored hash
       ↓
true / false
```

The source specifically uses bcrypt as the password hashing mechanism.

---

# 12. Why `select: false`?

Suppose we run:

```js
User.findById(userId);
```

We usually don't want the password hash casually appearing in the returned user object.

So:

```js
select: false
```

helps keep the password field excluded from ordinary queries.

When authentication specifically needs the password hash, we can explicitly request it.

Conceptually:

```text
Normal query
    ↓
User data
    ↓
password hidden
```

Authentication query:

```text
Login
 ↓
explicitly request password
 ↓
compare password
```

This is a good example of **secure defaults**.

---

# 13. Role

Next:

```js
role: {
    type: String,
    enum: ["user", "admin"],
    default: "user",
}
```

The source's starter architecture includes roles and specifically gives the example:

```js
export const ROLES = {
    USER: "user",
    ADMIN: "admin"
};
```

as a reason to centralize role values in constants.

So eventually we'd prefer:

```js
import { ROLES } from "../constants/roles.js";
```

rather than scattering:

```js
"admin"
"user"
```

through the application.

---

# 14. Why does the User need a role?

Because authentication answers:

```text
Who are you?
```

while authorization asks:

```text
What are you allowed to do?
```

For example:

```text
Rahul
 ↓
authenticated
 ↓
role = user
```

Another user:

```text
Admin
 ↓
authenticated
 ↓
role = admin
```

Then:

```text
GET /api/v1/users
```

might be available only to admins.

The roadmap deliberately separates authentication from authorization.

---

# 15. Don't make roles too complicated yet

For our starter:

```text
user
admin
```

is enough.

Later, a real application might need:

```text
student
instructor
admin
moderator
support
```

But don't introduce complexity before you need it.

The source itself recommends starting with simple role-based authorization before moving into permission-based authorization and resource ownership.

---

# 16. Refresh Token Hash

Next:

```js
refreshTokenHash: {
    type: String,
    select: false,
}
```

This field is extremely important.

Our authentication architecture eventually becomes:

```text
Login
 ↓
Generate access token
 ↓
Generate refresh token
 ↓
Hash refresh token
 ↓
Store hash
```

The source explicitly describes this flow.

---

# 17. Why hash the refresh token?

Suppose the refresh token is:

```text
abc123...
```

We don't necessarily want the raw refresh token sitting in MongoDB.

Instead:

```text
refresh token
      ↓
bcrypt hash
      ↓
refreshTokenHash
      ↓
MongoDB
```

So even though access tokens and refresh tokens are credentials, we're treating the stored refresh token carefully.

---

# 18. Password reset fields

Our model also contains:

```js
resetTokenHash
resetTokenExpires
```

Conceptually:

```text
Forgot password
       ↓
Generate reset token
       ↓
Hash token
       ↓
Store hash
       ↓
Store expiration
       ↓
Send reset link
```

Then:

```text
User clicks link
       ↓
Token submitted
       ↓
Compare with stored hash
       ↓
Check expiration
       ↓
Allow password reset
```

The source places password reset as part of the authentication architecture.

---

# 19. Why store expiration?

Imagine a reset token is created today.

Without expiration:

```text
Token
 ↓
could potentially remain usable indefinitely
```

Instead:

```text
resetTokenExpires
```

allows us to enforce:

```text
Token valid?
        │
        ├── YES → continue
        │
        └── NO → reject
```

This is another security boundary.

---

# 20. Timestamps

Finally:

```js
timestamps: true
```

Mongoose will maintain:

```text
createdAt
updatedAt
```

So a document becomes conceptually:

```json
{
  "firstName": "Rahul",
  "lastName": "Kumar",
  "email": "rahul@example.com",
  "role": "user",
  "createdAt": "...",
  "updatedAt": "..."
}
```

These are extremely useful for:

```text
auditing
sorting
administration
analytics
debugging
```

# 21. Let's build the schema

At a basic level:

```js
import mongoose from "mongoose";

const userSchema = new mongoose.Schema(
    {
        firstName: {
            type: String,
            required: true,
            trim: true,
        },

        lastName: {
            type: String,
            required: true,
            trim: true,
        },

        email: {
            type: String,
            required: true,
            unique: true,
            lowercase: true,
            trim: true,
        },

        password: {
            type: String,
            required: true,
            select: false,
        },

        role: {
            type: String,
            enum: ["user", "admin"],
            default: "user",
        },

        refreshTokenHash: {
            type: String,
            select: false,
        },

        resetTokenHash: {
            type: String,
            select: false,
        },

        resetTokenExpires: {
            type: Date,
            select: false,
        },
    },
    {
        timestamps: true,
    }
);

const User = mongoose.model("User", userSchema);

export default User;
```

This is the basic model.

But **don't rush to copy it**.

Let's understand what belongs here and what doesn't.

---

# 22. What does NOT belong in the User Model?

Don't turn your model into a giant application layer.

Avoid putting things like:

```text
sendEmail()
generateJWT()
login()
checkAdminPermission()
createResponse()
```

inside the User model.

Those responsibilities belong elsewhere.

Our architecture is:

```text
Model
 ↓
Data structure

Repository
 ↓
Database operations

Service
 ↓
Business logic

Controller
 ↓
HTTP

Middleware
 ↓
Request checks
```

The source repeatedly emphasizes this separation, especially the distinction between controller, service, repository, and model responsibilities.

---

# 23. User Model vs User Repository

This distinction will become very important in **25.14**.

### Model

Answers:

> What does a User document look like?

```text
User
├── email
├── password
├── role
└── ...
```

### Repository

Answers:

> How do I retrieve or modify Users?

```text
findUserByEmail()
findUserById()
createUser()
updateRefreshToken()
clearRefreshToken()
```

The source explicitly lists these kinds of operations for the repository.

---

# 24. User Model vs User Service

### Model

```text
Data structure
```

### Service

```text
Business operation
```

For example:

```text
authService.login()
```

could do:

```text
Find user
 ↓
Check password
 ↓
Generate tokens
 ↓
Hash refresh token
 ↓
Store refresh token hash
 ↓
Return authentication result
```

The source identifies this as the heart of the application's business logic.

The User Model should not own this whole process.

---

# 25. What should happen to passwords?

A clean flow is:

```text
Signup request
      ↓
Validation
      ↓
Service
      ↓
bcrypt.hash(password)
      ↓
User.create()
      ↓
MongoDB
```

The model receives:

```text
hashed password
```

not the original password.

That's an important architectural boundary.

---

# 26. What about hashing inside a Mongoose pre-save hook?

You might see tutorials doing:

```js
userSchema.pre("save", async function () {
    this.password = await bcrypt.hash(this.password, 12);
});
```

This can work.

But for **this starter architecture**, be careful about hiding important business behavior inside model hooks.

Our learning architecture is explicitly moving toward:

```text
Controller
 ↓
Service
 ↓
Repository
 ↓
Model
```

so authentication logic should remain understandable in the service layer rather than becoming invisible magic.

The source's authentication flow places password hashing in the service process.

---

# 27. A very important security rule

Never return this:

```json
{
  "email": "rahul@example.com",
  "password": "$2b$12$..."
}
```

Even though the password is hashed.

The hash itself is sensitive authentication material.

That's why:

```js
select: false
```

is useful.

And even when explicitly selected for authentication, don't include it in API responses.

---

# 28. User response vs User database document

These are different concepts.

### Database

```text
User document
├── email
├── password
├── refreshTokenHash
├── resetTokenHash
└── ...
```

### API response

```json
{
  "id": "123",
  "firstName": "Rahul",
  "lastName": "Kumar",
  "email": "rahul@example.com",
  "role": "user"
}
```

Sensitive internal fields should stay internal.

This distinction will become even more important when we build the API response layer.

---

# 29. The `toJSON` idea

Later, you might decide to transform user documents before sending them:

```js
userSchema.methods.toJSON = function () {
    const user = this.toObject();

    delete user.password;
    delete user.refreshTokenHash;
    delete user.resetTokenHash;
    delete user.resetTokenExpires;

    return user;
};
```

This can provide another safety layer.

But don't rely on this alone.

Your application should deliberately control what gets returned.

|Field|Sensitivity|

# 32. Common mistakes

### ❌ Mistake 1 — Plain password

```js

```

Never.

---

### ❌ Mistake 2 — Returning password hash

```js
res.json(user);
```

without considering sensitive fields.

---

### ❌ Mistake 3 — Storing raw refresh tokens

```text
refreshToken
```

instead of:

```text

```

---

### ❌ Mistake 4 — Allowing arbitrary roles

Bad:

```js

```

with no controlled role policy.

---

### ❌ Mistake 5 — Putting login logic inside the model

```js

```

that starts handling:

```text
JWT
cookies
HTTP
responses
```

That's mixing responsibilities.

---

### ❌ Mistake 6 — Treating `unique` as complete validation

You still need application-level validation and duplicate-key error handling.

# 36. The mental model to remember

Don't memorize the schema line by line.

Remember:

```text
USER
 │
 ├── Who is this?
 │      ├── firstName
 │      ├── lastName
 │      └── email
 │
 ├── How does authentication work?
 │      ├── password hash
 │      └── refresh token hash
 │
 ├── What can they do?
 │      └── role
 │
 ├── Can they recover their account?
 │      ├── reset token hash
 │      └── expiration
 │
 └── When was this record created/changed?
        └── timestamps
```

**The key lesson:** the User Model is not merely a MongoDB schema. It is the **data foundation for authentication, authorization, session security, and account recovery**.
