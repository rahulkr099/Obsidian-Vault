# Lesson 25.14 — Repository Layer

We are now moving from the **User Model** to the **Repository Layer**.

Your Phase 25 sequence is:

```text
25.13 User Model
        ↓
25.14 Repository Layer
        ↓
25.15 Service Layer
        ↓
25.16 Controller Layer
```

And your roadmap defines the repository as the layer responsible for **data access**, with examples such as `findUserByEmail()`, `findUserById()`, `createUser()`, `updateRefreshToken()`, and `clearRefreshToken()`.

The most important idea today is:

> **The repository talks to the database. The service talks to the repository.**

---

# 1. The problem we're solving

Imagine we don't have a repository.

Our service might directly contain MongoDB queries:

```js
const user = await User.findOne({ email });
```

Then another service does:

```js
const user = await User.findById(id);
```

Another one:

```js
await User.findByIdAndUpdate(id, {...});
```

Soon your business logic becomes mixed with database logic.

You get:

```text
Service
├── business logic
├── MongoDB queries
├── Mongoose details
├── update operations
├── filtering
└── database error handling
```

That's not ideal.

---

# 2. Enter the Repository

The repository gives us a boundary:

```text
Service
   ↓
Repository
   ↓
Mongoose Model
   ↓
MongoDB
```

The service says:

> "I need the user with this email."

The repository says:

> "I'll handle how that user is retrieved from MongoDB."

So:

```text
Service
    │
    │ "find user by email"
    ▼
Repository
    │
    │ User.findOne(...)
    ▼
MongoDB
```

Your source describes exactly this separation: the repository knows **how to get or modify data**, while it should not know about HTTP, JWT, cookies, or business rules.

---

# 3. Repository vs Model

This distinction is extremely important.

### Model

The model answers:

> **What does the data look like?**

```text
User Model
├── firstName
├── lastName
├── email
├── password
├── role
└── ...
```

### Repository

The repository answers:

> **How do I access that data?**

```text
User Repository
├── findUserByEmail()
├── findUserById()
├── createUser()
├── updateRefreshToken()
└── clearRefreshToken()
```

So:

```text
Model
  =
data structure

Repository
  =
data access
```

---

# 4. Repository vs Service

This is probably the most important distinction in this lesson.

### Repository

```text
"I know HOW to access data."
```

### Service

```text
"I know WHAT the application should do."
```

Example:

```text
Login
 ↓
Service
 ↓
"Find this user."
 ↓
Repository
 ↓
MongoDB
```

The repository shouldn't decide:

```text
"Is this password correct?"
```

That's business/application logic.

The service should.

Compare:

```js

```




# 13. Important distinction

Suppose signup happens.

The service might do:

```text

2. Check existing user
3. Hash password
4. Create user
```

The repository only handles the database operations:


So:

```text

└── calls repository

├── find

```

This separation is exactly what we're aiming for.

# 14. Refresh token operations

Our User model has:

```text
refreshTokenHash
```

So the repository needs an operation for updating it.

For example:

```js
export const updateRefreshToken = async (
    userId,
    refreshTokenHash
) => {
    return User.findByIdAndUpdate(
        userId,
        { refreshTokenHash },
        { new: true }
    );
};
```

Now:

```text
Service
 ↓
updateRefreshToken()
 ↓
Repository
 ↓
MongoDB
```

---

# 15. Clearing the refresh token

Logout eventually needs to invalidate the stored refresh-token hash.

Repository:

```js
export const clearRefreshToken = async (userId) => {
    return User.findByIdAndUpdate(
        userId,
        {
            $unset: {
                refreshTokenHash: 1,
            },
        },
        {
            new: true,
        }
    );
};
```

Conceptually:

```text
Logout
 ↓
Service
 ↓
clearRefreshToken()
 ↓
Repository
 ↓
refreshTokenHash removed
```

The source specifically lists `clearRefreshToken()` as a repository responsibility.

# 17. But there's a security problem

Remember our User model:

```js
password: {
    type: String,
    select: false,
}
```

So:

```js
User.findOne({ email });
```

normally won't include the password.

That's good for ordinary queries.

But login needs the password hash.

We therefore need a deliberate repository operation.

For example:

```js
export const findUserByEmailForAuth = async (email) => {
    return User.findOne({ email }).select("+password");
};
```

Now the intention is explicit:

```text
Normal user lookup
    ↓
password hidden

Authentication lookup
    ↓
password explicitly requested
```

This is a very good security pattern.

---

# 18. Why not always select the password?

Because then it's easy to accidentally do:

```js
const user = await findUserByEmail(email);

return res.json(user);
```

and expose the password hash.

Secure architecture prefers:

```text
Secure by default
       ↓
Explicitly request sensitive data
       ↓
Only where required
```

# 20. Should the repository hash passwords?

No.

The repository should **not** do:

```js
bcrypt.hash(...)
```

Why?

Because hashing is part of the authentication/application logic.

The architecture from your source puts password hashing in the authentication service flow.

So:

```text
Service
 ↓
bcrypt.hash(password)
 ↓
Repository
 ↓
createUser()
```

not:

```text
Service
 ↓
Repository
 ↓
Repository hashes password
```

---

# 21. Should the repository generate JWTs?

Absolutely not.

Bad:

```text
user.repository.js
    ↓
generateAccessToken()
```

JWTs belong to authentication utilities/service logic.

The repository should care about:

```text
database
```

not:

```text
HTTP
JWT
cookies
authentication decisions
```

Your source explicitly states that the repository should not know about HTTP, JWT, cookies, or business rules.

# 22. Repository parameters

Good:

```js
findUserById(userId)
```

Good:

```js
updateRefreshToken(userId, refreshTokenHash)
```

Avoid passing huge request objects:

```js
updateUser(req)
```

Why?

Because then the repository becomes coupled to Express.

Bad architecture:

```text
Repository
   ↓
req.body
req.params
req.user
res
```

Good architecture:

```text
Service
   ↓
repository(userId, data)
```

The repository receives the data it needs.

# 23. Repository should not know about `req`

Never:

```js
export const findUser = async (req) => {
    return User.findById(req.user.id);
};
```

Instead:

```js
export const findUserById = async (userId) => {
    return User.findById(userId);
};
```

Why?

Because now the repository can be used from:

```text
HTTP controller
background job
CLI script
test
cron job
another service
```

without requiring Express.

# 24. Ownership queries

This is where the repository becomes extremely important for security.

Suppose we have:

```text
Todo A
owner = User 123
```

Rahul is:

```text
userId = 456
```

Bad:

```js
Todo.findById(todoId);
```

That only checks:

```text
Does this Todo exist?
```

Better:

```js
Todo.findOne({
    _id: todoId,
    userId,
});
```

That checks:

```text
Does this Todo exist
AND
does it belong to this user?
```

Your roadmap explicitly highlights this ownership-query pattern as an important authorization defense.

---

# 25. Why ownership belongs in the data query

Imagine:

```text
User A
  ↓
Todo 100

User B
  ↓
Todo 200
```

User A asks for:

```text
Todo 200
```

If you first do:

```js
const todo = await Todo.findById(todoId);
```

and then somewhere later check ownership, you're making the system more complicated.

Instead:

```js
Todo.findOne({
    _id: todoId,
    userId,
});
```

makes the database query itself enforce the ownership boundary.

This is a powerful security pattern.

---

# 26. Repository vs authorization

Important nuance:

The repository doesn't decide:

```text
"Rahul is allowed to delete todos."
```

That's application authorization.

But the repository can enforce data boundaries:

```text
"Only retrieve records belonging to userId."
```

So:

```text
Authorization decision
       ↓
Service
       ↓
Ownership-aware repository query
       ↓
Database
```

This is why authorization can involve both service and repository layers.

Your roadmap specifically includes authorization inside services and repositories.

# 27. What about errors?

Suppose MongoDB fails:

```text
MongoDB
   ↓
error
   ↓
Repository
```

Should the repository send an HTTP response?

No.

Never:

```js
res.status(500).json(...)
```

inside the repository.

Instead:

```text
Repository
 ↓
throw/reject error
 ↓
Service
 ↓
Controller
 ↓
asyncHandler
 ↓
Global error middleware
```

This keeps the layers independent.

# 28. Repository error example

You might have:

```js
export const createUser = async (userData) => {
    return User.create(userData);
```

If MongoDB throws a duplicate-key error:


# 33. What each layer knows

|Layer|Main responsibility|
|---|---|
|Route|Which endpoint?|
|Middleware|Request checks|
|Controller|HTTP|
|Service|Business logic|
|Repository|Database access|
|Model|Data structure|
|MongoDB|Persistence|

A very useful rule:

> **The lower layer should not suddenly start doing the upper layer's job.**

For example:

```text
Repository ❌ HTTP
Repository ❌ res.json()
Repository ❌ JWT
Repository ❌ cookies
Repository ❌ business decisions
```
