# 1. What is a Service?

In simple words:

> **A service contains the decisions and rules that make your application do its actual work.**

For example:

```text
User wants to log in
        ↓
Is the email registered?
        ↓
Is the password correct?
        ↓
Generate tokens
        ↓
Save refresh-token hash
        ↓
Return authentication result
```

Those decisions belong in the service.

# 3. Why do we need a Service?

Imagine putting everything into a controller.

```js
export const login = async (req, res) => {
    const { email, password } = req.body;

    const user = await User.findOne({ email });

    if (!user) {
        return res.status(401).json({
            message: "Invalid credentials"
        });
    }

    const valid = await bcrypt.compare(
        password,
        user.password
    );

    if (!valid) {
        return res.status(401).json({
            message: "Invalid credentials"
        });
    }

    const accessToken = generateAccessToken(user);
    const refreshToken = generateRefreshToken(user);

    // hash refresh token
    // save hash
    // set cookie
    // return response
};
```

It works.

But now the controller knows:

```text
MongoDB
bcrypt
JWT
refresh tokens
cookies
business rules
HTTP responses
```

That's too much responsibility.

# 6. Service is about decisions

This is the most important concept.

Suppose:

```text
Create account
```

The repository knows:

```text
How to create a MongoDB document
```

But the service knows:

```text
Should this account be created?
Is the email already registered?
Should the password be hashed?
What role should the user receive?
What should happen after creation?
```

So:

```text
Repository
=
HOW to access data

Service
=
WHAT the application should do
```

# 7. Where should business rules live?

Consider:

```text
User registers
```

Possible rules:

```text
Email must be unique
Password must be hashed
New users get "user" role
Email should be normalized
Duplicate registration should fail
```

These are application rules.

Therefore:

```text
Controller ❌
Repository ❌
Service ✅
```

The repository can enforce database constraints, but the overall business process belongs in the service.

# 10. The service becomes useful when rules appear

Suppose signup receives:

```json
{
  "firstName": "Rahul",
  "lastName": "Kumar",
  "email": " Rahul@Example.com ",
  "password": "password123"
}
```

The service might perform:

```text
1. Normalize email
2. Check existing user
3. Hash password
4. Set default role
5. Create user
6. Remove sensitive fields
7. Return safe user
```

Now the service is doing real work.

---

# 11. Step 1 — Normalize email

```js
const email = data.email.trim().toLowerCase();
```

Input:

```text
" Rahul@Example.COM "
```

becomes:

```text
"rahul@example.com"
```

This is application behavior.

So it belongs naturally in the service.

---

# 12. Step 2 — Check existing user

The service calls the repository:

```js
const existingUser =
    await userRepository.findUserByEmail(email);
```

Then:

```js
if (existingUser) {
    throw new AppError(
        "User already exists",
        409
    );
}
```

Notice the separation.

The repository knows:

```text
How to find the user
```

The service knows:

```text
What it means if the user already exists
```

That's exactly the relationship we want.

---

# 13. Step 3 — Hash password

The service receives:

```text
password123
```

It should never send that directly to the database.

Instead:

```text
password123
     ↓
bcrypt
     ↓
hashed password
     ↓
repository
     ↓
MongoDB
```

Your source explicitly places password hashing inside the authentication service flow.

---

# 14. Step 4 — Create the user

Now:

```js
const user = await userRepository.createUser({
    firstName: data.firstName,
    lastName: data.lastName,
    email,
    password: hashedPassword,
});
```

Notice something important.

The service doesn't do:

```js
User.create(...)
```

It calls:

```js
userRepository.createUser(...)
```

That's the whole point of the repository layer we built in 25.14.

# 15. Step 5 — Return a safe result

The database may contain:

```text
password
refreshTokenHash
resetTokenHash
resetTokenExpires
```

But the service should return only what the caller needs.

For example:

```js
return {
    id: user._id,
    firstName: user.firstName,
    lastName: user.lastName,
    email: user.email,
    role: user.role,
};
```

This is another important security boundary.

# 17. Service inputs

A service should ideally receive **application data**, not Express objects.

Good:

```js
authService.signup({
    firstName,
    lastName,
    email,
    password,
});
```

Bad:

```js
authService.signup(req);
```

Why?

Because the service shouldn't depend on Express.

Then it can be reused from:

```text
HTTP controller
background job
CLI
tests
admin script
```

This is a very useful design property.

---

# 18. Service outputs

A service should generally return application-level results.

For example:

```js
return {
    user,
    accessToken,
};
```

or:

```js
return user;
```

It should not normally return:

```js
res.status(201).json(...)
```

That's the controller's responsibility.

Remember:

```text
Service
=
application

Controller
=
HTTP
```

---

# 19. Service should not know `req` or `res`

Avoid:

```js
export const login = async (req, res) => {
```

inside the service.

Instead:

```js
export const login = async ({
    email,
    password,
}) => {
```

Then the controller does:

```js
const result = await authService.login(req.body);
```

Clean boundary.

---

# 20. Service should not send HTTP status codes

Avoid:

```js
return res.status(401).json({
    message: "Invalid credentials"
});
```

Instead:

```js
throw new AppError(
    "Invalid credentials",
    401
);
```

Then:

```text
Service
 ↓
throw AppError
 ↓
Controller / asyncHandler
 ↓
Global error middleware
 ↓
HTTP response
```

Your previous Error Architecture phase is what makes this possible.

---

# 21. Service error handling

Suppose user doesn't exist.

The service can say:

```js
throw new AppError(
    "Invalid credentials",
    401
);
```

It doesn't need to know how the final JSON response looks.

That's handled elsewhere.

This gives us:

```text
Business error
       ↓
AppError
       ↓
Global error handler
       ↓
Consistent API response
```

# 24. Login example

Conceptually:

```js
export const login = async ({ email, password }) => {
    const normalizedEmail = email
        .trim()
        .toLowerCase();

    const user =
        await userRepository.findUserByEmailForAuth(
            normalizedEmail
        );

    if (!user) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    const passwordValid =
        await bcrypt.compare(
            password,
            user.password
        );

    if (!passwordValid) {
        throw new AppError(
            "Invalid credentials",
            401
        );
    }

    // Generate tokens...

    return {
        user,
        accessToken,
    };
};
```

Notice how much business logic is happening here.

That's why the service layer exists.

# 34. A clean signup service

A simplified version:

```js
import bcrypt from "bcrypt";
import * as userRepository from "../repositories/user.repository.js";
import { AppError } from "../utils/app-error.js";

export const signup = async ({
    firstName,
    lastName,
    email,
    password,
}) => {
    const normalizedEmail = email
        .trim()
        .toLowerCase();

    const existingUser =
        await userRepository.findUserByEmail(
            normalizedEmail
        );

    if (existingUser) {
        throw new AppError(
            "User already exists",
            409
        );
    }

    const hashedPassword =
        await bcrypt.hash(password, 12);

    const user =
        await userRepository.createUser({
            firstName,
            lastName,
            email: normalizedEmail,
            password: hashedPassword,
        });

    return {
        id: user._id,
        firstName: user.firstName,
        lastName: user.lastName,
        email: user.email,
        role: user.role,
    };
};
```

This is much easier to reason about than putting everything inside the controller.

# 38. Interview questions

You should now be able to answer:

### 1. What is a service layer?

> A layer containing business logic and coordinating application operations.

### 2. Why shouldn't controllers contain business logic?

Because controllers should primarily translate HTTP requests/responses, while business logic should remain reusable and independent of HTTP.

### 3. What does a repository do?

It handles database access.

### 4. What does a service do?

It decides and coordinates what the application should do.

### 5. Should a service receive `req` and `res`?

Generally, no.

### 6. Should a service call `User.findOne()` directly?

In our architecture, no. It should use the repository.

### 7. Where should password hashing happen?

In the authentication/business logic flow, not in the controller or repository.

### 8. What is service orchestration?

Coordinating multiple operations into one business operation.

# 39. The three-layer rule

This is the most important thing to remember from Lessons 25.13–25.15:

```text

        ↓

"How do I access the data?"

```

And then:


```text

                  │
                  ▼
             CONTROLLER

                  │

                  │
                  ▼

             "DB operations"
                  │
                  ▼
                MODEL
             "Data structure"
                  │
                  ▼
               MongoDB
```

This is the architecture you are ultimately trying to build from an empty project—not just memorize folder names. Your source explicitly frames Phase 25 as the point where you should be able to build the starter from scratch and understand why each layer exists.
