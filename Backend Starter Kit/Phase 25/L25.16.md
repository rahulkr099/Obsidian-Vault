# Lesson 25.16 — Controller Layer

We have now built the three most important backend layers:

```text
25.13  Model
   ↓
25.14  Repository
   ↓
25.15  Service
   ↓
25.16  Controller   ← WE ARE HERE
```

The controller is where **HTTP meets your application logic**.

The simple rule for today is:

> **The controller handles HTTP. The service handles business logic.**

---

# 1. Where does the Controller fit?

Our complete flow:

```text
Client
  │
  │ HTTP Request
  ▼
Route
  │
  ▼
Middleware
  │
  ▼
Controller
  │
  ▼
Service
  │
  ▼
Repository
  │
  ▼
Model
  │
  ▼
MongoDB
```

And the response travels back upward:

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
HTTP Response
   ↓
Client
```

So the controller is the **boundary between HTTP and application logic**.

---

# 2. What exactly does a Controller do?

A controller typically does four things:

```text
1. Read HTTP input
2. Call the appropriate service
3. Choose the HTTP response
4. Send the response
```

For example:

```js
export const signup = async (req, res) => {
    const result = await authService.signup(req.body);

    return res.status(201).json({
        success: true,
        data: result,
    });
};
```

That's a healthy controller.

Notice what's missing:

```text
❌ MongoDB query
❌ password hashing
❌ JWT generation
❌ business decisions
❌ database update
```

Those belong elsewhere.

---

# 3. Why shouldn't controllers contain business logic?

Consider this controller:

```js
export const signup = async (req, res) => {
    const email = req.body.email
        .trim()
        .toLowerCase();

    const existingUser =
        await User.findOne({ email });

    if (existingUser) {
        return res.status(409).json({
            message: "User already exists",
        });
    }

    const hashedPassword =
        await bcrypt.hash(req.body.password, 12);

    const user = await User.create({
        email,
        password: hashedPassword,
    });

    return res.status(201).json(user);
};
```

It works.

But the controller now knows:

```text
HTTP
MongoDB
Mongoose
bcrypt
business rules
user creation
```

That's a **fat controller**.

---

# 4. The better version

Controller:

```js
export const signup = async (req, res) => {
    const user = await authService.signup(req.body);

    return res.status(201).json({
        success: true,
        data: user,
    });
};
```

Service:

```text
normalize email
      ↓
check existing user
      ↓
hash password
      ↓
create user
      ↓
return safe user
```

Repository:

```text
find user
create user
```

Much cleaner.

---

# 5. Controller = HTTP adapter

Think of the controller as an **adapter**.

The outside world speaks:

```text
HTTP
```

Your application speaks:

```text
application/domain operations
```

The controller translates between them.

For example:

```text
HTTP
POST /api/v1/auth/signup
        │
        ▼
Controller
        │
        │ signup(data)
        ▼
Service
```

The service doesn't need to know:

```text
POST
headers
cookies
status codes
Express
req
res
```

That's the controller's world.

# 7. First controller

Let's build signup.

```js
import * as authService from "../services/auth.service.js";

export const signup = async (req, res) => {
    const result = await authService.signup(req.body);

    return res.status(201).json({
        success: true,
        data: result,
    });

```

That's almost the entire controller.

And that's a **good thing**.

---

# 8. Why is a small controller good?

Because you should be able to look at:

```js
export const signup = async (req, res) => {
    const result = await authService.signup(req.body);

    return res.status(201).json({
        success: true,
        data: result,
    });
};
```

and immediately understand:

```text
Request
  ↓
signup service
  ↓
201 response
```

If a controller is 150 lines long, that's usually a warning sign.

---

# 9. Controller responsibilities

Let's define them carefully.

## Responsibility 1 — Read request data

For example:

```js
const { email, password } = req.body;
```

or:

```js
const { userId } = req.params;
```

or:

```js
const { page, limit } = req.query;
```

This is HTTP-specific work.

---

# 10. Responsibility 2 — Call the service

Example:

```js
const result = await authService.login({
    email,
    password,
});
```

The controller converts:

```text
req.body
```

into:

```text
application input
```

This is a useful boundary.

---

# 11. Responsibility 3 — Handle HTTP response

The service might return:

```js
{
    user,
    accessToken
}
```

The controller decides:

```js
return res.status(200).json({
    success: true,
    data: result,
});
```

The service doesn't need to know that HTTP status `200` is being used.

---

# 12. Responsibility 4 — HTTP-specific things

Controllers can handle things like:

```text
status codes
cookies
headers
request params
request body
query parameters
response body
```

For example, refresh-token cookies may eventually be set in the controller layer or a dedicated HTTP response helper, depending on our final architecture.

The important part is:

> Don't put cookie mechanics into your repository.

---

# 13. What should NOT be in a controller?

Avoid:

```text
❌ User.findOne()
❌ User.create()
❌ bcrypt.hash()
❌ bcrypt.compare()
❌ JWT business logic
❌ complex authorization rules
❌ database transactions
❌ email business workflow
❌ large validation/business workflows
```

Instead:

```text
Controller
    ↓
Service
```

---

# 14. Controller and validation

There's an important distinction here.

Request validation usually happens **before** the controller:

```text
Request
   ↓
Validation Middleware
   ↓
Controller
```

For example:

```text
POST /auth/signup
        ↓
validateSignup
        ↓
signupController
        ↓
authService.signup()
```

So the controller can assume the request has passed the schema validation.

Your roadmap places validation in the middleware/validation layer rather than making controllers responsible for all validation logic.

---

# 15. Don't validate everything manually inside controllers

Bad:

```js
if (!req.body.email) {
    return res.status(400)...
}

if (!req.body.password) {
    return res.status(400)...
}

if (req.body.password.length < 8) {
    return res.status(400)...
}

// 50 more lines...
```

Better:

```text
Request
   ↓
Zod/Joi/etc.
   ↓
Validated request
   ↓
Controller
   ↓
Service
```

This keeps the controller focused.

---

# 16. Controller + asyncHandler

You already have an error architecture from earlier phases.

So instead of manually writing:

```js
try {
    ...
} catch (error) {
    next(error);
}
```

around every controller, we can use:

```js
export const signup = asyncHandler(
    async (req, res) => {
        const result =
            await authService.signup(req.body);

        return res.status(201).json({
            success: true,
            data: result,
        });
    }
);
```

Then errors flow into the centralized error middleware.

---

# 17. Why this is powerful

Suppose service throws:

```js
throw new AppError(
    "Invalid credentials",
    401
);
```

The controller doesn't need:

```js
try {
   ...
} catch {
   ...
}
```

Instead:

```text
Controller
    ↓
Service
    ↓
throws AppError
    ↓
asyncHandler
    ↓
Global Error Middleware
    ↓
HTTP 401
```

This is exactly why centralized error handling makes controllers much cleaner.

# 21. A very important pattern

Look at this:

```text
Controller:
"Here is the input."

Service:
"Here's what the application should do."

Repository:
"Here's how I access the data."

Model:
"Here's what the data looks like."
```

This is one of the most useful mental models in backend development.

---

# 22. Params vs body vs query

Controllers are responsible for extracting these HTTP inputs.

### Body

```js
const { title } = req.body;
```

### Params

```js
const { todoId } = req.params;
```

### Query

```js
const { page, limit } = req.query;
```

### Authenticated user

```js
const userId = req.user.id;
```

Then convert them into service input:

```js
await todoService.updateTodo({
    todoId,
    userId,
    title,
});
```

That's clean.

---

# 23. Don't pass `req` to services

Avoid:

```js
await todoService.updateTodo(req);
```

Why?

Because now your service knows about Express.

Instead:

```js
await todoService.updateTodo({
    todoId: req.params.todoId,
    userId: req.user.id,
    title: req.body.title,
});
```

Now the service is framework-independent.

---

# 24. Don't pass `res` to services

Never:

```js
await authService.login(req, res);
```

The service should return a result or throw an error.

Then:

```text
Service
 ↓
result
 ↓
Controller
 ↓
res.json()
```

This makes the service reusable.

---

# 25. Example — Get User

Suppose:

```text
GET /api/v1/users/:userId
```

Controller:

```js
export const getUser = asyncHandler(
    async (req, res) => {
        const { userId } = req.params;

        const user =
            await userService.getUserById(userId);

        return res.status(200).json({
            success: true,
            data: user,
        });
    }
);
```

Service:

```js
export const getUserById = async (userId) => {
    const user =
        await userRepository.findUserById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Repository:

```js
export const findUserById = async (userId) => {
    return User.findById(userId);
};
```

Beautiful separation.

# 27. Controller shouldn't know MongoDB

Imagine replacing MongoDB later with PostgreSQL.

If your controller contains:

```js
User.findById(...)
```

you have a problem.

If your controller contains:

```js
userService.getUserById(...)
```

nothing changes.

That's the benefit of layering.

---

# 28. Controller shouldn't know bcrypt

Similarly, don't do:

```js
bcrypt.compare(...)
```

inside the controller.

The controller only needs:

```js
authService.login(...)
```

Whether the service uses:

```text
bcrypt
argon2
another password system
```

isn't the controller's concern.

---

# 29. Controller shouldn't know JWT implementation

Same idea.

Don't:

```js
jwt.sign(...)
```

inside the controller.

The service handles token creation.

The controller receives the application result.

---

# 30. Controller as a thin layer

A common backend design goal is:

> **Thin controllers, meaningful services.**

Think:

```text
Controller
   ↓
10–20 lines
```

while:

```text
Service
   ↓
business workflow
```

This doesn't mean controllers can never be longer.

It means they shouldn't become the place where your entire application lives.

---

# 31. A practical controller structure

I recommend:

```js
import * as authService
    from "../services/auth.service.js";

import { asyncHandler }
    from "../middlewares/async-handler.js";

export const signup = asyncHandler(
    async (req, res) => {
        const result =
            await authService.signup(req.body);

```

Simple and readable.

# 32. Should controllers catch errors?

Generally:

```text
No.
```

Not when you already have:

```text
asyncHandler
+
global error middleware
```

So:

```js
try {
   ...
} catch (error) {
   next(error);
}
```

is unnecessary repetitive code.

Instead:

```js
const controller = asyncHandler(async (...) => {
    ...
});
```

Much cleaner.

Examples:

### Create


### Successful request


# 41. One subtle point: Controllers can coordinate HTTP-specific things

Suppose login returns:

```js
{
    accessToken,
    refreshToken
}
```

Maybe we don't want the refresh token in JSON.

The controller could do:

```js
res.cookie(
    "refreshToken",
    result.refreshToken,
    cookieOptions
);
```

and return only:

```js
{
    success: true,
    data: {
        accessToken: result.accessToken
    }
}
```

That cookie operation is HTTP-specific, so it belongs at the HTTP boundary.

The exact authentication/cookie architecture will be refined later in Phase 25.

# 42. Controller responsibility test

Whenever you're unsure where code belongs, ask:

### Does this code use `req`, `res`, headers, cookies, params or HTTP status?

```text
→ Controller
```

### Does this code decide what the application should do?

```text
→ Service
```

### Does this code execute database queries?

```text
→ Repository
```

### Does this code define database fields/schema/indexes?

```text
→ Model
```

This little test will save you a lot of confusion.

# 45. Interview questions

You should now be comfortable answering:

### What is a controller?

> The HTTP boundary that receives requests, calls application services, and sends HTTP responses.

### What should a controller contain?

```text
Request extraction
Service call
HTTP response
```

### Should controllers contain business logic?

Generally no.

### Should controllers directly query MongoDB?

No.

### Should controllers hash passwords?

No.

### Should controllers generate JWTs?

No.

### Should services receive `req` and `res`?

Generally no.

### Why should controllers be thin?

Because business logic should remain reusable, testable, and independent from HTTP.

## 🔑 Final takeaway

> **A controller should be boring.**

That's actually a compliment.

A good controller should mostly look like:

```js
export const createSomething = asyncHandler(
    async (req, res) => {
        const result =
            await somethingService.create({
                ...req.body,
                userId: req.user.id,
            });

        return res.status(201).json({
            success: true,
            data: result,
        });
    }
);
```

The interesting work happens in the **service**.

The database work happens in the **repository**.

The database structure lives in the **model**.

So our architecture is now:

```text
                HTTP
                 │
                 ▼
            Controller
           "HTTP work"
                 │
                 ▼
             Service
        "Business decisions"
                 │
                 ▼
           Repository
          "DB operations"
                 │
                 ▼
              Model
          "Data structure"
                 │
                 ▼
             MongoDB
```

That is the core controller architecture you should carry into the next lessons.
