# 1. What is a Route?

Suppose the client sends:

```http
POST /api/v1/users
```

Express needs to know:

> "Which function should handle this request?"

That's what the route does.

```js
router.post(
    "/users",
    userController.createUser
);
```

Think of it as:

```text
POST /users
     ↓
createUser()
```

---

# 2. Route vs Controller

This distinction is very important.

### Route

Answers:

> **Which handler should receive this request?**

### Controller

Answers:

> **What should we do with this HTTP request?**

So:

```text
Route
  ↓
Controller
```

For example:

```js
router.post(
    "/users",
    userController.createUser
);
```

The route says:

```text
POST /users
→ createUser controller
```

The controller then says:

```js
const user =
    await userService.createUser(req.body);
```

# 4. Why do we separate Routes?

Imagine putting everything into `app.js`:

```js
app.post("/signup", ...);
app.post("/login", ...);
app.get("/users", ...);
app.get("/users/:id", ...);
app.patch("/users/:id", ...);
app.delete("/users/:id", ...);
app.post("/todos", ...);
app.get("/todos", ...);
```

It quickly becomes difficult to manage.

Instead:

```text
routes/
├── auth.routes.js
├── user.routes.js
└── todo.routes.js
```

Now each file owns a particular area of the API.

# 5. `auth.routes.js`

For example:

```js
import { Router } from "express";

import * as authController
    from "../controllers/auth.controller.js";

const router = Router();

router.post(
    "/signup",
    authController.signup
);

router.post(
    "/login",
    authController.login
);

export default router;
```

Notice what isn't here:

```text
❌ MongoDB query
❌ Password hashing
❌ JWT generation
❌ Business logic
```

The route simply connects:

```text
URL + HTTP method
        ↓
controller
```

# 6. Mounting the route

Now `app.js` can mount the route:

```js
import authRoutes
    from "./routes/auth.routes.js";

app.use(
    "/api/v1/auth",
    authRoutes
);
```

This creates:

```text
/api/v1/auth
```

as the base path.

Therefore:

```js
router.post("/signup", ...)
```

becomes:

```text
POST /api/v1/auth/signup
```

And:

```js
router.post("/login", ...)
```

becomes:

```text
POST /api/v1/auth/login
```

# 7. Why use a Router?

Express provides:

```js
Router()
```

which lets us create a small routing module.

Example:

```js
const router = Router();
```

Then:

```js
router.get(...);
router.post(...);
router.patch(...);
router.delete(...);
```

This keeps route definitions organized.

---

# 8. HTTP methods belong to routes

The route defines the HTTP method.

### GET

```js
router.get("/users", getUsers);
```

### POST

```js
router.post("/users", createUser);
```

### PATCH

```js
router.patch("/users/:id", updateUser);
```

### DELETE

```js
router.delete("/users/:id", deleteUser);
```

Think:

```text
GET     → retrieve
POST    → create
PATCH   → partially update
DELETE  → delete
```

# 9. Route parameters

Suppose:

```text
GET /api/v1/users/123
```

Route:

```js
router.get(
    "/users/:userId",
    userController.getUser
);
```

Express gives the controller:

```js
req.params.userId
```

which is:

```text
123
```

So:

```text
/users/:userId
       ↑
    parameter
```

---

# 10. Query parameters

Suppose:

```text
GET /api/v1/users?page=2&limit=10
```

The route might simply be:

```js
router.get(
    "/users",
    userController.getUsers
);
```

The controller can access:

```js
req.query.page
req.query.limit
```

Routes don't need to manually process every query parameter.

---

# 11. Middleware belongs in the route chain

This is where routes become more powerful.

Suppose:

```text
GET /api/v1/users/me
```

requires authentication.

We can write:

```js
router.get(
    "/me",
    authenticate,
    userController.getMe
);
```

The execution becomes:

```text
Request
   ↓
authenticate
   ↓
getMe controller
```

---

# 12. Multiple middleware

You can have:

```js
router.post(
    "/users",
    authenticate,
    validateCreateUser,
    userController.createUser
);
```

Execution:

```text
Request
   ↓
authenticate
   ↓
validateCreateUser
   ↓
createUser controller
```

This is extremely useful.

---

# 13. Middleware order matters

This:

```js
router.post(
    "/users",
    authenticate,
    validateCreateUser,
    controller
);
```

is not necessarily equivalent to:

```js
router.post(
    "/users",
    validateCreateUser,
    authenticate,
    controller
);
```

Why?

Because middleware runs in order.

```text
1 → authenticate
2 → validate
3 → controller
```

or:

```text
1 → validate
2 → authenticate
3 → controller
```

You should deliberately choose the order.

# 15. Public vs protected routes

Public:

```js
router.post(
    "/login",
    authController.login
);
```

Protected:

```js
router.get(
    "/me",
    authenticate,
    authController.getMe
);
```

So:

```text
/login
   → public

/me
   → authenticated
```

# 19. Why `/api/v1`?

Your architecture uses versioned API paths:

```text
/api/v1/...
```

For example:

```text
/api/v1/auth
/api/v1/users
/api/v1/todos
```

This gives you room to introduce:

```text
/api/v2/...
```

later without immediately breaking existing clients.

Your roadmap specifically includes `/api/v1` architecture and API versioning as part of the broader API architecture.

# 21. A route should be boring

Just like the controller should be thin, routes should be simple.

Good:

```js
router.post(
    "/signup",
    validateSignup,
    authController.signup
);
```

Bad:

```js
router.post("/signup", async (req, res) => {
    const user = await User.findOne(...);

    if (...) {
        ...
    }

    const hash = await bcrypt.hash(...);

    ...
});
```

Now your route is doing:

```text
routing
validation
business logic
database
password hashing
response
```

That's exactly what we're trying to avoid.

# 22. Route vs Controller vs Service

This is worth memorizing:

|Layer|Main question|
|---|---|
|Route|**Where does this request go?**|
|Middleware|**Can/how should this request proceed?**|
|Controller|**How do I handle HTTP?**|
|Service|**What should the application do?**|
|Repository|**How do I access the data?**|
|Model|**What does the data look like?**|

So:

```text
POST /todos
     ↓
Route
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Model
```

# 23. Route naming

Prefer resource-oriented URLs.

Good:

```text
GET    /users
GET    /users/:id
POST   /users
PATCH  /users/:id
DELETE /users/:id
```

Avoid unnecessarily action-heavy URLs such as:

```text
GET /getAllUsers
POST /createUser
POST /deleteUser
```

The HTTP method already communicates the operation.

# 25. Don't authenticate login

This would be wrong:

```js
router.post(
    "/login",
    authenticate,
    authController.login
);
```

Why?

The user is trying to **become authenticated**.

They don't have a valid access token yet.

So:

```text
/signup → public
/login  → public
```

while:

```text
/me
/logout
/change-password
```

typically require authentication.

# 29. Think of Routes as a Map

This is probably the easiest analogy.

Imagine your backend is a large building:

```text
/api/v1/auth
/api/v1/users
/api/v1/todos
```

The route system is the **reception desk**.

Someone arrives and says:

> "I want `/api/v1/todos/123`."

The route says:

```text
"Okay, Todo section."
```

Then:

```text
authentication
      ↓
controller
      ↓
service
```

The route doesn't solve the user's problem.

It simply sends the request to the right place.

# 30. Common mistakes

### ❌ Business logic inside routes

```js
router.post("/", async (req, res) => {
    // 100 lines...
});
```

Move it into the service/controller architecture.

---

### ❌ Database queries inside routes

```js
router.get("/", async (req, res) => {
    const users = await User.find();
});
```

Avoid this.

---

### ❌ Giant `app.js`

Don't make:

```text
app.js
  ↓
500 lines of routes
```

Instead:

```text
app.js
 ↓
route modules
```

---

### ❌ Incorrect middleware order

Remember:

```text
middleware executes from left → right
```

---

### ❌ Mixing resource routes

Don't create one giant:

```text
routes.js
```

with hundreds of unrelated routes.

Prefer:

```text
auth.routes.js
user.routes.js
todo.routes.js
```

# 32. Interview questions

### What is a route?

A mapping between an HTTP method/path and the middleware/controller chain that handles it.

### Route vs controller?

```text
Route      → decides where the request goes
Controller → handles the HTTP operation
```

### Can a route have multiple middleware?

Yes.

```js
router.post(
    "/",
    authenticate,
    validate,
    controller
);
```

### Does a route contain business logic?

Generally no.

### Why use `express.Router()`?

To modularize and organize routes.

### Why use `/api/v1`?

To provide an explicit API version boundary.
