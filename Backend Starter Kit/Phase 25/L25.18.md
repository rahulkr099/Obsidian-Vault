# 1. What is Authentication?

Authentication answers:

> **"Who are you?"**

For example:

```text
Client
  ↓
Email + Password
  ↓
Backend
  ↓
Verify credentials
  ↓
User identified
```

Authorization is different.

```text
Authentication
→ Who are you?

Authorization
→ What are you allowed to do?
```

Your roadmap intentionally puts authentication before authorization.

# 5. Passwords must never be stored directly

Suppose the user sends:

```json
{
  "email": "rahul@example.com",
  "password": "MyPassword123"
}
```

Never store:

```text
password:
"MyPassword123"
```

Instead:

```text
"MyPassword123"
       ↓
 password hashing
       ↓
"$2b$12$...."
       ↓
 MongoDB
```

So our database contains a password hash, not the original password.

---

# 6. Hashing vs encryption

This distinction is extremely important.

### Encryption

```text
plain text
    ↓
encryption
    ↓
encrypted text
    ↓
can be decrypted
```

### Password hashing

```text
password
    ↓
hash
    ↓
password hash
    ↓
not reversibly decrypted
```

For passwords, we want **hashing**, not reversible encryption.

# 8. Password comparison

We don't do:

```js
if (password === user.password)
```

because:

```text
password
≠
password hash
```

Instead:

```text
User password
      +
Stored password hash
      ↓
Password comparison
      ↓
true / false
```

For example, using bcrypt:

```js
const valid = await bcrypt.compare(
    password,
    user.password
);
```

If false:

```js
throw new AppError(
    "Invalid credentials",
    401
);
```

---

# 9. Don't reveal which credential failed

Avoid responses such as:

```text
Email does not exist
```

and:

```text
Wrong password
```

Instead use:

```text
Invalid credentials
```

for both cases.

Why?

Because otherwise attackers can discover which email addresses are registered.

# 10. Access Token

After successful login, we need a way for the client to prove:

> "I already authenticated."

That's where the access token comes in.

Your roadmap defines the access token as:

```text
ACCESS TOKEN
Short-lived
Used for API authorization
```

Conceptually:

```text
Login
  ↓
Access Token
  ↓
API requests
```

---

# 11. Example access-token flow

Login:

```text
POST /auth/login
```

Response:

```text
Access Token
```

Then:

```text
GET /api/v1/users/me
Authorization: Bearer <access-token>
```

The backend:

```text
Bearer token
      ↓
verify token
      ↓
identify user
      ↓
req.user
      ↓
controller
```

---

# 12. Access tokens should be short-lived

Why?

Suppose an attacker steals an access token.

If it lasts:

```text
30 days
```

the attacker potentially has access for a long time.

Instead, access tokens are generally short-lived.

Conceptually:

```text
Access token
    ↓
short lifetime
    ↓
expires
```

Then the refresh-token mechanism can be used to obtain a new access token.

---

# 13. Refresh Token

The second token is the refresh token.

Your roadmap describes it as:

```text
REFRESH TOKEN
Long-lived
Used to obtain a new access token
```

So:

```text
Access Token
→ access APIs

Refresh Token
→ obtain new access token
```

This separation is extremely important.

---

# 14. Why two tokens?

Imagine:

```text
Access Token
expires in 15 minutes
```

If we had no refresh token, the user would need to log in every 15 minutes.

That's terrible UX.

Instead:

```text
Login
 │
 ├── Access Token ──────→ API
 │
 └── Refresh Token ─────→ Get new access token
```

So the user can remain logged in while the access token stays short-lived.

---

# 15. Recommended token storage

Your roadmap recommends:

```text
Access Token
    ↓
Authorization header

Refresh Token
    ↓
HttpOnly cookie
```

So:

```text
Access token
Authorization: Bearer <token>
```

and:

```text
Refresh token
HttpOnly cookie
```

The `HttpOnly` property helps prevent JavaScript from directly reading the cookie.

# 17. Where should token generation happen?

Not the controller.

Avoid:

```js
export const login = async (req, res) => {
    const token = jwt.sign(...);
};
```

Instead:

```text
Controller
    ↓
authService.login()
    ↓
token utility
```

The service coordinates the authentication operation.

---

# 18. Token utility

A clean architecture can have:

```text
utils/
├── token.util.js
└── password.util.js
```

For example:

```js
export const generateAccessToken = (payload) => {
    return jwt.sign(
        payload,
        process.env.ACCESS_TOKEN_SECRET,
        {
            expiresIn: "15m",
        }
    );
};
```

The exact expiration values should come from your environment/configuration rather than being scattered throughout the application.

---

# 19. What should go inside the token?

Don't put sensitive information inside a JWT.

A token might contain:

```json
{
  "sub": "user-id",
  "role": "user"
}
```

The `sub` claim can identify the user.

Avoid putting things like:

```text
password
password hash
refresh token
private information
```

inside the token.

Remember:

> A signed JWT is not automatically secret/encrypted.

# 21. `auth.middleware.js`

Conceptually:

```js
export const authenticate = async (
    req,
    res,
    next
) => {
    // get Authorization header

    // extract Bearer token

    // verify token

    // identify user

    // attach user to req

    next();
};
```

The middleware doesn't perform the business operation.

It answers:

> **"Is this request authenticated?"**

The header looks like:

```

      │
      ▼

      │

```

Middleware extracts the JWT.

# 23. Token verification

The middleware verifies:

```text
Is the token valid?
```

Possible outcomes:

```text
Valid
 ↓
continue

Invalid
 ↓
401 Unauthorized
```

Expired:

```text
Expired
 ↓
401 Unauthorized
```

Missing:

```text
Missing token

401 Unauthorized
```

# 24. `req.user`

After successful authentication:

```js
req.user = {
    id: decoded.sub,
    role: decoded.role,
};
```

Then:

```text
authenticate
     ↓
req.user
     ↓
controller
```

For example:

```js
export const getMe = asyncHandler(
    async (req, res) => {
        const user =
            await userService.getUserById(
                req.user.id
            );

        return res.json({
            success: true,
            data: user,
        });
    }
);
```

---

# 25. Why attach `req.user`?

Without middleware, every controller would need to:

```text
read token
verify token
decode token
find user
```

That's repetitive.

Instead:

```text
Authentication middleware
        ↓
req.user
        ↓
all protected controllers
```

Much cleaner.

The difference is:

```text

/me

```

# 28. Refresh flow

Eventually the access token expires.

Client sends:

```text
POST /auth/refresh
```

The refresh token is provided through the appropriate secure cookie mechanism.

Flow:

```text
Refresh request
      ↓
Read refresh token
      ↓
Verify refresh token
      ↓
Validate stored token state
      ↓
Generate new access token
      ↓
Possibly rotate refresh token
      ↓
Return new authentication result
```

Your broader authentication roadmap explicitly includes refresh-token hashing and rotation.

---

# 29. Why hash refresh tokens?

This is an important security improvement.

Imagine MongoDB contains:

```text
refreshToken:
"eyJhbGciOi..."
```

If your database is compromised, the attacker may obtain usable refresh tokens.

Instead:

```text
Refresh Token
      ↓
Hash
      ↓
Database
```

Your roadmap specifically includes:

```text
Refresh token hashing
Refresh token rotation
```

So the database stores a hash rather than the raw refresh token.

---

# 30. Refresh token rotation

Suppose:

```text
Refresh Token A
```

is used.

Instead of continuing to accept A forever:

```text
A
 ↓
used
 ↓
invalidate A
 ↓
issue B
```

Now:

```text
A → invalid
B → valid
```

This reduces the impact of stolen/replayed refresh tokens.

---

# 31. Logout

Logout should invalidate the server-side refresh-token state.

Conceptually:

```text
POST /auth/logout
       ↓
authenticate/identify session
       ↓
authService.logout()
       ↓
invalidate refresh token
       ↓
clear cookie
```

The controller handles HTTP cookie cleanup.

The service handles the application-level logout operation.

# 32. Authentication vs Authorization

This distinction is essential.

### Authentication

```text

```

Example:

```text

 ↓

```

### Authorization

```text
What can user 123 do?
```

Example:

```text

```

Then:

```text
Can user 123 delete this resource?
```

# 38. Important security rules

For our starter, keep these rules in mind:

```text
✓ Never store plaintext passwords
✓ Never return password hashes
✓ Use short-lived access tokens
✓ Protect refresh tokens carefully
✓ Prefer HttpOnly cookies for refresh tokens
✓ Don't put secrets inside JWT payloads
✓ Use generic login errors
✓ Validate authentication input
✓ Invalidate refresh-token state on logout
✓ Rotate refresh tokens where appropriate
✓ Keep authentication logic in services/middleware
```

These are consistent with the authentication architecture in your roadmap, particularly its emphasis on password hashing, access/refresh tokens, secure cookies, refresh-token hashing, and rotation.

---

### Mistake 3

Putting the entire user object in the JWT.

Avoid sensitive information.

# 41. Interview questions

### What is authentication?

Verifying the identity of a user.

### What is an access token?

A short-lived credential used to access protected APIs.

### What is a refresh token?

A longer-lived credential used to obtain new access tokens.

### Where should password hashing happen?

In the authentication/business logic layer, coordinated by the authentication service.

### Where should JWT verification happen?

Authentication middleware for protected requests.

### What does `req.user` represent?

The authenticated user's identity/context established by authentication middleware.

### Why use two token types?

To keep API access short-lived while allowing a longer-lived authenticated session.

### Authentication vs authorization?

```text
Authentication → Who are you?
Authorization  → What can you do?
```

## 🔑 Final takeaway

**Authentication is not one function.**

It is an architecture:

```text
Signup
  ↓
Password hashing
  ↓
Login
  ↓
Access token + refresh token
  ↓
Authentication middleware
  ↓
Protected routes
  ↓
Logout / token invalidation
```

And each part has a home:

```text
Validation      → validation layer
HTTP            → controller
Business logic  → auth service
Database        → repository
Password hash   → password utility/service
JWT creation    → token utility
JWT verification→ authentication middleware
User data       → model
```

Your source's Phase 25 sequence deliberately puts **Authentication immediately after Routes and before Authorization**, because now we have all the architectural layers necessary to build authentication cleanly.
