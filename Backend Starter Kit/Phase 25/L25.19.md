# Lesson 25.19 — Authorization

Now that **25.18 Authentication** is complete, we can answer the second security question:

> **"The user is authenticated — but what is this user allowed to do?"**

Your Phase 25 roadmap places **Authorization immediately after Authentication**, and the broader roadmap specifically focuses on roles, RBAC, permissions, resource ownership, and preventing horizontal/vertical privilege escalation.

---

## 1. Authentication vs Authorization

This distinction must become automatic in your mind.

### Authentication

```text
Who are you?
```

Example:

```text
JWT
 ↓
userId = 123
```

### Authorization

```text
What are you allowed to do?
```

Example:

```text
userId = 123
role = user

Can user 123 delete user 456?
→ No
```

So:

```text
Authentication
      ↓
Identity

Authorization
      ↓
Permissions
```

# 2. The request flow

We now have:

```text
Request
   ↓
Route
   ↓
Authentication Middleware
   ↓
req.user
   ↓
Authorization
   ↓
Controller
   ↓
Service
   ↓

   ↓

```

Authentication establishes:

```js
req.user = {
    id: "...",
    role: "user"
};
```

Authorization uses that information.

# 3. The easiest example

Imagine two users:

```text
Rahul
User ID: 101

Amit
User ID: 202
```

Rahul owns:

```text
Todo A
```

Amit owns:

```text
Todo B
```

Rahul requests:

```http
DELETE /api/v1/todos/B
```

Authentication says:

```text
✅ Rahul is logged in.
```

Authorization says:

```text
❌ Rahul doesn't own Todo B.
```

Therefore:

```text
403 Forbidden
```

That's authorization.

---

# 4. Authentication doesn't automatically give permission

This is a very common beginner mistake.

You might have:

```js
authenticate
```

and think:

> "The request is protected, so it's safe."

Not necessarily.

This:

```js
router.delete(
    "/todos/:todoId",
    authenticate,
    todoController.deleteTodo
);
```

only establishes:

```text
"This is a logged-in user."
```

It doesn't necessarily establish:

```text
"This user owns this Todo."
```

We need authorization logic too.

---

# 5. Roles

One common authorization mechanism is a **role**.

For example:

```text
user
admin
```

A user might have:

```js
{
    id: "123",
    role: "user"
}
```

An admin:

```js
{
    id: "456",
    role: "admin"
}
```

Now we can define:

```text
user
 → normal operations

admin
 → administrative operations
```

This is the beginning of **RBAC — Role-Based Access Control**.

---

# 6. RBAC

RBAC means:

> **Permissions are assigned through roles.**

Conceptually:

```text
User
  ↓
Role
  ↓
Permissions
```

For example:

```text
user
 ├── todo:create
 ├── todo:read
 ├── todo:update-own
 └── todo:delete-own
```

Admin:

```text
admin
 ├── todo:create
 ├── todo:read
 ├── todo:update
 ├── todo:delete
 ├── user:read
 ├── user:update
 └── user:delete
```

Your broader authorization roadmap explicitly progresses from roles → role middleware → RBAC → permissions → ownership.

---

# 7. Role middleware

A simple authorization middleware could look conceptually like:

```js
export const requireRole = (...roles) => {
    return (req, res, next) => {
        if (!roles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden",
            });
        }

        next();
    };
};
```

Then:

```js
router.delete(
    "/users/:userId",
    authenticate,
    requireRole("admin"),
    userController.deleteUser
);
```

Flow:

```text
Request
   ↓
authenticate
   ↓
req.user
   ↓
requireRole("admin")
   ↓
controller
```

---

# 8. Why authentication comes first

Notice:

```js
requireRole("admin")
```

needs:

```js
req.user.role
```

Where does `req.user` come from?

Authentication middleware.

Therefore:

```js
authenticate,
requireRole("admin"),
controller
```

is correct.

Not:

```js
requireRole("admin"),
authenticate,
controller
```

because the role middleware doesn't yet know who the user is.

---

# 9. `401` vs `403`

This is very important.

### `401 Unauthorized`

Usually means:

```text
You are not authenticated.
```

Examples:

```text
No token
Invalid token
Expired token
```

### `403 Forbidden`

Means:

```text
We know who you are,
but you aren't allowed to do this.
```

Example:

```text
Authenticated user
+
role = user
+
admin-only endpoint
=
403
```

Think:

```text
401 → Who are you?
403 → I know who you are, but no.
```

# 10. Admin route

Suppose:

```text
DELETE /api/v1/users/:userId
```

Only admins should be allowed.

Route:

```js
router.delete(
    "/:userId",
    authenticate,
    requireRole("admin"),
    userController.deleteUser
);
```

Now:

```text
Anonymous
    ↓
401

Logged-in user
    ↓
403

Admin
    ↓
Controller
```

That's clean.

---

# 11. But role checks aren't enough

Here's the important part.

Suppose Rahul is a normal user and requests:

```text
DELETE /todos/123
```

The endpoint allows:

```text
user
```

So:

```text
requireRole("user")
```

passes.

But what if Todo `123` belongs to Amit?

We still have a security problem.

This is called **resource ownership authorization**.

---

# 12. Resource ownership

Suppose:

```text
Todo 123
ownerId = Amit
```

Rahul requests:

```text
DELETE /todos/123
```

We need to check:

```text
req.user.id === todo.ownerId
```

If:

```text
Rahul !== Amit
```

reject the request.

This is the concept your roadmap highlights with ownership-aware queries.

---

# 13. The dangerous repository query

Imagine:

```js
Todo.findById(todoId);
```

This finds:

```text
Todo 123
```

without caring who owns it.

That can be dangerous.

---

# 14. Ownership-aware query

Instead:

```js
Todo.findOne({
    _id: todoId,
    userId: userId,
});
```

Now MongoDB must find a Todo satisfying **both**:

```text
Todo ID = 123
AND
owner ID = authenticated user
```

This is much stronger.

Your source specifically calls out:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

as an important ownership pattern.

---

# 15. Why checking ownership only in the controller can be risky

You might do:

```js
const todo = await todoService.getTodo(todoId);

if (todo.userId !== req.user.id) {
    return res.status(403).json(...);
}
```

This can work, but it creates a dangerous habit if other code paths forget the check.

A stronger design is to make the data access itself ownership-aware:

```js
todoRepository.findByIdForUser(
    todoId,
    userId
);
```

which performs:

```js
Todo.findOne({
    _id: todoId,
    userId
});
```

Now ownership becomes part of the query boundary.

---

# 16. Authorization can exist at multiple layers

This is one of the more advanced concepts.

Authorization may involve:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
```

But they don't all perform the same type of authorization.

For example:

### Route

```text
Should this endpoint require authentication?
```

### Middleware

```text
Does this user have the required role?
```

### Service

```text
Is this operation allowed by the business rules?
```

### Repository

```text
Can this user's identity be included in the database query?
```

---

# 17. Example: Admin vs ownership

Imagine:

```text
Admin
```

can delete any Todo.

Normal users can delete only their own.

The service could implement the business rule:

```text
if admin:
    delete any Todo

if normal user:
    delete only owned Todo
```

Conceptually:

```js
if (user.role === "admin") {
    return todoRepository.deleteById(todoId);
}

return todoRepository.deleteByIdForUser(
    todoId,
    user.id
);
```

This is much more meaningful than simply checking:

```text
role === "user"
```

because ownership is also part of authorization.

---

# 18. Horizontal privilege escalation

This is one of the security issues your roadmap explicitly covers.

Imagine:

```text
User A
  ↓
Todo A

User B
  ↓
Todo B
```

User A changes the URL:

```text
/todos/A
```

to:

```text
/todos/B
```

and gets User B's Todo.

That's:

> **Horizontal privilege escalation.**

Same privilege level, but accessing another user's resources.

---

# 19. Vertical privilege escalation

Now imagine:

```text
user
```

changes a request to become:

```text
admin
```

For example:

```http
PATCH /users/123
```

with:

```json
{
    "role": "admin"
}
```

If your backend blindly accepts that:

```text
normal user
      ↓
admin
```

That's:

> **Vertical privilege escalation.**

The attacker moves upward to a more powerful privilege level.

---

# 20. Never blindly trust `role` from request body

Bad:

```js
const user = await User.findByIdAndUpdate(
    req.user.id,
    req.body
);
```

Suppose the request contains:

```json
{
    "name": "Rahul",
    "role": "admin"
}
```

Now you've potentially created an authorization vulnerability.

Instead, explicitly choose allowed fields:

```js
const updates = {
    name: req.body.name,
};
```

And administrative role changes should go through a dedicated, protected operation.

---

# 21. Permission-based authorization

Roles are useful, but larger applications may need more flexibility.

Instead of:

```text
admin
user
```

we can define permissions:

```text
todo:create
todo:read
todo:update
todo:delete
user:read
user:update
user:delete
```

Then:

```text
admin
 ↓
all permissions

user
 ↓
limited permissions
```

This is **permission-based authorization**.

Your roadmap explicitly includes this after RBAC fundamentals.

---

# 22. Why permissions can scale better

Imagine your application eventually has:

```text
admin
editor
moderator
support
manager
user
```

Hardcoding every route:

```js
requireRole("admin", "manager", "moderator")
```

can become messy.

Instead:

```text
Role
 ↓
Permissions
 ↓
Authorization decision
```

For example:

```text
editor
 ├── todo:read
 ├── todo:create
 └── todo:update

support
 ├── user:read
 └── user:update
```

Much more flexible.

For your MERN starter, we don't need a huge authorization framework.

# 24. `requireRole()` mental model

Don't memorize the implementation.

Understand the concept:

```text
requireRole("admin")
```

means:

> "Only continue if the authenticated user's role is `admin`."

So:

```text
req.user.role
      │
      ▼
   "admin"?
    /    \
  yes     no
   │       │
 next()   403
```

# 25. Route example

Admin-only:

```js
router.delete(
    "/:userId",
    authenticate,
    requireRole("admin"),
    userController.deleteUser
);
```

User-owned resource:

```js
router.delete(
    "/:todoId",
    authenticate,
    todoController.deleteTodo
);
```

The ownership check may happen in the service/repository rather than a simple role middleware.

That's important:

> **Not every authorization rule should become middleware.**

---

# 26. Why not create `requireOwner()` for everything?

You could create:

```js
requireOwner()
```

but ownership often requires knowing which resource is being accessed.

For example:

```text
/todos/:todoId
/users/:userId
/comments/:commentId
/orders/:orderId
```

Each resource may have a different ownership relationship.

So a service/repository often has better knowledge of the actual resource relationship.

---

# 27. Authorization inside the service

Example:

```js
export const updateTodo = async ({
    todoId,
    userId,
    title,
}) => {
    const todo =
        await todoRepository.findByIdForUser(
            todoId,
            userId
        );

    if (!todo) {
        throw new AppError(
            "Todo not found",
            404
        );
    }

    return todoRepository.update(
        todoId,
        { title }
    );
};
```

The important part:

```text
userId
 ↓
ownership-aware repository
```

The service controls the business operation.

# 28. Interesting security behavior

Notice something subtle.

Suppose Todo `123` belongs to Amit.

Rahul asks:

```text
GET /todos/123
```

The query:

```js
Todo.findOne({
    _id: "123",
    userId: "Rahul"
});
```

returns:

```text
null
```

Your API could respond:

```text
404 Not Found
```

instead of:

```text
403 Forbidden
```

This can be useful because it doesn't reveal whether another user's resource exists.

The exact choice depends on your API's security and product requirements.

# 29. Authorization is not just middleware

This is one of today's biggest lessons.

Beginners often think:

```text
Authorization = requireRole()
```

But real authorization can involve:

```text
Role
Permissions
Ownership
Resource state
Business rules
User identity
Tenant

```

For example:

```text

```

might depend on:

```text
authenticated?
+

+
owns organization?
+
invoice belongs to organization?
+
invoice still editable?
```

That's application-level authorization.

Never do this:

```text

 ↓

```

# 37. Common authorization mistakes

### Mistake 1 — Authentication without authorization

```text
User is logged in
→ therefore they can access everything
```

❌ Wrong.

---

### Mistake 2 — Only checking roles

```text
role === "user"
```

doesn't mean:

```text
user owns resource
```

---

### Mistake 3 — Trusting `req.body.userId`

Use:

```js
req.user.id
```

for authenticated identity.

---

### Mistake 4 — Trusting the frontend

UI restrictions aren't security.

---

### Mistake 5 — Updating arbitrary fields

Avoid:

```js
Model.findByIdAndUpdate(id, req.body)
```

for sensitive resources.

Explicitly allow fields.

---

### Mistake 6 — Forgetting ownership in queries

Avoid:

```js
Todo.findById(todoId);
```

when the operation should be user-specific.

Prefer:

```js
Todo.findOne({
    _id: todoId,
    userId,
});
```

This exact ownership pattern is emphasized in your roadmap.

# 40. Interview questions

### What is authorization?

Determining whether an authenticated identity is allowed to perform an action on a resource.

### What is RBAC?

Role-Based Access Control — permissions are associated with roles.

### What is `requireRole()`?

Middleware that allows the request to continue only when the authenticated user's role matches an allowed role.

### 401 vs 403?

```text
401 → authentication missing/invalid
403 → authenticated but not permitted
```

### What is horizontal privilege escalation?

A user accessing another user's resources at the same privilege level.

### What is vertical privilege escalation?

A user gaining a higher privilege level, such as becoming an admin.

### Why use ownership-aware queries?

To ensure the authenticated user can access only resources they are allowed to access.

