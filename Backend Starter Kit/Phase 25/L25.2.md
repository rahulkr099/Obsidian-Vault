# Lesson 25.2 — Configure Node

In **25.1**, we created the project and initialized npm.

Now we configure Node properly before adding Express, MongoDB, authentication, or anything else.

Our goal is simple:

```text
Node Project
     ↓
ES Modules
     ↓
Proper scripts
     ↓
Ready for backend development
```

This lesson is based on the starter architecture you're rebuilding in Phase 25.

---

# 1. Why configure Node?

Right now your `package.json` is basically:

```json
{
  "name": "mern-backend-starter",
  "version": "1.0.0"
}
```

Node doesn't yet know how we want our project to behave.

We want to configure:

```text
1. Module system
2. Development command
3. Production command
4. Testing command
```

The most important one today is the **module system**.

---

# 2. CommonJS vs ES Modules

Node has two major module systems.

### CommonJS

```js
const express = require("express");
```

and:

```js
module.exports = something;
```

### ES Modules

```js
import express from "express";
```

and:

```js
export default something;
```

For our starter, we'll use **ES Modules**.

So our code will look like:

```js
import express from "express";
```

rather than:

```js
const express = require("express");
```

---

# 3. Tell Node to use ES Modules

Open:

```text
package.json
```

Add:

```json
"type": "module"
```

So it becomes approximately:

```json
{
  "name": "mern-backend-starter",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "type": "module",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}
```

The important addition is:

```json
"type": "module"
```

---

# 4. What does `"type": "module"` actually do?

It tells Node:

> Treat `.js` files in this package as ES modules.

Therefore:

```js
import something from "something";
```

works naturally.

For example:

```js
import fs from "node:fs";
```

Instead of:

```js
const fs = require("fs");
```

---

# 5. Why are we choosing ES Modules?

Because we're going to build a large application with many separate files:

```text
controllers/
services/
repositories/
models/
routes/
middlewares/
utils/
```

ES Modules make the dependency relationship explicit:

```js
import userService from "../services/user.service.js";
```

and:

```js
export const createUser = async () => {
    // ...
};
```

This becomes very readable when the application grows.

---

# 6. Important Node rule: file extensions

With ES Modules, you'll commonly write:

```js
import userService from "../services/user.service.js";
```

Notice:

```text
.js
```

Don't write:

```js
import userService from "../services/user.service";
```

when using normal Node ESM resolution.

This is one of the common beginner mistakes.

We'll encounter this repeatedly when we start creating the architecture.


```text

```

This seems trivial.

But we're practicing an important engineering habit:

> **Verify the foundation before building on top of it.**

# 8. Test an actual ES Module import

Let's make the test slightly more meaningful.

Create:

```text
math.js
```

```js
export const add = (a, b) => {
    return a + b;
};
```

Then change `test.js`:

```js
import { add } from "./math.js";

console.log(add(10, 20));
```

Run:

```bash
node test.js
```

Expected:

```text
30
```

Now we've proven that:

```text
package.json
      ↓
"type": "module"
      ↓
import/export
      ↓
Node
```

works.

# 11. Configure npm scripts

Now let's prepare the commands we'll use throughout the project.

Open `package.json`.

Change:

```json
"scripts": {
  "test": "echo \"Error: no test specified\" && exit 1"
}
```

to:

```json
"scripts": {
  "dev": "node --watch server.js",
  "start": "node server.js",
  "test": "node --test"
}
```

For now, `server.js` doesn't exist.

That's okay.

We'll create it later.

---

# 12. What is the `dev` script?

This:

```json
"dev": "node --watch server.js"
```

means we can eventually run:

```bash
npm run dev
```

and Node will execute:

```bash
node --watch server.js
```

The `--watch` option tells Node to restart when watched files change.

So instead of repeatedly doing:

```bash
node server.js
```

after every change, Node can restart automatically.

---

# 13. What is the `start` script?

This:

```json
"start": "node server.js"
```

will eventually be our normal production startup command:

```bash
npm start
```

which is equivalent to:

```bash
node server.js
```

We'll understand why `server.js` exists separately from `app.js` later.

For now, remember:

```text
npm start
    ↓
node server.js
```

---

# 14. What about the test script?

We're temporarily using Node's built-in test runner:

```json
"test": "node --test"
```

So:

```bash
npm test
```

will eventually run our tests.

Later in the course, when we build the actual testing architecture, we'll decide whether the final starter should use Node's test runner or Jest based on the testing setup we're building.

Don't install testing dependencies just yet.

That's Lesson 25.22's job.

# 16. One important distinction: `app.js` vs `server.js`

We're going to use both.

This can initially feel strange.

### `app.js`

Will eventually create/configure Express:

```text
app.js
 ↓
Express application
 ↓
middleware
 ↓
routes
 ↓
error handling
```

### `server.js`

Will eventually start the actual process:

```text
server.js
 ↓
environment
 ↓
database connection
 ↓
app
 ↓
HTTP server
```

Conceptually:

```text
              app.js
                │
                ▼
        Express Application
                │
                │
              server.js
                │
                ▼
          HTTP Server
                │
                ▼
             Port 5000
```

This separation becomes extremely useful for testing.

We'll build it properly later.

---

# 17. Why not use `server.js` for everything?

You might think:

> "Why not just put Express and the server in one file?"

You absolutely can in a tiny project:

```js
import express from "express";

const app = express();

app.listen(5000);
```

But our goal isn't a tiny project.

We're building a reusable starter that will eventually contain:

```text
authentication
authorization
database
security
validation
logging
testing
Docker
email
```

So separation of responsibilities becomes valuable.

# 23. Common mistakes

### Mistake 1 — Forgetting `"type": "module"`

Then you may get errors around:

```js
import ...
```

or:

```js
export ...
```

---

### Mistake 2 — Forgetting `.js`

With our ESM setup:

```js
import userService from "../services/user.service.js";
```

is the safe pattern.

---

### Mistake 3 — Running `npm start` too early

We haven't created:

```text
server.js
```

yet.

So don't expect the application to start.

---

### Mistake 4 — Installing everything now

Don't do:

```bash
npm install express mongoose cors helmet ...
```

yet.

That's **Lesson 25.3**.

We're intentionally building in layers.
