# Lesson 25.20 — API Responses

We are now at **25.20: API Responses** in the graduation phase. Your roadmap explicitly places this after authentication/authorization and before logging.

The goal is simple:

> **Every API endpoint should communicate with the frontend using a predictable response structure.**

Your earlier architecture also defines this as the point where we create a consistent API response contract, including success responses, errors, pagination, request IDs, and `/api/v1` versioning.

---

# 1. The problem with inconsistent responses

Imagine your backend has three endpoints.

### Endpoint 1

```json
{
  "success": true,
  "data": {
    "id": "123",
    "name": "Rahul"
  }
}
```

### Endpoint 2

```json
{
  "user": {
    "id": "123",
    "name": "Rahul"
  }
}
```

### Endpoint 3

```json
[
  {
    "id": "123",
    "name": "Rahul"
  }
]
```

All three may work.

But the frontend developer now has to remember:

```text
Endpoint A → response.data
Endpoint B → response.user
Endpoint C → response directly
```

That's unnecessary complexity.

---

# 2. What is an API response contract?

An API response contract is an agreement between:

```text
Frontend
    ↕
Backend
```

about the shape of data being exchanged.

For example:

```json
{
  "success": true,
  "message": "User fetched successfully",
  "data": {}
}
```

Now React knows what to expect.

The idea from your roadmap is:

> **Every endpoint follows the same response contract.**

---

# 3. Think of API responses like a standard envelope

Imagine sending a parcel.

Instead of giving the receiver a random box every time, you use the same type of envelope:

```text
┌──────────────────────────────┐
│ success                      │
│ message                      │
│ data                         │
│ meta                         │
└──────────────────────────────┘
```

The contents can change, but the outer structure stays familiar.

# 5. A basic error response

Suppose the Todo doesn't exist.

```json
{
  "success": false,
  "message": "Todo not found"
}
```

Or, with a request ID:

```json
{
  "success": false,
```

---

# 6. HTTP status code still matters

Don't make this mistake:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

with:

```http
200 OK
```

A consistent JSON body **doesn't replace HTTP status codes**.

Use both:

```text
HTTP status
+
JSON response
```

For example:

```text
201 Created
```

for successful creation.

```text
200 OK
```

for successful retrieval.

```text
400 Bad Request
```

for invalid input.

```text
401 Unauthorized
```

for authentication failure.

```text
403 Forbidden
```

for authorization failure.

```text
404 Not Found
```

for a missing resource.

```text
409 Conflict
```

for conflicts such as duplicate email.

```text
500 Internal Server Error
```

for unexpected server errors.

---

# 7. Status code + response body

Think:

```text
                 API Response
                      │
             ┌────────┴────────┐
             ▼                 ▼
        HTTP status         JSON body
             │                 │
          201                 success
                            message
                              data
```

They solve different problems.

# 8. Why create `ApiResponse`?

Your starter roadmap specifically proposes:

```text
utils/ApiResponse.js
```

for this architecture.

Instead of writing this everywhere:

```js
return res.status(200).json({
    success: true,
    message: "User fetched successfully",
    data: user,
});
```

you can create a reusable response utility.

---

# 9. A simple `ApiResponse` class

For example:

```js
export class ApiResponse {
    constructor({
        statusCode = 200,
        message = "Success",
        data = null,
        meta = undefined,
    }) {
        this.success = statusCode < 400;
        this.statusCode = statusCode;
        this.message = message;
        this.data = data;

        if (meta !== undefined) {
            this.meta = meta;
        }
    }
}
```

Then:

```js
return res.status(200).json(
    new ApiResponse({
        statusCode: 200,
        message: "User fetched successfully",
        data: user,
    })
);
```

---

# 10. Why include `statusCode`?

You might wonder:

> "We're already sending the HTTP status. Why put it inside JSON?"

It's optional.

There are two common approaches.

### Approach A

Only HTTP status:

```http
200 OK
```

and:

```json
{
  "success": true,
  "message": "Success",
  "data": {}
}
```

### Approach B

Both:

```http
200 OK
```

and:

```json
{
  "success": true,
  "statusCode": 200,
  "message": "Success",
  "data": {}
}
```

Either can work.

For your starter, consistency is more important than blindly following one universal format.

---

# 11. Keep the response structure simple

Don't create something unnecessarily complicated like:

```json
{
  "response": {
    "result": {
      "payload": {
        "content": {}
      }
    }
  }
}
```

That's painful for frontend developers.

Prefer:

```json
{
  "success": true,
  "message": "Success",
  "data": {}
}
```

Simple wins.


# 14. Pagination needs `meta`

Now suppose:

```http
GET /api/v1/todos?page=2&limit=20
```

Returning only the records isn't enough.

Frontend may need:

```text
current page
total pages
total records
limit
has next page
has previous page
```

So:

```json
{
  "success": true,
  "message": "Todos fetched successfully",
  "data": [
    {
      "id": "1",
      "title": "Learn Node"
    }
  ],
  "meta": {
    "page": 2,
    "limit": 20,
    "total": 75,
    "totalPages": 4,
    "hasNextPage": true,
    "hasPreviousPage": true
  }
}
```

Your roadmap specifically includes pagination responses as part of API response architecture.

---

# 15. Why separate `data` and `meta`?

Because they represent different things.

```text
data
 ↓
Actual resources

meta
 ↓
Information about the response
```

For example:

```text
data
 → Todos

meta
 → pagination information
```

This separation is very useful.

# 16. Error responses

Let's establish a predictable error structure.

For example:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": []
}
```

Or:

```json
{
  "success": false,
  "message": "Email already exists"
}
```

Or:

```json
{
  "success": false,
  "message": "Authentication required"
}
```

The exact fields can vary slightly depending on the type of error, but the main contract should remain recognizable.

---

# 17. Validation errors

Suppose the client sends:

```json
{
  "email": "wrong",
  "password": "123"
}
```

You may want to return:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    {
      "field": "email",
      "message": "Invalid email"
    },
    {
      "field": "password",
      "message": "Password is too short"
    }
  ]
}
```

This is much better for a React frontend than:

```text
"Something went wrong"
```

---

# 18. Why `errors` is useful

React can do:

```text
errors.email
errors.password
```

and show the right message next to each field.

For example:

```text
Email
[ wrong@email ]

❌ Invalid email
```

and:

```text
Password
[ 123 ]

❌ Password is too short
```

Your backend becomes easier to consume.

---

# 19. Don't expose internal errors

Suppose MongoDB throws:

```text
MongoServerError: E11000 duplicate key error collection...
```

Don't necessarily return the raw error to the client.

Bad:

```json
{
  "success": false,
  "message": "MongoServerError: E11000 duplicate key..."
}
```

Instead:

```json
{
  "success": false,
  "message": "Email already exists"
}
```

Your error architecture should translate internal errors into safe API responses.

This fits directly with the earlier Phase 8 architecture around global error handling and hiding sensitive production errors.

# 20. Request IDs

This becomes especially powerful when combined with your logging architecture.

The frontend can tell you:

> "I got error `req_8a92f`."

```text

```

Your roadmap explicitly includes **request IDs** as part of the response architecture.

# 22. A response helper

Instead of a class, you can also create functions.

For example:

```js
export const sendSuccess = (
    res,
    {
        statusCode = 200,
        message = "Success",
        data = null,
        meta,
    }
) => {
    const response = {
        success: true,
        message,
        data,
    };

    if (meta !== undefined) {
        response.meta = meta;
    }

    return res.status(statusCode).json(response);
};
```

Then:

```js
return sendSuccess(res, {
    statusCode: 200,
    message: "User fetched successfully",
    data: user,
});
```

This is often easier to understand than creating a large abstraction.

# 24. Controller example

Suppose we have:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(
        req.params.userId
    );

    return res.status(200).json(
        new ApiResponse({
            statusCode: 200,
            message: "User fetched successfully",
            data: user,
        })
    );
});
```

The controller's responsibility is still HTTP.

It gets:

```text
req
```

calls:

```text
service
```

and produces:

```text
HTTP response
```

The service remains separate.

---

# 25. Don't put business logic into `ApiResponse`

This is important.

`ApiResponse` should not decide:

```text
whether user exists
whether user is admin
whether todo belongs to user
whether password is valid
```

It only formats the result.

Think:

```text
Service
 ↓
Business decision

ApiResponse
 ↓
Response formatting
```

---

# 26. Response utility vs service

Bad:

```js
class ApiResponse {
    async createUser() {
        ...
    }
}
```

That's mixing responsibilities.

Better:

```text
UserService
 ↓
creates user

ApiResponse
 ↓
formats HTTP response
```

# 32. Backward compatibility

Imagine your frontend expects:

```json
{
  "success": true,
  "data": {
    "name": "Rahul"
  }
}
```

Then suddenly you change it to:

```json
{
  "result": {
    "user": {
      "displayName": "Rahul"
    }
  }
}
```

You've potentially broken the frontend.

This is why an API response is a **contract**, not just a random JSON object.

Your roadmap explicitly includes backward compatibility after API versioning.

# 33. Don't over-standardize everything

Consistency is good.

But don't force every response into weird structures.

For example, don't turn:

```json

  "success": true,
  "data": []

```

Good API design is:

```text
Predictable
+
Simple
+
```

# 34. Common mistakes

### ❌ Different shape for every endpoint

```text
/users → data
/todos → results
/auth → user
```

Try to maintain a common contract.

---

### ❌ Always returning 200

Don't use:

```http
200 OK
```

for every failure.

Use meaningful HTTP status codes.

---

### ❌ Returning raw database errors

Don't expose internal implementation details.

---

### ❌ Returning sensitive data

Never accidentally return:

```json
{
  "passwordHash": "...",
  "refreshTokenHash": "..."
}
```

Your API response should contain only what the client actually needs.

---

### ❌ Putting response formatting inside services

Services should focus on business logic.

---

### ❌ Giant `ApiResponse` class

Keep the utility small.

# 35. Security consideration

API responses are also part of your security boundary.

Suppose your User document contains:

```text
_id
name
email
passwordHash
refreshTokenHash
role
```

Don't simply do:

```js
data: user
```

if `user` contains sensitive fields.

Instead return a safe representation:

```js
data: {
    id: user._id,
    name: user.name,
    email: user.email,
}
```

The response should expose **public application data**, not your database internals.

# 39. Interview questions

### What is an API response contract?

A predictable agreement describing how the backend communicates results and errors to clients.

### Why use a response envelope?

To make responses consistent and easier for clients to consume.

### Should API responses use HTTP status codes?

Yes. A JSON response body does not replace HTTP semantics.

### What is `meta`?

Additional information about the response, such as pagination information.

### Why use request IDs?

To connect a client-visible error with server-side logs.

### Should services return Express responses?

Generally no.

The service should return application results; the controller handles HTTP responses.

### Should database documents be returned directly?

Not blindly. Sensitive/internal fields should be excluded.
