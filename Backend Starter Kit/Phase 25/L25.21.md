# Lesson 25.21 — Logging

We are now at **25.21: Logging** in the final starter-building phase. Your source roadmap defines this lesson as the point where the starter should capture **request ID, method, path, status, duration, and user ID**, with the flow:

```text
Request
 ↓
requestId
 ↓
logger
 ↓
controller
 ↓
service
 ↓
response
 ↓
logger
```

The purpose is to make production debugging much easier.

This lesson is also the practical version of the earlier **Phase 19 — Logging & Observability**, which covers structured logging, log levels, request IDs, request/error logging, user context, sensitive data, Pino, production logging, health checks, readiness checks, and metrics.

---

# 1. What is logging?

Logging means:

> **Recording useful information about what your application is doing.**

For example:

```text
Server started
Database connected
User logged in
Request received
Todo created
Request failed
Database error
```

Without logs, production debugging becomes guesswork.

---

# 2. Imagine your backend is a black box

Suppose your production API suddenly returns:

```http
500 Internal Server Error
```

The frontend tells you:

> "The Todo API is broken."

You open your code.

But you don't know:

```text
Who made the request?
Which endpoint?
Which user?
What happened?
How long did it take?
Which database operation failed?
```

Logs answer these questions.

---

# 3. Logging vs `console.log()`

You've probably written:

```js
console.log("User created");
```

That's technically logging.

But production logging needs more structure.

Instead of:

```text
User created
```

you want something like:

```text
INFO
requestId=req_123
userId=user_456
method=POST
path=/api/v1/users
status=201
duration=84ms
message="User created"
```

Now the log is useful to both humans and machines.

---

# 4. Structured logging

This is one of the most important concepts from Phase 19.

Instead of creating random text:

```text
User Rahul created todo
```

record structured fields:

```json
{
  "level": "info",
  "requestId": "req_123",
  "userId": "user_456",
  "method": "POST",
  "path": "/api/v1/todos",
  "statusCode": 201,
  "durationMs": 84,
  "message": "Todo created"
}
```

Now a logging system can search:

```text
requestId = req_123
```

or:

```text
statusCode >= 500
```

or:

```text
userId = user_456
```

That's much more powerful.

---

# 5. Why request IDs matter

Imagine one request:

```text
POST /api/v1/todos
```

We assign:

```text
requestId = req_a91f
```

That same ID travels through the request:

```text
Request
   ↓
req_a91f
   ↓
middleware
   ↓
controller
   ↓
service
   ↓
repository
   ↓
response
```

If something fails:

```text
requestId=req_a91f
```

appears in the error response/log.

Your roadmap specifically identifies request IDs as a key part of logging and API responses.

# 6. Why request IDs are extremely useful

Suppose you have:

```text
10,000 requests/minute
```

and one request fails.

Without a request ID:

```text

```

Hard.

With:

```text

```

you search:

```text
req_abc123
```

and find the entire story.

# 9. What should we NOT log?

This is extremely important for security.

Never casually log:

```text
password
passwordHash
JWT
refresh token
session secrets
API keys
credit-card data
OTP
password-reset tokens
```

Bad:

```js
console.log(req.body);
```

Because `req.body` might contain:

```json
{
  "email": "user@example.com",
  "password": "SuperSecret123"
}
```

Now you've accidentally put a password into your logs.

Logs are sensitive data too.

---

# 10. Logging can become a security problem

Think about:

```text
Application
   ↓
Logs
   ↓
Log storage
   ↓
Developers / monitoring systems
```

If you log secrets, you've created another place where attackers could potentially obtain them.

So:

> **Never treat logging as harmless.**

Your Phase 19 roadmap explicitly includes **sensitive data in logs** as a dedicated lesson.

---

# 11. Log levels

A professional logger doesn't treat every message equally.

Common levels are:

```text
trace
debug
info
warn
error
fatal
```

The exact levels can vary by logger.

For your learning, understand the hierarchy.

### `debug`

Detailed information useful while developing.

```text
Database query parameters
```

### `info`

Normal application events.

```text
Server started
User logged in
Request completed
```

### `warn`

Something unusual but not necessarily fatal.

```text
Slow request
Retrying external service
```

### `error`

Something failed.

```text
Database operation failed
Unhandled application error
```

### `fatal`

The application cannot safely continue.

```text
Critical startup failure
```

---

# 12. Why log levels matter

Imagine production generates:

```text
1 million logs/day
```

You don't want every debug message.

You might configure:

```text
Development:
debug + info + warn + error

Production:
info + warn + error
```

So logging can be controlled by environment.

# 18. Request logging middleware

Now we can understand the request logger.

Conceptually:

```js
const loggerMiddleware = (req, res, next) => {
    const start = Date.now();

    res.on("finish", () => {
        const duration = Date.now() - start;

        logger.info({
            method: req.method,
            path: req.originalUrl,
            statusCode: res.statusCode,
            durationMs: duration,
            requestId: req.requestId,
        });
    });

    next();
};
```

Don't rush to memorize this.

Let's understand it line by line.

---

# 19. `Date.now()`

```js
const start = Date.now();
```

We record the start time.

Suppose:

```text
start = 10:30:00.000
```

The request finishes:

```text
10:30:00.087
```

So:

```text
duration = 87ms
```

This gives us request latency.

---

# 20. Why measure duration?

Suppose users say:

> "The API is slow."

You need evidence.

Logs might show:

```text
GET /todos → 32ms
GET /users → 41ms
GET /reports → 3400ms
```

Now you know:

```text
/report
```

needs investigation.

---

# 21. `res.on("finish")`

This means:

> Run this code when the HTTP response has finished.

So the flow is:

```text
Request starts
     ↓
start timer
     ↓
Application processes request
     ↓
Response finishes
     ↓
calculate duration
     ↓
log result
```

That's why request logging can capture the final status code.

---

# 22. Status code

We can get:

```js
res.statusCode
```

For example:

```text
200
201
400
401
403
404
500
```

Then the log tells us:

```json
{
  "statusCode": 404
}
```

instead of just:

```text
Request completed
```

---

# 23. User context

After authentication:

```js
req.user
```

may contain:

```js
{
    id: "123",
    role: "user"
}
```

Then the request log can include:

```text
userId = 123
```

This helps answer:

> "Which authenticated user made this request?"

But remember:

> Don't log more user information than necessary.

Usually a stable internal user ID is much better than logging an email or other personal information.

---

# 24. Middleware order matters

This is a very important connection with your previous lessons.

Suppose you have:

```text
requestId
logger
authentication
routes
```

The logger may execute before authentication.

So initially:

```text
req.user
=
undefined
```

But after authentication:

```text
req.user
=
user
```

If you want the **completed request log** to include the user ID, you can read `req.user` when the response finishes.

So:

```text
Request
 ↓
requestId
 ↓
logger starts timer
 ↓
authentication
 ↓
controller
 ↓
response
 ↓
logger reads req.user
```

That's a nice architecture.

# 25. Request ID middleware

We need to generate the request ID before logging.

Conceptually:

```js
const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    res.setHeader(
        "X-Request-ID",
        req.requestId
    );

    next();
};
```

Now:

```text
req.requestId
```

is available to the rest of the application.

---

# 31. Application logs vs request logs

Don't confuse them.

### Request log

Answers:

```text
What HTTP request happened?
```

Example:

```text
GET /todos → 200 → 31ms
```

### Application log

Answers:

```text
What did the application do?
```

Example:

```text
User verification email queued
```

### Error log

Answers:

```text
What failed?
```

Example:

```text
MongoDB connection timeout
```

You need all three.

# 32. Startup logging

Your server should log important startup events.

For example:

```text
Database connected
Server listening
```

Conceptually:

```js
logger.info("Database connected");

logger.info("Server started", {
    port: env.port,
});
```

So if production doesn't start correctly, you can inspect the startup logs.

---

# 33. Database logging

Be careful here.

You generally don't want to log every MongoDB query with all parameters in production.

Why?

Because:

```text
queries can contain sensitive information
```

and excessive database logs can become noisy and expensive.

Log meaningful events instead.

For example:

```text
Database connection established
Database connection lost
Database reconnection attempt
```

rather than dumping everything.

---

# 34. Error logging

Your global error middleware is a natural place to log unexpected errors.

Conceptually:

```js
const errorMiddleware = (err, req, res, next) => {
    logger.error({
        requestId: req.requestId,
        method: req.method,
        path: req.originalUrl,
        userId: req.user?.id,
        error: err.message,
        stack: err.stack,
    });

    // send safe response
};
```

Notice:

```text
log
   ↓
detailed internal information

response
   ↓
safe public information
```

That's important.

---

# 35. Never send the stack trace to clients in production

Log:

```text
error.stack
```

internally.

But don't return:

```json
{
  "stack": "Error: MongoServerError..."
}
```

to the frontend.

Your production API should generally say:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "req_123"
}
```

while your server logs contain the details.

This connects directly to the error-handling architecture you already learned.

# 37. Logging a business event

Not every log needs to be an HTTP request.

Suppose a user successfully changes their password.

You might log:

```json
{
  "level": "info",
  "action": "PASSWORD_CHANGED",
  "userId": "123",
  "requestId": "req_456"
}
```

This becomes especially useful when you later build **activity/audit logging**.

Your source roadmap separates this idea from ordinary request logging: important actions such as login, Todo creation/deletion, password changes, and admin role changes should record **who, what, when, resource, and requestId**.

# 38. Logging vs audit logging

These are related but not identical.

### Request logging

```text
GET /todos
200
31ms
```

### Audit logging

```text
User 123
changed role
of User 456
```

Request logging focuses on:

> **What happened to the HTTP request?**

Audit logging focuses on:

> **What important action happened in the system?**

We'll keep that distinction in mind.

# 39. What makes a useful log?

A good log should answer:

```text
WHAT happened?
WHO did it?
WHEN?
WHERE?
HOW long?
DID it succeed?
WHY did it fail?
```

For a request:

```text
WHAT
→ GET /todos

WHO
→ user_123

WHEN
→ timestamp

WHERE
→ API server

HOW LONG
→ 42ms

RESULT
→ 200
```

That's useful.

---

# 40. What makes a bad log?

This:

```text
Something happened
```

or:

```text
HERE
```

or:

```text
error
```

These don't help you debug anything.

---

# 41. Avoid excessive logging

More logs doesn't automatically mean better observability.

Imagine:

```text
10,000 requests
×
20 log lines/request
=
200,000 log lines
```

You now have noise.

Good logging asks:

> **What information will help me understand or debug this system later?**

# 52. Logging and monitoring are different

Don't mix these concepts.

### Logging

Detailed events:

```text
Request completed
User logged in
Database error
```

### Metrics

Numerical measurements:

```text
Requests per second
Error rate
Average latency
CPU usage
Memory usage
```

### Monitoring

Watching the system using those signals.

```text
Logs
+
Metrics
+
Health checks
```

Your earlier observability roadmap treats metrics as a separate concept after health/readiness checks.

# 54. Common mistakes

## ❌ Mistake 1 — Logging passwords

```js
logger.info(req.body);
```

Dangerous.

---

## ❌ Mistake 2 — Logging tokens

Never casually log:

```text
Authorization: Bearer ...
```

or refresh tokens.

---

## ❌ Mistake 3 — No request ID

Then debugging individual requests becomes harder.

---

## ❌ Mistake 4 — Logging only errors

Successful requests can provide important performance information.

---

## ❌ Mistake 5 — Logging everything

Too much noise makes important events harder to find.

---

# 57. Interview questions

### What is structured logging?

Logging information as structured fields rather than only unstructured text.

### Why are request IDs useful?

They allow a specific request to be traced across logs and API responses.

### What should a request log contain?

At minimum, your starter targets:

```text
requestId
method
path
status
duration
userId
```

### Why shouldn't passwords be logged?

Because logs can contain sensitive information and may be accessible to many systems or people.

### What is a log level?

A classification indicating the importance/severity of a log event.

### Why use Pino?

For fast, structured logging in Node.js.

### Should detailed stack traces be returned to clients?

No. Keep detailed internal diagnostics in server-side logs and return safe error information.
