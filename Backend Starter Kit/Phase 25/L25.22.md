# Lesson 25.22 — Testing

This is the **testing lesson of the graduation phase**. Your roadmap places 25.22 immediately after Logging and before Docker, and the broader testing phase defines the goal as testing the backend **layer by layer and then as a complete request flow**.

The important idea is:

> **Testing is not just checking whether a function works. It is proving that your backend architecture behaves correctly.**

By the end of this lesson, you should understand how your starter can test:

```text
utilities
middleware
services
repositories
controllers
routes
authentication
authorization
CRUD
database
```

and then combine them into full HTTP tests.

---

# 1. Why do we need backend testing?

Imagine your Todo API has:

```text
POST   /api/v1/todos
GET    /api/v1/todos
GET    /api/v1/todos/:id
PATCH  /api/v1/todos/:id
DELETE /api/v1/todos/:id
```

You manually test everything:

```text
Create Todo
→ works

Get Todo
→ works

Update Todo
→ works

Delete Todo
→ works
```

Looks good.

But then you change the authentication middleware.

Suddenly:

```text
POST /todos
```

returns:

```text
401 Unauthorized
```

You didn't intentionally change Todo creation.

Your change accidentally broke something else.

Testing helps catch this automatically.

---

# 2. Testing gives you confidence

Think of your backend like a machine:

```text
┌─────────────────────────────┐
│        Your Backend         │
│                             │
│ Route                       │
│ Middleware                  │
│ Controller                  │
│ Service                     │
│ Repository                  │
│ Database                    │
└─────────────────────────────┘
```

Tests are like checking each component:

```text
Is this part working?
        ↓
Does this part work with another part?
        ↓
Does the whole machine work?
```

So we have different levels of testing.

```text

   ↓

   ↓
```

```text

```

Your roadmap explicitly separates those two categories.

# 4. Unit testing

A unit test tests a **small isolated piece** of code.

For example:

```js
function add(a, b) {
    return a + b;
}
```

Test:

```js
expect(add(2, 3)).toBe(5);
```

You're testing:

```text
add()
```

not the entire backend.

# 9. Your first Jest test

Suppose:

```js
export function add(a, b) {
    return a + b;
}
```

Test:

```js
import { add } from "./add.js";

test("adds two numbers", () => {
    expect(add(2, 3)).toBe(5);
});
```

Jest executes the test.

If:

```text
2 + 3 = 5
```

the test passes.

If:

```text
2 + 3 = 6
```

the test fails.

---

# 10. What does `expect()` mean?

This:

```js
expect(add(2, 3)).toBe(5);
```

means:

```text
Run add(2, 3)
        ↓
Take the result
        ↓
I expect it to be 5
```

So:

```text
actual
  ↓
expect(actual)
  ↓
matcher
  ↓
expected
```

---

# 11. Matchers

Some common Jest matchers:

```js
toBe()
toEqual()
toBeTruthy()
toBeFalsy()
toBeNull()
toBeDefined()
toContain()
toHaveLength()
```

For primitive values:

```js
expect(5).toBe(5);
```

For objects:

```js
expect(user).toEqual({
    name: "Rahul"
});
```

---

# 12. `toBe()` vs `toEqual()`

This is worth understanding.

```js
expect(5).toBe(5);
```

works because primitives are compared by value.

For objects:

```js
const user = {
    name: "Rahul"
};
```

you generally use:

```js
expect(user).toEqual({
    name: "Rahul"
});
```

because `toEqual()` checks the object structure and values.

# 13. Test naming

Bad:

```js
test("test1", () => {});
```

Good:

```js
test("returns user when valid user ID is provided", () => {});
```

A test name should explain the behavior.

When a test fails:

```text
❌ returns user when valid user ID is provided
```

is immediately useful.

# 14. `describe()`

```js
    });

    test("rejects duplicate email", () => {
        // ...
    });

});
```

Now the test structure reflects your application architecture.

# 17. Testing validation

Suppose your validation requires:

```text
email
password
```

Test valid input:

```js
test("accepts valid signup data", () => {
    const result = validateSignup({
        email: "rahul@example.com",
        password: "StrongPassword123"
    });

    expect(result.error).toBeUndefined();
});
```

Test invalid input:

```js
test("rejects invalid email", () => {
    const result = validateSignup({
        email: "wrong",
        password: "StrongPassword123"
    });

    expect(result.error).toBeDefined();
});
```

Now your validation rules have automated protection.

# 18. Testing middleware

Middleware can be tested too.

Suppose:

```js
const requireAdmin = (req, res, next) => {
    if (req.user?.role !== "admin") {
        return res.status(403).json({
            message: "Forbidden"
        });
    }

    next();
};
```

We want to test:

```text
Admin
 ↓
next()

Normal user
 ↓
403

No user
 ↓
403
```

This is much better than manually testing it every time.


For example:

```text

   │
   ├── yes → next()
   │
   └── no  → 401
```

Your test cases should represent both branches.

# 21. Example service test

Conceptually:

```js
describe("AuthService.login", () => {

    test("logs in with valid credentials", async () => {
        // arrange
        // act
        // assert
    });

    test("rejects invalid password", async () => {
        // arrange
        // act
        // assert
    });

});
```

Don't worry about the complete implementation yet.

The pattern is:

```text
Arrange
 ↓
Act
 ↓
Assert
```

---

# 22. Arrange → Act → Assert

This is one of the most useful testing patterns.

### Arrange

Prepare the situation.

```text
create user
prepare mock
prepare input
```

### Act

Run the code.

```text
call service
```

### Assert

Check the result.

```text
expect(...)
```

So:

```text
Arrange
   ↓
Act
   ↓
Assert
```

---


```js

```

### Act

```js

```

### Assert

```js

```

Simple.

# 25. Do we always need MongoDB for a repository unit test?

No.

This is where **mocking** becomes useful.

For a service unit test, you might replace:

```text
real repository
```

with:

```text
mock repository
```

Then the service can be tested independently.

---

# 26. What is mocking?

Mocking means:

> **Replace a real dependency with a controlled fake version.**

Imagine:

```text
AuthService
    ↓
UserRepository
    ↓
MongoDB
```

For a unit test:

```text
AuthService
    ↓
Mock UserRepository
```

MongoDB isn't needed.

---

# 27. Why mock dependencies?

Suppose MongoDB is:

```text
slow
unavailable
unpredictable
```

You don't want a simple service test to fail because the database is down.

Instead:

```text
Service
 ↓
Mock Repository
```

Now you can control exactly what the repository returns.

---

# 28. Example mock

Suppose service expects:

```js
userRepository.findByEmail(email)
```

Mock:

```js
const userRepository = {
    findByEmail: jest.fn()
};
```

Then:

```js
userRepository.findByEmail.mockResolvedValue({
    id: "123",
    email: "rahul@example.com"
});
```

Now the service thinks the repository found a user.

---

# 29. `jest.fn()`

This:

```js
jest.fn()
```

creates a mock function.

You can then ask:

```text
Was it called?
How many times?
With what arguments?
What did it return?
```

For example:

```js
expect(userRepository.findByEmail)
    .toHaveBeenCalledWith("rahul@example.com");
```

This is powerful for service tests.

---

# 30. But don't mock everything

This is a common beginner mistake.

If you mock:

```text
route
middleware
controller
service
repository
database
```

then your test isn't really testing how the system works together.

That's why you need both:

```text
Unit tests
+
Integration tests
```

Unit tests isolate.

Integration tests connect.

# 43. Testing API responses

This connects directly to **25.20 API Responses**.

Suppose your standard success response is:

```json
{
  "success": true,
  "message": "Todo created successfully",
  "data": {}
}
```

Your test can verify that contract:

```js
expect(response.body.success).toBe(true);
expect(response.body.message)
    .toBe("Todo created successfully");
expect(response.body.data).toBeDefined();
```

Now if someone accidentally changes the response shape later:

```json
{
  "result": {}
}
```

the test fails.

That's exactly what we want.

# 49. `beforeEach()`

Jest provides:

```js
beforeEach(() => {
    // setup
});
```

This runs before every test.

For example:

```js
beforeEach(async () => {
    await clearDatabase();
});
```

Then:

```text
Test A
→ clean database

Test B
→ clean database

Test C
→ clean database
```

---

# 50. `afterEach()`

You can also use:

```js
afterEach(() => {
    // cleanup
});
```

This is useful for restoring mocks or temporary state.



> "I need to test every line."

> **"I need to prove the system behaves correctly."**


# 71. Common testing mistakes

## ❌ Testing only happy paths

```text
valid request → success
```

Not enough.

---

## ❌ Testing only status codes

This:

```js
expect(response.status).toBe(200);
```

is useful.

But also test important response data.

---

## ❌ Using production database

Never.

Use a dedicated test database/environment.

---

## ❌ Tests depending on each other

Bad:

```text
Test B requires Test A to run first.
```

Tests should be independently runnable.

---

## ❌ Mocking everything

Then you're not really testing integration.

---

## ❌ No cleanup

Old data causes mysterious failures.

---

## ❌ Chasing 100% coverage

Coverage is a signal, not the final goal.

---

## ❌ Testing implementation details

Test behavior and contracts.

# 79. Interview questions

### What is unit testing?

Testing a small isolated piece of code.

### What is integration testing?

Testing multiple components working together.

### Why use mocks?

To isolate a component from its dependencies and control their behavior.

### Why use Supertest?

To test an HTTP application through request/response behavior.

### Why use a test database?

To prevent tests from modifying real application data and to test database integration safely.

### What is test isolation?

Ensuring one test doesn't depend on or pollute another test.

### Is 100% coverage enough?

No. Coverage measures execution, not whether the tests meaningfully verify behavior.

### What should you test?

The important **behavior and contracts** of the application, including success, failure, security, and edge cases.
