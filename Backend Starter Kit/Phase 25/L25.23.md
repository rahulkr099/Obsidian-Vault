# 1. First: What problem does Docker solve?

Imagine your backend works perfectly on your Linux Mint machine:

```text
Node.js 22
MongoDB 8
npm packages
environment variables
specific configuration
```

Then you give the project to someone else.

They have:

```text
Node.js 20
MongoDB 7
different OS
different environment
different configuration
```

Now:

```text
"It works on my machine."
```

😅

Docker helps solve this.

Instead of saying:

> Install these things and configure your machine exactly like mine.

we can package the application environment.

```text
Your application
      +
Dependencies
      +
Runtime
      +
Configuration
      ↓
   Container
```

---

# 2. Docker in one sentence

Think of Docker as:

> **A way to package and run your application in an isolated, reproducible environment.**

For your MERN backend:

```text
Node.js application
       ↓
   Docker image
       ↓
 Docker container
```

And MongoDB can run separately:

```text
Node container
      +
MongoDB container
```

Your roadmap describes exactly this application-container + MongoDB-container architecture.

# 3. Image vs Container

This is the first Docker concept you must understand.

### Image

An image is the **blueprint**.

```text
Docker image
     ↓
instructions + application + dependencies
```

### Container

A container is a **running instance of that image**.

```text
Image
  ↓
Container
  ↓
Running application
```

Analogy:

```text
Class
 ↓
Object
```

or:

```text
Recipe
 ↓
Actual dish
```

So:

```text
Dockerfile
    ↓
Docker image
    ↓
Docker container
```

# 4. Dockerfile

A `Dockerfile` tells Docker:

> "How should I build my application image?"

For example:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "src/server.js"]
```

Don't memorize this yet.

Understand what each instruction means.

---

# 5. `FROM`

```dockerfile
FROM node:22-alpine
```

This says:

> Start with an existing Node.js image.

So we don't need to manually install:

```text
Linux
Node.js
npm
```

Docker gives us a base environment.

Conceptually:

```text
node:22-alpine
       ↓
   base image
       ↓
our application
```

---

# 6. Why Alpine?

You will often see:

```text
node:22-alpine
```

instead of:

```text
node:22
```

Alpine Linux is designed to be small.

That can make the resulting image significantly smaller.

For a backend starter, this is attractive because:

```text
smaller image
     ↓
less storage
     ↓
faster transfer
     ↓
faster deployment
```

However, Alpine can occasionally create compatibility issues with native dependencies.

So don't blindly choose Alpine because "smaller is always better."

---

# 7. `WORKDIR`

```dockerfile
WORKDIR /app
```

This tells Docker:

> Work inside `/app`.

Then:

```dockerfile
COPY package*.json ./
```

means the package files go into:

```text
/app
```

So inside the container:

```text
/app
├── package.json
├── package-lock.json
└── ...
```

---

# 8. Why `WORKDIR` is useful

Without it, you would repeatedly have to specify paths.

With:

```dockerfile
WORKDIR /app
```

commands become simple:

```dockerfile
RUN npm ci
COPY . .
CMD ["node", "src/server.js"]
```

Everything happens relative to:

```text
/app
```

---

# 9. `COPY`

```dockerfile
COPY package*.json ./
```

This copies:

```text
package.json
package-lock.json
```

into the image.

Then:

```dockerfile
COPY . .
```

copies your application source.

So:

```text
Your machine
     │
     │ COPY
     ▼
Docker image
```

---

# 10. Why copy `package.json` first?

This is a very important Docker optimization.

Suppose you do:

```dockerfile
COPY . .
RUN npm ci
```

Every time **any source file changes**, Docker may need to reinstall dependencies during a rebuild.

Instead:

```dockerfile
COPY package*.json ./
RUN npm ci

COPY . .
```

Now Docker can reuse the dependency layer when only source code changes.

This connects directly to Docker's **layer architecture** from your earlier Phase 23 learning.

---

# 11. Docker layers

Think:

```text
Dockerfile
    │
    ├── FROM
    │
    ├── WORKDIR
    │
    ├── COPY package.json
    │
    ├── RUN npm ci
    │
    └── COPY source
```

Each instruction can contribute to the image's layer structure.

Conceptually:

```text
┌──────────────────────────┐
│ Application source       │
├──────────────────────────┤
│ node_modules             │
├──────────────────────────┤
│ package files            │
├──────────────────────────┤
│ Node runtime             │
└──────────────────────────┘
```

If the source changes:

```text
source layer → rebuild
```

but dependency layers can often be reused.

---

# 12. `RUN`

```dockerfile
RUN npm ci
```

means:

> Execute this command while building the image.

Important distinction:

```text
RUN
 ↓
build time
```

while:

```dockerfile
CMD
```

is about:

```text
container runtime
```

---

# 13. `npm ci` vs `npm install`

For production-oriented Docker builds, prefer:

```bash
npm ci
```

when you have a lockfile.

Why?

Because `npm ci` is designed for clean, reproducible installations using:

```text
package-lock.json
```

That is exactly what we want in a container.

We don't want:

```text
Developer machine:
works

Docker build:
different dependency versions
```

---

# 14. `CMD`

For example:

```dockerfile
CMD ["node", "src/server.js"]
```

This says:

> When the container starts, run the Node server.

So:

```text
docker build
     ↓
image
```

then:

```text
docker run
     ↓
container starts
     ↓
CMD executes
     ↓
Node server starts
```

Memorize this:

```text
Dockerfile
    │
    │ docker build
    ▼
Docker Image
    │
    │ docker run
    ▼
Docker Container
    │
    ▼
```

# 17. One container per major responsibility

A clean architecture is:

```text
┌───────────────────────┐
│    Node Container     │
│                       │
│ Express               │
│ API                   │
│ Business Logic        │
└───────────┬───────────┘
            │
            │ network
            ▼
┌───────────────────────┐
│   MongoDB Container   │
│                       │
│ Database              │
└───────────────────────┘
```

This is much better than:

```text
One giant container
 ├── Node
 ├── MongoDB
 ├── Redis
 └── everything
```

Keep responsibilities separated.

# 18. Docker Compose

Now we reach:

```text
docker-compose.yml
```

Docker Compose lets us define multiple services together.

For example:

```yaml
services:
  api:
    build: .
    ports:
      - "5000:5000"

  mongo:
    image: mongo:8
```

Conceptually:

```text
docker compose
      │
      ├── api
      │
      └── mongo
```

Your Phase 23 roadmap specifically includes Docker Compose and Node + MongoDB.

---

# 19. Why Compose is useful

Without Compose:

```bash
docker run ...
docker run ...
docker network ...
docker volume ...
```

You have to manage everything manually.

With Compose:

```bash
docker compose up
```

and your architecture starts together.

That's extremely useful for development.

# 20. Node + MongoDB

Your starter's development environment can conceptually become:

```text
docker compose
      │
      ├── api
      │    └── Node.js
      │
      └── mongo
           └── MongoDB
```

Then:

```text
API
 ↓
MongoDB
```

communicate over a Docker network.

---

# 21. Important: `localhost`

This is one of the biggest Docker beginner mistakes.

On your host:

```text
localhost:27017
```

means:

> MongoDB on my computer.

Inside the API container:

```text
localhost
```

means:

> **the API container itself.**

Not MongoDB.

So this is usually wrong inside the Node container:

```env
MONGODB_URI=mongodb://localhost:27017/mydb
```

when MongoDB is running in another container.

---

# 22. Docker service names become hostnames

Suppose Compose says:

```yaml
services:
  api:
    ...
  
  mongo:
    image: mongo:8
```

Inside `api`, you can use:

```text
mongo
```

as the hostname.

So conceptually:

```env
MONGODB_URI=mongodb://mongo:27017/mydb
```

because:

```text
api container
     │
     │ hostname: mongo
     ▼
mongo container
```

This is a **very important Docker networking concept**.

# 23. Ports

Suppose Express listens inside the container on:

```text
5000
```

You can map:

```yaml
ports:
  - "5000:5000"
```

This means:

```text
Host port 5000
       │
       ▼
Container port 5000
```

So your browser/client can call:

```text
http://localhost:5000
```

---

# 24. Port mapping mental model

Think:

```text
HOST
localhost:5000
       │
       │ mapping
       ▼
CONTAINER
:5000
       │
       ▼
Express
```

The two ports don't have to be identical.

For example:

```yaml
ports:
  - "8000:5000"
```

means:

```text
localhost:8000
       ↓
container:5000
```

# 25. MongoDB ports

You don't necessarily need to expose MongoDB publicly to your host.

For example:

```yaml
mongo:
  image: mongo:8
```

The API can communicate with MongoDB internally through Docker's network.

That means:

```text
API → mongo
```

without requiring:

```text
localhost:27017 → MongoDB
```

for the API.

This is a good security and architecture habit.

# 26. Volumes

MongoDB stores data.

What happens if the container disappears?

Without persistent storage:

```text
Mongo container
     ↓
container removed
     ↓
data may disappear
```

That's where volumes come in.

```text
MongoDB
   ↓
Docker volume
   ↓
Persistent data
```

Your roadmap explicitly includes volumes.

---

# 27. Volume mental model

```text
┌──────────────────────┐
│ MongoDB Container    │
│                      │
│      /data/db        │
└──────────┬───────────┘
           │
           ▼
     Docker Volume
           │
           ▼
       Persistent
          data
```

The container is disposable.

The volume preserves the database data.

---

# 28. Bind mounts vs volumes

There are two concepts you should know.

### Bind mount

Host directory:

```text
./src
```

is mounted into:

```text
/app/src
```

Great for development.

### Named volume

Docker manages the storage.

Great for persistent database data.

So development might use:

```text
source code → bind mount
```

while MongoDB uses:

```text
database → named volume
```

```text
  ↓
```

# 32. `.dockerignore`

Just like `.gitignore`, Docker can have:

```text
.dockerignore
```

For example:

```text

.git
.env

npm-debug.log
Dockerfile.dev
```

Why?

Because you don't want to copy unnecessary or sensitive files into the build context.

---

# 33. Never copy `.env` into your image

This is critical.

Don't do:

```dockerfile
COPY . .
```

and accidentally include:

```text
.env
```

if it contains:

```text
JWT_SECRET
MONGODB_PASSWORD
SMTP_PASSWORD
```

Instead, use environment variables/secrets at runtime.

Your Phase 24 roadmap separately emphasizes production environment secrets, and Docker is part of the production-hardening workflow.

---

# 34. Environment variables in Docker

Your application already uses environment variables.

For example:

```env
PORT=5000
MONGODB_URI=...
JWT_ACCESS_SECRET=...
JWT_REFRESH_SECRET=...
```

Docker should inject these.

Conceptually:

```text
Environment
     │
     ▼
Container
     │
     ▼
process.env
```

Your application doesn't need to know whether those variables came from:

```text
.env
Docker Compose
Kubernetes
cloud platform
CI/CD
```

That's a powerful separation.

---

# 35. Docker should not contain secrets

Bad:

```dockerfile
ENV JWT_SECRET=super-secret-value
```

Don't hardcode real secrets in the Dockerfile.

Why?

Because the Dockerfile becomes part of your source and image history.

Instead:

```text
Secret
  ↓
runtime environment
  ↓
container
```

# 37. Health vs readiness

You previously learned:

```text
/healthz
```

and:

```text
/readyz
```

The distinction is:

```text
/healthz
    ↓
Is the Node process alive?

/readyz
    ↓
Can the application actually serve traffic?
```

For example:

```text
Node running
+
MongoDB unavailable
```

could mean:

```text
healthz → healthy
readyz  → not ready
```

depending on your implementation.

# 38. Graceful shutdown

Your roadmap includes:

```text
23.14 Graceful shutdown
```

This becomes especially important with Docker.

When Docker stops your container:

```text
SIGTERM
   ↓
Node application
   ↓
stop accepting new requests
   ↓
finish active requests
   ↓
close MongoDB
   ↓
exit
```

You don't want:

```text
SIGTERM
   ↓
process instantly dies
   ↓
unfinished requests
   ↓
connections abruptly closed
```

# 40. Production Dockerfile concept

A good production Dockerfile might conceptually look like:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY . .

USER node

CMD ["node", "src/server.js"]
```

Don't blindly copy this into your project yet.

Understand the decisions:

```text
FROM
 ↓
small runtime
 ↓
WORKDIR
 ↓
package files
 ↓
production dependencies
 ↓
source
 ↓
non-root user
 ↓
start application
```

---

# 41. Why `npm ci --omit=dev`?

Your application needs:

```text
production dependencies
```

but may not need:

```text
Jest
ESLint
development tools
```

inside the production runtime.

So:

```bash
npm ci --omit=dev
```

reduces unnecessary packages.

This can make the production image:

```text
smaller
faster
less exposed
```

---

# 42. Why run as a non-root user?

Containers should follow least privilege where practical.

Instead of:

```text
root
```

your Node process can run as:

```text
node
```

This reduces the impact of certain container-level vulnerabilities.

Security isn't just:

```text
JWT
CORS
Helmet
```

It also includes:

```text
container privileges
filesystem access
process privileges
```

# 46. But `depends_on` doesn't mean "Mongo is ready"

Important subtle point.

This:

```yaml

  - mongo
```

generally means:

> Start the Mongo service before the API service.

It doesn't automatically guarantee:

> MongoDB is fully ready to accept connections.

# 48. Don't expose everything

Your production architecture should generally expose:

```text
Internet
   ↓
Reverse proxy / load balancer
   ↓
API container
   ↓
MongoDB
```

MongoDB should not normally be publicly accessible.

So:

```text
Internet
   ❌
   ↓
MongoDB
```

is a bad architecture.

Instead:

```text
Internet
   ↓
API
   ↓
private network
   ↓
MongoDB
```

# 49. Docker doesn't automatically make your application secure

This is very important.

Docker provides isolation and packaging.

It doesn't automatically fix:

```text
SQL/NoSQL injection
authentication bugs
authorization bugs
JWT problems
bad CORS
weak passwords
secrets leakage
broken business logic
```

Docker is one layer of your security architecture.
