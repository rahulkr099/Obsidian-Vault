# 5. Why each layer exists

Let's make this extremely simple.

### Route

**Question:**

> Which endpoint is being requested?

```text
POST /notes
```

---

### Middleware

**Question:**

> Can this request continue?

Examples:

```text
Is authenticated?
Is authorized?
Is input valid?
Is rate limit exceeded?
```

---

### Controller

**Question:**

> What HTTP operation should happen?

The controller deals with:

```text
req
res
HTTP status
HTTP response
```

Your source describes the controller as the translator between HTTP and the application.

---

### Service

**Question:**

> What business operation should happen?

For example:

```text
Can this user create the note?
Should a duplicate be rejected?
What business rules apply?
```

---

### Repository

**Question:**

> How do we communicate with MongoDB?

For example:

```text
findById()
create()
update()
delete()
findMany()
```

Your roadmap specifically separates repository responsibilities from business logic.

---

### Model

**Question:**

> What does the database data look like?

For example:

```text
Note
├── title
├── content
├── userId
├── createdAt
└── updatedAt
```

# 6. Don't make this mistake

A beginner often creates:

```js
createNote(req, res) {
    // validation
    // authentication
    // business logic
    // database query
    // response
    // logging
}
```

Everything is inside the controller.

That's difficult to maintain.

Instead:

```text
Controller
    ↓
noteService.createNote()
    ↓
noteRepository.create()
    ↓
MongoDB
```

Each layer has a job.

Your source explicitly teaches the transformation from controllers containing everything to controllers delegating business logic to services.

# 18. What you should be able to explain in an interview

Someone asks:

### "Why do you use a service layer?"

You should answer:

> The service layer keeps business logic separate from HTTP handling, so controllers stay focused on request/response concerns and business operations can be reused and tested independently.

---

### "Why use repositories?"

> To isolate database access from business logic, making the service layer less dependent on the database implementation and easier to test or change.

---

### "Why validation middleware?"

> To reject invalid input before it reaches business logic or database operations.

---

### "Why centralized error handling?"

> To keep error responses consistent and avoid repeating error-response logic across controllers.

---

### "Why request IDs?"

> To correlate logs belonging to the same request, which makes debugging distributed or production systems easier.

---

### "Why Docker?"

> To package the application into a reproducible runtime environment and make development and deployment more consistent.

---

### "Why tests at multiple levels?"

> Unit tests verify individual pieces, while integration tests verify that multiple layers work correctly together.
