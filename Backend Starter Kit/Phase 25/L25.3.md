# Lesson 25.3 — Install Dependencies

In **25.1**, we created the project.

In **25.2**, we configured Node and chose ES Modules.

Now we install the tools our backend will actually use.

The important rule for this lesson is:

> **Don't install packages because they appear in a starter template. Install them because you understand what problem they solve.**

Your reference roadmap groups the dependencies into runtime, security, validation, authentication, logging, and development/testing packages.

---

# 1. What is a dependency?

Suppose we want to create an HTTP server.

We could implement everything ourselves:

```text
HTTP parsing
Routing
Cookies
Security headers
JWT
Password hashing
Database communication
Logging
Testing
```

That would be enormous.

Instead, we use packages that already solve these problems.

For example:

```text
Express
   ↓
HTTP server + routing

Mongoose
   ↓
MongoDB interaction

bcrypt
   ↓
Password hashing

jsonwebtoken
   ↓
JWT creation/verification
```

So a dependency is basically:

> **Code written by another project that our application depends on.**

---

# 2. Runtime vs development dependencies

This distinction is extremely important.

There are two major categories.

### Production dependency

Your application needs it while running:

```text
express
mongoose
dotenv
jsonwebtoken
```

Install with:

```bash
npm install package-name
```

### Development dependency

You primarily need it while developing/testing:

```text
nodemon
jest
supertest
```

Install with:

```bash
npm install -D package-name
```

The `-D` means:

```text
--save-dev
```

# 7. CORS

Install:

```bash
npm install cors
```

CORS becomes important because our frontend and backend will often run on different origins.

For example:

```text
Frontend
http://localhost:5173

       ↓ HTTP

Backend
http://localhost:5000
```

The browser applies cross-origin rules.

`cors` helps us configure the server's CORS behavior.

Later we'll learn the security implications instead of simply writing:

```js
app.use(cors());
```

# 10. Rate limiting

Install:

```bash
npm install express-rate-limit
```

Why?

Imagine:

```text
POST /api/v1/auth/login
```

An attacker could repeatedly try:

```text
password1
password2
password3
password4
...
```

A rate limiter can restrict how frequently requests are accepted.

Conceptually:

```text
100 requests
     ↓
Rate limiter
     ↓
Allowed?

YES → continue
NO  → reject
```

Later we'll create separate strategies for general API traffic and sensitive authentication endpoints.

# 11. Joi

Install:

```bash
npm install joi
```

Joi is our validation library.

For example, eventually:

```js
const schema = Joi.object({
    email: Joi.string().email().required(),
    password: Joi.string().min(8).required()

```

Then:

```text
req.body
   ↓
Joi
   ↓
Valid?
 ├── No → error
 └── Yes → continue
```

Your roadmap specifically uses Joi as the validation layer.

# 13. bcrypt




# 16. Development dependency: Nodemon

Now install:

```bash
npm install -D nodemon
```

Nodemon watches your files and restarts the Node process when changes occur.

Without it:

```text
Edit code
   ↓
Stop server
   ↓
Start server
```

With it:

```text
Edit code
   ↓
Nodemon detects change
   ↓
Restart
```

### One important note

In **25.2**, we used:

```json
"dev": "node --watch server.js"
```

Since Node itself now provides a watch mode, **we don't actually need Nodemon for the basic starter**.

Your original roadmap lists Nodemon, but our current Node configuration already has a built-in alternative.

So you have two choices:

### Option A — Native Node

```json
"dev": "node --watch server.js"
```

No Nodemon needed.

### Option B — Nodemon

```json
"dev": "nodemon server.js"
```

and install:

```bash
npm install -D nodemon
```

For this starter, I recommend **Option A** initially because fewer dependencies are better.

We can introduce Nodemon later if there is a specific workflow reason to use it.

# 21. What happened to `package-lock.json`?

You should now have:

```text
mern-backend-starter/
│
├── .git/
├── node_modules/
├── package-lock.json
└── package.json
```

The important new files/directories are:

### `node_modules/`

Contains the installed packages.

### `package-lock.json`

Records the exact dependency tree npm resolved.

### `package.json`

Declares what the project depends on.

---

# 22. `package.json` vs `package-lock.json`

This distinction is worth remembering.

Think:

```text
package.json
    ↓
"What packages does my project need?"
```

while:

```text
package-lock.json
    ↓
"What exact dependency versions/tree were resolved?"
```

For example:

```text
package.json
    ↓
express

package-lock.json
    ↓
exact Express version
    +
Express's dependencies
    +
their exact versions
    +
...
```

This makes installations much more reproducible.

---

# 23. Never commit `node_modules`

This directory:

```text
node_modules/
```

can become enormous.

You don't want:

```bash
git add node_modules/
```

Instead, we'll create:

```text
.gitignore
```

in the next architecture/setup step.

The repository should contain:

```text
package.json
package-lock.json
```

but not the entire:

```text
node_modules/
```

directory.

# The main lesson

Don't memorize:

```bash
npm install express mongoose dotenv cors ...
```

Memorize the **problem → tool relationship**:

```text
Need HTTP server
      ↓
Express

Need MongoDB
      ↓
Mongoose

Need environment variables
      ↓
dotenv

Need validation
      ↓
Joi

Need password hashing
      ↓
bcrypt

Need JWT
      ↓
jsonwebtoken

Need security headers
      ↓
Helmet

Need rate limiting
      ↓
express-rate-limit

Need structured logs
      ↓
Pino

Need HTTP testing
      ↓
Supertest
```

That's the real skill.

Your reference architecture intentionally separates these concerns across security, validation, authentication, logging, and testing rather than treating the dependencies as one random package list.
