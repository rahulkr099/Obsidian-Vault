# Lesson 25.4 — Create the Folder Architecture

Now we have:

```text
Project
   ↓
Node configuration
   ↓
Dependencies
```

Today we create the **architecture of the application**.

The important rule:

> **A folder should exist because it owns a responsibility, not because every backend tutorial has that folder.**

Your reference starter is organized around layers such as `config`, `constants`, `controllers`, `middlewares`, `models`, `repositories`, `routes`, `services`, `utils`, `validations`, `mail`, `tests`, and `docs`.

# 2. First, understand the layers

Before running commands, understand what each directory will eventually own.

## `config/`

Application configuration.

```text
config/
├── env.js
└── db.js
```

Think:

> "How does my application get configured?"

---

## `constants/`

Values that are reused throughout the application.

Examples:

```text
roles
messages
HTTP-related constants
authentication constants
```

Think:

> "What values should have one central definition?"

---

## `middlewares/`

Code that runs **between the request and the final handler**.

Examples:

```text
authentication
authorization
validation
logging
security
request ID
error handling
```

Think:

> "What should happen before the controller?"

---

## `controllers/`

Controllers handle the HTTP layer.

```text
Request
   ↓
Controller
   ↓
Service
```

Think:

> "How do I translate this HTTP request into an application operation?"

---

## `services/`

Business logic.

```text
Controller
   ↓
Service
   ↓
Repository
```

Think:

> "What should the application actually do?"

---

## `repositories/`

Database access.

```text
Service
   ↓
Repository
   ↓
Model
   ↓
MongoDB
```

Think:

> "How do I retrieve or modify data?"

---

## `models/`

Database data structures.

For example:

```text
models/
└── user.model.js
```

Think:

> "What does this data look like in MongoDB?"

---

## `routes/`

URL and HTTP method definitions.

For example:

```text
POST /api/v1/auth/login
```

Think:

> "Which endpoint receives this request?"

---

## `validations/`

Input schemas.

Think:

> "Is the incoming data acceptable?"

---

## `utils/`

Small reusable utilities that don't belong to a specific business domain.

Examples:

```text
JWT helpers
API response helper
error helper
token utilities
```

---

## `mail/`

Email-related functionality.

Your reference architecture includes email rendering/sending and templates.

Think:

> "Everything related to sending application emails."

---

## `tests/`

Automated tests.

Eventually:

```text
tests/
├── unit/
└── integration/
```

Think:

> "How do we prove our backend works?"

---

## `docs/`

API and architecture documentation.

Eventually this can contain:


> "How does another developer understand and use this backend?"

# 4. Why are the folders empty?

Because Git doesn't track empty directories.

If you run:

```bash
git status
```

you won't see all those folders as separate tracked items.

That's normal.

Git tracks **files**, not directories.

So we'll create files inside the folders as we reach each part of the architecture.

# 6. Why are `app.js` and `server.js` outside folders?

Because they're the main entry points of the application.

We'll eventually have:

```text
app.js
```

responsible for:

```text
Express application
     ↓
middleware
     ↓
routes
     ↓
error handling
```

And:

```text
server.js
```

responsible for:

```text
environment
     ↓
database
     ↓
HTTP server
```

So:

```text
app.js
   =
application construction
```

while:

```text
server.js
   =
application startup
```

We'll build both later.

# 8. Why do we need `.env`?

Eventually we'll put sensitive/local configuration there.

For example:

```env
PORT=5000
MONGO_URI=...
ACCESS_TOKEN_SECRET=...
```

But **do not put real secrets into Git**.

That's why we also have:

```text
.env.example
```

The difference is:

```text
.env
   ↓
Real local values

.env.example
   ↓
Example variable names
```

We'll properly configure this in **Lesson 25.5**.

# 13. Why not put everything inside `controllers/`?

A beginner might create:

```text
controllers/
├── auth.js
├── user.js
└── todo.js
```

and put all the code there.

Then a controller might become:

```text
HTTP handling
+
validation
+
authentication
+
business rules
+
database queries
+
email
+
logging
```

That creates a **fat controller**.

Instead:

```text
Controller
   ↓
Service
   ↓
Repository
```

gives each layer a clear responsibility.

---

# 14. Why not put database queries directly inside services?

Because we're deliberately separating:

```text
Business logic
```

from:

```text
Data access
```

For example:

```text
auth.service.js
```

should be concerned with:

```text
"Can this user log in?"
```

while:

```text
user.repository.js
```

is concerned with:

```text
"How do I find this user in MongoDB?"
```

That's why both folders exist.

---

# 15. Why `routes/` and `controllers/` are separate

Consider:

```text
POST /api/v1/auth/login
```

The route answers:

> Which code handles this endpoint?

The controller answers:

> What do I do with the HTTP request?

So:

```text
Route
 ↓
authController.login
```

rather than putting the entire login implementation inside the route file.

---

# 16. Why `validations/` is separate

Validation schemas can become large.

For example:

```text
auth.validation.js
```

might eventually contain:

```text
signupSchema
loginSchema
refreshSchema
resetPasswordSchema
```

Keeping these outside controllers means:

```text
Controller
```

doesn't become cluttered with validation definitions.

---

# 17. Why `utils/` needs discipline

A common mistake is creating:

```text
utils/
```

and dumping everything into it.

Don't do that.

A utility should generally be:

> Small, reusable, and not tied to one specific business domain.

Good candidates:

```text
generateAccessToken()
formatApiResponse()
createPaginationMeta()
```

Bad candidates:

```text
createUser()
loginUser()
deleteTodo()
```

Those belong to business/application layers.

We'll revisit this when building the utility layer.

---

# 18. Why `constants/` exists

Imagine you repeatedly write:

```js
"user"
"admin"
```

throughout your application.

Instead:

```js
ROLES.USER
ROLES.ADMIN
```

Then one central definition controls the values.

Conceptually:

```text
constants/roles.js
       ↓
Controllers
Services
Middleware
Tests
```

One definition, many consumers.

# 22. Important security checkpoint

Before we go further:

**Never put secrets into `.env.example`.**

Good:

```env
MONGO_URI=
ACCESS_TOKEN_SECRET=
```

Bad:

```env
MONGO_URI=mongodb://real-production-server...
ACCESS_TOKEN_SECRET=my-real-secret
```

The example file describes the **shape** of configuration.

The real `.env` contains your local values.

We'll formalize this in the next lesson.
