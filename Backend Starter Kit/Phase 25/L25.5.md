# Lesson 25.5 — Environment System

Now we reach one of the most important parts of the starter:

> **Configuration and secrets must be separated from application code.**

In the previous lesson, we created:

```text
.env
.env.example
```

but they don't do anything useful yet.

Today we'll build the flow:

```text
.env
  ↓
dotenv
  ↓
config/env.js
  ↓
application
```

This matches your starter roadmap: environment variables are loaded through `dotenv`, then centralized through `config/env.js` instead of scattering `process.env.SOMETHING` throughout the application.

---

# 1. Why do we need an environment system?

Imagine writing this directly inside your code:

```js
const mongoUri = "mongodb://localhost:27017/myapp";
```

Or worse:

```js
const jwtSecret = "my-super-secret-password";
```

That's a problem.

Your application code should not contain environment-specific values.

Instead:

```text
Development
    ↓
.env
    ↓
configuration

Production
    ↓
production environment
    ↓
configuration
```

The same application code can therefore run in different environments.

---

# 2. Think about three environments

A backend commonly has at least:

```text
development
testing
production
```

For example:

```text
Development
PORT=5000
MONGO_URI=mongodb://localhost:27017/myapp_dev

Testing
PORT=5001
MONGO_URI=mongodb://localhost:27017/myapp_test

Production
PORT=8080
MONGO_URI=<production database>
```

The application code doesn't need to change.

Only the configuration changes.

That's the major idea.

---

Good candidates include:

# 4. `.env` vs `.env.example`

This distinction is extremely important.

## `.env`

Contains your **actual local values**.

Example:

```env
NODE_ENV=development
PORT=5000
MONGO_URI=mongodb://localhost:27017/mern_starter
ACCESS_TOKEN_SECRET=some-long-local-secret
REFRESH_TOKEN_SECRET=another-long-local-secret
ACCESS_TOKEN_EXPIRES_IN=15m
REFRESH_TOKEN_EXPIRES_IN=7d
FRONTEND_URL=http://localhost:5173
```

You generally **do not commit this file**.

---

## `.env.example`

Contains the **required configuration structure**, not real secrets.

Example:

```env
NODE_ENV=development
PORT=5000

MONGO_URI=

ACCESS_TOKEN_SECRET=
REFRESH_TOKEN_SECRET=

ACCESS_TOKEN_EXPIRES_IN=15m
REFRESH_TOKEN_EXPIRES_IN=7d

FRONTEND_URL=http://localhost:5173
```

This file **can be committed**.

It tells another developer:

> "These are the environment variables this application expects."

---

# 5. Real-world analogy

Imagine you're opening a restaurant.

Your application is the restaurant itself:

```text
Kitchen
Tables
Employees
Menu
```

But some information changes depending on where the restaurant operates:

```text
Address
Phone number
Bank account
Supplier credentials
Door key
```

You don't redesign the restaurant every time you move.

You simply provide different configuration.

That's what environment variables do for software.

# 10. What is `dotenv`?

We installed:

```bash
npm install dotenv
```

But what does it actually do?

It reads values from:

```text
.env
```

and makes them available through:

```js
process.env
```

Conceptually:

```text
.env
 │
 │ dotenv
 ▼
process.env
```

So:

```env
PORT=5000
```

becomes accessible as:

```js
process.env.PORT
```

# 12. Why do we need `dotenv.config()`?

Simply installing the package:

```bash
npm install dotenv
```

doesn't automatically mean your `.env` values are available in every situation.

We need to load the environment configuration.

That's what:


does.

It loads the `.env` file into the Node process environment.

# 14. The problem with using `process.env` everywhere

You might now think:

```js
const mongoUri = process.env.MONGO_URI;
```

Easy.

But imagine 50 files doing:

```js
process.env.MONGO_URI
process.env.PORT
process.env.ACCESS_TOKEN_SECRET
process.env.FRONTEND_URL
process.env.EMAIL_HOST
process.env.EMAIL_USER
...
```

Now configuration is scattered everywhere.

That's what we're going to avoid.

Your starter explicitly calls for a centralized `config/env.js` layer.

# 16. First version of `env.js`

Put:

```js
import dotenv from "dotenv";

dotenv.config();

const env = {
    nodeEnv: process.env.NODE_ENV || "development",
    port: Number(process.env.PORT) || 5000,

    mongoUri: process.env.MONGO_URI,

    accessTokenSecret: process.env.ACCESS_TOKEN_SECRET,
    refreshTokenSecret: process.env.REFRESH_TOKEN_SECRET,

    accessTokenExpiresIn:
        process.env.ACCESS_TOKEN_EXPIRES_IN || "15m",

    refreshTokenExpiresIn:
        process.env.REFRESH_TOKEN_EXPIRES_IN || "7d",

    frontendUrl:
        process.env.FRONTEND_URL || "http://localhost:5173",
};

export default env;
```

Don't worry if this looks like a lot.

Let's understand it piece by piece.

# 20. Why do we convert `PORT` to a number?

Environment variables are strings.

Even:

```env
PORT=5000
```

comes into Node as:

```js
"5000"
```

not:

```js
5000
```

So:

```js
Number(process.env.PORT)
```

converts:

```text
"5000"
 ↓
5000
```

This is a small but important configuration detail.

---

# 21. Why use defaults?

Consider:

```js
nodeEnv: process.env.NODE_ENV || "development"
```

If:

```text
NODE_ENV
```

exists:

```text
production
```

we use it.

If it doesn't exist:

```text
undefined
```

we fall back to:

```text
development
```

Same idea:

```js
port: Number(process.env.PORT) || 5000
```

means:

```text
PORT exists
   ↓
use it

PORT missing
   ↓
use 5000
```

---

# 22. But secrets are different

Notice:

```js
accessTokenSecret: process.env.ACCESS_TOKEN_SECRET
```

We didn't provide a fallback like:

```js
accessTokenSecret:
    process.env.ACCESS_TOKEN_SECRET || "secret"
```

That's intentional.

You should **never silently invent a security secret**.

A missing authentication secret should eventually cause application startup to fail.

We'll improve this configuration validation later.

# 26. Why is this better?

Imagine `server.js` needs the port.

Instead of:

```js
const port = process.env.PORT;
```

we'll eventually write:

```js
import env from "./config/env.js";

const port = env.port;
```

The database configuration can use:

```js
env.mongoUri
```

Authentication can use:

```js
env.accessTokenSecret
```

Email can use:

```js
env.smtpHost
```

Everything gets configuration from the same place.

# 27. The architecture is becoming clearer

We're now building:

```text
                    .env
                      │
                      ▼
                   dotenv
                      │
                      ▼
               config/env.js
                      │
              ┌───────┼────────┐
              ▼       ▼        ▼
           server    db      auth
```

This is much better than:

```text
server.js ─────→ process.env.PORT

db.js ─────────→ process.env.MONGO_URI

auth.js ───────→ process.env.ACCESS_TOKEN_SECRET

email.js ──────→ process.env.SMTP_PASSWORD
```

The second approach scatters configuration knowledge throughout the application.

The first centralizes it.

---

# 28. One important improvement: fail fast

Our current version allows:

```js
mongoUri: undefined
```

That's not ideal.

Imagine starting the backend with:

```text
MONGO_URI missing
```

and discovering the problem 30 seconds later when a request hits the database.

A better backend should detect configuration problems **during startup**.

Conceptually:

```text
Application starts
       ↓
Validate configuration
       ↓
Everything present?
    ┌──┴──┐
   YES    NO
    │      │
    ▼      ▼
Continue  Exit
```

We'll make the configuration system stricter as the starter develops.

For now, understand the principle:

> **Invalid configuration should be discovered as early as possible.**

# 29. Required vs optional variables

Not every environment variable is equal.

### Required

For example:

```text
MONGO_URI
ACCESS_TOKEN_SECRET
REFRESH_TOKEN_SECRET
```

The application may not be able to function without them.

### Optional/defaulted

For example:

```text
PORT
NODE_ENV
FRONTEND_URL
```

may have sensible development defaults.

So eventually our configuration system should distinguish:

```text
Required
Optional
Defaulted
```

This becomes particularly important in production.

---

# 30. Environment variables are strings

Remember this:

```env
PORT=5000
```

is loaded as:

```js
"5000"
```

Similarly:

```env
ENABLE_FEATURE=true
```

is:

```js
"true"
```

not:

```js
true
```

So this:

```js
if (process.env.ENABLE_FEATURE) {
}
```

can be dangerous because:

```js
Boolean("false")
```

is actually:

```js
true
```

Later, when we have boolean configuration, we'll parse it properly.

---

# 31. Never log secrets

Don't do:

```js
console.log(env);
```

in production.

Why?

Because:

```js
env.accessTokenSecret
env.refreshTokenSecret
```

could end up in your logs.

And logs are not automatically private.

Your previous logging/security work specifically emphasized avoiding sensitive data in logs. The roadmap places this concern within the observability architecture.

Safe debugging might be:

```js
console.log({
    nodeEnv: env.nodeEnv,
    port: env.port,
    mongoConfigured: Boolean(env.mongoUri),
});
```

rather than printing the actual secret.

---

# 32. `.env` is not a security system

This is another important distinction.

`.env` is simply a convenient way to provide configuration.

It does **not** magically encrypt secrets.

If someone gets access to:

```text
.env
```

they may get access to:

```text
database credentials
JWT secrets
API keys
SMTP credentials
```

Therefore:

```text
.env
```

is a development convenience.

Production should use an appropriate secret-management/environment mechanism.

Your production-hardening phase explicitly treats environment secrets as a separate concern.
