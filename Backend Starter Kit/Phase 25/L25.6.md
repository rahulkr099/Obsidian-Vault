# Lesson 25.6 — Database System

Now we're going to connect the configuration system we built in **25.5** to MongoDB.

The source roadmap defines this phase very clearly:

```text
server.js
   ↓
connectDB()
   ↓
MongoDB
   ↓
start HTTP server
```

The important rule is:

> **If MongoDB is required for the application, don't start accepting requests until the database connection succeeds.**

---

# 1. What are we building?

Currently we have:

```text
.env
   ↓
dotenv
   ↓
config/env.js
```

Now we're adding:

```text
config/env.js
      ↓
   config/db.js
      ↓

```

Eventually:

```text
server.js
   │
   ├── load environment

   │       ↓

   │

```

We're **not** creating models yet.

That comes later.

---

# 2. Why separate `db.js` from `server.js`?

You might initially think:

```js
// server.js

mongoose.connect(...);

app.listen(...);
```

It would work.

But then `server.js` would be responsible for:

```text
configuration
database implementation
Express startup
HTTP server
shutdown
```

That's too many responsibilities.

Instead:

```text
server.js
    ↓
connectDB()
```

and:

```text
config/db.js
    ↓
MongoDB connection implementation
```

So:

```text
server.js
= startup orchestration

db.js
= database connection
```

That's the separation we want.

# 5. Understand the MongoDB URI

Let's break this apart:

```text
mongodb://localhost:27017/mern_backend_starter
```

### `mongodb://`

Protocol telling the driver:

> This is a MongoDB connection.

### `localhost`

The database is running on this machine.

### `27017`

MongoDB's normal default port.

### `mern_backend_starter`

The database name.

So:

```text
mongodb://localhost:27017/mern_backend_starter
        │          │      │
        │          │      └── database
        │          └───────── port
        └──────────────────── host
```

# 8. First implementation

Put this into `config/db.js`:

```js
import mongoose from "mongoose";
import env from "./env.js";

const connectDB = async () => {
    try {
        await mongoose.connect(env.mongoUri);

        console.log("MongoDB connected");
    } catch (error) {
        console.error("MongoDB connection failed:", error.message);
        process.exit(1);
    }
};

export default connectDB;
```

Don't just copy it.

Let's understand every part.

```js
mongoose.connect(...)
```

# 11. Why import `env` instead of `process.env`?

We could technically write:

```js
await mongoose.connect(process.env.MONGO_URI);
```

But we deliberately don't want every part of the application accessing environment variables directly.

Instead:

```text
.env
 ↓
dotenv
 ↓
env.js
 ↓
db.js
```

So `db.js` only needs to know:

```js
env.mongoUri
```

That's cleaner.

---

# 12. Create `connectDB`

```js
const connectDB = async () => {
```

We're creating a function because the server needs a clear operation:

```text
connectDB()
```

This gives us a useful abstraction.

`server.js` doesn't need to know how MongoDB works.

It only needs to say:

```js
await connectDB();
```

---

# 13. Why is it `async`?

Connecting to MongoDB takes time.

It's an asynchronous operation.

Conceptually:

```text
Application
    ↓
"Connect to MongoDB"
    ↓
wait...
    ↓
MongoDB responds
```

So:

```js
await mongoose.connect(...)
```

means:

> Don't continue this startup function until the database connection attempt resolves.

---

# 14. The actual connection

```js
await mongoose.connect(env.mongoUri);
```

This is the core operation.

The flow is:

```text
env.mongoUri
     ↓
mongoose.connect()
     ↓
MongoDB
```

If successful, execution continues.

If it fails, the `catch` block handles it.

---

# 15. Why use `try/catch`?

Because database connections can fail.

For example:

```text
MongoDB isn't running
       ↓
Connection refused
```

or:

```text
Wrong URI
       ↓
Connection failure
```

or:

```text
Network unavailable
       ↓
Connection failure
```

We need to handle that explicitly.

---

# 16. Successful connection

```js
console.log("MongoDB connected");
```

For now, a simple log is enough.

Later, when our Pino logging architecture is ready, we'll replace this with structured logging.

For now we're learning database architecture, not logging architecture.

---

# 17. Failed connection

```js
catch (error) {
    console.error(
        "MongoDB connection failed:",
        error.message
    );

    process.exit(1);
}
```

The important part is:

```js
process.exit(1);
```

---

# 18. Why exit?

Suppose MongoDB is required for your application.

If MongoDB is unavailable, imagine this:

```text
MongoDB ❌
   ↓
Express starts anyway
   ↓
Application accepts requests
   ↓
Request needs database
   ↓
Database operation fails
```

Now your application is technically "running", but it isn't actually usable.

Instead:

```text
MongoDB ❌
   ↓
Startup fails
   ↓
Process exits
```

This is much cleaner.

The roadmap explicitly emphasizes:

> Don't start accepting requests before the required database connection is ready.

---

# 19. What does exit code `1` mean?

Generally:

```text
0 → success
non-zero → failure
```

So:

```js
process.exit(1);
```

means:

> Terminate the Node process and indicate that startup failed.

This is useful to:

- Docker
    
- process managers
    
- CI/CD
    
- orchestration systems
    
- deployment platforms
    

because they can detect that the application failed to start.

# 24. A subtle problem in our current implementation

Our current `env.js` allows:


to potentially be:

```text

```

The final configuration architecture should eventually behave more like:

```text

       ↓

     /       \

```

We'll improve this later.

# 27. Why database connection belongs before `listen()`

Imagine:

```js
app.listen(5000);
mongoose.connect(...);
```

Now the server can accept:

```text
POST /api/v1/users
```

before MongoDB is ready.

That creates a race:

```text
HTTP server
      │
      ├──────────────► Request arrives
      │
      ▼
MongoDB still connecting...
```

Instead:

```js
await connectDB();
app.listen(...);
```

means:

```text
MongoDB ready
      ↓
HTTP server starts
      ↓
Requests accepted
```

Much cleaner.

# 28. Mongoose connection lifecycle

A useful mental model is:

```text
Disconnected
     ↓
Connecting
     ↓
Connected
     ↓
Disconnected
```

Your application should understand that the database is an external dependency.

It can fail because:

```text
network
database server
credentials
URI
DNS
deployment
maintenance
```

So production systems need proper startup and shutdown behavior.

We'll eventually handle graceful shutdown in the production-hardening phase.

---

# 29. What about connection pooling?

Mongoose/MongoDB uses connections efficiently rather than opening a brand-new TCP connection for every query.

Conceptually:

```text
Application
     │
     ▼
Mongoose
     │
     ▼
Connection Pool
 ┌───┼───┬───┐
 ▼   ▼   ▼   ▼
 DB connections
```

Then requests can reuse those connections.

You don't need to manually connect and disconnect for every request.

So **do not** write:

```js
// ❌ Don't do this per request
await mongoose.connect(...);
await User.find(...);
await mongoose.disconnect();
```

Instead:

```text
Application startup
       ↓
One managed database connection
       ↓
Many requests
```

---

# 30. What should the repository do?

This is important for the architecture we'll build later.

`config/db.js` handles:

```text
"Can I connect to MongoDB?"
```

It does **not** handle:

```text
"Find this user."
"Create this todo."
"Update this order."
```

Those belong later in:

```text
repositories/
```

So don't put queries inside `db.js`.

Bad:

```js
// ❌ db.js
await mongoose.connect(...);
await User.find(...);
```

Good:

```text
config/db.js
    ↓
connection

repositories/user.repository.js
    ↓
User queries
```

# 34. Common mistakes

### ❌ Starting Express before MongoDB

```js
app.listen(5000);
connectDB();
```

For a database-required backend, this creates the wrong startup order.

---

### ❌ Connecting on every request

```js
app.get("/users", async () => {
    await mongoose.connect(...);
});
```

Don't.

---

### ❌ Putting queries in `db.js`

```js
await User.find();
```

`db.js` should manage connection infrastructure.

---

### ❌ Hard-coding the URI

```js
mongoose.connect(
    "mongodb://localhost:27017/myapp"
);
```

Use:

```js
mongoose.connect(env.mongoUri);
```

---

### ❌ Silently continuing after connection failure

Bad:

```js
catch (error) {
    console.error(error);
}
```

and then allowing startup to continue.

If MongoDB is required, startup should fail.
