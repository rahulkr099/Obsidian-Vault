# Lesson 25.7 — Express App

We now have the first two important infrastructure pieces:

```text
.env
   ↓
config/env.js
   ↓
configuration

config/db.js
   ↓
MongoDB connection
```

Now we build the **Express application itself**.

The key idea for this lesson is:

> **Creating an Express app and starting an HTTP server are two different responsibilities.**

Your starter architecture keeps `app.js` and `server.js` separate for exactly this reason.

---

# 1. What are we building?

Our architecture will become:

```text
                    server.js
                       │
                       ▼
                    connectDB()
                       │
                       ▼
                    MongoDB
                       │
                       ▼
                     app.js
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
        middleware   routes   error handler
             │         │
             └────┬────┘
                  ▼
              HTTP server
```

More precisely:

```text
server.js
    ↓
startup orchestration

app.js
    ↓
Express application configuration
```

---

# 2. What is Express?

Express is the HTTP application framework we'll use on top of Node.js.

Without Express, you'd work directly with Node's HTTP APIs.

Express gives us a much cleaner abstraction:

```js
app.get("/users", handler);
```

instead of manually inspecting:

```text
request method
request URL
headers
body
response
```

So:

```text
Node.js
   ↓
Express
   ↓
Our application
```

---

# 3. Create the Express application

Open:

```text
app.js
```

Put this:

```js
import express from "express";

const app = express();

export default app;
```

That's our first Express application.

Very small.

And that's intentional.

---

# 4. Understand `express()`

This:

```js
const app = express();
```

creates an Express application object.

You can think of `app` as:

```text
Application
│
├── middleware
├── routes
├── error handling
└── HTTP behavior
```

Later we'll attach things to it:

```js
app.use(...)
app.get(...)
app.post(...)
```

But we're not going to put everything in `app.js`.

---

# 5. Why export `app`?

We use:

```js
export default app;
```

because another file needs the application.

That file will be:

```text
server.js
```

Eventually:

```js
import app from "./app.js";
```

Then:

```text
server.js
    ↓
gets Express app
    ↓
starts HTTP server
```

This separation is extremely useful.

---

# 6. App creation vs server startup

This is one of the most important concepts in this lesson.

### `app.js`

Creates/configures the Express application:

```text
middleware
routes
error handling
```

### `server.js`

Starts the actual HTTP server:

```text
database connection
server.listen()
shutdown handling
```

So:

```text
app.js
=
"What should this application do?"

server.js
=
"When and where should this application run?"
```

---

# 7. Why not put `app.listen()` in `app.js`?

You might see beginner projects doing:

```js
const app = express();

app.listen(5000);
```

inside `app.js`.

It works.

But it creates a problem.

Now simply importing the app:

```js
import app from "./app.js";
```

also starts a network server.

That's undesirable for testing.

---

# 8. Testing becomes easier

Imagine:

```text
tests
   ↓
import app
   ↓
make request
```

If `app.js` automatically calls:

```js
app.listen(...)
```

then your tests may unexpectedly start a real server.

Instead:

```text
app.js
   ↓
create/configure app only

server.js
   ↓
start server
```

Now tests can safely import:

```js
import app from "../app.js";
```

without starting the server.

This separation becomes especially useful when we build the testing architecture.

---

# 9. Add basic middleware

Our Express app currently does almost nothing.

Let's add JSON parsing.

Update `app.js`:

```js
import express from "express";

const app = express();

app.use(express.json());

export default app;
```

Now the architecture is:

```text
HTTP request
     ↓
express.json()
     ↓
route/controller
```

---

# 10. What does `express.json()` do?

Suppose the client sends:

```http
POST /api/v1/users
Content-Type: application/json
```

with:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

Without JSON parsing, Express doesn't automatically give you the parsed object in:

```js
req.body
```

With:

```js
app.use(express.json());
```

Express parses the JSON body.

Then the controller can access:

```js
req.body
```

which becomes:

```js
{
    name: "Rahul",
    email: "rahul@example.com"
}
```

---

# 11. Middleware is a pipeline

This is the mental model you should build now.

```text
Request
   ↓
Middleware 1
   ↓
Middleware 2
   ↓
Middleware 3
   ↓
Route
   ↓
Controller
   ↓
Response
```

For example, eventually:

```text
Request
   ↓
request ID
   ↓
security headers
   ↓
CORS
   ↓
JSON parser
   ↓
request logger
   ↓
authentication
   ↓
route
   ↓
controller
```

This is why `app.js` will eventually become the place where the application's middleware pipeline is assembled.

---

# 12. But don't put middleware implementations here

This is another architectural rule.

We could technically write:

```js
app.use((req, res, next) => {
    console.log(req.method);
    next();
});
```

directly inside `app.js`.

For tiny experiments, that's fine.

But in our starter:

```text
middlewares/
```

will contain reusable middleware implementations.

Then `app.js` will assemble them.

Think:

```text
middlewares/
    ↓
implementation

app.js
    ↓
composition
```

# 13. Add a health endpoint

Before adding the full routing system, let's create a tiny endpoint to prove our Express app works.

Add:

```js
app.get("/health", (req, res) => {
    res.status(200).json({
        success: true,
        message: "API is healthy",
    });
});
```

So `app.js` becomes:

```js
import express from "express";

const app = express();

app.use(express.json());

app.get("/health", (req, res) => {
    res.status(200).json({
        success: true,
        message: "API is healthy",
    });
});

export default app;
```

---

# 14. Why a health endpoint?

A health endpoint is useful for checking:

```text
Is the HTTP application alive?
```

For example:

```http
GET /health
```

could return:

```json
{
  "success": true,
  "message": "API is healthy"
}
```

Later, we can build more meaningful health/readiness checks.

For now, this gives us a simple way to verify Express.

---

# 15. Important distinction: health vs readiness

Don't confuse these concepts.

### Health

> Is the application process alive?

### Readiness

> Is the application actually ready to serve traffic?

For example:

```text
Express running
MongoDB disconnected
```

The process may be alive:

```text
health = OK
```

but it may not be ready:

```text
readiness = NOT READY
```

This distinction becomes important in Docker, Kubernetes, load balancers, and production deployments.

We'll revisit it later.

```js

```

This is exactly the separation we want.

# 18. Now let's understand `server.js`

We currently have:

```text
server.js
```

but it is empty.

Its eventual responsibility will be:

```text
Load configuration
       ↓
Connect database
       ↓
Import Express app
       ↓
Start HTTP server
```

Conceptually:

```js
import app from "./app.js";
import connectDB from "./config/db.js";
import env from "./config/env.js";

const startServer = async () => {
    await connectDB();

    app.listen(env.port, () => {
        console.log(`Server running on port ${env.port}`);
    });
};

startServer();
```

We'll build the proper version in the next lessons as we add startup and error-handling concerns.

For now, understand the separation.

We're getting here:

              │                   │

---

# 20. Why `app.js` should stay boring

This is actually a good thing.

A well-designed `app.js` should mostly look like:

```js
const app = express();

app.use(...);
app.use(...);
app.use(...);

app.use("/api/v1/auth", authRoutes);
app.use("/api/v1/users", userRoutes);

app.use(notFoundHandler);
app.use(errorHandler);

export default app;
```

Notice what it **doesn't** contain:

```text
database queries
business logic
JWT implementation
password hashing
email implementation
large validation schemas
```

Those belong elsewhere.

`app.js` is primarily a **composition root for the HTTP layer**.

---

# 21. What is a composition root?

This is a useful professional concept.

A composition root is a place where application components are assembled.

For our Express application:

```text
app.js
```

will eventually connect:

```text
middleware
+
routes
+
error handling
```

into one application.

It doesn't need to implement those components.

It simply composes them.

---

# 22. Route mounting will come later

Eventually we'll do something like:

```js
import authRoutes from "./routes/auth.routes.js";
import userRoutes from "./routes/user.routes.js";

app.use("/api/v1/auth", authRoutes);
app.use("/api/v1/users", userRoutes);
```

Then:

```text
POST /api/v1/auth/login
```

flows into:

```text
/auth routes
    ↓
controller
    ↓
service
    ↓
repository
```

But we're deliberately not creating those route files yet.

---

# 23. Why `/api/v1`?

We'll eventually use API versioning.

For example:

```text
/api/v1/users
/api/v1/auth/login
/api/v1/products
```

The reason is that APIs evolve.

You might eventually have:

```text
/api/v1/users
/api/v2/users
```

without immediately breaking every existing client.

We'll design the actual API routing structure later.

---

# 24. What about CORS?

Not yet.

Eventually we'll add something like:

```js
app.use(cors(...));
```

But CORS configuration should be deliberate.

It shouldn't simply be:

```js
app.use(cors());
```

in production without understanding what that means.

We'll cover CORS in the security/middleware portion of the starter.

---

# 25. What about Helmet?

Same idea.

We'll eventually have security middleware.

Conceptually:

```text

   ↓
security middleware
   ↓
request parsing
   ↓
logging
   ↓
routes
```

But don't randomly install and configure every middleware now.

We're building the system in layers.

# 28. One important architectural distinction

Keep these three concepts separate in your head:

### Express application

```js
const app = express();
```

### Middleware

```js
app.use(...)
```

### HTTP server

```js
app.listen(...)
```

They are related, but they're not the same thing.

Think:

```text
Express App
    │
    ├── middleware
    ├── routes
    └── handlers
         │
         ▼
      HTTP Server
```

---

# 29. Why this matters for testing

Later, we'll be able to test:

```text
app.js
```

without starting:

```text
server.js
```

That means:

```text
Test
 ↓
import app
 ↓
send fake HTTP request
 ↓
inspect response
```

instead of:

```text
Start real server
 ↓
find available port
 ↓
send request
 ↓
stop server
```

This makes automated testing cleaner.

# 30. Common mistakes

### ❌ Mistake 1: Start the server inside `app.js`

```js
app.listen(5000);
```

Don't do that.

Keep startup in `server.js`.

---

### ❌ Mistake 2: Put database connection inside `app.js`

Don't:

```js
mongoose.connect(...);
```

inside the Express application setup.

Database startup belongs to the startup layer.

---

### ❌ Mistake 3: Put business logic in routes

Don't eventually create:

```js
app.post("/users", async (req, res) => {
    // 100 lines of business logic
});
```

We'll use:

```text
route
 ↓
controller
 ↓
service
 ↓
repository
```

---

### ❌ Mistake 4: Turn `app.js` into a giant file

If `app.js` becomes 1,000 lines long, that's a sign that responsibilities aren't being separated properly.
