# Lesson 25.8 — Server Startup

Now we're going to connect everything we've built so far.

We currently have three separate pieces:

```text
config/env.js
    ↓
configuration

config/db.js
    ↓
MongoDB connection

app.js
    ↓
Express application
```

The missing piece is:

```text
server.js
```

Its job is to **orchestrate startup**.

The roadmap's intended flow is:

```text
server.js
   ↓
connectDB()
   ↓
MongoDB ready
   ↓
start HTTP server
```

The important rule is that the application should **not accept HTTP requests before the required database connection is ready**.

---

# 1. What is server startup?

When you run:

```bash
npm run dev
```

something has to happen.

We want:

```text
Node starts
   ↓
Load configuration
   ↓
Connect MongoDB
   ↓
MongoDB succeeds
   ↓
Create/start HTTP server
   ↓
Application ready
```

If MongoDB fails:

```text
Node starts
   ↓
Connect MongoDB
   ↓
❌ Failure
   ↓
Exit process
```

We don't want:

```text
MongoDB ❌
   ↓
Express still starts
   ↓
Requests arrive
   ↓
Database operations fail
```

---

# 2. `app.js` vs `server.js`

This distinction should now be very clear.

### `app.js`

Responsible for:

```text
Express application
Middleware
Routes
Error handling
```

### `server.js`

Responsible for:

```text
Startup
Database connection
HTTP server
Shutdown
```

Think:

```text
app.js
=
WHAT the application does

server.js
=
HOW the application starts
```

# 3. What does `app.listen()` actually do?

When we write:

```js
app.listen(5000);
```

Express asks Node to create an HTTP server and listen for incoming connections.

Conceptually:

```text
Internet / Browser / Frontend
            │
            ▼
       HTTP server
            │
            ▼
        Express app
            │
            ▼
          Route
```

So `app.listen()` is the point where our application becomes reachable over the network.

# 14. What happens if MongoDB is down?

Stop MongoDB.

Then run:

```bash
npm run dev
```

You should see the connection error from `db.js`.

Because `connectDB()` calls:

```js
process.exit(1);
```

the application terminates.

The important behavior is:

```text
MongoDB unavailable
       ↓
connectDB() fails
       ↓
process exits
       ↓
HTTP server never starts
```

That's exactly what we want for a backend that requires MongoDB.

---

# 15. Why is this called "fail fast"?

**Fail fast** means:

> Detect a critical problem as early as possible instead of allowing the application to continue in a broken state.

Bad:

```text
MongoDB ❌
   ↓
Server starts
   ↓
Requests accepted
   ↓
Requests fail
```

Good:

```text
MongoDB ❌
   ↓
Startup fails
   ↓
Process exits
```

The second behavior is easier to understand and operate.

# 16. What happens if the port is already used?

Suppose another application is already using:

```text
5000
```

Then:

```js
app.listen(5000)
```

will fail.

You might see an error similar to:

```text
EADDRINUSE
```

meaning:

> Address already in use.

For example:

```bash
lsof -i :5000
```

can help identify what's using the port on Linux.

Then you can stop that process or choose another port.

# 17. One improvement: handle startup errors

Our current version has:

```js
const startServer = async () => {
    await connectDB();

    app.listen(...);
};

startServer();
```

This works because `connectDB()` already handles its own connection failure.

But there is another possible failure:

```text
app.listen()
```

itself can fail.

For example:

```text
port already occupied
permission issue
network configuration issue
```

So let's make startup more robust.

Use:

```js
import app from "./app.js";
import connectDB from "./config/db.js";
import env from "./config/env.js";

const startServer = async () => {
    try {
        await connectDB();

        app.listen(env.port, () => {
            console.log(`Server running on port ${env.port}`);
        });
    } catch (error) {
        console.error("Server startup failed:", error);
        process.exit(1);
    }
};

startServer();
```

Now startup has a clear failure boundary.

---

# 18. But there's a subtle issue

Our `connectDB()` currently catches its own error:

```js
try {
    await mongoose.connect(env.mongoUri);
} catch (error) {
    console.error(...);
    process.exit(1);
}
```

Because it calls:

```js
process.exit(1)
```

the error never reaches:

```js
catch (error)
```

inside `startServer()`.

That's not necessarily wrong, but it means responsibility is split.

We eventually want a cleaner error-handling architecture.

For now, understand that the database layer handles its connection failure and startup owns the overall startup sequence.

---

# 19. A cleaner database function

A more composable version of `config/db.js` would be:

```js
import mongoose from "mongoose";
import env from "./env.js";

const connectDB = async () => {
    try {
        await mongoose.connect(env.mongoUri);

        console.log("MongoDB connected");
    } catch (error) {
        console.error("MongoDB connection failed:", error.message);
        throw error;
    }
};

export default connectDB;
```

Notice:

```js
throw error;
```

instead of:

```js
process.exit(1);
```

Now the responsibility becomes:

```text
db.js
   ↓
report/propagate database failure

server.js
   ↓
decide whether startup should terminate
```

This is usually a cleaner separation.

---

# 20. Which version should you use?

For our starter architecture, I recommend the cleaner version:

### `config/db.js`

```js
import mongoose from "mongoose";
import env from "./env.js";

const connectDB = async () => {
    try {
        await mongoose.connect(env.mongoUri);

        console.log("MongoDB connected");
    } catch (error) {
        console.error("MongoDB connection failed:", error.message);
        throw error;
    }
};

export default connectDB;
```

### `server.js`

```js
import app from "./app.js";
import connectDB from "./config/db.js";
import env from "./config/env.js";

const startServer = async () => {
    try {
        await connectDB();

        app.listen(env.port, () => {
            console.log(`Server running on port ${env.port}`);
        });
    } catch (error) {
        console.error("Server startup failed:", error);
        process.exit(1);
    }
};

startServer();
```

Now responsibilities are clearer.

# 21. Why throw instead of exit?

Compare:

```js
process.exit(1);
```

with:

```js
throw error;
```

`process.exit()` makes the lower-level database module decide:

> The entire application must terminate.

That's a very strong decision.

Instead:

```js
throw error;
```

says:

> Something went wrong. The caller should decide what to do.

Then:

```text
db.js
   ↓
throw
   ↓
server.js
   ↓
exit
```

This gives us more flexibility.

---

# 22. Think in layers

This is an important backend engineering habit.

Lower layers should generally report problems.

Higher layers decide application-level behavior.

For example:

```text
MongoDB
   ↓
Mongoose
   ↓
db.js
   ↓
server.js
   ↓
process termination
```

The lower layer shouldn't necessarily control the entire application lifecycle.

# 32. The startup contract

Our backend now has a simple startup contract:

```text
1. Configuration must be available.
2. Database must connect.
3. HTTP server can start.
```

In shorthand:

```text
CONFIG
  ↓
DATABASE
  ↓
HTTP
```

This order is extremely important.

# 33. Why this matters in Docker

Later, when we put the application into Docker, the container might start:

```text
Container
   ↓
node server.js
```

If MongoDB is unavailable:

```text
server.js
   ↓
connectDB()
   ↓
failure
   ↓
exit 1
```

Docker can then detect that the process failed.

This is much better than a container that stays "running" while the application cannot actually function.

This connects directly with the Docker architecture and production-hardening work you'll build later.

# 34. Don't confuse MongoDB readiness with HTTP readiness

Suppose:

```text
Node process = alive
Express = initialized
MongoDB = unavailable
```

Then:

```text
Process alive = true
Application ready = false
```

That's why production systems often distinguish:

```text
liveness
readiness
```

Our `/health` endpoint is currently very simple.

Later we'll make health/readiness checks more meaningful.

# 35. Common mistakes

### ❌ Starting HTTP before DB

```js
app.listen(env.port);
await connectDB();
```

Wrong order for a DB-required application.

---

### ❌ Starting DB from `app.js`

```js
// app.js
await connectDB();
```

Keep application construction separate from startup.

---

### ❌ Using `process.env.PORT` directly

Prefer:

```js
env.port
```

because configuration is centralized.

---

### ❌ Calling `process.exit()` everywhere

Don't make every module decide when the entire application should die.

Prefer:

```text
lower layer
   ↓
throw error
   ↓
startup layer
   ↓
decide
```

---

### ❌ Putting `app.listen()` in `app.js`

Keep:

```text
app.js → application
server.js → startup
```
