# Lesson 25.9 — Middleware Pipeline

Now that our backend can actually start, we're ready to build the **middleware pipeline**.

Our current flow is:

```text
server.js
   ↓
connectDB()
   ↓
app.js
   ↓
Express
   ↓
/health
```

But a real backend needs several things to happen **before a request reaches a route**.

The roadmap specifically places middleware composition inside `app.js`, with middleware such as security, CORS, parsing, request IDs, logging, and error handling assembled in a deliberate order.

---

# 1. What is middleware?

Middleware is code that runs during the request/response lifecycle.

Think of a request moving through a pipeline:

```text
Client
  │
  ▼
Middleware 1
  │
  ▼
Middleware 2
  │
  ▼
Middleware 3
  │
  ▼
Route
  │
  ▼
Controller
  │
  ▼
Response
```

For example:

```text
GET /api/v1/users
       │
       ▼
Request ID
       │
       ▼
Security headers
       │
       ▼
CORS
       │
       ▼
JSON parsing
       │
       ▼
Logging
       │
       ▼
Authentication
       │
       ▼
Route
```

---

# 2. The three arguments

A normal Express middleware receives:

```js
(req, res, next)
```

For example:

```js
const middleware = (req, res, next) => {
    console.log("Request received");

    next();
};
```

They represent:

### `req`

The incoming request.

```js
req.method
req.url
req.headers
req.body
```

### `res`

The outgoing response.

```js
res.status(...)
res.json(...)
res.send(...)
```

### `next`

A function that tells Express:

> Continue to the next middleware.

---

# 3. Why `next()` matters

Consider:

```js
app.use((req, res, next) => {
    console.log("Middleware 1");

    next();
});
```

The request continues.

Without:

```js
next();
```

the request can get stuck.

For example:

```js
app.use((req, res, next) => {
    console.log("Hello");
});
```

There's no:

```js
next();
```

and no response:

```js
res.json(...)
```

So the request can remain hanging.

---

# 4. Middleware can end the request

Middleware doesn't always need to call `next()`.

It can send a response directly:

```js
app.use((req, res) => {
    res.status(401).json({
        success: false,
        message: "Unauthorized",
    });
});
```

The pipeline stops there.

This is useful for things like:

```text
authentication failure
rate limiting
maintenance mode
request blocking
```

So middleware has two basic choices:

```text
Continue
   ↓
next()

OR

Stop
   ↓
send response
```

---

# 5. Middleware ordering matters

This is one of the most important lessons.

Suppose:

```js
app.use(express.json());

app.use("/api/v1/users", userRoutes);
```

The JSON parser runs before the user routes.

Good.

But if you accidentally do:

```js
app.use("/api/v1/users", userRoutes);

app.use(express.json());
```

then the route may execute before the JSON body parser.

The order becomes:

```text
Request
   ↓
User route
   ↓
JSON parser ❌
```

instead of:

```text
Request
   ↓
JSON parser
   ↓
User route
```

So middleware order is part of application behavior.

# 8. Security middleware

Security middleware modifies or validates incoming/outgoing HTTP behavior.

A common package is:

```text
helmet
```

It helps set security-related HTTP headers.

Install it:

```bash
npm install helmet
```

Then:

```js
import helmet from "helmet";
```

and:

```js
app.use(helmet());
```

So:

```text
Request
   ↓
Helmet
   ↓
other middleware
   ↓
route
```

---

# 9. Why security headers?

Browsers understand various HTTP security headers.

For example, headers can help control:

```text
content loading
framing behavior
MIME sniffing
referrer behavior
```

The important point is:

> Security should be established as part of the application's HTTP pipeline rather than added randomly to individual routes.

Your broader security roadmap treats secure headers and middleware as part of the API security layer.

# 11. CORS

Next is:

> Cross-Origin Resource Sharing.

Suppose your backend runs:

```text
http://localhost:5000
```

and your frontend runs:

```text
http://localhost:5173
```

These are different origins.

The browser applies same-origin rules.

Your backend needs to explicitly decide which frontend origins are allowed.

---

# 12. Install CORS

Run:

```bash
npm install cors
```

Then:

```js
import cors from "cors";
```

A very permissive configuration would be:

```js
app.use(cors());
```

But don't blindly use that in production.

For our architecture, we already have:

```env
FRONTEND_URL=http://localhost:5173
```

So we can eventually configure:

```js
app.use(
    cors({
        origin: env.frontendUrl,
    })
);
```

This connects CORS to our centralized environment system.

---

# 13. Why centralize the frontend URL?

Instead of:

```js
origin: "http://localhost:5173"
```

we use:

```js
origin: env.frontendUrl
```

Then:

```text
Development
FRONTEND_URL=http://localhost:5173

Production
FRONTEND_URL=https://your-production-frontend.com
```

Same application code.

Different configuration.

That's exactly why we built `config/env.js`.

# 15. Request IDs

Now let's introduce an extremely useful production concept:

> **Every request should have a unique identifier.**

Imagine a user reports:

> "My request failed."

You look at your logs.

There may be thousands of requests.

How do you find the exact request?

A request ID gives you a correlation key.

Example:

```text
Request ID: 7f3d...
```

Then the same ID can appear in:

```text
request log
controller log
service log
error log
```

This is particularly useful given the logging and observability architecture we've already covered in earlier phases.

---

# 16. A simple request ID middleware

Create:

```text
middlewares/
└── requestId.middleware.js
```

Run:

```bash
touch middlewares/requestId.middleware.js
```

Put:

```js
import crypto from "node:crypto";

const requestId = (req, res, next) => {
    const id = req.headers["x-request-id"] || crypto.randomUUID();

    req.id = id;
    res.setHeader("x-request-id", id);

    next();
};

export default requestId;
```

Let's understand this.

---

# 17. Generate a UUID

```js
crypto.randomUUID()
```

generates a unique identifier.

For example:

```text
9c7c9d1e-...
```

This is useful as a request correlation ID.

---

# 18. Respect an existing request ID

We use:

```js
req.headers["x-request-id"] || crypto.randomUUID()
```

Meaning:

```text
Incoming request has ID?
        │
      ┌─┴─┐
     YES  NO
      │    │
      ▼    ▼
   reuse  generate
```

This can be useful when another service already assigned a request ID.

---

# 19. Store the ID on `req`

```js
req.id = id;
```

Now downstream code can access:

```js
req.id
```

For example:

```js
console.log({
    requestId: req.id,
});
```

Later our structured logger can automatically include it.

---

# 20. Return the request ID

We also send:

```js
res.setHeader("x-request-id", id);
```

So the client can see:

```http
X-Request-ID: 9c7c9d1e-...
```

This is useful when debugging API problems.

The client can tell you:

> "Request ID `9c7c9d1e...` failed."

You can then search your logs for that exact ID.

---

# 21. Add request ID middleware

In `app.js`:

```js
import express from "express";
import helmet from "helmet";
import cors from "cors";
import env from "./config/env.js";
import requestId from "./middlewares/requestId.middleware.js";

const app = express();

app.use(requestId);

app.use(helmet());

app.use(
    cors({
        origin: env.frontendUrl,
    })
);

app.use(express.json());

app.get("/health", (req, res) => {
    res.status(200).json({
        success: true,
        message: "API is healthy",
        requestId: req.id,
    });
});

export default app;
```

Now:

```bash
curl -i http://localhost:5000/health
```

You should see something similar to:

```text
HTTP/1.1 200 OK
X-Request-ID: 9c7c9d1e-...
```

and:

```json
{
  "success": true,
  "message": "API is healthy",
  "requestId": "9c7c9d1e-..."
}
```

---

# 22. Why request ID should happen early

Imagine this pipeline:

```text
Request
   ↓
Authentication
   ↓
Validation
   ↓
Request ID ❌
```

If authentication fails, there may be no request ID.

Instead:

```text
Request
   ↓
Request ID
   ↓
Authentication
   ↓
Validation
```

Now even rejected requests have an identifier.

That's why request identification is normally established very early.

# 23. Request parsing

We already have:

```js
app.use(express.json());
```

This handles JSON requests.

But you may also eventually need:

```text
URL encoded forms
multipart/form-data
file uploads
raw webhooks
```

Don't add every parser automatically.

Each parser has a purpose and security implications.

For our API, JSON is the main body format.

---

# 24. Body size limits

This is an important security improvement.

Instead of:

```js
app.use(express.json());
```

we can use:

```js
app.use(
    express.json({
        limit: "1mb",
    })
);
```

Why?

Because clients shouldn't be allowed to send unlimited request bodies.

Without reasonable limits, an attacker could send unnecessarily large payloads and consume memory/resources.

So:

```text
Request body
     ↓
Is it within allowed size?
     │
   ┌─┴─┐
  YES  NO
   │    │
   ▼    ▼
continue reject
```

---

# 25. Update JSON parsing

Use:

```js
app.use(
    express.json({
        limit: "1mb",
    })
);
```

This is a good starting point for a JSON API.

The exact limit should eventually be chosen based on the application's real requirements.

# 26. Middleware ordering

Our current pipeline is approximately:

```text
Request
   ↓
Request ID
   ↓
Helmet
   ↓
CORS
   ↓
JSON parser
   ↓
Routes
```

This ordering is intentional.

But there isn't one universal order for every backend.

You need to ask:

> What information does this middleware depend on, and what should happen before it?

That's how professional middleware ordering should be designed.

# 28. Authentication should not be global

One common beginner mistake is:

```js
app.use(authenticate);
```

for every route.

That would also protect:

```text
/health
/login
/register
```

which may not be what you want.

Instead, authentication is usually attached to protected route groups:

```js
app.use("/api/v1/users", authenticate, userRoutes);
```

while public routes remain accessible:

```text
/api/v1/auth/login
/api/v1/auth/register
/health
```

We'll build this properly later.

---

# 29. Logging middleware

We already have a dedicated logging architecture from earlier phases.

For now, don't create a second homemade logging system with:

```js
console.log(req.method, req.url);
```

everywhere.

Eventually the middleware pipeline should connect to our structured logger.

Conceptually:

```text
Request
   ↓
Request ID
   ↓
Logger
   ↓
Route
   ↓
Logger
   ↓
Response
```

The request ID lets the logs correlate one request across the application.

---

# 30. Why middleware should be reusable

Instead of putting this:

```js
app.use((req, res, next) => {
    ...
});
```

everywhere, create reusable middleware files:

```text
middlewares/
├── requestId.middleware.js
├── auth.middleware.js
├── rateLimit.middleware.js
├── validate.middleware.js
├── notFound.middleware.js
└── error.middleware.js
```

Then `app.js` composes them.

This gives us:

```text
middleware implementation
          ↓
       app.js
          ↓
     application
```

rather than giant anonymous functions inside `app.js`.

---

# 31. Error middleware is special

Normal middleware:

```js
(req, res, next)
```

Error middleware:

```js
(err, req, res, next)
```

That extra first argument tells Express:

> This middleware handles errors.

For example:

```js
const errorHandler = (err, req, res, next) => {
    // handle error
};
```

We'll build our centralized error middleware shortly.

For now, remember:

```text
Normal middleware
(req, res, next)

Error middleware
(err, req, res, next)
```

---

# 32. Error middleware goes near the end

This is important.

Generally:

```text
Routes
   ↓
404 handler
   ↓
Error handler
```

Why?

Because the error handler should catch errors generated by earlier middleware/routes.

If you put it too early:

```text
Error handler
   ↓
Routes
```

it won't automatically handle errors from middleware that comes after it in the pipeline.

---

# 33. 404 is not necessarily an error

Suppose:

```http
GET /does-not-exist
```

No route matches.

That's a **not found** condition.

We can create:

```js
const notFound = (req, res) => {
    res.status(404).json({
        success: false,
        message: "Route not found",
    });
};
```

Then mount it after all routes.

Conceptually:

```text
Request
   ↓
Routes
   ↓
No match
   ↓
404 middleware
```

We'll implement this in the next middleware lessons.

# 35. But don't memorize the exact order

The important thing isn't:

```text
requestId → helmet → cors → json
```

as a magic formula.

The important thing is understanding **why** middleware is ordered.

For every middleware, ask:

1. What does it do?
    
2. What does it depend on?
    
3. What should happen before it?
    
4. What should happen after it?
    
5. Can it terminate the request?
    
6. Should it run for every route?
    

That thinking will scale much better than memorizing snippets.

# 38. Important security idea

Middleware is not automatically secure just because you installed a package.

For example:

```js
cors()
```

doesn't mean:

> CORS is securely configured.

And:

```js
helmet()
```

doesn't mean:

> The entire API is secure.

Security requires understanding:

```text
configuration
+
middleware
+
authentication
+
authorization
+
validation
+
rate limiting
+
secure headers
+
logging
+
secrets
```

That's why your roadmap treats security as a cross-cutting concern rather than one magic middleware package.
