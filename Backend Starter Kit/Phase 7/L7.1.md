# Lesson 7.1 — What Is Middleware?

Let's begin from the absolute basics.

Suppose your React frontend sends:

```http
GET /api/v1/todos
```

Your Express server receives this request.

A very simple backend could look like:

```js
app.get("/api/v1/todos", (req, res) => {
    res.json({
        success: true,
        todos: []
    });
});
```

The request comes in and the route directly sends a response.

But real applications need to do things **before** the controller runs.

For example:

```text
Request
   ↓
Check authentication
   ↓
Check rate limit
   ↓
Validate input
   ↓
Log request
   ↓
Controller
   ↓
Response
```

Those intermediate functions are called **middleware**.

---

## 1. Simple Definition

In Express:

> **Middleware is a function that runs between the incoming request and the final response.**

Think of it like a checkpoint.

```text
Client
  │
  │ HTTP Request
  ▼
┌───────────────┐
│  Middleware   │
└───────┬───────┘
        │
        ▼
    Controller
        │
        ▼
     Response
```

Middleware can:

1. Read the request.
    
2. Modify the request.
    
3. Modify the response.
    
4. Perform some operation.
    
5. Stop the request.
    
6. Pass the request to the next function.
    

---

# 2. Real-World Analogy

Imagine entering an airport.

```text
You
 ↓
Security check
 ↓
Passport check
 ↓
Boarding check
 ↓
Aircraft
```

Each checkpoint performs a different job.

Your backend works similarly:

```text
HTTP Request
     ↓
Request ID middleware
     ↓
Logger middleware
     ↓
Authentication middleware
     ↓
Validation middleware
     ↓
Controller
     ↓
Database
```

Each middleware handles **one particular responsibility**.

---

# 3. The Basic Middleware Function

A basic Express middleware looks like this:

```js
const logger = (req, res, next) => {
    console.log("Request received");

    next();
};
```

There are three important things here:

```js
req
res
next
```

We'll study each deeply in **Lesson 7.4**.

For now, remember:

```text
req
 ↓
Incoming request

res
 ↓
Outgoing response

next()
 ↓
Continue to the next middleware
```

---

# 4. Using Middleware

Suppose we have:

```js
const logger = (req, res, next) => {
    console.log("Request received");

    next();
};
```

We can register it:

```js
app.use(logger);
```

Now:

```text
GET /todos
```

will go through:

```text
Request
   ↓
logger
   ↓
Route
   ↓
Response
```

---

# 5. What Happens Without `next()`?

Consider:

```js
const logger = (req, res, next) => {
    console.log("Request received");
};
```

Notice:

```js
next();
```

is missing.

The middleware doesn't send a response either.

So Express reaches:

```text
Request
   ↓
logger
   ↓
???
```

The request can remain hanging because you've told Express:

> "I'm handling this request, but I'm not sending a response and I'm not allowing anything else to continue."

That's one of the most common beginner mistakes.

---

# 6. Middleware Can Stop a Request

Middleware doesn't always have to call `next()`.

For example:

```js
const maintenanceMode = (req, res, next) => {
    return res.status(503).json({
        success: false,
        message: "Server is under maintenance"
    });
};
```

Here:

```text
Request
   ↓
maintenanceMode
   ↓
503 Response
```

The controller is never reached.

This is useful for things like:

```text
Authentication failure
Rate limit exceeded
Invalid input
Maintenance mode
Blocked origin
Permission denied
```

---

# 7. Middleware Can Modify `req`

Middleware can attach information to the request.

For example:

```js
const addRequestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    next();
};
```

Then later:

```js
app.get("/todos", (req, res) => {
    console.log(req.requestId);

    res.json({
        success: true
    });
});
```

So the request can move through the application carrying additional information:

```text
Incoming Request
       ↓
requestId middleware
       ↓
req.requestId added
       ↓
controller
       ↓
uses req.requestId
```

This idea becomes very important later when we build:

```text
Authentication
Request IDs
Logging
Authorization
```

---

# 8. Middleware Can Modify `res`

Middleware can also add something to the response.

For example:

```js
const responseTime = (req, res, next) => {
    res.setHeader("X-App-Version", "1.0");

    next();
};
```

Then the response contains:

```http
X-App-Version: 1.0
```

This becomes useful for things like:

```text
Security headers
Response metadata
Caching
Tracing
```

---

# 9. Middleware Doesn't Have to Be Security

This is an important point.

When you hear:

> middleware

don't immediately think:

> authentication.

Middleware can do many different things.

### Logging

```text
logger
```

### Authentication

```text
authenticateUser
```

### Authorization

```text
requireAdmin
```

### Validation

```text
validateRequest
```

### Security

```text
rateLimiter
```

### Request processing

```text
requestId
```

### Error handling

```text
errorHandler
```

So middleware is a **mechanism**, not a specific feature.

# 11. Your First Practical Exercise

Create a small Express project with this middleware:

```js
const logger = (req, res, next) => {
    console.log(`${req.method} ${req.url}`);

    next();
};
```

Register it:

```js
app.use(logger);
```

Then create:

```js
app.get("/", (req, res) => {
    res.json({
        message: "Hello World"
    });
});
```

Start your server and visit:

```text
http://localhost:5000/
```

You should see something similar in the terminal:

```text
GET /
```

And the browser/Postman should receive:

```json
{
    "message": "Hello World"
}
```

# 12. Your First Challenge

Don't copy the answer for this one.

Create a middleware called:

```text
requestTimer
```

Its job:

1. Record the time when the request arrives.
    
2. Call `next()`.
    
3. When the response finishes, calculate how long the request took.
    
4. Print something like:
    

```text
GET /todos → 12ms
```

**Hint:** You'll need to explore the response object's events. We'll properly discuss this kind of middleware later.
