# Phase 7 — Lesson 7.10

## Built-in Express Middleware

Now you've learned how to **write your own middleware**.

Today we're going to learn the middleware that Express already provides.

Your roadmap places **Built-in Express Middleware** at 7.10, followed by deeper lessons on `express.json()`, `express.urlencoded()`, and `cookie-parser`.

The important idea is:

> **Built-in middleware is functionality that Express provides so you don't have to write common request-processing logic yourself.**

---

# 1. First, What Does "Built-in" Mean?

You've already created middleware like:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);

    next();
};
```

That's **custom middleware**.

Express also provides middleware for common jobs.

For example:

```js
app.use(express.json());
```

Here:

```text
express.json()
      ↓
returns middleware
      ↓
app.use(...)
      ↓
middleware enters Express pipeline
```

So built-in middleware follows exactly the same middleware concept you've already learned.

---

# 2. The Important Built-in Middleware

For this course, the important ones are:

```text
express.json()
express.urlencoded()
express.static()
```

And you'll also commonly use packages such as:

```text
cookie-parser
cors
helmet
express-rate-limit
```

But there's an important distinction.

### Express built-ins

Provided by Express itself:

```text
express.json()
express.urlencoded()
express.static()
```

### Third-party middleware

Installed separately:

```text
cookie-parser
cors
helmet
express-rate-limit
```

Your starter roadmap specifically treats `cookie-parser` as the next lesson after the Express built-ins.

---

# 3. Why Do We Need Built-in Middleware?

Because HTTP requests contain data in different formats.

For example:

```text
Request
 ├── headers
 ├── URL
 ├── query parameters
 ├── route parameters
 ├── cookies
 └── body
```

Express needs some middleware to help your application understand certain parts of that request.

For example, suppose React sends:

```json
{
    "title": "Learn Express"
}
```

Your controller wants:

```js
req.body.title
```

Something needs to parse that JSON.

That's what:

```js
express.json()
```

helps with.

---

# 4. Think of Middleware as Translators

This is a useful mental model.

The client sends something in an HTTP format.

Middleware prepares it for your JavaScript application.

```text
HTTP Request
     ↓
Middleware
     ↓
JavaScript-friendly data
     ↓
Controller
```

For JSON:

```text
JSON body
   ↓
express.json()
   ↓
req.body
   ↓
controller
```

For URL-encoded data:

```text
URL-encoded body
   ↓
express.urlencoded()
   ↓
req.body
   ↓
controller
```

---

# 5. `express.json()`

This is probably the most important built-in middleware you'll use in a REST API.

You write:

```js
app.use(express.json());
```

This tells Express:

> "Parse incoming JSON request bodies."

Then:

```js
app.post("/todos", (req, res) => {
    console.log(req.body);

    res.json({
        success: true
    });
});
```

If the client sends:

```json
{
    "title": "Learn Middleware"
}
```

the controller can access:

```js
req.body.title
```

We'll spend the entire **7.11** lesson on this, so don't worry about memorizing its details yet.

---

# 6. `express.urlencoded()`

Another built-in middleware is:

```js
app.use(
    express.urlencoded({
        extended: true
    })
);
```

It parses URL-encoded request bodies.

This format commonly appears with traditional HTML forms.

For example:

```text
username=rahul&email=test@example.com
```

After parsing, the application can access:

```js
req.body.username
req.body.email
```

We'll study this properly in **7.12**.

---

# 7. `express.static()`

Express also has:

```js
express.static()
```

This is used to serve static files.

For example:

```text
public/
├── index.html
├── style.css
├── logo.png
└── app.js
```

You can write:

```js
app.use(
    express.static("public")
);
```

Now Express can serve files from that directory.

Conceptually:

```text
Browser
   ↓
GET /logo.png
   ↓
express.static()
   ↓
public/logo.png
   ↓
Response
```

---

# 8. Why `express.static()` Is Less Important for Your MERN API

In a typical MERN setup:

```text
React
   ↓
Vercel / frontend server
```

and:

```text
Express API
   ↓
Backend server
```

Your Express application often isn't responsible for serving the React application's static assets.

Instead, your backend mainly handles:

```text
API requests
   ↓
Express
   ↓
Controllers
   ↓
Database
```

Still, `express.static()` is important to know because Express provides it and it is useful in some applications.

---

# 9. Built-in vs Third-Party Middleware

This distinction is important.

### Built into Express

```js
express.json()
express.urlencoded()
express.static()
```

You don't install a separate package for these.

### Third-party

For example:

```js
import cookieParser from "cookie-parser";
```

You need:

```bash
npm install cookie-parser
```

Then:

```js
app.use(cookieParser());
```

Similarly:

```text
cors
helmet
express-rate-limit
```

are external packages.

---

# 10. Why Does Express Need Middleware at All?

Let's connect this to your previous lessons.

Without middleware:

```text
Request
   ↓
Route
   ↓
Controller
```

With body parsing:

```text
Request
   ↓
express.json()
   ↓
Route
   ↓
Controller
```

With authentication:

```text
Request
   ↓
express.json()
   ↓
authenticate
   ↓
Route
   ↓
Controller
```

With logging:

```text
Request
   ↓
express.json()
   ↓
requestId
   ↓
logger
   ↓
authenticate
   ↓
Route
   ↓
Controller
```

So built-in middleware is simply another layer in the pipeline.

# 11. A Small Application

Let's create a simple backend:

```js
import express from "express";

const app = express();

app.use(express.json());

app.post("/todos", (req, res) => {
    console.log(req.body);

    res.status(201).json({
        success: true,
        todo: req.body
    });
});

app.listen(5000, () => {
    console.log("Server running on port 5000");
});
```

Now send:

```http
POST /todos
Content-Type: application/json
```

Body:

```json
{
    "title": "Learn Express"
}
```

The flow is:

```text
POST /todos
     ↓
express.json()
     ↓
req.body
     ↓
POST /todos route
     ↓
res.json()
```

---

# 12. What Happens Without `express.json()`?

Try removing:

```js
app.use(express.json());
```

Then send:

```json
{
    "title": "Learn Express"
}
```

Your route won't have the parsed JSON body available in the same way.

You may see:

```js
req.body
```

as `undefined` or otherwise not contain the parsed object you expected.

This is why you'll very commonly see:

```js
app.use(express.json());
```

near the beginning of an Express application.

---

# 13. Why Does It Come Before Routes?

Because the route needs the parsed body.

Correct:

```js
app.use(express.json());

app.post("/todos", createTodo);
```

Think:

```text
Request
   ↓
JSON parser
   ↓
req.body available
   ↓
route
   ↓
controller
```

If you don't put the parser into the pipeline before the relevant route, the route can't rely on it having processed the request.

This is exactly the middleware-order principle from **7.6**.

---

# 14. Content-Type Matters

Suppose the client sends:

```http
Content-Type: application/json
```

with:

```json
{
    "title": "Learn Express"
}
```

Then:

```js
express.json()
```

is designed to parse that JSON body.

Think:

```text
Content-Type
      ↓
application/json
      ↓
express.json()
      ↓
req.body
```

This is why understanding HTTP basics is useful.

The parser needs to know what kind of body it's dealing with.

---

# 15. Built-in Middleware Doesn't Replace Validation

This is very important.

Suppose:

```js
app.use(express.json());
```

and the client sends:

```json
{
    "random": "data"
}
```

`express.json()` doesn't decide:

> "Is this a valid Todo?"

It only helps parse the JSON.

So:

```text
express.json()
    ↓
"What data was sent?"

validation
    ↓
"Is this data acceptable?"
```

These are different responsibilities.

Your roadmap deliberately teaches validation separately in Phase 9.

---

# 16. Built-in Middleware Doesn't Replace Authentication

Similarly:

```js
express.json()
```

doesn't answer:

> "Who is this user?"

That's authentication middleware's job.

So:

```text
express.json()
    ↓
Parse request body

authenticate
    ↓
Identify user

authorize
    ↓
Check permissions

validate
    ↓
Check input

controller
    ↓
Perform operation
```

Each middleware has a different responsibility.

---

# 17. Built-in Middleware Doesn't Replace Security

Don't think:

```js
app.use(express.json());
```

means:

> "My API is secure."

It isn't.

It simply parses JSON.

Your later security layer may include things like:

```text
CORS
Helmet
rate limiting
input sanitization
origin checking
authentication
authorization
```

Your source roadmap explicitly places those concepts later, after you've learned the middleware fundamentals.

---

# 18. `express.urlencoded()`

Let's briefly understand why this exists.

Traditional HTML forms can submit data like:

```text
name=Rahul&email=rahul@example.com
```

This isn't JSON.

So:

```js
app.use(
    express.urlencoded({
        extended: true
    })
);
```

can parse that body.

Then:

```js
req.body
```

can contain:

```js
{
    name: "Rahul",
    email: "rahul@example.com"
}
```

The important difference:

```text
JSON
 ↓
express.json()

URL-encoded
 ↓
express.urlencoded()
```

We'll go deeper in 7.12.

---

# 19. `extended: true`

You'll often see:

```js
express.urlencoded({
    extended: true
});
```

For now, don't get stuck on the option.

The important thing is:

```js
express.urlencoded(...)
```

parses URL-encoded form data.

We'll explore what `extended` means when we reach **7.12**.

# 20. `express.static()`

Let's see a practical example.

Create:

```text
backend/
├── public/
│   ├── hello.txt
│   └── image.png
└── server.js
```

Then:

```js
app.use(
    express.static("public")
);
```

Now a request like:

```http
GET /hello.txt
```

can be served from:

```text
public/hello.txt
```

The flow:

```text
GET /hello.txt
      ↓
express.static()
      ↓
Does public/hello.txt exist?
      │
 ┌────┴─────┐
 │          │
YES        NO
 │          │
 ▼          ▼
file      next()
```

That's an important concept:

> Static middleware can serve the file if it finds one; otherwise the request can continue through the pipeline.

---

# 21. This Is Another Example of `next()`

Suppose:

```js
app.use(express.static("public"));

app.get("/api/users", getUsers);
```

Request:

```text
GET /api/users
```

There probably isn't:

```text
public/api/users
```

So static middleware doesn't serve a file and the request can continue.

Conceptually:

```text
GET /api/users
      ↓
express.static()
      ↓
No matching static file
      ↓
next()
      ↓
/api/users route
```

That's a great example of middleware deciding:

> "This isn't mine; let the next handler deal with it."

---

# 22. Built-in Middleware in Your Future `app.js`

Eventually you'll see something conceptually like:

```js
const app = express();

app.use(express.json());

app.use(
    express.urlencoded({
        extended: true
    })
);

app.use(requestId);
app.use(logger);

app.use("/api/v1/auth", authRoutes);
app.use("/api/v1/users", userRoutes);
app.use("/api/v1/todos", todoRoutes);

app.use(notFound);
app.use(errorHandler);
```

Don't memorize this exact order as a universal rule.

Instead understand what each line contributes:

```text
express.json()
    ↓
Understand JSON bodies

express.urlencoded()
    ↓
Understand URL-encoded bodies

requestId
    ↓
Identify requests

logger
    ↓
Record requests

routes
    ↓
Handle API operations

notFound
    ↓
Handle unknown routes

errorHandler
    ↓
Handle errors
```

# 25. Built-in Middleware vs Your Custom Middleware

Let's compare.

### Built-in

```js
app.use(express.json());
```

Express gives you the middleware.

### Custom

```js
const logger = (req, res, next) => {
    console.log(req.method);
    next();
};

app.use(logger);
```

You created it.

### Third-party

```js
import cookieParser from "cookie-parser";

app.use(cookieParser());
```

Another package provides it.

So there are three useful categories:

```text
┌───────────────────────┐
│ Express built-in     │
│ express.json()       │
│ express.urlencoded() │
│ express.static()     │
└───────────────────────┘

┌───────────────────────┐
│ Your custom           │
│ logger                │
│ requestId             │
│ authenticate          │
└───────────────────────┘

┌───────────────────────┐
│ Third-party           │
│ cookie-parser         │
│ cors                  │
│ helmet                │
└───────────────────────┘
```

# 26. A Common Beginner Mistake

Don't install a package for something Express already provides.

For example, you don't need some random JSON parsing package just to parse ordinary JSON bodies in Express.

Use:

```js
app.use(express.json());
```

Similarly:

```js
app.use(express.urlencoded({
    extended: true
}));
```

for URL-encoded bodies.

Keep your dependency list reasonable.

---

# 27. Another Common Mistake

Don't confuse parsing with validation.

This:

```js
app.use(express.json());
```

doesn't mean:

```text
"Only valid data is allowed."
```

It means:

```text
"Parse JSON request bodies."
```

Then:

```text
express.json()
      ↓
validation
      ↓
controller
```

Validation will be handled later.

---

# 28. Another Common Mistake

Don't put built-in middleware randomly.

For example:

```js
app.get("/todos", getTodos);

app.use(express.json());
```

If `/todos` needs JSON parsing for its request body, you've put the parser too late.

Instead:

```js
app.use(express.json());

app.get("/todos", getTodos);
```

Again:

> **Middleware order follows dependency.**
