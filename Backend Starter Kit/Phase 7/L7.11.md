# Phase 7 — Lesson 7.11

## `express.json()` — Understanding JSON Request Bodies

In **7.10**, we learned that `express.json()` is built-in Express middleware.

Now we're going to understand it properly instead of treating this as magic:

```js
app.use(express.json());
```

This lesson is important because almost every modern MERN API receives JSON from React.

Your roadmap specifically places **`express.json()` at 7.11**, immediately after built-in Express middleware.

---

# 1. The Problem `express.json()` Solves

Imagine your React frontend sends:

```http
POST /api/v1/todos
Content-Type: application/json
```

with this body:

```json
{
  "title": "Learn Express",
  "completed": false
}
```

Your backend wants to do:

```js
console.log(req.body.title);
```

and get:

```text
Learn Express
```

But the HTTP request body arrives as **raw request data**.

Something needs to understand:

```text
"This body contains JSON"
```

and parse it into a JavaScript object.

That's where:

```js
express.json()
```

comes in.

---

# 2. The Mental Model

Think about the flow like this:

```text
React
  │
  │ JSON
  ▼
HTTP Request
  │
  ▼
express.json()
  │
  │ parses JSON
  ▼
req.body
  │
  ▼
Controller
```

So:

```text
JSON text
   ↓
JavaScript object
```

is the important transformation.

---

# 3. What Does `app.use(express.json())` Actually Mean?

This line:

```js
app.use(express.json());
```

has two operations happening conceptually.

### First:

```js
express.json()
```

creates/configures a middleware function.

### Second:

```js
app.use(...)
```

adds that middleware to your Express application pipeline.

So don't think of:

```js
express.json()
```

as a magical parser that automatically runs everywhere.

Think:

```text
express.json()
       ↓
creates middleware
       ↓
app.use(...)
       ↓
middleware enters request pipeline
```

---

# 4. Basic Example

Create:

```js
import express from "express";

const app = express();

app.use(express.json());

app.post("/todos", (req, res) => {
    console.log(req.body);

    res.json({
        success: true,
        data: req.body
    });
});

app.listen(5000);
```

Now send:

```http
POST /todos
Content-Type: application/json
```

with:

```json
{
  "title": "Learn Express"
}
```

The route can access:

```js
req.body
```

which contains:

```js
{
    title: "Learn Express"
}
```

---

# 5. Before and After `express.json()`

Without the JSON parser:

```text
HTTP Request
     ↓
Route
     ↓
req.body ❓
```

With:

```js
app.use(express.json());
```

we get:

```text
HTTP Request
     ↓
express.json()
     ↓
JSON parsed
     ↓
req.body
     ↓
Route
```

That's the entire purpose.

---

# 6. What Is `req.body`?

You've probably used:

```js
req.body
```

many times.

But now understand where it comes from.

`req` is the Express request object.

It contains information about the incoming HTTP request.

For example:

```js
req.method
req.url
req.headers
req.params
req.query
req.body
```

The important distinction is:

```text
req.body
```

contains data sent in the **request body**.

For example:

```json
{
  "email": "rahul@example.com",
  "password": "secret"
}
```

can become:

```js
req.body = {
    email: "rahul@example.com",
    password: "secret"
};
```

---

# 7. JSON Is Just Data Format

JSON stands for:

> **JavaScript Object Notation**

Example:

```json
{
  "name": "Rahul",
  "age": 22
}
```

It looks similar to a JavaScript object:

```js
{
    name: "Rahul",
    age: 22
}
```

But don't confuse them.

JSON is a **text/data representation format**.

JavaScript object is an actual JavaScript value.

Conceptually:

```text
JSON text
   ↓
JSON parser
   ↓
JavaScript object
```

That's what happens during request processing.

---

# 8. Why Does `Content-Type` Matter?

Suppose the client sends:

```http
Content-Type: application/json
```

This tells the server:

> "The request body is JSON."

Then `express.json()` can recognize and parse it.

Think:

```text
Content-Type
     ↓
application/json
     ↓
express.json()
     ↓
parse body
```

This is why your frontend request should normally specify the correct content type when sending JSON.

Axios usually handles this automatically when you send a JavaScript object.

---

# 9. Example With Axios

Your React frontend might do:

```js
axios.post(
    "/api/v1/todos",
    {
        title: "Learn Express"
    }
);
```

The request conceptually becomes:

```http
POST /api/v1/todos
Content-Type: application/json
```

Body:

```json
{
  "title": "Learn Express"
}
```

Express receives it:

```text
Request
   ↓
express.json()
   ↓
req.body
   ↓
{
   title: "Learn Express"
}
```

Then your controller can use:

```js
const { title } = req.body;
```

---

# 10. Why Must It Usually Come Before the Route?

Consider:

```js
app.use(express.json());

app.post("/todos", createTodo);
```

The pipeline is:

```text
Request
   ↓
express.json()
   ↓
createTodo
```

So when the controller executes:

```js
req.body
```

the JSON parser has already processed the body.

This connects directly to **Lesson 7.6: middleware execution order**.

---

# 11. What If You Put It After the Route?

Consider:

```js
app.post("/todos", createTodo);

app.use(express.json());
```

For that route, the JSON parser isn't positioned where you intended it in the request pipeline.

The lesson is:

> **Middleware must be registered before the handlers that depend on its work.**

So prefer:

```js
app.use(express.json());

app.post("/todos", createTodo);
```

---

# 12. `express.json()` Does NOT Validate Your Data

This is extremely important.

Suppose the client sends:

```json
{
  "title": 123456,
  "somethingRandom": true
}
```

`express.json()` doesn't say:

```text
❌ Invalid Todo
```

It simply parses the JSON.

So:

```text
express.json()
      ↓
"What data did they send?"

validation
      ↓
"Is that data allowed?"
```

These are different responsibilities.

Your roadmap intentionally teaches validation separately in Phase 9.

---

# 13. Example: Parsing vs Validation

Suppose your Todo requires:

```text
title → string
```

Client sends:

```json
{
  "title": 123
}
```

`express.json()` can successfully parse this.

Result:

```js
req.body = {
    title: 123
};
```

But your validation layer should later reject it:

```text
express.json()
      ↓
parsed successfully
      ↓
validation
      ↓
❌ title must be a string
```

This distinction will become very important when you learn Joi.

---

# 14. `express.json()` Does NOT Authenticate

Suppose the request contains:

```http
Authorization: Bearer abc123
```

`express.json()` doesn't verify the token.

It doesn't know:

```text
Who is the user?
```

That's authentication middleware's job.

So eventually your pipeline might be:

```text
Request
   ↓
express.json()
   ↓
requestId
   ↓
logger
   ↓
authenticate
   ↓
validate
   ↓
controller
```

Each layer has one responsibility.

---

# 15. `express.json()` Does NOT Sanitize Input

Suppose the body is:

```json
{
  "title": "<script>alert('hello')</script>"
}
```

`express.json()` doesn't clean it.

It simply parses the JSON.

So:

```text
JSON parsing
     ≠
validation
     ≠
sanitization
```

These are separate concepts.

You'll study sanitization later in your security lessons.

---

# 16. What Happens With Malformed JSON?

Now let's try something invalid.

Client sends:

```json
{
  "title": "Learn Express"
```

Notice the missing:

```text
}
```

This isn't valid JSON.

`express.json()` can't parse it successfully.

Conceptually:

```text
Request
   ↓
express.json()
   ↓
JSON parsing fails
   ↓
Error
```

This is one reason your application needs proper **error handling**.

And that's exactly why Phase 8 exists in your roadmap:

```text
Phase 8
→ Error Handling & Async Architecture
```

The roadmap explicitly builds global error handling after middleware fundamentals.

---

# 17. What Happens If the Request Isn't JSON?

Suppose the client sends:

```http
Content-Type: text/plain
```

with:

```text
Hello Express
```

`express.json()` is specifically for JSON request bodies.

It doesn't magically convert every possible request body into an object.

That's why different body formats can require different parsers.

For example:

```text
application/json
      ↓
express.json()

application/x-www-form-urlencoded
      ↓
express.urlencoded()
```

We'll study the second one in 7.12.

---

# 18. Nested JSON Works

JSON can contain nested objects.

For example:

```json
{
  "title": "Learn Express",
  "author": {
    "name": "Rahul",
    "role": "student"
  }
}
```

After parsing:

```js
req.body.title
```

gives:

```text
Learn Express
```

and:

```js
req.body.author.name
```

gives:

```text
Rahul
```

So `express.json()` doesn't just handle flat objects.

It parses valid JSON structures.

---

# 19. Arrays Work Too

You can receive:

```json
{
  "tags": [
    "node",
    "express",
    "mongodb"
  ]
}
```

Then:

```js
req.body.tags
```

is an array:

```js
[
    "node",
    "express",
    "mongodb"
]
```

Your application can then process it.

Again:

```text
JSON
 ↓
express.json()
 ↓
JavaScript data structure
```

# 20. Request Body vs Query vs Params

This is a very important distinction.

Suppose:

```http
GET /todos/123?page=2
```

You have:

### Route parameter

```js
req.params.id
```

Result:

```text
123
```

### Query parameter

```js
req.query.page
```

Result:

```text
2
```

But:

```js
req.body
```

is for data sent in the request body.

For example:

```http
POST /todos
```

with:

```json
{
  "title": "Learn Express"
}
```

Then:

```js
req.body.title
```

is:

```text
Learn Express
```

So:

```text
URL:    /todos/123?page=2

params → req.params.id
query  → req.query.page
body   → req.body
```

This distinction will become very important when you build validation middleware.

---

# 21. Why GET Usually Doesn't Need JSON Body Parsing

Most REST APIs use:

```text
GET
```

to retrieve resources.

For example:

```http
GET /todos?page=1
```

The information is normally in:

```js
req.query
```

rather than:

```js
req.body
```

Whereas:

```http
POST /todos
```

might contain:

```json
{
  "title": "Learn Express"
}
```

and therefore needs:

```js
req.body
```

This isn't an absolute HTTP law, but it's the common REST API pattern you should follow.

---

# 22. JSON Parsing and HTTP Methods

A common pattern:

|Method|Common data location|
|---|---|
|GET|`req.params`, `req.query`|
|POST|`req.body`|
|PUT|`req.body`|
|PATCH|`req.body`|
|DELETE|often `req.params`|

For example:

```http
POST /todos
```

```json
{
  "title": "Learn Express"
}
```

while:

```http
DELETE /todos/123
```

uses:

```js
req.params.id
```

for the Todo ID.

Again, these are conventions, not strict parser rules.

---

# 23. JSON Body Size

Here's an important production concept.

Imagine someone sends an extremely large JSON body:

```text
10 MB
100 MB
1 GB
```

You don't want your server blindly accepting enormous request bodies.

That's why JSON parsing can be configured with options such as a body-size limit.

For example:

```js
app.use(
    express.json({
        limit: "1mb"
    })
);
```

Now you're telling the parser:

> "Don't accept arbitrarily large JSON bodies."

This is useful for protecting server resources.

---

# 24. Why Body Size Limits Matter

Without sensible limits:

```text
Huge request
     ↓
Server reads body
     ↓
Memory/CPU consumption
     ↓
Potential resource exhaustion
```

With a limit:

```text
Huge request
     ↓
Parser checks size
     ↓
Too large
     ↓
Reject request
```

This is one small example of how **middleware can also be part of security engineering**.

We'll explore request limits more deeply later.

---

# 25. Example With a Limit

```js
app.use(
    express.json({
        limit: "1mb"
    })
);
```

Your normal request:

```json
{
  "title": "Learn Express"
}
```

works normally.

But an extremely large body can be rejected.

Don't blindly copy `1mb` into every project, though.

The correct limit depends on what your API is designed to accept.

---

# 26. What Does `express.json()` Return?

This is a useful JavaScript question.

When you write:

```js
express.json()
```

you're not directly getting:

```js
req.body
```

Instead, you're getting a middleware function configured to parse JSON.

Conceptually:

```js
const jsonParser = express.json();

app.use(jsonParser);
```

You can think of:

```text
express.json()
      ↓
middleware function
      ↓
app.use()
```

This is exactly the same pattern you learned with custom middleware.

---

# 27. Compare Custom Middleware

You wrote:

```js
const logger = (req, res, next) => {
    console.log(req.method);
    next();
};
```

Then:

```js
app.use(logger);
```

With Express:

```js
const jsonParser = express.json();
```

Then:

```js
app.use(jsonParser);
```

So conceptually:

```text
Your middleware:
create function → app.use()

Express middleware:
create function → app.use()
```

That's why `express.json()` shouldn't feel magical anymore.

# 29. A Realistic `app.js`

For your learning project:

```js

    express.json({

    res.json({
```


# 34. Common Mistakes

## ❌ Mistake 1 — Forgetting `express.json()`

```js
const app = express();

app.post("/todos", (req, res) => {
    console.log(req.body);
});
```

Then wondering why the JSON body isn't available as expected.

---

## ❌ Mistake 2 — Thinking it validates data

```js
app.use(express.json());
```

doesn't mean:

```text
"All incoming data is safe."
```

It means:

```text
"Parse JSON bodies."
```

---

## ❌ Mistake 3 — Putting it after routes that need it

Prefer:

```js
app.use(express.json());

app.use("/api", routes);
```

rather than relying on a later registration.

---

## ❌ Mistake 4 — Accepting huge bodies blindly

For APIs with controlled payload sizes, consider an appropriate limit:

```js
app.use(
    express.json({
        limit: "1mb"
    })
);
```

The correct value depends on the application.

---

## ❌ Mistake 5 — Confusing body, params and query

Remember:

```text
req.body
→ request body

req.params
→ URL parameters

req.query
→ query string
```

Example:

```http
GET /todos/123?page=2
```

```js
req.params.id   // "123"
req.query.page  // "2"
```

For:

```http
POST /todos
```

```json
{
  "title": "Learn Express"
}
```

```js
req.body.title  // "Learn Express"
```
