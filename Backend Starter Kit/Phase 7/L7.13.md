# Phase 7 — Lesson 7.13

## `cookie-parser` — Understanding Cookies in Express

In **7.11**, you learned JSON bodies.

In **7.12**, you learned URL-encoded bodies.

Now we're moving to another important part of HTTP requests:

> **Cookies**

Your Phase 7 roadmap specifically puts **`cookie-parser`** at 7.13.

And this topic is especially important because later, in your authentication phase, you'll learn:

```text
Access Token
    ↓
Authorization header

Refresh Token
    ↓
HttpOnly cookie
```

Your starter roadmap explicitly uses this authentication design.

So let's understand cookies from the ground up.

---

# 1. What Is a Cookie?

A cookie is a small piece of data that a server can ask the browser to store.

Think:

```text
Server
   ↓
"Browser, remember this value."
   ↓
Browser stores cookie
```

Later, when the browser makes another request:

```text
Browser
   ↓
sends cookie
   ↓
Server
```

So cookies create a way for the browser and server to maintain information across requests.

---

# 2. Why Do We Need Cookies?

HTTP is fundamentally stateless.

Imagine:

```text
Request 1
GET /profile
```

Then:

```text
Request 2
GET /profile
```

The server doesn't automatically know that both requests came from the same browser session.

Cookies can help carry state between requests.

Conceptually:

```text
Request 1
    ↓
Server sets cookie
    ↓
Browser stores cookie

Request 2
    ↓
Browser sends cookie
    ↓
Server reads cookie
```

---

# 3. A Simple Example

Suppose your server sends:

```http
Set-Cookie: theme=dark
```

The browser stores:

```text
theme=dark
```

Later, the browser may send:

```http
Cookie: theme=dark
```

So:

```text
Server
  │
  │ Set-Cookie
  ▼
Browser
  │
  │ Cookie
  ▼
Server
```

That's the basic cookie lifecycle.

---

# 4. Cookies Are Sent Through HTTP Headers

This is important.

A cookie isn't some magical JavaScript variable shared directly with Express.

Cookies travel through HTTP headers.

### Server → Browser

```http
Set-Cookie: theme=dark
```

### Browser → Server

```http
Cookie: theme=dark
```

So:

```text
Set-Cookie
    ↓
Browser stores cookie

Cookie
    ↓
Browser sends cookie back
```

---

# 5. Where Does `cookie-parser` Come In?

Express doesn't automatically give you convenient access to parsed cookies.

That's where the third-party package:

```text
cookie-parser
```

comes in.

Install it:

```bash
npm install cookie-parser
```

Then:

```js
import cookieParser from "cookie-parser";

app.use(cookieParser());
```

Now Express can expose parsed cookies through:

```js
req.cookies
```

---

# 6. The Basic Flow

Without thinking about implementation details:

```text
Browser
   │
   │ Cookie: theme=dark
   ▼
Express
   │
   ▼
cookie-parser
   │
   ▼
req.cookies
```

Then your route can do:

```js
console.log(req.cookies);
```

and get something like:

```js
{
    theme: "dark"
}
```

That's the main reason you use `cookie-parser`.

---

# 7. Installing `cookie-parser`

From your backend:

```bash
npm install cookie-parser
```

Then:

```js
import cookieParser from "cookie-parser";
```

Register it:

```js
app.use(cookieParser());
```

Your basic app:

```js
import express from "express";
import cookieParser from "cookie-parser";

const app = express();

app.use(express.json());
app.use(cookieParser());

app.get("/profile", (req, res) => {
    console.log(req.cookies);

    res.json({
        success: true
    });
});
```

# 8. Reading a Cookie

Suppose the browser sends:

```http
Cookie: theme=dark
```

After:

```js
app.use(cookieParser());
```

you can do:

```js
req.cookies.theme
```

Result:

```text
dark
```

So:

```text
HTTP Cookie header
       ↓
cookie-parser
       ↓
req.cookies
       ↓
req.cookies.theme
```

---

# 9. Creating a Cookie

Express itself can set cookies.

You don't need `cookie-parser` for this part.

You can use:

```js
res.cookie(
    "theme",
    "dark"
);
```

For example:

```js
app.get("/set-cookie", (req, res) => {
    res.cookie("theme", "dark");

    res.json({
        success: true
    });
});
```

The response will contain a `Set-Cookie` header.

Conceptually:

```text
GET /set-cookie
      ↓
res.cookie()
      ↓
Set-Cookie header
      ↓
Browser stores cookie
```

---

# 10. Important Distinction

This is worth remembering:

### `res.cookie()`

Used to **set** a cookie.

### `cookie-parser`

Used to conveniently **parse incoming cookies**.

So:

```text
Server → Browser
     res.cookie()

Browser → Server
     cookie-parser
```

You don't use `cookie-parser` to create cookies.

---

# 11. Complete Example

```js
import express from "express";
import cookieParser from "cookie-parser";

const app = express();

app.use(cookieParser());

app.get("/set-cookie", (req, res) => {
    res.cookie("username", "Rahul");

    res.json({
        success: true,
        message: "Cookie set"
    });
});

app.get("/read-cookie", (req, res) => {
    const username = req.cookies.username;

    res.json({
        username
    });
});

app.listen(5000);
```

Now:

```text
GET /set-cookie
```

causes:

```text
Server
  ↓
Set-Cookie: username=Rahul
  ↓
Browser
```

Then:

```text
GET /read-cookie
```

causes:

```text
Browser
  ↓
Cookie: username=Rahul
  ↓
cookie-parser
  ↓
req.cookies.username
  ↓
"Rahul"
```

# 13. Cookies vs `localStorage`

This is extremely important for your MERN journey.

You've probably used:

```js
localStorage.setItem(
    "token",
    token
);
```

That's **not the same thing as a cookie**.

### localStorage

```text
JavaScript
    ↓
localStorage
```

### Cookie

```text
Server
    ↓
Set-Cookie
    ↓
Browser cookie storage
```

Cookies also have security attributes that can control how browsers handle them.

# 14. Why Are Cookies Useful for Authentication?

Later you'll build:

```text
Access Token
+
Refresh Token
```

Your starter roadmap recommends:

```text
Access Token
    ↓
Authorization header

Refresh Token
    ↓
HttpOnly cookie
```

Why?

Because cookies have useful browser security controls.

One of the most important is:

```text
HttpOnly
```

---

# 15. What Is `HttpOnly`?

Suppose you set:

```js
res.cookie(
    "refreshToken",
    token,
    {
        httpOnly: true
    }
);
```

The browser stores the cookie, but normal client-side JavaScript cannot directly read it through:

```js
document.cookie
```

Conceptually:

```text
Browser
   │
   ├── Cookie storage
   │      ↓
   │   refreshToken
   │
   └── JavaScript
          ✗ cannot directly read HttpOnly cookie
```

But the browser can still send the cookie with appropriate requests.

This is one reason HttpOnly cookies are useful for sensitive authentication material.

**We'll study this properly in Phase 14**, not try to solve authentication in this lesson.

---

# 16. `Secure`

Another important cookie option is:

```js
secure: true
```

Example:

```js
res.cookie(
    "refreshToken",
    token,
    {
        httpOnly: true,
        secure: true
    }
);
```

`Secure` tells the browser to send the cookie only over secure HTTPS connections.

Conceptually:

```text
HTTPS
  ↓
Cookie allowed

HTTP
  ↓
Cookie not sent
```

For local development, you need to account for whether you're actually using HTTPS.

---

# 17. `SameSite`

Another important cookie attribute is:

```js
sameSite
```

For example:

```js
res.cookie(
    "refreshToken",
    token,
    {
        httpOnly: true,
        secure: true,
        sameSite: "lax"
    }
);
```

`SameSite` controls how cookies are handled in cross-site request situations.

This becomes particularly important when your:

```text
Frontend
```

and:

```text
Backend
```

are hosted on different origins/sites.

You've already encountered cookie/CORS problems in your MERN projects, so this concept will eventually be very useful.

We'll cover it much more deeply in authentication and security.

---

# 18. Cookie Options You Should Know

At a high level:

```js
res.cookie("name", "value", {
    httpOnly: true,
    secure: true,
    sameSite: "lax",
    maxAge: 1000 * 60 * 60
});
```

Important options:

|Option|Purpose|
|---|---|
|`httpOnly`|Prevent normal JS access|
|`secure`|Send over HTTPS|
|`sameSite`|Controls cross-site cookie behavior|
|`maxAge`|Cookie lifetime|
|`expires`|Explicit expiration|
|`path`|URL path where cookie applies|
|`domain`|Domain scope|

Don't memorize all of these yet.

Just understand what each controls.

---

# 19. Cookie Lifetime

You can create a temporary cookie:

```js
res.cookie(
    "theme",
    "dark",
    {
        maxAge: 1000 * 60 * 60
    }
);
```

Here:

```text
1000 ms
× 60
× 60
=
1 hour
```

So the cookie is intended to last around one hour.

---

# 20. Session Cookies

If you don't specify a persistent lifetime, a cookie can behave as a session cookie.

Conceptually:

```text
Browser session
      ↓
Cookie exists

Session ends
      ↓
Cookie may be removed
```

The exact browser behavior depends on cookie attributes and browser rules.

---

# 21. Deleting a Cookie

Express provides:

```js
res.clearCookie("theme");
```

For example:

```js
app.post("/logout", (req, res) => {
    res.clearCookie("refreshToken");

    res.json({
        success: true,
        message: "Logged out"
    });
});
```

Conceptually:

```text
Logout
   ↓
Clear cookie
   ↓
Browser no longer has refresh token cookie
```

Later, your real logout flow will also involve invalidating server-side token state.

So don't think:

```text
clearCookie()
=
complete authentication logout
```

It can be one part of logout.

---

# 22. Cookie Name Matters

Suppose you set:

```js
res.cookie(
    "refreshToken",
    token
);
```

Then you read:

```js
req.cookies.refreshToken
```

The names must match.

For example:

```text
Set:
refreshToken

Read:
refreshToken
```

Not:

```text
Set:
refresh_token

Read:
refreshToken
```

unless you've intentionally designed that mapping elsewhere.

# 23. Cookies Are Automatically Sent by Browsers

One major difference from `localStorage` is that browsers have built-in cookie handling.

Once a cookie is stored and its rules match a request:

```text
Browser
   ↓
Automatically includes Cookie header
```

You don't normally write:

```js
fetch(..., {
    headers: {
        Cookie: ...
    }
});
```

in browser JavaScript.

The browser manages cookies according to cookie rules and request context.

# 24. Cross-Origin Requests

This is where MERN developers often get confused.

Suppose:

```text
Frontend:
https://frontend.example.com

Backend:
https://api.example.com
```

The browser may need appropriate configuration for credentials/cookies to be sent.

With `fetch`, for example:

```js
fetch(
    "https://api.example.com/profile",
    {
        credentials: "include"
    }
);
```

With Axios:

```js
axios.get(
    "https://api.example.com/profile",
    {
        withCredentials: true
    }
);
```

But this is only one part of the setup.

The backend CORS configuration must also allow the appropriate credentialed request.

So:

```text
Frontend
   ↓
credentials: include
   ↓
Browser
   ↓
CORS rules
   ↓
Cookie
   ↓
Backend
```

We'll cover this properly later.

# 26. What `cookie-parser` Actually Gives You

Let's make the distinction very clear.

Suppose browser sends:

```http
Cookie: theme=dark; language=en
```

After:

```js
app.use(cookieParser());
```

you can access:

```js
req.cookies
```

roughly as:

```js
{
    theme: "dark",
    language: "en"
}
```

Then:

```js
req.cookies.theme
```

gives:

```text
dark
```

So `cookie-parser` primarily helps turn the raw cookie header into a convenient object.

---

# 27. Signed Cookies

`cookie-parser` also supports **signed cookies**.

You can configure it with a secret:

```js
app.use(
    cookieParser(process.env.COOKIE_SECRET)
);
```

Then cookies can be signed.

Conceptually:

```text
Cookie value
    +
Secret
    ↓
Signature
```

When the cookie comes back:

```text
Cookie
   ↓
verify signature
   ↓
valid?
```

This helps detect whether the cookie value was modified.

---

# 28. Important: Signed ≠ Encrypted

This is a very common misunderstanding.

A signed cookie is not automatically encrypted.

Think:

```text
Signed
→ Detect tampering

Encrypted
→ Hide the content
```

So if you sign:

```text
userId=123
```

the purpose is to help detect modification.

It doesn't necessarily hide:

```text
userId=123
```

from someone who can inspect the cookie.

For sensitive authentication cookies, other security properties—especially `HttpOnly`, `Secure`, appropriate `SameSite`, expiration, and server-side validation—matter too.

---

# 29. Example of a Signed Cookie

```js
app.use(
    cookieParser(process.env.COOKIE_SECRET)
);
```

Set:

```js
res.cookie(
    "session",
    "abc123",
    {
        signed: true
    }
);
```

Then read it using:

```js
req.signedCookies.session
```

instead of:

```js
req.cookies.session
```

Conceptually:

```text
Normal cookie
     ↓
req.cookies

Signed cookie
     ↓
req.signedCookies
```

---

# 30. Why Would We Sign Cookies?

Imagine you store something like:

```text
role=user
```

in a cookie.

A malicious client might try to modify it:

```text
role=admin
```

A signature lets the server detect that the value has been altered.

Conceptually:

```text
Original
role=user
   ↓
signature

Attacker changes:
role=admin
   ↓
old signature no longer matches
   ↓
invalid
```

But remember:

> **Never treat a client-controlled cookie as proof of authorization just because it is signed.**

Your server should still enforce authorization correctly.

---

# 31. Cookies vs JWT

These are not opposites.

This is a very important concept.

### Cookie

A **transport/storage mechanism** in the browser.

### JWT

A **token format**.

So you can have:

```text
JWT
 ↓
stored in cookie
```

or:

```text
JWT
 ↓
Authorization header
```

For example:

```text
Access JWT
   ↓
Authorization: Bearer <token>
```

while:

```text
Refresh JWT/token
   ↓
HttpOnly cookie
```

That's why saying:

> "JWT vs cookies"

isn't always the right comparison.

They're different concepts.

---

# 32. Cookie vs `localStorage`

Another useful distinction:

```text
localStorage
→ browser storage API

cookie
→ HTTP/browser mechanism
```

Cookies can be automatically attached to requests according to their rules.

`localStorage` values are not automatically sent to your API.

With localStorage, your frontend code typically has to retrieve the token and add it to a request header.

For example:

```js
const token = localStorage.getItem("accessToken");

axios.get("/profile", {
    headers: {
        Authorization: `Bearer ${token}`
    }
});
```

With cookies, browser cookie handling can attach the cookie automatically when the cookie/request rules permit it.

---

# 33. Why `HttpOnly` Is Valuable

Suppose your refresh token is:

```text
refreshToken=very-secret-value
```

If it is stored in an HttpOnly cookie:

```text
JavaScript
    ↓
cannot directly read cookie
```

That reduces exposure to token theft through certain client-side script attacks.

But don't misunderstand this as:

```text
HttpOnly
=
complete XSS protection
```

It isn't.

XSS can still cause other damage to an application.

Security is layered.

# 37. Middleware Doesn't Mean Every Route Needs Cookies

Just because:

```js
app.use(cookieParser());
```

is registered globally doesn't mean every route must use cookies.

For example:

```text

```

can simply return:

```json
{
    "success": true
}
```

while:

```text
POST /auth/refresh
```

can use:

```js
req.cookies.refreshToken
```

The parser is available, but the route only uses it when necessary.

# 42. Common Mistakes

### ❌ Mistake 1 — Thinking `cookie-parser` creates cookies

It doesn't.

Creating:

```js
res.cookie(...)
```

is handled by Express's response API.

`cookie-parser` primarily helps parse incoming cookies.

---

### ❌ Mistake 2 — Thinking cookies are encrypted

They're not automatically encrypted.

Remember:

```text
Signed
≠
Encrypted
```

---

### ❌ Mistake 3 — Storing secrets in ordinary readable cookies

If sensitive authentication material is stored in a cookie, security attributes matter.

For example, later you'll learn:

```js
httpOnly: true
secure: true
sameSite: ...
```

Don't put sensitive authentication data into a normal cookie without understanding the risks.

---

### ❌ Mistake 4 — Thinking `HttpOnly` makes cookies completely secure

It reduces one class of exposure, but it doesn't solve every web security problem.

You still need:

```text
HTTPS
CORS configuration
SameSite strategy
CSRF considerations
token expiration
server-side validation
```

depending on your architecture.

---

### ❌ Mistake 5 — Confusing cookies with JWT

Remember:

```text
Cookie
→ browser/HTTP mechanism

JWT
→ token format
```

A JWT can be stored in a cookie, but cookies don't have to contain JWTs.

### Next → **Lesson 7.14 — Creating Reusable Middleware**

This is where things start becoming more architectural. Instead of writing middleware directly inside `app.js`, you'll learn how to create files such as:

```text
middlewares/
├── logger.middleware.js
├── requestId.middleware.js
└── auth.middleware.js
```

and understand **why reusable middleware belongs in separate modules, how to export/import it, and how to design middleware that can be reused across many routes**.
