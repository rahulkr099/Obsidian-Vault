# Phase 7 — Lesson 7.14

## Creating Reusable Middleware

In the previous lessons, you learned **what middleware is**, how it works, and how to use built-in middleware such as:

```js
app.use(express.json());
app.use(cookieParser());
```

But there's a problem.

If you keep writing middleware directly inside `app.js`, your application will eventually become messy.

The Phase 7 roadmap therefore moves from basic middleware into **reusable middleware**, followed by middleware factories, conditional middleware, composition, debugging, and finally a reusable middleware system.

The goal of this lesson is simple:

> **Learn how to create middleware once, put it in its own module, and reuse it wherever you need it.**

---

# 1. The Problem With Writing Everything in `app.js`

Imagine this:

```js
import express from "express";

const app = express();

const logger = (req, res, next) => {
    console.log(req.method, req.url);
    next();
};

const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();
    next();
};

const authenticate = (req, res, next) => {
    // authentication logic
    next();
};

app.use(logger);
app.use(requestId);

app.get("/profile", authenticate, getProfile);
app.get("/todos", authenticate, getTodos);
```

This works.

But imagine you eventually have:

```text
20 middleware functions
50 routes
10 routers
```

Your `app.js` becomes huge.

That's not what we want.

---

# 2. The Better Approach

Move middleware into its own directory:

```text
middlewares/
├── logger.middleware.js
├── requestId.middleware.js
└── auth.middleware.js
```

Now:

```text
app.js
   ↓
imports middleware
   ↓
uses middleware
```

The actual middleware implementation lives somewhere else.

This follows the same idea as the starter architecture, where middleware is separated into dedicated files such as `auth.middleware.js`, `logger.middleware.js`, and `requestId.middleware.js`.

---

# 3. Think About Responsibilities

Your `app.js` should mainly answer:

> **"How is my Express application assembled?"**

It shouldn't contain every middleware implementation.

For example:

```text
app.js
 │
 ├── express.json()
 ├── logger
 ├── requestId
 ├── routes
 └── error handler
```

while:

```text
middlewares/
 │
 ├── logger.middleware.js
 ├── requestId.middleware.js
 └── auth.middleware.js
```

contains the actual middleware code.

---

# 4. First Reusable Middleware

Let's create:

```text
middlewares/
└── logger.middleware.js
```

Put:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);

    next();
};

export default logger;
```

Now the middleware is a separate module.

---

# 5. Import It Into `app.js`

Your `app.js`:

```js
import express from "express";
import logger from "./middlewares/logger.middleware.js";

const app = express();

app.use(logger);

export default app;
```

Now the flow is:

```text
app.js
   ↓
imports logger
   ↓
app.use(logger)
   ↓
Express pipeline
```

That's your first reusable middleware.

---

# 6. Why Is This Better?

Instead of:

```js
const logger = (...) => {
    ...
};
```

inside `app.js`, you have:

```text
app.js
    ↓
"Use logger middleware."

logger.middleware.js
    ↓
"Here is how logger works."
```

This creates separation.

---

# 7. Your First Important Architecture Rule

Remember:

> **Define a middleware once. Reuse it wherever necessary.**

For example:

```js
app.use(logger);
```

or:

```js
router.use(logger);
```

or:

```js
router.get(
    "/profile",
    logger,
    getProfile
);
```

The middleware itself doesn't need to be rewritten.

---

# 8. Create `requestId.middleware.js`

Now create:

```text
middlewares/
├── logger.middleware.js
└── requestId.middleware.js
```

Inside:

```js
import crypto from "crypto";

const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    next();
};

export default requestId;
```

Now your middleware has one responsibility:

```text
Create request ID
      ↓
Attach it to req
      ↓
next()
```

---

# 9. Use Both Middleware

Your `app.js`:

```js
import express from "express";

import logger from "./middlewares/logger.middleware.js";
import requestId from "./middlewares/requestId.middleware.js";

const app = express();

app.use(requestId);
app.use(logger);

app.get("/healthz", (req, res) => {
    res.json({
        success: true,
        requestId: req.requestId
    });
});

export default app;
```

Now the flow is:

```text
Request
   ↓
requestId
   ↓
logger
   ↓
/healthz
   ↓
response
```

---

# 10. Why Did We Put `requestId` First?

Look at the logger:

```js
const logger = (req, res, next) => {
    console.log(
        `[${req.requestId}]`,
        req.method,
        req.url
    );

    next();
};
```

It depends on:

```js
req.requestId
```

being created first.

Therefore:

```text
requestId
   ↓
logger
```

not:

```text
logger
   ↓
requestId
```

This is the middleware dependency principle you learned earlier.

---

# 11. Reusable Middleware Can Depend on Other Middleware

This is a very important concept.

Consider:

```text
requestId
   ↓
logger
```

`logger` depends on something created by `requestId`.

Later you might have:

```text
requestId
   ↓
logger
   ↓
authenticate
   ↓
authorize
   ↓
validate
   ↓
controller
```

Each layer may depend on information created by the previous layer.

This is why middleware architecture isn't just about making files.

It's about designing a **pipeline**.

---

# 12. Creating Authentication Middleware

Create:

```text
middlewares/
└── auth.middleware.js
```

For now, we'll use a very simple example.

```js
const authenticate = (req, res, next) => {
    const token = req.headers.authorization;

    if (!token) {
        return res.status(401).json({
            success: false,
            message: "Authentication required"
        });
    }

    req.user = {
        id: "123"
    };

    next();
};

export default authenticate;
```

Don't worry about real JWT verification yet.

That comes much later in your authentication phase.

The purpose here is to understand **middleware architecture**.

---

# 13. Use Authentication on a Route

```js
import authenticate from "./middlewares/auth.middleware.js";

app.get(
    "/profile",
    authenticate,
    (req, res) => {
        res.json({
            success: true,
            userId: req.user.id
        });
    }
);
```

Now:

```text
GET /profile
     ↓
authenticate
     ↓
req.user
     ↓
controller
```

---

# 14. Reuse the Same Middleware

Suppose you also have:

```text
GET /todos
POST /todos
DELETE /todos/:id
```

Instead of creating authentication again:

```js
app.get("/todos", authenticate, getTodos);

app.post("/todos", authenticate, createTodo);

app.delete(
    "/todos/:id",
    authenticate,
    deleteTodo
);
```

All three use the same middleware.

That's reuse.

---

# 15. Better: Router-Level Reuse

If every Todo route requires authentication, don't repeat it.

Create:

```text
routes/
└── todo.routes.js
```

Then:

```js
import express from "express";
import authenticate from "../middlewares/auth.middleware.js";

const router = express.Router();

router.use(authenticate);

router.get("/", getTodos);

router.post("/", createTodo);

router.delete("/:id", deleteTodo);

export default router;
```

Now:

```text
Todo Router
     ↓
authenticate
     ↓
all Todo routes
```

This combines:

- reusable middleware
    
- router-level middleware
    
- route organization
    

which you've already learned.

# 16. The Folder Structure Is Starting to Make Sense

Your project can now look like:

```text
backend/
├── app.js
├── server.js
│
├── middlewares/
│   ├── logger.middleware.js
│   ├── requestId.middleware.js

│
└── routes/
    ├── auth.routes.js
    ├── user.routes.js
    └── todo.routes.js
```

And the relationship is:

```text
app.js
  │
  ├── requestId
  ├── logger
  │
  └── routers
       │
       ├── auth
       ├── users
       └── todos
              │
              └── authenticate
```

This is exactly the kind of layer-building approach the source recommends rather than asking you to memorize folder names.

# 17. One Middleware = One Responsibility

This is a very useful rule.

Bad:

```js
const middleware = (req, res, next) => {
    // authenticate
    // validate
    // check role
    // log
    // sanitize
    // query database
    // send email
};
```

This middleware is doing far too much.

Better:

```text
requestId
   ↓
logger
   ↓
authenticate
   ↓
authorize
   ↓
validate
   ↓
controller
```

Each middleware has a focused job.

---

# 18. Why Small Middleware Is Better

Suppose authentication fails.

If authentication is separate:

```text
authenticate
   ↓
401
```

You immediately know which layer is responsible.

If everything is inside one giant middleware:

```text
megaMiddleware
```

you'll have to search through hundreds of lines.

Small middleware makes debugging easier.

---

# 19. Middleware Should Usually Not Know Business Logic

Consider:

```js
const authenticate = async (req, res, next) => {
    // verify token
    // find user
    // check subscription
    // check todo ownership
    // create todo
    // send email
};
```

That's too much.

Middleware should usually handle **request pipeline concerns**.

For example:

```text
Authentication
Authorization
Validation
Logging
Request ID
Rate limiting
```

Business operations belong deeper in the architecture.

The starter's intended request flow is:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
```

rather than putting all logic into middleware.

---

# 20. Middleware Can Add Information to `req`

This is one of the most useful patterns.

For example:

### Request ID

```js
req.requestId = "abc";
```

### Authentication

```js
req.user = user;
```

### Validation

Potentially:

```js
req.validated = validatedData;
```

Then later middleware/controllers can use that information.

Conceptually:

```text
middleware
    ↓
adds information
    ↓
req
    ↓
next middleware
    ↓
controller
```

---

# 21. Middleware Can Reject the Request

Reusable middleware isn't required to always call `next()`.

For example:

```js
const authenticate = (req, res, next) => {
    if (!req.headers.authorization) {
        return res.status(401).json({
            success: false,
            message: "Unauthorized"
        });
    }

    next();
};
```

There are two possible paths:

```text
Request
   ↓
authenticate
   │
   ├── no credentials → 401
   │
   └── credentials → next()
                         ↓
                      controller
```

This is one of the main reasons middleware is useful.

---

# 22. Middleware Can Be Used in Different Scopes

Because your middleware is reusable, you can use it at different levels.

### Application-level

```js
app.use(logger);
```

### Router-level

```js
router.use(authenticate);
```

### Route-level

```js
router.delete(
    "/:id",
    authenticate,
    requireAdmin,
    deleteTodo
);
```

Same middleware module.

Different scope.

Suppose:

```text

```

is useful everywhere:




The final architecture becomes:

```text

   ↓

   ↓
todoRouter
   ↓

   ↓
requireAdmin               ← route-level
   ↓
deleteTodo
```

This is exactly why reusable middleware is powerful.

# 25. Another Naming Style

You may also see:

```text

```

That's technically fine.

But for your learning project, I recommend:

```text

```

```text

```

# 26. Default Export vs Named Export

You can export middleware like this:

```js
const logger = (req, res, next) => {
    console.log(req.method);
    next();
};

export default logger;
```

Then:

```js
import logger from "./middlewares/logger.middleware.js";
```

Or named:

```js
export const logger = (req, res, next) => {
    console.log(req.method);
    next();
};
```

Then:

```js
import { logger } from "./middlewares/logger.middleware.js";
```

Both work.

For your project, choose one style and stay consistent.

# 30. A Better Way to Think About the Folder

Don't think:

```text
middlewares/
```

means:

> "A folder where random helper functions go."

Instead:

> **Middleware contains functions that participate in the HTTP request/response pipeline.**

For example:

```text
requestId
→ prepares request identity

logger
→ records request

authenticate
→ identifies user

authorize
→ checks permissions

validate
→ checks input

rateLimiter
→ controls request frequency
```

That's why these belong in middleware.

---

# 31. Middleware vs Utility

This distinction will help you later.

### Middleware

Has:

```js
(req, res, next)
```

and participates in an HTTP request.

Example:

```js
const logger = (req, res, next) => {
    ...
};
```

### Utility

Usually performs a general operation.

Example:

```js
const hashPassword = async (password) => {
    ...
};
```

It doesn't need:

```text
req
res
next
```

So:

```text
middleware
→ HTTP pipeline

utility
→ reusable general function
```

This distinction becomes very important as your architecture grows.

---

# 32. Middleware vs Service

Another important distinction:

### Middleware

```text
HTTP request pipeline
```

### Service

```text
Business logic
```

For example:

```text
authenticate middleware
     ↓
identify user
     ↓
controller
     ↓
authService.login()
```

Don't turn your service into middleware just because both are reusable functions.

They solve different problems.

---

# 33. Middleware vs Controller

### Middleware

Answers:

> "Can this request continue?"

or:

> "What information should I attach to this request?"

### Controller

Answers:

> "What HTTP operation should happen?"

Example:

```text
authenticate
   ↓
Can this user continue?
```

Then:

```text
createTodo
   ↓
Create the Todo operation
```

This distinction will save you from creating "fat middleware."

# 37. Don't Create a Middleware for Everything

This is another important lesson.

Don't turn every two-line operation into a middleware just because you can.

For example:

```js
const addTwoNumbers = (req, res, next) => {
    req.result = 2 + 2;
    next();
};
```

This doesn't necessarily need to be middleware.

Ask:

> **Does this operation logically belong in the HTTP request pipeline?**

If not, it may be better as a utility or service function.

---

# 38. Middleware Should Be Composable

Good middleware can be combined:

```js
router.post(
    "/",
    authenticate,
    validateTodo,
    createTodo
);
```

Each component has one job:

```text
authenticate
     ↓
validateTodo
     ↓
createTodo
```

This is much better than:

```js
router.post(
    "/",
    giantTodoMiddleware,
    createTodo
);
```

We'll study **middleware composition** properly in 7.17.

# 39. Common Mistakes

### ❌ Mistake 1 — Forgetting `export`

You create:

```js
const logger = ...
```

but forget:

```js
export default logger;
```

Then importing it fails.

---

### ❌ Mistake 2 — Wrong import path

From:

```text
routes/todo.routes.js
```

to:

```text
middlewares/auth.middleware.js
```

the path might be:

```js
import authenticate from "../middlewares/auth.middleware.js";
```

Pay attention to the directory level.

---

### ❌ Mistake 3 — Forgetting `next()`

If middleware neither sends a response nor calls:

```js
next();
```

the request can hang.

---

### ❌ Mistake 4 — Sending a response and calling `next()`

Don't do:

```js
res.status(401).json({
    message: "Unauthorized"
});

next();
```

If you've already rejected the request, stop execution:

```js
return res.status(401).json({
    message: "Unauthorized"
});
```

---

### ❌ Mistake 5 — Putting business logic into middleware

Avoid turning:

```text
auth.middleware.js
```

into:

```text
authentication + database + email + business rules + token generation + everything else
```

Keep the responsibility focused.

### Next → **7.15 — Middleware Factories**

This is the next important jump.

You'll learn how to create middleware that **accepts configuration and returns middleware**, like:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        // check role
    };
};
```

Then you can do:

```js
requireRole("admin")
```

instead of creating separate middleware for every role. This idea will later become very useful for **RBAC, rate limits, validation, permissions, and reusable security rules**.
