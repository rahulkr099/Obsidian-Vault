# Phase 7 — Lesson 7.15

## Middleware Factories

In **7.14**, you learned how to create reusable middleware:

```text
middlewares/
├── logger.middleware.js
├── requestId.middleware.js
└── auth.middleware.js
```

Now we're going one level deeper.

Today you'll learn how to create **middleware that can be configured**.

The official Phase 7 roadmap calls this **7.15 — Middleware factories**.

---

# 1. The Problem

Suppose you have this middleware:

```js
const requireAdmin = (req, res, next) => {
    if (req.user.role !== "admin") {
        return res.status(403).json({
            success: false,
            message: "Admin access required"
        });
    }

    next();
};
```

It works.

But now imagine you need:

```text
admin
teacher
student
moderator
```

You could create:

```text
requireAdmin
requireTeacher
requireStudent
requireModerator
```

That's repetitive.

Instead, wouldn't it be better if we could write:

```js
requireRole("admin")
```

or:

```js
requireRole("teacher")
```

?

That's exactly what a **middleware factory** allows us to do.

---

# 2. What Is a Middleware Factory?

A middleware factory is:

> **A function that accepts configuration and returns a middleware function.**

The basic shape is:

```js
const factory = (configuration) => {
    return (req, res, next) => {
        // middleware logic
    };
};
```

Notice the two functions:

```text
factory
   ↓
returns
   ↓
middleware
```

This is the most important idea in this lesson.

---

# 3. Normal Middleware vs Middleware Factory

### Normal middleware

```js
const logger = (req, res, next) => {
    console.log(req.method);
    next();
};
```

You use:

```js
app.use(logger);
```

There is only one function.

---

### Middleware factory

```js
const requireRole = (role) => {
    return (req, res, next) => {
        // use role
    };
};
```

You use:

```js
requireRole("admin")
```

Notice:

```text
requireRole("admin")
        ↓
returns middleware
        ↓
Express executes middleware
```

That's the key difference.

---

# 4. Why Do We Need Two Functions?

This can initially look confusing:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        ...
    };
};
```

Let's separate the jobs.

### Outer function

```js
(role) => {
```

answers:

> **"How should this middleware be configured?"**

### Inner function

```js
(req, res, next) => {
```

answers:

> **"What should happen when a request arrives?"**

So:

```text
             requireRole()
                  │
                  │ configuration
                  ▼
                "admin"
                  │
                  ▼
          middleware function
                  │
                  ▼
             HTTP request
```

---

# 5. Your First Middleware Factory

Let's build one.

```js
const requireRole = (role) => {
    return (req, res, next) => {
        if (req.user.role !== role) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};

export default requireRole;
```

Now we can use:

```js
requireRole("admin")
```

or:

```js
requireRole("teacher")
```

or:

```js
requireRole("student")
```

without creating three separate middleware functions.

---

# 6. How Express Sees It

Suppose you write:

```js
router.get(
    "/admin",
    requireRole("admin"),
    adminController
);
```

This is important.

Express does **not** receive:

```js
requireRole
```

It receives the result of:

```js
requireRole("admin")
```

Conceptually:

```text
requireRole("admin")
        ↓
middleware function
        ↓
router.get(...)
```

So Express eventually sees something equivalent to:

```js
router.get(
    "/admin",
    (req, res, next) => {
        // role checking
    },
    adminController
);
```

---

# 7. Let's Understand It Step by Step

When your application starts:

```js
requireRole("admin")
```

runs.

The outer function receives:

```text
role = "admin"
```

It returns:

```js
(req, res, next) => {
    if (req.user.role !== role) {
        ...
    }

    next();
}
```

That returned function is registered with Express.

Later, when a request arrives:

```text
GET /admin
     ↓
returned middleware runs
     ↓
req.user.role
     ↓
compare with "admin"
```

So there are **two different moments**:

```text
APPLICATION STARTUP
      ↓
configure middleware

REQUEST TIME
      ↓
execute middleware
```

This distinction is extremely important.

---

# 8. A Simple Analogy

Imagine a security guard factory.

You tell the factory:

> "Create a guard who only allows admins."

```js
requireRole("admin")
```

The factory gives you:

```text
Admin Security Guard
```

You place that guard at the door.

Later:

```text
Person arrives
     ↓
Guard checks role
     ↓
Allowed / rejected
```

If you instead say:

```js
requireRole("teacher")
```

you get:

```text
Teacher Security Guard
```

Same factory.

Different configuration.

# 9. The Real Power

Without a factory:

```js

```

With a factory:

```js

    ...
};
```

Then:

```js

requireRole("teacher");

```

This is much more reusable.

# 12. Middleware Factory With Authentication

Remember the order.

`requireRole()` expects:

```js
req.user
```

to already exist.

So this would be wrong:

```js
router.get(
    "/admin",
    requireRole("admin"),
    authenticate,
    adminController
);
```

Why?

Because:

```text
requireRole
    ↓
needs req.user
```

but:

```text
authenticate
    ↓
creates req.user
```

comes later.

Correct:

```js
router.get(
    "/admin",
    authenticate,
    requireRole("admin"),
    adminController
);
```

Now:

```text
Request
   ↓
authenticate
   ↓
req.user created
   ↓
requireRole("admin")
   ↓
controller
```

This connects directly to your previous lessons about **middleware execution order**.

---

# 13. The Complete Flow

Suppose:

```js
router.delete(
    "/users/:id",
    authenticate,
    requireRole("admin"),
    deleteUser
);
```

The request flow is:

```text
DELETE /users/123
        │
        ▼
 authenticate
        │
        │ creates req.user
        ▼
 requireRole("admin")
        │
        ├── role != admin
        │       ↓
        │      403
        │
        └── role == admin
                ↓
           deleteUser
```

Now the architecture is becoming powerful.

---

# 14. Middleware Factory Is Not Middleware Yet

This distinction is worth drilling into.

This:

```js
requireRole
```

is the **factory**.

This:

```js
requireRole("admin")
```

is the **middleware produced by the factory**.

Think:

```text
requireRole
     │
     │ call
     ▼
requireRole("admin")
     │
     │ returns
     ▼
middleware function
```

That's why this:

```js
router.get(
    "/admin",
    requireRole,
    controller
);
```

is wrong for our design.

You need:

```js
router.get(
    "/admin",
    requireRole("admin"),
    controller
);
```

---

# 15. Another Example: Minimum Role Level

Let's make the idea more interesting.

Suppose:

```text
student → level 1
teacher → level 2
admin   → level 3
```

You could create:

```js
const requireMinimumLevel = (minimumLevel) => {
    return (req, res, next) => {
        if (req.user.level < minimumLevel) {
            return res.status(403).json({
                success: false,
                message: "Insufficient permissions"
            });
        }

        next();
    };
};
```

Then:

```js
requireMinimumLevel(2)
```

means:

```text
teacher or admin
```

while:

```js
requireMinimumLevel(3)
```

means:

```text
admin only
```

Same middleware factory.

Different configuration.

# 16. Middleware Factory for Request Logging

Factories aren't only for authorization.

Suppose you want configurable logging.

```js
const logger = (prefix) => {
    return (req, res, next) => {
        console.log(
            `[${prefix}] ${req.method} ${req.url}`
        );

        next();
    };
};
```

Now:

```js
app.use(
    logger("API")
);
```

or:

```js
router.use(
    logger("ADMIN")
);
```

The factory lets you customize behavior.

Another common use is configuration.

The factory receives:

```js
{
    windowMs: 60_000,
```

# 18. Middleware Factory for Validation

This pattern will become extremely important in your later validation lessons.

Imagine:

The factory receives a schema:

```js
const validate = (schema) => {
```

# 21. Closures — The JavaScript Concept Behind This

This lesson is secretly teaching you an important JavaScript concept:

> **Closures**

Consider:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        console.log(role);

        next();
    };
};
```

We call:

```js
const adminOnly = requireRole("admin");
```

Now:

```js
adminOnly(req, res, next);
```

can still access:

```js
role
```

even though the outer function has already finished.

Why?

Because the returned function **closes over** the `role` variable.

---

# 22. Visualizing the Closure

When we execute:

```js
const adminOnly = requireRole("admin");
```

think:

```text
requireRole("admin")
       │
       ▼
┌───────────────────────┐
│ role = "admin"        │
│                       │
│ returned middleware   │
└───────────┬───────────┘
            │
            ▼
      adminOnly()
```

The returned middleware remembers:

```text
role = "admin"
```

That's closure behavior.

# 23. Try This Tiny JavaScript Example

Before middleware, understand the JavaScript:

```js
const createGreeter = (name) => {
    return () => {
        console.log(`Hello ${name}`);
    };

greetRahul();
```

Output:

```text

```

The inner function remembers:


That's a closure.

# 25. This Is Why Middleware Factories Are Powerful

You aren't creating completely different middleware.

You're creating:

> **One middleware generator that produces customized middleware.**

Think:

```text
                requireRole()
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      admin        teacher       student
        │            │            │
        ▼            ▼            ▼
   middleware    middleware   middleware
```

One implementation.

Many configurations.

# 26. Multiple Configuration Values

A factory can accept more than one option.

For example:

```js
const requirePermission = (resource, action) => {
    return (req, res, next) => {
        console.log(resource);
        console.log(action);

        next();
    };
};
```

Then:

```js
requirePermission("todo", "delete");
```

or:

```js
requirePermission("user", "update");
```

or:

```js
requirePermission("course", "create");
```

This becomes useful when implementing permission-based authorization later.

---

# 27. Prefer an Options Object for Many Options

If a factory needs many configuration values, avoid:

```js
createMiddleware(
    "todo",
    "delete",
    true,
    10,
    "admin"
);
```

That becomes difficult to understand.

Instead:

```js
createMiddleware({
    resource: "todo",
    action: "delete",
    requireAdmin: true,
    maxAttempts: 10
});
```

Then:

```js
const createMiddleware = (options) => {
    return (req, res, next) => {
        // use options
    };
};
```

This is easier to read and extend.

---

# 28. Example: `requireRole`

Let's improve our earlier implementation.

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};

export default requireRole;
```

Now we can write:

```js
requireRole("admin")
```

or:

```js
requireRole("admin", "teacher")
```

This means:

```text
admin only
```

or:

```text
admin OR teacher
```

respectively.

---

# 29. Why `...allowedRoles`?

This:

```js
(...allowedRoles)
```

collects all arguments into an array.

For:

```js
requireRole("admin")
```

we get:

```js
allowedRoles = ["admin"]
```

For:

```js
requireRole("admin", "teacher")
```

we get:

```js
allowedRoles = [
    "admin",
    "teacher"
]
```

Then:

```js
allowedRoles.includes(req.user.role)
```

checks whether the user's role is allowed.

This is normal JavaScript rest-parameter behavior.

# 31. Factory vs Configuration Object

These are related but different.

### Factory

```js
requireRole("admin")
```

creates middleware.

### Configuration object

```js
{
    roles: ["admin"],
    strict: true
}
```

contains configuration.

You can combine them:

```js
requireRole({
    roles: ["admin"],
    strict: true
});
```

Then:

```js
const requireRole = (options) => {
    return (req, res, next) => {
        // use options.roles
        // use options.strict
    };
};
```

---

# 32. When Should You Use a Middleware Factory?

Use one when:

> **The middleware behavior is mostly the same, but some configuration changes between uses.**

Good examples:

```text
requireRole(role)
validate(schema)
requirePermission(resource, action)
createRateLimiter(options)
logger(prefix)
checkFeature(flag)
```

Bad reason:

> "I heard factories are advanced, so I'll use one everywhere."

Don't.

If middleware has no meaningful configuration, ordinary middleware is simpler.

---

# 33. Normal Middleware Is Better Here

For example:

```js
const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();
    next();
};
```

There is no configuration.

So don't unnecessarily write:

```js
const requestId = () => {
    return (req, res, next) => {
        ...
    };
};
```

That adds complexity without giving you anything useful.

Use:

```js
app.use(requestId);
```

Simple.

---

# 34. Factory Is Better Here

For roles:

```js
requireRole("admin")
```

because the configuration changes.

So:

```text
requestId
→ normal middleware

requireRole("admin")
→ middleware factory
```

That's the practical rule.

# 35. A Complete Example

### `role.middleware.js`

```js
const requireRole = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};

export default requireRole;
```

### `user.routes.js`

```js
import express from "express";

import authenticate from "../middlewares/auth.middleware.js";
import requireRole from "../middlewares/role.middleware.js";

const router = express.Router();

router.get(
    "/profile",
    authenticate,
    getProfile
);

router.get(
    "/admin",
    authenticate,
    requireRole("admin"),
    getAdminDashboard
);

router.get(
    "/management",
    authenticate,
    requireRole("admin", "teacher"),
    getManagementDashboard
);

export default router;
```

Notice how clean the routes are.

# 36. What the Controller Doesn't Need to Know

The controller:

```js
const getAdminDashboard = (req, res) => {
    res.json({
        success: true
    });
};
```

doesn't need to know:

```text
How authentication works
How roles are checked
How many roles are allowed
```

Those concerns were handled before it.

So:

```text
authenticate
   ↓
requireRole("admin")
   ↓
controller
```

The controller receives an already-authorized request.

This is exactly the direction your starter architecture is moving toward.

---

# 37. A Factory Can Return Different Middleware

A factory doesn't necessarily have to return the same behavior.

For example:

```js
const checkFeature = (enabled) => {
    return (req, res, next) => {
        if (!enabled) {
            return res.status(404).json({
                success: false,
                message: "Feature unavailable"
            });
        }

        next();
    };
};
```

Then:

```js
checkFeature(true)
```

allows requests.

```js
checkFeature(false)
```

rejects them.

The factory controls the configuration.

---

# 38. Common Mistake — Forgetting the Inner Function

Wrong:

```js
const requireRole = (role) => {
    if (role !== "admin") {
        ...
    }
};
```

This isn't a middleware factory because it doesn't return:

```js
(req, res, next) => {}
```

Correct:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        ...
    };
};
```

---

# 39. Common Mistake — Passing the Factory Instead of the Result

Wrong:

```js
router.get(
    "/admin",
    requireRole,
    controller
);
```

Express receives the factory itself.

Correct:

```js
router.get(
    "/admin",
    requireRole("admin"),
    controller
);
```

Now Express receives the generated middleware.

---

# 40. Common Mistake — Wrong Middleware Order

Wrong:

```js
router.get(
    "/admin",
    requireRole("admin"),
    authenticate,
    controller
);
```

`requireRole` needs:

```js
req.user
```

but `authenticate` hasn't created it yet.

Correct:

```js
router.get(
    "/admin",
    authenticate,
    requireRole("admin"),
    controller
);
```

---

# 41. Common Mistake — Putting Business Logic in the Factory

Don't create:

```js
const requireRole = (role) => {
    return async (req, res, next) => {
        // role check
        // create user
        // send email
        // update database
        // create todo
    };
};
```

The factory should configure middleware behavior.

Keep business logic in services.

Remember your architecture:

```text
Middleware
    ↓
Controller
    ↓
Service
    ↓
Repository
```
