# Phase 7 — Lesson 7.16

## Conditional Middleware

In **7.15**, you learned middleware factories:

```js
requireRole("admin")
```

A factory lets us **configure** middleware.

Now we add another idea:

> **Sometimes middleware should behave differently depending on the request or configuration.**

This is **conditional middleware**.

Your Phase 7 roadmap places **7.16 Conditional Middleware** directly after middleware factories and before middleware composition.

The goal is not to memorize another pattern. The goal is to understand **when middleware should run, when it should skip, and when it should stop a request**.

---

# 1. What Is Conditional Middleware?

Normal middleware:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);

    next();
};
```

It runs for every request where you register it.

Conditional middleware asks:

> "Should I perform my special logic for this particular request?"

For example:

```text
Request
   ↓
Is this /healthz?
   │
   ├── Yes → skip special logic
   │
   └── No  → run special logic
```

So the basic idea is:

```text
Request
   ↓
Condition
   │
   ├── false → next()
   │
   └── true  → middleware logic
```

---

# 2. Why Do We Need It?

Imagine you have a logger that should log API requests but not health checks.

You don't necessarily want:

```text
GET /healthz
GET /api/users
GET /api/todos
GET /readyz
```

all treated exactly the same.

You could create different route registrations.

But sometimes it's cleaner for middleware itself to decide:

```js
if (req.path === "/healthz") {
    return next();
}
```

Then normal requests continue through the special logic.

---

# 3. The Simplest Conditional Middleware

```js
const middleware = (req, res, next) => {
    if (req.path === "/healthz") {
        return next();
    }

    console.log("Special middleware running");

    next();
};
```

The flow:

```text
GET /healthz
     ↓
condition true
     ↓
next()
     ↓
skip special logic
```

For:

```text
GET /api/todos
```

we get:

```text
Request
   ↓
condition false
   ↓
special middleware logic
   ↓
next()
```

---

# 4. Understand `return next()`

You'll often see:

```js
if (condition) {
    return next();
}
```

Why `return`?

Because we want to stop executing the rest of this middleware.

For example:

```js
const middleware = (req, res, next) => {
    if (req.path === "/healthz") {
        return next();
    }

    console.log("Running special logic");

    next();
};
```

Without `return`:

```js
if (req.path === "/healthz") {
    next();
}

console.log("Running special logic");

next();
```

you risk calling `next()` twice.

That's a common middleware bug.

---

# 5. The Three Possible Outcomes

A conditional middleware generally has three possible behaviors.

### 1. Skip

```js
return next();
```

Meaning:

> "This middleware doesn't apply to this request."

---

### 2. Continue after doing its work

```js
doSomething();

next();
```

Meaning:

> "This middleware applies, and the request can continue."

---

### 3. Stop the request

```js
return res.status(403).json({
    success: false
});
```

Meaning:

> "This request isn't allowed to continue."

So:

```text
Conditional middleware
       │
       ├── Skip → next()
       │
       ├── Process → logic → next()
       │
       └── Reject → response
```

This is the mental model I want you to remember.

---

# 6. Example: Skip Health Checks

Suppose:

```js
const logger = (req, res, next) => {
    if (req.path === "/healthz") {
        return next();
    }

    console.log(
        req.method,
        req.path
    );

    next();
};
```

Now:

```text
GET /healthz
```

doesn't produce the custom log.

But:

```text
GET /api/v1/todos
```

does.

---

# 7. Why Would We Skip Health Checks?

Health checks can be called frequently.

For example, a load balancer or deployment platform might repeatedly request:

```text
GET /healthz
```

If you have heavy logging, tracing, metrics, or other processing, you may not want every health check to create the same amount of application noise.

The source roadmap also treats `/healthz` and `/readyz` as infrastructure-related endpoints.

The exact behavior is an architectural choice.

---

# 8. Conditional Authentication

Here's a more useful example.

Suppose most of your API is protected, but:

```text
GET /healthz
GET /api/v1/auth/login
POST /api/v1/auth/signup
```

must be public.

One approach is to apply authentication only to protected routers:

```js
publicRouter...
protectedRouter.use(authenticate);
```

That's often cleaner.

But you can also create conditional behavior.

For example:

```js
const authenticateUnlessPublic = (req, res, next) => {
    const publicPaths = [
        "/healthz",
        "/api/v1/auth/login",
        "/api/v1/auth/signup"
    ];

    if (publicPaths.includes(req.path)) {
        return next();
    }

    return authenticate(req, res, next);
};
```

Now:

```text
Public request
     ↓
skip authentication

Protected request
     ↓
authenticate
```

---

# 9. But Be Careful With This Pattern

Although conditional authentication is possible, don't create one giant middleware containing:

```text
public routes
admin routes
user routes
auth routes
health routes
special routes
exceptions
```

That can become difficult to maintain.

Often this is cleaner:

```text
routes/
├── auth.routes.js
├── public.routes.js
└── protected.routes.js
```

Then:

```js
app.use("/api/v1/auth", authRoutes);

app.use(
    "/api/v1/users",
    authenticate,
    userRoutes
);
```

This is an important lesson:

> **Conditional middleware is a tool, not a reason to make your middleware complicated.**

# 10. Conditional Middleware Based on HTTP Method

You can also check:

```js
req.method
```

For example:

```js
const writeLogger = (req, res, next) => {
    if (req.method === "GET") {
        return next();
    }

    console.log(
        "Write operation:",
        req.method,
        req.url
    );

    next();
};
```

Now:

```text
GET
 ↓
skip

POST
 ↓
log

PUT
 ↓
log

DELETE
 ↓
log
```

This can be useful when you only care about specific types of operations.

# 11. Conditional Middleware Based on Path

Example:

```js
const apiOnlyMiddleware = (req, res, next) => {
    if (!req.path.startsWith("/api")) {
        return next();
    }

    console.log("API request");

    next();
};
```

Now:

```text
/api/users
   ↓
special logic

/healthz
   ↓
skip
```

Again, this is a simple conditional.

---

# 12. Conditional Middleware Based on Headers

You can inspect request headers:

```js
const internalRequest = (req, res, next) => {
    if (req.headers["x-internal-request"] !== "true") {
        return next();
    }

    console.log("Internal request");

    next();
};
```

Now:

```http
X-Internal-Request: true
```

causes special behavior.

Without that header:

```text
skip
```

Be careful with security-sensitive decisions based only on client-controlled headers.

A client can generally send arbitrary headers.

---

# 13. Conditional Middleware Based on Environment

Sometimes you want middleware only in development.

For example:

```js
const developmentLogger = (req, res, next) => {
    if (process.env.NODE_ENV !== "development") {
        return next();
    }

    console.log(
        "Development request:",
        req.method,
        req.url
    );

    next();
};
```

Now:

```text
development
    ↓
run logger

production
    ↓
skip logger
```

This is a common idea.

However, if the middleware should simply exist only in development, you can often conditionally register it instead:

```js
if (process.env.NODE_ENV === "development") {
    app.use(developmentLogger);
}
```

That's often cleaner.

---

# 14. Two Different Ways to Be Conditional

This distinction is very useful.

## A. Conditional registration

Decide when the application starts:

```js
if (process.env.NODE_ENV === "development") {
    app.use(logger);
}
```

This means:

```text
Application startup
     ↓
Should middleware exist?
     ↓
YES → register it
NO  → don't register it
```

---

## B. Conditional execution

Register the middleware, but decide per request:

```js
app.use((req, res, next) => {
    if (someCondition) {
        return next();
    }

    // do something
    next();
});
```

This means:

```text
Application startup
     ↓
Middleware registered

Request arrives
     ↓
Should middleware logic run?
```

These are different patterns.

---

# 15. When Should You Use Which?

Use **conditional registration** when the decision is based on application configuration.

Example:

```text
NODE_ENV
```

Use **conditional execution** when the decision depends on the incoming request.

Example:

```text
HTTP method
URL
user
headers
request properties
```

Think:

```text
Environment decision
     ↓
registration

Request decision
     ↓
execution
```

# 16. Conditional Middleware + Factory

Now combine today's lesson with **7.15**.

Suppose you create:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false
            });
        }

        if (req.user.role !== role) {
            return res.status(403).json({
                success: false
            });
        }

        next();
    };
};
```

That's a factory.

Now imagine a factory that itself accepts a condition:

```js
const middlewareIf = (condition, middleware) => {
    return (req, res, next) => {
        if (!condition(req)) {
            return next();
        }

        return middleware(req, res, next);
    };
};
```

This is a more advanced pattern.

---

# 17. Understanding `middlewareIf`

Suppose:

```js
const onlyPost = middlewareIf(
    (req) => req.method === "POST",
    logger
);
```

Then:

```text
GET
 ↓
condition false
 ↓
next()

POST
 ↓
condition true
 ↓
logger
 ↓
next()
```

This gives you a reusable conditional wrapper.

---

# 18. Build `middlewareIf`

Let's implement it carefully:

```js
const middlewareIf = (condition, middleware) => {
    return (req, res, next) => {
        if (!condition(req)) {
            return next();
        }

        return middleware(req, res, next);
    };
};

export default middlewareIf;
```

Notice the responsibilities:

### `condition`

Decides:

```text
Should middleware run?
```

### `middleware`

Does:

```text
The actual work
```

### Returned function

Connects the two to Express.

---

# 19. Use It

Suppose:

```js
const logger = (req, res, next) => {
    console.log(
        "Write:",
        req.method,
        req.url
    );

    next();
};
```

Create:

```js
const writeLogger = middlewareIf(
    (req) => req.method !== "GET",
    logger
);
```

Then:

```js
app.use(writeLogger);
```

The flow becomes:

```text
GET /todos
     ↓
condition false
     ↓
next()

POST /todos
     ↓
condition true
     ↓
logger
     ↓
next()
```

---

# 20. Why This Pattern Is Useful

Without the helper:

```js
app.use((req, res, next) => {
    if (req.method !== "GET") {
        logger(req, res, next);
        return;
    }

    next();
});
```

This works.

But if you need conditional behavior in many places, a reusable abstraction can make the intent clearer:

```js
middlewareIf(
    condition,
    logger
);
```

However, don't over-engineer simple applications.

For one condition, a normal `if` may be easier to read.

# 21. Conditional Middleware Based on User

Suppose authentication has already run:

```js
req.user
```

exists.

You might want additional behavior for admins:

```js
const adminAudit = (req, res, next) => {
    if (req.user?.role !== "admin") {
        return next();
    }

    console.log(
        "Admin request:",
        req.method,
        req.url
    );

    next();
};
```

Flow:

```text
Request
   ↓
authenticate
   ↓
req.user
   ↓
adminAudit
   │
   ├── admin → audit
   │
   └── user  → skip
   ↓
controller
```

Notice the dependency:

```text
authenticate
    ↓
adminAudit
```

because `adminAudit` needs `req.user`.

---

# 22. Conditional Middleware Based on Route

Suppose:

```text
/api/v1/admin/*
```

needs extra auditing.

You could register:

```js
app.use(
    "/api/v1/admin",
    adminAudit
);
```

This is actually often better than checking:

```js
if (req.path.startsWith("/api/v1/admin"))
```

inside a global middleware.

This gives us an important principle:

> **Use Express's routing structure to express conditions when possible.**

Instead of:

```text
global middleware
     ↓
if this route...
     ↓
if that route...
```

sometimes use:

```text
admin router
     ↓
admin middleware
```

Cleaner.

---

# 23. Conditional Middleware vs Route-Level Middleware

These can solve similar problems.

### Conditional middleware

```js
app.use((req, res, next) => {
    if (req.path.startsWith("/admin")) {
        ...
    }

    next();
});
```

### Route-level structure

```js
app.use(
    "/admin",
    adminMiddleware,
    adminRouter
);
```

The second is often easier to understand.

Why?

Because the condition is expressed by the **route structure itself**.

---

# 24. Prefer Structure Over Complex Conditions

This is an important architectural lesson.

Instead of:

```js
if (
    req.path.startsWith("/admin") &&
    req.method === "DELETE" &&
    req.user?.role === "admin"
) {
    ...
}
```

you may want:

```js
adminRouter.delete(
    "/users/:id",
    authenticate,
    requireRole("admin"),
    deleteUser
);
```

Now each concern is obvious.

```text
adminRouter
     ↓
authenticate
     ↓
requireRole("admin")
     ↓
deleteUser
```

This is easier to read, test, and maintain.

---

# 25. Conditional Middleware and `next()`

Let's make the three paths very clear.

### Skip

```js
if (condition === false) {
    return next();
}
```

### Execute and continue

```js
if (condition === true) {
    doSomething();
}

next();
```

### Reject

```js
if (condition === false) {
    return res.status(403).json({
        message: "Forbidden"
    });
}
```

The key difference:

```text
skip
→ next()

reject
→ response

process
→ work + next()
```

Don't confuse **skip** with **reject**.

---

# 26. Example: Maintenance Mode

Here's a realistic example.

Suppose your application enters maintenance mode.

You could create:

```js
const maintenanceMiddleware = (req, res, next) => {
    if (process.env.MAINTENANCE_MODE !== "true") {
        return next();
    }

    if (req.path === "/healthz") {
        return next();
    }

    return res.status(503).json({
        success: false,
        message: "Service temporarily unavailable"
    });
};
```

Flow:

```text
Request
   ↓
Maintenance mode?
   │
   ├── No → next()
   │
   └── Yes
        │
        ├── /healthz → next()
        │
        └── anything else → 503
```

This is a genuine conditional middleware use case.

---

# 27. Why Health Checks Might Be an Exception

Imagine deployment infrastructure needs:

```text
GET /healthz
```

to determine whether your application is alive.

If maintenance middleware returned:

```text
503
```

for the health check, your infrastructure might think:

> "The application is unhealthy."

So you might intentionally allow:

```text
/healthz
```

through.

This is an example of a conditional rule based on application requirements.

app.use(

# 29. Conditional Logging

You might want detailed logs only for certain requests.

For example:

```js
const debugRequests = (req, res, next) => {
    if (req.headers["x-debug"] !== "true") {
        return next();
    }

    console.log({
        method: req.method,
        path: req.path,
        query: req.query
    });

    next();
};
```

This can be useful during development.

But remember:

```text
Client-controlled debug header
```

shouldn't be treated as a security boundary.

It only controls logging behavior.

# 30. Conditional Middleware Based on Request Size

You can inspect request information and decide whether special handling is needed.

Conceptually:

```js
const largeRequestLogger = (req, res, next) => {
    if (Number(req.headers["content-length"]) < 100000) {
        return next();
    }

    console.log("Large request");

    next();
};
```

This is just an example of conditional execution.

In real applications, body-size handling should generally be designed using the appropriate parser/security configuration rather than relying on ad-hoc logging logic.

# 31. Conditional Middleware and Security

Conditional middleware becomes especially important when you later build security.

Your starter roadmap explicitly says:

> Not every middleware belongs on every route.

For example:

```text
GET /healthz
```

doesn't need authentication.

But:

```text
DELETE /todos/:id
```

does.

This is why you shouldn't simply think:

```text
"Add every security middleware globally."
```

Instead ask:

> **Which requests actually need this protection?**

---

# 32. But Some Security Middleware Should Be Global

For example, some security protections are naturally application-wide.

Your eventual `app.js` might contain things like:

```text
CORS
security headers
request ID
logging
body parsing
```

while route-specific middleware might include:

```text
authentication
authorization
validation
resource ownership checks
```

The correct placement depends on what the middleware protects.

This is architecture, not memorization.

# 33. Conditional Middleware + Authentication

Let's build a realistic flow.

```js
router.get(
    "/profile",
    authenticate,
    getProfile
);

router.delete(
    "/users/:id",
    authenticate,
    requireRole("admin"),
    deleteUser
);
```

We don't need conditional authentication inside `authenticate`.

Instead, the **route structure itself determines whether authentication runs**.

That's often cleaner.

So conditional middleware is not always the answer.

---

# 34. When Conditional Middleware Is a Good Choice

Good examples:

```text
✓ Skip health checks from verbose logging
✓ Enable behavior only in development
✓ Apply behavior to certain HTTP methods
✓ Enable maintenance mode
✓ Apply optional behavior based on request properties
✓ Wrap another middleware with a condition
```

Less ideal:

```text
✗ Giant middleware with dozens of route exceptions
✗ Complex authorization hidden inside path checks
✗ Replacing clean router structure with nested if statements
```

# 35. A Very Important Rule

When you see yourself writing:

```js
if (req.path === ...)
if (req.path === ...)
if (req.path === ...)
if (req.path === ...)
```

inside one global middleware, stop and ask:

> **Should these routes have different middleware chains instead?**

For example, instead of:

```text
global middleware
  ↓
if admin
  ↓
if auth
  ↓
if public
  ↓
if health
```

consider:

```text
Public Router
     ↓
public middleware

User Router
     ↓
authenticate

Admin Router
     ↓
authenticate
     ↓
requireRole("admin")
```

Much cleaner.

# 40. Common Mistakes

## ❌ Mistake 1 — Forgetting `return`

Bad:

```js
if (condition) {
    next();
}

doSomething();

next();
```

Potentially:

```text
next()
+
next()
```

Correct:

```js
if (condition) {
    return next();
}

doSomething();

next();
```

---

## ❌ Mistake 2 — Confusing skip with reject

Skip:

```js
return next();
```

Reject:

```js
return res.status(403).json(...);
```

They mean completely different things.

---

## ❌ Mistake 3 — Creating giant conditional middleware

Avoid:

```js
if (routeA) ...
if (routeB) ...
if (routeC) ...
if (routeD) ...
if (admin) ...
if (user) ...
```

Sometimes the correct solution is simply to use separate routers and middleware chains.

---

## ❌ Mistake 4 — Checking `req.user` before authentication

Wrong:

```text
requireRole
   ↓
authenticate
```

Correct:

```text
authenticate
   ↓
requireRole
```

because:

```text
authenticate
→ creates req.user
```

---

## ❌ Mistake 5 — Trusting client-controlled values for security

For example:

```js
if (req.headers["x-admin"] === "true") {
    // allow admin operation
}
```

This is **not authentication or authorization**.

A client can send:

```http
X-Admin: true
```

Headers are not proof of identity or permission.

---

# 41. Conditional Registration vs Conditional Execution

This is one of today's most important concepts.

### Conditional registration

```js
if (process.env.NODE_ENV === "development") {
    app.use(logger);
}
```

Decision happens:

```text
Application startup
```

### Conditional execution

```js
app.use((req, res, next) => {
    if (req.method === "GET") {
        return next();
    }

    logger(req, res, next);
});
```

Decision happens:

```text
Every request
```

Remember:

```text
Configuration condition
        ↓
registration

Request condition
        ↓
execution
```

# 43. The Key Difference: Factory vs Conditional Middleware

You learned two related but different concepts.

### Middleware factory

Changes middleware based on **configuration**:

```js
requireRole("admin")
```

Meaning:

```text
Create middleware configured for admin.
```

### Conditional middleware

Changes behavior based on **the current request or condition**:

```js
if (req.method === "POST") {
    ...
}
```

Meaning:

```text
For this request, should the middleware run?
```

So:

```text
Factory
→ configure

Conditional
→ decide
```

And they can be combined:

```text
factory
   ↓
configured middleware
   ↓
conditional execution
   ↓
controller
```

# 45. The Mental Model

If you remember only one thing from this lesson, remember:

```text
                    REQUEST
                       │
                       ▼
              CONDITIONAL CHECK
                       │
              ┌────────┴────────┐
              │                 │
           doesn't apply      applies
              │                 │
              ▼                 ▼
           next()          middleware logic
                                │
                         ┌──────┴──────┐
                         │             │
                       next()        response
                         │             │
                         ▼             ▼
                    next handler     request ends
```

And one architectural rule:

> **If your condition is becoming a long list of routes and exceptions, don't keep adding `if` statements. Move the condition into your route/router structure.**

That is how you keep middleware reusable without turning it into a giant mess.
