# Phase 7 — Lesson 7.17

## Middleware Composition

You now know:

- **7.14** → reusable middleware
    
- **7.15** → middleware factories
    
- **7.16** → conditional middleware
    

Now we put those ideas together.

The Phase 7 roadmap defines **7.17 as Middleware Composition**, followed by common mistakes, debugging, and finally building a reusable middleware system.

The main idea is:

> **Middleware composition means combining small middleware functions into a clean request pipeline.**

Instead of creating one giant middleware, we create several small pieces and connect them.

---

# 1. The Problem Composition Solves

Imagine a Todo API endpoint:

```text
POST /api/v1/todos
```

The request might need:

```text
Authentication
Validation
Authorization
Logging
Rate limiting
Controller
```

A beginner might put everything into one function:

```js
const createTodoMiddleware = async (req, res, next) => {
    // authenticate
    // validate
    // check role
    // check ownership
    // log
    // rate limit
    // create todo
};
```

This becomes difficult to understand.

Instead:

```text
Request
   ↓
authenticate
   ↓
validate
   ↓
authorize
   ↓
controller
```

Each middleware has one responsibility.

That's composition.

---

# 2. What Does "Composition" Mean?

In simple words:

> **Composition means building a bigger process by combining smaller functions.**

For example:

```text
A
↓
B
↓
C
↓
D
```

Instead of one giant:

```text
A + B + C + D
```

You create:

```text
middleware A
middleware B
middleware C
middleware D
```

and let Express execute them in sequence.

---

# 3. The Basic Express Example

```js
router.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

Here:

```text
authenticate
       ↓
validateTodo
       ↓
createTodo
```

This is middleware composition.

Technically, `createTodo` is your controller/handler rather than middleware in the same conceptual sense, but it participates in the same Express handler chain.

---

# 4. Think of It Like a Pipeline

Imagine a factory:

```text
Raw request
     │
     ▼
┌──────────────┐
│ Authentication│
└──────┬───────┘
       ▼
┌──────────────┐
│ Validation   │
└──────┬───────┘
       ▼
┌──────────────┐
│ Authorization│
└──────┬───────┘
       ▼
┌──────────────┐
│ Controller   │
└──────┬───────┘
       ▼
   Response
```

Each stage transforms, checks, or enriches the request.

---

# 5. Middleware Composition Is Already Something You've Used

You don't need a special library to compose middleware.

You've already done it.

For example:

```js
app.use(requestId);
app.use(logger);
```

That's composition.

And:

```js
router.get(
    "/profile",
    authenticate,
    requireRole("admin"),
    getProfile
);
```

is also composition.

You are simply combining handlers into a pipeline.

---

# 6. Why Small Middleware Is Better

Consider:

```js
const authenticate = ...
const validateTodo = ...
const requireRole = ...
```

Each function has a clear responsibility.

```text
authenticate
→ Who is this?

validateTodo
→ Is the input valid?

requireRole
→ Is this user allowed?

controller
→ What should the application do?
```

This makes the code easier to:

- read
    
- test
    
- reuse
    
- debug
    
- modify
    

This follows the starter's broader architecture goal: don't memorize folders; understand how the request moves through layers.

# 7. Example: Authentication + Authorization

Let's use what you learned in 7.15.

```js
router.delete(
    "/users/:id",
    authenticate,
    requireRole("admin"),
    deleteUser
);
```

The composition is:

```text
Request
   ↓
authenticate
   ↓
requireRole("admin")
   ↓
deleteUser
```

If authentication fails:

```text
authenticate
   ↓
401
```

The next middleware never runs.

If authentication succeeds but role fails:

```text
authenticate
   ↓
requireRole("admin")
   ↓
403
```

The controller never runs.

If everything succeeds:

```text
authenticate
   ↓
requireRole("admin")
   ↓
deleteUser
   ↓
response
```

# 8. Middleware Can Add Information

Composition becomes even more useful when middleware adds information to `req`.

For example:

### `requestId`

```js
req.requestId = crypto.randomUUID();
```

Then:

### `logger`

```js
console.log(req.requestId);
```

Then:

### `authenticate`

```js
req.user = user;
```

Then:

### `requireRole`

```js
req.user.role
```

So information can flow through the pipeline.

```text
request
   ↓
requestId
   │
   └── req.requestId
          ↓
       logger
          ↓
      authenticate
          │
          └── req.user
                 ↓
            requireRole
                 ↓
             controller
```

This is one of the most important patterns in backend architecture.

---

# 9. Middleware Composition Is About Data Flow Too

Don't think only:

```text
A → B → C
```

Think:

```text
A
 ↓
adds req.requestId
 ↓
B
 ↓
adds req.user
 ↓
C
 ↓
uses req.user + req.requestId
```

So your request object becomes a shared context.

Conceptually:

```text
req
├── requestId
├── user
├── validatedBody
└── other request metadata
```

The exact fields depend on your architecture.

# 10. Example: Request Context

Imagine:

```js
const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();
    next();
};
```

Then:

```js
const authenticate = (req, res, next) => {
    req.user = {
        id: "123",
        role: "admin"
    };

    next();
};
```

Then:

```js
const audit = (req, res, next) => {
    console.log({
        requestId: req.requestId,
        userId: req.user.id
    });

    next();
};
```

Composition:

```js
app.get(
    "/admin",
    requestId,
    authenticate,
    audit,
    controller
);
```

Flow:

```text
request
  ↓
requestId
  ↓
req.requestId
  ↓
authenticate
  ↓
req.user
  ↓
audit
  ↓
controller
```

# 11. Ordering Becomes Extremely Important

Composition doesn't remove the importance of order.

Consider:

```js
router.get(
    "/admin",
    requireRole("admin"),
    authenticate,
    controller
);
```

This is wrong if `requireRole` expects:

```js
req.user
```

because:

```text
requireRole
    ↓
needs req.user

authenticate
    ↓
creates req.user
```

Correct:

```js
router.get(
    "/admin",
    authenticate,
    requireRole("admin"),
    controller
);
```

Therefore:

> **Compose middleware according to dependencies.**

---

# 12. Dependency Thinking

Ask:

> "What does this middleware need before it can run?"

For example:

### `logger`

Needs:

```text
requestId
```

Therefore:

```text
requestId
 ↓
logger
```

### `requireRole`

Needs:

```text
req.user
```

Therefore:

```text
authenticate
 ↓
requireRole
```

### `validate`

May need:

```text
req.body
```

Therefore:

```text
express.json()
 ↓
validate
```

This is a very powerful way to design middleware order.

# 17. Composition With Conditional Middleware

You can also combine 7.16:

```js

    "/todos",
    authenticate,
    debugMiddleware,
    validateTodo,
    createTodo
```

`debugMiddleware` might internally decide:

```js

    return next();

```

So:

```text

   ↓

   ↓

```

This shows how the concepts build on each other.

# 18. Don't Create One Giant "Compose Everything" Middleware

A common mistake is thinking composition means:

```js
const everything = (req, res, next) => {
    authenticate();
    validate();
    authorize();
    sanitize();
    log();
    ...
};
```

That's not really the goal.

The goal is:

```text
authenticate
   ↓
validate
   ↓
authorize
   ↓
controller
```

**Composition should make the pieces easier to understand, not hide them.**


# 20. A `compose()` Helper

You may eventually encounter code like:

```js
compose(
    authenticate,
    validateTodo,
    requireRole("admin")
);
```

This means:

> "Create one middleware from these middleware functions."

Conceptually:

```text
authenticate
     +
validateTodo
     +
requireRole
     ↓
one composed middleware
```

Express itself already supports multiple middleware handlers, so you don't always need a custom `compose()` helper.

But understanding the concept is useful because many frameworks and libraries use function composition.

---

# 21. Building a Simple `compose`

For learning purposes, let's build one.

```js
const compose = (middlewares) => {
    return (req, res, next) => {
        let index = -1;

        const dispatch = (i) => {
            if (i <= index) {
                return next(
                    new Error("next() called multiple times")
                );
            }

            index = i;

            const middleware = middlewares[i];

            if (!middleware) {
                return next();
            }

            return middleware(
                req,
                res,
                () => dispatch(i + 1)
            );
        };

        dispatch(0);
    };
};

export default compose;
```

This is more advanced than you need for normal Express applications.

We're studying it to understand what composition means internally.

---

# 22. How `compose()` Works

Suppose:

```js
const pipeline = compose([
    requestId,
    logger,
    authenticate
]);
```

Calling:

```js
pipeline(req, res, next);
```

starts:

```text
dispatch(0)
```

which executes:

```text
requestId
```

When it calls:

```js
next()
```

the composition moves to:

```text
dispatch(1)
```

which executes:

```text
logger
```

Then:

```text
dispatch(2)
```

executes:

```text
authenticate
```

Finally:

```text
dispatch(3)
```

has no more middleware and calls the final:

```js
next()
```

So:

```text
dispatch(0)
   ↓
requestId
   ↓
dispatch(1)
   ↓
logger
   ↓
dispatch(2)
   ↓
authenticate
   ↓
dispatch(3)
   ↓
next()
```

---

# 23. Why `next()` Is the Connection

This is the beautiful part.

Each middleware doesn't need to know the whole pipeline.

It only knows:

> "When I'm finished, call `next()`."

For example:

```js
const A = (req, res, next) => {
    console.log("A");
    next();
};

const B = (req, res, next) => {
    console.log("B");
    next();
};

const C = (req, res, next) => {
    console.log("C");
    next();
};
```

Composition:

```text
A → B → C
```

comes from:

```text
A calls next()
       ↓
B runs

B calls next()
       ↓
C runs
```

That's the heart of Express middleware.

---

# 24. Middleware Is Cooperative

This is a useful way to think about it.

Each middleware cooperates with the next:

```text
Middleware A
     │
     │ next()
     ▼
Middleware B
     │
     │ next()
     ▼
Middleware C
```

If A doesn't call `next()` and doesn't send a response:

```text
A
 ↓
STOP
```

The request may hang.

If B sends a response:

```text
A
 ↓
B
 ↓
response
```

C doesn't execute.

So every middleware controls whether the pipeline continues.

---

# 25. Composition With Errors

Now suppose:

```js
const validateTodo = (req, res, next) => {
    if (!req.body.title) {
        return next(
            new Error("Title is required")
        );
    }

    next();
};
```

Then:

```text
authenticate
   ↓
validateTodo
   ↓
ERROR
   ↓
error middleware
```

The normal pipeline is interrupted.

This connects directly to your upcoming **Phase 8 error architecture**, where the starter uses `AppError`, `asyncHandler`, and global error middleware.

---

# 26. Normal Flow vs Error Flow

Normal:

```text
Request
 ↓
A
 ↓ next()
B
 ↓ next()
C
 ↓
Response
```

Error:

```text
Request
 ↓
A
 ↓ next()
B
 ↓
next(error)
 ↓
Error Middleware
 ↓
Error Response
```

So middleware composition isn't only about successful requests.

It also defines how failures move through the application.

# 28. Middleware Composition vs Service Composition

Don't confuse the two.

### Middleware composition

```text
authenticate
 ↓
validate
 ↓
authorize
 ↓
controller
```

It happens around the HTTP request.

### Service composition

Later you might have:

```text
authService
 ↓
userRepository
 ↓
passwordService
 ↓
tokenService
```

That's application/business logic.

Different layer.

---

# 29. Middleware Composition vs Function Composition

At the JavaScript level:

```js
f(g(x))
```

is function composition.

In Express:

```text
middleware A
     ↓
middleware B
     ↓
middleware C
```

is pipeline-style composition.

The idea is related:

> **Build larger behavior from smaller pieces.**

But don't assume every mathematical/function-composition rule maps directly to Express's `next()` pipeline.

# 30. Composition With Router-Level Middleware

This is one of the cleanest patterns.

```js
const todoRouter = express.Router();

todoRouter.use(authenticate);

todoRouter.post(
    "/",
    validateTodo,
    createTodo
);

todoRouter.patch(
    "/:id",
    validateTodoUpdate,
    updateTodo
);
```

Now:

```text
Every Todo route
       ↓
authenticate
```

Then each route adds its own requirements.

For POST:

```text
authenticate
   ↓
validateTodo
   ↓
createTodo
```

For PATCH:

```text
authenticate
   ↓
validateTodoUpdate
   ↓
updateTodo
```

This is composition at the router level.

---

# 31. A Good Rule for Composition

Ask three questions.

### Question 1

> Does every route need this middleware?

If yes:

```js
router.use(middleware);
```

---

### Question 2

> Does only one route need it?

If yes:

```js
router.post(
    "/",
    middleware,
    controller
);
```

---

### Question 3

> Does it depend on another middleware?

Then put the dependency first.

Example:

```text
authenticate
   ↓
requireRole
```

not:

```text
requireRole
   ↓
authenticate
```

There is also a danger.

Don't create:

```text

middleware5
```

# 35. A Practical Rule

For every middleware, ask:

> **"What single reason does this middleware exist?"**

Examples:

```text
requestId
→ identify request

logger
→ record request

authenticate
→ identify user

requireRole
→ check role

validate
→ validate input

rateLimiter
→ limit request frequency
```

If the answer becomes:

> "It does authentication, validation, logging, and database queries..."

you probably need to split it.

# 39. Debugging a Composition

Suppose:

```js
router.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

but the endpoint doesn't work.

Don't immediately stare at `createTodo`.

Trace the pipeline:

```text
Request
 ↓
authenticate
 ↓
validateTodo
 ↓
createTodo
```

Add temporary logs:

```js
console.log("1 - authenticate");
```

then:

```js
console.log("2 - validation");
```

then:

```js
console.log("3 - controller");
```

You can quickly discover where execution stops.

You'll study middleware debugging more deeply in **7.19**.

# 40. A Very Useful Debugging Trick

Give each middleware a visible marker:

```js
const middlewareA = (req, res, next) => {
    console.log("A");
    next();
};
```

```js
const middlewareB = (req, res, next) => {
    console.log("B");
    next();
};
```

```js
const middlewareC = (req, res, next) => {
    console.log("C");
    next();
};
```

If output is:

```text
A
B
```

and never:

```text
C
```

you immediately know:

```text
B
```

is where the pipeline stopped.

Simple, but extremely useful.

# 41. Common Mistake — Calling `next()` Twice

Bad:

```js
const middleware = (req, res, next) => {
    if (req.user) {
        next();
    }

    next();
};
```

If `req.user` exists:

```text
next()
next()
```

The request can behave unpredictably.

Correct:

```js
const middleware = (req, res, next) => {
    if (req.user) {
        return next();
    }

    return res.status(401).json({
        message: "Unauthorized"
    });
};
```

Every path should have a clear outcome.

# 42. Common Mistake — Sending Response and Continuing

Bad:

```js
const auth = (req, res, next) => {
    if (!req.user) {
        res.status(401).json({
            message: "Unauthorized"
        });
    }

    next();
};
```

You sent a response and then continued.

Correct:

```js
const auth = (req, res, next) => {
    if (!req.user) {
        return res.status(401).json({
            message: "Unauthorized"
        });
    }

    next();
};
```

This is one of the common middleware mistakes explicitly called out in your course material.

# 46. Your Final Mental Model

When you see:

```js
router.post(
    "/todos",
    authenticate,
    requireRole("user"),
    validateTodo,
    createTodo
);
```

your brain should translate it into:

```text
POST /todos
     │
     ▼
authenticate
     │
     │ adds req.user
     ▼
requireRole("user")
     │
     │ checks req.user.role
     ▼
validateTodo
     │
     │ checks req.body
     ▼
createTodo
     │
     ▼
response
```

And if anything fails:

```text
Middleware
    │
    └── next(error)
             ↓
       Error middleware
             ↓
          response
```

This is the foundation for the much larger architecture you'll build later:

```text
Request
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Model
 ↓
MongoDB
```

The source explicitly frames this request-to-database path as the mental model to understand rather than simply memorizing folder names.
