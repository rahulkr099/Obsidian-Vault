# Phase 7 — Lesson 7.18

## Common Middleware Mistakes

You've now learned how to:

```text
7.14 → create reusable middleware
7.15 → create middleware factories
7.16 → create conditional middleware
7.17 → compose middleware
```

Now we need to learn something equally important:

> **How middleware goes wrong.**

The Phase 7 plan specifically places **7.18 — Common Middleware Mistakes** after composition and before debugging middleware.

This lesson is important because middleware bugs can be confusing. Sometimes the code looks completely correct, but the request hangs, the response gets sent twice, or the wrong middleware runs.

---

# 1. Mistake #1 — Forgetting `next()`

This is probably the most common beginner mistake.

Consider:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);
};
```

Looks fine, right?

But there's a problem.

You never called:

```js
next();
```

So the request pipeline stops.

```text
Request
   ↓
logger
   ↓
STOP ❌
```

The browser may keep waiting.

---

# 2. Correct Version

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);

    next();
};
```

Now:

```text
Request
   ↓
logger
   ↓
next()
   ↓
next middleware
   ↓
controller
   ↓
response
```

Remember:

> If middleware doesn't send a response or pass control onward, the request may never finish.

---

# 3. When You DON'T Need `next()`

There is an important exception.

If middleware sends the response:

```js
const blocked = (req, res, next) => {
    return res.status(403).json({
        success: false,
        message: "Forbidden"
    });
};
```

you don't call:

```js
next();
```

because the request has already ended.

So:

```text
Middleware
   │
   ├── Continue → next()
   │
   └── Respond → response
```

These are two different paths.

---

# 4. Mistake #2 — Sending a Response and Then Calling `next()`

This is extremely common.

Bad:

```js
const authenticate = (req, res, next) => {
    if (!req.headers.authorization) {
        res.status(401).json({
            success: false,
            message: "Unauthorized"
        });

        next();
    }
};
```

What's wrong?

You already sent:

```text
401 Unauthorized
```

and then you're telling Express:

> "Continue to the next handler."

That can lead to errors such as:

```text
Cannot set headers after they are sent to the client
```

---

# 5. Correct Version

```js
const authenticate = (req, res, next) => {
    if (!req.headers.authorization) {
        return res.status(401).json({
            success: false,
            message: "Unauthorized"
        });
    }

    next();
};
```

The `return` is important.

It means:

```text
Unauthorized
   ↓
response sent
   ↓
STOP middleware
```

---

# 6. The Golden Rule

For every middleware, mentally identify the possible paths:

```text
                Middleware
                    │
          ┌─────────┴─────────┐
          │                   │
      Continue              Respond
          │                   │
        next()             return res...
```

A request should not accidentally take both paths.

---

# 7. Mistake #3 — Calling `next()` Twice

Consider:

```js
const middleware = (req, res, next) => {
    if (req.user) {
        next();
    }

    next();
};
```

If `req.user` exists:

```text
next()
  +
next()
```

The pipeline gets triggered twice.

This is a serious middleware bug.

---

# 8. Correct Version

```js
const middleware = (req, res, next) => {
    if (req.user) {
        return next();
    }

    return res.status(401).json({
        success: false,
        message: "Unauthorized"
    });
};
```

Now every path has exactly one outcome.

```text
User exists
   ↓
next()
```

or:

```text
User doesn't exist
   ↓
401 response
```

---

# 9. Mistake #4 — Wrong Middleware Order

Suppose:

```js
router.get(
    "/admin",
    requireRole("admin"),
    authenticate,
    getAdminDashboard
);
```

Looks reasonable.

But `requireRole()` expects:

```js
req.user
```

Who creates `req.user`?

```text
authenticate
```

But authentication is running **after** authorization.

Wrong:

```text
requireRole
   ↓
authenticate
```

Correct:

```text
authenticate
   ↓
requireRole
```

So:

```js
router.get(
    "/admin",
    authenticate,
    requireRole("admin"),
    getAdminDashboard
);
```

---

# 10. Think in Dependencies

Before putting middleware together, ask:

> **What does this middleware need?**

For example:

```text
logger
→ needs requestId

requireRole
→ needs req.user

validate
→ needs parsed req.body

controller
→ needs everything it expects
```

Therefore:

```text
requestId
   ↓
logger
   ↓
authenticate
   ↓
requireRole
   ↓
validate
   ↓
controller
```

This dependency-based thinking is much better than randomly arranging middleware.

---

# 11. Mistake #5 — Forgetting Body Parsing

Suppose your controller expects:

```js
req.body.title
```

but you forgot:

```js
app.use(express.json());
```

Then a request such as:

```json
{
    "title": "Learn Express"
}
```

may not be available through `req.body` as you expect.

Your pipeline should include:

```text
Request
   ↓
express.json()
   ↓
validation
   ↓
controller
```

The starter's intended `app.js` assembly includes body parsing before routes.

---

# 12. Mistake #6 — Putting Middleware in the Wrong Scope

Suppose every Todo route requires authentication.

You could write:

```js
todoRouter.get(
    "/",
    authenticate,
    getTodos
);

todoRouter.post(
    "/",
    authenticate,
    createTodo
);

todoRouter.patch(
    "/:id",
    authenticate,
    updateTodo
);

todoRouter.delete(
    "/:id",
    authenticate,
    deleteTodo
);
```

This works.

But you're repeating:

```text
authenticate
```

four times.

Instead:

```js
todoRouter.use(authenticate);
```

Then:

```js
todoRouter.get("/", getTodos);
todoRouter.post("/", createTodo);
todoRouter.patch("/:id", updateTodo);
todoRouter.delete("/:id", deleteTodo);
```

Now the architecture says:

> Every Todo route requires authentication.

That's clearer.

---

# 13. But Don't Apply Everything Globally

The opposite mistake is also possible.

Suppose:

```js
app.use(authenticate);
```

Now even:

```text
GET /healthz
```

might require authentication.

That's probably not what you want.

The starter specifically uses health/readiness endpoints as infrastructure endpoints, while protected application routes can require authentication.

A better structure might be:

```js
app.get("/healthz", healthController);

app.use("/api/v1/users", authenticate, userRouter);
app.use("/api/v1/todos", authenticate, todoRouter);
```

---

# 14. Mistake #7 — One Giant Middleware

Bad:

```js
const everything = async (req, res, next) => {
    // logging

    // request ID

    // authentication

    // authorization

    // validation

    // sanitization

    // database query

    // business logic

    // email

    next();
};
```

This becomes difficult to:

- understand
    
- test
    
- reuse
    
- debug
    
- modify
    

Instead:

```text
requestId
   ↓
logger
   ↓
authenticate
   ↓
authorize
   ↓
validate
   ↓
controller
   ↓
service
   ↓
repository
```

Your starter architecture is explicitly designed around separating these responsibilities.

---

# 15. Mistake #8 — Putting Business Logic in Middleware

Consider:

```js
const createTodoMiddleware = async (req, res, next) => {
    const user = await User.findById(req.user.id);

    const todo = await Todo.create({
        title: req.body.title,
        userId: user._id
    });

    await sendEmail(user.email);

    res.status(201).json(todo);
};
```

This is doing far too much.

It is no longer simply middleware.

A cleaner architecture is:

```text
Middleware
    ↓
Controller
    ↓
Service
    ↓
Repository
```

For example:

```text
authenticate
    ↓
validate
    ↓
createTodoController
    ↓
todoService.create()
    ↓
todoRepository.create()
```

This is exactly the layer-building approach in your starter course.

---

# 16. Mistake #9 — Database Queries Inside Simple Middleware

Suppose:

```js
const logger = async (req, res, next) => {
    const user = await User.findById(req.user.id);

    console.log(user);

    next();
};
```

Now your logger has a database dependency.

That's not necessarily _always_ wrong, but it creates unnecessary coupling.

A logger should generally log information already available to it.

For example:

```js
const logger = (req, res, next) => {
    console.log({
        method: req.method,
        path: req.path,
        requestId: req.requestId
    });

    next();
};
```

Keep middleware focused.

---

# 17. Mistake #10 — Trusting `req.user` Without Authentication

Consider:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        if (req.user.role !== role) {
            return res.status(403).json({
                message: "Forbidden"
            });
        }

        next();
    };
};
```

What if:

```js
req.user
```

doesn't exist?

You'll get something like:

```text
Cannot read properties of undefined
```

Better:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (req.user.role !== role) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

And still place:

```text
authenticate
   ↓
requireRole
```

in the route.

---

# 18. Mistake #11 — Mutating `req` Carelessly

It's perfectly normal for middleware to attach useful information:

```js
req.user = user;
req.requestId = requestId;
```

But don't randomly create dozens of properties:

```js
req.a = ...
req.b = ...
req.temp = ...
req.foo = ...
req.data = ...
req.result = ...
```

Your request object can become difficult to understand.

Prefer clear names:

```js
req.user
req.requestId
req.validated
```

and establish conventions for your project.

---

# 19. Mistake #12 — Overwriting Existing Properties

Avoid things like:

```js
req.body = somethingElse;
```

unless you have a very deliberate reason.

You may accidentally destroy information that later middleware or controllers expect.

Instead, consider:

```js
req.validatedBody = validatedData;
```

or another clearly named property.

For example:

```text
req.body
     ↓
raw parsed body

req.validatedBody
     ↓
validated application input
```

This can make the data flow easier to understand.

---

# 20. Mistake #13 — Async Middleware Without Error Handling

This one becomes very important.

Consider:

```js
const middleware = async (req, res, next) => {
    const user = await User.findById(req.user.id);

    req.userData = user;

    next();
};
```

What happens if:

```js
User.findById(...)
```

throws an error?

If you don't handle the rejected promise correctly, the error may not reach your intended error architecture.

This is why your next phase after middleware is **Error Handling & Async Architecture**, including `asyncHandler` and global error middleware.

---

# 21. Safer Async Middleware Pattern

Depending on your Express version and project conventions, you can use an async wrapper or explicit error forwarding.

For example:

```js
const middleware = async (req, res, next) => {
    try {
        const user = await User.findById(req.user.id);

        req.userData = user;

        next();
    } catch (error) {
        next(error);
    }
};
```

The important idea is:

```text
async operation
     ↓
success → next()
failure → next(error)
```

We'll study the complete pattern in Phase 8.

---

# 22. Mistake #14 — Catching an Error and Doing Nothing

Bad:

```js
const middleware = async (req, res, next) => {
    try {
        await something();
        next();
    } catch (error) {
        console.log(error);
    }
};
```

What happens?

The error is logged, but the request may never receive a response.

The pipeline effectively becomes:

```text
middleware
    ↓
ERROR
    ↓
console.log()
    ↓
????
```

Better:

```js
catch (error) {
    next(error);
}
```

Then:

```text
middleware
   ↓
error
   ↓
next(error)
   ↓
global error middleware
   ↓
response
```

---

# 23. Mistake #15 — Mixing Error Responses Everywhere

You might be tempted to do this in every middleware:

```js
return res.status(400).json(...);
```

then another middleware:

```js
return res.status(401).json(...);
```

then another:

```js
return res.status(403).json(...);
```

This can lead to inconsistent error formats.

Your starter architecture intentionally moves toward centralized error handling:

```text
AppError
   ↓
asyncHandler
   ↓
error.middleware
   ↓
consistent response
```

That architecture is introduced in Phase 8.

---

# 24. Mistake #16 — Using `next()` After an Async Response

Consider:

```js
const middleware = async (req, res, next) => {
    if (!req.user) {
        await res.status(401).json({
            message: "Unauthorized"
        });

        next();
    }
};
```

Don't do this.

`res.json()` isn't something you normally need to `await`.

And after sending the response, don't continue.

Use:

```js
if (!req.user) {
    return res.status(401).json({
        message: "Unauthorized"
    });
}
```

---

# 25. Mistake #17 — Assuming `next()` Means "Call the Controller"

This is a subtle misunderstanding.

Suppose:

```js
router.post(
    "/todos",
    middlewareA,
    middlewareB,
    createTodo
);
```

When `middlewareA` calls:

```js
next();
```

it means:

> **Continue to the next handler in the chain.**

It doesn't necessarily mean:

> "Go directly to the controller."

The next handler might be:

```text
middlewareB
```

So:

```text
A
 ↓ next()
B
 ↓ next()
C
 ↓ next()
controller
```

---

# 26. Mistake #18 — Forgetting That Middleware Order Is Local to the Chain

Consider:

```js
app.use(logger);

app.use("/admin", authenticate, adminRouter);

app.use("/public", publicRouter);
```

A request to:

```text
/admin/users
```

might go:

```text
logger
   ↓
authenticate
   ↓
adminRouter
```

But:

```text
/public/about
```

might go:

```text
logger
   ↓
publicRouter
```

Authentication isn't automatically part of every route just because it exists somewhere in `app.js`.

You need to understand **where middleware is mounted**.

---

# 27. Mistake #19 — Using `req.url` Without Understanding Router Mounting

This can confuse beginners.

Suppose:

```js
app.use("/api/v1/todos", todoRouter);
```

Inside the router, Express's request properties can reflect the mounted router/path differently depending on which property you inspect.

For debugging, it's useful to understand:

```js
req.originalUrl
req.baseUrl
req.path
```

For example, conceptually:

```text
originalUrl
→ full original request path

baseUrl
→ router mount path

path
→ path within current routing context
```

Don't memorize this yet; just know that router mounting affects what you see.

---

# 28. Mistake #20 — Conditional Middleware With Too Many Exceptions

Suppose you write:

```js
const middleware = (req, res, next) => {
    if (req.path === "/healthz") return next();
    if (req.path === "/login") return next();
    if (req.path === "/signup") return next();
    if (req.path === "/public") return next();
    if (req.path === "/docs") return next();

    // actual middleware
};
```

At first:

```text
5 exceptions
```

Fine.

Then:

```text
10 exceptions
```

Then:

```text
20 exceptions
```

Now the middleware is becoming a routing system.

Instead, use route structure:

```text
publicRouter
protectedRouter
adminRouter
```

This is cleaner.

---

# 29. Mistake #21 — Using Middleware When a Utility Is Better

Suppose you need:

```js
const normalizeEmail = (email) => {
    return email.trim().toLowerCase();
};
```

You don't need:

```js
(req, res, next)
```

This is a utility.

Don't turn everything into middleware.

Remember:

```text
Middleware
→ HTTP request pipeline

Utility
→ general reusable operation
```

---

# 30. Mistake #22 — Using Middleware When a Service Is Better

Suppose you need:

```text
Register user
```

and the operation involves:

```text
validate
hash password
create user
create refresh token
send email
```

Don't make:

```text
registerMiddleware
```

do everything.

Eventually:

```text
Controller
   ↓
authService.register()
   ↓
repository
```

This is exactly why your learning roadmap separates middleware from controllers, services, and repositories.

# 31. Mistake #23 — Leaking Sensitive Data Through Middleware Logs

Bad:

```js
console.log(req.body);
```

when the body contains:

```json
{
    "email": "user@example.com",
    "password": "SuperSecretPassword"
}
```

Now your password is in logs.

Don't blindly log:

```text
password
accessToken
refreshToken
cookies
authorization headers
API keys
```

Your later observability phase specifically includes **sensitive data in logs** as a dedicated topic.

For now, develop the habit:

> **Never log sensitive authentication data casually.**

# 32. Mistake #24 — Trusting Client-Controlled Headers

Don't do:

```js
if (req.headers["x-role"] === "admin") {
    // allow admin action
}
```

A client can send:

```http
X-Role: admin
```

That doesn't prove the user is an admin.

Authorization should be based on trusted server-side authentication state and authorization rules.

---

# 33. Mistake #25 — Confusing `401` and `403`

A very useful distinction:

### `401 Unauthorized`

Generally means:

> The request isn't authenticated properly.

Example:

```text
No valid authentication
```

### `403 Forbidden`

Generally means:

> The user is authenticated, but doesn't have permission.

Example:

```text
Logged-in student
trying to access admin route
```

So:

```text
No identity
   ↓
401

Identity exists
but insufficient permission
   ↓
403
```

This distinction will become very important in your Authentication and Authorization phases.

---

# 34. Mistake #26 — Authentication and Authorization Mixed Together

Avoid a giant middleware:

```text
authenticateAndAuthorizeEverything
```

Better:

```text
authenticate
   ↓
requireRole("admin")
```

Why?

Because they answer different questions.

### Authentication

> Who are you?

### Authorization

> Are you allowed to do this?

---

# 35. Mistake #27 — Modifying the Response Too Early

Middleware can modify the response:

```js
res.setHeader(...)
```

or similar operations.

But don't accidentally send a response before later middleware has completed if the architecture expects the chain to continue.

Remember:

```text
Middleware can prepare
       ↓
next()
       ↓
later handlers
       ↓
final response
```

Not every middleware should send a response.

---

# 36. Mistake #28 — No Clear Responsibility

Ask:

> "What exactly does this middleware do?"

If your answer is:

```text
"It checks auth, validates the body, logs the user, updates the database, and creates a response."
```

that's a warning sign.

A better design:

```text
requestId
→ request identity

logger
→ logging

authenticate
→ identity

authorize
→ permissions

validate
→ input

controller
→ HTTP translation

service
→ business logic

repository
→ database access
```

# 37. A Bad Pipeline

Let's look at a deliberately bad example:

```js
router.post(
    "/todos",
    async (req, res, next) => {
        console.log(req.body);

        if (!req.headers.authorization) {
            res.status(401).json({
                message: "Unauthorized"
            });
            next();
        }

        const user = await User.findById(...);

        if (user.role !== "admin") {
            res.status(403).json({
                message: "Forbidden"
            });
            next();
        }

        const todo = await Todo.create(req.body);

        res.status(201).json(todo);
    }
);
```

This has many problems:

```text
❌ logging sensitive body
❌ authentication
❌ authorization
❌ database access
❌ business logic
❌ response handling
❌ no proper async error handling
❌ potentially calling next() after response
❌ validation missing
❌ everything in one function
```

---

# 38. Refactor It

A better architecture:

```js
router.post(
    "/todos",
    authenticate,
    requireRole("admin"),
    validateTodo,
    createTodo
);
```

Now:

```text
Request
   ↓
authenticate
   ↓
requireRole("admin")
   ↓
validateTodo
   ↓
createTodo
```

And eventually:

```text
createTodo controller
   ↓
todoService.create()
   ↓
todoRepository.create()
   ↓
MongoDB
```

Much easier to understand.

# 39. The Middleware Checklist

Whenever you create middleware, ask these questions:

### 1. Does it have one clear responsibility?

```text
YES / NO
```

### 2. Does it either:

```text
next()
```

or:

```text
send response
```

appropriately?

### 3. Can it accidentally call `next()` twice?

### 4. Does it depend on another middleware?

### 5. Is the dependency placed before it?

### 6. Does it need to be global?

### 7. Should it be router-level?

### 8. Should it be route-level?

### 9. Does it perform business logic?

If yes, reconsider.

### 10. Does it perform database operations?

If yes, ask whether that responsibility belongs there.

### 11. Does it handle async errors correctly?

### 12. Does it log sensitive information?

### 13. Does it trust client-controlled data for security?

### 14. Does it send a response and then continue?

If yes, that's probably a bug.

# 40. A Healthy Middleware

Here's a simple example:

```js
const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    next();
};
```

Why is this good?

```text
One responsibility
       ↓
Create request ID

Adds useful request information
       ↓
req.requestId

Passes control onward
       ↓
next()
```

Simple.

---

# 41. A Healthy Authentication Middleware

Conceptually:

```js
const authenticate = (req, res, next) => {
    const token = getToken(req);

    if (!token) {
        return res.status(401).json({
            success: false,
            message: "Authentication required"
        });
    }

    const user = verifyToken(token);

    req.user = user;

    next();
};
```

Its responsibility is:

```text
Authentication
```

Not:

```text
Create Todo
Send Email
Update Database
```

---

# 42. A Healthy Authorization Factory

From 7.15:

```js
const requireRole = (role) => {
    return (req, res, next) => {
        if (!req.user) {
            return res.status(401).json({
                success: false,
                message: "Authentication required"
            });
        }

        if (req.user.role !== role) {
            return res.status(403).json({
                success: false,
                message: "Forbidden"
            });
        }

        next();
    };
};
```

Responsibility:

```text
Authorization
```

It doesn't need to authenticate the user again.

# 43. A Healthy Validation Middleware

Conceptually:

```js
const validate = (schema) => {
    return (req, res, next) => {
        const { error, value } = schema.validate(
            req.body
        );

        if (error) {
            return res.status(400).json({
                success: false,
                message: "Validation failed"
            });
        }

        req.validatedBody = value;

        next();
    };
};
```

Responsibility:

```text
Input validation
```

Not:

```text
Create database record
```

# 45. Debugging Exercise

Here's a broken middleware:

```js
const checkUser = (req, res, next) => {
    if (!req.user) {
        res.status(401).json({
            message: "Unauthorized"
        });
    }

    console.log("User exists");

    next();
};
```

Find the problem.

### Answer

If there is no user:

```text
401 response
   ↓
console.log()
   ↓
next()
```

That's wrong.

Correct:

```js
const checkUser = (req, res, next) => {
    if (!req.user) {
        return res.status(401).json({
            message: "Unauthorized"
        });
    }

    console.log("User exists");

    next();
};
```

# 46. Debugging Exercise #2

What's wrong here?

```js
const middleware = (req, res, next) => {
    if (req.method === "GET") {
        next();
    }

    console.log("Not GET");

    next();
};
```

For a GET request:

```text
next()
   +
next()
```

Correct:

```js
const middleware = (req, res, next) => {
    if (req.method === "GET") {
        return next();
    }

    console.log("Not GET");

    next();
};
```

This is exactly why `return next()` is so common in conditional middleware.

# 47. Debugging Exercise #3

What's wrong?

```js
router.get(
    "/admin",
    requireRole("admin"),
    authenticate,
    controller
);
```

Answer:

```text
requireRole
   ↓
needs req.user

authenticate
   ↓
creates req.user
```

Wrong order.

Correct:

```js
router.get(
    "/admin",
    authenticate,
    requireRole("admin"),
    controller
);
```

# 48. Debugging Exercise #4

What's wrong?

```js
const logger = async (req, res, next) => {
    try {
        await saveLog(req);

        next();
    } catch (error) {
        console.error(error);
    }
};
```

The error is swallowed.

Better:

```js
catch (error) {
    next(error);
}
```

Then your global error handling system can deal with it.

This leads directly into Phase 8.

# 49. The 5 Rules I Want You to Memorize

You don't need to memorize 30 mistakes.

Remember these five rules:

### Rule 1

> **Every middleware must either continue the pipeline or end the request.**

### Rule 2

> **Never send a response and then call `next()`.**

### Rule 3

> **Middleware order must respect dependencies.**

### Rule 4

> **Keep middleware focused on request/response concerns.**

### Rule 5

> **If middleware becomes complicated, question whether the logic belongs in another layer.**

These five rules will prevent a huge number of backend problems.

# 53. The Mental Model

Whenever you write middleware, imagine this:

```text
                  REQUEST
                     │
                     ▼
              ┌──────────────┐
              │  Middleware  │
              └──────┬───────┘
                     │
             What should happen?
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
      next()      next(error)   response
        │            │            │
        ▼            ▼            ▼
     continue     error flow    STOP
```

And never accidentally do:

```text
response
   +
next()
```

or:

```text
next()
   +
next()
```

Those two patterns alone will save you from many confusing bugs.
