# Phase 7 — Lesson 7.19

## Debugging Middleware

In **7.18**, you learned the common ways middleware breaks.

Now we're going to learn something even more practical:

> **How do you find exactly where the middleware pipeline is breaking?**

The Phase 7 roadmap puts **7.19 — Debugging Middleware** immediately before the final **7.20 — Build a reusable middleware system**.

By the end of this lesson, if a request gets stuck here:

```text
Request
 ↓
middleware A
 ↓
middleware B
 ↓
?????
 ↓
controller
```

you should be able to find the `?????` yourself.

---

# 1. The First Rule of Middleware Debugging

When a request doesn't behave correctly, **don't immediately inspect the controller**.

First trace the request:

```text
Request
   ↓
Route
   ↓
Middleware 1
   ↓
Middleware 2
   ↓
Middleware 3
   ↓
Controller
```

Your first question should be:

> **"How far did the request actually travel?"**

This simple question solves a lot of Express problems.

---

# 2. The Simplest Debugging Technique

Add a log before and after important operations.

For example:

```js
const auth = (req, res, next) => {
    console.log("AUTH: started");

    // authentication logic

    console.log("AUTH: finished");

    next();
};
```

Now you can see:

```text
AUTH: started
AUTH: finished
```

If you only see:

```text
AUTH: started
```

you know the problem happened somewhere between those two points.

---

# 3. Number Your Middleware

Suppose you have:

```js
app.use(requestId);
app.use(logger);
app.use(authenticate);
app.use(validate);
```

Temporarily add:

```js
console.log("1 - requestId");
```

```js
console.log("2 - logger");
```

```js
console.log("3 - authenticate");
```

```js
console.log("4 - validate");
```

Then make a request.

If you see:

```text
1 - requestId
2 - logger
3 - authenticate
```

but not:

```text
4 - validate
```

you've already narrowed down the problem.

---

# 4. Debugging the Full Request Flow

Suppose:

```js
router.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

Add temporary logs:

```js
const authenticate = (req, res, next) => {
    console.log("1. authenticate");

    // ...

    next();
};
```

```js
const validateTodo = (req, res, next) => {
    console.log("2. validateTodo");

    // ...

    next();
};
```

```js
const createTodo = (req, res) => {
    console.log("3. createTodo");

    // ...
};
```

Expected:

```text
1. authenticate
2. validateTodo
3. createTodo
```

If you get:

```text
1. authenticate
```

and then nothing:

```text
authenticate
    ↓
?????
```

you know authentication is not reaching the next stage.

---

# 5. The Most Common Symptom: Request Hangs

Imagine your browser keeps loading:

```text
POST /todos
Loading...
```

and never receives a response.

One of the first things to check is:

> **Did some middleware forget to call `next()`?**

For example:

```js
const logger = (req, res, next) => {
    console.log("Request received");

    // forgot next()
};
```

Flow:

```text
Request
   ↓
logger
   ↓
STOP ❌
```

The request can remain pending.

---

# 6. How to Confirm a Missing `next()`

Add logs:

```js
const logger = (req, res, next) => {
    console.log("logger started");

    console.log("logger finished");

    next();
};
```

If you see:

```text
logger started
logger finished
```

but the next middleware doesn't run, check whether:

```js
next();
```

is actually executed.

---

# 7. Debugging Conditional Middleware

This is especially important after 7.16.

Consider:

```js
const debugMiddleware = (req, res, next) => {
    if (req.method === "GET") {
        return next();
    }

    console.log("Debugging request");

    next();
};
```

If you expect:

```text
Debugging request
```

but don't see it for:

```text
GET /todos
```

that's not necessarily a bug.

Your condition says:

```text
GET
 ↓
skip
 ↓
next()
```

So debugging conditional middleware means checking **the condition first**.

---

# 8. Log the Condition

Instead of:

```js
if (req.method === "GET") {
    return next();
}
```

temporarily do:

```js
console.log("Method:", req.method);

if (req.method === "GET") {
    console.log("Skipping middleware");
    return next();
}
```

Now you might see:

```text
Method: GET
Skipping middleware
```

You immediately understand what's happening.

---

# 9. Debugging `req`

A huge part of backend debugging is inspecting the request.

For example:

```js
console.log(req.method);
console.log(req.url);
console.log(req.params);
console.log(req.query);
console.log(req.body);
```

You might see:

```text
POST
/api/v1/todos
{}
{}
{ title: "Learn Express" }
```

This tells you what Express actually received.

---

# 10. Inspect `req.user`

When debugging authentication:

```js
console.log("req.user:", req.user);
```

You might expect:

```js
{
    id: "123",
    role: "admin"
}
```

but instead get:

```text
req.user: undefined
```

Now you know:

> The problem is before authorization.

Your flow is probably:

```text
authenticate
    ↓
req.user
    ↓
requireRole
```

If `req.user` is missing, investigate `authenticate`.

---

# 11. Debugging `req.body`

If your validation is failing unexpectedly:

```js
console.log("BODY:", req.body);
```

You might expect:

```json
{
  "title": "Learn Express"
}
```

but receive:

```text
BODY: undefined
```

or:

```text
BODY: {}
```

Then check whether:

```js
app.use(express.json());
```

is registered before the route.

The expected flow is:

```text
Request
 ↓
express.json()
 ↓
req.body
 ↓
validation
 ↓
controller
```

---

# 12. Debugging `req.params`

For:

```text
GET /todos/123
```

and route:

```js
router.get("/todos/:id", controller);
```

check:

```js
console.log(req.params);
```

Expected:

```js
{
    id: "123"
}
```

If you get:

```js
{}
```

check the route definition.

Maybe you accidentally wrote:

```js
router.get("/todos", controller);
```

instead of:

```js
router.get("/todos/:id", controller);
```

---

# 13. Debugging `req.query`

For:

```text
GET /todos?page=2&limit=20
```

check:

```js
console.log(req.query);
```

You should see something conceptually like:

```js
{
    page: "2",
    limit: "20"
}
```

This becomes especially useful later when you build pagination and filtering.

---

# 14. Inspect the Whole Request Carefully

You can temporarily use:

```js
console.log({
    method: req.method,
    url: req.originalUrl,
    params: req.params,
    query: req.query,
    body: req.body,
    user: req.user
});
```

This gives you a useful snapshot.

But **don't blindly log everything in production**.

Never casually log:

```text
password
access token
refresh token
authorization header
cookies
API keys
```

Your later observability lessons explicitly include sensitive data in logs.

---

# 15. Debugging `next()`

You can't directly inspect `next()` like a normal variable, but you can log immediately before it:

```js
const auth = (req, res, next) => {
    console.log("AUTH: before next");

    next();

    console.log("AUTH: after next");
};
```

You might see:

```text
AUTH: before next
CONTROLLER
AUTH: after next
```

This can initially look strange.

Why?

Because `next()` transfers execution into the next handler, and the call stack can return later.

---

# 16. Understanding This Important Behavior

Consider:

```js
const first = (req, res, next) => {
    console.log("A - before");

    next();

    console.log("A - after");
};
```

And:

```js
const second = (req, res, next) => {
    console.log("B - before");

    next();

    console.log("B - after");
};
```

Output can be:

```text
A - before
B - before
B - after
A - after
```

Why?

Because middleware execution behaves like nested function calls.

Conceptually:

```text
A starts
 ↓
next()
 ↓
B starts
 ↓
next()
 ↓
next handler
 ↓
B resumes
 ↓
A resumes
```

This is a very useful debugging concept.

---

# 17. Visualizing the Call Stack

Think:

```text
A
│
├── before
│
└── next()
      │
      ▼
      B
      │
      ├── before
      │
      └── next()
            │
            ▼
         Controller
            │
            ▼
         B after
            │
            ▼
         A after
```

So middleware isn't simply:

```text
A completely finishes
 ↓
B starts
```

It's more like a chain of nested calls.

This becomes especially important when middleware modifies the response **after** `next()`.

---

# 18. A Very Useful Logging Pattern

For debugging middleware order:

```js
const middleware = (name) => {
    return (req, res, next) => {
        console.log(`[${name}] before`);

        next();

        console.log(`[${name}] after`);
    };
};
```

Then:

```js
app.use(middleware("A"));
app.use(middleware("B"));
app.use(middleware("C"));
```

You may see:

```text
[A] before
[B] before
[C] before
[C] after
[B] after
[A] after
```

This is a powerful way to visualize the middleware stack.

---

# 19. Don't Leave This Debug Logging Forever

This is important.

Temporary:

```js
console.log("AUTH START");
```

is useful.

But don't permanently fill production code with:

```js
console.log("A");
console.log("B");
console.log("C");
console.log("D");
```

Later you'll use structured logging.

Your starter's observability phase eventually introduces request IDs, structured logs, log levels, and production logging.

For now:

> Use simple logs to understand the pipeline.


but your logger expects:

```js
req.requestId
```

Then:

```text

 ↓

```

is wrong.

Your logger might print:



Now:


Suppose:

```js
app.use("/api/v1/todos", todoRouter);
```

and inside:

```js
todoRouter.get("/", controller);
```

The final endpoint is:

```text
GET /api/v1/todos
```

Not:

If your request returns:

# 22. Debugging 404 Errors

A `404` can come from several places.

Maybe:

```text
Wrong URL
```

or:

```text
Wrong HTTP method
```

or:

```text
Router wasn't mounted
```

or:

```text
Route path is wrong
```

or:

```text
A previous router didn't match
```

Start by checking:

```text
1. HTTP method
2. URL
3. router mount path
4. route path
5. route registration
```

---

# 23. Example: Finding a 404

You send:

```text
POST /api/v1/todos
```

Your app has:

```js
app.use("/api/v1/todo", todoRouter);
```

Notice:

```text
todos
```

vs:

```text
todo
```

The route you're requesting doesn't match the mounted router.

Debugging isn't always about middleware code.

Sometimes the pipeline was never reached.

# 24. Debugging 401 Errors

Suppose:

```text
GET /api/v1/profile
```

returns:

```json
{
  "success": false,
  "message": "Authentication required"
}
```

Don't immediately modify the controller.

Trace:

```text
Request
 ↓
authenticate
 ↓
?
```

Check:

```js
console.log(
    "Authorization:",
    req.headers.authorization
);
```

Then:

```js
console.log(
    "User:",
    req.user
);
```

Possible result:

```text
Authorization: undefined
User: undefined
```

Now the issue is probably the authentication input.

---

# 25. Debugging 403 Errors

Suppose:

```text
User is logged in
```

but:

```text
DELETE /admin/users/123
```

returns:

```text
403 Forbidden
```

Check:

```js
console.log("Authenticated user:", req.user);
```

Maybe:

```js
{
    id: "123",
    role: "user"
}
```

while:

```js
requireRole("admin")
```

expects:

```text
admin
```

Now the pipeline is working correctly.

The request is being rejected intentionally.

That's an important debugging distinction:

> **Not every error means your code is broken. Sometimes the middleware is correctly rejecting the request.**

---

# 26. Debugging 500 Errors

A `500` means something unexpected happened on the server.

Trace:

```text
Request
 ↓
middleware
 ↓
controller
 ↓
service
 ↓
repository
 ↓
error
```

If your middleware logs:

```text
AUTH OK
VALIDATION OK
CONTROLLER START
```

but you never see:

```text
CONTROLLER END
```

the problem may be inside the controller.

If you see:

```text
SERVICE START
```

but not:

```text
SERVICE END
```

look at the service.

This is essentially **binary searching your request pipeline**.

---

# 27. Binary-Search Your Pipeline

Suppose you have:

```text
A
B
C
D
E
F
G
H
```

and something fails.

Don't inspect all eight immediately.

Add logs around groups:

```text
A
B
C
D
   ↓
checkpoint 1

E
F
G
H
   ↓
checkpoint 2
```

If:

```text
checkpoint 1
```

appears but:

```text
checkpoint 2
```

doesn't, you've reduced the problem to:

```text
E–H
```

Then narrow it down.

This is a general debugging technique that becomes very useful as your backend grows.

---

# 28. Create a Request Trace

For learning, create:

```js
const trace = (name) => {
    return (req, res, next) => {
        console.log(
            `[TRACE] ${name} → ${req.method} ${req.originalUrl}`
        );

        next();
    };
};
```

Then:

```js
app.use(trace("requestId"));
app.use(trace("logger"));
app.use(trace("auth"));
```

You might get:

```text
[TRACE] requestId → POST /api/v1/todos
[TRACE] logger → POST /api/v1/todos
[TRACE] auth → POST /api/v1/todos
```

This makes the pipeline visible.

---

# 29. Better: Include a Request ID

Earlier you learned about `requestId`.

Combine them:

```js
const trace = (name) => {
    return (req, res, next) => {
        console.log({
            requestId: req.requestId,
            middleware: name,
            method: req.method,
            path: req.originalUrl
        });

        next();
    };
};
```

Now:

```text
requestId: abc123
middleware: auth
```

You can follow the same request across multiple logs.

This is one reason request IDs are so useful in real backend systems. Your starter specifically includes request ID handling as part of its middleware/observability architecture.

# 30. Debugging `res`

You can inspect some response state.

For example:

```js
console.log(res.statusCode);
```

At different points you might see:

```text
200
```

or:

```text
401
```

or:

```text
500
```

You can also inspect whether headers have already been sent:

```js
console.log(res.headersSent);
```

This is extremely useful for diagnosing:

```text
Cannot set headers after they are sent
```

---

# 31. `res.headersSent`

Suppose:

```js
if (!req.user) {
    res.status(401).json({
        message: "Unauthorized"
    });
}

console.log(res.headersSent);
```

After the response is sent, you may see:

```text
true
```

If your code then attempts another response:

```js
res.status(200).json(...)
```

you have a problem.

So:

```js
if (!req.user) {
    return res.status(401).json({
        message: "Unauthorized"
    });
}
```

prevents execution from continuing.

---

# 32. Debugging Double Responses

A classic error:

```text
Error: Cannot set headers after they are sent to the client
```

Think:

> **"Did this request attempt to send more than one response?"**

Search for:

```js
res.json(...)
res.send(...)
res.end(...)
res.status(...).json(...)
```

Then check whether execution continues afterward.

Common bug:

```js
if (!user) {
    res.status(401).json({
        message: "Unauthorized"
    });
}

res.json({
    user
});
```

Possible flow:

```text
401 response
   ↓
200 response ❌
```

Correct:

```js
if (!user) {
    return res.status(401).json({
        message: "Unauthorized"
    });
}

return res.json({
    user
});
```

---

# 33. Debugging `next(error)`

Suppose:

```js
const middleware = async (req, res, next) => {
    try {
        await something();
        next();
    } catch (error) {
        console.log("Middleware error:", error);
        next(error);
    }
};
```

Now trace:

```text
Middleware starts
      ↓
async operation
      ↓
ERROR
      ↓
catch
      ↓
next(error)
      ↓
error middleware
```

If the error middleware isn't running, check whether:

```js
next(error);
```

is actually being called.

---

# 34. Debugging Error Middleware

Your error middleware has a special signature:

```js
(err, req, res, next)
```

For debugging:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error("ERROR MIDDLEWARE:", err);

    // response
};
```

If you never see:

```text
ERROR MIDDLEWARE:
```

then the error probably isn't reaching the error handler.

The intended architecture in your starter is:

```text
Controller
   ↓
asyncHandler
   ↓
next(error)
   ↓
error.middleware
   ↓
JSON response
```

---

# 35. Debugging Async Middleware

Consider:

```js
const auth = async (req, res, next) => {
    console.log("AUTH START");

    const user = await findUser();

    console.log("AUTH USER:", user);

    req.user = user;

    next();
};
```

If you see:

```text
AUTH START
```

but not:

```text
AUTH USER:
```

then the problem is likely inside:

```js
await findUser();
```

Possible causes:

```text
database error
promise rejection
connection problem
query problem
```

You have now narrowed the problem significantly.

---

# 36. Add `try/catch` While Debugging

Temporarily:

```js
const auth = async (req, res, next) => {
    try {
        console.log("AUTH START");

        const user = await findUser();

        console.log("AUTH USER:", user);

        req.user = user;

        next();
    } catch (error) {
        console.error("AUTH ERROR:", error);

        next(error);
    }
};
```

Now you can see the actual failure.

Later, your `asyncHandler` abstraction will reduce this repetitive `try/catch` pattern.

# 37. Debugging Route Registration

Sometimes the middleware isn't the problem.

You might have:

```js
router.post(
    "/todos",
    authenticate,
    createTodo
);
```

but the router itself isn't mounted:

```js
// missing:
app.use("/api/v1", router);
```

Then your middleware never executes.

A simple log during startup can help:

```js
console.log("Todo router loaded");
```

Or:

```js
console.log("Registering todo routes");
```

This tells you whether your route module is even being imported.

with `app.js` assembling Express and `server.js` starting the application.

For example:

```text

Express app initialized

```

That gives you confidence the application booted correctly.

# 42. Debugging CORS vs Middleware

Suppose your frontend shows:

```text
CORS error
```

Don't automatically assume:

```text
your route is broken
```

The browser may block the request before your application behaves as expected.

A useful debugging step is to test the endpoint directly with:

```bash
curl
```

If:

```text
curl → works
browser → CORS error
```

then your business route may be fine and the problem is likely around browser-origin handling.

Your starter's security layer later covers CORS and origin checking.

# 45. The "Before / After" Technique

For complicated middleware:

```js
console.log("AUTH BEFORE");

await something();

console.log("AUTH AFTER");
```

This tells you whether the async operation completed.

For synchronous logic:

```js
console.log("BEFORE CHECK");

if (!valid) {
    return res.status(400).json(...);
}

console.log("AFTER CHECK");
```

If you see:

```text
BEFORE CHECK
```

but not:

```text
AFTER CHECK
```

the request took the rejection path.

# 46. Debugging Conditions

Suppose:

```js
if (req.user.role !== "admin") {
    return res.status(403).json(...);
}
```

Don't guess.

Print:

```js
console.log({
    actualRole: req.user?.role,
    requiredRole: "admin"
});
```

You may discover:

```text
actualRole: "ADMIN"
requiredRole: "admin"
```

Now the problem is obvious:


# 52. Build a Reusable Debug Middleware

Let's create a useful learning tool:

```js
const debugMiddleware = (name) => {
    return (req, res, next) => {
        const start = Date.now();

        console.log(
            `[${name}] START`,
            req.method,
            req.originalUrl
        );

        next();

        const duration = Date.now() - start;

        console.log(
            `[${name}] END`,
            `${duration}ms`
        );
    };
};
```

Use:

```js
app.use(debugMiddleware("GLOBAL"));
```

Then:

```text
[GLOBAL] START POST /api/v1/todos
...
[GLOBAL] END 35ms
```

This teaches you the idea of timing middleware.

Later, you'll build proper request logging and observability around this concept.

---

# 53. One Important Warning About Timing

This:

```js
next();

const duration = Date.now() - start;
```

can be useful for understanding middleware nesting, but it isn't automatically the best way to measure the **entire HTTP response duration**.

If you want to measure the complete request lifecycle, you usually listen for response lifecycle events such as:

```js
res.on("finish", ...)
```

For example:

```js
const requestTimer = (req, res, next) => {
    const start = Date.now();

    res.on("finish", () => {
        const duration = Date.now() - start;

        console.log({
            method: req.method,
            url: req.originalUrl,
            status: res.statusCode,
            duration
        });
    });

    next();
};
```

Now the timing represents the response finishing, not merely the middleware chain reaching the next handler.

That's a useful step toward real observability.

# 54. Debugging Should Not Change Application Behavior

A good debugging log:

```js
console.log("AUTH:", req.user);
```

shouldn't change the logic.

A bad debugging change:

```js
if (debug) {
    return next();
}
```

might change behavior.

While debugging, be careful not to "fix" the symptom by accidentally bypassing the middleware.

For example, don't temporarily do:

```js
// next(); // let's see if controller works
```

without understanding the consequences.

# 63. The Most Important Debugging Principle

Don't ask:

> "Why isn't my backend working?"

That's too broad.

> **"What is the last thing I know definitely happened?"**

For example:

```text

I know req.user was created.
I know authenticate called next().
I know validation started.
I don't see controller reached.
```

```text

   ↓
controller
```

That's debugging.
