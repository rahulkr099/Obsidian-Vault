# Phase 7 — Lesson 7.2

## Why Does Express Need Middleware?

In **7.1**, we learned:

> Middleware is a function that runs between the incoming request and the final response.

Now let's answer the more important question:

> **Why do we need middleware at all?**

Because without middleware, your controllers/routes would become **huge, repetitive, and difficult to maintain**.

---

# 1. Imagine a Backend Without Middleware

Suppose you have these endpoints:

```text
GET    /todos
GET    /todos/:id
POST   /todos
PUT    /todos/:id
DELETE /todos/:id
```

Every protected endpoint needs to check:

```text
Is the user logged in?
Is the token valid?
Is the user allowed?
Is the input valid?
Should we rate-limit this request?
Should we log it?
```

Without middleware, you might write:

```js
app.post("/todos", async (req, res) => {
    // check token

    // verify token

    // find user

    // check permission

    // validate body

    // business logic

    // database operation

    // send response
});
```

Then another route:

```js
app.put("/todos/:id", async (req, res) => {
    // check token

    // verify token

    // find user

    // check permission

    // validate body

    // business logic

    // database operation

    // send response
});
```

And another:

```js
app.delete("/todos/:id", async (req, res) => {
    // check token

    // verify token

    // find user

    // check permission

    // validate body

    // business logic

    // database operation

    // send response
});
```

See the problem?

We're repeating the same code.

---

# 2. The Problem Is Not Just Repetition

There are actually **four major problems**.

### Problem 1 — Repeated code

You may need authentication in 20 routes.

Without middleware:

```text
Route 1 → authentication code
Route 2 → authentication code
Route 3 → authentication code
Route 4 → authentication code
...
```

With middleware:

```text
authenticateUser()
       ↓
many routes
```

---

### Problem 2 — Difficult maintenance

Suppose you discover a security problem in your authentication logic.

Without middleware:

```text
20 routes
 ↓
20 places to fix
```

With middleware:

```text
authenticateUser()
       ↓
one place to fix
```

This is a huge reason middleware exists.

---

# 3. Separation of Responsibilities

Suppose your route is:

```http
POST /api/v1/todos
```

Its actual job is to eventually create a Todo.

It shouldn't also be responsible for:

```text
JWT verification
Rate limiting
Input validation
Logging
CORS
Request IDs
```

These are **different responsibilities**.

So we separate them:

```text
Request
   ↓
Authentication
   ↓
Validation
   ↓
Controller
   ↓
Service
```

Each part has a specific job.

---

# 4. Middleware Gives Us a Pipeline

This is one of the most important concepts in Express.

Think of middleware as a **pipeline**.

```text
Request
   │
   ▼
Middleware 1
   │
   ▼
Middleware 2
   │
   ▼
Middleware 3
   │
   ▼
Controller
   │
   ▼
Response
```

For example:

```text
POST /todos
     │
     ▼
requestId
     │
     ▼
logger
     │
     ▼
authenticate
     │
     ▼
validateTodo
     │
     ▼
createTodoController
```

Each stage performs one job.

---

# 5. A Real-World Example

Think about a bank.

You want to withdraw money.

You don't simply walk to the cash machine and take money.

There are several checks:

```text
Customer
   ↓
Identity check
   ↓
Account check
   ↓
Permission check
   ↓
Transaction validation
   ↓
Withdraw money
```

Backend requests work similarly:

```text
Client
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Business operation
```

Middleware allows us to create these checkpoints.

---

# 6. Middleware Makes Code Reusable

Suppose we create:

```js
const authenticate = (req, res, next) => {
    // authentication logic

    next();
};
```

Now we can reuse it:

```js
app.get("/profile", authenticate, profileController);

app.get("/todos", authenticate, todoController);

app.post("/todos", authenticate, createTodoController);

app.delete("/todos/:id", authenticate, deleteTodoController);
```

One middleware.

Many routes.

```text
             ┌── /profile
             │
authenticate ├── /todos
             │
             ├── /todos/:id
             │
             └── /settings
```

That's much cleaner.

---

# 7. Middleware Can Be Global

Some middleware should run for almost every request.

For example:

```js
app.use(express.json());
```

Now:

```text
POST /users
POST /todos
PUT /todos/123
PATCH /profile
```

can all use JSON request bodies.

Similarly:

```js
app.use(logger);
```

means the logger runs for requests passing through that point in the application.

Conceptually:

```text
                 REQUEST
                    │
                    ▼
               ┌─────────┐
               │ logger  │
               └────┬────┘
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       /users    /todos    /profile
```

We'll study **global vs route-level middleware** in Lessons 7.8 and 7.9.

---

# 8. Middleware Can Protect Routes

Consider:

```js
app.get("/public", publicController);
```

Anyone can access it.

But:

```js
app.get(
    "/profile",
    authenticate,
    profileController
);
```

Now the request must pass:

```text
authenticate
```

before reaching the controller.

```text
GET /profile
       ↓
authenticate
       │
       ├── invalid → 401
       │
       └── valid
            ↓
       controller
```

This is much better than putting authentication code inside every controller.

---

# 9. Middleware Can Reject Requests Early

Suppose the user sends:

```http
POST /todos
```

but the request body is invalid:

```json
{
    "title": ""
}
```

Instead of allowing it to reach the controller:

```text
Request
   ↓
Validation middleware
   ↓
❌ Invalid
   ↓
400 Response
```

The controller never runs.

That's useful because invalid requests are stopped as early as possible.

---

# 10. Middleware Can Add Information

Imagine authentication succeeds.

The authentication middleware can do:

```js
req.user = {
    id: "123",
    role: "user"
};
```

Then the controller receives:

```js
app.get("/profile", authenticate, (req, res) => {
    console.log(req.user.id);
});
```

The information flows through the request:

```text
Request
   ↓
authenticate
   ↓
req.user added
   ↓
controller
   ↓
req.user available
```

This is a very powerful pattern.

---

# 11. Middleware Prevents Fat Controllers

This is extremely important for the architecture you're learning.

Imagine this controller:

```js
const createTodo = async (req, res) => {
    // authenticate user

    // validate body

    // check rate limit

    // sanitize input

    // check permissions

    // create todo

    // log action

    // send response
};
```

That's a **fat controller**.

Instead:

```text
Request
   ↓
rateLimiter
   ↓
authenticate
   ↓
validate
   ↓
controller
   ↓
service
   ↓
repository
```

Now the controller can stay small:

```js
const createTodo = async (req, res) => {
    const todo = await todoService.create(
        req.user.id,
        req.body
    );

    res.status(201).json({
        success: true,
        data: todo
    });
};
```

This is the direction we're heading toward in your starter architecture.

---

# 12. Middleware Is Not Business Logic

This distinction will save you a lot of confusion later.

Suppose you're creating a Todo.

### Middleware

Can check:

```text
Is user authenticated?
Is body valid?
Is request allowed?
```

### Service

Should decide:

```text
Can this Todo be created?
What business rules apply?
What should happen?
```

### Repository

Should handle:

```text
How do we save the Todo?
```

So:

```text
Middleware
    ↓
Request processing

Controller
    ↓
HTTP handling

Service
    ↓
Business logic

Repository
    ↓
Database access
```

This separation is the foundation of your Phase 7+ architecture.

---

# 13. Middleware Creates "Cross-Cutting Concerns"

You will hear this term often in backend development.

A **cross-cutting concern** is something that affects many different parts of your application.

Examples:

```text
Logging
Authentication
Authorization
Rate limiting
Security headers
Request IDs
Error handling
```

For example, logging may apply to:

```text
/users
/todos
/orders
/payments
/comments
/profile
```

Instead of implementing logging inside every route, middleware gives us a central place.

```text
                 Logger
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
     Users       Todos       Orders
```

---

# 14. Middleware Also Controls Order

This is very important.

Suppose:

```js
app.use(authenticate);
app.use("/todos", todoRoutes);
```

Then authentication runs before the Todo routes.

But if you write:

```js
app.use("/todos", todoRoutes);
app.use(authenticate);
```

the Todo routes may already have processed the request before authentication middleware gets a chance to run.

So:

> **Middleware order matters.**

Think of it like a physical pipeline:

```text
A → B → C → D
```

You can't expect `C` to happen before `A`.

We'll study this deeply in **Lesson 7.6**.

---

# 15. Middleware Is a Form of Composition

Instead of creating one giant function:

```js
handleEverything()
```

we compose smaller functions:

```js
requestId
logger
authenticate
validate
controller
```

So:

```text
Big problem
     ↓
small functions
     ↓
compose together
     ↓
complete request pipeline
```

This is one of the biggest ideas behind Express.

---

# 16. Compare the Two Approaches

## Without Middleware

```text
                    Controller
                        │
        ┌───────────────┼────────────────┐
        │               │                │
   Authentication   Validation       Logging
        │               │                │
        └───────────────┼────────────────┘
                        │
                   Business Logic
                        │
                    Database
```

The controller becomes responsible for everything.

---

## With Middleware

```text
Request
  │
  ▼
Authentication
  │
  ▼
Validation
  │
  ▼
Logging
  │
  ▼
Controller
  │
  ▼
Service
  │
  ▼
Repository
  │
  ▼
Database
```

Much cleaner.

# 17. How This Connects to Your Starter

Your starter architecture has several middleware responsibilities.

Conceptually:

```text
middlewares/
│
├── auth.middleware.js
├── role.middleware.js
├── logger.middleware.js
├── requestId.middleware.js
│
└── security/
    ├── rateLimiter
    ├── sanitize
    ├── validation
    └── security-related middleware
```

Don't worry about understanding all of them yet.

We're going to **build the understanding one piece at a time**.

---

# 18. The Golden Rule

When you're wondering:

> "Should this be middleware?"

Ask:

### Question 1

Does it need to happen **before the controller**?

### Question 2

Does it apply to **multiple routes**?

### Question 3

Can it independently decide:

```text
Continue
OR
Stop
```

If yes, middleware may be a good fit.

---

# 19. Don't Put Everything Into Middleware

This is equally important.

Suppose your application says:

> A user can only delete their own Todo.

That's primarily a **business/authorization rule**, not just generic request processing.

You might have:

```text
authenticate
     ↓
controller
     ↓
service
     ↓
check ownership
     ↓
repository
```

Later we'll learn exactly where different authorization checks belong.

So don't create middleware for every possible piece of logic.

---

# 20. Your Mental Model

Remember this:

```text
                 HTTP REQUEST
                       │
                       ▼
              ┌─────────────────┐
              │    Middleware   │
              │                 │
              │ Check / prepare │
              │ / enrich / stop │
              └────────┬────────┘
                       │
                    next()
                       │
                       ▼
              ┌─────────────────┐
              │    Controller   │
              │                 │
              │ Handle HTTP     │
              └────────┬────────┘
                       │
                       ▼
                  Application
                    Logic
```

Middleware exists mainly because we want to:

> **Separate common request-processing responsibilities from our actual application logic.**
