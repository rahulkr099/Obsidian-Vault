# Phase 7 — Lesson 7.3

## The Request → Middleware → Response Lifecycle

In **7.1**, you learned what middleware is.

In **7.2**, you learned why Express needs middleware.

Now we're going to understand the **complete journey of one HTTP request through Express**.

This lesson is important because once you understand this flow, things like:

- `next()`
    
- middleware order
    
- authentication middleware
    
- validation middleware
    
- controllers
    
- error middleware
    

will become much easier.

---

# 1. The Big Picture

Imagine your React frontend sends:

```http
GET /api/v1/todos
```

The request doesn't magically jump directly to your controller.

It travels through the Express application.

The simplified flow is:

```text
React / Postman
      │
      │ HTTP Request
      ▼
   Express
      │
      ▼
Middleware 1
      │
      ▼
Middleware 2
      │
      ▼
Middleware 3
      │
      ▼
Route Handler / Controller
      │
      ▼
Service
      │
      ▼
Repository
      │
      ▼
MongoDB
      │
      ▼
Response
      │
      ▼
React / Postman
```

For now, focus only on:

```text
Request
   ↓
Middleware
   ↓
Route Handler
   ↓
Response
```

---

# 2. What Is an HTTP Request?

Before Express can do anything, a client sends a request.

For example:

```http
GET /api/v1/todos HTTP/1.1
Host: localhost:5000
Authorization: Bearer abc123
```

There are several pieces:

```text
GET
 ↓
HTTP method

/api/v1/todos
 ↓
URL/path

Authorization
 ↓
Header
```

And a request can also contain:

```text
Query parameters
URL parameters
Body
Cookies
Headers
```

For example:

```http
POST /api/v1/todos?draft=true
```

with:

```json
{
    "title": "Learn Express"
}
```

The browser sends all of this to your server.

---

# 3. Express Receives the Request

Your server might be:

```js
import express from "express";

const app = express();
```

And:

```js
app.listen(5000);
```

Now Express is listening for incoming HTTP requests.

When the browser sends:

```http
GET /api/v1/todos
```

Express receives it.

Think:

```text
Internet
   ↓
Port 5000
   ↓
Node.js
   ↓
Express
```

---

# 4. Express Starts Looking Through Its Middleware Stack

This is a very important concept.

Express essentially has a sequence of functions.

For example:

```js
app.use(logger);

app.use(requestId);

app.use(authenticate);

app.get("/todos", getTodos);
```

Conceptually:

```text
1. logger
2. requestId
3. authenticate
4. getTodos
```

When the request arrives, Express starts processing these functions **in order**.

```text
Request
   ↓
logger
   ↓
requestId
   ↓
authenticate
   ↓
getTodos
```

This is the **middleware stack**.

---

# 5. First Middleware Runs

Suppose:

```js
const logger = (req, res, next) => {
    console.log("Logger running");

    next();
};
```

The request enters:

```text
Request
   ↓
logger
```

The logger executes:

```js
console.log("Logger running");
```

Then:

```js
next();
```

tells Express:

> "I'm finished. Continue processing this request."

So:

```text
Request
   ↓
logger
   │
   │ next()
   ▼
next middleware
```

---

# 6. Second Middleware Runs

Suppose we have:

```js
const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    next();
};
```

Now:

```text
Request
   ↓
logger
   ↓
requestId
```

The request has been modified.

Originally:

```text
req
```

After the middleware:

```text
req
 └── requestId
```

So later middleware and controllers can access:

```js
req.requestId
```

---

# 7. Third Middleware Runs

Suppose:

```js
const authenticate = (req, res, next) => {
    // verify token

    req.user = {
        id: "123"
    };

    next();
};
```

Now:

```text
Request
   ↓
logger
   ↓
requestId
   ↓
authenticate
```

The request now contains:

```js
req.requestId
req.user
```

So information can be passed forward through the request.

---

# 8. Then the Route Handler Runs

Suppose:

```js
app.get("/todos", (req, res) => {
    res.json({
        success: true,
        userId: req.user.id,
        todos: []
    });
});
```

Once authentication calls:

```js
next();
```

Express reaches the route handler.

```text
Request
   ↓
logger
   ↓
requestId
   ↓
authenticate
   ↓
route handler
```

The route handler sends:

```json
{
    "success": true,
    "userId": "123",
    "todos": []
}
```

Now the request has completed.

---

# 9. The Full Journey

Let's put everything together.

```text
                   HTTP REQUEST
                        │
                        ▼
                 ┌─────────────┐
                 │    logger   │
                 └──────┬──────┘
                        │
                     next()
                        │
                        ▼
                 ┌─────────────┐
                 │  requestId  │
                 └──────┬──────┘
                        │
                     next()
                        │
                        ▼
                 ┌─────────────┐
                 │ authenticate│
                 └──────┬──────┘
                        │
                     next()
                        │
                        ▼
                 ┌─────────────┐
                 │   route     │
                 │   handler   │
                 └──────┬──────┘
                        │
                        ▼
                    res.json()
                        │
                        ▼
                   HTTP RESPONSE
```

This is the basic Express lifecycle.

# 10. What Exactly Does `next()` Do?

This is the question beginners usually struggle with.

When you write:

```js
next();
```

you're basically saying:

> **"Express, continue processing this request."**

For example:

```js
const first = (req, res, next) => {
    console.log("First");

    next();
};

const second = (req, res, next) => {
    console.log("Second");

    next();
};

app.get("/test", first, second, (req, res) => {
    console.log("Route");

    res.send("Done");
});
```

Request:

```http
GET /test
```

Output:

```text
First
Second
Route
```

Because:

```text
first
 ↓ next()
second
 ↓ next()
route
 ↓
response
```

---

# 11. What Happens If We Don't Call `next()`?

Consider:

```js
const first = (req, res, next) => {
    console.log("First");
};
```

And:

```js
const second = (req, res, next) => {
    console.log("Second");

    next();
};
```

Request:

```text
GET /test
```

Output:

```text
First
```

`second` never runs.

Why?

Because:

```text
first
  ↓
STOP
```

The request is stuck there unless `first` sends a response.

This is why this is dangerous:

```js
const middleware = (req, res, next) => {
    console.log("Hello");

    // forgot next()
};
```

---

# 12. Middleware Has Two Main Choices

When middleware finishes, it usually does one of two things.

### Choice 1 — Continue

```js
next();
```

Flow:

```text
Middleware
   ↓
next()
   ↓
Next middleware
```

### Choice 2 — Stop

```js
return res.status(401).json({
    success: false,
    message: "Unauthorized"
});
```

Flow:

```text
Middleware
   ↓
Response
   ↓
STOP
```

This gives us a very useful mental model:

```text
             Middleware
                 │
        ┌────────┴────────┐
        │                 │
     Allowed           Rejected
        │                 │
     next()             res
        │                 │
        ▼                 ▼
      Continue           STOP
```

---

# 13. Authentication Example

Suppose the user isn't authenticated.

```js
const authenticate = (req, res, next) => {
    const token = req.headers.authorization;

    if (!token) {
        return res.status(401).json({
            success: false,
            message: "Authentication required"
        });
    }

    next();
};
```

Flow:

```text
Request
   ↓
authenticate
   │
   ├── No token
   │      ↓
   │    401
   │
   └── Token exists
          ↓
        next()
          ↓
      Controller
```

This is exactly how middleware becomes a **checkpoint**.

---

# 14. Middleware Can Modify the Request

This is another major part of the lifecycle.

Suppose:

```js
const authenticate = (req, res, next) => {
    req.user = {
        id: "123",
        role: "user"
    };

    next();
};
```

Then the controller can do:

```js
const getProfile = (req, res) => {
    res.json({
        userId: req.user.id
    });
};
```

So:

```text
Original request
      ↓
authenticate
      ↓
req.user added
      ↓
controller
```

The request becomes richer as it moves through the pipeline.

---

# 15. The Request Object Is Shared Through the Pipeline

Conceptually:

```text
                  req
                   │
       ┌───────────┼────────────┐
       ▼           ▼            ▼
    logger      auth         validator
       │           │            │
       └───────────┼────────────┘
                   ▼
               controller
```

The same request object moves through the middleware chain.

So:

```js
req.requestId
req.user
req.body
req.params
req.query
```

can all be available later.

This is one reason middleware is so useful.

---

# 16. What About the Response?

The response object also travels through the pipeline.

For example:

```js
const securityHeaders = (req, res, next) => {
    res.setHeader(
        "X-App-Version",
        "1.0"
    );

    next();
};
```

Then later:

```js
res.json({
    success: true
});
```

The response will contain the header.

So:

```text
Request
 ↓
Middleware modifies res
 ↓
Controller sends response
 ↓
Client receives modified response
```

---

# 17. Middleware Can Run Before and After Things

This is slightly more advanced.

Suppose:

```js
const timer = (req, res, next) => {
    const start = Date.now();

    res.on("finish", () => {
        const duration = Date.now() - start;

        console.log(`${req.method} ${req.url} - ${duration}ms`);
    });

    next();
};
```

Notice something interesting.

Before `next()`:

```js
const start = Date.now();
```

We start the timer.

Then:

```js
next();
```

allows the request to continue.

Later, when the response finishes:

```js
res.on("finish", ...)
```

runs.

So the lifecycle can be thought of as:

```text
Request arrives
      ↓
Middleware starts timer
      ↓
next()
      ↓
Other middleware
      ↓
Controller
      ↓
Response
      ↓
"finish" event
      ↓
Calculate duration
```

This is the basic idea behind request-duration logging.

We'll explore this more later.

# 18. Where Does the Database Fit?

At this stage, you might wonder:

> "Where does MongoDB happen?"

In a well-structured application:

```text
Request
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

For example:

```text
POST /todos
     ↓
authenticate
     ↓
validateTodo
     ↓
createTodoController
     ↓
todoService.create()
     ↓
todoRepository.create()
     ↓
Todo model
     ↓
MongoDB
```

But don't worry about Service and Repository yet.

Those are later phases.

# 19. Why Order Matters

Consider:

```js
app.use(authenticate);

app.get("/todos", getTodos);
```

Flow:

```text
Request
 ↓
authenticate
 ↓
getTodos
```

Good.

But imagine:

```js
app.get("/todos", getTodos);

app.use(authenticate);
```

The route has already been registered before the authentication middleware.

This is why **middleware ordering and registration position matter**.

Later in this phase we'll spend an entire lesson on this:

# 20. A Practical Example

Let's create a tiny backend.

```js
import express from "express";

const app = express();

const logger = (req, res, next) => {
    console.log("1. Logger");

    next();
};

const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    console.log("2. Request ID");

    next();
};

const authenticate = (req, res, next) => {
    req.user = {
        id: "123"
    };

    console.log("3. Authentication");

    next();
};

app.use(logger);
app.use(requestId);

app.get(
    "/todos",
    authenticate,
    (req, res) => {
        console.log("4. Controller");

        res.json({
            success: true,
            requestId: req.requestId,
            userId: req.user.id
        });
    }
);

app.listen(5000);
```

Request:

```http
GET /todos
```

Output:

```text
1. Logger
2. Request ID
3. Authentication
4. Controller
```

Response:

```json
{
    "success": true,
    "requestId": "some-generated-id",
    "userId": "123"
}
```

# 22. The Most Important Mental Model

When debugging an Express application, don't think:

> "Why isn't my controller working?"

Instead ask:

```text
Did the request reach Express?
        ↓
Did middleware 1 run?
        ↓
Did middleware 1 call next()?
        ↓
Did middleware 2 run?
        ↓
Did middleware 2 reject the request?
        ↓
Did the route match?
        ↓
Did the controller run?
        ↓
Did the service run?
        ↓
Did the database operation succeed?
        ↓
Was a response sent?
```

This mindset will save you **a lot of debugging time**.

---

# 23. Debugging Trick

When something isn't working, temporarily add:

```js
console.log("Middleware 1");
```

Then:

```js
console.log("Middleware 2");
```

Then:

```js
console.log("Controller");
```

For example:

```text
Middleware 1
Middleware 2
```

but no:

```text
Controller
```

You immediately know:

> Something between middleware 2 and the controller is stopping the request.

This is much better than randomly changing code.
