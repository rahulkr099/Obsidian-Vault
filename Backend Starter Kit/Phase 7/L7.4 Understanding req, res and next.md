# Phase 7 — Lesson 7.4

## Understanding `req`, `res`, and `next`

This is one of the **most important Express lessons**.

You've already learned:

```text
Request
   ↓
Middleware
   ↓
Controller
   ↓
Response
```

Now we're going to understand the three objects/functions that make this pipeline work:

```js
(req, res, next)
```

Think of them as:

```text
req  → What did the client send me?
res  → What should I send back?
next → Should Express continue?
```

---

# 1. The Basic Middleware Function

You've already seen:

```js
const logger = (req, res, next) => {
    console.log("Request received");

    next();
};
```

Let's break it apart.

```text
(req, res, next)
   │    │     │
   │    │     └── Continue the pipeline
   │    │
   │    └──────── Send response
   │
   └───────────── Read/modify request
```

These are not random parameters.

Express provides them to your middleware/route handler.

---

# 2. `req` — The Request Object

`req` represents the **incoming HTTP request**.

Think:

> "What did the client send to my server?"

For example, if React sends:

```http
POST /api/v1/todos?draft=true
Authorization: Bearer abc123
Content-Type: application/json
```

with:

```json
{
    "title": "Learn Express"
}
```

Express gives you access to those pieces through `req`.

---

# 3. `req.method`

You can see the HTTP method:

```js
console.log(req.method);
```

For:

```http
GET /todos
```

you get:

```text
GET
```

For:

```http
POST /todos
```

you get:

```text
POST
```

For:

```http
DELETE /todos/123
```

you get:

```text
DELETE
```

Useful for logging:

```js
const logger = (req, res, next) => {
    console.log(req.method);

    next();
};
```

---

# 4. `req.url`

You can get the requested URL:

```js
console.log(req.url);
```

For:

```http
GET /todos?page=2
```

you may see:

```text
/todos?page=2
```

This is useful for logging.

For example:

```js
console.log(`${req.method} ${req.url}`);
```

Output:

```text
GET /todos?page=2
```

---

# 5. `req.path`

Express also gives you:

```js
req.path
```

For:

```http
GET /todos?page=2
```

the path is:

```text
/todos
```

Notice the difference:

```text
req.url
    ↓
/todos?page=2

req.path
    ↓
/todos
```

This becomes useful when you need the path without the query string.

---

# 6. `req.params`

This is extremely important.

Suppose your route is:

```js
app.get("/todos/:id", (req, res) => {
    console.log(req.params);
});
```

And the client requests:

```http
GET /todos/123
```

Then:

```js
req.params
```

contains:

```js
{
    id: "123"
}
```

So:

```js
req.params.id
```

gives:

```text
123
```

---

## Why?

Because your route says:

```text
/todos/:id
        ↑
    dynamic value
```

If the client sends:

```text
/todos/abc
```

then:

```js
req.params.id
```

is:

```text
abc
```

If:

```text
/todos/987
```

then:

```js
req.params.id
```

is:

```text
987
```

---

# 7. `req.query`

Query parameters come after `?`.

Example:

```http
GET /todos?page=2&limit=10
```

You can access:

```js
req.query
```

which looks conceptually like:

```js
{
    page: "2",
    limit: "10"
}
```

Then:

```js
req.query.page
```

gives:

```text
2
```

And:

```js
req.query.limit
```

gives:

```text
10
```

This becomes very important later for:

```text
Pagination
Filtering
Searching
Sorting
```

---

# 8. `req.body`

Suppose the frontend sends:

```http
POST /todos
Content-Type: application/json
```

with:

```json
{
    "title": "Learn Express",
    "completed": false
}
```

After enabling:

```js
app.use(express.json());
```

you can access:

```js
req.body
```

and get:

```js
{
    title: "Learn Express",
    completed: false
}
```

So:

```js
const createTodo = (req, res) => {
    console.log(req.body);
};
```

This is one of the most commonly used request properties in REST APIs.

---

# 9. Important: `express.json()`

You may wonder:

> "Why can't I just use `req.body`?"

Because Express needs middleware to parse JSON request bodies.

That's why we usually have:

```js
app.use(express.json());
```

Flow:

```text
JSON Request
     ↓
express.json()
     ↓
req.body
     ↓
Controller
```

We'll study `express.json()` properly in **Lesson 7.11**.

For now:

> `express.json()` converts incoming JSON into a JavaScript object available through `req.body`.

---

# 10. `req.headers`

HTTP requests contain headers.

Example:

```http
Authorization: Bearer abc123
Content-Type: application/json
Accept: application/json
```

You can access them with:

```js
req.headers
```

For example:

```js
console.log(req.headers.authorization);
```

could give:

```text
Bearer abc123
```

This becomes extremely important when we build authentication.

Eventually you'll have:

```text
Authorization header
       ↓
auth middleware
       ↓
extract token
       ↓
verify JWT
       ↓
req.user
```

---

# 11. `req.cookies`

When using cookies, you can access them through:

```js
req.cookies
```

But this usually requires:

```js
cookie-parser
```

For example, if the browser sends:

```text
refreshToken=abc123
```

you can eventually access:

```js
req.cookies.refreshToken
```

This will become important in your authentication lessons.

---

# 12. `req.user`

This one is **not automatically provided by Express**.

This is something **we add ourselves**.

For example:

```js
const authenticate = (req, res, next) => {
    req.user = {
        id: "123",
        role: "user"
    };

    next();
};
```

Now the controller can use:

```js
req.user.id
```

This gives us a powerful pattern:

```text
Request
   ↓
Authentication middleware
   ↓
req.user added
   ↓
Controller
```

Later your real authentication middleware will do something similar after verifying a JWT.

---

# 13. `req` Can Carry Information Through the Pipeline

This is worth remembering.

Suppose we have:

```text
Middleware 1
    ↓
Middleware 2
    ↓
Middleware 3
    ↓
Controller
```

Middleware 1 can add:

```js
req.requestId
```

Middleware 2 can add:

```js
req.user
```

Middleware 3 can add:

```js
req.permissions
```

Then the controller has:

```js
req.requestId
req.user
req.permissions
```

Conceptually:

```text
                req
                 │
       ┌─────────┼──────────┐
       ▼         ▼          ▼
 requestId      user    permissions
       │         │          │
       └─────────┼──────────┘
                 ▼
             Controller
```

This is one of the foundations of your future backend architecture.

---

# 14. `res` — The Response Object

Now let's look at:

```js
res
```

`res` represents the **outgoing HTTP response**.

Think:

> "What do I want to send back to the client?"

For example:

```js
res.send("Hello");
```

or:

```js
res.json({
    success: true
});
```

---

# 15. `res.send()`

The simplest response:

```js
app.get("/", (req, res) => {
    res.send("Hello World");
});
```

Client receives:

```text
Hello World
```

You can send strings, HTML, buffers, etc.

For REST APIs, however, you'll mostly use:

```js
res.json()
```

---

# 16. `res.json()`

This is extremely common in MERN applications.

```js
res.json({
    success: true,
    message: "Todo created"
});
```

Express sends JSON to the client.

The React frontend can then consume it.

For example:

```text
React
  ↓
Axios
  ↓
Express
  ↓
res.json()
  ↓
Axios response
  ↓
React
```

---

# 17. `res.status()`

You can set the HTTP status:

```js
res.status(201);
```

Then send:

```js
res.json({
    success: true
});
```

Usually you'll combine them:

```js
res.status(201).json({
    success: true,
    message: "Todo created"
});
```

Common examples:

```text
200 → OK
201 → Created
204 → No Content
400 → Bad Request
401 → Unauthorized
403 → Forbidden
404 → Not Found
409 → Conflict
500 → Internal Server Error
```

We'll study response architecture much more deeply later.

---

# 18. `res.status().json()` Is Chainable

This:

```js
res.status(201).json({
    success: true
});
```

works because Express methods can be chained.

Think:

```text
res
 ↓
status(201)
 ↓
json(...)
```

Very common Express style.

---

# 19. `res.sendStatus()`

You can also do:

```js
res.sendStatus(404);
```

This sends:

```text
404
```

with a default status message.

But in APIs, we usually want more useful JSON:

```js
res.status(404).json({
    success: false,
    message: "Todo not found"
});
```

So you'll probably use:

```text
res.status()
res.json()
```

much more often.

---

# 20. `res.setHeader()`

You can set response headers:

```js
res.setHeader(
    "X-App-Version",
    "1.0"
);
```

Then:

```js
res.json({
    success: true
});
```

The client receives that header.

Security middleware often modifies response headers.

For example:

```text
Helmet
   ↓
security headers
   ↓
response
```

---

# 21. `res.cookie()`

When using cookies, Express provides:

```js
res.cookie()
```

For example:

```js
res.cookie(
    "refreshToken",
    token,
    {
        httpOnly: true,
        secure: true
    }
);
```

This becomes important when we build refresh-token authentication.

The flow will eventually look like:

```text
Login
  ↓
Generate refresh token
  ↓
res.cookie()
  ↓
Browser stores cookie
```

---

# 22. `next()` — The Most Important One

Now we have:

```text
req → incoming information
res → outgoing response
next → continue
```

`next()` is not an object.

It's a **function**.

Example:

```js
const logger = (req, res, next) => {
    console.log(req.method);

    next();
};
```

When you call:

```js
next();
```

Express moves to the next matching middleware/handler.

---

# 23. Think of `next()` Like a Relay Baton

Imagine a relay race.

```text
Runner 1
   ↓
passes baton
   ↓
Runner 2
   ↓
passes baton
   ↓
Runner 3
```

Express:

```text
Middleware 1
   ↓
next()
   ↓
Middleware 2
   ↓
next()
   ↓
Middleware 3
   ↓
next()
   ↓
Controller
```

If a runner doesn't pass the baton:

```text
Runner 1
   ↓
STOP
```

Similarly:

```js
middleware
```

without:

```js
next()
```

or a response can stop the request.

---

# 24. `next(error)` Is Different

There are actually two important forms:

```js
next();
```

and:

```js
next(error);
```

Normal:

```js
next();
```

means:

> Continue normally.

Error:

```js
next(error);
```

means:

> Something went wrong. Send this error into Express's error-handling pipeline.

For example:

```js
const checkSomething = (req, res, next) => {
    const valid = false;

    if (!valid) {
        return next(new Error("Something went wrong"));
    }

    next();
};
```

Later we'll build:

```text
next(error)
    ↓
Global error middleware
    ↓
JSON error response
```

This becomes central to **Phase 8**.

---

# 25. `return` With `res`

You'll often see:

```js
return res.status(401).json({
    success: false,
    message: "Unauthorized"
});
```

Why `return`?

Because once you've sent the response, you don't want the function to continue executing.

Compare:

```js
if (!user) {
    res.status(404).json({
        message: "User not found"
    });
}

console.log("Continue...");
```

The function may continue.

Better:

```js
if (!user) {
    return res.status(404).json({
        message: "User not found"
    });
}

console.log("Continue...");
```

Now:

```text
User missing
   ↓
response
   ↓
return
   ↓
STOP
```

This is a very useful habit.

# 26. A Complete Example

Let's combine everything.

```js
const authenticate = (req, res, next) => {
    const token = req.headers.authorization;

    if (!token) {
        return res.status(401).json({
            success: false,
            message: "Authentication required"
        });
    }

    req.user = {
        id: "123",
        role: "user"
    };

    next();
};
```

And:

```js
app.get(
    "/profile",
    authenticate,
    (req, res) => {
        res.status(200).json({
            success: true,
            data: {
                userId: req.user.id,
                role: req.user.role
            }
        });
    }
);
```

Let's trace it.

---

# 27. Request Flow

Client sends:

```http
GET /profile
Authorization: Bearer abc123
```

Express receives it.

### Step 1

```js
authenticate(req, res, next)
```

### Step 2

Read:

```js
req.headers.authorization
```

### Step 3

Authentication succeeds.

### Step 4

Add:

```js
req.user
```

### Step 5

Call:

```js
next()
```

### Step 6

Controller/route handler runs.

### Step 7

Controller reads:

```js
req.user.id
```

### Step 8

Controller sends:

```js
res.status(200).json(...)
```

Complete flow:

```text
HTTP Request
     │
     ▼
     req
     │
     ▼
authenticate
     │
     ├── invalid → res.status(401)
     │
     └── valid
          │
          ▼
       req.user
          │
          ▼
        next()
          │
          ▼
      controller
          │
          ▼
       res.json()
          │
          ▼
        Client
```

### `res`


```text

```

# 29. A Practical Debugging Technique

When your backend isn't behaving correctly, temporarily inspect:

```js
console.log({
    method: req.method,
    url: req.url,
    params: req.params,
    query: req.query,
    body: req.body,
    headers: req.headers
});
```

Don't normally dump all headers in production because headers can contain sensitive information.

But during local learning/debugging, this can help you understand what Express is receiving.

# The Mental Model

Whenever you see:

```js
(req, res, next)
```

translate it in your head to:

```text
req
↓
"What did the client send?"

res
↓
"What should I send back?"

next
↓
"Should Express continue?"
```

And the complete pipeline:

```text
                CLIENT
                  │
                  │ HTTP REQUEST
                  ▼
             ┌──────────┐
             │   req    │
             └────┬─────┘
                  │
                  ▼
             MIDDLEWARE
                  │
          ┌───────┴────────┐
          │                │
       next()           response
          │                │
          ▼                ▼
       CONTINUE           STOP
          │
          ▼
      CONTROLLER
          │
          ▼
        res
          │
          ▼
        CLIENT
```

### Key takeaway

> **`req` carries information into your application, `res` carries information back to the client, and `next()` moves the request forward through Express's pipeline.**
