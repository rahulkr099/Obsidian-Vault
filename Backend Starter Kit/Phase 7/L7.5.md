# 1. What Is a Custom Middleware?

A custom middleware is simply a function **you write yourself** that follows Express's middleware pattern.

The basic structure is:

```js
const myMiddleware = (req, res, next) => {
    // do something

    next();
};
```

That's it.

There isn't some special class you need to extend.

There isn't some complicated Express API.

It's just a function.

The important part is what that function **does**.

---

# 2. The Three Responsibilities

A middleware can generally do three things.

### 1. Inspect

Look at the request:

```js
req.method
req.url
req.headers
req.body
req.query
req.params
```

### 2. Modify

Add or change information:

```js
req.requestId = "...";
```

or:

```js
res.setHeader("X-App-Version", "1.0");
```

### 3. Continue or stop

Continue:

```js
next();
```

Stop:

```js
return res.status(401).json({
    success: false,
    message: "Unauthorized"
});
```

So the basic model is:

```text
             Middleware
                 │
        ┌────────┼────────┐
        │        │        │
      Inspect  Modify   Decide
                          │
                    ┌─────┴─────┐
                    ▼           ▼
                  next()      response
                    │           │
                    ▼           ▼
                Continue       Stop
```

---

# 3. Your First Custom Middleware

Let's build the simplest possible one.

Create:

```js
const logger = (req, res, next) => {
    console.log("Request received");

    next();
};
```

Then register it:

```js
app.use(logger);
```

Now every request passing through this point will execute:

```text
Request
   ↓
logger
   ↓
next()
   ↓
next middleware / route
```

---

# 4. Let's Make It Actually Useful

Instead of:

```js
console.log("Request received");
```

let's inspect the request.

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);

    next();
};
```

Now:

```http
GET /todos
```

produces:

```text
GET /todos
```

And:

```http
POST /users
```

produces:

```text
POST /users
```

Already, we've created something useful.

---

# 5. Build a Better Logger

Let's improve it:

```js
const logger = (req, res, next) => {
    const start = Date.now();

    console.log(
        `[REQUEST] ${req.method} ${req.url}`
    );

    next();
};
```

Now we know:

```text
[REQUEST] GET /todos
```

But there's something missing.

We don't know whether the request succeeded.

For example:

```text
GET /todos → 200
GET /todos → 500
POST /todos → 201
```

We'll improve that later.

For now, focus on the basic middleware structure.

---

# 6. Middleware Is Just a Function

This is worth emphasizing.

You might see something like:

```js
app.use(express.json());
```

and think:

> "Middleware must be some special Express object."

No.

`express.json()` **returns a middleware function**.

Your custom middleware:

```js
const logger = (req, res, next) => {
    next();
};
```

is also just a function.

Then:

```js
app.use(logger);
```

tells Express:

> "Put this function into the middleware pipeline."

---

# 7. `app.use()` Is One Way to Register Middleware

You can do:

```js
app.use(logger);
```

This means:

> Run `logger` for requests that reach this point in the application.

Example:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);
    next();
};

app.use(logger);

app.get("/", (req, res) => {
    res.send("Home");
});

app.get("/todos", (req, res) => {
    res.json([]);
});
```

Now:

```text
GET /
```

goes through:

```text
logger
 ↓
/
```

And:

```text
GET /todos
```

goes through:

```text
logger
 ↓
/todos
```

---

# 8. Middleware Registration Order

Suppose you write:

```js
app.use(logger);

app.get("/todos", controller);
```

The flow is:

```text
GET /todos
   ↓
logger
   ↓
controller
```

But if you put:

```js
app.get("/todos", controller);

app.use(logger);
```

the route may handle the request before the later middleware gets a chance.

This is why you should think of your Express application as an ordered pipeline.

We'll dedicate Lesson **7.6** to this.

---

# 9. Route-Level Custom Middleware

You don't always want middleware to run everywhere.

Suppose you only want logging for:

```text
/todos
```

You can do:

```js
app.get(
    "/todos",
    logger,
    (req, res) => {
        res.json([]);
    }
);
```

Now:

```text
GET /todos
```

runs:

```text
logger
 ↓
controller
```

But:

```text
GET /users
```

doesn't use that particular middleware.

This is called **route-level middleware**.

We'll study this properly in Lesson 7.8.

# 10. Build a Request ID Middleware

Now let's build something closer to your real starter architecture.

A request ID helps us identify one request across logs.

Imagine:

```text
Request A
requestId = abc123
```

Then the logs can show:

```text
abc123 GET /todos
abc123 Database query
abc123 Response 200
```

This is extremely useful when debugging production systems.

---

## Step 1 — Import `crypto`

In modern Node.js:

```js
import crypto from "crypto";
```

Then:

```js
const requestId = (req, res, next) => {
    const id = crypto.randomUUID();

    req.requestId = id;

    next();
};
```

Now every request gets:

```js
req.requestId
```

---

# 11. Why Add It to `req`?

Because everything later in the request pipeline can access it.

```text
requestId middleware
       ↓
req.requestId
       ↓
logger
       ↓
controller
       ↓
service
       ↓
repository
```

For example:

```js
const controller = (req, res) => {
    console.log(
        "Request ID:",
        req.requestId
    );

    res.json({
        success: true
    });
};
```

The controller doesn't need to generate the ID itself.

The middleware already prepared the request.

---

# 12. We Can Also Send the ID Back

A useful improvement:

```js
const requestId = (req, res, next) => {
    const id = crypto.randomUUID();

    req.requestId = id;

    res.setHeader("X-Request-ID", id);

    next();
};
```

Now the request has:

```js
req.requestId
```

and the response has:

```http
X-Request-ID: abc123
```

So the frontend can see which request generated the response.

---

# 13. Build an Authentication-Like Middleware

Let's create a simple learning version.

Don't treat this as real JWT authentication yet.

```js
const fakeAuth = (req, res, next) => {
    req.user = {
        id: "123",
        role: "user"
    };

    next();
};
```

Then:

```js
app.get(
    "/profile",
    fakeAuth,
    (req, res) => {
        res.json({
            success: true,
            user: req.user
        });
    }
);
```

Request:

```http
GET /profile
```

Response:

```json
{
    "success": true,
    "user": {
        "id": "123",
        "role": "user"
    }
}
```

This demonstrates an important pattern:

```text
Middleware
    ↓
prepare request
    ↓
Controller
    ↓
use request information
```

Later, our actual authentication middleware will verify a JWT instead of creating a fake user.

---

# 14. Build a Middleware That Can Reject

Now let's make a middleware that checks for an API key.

```js
const requireApiKey = (req, res, next) => {
    const apiKey = req.headers["x-api-key"];

    if (!apiKey) {
        return res.status(401).json({
            success: false,
            message: "API key required"
        });
    }

    next();
};
```

Flow:

```text
Request
   ↓
requireApiKey
   │
   ├── no key → 401
   │
   └── key exists
          ↓
        next()
          ↓
       Controller
```

This demonstrates the two possible paths:

```text
ALLOW
 ↓
next()

REJECT
 ↓
response
```

---

# 15. Important Rule: Don't Call `next()` After Sending a Response

Avoid:

```js
if (!apiKey) {
    res.status(401).json({
        message: "API key required"
    });

    next();
}
```

This is wrong.

You've already sent the response.

Calling `next()` can cause another handler to execute and may produce errors like:

```text
Error: Cannot set headers after they are sent
```

Instead:

```js
if (!apiKey) {
    return res.status(401).json({
        message: "API key required"
    });
}
```

Then:

```js
next();
```

only happens when the request is allowed.

---

# 16. Build a Validation Middleware

Let's create a very simple learning example.

```js
const validateTodo = (req, res, next) => {
    const { title } = req.body;

    if (!title) {
        return res.status(400).json({
            success: false,
            message: "Title is required"
        });
    }

    next();
};
```

Then:

```js
app.post(
    "/todos",
    validateTodo,
    (req, res) => {
        res.status(201).json({
            success: true,
            message: "Todo created"
        });
    }
);
```

Flow:

```text
POST /todos
     ↓
validateTodo
     │
     ├── title missing → 400
     │
     └── valid
          ↓
        next()
          ↓
      controller
```

Later we'll replace this simple validation with Joi.

---

# 17. Middleware Can Be Very Small

A good middleware doesn't need to be huge.

For example:

```js
const addRequestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();
    next();
};
```

That's perfectly valid.

Don't feel like every middleware needs 100 lines of code.

In fact:

> **Small, focused middleware is usually easier to understand and maintain.**

---

# 18. Single Responsibility

Suppose you create this:

```js
const everything = (req, res, next) => {
    // logging
    // authentication
    // validation
    // rate limiting
    // authorization
    // database query
    // email
    // response
};
```

This defeats the entire purpose of middleware.

Instead:

```text
requestId
logger
rateLimiter
authenticate
validate
authorize
controller
```

Each has one clear responsibility.

---

# 19. Build a Small Middleware Pipeline

Let's put several together.

```js
import express from "express";
import crypto from "crypto";

const app = express();

const requestId = (req, res, next) => {
    const id = crypto.randomUUID();

    req.requestId = id;
    res.setHeader("X-Request-ID", id);

    next();
};

const logger = (req, res, next) => {
    console.log(
        `[${req.requestId}] ${req.method} ${req.url}`
    );

    next();
};

const fakeAuth = (req, res, next) => {
    req.user = {
        id: "123",
        role: "user"
    };

    next();
};

app.use(requestId);
app.use(logger);

app.get(
    "/profile",
    fakeAuth,
    (req, res) => {
        res.json({
            success: true,
            requestId: req.requestId,
            userId: req.user.id
        });
    }
);

app.listen(5000);
```

Now the flow is:

```text
GET /profile
      ↓
requestId
      ↓
logger
      ↓
fakeAuth
      ↓
controller
      ↓
response
```

And the request gradually becomes richer:

```text
req
 ↓
req.requestId
 ↓
req.user
 ↓
controller
```

# 21. Middleware Naming

Use names that clearly describe what the middleware does.

Good:

```text
requestId
logger
authenticate
requireAdmin
validateTodo
rateLimiter
sanitizeInput
```

Bad:

```text
handle
process
check
doStuff
middleware1
middleware2
```

When you read:

```js
router.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

you should immediately understand the pipeline.

---

# 22. Where Should Middleware Live?

Once your application grows, don't keep everything inside:

```text
server.js
```

You might start with:

```text
backend/
└── server.js
```

Then:

```text
backend/
├── app.js
├── server.js
└── middlewares/
    ├── logger.middleware.js
    ├── requestId.middleware.js
    └── auth.middleware.js
```

Later:

```text
middlewares/
├── auth.middleware.js
├── role.middleware.js
├── logger.middleware.js
├── requestId.middleware.js
└── security/
    ├── rateLimiter.middleware.js
    ├── sanitize.middleware.js
    └── validate.middleware.js
```

That's the direction your starter is designed around.

---

# 23. Don't Create a File Too Early

One important professional habit:

Don't create:

```text
middlewares/
├── checkSomething.js
├── checkSomethingElse.js
├── doSomething.js
├── anotherCheck.js
```

just because you can.

First ask:

> Is this responsibility actually reusable?

If yes, extract it.

If it's a tiny piece of logic used only once, it might belong somewhere else.

Good architecture isn't:

> "More files = more professional."

Good architecture is:

> **"Each piece of code has a clear responsibility and a useful boundary."**

# 24. A Useful Design Formula

When creating middleware, think:

```text
1. What information do I need?
              ↓
2. What should I check/do?
              ↓
3. What should I add/change?
              ↓
4. Should I stop or continue?
```

For example, authentication:

```text
What do I need?
→ Authorization header

What should I check?
→ JWT validity

What should I add?
→ req.user

Stop or continue?
→ invalid = stop
→ valid = next()
```

Validation:

```text
What do I need?
→ req.body

What should I check?
→ Schema

What should I add/change?
→ Clean validated data

Stop or continue?
→ invalid = stop
→ valid = next()
```

Request ID:

```text
What do I need?
→ nothing

What should I do?
→ generate ID

What should I add?
→ req.requestId

Stop or continue?
→ always next()
```

This formula will help you design middleware yourself.

# 27. Common Beginner Mistakes

### Mistake 1 — Forgetting `next()`

```js
const logger = (req, res, next) => {
    console.log("Hello");
};
```

Request may hang.

---

### Mistake 2 — Calling `next()` after sending a response

```js
res.status(401).json(...);
next();
```

Don't do this.

---

### Mistake 3 — Doing too much

```js
const middleware = async (...) => {
    // auth
    // database
    // email
    // business logic
    // response
};
```

Break it apart.

---

### Mistake 4 — Modifying random request properties

Avoid things like:

```js
req.fooBarSomething = ...
```

without a clear convention.

Prefer meaningful names:

```js
req.user
req.requestId
req.permissions
```

---

### Mistake 5 — Hiding business logic inside middleware

Don't turn:

```text
middleware
```

into:

```text
everything
```

We'll learn the proper boundary between middleware, controllers, services, and repositories in later phases.

# 28. Your Mental Model

A custom middleware is simply:

```text
             REQUEST
                │
                ▼
        ┌─────────────────┐
        │ Custom Middleware│
        └────────┬────────┘
                 │
       ┌─────────┴──────────┐
       │                    │
    Reject               Continue
       │                    │
       ▼                  next()
    Response                │
                            ▼
                     Next Middleware
                            │
                            ▼
                       Controller
```

And the basic code:

```js
const middleware = (req, res, next) => {

    // 1. inspect request

    // 2. do something

    // 3. modify req/res if needed

    // 4. stop OR continue

    next();
};
```
