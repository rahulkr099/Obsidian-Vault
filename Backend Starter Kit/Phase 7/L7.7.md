# Phase 7 — Lesson 7.7

## Multiple Middleware Functions

In the previous lessons, you learned that middleware forms a pipeline:

```text
Request
   ↓
Middleware
   ↓
Controller
   ↓
Response
```

But in real backend applications, **one route often needs multiple middleware functions**.

For example, creating a Todo might require:

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Controller
   ↓
Service
```

Today we'll learn how to build exactly that.

---

# 1. Why Do We Need Multiple Middleware?

Imagine this endpoint:

```http
POST /api/v1/todos
```

Before creating a Todo, we may need to check:

```text
1. Is the user authenticated?
2. Is the user allowed to create a Todo?
3. Is the request body valid?
4. Then create the Todo.
```

Instead of making one huge middleware:

```js
checkEverything();
```

we create small middleware:

```text
authenticate
authorize
validateTodo
```

Then compose them:

```text
authenticate
     ↓
authorize
     ↓
validateTodo
     ↓
controller
```

This is called **middleware composition**.

---

# 2. Multiple Middleware in One Route

Express allows you to provide multiple functions:

```js
app.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

Here we have:

```text
authenticate
validateTodo
createTodo
```

The execution order is:

```text
POST /todos
     ↓
authenticate
     ↓
validateTodo
     ↓
createTodo
     ↓
response
```

---

# 3. Let's Build a Simple Example

Start with three middleware functions.

### Middleware 1

```js
const first = (req, res, next) => {
    console.log("First middleware");

    next();
};
```

### Middleware 2

```js
const second = (req, res, next) => {
    console.log("Second middleware");

    next();
};
```

### Middleware 3

```js
const third = (req, res, next) => {
    console.log("Third middleware");

    next();
};
```

Now:

```js
app.get(
    "/test",
    first,
    second,
    third,
    (req, res) => {
        res.send("Done");
    }
);
```

Request:

```http
GET /test
```

Output:

```text
First middleware
Second middleware
Third middleware
```

Then:

```text
Done
```

---

# 4. Think of It as a Chain

The route:

```js
app.get(
    "/test",
    first,
    second,
    third,
    controller
);
```

is basically:

```text
               /test
                 │
                 ▼
              first
                 │
               next()
                 │
                 ▼
              second
                 │
               next()
                 │
                 ▼
               third
                 │
               next()
                 │
                 ▼
             controller
                 │
                 ▼
              response
```

Every middleware gets a chance to process the request.

---

# 5. Middleware Can Add Information for the Next Middleware

This is where multiple middleware become powerful.

Suppose the first middleware adds:

```js
const addRequestId = (req, res, next) => {
    req.requestId = "abc123";

    next();
};
```

The second middleware can use it:

```js
const logger = (req, res, next) => {
    console.log(req.requestId);

    next();
};
```

Then:

```js
app.get(
    "/test",
    addRequestId,
    logger,
    (req, res) => {
        res.json({
            requestId: req.requestId
        });
    }
);
```

Flow:

```text
addRequestId
     │
     └── req.requestId = "abc123"
                    │
                    ▼
                  logger
                    │
                    └── reads req.requestId
                              │
                              ▼
                          controller
```

This is one of the main reasons we compose middleware.

---

# 6. Middleware Can Stop the Chain

Suppose:

```js
const authenticate = (req, res, next) => {
    const token = req.headers.authorization;

    if (!token) {
        return res.status(401).json({
            success: false,
            message: "Authentication required"
        });
    }

    next();
};
```

Then:

```js
app.get(
    "/profile",
    authenticate,
    getProfile
);
```

If there's no token:

```text
Request
   ↓
authenticate
   ↓
❌ 401
```

`getProfile` doesn't run.

---

# 7. What If There Are Three Middleware?

Consider:

```js
app.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

There are three possible stopping points.

### Authentication fails

```text
Request
   ↓
authenticate
   ↓
401
```

### Authentication succeeds, validation fails

```text
Request
   ↓
authenticate
   ↓
validateTodo
   ↓
400
```

### Everything succeeds

```text
Request
   ↓
authenticate
   ↓
validateTodo
   ↓
createTodo
   ↓
201
```

So middleware creates a series of **gates**.

---

# 8. Think of Middleware as Gates

For a Todo endpoint:

```text
             POST /todos
                  │
                  ▼
          ┌───────────────┐
          │ Authenticated?│
          └───────┬───────┘
                  │
             YES  │  NO
                  │   └──────→ 401
                  ▼
          ┌───────────────┐
          │ Valid input?  │
          └───────┬───────┘
                  │
             YES  │  NO
                  │   └──────→ 400
                  ▼
             Controller
                  │
                  ▼
               Service
```

This is a very useful mental model.

# 9. Real Backend Example

Let's build something closer to your MERN backend.

Suppose:

```js
const authenticate = (req, res, next) => {
    req.user = {
        id: "123",
        role: "user"
    };

    next();
};
```

Then:

```js
const validateTodo = (req, res, next) => {
    if (!req.body.title) {
        return res.status(400).json({
            success: false,
            message: "Title is required"
        });
    }

    next();
};
```

And controller:

```js
const createTodo = (req, res) => {
    res.status(201).json({
        success: true,
        message: "Todo created",
        userId: req.user.id,
        title: req.body.title
    });
};
```

Route:

```js
app.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

# 11. Trace an Invalid Request

Request:

```http
POST /todos
```

Body:

```json
{}
```

Flow:

```text
POST /todos
      ↓
authenticate
      ↓
next()
      ↓
validateTodo
      ↓

      ↓
400 Bad Request
      ↓
STOP
```

The controller never runs.

This is exactly what we want.

---

# 12. What Happens If Authentication Fails?

Suppose:

```js
authenticate
```

rejects the request.

Then:

```text
POST /todos
      ↓
authenticate
      ↓
401
```

Neither:

```text
validateTodo
createTodo
```

runs.

So the chain behaves like:

```text
Middleware 1
    │
    ├── FAIL → STOP
    │
    └── PASS
         ↓
     Middleware 2
         │
         ├── FAIL → STOP
         │
         └── PASS
              ↓
          Middleware 3
              │
              ▼
          Controller
```

---

# 13. Multiple Middleware Functions Can Be Global Too

Multiple middleware aren't limited to routes.

You can write:

```js
app.use(requestId);
app.use(logger);
app.use(express.json());
```

Now many requests go through them.

Conceptually:

```text
                 Request
                    │
                    ▼
               requestId
                    │
                    ▼
                 logger
                    │
                    ▼
              express.json()
                    │
                    ▼
                  routes
```

We'll later build a more complete `app.js` around this idea.

---

# 14. Multiple Middleware With `app.use()`

You can also pass multiple middleware functions to `app.use()`:

```js
app.use(
    requestId,
    logger,
    securityMiddleware
);
```

Conceptually:

```text
requestId
   ↓
logger
   ↓
securityMiddleware
   ↓
next matching handler
```

It's another form of composition.

---

# 15. Middleware Arrays

Express also allows middleware to be stored in an array.

For example:

```js
const protectedMiddleware = [
    authenticate,
    validateTodo
];
```

Then:

```js
app.post(
    "/todos",
    ...protectedMiddleware,
    createTodo
);
```

The spread operator expands the array:

```js
app.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

This can be useful when a particular group of middleware is reused.

---

# 16. Example: Protected Middleware Group

Suppose many routes require:

```text
authentication
logging
```

You could create:

```js
const protectedRoutes = [
    authenticate,
    logger
];
```

Then:

```js
app.get(
    "/profile",
    ...protectedRoutes,
    getProfile
);

app.get(
    "/todos",
    ...protectedRoutes,
    getTodos
);
```

Conceptually:

```text
/profile
   ↓
authenticate
   ↓
logger
   ↓
getProfile
```

and:

```text
/todos
   ↓
authenticate
   ↓
logger
   ↓
getTodos
```

This can reduce repetition.

---

# 17. But Don't Over-Abstract

You might be tempted to create:

```js
const middlewareForEverything = [
    cors,
    helmet,
    logger,
    rateLimiter,
    auth,
    role,
    validation,
    sanitize,
    ...
];
```

Then put it everywhere.

Don't do that blindly.

Different routes have different requirements.

For example:

```text
/health
```

probably doesn't need:

```text
authentication
```

And:

```text
/login
```

can't require normal authentication because the user is trying to authenticate in the first place.

So:

> **Compose middleware according to the actual requirements of the route.**

---

# 18. Authentication + Authorization + Validation

This is a very common pattern:

```js
router.post(
    "/admin/todos",
    authenticate,
    requireRole("admin"),
    validateTodo,
    createTodo
);
```

The flow:

```text
Request
   ↓
authenticate
   ↓
Who are you?
   ↓
requireRole("admin")
   ↓
Are you allowed?
   ↓
validateTodo
   ↓
Is the input valid?
   ↓
createTodo
```

Notice how each middleware answers a **different question**.

|Middleware|Question|
|---|---|
|`authenticate`|Who are you?|
|`requireRole`|Are you allowed?|
|`validateTodo`|Is the input valid?|
|`createTodo`|What should the application do?|

This separation is extremely important.

---

# 19. Middleware Composition Is About Responsibility

Suppose we have:

```js
router.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

Each component has one job:

```text
authenticate
→ authentication

validateTodo
→ validation

createTodo
→ HTTP/business operation
```

We don't want:

```js
authenticateAndValidateAndCreateTodo()
```

because that creates a giant function that does too many things.

---

# 20. A More Realistic Architecture

Eventually your route might look like:

```js
router.post(
    "/todos",
    authenticate,
    validate(createTodoSchema),
    createTodo
);
```

And possibly:

```js
router.delete(
    "/todos/:id",
    authenticate,
    validate(todoIdSchema),
    deleteTodo
);
```

The route itself becomes almost like a sentence:

```text
POST /todos
→ authenticate
→ validate
→ createTodo
```

That's a sign of a clean architecture.

---

# 21. Middleware Can Share Data

Imagine:

### Middleware 1

```js
const authenticate = (req, res, next) => {
    req.user = {
        id: "123",
        role: "admin"
    };

    next();
};
```

### Middleware 2

```js
const requireAdmin = (req, res, next) => {
    if (req.user.role !== "admin") {
        return res.status(403).json({
            message: "Forbidden"
        });
    }

    next();
};
```

### Middleware 3

```js
const logger = (req, res, next) => {
    console.log(
        `User: ${req.user.id}`
    );

    next();
};
```

Now:

```text
authenticate
      ↓
req.user created
      ↓
requireAdmin
      ↓
req.user checked
      ↓
logger
      ↓
req.user logged
      ↓
controller
```

This demonstrates how information can travel through a middleware chain.

---

# 22. Middleware Order Still Matters

Suppose we write:

```js
router.post(
    "/admin",
    requireAdmin,
    authenticate,
    controller
);
```

That's wrong because:

```text
requireAdmin
    ↓
needs req.user
    ↓
req.user doesn't exist yet
```

Correct:

```js
router.post(
    "/admin",
    authenticate,
    requireAdmin,
    controller
);
```

So multiple middleware make the rule from Lesson 7.6 even more important:

> **The order must match the dependencies between middleware.**

# 23. Debugging Multiple Middleware

Suppose your route is:

```js
router.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

But the controller isn't running.

Don't randomly modify the controller.

Add temporary logs:

```js
const authenticate = (req, res, next) => {
    console.log("AUTH");

    next();
};
```

```js
const validateTodo = (req, res, next) => {
    console.log("VALIDATION");

    next();
};
```

```js
const createTodo = (req, res) => {
    console.log("CONTROLLER");

    res.json({
        success: true
    });
};
```

If you see:

```text
AUTH
VALIDATION
```

but not:

```text
CONTROLLER
```

then validation is probably stopping or failing before the controller.

This is a very practical debugging technique.

---

# 24. A Powerful Debugging Question

Whenever you have:

```text
Middleware A
 ↓
Middleware B
 ↓
Middleware C
 ↓
Controller
```

ask:

> **"What is the last thing that successfully executed?"**

If the logs say:

```text
A
B
```

then you know the problem is somewhere after B.

This makes debugging much faster.

# 26. Middleware Arrays — A Practical Example

Suppose all admin routes require:

```text
authenticate
requireAdmin
```

You can define:

```js
const adminMiddleware = [
    authenticate,
    requireAdmin
];
```

Then:

```js
router.get(
    "/users",
    ...adminMiddleware,
    getUsers
);

router.delete(
    "/users/:id",
    ...adminMiddleware,
    deleteUser
);
```

This gives:

```text
GET /users
      ↓
authenticate
      ↓
requireAdmin
      ↓
getUsers
```

and:

```text
DELETE /users/:id
      ↓
authenticate
      ↓
requireAdmin
      ↓
deleteUser
```

This is useful when several routes share the same protection.

# 27. Don't Put the Controller Inside Middleware

A common beginner mistake is:

```js
const authenticate = (req, res, next) => {
    // authentication

    createTodo(req, res);
};
```

Don't do this.

Instead:

```js
const authenticate = (req, res, next) => {
    // authentication

    next();
};
```

Then:

```js
router.post(
    "/todos",
    authenticate,
    createTodo
);
```

Why?

Because the middleware's responsibility is:

```text
Authenticate
```

The controller's responsibility is:

```text
Handle the Todo request
```

---

# 28. Multiple Middleware ≠ Multiple Controllers

Usually your chain looks like:

```text
Middleware
Middleware
Middleware
Controller
```

not:

```text
Controller
Controller
Controller
```

Once a controller sends the final response, the request is normally complete.

So:

```text
request processing
      ↓
middleware
      ↓
controller
      ↓
response
```

The service/repository layers then happen **inside the controller's application flow**, rather than as additional Express middleware.

---

# 29. The Pattern You Should Learn

For most protected CRUD routes, you'll frequently see something like:

```js
router.post(
    "/",
    authenticate,
    validate(createSchema),
    createController
);
```

or:

```js
router.delete(
    "/:id",
    authenticate,
    validate(idSchema),
    deleteController
);
```

The pattern is:

```text
               ROUTE
                 │
                 ▼
          Authentication
                 │
                 ▼
             Validation
                 │
                 ▼
             Controller
                 │
                 ▼
              Service
                 │
                 ▼
             Repository
                 │
                 ▼
             Database
```

This is one of the core patterns you'll repeatedly use in your MERN backend projects.

# 32. Common Mistakes

### ❌ Mistake 1 — Wrong order

```js
requireAdmin,
authenticate
```

when `requireAdmin` needs `req.user`.

---

### ❌ Mistake 2 — Forgetting `next()`

```js
const logger = (req, res, next) => {
    console.log("Hello");
};
```

---

### ❌ Mistake 3 — Calling `next()` after response

```js
return res.status(401).json(...);
next();
```

The `next()` is unreachable anyway.

---

### ❌ Mistake 4 — One giant middleware

```text
authenticate
validate
authorize
database
business logic
email
response
```

Break it apart.

---

### ❌ Mistake 5 — Reusing middleware without checking its assumptions

For example:

```js
requireAdmin
```

assumes:

```js
req.user
```

exists.

So you must place:

```text
authenticate
```

before it.

# ⭐ The Core Idea

Multiple middleware allow you to build a request pipeline out of **small, focused pieces**:

```text
Request
   ↓
requestId
   ↓
logger
   ↓
rateLimiter
   ↓
authenticate
   ↓
authorize
   ↓
validate
   ↓
controller
   ↓
service
   ↓
repository
   ↓
database
```

You don't need all of these on every route.

You **compose the ones that the route actually needs**.

That is the foundation for the middleware architecture in your MERN starter.
