# Phase 7 — Lesson 7.8

## Route-Level Middleware

This lesson is directly from the Phase 7 roadmap: **7.8 is Route-Level Middleware**. The goal is to understand why middleware sometimes belongs on **one specific route** instead of the entire application.

You already know:

```text
7.5 → Create middleware
7.6 → Middleware execution order
7.7 → Multiple middleware
7.8 → Route-level middleware
```

Let's build this from the ground up.

---

# 1. What Is Route-Level Middleware?

Route-level middleware is middleware that runs **only for a particular route or group of routes**.

For example:

```js
app.get(
    "/profile",
    authenticate,
    getProfile
);
```

Here:

```text
/profile
   ↓
authenticate
   ↓
getProfile
```

But if you request:

```text
/health
```

the `authenticate` middleware doesn't run for that route.

---

# 2. Why Do We Need It?

Imagine your application has:

```text
GET  /health
POST /auth/login
GET  /profile
GET  /todos
POST /todos
DELETE /todos/:id
```

Some routes are public:

```text
/health
/auth/login
```

Some require authentication:

```text
/profile
/todos
```

You don't want to make authentication run on **every route**.

Instead:

```text
Public
  ↓
No authentication

Protected
  ↓
Authentication
```

This is where route-level middleware becomes useful.

---

# 3. Application-Level vs Route-Level

This distinction is very important.

### Application-level

```js
app.use(logger);
```

Conceptually:

```text
Many requests
     ↓
   logger
```

### Route-level

```js
app.get(
    "/profile",
    authenticate,
    getProfile
);
```

Conceptually:

```text
/profile
   ↓
authenticate
   ↓
getProfile
```

So:

```text
Application-level
→ broad scope

Route-level
→ specific scope
```

---

# 4. Your First Route-Level Middleware

Create:

```js
const logger = (req, res, next) => {
    console.log("Logger running");

    next();
};
```

Now:

```js
app.get(
    "/profile",
    logger,
    (req, res) => {
        res.json({
            success: true
        });
    }
);
```

Request:

```http
GET /profile
```

Flow:

```text
GET /profile
     ↓
logger
     ↓
controller
     ↓
response
```

But:

```http
GET /health
```

doesn't use that route-level logger.

---

# 5. Compare With `app.use()`

### Global/application-level

```js
app.use(logger);

app.get("/profile", profileController);
app.get("/todos", todoController);
app.get("/health", healthController);
```

Flow:

```text
/profile → logger → controller
/todos   → logger → controller
/health  → logger → controller
```

### Route-level

```js
app.get(
    "/profile",
    logger,
    profileController
);

app.get(
    "/todos",
    logger,
    todoController
);

app.get(
    "/health",
    healthController
);
```

Flow:

```text
/profile → logger → controller
/todos   → logger → controller
/health  → controller
```

Notice the difference.

---

# 6. Why Would We Want Different Middleware?

Because different endpoints have different requirements.

For example:

```text
GET /health
```

might need:

```text
nothing special
```

But:

```text
DELETE /todos/:id
```

might need:

```text
authenticate
authorization
validation
```

So:

```js
app.delete(
    "/todos/:id",
    authenticate,
    validateTodoId,
    deleteTodo
);
```

Flow:

```text
DELETE /todos/:id
        ↓
authenticate
        ↓
validateTodoId
        ↓
deleteTodo
```

That's much cleaner than making every endpoint use all three.

---

# 7. Authentication Is a Perfect Example

Suppose:

```js
const authenticate = (req, res, next) => {
    const token = req.headers.authorization;

    if (!token) {
        return res.status(401).json({
            success: false,
            message: "Authentication required"
        });
    }

    req.user = {
        id: "123"
    };

    next();
};
```

Now:

```js
app.get(
    "/profile",
    authenticate,
    (req, res) => {
        res.json({
            success: true,
            userId: req.user.id
        });
    }
);
```

The authentication middleware applies specifically to `/profile`.

# 8. Public Route vs Protected Route

Let's build:

```js
app.get("/health", (req, res) => {
    res.json({
        success: true,
        message: "Healthy"
    });
});

app.get(
    "/profile",
    authenticate,
    (req, res) => {
        res.json({
            success: true,
            userId: req.user.id
        });
    }
);
```

Now:

### `/health`

```text
GET /health
     ↓
health controller
     ↓
200
```

### `/profile`

```text
GET /profile
     ↓
authenticate
     ↓
profile controller
     ↓
200
```

If `/profile` doesn't have a valid token:

```text
GET /profile
     ↓
authenticate
     ↓
401
```

# 9. Multiple Route-Level Middleware

You already learned multiple middleware in 7.7.

Now combine that with route-level middleware.

```js
app.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);
```

This route has **two middleware functions**:

```text
authenticate
validateTodo
```

followed by:

```text
createTodo
```

Flow:

```text
POST /todos
     ↓
authenticate
     ↓
validateTodo
     ↓
createTodo
     ↓
response
```

This is probably one of the most common patterns you'll use in your backend.

---

# 10. Different Routes, Different Middleware

Imagine:

```js
app.get(
    "/todos",
    authenticate,
    getTodos
);

app.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);

app.delete(
    "/todos/:id",
    authenticate,
    validateTodoId,
    deleteTodo
);
```

Now each endpoint has its own requirements.

### GET

```text
authenticate
    ↓
getTodos
```

### POST

```text
authenticate
    ↓
validateTodo
    ↓
createTodo
```

### DELETE

```text
authenticate
    ↓
validateTodoId
    ↓
deleteTodo
```

This is **middleware composition at the route level**.

---

# 11. Route-Level Middleware Can Modify `req`

Suppose:

```js
const authenticate = (req, res, next) => {
    req.user = {
        id: "123",
        role: "user"
    };

    next();
};
```

Then:

```js
app.get(
    "/profile",
    authenticate,
    (req, res) => {
        console.log(req.user);

        res.json({
            userId: req.user.id
        });
    }
);
```

The route handler can access the information created by the middleware.

Flow:

```text
authenticate
     ↓
req.user created
     ↓
route handler
     ↓
req.user used
```

---

# 12. Route-Level Middleware Can Reject

Consider:

```js
const requireAdmin = (req, res, next) => {
    if (req.user.role !== "admin") {
        return res.status(403).json({
            success: false,
            message: "Admin access required"
        });
    }

    next();
};
```

Then:

```js
app.delete(
    "/users/:id",
    authenticate,
    requireAdmin,
    deleteUser
);
```

Flow:

```text
DELETE /users/:id
       ↓
authenticate
       ↓
requireAdmin
       │
       ├── not admin → 403
       │
       └── admin
            ↓
        deleteUser
```

Notice the dependency:

```text
authenticate
     ↓
req.user
     ↓
requireAdmin
```

That's why the order matters.

---

# 13. Route-Level Middleware Can Be Reused

Suppose you have:

```js
const authenticate = ...
```

You can reuse it:

```js
app.get(
    "/profile",
    authenticate,
    getProfile
);

app.get(
    "/todos",
    authenticate,
    getTodos
);

app.post(
    "/todos",
    authenticate,
    validateTodo,
    createTodo
);

app.delete(
    "/todos/:id",
    authenticate,
    validateTodoId,
    deleteTodo
);
```

You're not rewriting authentication.

You define it once and attach it wherever required.

That's one of the major benefits of middleware.

# 14. A Common Real-World Pattern

Your eventual Todo routes might look roughly like:

```js
router.get(

router.post(

    "/:id",

    "/:id",

    validate(updateTodoSchema),
    updateTodo

    "/:id",
    authenticate,

    deleteTodo
);
```

Don't worry about `validate()` yet.

We'll properly build validation in **Phase 9**.

For now, focus on the structure:

```text
Route
 ↓
Required middleware
 ↓
Controller
```

# 15. Router-Level Middleware

There's another useful concept between application-level and individual route-level middleware.

Suppose you have:

```text
/api/v1/todos
```

with many routes:

```text
GET    /
POST   /
GET    /:id
PATCH  /:id
DELETE /:id
```

You might want authentication on **all Todo routes**.

Instead of writing:

```js
router.get("/", authenticate, getTodos);

router.post("/", authenticate, createTodo);

router.get("/:id", authenticate, getTodo);

router.patch("/:id", authenticate, updateTodo);

router.delete("/:id", authenticate, deleteTodo);
```

you can do:

```js
router.use(authenticate);
```

Then:

```js
router.get("/", getTodos);

router.post("/", createTodo);

router.get("/:id", getTodo);

router.patch("/:id", updateTodo);

router.delete("/:id", deleteTodo);
```

Conceptually:

```text
/api/v1/todos
       ↓
   authenticate
       ↓
 ┌─────┼─────┬─────┬─────┐
 ↓     ↓     ↓     ↓     ↓
GET   POST   GET  PATCH DELETE
```

This is extremely useful.

---

# 16. Why `router.use()` Is Powerful

Imagine:

```text
routes/
├── auth.routes.js
├── user.routes.js
└── todo.routes.js
```

Your Todo router:

```js
const router = express.Router();

router.use(authenticate);

router.get("/", getTodos);
router.post("/", createTodo);
router.patch("/:id", updateTodo);
router.delete("/:id", deleteTodo);

export default router;
```

Now every route inside this router passes through:

```text
authenticate
```

This gives you a clean separation.

---

# 17. Application-Level → Router-Level → Route-Level

Now we have three useful scopes.

### Application-level

```js
app.use(logger);
```

Broad.

### Router-level

```js
router.use(authenticate);
```

Applies to routes inside that router.

### Route-level

```js
router.post(
    "/",
    validateTodo,
    createTodo
);
```

Applies to one route.

Think:

```text
APPLICATION
     │
     ▼
  ROUTER
     │
     ▼
   ROUTE
```

And middleware can exist at each level.

---

# 18. Example Architecture

Imagine:

```text
app.js
```

contains:

```js
app.use(requestId);
app.use(logger);

app.use("/api/v1/todos", todoRoutes);
```

Then:

```text
todo.routes.js
```

contains:

```js
router.use(authenticate);

router.get("/", getTodos);

router.post(
    "/",
    validateTodo,
    createTodo
);

router.delete(
    "/:id",
    validateTodoId,
    deleteTodo
);
```

The final flow for:

```http
POST /api/v1/todos
```

is:

```text
Request
   ↓
requestId
   ↓
logger
   ↓
todo router
   ↓
authenticate
   ↓
validateTodo
   ↓
createTodo
   ↓
response
```

This is a very realistic Express architecture.

---

# 19. Why This Is Better Than One Giant `app.js`

Imagine putting everything in `app.js`:

```js
app.get(...);
app.post(...);
app.patch(...);
app.delete(...);
app.get(...);
app.post(...);
```

As your project grows, this becomes difficult to understand.

Instead:

```text
app.js
   ↓
/api/v1/todos → todo.routes.js
                 ↓
              middleware
                 ↓
              controller
```

So `app.js` becomes the place where you **assemble the application**, while routers organize endpoint-specific behavior.

This matches the architecture direction in your starter pack.

---

# 20. Important: Middleware Scope

Let's compare the three scopes.

|Type|Example|Scope|
|---|---|---|
|Application|`app.use(logger)`|Broad application scope|
|Router|`router.use(authenticate)`|Routes inside that router|
|Route|`router.post("/", validate, controller)`|One specific route|

Think:

```text
Application
    │
    ├── Auth Router
    │      ├── login
    │      └── signup
    │
    └── Todo Router
           │
           ├── GET /
           ├── POST /
           └── DELETE /:id
```

Middleware can be attached at different levels depending on how widely it should apply.

---

# 21. When Should You Use Which?

A simple rule:

### Use application-level middleware when:

Almost every request needs it.

Examples:

```text
request ID
logging
JSON parsing
some security headers
```

### Use router-level middleware when:

A whole group of routes needs it.

Examples:

```text
authentication for all Todo routes
admin authentication for all admin routes
```

### Use route-level middleware when:

Only a particular operation needs it.

Examples:

```text
validateCreateTodo
validateTodoId
requireAdmin for one sensitive operation
```

# 22. Example: Admin Router

Suppose:

```text
/api/v1/admin
```

Everything inside it requires:

```text
authenticate
requireAdmin
```

You could do:

```js
const router = express.Router();

router.use(authenticate);
router.use(requireAdmin);

router.get("/users", getUsers);
router.delete("/users/:id", deleteUser);
router.patch("/users/:id/role", updateUserRole);
```

Now:

```text
/admin/users
       ↓
authenticate
       ↓
requireAdmin
       ↓
getUsers
```

and:

```text
/admin/users/:id
       ↓
authenticate
       ↓
requireAdmin
       ↓
deleteUser
```

This is much cleaner than repeating those middleware on every route.

---

# 23. But Don't Accidentally Protect Public Routes

Suppose your router contains:

```text
POST /login
POST /signup
GET /profile
```

If you do:

```js
router.use(authenticate);
```

before all three:

```text
authenticate
   ↓
login
```

That creates a problem.

Why?

Because the user needs to **log in before they have authentication credentials**.

So your router structure must reflect the actual requirements.

For example:

```js
router.post("/login", login);

router.post("/signup", signup);

router.use(authenticate);

router.get("/profile", getProfile);
```

Now:

```text
/login
   ↓
login

/signup
   ↓
signup

/profile
   ↓
authenticate
   ↓
getProfile
```

This is another example of why **middleware order and scope must be designed together**.

---

# 24. A Very Useful Mental Model

When designing middleware, ask:

> **"How many routes need this middleware?"**

If:

```text
90% of routes
```

→ application-level might make sense.

If:

```text
all Todo routes
```

→ router-level.

If:

```text
only POST /todos
```

→ route-level.

This simple question helps you decide where middleware belongs.

# 27. Common Mistakes

### ❌ Mistake 1 — Making everything global

Don't automatically do:

```js
app.use(authenticate);
```

if some routes need to remain public.

---

### ❌ Mistake 2 — Putting authentication on login

Don't do:

```js
router.use(authenticate);

router.post("/login", login);
```

unless you have a very specific reason.

Usually login is public.

---

### ❌ Mistake 3 — Repeating the same middleware unnecessarily

Instead of:

```js
router.get("/", authenticate, getTodos);

router.post("/", authenticate, createTodo);

router.delete("/:id", authenticate, deleteTodo);
```

you can often use:

```js
router.use(authenticate);

router.get("/", getTodos);
router.post("/", createTodo);
router.delete("/:id", deleteTodo);
```

if **all routes in that router** require authentication.

---

### ❌ Mistake 4 — Using router-level middleware when only one route needs it

If only:

```text
DELETE /todos/:id
```

needs admin access, don't necessarily protect the entire Todo router with admin authorization.

Use:

```js
router.delete(
    "/:id",
    authenticate,
    requireAdmin,
    deleteTodo
);
```

# 29. The Big Picture

You now have three levels:

```text
                 APPLICATION
                      │
                app.use(...)
                      │
                      ▼
                   ROUTER
                      │
                router.use(...)
                      │
                      ▼
                    ROUTE
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      middleware  middleware   controller
```

For your future MERN backend, you'll frequently build something like:

```text
app.js
 │
 ├── requestId
 ├── logger
 ├── security
 │
 ├── auth.routes
 │
 ├── user.routes
 │      └── authenticate
 │
 ├── todo.routes
 │      └── authenticate
 │             ├── validate
 │             └── controller
 │
 └── admin.routes
        ├── authenticate
        ├── requireAdmin
        └── controller
```

That's the architecture you should understand—not just memorize.

# ⭐ The Core Rule

When deciding where middleware belongs, ask:

```text
"Who needs this middleware?"
```

If the answer is:

```text
Almost everyone
        ↓
Application-level
```

If:

```text
One entire router
        ↓
Router-level
```

If:

```text
One particular endpoint
        ↓
Route-level
```

That one question will make middleware organization much easier.
