# Phase 7 — Lesson 7.9

## Application-Level Middleware

In **7.8**, you learned route-level middleware.

Now we're moving one level higher:

```text
7.8 → Route-level middleware
7.9 → Application-level middleware
```

Your starter roadmap specifically places **Application-Level Middleware** at 7.9.

The goal today is to understand:

> **Which middleware should run for a large part of the application, and why do we put it in `app.js`?**

---

# 1. First: What Does "Application-Level" Mean?

Application-level middleware is middleware registered directly on the Express application:

```js
app.use(middleware);
```

For example:

```js
app.use(logger);
```

This tells Express:

> "Use this middleware as part of the main application pipeline."

Compare that with route-level middleware:

```js
app.get("/profile", authenticate, getProfile);
```

So:

```text
Application-level
        ↓
app.use(...)

Route-level
        ↓
app.get(..., middleware, ...)
```

---

# 2. Think of Your Application as a Building

Imagine your backend is a building.

At the **main entrance**, everyone passes through:

```text
Building entrance
       ↓
Security camera
       ↓
Visitor counter
       ↓
Main building
```

These are like application-level middleware.

Then imagine a special room:

```text
Admin room
   ↓
Special security check
```

That's more like route-level or router-level middleware.

So:

```text
Application-level
→ applies broadly

Router-level
→ applies to a group

Route-level
→ applies to a specific endpoint
```

Your starter roadmap describes `app.js` as the place where Express is assembled. It eventually contains things such as security middleware, CORS, body parsing, cookies, request ID, logging, routes, 404 handling, and error handling.

Think of the final structure as:

```text
                    REQUEST
                       │
                       ▼
              ┌─────────────────┐
              │ Security        │
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ CORS            │
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ Body Parser     │
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ Cookies         │
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ Request ID      │
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ Logger          │
              └────────┬────────┘
                       ▼
                    ROUTES
                       │
                       ▼
                  CONTROLLER
                       │
                       ▼
                   RESPONSE
```

Don't worry about implementing all of these yet.

We're learning **why `app.js` has this structure**.

# 4. Your First Application-Level Middleware

Let's create:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);

    next();
};
```

Then:

```js
app.use(logger);
```

Now consider these routes:

```js
app.get("/health", healthController);

app.get("/users", getUsers);

app.get("/todos", getTodos);
```

The logger can participate in all of them:

```text
GET /health
    ↓
logger
    ↓
healthController
```

```text
GET /users
    ↓
logger
    ↓
getUsers
```

```text
GET /todos
    ↓
logger
    ↓
getTodos
```

That's the main idea.

---

# 5. Why Not Put Logger on Every Route?

Without application-level middleware:

```js
app.get("/health", logger, healthController);

app.get("/users", logger, getUsers);

app.get("/todos", logger, getTodos);
```

You're repeating:

```js
logger
```

everywhere.

With application-level middleware:

```js
app.use(logger);

app.get("/health", healthController);
app.get("/users", getUsers);
app.get("/todos", getTodos);
```

Much cleaner.

```text
app.use(logger)
      ↓
many routes can use it
```

---

# 6. Application-Level Middleware Is About Scope

This is the key idea from the last lesson.

Ask:

> **"How many parts of my application need this middleware?"**

If the answer is:

```text
Almost the entire application
```

application-level middleware may be appropriate.

Examples can include:

```text
request ID
logging
JSON body parsing
certain security middleware
CORS configuration
```

Your starter roadmap explicitly describes these kinds of concerns as part of the `app.js` assembly.

---

# 7. But `app.use()` Doesn't Mean "Absolutely Everything"

This is an important correction to a common beginner misunderstanding.

When you write:

```js
app.use(logger);
```

it doesn't mean:

> "Every possible thing in my application will definitely execute this middleware."

It means the middleware is placed into the application's processing chain at that point.

Requests that reach that point and match the middleware's scope can pass through it.

For example, later middleware can stop the request.

```text
Request
   ↓
logger
   ↓
authentication
   ↓
401
   ↓
STOP
```

So logger may run, but later processing doesn't.

---

# 8. Order Still Matters

Suppose:

```js
app.use(logger);

app.get("/users", getUsers);
```

The flow is:

```text
Request
   ↓
logger
   ↓
getUsers
```

But:

```js
app.get("/users", getUsers);

app.use(logger);
```

doesn't give you the same pipeline for that route.

The general rule remains:

> **Middleware participates according to where it is registered in the application.**

That's why `app.js` should be read from top to bottom.

---

# 9. A Simple `app.js`

Let's create a tiny application:

```js
import express from "express";

const app = express();

const logger = (req, res, next) => {
    console.log(req.method, req.url);
    next();
};

app.use(logger);

app.get("/health", (req, res) => {
    res.json({
        success: true
    });
});

app.get("/users", (req, res) => {
    res.json({
        users: []
    });
});

export default app;
```

The important part is:

```js
app.use(logger);
```

comes before the routes.

# 10. What Happens When `/users` Is Requested?

Client:

```http
GET /users
```

Express sees:

```text
Request
   ↓
logger
   ↓
/users route
   ↓
res.json()
   ↓
Client
```

Logger prints:

```text
GET /users
```

Then:

```js
next();
```

allows the `/users` route to run.

# 11. Application-Level Middleware Can Modify `req`

Let's create a request ID middleware:

```js
import crypto from "crypto";

const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    next();
};
```

Register it:

```js
app.use(requestId);
```

Now every applicable request gets:

```js
req.requestId
```

Then your route can use it:

```js
app.get("/users", (req, res) => {
    res.json({
        success: true,
        requestId: req.requestId
    });
});
```

Flow:

```text
Request
   ↓
requestId
   ↓
req.requestId created
   ↓
/users
   ↓
response
```

---

# 12. Why Request IDs Are Good at Application Level

Suppose your application has:

```text
100 routes
```

and you want every request to have an ID.

You don't want to write:

```js
router.get("/", requestId, ...);

router.post("/", requestId, ...);

router.get("/:id", requestId, ...);

router.patch("/:id", requestId, ...);
```

Instead:

```js
app.use(requestId);
```

Now your entire application can use:

```js
req.requestId
```

This is one reason application-level middleware is useful.

Your starter roadmap also calls out request IDs as part of the broader application middleware architecture.

---

# 13. Application-Level Middleware Can Modify `res`

Middleware can also prepare the response.

For example:

```js
const appVersion = (req, res, next) => {
    res.setHeader("X-App-Version", "1.0.0");

    next();
};
```

Then:

```js
app.use(appVersion);
```

Every applicable response can contain:

```http
X-App-Version: 1.0.0
```

Flow:

```text
Request
   ↓
appVersion
   ↓
response header prepared
   ↓
route
   ↓
response
```

---

# 14. `express.json()` Is Application-Level Middleware

You have probably already seen:

```js
app.use(express.json());
```

Now you can understand what it actually means.

`express.json()` creates middleware.

Then:

```js
app.use(...)
```

adds it to the application's middleware pipeline.

So:

```js
app.use(express.json());
```

means roughly:

```text
Incoming request
       ↓
JSON parser
       ↓
req.body
       ↓
route
```

We'll study `express.json()` deeply in **7.11**.

---

# 15. Why Body Parsing Should Usually Be Early

Suppose:

```js
app.post("/todos", (req, res) => {
    console.log(req.body);
});
```

If the incoming request contains JSON, the application needs a JSON parser before this route can use the parsed body.

So:

```js
app.use(express.json());

app.post("/todos", createTodo);
```

Flow:

```text
POST /todos
   ↓
express.json()
   ↓
req.body
   ↓
createTodo
```

This is another example of dependency-based ordering.

# 16. Application-Level CORS

Your starter architecture includes CORS as part of the application-level setup.

Conceptually:

```js
app.use(cors(...));
```

The idea is:

```text
Browser request
      ↓
CORS middleware
      ↓
Allowed?
      │
 ┌────┴─────┐
 │          │
YES         NO
 │          │
 ▼          ▼

```

We'll learn CORS properly in the Security phase.

For now, understand **why it is a good candidate for application-level configuration**:

> CORS is usually an application-wide HTTP policy, although its exact configuration can be scoped more narrowly when needed.

# 18. Not Everything Should Be Application-Level

This is equally important.

Suppose:

```text
GET /healthz
```

should be public.

But:

```text
DELETE /todos/:id
```

requires authentication.

You don't necessarily want:

```js

```

for the entire application.

Instead:

```text
Application-level
→ general concerns

→ endpoint-specific concerns
```

# 20. The `app.js` Responsibility

Your starter roadmap describes `app.js` as:

> **Where I assemble Express.**

That means `app.js` is not supposed to contain every piece of business logic.

Instead, it brings the pieces together.

Think:

```text
app.js
 │
 ├── Express
 ├── Middleware
 ├── Routes
 ├── 404 handler
 └── Error handler
```

While:

```text
controllers/
services/
repositories/
models/
```

contain the actual application implementation.

This separation becomes increasingly important as your project grows.

---

# 21. `app.js` vs `server.js`

Your starter roadmap specifically emphasizes this distinction.

### `app.js`

Creates and configures the Express application:

```js
const app = express();

app.use(...);
app.use(...);

app.use("/api/v1/users", userRoutes);

export default app;
```

### `server.js`

Starts the server:

```js
import app from "./app.js";

app.listen(PORT, () => {
    console.log(`Server running on ${PORT}`);
});
```

So:

```text
app.js
   ↓
Build application

server.js
   ↓
Start application
```

---

# 22. Why Separate Them?

This becomes very useful for testing.

Imagine you want to test:

```text
GET /healthz
```

You can import:

```js
import app from "./app.js";
```

without necessarily starting a real listening server yourself.

Later, tools such as Supertest can interact with the Express application directly.

So:

```text
app.js
→ application

server.js
→ runtime startup
```

This is a small architectural decision with a big benefit.

# 23. A Better `app.js` Example

Let's now create a small architecture:

```js
import express from "express";
import crypto from "crypto";

const app = express();

const requestId = (req, res, next) => {
    req.requestId = crypto.randomUUID();

    next();
};

const logger = (req, res, next) => {
    console.log(
        `[${req.requestId}] ${req.method} ${req.url}`
    );

    next();
};

app.use(express.json());

app.use(requestId);

app.use(logger);

app.get("/healthz", (req, res) => {
    res.json({
        success: true,
        requestId: req.requestId
    });
});

export default app;
```

Read this from top to bottom:

```text
1. Create Express app
        ↓
2. Parse JSON
        ↓
3. Create request ID
        ↓
4. Log request
        ↓
5. Routes
```

That's the mindset you need.

At this stage, use this mental checklist.

### Application-wide concerns

```text

✓ URL-encoded parsing
✓ CORS
✓ security middleware
✓ request ID
✓ logging
✓ routers
✓ 404 handling
```

Avoid putting large amounts of:


# 27. A Bad `app.js`

Avoid this:

```js

    // validate
    // check auth
    // query database
    // create todo
    // send email
    // generate logs
    // handle errors
    // send response
});
```

Now `app.js` becomes enormous.

Instead:

```js
app.use(requestId);

```

Then:

```text

    ↓

    ↓
controller
    ↓
service
    ↓
repository
```

Much cleaner.

# 31. Common Mistakes

### ❌ Mistake 1 — Putting everything in `app.js`

`app.js` should assemble the application, not become the entire application.

---

### ❌ Mistake 2 — Making authentication global without thinking

```js
app.use(authenticate);
```

can accidentally protect routes that should be public.

---

### ❌ Mistake 3 — Putting middleware after routes without understanding the consequence

```js
app.get("/users", getUsers);

app.use(logger);
```

may not give `/users` the middleware behavior you intended.

---

### ❌ Mistake 4 — Ignoring order

If:

```text
logger
```

depends on:

```text
requestId
```

then:

```text
requestId
 ↓
logger
```

must come first.

---

### ❌ Mistake 5 — Mixing application assembly with business logic

Avoid:

```js
app.post("/login", async (...) => {
    // 100 lines of authentication logic
});
```

Instead:

```text
Route
 ↓
Controller
 ↓
Service
 ↓
Repository
```

We'll learn those layers in later phases.
