# 8.1 — Why Backend Error Handling Is Different

Before writing `AppError.js`, `asyncHandler.js`, or `error.middleware.js`, we need to understand the problem.

Suppose you have:

```js
app.get("/users", (req, res) => {
    res.json({
        success: true,
        users: []
    });
});
```

Everything is fine.

But what happens when MongoDB fails?

```text
Client
  ↓
GET /users
  ↓
Controller
  ↓
Service
  ↓
MongoDB ❌
```

Your application needs to decide:

```text
What status code?
What message?
What JSON structure?
Should the error be logged?
Should stack trace be exposed?
Should the server crash?
```

That's why backend error handling is an **architecture problem**, not just a `try/catch` problem.

---

# 1. The beginner approach

You might initially write:

```js
app.get("/users", async (req, res) => {
    try {
        const users = await User.find();

        res.json({
            success: true,
            data: users
        });
    } catch (error) {
        res.status(500).json({
            success: false,
            message: error.message
        });
    }
});
```

This works.

But imagine 50 controllers.

You would have:

```js
try {
   ...
} catch (error) {
   ...
}
```

everywhere.

That's repetitive.

Worse, every developer might return errors differently.

One endpoint:

```json
{
    "message": "Something went wrong"
}
```

Another:

```json
{
    "error": "Database failed"
}
```

Another:

```json
{
    "success": false,
    "message": "User not found"
}
```

Your frontend becomes harder to maintain.

---

# 2. The professional approach

Instead, we centralize error handling.

```text
                 Controller
                     │
                     ▼
                Something
                 goes wrong
                     │
                     ▼
                  Error
                     │
                     ▼
              Error Handler
                     │
                     ▼
              Standard JSON
```

Now every endpoint can follow the same system.

For example:

```json
{
    "success": false,
    "message": "User not found",
    "requestId": "abc123"
}
```

---

# 3. Real-world analogy

Imagine a large company.

Every employee doesn't personally decide:

> "If something goes wrong, I'll invent my own reporting format."

Instead:

```text
Employee
   ↓
Reports problem
   ↓
Manager
   ↓
Central incident system
   ↓
Standard process
```

Your backend does something similar:

```text
Controller
   ↓
throw error
   ↓
Global Error Middleware
   ↓
Standard response
```

The **global error middleware is your central incident desk.**

---

# 4. Two types of errors we'll deal with

There are many classifications, but initially think about two major categories.

### Expected / operational error

Something that can reasonably happen during normal application operation.

Examples:

```text
User doesn't exist
Invalid password
Invalid input
Unauthorized request
Todo doesn't exist
Expired token
```

These should usually become controlled API responses.

For example:

```text
User not found
     ↓
404
```

---

### Unexpected programming error

Something the developer didn't expect.

Example:

```js
const user = undefined;

console.log(user.name);
```

This causes:

```text
TypeError
```

The backend shouldn't expose internal details to the client.

Instead:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

while the actual details can be logged internally.

# 6. First concept: `try/catch`

Let's start with normal JavaScript.

```js
try {
    const result = riskyOperation();

    console.log(result);
} catch (error) {
    console.log("Something went wrong");
}
```

The basic flow:

```text
try
 ↓
Execute code
 ↓
Error?
 ├── NO → continue
 │
 └── YES
       ↓
     catch
```

For example:

```js
try {
    JSON.parse("hello");
} catch (error) {
    console.log("Invalid JSON");
}
```

`JSON.parse("hello")` throws an error.

So:

```text
try
 ↓
JSON.parse()
 ↓
❌ Error
 ↓
catch
```

---

# 7. Important: `catch` receives the error

```js
try {
    throw new Error("Something went wrong");
} catch (error) {
    console.log(error);
}
```

`error` is an object.

It contains information such as:

```js
error.message
error.name
error.stack
```

For example:

```js
console.log(error.message);
```

might produce:

```text
Something went wrong
```

---

# 8. Why `try/catch` isn't enough

Consider:

```js
app.get("/users", async (req, res) => {
    const users = await User.find();

    res.json(users);
});
```

Suppose:

```js
User.find()
```

rejects.

The problem is that asynchronous operations use **Promises**.

So we need to understand:

```text
Synchronous error
```

versus:

```text
Asynchronous error
```

That's our next lesson.
