# Lesson 8.10 — Creating `AppError`

Now we're reaching one of the most important pieces of your backend error architecture.

In the previous lessons, we learned:

```text
async error
    ↓
rejected Promise
    ↓
asyncHandler
    ↓
next(error)
    ↓
error middleware
```

But there is still a problem:

> **How does our application tell the error middleware what HTTP status code to send?**

That's what `AppError` solves.

Your roadmap specifically places **Creating AppError** after Promise rejection and before operational/programming errors.

---

# 1. The problem with normal `Error`

JavaScript already gives us:

```js
throw new Error("User not found");
```

That's useful.

But an API needs more information.

For example:

```text
Message:
User not found

HTTP status:
404
```

Normal `Error` mainly gives us information such as:

```text
message
name
stack
```

It doesn't automatically know:

```text
404
401
400
409
500
```

So we need our own error class.

---

# 2. What we actually want

We want to be able to write:

```js
throw new AppError("User not found", 404);
```

and have an object conceptually like:

```text
AppError
├── message: "User not found"
├── statusCode: 404
├── name: "AppError"
└── stack: ...
```

Then our error middleware can do:

```js
res.status(err.statusCode).json(...)
```

That's the basic idea.

---

# 3. Why not just do this?

We could technically write:

```js
const error = new Error("User not found");

error.statusCode = 404;

throw error;
```

This works.

But imagine doing this throughout your application:

```js
const error = new Error("User not found");
error.statusCode = 404;
throw error;
```

Then:

```js
const error = new Error("Unauthorized");
error.statusCode = 401;
throw error;
```

Then:

```js
const error = new Error("Todo already exists");
error.statusCode = 409;
throw error;
```

We're repeating ourselves.

A custom class gives us a reusable structure.

---

# 4. What is a class?

Before `AppError`, let's quickly understand classes.

You already know:

```js
const user = {
    name: "Rahul"
};
```

A class lets us define a reusable blueprint.

For example:

```js
class User {
    constructor(name) {
        this.name = name;
    }
}
```

Now:

```js
const user = new User("Rahul");
```

The object becomes:

```text
User
└── name: Rahul
```

Similarly, we'll create:

```js
class AppError {
    ...
}
```

and then:

```js
new AppError(...)
```

creates an error object.

---

# 5. But `AppError` should be an Error

This is very important.

We don't want:

```js
class AppError {
}
```

We want:

```js
class AppError extends Error {
}
```

Why?

Because `Error` already provides useful error behavior:

```text
message
stack
name
```

We're extending it with our application-specific information.

So:

```text
JavaScript Error
       ↓
    AppError
       ↓
statusCode
isOperational
...
```

This is called **inheritance**.

---

# 6. What does `extends Error` mean?

When we write:

```js
class AppError extends Error {
}
```

we're saying:

> `AppError` is a specialized version of `Error`.

Therefore:

```js
const error = new AppError("Something failed");
```

is still an Error.

Conceptually:

```text
AppError
   ↑
   │
inherits
   │
Error
```

This is important because existing error-handling mechanisms can still treat it as an error.

---

# 7. The constructor

Our first version:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
    }
}
```

Let's not copy this yet.

Let's understand every piece.

---

# 8. `constructor()`

The constructor runs when we do:

```js
new AppError(...)
```

For example:

```js
new AppError("User not found", 404);
```

The constructor receives:

```text
message → "User not found"
statusCode → 404
```

So:

```js
constructor(message, statusCode) {
}
```

means:

> When someone creates an `AppError`, give me the message and status code.

---

# 9. Why `super(message)`?

This is one of the most important lines:

```js
super(message);
```

Because we're extending:

```js
Error
```

we need to initialize the parent `Error` class.

Remember:

```js
class AppError extends Error
```

means:

```text
AppError
   ↓
Error
```

`super()` calls the parent constructor.

So:

```js
super(message);
```

essentially tells `Error`:

> "Initialize yourself using this message."

Then:

```js
error.message
```

works.

---

# 10. What happens without `super()`?

If you write:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        this.statusCode = statusCode;
    }
}
```

JavaScript will complain.

When extending a class, the derived class must initialize the parent using:

```js
super(...)
```

before using `this`.

So remember:

```text
extends Error
     ↓
constructor()
     ↓
super(message)
     ↓
this.statusCode = ...
```

---

# 11. Add `statusCode`

After:

```js
super(message);
```

we can add:

```js
this.statusCode = statusCode;
```

Now:

```js
const error = new AppError(
    "User not found",
    404
);
```

gives:

```text
error.message
→ "User not found"

error.statusCode
→ 404
```

Exactly what we need.

---

# 12. Our first complete `AppError`

Now:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
    }
}

export default AppError;
```

Put this in:

```text
src/
└── utils/
    └── AppError.js
```

# 14. Why `instanceof Error` matters

This:

```js
error instanceof Error
```

lets us determine whether something is an Error object.

Since:

```js
AppError extends Error
```

an `AppError` is also an `Error`.

That's useful when your global error middleware needs to distinguish expected application errors from unknown errors.

We'll use that idea more deeply later.

---

# 15. Add `name`

We can make the error easier to identify:

```js
this.name = "AppError";
```

So:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.name = "AppError";
        this.statusCode = statusCode;
    }
}
```

Now:

```js
console.log(error.name);
```

gives:

```text
AppError
```

---

# 16. Why do we need `name`?

JavaScript's normal Error has:

```js
error.name
```

which is usually:

```text
Error
```

Our custom error can say:

```text
AppError
```

This becomes useful when debugging.

For example:

```text
Error: Database connection failed

AppError: User not found
```

You can immediately see the difference.

---

# 17. Now connect it to your controller

Imagine:

```js
const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    res.json({
        success: true,
        data: user
    });
});
```

This is much better than:

```js
throw new Error("User not found");
```

because the application now knows:

```text
message = User not found
statusCode = 404
```

---

# 18. Follow the error

Let's trace it carefully.

The controller executes:

```js
throw new AppError("User not found", 404);
```

Because the controller is async:

```text
throw
 ↓
Promise rejected
```

Then:

```text
asyncHandler
 ↓
.catch(next)
```

Then:

```text
next(error)
```

Then:

```text
error middleware
```

And finally:

```js
res.status(error.statusCode)
```

So:

```text
AppError
   ↓
asyncHandler
   ↓
next(error)
   ↓
error middleware
   ↓
404
```

---

# 19. This is why `AppError` and `asyncHandler` are different

Don't mix them up.

### `AppError`

Creates a meaningful error:

```js
new AppError("User not found", 404)
```

### `asyncHandler`

Catches async errors:

```js
.catch(next)
```

### Error middleware

Sends the HTTP response:

```js
res.status(...)
```

Think:

```text
              AppError
                 │
             "What happened?"
                 │
                 ▼
            asyncHandler
                 │
             "Forward it."
                 │
                 ▼
          error middleware
                 │
             "Respond."
```

---

# 20. Why not send the response from `AppError`?

Don't do this:

```js
class AppError extends Error {
    constructor(message, statusCode, res) {
        super(message);

        res.status(statusCode).json(...);
    }
}
```

That's a bad separation of responsibilities.

`AppError` should represent an error.

It shouldn't know about:

```text
Express
res
HTTP
JSON
```

Keep it independent.

---

# 21. Why this separation is powerful

Your service could throw:

```js
throw new AppError("Email already exists", 409);
```

The service doesn't need to know:

```text
How will Express respond?
```

The controller doesn't need to know:

```text
How should errors be formatted?
```

The error middleware handles that.

This keeps your layers independent.

---

# 22. Add `isOperational`

Now we introduce another important property from the roadmap:

```js
this.isOperational = true;
```

So:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.name = "AppError";
        this.statusCode = statusCode;
        this.isOperational = true;
    }
}
```

What does this mean?

It means:

> **This error is an expected application-level failure.**

Examples:

```text
User not found
Invalid credentials
Email already exists
Invalid input
Unauthorized
Forbidden
```

These aren't necessarily bugs in our program.

They're conditions the application expects can happen.

---

# 23. Operational error example

Suppose:

```js
const user = await userRepository.findById(id);

if (!user) {
    throw new AppError("User not found", 404);
}
```

A user not existing isn't necessarily a programming bug.

It's a normal possibility in an API.

So:

```text
User not found
     ↓
Operational error
```

---

# 24. Programming error example

Now imagine:

```js
const user = await userRepository.findById(id);

console.log(user.profile.name);
```

But:

```text
user.profile
```

is `undefined`.

You might get:

```text
Cannot read properties of undefined
```

That's very different.

It might indicate:

```text
bug in application code
```

rather than:

```text
expected user input condition
```

That's closer to a **programming error**.

---

# 25. Why distinguish them?

Because you may want different behavior.

### Operational error

```text
Expected
↓
Safe to expose useful message
↓
Log appropriately
↓
Return controlled response
```

### Programming error

```text
Unexpected
↓
Investigate
↓
Log stack trace
↓
Don't expose internal details
```

This distinction becomes important in production.

Your roadmap specifically follows `AppError` with **Operational vs programming errors**, so we'll go deeper into this in Lesson 8.11.

---

# 26. What should the client see?

Suppose:

```js
throw new AppError(
    "User not found",
    404
);
```

The client might receive:

```json
{
    "success": false,
    "message": "User not found"
}
```

But suppose the database throws:

```text
MongoServerError:
E11000 duplicate key error...
```

You probably don't want to expose the entire internal database error to the client.

Instead:

```json
{
    "success": false,
    "message": "Something went wrong"
}
```

This is one reason centralized error handling is powerful.

---

# 27. Our `AppError` doesn't decide that

Important:

`AppError` doesn't decide whether to show:

```text
User not found
```

or:

```text
Something went wrong
```

It only carries information:

```text
message
statusCode
isOperational
```

The error middleware decides how much information is safe to expose.

---

# 28. The complete version

For your current architecture, we'll use:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.name = "AppError";
        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}

export default AppError;
```

Don't worry if this final line looks unfamiliar.

Let's understand it next.

---

# 29. What is `Error.captureStackTrace()`?

When an error occurs, JavaScript can give us a stack trace:

```text
Error: User not found
    at getUser (...)
    at ...
    at ...
```

This helps us find:

> Where did the error happen?

`Error.captureStackTrace()` helps create a clean stack trace for our custom error.

```js
Error.captureStackTrace(this, this.constructor);
```

means roughly:

> Capture the stack trace for this custom error and start it from the appropriate constructor boundary.

For now, you don't need to memorize the internals.

Just understand:

```text
AppError
   ↓
has useful stack trace
```

---

# 30. Is `Error.captureStackTrace()` mandatory?

No.

Your basic class works without it:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);
        this.statusCode = statusCode;
    }
}
```

But it's a common enhancement when creating custom error classes in Node.js.

So learn it as:

```text
optional improvement
```

rather than:

```text
magic line you must memorize
```

# 33. Don't overuse `AppError`

This is important.

Don't write:

```js
try {
    await database();
} catch (error) {
    throw new AppError(error.message, 500);
}
```

for every error.

Why?

Because you're potentially hiding useful information and unnecessarily converting every low-level error.

Instead, use `AppError` when you intentionally want to create a known application-level error.

For example:

```js
if (!user) {
    throw new AppError("User not found", 404);
}
```

That's a good use.

# 38. `AppError` vs `Error`

Let's make this crystal clear.

### Generic error

```js
throw new Error("Something failed");
```

Good when:

> Something unexpected happened.

### Application error

```js
throw new AppError(
    "User not found",
    404
);
```

Good when:

> The application intentionally wants to report a known failure condition.

---

# 39. One subtle but important point

`isOperational = true` does **not** magically make an error safe.

It is simply a flag your error-handling architecture can use.

For example:

```js
if (err.isOperational) {
    // controlled application error
} else {
    // unexpected error
}
```

The actual security behavior still depends on your error middleware.

# 43. Common Mistakes

### ❌ Mistake 1

```js
class AppError {
}
```

You're no longer extending JavaScript's Error.

---

### ❌ Mistake 2

Forgetting:

```js
super(message);
```

When extending `Error`, initialize the parent class.

---

### ❌ Mistake 3

Doing:

```js
this.status = statusCode;
```

and later expecting:

```js
err.statusCode
```

Pick one property name and stay consistent.

For your architecture:

```js
statusCode
```

is the clearer choice.

---

### ❌ Mistake 4

Putting Express logic inside `AppError`:

```js
res.status(...)
```

Don't.

`AppError` should represent the error, not send the response.

---

### ❌ Mistake 5

Returning database internals directly to users.

For example:

```js
res.json(err);
```

Don't blindly expose the entire error object.

It may contain:

```text
stack traces
database details
internal paths
implementation details
```

The global error middleware should control what reaches the client.

# 🧠 The Mental Model

Don't memorize the class first.

Understand **why it exists**:

```text
Normal JavaScript Error
        │
        │
        ├── message
        ├── name
        └── stack
```

But an API needs:

```text
Application Error
        │
        ├── message
        ├── statusCode
        ├── isOperational
        ├── name
        └── stack
```

So:

```text
             Error
               ▲
               │
            extends
               │
            AppError
               │
       ┌───────┼────────┐
       ▼       ▼        ▼
    message statusCode isOperational
```

Then:

```text
AppError
   ↓
throw
   ↓
Promise rejection
   ↓
asyncHandler
   ↓
next(error)
   ↓
global error middleware
   ↓
HTTP response
```

### The one sentence to remember

> **`AppError` is a custom `Error` class that lets your application attach meaningful information—especially an HTTP status code—to expected application-level failures.**
