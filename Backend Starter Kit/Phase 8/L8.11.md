# Lesson 8.11 — Operational vs Programming Errors

This lesson is very important because now we move from:

> **"How do I catch errors?"**

to:

> **"What kind of error is this, and how should my backend react to it?"**

Our Phase 8 roadmap explicitly places **Operational vs Programming Errors** after `AppError`, before HTTP status codes and the global error architecture.

---

# 1. Not every error means your code is broken

Suppose your API receives:

```http
GET /api/v1/users/123
```

and user `123` doesn't exist.

Is your program broken?

**No.**

A user not existing is a normal situation that your application should be prepared for.

You might intentionally write:

```js
throw new AppError("User not found", 404);
```

That's an expected application failure.

---

Now imagine this:

```js
const user = await userRepository.findById(id);

console.log(user.profile.name);
```

But `user.profile` is unexpectedly `undefined`.

JavaScript may produce:

```text
Cannot read properties of undefined
```

That could indicate a bug in your code.

These two errors are fundamentally different.

---

# 2. Two broad categories

Think of errors as:

```text
                    ERROR
                      │
             ┌────────┴────────┐
             │                 │
       Operational        Programming
          Error               Error
             │                 │
       Expected failure    Unexpected bug
```

### Operational error

> Something went wrong, but the application can reasonably expect this situation.

### Programming error

> Something went wrong because the application code, assumptions, or implementation is incorrect.

---

# 3. Operational errors

Examples:

```text
User not found
Invalid password
Email already registered
Invalid request
Authentication required
Permission denied
Database temporarily unavailable
External API unavailable
```

These can happen even when your code is working correctly.

---

# 4. Example: User not found

Suppose:

```js
const user = await userRepository.findById(userId);

if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

This is an operational error.

Why?

Because your application intentionally handles this possibility.

```text
Request
   ↓
Search user
   ↓
User doesn't exist
   ↓
Expected condition
   ↓
AppError
   ↓
404
```

---

# 5. Example: Invalid password

Suppose a user enters:

```text
Email: rahul@example.com
Password: wrong-password
```

Your service might do:

```js
if (!isPasswordCorrect) {
    throw new AppError(
        "Invalid email or password",
        401
    );
}
```

Again:

```text
Wrong password
     ↓
Expected possibility
     ↓
Operational error
```

Your application isn't broken.

A user simply provided invalid credentials.

---

# 6. Example: Duplicate email

Suppose:

```text
POST /auth/signup
```

with:

```json
{
    "email": "rahul@example.com"
}
```

but the email already exists.

You might intentionally respond:

```text
409 Conflict
```

Conceptually:

```js
throw new AppError(
    "Email already exists",
    409
);
```

Again:

```text
Expected business condition
        ↓
Operational error
```

---

# 7. Programming errors

Now consider:

```js
const user = await userRepository.findById(id);

console.log(user.name);
```

If `user` is `null`, you'll get:

```text
Cannot read properties of null
```

Maybe you forgot to check:

```js
if (!user) {
    ...
}
```

That's potentially a programming error.

The problem isn't:

> "The user doesn't exist."

The problem is:

> "Our code incorrectly assumed that the user always exists."

---

# 8. Another programming error

Imagine:

```js
const calculateTotal = (price, quantity) => {
    return price * quantity;
};
```

Then somewhere else:

```js
calculateTotal();
```

You may get:

```text
NaN
```

or another unexpected result.

This might indicate incorrect use of the function or missing validation.

Again:

```text
Bug / incorrect assumption
        ↓
Programming error
```

---

# 9. Another example: Typo

Imagine:

```js
const user = await getUser();

console.log(user.nmae);
```

You intended:

```js
user.name
```

but wrote:

```js
user.nmae
```

This isn't a normal business situation.

It's simply a bug.

---

# 10. The biggest difference

Remember this:

### Operational error

```text
"The application encountered a problem
that can reasonably happen during normal operation."
```

### Programming error

```text
"The application did something it shouldn't
have done because of a bug or bad assumption."
```

---

# 11. A useful real-world analogy

Imagine a restaurant.

### Operational error

A customer says:

> "We're out of the dish I ordered."

That's unfortunate, but the restaurant can handle it:

```text
Sorry → choose another dish
```

### Programming error

The chef accidentally mixes salt into the dessert because of a mistake in the recipe.

That's a process/programming problem.

The restaurant needs to investigate:

> "Why did this happen?"

---

# 12. Why does `AppError` help?

Remember our class:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.name = "AppError";
        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}
```

The important part for today's lesson is:

```js
this.isOperational = true;
```

So:

```js
throw new AppError(
    "User not found",
    404
);
```

creates something conceptually like:

```text
AppError
├── message: "User not found"
├── statusCode: 404
└── isOperational: true
```

That flag tells our error architecture:

> "This is an expected application-level error."

---

# 13. Programming errors usually don't need `AppError`

Suppose you have:

```js
const user = await userRepository.findById(id);

console.log(user.profile.name);
```

and something unexpectedly crashes.

Don't automatically do this:

```js
throw new AppError(
    "Cannot read properties of undefined",
    500
);
```

That hides the real nature of the problem.

You want to know:

```text
Why did user.profile become undefined?
```

That's something developers should investigate.

---

# 14. Why blindly converting everything to `AppError` is bad

Imagine this:

```js
try {
    const user = await userRepository.findById(id);
} catch (error) {
    throw new AppError(error.message, 500);
}
```

You might think:

> "Great! Now everything is an AppError."

But you've lost an important distinction.

You turned:

```text
unexpected internal failure
```

into:

```text
operational application error
```

That can make debugging and production monitoring harder.

---

# 15. Don't expose programming errors

Suppose your database produces:

```text
MongoServerError:
E11000 duplicate key error collection...
```

or Node produces:

```text
TypeError:
Cannot read properties of undefined...
```

You don't want your frontend receiving:

```json
{
    "success": false,
    "message": "TypeError: Cannot read properties of undefined at /home/rahul/project/src/..."
}
```

That exposes internal information.

Instead, production responses should generally be controlled:

```json
{
    "success": false,
    "message": "Something went wrong"
}
```

while the **server logs the real error** for developers.

---

# 16. Operational error response

For:

```js
throw new AppError(
    "User not found",
    404
);
```

the client can safely receive:

```json
{
    "success": false,
    "message": "User not found"
}
```

because this is an intentional application-level message.

---

# 17. Programming error response

For something unexpected like:

```text
TypeError: Cannot read properties of undefined
```

the client should generally get something generic:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

while your server logs:

```text
TypeError: Cannot read properties of undefined
    at user.service.js:42
    ...
```

So:

```text
CLIENT
  ↓
safe information

SERVER LOG
  ↓
detailed information
```

This separation is extremely important.

---

# 18. How the error middleware can use `isOperational`

Eventually, your global error middleware can conceptually do:

```js
const errorMiddleware = (err, req, res, next) => {
    if (err.isOperational) {
        return res.status(err.statusCode).json({
            success: false,
            message: err.message
        });
    }

    console.error(err);

    return res.status(500).json({
        success: false,
        message: "Internal server error"
    });
};
```

Now we have two paths:

```text
                    ERROR
                      │
              ┌───────┴────────┐
              │                │
       isOperational?        No
              │                │
             Yes               │
              │                │
              ▼                ▼
        Safe message       Log details
              │                │
              ▼                ▼
           4xx/5xx             500
```

This is the basic idea.

---

# 19. But `isOperational` isn't magic

Very important:

```js
isOperational = true
```

doesn't automatically mean:

> "This error is definitely safe."

It's simply metadata that **your error architecture uses**.

Your global error middleware still decides:

```text
What gets logged?
What gets exposed?
What status code is returned?
```

# 20. Where does MongoDB fit?

This gets interesting.

Suppose MongoDB becomes temporarily unavailable.

```text
Application
     ↓
MongoDB
     X
connection failed
```

Your application didn't necessarily contain a programming bug.

The database may simply be unavailable.

That can be treated as an operational/runtime failure.

For example:

```text
Database unavailable
        ↓
503 Service Unavailable
```

The exact handling depends on your architecture.

The important idea is:

> **External systems can fail even when your code is correct.**

---

# 21. External API failure

Imagine your application calls:

```text
Payment API
```

and the payment provider is temporarily unavailable.

Your code might be completely correct.

But:

```text
Payment API
     ↓
503
```

Your application has to handle that failure.

This is another example of an operational failure.

---

# 22. Network failure

Same idea:

```text
Your server
     ↓
Network
     X
```

Maybe DNS fails.

Maybe another service is down.

Maybe a timeout occurs.

These aren't necessarily bugs in your code.

They're runtime conditions your application needs to handle gracefully.

---

# 23. Business errors are usually operational

Think about:

```text
User not found
Email already exists
Insufficient balance
Todo doesn't belong to user
Invalid password
Token expired
Resource already deleted
```

These are generally part of normal application behavior.

You should design for them.

---

# 24. Programming errors require investigation

Examples:

```text
TypeError
ReferenceError
incorrect assumptions
wrong variable
wrong function call
unexpected undefined/null
logic bug
incorrect database query
```

These deserve developer attention.

The goal isn't merely:

```text
"Send 500"
```

The goal is:

> **Find and fix the underlying bug.**

---

# 25. A very important production principle

Never use:

```js
try {
    ...
} catch (error) {
    res.status(500).json({
        message: error.message
    });
}
```

as your entire error strategy.

Why?

Because:

```text
error.message
```

might expose:

```text
database details
file paths
stack information
library internals
configuration information
```

Instead:

```text
Expected error
     ↓
safe response

Unexpected error
     ↓
generic response
     +
detailed server log
```

       ↓

# 28. What if the repository itself breaks?

Suppose:

```js
const findById = async (id) => {
    return User.findById(id);
};
```

and MongoDB unexpectedly fails.

The repository doesn't necessarily need to catch and convert it.

Let the error propagate:

```text
MongoDB error
    ↓
Repository
    ↓
Service
    ↓
Controller
    ↓
asyncHandler
    ↓
error middleware
```

Your centralized error middleware can decide how to respond.

---

# 29. Don't confuse "operational" with "client's fault"

This is another subtle point.

An operational error doesn't necessarily mean:

> "The user did something wrong."

For example:

```text
Database unavailable
Payment provider unavailable
Network timeout
```

can also be operational errors.

So think:

```text
Operational
=
Expected runtime failure
```

not:

```text
Operational
=
User mistake
```

---

# 30. Don't confuse programming errors with server errors

A programming error often produces:

```text
HTTP 500
```

but:

> **HTTP 500 doesn't mean every 500 error is necessarily a programming bug.**

For example, an unexpected external dependency failure may also lead to a 500/503-type response depending on your design.

HTTP status codes describe the **API response**.

Operational/programming classification describes the **nature of the underlying failure**.

These are related but not identical concepts.

# 🧠 The most important mental model

Remember this:

```text
                SOMETHING FAILED
                       │
             ┌─────────┴─────────┐
             │                   │
        Expected/runtime      Unexpected bug
             │                   │
       Operational           Programming
             │                   │
        AppError often       Error/TypeError/etc.
             │                   │
       Safe response         Generic response
             │                   │
          4xx/5xx                500
             │                   │
             └─────────┬─────────┘
                       ▼
               Global Error Handler
```

And the practical rule:

> **Operational errors are conditions your application should handle. Programming errors are problems developers should investigate and fix.**
