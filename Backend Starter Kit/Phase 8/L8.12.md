You already understand:

```text

```

But one question remains:

> **What status code should the API return?**

Your Phase 8 roadmap places **HTTP Status Codes** here, followed by consistent error responses and global error middleware.

---

# 1. What is an HTTP status code?

Whenever your backend responds to a request, it sends a status code.

For example:

```http
HTTP/1.1 200 OK
```

or:

```http
HTTP/1.1 404 Not Found
```

The status code tells the client the **general result of the request**.

Think:

```text
HTTP Response
├── Status Code
├── Headers
└── Body
```

For example:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "success": true,
  "message": "User created"
}
```

---

# 2. Status codes are grouped into five categories

The first digit is important:

```text
1xx → Informational
2xx → Success
3xx → Redirection
4xx → Client/request problem
5xx → Server-side problem
```

For backend API development, you'll mostly work with:

```text
2xx
4xx
5xx
```

---

# 3. The most important codes for your MERN backend

You should become comfortable with these:

```text
200 OK
201 Created
204 No Content

400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests

500 Internal Server Error
503 Service Unavailable
```

You don't need to memorize hundreds of HTTP status codes.

These cover a huge portion of normal REST API work.

---

# 4. `200 OK`

Use `200` when a request succeeded and you're returning a response.

Example:

```http
GET /api/v1/users/123
```

User exists:

```http
200 OK
```

Response:

```json
{
  "success": true,
  "message": "User fetched successfully",
  "data": {
    "id": "123",
    "name": "Rahul"
  }
}
```

---

# 5. GET usually uses `200`

For:

```http
GET /api/v1/todos
```

you might return:

```http
200 OK
```

with:

```json
{
  "success": true,
  "data": [
    {
      "id": "1",
      "title": "Learn Express"
    }
  ]
}
```

Even if there are **zero todos**, the request itself can still be successful:

```json
{
  "success": true,
  "data": []
}
```

Don't automatically return `404` just because a list is empty.

---

# 6. `201 Created`

Use `201` when a new resource has been successfully created.

For example:

```http
POST /api/v1/todos
```

Request:

```json
{
  "title": "Learn Docker"
}
```

Response:

```http
201 Created
```

```json
{
  "success": true,
  "message": "Todo created successfully",
  "data": {
    "id": "abc123",
    "title": "Learn Docker"
  }
}
```

Mental model:

```text
POST
 ↓
Created something new
 ↓
201
```

---

# 7. `200` vs `201`

This is a common interview question.

### `200`

> Request succeeded.

### `201`

> Request succeeded **and created a new resource**.

For example:

```text
GET /users/1
→ 200

POST /users
→ 201
```

---

# 8. `204 No Content`

`204` means:

> The request succeeded, but there is no response body.

For example:

```http
DELETE /api/v1/todos/123
```

If deletion succeeds:

```http
204 No Content
```

There is no JSON body.

So don't do:

```js
res.status(204).json({
    success: true
});
```

A `204` response should not contain a response body.

You can instead:

```js
res.status(204).send();
```

---

# 9. `400 Bad Request`

`400` generally means:

> The request is malformed or invalid.

Example:

```http
POST /users
```

with invalid request data:

```json
{
  "email": "not-an-email"
}
```

You might return:

```http
400 Bad Request
```

```json
{
  "success": false,
  "message": "Invalid email"
}
```

This is especially common for basic request validation failures.

---

# 10. Don't think 400 means "anything went wrong"

This is important.

Don't do:

```js
catch (error) {
    return res.status(400).json(...);
}
```

for every error.

A database failure isn't automatically:

```text
400
```

A JWT problem isn't automatically:

```text
400
```

A server bug isn't:

```text
400
```

The status code should describe the actual situation.

---

# 11. `401 Unauthorized`

Despite the name, `401` is primarily about **authentication**.

Think:

> "I don't know who you are / your authentication isn't valid."

Examples:

```text
No access token
Invalid access token
Expired access token
Invalid credentials
```

Example:

```http
GET /api/v1/profile
```

without authentication:

```http
401 Unauthorized
```

Response:

```json
{
  "success": false,
  "message": "Authentication required"
}
```

---

# 12. `401` = Authentication

Remember:

```text
401
 ↓
WHO ARE YOU?
```

Examples:

```text
Missing JWT
Invalid JWT
Expired JWT
Invalid login credentials
```

This is different from authorization.

---

# 13. `403 Forbidden`

`403` generally means:

> I know who you are, but you're not allowed to do this.

Imagine:

```text
User
 ↓
Authenticated
 ↓
Trying to access admin endpoint
 ↓
Not an admin
```

Return:

```http
403 Forbidden
```

Example:

```json
{
  "success": false,
  "message": "You do not have permission to perform this action"
}
```

---

# 14. `401` vs `403`

This is one of the most important distinctions.

### 401

```text
Authentication problem
```

### 403

```text
Authorization problem
```

Think:

```text
401 → WHO ARE YOU?

403 → I KNOW WHO YOU ARE,
      BUT YOU CAN'T DO THIS.
```

---

# 15. Example

Imagine:

```http
DELETE /api/v1/users/123
```

### No token

```text
401
```

Because:

> We don't know who you are.

### Valid user token but normal user

```text
403
```

Because:

> We know who you are, but you're not allowed to delete users.

---

# 16. `404 Not Found`

This means:

> The requested resource couldn't be found.

Example:

```http
GET /api/v1/users/999
```

if user `999` doesn't exist:

```http
404 Not Found
```

Response:

```json
{
  "success": false,
  "message": "User not found"
}
```

This is one of the classic operational errors from the previous lesson.

---

# 17. `404` isn't just for users

It can apply to:

```text
User not found
Todo not found
Post not found
Comment not found
Order not found
Route not found
```

For example:

```http
GET /api/v1/todos/abc
```

```text
404
```

if that Todo doesn't exist.

---

# 18. `409 Conflict`

`409` is useful when:

> The request conflicts with the current state of the resource.

A classic example:

```text
Email already exists
```

Signup:

```http
POST /api/v1/auth/signup
```

```json
{
  "email": "rahul@example.com"
}
```

but the email already belongs to another user.

You might return:

```http
409 Conflict
```

```json
{
  "success": false,
  "message": "Email already exists"
}
```

---

# 19. Other examples of `409`

Potential situations:

```text
Username already exists
Duplicate resource
Resource state conflict
Trying to perform an operation incompatible with current state
```

Mental model:

```text
Request is understandable
        ↓
But it conflicts with current state
        ↓
409
```

---

# 20. `422 Unprocessable Content`

`422` is commonly used when:

> The request format is valid, but the data doesn't satisfy the application's validation rules.

For example:

```json
{
  "email": "rahul@example.com",
  "age": -5
}
```

The JSON itself is valid.

But:

```text
age = -5
```

is invalid according to your application's rules.

You may return:

```http
422 Unprocessable Content
```

with:

```json
{
  "success": false,
  "message": "Age must be greater than 0"
}
```

---

# 21. `400` vs `422`

This can be confusing because different APIs use them differently.

A practical approach:

### `400`

The request itself is malformed or broadly invalid.

Example:

```text
Malformed JSON
Missing required request structure
Invalid query format
```

### `422`

The request is structurally understandable, but validation/business rules reject the submitted values.

Example:

```text
Invalid email
Password too short
Age outside allowed range
```

However:

> **There is no universal rule that every validation error must be 422.**

Your API should choose a consistent convention.

For your learning project, either can work if you use it consistently.

---

# 22. `429 Too Many Requests`

This one becomes especially important when you learn security middleware.

`429` means:

> The client has sent too many requests in a given period.

Example:

```text
Login attempts
1
2
3
4
5
...
```

After exceeding the configured rate limit:

```http
429 Too Many Requests
```

Response:

```json
{
  "success": false,
  "message": "Too many requests. Please try again later."
}
```

---

# 23. Where will `429` appear in your starter?

Later, in Phase 10, you'll learn:

```text
Rate limiting
Brute-force protection
Authentication rate limiting
```

Your starter contains security middleware such as rate limiting, so `429` will become a very practical status code there.

---

# 24. `500 Internal Server Error`

This is the big one.

`500` generally means:

> Something unexpected went wrong on the server.

For example:

```text
Unexpected TypeError
Unexpected application failure
Unhandled internal error
```

The client should usually receive something generic:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

while the server logs the actual details.

---

# 25. Never expose stack traces in production

Bad:

```json
{
  "success": false,
  "message": "TypeError: Cannot read properties of undefined at /home/rahul/project/src/services/user.service.js:42"
}
```

Good:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

Server log:

```text
TypeError: Cannot read properties of undefined
    at user.service.js:42
    ...
```

This connects directly to the operational/programming error distinction from Lesson 8.11.

---

# 26. `503 Service Unavailable`

`503` generally means:

> The server is temporarily unable to handle the request.

Common examples:

```text
Database unavailable
External dependency unavailable
Service temporarily overloaded
Maintenance
```

For example:

```text
Node API
   ↓
MongoDB
   X
unavailable
```

You might choose:

```http
503 Service Unavailable
```

depending on your application's design.

---

# 27. `500` vs `503`

A useful mental model:

### 500

```text
Unexpected internal application failure
```

### 503

```text
Service temporarily unavailable
```

Example:

```text
Programming bug
→ 500
```

Potentially:

```text
Required database/service temporarily unavailable
→ 503
```

Again, the exact choice depends on your system design.

# 32. One important security detail

Suppose:

```http
GET /users/123
```

and user `123` exists but belongs to another user.

You could return:

```text
403 Forbidden
```

which reveals:

> User 123 exists.

Or your API could deliberately behave as if the resource doesn't exist:

```text
404 Not Found
```

This can reduce information leakage.

So status-code selection isn't always just:

> "Find the definition and use it."

Sometimes it is also a **security decision**.

You'll encounter this much more deeply during authorization and security testing.

---

# 33. Don't create status-code spaghetti

Avoid code like:

```js
if (condition1) {
    return res.status(400)...
}

if (condition2) {
    return res.status(401)...
}

if (condition3) {
    return res.status(409)...
}

if (condition4) {
    return res.status(500)...
}
```

all over your services.

Instead, your architecture should gradually become:

```text
Service
   ↓
throw AppError
   ↓
asyncHandler
   ↓
global error middleware
   ↓
status code
```

For example:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

The service doesn't need to know how the HTTP response is constructed.

# 35. Mini Project

Let's build a tiny error API.

### `AppError.js`

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.name = "AppError";
        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}

export default AppError;
```

### Controller

```js
const testErrors = async (req, res) => {
    throw new AppError(
        "User not found",
        404
    );
};
```

### Error middleware

```js
const errorMiddleware = (err, req, res, next) => {
    res.status(err.statusCode || 500).json({
        success: false,
        message: err.message
    });
};
```

Then:

```text
GET /test-error
      ↓
AppError
      ↓
404
```

# 🧠 Final Mental Model

Don't memorize a huge HTTP table.

Remember this:

```text
                 HTTP RESPONSE
                       │
        ┌──────────────┼──────────────┐
        │              │              │
      SUCCESS        CLIENT         SERVER
        │             ERROR          ERROR
        │              │              │
     2xx             4xx            5xx
        │              │              │
   ┌────┼────┐    ┌────┼────┐     ┌───┴───┐
   │    │    │    │    │    │     │       │
  200  201  204  400  401  403   500     503
                    │    │
                    │    └─ authenticated,
                    │       not allowed
                    └──── authentication
```

And your most useful practical map is:

```text
200 → Success
201 → Created
204 → Success, no body

400 → Bad/invalid request
401 → Authentication problem
403 → Authorization problem
404 → Resource not found
409 → Conflict
422 → Validation/business-rule failure
429 → Rate limit

500 → Unexpected server error
503 → Service temporarily unavailable
```

### One sentence to remember

> **HTTP status codes communicate the outcome of an HTTP request; `AppError` lets your application carry the appropriate status code from the business/application layer to the global error middleware.**

Next is **Lesson 8.13 — Designing Consistent Error Responses**, where we'll stop returning random error JSON like `{error: ...}`, `{message: ...}`, etc., and design one predictable response contract for your entire backend.
