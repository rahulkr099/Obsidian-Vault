# Lesson 8.13 — Designing Consistent Error Responses

Now we reach an important architectural step.

In Lesson 8.12, we learned **which HTTP status code to use**.

Today we answer:

> **What should the JSON response look like when something goes wrong?**

Your roadmap specifically places **“Designing consistent error responses”** immediately after HTTP status codes and before global error middleware.

The goal is simple:

> **Every endpoint in your backend should communicate errors in the same format.**

---

# 1. The problem with inconsistent responses

Imagine your backend has three endpoints.

### Endpoint 1

```json
{
  "error": "User not found"
}
```

### Endpoint 2

```json
{
  "message": "Invalid password"
}
```

### Endpoint 3

```json
{
  "success": false,
  "errorMessage": "Todo not found"
}
```

All three represent errors.

But the frontend now has to understand three different formats.

That's bad API design.

Your React code might end up looking like:

```js
if (response.data.error) {
    // ...
}

if (response.data.message) {
    // ...
}

if (response.data.errorMessage) {
    // ...
}
```

That's unnecessary complexity.

---

# 2. We want one contract

Your uploaded starter architecture recommends a consistent response structure such as:

```json
{
  "success": false,
  "message": "Todo not found",
  "requestId": "..."
}
```

and for successful responses:

```json
{
  "success": true,
  "message": "Todo created successfully",
  "data": {}
}
```

The important point from the source is that the **exact format can be your choice**; what matters is that every endpoint follows the same response contract.

So think:

```text
                  API RESPONSE
                       │
              ┌────────┴────────┐
              │                 │
           SUCCESS             ERROR
              │                 │
        success: true     success: false
        message           message
        data              requestId
```

---

# 3. Why consistency matters

Imagine your React frontend calls:

```text
GET /api/v1/todos
```

and gets:

```json
{
  "success": true,
  "message": "Todos fetched successfully",
  "data": [...]
}
```

Then:

```text
GET /api/v1/todos/123
```

returns:

```json
{
  "success": false,
  "message": "Todo not found",
  "requestId": "req_123"
}
```

The frontend immediately knows:

```js
if (response.data.success) {
    // use response.data.data
} else {
    // show response.data.message
}
```

That's predictable.

---

# 4. Think of the response as a contract

An API response is basically a contract between:

```text
Backend
   ↕
Frontend
```

The backend promises:

> "When I respond, I'll follow this structure."

The frontend can then safely depend on it.

For example:

```text
Success:
success
message
data

Error:
success
message
requestId
```

---

# 5. Success response structure

A simple success response can be:

```json
{
  "success": true,
  "message": "User fetched successfully",
  "data": {
    "id": "123",
    "name": "Rahul"
  }
}
```

Break it down:

```text
success
   ↓
Was operation successful?

message
   ↓
Human-readable explanation

data
   ↓
Actual useful result
```

---

# 6. Why have `success`?

You might wonder:

> "But we already have HTTP status codes. Why do we need `success`?"

Good question.

Technically, the frontend can use:

```js
response.status
```

But having a consistent application-level response structure can make your API easier to consume.

For example:

```json
{
  "success": true,
  "message": "Todo fetched successfully",
  "data": {}
}
```

versus:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

The body itself clearly communicates the outcome.

---

# 7. Don't use `success` instead of HTTP status

This is important.

Don't do this:

```http
HTTP/1.1 200 OK
```

with:

```json
{
  "success": false,
  "message": "User not found"
}
```

That's confusing.

If the user wasn't found:

```http
404 Not Found
```

should normally be used.

So:

```text
HTTP status
     +
response body
```

work together.

---

# 8. HTTP status = machine-level information

For example:

```http
404 Not Found
```

is useful to the client/application.

The frontend can do:

```js
if (error.response.status === 404) {
    // show "not found"
}
```

---

# 9. `message` = human-readable information

The body can contain:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

The `message` explains what happened in a human-friendly way.

---

# 10. `data` = actual result

For successful requests:

```json
{
  "success": true,
  "message": "Todo fetched successfully",
  "data": {
    "id": "123",
    "title": "Learn Node.js"
  }
}
```

Here:

```text
success → outcome
message → explanation
data    → result
```

---

# 11. Should every response have `data`?

Not necessarily.

For example:

```http
DELETE /api/v1/todos/123
```

might return:

```http
204 No Content
```

and therefore no JSON body at all.

Or you might use:

```http
200 OK
```

with:

```json
{
  "success": true,
  "message": "Todo deleted successfully"
}
```

No `data` is necessary.

---

# 12. Error response

A simple error response:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

This is enough for many situations.

But your starter architecture also introduces:

```text
requestId
```

which we'll understand more deeply later.

So a production-oriented error could be:

```json
{
  "success": false,
  "message": "Todo not found",
  "requestId": "req_abc123"
}
```

The roadmap explicitly calls out **request IDs + error handling** as part of Phase 8.

---

# 13. Why do we need a request ID?

Imagine a user reports:

> "I'm getting an error when deleting my Todo."

You look at your server logs.

There are thousands of requests:

```text
POST /login
GET /todos
GET /users/me
POST /todos
DELETE /todos/123
GET /todos
...
```

Which error belongs to that user?

A request ID helps.

For example:

```text
requestId = req_8f92ab
```

Server log:

```text
[req_8f92ab] DELETE /api/v1/todos/123
[req_8f92ab] User: 42
[req_8f92ab] Error: Todo not found
```

Client receives:

```json
{
  "success": false,
  "message": "Todo not found",
  "requestId": "req_8f92ab"
}
```

Now you can search your logs for:

```text
req_8f92ab
```

and find the exact request.

We'll build this properly later in **Lesson 8.19**.

---

# 14. Don't expose internal errors

This is extremely important.

Suppose MongoDB produces:

```text
MongoServerError: E11000 duplicate key error...
```

Don't blindly return:

```json
{
  "success": false,
  "message": "MongoServerError: E11000 duplicate key error collection users index email..."
}
```

That exposes internal implementation details.

Instead, your API should transform it into something safe, such as:

```json
{
  "success": false,
  "message": "Email already exists"
}
```

or another appropriate public message.

---

# 15. Another dangerous example

Suppose your application throws:

```text
TypeError: Cannot read properties of undefined
```

Don't return:

```json
{
  "success": false,
  "message": "TypeError: Cannot read properties of undefined at user.service.js:42"
}
```

The client doesn't need:

```text
TypeError
file path
line number
stack trace
internal implementation
```

Instead:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

The detailed error belongs in your server logs.

This follows directly from the operational/programming error distinction we learned in 8.11.

---

# 16. Public error vs internal error

Think of two layers:

```text
                    ERROR
                      │
             ┌────────┴────────┐
             │                 │
          CLIENT             SERVER
             │                 │
       Safe information    Detailed information
             │                 │
       "Todo not found"     stack trace
                             database error
                             file location
                             internal details
```

This separation is one of the most important production practices.

# 18. Don't put everything into `message`

Suppose validation fails for three fields:

```text
email
password
age
```

Don't create something ugly like:

```json
{
  "success": false,
  "message": "email is invalid, password is too short, age is invalid"
}
```

A structured error can be much better:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Invalid email",
    "password": "Password must be at least 8 characters",
    "age": "Age must be greater than 0"
  }
}
```

This is especially useful when we reach **Phase 9 — Validation & Input Processing**, which includes a dedicated lesson on validation error formatting.

---

# 19. `errors` vs `message`

Now we have:

```text
message
errors
```

They have different purposes.

### `message`

General explanation:

```json
"message": "Validation failed"
```

### `errors`

Specific details:

```json
"errors": {
    "email": "Invalid email",
    "password": "Password too short"
}
```

This is much easier for React forms.

---

# 20. Frontend becomes easier

Imagine your React form receives:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Invalid email",
    "password": "Password must be at least 8 characters"
  }
}
```

Your frontend can do:

```js
setErrors(error.response.data.errors);
```

Then:

```text
Email
[ invalid email ]

Password
[ Password must be at least 8 characters ]
```

Much cleaner than parsing a giant string.


### Error

```json
  "message": "Something went wrong"

```

### Validation error

```json

  "success": false,
  "message": "Validation failed",
```

---

# 22. Don't over-engineer the response

You may see APIs returning things like:

```json
{
  "status": "error",
  "statusCode": 404,
  "code": "USER_NOT_FOUND",
  "message": "User not found",
  "details": {},
  "metadata": {},
  "timestamp": "...",
  "requestId": "..."
}
```

This can be useful in some large systems.

But don't add 15 fields just because you can.

For your starter, start simple:

```json
{
  "success": false,
  "message": "User not found"
}
```

Then add fields when they solve a real problem.

---

# 23. Response architecture should be predictable

Imagine all your APIs:

```text
/auth/login
/auth/signup
/users/me
/todos
/todos/:id
/posts
/comments
```

Every endpoint should follow the same basic contract.

```text
                 API
                  │
        ┌─────────┴─────────┐
        │                   │
     SUCCESS               ERROR
        │                   │
   success:true        success:false
   message             message
   data                errors? 
                       requestId?
```

This means the frontend doesn't need to learn a new response structure for every endpoint.

---

# 24. Where should response formatting happen?

This is an important architectural question.

Should every controller manually construct the entire response?

You could write:

```js
res.status(200).json({
    success: true,
    message: "User fetched successfully",
    data: user
});
```

That's okay for simple projects.

But as your project grows, you may create an `ApiResponse` utility.

Your roadmap later explicitly introduces:

```text
utils/ApiResponse.js
```

for consistent API responses.

We'll study that much more deeply in the later **API Response Architecture** phase.

For now, understand the **contract** first.

---

# 25. Why shouldn't services return HTTP responses?

This is extremely important for the architecture you're learning.

Don't do:

```js
// user.service.js

return res.status(404).json({
    success: false,
    message: "User not found"
});
```

Why?

Because the service shouldn't know about Express's:

```text
req
res
HTTP
status codes
```

The service should deal with application logic.

For example:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

Then the error architecture handles the HTTP response.

This separation becomes important when you learn **controllers → services → repositories**.

---

# 26. The correct flow

Your architecture should gradually become:

```text
HTTP Request
     │
     ▼
Controller
     │
     ▼
Service
     │
     ▼
Repository
     │
     ▼
Database
```

If something fails:

```text
Database
   │
   ▼
Repository
   │
   ▼
Service
   │
   ▼
Controller
   │
   ▼
asyncHandler
   │
   ▼
Error Middleware
   │
   ▼
Consistent JSON
```

That is the architecture you're building toward.

# 27. Example: User not found

### Service

```js
const getUserById = async (userId) => {
    const user = await userRepository.findById(userId);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Notice:

**No `res`.**

---

### Controller

Conceptually:

```js
const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUserById(
        req.user.userId
    );

    res.status(200).json({
        success: true,
        message: "User fetched successfully",
        data: user
    });
});
```

If the service throws:

```text
AppError
   ↓
asyncHandler
   ↓
error middleware
```

The controller doesn't need:

```js
try/catch
```

# 30. Your response contract

For now, I want you to remember this:

```text
SUCCESS
{
    success: true,
    message: "...",
    data: ...
}
```

and:

```text
ERROR
{
    success: false,
    message: "...",
    errors?: ...,
    requestId?: "..."
}
```

The `?` means:

> This field is optional depending on the situation.

---

# 31. One important principle

Don't make the frontend guess.

Bad:

```text
Sometimes:
{ error: "..." }

Sometimes:
{ message: "..." }

Sometimes:
{ errors: [...] }

Sometimes:
{ msg: "..." }
```

Good:

```text
Always:
{
    success: ...,
    message: ...
}
```

and add:

```text
data
errors
requestId
```

when appropriate.

```text

                       │
             ┌─────────┴─────────┐
             │                   │
          SUCCESS              ERROR
             │                   │
             ▼                   ▼
       HTTP 2xx             HTTP 4xx/5xx
             │                   │

}                         errors?:{},
                          requestId?: "..."

```

And the most important principle:

> **An API should have one predictable response contract so the frontend always knows where to find the result, message, validation errors, and debugging identifier.**
