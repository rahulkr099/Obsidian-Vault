# Lesson 8.14 — Global Error Middleware

Now we're putting the pieces from **8.1–8.13 together**.

Your Phase 8 roadmap defines the core flow as:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
      ↓
JSON response
```

The key idea of today's lesson:

> **Global error middleware is the single place where your Express application turns errors into HTTP responses.**

---

# 1. Why do we need global error middleware?

Imagine you have 20 controllers:

```text
auth.controller.js
user.controller.js
todo.controller.js
post.controller.js
comment.controller.js
...
```

If every controller handles errors itself:

```js
try {
    // logic
} catch (error) {
    res.status(...).json(...);
}
```

you'll repeat the same code everywhere.

For example:

```js
try {
    const user = await userService.getUser(id);

    res.status(200).json({
        success: true,
        data: user
    });
} catch (error) {
    res.status(500).json({
        success: false,
        message: error.message
    });
}
```

Then another controller:

```js
try {
    const todo = await todoService.getTodo(id);

    res.status(200).json({
        success: true,
        data: todo
    });
} catch (error) {
    res.status(500).json({
        success: false,
        message: error.message
    });
}
```

You're repeating yourself.

---

# 2. The better approach

Instead:

```text
Controller
   ↓
throws error
   ↓
asyncHandler
   ↓
next(error)
   ↓
GLOBAL ERROR MIDDLEWARE
   ↓
consistent JSON
```

Now every controller can focus on its actual job.

---

# 3. What is global error middleware?

It is simply an Express middleware specifically designed to handle errors.

The signature is:

```js
const errorMiddleware = (err, req, res, next) => {
    // handle error
};
```

Notice something unusual:

```js
err
req
res
next
```

There are **four arguments**.

That is how Express recognizes it as error-handling middleware.

You learned this in Lesson 8.6.

---

# 4. Normal middleware vs error middleware

Normal middleware:

```js
(req, res, next)
```

Error middleware:

```js
(err, req, res, next)
```

The extra argument is:

```text
err
```

So:

```text
Normal:
request → middleware

Error:
error → error middleware
```

---

# 5. Where should it be placed?

This is extremely important.

Your error middleware should be registered **after your routes and other middleware that can generate errors**.

Think:

```text
Request
   ↓
Middleware
   ↓
Routes
   ↓
Controller
   ↓
ERROR
   ↓
Global error middleware
```

In `app.js`:

```js
app.use("/api/v1/users", userRoutes);
app.use("/api/v1/todos", todoRoutes);

app.use(errorMiddleware);
```

The error middleware comes near the end.

---

# 6. Why does order matter?

Express processes middleware in order.

Suppose:

```js
app.use(logger);
app.use(auth);
app.use(routes);
app.use(errorMiddleware);
```

A request moves downward:

```text
logger
  ↓
auth
  ↓
routes
  ↓
controller
  ↓
error
  ↓
errorMiddleware
```

But if you put:

```js
app.use(errorMiddleware);

app.use(routes);
```

then your architecture becomes incorrect for errors generated later.

So remember:

> **Global error middleware should be near the end of your Express middleware stack.**

---

# 7. A very simple error middleware

Start with the smallest possible version:

```js
const errorMiddleware = (err, req, res, next) => {
    res.status(500).json({
        success: false,
        message: "Internal server error"
    });
};

export default errorMiddleware;
```

Now any error reaching this middleware gets:

```http
500 Internal Server Error
```

with:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

---

# 8. But there's a problem

Suppose your service does:

```js
throw new AppError(
    "User not found",
    404
);
```

If our middleware always does:

```js
res.status(500)
```

then the client receives:

```http
500
```

instead of:

```http
404
```

That's wrong.

The middleware needs to understand:

```text
err.statusCode
```

---

# 9. Connect `AppError`

From Lesson 8.10, we created something conceptually like:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}
```

So:

```js
throw new AppError(
    "User not found",
    404
);
```

produces an error object containing:

```text
message
→ "User not found"

statusCode
→ 404

isOperational
→ true
```

Now our global middleware can use that information.

---

# 10. First useful version

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message: err.message
    });
};

export default errorMiddleware;
```

Now:

```js
throw new AppError("User not found", 404);
```

becomes:

```http
404 Not Found
```

```json
{
  "success": false,
  "message": "User not found"
}
```

That's the beginning of our global error architecture.

---

# 11. Why `|| 500`?

Look at:

```js
const statusCode = err.statusCode || 500;
```

It means:

```text
Does the error have a statusCode?
       │
   ┌───┴───┐
  YES      NO
   │        │
 use it    500
```

So:

```js
err.statusCode = 404
```

gives:

```text
404
```

But a normal JavaScript error like:

```js
throw new Error("Something broke");
```

may not have:

```js
err.statusCode
```

so we safely use:

```text
500
```

# 12. Example: operational error

Service:

```js
const getUser = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new AppError(
            "User not found",
            404
        );
    }

    return user;
};
```

Flow:

```text
Repository
    ↓
user doesn't exist
    ↓
Service
    ↓
AppError(404)
    ↓
asyncHandler
    ↓
next(error)
    ↓
errorMiddleware
```

Response:

```json
{
  "success": false,
  "message": "User not found"
}
```

# 13. Example: unexpected programming error

Suppose something accidentally causes:

```js
const name = user.profile.name;
```

but:

```text
user.profile === undefined
```

JavaScript throws:

```text
TypeError
```

The error may not have:

```text
statusCode
```

So:

```js
const statusCode = err.statusCode || 500;
```

becomes:

```text
500
```

Client gets:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

But there is a problem with our current implementation.

---

# 14. Don't expose `err.message` blindly

Our first version does:

```js
message: err.message
```

That's okay for a simple learning example.

But imagine this:

```js
throw new Error(
    "MongoServerError: E11000 duplicate key..."
);
```

or:

```text
TypeError: Cannot read properties of undefined
```

You don't necessarily want to send that directly to the client.

So we need to distinguish:

```text
Operational error
        vs
Programming/unexpected error
```

You learned this distinction in 8.11.

---

# 15. `isOperational` becomes useful

Our `AppError` contains:

```js
this.isOperational = true;
```

So:

```js
throw new AppError(
    "User not found",
    404
);
```

means:

```text
isOperational = true
```

But a normal JavaScript error:

```js
throw new Error("Database exploded");
```

doesn't have that property.

So we can distinguish:

```text
AppError
   ↓
Known/safe application error

Normal Error
   ↓
Unexpected/internal error
```

---

# 16. Build the distinction

Conceptually:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    const message = err.isOperational
        ? err.message
        : "Internal server error";

    res.status(statusCode).json({
        success: false,
        message
    });
};
```

Now:

### Known error

```js
throw new AppError(
    "Todo not found",
    404
);
```

Response:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

### Unexpected error

```js
throw new Error("Something weird happened");
```

Response:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

Much safer.

---

# 17. But what about logging?

If an unexpected error occurs, we **still need to know what happened**.

We just don't tell the client everything.

So:

```text
Unexpected error
       │
       ├──────────────→ Server logs
       │                 detailed error
       │
       └──────────────→ Client
                         safe message
```

For example:

### Server

```text
TypeError: Cannot read properties of undefined
    at user.service.js:42
```

### Client

```json
{
  "success": false,
  "message": "Internal server error"
}
```

This separation is essential.

This is a useful way to think about it.

The error middleware translates:


For example:

```text

          ↓

          ↓

  success: false,
```

# 20. What exactly does `next(error)` do?

Normally:

```js
next();
```

means:

> Continue to the next middleware.

But:

```js
next(error);
```

means:

> Something went wrong. Start Express's error-handling flow.

For example:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        Promise
            .resolve(controller(req, res, next))
            .catch(next);
    };
};
```

If the controller rejects:

```text
Promise rejection
      ↓
.catch(next)
      ↓
next(error)
      ↓
error middleware
```

That's why `asyncHandler` and global error middleware work so well together.

---

# 21. `asyncHandler` + global error middleware

This is one of the most important combinations in your starter.

### `asyncHandler`

Responsible for:

> **Getting async errors into Express's error pipeline.**

### `errorMiddleware`

Responsible for:

> **Turning those errors into HTTP responses.**

So:

```text
asyncHandler
     ↓
error enters Express
```

and:

```text
errorMiddleware
     ↓
error leaves Express as JSON
```

---

# 22. Don't confuse their responsibilities

### `asyncHandler`

Doesn't decide:

```text
404?
500?
401?
```

It simply forwards the error.

### `errorMiddleware`

Decides how the error becomes:

```text
HTTP status
JSON response
logging
safe public message
```

This separation is very important.

### `utils/asyncHandler.js`

# 27. A common mistake — sending two responses

Don't do this:

```js
if (!user) {
    res.status(404).json({
        success: false,
        message: "User not found"
    });

    throw new AppError("User not found", 404);
}
```

You've already sent the response.

Then you're throwing another error.

This can lead to:

```text
ERR_HTTP_HEADERS_SENT
```

Instead:

```js
if (!user) {
    throw new AppError(
        "User not found",
        404
    );
}
```

Let the global error middleware send the response.

---

# 28. Another common mistake — forgetting `next`

Wrong:

```js
const errorMiddleware = (err, req, res) => {
    ...
};
```

For a basic terminal error middleware, `next` may not be used, but keeping the standard four-argument signature is clearer and matches Express's error-handler convention:

```js
const errorMiddleware = (err, req, res, next) => {
    ...
};
```

The important part is that the first argument is:

```text
err
```

---

# 29. Another mistake — registering it too early

Avoid:

```js
app.use(errorMiddleware);

app.use("/api/users", userRoutes);
```

Prefer:

```js
app.use("/api/users", userRoutes);

app.use(errorMiddleware);
```

Think:

```text
ERROR PRODUCED
      ↓
ERROR HANDLER
```

The handler needs to be downstream of the middleware/routes that pass errors to it.

---

# 30. Another mistake — exposing everything

Avoid:

```js
res.status(500).json({
    success: false,
    message: err.message,
    stack: err.stack
});
```

Especially in production.

You don't want clients receiving:

```text
database details
file paths
stack traces
internal implementation
secrets
```

The Phase 8 roadmap explicitly includes **hiding sensitive errors in production** as a later lesson, so we'll go deeper into this in 8.18.

# 32. What happens to 404 routes?

There's another important distinction.

Suppose the user requests:

```http
GET /api/v1/does-not-exist
```

No route matches.

That's a **404 route-not-found situation**.

You can create a separate middleware:

```js
const notFoundMiddleware = (req, res, next) => {
    next(
        new AppError(
            `Route ${req.originalUrl} not found`,
            404
        )
    );
};
```

Then:

```js
app.use(notFoundMiddleware);
app.use(errorMiddleware);
```

Notice the order:

```text
Routes
  ↓
404 middleware
  ↓
Global error middleware
```

This lets the 404 middleware create an error and the global error middleware format it consistently.

# 34. The responsibility of each piece

This is worth memorizing:

|Component|Responsibility|
|---|---|
|`AppError`|Represents known application errors|
|`asyncHandler`|Forwards async errors to Express|
|`notFoundMiddleware`|Handles unmatched routes|
|`errorMiddleware`|Converts errors into HTTP responses|
|Logger|Records useful error information|
|Controller|Handles HTTP input/output|
|Service|Handles business logic|
|Repository|Handles data access|

This is how your starter architecture gradually stops looking like a collection of random files.

# 🧠 Final Mental Model

Forget the individual files for a moment.

Think about **one request**:

```text
GET /api/v1/todos/123
```

Something goes wrong.

Your brain should immediately see:

```text
Request
   ↓
Route
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Something fails
   ↓
throw AppError(...)
   ↓
asyncHandler
   ↓
next(error)
   ↓
Global error middleware
   ↓
statusCode
   +
safe message
   +
optional requestId
   ↓
HTTP JSON response
```

And this is the big idea of Lesson 8.14:

> **Don't make every controller solve error handling. Let errors flow into one central error-handling pipeline.**

Your starter's Phase 8 is designed around exactly this progression: first understand errors, then `asyncHandler`, then `AppError`, then status codes and response contracts, and finally bring them together through **global error middleware**.
