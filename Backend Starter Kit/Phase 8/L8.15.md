# Lesson 8.15 — Handling MongoDB Errors

Now we move from **application errors** to **database errors**.

This lesson is important because MongoDB/Mongoose doesn't automatically give you your nice:

```js
new AppError("Todo not found", 404)
```

format.

Instead, MongoDB/Mongoose can produce different kinds of errors, and your **global error middleware** needs to translate those into clean API responses.

Your Phase 8 roadmap explicitly places **Handling MongoDB errors** here, before validation and JWT errors.

---

# 1. The problem

Imagine your service does:

```js
const user = await User.create({
    email,
    password
});
```

Something goes wrong.

Mongoose might throw an error like:

```text
MongoServerError: E11000 duplicate key error
```

But your frontend shouldn't receive that raw database error.

You want:

```json
{
  "success": false,
  "message": "Email already exists"
}
```

with:

```http
409 Conflict
```

So we need:

```text
MongoDB/Mongoose Error
        ↓
Global Error Middleware
        ↓
Recognize error
        ↓
Convert it
        ↓
Clean API response
```

---

# 2. Why should the error middleware handle it?

Remember our architecture:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Mongoose
    ↓
MongoDB
```

Suppose MongoDB throws an error.

We don't want:

```js
repository
   ↓
res.status(...)
```

because the repository shouldn't know about HTTP.

Instead:

```text
MongoDB
   ↓
Mongoose Error
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
asyncHandler
   ↓
errorMiddleware
```

The global error middleware becomes the **translation layer**.

---

# 3. The important MongoDB/Mongoose errors

For your backend, understand these first:

```text
1. Duplicate key error
2. Mongoose ValidationError
3. CastError
4. Connection errors
5. Generic MongoDB errors
```

We'll focus on the first three because they're especially common in APIs.

---

# 4. Duplicate key error

This is probably the most important MongoDB error you'll encounter.

Suppose your User model has:

```js
email: {
    type: String,
    unique: true
}
```

Then:

```text
rahul@example.com
```

can only exist once.

Imagine:

```text
Database

User 1
email: rahul@example.com
```

Now another request tries:

```text
User 2
email: rahul@example.com
```

MongoDB rejects it.

---

# 5. What does MongoDB give us?

You'll commonly see:

```text
E11000 duplicate key error
```

The error's code is typically:

```js
error.code === 11000
```

So the middleware can detect:

```js
if (err.code === 11000) {
    // duplicate key
}
```

---

# 6. Don't return the raw MongoDB error

Bad:

```json
{
  "success": false,
  "message": "E11000 duplicate key error collection: app.users index: email_1 dup key..."
}
```

Why is this bad?

Because the client doesn't need MongoDB's internal details.

Instead:

```json
{
  "success": false,
  "message": "Email already exists"
}
```

---

# 7. What should the status code be?

This connects directly to Lesson 8.12.

Duplicate resource:

```text
409 Conflict
```

So:

```text
MongoDB duplicate key
        ↓
409 Conflict
```

---

# 8. Basic implementation

Inside your error middleware:

```js
const errorMiddleware = (err, req, res, next) => {

    if (err.code === 11000) {
        return res.status(409).json({
            success: false,
            message: "Resource already exists"
        });
    }

    // other errors...
};
```

This works, but:

```text
"Resource already exists"
```

isn't very helpful.

We'd prefer:

```text
Email already exists
```

---

# 9. Finding which field caused the duplicate

MongoDB's duplicate error can contain information about the duplicated field.

Depending on the MongoDB/Mongoose version and error shape, you may inspect:

```js
err.keyPattern
```

or:

```js
err.keyValue
```

For example, conceptually:

```js
err.keyValue
```

could look like:

```js
{
    email: "rahul@example.com"
}
```

Then you can identify:

```text
email
```

as the conflicting field.

---

# 10. A simple duplicate-key formatter

For learning:

```js
const handleDuplicateKeyError = (err) => {
    const field = Object.keys(err.keyValue || {})[0];

    return new AppError(
        `${field} already exists`,
        409
    );
};
```

So:

```text
err.keyValue
      ↓
{ email: "rahul@example.com" }
      ↓
field = "email"
      ↓
AppError
      ↓
409
```

---

# 11. But be careful

Don't blindly expose arbitrary database field names.

Imagine your database has:

```text
internalSecretField
```

You don't necessarily want:

```json
{
  "message": "internalSecretField already exists"
}
```

So in a production application, you may map known fields:

```js
const duplicateMessages = {
    email: "Email already exists",
    username: "Username already exists"
};
```

Then:

```js
const message =
    duplicateMessages[field] ||
    "Resource already exists";
```

This is safer.

---

# 12. Mongoose `ValidationError`

Now let's look at another common error.

Suppose your schema says:

```js
const userSchema = new mongoose.Schema({
    email: {
        type: String,
        required: true
    },

    age: {
        type: Number,
        min: 18
    }
});
```

Now somebody tries:

```js
await User.create({
    age: 10
});
```

Mongoose may produce:

```text
ValidationError
```

because:

```text
age >= 18
```

was required.

---

# 13. What does a Mongoose ValidationError contain?

Conceptually:

```js
err.name
```

could be:

```text
ValidationError
```

And:

```js
err.errors
```

can contain field-level validation errors.

For example:

```js
{
    age: {
        message: "Path `age` (10) is less than minimum allowed value (18)."
    }
}
```

The exact structure depends on the validation that failed.

---

# 14. Don't expose the raw validation object

Avoid returning:

```json
{
  "success": false,
  "message": "ValidationError: User validation failed: age: Path `age`..."
}
```

That's ugly and tightly coupled to Mongoose.

Instead:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "age": "Age must be at least 18"
  }
}
```

Now the frontend has something useful.

---

# 15. Mongoose validation vs Joi validation

This is important because you'll study validation in Phase 9.

You may eventually have:

```text
Request
 ↓
Joi validation
 ↓
Controller
 ↓
Service
 ↓
Mongoose
 ↓
Database
```

So why validate twice?

Because they solve slightly different problems.

### Joi

Validates incoming API input:

```text
req.body
req.params
req.query
```

### Mongoose

Validates data against the model/schema before persistence.

Think:

```text
Joi
 ↓
API boundary

Mongoose
 ↓
Database/model boundary
```

Your roadmap explicitly treats validation as its own phase after error handling.

---

# 16. Don't rely only on Mongoose validation

Suppose your API accepts:

```json
{
  "email": "not-an-email"
}
```

You don't want the request to travel all the way to the database before discovering that.

Better:

```text
Request
 ↓
Joi
 ↓
Invalid
 ↓
400
```

This is faster and gives you better control over the API contract.

But Mongoose validation is still valuable as a second boundary.

---

# 17. `CastError`

Another common Mongoose error is:

```text
CastError
```

This often happens when Mongoose expects a certain type but receives something it cannot convert.

For example:

```js
User.findById("hello")
```

If MongoDB expects an ObjectId, `"hello"` may produce a casting error.

Conceptually:

```text
Expected:
ObjectId

Received:
"hello"
```

Mongoose can throw:

```text
CastError
```

---

# 18. What should the API return?

You generally don't want:

```json
{
  "success": false,
  "message": "Cast to ObjectId failed for value..."
}
```

Instead:

```json
{
  "success": false,
  "message": "Invalid user ID"
}
```

And typically:

```text
400 Bad Request
```

---

# 19. Example

Request:

```http
GET /api/v1/users/not-a-valid-id
```

Your repository might do:

```js
User.findById("not-a-valid-id");
```

Mongoose may throw a `CastError`.

Your error middleware can recognize it:

```js
if (err.name === "CastError") {
    return res.status(400).json({
        success: false,
        message: "Invalid resource ID"
    });
}
```

---

# 20. Why not return `404`?

This is a subtle but important distinction.

Compare:

### Invalid ID

```text
/users/hello
```

The identifier itself is invalid.

Potentially:

```text
400
```

### Valid ID but resource doesn't exist

```text
/users/64abc123...
```

but no user has that ID.

Potentially:

```text
404
```

So:

```text
Invalid identifier
→ 400

Valid identifier + resource absent
→ 404
```

This distinction will become very useful when building repositories.

---

# 21. MongoDB connection errors

Now consider:

```text
Node
 ↓
Mongoose
 ↓
MongoDB
 X
```

Maybe:

```text
MongoDB is down
```

or:

```text
Network problem
```

or:

```text
Connection timeout
```

This is different from:

```text
User not found
```

because the application itself may be unable to access the database.

Depending on where and how the failure occurs, the appropriate response may be:

```text
503 Service Unavailable
```

rather than:

```text
404
```

---

# 22. Important distinction

Think:

```text
Database query succeeded
       ↓
No user
       ↓
404
```

versus:

```text
Database unavailable
       ↓
Application can't perform query
       ↓
potentially 503
```

The first is a resource problem.

The second is a service availability problem.

---

# 23. Don't catch every database error and call it 500

You might be tempted to write:

```js
catch (error) {
    throw new AppError(
        "Database error",
        500
    );
}
```

everywhere.

Don't.

You'll lose useful information.

For example:

```text
Duplicate key
→ 409

Invalid ObjectId
→ 400

Validation failure
→ 400/422 depending on your API convention

Unexpected database failure
→ 500

Temporary database/service unavailable
→ potentially 503
```

The error-handling layer should distinguish them.

---

# 24. Build dedicated error transformers

As your application grows, you can create small functions.

For example:

```js
const handleDuplicateKeyError = (err) => {
    // convert duplicate key
};

const handleValidationError = (err) => {
    // convert mongoose validation
};

const handleCastError = (err) => {
    // convert invalid ObjectId
};
```

Then:

```text
Mongo/Mongoose error
        ↓
identify type
        ↓
appropriate transformer
        ↓
AppError / standardized response
```

This keeps the main error middleware readable.

---

# 25. Example architecture

```js
const errorMiddleware = (err, req, res, next) => {

    if (err.code === 11000) {
        return handleDuplicateKeyError(err, res);
    }

    if (err.name === "ValidationError") {
        return handleValidationError(err, res);
    }

    if (err.name === "CastError") {
        return handleCastError(err, res);
    }

    // AppError
    if (err.isOperational) {
        return res.status(err.statusCode).json({
            success: false,
            message: err.message
        });
    }

    // Unknown error
    return res.status(500).json({
        success: false,
        message: "Internal server error"
    });
};
```

This is still a learning version.

We'll improve it as your architecture becomes more advanced.

---

# 26. Even better: normalize first

A cleaner architecture is:

```text
MongoDB/Mongoose error
        ↓
Error normalization
        ↓
AppError
        ↓
Final response formatting
```

For example:

```text
Mongo duplicate key
        ↓
AppError(
    "Email already exists",
    409
)
        ↓
Global response formatter
        ↓
JSON
```

This is a powerful concept.

Instead of teaching the final response layer about every possible database error, you can convert external errors into your application's own error representation.

---

# 27. Think in two stages

This is the mental model I recommend:

```text
STAGE 1
External error
     ↓
Normalize

STAGE 2
Normalized AppError
     ↓
Respond
```

For example:

```text
MongoDB
  ↓
E11000
  ↓
"Email already exists", 409
  ↓
AppError
  ↓
error.middleware
  ↓
JSON
```

---

# 28. Why is this architecture useful?

Imagine later you replace:

```text
MongoDB
```

with:

```text
PostgreSQL
```

If your entire application depends directly on MongoDB error shapes, you'll have lots of changes.

But if you normalize database errors:

```text
MongoDB error
      ↓
AppError

PostgreSQL error
      ↓
AppError
```

your API's error contract can remain the same.

That's a major architectural benefit.

# 33. A practical error mapper

For learning, you can create:

```js
const normalizeDatabaseError = (err) => {

    if (err.code === 11000) {
        return new AppError(
            "Resource already exists",
            409
        );
    }

    if (err.name === "CastError") {
        return new AppError(
            "Invalid resource ID",
            400
        );
    }

    if (err.name === "ValidationError") {
        const errors = {};

        for (const field in err.errors) {
            errors[field] = err.errors[field].message;
        }

        const error = new AppError(
            "Validation failed",
            400
        );

        error.details = errors;

        return error;
    }

    return err;
};
```

Then:

```js
const errorMiddleware = (err, req, res, next) => {
    const normalizedError = normalizeDatabaseError(err);

    // respond using normalizedError
};
```

This is the direction your architecture should eventually take.

# 35. Common mistakes

## Mistake 1 — Returning raw MongoDB errors

Bad:

```js
res.status(500).json({
    error: err
});
```

Don't expose internal database details.

---

## Mistake 2 — Treating duplicate key as 500

Bad:

```text
E11000
→ 500
```

Better:

```text
Duplicate resource
→ 409
```

---

## Mistake 3 — Treating invalid IDs as 404

Don't confuse:

```text
invalid ID
```

with:

```text
valid ID but resource doesn't exist
```

Usually:

```text
Invalid ID → 400
Not found → 404
```

---

## Mistake 4 — Catching errors in repositories just to send HTTP responses

Don't:

```js
catch (error) {
    return res.status(500).json(...);
}
```

Repositories shouldn't know about:

```text
res
HTTP
status codes
```

---

## Mistake 5 — Catching and destroying the original error

Bad:

```js
catch (error) {
    throw new Error("Database failed");
}
```

Now you've potentially lost:

```text
original error
error code
stack
metadata
```

If you need to transform it, preserve useful information.

This is probably the most important part of today's lesson.

→ AppError

# 🧠 Final Mental Model

When you see:

```js
await User.create(data);
```

don't think:

> "If this fails, I'll put a try/catch here."

Instead think:

```text
User.create()
      │
      ▼
Mongoose
      │
      ├── Success
      │
      └── Error
            │
            ├── 11000
            │     ↓
            │    409
            │
            ├── ValidationError
            │     ↓
            │    400/422
            │
            ├── CastError
            │     ↓
            │    400
            │
            └── Unexpected
                  ↓
                 500
```

Then:

```text
Database Error
      ↓
Normalize
      ↓
AppError / safe error
      ↓
Global Error Middleware
      ↓
Consistent JSON
```

### The key principle

> **Your database is allowed to have its own error format internally, but your API should expose your own stable, safe error format externally.**

That is the real purpose of **handling MongoDB errors**.
