# Lesson 8.16 — Handling Validation Errors

In **Lesson 8.15**, we learned how to handle MongoDB/Mongoose errors such as:

```text
E11000 duplicate key
CastError
Mongoose ValidationError
```

Now we'll focus specifically on **validation errors** and, more importantly, how to turn messy validation information into a clean API response.

Your roadmap places this lesson immediately after MongoDB errors and before JWT errors.

---

# 1. First: What is a validation error?

Validation means:

> **Checking whether incoming data follows the rules your application expects.**

For example, your signup API might require:

```json
{
  "email": "rahul@example.com",
  "password": "mypassword123"
}
```

But the client might send:

```json
{
  "email": "hello",
  "password": "123"
}
```

Problems:

```text
email
 ↓
maybe invalid format

password
 ↓
too short
```

The backend should reject this **before performing the business operation**.

---

# 2. Validation happens at a boundary

Think of your backend as a building:

```text
Internet
   │
   ▼
┌───────────────┐
│ Validation    │ ← Check input here
└───────┬───────┘
        │
        ▼
    Controller
        │
        ▼
     Service
        │
        ▼
   Repository
        │
        ▼
    Database
```

You don't want invalid data traveling all the way to MongoDB.

---

# 3. There are two validation systems we need to understand

In your MERN backend you'll commonly encounter:

```text
Joi
 ↓
API/request validation
```

and:

```text
Mongoose
 ↓
model/database validation
```

Your roadmap intentionally teaches validation as its own phase after error handling.

For today's lesson, understand both, but especially the **error-handling side**.

---

# 4. Joi validation error

Suppose we have:

```js
import Joi from "joi";

const signupSchema = Joi.object({
    email: Joi.string()
        .email()
        .required(),

    password: Joi.string()
        .min(8)
        .required()
});
```

Now imagine the request:

```json
{
  "email": "hello",
  "password": "123"
}
```

Joi can detect:

```text
email
❌ invalid email

password
❌ less than 8 characters
```

---

# 5. Why shouldn't we return Joi's entire error object?

You might be tempted to do:

```js
res.status(400).json({
    error: error
});
```

Don't.

Joi's internal error object contains much more information than your frontend needs.

Your API should expose a **stable response format**.

For example:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Invalid email",
    "password": "Password must be at least 8 characters"
  }
}
```

That's much easier for React to consume.

---

# 6. Why field-level errors are useful

Imagine your React form:

```text
Email:    [ hello          ]
Password: [ 123            ]
```

The backend responds:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Invalid email",
    "password": "Password must be at least 8 characters"
  }
}
```

Your frontend can do:

```text
email
 ↓
show error under email

password
 ↓
show error under password
```

So validation errors aren't just for developers.

They're part of your **API contract**.

---

# 7. Joi's useful property: `details`

A Joi validation error typically contains:

```js
error.details
```

Each item describes a validation problem.

Conceptually:

```js
[
    {
        message: "\"email\" must be a valid email",
        path: ["email"],
        type: "string.email"
    },
    {
        message: "\"password\" length must be at least 8 characters long",
        path: ["password"],
        type: "string.min"
    }
]
```

You don't want to send this raw structure directly.

Instead, transform it.

---

# 8. Convert Joi errors into your own format

We can create:

```js
const formatJoiErrors = (error) => {
    const errors = {};

    error.details.forEach((detail) => {
        const field = detail.path.join(".");

        errors[field] = detail.message;
    });

    return errors;
};
```

Suppose:

```js
detail.path
```

is:

```js
["email"]
```

Then:

```js
detail.path.join(".")
```

becomes:

```text
email
```

So:

```js
errors.email = detail.message;
```

---

# 9. The result

Input:

```json
{
  "email": "hello",
  "password": "123"
}
```

Joi detects two errors.

Our formatter produces:

```js
{
    email: "\"email\" must be a valid email",
    password: "\"password\" length must be at least 8 characters long"
}
```

Then the API can return:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "\"email\" must be a valid email",
    "password": "\"password\" length must be at least 8 characters long"
  }
}
```

---

# 10. You can improve the messages

Raw Joi messages aren't always ideal for users.

Instead of:

```text
"password" length must be at least 8 characters long
```

you might want:

```text
Password must be at least 8 characters
```

There are different ways to do this.

For example:

```js
const signupSchema = Joi.object({
    email: Joi.string()
        .email()
        .required()
        .messages({
            "string.email": "Please enter a valid email",
            "any.required": "Email is required"
        }),

    password: Joi.string()
        .min(8)
        .required()
        .messages({
            "string.min": "Password must be at least 8 characters",
            "any.required": "Password is required"
        })
});
```

Now the validation layer produces much cleaner messages.

---

# 11. Validation middleware

Instead of validating manually inside every controller:

```js
const signup = async (req, res) => {
    const { error } = signupSchema.validate(req.body);

    if (error) {
        ...
    }

    // business logic
};
```

create reusable middleware.

For example:

```js
const validate = (schema) => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req.body);

        if (error) {
            // send/forward validation error
        }

        req.body = value;

        next();
    };
};
```

Then:

```js
router.post(
    "/signup",
    validate(signupSchema),
    authController.signup
);
```

Now the controller doesn't need to know how Joi works.

This matches the architecture you're building toward in Phase 9: request → validate → clean data → controller.

---

# 12. Where should validation errors go?

You have two reasonable approaches.

### Approach A — Middleware sends response

```text
Request
 ↓
validate
 ↓
invalid
 ↓
400 response
```

### Approach B — Middleware forwards an error

```text
Request
 ↓
validate
 ↓
invalid
 ↓
next(error)
 ↓
global error middleware
 ↓
400 response
```

For the architecture you're learning, **Approach B is especially useful** because it gives you one centralized error-response system.

---

# 13. Connect validation to `AppError`

Remember:

```js
new AppError(
    "User not found",
    404
);
```

We can use the same idea for validation.

For example:

```js
const error = new AppError(
    "Validation failed",
    400
);

error.details = formatJoiErrors(validationError);

next(error);
```

Now the global error middleware receives:

```text
AppError
 ├── message
 ├── statusCode
 ├── isOperational
 └── details
```

---

# 14. Then the global error middleware can respond

Something like:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    const response = {
        success: false,
        message: err.isOperational
            ? err.message
            : "Internal server error"
    };

    if (err.details) {
        response.errors = err.details;
    }

    res.status(statusCode).json(response);
};
```

Now validation errors become:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Please enter a valid email",
    "password": "Password must be at least 8 characters"
  }
}
```

---

# 15. This creates a very nice pipeline

```text
POST /signup
       │
       ▼
validation middleware
       │
       ▼
    Joi
       │
   ┌───┴────┐
   │        │
 valid    invalid
   │        │
   │        ▼
   │     AppError
   │        │
   │        ▼
   │    next(error)
   │        │
   │        ▼
   │  error.middleware
   │        │
   │        ▼
   │       400
   │
   ▼
controller
```

This is the architecture you want.

---

# 16. Multiple validation errors

This is important.

Suppose the user sends:

```json
{
  "email": "",
  "password": "",
  "username": ""
}
```

You don't want the backend to return only:

```json
{
  "message": "Email is required"
}
```

It would be better to return all relevant errors:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Email is required",
    "password": "Password is required",
    "username": "Username is required"
  }
}
```

That's why we use:

```js
abortEarly: false
```

with Joi.

---

# 17. `abortEarly: false`

Normally Joi may stop at the first validation problem.

Instead:

```js
schema.validate(req.body, {
    abortEarly: false
});
```

means:

> Continue checking and collect all validation errors.

Example:

```js
const { error, value } = signupSchema.validate(
    req.body,
    {
        abortEarly: false
    }
);
```

Now the frontend gets a complete picture of what's wrong.

---

# 18. Example validation middleware

A useful learning version:

```js
const validate = (schema) => {
    return (req, res, next) => {
        const { error, value } = schema.validate(
            req.body,
            {
                abortEarly: false
            }
        );

        if (error) {
            const details = {};

            error.details.forEach((detail) => {
                const field = detail.path.join(".");

                details[field] = detail.message;
            });

            const validationError = new AppError(
                "Validation failed",
                400
            );

            validationError.details = details;

            return next(validationError);
        }

        req.body = value;

        next();
    };
};
```

This is not the final production version, but it demonstrates the architecture clearly.

---

# 19. Why `req.body = value`?

This line is important:

```js
req.body = value;
```

Joi can return the validated/transformed value.

For example:

```text
Input
 ↓
Joi
 ↓
validated value
 ↓
req.body
```

Now the controller receives the data that passed validation.

This idea becomes especially important later when you learn **normalization** and **sanitization**.

---

# 20. Don't modify input randomly

A common beginner mistake is:

```js
req.body.email = req.body.email.toLowerCase();
req.body.name = req.body.name.trim();
req.body.password = ...
```

inside controllers.

That creates scattered input-processing logic.

Better:

```text
Request
 ↓
Validation / normalization
 ↓
Controller
```

Then the controller gets data in the form it expects.

# 22. Joi vs Mongoose validation

Think of them as two gates:

```text
               CLIENT
                  │
                  ▼
          ┌──────────────┐
          │     Joi      │
          │ API boundary │
          └──────┬───────┘
                 │
                 ▼
             Controller
                 │
                 ▼
              Service
                 │
                 ▼
             Repository
                 │
                 ▼
          ┌──────────────┐
          │   Mongoose   │
          │ Model rules  │
          └──────┬───────┘
                 │
                 ▼
             MongoDB
```

### Joi

Concerned with:

```text
"Is this API request acceptable?"
```

### Mongoose

Concerned with:

```text
"Does this data satisfy my model rules?"
```

---

# 23. Why keep both?

You might ask:

> "If Joi already validates everything, why does Mongoose need validation?"

Because different layers have different responsibilities.

Suppose tomorrow you have:

```text
REST API
     │
     ├── Web app
     ├── Mobile app
     └── Admin script
```

Joi may protect one API boundary.

Mongoose still protects your model/data layer.

So:

```text
Joi
 ↓
API protection

Mongoose
 ↓
Model/data protection
```

---

# 24. Mongoose validation formatting

Suppose:

```js
err.name === "ValidationError"
```

and:

```js
err.errors
```

contains:

```js
{
    age: {
        message: "Path `age` (15) is less than minimum allowed value (18)."
    }
}
```

You can transform it:

```js
const details = {};

for (const field in err.errors) {
    details[field] = err.errors[field].message;
}
```

Result:

```js
{
    age: "Path `age` (15) is less than minimum allowed value (18)."
}
```

Then:

```text
Mongoose ValidationError
        ↓
normalize
        ↓
AppError
        ↓
global error middleware
```

# 26. Validation errors vs business errors

Don't confuse:

### Validation error

```text
The input is invalid.
```

Example:

```text
password = "123"
```

Usually:

```text
400 Bad Request
```

### Business error

```text
The input is valid, but the requested operation isn't possible.
```

Example:

```text
Email already exists
```

Potentially:

```text
409 Conflict
```

### Authentication error

```text
You haven't authenticated.
```

Usually:

```text
401 Unauthorized
```

### Authorization error

```text
You are authenticated, but aren't allowed.
```

Usually:

```text
403 Forbidden
```

These distinctions will become very important in the upcoming authentication and authorization phases.

---

# 27. Don't validate business logic with Joi

Suppose:

```text
User wants to delete a Todo.
```

Joi can check:

```text
todoId is a valid string
```

But Joi shouldn't decide:

```text
Does this Todo belong to this user?
```

That's business/authorization logic.

So:

```text
Joi
 ↓
"Is todoId shaped correctly?"

Service
 ↓
"Does this Todo belong to the user?"
```

This separation is extremely important.

# 32. A useful response contract

I recommend keeping your validation errors predictable.

For example:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Please enter a valid email",
    "password": "Password must be at least 8 characters"
  }
}
```

Notice:

```text
success
message
errors
```

The frontend always knows what to expect.

---

# 33. What if there is only one error?

Still use the same format:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Please enter a valid email"
  }
}
```

Don't create different formats such as:

```json
{
  "error": "Invalid email"
}
```

for one error and:

```json
{
  "errors": {}
}
```

for multiple errors.

Consistency is more important.

# 35. Common mistakes

## Mistake 1 — Validating inside every controller

Bad:

```js
const signup = async (req, res) => {

    const { error } = schema.validate(req.body);

    if (error) {
        ...
    }

    // logic
};
```

Do it in reusable middleware.

---

## Mistake 2 — Returning raw Joi errors

Bad:

```js
res.status(400).json(error);
```

Create your own API contract.

---

## Mistake 3 — Only returning the first error

Avoid unnecessarily using:

```js
abortEarly: true
```

when your frontend would benefit from all field errors.

Prefer:

```js
abortEarly: false
```

for form validation.

---

## Mistake 4 — Putting business rules into Joi

Don't use Joi for:

```text
"Does this user own this Todo?"
```

That's application logic.

---

## Mistake 5 — Thinking validation = sanitization

These are related but different.

```text
Validation
→ Is the input acceptable?

Sanitization
→ Can we safely normalize/clean it?
```

You'll study this distinction in Phase 9.

# 🧠 The Most Important Mental Model

Remember these four questions:

### 1. Is the request structurally valid?

```text
Joi
```

### 2. Does the model accept the data?

```text
Mongoose
```

### 3. Is the operation allowed?

```text
Service / Authorization
```

### 4. How should the error be communicated?

```text
Global Error Middleware
```

That's a very clean separation.

Your overall architecture is now becoming:

```text
Request
  ↓
Security
  ↓
Validation
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Model
  ↓
MongoDB
```

and errors from any layer can eventually flow into:

```text
             ERROR
               ↓
          AppError /
        Error Normalizer
               ↓
       Global Error Middleware
               ↓
          API Response
```

This is exactly the gradual architecture your starter-pack roadmap is designed to teach: validation comes after error handling, and later you'll turn it into a reusable validation architecture with request-body, params, query validation, formatting, whitelisting, stripping unknown fields, and normalization.
