# Lesson 8.17 — Handling JWT Errors

In **8.15**, we learned MongoDB errors.

In **8.16**, we learned validation errors.

Now we're going to handle **JWT errors**.

This is especially important because your starter architecture uses JWT authentication, and the roadmap places **JWT error handling directly after validation errors**.

The goal is not just to make JWT work. The goal is to understand:

> **When JWT verification fails, how does that failure travel through our backend and become a clean API response?**

---

# 1. First: What is a JWT error?

Suppose a protected route is:

```text
GET /api/v1/todos
```

The client sends:

```http
Authorization: Bearer eyJhbGciOiJIUzI1Ni...
```

Your authentication middleware does something like:

```js
jwt.verify(token, secret);
```

Sometimes verification succeeds.

Sometimes it fails.

For example:

```text
Token missing
Token malformed
Token expired
Token signed with wrong secret
Token not yet valid
```

These are **authentication failures**, not programming errors.

---

# 2. JWT's role in your architecture

Your starter roadmap eventually builds authentication like this:

```text
Authorization Header
        ↓
Extract Bearer token
        ↓
Verify JWT
        ↓
Find user information
        ↓
req.user
        ↓
next()
```

That's the intended authentication middleware flow.

So:

```text
Request
   ↓
authMiddleware
   ↓
jwt.verify()
   ↓
success?
 ┌─┴─┐
YES  NO
 │    │
 ▼    ▼
next  error
```

The error then needs to reach our global error system.

---

# 3. The three important JWT errors

When using the common `jsonwebtoken` library, you'll commonly encounter:

```text
JsonWebTokenError
TokenExpiredError
NotBeforeError
```

Let's understand each.

---

# 4. `JsonWebTokenError`

This is the general JWT verification error.

It can happen when the token is invalid.

For example:

```text
Malformed token
Invalid signature
Invalid token
```

Conceptually:

```text
Client
  ↓
bad JWT
  ↓
jwt.verify()
  ↓
JsonWebTokenError
```

---

# 5. Example

Suppose the client sends:

```http
Authorization: Bearer hello
```

That's not a valid JWT.

A JWT normally has three sections:

```text
header.payload.signature
```

So:

```text
hello
```

is obviously invalid.

`jwt.verify()` can throw:

```text
JsonWebTokenError
```

Your API shouldn't return:

```json
{
  "message": "jwt malformed"
}
```

as its public API contract.

Instead:

```json
{
  "success": false,
  "message": "Invalid authentication token"
}
```

Usually:

```http
401 Unauthorized
```

---

# 6. Why `401`?

Because the request doesn't contain valid authentication.

Remember:

```text
401
↓
Authentication problem
```

while:

```text
403
↓
Authorization problem
```

For example:

### Invalid token

```text
JWT invalid
→ 401
```

### Valid token but user isn't admin

```text
JWT valid
→ user authenticated
→ insufficient permissions
→ 403
```

This distinction will become very important in Phase 15 when you learn authorization/RBAC.

---

# 7. `TokenExpiredError`

This is another very common JWT error.

Suppose your access token expires after:

```text
15 minutes
```

Your starter roadmap intentionally teaches short-lived access tokens and longer-lived refresh tokens.

So:

```text
Login
  ↓
Access token
  ↓
15 minutes
  ↓
Expired
```

Now the client sends that token:

```text
GET /todos
Authorization: Bearer <expired-token>
```

`jwt.verify()` detects:

```text
TokenExpiredError
```

---

# 8. Should an expired token return 500?

Absolutely not.

Bad:

```text
Expired JWT
   ↓
500 Internal Server Error
```

An expired token is an expected authentication condition.

Better:

```text
Expired JWT
   ↓
401 Unauthorized
```

Response:

```json
{
  "success": false,
  "message": "Authentication token has expired"
}
```

---

# 9. Why is an expired token not a programming error?

Because expiration is intentional.

You deliberately configured:

```text
ACCESS_TOKEN_EXPIRES_IN=15m
```

Your roadmap explicitly distinguishes short-lived access tokens from longer-lived refresh tokens.

Therefore:

```text
Token expires
↓
Expected system behavior
```

not:

```text
Application crashed
```

This is why JWT authentication failures should be treated as **operational/client-facing errors**.

---

# 10. `NotBeforeError`

The third common error is:

```text
NotBeforeError
```

JWT can contain a `nbf` claim:

```text
not before
```

It means:

> This token should not be accepted before a particular time.

For example:

```text
Token created
       ↓
nbf = 10:00
       ↓
Request arrives at 09:59
       ↓
Token isn't valid yet
```

JWT verification can produce:

```text
NotBeforeError
```

You generally turn this into:

```text
401 Unauthorized
```

with a safe message such as:

```text
Authentication token is not active yet
```

---

# 11. The four JWT situations you should know

|Situation|Error|Typical status|
|---|---|--:|
|Missing token|Your own error|401|
|Invalid/malformed token|`JsonWebTokenError`|401|
|Expired token|`TokenExpiredError`|401|
|Not active yet|`NotBeforeError`|401|

The key idea:

```text
Authentication failed
        ↓
401
```

---

# 12. Missing token is slightly different

This is important.

If the request contains:

```http
GET /todos
```

but there is no:

```http
Authorization: Bearer ...
```

then `jwt.verify()` isn't even called.

Your middleware should detect it first.

For example:

```js
const authHeader = req.headers.authorization;

if (!authHeader) {
    throw new AppError(
        "Authentication required",
        401
    );
}
```

So:

```text
No token
 ↓
Your AppError
 ↓
401
```

Whereas:

```text
Bad token
 ↓
jsonwebtoken error
 ↓
normalize
 ↓
401
```

---

# 13. Don't expose JWT library messages

You might receive messages like:

```text
jwt malformed
```

or:

```text
invalid signature
```

or:

```text
jwt expired
```

You generally don't want your API contract to depend on these exact library messages.

Instead, create your own:

```text
Invalid authentication token
Authentication token has expired
Authentication required
```

Why?

Because your frontend shouldn't care which JWT library you use.

Today:

```text
jsonwebtoken
```

Tomorrow:

```text
another JWT implementation
```

Your API should still say:

```json
{
  "success": false,
  "message": "Invalid authentication token"
}
```

---

# 14. Error normalization again

Remember the concept from 8.15?

```text
External error
      ↓
Normalize
      ↓
AppError
      ↓
Global error middleware
```

JWT follows exactly the same pattern.

```text
jsonwebtoken
      ↓
JWT error
      ↓
normalize
      ↓
AppError(401)
      ↓
error.middleware
      ↓
JSON
```

This is one of the most important architectural patterns in this phase.

---

# 15. Example JWT middleware

A simple learning version:

```js
import jwt from "jsonwebtoken";
import AppError from "../utils/AppError.js";

const authMiddleware = (req, res, next) => {
    const authHeader = req.headers.authorization;

    if (!authHeader) {
        return next(
            new AppError(
                "Authentication required",
                401
            )
        );
    }

    const [scheme, token] = authHeader.split(" ");

    if (scheme !== "Bearer" || !token) {
        return next(
            new AppError(
                "Invalid authentication header",
                401
            )
        );
    }

    try {
        const decoded = jwt.verify(
            token,
            process.env.ACCESS_TOKEN_SECRET
        );

        req.user = decoded;

        next();

    } catch (error) {
        next(error);
    }
};
```

Notice something important:

```js
catch (error) {
    next(error);
}
```

We're not responding directly.

We're sending the error into the central error system.

---

# 16. Why use `next(error)`?

Because your architecture is:

```text
Middleware
    ↓
next(error)
    ↓
Global Error Middleware
```

Instead of:

```js
catch (error) {
    res.status(401).json(...);
}
```

inside every middleware.

Centralizing the final response keeps your architecture consistent.

---

# 17. But now we have a problem

Suppose:

```js
next(error);
```

receives:

```text
TokenExpiredError
```

Our global error middleware needs to understand it.

So:

```js
if (err.name === "TokenExpiredError") {
    ...
}
```

Likewise:

```js
if (err.name === "JsonWebTokenError") {
    ...
}
```

and:

```js
if (err.name === "NotBeforeError") {
    ...
}
```

---

# 18. JWT error normalization

You can create:

```js
const normalizeJwtError = (err) => {

    if (err.name === "TokenExpiredError") {
        return new AppError(
            "Authentication token has expired",
            401
        );
    }

    if (err.name === "JsonWebTokenError") {
        return new AppError(
            "Invalid authentication token",
            401
        );
    }

    if (err.name === "NotBeforeError") {
        return new AppError(
            "Authentication token is not active",
            401
        );
    }

    return err;
};
```

Now:

```text
JWT library
   ↓
normalizeJwtError()
   ↓
AppError
```

---

# 19. Global error middleware

Then:

```js
const errorMiddleware = (err, req, res, next) => {

    if (
        err.name === "TokenExpiredError" ||
        err.name === "JsonWebTokenError" ||
        err.name === "NotBeforeError"
    ) {
        err = normalizeJwtError(err);
    }

    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message: err.message
    });
};
```

Again, this is a learning version.

Later, you'll improve the architecture so the middleware isn't full of conditionals.

---

# 20. Better architecture

Eventually:

```text
                 ERROR
                   │
        ┌──────────┼──────────┐
        │          │          │
      Mongo       JWT       Joi
        │          │          │
        ▼          ▼          ▼
     Normalize  Normalize  Normalize
        │          │          │
        └──────────┼──────────┘
                   ▼
                AppError
                   │
                   ▼
          Global Error Middleware
                   │
                   ▼
             JSON Response
```

That's a much cleaner mental model.

# 21. Access token vs refresh token

This is where JWT errors connect with your authentication architecture.

Your roadmap teaches:

```text
ACCESS TOKEN
Short-lived
Used for API authorization
```

and:

```text
REFRESH TOKEN
Long-lived
Used to obtain a new access token
```

The intended flow is:

```text
Login
  │
  ├── Access Token
  │       ↓
  │   Authorization header
  │
  └── Refresh Token
          ↓
      HttpOnly cookie
```

So when an **access token expires**, you usually don't want the user to log in again immediately.

Instead:

```text
Access token expired
       ↓
401
       ↓
Frontend calls refresh endpoint
       ↓
Refresh token checked
       ↓
New access token
       ↓
Retry original request
```

The detailed refresh-token architecture comes later in Phase 14, so for now focus on understanding the error flow.

---

# 22. Important: Don't automatically refresh every 401

This is a common frontend mistake.

Suppose:

```text
POST /todos
```

returns:

```text
401
```

That doesn't necessarily mean:

```text
access token expired
```

It could mean:

```text
invalid token
```

or:

```text
authentication missing
```

So ideally your system distinguishes cases appropriately.

For example:

```text
expired access token
        ↓
refresh flow

invalid/tampered token
        ↓
logout / re-authentication
```

Don't blindly retry forever.

---

# 23. Infinite refresh loop

Imagine your Axios interceptor does:

```text
401
 ↓
refresh
 ↓
retry
 ↓
401
 ↓
refresh
 ↓
retry
 ↓
401
...
```

Congratulations, you've created an infinite loop. 😄

A good frontend architecture needs protection such as:

```text
retry only once
```

But that's a frontend concern.

From the backend perspective, the important lesson is:

> **Return consistent and meaningful authentication errors.**

---

# 24. JWT signature error

Suppose the server signs tokens using:

```text
SECRET_A
```

but verification uses:

```text
SECRET_B
```

The signature won't match.

Result:

```text
JsonWebTokenError
```

Conceptually:

```text
Token
 ↓
signature
 ↓
verify using wrong secret
 ↓
FAIL
```

Response:

```http
401 Unauthorized
```

Not:

```http
500 Internal Server Error
```

The client supplied a token that cannot be trusted.

---

# 25. Why signature errors are security-sensitive

Suppose you return:

```json
{
  "success": false,
  "message": "Invalid signature because server expected SECRET_A"
}
```

Obviously terrible.

Never expose:

```text
JWT secrets
internal configuration
signing keys
stack traces
```

The roadmap explicitly separates **hiding sensitive errors in production** into Lesson 8.18.

So for now remember:

```text
Internal:
JsonWebTokenError
invalid signature
stack trace
secret configuration

External:
Invalid authentication token
```

---

# 26. JWT payload shouldn't be blindly trusted

Suppose the decoded token contains:

```json
{
  "userId": "123",
  "role": "admin"
}
```

After successful verification:

```js
const decoded = jwt.verify(token, secret);
```

you can trust that the token was correctly signed by your server **subject to your token validation rules**.

But don't turn this into:

```js
req.user = decoded;
```

and assume the database state can never change.

For sensitive operations, you may still need to check the current user state.

For example:

```text
Token says:
role = admin

Database says:
role = user
```

Which should win?

Your application needs a deliberate policy.

Authorization is a later phase in your roadmap.

---

# 27. JWT verification isn't authorization

This distinction is extremely important.

JWT verification answers:

> **Is this token valid?**

Authorization answers:

> **Is this user allowed to perform this action?**

Example:

```text
JWT
 ↓
valid
 ↓
User authenticated
```

But:

```text
DELETE /admin/users/123
```

might require:

```text
role = admin
```

So:

```text
Authentication
    ↓
Who are you?

Authorization
    ↓
What are you allowed to do?
```

Your roadmap explicitly separates these into authentication and authorization/RBAC phases.

---

# 28. Missing token vs invalid token

These are worth keeping separate.

### Missing

```http
GET /todos
```

No Authorization header.

Response:

```json
{
  "success": false,
  "message": "Authentication required"
}
```

Status:

```text
401
```

### Invalid

```http
Authorization: Bearer abc
```

Response:

```json
{
  "success": false,
  "message": "Invalid authentication token"
}
```

Status:

```text
401
```

### Expired

```json
{
  "success": false,
  "message": "Authentication token has expired"
}
```

Status:

```text
401
```

All are authentication failures, but the messages can help the client decide what to do.

# 29. Should you reveal that a token is expired?

This is a design decision.

For your own API, something like:

```text
Authentication token has expired
```

is often useful because the frontend can trigger refresh.

But don't expose unnecessary internals like:

```text
expiration timestamp
secret
JWT payload
stack trace
library internals
```

Keep the message at the API level.

Your application is starting to have several error categories:

├── Authentication

# 36. A practical implementation

You can create a JWT error helper:

```js
const handleJwtError = (err) => {
    switch (err.name) {
        case "TokenExpiredError":
            return new AppError(
                "Authentication token has expired",
                401
            );

        case "JsonWebTokenError":
            return new AppError(
                "Invalid authentication token",
                401
            );

        case "NotBeforeError":
            return new AppError(
                "Authentication token is not active",
                401
            );

        default:
            return err;
    }
};
```

Then:

```js
const errorMiddleware = (err, req, res, next) => {

    if (
        err.name === "TokenExpiredError" ||
        err.name === "JsonWebTokenError" ||
        err.name === "NotBeforeError"
    ) {
        err = handleJwtError(err);
    }

    // continue with normal error handling...
};
```

# 37. Better: normalize near the source

An even cleaner approach is to handle JWT-specific errors in the authentication middleware:

```js
try {

    const decoded = jwt.verify(token, secret);

    req.user = decoded;

    next();

} catch (error) {

    if (error.name === "TokenExpiredError") {
        return next(
            new AppError(
                "Authentication token has expired",
                401
            )
        );
    }

    if (error.name === "JsonWebTokenError") {
        return next(
            new AppError(
                "Invalid authentication token",
                401
            )
        );
    }

    next(error);
}
```

Then the global error middleware doesn't need to know about `jsonwebtoken`.

That's a nice separation:

```text
auth middleware
    ↓
understands JWT

global error middleware
    ↓
understands AppError
```

This is the direction I'd recommend for the architecture you're building.

---

# 38. Why is that better?

Imagine you replace:

```text
jsonwebtoken
```

with another authentication library later.

If the global error middleware contains:

```js
if (err.name === "TokenExpiredError")
```

then your global error system knows about the JWT library.

That's unnecessary coupling.

Instead:

```text
JWT library
     ↓
auth middleware
     ↓
AppError
     ↓
global error middleware
```

Now the global layer doesn't care where the error came from.

This is the same normalization principle we've been building throughout Phase 8.

---

# 39. Don't do this

Avoid:

```js
try {
    const decoded = jwt.verify(token, secret);
} catch (error) {
    console.log(error);
    res.status(500).json({
        error: error
    });
}
```

Problems:

```text
❌ 500 for authentication failure
❌ raw library error exposed
❌ inconsistent response
❌ auth middleware owns HTTP response
❌ difficult to maintain
```

---

# 40. Prefer this

```js
try {
    const decoded = jwt.verify(token, secret);

    req.user = decoded;

    next();

} catch (error) {
    next(
        new AppError(
            "Invalid authentication token",
            401
        )
    );
}
```

And:

```text
auth middleware
      ↓
AppError
      ↓
global error middleware
```

Much cleaner.

# 41. One subtle problem: don't hide expiration accidentally

If you convert **every JWT error** into:

```text
Invalid authentication token
```

you lose the distinction between:

```text
expired
```

and:

```text
tampered/invalid
```

For example:

```js
catch (error) {
    next(
        new AppError(
            "Invalid authentication token",
            401
        )
    );
}
```

This is safe but less informative.

A better version:

```js
catch (error) {

    if (error.name === "TokenExpiredError") {
        return next(
            new AppError(
                "Authentication token has expired",
                401
            )
        );
    }

    return next(
        new AppError(
            "Invalid authentication token",
            401
        )
    );
}
```

Now the frontend can distinguish:

```text
expired
```

from:

```text
invalid
```

without seeing JWT internals.

---

# 42. Security principle

Remember:

> **Give the client enough information to handle the situation, but not enough information to expose your internals.**

Good:

```text
Authentication token has expired
```

Bad:

```text
TokenExpiredError: jwt expired at 2026-08-18T...
stack: ...
secret: ...
```

This principle becomes the main topic of **Lesson 8.18 — Hiding Sensitive Errors in Production**.

|Missing JWT|No Authorization header|`401`|
|Invalid JWT|Bad signature/token|`401`|
|Expired JWT|Access token expired|`401`|
|Authorization failure|User isn't admin|`403`|
|Resource missing|Todo doesn't exist|`404`|
|Unexpected error|Programming/server failure|`500`|

The exact status convention can vary by API design, but this is a sensible baseline for your starter.

# 🧠 The Most Important Mental Model

Don't think:

> "`jwt.verify()` throws some weird error."

Think:

```text
JWT library
    ↓
Authentication middleware understands it
    ↓
Convert it into AppError
    ↓
next(error)
    ↓
Global error middleware
    ↓
Safe API response
```

And remember:

```text
Missing token
     ↓
401

Invalid token
     ↓
401

Expired token
     ↓
401

Valid token
     ↓
Authentication successful
     ↓
Continue
```

Then:

```text
Valid token
     ↓
But user doesn't have permission
     ↓
403
```

That last distinction is the bridge from **authentication** to **authorization**, which you'll explore later in the roadmap.
