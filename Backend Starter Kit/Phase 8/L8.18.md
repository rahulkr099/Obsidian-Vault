# Lesson 8.18 — Hiding Sensitive Errors in Production

This lesson is the natural next step after **8.17 JWT errors**.

Your Phase 8 roadmap specifically defines **8.18 as “Hiding sensitive errors in production”**.

The main idea is simple:

> **Developers need detailed errors. Users should receive safe, useful errors.**

---

# 1. The problem

Imagine something goes wrong in your backend.

For example:

```js
const user = await User.findById(userId);
```

and MongoDB throws an error.

During development, you might see:

```text
MongoServerError: ...
    at Connection.sendCommand (...)
    at process.processTicksAndRejections (...)
    at ...
```

That's useful to **you**.

But imagine sending that entire error to the browser:

```json
{
  "success": false,
  "error": "MongoServerError: ...",
  "stack": "at Connection.sendCommand..."
}
```

That's a bad production API.

It can expose:

- internal implementation details
    
- database information
    
- file paths
    
- library names/versions
    
- stack traces
    
- query details
    
- authentication internals
    
- potentially sensitive data
    

So we need two different behaviors:

```text
Development
    ↓
Detailed error

Production
    ↓
Safe error
```

---

# 2. Think of it as two audiences

Your error system has two audiences:

```text
                ERROR
                  │
          ┌───────┴────────┐
          │                │
       Developer          User
          │                │
          ▼                ▼
   Detailed information   Safe message
```

### Developer

Needs:

```text
What happened?
Where?
Why?
Stack trace?
Database error?
```

### User

Usually needs:

```text
What happened?
Can I fix it?
Should I retry?
```

The user doesn't need:

```text
Which line of Node.js crashed?
Which MongoDB operation failed internally?
Which package generated the exception?
```

---

# 3. Development vs production

A useful mental model:

### Development

```text
NODE_ENV=development
```

You can expose more information **to yourself**.

For example:

```json
{
  "success": false,
  "message": "Something went wrong",
  "error": "CastError",
  "stack": "..."
}
```

### Production

```text
NODE_ENV=production
```

Return:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

And log the actual error internally.

---

# 4. Never lose the original error

There is an important distinction:

> **Hide an error from the client ≠ delete the error.**

Suppose production encounters:

```text
MongoServerError
```

Don't do:

```js
catch (error) {
    // ignore it
}
```

Instead:

```text
Error
 │
 ├── log detailed information internally
 │
 └── send safe information to client
```

So:

```text
              ERROR
                │
        ┌───────┴────────┐
        │                │
        ▼                ▼
      Logger          Response
        │                │
        ▼                ▼
 detailed error      safe error
```

This is one of the most important production concepts.

---

# 5. Example

Suppose this happens:

```js
throw new Error("MongoDB connection failed at cluster xyz...");
```

Internally:

```text
Error
message:
MongoDB connection failed at cluster xyz...

stack:
...
```

### Log

```text
[ERROR] MongoDB connection failed...
```

### Client

```json
{
  "success": false,
  "message": "Internal server error"
}
```

The developer can investigate.

The client doesn't receive your internal architecture.

---

# 6. Why stack traces are dangerous

A stack trace can look like:

```text
Error: Something failed
    at createUser (/app/src/services/auth.service.js:42:11)
    at processRequest (/app/src/controllers/auth.controller.js:17:5)
    at ...
```

This reveals:

```text
/app/src/
services/
controllers/
file names
line numbers
```

Even though this may not immediately compromise your application, there's no reason to expose unnecessary internal information.

Production should generally avoid returning stack traces to clients.

# 7. Your `AppError` makes this easier

You've already learned:

```js
new AppError(
    "User not found",
    404
);
```

The important thing is that `AppError` represents an **expected, controlled error**.

For example:

```js
throw new AppError(
    "Todo not found",
    404
);
```

This is safe to send:

```json
{
  "success": false,
  "message": "Todo not found"
}
```

But:

```js
throw new Error(
    "Unexpected database failure..."
);
```

should usually become:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

in production.

---

# 8. Operational vs programming errors

This connects directly to **Lesson 8.11**.

Remember:

### Operational error

Expected application condition.

Examples:

```text
User not found
Invalid input
Expired JWT
Email already exists
Todo doesn't exist
```

These can have useful client-facing messages.

---

### Programming/unexpected error

Something went wrong internally.

Examples:

```text
undefined.someProperty
Database connection failure
Unexpected library exception
Programming bug
```

Don't expose the internal details.

Instead:

```text
Internal server error
```

---

# 9. The basic production rule

Think:

```text
Operational error
       ↓
Known + safe
       ↓
Send useful message
```

But:

```text
Unexpected error
       ↓
Unknown + potentially sensitive
       ↓
Log detailed error
       ↓
Send generic message
```

---

# 10. A simple error middleware

You could start with:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message: err.message
    });
};
```

But there's a problem.

Suppose:

```js
throw new Error(
    "Mongo connection failed because internal server xyz..."
);
```

Then:

```js
err.message
```

gets exposed.

We need to distinguish safe errors from unexpected errors.

---

# 11. Using `isOperational`

Your `AppError` can have:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}
```

Now:

```text
AppError
   ↓
isOperational = true
```

while:

```js
new Error("Unexpected failure")
```

doesn't have that property.

So the error middleware can distinguish them.

---

# 12. Production error middleware

Conceptually:

```js
const errorMiddleware = (err, req, res, next) => {
    const isProduction =
        process.env.NODE_ENV === "production";

    if (isProduction) {

        if (err.isOperational) {
            return res.status(err.statusCode).json({
                success: false,
                message: err.message
            });
        }

        return res.status(500).json({
            success: false,
            message: "Internal server error"
        });
    }

    // Development response
    return res.status(err.statusCode || 500).json({
        success: false,
        message: err.message,
        stack: err.stack
    });
};
```

This gives us two behaviors.

Suppose:

```js
throw new Error("Database query failed");
```

Development might return:

```json
{
  "success": false,
  "message": "Database query failed",
  "stack": "Error: Database query failed..."
}
```

That's useful while you're building.

# 14. Production response

Same error:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

Much safer.

# 15. But there's an even better approach

Don't expose stack traces from your backend API at all.

Instead, use your logger.

Conceptually:

```text
Production error
      │
      ├──────────────→ Logger
      │                  │
      │                  ▼
      │             detailed error
      │
      └──────────────→ Client
                         │
                         ▼
                  safe response
```

For example:

```js
logger.error({
    err,
    requestId: req.requestId
}, "Unhandled error");
```

Then:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc-123"
}
```

The roadmap later dedicates Phase 19 to logging and observability, including request IDs, error logging, and sensitive data in logs.

---

# 16. Why include a request ID?

Imagine a user tells you:

> "I got an internal server error."

You check your logs.

There might be:

```text
10,000 requests
```

How do you find the user's exact error?

Give every request a unique ID:

```text
requestId
   ↓
abc-123
```

Return:

```json
{
  "success": false,
  "message": "Internal server error",
  "requestId": "abc-123"
}
```

Now you can search logs:

```text
requestId=abc-123
```

and find the exact failure.

This is the topic of the next lesson, **8.19 — Request ID + Error Handling**.

# 17. Never expose environment variables

Imagine this accidentally gets thrown:

```js
throw new Error(
    `Database URI: ${process.env.MONGO_URI}`
);
```

If you return:

```js
res.json({
    error: err.message
});
```

you might expose:

```text
mongodb+srv://username:password@cluster...
```

That's extremely dangerous.

So never expose:

```text
DATABASE_URL
MONGO_URI
JWT_SECRET
ACCESS_TOKEN_SECRET
REFRESH_TOKEN_SECRET
SMTP_PASSWORD
API keys
cloud credentials
```

Your starter specifically uses environment variables for secrets such as MongoDB and JWT configuration.

# 19. Database errors

Suppose MongoDB produces:

```text
MongoServerError
E11000 duplicate key error
collection: users
index: email_1
```

You probably don't want to return:

```json
{
  "error": "E11000 duplicate key error collection users index email_1"
}
```

Instead, your error normalization can convert it to:

```json
{
  "success": false,
  "message": "Email already exists"
}
```

This is exactly the kind of transformation you learned in **8.15**.

# 20. Validation errors

Validation errors are generally safe to expose because the client needs them.

For example:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "Please enter a valid email",
    "password": "Password must be at least 8 characters"
  }
}
```

That's useful information.

But don't expose internal validation objects containing unnecessary internals.

---

# 21. What about programming errors?

Suppose you accidentally write:

```js
const user = null;

console.log(user.name);
```

Node throws:

```text
TypeError:
Cannot read properties of null
```

Don't return:

```json
{
  "success": false,
  "message": "Cannot read properties of null (reading 'name')",
  "stack": "..."
}
```

Production should return:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

And your logger should receive the real error.

# 22. A useful error decision tree

Memorize this:

```text
                 ERROR
                   │
                   ▼
          Is it an AppError?
             /          \
           YES           NO
            │             │
            ▼             ▼
      Is it safe?     Unexpected
            │             │
            ▼             ▼
      Client message   Log details
                          │
                          ▼
                    Generic message
```

More simply:

```text
Known + safe
    ↓
show useful message

Unknown + internal
    ↓
hide details
    ↓
log everything internally
```

# 23. Don't make production completely blind

A beginner might think:

> "If we hide errors, we won't know what happened."

Wrong.

You hide them **from the client**, not from yourself.

You should have:

```text
                 Error
                   │
          ┌────────┴─────────┐
          │                  │
          ▼                  ▼
      Application          Logger
       response               │
          │                   ▼
          ▼             Full details
    Safe message
```

That's the professional approach.

A production error log could contain:

# 25. Don't log everything

This is just as important as hiding errors from users.

Bad:

```js
console.log(req.body);
```

because `req.body` could contain:

```json
{
  "email": "rahul@example.com",
  "password": "secret123"
}
```

You just logged a password.

Never casually log:

```text
passwords
JWTs
refresh tokens
cookies
authorization headers
API keys
credit-card information
private secrets
```

Your roadmap explicitly includes **“Sensitive data in logs”** later in the observability phase.

# 27. Why stable error messages matter

Suppose your frontend checks:

```js
if (error.response.data.message === "Token expired") {
    refreshToken();
}
```

If you suddenly change it to:

```text
JWT expired
```

your frontend might break.

So your API error messages should be deliberately designed.

Even better, eventually use an error code:

```json
{
  "success": false,
  "message": "Authentication token has expired",
  "code": "AUTH_TOKEN_EXPIRED"
}
```

Then frontend logic can use:

```js
if (error.code === "AUTH_TOKEN_EXPIRED") {
    // refresh
}
```

This is more stable than matching human-readable messages.

Your later API response architecture phase covers consistent API contracts and error responses in more depth.

consider:

  "success": false,

while the message remains human-readable.

This is a useful improvement to keep in mind for your eventual starter.

# 30. Example complete error middleware

Here's a learning-oriented version:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    const isProduction =
        process.env.NODE_ENV === "production";

    // Always log unexpected errors internally
    if (!err.isOperational) {
        console.error(err);
    }

    // Production
    if (isProduction) {

        if (err.isOperational) {
            return res.status(statusCode).json({
                success: false,
                message: err.message
            });
        }

        return res.status(500).json({
            success: false,
            message: "Internal server error"
        });
    }

    // Development
    return res.status(statusCode).json({
        success: false,
        message: err.message,
        stack: err.stack
    });
};
```

This isn't your final logging architecture yet. It simply demonstrates the core concept.

Suppose:

```http

```

Your API should produce something like:

```json
{
  "success": false,
  "message": "Route not found"
}
```

No stack trace is needed for the user.

Suppose your code crashes unexpectedly.

Production:

```json
{
  "success": false,
  "message": "Internal server error"
}
```

Internally:

```text
requestId=abc123
TypeError

```

# 34. Don't leak implementation details through status codes

For example, don't create responses like:

```json
{
  "message": "MongoDB is down"
}
```

unless the client genuinely needs to know.

Prefer:

```json
{
  "message": "Service temporarily unavailable"
}
```

The client cares that the operation couldn't complete.

It doesn't necessarily need to know:

```text
MongoDB
Redis
SMTP
internal service
```

was responsible.

---

# 35. Security principle: information disclosure

There's a general security problem here:

> **Information disclosure**

An attacker can learn about your system from overly detailed errors.

For example:

```text
MongoDB collection names
database structure
file paths
JWT implementation
authentication internals
package details
server configuration
```

Each piece might seem harmless.

Together, they provide useful information about your application.

So:

```text
Less unnecessary information
        ↓
Smaller attack surface
```

---

# 36. But don't hide useful client errors

Security does **not** mean:

```json
{
  "message": "Something went wrong"
}
```

for everything.

That's frustrating.

For example:

```text
Invalid email
Password too short
Todo not found
Token expired
Email already exists
```

are useful and safe.

The goal isn't:

> Hide everything.

The goal is:

> **Hide internal information while keeping client-facing information useful.**
