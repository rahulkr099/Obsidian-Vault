# Lesson 8.2 — JavaScript `try/catch` in Depth

In **8.1**, we learned the main problem:

> Errors can happen anywhere in a backend, so we need a consistent way to handle them.

Now we need to properly understand JavaScript's built-in error mechanism before creating `AppError` or `asyncHandler`.

---

# 1. What exactly is `try/catch`?

The basic structure is:

```js
try {
    // code that might fail
} catch (error) {
    // what to do if it fails
}
```

Example:

```js
try {
    const result = JSON.parse("hello");

    console.log(result);
} catch (error) {
    console.log("Something went wrong");
}
```

Execution:

```text
try
 │
 ▼
JSON.parse("hello")
 │
 ▼
❌ Error
 │
 ▼
catch(error)
 │
 ▼
"Something went wrong"
```

Instead of allowing the error to continue uncontrolled, `catch` gets a chance to handle it.

---

# 2. What happens without `try/catch`?

Consider:

```js
const data = JSON.parse("hello");

console.log(data);
```

`"hello"` isn't valid JSON.

So JavaScript throws an error.

You may see something like:

```text
SyntaxError: Unexpected token 'h'...
```

And execution stops at that point.

For example:

```js
const data = JSON.parse("hello");

console.log("This will not execute");
```

The `console.log()` won't run.

---

# 3. With `try/catch`

Now:

```js
try {
    const data = JSON.parse("hello");

    console.log(data);
} catch (error) {
    console.log("Invalid JSON");
}

console.log("Application continues");
```

Execution:

```text
try
 ↓
JSON.parse()
 ↓
ERROR
 ↓
catch
 ↓
Invalid JSON
 ↓
Application continues
```

This is an important concept:

> `catch` prevents the error from automatically terminating this execution path.

---

# 4. What does `throw` mean?

You can manually create an error condition using:

```js
throw
```

Example:

```js
throw new Error("Something went wrong");
```

This means:

> Stop normal execution here and throw this error.

For example:

```js
console.log("Before");

throw new Error("Something went wrong");

console.log("After");
```

Output:

```text
Before
Error: Something went wrong
```

This won't execute:

```js
console.log("After");
```

because execution stopped at `throw`.

---

# 5. Catching a manually thrown error

Now:

```js
try {
    throw new Error("Something went wrong");
} catch (error) {
    console.log(error.message);
}
```

Output:

```text
Something went wrong
```

Flow:

```text
throw
  ↓
Error object
  ↓
catch(error)
  ↓
error.message
```

This is the foundation of our future:

```js
throw new AppError(...)
```

---

# 6. `throw` doesn't only work with `Error`

JavaScript technically allows you to throw almost anything.

For example:

```js
throw "Something went wrong";
```

or:

```js
throw 404;
```

or:

```js
throw { message: "Something went wrong" };
```

These are technically valid.

But **don't do this in backend applications**.

Prefer:

```js
throw new Error("Something went wrong");
```

Why?

Because `Error` provides useful properties such as:

```js
error.message
error.name
error.stack
```

And later we'll create:

```js
class AppError extends Error
```

---

# 7. Understanding the `Error` object

Let's examine:

```js
const error = new Error("User not found");
```

Now:

```js
console.log(error.message);
```

gives:

```text
User not found
```

And:

```js
console.log(error.name);
```

gives:

```text
Error
```

And:

```js
console.log(error.stack);
```

gives a stack trace showing where the error originated.

Conceptually:

```text
Error
├── name
├── message
└── stack
```

---

# 8. Why is `error.stack` useful?

Suppose your backend produces:

```text
Error: User not found
    at getUser (...)
    at userService (...)
    at userController (...)
```

This tells the developer:

> Where did this error come from?

That's extremely useful when debugging.

But you generally **shouldn't expose the full stack trace to API clients in production**.

Bad:

```json
{
    "success": false,
    "stack": "Error: User not found at..."
}
```

Better:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

The stack can be logged internally.

We'll build this properly later in:

```text
8.16 Global Error Middleware
```

---

# 9. `catch(error)` gives us the actual error

Consider:

```js
try {
    throw new Error("Database connection failed");
} catch (error) {
    console.log(error);
}
```

The `error` variable contains the object created by:

```js
new Error("Database connection failed")
```

So:

```js
error.message
```

is:

```text
Database connection failed
```

---

# 10. You can create your own error variable

This:

```js
throw new Error("User not found");
```

is essentially creating an error object and throwing it.

You can also write:

```js
const error = new Error("User not found");

throw error;
```

Then:

```js
try {
    const error = new Error("User not found");

    throw error;
} catch (error) {
    console.log(error.message);
}
```

This distinction becomes useful when we later create custom errors.

---

# 11. Nested `try/catch`

You can have a `try/catch` inside another `try/catch`.

Example:

```js
try {
    try {
        throw new Error("Inner error");
    } catch (error) {
        console.log("Inner catch:", error.message);

        throw error;
    }
} catch (error) {
    console.log("Outer catch:", error.message);
}
```

Output:

```text
Inner catch: Inner error
Outer catch: Inner error
```

What's happening?

```text
             Error
               ↓
        Inner try/catch
               ↓
          Inner catch
               ↓
            throw
               ↓
        Outer catch
```

The inner `catch` handles the error, but it can **rethrow** it.

---

# 12. What does rethrowing mean?

This:

```js
catch (error) {
    throw error;
}
```

means:

> I caught this error, but I don't want to finish handling it here. Send it to the next error handler.

This idea is very important for backend architecture.

For example:

```text
Service
  ↓
error occurs
  ↓
service doesn't know how to respond HTTP
  ↓
throw error
  ↓
controller/Express
  ↓
global error middleware
  ↓
HTTP response
```

The service doesn't need to do:

```js
res.status(...)
```

because the service shouldn't know about HTTP.

---

# 13. `finally`

JavaScript also provides:

```js
finally
```

Structure:

```js
try {
    // attempt something
} catch (error) {
    // handle error
} finally {
    // always execute
}
```

Example:

```js
try {
    console.log("Trying...");
} catch (error) {
    console.log("Error");
} finally {
    console.log("Finished");
}
```

Output:

```text
Trying...
Finished
```

---

# 14. `finally` runs even when there is an error

```js
try {
    throw new Error("Something failed");
} catch (error) {
    console.log("Caught");
} finally {
    console.log("Cleanup");
}
```

Output:

```text
Caught
Cleanup
```

Flow:

```text
try
 ↓
error
 ↓
catch
 ↓
finally
```

---

# 15. Why is `finally` useful in backend development?

Imagine you open some resource:

```text
Open resource
    ↓
Perform operation
    ↓
Close resource
```

You want the cleanup to happen whether the operation succeeds or fails.

Conceptually:

```js
try {
    // use resource
} catch (error) {
    // handle error
} finally {
    // cleanup
}
```

Examples can include:

```text
database/session cleanup
file handles
temporary resources
locks
```

You won't use `finally` everywhere in Express, but understanding it is important.

---

# 16. Important: `return` and `finally`

Consider:

```js
function test() {
    try {
        return "try";
    } finally {
        console.log("finally");
    }
}

console.log(test());
```

Output:

```text
finally
try
```

Even though `return` happens inside `try`, `finally` executes before the function actually returns.

So remember:

```text
return
  ↓
finally executes
  ↓
function returns
```

---

# 17. What if `catch` throws another error?

Example:

```js
try {
    throw new Error("Original error");
} catch (error) {
    console.log("Caught original error");

    throw new Error("New error");
}
```

Now the original error has been replaced by another error.

Flow:

```text
Original Error
      ↓
    catch
      ↓
New Error
      ↓
continues upward
```

This is different from:

```js
throw error;
```

which preserves the original error.

---

# 18. Why this matters for your backend

Suppose your repository encounters:

```text
MongoDB error
```

Your service might catch it for a specific reason.

But if it cannot properly handle it:

```js
catch (error) {
    throw error;
}
```

Then the error can continue upward.

Eventually:

```text
Repository
    ↓
Service
    ↓
Controller
    ↓
asyncHandler
    ↓
Express error middleware
```

That's the architecture we're building.

---

# 19. A common beginner mistake

Don't do this:

```js
try {
    await something();
} catch (error) {
    console.log(error);
}
```

and then simply continue as if everything succeeded.

For example:

```js
try {
    await createUser();
} catch (error) {
    console.log(error);
}

res.json({
    success: true
});
```

If `createUser()` fails, you're still returning:

```json
{
    "success": true
}
```

That's obviously wrong.

Instead, either handle the error correctly or propagate it:

```js
try {
    await createUser();
} catch (error) {
    throw error;
}
```

Later, `asyncHandler` will help us avoid writing this repetitive pattern.

---

# 20. Another common mistake: hiding errors

Avoid:

```js
catch (error) {
    console.log("Error");
}
```

You lose valuable information.

At minimum during development:

```js
catch (error) {
    console.error(error);
}
```

And in our production architecture, we'll use structured logging.

---

# 21. Another mistake: exposing internal errors

Don't blindly do:

```js
res.status(500).json({
    message: error.message
});
```

Why?

Because the message might reveal internal information.

Imagine MongoDB produces:

```text
MongoServerError: E11000 duplicate key error collection...
```

You probably don't want to expose all database internals.

Instead, the global error handler decides what the client should see.

```text
                     ERROR
```


# 🧠 The Most Important Mental Model

Remember this:

```text
throw
  ↓
creates/propagates an error
  ↓
nearest matching catch
  ↓
catch can:
    ├── handle it
    ├── rethrow it
    └── transform it
```

And for your backend:

```text
Repository
    │
    │ throw
    ▼
Service
    │
    │ throw
    ▼
Controller
    │
    │ async error
    ▼
asyncHandler
    │
    │ next(error)
    ▼
Global Error Middleware
    │
    ▼
HTTP Response
```

### One sentence to remember

> **`try/catch` is JavaScript's basic error-control mechanism; our backend architecture will build a standardized system on top of it.**
