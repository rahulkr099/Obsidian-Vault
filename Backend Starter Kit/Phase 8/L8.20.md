# Lesson 8.20 — Build the Complete Error Architecture

This is the **final lesson of Phase 8**. The goal is not to learn one more isolated concept. It is to connect everything you've learned from **8.1 → 8.19** into one clean backend error system.

Your roadmap places **8.20 as “Build the complete error architecture.”**

By the end of this lesson, you should understand exactly what happens when **anything goes wrong anywhere in your backend**.

---

# 1. First: What problem are we solving?

Without an error architecture, a backend can become messy very quickly.

You might have:

```js
try {
    // database
} catch (error) {
    res.status(500).json(...);
}
```

inside every controller.

Then another controller:

```js
try {
    // something
} catch (error) {
    res.status(400).json(...);
}
```

And another:

```js
try {
    // something
} catch (error) {
    console.log(error);
    res.status(500).json(...);
}
```

Soon you have:

```text
Controller A → error format A
Controller B → error format B
Controller C → error format C
Controller D → error format D
```

That's exactly what we want to avoid.

---

# 2. Our goal

We want:

```text
ANY ERROR
    ↓
ONE CENTRAL ERROR SYSTEM
    ↓
ONE CONSISTENT RESPONSE
```

Our architecture should look like:

```text
                    REQUEST
                       │
                       ▼
                Request ID
                       │
                       ▼
                     Logger
                       │
                       ▼
                    Routes
                       │
                       ▼
                  Controller
                       │
                       ▼
                    Service
                       │
                       ▼
                  Repository
                       │
                       ▼
                   Database
                       │
                       │
                     ERROR
                       │
                       ▼
                 Error Pipeline
                       │
                       ▼
             Global Error Handler
                       │
               ┌───────┴────────┐
               │                │
               ▼                ▼
           Developer           Client
               │                │
               ▼                ▼
         Detailed logs      Safe response
```

This is the architecture we're building.

# 4. Start with the request

Suppose the client sends:

```http
POST /api/v1/todos
```

The request enters:

```text
Request
   ↓
Request ID
```

For example:

```text
requestId = req_abc123
```

Now the request carries:

```js
req.requestId
```

throughout the rest of its lifecycle.

---

# 5. Logger sees the Request ID

Your logger can now record:

```text
requestId=req_abc123
method=POST
path=/api/v1/todos
```

So right from the beginning, we can trace the request.

---

# 6. Request reaches the controller

Your controller should remain thin.

For example:

```js
export const createTodo = asyncHandler(
    async (req, res) => {

        const todo = await todoService.createTodo(
            req.user.userId,
            req.body
        );

        res.status(201).json({
            success: true,
            data: todo
        });
    }
);
```

Notice something important:

There is **no giant try/catch**.

Why?

Because `asyncHandler` handles rejected promises.

---

# 7. `asyncHandler` catches asynchronous errors

Our utility:

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};
```

Suppose:

```js
await todoService.createTodo(...);
```

throws an error.

The flow becomes:

```text
Controller
    ↓
Promise rejected
    ↓
asyncHandler
    ↓
next(error)
```

Now Express can send the error to the global error middleware.

---

# 8. Why `next(error)` is so important

Normal middleware:

```js
next();
```

means:

> Continue normally.

Error middleware:

```js
next(error);
```

means:

> Something went wrong. Send this error through the error-handling pipeline.

So:

```text
next()
   ↓
next middleware

next(error)
   ↓
error middleware
```

This distinction is fundamental to Express error architecture.

---

# 9. `AppError` represents expected errors

Suppose a user requests a Todo that doesn't exist.

The service can say:

```js
throw new AppError(
    "Todo not found",
    404
);
```

Now we have:

```text
AppError
message = Todo not found
statusCode = 404
isOperational = true
```

This is an **operational error**.

---

# 10. Why `AppError` is useful

Instead of doing this everywhere:

```js
res.status(404).json({
    success: false,
    message: "Todo not found"
});
```

you simply:

```js
throw new AppError(
    "Todo not found",
    404
);
```

The global error handler decides how to create the response.

That's a major architectural improvement.

---

# 11. Our `AppError`

A simple implementation:

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(
            this,
            this.constructor
        );
    }
}

export default AppError;
```

Now:

```js
throw new AppError(
    "User not found",
    404
);
```

contains:

```text
name
message
stack
statusCode
isOperational
```

---

# 12. Unexpected errors are different

Suppose you accidentally write:

```js
const user = null;

console.log(user.name);
```

JavaScript throws:

```text
TypeError
```

You didn't intentionally create that error.

It's unexpected.

So:

```text
AppError
   ↓
expected/operational

Error / TypeError / unknown
   ↓
unexpected
```

This distinction is extremely important.

---

# 13. The global error handler

Now everything eventually reaches:

```js
errorMiddleware
```

Its job is to:

1. identify the error
    
2. normalize it if necessary
    
3. log it
    
4. determine status code
    
5. determine safe message
    
6. include Request ID
    
7. send consistent response
    

Think of it as the **traffic controller for errors**.

# 15. Error normalization

Remember Lesson 8.15.

Different libraries produce different error shapes.

For example:

```text
Joi
MongoDB
Mongoose
JWT
JavaScript
```

might all produce completely different objects.

We don't want our controllers to understand every library's error format.

Instead:

```text
Library Error
     ↓
Normalize
     ↓
Our Application Error
     ↓
Global Error Handler
```

# 26. `requestId.middleware.js`

```js
import crypto from "crypto";

const requestIdMiddleware = (req, res, next) => {
    const requestId = crypto.randomUUID();

    req.requestId = requestId;

    res.setHeader(
        "X-Request-ID",
        requestId
    );

    next();
};

export default requestIdMiddleware;
```

Its only responsibility:

> Give every request a unique ID.

# 27. `notFound.middleware.js`

If no route matches:

```js
import AppError from "../utils/AppError.js";

const notFoundMiddleware = (req, res, next) => {
    next(
        new AppError(
            `Route not found: ${req.method} ${req.originalUrl}`,
            404
        )
    );
};

export default notFoundMiddleware;
```

Now 404 errors enter the same error pipeline.

This is important.

We don't want a separate error system for 404.

# 31. Global error middleware

A learning version:

```js
import normalizeError
    from "../utils/errorNormalizer.js";

const errorMiddleware = (
    err,
    req,
    res,
    next
) => {

    const error = normalizeError(err);

    const statusCode =
        error.statusCode || 500;

    const isProduction =
        process.env.NODE_ENV === "production";

    console.error({
        requestId: req.requestId,
        name: error.name,
        message: error.message,
        stack: error.stack
    });

    if (
        isProduction &&
        !error.isOperational
    ) {
        return res.status(500).json({
            success: false,
            message: "Internal server error",
            requestId: req.requestId
        });
    }

    const response = {
        success: false,
        message: error.message,
        requestId: req.requestId
    };

    if (!isProduction) {
        response.stack = error.stack;
    }

    return res
        .status(statusCode)
        .json(response);
};

export default errorMiddleware;
```

This is a **learning implementation**. Later, your logger and error normalization will become more sophisticated.

# 32. Why log before responding?

We want:

```text
Error
 ↓
Log
 ↓
Response
```

not:

```text
Error
 ↓
Response
 ↓
Maybe log
```

Because logging is part of your observability system.

If you return the response and then something fails while logging, your debugging pipeline could become unreliable.

In production architecture, the exact behavior depends on the logger, but conceptually:

> **Record the error internally before finishing the request.**

# 33. `app.js`

Now your application can look like:

```js
import express from "express";
import requestIdMiddleware
    from "./middlewares/requestId.middleware.js";

import notFoundMiddleware
    from "./middlewares/notFound.middleware.js";

import errorMiddleware
    from "./middlewares/error.middleware.js";

const app = express();

app.use(express.json());

app.use(requestIdMiddleware);

// Routes
app.use("/api/v1/todos", todoRoutes);
app.use("/api/v1/users", userRoutes);
app.use("/api/v1/auth", authRoutes);

// 404
app.use(notFoundMiddleware);

// Error handler
app.use(errorMiddleware);

export default app;
```

The important part is ordering.

# 34. Middleware ordering

Memorize:

```text
1. Request setup
2. Request ID
3. Logger
4. Security
5. Body parsing
6. Authentication/validation where needed
7. Routes
8. 404
9. Error handler
```

The exact order of some cross-cutting middleware can vary based on your application, but the major principle is:

> **Error middleware comes last.**

Your starter's build plan also places the 404 handler before the error handler.

The biggest change from the beginning of Phase 8 is this:

```text
BEFORE

Controller
  ├── try
  ├── catch
  ├── status
  ├── response
  └── error logic
```

becomes:

```text
AFTER

Controller
      │
      ▼
   Service
      │
      ▼
throw error
      │
      ▼
asyncHandler
      │
      ▼
Global Error Handler
      │
      ├── normalize
      ├── log
      ├── request ID
      ├── status
      └── safe response
```

**That is the real purpose of Phase 8:** you're no longer just learning how to `catch` errors. You're learning how a production backend **designs, classifies, transports, logs, and exposes errors consistently**.

And this foundation will make the much harder topics coming after Phase 8—**authentication/authorization, repositories, services, security, testing, and production architecture**—far easier to understand because you now know where failures belong and how they move through the application.
