# Lesson 8.3 — Synchronous vs Asynchronous Errors

In **8.2**, we learned:

```text
throw
  ↓
error
  ↓
catch
```

Now we need to understand one of the most important backend concepts:

> **Not all errors happen at the same time.**

Some errors happen **synchronously**.

Others happen **asynchronously**.

This difference is the reason your backend eventually needs:

```text
asyncHandler
```

Let's build the idea from zero.

---

# 1. What does "synchronous" mean?

Synchronous code executes **step by step**.

For example:

```js
console.log("A");
console.log("B");
console.log("C");
```

Execution:

```text
A
 ↓
B
 ↓
C
```

JavaScript waits for each statement to finish before moving to the next one.

---

# 2. A synchronous error

Consider:

```js
console.log("Before");

throw new Error("Something went wrong");

console.log("After");
```

Output:

```text
Before
Error: Something went wrong
```

`"After"` never executes.

Why?

Because the error happened **during the current execution**.

```text
console.log("Before")
        ↓
throw
        ↓
ERROR ❌
        ↓
execution stops
```

---

# 3. Catching a synchronous error

```js
try {
    console.log("Before");

    throw new Error("Something went wrong");

    console.log("After");
} catch (error) {
    console.log("Caught:", error.message);
}
```

Output:

```text
Before
Caught: Something went wrong
```

Flow:

```text
try
 ↓
Before
 ↓
throw
 ↓
catch
 ↓
Caught
```

Very straightforward.

---

# 4. Now let's introduce asynchronous code

Backend applications constantly perform operations that don't finish immediately.

For example:

```text
MongoDB query
API request
File operation
Email
Password hashing
Timer
Redis
External service
```

Consider:

```js
setTimeout(() => {
    console.log("Finished");
}, 1000);

console.log("Next");
```

Output:

```text
Next
Finished
```

Why?

Because JavaScript doesn't stop and wait for the timer.

Conceptually:

```text
Start
 │
 ├── schedule timer
 │
 └── continue
       ↓
     Next
       ↓
   timer finishes
       ↓
    Finished
```

This is asynchronous execution.

---

# 5. The important problem

Look at this:

```js
try {
    setTimeout(() => {
        throw new Error("Something went wrong");
    }, 1000);
} catch (error) {
    console.log("Caught:", error.message);
}
```

You might expect:

```text
Caught: Something went wrong
```

But that's **not what happens**.

The outer `try/catch` doesn't catch the error thrown inside the later timer callback.

Why?

Because the callback executes later.

---

# 6. Understand the timeline

Your code:

```js
try {
    setTimeout(() => {
        throw new Error("Something went wrong");
    }, 1000);
} catch (error) {
    console.log("Caught");
}
```

What actually happens:

### Step 1

JavaScript enters:

```js
try
```

### Step 2

It schedules:

```js
setTimeout(...)
```

### Step 3

`try` finishes.

There was no error **yet**.

### Step 4

One second later:

```js
() => {
    throw new Error(...);
}
```

runs.

But the original `try/catch` has already finished.

So:

```text
try/catch
    │
    │ finishes
    ▼
time passes
    │
    ▼
callback executes
    │
    ▼
ERROR ❌
```

That's the core idea.

---

# 7. This is why asynchronous errors are different

Compare:

### Synchronous

```text
try
 ↓
operation
 ↓
error
 ↓
catch
```

### Asynchronous

```text
try
 ↓
schedule operation
 ↓
try finishes
 ↓
later...
 ↓
async operation
 ↓
error
```

The original `try/catch` isn't around the asynchronous operation anymore.

---

# 8. But what about Promises?

This is where backend development gets interesting.

Consider:

```js
const promise = Promise.reject(
    new Error("Something failed")
);
```

A rejected Promise represents an asynchronous failure.

We can handle it using:

```js
promise.catch(error => {
    console.log(error.message);
});
```

Or with `async/await`.

---

# 9. `async/await` makes asynchronous code look synchronous

Consider:

```js
async function getUser() {
    const user = await User.findById("123");

    return user;
}
```

This looks like synchronous code:

```text
find user
 ↓
wait
 ↓
return user
```

But internally, `await` is dealing with a Promise.

That's extremely important.

```js
const user = await User.findById("123");
```

is waiting for an asynchronous operation.

---

# 10. `try/catch` DOES work with `await`

This is one of the most important things to understand.

```js
async function getUser() {
    try {
        const user = await User.findById("123");

        return user;
    } catch (error) {
        console.log("Caught:", error.message);
    }
}
```

If the Promise returned by:

```js
User.findById()
```

rejects, the `await` expression throws inside the async function.

So the `catch` can handle it.

Conceptually:

```text
async function
     ↓
try
     ↓
await Promise
     ↓
Promise rejects ❌
     ↓
await throws
     ↓
catch
```

This is different from our `setTimeout` example.

---

# 11. A simple Promise example

Let's avoid MongoDB for now.

```js
function getData() {
    return Promise.reject(
        new Error("Database failed")
    );
}
```

Now:

```js
async function main() {
    try {
        const data = await getData();

        console.log(data);
    } catch (error) {
        console.log("Caught:", error.message);
    }
}

main();
```

Output:

```text
Caught: Database failed
```

Why?

Because:

```text
Promise.reject()
      ↓
await
      ↓
throws inside async function
      ↓
catch
```

---

# 12. What happens without `await`?

Consider:

```js
async function main() {
    try {
        const promise = getData();

        console.log(promise);
    } catch (error) {
        console.log("Caught");
    }
}
```

The error won't be caught by that `catch`.

Why?

Because you didn't wait for the Promise.

You only received the Promise object.

```text
getData()
   ↓
Promise
   ↓
try finishes
   ↓
Promise rejects later
```

So:

```js
await
```

is important here.

---

# 13. The relationship between `async` and `await`

When you write:

```js
async function test() {
    const result = await something();
}
```

think:

```text
something()
     ↓
Promise
     ↓
await
     ↓
wait for Promise
     ↓
fulfilled → result
rejected → error
```

Therefore:

```js
try {
    await something();
} catch (error) {
    // handles rejection
}
```

is a very common backend pattern.

---

# 14. Why Express creates another problem

Now imagine your Express controller:

```js
app.get("/users", async (req, res) => {
    const users = await User.find();

    res.json({
        success: true,
        data: users
    });
});
```

What if:

```js
User.find()
```

rejects?

The async function itself rejects.

Conceptually:

```text
GET /users
    ↓
async controller
    ↓
await User.find()
    ↓
Promise rejection ❌
    ↓
async function rejects
```

We now need to make sure Express receives that error correctly.

That's where our next lessons are heading.

---

# 15. The beginner solution

You could write:

```js
app.get("/users", async (req, res, next) => {
    try {
        const users = await User.find();

        res.json({
            success: true,
            data: users
        });
    } catch (error) {
        next(error);
    }
});
```

This works.

Notice:

```js
catch (error) {
    next(error);
}
```

Instead of:

```js
res.status(500).json(...)
```

we're passing the error to Express.

This is exactly the beginning of our future architecture.

---

# 16. What is `next(error)`?

You already learned in Phase 7 that:

```js
next()
```

means:

> Move to the next middleware.

But:

```js
next(error)
```

means:

> Something went wrong. Send this error through Express's error-handling pipeline.

Conceptually:

```text
Controller
    ↓
next(error)
    ↓
Express
    ↓
Error middleware
```

We'll study this deeply in **8.6**.

---

# 17. Why `asyncHandler` exists

Imagine you have 30 async controllers.

You'd repeatedly write:

```js
try {
    ...
} catch (error) {
    next(error);
}
```

For every controller.

That's repetitive.

So we can create:

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};
```

Don't worry if this looks confusing.

**Do not memorize it yet.**

We'll build it line by line in:

> **8.9 — Creating `asyncHandler`**

The idea is simply:

```text
async controller
      ↓
asyncHandler
      ↓
Promise rejection
      ↓
next(error)
```

Eventually your backend will work like this:

```text
                 HTTP REQUEST
                      │
                      ▼
                    ROUTE
                      │
                      ▼
                 MIDDLEWARE
                      │
                      ▼
                 CONTROLLER
                      │
                      ▼
                   SERVICE
                      │
                      ▼
                REPOSITORY
                      │
                      ▼
                  MongoDB
                      │
                      │
                   ERROR ❌
                      │
                      ▼
                 Promise

                      │

                      │

```

This is the architecture you're ultimately learning.

# 19. A very important distinction

Don't confuse these three things:

### `throw`

Means:

> Create/propagate an error.

```js
throw new Error("Failed");
```

### `Promise.reject()`

Means:

> Return a rejected Promise.

```js
return Promise.reject(
    new Error("Failed")
);
```

### `next(error)`

Means:

> Tell Express that an error occurred.

```js
next(error);
```

They are related, but they aren't the same thing.

# 20. Example: synchronous error

```js
function validateId(id) {
    if (!id) {
        throw new Error("ID is required");
    }

    return id;
}

try {
    validateId();
} catch (error) {
    console.log(error.message);
}
```

Flow:

```text
validateId()
    ↓
throw
    ↓
catch
```

# 21. Example: asynchronous error

```js
function getUser() {
    return Promise.reject(
        new Error("Database unavailable")
    );
}

async function main() {
    try {
        await getUser();
    } catch (error) {
        console.log(error.message);
    }
}

main();
```

Flow:

```text
getUser()
    ↓
Promise.reject()
    ↓
await
    ↓
catch
```

---

# 22. Example: Express async error

```js
app.get("/users", async (req, res, next) => {
    try {
        const users = await User.find();

        res.json(users);
    } catch (error) {
        next(error);
    }
});
```

Flow:

```text
HTTP request
     ↓
async controller
     ↓
await
     ↓
MongoDB rejection
     ↓
catch
     ↓
next(error)
     ↓
error middleware
```

This is the pattern we'll automate.

# 23. One subtle but important point

`async` functions **always return a Promise**.

For example:

```js
async function hello() {
    return "Hello";
}
```

Even though you returned a string, the actual result is a Promise:

```js
const result = hello();

console.log(result);
```

Conceptually:

```text
Promise { "Hello" }
```

Therefore:

```js
async function
```

and:

```text
Promise
```

are tightly connected.

This is why async Express controllers need special attention.

# 🧠 The Core Mental Model

This is the part I really want you to remember:

```text
SYNCHRONOUS

try
 ↓
operation
 ↓
error
 ↓
catch
```

But asynchronous:

```text
ASYNC

async function
      ↓
    await
      ↓
    Promise
      │
      ├── fulfilled → continue
      │
      └── rejected → error
                         ↓
                       catch
```

And in Express:

```text
Promise rejection
       ↓
asyncHandler
       ↓
next(error)
       ↓
error middleware
       ↓
HTTP response
```

### One sentence to remember

> **`try/catch` can handle rejected Promises when you `await` them, but asynchronous work that happens outside the current execution stack needs a different error path.**
