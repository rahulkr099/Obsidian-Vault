# Lesson 8.4 — Express Error Handling

In **8.3**, we learned the difference between synchronous and asynchronous errors.

Now we move into **Express**.

The main question is:

> **When an error happens inside an Express request, how does Express know where to send that error?**

This is the foundation for the `error.middleware.js` in your backend starter.

---

# 1. Normal Express middleware

You already learned that middleware generally looks like this:

```js
const logger = (req, res, next) => {
    console.log(req.method, req.url);

    next();
};
```

It has three arguments:

```text
req
res
next
```

Flow:

```text
Request
   ↓
Middleware
   ↓
next()
   ↓
Next middleware
```

For example:

```js
app.use(logger);
```

---

# 2. Express has a special error middleware

Error-handling middleware looks different.

It has **four parameters**:

```js
const errorHandler = (err, req, res, next) => {
    // handle error
};
```

Notice:

```text
err
req
res
next
```

The first parameter is the error.

This is how Express recognizes:

> "This middleware is intended to handle errors."

So:

```js
(err, req, res, next)
```

is extremely important.

---

# 3. Compare normal middleware and error middleware

### Normal middleware

```js
const middleware = (req, res, next) => {
    next();
};
```

Three parameters:

```text
req
res
next
```

### Error middleware

```js
const errorMiddleware = (err, req, res, next) => {
    next();
};
```

Four parameters:

```text
err
req
res
next
```

The difference is:

```text
Normal:
(req, res, next)

Error:
(err, req, res, next)
```

---

# 4. A simple Express example

Let's create a tiny application:

```js
import express from "express";

const app = express();

app.get("/test", (req, res) => {
    throw new Error("Something went wrong");
});

app.use((err, req, res, next) => {
    console.log("Error middleware reached");

    res.status(500).json({
        success: false,
        message: err.message
    });
});

app.listen(5000);
```

Now request:

```text
GET /test
```

The controller does:

```js
throw new Error("Something went wrong");
```

Express detects the error and moves into the error-handling middleware.

Flow:

```text
GET /test
    ↓
Route
    ↓
throw Error
    ↓
Express Error Pipeline
    ↓
error middleware
    ↓
500 response
```

Response:

```json
{
  "success": false,
  "message": "Something went wrong"
}
```

---

# 5. Why does Express know it's an error?

Because you used:

```js
throw new Error(...)
```

or:

```js
next(error)
```

The second one is especially important.

Consider:

```js
app.get("/test", (req, res, next) => {
    const error = new Error("Something failed");

    next(error);
});
```

This tells Express:

> "There is an error. Start the error-handling process."

Flow:

```text
Route
  ↓
next(error)
  ↓
Express
  ↓
Error middleware
```

---

# 6. `next()` vs `next(error)`

This distinction is extremely important.

### `next()`

Means:

> Everything is okay. Continue.

```js
next();
```

Flow:

```text
Middleware
   ↓
next()
   ↓
Next middleware
```

---

### `next(error)`

Means:

> Something went wrong. Switch to error handling.

```js
next(error);
```

Flow:

```text
Middleware
   ↓
next(error)
   ↓
Error middleware
```

So:

```text
next()
    =
continue normally

next(error)
    =
enter error handling
```

---

# 7. Example with both

```js
app.get("/users", (req, res, next) => {

    const somethingWentWrong = true;

    if (somethingWentWrong) {
        return next(new Error("Unable to fetch users"));
    }

    res.json({
        success: true
    });
});
```

Then:

```js
app.use((err, req, res, next) => {
    res.status(500).json({
        success: false,
        message: err.message
    });
});
```

Flow:

```text
GET /users
     ↓
Route
     ↓
somethingWentWrong?
     ↓
   YES
     ↓
next(error)
     ↓
Error middleware
     ↓
500
```

---

# 8. Why `return next(error)`?

You will often see:

```js
return next(error);
```

instead of:

```js
next(error);
```

The `return` prevents the function from continuing.

For example:

```js
app.get("/users", (req, res, next) => {

    if (!user) {
        return next(new Error("User not found"));
    }

    res.json(user);
});
```

Without `return`:

```js
app.get("/users", (req, res, next) => {

    if (!user) {
        next(new Error("User not found"));
    }

    res.json(user);
});
```

The code may continue and try to send a response after passing the error onward.

That can create problems such as:

```text
Error: Cannot set headers after they are sent
```

So a useful pattern is:

```js
return next(error);
```

---

# 9. Error middleware should come after routes

This is extremely important.

Correct:

```js
app.use("/api/users", userRoutes);

app.use(errorMiddleware);
```

Think:

```text
Routes
   ↓
Possible error
   ↓
Error middleware
```

Usually your global error handler should be registered **after your routes and other middleware that may generate errors**.

---

# 10. Wrong ordering

Avoid putting the error middleware at the beginning:

```js
app.use(errorMiddleware);

app.use("/api/users", userRoutes);
```

Why?

Because your error handler is being registered before the routes that might pass errors to it.

The general structure should be:

```text
Request middleware
      ↓
Routes
      ↓
404 handling
      ↓
Error handling
```

We'll later discuss the exact ordering of your complete starter architecture.

---

# 11. Express error middleware can inspect the request

Because it receives:

```js
(err, req, res, next)
```

it has access to:

### Error

```js
err.message
err.stack
```

### Request

```js
req.method
req.originalUrl
req.user
req.requestId
```

### Response

```js
res.status(...)
res.json(...)
```

### Next

```js
next(...)
```

This is why error middleware is a powerful central location.

---

# 12. Example: logging errors

You could temporarily do:

```js
app.use((err, req, res, next) => {
    console.error(err);

    res.status(500).json({
        success: false,
        message: "Internal server error"
    });
});
```

Now:

```text
Client
   ↓
Request
   ↓
Error
   ↓
Error middleware
   ├── log error internally
   └── safe response to client
```

This separation is important.

---

# 13. Don't expose everything

Suppose your application throws:

```js
throw new Error(
    "MongoServerError: E11000 duplicate key collection users..."
);
```

You don't necessarily want the client to see all of that.

Instead:

```js
res.status(500).json({
    success: false,
    message: "Internal server error"
});
```

While your server logs:

```text
MongoServerError...
stack trace...
request ID...
endpoint...
```

So:

```text
Developer
   ↓
Detailed information

Client
   ↓
Safe information
```

This becomes especially important in production.

---

# 14. `next(error)` skips normal middleware

Consider:

```js
app.use((req, res, next) => {
    console.log("Middleware A");
    next();
});

app.use((err, req, res, next) => {
    console.log("Error handler");
    res.status(500).json({
        message: err.message
    });
});

app.use((req, res, next) => {
    console.log("Middleware B");
    next();
});
```

Now imagine:

```js
app.get("/test", (req, res, next) => {
    next(new Error("Failed"));
});
```

Once the error occurs, Express moves toward error handlers rather than continuing through normal middleware.

Conceptually:

```text
Route
  ↓
next(error)
  ↓
Error pipeline
  ↓
Error middleware
```

It doesn't simply behave like:

```text
next()
 ↓
next middleware
```

---

# 15. Important Express rule

When you call:

```js
next(error);
```

Express looks for error-handling middleware:

```js
(err, req, res, next)
```

This is one of the most important Express rules to remember.

---

# 16. What if there are multiple error handlers?

You can have more than one.

For example:

```js
app.use((err, req, res, next) => {
    console.log("First error handler");

    next(err);
});

app.use((err, req, res, next) => {
    console.log("Second error handler");

    res.status(500).json({
        success: false
    });
});
```

Flow:

```text
Error
  ↓
Error handler 1
  ↓
next(err)
  ↓
Error handler 2
  ↓
Response
```

This is useful when you want different error-processing layers.

---

# 17. Why would we have multiple error handlers?

In a large backend, you might eventually want:

```text
Error occurs
    ↓
Logging
    ↓
Error classification
    ↓
Response formatting
    ↓
HTTP response
```

For your starter, we'll eventually keep this cleaner and use one main global error middleware, with utilities and helpers around it.

---

# 18. Express's default error handler

Express also has its own default error handler.

If you don't create your own error middleware, Express can provide a default response.

But you shouldn't depend on that for a production API.

Why?

Because you want control over:

```text
status code
response format
logging
security
stack trace visibility
request ID
environment
```

That's why your starter has its own:

```text
middlewares/error.middleware.js
```

instead of relying on Express's default behavior.

# 20. A realistic example

Suppose:

```text
GET /api/v1/users/123
```

Your controller:

```js
const getUser = async (req, res, next) => {
    try {
        const user = await userService.getUser(req.params.id);

        if (!user) {
            return next(new Error("User not found"));
        }

        res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

Then global handler:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    res.status(500).json({
        success: false,
        message: err.message
    });
};
```

The flow is:

```text
GET /users/123
       ↓
Controller
       ↓
Service
       ↓
User not found
       ↓
next(error)
       ↓
Global error middleware
       ↓
HTTP 500
```

Later we'll improve this because `"User not found"` should generally become a **404**, not a 500.

That's exactly why we're going step by step.

# 21. A very important concept: error status

Right now we have:

```js
res.status(500)
```

But backend errors can have different HTTP statuses:

```text
400 → Bad Request
401 → Unauthorized
403 → Forbidden
404 → Not Found
409 → Conflict
422 → Unprocessable Entity
429 → Too Many Requests
500 → Internal Server Error
503 → Service Unavailable
```

For example:

```text
User doesn't exist
        ↓
404
```

Whereas:

```text
Database crashed
        ↓
500
```

And:

```text
Too many login attempts
        ↓
429
```

Our current normal `Error` object doesn't know the HTTP status.

That's one reason we'll eventually create:

```js
AppError
```

in **8.11**.

---

# 22. Why `AppError` will be useful

Instead of:

```js
throw new Error("User not found");
```

we'll eventually be able to do something conceptually like:

```js
throw new AppError(
    "User not found",
    404
);
```

Now the error itself knows:

```text
message
statusCode
```

Then:

```text
AppError
   ↓
Global Error Middleware
   ↓
404 response
```

That's much cleaner.

---

# 23. Another important distinction

Don't make your service do this:

```js
res.status(404).json({
    success: false,
    message: "User not found"
});
```

Why?

Because a service should not need to know about:

```text
Express
req
res
HTTP status
```

Instead:

```text
Service
   ↓
throw AppError("User not found", 404)
   ↓
Error middleware
   ↓
HTTP 404
```

This is one of the reasons the **service layer** and **error layer** work nicely together.
