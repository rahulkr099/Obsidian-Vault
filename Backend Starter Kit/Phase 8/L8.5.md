# Lesson 8.5 — The Error Middleware

In **8.4**, we learned that Express has a special kind of middleware for errors:

```js
(err, req, res, next)
```

Today we're going to understand this function **properly** and build our first reusable `error.middleware.js`.

This directly prepares you for the starter architecture, which uses:

```text
utils/
├── AppError.js
└── asyncHandler.js

middlewares/
└── error.middleware.js
```

Your uploaded roadmap specifically says Phase 8 should eventually produce the flow:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
      ↓
JSON response
```

---

# 1. What is error middleware?

Normal middleware:

```js
const middleware = (req, res, next) => {
    // ...
};
```

Error middleware:

```js
const errorMiddleware = (err, req, res, next) => {
    // ...
};
```

The biggest difference is:

```text
Normal middleware
(req, res, next)

Error middleware
(err, req, res, next)
```

The first parameter tells Express:

> "This function is an error handler."

---

# 2. Think of it as a central error desk

Imagine your backend is a company.

Different departments can encounter problems:

```text
Controller
Service
Repository
Database
Authentication
Validation
```

Instead of each one creating its own response:

```text
Controller → response
Service → response
Repository → response
```

we want:

```text
                 ERROR
                   │
       ┌───────────┼───────────┐
       │           │           │
 Controller     Service    Repository
       │           │           │
       └───────────┼───────────┘
                   ↓
            Global Error Handler
                   ↓
              HTTP Response
```

That's the main purpose of `error.middleware.js`.

---

# 3. Create a simple error middleware

Create:

```text
middlewares/
└── error.middleware.js
```

Start with:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    res.status(500).json({
        success: false,
        message: err.message
    });
};

export default errorMiddleware;
```

Don't worry about making this production-ready yet.

We're learning the pieces first.

---

# 4. Let's understand every parameter

Our function:

```js
const errorMiddleware = (err, req, res, next) => {
```

has four parameters.

---

## `err`

The actual error.

For example:

```js
const error = new Error("User not found");

next(error);
```

Then inside the error middleware:

```js
err.message
```

will be:

```text
User not found
```

You can also access:

```js
err.name
err.stack
```

---

# 5. `req`

This is the normal Express request object.

So you can access:

```js
req.method
req.originalUrl
req.params
req.query
req.body
```

For example:

```js
console.log(req.method);
console.log(req.originalUrl);
```

If the request was:

```text
GET /api/v1/users/123
```

you could get:

```text
GET
/api/v1/users/123
```

This is useful for logging.

---

# 6. `res`

This is the normal Express response object.

You can use:

```js
res.status(...)
res.json(...)
res.send(...)
```

For example:

```js
res.status(500).json({
    success: false,
    message: "Internal server error"
});
```

This is ultimately how the client receives the error.

---

# 7. `next`

`next` allows you to pass control to another middleware.

For example:

```js
next();
```

means:

> Continue normally.

And:

```js
next(err);
```

means:

> Pass this error to another error handler.

We won't need `next` much in our first version.

But it becomes useful when you have multiple error-handling layers.

---

# 8. Build a complete tiny example

Let's create:

```text
lesson-8.5.js
```

Code:

```js
import express from "express";

const app = express();

app.get("/error", (req, res, next) => {
    const error = new Error("Something went wrong");

    next(error);
});

const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    res.status(500).json({
        success: false,
        message: err.message
    });
};

app.use(errorMiddleware);

app.listen(5000, () => {
    console.log("Server running on port 5000");
});
```

Now request:

```text
GET http://localhost:5000/error
```

You'll receive:

```json
{
    "success": false,
    "message": "Something went wrong"
}
```

---

# 9. Understand the entire flow

This is the important part.

Request:

```text
GET /error
```

↓

Route:

```js
app.get("/error", ...)
```

↓

Create error:

```js
const error = new Error("Something went wrong");
```

↓

Pass error:

```js
next(error);
```

↓

Express enters error-handling flow.

↓

Express finds:

```js
(err, req, res, next)
```

↓

Error middleware:

```js
res.status(500).json(...)
```

↓

Client receives JSON.

So:

```text
GET /error
    ↓
Route
    ↓
next(error)
    ↓
Express
    ↓
errorMiddleware
    ↓
res.status(500)
    ↓
JSON
```

---

# 10. Why is the error middleware at the bottom?

Notice this:

```js
app.get("/error", ...);

app.use(errorMiddleware);
```

The error middleware comes **after** the routes.

Think of the application as a pipeline:

```text
Request
  ↓
Middleware
  ↓
Routes
  ↓
Error?
  ↓
Error middleware
```

If you register the error handler too early, you can break this flow.

Your starter architecture also treats error handling as a later layer in the application assembly.

---

# 11. Error middleware is not a 404 middleware

This distinction is very important.

A **404** means:

> No matching route was found.

An **error middleware** means:

> Something went wrong while processing the request.

For example:

```text
GET /api/users
```

doesn't exist:

```text
404
```

But:

```text
GET /api/users
      ↓
route exists
      ↓
database crashes
      ↓
500
```

That's an error.

So don't confuse:

```text
404 handler
```

with:

```text
error handler
```

We'll build 404 handling separately.

---

# 12. A 404 handler

A simple 404 handler might look like:

```js
app.use((req, res) => {
    res.status(404).json({
        success: false,
        message: "Route not found"
    });
});
```

Then the structure becomes:

```text
Routes
   ↓
No route matched?
   ↓
404 handler
   ↓
Error occurred?
   ↓
Error handler
```

So eventually:

```text
Request
   ↓
Middleware
   ↓
Routes
   ↓
404 handler
   ↓
Global error handler
```

This ordering will become important when you build your real `app.js`.

---

# 13. Don't send `err.stack` to the client

You might be tempted to do:

```js
res.status(500).json({
    success: false,
    message: err.message,
    stack: err.stack
});
```

Don't make this your production behavior.

The stack contains internal information such as:

```text
file paths
function names
internal code structure
dependencies
```

A client doesn't need that.

Instead:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

And log the detailed error on the server.

---

# 14. Development vs production

This is a very important concept.

During development, you might want:

```js
console.error(err.stack);
```

because you're debugging.

In production, the client should usually receive something safer:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

Conceptually:

```text
                 ERROR
                   │
          ┌────────┴────────┐
          │                 │
     Server logs        API response
          │                 │
          ▼                 ▼
     Detailed error     Safe message
     stack trace
```

Later, in **8.18**, we'll specifically learn how to hide sensitive errors in production.

---

# 15. Don't hard-code every error as 500 forever

Our current implementation:

```js
res.status(500).json(...)
```

is deliberately simple.

But imagine:

```text
User not found
```

That should normally be:

```text
404
```

And:

```text
Invalid credentials
```

might be:

```text
401
```

And:

```text
Too many requests
```

could be:

```text
429
```

So eventually our error object needs to carry information such as:

```text
message
statusCode
```

That's why we'll create:

```text
AppError
```

later.

The source roadmap explicitly places `AppError` and `asyncHandler` at the center of this phase.

---

# 16. Introducing the idea of `statusCode`

For now, imagine an error like:

```js
const error = new Error("User not found");

error.statusCode = 404;
```

Now:

```js
console.log(error.statusCode);
```

gives:

```text
404
```

Then our error middleware could eventually do:

```js
const statusCode = err.statusCode || 500;
```

Meaning:

```text
If error has a status → use it
Otherwise → 500
```

This is the beginning of our future `AppError`.

---

# 17. A slightly better error middleware

We could write:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message: err.message || "Internal server error"
    });
};
```

Now:

```js
const error = new Error("User not found");

error.statusCode = 404;

next(error);
```

would produce:

```json
{
    "success": false,
    "message": "User not found"
}
```

with:

```text
404
```

This is much closer to what we'll eventually build.

---

# 18. Why `|| 500`?

This:

```js
const statusCode = err.statusCode || 500;
```

means:

```text
err.statusCode exists?
       │
   ┌───┴───┐
  YES      NO
   │        │
   ▼        ▼
 status    500
```

For example:

```js
err.statusCode = 404;
```

→ use `404`.

But if:

```js
err.statusCode
```

doesn't exist:

→ use `500`.

Later you may see:

```js
const statusCode = err.statusCode ?? 500;
```

We'll discuss `||` vs `??` when we build the production version.

Imagine five applications:


# 20. The connection with `AppError`

Eventually we'll write something like:

```js
throw new AppError("User not found", 404);
```

Then:

```text
AppError
   │
   ├── message = "User not found"
   └── statusCode = 404
           │
           ▼
   errorMiddleware
           │
           ▼
       HTTP 404
```

So:

### `AppError`

describes:

> **What went wrong?**

### `errorMiddleware`

decides:

> **How should the client receive it?**

That's an important separation.

---

# 21. The connection with `asyncHandler`

Eventually you'll write:

```js
export const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    res.json({
        success: true,
        data: user
    });
});
```

If the service throws:

```js
throw new AppError("User not found", 404);
```

the flow becomes:

```text
Controller
    ↓
throws AppError
    ↓
asyncHandler
    ↓
next(error)
    ↓
errorMiddleware
    ↓
404 JSON response
```

This exact flow is part of the intended architecture in your uploaded starter roadmap.

# 22. The three components you must understand

Don't think of these as random files:

```text
AppError.js
asyncHandler.js
error.middleware.js
```

They solve **three different problems**.

### `AppError`

```text
Creates meaningful application errors.
```

### `asyncHandler`

```text
Catches async controller failures.
```

### `error.middleware`

```text
Converts errors into HTTP responses.
```

Think:

```text
       ERROR SYSTEM

       AppError
          ↓
   What went wrong?
          ↓
    asyncHandler
          ↓
  How does error travel?
          ↓
 error.middleware
          ↓
 How does client receive it?
```
