# Lesson 8.6 — The Four Arguments of Error Middleware

Today we'll slow down and understand this function completely:

```js
const errorMiddleware = (err, req, res, next) => {
    // ...
};
```

You should **not memorize this as boilerplate**.

You should understand why each argument exists and what happens when you use it.

This matters because your starter architecture eventually depends on this middleware to convert errors into consistent API responses.

---

# 1. The four arguments

Error middleware receives:

```js
(err, req, res, next)
```

Think of them as four pieces of information:

```text
err   → What went wrong?
req   → What request caused it?
res   → What should we send back?
next  → Where should the error go next?
```

So:

```text
              ERROR MIDDLEWARE

      ┌────────┬────────┬────────┬────────┐
      │        │        │        │
     err      req      res      next
      │        │        │        │
   error    request  response   continue
```

Let's understand each one.

---

# 2. `err` — the error

The first argument:

```js
err
```

contains the error that was passed into Express.

For example:

```js
app.get("/users", (req, res, next) => {
    const error = new Error("User not found");

    next(error);
});
```

Then:

```js
app.use((err, req, res, next) => {
    console.log(err);
});
```

The `err` is:

```js
Error: User not found
```

---

# 3. Reading `err.message`

The most commonly used property is:

```js
err.message
```

Example:

```js
app.use((err, req, res, next) => {
    console.log(err.message);

    res.status(500).json({
        success: false,
        message: err.message
    });
});
```

If the error was:

```js
new Error("User not found")
```

then:

```text
err.message
```

is:

```text
User not found
```

---

# 4. Reading `err.stack`

You can also inspect:

```js
err.stack
```

For example:

```js
console.error(err.stack);
```

This gives you information about where the error originated.

Conceptually:

```text
Error: User not found
    at getUser (...)
    at userService (...)
    at userController (...)
```

This is useful for **developers and logging**.

But don't normally send it to the client in production.

---

# 5. `req` — the request

The second argument:

```js
req
```

is the same Express request object you've already been using.

For example:

```js
req.method
req.originalUrl
req.params
req.query
req.body
```

Suppose the client sends:

```text
GET /api/v1/users/123
```

You can access:

```js
req.method
```

→

```text
GET
```

and:

```js
req.originalUrl
```

→

```text
/api/v1/users/123
```

---

# 6. Why does the error middleware need `req`?

At first you might think:

> "I'm handling an error. Why do I need the request?"

Because the request gives important context.

For example, you may want to log:

```js
console.error({
    method: req.method,
    url: req.originalUrl,
});
```

If an error occurs, your server log can tell you:

```text
GET /api/v1/users/123
Error: User not found
```

That's much more useful than:

```text
Error: User not found
```

---

# 7. `req` can contain authenticated user information

Later, authentication middleware may add:

```js
req.user
```

For example:

```js
req.user = {
    userId: "123",
    role: "user"
};
```

Then the error middleware could use that information for logging.

Conceptually:

```text
Request
 ├── method
 ├── URL
 ├── body
 └── user
       ↓
Error occurs
       ↓
Error middleware
       ↓
Log useful context
```

Be careful, though: **don't blindly log sensitive information**.

---

# 8. `res` — the response

The third argument:

```js
res
```

is the response object.

This is how the error middleware communicates with the client.

For example:

```js
res.status(404).json({
    success: false,
    message: "User not found"
});
```

The client receives:

```json
{
  "success": false,
  "message": "User not found"
}
```

---

# 9. `res.status()`

You can choose the HTTP status:

```js
res.status(404);
```

or:

```js
res.status(500);
```

Then send the response:

```js
res.status(500).json({
    success: false,
    message: "Internal server error"
});
```

Remember:

```text
404 → Resource/route not found
500 → Unexpected server-side failure
```

We'll build a proper status-code strategy later.

---

# 10. `res.json()`

The most common response format for your REST API will be:

```js
res.json({
    success: false,
    message: "Something went wrong"
});
```

This sends JSON to the client.

Your frontend can then consistently inspect:

```js
response.data.success
response.data.message
```

This is one reason centralized error handling is useful.

---

# 11. `next` — the interesting one

The fourth argument:

```js
next
```

is where things become more interesting.

You already know:

```js
next();
```

means:

> Continue to the next middleware.

But inside an error middleware, you can also do:

```js
next(err);
```

which means:

> Pass this error to another error handler.

---

# 12. `next()` inside error middleware

Suppose:

```js
app.use((err, req, res, next) => {
    console.log("First error handler");

    next();
});
```

Calling:

```js
next();
```

essentially says:

> "I'm done with this middleware. Continue normally."

However, **be careful** with this in an error handler.

If you haven't actually handled the error, simply doing:

```js
next();
```

can cause you to leave the error-handling flow.

Usually, if you're intentionally passing the error onward, use:

```js
next(err);
```

---

# 13. `next(err)` inside error middleware

Suppose we have two error handlers:

```js
app.use((err, req, res, next) => {
    console.log("Error handler 1");

    next(err);
});

app.use((err, req, res, next) => {
    console.log("Error handler 2");

    res.status(500).json({
        success: false,
        message: err.message
    });
});
```

Flow:

```text
Error
  ↓
Error handler 1
  ↓
next(err)
  ↓
Error handler 2
  ↓
Response
```

This is useful when one error middleware performs one responsibility and another performs another.

---

# 14. Why would we have multiple error handlers?

Imagine a bigger application:

```text
Error
  ↓
Logging middleware
  ↓
Error classification
  ↓
Response formatting
  ↓
Client
```

For example:

### Handler 1

Logs the error:

```js
console.error(err);
```

### Handler 2

Classifies it:

```text
ValidationError
MongoError
JWTError
AppError
UnknownError
```

### Handler 3

Creates the final response.

This is possible because:

```js
next(err);
```

passes the error forward.

For your starter, we will keep the architecture simpler rather than creating unnecessary middleware layers.

---

# 15. How Express chooses the next error handler

This is an important mental model.

Suppose:

```js
app.use((err, req, res, next) => {
    console.log("Handler A");
    next(err);
});

app.use((err, req, res, next) => {
    console.log("Handler B");
    next(err);
});

app.use((err, req, res, next) => {
    console.log("Handler C");

    res.status(500).json({
        success: false
    });
});
```

The flow is:

```text
                    ERROR
                      │
                      ▼
                  Handler A
                      │
                   next(err)
                      │
                      ▼
                  Handler B
                      │
                   next(err)
                      │
                      ▼
                  Handler C
                      │
                      ▼
                   Response
```

Each handler can either:

```text
handle the error
```

or:

```text
pass the error onward
```

---

# 16. What if a handler sends the response?

Suppose:

```js
app.use((err, req, res, next) => {
    res.status(500).json({
        success: false,
        message: "Something failed"
    });
});
```

The response has now been sent.

There is normally no reason to call:

```js
next(err);
```

after that.

You should generally choose one:

```text
Handle error
    ↓
send response
```

or:

```text
Don't handle it
    ↓
next(err)
```

---

# 17. Don't send two responses

This is a very common Express mistake.

Bad:

```js
app.use((err, req, res, next) => {
    res.status(500).json({
        success: false
    });

    next(err);
});
```

You already sent a response, then you're telling Express:

> "Please continue handling this error."

That can lead to response/header problems.

Think:

```text
res.json()
   ↓
Response sent
   ↓
Don't send another response
```

---

# 18. A safer pattern

You can check:

```js
if (res.headersSent) {
    return next(err);
}
```

For example:

```js
const errorMiddleware = (err, req, res, next) => {
    if (res.headersSent) {
        return next(err);
    }

    res.status(500).json({
        success: false,
        message: err.message
    });
};
```

You don't necessarily need this complexity in your first version, but you should understand why it exists.

---

# 19. What are "headers"?

When Express sends an HTTP response, headers are sent before the body.

For example:

```text
HTTP/1.1 500 Internal Server Error
Content-Type: application/json
```

Then:

```json
{
    "success": false
}
```

Once headers have already been sent, you can't safely change the status to something else.

That's why this error can happen:

```text
Cannot set headers after they are sent
```

---

# 20. A practical error middleware

Let's build a slightly better version:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    if (res.headersSent) {
        return next(err);
    }

    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({
        success: false,
        message: err.message || "Internal server error"
    });
};
```

Understand what each part does:

```text
console.error(err)
        ↓
Log the problem

res.headersSent?
        ↓
If already sent → pass error onward

statusCode
        ↓
Use custom status or 500

res.status(...)
        ↓
Set HTTP status

res.json(...)
        ↓
Send standard response
```

---

# 21. Why `err.statusCode` isn't available on normal Error

If you do:

```js
const error = new Error("User not found");
```

you get things like:

```js
error.message
error.name
error.stack
```

But:

```js
error.statusCode
```

doesn't automatically exist.

That's why this:

```js
const statusCode = err.statusCode || 500;
```

usually becomes:

```text
undefined → 500
```

unless we attach a status ourselves.

For example:

```js
const error = new Error("User not found");

error.statusCode = 404;
```

Now:

```js
err.statusCode
```

is:

```text
404
```

This temporary approach will soon be replaced by `AppError`.

---

# 22. Why `AppError` is better

Instead of doing this everywhere:

```js
const error = new Error("User not found");
error.statusCode = 404;

throw error;
```

we'll eventually write:

```js
throw new AppError("User not found", 404);
```

Then `AppError` can automatically store:

```text
message
statusCode
```

This gives your application a consistent way of creating known errors.

---

# 23. Error middleware should not contain business logic

This is an important architecture rule.

Don't do this:

```js
const errorMiddleware = async (err, req, res, next) => {
    const user = await User.findById(...);

    // decide what to do...
};
```

Why?

Because the error middleware shouldn't become another service layer.

Its job is mainly:

```text
receive error
   ↓
identify/classify error
   ↓
log appropriately
   ↓
choose response
   ↓
send response
```

Business operations should stay in:

```text
Controller
Service
Repository
```

---

# 24. Error middleware as a translator

A useful way to think about it:

```text
Internal application error
            ↓
     Error Middleware
            ↓
      HTTP response
```

It translates:

```text
JavaScript error
```

into:

```text
HTTP API response
```

For example:

```text
AppError(
    "User not found",
    404
)
```

becomes:

```http
HTTP/1.1 404 Not Found
```

and:

```json
{
    "success": false,
    "message": "User not found"
}
```

---

# 25. Error middleware and your layered architecture

Your backend architecture is roughly:

```text
Route
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
```

Errors can originate anywhere:

```text
Route
 ↓
Controller ❌
 ↓
Service ❌
 ↓
Repository ❌
 ↓
Database ❌
```

But the final response should be handled centrally:

```text
Any layer
   ↓
throw error
   ↓
asyncHandler
   ↓
next(error)
   ↓
errorMiddleware
   ↓
HTTP response
```

This is the big architectural benefit.

---

# 26. Example: Repository error

Imagine:

```js
const findUser = async (id) => {
    return User.findById(id);
};
```

MongoDB fails.

The repository doesn't do:

```js
res.status(500).json(...);
```

It simply allows the error to propagate.

Then:

```text
Repository
   ↓
error
   ↓
Service
   ↓
Controller
   ↓
asyncHandler
   ↓
errorMiddleware
```

The repository doesn't need to know anything about HTTP.

---

# 27. Example: Service-created error

Suppose the user doesn't exist.

Service:

```js
const getUser = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    return user;
};
```

Then:

```text
Service
   ↓
AppError(404)
   ↓
asyncHandler
   ↓
errorMiddleware
   ↓
404 response
```

This is exactly the separation we want.

# 31. One subtle point: error middleware isn't magic

It doesn't automatically catch every possible JavaScript error.

You still need to make sure errors enter Express's error flow.

For synchronous route code:

```js
app.get("/test", (req, res) => {
    throw new Error("Failed");
});
```

Express can handle this through its error mechanism.

For asynchronous code, your architecture needs to correctly propagate rejected Promises.

That's why we're going to build:

```text
asyncHandler
```

soon.

# 🧠 Final Mental Model

Don't memorize the function blindly.

Think:

```text
(err, req, res, next)
 │    │    │    │
 │    │    │    └── "Where should this go next?"
 │    │    └─────── "What response should client receive?"
 │    └──────────── "Which request caused this?"
 └───────────────── "What exactly went wrong?"
```

And the most important flow:

```text
        ERROR
          │
          ▼
     next(error)
          │
          ▼
 ┌─────────────────────┐
 │ Error Middleware    │
 │                     │
 │ err → understand    │
 │ req → get context   │
 │ res → reply         │
 │ next → forward      │
 └──────────┬──────────┘
            │
            ▼
       JSON response
```

### One sentence to remember

> **Error middleware is the central translator between your application's internal errors and the HTTP response sent to the client.**
