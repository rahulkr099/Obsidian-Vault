# Lesson 8.7 — Why Async Controllers Are Difficult

In the previous lessons, we built the error-handling foundation:

```text
Error
  ↓
next(error)
  ↓
error.middleware
  ↓
HTTP response
```

Now we have to answer an important question:

> **What happens when the error comes from an `async` controller?**

This is where `asyncHandler` becomes useful.

Your starter architecture specifically includes:

```text
utils/
├── AppError.js
└── asyncHandler.js
```

and the intended flow is:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
```

---

# 1. First: what is an async controller?

A normal controller might look like:

```js
const getUsers = (req, res) => {
    res.json({
        success: true,
        data: []
    });
};
```

An async controller looks like:

```js
const getUsers = async (req, res) => {
    const users = await User.find();

    res.json({
        success: true,
        data: users
    });
};
```

Why do we need `async`?

Because database operations are asynchronous.

For example:

```js
const users = await User.find();
```

The database may take some time to respond.

So:

```text
Request
   ↓
Controller
   ↓
Database
   ↓
Wait
   ↓
Result
   ↓
Response
```

---

# 2. The problem starts when the database fails

Suppose:

```js
const getUsers = async (req, res) => {
    const users = await User.find();

    res.json({
        success: true,
        data: users
    });
};
```

What happens if:

```js
await User.find();
```

rejects?

For example:

```text
MongoDB unavailable
```

The Promise becomes rejected.

Conceptually:

```text
getUsers()
    ↓
Promise
    ↓
REJECTED
    ↓
Error
```

Now we need to get that error into:

```js
errorMiddleware
```

---

# 3. The traditional solution: try/catch

The obvious solution is:

```js
const getUsers = async (req, res, next) => {
    try {
        const users = await User.find();

        res.json({
            success: true,
            data: users
        });
    } catch (error) {
        next(error);
    }
};
```

This works.

The flow is:

```text
Controller
    ↓
await database
    ↓
Database error
    ↓
catch(error)
    ↓
next(error)
    ↓
error middleware
```

This is perfectly valid.

But there is a problem.

---

# 4. The problem with try/catch everywhere

Imagine you have:

```text
50 controllers
```

Every controller needs:

```js
try {
    // business logic
} catch (error) {
    next(error);
}
```

For example:

```js
const getUsers = async (req, res, next) => {
    try {
        const users = await userService.getUsers();

        res.json({
            success: true,
            data: users
        });
    } catch (error) {
        next(error);
    }
};
```

Then:

```js
const getUser = async (req, res, next) => {
    try {
        const user = await userService.getUser(req.params.id);

        res.json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

Then:

```js
const createUser = async (req, res, next) => {
    try {
        const user = await userService.createUser(req.body);

        res.status(201).json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

Notice the pattern?

The actual business logic is tiny:

```js
const user = await userService.getUser(...);
```

But we surround it with repetitive code.

---

# 5. This is a classic abstraction opportunity

Look at this pattern:

```js
try {
    // controller logic
} catch (error) {
    next(error);
}
```

It repeats.

Whenever you see the same pattern repeated many times, ask:

> **Can I move the repeated behavior into a reusable function?**

The answer here is:

```text
asyncHandler
```

---

# 6. What should `asyncHandler` do?

Its job is simple:

> **Take an async controller and automatically forward rejected errors to Express.**

Instead of:

```text
Controller
 ↓
try/catch
 ↓
next(error)
```

we want:

```text
Controller
 ↓
asyncHandler
 ↓
next(error)
```

The controller becomes much cleaner.

---

# 7. Before building it, understand Promises

Consider:

```js
const getUsers = async (req, res) => {
    const users = await User.find();

    return users;
};
```

An `async` function always returns a Promise.

So:

```js
getUsers(...)
```

is conceptually:

```text
Promise
```

That Promise can:

```text
resolve
```

or:

```text
reject
```

---

# 8. Promise success

For example:

```js
const getData = async () => {
    return "Hello";
};
```

The Promise resolves:

```text
getData()
   ↓
Promise
   ↓
RESOLVED
   ↓
"Hello"
```

---

# 9. Promise failure

Now:

```js
const getData = async () => {
    throw new Error("Something failed");
};
```

The Promise rejects:

```text
getData()
   ↓
Promise
   ↓
REJECTED
   ↓
Error
```

This distinction is extremely important.

An async error is often a **rejected Promise**.

---

# 10. `await` makes the error look like a normal throw

Inside an async function:

```js
const getData = async () => {
    const result = await something();
};
```

If `something()` rejects:

```text
something()
    ↓
Promise rejection
    ↓
await
    ↓
throws inside async function
```

That's why `try/catch` works:

```js
try {
    await something();
} catch (error) {
    next(error);
}
```

---

# 11. Let's create the repetitive version first

Suppose:

```js
const getUser = async (req, res, next) => {
    try {
        const user = await userService.getUser(req.params.id);

        res.json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

The important parts are:

```text
Business logic:
await userService.getUser(...)

Error forwarding:
catch → next(error)
```

We want to remove only the repetitive part.

---

# 12. What if we create a wrapper?

Imagine this:

```js
const asyncHandler = (controller) => {
    // somehow execute controller
};
```

Then:

```js
const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    res.json({
        success: true,
        data: user
    });
});
```

This is much cleaner.

Now the controller doesn't contain:

```js
try {}
catch {}
```

---

# 13. How does the wrapper work?

Let's think carefully.

We receive a controller:

```js
controller
```

The controller is:

```js
async (req, res) => {
    const user = await userService.getUser(req.params.id);

    res.json({
        success: true,
        data: user
    });
}
```

Our wrapper needs to return a new Express middleware:

```js
(req, res, next) => {
    // execute controller
}
```

So conceptually:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        // execute controller
    };
};
```

---

# 14. Execute the controller

Inside:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res);
    };
};
```

Now the controller runs.

But what happens if it rejects?

We need to catch the Promise.

---

# 15. The Promise `.catch()` solution

Remember:

```js
controller(req, res)
```

returns a Promise because the controller is `async`.

So we can do:

```js
controller(req, res)
    .catch(next);
```

Now we have:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res)
            .catch(next);
    };
};
```

This is the basic idea behind async error wrappers.

---

# 16. What does `.catch(next)` mean?

This:

```js
.catch(next)
```

is shorthand for:

```js
.catch((error) => {
    next(error);
});
```

So:

```js
controller(req, res).catch(next);
```

means:

```text
Controller Promise
       ↓
    rejected?
       ↓
    catch(error)
       ↓
    next(error)
       ↓
Error middleware
```

This is the key concept of today's lesson.

---

# 17. Write it explicitly first

Before using the shorthand, understand this:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res)
            .catch((error) => {
                next(error);
            });
    };
};
```

This is easier to understand as a beginner.

Then:

```js
.catch(next)
```

is simply a shorter version.

---

# 18. Full example

Let's build a small example.

```js
import express from "express";

const app = express();

const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res)
            .catch((error) => {
                next(error);
            });
    };
};
```

Now our controller:

```js
const getUsers = asyncHandler(async (req, res) => {
    throw new Error("Database failed");

    res.json({
        success: true
    });
});
```

Route:

```js
app.get("/users", getUsers);
```

Error middleware:

```js
app.use((err, req, res, next) => {
    console.error(err);

    res.status(500).json({
        success: false,
        message: err.message
    });
});
```

Flow:

```text
GET /users
    ↓
getUsers
    ↓
throw Error
    ↓
Promise rejects
    ↓
asyncHandler catches
    ↓
next(error)
    ↓
errorMiddleware
    ↓
500 response
```

# 21. But why not just use try/catch?

You absolutely can.

`try/catch` isn't bad.

The problem is repetition.

Suppose you have:

```text
Users
Posts
Comments
Auth
Courses
Lessons
Payments
Orders
Analytics
Notifications
```

and each has many controllers.

You could end up with hundreds of:

```js
try {
    ...
} catch (error) {
    next(error);
}
```

That's unnecessary boilerplate.

`asyncHandler` gives you:

```text
One abstraction
    ↓
Many controllers
```

# 22. Important: asyncHandler does NOT handle business errors

This is an important distinction.

Suppose:

```js
const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    res.json({
        success: true,
        data: user
    });
});
```

`asyncHandler` doesn't decide:

```text
404
```

It only does:

```text
catch error
    ↓
next(error)
```

The **error middleware** decides how to turn that error into a response.

---

# 23. So each component has a different job

This is worth memorizing:

```text
AppError
    ↓
Create meaningful application error

asyncHandler
    ↓
Forward async errors

errorMiddleware
    ↓
Convert errors into HTTP responses
```

For example:

```text
Service
   ↓
throw new AppError("User not found", 404)
   ↓
asyncHandler
   ↓
next(error)
   ↓
errorMiddleware
   ↓
404 JSON
```

# 24. What happens without asyncHandler?

Imagine:

```js
app.get("/users", async (req, res) => {
    const users = await User.find();

    res.json(users);
});
```

If the database Promise rejects, you have to ensure that the rejection reaches Express's error pipeline.

Historically, Express applications commonly used explicit wrappers like `asyncHandler` to guarantee this propagation.

Modern Express versions have improved Promise rejection handling for route handlers, but the wrapper pattern is still useful as an **explicit architectural convention**, especially when your starter kit is designed around:

```text
controller
 ↓
asyncHandler
 ↓
errorMiddleware
```

So don't think:

> "asyncHandler is the only possible way to handle async errors."

Think:

> "asyncHandler is a reusable pattern that makes error propagation explicit and keeps controllers clean."

---

# 25. The important modern Express distinction

This is worth knowing for interviews.

With modern Express, rejected Promises from route handlers can be forwarded to the error-handling pipeline.

That means code such as:

```js
app.get("/users", async (req, res) => {
    const users = await User.find();

    res.json(users);
});
```

can propagate a rejected Promise into Express's error handling.

But your starter architecture still uses:

```text
asyncHandler
```

because it gives the project a consistent wrapper convention.

So learn **both concepts**:

```text
Express capability
        +
Project architecture
```

Don't confuse the two.

# 27. A more reusable implementation

The wrapper can be written as:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        Promise.resolve(controller(req, res, next))
            .catch(next);
    };
};

export default asyncHandler;
```

Why use:

```js
Promise.resolve(...)
```

instead of directly:

```js
controller(...).catch(...)
```

?

Because it makes the wrapper more tolerant of functions that return either:

```text
Promise
```

or:

```text
normal value
```

For an `async` controller, you'll normally get a Promise anyway.

---

# 28. Understand `Promise.resolve()`

Suppose:

```js
Promise.resolve("Hello")
```

gives a resolved Promise.

And:

```js
Promise.resolve(Promise.resolve("Hello"))
```

also works.

So:

```js
Promise.resolve(controller(...))
```

basically gives us a Promise that we can safely attach:

```js
.catch(next)
```

to.

The pattern becomes:

```js
Promise.resolve(controller(req, res, next))
    .catch(next);
```

---

# 29. Why pass `next` to the controller?

You may see:

```js
controller(req, res, next)
```

instead of:

```js
controller(req, res)
```

This allows the controller to explicitly call:

```js
next(error);
```

if needed.

For example:

```js
const controller = async (req, res, next) => {
    if (!req.params.id) {
        return next(new AppError("ID is required", 400));
    }

    // ...
};
```

The wrapper doesn't prevent normal Express middleware behavior.

---

# 30. But don't overuse `next` in controllers

If you're using:

```js
asyncHandler
```

then most async errors can simply be thrown:

```js
throw new AppError("User not found", 404);
```

rather than:

```js
return next(new AppError("User not found", 404));
```

For example:

```js
const getUser = asyncHandler(async (req, res) => {
    const user = await userService.getUser(req.params.id);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    res.json({
        success: true,
        data: user
    });
});
```

The wrapper catches the rejected Promise.
