# Lesson 8.8 — Building `asyncHandler.js` From Scratch

In Lesson 8.7, we learned **why** `asyncHandler` exists.

Now we'll build it ourselves instead of treating it like magic.

Your starter architecture has:

```text
src/
└── utils/
    ├── AppError.js
    └── asyncHandler.js
```

and the intended error flow is:

```text
Controller throws
      ↓
asyncHandler catches
      ↓
next(error)
      ↓
error.middleware
```

---

# 1. First, forget Express

Before writing:

```js
const asyncHandler = ...
```

let's understand the JavaScript problem.

Suppose we have:

```js
const getUser = async () => {
    throw new Error("User not found");
};
```

Because this function is `async`, calling it gives us a Promise:

```js
getUser();
```

Conceptually:

```text
getUser()
   ↓
Promise
   ↓
Rejected
   ↓
Error
```

We need something that can catch that rejection.

---

# 2. Catching the Promise manually

We can do:

```js
getUser()
    .catch((error) => {
        console.log(error.message);
    });
```

Output:

```text
User not found
```

So `.catch()` is capable of catching the rejected Promise.

---

# 3. What does `.catch(next)` mean?

Suppose Express gives us:

```js
next
```

and we have:

```js
getUser().catch(next);
```

This is shorthand for:

```js
getUser().catch((error) => {
    next(error);
});
```

So:

```js
.catch(next)
```

means:

> If the Promise rejects, give the error to `next`.

That's exactly what we want.

---

# 4. Now introduce the controller

Suppose our controller is:

```js
const getUser = async (req, res) => {
    const user = await User.findById(req.params.id);

    res.json({
        success: true,
        data: user
    });
};
```

This function returns a Promise because it's `async`.

So:

```js
getUser(req, res)
```

returns:

```text
Promise
```

Therefore we can theoretically do:

```js
getUser(req, res).catch(next);
```

But we don't want to repeat that in every route.

---

# 5. We need a reusable wrapper

Let's create:

```js
const asyncHandler = (controller) => {
    
};
```

The argument:

```js
controller
```

will be our async controller.

For example:

```js
asyncHandler(getUser);
```

Conceptually:

```text
asyncHandler
     ↑
  controller
     ↑
 async function
```

---

# 6. Why is this called a wrapper?

Because we're taking one function:

```js
getUser
```

and putting another function around it.

Think:

```text
        asyncHandler
       ┌─────────────┐
       │             │
       │  getUser    │
       │             │
       └─────────────┘
```

The outer function adds behavior around the inner function.

This is called a **higher-order function**.

---

# 7. What is a higher-order function?

A function is a higher-order function if it:

- receives a function as an argument, or
    
- returns a function.
    

`asyncHandler` does both.

It receives:

```js
controller
```

which is a function.

And it will return:

```js
(req, res, next) => {}
```

which is another function.

So:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        
    };
};
```

This is a very important JavaScript concept.

---

# 8. Why return another function?

Express expects middleware functions like:

```js
(req, res, next) => {
    // middleware logic
};
```

So `asyncHandler` needs to produce exactly that.

When we write:

```js
const getUser = asyncHandler(async (req, res) => {
    // ...
});
```

`asyncHandler(...)` returns:

```js
(req, res, next) => {
    // wrapper logic
};
```

Express can then use that function as middleware.

---

# 9. Let's build the wrapper slowly

Start with:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        
    };
};
```

Now we have:

```text
asyncHandler(controller)
        ↓
returns
        ↓
(req, res, next)
```

Exactly what Express expects.

---

# 10. Execute the controller

Inside the wrapper:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res, next);
    };
};
```

Now the controller is executed.

But there's a problem.

If the controller returns a rejected Promise, we're not catching it.

---

# 11. Store the Promise mentally

Remember:

```js
controller(req, res, next)
```

is an async function.

Therefore:

```js
controller(req, res, next)
```

returns:

```text
Promise
```

So we can attach:

```js
.catch(...)
```

to it.

---

# 12. Add `.catch()`

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res, next)
            .catch((error) => {
                next(error);
            });
    };
};
```

Congratulations.

You have built the basic `asyncHandler`.

---

# 13. Understand every line

Let's break it down:

```js
const asyncHandler = (controller) => {
```

Meaning:

> Create a function that receives a controller.

---

Then:

```js
return (req, res, next) => {
```

Meaning:

> Return an Express middleware function.

---

Then:

```js
controller(req, res, next)
```

Meaning:

> Execute the original controller.

---

Then:

```js
.catch((error) => {
```

Meaning:

> If the controller's Promise rejects...

---

Then:

```js
next(error);
```

Meaning:

> Send that error into Express's error-handling pipeline.

---

# 14. The complete flow

Suppose:

```js
const getUser = async (req, res) => {
    throw new Error("User not found");
};
```

We do:

```js
asyncHandler(getUser);
```

The wrapper becomes:

```text
Request
   ↓
asyncHandler wrapper
   ↓
getUser()
   ↓
Promise rejected
   ↓
.catch()
   ↓
next(error)
   ↓
error middleware
```

This is the entire purpose of the utility.

```text

    └── asyncHandler.js
```

Put:

```js

    return (req, res, next) => {

            });

```

This is the version I want you to understand first.

Don't rush toward shorter versions.

---

# 16. Now simplify `.catch()`

We previously learned:

```js
.catch((error) => {
    next(error);
});
```

can be shortened to:

```js
.catch(next);
```

Therefore:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res, next)
            .catch(next);
    };
};
```

Same idea.

---

# 17. Now introduce `Promise.resolve()`

A commonly used implementation is:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        Promise
            .resolve(controller(req, res, next))
            .catch(next);
    };
};
```

Why?

Because:

```js
Promise.resolve(...)
```

ensures that we're working with a Promise.

---

# 18. Understand `Promise.resolve()`

Example:

```js
Promise.resolve("Hello");
```

returns a resolved Promise.

You can do:

```js
Promise.resolve("Hello")
    .then((value) => {
        console.log(value);
    });
```

Output:

```text
Hello
```

---

# 19. What if we give it a Promise?

```js
const promise = Promise.resolve("Hello");

Promise.resolve(promise);
```

It still works.

So:

```js
Promise.resolve(controller(...))
```

gives us a Promise-like flow that we can safely attach:

```js
.catch(next)
```

to.

---

# 20. Why not simply use `.catch(next)`?

For your async controllers, this:

```js
controller(req, res, next)
    .catch(next);
```

is enough because an `async` function returns a Promise.

The `Promise.resolve()` version is a defensive/general-purpose pattern:

```js
Promise.resolve(controller(req, res, next))
    .catch(next);
```

For this course, understand both.

---

# 21. The version we'll use

For your backend starter, I recommend this simple implementation:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        Promise.resolve(controller(req, res, next))
            .catch(next);
    };
};

export default asyncHandler;
```

It's short, readable, and makes the intent clear.

Keep this mental model:

```text
┌──────────────────────────────┐
│ Controller                   │
│                              │
│ Business request handling    │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ asyncHandler                 │
│                              │
│ Promise error forwarding     │
└──────────────┬───────────────┘
               │
               ▼

│                              │

└──────────────────────────────┘
```

# 27. Why `asyncHandler` doesn't send responses

A common beginner mistake is trying to do:

```js
const asyncHandler = (controller) => {
    return async (req, res, next) => {
        try {
            await controller(req, res);
        } catch (error) {
            res.status(500).json({
                message: error.message
            });
        }
    };
};
```

It technically can work.

But it's not ideal for your architecture.

Why?

Because now `asyncHandler` is deciding the API response.

We want:

```text
asyncHandler
    ↓
next(error)
```

and:

```text
errorMiddleware
    ↓
res.status(...).json(...)
```

That separation is cleaner.

---

# 28. Why `asyncHandler` doesn't decide status codes

Suppose:

```js
throw new AppError("User not found", 404);
```

Another error:

```js
throw new AppError("Unauthorized", 401);
```

Another:

```js
throw new AppError("Database failed", 500);
```

`asyncHandler` shouldn't care.

It simply says:

```text
"An error happened."
        ↓
next(error)
```

Then the centralized error middleware decides:

```text
404
401
500
...
```

---

# 29. How `AppError` fits later

Eventually we'll have:

```js
throw new AppError("User not found", 404);
```

Then:

```text
AppError
   ↓
asyncHandler
   ↓
next(error)
   ↓
errorMiddleware
   ↓
err.statusCode
   ↓
404
```

So:

```text
AppError
```

describes the error.

```text
asyncHandler
```

moves the error.

```text
errorMiddleware
```

responds to the client.

This is an excellent separation of concerns.

# 30. One important edge case

Consider:

```js
const controller = (req, res) => {
    throw new Error("Something failed");
};
```

This controller is **not async**.

The simple implementation:

```js
controller(req, res, next).catch(next);
```

can fail because a synchronous function doesn't return a Promise.

That's one reason the more defensive version:

```js
Promise.resolve(controller(req, res, next))
    .catch(next);
```

is attractive.

However, there's a subtle point:

`Promise.resolve()` does not itself catch a synchronous throw that happens while evaluating the argument.

For example:

```js
Promise.resolve(controller(req, res, next))
```

first has to execute:

```js
controller(req, res, next)
```

If that synchronously throws, execution never reaches `Promise.resolve()`.

So if you wanted a wrapper that handles **both synchronous throws and Promise rejections**, you could use:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        Promise.resolve()
            .then(() => controller(req, res, next))
            .catch(next);
    };
};
```

Now:

```text
sync throw
   ↓
Promise rejection
   ↓
.catch(next)
```

and:

```text
async rejection
   ↓
.catch(next)
```

both enter the same pipeline.

---

# 31. Do we need that complicated version?

For your project, don't make things unnecessarily complicated.

Your controllers are intended to be async:

```js
async (req, res) => {
    ...
}
```

So this is perfectly understandable:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        controller(req, res, next)
            .catch(next);
    };
};
```

Or the common defensive style:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        Promise.resolve(controller(req, res, next))
            .catch(next);
    };
};
```

The important thing is **understanding what it does**, not blindly copying one implementation.

# 🧠 Final Mental Model

Don't memorize:

```js
Promise.resolve(controller(req, res, next)).catch(next);
```

Understand it as:

```text
             controller
                 │
                 ▼
        execute async code
                 │
          ┌──────┴──────┐
          │             │
       success        failure
          │             │
          ▼             ▼
       response      catch(error)
                        │
                        ▼
                   next(error)
                        │
                        ▼
                error middleware
                        │
                        ▼
                   JSON response
```

And remember the responsibilities:

```text
AppError
→ Describes an application error

asyncHandler
→ Forwards async errors

errorMiddleware
→ Converts errors into HTTP responses
```

That three-part relationship is one of the most important foundations of the backend architecture you're building.
