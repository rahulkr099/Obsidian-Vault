# Lesson 8.9 — Understanding Promise Rejection

Before we build `AppError` in **8.10**, we need to make one thing completely clear:

> **What exactly happens to an error inside an async function?**

Your Phase 8 roadmap places **Promise rejection immediately before `AppError`**, so this lesson is the bridge between `asyncHandler` and custom application errors.

---

## 1. The basic idea

An `async` function always returns a Promise.

```js
const getUser = async () => {
    return "Rahul";
};
```

Even though you wrote:

```js
return "Rahul";
```

JavaScript effectively gives you:

```text
getUser()
   ↓
Promise
   ↓
fulfilled
   ↓
"Rahul"
```

So:

```js
const result = getUser();

console.log(result);
```

doesn't immediately print:

```text
Rahul
```

It prints a Promise.

---

# 2. A Promise has two important outcomes

A Promise can:

```text
              Promise
              /     \
             /       \
       fulfilled    rejected
          │             │
       success         error
```

For example:

### Success

```js
const getUser = async () => {
    return "Rahul";
};
```

### Failure

```js
const getUser = async () => {
    throw new Error("User not found");
};
```

The second one produces a **rejected Promise**.

---

# 3. What does `throw` do inside `async`?

Look at:

```js
const getUser = async () => {
    throw new Error("User not found");
};
```

You might think:

> "The function throws an error."

That's true, but there's a more useful way to think about it:

```text
async function
     ↓
throw Error
     ↓
Promise becomes rejected
```

So:

```js
getUser()
```

results in:

```text
Promise
   ↓
REJECTED
   ↓
Error("User not found")
```

This is extremely important for `asyncHandler`.

---

# 4. Catching the rejection

You can use:

```js
getUser()
    .catch((error) => {
        console.log(error.message);
    });
```

Output:

```text
User not found
```

So:

```text
Rejected Promise
      ↓
.catch()
      ↓
error
```

---

# 5. `.catch()` is like async `try/catch`

Compare these two.

### Promise style

```js
getUser()
    .catch((error) => {
        console.log(error.message);
    });
```

### `try/catch` style

```js
try {
    await getUser();
} catch (error) {
    console.log(error.message);
}
```

They are different syntaxes for handling asynchronous failures.

Mental model:

```text
Promise
   ↓
.catch(error)

          ≈

await
   ↓
try/catch
```

---

# 6. What happens with `await`?

Consider:

```js
const getUser = async () => {
    throw new Error("User not found");
};

const main = async () => {
    const user = await getUser();

    console.log(user);
};
```

When:

```js
await getUser();
```

encounters a rejected Promise, the error is thrown at the `await` point.

So:

```text
getUser()
   ↓
Promise rejected
   ↓
await
   ↓
error thrown
```

That's why this works:

```js
try {
    const user = await getUser();
} catch (error) {
    console.log(error.message);
}
```

---

# 7. The important connection to controllers

Suppose your controller is:

```js
const getUser = async (req, res) => {
    const user = await User.findById(req.params.id);

    res.json({
        success: true,
        data: user
    });
};
```

If MongoDB fails:

```text
User.findById()
       ↓
Promise rejected
       ↓
await
       ↓
controller Promise rejected
```

That's why `asyncHandler` can catch it.

---

# 8. Revisit our `asyncHandler`

We built:

```js
const asyncHandler = (controller) => {
    return (req, res, next) => {
        Promise.resolve(controller(req, res, next))
            .catch(next);
    };
};
```

Now this should make more sense.

Suppose:

```js
const getUser = asyncHandler(async (req, res) => {
    throw new Error("User not found");
});
```

Flow:

```text
Request
   ↓
asyncHandler
   ↓
controller()
   ↓
throw Error
   ↓
Promise rejected
   ↓
.catch(next)
   ↓
next(error)
   ↓
error middleware
```

---

# 9. `.catch(next)` deserves special attention

You should be able to expand:

```js
.catch(next);
```

into:

```js
.catch((error) => {
    next(error);
});
```

So:

```js
controller(req, res, next)
    .catch(next);
```

really means:

```js
controller(req, res, next)
    .catch((error) => {
        next(error);
    });
```

This is one of those small pieces of JavaScript syntax that looks mysterious until you understand the function being passed.

---

# 10. Why does `next(error)` matter?

Express has two different kinds of `next()` calls:

```js
next();
```

and:

```js
next(error);
```

### `next()`

Means:

> Continue normal middleware execution.

### `next(error)`

Means:

> Something went wrong. Enter the error-handling pipeline.

So:

```text
next()
  ↓
normal middleware

next(error)
  ↓
error middleware
```

# 11. Full Express flow

Now combine everything:

```text
                  HTTP REQUEST
                       │
                       ▼
                    ROUTE
                       │
                       ▼
                 asyncHandler
                       │
                       ▼
                  CONTROLLER
                       │
                       ▼
                  await DB
                       │
                ┌──────┴──────┐
                │             │
             success        failure
                │             │
                ▼             ▼
             res.json()   Promise reject
                              │
                              ▼
                         .catch(next)
                              │
                              ▼
                         next(error)
                              │
                              ▼
                      error middleware
                              │
                              ▼
                         JSON response
```

This is the central error architecture from your starter.

---

# 12. Promise rejection is not always an HTTP error

This is an important distinction.

A Promise doesn't know anything about:

```text
HTTP
404
401
500
API
Express
```

It only knows:

```text
fulfilled
```

or:

```text
rejected
```

For example:

```js
const calculate = async () => {
    throw new Error("Invalid calculation");
};
```

JavaScript knows:

```text
Promise rejected
```

It doesn't know:

```text
HTTP 400
```

That HTTP meaning is something **our application architecture adds later**.

---

# 13. This is why `AppError` exists

Now we're getting close to the next lesson.

Suppose:

```js
throw new Error("User not found");
```

JavaScript knows:

```text
message = "User not found"
```

But your API also needs to know:

```text
statusCode = 404
```

Normal `Error` doesn't automatically provide that.

So eventually we'll create:

```js
throw new AppError("User not found", 404);
```

Then:

```text
AppError
├── message → "User not found"
└── statusCode → 404
```

That gives our error middleware useful information.

---

# 14. Compare normal `Error` and `AppError`

### Normal Error

```js
throw new Error("User not found");
```

Conceptually:

```text
Error
 ├── message
 ├── name
 └── stack
```

### AppError

Eventually:

```js
throw new AppError("User not found", 404);
```

Conceptually:

```text
AppError
 ├── message
 ├── statusCode
 ├── name
 └── stack
```

Now the error has **application meaning**.

---

# 15. Don't confuse error creation with error handling

This distinction is extremely important.

### Creating an error

```js
throw new AppError("User not found", 404);
```

### Catching/forwarding the error

```js
.catch(next);
```

### Sending the HTTP response

```js
res.status(404).json({
    success: false,
    message: err.message
});
```

Three different responsibilities:

```text
AppError
   ↓
Describe

asyncHandler
   ↓
Forward

errorMiddleware
   ↓
Respond
```

# 16. A real example

Suppose:

```js
const getUser = asyncHandler(async (req, res) => {
    const user = await userRepository.findById(req.params.id);

    if (!user) {
        throw new AppError("User not found", 404);
    }

    res.status(200).json({
        success: true,
        data: user
    });
});
```

Flow:

```text
GET /users/123
       ↓
Controller
       ↓
Repository
       ↓
User doesn't exist
       ↓
AppError("User not found", 404)
       ↓
Promise rejected
       ↓
asyncHandler
       ↓
next(error)
       ↓
error.middleware
       ↓
404
```

Now every layer has a clear responsibility.

# 17. What if MongoDB fails?

Suppose the repository does:

```js
const findById = async (id) => {
    return User.findById(id);
};
```

MongoDB suddenly fails.

The repository doesn't need to write:

```js
res.status(500).json(...);
```

It simply allows the error to propagate.

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
asyncHandler
   ↓
error middleware
```

That's one of the biggest advantages of centralized error handling.

---

# 18. What if validation fails?

Later, your validation middleware may detect:

```json
{
    "email": "wrong"
}
```

and produce an error.

It can enter the same pipeline:

```text
Validation error
      ↓
next(error)
      ↓
error middleware
      ↓
400 response
```

So many different error sources can converge on one place.

```text
Database error ─────┐
Validation error ───┤
Auth error ──────────┤
Business error ──────┤
JWT error ───────────┤
                      ▼
              Error Middleware
                      │
                      ▼
                HTTP response
```

# 19. Rejected Promise vs thrown error

This is a common interview topic.

### Synchronous function

```js
const test = () => {
    throw new Error("Failed");
};
```

The function directly throws.

### Async function

```js
const test = async () => {
    throw new Error("Failed");
};
```

The async function returns a **rejected Promise**.

Mental model:

```text
Normal function:
throw
 ↓
error

Async function:
throw
 ↓
rejected Promise
```

---

# 20. What happens if you don't catch the rejection?

Consider:

```js
const test = async () => {
    throw new Error("Boom");
};

test();
```

You created a rejected Promise but didn't handle it.

That's a problem.

In a backend, you want failures to enter your centralized error system.

That's why patterns like:

```js
asyncHandler(...)
```

exist.

---

# 21. Don't create random `.catch()` blocks everywhere

You might be tempted to write:

```js
const controller = async (req, res) => {
    try {
        // ...
    } catch (error) {
        console.log(error);
    }
};
```

or:

```js
someFunction()
    .catch(error => console.log(error));
```

everywhere.

But where should the error ultimately go?

For your architecture:

```text
Controller
    ↓
asyncHandler
    ↓
next(error)
    ↓
Global error middleware
```

Centralizing the final handling makes your API behavior consistent.

---

# 22. One important mistake

Never do this:

```js
const controller = asyncHandler(async (req, res) => {
    try {
        const user = await User.findById(req.params.id);
    } catch (error) {
        console.log(error);
    }
});
```

Why?

Because you've caught the error and then done nothing with it.

The error never reaches:

```text
error middleware
```

If you catch an error manually, either:

```js
throw error;
```

or:

```js
next(error);
```

depending on your architecture.

But most ordinary controller errors don't need a local `try/catch` when you're using `asyncHandler`.

---

# 23. When is local `try/catch` actually useful?

Sometimes you genuinely need to recover from an error.

Example:

```js
try {
    await sendEmail();
} catch (error) {
    console.log("Email failed, continuing...");
}
```

Maybe email is optional and the main operation can continue.

That's different from:

```text
Something failed
   ↓
I want the API request to fail
```

In that case:

```js
throw error;
```

or allow the rejection to reach `asyncHandler`.

So the rule isn't:

> "Never use try/catch."

Instead:

> **Use try/catch when you actually have something useful to do with the error.**

---

# 24. Error propagation is the important concept

Imagine a chain:

```text
Repository
    ↓
Service
    ↓
Controller
```

If the repository fails:

```text
Repository
    ❌
     │
     ▼
   throw
     │
     ▼
 Service
     │
     ▼
 Controller
     │
     ▼
asyncHandler
     │
     ▼
next(error)
```

Unless a layer intentionally handles the error, it should be allowed to propagate.

---

# 25. Think of errors like a package

A useful analogy:

```text
Error
  ↓
Package
```

Different layers can pass the package along:

```text
Repository
   ↓
Service
   ↓
Controller
   ↓
asyncHandler
   ↓
Error middleware
```

`asyncHandler` doesn't open the package.

It simply says:

> "This package contains an error. Send it to the error handler."

`error.middleware` finally opens it and decides what response to send.

# 27. Mini Exercise 2 — Add `asyncHandler`

Now create:

```js
const asyncHandler = (controller) => {
    return (...args) => {
        Promise.resolve(controller(...args))
            .catch((error) => {
                console.log("Caught:", error.message);
            });
    };
};
```

Then:

```js
const controller = asyncHandler(async () => {
    throw new Error("Controller failed");
});

controller();
```

Expected:

```text
Caught: Controller failed
```

You've just recreated the fundamental idea behind the utility used by your backend starter.
