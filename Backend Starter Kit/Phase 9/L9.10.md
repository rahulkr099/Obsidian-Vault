# Lesson 9.10 — Joi Array and Object Validation

So far we've learned how to validate:

```text
9.8 → Strings
9.9 → Numbers, Booleans, Dates
```

Now we're reaching an **important step**.

Real MERN API requests are rarely flat.

You will commonly receive data like:

```json
{
  "name": "Laptop",
  "tags": ["electronics", "computer"],
  "address": {
    "city": "Sitamarhi",
    "country": "India"
  }
}
```

Or even:

```json
{
  "items": [
    {
      "productId": "abc123",
      "quantity": 2
    },
    {
      "productId": "xyz789",
      "quantity": 1
    }
  ]
}
```

This is where Joi becomes much more powerful.

---

# 1. Joi Array

The basic array schema is:

```js
Joi.array()
```

Example:

```js
const schema = Joi.object({
    tags: Joi.array()
});
```

This means:

```text
tags
 ↓
must be an array
```

Valid:

```json
{
  "tags": ["javascript", "node", "mongodb"]
}
```

Invalid:

```json
{
  "tags": "javascript"
}
```

---

# 2. The Important Question

This:

```js
Joi.array()
```

only validates:

> Is this an array?

It doesn't necessarily tell us:

> What is allowed inside the array?

For example:

```json
{
  "tags": [
    "javascript",
    123,
    true,
    {},
    null
  ]
}
```

If your application expects only strings, we need to define that.

---

# 3. `.items()`

Use `.items()` to define the type of array elements.

```js
tags: Joi.array()
    .items(Joi.string())
```

Now:

```json
{
  "tags": [
    "javascript",
    "node",
    "mongodb"
  ]
}
```

is valid.

But:

```json
{
  "tags": [
    "javascript",
    123
  ]
}
```

is rejected.

Think:

```text
Joi.array()
    ↓
"Give me an array"

.items(Joi.string())
    ↓
"Every item must be a string"
```

---

# 4. Array of Numbers

You can do the same with numbers:

```js
ids: Joi.array()
    .items(Joi.number())
```

Example:

```json
{
  "ids": [10, 20, 30]
}
```

If they must be integers:

```js
ids: Joi.array()
    .items(
        Joi.number().integer()
    )
```

---

# 5. Array of Booleans

```js
flags: Joi.array()
    .items(Joi.boolean())
```

Valid:

```json
{
  "flags": [true, false, true]
}
```

---

# 6. Array of Dates

```js
dates: Joi.array()
    .items(
        Joi.date().iso()
    )
```

Example:

```json
{
  "dates": [
    "2026-08-20",
    "2026-08-21",
    "2026-08-22"
  ]
}
```

---

# 7. `.min()` for Arrays

Remember:

```js
Joi.string().min(3)
```

means minimum string length.

For an array:

```js
Joi.array().min(1)
```

means:

> The array must contain at least one item.

Example:

```js
tags: Joi.array()
    .items(Joi.string())
    .min(1)
```

So:

```json
{
  "tags": []
}
```

is rejected.

But:

```json
{
  "tags": ["javascript"]
}
```

is valid.

---

# 8. `.max()` for Arrays

You can limit the number of items:

```js
tags: Joi.array()
    .items(Joi.string())
    .min(1)
    .max(10)
```

Now:

```text
1–10 tags
```

are allowed.

This is extremely useful for API protection.

For example, don't allow a client to send:

```json
{
  "tags": [
    "...",
    "...",
    "...",
    "...",
    "...",
    "... thousands of items ..."
  ]
}
```

unless your application actually needs that.

---

# 9. `.length()`

If the array must contain exactly a specific number of items:

```js
coordinates: Joi.array()
    .items(Joi.number())
    .length(2)
```

Now:

```json
{
  "coordinates": [10, 20]
}
```

is valid.

But:

```json
{
  "coordinates": [10, 20, 30]
}
```

is invalid.

---

# 10. `.unique()`

Suppose you don't want duplicate tags.

Use:

```js
tags: Joi.array()
    .items(Joi.string())
    .unique()
```

Now:

```json
{
  "tags": ["node", "mongodb", "express"]
}
```

is valid.

But:

```json
{
  "tags": ["node", "mongodb", "node"]
}
```

is rejected.

This is useful for:

```text
tags
roles
permissions
IDs
categories
selected options
```

---

# 11. Array + String Validation

You can combine array rules with string rules:

```js
tags: Joi.array()
    .items(
        Joi.string()
            .trim()
            .lowercase()
            .min(2)
            .max(30)
    )
    .min(1)
    .max(10)
    .unique()
```

Now every tag must:

```text
✓ be a string
✓ be trimmed
✓ be lowercase
✓ contain 2–30 characters
```

and the array itself must:

```text
✓ contain at least 1 item
✓ contain at most 10 items
✓ contain no duplicates
```

This is a **real-world schema**.

---

# 12. A tags example

Imagine:

```http
POST /api/v1/products
```

Request:

```json
{
  "name": "Mechanical Keyboard",
  "tags": [
    "Keyboard",
    "Gaming",
    "Mechanical"
  ]
}
```

Schema:

```js
const productSchema = Joi.object({
    name: Joi.string()
        .trim()
        .required(),

    tags: Joi.array()
        .items(
            Joi.string()
                .trim()
                .lowercase()
                .min(2)
                .max(30)
        )
        .min(1)
        .max(10)
        .unique()
        .required()
});
```

The result can become normalized:

```text
"Keyboard"
     ↓
"keyboard"
```

depending on Joi's conversion behavior.

---

# 13. Arrays Can Be Optional

This:

```js
tags: Joi.array()
    .items(Joi.string())
```

means the field can be absent unless you make it required.

For example:

```json
{}
```

can be valid.

If the array must exist:

```js
tags: Joi.array()
    .items(Joi.string())
    .required()
```

---

# 14. Empty Arrays

This is an important design decision.

Suppose:

```js
tags: Joi.array()
    .items(Joi.string())
```

Do you want:

```json
{
  "tags": []
}
```

to be valid?

If yes, that's fine.

If no:

```js
tags: Joi.array()
    .items(Joi.string())
    .min(1)
```

So remember:

```text
required()
    ↓
field must exist

min(1)
    ↓
array must contain at least one item
```

These are different.

---

# 15. `.single()`

Sometimes an API accepts:

```text
tags=javascript
```

and also:

```text
tags=javascript&tags=node
```

Joi has `.single()` to allow a single value to be treated as an array.

Conceptually:

```js
tags: Joi.array()
    .items(Joi.string())
    .single()
```

This can be useful with query parameters.

But don't use it unless your API intentionally supports both formats.

A predictable API contract is usually better than accepting many formats.

---

# 16. Array of Objects

Now we reach the really important part.

Suppose you receive:

```json
{
  "items": [
    {
      "productId": "abc123",
      "quantity": 2
    },
    {
      "productId": "xyz789",
      "quantity": 1
    }
  ]
}
```

This is:

```text
object
  ↓
array
  ↓
objects
```

Joi can express this naturally.

```js
const schema = Joi.object({
    items: Joi.array()
        .items(
            Joi.object({
                productId: Joi.string().required(),
                quantity: Joi.number()
                    .integer()
                    .min(1)
                    .required()
            })
        )
        .min(1)
        .required()
});
```

---

# 17. Understand the Nesting

Look at this:

```js
Joi.object({
    items: Joi.array()
        .items(
            Joi.object({
                productId: Joi.string().required(),
                quantity: Joi.number()
                    .integer()
                    .min(1)
                    .required()
            })
        )
})
```

Read it from outside → inside:

```text
Request
 ↓
Object
 ↓
items
 ↓
Array
 ↓
Each item
 ↓
Object
 ↓
productId + quantity
```

This mental model is extremely useful.

---

# 18. Validate Every Object

Suppose the client sends:

```json
{
  "items": [
    {
      "productId": "abc",
      "quantity": 2
    },
    {
      "productId": "xyz",
      "quantity": -5
    }
  ]
}
```

The second object fails:

```text
quantity = -5
```

because:

```js
Joi.number()
    .integer()
    .min(1)
```

requires:

```text
quantity >= 1
```

So Joi validates **each array element** against the object schema.

---

# 19. Nested Objects

You don't need arrays to use nested objects.

Example:

```json
{
  "name": "Rahul",
  "address": {
    "city": "Sitamarhi",
    "state": "Bihar",
    "country": "India"
  }
}
```

Schema:

```js
const schema = Joi.object({
    name: Joi.string().required(),

    address: Joi.object({
        city: Joi.string().required(),
        state: Joi.string().required(),
        country: Joi.string().required()
    }).required()
});
```

This is one of the most common Joi patterns.

---

# 20. Why Nested Objects Matter in MERN

MongoDB documents often contain nested structures.

For example:

```js
{
    name: "Rahul",
    profile: {
        bio: "...",
        website: "...",
        location: {
            city: "...",
            country: "..."
        }
    }
}
```

Your API validation can mirror this structure:

```js
const schema = Joi.object({
    name: Joi.string(),

    profile: Joi.object({
        bio: Joi.string(),
        website: Joi.string().uri(),

        location: Joi.object({
            city: Joi.string(),
            country: Joi.string()
        })
    })
});
```

---

# 21. Nested Object + `.required()`

Compare:

```js
profile: Joi.object({
    bio: Joi.string()
})
```

with:

```js
profile: Joi.object({
    bio: Joi.string()
}).required()
```

The first means:

```text
profile can be missing
```

The second means:

```text
profile must exist
```

Again:

```text
required()
```

is about the field's presence.

---

# 22. Required Nested Fields

You can independently control each level:

```js
profile: Joi.object({
    bio: Joi.string().optional(),

    website: Joi.string()
        .uri()
        .optional(),

    age: Joi.number()
        .integer()
        .required()
}).required()
```

This means:

```text
profile → required

bio → optional
website → optional
age → required
```

This level of control is one reason Joi is useful for API schemas.

---

# 23. `.unknown(false)` on Objects

Suppose:

```js
const schema = Joi.object({
    name: Joi.string(),
    email: Joi.string().email()
});
```

You can explicitly reject unknown keys:

```js
const schema = Joi.object({
    name: Joi.string(),
    email: Joi.string().email()
}).unknown(false);
```

Now:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "admin": true
}
```

can be rejected because:

```text
admin
```

isn't part of the schema.

---

# 24. Unknown Keys Inside Nested Objects

This is important.

Consider:

```js
const schema = Joi.object({
    profile: Joi.object({
        bio: Joi.string()
    })
});
```

If you want strict control inside `profile`, you can define its unknown-key behavior too:

```js
const schema = Joi.object({
    profile: Joi.object({
        bio: Joi.string()
    }).unknown(false)
});
```

Now:

```json
{
  "profile": {
    "bio": "Hello",
    "isAdmin": true
  }
}
```

can be rejected.

Think about validation at **every boundary**.

# 25. Arrays of Objects in E-commerce

A shopping cart is a perfect example.

Request:

```json
{
  "items": [
    {
      "productId": "665abc",
      "quantity": 2
    },
    {
      "productId": "665xyz",
      "quantity": 3
    }
  ]
}
```

Schema:

```js
const cartSchema = Joi.object({
    items: Joi.array()
        .items(
            Joi.object({
                productId: Joi.string()
                    .trim()
                    .required(),

                quantity: Joi.number()
                    .integer()
                    .min(1)
                    .max(50)
                    .required()
            }).unknown(false)
        )
        .min(1)
        .max(50)
        .required()
}).unknown(false);
```

This is already very close to what you'll write in real applications.

---

# 26. What This Schema Guarantees

At the top level:

```text
✓ must be an object
✓ only known fields
✓ items is required
```

For `items`:

```text
✓ must be an array
✓ at least 1 item
✓ maximum 50 items
```

For each item:

```text
✓ must be an object
✓ only known fields
✓ productId required
✓ quantity required
✓ quantity integer
✓ quantity >= 1
✓ quantity <= 50
```

That's a strong API contract.

# 28. Don't Trust IDs Just Because They're Strings

A common beginner schema:

```js
productId: Joi.string().required()
```

may be enough for a first version.

But eventually you might want to validate the actual ID format.

For example, if your application expects MongoDB ObjectIds, you could create a dedicated validation rule.

Conceptually:

```text
productId
   ↓
correct type
   ↓
correct ID format
   ↓
database lookup
   ↓
does the product actually exist?
```

These are different layers.

---

# 29. Format vs Existence

This distinction is extremely important.

Suppose:

```json
{
  "productId": "665abc..."
}
```

Joi may determine:

```text
"this looks like a valid ID"
```

But that doesn't mean:

```text
"this product exists in MongoDB"
```

So:

```text
Joi
 ↓
format validation

Service
 ↓
existence/business validation
```

Keep those responsibilities separate.

---

# 30. Deeply Nested Objects

Joi can handle structures like:

```json
{
  "user": {
    "profile": {
      "contact": {
        "email": "rahul@example.com"
      }
    }
  }
}
```

Schema:

```js
const schema = Joi.object({
    user: Joi.object({
        profile: Joi.object({
            contact: Joi.object({
                email: Joi.string()
                    .email()
                    .required()
            }).required()
        }).required()
    }).required()
});
```

Read it as:

```text
user
 ↓
profile
 ↓
contact
 ↓
email
```

Don't be scared by the nesting.

Build schemas from the outside inward.

---

# 31. Reuse Nested Schemas

If the same structure appears in multiple places, don't copy it everywhere.

For example:

```js
const addressSchema = Joi.object({
    city: Joi.string()
        .trim()
        .required(),

    state: Joi.string()
        .trim()
        .required(),

    country: Joi.string()
        .trim()
        .required()
});
```

Then:

```js
const userSchema = Joi.object({
    name: Joi.string().required(),

    address: addressSchema.required()
});
```

This is much cleaner.

---

# 32. Reusable Item Schemas

Similarly:

```js
const cartItemSchema = Joi.object({
    productId: Joi.string().required(),

    quantity: Joi.number()
        .integer()
        .min(1)
        .required()
});
```

Then:

```js
const cartSchema = Joi.object({
    items: Joi.array()
        .items(cartItemSchema)
        .min(1)
        .required()
});
```

This is the beginning of **schema composition**.

It becomes very useful as your backend grows.

---

# 33. One Schema Per Responsibility

Don't create one giant Joi file containing every schema in your entire application.

Instead, organize them around API/domain responsibilities.

For example:

```text
src/
├── modules/
│   ├── users/
│   │   ├── user.validation.js
│   │   ├── user.controller.js
│   │   ├── user.service.js
│   │   └── user.repository.js
│   │
│   └── products/
│       ├── product.validation.js
│       ├── product.controller.js
│       ├── product.service.js
│       └── product.repository.js
```

We'll eventually connect this to the architecture you've been learning.

# 35. A More Complex Order Schema

Let's build something closer to a real application.

Request:

```json
{
  "shippingAddress": {
    "name": "Rahul Kumar",
    "city": "Sitamarhi",
    "state": "Bihar",
    "postalCode": "843301"
  },
  "items": [
    {
      "productId": "abc123",
      "quantity": 2
    },
    {
      "productId": "xyz789",
      "quantity": 1
    }
  ],
  "notes": "Please deliver carefully"
}
```

Schema:

```js
const orderSchema = Joi.object({
    shippingAddress: Joi.object({
        name: Joi.string()
            .trim()
            .min(2)
            .max(100)
            .required(),

        city: Joi.string()
            .trim()
            .min(2)
            .max(100)
            .required(),

        state: Joi.string()
            .trim()
            .min(2)
            .max(100)
            .required(),

        postalCode: Joi.string()
            .trim()
            .pattern(/^[0-9]{6}$/)
            .required()
    }).required(),

    items: Joi.array()
        .items(
            Joi.object({
                productId: Joi.string()
                    .trim()
                    .required(),

                quantity: Joi.number()
                    .integer()
                    .min(1)
                    .max(50)
                    .required()
            }).unknown(false)
        )
        .min(1)
        .max(50)
        .required(),

    notes: Joi.string()
        .trim()
        .max(500)
        .optional()
}).unknown(false);
```

Now you're thinking like an API developer.

# 36. Notice What We're NOT Validating

The order request may eventually need:

```text
product exists
price is correct
user is allowed to buy product
product has enough stock
shipping address is serviceable
user has permission
```

Joi should not do all of these things.

Joi primarily handles:

```text
shape
type
format
basic constraints
normalization
```

Then:

```text
Service layer
```

handles business logic.

This separation becomes **very important in Phase 7+ architecture**.

---

# 37. Validation Layer vs Service Layer

Think:

```text
                Request
                   │
                   ▼
             Joi Validation
                   │
        ┌──────────┴──────────┐
        │                     │
      invalid                valid
        │                     │
        ▼                     ▼
      400                  Controller
                              │
                              ▼
                           Service
                              │
                    Business validation
                              │
                              ▼
                         Repository
```

For example:

### Joi

```text
quantity must be integer >= 1
```

### Service

```text
requested quantity must not exceed available stock
```

Different responsibilities.

# 38. Arrays of Different Types

You can also define more complex array rules.

For example, perhaps an array can contain:

```text
string
number
```

Joi supports multiple allowed item schemas.

Conceptually:

```js
Joi.array().items(
    Joi.string(),
    Joi.number()
)
```

But be careful.

For most API contracts, it's better to have a predictable array type:

```text
all strings
```

or:

```text
all objects
```

rather than accepting many unrelated types.

Predictability makes APIs easier to maintain.

---

# 39. `.ordered()`

Joi also provides ordered array validation.

For example:

```js
const schema = Joi.array().ordered(
    Joi.string(),
    Joi.number(),
    Joi.boolean()
);
```

Conceptually:

```text
item 1 → string
item 2 → number
item 3 → boolean
```

Example:

```json
[
  "Rahul",
  22,
  true
]
```

This is useful in specialized cases, but normal REST APIs usually prefer arrays where every element has the same structure.

---

# 40. `.has()`

Joi also provides ways to require that an array contains an item matching a particular schema.

Conceptually:

```js
Joi.array()
    .items(Joi.string())
    .has(Joi.string().valid("admin"))
```

This can express:

> The array must contain `"admin"`.

Useful for specialized cases, but don't use advanced array rules just because they exist.

---

# 41. Think in Layers

When you see:

```js
Joi.array()
    .items(
        Joi.object({
            quantity: Joi.number()
                .integer()
                .min(1)
        })
    )
    .min(1)
    .max(50)
    .unique()
```

break it into layers:

```text
Array
 │
 ├── min/max → array-level rules
 │
 ├── unique → array-level rule
 │
 └── items
      │
      └── Object
           │
           └── quantity
                │
                ├── number
                ├── integer
                └── min(1)
```

This is the easiest way to understand complex Joi schemas.

---

# 42. A Common Beginner Error

Don't write:

```js
items: Joi.array({
    productId: Joi.string(),
    quantity: Joi.number()
})
```

That isn't how you define an array of objects.

Instead:

```js
items: Joi.array().items(
    Joi.object({
        productId: Joi.string(),
        quantity: Joi.number()
    })
)
```

Remember:

```text
array
  ↓
items()
  ↓
object()
```

---

# 43. Another Common Error

Don't confuse:

```js
Joi.object({
    tags: Joi.array().items(
        Joi.string()
    )
})
```

with:

```js
Joi.array().items(
    Joi.object({
        tags: Joi.string()
    })
)
```

They represent completely different JSON structures.

### First:

```json
{
  "tags": ["node", "mongodb"]
}
```

### Second:

```json
[
  {
    "tags": "node"
  },
  {
    "tags": "mongodb"
  }
]
```

Always compare your Joi schema to the actual JSON shape.

# 44. The Shape-First Technique

Before writing Joi, first draw the JSON structure.

For example:

```text
Order
│
├── shippingAddress
│   ├── name
│   ├── city
│   ├── state
│   └── postalCode
│
├── items[]
│   ├── productId
│   └── quantity
│
└── notes
```

Then convert each node into Joi.

```text
Order
 ↓
Joi.object()

shippingAddress
 ↓
Joi.object()

items[]
 ↓
Joi.array()

each item
 ↓
Joi.object()
```

This technique will save you a lot of confusion.

# 45. Real-World Validation Pattern

A strong schema often looks like:

```js
const schema = Joi.object({
    field1: Joi.string()
        .trim()
        .min(...)
        .max(...)
        .required(),

    field2: Joi.number()
        .integer()
        .min(...)
        .max(...)
        .required(),

    field3: Joi.array()
        .items(
            Joi.object({
                ...
            })
        )
        .min(...)
        .max(...)
        .required(),

    field4: Joi.object({
        ...
    }).optional()
}).unknown(false);
```

This pattern will appear constantly in your backend work.

Consider this request:

```json

  "name": "Keyboard",

  "tags": [
    "gaming",
```

```text
price = -100
```

Should fail because:


### Problem 2


Should fail:


### Problem 3

You may eventually have:

This makes your backend much easier to understand.

# 🔑 Final Takeaway

The most important patterns from today's lesson are:

### Array of strings

```js
Joi.array()
    .items(Joi.string())
```

### Controlled array

```js
Joi.array()
    .items(Joi.string())
    .min(1)
    .max(10)
    .unique()
```

### Nested object

```js
Joi.object({
    city: Joi.string().required(),
    country: Joi.string().required()
})
```

### Array of objects

```js
Joi.array().items(
    Joi.object({
        productId: Joi.string().required(),

        quantity: Joi.number()
            .integer()
            .min(1)
            .required()
    })
)
```

### Strict object

```js
Joi.object({
    name: Joi.string().required()
}).unknown(false)
```

And the most important mental model:

> **First understand the JSON shape. Then translate that shape into Joi.**

```text
JSON
 ↓
Shape
 ↓
Joi.object()
Joi.array()
Joi.items()
Joi.object()
 ↓
Field constraints
```

Once you understand this, even a deeply nested request body stops looking complicated.
