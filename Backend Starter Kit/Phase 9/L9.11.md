# Lesson 9.11 — Joi References & Cross-Field Validation

In the previous lessons, we learned how to validate **individual fields** and **nested structures**.

For example:

```js
password: Joi.string().min(8).required()
```

and:

```js
items: Joi.array().items(
    Joi.object({
        productId: Joi.string().required(),
        quantity: Joi.number().integer().min(1).required()
    })
)
```

But real applications often have rules involving **two or more fields**.

For example:

```text
password === confirmPassword

minPrice <= maxPrice

startDate <= endDate

newPassword !== oldPassword
```

These are called **cross-field validations**.

Today we'll learn how Joi handles them.

---

# 1. What Is Cross-Field Validation?

Normal validation asks:

> Is this individual field valid?

For example:

```js
age: Joi.number().integer().min(18)
```

But cross-field validation asks:

> Is this field valid **in relation to another field**?

For example:

```json
{
  "password": "secret123",
  "confirmPassword": "secret123"
}
```

The rule is:

```text
confirmPassword === password
```

Neither field is necessarily invalid by itself.

The problem only exists when we compare them.

---

# 2. Why Normal Joi Rules Aren't Enough

Consider:

```js
const schema = Joi.object({
    password: Joi.string()
        .min(8)
        .required(),

    confirmPassword: Joi.string()
        .required()
});
```

This validates:

```text
password → valid string
confirmPassword → valid string
```

But this request:

```json
{
  "password": "password123",
  "confirmPassword": "different123"
}
```

would pass those basic rules.

That's not what we want.

We need to tell Joi:

```text
confirmPassword must equal password
```

---

# 3. `Joi.ref()`

This is where:

```js
Joi.ref()
```

becomes important.

A reference means:

> Look at the value of another field.

Example:

```js
confirmPassword: Joi.string()
    .valid(Joi.ref("password"))
    .required()
```

Now:

```text
confirmPassword
      ↓
must equal
      ↓
password
```

---

# 4. Password Confirmation Example

Complete schema:

```js
const registerSchema = Joi.object({
    password: Joi.string()
        .min(8)
        .required(),

    confirmPassword: Joi.string()
        .valid(Joi.ref("password"))
        .required()
});
```

Valid:

```json
{
  "password": "password123",
  "confirmPassword": "password123"
}
```

Invalid:

```json
{
  "password": "password123",
  "confirmPassword": "password456"
}
```

This is one of the most common uses of `Joi.ref()`.

---

# 5. Think of `Joi.ref()` Like a Variable

Imagine:

```js
Joi.ref("password")
```

means:

```text
"Give me whatever value password currently has."
```

If:

```json
{
  "password": "abc123"
}
```

then:

```js
Joi.ref("password")
```

conceptually points to:

```text
"abc123"
```

So:

```js
.valid(Joi.ref("password"))
```

means:

```text
value must equal the current password value
```

---

# 6. `Joi.ref()` Is Not a String Value

This is wrong:

```js
.valid("password")
```

because that means:

```text
The value must literally be:
"password"
```

Whereas:

```js
.valid(Joi.ref("password"))
```

means:

```text
The value must equal the value stored in the password field.
```

Huge difference.

---

# 7. Password Schema in a Real API

You might have:

```js
const registerSchema = Joi.object({
    email: Joi.string()
        .email()
        .required(),

    password: Joi.string()
        .min(8)
        .max(100)
        .required(),

    confirmPassword: Joi.string()
        .valid(Joi.ref("password"))
        .required()
});
```

The validation flow becomes:

```text
Request
   │
   ├── email
   │
   ├── password
   │
   └── confirmPassword
             │
             ▼
      compare with password
             │
       ┌─────┴─────┐
       │           │
     equal       different
       │           │
       ▼           ▼
     valid       error
```

---

# 8. `.messages()` for Better Errors

The default error may not be very user-friendly.

You can customize it:

```js
confirmPassword: Joi.string()
    .valid(Joi.ref("password"))
    .required()
    .messages({
        "any.only": "Passwords do not match"
    })
```

Now the client can receive a clearer validation message.

This is especially useful for:

```text
password confirmation
password rules
business-specific validation
```

---

# 9. Another Example: Minimum and Maximum Price

Suppose your API accepts:

```json
{
  "minPrice": 100,
  "maxPrice": 1000
}
```

The rule is:

```text
minPrice <= maxPrice
```

You might try:

```js
const schema = Joi.object({
    minPrice: Joi.number().min(0),
    maxPrice: Joi.number().min(0)
});
```

But this doesn't enforce the relationship.

This request:

```json
{
  "minPrice": 1000,
  "maxPrice": 100
}
```

could still pass.

We need a reference.

---

# 10. `less()` With a Reference

You can express relationships using references.

For example:

```js
const schema = Joi.object({
    minPrice: Joi.number()
        .min(0),

    maxPrice: Joi.number()
        .min(Joi.ref("minPrice"))
});
```

Conceptually:

```text
maxPrice >= minPrice
```

So:

```text
minPrice = 100
maxPrice = 1000
```

is valid.

But:

```text
minPrice = 1000
maxPrice = 100
```

is invalid.

---

# 11. Important Direction

Be careful with this:

```js
maxPrice: Joi.number()
    .min(Joi.ref("minPrice"))
```

It means:

```text
maxPrice >= minPrice
```

The field containing the rule is:

```text
maxPrice
```

and it compares itself against:

```text
minPrice
```

A useful way to read it is:

> "`maxPrice` must be at least the value of `minPrice`."

---

# 12. Start Date and End Date

This same pattern is extremely useful with dates.

Request:

```json
{
  "startDate": "2026-08-01",
  "endDate": "2026-08-25"
}
```

Schema:

```js
const dateRangeSchema = Joi.object({
    startDate: Joi.date()
        .iso()
        .required(),

    endDate: Joi.date()
        .iso()
        .min(Joi.ref("startDate"))
        .required()
});
```

This expresses:

```text
endDate >= startDate
```

So:

```text
2026-08-01 → 2026-08-25
```

is valid.

But:

```text
2026-08-25 → 2026-08-01
```

is rejected.

---

# 13. Why This Is Better Than Controller Logic

You could technically write:

```js
if (endDate < startDate) {
    return res.status(400).json({
        message: "Invalid date range"
    });
}
```

inside your controller.

But if the rule is specifically **request validation**, keeping it in the Joi schema can be cleaner.

Then your architecture becomes:

```text
HTTP request
     ↓
Joi
     ↓
Basic + relationship validation
     ↓
Controller
     ↓
Service
```

The controller doesn't need to manually check every input relationship.

---

# 14. Numeric Comparison With References

Suppose:

```json
{
  "minAge": 18,
  "maxAge": 65
}
```

Schema:

```js
const schema = Joi.object({
    minAge: Joi.number()
        .integer()
        .min(0)
        .required(),

    maxAge: Joi.number()
        .integer()
        .min(Joi.ref("minAge"))
        .required()
});
```

Now:

```text
18 → 65
```

works.

But:

```text
65 → 18
```

doesn't.

---

# 15. `greater(Joi.ref())`

Sometimes you don't want equality.

Suppose:

```text
end > start
```

rather than:

```text
end >= start
```

You can use:

```js
end: Joi.number()
    .greater(Joi.ref("start"))
```

Now:

```text
start = 10
end = 20
```

valid.

But:

```text
start = 10
end = 10
```

invalid.

This distinction is important.

Remember:

```text
min(ref)
    ↓
>= reference

greater(ref)
    ↓
> reference
```

---

# 16. `less(Joi.ref())`

The opposite:

```js
start: Joi.number()
    .less(Joi.ref("end"))
```

means:

```text
start < end
```

For example:

```text
start = 10
end = 20
```

valid.

---

# 17. `max(Joi.ref())`

You can also use:

```js
discount: Joi.number()
    .max(Joi.ref("price"))
```

This means:

```text
discount <= price
```

Whether this is a sensible business rule depends on what your fields actually mean.

The important lesson is that Joi references let one field's validation depend on another field.

---

# 18. Conditional Validation

Now we reach another major concept:

```js
.when()
```

This lets you say:

> If one field has a particular value, change the validation rules for another field.

For example:

```text
isCompany = true
      ↓
companyName required
```

But:

```text
isCompany = false
      ↓
companyName optional
```

---

# 19. Basic `.when()`

Example:

```js
const schema = Joi.object({
    isCompany: Joi.boolean()
        .required(),

    companyName: Joi.string()
        .when("isCompany", {
            is: true,
            then: Joi.required(),
            otherwise: Joi.optional()
        })
});
```

Now:

```json
{
  "isCompany": true,
  "companyName": "ABC Pvt Ltd"
}
```

is valid.

But:

```json
{
  "isCompany": true
}
```

fails.

If:

```json
{
  "isCompany": false
}
```

then `companyName` doesn't need to be provided.

---

# 20. Read `.when()` Like English

This:

```js
companyName: Joi.string()
    .when("isCompany", {
        is: true,
        then: Joi.required(),
        otherwise: Joi.optional()
    })
```

means:

> When `isCompany` is `true`, `companyName` is required; otherwise, it is optional.

This is a very useful mental model.

---

# 21. Conditional Payment Fields

Imagine an order API:

```json
{
  "paymentMethod": "card",
  "cardNumber": "..."
}
```

You may want:

```text
paymentMethod = card
       ↓
cardNumber required
```

Schema:

```js
const paymentSchema = Joi.object({
    paymentMethod: Joi.string()
        .valid("card", "upi", "cod")
        .required(),

    cardNumber: Joi.string()
        .when("paymentMethod", {
            is: "card",
            then: Joi.required(),
            otherwise: Joi.forbidden()
        })
});
```

Now:

```text
card
 ↓
cardNumber required
```

and:

```text
upi
 ↓
cardNumber forbidden
```

This is a much stronger API contract.

---

# 22. Why `forbidden()` Is Useful Here

Consider:

```json
{
  "paymentMethod": "upi",
  "cardNumber": "123456"
}
```

If `cardNumber` is irrelevant for UPI, you don't necessarily want to silently accept it.

Instead:

```js
otherwise: Joi.forbidden()
```

says:

> This field should not exist in this situation.

This prevents strange or conflicting request states.

---

# 23. Conditional Address

Suppose:

```text
deliveryRequired = true
```

means:

```text
shippingAddress required
```

Schema:

```js
const schema = Joi.object({
    deliveryRequired: Joi.boolean()
        .required(),

    shippingAddress: Joi.object({
        city: Joi.string().required(),
        state: Joi.string().required()
    }).when("deliveryRequired", {
        is: true,
        then: Joi.required(),
        otherwise: Joi.forbidden()
    })
});
```

Now:

```text
deliveryRequired = true
       ↓
shippingAddress required
```

while:

```text
deliveryRequired = false
       ↓
shippingAddress forbidden
```

---

# 24. Conditional Fields Are Extremely Common

You'll encounter this pattern in:

```text
payment
shipping
user roles
account types
subscription plans
profile types
authentication methods
notification settings
```

For example:

```text
accountType = business
       ↓
companyName required
taxId required
```

while:

```text
accountType = personal
       ↓
companyName forbidden
taxId forbidden
```

---

# 25. Multiple Conditions

You can have more than one condition.

For example:

```text
role = admin
    ↓
permissions required
```

Schema:

```js
const schema = Joi.object({
    role: Joi.string()
        .valid("user", "admin")
        .required(),

    permissions: Joi.array()
        .items(Joi.string())
        .when("role", {
            is: "admin",
            then: Joi.required(),
            otherwise: Joi.forbidden()
        })
});
```

This is a clean API contract.

---

# 26. `.when()` With a Reference

You can also use a reference directly:

```js
.when("role", {
    is: Joi.valid("admin"),
    then: ...
})
```

The exact condition can become more advanced as your schemas grow.

For now, focus on the core idea:

```text
when field X has condition Y
    ↓
change rules for field Z
```

---

# 27. `Joi.ref()` vs `.when()`

This distinction is very important.

### `Joi.ref()`

Usually means:

```text
Compare one value to another value.
```

Example:

```js
confirmPassword: Joi.string()
    .valid(Joi.ref("password"))
```

### `.when()`

Usually means:

```text
Change validation rules based on another field.
```

Example:

```js
companyName: Joi.string()
    .when("isCompany", {
        is: true,
        then: Joi.required()
    })
```

Think:

```text
ref()
    → comparison

when()
    → conditional rules
```

---

# 28. A Real Registration Schema

Let's combine these concepts.

```js
const registerSchema = Joi.object({
    email: Joi.string()
        .email()
        .required(),

    password: Joi.string()
        .min(8)
        .required(),

    confirmPassword: Joi.string()
        .valid(Joi.ref("password"))
        .required()
        .messages({
            "any.only": "Passwords do not match"
        }),

    accountType: Joi.string()
        .valid("personal", "business")
        .required(),

    companyName: Joi.string()
        .trim()
        .when("accountType", {
            is: "business",
            then: Joi.required(),
            otherwise: Joi.forbidden()
        })
}).unknown(false);
```

Now our schema expresses several relationships.

---

# 29. Understand the Schema

### Password

```text
password
    ↓
minimum 8 characters
```

### Confirm password

```text
confirmPassword
    ↓
must equal password
```

### Account type

```text
personal OR business
```

### Company name

```text
business
    ↓
required

personal
    ↓
forbidden
```

This is far more powerful than checking each field independently.

# 30. Another Real Example: Product Discount

Suppose:

```json
{
  "price": 1000,
  "discountType": "percentage",
  "discount": 20
}
```

Possible rules:

```text
discountType = percentage
       ↓
discount <= 100
```

If:

```text
discountType = fixed
```

perhaps:

```text
discount < price
```

This can be expressed using conditional validation.

For example:

```js
const productSchema = Joi.object({
    price: Joi.number()
        .greater(0)
        .required(),

    discountType: Joi.string()
        .valid("percentage", "fixed")
        .required(),

    discount: Joi.number()
        .greater(0)
        .when("discountType", {
            is: "percentage",
            then: Joi.max(100),
            otherwise: Joi.max(Joi.ref("price"))
        })
        .required()
});
```

Now the validation depends on another field.

---

# 31. Conditional Validation Is About State

This is a useful way to think about `.when()`.

Your request has a **state**.

For example:

```text
accountType = business
```

creates one validation state.

```text
accountType = personal
```

creates another.

So:

```text
Request
   │
   ├── personal
   │      ↓
   │   personal rules
   │
   └── business
          ↓
       business rules
```

Joi lets the schema adapt to that state.

---

# 32. Cross-Field Validation vs Business Logic

Be careful here.

Not every business rule belongs in Joi.

For example:

```text
password === confirmPassword
```

is a good request validation rule.

But:

```text
user can only change password once every 24 hours
```

belongs in your service/business layer.

Similarly:

```text
productId has valid format
```

can be validation.

But:

```text
product exists and is currently available
```

belongs in the service/repository flow.

---

# 33. Another Example: New Password

Suppose:

```json
{
  "oldPassword": "old12345",
  "newPassword": "new12345"
}
```

You might want:

```text
newPassword !== oldPassword
```

Joi can express some comparisons, but password verification itself should **not** be done by Joi.

Why?

Because the database stores a password hash, not the original password.

Your service needs to:

```text
oldPassword
      ↓
bcrypt compare
      ↓
does it match stored hash?
```

That's business/security logic.

Then Joi can handle basic rules such as:

```text
newPassword >= 8 characters
confirmPassword === newPassword
```

This separation is critical.

---

# 34. Object-Level Validation

Sometimes the relationship is more complicated than a simple field reference.

For example:

```text
At least one of:
email
phone
```

must be provided.

Or:

```text
Either:
username + password

OR:
OAuth provider + OAuth token
```

These are object-level rules.

Joi has methods such as:

```text
or()
and()
xor()
oxor()
nand()
with()
without()
```

These are extremely useful.

---

# 35. `.or()`

Suppose a user must provide either:

```text
email
```

or:

```text
phone
```

You can use:

```js
const schema = Joi.object({
    email: Joi.string()
        .email(),

    phone: Joi.string()
        .pattern(/^[0-9]{10}$/)
}).or("email", "phone");
```

This means:

```text
at least one must be present
```

Valid:

```json
{
  "email": "rahul@example.com"
}
```

Valid:

```json
{
  "phone": "9876543210"
}
```

Invalid:

```json
{}
```

---

# 36. `.and()`

Suppose if the user provides:

```text
startDate
```

they must also provide:

```text
endDate
```

You can express a relationship such as:

```js
const schema = Joi.object({
    startDate: Joi.date().iso(),
    endDate: Joi.date().iso()
}).and("startDate", "endDate");
```

This means:

```text
startDate exists
    ↓
endDate must also exist
```

and vice versa.

But note:

```text
and()
```

doesn't itself mean:

```text
startDate <= endDate
```

You still need the date comparison.

---

# 37. `.xor()`

Sometimes you want **exactly one** option.

Example:

```text
login with email
OR
login with username
```

but not both.

```js
const schema = Joi.object({
    email: Joi.string().email(),
    username: Joi.string()
}).xor("email", "username");
```

Now:

```text
email only     → valid
username only  → valid
both           → invalid
neither        → invalid
```

This is different from `.or()`.

---

# 38. `or()` vs `xor()`

Remember:

```text
or()
 ↓
one or more
```

while:

```text
xor()
 ↓
exactly one
```

Example:

```text
email + phone
```

With `.or()`:

```text
valid
```

With `.xor()`:

```text
invalid
```

because both were provided.

---

# 39. `.with()`

Suppose:

```text
email
```

requires:

```text
emailVerified
```

You can use relationships such as:

```js
const schema = Joi.object({
    email: Joi.string().email(),
    emailVerified: Joi.boolean()
}).with("email", "emailVerified");
```

Conceptually:

> If `email` is present, `emailVerified` must also be present.

Again, this is a **presence relationship**, not necessarily a logical verification check.

---

# 40. `.without()`

The opposite idea:

```text
password
```

and:

```text
oauthToken
```

shouldn't be sent together.

Conceptually:

```js
const schema = Joi.object({
    password: Joi.string(),
    oauthToken: Joi.string()
}).without("password", "oauthToken");
```

This prevents conflicting authentication methods.

---

# 41. The Big Picture

At this point, Joi validation has several layers.

```text
                    Joi
                     │
        ┌────────────┼────────────┐
        │            │            │
      Type       Field Rules   Relationships
        │            │            │
    string        min/max       ref()
    number        required       when()
    boolean       pattern        or()
    date          valid()        and()
    array         unique()       xor()
    object        default()      with()
```

This is a useful mental map.

---

# 42. Example: Search API

Let's combine several concepts:

```http
GET /products?minPrice=100&maxPrice=1000
```

Schema:

```js
const searchSchema = Joi.object({
    minPrice: Joi.number()
        .min(0)
        .optional(),

    maxPrice: Joi.number()
        .min(Joi.ref("minPrice"))
        .optional()
});
```

Now the API understands:

```text
minPrice >= 0

maxPrice >= minPrice
```

But there is a subtle issue.

What happens when:

```text
minPrice
```

is missing?

This is where careful schema design becomes important.

Don't blindly use cross-field references without thinking about optional fields and the states your API supports.

---

# 43. Build Validation Rules From API States

Before writing `.when()` or `.ref()`, list the possible states.

For example:

```text
Price filter:

No min, no max
    → valid

min only
    → valid

max only
    → valid

min + max
    → max >= min
```

This is a better approach than immediately writing code.

You first understand the allowed states.

Then you design the schema.

---

# 44. This Is How Senior Developers Think

Instead of asking:

> "What Joi method do I use?"

ask:

> "What states can this API request be in, and which states are invalid?"

For example:

```text
paymentMethod = card
    → cardNumber required

paymentMethod = UPI
    → cardNumber forbidden

paymentMethod = COD
    → cardNumber forbidden
```

Then:

```js
.when()
```

becomes an implementation detail.

This mindset will help you far beyond Joi.

---

# 45. Full Example: Checkout Schema

Let's put everything together.

```js
const checkoutSchema = Joi.object({
    paymentMethod: Joi.string()
        .valid("card", "upi", "cod")
        .required(),

    cardNumber: Joi.string()
        .when("paymentMethod", {
            is: "card",
            then: Joi.required(),
            otherwise: Joi.forbidden()
        }),

    shippingAddress: Joi.object({
        city: Joi.string().required(),
        state: Joi.string().required(),
        postalCode: Joi.string()
            .pattern(/^[0-9]{6}$/)
            .required()
    }).required(),

    items: Joi.array()
        .items(
            Joi.object({
                productId: Joi.string().required(),

                quantity: Joi.number()
                    .integer()
                    .min(1)
                    .required()
            }).unknown(false)
        )
        .min(1)
        .max(50)
        .required()
}).unknown(false);
```

Notice how much we've built from simple pieces:

```text
object
 ↓
string
 ↓
when
 ↓
nested object
 ↓
array
 ↓
array of objects
 ↓
number rules
 ↓
unknown(false)
```

This is how real schemas grow.

---

# 46. What You Should NOT Do

Don't turn Joi into your entire business layer.

Avoid trying to make one schema perform:

```text
database queries
password verification
stock checking
authorization
payment processing
external API calls
```

Joi should sit near the **input boundary**.

Think:

```text
                    HTTP
                      │
                      ▼
                 Validation
                      │
                      ▼
                  Controller
                      │
                      ▼
                   Service
                      │
                      ▼
                Repository/DB
```

Each layer has a job.

Create a schema:

```json
{
  "password": "secret123",
  "confirmPassword": "secret123"
}
```

Requirements:

```text
password:
    string
    8–100 chars
    required

confirmPassword:
    required
    must equal password
```

Expected core rule:

```js
.valid(Joi.ref("password"))
```

# 🧪 Practice Exercise 3 — Account Type

Create:

```json
{
  "accountType": "business",
  "companyName": "ABC Pvt Ltd"
}
```

Rules:

```text
accountType:
    personal OR business

companyName:
    required for business
    forbidden for personal
```

Hint:

```js
.when("accountType", {
    is: "business",
    then: Joi.required(),
    otherwise: Joi.forbidden()
})
```

# 🧠 Mental Model

Remember these four concepts:

### 1. `Joi.ref()`

```text
"Look at another field's value."
```

Example:

```js
Joi.ref("password")
```

---

### 2. `.when()`

```text
"If this field has this value,
change another field's rules."
```

---

### 3. `.or()`

```text
"At least one of these fields."
```

---

### 4. `.xor()`

```text
"Exactly one of these fields."
```

And then:

```text
and()
with()
without()
```

help describe relationships between fields.

# 🔑 Final Takeaway

Before Lesson 9.11, you could validate:

```text
Is password a string?
Is age a number?
Is tags an array?
Is address an object?
```

Now you can start validating:

```text
Does confirmPassword equal password?

Is maxPrice >= minPrice?

Is endDate >= startDate?

If accountType is business,
is companyName present?

If paymentMethod is card,
is cardNumber present?

Are email and username mutually exclusive?
```

That's a major step.

The key distinction is:

```text
Field validation
       ↓
"What is this value?"

Cross-field validation
       ↓
"How does this value relate
to the other values?"
```

And the most important architectural lesson:

> **Joi should validate the shape, type, format, constraints, and simple relationships of incoming data. Your service layer should handle deeper business rules and database-dependent decisions.**
