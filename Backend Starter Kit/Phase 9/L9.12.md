# Lesson 9.12 — Joi Custom Validation with `.custom()`

In Lesson 9.11, we learned how Joi can compare fields:

```js
confirmPassword === password
```

and create conditional rules:

```text
accountType = business
        ↓
companyName required
```

But sometimes the built-in Joi rules are **not enough**.

You may need a rule such as:

```text
username must not contain spaces

product code must follow our custom format

two parts of a value must follow a special rule

phone number must satisfy our application's format

a value must pass some custom transformation
```

This is where:

```js
.custom()
```

becomes useful.

---

# 1. Why Do We Need `.custom()`?

Joi already provides many validators:

```js
Joi.string()
Joi.number()
Joi.boolean()
Joi.date()
Joi.array()
Joi.object()
```

and rules like:

```js
.min()
.max()
.email()
.pattern()
.valid()
.required()
.when()
```

But imagine your application has this rule:

```text
Username may contain:
- letters
- numbers
- underscore

But:
- it cannot start with a number
- it cannot end with underscore
```

There may not be a single built-in Joi rule that expresses exactly what you want.

You can create your own validator.

---

# 2. Basic `.custom()`

The basic structure is:

```js
Joi.string().custom((value, helpers) => {
    // custom validation
    return value;
})
```

There are two important arguments:

```js
(value, helpers)
```

### `value`

The value currently being validated.

### `helpers`

An object containing helper functions and validation information.

The most important helper initially is:

```js
helpers.error()
```

---

# 3. The Most Important Rule

Inside `.custom()` you generally do one of two things:

### Valid value

Return:

```js
return value;
```

### Invalid value

Return:

```js
return helpers.error("some.error.code");
```

Conceptually:

```text
custom validator
       │
       ├── valid
       │    ↓
       │  return value
       │
       └── invalid
            ↓
       helpers.error(...)
```

---

# 4. First Simple Example

Let's create a custom validator that rejects the word:

```text
admin
```

```js
const usernameSchema = Joi.string()
    .custom((value, helpers) => {
        if (value === "admin") {
            return helpers.error("any.invalid");
        }

        return value;
    });
```

Now:

```text
rahul
```

passes.

But:

```text
admin
```

fails.

---

# 5. Why Return `value`?

You might wonder:

> Why do we need `return value`?

Because Joi's custom validator needs to pass the value onward.

For example:

```js
const schema = Joi.string()
    .trim()
    .custom((value, helpers) => {
        return value;
    });
```

The value continues through the validation pipeline.

Think:

```text
input
 ↓
Joi.string()
 ↓
trim()
 ↓
custom()
 ↓
validated value
```

---

# 6. `.custom()` Is Not Just for Rejecting Values

A custom validator can also transform a value.

For example:

```js
const schema = Joi.string()
    .custom((value, helpers) => {
        return value.toUpperCase();
    });
```

Input:

```text
hello
```

can become:

```text
HELLO
```

This is useful, but don't use custom transformation when Joi already provides a clearer built-in rule.

For example:

```js
Joi.string().uppercase()
```

is clearer than:

```js
Joi.string().custom((value) => {
    return value.toUpperCase();
})
```

**Prefer built-in Joi rules whenever possible.**

---

# 7. Custom Validation Should Be Your Last Tool

This is an important principle.

Don't do this:

```js
Joi.string().custom(...)
```

for something Joi already supports.

For example, don't write:

```js
Joi.string().custom((value, helpers) => {
    if (value.length < 8) {
        ...
    }
})
```

when you can simply use:

```js
Joi.string().min(8)
```

Prefer:

```text
Built-in Joi rule
      ↓
Pattern/Reference/Condition
      ↓
Custom validator
```

Use `.custom()` when the built-in tools genuinely don't express the rule cleanly.

---

# 8. Custom Username Validation

Let's create a realistic example.

Requirement:

```text
username:
- lowercase
- letters/numbers/underscore only
- cannot start with number
- cannot end with underscore
```

We can handle much of this with built-in rules:

```js
const usernameSchema = Joi.string()
    .trim()
    .lowercase()
    .pattern(/^[a-z][a-z0-9_]*[a-z0-9]$/)
    .min(3)
    .max(30)
    .required();
```

Notice something important:

**We didn't need `.custom()`.**

That's actually good.

A regular expression can express the rule cleanly.

---

# 9. When Custom Becomes Useful

Suppose the username has a special application-specific rule:

> The username cannot contain three consecutive identical characters.

Examples:

```text
rahul
```

valid.

```text
raaaahul
```

invalid.

A custom validator can express this:

```js
const usernameSchema = Joi.string()
    .custom((value, helpers) => {
        if (/(.)\1\1/.test(value)) {
            return helpers.error("any.invalid");
        }

        return value;
    });
```

Now `.custom()` is reasonable because the rule is specific to our application.

---

# 10. Custom Error Codes

Instead of:

```js
helpers.error("any.invalid")
```

we can define our own error code.

For example:

```js
const schema = Joi.string()
    .custom((value, helpers) => {
        if (value === "admin") {
            return helpers.error("username.reserved");
        }

        return value;
    })
    .messages({
        "username.reserved": "This username is reserved."
    });
```

Now the validator has a meaningful error.

---

# 11. Understand the Flow

The code:

```js
.custom((value, helpers) => {
    if (value === "admin") {
        return helpers.error("username.reserved");
    }

    return value;
})
.messages({
    "username.reserved": "This username is reserved."
})
```

means:

```text
value
  ↓
Is value "admin"?
  │
  ├── yes
  │    ↓
  │ helpers.error()
  │
  └── no
       ↓
    return value
```

Then Joi converts the error code into the message.

---

# 12. `helpers.message()`

There are also ways to create custom error messages directly.

For example, conceptually:

```js
.custom((value, helpers) => {
    if (...) {
        return helpers.message({
            custom: "Username is not allowed"
        });
    }

    return value;
})
```

But for reusable validators, custom error codes with `.messages()` often give you a cleaner structure.

For now, remember:

```text
helpers.error()
    ↓
error code
    ↓
.messages()
    ↓
human-friendly message
```

---

# 13. Custom Number Validation

`.custom()` isn't limited to strings.

Example:

```js
const evenNumberSchema = Joi.number()
    .integer()
    .custom((value, helpers) => {
        if (value % 2 !== 0) {
            return helpers.error("number.even");
        }

        return value;
    })
    .messages({
        "number.even": "Number must be even."
    });
```

Now:

```text
2 → valid
4 → valid
8 → valid
```

while:

```text
3 → invalid
7 → invalid
```

---

# 14. But Could We Avoid `.custom()`?

Yes.

In this particular example, custom validation is not necessarily the best production approach.

You could use a pattern for strings, or a different schema strategy depending on the input.

The lesson isn't:

> "Use `.custom()` whenever you can."

The lesson is:

> "Know that `.custom()` exists when Joi's standard rules aren't enough."

---

# 15. Custom Array Validation

You can also customize arrays.

For example:

```text
The array must contain at least one admin role.
```

You might have:

```js
const rolesSchema = Joi.array()
    .items(Joi.string())
    .custom((value, helpers) => {
        if (!value.includes("admin")) {
            return helpers.error("roles.adminRequired");
        }

        return value;
    })
    .messages({
        "roles.adminRequired": "Admin role is required."
    });
```

Now:

```json
["admin", "editor"]
```

passes.

But:

```json
["editor", "viewer"]
```

fails.

---

# 16. But Wait — Could `.has()` Work?

Yes.

This is a great example of choosing the simpler Joi feature.

Instead of:

```js
.custom(...)
```

you could use:

```js
Joi.array()
    .items(Joi.string())
    .has(Joi.valid("admin"));
```

This is better because the rule directly describes the intent.

So again:

```text
Built-in Joi rule
      ↓
prefer it
```

Custom validation should not become your default hammer.

---

# 17. Custom Object Validation

Now things become more interesting.

Suppose we have:

```json
{
  "start": 10,
  "end": 20
}
```

and the rule:

```text
end must be greater than start
```

We've already seen that references can handle this:

```js
const schema = Joi.object({
    start: Joi.number().required(),

    end: Joi.number()
        .greater(Joi.ref("start"))
        .required()
});
```

So again, **don't use `.custom()` unnecessarily**.

---

# 18. When Object-Level Custom Validation Helps

Suppose the rule becomes complicated:

```text
If type = "range":
    start and end required

If type = "single":
    value required

If type = "open":
    start required
    end must not exist
```

At some point, object-level custom validation may be useful.

For example:

```js
const schema = Joi.object({
    type: Joi.string()
        .valid("range", "single", "open")
        .required(),

    start: Joi.number(),
    end: Joi.number(),
    value: Joi.number()
});
```

Then additional logic can be applied at the object level.

But before doing this, always ask:

> Can `.when()`, `.or()`, `.xor()`, `.with()`, `.without()`, or `Joi.ref()` express this more clearly?

---

# 19. The `helpers` Object

Inside:

```js
.custom((value, helpers) => {
```

you get access to useful information.

One important property is:

```js
helpers.state
```

which can provide information about where the current value sits in the validation structure.

You may also encounter:

```js
helpers.original
```

which represents the original input value before some transformations.

These are more advanced features.

For now, focus on:

```js
helpers.error()
helpers.message()
```

You will rarely need the deeper state APIs at the beginning.

---

# 20. Custom Validation and `Joi.ref()`

This is where `.custom()` becomes powerful.

Suppose you need access to another field while performing a custom rule.

You can work with Joi's validation context and references, but this is an area where beginners often make schemas unnecessarily complicated.

Before reaching for advanced context access, ask:

```text
Can I express this with:
Joi.ref()
.when()
min(ref)
max(ref)
greater(ref)
less(ref)
```

If yes, use those.

They're easier to understand and maintain.

---

# 21. A Better Example: Special Product Code

Suppose your application has product codes like:

```text
PROD-12345
```

Rules:

```text
PROD-
followed by exactly 5 digits
```

A normal regex is perfect:

```js
const productCodeSchema = Joi.string()
    .pattern(/^PROD-\d{5}$/)
    .required();
```

You don't need `.custom()`.

Valid:

```text
PROD-12345
```

Invalid:

```text
PROD-123
```

Invalid:

```text
ABC-12345
```

This is an important lesson:

> **Custom business rule doesn't automatically mean custom Joi validator.**

Regex may already solve it.

---

# 22. Example Where `.custom()` Makes Sense

Suppose your product code follows a checksum algorithm.

For example:

```text
ABC-12345-X
```

and the final character is calculated from the previous characters using an application-specific algorithm.

That's much harder to express cleanly with a regex.

Now `.custom()` becomes appropriate.

Conceptually:

```js
const productCodeSchema = Joi.string()
    .custom((value, helpers) => {
        const isValid = validateProductChecksum(value);

        if (!isValid) {
            return helpers.error("productCode.invalid");
        }

        return value;
    })
    .messages({
        "productCode.invalid": "Invalid product code."
    });
```

Here custom validation is doing something meaningful.

---

# 23. Keep Custom Functions Small

Don't create:

```js
.custom((value, helpers) => {
    // 100 lines of logic
})
```

That's a maintenance problem.

Instead:

```js
function validateProductChecksum(value) {
    // specialized algorithm
}
```

Then:

```js
const schema = Joi.string()
    .custom((value, helpers) => {
        if (!validateProductChecksum(value)) {
            return helpers.error("productCode.invalid");
        }

        return value;
    });
```

Much cleaner.

---

# 24. Even Better: Reusable Custom Validator

You can create a reusable function:

```js
const validateProductCode = (value, helpers) => {
    if (!validateProductChecksum(value)) {
        return helpers.error("productCode.invalid");
    }

    return value;
};
```

Then:

```js
const productCodeSchema = Joi.string()
    .custom(validateProductCode)
    .messages({
        "productCode.invalid": "Invalid product code."
    });
```

Now the schema remains readable.

---

# 25. Custom Validation With Normalization

Suppose you want to accept:

```text
"  PROD-12345  "
```

and normalize it before custom validation.

You could do:

```js
const schema = Joi.string()
    .trim()
    .custom((value, helpers) => {
        if (!validateProductCode(value)) {
            return helpers.error("productCode.invalid");
        }

        return value;
    });
```

The conceptual pipeline becomes:

```text
"  PROD-12345  "
       ↓
     trim
       ↓
"PROD-12345"
       ↓
custom validation
       ↓
validated value
```

This is one reason the order of schema rules can matter.

---

# 26. `.custom()` and Transformation

A custom validator can also normalize data.

For example:

```js
const schema = Joi.string()
    .custom((value, helpers) => {
        return value.replace(/\s+/g, "-");
    });
```

Input:

```text
"hello world"
```

could become:

```text
"hello-world"
```

But again:

> Don't use custom transformation when a built-in Joi rule or a dedicated normalization step is clearer.

Your validation schema should remain easy to read.

---

# 27. Validation vs Sanitization

This is a very important architectural distinction.

### Validation

Asks:

```text
Is this value acceptable?
```

### Sanitization / normalization

Asks:

```text
How should this acceptable value be cleaned or normalized?
```

For example:

```text
" Rahul "
```

can be normalized to:

```text
"Rahul"
```

while:

```text
""
```

may simply be rejected.

Joi can perform some conversions and transformations, but don't let your validation schema become a giant data-processing pipeline.

---

# 28. Custom Validation and Database Queries

Now we reach a **very important boundary**.

Imagine you want:

```text
username must be unique in MongoDB
```

Should you do:

```js
.custom(async (value, helpers) => {
    const exists = await User.findOne({ username: value });
    ...
})
```

**Don't make this your normal Joi validation approach.**

Why?

Because:

```text
Joi validation
```

should generally remain focused on the request's structure and validation.

Database-dependent business rules belong in your:

```text
Service layer
Repository layer
```

---

# 29. Correct Architecture for Username Uniqueness

Request:

```json
{
  "username": "rahul123"
}
```

### Joi

Checks:

```text
string
length
allowed characters
format
```

Then:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Service asks:

```text
Does username already exist?
```

If yes:

```text
409 Conflict
```

This separation is much healthier.

---

# 30. Why Not Put Database Logic in Joi?

Imagine:

```text
POST /users
```

Joi performs:

```text
format validation
 ↓
MongoDB query
 ↓
another database query
 ↓
external API call
```

Now your validation layer is:

```text
slow
hard to test
coupled to database
harder to reuse
harder to reason about
```

Instead:

```text
Joi
 ↓
fast input validation

Service
 ↓
business rules

Repository
 ↓
database access
```

Much cleaner.

---

# 31. Another Example: Product Existence

Request:

```json
{
  "productId": "665abc123"
}
```

Joi can check:

```text
Is it a valid ID format?
```

But not ideally:

```text
Does this product actually exist?
```

That belongs to:

```text
Service
   ↓
Repository
   ↓
Product.findById()
```

Then:

```text
not found
   ↓
404 Not Found
```

---

# 32. Custom Validation Should Be Deterministic

A good custom validator generally looks like:

```text
same input
   ↓
same result
```

For example:

```text
"PROD-12345"
   ↓
valid
```

It shouldn't depend on:

```text
database state
network state
current user
external API
time-sensitive external information
```

Those things belong elsewhere.

---

# 33. A Useful Rule of Thumb

Ask:

> "Can I determine whether this value is valid just by looking at the request data?"

If **yes**:

```text
Joi/custom validation may be appropriate.
```

If **no**, because you need:

```text
database
current authenticated user
external service
business state
```

then:

```text
Service/business layer
```

is usually the better place.

This rule will help you make good architectural decisions.

---

# 34. Example: Coupon Code

Request:

```json
{
  "coupon": "SAVE20"
}
```

Joi can check:

```text
string
uppercase
allowed characters
length
```

But:

```text
Does SAVE20 exist?
Is it expired?
Does the user qualify?
Has the user already used it?
Is it valid for this product?
```

These are **not Joi responsibilities**.

They belong in your service/business logic.

# 35. Example: Age Validation

Suppose the request contains:

```json
{
  "dateOfBirth": "2000-01-01"
}
```

A basic date format check:

```js
Joi.date().iso()
```

is clearly validation.

But:

```text
Is the user legally old enough to purchase this particular product?
```

is business/domain logic.

Don't mix those responsibilities.

# 36. Custom Error Codes

Let's build a reusable validator properly.

```js
const validateUsername = (value, helpers) => {
    if (value === "admin") {
        return helpers.error("username.reserved");
    }

    if (value === "root") {
        return helpers.error("username.reserved");
    }

    return value;
};
```

Then:

```js
const usernameSchema = Joi.string()
    .trim()
    .lowercase()
    .min(3)
    .max(30)
    .custom(validateUsername)
    .messages({
        "username.reserved": "This username is reserved."
    });
```

Now your custom logic is separated from your schema declaration.

---

# 37. Better: Use a Set

If you have multiple reserved usernames:

```js
const RESERVED_USERNAMES = new Set([
    "admin",
    "root",
    "system",
    "support"
]);
```

Then:

```js
const validateUsername = (value, helpers) => {
    if (RESERVED_USERNAMES.has(value)) {
        return helpers.error("username.reserved");
    }

    return value;
};
```

This is cleaner than:

```js
if (value === "admin" ||
    value === "root" ||
    value === "system" ||
    value === "support") {
    ...
}
```

Small design improvements like this make validation code easier to maintain.

---

# 38. Custom Validation With Multiple Rules

You can still combine built-in rules:

```js
const usernameSchema = Joi.string()
    .trim()
    .lowercase()
    .min(3)
    .max(30)
    .pattern(/^[a-z][a-z0-9_]*$/)
    .custom(validateUsername)
    .required();
```

Think:

```text
string
 ↓
trim
 ↓
lowercase
 ↓
min/max
 ↓
pattern
 ↓
custom business-specific format rule
 ↓
required
```

Each rule has a clear purpose.

---

# 39. Custom Validation Errors

Suppose:

```js
const validateUsername = (value, helpers) => {
    if (RESERVED_USERNAMES.has(value)) {
        return helpers.error("username.reserved");
    }

    if (value.startsWith("test_")) {
        return helpers.error("username.testPrefix");
    }

    return value;
};
```

Messages:

```js
.messages({
    "username.reserved": "This username is reserved.",

    "username.testPrefix":
        "Usernames starting with test_ are not allowed."
});
```

This gives your API precise errors.

---

# 40. Don't Expose Internal Details

Your custom error message should be safe for the API client.

Avoid messages like:

```text
MongoDB duplicate key error E11000...
```

Instead:

```text
Username is already taken.
```

And even better, remember that database uniqueness belongs in the service layer.

Validation errors should generally communicate:

```text
what input is invalid
```

without exposing:

```text
internal implementation details
```

---

# 41. Validation Error vs Business Error

This distinction will become very important in your backend architecture.

### Validation error

```text
email = "hello"
```

Joi says:

```text
Invalid email.
```

Usually:

```text
400 Bad Request
```

### Business error

```text
username = "rahul123"
```

but the database already has that username.

Service says:

```text
Username already exists.
```

Usually:

```text
409 Conflict
```

Different layers.

---

# 42. Custom Joi Validation and HTTP Status Codes

Don't put this inside `.custom()`:

```js
return res.status(400)...
```

A Joi validator should not know about:

```text
Express
res
HTTP status
controllers
```

Instead:

```text
Joi
 ↓
throws/returns validation error
 ↓
validation middleware
 ↓
HTTP response
```

This is a key separation of concerns.

---

# 43. What a Custom Validator Should Know

A good custom validator should primarily know:

```text
the value
validation rules
validation helpers
```

It should not know:

```text
Express response object
MongoDB connection
JWT
HTTP request
controller
repository
```

Keeping this boundary clean makes your code reusable.

# 45. A Full Custom Validation Example

Let's build a complete example.

Requirement:

```text
username:
- required
- 3–30 characters
- lowercase
- letters/numbers/underscore
- cannot be reserved
```

First:

```js
const RESERVED_USERNAMES = new Set([
    "admin",
    "root",
    "system",
    "support"
]);
```

Custom validator:

```js
const validateUsername = (value, helpers) => {
    if (RESERVED_USERNAMES.has(value)) {
        return helpers.error("username.reserved");
    }

    return value;
};
```

Schema:

```js
const usernameSchema = Joi.string()
    .trim()
    .lowercase()
    .min(3)
    .max(30)
    .pattern(/^[a-z][a-z0-9_]*$/)
    .custom(validateUsername)
    .required()
    .messages({
        "username.reserved":
            "This username is reserved."
    });
```

Now we have a clean combination of:

```text
built-in validation
+
custom validation
```

# 46. What Happens During Validation?

Input:

```text
"  Admin  "
```

Conceptually:

```text
"  Admin  "
     ↓
trim
     ↓
"Admin"
     ↓
lowercase
     ↓
"admin"
     ↓
pattern
     ↓
passes
     ↓
custom validator
     ↓
reserved?
     ↓
YES
     ↓
validation error
```

This is a good example of why transformation order and validation flow matter.

---

# 47. Custom Validation With `helpers.original`

You may occasionally need to distinguish:

```text
original input
```

from:

```text
converted value
```

For example, if Joi has already normalized:

```text
" Admin "
```

to:

```text
"admin"
```

then your custom validator sees the processed value.

Advanced Joi helpers can provide access to original input.

For now, don't use this unless you genuinely need it.

The simpler your validator is, the better.

---

# 48. Async Custom Validation

You may come across examples using asynchronous custom validation.

Be careful.

This often indicates that the developer is trying to push database/business logic into the validation layer.

For example:

```text
Joi
 ↓
database lookup
```

should make you stop and ask:

> Should this actually be in the service layer?

In most MERN APIs:

```text
Joi
 ↓
synchronous request validation
```

followed by:

```text
Service
 ↓
async business logic
```

is a much cleaner design.

---

# 49. Don't Make `.custom()` a Mini Service

Bad:

```js
.custom(async (value, helpers) => {
    // query database
    // call API
    // check permissions
    // calculate business rules
    // modify database
})
```

That's not validation anymore.

That's business logic hiding inside a schema.

Good:

```js
.custom((value, helpers) => {
    if (!isValidFormat(value)) {
        return helpers.error("custom.invalid");
    }

    return value;
});
```

Then service:

```text
database/business checks
```

This is one of the most important lessons of Phase 9.

### Level 1 — Joi built-in validation

```text
string
number
array
object
email

```

### Level 2 — Joi relationships/custom validation

```text

or
xor

```

### Level 3 — Service/business validation

```text

permissions
stock

```

```text
                Request
                   │
                   ▼
          ┌─────────────────┐

                   ▼
          ┌─────────────────┐

          └─────────────────┘
```

This separation will make your backend much easier to scale.

# 51. Common Beginner Mistakes

## Mistake 1 — Using `.custom()` for everything

Bad:

```js
.custom((value, helpers) => {
    if (value.length < 8) ...
})
```

when:

```js
.min(8)
```

already exists.

---

## Mistake 2 — Putting database queries inside Joi

Avoid:

```js
.custom(async username => {
    await User.findOne(...)
})
```

Prefer:

```text
Joi → format
Service → uniqueness
```

---

## Mistake 3 — Returning the wrong value

Don't forget:

```js
return value;
```

when validation succeeds.

---

## Mistake 4 — Returning `false`

Don't do:

```js
if (...) {
    return false;
}
```

Joi doesn't interpret that as:

> validation failed

Use:

```js
return helpers.error("any.invalid");
```

or a custom error code.

---

## Mistake 5 — Throwing random errors

Avoid:

```js
throw new Error("Invalid username");
```

inside a Joi custom validator unless you have a specific reason.

Use Joi's validation error mechanism.

# 56. Final Mental Model

When you need a validation rule, ask these questions **in order**:

### Question 1

Can Joi's built-in rule handle it?

```js
.min()
.max()
.email()
.pattern()
.valid()
```

If yes:

> Use the built-in rule.

---

### Question 2

Does it depend on another field?

Try:

```js
Joi.ref()
.when()
.or()
.and()
.xor()
.with()
.without()
```

---

### Question 3

Is it a special deterministic rule that cannot be expressed cleanly above?

Then:

```js
.custom()
```

---

### Question 4

Does it require:

```text
database
user identity
authorization
external API
business state
```

Then:

> **Move it to the service/business layer.**

# 🔑 The Big Lesson

Don't think:

> "Joi can validate everything."

Think:

```text
                Incoming Request
                       │
                       ▼
              ┌────────────────┐
              │ Joi             │
              │                │
              │ Type            │
              │ Format          │
              │ Constraints     │
              │ Relationships   │
              │ Custom rules    │
              └───────┬────────┘
                      │
                      ▼
              ┌────────────────┐
              │ Controller     │
              └───────┬────────┘
                      │
                      ▼
              ┌────────────────┐
              │ Service        │
              │                │
              │ Business rules │
              │ DB checks      │
              │ Permissions    │
              │ State           │
              └───────┬────────┘
                      │
                      ▼
              ┌────────────────┐
              │ Repository     │
              └────────────────┘
```

The most important principle from this lesson is:

> **Use `.custom()` for small, deterministic validation rules that Joi cannot express cleanly. Don't turn Joi into your service layer.**

That separation will become very important when we connect validation with the **middleware → controller → service → repository** architecture from your starter backend.

### What you should remember

```js
.custom((value, helpers) => {
    if (!isValid(value)) {
        return helpers.error("custom.invalid");
    }

    return value;
})
```

and:

```js
.messages({
    "custom.invalid": "Invalid value."
})
```

And the decision hierarchy:

```text
Built-in Joi
    ↓
ref / when / or / xor
    ↓
custom()
    ↓
Service layer
```
