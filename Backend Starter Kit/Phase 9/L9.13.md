# Lesson 9.13 — Joi Validation Middleware in Express

This is a **very important lesson** because now we connect what we've learned about Joi with the actual Express backend.

Until now, we have mostly written schemas like:

```js
const registerSchema = Joi.object({
    name: Joi.string().required(),
    email: Joi.string().email().required(),
    password: Joi.string().min(8).required()
});
```

But there is a problem:

> **Where do we actually run this schema for every incoming request?**

We don't want to write this inside every controller:

```js
const { error } = registerSchema.validate(req.body);

if (error) {
    // ...
}
```

That would create repeated code everywhere.

Instead, we'll create reusable **validation middleware**:

```text
Request
   ↓
validate(schema)
   ↓
Joi
   ↓
Controller
```

This is the foundation of clean request validation in your backend starter architecture.

---

# 1. The Problem Without Middleware

Suppose we have:

```js
router.post("/users", registerUser);
```

Controller:

```js
const registerUser = async (req, res) => {
    const { error } = registerSchema.validate(req.body);

    if (error) {
        return res.status(400).json({
            message: error.message
        });
    }

    // create user...
};
```

Now another route:

```js
router.post("/products", createProduct);
```

And again:

```js
const createProduct = async (req, res) => {
    const { error } = createProductSchema.validate(req.body);

    if (error) {
        return res.status(400).json({
            message: error.message
        });
    }

    // create product...
};
```

And another:

```js
router.patch("/users/:id", updateUser);
```

Again:

```js
const { error } = updateUserSchema.validate(req.body);
```

We're repeating ourselves.

---

# 2. The DRY Principle

This violates a common software engineering principle:

> **Don't Repeat Yourself (DRY).**

Instead of:

```text
Controller 1
    ↓
validation code

Controller 2
    ↓
validation code

Controller 3
    ↓
validation code
```

we want:

```text
              validate()
                  ↑
        ┌─────────┼─────────┐
        │         │         │
      Route     Route     Route
```

One middleware.

---

# 3. What Is Validation Middleware?

Express middleware is a function that runs between the request and the final route handler.

Basic middleware:

```js
const middleware = (req, res, next) => {
    // do something

    next();
};
```

So validation middleware will do:

```text
Request
   ↓
validate request
   ↓
valid?
 ┌─┴─┐
No  Yes
│    │
↓    ↓
error next()
       ↓
   Controller
```

---

# 4. Our Goal

We want to be able to write:

```js
router.post(
    "/users",
    validate(registerSchema),
    registerUser
);
```

This is beautiful because the route immediately tells us:

```text
POST /users
    ↓
validate registerSchema
    ↓
registerUser
```

The controller doesn't need to know how validation works.

---

# 5. Create the Middleware File

A common structure is:

```text
src/
├── controllers/
├── middlewares/
│   └── validate.middleware.js
├── routes/
├── schemas/
├── services/
└── repositories/
```

We'll create:

```text
middlewares/validate.middleware.js
```

---

# 6. First Version

Start with:

```js
const validate = (schema) => {
    return (req, res, next) => {
        const { error } = schema.validate(req.body);

        if (error) {
            return res.status(400).json({
                message: error.message
            });
        }

        next();
    };
};

export default validate;
```

This is the simplest useful version.

Let's understand it carefully.

---

# 7. Why Is `validate` a Function Returning a Function?

This is one of the most important concepts in this lesson.

We call:

```js
validate(registerSchema)
```

But Express expects middleware like:

```js
(req, res, next) => {}
```

Therefore:

```js
validate(schema)
```

must **return**:

```js
(req, res, next) => {}
```

So:

```js
const validate = (schema) => {
    return (req, res, next) => {
        ...
    };
};
```

Think:

```text
validate(schema)
       ↓
middleware function
       ↓
Express executes it
```

---

# 8. Why Not Just Write This?

You might ask:

```js
const validate = (req, res, next) => {
    ...
};
```

Then how would we tell it which schema to use?

We need different schemas:

```text
registerSchema
loginSchema
updateUserSchema
createProductSchema
updateProductSchema
```

Therefore we need:

```js
validate(registerSchema)
validate(loginSchema)
validate(updateUserSchema)
```

This is called a **middleware factory**.

---

# 9. What Is a Middleware Factory?

A middleware factory is simply:

> A function that creates and returns middleware.

Example:

```js
const validate = (schema) => {
    return (req, res, next) => {
        // middleware
    };
};
```

Input:

```js
registerSchema
```

Output:

```js
(req, res, next) => {
    // validate against registerSchema
}
```

This pattern is extremely useful in Express.

You'll see the same idea later with things like:

```js
authorize(...)
rateLimit(...)
upload(...)
```

---

# 10. Create a Schema

Let's create:

```text
schemas/user.schema.js
```

Example:

```js
import Joi from "joi";

export const registerSchema = Joi.object({
    name: Joi.string()
        .trim()
        .min(2)
        .max(50)
        .required(),

    email: Joi.string()
        .trim()
        .email()
        .required(),

    password: Joi.string()
        .min(8)
        .max(128)
        .required()
});
```

Now we have:

```text
registerSchema
```

# 11. Use It in the Route

```js
import express from "express";
import validate from "../middlewares/validate.middleware.js";
import { registerSchema } from "../schemas/user.schema.js";
import { registerUser } from "../controllers/user.controller.js";

const router = express.Router();

router.post(
    "/users",
    validate(registerSchema),
    registerUser
);

export default router;
```

Now the request flow is:

```text
POST /users
      ↓
validate(registerSchema)
      ↓
Joi
      ↓
registerUser
```

# 12. What Happens When the Request Is Invalid?

Suppose the client sends:

```json
{
    "name": "R",
    "email": "hello",
    "password": "123"
}
```

Joi sees:

```text
name
 ↓
too short

email
 ↓
invalid

password
 ↓
too short
```

Validation fails.

Our middleware does:

```js
if (error) {
    return res.status(400).json({
        message: error.message
    });
}
```

The controller is **never executed**.

This is important.

```text
Request
   ↓
Joi
   ↓
INVALID
   ↓
400 response

Controller ❌
```

---

# 13. Valid Request

Now:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "password": "StrongPassword123"
}
```

Joi passes.

Then:

```js
next();
```

runs.

Flow:

```text
Request
   ↓
Validation
   ↓
VALID
   ↓
next()
   ↓
Controller
```

---

# 14. Why `next()` Is Important

Express middleware does not automatically move to the next middleware.

You have to explicitly call:

```js
next();
```

So:

```js
if (error) {
    return res.status(400).json(...);
}

next();
```

means:

```text
invalid
   ↓
STOP

valid
   ↓
CONTINUE
```

---

# 15. Why `return` Matters

Look at:

```js
if (error) {
    return res.status(400).json({
        message: error.message
    });
}

next();
```

The `return` prevents execution from continuing.

Without it:

```js
if (error) {
    res.status(400).json(...);
}

next();
```

the code could attempt:

```text
send response
     ↓
next()
     ↓
controller
```

which is wrong.

You may eventually encounter errors such as:

```text
Cannot set headers after they are sent
```

So use:

```js
return res.status(...);
```

when ending the request.

---

# 16. Improve the Error Response

Our first version:

```js
{
    "message": "\"email\" must be a valid email"
}
```

works, but production APIs usually benefit from a more consistent structure.

For example:

```json
{
    "success": false,
    "message": "Validation failed",
    "errors": [
        {
            "field": "email",
            "message": "Email must be a valid email"
        }
    ]
}
```

This is much easier for frontend applications to consume.

---

# 17. Get Detailed Joi Errors

Joi's error object contains:

```js
error.details
```

For example:

```js
[
    {
        message: "\"email\" must be a valid email",
        path: ["email"],
        type: "string.email"
    }
]
```

We can transform this.

---

# 18. Better Middleware

Let's create:

```js
const validate = (schema) => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req.body);

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return res.status(400).json({
                success: false,
                message: "Validation failed",
                errors
            });
        }

        req.body = value;

        next();
    };
};

export default validate;
```

Now we have a much more useful middleware.

---

# 19. Why Do We Assign `req.body = value`?

This is very important.

Joi can perform conversions.

For example:

```js
Joi.string().trim()
```

Input:

```text
"   Rahul   "
```

may become:

```text
"Rahul"
```

Similarly, Joi can perform other conversions depending on the schema and options.

The validated/transformed value is:

```js
value
```

So:

```js
req.body = value;
```

ensures the controller receives the validated value.

---

# 20. The Flow Now

```text
Client
  │
  │  "   Rahul   "
  ▼
Express
  │
  ▼
validate(schema)
  │
  ▼
Joi
  │
  │ trim()
  ▼
"Rahul"
  │
  ▼
req.body = value
  │
  ▼
Controller
```

This is much better than validating but continuing to use the original request body.

---

# 21. Important: Joi Conversion

By default, Joi often performs useful conversions.

For example:

```js
Joi.number()
```

may convert a string representation of a number into a number when conversion is enabled.

For example:

```text
"25"
```

may become:

```text
25
```

So:

```js
req.body = value;
```

is an important step.

---

# 22. What If We Don't Assign `value`?

Suppose:

```js
const { error } = schema.validate(req.body);
```

and Joi trims the value internally.

But then the controller still uses:

```js
req.body
```

which may contain the original unprocessed value.

So:

```js
const { error, value } = schema.validate(req.body);

req.body = value;
```

makes the flow explicit.

# 23. Validate Different Request Parts

So far we've only validated:

```js
req.body
```

But an Express request has other important parts.

For example:

```text
req.body
req.params
req.query
req.headers
```

Examples:

### Body

```http
POST /users
```

```json
{
    "name": "Rahul"
}
```

### Params

```http
GET /users/123
```

where:

```js
req.params.id
```

### Query

```http
GET /users?page=2&limit=10
```

where:

```js
req.query.page
req.query.limit
```

A good validation middleware should eventually support all of them.

---

# 24. The Simple Body Version

Our current middleware:

```js
const validate = (schema) => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req.body);

        if (error) {
            ...
        }

        req.body = value;

        next();
    };
};
```

is excellent for learning.

But our backend will need something more flexible.

---

# 25. A Better API

Imagine:

```js
validate(registerSchema, "body")
```

or:

```js
validate(userParamsSchema, "params")
```

or:

```js
validate(searchSchema, "query")
```

Then the middleware can determine what to validate.

For example:

```js
const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[property]);

        if (error) {
            ...
        }

        req[property] = value;

        next();
    };
};
```

Now:

```js
validate(registerSchema, "body")
```

means:

```text
schema → req.body
```

and:

```js
validate(userParamsSchema, "params")
```

means:

```text
schema → req.params
```

---

# 26. Why `property = "body"`?

This:

```js
const validate = (schema, property = "body")
```

means:

> If the caller doesn't provide a property, use `"body"`.

So:

```js
validate(registerSchema)
```

is equivalent to:

```js
validate(registerSchema, "body")
```

This keeps the common case short.

---

# 27. Example: Params Validation

Suppose:

```http
GET /users/123
```

Schema:

```js
const userParamsSchema = Joi.object({
    id: Joi.string()
        .pattern(/^[0-9]+$/)
        .required()
});
```

Route:

```js
router.get(
    "/users/:id",
    validate(userParamsSchema, "params"),
    getUser
);
```

Flow:

```text
req.params
   ↓
Joi
   ↓
valid?
   ↓
getUser
```

# 28. Example: Query Validation

Suppose:

```http
GET /users?page=2&limit=10
```

Schema:

```js
const userQuerySchema = Joi.object({
    page: Joi.number()
        .integer()
        .min(1)
        .default(1),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(10)
});
```

Route:

```js
router.get(
    "/users",
    validate(userQuerySchema, "query"),
    getUsers
);
```

Now the controller receives validated query parameters.

---

# 29. Why Query Validation Is Important

Without validation:

```http
/users?page=hello&limit=-100
```

could reach your service.

Your service then has to worry about:

```text
Is page valid?
Is limit a number?
Is limit negative?
Is limit too large?
```

Instead:

```text
Request
  ↓
Query validation
  ↓
Service
```

The service can assume basic request structure is valid.

---

# 30. Headers Can Also Be Validated

Some APIs need to validate headers.

For example:

```text
x-api-version
x-client-version
```

You could support:

```js
validate(headerSchema, "headers")
```

However, be careful with standard headers and case normalization because Node/Express normalizes header names.

For your backend starter, body/params/query are the most important initially.

---

# 31. Don't Validate Everything in One Schema

Avoid creating something like:

```js
Joi.object({
    body: ...,
    params: ...,
    query: ...
})
```

unless you specifically want a schema representing the entire request.

It's generally clearer to have:

```text
Body schema
Params schema
Query schema
```

and middleware that knows which part it is validating.

---

# 32. Validation Middleware With Allowed Properties

For production-quality middleware, don't allow arbitrary:

```js
validate(schema, "somethingRandom")
```

You can restrict it:

```js
const VALID_PROPERTIES = [
    "body",
    "params",
    "query",
    "headers"
];
```

Then:

```js
if (!VALID_PROPERTIES.includes(property)) {
    throw new Error(`Invalid request property: ${property}`);
}
```

But this is an internal programming error, not a client validation error.

This distinction matters.

---

# 33. Client Error vs Developer Error

Suppose the user sends:

```json
{
    "email": "wrong"
}
```

That's a:

```text
client/input error
```

But if a developer writes:

```js
validate(schema, "banana")
```

that's:

```text
developer configuration error
```

Don't return:

```text
400 Bad Request
```

for developer mistakes.

Good backend architecture distinguishes these categories.

---

# 34. Joi Options

You may see:

```js
schema.validate(data, {
    abortEarly: false
});
```

What does this mean?

By default, Joi may stop after the first validation error.

For example:

```json
{
    "name": "",
    "email": "wrong",
    "password": "123"
}
```

You may only get one error.

With:

```js
abortEarly: false
```

Joi collects all validation errors.

This is usually much better for API clients.

---

# 35. Our Middleware Should Use `abortEarly: false`

So:

```js
const { error, value } = schema.validate(req[property], {
    abortEarly: false
});
```

Now the frontend can receive:

```json
{
    "success": false,
    "message": "Validation failed",
    "errors": [
        {
            "field": "name",
            "message": "\"name\" is not allowed to be empty"
        },
        {
            "field": "email",
            "message": "\"email\" must be a valid email"
        },
        {
            "field": "password",
            "message": "\"password\" length must be at least 8 characters long"
        }
    ]
}
```

This is much more useful.

---

# 36. `stripUnknown`

Another Joi option you may encounter is:

```js
stripUnknown: true
```

Suppose the schema says:

```js
Joi.object({
    name: Joi.string(),
    email: Joi.string().email()
})
```

but the client sends:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "isAdmin": true
}
```

If configured to strip unknown keys, Joi can remove:

```text
isAdmin
```

from the validated result.

This can be useful.

---

# 37. But Be Careful With Unknown Fields

There are two different strategies.

### Reject unknown fields

```text
Client sends extra field
       ↓
Validation error
```

### Strip unknown fields

```text
Client sends extra field
       ↓
Remove it
       ↓
continue
```

Neither is universally correct.

For sensitive APIs, rejecting unexpected fields can sometimes make mistakes easier to detect.

For flexible APIs, stripping unknown fields may be convenient.

We'll make this decision deliberately in your backend architecture rather than blindly enabling everything.

---

# 38. `allowUnknown`

Another option:

```js
allowUnknown: true
```

means unknown fields can remain.

For example:

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "somethingElse": "hello"
}
```

would be accepted.

Again, don't enable this globally without thinking about your API design.

---

# 39. A Strong Basic Middleware

For our project, a good starting version is:

```js
const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[property], {
            abortEarly: false
        });

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return res.status(400).json({
                success: false,
                message: "Validation failed",
                errors
            });
        }

        req[property] = value;

        next();
    };
};

export default validate;
```

This is already reusable across many routes.

# 41. Route Example

```js
router.post(
    "/users",
```

The controller becomes much cleaner:

```js
const registerUser = async (req, res) => {
```

---

# 42. Why This Is Better

Compare the old controller:

```js
const registerUser = async (req, res) => {
    const { error } = registerSchema.validate(req.body);

    if (error) {
        return res.status(400).json(...);
    }

    // more code...
};
```

with:

```js
const registerUser = async (req, res) => {
    const user = await userService.registerUser(req.body);

    return res.status(201).json({
        success: true,
        data: user
    });
};
```

The second one is much easier to read.

---

# 43. Validation Happens Before the Controller

This creates a very useful contract:

```text
Controller receives:
    structurally valid request data
```

For example:

```js
req.body.email
```

has already passed:

```js
Joi.string().email()
```

So the controller doesn't need to repeatedly ask:

```text
Is this an email?
```

---

# 44. But Don't Trust Validation for Everything

This does **not** mean:

> "After Joi, everything is safe."

Joi doesn't guarantee:

```text
user has permission
user owns resource
resource exists
business rule is satisfied
database operation succeeds
```

It only validates what the schema says.

That's why we still need:

```text
Controller
Service
Repository
Authentication
Authorization
Error handling
```

---

# 45. Validation and Authentication

Suppose:

```http
PATCH /users/123
```

Joi validates:

```text
id format
body format
```

But authentication middleware checks:

```text
Who is making the request?
```

Authorization checks:

```text
Can this user modify user 123?
```

So eventually:

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Controller
   ↓
Service
```

The exact order can vary depending on the route, but each middleware has a separate responsibility.

# 50. The Future Version

Eventually, your route might look like:

This makes middleware composable.

# 53. Practice Task

Create:

```text
src/middlewares/validate.middleware.js
```

with:

```js
const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[property], {
            abortEarly: false
        });

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return res.status(400).json({
                success: false,
                message: "Validation failed",
                errors
            });
        }

        req[property] = value;

        next();
    };
};

export default validate;
```

Then create:

```text
src/schemas/user.schema.js
```

with:

```js
import Joi from "joi";

export const registerUserSchema = Joi.object({

        .max(50)
        .required(),

    email: Joi.string()
        .trim()
        .email()
        .required(),

    password: Joi.string()
        .min(8)
        .max(128)

});
```

## 🔑 Remember These 7 Things

1. **Middleware sits between request and controller.**
    
2. `validate(schema)` is a **middleware factory**.
    
3. Use `schema.validate(req[property])`.
    
4. Use `abortEarly: false` to collect all errors.
    
5. Use `req[property] = value` to keep Joi's converted/validated value.
    
6. Don't put database/business logic inside Joi.
    
7. Keep validation, controller, service, and repository responsibilities separate.
