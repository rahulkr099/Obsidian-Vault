# Lesson 9.14 — Validating `req.body`, `req.params`, and `req.query`

In Lesson 9.13, we created a reusable middleware:

```js
validate(schema, property)
```

Today we'll make sure you fully understand **what `req.body`, `req.params`, and `req.query` are**, why each needs different validation, and how to use the same middleware for all three.

This is an important step because real APIs rarely receive all their data through `req.body`.

---

# 1. The Three Places Where API Input Comes From

Consider this request:

```http
PATCH /users/123?notify=true
```

with:

```json
{
    "name": "Rahul"
}
```

There are three different pieces of data here:

```text
PATCH /users/123?notify=true
       │       │
       │       └── query
       │
       └── params

Body:
{
    "name": "Rahul"
}
```

In Express:

```js
req.body
req.params
req.query
```

represent these three sources.

---

# 2. `req.body`

The request body contains data sent inside the HTTP request body.

Example:

```http
POST /users
Content-Type: application/json
```

```json
{
    "name": "Rahul",
    "email": "rahul@example.com",
    "password": "Password123"
}
```

Access it with:

```js
req.body
```

Individual values:

```js
req.body.name
req.body.email
req.body.password
```

This is usually used for:

- registration
    
- login
    
- creating products
    
- updating profiles
    
- creating orders
    
- submitting forms
    

---

# 3. `req.params`

Route parameters are values embedded into the URL path.

Example:

```http
GET /users/123
```

Route:

```js
router.get("/users/:id", getUser);
```

Then:

```js
req.params
```

contains:

```js
{
    id: "123"
}
```

And:

```js
req.params.id
```

gives:

```text
123
```

---

# 4. Important: Params Are Usually Strings

This is something beginners often miss.

If the client sends:

```http
GET /users/123
```

then:

```js
req.params.id
```

is normally:

```js
"123"
```

not:

```js
123
```

So if you need a number, your validation schema can convert it.

For example:

```js
const userParamsSchema = Joi.object({
    id: Joi.number()
        .integer()
        .positive()
        .required()
});
```

Then Joi can produce:

```js
{
    id: 123
}
```

when conversion is enabled.

---

# 5. `req.query`

Query parameters appear after `?` in the URL.

Example:

```http
GET /users?page=2&limit=10
```

Express gives:

```js
req.query
```

as something like:

```js
{
    page: "2",
    limit: "10"
}
```

Again, query values commonly arrive as strings.

That's why validation is especially useful here.

---

# 6. Why Do We Need Validation?

Suppose your API supports:

```http
GET /users?page=2&limit=10
```

You expect:

```text
page → positive integer
limit → positive integer
```

But the client could send:

```http
GET /users?page=hello&limit=-500
```

Without validation, this bad data can travel deeper into your application:

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Database
```

Instead:

```text
Request
   ↓
Query validation
   ↓
❌ 400
```

The invalid request stops early.

---

# 7. One Middleware, Three Sources

Our middleware from the previous lesson:

```js
const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[property], {
            abortEarly: false
        });

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return res.status(400).json({
                success: false,
                message: "Validation failed",
                errors
            });
        }

        req[property] = value;

        next();
    };
};

export default validate;
```

The important part is:

```js
req[property]
```

Because `property` can be:

```text
"body"
"params"
"query"
```

---

# 8. Body Validation

Suppose we have:

```js
const registerUserSchema = Joi.object({
    name: Joi.string()
        .trim()
        .min(2)
        .max(50)
        .required(),

    email: Joi.string()
        .trim()
        .email()
        .required(),

    password: Joi.string()
        .min(8)
        .required()
});
```

Route:

```js
router.post(
    "/users",
    validate(registerUserSchema, "body"),
    registerUser
);
```

Since `"body"` is already the default, this is also valid:

```js
router.post(
    "/users",
    validate(registerUserSchema),
    registerUser
);
```

---

# 9. Params Validation

Suppose we have:

```js
router.get(
    "/users/:id",
    validate(userIdParamsSchema, "params"),
    getUser
);
```

Schema:

```js
const userIdParamsSchema = Joi.object({
    id: Joi.number()
        .integer()
        .positive()
        .required()
});
```

Request:

```http
GET /users/123
```

Initially:

```js
req.params
```

may be:

```js
{
    id: "123"
}
```

Joi validates it and produces:

```js
{
    id: 123
}
```

Then:

```js
req.params = value;
```

So the controller can use:

```js
const { id } = req.params;
```

as a validated value.

---

# 10. Query Validation

Now imagine:

```http
GET /users?page=2&limit=10
```

Schema:

```js
const listUsersQuerySchema = Joi.object({
    page: Joi.number()
        .integer()
        .min(1)
        .default(1),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(10)
});
```

Route:

```js
router.get(
    "/users",
    validate(listUsersQuerySchema, "query"),
    getUsers
);
```

The flow becomes:

```text
?page=2&limit=10
        ↓
   req.query
        ↓
      Joi
        ↓
{
    page: 2,
    limit: 10
}
        ↓
   getUsers()
```

---

# 11. Defaults Are Very Useful

Look at:

```js
page: Joi.number()
    .integer()
    .min(1)
    .default(1)
```

Now the client can simply send:

```http
GET /users
```

There is no:

```text
?page=...
```

Joi can produce:

```js
{
    page: 1
}
```

Similarly:

```js
limit: Joi.number()
    .integer()
    .min(1)
    .max(100)
    .default(10)
```

produces:

```js
limit: 10
```

So your controller doesn't need to repeatedly write:

```js
const page = req.query.page || 1;
const limit = req.query.limit || 10;
```

The schema handles the input contract.

---

# 12. A Real Pagination Example

A common API:

```http
GET /products?page=2&limit=20
```

Schema:

```js
const paginationSchema = Joi.object({
    page: Joi.number()
        .integer()
        .min(1)
        .default(1),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(10)
});
```

Then:

```js
router.get(
    "/products",
    validate(paginationSchema, "query"),
    getProducts
);
```

Controller:

```js
const getProducts = async (req, res) => {
    const { page, limit } = req.query;

    // page and limit are validated

    const products = await productService.getProducts({
        page,
        limit
    });

    return res.status(200).json({
        success: true,
        data: products
    });
};
```

Very clean.

---

# 13. Search + Pagination

Real applications often combine:

```http
GET /products?search=laptop&page=2&limit=20
```

Schema:

```js
const productQuerySchema = Joi.object({
    search: Joi.string()
        .trim()
        .max(100)
        .allow("")
        .default(""),

    page: Joi.number()
        .integer()
        .min(1)
        .default(1),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(10)
});
```

Then:

```js
router.get(
    "/products",
    validate(productQuerySchema, "query"),
    getProducts
);
```

The service receives clean input.

---

# 14. Optional Query Parameters

Suppose:

```http
GET /products?search=laptop
```

We don't require:

```text
page
limit
```

because they have defaults.

But perhaps:

```js
category: Joi.string()
```

is optional.

You can explicitly write:

```js
category: Joi.string()
    .trim()
    .max(50)
    .optional()
```

Although optional is generally Joi's default for keys unless `.required()` is used.

---

# 15. Params With Multiple Values

Suppose:

```http
GET /users/123/posts/456
```

Route:

```js
router.get(
    "/users/:userId/posts/:postId",
    validate(postParamsSchema, "params"),
    getPost
);
```

Schema:

```js
const postParamsSchema = Joi.object({
    userId: Joi.number()
        .integer()
        .positive()
        .required(),

    postId: Joi.number()
        .integer()
        .positive()
        .required()
});
```

Then:

```js
req.params
```

might initially be:

```js
{
    userId: "123",
    postId: "456"
}
```

After Joi:

```js
{
    userId: 123,
    postId: 456
}
```

This gives the service clean IDs.

---

# 16. A Very Important Difference

Consider:

```http
GET /users/123?includePosts=true
```

Here:

```js
req.params
```

contains:

```js
{
    id: "123"
}
```

while:

```js
req.query
```

contains:

```js
{
    includePosts: "true"
}
```

These are **two different validation targets**.

You could have:

```js
validate(userParamsSchema, "params")
```

and:

```js
validate(userQuerySchema, "query")
```

on the same route.

---

# 17. Multiple Validation Middlewares

Example:

```js
router.get(
    "/users/:id",
    validate(userParamsSchema, "params"),
    validate(userQuerySchema, "query"),
    getUser
);
```

Flow:

```text
Request
   ↓
Validate params
   ↓
Validate query
   ↓
Controller
```

This is perfectly valid.

---

# 18. Is Multiple Validation Middleware Bad?

No.

In fact, it can make the route very clear.

```js
router.get(
    "/users/:id",
    validate(userParamsSchema, "params"),
    validate(userQuerySchema, "query"),
    getUser
);
```

Immediately tells another developer:

> This endpoint validates both its URL parameters and query parameters.

---

# 19. But We Can Also Create a Combined Request Validator

Sometimes you may want:

```js
validateRequest({
    params: userParamsSchema,
    query: userQuerySchema,
    body: updateUserSchema
})
```

This can be useful for complex endpoints.

But don't rush into this abstraction.

For learning, first become completely comfortable with:

```js
validate(schema, "body")
validate(schema, "params")
validate(schema, "query")
```

Simple abstractions are easier to debug.

---

# 20. A Common Beginner Mistake

Don't do this:

```js
validate(schema, req.body)
```

Why?

Because our middleware expects:

```js
property
```

not the actual request data.

Correct:

```js
validate(schema, "body")
```

The middleware itself accesses:

```js
req[property]
```

This allows Express to provide the request at execution time.

---

# 21. Another Common Mistake

Don't do:

```js
validate(schema("body"))
```

unless your schema itself is a function designed that way.

Our API is:

```js
validate(schema, "body")
```

because:

```text
schema
+
property
```

are configuration for the middleware factory.

---

# 22. Another Important Issue: `req.query`

There is a subtle point with query parameters.

Express's `req.query` can be backed by a query parser and isn't simply a normal object in every possible setup.

So be careful about assumptions such as:

```js
req.query = value;
```

For many normal Express configurations this works as expected, but your validation architecture should avoid making unnecessary mutations to request objects if a cleaner approach is available.

For our learning implementation, replacing the validated property is fine, but later we'll make the middleware more deliberate about how normalized values are stored.

---

# 23. Why Normalize Query Values?

Consider:

```http
GET /products?page=2&limit=10
```

Raw input:

```js
{
    page: "2",
    limit: "10"
}
```

Application logic wants:

```js
{
    page: 2,
    limit: 10
}
```

This is called **normalization**.

Validation isn't only:

> "Is this allowed?"

It can also be:

> "Turn the input into the shape our application expects."

This is one of the biggest benefits of schema validation.

---

# 24. Validation vs Sanitization

These two ideas are related but not identical.

### Validation

Ask:

```text
Is this value valid?
```

Example:

```js
email: Joi.string().email()
```

### Sanitization / normalization

Ask:

```text
Can we clean or normalize this value?
```

Example:

```js
name: Joi.string().trim()
```

Input:

```text
"   Rahul   "
```

Output:

```text
"Rahul"
```

Joi can perform both kinds of work depending on your schema and options.

---

# 25. Boolean Query Parameters

This is a great example.

Request:

```http
GET /products?featured=true
```

Raw query:

```js
{
    featured: "true"
}
```

Schema:

```js
const productQuerySchema = Joi.object({
    featured: Joi.boolean()
        .default(false)
});
```

After validation:

```js
{
    featured: true
}
```

This is extremely useful.

Without validation, you might accidentally do:

```js
if (req.query.featured === true) {
    ...
}
```

which fails because raw input may be:

```js
"true"
```

not:

```js
true
```

---

# 26. Enum Query Parameters

Suppose your API supports sorting:

```http
GET /products?sort=price
```

You don't want:

```http
?sort=whatever
```

Schema:

```js
const productQuerySchema = Joi.object({
    sort: Joi.string()
        .valid("price", "name", "createdAt")
        .default("createdAt")
});
```

Now the API has a clear contract.

Valid:

```text
price
name
createdAt
```

Invalid:

```text
banana
something
DROP_DATABASE
```

The last one is invalid input and gets rejected by the schema.

# 27. Params + Query + Body Example

Consider:

```http
PATCH /users/123?notify=true
```

Body:

```json
{
    "name": "Rahul"
}
```

We can have:

### Params schema

```js
const userParamsSchema = Joi.object({
    id: Joi.number()
        .integer()
        .positive()
        .required()
});
```

### Query schema

```js
const userQuerySchema = Joi.object({
    notify: Joi.boolean()
        .default(false)

```

### Body schema

```js
const updateUserSchema = Joi.object({
    name: Joi.string()
        .trim()
        .min(2)
        .max(50)

```

```js
router.patch(
```

# 28. Controller Becomes Simple

```js
const updateUser = async (req, res) => {
    const { id } = req.params;
    const { notify } = req.query;
    const { name } = req.body;

    const user = await userService.updateUser({
        id,
        name,
        notify
    });

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Notice:

```text
id
 ↓
validated

notify
 ↓
validated

name
 ↓
validated
```

The controller can focus on orchestration.

---

# 29. Validation Does Not Replace Business Rules

Suppose:

```js
id: Joi.number().positive()
```

This verifies:

```text
id is a positive number
```

But it doesn't verify:

```text
Does user 123 exist?
```

That belongs somewhere deeper:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Similarly:

```text
Is this user allowed to edit user 123?
```

is authorization, not Joi validation.

---

# 30. Three Different Questions

This distinction is extremely important.

### Validation

```text
Is the input structurally valid?
```

### Authorization

```text
Is this user allowed to perform this action?
```

### Business logic

```text
Does this operation make sense according to our application's rules?
```

Example:

```text
id = 123
```

Validation:

```text
Is 123 a valid ID?
```

Authorization:

```text
Can Rahul modify user 123?
```

Business rule:

```text
Can a user change their email after verification?
```

These should not be mixed together.

---

# 31. Recommended Middleware Order

For a protected route, you might eventually have:

```js
router.patch(
    "/users/:id",
    authenticate,
    authorize("user:update"),
    validate(userParamsSchema, "params"),
    validate(updateUserSchema, "body"),
    updateUser
);
```

Conceptually:

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Controller
```

Again, the exact ordering can vary depending on your requirements, but the separation of responsibilities is the key lesson.

---

# 32. A Reusable Validation File

I recommend keeping:

```text
src/
└── middlewares/
    └── validate.middleware.js
```

focused only on request validation.

Don't put schemas inside this file.

Bad:

```js
// validate.middleware.js

const registerSchema = ...
const loginSchema = ...
const productSchema = ...
const validate = ...
```

Better:

```text
schemas/
    user.schema.js
    product.schema.js
    auth.schema.js

middlewares/
    validate.middleware.js
```

This separation will become very valuable as the project grows.

# 33. Your Complete Example

### Middleware

```js
const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[property], {
            abortEarly: false
        });

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return res.status(400).json({
                success: false,
                message: "Validation failed",
                errors
            });
        }

        req[property] = value;

        next();
    };
};

export default validate;
```

### Params schema

```js
const userParamsSchema = Joi.object({
    id: Joi.number()
        .integer()
        .positive()
        .required()
});
```

### Query schema

```js
const userQuerySchema = Joi.object({
    notify: Joi.boolean()
        .default(false)
});
```

### Body schema

```js
const updateUserSchema = Joi.object({
    name: Joi.string()
        .trim()
        .min(2)
        .max(50)
        .required()
});
```

### Route

```js
router.patch(
    "/users/:id",
    validate(userParamsSchema, "params"),
    validate(userQuerySchema, "query"),
    validate(updateUserSchema, "body"),
    updateUser
);
```

# 34. Request Flow

For:

```http
PATCH /users/123?notify=true
```

```json
{
    "name": "Rahul"
}
```

the pipeline becomes:

```text
                    REQUEST
                       │
                       ▼
              /users/123?notify=true
                       │
                       ▼
             ┌─────────────────┐
             │ Validate params │
             │ id = 123        │
             └────────┬────────┘
                      │
                      ▼
             ┌─────────────────┐
             │ Validate query  │
             │ notify = true   │
             └────────┬────────┘
                      │
                      ▼
             ┌─────────────────┐
             │ Validate body   │
             │ name = Rahul    │
             └────────┬────────┘
                      │
                      ▼
                  Controller
                      │
                      ▼
                   Service
                      │
                      ▼
                 Repository
```

This is the architecture you should start seeing mentally whenever you look at an Express route.

# 🧠 What You Should Remember

The biggest idea from this lesson is:

```text
HTTP Request
     │
     ├── req.body
     │       ↓
     │    body schema
     │
     ├── req.params
     │       ↓
     │   params schema
     │
     └── req.query
             ↓
         query schema
```

And our reusable middleware lets us write:

```js
validate(schema, "body")
validate(schema, "params")
validate(schema, "query")
```

instead of writing validation logic inside every controller.

That is the beginning of a **clean, scalable Express architecture**.
