# Lesson 9.15 — Joi Validation Errors & Centralized Error Handling

In Lesson 9.14, we learned how to validate:

```text
req.body
req.params
req.query
```

Now we will solve an important production problem:

> **How should validation errors be handled consistently across the entire backend?**

Right now, our validation middleware directly sends:

```js
res.status(400).json(...)
```

That works, but it doesn't fit perfectly with the **centralized error-handling architecture** we started building in Phase 8.

The goal of this lesson is to move toward:

```text
Request
   ↓
Validation
   ↓
ValidationError
   ↓
Central Error Middleware
   ↓
Consistent API Response
```

---

# 1. The Problem With Our Current Middleware

Our current middleware looks like:

```js
const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[property], {
            abortEarly: false
        });

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return res.status(400).json({
                success: false,
                message: "Validation failed",
                errors
            });
        }

        req[property] = value;

        next();
    };
};
```

The problem is this:

```js
return res.status(400).json(...)
```

The validation middleware is now responsible for:

1. validating
    
2. creating error information
    
3. deciding HTTP status
    
4. formatting the API response
    

That's more responsibility than we want.

---

# 2. Think About Our Architecture

Remember the architecture we've been building:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

And errors should eventually flow toward:

```text
                  Error
                    ↓
        Central Error Middleware
                    ↓
             HTTP Response
```

So validation should ideally do:

```text
Validation fails
      ↓
create/forward error
      ↓
central error handler
```

instead of:

```text
Validation fails
      ↓
send response directly
```

---

# 3. Why Centralized Error Handling?

Imagine these errors:

```text
ValidationError
AuthenticationError
AuthorizationError
NotFoundError
ConflictError
DatabaseError
InternalServerError
```

If every middleware/controller formats its own response, you'll eventually get:

### Endpoint A

```json
{
    "success": false,
    "message": "Validation failed"
}
```

### Endpoint B

```json
{
    "error": "Invalid input"
}
```

### Endpoint C

```json
{
    "status": "error",
    "errors": [...]
}
```

That's messy.

We want one consistent format.

---

# 4. Our Target

Eventually, any validation failure should produce something like:

```json
{
    "success": false,
    "message": "Validation failed",
    "errors": [
        {
            "field": "email",
            "message": "\"email\" must be a valid email"
        },
        {
            "field": "password",
            "message": "\"password\" length must be at least 8 characters long"
        }
    ]
}
```

And the middleware responsible for formatting this response should be:

```text
error.middleware.js
```

---

# 5. First Understand `next(error)`

Express has a special error-handling mechanism.

Normal middleware:

```js
(req, res, next)
```

calls:

```js
next();
```

to continue.

But if something goes wrong:

```js
next(error);
```

tells Express:

> "Something failed. Send this error through the error-handling middleware."

This is extremely important.

---

# 6. Normal `next()`

Example:

```js
const middleware = (req, res, next) => {
    console.log("Middleware executed");

    next();
};
```

Flow:

```text
Middleware
    ↓
next()
    ↓
Next middleware
```

---

# 7. Error `next(error)`

Example:

```js
const middleware = (req, res, next) => {
    const error = new Error("Something went wrong");

    next(error);
};
```

Flow:

```text
Middleware
    ↓
next(error)
    ↓
Error middleware
```

This is how we can connect validation to our centralized error system.

---

# 8. Express Error Middleware

An Express error-handling middleware has **four arguments**:

```js
(err, req, res, next)
```

For example:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    return res.status(500).json({
        success: false,
        message: "Internal server error"
    });
};
```

Notice:

```js
(err, req, res, next)
```

The first argument is the error.

---

# 9. Why Four Arguments?

This is important:

```js
(err, req, res, next)
```

Express recognizes this as an **error-handling middleware**.

Don't accidentally write:

```js
(req, res, next)
```

That is normal middleware.

Error middleware must have:

```js
(err, req, res, next)
```

---

# 10. Our Validation Middleware

Now instead of:

```js
if (error) {
    return res.status(400).json(...);
}
```

we want:

```js
if (error) {
    return next(error);
}
```

But there's a problem.

What kind of error are we sending?

Joi gives us a Joi error object, but our application should eventually understand different types of errors.

This leads us to **custom application errors**.

---

# 11. Why Custom Errors?

Suppose we simply do:

```js
next(error);
```

where `error` is Joi's error.

Our centralized error handler now has to somehow determine:

```text
Is this a Joi validation error?
Database error?
Authentication error?
Something else?
```

We could check Joi's properties.

But a cleaner architecture is to create our own:

```text
ValidationError
```

and convert the Joi error into that application error.

---

# 12. Create `ValidationError`

Our project could have:

```text
src/
├── errors/
│   ├── AppError.js
│   └── ValidationError.js
```

First:

```js
class AppError extends Error {
    constructor(message, statusCode = 500) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}

export default AppError;
```

This is our base application error.

---

# 13. Create `ValidationError`

```js
import AppError from "./AppError.js";

class ValidationError extends AppError {
    constructor(message = "Validation failed", errors = []) {
        super(message, 400);

        this.errors = errors;
        this.name = "ValidationError";
    }
}

export default ValidationError;
```

Now we have:

```text
AppError
   │
   └── ValidationError
```

---

# 14. Why Extend `AppError`?

Because:

```js
ValidationError
```

is a type of:

```js
AppError
```

So:

```text
AppError
├── ValidationError
├── NotFoundError
├── UnauthorizedError
├── ForbiddenError
└── ConflictError
```

This gives us a clean error hierarchy.

---

# 15. Creating a Validation Error

Our middleware can now do:

```js
const validationError = new ValidationError(
    "Validation failed",
    errors
);

return next(validationError);
```

The flow becomes:

```text
Joi
 ↓
Joi error
 ↓
convert to ValidationError
 ↓
next(error)
 ↓
central error middleware
```

---

# 16. Updated Validation Middleware

Our middleware becomes:

```js
import ValidationError from "../errors/ValidationError.js";

const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(req[property], {
            abortEarly: false
        });

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return next(
                new ValidationError(
                    "Validation failed",
                    errors
                )
            );
        }

        req[property] = value;

        next();
    };
};

export default validate;
```

This is much cleaner.

# 17. What Changed?

Before:

```text

   ↓
HTTP response
```

Now:

```text
Validation
   ↓
ValidationError
   ↓
Error middleware
   ↓
HTTP response
```

That's a major architectural improvement.

# 18. Central Error Middleware

Now create:

```text
src/middlewares/error.middleware.js
```

Start with:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    return res.status(err.statusCode || 500).json({
        success: false,
        message: err.message || "Internal server error"
    });
};

export default errorMiddleware;
```

Now our `ValidationError` will automatically use:

```js
statusCode = 400
```

---

# 19. Add Validation Details

We want the `errors` array too.

So:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    return res.status(err.statusCode || 500).json({
        success: false,
        message: err.message || "Internal server error",
        errors: err.errors || undefined
    });
};

export default errorMiddleware;
```

Then a validation failure produces:

```json
{
    "success": false,
    "message": "Validation failed",
    "errors": [
        {
            "field": "email",
            "message": "\"email\" must be a valid email"
        }
    ]
}
```

---

# 20. Better: Don't Send `errors: undefined`

A cleaner implementation is:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    const response = {
        success: false,
        message: err.message || "Internal server error"
    };

    if (err.errors) {
        response.errors = err.errors;
    }

    return res.status(err.statusCode || 500).json(response);
};

export default errorMiddleware;
```

Now normal errors don't get an unnecessary:

```json
"errors": null
```

or:

```json
"errors": undefined
```

---

# 21. Register Error Middleware Correctly

This is very important.

Error middleware should generally be registered **after your routes**.

For example:

```js
app.use("/api/users", userRoutes);
app.use("/api/products", productRoutes);

app.use(errorMiddleware);
```

Think:

```text
Request
   ↓
Routes
   ↓
Something throws/fails
   ↓
errorMiddleware
```

---

# 22. Why Must It Come Last?

Imagine:

```js
app.use(errorMiddleware);

app.use("/api/users", userRoutes);
```

A validation error occurring later may not flow through the error middleware in the way you expect.

The normal structure is:

```text
normal middleware
      ↓
routes
      ↓
error middleware
```

So the error handler gets the errors passed forward by earlier layers.

# 24. Multiple Validation Errors

Let's test:

```json
{
    "name": "R",
    "email": "hello",
    "password": "123"
}
```

Because we use:

```js

```

Joi gives us multiple errors.

We convert them:

```js
const errors = error.details.map((detail) => ({
    field: detail.path.join("."),

```

Suppose Joi returns:

```text
name
email
password
```

We produce:

```json
{
    "success": false,
    "message": "Validation failed",
    "errors": [
        {
            "field": "name",
            "message": "\"name\" length must be at least 2 characters long"
        },
        {
            "field": "email",
            "message": "\"email\" must be a valid email"
        },
```

# 25. Why Convert Joi Errors?

Because we don't want the rest of our application to know Joi's internal error structure.

Bad architecture:

```text
Controller
   ↓
knows Joi
   ↓
knows error.details
   ↓
knows Joi error types
```

Better:

```text
Validation Middleware
   ↓
knows Joi
   ↓
converts Joi error
   ↓
ValidationError
   ↓
rest of application
```

This is called **separation of concerns**.

---

# 26. Joi Should Stay at the Validation Boundary

Think about this rule:

> **Joi belongs at the request-validation boundary.**

Your service shouldn't need:

```js
import Joi from "joi";
```

just to validate HTTP input.

The service should receive data that has already passed request validation.

For example:

```js
await userService.updateUser({
    id,
    name,
    email
});
```

The service can focus on business logic.

---

# 27. Validation Error vs Business Error

Consider:

```text
POST /users
```

with:

```json
{
    "email": "hello"
}
```

That's:

```text
ValidationError
```

But suppose:

```json
{
    "email": "rahul@example.com"
}
```

is valid, but the email already exists.

That's not a Joi problem.

That's:

```text
ConflictError
```

For example:

```text
Validation
    ↓
valid

Service
    ↓
email already exists
    ↓
ConflictError
```

This distinction is extremely important.

---

# 28. Another Example: User ID

Request:

```http
GET /users/abc
```

If the API expects a numeric ID:

```text
abc
```

is structurally invalid.

That's:

```text
ValidationError
```

But:

```http
GET /users/999999
```

may be a valid ID format.

If the user doesn't exist:

```text
999999
```

then:

```text
NotFoundError
```

So:

```text
/abc
 ↓
ValidationError

/999999
 ↓
valid input
 ↓
NotFoundError
```

Excellent distinction.

---

# 29. Don't Return 500 for Validation Errors

A common beginner mistake is:

```js
return res.status(500).json({
    message: error.message
});
```

for every error.

That's wrong.

A client sending invalid input should generally receive a client-error status such as:

```text
400 Bad Request
```

while unexpected server failures should generally be:

```text
500 Internal Server Error
```

Our custom error handles this:

```js
super(message, 400);
```

---

# 30. `isOperational`

Remember this property:

```js
this.isOperational = true;
```

Why?

It allows us to distinguish expected application errors from unexpected programming/system failures.

For example:

```text
ValidationError
    ↓
expected
    ↓
operational error
```

while something like:

```js
undefinedVariable.someMethod()
```

could represent an unexpected programming bug.

Later, our error-handling system can use this distinction for logging and production behavior.

---

# 31. Don't Expose Internal Errors

Suppose your database throws:

```text
MongoServerError:
E11000 duplicate key error collection...
```

You probably don't want to send the raw database error directly to the client.

Similarly, don't expose:

```text
file paths
stack traces
database internals
environment variables
SQL/Mongo details
```

in production responses.

Instead:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

while the actual technical details go into your logs.

---

# 32. Development vs Production

During development, you may want:

```js
console.error(err.stack);
```

because it helps debugging.

In production, your API response should generally remain safe:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

Your logging system can contain the technical details.

We'll go deeper into this later when we improve production logging.

# 35. Error Middleware With Environment Awareness

A basic production-friendly structure:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    const statusCode = err.statusCode || 500;

    const response = {
        success: false,
        message:
            err.isOperational
                ? err.message
                : "Internal server error"
    };

    if (err.errors) {
        response.errors = err.errors;
    }

    return res.status(statusCode).json(response);
};

export default errorMiddleware;
```

The key idea:

```text
Operational error
    ↓
safe known message

Unexpected error
    ↓
generic message
```

---

# 36. Why This Is Safer

Imagine an unexpected error:

```js
throw new Error(
    "MongoDB connection failed at /home/rahul/project/src/db/index.js"
);
```

We don't want the client receiving:

```json
{
    "message": "MongoDB connection failed at /home/rahul/project/src/db/index.js"
}
```

Instead:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

while your logs contain the actual error.

---

# 37. Validation Errors Are Safe to Show

Validation errors are generally safe to return because they describe the client's input.

For example:

```json
{
    "field": "email",
    "message": "\"email\" must be a valid email"
}
```

This helps the frontend correct the request.

But even validation messages should be designed carefully so they don't expose sensitive implementation details.

---

# 38. Field Paths

Remember:

```js
detail.path.join(".")
```

Why do we do that?

Suppose the schema contains:

```js
address: Joi.object({
    city: Joi.string().required()
})
```

and the client sends:

```json
{
    "address": {}
}
```

Joi's path might be:

```js
["address", "city"]
```

Joining:

```js
detail.path.join(".")
```

gives:

```text
address.city
```

That's very useful to frontend developers.

---

# 39. Arrays

Suppose:

```js
tags: Joi.array().items(
    Joi.string().required()
)
```

and the second item is invalid.

Joi may give a path similar to:

```js
["tags", 1]
```

Our:

```js
detail.path.join(".")
```

produces:

```text
tags.1
```

The frontend can use this to identify the exact problematic value.

---

# 40. Better Error Object

We could include the Joi error type:

```js
const errors = error.details.map((detail) => ({
    field: detail.path.join("."),
    message: detail.message,
    type: detail.type
}));
```

Example:

```json
{
    "field": "email",
    "message": "\"email\" must be a valid email",
    "type": "string.email"
}
```

Should we always expose `type`?

Not necessarily.

For a simple API, this is enough:

```json
{
    "field": "email",
    "message": "Email must be valid"
}
```

Keep your public error format stable and simple.

---

# 41. Customize Joi Messages

Instead of exposing Joi's default:

```text
"email" must be a valid email
```

you can define:

```js
email: Joi.string()
    .email()
    .messages({
        "string.email": "Please provide a valid email address"
    })
```

Then the API can return:

```json
{
    "field": "email",
    "message": "Please provide a valid email address"
}
```

This is much more user-friendly.

---

# 42. Should Every Message Be Customized?

Not necessarily.

For learning:

```js
Joi.string().email()
```

is fine.

As your project becomes polished, you may customize messages for important user-facing fields.

Don't create unnecessary complexity too early.

# 44. Complete Example

### `AppError.js`

```js
class AppError extends Error {
    constructor(message, statusCode = 500) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}

export default AppError;
```

### `ValidationError.js`

```js
import AppError from "./AppError.js";

    constructor(message = "Validation failed", errors = []) {
        super(message, 400);

        this.name = "ValidationError";
        this.errors = errors;
    }
}

export default ValidationError;
```

### `validate.middleware.js`

```js
import ValidationError from "../errors/ValidationError.js";

const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(
            req[property],
            {
                abortEarly: false
            }
        );

        if (error) {
            const errors = error.details.map((detail) => ({
                field: detail.path.join("."),
                message: detail.message
            }));

            return next(
                new ValidationError(
                    "Validation failed",
                    errors
                )
            );
        }

        req[property] = value;

        next();
    };
};

export default validate;
```

### `error.middleware.js`

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

        message: err.isOperational
            ? err.message
            : "Internal server error"
    };

    if (err.errors) {
        response.errors = err.errors;
    }

    return res.status(statusCode).json(response);
};

export default errorMiddleware;
```

# 48. One More Important Rule

Don't write:

```js
try {
    const { error } = schema.validate(...);

    if (error) {
        throw error;
    }
} catch (error) {
    return res.status(400).json(...);
}
```

just for Joi validation.

Joi's synchronous validation doesn't require this.

Simply:

```js
const { error, value } = schema.validate(...);

if (error) {
    return next(new ValidationError(...));
}
```

is cleaner.

# 49. What Happens When the Controller Throws?

Suppose:

```js
const controller = async (req, res) => {
    throw new Error("Something unexpected happened");
};
```

Eventually, with proper async error handling, that error should also reach:

```text
errorMiddleware
```

Then:

```text
ValidationError
       ↓
errorMiddleware

DatabaseError
       ↓
errorMiddleware

NotFoundError
       ↓
errorMiddleware

UnexpectedError
       ↓
errorMiddleware
```

This is why centralized error handling becomes so powerful.

# 🧠 What You Should Remember

The five most important ideas from this lesson are:

### 1. Don't let every middleware create its own response

Instead:

```js
next(error);
```

---

### 2. Convert Joi errors into your application's error type

```js
new ValidationError(...)
```

---

### 3. Centralize error responses

```text
error.middleware.js
```

---

### 4. Keep Joi at the validation boundary

```text
Request
 ↓
Joi
 ↓
Validated data
 ↓
Controller/Service
```

Your services don't need to know about Joi.

---

### 5. Separate error categories

```text
Invalid input
    → ValidationError (400)

Resource doesn't exist
    → NotFoundError (404)

Not authenticated
    → AuthenticationError (401)

Not allowed
    → AuthorizationError (403)

Duplicate/conflicting data
    → ConflictError (409)

Unexpected failure
    → Internal Server Error (500)
```

This distinction will become **very important in the next lessons**, because we'll start building a proper error system instead of treating every failure as simply `"Something went wrong"`.
