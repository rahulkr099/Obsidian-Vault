# Lesson 9.16 — Designing a Proper `AppError` Hierarchy

In Lesson 9.15, we changed our validation flow from:

```text
Validation fails
      ↓
send response directly
```

to:

```text
Validation fails
      ↓
ValidationError
      ↓
next(error)
      ↓
Central Error Middleware
      ↓
HTTP response
```

Now we need to make our error system more useful.

Instead of creating generic errors everywhere like:

```js
new AppError("Something went wrong", 500)
```

we'll create specific error classes:

```text
AppError
├── BadRequestError
├── ValidationError
├── UnauthorizedError
├── ForbiddenError
├── NotFoundError
└── ConflictError
```

This will make your backend much easier to understand and maintain.

---

# 1. Why Do We Need Different Errors?

Consider these requests.

### Invalid input

```http
POST /users
```

```json
{
  "email": "hello"
}
```

This is:

```text
400 Bad Request
```

---

### Not logged in

```http
GET /profile
```

without authentication.

This is:

```text
401 Unauthorized
```

---

### Logged in but not allowed

```http
DELETE /users/123
```

A normal user tries to delete another user's account.

This is:

```text
403 Forbidden
```

---

### Resource doesn't exist

```http
GET /users/999999
```

User doesn't exist.

This is:

```text
404 Not Found
```

---

### Duplicate resource

```http
POST /users
```

with an email that already exists.

This is commonly:

```text
409 Conflict
```

These are **different problems**.

Our backend should represent them differently.

---

# 2. HTTP Status Codes Are Part of Your API Contract

Your frontend may need to behave differently depending on the status.

For example:

```text
400 → show validation errors

401 → ask user to log in

403 → show "You don't have permission"

404 → show "Not found"

409 → show conflict message

500 → show generic server error
```

So choosing the correct error type isn't just about making code pretty.

It affects the entire application.

---

# 3. Our Base `AppError`

We already created:

```js
class AppError extends Error {
    constructor(message, statusCode = 500) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}

export default AppError;
```

Let's understand it carefully.

---

# 4. `extends Error`

```js
class AppError extends Error
```

means:

> `AppError` is a specialized JavaScript `Error`.

So this:

```js
throw new AppError("Something went wrong");
```

is still an `Error`.

We get normal error features such as:

```js
error.message
error.stack
error.name
```

---

# 5. `statusCode`

We store:

```js
this.statusCode = statusCode;
```

Example:

```js
new AppError("Something went wrong", 500);
```

gives:

```js
error.statusCode
```

as:

```text
500
```

This lets our central error middleware decide the HTTP response status.

---

# 6. `isOperational`

We also have:

```js
this.isOperational = true;
```

This tells our error handler:

> "This is an expected application error."

For example:

```text
User not found
Invalid email
Not authenticated
Not authorized
Duplicate email
```

These are expected situations.

They are not necessarily programming bugs.

---

# 7. `Error.captureStackTrace`

```js
Error.captureStackTrace(
    this,
    this.constructor
);
```

This gives us a useful stack trace while avoiding unnecessary constructor details.

For now, you don't need to memorize the implementation.

Just understand:

```text
AppError
   ↓
normal JavaScript Error
   ↓
useful stack trace
```

---

# 8. `BadRequestError`

Now let's create:

```text
src/errors/BadRequestError.js
```

```js
import AppError from "./AppError.js";

class BadRequestError extends AppError {
    constructor(message = "Bad request") {
        super(message, 400);

        this.name = "BadRequestError";
    }
}

export default BadRequestError;
```

Now instead of:

```js
new AppError("Invalid request", 400)
```

we can write:

```js
new BadRequestError("Invalid request");
```

Much clearer.

---

# 9. `ValidationError`

Our existing error:

```js
import AppError from "./AppError.js";

class ValidationError extends AppError {
    constructor(message = "Validation failed", errors = []) {
        super(message, 400);

        this.name = "ValidationError";
        this.errors = errors;
    }
}

export default ValidationError;
```

Notice:

```text
ValidationError
      ↓
400
```

This is a specialized form of bad request.

---

# 10. Should `ValidationError` Extend `BadRequestError`?

You could design it this way:

```text
AppError
   ↓
BadRequestError
   ↓
ValidationError
```

For example:

```js
class ValidationError extends BadRequestError {
    constructor(message = "Validation failed", errors = []) {
        super(message);

        this.name = "ValidationError";
        this.errors = errors;
    }
}
```

This is actually a nice hierarchy.

But for our starter architecture, keeping all application errors directly under `AppError` is simpler:

```text
AppError
├── BadRequestError
├── ValidationError
├── UnauthorizedError
├── ForbiddenError
├── NotFoundError
└── ConflictError
```

We'll use that for now.

---

# 11. `UnauthorizedError`

Create:

```text
src/errors/UnauthorizedError.js
```

```js
import AppError from "./AppError.js";

class UnauthorizedError extends AppError {
    constructor(message = "Authentication required") {
        super(message, 401);

        this.name = "UnauthorizedError";
    }
}

export default UnauthorizedError;
```

Use it when the client hasn't successfully authenticated.

For example:

```js
if (!req.user) {
    return next(
        new UnauthorizedError()
    );
}
```

Response:

```http
401 Unauthorized
```

---

# 12. The Meaning of 401

A common misconception is:

> 401 means "you don't have permission."

More precisely, `401` is about **authentication**.

Think:

```text
Who are you?
```

If the server cannot establish a valid authenticated identity:

```text
401
```

Examples:

```text
No access token
Invalid access token
Expired authentication
Invalid credentials
```

---

# 13. `ForbiddenError`

Now:

```text
src/errors/ForbiddenError.js
```

```js
import AppError from "./AppError.js";

class ForbiddenError extends AppError {
    constructor(message = "You do not have permission to perform this action") {
        super(message, 403);

        this.name = "ForbiddenError";
    }
}

export default ForbiddenError;
```

This means:

> "I know who you are, but you're not allowed to do this."

---

# 14. 401 vs 403

This distinction is extremely important.

### 401

```text
Authentication problem
```

Example:

```text
No valid login
```

### 403

```text
Authorization problem
```

Example:

```text
Logged in as normal user
but trying to access admin endpoint
```

Think:

```text
401 → Who are you?

403 → I know who you are,
      but you're not allowed.
```

---

# 15. `NotFoundError`

Create:

```text
src/errors/NotFoundError.js
```

```js
import AppError from "./AppError.js";

class NotFoundError extends AppError {
    constructor(message = "Resource not found") {
        super(message, 404);

        this.name = "NotFoundError";
    }
}

export default NotFoundError;
```

Use:

```js
const user = await userRepository.findById(id);

if (!user) {
    return next(
        new NotFoundError("User not found")
    );
}
```

Response:

```http
404 Not Found
```

---

# 16. `ConflictError`

Create:

```text
src/errors/ConflictError.js
```

```js
import AppError from "./AppError.js";

class ConflictError extends AppError {
    constructor(message = "Resource conflict") {
        super(message, 409);

        this.name = "ConflictError";
    }
}

export default ConflictError;
```

Typical examples:

```text
Email already registered
Username already taken
Duplicate resource
Version conflict
```

Example:

```js
const existingUser =
    await userRepository.findByEmail(email);

if (existingUser) {
    return next(
        new ConflictError(
            "Email is already registered"
        )
    );
}
```

# 18. The Hierarchy

Conceptually:

```text
                    Error
                      │
                   AppError
                      │
       ┌──────────────┼──────────────┐
       │              │              │
   BadRequest      Unauthorized    Forbidden
       │
   Validation

       ┌──────────────┐
       │              │
   NotFound       Conflict
```

Or, using the simpler direct-child design we're implementing:

```text
                    AppError
                       │
     ┌─────────┬───────┼────────┬──────────┐
     │         │       │        │          │
    400       401     403      404        409
     │         │       │        │          │
 BadRequest  Auth   Forbidden NotFound   Conflict
     │
Validation
```

# 19. Using Errors in a Controller

Suppose:

```js
const getUser = async (req, res, next) => {
    const { id } = req.params;

    const user = await userService.getUserById(id);

    if (!user) {
        return next(
            new NotFoundError("User not found")
        );
    }

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

The controller doesn't send:

```js
res.status(404).json(...)
```

Instead:

```js
next(new NotFoundError(...))
```

Then the centralized error handler takes over.

---

# 20. Controller Responsibility

The controller can now say:

```text
"The user doesn't exist."
```

It doesn't need to worry about:

```text
How should the JSON look?
What status should Express send?
Should stack traces be hidden?
How should errors be logged?
```

The error middleware handles those concerns.

---

# 21. Service Layer Can Also Create Errors

Suppose your service has:

```js
const getUserById = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

This can be reasonable when the condition is part of the business operation.

Then the controller can stay even simpler:

```js
const getUser = async (req, res) => {
    const user = await userService.getUserById(
        req.params.id
    );

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

The service throws:

```text
NotFoundError
      ↓
error handler
```

---

# 22. Where Should Errors Be Created?

A useful rule:

### Request shape problems

Middleware:

```text
ValidationError
```

### Authentication problems

Authentication middleware:

```text
UnauthorizedError
```

### Permission problems

Authorization middleware:

```text
ForbiddenError
```

### Resource/business problems

Service:

```text
NotFoundError
ConflictError
BadRequestError
```

### Unexpected technical failures

Usually:

```text
ordinary Error
```

and the central handler treats it as:

```text
500 Internal Server Error
```

# 25. Central Error Middleware

Our error middleware can now use the hierarchy:

```js
const errorMiddleware = (err, req, res, next) => {
    console.error(err);

    const statusCode = err.statusCode || 500;

    const response = {
        success: false,
        message: err.isOperational
            ? err.message
            : "Internal server error"
    };

    if (err.errors) {
        response.errors = err.errors;
    }

    return res.status(statusCode).json(response);
};

export default errorMiddleware;
```

Notice something important:

**The middleware doesn't need to know every error class.**

It only needs:

```js
err.statusCode
err.message
err.isOperational
```

That's one of the benefits of our base class.

# 27. Don't Create 50 Error Classes

This is an important architecture lesson.

You don't need:

```text
EmailAlreadyExistsError
UserAlreadyExistsError
ProductAlreadyExistsError
OrderAlreadyExistsError
...
```

Most of these are simply:

```text
ConflictError
```

with different messages.

For example:

```js
throw new ConflictError(
    "Email is already registered"
);
```

and:

```js
throw new ConflictError(
    "Username is already taken"
);
```

Same error category.

Different message.

---

# 28. Similarly, Don't Overuse `BadRequestError`

If the problem is specifically:

```text
Validation failed
```

use:

```js
ValidationError
```

If it's another malformed request condition that isn't schema validation:

```js
BadRequestError
```

For example:

```js
if (startDate > endDate) {
    throw new BadRequestError(
        "Start date must be before end date"
    );
}
```

This isn't necessarily a Joi schema problem.

It's a request/business constraint.

---

# 29. A Useful Decision Tree

When something goes wrong, ask:

```text
Is the request data structurally invalid?
       │
      YES
       ↓
ValidationError
       │
      NO
       ↓
Is the user authenticated?
       │
      NO
       ↓
UnauthorizedError
       │
      YES
       ↓
Is the user allowed?
       │
      NO
       ↓
ForbiddenError
       │
      YES
       ↓
Does the resource exist?
       │
      NO
       ↓
NotFoundError
       │
      YES
       ↓
Does this operation conflict with existing state?
       │
      YES
       ↓
ConflictError
       │
      NO
       ↓
BadRequestError / business error
```

This mental model will help you choose errors correctly.

# 30. Important: Don't Use 404 for Everything

Suppose:

```http
POST /users
```

with duplicate email.

Don't respond:

```text
404
```

because the user wasn't "not found."

Use:

```text
409 Conflict
```

Similarly:

```text
Invalid password
```

shouldn't automatically be:

```text
404
```

or:

```text
500
```

Choose the error category based on what actually happened.

---

# 31. Important: Don't Use 401 for Everything Authentication-Related

If a user is already authenticated but doesn't have permission:

```text
403
```

not:

```text
401
```

Keep this mental distinction:

```text
401 = authentication

403 = authorization
```

# 32. Error Classes Make Code Read Like English

Compare:

```js
if (!user) {
    return next(
        new AppError("User not found", 404)
    );
}
```

with:

```js
if (!user) {
    return next(
        new NotFoundError("User not found")
    );
}
```

The second version communicates the intent immediately.

That's a major advantage of domain-specific error classes.

# 33. A Cleaner `errors/index.js`

Once you have several errors, importing can become repetitive.

You can create:

```text
src/errors/index.js
```

```js
export { default as AppError } from "./AppError.js";
export { default as BadRequestError } from "./BadRequestError.js";
export { default as ValidationError } from "./ValidationError.js";
export { default as UnauthorizedError } from "./UnauthorizedError.js";
export { default as ForbiddenError } from "./ForbiddenError.js";
export { default as NotFoundError } from "./NotFoundError.js";
export { default as ConflictError } from "./ConflictError.js";
```

Then:

```js
import {
    NotFoundError,
    ConflictError
} from "../errors/index.js";
```

This is called a **barrel file**.

It's convenient, but don't worry about it if your project is still small.

# 35. Full Error Flow

Let's put everything together.

### Request

```http
GET /users/123
```

### Authentication

```text
No token
   ↓
UnauthorizedError
   ↓
401
```

If authentication succeeds:

```text
Authentication
      ↓
Authorization
      ↓
Validation
      ↓
Controller
      ↓
Service
```

If validation fails:

```text
ValidationError
      ↓
400
```

If user doesn't exist:

```text
NotFoundError
      ↓
404
```

If the operation conflicts:

```text
ConflictError
      ↓
409
```

If an unexpected error occurs:

```text
Error
 ↓
500
```

Everything eventually converges:

```text
                     Error
                       │
                       ▼
             Central Error Middleware
                       │
                       ▼
                 HTTP Response
```

# 🧠 The Most Important Part

Don't memorize the class files.

Understand the **reasoning**:

```text
Something went wrong
        ↓
What kind of problem?
        ↓
┌─────────────────────────────────┐
│                                 │
│ Input problem       → 400       │
│ Not authenticated   → 401       │
│ Not allowed         → 403       │
│ Not found           → 404       │
│ Conflict            → 409       │
│ Unexpected failure  → 500       │
│                                 │
└─────────────────────────────────┘
```

Then:

```text
Specific Error
      ↓
AppError
      ↓
Central Error Middleware
      ↓
Consistent JSON response
```

Once this clicks, error handling becomes much less confusing.
