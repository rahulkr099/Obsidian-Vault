# Lesson 9.17 — Error Propagation: `throw` vs `next(error)`

In the previous lessons, we created a proper error hierarchy:

```text
AppError
├── BadRequestError
├── ValidationError
├── UnauthorizedError
├── ForbiddenError
├── NotFoundError
└── ConflictError
```

Now comes a very important question:

> **When should I use `throw new Error()` and when should I use `next(error)`?**

This becomes especially important once your backend has:

```text
Route
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
```

---

# 1. The Basic Idea

There are two different mechanisms:

### `throw`

Used to **create/propagate an error inside your application code**.

```js
throw new NotFoundError("User not found");
```

### `next(error)`

Used to **pass an error to Express's error-handling middleware**.

```js
next(error);
```

Think:

```text
throw
  ↓
JavaScript error flow

next(error)
  ↓
Express error flow
```

This distinction is the foundation of today's lesson.

---

# 2. Why This Gets Confusing

Suppose we have:

```text
Controller
   ↓
Service
   ↓
Repository
```

A beginner might write:

```js
throw new NotFoundError(...)
```

in the controller.

Then somewhere else:

```js
next(error)
```

And they wonder:

> "Which one should I use?"

The answer depends heavily on **which layer you're currently in**.

---

# 3. Controller Has Express Context

A controller usually looks like:

```js
const getUser = async (req, res, next) => {
    // ...
};
```

The controller has:

```text
req
res
next
```

So it can directly communicate with Express.

For example:

```js
return next(
    new NotFoundError("User not found")
);
```

This sends the error into Express's error pipeline.

---

# 4. Service Doesn't Need Express

A service should ideally look like:

```js
const getUserById = async (id) => {
    // business logic
};
```

Notice:

```text
No req
No res
No next
```

That's intentional.

The service should not know that Express exists.

So this would be bad:

```js
const getUserById = async (id, req, res, next) => {
    // ...
};
```

Now your service is tightly coupled to Express.

We don't want that.

---

# 5. Service Should `throw`

Suppose:

```js
const getUserById = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

Here we use:

```js
throw
```

not:

```js
next(...)
```

because the service shouldn't know about Express.

---

# 6. The Flow

Suppose:

```js
const getUser = async (req, res, next) => {
    const user = await userService.getUserById(req.params.id);

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Service:

```js
const getUserById = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

Flow:

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
No user
   ↓
throw NotFoundError
   ↓
Controller async function rejects
   ↓
Express error handling
   ↓
Central error middleware
```

But there is an important detail here.

---

# 7. Express Must Receive Async Errors

If your controller is:

```js
const getUser = async (req, res, next) => {
    const user = await userService.getUserById(req.params.id);

    // ...
};
```

and the service throws:

```js
throw new NotFoundError("User not found");
```

the error becomes a rejected Promise.

Your Express setup needs to properly propagate that rejected Promise to the error middleware.

Depending on your Express version/setup, this may happen automatically or you may use an async wrapper.

For a starter architecture, we'll make this explicit.

---

# 8. The `asyncHandler` Pattern

A common helper is:

```text
src/utils/asyncHandler.js
```

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};

export default asyncHandler;
```

This does something very useful:

```text
Promise rejection
       ↓
catch(next)
       ↓
Express error middleware
```

---

# 9. Why Do We Need This?

Without proper async handling:

```js
const controller = async (req, res) => {
    throw new Error("Something failed");
};
```

the error may become an unhandled/rejected Promise depending on the Express setup.

With:

```js
asyncHandler(controller)
```

we get:

```text
async error
   ↓
Promise rejection
   ↓
.catch(next)
   ↓
error middleware
```

---

# 10. Using `asyncHandler`

Suppose our controller is:

```js
const getUser = async (req, res) => {
    const user = await userService.getUserById(
        req.params.id
    );

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

Notice there is no:

```js
next
```

because the controller doesn't manually catch the service error.

Then the route:

```js
router.get(
    "/:id",
    asyncHandler(getUser)
);
```

Now:

```text
Controller throws
      ↓
asyncHandler catches rejection
      ↓
next(error)
      ↓
errorMiddleware
```

This gives us very clean controllers.

---

# 11. Controller vs Service

This gives us a very useful rule:

### Service

```js
throw new NotFoundError(...)
```

### Controller

Normally:

```js
return res.json(...)
```

and let `asyncHandler` deal with rejected Promises.

### Express middleware

Use:

```js
next(error)
```

when passing an error directly into Express.

---

# 12. Validation Middleware Is Different

Our validation middleware is synchronous:

```js
const validate = (schema, property = "body") => {
    return (req, res, next) => {
        const { error, value } = schema.validate(
            req[property]
        );

        if (error) {
            return next(
                new ValidationError(
                    "Validation failed"
                )
            );
        }

        req[property] = value;

        next();
    };
};
```

Here:

```js
next(error)
```

is perfectly appropriate.

Why?

Because this middleware is directly inside Express's middleware pipeline.

---

# 13. Authentication Middleware

Same idea.

Suppose:

```js
const authenticate = (req, res, next) => {
    const token = req.headers.authorization;

    if (!token) {
        return next(
            new UnauthorizedError()
        );
    }

    // ...
    next();
};
```

Again:

```js
next(error)
```

because this is Express middleware.

---

# 14. Authorization Middleware

Similarly:

```js
const authorize = (roles) => {
    return (req, res, next) => {
        if (!roles.includes(req.user.role)) {
            return next(
                new ForbiddenError()
            );
        }

        next();
    };
};
```

Again:

```text
Middleware
   ↓
next(error)
```

---

# 15. Repository Layer

Now let's go deeper.

Repository:

```js
const findById = async (id) => {
    return User.findById(id);
};
```

There is no:

```text
req
res
next
```

So if something meaningful happens:

```js
throw error;
```

or let the underlying error reject naturally.

For example:

```js
const findById = async (id) => {
    try {
        return await User.findById(id);
    } catch (error) {
        throw error;
    }
};
```

Although in this simple case, the `try/catch` isn't even necessary.

You can simply:

```js
const findById = (id) => {
    return User.findById(id);
};
```

The rejected Promise will travel upward.

---

# 16. Error Propagation Through Layers

Imagine:

```text
Repository
    ↓
throws DatabaseError
    ↓
Service
    ↓
doesn't catch it
    ↓
Controller
    ↓
asyncHandler
    ↓
next(error)
    ↓
Error Middleware
```

This is called **error propagation**.

You don't have to catch an error at every layer.

---

# 17. Don't Catch Just to Re-throw

A common beginner pattern:

```js
const getUser = async (id) => {
    try {
        const user = await repository.findById(id);

        if (!user) {
            throw new NotFoundError("User not found");
        }

        return user;
    } catch (error) {
        throw error;
    }
};
```

This accomplishes almost nothing.

You caught the error only to throw the same error again.

Prefer:

```js
const getUser = async (id) => {
    const user = await repository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

Much cleaner.

---

# 18. When Should You Catch an Error?

Catch an error when you actually want to **do something useful with it**.

For example:

```js
try {
    await paymentService.charge();
} catch (error) {
    logger.error(error);

    throw error;
}
```

Here you're adding logging.

Or:

```js
try {
    await repository.create(data);
} catch (error) {
    if (isDuplicateKeyError(error)) {
        throw new ConflictError(
            "Email already exists"
        );
    }

    throw error;
}
```

This is extremely useful.

You're translating a low-level database error into an application-level error.

---

# 19. Error Translation

This is an important architecture concept.

MongoDB might give you:

```text
E11000 duplicate key error
```

Your application shouldn't necessarily expose that.

Instead:

```text
MongoDB error
      ↓
Repository/service recognizes it
      ↓
ConflictError
      ↓
Central error middleware
      ↓
409
```

So:

```text
Technical error
      ↓
Application error
```

This is called **error translation**.

---

# 20. Example: Duplicate Email

Suppose:

```js
const createUser = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        if (error.code === 11000) {
            throw new ConflictError(
                "Email is already registered"
            );
        }

        throw error;
    }
};
```

Notice:

```js
throw new ConflictError(...)
```

not:

```js
next(...)
```

because this code is not Express middleware.

---

# 21. The Rule to Remember

Here's the simplest rule:

> **If the function knows about Express, `next(error)` is available. If it doesn't know about Express, throw the error.**

For example:

|Layer|Usually|
|---|---|
|Route middleware|`next(error)`|
|Validation middleware|`next(error)`|
|Authentication middleware|`next(error)`|
|Authorization middleware|`next(error)`|
|Controller|`throw` / async handler|
|Service|`throw`|
|Repository|`throw` / natural Promise rejection|
|Error middleware|handles `err`|

This is one of the most useful rules to remember.

---

# 22. Don't Put `next` in Services

Avoid:

```js
const createUser = async (data, next) => {
    try {
        // ...
    } catch (error) {
        next(error);
    }
};
```

This is bad because now your service depends on Express.

Instead:

```js
const createUser = async (data) => {
    try {
        // ...
    } catch (error) {
        throw error;
    }
};
```

Or even better, if no translation is needed:

```js
const createUser = async (data) => {
    return User.create(data);
};
```

---

# 23. Don't Put `res` in Services

Avoid:

```js
const getUser = async (id, res) => {
    const user = await repository.findById(id);

    if (!user) {
        return res.status(404).json({
            message: "User not found"
        });
    }

    return user;
};
```

This mixes:

```text
Business logic
+
HTTP response handling
```

Instead:

```js
const getUser = async (id) => {
    const user = await repository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

Now the service is reusable.

---

# 24. Why Reusability Matters

Suppose later you want:

```text
REST API
GraphQL API
Background job
CLI
Cron job
WebSocket
```

If your service contains:

```js
res.status(...)
```

it only works with Express HTTP.

But this:

```js
throw new NotFoundError(...)
```

works anywhere.

That's why keeping services framework-independent is valuable.

# 25. Controller With `asyncHandler`

Let's create:

```text
src/utils/asyncHandler.js
```

```js
            .resolve(handler(req, res, next))

```

Then:

```js

    return res.status(200).json({
        success: true,
        data: user
    });

```

Route:

```js

    "/:id",
    asyncHandler(getUser)
);
```

---

# 26. What `asyncHandler` Actually Does

Suppose:

```js
userService.getUserById()
```

throws:

```js
NotFoundError
```

The async controller returns a rejected Promise:

```text
Promise rejected
      ↓
asyncHandler
      ↓
.catch(next)
      ↓
next(error)
      ↓
errorMiddleware
```

This is the complete chain.

---

# 27. Another Approach: Try/Catch in Controller

You could instead write:

```js
const getUser = async (req, res, next) => {
    try {
        const user =
            await userService.getUserById(req.params.id);

        return res.status(200).json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

This works.

But imagine doing this in 30 controllers.

You'll repeat:

```js
try {
    ...
} catch (error) {
    next(error);
}
```

everywhere.

That's why `asyncHandler` is useful.

# 30. What About Synchronous Errors?

Suppose:

```js
const controller = (req, res) => {
    throw new BadRequestError("Invalid request");
};
```

`asyncHandler` also handles this because the handler executes inside:

```js
Promise.resolve(handler(...))
```

The synchronous throw happens during evaluation of `handler(...)`, so in a robust implementation you may prefer a `try/catch` wrapper:

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        try {
            Promise
                .resolve(handler(req, res, next))
                .catch(next);
        } catch (error) {
            next(error);
        }
    };
};
```

However, with a normal async function, rejected Promises are the main case we're handling.

The important concept is:

```text
asyncHandler → route errors → next(error)
```

---

# 31. Modern Express

If you're using a current Express version with native Promise rejection handling, explicit `asyncHandler` may not be necessary.

But there is still value in understanding the pattern because:

- many existing MERN projects use it
    
- many tutorials use it
    
- many codebases have custom wrappers
    
- understanding Promise error propagation is important
    

So don't memorize:

> "I must always use asyncHandler."

Instead understand:

> "Async errors must reach Express's error middleware."

That's the real concept.

# 35. A Very Important Concept: Error Ownership

Ask:

> "Which layer is responsible for understanding this error?"

For example:

### Joi error

Validation middleware understands it.

```text
Joi
 ↓
ValidationError
```

### Mongo duplicate-key error

Repository/data-access layer may understand the technical error.

```text
Mongo error
 ↓
ConflictError
```

### User doesn't exist

Service understands the business meaning.

```text
null
 ↓

```

### Authentication failure

Auth middleware understands it.

```text

 ↓
UnauthorizedError
```

This is excellent architecture.

# 36. Don't Translate Errors Unnecessarily

Suppose repository throws:

```js
throw new ConflictError(
    "Email already exists"
);
```

Service doesn't need:

```js
try {
   ...
} catch (error) {
   throw new ConflictError(error.message);
}
```

That's pointless.

Just let it propagate:

```text
Repository
   ↓
ConflictError
   ↓
Service
   ↓
Controller
   ↓
Error middleware
```

Only translate when you need to add meaning or hide technical details.

---

# 37. Error Propagation Is Not Error Handling Everywhere

This is a subtle but important difference.

You don't need:

```text
Repository → catch
Service → catch
Controller → catch
Middleware → catch
```

That's excessive.

Instead:

```text
Repository
   ↓
throw/reject
   ↓
Service
   ↓
throw/reject
   ↓
Controller
   ↓
asyncHandler
   ↓
central handler
```

Only catch where you have something useful to do.

---

# 38. Example of Useful Translation

Suppose MongoDB produces:

```text
E11000 duplicate key
```

You don't want that low-level message.

So:

```js
try {
    return await User.create(data);
} catch (error) {
    if (error.code === 11000) {
        throw new ConflictError(
            "Email is already registered"
        );
    }

    throw error;
}
```

Now:

```text
MongoDB
  ↓
technical error
  ↓
ConflictError
  ↓
409
```

That's useful error handling.

# 39. Example of Bad Translation

Don't do:

```js
try {
    return await User.create(data);
} catch (error) {
    throw new AppError(
        "Something went wrong",
        500
    );
}
```

for every error.

Why?

Because you just destroyed useful information.

A duplicate email should become:

```text
409 Conflict
```

not:

```text
500 Internal Server Error
```

# 41. `throw` vs `next(error)` Cheat Sheet

|Situation|Use|
|---|---|
|Service detects business error|`throw`|
|Repository needs to translate DB error|`throw`|
|Validation middleware fails|`next(error)`|
|Auth middleware fails|`next(error)`|
|Authorization middleware fails|`next(error)`|
|Controller manually handles Express error|`next(error)`|
|Async controller wrapped with `asyncHandler`|`throw` inside controller/service; wrapper calls `next`|
|Central error middleware|receives `err`|

The key principle:

> **Keep Express-specific behavior at the HTTP boundary.**

---

# 42. One More Important Thing: `return next(error)`

In middleware, you'll often see:

```js
return next(error);
```

instead of:

```js
next(error);
```

Why?

Because `return` stops the current function.

For example:

```js
if (!user) {
    return next(
        new NotFoundError("User not found")
    );
}

console.log("This won't execute");
```

Without `return`:

```js
if (!user) {
    next(new NotFoundError("User not found"));
}

console.log("This might still execute");
```

That can cause confusing behavior.

So in middleware:

```js
return next(error);
```

is a good habit.

---

# 43. Don't Do This

```js
if (!user) {
    next(new NotFoundError("User not found"));
}

return res.json({
    success: true,
    data: user
});
```

Now you potentially have:

```text
next(error)
+
response
```

for the same request.

That's bad.

Instead:

```js
if (!user) {
    return next(
        new NotFoundError("User not found")
    );
}

return res.json({
    success: true,
    data: user
});
```

---

# 44. Don't Send Two Responses

This error is common:

```text
Error [ERR_HTTP_HEADERS_SENT]
```

It usually means your code attempted to send multiple responses.

For example:

```js
next(error);

res.status(200).json(...);
```

Don't do this.

Once you've handed the error to Express:

```js
return next(error);
```

stop processing the request.

---

# 45. The Golden Rule

Remember these three lines:

### Express middleware

```js
return next(error);
```

### Service

```js
throw error;
```

### Central error middleware

```js
(err, req, res, next) => {
    // handle error
}
```

That's the core pattern.

```text
       ↓
next(error)
       ↓
Central error middleware
       ↓
400 response
```

That separation is what makes a backend architecture scalable.

## 🔑 Lesson 9.17 Takeaway

The most important rule from this lesson is:

```text
                 Does this layer know Express?
                         │
              ┌──────────┴──────────┐
              │                     │
             YES                    NO
              │                     │
              ▼                     ▼
        next(error)               throw
              │                     │
              └──────────┬──────────┘
                         ▼
                Central Error Handler
                         │
                         ▼
                   HTTP Response
```

And your application should ideally follow:

```text
Middleware
   → next(error)

Controller
   → mostly let errors propagate

Service
   → throw

Repository
   → throw / reject

Central Error Middleware
   → convert error → HTTP response
```
