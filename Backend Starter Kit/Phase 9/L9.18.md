# Lesson 9.18 — `asyncHandler` and Async Error Propagation in Express

In Lesson 9.17, we learned the most important rule:

```text
Express middleware → next(error)

Service / Repository → throw error
```

But there is one missing piece:

> **How does an error thrown inside an `async` controller actually reach our central error middleware?**

That's what we'll learn today.

---

# 1. The Problem

Consider this controller:

```js
const getUser = async (req, res) => {
    const user = await userService.getUserById(
        req.params.id
    );

    return res.json({
        success: true,
        data: user
    });
};
```

Our service:

```js
const getUserById = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

If the user doesn't exist:

```text
Service
   ↓
throw NotFoundError
   ↓
Promise rejected
```

Now the question is:

```text
How does that rejected Promise
reach errorMiddleware?
```

---

# 2. Normal Synchronous Error

First understand ordinary JavaScript.

```js
const test = () => {
    throw new Error("Something failed");
};

try {
    test();
} catch (error) {
    console.log(error.message);
}
```

Flow:

```text
test()
  ↓
throw
  ↓
catch
```

That's synchronous error handling.

---

# 3. Async Functions Are Different

Now:

```js
const test = async () => {
    throw new Error("Something failed");
};
```

Calling:

```js
test();
```

doesn't behave exactly like a normal synchronous function.

An `async` function always returns a Promise.

So:

```js
const result = test();
```

means:

```text
result → Promise
```

And because the function threw:

```text
Promise → rejected
```

---

# 4. Think in Terms of Promises

This:

```js
const test = async () => {
    throw new Error("Something failed");
};
```

is conceptually similar to:

```js
const test = () => {
    return Promise.reject(
        new Error("Something failed")
    );
};
```

So:

```text
async throw
   ↓
Rejected Promise
```

That's the key idea.

---

# 5. `try/catch` With `await`

You can catch the rejection with:

```js
try {
    await test();
} catch (error) {
    console.log(error);
}
```

Flow:

```text
async function
      ↓
Promise rejected
      ↓
await
      ↓
catch
```

So one solution is:

```js
const controller = async (req, res, next) => {
    try {
        const user = await service.getUser();

        res.json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

This works.

But there's a problem.

---

# 6. Repeating `try/catch`

Imagine 20 controllers:

```js
const createUser = async (req, res, next) => {
    try {
        // ...
    } catch (error) {
        next(error);
    }
};
```

```js
const getUser = async (req, res, next) => {
    try {
        // ...
    } catch (error) {
        next(error);
    }
};
```

```js
const updateUser = async (req, res, next) => {
    try {
        // ...
    } catch (error) {
        next(error);
    }
};
```

```js
const deleteUser = async (req, res, next) => {
    try {
        // ...
    } catch (error) {
        next(error);
    }
};
```

That's repetitive boilerplate.

This is where `asyncHandler` comes in.

---

# 7. What Is `asyncHandler`?

`asyncHandler` is a small wrapper that says:

> "Run this async controller, and if its Promise rejects, send the error to Express."

Conceptually:

```text
async controller
      ↓
asyncHandler
      ↓
Promise rejection
      ↓
next(error)
```

---

# 8. Basic `asyncHandler`

Create:

```text
src/utils/asyncHandler.js
```

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};

export default asyncHandler;
```

This tiny function is very powerful.

Let's understand every part.

---

# 9. `handler`

Here:

```js
const asyncHandler = (handler) => {
```

`handler` is the controller we're passing in.

For example:

```js
asyncHandler(getUser)
```

means:

```text
handler = getUser
```

---

# 10. Returning Middleware

We return:

```js
return (req, res, next) => {
```

That means `asyncHandler` itself produces an Express middleware.

So:

```js
asyncHandler(getUser)
```

becomes something conceptually like:

```js
(req, res, next) => {
    // run getUser
}
```

That's why we can use it in routes.

---

# 11. Calling the Controller

Inside:

```js
handler(req, res, next)
```

we execute the controller.

For example:

```js
getUser(req, res, next)
```

Because `getUser` is async, it returns a Promise.

---

# 12. `Promise.resolve()`

We use:

```js
Promise.resolve(
    handler(req, res, next)
)
```

This gives us a Promise that we can attach:

```js
.catch(...)
```

to.

So:

```js
Promise.resolve(handler(...))
```

means:

> "Treat the result as a Promise."

---

# 13. `.catch(next)`

This is the most important part:

```js
.catch(next);
```

It is basically:

```js
.catch((error) => {
    next(error);
});
```

So:

```js
.catch(next)
```

means:

```text
Promise rejected
      ↓
next(error)
      ↓
Express error middleware
```

---

# 14. Complete Flow

Suppose:

```js
const getUser = async (req, res) => {
    const user = await userService.getUserById(
        req.params.id
    );

    return res.json({
        success: true,
        data: user
    });
};
```

Route:

```js
router.get(
    "/:id",
    asyncHandler(getUser)
);
```

Service:

```js
const getUserById = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

Flow:

```text
GET /users/123
       ↓
asyncHandler
       ↓
getUser()
       ↓
service
       ↓
repository
       ↓
user doesn't exist
       ↓
throw NotFoundError
       ↓
Promise rejected
       ↓
.catch(next)
       ↓
next(NotFoundError)
       ↓
errorMiddleware
       ↓
404 response
```

That's the entire concept.

---

# 15. Why the Service Can `throw`

Remember:

```js
const getUserById = async (id) => {
    if (!user) {
        throw new NotFoundError("User not found");
    }
};
```

The service doesn't know anything about:

```text
Express
req
res
next
```

It simply says:

> "This operation failed because the user doesn't exist."

Then the error travels upward.

---

# 16. Why the Controller Doesn't Need `try/catch`

Without `asyncHandler`:

```js
const getUser = async (req, res, next) => {
    try {
        const user = await service.getUserById(
            req.params.id
        );

        res.json({
            success: true,
            data: user
        });
    } catch (error) {
        next(error);
    }
};
```

With `asyncHandler`:

```js
const getUser = async (req, res) => {
    const user = await service.getUserById(
        req.params.id
    );

    res.json({
        success: true,
        data: user
    });
};
```

Route:

```js
router.get(
    "/:id",
    asyncHandler(getUser)
);
```

The second approach keeps your controller focused on the actual request logic.

---

# 17. The Controller Becomes Easier to Read

Without wrapper:

```text
try
 ├── business logic
 ├── response
catch
 └── next(error)
```

With wrapper:

```text
controller
 ├── business logic
 └── response
```

Error propagation becomes infrastructure.

That's a good separation.

---

# 18. A More Robust `asyncHandler`

For learning, you can understand this version:

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};
```

Another version commonly seen is:

```js
const asyncHandler = (handler) => {
    return async (req, res, next) => {
        try {
            await handler(req, res, next);
        } catch (error) {
            next(error);
        }
    };
};
```

Both express the same core idea:

```text
run async handler
       ↓
catch rejected error
       ↓
next(error)
```

For our architecture, either approach is understandable.

---

# 19. Which Version Should You Use?

I recommend starting with:

```js
const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};
```

It's short and clearly demonstrates Promise error propagation.

Later, you can choose whichever style your team/project prefers.

---

# 20. Express Version Matters

Modern Express versions have improved Promise error handling.

If you're using a recent Express version, rejected Promises from route handlers can be forwarded to the error middleware automatically.

That means:

```js
router.get("/:id", async (req, res) => {
    throw new Error("Failed");
});
```

can reach:

```js
app.use(errorMiddleware);
```

without manually writing an `asyncHandler`.

But you should still understand `asyncHandler` because:

- many existing projects use it
    
- older Express projects need it
    
- codebases often have custom wrappers
    
- it makes the error flow explicit
    
- it is common in MERN starter architectures
    

The important thing is the concept, not blindly adding wrappers everywhere.

---

# 21. Don't Double-Wrap Everything

If your Express setup already handles async errors correctly, don't create unnecessary layers like:

```js
router.get(
    "/users",
    asyncHandler(
        asyncHandler(
            getUsers
        )
    )
);
```

Obviously, this is unnecessary.

You want one clear error propagation strategy.

---

# 22. Don't Mix Multiple Strategies Randomly

Avoid having:

```text
Controller A
→ try/catch

Controller B
→ asyncHandler

Controller C
→ no handling

Controller D
→ custom promise wrapper
```

This makes the codebase difficult to understand.

Choose one consistent strategy.

For our starter architecture:

```text
Express middleware
→ next(error)

Async controllers
→ asyncHandler

Services
→ throw

Repositories
→ throw/reject

Central handler
→ format response
```

That's a clean strategy.

---

# 23. `asyncHandler` Does Not Handle Business Logic

This is important.

Don't put business logic inside:

```js
asyncHandler(...)
```

For example, don't do:

```js
router.get(
    "/:id",
    asyncHandler(async (req, res) => {
        // 100 lines of business logic
    })
);
```

for a large application.

Instead:

```text
Route
 ↓
Controller
 ↓
Service
```

Use `asyncHandler` only as an error-propagation wrapper.

```js

Nice and readable.

```

Notice what isn't here:

```text

database code
Joi validation
```

That's intentional.

# 26. Service Example

```js
const getUserById = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new NotFoundError("User not found");
    }

    return user;
};
```

The service owns the business condition:

```text
"No user exists."
```

So it throws the appropriate application error.

---

# 27. Repository Example

```js
const findById = async (id) => {
    return User.findById(id);
};
```

The repository simply handles data access.

If MongoDB fails:

```text
MongoDB error
 ↓
Promise rejection
 ↓
Service
 ↓
Controller
 ↓
asyncHandler
 ↓
error middleware
```

Unless you need to translate the error.

---

# 28. Translating Repository Errors

For example:

```js
const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        if (error.code === 11000) {
            throw new ConflictError(
                "Email already exists"
            );
        }

        throw error;
    }
};
```

Notice the two paths:

```text
Duplicate key
   ↓
ConflictError
```

and:

```text
Anything else
   ↓
throw original error
```

Don't hide unexpected errors.

---

# 29. Why `throw error` Matters

Suppose:

```js
try {
    return await User.create(data);
} catch (error) {
    if (error.code === 11000) {
        throw new ConflictError(
            "Email already exists"
        );
    }

    throw error;
}
```

The final:

```js
throw error;
```

means:

> "I don't know how to meaningfully handle this error here. Let the centralized system handle it."

That's a very useful pattern.

---

# 30. Error Propagation Is Like Passing a Package Upward

Imagine:

```text
Repository
   ↓
"Here is an error."
   ↓
Service
   ↓
"I understand this one."
   ↓
ConflictError
   ↓
Controller
   ↓
asyncHandler
   ↓
Express
   ↓
Error middleware
```

Each layer only needs to act when it has something meaningful to add.

---

# 31. `next(error)` Is Not a Replacement for `throw`

Don't write this in a service:

```js
const getUser = async (id, next) => {
    if (!user) {
        next(
            new NotFoundError("User not found")
        );
    }
};
```

Why?

Because the service now depends on:

```text
Express
```

That's exactly what we want to avoid.

Use:

```js
throw new NotFoundError("User not found");
```

---

# 32. Middleware Is Different

Middleware is part of Express.

Therefore:

```js
const authenticate = (req, res, next) => {
    if (!token) {
        return next(
            new UnauthorizedError()
        );
    }

    next();
};
```

Here `next` is appropriate.

The middleware's job includes interacting with Express's request pipeline.

---

# 33. Error Middleware Is the Final Destination

Eventually:

```js
app.use(errorMiddleware);
```

receives:

```js
err
```

Our handler:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    return res.status(statusCode).json({
        success: false,
        message: err.isOperational
            ? err.message
            : "Internal server error"
    });
};
```

This is where the application finally converts:

```text
JavaScript error
```

into:

```text
HTTP response
```

# 35. One Important Edge Case

Suppose a controller does:

```js
const controller = async (req, res) => {
    await something();

    res.json({
        success: true
    });

    throw new Error("Oops");
};
```

Don't do this.

You've already sent the response:

```text
res.json()
```

and then you're throwing an error.

Now your error middleware may try to send another response.

You can get:

```text
ERR_HTTP_HEADERS_SENT
```

Always make sure your request has one clear outcome.

---

# 36. Another Common Mistake

Don't do:

```js
try {
    const user = await service.getUser();
} catch (error) {
    console.log(error);
}

return res.json({
    success: true,
    data: user
});
```

You've swallowed the error.

If the service fails, your application continues as though everything succeeded.

Instead:

```js
try {
    const user = await service.getUser();
} catch (error) {
    throw error;
}
```

or, if you're at the Express boundary:

```js
catch (error) {
    return next(error);
}
```

---

# 37. Error Swallowing

This is called **swallowing an error**:

```js
try {
    await something();
} catch (error) {
    console.log(error);
}
```

The error happened, but you didn't:

```text
throw it
```

or:

```text
next(error)
```

So the rest of the application may not know anything went wrong.

Avoid this unless you intentionally handled the failure.

---

# 38. Logging Is Not Handling

This is another important distinction.

```js
catch (error) {
    console.error(error);
}
```

doesn't mean the error was handled.

Logging merely records it.

If the operation should still fail:

```js
catch (error) {
    console.error(error);
    throw error;
}
```

Now you've:

```text
logged
+
propagated
```

That's often correct.

---

# 39. When Should You Actually Recover?

Sometimes an error can be handled locally.

For example:

```js
try {
    const cacheValue = await cache.get(key);
    return cacheValue;
} catch (error) {
    console.warn("Cache unavailable");
    return null;
}
```

Here you're intentionally deciding:

> "Cache failure should not fail the entire request."

That's a valid reason to catch and not rethrow.

The important thing is:

> **Catch only when you have a deliberate recovery strategy.**

---

# 40. The Three Error Decisions

Whenever you catch an error, ask:

### 1. Can I recover?

```text
YES
 ↓
handle it
```

### 2. Can I translate it?

```text
YES
 ↓
throw appropriate AppError
```

### 3. Neither?

```text
throw error
```

This is a very useful rule.

# 🧠 What You Should Remember

Don't memorize the implementation of `asyncHandler`.

Understand this:

```text
async function
     ↓
returns Promise
     ↓
Promise rejects when async code throws
     ↓
asyncHandler catches rejection
     ↓
next(error)
     ↓
Express error middleware
```

And remember the layer rule:

```text
┌───────────────────────────────┐
│ Middleware                    │
│ → next(error)                 │
├───────────────────────────────┤
│ Controller                    │
│ → asyncHandler catches errors │
├───────────────────────────────┤
│ Service                       │
│ → throw                       │
├───────────────────────────────┤
│ Repository                    │
│ → throw / reject              │
├───────────────────────────────┤
│ Error Middleware              │
│ → create HTTP response        │
└───────────────────────────────┘
```

# 🔑 Lesson 9.18 Takeaway

The most important concept is **error propagation, not `asyncHandler` itself**.

A clean MERN backend should allow an error to travel naturally:

```text
Repository
    ↓
throw / Promise rejection
    ↓
Service
    ↓
throw / propagate
    ↓
Controller
    ↓
asyncHandler
    ↓
next(error)
    ↓
Central Error Middleware
    ↓
HTTP Response
```

Once you understand this flow, you won't feel the need to put `try/catch` everywhere.
