# Lesson 9.19 — Production-Quality Error Middleware

In Lesson 9.18, we learned how an error travels through the application:

```text
Repository
   ↓
throw / reject
   ↓
Service
   ↓
Controller
   ↓
asyncHandler
   ↓
next(error)
   ↓
Error Middleware
   ↓
HTTP Response
```

Today we are going to build the **final destination** of that pipeline:

> **A production-quality centralized error middleware.**

This is one of the most important pieces of a real backend.

---

# 1. Why Do We Need Central Error Middleware?

Imagine you have 50 endpoints.

Without centralized error handling, you might have:

```js
res.status(404).json(...)
```

in one controller,

```js
res.status(400).json(...)
```

in another,

```js
res.status(500).json(...)
```

somewhere else.

Your API responses could become inconsistent.

For example:

### Endpoint A

```json
{
    "message": "User not found"
}
```

### Endpoint B

```json
{
    "error": "Product not found"
}
```

### Endpoint C

```json
{
    "success": false,
    "message": "Something went wrong"
}
```

This becomes difficult for frontend developers.

Instead, we want:

```text
Any error
   ↓
One central middleware
   ↓
One response format
```

---

# 2. The Central Error Middleware

Create:

```text
src/middlewares/error.middleware.js
```

Basic version:

```js
const errorMiddleware = (err, req, res, next) => {
    const statusCode = err.statusCode || 500;

    return res.status(statusCode).json({
        success: false,
        message: err.message || "Internal server error"
    });
};

export default errorMiddleware;
```

Notice the four arguments:

```js
(err, req, res, next)
```

That is important.

---

# 3. Why Four Arguments?

Normal middleware:

```js
(req, res, next)
```

Error middleware:

```js
(err, req, res, next)
```

Express recognizes the four-argument signature as an error-handling middleware.

So:

```js
const errorMiddleware = (
    err,
    req,
    res,
    next
) => {
    // ...
};
```

means:

> "This middleware handles errors."

---

# 4. Where Should It Be Registered?

This is extremely important.

Your application might have:

```js
app.use("/api/users", userRoutes);
app.use("/api/products", productRoutes);
```

Then:

```js
app.use(errorMiddleware);
```

The error middleware should come **after your routes and other middleware that can generate errors**.

For example:

```js
app.use("/api/users", userRoutes);
app.use("/api/products", productRoutes);

app.use(notFoundMiddleware);
app.use(errorMiddleware);
```

The exact order will matter when we build the full request pipeline.

---

# 5. Error Middleware Is the Final Translator

Your application deals with JavaScript errors:

```js
throw new NotFoundError("User not found");
```

But the client doesn't understand JavaScript errors.

The client needs:

```http
404
```

and:

```json
{
    "success": false,
    "message": "User not found"
}
```

So the error middleware performs:

```text
Application Error
       ↓
HTTP Response
```

This is its primary responsibility.

---

# 6. The Problem With Returning `err.message`

Consider:

```js
throw new Error(
    "MongoDB connection failed at 192.168.1.20"
);
```

If you blindly send:

```js
message: err.message
```

the client may receive:

```json
{
    "success": false,
    "message": "MongoDB connection failed at 192.168.1.20"
}
```

That could reveal internal information.

Even worse:

```js
throw new Error(
    "Mongo query failed: mongodb://admin:password@..."
);
```

You absolutely don't want credentials or internal infrastructure details sent to users.

So production error handling needs another concept:

> **Operational errors vs unexpected errors.**

---

# 7. Operational Errors

An operational error is an error that we expect can happen during normal application operation.

Examples:

```text
User doesn't exist
Invalid password
Invalid input
Email already registered
Insufficient permissions
Resource not found
```

These aren't necessarily programming bugs.

For example:

```js
throw new NotFoundError(
    "User not found"
);
```

That's an expected application condition.

We can safely communicate an appropriate message to the client.

---

# 8. Unexpected Errors

Unexpected errors are different.

Examples:

```text
Programming bug
Unexpected database failure
Undefined variable
Broken dependency
Invalid internal state
Unexpected configuration problem
```

For example:

```js
const user = undefined;

console.log(user.name);
```

This might produce:

```text
TypeError: Cannot read properties of undefined
```

You don't want to expose that raw message to users.

Instead:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

---

# 9. Why Hide Unexpected Errors?

Suppose your API responds:

```json
{
    "success": false,
    "message": "Cannot read properties of undefined (reading 'password')"
}
```

Now an attacker knows:

- your runtime is JavaScript
    
- an internal variable is undefined
    
- the code accesses `password`
    
- potentially useful implementation details
    

Errors can accidentally become an information leak.

So:

```text
Operational error
→ safe known message

Unexpected error
→ generic message
```

---

# 10. Our `AppError`

Earlier we created an application error hierarchy.

For example:

```js
class AppError extends Error {
    constructor(
        message,
        statusCode,
        options = {}
    ) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational =
            options.isOperational ?? true;

        Error.captureStackTrace(
            this,
            this.constructor
        );
    }
}
```

Now we can distinguish:

```js
err.isOperational
```

from:

```text
unexpected JavaScript error
```

---

```js

    "User not found"
);
```

might produce:

```js
{
    message: "User not found",
    statusCode: 404,
    isOperational: true
}
```

But:

```js

    "Something broke internally"

```


So the middleware can tell the difference.

# 12. Basic Production Logic

Conceptually:

```js
const errorMiddleware = (err, req, res, next) => {
    if (err.isOperational) {
        // Safe, expected error
    } else {
        // Unexpected error
    }
};
```

This distinction is extremely useful.

There is another important distinction.

During development, you want:

```text

```

During production, you want:

```text

No internal implementation details
```

So:

```text

    ↓

production
    ↓
safe details only
```

# 16. Don't Send Stack Traces to Users

Avoid:

```js

    success: false,
```

# 17. Logging vs Response

This distinction is very important.

When an unexpected error occurs:

```text
                    ERROR
                      │
            ┌─────────┴─────────┐
            │                   │
            ▼                   ▼
          Logs              HTTP response
            │                   │
            ▼                   ▼
       detailed info      safe message
```

So developers can debug the problem without exposing the details to users.

# 18. A Better Error Middleware

Let's build a development/production-aware version:

```js
const errorMiddleware = (err, req, res, next) => {
    const isProduction =
        process.env.NODE_ENV === "production";

    const statusCode =
        err.statusCode || 500;

    const message =
        err.isOperational
            ? err.message
            : "Internal server error";

    const response = {
        success: false,
        message
    };

    if (!isProduction) {
        response.stack = err.stack;
    }

    return res.status(statusCode).json(response);
};

export default errorMiddleware;
```

This is much safer.

# 26. Error Codes

A useful future improvement is adding an application-level error code.

For example:

```json
{
    "success": false,
    "message": "User not found",
    "code": "USER_NOT_FOUND"
}
```

Or:

```json
{
    "success": false,
    "message": "Email already exists",
    "code": "EMAIL_ALREADY_EXISTS"
}
```

Why?

Because frontend code shouldn't always depend on English text.

Bad:

```js
if (message === "User not found") {
    // ...
}
```

Better:

```js
if (code === "USER_NOT_FOUND") {
    // ...
}
```

We will explore this more when we build API response standards.

# 33. The Error Middleware Should Stay Thin

Don't put this inside error middleware:

```text
Database queries
Email sending
Business logic
User creation
Complex authentication
```

Its job should be:

```text
1. Receive error
2. Determine error type
3. Log appropriately
4. Determine status code
5. Create safe response
6. Send response
```

That's it.

# 34. A Cleaner Implementation

Let's create a helper:

```js
const normalizeError = (err) => {
    return {
        statusCode: err.statusCode || 500,
        message: err.isOperational
            ? err.message
            : "Internal server error",
        isOperational: err.isOperational === true
    };
};
```

Then:

```js
const errorMiddleware = (
    err,
    req,
    res,
    next
) => {
    const normalized = normalizeError(err);

    if (!normalized.isOperational) {
        console.error(err);
    }

    return res
        .status(normalized.statusCode)
        .json({
            success: false,
            message: normalized.message
        });
};
```

This is easier to extend later.

---

# 35. What Does "Normalize" Mean?

Normalization means:

> Take different kinds of errors and convert them into one predictable internal shape.

For example:

### Error A

```js
new NotFoundError("User not found")
```

### Error B

```js
new Error("Database failed")
```

### Error C

```js
someThirdPartyLibraryError
```

Normalize them into:

```js
{
    statusCode,
    message,
    isOperational
}
```

Then the rest of the system becomes easier.

---

# 36. Unexpected Errors Should Usually Become 500

Suppose:

```js
throw new TypeError(
    "Cannot read properties of undefined"
);
```

We don't want:

```http
400
```

or:

```http
404
```

We want:

```http
500
```

because the server failed unexpectedly.

So:

```js
const statusCode = err.statusCode || 500;
```

is a useful fallback.

---

# 37. But Be Careful With `statusCode`

Don't trust arbitrary errors to contain a valid HTTP status code.

Someone could theoretically do:

```js
throw {
    statusCode: 99999
};
```

Your middleware shouldn't blindly send invalid values.

A more defensive approach:

```js
const isValidStatusCode = (statusCode) => {
    return Number.isInteger(statusCode) &&
        statusCode >= 400 &&
        statusCode <= 599;
};
```

Then:

```js
const statusCode = isValidStatusCode(err.statusCode)
    ? err.statusCode
    : 500;
```

This is a nice production improvement.

---

# 38. Production-Ready Basic Version

A good version for our starter architecture:

```js
const isValidStatusCode = (statusCode) => {
    return (
        Number.isInteger(statusCode) &&
        statusCode >= 400 &&
        statusCode <= 599
    );
};

const errorMiddleware = (err, req, res, next) => {
    const statusCode = isValidStatusCode(err.statusCode)
        ? err.statusCode
        : 500;

    const isOperational =
        err.isOperational === true;

    if (!isOperational) {
        console.error(err);
    }

    const message = isOperational
        ? err.message
        : "Internal server error";

    return res.status(statusCode).json({
        success: false,
        message
    });
};

export default errorMiddleware;
```

This is already much better than:

```js
res.status(500).json({
    message: err.message
});
```

# 41. A Common Mistake

Don't do:

```js

    return res.status(500).json({
        success: false,
        message: err.message,
        stack: err.stack
    });

```

Why is this bad?

Because:

```text
NotFoundError
→ always 500
```

and:

```text
Unexpected error
→ internal details leaked
```

and:

```text
Database error
→ raw database information leaked
```

Everything gets mixed together.

# 42. Another Common Mistake

Don't expose:

```js
err
```

directly:

```js
res.json(err);
```

Errors can contain:

```text
stack
cause
internal properties
database details
library-specific fields
```

Instead, deliberately construct your response:

```js
res.json({
    success: false,
    message: safeMessage
});
```

This gives you control over what leaves the server.

# 43. Error Middleware Doesn't Mean Every Error Is Safe

Even an `AppError` can contain sensitive information if you create it incorrectly.

Bad:

```js
throw new BadRequestError(
    `Password ${password} is invalid`
);
```

Now you're putting a secret into the error message.

Better:

```js
throw new BadRequestError(
    "Invalid credentials"
);
```

So security starts when you create the error, not only inside the error middleware.

# 47. What About `next` in Error Middleware?

You may wonder:

```js
(err, req, res, next)
```

Why do we still have:

```js
next
```

Sometimes an error middleware may decide:

> "I can't handle this error; let another error middleware handle it."

Then:

```js
next(err);
```

can pass the error onward.

For our main centralized middleware, we generally won't need to do this often.

But it's part of Express's error middleware API.

# 50. Full Example

Let's put everything together.

### `errors/AppError.js`

```js
class AppError extends Error {
    constructor(message, statusCode) {
        super(message);

        this.statusCode = statusCode;
        this.isOperational = true;

        Error.captureStackTrace(
            this,
            this.constructor
        );
    }
}

export default AppError;
```

---

### `errors/NotFoundError.js`

```js
import AppError from "./AppError.js";

class NotFoundError extends AppError {
    constructor(message = "Resource not found") {
        super(message, 404);
    }
}

export default NotFoundError;
```

---

### Service

```js
const getUserById = async (id) => {
    const user = await userRepository.findById(id);

    if (!user) {
        throw new NotFoundError(
            "User not found"
        );
    }

    return user;
};
```

---

### Controller

```js
const getUser = async (req, res) => {
    const user =
        await userService.getUserById(
            req.params.id
        );

    return res.status(200).json({
        success: true,
        data: user
    });
};
```

---

### Route

```js
router.get(
    "/:id",
    asyncHandler(getUser)
);
```

---

### Error Middleware

```js
const errorMiddleware = (
    err,
    req,
    res,
    next
) => {
    const statusCode =
        Number.isInteger(err.statusCode) &&
        err.statusCode >= 400 &&
        err.statusCode <= 599
            ? err.statusCode
            : 500;

    const isOperational =
        err.isOperational === true;

    if (!isOperational) {
        console.error(err);
    }

    return res.status(statusCode).json({
        success: false,
        message: isOperational
            ? err.message
            : "Internal server error"
    });
};
```

# 52. The Most Important Production Rule

Here's the rule I want you to remember:

> **Never let an unexpected internal error decide what the client should see.**

Instead:

```text
Unexpected error
      ↓
Log detailed information
      ↓
Return generic safe message
```

For example:

```text
Server logs:
TypeError...
file...
line...
stack...

Client:
"Internal server error"
```

This separation is extremely important in production.

# 53. Your Error Middleware Checklist

Before considering your middleware complete, check:

```text
✓ Four arguments: err, req, res, next
✓ Handles AppError
✓ Defaults unknown errors to 500
✓ Distinguishes operational errors
✓ Doesn't expose stack traces in production
✓ Doesn't expose database details
✓ Doesn't expose secrets
✓ Uses consistent JSON format
✓ Logs unexpected errors
✓ Validates status codes
✓ Is registered after routes
```

If these are true, you're on the right track.

# 🧠 Final Mental Model

Think of the error middleware as a **security boundary**:

```text
                 INTERNAL WORLD
                       │
        ┌──────────────┼──────────────┐
        │              │              │
    Database        Services       Libraries
        │              │              │
        └──────────────┼──────────────┘
                       │
                    Errors
                       │
                       ▼
              Error Middleware
                       │
              ┌────────┴────────┐
              │                 │
          Operational       Unexpected
              │                 │
              ▼                 ▼
        Safe message       Log details
              │                 │
              ▼                 ▼
            Client          Safe generic
                              response
```

The goal isn't simply:

> "Catch errors."

The goal is:

> **Catch, classify, log, sanitize, and consistently respond to errors.**

That is what turns basic error handling into **production-quality error handling**.

Your centralized error middleware should follow this logic:

```text

     ↓
Is it operational?
     ↓

 ↓                      ↓
```

```text
                      │

                 to clients
```
