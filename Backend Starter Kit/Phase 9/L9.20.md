# Lesson 9.20 — Building the Complete Error-Handling System

This is the **final lesson of Phase 9's error-handling section**.

Until now, we've built the pieces separately:

```text
9.18 → asyncHandler
9.19 → production error middleware
```

Now we're going to connect everything into **one complete system**.

The goal is that when something goes wrong anywhere in your backend, you understand exactly:

```text
WHERE the error is created
→ HOW it travels
→ WHO handles it
→ WHAT the client receives
```

---

# 1. The Complete Architecture

Our final error architecture will look like this:

```text
                    HTTP REQUEST
                         │
                         ▼
                       ROUTE
                         │
                         ▼
                   Middleware
                         │
              ┌──────────┴──────────┐
              │                     │
           success                 error
              │                     │
              ▼                     ▼
         Controller              next(error)
              │                     │
              ▼                     │
           Service                  │
              │                     │
              ▼                     │
         Repository                 │
              │                     │
          ┌───┴───┐                 │
          │       │                 │
       success   error              │
          │       │                 │
          │       ▼                 │
          │     throw               │
          │       │                 │
          └───────┴─────────────────┘
                  │
                  ▼
             asyncHandler
                  │
                  ▼
             next(error)
                  │
                  ▼
          Error Middleware
                  │
          ┌───────┴────────┐
          │                │
      Operational       Unexpected
          │                │
          ▼                ▼
      Safe message     Log details
          │                │
          └───────┬────────┘
                  ▼

```

This is the mental model you should carry into your future projects.

# 3. `AppError` — The Foundation

Start with:

```js
// errors/AppError.js

class AppError extends Error {
    constructor(message, statusCode, options = {}) {
        super(message);

        this.statusCode = statusCode;

        this.isOperational =
            options.isOperational ?? true;

        Error.captureStackTrace(
            this,
            this.constructor
        );
    }
}

export default AppError;
```

Now we have a common application error.

---

# 4. Why `AppError`?

Instead of doing:

```js
throw new Error("User not found");
```

we can do:

```js
throw new NotFoundError("User not found");
```

The error now carries useful information:

```js
{
    message: "User not found",
    statusCode: 404,
    isOperational: true
}
```

The error middleware can understand this.

# 12. `asyncHandler`

Now create:

```js
// utils/asyncHandler.js

const asyncHandler = (handler) => {
    return (req, res, next) => {
        Promise
            .resolve(handler(req, res, next))
            .catch(next);
    };
};

export default asyncHandler;
```

Its responsibility is very small:

> Catch rejected Promises and send the error into Express.

That's it.

# 19. Error Middleware

Now let's build the final piece.

```js
// middlewares/error.middleware.js

const isValidStatusCode = (statusCode) => {
    return (
        Number.isInteger(statusCode) &&
        statusCode >= 400 &&
        statusCode <= 599
    );
};

const errorMiddleware = (
    err,
    req,
    res,
    next
) => {
    const statusCode = isValidStatusCode(
        err.statusCode
    )
        ? err.statusCode
        : 500;

    const isOperational =
        err.isOperational === true;

    if (!isOperational) {
        console.error(err);
    }

    const message = isOperational
        ? err.message
        : "Internal server error";

    return res.status(statusCode).json({
        success: false,
        message
    });
};

export default errorMiddleware;
```

# 22. 404 Middleware

Create:

```js
// middlewares/notFound.middleware.js

import NotFoundError from "../errors/NotFoundError.js";

const notFoundMiddleware = (req, res, next) => {
    next(
        new NotFoundError(
            `Route not found: ${req.method} ${req.originalUrl}`
        )
    );
};

export default notFoundMiddleware;
```

Now an unknown route becomes an application error.

---

# 23. Middleware Order

This is extremely important.

Use:

```js
app.use(express.json());

app.use("/api/users", userRoutes);
app.use("/api/products", productRoutes);

// Unknown routes
app.use(notFoundMiddleware);

// Errors
app.use(errorMiddleware);
```

Think:

```text
Request
   ↓
Normal middleware
   ↓
Routes
   ↓
Did a route handle it?
   │
   ├── YES → response
   │
   └── NO
        ↓
  notFoundMiddleware
        ↓
    next(error)
        ↓
  errorMiddleware
        ↓
     response
```

---

# 24. Why `notFoundMiddleware` Comes Before `errorMiddleware`

Suppose:

```text
GET /api/unknown
```

No route handles it.

Then:

```text
notFoundMiddleware
```

creates:

```js
new NotFoundError(...)
```

and calls:

```js
next(error)
```

Express then looks for an error middleware:

```text
errorMiddleware
```

Therefore:

```text
notFound
   ↓
error
```

not:

```text
error
   ↓
notFound
```


```text

```

```text

   ↓

   ↓

   ↓

   ↓
```


# 29. The Difference Between These Two

### Expected application failure

```js
throw new NotFoundError(
    "User not found"
);
```

Client:

```json
{
    "success": false,
    "message": "User not found"
}
```

### Unexpected programming failure

```js
throw new TypeError(
    "Cannot read properties..."
);
```

Client:

```json
{
    "success": false,
    "message": "Internal server error"
}
```

Server:

```text
TypeError: Cannot read properties...
    at ...
    at ...
```

This distinction is the heart of production error handling.

# 30. Database Error Translation

Now let's connect this to the repository.

Suppose MongoDB produces duplicate-key error:

```text
E11000 duplicate key
```

We don't want:

```json
{
    "message": "E11000 duplicate key error..."
}
```

Instead:

```js
import ConflictError
    from "../errors/ConflictError.js";

const create = async (data) => {
    try {
        return await User.create(data);
    } catch (error) {
        if (error.code === 11000) {
            throw new ConflictError(
                "Email already exists"
            );
        }

        throw error;
    }
};
```

Now:

```text
MongoDB
  ↓
E11000
  ↓
ConflictError
  ↓
409
```

Response:

```json
{
    "success": false,
    "message": "Email already exists"
}
```

---

# 31. Why Translate Errors?

Because your API shouldn't be tightly coupled to MongoDB's error format.

Imagine you later move from:

```text
MongoDB
```

to:

```text
PostgreSQL
```

Your API should still be able to return:

```json
{
    "success": false,
    "message": "Email already exists"
}
```

The database implementation can change without changing your API contract.

This is one of the benefits of layering.

# 35. The Layer Rules

Let's make this extremely clear.

### Route

```text
Connect URL → Controller
```

### Middleware

```text
Check request
→ next()
or
→ next(error)
```

### Controller

```text
HTTP concerns
→ call service
→ return response
```

### Service

```text
Business logic
→ throw errors
```

### Repository

```text
Database
→ return data
→ throw/reject on failure
```

### `asyncHandler`

```text
Promise rejection
→ next(error)
```

### Error Middleware

```text
Error
→ log
→ classify
→ HTTP response
```

This separation will make your backend much easier to maintain.

# 36. One Big Anti-Pattern

Don't do this:

```js
const controller = async (req, res) => {
    try {
        const user = await User.findById(req.params.id);

        if (!user) {
            return res.status(404).json({
                success: false,
                message: "User not found"
            });
        }

        res.json({
            success: true,
            data: user
        });
    } catch (error) {
        return res.status(500).json({
            success: false,
            message: error.message
        });
    }
};
```

Why is this bad for our architecture?

The controller now knows:

```text
MongoDB
business logic
HTTP status mapping
error formatting
error security
```

Everything is mixed together.

# 42. Don't Put Sensitive Data in Errors

Never put things like:

```text
Passwords
JWT secrets
Database URLs
API keys
Access tokens
Private keys
Internal credentials
```

into error messages.

Bad:

```js
throw new Error(
    `Invalid password: ${password}`
);
```

Good:

```js
throw new UnauthorizedError(
    "Invalid credentials"
);
```

Remember:

> An error message can end up in logs, monitoring systems, and API responses.

Treat it accordingly.

# 🧠 Phase 9 Error Handling — Final Mental Model

```text
                         REQUEST

                            ▼
                         ROUTE
                            │
                            ▼
                       MIDDLEWARE

                 ┌──────────┴──────────┐

               next()             next(error)
                 │                     │
                 ▼                     │
            CONTROLLER                 │
                 │                     │
                 ▼                     │
              SERVICE                 │
                 │                     │
                 ▼                     │
            REPOSITORY                │
                 │                     │

                            │
                            ▼
                       asyncHandler
                            │
                            ▼
                       next(error)
                            │
                            ▼
                   ERROR MIDDLEWARE
                            │
                 ┌──────────┴──────────┐
                 │                     │
           Operational             Unexpected
                 │                     │
                 ▼                     ▼
          Safe client msg         Log details
                 │                     │
                 └──────────┬──────────┘
                            ▼
                       HTTP RESPONSE
```

## 🔑 The five rules

1. **Middleware uses `next(error)`.**
    
2. **Services throw application errors.**
    
3. **Controllers stay focused on HTTP concerns.**
    
4. **`asyncHandler` forwards rejected Promises.**
    
5. **Error middleware is the final security boundary between your server and client.**
    

Once these rules become natural to you, the "hard" backend architecture you've been learning starts becoming much easier to reason about.
