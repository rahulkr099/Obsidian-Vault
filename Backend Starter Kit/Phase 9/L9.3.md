# Lesson 9.3 — Trust Boundaries

This is one of the **most important concepts in backend development**.

If you understand trust boundaries properly, a lot of later topics will become easier:

- validation
    
- sanitization
    
- authentication
    
- authorization
    
- security middleware
    
- MongoDB security
    
- file uploads
    
- APIs
    
- JWTs
    

The core idea is simple:

> **A trust boundary is the point where data moves from something you don't control into something your application controls.**

---

# 1. Start with a simple example

Imagine your MERN application:

```text
React
  ↓
HTTP Request
  ↓
Express
  ↓
MongoDB
```

You control:

```text
React code
Express code
MongoDB configuration
Backend business logic
```

But you **do not control**:

```text
What the user types
What HTTP request they send
What values they put in JSON
What headers they send
What query parameters they send
What URL parameters they send
```

Therefore, the incoming HTTP request should initially be considered:

```text
UNTRUSTED
```

---

# 2. What does "untrusted" actually mean?

It does **not** mean:

> "Every user is a hacker."

It means:

> **Your backend has no reliable reason to assume that incoming data follows your rules.**

For example:

```json
{
  "name": "Rahul",
  "age": 22
}
```

This looks perfectly normal.

But your backend doesn't know whether it came from:

```text
Your React application
```

or:

```text
Postman
```

or:

```text
curl
```

or:

```text
A mobile application
```

or:

```text
A custom script
```

So the backend starts with:

```text
"I don't know whether this data is safe/correct yet."
```

---

# 3. Where does the trust boundary exist?

Consider:

```text
                 TRUST BOUNDARY
                       │
                       ▼
Internet ───────► Express API
                       │
                       ▼
                    Your App
```

Everything arriving from outside your backend crosses this boundary.

For example:

```text
req.body
req.params
req.query
req.headers
cookies
uploaded files
```

These should initially be treated as **untrusted input**.

---

# 4. `req.body` is untrusted

Suppose:

```http
POST /api/v1/users
```

The client sends:

```json
{
  "name": "Rahul",
  "age": 22
}
```

Express gives you:

```js
req.body
```

It is tempting to think:

```js
const { name, age } = req.body;
```

and immediately use them.

But:

```js
req.body
```

is still data supplied by someone outside your application.

It hasn't magically become trustworthy just because Express parsed it.

Think:

```text
HTTP Request
     ↓
Express parses JSON
     ↓
req.body
     ↓
STILL UNTRUSTED
```

Parsing ≠ validation.

---

# 5. `req.query` is also untrusted

Suppose:

```http
GET /api/v1/users?page=1&limit=20
```

You access:

```js
req.query.page
req.query.limit
```

But the user could send:

```http
?page=banana&limit=-500
```

or:

```http
?page=999999999
```

Therefore:

```text
req.query
   ↓
UNTRUSTED
```

It needs validation.

---

# 6. `req.params` is untrusted too

Suppose:

```js
router.get("/users/:id", ...)
```

and the request is:

```text
/users/65f123...
```

You get:

```js
req.params.id
```

But someone could request:

```text
/users/hello
```

or:

```text
/users/anything
```

So:

```text
req.params
   ↓
UNTRUSTED
```

Again, validation is needed.

---

# 7. Headers are untrusted

You might read:

```js
req.headers.authorization
```

For example:

```text
Authorization: Bearer eyJ...
```

But you cannot simply say:

> "The client sent a JWT, therefore it's valid."

The client can send anything.

```text
Authorization:
    Bearer fake-token
```

So later:

```text
JWT
 ↓
Verify signature
 ↓
Check expiration
 ↓
Check claims
```

Authentication is another form of crossing a trust boundary safely.

---

# 8. Cookies are untrusted too

Suppose your authentication uses:

```text
accessToken cookie
```

The browser sends:

```text
Cookie: accessToken=abc123
```

Your backend should **not** assume:

```text
Cookie exists
     ↓
User is authenticated
```

Instead:

```text
Cookie
  ↓
Read token
  ↓
Verify token
  ↓
Validate claims
  ↓
Identify user
```

The cookie itself is just external input.

---

# 9. Even your frontend cannot be trusted

This is worth repeating because MERN developers often get confused here.

You wrote:

```text
React frontend
```

You control the source code.

But the user controls the **environment running it**.

They can:

```text
Modify requests
Disable JavaScript
Change request payloads
Use DevTools
Use Postman
Use curl
Write their own client
```

Therefore:

```text
React
   ↓
Not a security boundary
```

Your backend is the security boundary.

---

# 10. The trust boundary in a MERN application

Here's the architecture you should remember:

```text
             OUTSIDE WORLD
                  │
                  │
          ┌───────▼────────┐
          │  HTTP Request   │
          │                 │
          │ body            │
          │ params          │
          │ query           │
          │ headers         │
          │ cookies         │
          │ files           │
          └───────┬────────┘
                  │
══════════════════╪══════════════════
             TRUST BOUNDARY
══════════════════╪══════════════════
                  │
                  ▼
          Validation
                  │
                  ▼
          Sanitization
                  │
                  ▼
          Authentication
                  │
                  ▼
          Authorization
                  │
                  ▼
             Controller
                  │
                  ▼
              Service
                  │
                  ▼
             Repository
                  │
                  ▼
              Database
```

The upper section is where data comes from outside.

The lower section is your application.

---

# 11. Important correction: validation doesn't make everything "trusted"

This is a subtle but important point.

Suppose we validate:

```json
{
  "email": "rahul@example.com"
}
```

Now we know:

```text
email
 ↓
matches expected format
```

But that doesn't mean:

```text
email
 ↓
belongs to a real user
```

Validation answers:

> **"Does this data satisfy the expected structure/rules?"**

It doesn't answer every security question.

For example:

```text
Validation
    ↓
Is email syntactically valid?

Authentication
    ↓
Who is this user?

Authorization
    ↓
Is this user allowed to do this?

Business logic
    ↓
Is this operation allowed by our application rules?
```

Each layer has a different job.

---

# 12. Four different questions

When data enters your backend, we can ask several questions.

### Question 1 — Is the data structurally valid?

```text
Validation
```

Example:

```text
Is age an integer?
```

---

### Question 2 — Can we safely process the data?

```text
Sanitization / security controls
```

Example:

```text
Should unknown fields be removed?
```

---

### Question 3 — Who is making this request?

```text
Authentication
```

Example:

```text
Is this Rahul's valid access token?
```

---

### Question 4 — Is this person allowed to do this?

```text
Authorization
```

Example:

```text
Can Rahul delete this user's account?
```

So:

```text
Validation
     ↓
Security
     ↓
Authentication
     ↓
Authorization
```

These concepts are related, but **not interchangeable**.

---

# 13. Trust boundaries aren't only about users

This is another important idea.

Trust boundaries can exist **inside your own system**.

Consider:

```text
React
  ↓
API
  ↓
Service
  ↓
External Payment API
  ↓
Payment Provider
```

Your backend doesn't fully control the payment provider.

Therefore:

```text
Payment provider response
        ↓
External data
        ↓
Needs careful handling
```

Similarly:

```text
Backend
   ↓
Email provider
```

or:

```text
Backend
   ↓
Cloud storage
```

or:

```text
Backend
   ↓
Third-party API
```

Responses from external systems should also be treated carefully.

---

# 14. Database data isn't automatically perfect either

You might think:

> "MongoDB is inside my application, so database data is trusted."

Usually you trust your own database more than user input, but you still shouldn't assume that every stored record is perfect forever.

Why?

Because:

```text
Old application version
       ↓
Bad migration
       ↓
Bug
       ↓
Corrupted/invalid data
```

or:

```text
Admin tool
   ↓
Unexpected modification
```

So good applications still enforce important invariants at multiple layers.

---

# 15. Defense in depth

This leads to an important security principle:

> **Don't depend on a single protection.**

Imagine:

```text
Frontend validation
        ↓
Backend validation
        ↓
Authorization
        ↓
Service business rules
        ↓
Database constraints
```

Each layer provides another protection.

This is called:

> **Defense in depth**

For example:

```text
React
  ↓
"Looks valid"

Backend validation
  ↓
"Actually valid"

Authorization
  ↓
"User is allowed"

Service
  ↓
"Business rule allows it"

Database
  ↓
"Data integrity maintained"
```

If one layer fails, another layer may still prevent damage.

---

# 16. A dangerous example

Suppose your API allows updating a user:

```http
PATCH /api/v1/users/123
```

The frontend sends:

```json
{
  "name": "Rahul"
}
```

But an attacker sends:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

Now imagine your backend does:

```js
await User.findByIdAndUpdate(
    req.params.id,
    req.body
);
```

That's dangerous.

Why?

Because you're effectively saying:

> "Whatever the client sends, I'll update."

This is exactly why trust boundaries matter.

The backend should define:

```text
What fields are allowed?
Who can update them?
What values are allowed?
```

We'll later connect this to:

- whitelisting
    
- mass assignment
    
- authorization
    
- security
    

---

# 17. Trust boundary and your validation middleware

Now we can understand why this architecture makes sense:

```js
router.post(
    "/signup",
    validate(signupSchema),
    authController.signup
);
```

The route is effectively saying:

```text
Request
   ↓
"Before you enter my application logic,
 prove that your input follows my rules."
```

Then:

```text
validate()
   ↓
Controller
```

This is why validation middleware belongs near the beginning of the request pipeline.

---

# 18. What should we validate?

At the API boundary, common inputs include:

```text
┌─────────────────────┐
│ Request Input       │
├─────────────────────┤
│ req.body            │
│ req.params          │
│ req.query           │
│ req.headers         │
│ cookies             │
│ uploaded files      │
└─────────────────────┘
```

Not every field needs the same validation.

For example:

### Body

```json
{
  "name": "Rahul",
  "age": 22
}
```

Validate structure and values.

### Query

```text
?page=1&limit=20
```

Validate numbers and allowed ranges.

### Params

```text
/users/:id
```

Validate ID format.

### Headers

Validate expected formats and security-related values where appropriate.

### Files

Validate things like:

```text
file type
file size
filename
content handling
```

We'll study file handling separately when we reach it.

---

# 19. Trust boundary ≠ one single middleware

Don't make the mistake of thinking:

```text
validate.middleware.js
        ↓
Everything is now trusted forever
```

Real security is layered.

For example:

```text
Request
  ↓
Input validation
  ↓
Authentication
  ↓
Authorization
  ↓
Business rules
  ↓
Database constraints
```

Each layer checks something different.

---

# 20. Think of it like a series of gates

A useful analogy:

```text
                    INTERNET
                       │
                       ▼
                 ┌───────────┐
                 │ Gate #1   │
                 │ Validation│
                 └─────┬─────┘
                       │
                       ▼
                 ┌───────────┐
                 │ Gate #2   │
                 │   Auth    │
                 └─────┬─────┘
                       │
                       ▼
                 ┌───────────┐
                 │ Gate #3   │
                 │   Role    │
                 └─────┬─────┘
                       │
                       ▼
                 ┌───────────┐
                 │ Gate #4   │
                 │ Business  │
                 │   Rules   │
                 └─────┬─────┘
                       │
                       ▼
                    Database
```

A request must pass the appropriate gates before performing sensitive operations.

---

# 21. Trust boundaries and services

Suppose your controller calls:

```js
authService.signup(data);
```

The service receives data from the controller.

Should the service blindly assume everything is perfect?

It can rely on the API validation for basic input structure, but **important business rules should still live in the service**.

For example:

```text
Validation:
"email has a valid format."

Service:
"An account with this email must not already exist."
```

These are different rules.

So:

```text
Validation
     ↓
Input correctness

Service
     ↓
Business correctness
```

This separation is extremely important when we reach Phase 12.

---

# 22. Trust boundaries and repositories

Similarly, the repository should not be responsible for deciding:

> "Should this user be allowed to delete another user?"

That's normally an application/business authorization concern.

The repository's job is primarily:

```text
Service
   ↓
"Find this user's data."
   ↓
Repository
   ↓
MongoDB
```

Again:

```text
Validation
   ↓
Service
   ↓
Repository
```

Different responsibilities.

# 24. The most important distinction

Let's make this extremely clear.

### Untrusted input

```text
req.body
req.query
req.params
req.headers
cookies
uploaded files
external API responses
```

### Validated input

```text
Data that passed your defined validation rules
```

### Authenticated identity

```text
A user whose identity has been verified
```

### Authorized operation

```text
An authenticated user who is allowed to perform a particular action
```

These are **four different states**.

Don't combine them.

---

# 25. A practical example

Imagine:

```http
DELETE /api/v1/users/123
```

A request arrives.

### Step 1 — Parameter validation

```text
Is "123" a valid user ID?
```

↓

### Step 2 — Authentication

```text
Who is making this request?
```

↓

### Step 3 — Authorization

```text
Is this user allowed to delete user 123?
```

↓

### Step 4 — Business rules

```text
Can this account actually be deleted?
```

↓

### Step 5 — Database operation

```text
Delete the user.
```

Each step answers a different question.

Imagine this request:

```http
Authorization: Bearer fake-token
Content-Type: application/json
```

Body:

```json
{
    "name": 123,
    "email": "hello",
    "role": "admin"
}
```

Now classify each piece.

### 1. `req.query.page`

Is it trusted or untrusted?

### 2. `Authorization` header

Trusted or untrusted?

### 3. `req.body.name`

Trusted or untrusted?

### 4. `req.body.role`

Trusted or untrusted?

### 5. If the JWT is successfully verified, what has been established?

### 6. Does a valid JWT automatically mean the user can perform every operation?

Think carefully about **authentication vs authorization**.

The entire lesson can be reduced to this:

```text
Anything coming from outside
            ↓
       UNTRUSTED
            ↓
       Verify it
            ↓
    Apply appropriate rules
            ↓
      Use it safely
```

And this is exactly why **validation is placed at the API boundary**.
