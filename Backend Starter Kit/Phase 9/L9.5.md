# Lesson 9.5 — Joi Object Schemas

In Lesson 9.4, we learned the basic idea of Joi:

```text
Schema
   ↓
Defines rules
   ↓
validate(data)
   ↓
Valid / Invalid
```

Today we'll focus deeply on **`Joi.object()`**, because almost every request body in a real MERN backend is an object.

For example:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123"
}
```

Our goal is to turn this into a clear validation contract.

---

# 1. Why `Joi.object()` is so important

Most API request bodies look like:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

That is a JavaScript object.

So we can describe it with:

```js
const signupSchema = Joi.object({
    name: Joi.string(),
    email: Joi.string()
});
```

Think of it as:

```text
Joi.object()
      │
      ├── name
      │     └── string
      │
      └── email
            └── string
```

---

# 2. `Joi.object()` creates an object contract

Consider:

```js
const userSchema = Joi.object({
    name: Joi.string(),
    age: Joi.number()
});
```

This tells Joi:

> "I expect an object, and inside that object I have `name` and `age`."

So the expected structure is:

```text
User object
│
├── name → string
└── age  → number
```

---

# 3. Nested objects

Real applications often have nested data.

For example:

```json
{
  "name": "Rahul",
  "address": {
    "city": "Sitamarhi",
    "state": "Bihar"
  }
}
```

We can represent this with nested Joi objects:

```js
const userSchema = Joi.object({
    name: Joi.string(),

    address: Joi.object({
        city: Joi.string(),
        state: Joi.string()
    })
});
```

Notice the structure:

```text
userSchema
│
├── name
│
└── address
      │
      ├── city
      └── state
```

This is one of the most useful features of Joi.

---

# 4. Nested objects are schemas too

This:

```js
Joi.object({
    city: Joi.string(),
    state: Joi.string()
})
```

is itself a schema.

So we can think:

```text
Main Schema
     │
     ├── name schema
     │
     └── address schema
            │
            ├── city schema
            └── state schema
```

This lets us model complex request bodies.

---

# 5. Making nested fields required

Suppose `address` itself must exist:

```js
const userSchema = Joi.object({
    name: Joi.string().required(),

    address: Joi.object({
        city: Joi.string().required(),
        state: Joi.string().required()
    }).required()
});
```

Now there are two levels of `required()`.

### Level 1

```js
address: Joi.object(...).required()
```

means:

> `address` must exist.

### Level 2

```js
city: Joi.string().required()
```

means:

> `city` must exist inside `address`.

So:

```text
user
│
├── name       → required
│
└── address    → required
      │
      ├── city  → required
      └── state → required
```

---

# 6. Why this distinction matters

Consider:

```json
{
  "name": "Rahul"
}
```

If `address` is required:

```text
address missing
      ↓
INVALID
```

But suppose `address` exists:

```json
{
  "name": "Rahul",
  "address": {}
}
```

Now:

```text
address exists
      ↓
city missing
      ↓
INVALID
```

That's why you need to understand the difference between:

```text
object required
```

and:

```text
fields inside object required
```

---

# 7. Optional nested objects

Sometimes an object isn't required.

For example:

```js
const profileSchema = Joi.object({
    name: Joi.string().required(),

    address: Joi.object({
        city: Joi.string().required(),
        state: Joi.string().required()
    })
});
```

Here, `address` is optional.

So this may be valid:

```json
{
  "name": "Rahul"
}
```

But if `address` is provided:

```json
{
  "name": "Rahul",
  "address": {
    "city": "Sitamarhi",
    "state": "Bihar"
  }
}
```

then its internal rules apply.

This gives us a useful pattern:

```text
Optional object
      │
      └── If present → validate its contents
```

---

# 8. Think in terms of a tree

Complex request bodies are easiest to understand as trees.

Example:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "profile": {
    "bio": "Developer",
    "address": {
      "city": "Sitamarhi",
      "state": "Bihar"
    }
  }
}
```

The schema becomes:

```text
User
│
├── name
├── email
│
└── profile
      │
      ├── bio
      │
      └── address
            │
            ├── city
            └── state
```

And Joi mirrors this tree:

```js
const userSchema = Joi.object({
    name: Joi.string(),
    email: Joi.string(),

    profile: Joi.object({
        bio: Joi.string(),

        address: Joi.object({
            city: Joi.string(),
            state: Joi.string()
        })
    })
});
```

This is the mental model you should use.

---

# 9. Object schemas can contain arrays

Real APIs also contain arrays.

For example:

```json
{
  "name": "Rahul",
  "skills": [
    "JavaScript",
    "React",
    "Node.js"
  ]
}
```

Joi can describe this too:

```js
const userSchema = Joi.object({
    name: Joi.string(),

    skills: Joi.array()
});
```

But this only says:

> `skills` should be an array.

We haven't said what the array should contain.

---

# 10. Arrays with specific item types

We can say:

```js
skills: Joi.array().items(Joi.string())
```

Now:

```text
skills
  ↓
array
  ↓
each item must be a string
```

So this is valid:

```json
{
  "skills": [
    "JavaScript",
    "React",
    "Node.js"
  ]
}
```

But this is not:

```json
{
  "skills": [
    "JavaScript",
    123,
    true
  ]
}
```

because not every item is a string.

---

# 11. Nested objects inside arrays

This is extremely common in APIs.

Suppose we have:

```json
{
  "name": "Rahul",
  "addresses": [
    {
      "city": "Sitamarhi",
      "state": "Bihar"
    },
    {
      "city": "Patna",
      "state": "Bihar"
    }
  ]
}
```

We can write:

```js
const userSchema = Joi.object({
    name: Joi.string(),

    addresses: Joi.array().items(
        Joi.object({
            city: Joi.string().required(),
            state: Joi.string().required()
        })
    )
});
```

The structure is:

```text
User
│
├── name
│
└── addresses
      │
      ├── object
      │     ├── city
      │     └── state
      │
      └── object
            ├── city
            └── state
```

This is a very common real-world schema.

---

# 12. Object + array + nested object

Let's create something slightly more realistic:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "profile": {
    "bio": "MERN developer",
    "skills": [
      "JavaScript",
      "React",
      "Node.js"
    ]
  }
}
```

Schema:

```js
const userSchema = Joi.object({
    name: Joi.string().required(),

    email: Joi.string().required(),

    profile: Joi.object({
        bio: Joi.string(),

        skills: Joi.array().items(
            Joi.string()
        )
    })
});
```

Notice how naturally Joi follows the JSON structure.

---

# 13. The schema should reflect the API contract

This is an important backend design principle.

Suppose your endpoint accepts:

```http
POST /api/v1/users
```

and the API contract is:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "profile": {
    "bio": "Developer"
  }
}
```

Your Joi schema should represent **that contract**.

Don't create a giant schema containing every possible User model field.

For example, your database might contain:

```text
User
├── _id
├── name
├── email
├── passwordHash
├── role
├── createdAt
├── updatedAt
└── lastLogin
```

But signup may only accept:

```text
name
email
password
```

Therefore:

> **API validation schemas should describe the request, not blindly mirror the database model.**

This will become extremely important later.

---

# 14. Request schema vs database schema

This distinction is worth remembering.

### Database model

Describes:

```text
What we store
```

### Joi request schema

Describes:

```text
What the client is allowed to send
```

For example:

```text
Client
  ↓
name
email
password
```

Then the service might transform it:

```text
password
  ↓
hash
  ↓
passwordHash
```

and save:

```text
Database
  ↓
name
email
passwordHash
```

So don't confuse:

```text
Request shape
```

with:

```text
Database shape
```

---

# 15. Unknown fields

Now we reach a very important object-schema topic.

Suppose your schema is:

```js
const signupSchema = Joi.object({
    name: Joi.string().required(),
    email: Joi.string().required()
});
```

But the client sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

What should happen to `role`?

This is where **unknown keys** become important.

The client is trying to send a field that isn't part of the schema.

We should not blindly accept every field.

---

# 16. Why unknown fields can be dangerous

Consider this:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

Suppose your backend does:

```js
User.create(req.body);
```

Now the client is influencing fields that perhaps the API never intended to expose.

This can lead to a class of problems commonly called:

> **Mass assignment / over-posting**

We'll study this more deeply later.

For now, remember:

> **Your validation schema should define what the client is allowed to provide.**

---

# 17. Don't blindly trust object shape

Imagine:

```js
const schema = Joi.object({
    name: Joi.string(),
    email: Joi.string()
});
```

The developer might think:

```text
"Only name and email exist."
```

But the client may send:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin",
  "isVerified": true
}
```

That's why handling unknown fields is an important part of API validation.

We'll cover the exact Joi behavior and the best strategy in the next lesson.

---

# 18. Nested objects and unknown fields

Unknown-field problems can also occur inside nested objects.

For example:

```json
{
  "profile": {
    "bio": "Developer",
    "role": "admin"
  }
}
```

Schema:

```js
const schema = Joi.object({
    profile: Joi.object({
        bio: Joi.string()
    })
});
```

Now `profile.role` wasn't defined.

This shows why object validation isn't just about the top level.

You need to think about the entire request tree.

---

# 19. Deeply nested schemas

Joi can represent fairly complex structures.

For example:

```js
const orderSchema = Joi.object({
    customer: Joi.object({
        name: Joi.string().required(),
        email: Joi.string().required()
    }).required(),

    items: Joi.array().items(
        Joi.object({
            productId: Joi.string().required(),
            quantity: Joi.number()
                .integer()
                .min(1)
                .required()
        })
    ).required()
});
```

This represents:

```text
Order
│
├── customer
│     ├── name
│     └── email
│
└── items[]
      │
      ├── productId
      └── quantity
```

This is much closer to the schemas you'll see in real backend projects.

---

# 20. Schema readability matters

You could write everything in one line:

```js
const schema = Joi.object({name:Joi.string().required(),email:Joi.string().required(),age:Joi.number().integer().min(18)});
```

Technically possible.

But don't.

Prefer:

```js
const schema = Joi.object({
    name: Joi.string().required(),

    email: Joi.string().required(),

    age: Joi.number()
        .integer()
        .min(18)
        .required()
});
```

Why?

Because validation schemas are effectively **documentation for your API**.

A developer can immediately understand:

```text
name → required string
email → required string
age → required integer >= 18
```

---

# 21. Build schemas from the outside inward

When creating a complex schema, use this method.

Suppose the JSON is:

```json
{
  "title": "My Course",
  "instructor": {
    "name": "Rahul"
  },
  "lessons": [
    {
      "title": "Introduction",
      "duration": 30
    }
  ]
}
```

Don't try to write the entire schema immediately.

Break it down.

### Step 1

Top level:

```js
Joi.object({
});
```

### Step 2

Add simple fields:

```js
Joi.object({
    title: Joi.string()
});
```

### Step 3

Add instructor:

```js
instructor: Joi.object({
    name: Joi.string()
})
```

### Step 4

Add lessons:

```js
lessons: Joi.array().items(
    Joi.object({
        title: Joi.string(),
        duration: Joi.number()
    })
)
```

This makes complex schemas much easier.

---

# 22. A useful schema-building technique

Whenever you see JSON, convert it like this:

```text
JSON value
   ↓
What type is it?
   ↓
string / number / boolean / object / array
   ↓
Choose Joi type
```

For example:

```json
{
  "name": "Rahul",
  "age": 22,
  "active": true,
  "address": {},
  "skills": []
}
```

Becomes:

```text
name    → Joi.string()
age     → Joi.number()
active  → Joi.boolean()
address → Joi.object()
skills  → Joi.array()
```

Then add rules.

This technique will save you a lot of confusion.

---

# 23. Boolean fields

Don't forget booleans.

Example:

```json
{
  "isActive": true
}
```

Schema:

```js
const schema = Joi.object({
    isActive: Joi.boolean()
});
```

If required:

```js
isActive: Joi.boolean().required()
```

This becomes useful for things like:

```text
isPublished
isVerified
isActive
notificationsEnabled
```

---

# 24. Null is different from missing

This is a subtle but important concept.

Consider:

```json
{}
```

versus:

```json
{
  "bio": null
}
```

These are not the same.

### Missing

```text
bio doesn't exist
```

### Null

```text
bio exists
but its value is null
```

Your schema may need to explicitly decide whether `null` is allowed.

For example:

```js
bio: Joi.string().allow(null)
```

Now `null` is accepted.

This distinction becomes important when building update APIs.

---

# 25. Why update APIs are different

Suppose signup requires:

```text
name → required
email → required
password → required
```

But an update request might be:

```json
{
  "name": "New Name"
}
```

The user isn't sending every field.

So your update schema may intentionally allow partial data.

Conceptually:

```text
Create
 ↓
Required fields

Update
 ↓
Optional/partial fields
```

This is one reason you shouldn't blindly reuse your signup schema for update operations.

We'll build this properly later.

---

# 26. Object schemas and API design

Good validation schemas force you to think about your API contract.

For every endpoint, ask:

```text
What can the client send?
What must the client send?
What is optional?
What types are allowed?
What values are allowed?
What fields should never be accepted?
```

Then create your schema.

This is much better than:

```js
User.create(req.body);
```

because the latter effectively says:

> "Client, you decide what my backend receives."

Your API should instead say:

> "I decide what my API accepts."

---

# 27. Real backend example

Imagine:

```http
POST /api/v1/auth/register
```

Request:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123"
}
```

A basic schema:

```js
import Joi from "joi";

export const registerSchema = Joi.object({
    name: Joi.string()
        .min(2)
        .max(50)
        .required(),

    email: Joi.string()
        .required(),

    password: Joi.string()
        .min(8)
        .required()
});
```

Later we'll improve this with:

```text
email format
password rules
unknown fields
custom messages
sanitization
```

Don't try to solve everything in one schema.

We're building this step by step.

---

# 28. A very important architecture rule

Don't put this:

```js
const userSchema = Joi.object(...);
```

inside your controller.

Avoid:

```js
const register = async (req, res) => {

    const schema = Joi.object({
        name: Joi.string().required(),
        email: Joi.string().required()
    });

    // ...
};
```

Instead:

```text
src/
├── controllers/
├── services/
├── repositories/
├── middlewares/
└── validations/
```

Then:

```text
validations/
    auth.validation.js
```

contains the schema.

This gives you:

```text
Validation rules
       ↓
separate from
       ↓
Controller logic
```

Much cleaner.

---

# 29. What we are building toward

Eventually you'll have something like:

```text
src/
│
├── controllers/
│
├── services/
│
├── repositories/
│
├── middlewares/
│   └── validate.middleware.js
│
├── validations/
│   ├── auth.validation.js
│   ├── user.validation.js
│   └── product.validation.js
│
└── routes/
```

And a route:

```js
router.post(
    "/register",
    validate(registerSchema),
    authController.register
);
```

The flow becomes:

```text
Request
   ↓
validate middleware
   ↓
Joi object schema
   ↓
Valid?
 ┌─┴─┐
No  Yes
│    │
Error Controller
      ↓
    Service
      ↓
   Repository
```

That's the architecture we're working toward.

# 🧠 The most important ideas from 9.5

### 1. `Joi.object()` represents an object

```js
Joi.object({
    name: Joi.string()
})
```

### 2. Objects can be nested

```js
Joi.object({
    address: Joi.object({
        city: Joi.string()
    })
})
```

### 3. Arrays can contain objects

```js
Joi.array().items(
    Joi.object({
        name: Joi.string()
    })
)
```

### 4. `required()` controls presence

```js
email: Joi.string().required()
```

### 5. Request schemas describe the API contract

They should describe:

> **What the client is allowed to send.**

Not necessarily everything stored in MongoDB.
