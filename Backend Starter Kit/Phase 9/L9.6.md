# Lesson 9.6 — Joi: `required()`, `optional()`, `allow()`, `valid()`, and `forbidden()`

In Lesson 9.5, we learned how to build object schemas.

Now we're going to learn how to control **whether a field is allowed to exist and what values it may contain**.

These five methods are extremely important:

```text
required()
optional()
allow()
valid()
forbidden()
```

Think of them as **field permission rules**.

---

# 1. `required()`

We already saw this:

```js
const schema = Joi.object({
    name: Joi.string().required()
});
```

It means:

> `name` must be present.

This is valid:

```json
{
  "name": "Rahul"
}
```

This is invalid:

```json
{}
```

The basic idea:

```text
name
 ↓
Must exist
```

---

# 2. What does "required" actually mean?

This is important.

When we say:

```js
name: Joi.string().required()
```

we are saying:

```text
The key `name` cannot be missing.
```

It doesn't mean:

```text
"name must contain a good name"
```

Other rules handle that.

For example:

```js
name: Joi.string()
    .min(2)
    .max(50)
    .required()
```

Now we have separate requirements:

```text
required()
    ↓
Must exist

string()
    ↓
Must be a string

min(2)
    ↓
At least 2 characters

max(50)
    ↓
At most 50 characters
```

This separation is important.

---

# 3. `optional()`

Now the opposite.

```js
const schema = Joi.object({
    nickname: Joi.string().optional()
});
```

This means:

> The `nickname` field may be missing.

Both can be valid:

```json
{}
```

and:

```json
{
  "nickname": "Rahul"
}
```

Think:

```text
optional()
    ↓
The field may exist
    ↓
but doesn't have to
```

---

# 4. Are fields optional by default?

This is a very important question.

For example:

```js
const schema = Joi.object({
    name: Joi.string(),
    age: Joi.number()
});
```

These fields are not required by default.

So:

```json
{}
```

can satisfy the basic presence rules.

Therefore:

```js
Joi.string()
```

does **not** mean:

```text
Required string
```

It means roughly:

```text
If supplied, it should be a string.
```

If you want mandatory presence:

```js
Joi.string().required()
```

---

# 5. `required()` vs `optional()`

Simple comparison:

|Rule|Meaning|
|---|---|
|`Joi.string()`|Optional string by default|
|`Joi.string().optional()`|Explicitly optional string|
|`Joi.string().required()`|Required string|

Example:

```js
const schema = Joi.object({
    username: Joi.string().required(),
    nickname: Joi.string().optional()
});
```

Expected:

```text
username → MUST exist
nickname → MAY exist
```

---

# 6. Why explicitly use `optional()`?

You might ask:

> "If fields are optional by default, why write `.optional()`?"

Good question.

Sometimes explicit code is easier to understand.

Compare:

```js
const schema = Joi.object({
    name: Joi.string(),
    bio: Joi.string()
});
```

with:

```js
const schema = Joi.object({
    name: Joi.string().required(),
    bio: Joi.string().optional()
});
```

The second one immediately communicates the API contract:

```text
name → required
bio  → optional
```

For a professional backend, clarity is valuable.

---

# 7. `allow()`

Now things become more interesting.

`allow()` tells Joi:

> "This value is allowed in addition to the normal values accepted by the schema."

The most common example you'll see is `null`.

Suppose:

```js
const schema = Joi.object({
    bio: Joi.string()
});
```

Then:

```json
{
  "bio": null
}
```

is not accepted by the normal string rule.

If your API intentionally allows `null`:

```js
const schema = Joi.object({
    bio: Joi.string().allow(null)
});
```

Now:

```json
{
  "bio": null
}
```

can be valid.

---

# 8. Missing vs `null`

This distinction is **very important for API development**.

Consider these two requests:

### Request A

```json
{}
```

### Request B

```json
{
  "bio": null
}
```

They mean different things.

Request A:

```text
bio wasn't provided
```

Request B:

```text
bio was provided
but its value is null
```

This becomes especially important with:

```text
PATCH /users/:id
```

For example:

```json
{
  "bio": null
}
```

could mean:

> "Remove my bio."

Whereas:

```json
{}
```

could mean:

> "Don't change my bio."

So understanding `allow(null)` is important for real APIs.

---

# 9. `allow()` doesn't mean "anything goes"

Don't misunderstand this.

Suppose:

```js
Joi.string().allow(null)
```

It does **not** mean:

```text
Accept anything
```

It means:

```text
Normal string values
       +
null
```

So:

```text
"Rahul" → valid
null    → valid
123     → invalid
true    → invalid
```

The base schema still matters.

---

# 10. `valid()`

Now let's learn `valid()`.

Suppose a field should only contain certain values.

For example:

```text
status:
    active
    inactive
```

We can write:

```js
const schema = Joi.object({
    status: Joi.string().valid("active", "inactive")
});
```

Now:

```json
{
  "status": "active"
}
```

is valid.

And:

```json
{
  "status": "inactive"
}
```

is valid.

But:

```json
{
  "status": "deleted"
}
```

is invalid.

---

# 11. `valid()` creates an allowed-value list

Think:

```js
Joi.string().valid("active", "inactive")
```

as:

```text
status
  ↓
must be string
  ↓
must be one of:
    active
    inactive
```

This is extremely useful for things like:

```text
role
status
sort order
category
visibility
payment state
```

---

# 12. Example: user role

Suppose your application has:

```text
user
admin
moderator
```

You could define:

```js
const schema = Joi.object({
    role: Joi.string()
        .valid("user", "admin", "moderator")
        .required()
});
```

Now:

```json
{
  "role": "admin"
}
```

passes the value rule.

But:

```json
{
  "role": "superadmin"
}
```

fails.

---

# 13. But here's a security warning ⚠️

Just because Joi allows:

```js
role: Joi.string().valid(
    "user",
    "admin"
)
```

does **not** mean the client should be allowed to choose their own role.

This is a perfect example of:

```text
Validation ≠ Authorization
```

The value:

```json
{
  "role": "admin"
}
```

might be structurally valid.

But your business rules might say:

> Normal users are not allowed to assign themselves the admin role.

So a registration schema might **not include `role` at all**.

For example:

```js
const registerSchema = Joi.object({
    name: Joi.string().required(),
    email: Joi.string().required(),
    password: Joi.string().required()
});
```

Then your service can assign:

```text
role = "user"
```

on the server.

This is much safer.

---

# 14. `forbidden()`

Now we reach a very useful method.

Suppose you have:

```js
const schema = Joi.object({
    name: Joi.string(),
    passwordHash: Joi.string().forbidden()
});
```

`forbidden()` means:

> This field must NOT be provided.

So:

```json
{
  "name": "Rahul"
}
```

can be valid.

But:

```json
{
  "name": "Rahul",
  "passwordHash": "some-value"
}
```

is invalid.

Think:

```text
forbidden()
     ↓
"This field is not part of this request contract."
```

---

# 15. Why would we forbid a field?

Imagine your database has:

```text
_id
name
email
passwordHash
role
isVerified
createdAt
```

But the client is allowed to send only:

```text
name
email
password
```

You don't want:

```json
{
  "role": "admin"
}
```

or:

```json
{
  "isVerified": true
}
```

or:

```json
{
  "passwordHash": "..."
}
```

coming directly from the client.

This is where field control becomes important.

---

# 16. `forbidden()` vs simply not defining a field

This is a subtle design question.

Suppose:

```js
const schema = Joi.object({
    name: Joi.string()
});
```

and the client sends:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

The `role` field isn't defined in the schema.

Depending on how your schema handles unknown keys, Joi may reject, strip, or otherwise handle it according to configuration.

But:

```js
role: Joi.forbidden()
```

makes the intent explicit:

> "`role` must not be supplied."

For some schemas, this makes the contract clearer.

We'll study **unknown keys and `.unknown()` / `.options()`** in the next lesson.

---

# 17. Comparing all five methods

Let's put them together.

### `required()`

```js
name: Joi.string().required()
```

Means:

```text
Must exist.
```

---

### `optional()`

```js
nickname: Joi.string().optional()
```

Means:

```text
May exist.
```

---

### `allow(null)`

```js
bio: Joi.string().allow(null)
```

Means:

```text
String OR null is allowed.
```

---

### `valid()`

```js
status: Joi.string().valid("active", "inactive")
```

Means:

```text
Only these values are allowed.
```

---

### `forbidden()`

```js
role: Joi.forbidden()
```

Means:

```text
Must NOT be provided.
```

---

# 18. A complete example

Let's create a profile update schema.

Suppose our API accepts:

```json
{
  "name": "Rahul",
  "bio": null,
  "status": "active"
}
```

Schema:

```js
const profileSchema = Joi.object({
    name: Joi.string()
        .min(2)
        .max(50)
        .optional(),

    bio: Joi.string()
        .allow(null)
        .optional(),

    status: Joi.string()
        .valid("active", "inactive")
        .optional(),

    role: Joi.forbidden()
});
```

Now we have:

```text
name
 ↓
optional string

bio
 ↓
optional string OR null

status
 ↓
optional string
 ↓
must be active/inactive

role
 ↓
forbidden
```

That's a much richer API contract.

---

# 19. A very important distinction: `optional()` and `allow(null)`

These two are often confused.

Consider:

```js
bio: Joi.string().optional()
```

This means:

```text
bio may be missing
```

It does **not necessarily mean**:

```text
bio may be null
```

If you want both:

```js
bio: Joi.string()
    .allow(null)
    .optional()
```

Then:

```text
missing → allowed
string  → allowed
null    → allowed
```

Think of the two rules separately:

```text
optional()
    ↓
Controls presence

allow(null)
    ↓
Controls an accepted value
```

This distinction is extremely useful.

---

# 20. `required()` and `allow(null)`

You can also combine these.

```js
bio: Joi.string()
    .allow(null)
    .required()
```

Now:

```text
bio must be present
       AND
bio can be a string or null
```

So:

```json
{
  "bio": "Developer"
}
```

valid.

And:

```json
{
  "bio": null
}
```

valid.

But:

```json
{}
```

invalid.

This can be useful when a field must always be explicitly supplied, even if its value is `null`.

---

# 21. `valid()` and `required()`

These can also be combined:

```js
status: Joi.string()
    .valid("active", "inactive")
    .required()
```

Now:

```text
status must exist
       AND
must be "active" or "inactive"
```

So:

```json
{
  "status": "active"
}
```

valid.

But:

```json
{}
```

invalid.

And:

```json
{
  "status": "deleted"
}
```

invalid.

---

# 22. `valid()` can work with other types

It isn't limited to strings.

For example:

```js
isAdmin: Joi.boolean().valid(true)
```

This says:

```text
isAdmin must be true
```

But be careful with security-sensitive fields. A client-controlled `isAdmin` field is usually a design problem.

You could also have:

```js
limit: Joi.number().valid(10, 20, 50)
```

meaning:

```text
10 OR 20 OR 50
```

This can be useful for controlled options.

---

# 23. `forbidden()` and conditional fields

Later we'll learn conditional validation, where a field might be:

```text
required in one situation
optional in another
forbidden in another
```

For example:

```text
paymentMethod = "card"
       ↓
cardNumber required

paymentMethod = "cash"
       ↓
cardNumber forbidden
```

This is one of the places where Joi becomes very powerful.

We'll get there later.

# 24. Real-world API example

Imagine an endpoint:

```http
PATCH /api/v1/users/me
```

Allowed request:

```json
{
  "name": "Rahul",
  "bio": "Backend developer"
}
```

But users must not modify:

```text
role
isVerified
passwordHash
```

A conceptual schema could be:

```js
const updateUserSchema = Joi.object({
    name: Joi.string()
        .min(2)
        .max(50)
        .optional(),

    bio: Joi.string()
        .allow(null)
        .optional(),

    role: Joi.forbidden(),

    isVerified: Joi.forbidden(),

    passwordHash: Joi.forbidden()
});
```

Now the API contract becomes clear:

```text
Client
  │
  ├── name       → allowed
  ├── bio        → allowed
  ├── role       → forbidden
  ├── isVerified → forbidden
  └── passwordHash → forbidden
```

That's much safer than blindly doing:

```js
User.findByIdAndUpdate(id, req.body)
```

---

# 25. Validation is about controlling the boundary

Remember Lesson 9.3.

The client is outside your trust boundary.

Therefore:

```text
Client
  ↓
"I want to send role=admin"
```

Your backend should decide:

```text
"Is role allowed in this endpoint?"
```

Joi helps express that decision.

This is why validation is not just about catching typos.

It's part of designing the **API boundary**.

---

# 26. One important warning about `forbidden()`

Don't think:

```text
forbidden()
=
security by itself
```

Suppose someone bypasses your Joi middleware.

You still need:

```text
authorization
business rules
safe database operations
```

Joi is one layer.

Remember:

```text
Validation
    +
Authentication
    +
Authorization
    +
Business rules
    +
Database safety
```

That's defense in depth.

---

# 27. Create vs Update

This lesson also helps explain why create and update schemas often differ.

### Create

```text
name       → required
email      → required
password   → required
role       → forbidden
```

### Update

```text
name       → optional
email      → optional
password   → optional
role       → forbidden
```

So:

```text
Create schema
      ≠
Update schema
```

Even though they may share some fields.

---

# 28. A good mental table

Keep this table in your notes:

|Joi rule|Meaning|
|---|---|
|`.required()`|Field must exist|
|`.optional()`|Field may be absent|
|`.allow(null)`|`null` is an accepted value|
|`.valid(...)`|Only specified values are accepted|
|`.forbidden()`|Field must not be provided|

And remember:

```text
Presence ≠ Value
```

For example:

```js
Joi.string().required()
```

controls:

```text
"Does the field exist?"
```

while:

```js
Joi.string().min(3)
```

controls:

```text
"Is the supplied value acceptable?"
```

Imagine every field has two questions:

```text
             FIELD
               │
       ┌───────┴────────┐
       │                │
   Should it        What values

       │                │
       ▼                ▼

```

This is a very useful way to think about Joi.

# 🔑 Final Takeaway

The five methods are small, but they give you powerful control:

```text
required()
    ↓
"MUST exist"

optional()
    ↓
"MAY exist"

allow(null)
    ↓
"NULL is allowed"

valid(...)
    ↓
"ONLY these values"

forbidden()
    ↓
"MUST NOT exist"
```

And the most important distinction:

```text
optional()
    ≠
allow(null)
```

Because:

```text
optional()
→ field may be missing

allow(null)
→ null may be the field's value
```

Once you understand that distinction, designing **create, update, and PATCH validation schemas** becomes much easier.
