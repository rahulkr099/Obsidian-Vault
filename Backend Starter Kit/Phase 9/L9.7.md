# Lesson 9.7 — Joi Unknown Fields and `.unknown()`

This lesson is **very important for real backend security**.

In the previous lesson, we learned:

```text
required()   → must exist
optional()   → may exist
allow()      → allows additional values such as null
valid()      → restricts allowed values
forbidden()  → must not be provided
```

Now we answer a very practical question:

> **What happens when the client sends a field that isn't present in our Joi schema?**

For example, our schema says:

```js
const schema = Joi.object({
    name: Joi.string().required(),
    email: Joi.string().required()
});
```

But the client sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

Where did `role` come from?

The client added it.

This is where **unknown keys** become important.

---

# 1. What is an unknown field?

Suppose our schema is:

```js
const userSchema = Joi.object({
    name: Joi.string(),
    email: Joi.string()
});
```

Known fields are:

```text
name
email
```

Now the client sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

`role` is an **unknown field** because we didn't define it in the schema.

Think:

```text
Schema
│
├── name       ← known
└── email      ← known

Request
│
├── name       ← known
├── email      ← known
└── role       ← UNKNOWN
```

---

# 2. Why should we care?

At first, an unknown field may look harmless.

For example:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "favoriteColor": "blue"
}
```

Maybe we simply ignore it.

But consider:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

or:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "isVerified": true
}
```

or:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "permissions": ["delete-users"]
}
```

Now unknown fields can become a security concern.

---

# 3. The danger of passing `req.body` directly

Consider this controller:

```js
const createUser = async (req, res) => {
    const user = await User.create(req.body);

    return res.status(201).json(user);
};
```

This effectively says:

> "Whatever fields the client sends, I'll give them to my database layer."

That's a bad boundary.

The client could send:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "role": "admin"
}
```

If your application isn't carefully designed, the client may influence fields it shouldn't control.

This general class of problem is often called:

> **Mass assignment / over-posting**

---

# 4. Your API should define the allowed input

Instead of thinking:

```text
"Client sent these fields."
```

think:

```text
"What fields does THIS endpoint allow?"
```

For example:

```js
const registerSchema = Joi.object({
    name: Joi.string().required(),
    email: Joi.string().required(),
    password: Joi.string().required()
});
```

The API contract is:

```text
REGISTER
│
├── name
├── email
└── password
```

Not:

```text
"Anything the client wants."
```

---

# 5. What does Joi do with unknown keys?

This is the part you need to understand carefully.

For an object schema:

```js
const schema = Joi.object({
    name: Joi.string()
});
```

you should **not assume** that an unknown key automatically means:

```text
400 error
```

Joi has configurable behavior around unknown keys.

The important concept is:

```text
Unknown key
     ↓
What should Joi do?
     │
     ├── reject it
     ├── allow it
     └── strip it
```

We'll learn how to control this.

---

# 6. `.unknown()`

Joi provides:

```js
.unknown()
```

for object schemas.

Example:

```js
const schema = Joi.object({
    name: Joi.string()
}).unknown();
```

This means:

> Unknown keys are allowed.

So:

```json
{
  "name": "Rahul",
  "somethingElse": "hello"
}
```

can be accepted.

The schema knows:

```text
name
```

but it also allows other keys.

---

# 7. Why would we ever allow unknown fields?

There are legitimate situations.

For example, imagine an object containing metadata:

```json
{
  "name": "Rahul",
  "metadata": {
    "browser": "Firefox",
    "os": "Linux",
    "customValue": "something"
  }
}
```

Maybe your application intentionally allows arbitrary metadata.

You could have:

```js
metadata: Joi.object().unknown()
```

Now:

```text
metadata
   ↓
object
   ↓
arbitrary keys allowed
```

This is very different from allowing arbitrary fields throughout your entire request.

---

# 8. Be careful with `.unknown()`

This is an important security rule:

> **Don't use `.unknown()` everywhere just because it makes validation easier.**

Bad approach:

```js
const schema = Joi.object({
    name: Joi.string(),
    email: Joi.string()
}).unknown();
```

Now your schema basically says:

```text
name → validate it
email → validate it
everything else → let it through
```

That may defeat the purpose of having a strict API contract.

---

# 9. `.unknown(false)`

You can explicitly say that unknown keys are not allowed:

```js
const schema = Joi.object({
    name: Joi.string(),
    email: Joi.string()
}).unknown(false);
```

Conceptually:

```text
Unknown field?
      ↓
NO
      ↓
Reject
```

This is useful when you want a strict object contract.

---

# 10. Why explicit strictness can be useful

Imagine:

```js
const updateUserSchema = Joi.object({
    name: Joi.string(),
    bio: Joi.string().allow(null)
}).unknown(false);
```

The API says:

```text
Allowed:
    name
    bio

Anything else:
    reject
```

So this:

```json
{
  "name": "Rahul",
  "bio": "Developer"
}
```

is fine.

But:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

fails because:

```text
role
 ↓
unknown
 ↓
not allowed
```

---

# 11. `.unknown(true)` vs `.unknown(false)`

Think of:

```js
Joi.object({
    name: Joi.string()
}).unknown(true)
```

as:

```text
Known fields:
    validate

Unknown fields:
    allow
```

And:

```js
Joi.object({
    name: Joi.string()
}).unknown(false)
```

as:

```text
Known fields:
    validate

Unknown fields:
    reject
```

This is a simple mental model.

---

# 12. What should we prefer for API request bodies?

For security-sensitive APIs, a good default mindset is:

```text
Only accept what the endpoint explicitly expects.
```

For example:

```js
const updateUserSchema = Joi.object({
    name: Joi.string(),
    bio: Joi.string().allow(null)
}).unknown(false);
```

Now the schema acts as an allow-list.

```text
Client
   ↓
"name" → allowed
"bio"  → allowed
"role" → rejected
"admin" → rejected
"anythingElse" → rejected
```

This is a strong API boundary.

---

# 13. But there's another option: strip unknown fields

Sometimes you don't want to reject the entire request.

Instead, you may want:

```text
Unknown field
     ↓
Remove it
     ↓
Continue with known fields
```

Joi supports this behavior through its preferences/options.

For example:

```js
const schema = Joi.object({
    name: Joi.string(),
    email: Joi.string()
}).options({
    stripUnknown: true
});
```

Conceptually:

```text
Input:

{
    name: "Rahul",
    email: "rahul@example.com",
    role: "admin"
}

        ↓ Joi

{
    name: "Rahul",
    email: "rahul@example.com"
}
```

The unknown field is removed.

---

# 14. Reject vs strip

This gives us an important design choice.

### Reject unknown fields

```text
Unknown field
      ↓
400 Validation Error
```

Advantages:

- client immediately knows it sent something invalid
    
- strict API contract
    
- easier to detect client bugs
    
- safer for many sensitive endpoints
    

---

### Strip unknown fields

```text
Unknown field
      ↓
Remove it
      ↓
Continue
```

Advantages:

- more tolerant clients
    
- useful for some APIs
    
- can simplify handling of extra metadata
    

But there is a downside:

> The client may think the field was accepted even though it was silently removed.

For many security-sensitive request bodies, **rejecting unexpected fields is easier to reason about**.

---

# 15. Don't confuse stripping with authorization

Suppose:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

and Joi strips `role`.

That's useful.

But imagine the client sends:

```json
{
  "name": "Rahul"
}
```

and later your service automatically assigns:

```text
role = admin
```

Then you still have an authorization/business logic problem.

So:

```text
Unknown-field handling
        ≠
Authorization
```

Again:

```text
Validation
   ↓
Input shape

Authorization
   ↓
Permission
```

Different responsibilities.

---

# 16. Unknown fields inside nested objects

This is where things get interesting.

Suppose:

```js
const schema = Joi.object({
    profile: Joi.object({
        bio: Joi.string()
    })
});
```

Request:

```json
{
  "profile": {
    "bio": "Developer",
    "role": "admin"
  }
}
```

Here:

```text
profile.role
```

is unknown **inside the nested object**.

You need to think about unknown-key behavior at each object level.

That's another reason schema design should be deliberate.

---

# 17. Example: strict nested object

```js
const schema = Joi.object({
    profile: Joi.object({
        bio: Joi.string(),
        age: Joi.number()
    }).unknown(false)
});
```

Now:

```json
{
  "profile": {
    "bio": "Developer",
    "age": 22
  }
}
```

is okay.

But:

```json
{
  "profile": {
    "bio": "Developer",
    "role": "admin"
  }
}
```

fails.

Because:

```text
profile.role
     ↓
unknown
     ↓
rejected
```

---

# 18. You can intentionally allow unknown nested data

Suppose you have:

```json
{
  "name": "Rahul",
  "metadata": {
    "browser": "Firefox",
    "theme": "dark",
    "someCustomValue": "hello"
  }
}
```

Maybe your API intentionally supports arbitrary metadata.

Then:

```js
const schema = Joi.object({
    name: Joi.string().required(),

    metadata: Joi.object().unknown(true)
});
```

This gives us:

```text
name
 ↓
strict

metadata
 ↓
arbitrary keys allowed
```

That's a much better use of `.unknown()`.

---

# 19. `.unknown()` should be intentional

Think about this:

```js
metadata: Joi.object().unknown()
```

Good if:

> "Metadata is intentionally extensible."

But:

```js
user: Joi.object().unknown()
```

can be dangerous if:

> "User objects should contain only known fields."

The rule is:

> **Use permissive schemas only where the data is intentionally extensible.**

---

# 20. `forbidden()` vs unknown-field rejection

These concepts are related but different.

Suppose:

```js
const schema = Joi.object({
    name: Joi.string(),
    role: Joi.forbidden()
}).unknown(false);
```

Now:

```text
role
 ↓
Known by schema
 ↓
Explicitly forbidden
```

while:

```text
somethingElse
 ↓
Unknown
 ↓
Rejected by unknown(false)
```

This gives you two different categories:

```text
Known + forbidden
```

and:

```text
Unknown
```

This distinction can make complex schemas clearer.

---

# 21. Example

```js
const schema = Joi.object({
    name: Joi.string().required(),

    role: Joi.forbidden(),

    bio: Joi.string().allow(null)
}).unknown(false);
```

Now:

### Valid

```json
{
  "name": "Rahul",
  "bio": "Developer"
}
```

### Invalid — forbidden field

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

### Invalid — unknown field

```json
{
  "name": "Rahul",
  "favoriteColor": "blue"
}
```

This gives us a very explicit contract.

---

# 22. Why this matters for PATCH APIs

Imagine:

```http
PATCH /api/v1/users/me
```

Allowed fields:

```text
name
bio
avatar
```

Forbidden:

```text
role
isVerified
permissions
```

Unknown:

```text
anything else
```

Your schema can represent that contract.

Conceptually:

```js
const updateUserSchema = Joi.object({
    name: Joi.string().min(2).max(50),
    bio: Joi.string().allow(null),
    avatar: Joi.string(),

    role: Joi.forbidden(),
    isVerified: Joi.forbidden(),
    permissions: Joi.forbidden()
}).unknown(false);
```

Now the API boundary is clear.

---

# 23. This protects against a common mistake

A common beginner pattern is:

```js
const updateUser = async (req, res) => {
    const user = await User.findByIdAndUpdate(
        req.user.id,
        req.body,
        { new: true }
    );

    return res.json(user);
};
```

The problem is:

```text
req.body
```

is controlled by the client.

If the client sends:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

you don't want to blindly pass that object into the update operation.

Instead:

```text
Request
   ↓
Validate allowed fields
   ↓
Validated data
   ↓
Service
   ↓
Repository
   ↓
Database
```

This is exactly why we're learning validation before we build the final middleware architecture.

---

# 24. But validation alone isn't enough

Even with:

```js
.unknown(false)
```

you still need good service and repository design.

For example:

```text
Validation
 ↓
Allowed fields
```

doesn't answer:

```text
"Is Rahul allowed to modify this user?"
```

That's authorization.

And it doesn't answer:

```text
"Can the email be changed after verification?"
```

That's business logic.

So your final architecture remains:

```text
Request
   ↓
Validation
   ↓
Authentication
   ↓
Authorization
   ↓
Controller
   ↓
Service
   ↓
Repository
```

---

# 25. A useful security principle: allow-list

This lesson introduces an important security mindset:

> **Prefer explicitly allowed data over blindly accepted data.**

Compare:

### Weak mindset

```text
"Accept everything unless something looks dangerous."
```

with:

### Stronger mindset

```text
"Accept only what this endpoint explicitly needs."
```

The second approach is called an **allow-list mindset**.

For API design, this is very useful.

---

# 26. Unknown fields and frontend compatibility

There is one trade-off.

Suppose your frontend sends:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "theme": "dark"
}
```

but the backend schema doesn't know `theme`.

A strict backend might reject the entire request.

That is good for detecting mistakes, but it can sometimes create compatibility problems when clients evolve.

This is why API design requires a conscious decision:

```text
Should unknown fields:
    reject?
    strip?
    allow?
```

There isn't one universal answer for every object.

---

# 27. A practical rule for your MERN projects

For normal API request bodies:

```text
Strict by default.
```

For intentionally extensible objects:

```text
Allow unknown fields deliberately.
```

For example:

```text
User profile
    → strict

Registration
    → strict

Password change
    → strict

Payment request
    → strict

Metadata
    → potentially flexible

Custom plugin configuration
    → potentially flexible
```

This is a good starting rule.

# 28. Schema options

Joi also allows you to configure behavior through options.

For example:

```js
const schema = Joi.object({
    name: Joi.string()
}).options({
    abortEarly: false,
    stripUnknown: true
});
```

Here we're configuring the schema's validation behavior.

We already saw:

```text
abortEarly
```

and now:

```text
stripUnknown
```

We'll learn more about schema options as we go.

---

# 29. Don't put every option everywhere

You might be tempted to write:

```js
const schema = Joi.object({
    // ...
}).options({
    abortEarly: false,
    stripUnknown: true,
    allowUnknown: true,
    // many more...
});
```

Don't blindly add options.

Every option changes behavior.

Instead ask:

```text
Why do I need this option?
What should happen to invalid data?
Does this endpoint want strictness or flexibility?
```

Good backend code is deliberate.

# 31. A complete example

Let's create a strict profile-update schema:

```js
import Joi from "joi";

export const updateProfileSchema = Joi.object({
    name: Joi.string()
        .min(2)
        .max(50)
        .optional(),

    bio: Joi.string()
        .allow(null)
        .optional(),

    website: Joi.string()
        .optional(),

    role: Joi.forbidden(),

    isVerified: Joi.forbidden(),

    permissions: Joi.forbidden()
}).unknown(false);
```

The API contract is now:

```text
Allowed:
    name
    bio
    website

Forbidden:
    role
    isVerified
    permissions

Unknown:
    rejected
```

That's a very clear boundary.

---

# 32. What if we want arbitrary metadata?

We can intentionally make only one nested object flexible:

```js
const schema = Joi.object({
    name: Joi.string().required(),

    metadata: Joi.object().unknown(true),

    role: Joi.forbidden()
}).unknown(false);
```

Now:

```json
{
  "name": "Rahul",
  "metadata": {
    "browser": "Firefox",
    "customThing": "hello"
  }
}
```

can work.

But:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

still fails.

And:

```json
{
  "name": "Rahul",
  "randomField": "hello"
}
```

fails.

This is a **much better design** than making the entire request flexible.

---

# 33. The three strategies

Remember these three:

## Strategy 1 — Reject

```text
Unknown
   ↓
Error
```

Use when you want a strict API contract.

---

## Strategy 2 — Strip

```text
Unknown
   ↓
Remove
   ↓
Continue
```

Use when you intentionally want tolerant input.

---

## Strategy 3 — Allow

```text
Unknown
   ↓
Keep
   ↓
Continue
```

Use when the object is intentionally extensible.

---

# 34. Which one should you choose?

For the backend projects you're building, a good starting approach is:

```text
Normal API input
      ↓
REJECT unknown fields
```

And:

```text
Explicitly extensible object
      ↓
ALLOW unknown fields
```

Use stripping only when you have a clear reason.

Why?

Because silent removal can hide client mistakes.

For example, if the frontend accidentally sends:

```json
{
  "usernmae": "Rahul"
}
```

and your backend silently strips it, you may end up with confusing behavior.

Strict validation makes the bug visible.

# 🔑 Final Takeaway

The key concept from this lesson is **not just `.unknown()`**.

It's this:

> **Your API should deliberately decide what happens to data that it didn't explicitly expect.**

You have three major choices:

```text
Unknown field
     │
     ├── Reject
     │
     ├── Strip
     │
     └── Allow
```

And for most security-sensitive API request bodies, your starting mindset should be:

```text
Explicitly allowed fields
        ↓
ACCEPT

Explicitly forbidden fields
        ↓
REJECT

Unexpected fields
        ↓
REJECT
```

This gives your backend a much stronger trust boundary.
