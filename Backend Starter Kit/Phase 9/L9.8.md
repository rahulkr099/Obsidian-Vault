# Lesson 9.8 — Joi String Validation

Now we're going to learn one of the **most frequently used parts of Joi**: validating strings properly.

In a MERN backend, strings appear everywhere:

```text
name
username
email
password
phone
URL
search query
title
description
status
role
```

A simple:

```js
Joi.string()
```

is often not enough.

We want to answer questions like:

> How short can this string be?  
> How long can it be?  
> Should spaces be removed?  
> Should it be lowercase?  
> Should it match a pattern?  
> Should it contain only certain characters?

---

# 1. Basic `Joi.string()`

The simplest rule:

```js
const schema = Joi.object({
    name: Joi.string()
});
```

This means:

> If `name` is provided, it should be a string.

Valid:

```json
{
  "name": "Rahul"
}
```

Invalid:

```json
{
  "name": 123
}
```

Also remember from the previous lessons:

```js
Joi.string()
```

doesn't automatically mean:

```text
required
```

If `name` must exist:

```js
Joi.string().required()
```

---

# 2. `.min()`

Use `.min()` to specify the minimum string length.

```js
username: Joi.string().min(3)
```

This means:

```text
username
    ↓
at least 3 characters
```

So:

```text
abc      → valid
rahul    → valid
ab       → invalid
```

Example:

```js
const schema = Joi.object({
    username: Joi.string()
        .min(3)
        .required()
});
```

---

# 3. `.max()`

`.max()` specifies the maximum length.

```js
username: Joi.string().max(20)
```

Meaning:

```text
Maximum = 20 characters
```

Combine it with `.min()`:

```js
username: Joi.string()
    .min(3)
    .max(20)
    .required()
```

Now:

```text
3 ≤ username length ≤ 20
```

This is a very common backend rule.

---

# 4. Why length limits matter

Suppose you have:

```js
description: Joi.string()
```

A client could theoretically send a huge amount of text.

Instead:

```js
description: Joi.string().max(500)
```

creates a clear API contract.

For example:

```text
name
    2–50

username
    3–20

title
    3–100

description
    0–500
```

These limits are useful for:

- validation
    
- database design
    
- API consistency
    
- preventing accidental huge payloads
    

---

# 5. `.length()`

Sometimes you want an **exact** length.

```js
code: Joi.string().length(6)
```

Meaning:

```text
Exactly 6 characters.
```

For example:

```text
123456 → valid
12345  → invalid
1234567 → invalid
```

This can be useful for fixed-length values such as certain application-generated codes.

---

# 6. `.trim()`

This is extremely useful.

Consider:

```json
{
  "name": "   Rahul   "
}
```

The actual value contains spaces.

You can use:

```js
name: Joi.string().trim()
```

Joi can trim whitespace around the string during validation/conversion.

Conceptually:

```text
"   Rahul   "
       ↓
"Rahul"
```

This is useful for:

```text
name
username
email
search query
title
```

But be careful: trimming is about **leading/trailing whitespace**, not removing all spaces inside a string.

For example:

```text
"Rahul Kumar"
```

should normally remain:

```text
"Rahul Kumar"
```

---

# 7. `.lowercase()`

You can ask Joi to convert a string to lowercase:

```js
email: Joi.string().lowercase()
```

For example:

```text
"RAHUL@EXAMPLE.COM"
          ↓
"rahul@example.com"
```

This is often useful for things such as email addresses and case-insensitive identifiers.

Example:

```js
const schema = Joi.object({
    email: Joi.string()
        .trim()
        .lowercase()
        .required()
});
```

Now the validation pipeline is conceptually:

```text
Input
 ↓
trim
 ↓
lowercase
 ↓
required/string validation
```

---

# 8. `.uppercase()`

The opposite:

```js
code: Joi.string().uppercase()
```

For example:

```text
"ab12cd"
    ↓
"AB12CD"
```

This can be useful when your application wants a canonical uppercase representation.

Don't use it blindly.

For example, you probably don't want:

```text
name → uppercase
```

unless your application specifically wants names stored that way.

---

# 9. Normalization vs validation

This is an important concept.

Consider:

```js
email: Joi.string()
    .trim()
    .lowercase()
```

Some of these rules are doing more than simply asking:

> "Is this valid?"

They are also **normalizing** the input.

Think:

```text
Validation
    ↓
"Is this acceptable?"

Normalization
    ↓
"Can we convert it into a consistent form?"
```

For example:

```text
"  RAHUL@example.com "
          ↓
"rahul@example.com"
```

This makes your application more consistent.

---

# 10. `.email()`

One of the most useful Joi string rules:

```js
email: Joi.string().email()
```

Example:

```js
const schema = Joi.object({
    email: Joi.string()
        .email()
        .required()
});
```

This tells Joi that the value should follow an email format.

Valid examples might include:

```text
rahul@example.com
user123@example.org
hello.world@example.net
```

Invalid examples include obviously malformed values such as:

```text
rahul
rahul@
@example.com
```

---

# 11. A practical email schema

A common pattern:

```js
email: Joi.string()
    .trim()
    .lowercase()
    .email()
    .required()
```

Think about what each rule does:

```text
string()
    ↓
must be a string

trim()
    ↓
remove surrounding whitespace

lowercase()
    ↓
normalize case

email()
    ↓
must look like an email

required()
    ↓
must be present
```

This is a very useful pattern to remember.

---

# 12. `.pattern()`

Sometimes built-in rules aren't enough.

Suppose usernames should contain only:

```text
letters
numbers
underscore
```

You can use a regular expression:

```js
username: Joi.string()
    .pattern(/^[a-zA-Z0-9_]+$/)
```

Now:

```text
rahul       → valid
rahul123    → valid
rahul_dev   → valid
rahul-dev   → invalid
rahul dev   → invalid
```

because `-` and spaces aren't allowed by this pattern.

---

# 13. Understanding the regex

Let's break this down:

```js
/^[a-zA-Z0-9_]+$/
```

### `^`

Start of string.

```text
^
↓
start
```

### `[a-zA-Z0-9_]`

Allowed characters:

```text
a-z
A-Z
0-9
_
```

### `+`

One or more characters.

### `$`

End of string.

So:

```text
^ + allowed characters + $
```

means:

> The entire string must consist only of those allowed characters.

---

# 14. Pattern + length

You can combine rules.

```js
username: Joi.string()
    .min(3)
    .max(20)
    .pattern(/^[a-zA-Z0-9_]+$/)
    .required()
```

Now the username must:

```text
✓ exist
✓ be a string
✓ contain 3–20 characters
✓ contain only letters, numbers and _
```

This is much stronger than:

```js
username: Joi.string()
```

---

# 15. `.alphanum()`

Joi also provides:

```js
Joi.string().alphanum()
```

This means the string should contain only:

```text
A-Z
a-z
0-9
```

For example:

```js
username: Joi.string()
    .alphanum()
    .min(3)
    .max(20)
```

Then:

```text
rahul123 → valid
rahul     → valid
rahul_123 → invalid
rahul-dev → invalid
```

If you need underscores, `.pattern()` is more flexible.

---

# 16. `.hex()`

For hexadecimal strings:

```js
token: Joi.string().hex()
```

Hexadecimal characters are:

```text
0-9
a-f
A-F
```

Example:

```text
a1b2c3 → valid
ABCDEF → valid
123456 → valid
xyz123 → invalid
```

This can be useful when working with certain IDs, hashes, or encoded values.

---

# 17. `.uri()`

For URLs/URIs, Joi provides:

```js
website: Joi.string().uri()
```

Example:

```js
const schema = Joi.object({
    website: Joi.string()
        .uri()
        .optional()
});
```

You can use this for fields such as:

```text
website
avatar URL
callback URL
redirect URL
resource URL
```

However, URL validation often needs application-specific rules too.

For example, you might only want:

```text
https://
```

rather than every URI scheme.

---

# 18. Restricting URL schemes

You can configure URI validation to be stricter.

For example, conceptually you may want:

```text
http://
https://
```

rather than:

```text
ftp://
file://
```

Joi's URI rules support options for allowed schemes.

The important lesson is:

> Don't assume "valid URL" automatically means "safe URL for my application."

The application's security requirements still matter.

---

# 19. `.hostname()`

For hostname values, Joi has:

```js
Joi.string().hostname()
```

Useful for things like:

```text
example.com
api.example.com
localhost
```

depending on the exact validation rules and options you're using.

This is useful when your API accepts a host separately from a full URL.

---

# 20. `.ip()`

Joi also supports IP address validation:

```js
Joi.string().ip()
```

For example:

```text
192.168.1.10
```

can be validated as an IP address.

There are options for IPv4/IPv6 behavior.

This is useful for things like:

```text
trusted IP
server address
network configuration
```

But remember:

> Validating an IP format does not mean the IP is trustworthy.

---

# 21. `.token()`

Joi provides:

```js
Joi.string().token()
```

This is useful for strings containing only token-style characters according to Joi's token rules.

It's another example of using a built-in rule instead of manually creating a regex when Joi already provides what you need.

---

# 22. `.creditCard()` — don't use it blindly

Joi has specialized validation rules for some formats, but you should be careful about what "valid" means.

For sensitive data such as payment information:

```text
Format validation
       ≠
Payment authorization
       ≠
Payment processing
```

In a real application, payment details should generally be handled through a proper payment provider rather than stored casually in your database.

The lesson here is broader:

> A validation rule only validates the property it was designed to validate.

---

# 23. `.valid()`

We already learned this, but it's especially useful with strings.

For example:

```js
status: Joi.string()
    .valid("active", "inactive", "pending")
    .required()
```

Now the value must be exactly one of those options.

This is often better than:

```js
status: Joi.string()
```

because otherwise:

```text
"banana"
"random"
"something"
```

could satisfy the basic string type.

---

# 24. Case-sensitive values

Suppose:

```js
status: Joi.string().valid("active", "inactive")
```

You should think carefully about:

```text
active
ACTIVE
Active
```

If your application expects a canonical representation, normalize first:

```js
status: Joi.string()
    .lowercase()
    .valid("active", "inactive")
```

Then values can be normalized to lowercase before comparison.

This can be useful for controlled fields.

But don't normalize values if case has meaning.

---

# 25. `.replace()`

Joi can also transform certain values.

For example, you may want to replace a particular value:

```js
status: Joi.string()
    .replace("enabled", "active")
```

Conceptually:

```text
enabled
   ↓
active
```

This can be useful when migrating old client formats.

But don't use transformations everywhere.

It's usually better to keep your API contract clear rather than silently changing lots of input.

---

# 26. `.custom()`

Sometimes your validation rule is too specific for built-in Joi methods.

Then you can use:

```js
Joi.string().custom((value, helpers) => {
    // custom validation
    return value;
})
```

This allows custom logic.

For example:

```text
username
    ↓
basic Joi rules
    ↓
custom business-independent format rule
```

We'll study `.custom()` separately because it's powerful and easy to misuse.

---

# 27. Don't put database checks inside string validation

Suppose you want to validate:

```text
email must not already exist
```

It might be tempting to do:

```js
Joi.string().custom(async ...)
```

and query MongoDB.

Don't make your basic Joi validation layer responsible for database business logic.

Instead:

```text
Joi
 ↓
"Is this a correctly formatted email?"

Service
 ↓
"Does this email already belong to another user?"
```

This separation is important.

---

# 28. Password validation

Now let's build a realistic password rule.

Suppose your application requires:

```text
minimum 8 characters
maximum 72 characters
```

You could write:

```js
password: Joi.string()
    .min(8)
    .max(72)
    .required()
```

You may also add more complexity rules if your application's security policy requires them.

For example:

```text
uppercase
lowercase
number
special character
```

But don't automatically assume that "more complicated password rules" always mean better security.

Modern password security also depends heavily on:

```text
strong password hashing
rate limiting
MFA where appropriate
breach protection
secure password reset
```

Validation is only one piece.

---

# 29. Password confirmation

Suppose your registration request contains:

```json
{
  "password": "Secret123!",
  "confirmPassword": "Secret123!"
}
```

You can use Joi references later to express:

```text
confirmPassword
       ↓
must equal
       ↓
password
```

We'll cover references and cross-field validation in a later lesson.

For now, understand that string validation can be combined with **relationships between fields**.

---

# 30. Names

A simple name schema could be:

```js
name: Joi.string()
    .trim()
    .min(2)
    .max(50)
    .required()
```

This is a reasonable starting point.

Notice what we aren't doing:

```js
.pattern(/^[a-zA-Z]+$/)
```

Why?

Because real names can contain:

```text
spaces
hyphens
apostrophes
Unicode characters
```

For example:

```text
Rahul Kumar
Mary-Jane
O'Connor
```

So don't make validation unnecessarily restrictive.

---

# 31. Username

Username rules can be stricter.

For example:

```js
username: Joi.string()
    .trim()
    .lowercase()
    .min(3)
    .max(20)
    .pattern(/^[a-z0-9_]+$/)
    .required()
```

Now your application has a predictable username format:

```text
rahul
rahul123
rahul_dev
```

This is often useful for URLs and lookups.

---

# 32. Email

A practical schema:

```js
email: Joi.string()
    .trim()
    .lowercase()
    .email()
    .required()
```

This gives you:

```text
type
 ↓
string

normalization
 ↓
trim + lowercase

format
 ↓
email

presence
 ↓
required
```

---

# 33. Bio

A bio might be:

```js
bio: Joi.string()
    .trim()
    .max(500)
    .allow(null)
    .optional()
```

Meaning:

```text
missing → allowed
null    → allowed
string  → allowed
>500    → rejected
```

This combines several concepts we've learned.

---

# 34. URL

For an optional profile website:

```js
website: Joi.string()
    .trim()
    .uri()
    .optional()
    .allow(null)
```

Meaning:

```text
missing → allowed
null    → allowed
valid URI → allowed
invalid URI → rejected
```

Again, you may later add stricter application-specific URL rules.

---

# 35. Status

For status:

```js
status: Joi.string()
    .trim()
    .lowercase()
    .valid("active", "inactive")
    .required()
```

Now:

```text
"ACTIVE"
```

can be normalized to:

```text
"active"
```

depending on Joi's conversion settings.

---

# 36. Putting it all together

Here's a realistic user schema:

```js
const userSchema = Joi.object({
    name: Joi.string()
        .trim()
        .min(2)
        .max(50)
        .required(),

    username: Joi.string()
        .trim()
        .lowercase()
        .min(3)
        .max(20)
        .pattern(/^[a-z0-9_]+$/)
        .required(),

    email: Joi.string()
        .trim()
        .lowercase()
        .email()
        .required(),

    password: Joi.string()
        .min(8)
        .max(72)
        .required(),

    bio: Joi.string()
        .trim()
        .max(500)
        .allow(null)
        .optional(),

    website: Joi.string()
        .trim()
        .uri()
        .allow(null)
        .optional(),

    status: Joi.string()
        .lowercase()
        .valid("active", "inactive")
        .required()
});
```

This is already a much more professional schema than:

```js
const userSchema = Joi.object({
    name: Joi.string(),
    username: Joi.string(),
    email: Joi.string(),
    password: Joi.string()
});
```

---

# 37. But don't overvalidate

This is another important professional lesson.

Suppose you decide:

```js
name: Joi.string()
    .pattern(/^[A-Za-z]+$/)
```

Now:

```text
Rahul Kumar
```

fails.

That's probably not what you want.

Or:

```js
username: Joi.string()
    .pattern(/^[a-z]+$/)
```

Now:

```text
rahul123
```

fails.

Maybe your product actually wants numbers.

So always ask:

> What does the application actually require?

Not:

> What is the most restrictive validation I can write?

---

# 38. Validation should match business requirements

Think:

```text
Business requirement
        ↓
Validation rule
```

Not:

```text
Cool regex
        ↓
Force it onto users
```

For example:

```text
Requirement:
Username may contain lowercase letters,
numbers and underscores.

        ↓

Regex:
^[a-z0-9_]+$
```

That's good.

---

# 39. Order of rules

You will often see:

```js
email: Joi.string()
    .trim()
    .lowercase()
    .email()
    .required()
```

Don't obsess over memorizing a perfect ordering.

The important thing is understanding the roles:

```text
string()
    ↓
type

trim()
lowercase()
    ↓
normalization

min()
max()
pattern()
email()
valid()
    ↓
constraints

required()
optional()
allow(null)
    ↓
presence/value behavior
```

Think in terms of purpose rather than memorizing syntax.

---

# 40. Validation vs sanitization

This lesson also introduces another important backend concept.

You may hear:

> "Sanitize the input."

That can mean different things depending on context.

For example:

```js
.trim()
.lowercase()
```

are transformations/normalization.

But escaping HTML, removing dangerous content, or encoding output are different security concerns.

Don't assume:

```text
Joi validation
=
complete sanitization
=
XSS protection
```

It doesn't.

Security is layered.

---

# 41. A strong MERN architecture

Eventually, your request flow should look something like:

```text
Client
  │
  ▼
Express
  │
  ▼
Validation Middleware
  │
  ▼
Joi
  │
  ├── invalid → 400
  │
  ▼
Validated Input
  │
  ▼
Controller
  │
  ▼
Service
  │
  ▼
Repository
  │
  ▼
MongoDB
```

Joi's string rules help make sure the data crossing the boundary has the expected shape.

# 🧠 Mental Model

For every string field, ask five questions:

```text
1. Is it required?
       ↓
   required()

2. Can it be null?
       ↓
   allow(null)

3. How long can it be?
       ↓
   min() / max()

4. What format should it have?
       ↓
   email() / uri() / pattern() / etc.

5. Should it be normalized?
       ↓
   trim() / lowercase() / uppercase()
```

For example:

```js
email: Joi.string()
    .trim()
    .lowercase()
    .email()
    .required()
```

You can mentally read that as:

```text
email
 ↓
must be string
 ↓
remove surrounding whitespace
 ↓
normalize to lowercase
 ↓
must have email format
 ↓
must exist
```

# 🔑 Final Takeaway

The most useful Joi string rules you'll use repeatedly are:

```text
Joi.string()
    .min()
    .max()
    .length()
    .trim()
    .lowercase()
    .uppercase()
    .email()
    .pattern()
    .alphanum()
    .uri()
    .valid()
    .required()
    .optional()
    .allow(null)
```

Don't memorize all of them at once.

Start with these:

```text
string()
min()
max()
trim()
email()
pattern()
valid()
required()
optional()
allow(null)
```

Those will cover a huge portion of your MERN backend validation.
