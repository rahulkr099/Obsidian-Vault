# Lesson 9.9 — Joi Number, Boolean, and Date Validation

In Lesson 9.8, we focused on strings.

Now we'll validate three other types that appear constantly in MERN APIs:

```text
Number
Boolean
Date
```

These are especially important for:

- pagination
    
- prices
    
- quantities
    
- ages
    
- ratings
    
- flags
    
- timestamps
    
- date ranges
    
- filtering
    

The goal isn't just to learn the Joi methods. We want to understand **how to design safe API input rules**.

---

# 1. Joi Number

The basic rule is:

```js
Joi.number()
```

Example:

```js
const schema = Joi.object({
    age: Joi.number()
});
```

This expects:

```json
{
  "age": 22
}
```

rather than:

```json
{
  "age": "hello"
}
```

---

# 2. `.integer()`

Usually, some values should be whole numbers.

For example:

```text
age
quantity
page
limit
```

For these, use:

```js
Joi.number().integer()
```

Example:

```js
age: Joi.number()
    .integer()
    .required()
```

Now:

```text
22    → valid
25    → valid
22.5  → invalid
```

This is much better than:

```js
age: Joi.number()
```

because an age like `22.7` usually doesn't make sense in this API context.

---

# 3. `.min()`

For numbers, `.min()` specifies the minimum numeric value.

```js
age: Joi.number()
    .integer()
    .min(18)
```

Meaning:

```text
age >= 18
```

So:

```text
18 → valid
25 → valid
17 → invalid
```

This is different from the string version of `.min()`.

For a string:

```js
Joi.string().min(8)
```

means:

```text
minimum 8 characters
```

For a number:

```js
Joi.number().min(8)
```

means:

```text
minimum numeric value = 8
```

---

# 4. `.max()`

Similarly:

```js
age: Joi.number()
    .integer()
    .min(18)
    .max(100)
```

means:

```text
18 <= age <= 100
```

This is useful because it prevents obviously invalid input.

---

# 5. `.greater()`

Sometimes you need a strict comparison.

```js
Joi.number().greater(0)
```

means:

```text
value > 0
```

Notice the difference:

```text
min(0)
```

means:

```text
value >= 0
```

while:

```text
greater(0)
```

means:

```text
value > 0
```

So:

```text
0
```

would be accepted by `.min(0)` but rejected by `.greater(0)`.

---

# 6. `.less()`

The opposite:

```js
Joi.number().less(100)
```

means:

```text
value < 100
```

This is useful when the boundary itself should not be accepted.

---

# 7. `.greater()` vs `.min()`

Remember this:

```text
min(10)
    ↓
>= 10
```

while:

```text
greater(10)
    ↓
> 10
```

Similarly:

```text
max(10)
    ↓
<= 10

less(10)
    ↓
< 10
```

This tiny difference matters in real APIs.

---

# 8. `.multiple()`

Suppose a number must be a multiple of 5:

```js
quantity: Joi.number()
    .integer()
    .multiple(5)
```

Then:

```text
5   → valid
10  → valid
15  → valid
12  → invalid
```

This can be useful for APIs where values move in fixed steps.

For example:

```text
storage size
batch size
discount increments
```

when your business rules require it.

---

# 9. `.precision()`

You may need to restrict decimal precision.

For example:

```js
price: Joi.number().precision(2)
```

Conceptually:

```text
10.25 → valid
10.50 → valid
10.999 → may be converted/handled according to Joi's conversion behavior
```

But there's an important backend lesson here:

> **Don't rely on JavaScript floating-point numbers for financial calculations just because Joi validates decimal places.**

Validation and numerical accuracy are separate problems.

We'll discuss money handling more deeply later.

---

# 10. Price validation

Suppose you're building an e-commerce API.

You might start with:

```js
price: Joi.number()
    .greater(0)
    .required()
```

This prevents:

```text
0
-10
-500
```

and requires:

```text
price > 0
```

You could also use:

```js
price: Joi.number()
    .greater(0)
    .precision(2)
    .required()
```

if your API expects values with at most two decimal places.

---

# 11. Quantity validation

For product quantity:

```js
quantity: Joi.number()
    .integer()
    .min(1)
    .required()
```

This gives:

```text
1  → valid
2  → valid
100 → valid

0    → invalid
-1   → invalid
1.5  → invalid
```

This is a very common schema.

---

# 12. Pagination

Now we reach one of the most useful applications of number validation.

Imagine:

```http
GET /api/v1/products?page=2&limit=20
```

Your query parameters arrive as strings:

```text
page  = "2"
limit = "20"
```

You can validate them with Joi.

For example:

```js
const paginationSchema = Joi.object({
    page: Joi.number()
        .integer()
        .min(1)
        .default(1),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(20)
});
```

This says:

```text
page
    integer
    minimum 1
    default 1

limit
    integer
    minimum 1
    maximum 100
    default 20
```

---

# 13. Why `limit.max(100)` is important

Imagine the client sends:

```http
GET /products?limit=1000000000
```

Without a reasonable limit, your application might attempt to process a huge amount of data.

So:

```js
limit: Joi.number()
    .integer()
    .min(1)
    .max(100)
```

creates a boundary.

Think:

```text
Client
  │
  │ limit=1000000000
  ▼
Joi
  │
  └── rejected
```

This is one reason validation is also part of defensive backend engineering.

---

# 14. `.default()`

We just used:

```js
.default(1)
```

This means:

> If the value isn't provided, use this default.

Example:

```js
page: Joi.number()
    .integer()
    .min(1)
    .default(1)
```

If the request is:

```http
GET /products
```

you can end up with:

```js
{
    page: 1
}
```

depending on how you perform validation and use the validated result.

---

# 15. Don't confuse `.default()` with `.required()`

These are different:

```js
page: Joi.number().default(1)
```

means:

```text
If missing → use 1
```

while:

```js
page: Joi.number().required()
```

means:

```text
If missing → error
```

You generally don't need both:

```js
page: Joi.number()
    .required()
    .default(1)
```

because their intentions conflict.

Think:

```text
required()
    → client must provide it

default()
    → client doesn't have to provide it
```

---

# 16. Number `.allow(null)`

You can allow null:

```js
age: Joi.number()
    .integer()
    .min(0)
    .allow(null)
```

Now:

```text
25   → valid
null → valid
```

while invalid numeric values are still rejected.

This is useful for optional profile information.

---

# 17. Boolean validation

The basic boolean rule:

```js
Joi.boolean()
```

Example:

```js
isActive: Joi.boolean()
```

Valid conceptual values:

```json
{
  "isActive": true
}
```

and:

```json
{
  "isActive": false
}
```

---

# 18. `.truthy()` and `.falsy()`

This is particularly interesting for HTTP requests.

Remember:

```http
GET /users?active=true
```

Query parameters arrive as text.

So the application may receive:

```text
"true"
```

rather than the JavaScript boolean:

```js
true
```

Joi's boolean conversion behavior can be configured to recognize specific representations.

For example:

```js
isActive: Joi.boolean()
    .truthy("true")
    .falsy("false")
```

The exact conversion behavior depends on Joi's conversion settings.

The important concept is:

```text
HTTP input
    ↓
string representation
    ↓
Joi
    ↓
boolean
```

---

# 19. Boolean `.sensitive()`

Joi supports marking some schemas as sensitive.

For example:

```js
password: Joi.string().sensitive()
```

This can help prevent sensitive values from being exposed in validation error details.

This becomes useful for:

```text
password
API secrets
tokens
other sensitive input
```

It's another example of thinking about validation as part of a larger security design.

---

# 20. Boolean `.default()`

You can also use defaults:

```js
isActive: Joi.boolean().default(true)
```

Meaning:

```text
missing
  ↓
true
```

This is useful for fields such as:

```text
isActive
notificationsEnabled
publicProfile
```

when your business rules define a sensible default.

---

# 21. Boolean `.required()`

If the client must explicitly provide a boolean:

```js
isActive: Joi.boolean().required()
```

Now:

```json
{
  "isActive": true
}
```

works.

And:

```json
{}
```

fails.

---

# 22. A common boolean mistake

Don't do this:

```js
isActive: Joi.string()
    .valid("true", "false")
```

unless your API intentionally wants strings.

Usually, if the concept is a boolean, model it as:

```js
Joi.boolean()
```

Your API should represent the data according to what it actually means.

---

# 23. Date validation

Now let's look at dates.

Basic rule:

```js
Joi.date()
```

Example:

```js
birthDate: Joi.date()
```

This tells Joi that the value should represent a valid date.

---

# 24. `.iso()`

For APIs, ISO-style dates are usually a good choice.

```js
birthDate: Joi.date().iso()
```

Example:

```text
2026-08-25
```

or an ISO date-time representation such as:

```text
2026-08-25T10:30:00Z
```

The exact accepted forms depend on Joi's date parsing rules.

The important point is:

> Define a predictable date format at your API boundary.

---

# 25. Why ISO dates are useful

Compare:

```text
08/25/2026
25/08/2026
2026/08/25
2026-08-25
```

Some are ambiguous depending on locale.

But:

```text
2026-08-25
```

is much easier for systems to exchange consistently.

For APIs, standardized date representations are usually preferable.

---

# 26. `.min()` for dates

Joi's date schema can also use minimum dates.

Conceptually:

```js
startDate: Joi.date()
    .min("now")
```

This means the date should not be before the current time, depending on the exact validation context.

But be careful:

```text
"today"
```

and:

```text
"now"
```

are not necessarily the same thing.

For a date-only field such as:

```text
2026-08-25
```

you may need to think carefully about time zones and whether you're comparing:

```text
calendar dates
```

or:

```text
timestamps
```

---

# 27. `.max()` for dates

Similarly:

```js
birthDate: Joi.date()
    .max("now")
```

can ensure that a birth date isn't in the future.

This is a common validation rule.

For example:

```js
birthDate: Joi.date()
    .iso()
    .max("now")
    .required()
```

Conceptually:

```text
birthDate <= current date/time
```

---

# 28. Start date and end date

A very common API request is:

```json
{
  "startDate": "2026-08-01",
  "endDate": "2026-08-25"
}
```

You want:

```text
startDate <= endDate
```

This is called **cross-field validation**.

You can't fully express that simply by validating each field independently.

For example:

```js
startDate: Joi.date().iso(),
endDate: Joi.date().iso()
```

only tells us:

```text
startDate is a date
endDate is a date
```

It doesn't automatically tell us:

```text
startDate comes before endDate
```

We'll handle this using Joi references and object-level validation in a later lesson.

---

# 29. Date range APIs

Imagine:

```http
GET /analytics?startDate=2026-08-01&endDate=2026-08-25
```

Your validation might eventually enforce:

```text
startDate
    valid ISO date

endDate
    valid ISO date

startDate <= endDate

range <= 90 days
```

Notice how the last two are business/API rules rather than simple type validation.

This distinction becomes important as your schemas become more advanced.

---

# 30. Number ranges

The same idea applies to numbers.

Suppose a rating must be:

```text
1 through 5
```

Use:

```js
rating: Joi.number()
    .integer()
    .min(1)
    .max(5)
    .required()
```

Now:

```text
1 → valid
3 → valid
5 → valid

0 → invalid
6 → invalid
4.5 → invalid
```

Very clean.

---

# 31. Percentage

For a percentage:

```js
discount: Joi.number()
    .min(0)
    .max(100)
```

This gives:

```text
0 <= discount <= 100
```

If decimals are allowed:

```text
10.5
```

can be valid.

If only whole percentages are allowed:

```js
discount: Joi.number()
    .integer()
    .min(0)
    .max(100)
```

---

# 32. Rating

For a 1–5 rating:

```js
rating: Joi.number()
    .min(1)
    .max(5)
    .required()
```

If only whole stars are allowed:

```js
rating: Joi.number()
    .integer()
    .min(1)
    .max(5)
    .required()
```

If half-stars are allowed:

```text
1
1.5
2
2.5
...
5
```

then don't use `.integer()`.

This is a perfect example of:

> Validation should follow product requirements.

---

# 33. Page and limit schema

Let's create a reusable pagination schema:

```js
const paginationSchema = Joi.object({
    page: Joi.number()
        .integer()
        .min(1)
        .default(1),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(20)
});
```

This is a pattern you'll use again and again.

Think:

```text
page
  ↓
positive integer
  ↓
default 1

limit
  ↓
1–100
  ↓
default 20
```

---

# 34. Offset pagination

Some APIs use:

```text
offset
limit
```

instead of:

```text
page
limit
```

Schema:

```js
const schema = Joi.object({
    offset: Joi.number()
        .integer()
        .min(0)
        .default(0),

    limit: Joi.number()
        .integer()
        .min(1)
        .max(100)
        .default(20)
});
```

Notice:

```text
offset → min(0)
```

because zero is a valid starting position.

---

# 35. Number validation is not database validation

Suppose:

```js
price: Joi.number()
    .greater(0)
```

This means:

> The request contains a positive number.

It does **not** mean:

> The product's price is correct according to our business rules.

For example:

```text
Current database price = ₹500
Client sends price = ₹1
```

Joi may say:

```text
valid number
```

But your business logic may say:

```text
client isn't allowed to set price
```

That's why we keep responsibilities separate.

---

# 36. Validation vs authorization again

Suppose:

```json
{
  "price": 1
}
```

Joi checks:

```text
Is 1 a valid number?
```

Authorization checks:

```text
Is this user allowed to change the price?
```

Business logic checks:

```text
Is changing the price allowed in this situation?
```

These are three different questions.

---

# 37. Date + timezone warning

This is one of the most important things to understand early.

A date can mean different things:

```text
2026-08-25
```

might mean:

> A calendar date.

While:

```text
2026-08-25T10:30:00Z
```

means:

> A specific point in time.

These aren't always interchangeable.

For example:

```text
birthday
```

is often a calendar date.

While:

```text
createdAt
updatedAt
loginAt
```

are timestamps.

Your API should model them appropriately.

---

# 38. Birth date example

For a birth date:

```js
birthDate: Joi.date()
    .iso()
    .max("now")
    .required()
```

Conceptually:

```text
must be valid date
        +
must not be in the future
        +
must be provided
```

You may later want additional age-related rules.

For example:

```text
minimum age = 18
```

But that becomes a more advanced cross-field/date calculation.

---

# 39. Created timestamps

Usually the client shouldn't control:

```text
createdAt
updatedAt
```

So instead of:

```js
createdAt: Joi.date()
```

you may want:

```js
createdAt: Joi.forbidden(),
updatedAt: Joi.forbidden()
```

for a client-facing update schema.

The server/database should manage those values.

This connects back to our previous lesson about:

```text
forbidden()
```

and unknown fields.

---

# 40. A realistic product schema

Let's combine number, boolean, date, and string validation:

```js
const productSchema = Joi.object({
    name: Joi.string()
        .trim()
        .min(2)
        .max(100)
        .required(),

    price: Joi.number()
        .greater(0)
        .precision(2)
        .required(),

    quantity: Joi.number()
        .integer()
        .min(0)
        .required(),

    rating: Joi.number()
        .min(0)
        .max(5)
        .optional(),

    isActive: Joi.boolean()
        .default(true),

    availableFrom: Joi.date()
        .iso()
        .optional(),

    role: Joi.forbidden()
}).unknown(false);
```

Now we have a strong API contract.

# 42. Common beginner mistakes

## Mistake 1

```js
age: Joi.number()
```

and assuming:

```text
age = -500
```

will be rejected.

It won't necessarily be rejected just because it's a number.

Instead:

```js
age: Joi.number()
    .integer()
    .min(0)
```

---

## Mistake 2

```js
quantity: Joi.number()
```

and accepting:

```text
2.5
```

when quantity must be whole.

Use:

```js
.integer()
```

---

## Mistake 3

```js
limit: Joi.number()
    .min(1)
```

without a maximum.

A client could request an unnecessarily large page size.

Use something like:

```js
.max(100)
```

based on your application's requirements.

---

# 43. Common beginner mistake: trusting dates

Don't assume:

```js
Joi.date()
```

means the date is semantically correct.

For example:

```text
birthDate = tomorrow
```

might be syntactically valid as a date.

But it doesn't make business sense.

So you may need:

```js
.max("now")
```

or additional application logic.

---

# 44. Common beginner mistake: using strings for everything

You might be tempted to define:

```js
age: Joi.string()
price: Joi.string()
quantity: Joi.string()
isActive: Joi.string()
```

because HTTP query parameters often arrive as strings.

Don't design your schema around the transport representation alone.

Think about the **meaning of the data**.

```text
age       → number
price     → number
quantity  → number
isActive  → boolean
date      → date
```

Then let your validation/conversion layer handle the input representation appropriately.

---

# 45. Query parameters are special

Suppose:

```http
GET /products?page=2&limit=20
```

HTTP query parameters are text.

So conceptually:

```text
"2"
"20"
```

may need to become:

```js
2
20
```

Joi can perform conversion when validation is configured to allow it.

This is one reason you should always work with the **validated value returned by Joi**, rather than assuming `req.query` has exactly the types you want.

We'll build this properly when we create validation middleware.

---

# 46. Don't mutate `req.query` blindly

Avoid doing random conversions everywhere:

```js
req.query.page = Number(req.query.page);
req.query.limit = Number(req.query.limit);
```

throughout your controllers.

Instead:

```text
Request
   ↓
Validation
   ↓
Validated + normalized data
   ↓
Controller
```

This keeps type conversion in one predictable place.

---

# 47. The architecture we're building toward

We're gradually moving toward:

```text
HTTP Request
      │
      ▼
┌─────────────────────┐
│ Validation Middleware│
└──────────┬──────────┘
           │
           ▼
       Joi Schema
           │
     ┌─────┴─────┐
     │           │
  Invalid       Valid
     │           │
     ▼           ▼
   Error     Validated Data
                 │
                 ▼
             Controller
                 │
                 ▼
              Service
                 │
                 ▼
             Repository
```

So when we later create your reusable validation middleware, these schemas will become the rules that protect your API boundary.

# 🧠 Mental Model

For every **number**, ask:

```text
Is it a whole number?
    ↓
integer()

What's the minimum?
    ↓
min()

What's the maximum?
    ↓
max()

Must it be strictly greater?
    ↓
greater()

Must it be strictly smaller?
    ↓
less()

Does it need a default?
    ↓
default()
```

For every **boolean**:

```text
Is it actually boolean?
    ↓
boolean()

Does it need a default?
    ↓
default()

Can the API receive string representations?
    ↓
truthy()/falsy() where appropriate
```

For every **date**:

```text
Is it a date?
    ↓
date()

Should it follow ISO format?
    ↓
iso()

Can it be in the future?
    ↓
max()

Can it be before a certain date?
    ↓
min()
```

# 🔑 Final Takeaway

The most useful rules from today's lesson are:

```js
Joi.number()
Joi.number().integer()

.min()
.max()
.greater()
.less()
.multiple()
.precision()

Joi.boolean()
.truthy()
.falsy()
.default()

Joi.date()
.iso()
.min()
.max()
```

And remember the bigger lesson:

> **Don't merely validate the data type. Validate the range and meaning of the data.**

For example:

```js
quantity: Joi.number()
    .integer()
    .min(1)
    .max(100)
    .required()
```

is much more useful than:

```js
quantity: Joi.number()
```

because your API isn't just saying:

> "Give me a number."

It's saying:

> "Give me a whole number between 1 and 100, and you must provide it."

That is what makes validation a real **API contract** rather than just a type check.
