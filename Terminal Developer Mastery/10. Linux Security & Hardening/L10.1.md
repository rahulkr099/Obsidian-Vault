# Lesson 10.1 — Introduction to Linux Security 🔐

**Module 10: Linux Security & Hardening**  
**Level:** Intermediate → Advanced

Linux security is not about installing one security tool and declaring the server "secure." It is about **reducing attack opportunities, limiting damage, detecting suspicious activity, and recovering when something goes wrong.**

As a backend developer, this matters because your Node.js application will eventually run on a Linux server.

---

# 1. What Is Linux Security?

Linux security means protecting:

- 👤 Users and accounts
    
- 📁 Files and directories
    
- ⚙️ Processes and services
    
- 🌐 Network connections
    
- 🔑 Credentials and secrets
    
- 🗄️ Application data
    
- 📝 Logs and audit records
    
- 🖥️ The operating system itself
    

Think of a production server like a building:

```text
                    INTERNET
                       │
                       ▼
                ┌──────────────┐
                │   Firewall   │
                └──────┬───────┘
                       │
             ┌─────────┴─────────┐
             │                   │
            SSH                HTTPS
             │                   │
             ▼                   ▼
        Admin Access          Nginx
                                 │
                                 ▼
                            Node.js API
                                 │
                                 ▼
                              MongoDB
```

Security means protecting **every layer**.

---

# 2. The CIA Triad

One of the most important concepts in security is the **CIA Triad**.

CIA means:

```text
C → Confidentiality
I → Integrity
A → Availability
```

## Confidentiality

Only authorized people should be able to access information.

Example:

```text
.env
database password
JWT secret
Razorpay secret
SSH private key
```

These should not be publicly accessible.

For example:

```bash
ls -l .env
```

You might want:

```text
-rw------- .env
```

Only the owner can read/write it.

---

## Integrity

Data should not be modified by unauthorized people.

Example:

Suppose your Node.js application contains:

```text
server.js
```

An attacker shouldn't be able to modify:

```javascript
app.post("/login", ...)
```

and insert malicious code.

Linux permissions help protect application files.

---

## Availability

The system should remain available to legitimate users.

For example:

```text
Your API
   │
   ├── CPU exhausted
   ├── RAM exhausted
   ├── Disk full
   └── Network flooded
```

Your application could become unavailable.

Security therefore also involves:

- resource limits
    
- firewalling
    
- rate limiting
    
- monitoring
    
- backups
    
- disaster recovery
    

---

# 3. Why Linux Servers Get Attacked

A Linux server connected to the internet can potentially be discovered by attackers.

For example:

```text
Your Server
     │
     ├── Port 22   → SSH
     ├── Port 80   → HTTP
     ├── Port 443  → HTTPS
     ├── Port 3000  → Node.js
     └── Port 27017 → MongoDB
```

The more unnecessary services and ports you expose, the larger your **attack surface** becomes.

---

# 4. Attack Surface

The **attack surface** is everything an attacker could potentially interact with.

Imagine:

```text
                SERVER
                  │
       ┌──────────┼──────────┐
       │          │          │
      SSH        HTTP       API
       │          │          │
     Login      Nginx      Node.js
       │                     │
       │                  MongoDB
       │                     │
       └──────────────┬──────┘
                      │
                 Attack Surface
```

You want to minimize unnecessary exposure.

### Bad example

```text
Internet
   │
   ├── SSH
   ├── MongoDB
   ├── Redis
   ├── MySQL
   ├── Node
   ├── Admin panel
   └── Debug server
```

### Better

```text
Internet
   │
   ├── 80  → HTTP
   ├── 443 → HTTPS
   └── 22  → SSH
```

And internal services remain private:

```text
MongoDB → localhost/private network
Redis   → localhost/private network
Node    → localhost/private network
```

This is one of the most important production security principles.

---

# 5. Principle of Least Privilege ⭐

**Give a user/process only the permissions it actually needs.**

Suppose your Node.js application only needs to:

```text
read/write application files
connect to MongoDB
listen on localhost
```

It does **not** need:

```text
root access
```

Running everything as root is dangerous.

### Bad

```bash
sudo node server.js
```

If your application is compromised:

```text
Attacker
   ↓
Node.js vulnerability
   ↓
Node process
   ↓
ROOT
   ↓
Entire server
```

Potential damage is huge.

### Better

```text
Attacker
   ↓
Node.js vulnerability
   ↓
Node user
   ↓
Limited permissions
```

The attacker has a much smaller blast radius.

---

# 6. What Is `root`?

`root` is the most powerful user on a Linux system.

Check your current user:

```bash
whoami
```

Check UID:

```bash
id
```

You might see:

```text
uid=1000(rahul) gid=1000(rahul)
```

Root normally has:

```text
uid=0
```

You can check:

```bash
id root
```

Output:

```text
uid=0(root) gid=0(root)
```

---

# 7. Why Root Is Dangerous

Consider:

```bash
rm -rf /
```

A normal user may not have permission to do this.

Root potentially does.

That's why this:

```bash
sudo command
```

should be used carefully.

`sudo` essentially means:

> Execute this command with elevated privileges according to the system's sudo policy.

---

# 8. Defense in Depth

Never depend on one security mechanism.

Suppose you have:

```text
SSH key
```

That's good.

But production security should look more like:

```text
             Defense in Depth

                Firewall
                   ↓
              SSH Hardening
                   ↓
             SSH Keys
                   ↓
            User Permissions
                   ↓
            Service Isolation
                   ↓
            Application Security
                   ↓
              Monitoring
                   ↓
                Backups
```

If one layer fails, another layer can still protect you.

For example:

```text
Attacker
   ↓
SSH vulnerability
   ↓
Firewall restrictions
   ↓
Non-root account
   ↓
Limited file permissions
   ↓
Audit logs
   ↓
Alert
```

Security becomes much stronger through multiple layers.

# 9. Common Linux Attacks

You should understand the common attack categories.

## 9.1 Brute-force attacks

An attacker repeatedly tries passwords:

```text
admin
123456
password
root
qwerty
...
```

SSH servers are common targets.

Protection:

```text
SSH keys
+
disable password login
+
fail2ban
+
firewall
```

---

## 9.2 Privilege Escalation

Attacker starts with:

```text
normal user
```

and attempts to become:

```text
root
```

Example:

```text
Web vulnerability
      ↓
Application user
      ↓
Privilege escalation
      ↓
root
```

This is why:

- patching
    
- least privilege
    
- service isolation
    
- secure permissions
    

are important.

---

## 9.3 Malware

Malicious software can be installed after compromise.

Examples include:

```text
cryptominers
backdoors
trojans
botnet software
```

An attacker might secretly use your server's CPU for cryptocurrency mining.

You might notice:

```bash
top
```

showing unexpectedly high CPU usage.

---

## 9.4 Web Application Attacks

Your Linux server may be secure but your application may still be vulnerable.

For example:

```text
Internet
   ↓
Nginx
   ↓
Node.js
   ↓
Vulnerable API
```

Possible attacks include:

- SQL/NoSQL injection
    
- command injection
    
- authentication attacks
    
- insecure file uploads
    
- SSRF
    
- XSS
    
- broken authorization
    

This is why Linux security and application security must work together.

---

## 9.5 Denial of Service

An attacker sends excessive traffic or requests:

```text
Attacker
   │
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   └── ...
          ↓
       Server
          ↓
       CPU/RAM
          ↓
      Application
          ↓
        DOWN
```

Protection can include:

- rate limiting
    
- firewall rules
    
- reverse proxy
    
- resource limits
    
- CDN/WAF
    
- monitoring

# 10. Security Lifecycle

Security isn't a one-time task.

A good security lifecycle looks like:

```text
       Identify
          ↓
       Protect
          ↓
        Detect
          ↓
       Respond
          ↓
       Recover
          ↓
       Improve
          │
          └──────────────► Identify
```

Let's understand this.

### 1. Identify

Find what needs protection.

```text
Users
SSH
API
Database
Secrets
Files
Logs
```

### 2. Protect

Implement security controls.

```text
Firewall
SSH keys
Permissions
TLS
Backups
```

### 3. Detect

Find suspicious activity.

```text
auditd
journalctl
fail2ban
monitoring
```

### 4. Respond

Something happened.

```text
Detect
 ↓
Investigate
 ↓
Contain
```

### 5. Recover

Restore the system.

```text
Backup
 ↓
Restore
 ↓
Verify
 ↓
Return to production
```

### 6. Improve

Ask:

> Why did this happen and how can we prevent it next time?

# 11. Security Is Not Just Tools

A common beginner mistake is thinking:

```text
Install fail2ban
       +
Install antivirus
       =
Secure server
```

Not true.

Security is a combination of:

```text
People
+
Processes
+
Configuration
+
Software
+
Monitoring
+
Backups
```

For example, even with a firewall:

```text
Firewall ✓

SSH password = weak
Root login = enabled
MongoDB = public
.env = 777
Node = running as root
No backups
No monitoring
```

The server is still badly configured.

---

# 12. Security Baseline

Before deploying a backend application, you should have a basic baseline.

Something like:

```text
✓ Updated OS
✓ Non-root admin user
✓ SSH keys
✓ Root SSH login disabled
✓ Password SSH login disabled
✓ Firewall enabled
✓ Only required ports exposed
✓ Fail2ban configured
✓ Services running with least privilege
✓ Secrets protected
✓ TLS enabled
✓ Logs available
✓ Monitoring enabled
✓ Backups configured
✓ Restore tested
```

We'll build this throughout Module 10.

# 15. Think Like an Attacker

A very useful security habit is to ask:

> "If I were an attacker, what could I interact with?"

For example:

```bash
ss -tulpn
```

might show:

```text
LISTEN 0 128 0.0.0.0:22
LISTEN 0 128 0.0.0.0:80
LISTEN 0 128 0.0.0.0:443
LISTEN 0 128 127.0.0.1:3000
```

You should immediately think:

```text
22   → SSH → Is it hardened?
80   → HTTP → Is HTTPS configured?
443  → HTTPS → Is TLS configured correctly?
3000 → Node → Why is it localhost only?
```

That mindset is much more valuable than memorizing commands.

# 17. Interview Questions

### Q1. What is the CIA Triad?

**Answer:**

The CIA Triad represents:

```text
Confidentiality
Integrity
Availability
```

It is a basic model for understanding information security requirements.

---

### Q2. What is the principle of least privilege?

Give users and processes **only the permissions they need to perform their job**, and no more.

---

### Q3. What is an attack surface?

The attack surface is the collection of possible entry points that an attacker could use to interact with or compromise a system.

---

### Q4. Why shouldn't applications run as root?

Because if the application is compromised, the attacker may inherit root privileges and gain much greater control over the server.

---

### Q5. What is defense in depth?

Using multiple independent security controls so that failure of one layer does not automatically compromise the entire system.

---

# 18. Key Takeaways

Remember these five ideas:

```text
1. Minimize attack surface
2. Follow least privilege
3. Never trust a single security layer
4. Detect and log suspicious activity
5. Always have tested backups
```

A secure production server isn't:

```text
"Impossible to hack"
```

Instead, the goal is:

```text
Harder to attack
      ↓
Harder to compromise
      ↓
Limited damage
      ↓
Detected quickly
      ↓
Recovered quickly
```

That's the mindset you should carry throughout the rest of **Module 10**.
