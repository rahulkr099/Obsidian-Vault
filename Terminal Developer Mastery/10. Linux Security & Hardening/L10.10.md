# Lesson 10.10 — Secure Networking 🌐🔐

**Module 10 — Linux Security & Hardening**  
**Part 4: Network Security**

In the previous lessons, we learned:

```text
10.8 → Firewall
10.9 → Fail2ban
```

Now we're going one level higher.

A production server shouldn't simply be:

```text
Internet → Server
```

Instead, we want:

```text
                    INTERNET
                       │
                       ▼
                  DNS / CDN
                       │
                       ▼
                 TLS / HTTPS
                       │
                       ▼
                   FIREWALL
                       │
                       ▼
                    NGINX
                       │
                       ▼
                  Node.js API
                       │
              ┌────────┴────────┐
              ▼                 ▼
           MongoDB            Redis
          PRIVATE             PRIVATE
```

Today we'll learn how to build this kind of secure network architecture.

---

# 1. What Is Secure Networking?

Secure networking means designing communication so that:

- unauthorized users cannot access services
    
- data is protected while travelling
    
- services expose only necessary ports
    
- internal services aren't unnecessarily public
    
- certificates are managed correctly
    
- networks are segmented
    
- administrators have controlled access
    

Think:

> **Who can communicate with whom, through which protocol, on which port, and under what conditions?**

That is the core question of network security.

---

# 2. The Three Main Network Security Goals

A secure network generally protects:

### Confidentiality

Prevent others from reading data.

```text
Client
  │
  │ encrypted
  ▼
Server
```

TLS/HTTPS helps here.

---

### Integrity

Prevent unauthorized modification.

For example:

```text
Client
  │
  │ "Transfer ₹500"
  ▼
Server
```

An attacker shouldn't be able to change it to:

```text
"Transfer ₹50,000"
```

TLS provides integrity protection for the connection.

---

### Availability

Keep services reachable for legitimate users.

Examples:

```text
Firewall
Rate limiting
DDoS protection
Redundancy
Load balancing
```

Together:

```text
CIA
│
├── Confidentiality
├── Integrity
└── Availability
```

---

# 3. Public vs Private Network

One of the most important production concepts is:

> **Not every service needs to be reachable from the internet.**

Imagine:

```text
Internet
   │
   ▼
Nginx
   │
   ▼
Node.js
   │
   ▼
MongoDB
```

Only Nginx may need public access.

Node.js:

```text
127.0.0.1:3000
```

MongoDB:

```text
127.0.0.1:27017
```

This creates a simple security boundary.

---

# 4. Public Services

Typical public-facing services:

```text
80   → HTTP
443  → HTTPS
```

Sometimes:

```text
22 → SSH
```

but SSH should ideally be restricted.

Public exposure should be minimized.

---

# 5. Private Services

Internal services might include:

```text
MongoDB
PostgreSQL
Redis
RabbitMQ
Node.js
Internal APIs
Monitoring systems
Admin dashboards
```

Example:

```text
Internet
   │
   ▼
Nginx
   │
   ▼
Node.js
   │
   ├── MongoDB
   └── Redis
```

The internet never directly reaches:

```text
MongoDB
Redis
Node.js
```

unless your architecture explicitly requires it.

---

# 6. Secure Ports

A port isn't automatically insecure.

The question is:

> **Who can access it?**

For example:

```text
443
```

is publicly accessible in most web applications.

That's normal.

But:

```text
27017
```

being publicly accessible is usually unnecessary for MongoDB.

So don't think:

```text
Port = dangerous
```

Think:

```text
Exposure + service + authentication + network source
```

Now we reach one of the most important technologies in modern web development:

> **TLS — Transport Layer Security**

TLS protects network communication.

For your MERN applications:

```text
Browser
   │
   │ HTTPS/TLS
   ▼
Nginx
   │
   ▼
```

# 8. HTTP vs HTTPS

Without HTTPS:

```text
Browser
   │
   │ HTTP
   │
   ▼
Server
```

With HTTPS:

```text
Browser
   │
   │ encrypted TLS connection
   ▼
Server
```

HTTPS is:

```text
HTTP
 +
TLS
```

---

# 9. What Does TLS Provide?

TLS provides three major properties:

```text
Confidentiality
Integrity
Authentication
```

### Confidentiality

Others shouldn't be able to read the traffic.

### Integrity

Traffic shouldn't be silently modified.

### Authentication

The client can verify that it's communicating with the intended server, based on certificate validation.

---

# 10. HTTPS in Your MERN Architecture

A production application should generally look like:

```text
                     USER
                       │
                       │ HTTPS :443
                       ▼
                  ┌──────────┐
                  │  NGINX   │
                  └────┬─────┘
                       │
                       │ internal
                       ▼
                  Node.js API
                       │
                       ▼
                    MongoDB
```

Not:

```text
Browser
   │
   │ HTTP :3000
   ▼
Node.js
```

for a public production application.

---

# 11. TLS Certificates

TLS relies on certificates.

A certificate associates a domain name with a public key and contains information that allows clients to validate the server identity through a trusted certificate chain.

For example:

```text
example.com
     │
     ▼
TLS Certificate
     │
     ▼
Public Key
```

The browser validates the certificate before establishing the secure connection.

---

# 12. Certificate Authority

Certificates are normally issued by a:

> **Certificate Authority (CA)**

Examples include:

- Let's Encrypt
    
- DigiCert
    
- GlobalSign
    
- Sectigo
    

The basic trust model is:

```text
Browser
   │
   ▼
Trusted CA
   │
   ▼
Server Certificate
   │
   ▼
example.com
```

Your browser already contains trusted root CA certificates.

---

# 13. Let's Encrypt

For many web developers, one of the most useful certificate authorities is:

> **Let's Encrypt**

It provides publicly trusted TLS certificates through automated certificate issuance.

A common production setup is:

```text
Domain
   ↓
DNS
   ↓
Server
   ↓
Nginx
   ↓
Let's Encrypt certificate
   ↓
HTTPS
```

---

# 14. Certificate Expiration

Certificates have expiration dates.

Imagine:

```text
Certificate
    │
    ├── Issued: January
    │
    └── Expires: March
```

If you don't renew it:

```text
Certificate expired
       ↓
Browser warning
       ↓
Production outage
```

That's why certificate automation is extremely important.

---

# 15. Automatic Certificate Renewal

In production:

```text
Certificate
    ↓
Automatic renewal
    ↓
Install renewed certificate
    ↓
Reload Nginx
```

Don't rely on:

```text
"Someone will remember to renew it."
```

Automation is better.

This connects directly to the **Security Automation** lesson later in this module.

---

# 16. TLS Private Key

A certificate contains public information.

But the corresponding private key must remain secret.

Think:

```text
Certificate
    │
    └── Public information

Private key
    │
    └── SECRET
```

Never:

```text
git add private-key.pem
```

Never:

```text
commit TLS private keys
```

Never:

```text
paste private keys into public repositories
```

---

# 17. Private Key Permissions

TLS private keys should have restrictive permissions.

For example:

```bash
chmod 600 private.key
```

Then:

```text
Owner → read/write
Group → none
Others → none
```

Depending on how your web server runs, the exact ownership and permissions must allow the service to read the key while preventing unnecessary access.

---

# 18. TLS Versions

Modern systems should use current secure TLS versions.

The important modern version is:

```text
TLS 1.3
```

TLS 1.2 is also still widely supported.

Avoid obsolete protocols such as:

```text
SSLv2
SSLv3
TLS 1.0
TLS 1.1
```

when configuring modern production systems.

---

# 19. Don't Confuse SSL and TLS

You'll still hear people say:

```text
SSL certificate
```

But modern HTTPS uses:

> **TLS**

SSL is the older protocol family.

So technically:

```text
"SSL certificate"
```

is often just an informal term for a TLS certificate.

# 21. `curl` and HTTPS

You can test:

```bash

```

You might see:

```text

```

or:

```text
HTTP/1.1 301 Moved Permanently
```

```bash

```

# 22. HTTP → HTTPS Redirect

A common production setup:

```text
http://example.com
        │
        ▼
      301/308
        │
        ▼
https://example.com
```

This ensures users are directed to the encrypted connection.

# 23. Why Keep Port 80?

You might wonder:

> If HTTPS is secure, why allow port 80?

There are several reasons.

For example:

```text
HTTP :80
   ↓
Redirect
   ↓
HTTPS :443
```

Port 80 can also be useful for certain certificate-validation workflows.

But your actual application traffic should generally use HTTPS.

---

# 24. HSTS

Another important web-security mechanism is:

> **HSTS — HTTP Strict Transport Security**

It tells compatible browsers:

> Use HTTPS for this site.

Conceptually:

```text
Browser
   │
   │ HSTS policy
   ▼
Always use HTTPS
```

An HSTS header looks conceptually like:

```http
Strict-Transport-Security: max-age=31536000
```

Production HSTS configuration should be introduced carefully, especially before using options such as `includeSubDomains` or `preload`.

# 25. Secure DNS

Before your browser connects to:

```text
https://api.example.com
```

it needs to resolve:

```text
api.example.com
      ↓
IP address
```

DNS is therefore a critical part of your network architecture.

Basic flow:

```text
Browser
   ↓
DNS
   ↓
IP address
   ↓
Server
```

---

# 26. DNS Records

You'll commonly work with:

### A

Maps a hostname to IPv4.

```text
example.com → 203.0.113.10
```

### AAAA

Maps a hostname to IPv6.

```text
example.com → IPv6 address
```

### CNAME

Creates an alias.

```text
www.example.com
       ↓
example.com
```

### MX

Mail server routing.

### TXT

Used for various verification and security mechanisms.

---

# 27. DNS Security

DNS can be abused through:

```text
DNS spoofing
DNS hijacking
Cache poisoning
Misconfiguration
Domain takeover
```

So domain security is part of infrastructure security.

Protect:

```text
Domain registrar
DNS provider
DNS credentials
DNS records
```

especially carefully.

---

# 28. DNSSEC

DNSSEC adds cryptographic signatures to DNS data.

Its purpose is to help validate that DNS responses haven't been tampered with.

Conceptually:

```text
DNS request
    ↓
DNS response
    ↓
Signature verification
    ↓
Trusted result
```

DNSSEC is different from TLS.

TLS protects:

```text
Browser ↔ Website
```

DNSSEC protects the authenticity/integrity of DNS data.

---

# 29. DNSSEC vs HTTPS

Important interview distinction:

|Technology|Protects|
|---|---|
|HTTPS/TLS|Application network connection|
|DNSSEC|DNS data authenticity/integrity|

They solve different problems.

---

# 30. VPN

A:

> **VPN — Virtual Private Network**

creates a secure network connection between endpoints.

Conceptually:

```text
Laptop
   │
   │ encrypted tunnel
   ▼
VPN Server
   │
   ▼
Private Network
```

This can be useful for administration.

Instead of:

```text
Internet
   │
   ▼
SSH
   │
   ▼
Production Server
```

you can potentially use:

```text
Laptop
   │
   ▼
VPN
   │
   ▼
Private network
   │
   ▼
SSH
   │
   ▼
Server
```

---

# 31. VPN Does Not Mean "Automatically Secure"

A VPN creates a protected tunnel, but you still need:

```text
Authentication
Authorization
Firewall
Patch management
Logging
Key management
```

A compromised VPN account can still become a security problem.

# 32. WireGuard

One modern VPN technology worth knowing is:

> **WireGuard**

It is designed as a relatively simple, modern VPN protocol.

Architecture:

```text

  │ WireGuard

  └── Admin services
```

# 33. Network Segmentation

This is one of the most important advanced concepts.

Instead of putting everything on one network:

```text
Internet
   │
   └── Everything
```

divide your infrastructure:

```text
                 INTERNET
                    │
                    ▼
               PUBLIC NETWORK
                    │
                    ▼
              APPLICATION NETWORK
                    │
                    ▼
               DATABASE NETWORK
```

Now:

```text
Internet → Database
```

can be completely prohibited.

---

# 34. Example Segmentation

Imagine:

```text
Public subnet
   │
   └── Nginx

Application subnet
   │
   └── Node.js

Database subnet
   │
   └── MongoDB
```

Communication:

```text
Internet
   │
   ▼
Nginx
   │
   ▼
Node.js
   │
   ▼
MongoDB
```

But:

```text
Internet ─────X─────> MongoDB
```

This is significantly stronger than simply relying on MongoDB authentication.

---

# 35. Why Segmentation Matters

Suppose Nginx gets compromised.

Without segmentation:

```text
Nginx
 │
 ├── Node
 ├── MongoDB
 ├── Redis
 └── everything
```

With segmentation:

```text
Nginx
 │
 ▼
Node.js
 │
 ▼
MongoDB
```

The attacker has fewer possible paths.

This is called reducing the:

> **Attack surface**

and potentially limiting:

> **Lateral movement**

# 38. WAF

A:

> **Web Application Firewall**

operates at the HTTP/application layer.

A traditional firewall might say:

```text
Allow TCP 443
```

A WAF can inspect HTTP requests.

For example:

```text
POST /login
```

and potentially detect patterns associated with:

```text
SQL injection
XSS
malicious request patterns
automated abuse
```

A WAF is not a replacement for secure application code.

---

# 39. Firewall vs WAF

|Layer|Example|
|---|---|
|Network firewall|Port/IP rules|
|WAF|HTTP request rules|
|Application security|Secure Node.js code|

Think:

```text
Firewall
   ↓
"Can this network connection enter?"

WAF
   ↓
"Is this HTTP request suspicious?"

Application
   ↓
"Is this request authorized and safe?"
```

# 40. Reverse Proxy

```text

   │
   ▼

   ▼
```

- TLS termination

# 41. TLS Termination

A common architecture is:

```text
Browser
   │
   │ HTTPS
   ▼
Nginx
   │
   │ internal HTTP
   ▼
Node.js
```

Nginx terminates the public TLS connection.

However, whether the internal hop should also use TLS depends on your infrastructure.

---

# 42. When Internal TLS Matters

Suppose:

```text
Nginx
   │
   │ same machine
   ▼
Node.js
```

Using localhost may be reasonable.

But:

```text
Nginx
   │
   │ network
   ▼
Node.js on another machine
```

You should consider encrypting that connection too.

For example:

```text
Nginx
   │
   │ mTLS/TLS
   ▼
Application server
```

The security requirement depends on the network trust boundary.

---

# 43. mTLS

> **Mutual TLS**

means both sides authenticate each other.

Normal TLS:

```text
Client → verifies → Server
```

mTLS:

```text
Client ↔ verifies ↔ Server
```

This can be useful for:

```text
Internal microservices
Service-to-service communication
Private APIs
Zero-trust architectures
```

You don't necessarily need mTLS for a simple MERN application, but understanding it is valuable for advanced backend engineering.

---

# 44. Zero Trust

Traditional thinking:

```text
Inside network = trusted
Outside network = untrusted
```

Modern security increasingly follows:

> **Never automatically trust based only on network location.**

Instead:

```text
Identity
+
Authentication
+
Authorization
+
Device/context
+
Network policy
```

determine access.

This is the foundation of **Zero Trust** security models.

# 51. Common Secure-Networking Mistakes

## ❌ Mistake 1 — HTTP-only production

```text
http://example.com
```

Use HTTPS.

---

## ❌ Mistake 2 — Exposing MongoDB

```text
0.0.0.0:27017
```

Avoid unnecessary public database exposure.

---

## ❌ Mistake 3 — Exposing Node.js directly

```text
0.0.0.0:3000
```

Prefer a reverse proxy/private binding where appropriate.

---

## ❌ Mistake 4 — Leaking TLS private keys

Never commit:

```text
private.key
```

to Git.

---

## ❌ Mistake 5 — Forgetting certificate renewal

Expired certificates can cause outages.

---

## ❌ Mistake 6 — Ignoring IPv6

A service may be reachable through IPv6 even when you secured only IPv4.

---

## ❌ Mistake 7 — Trusting internal networks blindly

Internal networks can also be compromised.

---

## ❌ Mistake 8 — Treating VPN as a magic security solution

A VPN is a security layer, not a complete security strategy.

# 52. Interview Questions

### Q1. What does HTTPS provide?

HTTPS uses TLS to provide encryption, integrity protection, and server authentication for web communication.

---

### Q2. What is TLS?

TLS is a cryptographic protocol used to secure network communication.

---

### Q3. What is the difference between HTTP and HTTPS?

```text
HTTP
→ unencrypted application protocol

HTTPS
→ HTTP over TLS
```

---

### Q4. What is a certificate authority?

A trusted organization/system that issues certificates used to establish authenticated TLS connections.

---

### Q5. What is network segmentation?

Dividing infrastructure into separate network zones so access between components can be restricted.

---

### Q6. Why should databases normally be private?

Because exposing databases directly increases attack surface and allows attackers to interact with the database without going through application-level controls.

---

### Q7. What is a VPN?

A VPN creates an authenticated/encrypted tunnel between endpoints, allowing secure communication over an untrusted network.

---

### Q8. What is a WAF?

A Web Application Firewall inspects and filters HTTP/application-layer traffic based on security rules.

---

### Q9. What is mTLS?

Mutual TLS authenticates both sides of a TLS connection instead of only authenticating the server.

---

### Q10. What is Zero Trust?

A security model that avoids automatically trusting users/devices/services based only on network location and instead continuously applies identity, authentication, authorization, and policy controls.

# 55. The Most Important Mental Model

Whenever you deploy a service, ask these five questions:

```text
1. Who needs access?
2. From where?
3. On which port?
4. Is the connection encrypted?
5. Can the service be moved to a private network?
```

For example, MongoDB:

```text
Who?
→ Node.js

From where?
→ Same server/private network

Port?
→ 27017

Encrypted?
→ Depends on deployment requirements

Public?
→ No
```

That's secure network thinking.
