# Lesson 10.11 — System Services & systemd Security ⚙️🔐

**Module 10 — Linux Security & Hardening**  
**Part 5: Process & Service Security**

In the previous lessons, we secured:

```text
Users & permissions
        ↓
SSH
        ↓
Firewall
        ↓
Fail2ban
        ↓
TLS / networking
        ↓
Private services
```

Now we're going inside the server.

The question is:

> **What happens if one of my applications gets compromised?**

A production server should be designed so that even if a service is compromised, the attacker has **as little power as possible**.

That's where **systemd service security** becomes extremely useful.

---

# 1. What Is systemd?

`systemd` is the service and system manager used by many modern Linux distributions.

It manages things such as:

```text
SSH
Nginx
Docker
MongoDB
Node.js applications
Cron-like timers
Logging
Network services
```

You can inspect it with:

```bash
systemctl
```

For example:

```bash
systemctl status ssh
```

or:

```bash
systemctl status nginx
```

---

# 2. Why systemd Matters for Security

Imagine your Node.js application is compromised.

Bad architecture:

```text
Internet
   ↓
Node.js
   ↓
ROOT
   ↓
Entire server
```

If the Node.js process runs as `root`, an application vulnerability could potentially become a complete system compromise.

Better:

```text
Internet
   ↓
Nginx
   ↓
Node.js
   ↓
appuser
   ↓
Only application files
```

Now the attacker has much less authority.

This is:

> **Privilege separation**

---

# 3. Never Run Your Application as Root 🚨

Suppose:

```bash
sudo node server.js
```

This means your Node.js process runs with root privileges.

That's dangerous.

If your application gets exploited:

```text
Node.js vulnerability
       ↓
Attacker controls process
       ↓
Process = root
       ↓
Potential system-wide access
```

Instead:

```text
Node.js
   ↓
Dedicated user
   ↓
Limited permissions
```

This is one of the most important production practices you'll learn.

---

# 4. Principle of Least Privilege

We discussed this in Lesson 10.1.

The idea is:

> Give a service only the permissions it actually needs.

For example, your Node.js backend might need:

```text
Read application code
Read configuration
Write application logs
Access MongoDB
```

It probably does **not** need:

```text
Read /etc/shadow
Modify /boot
Control network interfaces
Access every user's home directory
Install packages
Modify system configuration
```

So:

```text
Required permissions
       ↓
Grant only those
       ↓
Everything else
       ↓
Deny
```

---

# 5. Dedicated Service Users

Suppose you have:

```text
Node.js
Nginx
MongoDB
Redis
```

Don't run all of them as the same user.

Instead:

```text
nodeapp
nginx
mongodb
redis
```

Conceptually:

```text
Node.js → nodeapp
Nginx   → www-data
MongoDB → mongodb
Redis   → redis
```

Now a compromise of one service doesn't automatically give the same identity access to another service's files.

---

# 6. Create a Dedicated Application User

For a test server, you might create:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin nodeapp
```

Let's understand this.

### `--system`

Creates a system account intended for services.

### `--no-create-home`

No normal home directory is required.

### `--shell /usr/sbin/nologin`

The account isn't intended for interactive login.

So:

```text
nodeapp
   │
   ├── service identity
   ├── no normal home
   └── no interactive shell
```

This is a good security pattern.

---

# 7. Why Disable Interactive Login?

Suppose the application user has:

```text
/bin/bash
```

An attacker who somehow obtains its credentials may be able to log in interactively.

Instead:

```text
nodeapp
    ↓
/usr/sbin/nologin
```

means:

> This account is intended for running a service, not for normal interactive administration.

Again, this is defense in depth.

---

# 8. Application Directory Ownership

Suppose your application is:

```text
/opt/myapp
```

You might configure:

```bash
sudo chown -R nodeapp:nodeapp /opt/myapp
```

But don't blindly use recursive ownership changes on production directories.

First inspect:

```bash
ls -la /opt/myapp
```

Understand which files actually need to belong to the service.

---

# 9. Better File Permissions

A common structure:

```text
/opt/myapp
├── server.js
├── package.json
├── node_modules/
├── config/
└── logs/
```

You might want:

```text
Application code
→ read-only

Configuration
→ restricted

Logs
→ writable only where required
```

Don't give the entire application directory unrestricted write access unless it's actually needed.

---

# 10. Why Read-Only Code Matters

Suppose your Node.js process can modify:

```text
server.js
```

If an attacker compromises the application:

```text
Attacker
   ↓
Node.js
   ↓
Modify server.js
   ↓
Persistent malicious code
```

Instead:

```text
Node.js
   ↓
Read application code
   X
Cannot modify application code
```

This makes persistence more difficult.

---

# 11. systemd Unit Files

A systemd service is defined using a unit file.

For example:

```text
/etc/systemd/system/myapp.service
```

A simple service could look like:

```ini
[Unit]
Description=My Node.js Application
After=network.target

[Service]
User=nodeapp
Group=nodeapp
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/node /opt/myapp/server.js
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

This is already much better than:

```bash
sudo node server.js
```

---

# 12. Understanding `[Unit]`

Example:

```ini
[Unit]
Description=My Node.js Application
After=network.target
```

### `Description`

Human-readable service description.

### `After`

Defines startup ordering.

It doesn't itself guarantee the dependency is available.

For example:

```text
network.target
      ↓
myapp.service
```

---

# 13. `[Service]`

This is where most of the interesting configuration happens.

```ini
[Service]
User=nodeapp
Group=nodeapp
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/node /opt/myapp/server.js
Restart=on-failure
```

The important security setting is:

```ini
User=nodeapp
```

Now the service runs as:

```text
nodeapp
```

instead of:

```text
root
```

---

# 14. `WorkingDirectory`

```ini
WorkingDirectory=/opt/myapp
```

This defines where the application runs.

Your application can then work with relative paths predictably.

It also makes the service configuration easier to understand.

---

# 15. `ExecStart`

```ini
ExecStart=/usr/bin/node /opt/myapp/server.js
```

This is the command systemd starts.

You can find the Node binary:

```bash
which node
```

or:

```bash
command -v node
```

For production systemd services, use a stable absolute path.

---

# 16. Restart Policy

For example:

```ini
Restart=on-failure
```

If the application crashes:

```text
Node.js crashes
      ↓
systemd detects failure
      ↓
systemd restarts service
```

This provides basic availability.

But don't use:

```ini
Restart=always
```

blindly.

A service that continuously crashes may enter a restart loop.

---

# 17. Restart Limits

systemd can control restart behavior.

For example:

```ini
RestartSec=5
```

means:

```text
Crash
 ↓
Wait 5 seconds
 ↓
Restart
```

You can also use rate limiting settings to prevent a broken service from restarting endlessly.

This protects system resources.

---

# 18. Environment Variables

Node.js applications often use:

```text
NODE_ENV
PORT
DATABASE_URL
JWT_SECRET
API_KEY
```

You can configure environment variables in systemd.

For example:

```ini
Environment="NODE_ENV=production"
Environment="PORT=3000"
```

But be careful with secrets.

---

# 19. Don't Put Secrets in Public Unit Files

Avoid:

```ini
Environment="JWT_SECRET=super-secret-value"
```

in a broadly readable service file.

Instead, use a protected environment file where appropriate:

```ini
EnvironmentFile=/etc/myapp/myapp.env
```

Then:

```bash
sudo chmod 600 /etc/myapp/myapp.env
```

and ensure ownership/permissions are appropriate.

---

# 20. Better Secret Architecture

Think:

```text
Application
    │
    ▼
Protected configuration
    │
    ▼
Secret
```

Not:

```text
GitHub
  │
  ▼
.env
  │
  ▼
Public repository
```

This connects directly to the security lessons we'll cover later.

```bash
sudo systemctl daemon-reload
```

> Reload the unit configuration.



To start automatically:


```text
enable + start
```

You'll see:

```text

```

if everything is healthy.

Run:

```bash
sudo journalctl -u myapp
```

```text

   ↓
```

If something suspicious happens:

```text
Application
```

```bash
node server.js
```

# 26. systemd Sandboxing ⭐

Here's where things become more interesting.

systemd can restrict what a service can do.

For example:

```ini
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
```

These are **sandboxing controls**.

They can significantly reduce the damage an exploited service can cause.

---

# 27. `NoNewPrivileges`

```ini
NoNewPrivileges=true
```

This prevents the service and its children from gaining additional privileges through mechanisms such as set-user-ID/set-group-ID execution or related privilege escalation paths.

Think:

```text
Node.js
   ↓
compromised
   ↓
Try to gain more privileges
   X
NoNewPrivileges
```

This is a powerful defense-in-depth setting.

---

# 28. `PrivateTmp`

```ini
PrivateTmp=true
```

This gives the service an isolated temporary directory view.

Instead of:

```text
All services
     ↓
/tmp
```

the service gets a more isolated temporary environment.

This reduces unnecessary interaction with other processes using temporary storage.

---

# 29. `ProtectSystem`

One useful setting is:

```ini
ProtectSystem=strict
```

Conceptually:

```text
System files
     ↓
Read-only
```

This can prevent the service from modifying large parts of the filesystem.

However, your application may need specific writable directories.

You can provide exceptions using settings such as:

```ini
ReadWritePaths=/opt/myapp/logs
```

This is a very important security pattern:

> **Make everything read-only, then explicitly allow only required write locations.**

---

# 30. `ProtectHome`

```ini
ProtectHome=true
```

This helps prevent the service from accessing user home directories such as:

```text
/home/rahul
/home/alice
/home/bob
```

Your backend probably doesn't need access to people's home directories.

So:

```text
Node.js
   ↓
ProtectHome
   X
/home/*
```

This reduces attack surface.

---

# 31. `PrivateDevices`

Another useful sandbox option:

```ini
PrivateDevices=true
```

This can restrict access to device files.

A typical Node.js web server doesn't need direct access to:

```text
/dev/*
```

So restricting it can be useful.

---

# 32. `ProtectKernelTunables`

You may see:

```ini
ProtectKernelTunables=true
```

This helps prevent a service from modifying kernel parameters.

A normal web application shouldn't need to change:

```text
/proc/sys/*
```

or similar kernel tuning interfaces.

Therefore:

```text
Node.js
   ↓
Kernel configuration
   X
```

is generally a good boundary.

---

# 33. `ProtectKernelModules`

```ini
ProtectKernelModules=true
```

This helps prevent the service from interacting with kernel module loading mechanisms.

A Node.js API should not need to:

```text
load kernel modules
```

So restricting this is another layer of defense.

---

# 34. `ProtectControlGroups`

You may also encounter:

```ini
ProtectControlGroups=true
```

This prevents unnecessary access to control-group management interfaces.

Again:

> Your web application should have access only to what it actually needs.

---

# 35. `RestrictAddressFamilies`

A web application normally needs network communication.

You can restrict which address families it can use.

For example:

```ini
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
```

Conceptually:

```text
IPv4 ✓
IPv6 ✓
Unix sockets ✓
Everything else ✗
```

This is an advanced control.

Don't copy arbitrary restrictions without understanding your application's networking requirements.

---

# 36. Capabilities

Linux traditionally has a powerful:

```text
root
```

identity.

But Linux capabilities divide some privileged operations into smaller permissions.

For example:

```text
CAP_NET_BIND_SERVICE
```

allows binding to privileged ports below 1024.

This is useful because:

```text
Traditional:
root → bind port 443

More granular:
service → specific capability
```

This is the principle of least privilege at the kernel level.

---

# 37. Why Capabilities Matter

Imagine Node.js needs to bind directly to:

```text
443
```

Normally ports below 1024 require elevated privilege.

Instead of:

```text
Node.js → root
```

you can potentially use:

```text
Node.js
   ↓
CAP_NET_BIND_SERVICE
   ↓
Port 443
```

This is much more precise.

In many production architectures, though, Nginx binds to 443 and Node.js remains on an unprivileged port such as 3000, which is often simpler and safer.

---

# 38. Drop Capabilities

systemd can also restrict capabilities.

For example:

```ini
CapabilityBoundingSet=
```

can be used to remove capabilities the service doesn't need.

This is an advanced security control.

For a normal Node.js API:

```text
Required capabilities
→ ideally very few
```

---

# 39. Service Isolation

Imagine:

```text
Server
│
├── Nginx
├── Node.js
├── MongoDB
└── Redis
```

Each service should ideally have:

```text
Different user
Different files
Different permissions
Different network exposure
Different systemd restrictions
```

Then:

```text
Node.js compromised
      ↓
Node.js user
      ↓
Limited filesystem
      ↓
Limited capabilities
      ↓
Limited network
```

This is much safer.

---

# 40. `PrivateNetwork`

Another systemd sandbox option is:

```ini
PrivateNetwork=true
```

But **be careful**.

This creates a private network namespace for the service.

A web application that needs network access may stop functioning correctly if you enable this blindly.

For example:

```text
Node.js
   ↓
PrivateNetwork=true
   ↓
Normal network assumptions may break
```

So only use it when you understand exactly what network access the service requires.

This is a good example of:

> Security controls must be tested against application requirements.

---

# 41. Read-Only Filesystem

A very strong pattern is:

```text
Application
   ↓
Read-only filesystem
   +
specific writable directories
```

For example:

```ini
ProtectSystem=strict
ReadWritePaths=/opt/myapp/logs
```

Conceptually:

```text
/opt/myapp
├── code        READ ONLY
├── config      READ ONLY
└── logs        READ/WRITE
```

This limits the attacker's ability to modify application code.

---

# 42. Secure Node.js Service Example

A more security-focused example might look like:

```ini
[Unit]
Description=My Node.js Application
After=network.target

[Service]
Type=simple

User=nodeapp
Group=nodeapp

WorkingDirectory=/opt/myapp

ExecStart=/usr/bin/node /opt/myapp/server.js

Restart=on-failure
RestartSec=5

Environment=NODE_ENV=production
EnvironmentFile=/etc/myapp/myapp.env

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true

ReadWritePaths=/opt/myapp/logs

[Install]
WantedBy=multi-user.target
```

This is an **example**, not something you should blindly copy into production.

Some applications require additional permissions.

---

# 43. Why We Don't Copy Security Configurations Blindly

Suppose you enable:

```ini
ProtectSystem=strict
```

but your application needs:

```text
/tmp
/opt/myapp/uploads
/var/cache/myapp
```

It may fail.

Or:

```ini
PrivateNetwork=true
```

could break database connectivity.

Therefore:

```text
Security setting
      ↓
Understand requirement
      ↓
Apply
      ↓
Test application
      ↓
Monitor logs
```

Security hardening is an engineering process.

---

# 44. systemd Security Analyzer ⭐

One of the coolest tools you'll learn is:

```bash
systemd-analyze security myapp.service
```

This analyzes the service's security exposure.

You may get a report containing things like:

```text
NAME                      DESCRIPTION
NoNewPrivileges=          ...
PrivateTmp=               ...
ProtectSystem=            ...
ProtectHome=              ...
CapabilityBoundingSet=    ...
```

It may also provide an overall exposure score.

The goal isn't necessarily:

```text
"Get a perfect score at any cost."
```

Instead:

> Understand which protections are missing and decide which are appropriate.

---

# 45. This Is Similar to a Security Checklist

Think:

```text
systemd-analyze security
             ↓
Security posture
             ↓
Missing controls
             ↓
Evaluate
             ↓
Harden
```

This is exactly the mindset used in production security reviews.

You can inspect:

```bash
systemctl list-units --type=service
```

Or:

```bash
systemctl --type=service --state=running
```

```text

```

# 47. Attack Surface

Suppose your server has:

```text
SSH
Nginx
Node.js
MongoDB
Redis
FTP
Mail server
Old monitoring daemon
Unused database
```

Every unnecessary service creates potential:

```text
Vulnerability
Configuration error
Authentication surface
Network exposure
```

So:

```text
More services
     ↓
Larger attack surface
```

Hardening means:

```text
Remove unnecessary services
```

---

# 48. Disable Unnecessary Services

First inspect:

```bash
systemctl --type=service --state=running
```

Then determine what each service does.

Don't randomly execute:

```bash
sudo systemctl disable something
```

because a service may be required by your desktop or operating system.

Instead:

```text
Identify
 ↓
Understand dependency
 ↓
Determine necessity
 ↓
Disable if unnecessary
```




```bash

```

Check running status.

# 50. Masking a Service

You can completely prevent a service from being started normally:

```bash
sudo systemctl mask SERVICE
```

Conceptually:

```text
Service
   ↓
MASKED
   ↓
Cannot normally start
```

Unmask:

```bash
sudo systemctl unmask SERVICE
```

Use this carefully.

# 51. Service Dependencies

Services can depend on other services.

For example:

```text
Node.js
   ↓
Network
   ↓
Database
```

systemd can model dependencies and ordering.

Useful commands include:

```bash
systemctl list-dependencies myapp.service
```

This helps you understand:

```text
What does this service depend on?
```

---

# 52. Why Dependencies Matter for Security

Suppose:

```text
myapp.service
   ↓
database.service
```

You need to know:

- what starts first
    
- what happens when a dependency fails
    
- whether restarting one service affects another
    
- whether unnecessary dependencies increase attack surface
    

Good production systems keep dependencies clear and minimal.

---

# 53. Process Limits

systemd can also limit resources.

For example:

```ini
LimitNOFILE=65535
```

controls file descriptors.

You can also use controls related to:

```text
CPU
Memory
Processes
File descriptors
Tasks
```

This can help protect against resource exhaustion.

---

# 54. Resource Limits and Security

Suppose an exploited application creates:

```text
100,000 processes
```

Without controls:

```text
Server
   ↓
Resource exhaustion
   ↓
Other services fail
```

With appropriate limits:

```text
Node.js
   ↓
Resource limit
   ↓
Attack impact reduced
```

This is another form of containment.

---

# 55. CPU and Memory Controls

Modern systemd can work with cgroups to control resource usage.

For example, depending on your setup:

```ini
MemoryMax=512M
CPUQuota=80%
```

Conceptually:

```text
Node.js
   │
   ├── Memory ≤ 512 MB
   └── CPU ≤ 80%
```

Again, these values must be based on actual application requirements.

---

# 56. Why Resource Limits Matter for Node.js

Suppose a malicious request triggers an expensive operation:

```text
Request
   ↓
Memory allocation
   ↓
Huge memory consumption
   ↓
Server instability
```

A service-level memory limit can reduce the blast radius.

It doesn't fix the vulnerability, but it can provide containment.

# 57. systemd + Docker

You may wonder:

> "If I'm using Docker, do I still need systemd security?"

Usually, you should understand both.

Docker provides:

```text

```

systemd provides:

```text
Service management
Process supervision
Sandboxing
Resource control
Logging integration
```

The exact combination depends on your deployment architecture.

# 60. What Happens During an Exploit?

Let's compare.

### Bad setup

```text
Attacker
   ↓
Node.js vulnerability
   ↓
Node.js = root
   ↓
/etc
/var
/home
/boot
everything
```

### Hardened setup

```text
Attacker
   ↓
Node.js vulnerability
   ↓
nodeapp
   ↓
NoNewPrivileges
   ↓
Limited filesystem
   ↓
Protected home directories
   ↓
Limited capabilities
   ↓
Limited resources
```

The attacker may still have a foothold, but their ability to escalate and move around the system is reduced.

That's the purpose of hardening.

# 62. Practical Lab 🧪

Let's inspect your current Linux Mint system.

### Step 1 — List running services

```bash
systemctl --type=service --state=running
```

Don't change anything yet.

---

### Step 2 — Inspect SSH


# 72. Don't Chase a Perfect Score

`systemd-analyze security` may show a security exposure score.

Don't blindly try to make it:

```text
0.0
```

by enabling every possible restriction.

For example:

```ini
PrivateNetwork=true
```

might improve isolation but break your application's network connectivity.

The real goal is:

```text
Security
   +
Functionality
   +
Reliability
```

# 73. Production Hardening Process

A good workflow is:

```text
1. Understand application
        ↓
2. Identify required permissions
        ↓
3. Create dedicated service user
        ↓
4. Restrict filesystem
        ↓
5. Restrict capabilities
        ↓
6. Restrict resources
        ↓
7. Apply systemd sandboxing
        ↓
8. Test application
        ↓
9. Analyze security posture
        ↓
10. Monitor in production
```

This is much better than copying a random hardening configuration from the internet.

# 74. Interview Questions

### Q1. Why shouldn't Node.js run as root?

Because a vulnerability in the application could allow an attacker to inherit root privileges and potentially compromise the entire server.

---

### Q2. What is systemd?

A system and service manager used by many modern Linux distributions.

---

### Q3. What is a systemd unit?

A configuration object describing a resource managed by systemd, such as a service, socket, timer, mount, or other unit type.

---

### Q4. What does `User=` do?

It specifies the Linux user under which the service process runs.

---

### Q5. What does `NoNewPrivileges=true` do?

It prevents the service and its children from gaining additional privileges through mechanisms such as set-user-ID/set-group-ID execution.

---

### Q6. What does `ProtectSystem=strict` do?

It makes broad portions of the filesystem read-only to the service, reducing its ability to modify system files. Specific writable paths can be explicitly allowed.

---

### Q7. What does `ProtectHome=true` do?

It restricts access to user home directories.

---

### Q8. What does `PrivateTmp=true` do?

It provides the service with an isolated temporary-directory view.

---

### Q9. What are Linux capabilities?

Capabilities divide certain traditionally root-only privileges into more granular permissions.

---

### Q10. How do you inspect a systemd service's security posture?

```bash
systemd-analyze security SERVICE
```

# 78. Final Takeaway

Don't think of `systemd` as just a tool for:

```bash
systemctl start nginx
```

Think of it as a **security boundary**.

Your Node.js application can be:

```text
                     NODE.JS
                        │
          ┌─────────────┼─────────────┐
          │             │             │
       User          Files         Network
          │             │             │
      nodeapp       read-only      private
          │             │             │
          └─────────────┼─────────────┘
                        │
                     systemd
                        │
              privilege containment
```

The key idea is:

> **Run services with the minimum identity, filesystem access, capabilities, network access, and resources they need.**

That way, if your Node.js application is compromised, the attacker doesn't automatically get the keys to the entire Linux server.
