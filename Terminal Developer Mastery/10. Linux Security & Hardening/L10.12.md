# 1. What Is a Process?

A process is a running instance of a program.

When you execute:

```bash
node server.js
```

Linux creates a process.

Conceptually:

```text
server.js
   ↓
Node.js
   ↓
Linux Process
   ↓
PID
```

You can see it with:

```bash
ps aux | grep node
```

or:

```bash
pgrep node
```

---

# 2. Process Security

Process security asks:

> **What is this process allowed to do?**

For example:

```text
Node.js process
│
├── Which user?
├── Which group?
├── Which files?
├── Which capabilities?
├── Which network access?
├── Which system calls?
├── How much memory?
├── How many processes?
└── Which signals?
```

This is much deeper than simply:

```text
"Is the firewall enabled?"
```

---

# 3. The Process Security Model

Think of a process like this:

```text
                     PROCESS
                        │
       ┌────────────────┼────────────────┐
       │                │                │
      UID              GID          Capabilities
       │                │                │
       ▼                ▼                ▼
    Identity        Group access     Privileges
       │
       ├───────────────┐
       │               │
    Filesystem       Network
       │               │
       ▼               ▼
   Permissions      Connections
       │
       └───────┬───────┘
               ▼
          System Calls
               │
               ▼
             Kernel
```

This is the foundation of Linux process security.

---

# 4. Process IDs

Every process has a PID.

Run:

```bash
ps aux
```

You'll see something similar to:

```text
USER       PID  %CPU %MEM COMMAND
root         1   ...  ... /sbin/init
rahul     2314   ...  ... bash
rahul     4501   ...  ... node server.js
```

The important field:

```text
PID
```

means:

> **Process ID**

---

# 5. Why PID Matters

You can target a specific process using its PID.

For example:

```bash
kill 4501
```

This sends a signal to process:

```text
4501
```

You can inspect it:

```bash
ps -p 4501 -f
```

This is important for process administration and incident response.

---

# 6. PID 1

On a typical modern system using systemd:

```text
PID 1
```

is usually:

```text
systemd
```

You can check:

```bash
ps -p 1 -f
```

You may see:

```text
/sbin/init
```

with systemd underneath, depending on the distribution.

PID 1 has a special role in managing the system.

---

# 7. Process Ownership

Check a process:

```bash
ps -o pid,user,group,cmd -p <PID>
```

Example:

```text
PID    USER      GROUP     CMD
4501   nodeapp   nodeapp   node server.js
```

This tells you:

```text
UID → nodeapp
GID → nodeapp
```

If your application runs as:

```text
root
```

that's a major security concern.

---

# 8. Real vs Effective User ID

Linux processes can have multiple identity-related IDs.

You'll encounter:

```text
UID
EUID
GID
EGID
```

For basic understanding:

### UID

The real user identity associated with the process.

### EUID

The identity used for many permission checks.

This becomes particularly important with mechanisms such as:

```text
SUID
```

and privilege transitions.

---

# 9. Why Effective UID Matters

Imagine a process has:

```text
UID = normaluser
EUID = root
```

Permission checks may use the effective identity.

This is one reason privileged execution mechanisms need careful security handling.

It also explains why Linux permissions aren't always as simple as:

```text
"Who started the program?"
```

---

# 10. Process Groups

Processes can belong to:

```text
Process group
Session
```

This is useful for managing related processes.

For example:

```text
systemd
   │
   └── Node.js
         │
         ├── child process
         └── child process
```

Signals can sometimes be delivered to groups of processes.

This becomes useful when stopping applications cleanly.

---

# 11. Signals

Linux processes communicate and are controlled using **signals**.

You've already seen:

```bash
kill PID
```

This sends a signal.

Important signals include:

```text
SIGTERM
SIGKILL
SIGHUP
SIGINT
SIGSTOP
SIGCONT
```

You should know what these do.

---

# 12. SIGTERM

```text
SIGTERM
```

means roughly:

> Please terminate gracefully.

For example:

```bash
kill <PID>
```

normally sends:

```text
SIGTERM
```

This gives the application a chance to clean up.

For Node.js:

```javascript
process.on("SIGTERM", () => {
  // graceful shutdown
});
```

This is very important in production.

---

# 13. Graceful Shutdown

Imagine your backend is processing:

```text
Payment
Database transaction
File upload
HTTP request
```

Suddenly:

```text
systemctl restart myapp
```

If the application handles SIGTERM correctly:

```text
SIGTERM
   ↓
Stop accepting new requests
   ↓
Finish existing work
   ↓
Close database connection
   ↓
Exit
```

This is called:

> **Graceful shutdown**

---

# 14. SIGKILL

```text
SIGKILL
```

is much more aggressive.

```bash
kill -9 <PID>
```

sends:

```text
SIGKILL
```

The process cannot catch or ignore it.

Conceptually:

```text
SIGTERM
   ↓
"Please stop."

SIGKILL
   ↓
"Stop immediately."
```

Use SIGKILL only when necessary.

---

# 15. Why SIGKILL Is Dangerous

Suppose your application is:

```text
Writing database data
```

and you send:

```bash
kill -9 PID
```

The process disappears immediately.

That can interrupt cleanup operations.

Therefore:

```text
SIGTERM
   ↓
Try graceful shutdown

SIGKILL
   ↓
Last resort
```

---

# 16. SIGHUP

Historically:

```text
SIGHUP
```

was associated with terminal hangups.

Many applications also use it to mean:

> Reload configuration.

For example:

```text
Nginx
  ↓
SIGHUP
  ↓
Reload configuration
```

The exact behavior depends on the application.

---

# 17. SIGINT

```text
SIGINT
```

is typically generated by:

```text
Ctrl + C
```

For example:

```bash
node server.js
```

Then:

```text
Ctrl+C
```

sends an interrupt signal.

Node.js can handle it:

```javascript
process.on("SIGINT", () => {
  console.log("Shutting down...");
});
```

---

# 18. Inspect Signals

You can use:

```bash
kill -l
```

to list signals.

You'll see names such as:

```text
SIGTERM
SIGKILL
SIGINT
SIGHUP
SIGSTOP
SIGCONT
```

You don't need to memorize every Linux signal.

Know the important ones.

---

# 19. Sending Signals Safely

Check process first:

```bash
ps -p <PID> -f
```

Then:

```bash
kill <PID>
```

If necessary:

```bash
kill -TERM <PID>
```

Only as a last resort:

```bash
kill -KILL <PID>
```

---

# 20. Capabilities — The Interesting Part ⭐

Traditional Unix permissions had a simple idea:

```text
root
  ↓
Almost everything

normal user
  ↓
Limited
```

Linux capabilities break some privileged operations into smaller pieces.

For example:

```text
CAP_NET_BIND_SERVICE
```

allows a process to bind to privileged network ports.

So instead of:

```text
root
 ↓
port 443
```

you can potentially have:

```text
normal user
 ↓
specific capability
 ↓
port 443
```

---

# 21. Why Capabilities Are Useful

Imagine:

```text
Node.js
```

needs one privileged operation.

Bad:

```text
Node.js
   ↓
root
```

Better:

```text
Node.js
   ↓
specific capability
```

This follows:

> **Least privilege**

---

# 22. View Process Capabilities

For a process:

```bash
sudo cat /proc/<PID>/status
```

Look for:

```text
CapInh
CapPrm
CapEff
CapBnd
CapAmb
```

These are hexadecimal capability masks.

You can decode them with:

```bash
capsh --decode=<hex-value>
```

if `libcap2-bin`/the relevant capability tools are installed.

---

# 23. `getcap`

For executable files, use:

```bash
getcap /path/to/program
```

For example:

```bash
getcap /usr/bin/ping
```

You might encounter output like:

```text
/usr/bin/ping cap_net_raw=ep
```

This means the binary has a specific capability instead of requiring full root privileges.

---

# 24. `setcap`

Capabilities can be assigned using:

```bash
setcap
```

For example, conceptually:

```bash
sudo setcap cap_net_bind_service=+ep /path/to/program
```

⚠️ Be careful with `setcap`.

Giving a binary extra capabilities increases its privilege.

Never blindly run `setcap` commands from random tutorials.

---

# 25. Capability Bounding Set

systemd can restrict capabilities with:

```ini
CapabilityBoundingSet=
```

For example:

```ini
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
```

This conceptually says:

```text
Service
  ↓
Allowed capability
  ↓
CAP_NET_BIND_SERVICE
```

Other capabilities can be excluded.

---

# 26. Drop Capabilities

If your Node.js backend doesn't need special capabilities:

```ini
CapabilityBoundingSet=
```

can be used to give it an empty capability bounding set.

Combined with:

```ini
NoNewPrivileges=true
```

you can significantly reduce privilege escalation opportunities.

But again:

> Test your application after applying restrictions.

---

# 27. Environment Variables

Your Node.js application probably uses:

```text
DATABASE_URL
JWT_SECRET
RAZORPAY_KEY_ID
RAZORPAY_KEY_SECRET
PORT
NODE_ENV
```

These are environment variables.

You can inspect the environment of a process:

```bash
sudo tr '\0' '\n' < /proc/<PID>/environ
```

⚠️ This can expose secrets.

Only do this on systems you control.

---

# 28. Why Environment Variables Can Be Sensitive

Suppose:

```text
DATABASE_URL=mongodb+srv://...
JWT_SECRET=...
API_KEY=...
```

If an attacker gets access to the process environment:

```text
Attacker
   ↓
/proc/PID/environ
   ↓
Secrets
```

they may gain access to other systems.

Therefore:

> Environment variables are convenient, but they are not automatically a secure secret-management system.

---

# 29. Protecting Environment Files

If you're using:

```text
/etc/myapp/myapp.env
```

make it restrictive:

```bash
sudo chmod 600 /etc/myapp/myapp.env
```

Then ensure the correct service identity can read it.

For example:

```text
root:nodeapp
```

with appropriate permissions may be more suitable than making it globally readable.

---

# 30. Better Secret Management

As your applications become more advanced, consider dedicated secret-management systems.

Examples include:

```text
HashiCorp Vault
Cloud secret managers
Kubernetes Secrets
Docker secrets
```

The important principle is:

```text
Secret
  ↓
Controlled access
  ↓
Audit
  ↓
Rotation
```

not:

```text
Secret
  ↓
.env
  ↓
GitHub
```

```text
/proc
```

For example:

```bash
ls /proc
```

You'll see directories such as:

```text
/proc/1

/proc/5678
```

# 32. Inspect a Process

For PID 1234:

```bash
cat /proc/1234/status
```

You can learn things like:

```text
Name

PPid
Uid
Gid
Groups

```

This is extremely useful for debugging and security investigation.

# 33. Process File Descriptors

A process has file descriptors.

Inspect:

```bash
ls -l /proc/<PID>/fd
```

You might see:

```text
0 → stdin
1 → stdout
2 → stderr
```

and network sockets/files.

This helps answer:

> What resources is this process currently using?

You can use:

```bash
sudo ss -tulpn
```

or:

```bash
sudo lsof -i -P -n
```

to inspect network activity.

For a specific process:

```bash
sudo lsof -p <PID>
```

This can show:

```text
Files
Sockets
Libraries
Network connections
```

# 35. Why This Matters During an Incident

Imagine you discover:

```text
Unknown Node.js process
```

You can investigate:

```text
PID
 ↓
User
 ↓
Command
 ↓
Executable
 ↓
Files
 ↓
Network connections
 ↓
Environment
 ↓
Parent process
```

This is basic Linux incident-response thinking.

---

# 36. Parent and Child Processes

A process can create another process.

Example:

```text
Node.js
   │
   ├── child process
   └── child process
```

Check:

```bash
pstree -p
```

or:

```bash
pstree -p <PID>
```

This is very useful for spotting unexpected process relationships.

---

# 37. Why Child Processes Matter for Node.js

Node.js can execute external programs through APIs such as:

```javascript
child_process.exec()
child_process.spawn()
child_process.execFile()
```

If user-controlled input reaches these APIs incorrectly, you can get:

> **Command injection**

For example, conceptually:

```text
User input
   ↓
exec()
   ↓
Shell command
   ↓
Attacker-controlled command
```

This is why process security is directly relevant to backend development.

---

# 38. Secure Child Processes

If you need to run an external command:

Prefer:

```javascript
spawn("program", ["arg1", "arg2"]);
```

over building a shell command from user input.

Avoid:

```javascript
exec(`some-command ${userInput}`);
```

unless the input is carefully controlled and safely handled.

This is both an application-security and process-security issue.

---

# 39. Seccomp ⭐⭐⭐⭐⭐

Now we reach one of the most advanced topics in this lesson:

> **Seccomp — Secure Computing Mode**

Seccomp restricts the system calls a process can make.

Remember:

```text
Node.js
   ↓
System calls
   ↓
Linux kernel
```

Examples of system-call categories include operations involving:

```text
Files
Memory
Processes
Sockets
Signals
```

Seccomp can restrict which system calls are permitted.

---

# 40. What Is a System Call?

Applications don't directly control the kernel.

They request kernel services through:

> **System calls**

Conceptually:

```text
Node.js
   │
   │ system call
   ▼
Linux Kernel
   │
   ▼
Hardware / filesystem / network
```

Examples include system calls associated with:

```text
read
write
openat
socket
execve
clone
```

You don't need to memorize all system calls.

---

# 41. Why Restrict System Calls?

Suppose your Node.js web server only needs a subset of kernel functionality.

If an attacker compromises it:

```text
Attacker
   ↓
Node.js process
   ↓
Try unusual system call
   ↓
Seccomp
   X
Denied
```

This can reduce the attack surface of the kernel interface available to the process.

---

# 42. Seccomp Mental Model

Think:

```text
                   Node.js
                      │
                      ▼
               System Calls
                      │
              ┌───────┴───────┐
              │               │
           Allowed          Blocked
              │               │
              ▼               X
           Kernel          Seccomp
```

This is another containment layer.

---

# 43. Seccomp in Containers

You'll encounter seccomp frequently in:

```text
Docker
Kubernetes
Container runtimes
Sandboxed applications
```

A container runtime can apply a seccomp profile that restricts dangerous/unnecessary system calls.

Conceptually:

```text
Container
   │
   ▼
Seccomp profile
   │
   ├── allowed syscalls
   └── blocked syscalls
```

This helps contain compromised workloads.

---

# 44. systemd and Seccomp

systemd can also provide system-call filtering controls.

For example:

```ini
SystemCallFilter=
```

You can use it to restrict which system-call groups a service can use.

But this is an **advanced hardening feature**.

Don't start by writing a complicated syscall allowlist for Node.js.

Why?

Because Node.js and its dependencies may use more system calls than you expect.

---

# 45. Better Approach to Seccomp

Use this process:

```text
Application
   ↓
Understand behavior
   ↓
Observe required syscalls
   ↓
Build restriction
   ↓
Test extensively
   ↓
Deploy
   ↓
Monitor
```

Don't:

```text
Copy random seccomp profile
       ↓
Production
       ↓
Application breaks
```

---

# 46. `strace`

One useful Linux debugging/security tool is:

```bash
strace
```

It shows system calls made by a process.

For example:

```bash
strace ls
```

You'll see calls related to:

```text
openat()
read()
write()
close()
```

For a test Node.js process:

```bash
strace -p <PID>
```

⚠️ Attaching `strace` to production processes can have performance and security implications. Use it carefully.

---

# 47. Why `strace` Is Useful

Suppose your systemd sandbox breaks your application.

You can investigate:

```text
Application
   ↓
Operation fails
   ↓
What syscall/resource was required?
   ↓
strace / logs
   ↓
Understand requirement
```

This helps you create **minimal** security policies.

# 48. Resource Limits

A process can consume:

```text
CPU
Memory
Processes
Threads
File descriptors
Disk
Network
```

If unrestricted, an application bug can become a denial-of-service condition.

For example:

```text
Memory leak
   ↓
RAM consumed
   ↓
Swap
   ↓
System becomes slow
   ↓
Other services fail
```

Resource limits help reduce this risk.

---

# 49. File Descriptor Limits

Every open file/socket consumes a file descriptor.

Check:

```bash
ulimit -n
```

You might see:

```text
1024
```

or a larger number.

Node.js servers handling many connections may need more.

systemd can configure:

```ini
LimitNOFILE=65535
```

if justified.

---

# 50. Process Limits

You can also limit the number of processes/tasks.

For systemd:

```ini
TasksMax=512
```

Conceptually:

```text
Node.js
   ↓
Maximum tasks
   ↓
512
```

This can help contain fork bombs or unexpected process creation.

Again:

> Choose values based on your application.

---

# 51. Memory Limits

For example:

```ini
MemoryMax=512M
```

means:

```text
Service
   ↓
Memory limit
   ↓
512 MB
```

If the service exceeds the configured limit, systemd/cgroup behavior can terminate or constrain processes depending on the configuration.

This provides containment.

---

# 52. CPU Limits

You may see:

```ini
CPUQuota=80%
```

This limits CPU consumption.

Conceptually:

```text
Node.js
   ↓
CPU limit
   ↓
Protect rest of system
```

This can be useful against:

- runaway processes
    
- accidental infinite loops
    
- some denial-of-service scenarios
    

---

# 53. Signals + Resource Limits

These controls work together.

For example:

```text
Application
    │
    ├── SIGTERM → graceful shutdown
    │
    ├── SIGKILL → emergency termination
    │
    ├── MemoryMax → memory containment
    │
    ├── TasksMax → process containment
    │
    └── CPUQuota → CPU containment
```

This is a very powerful operational model.

---

# 54. Process Security During an Attack

Imagine an attacker finds an RCE vulnerability.

Bad architecture:

```text
RCE
 ↓
Node.js
 ↓
root
 ↓
Unlimited access
```

Hardened architecture:

```text
RCE
 ↓
Node.js
 ↓
nodeapp
 ↓
NoNewPrivileges
 ↓
Limited filesystem
 ↓
Limited capabilities
 ↓
Restricted syscalls
 ↓
Resource limits
 ↓
Limited network
```

The attacker may still execute code inside the application context, but the **blast radius** is reduced.

---

# 55. Blast Radius

This is an important security term.

**Blast radius** means:

> How much damage can occur when something is compromised?

Compare:

### Poor isolation

```text
Compromise
   ↓
Entire server
```

### Strong isolation

```text
Compromise
   ↓
One process
   ↓
One user
   ↓
Limited files
   ↓
Limited capabilities
   ↓
Limited network
```

The second architecture has a smaller blast radius.

---

# 56. Process Security vs Application Security

These are different.

### Application security

```text
Input validation
Authentication
Authorization
CSRF
XSS
SQL injection
Command injection
```

### Process security

```text
User
Permissions
Capabilities
Seccomp
Signals
Resource limits
Filesystem isolation
```

You need both.

# 58. Secure Upload Architecture

Instead of:

```text
Node.js
   ↓
Entire filesystem writable
```

use:

```text
Node.js
   │
   └── /opt/myapp/uploads
                │
                └── writable
```

Everything else:

```text
Read-only
```

This is a very strong production pattern.

---

# 59. Secure Environment Architecture

Instead of:

```text
Node.js
   ↓
All environment secrets
```

consider:

```text
Node.js
   ↓
Only required secrets
```

For example, if a service doesn't need:

```text
AWS_SECRET_ACCESS_KEY
```

don't give it that secret.

Least privilege applies to secrets too.

# 60. Process Security Checklist ⭐

For a production Node.js service:

```text
[✓] Dedicated service user
[✓] No root
[✓] No interactive shell
[✓] Minimal filesystem permissions
[✓] Application code read-only where possible
[✓] Restricted writable directories
[✓] NoNewPrivileges
[✓] Limited capabilities
[✓] Protected home directories
[✓] Protected system directories
[✓] Restricted temporary storage
[✓] Resource limits
[✓] Controlled environment variables
[✓] Secret permissions
[✓] Appropriate network access
[✓] systemd supervision
[✓] Logs enabled
[✓] Security posture reviewed
```

# 68. Interview Questions

### Q1. What is a Linux process?

A running instance of a program managed by the Linux kernel.

---

### Q2. What is PID?

Process ID — a unique identifier assigned to a process.

---

### Q3. What is SIGTERM?

A request for a process to terminate gracefully.

---

### Q4. What is SIGKILL?

A non-catchable signal that immediately terminates a process.

---

### Q5. Why prefer SIGTERM before SIGKILL?

Because applications can handle SIGTERM and perform graceful cleanup.

---

### Q6. What are Linux capabilities?

A mechanism that divides certain privileged operations into more granular permissions instead of requiring full root privileges.

---

### Q7. What is seccomp?

A Linux security mechanism that restricts the system calls a process can make.

---

### Q8. Why use resource limits?

To prevent a process from consuming excessive system resources and affecting other services.

---

### Q9. What is the blast radius?

The amount of system or infrastructure damage an attacker can cause after compromising a component.

---

### Q10. Why should a Node.js application run as a dedicated user?

To reduce privileges and limit the damage if the application is compromised.
