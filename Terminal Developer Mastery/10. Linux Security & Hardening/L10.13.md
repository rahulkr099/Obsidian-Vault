# Lesson 10.13 — Linux Security Auditing with `auditd` 🔎🛡️

**Module 10 — Linux Security & Hardening**  
**Part 6: Auditing & Logging**

You've already learned in Module 9 that logs tell us **what happened**.

Now we're going deeper:

> **Security auditing is about recording important security-related actions so we can later answer who did what, when, and to which resource.**

This is extremely important for production servers and incident response.

---

# 1. What Is Security Auditing?

Imagine someone changes:

```text
/etc/ssh/sshd_config
```

A normal application log might not tell you:

```text
Who changed it?
When?
Which process made the change?
What user was involved?
```

Linux auditing can help answer these questions.

Conceptually:

```text
User
  ↓
Action
  ↓
Linux kernel
  ↓
audit subsystem
  ↓
auditd
  ↓
Audit logs
  ↓
Investigation
```

---

# 2. Logging vs Auditing

This distinction is important for interviews.

### Normal logging

Usually tells you:

```text
Application started
Request received
Database connection failed
SSH login failed
```

### Security auditing

Focuses more on:

```text
Who performed an action?
What resource was accessed?
What operation occurred?
When did it happen?
Which process performed it?
```

Think:

```text
Logging
   ↓
"What happened?"

Auditing
   ↓
"Who did what, when, and to what?"
```

There is overlap, but auditing is more focused on accountability and security evidence.

---

# 3. What Is `auditd`?

`auditd` is the Linux Audit daemon.

It receives audit events and writes them to audit logs.

Architecture:

```text
                  Linux Kernel
                       │
                       ▼
                 Audit subsystem
                       │
                       ▼
                    auditd
                       │
                       ▼
              /var/log/audit/
                       │
                       ▼
                  Investigation
```

The audit system is deeper than simply watching a text log.

---

# 4. Why `auditd` Matters

Suppose your production server suddenly has:

```text
/etc/passwd
```

modified.

You want to know:

```text
Who?
When?
Which process?
Which executable?
What type of operation?
```

Auditing can provide valuable evidence.

---

# 5. Installing `auditd`

On Ubuntu/Debian/Linux Mint:

```bash
sudo apt update
sudo apt install auditd audispd-plugins
```

Check:

```bash
sudo systemctl status auditd
```

On some distributions, the audit subsystem may already be installed.

---

# 6. Starting the Service

If needed:

```bash
sudo systemctl enable auditd
```

Depending on your distribution's audit configuration, starting/restarting `auditd` can have special behavior because the kernel audit subsystem is security-sensitive.

Check its current state first:

```bash
sudo systemctl status auditd
```

Don't blindly restart audit services on production systems.

---

# 7. Where Are Audit Logs Stored?

A common location is:

```text
/var/log/audit/audit.log
```

Check:

```bash
sudo ls -lah /var/log/audit/
```

Then:

```bash
sudo less /var/log/audit/audit.log
```

You may see records containing fields such as:

```text
type=SYSCALL
type=PATH
type=USER_LOGIN
type=EXECVE
```

We'll understand these shortly.

---

# 8. `auditctl`

The main command-line tool for viewing/managing audit rules is:

```bash
auditctl
```

Check current rules:

```bash
sudo auditctl -l
```

You may see:

```text
No rules
```

or existing rules.

---

# 9. Audit Rules

An audit rule essentially says:

> **Watch this activity and generate an audit event when it occurs.**

For example:

```text
Watch
 ↓
/etc/passwd
 ↓
Write/change
 ↓
Generate audit event
```

This is different from continuously monitoring every file on the system.

---

# 10. Why We Don't Audit Everything

A beginner might think:

> "Let's audit every file and every system call!"

That's usually a bad idea.

Why?

```text
Too many events
      ↓
Huge logs
      ↓
More CPU/storage overhead
      ↓
Harder investigation
      ↓
Important events get buried
```

Instead:

> **Audit security-sensitive activity.**

This is an important engineering principle.

---

# 11. Audit Sensitive Files

Common sensitive files/directories include:

```text
/etc/passwd
/etc/shadow
/etc/group
/etc/sudoers
/etc/ssh/
/etc/systemd/system/
/etc/cron*
```

Your exact audit policy should depend on your system and threat model.

---

# 12. Watch a File

A traditional example is:

```bash
sudo auditctl -w /etc/passwd -p wa -k identity
```

Let's break it down.

```text
-w
```

means watch the path.

```text
/etc/passwd
```

is the target.

```text
-p wa
```

means monitor:

```text
w → write
a → attribute changes
```

And:

```text
-k identity
```

adds a searchable key:

```text
identity
```

---

# 13. Why Use `-k`?

The key makes searching easier.

Instead of searching through the entire audit log manually:

```text
audit.log
  ↓
thousands of events
```

you can search:

```bash
sudo ausearch -k identity
```

This gives you the events associated with the key.

---

# 14. `ausearch`

`ausearch` is one of the most useful audit investigation commands.

For example:

```bash
sudo ausearch -k identity
```

You can also search by message type:

```bash
sudo ausearch -m USER_LOGIN
```

or by date/time.

We'll explore these.

---

# 15. `aureport`

Another useful command:

```bash
sudo aureport
```

`aureport` generates summaries from audit logs.

For example:

```bash
sudo aureport --auth
```

can provide authentication-related information.

This is useful for quickly answering:

> "What authentication activity has happened?"

---

# 16. Audit Events

Audit records can contain different event types.

Common ones include:

```text
SYSCALL
PATH
EXECVE
USER_LOGIN
USER_START
USER_END
USER_ACCT
USER_CMD
CRED_ACQ
```

The exact records generated depend on the action and your audit rules.

---

# 17. `SYSCALL`

A `SYSCALL` record describes a system call associated with an audited event.

It can contain information such as:

```text
syscall
success
exit
pid
ppid
uid
auid
comm
exe
```

This is extremely valuable during investigations.

---

# 18. Important Audit Fields

You should understand these:

```text
pid
ppid
uid
auid
euid
comm
exe
success
```

Let's go through them.

---

# 19. `pid`

```text
pid
```

means:

> Process ID.

Example:

```text
pid=4217
```

You can investigate that process if it's still running:

```bash
ps -p 4217 -f
```

If it's gone, other audit records can still provide historical information.

---

# 20. `ppid`

```text
ppid
```

means:

> Parent Process ID.

For example:

```text
bash
 ↓
sudo
 ↓
systemctl
```

Each process can have a parent.

This helps establish:

```text
Who launched what?
```

---

# 21. `uid`

`uid` represents the user identity associated with the process/event.

For example:

```text
uid=1000
```

You can resolve it with:

```bash
getent passwd 1000
```

---

# 22. `auid`

This one is particularly important.

`auid` means:

> **Audit User ID**

It can preserve the identity associated with the original authenticated user across privilege changes.

For example:

```text
Rahul
   ↓
sudo
   ↓
root command
```

The effective user may become:

```text
root
```

but the audit identity can still help associate the action with the original user.

This is extremely valuable for accountability.

---

# 23. `euid`

`euid` means:

> Effective User ID.

This is the identity used for many permission checks.

So you might see:

```text
auid=1000
euid=0
```

meaning conceptually:

```text
Original audit identity → normal user

Effective identity → root
```

This distinction is very important.

---

# 24. `comm`

`comm` usually identifies the command name.

For example:

```text
comm="sudo"
```

or:

```text
comm="sshd"
```

This helps identify which program was involved.

---

# 25. `exe`

`exe` identifies the executable path.

For example:

```text
exe="/usr/bin/sudo"
```

This is more precise than only knowing:

```text
comm="sudo"
```

because you can see which executable was involved.

---

# 26. `success`

Audit records may contain:

```text
success=yes
```

or:

```text
success=no
```

This tells you whether the audited operation succeeded.

For example:

```text
User attempts unauthorized operation
        ↓
Audit event
        ↓
success=no
```

That can be extremely useful when investigating attack attempts.

---

# 27. `EXECVE`

An `EXECVE` record can provide information about a command being executed.

For example:

```bash
sudo systemctl restart nginx
```

may produce audit information showing command arguments.

This can be very valuable during investigations.

---

# 28. Login Auditing

You can search authentication activity:

```bash
sudo ausearch -m USER_LOGIN
```

Or use:

```bash
sudo aureport --auth
```

This can help identify:

```text
Successful logins
Failed authentication
User identities
Authentication sources
```

---

# 29. Why Login Auditing Matters

Imagine you receive an alert:

```text
Unexpected production change
```

You can investigate:

```text
1. What changed?
2. Which process changed it?
3. Which user was responsible?
4. Was there a recent login?
5. Was sudo used?
6. From which source?
```

Auditing helps connect these events.

---

# 30. Monitoring `/etc/passwd`

`/etc/passwd` contains account information.

It should be protected.

You can audit changes with a rule such as:

```bash
sudo auditctl -w /etc/passwd -p wa -k identity
```

Then inspect:

```bash
sudo ausearch -k identity
```

---

# 31. Monitoring `/etc/shadow`

`/etc/shadow` contains password-related account information and is highly sensitive.

You could create an audit rule:

```bash
sudo auditctl -w /etc/shadow -p wa -k identity
```

Then:

```bash
sudo ausearch -k identity
```

Be aware that legitimate system operations may touch sensitive files, so don't treat every event as an attack.

---

# 32. Monitoring SSH Configuration

You may want to monitor:

```text
/etc/ssh/
```

For example:

```bash
sudo auditctl -w /etc/ssh/sshd_config -p wa -k ssh_config
```

Then:

```bash
sudo ausearch -k ssh_config
```

Now you can detect configuration modifications.

---

# 33. Why SSH Configuration Is Important

Imagine an attacker compromises your server and modifies:

```text
/etc/ssh/sshd_config
```

to weaken authentication.

An audit event can help you discover:

```text
The file changed
       ↓
When?
       ↓
Which process?
       ↓
Which user?
```

This is exactly the kind of activity security auditing is designed to record.

---

# 34. Monitoring `sudoers`

Another sensitive target:

```text
/etc/sudoers
```

and:

```text
/etc/sudoers.d/
```

An attacker who modifies sudo configuration may attempt to gain additional privileges.

Therefore, monitoring changes to these files can be valuable.

---

# 35. Monitoring Systemd Services

Remember Lesson 10.11.

Your production Node.js service might be:

```text
/etc/systemd/system/myapp.service
```

An attacker who modifies it could potentially establish persistence.

For example:

```text
myapp.service
   ↓
ExecStart=/malicious/program
```

Therefore, monitoring important systemd unit files can help detect tampering.

---

# 36. Persistence

In security, **persistence** means:

> Maintaining access to a system after the initial compromise.

Common persistence locations can include:

```text
systemd services
cron jobs
SSH authorized_keys
startup scripts
shell profiles
```

Auditing changes to these areas can help detect persistence mechanisms.

---

# 37. Audit SSH `authorized_keys`

An attacker who obtains access may attempt:

```text
~/.ssh/authorized_keys
```

and add their own public key.

Then they can potentially log in later without a password.

This is why monitoring authorized keys can be valuable on production systems.

For example:

```bash
sudo auditctl -w /home/<user>/.ssh/authorized_keys -p wa -k ssh_keys
```

Use the actual service/admin account paths on your server.

---

# 38. Audit Cron Configuration

Attackers may attempt persistence through scheduled tasks.

Relevant locations include:

```text
/etc/crontab
/etc/cron.d/
/etc/cron.daily/
/etc/cron.hourly/
```

Monitoring modifications can help detect suspicious persistence.

# 39. Audit Rule Example

Conceptually:

```text
Sensitive file
      ↓
Audit rule
      ↓
Event
      ↓
Key
      ↓
ausearch
      ↓
Investigation
```

For example:

```bash
sudo auditctl -w /etc/ssh/sshd_config -p wa -k ssh_config
```

Then:

```bash

```

---

# 40. Temporary vs Persistent Rules

This is important.

Rules added with:

```bash
auditctl
```

are generally runtime rules.

They may not survive reboot unless configured persistently.

For persistent configuration, audit rules are commonly stored under:

```text
/etc/audit/rules.d/
```

---

# 41. Persistent Audit Rules

A common approach is:

```bash
sudo nano /etc/audit/rules.d/hardening.rules
```

Then add rules.

For example:

```text
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
```

Then the audit rules can be loaded using the system's audit rule-loading mechanism.

On systems using `augenrules`, you may use:

```bash
sudo augenrules --load
```

Then verify:

```bash
sudo auditctl -l
```

---

# 42. Why Separate Rule Files?

Instead of putting everything into one giant file:

```text
audit.rules
```

you can organize rules:

```text
/etc/audit/rules.d/
├── identity.rules
├── ssh.rules
├── systemd.rules
└── hardening.rules
```

This makes your security policy easier to maintain.

---

# 43. Audit Rule Design

Good auditing follows:

```text
Risk
 ↓
Important resource
 ↓
Relevant event
 ↓
Useful audit rule
```

Don't start with:

```text
"Audit everything."
```

Start with:

> "What security events would I actually need to investigate?"

# 47. `auditd` vs Shell History

You might ask:

> "Why not just use `.bash_history`?"

Because shell history is not a strong security audit mechanism.

Problems include:

```text
History can be modified
History can be disabled
Commands can run from other shells/processes
Non-interactive commands don't necessarily appear
```

Audit records operate much closer to the kernel/system activity.

Therefore:

```text
.bash_history
     ≠
security audit
```

---

# 48. `auditd` vs Application Logs

Suppose your Node.js application logs:

```text
POST /admin/delete-user
```

That tells you something about the application.

But `auditd` can help answer questions about operating-system activity:

```text
Which process executed this?
Which user identity?
Which executable?
Which file changed?
Which system call?
```

Different layers provide different visibility.

---

# 49. Three Layers of Visibility

Think:

```text
Application
   ↓
Application logs

Service
   ↓
systemd/journald

Kernel/system activity
   ↓
auditd
```

Together:

```text
Application logs
+
systemd logs
+
audit logs
=
Much stronger observability
```

This connects Module 9 and Module 10.

# 50. Security Event Correlation

Imagine:

```text
20:10 → SSH login
20:12 → sudo command
20:14 → sshd_config modified
20:15 → systemd service modified
20:16 → unknown process started
```

Individually, these events might not look catastrophic.

Together:

```text
SSH login
 ↓
Privilege escalation
 ↓
Configuration modification
 ↓
Persistence
 ↓
Suspicious process
```

Now you have a potential incident.

This is why timestamps and audit trails are so important.

---

# 51. Time Synchronization

Security auditing depends heavily on accurate timestamps.

Imagine:

```text
Server A → 20:10
Server B → 19:42
Server C → 21:03
```

Correlation becomes difficult.

That's why production systems should use time synchronization.

Common technology:

```text
NTP
```

or modern time-sync services.

We'll revisit this in the hardening checklist.

---

# 52. Audit Log Integrity

There is an important problem:

> What if an attacker gains root access and modifies the audit logs?

That's why serious environments may use:

```text
Centralized logging
Remote log storage
SIEM
Immutable storage
Restricted log access
```

For example:

```text
Server
   ↓
Audit logs
   ↓
Central logging system
   ↓
SIEM
```

Now an attacker can't easily erase every trace locally.

---

# 53. Why Remote Logging Matters

Suppose:

```text
Production Server
      ↓
/var/log/audit/audit.log
```

Attacker gets root:

```text
Attacker
   ↓
Delete logs
   ↓
Evidence lost
```

But:

```text
Production Server
      ↓
Remote log collector
      ↓
Central storage
```

is much harder for the attacker to erase completely.

This is a major production security principle.


So audit design should follow:

> **High-value events first.**

Examples:

```text

Privilege changes

SSH configuration
Sudo configuration
Sensitive files
Security policy changes
```

# 67. What `auditd` Does NOT Do

`auditd` is not:

```text
❌ Antivirus
❌ Firewall
❌ Intrusion prevention system
❌ Vulnerability scanner
❌ Malware remover
```

Its primary role is:

```text
Security auditing
+
Evidence
+
Accountability
```

You still need:

```text
Firewall
Fail2ban
Application security
Patch management
Monitoring
Backups
```

---

# 68. Audit vs Fail2ban

We learned Fail2ban in Lesson 10.9.

### Fail2ban

```text
Detect repeated suspicious behavior
        ↓
Take enforcement action
        ↓
Ban IP
```

### auditd

```text
Record security-relevant activity
        ↓
Preserve evidence
        ↓
Investigate
```

So:

```text
Fail2ban → Response
auditd   → Evidence
```

They complement each other.

---

# 69. Audit vs EDR

Enterprise systems may also use:

```text
EDR
Endpoint Detection and Response
```

EDR typically provides broader:

```text
Detection
Behavior analysis
Process monitoring
Threat intelligence
Response
```

`auditd` is lower-level Linux auditing infrastructure.

For a developer learning Linux security:

> Learn `auditd` first. Then understand how EDR/SIEM systems consume and correlate this kind of telemetry.

```text
-W
```

```bash

```

Verify the demo rule is gone.

# 77. Interview Questions

### Q1. What is `auditd`?

A Linux auditing daemon that records security-relevant system activity for accountability and investigation.

---

### Q2. Where are audit logs commonly stored?

```text
/var/log/audit/audit.log
```

---

### Q3. What is `auditctl`?

A command-line tool used to inspect and manage Linux audit rules.

---

### Q4. What is `ausearch`?

A tool used to search audit records.

Example:

```bash
sudo ausearch -k identity
```

---

### Q5. What is `aureport`?

A tool that generates summarized reports from audit data.

---

### Q6. What is `auid`?

The audit user ID, useful for tracking the original authenticated identity across privilege changes.

---

### Q7. Why is `auditd` useful during incident response?

It can provide detailed evidence about users, processes, files, commands, authentication, and other security-relevant activity.

---

### Q8. Why shouldn't you audit everything?

Because excessive auditing can create high event volume, performance/storage overhead, and make investigations harder.

---

### Q9. What is the difference between `auditd` and Fail2ban?

```text
auditd
→ records and provides evidence

Fail2ban
→ detects patterns and can enforce bans
```

---

### Q10. Why is remote audit/log storage useful?

Because an attacker who gains control of a server may try to delete or modify local logs. Remote storage makes complete evidence destruction more difficult.
