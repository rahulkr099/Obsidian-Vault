# Lesson 10.14 — Malware & Rootkit Detection 🦠🔍

**Module 10 — Linux Security & Hardening**  
**Part 6: Auditing & Logging**

In Lesson 10.13, we learned how to record security activity with `auditd`.

Now we'll answer a different question:

> **How do I know whether a Linux server has been compromised by malware, a rootkit, or some other suspicious process?**

This lesson is especially useful for your future MERN production servers because you need to understand how to investigate a server **after something looks wrong**, not just how to prevent attacks.

---

# 1. What Is Malware?

**Malware** means malicious software.

It is software intentionally designed to perform harmful or unauthorized actions.

Examples:

```text
Virus
Worm
Trojan
Backdoor
Botnet malware
Cryptominer
Ransomware
Rootkit
```

On a Linux server, malware might attempt to:

```text
Steal credentials
Run cryptocurrency miners
Create backdoors
Modify services
Steal application secrets
Attack other machines
Hide its processes
Persist after reboot
```

---

# 2. Linux Is Not "Immune" to Malware

You may hear:

> "Linux doesn't get viruses."

That's false.

Linux has a strong security model, but it can still be compromised.

For example:

```text
Internet
   ↓
Vulnerable application
   ↓
Remote code execution
   ↓
Malicious command
   ↓
Malware
```

The operating system isn't automatically protected from an exploited application.

---

# 3. How a Linux Server Can Become Infected

A common attack chain looks like:

```text
1. Vulnerable application
        ↓
2. Attacker gains code execution
        ↓
3. Attacker downloads payload
        ↓
4. Payload executes
        ↓
5. Persistence established
        ↓
6. Credentials stolen
        ↓
7. Attacker expands access
```

For example:

```text
Express vulnerability
        ↓
Command execution
        ↓
wget/curl
        ↓
Malicious binary
        ↓
/tmp
        ↓
Execute
```

This is why application security and Linux security are connected.

---

# 4. What Is a Rootkit?

A **rootkit** is malicious software designed to maintain privileged access and/or hide malicious activity.

The key idea is:

> **Persistence + stealth**

A rootkit may attempt to hide:

```text
Processes
Files
Network connections
Modules
Accounts
```

Conceptually:

```text
Attacker
   ↓
Root access
   ↓
Rootkit
   ├── Hide process
   ├── Hide file
   ├── Hide connection
   └── Maintain persistence
```

---

# 5. Why Rootkits Are Dangerous

Imagine:

```bash
ps aux
```

shows:

```text
nginx
node
mongodb
```

But a malicious process is actually running.

A sophisticated rootkit may attempt to make it invisible to normal tools.

So:

```text
Normal tools
     ↓
"Everything looks fine."
```

while:

```text
Underlying system
     ↓
Malicious activity
```

may be happening.

This is why rootkit detection requires multiple sources of evidence.

---

# 6. Rootkit Levels

Rootkits can operate at different levels.

### User-space rootkit

Targets:

```text
Applications
Libraries
User-space commands
```

### Kernel rootkit

Targets:

```text
Kernel
Kernel modules
System-call behavior
```

Kernel-level compromise is much more serious.

Conceptually:

```text
Application
    ↓
User space
    ↓
Kernel
    ↓
Hardware
```

The deeper the attacker gets, the harder detection becomes.

---

# 7. User-Space vs Kernel-Space

Think:

```text
┌───────────────────────┐
│     Applications      │
│ Node.js / Nginx / SSH │
├───────────────────────┤
│       User Space      │
├───────────────────────┤
│        Kernel         │
├───────────────────────┤
│       Hardware        │
└───────────────────────┘
```

A user-space compromise is bad.

A kernel compromise is potentially much worse because the attacker is operating closer to the operating system's core.

---

# 8. Common Signs of Compromise 🚨

You should learn these signals.

### CPU suddenly very high

```text
CPU = 100%
```

Could indicate:

```text
Cryptominer
Runaway process
DoS
Application bug
```

---

### Unknown processes

```bash
ps aux
```

shows:

```text
/tmp/.something
```

that you don't recognize.

Investigate it.

---

### Unexpected network connections

```bash
sudo ss -tulpn
```

shows an unknown process connecting externally.

Potential concern.

---

### Unknown users

```bash
cat /etc/passwd
```

contains an unexpected account.

Investigate.

---

### SSH keys changed

Unexpected:

```text
~/.ssh/authorized_keys
```

modification.

Potential persistence.

---

### Systemd services changed

Unexpected:

```text
/etc/systemd/system/
```

service.

Potential persistence.

---

### Cron jobs changed

Unexpected:

```text
/etc/cron.d/
```

entry.

Potential persistence.

---

# 9. Other Warning Signs

Look for:

```text
Unexpected outbound traffic
Disabled logging
Modified firewall rules
Changed sudo permissions
Unknown binaries
Files in /tmp
Strange DNS requests
Unexpected CPU usage
New listening ports
Failed SSH login spikes
```

No single sign proves compromise.

You need correlation.

---

# 10. `rkhunter`

One tool we'll study is:

```text
rkhunter
```

which stands for:

> Rootkit Hunter

It checks for various indicators associated with rootkits and other suspicious system changes.

Install on Debian/Ubuntu/Mint:

```bash
sudo apt update
sudo apt install rkhunter
```

Check:

```bash
rkhunter --versioncheck
```

---

# 11. Important Warning About `rkhunter`

Don't think:

```text
rkhunter says clean
       ↓
Server definitely safe
```

That's wrong.

Security scanners can produce:

```text
False positives
False negatives
Outdated signatures
Environment-specific warnings
```

Therefore:

> **Scanner output is evidence, not absolute truth.**

---

# 12. Update `rkhunter`

Before scanning, update its data where supported:

```bash
sudo rkhunter --update
```

Then:

```bash
sudo rkhunter --propupd
```

⚠️ Be careful with `--propupd`.

It updates the known-good file properties database.

You should only do that when you're confident the system is in a trustworthy state.

Otherwise, you could effectively tell the tool:

> "Treat the current potentially compromised files as legitimate."

That's dangerous.

---

# 13. Run a Scan

You can run:

```bash
sudo rkhunter --check
```

You'll be guided through checks.

Some environments also support:

```bash
sudo rkhunter --check --skip-keypress
```

to avoid interactive pauses.

---

# 14. Understanding `rkhunter` Results

You might see:

```text
[ OK ]
[ Warning ]
[ Not Found ]
```

Don't panic when you see:

```text
Warning
```

A warning can be caused by:

```text
Normal system configuration
Development tools
Changed binaries
Unexpected but legitimate files
Known software behavior
```

Always investigate.

---

# 15. View `rkhunter` Warnings

A useful command is:

```bash
sudo rkhunter --check
```

and then inspect its logs.

A common log location is:

```text
/var/log/rkhunter.log
```

For example:

```bash
sudo less /var/log/rkhunter.log
```

The exact location can vary by distribution/configuration.

---

# 16. `chkrootkit`

Another traditional tool is:

```text
chkrootkit
```

Install:

```bash
sudo apt install chkrootkit
```

Run:

```bash
sudo chkrootkit
```

It performs a series of checks for known rootkit indicators.

---

# 17. `chkrootkit` Limitations

Just like `rkhunter`:

```text
chkrootkit ≠ proof of security
```

It can:

```text
Miss new threats
Generate false positives
Depend on system configuration
Detect known patterns rather than every possible attack
```

So use it as **one layer** of detection.

---

# 18. rkhunter vs chkrootkit

Think:

|Tool|Purpose|
|---|---|
|`rkhunter`|Rootkit and suspicious system checks|
|`chkrootkit`|Traditional rootkit detection checks|

You don't need to treat one as "the winner."

Using multiple independent checks can increase confidence.

But running many scanners without understanding their output can create noise.

---

# 19. File Integrity Monitoring

Another important technique is:

> **File Integrity Monitoring (FIM)**

The idea:

```text
Known-good file
      ↓
Calculate hash
      ↓
Store reference
      ↓
Later calculate hash
      ↓
Compare
```

If:

```text
Before:
ABC123

After:
XYZ789
```

the file changed.

---

# 20. Why Hashes Help

Cryptographic hashes produce a fingerprint of file contents.

For example:

```bash
sha256sum myapp.js
```

Output:

```text
abc123...  myapp.js
```

Change the file:

```text
Original
   ↓
Modified
   ↓
Different SHA-256 hash
```

This is useful for detecting unauthorized modifications.

---

# 21. Hashes Don't Tell You Who Changed the File

Important distinction.

A hash can tell you:

```text
The file changed.
```

It cannot directly tell you:

```text
Who changed it?
```

That's where:

```text
auditd
```

becomes useful.

Together:

```text
FIM
 ↓
File changed

auditd
 ↓
Who/process/when
```

This is much stronger.

---

# 22. Combining Security Tools

This is the architecture you should remember:

```text
rkhunter
    ↓
Rootkit indicators

chkrootkit
    ↓
Rootkit checks

File hashes
    ↓
File integrity

auditd
    ↓
Who/when/how

journalctl
    ↓
System/service context

ss
    ↓
Network activity

ps
    ↓
Processes
```

No single tool provides complete visibility.

---

# 23. Investigating a Suspicious Process

Suppose you discover:

```text
PID 9876
```

Start:

```bash
ps -p 9876 -f
```

Then:

```bash
sudo readlink -f /proc/9876/exe
```

This tells you which executable the process is running.

---

# 24. Check Its Command Line

Run:

```bash
sudo tr '\0' ' ' < /proc/9876/cmdline
```

You may discover:

```text
/usr/bin/node /opt/myapp/server.js
```

or something suspicious:

```text
/tmp/.hidden/process
```

The second deserves investigation.

---

# 25. Check the Process User

```bash
ps -o pid,ppid,user,group,cmd -p 9876
```

Ask:

```text
Which user owns it?
```

If:

```text
root
```

and you don't expect it to be root, that's significant.

---

# 26. Check the Parent Process

```bash
ps -o pid,ppid,user,cmd -p 9876
```

Then:

```bash
ps -p <PPID> -f
```

or:

```bash
pstree -ap 9876
```

You want to understand:

```text
Who launched this process?
```

For example:

```text
systemd
   ↓
nginx
```

might be normal.

But:

```text
sshd
   ↓
bash
   ↓
curl
   ↓
/tmp/malware
```

could be suspicious depending on context.

---

# 27. Check Open Files

Run:

```bash
sudo lsof -p 9876
```

Look for:

```text
Unexpected files
Unexpected sockets
Deleted files
Temporary directories
Sensitive files
```

---

# 28. Check Network Connections

Run:

```bash
sudo lsof -Pan -p 9876 -i
```

or:

```bash
sudo ss -tpn
```

Ask:

```text
Where is this process connecting?
Why?
Is the destination expected?
```

---

# 29. Check `/proc`

A suspicious process can be investigated through:

```text
/proc/<PID>/
```

Useful files:

```text
/proc/PID/status
/proc/PID/cmdline
/proc/PID/environ
/proc/PID/exe
/proc/PID/fd/
```

This is one of the most useful Linux investigation skills.

---

# 30. Deleted Executables 🚨

Sometimes an attacker may execute a file and then delete it.

You might see something like:

```text
/tmp/malware (deleted)
```

in:

```bash
sudo lsof
```

This is a strong investigation signal.

It means:

```text
File removed from directory
        ↓
Process still has it open
        ↓
Process continues running
```

Don't immediately assume maliciousness, though. Some legitimate programs also replace/delete files while running.

---

# 31. `/tmp` and Suspicious Files

Attackers sometimes use temporary directories because they're convenient.

Inspect:

```bash
ls -lah /tmp
```

Look for:

```text
Unknown binaries
Hidden-looking names
Unexpected scripts
Recently created files
Executables
```

But again:

> `/tmp` containing strange files doesn't automatically mean malware.

Many legitimate applications use `/tmp`.

Context matters.

---

# 32. Check Executable Files

For a suspicious file:

```bash
file /path/to/file
```

Then:

```bash
ls -lah /path/to/file
```

Then:

```bash
sha256sum /path/to/file
```

You can also inspect its permissions:

```bash
stat /path/to/file
```

---

# 33. Check File Metadata

`stat` gives useful information:

```bash
stat /path/to/file
```

You'll see things such as:

```text
Size
Permissions
UID
GID
Access time
Modify time
Change time
```

This helps build a timeline.

---

# 34. `mtime`, `ctime`, `atime`

You should understand these.

### `mtime`

Content modification time.

### `ctime`

Metadata/status change time.

### `atime`

Last access time.

These timestamps can help during investigation.

But don't treat them as perfect forensic evidence.

Attackers and system operations can modify timestamps.

---

# 35. Look for Unexpected SUID Files

SUID allows an executable to run with the file owner's effective privileges.

Find SUID files:

```bash
sudo find / -perm -4000 -type f 2>/dev/null
```

You may find legitimate programs.

The important question is:

```text
Is this expected?
```

An unexpected SUID executable can be dangerous.

---

# 36. Look for Unexpected SGID Files

Similarly:

```bash
sudo find / -perm -2000 -type f 2>/dev/null
```

Again, don't delete files just because they appear here.

Understand what they are first.

---

# 37. Check Kernel Modules

Kernel modules can be legitimate:

```bash
lsmod
```

You can inspect loaded modules:

```bash
lsmod
```

or:

```bash
cat /proc/modules
```

An unexpected module deserves investigation.

But kernel module output can vary greatly by hardware and distribution.

---

# 38. Why Kernel Modules Matter

A malicious kernel module could potentially:

```text
Hide processes
Modify kernel behavior
Intercept operations
Hide files
Hide network activity
```

This is why kernel-level rootkits are particularly dangerous.

---

# 39. Check Loaded Modules Carefully

Don't assume:

```text
Unknown module = malware
```

You may simply not recognize a legitimate hardware or virtualization module.

Investigate:

```bash
modinfo module_name
```

For example:

```bash
modinfo <module>
```

Look at:

```text
Description
Author
Filename
Version
```

---

# 40. Check Listening Ports

Run:

```bash
sudo ss -lntup
```

This shows listening TCP/UDP sockets and associated processes where available.

Look for:

```text
Unknown port
Unknown process
Unexpected external binding
```

For a production MERN server, you might expect:

```text
22    SSH
80    HTTP
443   HTTPS
```

and perhaps:

```text
3000  Node.js
```

but ideally Node.js itself is not publicly exposed if Nginx is the public reverse proxy.

---

# 41. Public vs Private Services

Good architecture:

```text
Internet
   │
   ▼
80/443
   │
   ▼
Nginx
   │
   ▼
127.0.0.1:3000
   │
   ▼
Node.js
```

Bad exposure:

```text
Internet
   │
   ├── 80
   ├── 443
   ├── 3000  ← unnecessary public exposure
   ├── 27017 ← MongoDB exposed
   └── 6379  ← Redis exposed
```

Reducing exposure makes compromise less likely.

---

# 42. Check Outbound Connections

Don't only inspect listening ports.

Attackers often need outbound communication:

```text
Compromised server
       ↓
Command-and-control server
```

Check:

```bash
sudo ss -tpn
```

and:

```bash
sudo lsof -i
```

Look for:

```text
Unexpected external IP
Unexpected destination port
Unexpected process
```

---

# 43. DNS Investigation

A compromised process may communicate using DNS.

You can inspect DNS activity through your system's normal network/logging tools.

For example:

```bash
resolvectl status
```

and depending on your environment:

```bash
resolvectl statistics
```

The exact commands vary with the resolver configuration.

---

# 44. Cryptominers

One common server compromise is cryptocurrency mining.

Typical signals:

```text
High CPU
Unknown process
Unexpected outbound network traffic
Process starts after reboot
Binary stored in suspicious directory
```

Example:

```text
CPU
 ↓
95%
 ↓
Unknown process
 ↓
/tmp/.miner
```

This is suspicious.

But high CPU alone isn't proof.

Your Node.js application itself might simply have a bug or expensive workload.

---

# 45. Persistence Investigation

If you discover malware, ask:

> How does it survive a reboot?

Check:

```text
systemd
cron
SSH keys
shell startup files
application startup
kernel modules
```

For systemd:

```bash
systemctl list-unit-files
```

For timers:

```bash
systemctl list-timers --all
```

For cron:

```bash
sudo ls -lah /etc/cron.d/
sudo ls -lah /etc/cron.daily/
```

---

# 46. Check User Cron Jobs

For a specific user:

```bash
crontab -l
```

For another user:

```bash
sudo crontab -u <user> -l
```

Unexpected scheduled commands deserve investigation.

---

# 47. Check SSH Keys

For your admin account:

```bash
cat ~/.ssh/authorized_keys
```

Look for keys you don't recognize.

On production systems, consider auditing changes to authorized key files.

---

# 48. Check Accounts

List users:

```bash
cut -d: -f1 /etc/passwd
```

Or:

```bash
getent passwd
```

Then investigate unexpected accounts.

Check users with shells:

```bash
grep -E '/bin/(bash|sh|zsh)$' /etc/passwd
```

A service account should generally not have an interactive shell unless there's a specific reason.

---

# 49. Check Recent Logins

Useful commands include:

```bash
last
```

and:

```bash
lastlog
```

Depending on your system, these can help identify:

```text
Recent logins
Last login
Unexpected users
Unexpected access times
```

Combine this with:

```bash
ausearch
```

for stronger evidence.

---

# 50. Rootkit Detection Is Not a Single Command

Never think:

```bash
sudo rkhunter --check
```

and you're finished.

A proper investigation looks more like:

```text
             Suspicion
                 │
      ┌──────────┼──────────┐
      ▼          ▼          ▼
    ps         ss/lsof     logs
      │          │          │
      └─────┬────┴────┬─────┘
            ▼         ▼
         auditd    file integrity
            │         │
            └────┬────┘
                 ▼
          rkhunter/chkrootkit
                 │
                 ▼
             Correlation
                 │
                 ▼
             Conclusion
```

That's a much better approach.

---

# 51. False Positives ⚠️

This is one of the most important parts of security work.

Suppose:

```text
rkhunter → Warning
```

Don't immediately conclude:

```text
SERVER HACKED!!!
```

Instead:

```text
Warning
  ↓
Identify what triggered it
  ↓
Understand expected behavior
  ↓
Compare with baseline
  ↓
Check logs
  ↓
Check process/file/network evidence
  ↓
Determine severity
```

Security engineers spend a lot of time separating signals from noise.

---

# 52. Establish a Baseline

Before a server goes into production, record its normal state.

For example:

```text
Expected users
Expected services
Expected ports
Expected processes
Expected systemd units
Expected kernel modules
Expected file hashes
Expected SSH keys
```

Then:

```text
Normal baseline
       ↓
Current system
       ↓
Difference
       ↓
Investigation
```

This makes detection much easier.

---

# 53. Example Baseline

Your MERN server might normally have:

```text
Users:
root
deploy
nodeapp

Ports:
22
80
443

Services:
ssh
nginx
myapp

Processes:
sshd
nginx
node

Database:
MongoDB private network only
```

If suddenly:

```text
Port 4444
Process /tmp/x
User hacker
systemd service evil.service
```

appears:

🚨 That's a significant deviation from baseline.

---

# 54. File Integrity Baseline

You can hash important files:

```bash
sha256sum /etc/ssh/sshd_config
```

Store the expected hash securely.

Later:

```bash
sha256sum /etc/ssh/sshd_config
```

Compare.

If different:

```text
Hash changed
   ↓
Investigate
```

For production, use a proper FIM system rather than maintaining dozens of hashes manually.

---

# 55. `AIDE`

Another tool worth knowing is:

> **AIDE — Advanced Intrusion Detection Environment**

It provides file integrity monitoring.

On Debian/Ubuntu-based systems:

```bash
sudo apt install aide
```

AIDE can maintain a database of expected file properties and compare future system state against it.

Conceptually:

```text
Baseline
   ↓
AIDE database
   ↓
Later scan
   ↓
Changes detected
```

---

# 56. Why AIDE Is Different

Compare:

```text
rkhunter
→ Rootkit-oriented checks

chkrootkit
→ Rootkit-oriented checks

AIDE
→ File integrity monitoring

auditd
→ Security activity/audit events
```

Together, these tools cover different areas.

|Tool|Main purpose|
|---|---|
|`rkhunter`|Rootkit/suspicious-system checks|
|`chkrootkit`|Rootkit detection checks|
|AIDE|File integrity|
|`auditd`|Security auditing|

# 58. What To Do If You Suspect Compromise

This is extremely important.

**Don't immediately start deleting suspicious files.**

If the server may be compromised:

```text
1. Don't panic
2. Preserve evidence
3. Assess scope
4. Isolate if necessary
5. Record what you observe
6. Investigate
7. Rotate credentials
8. Rebuild from trusted sources when appropriate
```

This leads directly into our next lesson on incident response.

---

# 59. Why Rebuilding Can Be Better Than Cleaning

Suppose an attacker obtained root.

You don't know:

```text
What changed?
Which binaries changed?
Which backdoors exist?
Which credentials were stolen?
Which persistence mechanisms exist?
```

Even if scanners say:

```text
"Clean"
```

you may not have confidence.

For serious compromises:

```text
Compromised server
       ↓
Preserve evidence
       ↓
Revoke credentials
       ↓
Build clean server
       ↓
Restore trusted application/data
       ↓
Harden
       ↓
Monitor
```

This is often safer than trying to manually "clean" a deeply compromised server.

# 63. Check AIDE

If you want to experiment:

```bash
sudo apt install aide
```

Then initialize its database according to your distribution's AIDE configuration.

The basic idea is:

```text
Trusted system
     ↓
Create baseline
     ↓
Later scan
     ↓
Compare
```

Be careful about where the baseline database is stored. If an attacker can modify both the system and its integrity database, the integrity check loses much of its value.

# 64. Build a Security Investigation Script

Later, you can automate checks such as:

```text
CPU usage
Memory usage
Listening ports
Active connections
Running services
Recent logins
Unexpected users
Systemd timers
SUID files
SSH keys
Audit events
```

For example:

```bash
#!/bin/bash

echo "=== High CPU ==="
ps aux --sort=-%cpu | head

echo "=== Listening Ports ==="
ss -lntup

echo "=== Running Services ==="
systemctl --type=service --state=running

echo "=== Recent Logins ==="
last | head
```

This is a nice beginner security-automation project.

# 65. But Don't Over-Automate Detection

A script saying:

```text
UNKNOWN PROCESS = HACKED
```

would create lots of false alarms.

Instead:

```text
Detection
   ↓
Evidence
   ↓
Context
   ↓
Investigation
   ↓
Decision
```

Automation should help the analyst, not replace reasoning.

# 66. Interview Questions

### Q1. What is a rootkit?

Malicious software designed to maintain privileged access and/or hide malicious activity.

---

### Q2. Are Linux systems immune to malware?

No. Linux can be compromised through vulnerable applications, stolen credentials, misconfiguration, supply-chain attacks, and other vectors.

---

### Q3. What is `rkhunter`?

A tool that checks for various indicators associated with rootkits and suspicious system modifications.

---

### Q4. What is `chkrootkit`?

A traditional tool that performs checks for known rootkit indicators.

---

### Q5. Are `rkhunter` and `chkrootkit` enough to secure a server?

No. They are only detection tools and can have false positives/negatives.

---

### Q6. What is file integrity monitoring?

Monitoring important files for unauthorized changes, often using cryptographic hashes and metadata.

---

### Q7. What is AIDE?

An open-source file integrity monitoring system that compares the current filesystem against a trusted baseline.

---

### Q8. How would you investigate a suspicious process?

I'd inspect:

```text
PID
User
Command line
Executable
Parent process
Open files
Network connections
Environment
Logs
Audit events
Persistence mechanisms
```

---

### Q9. Why is a root compromise difficult to trust after cleanup?

Because the attacker may have modified binaries, created hidden persistence, stolen credentials, or altered logging. You may not be able to prove the system is trustworthy.

---

### Q10. What is the preferred approach after a serious server compromise?

Preserve evidence, contain the incident, revoke/rotate credentials, rebuild from trusted sources, restore verified data, harden the new system, and monitor it carefully.

# 67. The Most Important Security Lesson ⭐⭐⭐⭐⭐

Don't rely on one security tool.

A strong Linux security strategy looks like:

```text
              ┌───────────────┐
              │   Firewall    │
              └───────┬───────┘
                      │
              ┌───────▼───────┐
              │    Fail2ban   │
              └───────┬───────┘
                      │
              ┌───────▼───────┐
              │    systemd    │
              │    sandbox    │
              └───────┬───────┘
                      │
              ┌───────▼───────┐
              │    auditd     │
              └───────┬───────┘
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼

```

Each layer answers a different question.

# 69. Final Mental Model

When you suspect malware:

```text
             SUSPICION
                 │
                 ▼
          Observe, don't panic
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Process    Network     Files
       │         │         │
       └─────────┼─────────┘
                 ▼
              auditd
                 │
                 ▼
             Persistence
                 │
                 ▼
       rkhunter / chkrootkit
                 │
                 ▼
             File integrity
                 │
                 ▼
             Correlation
                 │
                 ▼
             Assessment
```

The most important mindset is:

> **A security scanner finding something is the beginning of an investigation, not the end.**

And the reverse is also true:

> **A scanner reporting "clean" does not prove that a server is uncompromised.**

You need multiple independent sources of evidence.
