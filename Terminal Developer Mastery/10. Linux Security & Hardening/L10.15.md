# Lesson 10.15 — Linux Incident Response Basics 🚨🛡️

**Module 10 — Linux Security & Hardening**  
**Part 7: Security Operations**

You've now learned how to:

```text
10.13 → Audit Linux activity with auditd
10.14 → Detect malware/rootkit indicators
```

Now we put those skills together.

> **Incident response is the structured process of detecting, containing, investigating, recovering from, and learning from a security incident.**

For a backend developer, this is important because production security isn't only about preventing attacks.

You also need to know:

> **What should I do when the server is already compromised?**

---

# 1. What Is a Security Incident?

A security incident is an event that threatens:

```text
Confidentiality
Integrity
Availability
```

the CIA triad from Lesson 10.1.

Examples:

```text
Unauthorized SSH login
Stolen credentials
Malicious process
Ransomware
Data breach
Web shell
Command injection
Unauthorized user
Modified system files
Compromised API key
Suspicious outbound traffic
```

---

# 2. Event vs Incident

Not every security event is an incident.

For example:

```text
Failed SSH login
```

is a:

> **Security event**

But:

```text
1000 failed logins
+
successful login
+
new sudo user
+
unknown process
```

could indicate:

> **Security incident**

Think:

```text
Event
  ↓
Investigation
  ↓
Potential incident
```

# 7. Incident Response Runbook

A **runbook** is a documented set of steps for handling a situation.

Example:

```text

1. Confirm alert
2. Assess severity
3. Preserve evidence
4. Contain affected system
5. Revoke credentials
6. Investigate
7. Rebuild
8. Restore trusted data
9. Verify
10. Monitor
11. Document
```

When you're under pressure, a runbook is extremely useful.

# 8. Phase 2 — Detection

Detection means:

> **Something suspicious has been identified.**

Sources can include:

```text
Monitoring
Application logs
auditd
journalctl
Fail2ban
Firewall logs
AIDE
rkhunter
Network monitoring
User reports
Cloud alerts
```

Example:

```text
Alert:
CPU > 95% for 15 minutes
```

This isn't necessarily a security incident.

Investigate.

---

# 9. Example Detection

Suppose your monitoring reports:

```text
Node.js CPU = 99%
```

You run:

```bash
ps aux --sort=-%cpu | head
```

You discover:

```text
node      99%
```

Possible explanations:

```text
Normal traffic
Infinite loop
Memory/CPU bug
Expensive operation
DDoS
Cryptominer
Compromise
```

Never jump directly to:

```text
CPU high = hacked
```

---

# 10. Detection Requires Context

Suppose your server normally has:

```text
CPU: 20–40%
```

but suddenly:

```text
CPU: 99%
```

and simultaneously:

```text
Unknown process
Unknown outbound connection
New cron job
```

Now the evidence is much stronger.

Security is about:

> **Correlation, not isolated signals.**

# 11. Severity Classification

Not every incident has the same severity.

A simple model:

### Low

```text
Single suspicious login
No evidence of compromise
```

### Medium

```text
Compromised user account
Limited system access
```

### High

```text
Root compromise
Sensitive data exposure
Production application compromised
```

### Critical

```text
Major data breach
Ransomware
Multiple production systems compromised
Customer data affected
```

Your organization should define its own severity criteria.

---

# 12. Why Severity Matters

Suppose:

```text
Low severity
```

You may investigate during normal operations.

But:

```text
Critical severity
```

might require:

```text
Immediate containment
Security team
Management
Legal/privacy response
Customer communication
```

Don't treat every event the same way.

# 14. Start With Evidence

Useful sources:

```text
auditd
journalctl
Application logs
Nginx logs
SSH logs
Firewall logs

Network connections
Filesystem metadata
File integrity data
Backups
```

For example:

```bash

```

and:

```bash
sudo journalctl --since "1 hour ago"
```

# 15. Investigate Processes

Start:

```bash
ps aux
```

Then identify suspicious processes:

```bash
ps -p <PID> -f
```

Inspect executable:

```bash
sudo readlink -f /proc/<PID>/exe
```

Command line:

```bash
sudo tr '\0' ' ' < /proc/<PID>/cmdline
```

Parent process:

```bash
pstree -ap <PID>
```

---

# 16. Investigate Network Activity

Check listening ports:

```bash
sudo ss -lntup
```

Check established connections:

```bash
sudo ss -tpn
```

For a specific process:

```bash
sudo lsof -Pan -p <PID> -i
```

Ask:

```text
What is this process connecting to?
Why?
Was this expected?
```

---

# 17. Investigate User Activity

Check:

```bash
last
```

and:

```bash
lastlog
```

Audit authentication:

```bash
sudo ausearch -m USER_LOGIN -i
```

Search sudo activity if your audit rules capture it:

```bash
sudo ausearch -x /usr/bin/sudo -i
```

Now you can start constructing:

```text
User
 ↓
Login
 ↓
Privilege escalation
 ↓
Command
 ↓
System modification
```

---

# 18. Investigate Files

Look for recently modified files in sensitive areas.

For example:

```bash
sudo find /etc -type f -mtime -1 -ls
```

This means:

> Files under `/etc` modified within roughly the last day.

Don't interpret every result as malicious.

System updates and legitimate configuration changes also modify files.

---

# 19. Investigate Persistence

Check:

### Systemd

```bash
systemctl list-unit-files
```

### Timers

```bash
systemctl list-timers --all
```

### Cron

```bash
sudo ls -la /etc/cron.d/
```

### User cron

```bash
crontab -l
```

### SSH keys

```bash
cat ~/.ssh/authorized_keys
```

Look for unexpected changes.

# 20. Phase 4 — Containment

Once you believe a system is compromised:

> **Stop the attacker from causing additional damage.**

Containment can include:

```text
Network isolation
Disable compromised account
Block malicious IP
Stop malicious process
Remove public access
Rotate credentials
Restrict service
```

The correct action depends on the incident.

---

# 21. Isolation

One strong containment technique is:

```text
Internet
   X
   │
Server
```

You might:

```text
Remove server from public network
```

or:

```text
Restrict firewall access
```

But be careful:

> Disconnecting a machine can destroy useful live evidence and may interrupt business-critical services.

Containment should be deliberate.

---

# 22. Don't Immediately Reboot 🚨

This is an important incident-response lesson.

If you suspect a serious compromise, don't automatically run:

```bash
sudo reboot
```

Why?

Because volatile information can disappear:

```text
Running processes
Memory contents
Network connections
Temporary state
```

For a serious incident, preserve evidence before destructive actions when feasible.

---

# 23. Volatile vs Non-Volatile Evidence

### Volatile

Lost when the system shuts down:

```text
RAM
Running processes
Active connections
Current process state
```

### Non-volatile

Usually survives shutdown:

```text
Disk files
Logs
Filesystem metadata
Configuration
```

Conceptually:

```text
RAM
 ↓
Most volatile

Disk
 ↓
Less volatile
```

Forensic collection should prioritize appropriately.

---

# 24. Live Response

During live response, you may collect:

```text
Current processes

Open files
System time
Memory information
Running services
```

Useful commands:

```bash
date

```

Record outputs carefully.

---

# 25. Preserve Evidence

Instead of:

```text
Run command
 ↓
Look at output
 ↓
Forget
```

do:

```text
Command
 ↓
Save output
 ↓
Timestamp
 ↓
Document
```

For example:

```bash
date | tee incident-date.txt
ps aux | tee processes.txt
sudo ss -tpn | tee connections.txt
```

This creates an investigation record.

# 26. Evidence Integrity

You want to know:

> **Has the evidence itself been modified?**

Cryptographic hashes can help.

For example:

```bash
sha256sum incident-notes.txt
```

For forensic workflows, evidence handling should be much more rigorous than casually hashing a text file.

The principle is:

```text
Evidence
 ↓
Preserve
 ↓
Hash
 ↓
Document
 ↓
Control access
```

---

# 27. Chain of Custody

**Chain of custody** means documenting:

```text
Who collected evidence?
When?
How?
Where was it stored?
Who accessed it?
Was it modified?
```

This becomes especially important in:

```text
Legal investigations
Compliance
Major breaches
Corporate investigations
```

For a small personal VPS, you may not need a formal legal process, but the concept is still valuable.

---

# 28. Containment Example

Suppose:

```text
Attacker
 ↓
Compromised account
 ↓
SSH access
```

Possible containment:

```text
Disable account
      +
Revoke SSH keys
      +
Restrict SSH firewall
      +
Rotate credentials
```

Example:

```bash
sudo passwd -l compromised_user
```

This locks the account's password-based login.

But if SSH keys or other authentication paths are involved, you must revoke those separately.

---

# 29. Don't Delete the User Immediately

A common beginner reaction:

```bash
sudo userdel -r hacker
```

That may destroy evidence.

Better:

```text
Disable account
 ↓
Preserve evidence
 ↓
Investigate
 ↓
Remove/rebuild later
```

This is an important incident-response mindset.

---

# 30. Credential Rotation

If you suspect compromise, assume secrets may be exposed.

Potentially affected:

```text
SSH keys
Database passwords
JWT secrets
API keys
Cloud credentials
GitHub tokens
Razorpay secrets
SMTP credentials
```

For your MERN applications, this is especially important.

If a server was compromised:

> **Do not assume `.env` secrets are still secret.**

---

# 31. Example MERN Incident

Imagine your production Node.js server contains:

```text
DATABASE_URL
JWT_SECRET
RAZORPAY_KEY_SECRET
SMTP_PASSWORD
```

An attacker gets root.

Even if the application itself looks fine:

```text
.env
 ↓
Potentially readable by root
```

Therefore:

```text
Compromise
 ↓
Assume secrets exposed
 ↓
Rotate credentials
 ↓
Update application
 ↓
Invalidate old credentials
```

---

# 32. Token Rotation

Suppose your backend uses:

```text
JWT_SECRET
```

and it may have been exposed.

Simply restarting Node.js isn't enough.

You may need to:

```text
Generate new secret
 ↓
Deploy new secret
 ↓
Invalidate existing sessions/tokens
 ↓
Require re-authentication
```

The exact approach depends on your authentication architecture.

---

# 33. Database Credentials

If:

```text
DATABASE_URL
```

may have been exposed:

```text
1. Rotate database password
2. Restrict database network access
3. Review database logs
4. Check suspicious queries
5. Review database users
```

Don't wait until after rebuilding to think about credentials.

---

# 34. API Keys

If an API secret may have leaked:

```text
Razorpay
AWS
GitHub
Google
SMTP
Cloudinary
```

you should:

```text
Revoke old key
 ↓
Create new key
 ↓
Update application
 ↓
Verify old key no longer works
```

This is one reason secret rotation procedures should exist **before** an incident.

# 35. Phase 5 — Eradication

Containment stops the immediate threat.

Eradication removes the cause.

For example:

```text
Malware
 ↓
Remove

Backdoor
 ↓
Remove

Compromised account
 ↓
Disable/remove

Vulnerability
 ↓
Patch

Malicious SSH key
 ↓
Revoke
```

But for serious root compromise, rebuilding is often safer.

---

# 36. Patch the Vulnerability

Suppose the attack entered through:

```text
Old Node.js package
```

Then removing the malware isn't enough.

You must fix:

```text
Vulnerable dependency
```

Otherwise:

```text
Clean server
 ↓
Same vulnerability
 ↓
Attacker returns
```

This is called:

> **Reinfection**

---

# 37. Dependency Security

For Node.js:

```bash
npm audit
```

can identify known vulnerabilities in dependencies.

Also inspect:

```bash
npm outdated
```

and keep dependencies maintained.

But don't blindly run:

```bash
npm audit fix --force
```

on production.

Major dependency changes can introduce breaking changes.

Security fixes must be tested.

# 40. Why Rebuild Is Powerful

Imagine you don't know:

```text
Which files changed?
Which binaries were replaced?
Which persistence mechanisms exist?
```

Manual cleanup:

```text
Search
 ↓
Guess
 ↓

 ↓

```

Rebuild:

```text

 ↓

 ↓
Known-good application
 ↓
Trusted configuration
```

The second approach gives you much higher confidence.

# 46. Incident Communication

During a serious incident, communication matters.

A useful structure:

```text
What happened?
What is affected?
What is not affected?
What are we doing?
What is the current risk?
When is the next update?
```

Avoid:

```text
"We're probably fine."
```

Use factual statements.

Technical team:

```text

```


# 48. Don't Destroy Evidence

During incidents, avoid actions like:

```text
rm -rf suspicious-directory
reboot immediately
clear logs
delete user
kill everything
```

without first considering evidence and operational impact.

Sometimes immediate containment requires destructive actions.

But when feasible:

> **Preserve first, destroy later.**

# 54. RPO and RTO Preview

Two important concepts:

### RPO

**Recovery Point Objective**

> How much data can you afford to lose?

Example:

```text
RPO = 1 hour
```

means you aim to recover to within roughly the last hour of data.

### RTO

**Recovery Time Objective**

> How quickly must the service be restored?

Example:

```text
RTO = 30 minutes
```

means you aim to restore service within roughly 30 minutes.

We'll study these properly in 10.16.

# 55. Interview Questions

### Q1. What is incident response?

A structured process for detecting, analyzing, containing, eradicating, recovering from, and learning from security incidents.

---

### Q2. What are the major incident-response phases?

```text
Preparation
Detection
Analysis
Containment
Eradication
Recovery
Lessons learned
```

---

### Q3. Why shouldn't you immediately reboot a compromised server?

Because rebooting destroys volatile evidence such as running processes, memory state, and active network connections.

---

### Q4. What is containment?

Actions taken to limit the attacker's ability to continue causing damage.

---

### Q5. What is eradication?

Removing the malicious activity and fixing the underlying cause.

---

### Q6. Why might you rebuild instead of cleaning a compromised server?

After a serious compromise, you may not be able to confidently determine everything the attacker changed. Rebuilding from trusted sources provides stronger assurance.

---

### Q7. What credentials should be rotated after a server compromise?

Potentially:

```text
SSH keys
Database credentials
API keys
Cloud credentials
JWT secrets
SMTP credentials
Third-party service secrets
```

depending on what the attacker could access.

---

### Q8. What is the difference between containment and eradication?

```text
Containment
→ Stop the damage.

Eradication
→ Remove the cause and attacker persistence.
```

---

### Q9. Why are backups important for incident response?

They provide a trusted path to recover data and services after destructive or malicious events.

---

### Q10. What is a post-incident review?

A structured review of what happened, why it happened, what worked, what failed, and what should be improved.

# 59. The Most Important Mindset

A beginner thinks:

> "How do I remove the virus?"

A security engineer asks:

```text
How did they get in?

What did they access?

What did they change?

How long were they there?

What credentials were exposed?

How do I know they're gone?

Can they get back in?

How do I prevent this from happening again?
```

That's the difference between **cleanup** and **incident response**.
