# Lesson 10.16 — Backup & Disaster Recovery 💾🛡️

**Module 10 — Linux Security & Hardening**  
**Part 7: Security Operations**

In Lesson 10.15, we learned what to do **when a server is compromised**.

Now we answer:

> **How do we make sure we can recover our application and data when something goes seriously wrong?**

This is where **backups and disaster recovery** come in.

For your future MERN production applications, this is one of the most important production skills you can learn.

---

# 1. What Is a Backup?

A backup is a separate copy of data that can be used to restore the original after:

```text
Accidental deletion
Hardware failure
Ransomware
Server compromise
Database corruption
Bad deployment
Human error
Cloud outage
```

Conceptually:

```text
Production
    │
    ▼
Application Data
    │
    ├──────────► Backup 1
    │
    ├──────────► Backup 2
    │
    └──────────► Off-site Backup
```

---

# 2. Backup ≠ Disaster Recovery

These terms are related but different.

### Backup

> A copy of data.

### Disaster Recovery

> The complete process of restoring systems and services after a major failure.

Think:

```text
Backup
   ↓
Data protection

Disaster Recovery
   ↓
Data + infrastructure + application + people + procedures
```

A backup is only one component of disaster recovery.

---

# 3. Example

Suppose your production server dies.

You have:

```text
MongoDB backup
```

Great.

But what about:

```text
Node.js application
Nginx configuration
SSL certificates
Environment configuration
systemd service
Firewall rules
Users
DNS
```

If you don't know how to reconstruct these:

```text
Backup exists
      ↓
But application still unavailable
```

That's why disaster recovery is broader.

---

# 4. The Three Questions

A good backup strategy answers:

### 1. What do we back up?

```text
Database
Application data
Configuration
```

### 2. Where do we store it?

```text
Local
Remote
Off-site
Cloud
```

### 3. Can we restore it?

This third question is the most important.

> **A backup that has never been successfully restored is only an assumption.**

---

# 5. The 3-2-1 Backup Rule ⭐⭐⭐⭐⭐

One of the most useful concepts:

> **3 copies of your data, on 2 different types of storage, with 1 copy off-site.**

Example:

```text
Original production data
        │
        ├──► Local backup
        │
        ├──► Secondary backup
        │
        └──► Off-site backup
```

So:

```text
3 copies
2 storage locations/types
1 off-site
```

---

# 6. Why 3-2-1?

Imagine:

```text
Server
   ↓
Backup on same server
```

Server dies:

```text
Server ❌
Backup ❌
```

Not useful.

Now:

```text
Server
   ↓
Local backup
   ↓
Off-site backup
```

Server failure doesn't destroy every copy.

---

# 7. Modern Backup Thinking

The traditional 3-2-1 rule is a good starting point.

Modern systems may go further:

```text
3 copies
2 media/storage types
1 off-site
+
1 immutable/offline copy
+
Regular restore testing
```

This is especially useful against ransomware.

---

# 8. What Should You Back Up?

For your MERN application:

```text
                    BACKUP
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
   Database        Application       Configuration
       │               │                │
       ▼               ▼                ▼
    MongoDB         Source/build      Nginx
    data            artifacts         systemd
                                     firewall
                                     TLS
```

But don't blindly back up everything.

---

# 9. Database Backup

For MongoDB, your most important data is usually:

```text
Users
Courses
Orders
Payments
Progress
Analytics
Application records
```

You need a reliable database backup strategy.

For MongoDB tools, `mongodump` can create BSON-based backups.

Example:

```bash
mongodump --uri="$MONGODB_URI" --out="/backup/mongodb"
```

Then restore with:

```bash
mongorestore --uri="$MONGODB_URI" /backup/mongodb
```

Always test these against a **test database/environment**, not production.

---

# 10. Don't Store Database Passwords in Shell History

Avoid doing:

```bash
mongodump --uri="mongodb+srv://username:password@..."
```

directly in commands that may end up in shell history.

Better:

```bash
export MONGODB_URI='...'
mongodump --uri="$MONGODB_URI" ...
```

Even better for production:

> Use a dedicated secret-management mechanism and carefully control who can access it.

---

# 11. MongoDB Atlas Backups

If you're using MongoDB Atlas, Atlas may provide managed backup capabilities depending on your cluster tier/configuration.

This can reduce the need to manually build everything yourself.

But remember:

```text
Managed backup
      ≠
Complete disaster recovery
```

You still need to know:

```text
How do I restore?
How long does restoration take?
Which configuration is required?
Where is my application?
```

# 12. Application Backup

Your source code should normally live in:

```text
Git
```

For example:

```text
GitHub
   ↓
Repository
   ↓
Source code
```

Therefore, you generally shouldn't treat your production server as the primary source of truth for application code.

Instead:

```text
Git repository
     ↓
CI/CD
     ↓
Production
```

This makes recovery much easier.

---

# 13. Configuration Backup

Configuration is often forgotten.

Important examples:

```text
/etc/nginx/
/etc/systemd/system/
/etc/ssh/
/etc/ufw/
/etc/audit/
/etc/fail2ban/
```

You don't necessarily need to blindly back up the entire `/etc`.

Instead, identify the configuration required to reconstruct the server.

---

# 14. Secrets Are Different

Be careful with:

```text
.env
Private SSH keys
Database passwords
API secrets
TLS private keys
Cloud credentials
```

You generally should **not** put production secrets into a normal Git repository.

A backup containing secrets must itself be protected.

Think:

```text
Backup
   ↓
Encryption
   ↓
Access control
   ↓
Audit
```

---

# 15. Full Backup

A full backup copies everything selected.

Example:

```text
Monday
 ↓
Full backup
 ↓
10 GB
```

Advantages:

```text
Simple restoration
Self-contained
Easy to understand
```

Disadvantages:

```text
More storage
More time
More bandwidth
```

---

# 16. Incremental Backup

An incremental backup stores changes since the **previous backup**.

Example:

```text
Sunday
 ↓
Full backup
 ↓
Monday
 ↓
Incremental changes

Tuesday
 ↓
Incremental changes

Wednesday
 ↓
Incremental changes
```

Storage-efficient.

But restoration can require:

```text
Full
+
Monday incremental
+
Tuesday incremental
+
Wednesday incremental
```

---

# 17. Differential Backup

A differential backup stores changes since the **last full backup**.

Example:

```text
Sunday
 ↓
Full

Monday
 ↓
Changes since Sunday

Tuesday
 ↓
All changes since Sunday

Wednesday
 ↓
All changes since Sunday
```

Restore:

```text
Full
+
Latest differential
```

Usually simpler than a long incremental chain, but later differential backups become larger.

---

# 18. Comparison

|Backup|Based On|Storage|Restore|
|---|---|--:|---|
|Full|Everything|High|Easy|
|Incremental|Previous backup|Low|More complex|
|Differential|Last full|Medium|Easier|

For many systems, a hybrid strategy is practical.

---

# 19. Example Backup Strategy

For a small production MERN application:

```text
Sunday
  ↓
Full backup

Monday
  ↓
Incremental

Tuesday
  ↓
Incremental

Wednesday
  ↓
Incremental

Thursday
  ↓
Incremental

Friday
  ↓
Incremental

Saturday
  ↓
Incremental
```

Then periodically create a new full backup.

The exact schedule should depend on:

```text
Data volume
Recovery requirements
Storage cost
RPO
```

---

# 20. RPO ⭐⭐⭐⭐⭐

**RPO = Recovery Point Objective**

It answers:

> **How much data can we afford to lose?**

Example:

```text
RPO = 24 hours
```

means:

> Losing up to roughly one day's data may be acceptable.

---

# 21. RPO Examples

### Personal blog

```text
RPO = 24 hours
```

Maybe acceptable.

### E-commerce application

```text
RPO = 1 hour
```

Potentially more appropriate.

### Banking system

```text
RPO = very low
```

Potentially requiring specialized replication/backup architecture.

---

# 22. RTO ⭐⭐⭐⭐⭐

**RTO = Recovery Time Objective**

It answers:

> **How long can the service be unavailable?**

Example:

```text
RTO = 4 hours
```

means:

> The service should be restored within roughly four hours.

---

# 23. RPO vs RTO

Memorize this:

```text
RPO
 ↓
How much data can I lose?

RTO
 ↓
How much time can I lose?
```

Or:

```text
RPO → DATA
RTO → TIME
```

Very common interview question.

---

# 24. Example

Suppose:

```text
Database failure
```

Your requirements:

```text
RPO = 1 hour
RTO = 30 minutes
```

That means:

```text
Data loss:
≤ approximately 1 hour

Downtime:
≤ approximately 30 minutes
```

Your architecture must be designed around those requirements.

---

# 25. Backup Frequency Depends on RPO

If:

```text
RPO = 24 hours
```

daily backups may be sufficient.

If:

```text
RPO = 15 minutes
```

daily backups aren't enough.

You may need:

```text
Frequent snapshots
Continuous replication
Point-in-time recovery
Transaction logs
```

So:

> **Backup frequency should come from business requirements, not habit.**

---

# 26. Recovery Depends on RTO

Suppose your backup takes:

```text
2 hours
```

to download.

Then:

```text
RTO = 30 minutes
```

is impossible using that recovery process.

This reveals an important principle:

> **Recovery procedures must be tested against the actual RTO.**

---

# 27. Restore Testing ⭐⭐⭐⭐⭐

Imagine:

```text
Backup exists
```

You assume:

```text
Everything is fine.
```

Then disaster happens:

```text
Restore
 ↓
Backup corrupted
```

or:

```text
Restore
 ↓
Missing configuration
```

or:

```text
Restore
 ↓
Application doesn't start
```

Therefore:

> **Restore testing is more important than backup creation.**

---

# 28. Backup Verification

After creating a backup, verify:

```text
File exists
Size is reasonable
Checksum available
Database backup completed
No errors
Expected collections/data exist
```

But this still isn't enough.

The strongest test is:

```text
Restore
 ↓
Start application
 ↓
Run tests
 ↓
Verify data
```

---

# 29. Test Environment

Never experiment with restoration by overwriting your production database.

Use:

```text
Production
   ↓
Backup
   ↓
Test environment
   ↓
Restore
   ↓
Verify
```

For example:

```text
MongoDB production
        ↓
backup
        ↓
MongoDB test database
        ↓
restore
```

---

# 30. MongoDB Restore Test

Conceptually:

```bash
mongodump --uri="$MONGODB_URI" --out="/backup/test"
```

Then restore into a separate database/environment.

Don't test restoration by pointing `mongorestore` at production unless you have a carefully controlled procedure.

# 31. Backup Encryption

Backups can contain:

```text
User data
Emails
Passwords/hashes
Orders
Payments
API data
Personal information
```

Therefore:

> **Backups are sensitive data.**

Encrypt them.

Conceptually:

```text
Production data
      ↓
Backup
      ↓
Encryption
      ↓
Remote storage
```

---

# 32. GPG

You've already listed:

```text
gpg
```

in your Module 10 tools.

GPG can encrypt files.

For example, conceptually:

```bash
gpg --symmetric backup.tar.gz
```

This creates an encrypted backup file.

You should use a strong passphrase and have a secure process for recovering the encryption key.

---

# 33. The Key Management Problem

Encryption is useless if:

```text
Backup = encrypted
Key = lost
```

Then:

```text
Backup
 ↓
Can't decrypt
 ↓
Data inaccessible
```

So:

> **Backup the backup encryption keys securely.**

But don't store:

```text
backup.tar.gz
backup-key.txt
```

in the same unprotected directory.

---

# 34. Off-Site Backups

Suppose your server is:

```text
Mumbai
```

and your backup is:

```text
same server
```

A server failure destroys both.

Better:

```text
Production server
      ↓
Remote storage
```

Possible destinations:

```text
Cloud object storage
Separate server
Dedicated backup system
Different geographic region
```

---

# 35. Immutable Backups

An immutable backup is designed so that it cannot be easily modified or deleted during its retention period.

This is particularly useful against ransomware.

Conceptually:

```text
Attacker
   ↓
Production
   ↓
Deletes backups
   X
Immutable backup
   ✓
```

This can dramatically improve recovery resilience.

---

# 36. Offline Backups

Another approach:

```text
Production
   ↓
Backup
   ↓
Offline storage
```

The backup isn't continuously connected to the production environment.

Therefore, if production credentials are compromised:

```text
Attacker
   X
Offline backup
```

This provides another layer of protection.

---

# 37. Backup Retention

Don't keep:

```text
Every backup forever
```

without a plan.

You might define:

```text
Daily → 7 days
Weekly → 4 weeks
Monthly → 12 months
```

This is only an example.

Retention depends on:

```text
Business requirements
Compliance
Storage cost
Data sensitivity
Recovery needs
```

---

# 38. Why Multiple Retention Periods?

Imagine someone notices:

```text
Corruption
```

after:

```text
10 days
```

If you only keep:

```text
Last 7 days
```

your clean backup may be gone.

Longer-term snapshots can protect against delayed detection.

---

# 39. Backup Rotation

A common strategy:

```text
Daily
 ↓
Short retention

Weekly
 ↓
Medium retention

Monthly
 ↓
Long retention
```

This balances:

```text
Storage cost
+
Recovery flexibility
```

# 40. Backing Up the Wrong Things

Don't blindly do:

```bash
sudo tar -czf server.tar.gz /
```

This can create huge, problematic, and potentially sensitive archives.

You may capture:

```text

/sys
/dev
/tmp
runtime sockets
secrets
cache
```

that don't belong in a normal backup.

Instead:

> Define exactly what needs recovery.

# 51. Example Backup Script

For a learning environment:

```bash
#!/bin/bash

set -e

DATE=$(date +"%Y-%m-%d_%H-%M-%S")
BACKUP_DIR="/backup/mongodb/$DATE"

mkdir -p "$BACKUP_DIR"

mongodump \
  --uri="$MONGODB_URI" \
  --out="$BACKUP_DIR"

echo "Backup completed: $BACKUP_DIR"
```

The important thing is:

```text
set -e
```

If an important command fails, the script should not silently report success.

# 52. Add Compression

You may compress the backup:

```bash
tar -czf backup.tar.gz backup-directory/
```

Compression can reduce:

```text
Storage
Bandwidth
Transfer time
```

But compression also consumes CPU.

Choose based on your environment.

---

# 53. Add Checksums

Generate:

```bash
sha256sum backup.tar.gz > backup.tar.gz.sha256
```

Then later:

```bash
sha256sum -c backup.tar.gz.sha256
```

This verifies that the file hasn't changed or become corrupted.

Important:

> A checksum proves integrity relative to the expected hash; it doesn't prove the backup contents are complete or logically restorable.

# 60. Interview Questions

### Q1. What is the difference between backup and disaster recovery?

```text
Backup
→ Copy of data.

Disaster recovery
→ Complete process for restoring systems/services.
```

---

### Q2. What is the 3-2-1 backup rule?

```text
3 copies
2 different storage/media types
1 off-site copy
```

---

### Q3. What is RPO?

> Maximum acceptable amount of data loss, measured in time.

---

### Q4. What is RTO?

> Maximum acceptable recovery time for restoring a service.

---

### Q5. RPO vs RTO?

```text
RPO → Data loss
RTO → Downtime
```

---

### Q6. Why test backups?

Because a successful backup job doesn't prove that the data can actually be restored.

---

### Q7. Why should backups be encrypted?

Because backups often contain sensitive production data.

---

### Q8. Why use off-site backups?

To protect against failures or incidents affecting the primary location.

---

### Q9. What is an immutable backup?

A backup designed to resist modification/deletion for a defined retention period.

---

### Q10. Why might you prefer rebuilding infrastructure instead of restoring the entire server image?

Infrastructure can often be recreated from trusted code/configuration, reducing uncertainty after a compromise and making recovery more reproducible.

# 61. Practical Lab 🧪 — Create a Local Backup

Let's create a simple learning backup.

Create:

```bash
mkdir -p ~/backup-lab/data
```

Create test data:

```bash
echo "Important application data" > ~/backup-lab/data/example.txt
```

Create archive:

```bash
tar -czf ~/backup-lab/backup.tar.gz ~/backup-lab/data
```

Check:

```bash
ls -lh ~/backup-lab/
```

```bash
sha256sum ~/backup-lab/backup.tar.gz \
  > ~/backup-lab/backup.tar.gz.sha256
```

Verify:

```bash
sha256sum -c ~/backup-lab/backup.tar.gz.sha256
```

You should see something similar to:

```text
backup.tar.gz: OK
```

# 63. Simulate Data Loss

Delete the original test data:

```bash
rm -rf ~/backup-lab/data
```

Now:

```bash
ls ~/backup-lab/
```

The original data is gone.

But your backup remains.

---

# 64. Restore the Backup

Run:

```bash
tar -xzf ~/backup-lab/backup.tar.gz -C ~/
```

Then:

```bash
cat ~/backup-lab/data/example.txt
```

You should get:

```text
Important application data
```

Congratulations.

You've performed a basic:

```text
Backup
 ↓
Delete
 ↓
Restore
 ↓
Verify
```

workflow.

For your MERN projects, I'd recommend thinking in this structure:

```text
                  PRODUCTION
```

# 67. The Most Important Mental Model ⭐⭐⭐⭐⭐

Think about disaster recovery as:

```text
CAN I RECOVER?
      │
      ▼
Do I have the data?
      │
      ▼
Is the backup trustworthy?
      │
      ▼
Can I restore it?
      │
      ▼
Can I rebuild the application?
      │
      ▼
Can I recover within RTO?
      │
      ▼
Can I recover within RPO?
      │
      ▼
Have I tested it?
```

If you can't answer **yes** to these questions, your disaster recovery isn't complete.
