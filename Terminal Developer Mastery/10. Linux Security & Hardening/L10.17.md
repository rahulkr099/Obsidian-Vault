**Module 10 — Linux Security & Hardening**

Now we're going to turn all of that knowledge into something practical:

> **A repeatable checklist for securing a Linux server before putting a backend application into production.**

For your MERN projects, this is especially important because a server is not secure just because the application works.

---

# 1. What Is Linux Hardening?

**Hardening** means reducing the number of ways an attacker can compromise your system.

Think of a default Linux server as:

```text
Fresh Server
     ↓
Many packages
Many services
Many ports
Default configurations
     ↓
Larger attack surface
```

Hardening changes that to:

```text
Fresh Server
     ↓
Remove unnecessary software
Disable unnecessary services
Restrict users
Harden SSH
Configure firewall
Update system
Secure services
Enable auditing
Configure backups
     ↓
Smaller attack surface
```

---

# 2. Attack Surface

The **attack surface** is the collection of possible entry points an attacker can target.

For example:

```text
Internet
   │
   ├── SSH
   ├── Nginx
   ├── Node.js
   ├── MongoDB
   ├── Redis
   ├── Docker
   └── Other services
```

Every unnecessary exposed service increases potential risk.

So:

> **Reduce what you don't need.**

---

# 3. The Linux Hardening Pyramid

A useful mental model:

```text
                 ┌───────────────┐
                 │ Monitoring    │
                 ├───────────────┤
                 │ Auditing      │
                 ├───────────────┤
                 │ Backups       │
                 ├───────────────┤
                 │ Applications  │
                 ├───────────────┤
                 │ Services      │
                 ├───────────────┤
                 │ Network       │
                 ├───────────────┤
                 │ Users         │
                 ├───────────────┤
                 │ OS            │
                 └───────────────┘
```

Security needs to exist at every layer.

# 5. Step 1 — Know Your Server

Before securing a server, know what's running.

Check OS:

```bash
cat /etc/os-release
```

Kernel:

```bash
uname -r
```

Hostname:

```bash
hostnamectl
```

CPU:

```bash
lscpu
```

Memory:

```bash
free -h
```

Disk:

```bash
df -h
```

---

# 6. Create a Server Inventory

Document:

```text
Hostname:
OS:
Kernel:
IP:
Public services:
Internal services:
Users:
Database:
Web server:
Application:
Backup system:
Monitoring:
```

Example:

```text
OS: Ubuntu 24.04
Web: Nginx
Backend: Node.js
Database: MongoDB
SSH: 22
HTTP: 80
HTTPS: 443
App: 127.0.0.1:3000
```

This gives you a baseline.

---

# 7. Step 2 — Update the System

First:

```bash
sudo apt update
```

Then:

```bash
sudo apt upgrade
```

For a production environment, understand what packages are being upgraded before blindly applying changes.

Security updates are critical because attackers frequently exploit known vulnerabilities.

---

# 8. Check Available Updates

You can inspect:

```bash
apt list --upgradable
```

Then review important updates.

For production:

```text
Test
 ↓
Deploy
 ↓
Monitor
```

is better than:

```text
Upgrade production blindly
```

---

# 9. Automatic Security Updates

For Debian/Ubuntu systems, you can use:

```bash
sudo apt install unattended-upgrades
```

Then configure automatic updates according to your environment.

The goal:

```text
Security patch released
       ↓
System automatically receives patch
```

But automatic updates should still be monitored.

---

# 10. Why Updates Matter

Suppose:

```text
Vulnerability discovered
       ↓
Patch released
       ↓
You don't update
       ↓
Attacker scans internet
       ↓
Your server vulnerable
```

Security isn't:

> "I installed a firewall."

It's:

> **Continuous maintenance.**

---

# 11. Step 3 — Review Users

List users:

```bash
getent passwd
```

Look for:

```text
Unexpected users
Unused accounts
Service accounts
Interactive shells
```

You should know why each privileged user exists.

---

# 12. Disable Unused Accounts

If an account is no longer needed, disable it rather than leaving it active.

For example:

```bash
sudo passwd -l username
```

This locks password authentication for that account.

Don't remove accounts blindly.

First understand:

```text
Who owns it?
What services use it?
Does automation depend on it?
```

---

# 13. Create a Dedicated Deployment User

Instead of doing everything as root:

```text
root
 ↓
Node.js
 ↓
Application
```

prefer:

```text
deploy
 ↓
Deployment

nodeapp
 ↓
Node.js application
```

This provides privilege separation.

---

# 14. Principle of Least Privilege

Give users and services:

> **Only the permissions they need.**

For example:

```text
Node.js
   ↓
Needs application directory
   ↓
Doesn't need
/etc/shadow
```

Similarly:

```text
Nginx
   ↓
Needs web files/network access
   ↓
Doesn't need root-level database access
```

---

# 15. Step 4 — Sudo

Check sudo access carefully.

Users with sudo effectively have powerful administrative access.

List members of the sudo group:

```bash
getent group sudo
```

Review:

```text
Who has sudo?
Why?
Do they still need it?
```

---

# 16. Use `visudo`

Never casually edit:

```text
/etc/sudoers
```

with a normal editor.

Use:

```bash
sudo visudo
```

Why?

`visudo` checks syntax before applying the configuration.

A syntax error in sudo configuration can create a serious administrative problem.

---

# 17. Step 5 — SSH Hardening

SSH is one of the most important areas.

Inspect:

```bash
sudo sshd -T
```

This is useful because it shows effective SSH configuration.

Check the configuration file:

```bash
sudo nano /etc/ssh/sshd_config
```

---

# 18. Disable Root SSH Login

A common hardening setting is:

```text
PermitRootLogin no
```

Then restart/reload SSH carefully.

On systemd systems:

```bash
sudo systemctl reload ssh
```

or depending on distribution:

```bash
sudo systemctl reload sshd
```

Always verify your system's service name first.

---

# 19. Use SSH Keys

Prefer:

```text
SSH key
```

over:

```text
Password
```

A typical setup:

```text
Laptop
  │
  │ private key
  ▼
SSH server
  │
  ▼
authorized_keys
```

Keep the private key only on trusted devices.

---

# 20. Disable Password Authentication

Once key-based authentication is tested and working, you can consider:

```text
PasswordAuthentication no
```

But don't disable password authentication before confirming that key authentication works.

Otherwise:

```text
SSH
 ↓
Password disabled
 ↓
Key doesn't work
 ↓
Locked out
```

Always maintain a tested recovery path.

---

# 21. SSH Configuration Example

A hardened SSH configuration might conceptually contain:

```text
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
```

But don't blindly copy configurations from the internet.

Your environment may require different settings.

---

# 22. SSH Port Changing

You might hear:

> "Change SSH from port 22 to 2222."

This can reduce automated noise.

But:

> **Changing the port is not a primary security control.**

An attacker can discover the new port through scanning.

Real security comes from:

```text
SSH keys
Firewall
MFA where appropriate
Rate limiting
Fail2ban
Strong access control
```

---

# 23. Step 6 — File Permissions

Check sensitive files.

For example:

```bash
ls -l /etc/shadow
```

Usually, it should not be readable by normal users.

Application secrets should also have restricted permissions.

For example:

```bash
chmod 600 .env
```

if the file should only be readable by its owner.

---

# 24. Understand `umask`

Check:

```bash
umask
```

A restrictive `umask` helps prevent newly created files from becoming unnecessarily accessible.

Example:

```text
umask 027
```

can be appropriate for some server environments, but choose based on the application's requirements.

---

# 25. Search for World-Writable Files

A useful audit:

```bash
sudo find / -xdev -type f -perm -0002 -ls 2>/dev/null
```

This searches for files writable by everyone.

Don't blindly change every result.

Some applications legitimately require specific permissions.

The goal is:

> **Find unexpected permissions.**

---

# 26. Check SUID Files

Run:

```bash
sudo find / -xdev -perm -4000 -type f 2>/dev/null
```

Review unusual SUID binaries.

Remember:

```text
SUID
 ↓
Program runs with owner's effective privileges
```

This can be useful but also dangerous when misconfigured.

---

# 27. Step 7 — Firewall

A production server should have an explicit network policy.

Conceptually:

```text
Internet
   ↓
Firewall
   ↓
Allowed services only
```

For example:

```text
22   → SSH
80   → HTTP
443  → HTTPS
```

Everything else:

```text
DENY
```

unless there is a specific reason to allow it.

---

# 28. UFW

On Ubuntu/Debian-based systems:

```bash
sudo ufw status
```

Enable:

```bash
sudo ufw enable
```

Before enabling it remotely, make sure SSH access is allowed.

For example:

```bash
sudo ufw allow OpenSSH
```

Then:

```bash
sudo ufw status verbose
```

---

# 29. Don't Lock Yourself Out

This is a classic mistake:

```bash
sudo ufw enable
```

without allowing SSH.

Result:

```text
SSH
 ↓
Firewall
 ↓
BLOCKED
```

Always establish your access rule first.

---

# 30. Better Firewall Design

For your MERN server:

```text
Internet
   │
   ▼
┌───────────────┐
│   Firewall    │
├───────────────┤
│ 22 → SSH      │
│ 80 → HTTP     │
│ 443 → HTTPS   │
└───────┬───────┘
        │
        ▼
      Nginx
        │
        ▼
  127.0.0.1:3000
        │
        ▼
     Node.js
```

MongoDB shouldn't be publicly exposed just because the application uses it.

---

# 31. Check Listening Ports

Run:

```bash
sudo ss -lntup
```

Create a list:

```text
Expected:
22
80
443
```

Then investigate:

```text
27017
6379
3000
4444
8080
```

if they are unexpectedly exposed.

---

# 32. Step 8 — Disable Unused Services

List running services:

```bash
systemctl --type=service --state=running
```

Ask:

```text
Do I need this?
Why is it running?
Is it publicly reachable?
Can it be disabled?
```

Disable an unnecessary service:

```bash
sudo systemctl disable --now service-name
```

But understand what the service does before disabling it.

---

# 33. Why Remove Unused Services?

Suppose:

```text
10 services
```

are exposed.

Each service potentially contains:

```text
Code
Dependencies
Configuration
Credentials
Network listeners
Vulnerabilities
```

Reducing services reduces:

```text
Attack surface
```

---

# 34. Step 9 — Remove Unnecessary Packages

List installed packages:

```bash
apt list --installed
```

Remove packages you genuinely don't need.

For example:

```bash
sudo apt remove package-name
```

Then:

```bash
sudo apt autoremove
```

Again:

> Don't remove packages simply because you don't recognize them.

Some are dependencies required by other software.

---

# 35. Minimal Server Philosophy

A good production server should ideally contain:

```text
OS
+
Required runtime
+
Required services
+
Security tools
+
Monitoring
```

Not:

```text
OS
+
Games
+
GUI
+
Unused databases
+
Compilers
+
Random packages
+
Development tools
```

unless there's a specific reason.

---

# 36. Step 10 — Kernel Hardening

Keep the kernel updated:

```bash
uname -r
```

Check installed kernels:

```bash
dpkg -l | grep linux-image
```

Kernel security updates can fix:

```text
Privilege escalation
Memory vulnerabilities
Network vulnerabilities
Filesystem vulnerabilities
```

---

# 37. Kernel Parameters

Linux exposes many security-related parameters through:

```text
/proc/sys/
```

and:

```bash
sysctl
```

For example:

```bash
sysctl net.ipv4.ip_forward
```

You may encounter settings related to:

```text
IP forwarding
Reverse path filtering
ICMP
Network behavior
Kernel protections
```

But don't blindly apply random "Linux hardening sysctl" lists from the internet.

Some can break legitimate networking.

---

# 38. Step 11 — Secure Boot

**Secure Boot** helps ensure that trusted boot components are used during system startup.

Conceptually:

```text
Power on
   ↓
Firmware
   ↓
Verify bootloader
   ↓
Verify trusted components
   ↓
Boot OS
```

It can make certain boot-level attacks more difficult.

---

# 39. Secure Boot Is Not a Complete Security Solution

Secure Boot doesn't protect you from:

```text
Application vulnerabilities
Weak passwords
Exposed databases
Bad permissions
Compromised npm package
SQL/NoSQL injection
```

Think:

```text
Secure Boot
     +
OS hardening
     +
Application security
     +
Network security
```

---

# 40. Step 12 — Time Synchronization ⏰

Accurate time is extremely important for:

```text
Logs
Auditing
Incident response
TLS
Distributed systems
Monitoring
```

Check:

```bash
timedatectl
```

Look for:

```text
System clock synchronized: yes
NTP service: active
```

---

# 41. Why Time Matters During an Incident

Imagine:

```text
Server A:
10:01 attack

Server B:
09:55 login

Server C:
10:08 file modification
```

If clocks aren't synchronized, your timeline becomes unreliable.

With synchronized time:

```text
10:01 → Login
10:03 → Privilege escalation
10:05 → File modified
10:07 → Network connection
```

Much easier to investigate.

---

# 42. Step 13 — Logging

Check:

```bash
journalctl
```

For recent logs:

```bash
journalctl --since "1 hour ago"
```

For SSH:

```bash
journalctl -u ssh
```

or depending on the system:

```bash
journalctl -u sshd
```

Logs should be:

```text
Available
Protected
Retained
Monitored
```

---

# 43. Don't Keep All Logs Only Locally

If an attacker gets root:

```text
Server
 ↓
Attacker
 ↓
Deletes logs
```

Now investigation becomes much harder.

For important environments, consider:

```text
Server
 ↓
Central log system
```

This connects directly with your Module 9 observability knowledge.

---

# 44. Step 14 — Auditd

Check:

```bash
sudo systemctl status auditd
```

You should know what you're auditing.

Examples:

```text
Authentication
Privilege changes
Sensitive file modifications
sudo usage
Security configuration
```

Avoid auditing everything blindly.

Excessive auditing can generate enormous amounts of data.

---

# 45. Step 15 — Malware Detection

From Lesson 10.14:

```text
rkhunter
chkrootkit
AIDE
```

You can periodically run security checks.

For example:

```bash
sudo rkhunter --check
```

and use AIDE for file integrity monitoring.

Remember:

> These tools complement hardening; they don't replace it.

---

# 46. Step 16 — Fail2ban

For exposed services like SSH, consider:

```text
fail2ban
```

It monitors logs and can temporarily block clients showing malicious patterns.

Conceptually:

```text
Failed SSH attempts
       ↓
fail2ban
       ↓
Firewall block
```

This helps reduce brute-force noise and attacks.

---

# 47. Step 17 — Secure Nginx

If you're using Nginx:

Check configuration:

```bash
sudo nginx -t
```

Avoid exposing:

```text
Server version
Debug information
Internal application ports
```

Use HTTPS.

Conceptually:

```text
Internet
   ↓
HTTPS
   ↓
Nginx
   ↓
Node.js
```

---

# 48. Step 18 — Secure Node.js

Your Node.js process should not run as root.

Bad:

```text
root
 ↓
node app
```

Better:

```text
nodeapp
 ↓
Node.js
```

The application should have only the permissions it needs.

---

# 49. Node.js Environment Variables

Your production application may have:

```text
MONGODB_URI
JWT_SECRET
RAZORPAY_KEY_SECRET
SMTP_PASSWORD
```

Protect them.

Don't:

```text
git add .env
```

Don't:

```text
chmod 644 .env
```

if the file contains secrets and doesn't need to be world-readable.

---

# 50. Step 19 — Database Exposure

Check whether MongoDB is listening publicly.

For example:

```bash
sudo ss -lntup | grep 27017
```

If MongoDB is only needed locally:

```text
127.0.0.1
```

or on a private network is preferable.

Bad:

```text
0.0.0.0:27017
```

with broad firewall access.

---

# 51. Step 20 — Docker Security

If you're using Docker:

Avoid:

```text
--privileged
```

unless genuinely required.

Avoid mounting sensitive host paths unnecessarily:

```text
-v /:/host
```

Also avoid running every container as root.

Use:

```text
Non-root containers
Minimal images
Read-only filesystem where possible
Dropped capabilities
Network restrictions
Secret management
```

This connects with your Phase 13 Docker/CI-CD work.

---

# 52. Step 21 — Secrets Management

Don't scatter secrets across:

```text
Shell scripts
Git repositories
Dockerfiles
Logs
Chat messages
Plain-text notes
```

Use an appropriate secret-management approach.

At minimum:

```text
Restricted permissions
Encrypted storage
Limited access
Rotation procedure
```

# 53. Step 22 — Backups

From Lesson 10.16:

```text
3-2-1
```

Check:

```text
[ ] Backup exists
[ ] Backup is recent
[ ] Backup is encrypted
[ ] Backup is off-site
[ ] Backup is monitored
[ ] Restore tested

```

# 54. Step 23 — Recovery

Don't stop at:

```text
Backup successful
```

Test:

```text
Fresh server
 ↓
Restore
 ↓
Application starts
 ↓
Database works
 ↓
Users can log in
 ↓
Files accessible
 ↓
HTTPS works
```

This validates the entire recovery chain.

# 55. Step 24 — Application Security

Linux hardening doesn't protect you from application vulnerabilities.

Your MERN application still needs:

```text
Input validation
Authentication
Authorization
Rate limiting
Secure cookies
CSRF protection where applicable
CORS configuration
Dependency security
NoSQL injection protection
XSS protection
Secure headers
Error handling
Secret management
```

This is why your earlier security lessons remain important.

# 56. Step 25 — Dependency Security

For Node.js:

```bash
npm audit
```

Also:

```bash
npm outdated
```

Review dependencies regularly.

Security should exist in:

```text
Developer laptop
       ↓
Git
       ↓
CI/CD
       ↓
Production
```

not only on the Linux server.

---

# 57. Step 26 — Remove Development Tools From Production

If your production server doesn't need:

```text
VS Code
Git GUI
Compilers
Debugging tools
Development databases
```

don't install them unnecessarily.

A production server should be focused.

But don't take this too literally: some operational tools may be valuable for diagnostics. The goal is **minimum necessary software**, not zero tools.

---

# 58. Step 27 — Disable Debug Mode

Never run production applications with development debugging enabled.

For example:

```text
NODE_ENV=production
```

should generally be set appropriately for production.

Avoid exposing:

```text
Stack traces
Environment variables
Debug endpoints
Internal errors
```

to users.

---

# 59. Step 28 — Security Headers

At the reverse proxy/application layer, consider appropriate headers such as:

```text
Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options
Referrer-Policy
```

Use headers based on your application's actual requirements.

Security headers should complement, not replace, proper application security.


### Check ports

### Check services


### Check synchronization

```bash
timedatectl
```

### Check audit

```bash
sudo systemctl status auditd
```

### Check disk

# 71. Interview Questions

### Q1. What is Linux hardening?

Reducing a Linux system's attack surface by removing unnecessary components, restricting access, securing services, applying updates, and implementing security controls.

---

### Q2. Why disable unused services?

Every unnecessary service can introduce additional attack surface and potential vulnerabilities.

---

### Q3. Why shouldn't applications run as root?

If the application is compromised, the attacker may inherit root-level privileges.

---

### Q4. What is least privilege?

Giving users, applications, and services only the permissions they actually need.

---

### Q5. Why is changing SSH port not a strong security control?

It can reduce automated scanning noise, but attackers can discover non-standard ports. SSH keys, access restrictions, MFA, firewall rules, and rate limiting provide stronger security.

---

### Q6. Why synchronize server time?

Accurate time is essential for logs, security auditing, incident timelines, TLS, and distributed systems.

---

### Q7. Why shouldn't MongoDB be publicly exposed?

It unnecessarily increases attack surface and could allow unauthorized access if authentication or network controls fail.

---

### Q8. What is defense in depth?

Using multiple independent security layers so that failure of one control doesn't expose the entire system.

---

### Q9. What is a security baseline?

A documented definition of the expected secure configuration against which the current system can be compared.

---

### Q10. What is the difference between hardening and monitoring?

```text
Hardening → Reduce/prevent risk
Monitoring → Detect suspicious activity
```
