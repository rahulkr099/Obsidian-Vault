---

# 6. Good Bash Practices

Use:

```bash
#!/bin/bash

set -euo pipefail
```

This gives you stronger error handling.

### `-e`

Exit when a command fails.

### `-u`

Treat undefined variables as errors.

### `pipefail`

Make pipelines fail if an earlier command fails.

This is especially useful for backup/security scripts.

# 11. Check Disk Space Automatically

Disk exhaustion can become a security and availability problem.

Example:

```bash
df -P / | awk 'NR==2 {print $5}'
```

You might get:

```text
78%
```

You can turn that into a check.

---

# 12. Disk Alert Script

Example:

```bash
#!/bin/bash

set -euo pipefail

THRESHOLD=80

USAGE=$(df -P / | awk 'NR==2 {gsub("%",""); print $5}')

if [ "$USAGE" -ge "$THRESHOLD" ]; then
    echo "WARNING: Root filesystem usage is ${USAGE}%"
else
    echo "Disk usage OK: ${USAGE}%"
fi
```

Now your server can automatically detect disk pressure.

[Install]

# 33. Check Certificate Expiry

For a certificate:

```bash
openssl x509 -in certificate.crt -noout -dates
```

You'll see:

```text
notBefore=...
notAfter=...
```

For a remote HTTPS server:

```bash
echo | openssl s_client \
  -connect example.com:443 \
  -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates
```

This is useful for learning certificate automation.

---

# 38. Example Compliance Script

```bash
#!/bin/bash

check() {
    local name="$1"
    local condition="$2"

    if eval "$condition"; then
        echo "[PASS] $name"
    else
        echo "[FAIL] $name"
    fi
}

check "Firewall enabled" \
      "sudo ufw status | grep -q 'Status: active'"

check "Root SSH disabled" \
      "sudo sshd -T | grep -q 'permitrootlogin no'"
```

This is a simple starting point.

---

# 39. Be Careful With `eval`

The example above is educational.

For production security scripts, avoid using `eval` with untrusted input.

Prefer explicit commands and functions.

For example:

```bash
if sudo ufw status | grep -q "Status: active"; then
    echo "[PASS] Firewall"
else
    echo "[FAIL] Firewall"
fi
```

Security automation itself must be secure.

# 57. Automation Security

This is extremely important:

> **Security automation itself is privileged software.**

Suppose your script runs as root:

```text
security-audit.sh
```

If an attacker can modify it:

```text
Attacker
 ↓
Modify script
 ↓
systemd runs script as root
 ↓
Root compromise
```

This creates a privilege-escalation path.

---

# 58. Protect Automation Scripts

For root-owned scripts:

```bash
sudo chown root:root /usr/local/bin/security-audit.sh
```

Permissions:

```bash
sudo chmod 750 /usr/local/bin/security-audit.sh
```

You want:

```text
root
 ↓
write
```

while normal users should generally not be able to modify it.

---

# 59. Protect Configuration

Similarly:

```text
/etc/systemd/system/security-audit.service
```

should not be writable by ordinary users.

Check:

```bash
ls -l /etc/systemd/system/security-audit.service
```

Security automation must follow least privilege too.

---

# 63. Idempotency

A very useful DevOps concept:

> Running an automation multiple times should produce the same desired state without causing damage.

For example:

```text
Ensure firewall is enabled
```

is better than:

```text
Enable firewall blindly every time
```

Similarly:

```text
Ensure user exists
```

instead of:

```text
Create user
```

This becomes extremely important when you start using Ansible.

---

# 64. Example Idempotent Logic

Instead of:

```bash
useradd deploy
```

every time, use:

```bash
if id deploy >/dev/null 2>&1; then
    echo "deploy already exists"
else
    sudo useradd deploy
fi
```

Now the script can run repeatedly.

# 73. Interview Questions

### Q1. Why automate security tasks?

To make security controls consistent, repeatable, timely, and less dependent on manual work.

### Q2. Cron vs systemd timer?

Both schedule tasks. systemd timers integrate deeply with systemd services, journald, dependencies, and service state.

### Q3. What is idempotency?

An operation can be executed repeatedly without causing unintended changes beyond reaching the desired state.

### Q4. Why is security automation itself a security risk?

Because privileged scripts and services can become attack vectors if attackers can modify or influence them.

### Q5. Why should automated scripts have logging and exit codes?

So failures can be detected, investigated, and alerted on rather than silently ignored.

### Q6. Why shouldn't every security problem be automatically fixed?

Automated remediation can destroy evidence, break production systems, or incorrectly respond to false positives.

### Q7. How can security be integrated into CI/CD?

Through automated testing, dependency scanning, secret scanning, container scanning, infrastructure checks, and deployment verification.

### Q8. What is DevSecOps?

Integrating security practices throughout the software development and deployment lifecycle rather than treating security as a final step.
