# 2. Important Rule Before Starting ⚠️

Do this exercise on:

- a disposable VPS,


# 6. Step 3 — Create a Dedicated Admin User

Don't perform all administration through root.

Create:

```bash
sudo adduser deploy
```

Add sudo access:

```bash
sudo usermod -aG sudo deploy
```

Verify:

```bash
groups deploy
```

You should see:

```text
deploy sudo
```

---

# 7. Why `deploy`?

We'll use:

```text
root
 ↓
System administration

deploy
 ↓
Deployment

nodeapp
 ↓
Node.js application
```

This separates responsibilities.

That's **privilege separation**.

---

# 8. Step 4 — Configure SSH Keys

On your local machine:

```bash
ssh-keygen -t ed25519
```

This creates:

```text
~/.ssh/id_ed25519
~/.ssh/id_ed25519.pub
```

The important rule:

```text
Private key → stays private
Public key  → goes to server
```

Never upload your private key to the server.

---

# 9. Copy the Public Key

You can use:

```bash
ssh-copy-id deploy@SERVER_IP
```

Then test:

```bash
ssh deploy@SERVER_IP
```

Before changing SSH configuration, **make sure this works**.

---

# 10. Step 5 — Test a Second SSH Session

This is a very important operational habit.

Keep your current SSH connection open.

Open another terminal:

```bash
ssh deploy@SERVER_IP
```

Now you have:

```text
Terminal 1 → Existing session
Terminal 2 → Test session
```

Only make risky SSH changes while you have a working fallback session.

---

# 11. Step 6 — Harden SSH

Edit:

```bash
sudo nano /etc/ssh/sshd_config
```

Common hardening settings include:

```text
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
MaxAuthTries 3
```

Depending on your environment, you may also restrict which users can log in.

For example:

```text
AllowUsers deploy
```

Be careful: if you have multiple legitimate administrators, include them appropriately.

---

# 12. Validate SSH Configuration

Before restarting:

```bash
sudo sshd -t
```

If there is no output, the syntax is generally valid.

This is a very important command.

Never change SSH configuration and immediately restart without checking it.

---

# 13. Reload SSH

If configuration is valid:

```bash
sudo systemctl reload ssh
```

or on systems using `sshd` as the service name:

```bash
sudo systemctl reload sshd
```

Then test your second connection.

---

# 14. Verify Effective Configuration

Run:

```bash
sudo sshd -T | grep -E \
'permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries'
```

You want to confirm the actual effective configuration, not just what you think you configured.

---

# 15. Step 7 — Firewall

First check:

```bash
sudo ufw status verbose
```

If using UFW, establish SSH access before enabling the firewall.

For example:

```bash
sudo ufw allow OpenSSH
```

Then:

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

Enable:

```bash
sudo ufw enable
```

Check:

```bash
sudo ufw status numbered
```

---

# 16. Default Deny

A common firewall model is:

```text
Incoming → DENY
Outgoing → ALLOW
```

Then explicitly allow required incoming traffic.

Conceptually:

```text
Internet
   │
   ├── 22  → SSH ✓
   ├── 80  → HTTP ✓
   ├── 443 → HTTPS ✓
   │
   ├── 27017 → MongoDB ✗
   ├── 3000  → Node.js ✗
   └── everything else ✗
```

This is a strong baseline for a simple single-server architecture.

# 18. Public vs Private Services

A useful model:

```text
PUBLIC
│
├── Nginx :443
└── SSH :22

PRIVATE
│
├── Node.js :3000
└── MongoDB :27017
```

The internet should interact with your application through Nginx, not directly with Node.js.

# 19. Step 9 — Remove Unnecessary Services

List running services:

```bash
systemctl --type=service --state=running
```

Then ask:

```text
Do I need this?
Who uses it?
Is it listening on a port?
Can it be disabled?
```

Disable only services you understand:

```bash
sudo systemctl disable --now SERVICE
```

Don't randomly disable services from a hardening tutorial.

# 21. Step 11 — Create the Application User

Create a dedicated user:

```bash
sudo useradd \
  --system \
  --create-home \
  --shell /usr/sbin/nologin \
  nodeapp
```

```bash

```

This user doesn't need an interactive shell.

---

# 22. Why `nologin`?

The Node.js application doesn't need:

```text
SSH login
Interactive shell
```

It only needs to run the application.

Therefore:

```text
nodeapp
   ↓
Node.js process
```

rather than:

```text
nodeapp
   ↓
SSH
   ↓
Shell
```

This reduces unnecessary access.

# 26. Protect `.env`

If your application uses:

```text
.env
```

protect it.

For example:

```bash
sudo chown nodeapp:nodeapp /opt/myapp/.env
sudo chmod 600 /opt/myapp/.env
```

Only the application user can read it.

But for larger production systems, a dedicated secrets manager is preferable.

---

# 27. Step 14 — Create systemd Service

Create:

```bash
sudo nano /etc/systemd/system/myapp.service
```

Example:

```ini
[Unit]
Description=MERN Backend
After=network.target

[Service]
Type=simple
User=nodeapp
Group=nodeapp

WorkingDirectory=/opt/myapp

Environment=NODE_ENV=production

ExecStart=/usr/bin/node /opt/myapp/server.js

Restart=on-failure
RestartSec=5

NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

This is a basic example.

---

# 28. Why `User=nodeapp`?

This is extremely important.

Without it:

```text
root
 ↓
Node.js
 ↓
Application compromise
 ↓
Potential root compromise
```

With:

```text
nodeapp
 ↓
Node.js
 ↓
Application compromise
 ↓
Limited privileges
```

That's defense in depth.

---

# 29. `NoNewPrivileges=true`

This systemd setting prevents the service from gaining additional privileges through certain mechanisms.

It's an example of systemd sandboxing.

Security isn't just:

```text
User=nodeapp
```

You can add additional restrictions when compatible with the application.

# 34. Reverse Proxy

Nginx receives:

```text
https://api.example.com
```

and forwards:

```text
http://127.0.0.1:3000
```

Architecture:

```text
Browser
   │
 HTTPS
   ▼
 Nginx
   │
 HTTP localhost
   ▼
 Node.js
```

Node.js doesn't need to be directly exposed to the internet.

---

# 35. Example Nginx Configuration

Conceptually:

```nginx
server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Then:

```bash
sudo nginx -t
```

and reload:

```bash
sudo systemctl reload nginx
```

# 39. MongoDB Authentication

Production databases should have appropriate authentication and authorization configured.

Conceptually:

```text
Node.js
   │
   │ credentials
   ▼
MongoDB
   │
   ▼
Authorized database/user
```

Your application shouldn't connect using an all-powerful database administrator account if a more restricted application user is sufficient.

---

# 40. Database Least Privilege

Instead of:

```text
Node.js
 ↓
MongoDB admin
```

prefer:

```text
Node.js
 ↓
Application DB user
 ↓
Only required database permissions
```

This follows the same principle as Linux users.

Then configure CORS accordingly.

# 65. What Happens During an Attack?

Let's see how all your controls work together.

Suppose an attacker tries SSH brute force.

```text
Attacker
   │
   ▼
Firewall
   │
   ▼
SSH
   │
   ▼
Authentication fails
   │
   ▼
Fail2ban detects pattern
   │
   ▼
IP temporarily blocked
   │
   ▼
Logs generated
   │
   ▼
Monitoring alert
```

Multiple layers worked together.

# 66. What If Node.js Is Compromised?

Suppose your Node.js application has a vulnerability.

Attacker gets code execution.

Because:

```text
Node.js
 ↓
nodeapp user
```

they don't automatically get root.

They may encounter:

```text
No sudo
Restricted filesystem
No interactive shell
Firewall
Private services
systemd restrictions
```

That's **defense in depth**.

---

# 69. Defense in Depth

This is one of the most important concepts from the entire module.

Imagine:

```text
Layer 1 → Firewall
Layer 2 → SSH keys
Layer 3 → Fail2ban
Layer 4 → Non-root application
Layer 5 → Private database
Layer 6 → systemd restrictions
Layer 7 → Monitoring
Layer 8 → Backups
```

If one layer fails:

```text
Layer 1 ❌
      ↓
Layer 2
      ↓
Layer 3
      ↓
Layer 4
      ↓
...
```

The attacker still has more barriers to overcome.

# 70. Production Hardening Script

At this stage, you can build a simple verification script:

```bash
#!/bin/bash

set -euo pipefail

echo "===== PRODUCTION SECURITY CHECK ====="

echo
echo "[1] SSH"
sudo sshd -T | grep -E \
'permitrootlogin|passwordauthentication|pubkeyauthentication'

echo
echo "[2] FIREWALL"
sudo ufw status

echo
echo "[3] PORTS"
sudo ss -lntup

echo
echo "[4] AUDITD"
sudo systemctl is-active auditd

echo
echo "[5] FAIL2BAN"
sudo systemctl is-active fail2ban

echo
echo "[6] NODE APP"
sudo systemctl is-active myapp

echo
echo "[7] NGINX"
sudo systemctl is-active nginx

echo
echo "[8] TIME"
timedatectl

echo
echo "[9] DISK"
df -h

echo
echo "===== CHECK COMPLETE ====="
```

This isn't a full security scanner, but it gives you a useful baseline.

# 75. Interview Questions

### Q1. How would you secure a Linux server before deploying a Node.js application?

A strong answer:

> I would first update the OS and remove unnecessary services, create dedicated users, configure SSH key-based access and disable root/password login where appropriate, enable a firewall with only required ports, run the Node.js application as a non-root user, keep MongoDB private, put Nginx in front with HTTPS, configure Fail2ban and auditing, protect secrets, enable logging and monitoring, automate backups, and test the recovery process.

That's a strong production-level answer.

---

### Q2. Why shouldn't Node.js run as root?

Because application vulnerabilities could become root-level compromise.

---

### Q3. Why put Nginx in front of Node.js?

It can provide:

```text
TLS termination
Reverse proxy
Security headers
Request handling
Static files
Rate limiting
Access control
```

depending on the architecture.

---

### Q4. Why keep MongoDB private?

It reduces attack surface and ensures database access goes through controlled application/network paths.

---

### Q5. What happens if an attacker compromises Node.js?

If properly hardened:

```text
Node.js compromised
       ↓
nodeapp user
       ↓
Limited privileges
       ↓
No root
       ↓
Private database
       ↓
Firewall
       ↓
Monitoring
```

The compromise is more contained.

---

### Q6. Why do you need backups if you have security controls?

Because prevention can fail.

Security needs:

```text
Prevent
Detect
Respond
Recover
```

---

### Q7. What is defense in depth?

Using multiple independent security layers so failure of one control doesn't compromise the entire system.
