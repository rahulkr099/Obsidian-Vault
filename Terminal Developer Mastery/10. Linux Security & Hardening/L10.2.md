# 1. The Linux Permission Model

Linux follows a simple idea:

```text
User → Group → Others
```

Every file and directory has:

1. An owner
    
2. A group
    
3. Permissions for the owner
    
4. Permissions for the group
    
5. Permissions for everyone else
    

Let's see an example.

```bash
ls -l
```

You might get:

```text
-rw-r--r-- 1 rahul developers 1250 Aug 15 server.js
```

Break it down:

```text
-rw-r--r--
│││ │││ │││
│││ │││ │└── Others
│││ │││ └─── Group
│││ └─────── Owner
│└────────── File type
└─────────── Permission information
```

More clearly:

```text
-rw-r--r--
 │  │  │
 │  │  └── Others: read
 │  └───── Group: read
 └──────── Owner: read + write
```

# 2. Linux Users

Every process in Linux runs under a user identity.

Check your current user:

```bash
whoami
```

Example:

```text
rahul
```

Get more information:

```bash
id
```

Example:

```text
uid=1000(rahul) gid=1000(rahul) groups=1000(rahul),27(sudo)
```

Here:

```text
uid=1000
```

is your **User ID**.

```text
gid=1000
```

is your primary **Group ID**.

```text
groups=...
```

shows groups your user belongs to.

---

# 3. UID — User ID

Linux doesn't internally identify users only by their names.

It primarily uses numeric IDs.

For example:

```text
rahul → UID 1000
```

Root:

```text
root → UID 0
```

You can see users and their UIDs with:

```bash
getent passwd
```

You might see:

```text
root:x:0:0:root:/root:/bin/bash
rahul:x:1000:1000:Rahul:/home/rahul:/bin/bash
```

The important structure is:

```text
username : password-field : UID : GID : description : home : shell
```

---

# 4. Root User

Root has UID:

```text
0
```

Check:

```bash
id root
```

Output:

```text
uid=0(root) gid=0(root)
```

Root can generally:

- read protected files
    
- modify system configuration
    
- create/delete users
    
- install packages
    
- change ownership
    
- manage services
    
- access devices
    
- modify networking
    

That's why root access must be protected carefully.

---

# 5. System Users

Not every Linux user represents a human.

Linux creates service accounts for applications.

For example:

```text
www-data
```

is commonly used by web servers.

Other distributions/applications may have users such as:

```text
nginx
postgres
mysql
redis
```

The idea is:

```text
Nginx process
     ↓
www-data
     ↓
Limited permissions
```

instead of:

```text
Nginx process
     ↓
root
     ↓
Everything
```

This is **privilege separation**.

# 6. Creating a User

On Debian/Ubuntu/Linux Mint systems, you can use:

```bash
sudo adduser devuser
```

You'll be asked for:

```text
Password
Full Name
Other information
```

For server administration, another common command is:

```bash
sudo useradd -m -s /bin/bash devuser
```

Let's understand:

```text
-m
```

creates the home directory.

```text
-s /bin/bash
```

sets Bash as the login shell.

---

# 7. Switching Users

You can switch to another user with:

```bash
su - devuser
```

Or:

```bash
sudo -iu devuser
```

The second approach is usually preferable for administrators because it uses `sudo` and the system's authorization policy.

Return to your previous user:

```bash
exit
```

---

# 8. Deleting a User

You can remove a user with:

```bash
sudo userdel devuser
```

To also remove their home directory:

```bash
sudo userdel -r devuser
```

⚠️ Be careful with `-r`.

It deletes the user's home directory and its contents.

# 9. Groups

Groups make permission management much easier.

Imagine you have:

```text
rahul
amit
priya
```

All three need access to:

```text
/var/www/myapp
```

Instead of assigning permissions individually:

```text
rahul → access
amit  → access
priya → access
```

Create:

```text
developers
```

Then:

```text
developers
    │
    ├── rahul
    ├── amit
    └── priya
```

Now permissions can be assigned to the group.

---

# 10. Creating Groups

```bash
sudo groupadd developers
```

Check:

```bash
getent group developers
```

You may see:

```text
developers:x:1001:
```

---

# 11. Adding a User to a Group

```bash
sudo usermod -aG developers rahul
```

The important part is:

```text
-aG
```

Meaning:

```text
-a → append
-G → supplementary group
```

### Very important mistake

Don't accidentally do:

```bash
sudo usermod -G developers rahul
```

without `-a`.

That can replace the user's existing supplementary groups.

Prefer:

```bash
sudo usermod -aG developers rahul
```

---

# 12. Checking Group Membership

```bash
groups rahul
```

Or:

```bash
id rahul
```

After adding a user to a group, log out and log back in for the new group membership to appear in a normal login session.

You can also inspect the current shell's groups with:

```bash
id
```

# 13. File Ownership

Let's create a test file:

```bash
touch test.txt
```

Check:

```bash
ls -l test.txt
```

Example:

```text
-rw-r--r-- 1 rahul rahul 0 Aug 15 20:00 test.txt
```

Here:

```text
Owner → rahul
Group → rahul
```

---

# 14. Changing Ownership

Use:

```bash
chown
```

Example:

```bash
sudo chown devuser test.txt
```

Now:

```text
Owner → devuser
```

You can change both owner and group:

```bash
sudo chown devuser:developers test.txt
```

Result:

```text
Owner → devuser
Group → developers
```

---

# 15. Changing Group Ownership

Use:

```bash
chgrp
```

Example:

```bash
sudo chgrp developers test.txt
```

Now:

```text
Owner → rahul
Group → developers
```

---

# 16. File Permissions

Linux has three basic permissions:

```text
r → read
w → write
x → execute
```

Their numeric values are:

```text
r = 4
w = 2
x = 1
```

Therefore:

```text
rwx = 4 + 2 + 1 = 7
rw- = 4 + 2 = 6
r-x = 4 + 1 = 5
r-- = 4
-w- = 2
--x = 1
--- = 0
```

This is the foundation of numeric `chmod`.

---

# 17. Three Permission Categories

Suppose we have:

```text
-rwxr-xr--
```

Divide it:

```text
rwx | r-x | r--
 │     │     │
 │     │     └── Others
 │     └──────── Group
 └────────────── Owner
```

So:

```text
Owner  → rwx
Group  → r-x
Others → r--
```

Numerically:

```text
rwx = 7
r-x = 5
r-- = 4
```

Therefore:

```text
754
```

---

# 18. `chmod`

`chmod` means:

> Change mode.

Example:

```bash
chmod 644 test.txt
```

This means:

```text
Owner  → rw-
Group  → r--
Others → r--
```

So:

```text
644
```

is:

```text
6 = rw-
4 = r--
4 = r--
```

---

# 19. Common Permission Patterns

### 600

```bash
chmod 600 secret.txt
```

```text
Owner  → read/write
Group  → nothing
Others → nothing
```

Great for sensitive files.

For example:

```text
.env
private keys
credentials
```

---

### 644

```bash
chmod 644 file.txt
```

```text
Owner  → read/write
Group  → read
Others → read
```

Common for regular files.

---

### 700

```bash
chmod 700 script.sh
```

```text
Owner  → read/write/execute
Group  → nothing
Others → nothing
```

Useful for private scripts/directories.

---

### 755

```bash
chmod 755 script.sh
```

```text
Owner  → rwx
Group  → r-x
Others → r-x
```

Common for executable programs and directories that should be traversable/readable by others.

---

### 777 ⚠️

```bash
chmod 777 file
```

means:

```text
Owner  → rwx
Group  → rwx
Others → rwx
```

This is almost always a bad default for application files.

Avoid blindly doing:

```bash
chmod -R 777 .
```

This is one of the classic beginner mistakes.

---

# 20. Directory Permissions Are Slightly Different

This is important.

For a **directory**:

```text
r → list contents
w → create/delete/rename entries
x → enter/traverse directory
```

Consider:

```text
drwxr-x---
```

The `x` permission allows a user to enter/traverse the directory.

Without it, having `r` alone doesn't provide normal access to files inside.

---

# 21. Why `x` Matters for Directories

Suppose:

```text
/home/rahul/project
```

has:

```text
r--
```

for someone.

They might be able to see directory entries depending on the combination of permissions, but they cannot properly traverse/access the directory without `x`.

For a directory, think:

```text
r = see names
x = enter/access
w = modify entries
```

This distinction is frequently asked in interviews.

---

# 22. Symbolic `chmod`

You don't always have to use numbers.

For example:

```bash
chmod u+x script.sh
```

Means:

```text
u = user/owner
+x = add execute
```

Other symbols:

```text
u → user
g → group
o → others
a → all
```

Examples:

```bash
chmod g+w file.txt
```

Add group write permission.

```bash
chmod o-r file.txt
```

Remove read permission from others.

```bash
chmod a+x script.sh
```

Add execute permission for everyone.

---

# 23. `sudo`

`sudo` allows an authorized user to execute commands with elevated privileges.

Example:

```bash
sudo systemctl restart nginx
```

Instead of logging in directly as root.

This is safer because:

- commands can be audited
    
- permissions can be controlled
    
- users don't need the root password
    
- administrative privileges can be limited
    

---

# 24. `sudo -i` vs `sudo command`

Normal:

```bash
sudo apt update
```

Only that command gets elevated privileges.

You can also get a root shell:

```bash
sudo -i
```

You'll see something like:

```text
root@server:~#
```

Be careful.

Now every command you execute is running as root.

Exit:

```bash
exit
```

### Best practice

Prefer:

```bash
sudo specific-command
```

instead of staying inside a root shell unnecessarily.

---

# 25. `visudo`

The sudo configuration is controlled through:

```text
/etc/sudoers
```

Don't edit it casually with:

```bash
sudo nano /etc/sudoers
```

Instead use:

```bash
sudo visudo
```

Why?

`visudo` validates the syntax before saving.

A syntax error in sudoers can potentially prevent administrative access.

---

# 26. Privilege Separation

This concept will appear repeatedly throughout Module 10.

Imagine:

```text
                    SERVER
                       │
       ┌───────────────┼───────────────┐
       │               │               │
     nginx            node           mongodb
       │               │               │
   www-data         nodeuser       mongodb-user
```

Each service gets its own identity.

If Node.js gets compromised:

```text
Attacker
   ↓
Node.js
   ↓
nodeuser
```

not:

```text
Attacker
   ↓
Node.js
   ↓
root
```

That's a huge security improvement.

---

# 27. Example: Secure Node.js Deployment

Suppose your application lives at:

```text
/var/www/myapp
```

You could have:

```text
/var/www/myapp
       │
       ├── server.js
       ├── package.json
       ├── src/
       └── .env
```

A production setup should avoid making everything writable by everyone.

For example:

```text
Application owner → deploy
Application group → app
Node process      → appuser
```

Sensitive files like:

```text
.env
```

should have much tighter permissions.

Example:

```bash
chmod 600 .env
```

And ownership should be deliberately chosen.

The exact ownership model depends on your deployment architecture; don't blindly copy permissions from another server.

# 28. Special Permission Bits

Linux has three important special permission mechanisms:

```text
SUID
SGID
Sticky Bit
```

You'll study these more deeply in Lesson 10.6.

For now, remember:

```text
SUID      → execute with file owner's privileges
SGID      → special group behavior
Sticky    → controls deletion in shared directories
```

A famous example is:

```bash
ls -l /usr/bin/passwd
```

You may see:

```text
-rwsr-xr-x
```

Notice:

```text
s
```

instead of:

```text
x
```

That indicates SUID.

⚠️ SUID binaries deserve security attention because vulnerabilities in privileged executables can potentially lead to privilege escalation.

# 29. Security Mistakes to Avoid

### ❌ Running application as root

```bash
sudo node server.js
```

### ❌ Giving everything 777

```bash
chmod -R 777 /var/www
```

### ❌ Making `.env` world-readable

```text
-rw-r--r-- .env
```

### ❌ Giving unnecessary sudo privileges

Don't give users unrestricted administrative access when they only need one specific task.

### ❌ Sharing one account

Avoid:

```text
admin
admin
admin
```

for everyone.

Prefer individual accounts:

```text
rahul
amit
deploy
```

Then permissions can be tracked properly.

# 31. A Very Useful Command

Whenever you're confused about a file's permissions:

```bash
namei -l /path/to/file
```

For example:

```bash
namei -l ~/linux-security-lab/private.txt
```

This is extremely useful because it shows permissions for each directory in the path.

Think:

```text
/
└── home
    └── rahul
        └── linux-security-lab
            └── private.txt
```

A permission problem can exist anywhere in that path.

# 33. Interview Questions

### Q1. What are the three basic Linux permission categories?

```text
Owner
Group
Others
```

---

### Q2. What do `r`, `w`, and `x` mean?

For files:

```text
r → read
w → write
x → execute
```

For directories:

```text
r → list
w → modify directory entries
x → traverse/access
```

---

### Q3. What does `chmod 600 file` mean?

```text
Owner  → read/write
Group  → no access
Others → no access
```

---

### Q4. What does `chmod 755 file` mean?

```text
Owner  → rwx
Group  → r-x
Others → r-x
```

---

### Q5. Why is `chmod 777` dangerous?

Because it gives **read, write, and execute permissions to everyone**, potentially allowing unauthorized users or compromised processes to modify or execute files.

---

### Q6. Why use groups?

Groups allow permissions to be assigned to multiple users efficiently without managing each user individually.

---

### Q7. Why shouldn't applications run as root?

Because a compromise of the application could become a compromise of the entire server.

---

### Q8. Why use `visudo`?

Because it safely edits the sudoers configuration while checking its syntax.

# 34. The Mental Model to Remember

When you see:

```text
-rwxr-x---
```

immediately think:

```text
             FILE
              │
       ┌──────┼──────┐
       │      │      │
     Owner   Group  Others
       │      │      │
      rwx    r-x     ---
       │      │      │
      7       5       0
```

Therefore:

```text
750
```

And when you see:

```text
drwxr-x---
```

remember that it's a **directory**, so `x` means:

> "You can traverse/enter this directory."
