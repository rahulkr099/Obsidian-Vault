# Lesson 10.20 — Final Security Project ⭐⭐⭐⭐⭐

**Module 10 — Linux Security & Hardening**

Congratulations — this is the **final lesson of Module 10**. 🎯

You've learned Linux security piece by piece. Now we're going to combine everything into one practical project that resembles what you'd do when preparing a Linux server for a real MERN application.

> **Project Goal:** Build, harden, audit, monitor, back up, and test the recovery of a production-style Linux server.

---

# 9. Phase 5 — Harden SSH

Edit:

```bash
sudo nano /etc/ssh/sshd_config
```

Review settings such as:

```text
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
MaxAuthTries 3
```

You can also restrict allowed users:

```text
AllowUsers deploy
```

if that matches your environment.

# 12. Phase 6 — Firewall


```bash

```

```bash

```

```bash

```

Then:

```bash
sudo ufw enable
```

Check:

```bash
sudo ufw status numbered
```

# 13. Firewall Requirement

```text

80    → HTTP
443   → HTTPS
```

```text

27017 → MongoDB
6379  → Redis
```

unless those services genuinely need external access.

# 19. Security Test #3 — Environment File

Try reading it as an unrelated user.

For example:


```bash
sudo -u nodeapp cat /opt/myapp/.env
```

Only do this in a safe lab because it prints secrets.

# 33. Create a Sensitive File Audit

You can create an audit rule for a sensitive configuration file.

For example:

```text
/etc/ssh/sshd_config
```

A typical rule concept is:

```bash
sudo auditctl -w /etc/ssh/sshd_config -p wa -k ssh_config
```

Then inspect:

```bash
sudo ausearch -k ssh_config
```

For persistent rules, configure them through your distribution's audit rules configuration rather than relying only on a temporary `auditctl` command.

# 51. RPO Test

Suppose:

```text
Last backup:
02:00

Server destroyed:
15:00
```

Your maximum theoretical data-loss window is around:

```text
13 hours
```

Your actual RPO depends on what data is backed up and how often.

If you need:

```text
RPO = 1 hour
```

then daily backups aren't enough.

You need a more frequent backup strategy.

---

# 52. RTO Test

Suppose:

```text
Server destroyed
10:00

Application restored
12:30
```

Your recovery time:

```text
2 hours 30 minutes
```

Your measured RTO is therefore approximately:

```text
2h 30m
```

This is much better than simply claiming:

# 54. Risk Classification

When you find problems, classify them.

### Critical 🔴

Could cause severe compromise.

Example:

```text
Public database with unrestricted access
```

### High 🟠

Significant security issue.

Example:

```text
Root SSH login enabled
```

### Medium 🟡

Should be fixed but has limited immediate impact.

Example:

```text
Unnecessary service running internally
```

### Low 🔵

Improvement opportunity.

Example:

```text
Security documentation incomplete
```

# 56. Add One Important Section: Findings

Never make every report say:

```text
Everything is secure.
```

Security is rarely absolute.

Instead:

```text
FINDINGS

[MEDIUM]
Certificate renewal has not been tested.

[LOW]
Security audit logs are retained locally only.

[LOW]
Restore procedure isn't documented.

RECOMMENDATIONS

1. Test certificate renewal.
2. Send logs to centralized storage.
3. Document DR procedure.
```

This demonstrates real security thinking.

# 62. Interview-Level Answer

If an interviewer asks:

> **"How would you secure a Linux server hosting a Node.js application?"**

You can now answer:

> "First I'd inventory the server and apply security updates. I'd create dedicated users and use least privilege. For SSH, I'd use key-based authentication, disable root login and password authentication where appropriate, and restrict administrative access. I'd configure a firewall allowing only required ports such as SSH and HTTPS. I'd run Node.js as a non-root service account and keep internal services like MongoDB private. I'd put Nginx in front of Node.js for TLS and reverse proxying. I'd add Fail2ban, auditd, secure logging, monitoring, and automated security checks. I'd protect secrets, scan dependencies, and configure encrypted off-site backups. Finally, I'd test the security controls, backup restoration, and disaster-recovery procedure instead of assuming the configuration is correct."

That's a **very solid junior-to-mid-level backend interview answer**.
