# Lesson 10.3 — Authentication & Authorization 🔐

**Module 10 — Linux Security & Hardening**  
**Part 1: Linux Security Fundamentals**

This lesson covers one of the most important security concepts you'll use as a backend developer:

> **Authentication answers: "Who are you?"**  
> **Authorization answers: "What are you allowed to do?"**

Understanding this difference is essential for Linux, SSH, APIs, databases, and your MERN applications.

---

# 1. Authentication vs Authorization

Let's say you SSH into a Linux server.

```text
You
 │
 │ username + SSH key
 ▼
Linux Server
 │
 ├── Authentication
 │       ↓
 │   "Is this really Rahul?"
 │
 └── Authorization
         ↓
     "What can Rahul do?"
```

### Authentication

Verifies identity.

Examples:

```text
Password
SSH key
MFA
Biometrics
Certificate
```

### Authorization

Determines permissions.

Examples:

```text
Can read /var/log/app.log
Can restart nginx
Can access /var/www
Can use sudo
Can modify database
```

---

# 2. Simple Example

Imagine your Linux server has:

```text
rahul
deploy
backup
```

Rahul might have:

```text
sudo access
```

The deployment user might have:

```text
application directory access
```

The backup user might have:

```text
read access to backup directories
```

They all authenticate themselves, but their authorization differs.

```text
              Authentication
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
     rahul         deploy        backup
       │             │             │
       ▼             ▼             ▼
    sudo          app files      backups
```

You already work with concepts such as:

```text
JWT
```

```text

  ↓

```

# 4. Password Authentication

The traditional way to authenticate into Linux is:

```text
username + password
```

For example:

```text
ssh rahul@server
```

Then:

```text
password:
```

If the password is correct, authentication succeeds.

But password-based SSH has several weaknesses.

---

# 5. Why Passwords Are Risky

Imagine an SSH server exposed to the internet:

```text
Internet
   │
   ▼
Port 22
   │
   ▼
SSH
   │
   ├── root
   ├── admin
   ├── ubuntu
   ├── user
   └── ...
```

An attacker can repeatedly attempt passwords.

```text
Attempt 1
Attempt 2
Attempt 3
...
Attempt 10000
```

This is called a **brute-force attack**.

Even strong passwords can be targeted through:

- credential stuffing
    
- password leaks
    
- phishing
    
- automated guessing
    

That's one reason production SSH commonly uses **SSH keys**.

---

# 6. SSH Key Authentication ⭐

SSH keys use asymmetric cryptography.

You have two keys:

```text
Private Key 🔑
Public Key 🔓
```

Think of it like:

```text
Private key
    ↓
You keep it secret

Public key
    ↓
Server stores it
```

For example:

```text
Your computer
~/.ssh/id_ed25519
       │
       │ private
       ▼
   SSH client
       │
       │ cryptographic proof
       ▼
    Server
~/.ssh/authorized_keys
       │
       └── public key
```

The private key should **never be uploaded to the server**.

---

# 7. Creating an SSH Key

On your Linux machine:

```bash
ssh-keygen -t ed25519
```

You'll normally see something like:

```text
Enter file in which to save the key:
```

Press Enter to use the default location.

You'll then be asked for a passphrase.

### Use a passphrase.

Don't leave important private keys unprotected if you can avoid it.

You will get:

```text
~/.ssh/id_ed25519
~/.ssh/id_ed25519.pub
```

The difference:

```text
id_ed25519
    ↓
PRIVATE KEY

id_ed25519.pub
    ↓
PUBLIC KEY
```

---

# 8. Never Share Your Private Key

This is extremely important.

### Safe to share:

```text
id_ed25519.pub
```

### Never share:

```text
id_ed25519
```

Also never put the private key into:

```text
GitHub
GitLab
.env
Discord
WhatsApp
public documentation
```

Treat the private key like a password—but ideally even more carefully.

---

# 9. Copying Your Public Key to a Server

A common command is:

```bash
ssh-copy-id user@server
```

For example:

```bash
ssh-copy-id rahul@192.168.1.50
```

This adds your public key to:

```text
~/.ssh/authorized_keys
```

on the server.

Then you can connect:

```bash
ssh rahul@192.168.1.50
```

---

# 10. What Is `authorized_keys`?

On the server:

```text
~/.ssh/authorized_keys
```

contains public keys that are allowed to authenticate as that user.

Example:

```text
/home/rahul/.ssh/authorized_keys
```

Conceptually:

```text
Client
 │
 │ Private key
 ▼
SSH Server
 │
 └── authorized_keys
       │
       ├── Public Key A
       ├── Public Key B
       └── Public Key C
```

If your public key isn't authorized, authentication fails.

---

# 11. How SSH Key Authentication Works

A simplified version:

```text
Client                           Server
  │                                │
  │──── SSH connection ───────────►│
  │                                │
  │◄── Authentication challenge ───│
  │                                │
  │──── Cryptographic proof ──────►│
  │                                │
  │                    Verify using public key
  │                                │
  │◄──────── Authentication OK ────│
```

Your private key doesn't need to be sent to the server.

That's one of the major benefits.

---

# 12. Password + SSH Key

SSH keys can also be protected with a passphrase.

Think:

```text
SSH Private Key
      │
      ▼
 Passphrase
      │
      ▼
Private key unlocked
      │
      ▼
SSH authentication
```

So even if someone steals your private key file, the passphrase provides another layer of protection.

---

# 13. SSH Agent

Typing your SSH key passphrase every time can be annoying.

An SSH agent can temporarily hold the unlocked key.

Start the agent:

```bash
eval "$(ssh-agent -s)"
```

Add your key:

```bash
ssh-add ~/.ssh/id_ed25519
```

Check:

```bash
ssh-add -l
```

Now SSH can use the loaded key without repeatedly asking for its passphrase during that agent session.

---

# 14. File Permissions for SSH Keys

Your private key should be protected.

Check:

```bash
ls -la ~/.ssh
```

You may see:

```text
-rw------- id_ed25519
-rw-r--r-- id_ed25519.pub
```

The important part is:

```text
id_ed25519
600
```

You can enforce it:

```bash
chmod 600 ~/.ssh/id_ed25519
```

For the `.ssh` directory:

```bash
chmod 700 ~/.ssh
```

And commonly:

```bash
chmod 600 ~/.ssh/authorized_keys
```

# 15. PAM — Pluggable Authentication Modules

Now we move deeper into Linux authentication.

**PAM** stands for:

> Pluggable Authentication Modules

PAM provides a framework that allows Linux applications to use standardized authentication mechanisms.

Examples of applications that can use PAM:

```text
SSH
sudo
login
su
```

Conceptually:

```text
Application
     │
     ▼
    PAM
     │
 ┌───┼────┐
 ▼   ▼    ▼
Password MFA Account policy
```

---

# 16. Why PAM Exists

Without a common authentication framework, every application would need to implement its own authentication system.

PAM provides reusable authentication components.

For example:

```text
sshd
  │
  ▼
 PAM
  │
  ├── password checks
  ├── account restrictions
  ├── authentication modules
  └── session configuration
```

This makes authentication more modular.

---

# 17. PAM Configuration

On Debian/Ubuntu/Linux Mint systems, you'll commonly encounter:

```text
/etc/pam.d/
```

List it:

```bash
ls /etc/pam.d/
```

You may see files such as:

```text
common-auth
common-account
common-password
common-session
sudo
sshd
```

These configure authentication behavior for different services.

⚠️ Don't randomly modify PAM configuration.

A bad PAM configuration can potentially prevent users—including administrators—from logging in.

---

# 18. PAM's Four Main Categories

You will commonly see four types of PAM management:

```text
auth
account
password
session
```

### `auth`

Authentication.

```text
"Who are you?"
```

### `account`

Account restrictions.

```text
"Are you allowed to log in?"
```

### `password`

Password management.

```text
"Can the password be changed?"
```

### `session`

Actions around login/logout.

```text
"What should happen when the session starts/ends?"
```

---

# 19. Multi-Factor Authentication (MFA)

MFA means using multiple authentication factors.

The common categories are:

### Something you know

```text
Password
PIN
```

### Something you have

```text
Phone
Security key
Authenticator device
```

### Something you are

```text
Fingerprint
Face
Biometrics
```

A typical MFA flow:

```text
Password
   ↓
Correct
   ↓
Authenticator code
   ↓
Correct
   ↓
Login
```

Even if the password is stolen, the attacker may still need the second factor.

---

# 20. SSH + MFA

For high-security servers, you can combine:

```text
SSH key
+
MFA
```

Conceptually:

```text
SSH Key
   ↓
Authentication
   ↓
MFA
   ↓
Server access
```

For extremely sensitive infrastructure, hardware security keys can provide another strong option.

We'll discuss practical SSH hardening later.

# 21. Account Locking

Linux can restrict accounts after certain authentication failures.

For example:

```text
Failed attempt
     ↓
Failed attempt
     ↓
Failed attempt
     ↓
Account temporarily restricted
```

This helps reduce brute-force attacks.

Tools/configuration involved can include:

```text
PAM
faillock
```

Check whether your system has it:

```bash
man faillock
```

You can also inspect:

```bash
faillock --help
```

Don't modify authentication policies on your main system yet.

We'll handle the practical configuration later.

# 22. Password Policies

A production system should discourage weak passwords.

Policies can include:

```text
Minimum length
Password complexity
Password expiration
Password history
Failed-login restrictions
```

But there's an important modern security principle:

> **Password length is generally more useful than forcing users into strange character combinations.**

For example:

```text
correct-horse-battery-staple
```

can be easier to remember and potentially stronger than a short password such as:

```text
P@ss1!
```

---

# 23. Password Hashing

Linux doesn't normally store your actual password in plaintext.

Instead, authentication systems use password hashes.

Conceptually:

```text
Password
   │
   ▼
Password Hash
   │
   ▼
Stored securely
```

On traditional Linux systems, password-related account information can involve:

```text
/etc/passwd
/etc/shadow
```

---

# 24. `/etc/passwd`

View it:

```bash
cat /etc/passwd
```

You might see:

```text
root:x:0:0:root:/root:/bin/bash
rahul:x:1000:1000:Rahul:/home/rahul:/bin/bash
```

Remember:

```text
/etc/passwd
```

contains account information, but modern systems generally don't store actual password hashes there.

The `x` indicates that password information is stored elsewhere.

---

# 25. `/etc/shadow`

Password hash information is generally stored in:

```text
/etc/shadow
```

Try:

```bash
sudo cat /etc/shadow
```

You'll see sensitive-looking entries.

Example structure:

```text
username:$hash:...
```

### Important

Do **not** post your `/etc/shadow` contents online.

Don't paste it into:

```text
GitHub
Discord
ChatGPT
Stack Overflow
```

or anywhere public.

---

# 26. Why `/etc/shadow` Is Protected

Check:

```bash
ls -l /etc/shadow
```

Typically, access is heavily restricted.

Conceptually:

```text
/etc/passwd
    ↓
Generally readable

/etc/shadow
    ↓
Highly restricted
```

This follows the principle:

> Sensitive information should only be accessible to processes/users that need it.

# 27. Authentication vs Authorization in Your MERN App

Let's connect this directly to your backend work.

Suppose:

```text
POST /login
```

User submits:

```json
{
  "email": "rahul@example.com",
  "password": "..."
}
```

### Authentication

Your backend verifies:

```text
Does this user exist?
Is the password correct?
```

Then:

```text
Access Token
Refresh Token
```

may be issued.

### Authorization

Later:

```text
DELETE /admin/users/123
```

Your backend checks:

```text
Is user authenticated?
        ↓
Is user an admin?
        ↓
Allowed?
```

So:

```text
Authentication
      ↓
Who are you?

Authorization
      ↓
What can you do?
```

# 28. Linux Equivalent

Your Linux server follows the same basic model:

```text
SSH key/password
       ↓
Authentication
       ↓
Linux user
       ↓
Groups + permissions + sudo
       ↓
Authorization
```

That's why the concept is so important for you.

You're learning the same security model at **two different layers**:

```text
Application Layer
      ↓
JWT / Sessions / Roles

Operating System Layer
      ↓
Users / Groups / Permissions / sudo
```

# 29. Authentication Security Checklist

For production Linux servers:

```text
✓ Use SSH keys
✓ Protect private keys
✓ Use strong key/passphrase protection
✓ Disable unnecessary password authentication
✓ Disable root SSH login
✓ Use individual user accounts
✓ Use least privilege
✓ Restrict sudo access
✓ Consider MFA
✓ Monitor authentication logs
✓ Apply account lockout policies where appropriate
✓ Keep the OS updated
```

We'll configure many of these in later lessons.

# 31. Check SSH Configuration Safely

Don't edit anything yet.

You can inspect the effective SSH configuration with:

```bash
sudo sshd -T
```

If `sshd` is installed and running, this can show the effective configuration.

For example, you can search for authentication settings:

```bash
sudo sshd -T | grep -E 'passwordauthentication|pubkeyauthentication|permitrootlogin'
```

You might see:

```text
passwordauthentication yes
pubkeyauthentication yes
permitrootlogin prohibit-password
```

**Don't change these settings yet.**

We'll properly harden SSH in **Lesson 10.4**.

# 32. Important Security Principle

Never make authentication changes blindly on a remote production server.

Imagine:

```text
SSH connection
      ↓
Change sshd config
      ↓
Restart SSH
      ↓
Configuration mistake
      ↓
Current session closes
      ↓
Cannot log in
      ↓
Locked out of server
```

A professional approach is:

```text
Backup configuration
        ↓
Test configuration
        ↓
Keep existing session open
        ↓
Open second SSH session
        ↓
Test new authentication
        ↓
Only then close old session
```

This habit will save you from many painful server incidents.

# 33. Interview Questions

### Q1. What is authentication?

Authentication verifies the identity of a user or system.

---

### Q2. What is authorization?

Authorization determines what an authenticated identity is allowed to access or perform.

---

### Q3. Authentication vs authorization?

```text
Authentication → Who are you?
Authorization   → What can you do?
```

---

### Q4. Why are SSH keys better than passwords?

SSH keys provide strong cryptographic authentication and are much harder to brute-force than passwords when properly generated and protected.

---

### Q5. What is PAM?

PAM, or Pluggable Authentication Modules, is a Linux framework that provides a modular way for applications and services to perform authentication, account management, password management, and session management.

---

### Q6. What is `/etc/shadow`?

It is a protected system file containing password-related account information, including password hashes on traditional Linux systems.

---

### Q7. Should you share your SSH private key?

**Absolutely not.**

The private key must remain secret.

---

### Q8. What is MFA?

Multi-factor authentication requires two or more different authentication factors, such as a password plus an authenticator code or hardware security key.
