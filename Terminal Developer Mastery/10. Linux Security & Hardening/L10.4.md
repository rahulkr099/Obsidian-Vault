# Lesson 10.4 — SSH Hardening 🔐

**Module 10 — Linux Security & Hardening**  
**Part 2: Securing SSH**

SSH is one of the most important services on a Linux server.

If you deploy your MERN backend on a VPS, cloud VM, or dedicated server, SSH may be the primary way you administer it.

So we want this:

```text
Internet
   │
   ▼
SSH
   │
   ├── Strong authentication
   ├── Limited users
   ├── No root login
   ├── No password login
   ├── Connection limits
   └── Proper logging
```

The goal isn't to make SSH "invisible." The goal is to make unauthorized access **much harder and easier to detect**.

---

# 1. What Is SSH?

SSH stands for:

> **Secure Shell**

It provides an encrypted connection between a client and a server.

```text
Your Laptop
    │
    │ encrypted SSH connection
    ▼
Linux Server
    │
    ▼
Remote Shell
```

Example:

```bash
ssh rahul@your-server-ip
```

After authentication, you get a shell on the remote machine.

---

# 2. Why SSH Needs Hardening

Imagine your server has a public IP:

```text
Internet
   │
   ▼
203.x.x.x
   │
   ▼
Port 22
   │
   ▼
sshd
```

Automated scanners constantly search internet-facing systems.

They may try:

```text
root
admin
ubuntu
test
user
```

with common or leaked passwords.

Therefore:

```text
Public SSH
+
Weak authentication
+
Root access
=
High risk
```

A better setup is:

```text
Public SSH
+
SSH keys
+
No root login
+
Limited users
+
Firewall
+
Fail2ban
=
Much stronger security
```

---

# 3. SSH Architecture

There are two important components:

```text
SSH Client
     │
     │
     ▼
SSH Server
```

The server daemon is:

```text
sshd
```

On most modern Linux distributions, its configuration is commonly found at:

```text
/etc/ssh/sshd_config
```

Check:

```bash
ls -l /etc/ssh/
```

You may see:

```text
ssh_config
sshd_config
sshd_config.d/
```

---

# 4. `ssh_config` vs `sshd_config`

This distinction is important.

### `ssh_config`

Controls the **client**.

```text
Your computer
    │
    └── ssh client configuration
```

### `sshd_config`

Controls the **server**.

```text
Linux server
    │
    └── sshd server configuration
```

Remember:

```text
ssh       → client
sshd      → server
```

---

# 5. Before Changing SSH Configuration ⚠️

This is one of the most important rules of the entire lesson.

If you're connected to a remote server:

> **Never change SSH configuration without keeping a working session open.**

Imagine:

```text
Terminal 1
SSH ───────────────► Server
```

Now you modify SSH.

```text
Change config
     ↓
Restart SSH
     ↓
Configuration mistake
```

If your current session closes:

```text
You
 │
 X
 │
Server
```

You may be locked out.

### Safe workflow

```text
SSH Session #1
       │
       ├── Keep open
       │
       ▼
Change configuration
       │
       ▼
Validate configuration
       │
       ▼
Open SSH Session #2
       │
       ▼
Test login
       │
       ▼
Only then close Session #1
```

This is a professional habit.

---

# 6. Back Up SSH Configuration

Before modifying anything:

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.backup
```

Verify:

```bash
ls -l /etc/ssh/sshd_config*
```

Now you have:

```text
sshd_config
sshd_config.backup
```

---

# 7. Check Current SSH Status

Check the SSH service:

```bash
sudo systemctl status ssh
```

On some systems the service may be named:

```text
sshd
```

You can check:

```bash
systemctl status sshd
```

If one doesn't exist, don't worry—the exact service name can vary by distribution.

---

# 8. Inspect the Effective Configuration

Instead of guessing what SSH is actually using, use:

```bash
sudo sshd -T
```

This is extremely useful.

For example:

```bash
sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication|pubkeyauthentication'
```

You may get:

```text
permitrootlogin prohibit-password
passwordauthentication yes
pubkeyauthentication yes
```

The important thing is:

> `sshd -T` shows the effective configuration after configuration files and defaults are processed.

---

# 9. SSH Keys Should Be Your Default

For production servers, prefer:

```text
SSH key
```

over:

```text
Password
```

The basic setup:

```text
Your laptop
 ~/.ssh/id_ed25519
       │
       │ private key
       ▼
SSH server
 ~/.ssh/authorized_keys
       │
       └── public key
```

The private key stays on your machine.

---

# 10. Disable Root Login

One of the most important SSH hardening settings is:

```text
PermitRootLogin
```

Check your current value:

```bash
sudo sshd -T | grep permitrootlogin
```

A hardened configuration commonly uses:

```text
PermitRootLogin no
```

This means:

```text
ssh root@server
       ↓
     DENIED
```

Instead:

```text
ssh rahul@server
       ↓
     Login
       ↓
sudo command
```

This gives you a named account and controlled privilege escalation.

---

# 11. Why Disable Root SSH Login?

Suppose an attacker discovers:

```text
root@your-server
```

Now they only need to defeat authentication for the most privileged account.

Compare:

### Less secure

```text
Internet
   ↓
SSH
   ↓
root
   ↓
Full system access
```

### Better

```text
Internet
   ↓
SSH
   ↓
rahul
   ↓
Limited privileges
   ↓
sudo when required
```

Even if the account is compromised, the blast radius can be smaller.

---

# 12. Disable Password Authentication

Once SSH key authentication has been tested and confirmed, a production server can disable password authentication:

```text
PasswordAuthentication no
```

Then:

```text
ssh user@server
       │
       ├── Password ❌
       │
       └── SSH key ✅
```

This dramatically reduces password brute-force attacks.

---

# 13. ⚠️ Never Disable Password Authentication Too Early

This mistake can lock you out.

Bad workflow:

```text
Disable passwords
      ↓
Try SSH key
      ↓
SSH key doesn't work
      ↓
LOCKED OUT
```

Correct workflow:

```text
Create SSH key
      ↓
Install public key
      ↓
Test SSH key
      ↓
Open second terminal
      ↓
Confirm key login works
      ↓
Disable passwords
      ↓
Test again
```

Always test first.

---

# 14. Public Key Authentication

Check:

```bash
sudo sshd -T | grep pubkeyauthentication
```

You generally want:

```text
pubkeyauthentication yes
```

This enables public-key authentication.

---

# 15. Restrict SSH Users

Suppose your server has:

```text
rahul
amit
backup
test
guest
```

But only:

```text
rahul
```

should SSH into the server.

You can use:

```text
AllowUsers rahul
```

Then:

```text
rahul → SSH allowed
amit  → SSH denied
test  → SSH denied
guest → SSH denied
```

This reduces the SSH attack surface.

---

# 16. Restrict by Group

Another approach is:

```text
AllowGroups sshusers
```

Then:

```text
sshusers
   │
   ├── rahul
   └── devadmin
```

Only members of that group can authenticate through SSH.

This is useful on servers with multiple administrators.

---

# 17. SSH Port

The default SSH port is:

```text
22
```

You might see:

```text
Port 22
```

Some administrators change it:

```text
Port 2222
```

Why?

It can reduce noise from automated scanners that blindly target port 22.

But there is an important point:

> **Changing the SSH port is not a strong security control by itself.**

This is called **security through obscurity**.

A scanner can discover:

```text
2222
```

just as easily with proper port scanning.

So:

```text
Change port
      ≠
Real security
```

Your important controls are:

```text
SSH keys
+
No root login
+
Firewall
+
Limited users
+
Fail2ban
+
Updates
```

Changing the port can be an additional measure, but shouldn't be your main defense.

---

# 18. Firewall + SSH

Suppose your server exposes:

```text
22
80
443
3000
27017
```

You probably don't want all of these publicly accessible.

A typical production architecture is:

```text
Internet
   │
   ├── 80  → Nginx
   ├── 443 → Nginx
   │
   └── SSH → restricted
                │
                ▼
              Server
                │
                ├── Node.js → private
                └── MongoDB → private
```

Your Node.js server doesn't need to be directly exposed to the internet if Nginx is acting as the reverse proxy.

We'll explore firewall configuration in **Lesson 10.8**.

---

# 19. Connection Limits

SSH can be configured to control connection behavior.

Examples include:

```text
MaxAuthTries
MaxSessions
MaxStartups
```

Check:

```bash
sudo sshd -T | grep -E 'maxauthtries|maxsessions|maxstartups'
```

---

# 20. `MaxAuthTries`

This controls how many authentication attempts are permitted per connection.

For example:

```text
MaxAuthTries 3
```

Conceptually:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
        ↓
Connection rejected
```

This can help reduce brute-force attempts.

But don't make settings unnecessarily restrictive without understanding your environment.

---

# 21. `MaxSessions`

This controls the number of open shell/login sessions allowed per network connection.

Example:

```text
MaxSessions 10
```

This is useful for controlling resource usage.

---

# 22. `MaxStartups`

This controls unauthenticated connection handling.

Why does this matter?

Imagine:

```text
Attacker
  │
  ├── SSH connection
  ├── SSH connection
  ├── SSH connection
  ├── SSH connection
  └── thousands...
```

SSH has mechanisms for limiting how many unauthenticated connections can be active.

Check:

```bash
sudo sshd -T | grep maxstartups
```

---

# 23. Idle Sessions

Long-running unused SSH sessions can be undesirable.

SSH provides settings such as:

```text
ClientAliveInterval
ClientAliveCountMax
```

For example, conceptually:

```text
ClientAliveInterval
        ↓
Server checks client periodically
        ↓
Client doesn't respond
        ↓
Count increases
        ↓
Connection eventually closed
```

These settings should be chosen carefully because aggressive timeouts can annoy legitimate administrators.

---

# 24. SSH Configuration Includes

A hardened SSH configuration may contain settings like:

```text
Port 22
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
AllowUsers rahul
MaxAuthTries 3
```

But **don't blindly paste this into your configuration**.

Different distributions and environments have different requirements.

First inspect:

```bash
sudo sshd -T
```

Then make one change at a time.

---

# 25. Configuration Validation ⭐

This is one of the most important commands:

```bash
sudo sshd -t
```

If configuration is valid:

You may get no output.

If there's a syntax problem, you'll get an error.

Think:

```text
Edit config
     ↓
sshd -t
     ↓
Valid?
 ┌───┴────┐
No       Yes
 │         │
Fix      Continue
```

**Never restart SSH blindly after modifying configuration.**

---

# 26. Reload vs Restart

You may encounter:

```bash
sudo systemctl reload ssh
```

and:

```bash
sudo systemctl restart ssh
```

### Reload

Asks the service to reload its configuration.

Usually less disruptive.

### Restart

Stops and starts the service.

Potentially more disruptive.

For configuration changes, a reload can often be preferable when supported.

But always validate first:

```bash
sudo sshd -t
```

---

# 27. Check SSH Logs

Security requires visibility.

On systemd-based Linux:

```bash
sudo journalctl -u ssh
```

Follow logs live:

```bash
sudo journalctl -u ssh -f
```

On some distributions, authentication messages may also appear in:

```text
/var/log/auth.log
```

For example:

```bash
sudo tail -f /var/log/auth.log
```

These logs can help you detect:

```text
Failed password
Invalid user
Accepted publickey
Connection attempts
```

---

# 28. Finding Failed SSH Attempts

You can search logs:

```bash
sudo journalctl -u ssh | grep -i "failed"
```

Or:

```bash
sudo grep -i "failed" /var/log/auth.log
```

You might discover entries like:

```text
Failed password for invalid user admin
Failed password for root
Failed password for test
```

On an internet-facing server, seeing automated attempts is not unusual.

The important thing is ensuring those attempts **cannot successfully authenticate**.

# 29. SSH Security Layers

A strong SSH setup looks like:

```text
                    INTERNET
                       │
                       ▼
                   FIREWALL
                       │
                       ▼
                     SSH
                       │
            ┌──────────┴──────────┐
            │                     │
        Allowed user          Other users
            │                     │
            ▼                     X
      SSH key required
            │
            ▼
      Root login disabled
            │
            ▼
      Password login disabled
            │
            ▼
       Normal user
            │
            ▼

```

And then:

```text
             Logs
               │
               ▼
            Monitoring
               │
               ▼
            fail2ban
```

# 30. SSH Key Restrictions

SSH also supports advanced restrictions in `authorized_keys`.

For example, a key can potentially be restricted using options such as:

```text
no-port-forwarding
no-agent-forwarding
no-X11-forwarding
restrict
```

This is particularly useful for deployment or automation keys.

For example:

```text
restrict ssh-ed25519 AAAA...
```

means the key has additional restrictions.

We'll explore this in **Lesson 10.5**.

# 31. SSH Agent Forwarding ⚠️

Agent forwarding allows a remote server to use your local SSH agent.

It can be useful:

```text
Laptop
  │
  ├── SSH → Server A
  │            │
  │            └── SSH → Server B
```

But it increases risk.

If Server A is compromised, an attacker may potentially abuse the forwarded agent while your session is active.

Therefore:

> Don't enable SSH agent forwarding unless you actually need it.

# 35. Common SSH Hardening Mistakes

## ❌ Mistake 1 — Disabling passwords before testing keys

```text
PasswordAuthentication no
```

before key authentication works.

Potential result:

```text
LOCKED OUT
```

---

## ❌ Mistake 2 — Closing your only SSH session

Always keep one working session open while testing.

---

## ❌ Mistake 3 — Changing the SSH port and assuming you're secure

```text
22 → 2222
```

doesn't solve authentication vulnerabilities.

---

## ❌ Mistake 4 — Using root for everything

Prefer:

```text
normal user
   ↓
sudo
```

---

## ❌ Mistake 5 — Sharing private keys

Never.

---

## ❌ Mistake 6 — Copy-pasting random hardening configs

A configuration from a blog may conflict with:

- your OS
    
- cloud provider
    
- SSH version
    
- networking
    
- automation
    
- deployment tools
    

Understand every setting before applying it.

# 36. Interview Questions

### Q1. What is SSH hardening?

SSH hardening is the process of reducing the risk of unauthorized SSH access through stronger authentication, restricted users, reduced privileges, connection controls, firewall rules, and proper logging.

---

### Q2. Why disable root login?

Because root has unrestricted privileges. Preventing direct root SSH login reduces the impact of stolen credentials or authentication attacks.

---

### Q3. Why use SSH keys instead of passwords?

SSH keys provide cryptographic authentication and are much more resistant to automated password guessing and brute-force attacks.

---

### Q4. Is changing SSH from port 22 to another port enough?

No.

It may reduce automated scanning noise, but it isn't a fundamental security control.

---

### Q5. What does `sshd -t` do?

It checks the SSH server configuration for syntax errors without starting or restarting the SSH service.

---

### Q6. What does `sshd -T` do?

It displays the effective SSH server configuration after configuration files and defaults are processed.

---

### Q7. What is `authorized_keys`?

It contains public keys that are authorized to authenticate as a particular Linux user.

---

### Q8. Why should you keep an existing SSH session open while changing SSH configuration?

Because a configuration mistake could prevent new connections. The existing session provides a way to recover and fix the configuration.

---

# 37. Your SSH Hardening Checklist

Eventually, your production server should move toward:

```text
[ ] Dedicated non-root admin user
[ ] SSH key authentication
[ ] Private key protected with passphrase
[ ] Public key stored in authorized_keys
[ ] Root SSH login disabled
[ ] Password SSH authentication disabled
[ ] SSH users restricted
[ ] Unnecessary forwarding disabled
[ ] Authentication attempts limited
[ ] Connection limits reviewed
[ ] Idle session behavior reviewed
[ ] Firewall configured
[ ] SSH logs monitored
[ ] fail2ban configured
[ ] OS and OpenSSH regularly updated
```

Don't try to implement the entire list today.

We'll build it piece by piece.

```text

                 FIREWALL
                     │
                     ▼
                    SSH
                     │
          ┌──────────┴──────────┐
          │                     │

          │                     │
```

The philosophy is:

> **Don't give an attacker one giant door to break through. Give them multiple security boundaries to overcome.**
