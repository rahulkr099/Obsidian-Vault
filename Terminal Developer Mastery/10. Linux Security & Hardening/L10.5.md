# 1. The SSH Key Architecture

Let's first understand the complete picture.

```text
                YOUR LAPTOP
                    │
              ~/.ssh/
                    │
          ┌─────────┴─────────┐
          │                   │
   Private Key 🔐       Public Key 🔓
          │                   │
          │                   │
          │             ┌─────▼─────┐
          │             │  Server   │
          │             │            │
          └────────────►│authorized_ │
             proof      │   keys     │
                        └────────────┘
```

The critical rule:

> **Private key stays private. Public key goes to the server.**

---

# 2. `authorized_keys`

On the server, each Linux user can have:

```text
~/.ssh/authorized_keys
```

Example:

```bash
cat ~/.ssh/authorized_keys
```

You may see something like:

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... rahul@laptop
```

Each line generally represents an authorized public key.

For example:

```text
Key 1 → Rahul laptop
Key 2 → Rahul desktop
Key 3 → Deployment system
```

This allows you to have multiple authorized devices.

---

# 3. Never Put Private Keys in `authorized_keys`

This is wrong:

```text
-----BEGIN OPENSSH PRIVATE KEY-----
...
```

`authorized_keys` should contain **public keys**.

Typically:

```text
ssh-ed25519 AAAA...
```

If you accidentally upload a private key to the server, treat it as compromised and rotate it.

---

# 4. Permissions for `.ssh`

SSH is strict about permissions in many configurations.

Recommended starting point:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
```

Think:

```text
~/.ssh
   ↓
700

authorized_keys
   ↓
600

private key
   ↓
600

public key
   ↓
644
```

Check:

```bash
ls -ld ~/.ssh
ls -l ~/.ssh
```

---

# 5. Ownership Matters Too

Permissions alone aren't enough.

Check:

```bash
ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
```

You generally want:

```text
Owner → correct user
Group → appropriate group
```

For example:

```text
rahul rahul ~/.ssh
rahul rahul ~/.ssh/authorized_keys
```

If someone else owns these files unexpectedly, investigate.

---

# 6. Multiple SSH Keys

You don't have to use one key for everything.

A better approach can be:

```text
Laptop
 │
 ├── Personal server key
 ├── GitHub key
 └── Work server key
```

For example:

```text
~/.ssh/
├── id_ed25519
├── id_ed25519.pub
├── github_ed25519
├── github_ed25519.pub
├── production_ed25519
└── production_ed25519.pub
```

This provides **key separation**.

If one key is compromised, you don't necessarily need to replace every other key.

---

# 7. SSH Config

Instead of typing:

```bash
ssh -i ~/.ssh/production_ed25519 rahul@203.0.113.10
```

every time, you can configure:

```text
~/.ssh/config
```

Example:

```text
Host production
    HostName 203.0.113.10
    User rahul
    IdentityFile ~/.ssh/production_ed25519
```

Then:

```bash
ssh production
```

Much cleaner.

---

# 8. Protect `~/.ssh/config`

Use:

```bash
chmod 600 ~/.ssh/config
```

And make sure you're the owner:

```bash
chown "$USER:$USER" ~/.ssh/config
```

---

# 9. SSH Key Naming

A useful naming strategy:

```text
github_ed25519
production_ed25519
staging_ed25519
personal_ed25519
```

This is better than creating dozens of keys with confusing names.

---

# 10. SSH Key Passphrases ⭐

When creating a key:

```bash
ssh-keygen -t ed25519
```

you'll be asked for:

```text
Enter passphrase:
```

Use a strong passphrase for important personal/admin keys.

Your security becomes:

```text
Private Key
     +
Passphrase
     ↓
Strong protection
```

Without a passphrase:

```text
Stolen private key
      ↓
Potential unauthorized access
```

With a passphrase:

```text
Stolen private key
      ↓
Passphrase required
      ↓
Additional barrier
```

---

# 11. SSH Agent

SSH agent lets you keep the private key unlocked in memory temporarily.

Start:

```bash
eval "$(ssh-agent -s)"
```

Add:

```bash
ssh-add ~/.ssh/production_ed25519
```

List keys:

```bash
ssh-add -l
```

Remove all keys from the agent:

```bash
ssh-add -D
```

Remove one key:

```bash
ssh-add -d ~/.ssh/production_ed25519
```

---

# 12. Agent Forwarding ⚠️

This is an important security concept.

Normally:

```text
Laptop
  │
  │ SSH
  ▼
Server A
```

With agent forwarding:

```text
Laptop
  │
  │ SSH + agent forwarding
  ▼
Server A
  │
  │ SSH
  ▼
Server B
```

Server A can use your forwarded agent to authenticate to Server B.

This can be convenient.

But there's a risk.

If Server A is compromised:

```text
Attacker
   ↓
Compromised Server A
   ↓
Forwarded SSH agent
   ↓
Potential abuse during active session
```

The private key itself isn't copied to Server A, but the forwarded agent can potentially be abused while available.

Therefore:

> **Avoid agent forwarding unless you actually need it.**

---

# 13. Disable Agent Forwarding by Default

In your SSH client configuration:

```text
Host *
    ForwardAgent no
```

Then enable it only for a specific trusted server when necessary:

```text
Host bastion
    HostName example.com
    User rahul
    ForwardAgent yes
```

This is much safer than globally enabling it.

---

# 14. SSH Key Restrictions

Here's where SSH becomes really interesting.

An entry in `authorized_keys` can contain restrictions.

Example:

```text
restrict ssh-ed25519 AAAAC3... deployment
```

The `restrict` option applies several restrictions to the key.

You can also use specific options such as:

```text
no-agent-forwarding
no-port-forwarding
no-X11-forwarding
```

This follows the principle:

> **A key should have only the capabilities it needs.**

---

# 15. Why Key Restrictions Matter

Suppose you create a deployment key:

```text
CI/CD
   ↓
SSH
   ↓
Production server
```

Does the CI/CD system need:

```text
SSH agent forwarding?
Port forwarding?
X11?
Interactive shell?
```

Probably not.

So don't give it unnecessary capabilities.

This reduces the blast radius if that key is compromised.

---

# 16. Deployment Keys

Imagine GitHub Actions needs to deploy your Node.js application:

```text
GitHub Actions
      │
      │ SSH
      ▼
Production Server
      │
      ▼
/var/www/myapp
```

You could create a dedicated deployment key:

```text
deploy_ed25519
```

Instead of using your personal SSH key.

This gives you:

```text
Personal Key
     │
     └── Admin access

Deployment Key
     │
     └── Deployment access
```

This is called **credential separation**.

---

# 17. Never Use Your Personal Key in CI/CD

Avoid:

```text
GitHub Actions
      ↓
Rahul's personal private key
```

Prefer:

```text
GitHub Actions
      ↓
Dedicated deployment key
      ↓
Restricted permissions
```

If the CI/CD credential is compromised, you can revoke it without replacing your personal administrative key.

---

# 18. Deployment User

A dedicated Linux user can also help:

```text
deploy
```

Then:

```text
CI/CD
   ↓
deploy user
   ↓
/var/www/myapp
```

Instead of:

```text
CI/CD
   ↓
root
```

This is a major improvement.

---

# 19. Don't Give Deployment Users Full `sudo`

A common mistake is:

```text
deploy
   ↓
sudo ALL=(ALL) NOPASSWD: ALL
```

Now the deployment account is effectively root.

That's dangerous.

Instead, give only the permissions required for deployment.

For example, perhaps the deployment process needs to:

```text
restart one service
update one directory
```

Its permissions should be designed around those exact requirements.

We'll revisit this when we discuss service security.

---

# 20. SSH Host Key vs User Key

This distinction is often confusing.

There are two different concepts.

### User authentication key

Proves:

> "I am Rahul."

Example:

```text
~/.ssh/id_ed25519
```

### Server host key

Proves:

> "This is the server you're connecting to."

Stored by the client in:

```text
~/.ssh/known_hosts
```

So:

```text
Client
 │
 ├── User key → proves your identity
 │
 └── known_hosts → remembers server identity
```

---

# 21. `known_hosts`

When you connect to a new server:

```bash
ssh rahul@server
```

SSH may show:

```text
The authenticity of host 'server' can't be established.
```

It asks whether you trust the server's host key.

After accepting it, the key is stored in:

```text
~/.ssh/known_hosts
```

---

# 22. Why `known_hosts` Matters

Suppose you connect to:

```text
production.example.com
```

Today:

```text
Server Host Key A
```

Later:

```text
Server Host Key B
```

SSH may warn:

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

This could mean:

- legitimate server rebuild
    
- host key rotation
    
- DNS/IP change
    
- man-in-the-middle attack
    

Never blindly ignore such warnings.

Investigate why the key changed.

---

# 23. `ssh-keygen -F`

To check a known host:

```bash
ssh-keygen -F example.com
```

To remove an old entry:

```bash
ssh-keygen -R example.com
```

But don't remove a changed key simply to make the warning disappear.

First determine why it changed.

---

# 24. SSH Auditing

Security isn't just preventing attacks.

You also need to know:

> **Who logged in?**

Useful commands:

```bash
last
```

```bash
lastlog
```

And:

```bash
sudo journalctl -u ssh
```

Depending on the system, authentication events may also be in:

```bash
sudo tail -f /var/log/auth.log
```

---

# 25. Successful vs Failed Logins

Search:

```bash
sudo journalctl -u ssh | grep -i "accepted"
```

You might see:

```text
Accepted publickey for rahul
```

Failed attempts:

```bash
sudo journalctl -u ssh | grep -i "failed"
```

You might see:

```text
Failed password for invalid user admin
```

This gives you visibility into authentication activity.

---

# 26. Investigating Suspicious SSH Activity

Imagine you see:

```text
Failed password for root
Failed password for admin
Failed password for test
Failed password for ubuntu
```

Repeatedly.

Your investigation could be:

```text
1. Which IP?
2. How many attempts?
3. When did they start?
4. Did any attempt succeed?
5. Which account was targeted?
6. Should the IP be blocked?
```

This is the beginning of incident response.

Later we'll automate much of this using **fail2ban**.

---

# 27. SSH Key Rotation

Keys shouldn't necessarily exist forever.

Imagine:

```text
2026 → Key created
2027 → Employee changes role
2028 → Device replaced
```

Old keys should be removed.

For example:

```text
authorized_keys

Key A → old laptop ❌
Key B → current laptop ✅
Key C → deployment system ✅
```

Remove:

```text
Key A
```

This is **credential lifecycle management**.

---

# 28. When Should You Rotate a Key?

Consider rotating/revoking keys when:

- private key may have been exposed
    
- laptop is lost
    
- employee leaves
    
- access requirements change
    
- old device is retired
    
- security policy requires periodic rotation
    

If a private key is definitely compromised:

> **Don't merely change the passphrase and assume everything is fine. Replace/revoke the key.**

---

# 29. SSH Key Inventory

For production environments, maintain a simple inventory:

```text
Key                  Owner       Purpose
------------------------------------------------
personal-ed25519     Rahul       Admin
production-ed25519   Rahul       Production
staging-ed25519      Rahul       Staging
deploy-ed25519       CI/CD       Deployment
```

This becomes very valuable as your infrastructure grows.

# 30. SSH Configuration Profiles

A clean `~/.ssh/config` might conceptually look like:

```text
Host production
    HostName production.example.com
    User rahul
    IdentityFile ~/.ssh/production_ed25519
    ForwardAgent no

Host staging
    HostName staging.example.com
    User rahul
    IdentityFile ~/.ssh/staging_ed25519
    ForwardAgent no

Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/github_ed25519
    ForwardAgent no
```

Now:

```bash
ssh production
```

or:

```bash
ssh staging
```

Much easier than remembering IP addresses and key paths.

# 31. GitHub + SSH

As a developer, you'll commonly use:

```text
git@github.com
```

Your local machine can use a dedicated key:

```text
github_ed25519
```

Then:

```bash
git clone git@github.com:username/repository.git
```

The benefit of separate keys is clear:

```text
GitHub key compromised
        ↓
Revoke GitHub key
        ↓
Production key unaffected
```

That's good security design.

---

# 32. Secure Private-Key Storage

Your private keys should not be casually stored everywhere.

Avoid:

```text
Downloads/
Desktop/
project/
Git repository/
public cloud folder/
```

Prefer:

```text
~/.ssh/
```

with restrictive permissions.

For especially sensitive environments, hardware-backed security keys can provide stronger protection than ordinary files.

---

# 33. SSH Private Key Backup

This is a difficult balance.

You don't want:

```text
No backup
```

because losing the key could mean losing access.

But you also don't want:

```text
Private key
   ↓
Google Drive
   ↓
Dropbox
   ↓
Email
```

A better approach is to maintain an encrypted, controlled backup according to your security needs.

For example, an encrypted backup protected by a strong passphrase can be considered.

Never upload unencrypted private keys to arbitrary cloud storage.

---

# 34. `ssh-agent` Security

Check currently loaded keys:

```bash
ssh-add -l
```

If you see keys you no longer need, remove them:

```bash
ssh-add -d ~/.ssh/old_key
```

Or clear the agent:

```bash
ssh-add -D
```

The principle is:

> Keep credentials loaded only when needed.

# 35. SSH Security for CI/CD

For your future Docker/CI/CD deployment pipeline:

```text
GitHub Actions
      │
      │ deployment key
      ▼
Production Server
      │
      ▼

      │
      ▼

```

Better than:



# 36. SSH Bastion / Jump Host

In larger infrastructure, you may not expose SSH directly to every server.

Instead:

```text
Laptop
   │
   ▼
Bastion / Jump Host
   │
   ├──► App Server
   ├──► Database Server
   └──► Internal Server
```

The public internet only reaches the bastion.

Internal servers can remain private.

This is called a **jump host** or **bastion host**.

You can later connect using SSH's `ProxyJump` functionality.

---

# 37. Example `ProxyJump`

Your SSH config might conceptually contain:

```text
Host app-server
    HostName 10.0.1.20
    User deploy
    ProxyJump bastion

Host bastion
    HostName bastion.example.com
    User rahul
```

Then:

```bash
ssh app-server
```

SSH automatically goes:

```text
Laptop
   ↓
Bastion
   ↓
App Server
```

The app server doesn't need a public SSH endpoint.

This is a more advanced production architecture.

# 38. Common Mistakes

### ❌ One key for everything

```text
GitHub
Production
Staging
Personal VPS
CI/CD
     ↓
One private key
```

Bad separation.

---

### ❌ Personal key in CI/CD

Use a dedicated deployment credential.

---

### ❌ Agent forwarding everywhere

Only enable it where genuinely required.

---

### ❌ Ignoring `known_hosts` warnings

Investigate changed host keys.

---

### ❌ Keeping old keys forever

Remove unused keys.

---

### ❌ Uploading private keys to Git

Never.

Check your repository:

```bash
find . -type f \( -name "id_*" -o -name "*.pem" \)
```

Be careful with the output; private-key filenames aren't always predictable.

# 39. Practical Lab 🧪

Let's inspect your local SSH environment without making risky changes.

### Step 1 — SSH directory

```bash
ls -la ~/.ssh
```

### Step 2 — Permissions

```bash
stat ~/.ssh
```

### Step 3 — SSH configuration

```bash

```

### Step 4 — Known hosts

```bash
ls -l ~/.ssh/known_hosts 2>/dev/null
```

```bash

```

If you see:

```text

```

that's okay; it simply means an agent isn't currently available.

### Step 6 — Public keys

```bash
find ~/.ssh -maxdepth 1 -type f -name "*.pub" -print
```

# 42. Interview Questions

### Q1. What is `authorized_keys`?

A file containing public keys authorized to authenticate as a specific Linux user.

---

### Q2. Why should different environments use different SSH keys?

To provide credential separation and limit the blast radius if one key is compromised.

---

### Q3. What is SSH agent forwarding?

It allows a remote server to use your local SSH agent for authentication to another server without copying your private key to the remote server.

It can be risky on untrusted machines.

---

### Q4. Why is agent forwarding dangerous?

A compromised remote host may potentially abuse the forwarded agent while the session is active.

---

### Q5. What is `known_hosts`?

A client-side file that stores identities/host keys of SSH servers you've connected to.

---

### Q6. What should you do when SSH reports that a host key changed?

Don't blindly delete the old key. Investigate whether the server was legitimately rebuilt, rekeyed, or changed before trusting the new key.

---

### Q7. Why use separate deployment keys?

They isolate CI/CD credentials from personal administrative credentials and reduce the blast radius of a compromise.

---

### Q8. What is a bastion host?

A controlled gateway server through which administrators connect to private/internal servers.

# 44. The Security Model to Remember

The biggest lesson from 10.5 is **credential separation**.

Instead of:

```text
                 ONE KEY
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
    GitHub      Production    Staging
```

prefer:

```text
             DIFFERENT KEYS
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
   GitHub      Production  Staging
      │            │          │
   Git key     Prod key    Stage key
```

And for deployment:

```text
CI/CD
  │
  ▼
Dedicated deployment key
  │
  ▼
deploy user
  │
  ▼
Only required permissions
```

That's **least privilege + credential separation + defense in depth**.

# ⭐ Final Mental Model

When designing SSH security, think in this order:

```text
1. WHO can connect?
        ↓
2. HOW do they authenticate?
        ↓
3. WHAT can their key do?
        ↓
4. WHICH Linux user do they become?
        ↓
5. WHAT permissions does that user have?
        ↓
6. WHAT sudo privileges do they have?
        ↓
7. WHAT gets logged?
        ↓
8. HOW quickly can we detect abuse?
        ↓
9. HOW do we revoke their access?
```

That is how you move from simply **"knowing SSH commands"** to actually **designing secure SSH access**.
