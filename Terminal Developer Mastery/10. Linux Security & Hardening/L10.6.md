# Lesson 10.6 — File Permissions in Depth 🔐

**Module 10 — Linux Security & Hardening**  
**Part 3: File System Security**

This is one of the most important Linux security lessons.

By the end, you should be comfortable with:

```text
chmod
chown
umask
setfacl
getfacl
SUID
SGID
Sticky Bit
```

And, more importantly, you'll understand **why** these mechanisms exist.

---

# 1. Why File Permissions Matter

Imagine your production server contains:

```text
/var/www/myapp/
├── server.js
├── package.json
├── .env
├── uploads/
└── logs/
```

Now imagine an attacker compromises some low-privileged process.

If your permissions are badly configured:

```text
Attacker
   ↓
Compromised Node.js process
   ↓
Can modify .env
   ↓
Can modify server.js
   ↓
Can modify system files
```

That's a serious problem.

With proper permissions:

```text
Attacker
   ↓
Compromised process
   ↓
Limited user
   ↓
Limited permissions
   ↓
Limited damage
```

This is **least privilege applied to the filesystem**.

---

# 2. Linux Permission Structure

Run:

```bash
ls -l
```

Example:

```text
-rwxr-x--- 1 rahul developers 2048 Aug 15 server.js
```

Break it down:

```text
- rwx r-x ---
  │   │   │
  │   │   └── Others
  │   └────── Group
  └────────── Owner
```

So:

```text
Owner  → rwx
Group  → r-x
Others → ---
```

Numerically:

```text
rwx = 7
r-x = 5
--- = 0
```

Therefore:

```text
750
```

---

# 3. File Type

The first character isn't a permission.

For example:

```text
-rwxr-x---
```

The first character:

```text
-
```

means regular file.

Common types:

```text
-  → regular file
d  → directory
l  → symbolic link
c  → character device
b  → block device
s  → socket
p  → named pipe
```

Example:

```text
drwxr-xr-x
```

is a directory.

---

# 4. Read, Write, Execute

For regular files:

```text
r → read contents
w → modify contents
x → execute the file
```

For directories, the meaning changes slightly:

```text
r → list directory entries
w → create/delete/rename entries
x → enter/traverse the directory
```

This distinction is extremely important.

---

# 5. Directory `x` Permission ⭐

Suppose:

```text
/var/www/myapp
```

has:

```text
r--r--r--
```

for someone.

They may be able to see names depending on the permission combination, but without `x`, they can't properly traverse the directory.

For directories:

```text
r = "Can I see what's inside?"
w = "Can I change directory entries?"
x = "Can I enter/traverse it?"
```

Think:

```text
Directory
   │
   ├── r → list
   ├── w → modify entries
   └── x → access/traverse
```

---

# 6. `chmod` — Change Permissions

The basic syntax:

```bash
chmod MODE FILE
```

Example:

```bash
chmod 644 server.js
```

Now:

```text
Owner  → rw-
Group  → r--
Others → r--
```

---

# 7. Numeric Permissions

Remember:

```text
r = 4
w = 2
x = 1
```

Therefore:

```text
rwx = 7
rw- = 6
r-x = 5
r-- = 4
-w- = 2
--x = 1
--- = 0
```

Examples:

```text
755
│││
││└── Others = 5
│└─── Group  = 5
└──── Owner  = 7
```

So:

```text
755 = rwxr-xr-x
```

---

# 8. Important Permission Values

|Mode|Meaning|Common use|
|---|---|---|
|`600`|Owner read/write|secrets|
|`640`|Owner rw, group r|sensitive shared files|
|`644`|Owner rw, others r|normal files|
|`700`|Owner full access|private directories/scripts|
|`750`|Owner full, group rx|applications|
|`755`|Owner full, others rx|public executables/directories|
|`770`|Owner/group full|shared private directory|
|`777`|Everyone full access|generally avoid|

---

# 9. `chmod 600`

Example:

```bash
chmod 600 .env
```

Permissions:

```text
Owner  → rw-
Group  → ---
Others → ---
```

This is useful for sensitive files.

Examples:

```text
.env
private SSH keys
credentials
certain configuration files
```

But remember:

> The correct permission depends on which process actually needs the file.

Don't blindly use `600` for everything.

---

# 10. `chmod 640`

```bash
chmod 640 app.log
```

Means:

```text
Owner  → rw-
Group  → r--
Others → ---
```

This is useful when:

```text
Owner → application/admin
Group → monitoring/logging
Others → no access
```

This is often better than making sensitive logs world-readable.

---

# 11. `chmod 750`

```bash
chmod 750 /var/www/myapp
```

Means:

```text
Owner  → rwx
Group  → r-x
Others → ---
```

Useful for directories where:

```text
Owner → full control
Group → read/traverse
Others → no access
```

---

# 12. Symbolic `chmod`

Numeric mode isn't the only method.

Example:

```bash
chmod u+x deploy.sh
```

Meaning:

```text
u → owner
+x → add execute
```

Other identifiers:

```text
u → user/owner
g → group
o → others
a → all
```

Examples:

```bash
chmod g+w file.txt
```

Add group write.

```bash
chmod o-r file.txt
```

Remove read from others.

```bash
chmod u-x script.sh
```

Remove execute from owner.

```bash
chmod a+r file.txt
```

Add read permission to everyone.

---

# 13. `chmod` With `=` ⭐

You can explicitly set permissions:

```bash
chmod u=rwx,g=rx,o= file
```

Equivalent to:

```text
Owner  → rwx
Group  → r-x
Others → ---
```

So:

```text
750
```

This can be clearer than repeatedly adding/removing permissions.

---

# 14. Recursive Permissions

You can use:

```bash
chmod -R 750 directory/
```

But:

> ⚠️ Be extremely careful with `-R`.

Why?

Because files and directories often need **different permissions**.

For example:

```text
directories → 750
files       → 640
```

Running:

```bash
chmod -R 750 /var/www/myapp
```

would make regular files executable too.

That's usually undesirable.

---

# 15. Better Application Permission Strategy

For example:

```text
/var/www/myapp
├── src/
├── config/
├── public/
├── logs/
└── .env
```

You might want:

```text
Directories → 750
Regular files → 640
.env → 600
```

The exact ownership and permissions depend on how Nginx, Node.js, deployment, and logging are configured.

Security is about designing the access model, not applying one magic command.

---

# 16. `chown` — Change Ownership

Syntax:

```bash
chown USER FILE
```

Example:

```bash
sudo chown rahul server.js
```

Change owner and group:

```bash
sudo chown rahul:developers server.js
```

Now:

```text
Owner → rahul
Group → developers
```

---

# 17. Recursive `chown`

You can use:

```bash
sudo chown -R rahul:developers project/
```

Again:

> Be careful with `-R`.

Changing ownership recursively on system directories can break services.

Never casually run:

```bash
sudo chown -R $USER:$USER /
```

That can seriously damage a Linux installation.

---

# 18. `chgrp`

To change only the group:

```bash
sudo chgrp developers project/
```

Recursive:

```bash
sudo chgrp -R developers project/
```

This is useful when ownership should remain the same but group access needs to change.

---

# 19. `umask`

Now we reach an important concept.

`umask` controls the **default permissions removed when new files/directories are created**.

Check yours:

```bash
umask
```

You might see:

```text
0022
```

or:

```text
0002
```

---

# 20. Why `umask` Exists

Suppose a program creates:

```text
newfile.txt
```

Linux starts with a base permission concept and applies the process's `umask`.

For normal files, the typical maximum starting mode is:

```text
666
```

For directories:

```text
777
```

Then `umask` removes permissions.

---

# 21. Example: `umask 022`

Suppose:

```text
umask = 022
```

New regular file:

```text
666
-
022
=
644
```

So:

```text
rw-r--r--
```

New directory:

```text
777
-
022
=
755
```

So:

```text
rwxr-xr-x
```

This is why you often see:

```text
files       → 644
directories → 755
```

by default.

---

# 22. Example: `umask 027`

Suppose:

```text
umask 027
```

New files:

```text
666
-
027
=
640
```

New directories:

```text
777
-
027
=
750
```

So:

```text
Files       → 640
Directories → 750
```

This is a much more restrictive default.

It can be useful on systems where group collaboration is needed but access by everyone else should be blocked.

---

# 23. Testing `umask` Safely

Don't change your global configuration yet.

You can temporarily set it:

```bash
umask 027
```

Check:

```bash
umask
```

Then create:

```bash
touch test-file
mkdir test-dir
```

Check:

```bash
ls -ld test-file test-dir
```

Afterward, your shell's `umask` can be restored if necessary.

You can see the previous value with:

```bash
umask
```

before changing it.

---

# 24. Why `umask` Matters for Backend Apps

Imagine your Node.js process creates:

```text
uploads/user-data.json
```

If your default permissions are too open:

```text
-rw-r--r-- user-data.json
```

maybe other users/processes can read it.

A stricter `umask` can help ensure newly created files aren't accidentally accessible to unrelated users.

But remember:

> `umask` is a default, not a replacement for explicit permission management.

---

# 25. ACLs — Access Control Lists

Traditional permissions give us:

```text
Owner
Group
Others
```

But sometimes that's not enough.

Imagine:

```text
project/
```

and you want:

```text
rahul  → full access
amit   → read/write
priya  → read-only
others → no access
```

One traditional group isn't enough if you need different permissions for multiple users.

That's where **ACLs** help.

---

# 26. What Is an ACL?

ACL means:

> **Access Control List**

It allows more detailed permissions for specific users and groups.

Conceptually:

```text
project/
│
├── Owner: rahul → rwx
├── Group: developers → r-x
├── User: amit → rwx
├── User: priya → r-x
└── Others → ---
```

This is more flexible than traditional owner/group/other permissions.

---

# 27. `getfacl`

To view ACLs:

```bash
getfacl file.txt
```

Example:

```text
# file: file.txt
# owner: rahul
# group: developers
user::rw-
group::r--
other::---
```

The syntax can initially look strange, but it becomes easy once you understand it.

---

# 28. `setfacl`

Add an ACL for a specific user:

```bash
setfacl -m u:amit:rw file.txt
```

Meaning:

```text
u → user
amit → username
rw → read/write
```

Now Amit gets access without changing the traditional owner.

---

# 29. ACL for a Group

Example:

```bash
setfacl -m g:developers:rwx project/
```

Now the `developers` group receives:

```text
rwx
```

on the directory.

---

# 30. Remove an ACL

```bash
setfacl -x u:amit file.txt
```

This removes Amit's specific ACL entry.

Check:

```bash
getfacl file.txt
```

---

# 31. ACLs and `ls -l`

Sometimes you'll see:

```text
-rw-rw-r--+
```

Notice:

```text
+
```

The `+` means extended ACL information exists.

Example:

```text
-rw-rw-r--+ file.txt
```

Check it with:

```bash
getfacl file.txt
```

---

# 32. Default ACLs ⭐

ACLs can also be inherited by newly created files/directories.

For example:

```bash
setfacl -d -m g:developers:rwx project/
```

The:

```text
-d
```

means **default ACL**.

This can be useful for shared project directories.

Example:

```text
project/
   │
   ├── file1
   ├── file2
   └── new/
        │
        └── inherited ACL
```

We'll practice this more in a later lab.

---

# 33. ACL Mask

ACLs introduce another concept:

```text
mask
```

The mask limits the maximum effective permissions for certain ACL entries.

For example, you might see:

```text
user::rwx
user:amit:rwx
group::r-x
mask::r-x
other::---
```

Even though Amit's ACL says:

```text
rwx
```

the mask:

```text
r-x
```

limits the effective permissions.

This is why `getfacl` may show:

```text
user:amit:rwx          #effective:r-x
```

Don't ignore the mask when debugging ACL permissions.

---

# 34. SUID — Set User ID

Now we move into special permissions.

SUID allows an executable file to run with the **file owner's privileges**.

Example:

```bash
ls -l /usr/bin/passwd
```

You may see something like:

```text
-rwsr-xr-x
```

Notice:

```text
s
```

instead of:

```text
x
```

That indicates SUID.

---

# 35. Why SUID Exists

Consider:

```text
passwd
```

A normal user needs to change password-related information that is protected.

The `passwd` program may need elevated privileges for a limited operation.

Conceptually:

```text
Normal user
    │
    ▼
passwd
    │
    ▼
Privileged operation
```

SUID allows the executable to run with the owner's effective privileges.

---

# 36. Why SUID Is Dangerous

Suppose:

```text
SUID program
      ↓
runs as root
```

and the program contains a serious vulnerability.

An attacker could potentially exploit it:

```text
Attacker
   ↓
SUID vulnerability
   ↓
Root privileges
```

That's why you should regularly audit unnecessary SUID binaries.

Find them:

```bash
sudo find / -perm -4000 -type f 2>/dev/null
```

Don't modify or delete anything from this output just because you don't recognize it.

---

# 37. SGID — Set Group ID

SGID has different behavior depending on whether it's applied to a file or directory.

For an executable file:

```text
SGID
```

can cause it to run with the file's group privileges.

For directories, SGID is particularly useful.

---

# 38. SGID on Directories ⭐

Suppose:

```text
/var/www/project
```

belongs to:

```text
developers
```

Set SGID:

```bash
chmod g+s /var/www/project
```

You may then see:

```text
drwxrws---
```

The:

```text
s
```

appears in the group execute position.

The useful behavior is:

> New files/directories created inside inherit the directory's group.

So:

```text
project/
   ↓
developers
```

new files tend to inherit:

```text
developers
```

as their group.

This is extremely useful for shared development/deployment directories.

---

# 39. Shared Project Example

Suppose:

```text
developers
├── rahul
├── amit
└── priya
```

Directory:

```text
/var/www/project
```

We want:

```text
Owner → rwx
Group → rwx
Others → ---
```

Set:

```bash
chmod 2770 /var/www/project
```

Why `2770`?

```text
2 → SGID
7 → Owner rwx
7 → Group rwx
0 → Others ---
```

So:

```text
drwxrws---
```

Now new files can inherit the `developers` group.

---

# 40. Sticky Bit

The sticky bit is especially important for shared directories.

A classic example is:

```text
/tmp
```

Check:

```bash
ls -ld /tmp
```

You'll commonly see something similar to:

```text
drwxrwxrwt
```

Notice:

```text
t
```

at the end.

---

# 41. What Does Sticky Bit Do?

In a shared writable directory:

```text
User A
User B
User C
```

all may be able to create files.

Without sticky-bit protection, one user could potentially delete another user's files if directory permissions allow it.

The sticky bit restricts deletion/renaming so that generally only:

- the file owner
    
- the directory owner
    
- root
    

can remove/rename the entry.

This is why `/tmp` uses it.

---

# 42. Setting Sticky Bit

```bash
chmod +t shared/
```

Or numerically:

```bash
chmod 1777 shared/
```

Breakdown:

```text
1 → sticky bit
7 → owner
7 → group
7 → others
```

Result:

```text
drwxrwxrwt
```

---

# 43. SUID, SGID, Sticky Bit — Memory Trick

Remember:

```text
SUID   → User
SGID   → Group
Sticky → Delete protection
```

And their numeric prefixes:

```text
SUID    → 4
SGID    → 2
Sticky  → 1
```

So:

```text
chmod 4755 file
```

means:

```text
4    755
│    │
SUID permissions
```

And:

```text
chmod 2770 directory
```

means:

```text
2    770
│    │
SGID permissions
```

And:

```text
chmod 1777 directory
```

means:

```text
1    777
│    │
Sticky bit
```

---

# 44. Finding Special Permission Files

Find SUID:

```bash
sudo find / -perm -4000 -type f 2>/dev/null
```

Find SGID:

```bash
sudo find / -perm -2000 -type f 2>/dev/null
```

Find both:

```bash
sudo find / -perm /6000 -type f 2>/dev/null
```

Again:

> Don't delete or modify system binaries simply because they have SUID/SGID.

Some are legitimate.

Security work requires understanding **why** a permission exists before changing it.

# 45. Secure Shared Directory

Let's build a safe lab.

Create:

```bash
mkdir -p ~/linux-security-lab/shared
```

Create a group:

```bash
sudo groupadd securityteam
```

Add yourself:

```bash
sudo usermod -aG securityteam "$USER"
```

Now set ownership:

```bash
sudo chown "$USER":securityteam ~/linux-security-lab/shared
```

Set permissions:

```bash
chmod 2770 ~/linux-security-lab/shared
```

Check:

```bash
ls -ld ~/linux-security-lab/shared
```

You should see something resembling:

```text
drwxrws---
```

This demonstrates SGID + group collaboration.

---

# 46. Test SGID Behavior

Create:

```bash
touch ~/linux-security-lab/shared/example.txt
```

Check:

```bash
ls -l ~/linux-security-lab/shared/example.txt
```

The group should normally be inherited from the SGID directory.

This is a very useful real-world pattern.

# 47. ACL Practical Lab

Create:

```bash
touch ~/linux-security-lab/acl-test.txt
```

Check:

```bash
getfacl ~/linux-security-lab/acl-test.txt
```

Now, if another local test user exists, you could grant that user access:

```bash
sudo setfacl -m u:testuser:rw ~/linux-security-lab/acl-test.txt
```

Check:

```bash
getfacl ~/linux-security-lab/acl-test.txt
```

You'll see something like:

```text
user::rw-
user:testuser:rw-
group::r--
mask::rw-
other::---
```

This is a good way to understand ACLs without touching system files.

---

# 48. ACL vs Traditional Permissions

Traditional permissions:

```text
Owner
Group
Others
```

ACL:

```text
Owner
Specific users
Specific groups
Group
Mask
Others
```

Use traditional permissions when they are sufficient.

Use ACLs when you need **more precise access control**.

Don't create complicated ACLs unnecessarily.

Complex permissions can become difficult to audit.

---

# 49. `namei` — Permission Debugging

This command is extremely useful:

```bash
namei -l /var/www/myapp/.env
```

It shows permissions for every directory in the path.

Example:

```text
f /var/www/myapp/.env
drwxr-xr-x /
drwxr-xr-x var
drwxr-x--- www
drwxr-x--- myapp
-rw------- .env
```

This helps answer:

> "Why can't my application access this file?"

Sometimes the file itself has correct permissions, but a parent directory doesn't allow traversal.

---

# 50. `stat` — Detailed Metadata

Use:

```bash
stat file.txt
```

You'll see:

```text
File
Size
Blocks
IO Block
Device
Inode
Links
Access
Uid
Gid
Access time
Modify time
Change time
```

The three timestamps are important:

```text
atime → access
mtime → content modification
ctime → metadata/status change
```

Note:

`ctime` does **not** mean "creation time."

---

# 51. File Permission Security for `.env`

Consider:

```text
/var/www/myapp/.env
```

It may contain:

```text
MONGO_URI=...
JWT_SECRET=...
RAZORPAY_KEY_SECRET=...
```

A reasonable starting point is:

```bash
chmod 600 .env
```

But ownership must also be correct.

For example:

```text
Owner → application/deployment user
Group → appropriate service group
Others → none
```

The exact design depends on who needs to read `.env`.

---

# 52. File Permissions and Node.js

Suppose:

```text
Node process
   ↓
nodeuser
```

and:

```text
.env
Owner → deploy
Permissions → 600
```

Then Node may not be able to read it.

That's not necessarily a problem.

It means you need to **design the ownership model correctly**.

For example, perhaps:

```text
nodeuser
   ↓
Group app
   ↓
.env → app group read
```

with something like:

```text
640
```

instead of blindly changing it to:

```text
777
```

This is an important professional mindset:

> **Fix ownership and access design rather than weakening permissions.**

---

# 53. What `chmod 777` Usually Means

Suppose someone gets:

```text
Permission denied
```

and runs:

```bash
chmod -R 777 .
```

The application works.

But now:

```text
Everyone
   ↓
Read
Write
Execute
```

Potentially:

```text
Any compromised process
      ↓
Modify application files
      ↓
Inject malicious code
```

This is why:

```text
"Works"
```

doesn't mean:

```text
"Secure"
```

---

# 54. Permission Debugging Strategy ⭐

When you get:

```text
Permission denied
```

don't immediately use `chmod 777`.

Instead ask:

```text
1. Who is running the process?
2. Who owns the file?
3. What group owns it?
4. What permissions exist?
5. What permissions do parent directories have?
6. Is there an ACL?
7. Is SELinux/AppArmor involved?
8. Is the process actually accessing the expected path?
```

Useful commands:

```bash
ps aux
ls -l
namei -l
getfacl
id
```

This is much closer to real production debugging.

### Find world-writable directories

Don't assume every result is a vulnerability.

# 56. Production Permission Model

For your future Node.js deployment, think like this:

```text
                    /var/www/myapp
                           │
             ┌─────────────┼─────────────┐
             │             │             │
            src          logs           .env
             │             │             │
          640/750        640           600
             │             │             │
             └─────────────┼─────────────┘
                           │
                     Correct owner
                           │
                     Correct group
                           │
                    Node.js user
```

The goal isn't to use particular numbers everywhere.

The goal is:

```text
Only required users/processes
        ↓
Get required permissions
        ↓
Nothing more
```

# 57. Interview Questions

### Q1. What is `umask`?

`umask` controls which permission bits are removed from the default permissions assigned to newly created files and directories.

---

### Q2. What does `chmod 640` mean?

```text
Owner  → rw-
Group  → r--
Others → ---
```

---

### Q3. What is an ACL?

An Access Control List allows more granular permissions for specific users and groups beyond the traditional owner/group/other model.

---

### Q4. What does SUID do?

SUID causes an executable to run with the effective privileges of its file owner.

---

### Q5. What does SGID do on a directory?

New files and directories created inside generally inherit the directory's group.

---

### Q6. What does the sticky bit do?

On a shared writable directory, it restricts deletion/renaming of entries so users generally can't remove or rename files belonging to other users.

---

### Q7. Why is `/tmp` commonly configured with a sticky bit?

Because multiple users/processes need to write there, while users should generally not be able to delete each other's files.

---

### Q8. What is the difference between `chmod` and `chown`?

```text
chmod → changes permissions
chown → changes ownership
```

---

### Q9. Why shouldn't you use `chmod -R 777`?

Because it grants excessive permissions and can allow unauthorized users/processes to modify or execute files.

```text

   │
   ├── rahul       → administrator
```

With:

```text
root
 ↓
Not used by Node.js
```

```text
Node.js compromise
       ↓
nodeuser
       ↓
Limited filesystem access
       ↓
Reduced blast radius
```
