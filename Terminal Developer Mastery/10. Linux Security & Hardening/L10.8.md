# Lesson 10.8 — Firewall Hardening 🔥🛡️

**Module 10 — Linux Security & Hardening**  
**Part 4: Network Security**

A firewall is one of the first security boundaries between your Linux server and the internet.

If your server is running:

```text
SSH
Nginx
Node.js
MongoDB
Redis
Docker
```

you **should not automatically expose all of them to the internet**.

A firewall lets you define:

> **Which network connections are allowed and which should be blocked?**

---

# 1. What Is a Firewall?

A firewall controls network traffic based on rules.

Think of your server as a building:

```text
                  INTERNET
                     │
                     ▼
              ┌──────────────┐
              │   FIREWALL   │
              └──────┬───────┘
                     │
          ┌──────────┼──────────┐
          │          │          │
         SSH       HTTPS      Other
          │          │          │
         ALLOW      ALLOW      DENY
```

Without a firewall:

```text
Internet
   │
   ├── Port 22
   ├── Port 80
   ├── Port 443
   ├── Port 3000
   ├── Port 5000
   ├── Port 27017
   └── ...
```

With a properly configured firewall:

```text
Internet
   │
   ├── 22   → restricted SSH
   ├── 80   → HTTP
   ├── 443  → HTTPS
   │
   └── everything else → DENY
```

---

# 2. Why Firewalls Matter

Imagine your Node.js application listens on:

```text
0.0.0.0:3000
```

That means it may accept connections on all network interfaces.

Without appropriate firewall/network controls:

```text
Internet
   │
   ▼
Your server
   │
   ▼
Node.js :3000
```

An attacker can potentially interact directly with your application.

A better production architecture is:

```text
Internet
   │
   ▼
Firewall
   │
   ├── 80/443 → Nginx
   │
   └── SSH → restricted
                │
                ▼
             Server
                │
                ▼
             Node.js
                │
                ▼
             MongoDB
```

Node.js and MongoDB can remain private.

---

# 3. Ports

A port is a logical endpoint used by network services.

Common ports:

|Port|Common service|
|--:|---|
|22|SSH|
|53|DNS|
|80|HTTP|
|443|HTTPS|
|3000|Node.js/dev servers|
|5000|Common backend development port|
|5432|PostgreSQL|
|3306|MySQL|
|6379|Redis|
|27017|MongoDB|

These aren't hard rules. Applications can listen on different ports.

---

# 4. Listening Ports

Before configuring a firewall, find out what's actually listening.

Run:

```bash
sudo ss -tulpn
```

You may see:

```text
Netid  Local Address       Process
tcp    0.0.0.0:22          sshd
tcp    0.0.0.0:80          nginx
tcp    127.0.0.1:3000      node
```

Interpretation:

```text
0.0.0.0:22
```

means SSH is listening on all IPv4 interfaces.

But:

```text
127.0.0.1:3000
```

means Node.js is only listening on localhost.

That's already an important security distinction.

---

# 5. `127.0.0.1` vs `0.0.0.0`

### `127.0.0.1`

Only the local machine can normally access it.

```text
Server
 │
 └── 127.0.0.1:3000
```

### `0.0.0.0`

The service can listen on all IPv4 interfaces.

```text
Internet
   │
   ▼
0.0.0.0:3000
   │
   ▼
Node.js
```

For backend production:

```text
Node.js → localhost/private network
Nginx   → public 80/443
```

is often a better architecture.

---

# 6. Firewall vs Listening Service

This distinction is extremely important.

Suppose:

```text
Node.js
listens on 0.0.0.0:3000
```

and firewall blocks port 3000:

```text
Internet
   │
   ▼
Firewall
   │
   X
   │
Node.js
```

The service is still listening.

The firewall is simply preventing external access.

A stronger design is often:

```text
Node.js
listens on 127.0.0.1:3000
```

plus:

```text
Firewall
```

This gives you **multiple layers of protection**.

---

# 7. Linux Firewall Technologies

You'll encounter:

```text
iptables
nftables
ufw
```

Their relationship can be confusing.

Modern Linux networking primarily uses:

> **nftables**

`iptables` is the older firewall command/interface that remains widely encountered.

`ufw` is a simpler firewall management interface commonly used on Ubuntu/Debian-based systems.

Think:

```text
High-level
    │
    ▼
   UFW
    │
    ▼
Firewall rules/framework
    │
    ▼
 nftables
```

The exact backend and integration can vary by distribution/version.

---

# 8. `ufw`

UFW means:

> **Uncomplicated Firewall**

It provides a simpler interface for common firewall tasks.

For example:

```bash
sudo ufw status
```

You might see:

```text
Status: inactive
```

or:

```text
Status: active
```

---

# 9. Why UFW Is Useful

Raw firewall rules can become complicated.

UFW provides simple commands:

```bash
sudo ufw allow 22
sudo ufw allow 80
sudo ufw allow 443
```

This is much easier for beginners.

For a typical small VPS, UFW is often enough.

---

# 10. ⚠️ The Most Important Firewall Rule

Before enabling a firewall on a remote server:

> **Make sure your SSH access is explicitly allowed.**

Otherwise:

```text
SSH
 │
 ▼
Firewall enabled
 │
 ▼
Port 22 blocked
 │
 ▼
You
 │
 X
 │
Server
```

You can lock yourself out.

The safe order is:

```text
Allow SSH
   ↓
Allow required services
   ↓
Set default policies
   ↓
Enable firewall
   ↓
Verify
```

---

# 11. UFW Status

On your Linux Mint system, you can safely inspect:

```bash
sudo ufw status verbose
```

You may see:

```text
Status: inactive
```

That's okay.

Don't enable it yet if you're unsure about your current network configuration.

---

# 12. Default-Deny Principle

One of the most important firewall concepts is:

> **Deny what isn't explicitly needed.**

Instead of:

```text
Allow everything
   ↓
Block individual bad things
```

prefer:

```text
Deny by default
   ↓
Allow only required traffic
```

This is the network version of least privilege.

---

# 13. Default Policies

UFW can use:

```bash
sudo ufw default deny incoming
```

and:

```bash
sudo ufw default allow outgoing
```

This means:

```text
Incoming → DENY by default
Outgoing → ALLOW by default
```

Then explicitly allow what you need:

```text
SSH
HTTP
HTTPS
```

---

# 14. Example Production Firewall

For a basic web server:

```text
Internet
   │
   ├── 80  → ALLOW
   ├── 443 → ALLOW
   ├── 22  → ALLOW/restricted
   │
   ├── 3000 → DENY
   ├── 27017 → DENY
   └── everything else → DENY
```

This is much safer than exposing every service.

---

# 15. Allowing SSH

You can allow SSH with:

```bash
sudo ufw allow ssh
```

Or:

```bash
sudo ufw allow 22/tcp
```

The application-level name:

```text
ssh
```

maps to the standard SSH service/port configuration.

---

# 16. Allowing HTTP

```bash
sudo ufw allow 80/tcp
```

This allows TCP traffic to port 80.

---

# 17. Allowing HTTPS

```bash
sudo ufw allow 443/tcp
```

Now:

```text
HTTP  → 80
HTTPS → 443
```

can reach your server.

---

# 18. Allowing a Specific Application Port

Suppose you have:

```text
Node.js → 3000
```

You could technically:

```bash
sudo ufw allow 3000/tcp
```

But ask:

> **Does Node.js actually need to be publicly reachable?**

If Nginx is your reverse proxy:

```text
Internet
   │
   ▼
443
   │
   ▼
Nginx
   │
   ▼
127.0.0.1:3000
   │
   ▼
Node.js
```

then you usually don't need public port 3000.

This is a much better architecture.

---

# 19. Don't Expose MongoDB Publicly

MongoDB commonly uses:

```text
27017
```

Avoid:

```text
sudo ufw allow 27017/tcp
```

unless you have a very specific architecture requiring it and have implemented strong network controls.

Instead:

```text
Internet
   │
   X
27017
   │
   ▼
MongoDB
```

Keep the database on:

```text
localhost
```

or a private network.

---

# 20. Firewall Rule Specificity

You can create more precise rules.

For example:

```bash
sudo ufw allow from 203.0.113.10 to any port 22 proto tcp
```

This means:

```text
Only:
203.0.113.10
       ↓
SSH
       ↓
Allowed
```

Everyone else:

```text
SSH → denied
```

This can be very useful if you have a fixed trusted admin IP.

However, if your ISP gives you a changing IP, you could accidentally lock yourself out when your IP changes.

---

# 21. Port + Protocol

Firewall rules can specify:

```text
Port
Protocol
Source
Destination
```

For example:

```text
22/tcp
```

means:

```text
Port → 22
Protocol → TCP
```

You may also encounter UDP:

```text
53/udp
```

for DNS-related traffic.

---

# 22. TCP vs UDP

### TCP

Connection-oriented.

Common examples:

```text
SSH
HTTP
HTTPS
PostgreSQL
MongoDB
```

### UDP

Connectionless.

Common examples:

```text
DNS
DHCP
certain VPNs
streaming/real-time applications
```

Firewall rules should specify the appropriate protocol.

---

# 23. UFW Application Profiles

UFW can have application profiles.

List them:

```bash
sudo ufw app list
```

You may see:

```text
OpenSSH
Nginx Full
Nginx HTTP
Nginx HTTPS
```

Then:

```bash
sudo ufw allow 'Nginx Full'
```

This can be easier than manually specifying ports.

---

# 24. UFW Status With Rules

After configuring rules:

```bash
sudo ufw status numbered
```

Example:

```text
[ 1] 22/tcp
[ 2] 80/tcp
[ 3] 443/tcp
```

The numbered output is useful when removing rules.

---

# 25. Removing a UFW Rule

You can remove by rule number:

```bash
sudo ufw status numbered
```

Then:

```bash
sudo ufw delete 2
```

Always check the numbered list first.

Don't blindly delete a rule on a production server.

---

# 26. UFW Logging

Firewall events can be logged.

Enable:

```bash
sudo ufw logging medium
```

Available levels can include:

```text
off
low
medium
high
full
```

You don't always want the highest level because excessive logging can create noise and consume storage.

---

# 27. Why Firewall Logs Matter

Suppose an attacker repeatedly probes:

```text

27017
```

Firewall logs can help reveal:

```text

Destination

```

Then:


# 28. `nftables`

Now let's move deeper.

Modern Linux firewalling uses:

> **nftables**

Check whether it's available:

```bash
sudo nft --version
```

View the current ruleset:

```bash
sudo nft list ruleset
```

This command is especially useful for understanding what the kernel firewall is actually configured to do.

---

# 29. nftables Architecture

Think:

```text
                Network Packet
                       │
                       ▼
                 Linux Kernel
                       │
                       ▼
                  nftables
                       │
             ┌─────────┴─────────┐
             │                   │
           ALLOW                DROP
             │                   │
             ▼                   X
          Service              Packet
```

Rules are evaluated inside the kernel networking stack.

---

# 30. nftables Tables

A common nftables structure is:

```text
table
  │
  ├── chains
  │      │
  │      ├── input
  │      ├── output
  │      └── forward
  │
  └── rules
```

You can think of it as:

```text
Table
 ↓
Chain
 ↓
Rule
```

---

# 31. Input, Output, Forward

These three concepts are fundamental.

### Input

Traffic coming **into** your machine.

```text
Internet
   ↓
Server
```

### Output

Traffic going **out** from your machine.

```text
Server
   ↓
Internet
```

### Forward

Traffic passing **through** the machine.

```text
Network A
    ↓
Linux Router
    ↓
Network B
```

For a typical web server, the most important chain is often:

```text
input
```

---

# 32. nftables Default Policy

Conceptually, you might configure:

```text
input → drop
output → accept
forward → drop
```

Then allow specific incoming traffic.

This is similar to UFW's default-deny approach.

---

# 33. Example nftables Concept

A simplified conceptual policy:

```text
Input:
    established/related → ACCEPT
    loopback            → ACCEPT
    SSH                 → ACCEPT
    HTTP                → ACCEPT
    HTTPS               → ACCEPT
    everything else     → DROP
```

This is a powerful pattern.

---

# 34. Established Connections

Imagine:

```text
Client
   │
   │ HTTP request
   ▼
Server
   │
   │ response
   ▼
Client
```

Firewall state tracking can understand that the response belongs to an existing connection.

This is called **stateful firewalling**.

Conceptually:

```text
NEW
ESTABLISHED
RELATED
```

These connection states are very important in firewall design.

---

# 35. Stateful Firewall

Instead of treating every packet independently:

```text
Packet
 ↓
Rule
```

a stateful firewall understands connection context:

```text
Connection
    │
    ├── NEW
    ├── ESTABLISHED
    └── RELATED
```

This makes firewall policies much more practical.

---

# 36. `iptables`

You will still encounter:

```bash
iptables
```

on many systems and in older tutorials.

Check:

```bash
sudo iptables -L -n -v
```

You may see:

```text
Chain INPUT
Chain FORWARD
Chain OUTPUT
```

But don't assume every modern Linux system should be configured directly using iptables.

On modern distributions, **nftables is the underlying direction**, while compatibility layers and higher-level tools may still expose iptables commands.

---

# 37. UFW vs nftables vs iptables

A useful mental model:

|Tool|Purpose|
|---|---|
|UFW|Simple firewall management|
|nftables|Modern low-level firewall framework|
|iptables|Older/common firewall interface|

For your learning path:

```text
Beginner
   ↓
UFW
   ↓
Understand concepts
   ↓
nftables
   ↓
Understand lower-level rules
   ↓
iptables
   ↓
Understand legacy systems
```

As a backend developer, you don't need to memorize hundreds of firewall commands.

You need to understand **network policy**.

# 38. Firewall Policy for a MERN Server ⭐

Suppose your server has:

```text
Nginx
Node.js
MongoDB
SSH
```

A good conceptual design is:

```text
Internet
   │
   ├──────────────┐
   │              │
  80             443
   │              │
   └──────┬───────┘
          ▼
        Nginx
          │
          ▼
   127.0.0.1:3000
          │
          ▼
       Node.js
          │
          ▼
      MongoDB
   127.0.0.1:27017
```

Firewall:

```text
22  → restricted
80  → allow
443 → allow
3000 → deny public
27017 → deny public
```

This is a much better starting architecture than:

```text
22
80
443
3000
5000
27017
6379
5432
...
```

all exposed.

---

# 39. Defense in Depth

Don't rely on the firewall alone.

For example:

```text
Firewall
   ↓
Node.js listens only on localhost
   ↓
MongoDB listens only privately
   ↓
Authentication
   ↓
Authorization
```

If the firewall is accidentally changed:

```text
Port 27017
```

MongoDB still isn't necessarily publicly reachable if it's bound only to localhost/private interfaces.

That's **defense in depth**.

---

# 40. Firewall and Docker ⚠️

This is particularly important for your future Docker work.

Docker can manipulate networking and firewall rules.

You might run:

```bash
docker run -p 3000:3000 myapp
```

and unintentionally expose a service beyond what you expected.

Think:

```text
Docker
   ↓
Port publishing
   ↓
Network rules
   ↓
Firewall interaction
```

Therefore, when securing Docker servers, don't assume:

```text
UFW says blocked
```

automatically means every Docker-published port is unreachable.

Docker networking needs to be understood separately.

This will become important when we connect this module to your Module 13 Docker/CI/CD knowledge.

# 42. Firewall Rule Design

Before writing a rule, ask:

### 1. Who needs access?

```text
Everyone?
Admin?
Application server?
Internal network?
```

### 2. What service?

```text
SSH?
HTTP?
Database?
```

### 3. Which port?

```text
22?
443?
27017?
```

### 4. Which protocol?

```text
TCP?
UDP?
```

### 5. From where?

```text
Internet?
Private subnet?
Specific IP?
```

### 6. Why is it needed?

If you can't explain the rule, reconsider it.

# 43. Example Firewall Design

Imagine:

```text
Admin IP
203.0.113.10
```

You could conceptually have:

```text
SSH
Source → 203.0.113.10
Destination → Server
Port → 22
Action → ACCEPT
```

And:

```text
HTTP
Source → Any
Port → 80
Action → ACCEPT
```

```text
HTTPS
Source → Any
Port → 443
Action → ACCEPT
```

Everything else:

```text
DROP
```

This is much stronger than:

```text
ALLOW ALL
```

# 44. Rate Limiting and Firewalls

A firewall can block traffic based on network characteristics.

But it isn't necessarily enough to protect an application from:

```text
100,000 legitimate-looking HTTP requests
```

That's where application-level controls matter:

```text
Firewall
   ↓
Reverse proxy
   ↓
Rate limiting
   ↓
Application
```

For your Node.js application, you might use:

```text
express-rate-limit
```

or infrastructure-level rate limiting.

So:

```text
Firewall ≠ Application security
```

They complement each other.

---

# 45. IPv4 vs IPv6 ⚠️

One common mistake is configuring IPv4 rules while forgetting IPv6.

For example:

```text
IPv4
   ↓
Firewall configured ✓
```

but:

```text
IPv6
   ↓
Firewall rules missing ❌
```

Your service could still be reachable through IPv6.

Always consider both:

```text
IPv4
+
IPv6
```

if IPv6 is enabled.

---

# 46. Loopback Traffic

Your server needs local communication:

```text
127.0.0.1
```

For example:

```text
Nginx → Node.js
Node.js → MongoDB
```

if these services communicate through localhost.

Firewall policies generally need to allow legitimate loopback traffic.

Conceptually:

```text
loopback
   ↓
trusted local communication
```

Don't block it blindly.

# 49. Safe UFW Lab

If you're practicing on your **Linux Mint desktop**, don't blindly enable a restrictive firewall while you're connected to something important.

You can inspect UFW first:

```bash
sudo ufw status numbered
```

If you're working on a disposable VM, you can practice the full workflow.

For a test server, the conceptual sequence is:

```bash
sudo ufw allow ssh
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw default deny incoming
sudo ufw default allow outgoing
```

Then:

```bash
sudo ufw enable
```

And verify:

```bash
sudo ufw status verbose
```

### ⚠️ Remote-server rule

If you're connected over SSH, **allow SSH before enabling UFW**.

Keep your current SSH session open and test a second session after enabling the firewall.

# 51. Firewall Troubleshooting

Suppose:

```text
curl https://example.com
```

fails.

Don't immediately change firewall rules.

Check systematically:

```text
1. Is the service running?
2. Is it listening?
3. Is it listening on the expected interface?
4. Is the port correct?
5. Is firewall blocking it?
6. Is DNS working?
7. Is routing working?
8. Is the remote server blocking traffic?
```

Useful commands:

```bash
ss -tulpn
```

```bash
sudo ufw status
```

```bash
sudo nft list ruleset
```

```bash
ip route
```

```bash
dig example.com
```

# 53. Common Firewall Mistakes

## ❌ Mistake 1 — Enable firewall before allowing SSH

Result:

```text
LOCKED OUT
```

---

## ❌ Mistake 2 — Open every port

```text
ufw allow 1:65535/tcp
```

This defeats the purpose of firewalling.

---

## ❌ Mistake 3 — Expose MongoDB

```text
27017 → Internet
```

Usually unnecessary and risky.

---

## ❌ Mistake 4 — Expose Node.js directly

```text
3000 → Internet
```

when Nginx could proxy to localhost.

---

## ❌ Mistake 5 — Ignore IPv6

Configure IPv6 security if IPv6 is enabled.

---

## ❌ Mistake 6 — Assume changing SSH port is security

```text
22 → 2222
```

doesn't replace proper authentication and firewall controls.

---

## ❌ Mistake 7 — Forget Docker networking

Published Docker ports can change your effective exposure.

# 54. Interview Questions

### Q1. What is a firewall?

A firewall controls network traffic according to defined security rules.

---

### Q2. What is the principle of default deny?

Traffic is blocked unless it is explicitly allowed.

---

### Q3. What is UFW?

UFW is a simplified firewall management interface commonly used on Ubuntu/Debian-based Linux systems.

---

### Q4. What is nftables?

nftables is the modern Linux packet-filtering and firewall framework.

---

### Q5. What is the difference between `iptables` and `nftables`?

`iptables` is the older firewall interface, while nftables is the modern Linux firewall framework. Compatibility tooling can still make iptables commands relevant on contemporary systems.

---

### Q6. What is the difference between input, output, and forward traffic?

```text
INPUT   → traffic entering the machine
OUTPUT  → traffic leaving the machine
FORWARD → traffic passing through the machine
```

---

### Q7. Should MongoDB port 27017 be publicly accessible?

Normally, no. It should generally be restricted to localhost or a private network unless there's a specific architecture requiring remote access.

---

### Q8. Why shouldn't Node.js port 3000 normally be public when using Nginx?

Because Nginx can expose HTTPS publicly and proxy requests internally to Node.js, reducing the application's network exposure.

## ⭐ Final Takeaway

The most important rule from this lesson is:

> **Don't ask "Which ports should I open?" Ask "Which services actually need to be reachable, from where, and why?"**

That changes firewall configuration from memorizing commands into actual security engineering.

Your production baseline should eventually look roughly like:

```text
[✓] Default-deny incoming
[✓] SSH explicitly allowed/restricted
[✓] HTTP/HTTPS allowed where required
[✓] Node.js not publicly exposed unnecessarily
[✓] MongoDB not publicly exposed
[✓] IPv4 considered
[✓] IPv6 considered
[✓] Firewall logging reviewed
[✓] Listening ports regularly audited
[✓] Docker networking reviewed
[✓] Firewall rules documented
```
