# Lesson 10.9 — Intrusion Prevention with Fail2ban 🚨🛡️

**Module 10 — Linux Security & Hardening**  
**Part 4: Network Security**

In Lesson 10.8, we learned:

```text
Firewall
   ↓
Controls network access
```

Today we'll add another layer:

```text
Logs
   ↓
Fail2ban
   ↓
Detect repeated suspicious behavior
   ↓
Temporarily block the source
```

This is especially useful for protecting:

- SSH
    
- Nginx
    
- authentication endpoints
    
- other services that produce useful security logs
    

---

# 1. What Is Fail2ban?

**Fail2ban** is an intrusion-prevention tool that watches logs for patterns of suspicious activity.

For example:

```text
Attacker
   │
   ├── Failed SSH login
   ├── Failed SSH login
   ├── Failed SSH login
   ├── Failed SSH login
   └── Failed SSH login
             │
             ▼
          Fail2ban
             │
             ▼
          Firewall
             │
             X
          Attacker
```

The important idea is:

> **Fail2ban detects behavior; the firewall enforces the block.**

---

# 2. Fail2ban Is Not a Firewall

This distinction is important.

### Firewall

Answers:

> Should traffic from this source be allowed?

### Fail2ban

Answers:

> Has this source shown suspicious behavior repeatedly?

So:

```text
Firewall
   ↓
Network access control
```

while:

```text
Fail2ban
   ↓
Behavior-based temporary blocking
```

They work together.

---

# 3. Why Do We Need Fail2ban?

Suppose SSH is exposed:

```text
Internet
   │
   ▼
Port 22
   │
   ▼
SSH
```

An attacker can repeatedly attempt passwords:

```text
root
admin
ubuntu
test
user
...
```

A firewall allowing SSH cannot necessarily tell whether an individual connection is legitimate.

Fail2ban can inspect authentication logs and identify repeated failures.

---

# 4. Basic Architecture

The architecture looks like:

```text
                    INTERNET
                       │
                       ▼
                     SSH
                       │
                       ▼
                    sshd
                       │
                       ▼
                      Logs
                       │
                       ▼
                    Fail2ban
                       │
              ┌────────┴────────┐
              │                 │
          No threshold      Threshold reached
              │                 │
              ▼                 ▼
            Allow             Ban
                                │
                                ▼
                             Firewall
                                │
                                X
```

This is a classic example of **security automation**.

---

# 5. What Is a Jail?

A **jail** is a Fail2ban configuration that says:

> Watch a particular service/log for suspicious behavior and take an action when a threshold is reached.

For example:

```text
[sshd]
```

A jail can define things such as:

```text
enabled
port
log source
filter
maxretry
findtime
bantime
action
```

---

# 6. Important Fail2ban Terms

These are the terms you should memorize:

```text
jail
filter
logpath
maxretry
findtime
bantime
action
ignoreip
```

We'll understand each one.

---

# 7. `maxretry`

Suppose:

```text
maxretry = 5
```

This means Fail2ban can trigger a ban after the configured number of matching failures.

Conceptually:

```text
1 failure → okay
2 failures → okay
3 failures → okay
4 failures → okay
5 failures → BAN
```

The exact behavior also depends on the other jail settings.

---

# 8. `findtime`

`findtime` defines the time window in which Fail2ban counts failures.

For example:

```text
findtime = 10 minutes
maxretry = 5
```

means roughly:

> If 5 matching failures occur within 10 minutes, trigger the jail action.

So:

```text
5 failures
+
within 10 minutes
=
ban condition
```

---

# 9. `bantime`

`bantime` determines how long the source remains banned.

For example:

```text
bantime = 1 hour
```

means:

```text
Suspicious IP
    ↓
Blocked
    ↓
1 hour
    ↓
Automatically unblocked
```

This is different from permanently blocking the address.

---

# 10. Why Temporary Bans?

Temporary bans reduce the chance of accidental permanent lockouts.

Imagine:

```text
You
 ↓
Wrong password
 ↓
Wrong password
 ↓
Wrong password
```

If your system permanently banned every mistake, you could create operational problems.

Instead:

```text
Temporary ban
     ↓
Cooldown
     ↓
Access restored
```

This is one reason Fail2ban is useful.

---

# 11. `filter`

A filter tells Fail2ban:

> **What log pattern represents suspicious behavior?**

For SSH, the filter looks for authentication failures in SSH logs.

Conceptually:

```text
Log:
Failed password for invalid user admin from 203.0.113.20

       ↓

SSH filter recognizes pattern

       ↓

Fail2ban counts the event
```

---

# 12. `logpath`

Fail2ban needs to know where the relevant logs are.

Depending on the Linux distribution and logging configuration, authentication information may come from:

```text
/var/log/auth.log
```

or systemd journal.

Modern setups can use the systemd journal directly.

That's important because you shouldn't assume every Linux distribution stores logs in exactly the same place.

---

# 13. `action`

After the threshold is reached, Fail2ban needs to do something.

That is the **action**.

Historically this often means:

```text
Fail2ban
   ↓
Firewall rule
   ↓
DROP/BLOCK
```

The exact action can use different firewall mechanisms depending on your system.

---

# 14. `ignoreip`

You can whitelist trusted addresses.

For example:

```text
ignoreip = 127.0.0.1/8
```

Potentially you might add a trusted administration network.

But be careful.

If you add:

```text
0.0.0.0/0
```

to `ignoreip`, you've effectively told Fail2ban:

> Ignore everyone.

That defeats the purpose.

# 17. Never Edit `jail.conf` Directly

You may find:

```text
/etc/fail2ban/jail.conf
```

It's tempting to edit it directly.

Don't.

The recommended approach is generally to use:

```text
/etc/fail2ban/jail.local
```

or files under:

```text
/etc/fail2ban/jail.d/
```

Why?

Because package updates can replace the default configuration.

Your custom configuration should be separate.

---

# 18. Inspect the Default Configuration

You can safely read:

```bash
sudo less /etc/fail2ban/jail.conf
```

Don't modify it.

You're mainly looking for concepts like:

```text
[DEFAULT]

bantime
findtime
maxretry
```

and individual jails.

---

# 19. Creating `jail.local`

Create:

```bash
sudo nano /etc/fail2ban/jail.local
```

A basic configuration might look conceptually like:

```ini
[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
```

The exact settings should be adapted to your environment.

---

# 20. Why `jail.local`?

Think:

```text
/etc/fail2ban/jail.conf
       ↓
Default/package configuration

/etc/fail2ban/jail.local
       ↓
Your local customization
```

This separation makes maintenance much easier.

```bash

```

You may get:

```text

```

This means:

```text

   │
```

# 22. Inspect a Specific Jail

Run:

```bash
sudo fail2ban-client status sshd
```

You may see:

```text
Status for the jail: sshd
|- Filter
|  |- Currently failed: ...
|  `- Total failed: ...
`- Actions
   |- Currently banned: ...
   `- Total banned: ...
```

This is one of the most useful Fail2ban commands.

---

# 23. Understanding the Status

Suppose:

```text
Currently failed: 2
Total failed: 17
Currently banned: 1
Total banned: 4
```

This tells you:

```text
2 → currently tracked failures
17 → total matching failures
1 → currently banned address
4 → total bans triggered
```

This becomes useful during security investigations.

---

# 24. View Banned IPs

Depending on the installed Fail2ban version:

```bash
sudo fail2ban-client status sshd
```

may show:

```text
Banned IP list:
203.0.113.20
```

This tells you which addresses are currently blocked by that jail.

---

# 25. Manually Ban an IP

You can manually ban an address:

```bash
sudo fail2ban-client set sshd banip 203.0.113.20
```

Then check:

```bash
sudo fail2ban-client status sshd
```

This is useful for testing.

### ⚠️ Don't ban your own current public IP on a remote server.

You could lock yourself out.

---

# 26. Manually Unban an IP

If an address was incorrectly banned:

```bash
sudo fail2ban-client set sshd unbanip 203.0.113.20
```

Then:

```bash
sudo fail2ban-client status sshd
```

For example:

```text

     ├── wrong password
     ├── wrong password
     └── ...

           Fail2ban
              ↓

```

This gives you practical experience without attacking a real service.

# 28. How Fail2ban Detects Attacks

Imagine your SSH log contains:

```text
Failed password for invalid user admin from 10.0.0.50
Failed password for invalid user test from 10.0.0.50
Failed password for root from 10.0.0.50
```

Fail2ban processes the logs:

```text
Log entry
   ↓
Filter
   ↓
Match?
   ↓
Count failure
   ↓
Threshold reached?
   ├── No → continue monitoring
   └── Yes → ban
```

---

# 29. Fail2ban Is Event-Driven

It doesn't simply ask:

> "Is this IP bad?"

Instead, it looks for:

```text
Repeated events
+
Within a time window
+
Matching a security pattern
```

This is why these three settings are so important:

```text
maxretry
findtime
bantime
```

---

# 30. The Three Numbers to Remember

Think:

```text
maxretry
    ↓
How many failures?

findtime
    ↓
Within how much time?

bantime
    ↓
How long should the ban last?
```

For example:

```text
maxretry = 5
findtime = 10m
bantime  = 1h
```

means conceptually:

```text
5 failures
within 10 minutes
       ↓
1-hour ban
```

# 32. Why SSH Keys + Fail2ban?

Someone might ask:

> "If password authentication is disabled, why do I still need Fail2ban?"

Good question.

SSH keys significantly reduce password brute-force risk.

But Fail2ban can still help against:

- repeated invalid-user attempts
    
- other authentication events
    
- misconfigured services
    
- exposed legacy authentication mechanisms
    
- application-level logs, depending on configuration
    

And it provides another layer.

Security isn't about one perfect control.

---

# 33. Fail2ban and Nginx

Fail2ban isn't limited to SSH.

You can create jails for services such as Nginx.

For example, you could detect patterns such as:

```text
Repeated authentication failures
Repeated malicious requests
Repeated probing
```

Then:

```text
Nginx logs
   ↓
Fail2ban filter
   ↓
Repeated suspicious IP
   ↓
Ban
```

This is especially useful when combined with your application logs.

---

# 34. Application Authentication + Fail2ban

Imagine your backend has:

```text
POST /api/login
```

An attacker repeatedly tries:

```text
admin/password1
admin/password2
admin/password3
...
```

Fail2ban can potentially be configured to consume appropriate application logs.

But don't automatically use Fail2ban as your main API rate limiter.

For a Node.js API, use application-level controls such as:

```text
Rate limiting
Account lockout strategy
CAPTCHA where appropriate
MFA
IP/device signals
Credential stuffing detection
```

Fail2ban is an additional infrastructure layer.

---

# 35. Fail2ban vs Rate Limiting

This distinction matters for your MERN development.

### Fail2ban

Usually:

```text
Logs
 ↓
Detect repeated abuse
 ↓
Firewall ban
```

### API rate limiting

Usually:

```text
Request
 ↓
Middleware
 ↓
Rate limit
 ↓
Allow / reject
```

For example:

```text
express-rate-limit
```

works at the application layer.

So:

```text
Firewall
+
Fail2ban
+
Nginx
+
API rate limiting
```

can provide multiple defensive layers.

# 36. Whitelisting

Suppose your production server has a trusted administrative IP:

```text
203.0.113.10
```

You might configure it as an ignored address.

But be careful.

Ask:

```text
Is the IP static?
Is it actually trusted?
Could it change?
Is it shared?
```

If your IP changes and you depend on it for SSH access, you can create an operational problem.

---

# 37. Don't Blindly Whitelist Your Entire Network

Avoid overly broad rules such as:

```text
10.0.0.0/8
```

unless you actually understand your private network architecture.

Likewise:

```text
0.0.0.0/0
```

means essentially everyone for IPv4.

Whitelisting should be:

> **As narrow as practical.**

---

# 38. Fail2ban and IPv6

Modern systems may have:

```text
IPv4
+
IPv6
```

Your Fail2ban configuration and firewall action should properly handle the address families you actually use.

Don't assume that protecting IPv4 automatically means IPv6 is protected.

This is another reason to audit:

```bash
ip -6 addr
```

and your firewall configuration.

# 43. Banning Doesn't Mean "Attacker Gone"

Suppose:

```text
203.0.113.20
```

is banned.

An attacker can potentially switch to:

```text
203.0.113.21
203.0.113.22
203.0.113.23
```

or use distributed infrastructure.

Therefore:

> Fail2ban is not a complete defense against distributed attacks.

It's a useful layer against repeated abusive behavior.

# 44. Distributed Brute Force

Imagine:

```text
IP 1 → 2 attempts
IP 2 → 2 attempts
IP 3 → 2 attempts
IP 4 → 2 attempts
...
```

Each individual IP might stay below your threshold.

This is why serious systems also use:

```text
MFA
Strong authentication
Rate limiting
Credential protection
IP reputation
WAF
Network controls
```

Fail2ban is only one tool.

```text

 ↓
```

```bash

```



But in production, understand the effect of your configuration change before restarting a security service.

# 49. Common Mistakes

## ❌ Mistake 1 — Whitelisting everyone

```text
ignoreip = 0.0.0.0/0
```

This destroys the value of the jail.

---

## ❌ Mistake 2 — Blocking yourself

Your own IP can be banned.

Always keep another administrative path available when testing production systems.

---

## ❌ Mistake 3 — Editing `jail.conf`

Use:

```text
jail.local
```

or:

```text
jail.d/*.conf
```

for local customization.

---

## ❌ Mistake 4 — Assuming Fail2ban replaces a firewall

It doesn't.

Fail2ban generally works by creating enforcement actions through firewall/network mechanisms.

---

## ❌ Mistake 5 — Using extremely aggressive thresholds

For example:

```text
maxretry = 1
```

could create unnecessary bans and false positives.

---

# 50. False Positives

Imagine:

```text
maxretry = 3
```

and you accidentally type the wrong password three times.

You might get banned.

Now imagine a shared office IP:

```text
100 developers
      ↓
One public IP
```

If one person behaves badly, a ban could affect everyone.

This is why thresholds and whitelists must be designed carefully.


You still need:


# 58. Interview Questions

### Q1. What is Fail2ban?

Fail2ban is an intrusion-prevention tool that monitors logs for repeated suspicious activity and can temporarily block offending sources through firewall/network actions.

---

### Q2. Is Fail2ban a firewall?

No.

It detects suspicious behavior and can use firewall mechanisms to enforce temporary bans.

---

### Q3. What is a jail?

A configuration that defines how Fail2ban monitors a service, detects failures, and responds to them.

---

### Q4. What does `maxretry` mean?

The number of matching failures allowed before the configured ban action is triggered within the relevant time window.

---

### Q5. What does `findtime` mean?

The time window during which Fail2ban counts matching failures.

---

### Q6. What does `bantime` mean?

How long a source remains banned.

---

### Q7. Why shouldn't you edit `jail.conf` directly?

Because it's generally package-provided default configuration. Local changes should be placed in `jail.local` or appropriate `jail.d` configuration files so they survive updates more reliably.

---

### Q8. Does Fail2ban protect against all attacks?

No.

It mainly helps with repeated recognizable patterns in logs. It does not replace secure application design, patching, authentication, authorization, firewalls, rate limiting, or monitoring.
