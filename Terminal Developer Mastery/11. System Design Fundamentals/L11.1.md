# Lesson 11.1 — Introduction to System Design ⭐⭐⭐⭐⭐

> **Goal:** Understand what system design actually means and learn the fundamental concepts used to design scalable backend systems.

---

# 1. What Is System Design?

**System design is the process of deciding how different components of a software system will work together to satisfy requirements.**

For example, imagine you're asked:

> "Build a URL shortener like Bitly."

A beginner might think:

```text
URL → Database → Short URL
```

But a production system has many more questions:

```text
                    ┌──────────────┐
                    │    Client    │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ Load Balancer│
                    └──────┬───────┘
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
        ┌─────────┐   ┌─────────┐   ┌─────────┐
        │ Server 1│   │ Server 2│   │ Server 3│
        └────┬────┘   └────┬────┘   └────┬────┘
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                      ┌────────┐
                      │ Redis  │
                      └────┬───┘
                           │
                           ▼
                    ┌────────────┐
                    │  Database  │
                    └────────────┘
```

Now we have to answer:

- What happens if 1,000 users arrive at once?
    
- What happens if 1 million users arrive?
    
- What happens if a server crashes?
    
- How do we make URLs load quickly?
    
- How do we prevent database overload?
    
- How do we handle duplicate requests?
    
- How do we store billions of URLs?
    
- How do we monitor failures?
    
- How do we secure the API?
    

**System design is about answering these questions before building the system.**

---

# 2. System Design Is More Than Architecture Diagrams

A common misconception is:

> System design = drawing boxes.

Not really.

A good system design involves:

```text
Requirements
      ↓
Capacity Estimation
      ↓
Architecture
      ↓
Database Design
      ↓
API Design
      ↓
Caching
      ↓
Scalability
      ↓
Reliability
      ↓
Security
      ↓
Monitoring
      ↓
Trade-offs
```

The architecture diagram is just the **visual representation** of these decisions.

---

# 3. Functional Requirements

The first thing you should ask when designing a system is:

> **What should the system do?**

These are called **functional requirements**.

They describe the actual features of the system.

### Example: URL Shortener

Functional requirements might be:

1. User can submit a long URL.
    
2. System generates a short URL.
    
3. User can access the short URL.
    
4. System redirects to the original URL.
    
5. User can view click statistics.
    

For example:

```text
POST /api/urls

{
    "url": "https://example.com/very/long/url"
}
```

Response:

```json
{
    "shortUrl": "https://short.ly/aB92x"
}
```

Then:

```text
GET /aB92x
```

produces:

```text
302 Redirect
        ↓
https://example.com/very/long/url
```

These are functional requirements because they describe **what the system does**.

---

# 4. Non-Functional Requirements

Now consider another question:

> **How should the system behave?**

These are **non-functional requirements**.

They don't describe features directly.

Instead, they describe qualities such as:

- performance
    
- scalability
    
- reliability
    
- availability
    
- security
    
- maintainability
    

For our URL shortener:

```text
Functional:

Create short URL
Redirect short URL
Track clicks


Non-functional:

Response < 100 ms
99.99% availability
Support millions of users
Secure APIs
Handle traffic spikes
```

This distinction is extremely important in system design interviews.

---

# 5. Functional vs Non-Functional

Think about an e-commerce application.

### Functional requirements

```text
User registration
Login
Product search
Add to cart
Place order
Make payment
Track order
```

### Non-functional requirements

```text
Search should be fast
System should support millions of users
Payment must be reliable
Passwords must be secure
System should remain available during failures
```

A simple way to remember:

> **Functional = What the system does**

> **Non-functional = How well the system does it**

---

# 6. Scalability

One of the most important system-design concepts is **scalability**.

Scalability means:

> **The ability of a system to handle increasing workload by adding resources or improving architecture.**

Suppose your application currently handles:

```text
1,000 requests/sec
```

Then your application becomes popular.

Traffic grows:

```text
10,000 requests/sec
```

Then:

```text
100,000 requests/sec
```

A scalable architecture should allow you to handle this growth.

---

# 7. Example of a Non-Scalable Architecture

Imagine:

```text
Users
  ↓
Node.js Server
  ↓
MongoDB
```

Initially:

```text
100 users
```

Everything works.

But eventually:

```text
1,000,000 users
```

Now one server may become overloaded.

```text
              1,000,000 users
                     │
                     ▼
              ┌─────────────┐
              │ Node Server │ 💥
              └──────┬──────┘
                     │
                     ▼
                  MongoDB
                    💥
```

We need to introduce scalability mechanisms.

---

# 8. Horizontal Scaling

Instead of using one giant server:

```text
        Users
          ↓
      Server
```

we can use multiple servers:

```text
              Users
                │
                ▼
          Load Balancer
          /     |      \
         ↓      ↓       ↓
      Server  Server  Server
        1       2       3
```

Now traffic can be distributed.

This is called:

**Horizontal Scaling / Scale Out**

We'll study this deeply in Lesson 11.4.

---

# 9. Vertical Scaling

Another option is making one server more powerful.

For example:

```text
Before:

CPU:    2 cores
RAM:    4 GB


After:

CPU:    16 cores
RAM:    64 GB
```

This is called:

**Vertical Scaling / Scale Up**

We'll compare this with horizontal scaling later.

---

# 10. Availability

Availability means:

> **How often your system is operational and accessible when users need it.**

Imagine your application is unavailable for 1 hour every week.

That's bad for a production application.

A common availability target is:

```text
99.9%
```

or:

```text
99.99%
```

or even:

```text
99.999%
```

These are sometimes called **availability nines**.

---

# 11. The Famous Availability Numbers

Approximate downtime:

|Availability|Downtime/year|
|---|--:|
|99%|~3.65 days|
|99.9%|~8.76 hours|
|99.99%|~52.6 minutes|
|99.999%|~5.26 minutes|

Notice something interesting.

Going from:

```text
99%
```

to:

```text
99.9%
```

is a big improvement.

But going from:

```text
99.99%
```

to:

```text
99.999%
```

can become very expensive.

That's why system design involves **trade-offs**.

---

# 12. Reliability

Reliability means:

> **The system continues to behave correctly even when failures happen.**

Failures are normal.

For example:

```text
Server crashes
Database becomes unavailable
Network request times out
Redis crashes
Message queue becomes unavailable
Disk fails
```

A reliable system is designed assuming:

> **Something will eventually fail.**

For example:

```text
Server 1
   ❌

Server 2
   ✅

Server 3
   ✅
```

If the load balancer detects Server 1 is dead, traffic can go to Servers 2 and 3.

That's fault tolerance.

We'll study this deeply in Lesson 11.13.

---

# 13. Reliability vs Availability

These concepts are related but not identical.

### Availability

> Is the system accessible?

### Reliability

> Does the system behave correctly and consistently?

Example:

A payment API returns:

```text
HTTP 200 OK
```

but the payment wasn't actually processed.

The service was technically **available**, but it wasn't **reliable**.

---

# 14. Maintainability

Imagine you have a backend with:

```text
50,000 lines
```

and everything is inside:

```text
server.js
```

You might be able to run it.

But changing one feature could break five others.

That's poor maintainability.

A maintainable system should have:

```text
Controllers
Services
Repositories
Database
Queues
Cache
Utilities
Monitoring
```

with clear responsibilities.

This connects directly with the layered architecture you've been learning.

---

# 15. Performance

Performance describes how quickly the system responds and processes work.

Important metrics include:

### Latency

How long does one request take?

```text
Request → Server → Response

        80 ms
```

### Throughput

How much work can the system process?

For example:

```text
10,000 requests/sec
```

### Resource utilization

How much CPU, memory, network, and database capacity are being used?

```text
CPU:     72%
Memory:  65%
Disk:    80%
```

Performance becomes especially important when designing large systems.

---

# 16. System Design Is About Trade-offs

This is one of the **most important ideas in system design**.

There is rarely a perfect architecture.

You usually choose one advantage at the cost of another.

For example:

```text
More caching
    ↓
Faster reads
    ↓
But
    ↓
More complexity
    +
Cache invalidation problem
```

Another:

```text
More replicas
    ↓
Better availability
    ↓
But
    ↓
Higher infrastructure cost
```

Another:

```text
Microservices
    ↓
Independent scaling
    ↓
But
    ↓
More operational complexity
```

A good system designer doesn't say:

> "This architecture is perfect."

Instead:

> "Given these requirements, this design provides the best trade-off."

---

# 17. A Simple System Design Mindset

Whenever you receive a system-design problem, think:

```text
1. What are we building?
        ↓
2. Who will use it?
        ↓
3. What features are required?
        ↓
4. How much traffic?
        ↓
5. How much data?
        ↓
6. What architecture?
        ↓
7. What database?
        ↓
8. Do we need caching?
        ↓
9. How do we scale?
        ↓
10. What happens when something fails?
        ↓
11. How do we secure it?
        ↓
12. What are the trade-offs?
```

This process will become your **system-design framework**.

Let's apply today's concepts.

Suppose we have:

```text

  ↓

Short URL
  ↓

  ↓
```

### Functional requirements

```text
Create short URL

```

### Non-functional requirements

```text
Low latency

Maintainable
```

### Possible architecture

```text
                         Users
                           │
                           ▼
                    ┌─────────────┐
                    │ Load Balancer│
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
          Node.js       Node.js      Node.js
           Server        Server       Server
              │            │            │
              └────────────┼────────────┘
```

```text
                    Message Queue
```

```text

  ↓

  ↓

```

# 19. Architecture Evolution

A real application usually doesn't start with 20 components.

It may begin as:

```text
Browser
   ↓
Node.js
   ↓
MongoDB
```

Then growth introduces:

### Stage 1

```text
Node.js → MongoDB
```

### Stage 2

```text
Load Balancer
      ↓
Node.js × 3
      ↓
MongoDB
```

### Stage 3

```text
Load Balancer
      ↓
Node.js × 5
      ↓
Redis
      ↓
MongoDB
```

### Stage 4

```text
Load Balancer
      ↓
API Servers
   ↙       ↘
Redis    Message Queue
   ↓          ↓
MongoDB    Workers
```

### Stage 5

Eventually:

```text
                 CDN
                  │
                  ▼
            Load Balancer
                  │
          ┌───────┴───────┐
          ▼               ▼
       API Servers    API Servers
          │               │
          └───────┬───────┘
                  │
          ┌───────┴────────┐
          ▼                ▼
        Redis          Message Queue
          │                │
          ▼                ▼
      DB Cluster         Workers
```

**This is an important mindset: don't add infrastructure just because it sounds advanced.**

Add a component because you have a problem that component solves.

# 20. Key Terms to Remember

You should be comfortable with these terms after today's lesson:

|Term|Simple Meaning|
|---|---|
|System Design|Planning how system components work together|
|Functional Requirement|What the system should do|
|Non-functional Requirement|How the system should behave|
|Scalability|Ability to handle increasing workload|
|Availability|System is accessible when needed|
|Reliability|System behaves correctly despite failures|
|Maintainability|Easy to understand, modify and operate|
|Latency|Time taken to respond|
|Throughput|Amount of work processed per second|
|Trade-off|Giving up one benefit to gain another|
|Bottleneck|Component limiting overall performance|
|Fault Tolerance|Ability to continue despite failures|

# 21. Interview Perspective 🎯

Suppose an interviewer asks:

> **"Design a URL shortener."**

Don't immediately start drawing:

```text
Load Balancer
Redis
Kafka
MongoDB
Kubernetes
```

That is a common beginner mistake.

Instead start with:

> "Before designing the architecture, I'd like to clarify the functional and non-functional requirements."

Then ask:

```text
How many users?
How many URLs?
Read/write ratio?
Expected RPS?
How long should URLs live?
Do we need analytics?
What availability do we need?
What latency is acceptable?
```

**Then** design the architecture.

That's the professional approach.

---

# 22. Important Rule ⭐

Remember this:

> **Requirements drive architecture.**

Not:

> Architecture drives requirements.

For example:

If your application has:

```text
1,000 users
```

you probably don't need:

```text
Kafka
Kubernetes
20 microservices
Multi-region databases
```

But if you have:

```text
100 million users
```

the requirements may justify much more sophisticated infrastructure.
