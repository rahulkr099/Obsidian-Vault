# Lesson 11.11 — Consistency Models ⭐⭐⭐⭐⭐

> **Goal:** Understand how distributed systems decide **when a write becomes visible to reads**, what "strong consistency" and "eventual consistency" really mean, how replication lag causes stale reads, how quorum works, and how to choose the right consistency model for a backend system.

This lesson directly continues from **Lesson 11.10 — CAP Theorem**.

The key difference is:

> **CAP tells us about the trade-off during network partitions. Consistency models tell us what guarantees users get when they read and write data.**

---

# 1. Why Do We Need Consistency Models?

Imagine we have:

```text
                Application
                     │
              ┌──────┴──────┐
              ▼             ▼
           Primary       Replica
              │             │
              └─────┬───────┘
                    │
               Replication
```

Suppose the primary has:

```text
balance = 1000
```

A user updates it:

```text
balance = 500
```

The primary immediately has:

```text
500
```

But the replica might temporarily still have:

```text
1000
```

Now:

```text
User → Read → Replica
```

What should the user see?

```text
500?
```

or:

```text
1000?
```

The answer depends on the **consistency model**.

---

# 2. Consistency Model — Simple Definition

A consistency model defines:

> **What a system guarantees about the order and visibility of reads and writes across distributed nodes.**

In simple words:

> **After I write something, when can I expect other reads to see it?**

This is extremely important in distributed systems.

---

# 3. The Basic Models

We'll focus on:

```text
Consistency Models
        │
        ├── Strong Consistency
        │
        ├── Eventual Consistency
        │
        ├── Read-After-Write
        │
        ├── Monotonic Reads
        │
        └── Quorum-Based Consistency
```

There are many more formal models, but these are the most useful for backend/system-design interviews.

---

# 4. Strong Consistency

Strong consistency means, roughly:

> **Once a write is successfully committed, subsequent reads observe that latest value according to the system's guarantee.**

Example:

```text
Initial:
balance = ₹1000
```

Write:

```text
balance = ₹500
```

Then:

```text
Read → ₹500
```

not:

```text
Read → ₹1000
```

assuming the read is covered by the same consistency guarantee.

---

# 5. Strong Consistency Example

Imagine a banking system.

```text
Account balance:
₹10,000
```

User withdraws:

```text
₹3,000
```

New balance:

```text
₹7,000
```

Immediately checking the balance should return:

```text
₹7,000
```

rather than an old value.

For financial operations, strong consistency is often important.

---

# 6. Strong Consistency Architecture

One possible approach:

```text
Client
  │
  ▼
Primary
  │
  ├── Replica 1
  └── Replica 2
```

The system may only acknowledge a write after enough replicas have confirmed it, depending on its configuration.

Then:

```text
Write
  ↓
Replication
  ↓
Required acknowledgement
  ↓
Success
```

This can increase consistency but may increase latency or reduce availability during failures.

---

# 7. Eventual Consistency

Eventual consistency means:

> **If no new updates occur and the system continues operating, replicas will eventually converge to the same value.**

Example:

```text
T1:

Primary  → 100
Replica  → 100
```

Write:

```text
T2:

Primary  → 200
Replica  → 100
```

After replication:

```text
T3:

Primary  → 200
Replica  → 200
```

The replica was temporarily stale.

---

# 8. Eventual Consistency Doesn't Mean "Random Data"

A common misunderstanding is:

> "Eventual consistency means anything can happen."

No.

It means the system provides weaker timing guarantees for visibility.

There are still usually rules around:

- replication
    
- ordering
    
- conflict resolution
    
- convergence
    

The exact guarantees depend on the system.

---

# 9. Where Eventual Consistency Is Useful

Examples:

```text
Social media likes
View counts
Analytics
Recommendations
Search indexes
Notifications
Activity feeds
```

Suppose:

```text
Like count = 10,000
```

and one replica temporarily says:

```text
10,001
```

while another says:

```text
10,000
```

A delay of a fraction of a second may be perfectly acceptable.

---

# 10. Strong vs Eventual Consistency

|Feature|Strong|Eventual|
|---|---|---|
|Latest value immediately visible|Yes, within guarantee|Not necessarily|
|Stale reads|Generally not allowed by guarantee|Possible|
|Latency|Often higher|Can be lower|
|Availability during failures|May be reduced|Often prioritized|
|Complexity|Coordination required|Reconciliation may be needed|
|Example|Financial state|Analytics|

Remember:

> **Eventual consistency isn't "bad consistency." It's a deliberate trade-off.**

---

# 11. Replication Lag

This is one of the biggest causes of consistency problems.

Suppose:

```text
Primary
  │
  │ replication
  ▼
Replica
```

Write:

```text
Primary:
balance = 500
```

But replication takes:

```text
100 ms
```

During those 100 ms:

```text
Primary → 500
Replica → 1000
```

That difference is:

> **Replication lag**

---

# 12. Why Replication Lag Happens

Possible reasons:

```text
Network latency
High write volume
Replica CPU overload
Disk I/O
Large transactions
Replication queue backlog
Database contention
```

For example:

```text
Primary
   │
   │ 50,000 writes/sec
   ▼
Replication stream
   │
   ▼
Replica
```

If the replica can only process:

```text
40,000 writes/sec
```

the lag can grow.

---

# 13. Replication Lag Example

Suppose:

```text
Primary:
10:00:00 → order created
```

Replica receives it:

```text
10:00:02
```

Replication lag:

```text
2 seconds
```

If your application reads from the replica at:

```text
10:00:01
```

the order may not exist there yet.

---

# 14. Read-After-Write Consistency

This is extremely important for web applications.

Read-after-write consistency means:

> **After a client successfully writes data, that client should be able to read the value it just wrote.**

Example:

```text
POST /profile
name = Rahul
```

returns:

```text
200 OK
```

Then immediately:

```text
GET /profile
```

should return:

```json
{
  "name": "Rahul"
}
```

not the old name.

---

# 15. Read-After-Write Problem

Suppose:

```text
POST /profile
      ↓
Primary
      ↓
name = Rahul
```

Then:

```text
GET /profile
      ↓
Replica
      ↓
name = Amit
```

The user sees:

```text
Amit
```

even though their update succeeded.

That's a terrible user experience.

---

# 16. Solution 1 — Read From Primary

After a write:

```text
Write → Primary
Read  → Primary
```

This gives a strong guarantee if the primary's behavior provides it.

For example:

```text
POST /profile
      ↓
Primary

GET /profile
      ↓
Primary
```

The downside:

```text
Primary
   ↓
More read traffic
```

which can reduce the benefit of read replicas.

---

# 17. Solution 2 — Sticky Reads

You can temporarily route a user's reads to the same node that processed their write.

Conceptually:

```text
User
  ↓
Primary
  ↓
Write
```

Then:

```text
User
  ↓
Same primary
  ↓
Read
```

This is sometimes called:

> **Session stickiness / sticky reads**

However, implementation depends on the architecture and can introduce load-balancing complexity.

---

# 18. Solution 3 — Wait for Replication

Another approach:

```text
Write
  ↓
Primary
  ↓
Wait until required replicas confirm
  ↓
Success
```

Now the system has stronger guarantees that replicas have the write.

But:

```text
More coordination
       ↓
Higher latency
```

---

# 19. Solution 4 — Accept Eventual Consistency

Sometimes you don't need to solve the problem.

For example:

```text
POST /like
```

returns:

```text
Success
```

and the displayed count might update slightly later.

That's fine.

You can design the application around eventual consistency.

---

# 20. Monotonic Reads

Here's another useful consistency guarantee.

> **Once a client has seen a newer version of data, it should not later see an older version.**

Example:

First request:

```text
Read → version 5
```

Later request should not return:

```text
version 4
```

because that feels like the system is going backward.

Bad experience:

```text
Request 1 → 100 likes
Request 2 → 105 likes
Request 3 → 101 likes ❌
```

Monotonic reads aim to prevent this kind of regression.

---

# 21. Why Monotonic Reads Matter

Imagine you're scrolling through a social feed.

Request 1:

```text
Posts through ID 500
```

Request 2:

```text
Posts through ID 520
```

Then suddenly:

```text
Posts through ID 510
```

The user may see data disappear or move backward.

Consistency guarantees can help avoid these confusing experiences.

---

# 22. Session Consistency

A useful way to think about user-facing consistency is:

> **What does one particular user experience across their requests?**

For example:

```text
Rahul writes:
name = Rahul
```

Rahul's subsequent reads should ideally reflect:

```text
name = Rahul
```

even if other users may temporarily observe something else.

This can be achieved through various architectures.

---

# 23. Quorum

Now let's connect this to distributed databases.

Suppose:

```text
N = 3 replicas
```

```text
Replica 1
Replica 2
Replica 3
```

A write might require:

```text
W = 2
```

replicas to acknowledge.

A read might require:

```text
R = 2
```

replicas to respond.

So:

```text
W + R > N
```

because:

```text
2 + 2 > 3
```

This creates overlap.

---

# 24. Why Quorum Works

Imagine a write:

```text
x = 100
```

requires two replicas:

```text
R1 → 100
R2 → 100
R3 → old
```

Then a read requests two replicas:

```text
R2
R3
```

At least one of them:

```text
R2 → 100
```

has the latest write.

The system can use versions/timestamps/metadata to determine the latest value.

---

# 25. Quorum Formula

For a simple quorum model:

```text
N = total replicas
W = write quorum
R = read quorum
```

A common condition for overlap is:

```text
W + R > N
```

For example:

```text
N = 5
W = 3
R = 3
```

Then:

```text
3 + 3 > 5
```

So read and write quorums overlap.

---

# 26. But Quorum Doesn't Automatically Mean Strong Consistency

Important!

A simple:

```text
W + R > N
```

is useful intuition, but real distributed systems need to account for:

- concurrent writes
    
- version ordering
    
- failures
    
- sloppy quorums
    
- hinted handoff
    
- conflict resolution
    
- leader-based replication
    
- network partitions
    

So don't say:

> "Quorum always guarantees strong consistency."

That's too simplistic.

---

# 27. Quorum and Availability

Suppose:

```text
N = 3
W = 3
```

All three replicas must respond.

If one fails:

```text
R1 ✅
R2 ✅
R3 ❌
```

the write may fail.

This improves consistency guarantees but reduces availability.

If instead:

```text
W = 1
```

the write can succeed even when replicas are unavailable.

But the system may provide weaker consistency guarantees.

This is the fundamental trade-off.

---

# 28. Consistency vs Availability vs Latency

In real system design, you're usually balancing:

```text
Consistency
     ↕
Availability
     ↕
Latency
```

Stronger consistency often requires:

```text
More coordination
      ↓
More network communication
      ↓
Potentially higher latency
```

Higher availability may mean:

```text
Allow reads/writes
even when some replicas are unreachable
```

which can produce stale data.

---

# 29. Linearizability

You may encounter a more formal consistency model:

> **Linearizability**

It means operations appear to happen atomically at a single point in time, respecting real-time ordering.

Suppose:

```text
Write x = 10
```

completes.

Then:

```text
Read x
```

must observe:

```text
10
```

if the read occurs afterward under the linearizable guarantee.

Think:

```text
Real world time
─────────────────────────────>

Write completes
       │
       ▼
Read begins
       │
       ▼
Read must see new value
```

Linearizability is a very strong consistency guarantee.

---

# 30. Sequential Consistency

Another model is:

> **Sequential consistency**

Operations appear in some sequential order that respects each client's operation order.

It doesn't necessarily provide the same real-time guarantees as linearizability.

For interview purposes:

```text
Linearizability
    ↓
Very strong
    ↓
Operations respect real-time ordering
```

You don't need to master formal proofs yet, but knowing the concept is useful.

---

# 31. Eventual Consistency vs Strong Consistency

Let's visualize.

### Strong:

```text
Write
  ↓
100
  ↓
All reads according to guarantee
see 100
```

### Eventual:

```text
Write
  ↓
Primary = 100
Replica = 90
  ↓
Replication
  ↓
Replica = 100
```

The second allows a temporary inconsistency window.

---

# 32. Consistency Window

The period during which replicas may disagree can be thought of as:

> **Consistency window**

Example:

```text
Write at:
10:00:00.000

Replica catches up:
10:00:00.150
```

Potential consistency window:

```text
150 ms
```

For some applications:

```text
150 ms
```

is perfectly fine.

For others:

```text
150 ms
```

could be unacceptable.

---

# 33. Read Your Own Writes

This is another useful guarantee.

Imagine:

```text
User updates profile
```

Then the same user reads it.

The user should see their own update.

This is essentially a user-centric consistency expectation related to read-after-write behavior.

Example:

```text
PUT /profile
name = Rahul
```

then:

```text
GET /profile
```

should return:

```text
Rahul
```

not:

```text
Amit
```

---

# 34. Causal Consistency

Another advanced concept is:

> **Causal consistency**

If operation B depends on operation A, users should not observe B before A in a causally contradictory way.

Example:

```text
Rahul creates post
      ↓
Amit comments on post
```

There is a causal relationship:

```text
Post → Comment
```

A user shouldn't normally see:

```text
Comment
```

without the:

```text
Post
```

that the comment refers to.

Causal consistency tries to preserve these relationships.

---

# 35. Why Causal Consistency Is Useful

Consider chat:

```text
Rahul:
"Hello"

Rahul:
"How are you?"
```

The second message causally follows the first.

A system shouldn't show:

```text
"How are you?"
```

before:

```text
"Hello"
```

because that violates the user's expected ordering.

---

# 36. Consistency Hierarchy

A rough mental model:

```text
Stronger
   │
   ├── Linearizable
   │
   ├── Sequential
   │
   ├── Causal
   │
   ├── Session guarantees
   │
   └── Eventual
   │
Weaker
```

This isn't a universal strict hierarchy for every formal definition, but it is useful as a conceptual map.

Different guarantees provide different trade-offs.

# 37. Consistency in MongoDB

MongoDB provides configurable:

```text
Read Concern
Write Concern
Read Preference
```

These influence how operations interact with replica sets.

---

# 38. Write Concern

Write concern controls how much acknowledgement MongoDB requires before considering a write successful.

Conceptually:

```javascript
{
    w: "majority"
}
```

means the write should be acknowledged by a majority according to MongoDB's semantics.

Another configuration could require fewer acknowledgements.

The trade-off is:

```text
More acknowledgement
       ↓
Potentially stronger durability/consistency behavior
       ↓
Potentially higher latency
```

---

# 39. Read Preference

MongoDB can route reads differently depending on read preference.

Conceptually:

```text
primary
primaryPreferred
secondary
secondaryPreferred
nearest
```

For example:

```text
primary
```

means:

```text
Read → Primary
```

While:

```text
secondaryPreferred
```

can prefer secondaries where appropriate.

This is useful for understanding:

> **Read scaling vs consistency.**

---

# 40. MongoDB Read Concern

Read concern controls the consistency/isolation properties of reads.

Examples include concepts such as:

```text
local
majority
snapshot
linearizable
```

The exact guarantees differ.

For system design, remember:

> **MongoDB doesn't have one single consistency behavior. You can configure consistency characteristics depending on your workload.**

# 41. PostgreSQL Read Replicas

Suppose:

```text
PostgreSQL Primary
      │
 ┌────┴────┐
 ▼         ▼
Replica 1 Replica 2
```

If application reads from replicas:

```text
GET /profile
   ↓
Replica
```

there can be replication lag.

So:

```text
Write → Primary
Read  → Replica
```

can produce stale data.

This is not unique to PostgreSQL.

It is a general distributed-system problem.

---

# 42. Pattern: Primary for Writes, Replica for Reads

Common architecture:

```text
                 Application
                /           \
             Write          Read
               │              │
               ▼              ▼
            Primary       Read Replica
               │
               └───────→ Replication
```

Advantages:

```text
Read scaling
Availability
```

Trade-off:

```text
Potential stale reads
```

---

# 43. Pattern: Read-After-Write Routing

You can implement:

```text
Write
 ↓
Primary
 ↓
Mark session as "recently written"
 ↓
Reads → Primary temporarily
```

After the replica catches up:

```text
Reads → Replicas
```

This is a sophisticated technique for balancing user experience and read scaling.

---

# 44. Pattern: Version-Based Reads

Another approach is to associate data with a version.

For example:

```text
Version = 42
```

Client says:

```text
"I need version >= 42"
```

A replica that only has:

```text
version = 40
```

isn't eligible.

The system waits or routes elsewhere.

This can provide stronger consistency without forcing every read to the primary.

Product data:

```text

```

Different fields may need different consistency.

### Description

Eventual consistency may be fine.

### Price

Stronger consistency is important.

### Stock

Very strong correctness may be required.

> **Consistency requirements can differ even within the same entity.**

# 46. Example: URL Shortener

Your URL shortener has:

```text

```

Different fields:

Needs to be correct.

A redirect to the wrong URL is a serious functional problem.

### clickCount

This is a great example of how one application can use different consistency requirements.

Suppose:

```text

```

Then:

```text
Order Service
      ↓
Queue
      ↓

```

The notification may arrive later.

# 49. Exactly-Once Is Difficult

In distributed systems, you often encounter:

```text
At-most-once
At-least-once
Exactly-once
```

### At-most-once

Message is processed:

```text
0 or 1 times
```

Possible message loss.

### At-least-once

Message is processed:

```text
1 or more times
```

Possible duplicates.

### Exactly-once

Ideally:

```text
Exactly 1 time
```

This is much harder to guarantee end-to-end.

This is why idempotent consumers are so important.

We'll revisit this in the message queue lesson.

---

# 50. Idempotency and Consistency

Suppose a payment event is delivered twice:

```text
payment.created
payment.created
```

Your consumer should ideally handle duplicates safely.

For example:

```text
if eventId already processed:
    ignore
else:
    process
    record eventId
```

This turns:

```text
At-least-once delivery
```

into something that can behave safely from the application's perspective.

---

# 51. Consistency vs Latency

Suppose you have:

```text
Region A
   │
   │ 100ms
   ▼
Region B
```

If every operation requires synchronous confirmation from both regions:

```text
Write
 ↓
Region A
 ↓
Region B
 ↓
ACK
```

the minimum latency can be affected by network round trips.

If instead:

```text
Write
 ↓
Region A
 ↓
ACK
 ↓
Async replication → Region B
```

you can respond faster.

But now:

```text
Region B
```

may temporarily have stale data.

This is the classic:

```text
Consistency ↔ Latency
```

trade-off.

# 54. Interview Question 🎯

### "What is eventual consistency?"

Strong answer:

> Eventual consistency means that after a successful update, replicas may temporarily return different or stale values, but if no new updates occur and the system continues operating, the replicas will eventually converge to the same state.

---

# 55. Interview Question 🎯

### "What is replication lag?"

Strong answer:

> Replication lag is the delay between a write becoming available on the primary and that change being applied or made visible on a replica. It can cause stale reads, particularly when writes go to a primary and subsequent reads are routed to replicas.

---

# 56. Interview Question 🎯

### "How do you solve read-after-write inconsistency?"

Possible answers:

> Route the relevant reads to the primary, use sticky/session-aware reads, wait for sufficient replication acknowledgement, or use version-aware routing. The right solution depends on the consistency requirement and acceptable latency.

Excellent answer.

---

# 57. Interview Question 🎯

### "What is quorum?"

Strong answer:

> Quorum is a replication strategy where a read or write must receive acknowledgements from a specified number of replicas. With `N` replicas, `W` write acknowledgements and `R` read acknowledgements, a common overlap condition is `W + R > N`, although the exact consistency guarantees depend on the database's replication and conflict-resolution semantics.

---

# 58. Interview Question 🎯

### "Strong consistency vs eventual consistency?"

Strong answer:

> Strong consistency provides a guarantee that reads observe the latest committed state according to the system's consistency model, while eventual consistency allows temporary stale or divergent reads but guarantees convergence if updates stop and the system remains healthy. Strong consistency generally requires more coordination and may increase latency or reduce availability during failures.

---

# 59. Common Beginner Mistakes ❌

### Mistake 1

> "Eventual consistency means bad data."

No.

It means data may temporarily be stale.

---

### Mistake 2

> "Read replicas always return the latest data."

No.

Replication lag can cause stale reads.

---

### Mistake 3

> "Quorum automatically guarantees strong consistency."

Not necessarily.

The exact replication semantics matter.

---

### Mistake 4

> "Strong consistency is always better."

No.

It can increase:

```text
Latency
Coordination
Cost
Failure sensitivity
```

---

### Mistake 5

> "Everything should eventually be consistent."

No.

Some data requires stronger guarantees.

---

### Mistake 6

> "CAP and consistency models are the same thing."

No.

CAP describes a distributed-system trade-off under partition.

Consistency models describe what read/write guarantees the system provides.

# 60. The Most Important Mental Model 🧠

Think about a distributed write:

```text
                    WRITE
                      │
                      ▼
                   Primary
                      │
              ┌───────┴───────┐
              ▼               ▼
          Replica A        Replica B
              │               │
           100ms lag        200ms lag
              │               │
              ▼               ▼
             READ            READ
```

The fundamental question is:

> **How much stale data are we willing to tolerate?**

If:

```text
0 stale data acceptable
```

you need stronger consistency.

If:

```text
200ms stale data acceptable
```

you can potentially use a more available/low-latency architecture.

---

# 61. Your System Design Rule ⭐

When designing any distributed system, don't simply say:

> "Use strong consistency."

Instead say:

> **"I'll use the weakest consistency model that still satisfies the business requirement."**

Why?

Because stronger consistency often costs:

```text
More coordination
+
More latency
+
Less availability during failures
```

If eventual consistency is good enough:

```text
Don't pay the cost of strong consistency unnecessarily.
```

This is a very mature system-design mindset.

# 🎯 Final Cheat Sheet

```text
Strong Consistency
→ Reads see latest committed state
→ Higher coordination
→ Useful for payments/inventory

Eventual Consistency
→ Temporary stale reads allowed
→ Replicas eventually converge
→ Useful for analytics/social features

Read-After-Write
→ User sees their own successful update

Monotonic Reads
→ User doesn't move backward to older data

Causal Consistency
→ Related operations preserve causal ordering

Quorum
→ R/W acknowledgements across replicas
→ W + R > N is a common overlap condition

Replication Lag
→ Delay between primary update and replica visibility
```

And the key sentence:

> **Use the weakest consistency guarantee that safely satisfies the business requirement.**
