# Lesson 11.13 — Fault Tolerance ⭐⭐⭐⭐⭐

> **Goal:** Learn how to design backend systems that continue working when components fail. You'll understand **single points of failure, redundancy, timeouts, retries, circuit breakers, bulkheads, graceful degradation, failover, and failure isolation**.

This is the beginning of **Part 5 — Reliability**.

So far you've learned how to scale systems:

```text
Part 2 → Scalability
Part 3 → Databases
Part 4 → Distributed Systems
```

Now we ask a more important production question:

> **"What happens when something breaks?"**

Because in production, something **will** break.

---

# 1. Failure Is Normal

A beginner designs:

```text
Client
  ↓
API
  ↓
Database
  ↓
Response
```

and assumes:

```text
Everything works ✅
```

A production engineer thinks:

```text
What if API crashes?
What if DB is slow?
What if Redis is unavailable?
What if network fails?
What if third-party API times out?
What if a server runs out of memory?
What if a deployment breaks?
What if a message is processed twice?
```

That's the mindset of:

> **Fault-tolerant system design**

---

# 2. What Is Fault Tolerance?

Fault tolerance means:

> **The system can continue providing acceptable functionality even when some components fail.**

For example:

```text
Server A ❌
Server B ✅
Server C ✅
```

The application continues:

```text
Users
  ↓
Load Balancer
  ├── Server A ❌
  ├── Server B ✅
  └── Server C ✅
```

Users may not even notice the failure.

---

# 3. Fault Tolerance vs Reliability

These concepts are related but not identical.

### Reliability

How consistently the system performs correctly over time.

### Fault tolerance

How well the system continues functioning when failures occur.

Think:

```text
Reliability
    ↓
System works correctly

Fault tolerance
    ↓
System continues working when something fails
```

---

# 4. The Most Important Concept: Assume Failure

A strong system designer assumes:

```text
Network → can fail
Server → can fail
Database → can fail
Disk → can fail
Cache → can fail
External API → can fail
Deployment → can fail
```

Instead of:

> "This won't happen."

Think:

> **"When this happens, what will the system do?"**

That's a major shift in engineering thinking.

---

# 5. Single Point of Failure

A:

> **Single Point of Failure (SPOF)**

is a component whose failure can bring down the entire system.

Example:

```text
Users
  ↓
Single API Server
  ↓
Database
```

If:

```text
API Server ❌
```

then:

```text
Application ❌
```

The API server is a single point of failure.

---

# 6. Removing a Single Point of Failure

Instead:

```text
             Load Balancer
                  │
          ┌───────┼───────┐
          ▼       ▼       ▼
        API 1   API 2   API 3
```

Now:

```text
API 1 ❌
```

doesn't necessarily bring down the system.

Traffic can go to:

```text
API 2
API 3
```

This is:

> **Redundancy**

---

# 7. Redundancy

Redundancy means:

> **Having additional resources that can take over when another resource fails.**

Examples:

```text
2+ API servers
2+ database replicas
Multiple availability zones
Multiple network paths
Multiple workers
Backup storage
Multiple cache nodes
```

Basic idea:

```text
Primary
   │
   └── Backup
```

More resilient:

```text
Primary
  │
  ├── Backup 1
  └── Backup 2
```

---

# 8. Redundancy Isn't Free

More redundancy means:

```text
More servers
More infrastructure
More cost
More networking
More operational complexity
```

So don't blindly create:

```text
100 servers
```

for a system serving:

```text
100 users
```

Design according to:

```text
Availability requirement
Traffic
Budget
Business impact
Failure tolerance
```

---

# 9. N+1 Redundancy

A common strategy is:

> **N+1 redundancy**

Suppose you need:

```text
3 servers
```

to handle normal traffic.

Instead of deploying exactly 3:

```text
N = 3
```

deploy:

```text
N + 1 = 4
```

Now if one fails:

```text
Server 1 ❌
Server 2 ✅
Server 3 ✅
Server 4 ✅
```

you still have enough capacity.

---

# 10. Active-Passive

Architecture:

```text
Primary
   ↓
Active

Secondary
   ↓
Standby
```

Only the primary handles traffic.

If it fails:

```text
Primary ❌
    ↓
Failover
    ↓
Secondary becomes active
```

Advantages:

```text
Simple
Easy consistency model
Good for some stateful systems
```

Disadvantages:

```text
Standby resources may be underutilized
Failover can take time
Failover itself can fail
```

---

# 11. Active-Active

Both instances handle traffic:

```text
        Load Balancer
          /       \
         ▼         ▼
      Server A  Server B
         ▲         ▲
         └────┬────┘
              │
           Database
```

If:

```text
Server A ❌
```

Server B continues serving.

Advantages:

```text
Better resource utilization
Fast failover
Higher availability
```

Disadvantages:

```text
More complex
State synchronization
Conflict handling
More complicated deployments
```

---

# 12. Health Checks

How does a load balancer know whether a server is healthy?

Health checks.

For example:

```http
GET /health
```

Healthy:

```json
{
  "status": "ok"
}
```

Unhealthy:

```text
HTTP 500
```

The load balancer can stop sending traffic to unhealthy instances.

---

# 13. Liveness vs Readiness

In containerized systems, especially Kubernetes, these concepts are important.

### Liveness

> Is the process alive?

```text
Process running?
```

If not:

```text
Restart it.
```

### Readiness

> Is the service ready to receive traffic?

For example:

```text
Server process → running
Database connection → not ready
```

The process is alive but shouldn't receive requests yet.

---

# 14. Why Readiness Matters

Imagine deployment:

```text
New API Server
     ↓
Starts
     ↓
Still connecting to DB
```

If load balancer immediately sends traffic:

```text
Request
  ↓
New server
  ↓
DB not ready ❌
```

Readiness checks prevent this.

---

# 15. Timeouts ⏱️

One of the most important reliability techniques:

> **Never wait forever.**

Suppose your Node.js API calls:

```text
Payment Service
```

and the payment service hangs.

Without timeout:

```text
Request
 ↓
Payment API
 ↓
...
 ↓
...
 ↓
...
```

Your connection stays occupied.

Enough requests like this can exhaust server resources.

---

# 16. Timeout Example

Set:

```text
timeout = 5 seconds
```

Then:

```text
Request
 ↓
Payment API
 ↓
5 seconds
 ↓
Timeout ❌
```

Your backend can then:

```text
Return controlled error
Retry
Fallback
Queue work
```

instead of waiting forever.

---

# 17. Types of Timeouts

You can have:

```text
Connection timeout
Request timeout
Read timeout
Write timeout
Database timeout
Queue timeout
```

For example:

```text
API
 ↓
DB query
 ↓
timeout = 2 seconds
```

If the database doesn't respond:

```text
Stop waiting
```

---

# 18. Timeout Is Not Failure Prevention

A timeout doesn't make the downstream service healthy.

It simply prevents:

```text
One slow dependency
        ↓
Unlimited waiting
        ↓
Resource exhaustion
```

So think of timeout as:

> **Failure containment**

---

# 19. Retry

If a temporary failure occurs:

```text
Request
 ↓
Service
 ↓
Timeout ❌
```

you might retry:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ✅
```

Retries are useful for transient failures.

Examples:

```text
Temporary network failure
Temporary database connection issue
503 from external service
Transient cloud error
```

---

# 20. Don't Retry Everything

Suppose:

```text
POST /payment
```

fails because:

```text
Card declined
```

Retrying won't fix it.

Similarly:

```text
400 Bad Request
```

shouldn't normally be retried.

So distinguish:

```text
Transient failure
       vs
Permanent failure
```

---

# 21. Retryable vs Non-Retryable Errors

### Usually retryable

```text
Timeout
503 Service Unavailable
Temporary network failure
429 Too Many Requests
```

### Usually not retryable

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
Validation failure
Business-rule rejection
```

There are exceptions, so your API contract matters.

---

# 22. Exponential Backoff

Never do:

```text
Retry
Retry
Retry
Retry
```

immediately.

Instead:

```text
Attempt 1 → 1 sec
Attempt 2 → 2 sec
Attempt 3 → 4 sec
Attempt 4 → 8 sec
```

This is:

> **Exponential backoff**

---

# 23. Add Jitter

Imagine 10,000 workers fail at exactly:

```text
12:00:00
```

If all retry at:

```text
12:00:01
```

you get another traffic spike.

Instead:

```text
Worker 1 → 1.2s
Worker 2 → 1.7s
Worker 3 → 0.9s
Worker 4 → 1.4s
```

This random variation is:

> **Jitter**

A common production pattern is:

```text
Exponential Backoff + Jitter
```

---

# 24. The Retry Storm

Consider:

```text
1000 API servers
      ↓
External Service ❌
```

All retry:

```text
1000 requests
 ↓
1000 retries
 ↓
1000 retries
```

The external service becomes even more overloaded.

This is:

> **Retry storm**

Retries must therefore be limited and controlled.

---

# 25. Maximum Retry Count

Example:

```text
maxRetries = 3
```

Flow:

```text
Attempt 1 ❌
   ↓
Wait
   ↓
Attempt 2 ❌
   ↓
Wait
   ↓
Attempt 3 ❌
   ↓
Give up
```

Then:

```text
Fallback
or
Queue
or
Error response
```

---

# 26. Circuit Breaker 🔌

Now we reach one of the most important reliability patterns.

Imagine:

```text
Your API
   ↓
Payment Service
```

Payment service is completely down.

Your API keeps sending:

```text
Request
Request
Request
Request
Request
...
```

and repeatedly times out.

This wastes resources.

A:

> **Circuit breaker**

can stop calls temporarily.

---

# 27. Circuit Breaker States

A circuit breaker usually has three states:

```text
CLOSED
   ↓
OPEN
   ↓
HALF-OPEN
```

---

# 28. CLOSED

Everything is normal.

```text
Your Service
    ↓
Payment Service
    ↓
Success
```

Circuit:

```text
CLOSED
```

Requests flow normally.

---

# 29. OPEN

Suppose failures become excessive:

```text
Failure
Failure
Failure
Failure
Failure
```

Circuit opens:

```text
Your Service
    X
Payment Service
```

Requests are blocked immediately.

Instead of waiting for timeouts:

```text
Fast failure
```

---

# 30. HALF-OPEN

After some recovery period:

```text
OPEN
 ↓
wait
 ↓
HALF-OPEN
```

The circuit allows a small number of test requests.

If successful:

```text
HALF-OPEN
    ↓
Success
    ↓
CLOSED
```

If failures continue:

```text
HALF-OPEN
    ↓
Failure
    ↓
OPEN
```

---

# 31. Circuit Breaker Diagram

```text
             ┌───────────┐
             │  CLOSED   │
             └─────┬─────┘
                   │
             failures exceed
                threshold
                   │
                   ▼
             ┌───────────┐
             │   OPEN    │
             └─────┬─────┘
                   │
              wait period
                   │
                   ▼
             ┌───────────┐
             │ HALF-OPEN │
             └─────┬─────┘
                success?
              /         \
            yes          no
             │            │
             ▼            ▼
          CLOSED        OPEN
```

---

# 32. Circuit Breaker vs Retry

These are complementary.

### Retry

```text
Temporary failure?
       ↓
Try again
```

### Circuit breaker

```text
Repeated failures?
       ↓
Stop calling temporarily
```

You often combine:

```text
Timeout
+
Retry
+
Circuit Breaker
```

---

# 33. Example

Suppose:

```text
Payment API timeout = 2s
Max retries = 2
Circuit threshold = 5 failures
```

Request:

```text
Attempt 1 → timeout
Attempt 2 → timeout
```

After repeated failures:

```text
Circuit opens
```

Future requests immediately receive:

```text
Payment service temporarily unavailable
```

instead of waiting 4 seconds each.

---

# 34. Graceful Degradation

Another powerful concept:

> **When a dependency fails, provide reduced functionality instead of total failure.**

Example:

```text
E-commerce homepage
```

Dependencies:

```text
Products
Recommendations
Reviews
Analytics
```

Suppose recommendation service fails.

Bad design:

```text
Recommendations ❌
      ↓
Entire homepage ❌
```

Better:

```text
Recommendations ❌
      ↓
Show popular products instead
```

That's graceful degradation.

---

# 35. Example: Your LMS

Suppose your LMS has:

```text
Course page
```

Dependencies:

```text
Course database
Video service
Recommendation service
Analytics service
```

If analytics is down:

```text
Course page
     ↓
Course loads ✅
Video loads ✅
Analytics ❌
```

Don't break the course page just because analytics is unavailable.

---

# 36. Critical vs Non-Critical Dependencies

Classify dependencies.

### Critical

```text
Authentication
Payment
Order creation
Core database
```

Failure may prevent the operation.

### Non-critical

```text
Analytics
Recommendations
Metrics
Some notifications
```

Failure shouldn't necessarily block the user.

This classification is extremely useful.

---

# 37. Bulkhead Pattern

Imagine a ship:

```text
██████████████████
│ Room 1 │ Room 2 │
██████████████████
```

If one compartment floods:

```text
Room 1 → flooded
```

the whole ship doesn't sink.

In software:

> **Bulkheads isolate resources so one failure doesn't consume everything.**

---

# 38. Example of Bulkheads

Suppose your API handles:

```text
Payment requests
Image processing
Search
Notifications
```

Without isolation:

```text
Image processing overload
        ↓
All threads/workers consumed
        ↓
Payment requests fail too
```

With separate pools:

```text
Payment Pool      → 10 workers
Image Pool        → 20 workers
Notification Pool → 5 workers
```

Image overload:

```text
Image Pool ❌
```

but:

```text
Payment Pool ✅
```

This is resource isolation.

---

# 39. Bulkheads in Node.js

Node.js uses an event loop, so you don't usually think in terms of one thread per request like traditional server models.

But the same idea still applies.

You can isolate:

```text
Queue workers
Connection pools
Concurrency limits
Separate services
Separate process pools
```

For example:

```text
Image jobs
→ Image queue
→ limited concurrency

Email jobs
→ Email queue
→ separate concurrency
```

Now image processing can't consume all worker capacity.

---

# 40. Connection Pool Exhaustion

A common backend failure:

```text
API
 ↓
Database connection pool
```

Suppose pool size:

```text
10 connections
```

and all 10 are stuck on slow queries.

New requests:

```text
Request
 ↓
Waiting for DB connection
 ↓
Waiting
 ↓
Waiting
```

Eventually your entire application becomes unhealthy.

Timeouts and query limits help prevent this.

---

# 41. Resource Limits

Fault tolerance isn't only about network failures.

You also need limits for:

```text
CPU
Memory
Connections
Threads/workers
Queue size
Request body size
File uploads
Concurrent requests
Database queries
```

Why?

Because:

> **Unlimited resource usage is itself a failure mode.**

---

# 42. Rate Limiting

Suppose an API receives:

```text
100,000 requests/sec
```

but normally supports:

```text
1,000 requests/sec
```

Without protection:

```text
CPU → 100%
Memory → high
DB → overloaded
```

Rate limiting protects the system.

For example:

```text
100 requests/minute/user
```

Excess requests:

```text
HTTP 429
```

---

# 43. Load Shedding

When a system is overloaded, it may be better to reject some work intentionally.

For example:

```text
System capacity = 10,000 RPS
Traffic = 50,000 RPS
```

Trying to process everything may cause:

```text
Everything fails
```

Instead:

```text
Accept important traffic
Reject low-priority traffic
```

This is:

> **Load shedding**

---

# 44. Priority Queues

Not all requests are equally important.

Example:

```text
Priority 1 → Payment
Priority 2 → Order
Priority 3 → Notification
Priority 4 → Analytics
```

During overload:

```text
Process:
Payment
Order

Delay:
Notification

Drop/defer:
Analytics
```

This allows the system to protect critical functionality.

---

# 45. Failure Isolation

Suppose:

```text
Recommendation Service
```

becomes unhealthy.

You don't want:

```text
Recommendation failure
       ↓
Homepage failure
       ↓
Checkout failure
       ↓
Entire application failure
```

Instead:

```text
Recommendation failure
       ↓
Fallback
       ↓
Homepage continues
```

This is:

> **Failure isolation**

---

# 46. Dependency Failure

Every dependency should be treated as potentially unreliable.

Example:

```text
Your API
 ├── PostgreSQL
 ├── Redis
 ├── Payment API
 ├── Email API
 └── Object Storage
```

Ask:

```text
What happens if PostgreSQL fails?
What happens if Redis fails?
What happens if payment fails?
What happens if email fails?
What happens if storage fails?
```

This gives you a:

> **Failure matrix**

---

# 47. Failure Matrix

Example:

|Dependency|Failure Behavior|
|---|---|
|PostgreSQL|Fail request / failover|
|Redis|Fall back to DB|
|Payment|Retry + circuit breaker|
|Email|Queue for later|
|Analytics|Drop/defer|
|Recommendations|Use fallback|
|Object storage|Retry / alternate storage|

This is excellent system-design practice.

# 48. Redis Failure Example

Suppose:

```text
API
 ↓
Redis
 ↓
Cache miss
 ↓
Database
```

Now Redis is completely down.

Bad architecture:

```text
Redis ❌
 ↓
Application ❌
```

Better:

```text
Redis ❌
 ↓
Fallback to DB
```

Performance may degrade, but the application remains functional.

This is graceful degradation.

# 49. Database Failure

Database failure is much more serious.

Potential architecture:

```text
                Database
             /           \
        Primary        Replica
```

If primary fails:

```text
Primary ❌
    ↓
Failover
    ↓
Replica becomes primary
```

But failover introduces questions:

```text
How quickly?
Data loss?
Replication lag?
How do clients reconnect?
How is split-brain prevented?
```

We'll explore high availability more deeply in **Lesson 11.14**.

# 50. Split Brain

A dangerous distributed-system failure occurs when two nodes both believe they are primary.

Example:

```text
Node A → "I'm primary"
Node B → "I'm primary"
```

Both accept writes:

```text
A → x = 100
B → x = 200
```

Now you have conflicting state.

This is:

> **Split brain**

Leader election and quorum mechanisms help prevent this.

---

# 51. Retry + Idempotency

These two should often be discussed together.

Suppose:

```text
POST /orders
```

Network timeout occurs.

Client retries:

```text
POST /orders
```

The first request may actually have succeeded.

Without idempotency:

```text
Order 1
Order 2 ❌
```

With an idempotency key:

```http
Idempotency-Key: order-request-123
```

the backend can recognize the duplicate request.

This is extremely important for payments and order creation.

---

# 52. Timeout + Retry + Circuit Breaker

These patterns work together.

```text
Request
   ↓
Timeout
   ↓
Retry
   ↓
Timeout
   ↓
Retry
   ↓
Repeated failures
   ↓
Circuit opens
   ↓
Fast failure
```

This prevents a failing dependency from consuming all your resources.

---

# 53. Graceful Degradation + Circuit Breaker

Example:

```text
Recommendation Service
        ↓
Failures
        ↓
Circuit OPEN
        ↓
Fallback
        ↓
"Popular courses"
```

Instead of:

```text
Recommendation Service
        ↓
Failure
        ↓
500 Error
```

This gives users a better experience.

# 54. Cascading Failure

One of the most dangerous problems in distributed systems.

Imagine:

```text
Service A
   ↓
Service B
   ↓
Service C
   ↓
Database
```

Service C becomes slow.

Then:

```text
C slow
 ↓
B waits
 ↓
A waits
 ↓
Connections exhausted
 ↓
Entire system slows
```

This is:

> **Cascading failure**

---

# 55. How to Stop Cascading Failures

Use:

```text
Timeouts
Retries with limits
Circuit breakers
Bulkheads
Rate limiting
Load shedding
Queueing
Resource limits
Graceful degradation
```

These mechanisms prevent one unhealthy dependency from taking down the entire system.

---

# 56. Example: Cascading Failure

Suppose:

```text
API → Recommendation Service
```

Recommendation becomes slow:

```text
Latency:
100ms → 1s → 5s → 20s
```

API requests pile up:

```text
100 requests
500 requests
1000 requests
5000 requests
```

Eventually:

```text
Connection pool exhausted
```

Now unrelated requests fail.

This is exactly what fault tolerance should prevent.

---

# 57. Timeout Prevents This

Set:

```text
Recommendation timeout = 1 second
```

Now:

```text
Request
 ↓
Recommendation
 ↓
1 sec
 ↓
Timeout
 ↓
Fallback
```

The request doesn't occupy resources for 20 seconds.

---

# 58. Circuit Breaker Prevents This

After repeated failures:

```text
Circuit OPEN
```

Now:

```text
Request
 ↓
Circuit
 ↓
Immediate fallback
```

No downstream call.

This protects both services.

---

# 59. Bulkhead Prevents This

Separate capacity:

```text
Core API
   │
   ├── Payment capacity
   ├── Course capacity
   └── Recommendation capacity
```

Recommendation overload:

```text
Recommendation capacity ❌
```

doesn't consume:

```text
Payment capacity
```

---

# 60. Queue Prevents This

Instead of doing expensive work synchronously:

```text
API
 ↓
Expensive processing
```

use:

```text
API
 ↓
Queue
 ↓
Worker
```

Now the API can return quickly.

The queue absorbs spikes.

Let's combine everything:

             │             │              │

With:

```text

```

Now you're thinking like a production engineer.

# 62. Fault-Tolerant Node.js Example

Suppose your Express server calls an external service.

A simplified pattern:

```javascript
async function callPaymentService() {
  try {
    const response = await axios.post(
      PAYMENT_URL,
      paymentData,
      {
        timeout: 3000
      }
    );

    return response.data;
  } catch (error) {
    // Handle timeout / transient failure
    throw error;
  }
}
```

The important part is:

```javascript
timeout: 3000
```

Never let external requests hang indefinitely.

---

# 63. Add Retry Carefully

Conceptually:

```javascript
for (let attempt = 1; attempt <= 3; attempt++) {
  try {
    return await callService();
  } catch (error) {
    if (!isRetryable(error) || attempt === 3) {
      throw error;
    }

    await sleep(backoff(attempt));
  }
}
```

In production, you'd want:

```text
Timeout
+
Exponential backoff
+
Jitter
+
Retry limit
+
Idempotency
```

# 65. What Should Your Backend Do During Failure?

For every external dependency, define:

```text
Timeout?
Retry?
Fallback?
Circuit breaker?
Queue?
Fail request?
```

Example:

# 70. Interview Question 🎯

### "What is fault tolerance?"

Strong answer:

> Fault tolerance is the ability of a system to continue providing acceptable functionality when one or more components fail. It is usually achieved through redundancy, failover, timeouts, retries, circuit breakers, isolation, graceful degradation, and controlled resource usage.

---

# 71. Interview Question 🎯

### "Why are timeouts important?"

Strong answer:

> Without timeouts, a slow dependency can hold connections and resources indefinitely, eventually causing resource exhaustion and cascading failures. Timeouts bound how long a service waits and allow it to fail fast, retry, or use a fallback.

---

# 72. Interview Question 🎯

### "What is a circuit breaker?"

Strong answer:

> A circuit breaker prevents repeated calls to an unhealthy dependency. It typically moves from closed to open after repeated failures, rejects calls quickly while open, and periodically enters a half-open state to test whether the dependency has recovered.

---

# 73. Interview Question 🎯

### "How do you prevent cascading failures?"

Strong answer:

> I would use bounded timeouts, limited retries with exponential backoff and jitter, circuit breakers, bulkheads or concurrency limits, rate limiting, load shedding, queues for asynchronous work, and graceful degradation for non-critical dependencies.

That's a strong production-level answer.

---

# 74. Common Mistakes ❌

### Mistake 1

> "Just retry failed requests."

Retries can amplify outages.

Use:

```text
Timeout
+
Backoff
+
Jitter
+
Limit
```

---

### Mistake 2

> "More replicas solve everything."

Replicas don't solve:

```text
Bad queries
Network partitions
Application bugs
Split brain
Configuration errors
```

---

### Mistake 3

> "Circuit breakers replace retries."

No.

They solve different problems.

---

### Mistake 4

> "If Redis fails, the whole application should fail."

Not necessarily.

If Redis is only a cache:

```text
Redis ❌
 ↓
Database fallback
```

may be appropriate.

---

### Mistake 5

> "Everything should have a fallback."

No.

Some operations cannot safely fall back.

For example:

```text
Payment authorization
```

shouldn't simply return:

```text
"Payment successful"
```

when the payment provider is unavailable.

Never fake success.

# 🧠 Final Mental Model

A reliable system isn't one where:

```text
Nothing fails.
```

That's impossible.

A reliable system is one where:

```text
Something fails
      ↓
System detects it
      ↓
Failure is contained
      ↓
Traffic is redirected/reduced
      ↓
Fallback is used if possible
      ↓
System recovers
      ↓
Users experience minimal impact
```

That's **fault tolerance**.
