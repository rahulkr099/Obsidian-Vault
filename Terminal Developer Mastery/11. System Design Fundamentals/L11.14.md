# Lesson 11.14 — High Availability ⭐⭐⭐⭐⭐

> **Goal:** Learn how to design systems that remain available even when servers, databases, networks, or entire infrastructure locations fail.

This lesson builds directly on:

```text
11.10 → CAP Theorem
11.11 → Consistency Models
11.12 → Message Queues
11.13 → Fault Tolerance
11.14 → High Availability ⭐
```

The central question is:

> **"How can users continue using our application even when parts of our infrastructure fail?"**

---

# 1. What Is High Availability?

**High Availability (HA)** means:

> A system is designed to remain accessible and operational for a very high percentage of time.

Instead of:

```text
Server fails
    ↓
Application unavailable ❌
```

we want:

```text
Server A ❌
    ↓
Traffic moves
    ↓
Server B ✅
    ↓
Application continues
```

High availability is therefore heavily based on:

```text
Redundancy
+
Failover
+
Health checks
+
Failure isolation
```

---

# 2. Availability Is Measured as a Percentage

You'll often see:

```text
99%
99.9%
99.99%
99.999%
```

These numbers look very close.

But their practical difference is huge.

---

# 3. The Famous "Nines"

Approximate downtime per year:

|Availability|Downtime/year|
|---|--:|
|99%|~3.65 days|
|99.9%|~8.76 hours|
|99.99%|~52.6 minutes|
|99.999%|~5.26 minutes|
|99.9999%|~31.6 seconds|

This is why:

> **Adding another 9 becomes increasingly difficult and expensive.**

---

# 4. 99.9% Availability

Suppose your API promises:

```text
99.9%
```

That means approximately:

```text
8 hours 45 minutes
```

of downtime could theoretically fit within a year.

For many internal applications, that may be acceptable.

For critical financial infrastructure, probably not.

---

# 5. 99.99% Availability

Now:

```text
99.99%
```

allows roughly:

```text
52 minutes/year
```

That is much stricter.

You need better:

```text
Monitoring
Failover
Deployment practices
Infrastructure redundancy
Recovery procedures
```

---

# 6. 99.999% Availability

Five nines:

```text
99.999%
```

means roughly:

```text
5 minutes/year
```

Now even small incidents matter.

A bad deployment that causes 10 minutes of downtime can consume the entire annual budget.

This is why highly available systems require serious engineering discipline.

---

# 7. Availability Formula

A simple formula:

```text
Availability =
Uptime / (Uptime + Downtime)
```

For example:

```text
Uptime = 999 hours
Downtime = 1 hour
```

Then:

```text
Availability =
999 / 1000
= 99.9%
```

---

# 8. SLA, SLO, SLI

These three terms appear frequently in production engineering.

```text
SLI
 ↓
SLO
 ↓
SLA
```

Let's understand them.

---

# 9. SLI — Service Level Indicator

An SLI is:

> **A measurement of actual service performance.**

Examples:

```text
Request success rate
Latency
Availability
Error rate
Throughput
```

For example:

```text
99.95% of requests succeeded
```

That's an SLI measurement.

---

# 10. SLO — Service Level Objective

An SLO is:

> **The target you want to achieve.**

Example:

```text
API availability SLO:
99.95%
```

Or:

```text
99% of requests
must complete under 300ms
```

SLOs are engineering targets.

---

# 11. SLA — Service Level Agreement

An SLA is:

> **A formal commitment made to customers or users.**

Example:

```text
99.9% availability guaranteed
```

An SLA may include consequences if the provider doesn't meet the agreement.

Think:

```text
SLI → What we measure
SLO → What we target
SLA → What we promise
```

---

# 12. Example

Suppose your LMS API has:

```text
SLI:
Actual availability = 99.97%
```

Your engineering target:

```text
SLO:
99.95%
```

Your customer contract:

```text
SLA:
99.9%
```

That's completely reasonable.

Your internal target is usually stricter than your external commitment.

---

# 13. Error Budget

If your SLO is:

```text
99.9%
```

then the remaining:

```text
0.1%
```

is your:

> **Error budget**

You can think of it as the amount of unreliability you're allowed before violating your target.

For 99.9%:

```text
~8.76 hours/year
```

of allowable downtime.

---

# 14. Why Error Budgets Matter

Suppose your team wants to release a risky feature.

Your reliability team says:

```text
Current error budget:
almost exhausted
```

Then deploying risky changes isn't a good idea.

If instead:

```text
Error budget:
healthy
```

you may have more room for experimentation.

This connects:

```text
Reliability
+
Development velocity
```

---

# 15. High Availability Starts With Redundancy

Single server:

```text
Users
  ↓
Server A
```

Failure:

```text
Server A ❌
    ↓
Everything down
```

High availability:

```text
              Load Balancer
              /           \
             ▼             ▼
         Server A       Server B
```

Now:

```text
A ❌
B ✅
```

Traffic continues.

---

# 16. Load Balancer

A load balancer distributes traffic among healthy servers.

```text
                 Users
                   │
                   ▼
              Load Balancer
              /     |      \
             ▼      ▼       ▼
           API 1  API 2   API 3
```

If:

```text
API 2 ❌
```

the load balancer routes traffic to:

```text
API 1
API 3
```

---

# 17. Health Checks

The load balancer needs to know:

> Which servers are healthy?

For example:

```http
GET /health
```

Healthy:

```text
200 OK
```

Unhealthy:

```text
500
```

The load balancer removes unhealthy servers from rotation.

---

# 18. But What Should `/health` Check?

A naive health endpoint:

```javascript
app.get("/health", (req, res) => {
  res.json({ status: "ok" });
});
```

only proves:

```text
Node.js process is running.
```

It doesn't necessarily prove:

```text
Database works
Redis works
Queue works
```

This distinction is important.

---

# 19. Liveness vs Readiness

### Liveness

Answers:

> "Is the application process alive?"

```text
Node process running?
```

If not:

```text
Restart it.
```

### Readiness

Answers:

> "Can this instance safely receive traffic?"

For example:

```text
Node running ✅
Database connection ❌
```

The service is alive but not ready.

---

# 20. Multi-AZ Architecture

Cloud infrastructure commonly provides:

> **Availability Zones (AZs)**

An availability zone is an isolated infrastructure location within a cloud region.

Instead of:

```text
Region
   │
   └── AZ A
         └── All servers
```

use:

```text
               Region
            /          \
          AZ-A         AZ-B
           │             │
        API 1          API 2
           │             │
           └─────┬───────┘
                 │
              Database
```

Now failure of one zone doesn't necessarily take down the entire application.

---

# 21. Why Multiple Availability Zones?

Imagine:

```text
AZ-A
```

has a major infrastructure problem.

If everything is there:

```text
AZ-A ❌
    ↓
Application ❌
```

With:

```text
AZ-A → API 1
AZ-B → API 2
```

traffic can move to:

```text
AZ-B
```

This is much more resilient.

---

# 22. Multi-AZ vs Multi-Region

These are not the same.

### Multi-AZ

```text
Region
 ├── AZ A
 └── AZ B
```

### Multi-Region

```text
Region A
    │
    └── AZs

Region B
    │
    └── AZs
```

Multi-region is much more complex.

---

# 23. Why Multi-Region?

Suppose an entire cloud region becomes unavailable.

For example:

```text
Region A ❌
```

If your application only exists there:

```text
Application ❌
```

With another region:

```text
Region A ❌

Region B ✅
```

traffic can potentially fail over to Region B.

---

# 24. Multi-Region Architecture

Conceptually:

```text
                     Global DNS
                         │
                ┌────────┴────────┐
                ▼                 ▼
           Region A           Region B
           /      \           /      \
         AZ-A    AZ-B       AZ-A    AZ-B
          │        │         │        │
         API      API       API      API
```

This provides strong disaster resilience.

But it introduces major complexity.

---

# 25. Multi-Region Challenges

You now have to deal with:

```text
Cross-region latency
Database replication
Replication conflicts
Data residency
DNS failover
Traffic routing
Cache consistency
Deployment coordination
Cost
Observability
```

Especially:

> **Data consistency**

---

# 26. Active-Passive Multi-Region

One region is active:

```text
Region A
   ↓
ACTIVE

Region B
   ↓
STANDBY
```

If A fails:

```text
Region A ❌
     ↓
Failover
     ↓
Region B ACTIVE
```

Advantages:

```text
Simpler
Easier consistency
```

Disadvantages:

```text
Standby resources underused
Failover takes time
```

---

# 27. Active-Active Multi-Region

Both regions serve traffic:

```text
Region A → Active
Region B → Active
```

Traffic can be routed based on:

```text
Location
Latency
Health
Capacity
```

Advantages:

```text
High availability
Low regional latency
Better resource utilization
```

Disadvantages:

```text
Much more complicated
Conflict resolution
Cross-region consistency
Complex deployments
```

---

# 28. Database High Availability

Your API can have:

```text
10 servers
```

but if all of them depend on:

```text
ONE database
```

you still have a major single point of failure.

So:

```text
Application HA
```

must be matched by:

```text
Database HA
```

---

# 29. Primary + Replica

Basic architecture:

```text
              Primary
             /       \
            ▼         ▼
        Replica 1  Replica 2
```

If primary fails:

```text
Primary ❌
   ↓
Election / Failover
   ↓
Replica becomes primary
```

This is a common HA pattern.

---

# 30. Database Failover

Failover means:

> **Switching from a failed component to a healthy backup.**

Example:

```text
Primary DB
    ↓
Failure
    ↓
Replica
    ↓
New Primary
```

But failover isn't instantaneous.

There may be:

```text
Detection time
+
Election time
+
Connection recovery
```

During this period some requests may fail.

---

# 31. RPO

Now we reach two extremely important disaster-recovery concepts.

### RPO

> **Recovery Point Objective**

It answers:

> **How much data can we afford to lose?**

Example:

```text
RPO = 5 minutes
```

means that losing up to about five minutes of recent data may be acceptable under the recovery plan.

---

# 32. RTO

### Recovery Time Objective

RTO answers:

> **How quickly must the system be restored?**

Example:

```text
RTO = 30 minutes
```

means:

```text
Major failure
    ↓
System restored within ~30 min
```

---

# 33. RPO vs RTO

Remember:

```text
RPO
→ How much data can we lose?

RTO
→ How long can we be down?
```

Example:

```text
RPO = 5 minutes
RTO = 30 minutes
```

This means:

```text
Data loss tolerance → 5 min
Downtime tolerance   → 30 min
```

---

# 34. Backup Strategy

Backups are a critical part of availability and disaster recovery.

You might have:

```text
Daily full backup
+
Hourly incremental backup
+
Off-site storage
```

But:

> **A backup is not a backup until you've successfully restored it.**

This is a very important production principle.

---

# 35. Test Your Backups

Suppose:

```text
Database destroyed 💥
```

You discover:

```text
Backup file exists.
```

Great?

Not necessarily.

Maybe:

```text
Backup is corrupted
Credentials are missing
Restore script doesn't work
Schema is incompatible
```

Therefore:

```text
Backup
 ↓
Restore test
 ↓
Validation
```

must be part of your process.

# 36. Disaster Recovery

Disaster Recovery (DR) is the process of restoring systems after major failures.

Possible disasters:

```text
Region outage
Database corruption
Accidental deletion
Ransomware
Cloud outage
Major deployment failure
Infrastructure destruction
```

A DR plan should answer:

```text
Where is the backup?
How do we restore it?
How long will it take?
Who performs the recovery?
How do we verify the system?
```

---

# 37. Backup Types

Common concepts:

```text
Full backup
Incremental backup
Differential backup
Snapshot
Continuous replication
Point-in-time recovery
```

You don't need to memorize every implementation yet.

Understand the goal:

> **Recover data to an acceptable point in time.**

---

# 38. Point-in-Time Recovery

Suppose:

```text
10:00 → Good
11:00 → Good
12:00 → Good
13:00 → Accidental DELETE 💥
```

Point-in-time recovery allows you to restore to something like:

```text
12:59
```

instead of restoring only yesterday's backup.

This can dramatically reduce data loss.

---

# 39. High Availability Doesn't Mean Zero Downtime

No realistic system guarantees:

```text
0 seconds downtime
```

Instead:

```text
Minimize downtime
+
Detect failures quickly
+
Recover automatically
```

That's the practical goal.

# 40. Deployment and Availability

Deployments themselves can cause outages.

Bad approach:

```text
Stop old version
      ↓
Deploy new version
      ↓
Start
```

Potential downtime:

```text
Users → ❌
```

A better strategy:

> **Rolling deployment**

---

# 41. Rolling Deployment

Suppose:

```text
API 1
API 2
API 3
```

Deploy new version gradually:

```text
API 1 → v2
API 2 → v1
API 3 → v1
```

Then:

```text
API 1 → v2
API 2 → v2
API 3 → v1
```

Finally:

```text
All → v2
```

Traffic continues during deployment.

---

# 42. Blue-Green Deployment

Another strategy:

```text
BLUE
v1
```

and:

```text
GREEN
v2
```

Both environments exist.

Initially:

```text
Traffic → BLUE
```

After testing:

```text
Traffic → GREEN
```

If problems occur:

```text
Traffic → BLUE
```

This makes rollback fast.

---

# 43. Canary Deployment

Instead of sending everyone to v2:

```text
95% → v1
5%  → v2
```

Monitor:

```text
Errors
Latency
CPU
Business metrics
```

If v2 looks healthy:

```text
25% → v2
50% → v2
100% → v2
```

This is:

> **Canary deployment**

It reduces blast radius.

---

# 44. Blast Radius

Blast radius means:

> **How much of the system is affected by a failure.**

Bad deployment:

```text
One bad release
 ↓
100% users affected
```

Canary:

```text
One bad release
 ↓
5% users affected
```

That's a much smaller blast radius.

---

Suppose your application has:

```text

```

If analytics crashes:

```text

```


Isolation increases overall availability.

# 46. Availability and Queues

Queues help absorb temporary failures.

Suppose:

```text
Email Service ❌
```

Instead of failing the request:

```text
User registration
 ↓
Queue
```

Later:

```text
Email Service recovers
 ↓
Queue
 ↓
Email Worker
```

The user's core operation remains successful.

# 47. Availability and Caching

Caching can also improve availability.

Suppose:

```text
Database ❌
```

but cached data exists:

```text
Redis → product data
```

You may still serve:

```text
Product page ✅
```

This is another form of graceful degradation.

But be careful:

> Cached data may be stale.

So you must decide whether stale data is acceptable.

# 53. Availability Calculation for Multiple Components

Here's an important system-design concept.

Suppose:

```text
Service A availability = 99.9%
Service B availability = 99.9%
```

If your request **requires both services** to succeed, the combined availability can be approximately:

```text
0.999 × 0.999
= 0.998001
≈ 99.8001%
```

So:

> **Adding dependencies can reduce end-to-end availability.**

---

# 54. Dependency Chains

Imagine:

```text
API
 ↓
Auth Service
 ↓
Payment Service
 ↓
Database
```

If all are required synchronously, overall availability is roughly the product of their availability.

This is one reason:

```text
Graceful degradation
+
Asynchronous processing
+
Failure isolation
```

are so powerful.

---

# 55. Reduce Synchronous Dependencies

Instead of:

```text
API
 ↓
Auth
 ↓
Payment
 ↓
Notification
 ↓
Analytics
```

you might design:

```text
API
 ↓
Core operation
 ↓
Response

Later:
Queue
 ├── Notification
 └── Analytics
```

Now notification and analytics don't determine whether the core request succeeds.

This improves availability.

---

# 56. Availability Through Simplicity

Here's a counterintuitive idea:

> **Sometimes the most reliable architecture is the simplest architecture.**

Every additional component creates another possible failure:

```text
API
 ↓
Service A
 ↓
Service B
 ↓
Service C
 ↓
Service D
```

versus:

```text
API
 ↓
Database
```

The second may be easier to operate reliably.

Don't introduce distributed systems unless the problem requires them.

# 57. Interview Question 🎯

### "How would you make an API highly available?"

Strong answer:

> I'd run multiple stateless API instances across multiple availability zones behind a load balancer, use health checks and automatic failover, ensure the database and other critical dependencies are also highly available, and use timeouts, retries, circuit breakers, queues, monitoring, and graceful degradation to prevent cascading failures.

---

# 58. Interview Question 🎯

### "What is the difference between RPO and RTO?"

Strong answer:

> RPO defines how much data loss the business can tolerate after a disaster, while RTO defines how quickly the system must be restored.

Remember:

```text
RPO → Data loss
RTO → Downtime
```

---

# 59. Interview Question 🎯

### "Multi-AZ vs Multi-Region?"

Strong answer:

> Multi-AZ protects against failures within a cloud region by distributing infrastructure across isolated availability zones. Multi-region extends resilience to an entire regional outage but introduces significantly more complexity around routing, replication, latency, consistency, failover, and data residency.

---

# 60. Interview Question 🎯

### "Active-active vs active-passive?"

Strong answer:

> In active-active architecture, multiple instances or regions actively serve traffic, improving resource utilization and potentially reducing failover time but increasing synchronization complexity. In active-passive, one side serves traffic while another waits for failover, making the architecture simpler but potentially leaving standby capacity underutilized.

---

# 61. Interview Question 🎯

### "How do you achieve high availability for a database?"

A good answer:

> I'd use replication with automatic failover, distribute database nodes across availability zones, monitor replication health, use appropriate read replicas where needed, maintain tested backups and point-in-time recovery, and define clear RPO and RTO targets.

Then add:

> The exact design depends on the database and consistency requirements.

Excellent.

---

# 62. Common Mistakes ❌

### Mistake 1

> "High availability means no downtime."

No.

It means minimizing downtime and continuing service through failures where possible.

---

### Mistake 2

> "Just add more servers."

More servers don't help if:

```text
Database is a SPOF
Load balancer is a SPOF
Network is a SPOF
Configuration is broken
```

HA must cover the whole dependency chain.

---

### Mistake 3

> "Multi-region is always better."

No.

It introduces:

```text
Consistency challenges
Cost
Latency
Operational complexity
```

---

### Mistake 4

> "Backups provide high availability."

Backups primarily provide:

```text
Recovery
```

not instant availability.

Replication and failover are more directly related to HA.

---

### Mistake 5

> "99.99% and 99.999% are almost the same."

They are not.

Approximate annual downtime:

```text
99.99%  → 52.6 minutes
99.999% → 5.26 minutes
```

That difference is enormous operationally.
