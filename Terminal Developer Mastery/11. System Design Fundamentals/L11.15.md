# Lesson 11.15 — API Design ⭐⭐⭐⭐⭐

> **Goal:** Learn how to design APIs that are clean, predictable, scalable, secure, and easy for frontend developers and other services to consume.

You already know how to build APIs with **Node.js + Express**. Now we're going to move from:

> **"How do I make an API work?"**

to:

> **"How do I design an API professionally?"**

This distinction is extremely important for backend engineering interviews and real-world development.

---

# 1. What Is API Design?

API design is deciding how clients communicate with your backend.

For example:

```text
React Frontend
      │
      │ HTTP
      ▼
Express API
      │
      ▼
Database
```

A well-designed API defines:

```text
Endpoints
HTTP methods
Request format
Response format
Status codes
Authentication
Authorization
Pagination
Filtering
Versioning
Errors
Rate limits
Idempotency
```

The goal is:

> **Make the API predictable and easy to use.**

---

# 2. What Makes a Good API?

A good API should be:

```text
Predictable
Consistent
Simple
Secure
Performant
Versionable
Well documented
Backward compatible
```

For example:

```http
GET /api/v1/courses
```

is much easier to understand than:

```http
GET /api/getAllCoursesFromDatabaseNow
```

---

# 3. REST API

REST stands for:

> **Representational State Transfer**

REST is an architectural style for designing network APIs.

The basic idea is:

> **Think about resources rather than actions.**

For example:

```text
User
Course
Lesson
Order
Product
Payment
```

These become resources.

---

# 4. Resource-Based URLs

Good:

```http
GET /users
GET /users/123

GET /courses
GET /courses/456

GET /orders
GET /orders/789
```

Avoid putting actions directly into the URL when HTTP methods already express the action.

Less REST-like:

```http
GET /getUsers
POST /createUser
POST /deleteUser
```

Prefer:

```http
GET /users
POST /users
DELETE /users/123
```

---

# 5. HTTP Methods

The main methods you'll use:

```text
GET
POST
PUT
PATCH
DELETE
```

Think:

```text
GET    → Read
POST   → Create
PUT    → Replace
PATCH  → Partially update
DELETE → Delete
```

---

# 6. GET

Used to retrieve resources.

```http
GET /api/v1/users
```

Response:

```json
{
  "data": [
    {
      "id": "1",
      "name": "Rahul"
    }
  ]
}
```

Single resource:

```http
GET /api/v1/users/123
```

---

# 7. POST

Used to create a new resource.

```http
POST /api/v1/users
```

Request:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

Response:

```http
201 Created
```

---

# 8. PUT

PUT generally means:

> **Replace the resource representation.**

Example:

```http
PUT /api/v1/users/123
```

Request:

```json
{
  "name": "Rahul Kumar",
  "email": "rahul@example.com"
}
```

You are conceptually providing the complete updated representation.

---

# 9. PATCH

PATCH means:

> **Partially modify a resource.**

For example:

```http
PATCH /api/v1/users/123
```

Request:

```json
{
  "name": "Rahul Kumar"
}
```

Only the name changes.

For most CRUD applications, PATCH is very useful.

---

# 10. DELETE

Used to remove a resource.

```http
DELETE /api/v1/users/123
```

Possible response:

```http
204 No Content
```

---

# 11. REST CRUD Mapping

Memorize this:

|Operation|Method|Endpoint|
|---|---|---|
|List users|GET|`/users`|
|Get user|GET|`/users/:id`|
|Create user|POST|`/users`|
|Replace user|PUT|`/users/:id`|
|Update user|PATCH|`/users/:id`|
|Delete user|DELETE|`/users/:id`|

This pattern works across:

```text
users
courses
products
orders
posts
comments
```

---

# 12. Nested Resources

Suppose:

```text
Course
 └── Lessons
```

You could have:

```http
GET /courses/123/lessons
```

This communicates:

> "Get lessons belonging to course 123."

Another example:

```http
GET /posts/123/comments
```

---

# 13. Don't Over-Nest URLs

Avoid:

```http
/users/1/orders/2/products/3/reviews/4
```

This becomes difficult to maintain.

Usually:

```http
GET /reviews/4
```

is enough if the review has its own identity.

A useful rule:

> **Nest resources when the relationship is important and obvious, but don't create unnecessarily deep URLs.**

---

# 14. HTTP Status Codes

A professional API uses status codes correctly.

### Success

```text
200 OK
201 Created
202 Accepted
204 No Content
```

### Client errors

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests
```

### Server errors

```text
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

---

# 15. 200 vs 201

If you successfully retrieve something:

```http
200 OK
```

If you successfully create something:

```http
201 Created
```

Example:

```http
POST /users
```

Response:

```http
201 Created
```

This communicates more information than always returning:

```http
200 OK
```

---

# 16. 204 No Content

Useful when an operation succeeds but there's nothing to return.

Example:

```http
DELETE /users/123
```

Response:

```http
204 No Content
```

No response body is required.

---

# 17. 400 Bad Request

Use when the request itself is invalid.

Example:

```json
{
  "email": "hello"
}
```

If your API requires a valid email:

```http
400 Bad Request
```

---

# 18. 401 Unauthorized

Despite its name, think:

> **Authentication is missing or invalid.**

Example:

```http
GET /api/v1/profile
```

without a valid token:

```http
401 Unauthorized
```

---

# 19. 403 Forbidden

The user is authenticated but doesn't have permission.

Example:

```text
User → authenticated
Role → student
Endpoint → admin-only
```

Response:

```http
403 Forbidden
```

Remember:

```text
401 → Who are you?
403 → I know who you are, but you can't do this.
```

---

# 20. 404 Not Found

Resource doesn't exist.

```http
GET /users/999999
```

If user doesn't exist:

```http
404 Not Found
```

---

# 21. 409 Conflict

Useful when the request conflicts with current state.

Example:

```http
POST /users
```

with:

```json
{
  "email": "existing@example.com"
}
```

If email must be unique:

```http
409 Conflict
```

Another example:

```text
Trying to create a resource that already exists.
```

---

# 22. 422 Unprocessable Content

Useful when the request structure is valid but the submitted data cannot be accepted semantically.

For example:

```json
{
  "age": -10
}
```

The JSON is valid.

But:

```text
age = -10
```

may violate business validation.

You may use:

```http
422 Unprocessable Content
```

depending on your API conventions.

The most important thing is consistency across your API.

---

# 23. 429 Too Many Requests

Used for rate limiting.

Example:

```text
User
 ↓
1000 requests/min
 ↓
API limit = 100
```

Response:

```http
429 Too Many Requests
```

You may also provide:

```http
Retry-After: 60
```

to tell the client when to try again.

---

# 24. Error Response Design

Don't return random errors from different endpoints.

Bad:

```json
{
  "error": "Something went wrong"
}
```

Another endpoint:

```json
{
  "message": "User not found"
}
```

Another:

```json
{
  "err": "Invalid"
}
```

Inconsistent APIs become painful to consume.

---

# 25. Consistent Error Format

A better approach:

```json
{
  "success": false,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User does not exist"
  }
}
```

Another:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid email address"
  }
}
```

Now frontend code can reliably handle errors.

---

# 26. Don't Leak Internal Errors

Never return:

```json
{
  "error": "MongoServerError: E11000 duplicate key..."
}
```

to users in production.

Instead:

```json
{
  "success": false,
  "error": {
    "code": "EMAIL_ALREADY_EXISTS",
    "message": "An account with this email already exists."
  }
}
```

Log the detailed technical error internally.

This connects directly with your **security and observability** lessons.

---

# 27. API Response Structure

You can standardize successful responses too.

For example:

```json
{
  "success": true,
  "data": {
    "id": "123",
    "name": "Rahul"
  }
}
```

For lists:

```json
{
  "success": true,
  "data": [
    {
      "id": "1",
      "name": "Rahul"
    },
    {
      "id": "2",
      "name": "Amit"
    }
  ]
}
```

The exact envelope is a design choice.

Consistency matters more than the specific shape.

---

# 28. Pagination

Imagine:

```http
GET /courses
```

and your database has:

```text
10 million courses
```

Returning everything is terrible.

Instead:

```http
GET /courses?page=1&limit=20
```

Response:

```json
{
  "data": [...],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 10000000
  }
}
```

---

# 29. Why Pagination Matters

Without pagination:

```text
Database
   ↓
10 million rows
   ↓
API
   ↓
Huge JSON
   ↓
Network
   ↓
Browser 💥
```

With pagination:

```text
Database
   ↓
20 rows
   ↓
API
   ↓
Browser
```

Benefits:

```text
Lower DB load
Lower memory
Lower bandwidth
Faster response
Better UX
```

---

# 30. Offset Pagination

The common approach:

```http
GET /courses?page=3&limit=20
```

Calculate:

```text
offset = (page - 1) × limit
```

For:

```text
page = 3
limit = 20
```

we get:

```text
offset = 40
```

So:

```text
Rows 41–60
```

are returned.

---

# 31. Problem With Large Offsets

Suppose:

```text
page = 500000
```

The database may need to skip a huge number of rows.

This can become expensive.

For very large datasets, another approach is often better.

---

# 32. Cursor Pagination

Instead of:

```http
GET /courses?page=500000
```

you might use:

```http
GET /courses?limit=20&cursor=eyJpZCI6MTIzfQ
```

The cursor represents where to continue.

Conceptually:

```text
Page 1
 ↓
last item ID = 20
 ↓
cursor
 ↓
Page 2
 ↓
start after ID 20
```

This is often better for large or frequently changing datasets.

---

# 33. Cursor Pagination Example

Response:

```json
{
  "data": [
    {
      "id": "101"
    },
    {
      "id": "102"
    }
  ],
  "nextCursor": "102"
}
```

Client:

```http
GET /courses?cursor=102&limit=20
```

The server continues from there.

---

# 34. Offset vs Cursor

|Feature|Offset|Cursor|
|---|---|---|
|Simple|⭐⭐⭐⭐⭐|⭐⭐⭐|
|Easy to understand|Yes|Moderate|
|Large datasets|Can become expensive|Usually better|
|Jump to page|Easy|Difficult|
|Real-time feeds|Less ideal|Excellent|
|Stable pagination|Can shift|Better with proper cursor|

For admin dashboards:

```text
Offset pagination
```

is often perfectly fine.

For:

```text
News feeds
Activity streams
Large datasets
```

cursor pagination is often better.

---

# 35. Filtering

Suppose:

```http
GET /courses
```

You want only published courses.

Use query parameters:

```http
GET /courses?status=published
```

Multiple filters:

```http
GET /courses?status=published&category=backend
```

---

# 36. Sorting

Example:

```http
GET /courses?sort=createdAt
```

Descending:

```http
GET /courses?sort=-createdAt
```

Or explicitly:

```http
GET /courses?sortBy=createdAt&order=desc
```

Pick one convention and use it consistently.

---

# 37. Searching

Example:

```http
GET /courses?search=javascript
```

The server can search:

```text
title
description
tags
```

For serious search requirements, a dedicated search system may eventually be better than simple database queries.

We'll discuss search-system design later.

---

# 38. Filtering + Pagination + Sorting

A realistic API:

```http
GET /courses
    ?status=published
    &category=backend
    &sortBy=createdAt
    &order=desc
    &page=2
    &limit=20
```

This is a common pattern.

---

# 39. Query Parameter Validation

Never blindly trust query parameters.

Suppose:

```http
GET /courses?limit=-999999
```

or:

```http
GET /courses?limit=999999999
```

You should validate:

```text
minimum = 1
maximum = 100
```

For example:

```javascript
const limit = Math.min(
  Math.max(Number(req.query.limit) || 20, 1),
  100
);
```

Better still, validate using your schema-validation library.

---

# 40. API Versioning

Your API will evolve.

Version 1:

```http
/api/v1/users
```

Later:

```http
/api/v2/users
```

Why?

Because changing an API can break existing clients.

---

# 41. Breaking Changes

Suppose v1 returns:

```json
{
  "name": "Rahul"
}
```

You later change it to:

```json
{
  "firstName": "Rahul",
  "lastName": "Kumar"
}
```

An old frontend might expect:

```javascript
user.name
```

Now:

```text
undefined
```

That's a breaking change.

---

# 42. URL Versioning

Simple approach:

```http
/api/v1/users
/api/v2/users
```

Advantages:

```text
Easy to understand
Easy to route
Easy to document
```

This is very common.

---

# 43. Header Versioning

Another approach:

```http
Accept: application/vnd.myapi.v2+json
```

This keeps the URL unchanged.

But it is less obvious and can be harder for beginners.

For many projects:

```text
/api/v1/...
```

is perfectly reasonable.

---

# 44. Don't Version Every Small Change

Not every change needs:

```text
v2
v3
v4
```

Adding an optional field:

```json
{
  "name": "Rahul",
  "email": "..."
}
```

usually isn't a breaking change.

But removing or changing the meaning of fields can be.

Think:

> **Version when compatibility actually breaks.**

---

# 45. Backward Compatibility

A good API evolves without unnecessarily breaking existing clients.

Prefer:

```text
Add new field
```

instead of:

```text
Remove old field immediately
```

You can:

```text
Introduce new field
      ↓
Clients migrate
      ↓
Deprecate old field
      ↓
Eventually remove
```

This is a safer evolution strategy.

---

# 46. Deprecation

Suppose:

```http
GET /api/v1/users
```

will eventually be replaced.

You can announce:

```text
Deprecated
```

and provide:

```text
Migration guide
Replacement endpoint
Removal timeline
```

This is important for APIs used by external clients.

---

# 47. Idempotency

You learned about this in the message queue lesson.

Now apply it to APIs.

An operation is idempotent when repeating the same operation doesn't create additional unintended effects.

For example:

```http
PUT /users/123
```

with:

```json
{
  "name": "Rahul"
}
```

can be repeated safely.

---

# 48. GET Is Idempotent

If you perform:

```http
GET /users/123
```

10 times:

```text
Same read
```

It shouldn't create:

```text
10 users
```

GET should be safe and idempotent under normal REST semantics.

---

# 49. DELETE Is Usually Idempotent

Suppose:

```http
DELETE /users/123
```

First request:

```text
User deleted
```

Second request:

```text
User already absent
```

The final state is still:

```text
User does not exist
```

So DELETE is generally considered idempotent even though the responses can differ.

---

# 50. POST Is Not Naturally Idempotent

Suppose:

```http
POST /orders
```

Request:

```json
{
  "productId": "123",
  "quantity": 1
}
```

If the client retries:

```text
POST
POST
```

you could get:

```text
Order 1
Order 2 ❌
```

This is dangerous for payments and orders.

---

# 51. Idempotency Keys

A client can send:

```http
Idempotency-Key: 7e3d9a...
```

The server stores:

```text
key
request
result
```

If the same key arrives again:

```text
Don't perform the operation again.
Return the previous result.
```

---

# 52. Idempotency Flow

```text
Client
  │
  │ POST /payments
  │ Idempotency-Key: abc123
  ▼
API
  │
  ├── Key exists?
  │      │
  │      ├── Yes → return previous result
  │      │
  │      └── No
  │           ↓
  │        Process
  │           ↓
  │        Store result
  │
  ▼
Response
```

This is extremely useful for:

```text
Payments
Orders
Subscriptions
Transfers
```

---

# 53. API Rate Limiting

APIs need protection from excessive traffic.

Example:

```text
100 requests/minute/IP
```

or:

```text
1000 requests/hour/user
```

When exceeded:

```http
429 Too Many Requests
```

---

# 54. Rate Limit Strategies

Common approaches include:

```text
Fixed window
Sliding window
Token bucket
Leaky bucket
```

You don't need to implement all of them immediately.

For your Node.js backend, understand the concepts first.

---

# 55. Token Bucket

Imagine a bucket containing tokens:

```text
Bucket capacity = 100
```

Each request consumes:

```text
1 token
```

Tokens are replenished over time.

If there are no tokens:

```text
429 Too Many Requests
```

This allows controlled bursts while limiting sustained traffic.

# 56. API Gateway

In larger systems:

```text
Client
   ↓
API Gateway
   ↓
Microservices
```

The gateway can handle:

```text
Authentication
Rate limiting
Routing
Logging
TLS termination
Request transformation
Load balancing
```

Example:

```text
             API Gateway
            /     |      \
           ▼      ▼       ▼
        Users   Orders   Courses
```

We'll discuss API gateways more deeply in the later system-design projects.

# 57. Authentication vs Authorization

API design must clearly separate these.

### Authentication

> Who are you?

Example:

```text
JWT
Session
OAuth
```

### Authorization

> What are you allowed to do?

Example:

```text
Student → view courses
Instructor → create courses
Admin → delete users
```

---

# 58. Don't Trust Client Roles

Never do:

```javascript
if (req.body.role === "admin") {
  // allow
}
```

The client controls:

```text
req.body
```

Instead:

```text
JWT/session
     ↓
Server identifies user
     ↓
Database/claims determine role
     ↓
Authorization middleware
```

This connects directly to your **Security Engineering module**.

# 61. Keep Controllers Thin

Bad:

```javascript
router.post("/courses", async (req, res) => {
  // validation
  // authorization
  // database queries
  // business logic
  // email
  // response formatting
});
```

Better:

```text
Route
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
```

For example:

```javascript
router.post(
  "/",
  authenticate,
  authorize("instructor"),
  validate(createCourseSchema),
  courseController.create
);
```

Controller:

```javascript
const create = async (req, res) => {
  const course = await courseService.create(
    req.user.id,
    req.body
  );

  res.status(201).json({
    success: true,
    data: course
  });
};
```

That's clean API architecture.

# 62. API Validation

Never trust:

```text
body
query
params
headers
```

Validate them.

Example request:

```json
{
  "title": "",
  "price": -100
}
```

Your validation layer should reject it before business logic.

You've already worked with **Joi**, which fits perfectly here.

---

# 63. Validation Flow

```text
Request
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

This keeps responsibilities separated.

> **OpenAPI**

Tools such as Swagger UI can generate interactive API documentation from an OpenAPI specification.

Example:

```text
GET /api/v1/courses
```

```text

Response
Errors

```

# 65. API Contract

Think of an API as a contract:

```text
Frontend
   │
   │
   ▼
┌──────────────────┐
│   API Contract   │
├──────────────────┤
│ Request          │
│ Response         │
│ Errors           │
│ Status codes     │
└──────────────────┘
   │
   ▼
Backend
```

If you change the contract carelessly:

```text
Frontend ❌
```

So API design is partly about:

> **Managing contracts over time.**

---

# 66. API Design for Performance

Good API design also affects performance.

Avoid:

```http
GET /users
```

returning:

```text
50 fields
1000 records
```

when the frontend only needs:

```text
id
name
avatar
```

Consider:

```http
GET /users?fields=id,name,avatar
```

if field selection makes sense for your API.

But don't add complexity unless it solves a real problem.

---

# 67. N+1 Problem

Suppose:

```text
GET /courses
```

returns:

```text
100 courses
```

Then your backend performs:

```text
1 query → courses
100 queries → instructor
```

Total:

```text
101 queries
```

This is the:

> **N+1 query problem**

API design and database design are closely connected.

---

# 68. API Aggregation

Sometimes frontend needs:

# 72. API Timeout Headers

If your architecture has multiple services:

```text
API Gateway
 ↓
Service A
 ↓
Service B
```

you need to think about timeout budgets.

Suppose overall request budget is:

```text
2 seconds
```

Don't let:

```text
Service A → 2 seconds
Service B → 2 seconds
```

because the total could become much larger.

Distributed systems require careful timeout budgeting.

# 74. Designing a Professional Endpoint

Suppose you need:

```http

    ?category=backend
    &status=published
    &sortBy=createdAt
    &order=desc
    &limit=20
```

This is much better than:

```http
GET /api/getBackendPublishedCoursesSortedByNewest
```

The first is:

```text
Resource-oriented
Composable
Predictable
Easy to extend
```

# 75. API Design Golden Rules ⭐

Memorize these:

```text
1. Model resources clearly.
2. Use HTTP methods correctly.
3. Use meaningful status codes.
4. Keep response formats consistent.
5. Validate every input.
6. Paginate large collections.
7. Support filtering/sorting where useful.
8. Version breaking changes.
9. Make critical operations idempotent.
10. Rate-limit sensitive endpoints.
11. Don't leak internal errors.
12. Keep controllers thin.
13. Document the API contract.
14. Monitor API latency and errors.
15. Design for backward compatibility.
```

# 76. Interview Question 🎯

### "How would you design a REST API?"

Strong answer:

> I'd first identify the resources and relationships, then define resource-oriented endpoints and appropriate HTTP methods. I'd standardize request and response formats, status codes, validation, error handling, pagination, filtering, authentication, authorization, rate limiting, and versioning. For critical write operations I'd also consider idempotency and backward compatibility.

---

# 77. Interview Question 🎯

### "PUT vs PATCH?"

Strong answer:

> PUT generally represents replacing the resource representation, while PATCH represents a partial update. PATCH is useful when only a subset of fields needs to change.

---

# 78. Interview Question 🎯

### "How do you paginate a large API?"

Strong answer:

> For simple administrative datasets I'd use offset-based pagination because it's easy to understand and supports page navigation. For very large or frequently changing datasets such as feeds, I'd prefer cursor-based pagination because it avoids expensive large offsets and provides more stable traversal.

---

# 79. Interview Question 🎯

### "How do you make POST requests idempotent?"

Strong answer:

> For operations such as payments or order creation, I'd accept an idempotency key from the client, store the key and resulting operation atomically, and return the previous result if the same key is submitted again.

---

# 80. Interview Question 🎯

### "How would you version an API?"

Strong answer:

> I'd version only when there are breaking changes. A simple approach is URL versioning such as `/api/v1/users` and `/api/v2/users`. I'd keep changes backward compatible where possible and deprecate older versions with a migration path rather than breaking clients immediately.

# 81. Common Mistakes ❌

### Mistake 1

Using:

```http

```

### Mistake 2

Returning:

```http

```

for every situation.

Use meaningful status codes.

### Mistake 3

Returning millions of records.

Always consider:

```text

Filtering
Sorting
```

### Mistake 4

Putting business logic inside routes/controllers.

Use:

```text

 ↓

 ↓

```

### Mistake 5

Changing API responses without thinking about clients.

Remember:
