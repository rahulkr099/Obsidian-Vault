# Lesson 11.17 — Security in System Design ⭐⭐⭐⭐⭐

> **Goal:** Learn how to build security directly into system architecture instead of treating it as something added at the end.

You've already studied **Linux Security & Hardening** and have a dedicated **Security Engineering module**, so this lesson focuses on a different question:

> **How do security decisions affect the design of a scalable backend system?**

A production system must balance:

```text
Security
   +
Performance
   +
Scalability
   +
Reliability
   +
Developer Experience
```

---

# 1. Security Is an Architectural Concern

A beginner might design:

```text
Client
   ↓
API
   ↓
Database
```

and later add:

```text
"Let's add authentication."
```

A better design starts with:

```text
Who can access the system?
What can they access?
How are requests authenticated?
How are permissions checked?
Where are secrets stored?
How are services authenticated?
How are attacks detected?
```

Security should be part of the architecture from day one.

---

# 2. Security Layers

A typical backend can have several security layers:

```text
                    Client
                      │
                      ▼
                 CDN / WAF
                      │
                      ▼
                Load Balancer
                      │
                      ▼
                API Gateway
                      │
             ┌────────┴────────┐
             ▼                 ▼
       Authentication      Rate Limiting
             │                 │
             └────────┬────────┘
                      ▼
                Authorization
                      │
                      ▼
                  Services
                      │
             ┌────────┼────────┐
             ▼        ▼        ▼
          Database   Cache    Queue
```

And across everything:

```text
TLS
Secrets Management
Logging
Monitoring
Auditing
```

---

# 3. Authentication vs Authorization

This is one of the most important distinctions.

### Authentication

> **Who are you?**

Example:

```text
Email + password
JWT
Session
OAuth
```

### Authorization

> **What are you allowed to do?**

Example:

```text
Student → view course
Instructor → create course
Admin → delete course
```

Think:

```text
Authentication
      ↓
Identity

Authorization
      ↓
Permissions
```

---

# 4. Authentication Flow

A typical login:

```text
User
 │
 │ email + password
 ▼
API
 │
 ▼
Validate credentials
 │
 ▼
Generate session/token
 │
 ▼
Client
```

The client then uses the authentication mechanism on future requests.

---

# 5. Password Security

Never store:

```text
password = "mypassword123"
```

in your database.

Instead:

```text
Password
   ↓
Password hashing algorithm
   ↓
Password hash
   ↓
Database
```

Use an appropriate password hashing algorithm such as:

```text
Argon2id
bcrypt
scrypt
```

Do not use simple:

```text
SHA-256(password)
```

as a password-storage strategy.

Password hashing should be deliberately expensive.

---

# 6. Why Password Hashing Is Expensive

If hashing were extremely fast:

```text
1 billion guesses/sec
```

would make stolen password databases much easier to attack.

Password hashing intentionally makes each guess more expensive:

```text
Password
   ↓
Slow hashing
   ↓
Hash
```

The goal is:

> **Make legitimate authentication acceptable while making mass guessing expensive.**

---

# 7. Session-Based Authentication

One approach:

```text
Client
  ↓
Login
  ↓
Server creates session
  ↓
Session ID
  ↓
Client
```

The session may be stored server-side:

```text
Session ID
   ↓
Redis / Database
```

Subsequent request:

```text
Client
   ↓
Session ID
   ↓
Server
   ↓
Session lookup
   ↓
User
```

---

# 8. JWT Authentication

Another common approach:

```text
Login
  ↓
Server
  ↓
JWT
  ↓
Client
```

Later:

```text
Client
  ↓
JWT
  ↓
API
  ↓
Verify token
  ↓
User identity
```

JWTs can be useful for distributed systems because services can often validate signed tokens without a central session lookup.

But JWTs also introduce trade-offs.

---

# 9. JWT Is Not Automatically Better

JWT benefits:

```text
Stateless verification
Distributed service compatibility
Useful for APIs
```

Challenges:

```text
Revocation
Token lifetime
Token theft
Payload size
Key management
Refresh-token management
```

Don't choose JWT just because:

> "Modern applications use JWT."

Choose the authentication model based on your architecture.

---

# 10. Access Token + Refresh Token

A common architecture:

```text
Login
  │
  ├── Access Token
  │
  └── Refresh Token
```

Access token:

```text
Short lifetime
```

Refresh token:

```text
Longer lifetime
Used to obtain a new access token
```

Conceptually:

```text
Access Token
   ↓
Short-lived
   ↓
API access

Refresh Token
   ↓
Longer-lived
   ↓
New Access Token
```

---

# 11. Why Short-Lived Access Tokens?

Suppose an access token is stolen.

If it lasts:

```text
30 days
```

the attacker potentially has a large window.

If it lasts:

```text
10 minutes
```

the exposure window is smaller.

This doesn't make token theft harmless, but it reduces the lifetime of the stolen access token.

---

# 12. Refresh Token Security

Refresh tokens are highly sensitive.

Treat them carefully.

Depending on your architecture, a common web approach is:

```text
Refresh Token
      ↓
Secure
HttpOnly
SameSite cookie
```

This can reduce exposure to JavaScript-based token theft.

But cookie security requires correct:

```text
CSRF protection
SameSite configuration
CORS configuration
HTTPS
```

---

# 13. Token Storage Trade-offs

You may hear:

```text
localStorage
sessionStorage
cookies
memory
```

There isn't a single universal answer.

For browser applications, storing long-lived sensitive tokens in JavaScript-accessible storage can increase exposure if an XSS vulnerability exists.

A common architecture is:

```text
Short-lived access token
+
HttpOnly secure refresh-token cookie
```

with appropriate CSRF defenses.

---

# 14. Authorization

After authentication:

```text
Who is this user?
```

you need:

```text
What can this user do?
```

For example:

```text
User:
id = 123
role = instructor
```

Authorization checks:

```text
Can instructor create course?
YES

Can instructor delete another instructor?
NO
```

---

# 15. RBAC

RBAC means:

> **Role-Based Access Control**

Example:

```text
Student
Instructor
Admin
```

Permissions:

```text
Student
 ├── view courses
 └── enroll

Instructor
 ├── view courses
 ├── create courses
 └── update own courses

Admin
 ├── manage users
 ├── manage courses
 └── manage system
```

This is simple and useful.

---

# 16. ABAC

ABAC means:

> **Attribute-Based Access Control**

Instead of only checking role:

```text
role = instructor
```

you can check attributes:

```text
user.id === course.instructorId
```

Example:

```text
Instructor A
   ↓
Course owned by Instructor A
   ↓
Allowed

Instructor A
   ↓
Course owned by Instructor B
   ↓
Denied
```

This is much more precise.

---

# 17. Resource-Level Authorization

A dangerous mistake:

```javascript
app.get("/courses/:id", authenticate, getCourse);
```

Authentication only proves:

```text
User is logged in.
```

It doesn't prove:

```text
User is allowed to access this course.
```

You may need:

```text
authenticate
     ↓
authorize
     ↓
check resource ownership/permission
```

---

# 18. IDOR / BOLA

One of the most important API security problems is:

> **Broken Object Level Authorization (BOLA)**

Example:

```http
GET /api/v1/users/123/orders
```

User 123 can access their orders.

But what if another authenticated user changes:

```http
GET /api/v1/users/456/orders
```

and the server returns them?

That's an authorization vulnerability.

Never assume:

> "The user is authenticated, so they can access the resource."

---

# 19. API Gateway

In larger systems:

```text
Client
   ↓
API Gateway
   ↓
Services
```

The gateway can provide centralized controls:

```text
Authentication
Rate limiting
Routing
TLS termination
Request validation
Logging
```

But:

> **Don't rely only on the gateway for authorization.**

Services should protect their own sensitive resources too.

# 20. Defense in Depth

Suppose:

```text
Internet
   ↓
WAF
   ↓
API Gateway
   ↓
Service
   ↓
Database
```

Each layer has protections.

If one layer fails:

```text
Another layer
   ↓
Can still provide protection
```

This is:

> **Defense in depth**

---

# 21. TLS / HTTPS

Never send sensitive authentication information over plain HTTP.

Use:

```text
HTTPS
   ↓
TLS
```

TLS protects data:

```text
Client
  ⇅ encrypted
Server
```

Against attackers attempting to observe or modify traffic in transit.

---

# 22. TLS Everywhere

In a distributed architecture:

```text
Client
  ↓ HTTPS
Gateway
  ↓
Service A
  ↓
Service B
  ↓
Database
```

You should also consider encryption for internal traffic.

Why?

Because:

> Internal networks shouldn't automatically be considered trustworthy.

This becomes especially important in multi-service and cloud environments.

---

# 23. Service-to-Service Authentication

Suppose:

```text
Order Service
    ↓
Payment Service
```

Don't simply assume:

> "It's internal, so it's trusted."

Instead use mechanisms such as:

```text
mTLS
Service identity
Signed tokens
Workload identity
Short-lived credentials
```

The exact mechanism depends on infrastructure.

---

# 24. mTLS

mTLS means:

> **Mutual TLS**

Normal TLS:

```text
Client → proves server identity
```

mTLS:

```text
Client → proves identity
Server → proves identity
```

Conceptually:

```text
Service A
   ⇅
TLS + client certificate
   ⇅
Service B
```

This can be useful in high-security service-to-service environments.

---

# 25. Secrets Management

Your application needs secrets:

```text
Database password
JWT signing key
OAuth client secret
API keys
Encryption keys
```

Never put them directly into source code:

```javascript
const password = "my-secret-password";
```

That's dangerous.

---

# 26. Environment Variables

For smaller deployments:

```text
DATABASE_URL
JWT_SECRET
API_KEY
```

can be provided through environment configuration.

For example:

```text
process.env.DATABASE_URL
```

This is better than hardcoding secrets.

But:

> Environment variables aren't a complete secrets-management solution for every production environment.

---

# 27. Secrets Managers

Larger systems may use dedicated secret-management systems.

Examples include:

```text
HashiCorp Vault
AWS Secrets Manager
Google Secret Manager
Azure Key Vault
```

These systems can provide:

```text
Secure storage
Access control
Rotation
Auditing
Versioning
```

---

# 28. Secret Rotation

Suppose:

```text
Database password
```

has been used for:

```text
2 years
```

If it's leaked, that's dangerous.

A better system supports:

```text
Old secret
     ↓
New secret
     ↓
Applications migrate
     ↓
Old secret revoked
```

This is:

> **Secret rotation**

---

# 29. Don't Log Secrets

Bad:

```javascript
console.log({
  token,
  password,
  authorizationHeader
});
```

Your logs may become a security breach.

Never casually log:

```text
Passwords
Access tokens
Refresh tokens
API keys
Session IDs
Credit-card data
```

Mask sensitive values when logging is necessary.

---

# 30. API Rate Limiting

Security and performance meet here.

Suppose an attacker sends:

```text
100,000 login attempts/sec
```

Your API could be overwhelmed.

Rate limiting:

```text
100 attempts
 ↓
429
```

can protect the system.

---

# 31. Different Endpoints Need Different Limits

Don't necessarily use:

```text
100 requests/minute
```

for everything.

For example:

```text
GET /courses
→ 300/min

POST /login
→ 10/min

POST /password-reset
→ 5/hour

POST /payment
→ carefully controlled
```

Sensitive operations deserve stricter limits.

---

# 32. Brute-Force Protection

Login endpoints are especially sensitive.

Attack:

```text
admin@example.com
password1
password2
password3
...
```

Defenses can include:

```text
Rate limiting
Account lockout carefully designed
Progressive delays
CAPTCHA/risk controls
MFA
IP/device reputation
Monitoring
```

Be careful with permanent account lockouts because attackers can abuse them to lock legitimate users out.

---

# 33. Input Validation

Never trust:

```text
body
query
params
headers
cookies
```

Validate everything.

Example:

```json
{
  "age": -100000
}
```

Your validation layer should reject invalid input before business logic.

---

# 34. SQL Injection

Dangerous:

```javascript
const query =
  `SELECT * FROM users WHERE email = '${email}'`;
```

If user input is inserted directly into SQL, attackers may manipulate the query.

Use:

```text
Parameterized queries
Prepared statements
ORM/query builders correctly
```

---

# 35. NoSQL Injection

MongoDB doesn't magically eliminate injection risks.

Dangerous patterns can occur when untrusted objects are passed directly into query operators.

For example, don't blindly accept:

```json
{
  "email": {
    "$ne": null
  }
}
```

as a query object from clients.

Validate the expected shape:

```text
email → string
```

not:

```text
email → arbitrary object
```

---

# 36. Mass Assignment

Suppose your API accepts:

```json
{
  "name": "Rahul",
  "role": "admin"
}
```

If you do:

```javascript
User.updateOne(
  { _id: userId },
  req.body
);
```

the user might modify fields they shouldn't control.

Instead explicitly choose fields:

```javascript
const allowedFields = {
  name: req.body.name,
  bio: req.body.bio
};
```

This is:

> **Allowlisting fields**

---

# 37. CORS

CORS controls which browser origins can make cross-origin requests.

Bad:

```text
Access-Control-Allow-Origin: *
```

for sensitive authenticated APIs may be too permissive depending on your architecture.

Better:

```text
https://your-frontend.example
```

only when appropriate.

Remember:

> CORS is a browser security mechanism, not an authentication system.

---

# 38. CSRF

If authentication uses cookies, attackers may attempt:

```text
Malicious Website
      ↓
Victim's Browser
      ↓
Authenticated Request
```

CSRF defenses can include:

```text
SameSite cookies
CSRF tokens
Origin/Referer validation
Appropriate architecture
```

Especially important for cookie-based authentication.

---

# 39. XSS

XSS means:

> **Cross-Site Scripting**

An attacker injects malicious JavaScript into content rendered by the browser.

Example:

```text
User comment
   ↓
Stored in database
   ↓
Rendered without escaping
   ↓
Attacker JavaScript executes
```

Defenses include:

```text
Output encoding
Safe templating
Content Security Policy
Input handling
Avoid unsafe HTML rendering
```

---


For Express applications, middleware such as Helmet can help configure several security headers.

You already encountered Helmet in your backend projects.

# 41. File Upload Security

```http
POST /uploads
```

allows users to upload files.


Security considerations:


# 42. Object Storage

Instead of storing huge files directly on your application server:

```text
Client
 ↓
API
 ↓
Server disk
```

you can use:

```text
Client
 ↓
API
 ↓
Object Storage
```

Examples:

```text
S3-compatible storage
Cloud object storage
```

For large uploads, pre-signed URLs can reduce API server load.

---

# 43. Pre-Signed Upload

Architecture:

```text
Client
  │
  │ Request upload URL
  ▼
API
  │
  ▼
Generate temporary signed URL
  │
  ▼
Client
  │
  │ Direct upload
  ▼
Object Storage
```

Advantages:

```text
Less API bandwidth
Less API memory usage
Better scalability
Temporary permissions
```

This is both a **performance** and **security** pattern.

---

# 44. Database Security

Your API should not connect to the database using an all-powerful account if unnecessary.

Use:

```text
Least privilege
```

Example:

```text
Application DB user
   ↓
Can read/write application tables
   ↓
Cannot manage database users
Cannot drop unrelated databases
```

---

# 45. Least Privilege

The principle:

> **Give each component only the permissions it needs.**

Example:

```text
Frontend
→ No database access

API
→ Application database access

Analytics worker
→ Read-only analytics data

Migration tool
→ Schema modification access
```

This limits damage if a component is compromised.

---

# 46. Network Segmentation

A production architecture can separate:

```text
Internet
   ↓
Public Load Balancer
   ↓
Private Application Network
   ↓
Private Database Network
```

The database shouldn't normally be directly reachable from the public internet.

Conceptually:

```text
Internet
   │
   ▼
[ Load Balancer ]
   │
   ▼
[ API Servers ]
   │
   ▼
[ Private DB ]
```

---

# 47. Zero Trust

Traditional thinking:

```text
Inside network = trusted
Outside network = untrusted
```

Modern security increasingly follows:

> **Never automatically trust a request simply because it comes from an internal network.**

Verify:

```text
Identity
Device/workload
Permissions
Request context
```

This is the basic idea behind:

> **Zero Trust**

# 49. WAF

WAF means:

> **Web Application Firewall**

It sits in front of web applications and can help detect/block certain malicious patterns.

Conceptually:

```text
Internet
   ↓
WAF
   ↓
Load Balancer
   ↓
Application
```

A WAF can help protect against common web attack patterns, but it isn't a replacement for secure application code.

# 50. Security vs Performance

Security controls often have performance costs.

For example:

```text
Strong encryption
   ↓
CPU overhead
```

Authentication:

```text
Token verification
   ↓
CPU
```

Authorization:

```text
Permission lookup
   ↓
Database/Redis access
```

Rate limiting:

```text
Request tracking
   ↓
Redis/database/network
```

The solution isn't:

> "Remove security."

Instead:

> **Design security efficiently.**

# 51. Caching Authorization

Suppose every request requires:

```text
API
 ↓
Database
 ↓
User permissions
```

This can be expensive.

You might cache relatively stable permission information:

```text
API
 ↓
Redis
 ↓
Permissions
```

But be careful with:

```text
Revocation
Permission changes
Stale authorization
Security-sensitive operations
```

Security correctness always comes first.

---

# 52. Authentication at Scale

Suppose you have:

```text
10 API servers
```

and sessions stored only in:

```text
Server 1 memory
```

A request may hit:

```text
Server 2
```

and not find the session.

You need something like:

```text
Shared session store
```

or a stateless token architecture.

For example:

```text
API 1 ─┐
API 2 ─┼── Redis sessions
API 3 ─┘
```

This connects authentication architecture with horizontal scaling.

---

# 53. Stateless Authentication

With signed access tokens:

```text
API 1 → verify token
API 2 → verify token
API 3 → verify token
```

No centralized session lookup is necessarily required for every request.

This can make horizontal scaling easier.

But revocation and token lifecycle become harder.

That's a classic system-design trade-off.

---

# 54. JWT Key Management

If you're signing JWTs:

```text
Private signing key
      ↓
Sign token
```

Services may verify using:

```text
Public key
```

For asymmetric algorithms.

Important:

```text
Private key → protect carefully
Public key → can be distributed
```

Never expose private signing keys.

---

# 55. Key Rotation

Suppose:

```text
Key A
```

is currently used.

Eventually:

```text
Key B
```

becomes active.

You may need:

```text
Old tokens → still temporarily verifiable
New tokens → signed with Key B
```

Then eventually:

```text
Key A → revoked
```

This is why production authentication systems need proper key management.

# 64. Security vs Performance

Suppose every request performs:

```text
API
 ↓
DB
 ↓
Permission lookup
```

At:

```text
100 RPS
```

maybe fine.

At:

```text
100,000 RPS
```

it may become a bottleneck.

You may need:

```text
Cached permissions
Signed claims
Efficient authorization
Connection pooling
Horizontal scaling
```

But never sacrifice authorization correctness just to reduce latency.

# 65. Security vs Developer Experience


Better:

```text

   ↓
Secret manager
   ↓
Temporary access
```

Security should ideally make the safe path the easy path.

# 67. Interview Question 🎯

### "How would you secure a public API?"

Strong answer:

> I'd use HTTPS, strong authentication, resource-level authorization, input validation, rate limiting, secure headers, carefully configured CORS, request-size limits, secure secret management, least-privilege database access, audit logging, monitoring, and appropriate WAF/API-gateway protections. I'd also protect sensitive endpoints more aggressively than general read endpoints.

---

# 68. Interview Question 🎯

### "JWT vs sessions?"

Strong answer:

> Server-side sessions make revocation and centralized session control straightforward but require shared session storage when horizontally scaling. JWTs can simplify stateless verification across multiple services but make revocation, token lifecycle, and key management more complex. The choice depends on the architecture and security requirements.

Excellent answer.

---

# 69. Interview Question 🎯

### "How do you secure service-to-service communication?"

Strong answer:

> I'd authenticate workloads using mechanisms such as mTLS, signed service tokens, or cloud workload identities, encrypt traffic using TLS, apply least-privilege authorization, and avoid assuming that internal network traffic is automatically trusted.

---

# 70. Interview Question 🎯

### "How do you protect a login endpoint?"

A strong answer:

```text
Rate limiting
+
Credential hashing
+
Secure session/token handling
+
MFA where appropriate
+
Monitoring
+
Brute-force protection
+
Generic authentication errors
```

For example, don't reveal:

```text
"This email exists but the password is wrong."
```

if that would enable account enumeration.

---

# 71. Interview Question 🎯

### "What happens if an attacker gets a JWT?"

A good answer:

> The impact depends on the token's lifetime and privileges. I'd use short-lived access tokens, secure refresh-token handling, appropriate token scopes, key rotation, monitoring, and revocation mechanisms where necessary. I'd also ensure the token doesn't contain unnecessary sensitive information.

# 72. Common Mistakes ❌

### Mistake 1

> "HTTPS means the API is secure."

No.

HTTPS only protects data in transit.

You still need:

```text
Authentication
Authorization
Validation
Rate limiting
Secure storage
```

---

### Mistake 2

> "JWT is encrypted."

Not necessarily.

A normal signed JWT is primarily:

```text
Encoded + signed
```

not automatically encrypted.

Don't put secrets or sensitive information into its payload just because it's a JWT.

---

### Mistake 3

> "Internal services don't need authentication."

Wrong.

Internal services can also be compromised.

---

### Mistake 4

> "Authentication means authorization."

No.

```text
Authentication → Identity
Authorization → Permission
```

---

### Mistake 5

> "API Gateway handles all security."

It shouldn't be your only defense.

Use:

```text
Defense in depth
```

# 🧠 Final Mental Model

When designing any system, ask these **five questions**:

### 1. Scalability

```text
Can it handle more traffic?
```

### 2. Reliability
