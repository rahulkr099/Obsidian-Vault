# Lesson 11.18 — Designing Common Systems ⭐⭐⭐⭐⭐

> **Goal:** Learn how to take the concepts from the previous 17 lessons and apply them to real systems.

This is one of the **most important lessons in Module 11** because system design is not mainly about memorizing Redis, Kafka, MongoDB, or Kubernetes.

It's about being able to say:

> **"Given this problem and this scale, here's how I would design the system, and here's why."**

We'll start with systems that are common in backend interviews and real-world applications.

---

# 1. The System Design Process

Before designing anything, follow this process:

```text
1. Understand requirements
        ↓
2. Estimate scale
        ↓
3. Identify core entities
        ↓
4. Design APIs
        ↓
5. Design database
        ↓
6. Draw high-level architecture
        ↓
7. Identify bottlenecks
        ↓
8. Add caching / queues / replicas
        ↓
9. Think about failures
        ↓
10. Discuss trade-offs
```

This framework is more important than memorizing individual architectures.

---

# 2. Functional vs Non-Functional Requirements

Start every design by separating:

### Functional requirements

What should the system do?

Example for URL shortener:

```text
Create short URL
Redirect short URL
View analytics
Delete URL
```

### Non-functional requirements

How should it behave?

```text
Highly available
Low latency
Scalable
Secure
Reliable
```

# 9. Why Redis?

Redirect traffic can be enormous.

Suppose:

```text
Create URLs = 100/sec
Redirects = 100,000/sec
```

Reads massively outnumber writes.

Instead of:

```text
100,000 requests
       ↓
Database
```

we can do:

```text
100,000 requests
       ↓
Redis
```

The database receives far fewer requests.

```text
   Redis
```

# 11. Short Code Generation

How do we create:

```text
aB92x
```

?

One option:

```text
Base62
```

Characters:

```text
a-z
A-Z
0-9
```

That's:

```text
26 + 26 + 10 = 62
```

possible characters.

---

# 12. Base62 Capacity

Suppose code length is:

```text
6
```

Number of possible codes:

```text
62⁶
```

which is approximately:

```text
56.8 billion
```

That gives enormous theoretical capacity.

Longer codes provide even more combinations.

---

# 13. URL ID Generation

Possible approach:

```text
Database ID
    ↓
Base62 encoding
    ↓
Short code
```

Example:

```text
123456
   ↓
Base62
   ↓
"w7e"
```

But at very large scale, generating IDs through a single database sequence may become a bottleneck.

Other approaches include:

```text
Random IDs
Distributed ID generators
Snowflake-style IDs
Pre-generated ID ranges
```

---

# 14. Collision Problem

Suppose randomly generated:

```text
aB92x
```

already exists.

You need:

```text
unique constraint
```

and collision handling.

For example:

```text
Generate code
     ↓
Try insert
     ↓
Collision?
 ┌────┴────┐
 No        Yes
 │          │
 ▼          ▼
Success   Generate again
```

---

# 15. Analytics Architecture

Don't make redirects wait for analytics.

Bad:

```text
Redirect request
      ↓
Database
      ↓
Store analytics
      ↓
Return redirect
```

This increases latency.

Better:

```text
Redirect
   │
   ├─────────────► Queue
   │                  │
   ▼                  ▼
Redirect           Worker
                       │
                       ▼
                  Analytics DB
```

The user gets the redirect immediately.

# 19. HTTP vs WebSocket

Traditional HTTP:

```text
Client → Request
Server → Response
```

For chat:

```text
Client
  ⇅
Persistent WebSocket connection
  ⇅
Server
```

The server can send:

```text
New message
Typing indicator
Online status
```

without waiting for another HTTP request.

```text
  ▼

  │

```

```text

```


# 21. WebSocket Scaling Problem

Suppose:

```text
Server A
Server B
Server C
```

Rahul is connected to:

```text
Server A
```

Amit is connected to:

```text
Server C
```

Rahul sends:

```text
Hello
```

How does Server A find Amit?

A shared system such as Redis can track connection/presence information:

```text
user:amit → server:C
```

Then:

```text
Server A
   ↓
Redis
   ↓
Server C
   ↓
Amit
```

# 26. Why Use a Queue?

Suppose:

```text
User places order
```

You need:

```text
Email
SMS
Push notification
Analytics
```

Without a queue:

```text
Order API
 ↓
Email
 ↓
SMS
 ↓
Push
 ↓
Analytics
 ↓
Response
```

Potentially very slow.

With queue:

```text
Order API
 ↓
Create order
 ↓
Publish events
 ↓
Return response
```

Workers process everything asynchronously.

# 27. Notification Retry

Suppose email provider fails:

```text
Email Worker
   ↓
Provider
   ↓
Failure
```

Don't necessarily lose the notification.

Use:

```text
Retry
 ↓
Retry
 ↓
Retry
 ↓
Dead Letter Queue
```

---

# 28. Dead Letter Queue

A DLQ stores messages that repeatedly fail.

```text
Queue
  ↓
Worker
  ↓
Failure
  ↓
Retry
  ↓
Retry
  ↓
Still fails
  ↓
DLQ
```

Operations teams can inspect failed messages later.

# 36. Eventual Consistency in Search

Suppose:

```text
Create course
```

Database updates immediately.

Search index may update:

```text
100 ms later
```

So for a short period:

```text
Database → new course exists
Search → course not found
```

This is:

> **Eventual consistency**

Often acceptable for search systems.

---

# 38. Fan-Out on Read

When user opens feed:

```text
Fetch followed users
      ↓
Fetch their posts
      ↓
Merge
      ↓
Sort
      ↓
Return
```

Simple, but potentially expensive.

---

# 39. Fan-Out on Write

When someone posts:

```text
New post
   ↓
Find followers
   ↓
Add post to their feed
```

Then reading the feed is fast:

```text
User
 ↓
Feed cache
 ↓
Posts
```

But writing becomes expensive for users with millions of followers.

---

# 40. Hybrid Feed

Large systems may combine both.

Normal users:

```text
Fan-out on write
```

Celebrity accounts:

```text
Fan-out on read
```

Why?

Suppose:

```text
Celebrity
 ↓
50 million followers
```

Copying the post into 50 million feeds immediately is expensive.

So:

```text
Normal users → write fan-out
Celebrities → read fan-out
```

This is a classic system-design trade-off.

# 54. System Design Trade-Offs

Almost every design involves trade-offs.

For example:

### Cache

```text
Faster reads
     vs
Stale data
```

### Replicas

```text
More read capacity
     vs
Replication lag
```

### Microservices

```text
Independent scaling
     vs
Operational complexity
```

### Async processing

```text
Faster user response
     vs
Eventual consistency
```

### Strong consistency

```text
Correct latest state
     vs
Higher coordination cost
```

A good engineer explains both sides.

# 63. Final Mental Model ⭐

System design is essentially:

```text
Requirements
      ↓
Scale
      ↓
Data
      ↓
Traffic
      ↓
Architecture
      ↓
Bottlenecks
      ↓
Failure modes
      ↓
Security
      ↓
Trade-offs
```

And the most important question is always:

> **"Why?"**

Why Redis?

> Because database reads are too expensive.

Why Kafka?

> Because we need durable, scalable asynchronous event processing.

Why CDN?

> Because users are globally distributed and static/video content is expensive to serve from the origin.

Why read replicas?

> Because reads significantly outnumber writes.

Why object storage?

> Because large files shouldn't consume application-server resources.

That's system design.

# 🚀 Next: Lesson 11.19 — System Design Interview Framework

This will turn everything you've learned into a repeatable interview process:

```text
Interviewer gives problem
        ↓
Clarify requirements
        ↓
Estimate capacity
        ↓
Identify APIs
        ↓
Design data model
        ↓
Draw architecture
        ↓
Explain each component
        ↓
Find bottlenecks
        ↓
Scale the system
        ↓
Discuss failures
        ↓
Discuss security
        ↓
Explain trade-offs
```

We'll also practice how to **speak while designing**, what questions to ask the interviewer, what mistakes to avoid, and how to handle changes in requirements during the interview.
