# Lesson 11.19 — System Design Interview Framework ⭐⭐⭐⭐⭐

> **Goal:** Learn a repeatable method for solving open-ended system design problems in interviews.

You've already learned the building blocks:

```text
Scalability
Caching
Databases
Replication
Sharding
Queues
Consistency
Fault tolerance
High availability
API design
Performance
Security
```

Now the important question is:

> **How do I put all of these together when an interviewer gives me a completely new problem?**

That's what this lesson teaches.

---

# 1. What Is a System Design Interview?

The interviewer might say:

> "Design a URL shortener."

or:

> "Design WhatsApp."

or:

> "Design YouTube."

or:

> "Design an e-commerce system."

There isn't one perfect answer.

The interviewer wants to see whether you can:

```text
Understand ambiguity
        ↓
Ask useful questions
        ↓
Estimate scale
        ↓
Break the problem down
        ↓
Design architecture
        ↓
Identify bottlenecks
        ↓
Make trade-offs
        ↓
Explain your decisions
```

---

# 2. The Biggest Mistake Beginners Make ❌

They immediately start drawing:

```text
Client
  ↓
Load Balancer
  ↓
Redis
  ↓
Kafka
  ↓
MongoDB
  ↓
Kubernetes
```

Then the interviewer asks:

> "Why Kafka?"

And the candidate says:

> "Because it's scalable."

That's not enough.

The better approach is:

> **Requirements → scale → architecture → technology choices.**

---

# 3. The 6-Step Framework

Use this framework:

```text
1. Requirements
       ↓
2. Capacity Estimation
       ↓
3. API & Data Model
       ↓
4. High-Level Architecture
       ↓
5. Deep Dive
       ↓
6. Bottlenecks & Trade-offs
```

You can remember it as:

> **R → E → D → A → D → T**

Requirements → Estimation → Data → Architecture → Deep Dive → Trade-offs.

---

# 4. Step 1 — Clarify Requirements

The first thing you should do is ask questions.

Suppose the interviewer says:

> "Design a URL shortener."

Don't immediately design it.

Ask:

```text
What features do we need?
How many users?
How many URLs created?
How many redirects?
Do URLs expire?
Do we need custom aliases?
Do we need analytics?
Is the system global?
What availability is expected?
```

---

# 5. Functional Requirements

Determine:

> **What does the system need to do?**

For URL shortener:

```text
Create short URL
Redirect short URL
Delete URL
Custom alias
Expiration
Analytics
```

Don't add unnecessary features.

You can say:

> "I'll focus on creating URLs, redirecting URLs, and basic analytics unless you'd like me to include additional features."

This shows you're controlling scope.

---

# 6. Non-Functional Requirements

Then ask:

> **How should the system behave?**

Examples:

```text
High availability
Low latency
Scalability
Durability
Consistency
Security
```

For a URL shortener:

```text
Redirect latency < 100ms
High availability
Billions of redirects
```

Now your architecture has direction.

---

# 7. Functional vs Non-Functional

Example:

|Type|Requirement|
|---|---|
|Functional|Create short URL|
|Functional|Redirect URL|
|Functional|View analytics|
|Non-functional|High availability|
|Non-functional|Low latency|
|Non-functional|Handle high traffic|

Remember:

> **Functional = what the system does.**

> **Non-functional = how well the system does it.**

---

# 8. Step 2 — Capacity Estimation

Now estimate scale.

Suppose:

```text
100 million users
10 million URLs/day
1 billion redirects/day
```

Calculate:

```text
Average writes/sec
Average reads/sec
Peak traffic
Storage
Bandwidth
```

You don't need exact numbers.

You need reasonable approximations.

---

# 9. Convert Daily Traffic to RPS

Suppose:

```text
1 billion redirects/day
```

There are:

```text
86,400 seconds/day
```

Therefore:

```text
1,000,000,000 / 86,400
≈ 11,574 requests/sec
```

So approximately:

```text
11.6K RPS
```

Average.

---

# 10. Estimate Peak Traffic

Real traffic isn't perfectly uniform.

A common interview assumption might be:

```text
Peak = 3 × average
```

Then:

```text
11.6K × 3
≈ 34.8K RPS
```

So you could design for roughly:

```text
35K RPS peak
```

Always state your assumption.

For example:

> "I'll assume peak traffic is roughly three times average traffic."

---

# 11. Storage Estimation

Suppose:

```text
10 million URLs/day
```

Average record size:

```text
500 bytes
```

Storage/day:

```text
10,000,000 × 500
= 5,000,000,000 bytes
≈ 5 GB/day
```

Year:

```text
5 GB × 365
≈ 1.8 TB/year
```

Then account for:

```text
Indexes
Replication
Backups
Metadata
```

You might estimate:

```text
2–4 TB/year
```

depending on assumptions.

---

# 12. Back-of-the-Envelope Math

You don't need perfect calculations.

The interviewer wants to know:

> **Can you reason about scale?**

Useful conversions:

```text
1 KB ≈ 1,000 bytes
1 MB ≈ 1,000 KB
1 GB ≈ 1,000 MB
1 TB ≈ 1,000 GB
```

And:

```text
1 day = 86,400 seconds
```

---

# 13. Step 3 — Identify Core Entities

Before designing the database, identify the important objects.

URL shortener:

```text
URL
User
ClickEvent
```

E-commerce:

```text
User
Product
Cart
Order
Payment
Inventory
```

Chat:

```text
User
Conversation
Message
```

This gives you the foundation for data modeling.

---

# 14. Step 4 — Design APIs

Now define the important API endpoints.

For URL shortener:

```http
POST /api/v1/urls
GET /:shortCode
GET /api/v1/urls/:id/analytics
DELETE /api/v1/urls/:id
```

You don't need to design every endpoint.

Focus on the core operations.

---

# 15. API Request Example

```http
POST /api/v1/urls
```

Request:

```json
{
  "originalUrl": "https://example.com/article"
}
```

Response:

```json
{
  "shortCode": "aB92x",
  "shortUrl": "https://short.example/aB92x"
}
```

Now the interviewer understands how clients interact with your system.

---

# 16. Step 5 — Data Model

For example:

```text
URL
├── id
├── shortCode
├── originalUrl
├── userId
├── createdAt
└── expiresAt
```

Analytics:

```text
ClickEvent
├── id
├── urlId
├── timestamp
├── country
├── device
└── referrer
```

At large scale, you might separate analytics storage from transactional URL data.

---

# 17. Step 6 — Draw the Simplest Architecture First

Start simple.

```text
Client
   │
   ▼
API Server
   │
   ▼
Database
```

Then ask:

> "What problems will appear as traffic increases?"

This is a very powerful interview technique.

---

# 18. Add Load Balancing

If one API server isn't enough:

```text
                 Load Balancer
                 /     |     \
                ▼      ▼      ▼
              API    API    API
                \      |     /
                 \     |    /
                   Database
```

Now you have:

```text
Horizontal scaling
Fault tolerance
Traffic distribution
```

---

# 19. Add Redis

If reads are extremely frequent:

```text
Load Balancer
      │
      ▼
   API Servers
      │
      ▼
    Redis
      │
      ▼
   Database
```

Explain:

> "I'll use Redis as a cache because redirects are read-heavy and the same short codes may be accessed frequently."

Now Redis has a reason.

---

# 20. Add Replicas

If database reads become a bottleneck:

```text
                Primary
               /       \
              ▼         ▼
         Replica 1   Replica 2
```

Write:

```text
Primary
```

Read:

```text
Replicas
```

Explain the trade-off:

> "Read replicas increase read capacity, but replication lag means some reads may be slightly stale."

---

# 21. Add a Queue

Suppose analytics processing is expensive.

Don't do:

```text
Redirect
  ↓
Store analytics
  ↓
Return response
```

Instead:

```text
Redirect
   │
   ├─────────────► Queue
   │                  │
   ▼                  ▼
Response            Worker
                       │
                       ▼
                  Analytics DB
```

Explain:

> "Analytics don't need to block the redirect, so I'll process them asynchronously."

---

# 22. Final URL Shortener Architecture

You can gradually arrive at:

```text
                         Client
                           │
                           ▼
                         CDN
                           │
                           ▼
                    Load Balancer
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
           API 1         API 2         API 3
             │             │             │
             └─────────────┼─────────────┘
                           │
                       ┌───┴───┐
                       ▼       ▼
                     Redis   Database
                               │
                         ┌─────┴─────┐
                         ▼           ▼
                      Primary     Replicas

Redirect analytics
       │
       ▼
     Queue
       │
       ▼
    Workers
       │
       ▼
 Analytics Storage
```

That's a strong architecture.

---

# 23. Step 7 — Identify Bottlenecks

Now ask:

> **What's likely to break first?**

Potential bottlenecks:

```text
Database reads
Database writes
Redis memory
API CPU
Network bandwidth
Queue throughput
External APIs
Storage
```

For URL shortener:

```text
Redirect traffic
      ↓
Redis
      ↓
Database
```

The database is protected by the cache.

---

# 24. Think About Failure

Now ask:

> "What happens if Redis goes down?"

You should have an answer:

```text
Redis unavailable
      ↓
API falls back to database
      ↓
Higher database load
```

Then perhaps:

```text
Circuit breaker
Rate limiting
Database capacity
Redis replication
```

depending on the required resilience.

---

# 25. Failure Scenario: Database Down

What happens?

```text
API
 ↓
Database ❌
```

Possible response:

```text
503 Service Unavailable
```

But cached redirects might still work:

```text
Redis
 ↓
Cached URL
 ↓
Redirect
```

This is an example of graceful degradation.

---

# 26. Failure Scenario: Queue Down

If analytics queue is unavailable:

```text
Redirect
   ↓
Queue ❌
```

Should the redirect fail?

Probably not.

The core functionality is:

```text
Redirect
```

Analytics are secondary.

You could:

```text
Log locally
Retry
Buffer temporarily
Drop non-critical analytics
```

depending on requirements.

This is a great interview point:

> **Critical functionality should be isolated from non-critical functionality.**

---

# 27. Deep Dive

After the high-level architecture, the interviewer may ask:

> "How does Redis work here?"

or:

> "How do you generate short codes?"

or:

> "How do you handle 100K RPS?"

Now go deeper into that specific component.

Don't explain everything at once.

---

# 28. Example Deep Dive — Redis

Suppose:

```text
100K redirects/sec
```

You might say:

> "I'd cache shortCode → originalURL mappings in Redis. The application first checks Redis. On a miss, it reads from the database and populates Redis."

Then discuss:

```text
TTL
Cache eviction
Replication
Memory
Hot keys
Failure fallback
```

That's enough unless the interviewer asks for more.

---

# 29. Hot Keys

Suppose one URL becomes extremely popular:

```text
/abc123
```

and receives:

```text
500,000 requests/sec
```

Now one Redis key becomes a:

> **Hot key**

Potential solutions:

```text
Local in-process caching
Replicated cache reads
CDN caching
Request distribution
Special handling for popular URLs
```

This is the kind of advanced bottleneck discussion that impresses interviewers.

---

# 30. Trade-Off Discussion

Every architecture needs trade-offs.

For example:

### Redis

```text
Pros:
Fast
Low latency
Reduces DB load

Cons:
Extra infrastructure
Cache invalidation
Memory cost
Potential stale data
```

### Read Replicas

```text
Pros:
More read capacity
Improved scalability

Cons:
Replication lag
More infrastructure
Consistency complexity
```

### Queue

```text
Pros:
Async processing
Traffic smoothing
Retry support

Cons:
Eventual consistency
Operational complexity
Duplicate processing
```

---

# 31. Don't Say "Best"

Avoid:

> "Redis is the best database."

Instead:

> "Redis is a good fit here because the workload is read-heavy and requires low-latency lookups."

System design is about:

```text
Requirements
      ↓
Trade-offs
      ↓
Decision
```

not:

```text
Technology
      ↓
Use everywhere
```

---

# 32. Handling Interviewer Changes

This is very important.

Suppose you design:

```text
1 million users
```

Then interviewer says:

> "Actually, we now have 100 million users."

Don't panic.

Say:

> "That changes the scaling requirements. I'd revisit the database capacity, caching strategy, partitioning, traffic distribution, and possibly introduce read replicas or sharding."

Then modify your design.

---

# 33. Requirement Change Example

Initial:

```text
10K RPS
```

Architecture:

```text
Load Balancer
 ↓
API × 3
 ↓
Database
```

Interviewer:

> "Traffic increases to 1M RPS."

Now:

```text
CDN
 ↓
Load Balancer
 ↓
API × many
 ↓
Redis Cluster
 ↓
Sharded Database
```

You don't need to redraw everything.

Explain what changed and why.

---

# 34. When Requirements Conflict

Interviewer:

> "We need strong consistency and extremely low latency globally."

Don't blindly say:

> "Sure."

Instead identify the trade-off:

```text
Strong consistency
       vs
Global low latency
```

You might explain:

> "Strong global consistency requires coordination between regions, which can increase latency. I'd clarify which operations truly require strong consistency and where eventual consistency is acceptable."

This demonstrates maturity.

---

# 35. Handling "Why?"

The interviewer may repeatedly ask:

> Why Redis?

Answer:

> "Because this workload has frequent reads and requires low latency."

Then:

> Why not PostgreSQL?

> "PostgreSQL remains the source of truth, but using Redis avoids repeatedly hitting the database for hot reads."

Then:

> Why not just use more PostgreSQL replicas?

> "Replicas help read scaling, but Redis can provide much lower latency for frequently accessed key-value data and reduce database pressure."

That's how you defend decisions.

---

# 36. System Design Communication

Your speaking style matters.

Don't talk continuously for 30 minutes.

Use checkpoints.

Example:

> "I'll start with the requirements."

Then:

> "I'll estimate the traffic."

Then:

> "Based on those numbers, here's the initial architecture."

Then:

> "I'd like to deep-dive into the database and caching because those are likely bottlenecks."

This keeps the interviewer involved.

---

# 37. Think Out Loud

Don't silently draw for five minutes.

Explain:

> "I'm choosing Redis here because the read-to-write ratio is very high."

or:

> "I'm separating analytics from the main database because analytics are write-heavy and shouldn't affect redirect latency."

The interviewer needs to see your reasoning.

---

# 38. Ask Questions, But Don't Overdo It

Good:

```text
What is the expected scale?
What operations are most important?
What latency is acceptable?
Do we require strong consistency?
Is global availability required?
```

Bad:

```text
What color is the UI?
What font does the application use?
```

Stay focused on architecture.

---

# 39. Don't Spend Too Long on APIs

System design interviews are not usually coding interviews.

You don't need:

```text
50 endpoints
```

Usually:

```text
3–5 important APIs
```

are enough to establish the contract.

Spend more time on:

```text

Data
Architecture
Bottlenecks
Trade-offs
```


### MongoDB

Good when you need:

```text

```

### Redis

# 46. Full Interview Answer Example

Interviewer:

> "Design a URL shortener."

You:

### Step 1 — Requirements

> "I'll assume users can create short URLs, redirect them, and view basic analytics. I'll assume URLs may optionally expire."

### Step 2 — Scale

> "Let's assume 10 million URLs created per day and 1 billion redirects per day, giving around 11.6K average redirect RPS. Assuming 3× peak traffic, I'd design for roughly 35K RPS."

### Step 3 — Data

> "I'll store the short code, original URL, owner, creation time, and expiration in the primary database. Click events can be stored separately."

### Step 4 — Architecture

```text
Client
 ↓
Load Balancer
 ↓
API Servers
 ↓
Redis
 ↓
Database
```

### Step 5 — Scale

> "Because redirects are read-heavy, Redis will cache short-code mappings. If database reads increase, I'd add read replicas."

### Step 6 — Analytics

> "Analytics shouldn't block redirects, so I'll publish click events to a queue and process them asynchronously."

### Step 7 — Reliability

> "If Redis fails, the service can fall back to the database. Redis replication and database replication can improve availability."

### Step 8 — Security

> "I'd validate destination URLs, rate-limit creation endpoints, authenticate analytics APIs, and prevent abuse such as malicious redirects."

### Step 9 — Monitoring

> "I'd monitor redirect latency, p95/p99, error rate, cache hit ratio, database latency, and queue depth."

That's a strong answer.

# 48. Common Interview Mistakes ❌

### 1. Jumping into architecture

```text
"Let's use Kafka."
```

before understanding the requirements.

---

### 2. Overengineering

```text
10 users
 ↓
Kubernetes + Kafka + 20 microservices
```

No.

---

### 3. Ignoring scale

You can't design the same architecture for:

```text
1K users
```

and:

```text
1B users
```

---

### 4. Ignoring failures

Always ask:

```text
What if Redis fails?
What if DB fails?
What if network fails?
What if worker crashes?
```

---

### 5. Ignoring consistency

Ask:

```text
Does this data need to be immediately consistent?
```

---

### 6. Ignoring security

Mention:

```text
Auth
Authorization
Rate limiting
Validation
HTTPS
Secrets
```

---

### 7. Giving one-word answers

Bad:

> "Use Redis."

Better:

> "I'd use Redis for frequently accessed URL mappings because redirects are read-heavy and latency-sensitive."

# 49. A Powerful Interview Habit

Whenever you propose a component, complete this sentence:

> **"I'm using X because..."**

Examples:

```text
I'm using Redis because...

I'm using PostgreSQL because...

I'm using Kafka because...

I'm using a queue because...

I'm using a CDN because...

I'm using read replicas because...
```

If you can't complete that sentence, you probably don't need the component yet.

# 52. System Design Is Iterative

Your first architecture doesn't need to be perfect.

Start:

```text
Simple
```

Then:

```text
Traffic increases
       ↓
Add load balancing
       ↓
Reads increase
       ↓
Add caching
       ↓
DB grows
       ↓
Add replicas/sharding
       ↓
Background work grows
       ↓
Add queues/workers
       ↓
Global users
       ↓
CDN/multi-region
```

That's how real systems evolve.

---

# 53. The Most Important Principle ⭐

Don't design:

> **"The biggest system possible."**

Design:

> **"The simplest system that satisfies the current requirements, while leaving a reasonable path to scale."**

This is one of the most valuable engineering principles you can carry into your career.
