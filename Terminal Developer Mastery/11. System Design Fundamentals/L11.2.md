# Lesson 11.2 — Capacity Estimation ⭐⭐⭐⭐⭐

> **Goal:** Learn how to estimate the amount of traffic, storage, bandwidth, memory, and compute a system will need before designing its architecture.

Capacity estimation is one of the most useful system-design skills because it answers:

> **"How big does this system actually need to be?"**

You don't need exact numbers. You need **reasonable estimates that help you make architectural decisions**.

---

# 1. What Is Capacity Estimation?

Imagine you're asked:

> Design a URL shortener for 100 million users.

Before choosing:

- MongoDB or PostgreSQL?
    
- Redis?
    
- How many servers?
    
- Do we need Kafka?
    
- Do we need database sharding?
    

you need to understand the scale.

For example:

```text
100 million users
        ↓
How many active users?
        ↓
How many requests?
        ↓
How much data?
        ↓
How much bandwidth?
        ↓
How much CPU/memory?
```

This process is called **capacity estimation**.

---

# 2. Why Is Capacity Estimation Important?

Suppose you build:

```text
Node.js
   ↓
MongoDB
```

and assume:

```text
100 requests/sec
```

But the real system receives:

```text
100,000 requests/sec
```

Your architecture may collapse.

On the other hand, if the system only receives:

```text
10 requests/sec
```

and you build:

```text
20 microservices
Kafka
Kubernetes
Redis Cluster
Multi-region database
```

you've created unnecessary complexity.

So:

> **Capacity estimation helps you choose an architecture appropriate for the workload.**

---

# 3. The Main Numbers We Estimate

During system design, you'll commonly estimate:

```text
1. Users
2. Daily Active Users
3. Requests per second
4. Read/write ratio
5. Storage
6. Bandwidth
7. Memory
8. CPU
9. Peak traffic
```

Let's understand each one.

---

# 4. Users

Start with the total number of users.

Example:

```text
Registered users = 10 million
```

But this doesn't mean:

```text
10 million users
→
10 million active simultaneously
```

Usually only a portion of users are active.

---

# 5. DAU — Daily Active Users

**DAU = Daily Active Users**

Suppose:

```text
Total users = 10 million
```

and:

```text
20% use the application every day
```

Then:

```text
DAU = 10,000,000 × 20%

    = 2,000,000
```

So:

> **2 million daily active users**

---

# 6. MAU — Monthly Active Users

Another useful metric is:

**MAU = Monthly Active Users**

Suppose:

```text
Total registered users = 10 million
Monthly active users = 6 million
```

Then:

```text
MAU = 6 million
```

DAU and MAU help us understand actual usage.

---

# 7. Requests Per Second — RPS

This is one of the most important numbers.

**RPS = Requests Per Second**

Suppose:

```text
DAU = 1,000,000
```

Each user makes:

```text
10 requests/day
```

Total requests:

```text
1,000,000 × 10

= 10,000,000 requests/day
```

Now convert that to requests per second.

One day:

```text
24 × 60 × 60
= 86,400 seconds
```

Therefore:

```text
RPS = 10,000,000 / 86,400

    ≈ 116 RPS
```

So our average traffic is approximately:

> **116 requests/sec**

---

# 8. Average RPS vs Peak RPS

This is extremely important.

Traffic isn't evenly distributed throughout the day.

For example:

```text
00:00 ─── Low
06:00 ─── Low
09:00 ─── Medium
12:00 ─── High
18:00 ─── Very High
21:00 ─── High
23:00 ─── Low
```

If average traffic is:

```text
116 RPS
```

we might assume peak traffic is:

```text
5 × average
```

So:

```text
Peak RPS = 116 × 5
         = 580 RPS
```

The exact multiplier depends on the application.

A common interview assumption might be:

```text
Peak = 2–5 × average
```

But **state your assumption**.

---

# 9. Back-of-the-Envelope Calculation

System design doesn't usually require perfect mathematical precision.

Instead, we make quick estimates.

For example:

```text
1 million users
× 10 requests/day
= 10 million requests/day
```

Then:

```text
10 million / 86,400
≈ 116 RPS
```

Then:

```text
Peak ≈ 500–600 RPS
```

That's already enough to influence architectural decisions.

This is called a:

> **Back-of-the-envelope calculation**

---

# 10. Read vs Write Traffic

Suppose your application has:

```text
1000 RPS
```

and:

```text
90% reads
10% writes
```

Then:

```text
Read RPS:

1000 × 90%
= 900 RPS
```

and:

```text
Write RPS:

1000 × 10%
= 100 RPS
```

So:

```text
Total = 900 reads + 100 writes
```

This distinction matters because reads and writes can be handled differently.

For example:

```text
Reads
  ↓
Redis
  ↓
Database

Writes
  ↓
Database
```

Later, read replicas can also help.

---

# 11. Read/Write Ratio

A system might have:

```text
10 : 1
```

read-to-write ratio.

Meaning:

```text
10 reads
1 write
```

Examples:

### Social media

```text
Many users read posts
Few users create posts
```

Potentially very read-heavy.

### Analytics ingestion

```text
Huge number of events written
Relatively fewer reads
```

Potentially write-heavy.

This influences:

- database design
    
- caching
    
- replication
    
- indexing
    
- architecture
    

---

# 12. Storage Estimation

Now suppose we need to store data.

Example:

```text
1 million new URLs/day
```

Each URL record requires approximately:

```text
500 bytes
```

Daily storage:

```text
1,000,000 × 500 bytes
```

= 500,000,000 bytes

≈ **500 MB/day**

Monthly:

```text
500 MB × 30
≈ 15 GB/month
```

Yearly:

```text
15 GB × 12
≈ 180 GB/year
```

So approximately:

> **180 GB/year**

And this is before considering indexes, replication, backups, metadata, etc.

---

# 13. Always Account for Overhead

Our previous calculation said:

```text
180 GB/year
```

But the actual database may need more.

Why?

Because we also store:

```text
Indexes
Metadata
Replication
Backups
Transaction logs
Database overhead
```

Suppose we estimate:

```text
30% overhead
```

Then:

```text
180 GB × 1.3

= 234 GB
```

So we'd plan around:

> **~234 GB/year**

Again, we're estimating.

---

# 14. Storage Formula

A simple formula:

```text
Storage/day

= Records/day × Average record size
```

Then:

```text
Storage/year

= Storage/day × 365
```

Then add overhead:

```text
Final storage

= Raw storage × (1 + overhead)
```

---

# 15. Example: URL Shortener Storage

Suppose:

```text
New URLs/day = 5 million
```

Average record:

```text
1 KB
```

Then:

```text
5 million × 1 KB

= 5 GB/day
```

Monthly:

```text
5 × 30

= 150 GB/month
```

Yearly:

```text
150 × 12

= 1.8 TB/year
```

With 30% overhead:

```text
1.8 TB × 1.3

≈ 2.34 TB/year
```

Now we have a much clearer understanding of our storage requirements.

---

# 16. Bandwidth Estimation

Bandwidth tells us how much data travels through the network.

Suppose:

```text
RPS = 1,000
```

Average response:

```text
100 KB
```

Then:

```text
Bandwidth/sec

= 1,000 × 100 KB

= 100,000 KB/sec
```

Approximately:

```text
100 MB/sec
```

So our outgoing bandwidth is around:

> **100 MB/s**

---

# 17. Convert Bandwidth to Daily Data

If we have:

```text
100 MB/sec
```

Then:

```text
100 × 86,400
```

≈

```text
8.64 TB/day
```

That's a lot of traffic.

This immediately tells us that we may need:

- CDN
    
- compression
    
- caching
    
- optimized responses
    
- efficient APIs
    

---

# 18. Request Size Matters Too

Bandwidth isn't only about responses.

You can have:

```text
Incoming bandwidth
```

and:

```text
Outgoing bandwidth
```

For example:

```text
Client
  │
  │ 5 KB request
  ▼
Server
  │
  │ 50 KB response
  ▼
Client
```

At:

```text
1,000 RPS
```

Incoming:

```text
1,000 × 5 KB
= 5 MB/s
```

Outgoing:

```text
1,000 × 50 KB
= 50 MB/s
```

So we need to consider both.

---

# 19. Memory Estimation

Memory estimation becomes particularly important when using caches.

Suppose:

```text
10 million frequently accessed objects
```

Each object:

```text
1 KB
```

Then:

```text
10 million × 1 KB
= 10 GB
```

But Redis also needs metadata and internal overhead.

So we might provision significantly more than 10 GB.

For example:

```text
Raw data ≈ 10 GB
Overhead ≈ 30%
```

Then:

```text
≈ 13 GB
```

We may choose:

```text
16 GB Redis
```

depending on the workload and eviction strategy.

---

# 20. Cache Estimation Example

Suppose our URL shortener receives:

```text
100 million redirects/day
```

and:

```text
20% of URLs generate 80% of traffic
```

This is an example of the **Pareto principle**.

We may not need to cache every URL.

Instead:

```text
Hot URLs
   ↓
Redis
```

while less frequently accessed URLs can come from:

```text
MongoDB
```

This is one reason capacity estimation and caching strategy are closely connected.

---

# 21. CPU Estimation

CPU estimation is harder because it depends heavily on workload.

For example:

```text
Simple API
```

might require very little CPU.

But:

```text
Video encoding
Image processing
Machine learning inference
Encryption
Complex calculations
```

can require much more CPU.

A simple approach is to benchmark the application.

Suppose one server can reliably process:

```text
2,000 RPS
```

and our peak load is:

```text
10,000 RPS
```

Then:

```text
10,000 / 2,000
= 5 servers
```

We might actually deploy:

```text
6–7 servers
```

to provide headroom and redundancy.

---

# 22. Don't Run Servers at 100% Capacity

This is an important production principle.

Suppose:

```text
Server capacity = 2,000 RPS
```

and:

```text
Traffic = 2,000 RPS
```

You're running at:

```text
100%
```

That's dangerous.

A sudden spike could cause:

```text
Latency ↑
CPU ↑
Timeouts ↑
Errors ↑
```

Instead, we might aim for something like:

```text
60–70% utilization
```

depending on workload and scaling strategy.

Then we have room for traffic spikes.

---

# 23. Capacity Headroom

Suppose:

```text
Expected peak = 10,000 RPS
```

We shouldn't necessarily provision exactly:

```text
10,000 RPS
```

Maybe we target:

```text
15,000 RPS capacity
```

That's:

```text
50% headroom
```

This protects against:

- unexpected traffic
    
- traffic spikes
    
- server failures
    
- deployments
    
- maintenance
    

---

# 24. A Complete Example

Let's design a hypothetical URL shortener.

Requirements:

```text
Registered users = 10 million
DAU = 2 million
Requests/user/day = 20
```

### Step 1 — Daily requests

```text
2 million × 20

= 40 million requests/day
```

### Step 2 — Average RPS

```text
40,000,000 / 86,400

≈ 463 RPS
```

### Step 3 — Peak RPS

Assume:

```text
Peak = 5 × average
```

Therefore:

```text
463 × 5

≈ 2,315 RPS
```

So we should design for roughly:

> **2.3K peak RPS**

---

# 25. Storage Calculation

Suppose:

```text
New URLs/day = 2 million
```

Average record:

```text
500 bytes
```

Then:

```text
2 million × 500 bytes

= 1 GB/day
```

Yearly:

```text
1 × 365

= 365 GB/year
```

With 30% overhead:

```text
365 × 1.3

≈ 475 GB/year
```

So approximately:

> **~475 GB/year**

before considering additional backup/replica policies.

---

# 26. Architecture Based on These Numbers

Now our architecture has some justification.

```text
                         Clients
                            │
                            ▼
                       Load Balancer
                            │
                ┌───────────┼───────────┐
                ▼           ▼           ▼
             Server      Server      Server
                │           │           │
                └───────────┼───────────┘
                            │
                       ┌────▼────┐
                       │  Redis  │
                       └────┬────┘
                            │
                       ┌────▼────┐
                       │ MongoDB │
                       └─────────┘
```

Why?

### Multiple servers

Peak:

```text
~2,315 RPS
```

So one server may not be enough.

### Redis

URL redirects are likely read-heavy.

Caching can reduce database pressure.

### MongoDB

Our data model naturally fits a document-oriented model.

Later we might add:

```text
MongoDB replica set
```

or another scaling strategy.

---

# 27. Important Approximation Rules

You don't need a calculator for every small calculation.

Memorize:

```text
1 day = 86,400 sec
       ≈ 100,000 sec
```

This approximation is very useful.

Therefore:

```text
100 million requests/day

≈ 100,000,000 / 100,000

≈ 1,000 RPS
```

---

# 28. Useful Time Conversions

Memorize these:

```text
1 minute  = 60 sec
1 hour    = 3,600 sec
1 day     = 86,400 sec
1 month   ≈ 2.6 million sec
1 year    ≈ 31.5 million sec
```

For interviews, approximation is completely acceptable if you clearly state your assumptions.

---

# 29. Powers of Ten

System design uses large numbers constantly.

Remember:

```text
1 thousand       = 10³
1 million        = 10⁶
1 billion        = 10⁹
1 trillion       = 10¹²
```

For storage:

```text
1 KB ≈ 10³ bytes
1 MB ≈ 10⁶ bytes
1 GB ≈ 10⁹ bytes
1 TB ≈ 10¹² bytes
```

Exact binary units exist, but for back-of-the-envelope calculations, these approximations are usually enough.

# 31. Common Beginner Mistakes ❌

### Mistake 1 — Using total users as concurrent users

```text
10 million users
≠
10 million simultaneous users
```

---

### Mistake 2 — Using average traffic as peak traffic

```text
Average RPS ≠ Peak RPS
```

Always consider traffic spikes.

---

### Mistake 3 — Ignoring read/write ratio

A system with:

```text
90% reads
10% writes
```

has very different requirements from:

```text
10% reads
90% writes
```

---

### Mistake 4 — Ignoring overhead

If your calculation says:

```text
500 GB
```

don't immediately provision exactly 500 GB.

Think about:

```text
Indexes
Replication
Backups
Logs
Metadata
Headroom
```

---

### Mistake 5 — Pretending estimates are exact

Don't say:

> "We need exactly 7 servers."

Say:

> "Based on our estimated peak traffic and assuming each server handles around 2,000 RPS, we'd need roughly 2–3 servers initially, with additional capacity for redundancy and traffic spikes."

That's much more realistic.

# 32. Interview Example 🎯

**Interviewer:**

> Design a service with 10 million daily active users. Each user makes 10 requests per day. Estimate the RPS.

You should think:

```text
10M users
×
10 requests/day

=
100M requests/day
```

Then:

```text
100M / 86,400

≈ 1,157 RPS
```

So:

> Average ≈ **1.2K RPS**

If we assume a 5× peak:

```text
1,157 × 5
≈ 5,785 RPS
```

So:

> Peak ≈ **5.8K RPS**

That's already a useful system-design number.

# 33. Your Mental Model 🧠

Think of capacity estimation as:

```text
                    USERS
                      ↓
                 ACTIVE USERS
                      ↓
                REQUESTS/DAY
                      ↓
                    RPS
                      ↓
                 PEAK RPS
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
     Storage       Bandwidth      Compute
        ↓             ↓             ↓
     Database        Network       Servers
        ↓
      Cache
```

This gives you the numbers required to make architectural decisions.

---

# 🔥 The Most Important Formulas

Keep these somewhere in your system-design notes:

```text
DAU
= Total Users × Daily Active %

Requests/day
= DAU × Requests/User/Day

Average RPS
= Requests/day ÷ 86,400

Peak RPS
= Average RPS × Peak Factor

Storage/day
= Records/day × Record Size

Storage/year
= Storage/day × 365

Bandwidth/sec
= RPS × Average Request/Response Size

Servers
≈ Peak RPS ÷ Capacity per Server
```

And remember:

> **These are estimates, not exact measurements.**
