# 14. E-Commerce Critical Requirement

One of the hardest problems:

> **Inventory consistency.**

Suppose:

```text
Product stock = 1
```

Two users purchase simultaneously:

```text
User A ─┐
        ├──> Product
User B ─┘
```

Without proper concurrency control:

```text
A → sees 1
B → sees 1
A → buys
B → buys
```

Now:

```text
Stock = -1 ❌
```

You need atomic inventory handling.

# 15. Payment Architecture

Never assume:

```text
Order created = payment successful
```

A safer flow:

```text
Create Order
     ↓
Payment Processing
     ↓
Payment Provider
     ↓
Webhook
     ↓
Verify Payment
     ↓
Update Order
```

The payment provider's webhook should be treated carefully and verified.

---

# 16. Idempotency in Payments

Suppose the client sends:

```text
POST /payment
```

twice because of a network retry.

You don't want:

```text
₹1000
+
₹1000
=
₹2000 ❌
```

Use an idempotency key:

```text
Idempotency-Key: abc123
```

Then:

```text
First request
 → process

Second request
 → return previous result
```

This is extremely important for financial operations.

# 21. Notification Reliability

Suppose SMS provider fails.

```text
Worker
 ↓
SMS Provider ❌
```

Use:

```text
Retry
 ↓
Retry
 ↓
Retry
 ↓
Dead Letter Queue
```

Also use:

```text
Exponential backoff
```

Example:

```text
1 sec
2 sec
4 sec
8 sec
...
```

Don't retry thousands of times immediately.

# 29. Queue Backpressure

Suppose:

```text
Incoming jobs = 10,000/sec
Processing = 2,000/sec
```

Queue grows:

```text
10K
20K
30K
40K
...
```

Eventually you'll run out of resources.

You need:

```text
Backpressure
Rate limiting
Autoscaling
Priority queues
Load shedding
```

This is a very important production concept.

---

# 30. Queue Idempotency

Workers can sometimes process the same message twice.

Therefore:

```text
Message
 ↓
Worker
 ↓
Processing
```

should ideally be safe to retry.

For example:

```text
jobId = 123
```

Store processing state:

```text
job 123 → completed
```

If the message appears again:

```text
Already completed
 → Don't perform duplicate side effect
```

This is **idempotent processing**.

# 36. The Most Important Trade-Off

You should always ask:

> **Does this component solve a real problem?**

For example:

```text
Problem:
Database is overloaded.

Solution:
Redis / replicas / query optimization.
```

Not:

```text
Problem:
Database is overloaded.

Solution:
Kubernetes + Kafka + microservices + Elasticsearch.
```

That's overengineering.

---

# 37. Monolith vs Microservices

For a small application:

```text
React
 ↓
Monolith API
 ↓
Database
```

can be excellent.

As complexity grows:

```text
API Gateway
 ├── Auth
 ├── Users
 ├── Products
 ├── Orders
 ├── Payments
 └── Notifications
```

can make sense.

But microservices introduce:

```text
Network failures
Distributed tracing
Service discovery
Deployment complexity
Data consistency problems
Operational overhead
```

So don't split services just for the sake of it.

# 52. The Golden Rule of System Design 🏆

Remember this:

> **Don't start with technology. Start with the problem.**

Not:

```text
"I'll use Kafka."
```

Instead:

```text
"We have a large amount of asynchronous work
that shouldn't block user requests."

Therefore:

"Let's introduce a queue."
```

Then choose:

```text
RabbitMQ?
Kafka?
SQS?
Another queue?
```

based on the requirements.
