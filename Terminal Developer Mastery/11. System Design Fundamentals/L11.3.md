# Lesson 11.3 — Client-Server Architecture ⭐⭐⭐⭐⭐

> **Goal:** Understand how clients and backend servers communicate, how a request travels through a production system, and why modern applications use stateless servers.

This lesson is especially important for you because you're already working with **React + Node.js + Express + MongoDB**. We're going to take the architecture you already use and understand what happens underneath it.

---

# 1. What Is Client-Server Architecture?

The basic idea is simple:

> **The client requests something, and the server processes that request and sends back a response.**

For a web application:

```text
┌──────────────┐
│    Client    │
│ React / Web  │
└──────┬───────┘
       │
       │ HTTP Request
       ▼
┌──────────────┐
│    Server    │
│ Node/Express │
└──────┬───────┘
       │
       │ Database Query
       ▼
┌──────────────┐
│   Database   │
│   MongoDB    │
└──────────────┘
```

For example, when your React application sends:

```javascript
axios.get("/api/users");
```

the browser is the **client**.

Your Node.js/Express application is the **server**.

MongoDB is the **database** used by the server.

---

# 2. Client vs Server

Let's clearly separate their responsibilities.

## Client

The client is usually responsible for:

- User interface
    
- User interactions
    
- Sending requests
    
- Displaying responses
    
- Some client-side validation
    
- Managing UI state
    

Examples:

```text
React
Angular
Vue
Mobile apps
Desktop applications
```

Your React application is a client.

---

## Server

The server is responsible for:

- Business logic
    
- Authentication
    
- Authorization
    
- Validation
    
- Database operations
    
- API processing
    
- Security
    
- Background jobs
    
- Returning responses
    

Examples:

```text
Node.js
Express
Django
Spring Boot
Laravel
Go
.NET
```

Your Express backend is a server.

# 4. Real-World Request Flow

Let's go deeper.

Suppose your frontend is:

```text
https://app.example.com
```

and backend:

```text
https://api.example.com
```

The browser sends:

```http
GET /api/users/me
Host: api.example.com
Authorization: Bearer <token>
```

The request doesn't magically reach your Express controller.

There are several layers involved.

A simplified production architecture might look like:

```text
                         Internet
                            │
                            ▼
                     ┌────────────┐
                     │    DNS     │
                     └─────┬──────┘
                           │
                           ▼
                     ┌────────────┐
                     │    CDN     │
                     └─────┬──────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │ Load Balancer   │
                  └────────┬────────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌─────────┐  ┌─────────┐  ┌─────────┐
         │ Node #1 │  │ Node #2 │  │ Node #3 │
         └────┬────┘  └────┬────┘  └────┬────┘
              │            │            │
              └────────────┼────────────┘
                           │
                 ┌─────────┴─────────┐
                 ▼                   ▼
              Redis              Database
```

Don't worry if some components are unfamiliar.

We'll study them individually throughout this module.

---

# 5. Step 1 — DNS

Suppose the user opens:

```text
https://api.example.com
```

The browser needs to find the server's IP address.

DNS means:

> **Domain Name System**

It translates domain names into IP addresses.

Conceptually:

```text
api.example.com
       │
       ▼
DNS
       │
       ▼
203.0.113.10
```

You don't normally type:

```text
http://203.0.113.10
```

Instead, you use:

```text
api.example.com
```

DNS provides the mapping.

---

# 6. Step 2 — Establishing the Connection

For HTTPS, the browser establishes a secure connection with the server.

Conceptually:

```text
Browser
   │
   │ TCP connection
   ▼
Server
   │
   │ TLS handshake
   ▼
Encrypted HTTPS connection
```

You don't need to memorize every TCP/TLS detail for system design yet.

The important idea is:

> **HTTPS protects communication between client and server.**

---

# 7. Step 3 — Load Balancer

In a small application, you might have:

```text
Client
  ↓
Node.js
```

But a large application may have:

```text
Client
   ↓
Load Balancer
   ↓
┌───────┬───────┬───────┐
Node 1  Node 2  Node 3
```

The load balancer decides which server should handle the request.

For example:

```text
Request 1 → Node 1
Request 2 → Node 2
Request 3 → Node 3
Request 4 → Node 1
Request 5 → Node 3
```

We'll study load balancing deeply in **Lesson 11.5**.

---

# 8. Step 4 — Node.js / Express

Eventually the request reaches your backend.

For example:

```javascript
app.get("/api/users/me", auth, getProfile);
```

Express receives:

```text
GET /api/users/me
```

Then middleware executes.

For example:

```text
Request
   ↓
CORS
   ↓
Rate Limiter
   ↓
Authentication
   ↓
Validation
   ↓
Controller
```

This should look familiar from your backend work.

---

# 9. Step 5 — Controller

The controller receives the request and coordinates the operation.

For example:

```javascript
const getProfile = async (req, res) => {
    const user = await userService.getProfile(req.user.userId);

    return res.status(200).json({
        success: true,
        user
    });
};
```

The controller shouldn't normally contain huge amounts of business logic.

Instead:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

This is a maintainable architecture.

---

# 10. Step 6 — Service Layer

The service contains business logic.

For example:

```text
Controller
    ↓
User Service
    ↓
Repository
```

The service might decide:

```text
Does user exist?
Is account active?
Can user access this resource?
What business rules apply?
```

Then it asks the repository for the required data.

---

# 11. Step 7 — Repository

The repository handles database interaction.

For example:

```javascript
const findUserById = async (userId) => {
    return User.findById(userId);
};
```

Architecture:

```text
HTTP
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
MongoDB
```

This separation becomes very useful as applications become larger.

---

# 12. Step 8 — Database

The repository sends a query to MongoDB.

Conceptually:

```text
MongoDB

users
────────────────────
_id
name
email
password
createdAt
```

MongoDB finds the document and returns it.

Then:

```text
MongoDB
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
Express
```

---

# 13. Step 9 — Response

The server sends something like:

```json
{
  "success": true,
  "user": {
    "id": "123",
    "name": "Rahul",
    "email": "user@example.com"
  }
}
```

The browser receives it.

React updates its state.

Then the user sees:

```text
┌─────────────────────────┐
│ Profile                 │
│                         │
│ Name: Rahul             │
│ Email: user@example.com │
└─────────────────────────┘
```

That's the complete request-response cycle.

# 15. What Is a Stateless Server?

Now we reach one of today's most important concepts.

A **stateless server** doesn't store client-specific session state in its own memory between requests.

Suppose:

```text
Request 1 → Server A
Request 2 → Server B
Request 3 → Server C
```

All servers can process the requests.

Why?

Because the necessary information is available in the request or in shared infrastructure.

For example:

```text
Authorization: Bearer JWT
```

The JWT contains information allowing the server to identify the user.

So:

```text
Request
   ↓
Any server
   ↓
Verify token
   ↓
Process request
```

---

# 16. Why Stateless Servers Are Useful

Suppose we have:

```text
             Load Balancer
             /     |     \
            ↓      ↓      ↓
         Server A Server B Server C
```

If the servers are stateless:

```text
User Request 1 → A
User Request 2 → C
User Request 3 → B
```

No problem.

Each server can independently process the request.

This makes **horizontal scaling much easier**.

---

# 17. Stateful Server

A stateful server stores user-specific state locally.

For example:

```text
Server A memory:

user123 → logged in
cart → [item1, item2]
session → abc123
```

Now imagine:

```text
Request 1 → Server A
Request 2 → Server B
```

Server B doesn't know about the state stored in Server A.

That can cause problems.

```text
Request 1
    ↓
Server A
    ↓
Session stored here


Request 2
    ↓
Server B
    ↓
"Who is this user?"
```

---

# 18. Session-Based Authentication Example

Traditional session architecture might look like:

```text
Browser
   ↓
Login
   ↓
Server
   ↓
Session created
   ↓
Server Memory
```

Then:

```text
Browser
   ↓
Session ID
   ↓
Server
```

If the request goes to another server:

```text
Browser
   ↓
Load Balancer
   ↓
Server B
```

Server B may not know the session.

---

# 19. Solution: Shared Session Storage

Instead of:

```text
Server A
   ↓
Local Memory
```

we can use:

```text
Server A ──┐
Server B ──┼──→ Redis
Server C ──┘
```

Now every server can access the same session data.

```text
                 Redis
               /   |   \
              /    |    \
         Server A Server B Server C
```

This allows horizontal scaling while still using sessions.

---

# 20. JWT and Stateless Authentication

Another approach is JWT-based authentication.

For example:

```text
Client
   │
   │ Authorization: Bearer JWT
   ▼
Server
   │
   ▼
Verify JWT
   │
   ▼
Identify User
```

The server doesn't necessarily need to store the authentication session locally.

Any server can verify the token.

Therefore:

```text
Request 1 → Server A
Request 2 → Server C
Request 3 → Server B
```

can all work.

This is one reason stateless APIs are popular.

**Important:** JWTs don't automatically make every application fully stateless; other state can still exist elsewhere, and token revocation/session management can require shared state.

---

# 21. Stateless Architecture

A typical scalable architecture might look like:

```text
                   Load Balancer
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       Server A      Server B      Server C
          │             │             │
          └─────────────┼─────────────┘
                        │
                 Shared Services
                   /           \
                  ▼             ▼
               Redis         Database
```

The application servers themselves don't need to keep important persistent user state in RAM.

---

# 22. Why Local Memory Can Be Dangerous

Imagine:

```text
Server A
   ↓
Important user state
```

Then:

```text
Server A 💥
```

The state disappears.

That's a reliability problem.

Instead:

```text
Server A ──┐
Server B ──┼──→ Redis / Database
Server C ──┘
```

Now the state is stored in shared infrastructure.

If Server A crashes:

```text
Server A ❌

Server B ✅
Server C ✅
```

The system can continue.

---

# 23. Stateless ≠ No State

This is an important interview point.

A stateless server does **not** mean:

> "The entire application has no state."

Obviously your application has data:

```text
Users
Orders
Products
Messages
Payments
```

The idea is:

> **The individual application server should avoid depending on local state that prevents another server from handling the request.**

For example:

```text
❌ Node Server Memory
   Critical persistent session state


✅ Shared Redis
   Shared session state
```

or:

```text
✅ Database
   Persistent application data
```

---

# 24. Stateful vs Stateless

|Feature|Stateful|Stateless|
|---|---|---|
|Server stores client state locally|Yes|No/minimal|
|Horizontal scaling|Harder|Easier|
|Server replacement|More difficult|Easier|
|Load balancing|More complex|Simpler|
|Shared storage|Often needed eventually|Common|
|Failure recovery|More difficult|Easier|
|Typical REST API|Usually avoided|Preferred|

---

# 25. What About Sticky Sessions?

There's another technique called:

> **Sticky Sessions**

The load balancer tries to send the same user to the same server.

For example:

```text
Rahul
  ↓
Load Balancer
  ↓
Server A
```

Future requests:

```text
Rahul
  ↓
Load Balancer
  ↓
Server A
```

This can help stateful applications.

But it introduces drawbacks.

If Server A fails:

```text
Server A ❌
```

the user's local state may disappear.

Therefore, when possible, we generally prefer:

```text
Stateless application servers
+
Shared state storage
```

rather than relying heavily on sticky sessions.

# 27. APIs Are the Contract

The client and server need a well-defined communication interface.

That's what an API provides.

For example:

```http
GET /api/users/123
```

Response:

```json
{
  "id": "123",
  "name": "Rahul"
}
```

The React application doesn't need to know how the server gets the data.

It only needs to understand the API contract.

This creates separation:

```text
Frontend
   │
   │ API Contract
   │
Backend
   │
   │ Database Implementation
   │
Database
```

---

# 28. Why This Separation Is Powerful

Imagine tomorrow you change:

```text
MongoDB
```

to:

```text
PostgreSQL
```

Your React frontend shouldn't need to change.

The API can remain:

```text
GET /api/users/123
```

The backend implementation changes internally.

That's **separation of concerns**.

---

# 29. Microservices Still Use Client-Server Communication

Later, you may encounter:

```text
Frontend
    ↓
API Gateway
    ↓
┌───────────┬────────────┬────────────┐
│ User      │ Order      │ Payment    │
│ Service   │ Service    │ Service    │
└───────────┴────────────┴────────────┘
```

Each service can act as:

- a server to another service
    
- a client when calling another service
    

For example:

```text
Order Service
     │
     │ HTTP/gRPC
     ▼
Payment Service
```

So client-server architecture isn't only:

```text
Browser → Backend
```

It can also be:

```text
Service A → Service B
```

# 30. Synchronous vs Asynchronous Communication

A client can communicate synchronously:

```text
Client
  │
  │ Request
  ▼
Server
  │
  │ Processing
  ▼
Response
```

The client waits.

But sometimes we don't want to wait.

For example:

> User uploads a video.

Instead of:

```text
Upload
  ↓
Wait 10 minutes
  ↓
Video processing
  ↓
Response
```

we can use a queue:

```text
Client
  ↓
API Server
  ↓
Message Queue
  ↓
Worker
  ↓
Video Processing
```

The API can quickly respond:

```text
202 Accepted
```

and processing happens asynchronously.

We'll study message queues in **Lesson 11.12**.

### Request-response

```text
Client → Server → Response
```

Good for:

```text
Login
Get profile
Fetch products
Create order
```

### Event-driven

```text
Service
   ↓
Event
   ↓
Queue
   ↓
Consumer
```

Good for:

```text
Emails
Notifications
Analytics

Background jobs
```

Both patterns are important.

# 32. Important Interview Question 🎯

### Question:

> Why are stateless servers preferred for scalable applications?

A strong answer:

> Stateless servers don't depend on client-specific state stored locally on one server. Because any server can process a request, a load balancer can distribute traffic freely across multiple instances. This makes horizontal scaling, failover, and server replacement easier.

That's the kind of answer you should eventually be able to give naturally.

---

# 33. Another Interview Question

### Question:

> What happens if one server crashes?

With a properly designed stateless architecture:

```text
              Load Balancer
             /      |      \
            ▼       ▼       ▼
         Server A Server B Server C
            ❌       ✅       ✅
```

The load balancer detects that Server A is unhealthy.

Traffic goes to:

```text
Server B
Server C
```

Because important state is stored in shared infrastructure:

```text
Redis
Database
Object Storage
```

the application can continue operating.

# 34. Common Beginner Mistakes ❌

### Mistake 1

Thinking:

> Client = React and Server = Database.

No.

```text
React → Server → Database
```

The database isn't normally the HTTP server for your application.

---

### Mistake 2

Putting important state inside Node.js memory.

For example:

```javascript
const sessions = {};
```

This doesn't scale well across multiple instances.

---

### Mistake 3

Assuming JWT solves every state problem.

JWT can help make authentication requests independently verifiable, but your application may still require shared state for:

- refresh tokens
    
- token revocation
    
- sessions
    
- rate limiting
    
- caching
    
- other business data
    

---

### Mistake 4

Adding load balancers without understanding why.

The load balancer exists primarily to help distribute traffic and support availability/scaling—not simply because "production apps need one."
