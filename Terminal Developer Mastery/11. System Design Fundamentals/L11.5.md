# Lesson 11.5 — Load Balancing ⭐⭐⭐⭐⭐

> **Goal:** Understand why load balancers are needed, how they distribute traffic, the difference between Layer 4 and Layer 7 load balancing, common algorithms, health checks, failover, and how this fits into your Node.js/Express applications.

Load balancing is the natural next step after horizontal scaling.

We learned:

```text
One server
    ↓
Not enough
    ↓
Multiple servers
```

But now we have a new problem:

> **Who decides which server receives each request?**

That's the job of the **load balancer**.

---

# 1. What Is a Load Balancer?

A load balancer is a component that receives incoming traffic and distributes it across multiple backend servers.

Instead of:

```text
Users
  │
  ▼
Server
```

we have:

```text
                    Users
                      │
                      ▼
                Load Balancer
                 /     |     \
                ▼      ▼      ▼
             Server  Server  Server
               A       B       C
```

The load balancer acts as the **traffic manager**.

---

# 2. Why Do We Need Load Balancing?

Suppose you have:

```text
Server A → 10,000 requests
Server B → 0 requests
Server C → 0 requests
```

That's obviously a terrible architecture.

Instead:

```text
Server A → ~3,333
Server B → ~3,333
Server C → ~3,334
```

The load balancer distributes traffic.

This provides several benefits:

- Better scalability
    
- Better availability
    
- Fault tolerance
    
- Traffic distribution
    
- Health checking
    
- Easier deployments
    
- Better resource utilization
    

---

# 3. Basic Architecture

A typical architecture:

```text
                         Internet
                            │
                            ▼
                     ┌─────────────┐
                     │Load Balancer│
                     └──────┬──────┘
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ Node.js  │  │ Node.js  │  │ Node.js  │
        │ Server 1 │  │ Server 2 │  │ Server 3 │
        └────┬─────┘  └────┬─────┘  └────┬─────┘
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                      ┌─────────┐
                      │ MongoDB │
                      └─────────┘
```

---

# 4. A Simple Real-World Example

Suppose your MERN backend has:

```text
API Server 1
10.0.0.11

API Server 2
10.0.0.12

API Server 3
10.0.0.13
```

Users don't need to know these IP addresses.

They access:

```text
https://api.example.com
```

DNS points to the load balancer.

```text
api.example.com
       ↓
Load Balancer
       ↓
┌──────┼──────┐
↓      ↓      ↓
10.0.0.11
10.0.0.12
10.0.0.13
```

---

# 5. Load Balancer as a Reverse Proxy

A load balancer often behaves like a **reverse proxy**.

The client thinks:

```text
Client
  ↓
api.example.com
```

But internally:

```text
Load Balancer
      ↓
Backend Server
```

The client doesn't directly communicate with the backend server.

This gives the load balancer control over:

- routing
    
- TLS termination
    
- health checks
    
- traffic distribution
    
- security policies
    

---

# 6. Forward Proxy vs Reverse Proxy

This distinction is useful.

### Forward Proxy

The proxy acts on behalf of the **client**.

```text
Client
   ↓
Forward Proxy
   ↓
Internet
```

Common use cases:

- Corporate proxy
    
- Privacy filtering
    
- Network access control
    

---

### Reverse Proxy

The proxy acts on behalf of the **servers**.

```text
Client
   ↓
Reverse Proxy
   ↓
Backend Servers
```

Common technologies:

- Nginx
    
- HAProxy
    
- Envoy
    
- Cloud load balancers
    

A load balancer can function as a reverse proxy.

---

# 7. Layer 4 vs Layer 7 Load Balancing

This is an important interview topic.

The two common categories are:

```text
Layer 4
Layer 7
```

Let's understand them.

---

# 8. Layer 4 Load Balancing

Layer 4 operates at the **transport layer**.

It primarily works with:

```text
TCP
UDP
IP
Port
```

It doesn't need to understand the actual HTTP request content.

For example:

```text
Client
   │
   │ TCP connection
   ▼
L4 Load Balancer
   │
   ├── Server A
   ├── Server B
   └── Server C
```

It can make decisions based on things like:

```text
Source IP
Destination IP
Port
Protocol
```

---

# 9. Advantages of Layer 4

L4 load balancing can be:

- Fast
    
- Efficient
    
- Lower overhead
    
- Suitable for high-throughput traffic
    
- Useful for non-HTTP protocols
    

For example:

```text
TCP
UDP
Database traffic
Game servers
Custom protocols
```

---

# 10. Layer 7 Load Balancing

Layer 7 operates at the **application layer**.

For web applications, this usually means:

```text
HTTP
HTTPS
```

The load balancer can understand:

```text
URL
HTTP method
Headers
Cookies
Host
Query parameters
```

For example:

```http
GET /api/users
```

could go to:

```text
User Service
```

while:

```http
GET /api/products
```

could go to:

```text
Product Service
```

---

# 11. Layer 7 Routing Example

Imagine:

```text
                 Load Balancer
                       │
           ┌───────────┴───────────┐
           │                       │
           ▼                       ▼
    /api/users                /api/products
           │                       │
           ▼                       ▼
     User Servers            Product Servers
```

This is possible because an L7 load balancer understands HTTP requests.

---

# 12. L4 vs L7

|Feature|Layer 4|Layer 7|
|---|---|---|
|Layer|Transport|Application|
|Understands HTTP|No|Yes|
|Routing based on URL|No|Yes|
|Routing based on headers|No|Yes|
|Speed|Very high|More processing|
|Protocols|TCP/UDP|HTTP/HTTPS|
|Content-aware|No|Yes|

### Easy memory trick:

> **L4 knows the connection.**

> **L7 knows the request.**

---

# 13. Round Robin

Now let's look at load-balancing algorithms.

The simplest is:

> **Round Robin**

Suppose:

```text
Server A
Server B
Server C
```

Requests are distributed:

```text
Request 1 → A
Request 2 → B
Request 3 → C
Request 4 → A
Request 5 → B
Request 6 → C
```

Like this:

```text
A → B → C → A → B → C
```

Very simple.

---

# 14. When Round Robin Works Well

Round Robin works well when:

- Servers have similar capacity
    
- Requests have similar processing cost
    
- Traffic is relatively uniform
    

For example:

```text
Server A = 8 CPU
Server B = 8 CPU
Server C = 8 CPU
```

and requests are roughly similar.

---

# 15. Problem with Round Robin

Suppose:

```text
Server A → powerful
Server B → medium
Server C → weak
```

Round Robin still does:

```text
A → B → C → A → B → C
```

It doesn't understand server workload.

Another problem:

```text
Request A = 10 ms
Request B = 5 seconds
```

If Server A receives a huge number of long-running requests, simple Round Robin may not react intelligently.

That's where other algorithms help.

---

# 16. Weighted Round Robin

We can assign weights.

Suppose:

```text
Server A → weight 3
Server B → weight 2
Server C → weight 1
```

Traffic could roughly become:

```text
A A A
B B
C
```

So:

```text
A → 50%
B → 33%
C → 17%
```

This is useful when servers have different capacities.

---

# 17. Least Connections

Another algorithm:

> **Send the request to the server with the fewest active connections.**

Suppose:

```text
Server A → 100 connections
Server B → 20 connections
Server C → 50 connections
```

A new request goes to:

```text
Server B
```

because:

```text
20 < 50 < 100
```

Architecture:

```text
              Load Balancer
                    │
          Choose lowest connections
                    │
             ┌──────┼──────┐
             ▼      ▼      ▼
            A      B       C
          100     20      50
```

---

# 18. Why Least Connections Can Be Better

Suppose requests have different processing times.

Round Robin:

```text
A → Request
B → Request
C → Request
```

might send long-running requests to a busy server.

Least Connections considers current connection count.

This can distribute workload more intelligently.

---

# 19. IP Hash

Another technique is:

> **IP Hash**

The load balancer calculates a hash based on the client's IP address.

Conceptually:

```text
Client IP
   ↓
Hash Function
   ↓
Server Selection
```

For example:

```text
User A → Server B
User B → Server A
User C → Server C
```

The same client IP tends to go to the same backend server.

---

# 20. Why Use IP Hash?

It can provide a form of session affinity.

For example:

```text
User
 ↓
IP Hash
 ↓
Server A
```

Future requests from that IP tend to go to Server A.

But IP-based affinity isn't always reliable because many users can share an IP.

For example:

```text
College Wi-Fi
     │
     ├── User A
     ├── User B
     ├── User C
     └── User D
```

All users may appear behind the same public IP.

So IP hashing has limitations.

---

# 21. Sticky Sessions

Sticky sessions mean:

> **Try to keep a user's requests going to the same backend server.**

Example:

```text
User
  ↓
Load Balancer
  ↓
Server A
```

Future requests:

```text
User
  ↓
Load Balancer
  ↓
Server A
```

This can be implemented using mechanisms such as cookies or other affinity techniques.

---

# 22. Why Sticky Sessions Can Be a Problem

Suppose:

```text
Server A
Server B
Server C
```

and Server A has many sticky users:

```text
Server A → 90% load
Server B → 40%
Server C → 30%
```

The traffic isn't balanced anymore.

Also:

```text
Server A 💥
```

Users attached to Server A may be affected.

Therefore, whenever possible:

> **Prefer stateless application servers instead of relying heavily on sticky sessions.**

---

# 23. Health Checks

A very important load-balancer feature is:

> **Health checking**

The load balancer periodically asks:

```text
Are you healthy?
```

For example:

```http
GET /health
```

Response:

```json
{
  "status": "ok"
}
```

If the server responds correctly:

```text
Server A → Healthy ✅
```

If it fails:

```text
Server B → Unhealthy ❌
```

The load balancer stops sending new traffic to it.

---

# 24. Health Check Example

Suppose:

```text
              Load Balancer
             /      |      \
            ▼       ▼       ▼
         Server A Server B Server C
            ✅       ❌       ✅
```

The load balancer removes Server B:

```text
              Load Balancer
                /       \
               ▼         ▼
           Server A   Server C
              ✅         ✅
```

Users may not even notice that Server B failed.

That's a major reason load balancers improve availability.

---

# 25. Health Checks Should Be Meaningful

A simple:

```http
GET /health
```

might only check whether Node.js is running.

But a deeper health check could verify:

```text
Application running
Database reachable
Redis reachable
Required dependencies available
```

However, there's a trade-off.

If your health check requires every dependency to be healthy, a temporary dependency problem might cause the load balancer to remove every server.

So production systems often distinguish between:

### Liveness

> Is the process alive?

### Readiness

> Is the instance ready to receive traffic?

This distinction becomes especially important with containers and Kubernetes.

---

# 26. Liveness vs Readiness

Imagine:

```text
Node.js process → running
Database connection → not ready
```

The application is alive:

```text
Liveness = healthy
```

But it may not be ready to serve requests:

```text
Readiness = unhealthy
```

Therefore:

```text
Load Balancer
      │
      ├── Is server alive?
      └── Is server ready?
```

This is a powerful production concept.

---

# 27. Failover

Suppose:

```text
Server A ❌
Server B ✅
Server C ✅
```

The load balancer detects:

```text
A = unhealthy
```

and routes traffic:

```text
              Load Balancer
                /       \
               ▼         ▼
             B           C
```

This is **failover**.

The system continues functioning despite an individual server failure.

---

# 28. What Happens During a Traffic Spike?

Suppose:

```text
Normal:
1,000 RPS
```

Suddenly:

```text
10,000 RPS
```

The architecture might use:

```text
                 Load Balancer
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
     Server 1      Server 2      Server 3
        │             │             │
        └─────────────┼─────────────┘
                      │
                 Auto Scaling
                      │
                 Add Servers
```

New servers join the pool.

The load balancer starts sending traffic to them.

---

# 29. Load Balancer + Auto Scaling

These two work very well together.

```text
Traffic increases
       ↓
CPU increases
       ↓
Auto Scaling launches
new server
       ↓
Server passes health check
       ↓
Load Balancer adds server
       ↓
Traffic distributed
```

Then:

```text
Traffic decreases
       ↓
Servers become underutilized
       ↓
Auto Scaling removes instances
```

This gives you elasticity.

---

# 30. TLS Termination

Another important load-balancer responsibility can be:

> **TLS termination**

Instead of every backend server handling the public HTTPS connection:

```text
Client
  │
  │ HTTPS
  ▼
Load Balancer
  │
  │ HTTP/private HTTPS
  ▼
Backend
```

The load balancer decrypts the HTTPS connection.

This can simplify certificate management.

However, internal encryption may still be desirable depending on your security requirements.

---

# 31. Example with Nginx

Nginx can act as a reverse proxy and basic load balancer.

Conceptually:

```text
Client
   ↓
Nginx
  / \
 ↓   ↓
Node Node
```

A simplified configuration could look like:

```nginx
upstream backend {
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

Now requests can be distributed among:

```text
3001
3002
3003
```

By default, Nginx can use a round-robin style distribution for an upstream group.

---

# 32. Least Connections with Nginx

Nginx can also use least connections:

```nginx
upstream backend {
    least_conn;

    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}
```

Now Nginx tries to select the backend with fewer active connections.

---

# 33. Important Production Detail

A load balancer doesn't magically make a bad application scalable.

Imagine:

```text
Load Balancer
   ↓
10 Node Servers
   ↓
One overloaded MongoDB
```

The architecture can still fail.

Likewise:

```text
Load Balancer
   ↓
10 Node Servers
   ↓
Redis
   ↓
One external API
```

If the external API is slow:

```text
External API
      ↓
10 second latency
```

your entire request path may become slow.

Therefore:

> **A load balancer distributes traffic; it doesn't remove every bottleneck.**

---

# 34. Connection Draining

Here's another useful production concept.

Suppose Server A is being removed for deployment.

We don't want:

```text
Existing requests → suddenly killed
```

Instead:

```text
Load Balancer
      ↓
Stop sending NEW requests to A
      ↓
Allow existing requests to finish
      ↓
Server A shuts down
```

This is called:

> **Connection draining / graceful draining**

It helps prevent interrupted requests during deployments or scaling events.

---

# 35. Load Balancer as a Security Boundary

A load balancer can also provide:

```text
TLS termination
Rate limiting
IP filtering
Request routing
DDoS protection integration
Access control
```

Some cloud load balancers also integrate with web application firewalls.

So it isn't necessarily just a traffic distributor.

---

# 36. Load Balancing Multiple Services

Suppose you eventually have:

```text
/api/users
/api/orders
/api/payments
/api/courses
```

A Layer 7 load balancer or API gateway could route based on paths:

```text
                  Load Balancer
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   /api/users      /api/orders     /api/payments
        │               │               │
        ▼               ▼               ▼
   User Service    Order Service   Payment Service
```

This is one of the foundations of microservice architectures.

---

# 37. Load Balancer vs API Gateway

Don't confuse these.

### Load Balancer

Main purpose:

```text
Distribute traffic
```

### API Gateway

Usually provides a broader API-management layer:

```text
Routing
Authentication
Rate limiting
Request transformation
API versioning
Aggregation
Observability
```

There can be overlap.

We'll explore API gateways more deeply later.

---

# 38. Load Balancer vs Reverse Proxy

They overlap significantly.

A reverse proxy:

```text
Client
  ↓
Reverse Proxy
  ↓
Server
```

A load balancer:

```text
Client
  ↓
Load Balancer
  ↓
Server A / B / C
```

A reverse proxy can perform load balancing.

Nginx is a good example.

---

# 39. Important Algorithms

You should know these:

```text
Round Robin
Weighted Round Robin
Least Connections
IP Hash
Sticky Sessions
```

### Quick comparison

|Algorithm|Main Idea|
|---|---|
|Round Robin|Rotate servers|
|Weighted Round Robin|More traffic to stronger servers|
|Least Connections|Choose server with fewer connections|
|IP Hash|Map client IP to server|
|Sticky Session|Keep client attached to server|

---

# 40. Which Algorithm Should You Choose?

There's no universal answer.

### Similar servers + similar requests

```text
Round Robin
```

is often sufficient.

### Different server capacities

```text
Weighted Round Robin
```

can help.

### Different request durations

```text
Least Connections
```

may be useful.

### Need connection affinity

```text
IP Hash / Sticky Sessions
```

can be considered.

But if your application is properly stateless, you often don't need affinity.

# 42. Interview Question 🎯

### "What happens when one backend server fails?"

A strong answer:

> The load balancer continuously performs health checks on backend instances. If an instance becomes unhealthy, the load balancer removes it from the active pool and routes new requests to healthy instances. Existing connections may be drained or terminated depending on the failure and configuration. This improves availability and fault tolerance.

---

# 43. Interview Question 🎯

### "Why use a load balancer?"

A good answer:

> A load balancer distributes incoming traffic across multiple backend instances, preventing individual servers from becoming overloaded. It also enables horizontal scaling, health checks, failover, and smoother deployments.

---

# 44. Interview Question 🎯

### "What is Layer 4 vs Layer 7 load balancing?"

Good answer:

> Layer 4 load balancing operates at the transport layer and primarily routes based on network-level information such as IP addresses and ports. Layer 7 operates at the application layer and understands protocols such as HTTP, allowing routing based on URLs, headers, cookies, and other request information.

> Load balancer = just round robin.

No.

```text

Failover
TLS
Routing
Connection management
Traffic policies
```

---

### Mistake 2

Thinking:

> More backend servers automatically solve everything.

No.

You can still have:

```text
Database bottleneck
Redis bottleneck
Network bottleneck
External API bottleneck
```

---

### Mistake 3

Using sticky sessions everywhere.

If you can build:

```text
Stateless servers
+
Shared state
```

that's often easier to scale.

---

### Mistake 4

Sending traffic to unhealthy servers.

That's why health checks matter.
