# Lesson 11.6 — Caching ⭐⭐⭐⭐⭐

> **Goal:** Understand why caching dramatically improves backend performance, how Redis fits into a production architecture, different caching strategies, cache invalidation, TTL, cache stampede, and practical Node.js examples.

Caching is one of the most important concepts in backend engineering.

If you understand caching properly, you'll understand why systems like:

- Instagram
    
- YouTube
    
- Amazon
    
- Netflix
    
- Reddit
    
- large SaaS platforms
    

can serve huge amounts of traffic without querying their primary database for every request.

---

# 1. What Is Caching?

A **cache** is a fast storage layer that keeps frequently used data closer to the application.

Instead of:

```text
Client
  ↓
Node.js
  ↓
Database
  ↓
Response
```

we can have:

```text
Client
  ↓
Node.js
  ↓
Redis
  ↓
Response
```

If the data isn't in Redis:

```text
Client
  ↓
Node.js
  ↓
Redis ❌
  ↓
Database
  ↓
Redis ← Store result
  ↓
Response
```

The next request can retrieve the data directly from Redis.

---

# 2. Why Is Caching Necessary?

Databases are powerful, but database operations are much more expensive than reading data from memory.

Conceptually:

```text
CPU cache
   ↓
RAM
   ↓
SSD
   ↓
Database
   ↓
Remote service
```

The closer the data is to the CPU/application, the faster access can be.

Redis primarily stores data in memory, making it extremely fast for many workloads.

---

# 3. Database vs Redis

Imagine:

```text
MongoDB
   ↓
Disk / memory-backed database engine
```

versus:

```text
Redis
   ↓
Primarily memory
```

The exact performance depends on workload, network, query complexity, hardware, and configuration, but the key idea is:

> **Memory access is generally much faster than querying persistent storage.**

Therefore:

```text
Frequently accessed data
        ↓
      Redis
        ↓
      Fast ⚡
```

while less frequently accessed data can remain in the database.

---

# 4. Basic Caching Architecture

A common architecture:

```text
                         Client
                           │
                           ▼
                       API Server
                           │
                           ▼
                       ┌───────┐
                       │ Redis │
                       └───┬───┘
                           │
                     Cache Miss
                           │
                           ▼
                      ┌─────────┐
                      │ MongoDB │
                      └─────────┘
```

The application checks Redis first.

---

# 5. Cache Hit

Suppose the application requests:

```text
user:123
```

Redis contains:

```text
user:123 → Rahul
```

The application gets it immediately.

That's a:

> **Cache Hit**

```text
Request
   ↓
Redis
   ↓
Found ✅
   ↓
Response
```

---

# 6. Cache Miss

Now suppose Redis doesn't contain:

```text
user:456
```

The application asks the database.

```text
Request
   ↓
Redis
   ↓
Not found ❌
   ↓
MongoDB
   ↓
Get data
   ↓
Store in Redis
   ↓
Response
```

That's a:

> **Cache Miss**

---

# 7. Cache Hit Ratio

One important metric is:

> **Cache Hit Ratio**

Formula:

```text
Cache Hit Ratio
=
Cache Hits / Total Requests
```

Suppose:

```text
Total requests = 10,000
Cache hits = 8,000
```

Then:

```text
8,000 / 10,000
= 80%
```

So:

> **Cache hit ratio = 80%**

That means only approximately 20% of requests need to go to the database.

---

# 8. Why Cache Hit Ratio Matters

Suppose:

```text
100,000 requests/sec
```

Without caching:

```text
100,000 → Database
```

With 90% cache hit ratio:

```text
90,000 → Redis
10,000 → Database
```

That's a huge reduction in database traffic.

This is one of the main reasons caching improves scalability.

---

# 9. The Most Common Strategy: Cache-Aside

The most common caching pattern for backend applications is:

> **Cache-Aside**

The application manages the cache.

Flow:

```text
Request
   ↓
Check Cache
   ↓
 ┌───────────────┐
 │               │
Hit             Miss
 │               │
 ▼               ▼
Return        Database
                 │
                 ▼
              Cache
                 │
                 ▼
              Return
```

This is sometimes called:

> **Lazy loading**

because data is placed into the cache only when requested.

---

# 10. Cache-Aside Example

Suppose:

```text
GET /api/users/123
```

Application:

```javascript
const cachedUser = await redis.get("user:123");

if (cachedUser) {
    return JSON.parse(cachedUser);
}

const user = await User.findById("123");

await redis.set(
    "user:123",
    JSON.stringify(user),
    { EX: 300 }
);

return user;
```

The flow is:

```text
Redis?
  │
  ├── YES → return
  │
  └── NO
       ↓
    MongoDB
       ↓
     Redis
       ↓
     return
```

---

# 11. Why Cache-Aside Is Popular

Advantages:

- Simple
    
- Application controls what gets cached
    
- Database remains the source of truth
    
- Only requested data is cached
    
- Easy to introduce gradually
    

For many Node.js applications, this is a good starting strategy.

---

# 12. Read-Through Cache

In a **read-through cache**, the application asks the cache for data, and the cache itself loads the data from the database when necessary.

Conceptually:

```text
Application
    ↓
  Cache
    │
    ├── Hit → Return
    │
    └── Miss
          ↓
       Database
          ↓
        Cache
          ↓
       Return
```

The difference is mainly **who is responsible for loading the data**.

### Cache-aside

```text
Application
   ↓
Cache
   ↓
Application
   ↓
Database
```

### Read-through

```text
Application
   ↓
Cache
   ↓
Database
```

The cache abstraction handles the loading.

---

# 13. Write-Through Cache

Now we have a different question:

> What happens when data changes?

In **write-through caching**:

```text
Application
    ↓
  Cache
    ↓
Database
```

The cache and database are updated as part of the write flow.

Conceptually:

```text
Write
 ↓
Cache
 ↓
Database
```

This helps keep cached data fresh.

---

# 14. Example

Suppose user changes their name:

```text
PUT /api/users/123
```

Write-through approach:

```text
Request
   ↓
Update Redis
   ↓
Update Database
   ↓
Success
```

Now:

```text
Redis → New name
MongoDB → New name
```

---

# 15. Write-Back Cache

Another strategy is:

> **Write-Back / Write-Behind**

The application writes to the cache first.

```text
Application
    ↓
  Cache
    ↓
   Later
    ↓
Database
```

This can make writes very fast.

But it introduces risk.

Suppose:

```text
Cache
  ↓
Data not yet written to DB
```

and Redis crashes.

You could lose data.

Therefore write-back caching is appropriate only for certain workloads where the durability and consistency trade-offs are acceptable.

---

# 16. Comparing Cache Strategies

|Strategy|Read|Write|Main Advantage|Main Risk|
|---|---|---|---|---|
|Cache-Aside|App checks cache|App controls DB/cache|Simple|Cache misses|
|Read-Through|Cache handles read|Depends|Simpler app logic|Cache infrastructure complexity|
|Write-Through|Cache + DB|Both updated|Fresh cache|Higher write latency|
|Write-Back|Cache first|DB later|Fast writes|Data-loss risk|

For your Node.js projects:

> **Start by understanding Cache-Aside extremely well.**

It's the pattern you'll encounter frequently.

---

# 17. TTL — Time To Live

One of the most important caching concepts is:

> **TTL = Time To Live**

It determines how long cached data remains valid.

For example:

```text
user:123
TTL = 300 seconds
```

After 5 minutes:

```text
user:123
   ↓
Expired
```

Redis removes or makes the key unavailable according to its expiration behavior.

---

# 18. Why Use TTL?

Suppose you cache:

```text
Popular products
```

but never expire them.

Eventually:

```text
Database:
Product price = ₹1,000

Cache:
Product price = ₹800
```

Now users receive stale information.

TTL helps limit how long stale data can survive.

---

# 19. Example Redis TTL

Conceptually:

```javascript
await redis.set(
    "product:123",
    JSON.stringify(product),
    {
        EX: 300
    }
);
```

Meaning:

```text
EX = expiration in seconds
300 = 5 minutes
```

So:

```text
product:123
     ↓
5 minutes
     ↓
Expired
```

---

# 20. Choosing TTL

TTL depends on the data.

### User profile

Maybe:

```text
5–30 minutes
```

### Product catalog

Maybe:

```text
minutes
```

### Exchange rate

Maybe:

```text
seconds/minutes
```

### Configuration

Maybe:

```text
hours
```

### Frequently changing stock

Maybe:

```text
very short TTL
```

There isn't a universal TTL.

Ask:

> **How stale can this data safely be?**

---

# 21. Cache Invalidation

Here's the famous problem:

> **Cache invalidation is one of the hardest parts of caching.**

Suppose:

```text
MongoDB:
price = ₹1000

Redis:
price = ₹1000
```

Then user updates:

```text
MongoDB:
price = ₹1200
```

But Redis still contains:

```text
Redis:
price = ₹1000
```

Now:

```text
GET /product/123
```

returns:

```text
₹1000
```

That's stale data.

---

# 22. Delete Cache on Update

A common solution:

```text
Update Database
      ↓
Delete Cache
```

Example:

```javascript
await Product.findByIdAndUpdate(
    productId,
    update
);

await redis.del(`product:${productId}`);
```

Then the next request:

```text
Redis → Miss
   ↓
MongoDB → New data
   ↓
Redis → Cache new data
```

This is a common cache-aside invalidation pattern.

---

# 23. Update Cache Instead

Another approach:

```text
Update Database
      ↓
Update Redis
```

For example:

```text
MongoDB:
price = ₹1200

Redis:
price = ₹1200
```

This can avoid the next cache miss.

But now you have to make sure the cache update succeeds and remains consistent with the database.

---

# 24. Delete vs Update

### Delete cache

```text
DB update
   ↓
Delete Redis
```

Pros:

- Simple
    
- Next read gets fresh data
    

Cons:

- Next read causes cache miss
    

### Update cache

```text
DB update
   ↓
Update Redis
```

Pros:

- Next read remains fast
    

Cons:

- More complicated consistency handling
    

For many applications:

> **Invalidate/delete is the simpler and safer starting point.**

---

# 25. Cache Stampede

Now let's look at an important production problem.

Suppose a very popular key expires:

```text
popular:course:123
```

Thousands of users request it at exactly the same time.

Before expiration:

```text
10,000 requests
     ↓
Redis
     ↓
Cache hit
```

Then:

```text
Cache expires
```

Suddenly:

```text
10,000 requests
     ↓
Redis MISS
     ↓
10,000 database queries 😱
```

The database gets hammered.

This is called:

> **Cache Stampede**

Also called:

> **Thundering Herd**

---

# 26. How to Prevent Cache Stampede

Several techniques exist.

### 1. Locking

Allow only one request to rebuild the cache.

```text
Request A → Cache miss → Acquire lock → DB
Request B → Cache miss → Wait
Request C → Cache miss → Wait
```

Then:

```text
Request A → Update cache
Request B → Redis hit
Request C → Redis hit
```

---

### 2. TTL Jitter

Instead of every cache entry expiring at exactly:

```text
300 seconds
```

use slightly different expiration times.

For example:

```text
300 + random(0–60)
```

This spreads expirations over time.

---

### 3. Background Refresh

Refresh popular data before it expires.

```text
Cache
  ↓
Near expiration
  ↓
Background refresh
  ↓
New TTL
```

This prevents users from experiencing a large cache miss.

---

# 27. Cache Penetration

Another problem:

Suppose attackers repeatedly request:

```text
/user/does-not-exist-123
/user/does-not-exist-456
/user/does-not-exist-789
```

Every request:

```text
Redis MISS
   ↓
MongoDB
   ↓
Not found
```

The database receives unnecessary queries.

This is sometimes called:

> **Cache penetration**

A common solution is to cache negative results carefully.

For example:

```text
user:does-not-exist-123
        ↓
NULL
        ↓
TTL = 30 seconds
```

Now repeated requests don't hit the database every time.

---

# 28. Cache Avalanche

Imagine thousands of keys all have:

```text
TTL = 1 hour
```

and they were created at the same time.

One hour later:

```text
Thousands of keys expire
       ↓
Huge number of cache misses
       ↓
Database overload
```

This is often called a:

> **Cache avalanche**

TTL jitter and staggered expiration can reduce this problem.

---

# 29. What Should You Cache?

Good cache candidates are usually:

- Frequently accessed
    
- Expensive to calculate/query
    
- Relatively stable
    
- Safe to be slightly stale
    

Examples:

```text
User profiles
Popular products
Course information
Configuration
Permissions
Frequently accessed URLs
Popular posts
API responses
```

---

# 30. What Should You Avoid Caching?

Be careful with:

### Highly sensitive data

For example:

```text
Passwords
Private keys
Raw authentication secrets
```

Never casually cache sensitive data.

### Highly volatile data

For example:

```text
Real-time bank balance
Real-time inventory
```

unless your consistency requirements allow it.

### Huge objects

Caching very large objects can consume memory quickly.

---

# 31. Caching Your URL Shortener

This is a perfect example.

Suppose:

```text
GET /aB92x
```

needs:

```text
aB92x → https://example.com/very/long/url
```

Without Redis:

```text
Request
  ↓
Node.js
  ↓
MongoDB
  ↓
URL
  ↓
Redirect
```

If this URL receives:

```text
100,000 requests/day
```

MongoDB gets hit repeatedly.

---

# 32. URL Shortener with Redis

Now:

```text
Request /aB92x
       ↓
     Redis
       │
    ┌──┴──┐
    │     │
   Hit   Miss
    │     │
    │     ▼
    │  MongoDB
    │     │
    │     ▼
    │   Redis
    │     │
    └──┬──┘
       ▼
    Redirect
```

For a hot URL, Redis can absorb a huge portion of the read traffic.

---

# 33. Cache Key Design

Good cache keys are important.

For example:

```text
user:123
product:456
course:789
url:aB92x
```

Avoid unclear keys like:

```text
123
456
789
```

A namespace makes the key understandable.

For example:

```text
user:123
```

clearly represents a user.

---

# 34. Cache Key Versioning

Suppose your cached object structure changes.

You can use:

```text
user:v1:123
```

Then later:

```text
user:v2:123
```

This can help avoid conflicts between old and new cached representations.

# 35. Cache Serialization

Redis commonly stores strings/bytes.

Your Node.js object:

```javascript
{
    id: "123",
    name: "Rahul"
}
```

may be stored as:

```javascript
JSON.stringify(user)
```

Then retrieved:

```javascript
JSON.parse(cachedUser)
```

Conceptually:

```text
JavaScript Object
      ↓
JSON.stringify()
      ↓
Redis
      ↓
JSON.parse()
      ↓
JavaScript Object
```

Redis can also be used for:

```text
                 Node Server
                      │
                      ▼
                  ┌───────┐
                  │ Redis │
                  └───┬───┘
                      │
                 Cache Miss
                      │
                      ▼
                 ┌─────────┐
```

At larger scale:

```text
              Node Servers
          /       |       \

       Primary       Replica
```

# 38. Cache and Database Are Different

Remember:

```text
Database = Source of truth
Cache    = Performance layer
```

Usually:

```text
Database
   ↓
Persistent data
```

while:

```text
Redis
   ↓
Fast temporary copy
```

If Redis disappears:

```text
Redis ❌
```

your application should ideally be able to recover by reading from the database.

This is a very useful design principle.

---

# 39. Cache Failure

What happens if Redis goes down?

Bad architecture:

```text
Redis ❌
   ↓
Entire application ❌
```

Better architecture:

```text
Redis ❌
   ↓
Cache misses
   ↓
Database
   ↓
Application continues
```

Performance may degrade, but the system remains functional.

This is called **graceful degradation**.

We'll study this deeply in Lesson 11.13.

---

# 40. Cache Failure and Database Protection

But there's a problem.

Suppose Redis fails:

```text
100,000 RPS
   ↓
Redis ❌
   ↓
100,000 RPS → MongoDB 😱
```

The database may collapse.

Therefore, a production system may use:

```text
Redis
+
Rate limiting
+
Request coalescing
+
Database capacity
+
Fallback strategies
```

This is why system design concepts are connected.

# 41. Cache Consistency

You should always ask:

> **How stale can the cache be?**

For example:

### Social media post

A few seconds of stale data may be acceptable.

### Product description

Maybe minutes are acceptable.

### Bank account balance

Stale data may be unacceptable.

Therefore:

```text
Consistency requirement
        ↓
Caching strategy
        ↓
TTL / invalidation strategy
```

# 42. Caching and Read-Heavy Systems

Caching works especially well for:

```text
90% reads
10% writes
```

For example:

```text
100,000 requests
      ↓
90,000 reads
10,000 writes
```

If many reads request the same data:

```text
Redis
   ↓
Absorb repeated reads
```

This can dramatically reduce database load.

# 43. Cache Locality

Suppose users repeatedly request:

```text
Product A
Product A
Product A
Product B
Product A
Product C
```

The most frequently accessed data becomes "hot."

```text
Hot data
   ↓
Cache
```

This is known as:

> **Temporal locality**

Recently accessed data is likely to be accessed again.

This is one reason caching works so well.

# 49. Cache Security

Caching can introduce security bugs.

Suppose:

```text
GET /api/profile
```

returns user-specific data.

If you use:

```text
profile
```

as the cache key, you might accidentally return one user's profile to another user.

Bad:

```text
profile → Rahul
```

Then:

```text
User B → profile
       ↓
Rahul's data 😱
```

Instead, use a user-specific key:

```text
profile:user:123
profile:user:456
```

Always consider authorization boundaries when caching.

# 50. Cache-Control and HTTP Caching

HTTP itself supports caching.

For example:

```http

```

This tells clients/CDNs that the response may be cached for a period.

You can also use:

```text
ETag
Last-Modified
Expires
Cache-Control
```

This is separate from Redis but follows the same general idea:

> **Avoid recomputing or transferring data unnecessarily.**

# 51. A Practical Node.js Cache-Aside Pattern

A simplified service might look like:

```javascript
async function getUser(userId) {
    const key = `user:${userId}`;

    const cached = await redis.get(key);

    if (cached) {
        return JSON.parse(cached);
    }

    const user = await userRepository.findById(userId);

    if (!user) {
        return null;
    }

    await redis.set(
        key,
        JSON.stringify(user),
        { EX: 300 }
    );

    return user;
}
```

Flow:

```text
getUser()
   ↓
Redis GET
   │
   ├── Hit → return
   │
   └── Miss
        ↓
     Database
        ↓
      Redis SET
        ↓
      return
```

---

# 52. Practical Update Pattern

```javascript
async function updateUser(userId, data) {
    const user = await userRepository.update(userId, data);

    await redis.del(`user:${userId}`);

    return user;
}
```

This creates:

```text
Write
 ↓
Database
 ↓
Invalidate Cache
```

Then the next read rebuilds the cache.

# 53. Don't Cache Everything

This is a very important rule.

Bad architecture:

```text
Every database query
      ↓
Redis
```

You may end up with:

```text
Huge Redis memory usage
Complex invalidation
Stale data
More infrastructure
```

Instead:

> **Cache data that actually benefits from caching.**

Think about:

```text
Frequency
Cost
Stability
Size
Freshness requirement
```

---

# 54. Cache Decision Framework

Before caching something, ask:

```text
1. Is it frequently read?
2. Is the database query expensive?
3. Is the data relatively stable?
4. Can stale data be tolerated?
5. Is the object small enough?
6. How will we invalidate it?
7. What happens if Redis fails?
```

If the answers make sense, caching may be valuable.

---

# 55. Interview Question 🎯

### "Why does caching improve scalability?"

Strong answer:

> Caching stores frequently accessed data in a faster layer such as Redis, allowing the application to serve repeated reads without querying the primary database each time. This reduces database load, lowers latency, and allows the system to handle more traffic with the same backend infrastructure.

---

# 56. Interview Question 🎯

### "What is cache-aside?"

Strong answer:

> In cache-aside, the application first checks the cache. If the data exists, it returns it directly. If there is a cache miss, the application reads from the database, stores the result in the cache, and then returns it. The application is responsible for managing the cache.

---

# 57. Interview Question 🎯

### "What is cache invalidation?"

Strong answer:

> Cache invalidation is the process of removing or updating cached data when the underlying source of truth changes, so that clients don't continue receiving stale data.

---

# 58. Interview Question 🎯

### "What happens if Redis goes down?"

Strong answer:

> Ideally, the application falls back to the database so the system remains functional, although performance may degrade. However, the architecture must also protect the database from a sudden surge of cache misses, using mechanisms such as rate limiting, request coalescing, capacity headroom, or controlled fallback behavior.

That's a much stronger answer than simply saying:

> "The application will use MongoDB."

# 60. Your URL Shortener Architecture

Let's upgrade our previous design.

Before:

```text
                 Load Balancer
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Node 1       Node 2       Node 3
          │            │            │
          └────────────┼────────────┘
                       ▼
                    MongoDB
```

Now:

```text
                 Load Balancer
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Node 1       Node 2       Node 3
          │            │            │
          └────────────┼────────────┘
                       │
                       ▼
                  ┌─────────┐
                  │  Redis  │
                  └────┬────┘
                       │
                 Cache Miss
                       │
                       ▼
                  ┌─────────┐
                  │ MongoDB │
                  └─────────┘
```

Now:

```text
Hot URL
   ↓
Redis
   ↓
Fast redirect ⚡
```

while:

```text
Cold URL
   ↓
Redis MISS
   ↓
MongoDB
   ↓
Redis
   ↓
Redirect
```

This is a much more scalable architecture.
