# Lesson 11.7 — Database Scaling ⭐⭐⭐⭐⭐

> **Goal:** Understand how databases scale when a single database server is no longer enough, and learn **replication, read replicas, partitioning, sharding, replication lag, failover, and high availability**.

This is a very important lesson for backend engineers.

So far, we've built:

```text
Client
   ↓
Load Balancer
   ↓
Multiple Node.js Servers
   ↓
Redis
   ↓
Database
```

But now imagine your application grows to millions of users.

Your Node.js servers can handle the traffic.

Redis is handling many reads.

But eventually:

```text
                    MongoDB
                       💥
```

becomes the bottleneck.

So the question becomes:

> **How do we scale the database?**

---

# 1. Why Is Database Scaling Difficult?

Scaling application servers is relatively straightforward:

```text
1 Server
   ↓
3 Servers
   ↓
10 Servers
```

because application servers can often be stateless.

Databases are different.

They contain **persistent shared state**:

```text
Users
Orders
Payments
Products
Messages
URLs
```

You can't simply create:

```text
Database 1
Database 2
Database 3
```

and assume everything works.

You need to decide:

- Where is the data stored?
    
- Which database handles writes?
    
- Which handles reads?
    
- How is data copied?
    
- What happens if a database fails?
    
- How do we keep replicas synchronized?
    
- How do we split data?
    
- How do we find the correct shard?
    

That's what database scaling solves.

---

# 2. Database Scaling Strategies

There are several major approaches:

```text
1. Vertical Scaling
2. Replication
3. Read Replicas
4. Partitioning
5. Sharding
6. Caching
```

We've already discussed vertical scaling and caching.

Today we'll focus heavily on:

```text
Replication
Read Replicas
Partitioning
Sharding
```

---

# 3. Vertical Scaling a Database

The simplest approach:

> Make the database server more powerful.

For example:

```text
Before:

CPU: 4 cores
RAM: 16 GB
SSD: 500 GB
```

Upgrade:

```text
After:

CPU: 32 cores
RAM: 128 GB
SSD: 4 TB
```

Architecture remains:

```text
Node Servers
     │
     ▼
┌─────────────┐
│   MongoDB   │
│  Powerful   │
│   Server    │
└─────────────┘
```

This can work surprisingly well for smaller systems.

But eventually you hit limits.

---

# 4. The Problem With Vertical Scaling

Suppose your database needs:

```text
512 GB RAM
```

You might find an appropriately sized machine.

But eventually:

```text
CPU
RAM
Storage
Network
Cost
```

all have practical limits.

And there's another problem:

> **One database server can become a single point of failure.**

If:

```text
MongoDB Server ❌
```

your application may lose access to its data.

This leads us to replication.

---

# 5. Database Replication

Replication means:

> **Maintaining copies of the same data on multiple database servers.**

For example:

```text
                  Primary
                    │
             ┌──────┴──────┐
             ▼             ▼
         Replica 1      Replica 2
```

All contain copies of the data.

If the primary contains:

```text
users
orders
products
```

the replicas maintain copies.

---

# 6. Why Replication?

Replication provides several benefits:

### High availability

If primary fails:

```text
Primary ❌
Replica 1 ✅
Replica 2 ✅
```

another node can potentially become primary.

### Read scaling

Reads can be distributed across replicas.

### Disaster recovery

Multiple copies of data reduce the risk of losing everything from a single machine failure.

---

# 7. Primary + Replicas

A common architecture:

```text
                       Application
                           │
                           ▼
                    ┌────────────┐
                    │   Primary  │
                    └─────┬──────┘
                          │
                 Replication
                    /     \
                   ▼       ▼
              Replica 1  Replica 2
```

The primary usually handles writes:

```text
INSERT
UPDATE
DELETE
```

and replicas can serve reads depending on the database and consistency requirements.

---

# 8. Write Flow

Suppose a user creates an account.

```text
POST /api/users
```

The application sends the write to the primary:

```text
Node.js
   ↓
Primary DB
   ↓
Write
```

Then replication propagates the change:

```text
Primary
   │
   ├────────→ Replica 1
   │
   └────────→ Replica 2
```

---

# 9. Read Flow

Suppose users request profiles.

```text
GET /api/users/123
```

We can potentially route reads to replicas:

```text
                  Read Request
                       │
              ┌────────┴────────┐
              ▼                 ▼
         Replica 1          Replica 2
```

This reduces pressure on the primary.

---

# 10. Read Scaling

Suppose:

```text
100,000 requests/sec
```

and:

```text
90% reads
10% writes
```

Then:

```text
90,000 reads/sec
10,000 writes/sec
```

A single primary may struggle with all operations.

Instead:

```text
                       Application
                       /         \
                    Reads       Writes
                      │            │
                      ▼            ▼
                 Replicas       Primary
```

Now read traffic can be distributed.

---

# 11. Read Replica Architecture

A more realistic architecture:

```text
                    Application Servers
                         /       \
                        /         \
                   Reads          Writes
                     │               │
                     ▼               ▼
              ┌────────────┐    ┌──────────┐
              │ Read Router│    │ Primary  │
              └─────┬──────┘    └────┬─────┘
                    │                │
             ┌──────┼──────┐         │
             ▼      ▼      ▼         │
          Replica Replica Replica    │
             1        2       3      │
                                     │
                                     └── Replication
```

The exact implementation depends on the database.

---

# 12. MongoDB Example

MongoDB commonly uses a:

> **Replica Set**

For example:

```text
                MongoDB Replica Set

                   Primary
                      │
             ┌────────┴────────┐
             ▼                 ▼
          Secondary          Secondary
```

One node is primary.

Other nodes maintain copies.

If the primary fails, an eligible secondary can be elected as the new primary.

---

# 13. PostgreSQL Example

PostgreSQL can also use replication.

Conceptually:

```text
                 PostgreSQL Primary
                         │
                ┌────────┴────────┐
                ▼                 ▼
           Read Replica       Read Replica
```

The exact replication technologies and deployment patterns vary, but the system-design concept is the same:

> **One source handles writes and other nodes maintain copies for availability/read scaling.**

---

# 14. Replication Is Not Instantaneous

This is extremely important.

Suppose:

```text
Primary
  ↓
UPDATE balance = 1000
```

The replica might receive the update slightly later.

So:

```text
Primary:
balance = 1000

Replica:
balance = 900
```

for a short period.

This is called:

> **Replication Lag**

---

# 15. Replication Lag Example

Imagine:

```text
User
  ↓
POST /profile
  ↓
Primary
  ↓
name = Rahul
```

Immediately after:

```text
GET /profile
```

might go to:

```text
Replica
```

But the replica hasn't received the update yet.

The response could contain:

```text
name = old value
```

That's a consistency problem.

---

# 16. Read-After-Write Problem

Suppose:

```text
Write:
POST /api/profile
```

returns successfully.

Then immediately:

```text
GET /api/profile
```

returns old data.

The user might think:

> "My update didn't work!"

But actually:

```text
Primary = updated
Replica = not updated yet
```

This is one reason we need to understand consistency models.

We'll study them in **Lesson 11.11**.

---

# 17. Solutions to Read-After-Write Problems

Depending on requirements, you can:

### Option 1 — Read from primary

Immediately after a write:

```text
Write → Primary
Read  → Primary
```

This provides stronger consistency.

### Option 2 — Track session/operation state

Temporarily prefer a sufficiently fresh replica.

### Option 3 — Wait for replication

Only return success after the required replication condition is satisfied.

### Option 4 — Accept eventual consistency

For some data, slight delay is perfectly acceptable.

The correct solution depends on the business requirement.

---

# 18. Strong vs Eventual Consistency

Very simplified:

### Strong consistency

After a successful write:

```text
Read → New value
```

### Eventual consistency

After a successful write:

```text
Read → Maybe old value temporarily
```

Eventually:

```text
Read → New value
```

For example:

### Banking

Strong consistency is usually important.

### Social media likes

A small delay may be acceptable.

We'll study this in detail later.

---

# 19. Replication and High Availability

Suppose:

```text
Primary
   ❌
```

Without replication:

```text
Application
    ↓
Database ❌
```

With replication:

```text
               Primary ❌
                  │
             Election
                  │
                  ▼
              Secondary
                  ↓
              New Primary
```

The application can potentially continue operating.

This provides:

> **High availability**

---

# 20. Replication Does NOT Automatically Increase Write Capacity

This is a common beginner mistake.

Suppose:

```text
Primary
   ↓
Replica 1
Replica 2
Replica 3
```

You might think:

> "Now I have four databases, so I can handle four times the writes."

Not necessarily.

If all writes still go to:

```text
Primary
```

then the primary remains the write bottleneck.

Replication primarily helps with:

```text
Read scaling
Availability
Redundancy
```

not automatically write scaling.

---

# 21. Write Scaling

If writes themselves become the bottleneck, we need other strategies.

One major approach is:

> **Sharding**

---

# 22. What Is Sharding?

Sharding means:

> **Splitting data across multiple database servers so that each server stores only part of the dataset.**

Instead of:

```text
             One Database
          ┌───────────────┐
          │ All users     │
          │ All orders    │
          │ All products  │
          └───────────────┘
```

we divide the data:

```text
            Database Cluster

        ┌─────────┬─────────┬─────────┐
        │ Shard 1 │ Shard 2 │ Shard 3 │
        └─────────┴─────────┴─────────┘
```

Each shard owns a subset of data.

---

# 23. Simple Sharding Example

Suppose we have:

```text
30 million users
```

We could divide them:

```text
Shard 1 → Users 1–10M
Shard 2 → Users 10M–20M
Shard 3 → Users 20M–30M
```

Now:

```text
User request
     ↓
Determine shard
     ↓
┌────┼────┐
▼    ▼    ▼
S1   S2   S3
```

Each database handles only part of the workload.

---

# 24. Shard Key

To determine where data belongs, we use a:

> **Shard Key**

For example:

```text
userId
```

A routing mechanism may calculate:

```text
hash(userId)
```

and choose the shard.

Conceptually:

```text
userId
   ↓
Hash Function
   ↓
Shard Number
```

---

# 25. Hash-Based Sharding

Suppose:

```text
userId = 12345
```

We calculate:

```text
hash(12345)
```

Then perhaps:

```text
hash % 3
```

returns:

```text
Shard 2
```

So:

```text
User 12345
      ↓
Shard 2
```

Another user:

```text
User 98765
      ↓
Shard 1
```

This distributes users relatively evenly when the hash/key distribution is good.

---

# 26. Range-Based Sharding

Another approach is range-based.

For example:

```text
Shard 1:
userId 1–1,000,000

Shard 2:
userId 1,000,001–2,000,000

Shard 3:
userId 2,000,001–3,000,000
```

This is simple to understand.

But it can create uneven load.

---

# 27. Hot Shard Problem

Suppose most users are from:

```text
userId 1–1,000,000
```

and these users are much more active.

Then:

```text
Shard 1 → 90% traffic 💥
Shard 2 → 5%
Shard 3 → 5%
```

This is called a:

> **Hot shard**

A bad shard key can destroy the benefits of sharding.

---

# 28. Choosing a Good Shard Key

A good shard key should ideally provide:

- Even distribution
    
- High cardinality
    
- Good query patterns
    
- Avoidance of hotspots
    
- Predictable routing
    

For example:

```text
userId
```

may work well for some systems.

But it depends on how your queries and traffic are distributed.

---

# 29. Partitioning vs Sharding

These terms are often confused.

### Partitioning

Partitioning means dividing a dataset into smaller logical pieces.

For example:

```text
Orders 2024
Orders 2025
Orders 2026
```

These partitions might still exist within one database system.

### Sharding

Sharding distributes those pieces across different database servers.

```text
Database Cluster

Server 1 → Partition A
Server 2 → Partition B
Server 3 → Partition C
```

A useful mental model:

> **Partitioning = splitting data.**

> **Sharding = splitting data across machines.**

Sharding often involves partitioning, but partitioning doesn't necessarily require multiple machines.

---

# 30. Vertical Partitioning

There's another type:

> **Vertical partitioning**

Instead of splitting rows, you split columns/data groups.

Suppose:

```text
User
────────────────────
id
name
email
password
profileImage
bio
preferences
```

You might separate:

```text
Core User Data
──────────────
id
name
email
```

and:

```text
Profile Data
────────────
profileImage
bio
preferences
```

This can reduce the amount of data needed for common queries.

---

# 31. Horizontal Partitioning

Horizontal partitioning means splitting rows.

For example:

```text
Partition A:
Users 1–1M

Partition B:
Users 1M–2M

Partition C:
Users 2M–3M
```

Each partition has the same schema but different rows.

---

# 32. Database Sharding Architecture

A larger architecture could look like:

```text
                       Application
                            │
                            ▼
                      Query Router
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
          Shard 1       Shard 2       Shard 3
             │             │             │
         Replica Set   Replica Set   Replica Set
```

This is much more scalable than one database server.

But also much more complex.

---

# 33. Sharding Is Not Free

Sharding introduces problems:

```text
More infrastructure
More operational complexity
Cross-shard queries
Cross-shard transactions
Data rebalancing
Shard-key decisions
Monitoring complexity
Backups
Failover
```

Therefore:

> **Don't shard simply because your application has many users.**

Shard when your workload actually requires it.

---

# 34. Cross-Shard Queries

Suppose:

```text
Users are sharded by userId
```

Now you want:

> "Find all users named Rahul."

Where should you search?

You may need:

```text
Shard 1
Shard 2
Shard 3
Shard 4
...
```

Then combine the results.

This is more expensive and complicated than querying one database.

Therefore:

> **Your shard key should align with important query patterns whenever possible.**

---

# 35. Cross-Shard Transactions

Imagine an order requires:

```text
User data
+
Inventory data
+
Payment data
```

If these live on different shards, coordinating a transaction becomes much harder.

This is one reason distributed transactions should not be introduced casually.

---


↓

```text

```

↓


↓

# 37. Don't Shard Too Early

Suppose your application has:

```text
10,000 users
```

and you create:

```text
10 database shards
```

That's probably unnecessary.

You now have to manage:

```text
10 databases
10 backups
10 monitoring targets
10 failure scenarios
10 deployment concerns
```

The complexity isn't justified.

Start simple.

Scale when measurements show that you need to.

---

# 38. Read Replicas vs Sharding

This distinction is extremely important.

### Read replicas

Mainly solve:

```text
Too many reads
```

Architecture:

```text
Primary
  │
  ├── Replica 1
  ├── Replica 2
  └── Replica 3
```

### Sharding

Can solve:

```text
Too much total data
Too many writes
Too much workload for one database
```

Architecture:

```text
Shard 1
Shard 2
Shard 3
```

---

# 39. Comparison

|Feature|Read Replicas|Sharding|
|---|---|---|
|Data|Full/near-full copy|Different subset|
|Main purpose|Read scaling|Data/workload scaling|
|Write scaling|Limited|Yes, potentially|
|Storage scaling|Limited|Yes|
|Complexity|Moderate|High|
|Failover|Good|More complex|
|Cross-data queries|Easier|Harder|

---

# 40. Replication + Sharding

Large systems can combine both.

For example:

```text
                  Application
                       │
                       ▼
                  Query Router
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Shard 1      Shard 2      Shard 3
          │            │            │
       ┌──┴──┐      ┌──┴──┐      ┌──┴──┐
       ▼     ▼      ▼     ▼      ▼     ▼
    Primary Rep Primary Rep Primary Rep
```

Now:

- Data is partitioned across shards.
    
- Each shard has replicas.
    
- Replicas provide redundancy and read scaling.
    
- Shards provide data/workload scaling.
    

This is a common pattern at very large scale.

---

# 41. Database Load Balancing

Once we have replicas, we need routing.

For example:

```text
Writes
   ↓
Primary

Reads
   ↓
Read Router
   ↓
Replica 1 / Replica 2 / Replica 3
```

The application or database driver may handle some of this.

The exact mechanism depends on the database.

---

# 42. Connection Pooling

Earlier we discussed connection bottlenecks.

Each application server often maintains a pool of database connections.

For example:

```text
Node Server 1
   └── 20 DB connections

Node Server 2
   └── 20 DB connections

Node Server 3
   └── 20 DB connections
```

Total:

```text
20 × 3 = 60 connections
```

If you scale to:

```text
20 Node servers
```

you might suddenly have:

```text
20 × 20 = 400 connections
```

So database scaling also requires connection management.

---

# 43. Database Scaling and Redis

Remember our caching architecture:

```text
Node
  ↓
Redis
  ↓
Database
```

Caching reduces database load.

Therefore a good scaling strategy might be:

```text
Optimize queries
       ↓
Add indexes
       ↓
Add Redis
       ↓
Read replicas
       ↓
Sharding if necessary
```

Don't jump straight to sharding.

# 44. Example: URL Shortener

Let's apply everything to your URL shortener.

Suppose:

```text
100 million redirects/day
```

and:

```text
95% reads
5% writes
```

Caching:

```text
Redis
```

might absorb most redirect lookups.

Then:

```text
Application
   ↓
Redis
   ↓
MongoDB
```

For database scaling:

```text
MongoDB Primary
      │
 ┌────┴────┐
 ▼         ▼

```

Writes:

```text
Create short URL
       ↓
Primary
```

Reads:

```text

       ↓

```

# 45. What About Analytics?

Your URL shortener also tracks:

```text
clicks
timestamp
IP information
referrer
device
location
```

Imagine:

```text
100 million redirects/day
```

If every redirect performs:

```text
1 analytics write
```

then:

```text
100 million writes/day
```

Now we have a write-heavy workload.

Instead of making the user wait:

```text

   ↓
Write analytics
   ↓
Redirect response
```

we could use:

```text

   ↓
```

# 46. Database Scaling Is Often About Workload Separation

Instead of asking:

> "How do I make MongoDB infinitely powerful?"

ask:

> **"How can I reduce the amount of work MongoDB needs to perform?"**

For example:

```text
Caching
    ↓
Reduce reads

Indexes
    ↓
Reduce query cost

Read replicas
    ↓
Distribute reads

Queues
    ↓
Move background writes

Sharding
    ↓
Distribute data/workload
```

This is a much stronger system-design mindset.

# 47. High Availability

Database high availability means:

> **The system can continue operating when a database node fails.**

For example:

```text
                  Primary
                     │
             ┌───────┴───────┐
             ▼               ▼
          Replica 1       Replica 2
```

If primary fails:

```text
Primary ❌
    ↓
Election / Failover
    ↓
Replica 1 becomes primary
```

The exact mechanism depends on the database.

---

# 48. Failover

Failover means:

> **Automatically or manually switching to another healthy database node when the current primary fails.**

Example:

```text
Before:

Primary → A
Replica → B
Replica → C


Failure:

A ❌


After:

Primary → B
Replica → C
```

This improves availability.

---

# 49. Automatic Failover

Modern database systems can often detect:

```text
Primary unavailable
```

and trigger an election or failover process.

The important concept is:

```text
Failure
   ↓
Detection
   ↓
Election
   ↓
New Primary
   ↓
Application reconnects
```

This is one of the foundations of highly available databases.

---

# 50. Backups Are Still Necessary

Replication is **not the same as backup**.

This is extremely important.

Suppose:

```text
Primary
   ↓
Replica 1
   ↓
Replica 2
```

An administrator accidentally runs:

```sql
DELETE FROM users;
```

The replicas may faithfully replicate the deletion.

Now:

```text
Primary ❌
Replica 1 ❌
Replica 2 ❌
```

The data was replicated—but the mistake was replicated too.

Therefore you still need:

```text
Backups
Point-in-time recovery
Disaster recovery
```

Replication protects primarily against certain **infrastructure failures**.

Backups help recover from:

- accidental deletion
    
- corruption
    
- bad deployments
    
- logical errors
    
- certain security incidents
    

---

# 51. Database Scaling Decision Tree

When your database becomes slow:

```text
Database slow
     │
     ▼
Check queries
     │
     ├── Bad queries?
     │       ↓
     │    Optimize
     │
     ├── Missing indexes?
     │       ↓
     │    Add indexes
     │
     ├── Too many reads?
     │       ↓
     │    Cache / replicas
     │
     ├── Too much data?
     │       ↓
     │    Partition
     │
     └── Too much overall workload?
             ↓
          Consider sharding
```

This is a much better approach than immediately saying:

> "Let's shard MongoDB."

---

# 52. Interview Question 🎯

### "What are read replicas?"

Strong answer:

> Read replicas are database instances that maintain copies of data from a primary database. They can serve read traffic, reducing the workload on the primary and improving read scalability. They can also improve availability, but replication lag means reads from replicas may temporarily return stale data.

---

# 53. Interview Question 🎯

### "What is database sharding?"

Strong answer:

> Sharding is a horizontal scaling technique where data is distributed across multiple database nodes based on a shard key. Each shard owns a subset of the data, allowing the system to distribute storage and workload across multiple machines.

---

# 54. Interview Question 🎯

### "What is replication lag?"

Strong answer:

> Replication lag is the delay between a change being committed on the primary database and that change becoming available on a replica. It can cause stale reads and create read-after-write consistency issues.

---

# 55. Interview Question 🎯

### "Does replication solve database write scaling?"

Strong answer:

> Not by itself. In a typical primary-replica architecture, writes still go through the primary, so replication primarily helps with read scaling and availability. Write scaling may require techniques such as partitioning, sharding, batching, workload separation, or application-level redesign.

---

```text

                 Reads                     Writes
```
