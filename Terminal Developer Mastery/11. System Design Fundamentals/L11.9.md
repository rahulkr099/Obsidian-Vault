# Lesson 11.9 — Database Indexing ⭐⭐⭐⭐⭐

> **Goal:** Understand how database indexes make queries fast, how B-Tree and hash indexes work, how to design compound/composite indexes, how to use `EXPLAIN`, and the mistakes that make indexes ineffective.

This is one of the **most practical backend lessons** in this module.

You can have:

```text
1 million documents
```

and a query might be slow.

Add the right index:

```text
1 million documents
        ↓
      Index
        ↓
Much faster lookup ⚡
```

But indexes aren't magic.

A badly designed index can:

- waste memory
    
- slow down writes
    
- increase storage
    
- fail to improve a query
    

So let's understand what's really happening.

---

# 1. What Is an Index?

An index is a **data structure that helps a database find rows/documents faster without scanning the entire dataset**.

Imagine a book with 1,000 pages.

Without an index, you might do:

```text
Page 1
Page 2
Page 3
...
Page 1000
```

until you find:

```text
"MongoDB"
```

That's similar to a:

> **Full collection/table scan**

With an index:

```text
MongoDB → Page 347
```

You jump much closer to the required data.

---

# 2. Database Without an Index

Suppose MongoDB has:

```text
1,000,000 users
```

and you execute:

```javascript
User.findOne({
    email: "rahul@example.com"
});
```

Without an index on `email`, the database may need to inspect many documents:

```text
Document 1 ❌
Document 2 ❌
Document 3 ❌
...
Document 500,000 ❌
...
Document 823,471 ✅
```

This is expensive.

---

# 3. Full Collection Scan

A full scan is conceptually:

```text
Database
   │
   ├── Document 1
   ├── Document 2
   ├── Document 3
   ├── ...
   └── Document 1,000,000
```

The database checks documents until it finds the required data or completes the query.

This can become very expensive as data grows.

---

# 4. Database With an Index

Create an index:

```javascript
db.users.createIndex({
    email: 1
});
```

Now the database has a separate structure:

```text
Index
──────────────────────
email → document location

a@example.com → ...
b@example.com → ...
rahul@example.com → ...
z@example.com → ...
```

Query:

```javascript
db.users.findOne({
    email: "rahul@example.com"
});
```

The database can use the index to locate the matching document much more efficiently.

---

# 5. Important Mental Model

Think:

```text
Without index:

Query
  ↓
Scan many records
  ↓
Find result
```

With index:

```text
Query
  ↓
Search index
  ↓
Find matching record(s)
  ↓
Read actual data
```

The index acts like a navigation structure.

---

# 6. Indexes Are Separate Data Structures

An index is not simply:

```text
"Make this field faster."
```

The database creates and maintains an additional data structure.

Conceptually:

```text
                 Database
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Table/Data          Index
          │                   │
          │             email → row
          │             email → row
          │             email → row
          │
          └──────────────┐
                         ▼
                     Actual data
```

This is why indexes consume:

- memory
    
- storage
    
- CPU during writes
    

---

# 7. Why Indexes Improve Read Performance

Suppose:

```text
N = 1,000,000 records
```

Without a useful index, the database may need to inspect a large portion of those records.

With an appropriate tree-based index, the number of index comparisons can be dramatically smaller.

For a balanced B-Tree-like structure, lookup is roughly:

```text
O(log N)
```

instead of a linear scan:

```text
O(N)
```

The actual query cost is more complicated, but this gives you the right mental model.

---

# 8. B-Tree Index

One of the most important index structures is:

> **B-Tree**

Many relational databases use B-Tree-family indexes as their general-purpose default.

MongoDB also uses B-tree-based index structures.

Conceptually:

```text
                         [50]
                       /      \
                    [20]      [80]
                   /   \      /   \
                [10] [30]  [60] [90]
```

The tree remains balanced.

---

# 9. Searching a B-Tree

Suppose we're looking for:

```text
60
```

Start:

```text
50
```

Since:

```text
60 > 50
```

go right.

```text
80
```

Since:

```text
60 < 80
```

go left.

```text
60 ✅
```

We didn't scan everything.

---

# 10. Why B-Trees Are Powerful

B-Trees are useful for:

```text
Equality
Range queries
Sorting
Prefix-like ordered access
```

For example:

```sql
SELECT *
FROM users
WHERE age > 20;
```

or:

```sql
SELECT *
FROM users
ORDER BY created_at DESC;
```

A suitable B-Tree index can help these operations.

---

# 11. Range Queries

Suppose:

```text
age
```

has an index.

Query:

```sql
SELECT *
FROM users
WHERE age BETWEEN 20 AND 30;
```

A B-Tree is well suited to finding a range:

```text
20 ─────────────── 30
```

This is one reason B-Trees are so common.

---

# 12. Hash Index

Another index structure is:

> **Hash index**

Conceptually:

```text
Hash(key)
    ↓
Bucket
    ↓
Value
```

For example:

```text
email
   ↓
Hash Function
   ↓
Bucket
```

This is particularly useful for equality lookups such as:

```text
email = "rahul@example.com"
```

---

# 13. Hash vs B-Tree

A simplified comparison:

|Feature|B-Tree|Hash|
|---|---|---|
|Equality|✅|✅|
|Range queries|✅|❌/poor fit|
|Sorting|✅|❌|
|Ordered traversal|✅|❌|
|General-purpose|Excellent|Specialized|

For example:

```sql
WHERE age > 20
```

B-Tree is useful.

But:

```text
WHERE email = exact_value
```

can be well suited to a hash index.

In practice, B-Tree is often the default choice because it supports a wider range of query patterns.

---

# 14. MongoDB Index Example

Suppose:

```javascript
db.users.createIndex({
    email: 1
});
```

`1` means ascending order.

You can also see:

```javascript
db.users.createIndex({
    email: -1
});
```

which represents descending order.

For many equality lookups, the direction doesn't change the basic ability to locate the value.

---

# 15. Unique Index

Suppose every user must have a unique email.

MongoDB:

```javascript
db.users.createIndex(
    { email: 1 },
    { unique: true }
);
```

Now:

```text
rahul@example.com
```

can exist only once.

This gives you both:

```text
Fast lookup
+
Uniqueness enforcement
```

In PostgreSQL:

```sql
CREATE UNIQUE INDEX users_email_idx
ON users(email);
```

or a `UNIQUE` constraint can create an appropriate unique index behind the scenes.

---

# 16. Why Unique Indexes Matter

Imagine your registration API:

```text
POST /register
```

Two requests arrive:

```text
Request A:
rahul@example.com

Request B:
rahul@example.com
```

Application-level checking alone can have race conditions:

```text
A → "Does email exist?" → No
B → "Does email exist?" → No
A → Insert
B → Insert
```

A database-level unique constraint/index provides the final correctness guarantee.

This is an important backend principle:

> **Business invariants that must always hold should be enforced by the database when appropriate.**

---

# 17. Composite / Compound Index

Now suppose you frequently query:

```text
userId + createdAt
```

For example:

```javascript
Post.find({
    userId: userId
}).sort({
    createdAt: -1
});
```

A single-field index on `userId` helps find the user's posts, but a compound index can be better:

```javascript
db.posts.createIndex({
    userId: 1,
    createdAt: -1
});
```

This is a:

> **Compound index**

Also called:

> **Composite index**

---

# 18. Why Compound Indexes?

Imagine:

```text
posts
────────────────────────────
userId | createdAt | title
```

Query:

```text
userId = 123
ORDER BY createdAt DESC
```

Index:

```text
(userId, createdAt)
```

can help the database:

1. Find the user's records
    
2. Get them in the desired date order
    

This can be much more efficient than filtering and sorting a large result set separately.

---

# 19. The Order of Fields Matters

This is extremely important.

Suppose:

```javascript
{
    userId: 1,
    createdAt: -1
}
```

is your index.

The index is logically organized like:

```text
userId
   ↓
createdAt
```

The order affects which queries can use the index efficiently.

---

# 20. The Leftmost Prefix Rule

For a compound index:

```text
(A, B, C)
```

the index is naturally useful for queries involving:

```text
A
A + B
A + B + C
```

But not necessarily as efficiently for:

```text
B
C
B + C
```

This is often called the:

> **Leftmost prefix principle**

For example:

```javascript
{
    userId: 1,
    createdAt: -1,
    status: 1
}
```

supports query patterns involving:

```text
userId
userId + createdAt
userId + createdAt + status
```

but a query only on:

```text
status
```

generally needs a different index if you want efficient lookup.

---

# 21. Example

Index:

```text
(A, B, C)
```

### Query 1

```text
WHERE A = ?
```

Good.

### Query 2

```text
WHERE A = ? AND B = ?
```

Good.

### Query 3

```text
WHERE A = ?
AND B = ?
AND C = ?
```

Good.

### Query 4

```text
WHERE B = ?
```

Not a good match.

### Query 5

```text
WHERE C = ?
```

Not a good match.

---

# 22. Index Order and Sorting

Suppose you frequently query:

```javascript
Post.find({
    userId: 123
}).sort({
    createdAt: -1
});
```

A useful index:

```javascript
{
    userId: 1,
    createdAt: -1
}
```

The index can help both:

```text
Filtering
+
Ordering
```

This can avoid expensive in-memory sorting.

---

# 23. Selectivity

Another important concept:

> **Selectivity**

Selectivity describes how well a field distinguishes between records.

Suppose we have:

```text
1,000,000 users
```

Field:

```text
country
```

might have:

```text
India → 300,000
USA → 100,000
...
```

That's relatively low selectivity.

But:

```text
email
```

might have:

```text
1 unique email per user
```

That's very high selectivity.

---

# 24. High vs Low Selectivity

Imagine:

```text
1,000,000 records
```

Query:

```text
WHERE gender = 'male'
```

Maybe:

```text
500,000 matches
```

The index may not eliminate much work.

But:

```text
WHERE email = 'rahul@example.com'
```

might return:

```text
1 match
```

The index is extremely useful.

---

# 25. Important: Low Selectivity Doesn't Mean "Never Index"

A low-selectivity field can still be useful depending on:

- Other predicates
    
- Compound indexes
    
- Data distribution
    
- Query cost
    
- Sorting
    
- Partitioning
    
- Database optimizer behavior
    

For example:

```text
status = "active"
```

might be low-selectivity alone.

But:

```text
status = "active"
AND createdAt > ...
```

could benefit from a compound index.

So don't use a simplistic rule:

> "Low cardinality means never index."

---

# 26. Cardinality

Closely related:

> **Cardinality**

It refers to the number of distinct values in a field.

For example:

```text
gender:
2–3 distinct values

country:
~200 distinct values

email:
~1 distinct value per user
```

Higher cardinality often makes an index more selective.

But again:

> Query patterns matter more than a single rule.

---

# 27. Query Planner

Modern databases don't blindly use every available index.

They have a:

> **Query optimizer / query planner**

It evaluates possible execution strategies.

Conceptually:

```text
Query
  ↓
Query Planner
  ↓
Choose execution plan
  ├── Index Scan
  ├── Collection/Table Scan
  └── Other strategies
```

The planner tries to find a low-cost plan.

---

# 28. Why Doesn't the Database Always Use an Index?

Because sometimes an index isn't actually faster.

Suppose:

```text
1,000,000 records
```

and your query returns:

```text
900,000 records
```

Using an index might require:

```text
Index
  ↓
900,000 record lookups
```

A sequential scan could be cheaper.

Therefore:

> **An index existing doesn't mean the optimizer should use it.**

---

# 29. EXPLAIN

One of the most important tools for backend engineers is:

> **EXPLAIN**

It shows how the database plans to execute a query.

PostgreSQL:

```sql
EXPLAIN
SELECT *
FROM users
WHERE email = 'rahul@example.com';
```

For deeper analysis:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'rahul@example.com';
```

---

# 30. MongoDB Explain

MongoDB provides:

```javascript
db.users.find({
    email: "rahul@example.com"
}).explain("executionStats");
```

This is extremely useful.

You can inspect things such as:

```text
executionTimeMillis
totalKeysExamined
totalDocsExamined
nReturned
```

---

# 31. totalDocsExamined

Suppose:

```text
nReturned = 1
totalDocsExamined = 1,000,000
```

That's a warning sign.

The database returned only one document but examined a million.

You probably need to investigate indexing/query design.

---

# 32. Good Example

Suppose:

```text
nReturned = 1
totalDocsExamined = 1
```

That's much better.

Maybe:

```text
totalKeysExamined = 1
```

as well.

Conceptually:

```text
Query
 ↓
Index
 ↓
1 matching entry
 ↓
1 document
```

Very efficient.

---

# 33. COLLSCAN vs IXSCAN

In MongoDB explain output, you'll commonly encounter:

```text
COLLSCAN
```

meaning:

> **Collection Scan**

The database scans documents.

And:

```text
IXSCAN
```

meaning:

> **Index Scan**

The database uses an index.

For example:

```text
COLLSCAN
    ↓
Potentially expensive
```

versus:

```text
IXSCAN
    ↓
Index
    ↓
Document
```

---

# 34. PostgreSQL Seq Scan vs Index Scan

PostgreSQL may show:

```text
Seq Scan
```

which means sequential scan.

Or:

```text
Index Scan
```

which means an index is being used.

Again, a sequential scan isn't automatically bad.

If the query needs most of the table, sequential scanning may be the better plan.

---

# 35. Covering Index

An advanced but important concept:

> **Covering index**

Suppose you query:

```sql
SELECT email
FROM users
WHERE user_id = 123;
```

and the index contains all the information needed for the query.

Then the database may be able to answer directly from the index without fetching the full table row.

Conceptually:

```text
Query
 ↓
Index
 ↓
Result
```

instead of:

```text
Query
 ↓
Index
 ↓
Table row
 ↓
Result
```

This can significantly reduce I/O.

---

# 36. PostgreSQL INCLUDE

PostgreSQL supports included columns in indexes.

For example:

```sql
CREATE INDEX users_email_idx
ON users(user_id)
INCLUDE (email);
```

Now the index contains:

```text
user_id
email
```

which may help certain index-only scans.

---

# 37. MongoDB Covered Queries

MongoDB also has the concept of queries that can potentially be answered entirely from the index.

For example, if your query only needs fields represented in the index, MongoDB may avoid fetching full documents.

This can reduce work.

---

# 38. Indexes Cost Something

Here's the critical trade-off:

> **Indexes improve reads but make writes more expensive.**

Suppose you have:

```text
users
```

with:

```text
100 indexes
```

Now you insert:

```text
new user
```

The database may need to update many index structures.

Conceptually:

```text
INSERT
  │
  ├── Update table/document
  ├── Update index 1
  ├── Update index 2
  ├── Update index 3
  └── ...
```

Therefore:

> **Don't create indexes blindly.**

---

# 39. Index Storage Cost

Suppose your table is:

```text
10 GB
```

and you create several indexes.

You might end up with:

```text
Table → 10 GB
Indexes → several GB
```

The exact amount depends on data types and index structure.

Indexes consume:

- disk
    
- memory/cache space
    
- CPU
    

---

# 40. Too Many Indexes

Suppose your collection has:

```text
100 million documents
```

and you create:

```text
20 indexes
```

You may have:

```text
Huge storage
More write overhead
More memory pressure
More maintenance
```

You should periodically evaluate whether indexes are actually used.

---

# 41. Index Every Field?

No.

This is a common beginner mistake.

Suppose:

```text
User
├── name
├── email
├── age
├── city
├── phone
├── bio
├── createdAt
└── ...
```

Don't automatically create:

```text
name index
email index
age index
city index
phone index
bio index
createdAt index
...
```

Instead:

> **Index according to your actual query patterns.**

---

# 42. Query-Driven Indexing

Suppose your API frequently performs:

```text
GET /users?email=...
```

Create:

```text
email index
```

Suppose:

```text
GET /posts?userId=123&sort=createdAt
```

Create:

```text
(userId, createdAt)
```

Suppose:

```text
GET /orders?status=paid&createdAt>...
```

Consider:

```text
(status, createdAt)
```

The index should follow the workload.

---

# 43. Example: E-Commerce

Suppose:

```text
GET /products?category=electronics
```

You might use:

```text
category
```

Then:

```text
GET /products?category=electronics&price<50000
```

Potentially:

```text
(category, price)
```

Then:

```text
GET /products?category=electronics
ORDER BY price ASC
```

Again:

```text
(category, price)
```

can be useful.

---

# 44. Example: URL Shortener

Your URL shortener has:

```text
shortCode
```

and frequently performs:

```text
findOne({ shortCode })
```

This is an excellent index candidate.

MongoDB:

```javascript
db.urls.createIndex(
    { shortCode: 1 },
    { unique: true }
);
```

Now:

```text
shortCode
   ↓
Index
   ↓
URL document
```

This is exactly the kind of query where an index is extremely valuable.

---

# 45. Example: Analytics

Suppose your analytics data contains:

```text
urlId
timestamp
device
country
referrer
```

You frequently query:

```text
urlId = X
ORDER BY timestamp DESC
```

A compound index:

```javascript
{
    urlId: 1,
    timestamp: -1
}
```

is a strong candidate.

Why?

Because it matches:

```text
filter → urlId
sort   → timestamp
```

---

# 46. Index Prefixes

Suppose:

```javascript
{
    urlId: 1,
    timestamp: -1
}
```

This index can be useful for:

```text
urlId
```

and:

```text
urlId + timestamp
```

But not generally as the ideal index for:

```text
timestamp
```

alone.

Again:

> **The leftmost field matters.**

---

# 47. ESR Rule

For MongoDB compound indexes, you'll often hear about the:

> **ESR rule**

It stands for:

```text
E → Equality
S → Sort
R → Range
```

A common guideline is:

```text
Equality fields
        ↓
Sort fields
        ↓
Range fields
```

For example:

```text
{
    userId: 1,       // Equality
    createdAt: -1,   // Sort
    amount: 1        // Range
}
```

This is a useful starting heuristic for compound index design.

It isn't a universal law; the actual query and planner behavior still matter.

---

# 48. Example of ESR

Suppose query:

```javascript
db.orders.find({
    userId: 123,
    amount: { $gt: 1000 }
}).sort({
    createdAt: -1
});
```

Potential index:

```javascript
{
    userId: 1,
    createdAt: -1,
    amount: 1
}
```

Conceptually:

```text
Equality
userId
   ↓
Sort
createdAt
   ↓
Range
amount
```

Then test it with `explain()`.

---

# 49. Index Prefix vs Query Prefix

Don't blindly memorize ESR and create indexes without measuring.

For every important query, ask:

```text
What does the query filter on?
What does it sort on?
What range does it use?
How selective are the predicates?
How many documents are returned?
```

Then validate with:

```text
EXPLAIN
```

This is how real performance work is done.

---

# 50. Partial Indexes

Sometimes you only want to index a subset of data.

For example, suppose:

```text
1 million users
```

but only:

```text
100,000 active users
```

are queried frequently.

A partial index can index only matching documents.

PostgreSQL example:

```sql
CREATE INDEX active_users_email_idx
ON users(email)
WHERE active = true;
```

Now the index doesn't need to cover inactive users.

This can save space and improve efficiency for certain workloads.

---

# 51. Sparse Indexes

MongoDB also supports sparse indexes.

A sparse index can omit documents where the indexed field doesn't exist.

For example:

```javascript
db.users.createIndex(
    { phone: 1 },
    { sparse: true }
);
```

This can be useful when a field is optional.

However, sparse and partial indexing have different semantics, so choose based on the actual requirement.

---

# 52. TTL Indexes in MongoDB

MongoDB supports TTL indexes.

For example, suppose you have temporary sessions:

```text
session
expiresAt
```

You can create:

```javascript
db.sessions.createIndex(
    { expiresAt: 1 },
    { expireAfterSeconds: 0 }
);
```

Then MongoDB can automatically remove documents after their expiration time.

This is useful for:

```text
Temporary sessions
OTP records
Temporary tokens
Short-lived data
```

Be careful with security-sensitive workflows and understand the TTL monitor's behavior; expiration isn't necessarily an exact-to-the-second deletion mechanism.

---

# 53. Indexing and Security

Indexes can also support security-sensitive operations.

For example:

```text
Find user by email
```

with:

```text
unique email index
```

can enforce uniqueness.

But don't store secrets in indexed fields just because they're indexed.

For example:

```text
password hash
```

shouldn't be exposed through queries or APIs simply because the database contains it.

Indexing doesn't change the sensitivity of data.

---

# 54. Indexing and Pagination

Indexes are extremely important for pagination.

Suppose you use:

```text
?page=1000
```

with:

```sql
OFFSET 100000
LIMIT 20
```

The database may still need to process/skip many rows.

A better approach for large datasets is often:

> **Cursor-based / keyset pagination**

Suppose:

```text
createdAt
id
```

are indexed.

You can query:

```text
createdAt < lastSeenCreatedAt
```

and retrieve the next batch.

---

# 55. Keyset Pagination Example

Suppose:

```text
createdAt
```

is indexed.

First request:

```text
GET /posts?limit=20
```

Then the client receives:

```text
lastCreatedAt = 2026-08-15T10:00:00
```

Next:

```text
GET /posts?before=2026-08-15T10:00:00&limit=20
```

The database can use the index to jump into the correct range.

This is much more scalable than large offsets for many workloads.

---

# 56. Indexes and Sorting

Suppose:

```sql
SELECT *
FROM posts
ORDER BY created_at DESC
LIMIT 20;
```

An index on:

```text
created_at
```

can potentially let the database retrieve the newest records efficiently.

Without a suitable index:

```text
Scan many rows
   ↓
Sort
   ↓
Take 20
```

With a suitable index:

```text
Index
   ↓
Newest records
   ↓
Take 20
```

Huge difference on large datasets.

---

# 57. Indexing Relationships

Suppose:

```text
orders.user_id
```

is frequently used:

```sql
SELECT *
FROM orders
WHERE user_id = 123;
```

Index:

```sql
CREATE INDEX orders_user_id_idx
ON orders(user_id);
```

This is particularly important for foreign-key-like lookup columns used in application queries.

---

# 58. Foreign Keys and Indexes

In PostgreSQL, a foreign key does not automatically mean the referencing column has an index.

For example:

```text
orders.user_id
```

may benefit from an index if you frequently:

```text
JOIN orders
ON users.id = orders.user_id
```

or:

```text
WHERE user_id = ?
```

Indexing foreign-key columns is often useful, especially for joins and parent-row updates/deletes.

---

# 59. Indexing Doesn't Fix Bad Queries

Suppose you have:

```sql
SELECT *
FROM users;
```

No index can make:

> "Return every user."

cheap if you genuinely need every row.

Likewise:

```javascript
db.users.find({})
```

will naturally require a lot of work if you're asking for the entire collection.

Indexes help specific access patterns.

---

# 60. Avoid SELECT *

For APIs, don't blindly return every column.

Instead of:

```sql
SELECT *
FROM users
WHERE id = 123;
```

you might use:

```sql
SELECT id, name, email
FROM users
WHERE id = 123;
```

Benefits:

- Less data read
    
- Less network transfer
    
- Less serialization
    
- Potentially enables covering/index-only strategies
    

This is a small but useful optimization.

---

# 61. N+1 Query Problem

Indexes won't solve everything.

Suppose:

```text
Get 100 courses
```

Then your application does:

```text
Query course 1
Query teacher 1
Query course 2
Query teacher 2
...
```

You could end up with:

```text
101 queries
```

Even if every query is indexed.

This is an:

> **N+1 query problem**

You may need:

- joins
    
- batching
    
- aggregation
    
- eager loading
    
- better data modeling
    

Indexing is only one part of query optimization.

# 62. Indexing + Caching

Remember Lesson 11.6.

A good architecture might be:

```text
Request
   ↓
Redis
   │
   ├── Hit → Response
   │
   └── Miss
        ↓
      Database
        ↓
      Index
        ↓
      Result
        ↓
      Redis
```

So:

```text
Redis
  ↓
Reduces database requests

Index
  ↓
Makes remaining database requests faster
```

They solve different problems.

# 63. Indexing + Read Replicas

You can also combine:

```text
Application
    │
    ▼
Redis
    │
    ▼
Read Replica
    │
    ▼
```

This gives:

```text
+

```

# 64. Don't Over-Index

Imagine:

```text
Write-heavy system
```

with:

```text
20 indexes
```

Every insert/update may require index maintenance.

Your reads may be fast, but writes become expensive.

Therefore:

> **Index based on real query patterns and measured performance.**

# 65. Index Lifecycle

In a real application:

```text

    ↓
Monitor slow queries
    ↓
Identify expensive query
    ↓
EXPLAIN
    ↓
Design index
    ↓
Test
    ↓

    ↓
```

This is much better than:


# 66. Practical Mongoose Example

Suppose your schema:

```javascript
const userSchema = new mongoose.Schema({
```

You can also define indexes explicitly:

```javascript
userSchema.index({
```

```javascript
postSchema.index({
    userId: 1,
```

# 68. A Practical Query Analysis

Suppose:

```javascript
db.urls.find({
    nanoId: "aB92x"
}).explain("executionStats");
```

Before index:

```text
COLLSCAN
totalDocsExamined: 500000
nReturned: 1
```

That's concerning.

Create:

```javascript
db.urls.createIndex({
    nanoId: 1
});
```

Then:

```text
IXSCAN
totalKeysExamined: 1
totalDocsExamined: 1
nReturned: 1
```

That's a huge improvement.

---

# 69. But Don't Chase "1 Document Examined" Blindly

Real queries can be more complex.

For example:

```text
nReturned = 10,000
```

Then examining many documents may be unavoidable.

The correct question is:

> **Is the query doing a reasonable amount of work for the result it needs to produce?**

Performance engineering is about understanding workload, not blindly minimizing every metric.

---

# 70. Interview Question 🎯

### "What is a database index?"

A strong answer:

> A database index is an auxiliary data structure that allows the database to locate records more efficiently for specific query patterns, reducing the need for full table or collection scans. The trade-off is additional storage and overhead during inserts and updates.

---

# 71. Interview Question 🎯

### "Why don't we index every column?"

Strong answer:

> Indexes consume storage and memory and must be maintained when data changes. Too many indexes can significantly increase write cost and maintenance overhead. Therefore indexes should be created based on actual query and access patterns.

---

# 72. Interview Question 🎯

### "What is a compound index?"

Strong answer:

> A compound index contains multiple fields in a defined order. It can efficiently support queries that match the index's prefix and can often help with filtering and sorting together. The order of fields is important.

---

# 73. Interview Question 🎯

### "What is the difference between B-Tree and Hash indexes?"

Strong answer:

> B-Tree indexes maintain ordered data and support equality, range queries, and ordering. Hash indexes are optimized primarily for exact equality lookups and don't naturally support range queries or ordering. B-Tree is therefore a common general-purpose choice.

---

# 74. Interview Question 🎯

### "How would you investigate a slow query?"

A strong backend-engineer answer:

> First I'd identify the query and measure its latency and frequency. Then I'd inspect its execution plan using tools such as `EXPLAIN`, `EXPLAIN ANALYZE`, or MongoDB's `explain("executionStats")`. I'd check for full scans, excessive documents examined, poor index usage, inefficient sorting, large result sets, and N+1 patterns. Then I'd test an appropriate index or query/data-model change and compare before-and-after measurements.

That's an excellent practical answer.

---

# 75. Common Beginner Mistakes ❌

### Mistake 1

> "Add an index and everything becomes fast."

No.

---

### Mistake 2

Indexing every field.

Bad.

---

### Mistake 3

Ignoring index order in compound indexes.

Very common.

---

### Mistake 4

Ignoring writes.

Indexes make writes more expensive.

---

### Mistake 5

Never using `EXPLAIN`.

If you're debugging database performance, execution plans are extremely valuable.

---

### Mistake 6

Thinking:

```text
COLLSCAN = always bad
```

Not necessarily.

A full scan can be the correct plan for some queries.

---

# 76. The Golden Rule ⭐

Remember:

> **Indexes should follow queries, not the other way around.**

Don't think:

```text
"What fields should I index?"
```

Think:

```text
"What queries does my application execute frequently?"
              ↓
"What does their execution plan look like?"
              ↓
"What index would make that access pattern efficient?"
```

That's how professional database optimization works.
