# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.1 — What is CI/CD? ⭐⭐⭐⭐⭐

CI/CD is one of the most important concepts for a backend engineer because it connects **your code** to **production** in a reliable and automated way.

Instead of doing this manually:

```text
Write Code
   ↓
git push
   ↓
SSH into server
   ↓
git pull
   ↓
npm install
   ↓
run tests
   ↓
build
   ↓
restart server
   ↓
check if everything works
```

you can build a pipeline:

```text
Code
 ↓
Git Push
 ↓
CI Pipeline
 ├── Install
 ├── Lint
 ├── Test
 └── Build
       ↓
Docker Image
       ↓
Registry
       ↓
Deployment
       ↓
Health Check
       ↓
Production
```

The machine does most of the repetitive work for you.

---

# 1. What Does CI/CD Mean?

CI/CD usually refers to:

- **CI — Continuous Integration**
    
- **CD — Continuous Delivery**
    
- **CD — Continuous Deployment**
    

The second `CD` can mean either **Continuous Delivery** or **Continuous Deployment**, depending on the organization.

---

# 2. Continuous Integration

### Simple definition

> **Continuous Integration means frequently merging code into a shared repository and automatically verifying that the code still works.**

Imagine a team has:

```text
main
 │
 ├── feature/auth
 ├── feature/payment
 └── feature/profile
```

A developer finishes authentication:

```bash
git add .
git commit -m "add authentication"
git push origin feature/auth
```

A Pull Request is created.

GitHub Actions can automatically run:

```text
Install dependencies
       ↓
Run ESLint
       ↓
Run tests
       ↓
Build application
       ↓
Security checks
```

If something fails:

```text
❌ Tests failed
```

The developer knows before the code is merged.

---

# 3. Why Continuous Integration Is Important

Without CI:

```text
Developer A → code
Developer B → code
Developer C → code
       ↓
      merge
       ↓
     💥
Production broken
```

With CI:

```text
Developer
   ↓
Pull Request
   ↓
Automated checks
   ↓
   ├── ❌ Failed → Fix
   │
   └── ✅ Passed
          ↓
        Review
          ↓
        Merge
```

CI catches problems early.

### Important principle

> **The earlier you detect a bug, the cheaper it is to fix.**

---

# 4. Continuous Delivery

Continuous Delivery means:

> **Every change that passes the pipeline is kept ready for deployment.**

For example:

```text
Git Push
   ↓
Tests
   ↓
Build
   ↓
Docker Image
   ↓
Registry
   ↓
READY FOR PRODUCTION
```

But there may still be a **manual approval** before production deployment.

Example:

```text
Pull Request
     ↓
CI
     ↓
Build
     ↓
Staging
     ↓
Manual Approval
     ↓
Production
```

This is common in organizations where production deployments require approval.

---

# 5. Continuous Deployment

Continuous Deployment goes one step further.

> **Every change that passes all required checks is automatically deployed to production.**

Example:

```text
git push
   ↓
CI
   ↓
Tests
   ↓
Build
   ↓
Docker Image
   ↓
Deploy
   ↓
Health Check
   ↓
Production
```

No human needs to click a deployment button.

---

# 6. Delivery vs Deployment

This distinction is very important for interviews.

|Concept|Production deployment|
|---|---|
|Continuous Integration|❌ Not necessarily|
|Continuous Delivery|🟡 Ready for deployment|
|Continuous Deployment|✅ Automatic|

Think of it like this:

### Continuous Delivery

```text
"Ready to deploy."
```

### Continuous Deployment

```text
"Already deployed."
```

---

# 7. CI/CD Is More Than Deployment

Many beginners think:

> CI/CD = automatically deploy my application.

That's incomplete.

A good pipeline can handle:

```text
Code
 ↓
Formatting
 ↓
Linting
 ↓
Testing
 ↓
Security scanning
 ↓
Build
 ↓
Package
 ↓
Docker image
 ↓
Registry
 ↓
Deployment
 ↓
Health check
 ↓
Monitoring
```

So CI/CD is really an **automation system for software delivery**.

# 8. Typical Backend CI/CD Pipeline

Let's take your MERN application.

Suppose your repository looks like:

```text
my-app/
├── client/
├── server/
├── docker-compose.yml
├── Dockerfile
└── package.json
```

You push:

```bash
git push origin main
```

GitHub receives the event.

Then:

```text
GitHub
   ↓
GitHub Actions
   ↓
Checkout code
   ↓
Install dependencies
   ↓
Run lint
   ↓
Run tests
   ↓
Build frontend
   ↓
Build Docker image
   ↓
Push image to GHCR
   ↓
SSH into server
   ↓
Pull new image
   ↓
Start new container
   ↓
Health check
   ↓
Nginx → Application
```

That's a real production-style workflow.

# 9. What Happens Without CI/CD?

Imagine deploying manually.

You connect to your server:

```bash
ssh user@server
```

Then:

```bash
cd my-app
git pull
npm install
npm test
npm run build
pm2 restart app
```

Then you discover:

```text
❌ Tests failed
```

Or:

```text
❌ Environment variable missing
```

Or:

```text
❌ Build failed
```

Or worse:

```text
Application started
       ↓
Database migration failed
       ↓
Production broken
```

Manual deployment is error-prone.

---

# 10. CI/CD Gives You Repeatability

Suppose you deploy 100 times.

A manual process might look like:

```text
Deployment #1 → commands A B C D
Deployment #2 → commands A B C
Deployment #3 → commands A B C D E
Deployment #4 → forgot command C
Deployment #5 → different configuration
```

This creates **configuration drift** and human mistakes.

With automation:

```text
Deployment #1 ─┐
Deployment #2 ─┤
Deployment #3 ─┤→ Same pipeline
Deployment #4 ─┤
Deployment #5 ─┘
```

Same process every time.

That's a major advantage.

# 11. The Four Major CI/CD Stages

A useful mental model is:

```text
SOURCE
   ↓
VERIFY
   ↓
PACKAGE
   ↓
DEPLOY
```

### Stage 1 — Source

Code comes from Git:

```bash
git push
```

---

### Stage 2 — Verify

Check whether the application is healthy:

```text
Lint
Tests
Security scan
Build
```

---

### Stage 3 — Package

Create something deployable:

```text
Docker Image
        or
Build Artifact
```

For example:

```bash
docker build -t my-api:1.0.0 .
```

---

### Stage 4 — Deploy

Send it to production:

```text
Registry
   ↓
Server
   ↓
Docker
   ↓
Nginx
```

---

# 12. CI/CD Pipeline vs CI/CD Tool

Don't confuse the two.

### CI/CD pipeline

The **process**.

Example:

```text
Test → Build → Package → Deploy
```

### CI/CD tool

The software that executes the process.

Examples:

- GitHub Actions
    
- GitLab CI/CD
    
- Jenkins
    
- CircleCI
    
- Azure Pipelines
    

In this module, we'll mainly use **GitHub Actions**.

---

# 13. GitHub Actions

GitHub Actions allows you to automate workflows inside GitHub.

A workflow can say:

```yaml
on:
  push:
    branches:
      - main
```

Meaning:

> Whenever code is pushed to `main`, execute this workflow.

Then:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
```

Meaning:

> Start an Ubuntu runner and execute the job.

Then:

```yaml
steps:
  - checkout code
  - install dependencies
  - run tests
```

We'll learn the actual syntax in **Lesson 12.6**.

# 14. CI/CD and Docker

Docker fits extremely well into CI/CD.

Without Docker:

```text
Developer machine
       ↓
Different Node version
       ↓
Production server
       ↓
Different environment
       ↓
💥
```

With Docker:

```text
Application
    ↓
Docker Image
    ↓
Same image
 ┌──┴───────┐
 ↓          ↓
Staging   Production
```

The same image can be tested and deployed.

This gives you a much more predictable deployment process.

# 17. What If Deployment Fails?

This is where professional CI/CD becomes interesting.

Suppose:

```text
New version
   ↓
Container starts
   ↓
Health check
   ↓
❌ FAILED
```

A good deployment system should **not blindly send traffic to it**.

Instead:

```text
New Version
     ↓
Health Check
     ↓
     ❌
     ↓
Rollback
     ↓
Previous Version
```

For example:

```text
v1.4.0 → working
v1.5.0 → broken
             ↓
         rollback
             ↓
v1.4.0 → working
```

We'll study this deeply in Lessons **12.13 and 12.17**.

# 18. Important CI/CD Principles

Remember these principles.

### 1. Automate repetitive work

Don't make developers repeatedly run:

```bash
npm test
npm run lint
docker build
docker push
ssh ...
```

Automate them.

---

### 2. Fail early

Bad:

```text
Build
 ↓
Deploy
 ↓
Production
 ↓
Tests
```

Good:

```text
Test
 ↓
Build
 ↓
Deploy
```

Never deploy known-broken code.

---

### 3. Make deployments repeatable

Every deployment should follow the same process.

```text
Same input
   ↓
Same pipeline
   ↓
Predictable result
```

---

### 4. Keep deployments reversible

Always have a way back.

```text
Version A
   ↓
Version B
   ↓
problem
   ↓
Version A
```

---

### 5. Never put secrets in Git

Never do:

```yaml
password: mySuperSecret123
```

inside your repository.

Instead:

```text
GitHub Secrets
       ↓
CI/CD
       ↓
Environment
```

We'll cover this properly in Lesson 12.8.

---

### 6. Deployment is not complete until verified

Don't assume:

```text
Container started = application works
```

Instead:

```text
Container started
       ↓
Health check
       ↓
API check
       ↓
Logs
       ↓
Traffic verification
```

# 19. CI/CD Interview Questions

### Q1. What is CI?

**Answer:**

> Continuous Integration is the practice of frequently integrating code changes into a shared repository and automatically running validation such as tests, linting, and builds.

---

### Q2. What is Continuous Delivery?

> Continuous Delivery keeps successfully tested software ready for production deployment, usually with a manual approval step.

---

### Q3. What is Continuous Deployment?

> Continuous Deployment automatically deploys successfully validated changes to production without requiring manual approval.

---

### Q4. Why is CI/CD useful?

Because it provides:

- Automation
    
- Faster releases
    
- Consistent deployments
    
- Early bug detection
    
- Reduced human error
    
- Repeatability
    
- Easier rollback
    
- Better developer productivity
    

---

### Q5. Does CI/CD mean everything is automatically deployed?

**No.**

CI/CD can include manual approval.

For example:

```text
CI
 ↓
Build
 ↓
Staging
 ↓
Manual Approval
 ↓
Production
```

That's still a CI/CD workflow.

## 🔑 Lesson 12.1 Takeaways

Remember these **8 points**:

1. **CI = continuously integrate and verify code.**
    
2. **Continuous Delivery = keep validated software ready to deploy.**
    
3. **Continuous Deployment = automatically deploy validated software.**
    
4. CI/CD is much more than simply deploying an application.
    
5. Docker makes CI/CD deployments more predictable.
    
6. Secrets should never be committed to Git.
    
7. Production deployments should include health checks.
    
8. A professional deployment system must have a **rollback strategy**.
