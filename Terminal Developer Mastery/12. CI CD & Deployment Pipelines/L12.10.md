# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.10 — Container Registries ⭐⭐⭐⭐⭐

In Lesson 12.9, we learned how GitHub Actions can turn your application into a Docker image:

```text
Git Commit
    ↓
GitHub Actions
    ↓
Tests
    ↓
Docker Build
    ↓
my-api:<git-sha>
```

But now we have a problem:

> **Where does the Docker image live after CI builds it?**

We need a **container registry**.

---

# 1. What Is a Container Registry?

A container registry is a service that stores Docker/OCI images so they can be pushed, pulled, versioned, and deployed.

Think of it as:

```text
GitHub Repository
      ↓
Source Code

Container Registry
      ↓
Docker Images
```

For example:

```text
my-api:a83f91c
my-api:1.4.0
```

can be stored in a registry.

Then your production server can download the exact image:

```bash
docker pull ...
```

---

# 2. The Complete Flow

Our pipeline now becomes:

```text
Developer
    ↓
Git Push
    ↓
GitHub
    ↓
GitHub Actions
    ↓
Tests
    ↓
Docker Build
    ↓
Docker Image
    ↓
Container Registry
    ↓
Production Server
    ↓
Docker Container
```

This is the bridge between **CI and CD**.

---

# 3. Why Not Build Directly on Production?

You could SSH into your server and run:

```bash
git pull
docker build .
docker compose up
```

But this has drawbacks.

Your production server becomes responsible for:

```text
Source code
Build tools
Git
Docker build process
Dependency downloads
Compilation
```

Instead:

```text
CI
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Registry
```

Production only needs to:

```text
Pull image
 ↓
Run image
```

This makes production simpler.

---

# 4. Two Popular Registries

For this roadmap, we'll focus on:

### Docker Hub

```text
docker.io
```

### GitHub Container Registry

```text
ghcr.io
```

Both can store Docker images.

For your GitHub-based CI/CD setup, **GHCR is especially convenient** because it integrates naturally with GitHub repositories and Actions.

---

# 5. Docker Hub

Docker Hub is one of the most widely known container registries.

An image might look like:

```text
username/my-api:1.0.0
```

or:

```text
username/my-api:a83f91c
```

Conceptually:

```text
Docker Hub
   │
   └── username
          │
          └── my-api
                 ├── 1.0.0
                 ├── 1.1.0
                 └── a83f91c
```

---

# 6. GitHub Container Registry

GitHub Container Registry uses:

```text
ghcr.io
```

A typical image reference looks like:

```text
ghcr.io/username/my-api:a83f91c
```

So:

```text
ghcr.io
   ↓
username
   ↓
my-api
   ↓
a83f91c
```

For a GitHub repository, this makes the relationship between:

```text
Git repository
      ↓
GitHub Actions
      ↓
GHCR image
```

very clear.

---

# 7. Image Naming

Docker image names follow a structure.

For example:

```text
ghcr.io/rahul/my-api:abc123
```

Break it down:

```text
ghcr.io       → registry
rahul         → owner/namespace
my-api        → image/repository
abc123        → tag
```

Conceptually:

```text
registry / owner / image : tag
```

---

# 8. Image Tags

You can use:

```text
my-api:latest
my-api:1.0.0
my-api:1.2.0
my-api:a83f91c
```

For CI/CD, Git SHA tags are very useful:

```text
my-api:a83f91c
```

because they provide traceability.

---

# 9. Tagging Strategy

For your project, I recommend:

```text
Every commit:
my-api:<git-sha>
```

For releases:

```text
my-api:1.0.0
```

Optionally:

```text
my-api:latest
```

for convenience.

But production should ideally deploy:

```text
my-api:<immutable-version>
```

rather than:

```text
my-api:latest
```

---

# 10. Why `latest` Is Dangerous

Imagine:

```text
my-api:latest
```

points to:

```text
version A
```

Production runs:

```text
version A
```

Then someone pushes:

```text
version B
```

and updates:

```text
latest
```

Now:

```text
latest → version B
```

You no longer have a stable reference.

With:

```text
my-api:a83f91c
```

you know exactly what you're deploying.

---

# 11. Image Digests

Docker images also have immutable content digests.

For example:

```text
sha256:9a8f...
```

A digest identifies the exact image content.

So instead of:

```text
my-api:latest
```

you can eventually deploy:

```text
my-api@sha256:9a8f...
```

This provides strong immutability.

---

# 12. Tags vs Digests

Think of:

```text
Tag
 ↓
Human-friendly name
```

while:

```text
Digest
 ↓
Exact image identity
```

Example:

```text
my-api:1.4.0
       ↓
sha256:abc123...
```

The tag can potentially move.

The digest identifies the exact content.

---

# 13. Public vs Private Images

Registries usually support:

```text
Public
Private
```

### Public image

Anyone can potentially pull it.

Useful for:

```text
Open-source projects
Public base images
Public software
```

### Private image

Only authorized users/services can pull it.

Production backend images should generally be:

```text
Private
```

especially if they contain proprietary application code.

---

# 14. Docker Login

For Docker Hub, you can authenticate with:

```bash
docker login
```

Then Docker asks for credentials.

For GHCR:

```bash
docker login ghcr.io
```

Authentication is required before pushing private images or pushing under an account.

---

# 15. Never Put Registry Passwords in Git

Never do:

```bash
docker login -u rahul -p mypassword
```

inside a repository.

Instead use:

```text
Credential
   ↓
Secret storage
   ↓
CI
   ↓
docker login
```

GitHub Actions can securely provide credentials.

---

# 16. GitHub Container Registry Authentication

For GitHub Actions, GitHub provides a special token:

```text
GITHUB_TOKEN
```

This can often be used for operations involving GitHub resources, including publishing packages when the workflow has appropriate permissions.

For example:

```yaml
permissions:
  contents: read
  packages: write
```

Notice:

```text
contents: read
```

and:

```text
packages: write
```

The workflow needs permission to publish the image.

---

# 17. Why Permissions Matter

Compare:

```yaml
permissions:
  contents: write
  packages: write
```

with:

```yaml
permissions:
  contents: read
  packages: write
```

The second is safer if the workflow only needs to:

```text
Read repository
+
Push package
```

It doesn't need to modify repository contents.

This is the **least privilege** principle from Lesson 12.8.

---

# 18. Login to GHCR in GitHub Actions

A common pattern is:

```yaml
- name: Login to GHCR
  uses: docker/login-action@v3
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

In GitHub Actions, `GITHUB_TOKEN` is typically provided automatically.

The exact permissions must be configured correctly.

---

# 19. Build and Push

Now we can combine:

```text
Docker Build
+
Registry Push
```

Example:

```yaml
- name: Build and push
  uses: docker/build-push-action@v6
  with:
    context: .
    push: true
    tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

This creates:

```text
ghcr.io/<owner>/<repository>:<commit-sha>
```

and pushes it to GHCR.

---

# 20. Complete GHCR Workflow

A simple version:

```yaml
name: Build Image

on:
  push:
    branches:
      - main

permissions:
  contents: read
  packages: write

jobs:
  docker:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

The flow is:

```text
Push main
   ↓
GitHub Actions
   ↓
Checkout
   ↓
Buildx
   ↓
GHCR Login
   ↓
Docker Build
   ↓
Docker Push
   ↓
GHCR
```

---

# 21. Important: Test Before Push

Our earlier CI architecture should still be respected.

Don't immediately do:

```text
Push
 ↓
Docker build
 ↓
Registry
```

Better:

```text
Push
 ↓
Lint
 ↓
Tests
 ↓
Build
 ↓
Docker image
 ↓
Registry
```

So your Docker job should depend on your test/quality jobs.

---

# 22. Professional Workflow

For example:

```yaml
jobs:
  test:
    ...

  docker:
    needs: test
    ...
```

Now:

```text
test
 ↓
PASS
 ↓
Docker Build
 ↓
Push
```

If tests fail:

```text
test ❌
 ↓
Docker Push skipped
```

That's exactly what you want.

---

# 23. Don't Push Images From Pull Requests

A good rule:

```text
Pull Request
    ↓
Tests
    ↓
Docker Build
    ↓
No Push
```

After merge:

```text
main
 ↓
Tests
 ↓
Docker Build
 ↓
Push
```

This prevents untrusted PR code from automatically publishing images.

---

# 24. Why PR Code Is Potentially Dangerous

Remember:

```text
Pull Request
```

could contain code from:

```text
External contributor
```

or a compromised branch.

If your workflow automatically exposes:

```text
GITHUB_TOKEN
Registry credentials
Production credentials
```

to untrusted PR code, you could create a serious security problem.

Therefore:

> **Keep privileged operations restricted to trusted workflows and branches.**

---

# 25. Registry Authentication vs Application Secrets

Don't confuse:

```text
Registry credentials
```

with:

```text
Application secrets
```

Registry credentials allow:

```text
Push/pull images
```

Application secrets include:

```text
DATABASE_URL
JWT_SECRET
PAYMENT_SECRET
```

Keep them separate.

---

# 26. Pulling the Image on Production

Suppose GHCR contains:

```text
ghcr.io/rahul/my-api:a83f91c
```

Your Linux server can pull:

```bash
docker pull ghcr.io/rahul/my-api:a83f91c
```

Then:

```bash
docker run ghcr.io/rahul/my-api:a83f91c
```

or Docker Compose can use it.

Eventually:

```yaml
services:
  api:
    image: ghcr.io/rahul/my-api:a83f91c
```

Now production doesn't need your Git repository.

It just needs the image.

---

# 27. Production Server Authentication

If your image is private:

```text
Production Server
       ↓
docker login ghcr.io
       ↓
Pull private image
```

The production server needs credentials with enough permission to pull the image.

Prefer a credential specifically intended for image pulling rather than using a personal account token.

---

# 28. Pull-Only Credentials

This is another least-privilege concept.

Production only needs:

```text
packages: read
```

It doesn't need:

```text
packages: write
```

because production shouldn't publish images.

Architecture:

```text
GitHub Actions
      ↓
packages: write
      ↓
GHCR

Production Server
      ↓
packages: read
      ↓
GHCR
```

Excellent separation.

---

# 29. Image Pull Policy

Docker Compose can pull images based on configuration and commands.

For example:

```bash
docker compose pull
```

downloads the image referenced by your Compose file.

Then:

```bash
docker compose up -d
```

starts the services.

A deployment might eventually be:

```text
New image
   ↓

   ↓

```

We'll build this in Lesson 12.11.

# 30. Image Versioning

Suppose you deploy:

```text
a83f91c
```

Then later:

```text
b7194e2
```

Your registry now contains:

```text
my-api
├── a83f91c
└── b7194e2
```

Rollback becomes easy:

```text
Production
   ↓
b7194e2 ❌
   ↓
a83f91c ✅
```

You don't need to rebuild anything.

This is one of the biggest benefits of using an image registry.

---

# 31. Rollback Without Rebuilding

This is worth emphasizing.

Without immutable artifacts:

```text
Rollback
 ↓
Checkout old code
 ↓
Build again
 ↓
Deploy
```

With versioned images:

```text
Rollback
 ↓
Select previous image
 ↓
Deploy
```

Much faster.

For example:

```text
Current:
my-api:b7194e2

Rollback:
my-api:a83f91c
```

That's a very clean rollback strategy.

---

# 32. Image Retention

If you build every commit:

```text
100 commits
 ↓
100 images
```

Eventually:

```text
1000 commits
 ↓
1000 images
```

Registry storage can grow.

So production systems often have retention policies.

For example:

```text
Keep:
latest 20 CI images
all release images
currently deployed versions
```

The exact policy depends on your needs.

---

# 33. Don't Delete Images Too Aggressively

Suppose:

```text
Production
 ↓
version A
```

and your cleanup process deletes A immediately.

Then rollback becomes difficult.

Keep enough history for:

- Recent rollback
    
- Incident investigation
    
- Reproducibility
    
- Compliance, if applicable

# 🧠 Interview Questions

### Q1. What is a container registry?

> A service that stores and distributes container images so they can be pushed, pulled, versioned, and deployed.

### Q2. What is GHCR?

> GitHub Container Registry, a GitHub-integrated registry for storing packages including container images.

### Q3. Why tag images with Git SHA?

> It creates a direct relationship between the container image and the exact source-code commit that produced it.

### Q4. Why shouldn't production use only `latest`?

> Because `latest` is mutable and doesn't uniquely identify a specific image version.

### Q5. What is an image digest?

> An immutable content identifier that uniquely identifies a specific container image.

### Q6. Why shouldn't production have push permissions?

> Production normally only needs to pull images. Granting push permissions violates least privilege and increases risk.

### Q7. Why shouldn't Pull Requests automatically push production images?

> PR code may be untrusted. Publishing privileges can expose credentials or allow malicious images to enter trusted infrastructure.

### Q8. What is the benefit of a registry in CI/CD?

> It separates image building from deployment and allows the exact same tested image to be deployed to multiple environments.

### Q9. Docker Hub vs GHCR?

> Both are container registries. Docker Hub is a general-purpose registry, while GHCR integrates particularly well with GitHub repositories and Actions.

### Q10. How does a registry improve rollback?

> Previous image versions remain available, allowing deployment to switch to an earlier known-good image without rebuilding it.

Remember these **15 points**:

1. **A container registry stores and distributes Docker images.**
    
2. Docker Hub and GHCR are two important registries.
    
3. GHCR integrates especially well with GitHub Actions.
    
4. Use versioned image tags.
    
5. Git SHA tags provide excellent traceability.
    
6. Image digests provide immutable image identity.
    
7. Don't depend on `latest` for production deployments.
    
8. Keep production images private when the application is proprietary.
    
9. CI needs permission to **push** images.
    
10. Production normally needs permission only to **pull** images.
    
11. Don't expose registry credentials to untrusted PR workflows.
