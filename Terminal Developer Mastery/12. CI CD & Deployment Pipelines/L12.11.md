---

# 1. What Is Docker Compose?

Docker Compose lets you define multiple containers and their configuration in one YAML file.

Instead of:

```bash
docker run ...
docker run ...
docker network create ...
docker volume create ...
```

you define:

```yaml
services:
  nginx:
  frontend:
  api:
  mongodb:
```

and run:

```bash
docker compose up -d
```

Compose creates and connects the required resources.

---

# 2. Why Do We Need Compose?

Imagine your MERN production application has:

```text
Nginx
Frontend
Backend
MongoDB
Redis
```

Without Compose:

```text
docker run nginx ...
docker run frontend ...
docker run backend ...
docker run mongo ...
docker run redis ...
```

You need to remember:

- Ports
    
- Networks
    
- Volumes
    
- Environment variables
    
- Restart policies
    
- Health checks
    
- Container names
    
- Dependencies
    

Compose centralizes this configuration.

---

# 3. Basic Compose File

Create:

```text
docker-compose.yml
```

or the modern:

```text
compose.yml
```

Example:

```yaml
services:

  api:
    image: ghcr.io/your-user/my-api:latest
    ports:
      - "5000:5000"

  mongo:
    image: mongo:8
    ports:
      - "27017:27017"
```

Then:

```bash
docker compose up -d
```

Compose starts:

```text
api
mongo
```

---

# 4. Compose Is Declarative

This is an important concept.

You don't tell Compose:

```text
"Create container A, then create network B, then attach container C..."
```

Instead, you describe the desired state:

```text
"I want an API container and MongoDB container connected together."
```

Compose figures out the necessary Docker operations.

This is called a:

> **Declarative configuration**

---

# 5. Services

A Compose file is organized around **services**.

Example:

```yaml
services:

  api:
    image: my-api:latest

  mongo:
    image: mongo:8
```

Here:

```text
api
mongo
```

are services.

Each service generally becomes one or more containers.

# 7. Docker Networks

One of the biggest advantages of Compose is automatic networking.

Suppose:

```yaml
services:
  api:
    image: my-api

  mongo:
    image: mongo
```

Both services are normally placed on a Compose-managed network.

The API can communicate with MongoDB using the service name:

```text
mongodb://mongo:27017/myapp
```

Notice:

```text
mongo
```

is not:

```text
localhost
```

---

# 8. Very Important: `localhost`

This is one of the most common Docker mistakes.

Inside the API container:

```text
localhost
```

means:

> **The API container itself.**

It does NOT mean the MongoDB container.

So this is usually wrong:

```text
mongodb://localhost:27017/myapp
```

if MongoDB is in another container.

Instead:

```text
mongodb://mongo:27017/myapp
```

because:

```text
mongo
```

is the Compose service name.

---

# 9. Service Discovery

Compose provides DNS-based service discovery.

For:

```yaml
services:

  api:
    ...

  mongo:
    ...
```

the API can reach:

```text
mongo
```

by hostname.

Conceptually:

```text
api container
     ↓
DNS lookup: mongo
     ↓
MongoDB container IP
```

You don't need to manually discover the container IP.

---

# 10. Don't Hard-Code Container IPs

Bad:

```text
mongodb://172.18.0.4:27017
```

Container IPs can change.

Better:

```text
mongodb://mongo:27017
```

Service names are stable.

---

# 11. Ports

Suppose your API listens on:

```text
5000
```

You can define:

```yaml
ports:
  - "5000:5000"
```

Format:

```text
HOST:CONTAINER
```

So:

```text
5000:5000
```

means:

```text
Host port 5000
       ↓
Container port 5000
```

---

# 12. Internal vs External Ports

This is very important for production.

Suppose:

```text
Nginx → API
```

You may not need to expose the API to the public internet.

Instead of:

```yaml
ports:
  - "5000:5000"
```

you can potentially use:

```yaml
expose:
  - "5000"
```

or simply let services communicate over the internal network without publishing the port.

Then:

```text
Internet
   ↓
Nginx
   ↓
Internal Docker Network
   ↓
API:5000
```

This is more secure.

---

# 13. Public vs Internal Services

A production architecture might be:

```text
Internet
   ↓
Nginx :80/:443
   │
   ├──→ Frontend
   │
   └──→ API :5000
            │
            └──→ MongoDB :27017
```

Only Nginx needs to be publicly reachable.

This reduces attack surface.

# 14. Environment Variables

Your API needs:

```text
PORT
DATABASE_URL
JWT_SECRET
NODE_ENV
```

Compose can provide them.

Example:

```yaml
services:

  api:
    image: ghcr.io/your-user/my-api:v1.0.0
    environment:
      NODE_ENV: production
      PORT: 5000
      DATABASE_URL: ${DATABASE_URL}
      JWT_SECRET: ${JWT_SECRET}
```

The actual secret values stay outside the Compose file.

---

# 15. `.env` With Compose

You can have:

```text
.env
```

on the production server:

```text
DATABASE_URL=mongodb://mongo:27017/myapp
JWT_SECRET=very-secret-value
```

Then:

```yaml
environment:
  DATABASE_URL: ${DATABASE_URL}
  JWT_SECRET: ${JWT_SECRET}
```

Compose reads the values from the environment.

However:

> **Don't commit the production `.env` file to Git.**

---

# 16. `.env.example`

Your repository can contain:

```text
.env.example
```

such as:

```text
DATABASE_URL=
JWT_SECRET=
NODE_ENV=production
PORT=5000
```

But production keeps:

```text
.env
```

on the server or uses a proper secret-management mechanism.

# 17. Environment Files

Compose also supports:

```yaml
env_file:
  - .env
```

Example:

```yaml
services:

  api:
    image: ghcr.io/your-user/my-api:v1.0.0
    env_file:
      - .env
```

Now the variables from `.env` are provided to the container.

For simple deployments, this can be convenient.

---

# 18. Environment Variable Precedence

Environment configuration can come from several places.

This can become confusing if you mix:

```text
.env
env_file
environment
shell variables
```

For production systems:

> Keep configuration simple and predictable.

For your learning project, I recommend:

```text
production .env
       ↓
Compose
       ↓
Container
```

and clearly document which values are required.

# 19. MongoDB Persistent Storage

Now a very important problem.

Containers are disposable.

If MongoDB stores its data only inside the container filesystem:

```text
MongoDB container
    ↓
Data
```

and the container is deleted:

```text
Container deleted
     ↓
Data potentially lost
```

We need persistent storage.

---

# 20. Docker Volumes

A Docker volume keeps data outside the container lifecycle.

Example:

```yaml
services:

  mongo:
    image: mongo:8
    volumes:
      - mongo_data:/data/db

volumes:
  mongo_data:
```

Architecture:

```text
MongoDB container
       │
       ↓
/data/db
       │
       ↓
Docker Volume
       │
       ↓
Persistent data
```

---

# 21. Container vs Volume

Think:

```text
Container
   = Application process
```

while:

```text
Volume
   = Persistent data
```

So:

```text
MongoDB container
     ↓
Can be replaced

MongoDB volume
     ↓
Data remains
```

This separation is extremely important.

---

# 22. Restarting vs Removing

If you run:

```bash
docker compose restart
```

the container restarts.

If you run:

```bash
docker compose down
```

the containers and network are removed.

But named volumes are normally preserved unless explicitly removed.

Be careful with:

```bash
docker compose down -v
```

The `-v` option removes associated volumes.

For databases:

> **Never casually use `docker compose down -v`.**

You could delete your persistent database data.

# 23. MongoDB in Production

For learning, you can run MongoDB in Compose.

For serious production systems, you should carefully evaluate whether you want your database inside the same Compose stack.

Alternatives include managed databases such as:

```text
MongoDB Atlas
AWS DocumentDB
Other managed database services
```

The reason is that database operations involve:

- Backups
    
- Replication
    
- Failover
    
- Monitoring
    
- Storage
    
- Security
    
- Upgrades
    

For your roadmap, we'll understand both approaches.

# 24. Health Checks

A container being "running" doesn't necessarily mean the application is healthy.

For example:

```text
Container: running
API: broken
Database: unavailable
```

Docker sees:

```text
running
```

but your application isn't actually usable.

Health checks solve this.

---

# 25. API Health Check

Your Express backend should have:

```text
GET /health
```

Example:

```javascript
app.get("/health", (req, res) => {
  res.status(200).json({
    status: "ok"
  });
});
```

Then Compose can check it.

---

# 26. Compose Healthcheck

Example:

```yaml
services:

  api:
    image: ghcr.io/your-user/my-api:v1.0.0
    healthcheck:
      test:
        [
          "CMD-SHELL",
          "wget --spider -q http://localhost:5000/health || exit 1"
        ]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s
```

The exact command depends on what's installed in your image.

For example, if your image doesn't contain `wget`, this check won't work.

---

# 27. Health Check Lifecycle

Conceptually:

```text
Container starts
      ↓
Starting
      ↓
Health checks
      ↓
Healthy
```

or:

```text
Container starts
      ↓
Health checks
      ↓
Unhealthy
```

Now other systems can make decisions based on actual health.

---

# 28. MongoDB Health Check

You can also check MongoDB.

A simple health check may use:

```yaml
healthcheck:
  test:
    [
      "CMD",
      "mongosh",
      "--eval",
      "db.adminCommand('ping')"
    ]
  interval: 10s
  timeout: 5s
  retries: 5
```

Again, make sure the chosen MongoDB image actually contains the command you're using.

---

# 29. Health vs Readiness

These concepts are worth learning early.

### Health

> Is the service functioning?

### Readiness

> Is the service ready to receive traffic?

For example:

```text
API container starts
      ↓
Node process running
      ↓
MongoDB connection not ready
      ↓
Not ready
```

A production deployment should avoid sending traffic to an application that isn't ready.

---

# 30. `depends_on`

You can express relationships:

```yaml
services:

  api:
    depends_on:
      mongo:
        condition: service_healthy

  mongo:
    ...
```

This can tell Compose:

```text
MongoDB
 ↓
Healthy
 ↓
Start API
```

But there is an important caveat:

> `depends_on` is not a replacement for application-level retry logic.

Your backend should still handle temporary database connection failures gracefully.

---

# 31. Why Startup Order Isn't Enough

Imagine:

```text
MongoDB starts
 ↓
API starts
```

MongoDB may technically have started but still be initializing.

Therefore:

```text
started ≠ ready
```

That's why health checks and retry logic matter.

---

# 32. Restart Policies

Production services should generally restart after unexpected failures.

Example:

```yaml
restart: unless-stopped
```

Now:

```text
API crashes
 ↓
Docker restarts it
```

This improves resilience.

---

# 33. Restart Policies

Common options include:

```text
no
always
on-failure
unless-stopped
```

For a production application:

```yaml
restart: unless-stopped
```

is often a reasonable starting point.

But restart policies don't fix application bugs.

If your app repeatedly crashes:

```text
Crash
 ↓
Restart
 ↓
Crash
 ↓
Restart
```

you still need observability and investigation.

---

# 34. Restart vs Health Recovery

A subtle point:

A health check reporting:

```text
unhealthy
```

does not automatically mean:

```text
restart container
```

in every Compose setup.

Health status and restart policy are related but distinct concepts.

You should understand:

```text
Process failure
    ↓
Restart policy

Health failure
    ↓
Monitoring/orchestration response
```

Don't assume one automatically fixes the other.

# 35. Production Compose Example

Let's build a basic architecture:

```yaml
services:

  api:
    image: ghcr.io/your-user/my-api:v1.0.0
    env_file:
      - .env
    restart: unless-stopped
    expose:
      - "5000"
    depends_on:
      mongo:
        condition: service_healthy

  mongo:
    image: mongo:8
    restart: unless-stopped
    volumes:
      - mongo_data:/data/db
    healthcheck:
      test:
        [
          "CMD",
          "mongosh",
          "--eval",
          "db.adminCommand('ping')"
        ]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  mongo_data:
```

Architecture:

```text
             Docker Network
                  │
          ┌───────┴───────┐
          ↓               ↓
        API            MongoDB
          │               │
          │               ↓
          │          mongo_data
          │
          ↓
       port 5000
```

Notice:

> API isn't publishing port 5000 to the public host.

For simple Compose applications, the default network is often enough.

Explicit networks become useful when you want to separate traffic.

For example:

```text

      │
    Nginx
      │

      │
```

# 52. Graceful Shutdown

Your Node.js application should handle termination signals properly.

Docker may send:

```text
SIGTERM
```

when stopping a container.

Your application should:

```text
Receive SIGTERM
      ↓
Stop accepting new requests
      ↓
Finish existing requests
      ↓
Close DB connections
      ↓
Exit
```

Example:

```javascript
process.on("SIGTERM", async () => {
  console.log("SIGTERM received");

  await mongoose.connection.close();

  process.exit(0);
});
```

The exact implementation depends on your application architecture.

This becomes very important for zero-downtime deployments.

---

# 53. Why Graceful Shutdown Matters

Without graceful shutdown:

```text
Deployment
   ↓
Container killed
   ↓
Active request interrupted
```

With graceful shutdown:

```text
Deployment
   ↓
SIGTERM
   ↓
Finish requests
   ↓
Close connections
   ↓
Exit
```

This reduces failed requests during deployments.

# 🧠 Interview Questions

### Q1. What is Docker Compose?

> A tool for defining and managing multi-container applications using a declarative YAML configuration.

### Q2. Why use Compose in production?

> It provides a repeatable way to define services, networks, volumes, environment variables, health checks, and restart behavior.

### Q3. How does one container communicate with another?

> Through the Docker network, usually using the Compose service name as the hostname.

### Q4. Why shouldn't the API use `localhost` to connect to MongoDB?

> Inside the API container, `localhost` refers to the API container itself, not the MongoDB container.

### Q5. What is a Docker volume?

> Persistent storage managed separately from the container lifecycle.

### Q6. Why are volumes important for MongoDB?

> Containers can be recreated, while database data must survive container replacement.

### Q7. What does `restart: unless-stopped` do?

> It tells Docker to automatically restart the container after many failure/restart scenarios unless it was intentionally stopped.

### Q8. What is a health check?

> A mechanism for determining whether a service is actually functioning rather than merely having a running process.

### Q9. What does `depends_on` do?

> It expresses service startup/dependency relationships. With supported health conditions, Compose can wait for a dependency's health status before starting a dependent service.

### Q10. Why shouldn't MongoDB normally expose port 27017 publicly?

> The application can access MongoDB through the private Docker network, so exposing it publicly unnecessarily increases the attack surface.

# 🔑 Lesson 12.11 Takeaways

Remember these **16 points**:

1. **Docker Compose manages multi-container applications.**
    
2. Compose configuration is declarative.
    
3. Services communicate using Docker networks.
    
4. The Compose service name can act as a hostname.
    
5. `localhost` inside a container means that container itself.
    
6. Don't hard-code container IP addresses.
    
7. Use `expose`/internal networking when a service doesn't need public access.
    
8. Keep databases off the public internet whenever possible.
    
9. Use Docker volumes for persistent database data.
    
10. Be extremely careful with `docker compose down -v`.
    
11. Use health checks to determine real service health.
    
12. `depends_on` helps with startup relationships but isn't a replacement for application retry logic.
    
13. Use restart policies for basic resilience.
    
14. Keep production secrets outside Git.
    
15. Keep the Docker image separate from environment-specific configuration.
    
16. Use **versioned immutable images** in production instead of blindly using `latest`.
