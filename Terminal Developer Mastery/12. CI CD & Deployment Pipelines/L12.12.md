# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.12 — Deploying with SSH ⭐⭐⭐⭐⭐

This lesson connects everything we've built so far.

We now have:

```text
Git
 ↓
GitHub Actions
 ↓
Tests
 ↓
Docker Build
 ↓
GHCR
 ↓
Docker Image
```

Now we want:

```text
GHCR
 ↓
Linux Production Server
 ↓
Docker Compose
 ↓
Application
```

And we want GitHub Actions to perform that deployment **automatically over SSH**.

---

# 1. What Are We Building?

Our target pipeline:

```text
                    Developer
                       │
                       ↓
                    git push
                       │
                       ↓
                 GitHub Repository
                       │
                       ↓
                 GitHub Actions
                       │
              ┌────────┴────────┐
              ↓                 ↓
           Lint/Test          Build
              └────────┬────────┘
                       ↓
                 Docker Image
                       ↓
                      GHCR
                       ↓
                  SSH Connection
                       ↓
                Linux Production
                       ↓
             docker compose pull
                       ↓
             docker compose up -d
                       ↓
                  Health Check
                       ↓
                   Production
```

This is a real CI/CD deployment flow.

---

# 2. Why SSH?

SSH gives us secure remote access to a Linux machine.

From your own computer:

```bash
ssh user@server
```

The same concept can be used by GitHub Actions:

```text
GitHub Actions
      ↓
SSH
      ↓
Linux Server
```

Then GitHub Actions can execute deployment commands remotely.

---

# 3. SSH Is Not the Deployment

This distinction is important.

SSH is simply the **secure communication channel**.

The actual deployment might be:

```text
SSH
 ↓
docker compose pull
 ↓
docker compose up -d
```

So:

```text
SSH = connection mechanism
Docker Compose = deployment mechanism
```

---

# 4. Why Not Copy the Entire Source Code?

A beginner deployment might do:

```text
GitHub Actions
 ↓
scp source code
 ↓
Server
 ↓
npm install
 ↓
npm build
```

But we're already building Docker images.

So a better architecture is:

```text
GitHub Actions
 ↓
Docker Image
 ↓
GHCR
 ↓
SSH
 ↓
Server
 ↓
docker compose pull
```

The production server doesn't need the source repository.

---

# 5. Production Server Responsibilities

Ideally, your server mainly needs:

```text
Docker
Docker Compose
Nginx
SSH
Application configuration
```

It doesn't need:

```text
Git
Node.js development environment
npm
Source repository
Build tools
```

The CI system performs the build.

---

# 6. The Deployment User

Don't use `root` for automated deployment if you can avoid it.

Create a dedicated user such as:

```text
deploy
```

Then:

```text
GitHub Actions
      ↓
SSH
      ↓
deploy user
      ↓
Docker Compose
```

This is safer than:

```text
GitHub Actions
      ↓
SSH
      ↓
root
```

---

# 7. Why a Dedicated User?

Suppose your CI credentials are compromised.

If the account is:

```text
root
```

the attacker potentially gets complete server control.

With:

```text
deploy
```

you can restrict what that account can do.

This follows:

> **Principle of least privilege.**

---

# 8. Create the Deployment User

On your Linux server:

```bash
sudo adduser deploy
```

Then create the SSH directory:

```bash
sudo mkdir -p /home/deploy/.ssh
```

Set ownership:

```bash
sudo chown -R deploy:deploy /home/deploy/.ssh
```

Set permissions:

```bash
sudo chmod 700 /home/deploy/.ssh
```

---

# 9. SSH Key Authentication

We want:

```text
GitHub Actions
     │
     │ Private Key
     ↓
SSH Server
     │
     │ Public Key
     ↓
authorized_keys
```

The private key stays with GitHub Actions.

The public key goes on the server.

---

# 10. Generate a Dedicated SSH Key

Do this from a secure machine, not by putting a private key into your repository.

Example:

```bash
ssh-keygen -t ed25519 -C "github-actions-deploy"
```

You'll get:

```text
private key
public key
```

Typically:

```text
~/.ssh/github-actions-deploy
~/.ssh/github-actions-deploy.pub
```

---

# 11. Private vs Public Key

Remember:

### Private key

```text
github-actions-deploy
```

Must remain secret.

### Public key

```text
github-actions-deploy.pub
```

Can be placed on the server.

Never reverse these.

---

# 12. Put the Public Key on the Server

Add the public key to:

```text
/home/deploy/.ssh/authorized_keys
```

For example:

```bash
sudo nano /home/deploy/.ssh/authorized_keys
```

Paste the public key:

```text
ssh-ed25519 AAAAC3... github-actions-deploy
```

Then:

```bash
sudo chown deploy:deploy /home/deploy/.ssh/authorized_keys
sudo chmod 600 /home/deploy/.ssh/authorized_keys
```

---

# 13. Test SSH Manually First

Before involving GitHub Actions, test:

```bash
ssh -i ~/.ssh/github-actions-deploy deploy@YOUR_SERVER
```

If this doesn't work manually:

> **Don't move to GitHub Actions yet.**

First make SSH authentication work correctly.

---

# 14. Common SSH Permissions

SSH is strict about permissions.

Typical:

```text
~/.ssh              700
authorized_keys     600
private key         600
```

Wrong permissions can cause authentication failures.

---

# 15. GitHub Secrets

Now we need to give GitHub Actions access to the private key.

Store:

```text
PRODUCTION_SSH_KEY
```

as a GitHub Secret.

Also potentially:

```text
PRODUCTION_HOST
PRODUCTION_USER
PRODUCTION_PORT
```

But remember:

> Only truly sensitive values belong in Secrets.

A hostname may not be secret depending on your setup.

---

# 16. Production Environment

Even better:

```text
GitHub
 └── Environments
      └── production
           ├── PRODUCTION_SSH_KEY
           ├── PRODUCTION_HOST
           └── PRODUCTION_USER
```

Then your deployment job targets:

```yaml
environment: production
```

This allows production-specific protection rules.

---

# 17. Why Environment Protection Matters

You can configure production so:

```text
CI
 ↓
Tests
 ↓
Build
 ↓
Production deployment
 ↓
Approval
 ↓
SSH
```

This prevents every workflow from automatically getting production access.

---

# 18. SSH Host Key Verification

This is a very important security concept.

When you connect to an SSH server, you should verify:

```text
"Am I really connecting to my server?"
```

SSH uses host keys for this purpose.

Your local machine stores known hosts in:

```text
~/.ssh/known_hosts
```

---

# 19. Why `StrictHostKeyChecking=no` Is Dangerous

You may see tutorials doing:

```bash
ssh -o StrictHostKeyChecking=no ...
```

This makes automation easier.

But it weakens host identity verification.

It can allow a man-in-the-middle attack to go unnoticed.

For production CI/CD:

> Prefer proper host-key verification.

---

# 20. `known_hosts`

You can add your production server's SSH host key to a known-hosts value.

For example, obtain it securely:

```bash
ssh-keyscan -H YOUR_SERVER
```

But don't blindly trust arbitrary output.

The fingerprint should be verified through a trusted channel.

Then store the resulting known-hosts data as a protected configuration/secret if appropriate.

---

# 21. SSH-Agent

GitHub Actions can use an SSH agent to load the private key.

Conceptually:

```text
GitHub Secret
     ↓
SSH Agent
     ↓
Private Key
     ↓
SSH Connection
```

The private key doesn't need to be written permanently into the repository.

---

# 22. Example SSH Setup

A common pattern is to use an SSH action or install/configure an SSH client.

Conceptually:

```yaml
- name: Configure SSH
  run: |
    mkdir -p ~/.ssh
    echo "${{ secrets.PRODUCTION_SSH_KEY }}" > ~/.ssh/deploy_key
    chmod 600 ~/.ssh/deploy_key
```

Then:

```bash
ssh -i ~/.ssh/deploy_key deploy@server
```

However, production workflows should also handle host-key verification correctly.

---

# 23. Better: Use a Deployment Action Carefully

There are GitHub Actions that can perform SSH commands.

For example, an SSH action may accept:

```text
host
username
key
script
```

Conceptually:

```yaml
- name: Deploy
  uses: some-ssh-action
  with:
    host: ${{ secrets.PRODUCTION_HOST }}
    username: ${{ secrets.PRODUCTION_USER }}
    key: ${{ secrets.PRODUCTION_SSH_KEY }}
    script: |
      cd /opt/myapp
      docker compose pull
      docker compose up -d
```

But don't blindly trust third-party Actions.

We'll discuss Action supply-chain security later.

---

# 24. Prefer Trusted Actions

GitHub Actions can execute arbitrary code.

So:

```yaml
uses: random-user/some-action@v1
```

should not be treated as harmless.

Before using an Action:

- Check its repository
    
- Check who maintains it
    
- Review permissions
    
- Pin versions appropriately
    
- Understand what it executes
    

This connects directly to your security module.

---

# 25. The Deployment Script

Instead of putting everything into GitHub Actions, create a deployment script on the server.

For example:

```text
/opt/myapp/
├── compose.yml
├── .env
└── deploy.sh
```

`deploy.sh`:

```bash
#!/usr/bin/env bash

set -e

cd /opt/myapp

docker compose pull
docker compose up -d

docker compose ps
```

Then:

```bash
chmod +x deploy.sh
```

---

# 26. Why Use a Deployment Script?

Your GitHub workflow becomes simple:

```text
SSH
 ↓
/opt/myapp/deploy.sh
```

Instead of:

```text
SSH
 ↓
cd ...
 ↓
pull...
 ↓
compose...
 ↓
health...
 ↓
cleanup...
 ↓
...
```

The deployment logic lives on the server.

---

# 27. But Should Deployment Logic Live on the Server?

There are two common approaches.

### Approach A — Server script

```text
GitHub
 ↓
SSH
 ↓
deploy.sh
```

### Approach B — CI-controlled commands

```text
GitHub
 ↓
SSH
 ↓
docker compose pull
 ↓
docker compose up
```

Both can work.

For your learning project, I'd start with a server-side deployment script because it's easier to test and reuse.

---

# 28. Deployment Script Should Fail Fast

Use:

```bash
set -e
```

This means a command returning an error causes the script to stop.

Without this:

```text
docker compose pull ❌
       ↓
docker compose up
       ↓
continue anyway
```

That's dangerous.

With:

```text
pull ❌
 ↓
STOP
```

Much safer.

---

# 29. More Robust Bash Settings

You may see:

```bash
set -Eeuo pipefail
```

This provides stricter error handling.

Conceptually:

```text
-e → fail on errors
-u → fail on unset variables
-o pipefail → detect pipeline failures
```

For deployment scripts, this can be useful.

---

# 30. Example Deployment Script

A more robust version:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

APP_DIR="/opt/myapp"

cd "$APP_DIR"

echo "Pulling latest image..."

docker compose pull

echo "Starting services..."

docker compose up -d

echo "Checking services..."

docker compose ps

echo "Deployment completed."
```

Simple, but much more professional.

---

# 31. Deployment by Image Tag

Now we need to tell the server **which image version to deploy**.

Suppose CI built:

```text
ghcr.io/rahul/my-api:a83f91c
```

Your Compose file should reference that version.

There are several approaches.

---

# 32. Approach 1 — Update Compose File

You could change:

```yaml
image: ghcr.io/rahul/my-api:a83f91c
```

to:

```yaml
image: ghcr.io/rahul/my-api:b7194e2
```

But then CI would need to modify server configuration.

Not ideal.

---

# 33. Approach 2 — Use an Environment Variable

Better:

```yaml
services:
  api:
    image: ghcr.io/rahul/my-api:${IMAGE_TAG}
```

Then:

```text
IMAGE_TAG=a83f91c
```

can be supplied through the environment.

Now deployment becomes:

```text
IMAGE_TAG=a83f91c
       ↓
Compose
       ↓
ghcr.io/rahul/my-api:a83f91c
```

This is much cleaner.

---

# 34. Production `.env`

Your server might have:

```text
IMAGE_TAG=a83f91c
NODE_ENV=production
DATABASE_URL=mongodb://mongo:27017/app
JWT_SECRET=...
```

Then Compose:

```yaml
services:
  api:
    image: ghcr.io/rahul/my-api:${IMAGE_TAG}
```

Now changing versions only requires changing:

```text
IMAGE_TAG
```

---

# 35. CI Updating the Image Tag

GitHub Actions can remotely execute:

```bash
sed -i 's/^IMAGE_TAG=.*/IMAGE_TAG=a83f91c/' .env
```

Then:

```bash
docker compose pull
docker compose up -d
```

But be careful with shell escaping and secrets.

For more robust deployments, you may use a dedicated deployment script that accepts the image tag.

---

# 36. Better Deployment Script With Tag

For example:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

APP_DIR="/opt/myapp"
IMAGE_TAG="${1:?Image tag required}"

cd "$APP_DIR"

sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=$IMAGE_TAG/" .env

docker compose pull
docker compose up -d
```

Then:

```bash
./deploy.sh a83f91c
```

The script knows exactly which image to deploy.

---

# 37. Even Better: Don't Mutate Configuration Blindly

For more advanced systems, you may avoid modifying `.env` directly.

For example:

```bash
IMAGE_TAG=a83f91c docker compose up -d
```

Compose can use environment variables supplied for that command.

This can reduce configuration mutation.

However, for a simple server deployment, keeping a clearly managed deployment state can also be perfectly reasonable.

---

# 38. Deployment State

A good deployment system should always know:

```text
Currently deployed:
a83f91c
```

This is important for:

- Rollbacks
    
- Debugging
    
- Auditing
    
- Incident response
    

Don't make production state impossible to discover.

---

# 39. Deployment Script With Health Check

Now let's improve our script.

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

APP_DIR="/opt/myapp"
IMAGE_TAG="${1:?Image tag required}"

cd "$APP_DIR"

echo "Deploying $IMAGE_TAG"

IMAGE_TAG="$IMAGE_TAG" docker compose pull

IMAGE_TAG="$IMAGE_TAG" docker compose up -d

echo "Waiting for application..."

sleep 5

curl --fail http://localhost/health

echo "Deployment successful."
```

If health check fails:

```text
curl ❌
 ↓
script exits non-zero
 ↓
CI knows deployment failed
```

This becomes important in the next lessons.

---

# 40. Health Check Location

If Nginx is public:

```text
curl https://example.com/health
```

might be better than:

```text
curl localhost:5000/health
```

because it verifies the whole path:

```text
Internet/Nginx
     ↓
API
     ↓
Application
```

However, internal checks can also be useful.

We'll build a proper verification strategy later.

---

# 41. `rsync` vs `scp`

Our pipeline might need to copy files.

Two common tools:

```text
scp
rsync
```

### `scp`

Simple file copying:

```bash
scp compose.yml deploy@server:/opt/myapp/
```

### `rsync`

More efficient synchronization:

```bash
rsync -avz deployment/ deploy@server:/opt/myapp/
```

---

# 42. Why `rsync` Is Powerful

Suppose you have:

```text
deployment/
├── compose.yml
├── deploy.sh
└── nginx/
    └── nginx.conf
```

`rsync` can synchronize only changed files.

Instead of copying everything:

```text
Changed nginx.conf
 ↓
Transfer only required changes
```

This can be faster and more efficient.

---

# 43. But We Don't Need to Copy the Application

Remember:

```text
Application source
```

already became:

```text
Docker image
```

So deployment only needs:

```text
Compose configuration
Nginx configuration
Deployment script
```

not:

```text
src/
node_modules/
package.json
```

This is a major architectural improvement.

---

# 44. `scp` Example

GitHub Actions could do:

```bash
scp \
  -i ~/.ssh/deploy_key \
  compose.yml \
  deploy@server:/opt/myapp/
```

Then:

```text
SSH
 ↓
compose.yml
 ↓
server
```

But if you're using a stable server configuration, you may not need to transfer the Compose file every deployment.

# 45. Configuration Versioning

Your infrastructure configuration should also be version controlled.

For example:

```text
repository/
├── backend/
├── frontend/
└── deployment/
    ├── compose.yml
    ├── nginx/

```

Then:

```text

 ↓

```

is versioned alongside your application.

But:

```text
.env
```

stays outside Git if it contains secrets.

# 49. Don't Hard-Code the Server

Avoid:

```yaml
run: ssh deploy@123.45.67.89 ...
```

Instead use:

```yaml
run: ssh ${{ secrets.PRODUCTION_USER }}@${{ secrets.PRODUCTION_HOST }} ...
```

This keeps deployment configuration outside the workflow code.

---

# 50. Don't Hard-Code the SSH Key

Never:

```yaml

  -----BEGIN OPENSSH PRIVATE KEY-----
  ...
```

Instead:

```yaml
key: ${{ secrets.PRODUCTION_SSH_KEY }}
```

The secret stays in GitHub's protected storage.

# 55. Deployment Verification

Never assume:

```text
docker compose up -d
```

means deployment succeeded.

Verify:

```bash
docker compose ps
```

Then:

```bash
curl --fail http://localhost/health
```

Potentially:

```bash

```

Then:

```text
Deployment
 ↓
Verification
 ↓
Success/Failure
```

# 56. Why `curl --fail`?

Without:

```bash
curl --fail
```

a server returning:

```text
500 Internal Server Error
```

might not cause the shell script to fail as expected.

With:

```bash
curl --fail
```

HTTP errors produce a non-zero exit status.

Then:

```text
health check fails
 ↓
deploy.sh fails
 ↓
GitHub Actions fails
```

Exactly what we want.

# 62. Don't Give the Deployment User Unlimited Docker Power Without Thinking

There's an important Linux/Docker security detail.

Users who can control the Docker daemon often effectively have very high privileges on the host.

So:

```text
deploy user
    ↓
Docker access
```

must be treated carefully.

Adding a user to:

```text
docker
```

group can effectively provide root-equivalent capabilities on many Linux systems.

Therefore:

> Don't assume "not root" automatically means "low privilege."

This is a very important production security lesson.

# 🧠 Interview Questions

### Q1. Why use SSH in CI/CD?

> SSH provides a secure channel through which CI can execute deployment operations on a remote Linux server.

### Q2. Why use a dedicated deployment user?

> To reduce the privileges available to automated deployment processes and limit the impact of compromised credentials.

### Q3. Why shouldn't CI use root?

> A compromised CI credential with root access could give an attacker complete control over the server.

### Q4. What is an SSH key pair?

> A private key kept secret by the client and a public key placed on the server for authentication.

### Q5. Where should the private key be stored?

> In protected secret storage such as GitHub Actions Secrets, never in the repository.

### Q6. What is `known_hosts`?

> It stores trusted SSH server host keys so the client can verify the identity of the remote server.

### Q7. Why is `StrictHostKeyChecking=no` dangerous?

> It disables important server identity verification and can make man-in-the-middle attacks easier.

### Q8. Why use a deployment script?

> It centralizes deployment logic, makes manual testing easier, and keeps the CI workflow simpler.

### Q9. Why deploy a Docker image instead of source code?

> The image is already built and tested, making the production environment more consistent and eliminating the need to build on the production server.

### Q10. Why use `curl --fail` after deployment?

> It makes HTTP failures return a non-zero exit status so CI can detect an unsuccessful deployment.

# 🔑 Lesson 12.12 Takeaways

Remember these **16 points**:

1. **SSH is the secure communication channel, not the deployment itself.**
    
2. Use SSH keys rather than passwords for automated deployment.
    
3. Create a dedicated deployment user.
    
4. Avoid automated SSH access as `root`.
    
5. Store private keys in GitHub Secrets.
    
6. Put only the public key on the server.
    
7. Verify SSH host keys properly.
    
8. Don't blindly use `StrictHostKeyChecking=no`.
    
9. Keep application source code out of the production server when using container images.
    
10. Pull versioned images from GHCR.
    
11. Use an image tag such as the Git SHA to identify the exact deployment.
    
12. Keep production secrets outside Git.
    
13. Use a deployment script with strict error handling.
    
14. Verify deployment with health checks.
    
15. Make manual deployment work before automating it.
    
16. Prepare rollback by keeping previous image versions available.
