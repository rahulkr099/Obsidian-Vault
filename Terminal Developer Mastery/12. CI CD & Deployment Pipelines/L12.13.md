# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.13 — Zero-Downtime Deployment ⭐⭐⭐⭐⭐

In Lesson 12.12, we built:

```text
GitHub Actions
      ↓
GHCR
      ↓
SSH
      ↓
Linux Server
      ↓
Docker Compose
      ↓
Application
```

But there is a problem.

Suppose production is running:

```text
Version A
```

and we deploy:

```text
Version B
```

If we simply stop A and start B:

```text
Version A
   ↓
STOP ❌
   ↓
Version B
   ↓
START
```

there can be a period where **no application is available**.

Users may see:

```text
502 Bad Gateway
503 Service Unavailable
Connection refused
Timeout
```

Today we'll learn how professional systems reduce or eliminate this downtime.

---

# 1. What Is Zero-Downtime Deployment?

A zero-downtime deployment aims to update an application **without making the service unavailable to users**.

Instead of:

```text
A → STOP → B
```

we want something closer to:

```text
A
↓
Start B
↓
B becomes healthy
↓
Send traffic to B
↓
Stop A
```

At every important point, at least one healthy version is available.

---

# 2. Why Downtime Happens

A naive deployment might execute:

```bash
docker compose down
docker compose pull
docker compose up -d
```

Timeline:

```text
10:00:00  Application running
10:00:05  Container stopped
10:00:06  New image pulled
10:00:20  New container starts
10:00:25  Application ready
```

Users experience:

```text
10:00:05 → 10:00:25
      downtime
```

That's unacceptable for many production applications.

---

# 3. The Core Idea

The fundamental idea is:

> **Never remove the currently healthy version until the replacement is ready.**

Think:

```text
Current
   ↓
A 🟢

New
   ↓
B 🟡
```

Wait:

```text
B 🟡
 ↓
health check
 ↓
B 🟢
```

Then:

```text
Traffic
   ↓
B 🟢
```

Only after that:

```text
A 🟢
 ↓
Stop
```

---

# 4. Deployment Strategies

There are several important strategies:

1. Rolling deployment
    
2. Blue-Green deployment
    
3. Canary deployment
    

We'll also discuss:

4. Recreate deployment
    

because understanding the difference is important.

---

# 5. Recreate Deployment

This is the simplest approach:

```text
A
↓
STOP
↓
B
↓
START
```

There is downtime.

Example:

```bash
docker compose up -d
```

depending on what changed and how the stack is configured.

This is acceptable for:

- Development
    
- Small internal applications
    
- Applications where downtime is acceptable
    

But it isn't true zero-downtime deployment.

---

# 6. Rolling Deployment

A rolling deployment gradually replaces old instances with new ones.

Suppose we have:

```text
A1
A2
A3
```

We want:

```text
B1
B2
B3
```

Instead of replacing everything at once:

```text
A1 A2 A3
 ↓
B1 A2 A3
 ↓
B1 B2 A3
 ↓
B1 B2 B3
```

Traffic remains available during the transition.

---

# 7. Rolling Deployment Architecture

```text
                    Load Balancer
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
        API A          API A          API A
          │              │              │
          └──────────────┴──────────────┘
```

Replace one:

```text
                    Load Balancer
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
        API B          API A          API A
```

Then:

```text
                    Load Balancer
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
        API B          API B          API A
```

Finally:

```text
                    Load Balancer
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
        API B          API B          API B
```

---

# 8. Does Docker Compose Automatically Give You Rolling Deployment?

No.

This is important.

Docker Compose is excellent for:

- Multi-container applications
    
- Local environments
    
- Small production deployments
    
- Simple server orchestration
    

But it isn't a full cluster orchestrator.

For sophisticated rolling deployments across many machines, tools such as:

- Kubernetes
    
- Docker Swarm
    
- Nomad
    
- Cloud container platforms
    

provide more advanced orchestration.

For our single-server Linux deployment, we'll use simpler patterns.

---

# 9. Blue-Green Deployment

Blue-Green is extremely useful for your learning project.

We maintain two environments:

```text
BLUE
GREEN
```

Suppose:

```text
BLUE = current production
GREEN = new version
```

Initially:

```text
Internet
   ↓
Nginx
   ↓
BLUE
```

---

# 10. Deploying Green

Start the new version:

```text
Internet
   ↓
Nginx
   ↓
BLUE 🟢

GREEN 🟡
```

GREEN is not receiving production traffic yet.

We can test it.

```text
GREEN
 ↓
Health Check
 ↓
PASS
```

Now:

```text
GREEN 🟢
```

---

# 11. Traffic Switching

Once GREEN is healthy:

```text
Before:

Nginx
  ↓
BLUE
```

Switch:

```text
After:

Nginx
  ↓
GREEN
```

Then:

```text
BLUE
 ↓
Keep temporarily
```

This is powerful because rollback becomes:

```text
Nginx
 ↓
BLUE
```

again.

---

# 12. Blue-Green Architecture

```text
                         Internet
                            │
                            ↓
                          Nginx
                            │
                    ┌───────┴───────┐
                    ↓               ↓
                 BLUE            GREEN
                  🟢                🟢
               Current            New
```

Only one receives production traffic at a time.

---

# 13. Why Blue-Green Is Easy to Understand

You can think of it as two rooms:

```text
Room A = current application
Room B = new application
```

Users are in Room A.

You prepare Room B completely.

When B is ready:

```text
Users
 ↓
Room B
```

If B breaks:

```text
Users
 ↓
Room A
```

This is why Blue-Green is excellent for rollback.

---

# 14. The Cost of Blue-Green

You need resources for both versions.

For example:

```text
BLUE
Node.js
Memory: 500 MB

GREEN
Node.js
Memory: 500 MB
```

You might temporarily need:

```text
~1 GB+
```

instead of:

```text
~500 MB
```

So:

> Zero-downtime often requires additional infrastructure resources.

---

# 15. Canary Deployment

Canary deployment takes a different approach.

Instead of sending:

```text
100%
```

of traffic to the new version immediately:

```text
5%
```

goes to the new version.

Example:

```text
Users
 │
 ├── 95% → Version A
 │
 └── 5%  → Version B
```

Monitor:

- Errors
    
- Latency
    
- CPU
    
- Memory
    
- Application metrics
    
- User behavior
    

If everything looks good:

```text
5%
 ↓
25%
 ↓
50%
 ↓
100%
```

---

# 16. Canary Rollback

Suppose:

```text
95% → A
5%  → B
```

and B starts producing:

```text
500 errors
```

You simply stop sending traffic to B:

```text
100% → A
```

This limits the impact.

---

# 17. Canary vs Blue-Green

### Blue-Green

```text
100% → A

switch

100% → B
```

### Canary

```text
95% → A
5%  → B

then:

75% → A
25% → B

then:

50% → A
50% → B
```

Canary is more gradual.

---

# 18. When Should You Use Each?

|Strategy|Good For|
|---|---|
|Recreate|Simple/dev deployments|
|Rolling|Multiple application instances|
|Blue-Green|Fast switching + easy rollback|
|Canary|Risk-sensitive gradual releases|

For your current Linux + Docker Compose learning environment:

> **Blue-Green is the easiest advanced strategy to understand and implement.**

---

# 19. Health Checks Are Critical

Zero-downtime deployment depends heavily on:

```text
Health checks
```

Suppose:

```text
New API container
       ↓
Running
```

Does that mean:

```text
Healthy?
```

No.

The process may be running while:

```text
MongoDB connection failed
Environment variable missing
Application startup incomplete
Critical dependency unavailable
```

---

# 20. Running ≠ Ready

This distinction is essential:

```text
Container running
        ≠
Application ready
```

You should have:

```text
Container starts
       ↓
Application initializes
       ↓
Dependencies connect
       ↓
Readiness check
       ↓
Ready
```

Only then should traffic be sent to it.

---

# 21. Health Endpoint

Your Node.js application should have something like:

```javascript
app.get("/health", (req, res) => {
  res.status(200).json({
    status: "ok"
  });
});
```

For deeper health checking, you might verify dependencies too.

For example:

```text
GET /health
```

could mean:

```text
API process = OK
```

while:

```text
GET /ready
```

could mean:

```text
API
+
MongoDB
+
required dependencies
=
READY
```

---

# 22. Liveness vs Readiness

These terms are common in modern orchestration.

### Liveness

> Is the application alive?

### Readiness

> Can the application safely receive traffic?

Example:

```text
/health
```

might represent liveness.

```text
/ready
```

might represent readiness.

---

# 23. Why Readiness Matters

Imagine a new API starts:

```text
B starts
 ↓
Node process running
 ↓
MongoDB connection still initializing
```

If Nginx immediately sends requests:

```text
Nginx
 ↓
B
 ↓
500 errors
```

Instead:

```text
B starts
 ↓
Not ready
 ↓
Wait
 ↓
MongoDB connected
 ↓
Ready
 ↓
Traffic
```

Much safer.

---

# 24. Graceful Shutdown

We discussed this in Lesson 12.12.

When retiring Version A:

```text
SIGTERM
 ↓
Stop accepting new work
 ↓
Finish active requests
 ↓
Close database connections
 ↓
Exit
```

This helps prevent dropped requests.

---

# 25. Deployment Timeline

A safe deployment might look like:

```text
T0
A = healthy
B = doesn't exist

T1
Start B

T2
B = starting

T3
B = ready

T4
Nginx → B

T5
A drains existing connections

T6
A stops

T7
B = production
```

At no point do we intentionally have:

```text
No healthy version
```

# 26. Nginx as Traffic Switch

This is where Nginx becomes very useful.

Imagine:

```text
Nginx
   ↓
127.0.0.1:5001
```

and:

```text
BLUE → 5001
```

GREEN:

```text
GREEN → 5002
```

Initially:

```text
Nginx
 ↓
5001
 ↓
BLUE
```

After deployment:

```text
Nginx
 ↓
5002
 ↓
GREEN
```

---

# 27. Example Nginx Configuration

Initial:

```nginx
upstream backend {
    server 127.0.0.1:5001;
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://backend;
    }
}
```

Now:

```text
Nginx
 ↓
5001
 ↓
BLUE
```

---

# 28. Switch to Green

Change:

```nginx
upstream backend {
    server 127.0.0.1:5002;
}
```

Then test configuration:

```bash
sudo nginx -t
```

If valid:

```bash
sudo systemctl reload nginx
```

Now:

```text
Nginx
 ↓
5002
 ↓
GREEN
```

Notice:

> `reload` is preferred over restarting Nginx for a configuration change because it can gracefully apply the new configuration.

---

# 29. Why `nginx -t`?

Never blindly reload a new Nginx configuration.

First:

```bash
sudo nginx -t
```

If:

```text
syntax is ok
test is successful
```

then:

```bash
sudo systemctl reload nginx
```

If the configuration is invalid:

```text
nginx -t ❌
```

don't reload.

---

# 30. Blue-Green With Docker

You could run:

```text
BLUE
port 5001

GREEN
port 5002
```

For example:

```yaml
services:

  blue:
    image: ghcr.io/rahul/my-api:a83f91c
    ports:
      - "5001:5000"

  green:
    image: ghcr.io/rahul/my-api:b7194e2
    ports:
      - "5002:5000"
```

Then Nginx chooses which one receives traffic.

---

# 31. Why Different Host Ports?

Both containers listen internally on:

```text
5000
```

but the host exposes:

```text
BLUE  → 5001
GREEN → 5002
```

So:

```text
Host
 ├── 5001 → BLUE:5000
 └── 5002 → GREEN:5000
```

Nginx can switch between them.

---

# 32. A Simple Blue-Green Deployment

Suppose:

```text
Current:
BLUE = v1.0.0
```

Deploy:

```text
GREEN = v1.1.0
```

Steps:

```text
1. Pull v1.1.0
2. Start GREEN
3. Wait for GREEN readiness
4. Test GREEN
5. Update Nginx
6. nginx -t
7. Reload Nginx
8. Monitor
9. Keep BLUE temporarily
```

That's a safe deployment.

---

# 33. What Happens If Green Fails?

Suppose:

```text
GREEN
 ↓
health check ❌
```

Then:

```text
Nginx
 ↓
BLUE
```

remains unchanged.

Users don't experience a broken deployment.

This is one of the strongest advantages of Blue-Green.

---

# 34. What Happens If Green Fails After Switching?

This is more interesting.

Suppose:

```text
Nginx
 ↓
GREEN
```

Then errors appear.

Rollback:

```text
Nginx
 ↓
BLUE
```

Run:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Then:

```text
GREEN ❌
BLUE 🟢
```

This can be very fast.

---

# 35. Rollback Is a First-Class Operation

A professional deployment system should not think:

```text
deploy
```

only.

It should think:

```text
deploy
rollback
verify
```

A useful mental model:

```text
Deploy = forward operation
Rollback = equally important recovery operation
```

---

# 36. Database Compatibility Problem

Zero-downtime deployment isn't only about containers.

Suppose Version A expects:

```text
users.name
```

Version B expects:

```text
users.full_name
```

You deploy B while the database still has:

```text
name
```

B might fail.

This is why database migrations must be designed for compatibility.

We'll study this deeply in Lesson 12.16.

---

# 37. Backward-Compatible Database Changes

A safer migration pattern:

```text
Step 1
Add new field

Step 2
Deploy application that can use both

Step 3
Migrate data

Step 4
Switch fully to new field

Step 5
Remove old field later
```

Instead of:

```text
Delete old field
 ↓
Deploy new application
```

This is called an **expand-and-contract** style migration.

---

# 38. Connection Draining

When switching from:

```text
BLUE
```

to:

```text
GREEN
```

existing requests may still be running.

You don't want to instantly kill BLUE.

Instead:

```text
BLUE
 ↓
Stop receiving new traffic
 ↓
Existing requests finish
 ↓
Shutdown
```

This is:

> **Connection/request draining**

---

# 39. Why Draining Matters

Suppose a request takes:

```text
20 seconds
```

You switch traffic at:

```text
T = 0
```

The request is still running on BLUE.

If you immediately kill BLUE:

```text
Request
 ↓
Connection terminated ❌
```

With graceful draining:

```text
Request
 ↓
Finish
 ↓
Response
 ↓
BLUE exits
```

Much better.

---

# 40. Canary Deployment in More Detail

Suppose:

```text
100 users
```

You deploy:

```text
B
```

but only send:

```text
5 users → B
95 users → A
```

Monitor:

```text
Error rate
Latency
CPU
Memory
Logs
Business metrics
```

If good:

```text
25 → B
75 → A
```

Then:

```text
50 → B
50 → A
```

Then:

```text
100 → B
```

# 41. Canary Requires Traffic Control

To perform proper canary releases, you need a mechanism that can control traffic distribution.

Examples include:

- Nginx
    
- Load balancers
    
- Kubernetes
    
- Cloud load balancers
    
- Service meshes
    

For a simple single-server setup, Nginx can provide basic traffic routing.

---

# 42. Weighted Nginx Routing

Conceptually:

```nginx
upstream backend {
    server blue:5000 weight=95;
    server green:5000 weight=5;
}
```

This conceptually gives:

```text
95% → BLUE
5%  → GREEN
```

However, real production traffic behavior isn't always perfectly proportional, and health/failure behavior must also be considered.

---

# 43. Blue-Green vs Canary

Let's compare:

||Blue-Green|Canary|
|---|---|---|
|New version|100% ready before switch|Small traffic first|
|Traffic|Switches|Gradually shifts|
|Rollback|Very fast|Usually gradual/reverse|
|Resource usage|Higher temporarily|Can be lower|
|Complexity|Moderate|Higher|
|Risk|Moderate|Lower if well monitored|

---

# 44. Zero-Downtime Doesn't Mean Zero Risk

This is a very important interview concept.

A deployment can have:

```text
0 seconds downtime
```

and still be:

```text
❌ broken
```

For example:

```text
Application responds 200
but
payments fail
```

Therefore zero-downtime must be combined with:

- Health checks
    
- Monitoring
    
- Logging
    
- Metrics
    
- Smoke tests
    
- Rollback
    

---

# 45. Smoke Tests

After deploying B:

```bash
curl --fail https://example.com/health
```

Then perhaps:

```bash
curl --fail https://example.com/api/health
```

You can also test a safe read-only endpoint.

For example:

```text
GET /api/status
```

Smoke tests answer:

> "Does the application appear to work after deployment?"

A mature deployment can verify:

### Layer 1 — Container

```text
Running?
```

### Layer 2 — Health

```text
Healthy?
```

### Layer 3 — HTTP

```text
200 response?
```

### Layer 4 — Application

```text

```

### Layer 5 — Monitoring

```

```

alone.

# 47. Automatic Rollback

A mature pipeline might do:

```text
Deploy B
   ↓
Health Check
   ↓
PASS?
 ┌─┴─┐
YES  NO
 ↓    ↓
Keep  Rollback A
```

Even better:

```text
Deploy B
 ↓
Health check
 ↓
Smoke tests
 ↓
Monitor error rate
 ↓
Decision
```

This is the foundation of automated deployment safety.

# 48. Simple Deployment State Machine

Think of deployment as states:

```text
PREPARE
   ↓
START_NEW
   ↓
WAIT_FOR_READY
   ↓
VERIFY
   ↓
SWITCH_TRAFFIC
   ↓
MONITOR
   ↓
SUCCESS
```

Failure:

```text
ANY STATE
   ↓
FAILURE
   ↓
ROLLBACK
   ↓
VERIFY_OLD
```

This is a very useful system-design way to think about deployments.

---

# 49. Deployment Lock

Imagine two deployments start simultaneously:

```text
Deployment A
     ↓
Production

Deployment B
     ↓
Production
```

Now they can interfere with each other.

You want:

```text
Deployment A
     ↓
LOCK
     ↓
Deploy
     ↓
UNLOCK
```

GitHub Actions supports concurrency controls that can prevent overlapping deployments.

Conceptually:

```yaml
concurrency:
  group: production
  cancel-in-progress: false
```

This prevents multiple production deployments from running simultaneously.

---

# 50. Why Deployment Concurrency Matters

Without a lock:

```text
Deploy A → v1.2
Deploy B → v1.3
```

could produce:

```text
A starts
B starts
A finishes
B finishes
```

or:

```text
B starts
A modifies config
B pulls image
```

Result:

```text
Unknown production state
```

Always think:

> **One controlled production deployment at a time.**

---

# 51. Docker Compose Limitation

With a simple Compose deployment:

```text
BLUE
GREEN
```

you can implement basic Blue-Green manually.

But if you need:

```text
100 application instances
10 servers
automatic rescheduling
service discovery
advanced rolling updates
```

Compose isn't the ideal tool.

That's where:

```text
Kubernetes
```

and cloud orchestration platforms become useful.

But don't jump to Kubernetes yet.

Understanding the underlying mechanics first is much more valuable.

# 52. Practical Blue-Green Example

Suppose:

```text
BLUE = v1.0.0
GREEN = v1.1.0
```

Docker:

```text
blue  → localhost:5001
green → localhost:5002
```

Nginx:

```text
backend → 5001
```

Deployment:

```text
1. Pull v1.1.0
2. Start green
3. Check localhost:5002/health
4. Run smoke tests
5. nginx -t
6. Switch backend → 5002
7. Reload Nginx
8. Verify public endpoint
9. Keep blue alive temporarily
```

If everything is good:

```text
Remove blue later
```

If bad:

```text
Switch Nginx → 5001
Reload
```

---

# 53. Why Keep Blue Temporarily?

Suppose:

```text
GREEN
```

looks healthy initially.

After 10 minutes:

```text
Database errors
```

If BLUE still exists:

```text
Rollback:
GREEN → BLUE
```

If you deleted BLUE immediately:

```text
Rollback
 ↓
Rebuild/redeploy old version
```

which takes longer.

Therefore:

> Keep the previous version around until you're confident in the new deployment.

---

# 54. Deployment Window

You can define a rollback retention period:

```text
New deployment
 ↓
Keep old version for 30 minutes
 ↓
Monitor
 ↓
Delete old version
```

For critical applications:

```text
hours
```

or longer may be appropriate.

The exact period depends on:

- Risk
    
- Traffic
    
- Release frequency
    
- Storage
    
- Business requirements
    

---

# 55. Graceful Nginx Reload

When changing Nginx configuration:

```bash
sudo nginx -t
```

then:

```bash
sudo systemctl reload nginx
```

not:

```bash
sudo systemctl stop nginx
sudo systemctl start nginx
```

A reload allows Nginx to gracefully apply configuration changes.

```text

                       ↓
                     Nginx
                       │
                 ┌─────┴─────┐
                 ↓           ↓
              BLUE          GREEN
              v1.0          v1.1

                              │

                              │

```

This is the foundation of zero-downtime deployment.

# 59. Common Mistakes

### Mistake 1

Stopping old version before starting new version.

```text
A ❌
B 🟡
```

Result:

```text
Downtime
```

---

### Mistake 2

Checking only:

```bash
docker ps
```

A container can be running while the application is broken.

# 60. Interview Questions

### Q1. What is zero-downtime deployment?

> A deployment strategy designed to keep a healthy version of the application serving users while a new version is prepared and activated.

### Q2. What is a rolling deployment?

> Gradually replacing old application instances with new instances instead of replacing everything at once.

### Q3. What is Blue-Green deployment?

> Maintaining two application environments, switching traffic from the current environment to a fully tested new environment, and retaining the old one for quick rollback.

### Q4. What is Canary deployment?

> Gradually sending a small percentage of traffic to a new version and increasing it after monitoring confirms that the new version is healthy.

### Q5. What is readiness?

> Whether an application is ready to receive production traffic.

### Q6. Why is `running` not the same as `healthy`?

> A process can be running while dependencies are unavailable or the application is unable to serve requests correctly.

### Q7. Why is graceful shutdown important?

> It allows active requests to finish and resources such as database connections to close cleanly before the old instance exits.

### Q8. Why keep the old version during Blue-Green deployment?

> It allows fast rollback if problems appear after switching traffic.

### Q9. Why use `nginx -t` before reload?

> To validate the configuration and avoid replacing a working configuration with an invalid one.

### Q10. What is the biggest difference between Blue-Green and Canary?

> Blue-Green generally switches traffic between two complete environments, while Canary gradually exposes the new version to increasing portions of traffic.

# 🔑 Lesson 12.13 Takeaways

Remember these **18 points**:

1. **Zero-downtime deployment keeps a healthy version available during releases.**
    
2. Never stop the current application before the replacement is ready.
    
3. `running` does not mean `healthy`.
    
4. Health checks are critical.
    
5. Readiness determines whether an application should receive traffic.
    
6. Graceful shutdown prevents unnecessary dropped requests.
    
7. Rolling deployment replaces instances gradually.
    
8. Blue-Green maintains two environments.
    
9. Canary gradually shifts traffic.
    
10. Blue-Green gives very fast rollback.
    
11. Canary reduces the blast radius of a new release.
    
12. Nginx can act as a traffic switch on a single Linux server.
    
13. Always validate Nginx with `nginx -t`.
    
14. Use `systemctl reload nginx` for graceful configuration changes.
    
15. Keep the previous version available for rollback.
    
16. Database migrations must be compatible with old and new application versions.
    
17. Prevent simultaneous production deployments with deployment concurrency controls.
    
18. **Zero downtime is not enough — you also need health checks, smoke tests, monitoring, and rollback.**
