# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.14 — Nginx in Production ⭐⭐⭐⭐⭐

In Lesson 12.13, we learned how to deploy a new application version without intentionally creating downtime.

Now we're going to connect **Nginx** to that deployment architecture.

For your MERN applications, Nginx can become the **front door of the production system**:

```text
                         Internet
                            │
                         HTTPS :443
                            ↓
                         Nginx
                    ┌───────┴───────┐
                    ↓               ↓
                React App          API
                                    ↓
                                 MongoDB
```

Nginx handles things such as:

- HTTPS
    
- Reverse proxying
    
- React static files
    
- API routing
    
- Load balancing
    
- WebSockets
    
- Security headers
    
- Compression
    
- Configuration reloads
    
- Traffic switching during deployments
    

---

# 1. What Is Nginx?

Nginx is a high-performance web server and reverse proxy.

It can work as:

```text
Web Server
Reverse Proxy
Load Balancer
TLS/HTTPS Endpoint
Static File Server
Gateway
```

For a MERN application, one of its most useful roles is:

> **Reverse proxy between the internet and your backend containers.**

---

# 2. Why Do We Need Nginx?

Suppose your Node.js backend runs on:

```text
localhost:5000
```

You could expose:

```text
http://your-server:5000
```

directly.

But production users should normally access:

```text
https://example.com
```

rather than:

```text
http://example.com:5000
```

Nginx sits in front:

```text
Browser
   ↓
HTTPS
   ↓
Nginx :443
   ↓
Node.js :5000
```

---

# 3. Nginx as a Reverse Proxy

A reverse proxy receives requests on behalf of your application.

Example:

```text
Client
  ↓
https://example.com/api/users
  ↓
Nginx
  ↓
http://api:5000/api/users
```

The client doesn't directly communicate with Node.js.

---

# 4. Why This Architecture Is Better

Instead of:

```text
Internet
   ↓
Node.js
```

we use:

```text
Internet
   ↓
Nginx
   ↓
Node.js
```

Nginx can handle:

- TLS
    
- Request routing
    
- Connection handling
    
- Static files
    
- Rate limiting
    
- Load balancing
    
- Security headers
    

while Node.js focuses on:

```text
Business logic
API
Database interaction
Authentication
```

---

# 5. Production Architecture

For your MERN stack:

```text
                         Internet
                            │
                            ↓
                         Firewall
                            │
                            ↓
                       Nginx :443
                      /           \
                     ↓             ↓
                React files       API
                                    │
                                    ↓
                                MongoDB
```

Only the necessary ports should be exposed publicly.

Typically:

```text
80  → HTTP
443 → HTTPS
```

Your backend might remain internal.

---

# 6. Public vs Internal Ports

Suppose:

```text
Nginx
  ↓
API container :5000
```

You don't necessarily need:

```text
Internet → :5000
```

Instead:

```text
Internet
   ↓
:443
   ↓
Nginx
   ↓
Docker network
   ↓
API:5000
```

This is a better security boundary.

---

# 7. Basic Reverse Proxy

A basic Nginx configuration:

```nginx
server {
    listen 80;

    server_name example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:5000;
    }
}
```

Now:

```text
GET /api/users
```

goes approximately:

```text
Browser
 ↓
Nginx
 ↓
127.0.0.1:5000
 ↓
Express
```

---

# 8. Docker + Nginx

If Nginx is also running inside Docker Compose, don't use:

```nginx
proxy_pass http://127.0.0.1:5000;
```

for another container.

Why?

Because inside the Nginx container:

```text
127.0.0.1
```

means:

> The Nginx container itself.

Instead use the Compose service name:

```nginx
proxy_pass http://api:5000;
```

Architecture:

```text
Nginx container
      ↓
Docker DNS
      ↓
api
      ↓
API container :5000
```

This is exactly the same Docker networking concept we learned in Lesson 12.11.

Now:

```text

   ↓
Nginx :80/:443
   ↓
private Docker network
   ↓
API :5000
```

# 10. Nginx Configuration

Example:

```nginx
server {
    listen 80;

    server_name example.com;

    location /api/ {
        proxy_pass http://api:5000;
    }
}
```

The important part:

```nginx
proxy_pass http://api:5000;
```

Here:

```text
api
```

is the Docker Compose service name.

---

# 11. Forwarded Headers

Your backend should know information about the original client request.

Nginx can pass headers:

```nginx
location /api/ {
    proxy_pass http://api:5000;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

These are very useful.

---

# 12. `Host`

```nginx
proxy_set_header Host $host;
```

Preserves the original hostname.

For example:

```text
example.com
```

rather than exposing an internal upstream hostname.

---

# 13. `X-Real-IP`

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

Passes the client's IP address to the backend.

Your Express application can use this information when configured correctly for a reverse proxy.

---

# 14. `X-Forwarded-For`

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

This is commonly used to preserve the chain of client/proxy IPs.

It becomes particularly important when multiple proxies exist:

```text
Client
 ↓
CDN
 ↓
Load Balancer
 ↓
Nginx
 ↓
Node.js
```

---

# 15. `X-Forwarded-Proto`

```nginx
proxy_set_header X-Forwarded-Proto $scheme;
```

This tells the backend whether the original request was:

```text
http
```

or:

```text
https
```

This matters for:

- Secure cookies
    
- Redirect logic
    
- URL generation
    
- Security decisions
    

---

# 16. Express Trust Proxy

When Express is behind Nginx, you may need:

```javascript
app.set("trust proxy", 1);
```

depending on your proxy architecture.

Why?

Because Express otherwise may not correctly interpret forwarded client/protocol information.

This is especially important when using:

```javascript
req.ip
```

or secure cookies.

Don't blindly trust arbitrary `X-Forwarded-*` headers from direct clients; configure your proxy trust correctly.

---

# 17. HTTPS

Production applications should normally use:

```text
https://
```

instead of:

```text
http://
```

HTTPS provides:

```text
Encryption
Authentication
Integrity
```

Architecture:

```text
Browser
   │
   │ HTTPS
   ↓
Nginx
   │
   │ HTTP/internal TLS as appropriate
   ↓
Node.js
```

The public TLS connection can terminate at Nginx.

---

# 18. TLS Termination

This is called:

> **TLS termination**

Nginx handles:

```text
HTTPS
  ↓
Decrypt
  ↓
HTTP/internal connection
  ↓
Node.js
```

Your Node.js application doesn't necessarily need to manage public TLS directly.

This simplifies application deployment.

# 19. Typical Production Ports

A common server setup:

```text
22  → SSH
80  → HTTP
443 → HTTPS
```

Firewall:

```text
Internet
   │
   ├── 80
   └── 443
```

SSH should ideally be restricted as much as practical.

Your API port:

```text
5000
```

doesn't need to be publicly exposed.

# 20. HTTP → HTTPS Redirect

A common setup is:

```nginx
server {
    listen 80;

    server_name example.com www.example.com;

    return 301 https://$host$request_uri;
}
```

Then:

```text
http://example.com
       ↓
301 Redirect
       ↓
https://example.com
```

# 21. HTTPS Server

Conceptually:

```nginx
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    location /api/ {
        proxy_pass http://api:5000;
    }
}
```

In real deployments, certificate management should be automated.

---

# 22. Let's Encrypt

A common free certificate authority is:

> **Let's Encrypt**

You can use an ACME client such as Certbot or another ACME-compatible tool.

The goal is:

```text
Domain
 ↓
Certificate
 ↓
Nginx
 ↓
HTTPS
```

The important production concept is not the exact tool.

It's:

> **Certificate issuance + automatic renewal.**

---

# 23. Certificate Renewal

Certificates expire.

You don't want:

```text
Certificate expires
 ↓
HTTPS breaks
```

Instead:

```text
Certificate
 ↓
Automatic renewal
 ↓
New certificate
 ↓
Nginx reload
```

Certificate renewal should be monitored.

---

# 24. Never Manually Forget Certificate Expiration

A production server shouldn't depend on someone remembering:

```text
"Renew SSL certificate this month."
```

Automation should handle renewal.

This is a perfect example of why:

> **Automation is reliability.**

# 25. Nginx Configuration Test

Before applying changes:

```bash
sudo nginx -t
```

Successful:

```text
syntax is ok
test is successful
```

Then:

```bash
sudo systemctl reload nginx
```

This should become a habit.

---

# 26. Reload vs Restart

### Restart

```bash
sudo systemctl restart nginx
```

Stops and starts the service.

### Reload

```bash
sudo systemctl reload nginx
```

Tells Nginx to gracefully apply the new configuration.

For routine configuration changes:

> Prefer reload after successful validation.

---

# 27. Why Reload Helps Zero Downtime

Suppose Nginx currently routes:

```text
Nginx
 ↓
BLUE
```

You change it to:

```text
Nginx
 ↓
GREEN
```

Run:

```bash
nginx -t
```

then:

```bash
systemctl reload nginx
```

Nginx can gracefully transition to the new configuration.

Users don't need to experience a full Nginx restart.

# 30. React + Nginx

A simple configuration:

```nginx
server {
    listen 80;

    server_name example.com;

    root /usr/share/nginx/html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

The important part:

```nginx
try_files $uri $uri/ /index.html;
```

---

# 31. Why `try_files` Matters for React

React Router may have:

```text
/dashboard
/profile
/settings
/courses/123
```

Suppose the user directly opens:

```text
https://example.com/dashboard
```

Nginx looks for:

```text
/dashboard
```

There isn't necessarily a physical file.

Without the fallback:

```text
404
```

With:

```nginx
try_files $uri $uri/ /index.html;
```

Nginx serves:

```text
index.html
```

Then React Router handles:

```text
/dashboard
```

on the client.

---

# 32. API + React on the Same Domain

A clean architecture is:

```text
https://example.com/
        ↓
React

https://example.com/api/
        ↓
Node.js API
```

Nginx can route based on path:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}

location /api/ {
    proxy_pass http://api:5000;
}
```

Now:

```text
/             → React
/dashboard    → React
/api/users    → Express
/api/auth     → Express
```

---

# 33. This Simplifies CORS

If frontend and backend use the same origin:

```text
https://example.com
```

and:

```text
https://example.com/api
```

you may avoid many cross-origin problems.

Compare:

```text
Frontend:
https://frontend.example.com

Backend:
https://api.example.com
```

with:

```text
Frontend:
https://example.com

Backend:
https://example.com/api
```

The second architecture can be simpler for browser authentication.

---

# 34. Cookies Become Easier

For example:

```text
https://example.com
```

can communicate with:

```text
https://example.com/api
```

under the same origin.

This can make:

- Cookies
    
- Authentication
    
- CORS
    
- CSRF configuration
    

easier to reason about.

It doesn't eliminate security concerns, but it reduces unnecessary complexity.

---

# 35. WebSocket Proxying

If your backend uses WebSockets:

```text
Browser
 ↓
Nginx
 ↓
Node.js WebSocket server
```

Nginx needs upgrade headers.

Example:

```nginx
location /socket.io/ {
    proxy_pass http://api:5000;

    proxy_http_version 1.1;

    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

Without the correct upgrade handling, WebSocket connections may fail.

---

# 36. WebSocket Architecture

```text
Browser
   │
   │ WebSocket
   ↓
Nginx
   │
   │ Upgrade
   ↓
Node.js
```

This is common for:

- Chat applications
    
- Notifications
    
- Live dashboards
    
- Multiplayer features
    
- Real-time collaboration

# 37. Request Timeouts

Nginx has timeout settings.

For APIs that perform longer operations, you may configure appropriate values such as:

```nginx
proxy_connect_timeout 5s;
proxy_send_timeout 60s;
proxy_read_timeout 60s;
```

But don't blindly make everything:

```text
600s
```

Long timeouts can hide slow application problems.

A better system often uses:

```text
Fast API
+
Background jobs
```

for long-running work.

---

# 38. Upload Size

If your MERN application allows file uploads, Nginx may reject large requests.

You can configure:

```nginx
client_max_body_size 20M;
```

For example:

```nginx
server {
    client_max_body_size 20M;
}
```

Choose a limit based on your actual application requirements.

Don't make it unnecessarily huge.

---

# 39. Security Headers

Nginx can add security headers.

For example:

```nginx
add_header X-Content-Type-Options "nosniff" always;
```

Other useful headers may include:

```text
Content-Security-Policy
Referrer-Policy
Permissions-Policy
Strict-Transport-Security
```

But security headers should be configured carefully based on the application.

---

# 40. HSTS

HSTS means:

> HTTP Strict Transport Security

Example:

```nginx
add_header Strict-Transport-Security "max-age=31536000" always;
```

It tells compatible browsers to use HTTPS for future requests.

But don't enable aggressive HSTS settings blindly on a domain that isn't fully ready for HTTPS.

Especially be careful with:

```text
includeSubDomains
preload
```

because they can make recovery from HTTPS configuration mistakes harder.

---

# 41. Compression

Nginx can compress responses.

For example:

```nginx
gzip on;
gzip_types
    text/plain
    text/css
    application/json
    application/javascript
    application/xml;
```

This can reduce response size.

Modern setups may also use Brotli, depending on the Nginx build/modules available.

---

# 42. Cache Static Assets

React/Vite generates hashed assets:

```text
index-a83f91c.js
index-b7194e2.css
```

These can often be cached for a long time:

```nginx
location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

Why is this safe?

Because the filename changes when the content changes.

```text
old:
app-a83f91c.js

new:
app-b7194e2.js
```

---

# 43. Cache-Control Strategy

For hashed assets:

```text
Cache aggressively
```

For:

```text
index.html
```

you generally want a shorter caching policy so users can discover new deployments promptly.

This is an important frontend deployment consideration.

---

# 44. Static Asset Deployment

Imagine:

```text
Version A
index-a.js

Version B
index-b.js
```

If you delete A's assets immediately while some users still have the old HTML:

```text
Old HTML
 ↓
requests index-a.js
 ↓
404 ❌
```

Therefore:

> During deployments, retaining old hashed assets for some time can help avoid broken sessions.

This becomes especially important with CDNs and rolling deployments.

---

# 45. Load Balancing

Nginx can distribute requests across multiple backend instances.

Example:

```nginx
upstream backend {
    server api1:5000;
    server api2:5000;
    server api3:5000;
}
```

Then:

```nginx
location /api/ {
    proxy_pass http://backend;
}
```

Architecture:

```text
                    Nginx
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
        API 1       API 2       API 3
```

---

# 46. Why Multiple Instances?

Suppose:

```text
API 1 crashes
```

Nginx can potentially continue routing to:

```text
API 2
API 3
```

This improves availability.

It also allows:

```text
More traffic
```

to be distributed across instances.

---

# 47. Load Balancing Algorithms

Nginx supports different approaches.

Basic:

```text
Round Robin
```

Example:

```text
Request 1 → API1
Request 2 → API2
Request 3 → API3
Request 4 → API1
```

Other strategies include:

```text
least_conn
ip_hash
weights
```

Each has different tradeoffs.

---

# 48. Sticky Sessions

Some applications incorrectly depend on server-local session state.

Example:

```text
Session stored in API1 memory
```

Then:

```text
Request 1 → API1
Request 2 → API2
```

and API2 doesn't know the session.

Better architecture:

```text
Session
 ↓
Redis / Database / External store
```

Then any API instance can handle the request.

This is an important system-design principle.

---

# 49. Stateless Backend

Your Node.js API should ideally be stateless.

Instead of:

```text
API1
 └── User session in RAM
```

prefer:

```text
API1 ─┐
API2 ─┼── Redis/Database
API3 ─┘
```

Then horizontal scaling becomes much easier.

---

# 52. Nginx Configuration Example

A simplified combined configuration:

```nginx
server {
    listen 80;

    server_name example.com;

    location / {
        proxy_pass http://frontend;
    }

    location /api/ {
        proxy_pass http://api:5000;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

If Nginx serves the React build directly, the frontend configuration would instead use `root` and `try_files`.

# 57. What Does 502 Mean?

A common Nginx error:

```text
502 Bad Gateway
```

usually means Nginx couldn't successfully communicate with the upstream.

For example:

```text
Nginx
 ↓
API:5000
 ↓
Connection refused
```

Possible causes:

- API container stopped
    
- Wrong port
    
- Wrong hostname
    
- API crashed
    
- Docker network problem
    
- Upstream unavailable
    

---

# 58. What Does 503 Mean?

A:

```text
503 Service Unavailable
```

generally means the service isn't currently able to handle the request.

Exact causes depend on configuration.

The important debugging path is:

```text
Browser
 ↓
Nginx
 ↓
Upstream
 ↓
Application
 ↓
Database
```

Check each layer.

---

# 59. Debugging 502

Run:

```bash
docker compose ps
```

Then:

```bash
docker compose logs api
```

Check connectivity:

```bash
docker exec -it nginx-container ...
```

Then test the API from inside the Nginx network if appropriate.

For example:

```bash
curl http://api:5000/health
```

If this works:

```text
Docker network → API
```

# 60. Nginx Configuration Mistake

This is wrong if Nginx is inside Docker:

```nginx
proxy_pass http://localhost:5000;
```

when the API is another container.

Use:

```nginx
proxy_pass http://api:5000;
```

because:

```text
api
```

is the Compose service hostname.

---

# 61. DNS Inside Docker

Compose provides internal DNS.

For:

```yaml
services:
  nginx:
  api:
```

Nginx can resolve:

```text
api
```

to the appropriate container.

You don't need to manually configure:

```text
172.18.x.x
```

addresses.

---

# 62. Don't Hard-Code Container IPs

Never build configurations around:

```nginx
proxy_pass http://172.18.0.5:5000;
```

Container IPs can change.

Use:

```nginx
proxy_pass http://api:5000;
```

This is more resilient.

# 63. Nginx and Rate Limiting

Nginx can also provide basic rate limiting.

For example:

```nginx
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
```

Then:

```nginx
location /api/ {
    limit_req zone=api_limit burst=20;
    proxy_pass http://api:5000;
}
```

This can provide an additional protection layer.

Your Express application should still have its own security controls.

Defense in depth is better than relying on a single layer.

# 🧠 Interview Questions

### Q1. What is Nginx?

> A high-performance web server and reverse proxy that can also perform TLS termination, static file serving, load balancing, and request routing.

### Q2. Why use Nginx in front of Node.js?

> It provides a controlled public entry point and can handle TLS, static assets, routing, buffering, rate limiting, and load balancing while Node.js focuses on application logic.

### Q3. Why shouldn't Nginx in Docker use `localhost` to reach the API?

> Because `localhost` inside the Nginx container refers to the Nginx container itself. The API should be reached using its Compose service name, such as `api:5000`.

### Q4. What is TLS termination?

> Nginx receives and decrypts HTTPS traffic and forwards the request to the internal application.

### Q5. Why use `nginx -t` before reload?

> To detect configuration errors before applying the new configuration.

### Q6. Why use `reload` instead of `restart`?

> Reload allows Nginx to apply configuration changes more gracefully without unnecessarily stopping the service.

### Q7. Why use `try_files ... /index.html` for React?

> React Router handles client-side routes, so Nginx needs to return the SPA's `index.html` when a requested route isn't a physical file.

### Q8. What is a 502 error?

> It commonly indicates that Nginx couldn't successfully communicate with its configured upstream.

### Q9. How can Nginx participate in Blue-Green deployment?

> It can route traffic to either the Blue or Green backend and switch the upstream after the new version passes health checks.

### Q10. What is TLS certificate renewal?

> The automated process of obtaining a replacement certificate before the current certificate expires.

# 🔑 Lesson 12.14 Takeaways

Remember these **20 points**:

1. **Nginx can be the public entry point for your application.**
    
2. It can act as a reverse proxy.
    
3. It can terminate HTTPS/TLS.
    
4. It can serve React static files.
    
5. It can route `/api/*` to your Express backend.
    
6. In Docker, use service names such as `api:5000`, not `localhost`.
    
7. Forward the appropriate `Host` and `X-Forwarded-*` headers.
    
8. Configure Express proxy trust appropriately.
    
9. Keep internal API/database ports private when possible.
    
10. Use HTTPS in production.
    
11. Automate TLS certificate renewal.
    
12. Use `try_files` for React SPA routing.
    
13. Cache hashed static assets aggressively when appropriate.
    
14. Don't cache `index.html` the same way as immutable hashed assets.
    
15. Configure WebSocket upgrade headers when using WebSockets.
    
16. Use reasonable request-size and timeout limits.
    
17. Validate configuration with `nginx -t`.
    
18. Prefer graceful `reload` for configuration changes.
    
19. Nginx can load-balance multiple API instances.
    
20. **Nginx can become the traffic-switching layer for Blue-Green deployments.**
