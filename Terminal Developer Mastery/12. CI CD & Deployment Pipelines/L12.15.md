# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.15 — Versioning & Releases ⭐⭐⭐⭐⭐

We now have most of the deployment machinery:

```text
Developer
   ↓
Git
   ↓
GitHub Actions
   ↓
Tests
   ↓
Docker Build
   ↓
GHCR
   ↓
SSH
   ↓
Linux Server
   ↓
Docker Compose
   ↓
Nginx
   ↓
Production
```

But there's one very important question:

> **Exactly which version is running in production?**

If production breaks and someone asks:

```text
"What version are we running?"
```

you should be able to answer immediately:

```text
v1.4.2
Git commit: 8f31c2a
Docker image: ghcr.io/rahul/my-api:8f31c2a
Deployed: 2026-08-15
```

That's what **versioning and release management** help us achieve.

---

# 1. What Is Versioning?

Versioning gives a unique identity to different states of your software.

For example:

```text
v1.0.0
v1.1.0
v1.2.0
v2.0.0
```

Instead of saying:

```text
"the latest code"
```

we can say:

```text
"v1.2.0"
```

This makes software releases:

- Identifiable
    
- Reproducible
    
- Traceable
    
- Rollback-friendly
    

---

# 2. Why Versioning Matters in CI/CD

Imagine:

```text
Monday:
Production → latest

Tuesday:
Production → latest

Wednesday:
Production → latest
```

Then production breaks.

Which code is running?

You don't know.

Now imagine:

```text
Production → v1.4.2
```

You immediately know the release.

This is why:

> **Never treat production as an anonymous state.**

---

# 3. Semantic Versioning

One of the most common versioning systems is:

> **Semantic Versioning (SemVer)**

Format:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.4.7
```

means:

```text
MAJOR   = 2
MINOR   = 4
PATCH   = 7
```

Usually written:

```text
v2.4.7
```

---

# 4. MAJOR Version

Increase the major version when you introduce **breaking changes**.

Example:

```text
v1.4.2
   ↓
v2.0.0
```

Imagine your API previously had:

```http
GET /api/users
```

and now you change the response contract in a way that breaks existing clients.

That's a possible major release.

Think:

```text
1.x
 ↓
Breaking API change
 ↓
2.0.0
```

---

# 5. MINOR Version

Increase the minor version when you add functionality without intentionally breaking the existing API.

Example:

```text
v1.4.2
   ↓
v1.5.0
```

For example:

```text
Existing API
+
New endpoint
```

such as:

```http
GET /api/courses
```

while existing endpoints continue to work.

---

# 6. PATCH Version

Patch releases generally contain backward-compatible fixes.

Example:

```text
v1.5.0
   ↓
v1.5.1
```

Typical changes:

- Bug fixes
    
- Security fixes
    
- Small corrections
    
- Dependency patches
    

Example:

```text
Login bug
 ↓
v1.5.1
```

---

# 7. SemVer Mental Model

Remember:

```text
MAJOR.MINOR.PATCH
   │      │      │
   │      │      └── Bug fix
   │      └───────── New backward-compatible feature
   └──────────────── Breaking change
```

Example:

```text
v3.7.2
```

means:

```text
3 = major
7 = minor
2 = patch
```

---

# 8. Examples

Starting:

```text
v1.0.0
```

Bug fix:

```text
v1.0.1
```

New feature:

```text
v1.1.0
```

Another bug fix:

```text
v1.1.1
```

Breaking change:

```text
v2.0.0
```

Then:

```text
v2.0.1
v2.1.0
v3.0.0
```

# 9. What Is a Git Tag?

A Git tag gives a name to a specific commit.

For example:

```text
commit: 8f31c2a
        ↓
tag: v1.4.2
```

Now:

```text
v1.4.2
```

points to an exact state of your repository.

This is extremely useful for releases.

---

# 10. Creating a Git Tag

Suppose you're currently on the commit you want to release:

```bash
git status
```

Then:

```bash
git tag -a v1.4.2 -m "Release v1.4.2"
```

Check:

```bash
git tag
```

You might see:

```text
v1.0.0
v1.1.0
v1.2.0
v1.4.2
```

---

# 11. Push the Tag

Tags aren't automatically pushed with every normal Git push.

Push:

```bash
git push origin v1.4.2
```

or:

```bash
git push origin --tags
```

Now GitHub knows about the release tag.

---

# 12. Tag → Commit

Imagine:

```text
A → B → C → D → E
            ↑
          v1.4.2
```

The tag identifies commit:

```text
C
```

So even if the branch later moves:

```text
A → B → C → D → E → F → G
            ↑
          v1.4.2
```

`v1.4.2` still points to C.

That's why tags are excellent release identifiers.

---

# 13. Why Tags Are Better Than "Latest"

Compare:

```text
latest
```

with:

```text
v1.4.2
```

`latest` can change.

```text
latest
 ↓
v1.4.1
```

then later:

```text
latest
 ↓
v1.4.2
```

But:

```text
v1.4.2
```

always means the same release.

For production:

> **Prefer immutable/versioned references.**

---

# 14. Docker Image Versioning

We can connect Git tags to Docker images.

Suppose Git tag:

```text
v1.4.2
```

creates:

```text
ghcr.io/rahul/my-api:v1.4.2
```

We can also tag with the Git commit:

```text
ghcr.io/rahul/my-api:8f31c2a
```

Now we have:

```text
Git
 ↓
v1.4.2
 ↓
commit 8f31c2a
 ↓
Docker image
ghcr.io/rahul/my-api:v1.4.2
```

This is excellent traceability.

---

# 15. Why Use Both Version and Commit SHA?

Suppose:

```text
v1.4.2
```

is human-friendly.

And:

```text
8f31c2a
```

is machine-friendly and uniquely tied to a commit.

You can publish both:

```text
my-api:v1.4.2
my-api:8f31c2a
```

Then:

```text
v1.4.2
    ↓
8f31c2a
    ↓
Docker image
```

---

# 16. Human vs Machine Identifiers

Think:

```text
v1.4.2
```

is for:

> Humans

while:

```text
8f31c2a
```

is useful for:

> Exact source traceability

A strong production system can use both.

---

# 17. Immutable Artifacts

An artifact should ideally be immutable.

Meaning:

```text
v1.4.2
```

should always refer to the same software.

Avoid rebuilding:

```text
v1.4.2
```

with different source code.

Otherwise:

```text
v1.4.2
```

could mean:

```text
Monday → build A
Tuesday → build B
```

That's dangerous.

---

# 18. Build Once, Deploy Many

This is one of the most important CI/CD principles.

Instead of:

```text
Build for staging
Build for production
```

prefer:

```text
Build once
   ↓
Artifact
   ↓
Staging
   ↓
Production
```

Example:

```text
Git commit
   ↓
Docker image
   ↓
GHCR
   ↓
Staging
   ↓
Production
```

Same image.

---

# 19. Why Rebuilding Is Dangerous

Suppose staging uses:

```text
image A
```

and production rebuilds from the same source:

```text
image B
```

They should theoretically be identical.

But differences can occur due to:

- Dependency changes
    
- Build environment
    
- Base image updates
    
- Network dependencies
    
- Unpinned packages
    

Therefore:

> **Promote the tested artifact rather than rebuilding it.**

---

# 20. Docker Tags

You might publish:

```text
my-api:v1.4.2
my-api:8f31c2a
my-api:latest
```

They have different purposes.

### Version tag

```text
v1.4.2
```

Human release.

### Commit tag

```text
8f31c2a
```

Exact source version.

### `latest`

```text
latest
```

Moving pointer.

For production:

> Prefer the version or commit tag.

---

# 21. Docker Digest

There's an even stronger identifier.

Docker images can be referenced by digest:

```text
sha256:abc123...
```

For example:

```text
ghcr.io/rahul/my-api@sha256:abc123...
```

A digest identifies the exact image content.

This is stronger than a mutable tag.

---

# 22. Tag vs Digest

Think:

```text
v1.4.2
   ↓
human-friendly
```

while:

```text
sha256:...
   ↓
content-addressed
```

For high-security production deployments, digest pinning can provide stronger guarantees.

# 23. Release Notes

A release should tell users and engineers:

```text
What changed?
What was fixed?
Are there breaking changes?
Are migrations required?
Are there security fixes?
```

Example:

```text
v1.4.2

Added:
- Course search
- Pagination

Fixed:
- Login redirect bug
- Dashboard loading issue

Security:
- Updated vulnerable dependency

Migration:
- No database migration required
```

This is much more useful than:

```text
v1.4.2
```

alone.

---

```text
CHANGELOG.md
```

could contain:

```markdown
### Fixed
- Fixed login redirect

### Added
- Course search

### Added
- User dashboard
```

# 25. Changelog vs Git History

Git history:

```text
commit abc
commit def
commit ghi
commit jkl
```

is developer-oriented.

Changelog:

```text
v1.4.2
- Fixed login
- Fixed pagination
```

is release-oriented.

You need both.

Suppose:


Then:


# 30. Hotfix Releases

Imagine production:

```text
v1.4.2
```

has a serious bug.

You don't want to wait for:

```text
v1.5.0
```

You can release:

```text
v1.4.3
```

Flow:

```text
v1.4.2
   ↓
Bug discovered
   ↓
Hotfix
   ↓
v1.4.3
```

This is why PATCH versions are useful.

# 31. Security Releases

Suppose a dependency vulnerability is discovered.

Current:

```text
v1.4.2
```

Security fix:

```text
v1.4.3
```

Release notes should clearly mention:

```text
Security:
- Updated vulnerable dependency
```

For important vulnerabilities, you may also publish advisories depending on the project.

# 32. Pre-Releases

Sometimes a version isn't ready for general production.

You can use:

```text
v2.0.0-alpha.1
v2.0.0-beta.1
v2.0.0-rc.1
```

Meaning:

```text
alpha → early testing
beta  → broader testing
rc    → release candidate
```

Then:

```text
v2.0.0
```

becomes the stable release.

---

# 33. Release Candidate

For example:

```text
v2.0.0-rc.1
```

can go to staging.

Test:

```text

 ↓
RC
 ↓
Staging
 ↓
Smoke tests
 ↓
Production
```

If everything works:

```text
v2.0.0
```

# 34. Versioning API Contracts

Versioning isn't only about application versions.

You may also version APIs.

For example:

```text
/api/v1/users
```

and eventually:

```text
/api/v2/users
```

This can allow older clients to continue working.

But don't add API versions automatically for every small change.

Use versioning when you actually need compatibility boundaries.

```bash
curl https://example.com/api/version
```

```text

 ↓

 ↓
```

# 43. Extracting the Version

If the workflow is triggered by:

```text

```


Then:

```text

```

# 44. Git SHA Tag

At the same time:

```text
commit = 8f31c2a
```

Then publish:

```text
ghcr.io/rahul/my-api:v1.4.2

```

Potentially also:



---

# 45. Mutable vs Immutable Tags

Suppose:

```text
my-api:1
```

points to:

```text
v1.4.2
```

Later:

```text
my-api:1
```

could point to:

```text
v1.5.0
```

Therefore:

```text
1
```

is mutable.

Whereas:

```text
v1.4.2
```

should remain fixed.

And:

```text
sha256:...
```

is content-addressed.

---

# 46. Production Recommendation

For your production deployments:

Prefer:

```text
ghcr.io/rahul/my-api:v1.4.2
```

or even:

```text
ghcr.io/rahul/my-api@sha256:...
```

rather than:

```text
ghcr.io/rahul/my-api:latest
```

This makes deployments reproducible.

# 48. Artifact Traceability

A strong release system gives you:

```text

 ↓
Git tag
 ↓
Commit
 ↓
Docker image
 ↓

 ↓

```

For example:

```text

   ↓

   ↓

```

This chain is called:

> **Artifact traceability**

---

# 49. Why Traceability Matters

During an incident:

```text
Production broken
```

You need to answer:

```text
Which release?
Which commit?
Which image?
Which deployment?
Which changes?
```

Without traceability:

```text
🤷
```

With traceability:

```text
v1.4.2
→ 8f31c2a
→ image digest
→ deployment #183
```

Much easier.

```text

```

or:

```text

```

This information can help automated versioning tools determine:

```text

MINOR
MAJOR
```

# 57. Release vs Deployment

These are not the same thing.

### Release

> A version of software is formally identified and published.

### Deployment

> That version is installed/runs in an environment.

For example:

```text
v1.5.0
```

can be:

```text
Released
```

but not yet:

```text
Production
```

It could first go to staging.

---

# 58. One Release, Multiple Environments

```text
v1.5.0
   │
   ├──→ Development
   │
   ├──→ Staging
   │
   └──→ Production
```

The artifact stays the same.

Only the environment changes.

This is a very important CI/CD concept.

---

# 59. Release Gates

Before production:

```text
v1.5.0
 ↓
Staging
 ↓
Tests
 ↓
Smoke tests
 ↓
Approval
 ↓
Production
```

Each stage acts as a gate.

This reduces the probability of pushing a bad version directly into production.

---

# 60. Release Rollback

Suppose:

```text
Production
 ↓
v1.5.0
```

fails.

You can deploy:

```text
v1.4.3
```

because the artifact still exists.

That's much safer than:

```text
"Let's rebuild the old code."
```

---

# 61. Never Delete Old Production Artifacts Too Quickly

Suppose you deploy:

```text
v1.5.0
```

and immediately delete:

```text
v1.4.3
```

Then rollback becomes difficult.

Keep old versions according to your retention policy.

For example:

```text
Current
v1.5.0

Previous
v1.4.3

Older
v1.4.2
v1.4.1
```

---

# 62. Artifact Retention

You don't need every image forever.

You can define:

```text
Keep:
- Current production
- Last 5 releases
- Security-critical releases
```

The exact policy depends on:

- Storage
    
- Compliance
    
- Rollback requirements
    
- Release frequency

# 73. Interview Questions

### Q1. What is Semantic Versioning?

> A versioning convention using MAJOR.MINOR.PATCH to communicate breaking changes, new backward-compatible functionality, and bug fixes.

### Q2. What is a Git tag?

> A named reference to a specific Git object, commonly used to identify a release commit.

### Q3. Why use Git tags for releases?

> They provide a stable, identifiable reference to the exact source code associated with a release.

### Q4. Why shouldn't production use `latest`?

> `latest` is a moving tag and doesn't reliably identify the exact artifact being deployed.

### Q5. What is an immutable artifact?

> An artifact whose contents remain fixed after creation, allowing reliable promotion and rollback.

### Q6. Why use both version and Git SHA Docker tags?

> The version is human-friendly while the Git SHA provides exact source-code traceability.

### Q7. What is a Docker digest?

> A content-addressed SHA-256 identifier representing the exact image content.

### Q8. What is the difference between a release and a deployment?

> A release identifies and publishes a software version, while deployment installs/runs that version in a particular environment.

### Q9. Why is "build once, deploy many" useful?

> It ensures staging and production use the same tested artifact instead of rebuilding potentially different artifacts.

### Q10. Why keep old Docker images?

> They provide reliable rollback targets and help with incident investigation.

# 🔑 Lesson 12.15 Takeaways

Remember these **20 points**:

1. **Every production deployment should have a clear version.**
    
2. SemVer uses `MAJOR.MINOR.PATCH`.
    
3. Breaking changes generally increase MAJOR.
    
4. New backward-compatible features generally increase MINOR.
    
5. Bug/security fixes generally increase PATCH.
    
6. Git tags identify exact release commits.
    
7. Prefer versioned Docker tags over `latest`.
    
8. Git SHA tags provide exact source traceability.
    
9. Docker digests identify exact image content.
    
10. Production artifacts should be immutable whenever possible.
    
11. **Build once, deploy many.**
    
12. A release and a deployment are different concepts.
    
13. Changelogs communicate changes to humans.
    
14. Git history records development details.
    
15. Release notes should mention breaking changes and migrations.
    
16. Keep previous production artifacts for rollback.
    
17. Expose build/version metadata through a `/version` endpoint.
    
18. Version infrastructure configuration alongside application code.
    
19. Connect releases → commits → images → deployments.
    
20. **A professional production system should always be able to answer: "Exactly what is running right now?"**
