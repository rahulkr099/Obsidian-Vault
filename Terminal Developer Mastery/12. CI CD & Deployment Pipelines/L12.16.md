# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.16 — Database Migrations ⭐⭐⭐⭐⭐

This is one of the **most important production deployment lessons**.

So far, we've learned how to deploy:

```text
Git
 ↓
GitHub Actions
 ↓
Docker
 ↓
GHCR
 ↓
Linux
 ↓
Nginx
 ↓
Application
```

But there's another system that changes during deployment:

```text
                    Application
                         │
                         ↓
                     Database
```

Your application code can be deployed perfectly and still break production if the **database schema or data isn't compatible** with the new version.

---

# 1. What Is a Database Migration?

A database migration is a controlled change to the database structure or data.

Examples:

```text
Add a column
Remove a column
Rename a column
Create an index
Create a table
Modify constraints
Move/transform data
```

For MongoDB, examples include:

```text
Create a collection
Create an index
Backfill a field
Rename a field
Transform documents
```

For SQL databases:

```sql
ALTER TABLE users ADD COLUMN display_name TEXT;
```

The important idea is:

> **Database changes should be versioned and repeatable, not manually performed randomly on production.**

---

# 2. Why Migrations Matter in CI/CD

Imagine your current production application:

```text
App v1
 ↓
users.name
```

You release:

```text
App v2
 ↓
users.full_name
```

But production database still contains:

```text
name
```

Now:

```text
App v2
 ↓
full_name
 ↓
doesn't exist
```

Possible result:

```text
500 Internal Server Error
```

This is why application deployment and database migration must be designed together.

---

# 3. The Dangerous Deployment

Suppose we do:

```text
1. Change database
2. Deploy new application
```

and the migration removes something the old application still needs.

Production:

```text
Old App
   ↓
Database changed ❌
```

The old application can immediately break.

A safer approach is:

```text
Database
   ↓
Backward-compatible change
   ↓
New application
   ↓
Data migration
   ↓
Cleanup
```

---

# 4. Database Schema Version

Just like application versions:

```text
App:
v1.5.0
```

the database may have:

```text
Migration:
27
```

Conceptually:

```text
v1.4.0
 ↓
migration 25

v1.4.1
 ↓
migration 26

v1.5.0
 ↓
migration 27
```

Your migration system tracks which changes have already been applied.

---

# 5. Migration History

A migration system might maintain:

```text
migrations/
├── 001-create-users
├── 002-add-email-index
├── 003-add-role
├── 004-add-profile
└── 005-backfill-profile
```

Production records:

```text
001 ✓
002 ✓
003 ✓
004 ✓
005 ✗
```

The migration runner knows:

```text
Run 005
```

instead of rerunning everything.

---

# 6. Why Version-Control Migrations?

Without migrations, someone might say:

> "I manually changed production last Tuesday."

That's dangerous.

Instead:

```text
Git
 ↓
Migration file
 ↓
Code review
 ↓
CI
 ↓
Production
```

Now the database change is:

- Reviewable
    
- Reproducible
    
- Auditable
    
- Documented
    

---

# 7. Migration Files

A migration might conceptually look like:

```text
migrations/
└── 027-add-user-role.js
```

For MongoDB:

```javascript
export async function up(db) {
  await db.collection("users").updateMany(
    { role: { $exists: false } },
    { $set: { role: "user" } }
  );
}
```

The exact implementation depends on your migration tool.

The important idea is:

```text
up()
 ↓
Apply migration
```

---

# 8. Down Migrations

Some migration systems also support:

```javascript
export async function down(db) {
  // reverse migration
}
```

Conceptually:

```text
up:
old → new

down:
new → old
```

But here's an important production lesson:

> **Not every migration can or should be automatically reversed.**

---

# 9. Why Rollback Isn't Always Simple

Suppose you remove data:

```text
name = Rahul
```

and then:

```text
DELETE name
```

How can you automatically restore:

```text
name = Rahul
```

if the value is gone?

You can't.

Therefore:

```text
Schema rollback
≠
Data rollback
```

This distinction is extremely important.

---

# 10. Roll-Forward Strategy

Instead of trying to reverse every production migration:

```text
v1.5.0
 ↓
migration 27
 ↓
bug
```

you might create:

```text
migration 28
```

that fixes the problem.

So:

```text
27
 ↓
28
```

instead of:

```text
27
 ↓
ROLLBACK 27
```

This is called:

> **Roll-forward recovery**

It is often safer for production data.

---

# 11. Schema Migration vs Data Migration

These are different.

### Schema migration

Changes database structure.

Example:

```text
Add index
Add field
Create table
```

### Data migration

Changes existing data.

Example:

```text
name
 ↓
fullName
```

or:

```text
role = "student"
 ↓
role = "learner"
```

You need to consider them separately.

---

# 12. MongoDB Example

Suppose existing documents:

```json
{
  "_id": "1",
  "name": "Rahul"
}
```

New application expects:

```json
{
  "_id": "1",
  "fullName": "Rahul"
}
```

You could migrate:

```javascript
await db.collection("users").updateMany(
  { fullName: { $exists: false } },
  [
    {
      $set: {
        fullName: "$name"
      }
    }
  ]
);
```

Now:

```text
name
 ↓
fullName
```

But don't immediately delete `name`.

We'll see why.

---

# 13. The Dangerous Rename

Bad deployment:

```text
1. Rename name → fullName
2. Deploy new app
```

Current application:

```text
v1
 ↓
expects name
```

Database:

```text
fullName
```

Result:

```text
v1 ❌
```

If your deployment has multiple application instances, this becomes even more dangerous.

---

# 14. Expand-and-Contract

The safer approach is:

> **Expand → Migrate → Switch → Contract**

This is one of the most important patterns in production database deployments.

---

# 15. Step 1 — Expand

Add the new structure without removing the old one.

Current:

```text
name
```

Add:

```text
fullName
```

Now:

```text
name
fullName
```

Both exist.

---

# 16. Step 2 — Deploy Compatible Application

Deploy an application that can work with both:

```text
name
```

and:

```text
fullName
```

For example:

```javascript
const fullName = user.fullName ?? user.name;
```

Now:

```text
Old data
   ↓
name
   ↓
Application works

New data
   ↓
fullName
   ↓
Application works
```

This creates compatibility during deployment.

---

# 17. Step 3 — Backfill Data

Now migrate existing documents:

```text
name
 ↓
fullName
```

For example:

```json
{
  "name": "Rahul",
  "fullName": "Rahul"
}
```

You can perform this migration gradually for large databases.

---

# 18. Step 4 — Switch Application

Now the application can primarily use:

```text
fullName
```

instead of:

```text
name
```

Because all important data has been migrated.

---

# 19. Step 5 — Contract

Only after you're certain no application version needs `name` anymore:

```text
Remove name
```

Now:

```text
fullName
```

is the only field.

Final state:

```text
fullName
```

---

# 20. Full Expand-and-Contract Flow

Remember this:

```text
Old
 │
 ├── name
 │
 ↓
EXPAND
 │
 ├── name
 └── fullName
 │
 ↓
COMPATIBLE APP
 │
 ↓
BACKFILL
 │
 ↓
NEW APP
 │
 └── fullName
 │
 ↓
CONTRACT
 │
 └── fullName
```

This pattern dramatically reduces deployment risk.

---

# 21. Why This Works With Zero-Downtime

Suppose during deployment you temporarily have:

```text
Old App
New App
```

Both may be running simultaneously.

If both understand:

```text
name
fullName
```

then:

```text
Old App ─┐
         ├──→ Database
New App ─┘
```

can safely coexist.

This is exactly what we need for:

- Blue-Green deployment
    
- Rolling deployment
    
- Canary deployment
    

---

# 22. Database Compatibility Window

During a deployment, there may be a period where:

```text
v1
+
v2
```

are both active.

Therefore your database needs a:

> **Compatibility window**

Think:

```text
Database
   ↑
   │
v1 ─┤
v2 ─┤
```

Both must understand the database during the transition.

---

# 23. Backward Compatibility

A database change is backward-compatible when the old application can continue working after the change.

Example:

```text
Add new nullable field
```

Old application:

```text
Doesn't care about new field
```

Good.

But:

```text
Delete existing required field
```

Old application:

```text
Still expects field
```

Bad.

---

# 24. Safe vs Unsafe Changes

### Usually safer

```text
Add optional field
Add table
Add index
Add nullable column
```

### Potentially dangerous

```text
Rename field
Remove field
Change data type
Add strict constraint
Delete data
```

The exact safety depends on the application and database.

---

# 25. Adding an Index

Suppose:

```text
users.email
```

is frequently queried.

You want:

```text
index(email)
```

This is generally safer than removing a field.

But:

> Large index creation can still consume significant CPU, memory, disk I/O, and lock resources depending on the database and index operation.

So even "safe" migrations require production planning.

---

# 26. Large Data Migrations

Imagine:

```text
10 million documents
```

You need to transform:

```text
oldField
 ↓
newField
```

Don't necessarily do:

```javascript
await updateMany(...)
```

without thinking.

A huge migration may:

- Consume memory
    
- Increase database load
    
- Increase latency
    
- Create replication pressure
    
- Take a long time
    
- Compete with production traffic
    

---

# 27. Batch Migration

A safer strategy is often:

```text
1000 records
 ↓
pause/check
 ↓
1000
 ↓
pause/check
 ↓
1000
```

Conceptually:

```text
Database
 ├── batch 1
 ├── batch 2
 ├── batch 3
 ├── ...
 └── batch N
```

This allows better control.

---

# 28. Migration Progress

For large migrations, track progress.

For example:

```text
Processed:
2,500,000 / 10,000,000
```

You might maintain:

```text
migration_status
```

or use a dedicated migration framework.

This makes recovery easier if the process stops.

---

# 29. Idempotent Migrations

A very useful property is:

> Running a migration again should not corrupt already-migrated data.

For example:

```javascript
updateMany(
  { fullName: { $exists: false } },
  ...
);
```

If the migration runs twice:

```text
Already migrated
 ↓
fullName exists
 ↓
skip
```

This is much safer than:

```text
update everything blindly
```

---

# 30. Why Idempotency Matters

Suppose migration:

```text
migration 27
```

starts:

```text
1M records
```

Then server crashes at:

```text
700k
```

You restart it.

If it's idempotent:

```text
already migrated → skip
not migrated → process
```

You can safely continue.

---

# 31. Migration Transactions

Some databases support transactions for migrations.

Conceptually:

```text
BEGIN
 ↓
Change A
 ↓
Change B
 ↓
Change C
 ↓
COMMIT
```

If something fails:

```text
ROLLBACK
```

But don't assume every migration can safely fit into one giant transaction.

Large migrations may need batching.

And MongoDB transactions have their own constraints and performance considerations.

---

# 32. Schema Migration vs Data Migration Transactions

Consider:

```text
Schema:
add fullName

Data:
copy name → fullName
```

You might perform these separately:

```text
Migration 27
 ↓
Add field/index

Migration 28
 ↓
Backfill data
```

This can make the deployment easier to control.

---

# 33. Migration Ordering

Never assume:

```text
Application deploy
```

and:

```text
Database migration
```

can happen in any order.

You must define the dependency.

For expand-and-contract:

```text
Expand
 ↓
Compatible application
 ↓
Backfill
 ↓
New application
 ↓
Contract
```

Order matters.

---

# 34. Dangerous CI/CD Order

This is risky:

```text
Deploy new app
 ↓
Migration
```

if the new application requires the migration immediately.

A safer flow may be:

```text
Run backward-compatible migration
 ↓
Deploy application
```

But even that isn't universal.

The correct sequence depends on the migration.

---

# 35. Three Common Migration Strategies

### Strategy 1 — Migration before deployment

```text
DB migration
 ↓
App deployment
```

Useful when the migration is backward-compatible.

---

### Strategy 2 — Application before migration

```text
App deployment
 ↓
DB migration
```

Useful when the new application can safely operate before the migration.

---

### Strategy 3 — Multi-step migration

```text
Expand
 ↓
Deploy compatible app
 ↓
Backfill
 ↓
Switch
 ↓
Contract
```

This is the safest pattern for complex changes.

---

# 36. Migration Automation

Your CI/CD pipeline can execute:

```text
Tests
 ↓
Build
 ↓
Migration
 ↓
Deploy
```

But be careful.

A database migration is a production change.

You should not allow:

```text
random branch
 ↓
automatic migration
 ↓
production
```

without controls.

---

# 37. Production Migration Gate

A better pipeline:

```text
Pull Request
 ↓
CI
 ↓
Tests
 ↓
Staging migration
 ↓
Staging tests
 ↓
Approval
 ↓
Production migration
 ↓
Deployment
```

For critical systems, production migration may require explicit approval.

---

# 38. Backup Before Migration

Before a risky production migration:

```text
Database
   ↓
Backup
   ↓
Migration
```

If something goes wrong:

```text
Restore
```

can become your recovery path.

But:

> A backup is only useful if you can actually restore it.

We'll revisit this in Lesson 12.17.

---

# 39. Backup Verification

Don't just say:

```text
Backup created ✓
```

Also verify:

```text
Backup
 ↓
Can it be read?
 ↓
Can it be restored?
 ↓
Is the data usable?
```

A backup that has never been tested is only an assumption.

---

# 40. Database Migration Logs

Every migration should produce useful logs.

For example:

```text
Migration 027 started
Migration 027 completed
Duration: 14.2s
Records processed: 125,000
```

If something fails:

```text
Migration 027 failed
Reason: duplicate key
```

This is extremely useful during incidents.

---

# 41. Migration Locking

Imagine two deployments start simultaneously:

```text
Deployment A
 ↓
Migration 27

Deployment B
 ↓
Migration 27
```

You don't want both executing it simultaneously.

Migration systems commonly use a lock or migration history mechanism to prevent concurrent migration execution.

This connects to our earlier lesson about:

```text
Deployment concurrency
```

---

# 42. CI/CD + Migration Concurrency

Your production pipeline should ideally prevent:

```text
Deployment A
+
Deployment B
```

from changing the same database simultaneously.

For GitHub Actions, a production deployment workflow can use concurrency controls such as:

```yaml
concurrency:
  group: production
  cancel-in-progress: false
```

This helps ensure controlled production changes.

---

# 43. Database Connection Management

During migrations, the application may still be serving traffic.

Suppose:

```text
Migration
 ↓
Database
```

while:

```text
Users
 ↓
API
 ↓
Database
```

are also querying.

The migration must be designed to coexist safely with normal traffic.

This is another reason to avoid heavy blocking migrations during peak traffic.

---

# 44. Maintenance Windows

Some changes are too risky to perform during normal traffic.

In that case:

```text
Low traffic
 ↓
Maintenance
 ↓
Migration
```

might be appropriate.

But modern systems often try to design migrations so maintenance windows aren't required.

The goal is:

> **Make schema changes online whenever reasonably possible.**

---

# 45. Expand-and-Contract Example — SQL

Suppose we have:

```text
users.name
```

We want:

```text
users.first_name
users.last_name
```

### Step 1

Add:

```text
first_name
last_name
```

Keep:

```text
name
```

---

### Step 2

Deploy code that supports:

```text
name
+
first_name
+
last_name
```

---

### Step 3

Backfill:

```text
"Rahul Kumar"
```

into:

```text
first_name = "Rahul"
last_name = "Kumar"
```

---

### Step 4

Switch application to:

```text
first_name
last_name
```

---

### Step 5

Remove:

```text
name
```

later.

---

# 46. MongoDB Example

Current:

```json
{
  "_id": 1,
  "name": "Rahul Kumar"
}
```

Expanded:

```json
{
  "_id": 1,
  "name": "Rahul Kumar",
  "firstName": "Rahul",
  "lastName": "Kumar"
}
```

Application switches to:

```text
firstName
lastName
```

Later:

```json
{
  "_id": 1,
  "firstName": "Rahul",
  "lastName": "Kumar"
}
```

This is a safe conceptual evolution.

---

# 47. Renaming a MongoDB Field

MongoDB supports field renaming using `$rename`.

Conceptually:

```javascript
await db.collection("users").updateMany(
  {},
  {
    $rename: {
      name: "fullName"
    }
  }
);
```

But don't automatically run this in a zero-downtime deployment if the old application still expects `name`.

The operation itself may work perfectly while the deployment strategy remains unsafe.

---

# 48. Database Migration Doesn't Mean Only Schema

Migration can also mean:

```text
Old data
 ↓
Transform
 ↓
New data
```

For example:

```text
role: "student"
```

becomes:

```text
role: "learner"
```

This is a **data migration**.

---

# 49. Data Migration Risks

A data migration can introduce:

```text
Incorrect transformations
Duplicate records
Lost information
Performance problems
Partial migration
Unexpected null values
```

Therefore:

> Treat data migrations as production code.

They deserve:

- Code review
    
- Tests
    
- Logs
    
- Monitoring
    
- Rollback/recovery planning
    

---

# 50. Test Migrations

Before production:

```text
Production-like database
        ↓
Run migration
        ↓
Verify schema
        ↓
Verify data
        ↓
Run application tests
```

Don't test only:

```text
migration executes without error
```

Also test:

```text
data is correct afterward
```

---

# 51. Migration Testing Example

Before:

```json
{
  "name": "Rahul"
}
```

After:

```json
{
  "name": "Rahul",
  "fullName": "Rahul"
}
```

Test:

```javascript
expect(user.fullName).toBe("Rahul");
```

Also verify:

```text
Existing functionality still works.
```

---

# 52. Migration Performance Testing

For a large migration:

```text
1000 records
```

isn't enough.

Test with:

```text
100,000
1,000,000
```

or a representative dataset.

Measure:

```text
Duration
CPU
Memory
Database load
Query latency
Lock behavior
```

---

# 53. Migration Timeout

Your deployment shouldn't wait forever.

For example:

```text
Migration
 ↓
30 minutes
 ↓
Still running
```

Something may be wrong.

You need:

- Monitoring
    
- Timeout strategy
    
- Safe interruption
    
- Recovery plan
    

Never use an arbitrary timeout without understanding whether stopping the operation is safe.

---

# 54. Migration Failure

Suppose:

```text
Migration 27
 ↓
fails at step 3
```

Don't immediately run:

```bash
migration rollback
```

First determine:

```text
What changed?
Was it transactional?
Is the migration partially applied?
Can it safely resume?
Was data modified?
```

Then decide:

```text
Rollback
```

or:

```text
Repair / roll forward
```

---

# 55. Migration State

Your migration system should know:

```text
Applied:
001
002
003
004

Pending:
005
006
```

If 005 fails:

```text
001 ✓
002 ✓
003 ✓
004 ✓
005 ✗
006 pending
```

The system should not incorrectly claim:

```text
005 ✓
```

---

# 56. Migration Naming

Use clear names:

```text
027-add-user-role
028-create-course-index
029-backfill-course-slugs
030-add-profile-fields
```

Bad:

```text
migration1
update
fix
new
final
final2
```

Migration history should be understandable months later.

---

# 57. Don't Edit Applied Migrations

This is a very important rule.

Suppose:

```text
027-add-user-role
```

has already run in production.

Don't edit it to:

```text
027-add-user-role
```

with different behavior.

Instead create:

```text
028-fix-user-role
```

Why?

Because production already has the old migration.

Changing the file doesn't magically change production.

---

# 58. Migration Immutability

Think of migrations as historical records:

```text
001 ✓
002 ✓
003 ✓
```

Once applied:

> Treat them as immutable.

New changes should create new migrations.

This is similar to Git commits and release artifacts.

---

# 59. Migration Dependencies

Suppose:

```text
028
```

expects:

```text
027
```

to have created a field.

Then:

```text
028
```

depends on:

```text
027
```

The migration order must be deterministic.

```text
027
 ↓
028
 ↓
029
```

Never randomly reorder applied migrations.

---

# 61. Migration + Blue-Green

Suppose:

```text
BLUE = v1.4
GREEN = v1.5
```

You cannot blindly modify the database for GREEN if BLUE still needs the old schema.

Instead:

```text
Expand DB
 ↓
BLUE still works
GREEN still works
 ↓
Deploy GREEN
 ↓
Switch traffic
 ↓
Remove old schema later
```

This is the connection between:

```text
Database migrations
+
Zero-downtime deployments
```

---

# 62. Migration + Canary

Canary makes compatibility even more important.

Suppose:

```text
95% → v1.4
5%  → v1.5
```

Both versions are active.

Therefore:

```text
Database
 ↓
must support v1.4 + v1.5
```

until the migration is complete.

---

# 63. The Compatibility Matrix

For complex deployments, think in terms of a matrix:

|Database|App v1.4|App v1.5|
|---|--:|--:|
|Old schema|✅|❌|
|Expanded schema|✅|✅|
|Final schema|❌|✅|

This table tells you exactly why:

```text
Expand first
```

is so useful.

---

# 64. Migration Strategy Selection

Before writing a migration, ask:

```text
1. Can old application work with the new schema?
2. Can new application work with the old schema?
3. Will both versions run simultaneously?
4. Is data being deleted?
5. Is the operation expensive?
6. Can it be done in batches?
7. Do we need a backup?
8. Can we roll forward?
```

These questions prevent many production mistakes.

# 66. A Practical MERN Migration Structure

For your Node.js/MongoDB projects, you can organize:

```text
server/
```

# 69. Why Exit Codes Matter

Suppose:

```bash
npm run migrate
```

fails.

Your CI/CD pipeline needs to know.

Correct:

```text
Migration fails
 ↓
exit 1
 ↓
GitHub Actions detects failure
 ↓
Deployment stops
```

Bad:

```text
Migration fails
 ↓
script still exits 0
 ↓
pipeline thinks success
 ↓
broken deployment
```

This is why Linux exit codes matter in CI/CD.

# 70. Deployment Gate

Your pipeline can do:

```bash
npm run migrate
```

then:

```bash
if [ $? -ne 0 ]; then
    echo "Migration failed"
    exit 1
fi
```

Although shell's `set -e` or explicit error handling can often make this cleaner.

The important concept:

> **Migration failure must block an unsafe deployment when the application depends on that migration.**

# 73. The Most Important Rule

# 74. Interview Questions

### Q1. What is a database migration?

> A version-controlled, repeatable change to database schema or data.

### Q2. Why are migrations important in CI/CD?

> They allow database changes to be tracked, reviewed, tested, and automatically applied in a controlled manner.

### Q3. What is expand-and-contract?

> A migration strategy where you first add the new structure, deploy compatible code, migrate data, switch the application, and only later remove the old structure.

### Q4. Why shouldn't you immediately rename a production field?

> Because older application versions may still depend on the original field.

### Q5. What is a data migration?

> A controlled transformation of existing database records.

### Q6. Why are large data migrations risky?

> They can consume significant database resources and increase latency, locking, replication pressure, and operational risk.

### Q7. What does idempotent migration mean?

> Re-running the migration doesn't incorrectly modify data that has already been migrated.

### Q8. Why shouldn't applied migration files be edited?

> Because they represent historical changes that may already have been applied to production. New changes should use a new migration.

### Q9. Rollback or roll-forward?

> Roll-forward is often safer for production data because destructive data changes may not be reversible.

### Q10. Why do Blue-Green deployments require backward-compatible database changes?

> Because old and new application versions can temporarily run at the same time and both need to work with the database.

# 🔑 Lesson 12.16 Takeaways

Remember these **20 points**:

1. **Database migrations are part of deployment engineering.**
    
2. Never treat production database changes as random manual commands.
    
3. Version migrations in Git.
    
4. Treat applied migrations as immutable history.
    
5. Schema changes and data changes are different.
    
6. `running` old and new application versions simultaneously requires database compatibility.
    
7. **Expand-and-contract is one of the most important safe migration patterns.**
    
8. Add new structures before removing old ones.
    
9. Backfill data separately when appropriate.
    
10. Don't immediately delete old fields.
    
11. Large data migrations should often be batched.
    
12. Idempotent migrations are safer.
    
13. Migration failures must be visible to CI/CD.
    
14. Use proper exit codes.
    
15. Test migrations against production-like data.
    
16. Back up important data before risky migrations.
    
17. A backup is useless if restoration has never been tested.
    
18. Roll-forward can be safer than attempting destructive rollbacks.
    
19. Control concurrent production migrations.
    
20. **Never make a destructive schema change while an active application version still depends on the old schema.**
