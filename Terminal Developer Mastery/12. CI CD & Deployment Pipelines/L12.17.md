# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.17 — Rollbacks & Disaster Recovery ⭐⭐⭐⭐⭐

This lesson is extremely important because **successful deployment is only half of production engineering**.

A professional engineer doesn't only ask:

> "How do I deploy?"

They also ask:

> **"What happens when deployment goes wrong?"**

A production system should be designed with failure in mind.

---

# 1. The Production Mindset

A beginner thinks:

```text
Code
 ↓
Deploy
 ↓
Done
```

A production engineer thinks:

```text
Code
 ↓
Test
 ↓
Deploy
 ↓
Verify
 ↓
Monitor
 ↓
Failure?
 ↓
Rollback / Recover
```

The difference is huge.

---

# 2. What Is a Rollback?

A rollback means:

> **Returning the application to a previously known-good version.**

Suppose:

```text
Production
 ↓
v1.4.3 🟢
```

You deploy:

```text
v1.5.0
```

Then:

```text
500 errors
```

Rollback:

```text
v1.5.0 ❌
   ↓
v1.4.3 🟢
```

---

# 3. Rollback vs Disaster Recovery

These are related but different.

### Rollback

Deals primarily with:

```text
Bad deployment
Bad release
Broken configuration
```

Example:

```text
v1.5.0 → v1.4.3
```

### Disaster Recovery

Deals with larger failures:

```text
Server destroyed
Database corrupted
Disk failure
Cloud outage
Accidental deletion
Ransomware
```

Example:

```text
Primary server
     ❌
       ↓
Restore infrastructure
       ↓
Restore database
       ↓
Recover service
```

---

# 4. Rollback Is Not Always Enough

Suppose your application deployment fails:

```text
v1.5.0
```

Easy:

```text
→ v1.4.3
```

But suppose the migration did:

```text
DELETE old_user_data
```

and the data is gone.

Rolling the application back:

```text
v1.5.0
 ↓
v1.4.3
```

doesn't restore the deleted data.

Therefore:

> **Application rollback and database recovery are different operations.**

---

# 5. Three Recovery Layers

Think about recovery in layers:

```text
Layer 1
Application rollback

Layer 2
Database recovery

Layer 3
Infrastructure recovery
```

Example:

```text
Bad application
    ↓
Rollback image
```

Database corruption:

```text
Corrupted DB
    ↓
Restore backup
```

Server destroyed:

```text
Server lost
    ↓
Recreate server
    ↓
Restore application
    ↓
Restore database
```

---

# 6. Known-Good Version

A rollback requires something important:

> **A known-good version.**

Suppose production history is:

```text
v1.3.0
v1.3.1
v1.4.0
v1.4.1
v1.4.2
v1.5.0 ❌
```

You need to know:

```text
v1.4.2 = last known-good
```

This is why we learned versioning.

---

# 7. Why Immutable Docker Images Help

Suppose:

```text
ghcr.io/rahul/api:v1.4.2
```

is immutable.

Then rollback can simply use:

```text
ghcr.io/rahul/api:v1.4.2
```

Instead of rebuilding old code.

Architecture:

```text
Production
   ↓
v1.5.0 ❌
   ↓
v1.4.2 🟢
```

This can be very fast.

---

# 8. Rollback With Blue-Green

This is where Lesson 12.13 becomes useful.

Suppose:

```text
BLUE = v1.4.2 🟢
GREEN = v1.5.0 🟡
```

Traffic:

```text
Nginx
 ↓
GREEN
```

Something breaks.

Switch:

```text
Nginx
 ↓
BLUE
```

Now:

```text
GREEN ❌
BLUE  🟢
```

This can be an extremely fast rollback.

---

# 9. Rollback With Docker Compose

Suppose your Compose file currently has:

```yaml
services:
  api:
    image: ghcr.io/rahul/my-api:v1.5.0
```

Change to:

```yaml
services:
  api:
    image: ghcr.io/rahul/my-api:v1.4.2
```

Then:

```bash
docker compose pull
docker compose up -d
```

Verify:

```bash
docker compose ps
```

and:

```bash
curl --fail https://example.com/api/health
```

---

# 10. Better: Versioned Deployment Configuration

Instead of manually editing production:

```text
.env
compose.yml
```

you can store deployment configuration in Git.

Example:

```text
deploy/
├── releases/
│   ├── v1.4.2.env
│   ├── v1.5.0.env
│   └── v1.5.1.env
```

Or maintain a deployment manifest.

Then:

```text
Current → v1.5.0
Previous → v1.4.2
```

Rollback becomes deterministic.

---

# 11. Automated Rollback

A deployment pipeline can implement:

```text
Deploy
 ↓
Health check
 ↓
PASS?
 ┌────┴────┐
YES       NO
 ↓         ↓
Success   Rollback
```

But health checks alone aren't enough.

A better system:

```text
Deploy
 ↓
Container health
 ↓
Smoke tests
 ↓
HTTP verification
 ↓
Monitor error rate
 ↓
Decision
```

---

# 12. Example Rollback Logic

Conceptually:

```bash
deploy_new_version

if ! health_check; then
    rollback
    exit 1
fi

if ! smoke_test; then
    rollback
    exit 1
fi
```

The important principle:

> **Failure must stop the pipeline instead of allowing a broken deployment to continue.**

---

# 13. Rollback Script

You could create:

```text
deployment/
├── deploy.sh
├── rollback.sh
└── health-check.sh
```

`rollback.sh` might conceptually:

```bash
#!/usr/bin/env bash

set -e

echo "Rolling back..."

# Restore previous application version
# Restart/update containers
# Verify health

echo "Rollback completed."
```

The exact commands depend on your deployment architecture.

---

# 14. Store the Previous Version

Your server should know:

```text
CURRENT_VERSION=v1.5.0
PREVIOUS_VERSION=v1.4.2
```

After a successful deployment:

```text
PREVIOUS = CURRENT
CURRENT = NEW
```

So:

```text
Before:
CURRENT  = v1.4.2
PREVIOUS = v1.4.1

After v1.5.0:
CURRENT  = v1.5.0
PREVIOUS = v1.4.2
```

Now rollback is straightforward.

# 15. Release History

Keep a deployment history:

```text
2026-08-10  v1.4.0
2026-08-12  v1.4.1
2026-08-13  v1.4.2
2026-08-15  v1.5.0
```

If:

```text
v1.5.0 ❌
```

you know:

```text
rollback → v1.4.2
```

---

# 16. Why Rollback Speed Matters

Suppose:

```text
Error rate = 80%
```

and it takes:

```text
30 minutes
```

to manually recover.

Users suffer for 30 minutes.

If automated rollback takes:

```text
30 seconds
```

the impact is dramatically reduced.

This is why:

> **Recovery should be automated whenever safely possible.**

---

# 17. What Is Disaster Recovery?

Disaster Recovery, or DR, is the process of restoring service after a major failure.

Imagine:

```text
Production Server
      💥
```

Your application, Nginx, Docker and local files may all be gone.

Now what?

A good DR system has:

```text
Infrastructure definition
+
Application artifacts
+
Database backups
+
Secrets recovery
+
Recovery procedures
```

---

# 18. Disaster Recovery Architecture

```text
                 Production
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
   Application    Database     Config
        │            │            │
        ↓            ↓            ↓
    Registry      Backups       Git
        │            │            │
        └────────────┼────────────┘
                     ↓
                Recovery
```

If production disappears, you reconstruct it from these sources.

---

# 19. Backup vs Disaster Recovery

A backup is:

> A copy of data.

Disaster recovery is:

> The complete process of restoring the service.

You need both.

Example:

```text
Backup exists
```

doesn't automatically mean:

```text
Application can be restored
```

You also need:

- Infrastructure
    
- Docker images
    
- Configuration
    
- Secrets
    
- DNS
    
- Certificates
    
- Database restoration procedure
    

---

# 20. The 3-2-1 Backup Rule

A traditional backup strategy is:

> **3 copies of data, 2 different storage/media types, 1 copy offsite.**

Example:

```text
Primary DB
   ↓
Backup #1 → server storage
Backup #2 → separate storage
Backup #3 → offsite/object storage
```

The exact implementation can vary, but the principle is valuable.

---

# 21. Why Offsite Backup Matters

Suppose:

```text
Server disk
 ↓
Database
 ↓
Backup
```

Then the server is destroyed.

Both are gone.

That's why:

```text
Production
   ↓
Offsite backup
```

is important.

Examples include:

- Object storage
    
- Separate backup server
    
- Cloud storage
    

---

# 22. What Should You Back Up?

For a MERN production system, think about:

```text
Database
Application data
Uploaded files
Configuration
Infrastructure definitions
Deployment metadata
```

You generally don't need to back up:

```text
Docker images
```

if they are safely stored in a registry and can be pulled again.

But you should ensure the registry artifacts remain available.

---

# 23. Don't Store Secrets in Git

Never treat:

```text
.env
```

containing production secrets as normal source code.

Instead use:

```text
GitHub Secrets
Secret manager
Server-side protected environment
```

For recovery, you need a secure way to retrieve those secrets.

---

# 24. Recovery Requires Secrets Too

Imagine:

```text
New server
 ↓
Docker
 ↓
Application
```

but:

```text
MONGODB_URI
JWT_SECRET
PAYMENT_SECRET
```

are missing.

Application cannot start correctly.

Therefore:

> **Secrets recovery is part of disaster recovery.**

---

# 25. RPO

Now we introduce two very important concepts.

### RPO — Recovery Point Objective

RPO answers:

> **How much data can we afford to lose?**

Example:

```text
RPO = 1 hour
```

means you might accept losing up to approximately one hour of data in the worst case.

---

# 26. RTO

### RTO — Recovery Time Objective

RTO answers:

> **How quickly must the service be restored?**

Example:

```text
RTO = 30 minutes
```

means your recovery target is to restore service within roughly 30 minutes.

---

# 27. RPO vs RTO

Remember:

```text
RPO
 ↓
How much data can I lose?

RTO
 ↓
How much time can I be down?
```

Example:

```text
RPO = 15 minutes
RTO = 30 minutes
```

means:

```text
Data loss target ≈ 15 min
Recovery time target ≈ 30 min
```

---

# 28. Why RPO Changes Architecture

Suppose:

```text
RPO = 24 hours
```

Daily backups might be sufficient.

But:

```text
RPO = 5 minutes
```

Daily backups are nowhere near enough.

You may need:

```text
Continuous replication
Frequent snapshots
Point-in-time recovery
```

Requirements drive architecture.

---

# 29. Why RTO Changes Architecture

Suppose:

```text
RTO = 24 hours
```

You can potentially rebuild infrastructure manually.

But:

```text
RTO = 5 minutes
```

manual recovery is probably too slow.

You may need:

```text
Automated infrastructure
Warm standby
Automated deployment
Fast database recovery
```

---

# 30. Backup Frequency

Suppose:

```text
Backup every 24 hours
```

Possible data loss:

```text
up to ~24 hours
```

If:

```text
Backup every 1 hour
```

potential loss:

```text
up to ~1 hour
```

This is a simplified model; actual recovery points depend on backup completion, replication, and failure timing.

---

# 31. Full vs Incremental Backup

### Full backup

Copies the entire dataset.

```text
Database
 ↓
Full copy
```

### Incremental backup

Copies changes since a previous backup.

```text
Full
 ↓
Changes
 ↓
Changes
 ↓
Changes
```

Incremental backups can reduce storage and backup time, but restoration may be more complex depending on the backup system.

---

# 32. Point-in-Time Recovery

Point-in-time recovery lets you restore the database to a particular moment.

For example:

```text
12:00
12:15
12:30
12:45
13:00
```

Suppose accidental deletion happened:

```text
12:47
```

You may restore to:

```text
12:46
```

instead of restoring the entire database to yesterday.

This can dramatically improve recovery options.

---

# 33. Backup Encryption

Production backups may contain:

```text
User data
Emails
Orders
Personal information
Application secrets
```

Backups should therefore be protected appropriately:

```text
Encryption at rest
Encryption in transit
Access control
Audit logging
```

A backup is another copy of your production data, so it needs security too.

---

# 34. Backup Access Control

Don't allow:

```text
Everyone
 ↓
Production backups
```

Prefer:

```text
Authorized recovery identity
        ↓
Backup storage
```

Principle:

> **Least privilege applies to backups too.**

---

# 35. Restore Testing

This is one of the most important ideas in this lesson:

> **A backup that has never been restored is not a proven backup.**

You should periodically test:

```text

 ↓
Restore
 ↓
Verify data
 ↓
Start application
 ↓
Run health checks
```

# 37. Recovery Is a Process

A real recovery plan should look like:

```text
1. Detect incident
2. Declare incident
3. Identify failure
4. Stop further damage
5. Select recovery strategy
6. Restore infrastructure
7. Restore data
8. Deploy application
9. Configure networking
10. Verify service
11. Monitor
12. Communicate

```

# 38. Incident Response

Disaster recovery connects to incident response.

Suppose:

```text
Production API returning 500s
```

First:

```text
Is this a bad deployment?
```

If yes:

```text
Rollback
```

If database corruption:

```text
Database recovery
```

If server destroyed:

```text
Infrastructure recovery
```

Correct diagnosis prevents the wrong recovery action.

---

# 39. Incident Severity

Not every incident needs the same response.

Example:

```text
P1
Complete production outage

P2
Major functionality broken

P3
Limited impact

P4
Minor issue
```

Your organization may use different naming.

The idea is:

> Prioritize recovery based on business impact.

---

# 40. Stop the Bleeding

During an incident, first prevent additional damage.

For example:

```text
Bad deployment
 ↓
Stop automatic deployments
```

or:

```text
Database corruption
 ↓
Stop destructive jobs
```

Don't blindly keep deploying while the system is unstable.

---

# 41. Rollback Decision

A simple decision tree:

```text
Production problem
       │
       ↓
Recent deployment?
   ┌───┴───┐
  YES      NO
   ↓        ↓
Rollback   Investigate
```

If rollback doesn't solve it:

```text
Database?
   ↓
Infrastructure?
   ↓
External dependency?
```

---

# 42. Automated Rollback Threshold

You can define:

```text
If:
error rate > 10%
for 5 minutes
```

then:

```text
Rollback
```

But don't blindly automate every threshold.

False positives can cause deployment flapping.

Automation should be based on reliable signals.

---

# 43. Health Check vs Business Health

A health endpoint:

```text
/health → 200
```

doesn't guarantee:

```text
Payments work
Orders work
Authentication works
```

Therefore advanced rollback systems may monitor:

```text
HTTP errors
Latency
Business errors
Dependency failures
```

This connects directly to your Observability module.

---

# 44. Rollback Safety

Before automatic rollback, ask:

```text
Is previous version compatible with current DB?
```

This is critical.

Suppose:

```text
Migration removed old field
```

and you deploy old application:

```text
v1.4
```

It may fail.

This is why:

> **Database compatibility determines whether application rollback is safe.**

---

# 45. The Expand-and-Contract Benefit

Recall Lesson 12.16.

If you use:

```text
Expand
 ↓
Compatible app
 ↓
Backfill
 ↓
Switch
 ↓
Contract later
```

then application rollback remains easier during the compatibility window.

This is another reason expand-and-contract is so powerful.

# 46. Rollback Matrix

For a release:

|Component|Current|Previous|Rollback|
|---|---|---|---|
|Backend|v1.5.0|v1.4.2|Easy|
|Frontend|v1.5.0|v1.4.2|Easy|
|Database|migration 28|migration 27|Depends|
|Nginx|config B|config A|Easy|
|Infrastructure|revision B|revision A|Depends|

Notice:

> **Not every component has the same rollback strategy.**

---

# 47. Database Rollback Difficulty

Application:

```text
v1.5 → v1.4
```

usually straightforward if the image exists.

Database:

```text
schema 28 → schema 27
```

may be difficult or impossible without data loss.

Therefore production systems often favor:

```text
Application rollback
+
Database roll-forward
```

rather than blindly rolling everything backward.

# 63. Failover vs Recovery

### Recovery

Restore the failed system.

```text
Server A fails
 ↓
Restore Server A
```

### Failover

Switch to another already-available system.

```text
Server A ❌
      ↓
Server B 🟢
```

Failover can be much faster.

But it usually costs more infrastructure.

---

# 64. Backup vs Replication

Don't confuse them.

### Backup

Historical copy:

```text
12:00 snapshot
13:00 snapshot
14:00 snapshot
```

### Replication

Copies current changes:

```text
Primary
  ↓
Replica
```

Replication helps availability.

Backups help recovery from:

- Accidental deletion
    
- Corruption
    
- Bad writes
    
- Historical recovery
    

A replica can also replicate bad data.

Therefore:

> **Replication is not a replacement for backups.**

# 73. Interview Questions

### Q1. What is rollback?

> Returning production to a previously known-good application version.

### Q2. What is disaster recovery?

> The process of restoring service after a major infrastructure, data, or system failure.

### Q3. What is RPO?

> Recovery Point Objective: the maximum acceptable amount of data loss measured in time.

### Q4. What is RTO?

> Recovery Time Objective: the target maximum time required to restore service.

### Q5. Why isn't a database rollback always possible?

> Destructive data changes may permanently remove information, making automatic reversal impossible.

### Q6. Why is roll-forward often safer?

> Instead of trying to reverse potentially destructive changes, a new migration can correct the problem while preserving data history.

### Q7. Why aren't replicas replacements for backups?

> A replica can copy corrupted or accidentally deleted data immediately; backups provide historical recovery points.

### Q8. Why should backups be tested?

> Because successful backup creation doesn't guarantee successful restoration.

### Q9. What is the 3-2-1 backup rule?

> Maintain three copies, on two different storage/media types, with at least one copy offsite.

### Q10. How does Blue-Green help rollback?

> The previous environment remains available, allowing traffic to be switched back quickly.

### Q11. What should happen if a health check fails after deployment?

> The deployment should stop and, when safe, rollback to the known-good version.

### Q12. Why is database compatibility important during rollback?

> The previous application version may depend on database structures that the new migration has already changed or removed.

# 🔑 Lesson 12.17 Takeaways

Remember these **25 points**:

1. **A production deployment system must have a recovery strategy.**
    
2. Rollback means returning to a known-good application version.
    
3. Disaster recovery handles larger failures.
    
4. Application rollback and database recovery are different.
    
5. Immutable Docker images make rollback easier.
    
6. Blue-Green deployments provide fast rollback.
    
7. Keep the previous production version available.
    
8. Automate health checks and smoke tests.
    
9. Failed deployments should stop the pipeline.
    
10. Don't automatically rollback databases without understanding the data impact.
    
11. Roll-forward is often safer for production data.
    
12. RPO measures acceptable data loss.
    
13. RTO measures acceptable recovery time.
    
14. Backups and replication are different.
    
15. Replication doesn't replace backups.
    
16. Follow the 3-2-1 backup principle where appropriate.
    
17. Keep at least one backup offsite.
    
18. Encrypt and restrict access to backups.
    
19. **Test restoration, not just backup creation.**
    
20. Recovery procedures should be documented as runbooks.
    
21. Infrastructure should be reproducible.
    
22. Secrets must have a secure recovery path.
    
23. Measure actual recovery time against your RTO.
    
24. Perform disaster recovery drills.
    
25. **The best recovery system is one you have already tested before the real incident.**
