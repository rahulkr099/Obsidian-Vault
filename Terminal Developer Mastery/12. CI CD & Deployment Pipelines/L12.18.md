
# 1. What Is Infrastructure as Code?

**Infrastructure as Code (IaC)** means managing infrastructure using configuration/code files instead of manually configuring everything.

Without IaC:

```text
Create server
   ↓
SSH
   ↓
Install Docker
   ↓
Install Nginx
   ↓
Configure firewall
   ↓
Create users
   ↓
Configure SSH
   ↓
Configure application
```

You might manually repeat these commands.

With IaC:

```text
Infrastructure code
        ↓
Automation tool
        ↓
Server
        ↓
Configuration
        ↓
Application
```

The infrastructure becomes reproducible.

---

# 2. The Problem With Manual Infrastructure

Imagine you manually configure:

```text
Server A
```

with:

```text
Docker
Nginx
UFW
SSH
Node
Monitoring
```

Then six months later you create:

```text
Server B
```

You might forget:

```text
One firewall rule
One Nginx setting
One security configuration
One package
```

Now:

```text
Server A ≠ Server B
```

This creates:

> **Configuration drift**

---

# 3. Configuration Drift

Configuration drift means:

> The actual infrastructure slowly becomes different from the intended configuration.

Example:

```text
Expected:

Docker = installed
Nginx = installed
UFW = enabled
SSH = hardened
```

Actual server:

```text
Docker = installed
Nginx = installed
UFW = disabled ❌
SSH = old configuration ❌
```

Over time:

```text
Expected ≠ Actual
```

IaC helps reduce this problem.

# 6. Imperative vs Declarative

This distinction is extremely important.

### Imperative

You say **how** to do something.

```bash
apt update
apt install nginx
systemctl enable nginx
systemctl start nginx
```

You're giving instructions.

### Declarative

You say **what** you want.

```text
Nginx should be installed and running.
```

The tool determines how to achieve that state.

# 10. Terraform Workflow

The common workflow is:

```bash
terraform init
terraform plan
terraform apply
```

Let's understand each.

---

# 11. `terraform init`

Run:

```bash
terraform init
```

This initializes the Terraform project.

It can:

- Download providers
    
- Initialize modules
    
- Prepare the working directory
    

Conceptually:

```text
Terraform code
      ↓
terraform init
      ↓
Terraform environment ready
```

---

# 12. `terraform plan`

Run:

```bash
terraform plan
```

Terraform compares:

```text
Desired state
      ↓
Actual state
```

and shows proposed changes.

For example:

```text
+ create server
+ create firewall
+ create network
```

This is very useful because you can review changes **before applying them**.

---

# 13. `terraform apply`

Then:

```bash
terraform apply
```

Terraform applies the changes.

Conceptually:

```text
plan
 ↓
review
 ↓
apply
 ↓
infrastructure created/updated
```

This is much safer than blindly changing production.

---

# 14. Terraform State

Terraform needs to know what it manages.

It maintains state.

Conceptually:

```text
Terraform Code
      +
Terraform State
      ↓
Actual Infrastructure
```

The state helps Terraform understand:

```text
What exists?
What changed?
What needs to be created?
What needs to be removed?
```

---

# 15. Terraform State Is Important

State can contain sensitive infrastructure information.

Therefore:

> **Don't casually commit Terraform state files to a public Git repository.**

For team environments, Terraform state is often stored remotely with appropriate locking and access control.

# 25. Idempotency in Ansible

Another extremely important concept:

> Running the same configuration multiple times should produce the same desired state without unnecessarily repeating destructive work.

For example:

```text
Install Docker
```

First run:

```text
Docker not installed
 ↓
Install
```

Second run:

```text
Docker already installed
 ↓
No unnecessary change
```

This is **idempotency**.

---

# 26. Why Idempotency Matters

Suppose:

```bash
ansible-playbook setup.yml
```

fails halfway.

You run it again.

You want:

```text
Already configured
 ↓
Skip
```

instead of:

```text
Duplicate configuration
Broken system
```

This is similar to the idempotent database migrations we discussed in Lesson 12.16.

# 49. State Locking

Imagine:

```text
Engineer A
terraform apply
```

and simultaneously:

```text
Engineer B
terraform apply
```

Without coordination:

```text
Race condition
```

State locking helps prevent concurrent conflicting operations.

This is another example of why production automation needs concurrency control.

# 79. Interview Questions

### Q1. What is Infrastructure as Code?

> Managing and provisioning infrastructure using version-controlled configuration/code rather than manual processes.

### Q2. What problem does IaC solve?

> It improves reproducibility, consistency, automation, auditing, and reduces configuration drift.

### Q3. What is Terraform?

> An infrastructure provisioning and management tool that allows infrastructure resources to be defined as code.

### Q4. What is Ansible?

> An automation and configuration-management tool used to configure and manage systems.

### Q5. Terraform vs Ansible?

> Terraform primarily provisions infrastructure; Ansible primarily configures machines and services.

### Q6. What is cloud-init?

> A system commonly used to perform initial configuration when a cloud server first boots.

### Q7. What is configuration drift?

> The difference that develops between the intended infrastructure configuration and the actual infrastructure.

### Q8. What is idempotency?

> Running the same automation repeatedly results in the desired state without unnecessary or harmful repeated changes.

### Q9. Why store IaC in Git?

> To provide version history, code review, auditing, collaboration, and reproducibility.

### Q10. Why is Terraform state important?

> It allows Terraform to track resources and determine what infrastructure changes are required.

### Q11. Why shouldn't Terraform state be publicly exposed?

> It can contain sensitive infrastructure information and sometimes sensitive values.

### Q12. What is immutable infrastructure?

> Infrastructure that is replaced rather than continuously modified in place.

# 🔑 Lesson 12.18 Takeaways

Remember these **25 points**:

1. **Infrastructure can be managed as code.**
    
2. IaC reduces manual configuration.
    
3. IaC improves reproducibility.
    
4. IaC reduces configuration drift.
    
5. Desired state is a central concept.
    
6. Declarative systems describe what should exist.
    
7. Terraform primarily manages infrastructure resources.
    
8. Ansible primarily manages machine configuration.
    
9. cloud-init is useful for first-boot initialization.
    
10. Terraform and Ansible solve different but complementary problems.
    
11. Docker packages and runs applications.
    
12. Docker Compose orchestrates multi-container applications on a host.
    
13. GitHub Actions automates CI/CD.
    
14. Infrastructure should be version-controlled.
    
15. Infrastructure changes should go through review.
    
16. `terraform plan` lets you inspect changes before applying them.
    
17. Terraform state must be protected.
    
18. State locking helps prevent conflicting operations.
    
19. Ansible should be designed to be idempotent.
    
20. Avoid mixing unmanaged manual changes with IaC-managed resources.
    
21. Modules and roles improve infrastructure organization.
    
22. Secrets should never be casually committed to Git.
    
23. IaC can dramatically improve disaster recovery.
    
24. Immutable infrastructure can reduce configuration drift.
    
25. **Treat infrastructure like production software: version it, review it, test it, secure it, and automate it.**
