# 2. CI/CD Pipeline Stages

A mature pipeline can be divided into:

```text
1. Source
2. CI
3. Build
4. Security
5. Package
6. Registry
7. Staging
8. Migration
9. Production
10. Verification
11. Monitoring
12. Rollback
```

Let's understand each.

---

# 3. Stage 1 — Source Control

Developer creates a feature:

```bash
git checkout -b feature/course-search
```

Works on code:

```text
React
Express
MongoDB
```

Then:

```bash
git add .
git commit -m "feat: add course search"
git push origin feature/course-search
```

GitHub receives the change.

---

# 4. Pull Request

The developer opens:

```text
feature/course-search
        ↓
Pull Request
        ↓
main
```

GitHub Actions automatically starts.

```text
PR
 ↓
CI
```

This is **Continuous Integration**.

---

# 5. Stage 2 — Install Dependencies

The pipeline first installs dependencies.

For Node.js:

```bash
npm ci
```

Why prefer:

```bash
npm ci
```

in CI?

Because it installs from the lockfile and is designed for clean, reproducible installs.

---

# 6. `npm install` vs `npm ci`

### Local development

```bash
npm install
```

is commonly used.

### CI

```bash
npm ci
```

is generally preferred when you have a lockfile.

Conceptually:

```text
package.json
     +
package-lock.json
     ↓
npm ci
     ↓
Exact dependency tree
```

```bash

```

```text

 ↓

```

```text
❌ Pipeline stops
```

# 8. Stage 4 — Tests

```bash

Potential tests:

```

Pipeline:

```text

 ↓
Lint
 ↓

```

# 9. Stage 5 — Build

Frontend:

```bash
npm run build
```

Backend might not require a traditional build if you're using plain JavaScript.

For TypeScript:

```bash
npm run build
```

produces:

```text
dist/
```

The pipeline verifies that production artifacts can actually be created.

# 10. Stage 6 — Security Scanning

Now scan dependencies.

For example:

```bash
npm audit
```

or dedicated security scanners.

You can also scan:

```text
Source code
Dependencies
Docker images
Secrets
Infrastructure
```

Pipeline:

```text

 ↓
Tests
 ↓
Security
```

---

# 11. Secret Detection

You don't want:

```text
MONGODB_URI=...
JWT_SECRET=...
RAZORPAY_SECRET=...
```

accidentally committed.

Secret scanning can detect suspicious credentials.

If detected:

```text
❌ CI fails
```

---

# 12. Stage 7 — Docker Build

Once CI passes:

```bash
docker build -t my-api .
```

But don't rely only on:

```text
latest
```

for production.

Instead use a version.

For example:

```text
v1.5.0
```

or:

```text
git SHA
```

---

# 13. Image Tags

A strong tagging strategy might be:

```text
my-api:v1.5.0
my-api:8f3a91c
```

Where:

```text
v1.5.0
```

is human-friendly and:

```text
8f3a91c
```

is tied directly to a Git commit.

This gives you traceability.

---

# 14. Why Git SHA Tags Are Useful

Suppose production runs:

```text
my-api:8f3a91c
```

You can ask:

```text
Which commit created this?
```

and trace it back to Git.

This creates:

```text
Git commit
 ↓
Docker image
 ↓
Deployment
```

Traceability is extremely valuable during incidents.

---

# 15. Stage 8 — Push to GHCR

Your pipeline authenticates to GitHub Container Registry.

Then:

```bash
docker push ghcr.io/username/my-api:v1.5.0
```

Now:

```text
GitHub
   ↓
GitHub Actions
   ↓
Docker
   ↓
GHCR
```

The image becomes a deployment artifact.

---

# 16. Artifact Immutability

Ideally:

```text
v1.5.0
```

should always mean:

```text
the same image
```

Don't rebuild different code under the same production tag.

This is why immutable image tags are valuable.

# 19. Why Staging Matters

Without staging:

```text
GitHub
 ↓
Production
```

A bug can immediately affect users.

With staging:

```text
GitHub
 ↓
CI
 ↓
Staging
 ↓
Verification
 ↓
Production
```

There is an additional safety barrier.

# 20. Stage 10 — Database Migration

Now run the migration.

For example:

```bash
npm run migrate
```

But remember Lesson 12.16:

```text
Migration strategy depends on the schema change.
```

For a backward-compatible migration:

```text
Migration
 ↓
Deploy
```

For complex changes:

```text

 ↓

 ↓

 ↓

```

# 21. Migration Failure

Suppose:

```text
Migration
   ↓
FAILED ❌
```

The pipeline should not continue blindly.

```text
Migration failed
       ↓
Stop deployment
       ↓
Investigate
```

This is why migration commands need correct exit codes.

# 22. Stage 11 — Health Checks

After deployment:

```bash
curl --fail https://api.example.com/health
```

Expected:

```text
HTTP 200
```

But remember:

```text
HTTP 200
≠

```

You may also check:

```text
Database connectivity
Redis

Critical endpoints
```

# 23. Smoke Tests

Smoke tests are quick tests that answer:

> **Does the deployed application basically work?**

Examples:

```text
GET /health
POST /auth/login
GET /courses
GET /users/me
```

You don't need to run every test again.

The goal is fast deployment verification.

---

# 24. Stage 12 — Production Approval

For an important production environment:

```text
Staging
 ↓
Tests pass
 ↓
Production approval
 ↓
Deploy
```

GitHub Actions environments can be configured with protection rules and required reviewers.

This creates a controlled production gate.

# 25. Production Deployment

Now:

```text
GHCR
 ↓
Production server
```

The server pulls:

```text
my-api:v1.5.0
```

Then Docker Compose starts the new version.

---

# 26. Zero-Downtime Deployment

We don't want:

```text
Old App
 ↓
STOP
 ↓
Users see downtime
 ↓
New App
```

Instead:

```text
Old App 🟢
     +
New App 🟢
     ↓
Health check
     ↓
Traffic switch
```

This is the basic idea behind Blue-Green deployment.

---

# 27. Blue-Green Example

Suppose:

```text
BLUE  = v1.4.2
GREEN = v1.5.0
```

Initially:

```text
Nginx
 ↓
BLUE
```

Deploy:

```text
GREEN
```

Then:

```text
GREEN
 ↓
Health check
 ↓
Smoke tests
```

If healthy:

```text
Nginx
 ↓
GREEN
```

---

# 28. Automatic Rollback

If:

```text
GREEN
 ↓
Health check ❌
```

then:

```text
Nginx
 ↓
BLUE
```

The user traffic never needs to stay on the broken version.

This is one of the strongest deployment patterns for minimizing downtime.

---

# 29. Stage 13 — Monitoring

Deployment doesn't end when the command succeeds.

After deployment:

```text
Deploy
 ↓
Monitor
```

Look at:

```text
Error rate
Latency
CPU
Memory
Database errors
HTTP 5xx
Container health
```

---

# 30. Deployment Verification Window

A useful pattern is:

```text
Deploy
 ↓
Health check
 ↓
Smoke test
 ↓
Monitor for short period
 ↓
Success
```

Why?

Because some bugs only appear under real traffic.

For example:

```text
Health = OK
```

but:

```text
POST /payment = 500
```

---

# 31. Deployment Notifications

At the end:

```text
Deployment successful
```

send a notification.

For example:

```text
🚀 Production Deployment

Version: v1.5.0
Commit: 8f3a91c
Status: SUCCESS
Environment: production
```

If failure:

```text
🚨 Deployment Failed

Version: v1.5.0
Status: ROLLED BACK
Reason: health check failed
```

This can integrate with your team's communication system.

# 33. GitHub Actions Workflow

A simplified workflow could look like:

```yaml
name: CI/CD

on:
  pull_request:
  push:
    branches:
      - main

jobs:

  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci

      - run: npm run lint

      - run: npm test

      - run: npm run build
```

This is your CI foundation.

---

# 34. Build Job

After tests:

```yaml
  build:
    needs: test
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Build Docker image
        run: |
          docker build \
            -t ghcr.io/example/my-api:${{ github.sha }} .
```

Notice:

```text
needs: test
```

This means:

```text
Tests
 ↓
Build
```

If tests fail:

```text
Build doesn't run.
```

---

# 35. Push Job

Conceptually:

```yaml
  push:
    needs: build
    runs-on: ubuntu-latest

    steps:
      - name: Login to GHCR
        ...

      - name: Push image
        run: |
          docker push \
            ghcr.io/example/my-api:${{ github.sha }}
```

Now:

```text
Test
 ↓
Build
 ↓
Push
```

---

# 36. Deploy Job

Conceptually:

```yaml
  deploy:
    needs: push
    runs-on: ubuntu-latest

    steps:
      - name: Deploy
        run: |
          ssh deploy@server \
            "/opt/app/deploy.sh ${{ github.sha }}"
```

The server executes:

```text
deploy.sh
```

with the exact image version.

---

# 37. Why SSH Deployment Can Be Useful

For your current Linux backend learning path, SSH deployment is excellent because you learn:

```text

Linux
Shell
Permissions
Nginx
Deployment scripts
```

all together.

Later, you can move toward more advanced orchestration.

# 38. Deployment Script

Your server might have:

```text
/opt/myapp/
├── compose.yml
├── .env
├── deploy.sh
├── rollback.sh
└── health-check.sh
```

`deploy.sh` receives:

```text
VERSION=v1.5.0
```

Then:

```text
Pull image
 ↓
Update deployment
 ↓
Start new container
 ↓
Health check
 ↓
Traffic switch
```

---

# 39. Example Deployment Logic

Conceptually:

```bash
#!/usr/bin/env bash

set -euo pipefail

VERSION="${1:?Version required}"

echo "Deploying ${VERSION}"

docker pull "ghcr.io/example/my-api:${VERSION}"

# Update deployment configuration
# Start new container
# Wait for health
# Switch traffic

echo "Deployment successful"
```

The important part is not the exact script.

It's the **deployment contract**:

```text
deploy.sh VERSION
```

---

# 40. Deployment Contract

Your deployment script should have predictable behavior:

```text
Input:
VERSION

Success:
exit 0

Failure:
exit non-zero
```

That lets GitHub Actions understand:

```text
Deployment succeeded
```

or:

```text
Deployment failed
```

---

# 41. Secrets

Your CI/CD pipeline may require:

```text
GHCR credentials
SSH private key
Server host
Server user
Production environment secrets
```

Never hardcode them:

```yaml
password: "my-secret"
```

Instead:

```yaml
password: ${{ secrets.GHCR_TOKEN }}
```

---

# 42. Environment Separation

You should have different environments:

```text
development
staging
production
```

with separate credentials where appropriate.

Example:

```text
STAGING_MONGODB_URI
PRODUCTION_MONGODB_URI
```

Don't let staging accidentally use production credentials.

---

# 43. Production Environment Protection

A production environment can require:

```text
Manual approval
Required reviewers
Environment-specific secrets
Deployment restrictions
```

So:

```text
main
 ↓
CI
 ↓
Staging
 ↓
Approval
 ↓
Production
```

becomes safer.

---

# 44. Concurrency Control

Imagine two commits arrive:

```text
v1.5.0
v1.5.1
```

at almost the same time.

You don't want:

```text
Deploy v1.5.0
+
Deploy v1.5.1
```

fighting each other.

Use deployment concurrency.

Conceptually:

```yaml
concurrency:
  group: production
  cancel-in-progress: false
```

Now production deployments are serialized.

---

# 45. Why `cancel-in-progress: false`?

Suppose:

```text
v1.5.0 deployment
```

is already running.

Then:

```text
v1.5.1
```

arrives.

You generally don't want to abruptly interrupt a production deployment without considering its current state.

Instead:

```text
v1.5.0
 ↓
complete
 ↓
v1.5.1
```

This is one possible safe strategy.

---

# 46. Artifact Promotion

A mature system may build an image once:

```text
Image
 ↓
Staging
 ↓
Production
```

rather than rebuilding separately.

Example:

```text
ghcr.io/example/api:8f3a91c
```

Staging tests it.

Then production deploys **the same image**.

This gives:

> **Build once, promote the same artifact.**

---

# 47. Why Rebuilding Is Dangerous

Suppose staging runs:

```text
image A
```

Production rebuilds from source:

```text
image B
```

Even though the Git commit is the same, environmental differences or dependency behavior could potentially produce differences.

Better:

```text
Build once
 ↓
Test artifact
 ↓
Promote same artifact
```

---

# 48. Database Migration Position

A mature pipeline should deliberately define:

```text
When does migration happen?
```

For a backward-compatible change:

```text
Build
 ↓
Migration
 ↓
Deploy
```

For expand-and-contract:

```text
Expand
 ↓
Compatible application
 ↓
Backfill
 ↓
Switch
 ↓
Contract
```

Never make this an accidental decision.

# 53. Security in the Pipeline

Your pipeline itself is an attack surface.

Protect:

```text
GitHub
GitHub Actions
GHCR
SSH
Deployment server
Secrets
```

Use:

```text
Least privilege
Short-lived credentials where possible
Protected branches
Required reviews
Secret scanning
Dependency scanning
Container scanning
```

---

# 54. Don't Give CI Unlimited Power

A dangerous design:

```text
GitHub Actions
      ↓
Root SSH access
      ↓
Production
```

If the CI credential is compromised, production could be compromised.

Prefer:

```text
GitHub Actions
      ↓
Restricted deploy identity
      ↓
Specific deployment permissions
```

This follows the principle of least privilege.

---

# 55. Production Deployment User

Instead of:

```text
root
```

use a dedicated user:

```text
deploy
```

with only the required permissions.

For example:

```text
deploy
 ↓
Docker deployment
 ↓
Application
```

and not unrestricted system administration.

Exact permissions depend on your deployment architecture.

---

# 56. SSH Security

Your deployment SSH access should ideally use:

```text
SSH key authentication
```

rather than passwords.

And:

```text
No password authentication
```

may be appropriate for hardened servers, depending on your access strategy.

You learned these concepts earlier in the SSH/security modules.

```bash

```

checks configuration syntax.

Then:

```bash

```

reloads configuration without unnecessarily stopping the service.

Afterward:

```bash
curl -I https://example.com
```

verifies HTTP behavior.

# 58. Docker Verification

After deployment:

```bash

```

Check:

```text

```

Then:

```bash

```

Inspect recent logs if needed.

# 72. Interview Questions

### Q1. Explain a production CI/CD pipeline.

A strong answer:

> Code is pushed to GitHub, CI runs linting, tests and security checks, a Docker image is built and published to a registry, the same artifact is deployed to staging, migrations and smoke tests are executed, production deployment requires appropriate approval, health checks verify the deployment, and failed releases can be rolled back to the previous known-good version.

---

### Q2. Why build Docker images in CI?

> To create a reproducible deployment artifact and keep the build process consistent.

---

### Q3. Why use immutable image tags?

> They allow you to identify exactly which artifact is running and make rollback deterministic.

---

### Q4. Why deploy to staging first?

> To validate the artifact and deployment process in an environment similar to production before exposing users to the change.

---

### Q5. What happens if a migration fails?

> The pipeline should stop or enter a controlled recovery path rather than continuing blindly.

---

### Q6. How do you achieve zero-downtime deployment?

> Use strategies such as rolling or Blue-Green deployment, health-check the new version, then gradually or atomically shift traffic.

---

### Q7. How would you automatically rollback?

> Deploy the new version, verify health and critical behavior, and if predefined failure conditions occur, switch traffic back to the previous known-good version.

---

### Q8. Why shouldn't you rebuild the Docker image for production after testing staging?

> The production artifact may differ from the tested artifact. A better pattern is to build once and promote the same immutable artifact.

---

### Q9. How do you secure a CI/CD pipeline?

> Protect secrets, use least-privilege credentials, protect production branches/environments, scan dependencies and images, restrict deployment access, and audit deployments.

---

### Q10. What is the difference between CI and CD?

> CI continuously integrates and validates code changes. CD automates delivering those validated changes toward production, either with an approval step or automatically.
