# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.2 — Git Workflow for Teams ⭐⭐⭐⭐⭐

Git is not just a tool for saving code.

In a professional team, Git becomes the **coordination system** through which developers safely work on the same codebase.

A good Git workflow answers questions like:

- Where should I create my branch?
    
- How do I submit my changes?
    
- When should code be reviewed?
    
- Who can merge into `main`?
    
- How do we handle conflicts?
    
- How do we release a version?
    
- What happens when production breaks?
    
- How do we deploy a hotfix?
    

---

# 1. Why Do Teams Need a Git Workflow?

Imagine five developers working directly on `main`:

```text
Developer A ─┐
Developer B ─┤
Developer C ─┼──→ main
Developer D ─┤
Developer E ─┘
```

Everyone is changing the same branch.

This creates problems:

```text
❌ Broken builds
❌ Accidental overwrites
❌ Difficult code reviews
❌ Merge conflicts
❌ Unclear ownership
❌ Production bugs
```

Instead, teams usually work with branches:

```text
                    main
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
      feature/A   feature/B   feature/C
          │           │           │
          └─────→ Pull Requests ←┘
                      │
                      ↓
                    main
```

---

# 2. The Main Branch

Most modern repositories have a protected branch such as:

```text
main
```

It represents the stable version of the project.

You generally **should not directly push** to it.

Instead:

```text
feature branch
      ↓
Pull Request
      ↓
Code Review
      ↓
CI checks
      ↓
Merge
      ↓
main
```

This creates a safety barrier.

---

# 3. Feature Branches

A feature branch is a separate branch where you work on one particular task.

For example:

```bash
git switch main
git pull origin main
git switch -c feature/user-authentication
```

Now:

```text
main
 │
 └── feature/user-authentication
```

You can safely work without modifying `main`.

---

# 4. Good Branch Naming

Use names that tell the team what the branch does.

### Features

```text
feature/user-authentication
feature/payment-integration
feature/course-search
```

### Bug fixes

```text
fix/login-error
fix/payment-timeout
fix/navbar-mobile
```

### Refactoring

```text
refactor/auth-service
refactor/database-repository
```

### Documentation

```text
docs/api-documentation
docs/setup-guide
```

### Performance

```text
perf/database-indexes
perf/api-response-time
```

A consistent naming convention makes repositories much easier to manage.

---

# 5. The Basic Feature Workflow

Suppose you need to add a password reset API.

Start from the latest `main`:

```bash
git switch main
git pull origin main
```

Create your branch:

```bash
git switch -c feature/password-reset
```

Work:

```bash
git add .
git commit -m "add password reset API"
```

Push:

```bash
git push -u origin feature/password-reset
```

Then open a Pull Request.

The workflow becomes:

```text
main
 ↓
create branch
 ↓
feature/password-reset
 ↓
write code
 ↓
commit
 ↓
push
 ↓
Pull Request
 ↓
CI
 ↓
Code Review
 ↓
Merge
 ↓
main
```

---

# 6. What Is a Pull Request?

A Pull Request, or **PR**, is a request to merge your changes into another branch.

For example:

```text
feature/password-reset
          ↓
       Pull Request
          ↓
         main
```

A PR gives the team a place to:

- Review code
    
- Discuss changes
    
- Run automated tests
    
- Check security
    
- Check formatting
    
- Approve or reject the change
    

---

# 7. Pull Requests and CI/CD

This is where Git workflow connects directly with the previous lesson.

When you open a PR:

```text
Pull Request
     ↓
GitHub Actions
     ↓
┌──────────────┐
│ Install      │
│ Lint         │
│ Test         │
│ Build        │
│ Security     │
└──────────────┘
     ↓
  All Passed
     ↓
Code Review
     ↓
Merge
```

This is a major professional workflow.

---

# 8. Branch Protection

A professional repository can protect `main`.

For example:

```text
main
 │
 ├── Direct push ❌
 ├── PR required ✅
 ├── CI required ✅
 ├── Review required ✅
 └── Branch must be up-to-date ✅
```

This prevents someone from accidentally doing:

```bash
git push origin main
```

and breaking production.

---

# 9. Code Review

Code review means another developer examines your changes before they are merged.

Suppose you changed:

```javascript
const user = await User.findById(id);
```

The reviewer might ask:

> Should this query use `.lean()` because the returned document isn't modified?

Or:

> Should this operation be moved into the service layer?

Or:

> What happens if the user doesn't exist?

Code review isn't only about finding syntax errors.

It helps improve:

- Architecture
    
- Security
    
- Performance
    
- Maintainability
    
- Readability
    
- Error handling
    

---

# 10. Good Pull Request Structure

A good PR should clearly explain:

### What changed?

```text
Added password reset functionality.
```

### Why?

```text
Users can now recover their accounts when they forget passwords.
```

### How?

```text
Added reset-token generation, expiry,
email delivery, and password update logic.
```

### Testing

```text
Added unit and integration tests.
```

### Screenshots

For frontend changes, screenshots can help.

---

# 11. Small PRs Are Better

Bad:

```text
PR #42

Changes:
- authentication
- payment
- dashboard
- database migration
- navbar
- logging
- Docker
- Nginx
```

That's extremely difficult to review.

Better:

```text
PR #42
Add password reset API
```

Then:

```text
PR #43
Add password reset UI
```

Then:

```text
PR #44
Add password reset email template
```

Smaller PRs are easier to:

- Review
    
- Test
    
- Understand
    
- Merge
    
- Revert

# 12. GitHub Flow

For many modern teams, **GitHub Flow** is a simple and effective workflow.

The model is:

```text
main
 │
 ├── feature branch
 │       ↓
 │    commits
 │       ↓
 │    Pull Request
 │       ↓
 │    CI + Review
 │       ↓
 └──── merge
        ↓
       main
        ↓
     deploy
```

Typical process:

```bash
git switch main
git pull

git switch -c feature/add-search

# work
git add .
git commit -m "add course search"

git push -u origin feature/add-search
```

Open PR → review → merge.

---

# 13. Why GitHub Flow Is Popular

It is simple.

You mainly have:

```text
main
feature/*
```

This works especially well for:

- Web applications
    
- SaaS products
    
- Startups
    
- Continuous deployment
    
- Small development teams
    

For your MERN projects, **GitHub Flow is a very good default workflow**.

---

# 14. Git Flow

Git Flow is a more structured branching model.

It commonly uses:

```text
main
develop
feature/*
release/*
hotfix/*
```

Diagram:

```text
                    main
                     ↑
                     │
                 release
                     ↑
                     │
develop ←────────────┘
   ↑
   │
feature/*
```

Hotfixes can branch from `main`:

```text
main
 │
 └── hotfix/payment-bug
          ↓
        main
```

---

# 15. Git Flow Branches

### `main`

Production-ready code.

```text
main → production
```

### `develop`

Integration branch for upcoming changes.

```text
feature/*
     ↓
 develop
```

### `feature/*`

Individual features.

```text
feature/auth
feature/payment
feature/search
```

### `release/*`

Preparation for a release.

```text
release/2.0.0
```

### `hotfix/*`

Emergency production fixes.

```text
hotfix/payment-crash
```

---

# 16. GitHub Flow vs Git Flow

This is important.

|GitHub Flow|Git Flow|
|---|---|
|Simple|More complex|
|`main` + feature branches|Multiple long-lived branches|
|Continuous delivery friendly|Release-cycle friendly|
|Great for web apps|Useful for scheduled releases|
|Fast development|More structured|
|Easier for small teams|More process-heavy|

For a modern MERN startup:

```text
GitHub Flow ⭐⭐⭐⭐⭐
```

is usually a better starting point.

You should still understand Git Flow because you'll encounter it in existing organizations.

---

# 17. Release Branches

Sometimes a team needs to prepare a specific release.

Example:

```text
main
 │
 └── release/2.5.0
```

The release branch might contain:

```text
Bug fixes
Documentation
Version updates
Final testing
```

Once ready:

```text
release/2.5.0
      ↓
    main
      ↓
Production
```

---

# 18. Semantic Versioning

Releases often use:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.4.1
```

Meaning:

```text
2 = MAJOR
4 = MINOR
1 = PATCH
```

We'll study SemVer properly in Lesson 12.15.

For now, remember:

```text
MAJOR → breaking changes
MINOR → new backward-compatible features
PATCH → bug fixes
```

# 19. Merge Conflicts

Now let's discuss one of the most common Git problems.

Suppose you modify:

```javascript
const port = 5000;
```

Developer B changes the same line:

```javascript
const port = 8000;
```

Now Git doesn't know which version should win.

You may see:

```text
<<<<<<< HEAD
const port = 5000;
=======
const port = 8000;
>>>>>>> feature/config
```

This is a **merge conflict**.

---

# 20. How to Resolve a Conflict

Suppose you're on:

```text
feature/payment
```

and `main` has changed.

First:

```bash
git fetch origin
```

Then update your branch:

```bash
git merge origin/main
```

Git may report:

```text
CONFLICT
```

Open the file and decide what the correct code should be.

For example:

```javascript
const port = process.env.PORT || 5000;
```

Then:

```bash
git add .
git commit
```

Finally:

```bash
git push
```

Your PR now contains the conflict resolution.

---

# 21. Merge vs Rebase

You will frequently hear:

```text
merge
```

and:

```text
rebase
```

### Merge

```text
A---B---C
     \
      D---E
           \
            M
```

Git creates a merge commit.

### Rebase

```text
A---B---C---D---E
```

Your commits are replayed on top of the latest base.

Rebase creates a cleaner linear history, but it rewrites commit history.

---

# 22. Simple Rule for Rebase

A good beginner rule:

> **Rebase your own local feature branch; don't casually rebase shared public branches.**

For example:

```bash
git switch feature/payment
git fetch origin
git rebase origin/main
```

Then you may need:

```bash
git push --force-with-lease
```

Notice:

```bash
--force-with-lease
```

rather than:

```bash
--force
```

`--force-with-lease` provides an important safety check.

---

# 23. Why `git push --force` Can Be Dangerous

Imagine:

```text
Developer A
   ↓
shared branch
```

Developer B also works on it.

Developer A executes:

```bash
git push --force
```

Their rewritten history can overwrite commits pushed by Developer B.

Potential result:

```text
Developer B's work
        ↓
      💥 lost
```

That's why force pushing should be used carefully.

# 24. Hotfixes

Now imagine production is broken.

Example:

```text
Production
    ↓
Payment API
    ↓
💥 500 errors
```

You don't want to wait for the next large release.

Create:

```bash
git switch main
git pull
git switch -c hotfix/payment-api
```

Fix the bug:

```bash
git add .
git commit -m "fix payment API failure"
git push -u origin hotfix/payment-api
```

Then:

```text
hotfix
   ↓
PR
   ↓
CI
   ↓
Review
   ↓
main
   ↓
Production
```

The key idea is:

> **A hotfix is a small, urgent change intended to restore production health.**

---

# 25. Hotfix + CI/CD

This becomes very powerful when connected to CI/CD.

```text
Production failure
        ↓
hotfix branch
        ↓
Pull Request
        ↓
Automated tests
        ↓
Code review
        ↓
Merge
        ↓
Automatic deployment
        ↓
Health check
        ↓
Production restored
```

Instead of manually editing files on the production server.

**Never treat production as a place where you casually edit source code.**

---

# 26. A Very Important Production Rule

Never do this:

```bash
ssh production-server

vim app.js

# manually modify production
```

This creates **configuration drift**.

Your Git repository says:

```text
Version A
```

but production is secretly:

```text
Version A + random manual changes
```

Now nobody knows exactly what is running.

Better:

```text
Git
 ↓
Pull Request
 ↓
CI
 ↓
Build
 ↓
Deploy
 ↓
Production
```

Production should be generated from a known version of your source/artifacts.

---

# 27. Commit Messages

Good commit messages are useful when investigating production problems.

Bad:

```bash
git commit -m "changes"
git commit -m "update"
git commit -m "fix"
```

Better:

```bash
git commit -m "add refresh token endpoint"
git commit -m "fix payment webhook validation"
git commit -m "add database health check"
```

A useful format is:

```text
<action> <what changed>
```

Examples:

```text
add user registration API
fix expired refresh token handling
refactor authentication service
update Docker health check
remove unused dependency
```

---

# 28. Conventional Commits

Some teams use:

```text
type(scope): description
```

Examples:

```text
feat(auth): add Google login
fix(payment): handle webhook timeout
refactor(user): simplify repository
docs(api): update authentication docs
test(auth): add refresh token tests
chore(deps): update Express
```

Common types:

```text
feat
fix
refactor
docs
test
chore
perf
ci
build
```

This becomes especially useful when automating releases and changelogs.

# 29. Recommended Workflow for Your MERN Projects

For your current stage, I recommend keeping things simple:

```text
main
 │
 ├── feature/*
 ├── fix/*
 ├── refactor/*
 └── hotfix/*
```

Workflow:

```text
1. Update main
2. Create branch
3. Implement one task
4. Commit
5. Push
6. Open PR
7. CI runs
8. Review
9. Merge
10. Deploy
```

Example:

```bash
git switch main
git pull origin main

git switch -c feature/course-search

# code...

git add .
git commit -m "feat(course): add course search"

git push -u origin feature/course-search
```

Then open the PR.

# 🧠 Interview Questions

### 1. Why shouldn't developers directly push to `main`?

Because protected branches + PRs + CI + code review reduce the chance of broken or unreviewed code reaching production.

---

### 2. What is a feature branch?

A temporary branch used to develop a specific feature independently from the main codebase.

---

### 3. What is a Pull Request?

A request to merge changes from one branch into another, usually accompanied by automated checks and code review.

---

### 4. GitHub Flow vs Git Flow?

**GitHub Flow** is simpler and works well with continuous delivery.

**Git Flow** has more branches and is useful for teams with structured release cycles.

---

### 5. What is a hotfix?

A small, urgent change used to fix a production problem.

---

### 6. Why are small PRs preferred?

They are easier to:

- Review
    
- Test
    
- Understand
    
- Merge
    
- Revert
    

---

### 7. Why shouldn't you manually modify production?

Because the changes won't necessarily exist in Git, creating configuration drift and making deployments difficult to reproduce.

# 🔑 Lesson 12.2 Takeaways

Remember these:

1. **Don't treat `main` as your personal development branch.**
    
2. Use **feature branches** for development.
    
3. Use **Pull Requests** for review and integration.
    
4. Run **CI checks before merging**.
    
5. Protect `main`.
    
6. Keep PRs small and focused.
    
7. Learn both **GitHub Flow** and **Git Flow**, but use the simpler workflow when appropriate.
    
8. Understand **merge conflicts and rebasing**.
    
9. Use **hotfix branches** for urgent production fixes.
    
10. Never casually edit source code directly on production.
    
11. Use meaningful commit messages.
    
12. Your Git workflow should eventually connect directly to your **CI/CD pipeline**.
    

### The professional mindset

```text
Don't think:

"I need to put my code on the server."

Think:

"I need to move a tested, versioned,
reproducible artifact safely into production."
```

That mindset is a big step from **junior developer → backend/DevOps engineer**.
