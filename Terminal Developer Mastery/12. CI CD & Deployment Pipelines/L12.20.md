# 7. Readiness vs Liveness

For a more advanced implementation:

```text
/health/live
```

means:

> Is the application process alive?

And:

```text
/health/ready
```

means:

> Is the application ready to serve traffic?

For example:

```text
/health/live
     ↓
Node process alive

/health/ready
     ↓
Node
 +
MongoDB
 +
Required dependencies
```

This becomes very useful for zero-downtime deployments.

# 8. Graceful Shutdown

Your Node.js server should handle:

```text
SIGTERM
SIGINT
```

Conceptually:

```javascript
process.on("SIGTERM", async () => {
  await server.close();
  await database.disconnect();
  process.exit(0);
});
```

The exact implementation should match your application.

Why?

During deployment:

```text
Old container
    ↓
SIGTERM
    ↓
Finish existing requests
    ↓
Close connections
    ↓
Exit
```

This helps prevent dropped requests.


# 28. Zero-Downtime Strategy

For your capstone, implement a simple Blue-Green architecture.

```text
                  Nginx
                    │
             ┌──────┴──────┐
             ↓             ↓
           BLUE          GREEN
          v1.4.2         v1.5.0
```

Initially:

```text
Nginx → BLUE
```

Deploy GREEN:

```text
Nginx → BLUE
            +
          GREEN
```

Check:

```text
GREEN → healthy
```

Then:

```text
Nginx → GREEN
```


# 41. Firewall

Only expose what is necessary.

Typical public services:

```text
22   SSH
80   HTTP
443  HTTPS
```

But SSH access should ideally be restricted appropriately, rather than left broadly exposed when your infrastructure allows tighter control.

Do not expose:

```text
MongoDB
Redis
Internal application ports
```

to the public internet unless there is a deliberate, secured reason.

# 64. What You Should Be Able to Explain

After completing this capstone, you should be able to answer:

### "How does your application reach production?"

You:

> Developer pushes code → GitHub Actions runs tests and security checks → Docker images are built → images are pushed to GHCR → the artifact is deployed to staging → migrations and smoke tests run → production approval happens → the same immutable image is deployed to production → health checks verify it → Nginx switches traffic → monitoring watches the release → failed deployments can roll back.

That's a **very strong interview answer**.

# 65. Another Interview Question

### "What happens if your deployment fails?"

You:

> The new version is health-checked before receiving production traffic. If health checks or smoke tests fail, the deployment is stopped. With Blue-Green deployment, traffic can be switched back to the previous known-good version. Database changes are handled separately using backward-compatible migration strategies, because application rollback doesn't necessarily mean database rollback.

That's the kind of answer that demonstrates actual engineering understanding.

---

# 66. Another Important Question

### "What happens if the entire server is destroyed?"

You:

> Infrastructure is reproducible through Terraform and Ansible/cloud-init, application artifacts are stored in GHCR, secrets have a secure recovery path, and database backups are stored separately. I can provision a replacement server, configure it, restore the database, deploy the known-good application image, configure Nginx and HTTPS, and run health checks. The recovery target is defined using RTO and RPO.

Excellent.

---

# 67. Another Interview Question

### "Why Docker?"

You:

> Docker creates a reproducible application artifact that packages the application and its runtime dependencies. The same image can be tested in CI, deployed to staging, and promoted to production, reducing environment differences.

---

# 68. Another Interview Question

### "Why Nginx?"

You:

> Nginx provides the public entry point for the application. It can terminate TLS, serve static React assets, reverse proxy API requests, perform traffic routing, and support deployment strategies such as Blue-Green switching.

---

# 69. Another Interview Question

### "Why Terraform?"

You:

> Terraform lets me define infrastructure declaratively and version it alongside the project. This improves reproducibility, reviewability, and disaster recovery while reducing configuration drift.

---

# 70. Another Interview Question

### "Why GitHub Actions?"

You:

> GitHub Actions allows CI/CD to run close to the source repository. I can automatically test pull requests, build immutable Docker artifacts, publish them to GHCR, deploy them to staging and production, perform health checks, and trigger controlled rollback workflows.

# 75. 🧠 Final 30 Concepts to Remember

If you remember only the most important things from this entire module:

1. CI validates changes.
    
2. CD delivers validated changes.
    
3. Git is the source of truth for application code.
    
4. Infrastructure should also be version-controlled.
    
5. Tests must run automatically.
    
6. Security scanning belongs in CI.
    
7. Build immutable artifacts.
    
8. Tag Docker images predictably.
    
9. Build once and promote the same artifact.
    
10. Store artifacts in a registry.
    
11. Staging reduces production risk.
    
12. Database migrations must be planned.
    
13. Never make destructive DB changes carelessly.
    
14. Health checks verify deployment state.
    
15. Smoke tests verify critical functionality.
    
16. Nginx manages public traffic.
    
17. HTTPS is mandatory for production web applications.
    
18. Zero-downtime deployments reduce user impact.
    
19. Keep a known-good version for rollback.
    
20. Application rollback isn't database rollback.
    
21. Backups aren't the same as replication.
    
22. Test restoration regularly.
    
23. RPO defines acceptable data loss.
    
24. RTO defines acceptable downtime.
    
25. Terraform manages infrastructure.
    
26. Ansible manages configuration.
    
27. cloud-init bootstraps machines.
    
28. Monitoring detects failures.
    
29. Runbooks make recovery repeatable.
    
30. **Production engineering is fundamentally about making systems predictable, observable, secure, and recoverable.**
