# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.4 — Automated Testing in CI ⭐⭐⭐⭐⭐

In the previous lesson, we learned how source code becomes a **build artifact**.

Now we need to answer an even more important question:

> **How do we know that the artifact is actually safe to deploy?**

The answer is **automated testing**.

A professional CI pipeline should not simply ask:

```text
"Does the code build?"
```

It should ask:

```text
"Does the code work correctly?"
"Did we break anything?"
"Does the API work?"
"Does the application behave correctly?"
"Is the build safe enough to deploy?"
```

That's where automated testing comes in.

---

# 1. What Is Automated Testing?

Automated testing means using software to automatically verify that your application behaves as expected.

Instead of manually checking:

```text
Open website
   ↓
Login
   ↓
Create course
   ↓
Edit course
   ↓
Delete course
   ↓
Logout
```

we can write tests that perform these checks automatically.

For example:

```text
Test
 ↓
POST /login
 ↓
Expected: 200
 ↓
PASS ✅
```

Then CI can execute those tests every time code changes.

---

# 2. Why Run Tests in CI?

Imagine you modify authentication:

```text
Developer changes login
        ↓
git push
        ↓
CI
        ↓
Tests
        ↓
❌ refresh token test failed
```

You discover the problem **before production**.

Without CI:

```text
Developer changes login
        ↓
git push
        ↓
Production
        ↓
Users report login is broken
        ↓
😰
```

The purpose of CI testing is therefore:

> **Catch regressions as early as possible.**

---

# 3. The Testing Pyramid

A useful model is the **testing pyramid**.

```text
             /\
            /  \
           / E2E\
          /------\
         /Integr. \
        /----------\
       /   Unit     \
      /--------------\
```

The bottom contains many fast tests.

The top contains fewer but slower tests.

Generally:

```text
Unit tests
    ↓
Integration tests
    ↓
E2E tests
```

The higher you go, the more expensive testing usually becomes.

---

# 4. Unit Tests

A unit test checks a small piece of functionality in isolation.

For example:

```javascript
function calculateTotal(price, quantity) {
  return price * quantity;
}
```

Test:

```javascript
expect(calculateTotal(100, 3)).toBe(300);
```

You're testing one small unit:

```text
calculateTotal()
```

Not the entire application.

---

# 5. Why Unit Tests Are Fast

A unit test might execute in milliseconds.

Imagine:

```text
100 unit tests
       ↓
0.5 seconds
```

That's excellent for CI.

You can run them on every:

```text
commit
push
pull request
```

without slowing developers down too much.

---

# 6. What Should Be Unit Tested?

For a Node.js backend, good candidates include:

### Utility functions

```text
hashPassword()
generateToken()
validateEmail()
calculatePrice()
formatDate()
```

### Business logic

```text
calculateOrderTotal()
checkCourseAccess()
calculateDiscount()
```

### Validation

```text
validateUserInput()
validatePassword()
```

For example:

```text
Input
 ↓
Service function
 ↓
Expected result
```

---

# 7. Integration Tests

Integration tests check whether multiple components work correctly together.

For example:

```text
API
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
```

You might test:

```http
POST /api/users
```

and verify:

```text
HTTP 201
User created
Database contains user
```

That's more realistic than a unit test.

---

# 8. Backend Integration Test Example

Imagine:

```http
POST /api/auth/register
```

Request:

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "StrongPassword123"
}
```

Your integration test might verify:

```text
Request
   ↓
Express
   ↓
Validation
   ↓
Controller
   ↓
Service
   ↓
MongoDB
   ↓
Response
```

Expected:

```text
201 Created
```

This gives you much stronger confidence than testing the service function alone.

---

# 9. Unit vs Integration Testing

|Unit|Integration|
|---|---|
|Small component|Multiple components|
|Usually isolated|Real interactions|
|Very fast|Slower|
|Easy to debug|More complex|
|Many tests|Fewer tests|
|No database usually|Database/API may be involved|

Think:

```text
Unit:
"Does this function work?"

Integration:
"Do these components work together?"
```

---

# 10. End-to-End Testing

E2E testing means testing the application from the user's perspective.

For a MERN application:

```text
Browser
   ↓
React
   ↓
Nginx
   ↓
Express API
   ↓
MongoDB
```

An E2E test might do:

```text
Open website
    ↓
Click Login
    ↓
Enter email
    ↓
Enter password
    ↓
Submit
    ↓
Dashboard appears
```

This tests the complete system.

---

# 11. E2E Tests Are Powerful but Expensive

Suppose you have:

```text
500 unit tests
50 integration tests
10 E2E tests
```

That can be a healthy balance.

Why not:

```text
560 E2E tests?
```

Because E2E tests are generally:

- Slower
    
- More fragile
    
- More expensive
    
- Harder to debug
    
- More dependent on infrastructure
    

So the testing pyramid encourages:

```text
Many unit tests
      ↓
Some integration tests
      ↓
Few E2E tests
```

---

# 12. Smoke Tests

A **smoke test** is a quick check that the application is fundamentally alive.

For example:

```bash
curl https://api.example.com/health
```

Expected:

```json
{
  "status": "ok"
}
```

If this fails:

```text
❌ Don't send traffic
```

Smoke tests are especially useful **after deployment**.

---

# 13. Smoke Test vs Health Check

These terms are related but can mean slightly different things.

### Health check

Usually answers:

> "Is this service healthy enough to run?"

Example:

```http
GET /health
```

### Smoke test

Usually answers:

> "Does the most basic functionality work?"

For example:

```http
GET /health
GET /api/courses
POST /api/auth/login
```

A deployment might perform:

```text
Container starts
    ↓
Health check
    ↓
Smoke test
    ↓
Traffic enabled
```

---

# 14. Test Coverage

Test coverage tells you how much of your code is exercised by tests.

For example:

```text
Statements: 92%
Branches:   84%
Functions:  95%
Lines:      91%
```

This sounds impressive.

But:

> **High coverage does not automatically mean high-quality tests.**

You could have:

```text
100% coverage
```

and still have terrible assertions.

---

# 15. Bad Test Coverage Thinking

Don't think:

> "I need 100% coverage."

Think:

> "I need strong tests for important behavior."

For example, payment code might deserve very strong testing:

```text
Payment success
Payment failure
Duplicate payment
Timeout
Webhook verification
Refund
```

while a trivial formatting function may need much less.

Coverage is a **signal**, not the final goal.

---

For your backend projects, prioritize:

### Authentication

```text

Login

Invalid token
Expired token
Unauthorized request
```

### Authorization

```text
User
Admin
Owner
Forbidden resource
```

### Payments

```text
Success
Failure
Duplicate request
Webhook
Refund
```

### Database

```text

Read
Update

```

### API validation

```text

```

These are more valuable than blindly chasing coverage numbers.

# 17. Test Execution in CI

A basic pipeline might look like:

```text
Git Push
   ↓
Install dependencies
   ↓
Lint
   ↓
Unit Tests
   ↓
Integration Tests
   ↓
Build
```

If unit tests fail:

```text
Unit Tests
    ↓
    ❌
    ↓
STOP
```

If integration tests fail:

```text
Integration Tests
       ↓
       ❌
       ↓
     STOP
```

Only successful builds should continue toward deployment.

---

# 18. Test Databases

Integration tests often need a database.

You should **not normally run your production database during CI tests**.

Instead:

```text
CI
 ↓
Temporary MongoDB
 ↓
Run tests
 ↓
Destroy database
```

For PostgreSQL:

```text
CI
 ↓
Temporary PostgreSQL
 ↓
Tests
 ↓
Destroy
```

For MongoDB, you can use a temporary test database or a dedicated CI database depending on your setup.

The important rule:

> **CI should never accidentally modify production data.**

---

# 19. Test Data

Suppose your integration test needs a user.

You could create:

```json
{
  "name": "Test User",
  "email": "test@example.com"
}
```

Then:

```text
Test
 ↓
Create test user
 ↓
Perform operation
 ↓
Verify result
 ↓
Clean up
```

Good tests should ideally be isolated.

Test A shouldn't depend on:

```text
Test B ran first
```

---

# 20. Test Isolation

Bad:

```text
Test A
 ↓
creates user

Test B
 ↓
expects user from Test A
```

If Test A fails:

```text
Test B
 ↓
also fails
```

Now debugging becomes difficult.

Better:

```text
Test A → own data
Test B → own data
Test C → own data
```

Each test should create the data it needs.

---

# 21. Environment Separation

You might have:

```text
Development
     ↓
dev database

CI
     ↓
test database

Staging
     ↓
staging database

Production
     ↓
production database
```

Never accidentally use:

```text
CI → production database
```

That's a serious operational mistake.

---

# 22. Test Secrets

Tests sometimes require credentials.

For example:

```text
TEST_DATABASE_URL
TEST_JWT_SECRET
TEST_API_KEY
```

These should be stored securely.

Later we'll use:

```text
GitHub Secrets
```

instead of:

```javascript
const secret = "my-secret";
```

# 23. Testing Pull Requests

One of the most useful CI workflows is:

```text
Developer
   ↓
Pull Request
   ↓
CI
   ├── Lint
   ├── Unit tests
   ├── Integration tests
   └── Build
        ↓
      PASS
        ↓
    Code Review
        ↓
      Merge
```

If tests fail:

```text
Pull Request
     ↓
CI
     ↓
❌ Failed
     ↓
Fix code
     ↓
Push again
     ↓
CI runs again
```

This is a very effective development loop.

# 24. Required CI Checks

You can configure GitHub so that certain checks are required before merging.

For example:

```text
Required checks:

✅ ESLint
✅ Unit Tests
✅ Integration Tests
✅ Build
```

If:

```text
Integration Tests ❌
```

then:

```text
Merge → BLOCKED
```

This is an important production safety mechanism.

---

# 25. Test Stages

You don't necessarily need every test on every event.

A practical strategy might be:

### Every Pull Request

```text
Lint
Unit tests
Build
```

### Main branch

```text
Lint
Unit tests
Integration tests
Build
Security checks
```

### Before production

```text
Integration
E2E
Smoke
Health checks
```

This balances speed and confidence.

---

# 26. Fast Feedback Matters

Imagine CI takes:

```text
30 seconds
```

Great.

Developer gets feedback quickly.

But if CI takes:

```text
45 minutes
```

developers may stop paying attention to failures.

So CI pipelines should be designed for **fast feedback**.

Typical optimization:

```text
Fast
 ↓
Lint
 ↓
Unit tests
 ↓
Build
 ↓
Slower
 ↓
Integration
 ↓
E2E
```

If linting already fails, there's no reason to run expensive E2E tests.

# 27. Parallel Tests

Some tests can run simultaneously.

Instead of:

```text
Unit tests
   ↓
Frontend tests
   ↓
Backend tests
   ↓
Lint
```

you could have:

```text
             ┌→ Backend tests ─┐
             │                 │
CI ──────────┼→ Frontend tests ┼→ Build
             │                 │
             └→ Lint ─────────┘
```

This can significantly reduce CI execution time.

GitHub Actions supports parallel jobs.

We'll use this concept in Lesson 12.7.

# 29. What Happens When a Test Fails?

Suppose:

```text
npm test

FAIL auth.test.js

Expected:
200

Received:
401
```

CI should report:

```text
❌ Tests failed
```

Then:

```text
Pull Request
     ↓
❌ CI failed
     ↓
Developer investigates
     ↓
Fix
     ↓
Push
     ↓
CI again
```

This is much better than discovering the bug after deployment.

---

# 30. Flaky Tests

A **flaky test** sometimes passes and sometimes fails without code changes.

Example:

```text
Run #1 → PASS
Run #2 → PASS
Run #3 → FAIL
Run #4 → PASS
```

This is dangerous.

Why?

Because developers may start thinking:

```text
"CI fails randomly; just rerun it."
```

Then real failures can be ignored.

Common causes:

- Timing issues
    
- Race conditions
    
- Shared state
    
- External services
    
- Network dependencies
    
- Incorrect test cleanup
    

A professional team should investigate flaky tests rather than endlessly rerunning them.

---

# 31. External Services in CI

Suppose your application uses:

```text
Stripe
MongoDB
Redis
Email service
```

Should every CI test call the real services?

Usually:

**No.**

You can use:

```text
Mocks
Stubs
Test containers
Dedicated test services
```

For example:

```text
Payment service
     ↓
Mock payment provider
```

This makes tests:

- Faster
    
- Cheaper
    
- More reliable
    
- Safer

# 32. Contract Testing

For larger systems, another useful concept is **contract testing**.

Imagine:

```text
Frontend
   ↓
API
```

Frontend expects:

```json
{
  "id": "123",
  "name": "Rahul"
}
```

But backend suddenly changes:

```json
{
  "userId": "123",
  "fullName": "Rahul"
}
```

The API technically works, but the frontend breaks.

Contract tests help verify that systems continue to agree on their interfaces.

This becomes more important in microservices and larger architectures.

# 36. CI Test Order

A good default order is:

```text
1. Install dependencies
        ↓
2. Lint
        ↓
3. Unit tests
        ↓
4. Integration tests
        ↓
5. Build
        ↓
6. Security checks
        ↓
7. Package artifact
```

But there isn't one universal order.

For example, some security scans can run in parallel.

The key principle is:

> **Run cheap, fast checks early and expensive checks later.**

# 38. Important Principle: Test Before Deploy

Never design your pipeline like:

```text
Build
 ↓
Deploy
 ↓
Test
```

unless you're talking about post-deployment smoke tests.

Your main validation should happen **before production deployment**:

```text
Code
 ↓
Test
 ↓
Build
 ↓
Deploy
```

Then you can additionally test production:

```text
Deploy
 ↓
Health check
 ↓
Smoke test
```

So you have both:

```text
Pre-deployment tests
+
Post-deployment verification
```

# 🧪 Mini Project — Add Testing to a MERN Backend

Take your Node/Express project and create at least these categories:

```text
tests/
├── unit/
│   └── auth.service.test.js
│
├── integration/
│   └── auth.api.test.js
│
└── smoke/
    └── health.test.js
```

You don't need to build everything at once.

Start with one unit test.

For example, if you have:

```javascript
function add(a, b) {
  return a + b;
}
```

write a test:

```javascript
test("adds two numbers", () => {
  expect(add(2, 3)).toBe(5);
});
```

Then make sure:

```bash
npm test
```

works locally.

The goal is to eventually reach:

```text
npm ci
   ↓
npm run lint
   ↓
npm test
   ↓
npm run build
```

That exact workflow will become automated in GitHub Actions.

# 🧠 Interview Questions

### Q1. What is the testing pyramid?

A model that recommends having many fast unit tests, fewer integration tests, and a smaller number of expensive E2E tests.

---

### Q2. Unit vs integration test?

**Unit test:**

> Tests a small isolated piece of code.

**Integration test:**

> Tests whether multiple components work together correctly.

---

### Q3. What is an E2E test?

> A test that verifies a complete user workflow across the application stack.

---

### Q4. What is a smoke test?

> A quick test that verifies the most basic functionality of an application, often immediately after deployment.

---

### Q5. Does 100% coverage mean the application is bug-free?

**No.**

Coverage measures how much code is exercised, not whether the tests properly verify the application's behavior.

---

### Q6. Why shouldn't CI use the production database?

Because tests could modify or destroy real production data.

---

### Q7. What is a flaky test?

A test that inconsistently passes or fails without corresponding code changes.

---

### Q8. Why run tests before deployment?

To prevent known-broken code from reaching production.

---

# 🔑 Lesson 12.4 Takeaways

Remember these **12 points**:

1. **Automated tests catch bugs before production.**
    
2. Unit tests are small and fast.
    
3. Integration tests verify component interactions.
    
4. E2E tests verify complete user workflows.
    
5. Smoke tests verify basic application health.
    
6. Use the **testing pyramid** rather than relying heavily on E2E tests.
    
7. Test important business behavior, not just code coverage.
    
8. Keep CI test environments separate from production.
    
9. Tests should be isolated and repeatable.
    
10. Flaky tests should be fixed rather than endlessly rerun.
    
11. Run fast tests early and expensive tests later.
    
12. Use both **pre-deployment testing** and **post-deployment health/smoke checks**.
