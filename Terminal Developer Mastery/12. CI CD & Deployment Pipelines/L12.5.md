# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.5 — Code Quality Automation ⭐⭐⭐⭐⭐

So far, our CI pipeline looks like:

```text
Git Push
   ↓
Install dependencies
   ↓
Lint
   ↓
Unit Tests
   ↓
Integration Tests
   ↓
Build
   ↓
Artifact
   ↓
Deploy
```

But there is another important question:

> **How do we automatically detect bad code, insecure dependencies, leaked secrets, and common programming mistakes before deployment?**

That's the job of **code quality automation**.

A professional CI pipeline should check more than:

```text
"Does the application run?"
```

It should also check:

```text
"Is the code clean?"
"Are there obvious bugs?"
"Are dependencies vulnerable?"
"Did someone accidentally commit a secret?"
"Are we violating project rules?"
```

---

# 1. What Is Code Quality Automation?

Code quality automation means using tools to automatically inspect your codebase.

Typical checks include:

```text
Source Code
    ↓
┌──────────────────────┐
│ ESLint               │
│ Prettier              │
│ Type checking         │
│ Static analysis       │
│ Dependency scanning   │
│ Secret detection      │
│ Security scanning     │
└───────────┬──────────┘
            ↓
        CI Result
```

If everything passes:

```text
✅ Quality checks passed
```

If something important fails:

```text
❌ Pipeline blocked
```

---

# 2. Why Automate Code Quality?

Imagine a team of 10 developers.

Without automation, someone might accidentally commit:

```javascript
console.log(user.password);
```

Another developer might write:

```javascript
if (user == null) {
```

Another might leave:

```javascript
const unusedVariable = "hello";
```

Another might accidentally commit:

```text
.env
```

with:

```text
DATABASE_PASSWORD=...
JWT_SECRET=...
```

Human code review can catch some of these.

Automation can catch many of them **consistently**.

---

# 3. ESLint

ESLint is one of the most important tools for JavaScript and TypeScript projects.

It analyzes source code and identifies:

- Potential bugs
    
- Bad patterns
    
- Unused variables
    
- Incorrect syntax patterns
    
- Style violations
    
- Problematic constructs
    

For example:

```javascript
const user = "Rahul";

console.log(user);

const unused = 123;
```

ESLint can detect that:

```text
unused
```

is never used.

---

# 4. ESLint in CI

Your `package.json` might contain:

```json
{
  "scripts": {
    "lint": "eslint ."
  }
}
```

Then locally:

```bash
npm run lint
```

CI can execute exactly the same command:

```bash
npm ci
npm run lint
```

If ESLint finds an error:

```text
❌ ESLint failed
```

CI stops.

---

# 5. Why the Same Command Matters

You don't want:

```text
Developer:
npm run lint

CI:
some completely different lint command
```

Instead:

```text
Developer
    ↓
npm run lint
    │
    └──────────────┐
                   ↓
                  CI
                   ↓
             npm run lint
```

This keeps local development and CI behavior aligned.

---

# 6. ESLint Rules

ESLint uses rules.

For example:

```javascript
const unused = 10;
```

A rule might say:

```text
no-unused-vars → error
```

Then:

```text
❌ unused is defined but never used
```

You can configure rules based on your project.

---

# 7. ESLint Configuration

Modern ESLint configurations can be defined using:

```text
eslint.config.js
```

For example, conceptually:

```javascript
export default [
  {
    rules: {
      "no-unused-vars": "error"
    }
  }
];
```

The exact configuration depends on your JavaScript/TypeScript setup.

The important concept is:

```text
Rules
  ↓
ESLint
  ↓
Code quality result
```

---

# 8. Errors vs Warnings

Quality tools often distinguish between:

```text
Warning
```

and:

```text
Error
```

For example:

```text
Unused variable → warning
Security violation → error
```

Your CI policy can decide which issues block the pipeline.

For critical issues:

```text
ERROR
  ↓
CI FAIL
```

This is important because not every warning should necessarily block every deployment.

---

# 9. Prettier

ESLint primarily focuses on code quality and rules.

**Prettier** focuses heavily on formatting.

For example, inconsistent code:

```javascript
const user={name:"Rahul",age:22};
```

Prettier might format it as:

```javascript
const user = {
  name: "Rahul",
  age: 22,
};
```

Now everyone on the team gets consistent formatting.

---

# 10. Why Formatting Matters

Imagine 20 developers all have different styles.

One writes:

```javascript
function login(user){return user.token}
```

Another:

```javascript
function login(user) {
  return user.token;
}
```

Another:

```javascript
function login(user)
{
    return user.token;
}
```

All may work.

But inconsistent formatting makes code reviews harder.

Prettier solves this automatically.

---

# 11. Prettier in CI

You can use a script such as:

```json
{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  }
}
```

Developers can format locally:

```bash
npm run format
```

CI can verify formatting:

```bash
npm run format:check
```

If someone commits poorly formatted code:

```text
❌ Formatting check failed
```

---

# 12. ESLint vs Prettier

A simple way to remember:

```text
ESLint
   ↓
"Is this code problematic?"

Prettier
   ↓
"Is this code consistently formatted?"
```

They solve different problems.

You can use both:

```text
ESLint
 +
Prettier
```

---

# 13. Type Checking

If you're using TypeScript, CI should also perform type checking.

For example:

```bash
npx tsc --noEmit
```

`--noEmit` means:

> Check the TypeScript code but don't generate JavaScript output.

Suppose:

```typescript
const age: number = "twenty";
```

TypeScript can detect:

```text
❌ Type 'string' is not assignable to type 'number'
```

CI should block the change.

---

# 14. Static Analysis

**Static analysis** means analyzing source code without executing the application.

For example:

```text
Source code
    ↓
Static analyzer
    ↓
Potential problems
```

It can detect things such as:

- Dangerous patterns
    
- Duplicated code
    
- Complex functions
    
- Unreachable code
    
- Potential bugs
    
- Security weaknesses
    

This is different from runtime testing.

---

# 15. Static Analysis vs Testing

### Static analysis

```text
Code
 ↓
Analyze
```

No application execution is required.

### Dynamic testing

```text
Code
 ↓
Run application/function
 ↓
Check behavior
```

Both are useful.

Think:

```text
Static analysis
     +
Automated tests
     =
Stronger CI
```

---

# 16. Code Complexity

Static analysis can also identify overly complicated code.

For example:

```javascript
function processOrder(order) {
  if (...) {
    if (...) {
      if (...) {
        if (...) {
          // lots of logic
        }
      }
    }
  }
}
```

This may technically work.

But high complexity makes code:

- Difficult to understand
    
- Difficult to test
    
- Difficult to maintain
    
- More likely to contain bugs
    

Quality tools can help identify such problems.

---

# 17. Dependency Vulnerability Scanning

Your application depends on packages:

```text
express
mongoose
jsonwebtoken
axios
cors
helmet
```

These packages can contain security vulnerabilities.

For example:

```text
Your application
      ↓
Dependency A
      ↓
Dependency B
      ↓
Vulnerable dependency
```

Even if **your code is secure**, a vulnerable dependency can create risk.

---

# 18. `npm audit`

For Node.js applications, you can use:

```bash
npm audit
```

It checks installed dependencies against known vulnerabilities.

You may see something like:

```text
found 2 vulnerabilities

1 moderate
1 high
```

This should be investigated.

---

# 19. Should Every `npm audit` Failure Block CI?

Not necessarily.

This is an important engineering decision.

Suppose:

```text
1 low severity vulnerability
```

Automatically blocking every deployment might create unnecessary noise.

But:

```text
Critical vulnerability
in production dependency
```

is much more serious.

A mature team defines a policy such as:

```text
Low       → monitor
Moderate  → review
High      → fix / approval
Critical  → block
```

The exact policy depends on the project.

---

# 20. Secret Detection

One of the most important CI security checks is **secret detection**.

Imagine someone commits:

```text
.env
```

containing:

```text
DATABASE_URL=mongodb+srv://...
JWT_SECRET=...
STRIPE_SECRET_KEY=...
```

Now the secret is in Git history.

Even if you delete the file later:

```text
git rm .env
```

the secret may still exist in previous commits.

That's why prevention is extremely important.

---

# 21. Common Secrets

Things you should protect include:

```text
API keys
Database passwords
JWT secrets
Cloud credentials
SSH private keys
OAuth client secrets
Payment provider secrets
Encryption keys
```

Never commit them directly.

---

# 22. `.gitignore`

A basic protection is:

```text
.env
.env.*
```

in:

```text
.gitignore
```

Then Git won't normally track those files.

But remember:

> `.gitignore` protects you from accidentally adding files; it doesn't remove secrets that are already tracked.

---

# 23. Secret Scanning

You can also use secret scanning tools.

Conceptually:

```text
Git Push
   ↓
Secret Scanner
   ↓
Search for API keys
Passwords
Tokens
Private keys
   ↓
❌ Secret detected
```

GitHub also provides secret scanning capabilities for supported repositories/plans.

We'll later connect this with GitHub Actions.

---

# 24. What If a Secret Is Detected?

Do **not** simply delete the line and continue.

If a real secret was exposed:

```text
Secret exposed
     ↓
Revoke / rotate secret
     ↓
Replace with new secret
     ↓
Remove exposed secret
     ↓
Review Git history if necessary
```

For example, if an API key is leaked:

```text
OLD_KEY
  ↓
REVOKE ❌
  ↓
NEW_KEY
  ↓
GitHub Secret
```

The old key should no longer be trusted.

---

# 25. SAST

**SAST** means:

> Static Application Security Testing.

It analyzes source code for potential security problems.

Conceptually:

```text
Source Code
     ↓
SAST
     ↓
Security Findings
```

It can detect patterns such as:

```text
SQL injection risks
Command injection
Unsafe data flow
Weak cryptography
Dangerous APIs
```

The exact findings depend on the tool and language.

---

# 26. SCA

Another term you'll hear is:

> **Software Composition Analysis (SCA)**

SCA focuses heavily on third-party dependencies.

Think:

```text
SAST
 ↓
Your source code

SCA
 ↓
Your dependencies
```

For example:

```text
express
mongoose
lodash
jsonwebtoken
     ↓
Dependency scanner
     ↓
Known vulnerabilities?
```

---

# 27. SAST vs SCA

|Tool type|Main target|
|---|---|
|ESLint|Code quality|
|Prettier|Formatting|
|TypeScript|Type correctness|
|SAST|Source-code security|
|SCA|Dependencies|
|Secret scanner|Credentials/secrets|
|Tests|Runtime behavior|

A mature pipeline can combine all of them.

---

# 28. Quality Gates

A **quality gate** is a condition that must pass before the pipeline continues.

For example:

```text
                    CI
                     ↓
             ┌──────────────┐
             │ Quality Gate │
             └──────┬───────┘
                    ↓
          ┌─────────┼─────────┐
          ↓         ↓         ↓
        Lint      Tests     Security
          │         │         │
          └─────────┼─────────┘
                    ↓
                 PASS?
                /     \
              YES      NO
               ↓        ↓
             Build     STOP
```

This is an extremely important CI/CD concept.

---

# 29. Example Quality Gate

You might define:

```text
Lint → must pass
Unit tests → must pass
Integration tests → must pass
Build → must pass
Critical vulnerabilities → zero
Secrets detected → zero
```

Then:

```text
Everything passes
       ↓
Build artifact
       ↓
Deploy
```

But:

```text
Critical vulnerability
       ↓
STOP
```

---

# 30. Quality Gates Should Be Practical

Don't create impossible rules.

Bad:

```text
100% test coverage
0 warnings
0 dependencies with any vulnerability
Every line perfectly formatted
```

You may end up with:

```text
Developer
   ↓
CI
   ↓
❌
❌
❌
❌
```

and developers start bypassing the system.

Instead, use meaningful thresholds.

For example:

```text
Tests → required
Build → required
Critical security issues → required
Secret detection → required
Coverage → reasonable threshold
Warnings → manageable
```

The goal is to make the pipeline **useful**, not annoying.

---

# 31. Pre-Commit vs CI Checks

Some checks can run before a commit.

For example:

```text
Developer
   ↓
git commit
   ↓
pre-commit hook
   ├── format
   ├── lint
   └── quick tests
```

Then CI runs the complete validation:

```text
Push
 ↓
CI
 ├── lint
 ├── tests
 ├── integration
 ├── security
 └── build
```

Why run checks twice?

Because local checks improve developer experience, while CI provides the **trusted final gate**.

A developer could bypass local hooks.

They should not be able to bypass required CI checks.

---

# 32. Husky

For JavaScript projects, a popular approach is **Husky** for Git hooks.

Conceptually:

```text
git commit
     ↓
Husky
     ↓
lint / format / tests
     ↓
PASS → commit
FAIL → commit blocked
```

This is useful, but don't rely on hooks as your only protection.

The authoritative checks should still happen in CI.

A good pipeline might look like:

```text
                   Git Push
                      ↓
                Install deps
                      ↓
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       ESLint      Prettier    Type Check

          └───────────┼───────────┘

                      ↓
```

This is becoming a real production CI pipeline.

# 34. Example for Your MERN Backend

Suppose your project has:

```text
backend/
├── src/
├── tests/
├── package.json
├── package-lock.json
└── eslint.config.js
```

Your scripts could eventually look like:

```json
{
  "scripts": {
    "dev": "nodemon src/server.js",
    "start": "node src/server.js",
    "lint": "eslint .",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "test": "jest",
    "test:coverage": "jest --coverage"
  }
}
```

Then CI can run:

```bash
npm ci
npm run format:check
npm run lint
npm test
npm audit
```

Eventually:

```text
npm ci
   ↓
format check
   ↓
lint
   ↓
tests
   ↓
security scan
   ↓
build
```

---

# 35. A Note About `npm audit fix`

You may see advice like:

```bash
npm audit fix
```

Be careful.

It can update dependencies.

That might introduce breaking changes.

Don't blindly execute:

```bash
npm audit fix --force
```

in a production project.

Instead:

```text
Vulnerability
    ↓
Understand affected package
    ↓
Check severity
    ↓
Check available fix
    ↓
Update dependency
    ↓
Run tests
    ↓
Review
```

Security updates still need normal engineering discipline.

---

# 36. Dependency Pinning

You should also understand dependency versions.

For example:

```json
"express": "^5.1.0"
```

The lockfile controls the exact installed version.

CI:

```bash
npm ci
```

helps ensure the lockfile is respected.

For Docker base images, versioning is also important.

Instead of blindly using:

```dockerfile
FROM node:latest
```

you can use a more controlled version:

```dockerfile
FROM node:22
```

and, when stricter reproducibility is needed, pin even more precisely.

---

# 37. Don't Ignore CI Warnings

One dangerous team culture is:

```text
CI:
⚠️ Warning
⚠️ Warning
⚠️ Warning
⚠️ Warning
```

Eventually everyone ignores warnings.

Then:

```text
Real security problem
       ↓
⚠️
       ↓
Ignored
```

So teams should regularly clean up warnings and maintain a healthy signal-to-noise ratio.

---

# 38. Code Quality as a Team Contract

Quality automation is not about punishing developers.

It's about creating consistent engineering standards.

For example:

```text
Team agrees:

✓ Code must pass lint
✓ Code must be formatted
✓ Tests must pass
✓ Critical vulnerabilities block merge
✓ Secrets are forbidden
✓ Build must succeed
```

Now developers don't need to argue about these things during every PR.

The tools enforce the agreement.

Think of each tool as answering a different question:

```text

"Is the code problematic?"

Prettier
"Is the formatting consistent?"

TypeScript
"Are the types correct?"

Tests
"Does the application behave correctly?"

SAST
"Does the source contain security problems?"
```

Together:

```text
              Code
                ↓
```

# 🧠 Interview Questions

### Q1. What is ESLint?

> ESLint is a static analysis tool for JavaScript and TypeScript that identifies problematic code patterns and enforces configurable coding rules.

### Q2. ESLint vs Prettier?

> ESLint primarily analyzes code quality and coding rules, while Prettier primarily handles consistent formatting.

### Q3. What is SAST?

> Static Application Security Testing analyzes source code for potential security vulnerabilities without executing the application.

### Q4. What is SCA?

> Software Composition Analysis checks third-party dependencies for known vulnerabilities and licensing or dependency risks.

### Q5. Why is secret scanning important?

> It helps detect accidentally committed credentials such as API keys, passwords, tokens, and private keys before they are used or exposed further.

### Q6. Should every vulnerability block deployment?

**Not necessarily.**

Teams should define severity-based policies.

For example:

```text
Critical → block
High → investigate / usually block
Moderate → review
Low → monitor
```

The exact policy depends on risk.

### Q7. What is a quality gate?

> A set of automated conditions that must pass before a pipeline is allowed to continue.

# 🔑 Lesson 12.5 Takeaways

Remember these **12 points**:

1. **Code quality automation makes engineering standards enforceable.**
    
2. ESLint detects problematic JavaScript/TypeScript patterns.
    
3. Prettier keeps formatting consistent.
    
4. TypeScript can catch type errors before runtime.
    
5. Static analysis examines code without executing it.
    
6. Dependency scanning identifies vulnerable third-party packages.
    
7. Secret scanning helps prevent credentials from entering the repository.
    
8. SAST focuses on source-code security.
    
9. SCA focuses heavily on third-party dependencies.
    
10. A **quality gate** determines whether CI can continue.
    
11. Local checks improve developer experience, but **CI is the trusted gate**.
    
12. Security tools should reduce risk without creating so much noise that developers start ignoring them.
