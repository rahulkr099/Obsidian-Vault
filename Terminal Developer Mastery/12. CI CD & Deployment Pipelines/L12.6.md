# 1. What Is GitHub Actions?

GitHub Actions is GitHub's built-in automation platform.

It allows you to automatically run tasks when something happens in your repository.

For example:

```text
Developer pushes code
        ↓
GitHub detects push
        ↓
GitHub Actions starts
        ↓
Install dependencies
        ↓
Run tests
        ↓
Build
        ↓
Result
```

You can also trigger workflows when:

- A Pull Request is opened
    
- Code is pushed
    
- A release is created
    
- A tag is pushed
    
- A schedule occurs
    
- A workflow is manually started

# 3. Workflow

A **workflow** is an automated process.

Example:

```text
CI Workflow
```

It might perform:

```text
Install
 ↓
Lint
 ↓
Test
 ↓
Build
```

Workflow files live inside:

```text
.github/workflows/
```

For example:

```text
.github/
└── workflows/
    └── ci.yml
```

---

# 4. Your First Workflow

Create:

```bash
mkdir -p .github/workflows
```

Then:

```bash
vim .github/workflows/ci.yml
```

Put:

```yaml
name: CI

on:
  push:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
```

Commit it:

```bash
git add .github/workflows/ci.yml
git commit -m "ci: add GitHub Actions workflow"
git push
```

Now GitHub will execute the workflow.

🎉 You have created your first CI pipeline.

You can allow a workflow to be manually started.

```yaml

  workflow_dispatch:
```

```text

```


# 10. Scheduled Workflows

GitHub Actions also supports schedules.

For example:

```yaml
on:
  schedule:
    - cron: "0 0 * * *"
```

This means the workflow is scheduled to run at a specific UTC time.

Possible uses:

```text
Dependency checks
Maintenance
Reports
Automated cleanup
```

Be careful with scheduled workflows because GitHub Actions cron uses **UTC**.

---

# 11. Jobs

A workflow contains one or more **jobs**.

Example:

```yaml
jobs:
  test:
```

Here:

```text
test
```

is the job ID.

A workflow can have:

```text
jobs:
  test:
  build:
  deploy:
```

Conceptually:

```text
Workflow
 ├── test
 ├── build
 └── deploy
```

---

# 12. Runner

Every job needs a machine on which it runs.

For example:

```yaml
runs-on: ubuntu-latest
```

This tells GitHub:

> Run this job on a GitHub-hosted Ubuntu runner.

Conceptually:

```text
GitHub
   ↓
Create temporary Ubuntu machine
   ↓
Run job
   ↓
Destroy machine
```

This is important.

Your CI runner is generally a **fresh environment**, not your personal Linux machine.

---

# 13. Why Clean Runners Are Useful

Suppose your laptop has:

```text
Node.js
Docker
MongoDB
Redis
random global npm packages
```

Your code might work because your machine happens to have everything configured.

CI starts clean.

```text
Fresh Ubuntu
     ↓
Install exactly what workflow specifies
     ↓
Run application
```

If your project works there, you gain more confidence that it isn't depending on hidden local configuration.

---

# 14. Steps

A job contains steps.

Example:

```yaml
steps:
  - name: Checkout code
    uses: actions/checkout@v4

  - name: Setup Node.js
    uses: actions/setup-node@v4

  - name: Install dependencies
    run: npm ci

  - name: Run tests
    run: npm test
```

A job might look like:

```text
Job
 │
 ├── Step 1 → checkout
 ├── Step 2 → setup Node
 ├── Step 3 → npm ci
 └── Step 4 → npm test
```

By default, steps execute sequentially.

---

# 15. `run` vs `uses`

This is one of the most important things to understand.

### `run`

Executes a shell command.

Example:

```yaml
- name: Install dependencies
  run: npm ci
```

Equivalent to running:

```bash
npm ci
```

---

### `uses`

Uses an existing GitHub Action.

Example:

```yaml
- name: Checkout
  uses: actions/checkout@v4
```

Instead of writing all the Git checkout logic yourself, you use a reusable Action.

Think:

```text
run
 ↓
"My command"

uses
 ↓
"Someone already packaged this automation"
```

# 17. The Checkout Action

This:

```yaml
- uses: actions/checkout@v4
```

checks out your repository into the runner.

Without it, your workflow runner doesn't automatically have your repository source code available in the normal workflow workspace.

Think:

```text
GitHub Repository
       ↓
actions/checkout
       ↓
Runner workspace
       ↓
Your files
```

Now commands like:

```bash
npm ci
```

can operate on your project.

---

# 18. Setup Node.js

Use:

```yaml
- name: Setup Node.js
  uses: actions/setup-node@v4
  with:
    node-version: 22
```

Now the runner has Node.js 22 available.

This is much better than assuming:

```text
"Whatever Node version happens to be installed."
```

You explicitly define your runtime.

---

# 19. `with`

The `with` section provides inputs to an Action.

Example:

```yaml
with:
  node-version: 22
```

Think:

```text
Action
 ↓
Configuration
 ↓
with:
```

For example:

```yaml
with:
  node-version: 22
  cache: npm
```

This can configure Node setup and dependency caching.

# 20. A Better Node CI Workflow

Suppose:

```yaml

  run: npm test
```

```text

```

The step fails.

Usually the subsequent steps won't run.

For example:

```text

Build          ⏭️

```

This is exactly what we want.

# 24. Job Dependencies

Sometimes jobs need to execute in a specific order.

For example:

```text
test
  ↓
build
  ↓
deploy
```

You can express that with:

```yaml
needs:
```

Example:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: npm run build
```

Now:

```text
test
 ↓
PASS
 ↓
build
```

If tests fail:

```text
test ❌
  ↓
build skipped
```

---

# 25. Multiple Dependencies

You can have:

```yaml
deploy:
  needs:
    - test
    - build
```

Meaning:

```text
test ────┐
         ├──→ deploy
build ───┘
```

Deployment waits for both.

# 30. Action Versions

You may see:

```yaml
uses: actions/checkout@v4
```

The `@v4` specifies the Action version.

Don't casually use:

```yaml
uses: actions/checkout@main
```

because the referenced code could change unexpectedly.

For stronger supply-chain security, some organizations pin Actions to specific commit SHAs.

For example, conceptually:

```text
Action
 ↓
Specific immutable commit
```

This reduces the risk of unexpected changes.

# 33. A Complete Basic CI Workflow

Here's a good starting workflow for a Node.js backend:

```yaml
name: Backend CI

on:
  pull_request:
    branches:
      - main

  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Check formatting
        run: npm run format:check

      - name: Run lint
        run: npm run lint

      - name: Run tests
        run: npm test

      - name: Build application
        run: npm run build
```

This gives you:

```text
Pull Request / Push
        ↓
Checkout
        ↓
Node 22
        ↓
npm ci
        ↓
Formatting
        ↓
Lint
        ↓
Tests
        ↓
Build
```

That's a genuine CI pipeline.

# 38. Common Beginner Mistakes

### Mistake 1 — Wrong YAML indentation

YAML depends heavily on indentation.

Bad:

```yaml
jobs:
test:
runs-on: ubuntu-latest
```

Correct:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
```

---

### Mistake 2 — Wrong Node version

Your project might require Node 22 but CI uses another version.

Explicitly configure it.

---

### Mistake 3 — Forgetting `npm ci`

Using:

```bash
npm install
```

can produce different dependency behavior.

Prefer:

```bash
npm ci
```

in CI.

---

### Mistake 4 — Storing secrets in YAML

Never:

```yaml
env:
  JWT_SECRET: my-secret
```

We'll learn the correct approach in Lesson 12.8.

---

### Mistake 5 — Giving too many permissions

Don't give:

```text
write-all
```

when the workflow only needs:

```text
contents: read
```

Follow least privilege.

# 🧠 Interview Questions

### Q1. What is GitHub Actions?

> GitHub Actions is a CI/CD automation platform integrated into GitHub that executes workflows in response to repository events or schedules.

### Q2. What is a workflow?

> A YAML-defined automation process containing jobs and steps.

### Q3. What is a runner?

> The machine/environment where a GitHub Actions job executes.

### Q4. Difference between `run` and `uses`?

> `run` executes shell commands, while `uses` invokes a reusable GitHub Action.

### Q5. What is `needs`?

> `needs` defines dependencies between jobs, allowing one job to wait for another to complete successfully.

### Q6. Why use `actions/checkout`?

> It checks the repository's source code into the runner workspace so subsequent steps can operate on it.

### Q7. Why specify Node.js version?

> To make the CI environment predictable and avoid differences between the developer's environment and the CI environment.

### Q8. Why shouldn't Actions have unnecessary permissions?

> Because excessive permissions increase the potential impact if a workflow or dependency is compromised.

# 🔑 Lesson 12.6 Takeaways

Remember these:

1. **GitHub Actions automates CI/CD directly inside GitHub.**
    
2. A **workflow** defines an automated process.
    
3. An **event** determines when the workflow starts.
    
4. A **job** is a group of related steps.
    
5. A **runner** executes the job.
    
6. A **step** performs an individual operation.
    
7. `run:` executes shell commands.
    
8. `uses:` executes a reusable Action.
    
9. `needs:` controls dependencies between jobs.
    
10. `actions/checkout` gets your repository onto the runner.
    
11. `actions/setup-node` gives CI a predictable Node.js environment.
    
12. Keep workflow permissions as small as possible.
    
13. CI should run automatically on Pull Requests.
    
14. Failed CI checks should prevent unsafe code from reaching `main`.
