## Lesson 12.7 — Building CI Pipelines ⭐⭐⭐⭐⭐

In Lesson 12.6, you created your first GitHub Actions workflow.

Now we're going to move from:

```text
Simple CI
   ↓
npm ci
   ↓
npm test
```

to a more professional pipeline:

```text
                    Pull Request
                         ↓
                ┌────────────────┐
                │ GitHub Actions │
                └───────┬────────┘
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
           Quality              Tests
              ↓                   ↓
          Lint/Format       Unit/Integration
              │                   │

                        ↓
                      Build
                        ↓
                    Artifact
                        ↓

```

We'll learn how to make CI **faster, safer, and easier to maintain**.

---

# 1. What Makes a Good CI Pipeline?

A beginner might create:

```text
Install
 ↓
Test
 ↓
Lint
 ↓
Build
```

That works.

But a professional pipeline should also consider:

- Speed
    
- Parallel execution
    
- Caching
    
- Dependency management
    
- Build verification
    
- Artifacts
    
- Failure handling
    
- Matrix testing
    
- Job dependencies
    
- Security
    
- Clear logs
    

The goal isn't simply:

> "Make CI run."

The goal is:

> **Build a reliable automated verification system that gives developers fast feedback.**

---

# 2. A Basic CI Pipeline

Let's start with:

```yaml
name: CI

on:
  pull_request:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - run: npm ci
      - run: npm test
```

Pipeline:

```text
Checkout
   ↓
Node
   ↓
Install
   ↓
Tests
```

Simple, but we can improve it.

---

# 3. Add Code Quality

From Lesson 12.5:

```text
Formatting
Linting
Type checking
Testing
```

So:

```yaml
- name: Check formatting
  run: npm run format:check
```

Now:

```text
Install

Format
 ↓
Lint
 ↓

```

# 4. Add Build Verification

Tests passing doesn't necessarily mean your production build works.

Suppose:

```text
Unit tests → ✅
```

but:

```bash
npm run build
```

fails.

You want to know that **before deployment**.

So add:

```yaml
- name: Build application
  run: npm run build
```

Now:

```text
Install
 ↓
Format
 ↓
Lint
 ↓
Tests
 ↓
Build
```

# 5. Quality Pipeline

Your pipeline is becoming:

```text
                   CI
                    │
                    ↓
              npm ci
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
       Format      Lint     Typecheck
          └─────────┼─────────┘
                    ↓
                  Tests
                    ↓
                  Build
                    ↓
                 SUCCESS
```

That's already a solid CI foundation.

# 6. Sequential vs Parallel Jobs

Now an important optimization.

Suppose:

```text
Lint → 20 seconds
Tests → 60 seconds
```

If they run sequentially:

```text
Lint
 ↓
20 sec
 ↓
Tests
 ↓
60 sec

Total ≈ 80 sec
```

If they're independent:

```text
        ┌→ Lint ─────┐
CI ─────┤             ├→ Build
        └→ Tests ────┘
```

They can run in parallel:

```text
max(20, 60) ≈ 60 sec
```

You save time.

---

# 7. Separate Jobs

Example:

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run lint

  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm test
```

Now:

```text
           CI
            │
       ┌────┴────┐
       ↓         ↓
     lint       test
```

These jobs can run simultaneously.

---

# 8. But There's a Tradeoff

Parallel jobs are faster.

But each job gets its own runner.

That means:

```text
lint runner
   ↓
npm ci

test runner
   ↓
npm ci
```

Dependencies may be installed twice.

So you trade:

```text
Speed
  vs
Resource usage
```

For many projects, the speed improvement is worth it.

---

# 9. Dependency Caching

One of the easiest optimizations is caching dependencies.

With `setup-node`:

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: npm
```

GitHub can cache npm-related data.

Conceptually:

```text
First CI run
   ↓
Download dependencies
   ↓
Create cache
```

Next run:

```text
CI
 ↓
Restore cache
 ↓
Faster dependency setup
```

Caching can significantly improve CI speed.

---

# 10. Cache ≠ Source of Truth

Remember:

> **A cache is an optimization, not a dependency source of truth.**

Your real dependency definition remains:

```text
package.json
package-lock.json
```

If the cache disappears:

```text
No cache
 ↓
npm ci
 ↓
Download dependencies
 ↓
Continue
```

Your pipeline should still work.

---

# 11. Build Artifacts

Now let's say:

```bash
npm run build
```

produces:

```text
dist/
```

You can upload that directory as an artifact.

GitHub provides an artifact action such as:

```yaml
- name: Upload build artifact
  uses: actions/upload-artifact@v4
  with:
    name: frontend-build
    path: dist/
```

Now:

```text
Build
 ↓
dist/
 ↓
Upload Artifact
 ↓
GitHub
```

---

# 12. Why Artifacts Matter

Artifacts are useful for:

- Build outputs
    
- Coverage reports
    
- Test results
    
- Debugging files
    
- Deployment packages
    

For example:

```text
CI
 ↓
Build
 ↓
frontend-dist.zip
```

Another job can consume that artifact later.

---

# 13. Artifact vs Docker Image

These are related but different.

### Artifact

Generic build output:

```text
dist/
coverage/
app.tar.gz
```

### Docker image

A packaged runtime environment:

```text
my-api:abc123
```

For your backend deployment, the Docker image will eventually become the primary deployment artifact.

---

# 14. Job Dependencies with `needs`

Suppose you have:

```text
lint
test
   ↓
build
```

Build should only happen if both pass.

Use:

```yaml
build:
  needs:
    - lint
    - test
```

Now:

```text
lint ────┐
         ├──→ build
test ────┘
```

If either fails:

```text
lint ✅
test ❌
 ↓
build skipped
```

This is exactly what we want.

# 15. A Professional Job Graph

Your workflow can become:

```text
                    CI
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
        lint                   test
          │                     │
          └──────────┬──────────┘
                     ↓
                   build
                     ↓
                 artifact
```

This is called a **job dependency graph**.

Thinking in graphs is useful when designing CI/CD pipelines.

# 16. Matrix Builds

Now imagine your application supports:

```text
Node 20
Node 22
Node 24
```

You could create separate jobs manually.

But GitHub Actions supports a **matrix strategy**.

Example:

```yaml
strategy:
  matrix:
    node-version: [20, 22, 24]
```

Then:

```yaml
uses: actions/setup-node@v4
with:
  node-version: ${{ matrix.node-version }}
```

GitHub creates:

```text
             test
               │
       ┌───────┼───────┐
       ↓       ↓       ↓
     Node20  Node22  Node24
       ↓       ↓       ↓
     Tests   Tests   Tests
```

---

# 17. Why Matrix Testing Is Useful

It helps when your software supports multiple environments.

Examples:

```text
Node versions
Python versions
Operating systems
Database versions
Browser versions
```

For example:

```yaml
matrix:
  os:
    - ubuntu-latest
    - windows-latest
  node-version:
    - 22
```

Could produce:

```text
Ubuntu + Node 22
Windows + Node 22
```

---

# 18. Don't Use Huge Matrices Without Reason

Imagine:

```text
3 OS
×
4 Node versions
×
3 database versions
```

That's:

```text
3 × 4 × 3 = 36 combinations
```

CI can become expensive and slow.

Use matrix testing where compatibility actually matters.

For your MERN projects:

```text
Node 22
+
ubuntu-latest
```

may be completely sufficient.

---

# 19. Conditional Steps

Sometimes a step should only run under certain conditions.

For example:

```text
Pull Request
 ↓
Test
```

but:

```text
main
 ↓
Test
 ↓
Build Docker image
```

You can use conditions.

For example:

```yaml
if: github.ref == 'refs/heads/main'
```

Then that step only runs on `main`.

# 20. PR vs Main Pipelines

A good strategy is:

### Pull Request

```text

 ↓

 ↓

```

### Main

```text

 ↓

 ↓

 ↓
```

```text

```

Very clean.

# 21. Don't Deploy From Every Branch

Imagine:

```text
feature/auth
feature/payment
feature/search
feature/admin
```

If every push automatically deploys to production:

```text
feature/auth
     ↓
Production 💥
```

Instead:

```text
feature/*
    ↓
CI only

main
 ↓
CI
 ↓
CD
 ↓
Production
```

That's much safer.

You may eventually have:

```text

 ↓

 ↓

 ↓
```

```yaml

  needs: staging
```

Conceptually:

```text

 ↓

```

# 23. Failure Handling

Suppose:

```text
lint → PASS
test → PASS
build → FAIL
```

Then:

```text
deploy → SKIPPED
```

That's good.

We don't want:

```text
build ❌
   ↓
deploy 🚀
   ↓
Production 💥
```

CI should be designed to **fail safely**.

---

# 24. Timeouts

A workflow shouldn't run forever.

Imagine:

```text
Integration test
   ↓
hangs
   ↓
20 minutes
   ↓
still running
```

You can define job timeouts.

Conceptually:

```yaml
timeout-minutes: 10
```

Now:

```text
10 minutes
 ↓
Job automatically stops
```

This is especially useful for tests and deployment jobs.

---

# 25. Concurrency

Suppose a developer pushes three commits quickly:

```text
commit A
commit B
commit C
```

Now you may have:

```text
CI A → running
CI B → running
CI C → running
```

Sometimes you don't need all three runs to finish.

GitHub Actions supports concurrency controls.

Conceptually:

```text
New workflow
   ↓
Cancel obsolete workflow
   ↓
Run latest
```

This can save CI resources.

---

# 26. Example Concurrency

A typical pattern is:

```yaml
concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

Meaning:

> If a newer run starts for the same workflow/ref, cancel the older one.

This is particularly useful for Pull Requests where developers push several updates.

# 29. Reusing Dependencies Between Jobs

One challenge with parallel jobs is:

```text
lint runner
 ↓
npm ci

test runner
 ↓
npm ci
```

Each runner is isolated.

You can use caching:

```text
npm cache
    ↓
shared cache mechanism
```

But don't assume the `node_modules` directory itself should always be passed between jobs.

In many cases, using the package manager's cache is cleaner.

# 30. Build Once

Suppose you have:

```text
build
```

and later:

```text
deploy
```

Ideally:

```text
build
  ↓
artifact
  ↓
deploy
```

Don't rebuild unnecessarily:

```text
build
 ↓
staging

build AGAIN
 ↓
production
```

Instead:

```text
one artifact
 ↓
staging
 ↓
production
```

This is the **build once, deploy many** principle from Lesson 12.3.

# 33. Pipeline Optimization

A good CI pipeline should follow:

```text
FAST CHECKS
    ↓
EXPENSIVE CHECKS
    ↓
BUILD
    ↓
PACKAGE
    ↓
DEPLOY
```

For example:

```text
Format
 ↓
Lint
 ↓
Unit Tests
 ↓
Integration Tests
 ↓
Build
 ↓
Docker Build
 ↓
Security Scan
 ↓
Deploy
```

Some independent steps can run in parallel.

---

# 34. Example Professional Pipeline

Here's a useful structure:

```yaml
name: CI

on:
  pull_request:
    branches:
      - main

permissions:
  contents: read

jobs:
  quality:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run format:check
      - run: npm run lint

  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm test

  build:
    needs:
      - quality
      - test

    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run build

      - name: Upload build
        uses: actions/upload-artifact@v4
        with:
          name: build
          path: dist/
```

The graph:

```text
             Pull Request
                  ↓
        ┌─────────┴─────────┐
        ↓                   ↓
     quality               test
        │                   │
        └─────────┬─────────┘
                  ↓
                build
                  ↓
               artifact
```

That's a very good CI architecture.

# 35. Important: Duplicate Dependency Installation

You may notice:

```text
quality → npm ci
test    → npm ci
build   → npm ci
```

Yes, that's normal when jobs use separate runners.

You can optimize further with caching or restructuring jobs.

But don't sacrifice isolation just to avoid a small amount of installation time.

**Reliable CI is more important than premature optimization.**

# 🧪 Mini Project — Build Your Professional CI

For one of your MERN projects, create:

```text
.github/
└── workflows/
    └── ci.yml
```

Start with:

```yaml
name: CI

on:
  pull_request:
    branches:
      - main

  push:
    branches:
      - main

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  quality:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install
        run: npm ci

      - name: Format check
        run: npm run format:check

      - name: Lint
        run: npm run lint

  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install
        run: npm ci

      - name: Test
        run: npm test

  build:
    needs:
      - quality
      - test

    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install
        run: npm ci

      - name: Build
        run: npm run build
```

If your project doesn't have:

```text
npm run format:check
npm run lint
npm test
npm run build
```

yet, adapt the commands to your actual project.

The important thing is the architecture:

```text
             quality
                │
                │
             test
                │
         ┌──────┴──────┐
         ↓             ↓
       PASS           PASS
         └──────┬──────┘
                ↓
              build
```

# 🧠 Interview Questions

### Q1. Why use multiple jobs?

To separate responsibilities and allow independent work to run in parallel.

### Q2. What does `needs` do?

It defines job dependencies.

```text
test
 ↓
build
```

### Q3. What is a matrix build?

It runs the same job against multiple configurations, such as Node.js versions or operating systems.

### Q4. Why use caching?

To reduce repeated dependency downloads and speed up CI.

### Q5. What is an artifact?

A file or package produced by CI that can be stored or passed to later stages.

### Q6. Why use `concurrency`?

To prevent unnecessary duplicate workflow runs, especially when developers push multiple commits quickly.

### Q7. Why shouldn't every branch deploy to production?

Because feature branches are still under development. Production deployment should normally be restricted to trusted branches or controlled release workflows.

### Q8. Why should CI jobs be isolated?

Isolation makes builds more reproducible and prevents one job's environment from accidentally affecting another.

# 🔑 Lesson 12.7 Takeaways

Remember these **12 points**:

1. A good CI pipeline should be **fast, reliable, and reproducible**.
    
2. Independent jobs can run in parallel.
    
3. `needs` creates dependencies between jobs.
    
4. Cache dependencies to reduce CI time.
    
5. Cache is an optimization, not the source of truth.
    
6. Upload important build/test outputs as artifacts.
    
7. Matrix builds test multiple supported environments.
    
8. Don't create unnecessarily huge matrices.
    
9. Use conditions to control when expensive operations run.
    
10. Use concurrency to cancel obsolete runs when appropriate.
    
11. **Build once, deploy the same artifact** whenever possible.
    
12. Treat your CI workflow itself as security-sensitive infrastructure.
