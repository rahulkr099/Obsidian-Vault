# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.8 — Secrets & Environment Variables ⭐⭐⭐⭐⭐

This is one of the **most important security lessons** in the entire CI/CD module.

By now, your pipeline can:

```text
Git Push
   ↓
GitHub Actions
   ↓
Lint
   ↓
Tests
   ↓
Build
```

Soon, it will also:

```text
Docker Build
   ↓
Push Image
   ↓
SSH
   ↓
Production Server
```

But now we have a problem:

> **How does GitHub Actions securely access databases, APIs, SSH servers, Docker registries, and other protected resources without putting passwords and private keys inside Git?**

That's what this lesson solves.

---

# 1. What Is a Secret?

A secret is sensitive information that should not be exposed publicly.

Examples:

```text
DATABASE_URL
DATABASE_PASSWORD
JWT_SECRET
STRIPE_SECRET_KEY
AWS_SECRET_ACCESS_KEY
SSH_PRIVATE_KEY
GHCR_TOKEN
API_KEY
```

For example:

```text
MONGODB_URI=mongodb+srv://user:password@...
```

This is sensitive.

You should **never** commit it to Git.

---

# 2. The Golden Rule

Remember this:

> **Source code can be public. Secrets should not be.**

Bad:

```javascript
const JWT_SECRET = "my-super-secret-key";
```

Bad:

```yaml
env:
  DATABASE_PASSWORD: "mypassword"
```

Bad:

```text
.env
```

committed to Git.

Better:

```javascript
const JWT_SECRET = process.env.JWT_SECRET;
```

And provide the value securely through the environment.

---

# 3. Environment Variables

An environment variable is a value supplied to the application through its environment.

Example:

```bash
export PORT=5000
```

Your Node.js application can read:

```javascript
process.env.PORT
```

Another example:

```bash
export NODE_ENV=production
```

Then:

```javascript
process.env.NODE_ENV
```

---

# 4. Why Environment Variables?

They allow the same application code to work in different environments.

```text
             Same Code
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
 Development  Staging  Production
       │         │         │
     config    config    config
```

For example:

```text
Development
DATABASE_URL → localhost

Staging
DATABASE_URL → staging database

Production
DATABASE_URL → production database
```

The code doesn't need to change.

---

# 5. `.env` Files

Locally, developers commonly use:

```text
.env
```

Example:

```text
PORT=5000
DATABASE_URL=mongodb://localhost:27017/myapp
JWT_SECRET=development-secret
```

Node.js can load these values using a package such as `dotenv`, or through the runtime/tooling environment.

But:

> **`.env` files containing secrets should normally not be committed to Git.**

---

# 6. `.gitignore`

Add:

```text
.env
.env.*
```

to:

```text
.gitignore
```

Then:

```bash
git status
```

should not show your local `.env` as an untracked file.

---

# 7. Important `.gitignore` Trap

Suppose you already committed:

```text
.env
```

Then later add:

```text
.env
```

to `.gitignore`.

That does **not** remove the file from Git tracking.

You must first remove it from tracking:

```bash
git rm --cached .env
```

Then:

```bash
git commit -m "chore: stop tracking env file"
```

But there's a bigger issue.

If the secret was already pushed:

> **Assume the secret is compromised and rotate it.**

---

# 8. Secret Rotation

Suppose you accidentally publish:

```text
STRIPE_SECRET_KEY=old_secret
```

Deleting the file is not enough.

Do:

```text
Secret exposed
     ↓
Revoke old secret
     ↓
Generate new secret
     ↓
Update secret storage
     ↓
Deploy new configuration
```

The old credential should no longer work.

This principle applies to:

- API keys
    
- Database passwords
    
- SSH keys
    
- OAuth secrets
    
- Cloud credentials
    

---

# 9. GitHub Secrets

GitHub provides secure storage for secrets used by Actions.

Conceptually:

```text
GitHub Repository
      │
      └── Secrets
            │
            ├── DATABASE_URL
            ├── JWT_SECRET
            ├── SSH_PRIVATE_KEY
            └── API_KEY
```

Your workflow can then reference a secret.

Example:

```yaml
env:
  DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

The actual value doesn't need to appear in the YAML file.

---

# 10. Repository Secrets

Repository secrets are associated with a repository.

For example:

```text
Repository
    ↓
Settings
    ↓
Secrets and variables
    ↓
Actions
```

You can store:

```text
DATABASE_URL
JWT_SECRET
SSH_PRIVATE_KEY
```

Then workflows can use them.

---

# 11. Secrets vs Variables

GitHub Actions has both:

```text
Secrets
Variables
```

Use **Secrets** for sensitive values.

Examples:

```text
Passwords
Tokens
Private keys
API secrets
```

Use regular **Variables** for values that aren't sensitive.

Examples:

```text
NODE_VERSION=22
APP_NAME=my-api
DEPLOY_HOST=example.com
```

Though whether a hostname is sensitive depends on your environment.

The rule is:

> **If leaking the value could help an attacker, treat it as sensitive.**

---

# 12. Secret vs Environment Variable

These are related but not identical concepts.

### Environment variable

A mechanism for providing configuration:

```text
KEY=value
```

### Secret

Sensitive data that needs protected storage and controlled access.

So:

```text
Secret
  ↓
GitHub Secret Store
  ↓
Environment Variable
  ↓
Application
```

A secret can ultimately be exposed to a process as an environment variable.

---

# 13. Workflow Example

Suppose your application needs:

```text
DATABASE_URL
JWT_SECRET
```

Your workflow could have:

```yaml
- name: Run tests
  run: npm test
  env:
    DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
    JWT_SECRET: ${{ secrets.TEST_JWT_SECRET }}
```

Notice something important:

We're using:

```text
TEST_DATABASE_URL
```

rather than:

```text
PRODUCTION_DATABASE_URL
```

CI tests should generally use a test environment.

---

# 14. Never Give CI Production Secrets Unnecessarily

Bad architecture:

```text
Pull Request
     ↓
GitHub Actions
     ↓
PRODUCTION_DATABASE_PASSWORD
```

Why does a normal PR need production credentials?

It shouldn't.

Better:

```text
Pull Request
     ↓
Test environment
     ↓
TEST_DATABASE_URL
```

Production credentials should only be available to workflows/jobs that actually need them.

This is **least privilege**.

---

# 15. GitHub Environments

GitHub supports deployment environments such as:

```text
development
staging
production
```

You can associate secrets with environments.

For example:

```text
production
 ├── PROD_DATABASE_URL
 ├── PROD_SSH_KEY
 └── PROD_API_KEY
```

This is much better than making every workflow able to access every secret.

---

# 16. Environment Protection

Production environments can have additional protection.

For example:

```text
Deploy
  ↓
Production environment
  ↓
Approval required
  ↓
Deployment continues
```

This is useful when you want:

```text
CI → automatic
Staging → automatic
Production → manual approval
```

That gives you **Continuous Delivery** rather than fully automatic Continuous Deployment.

---

# 17. Development vs Staging vs Production

A mature deployment system often looks like:

```text
Development
     ↓
Staging
     ↓
Production
```

Each environment can have different configuration:

```text
                 DATABASE_URL
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
       Dev          Staging       Prod
        │             │             │
      local        staging       production
```

Same code.

Different configuration.

---

# 18. Environment-Specific Secrets

Example:

```text
TEST_DATABASE_URL
STAGING_DATABASE_URL
PRODUCTION_DATABASE_URL
```

Similarly:

```text
STAGING_API_KEY
PRODUCTION_API_KEY
```

This reduces accidental cross-environment access.

---

# 19. SSH Private Keys

Soon our CI pipeline will deploy to a Linux server.

One common approach is:

```text
GitHub Actions
      ↓
SSH
      ↓
Linux Server
```

SSH authentication uses a key pair:

```text
Private Key 🔐
Public Key 🔓
```

The server stores the public key in:

```text
~/.ssh/authorized_keys
```

The private key should **never** be committed to Git.

---

# 20. SSH Deployment Architecture

Eventually you'll have:

```text
GitHub Actions
      │
      │ SSH_PRIVATE_KEY
      ↓
SSH Client
      │
      ↓
Linux Server
      │
      ↓
Docker Compose
      │
      ↓
Application
```

The private key lives in:

```text
GitHub Secret
```

not:

```text
repository/
└── deploy-key.pem
```

---

# 21. Dedicated Deployment Key

Don't necessarily reuse your personal SSH key.

Instead, create a dedicated deployment identity.

For example:

```text
CI Deployment Key
```

Then:

```text
GitHub Actions
       ↓
CI private key
       ↓
Production server
```

If the CI key is compromised, you can revoke it without affecting your personal SSH access.

---

# 22. Restrict Deployment Access

Ideally, your deployment identity should have only the permissions required for deployment.

For example:

```text
CI user
  ↓
can deploy application
  ↓
cannot modify unrelated system files
```

This is much safer than:

```text
CI
 ↓
root
```

Avoid giving CI root access unless there is a strong reason.

---

# 23. GitHub Actions Permissions

There are two different permission concepts to remember:

### GitHub permissions

What the workflow can do inside GitHub.

Example:

```yaml
permissions:
  contents: read
```

### Server permissions

What the deployment user can do on Linux.

Example:

```text
deploy user
   ↓
Docker commands
   ↓
application deployment
```

Both should follow least privilege.

---

# 24. Secrets Are Not Logs

Never do:

```bash
echo "$DATABASE_PASSWORD"
```

in CI.

Even though GitHub attempts to mask configured secrets, don't intentionally print them.

Bad:

```text
DATABASE_PASSWORD=supersecret123
```

Good:

```text
DATABASE_PASSWORD=********
```

Treat logs as potentially accessible to people who can view workflow runs.

---

# 25. Secret Masking

GitHub Actions can mask secrets when they appear in logs in many normal cases.

But don't rely on masking as a security strategy.

For example, don't do:

```bash
echo "SECRET=$SECRET"
```

The correct principle is:

> **Don't expose secrets in the first place.**

Masking is a safety net, not permission to print credentials.

---

# 26. Secret Values in Command Arguments

Be careful with commands such as:

```bash
some-command --password "$PASSWORD"
```

Depending on the tool and logging behavior, credentials can potentially appear in process listings or logs.

Prefer mechanisms designed for secret input, such as:

```text
environment variables
stdin
secret files
credential helpers
```

depending on the tool.

---

# 27. Environment Variables in Docker

Your Docker container might need:

```text
DATABASE_URL
JWT_SECRET
REDIS_URL
```

Docker Compose can provide them.

For example:

```yaml
services:
  api:
    environment:
      DATABASE_URL: ${DATABASE_URL}
      JWT_SECRET: ${JWT_SECRET}
```

Then the values come from the deployment environment.

This lets you keep:

```text
Docker Compose
```

separate from:

```text
actual production secrets
```

---

# 28. Don't Put Secrets in Docker Images

This is a critical Docker security rule.

Bad:

```dockerfile
ENV JWT_SECRET=my-secret
```

Why?

Because the secret can become part of the image metadata/history.

Instead:

```text
Docker Image
   ↓
generic application
```

Then:

```text
Container runtime
   ↓
production environment
   ↓
JWT_SECRET
```

Secrets should generally be supplied at runtime.

---

# 29. Build-Time Secrets vs Runtime Secrets

This distinction is extremely important.

### Runtime secret

```text
Container starts
     ↓
DATABASE_URL
JWT_SECRET
```

These stay server-side.

### Build-time secret

Sometimes a build genuinely needs credentials.

For example:

```text
private package registry
```

But build secrets need special handling.

Don't simply do:

```dockerfile
ARG NPM_TOKEN
```

and assume the token is safe.

Build secrets require careful Docker configuration so credentials aren't accidentally persisted in image layers.

For your normal MERN deployment, try to keep secrets **runtime-only** whenever possible.

---

# 30. Frontend Environment Variables

This is one of the most important concepts for React/Vite developers.

Suppose you have:

```text
VITE_API_URL=https://api.example.com
```

That's okay.

But:

```text
VITE_STRIPE_SECRET_KEY=...
```

is **not** okay.

Why?

Because frontend environment variables can become part of the generated JavaScript.

The browser receives the bundle.

Therefore:

```text
Frontend
   ↓
Browser
   ↓
User can inspect files
```

Anything bundled into frontend code should be treated as potentially public.

---

# 31. Public vs Secret Configuration

A good mental model:

### Public

```text
API base URL
Public analytics ID
Public application name
Feature flags intended for clients
```

### Secret

```text
JWT signing secret
Database password
Private API key
Cloud secret
Payment secret
SSH private key
```

If the browser needs the value, it generally isn't a secret.

---

# 32. Secret Rotation

Professional systems should make secret rotation possible.

Suppose:

```text
JWT_SECRET=v1
```

Later:

```text
JWT_SECRET=v2
```

You update the secret store and redeploy.

The application should not require source-code changes.

That's one major advantage of externalized configuration.

---

# 33. Rotation Strategy

A production-grade approach may be:

```text
Generate new secret
       ↓
Deploy configuration
       ↓
Verify application
       ↓
Revoke old secret
```

For credentials that support overlapping validity, you can temporarily support both:

```text
old key + new key
       ↓
migration
       ↓
remove old key
```

This can avoid downtime.

---

# 34. Database Credentials

Your backend might have:

```text
DATABASE_URL
```

Development:

```text
mongodb://localhost:27017/dev
```

Production:

```text
mongodb+srv://production...
```

The application code remains:

```javascript
mongoose.connect(process.env.DATABASE_URL);
```

This is exactly how environment-specific configuration should work.

---

# 35. Configuration Validation

Don't blindly assume environment variables exist.

Bad:

```javascript
mongoose.connect(process.env.DATABASE_URL);
```

and then discover at runtime that it's undefined.

Better:

```javascript
if (!process.env.DATABASE_URL) {
  throw new Error("DATABASE_URL is required");
}
```

Even better, use a configuration validation system.

For example:

```text
Application starts
       ↓
Validate environment
       ↓
Missing required variable?
       ↓
❌ Fail immediately
```

This is called **fail-fast configuration validation**.

---

# 36. Example Configuration

Conceptually:

```javascript
const config = {
  port: process.env.PORT || 5000,
  databaseUrl: process.env.DATABASE_URL,
  jwtSecret: process.env.JWT_SECRET,
};
```

Then validate:

```text
DATABASE_URL → required
JWT_SECRET    → required
PORT          → optional/default
```

Now configuration is centralized.

This is much cleaner than scattering:

```javascript
process.env.SOMETHING
```

throughout the application.

# 37. Environment Variables Should Be Documented

```text
.env
```

but you should commit something like:


Example:


No real secrets.


# 46. Don't Put Secrets in Commit Messages

Avoid:

```bash
git commit -m "fix using API key sk_live_..."
```

Commit messages are permanent repository history.

Secrets can leak through:

- Commits
    
- PR descriptions
    
- Issues
    
- Logs
    
- Screenshots
    
- CI output
    
- Docker layers
    

You need a **whole-system secret mindset**.

---

# 47. Don't Put Secrets in Comments

Bad:

```javascript
// Production password: MySecretPassword123
```

Even comments can end up in:

- Git history
    
- Code search
    
- Build artifacts
    
- Logs
    

Treat comments as public.

# 48. Secrets in Pull Requests

Be careful when debugging.

Don't paste:

```text

```

into a PR comment.

Instead say:

```text

```

This keeps sensitive values out of collaboration tools.

# 🧪 Mini Project — Configure Your Project Securely

Take one of your MERN projects.

### Step 1 — Create `.env.example`

```text
PORT=5000
DATABASE_URL=

```

Commit this file.

---

### Step 2 — Ignore `.env`

In `.gitignore`:

```text
.env
.env.*
!.env.example
```

The final rule keeps `.env.example` tracked while ignoring actual environment files.

---

### Step 3 — Use `process.env`

Backend:

```javascript

const databaseUrl = process.env.DATABASE_URL;

```

At application startup:

```text
DATABASE_URL missing?
       ↓
❌ Stop application
```

Don't allow the server to silently run with invalid production configuration.

---

### Step 5 — Add GitHub Secrets

In your GitHub repository, create test-specific secrets such as:

```text

TEST_JWT_SECRET
```

Then your CI can eventually use:

```yaml
env:
  DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
  JWT_SECRET: ${{ secrets.TEST_JWT_SECRET }}
```

**Do not use your real production credentials for this exercise.**

# 🧠 Interview Questions

### Q1. What is a secret?

> Sensitive information such as passwords, API keys, tokens, database credentials, or private keys that must be protected from unauthorized access.

### Q2. Why use environment variables?

> To separate configuration from application source code and allow the same code to run with different environment-specific settings.

### Q3. Where should GitHub Actions secrets be stored?

> In GitHub's protected Secrets storage or appropriate environment-level secret storage, not inside the repository.

### Q4. Should production secrets be available to Pull Request workflows?

> Generally no. They should only be exposed to trusted deployment jobs that actually require them.

### Q5. Why shouldn't secrets be inside Docker images?

> They can become part of image metadata or layers and may be accessible to anyone who can inspect or pull the image.

### Q6. What should you do if an API key is accidentally committed?

> Treat it as compromised, revoke or rotate it immediately, remove it from the repository/history as appropriate, and replace it with a securely stored credential.

### Q7. What is least privilege?

> Giving each user, process, workflow, or service only the permissions and secrets it actually needs.

### Q8. Why is `.env.example` useful?

> It documents the required environment variables without exposing their real values.

# 🔑 Lesson 12.8 Takeaways

Remember these **14 points**:

1. **Never commit real secrets to Git.**
    
2. Use environment variables for environment-specific configuration.
    
3. Keep `.env` files with real secrets out of Git.
    
4. Commit `.env.example` to document required configuration.
    
5. Use GitHub Secrets for sensitive CI/CD values.
    
6. Use GitHub Variables for non-sensitive configuration.
    
7. Separate development, staging, and production credentials.
    
8. Don't give Pull Request workflows production secrets.
    
9. Use **least privilege** everywhere.
    
10. Never put backend secrets in React/Vite frontend variables.
    
11. Don't put secrets inside Docker images.
    
12. Don't print secrets into CI logs.
    
13. If a secret leaks, **rotate/revoke it immediately**.
    
14. Treat your CI/CD system itself as security-sensitive infrastructure.

And secrets remain outside your repository:

```text
             GitHub
                │
       ┌────────┴────────┐
       ↓                 ↓
   Source Code       Secret Store
                         │
                  ┌──────┴──────┐
                  ↓             ↓
               Staging      Production
               Secrets        Secrets
                  │             │
                  └──────┬──────┘
                         ↓
                     Deployment
```

This is the foundation we'll use for the deployment lessons.
