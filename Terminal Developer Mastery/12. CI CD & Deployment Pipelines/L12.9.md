# Module 12 — CI/CD & Deployment Pipelines

## Lesson 12.9 — Docker in CI/CD ⭐⭐⭐⭐⭐

Now we're entering the most important part of the deployment pipeline:

> **How do we turn our tested source code into a versioned Docker image that can be deployed anywhere?**

So far:

```text
Git Push
   ↓
GitHub Actions
   ↓
Lint
   ↓
Tests
   ↓
Build
   ↓
Quality Gate
```

Now we'll add:

```text
Quality Gate
   ↓
Docker Build
   ↓
Docker Image
   ↓
Image Tag
   ↓
Container Registry
   ↓
Production
```

This is where **CI starts producing a real deployment artifact**.

---

# 1. Why Docker in CI/CD?

Without Docker, your deployment might look like:

```text
GitHub Actions
    ↓
SSH Server
    ↓
git pull
    ↓
npm install
    ↓
npm build
    ↓
restart application
```

This can work, but the production environment may differ from CI or your development machine.

Docker gives us:

```text
Source Code
    ↓
Dockerfile
    ↓
Docker Image
    ↓
Same Image
    ↓
Staging
    ↓
Production
```

The environment becomes much more predictable.

---

# 2. The Core Idea

Think of a Docker image as a **deployable package** containing your application and its runtime requirements.

For example:

```text
my-api:1.0.0
```

contains:

```text
Node.js
Application code
Production dependencies
Required filesystem
Runtime configuration structure
```

Then:

```text
Docker Image
      ↓
Container
```

The same image can run on:

```text
Developer machine
CI runner
Staging server
Production server
```

---

# 3. Build Once, Deploy Many

This is one of the most important CI/CD principles.

Bad:

```text
Build
 ↓
Staging

Build again
 ↓
Production
```

The two builds might technically be different.

Better:

```text
Source
  ↓
Build Image
  ↓
my-api:abc123
  ↓
Staging
  ↓
Production
```

The exact same artifact moves through environments.

This is called:

> **Build once, deploy many.**

---

# 4. Dockerfile

Your backend may have:

```text
backend/
├── src/
├── package.json
├── package-lock.json
└── Dockerfile
```

A simple Dockerfile:

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["npm", "start"]
```

Let's understand each part.

---

# 5. Base Image

```dockerfile
FROM node:22
```

This provides the Node.js runtime.

Conceptually:

```text
Node 22 image
     ↓
Your application
     ↓
Your Docker image
```

The base image becomes the foundation of your application image.

---

# 6. Working Directory

```dockerfile
WORKDIR /app
```

Now Docker commands operate inside:

```text
/app
```

Instead of scattering files throughout the container filesystem.

---

# 7. Copy Package Files First

```dockerfile
COPY package*.json ./
```

This copies:

```text
package.json
package-lock.json
```

before the application source.

Why?

**Docker layer caching.**

This becomes very important.

---

# 8. Install Dependencies

```dockerfile
RUN npm ci
```

Now dependencies are installed inside the image.

You generally want:

```text
package.json
+
package-lock.json
       ↓
npm ci
       ↓
node_modules
```

For production images, we'll later improve this further.

---

# 9. Copy Application Code

```dockerfile
COPY . .
```

Now:

```text
src/
controllers/
routes/
models/
```

and other application files enter the image.

---

# 10. Start Command

```dockerfile
CMD ["npm", "start"]
```

When the container starts:

```text
Docker
 ↓
npm start
 ↓
Node.js
 ↓
Express
```

---

# 11. Building the Image Locally

From your backend directory:

```bash
docker build -t my-api:latest .
```

Docker reads:

```text
Dockerfile
```

and creates:

```text
my-api:latest
```

Check it:

```bash
docker images
```

You might see:

```text
REPOSITORY   TAG       IMAGE ID
my-api       latest    abc123...
```

---

# 12. Running the Image

Run:

```bash
docker run --rm -p 5000:5000 my-api:latest
```

Now:

```text
Browser / curl
      ↓
localhost:5000
      ↓
Docker container
      ↓
Express
```

Test:

```bash
curl http://localhost:5000/health
```

If your health endpoint returns:

```json
{
  "status": "ok"
}
```

your image is working.

---

# 13. Docker in GitHub Actions

Now let's automate the build.

A basic step:

```yaml
- name: Build Docker image
  run: docker build -t my-api:latest .
```

GitHub's runner already provides Docker tooling in commonly used Linux environments.

The pipeline becomes:

```text
Git Push
   ↓
Tests
   ↓
Build
   ↓
docker build
   ↓
Docker Image
```

---

# 14. Should Docker Build Run Before Tests?

Usually, your pipeline should establish correctness before spending time packaging.

A useful structure:

```text
Checkout
   ↓
Install
   ↓
Lint
   ↓
Tests
   ↓
Application Build
   ↓
Docker Build
```

Why?

Because if:

```text
npm test
```

fails, there's little reason to build the production image.

---

# 15. Docker Build After Quality Gate

For example:

```yaml
jobs:
  test:
    ...

  docker:
    needs: test
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Build Docker image
        run: docker build -t my-api:latest .
```

Architecture:

```text
        test
         ↓
       PASS
         ↓
    Docker Build
```

If tests fail:

```text
test ❌
  ↓
Docker Build ⏭️
```

---

# 16. Docker Image Tags

Now comes an extremely important topic:

> **How do we identify which version of our application an image contains?**

You can use:

```text
my-api:latest
```

But `latest` isn't enough for production.

Suppose:

```text
latest
```

currently points to:

```text
version A
```

Then you deploy version B:

```text
latest
```

now points to:

```text
version B
```

What happens if you need to roll back?

It's ambiguous.

---

# 17. Better Image Tags

Use unique versions.

For example:

```text
my-api:1.4.0
```

or:

```text
my-api:abc123
```

where:

```text
abc123
```

is the Git commit SHA.

Now:

```text
my-api:abc123
```

uniquely identifies the source version.

---

# 18. Git SHA as an Image Tag

Suppose Git commit:

```text
a83f91c
```

produced the image:

```text
my-api:a83f91c
```

Now you have:

```text
Git commit
    ↓
a83f91c
    ↓
Docker image
    ↓
my-api:a83f91c
```

This gives you traceability.

You can answer:

> "Which exact commit is running in production?"

---

# 19. Why Traceability Matters

Imagine production has a bug.

You see:

```text
Production
 ↓
my-api:a83f91c
```

Then:

```bash
git show a83f91c
```

You can inspect the exact source revision.

This creates:

```text
Production container
       ↓
Image tag
       ↓
Git commit
       ↓
Source code
```

That's extremely valuable during incidents.

---

# 20. Semantic Version Tags

You can also use:

```text
my-api:1.0.0
my-api:1.1.0
my-api:1.2.0
```

This works well with releases.

You can combine tags:

```text
my-api:1.2.0
my-api:a83f91c
```

Both can refer to the same image.

---

# 21. Recommended Tagging Strategy

For your projects, a good approach is:

```text
my-api:<git-sha>
```

for every build.

For releases:

```text
my-api:1.2.0
```

And optionally:

```text
my-api:latest
```

for convenience.

But production deployments should preferably reference an **immutable tag or digest**, not blindly `latest`.

---

# 22. `latest` Is Not a Version

This is a common beginner mistake:

```text
production:
  image: my-api:latest
```

Then someone pushes a new image.

Now:

```text
latest
```

points somewhere else.

Your deployment becomes less predictable.

Better:

```text
production:
  image: my-api:a83f91c
```

Now the deployment explicitly identifies the version.

---

# 23. Docker Image Digests

Docker images can also be identified by a digest:

```text
sha256:abc123...
```

Conceptually:

```text
Tag
 ↓
Image
 ↓
Digest
```

A digest identifies the exact image content.

This gives you an even stronger guarantee:

```text
Deploy this exact image
```

rather than:

```text
Deploy whatever currently has this tag
```

# 24. Multi-Stage Builds

Now let's improve our Dockerfile.

A naive Dockerfile:

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .

CMD ["npm", "start"]
```

may contain development dependencies and unnecessary files.

A **multi-stage build** lets us separate build and runtime environments.

Conceptually:

```text
Stage 1
Build Environment
   ↓
Build application
   ↓
Stage 2
Runtime Environment
   ↓
Only production files
```

---

# 25. Example Multi-Stage Node Build

For an application that needs a build step:

```dockerfile
FROM node:22 AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM node:22-alpine AS runtime

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist

EXPOSE 5000

CMD ["node", "dist/server.js"]
```

The important idea is:

```text
builder
   ↓
produces dist/
   ↓
runtime
   ↓
copies only required output
```

---

# 26. Why Multi-Stage Builds?

They can produce smaller and cleaner images.

Instead of:

```text
Production Image
 ├── source
 ├── build tools
 ├── dev dependencies
 ├── test files
 └── runtime
```

you want closer to:

```text
Production Image
 ├── runtime
 ├── production dependencies
 └── application output
```

Smaller images generally mean:

- Faster downloads
    
- Faster deployments
    
- Smaller attack surface
    
- Less storage
    

---

# 27. Development Dependencies

Suppose:

```text
devDependencies
├── jest
├── eslint
├── prettier
└── nodemon
```

You probably don't need all of these in your production container.

Production may only need:

```text
dependencies
├── express
├── mongoose
├── helmet
└── cors
```

That's why:

```bash
npm ci --omit=dev
```

can be useful in a production runtime image.

---

# 28. Frontend Docker Images

React/Vite is different.

You usually don't need Node.js running in production to serve the generated static files.

Instead:

```text
React source
    ↓
npm run build
    ↓
dist/
    ↓
Nginx
    ↓
Browser
```

A multi-stage frontend Dockerfile could be:

```dockerfile
FROM node:22 AS builder

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build


FROM nginx:alpine

COPY --from=builder /app/dist /usr/share/nginx/html
```

Now:

```text
Node
 ↓
Build React
 ↓
dist
 ↓
Nginx
```

The final image doesn't need Node.js.

# 29. Docker Build Context

When you run:

```bash
docker build -t my-api .
```

the final:

```text
.
```

is the **build context**.

Docker can access files inside that context.

For example:

```text
backend/
├── Dockerfile
├── package.json
├── src/
└── .dockerignore
```

The context is:

```text
backend/
```

---

# 30. `.dockerignore`

Just as Git has:

```text
.gitignore
```

Docker has:

```text
.dockerignore
```

Example:

```text
node_modules
npm-debug.log
.git
.github
.env
coverage
Dockerfile
README.md
```

This prevents unnecessary files from being sent to Docker during the build.

---

# 31. Why `.dockerignore` Matters

Imagine your project contains:

```text
node_modules/
```

with thousands of files.

If Docker sends all of that as build context:

```text
Docker build
    ↓
Huge context
    ↓
Slower build
```

With:

```text
node_modules
```

in `.dockerignore`:

```text
Docker build
    ↓
Small context
    ↓
Faster build
```

---

# 32. Never Put `.env` in the Docker Context

This is important.

Your `.dockerignore` should normally include:

```text
.env
.env.*
```

unless you have a specific, safe reason not to.

You don't want:

```text
.env
   ↓
Docker build context
   ↓
Potentially copied into image
```

Secrets should enter the container at runtime.

---

# 33. Docker Layer Caching

Docker builds images in layers.

For example:

```dockerfile
COPY package*.json ./
RUN npm ci
COPY . .
```

Docker can cache:

```text
COPY package*.json
       ↓
npm ci
```

If your source code changes but:

```text
package-lock.json
```

doesn't change, Docker can reuse the dependency layer.

That's why this ordering is useful.

---

# 34. Bad Dockerfile Ordering

Suppose:

```dockerfile
COPY . .

RUN npm ci
```

Every source code change may invalidate the cache before `npm ci`.

So:

```text
Source change
 ↓
COPY changes
 ↓
npm ci runs again
```

This can be slow.

Better:

```dockerfile
COPY package*.json ./
RUN npm ci

COPY . .
```

Now:

```text
Source change
 ↓
dependency layer unchanged
 ↓
npm ci cache reused
```

---

# 35. CI Build Cache

Docker caching becomes even more useful in CI.

Without caching:

```text
Every CI run
 ↓
Download everything
 ↓
Build everything
```

With caching:

```text
CI
 ↓
Restore Docker cache
 ↓
Reuse unchanged layers
 ↓
Build only changed layers
```

This can significantly speed up builds.

# 36. GitHub Actions Docker Build

A common approach is to use Docker's official Buildx tooling.

For example:

```yaml
- name: Set up Docker Buildx
  uses: docker/setup-buildx-action@v3
```

Then you can use:

```yaml
- name: Build Docker image
  uses: docker/build-push-action@v6
  with:
    context: .
    push: false
    tags: my-api:${{ github.sha }}
```

This creates an image tagged with the commit SHA.

# 37. What Is Buildx?

Buildx is Docker's extended build functionality.

It supports features such as:

- Advanced caching
    
- Multi-platform builds
    
- Build secrets
    
- BuildKit features
    
- More advanced build workflows
    

For CI/CD, Buildx is commonly used instead of a plain:

```bash

```

# 42. Reproducible Builds

A reproducible build aims to produce the same output from the same source and dependency inputs.

You improve reproducibility through:

```text
package-lock.json
       +
fixed Node version
       +
controlled Docker base image
       +
deterministic build
```

Avoid:

```text
node:latest
```

for strict production workflows.

Prefer a controlled version.

---

# 43. Base Image Updates

Suppose you use:

```dockerfile
FROM node:22
```

Node base images can change over time.

That means rebuilding later may produce a different image.

For stricter reproducibility, teams may pin the base image more precisely, potentially by digest.

The tradeoff is:

```text
Reproducibility
      vs
Automatic security updates
```

You need a process for regularly updating base images.

# 44. Container Image Security

A Docker image can contain vulnerabilities.

For example:

```text
Your application
      ↓
Node runtime
      ↓
OS packages
      ↓
Vulnerable package
```

So after building:

```text
Docker Image
     ↓
Image Scanner
     ↓
Vulnerabilities?
```

Tools such as image vulnerability scanners can inspect the result.

We'll connect this with the security concepts from your earlier module.

# 45. Image Size

Suppose:

```text
Image A → 1.2 GB
Image B → 180 MB
```

Deploying Image B is generally much more efficient.

Smaller images mean:

```text
Registry download ↓
Deployment time ↓
Storage ↓
Attack surface ↓
```

But don't obsess over image size at the cost of maintainability.

---

# 46. Alpine vs Debian-Based Images

You'll often see:

```text
node:22
node:22-alpine
```

`alpine` is smaller.

But Alpine uses musl libc instead of glibc, and some native dependencies can behave differently.

Therefore:

> Don't choose Alpine purely because it's smaller.

Test your application.

For many Node.js applications, both can work well.

```javascript
app.get("/health", (req, res) => {
```

Then:

```text
Docker container
      ↓
/health

```

This becomes extremely important later for:

- Health checks
    
- Zero-downtime deployments

# 48. Docker Healthcheck

You can also define:

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s \
  CMD curl -f http://localhost:5000/health || exit 1
```

But whether this exact form works depends on what's installed in your base image.

For example, minimal images may not contain `curl`.

So don't blindly copy health checks without checking the image contents.

# 50. Complete GitHub Actions Example

Here's a good starting point for your backend:

```yaml
name: Backend CI

on:
  pull_request:
    branches:
      - main

  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Format check
        run: npm run format:check

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test

  docker:
    needs: test
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build Docker image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: false
          tags: my-api:${{ github.sha }}
```

The flow:

```text
                Pull Request / Push
                        ↓
                      test
                        ↓
                   ┌────┴────┐
                   │         │
                 format     lint
                   │         │
                   └────┬────┘
                        ↓
                      tests
                        ↓
                      PASS
                        ↓
                  Docker Build
                        ↓
                 my-api:<SHA>
```

# 51. Why `github.sha`?

GitHub provides information about the workflow execution.

One of the most useful values is:

```text
github.sha
```

It represents the commit SHA associated with the workflow.

So:

```yaml
tags: my-api:${{ github.sha }}
```

could produce:

```text
my-api:8f72c91...
```

Now your Docker image is directly connected to Git.

# 52. The Complete Traceability Chain

This is one of the most valuable concepts in production engineering:

```text
Git Commit
    ↓
GitHub Actions Run
    ↓
Docker Build
    ↓
Docker Image
    ↓
Registry
    ↓
Production Container
```

For example:

```text
Commit:
a83f91c

Image:
my-api:a83f91c

Container:
my-api:a83f91c

Production:
running a83f91c
```

You can trace a production bug all the way back to its source commit.

# 54. Better Production Dockerfile

Once your basic image works, move toward:

```dockerfile
FROM node:22 AS runtime

WORKDIR /app

ENV NODE_ENV=production

COPY package*.json ./

RUN npm ci --omit=dev

COPY src ./src

EXPOSE 5000

USER node

CMD ["node", "src/server.js"]
```

Notice several improvements:

```text
NODE_ENV=production
        ↓
Production dependencies only
        ↓
Only necessary source copied
        ↓
Non-root user
```

However, the exact structure depends on your application.

If your app has a build step, use a multi-stage build.

---

# 55. Running as Non-Root

By default, some containers can run as root.

That's unnecessary risk.

For example:

```dockerfile
USER node
```

allows the application to run as the non-root Node user in official Node images where available.

This is an example of **defense in depth**.

If the application is compromised:

```text
Attacker
   ↓
Application process
   ↓
Non-root user
```

rather than immediately having:

```text
root
```

privileges.

---

# 56. Important Security Rule

Never put:

```text
DATABASE_URL
JWT_SECRET
SSH_PRIVATE_KEY
```

inside the Dockerfile.

Instead:

```text
Docker Image
    ↓
Generic
    ↓
No production secrets
```

At runtime:

```text
Docker Compose
    ↓
Environment
    ↓
Secrets
    ↓
Container
```

This separation is fundamental.

```text
                       Application
```

This is the foundation of modern containerized deployment.

# 🧠 Interview Questions

### Q1. Why use Docker in CI/CD?

> Docker packages the application and runtime dependencies into a consistent artifact that can be tested and deployed across environments.

### Q2. What is "build once, deploy many"?

> Build the deployment artifact once and promote the same artifact through staging and production instead of rebuilding it for each environment.

### Q3. Why tag Docker images with Git SHA?

> It provides traceability between a deployed container and the exact source-code commit that produced it.

### Q4. Why is `latest` not ideal for production?

> `latest` is mutable and doesn't uniquely identify an application version, making deployments and rollbacks less predictable.

### Q5. What is a multi-stage Docker build?

> A Docker build using multiple stages so that build dependencies and tools can be excluded from the final runtime image.

### Q6. Why use `.dockerignore`?

> To prevent unnecessary files such as `node_modules`, `.git`, `.env`, and coverage data from entering the Docker build context.

### Q7. Why copy `package.json` before source code?

> It allows Docker to reuse the dependency installation layer when only application source files change.

### Q8. Why shouldn't secrets be included in Docker images?

> Images can be inspected, cached, stored, and distributed. A secret inside an image can therefore be exposed to anyone with access to that image.

### Q9. What is Buildx?

> Docker Buildx provides advanced build capabilities such as BuildKit-based caching and multi-platform builds.

### Q10. What is the deployment artifact in a containerized system?

> Typically a versioned Docker image, preferably referenced by an immutable tag or digest.

# 🔑 Lesson 12.9 Takeaways

Remember these **15 points**:

1. **Docker turns your application into a portable deployment artifact.**
    
2. CI should build the Docker image after important quality checks pass.
    
3. Use **build once, deploy many**.
    
4. Tag images with Git SHA or another unique version.
    
5. `latest` should not be your only production version identifier.
    
6. Image digests provide stronger immutability.
    
7. Multi-stage builds create cleaner runtime images.
    
8. Don't ship unnecessary development dependencies.
    
9. `.dockerignore` reduces build context and prevents accidental files from entering builds.
    
10. Keep `.env` and secrets out of Docker build contexts.
    
11. Order Dockerfile instructions to maximize layer caching.
    
12. Use Docker Buildx for advanced CI builds and caching.
    
13. Run production containers as non-root where practical.
    
14. Keep secrets outside the image and provide them at runtime.
    
15. Always maintain the chain:
    

```text
Git Commit
    ↓
CI Run
    ↓
Docker Image
    ↓
Registry
    ↓
Production
```
