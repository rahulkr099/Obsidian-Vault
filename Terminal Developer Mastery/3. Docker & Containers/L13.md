# Module 3 — Lesson 13: Image Optimization & Security 🛡️

> **"A Docker image that works isn't enough. A production image should also be small, fast, secure, and maintainable."**

Many security incidents happen not because of application code, but because of **poor container configuration**:

- Running as root
- Outdated base images
- Hardcoded secrets
- Huge images with unnecessary tools
- Vulnerable dependencies

This lesson teaches the practices used by professional backend teams.

Bad:


# Multi-stage Builds

Never ship build tools.

Instead:

```
Builder

↓

Compile

↓

Copy Build Output

↓

Runtime Image
```

Example:

```docker
# Build Stage
FROM node:22 AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build

# Runtime Stage
FROM node:22-slim

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist

CMD ["node","dist/server.js"]
```

Production image stays much smaller.

---

# Don't Run as Root

By default:

```
Container

↓

root
```

If an attacker escapes the application, running as root increases the risk.

---

Better:

```docker
RUN useradd -m appuser

USER appuser
```

Now the application runs with fewer privileges.

---

Inside container:



# Copy Only Required Files

Bad:

```docker
COPY . .
```

Might copy:

```
.git

tests

README

coverage

videos

```

---

Better:

```docker
COPY package*.json ./

COPY src ./src
```

Copy only what's needed.

# .dockerignore

Example:

```
node_modules
.git
coverage
.env
tests
*.log
README.md
```

Reduces:

- Build time
- Image size
- Secret exposure

---

# Install Only Production Dependencies

Instead of:

```bash
npm install
```

Use:

```bash
npm ci --omit=dev
```

Development packages:

```
eslint

jest

prettier

nodemon
```

should not exist in production.

---

# Pin Image Versions

Avoid:

```docker
FROM node:latest
```

Better:

```docker
FROM node:22.19-slim
```

Or another specific version you've tested.

Benefits:

- Predictable builds
- Easier debugging
- Stable deployments

---

# Reduce Layers

Bad:

```docker
RUN apt update

RUN apt install curl

RUN apt clean
```

Better:

```docker
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
```

One layer.

Smaller image.

---

# Avoid Installing Unnecessary Packages

Don't install:

- Git
- Nano
- Vim
- GCC
- Curl

unless the application truly needs them at runtime.

Keep runtime images minimal.

# Image Scanning

Docker can scan images for vulnerabilities.

Example:

```bash
docker scout quickview my-app
```

Or, if your environment supports it:

```bash
docker scout cves my-app
```

Look for:

- High severity
- Critical severity

Fix them promptly.

> **Note:** Docker Scout is the modern Docker image analysis tool. Some older tutorials mention `docker scan`, but Docker Scout is the recommended approach.

# Read-only Filesystem

Some applications can run with a read-only root filesystem.

Example:

```bash
docker run \
--read-only \
my-app
```

Benefits:

- Harder for attackers to modify files.
- Reduces accidental writes.

Applications that need writable directories (logs, temp files, uploads) must mount writable volumes or `tmpfs`.

---

# Resource Limits

Limit memory:

```bash
docker run \
--memory=512m \
my-app
```

Limit CPUs:

```bash
docker run \
--cpus=1
```

Prevents one container from consuming all host resources.

---

# Drop Linux Capabilities

Containers don't always need every Linux capability.

Example:

```bash
docker run \
--cap-drop ALL \
--cap-add NET_BIND_SERVICE \
my-app
```

Grant only what the application actually requires.

---

# Health Checks

Dockerfile:

```docker
HEALTHCHECK \
CMD curl -f <http://localhost:5000/health> || exit 1
```

Docker can detect unhealthy containers automatically.

> If your runtime image doesn't include `curl`, consider using another lightweight command or implement the health check in a way that matches your image contents.

# 💡 Senior Backend Engineer Insight

Optimizing a Docker image is only one part of container security. Production systems usually combine several layers of defense:

```
Source Code
      │
      ▼
Dependency Scanning
      │
      ▼
Docker Image Scan
      │
      ▼
CI/CD Security Checks
      │
      ▼
Container Runtime Security
      │
      ▼
Monitoring & Alerts
```

This **defense-in-depth** approach means that if one layer misses a problem, another layer can still detect or mitigate it.
