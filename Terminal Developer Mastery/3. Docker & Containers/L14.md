# What Is a Docker Registry?

A registry stores Docker images.

```
Developer

↓

docker build

↓

Docker Image

↓

Push

↓

Docker Registry

↓

Pull

↓

Production Server
```

Without registries:

- Images stay on your computer.

With registries:

- Anyone with permission can download them.

---

# Popular Registries

|Registry|Use Case|
|---|---|
|Docker Hub|Public & private images|
|GitHub Container Registry (GHCR)|GitHub projects|
|Amazon ECR|AWS|
|Google Artifact Registry|Google Cloud|
|Azure Container Registry|Azure|
|Harbor|Self-hosted enterprise registry|

For backend development, **Docker Hub** and **GHCR** are the most useful places to start.

# Image Naming Convention

A Docker image name looks like this:

```
username/image-name:tag
```

Example:

```
rahul/backend-api:v1
```

Breakdown:

```
rahul

↓

Repository Owner

backend-api

↓

Repository Name

v1

↓

Version Tag
```

---

# Default Tag

If you don't specify one:

```bash
docker build -t backend-api .
```

Docker automatically assigns:

```
latest
```

Equivalent to:

```
backend-api:latest
```

---

# Why "latest" Is Misleading

Many beginners think:

```
latest

=

Newest Version
```

Not necessarily.

It simply means:

> "The image currently tagged as `latest`."

Production teams usually deploy **explicit version tags** instead.

---

# Good Versioning

Instead of:

```
latest
```

Use:

```
v1.0.0

v1.1.0

v1.2.3

2026-07-25

commit-a1b2c3d
```

Semantic versioning (`MAJOR.MINOR.PATCH`) is a common choice.

# Push an Image

```bash
docker push rahul/backend-api:v1
```

Flow:

```
Local Image

↓

Upload Layers

↓

Docker Hub
```

Docker uploads only layers that aren't already present.

---

# Pull an Image

On another computer:

```bash
docker pull rahul/backend-api:v1
```

Run:

```bash
docker run rahul/backend-api:v1
```

---

# Layer Uploads

Docker images consist of layers.

```
Layer 1

↓

Layer 2

↓

Layer 3

↓

Layer 4
```

If only Layer 4 changed:

Only Layer 4 uploads.

This makes pushes much faster.

# Multiple Tags

One image can have several tags.

```bash

docker tag backend-api rahul/backend-api:v1
```

Both tags can reference the same image.

---

# Docker Hub Repository

Example:

```
rahul/

backend-api

↓

Tags

↓

v1

v2

```

Each tag points to a specific image version.

---

# GitHub Container Registry (GHCR)

GHCR stores Docker images alongside GitHub repositories.

Example image:

```
ghcr.io/username/backend-api:v1
```

Advantages:

- Integrates with GitHub permissions
- Works well with GitHub Actions
- Public or private images

---

# Login to GHCR

Use a GitHub Personal Access Token with the appropriate package permissions.

Example:

```bash
echo YOUR_TOKEN | docker login ghcr.io \
  -u YOUR_GITHUB_USERNAME \
  --password-stdin
```

Using `--password-stdin` avoids exposing the token in your shell history.

---

# Tag for GHCR

```bash
docker tag backend-api \
ghcr.io/username/backend-api:v1
```

Push:

```bash
docker push \
ghcr.io/username/backend-api:v1
```

---

# Pull from GHCR

```bash
docker pull \
ghcr.io/username/backend-api:v1
```

# Cleaning Old Images

List images:

```bash
docker images
```

Remove one:

```bash
docker rmi image-id
```

Remove unused images:

```bash
docker image prune
```

Remove all unused images (including older tagged images that aren't referenced):

```bash
docker image prune -a
```

Be careful with `-a`; you'll need to pull or rebuild removed images later.

---

# Save Images as Files

Sometimes there's no registry.

Save:

```bash
docker save -o backend-api.tar \
backend-api:v1
```

Load elsewhere:

```bash
docker load -i backend-api.tar
```

Useful for offline environments.

# Best Practices

### Version Every Image

Never rely solely on `latest`.

---

### Keep Registries Clean

Remove obsolete tags when appropriate.

---

### Use Immutable Deployments

Deploy:

```
backend-api:1.2.0
```

instead of:

```
latest
```

---

### Push Only Tested Images

Build → Test → Push → Deploy.

---

### Automate Publishing

Let CI/CD create and publish images automatically after successful tests.

---

### Protect Credentials

Use Personal Access Tokens or credential helpers instead of storing passwords in scripts.

# 💡 Senior Backend Engineer Insight

A production deployment rarely builds Docker images directly on the server. Instead, the workflow usually looks like this:

```
Developer
     │
     ▼
Git Push
     │
     ▼
CI/CD Pipeline
     │
     ├── Run Tests
     ├── Build Docker Image
     ├── Security Scan
     ├── Push to Registry
     ▼
Docker Registry
     │
     ▼
Production Server
     │
docker pull backend-api:1.2.0
     │
     ▼
Deploy
```

This approach has several advantages:

- The exact same tested image is deployed everywhere.
- Rollbacks are as simple as deploying a previous tag.
- Builds are reproducible and traceable.
- Security scanning happens before deployment.
