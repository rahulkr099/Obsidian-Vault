# What Is a Docker Image?

A Docker image is a **read-only template** containing everything needed to run an application.

An image may contain:

- Linux filesystem
- Runtime (Node.js, Python, Java, etc.)
- Application dependencies
- Configuration
- Startup command

Think of an image as a snapshot of an application environment.

---

# Real Example

Image:

```
node:22
```

Contains:

```
Linux Filesystem
Node.js 22
npm
```

It does **not** include your project.

Your project is added later with a Dockerfile.

```

     ▼          ▼          ▼
```

Stopping one does not stop the others.

# Images Are Immutable

Once built:

```
node:22
```

cannot be modified.

If you need changes:

Build a **new image**.

This makes deployments predictable.

---

# Image Layers

Images are made of layers.

Example:

```
Layer 5  Your App
───────────────
Layer 4  npm install
───────────────
Layer 3  COPY package.json
───────────────
Layer 2  Node.js
───────────────
Layer 1  Ubuntu
```

Each layer is cached.

---

# Why Layers Matter

Suppose you only change:

```
index.js
```

Docker **doesn't rebuild everything**.

It reuses cached layers and rebuilds only what changed.

This is why Docker builds are often very fast.

# Docker Image Naming

General format:

```
registry/namespace/image:tag
```

Example:

```
docker.io/library/node:22
```

Breaking it down:

|Part|Meaning|
|---|---|
|[docker.io](http://docker.io)|Registry|
|library|Namespace|
|node|Image|
|22|Tag|

# What Is a Tag?

Tags identify image versions.

Examples:

```
node:18

node:20

node:22

node:latest
```

Never assume `latest` means newest.

It simply means **the image tagged as `latest`**.

For production, prefer explicit versions like:

```
node:22
```

# Alpine Images

Example:

```
node:22-alpine
```

Uses Alpine Linux.

Benefits:

- Very small
- Fast downloads
- Good for production

Trade-offs:

- Smaller package ecosystem
- Some native modules require extra setup

---

# Removing Images

Remove:

```
docker rminode:22
```

If a container still uses the image, Docker will prevent removal until that dependency is gone.

---

# Dangling Images

These are untagged images left over from builds.

List them:

```
docker imagels-fdangling=true
```

Remove unused images:

```
docker image prune
```

We'll cover cleanup in more detail later.

---

# Image Cache

Example:

First build:

```
30 seconds
```

Second build:

```
3 seconds
```

Why?

Docker reuses unchanged layers from the cache.

---

# Backend Example

Suppose your Express project looks like:

```
backend/
│
├── package.json
├── package-lock.json
└── server.js
```

An efficient Dockerfile copies `package*.json` first, installs dependencies, then copies the application source. This lets Docker reuse the dependency layer when only application code changes.

```
Layer 1
Node

↓

Layer 2
package.json

↓

Layer 3
npm install

↓

Layer 4
Source Code
```

# 💡 Backend Engineer Insight

A professional backend workflow usually looks like this:

1. Write your code.
2. Build a Docker image.
3. Push the image to a registry.
4. Pull the same image in staging and production.
5. Run containers from that image.

Notice that **the image never changes** between environments. This is one of Docker's biggest strengths—it ensures that what you tested is exactly what you deploy.

In **Lesson 4**, you'll start using Docker daily by mastering the **essential Docker commands** for creating, managing, inspecting, stopping, removing, and interacting with containers. These commands form the core of every Docker workflow.
