# What Is a Dockerfile?

A Dockerfile is simply a text file.

Example:

```
Dockerfile
```

Inside it, you write instructions.

Example:

```docker
FROM node:22

WORKDIR /app

COPY . .

RUN npm install

CMD ["node", "server.js"]
```

Docker reads these instructions from top to bottom.

# Dockerfile Instructions

The most common instructions are:

|Instruction|Purpose|
|---|---|
|`FROM`|Base image|
|`WORKDIR`|Working directory|
|`COPY`|Copy files|
|`RUN`|Execute commands during build|
|`ENV`|Set environment variables|
|`EXPOSE`|Document application port|
|`CMD`|Default startup command|
|`ENTRYPOINT`|Fixed executable|

These cover about **90% of Dockerfiles** you'll encounter.

---

# 1. FROM

Every Dockerfile starts with a base image.

```docker
FROM node:22
```

Meaning:

```
Start with

↓

Node.js 22 image
```

Without `FROM`, Docker doesn't know where to begin.

---

# 2. WORKDIR

Sets the current working directory.

```docker
WORKDIR /app
```

Equivalent to:

```bash
cd /app
```

for all following instructions.

---

# 3. COPY

Copies files into the image.

```docker
COPY . .
```

Meaning:

```
Host Project

↓

Docker Image
```

A better approach is:

```docker
COPY package*.json ./
```

This copies only dependency files first.

Later:

```docker
COPY . .
```

copies the remaining project files.

---

# Why Copy package.json First?

Suppose your Dockerfile looks like this:

```docker
COPY . .

RUN npm install
```

Every time you change **any file**, Docker reruns:

```bash
npm install
```

That's slow.

Instead:

```docker
COPY package*.json ./

RUN npm install

COPY . .
```

Now Docker only reinstalls dependencies when `package.json` changes.

---

# 4. RUN

Runs commands while building the image.

Example:

```docker
RUN npm install
```

Other examples:

```docker
RUN apt-get update

RUN mkdir logs

RUN npm run build
```

These commands execute **once during image creation**.

---

# 5. ENV

Sets environment variables.

```docker
ENV NODE_ENV=production
```

Now inside the container:

```bash
echo $NODE_ENV
```

Output:

```
production
```

---

# 6. EXPOSE

Example:

```docker
EXPOSE 5000
```

Important:

This **does not publish** the port.

It only documents:

> "This application listens on port 5000."

To access it from the host, you still need:

```bash
docker run -p 5000:5000 my-app
```

---

# 7. CMD

Defines the default command.

Example:

```docker
CMD ["node", "server.js"]
```

When you run:

```bash
docker run my-app
```

Docker executes:

```bash
node server.js
```

---

# CMD vs RUN

`RUN`

```docker
RUN npm install
```

Occurs:

```
During image build
```

---

`CMD`

```docker
CMD ["node","server.js"]
```

Occurs:

```
When container starts
```

This difference is asked frequently in interviews.

---

# 8. ENTRYPOINT

Suppose:

```docker
ENTRYPOINT ["node"]
```

Then:

```bash
docker run my-app server.js
```

becomes:

```bash
node server.js
```

Unlike `CMD`, `ENTRYPOINT` is harder to override.

For most Express applications:

Use `CMD`.

# Understanding Build Layers

```
FROM node

↓

WORKDIR

↓

COPY package.json

↓

RUN npm install

↓

COPY source

↓

CMD
```

Each instruction creates a new image layer.

---

# .dockerignore

Just like `.gitignore`, Docker has:

```
.dockerignore
```

Example:

```
node_modules
.git
.env
coverage
dist
```

Why?

You don't want Docker copying unnecessary files into the image.

---

# Bad Dockerfile

```docker
FROM node:22

COPY . .

RUN npm install
```

Problems:

- Copies everything
- Poor cache usage
- Larger image

---

# Better Dockerfile

```docker
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

CMD ["node","server.js"]
```

Much faster rebuilds.

---

# Build Context

When you run:

```bash
docker build .
```

Docker sends **everything in the current directory** to the Docker daemon.

Example:

```
project/

├── src
├── node_modules
├── videos
├── .git
```

Without `.dockerignore`, Docker sends all of it.

Large build contexts make builds slower.

# Common Mistakes

❌ Forgetting `.dockerignore`

Results in huge images.

---

❌ Copying everything first

Destroys Docker cache efficiency.

---

❌ Confusing `EXPOSE` with `-p`

`EXPOSE`

```
Documentation only
```

- `p`

```
Actually publishes the port
```

---

❌ Using `latest` everywhere

Pin image versions.

As your applications grow, your Dockerfiles will evolve beyond the basic template. A production-ready Node.js Dockerfile often includes:

- Multi-stage builds to reduce image size
- Non-root users for better security
- Health checks
- Optimized dependency installation
- Build-time and runtime environment separation
- Smaller base images such as Alpine or Debian Slim (when appropriate)
