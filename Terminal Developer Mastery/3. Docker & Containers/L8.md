# Docker Build Cache

Every Dockerfile instruction creates a layer.

```
FROM node:22
↓

WORKDIR /app
↓

COPY package.json
↓

RUN npm install
↓

COPY .
↓

CMD
```

Docker saves each layer in its cache.

---

# First Build

```bash
docker build -t my-app .
```

Output:

```
Step 1/6
Step 2/6
...
Step 6/6
```

Everything is built.

---

# Second Build

Nothing changed.

```bash
docker build -t my-app .
```

Docker reports:

```
Using cache
Using cache
Using cache
```

The build is much faster.

---

# Cache Invalidation

Suppose you change:

```
server.js
```

Docker rebuilds only:

```
COPY .

↓

CMD
```

Earlier layers stay cached.

---

# Bad Dockerfile

```docker
FROM node:22

COPY . .

RUN npm install

CMD ["node","server.js"]
```

Problem:

Every source code change causes:

```bash
npm install
```

to run again.

Very slow.

---

# Better Dockerfile

```docker
FROM node:22

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

CMD ["node","server.js"]
```

Now:

- Source code changes → Fast rebuild
- Dependency changes → Reinstall packages

---

# Understanding Layer Order

Good order:

```
Stable Layers

↓

Changing Layers
```

Example:

```
FROM

↓

WORKDIR

↓

COPY package.json

↓

RUN npm install

↓

COPY source
```

The more stable a layer is, the earlier it should appear.

---

# Cache Example

Only changed:

```
routes/user.js
```

Docker reuses:

```
✓ FROM

✓ WORKDIR

✓ COPY package.json

✓ npm install

↓

Rebuild

COPY .

CMD
```

Huge time savings.

# .dockerignore Review

Example:

```
node_modules
.git
.env
coverage
dist
*.log
```

Without `.dockerignore`:

```
Build Context

↓

Everything
```

With `.dockerignore`:

```
Only necessary files
```

Smaller build context means faster builds.

---

# Why Exclude node_modules?

Never copy:

```
node_modules
```

Reason:

```
Host

↓

Linux

↓

Docker Linux
```

Dependencies should be installed inside the container, not copied from the host.

---

# Build Context

Suppose:

```
project/

├── src
├── node_modules
├── videos
├── .git
├── screenshots
```

Running:

```bash
docker build .
```

sends everything to Docker unless ignored.

Large build contexts slow down every build.

# Multi-stage Builds

One of Docker's best features.

Instead of:

```
Build Image

↓

Production Image
```

Separate them.

---

# Traditional Build

```
Node

↓

Install Dependencies

↓

Build

↓

Development Tools

↓

Production
```

Everything ends up in the final image.

---

# Multi-stage Build

```
Builder Stage

↓

Compile

↓

Final Stage

↓

Only Runtime Files
```

Production image becomes much smaller.

---

# Example Project

```
project/

├── src
├── package.json
├── Dockerfile
```

---

# Stage 1

```docker
FROM node:22 AS builder

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

RUN npm run build
```

This stage:

- Installs dependencies
- Builds the project

---

# Stage 2

```docker
FROM node:22-slim

WORKDIR /app

COPY --from=builder /app/dist ./dist

COPY package*.json ./

RUN npm install --omit=dev

CMD ["node","dist/server.js"]
```

Notice:

```docker
COPY --from=builder
```

Only the built application is copied.

Development files stay behind.

---

# Visual Flow

```
Builder Image

↓

Compile

↓

dist/

↓

Copy

↓

Production Image
```

Only production files survive.

# Image Size Comparison

Example:

|Image|Size|
|---|---|
|Basic Node image|1.1 GB|
|node:slim|220 MB|
|node:alpine|70–120 MB (varies by app)|

Smaller images:

- Pull faster
- Push faster
- Deploy faster
- Reduce storage costs

---

# Alpine vs Slim

### Alpine

Pros:

- Extremely small
- Fast downloads

Cons:

- Some native Node modules need additional packages
- Debugging can be harder

---

### Slim

Pros:

- Easier compatibility
- Better for many Node applications

Cons:

- Larger than Alpine

---

# Which Should You Choose?

|Situation|Recommendation|
|---|---|
|Learning Docker|`node:22`|
|Production API|`node:22-slim` ⭐|
|Very small images|`node:22-alpine` (after testing)|

# Installing Production Dependencies

Instead of:

```bash
npm install
```

Use:

```bash
npm install --omit=dev
```

Development packages stay out of production.

Examples:

Keep:

```
express
mongoose
redis
```

Exclude:

```
eslint
prettier
nodemon
jest
```

---

# Build Arguments

Sometimes values are only needed while building.

```docker
ARG NODE_VERSION=22
```

Use:

```docker
FROM node:${NODE_VERSION}
```

Build:

```bash
docker build \
--build-arg NODE_VERSION=22 \
-t my-app .
```

---

# Environment Variables

Build time:

```docker
ARG API_URL
```

Runtime:

```docker
ENV NODE_ENV=production
```

Remember:

```
ARG

↓

Only during build

ENV

↓

Available inside running container
```

# Best Practices

### Put Stable Layers First

Good:

```
package.json

↓

npm install

↓

Application Code
```

---

### Always Use `.dockerignore`

Avoid copying unnecessary files.

---

### Use Multi-stage Builds

Especially for production.

---

### Install Only Production Dependencies

```bash
npm install --omit=dev
```

---

### Use Smaller Base Images

Prefer:

```
node:22-slim
```

for production unless your app specifically benefits from another base image.

---

# Common Mistakes

❌ Copying everything first

Breaks build cache.

---

❌ Shipping development dependencies

Makes images larger and less secure.

---

❌ Forgetting `.dockerignore`

Results in slower builds.

---

❌ Using one-stage builds for production

Leaves unnecessary build tools in the final image.

# Production Dockerfile Example

```docker
# Stage 1 - Build
FROM node:22 AS builder

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

RUN npm run build

# Stage 2 - Runtime
FROM node:22-slim

WORKDIR /app

COPY package*.json ./

RUN npm install --omit=dev

COPY --from=builder /app/dist ./dist

ENV NODE_ENV=production

EXPOSE 5000

CMD ["node", "dist/server.js"]
```

# 💡 Backend Engineer Insight

For a production Express API, a good Docker image should aim to be:

- ✅ Small (use a minimal runtime image)
- ✅ Fast to build (take advantage of Docker's layer cache)
- ✅ Secure (exclude development dependencies and unnecessary files)
- ✅ Reproducible (pin image versions and dependency versions)
- ✅ Easy to deploy (immutable image with environment-specific configuration)

Most professional backend teams spend time optimizing their Dockerfiles because faster CI/CD pipelines and smaller deployments improve both developer productivity and production reliability.
