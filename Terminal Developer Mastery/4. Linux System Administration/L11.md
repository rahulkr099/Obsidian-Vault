# The Four Core Resources

Almost every performance issue involves one or more of these:

```
CPU
 │
RAM
 │
Disk
 │
Network
```

Your investigation should always identify which resource is under pressure.

---

# First Health Check

Start with:

```
uptime
```

Example:

```
15:30:15 up 8 days, 3:10,
2 users,
load average: 0.42, 0.58, 0.71
```

---

# Understanding Load Average

Example:

```
0.50
```

means:

The CPU is mostly idle.

Example:

```
12.50
```

on a **4-core CPU** means:

Many processes are waiting for CPU time.

---

# Rule of Thumb

|CPU Cores|Healthy Load|
|---|---|
|2|< 2|
|4|< 4|
|8|< 8|
|16|< 16|

A load higher than the number of CPU cores for an extended period deserves investigation.

```

8G     3G    1G   400M   4G          4.8G
```

---

# Important Column

Focus on:

```
Available
```

Linux uses unused RAM as cache, so **Free** memory alone is not the best indicator.

---

# Memory Pressure

Signs:

- Swap increasing
- Available memory decreasing
- Slow applications
- Out-of-memory (OOM) kills

---

# Swap Usage

```
swapon--show
```

---

# OOM Killer

If RAM is exhausted:

```
Out of memory

Killed process 4521 (node)
```

Check:

```
dmesg |grep-i oom
```

or

```
journalctl-k |grep-i oom
```

# Disk Performance

CPU isn't always the bottleneck.

Sometimes:

```
Disk is slow.
```

Install if needed:

```
sudo apt install sysstat
```

---

# Disk Statistics

```
iostat-xz2
```

Meaning:

- Disk utilization
- Read/write speed
- Wait time
- Queue length

---

# Virtual Memory Statistics

```
vmstat2
```

Updates every two seconds.

Important columns:

|Column|Meaning|
|---|---|
|r|Runnable processes|
|b|Blocked processes|
|si|Swap in|
|so|Swap out|
|us|User CPU|
|sy|System CPU|
|id|Idle CPU|
|wa|I/O wait|

---

# I/O Wait

High:

```

```

means:

CPU is waiting for storage.

Fast CPUs can't compensate for slow disks.

# Process Monitoring

---

# Detailed Process

```
ps-fp PID
```

Replace `PID` with the process ID.

---

# Kill a Process

Graceful:

```
kill PID
```

Force:

```
kill-9 PID
```

Prefer `kill` first. `kill -9` should be a last resort because it doesn't allow the application to clean up.

# Real Production Scenario

Users complain:

```
API is slow.
```

Investigation:

```
User Complaint
      │
      ▼
uptime
(Check load)
      │
      ▼
htop
(Check CPU/RAM)
      │
      ▼
free -h
(Check available memory)
      │
      ▼
iostat -xz
(Check disk I/O)
      │
      ▼
ss -tulpn
(Check listening services)
      │
      ▼
journalctl -u backend
(Check errors)
      │
      ▼
curl localhost:5000
(Measure response time)
```

This systematic workflow is much more effective than restarting services immediately.

# Best Practices

### Start Broad

Use:

```
uptime
```

before diving into specific metrics.

---

### Monitor Continuously

Use:

```
watch
```

or interactive tools like `htop` and `btop`.

---

### Check Logs Alongside Metrics

High CPU without logs may indicate an infinite loop. High memory with OOM logs suggests a different problem.

---

### Prefer Graceful Shutdowns

Try:

```
kill PID
```

before:

```
kill-9 PID
```

---

### Monitor Trends

A server that's slowly consuming memory over days often points to a memory leak.

---

# Common Mistakes

❌ Looking only at CPU usage.

---

❌ Assuming low "Free" RAM means the system is out of memory.

---

❌ Ignoring swap usage.

---

❌ Restarting applications before collecting evidence.

---

❌ Focusing on one metric while ignoring disk or network bottlenecks.

# 💡 Senior Backend Engineer Insight

Experienced engineers diagnose performance issues in a consistent order instead of jumping to conclusions.

```
User reports slowness
        │
        ▼
uptime
(Check load)
        │
        ▼
htop / btop
(Check CPU & RAM)
        │
        ▼
free -h
(Check available memory & swap)
        │
        ▼
iostat -xz
(Check disk I/O)
        │
        ▼
ss -tun
(Check network connections)
        │
        ▼
journalctl -u backend
(Check application logs)
        │
        ▼
curl -w
(Measure response time)
        │
        ▼
Identify the bottleneck
        │
        ▼
Apply the appropriate fix
```

The key is **collect evidence first, optimize second**. This disciplined approach leads to faster and more reliable troubleshooting.
