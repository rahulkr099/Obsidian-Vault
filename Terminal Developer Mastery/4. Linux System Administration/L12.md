# Module 4 — Lesson 12: Linux Security 🔒

> **"Security isn't a feature you add later. It's part of every backend deployment."**

Most Linux servers aren't hacked because of advanced exploits. They're compromised because of simple mistakes:

- Weak passwords
- Root login enabled
- Open ports
- Outdated software
- Leaked API keys
- Incorrect file permissions
- Running everything as `root`

As a backend engineer, your goal is to **reduce risk by following good security practices**.

Linux security is built in layers.

```
Internet
    │
    ▼

    ▼

    ▼
User Permissions
```

# Principle of Least Privilege

One of the most important security concepts.

Give users and applications **only the permissions they actually need**.

Example:

❌ Bad

```
Application runs as root
```

✅ Better

```
Application runs as nodeapp
```

---

# Never Run Everything as Root

Create a dedicated service user:

```bash
sudo adduser --system nodeapp
```

Run your backend with:

```
User=nodeapp
```

inside your `systemd` service.

---

# Check Current User

```bash

```

Check identity:

```bash

```

Example:

```
uid=1000(rahul)

```

---

# File Permissions

Review permissions:

```bash
ls -l
```

Sensitive files:

```
.env

id_ed25519

database backups
```

should not be world-readable.

---

# Secure a Secret File

```bash
chmod 600 .env
```

Meaning:

```
Owner → Read + Write

Everyone else → No access
```

---

# Secure SSH Keys

Private key:

```bash
chmod 600 ~/.ssh/id_ed25519
```

Directory:

```bash
chmod 700 ~/.ssh
```

---

# Password Security

Generate strong passwords.

Avoid:

```
password123

admin123

qwerty
```

Prefer:

- Long passphrases
- Password managers
- Unique passwords per service

---

# Keep Software Updated

Regularly run:

```bash
sudo apt update

sudo apt upgrade
```

Security patches often fix known vulnerabilities.

---

# Check Upgradable Packages

```bash
apt list --upgradable
```

---

# Automatic Security Updates

Install:

```bash
sudo apt install unattended-upgrades
```

Enable:

```bash
sudo dpkg-reconfigure unattended-upgrades
```

This can automatically install eligible security updates.

# Firewall

Ubuntu/Linux Mint uses **UFW** (Uncomplicated Firewall).

Check status:

```bash
sudo ufw status
```

---

# Enable Firewall

```bash
sudo ufw enable
```

Verify:

```bash
sudo ufw status verbose
```

---

# Allow SSH

Before enabling UFW on a remote server:

```bash
sudo ufw allow OpenSSH
```

or

```bash
sudo ufw allow 22/tcp
```

⚠️ **Always allow SSH before enabling the firewall on a remote server**, or you may lock yourself out.

---

# Allow HTTP & HTTPS

```bash
sudo ufw allow 80/tcp

sudo ufw allow 443/tcp
```

---

# Allow Backend Port (Development Only)

```bash
sudo ufw allow 5000/tcp
```

In production, it's usually better to expose only Nginx (80/443) and keep the backend accessible only locally or through the reverse proxy.

---

# Remove a Rule

List numbered rules:

```bash
sudo ufw status numbered
```

Delete:

```bash
sudo ufw delete NUMBER
```

---

# SSH Hardening

Configuration:

```
/etc/ssh/sshd_config
```

Recommended settings:

```
PermitRootLogin no

PasswordAuthentication no

PubkeyAuthentication yes
```

Restart:

```bash
sudo systemctl restart ssh
```

---

# Verify SSH Service

```bash
systemctl status ssh
```

Logs:

```bash
journalctl -u ssh
```

---

# Fail2Ban

Protects against repeated login attempts.

Install:

```bash
sudo apt install fail2ban
```

Enable:

```bash
sudo systemctl enable --now fail2ban
```

Status:

```bash
sudo fail2ban-client status
```

SSH jail:

```bash
sudo fail2ban-client status sshd
```

---

# Check Listening Ports

```bash
ss -tulpn
```

Ask yourself:

> "Does every listening port really need to be accessible?"

---

# Open Ports Example

```
22  SSH

80  HTTP

443 HTTPS
```

Everything else should be justified.

---

# Verify Running Services

```bash
systemctl list-units --type=service
```

Disable unnecessary services to reduce the attack surface.

---

# Environment Variables

Store secrets in:

```
.env
```

Never hardcode:

- API keys
- Database passwords
- JWT secrets
- OAuth secrets

Example:

```
JWT_SECRET=super-secret-key

DATABASE_URL=...
```

---

# Never Commit Secrets

Bad:

```
GitHub

↓

.env
```

Good:

```
.gitignore

↓

.env
```

Example:

```
# .gitignore

.env
```

---

# Check Git Status

Before pushing:

```bash
git status
```

Verify that secret files are not staged.

---

# Generate Secure Secrets

Example:

```bash
openssl rand -hex 32
```

Sample output:

```
9b3d0d5b...
```

Ideal for JWT secrets or API keys.

---

# Secure File Transfer

Use:

```bash
scp
```

or

```bash
rsync
```

Avoid unencrypted protocols like FTP for production systems.

---

# HTTPS

Always encrypt traffic.

Typical production setup:

```
Browser

↓

HTTPS

↓

Nginx

↓

Node.js
```

TLS termination usually happens at Nginx or another reverse proxy.

---

# Verify Certificates

```bash
openssl s_client -connect example.com:443
```

Useful for debugging TLS issues.

---

# Sudo

Run privileged commands only when necessary.

Instead of:

```bash
sudo -i
```

prefer:

```bash
sudo apt update
```

Use elevated privileges for the specific command rather than the entire session.

---

# Audit Failed Logins

Ubuntu/Linux Mint:

```bash
grep "Failed password" /var/log/auth.log
```

Successful logins:

```bash
grep "Accepted" /var/log/auth.log
```

---

# Find World-Writable Files

```bash
find / -type f -perm -002 2>/dev/null
```

Review results carefully before changing permissions.

---

# Check File Ownership

```bash
ls -l
```

or

```bash
stat filename
```

---

# Verify Installed Packages

```bash
dpkg -l
```

Remove software you no longer need.

---

# Check Scheduled Jobs

```bash
crontab -l

sudo ls /etc/cron.d
```

Unexpected scheduled tasks deserve investigation.

---

# Docker Security

Avoid:

```
docker run --privileged
```

unless you fully understand why it's required.

Prefer:

- Minimal images
- Non-root containers
- Read-only filesystems when practical

# Production Security Checklist

Before deploying a Node.js backend:

```
✓ System updated
✓ SSH keys configured
✓ Root login disabled
✓ Password authentication disabled (after verifying key access)
✓ UFW enabled
✓ Only ports 80 & 443 exposed
✓ Backend runs as non-root user
✓ .env secured
✓ .env ignored by Git
✓ Fail2Ban enabled
✓ HTTPS configured
✓ Automatic security updates configured
✓ Logs monitored
✓ Backups tested
```

# Best Practices

### Use Dedicated Service Accounts

Run applications as users like:

```
nodeapp
```

instead of `root`.

---

### Protect Secrets

Store them in environment variables or secure secret-management systems—not in source code.

---

### Keep Systems Updated

Install security patches regularly.

---

### Minimize the Attack Surface

Disable unnecessary services and close unused ports.

---

### Monitor Security Logs

Review authentication failures and unusual activity.

---

# Common Mistakes

❌ Committing `.env` to Git.

---

❌ Running production applications as `root`.

---

❌ Leaving password authentication enabled after confirming SSH key access (if your environment allows disabling it).

---

❌ Exposing databases directly to the internet.

---

❌ Opening unnecessary firewall ports.

# 💡 Senior Backend Engineer Insight

Strong Linux security isn't about one tool—it's about combining multiple defenses.

A typical production hardening workflow looks like this:

```
Fresh Linux Server
        │
        ▼
Update Packages
        │
        ▼
Create Non-Root User
        │
        ▼
Configure SSH Keys
        │
        ▼
Disable Root Login
        │
        ▼
Enable Firewall
        │
        ▼
Install Fail2Ban
        │
        ▼
Deploy Backend as nodeapp
        │
        ▼
Secure .env
        │
        ▼
Enable HTTPS
        │
        ▼
Monitor Logs & Keep Updated
```

No single step makes a server secure, but together they significantly reduce the attack surface and improve resilience.
