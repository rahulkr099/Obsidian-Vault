# What is a Process?

A **process** is simply a running program.

Example:

```
Code
    │
    ▼
Execution
    │
    ▼
Process
```

Examples:

```
Firefox

Node.js

MongoDB

Redis

Docker

Neovim

Git
```

Each running program gets a unique identifier called a **PID (Process ID).**

---

# Viewing Running Processes

Basic command:

```bash
ps
```

Typical output:

```
PID TTY      TIME CMD

2389 pts/0   00:00 zsh

2510 pts/0   00:00 ps
```

This only shows processes attached to your current terminal.

---

# View All Processes

```bash
ps -ef
```

or

```bash
ps aux
```

Example:

```
USER   PID  %CPU %MEM COMMAND

root     1   0.1  0.2 systemd

rahul  2048  1.3  3.4 node

redis  1450  0.2  0.5 redis-server
```

This is one of the most frequently used commands on Linux servers.

---

# Understanding ps Output

Example:

```
USER PID %CPU %MEM COMMAND
```

|Column|Meaning|
|---|---|
|USER|Process owner|
|PID|Process ID|
|%CPU|CPU usage|
|%MEM|Memory usage|
|COMMAND|Executable|

---

# Process Tree

View parent-child relationships:

```bash
pstree
```

Example:

```
systemd
├── NetworkManager
├── docker
├── sshd
├── node
└── nginx
```

This helps you understand how processes relate to each other.

---

# Process IDs

Every process has a PID.

Example:

```
Node.js

PID 3456
```

Find your shell PID:

```bash
echo $$
```

Current shell:


# Find a Process

Using `pgrep`:

```bash
pgrep node
```

Example:

```
3156
```

Show names too:

```bash
pgrep -a node
```

Output:

```
3156 node server.js
```

# Search with grep

```bash
ps aux | grep node
```

Useful when you want more detailed information.

# Live Process Monitoring

Run:

```bash
top
```

Shows:

- CPU usage
- RAM usage
- Running processes
- Load average
- Uptime

Refreshes automatically.

Quit:

```
q
```

# Better Alternative: htop

If installed:

# Even Better: btop

You've already installed `btop`.

Run:


# CPU Usage

Inside `top`:

```
%CPU
```

Meaning:

```
100%

↓

One CPU core fully utilized
```

On multi-core systems, percentages can exceed 100% for multi-threaded workloads.

---

# Memory Usage

Look for:

```
%MEM
```

Example:

```
node

4.2%
```

Large memory growth over time may indicate a memory leak.

---

# Finding Port Usage

Which process uses port 5000?

```bash
sudo ss -tulpn | grep :5000
```

Example:

```
LISTEN

5000

node
```

This is invaluable when you see:

```
EADDRINUSE
```

---

# Kill a Process

Graceful termination:

```bash
kill PID
```

Example:

```bash
kill 3456
```

This sends **SIGTERM (15)**, giving the application a chance to shut down cleanly.

---

# Force Kill

```bash
kill -9 PID
```

Example:

```bash
kill -9 3456
```

This sends **SIGKILL**, which the process cannot ignore.

⚠️ Use this only when a graceful shutdown fails.

---

# Kill by Name

```bash
pkill node
```

Kills all matching Node.js processes owned by you.

Specific:

```bash
pkill -f server.js
```

---

# killall

```bash
killall node
```

Also kills processes by name.

---

# Common Signals

|Signal|Number|Purpose|
|---|---|---|
|SIGTERM|15|Graceful stop|
|SIGKILL|9|Force stop|
|SIGINT|2|Ctrl+C|
|SIGHUP|1|Reload configuration (many daemons)|

# Background Jobs

Run:

```bash
sleep 60
```

Terminal waits.

Instead:

```bash
sleep 60 &
```

Output:

```
[1] 4321
```

Now it runs in the background.

---

# View Background Jobs

```bash
jobs
```

Example:

```
[1]+ Running sleep 60 &
```

---

# Bring Back to Foreground

```bash
fg
```

---

# Pause a Process

Press:

```
Ctrl+Z
```

Output:

```
Stopped
```

Resume:

Foreground:

```bash
fg
```

Background:

```bash
bg
```

---

# nohup

Keep a process running after logout:

```bash
nohup node server.js &
```

Output goes to:

```
nohup.out
```

Historically useful for long-running jobs. For production services, you'll later learn to use `systemd` instead.

---

# Nice Values (Priority)

Linux schedules CPU time using priorities.

Default:

```
0
```

Lower nice value:

```
Higher Priority
```

Higher nice value:

```
Lower Priority
```

Range:

```
-20

↓

Highest Priority

↓

19

Lowest Priority
```

---

# Start with Lower Priority

```bash
nice -n 10 node server.js
```

---

# Change Priority

```bash
renice 10 PID
```

Higher-priority (negative) values usually require elevated privileges.

---

# View Priority

```bash
ps -o pid,ni,comm
```

Example:

```
PID NI COMMAND

3210 0 node

4500 10 python
```

---

# Load Average

View:

```bash
uptime
```

Example:

```
load average:

0.45

0.60

0.70
```

Three numbers represent averages over:

- 1 minute
- 5 minutes
- 15 minutes

A load close to the number of CPU cores often indicates full utilization.

---

# Zombie Processes

Sometimes:

```
STAT

↓

Z
```

Zombie means:

- Process has exited.
- Parent hasn't collected its exit status yet.

Usually, you fix the parent process rather than trying to kill the zombie itself.

---

# Process States

|State|Meaning|
|---|---|
|R|Running|
|S|Sleeping|
|D|Uninterruptible sleep (often waiting on I/O)|
|T|Stopped|
|Z|Zombie|


# Best Practices

### Use SIGTERM First

```bash
kill PID
```

Only use `kill -9` if necessary.

---

### Monitor Before Killing

Use:

```bash
top
```

or:

```bash
btop
```

Understand the problem before acting.

---

### Prefer `systemd` for Services

Avoid relying on `nohup` for production applications.

---

### Investigate High Resource Usage

Check logs, application behavior, and system metrics before restarting processes.

---

# Common Mistakes

❌ Using `kill -9` immediately.

---

❌ Killing the wrong PID.

---

❌ Running production apps in the foreground.

---

❌ Ignoring high memory usage.

---

❌ Forgetting that background jobs stop when the shell exits (unless managed by tools like `nohup` or `systemd`).

# 💡 Senior Backend Engineer Insight

When a backend service goes down, experienced engineers usually follow a consistent workflow instead of guessing:

```
Service Down
     │
     ▼
Is the process running?
     │
     ▼
Check logs
     │
     ▼
Check CPU & Memory
     │
     ▼
Check Port Binding
     │
     ▼
Restart Gracefully
     │
     ▼
Verify Health Endpoint
```

A repeatable process like this helps you solve production incidents quickly and reduces the risk of making the situation worse.
