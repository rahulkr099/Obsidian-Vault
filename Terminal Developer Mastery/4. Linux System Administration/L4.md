# Module 4 — Lesson 4: Services & systemd ⚙️

> **"In production, you don't start your backend with `node server.js`. You let `systemd` manage it."**

`systemd` is the service manager used by most modern Linux distributions (Ubuntu, Debian, Fedora, Linux Mint, RHEL, etc.).

It automatically:

- Starts services during boot
- Restarts crashed services
- Collects logs
- Tracks service status
- Manages dependencies

If you deploy Node.js applications to Linux servers, you'll use `systemd` regularly.

# What is systemd?

Think of `systemd` as the operating system's service manager.

```
Computer Boots
      │
      ▼
systemd Starts
      │
      ├── Network
      ├── SSH
      ├── Docker
      ├── Nginx
      ├── MongoDB
      └── Your Backend
```

Instead of manually starting applications every time the server reboots:

```bash
node server.js
```

`systemd` does it automatically.

Check PID 1:

On most Linux systems, PID 1 is `systemd`.

# Anatomy of a Service File

Location:

```
/etc/systemd/system/
```

Example:

```
my-backend.service
```

A service file is a plain text configuration.

---

# Basic Service File

```
[Unit]
Description=My Node Backend
After=network.target

[Service]
Type=simple
User=nodeapp
WorkingDirectory=/opt/backend
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

---

# Understanding Each Section

## [Unit]

General information.

```
Description=My Backend API
```

Human-readable description.

```
After=network.target
```

Start after networking is available.

---

## [Service]

The application's runtime configuration.

```
User=nodeapp
```

Run as:

```
nodeapp
```

Not:

```
root
```

---

```
WorkingDirectory=/opt/backend
```

Equivalent to:

```bash
cd /opt/backend
```

before starting.

---

```
ExecStart=/usr/bin/node server.js
```

Command to run.

---

```
Restart=always
```

If application crashes:

```
systemd

↓

Restart
```

---

```
RestartSec=5
```

Wait five seconds before restarting.

---

## [Install]

```
WantedBy=multi-user.target
```

Allows the service to start during the normal multi-user boot process.

# Logs with journalctl

Every service has logs.

Show backend logs:

```bash
journalctl -u backend
```

Latest logs:

```bash
journalctl -u backend -n 50
```

Follow logs live:

```bash
journalctl -u backend -f
```

This is similar to:

```bash
tail -f logfile
```

but works directly with the system journal.

---

# Boot Logs

View logs from the current boot:

```bash

```

Previous boot:

```bash

```

Very useful after reboot-related issues.

# Restart on Failure

```
Restart=on-failure
```

or

```
Restart=always
```

Difference:

|Option|Behavior|
|---|---|
|`on-failure`|Restarts only if the process exits with an error or crashes|
|`always`|Restarts after almost every exit, even if the application exits normally|

For long-running backend servers, `Restart=on-failure` is often a sensible default.

# Environment Variables

Avoid:

```jsx
const PORT = 5000;
```

Instead:

```
Environment=PORT=5000
Environment=NODE_ENV=production
```

Or better:

```
EnvironmentFile=/opt/backend/.env
```

This keeps configuration separate from the service definition.

# Common Startup Failures

### Wrong Node Path

Find Node:

```bash
which node
```

Example:

```
/usr/bin/node
```

Use that path in `ExecStart`.

---

### Wrong Working Directory

If `WorkingDirectory` is incorrect:

```
Cannot find package.json
```

or

```
Cannot find module
```

---

### Permission Problem

Check:

```bash
ls -ld /opt/backend
```

Ensure the service user has access.

---

### Environment Variables Missing

Check the journal:

```bash
journalctl -u backend -n 20
```

Look for messages such as:

```
Missing JWT_SECRET
```

---

# Real Backend Example

Create a dedicated service account:

```bash
sudo adduser --system nodeapp
```

Set ownership:

```bash
sudo chown -R nodeapp:nodeapp /opt/backend
```

Run service as:

```
User=nodeapp
```

This follows the principle of least privilege.

# 💡 Senior Backend Engineer Insight

Many beginners use **PM2** to keep Node.js applications running. PM2 is a great process manager for Node.js, but experienced Linux administrators often think in layers:

```
Node.js Application
        │
        ▼
PM2 (optional)
        │
        ▼
systemd
        │
        ▼
Linux
```

For a **single backend application on a Linux server**, `systemd` alone is often sufficient.

For **Node.js clusters**, advanced log management, or zero-downtime reloads, PM2 can add useful features. Understanding `systemd` first gives you a solid foundation because it manages not only Node.js applications, but also Docker, Nginx, databases, and most other services running on Linux.
