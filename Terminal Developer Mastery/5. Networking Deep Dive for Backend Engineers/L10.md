# Module 5 — Lesson 10: API Security 🛡️

> **"A working API is not enough. A secure API is what survives production."**

Most successful cyberattacks exploit **simple mistakes**:

- Missing authentication
- Weak authorization
- Poor input validation
- Exposed secrets
- Missing rate limiting

As a backend engineer, your responsibility is to assume that **every request is potentially malicious**.

# Authentication vs Authorization

## Authentication

Question:

> **Who are you?**

Example:

```
Login

↓

Email + Password

↓

JWT Issued
```

---

## Authorization

Question:

> **What are you allowed to do?**

Example:

```
User

↓

Delete Another User?

↓

❌ Forbidden
```

---

# Password Security

Never store:

```
password123
```

Instead:

```
$2b$12$7H...
```

Always hash passwords.

---

# Hashing with bcrypt

Install:

```bash
npm install bcrypt
```

Hash:

```jsx
import bcrypt from "bcrypt";

const hashedPassword = await bcrypt.hash(password, 12);
```

Verify:

```jsx
const isValid = await bcrypt.compare(
    password,
    user.password
);
```

---

# Why Hashing?

Even if the database leaks:

```
password123
```

becomes

```
$2b$12$98asd9...
```

Attackers don't immediately know the original password.

# JWT Middleware

```jsx
export const authenticate = (req, res, next) => {

    const auth = req.headers.authorization;

    if (!auth?.startsWith("Bearer ")) {
        return res.sendStatus(401);
    }

    next();

};
```

In production, also verify the token signature and claims.

---

# Authorization Middleware

Example:

```jsx
if (req.user.role !== "admin") {
    return res.sendStatus(403);
}
```

Authentication:

```
User exists
```

Authorization:

```
User may perform action
```

---

# Principle of Least Privilege

Users should have only the permissions they need.

Example:

```
Admin

Create Users ✓

Delete Users ✓

Manage Roles ✓
```

```
Normal User

Read Profile ✓

Edit Own Profile ✓

Delete All Users ❌
```

# Input Validation

Never trust:

```json
{
    "age": -500
}
```

Validate:

- Required fields
- Data type
- Length
- Format
- Range

---

# Joi Validation

Install:

```bash
npm install joi
```

Example:

```jsx
const schema = Joi.object({
    email: Joi.string().email().required(),
    password: Joi.string().min(8).required()
});
```

---

# Sanitization

Validation checks whether data is acceptable.

Sanitization modifies data into a safer form.

Example:

Input:

```
   Rahul
```

Sanitized:

```
Rahul
```

---

# SQL Injection

Unsafe:

```sql
SELECT * FROM users
WHERE email = 'input'
```

Attacker enters:

```sql
' OR 1=1 --
```

Query becomes unsafe.

---

# Prevent SQL Injection

Use:

- Parameterized queries
- Prepared statements
- ORM/query builders

Never concatenate raw user input into SQL queries.

---

# NoSQL Injection

Unsafe:

```jsx
User.findOne(req.body);
```

Malicious input:

```json
{
    "email": {
        "$ne": null
    }
}
```

Always validate and whitelist expected fields before querying.

---

# XSS (Cross-Site Scripting)

Attacker submits:

```html
<script>alert("Hacked")</script>
```

If rendered without escaping:

```
Browser

↓

Runs JavaScript
```

---

# Prevent XSS

- Escape user-generated HTML
- Sanitize rich text
- Use appropriate output encoding
- Set a strong Content Security Policy (CSP)

---

# CSRF (Cross-Site Request Forgery)

Victim is logged in.

Attacker tricks them into visiting a malicious page.

That page silently submits:

```
POST /transfer-money
```

Browser may include cookies automatically.

---

# Prevent CSRF

Common defenses:

- CSRF tokens
- `SameSite` cookies
- Origin/Referer validation for sensitive actions

---

# Helmet

Install:

```bash
npm install helmet
```

Use:

```jsx
import helmet from "helmet";

app.use(helmet());
```

Helmet sets several helpful HTTP security headers.

---

# Useful Security Headers

Examples:

```
X-Content-Type-Options: nosniff

X-Frame-Options: SAMEORIGIN

Referrer-Policy: no-referrer
```

Modern Helmet configures many of these automatically.

---

# Rate Limiting

Protects against:

- Brute-force attacks
- API abuse
- Basic denial-of-service attempts

Install:

```bash
npm install express-rate-limit
```

Example:

```jsx
import rateLimit from "express-rate-limit";

const limiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    limit: 100
});

app.use(limiter);
```

---

# API Keys

Useful for:

- Third-party integrations
- Internal services
- Public developer APIs

Example:

```
x-api-key: abc123
```

Remember:

API keys identify clients but are **not** a replacement for user authentication.

---

# Secrets

Never write:

```jsx
const JWT_SECRET = "secret123";
```

Instead:

```
JWT_SECRET=very-long-random-secret
```

Read it:

```jsx
process.env.JWT_SECRET
```

---

# Secure File Uploads

Always verify:

- File type
- File size
- File extension
- MIME type (don't rely on it alone)
- Scan uploads if required

Never trust the filename from the client.

---

# Logging

Log:

```
Login Success

Failed Login

Unauthorized Access

Server Errors
```

Don't log:

- Passwords
- JWTs
- Refresh tokens
- API secrets

# Express Security Stack

```jsx
app.use(helmet());

app.use(cors(corsOptions));

app.use(rateLimiter);

app.use(express.json());

app.use(authenticate);
```

Keep route-specific authentication where appropriate rather than protecting every route globally.

# Common Vulnerabilities

|Vulnerability|Prevention|
|---|---|
|SQL Injection|Parameterized queries|
|NoSQL Injection|Validate input|
|XSS|Escape/sanitize output|
|CSRF|Tokens + SameSite|
|Brute Force|Rate limiting|
|Password Leak|bcrypt|
|MITM|HTTPS|
|Secret Exposure|Environment variables|

# Best Practices

### Hash Every Password

Never store plaintext passwords.

---

### Validate Every Request

Treat every client input as untrusted.

---

### Use HTTPS

Protect all authentication traffic.

---

### Apply Least Privilege

Grant only the permissions required.

---

### Store Secrets Outside Source Code

Use environment variables or a dedicated secret manager.

---

### Keep Dependencies Updated

Regularly update packages to receive security fixes.

# 💡 Senior Backend Engineer Insight

A mature backend doesn't rely on a single security feature. It combines multiple defenses so that if one layer fails, others still protect the application.

```
                Internet
                    │
                    ▼
           HTTPS (TLS Encryption)
                    │
                    ▼
        Nginx + Rate Limiting
                    │
                    ▼
         Helmet Security Headers
                    │
                    ▼
       Authentication (JWT/Session)
                    │
                    ▼
    Authorization (Role-Based Access)
                    │
                    ▼
     Input Validation & Sanitization
                    │
                    ▼
        Business Logic & Database
```

Security is a continuous process, not a one-time task. Every new endpoint should prompt questions such as:

- Who can access this?
- What input is accepted?
- How is it validated?
- What happens if someone abuses it?
- What sensitive information could be exposed?

Thinking this way helps you build APIs that remain reliable even when exposed to the public Internet.
