# What is Performance?

Performance is measured by:

```
Request

↓

Server

↓

Response
```

Important metrics:

- Response Time (Latency)
- Throughput (Requests/Second)
- CPU Usage
- Memory Usage
- Database Query Time
- Network Usage

---

# Latency vs Throughput

## Latency

How long **one request** takes.

Example:

```
GET /users

↓

120 ms
```

---

## Throughput

How many requests the server handles.

Example:

```
2,000 Requests/Second
```

---

# Where Does Time Go?

Typical API request:

```
Browser
    │
Network (20ms)
    │
Nginx (2ms)
    │
Express (5ms)
    │
MongoDB (60ms)
    │
Response (20ms)
```

Most of the time is often spent waiting for the database.

---

# What is Caching?

Caching means:

> **Store expensive results so you don't compute them again.**

Instead of:

```
Request

↓

Database

↓

Response
```

Use:

```
Request

↓

Cache

↓

Response
```

Much faster.

---

# Types of Cache

```
Caching

├── Browser Cache

└── Database Cache
```

# Browser Cache

Browser stores:

- CSS
- JavaScript
- Images
- Fonts

Example:

First visit:

```
Browser

Download logo.png
```

Second visit:

```
Browser

↓

↓

No Download
```

---

# Cache-Control Header

Example:

```
Cache-Control: public, max-age=3600
```

Meaning:

- Cache publicly
- Valid for one hour

---

# Common Cache-Control Values

```
no-store
```

Never cache.

---

```
no-cache
```

Revalidate before using.

---

```
public
```

Anyone may cache.

---

```
private
```

Only browser caches.

---

# ETag

ETag = Entity Tag

Server:

```
ETag: "abc123"
```

Browser stores it.

Later:

```
If-None-Match: "abc123"
```

If unchanged:

```
304 Not Modified
```

No response body is sent.

---

# ETag Flow

```
First Request

↓

200 OK

↓

ETag Stored

↓

Second Request

↓

If-None-Match

↓

304
```

Saves bandwidth.

# Redis

Redis is an **in-memory key-value database**.

Perfect for caching.

Example:

```
Key

↓

user:15

↓

Value

↓

JSON
```

Redis is much faster than disk-backed databases for cache lookups.

---

# Redis Cache Flow

Without Redis:

```
Request

↓

MongoDB

↓

Response
```

With Redis:

```
Request

↓

Redis

↓

Found?

↓

YES

↓

Response

↓

NO

↓

MongoDB

↓

Store in Redis

↓

Response
```

# Pagination

Never return:

```
1 Million Users
```

Instead:

```
20 Users
```

per page.

---

# Skip & Limit

Example:

```
User.find().skip(40).limit(20);
```

---

# Cursor-Based Pagination

Better for very large datasets.

Example:

```
After ID

↓

Next 20 Results
```

Often more efficient than large `skip()` values.

---

# Projection

Don't fetch unnecessary fields.

Bad:

```
User.find();
```

Good:

```
User.find().select("name email");
```

Less data.

Faster queries.

---

# Lean Queries

Mongoose:

```
User.find().lean();
```

Returns plain JavaScript objects.

Uses less memory and avoids Mongoose document overhead.

---

# Compression

Nginx:

```

```

```

```

Smaller responses.

# Best Practices

### Cache Frequently Read Data

Avoid repeatedly querying unchanged data.

---

### Set Reasonable TTLs

Cached data should eventually expire or be invalidated.

---

### Index Fields Used in Queries

Especially fields used in filtering, sorting, and joins/lookups.

---

### Return Only Required Fields

Use projections to reduce network and memory usage.

---

### Measure Before Optimizing

Use metrics and profiling tools to find real bottlenecks.

---

# Common Mistakes

❌ Caching everything indefinitely.

---

❌ Creating unnecessary indexes (they speed up reads but slow writes and consume storage).

---

❌ Returning huge datasets without pagination.

---

❌ Optimizing code before identifying the bottleneck.

# 💡 Senior Backend Engineer Insight

A high-performance production backend is built by optimizing **the entire request lifecycle**, not just a single function.

```
                Client Request
                      │
                      ▼
          Browser Cache (Cache-Control/ETag)
                      │
                      ▼
           CDN / Reverse Proxy Cache
                      │
                      ▼
             Nginx (Compression)
                      │
                      ▼
                Express Server
                      │
          Redis Cache (Cache Hit?)
              │               │
             Yes             No
              │               ▼
              │          MongoDB Query
              │               │
              └──────► Store in Redis
                      │
                      ▼
                 Send Response
```

When an API becomes slow, don't immediately assume your Node.js code is the problem. Measure each layer:

- Is the network slow?
- Is the cache being used?
- Is the database missing an index?
- Are you returning too much data?
- Is compression enabled?
- Are repeated queries being executed unnecessarily?

This systematic approach is what distinguishes experienced backend engineers from developers who optimize by guesswork.
