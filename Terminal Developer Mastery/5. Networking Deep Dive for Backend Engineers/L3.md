# Module 5 — Lesson 3: DNS Deep Dive 🌍

> **"The Internet doesn't understand domain names. It understands IP addresses."**

When you type:

```
<https://github.com>
```

your browser **cannot** connect to `github.com` directly.

It must first answer one question:

> **"What is the IP address of [github.com](http://github.com)?"**

That entire process is called **DNS (Domain Name System)**.

# What is DNS?

DNS stands for:

> **Domain Name System**

It translates:

```
google.com
```

into

```
142.250.xxx.xxx
```

Think of DNS as the **phonebook of the Internet**.

---

# Why Do We Need DNS?

Humans remember:

```
github.com
```

Computers communicate using:

```
140.82.121.3
```

DNS bridges that gap.

---

# Simple DNS Flow

```

    ▼
```

# The Complete Journey

Suppose you visit:

```
<https://example.com>
```

The browser performs:

```
Browser
     │
     ▼
Check Browser Cache
     │
     ▼
Check Operating System Cache
     │
     ▼
Check Router Cache
     │
     ▼
Ask Recursive Resolver
     │
     ▼
Root DNS Server
     │
     ▼
TLD Server
     │
     ▼
Authoritative Server
     │
     ▼
IP Address
     │
     ▼
Browser Connects
```

Only after getting the IP address can the TCP connection begin.

---

# DNS Components

## Browser Cache

Browsers cache recent DNS lookups.

Benefit:

- Faster browsing
- Less network traffic

---

## OS Cache

Linux also caches DNS (depending on your resolver configuration).

This avoids unnecessary repeated lookups.

---

## Recursive Resolver

Usually provided by:

- ISP
- Google DNS
- Cloudflare DNS

Example:

```
1.1.1.1
```

or

```
8.8.8.8
```

Its job is to find the answer on your behalf.

---

# Root Name Servers

The resolver first asks:

```
Where is .com?
```

Root servers don't know the IP of `github.com`.

They only know where the `.com` servers are.

---

# TLD Servers

TLD means:

**Top Level Domain**

Examples:

```
.com
.org
.net
.dev
.io
.in
```

The `.com` server answers:

> "Ask GitHub's authoritative server."

---

# Authoritative Name Server

This server owns the official DNS records.

It finally replies:

```
github.com

↓

140.82.xxx.xxx
```

Resolution complete.

# DNS Records

Different record types serve different purposes.

---

# A Record

Maps:

```
Domain

↓

IPv4 Address
```

Example:

```
example.com

↓

93.184.216.34
```

---

# AAAA Record

Maps:

```
Domain

↓

IPv6 Address
```

---

# CNAME Record

Alias.

Example:

```
www.example.com

↓

example.com
```

Instead of pointing directly to an IP, it points to another hostname.

---

# MX Record

Mail server.

Example:

```
gmail.com

↓

Google Mail Servers
```

Email delivery depends on MX records.

---

# TXT Record

Stores arbitrary text.

Often used for:

- Domain verification
- SPF
- DKIM
- DMARC

Example:

```
google-site-verification=...
```

---

# NS Record

Specifies which name servers are authoritative for a domain.

Example:

```
example.com

↓

ns1.provider.com

ns2.provider.com
```

---

# TTL (Time To Live)

DNS responses include a TTL.

Example:

```
300 seconds
```

Meaning:

> Cache this answer for 5 minutes.

---

# Why TTL Matters

Suppose:

```
Old IP

↓

New IP
```

Browsers and resolvers may continue using the old IP until the TTL expires.

This explains why DNS changes don't always appear instantly.

---

# DNS Caching

Caching occurs at multiple levels.

```
Browser

↓

Operating System

↓

Router

↓

ISP Resolver
```

Caching improves speed and reduces load.

Example:

```bash

```

---

# DNS Propagation

After changing DNS:

```
Old Record

↓

New Record
```

The update spreads gradually as caches expire.

This process is commonly called **DNS propagation**, although the records themselves don't physically travel around the Internet.

---

# Backend Example

Suppose your backend is hosted on:

```

```

You create:

```

```

DNS:

```

```

Now users access:

```
<https://api.myapp.com>
```

instead of remembering the IP address.

# Common DNS Errors

## NXDOMAIN

```
NXDOMAIN
```

Means:

> The domain doesn't exist.

---

## SERVFAIL

DNS server failed to answer.

Possible causes:

- Misconfiguration
- Upstream issues
- DNSSEC problems

---

## Timeout

Resolver couldn't reach the DNS server.

Possible causes:

- Firewall
- Network outage
- Incorrect DNS configuration

---

# Wrong DNS Record

Example:

```
api.example.com

↓

Wrong IP
```

Symptoms:

- Website unreachable
- SSL errors
- Requests reaching the wrong server

# Diagnose DNS

Step 1

```bash
doggo example.com
```

---

Step 2

Compare with:

```bash

```

---

Step 3

Compare with:

```bash

```

```
     │

```

Without DNS, HTTPS cannot even begin (unless you connect directly using an IP address).

# Best Practices

### Use Descriptive Subdomains

Examples:

```
api.example.com

app.example.com

admin.example.com
```

---

### Lower TTL Before Planned Migrations

Reduce TTL ahead of a server migration if you expect to change DNS records. This can help clients pick up the new IP more quickly after the change.

---

### Verify DNS After Changes

Always confirm your records with:

```bash
doggo
```

instead of assuming the change has propagated everywhere.

---

### Understand Caching

Different users may see different results temporarily because their DNS caches expire at different times.

---

# 💡 Senior Backend Engineer Insight

When a user types:

```
<https://api.example.com>
```

many developers think:

```
Browser
   │
   ▼
Server
```

A backend engineer thinks:

```
Browser
    │
Browser DNS Cache
    │
OS DNS Cache
    │
Recursive Resolver
    │
Root Name Server
    │
TLD Name Server (.com)
    │
Authoritative Name Server
    │
Receive IP Address
    │
TCP Three-Way Handshake
    │
TLS Handshake
    │
HTTP Request
```

This layered understanding is invaluable when diagnosing issues like **DNS propagation delays, misconfigured records, SSL certificate mismatches, or requests reaching the wrong server**.
