# What is HTTP?

HTTP stands for:

> **HyperText Transfer Protocol**

It is the protocol used by browsers and servers to exchange data.

Example:

```
Browser
    │
HTTP Request
    ▼
Server
    │
HTTP Response
    ▼
Browser
```

HTTP itself is **stateless**.

Every request is independent unless state is maintained through cookies, sessions, or tokens.

# Request Line

Contains:

```
HTTP Method
Request Path
HTTP Version
```

Example:

```
GET /products HTTP/1.1
```

---

# Request Headers

Headers provide metadata.

Example:

```
Host: api.example.com
User-Agent: Mozilla/5.0
Accept: application/json
Authorization: Bearer <token>
Content-Type: application/json
Cookie: session=abc123
```

Common headers:

|Header|Purpose|
|---|---|
|Host|Target server|
|Authorization|Authentication|
|Accept|Expected response format|
|Content-Type|Format of request body|
|Cookie|Session data|
|User-Agent|Client information|
|Origin|Used by CORS|
|Referer|Previous page|

---

# HTTP Methods

## GET

Retrieve data.

```
GET /users
```

Safe and idempotent.

---

## POST

Create data.

```
POST /users
```

Usually **not idempotent**.

---

## PUT

Replace an entire resource.

```
PUT /users/5
```

Idempotent.

---

## PATCH

Update part of a resource.

```
PATCH /users/5
```

---

## DELETE

Delete a resource.

```
DELETE /users/5
```

Idempotent.

---

## OPTIONS

Returns supported methods.

Often used during **CORS preflight**.

---

## HEAD

Returns only headers.

No response body.

Useful for checking:

- File size
- Existence
- Metadata

---

# Idempotency

A request is idempotent if making it multiple times has the same effect as making it once.

|Method|Idempotent|
|---|---|
|GET|✅|
|PUT|✅|
|DELETE|✅|
|HEAD|✅|
|OPTIONS|✅|
|POST|❌|
|PATCH|Usually ❌|

# Stateless Nature of HTTP

HTTP doesn't remember previous requests.

Request 1:

```
Login
```

Request 2:

```
Fetch Profile
```

The server doesn't automatically know they're from the same user.

State is maintained using:

- Cookies
- Sessions
- JWTs

---

# Cookies

Example response:

```
Set-Cookie: session=abc123
```

Browser stores it.

Future requests include:

```
Cookie: session=abc123
```

We'll explore this deeply in **Lesson 9**.

# Keep-Alive

Without Keep-Alive:

```
Request

↓

Close Connection

↓

New Request

↓

New Connection
```

Many TCP handshakes.

---

With Keep-Alive:

```
Connection

↓

Request

↓

Response

↓

Request

↓

Response
```

One connection reused for multiple requests.

Improves performance.

---

# HTTP/1.1

Features:

- Persistent connections
- Text-based protocol
- One request at a time per connection (without pipelining, which is rarely used)

Limitation:

Head-of-line blocking within a connection.

---

# HTTP/2

Major improvements:

- Binary protocol
- Multiplexing
- Header compression
- Server Push (supported by the protocol but rarely used in practice)

Diagram:

```
Single Connection

├── Request 1

├── Request 2

├── Request 3

├── Request 4
```

Multiple streams share one connection.

---

# HTTP/3

Uses:

```
QUIC

↓

UDP
```

Benefits:

- Faster connection establishment
- Better performance on unreliable networks
- Reduced impact of packet loss across independent streams

---

# HTTPS

HTTPS =

```
HTTP

+

TLS
```

Everything is encrypted.

---

# Without HTTPS

```
Browser

↓

HTTP

↓

Internet

↓

Anyone can inspect the traffic
```

Sensitive data could be exposed.

---

# With HTTPS

```
Browser

↓

Encrypted

↓

Internet

↓

Server
```

Intermediaries can see that communication is happening, but not the encrypted contents.

---

# TLS Handshake (Simplified)

```
Browser
     │
Hello
     ▼
Server
     │
Certificate
     ▼
Browser
     │
Verify Certificate
     │
Generate Shared Secret
     ▼
Encrypted Communication
```

After the handshake, application data is encrypted.

---

# Certificates

A certificate proves:

```
This server owns:

example.com
```

Browsers verify certificates before trusting the connection.

# Best Practices

### Use Correct HTTP Methods

- GET for reading
- POST for creating
- PUT for full replacement
- PATCH for partial updates
- DELETE for removal

---

### Return Meaningful Status Codes

A `201 Created` response communicates more than a generic `200 OK` after creating a resource.

---

### Prefer HTTPS

Encrypt all production traffic, not just login pages.

---

### Inspect Requests Before Debugging Code

Many issues are visible in the request or response before you need to open your application code.

---

# Common Mistakes

❌ Returning `200 OK` for every situation.

---

❌ Using `GET` for operations that modify data.

---

❌ Ignoring HTTP status codes in frontend applications.

---

❌ Disabling TLS certificate verification in production instead of fixing certificate issues.

# 💡 Senior Backend Engineer Insight

When you type:

```
<https://api.example.com/users>
```

a backend engineer mentally sees:

```
Browser
    │
DNS Resolution
    │
TCP Connection
    │
TLS Handshake
    │
HTTP Request
    │
Nginx Reverse Proxy
    │
Express Route
    │
Business Logic
    │
Database Query
    │
HTTP Response
    │
Browser Renders Data
```

Every production issue—whether it's a **404**, **401**, **502**, slow response, missing cookie, or TLS error—occurs at one of these layers. Learning to identify the failing layer quickly is one of the most valuable debugging skills you can develop as a backend engineer.
