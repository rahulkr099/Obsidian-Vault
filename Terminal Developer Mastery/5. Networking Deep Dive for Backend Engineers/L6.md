# The Problem with HTTP

HTTP follows a **request-response** model.

```
Browser
    │
Request
    ▼
Server
    │
Response
    ▼
Browser
```

After the response:

❌ Connection usually isn't used for arbitrary future server messages.

The server **cannot independently push application messages to the client** over ordinary HTTP.

---

# Example: Chat App Using HTTP

Suppose Alice sends a message.

```
Alice
   │
   ▼
Server
```

Bob receives it only after asking:

```
Bob

↓

GET /messages
```

If Bob never asks again...

❌ No new messages appear.

---

# Solution 1 — Polling

Client repeatedly asks:

```
Every 5 Seconds

↓

GET /messages
```

Timeline:

```
Client ── GET ─► Server
Client ◄─ Data ─ Server

(wait)

Client ── GET ─► Server
Client ◄─ Data ─ Server
```

---

# Problems with Polling

Suppose nobody sends messages.

Client still sends:

```
GET /messages
```

every few seconds.

Result:

- Extra network traffic
- Extra CPU usage
- Extra database queries
- Higher latency

---

# Solution 2 — Long Polling

Instead of responding immediately:

```
Client
    │
GET /messages
    │
Server waits...
    │
New Message
    │
Response
```

Better than polling, but still requires opening new HTTP requests over time.

---

# Solution 3 — Server-Sent Events (SSE)

Server continuously pushes updates to the client **over a single HTTP response stream**.

```
Server
   │
   ▼
Browser
```

Characteristics:

- One-way (server → client)
- Great for notifications
- Simple to implement
- Browser support is good

Not suitable when the client also needs continuous low-latency communication.

---

# Solution 4 — WebSockets

WebSocket creates one persistent connection.

```
Browser
        ⇅
 WebSocket
        ⇅
Server
```

Both sides can send data at any time.

---

# HTTP vs WebSocket

|HTTP|WebSocket|
|---|---|
|Request → Response|Full duplex|
|Stateless|Persistent connection|
|Repeated requests|One connection|
|Higher overhead for frequent updates|Low overhead after connection|
|Best for REST APIs|Best for real-time apps|

---

# What is Full Duplex?

Both sides communicate independently.

```
Client  ◄────►  Server
```

Client can send.

Server can send.

No need to wait for a request before every message.

---

# WebSocket Handshake

WebSockets begin as an HTTP request.

```
Browser

↓

HTTP Upgrade Request

↓

Server

↓

101 Switching Protocols

↓

WebSocket Connection
```

After the upgrade:

HTTP ends.

WebSocket begins.

---

# Handshake Example

Client:

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: abc123
Sec-WebSocket-Version: 13
```

Server:

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

After this:

```
Persistent Connection Established
```

---

# WebSocket URL

Instead of:

```
http://
```

Use:

```

```

Secure version:

```

```

Equivalent to HTTPS for WebSockets.

# Message Flow

```
Client
   │
Hello
   ▼
Server
   │

```

# WebSocket Frames

Unlike HTTP requests, WebSockets exchange **frames**.

```
Frame

↓

Message

↓

Frame

↓

Message
```

Frames can carry:

- Text
- Binary data
- Ping
- Pong
- Close

---

# Ping & Pong

WebSockets periodically verify that the connection is alive.

```
Server

↓

PING

↓

Client

↓

PONG
```

This is different from HTTP keep-alive.

---

# Closing a Connection

Either side can initiate closure.

```
Client

↓

Close Frame

↓

Server

↓

Close Frame
```

Graceful shutdown.

# Node.js WebSocket Example

Install:

```bash
npm install ws
```

Simple server:

```jsx
import { WebSocketServer } from "ws";

const wss = new WebSocketServer({ port: 8080 });

wss.on("connection", (socket) => {
    console.log("Client connected");

    socket.send("Welcome!");

    socket.on("message", (message) => {
        console.log(message.toString());
    });
});
```

---

# Browser Client

```jsx
const socket = new WebSocket("ws://localhost:8080");

socket.onopen = () => {
    console.log("Connected");
};

socket.onmessage = (event) => {
    console.log(event.data);
};

socket.send("Hello Server");
```

# [Socket.IO](http://Socket.IO)

[Socket.IO](http://Socket.IO) is **not the WebSocket protocol itself**.

It is a library that:

- Prefers WebSocket when available
- Can fall back to other transports if necessary
- Adds useful features

---

# [Socket.IO](http://Socket.IO) Features

- Automatic reconnection
- Rooms
- Namespaces
- Broadcasting
- Event-based API
- Acknowledgements

Example:

```jsx
io.on("connection", (socket) => {

    socket.emit("welcome");

    socket.on("chat-message", (msg) => {
        console.log(msg);
    });

});
```

# When NOT to Use WebSockets

Don't use WebSockets for:

- Login
- Registration
- Simple CRUD APIs
- Static pages
- File downloads

HTTP/REST is simpler and usually the better choice.

---

# Scalability Challenge

One WebSocket connection per client means the server maintains many long-lived connections.

```
10,000 Clients

↓

10,000 Connections
```

Large deployments often add:

- Multiple application servers
- Load balancers with sticky sessions or shared state
- Shared messaging systems (for example, Redis Pub/Sub) so events reach clients connected to different servers

# Best Practices

### Use REST for CRUD

Keep login, registration, and most data management endpoints as REST APIs.

---

### Use WebSockets Only for Real-Time Features

Choose WebSockets when low-latency, bidirectional communication provides clear value.

---

### Handle Reconnection

Clients should detect disconnects and reconnect gracefully when appropriate.

---

### Validate Messages

Treat incoming WebSocket messages like any other user input.

Authenticate users and validate payloads before acting on them.

---

# Common Mistakes

❌ Using WebSockets for every endpoint.

---

❌ Forgetting authentication after the WebSocket connection is established.

---

❌ Not handling disconnects and reconnects.

---

❌ Using `ws://` from an HTTPS website instead of `wss://`.

# 💡 Senior Backend Engineer Insight

A production backend rarely chooses **REST or WebSockets**—it usually uses **both**.

A typical architecture looks like this:

```
                React Frontend
                │           │
      REST API  │           │ WebSocket
                ▼           ▼
           Express + Socket.IO
                    │
          Business Logic Layer
                    │
             MongoDB / Redis
```

Use **REST** for predictable request-response operations such as authentication, CRUD, and file uploads.

Use **WebSockets** for features where the server needs to notify clients immediately, such as chat, live dashboards, collaborative editing, notifications, or multiplayer games.

Choosing the right communication model for each feature leads to systems that are easier to maintain, scale, and debug.
