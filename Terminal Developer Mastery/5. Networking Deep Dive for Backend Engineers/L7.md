Most beginners imagine:

```

    │
    ▼
Node.js Server
```

Production looks like:

```
Internet
    │
    ▼
Nginx (Reverse Proxy)

    ▼
Node.js (Express)
    │
    ▼

```

Users never communicate directly with your Express application.

---

# What is a Reverse Proxy?

A **reverse proxy** sits **between clients and backend servers**.

```
Client
   │
   ▼
Reverse Proxy
   │
   ▼
Backend Server
```

The client thinks it is communicating with one server.

The reverse proxy decides where the request actually goes.

---

# Why Use a Reverse Proxy?

Without Nginx:

```
Internet
    │
    ▼
Express App
```

Problems:

- Node.js exposed directly
- SSL handled by Node
- Static files served inefficiently
- Harder to scale

---

With Nginx:

```
Internet
    │
    ▼
Nginx
 ├── Static Files
 ├── HTTPS
 ├── Compression
 ├── Security Headers
 └── Proxy Requests
        │
        ▼
Express
```

Much cleaner and more scalable.

---

# Reverse Proxy vs Forward Proxy

## Reverse Proxy

Protects **servers**.

```
Users
   │
   ▼
Reverse Proxy
   │
   ▼
Backend Servers
```

Examples:

- Nginx
- HAProxy
- Apache HTTP Server (reverse proxy mode)

---

## Forward Proxy

Protects **clients**.

```
User
   │
   ▼
Forward Proxy
   │
   ▼
Internet
```

Common uses:

- Corporate networks
- Content filtering
- Privacy
- Caching

---

# Nginx Reverse Proxy

Suppose Express runs on:

```
localhost:5000
```

Users visit:

```
<https://example.com>
```

Nginx forwards traffic.

---

Example configuration:

```
server {
    listen 80;

    server_name example.com;

    location / {
        proxy_pass <http://127.0.0.1:5000>;
    }
}
```

Flow:

```
Browser
     │
     ▼
Nginx
     │
proxy_pass
     ▼
Express
```

---

# Useful Proxy Headers

A production configuration usually forwards client information.

```
location / {

    proxy_pass <http://127.0.0.1:5000>;

    proxy_set_header Host $host;

    proxy_set_header X-Real-IP $remote_addr;

    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    proxy_set_header X-Forwarded-Proto $scheme;

}
```

These headers allow Express to know:

- Original host
- Client IP
- HTTP vs HTTPS

---

# Express Behind Nginx

Express should trust the reverse proxy.

```jsx
app.set("trust proxy", true);
```

Now:

```jsx
req.ip
```

returns the original client IP instead of the proxy's IP.

# Serving Static Files

Instead of Express:

```
Browser
    │
Express
    │

```

Use Nginx:

```
Browser
    │
Nginx
    │

```

Nginx is optimized for static content.

Example:

```

    root /var/www/html;
}
```

# SSL Termination

HTTPS usually ends at Nginx.

```
Browser

HTTPS

↓

Nginx

HTTP

↓

Express
```

Advantages:

- Simpler Node.js application
- Easier certificate renewal
- Better TLS performance

# Load Balancing

Suppose one Node.js server becomes overloaded.

Instead of:

```
Users
    │
    ▼
Node.js
```

Use multiple servers:

```
           Nginx
        /     |     \
       ▼      ▼      ▼
    Node1   Node2   Node3
```

Nginx distributes requests.

---

# Upstream Block

```
upstream backend {

    server 127.0.0.1:5000;

    server 127.0.0.1:5001;

    server 127.0.0.1:5002;

}

server {

    location / {

        proxy_pass <http://backend>;

    }

}
```

---

# Round Robin

Default algorithm.

```
Request 1 → Server A

Request 2 → Server B

Request 3 → Server C

Request 4 → Server A
```

Balanced distribution.

---

# Least Connections

New requests go to the server with the fewest active connections.

```
Server A : 15

Server B : 4

↓

Next request

↓

Server B
```

Useful when request durations vary significantly.

---

# IP Hash

Clients with the same IP are sent to the same backend whenever possible.

```
Client A

↓

Server 1

Client A

↓

Server 1
```

Helpful for applications that rely on local in-memory session state, though shared session storage is generally preferred for scalability.

---

# Sticky Sessions

Some applications store sessions in server memory.

Without stickiness:

```
Login

↓

Server 1

Next Request

↓

Server 2

↓

Session Missing
```

Solutions:

- Sticky sessions
- Shared session store (Redis is a common choice)

---

# Health Checks

Production load balancers avoid unhealthy servers.

Healthy:

```
Node 1 ✓

Node 2 ✓

Node 3 ✗
```

Requests are sent only to healthy instances.

---

# Compression

Nginx can compress responses.

```
gzip on;
gzip_types text/plain application/json;
```

Smaller responses.

Faster downloads.

---

# Caching

Frequently requested files:

```
logo.png

style.css

app.js
```

can be cached.

Example:

```
location /assets/ {

    expires 30d;

}
```

---

# Security Headers

Nginx can add headers.

```
add_header X-Frame-Options SAMEORIGIN;
add_header X-Content-Type-Options nosniff;
```

These provide additional browser protections.

---

# Rate Limiting

Protect against abuse.

```
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
```

Example:

```
1000 Requests

↓

Allowed

↓

10 Requests / Second
```

# Common Errors

## 502 Bad Gateway

Meaning:

```
Nginx

↓

Cannot reach backend
```

Check:

```bash
systemctl status backend
```

---

## 504 Gateway Timeout

Meaning:

Backend didn't respond in time.

Possible causes:

- Slow database query
- Infinite loop
- Server overload

---

## 403 Forbidden

Often caused by:

- Incorrect file permissions
- Nginx configuration
- SELinux/AppArmor policies (where applicable)

---

## 404 Not Found

Could be:

- Wrong Nginx route
- Wrong Express route
- Incorrect `root` or `alias` configuration

# Best Practices

### Keep Node.js Private

Expose only Nginx to the Internet.

---

### Let Nginx Handle HTTPS

Terminate TLS at the reverse proxy unless you have a specific reason not to.

---

### Serve Static Assets from Nginx

Reserve Node.js resources for application logic.

---

### Use Shared Session Storage

Avoid relying on sticky sessions when a centralized session store is practical.

---

### Validate Nginx Configurations

Always run:

```bash
sudo nginx -t
```

before reloading.

---

# Common Mistakes

❌ Exposing Express directly to the Internet.

---

❌ Forgetting:

```jsx
app.set("trust proxy", true);
```

when running behind Nginx.

---

❌ Restarting Nginx without testing the configuration.

---

❌ Ignoring Nginx error logs while debugging.

# 💡 Senior Backend Engineer Insight

When you deploy a production backend, think of **Nginx as the gatekeeper**.

```
                Internet
                    │
                    ▼
              Nginx (Gatekeeper)
      ┌──────────┼──────────┐
      │          │          │
 HTTPS/TLS   Static Files   Rate Limiting
      │          │          │
      └──────────┼──────────┘
                 ▼
        Load Balancer (Upstream)
          │        │        │
          ▼        ▼        ▼
      Node 1    Node 2    Node 3
                 │
                 ▼
             MongoDB
```

Your Express application focuses on **business logic**, while Nginx handles networking concerns such as TLS termination, request routing, compression, static assets, and (optionally) load balancing. This separation of responsibilities is a hallmark of production-ready backend architecture.
