# Why Do We Need HTTPS?

Imagine logging into your bank using plain HTTP.

```
Browser
     │
HTTP
     │
Internet
     │
Attacker
     │
Server
```

Everything is readable:

- Username
- Password
- Cookies
- Credit card numbers

Anyone intercepting the traffic could read it.

---

# HTTPS Solves Three Problems

## 1. Confidentiality 🔒

Only the browser and server can read the data.

---

## 2. Integrity ✅

Data cannot be modified without detection.

---

## 3. Authentication 🪪

The browser can verify that it is communicating with the legitimate server.

---

# SSL vs TLS

Originally:

```
SSL
```

Modern Internet:

```
TLS
```

SSL is obsolete.

Today:

- TLS 1.2
- TLS 1.3

People still say "SSL certificate", but they usually mean a certificate used with TLS.

---

# Encryption Basics

Two major types:

```
Encryption

├── Symmetric

└── Asymmetric
```

---

# Symmetric Encryption

Same key:

```
Secret Key

↓

Encrypt

↓

Decrypt
```

Example:

```
Key = "abc123"
```

Both sender and receiver must know it.

---

## Advantages

- Very fast
- Efficient
- Used for bulk data

---

## Problem

How do you securely share the secret key?

That is exactly what TLS solves.

---

# Asymmetric Encryption

Uses two keys.

```
Public Key

Private Key
```

Different keys.

---

# Public Key

Can be shared with everyone.

---

# Private Key

Must never leave the server.

---

# How It Works

```
Browser

↓

Encrypt with Public Key

↓

Server

↓

Decrypt with Private Key
```

Only the server can decrypt the message.

---

# Real Analogy

Imagine a special mailbox.

Public key:

```
Open Slot
```

Anyone can drop letters in.

Private key:

```
Mailbox Key
```

Only the owner can open it.

---

# Why Not Use Asymmetric Encryption for Everything?

Because it's much slower than symmetric encryption.

TLS combines both approaches.

---

# Hybrid Encryption

TLS works like this:

```
Browser

↓

Public Key

↓

Securely Exchange Secret

↓

Symmetric Encryption

↓

Fast Communication
```

Best of both worlds.

---

# Digital Certificates

How does your browser know the public key actually belongs to the website?

Example:

```
github.com
```

vs

```
fake-github.com
```

This is where certificates come in.

---

# Certificate

Contains:

- Domain name
- Public key
- Expiration date
- Issuer
- Digital signature

---

# Certificate Authority (CA)

Trusted organizations issue certificates.

Examples:

- Let's Encrypt
- DigiCert
- GlobalSign
- Sectigo

Browsers trust these authorities.

---

# Trust Chain

```
Browser

↓

Root CA

↓

Intermediate CA

↓

Website Certificate
```

If every signature validates, the browser trusts the website.

---

# Certificate Verification

Browser checks:

- Domain matches
- Certificate not expired
- Signature valid
- Trusted CA
- Certificate not revoked (where applicable)

If everything succeeds:

```
🔒 Secure
```

---

# TLS Handshake (Simplified)

### Step 1 — Client Hello

Browser:

```
Hello

Supported TLS Versions

Supported Cipher Suites

Random Number
```

---

### Step 2 — Server Hello

Server responds:

```
Chosen TLS Version

Chosen Cipher Suite

Random Number

Certificate
```

---

### Step 3 — Verify Certificate

Browser validates:

- Domain
- CA
- Signature
- Expiration

---

### Step 4 — Key Exchange

Both sides securely derive a shared secret.

Modern TLS (especially TLS 1.3) commonly uses ephemeral key exchange (such as ECDHE), so the shared secret is derived rather than sent directly.

---

### Step 5 — Secure Communication

All future application data uses fast symmetric encryption.

---

# TLS Handshake Diagram

```
Browser                    Server

ClientHello  ─────────────►

             ◄──────────── ServerHello
                           Certificate
                           Key Exchange Data

Verify Certificate

Key Exchange

Encrypted Channel Established

HTTP Requests
```

---

# TLS 1.2 vs TLS 1.3

|Feature|TLS 1.2|TLS 1.3|
|---|---|---|
|Speed|Good|Faster|
|Security|Strong|Stronger|
|Cipher Suites|More options|Simpler, modern set|
|Round Trips|More|Fewer|

TLS 1.3 is generally preferred when supported.

```

```

Notice:

HTTP happens **after** TLS.

- Verification result

# Nginx HTTPS Configuration

Example:

```
server {

    listen 443 ssl;

    server_name example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;

    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {

        proxy_pass <http://127.0.0.1:5000>;

    }

}
```

---

# Redirect HTTP → HTTPS

```
server {

    listen 80;

    server_name example.com;

    return 301 https://$host$request_uri;

}
```

Always redirect users to HTTPS.

# Self-Signed Certificates

Generated by yourself.

Useful for:

- Local development
- Internal testing

Browsers show warnings because they aren't signed by a trusted CA.

Not recommended for public production websites.

---

# Common TLS Errors

## Certificate Expired

```
NET::ERR_CERT_DATE_INVALID
```

Renew the certificate.

---

## Domain Mismatch

Certificate:

```
example.com
```

Website:

```
api.example.com
```

Names don't match.

---

## Self-Signed Warning

Browser doesn't trust the issuer.

---

## Mixed Content

Website:

```
HTTPS
```

Loads:

```
<http://image.jpg>
```

Browsers often block these insecure resources.

---

# HSTS (HTTP Strict Transport Security)

Header:

```
Strict-Transport-Security:
max-age=31536000
```

Instructs browsers to use HTTPS for future visits.

Enable HSTS only after you're confident HTTPS is correctly configured for your domain.

---

# Perfect Forward Secrecy

Modern TLS commonly uses ephemeral key exchange.

Result:

Even if a server's long-term private key is compromised later, previously captured encrypted sessions remain protected.

# Best Practices

### Use HTTPS Everywhere

Protect all production traffic.

---

### Prefer TLS 1.3

Enable TLS 1.3 where supported, while keeping TLS 1.2 available if you need compatibility with older clients.

---

### Protect Private Keys

Never commit them to Git.

Restrict file permissions.

---

### Automate Certificate Renewal

Monitor renewals before certificates expire.

---

### Redirect HTTP to HTTPS

Avoid serving sensitive content over HTTP.

---

# Common Mistakes

❌ Using expired certificates.

---

❌ Storing private keys in repositories.

---

❌ Serving mixed HTTP and HTTPS content.

---

❌ Ignoring certificate validation errors instead of fixing them.

# 💡 Senior Backend Engineer Insight

A senior backend engineer doesn't just think:

```
HTTPS = Encryption
```

They think:

```
Browser
    │
DNS Resolution
    │
TCP Three-Way Handshake
    │
TLS Handshake
    ├── Verify Certificate
    ├── Negotiate Cipher Suite
    ├── Derive Shared Secret
    ▼
Encrypted HTTP
    │
Nginx (TLS Termination)
    │
Express
    │
Database
```

When users report certificate warnings, failed HTTPS connections, or TLS handshake errors, this mental model helps you determine whether the issue lies with DNS, certificates, Nginx configuration, protocol negotiation, or the application itself.
