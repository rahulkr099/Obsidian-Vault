# The Same-Origin Policy (SOP)

Browsers restrict JavaScript from freely accessing resources on different origins.

An **origin** is defined by:

```
Protocol + Host + Port
```

Example:

```
<https://example.com:443>
```

---

# Same Origin Examples

|URL|Same Origin?|
|---|---|
|[](https://example.com/)[https://example.com](https://example.com)|✅|
|[https://example.com/users](https://example.com/users)|✅|
|[https://example.com/profile](https://example.com/profile)|✅|

Only the path changes.

---

# Different Origin Examples

|URL|Same Origin?|Reason|
|---|---|---|
|[](http://example.com/)[http://example.com](http://example.com)|❌|Protocol|
|[](https://api.example.com/)[https://api.example.com](https://api.example.com)|❌|Host|
|[](https://example.com:5000/)[https://example.com:5000](https://example.com:5000)|❌|Port|

Changing **protocol, host, or port** creates a new origin.

---

# Why SOP Exists

Without SOP:

```
Bank Website

↓

Cookie

↓

Malicious Website

↓

Steal Data
```

The Same-Origin Policy prevents many cross-site attacks by restricting what scripts can read from other origins.

---

# What is CORS?

CORS stands for:

> **Cross-Origin Resource Sharing**

CORS is a browser security mechanism that allows servers to explicitly permit certain cross-origin requests.

Think of it as the server saying:

```
"I trust requests from this origin."
```

---

# MERN Example

Frontend:

```
<https://app.example.com>
```

Backend:

```
<https://api.example.com>
```

Different origins.

Browser checks:

```
Can app.example.com access api.example.com?
```

If the server allows it:

✅ Request succeeds.

Otherwise:

❌ Browser blocks JavaScript from accessing the response.

---

# Request Flow

```
Browser
     │
Request
     │
Server
     │
Access-Control-Allow-Origin?
     │
YES → Response Available
NO  → Browser Blocks Access
```

---

# Simple CORS Request

Browser:

```
GET /users

Origin: <https://app.example.com>
```

Server:

```
Access-Control-Allow-Origin:
<https://app.example.com>
```

Success.

---

# CORS Response Headers

Important headers:

```
Access-Control-Allow-Origin:
<https://app.example.com>

Access-Control-Allow-Credentials: true

Access-Control-Allow-Methods:
GET, POST, PATCH, DELETE

Access-Control-Allow-Headers:
Authorization, Content-Type
```

---

# What is a Preflight Request?

Some requests require the browser to ask permission **before** sending the real request.

Browser sends:

```
OPTIONS /users
```

This is called a **preflight request**.

---

# When Does Preflight Happen?

Common triggers:

- `PUT`
- `PATCH`
- `DELETE`
- Custom headers
- `Authorization`
- JSON requests with non-simple characteristics

The browser first verifies what the server allows.

---

# Preflight Flow

```
Browser

↓

OPTIONS /users

↓

Server

↓

Allowed?

↓

YES

↓

Real Request
```

# Express CORS

Install:

```bash
npm install cors
```

---

Basic configuration:

```jsx
import cors from "cors";

app.use(cors());
```

This is acceptable for local development, but **not recommended for production**.

---

# Production Configuration

```jsx
app.use(cors({
    origin: "<https://app.example.com>",
    credentials: true,
    methods: ["GET","POST","PUT","PATCH","DELETE"],
    allowedHeaders: [
        "Content-Type",
        "Authorization"
    ]
}));
```

Never use:

```jsx
origin: "*"
```

together with:

```jsx
credentials: true
```

Browsers reject that combination.

---

# Credentials

If cookies are involved:

Frontend:

```jsx
fetch(url, {
    credentials: "include"
});
```

Backend:

```jsx
credentials: true
```

Both sides must be configured correctly.

# Cookies

A cookie is a small piece of data stored by the browser.

Server:

```
Set-Cookie:
session=abc123
```

Browser stores it.

Future requests:

```
Cookie:
session=abc123
```

---

# Cookie Lifecycle

```
Login

↓

Server

↓

Set-Cookie

↓

Browser Stores Cookie

↓

Future Requests

↓

Cookie Automatically Sent
```

---

# Common Cookie Attributes

## HttpOnly

```
HttpOnly
```

JavaScript cannot access the cookie.

Helps reduce the impact of XSS attacks.

---

## Secure

```
Secure
```

Cookie is sent only over HTTPS.

Use in production.

---

## SameSite

Options:

```
Strict

Lax

None
```

---

### Strict

Most restrictive.

Cross-site requests generally won't include the cookie.

---

### Lax

Good default for many applications.

Allows cookies in some top-level navigations while providing CSRF protection.

---

### None

Allows cross-site cookies.

Requires:

```
Secure
```

---

# Cookie Example

```jsx
res.cookie("refreshToken", token, {
    httpOnly: true,
    secure: true,
    sameSite: "none",
    maxAge: 7 * 24 * 60 * 60 * 1000
});
```

---

# Sessions

Instead of storing user information in the cookie:

Cookie:

```
session=abc123
```

Server:

```
abc123

↓

User Data
```

The cookie stores only a session identifier.

---

# Session Flow

```
Browser

↓

Session Cookie

↓

Server

↓

Session Store

↓

User
```

---

# Session Store

Avoid storing sessions only in application memory.

Better choices:

- Redis
- Database-backed session stores

This is especially important when running multiple application instances.

---

# JWT Authentication

Instead of storing a session ID:

Browser:

```
JWT
```

Token contains signed claims.

Server verifies the signature rather than looking up a session for every request.

---

# JWT Flow

```
Login

↓

JWT

↓

Browser

↓

Authorization Header

↓

Server Verification
```

---

# Sessions vs JWT

|Sessions|JWT|
|---|---|
|Server stores session|Client stores token|
|Easy revocation|Usually stateless|
|Needs shared store for scaling|Easier horizontal scaling|
|Cookie-based|Header or cookie based|

Neither is universally better. The right choice depends on your application's requirements.

# Common CORS Errors

## No Access-Control-Allow-Origin

Browser blocks access.

Cause:

Server didn't allow the requesting origin.

---

## Credentials Error

Example:

```
Credentials included

↓

Origin = *
```

Invalid.

Specify the exact origin instead of `"*"`.

---

## Preflight Failed

Usually:

- OPTIONS not handled
- Missing allowed headers
- Missing allowed methods

---

## Cookie Not Sent

Common causes:

- Missing `credentials: "include"`
- Missing `Access-Control-Allow-Credentials: true`
- `SameSite` or `Secure` configured incorrectly
- Using HTTP when the cookie requires HTTPS

# Best Practices

### Allow Only Trusted Origins

Never expose your production API to every origin unless you intentionally provide a public API.

---

### Use HttpOnly Cookies for Sensitive Tokens

This reduces exposure to client-side JavaScript.

---

### Use `Secure` in Production

Sensitive cookies should travel only over HTTPS.

---

### Validate Every Request

Whether using sessions or JWTs, always verify authentication and authorization.

---

### Use Shared Session Storage

If using sessions with multiple backend instances, store them in Redis or another shared backend.

---

# Common Mistakes

❌ Using:

```jsx
origin: "*"
```

with credentials.

---

❌ Storing highly sensitive tokens in locations without considering the security trade-offs.

---

❌ Forgetting `credentials: "include"` on the frontend.

---

❌ Ignoring the browser's Network tab while debugging CORS.

# 💡 Senior Backend Engineer Insight

A production MERN authentication flow typically looks like this:

```
React (<https://app.example.com>)
            │
            │ fetch(..., { credentials: "include" })
            ▼
        Browser
            │
            │ Cookie (HttpOnly, Secure)
            ▼
Nginx (HTTPS + TLS Termination)
            │
            ▼
Express API
            │
     Authentication Middleware
            │
     Session Store / JWT Verification
            ▼
MongoDB
```

When login "doesn't work," experienced backend engineers debug layer by layer:

1. Is the browser sending the request?
2. Is there a CORS error?
3. Did the preflight (`OPTIONS`) succeed?
4. Was the cookie set by the server?
5. Is the browser sending the cookie back?
6. Is Express reading and validating it?
7. Is the session or JWT valid?

Following this sequence usually identifies the problem much faster than changing CORS settings at random.
