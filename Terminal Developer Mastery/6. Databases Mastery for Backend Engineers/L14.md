# PostgreSQL Monitoring

Useful built-in views:

```sql
pg_stat_activity
```

```sql
pg_stat_database
```

```sql
pg_stat_user_tables
```

```sql
pg_stat_user_indexes
```

These provide insight into active sessions, database activity, table usage, and index usage.

---

# Active Queries

Show running queries:

```sql
SELECT *

FROM pg_stat_activity;
```

Useful fields include:

- PID
- State
- Query
- Query start time

---

# Long Running Queries

Example:

```sql
SELECT
pid,
now() - query_start AS duration,
query

FROM pg_stat_activity

WHERE state='active';
```

Long-running queries often indicate:

- Missing indexes
- Poor query design
- Blocking transactions

---

# Slow Query Logging

Enable slow query logging.

Example configuration:

```
log_min_duration_statement = 500
```

Meaning:

Log queries taking longer than:

```
500 milliseconds
```

---

# Index Usage

Find unused indexes.

```sql
SELECT *

FROM pg_stat_user_indexes;
```

Unused indexes consume storage and slow writes.

---

# Table Statistics

Monitor:

```sql
pg_stat_user_tables
```

Includes:

- Sequential scans
- Index scans
- Inserts
- Updates
- Deletes

# PostgreSQL Locks

Monitor locks:

```sql

```

# EXPLAIN ANALYZE

Never guess why a query is slow.

Instead:

```sql
EXPLAIN ANALYZE

SELECT *

FROM users

WHERE email='rahul@example.com';
```

Observe:

- Execution time
- Scan type
- Rows examined

# Cache Hit Ratio

Important metric.

```
Requests

↓

Redis

↓

Hit?

↓

YES

↓

Fast

↓

NO

↓

Database
```

Higher cache hit ratios generally mean fewer database queries.

---

# Redis Memory

Watch:

```
used_memory
```

If memory approaches the configured limit, Redis may begin evicting keys depending on the eviction policy.

---

# Redis Evictions

Monitor:

```
evicted_keys
```

Unexpected increases may indicate insufficient memory or missing TTL strategies.

---

# Replication Lag

# Best Practices

### Monitor Continuously

Don't wait for production failures.

---

### Create Meaningful Alerts

Avoid alert fatigue.

Alerts should require action.

---

### Review Slow Queries Regularly

Many performance improvements come from query optimization.

---

### Monitor Trends

One snapshot isn't enough.

Watch metrics over time.

---

### Correlate Metrics

A slow query may coincide with:

- High CPU
- Low cache hit ratio
- Increased connections

Looking at multiple metrics together often reveals the root cause.

# 💡 Senior Backend Engineer Insight

Monitoring is only one part of **observability**.

A production-ready backend combines three pillars:

```
                    Observability
                         │
     ┌───────────────────┼───────────────────┐
     ▼                   ▼                   ▼
   Metrics             Logs              Traces
(CPU, Memory,      (Errors, SQL,      (Request Flow,
Latency, Cache)     Events)            Service Timing)
```

Together, they answer different questions:

- **Metrics** tell you **that** something is wrong.
- **Logs** tell you **what** happened.
- **Traces** tell you **where** the request slowed down across multiple services.

For modern backend systems, common tooling includes:

- **Metrics:** Prometheus + Grafana
- **Logs:** Loki, Elasticsearch/OpenSearch
- **Tracing:** OpenTelemetry + Jaeger or Tempo

Learning to interpret these signals is a key step toward becoming a senior backend engineer.
