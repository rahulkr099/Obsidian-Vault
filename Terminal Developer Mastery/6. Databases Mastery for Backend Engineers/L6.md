# Why Queries Become Slow

Imagine a table:

```
Users

1 million rows
```

You run:

```sql
SELECT *
FROM users
WHERE email='rahul@example.com';
```

How does PostgreSQL find Rahul?

---

## Option 1 — Full Table Scan

Without an index:

```
Row 1

↓

Row 2

↓

Row 3

↓

...

↓

Row 1,000,000
```

This is called a **Sequential Scan**.

Time grows as the table grows.

---

## Option 2 — Using an Index

With an index:

```
Index

↓

rahul@example.com

↓

Jump directly

↓

Matching row
```

Much faster.

---

# What is an Index?

An index is a **special data structure** that helps PostgreSQL locate rows quickly.

Think of a textbook.

Without an index:

```
Read every page.
```

With an index:

```
Go to:

Networking → Page 210
```

---

# Database Without Index

```
Users

1

2

3

4

5

6

...

1,000,000
```

Search:

```
Find ID = 700000
```

Must inspect many rows.

---

# Database With Index

```
Index

↓

700000

↓

Pointer

↓

Actual Row
```

Fast lookup.

---

# B-Tree Index

Default PostgreSQL index.

Create:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Structure:

```
                Root
              /      \
          Node      Node
         /   \      /   \
      Leaf Leaf  Leaf Leaf
```

Efficient for:

- Equality (`=`)
- Range (`>`, `<`, `BETWEEN`)
- Sorting (`ORDER BY`)

---

# Why B-Tree?

Suppose:

```
1

2

3

...

1,000,000
```

Instead of checking one by one:

```
Middle

↓

Quarter

↓

Smaller Section

↓

Target
```

Very few comparisons.

---

# Hash Index

Optimized for equality.

```sql
CREATE INDEX idx_email_hash
ON users
USING HASH(email);
```

Good for:

```sql
WHERE email='rahul@example.com'
```

Not suitable for:

```sql
ORDER BY

BETWEEN

>

<
```

In practice, B-tree is usually the default choice.

---

# Composite Index

Index on multiple columns.

```sql
CREATE INDEX idx_orders_user_date
ON orders(user_id, created_at);
```

Useful:

```sql
WHERE user_id = 1

ORDER BY created_at;
```

---

# Column Order Matters

Index:

```sql
(user_id, created_at)
```

Good:

```sql
WHERE user_id = 5
```

Good:

```sql
WHERE user_id = 5
ORDER BY created_at;
```

Not as useful:

```sql
WHERE created_at > NOW() - INTERVAL '7 days';
```

because the leading indexed column (`user_id`) isn't used.

# Covering Index

Suppose:

```sql
SELECT name,email
FROM users
WHERE email='rahul@example.com';
```

Index:

```sql
CREATE INDEX idx_users_email_name
ON users(email,name);
```

In PostgreSQL, you can also use included columns:

```sql
CREATE INDEX idx_users_email
ON users(email)
INCLUDE (name);
```

The database may satisfy the query using the index alone, reducing table access.

---

# Partial Index

Index only some rows.

Example:

```sql
CREATE INDEX idx_active_users

ON users(email)

WHERE is_active = TRUE;
```

Smaller index.

Faster lookups.

Great when most queries target a subset of rows.

---

# Unique Index

Automatically created:

```sql
email UNIQUE
```

Equivalent to:

```
Unique Index
```

Guarantees:

```
No duplicate email.
```

---

# Index on Primary Key

```sql
PRIMARY KEY
```

Automatically creates an index.

No need to create another.

---

# When NOT to Create an Index

Don't index everything.

Bad:

```
Every Column

↓

Huge Storage

↓

Slow Inserts

↓

Slow Updates
```

Indexes speed reads but add overhead to writes.

---

# Insert Performance

Without index:

```
Insert

↓

Done
```

With many indexes:

```
Insert

↓

Update Index 1

↓

Update Index 2

↓

Update Index 3

↓

Done
```

More indexes = slower writes.

---

# Sequential Scan

Example:

```sql
SELECT *

FROM users;
```

Planner:

```
Sequential Scan
```

Perfectly acceptable because every row is needed.

---

# Index Scan

Example:

```sql
SELECT *

FROM users

WHERE email='rahul@example.com';
```

Planner:

```
Index Scan
```

Fast.

---

# Bitmap Index Scan

Useful when many rows match.

Planner combines index lookups before accessing the table.

Efficient for medium-sized result sets.

---

# EXPLAIN

Shows PostgreSQL's plan.

```sql
EXPLAIN

SELECT *

FROM users

WHERE email='rahul@example.com';
```

Output:

```
Index Scan

Cost

Rows
```

No query execution.

---

# EXPLAIN ANALYZE

Actually runs the query.

```sql
EXPLAIN ANALYZE

SELECT *

FROM users

WHERE email='rahul@example.com';
```

Shows:

- Actual time
- Actual rows
- Buffers (if enabled)
- Planning time
- Execution time

---

# Reading EXPLAIN

Example:

```
Index Scan

Cost: 0.29..8.30

Rows:1

Actual Time:0.02ms
```

Interpretation:

- Uses index
- Expected one row
- Completed in 0.02 ms

---

# Cost

Not milliseconds.

It's PostgreSQL's internal estimate used to compare plans.

Lower estimated cost generally indicates a more efficient plan.

---

# Rows

Estimated:

```
Rows = 1
```

Actual:

```
Rows = 500
```

Large differences may indicate outdated statistics.

---

# ANALYZE

Refresh planner statistics.

```sql
ANALYZE users;
```

Or:

```sql
VACUUM ANALYZE users;
```

Useful after major data changes.

---

# VACUUM

When rows are deleted, PostgreSQL doesn't immediately reclaim disk space.

```
Delete

↓

Dead Tuples

↓

VACUUM
```

Benefits:

- Cleans dead tuples
- Improves storage reuse
- Helps performance

---

# Query Planner

Planner chooses:

```
Sequential Scan

or

Index Scan
```

Based on estimated cost.

Sometimes a sequential scan is actually faster.

---

# Example

Tiny table:

```
50 rows
```

Sequential scan wins.

Huge table:

```
10 million rows
```

Index scan usually wins.

---

# Slow Query Example

Bad:

```sql
SELECT *

FROM users

WHERE LOWER(email)='rahul@example.com';
```

Regular index on `email` cannot be used efficiently because the column is wrapped in a function.

Better:

```sql
CREATE INDEX idx_users_lower_email

ON users(LOWER(email));
```

This is called a **functional index**.

---

# LIKE Optimization

Good:

```sql
WHERE name LIKE 'Rah%'
```

Can use a B-tree index.

Bad:

```sql
WHERE name LIKE '%hul'
```

Leading wildcard prevents efficient B-tree usage.

---

# ORDER BY Optimization

Index:

```sql
(email)
```

Query:

```sql
ORDER BY email;
```

May avoid an extra sort.

---

# LIMIT Optimization

```sql
SELECT *

FROM users

ORDER BY created_at DESC

LIMIT 10;
```

Index:

```sql
(created_at DESC)
```

Allows PostgreSQL to quickly retrieve the newest rows.

---

# Indexes for Foreign Keys

Always consider indexing frequently joined foreign keys.

```sql
orders.user_id
```

Joins become much faster.

---

# Real Example — Todo App

```sql
CREATE INDEX idx_todos_user

ON todos(user_id);
```

Query:

```sql
SELECT *

FROM todos

WHERE user_id=5;
```

Fast.

---

# Real Example — URL Shortener

```sql
CREATE UNIQUE INDEX idx_short_code

ON urls(short_code);
```

Redirect query:

```sql
SELECT original_url

FROM urls

WHERE short_code='abc123';
```

Milliseconds.

---

# Real Example — Analytics

```sql
CREATE INDEX idx_clicks_time

ON clicks(clicked_at);
```

Useful:

```sql
WHERE clicked_at >= CURRENT_DATE - INTERVAL '7 days'
```


# Indexing Cheat Sheet

```sql
-- Create index
CREATE INDEX idx_users_email
ON users(email);

-- Composite index
CREATE INDEX idx_orders_user_date
ON orders(user_id, created_at);

-- Partial index
CREATE INDEX idx_active_users
ON users(email)
WHERE is_active = TRUE;

-- Functional index
CREATE INDEX idx_lower_email
ON users(LOWER(email));

-- Show query plan
EXPLAIN
SELECT * FROM users;

-- Execute and analyze
EXPLAIN ANALYZE
SELECT * FROM users;

-- Update statistics
ANALYZE users;

-- Cleanup and analyze
VACUUM ANALYZE users;
```

# 💡 Senior Backend Engineer Insight

When a production API becomes slow, experienced engineers follow a structured approach instead of immediately adding indexes.

```
Slow API
    │
    ▼
Measure (EXPLAIN ANALYZE)
    │
    ▼
Find Bottleneck
    │
    ├── Sequential Scan?
    ├── Missing Index?
    ├── Too Many Rows?
    ├── Bad JOIN?
    ├── N+1 Query?
    └── Outdated Statistics?
    │
    ▼
Optimize
    │
    ▼
Measure Again
```

A few principles used by senior backend engineers:

- **Measure first, optimize second.** Never guess.
- **Indexes are not free.** Every additional index speeds up reads but slows down writes and uses storage.
- **Design indexes around real queries**, not around tables.
- **Use `EXPLAIN ANALYZE` regularly**—it's one of the most valuable tools for diagnosing database performance.

Many backend performance problems are solved with a combination of better indexes, more selective queries, and improved schema design rather than adding more application code.
