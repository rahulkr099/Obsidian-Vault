# What is MongoDB?

MongoDB is a **NoSQL document database**.

Instead of:

```
Database
    ↓
Tables
    ↓
Rows
    ↓
Columns
```

MongoDB uses:

```
Database
    ↓
Collections
    ↓
Documents
```

---

# SQL vs MongoDB

SQL:

```
Users Table

ID
Name
Age
```

MongoDB:

```json
{
  "_id": "...",
  "name": "Rahul",
  "age": 22
}
```

Every document is self-contained.

# BSON

MongoDB stores data as **BSON** (Binary JSON).

JSON:

```json
{
  "age": 22
}
```

BSON supports additional types:

- Date
- Binary
- ObjectId
- Decimal128
- Long
- Timestamp

Advantages:

- Faster parsing
- More data types
- Efficient storage

---

# ObjectId

Default MongoDB primary key.

Example:

```
685d69afef9d6b79b54a7e10
```

ObjectIds are:

- Globally unique
- Ordered by creation time
- Efficient for indexing

---

# ObjectId Structure

```
ObjectId

├── Timestamp
├── Random Value
└── Counter
```

This is why newer documents generally have larger ObjectIds.

# Schema Design

Unlike SQL, MongoDB doesn't require a rigid schema.

That doesn't mean:

```
Anything goes.
```

Production systems still define clear document structures.

# Embed vs Reference

This is one of MongoDB's most important design decisions.

---

# Embedding

```json
{
  "name": "Rahul",
  "addresses": [
    {
      "city": "Delhi",
      "country": "India"
    }
  ]
}
```

Everything stored together.

---

# Referencing

Users:

```json
{
  "_id": "...",
  "name": "Rahul"
}
```

Orders:

```json
{
  "_id": "...",
  "userId": "..."
}
```

Relationship through IDs.

---

# When to Embed

Embed when:

- Data belongs only to one document
- Data is read together
- Arrays remain reasonably small

Examples:

- Addresses
- User preferences
- Social links

---

# When to Reference

Reference when:

- Data is shared
- Data grows indefinitely
- Many documents refer to the same entity

Examples:

- Users
- Orders
- Products
- Posts

---

# Aggregation Pipeline

MongoDB's most powerful feature.

Pipeline:

```
Documents

↓

Stage 1

↓

Stage 2

↓

Stage 3

↓

Result
```

Each stage transforms the data.

---

# $match

Equivalent to SQL:

```sql
WHERE
```

Example:

```jsx
db.users.aggregate([
  {
    $match: {
      age: { $gte: 18 }
    }
  }
]);
```

---

# $project

Choose fields.

```jsx
db.users.aggregate([
  {
    $project: {
      name: 1,
      email: 1
    }
  }
]);
```

Equivalent to selecting specific columns.

---

# $group

Equivalent to SQL:

```sql
GROUP BY
```

Example:

```jsx
db.orders.aggregate([
  {
    $group: {
      _id: "$userId",
      totalSpent: {
        $sum: "$total"
      }
    }
  }
]);
```

---

# $sort

```jsx
{
  $sort: {
    totalSpent: -1
  }
}
```

Descending.

---

# $limit

```jsx
{
  $limit: 10
}
```

---

# Complete Pipeline

```jsx
db.orders.aggregate([
  {
    $match: {
      status: "completed"
    }
  },
  {
    $group: {
      _id: "$userId",
      revenue: {
        $sum: "$total"
      }
    }
  },
  {
    $sort: {
      revenue: -1
    }
  },
  {
    $limit: 5
  }
]);
```

Top five customers.

---

# $lookup

Equivalent to SQL JOIN.

Users:

↓

Orders

```jsx
db.users.aggregate([
  {
    $lookup: {
      from: "orders",
      localField: "_id",
      foreignField: "userId",
      as: "orders"
    }
  }
]);
```

---

# $unwind

# MongoDB Indexes

Create:

```jsx
db.users.createIndex({
  email: 1
});
```

Search:

```jsx
db.users.find({
  email: "rahul@example.com"
});
```

Fast.

---

# Compound Index

```jsx
db.orders.createIndex({
  userId: 1,
  createdAt: -1
});
```

Useful:

```jsx
find({
  userId: ...
}).sort({
  createdAt: -1
});
```

---

# Unique Index

```jsx
db.users.createIndex(
  {
    email: 1
  },
  {
    unique: true
  }
);
```

No duplicate emails.

---

# Explain

```jsx
db.users.find({
  email: "rahul@example.com"
}).explain("executionStats");
```

Shows:

- Index used
- Documents examined
- Execution time

# Replica Set

High availability.

```
Primary

↓

Secondary

↓

Secondary
```

Primary handles writes.

Secondaries replicate data.

---

# Failover

Primary crashes.

↓

Secondary becomes new Primary.

Applications continue working after reconnection.

---

# Write Concern

Control write acknowledgment.

Example:

```jsx
{
  writeConcern: {
    w: "majority"
  }
}
```

Ensures most replica set members acknowledge the write before success is reported.

---

# Read Preference

Choose where reads come from.

Examples:

- Primary
- Secondary
- Nearest

Most applications use the primary by default for the freshest data.

---

# Sharding

Horizontal scaling.

Without sharding:

```
Server

↓

2 TB Data
```

One machine.

---

With sharding:

```
Shard 1

Shard 2

Shard 3
```

Data distributed across multiple servers.

---

# Shard Key

Critical decision.

Examples:

```
userId

createdAt

region
```

A poor shard key can lead to uneven data distribution (hotspots).

---

# Transactions

MongoDB supports ACID transactions.

```jsx
const session = await mongoose.startSession();

await session.withTransaction(async () => {

  // operations

});
```

Use when multiple documents must remain consistent.

---

# Change Streams

Listen for changes.

```jsx
User Updated

↓

MongoDB

↓

Notification
```

Example use cases:

- Notifications
- Audit logs
- Cache invalidation

Replica sets are required.

---

# TTL Index

Automatically delete expired documents.

```jsx
db.sessions.createIndex(
  {
    expiresAt: 1
  },
  {
    expireAfterSeconds: 0
  }
);
```

Perfect for:

- Sessions
- OTPs
- Temporary tokens

# MongoDB vs PostgreSQL

|PostgreSQL|MongoDB|
|---|---|
|Tables|Collections|
|Rows|Documents|
|JOINs|`$lookup`|
|Fixed schema|Flexible schema|
|Strong relational modeling|Document modeling|
|Excellent for complex transactions|Excellent for document-centric applications|

Neither is universally better—the choice depends on the problem.

# Best Practices

### Design Documents Around Access Patterns

Think about how your application reads data, not just how it stores data.

---

### Embed Small, Related Data

Addresses and preferences are good candidates.

---

### Reference Large or Shared Data

Orders, users, and products usually deserve separate collections.

---

### Index Frequently Queried Fields

Examples:

- email
- userId
- createdAt

---

### Use Aggregation Instead of Heavy Application Logic

Let MongoDB process data efficiently.

---

❌ Embedding unbounded arrays that grow forever.

---

❌ Creating indexes on every field.

---

❌ Using MongoDB because it seems "schema-free."

---

❌ Ignoring `explain()`.

---

❌ Using `$lookup` excessively when a better document design could avoid it.

# MongoDB Cheat Sheet

```jsx
// Create index
db.users.createIndex({ email: 1 });

db.users.createIndex(
  { email: 1 },
  { unique: true }
);

// Compound index
db.orders.createIndex({
  userId: 1,
  createdAt: -1
});

// Aggregation
db.orders.aggregate([
  { $match: { status: "completed" } },
  { $group: { _id: "$userId", total: { $sum: "$total" } } }
]);

// Explain

  email: "rahul@example.com"
```

# 💡 Senior Backend Engineer Insight

A common mistake is asking:

> **"Should I use PostgreSQL or MongoDB?"**

A better question is:

> **"What type of data am I storing, and how will it be accessed?"**

A modern backend often combines both:

```
                 React
                   │
                   ▼
              Express API
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
 PostgreSQL     MongoDB      Redis
   Orders       Logs &       Cache,
  Payments      Analytics    Sessions
 Relationships  Flexible
```

For example, in a SaaS application:

- **PostgreSQL** stores users, subscriptions, invoices, and payments.
- **MongoDB** stores activity logs, audit events, and flexible metadata.
- **Redis** caches frequently accessed data, sessions, OTPs, and rate-limiting counters.

Choosing the right database for each workload is a hallmark of experienced backend engineering.
