# The Troubleshooting Mindset

When a user says:

> "The API isn't working."

Don't immediately restart the server.

Instead ask:

1. Can the client resolve the hostname?
    
2. Can the client reach the server?
    
3. Is the server listening?
    
4. Is the firewall blocking traffic?
    
5. Is the application healthy?
    
6. Is the reverse proxy configured correctly?
    

Always work from the outside in.

# Scenario 1 — Connection Refused

Browser:

```text
Connection Refused
```

What it means:

The destination machine is reachable, but **nothing is accepting connections on that port**, or the connection is immediately rejected.

---

## Step 1

Check the listening ports:

```bash
ss -tuln
```

Expected:

```text
LISTEN 0.0.0.0:3000
```

If port `3000` is missing:

- The application may not be running.
    
- The application may be listening on a different port.
    

---

## Step 2

Check the application process:

```bash
ps aux | grep node
```

or

```bash
systemctl status myapp
```

depending on how the service is managed.

---

## Step 3

Inspect application logs.

For example:

```text
EADDRINUSE
```

or

```text
Database connection failed
```

---

# Scenario 2 — Connection Timed Out

Browser:

```text
Connection Timed Out
```

Meaning:

Packets are not reaching the application or responses are not returning.

---

## Check connectivity

```bash
ping server-ip
```

No response?

Possible causes:

- Server down
    
- Firewall
    
- Routing issue
    
- ICMP blocked (some servers intentionally do this)
    

---

## Check routing

```bash
traceroute server-ip
```

If packets stop halfway:

The routing path is broken or filtered.

---

## Capture packets

```bash
sudo tcpdump port 443
```

No packets?

Traffic never reaches the server.

---

# Scenario 3 — DNS Failure

Browser:

```text
DNS_PROBE_FINISHED_NXDOMAIN
```

---

## Verify DNS

```bash
dig example.com
```

or

```bash
host example.com
```

No answer?

DNS is likely the issue.

---

## Query another resolver

```bash
dig @8.8.8.8 example.com
```

If this works but your default resolver fails:

The local DNS server is probably misconfigured or unavailable.

---

# Scenario 4 — API Works Locally but Not From Another Computer

Local:

```text
localhost:3000

✓ Works
```

Another computer:

```text
192.168.1.20:3000

✗ Doesn't work
```

---

## Check listening address

```bash
ss -tuln
```

Bad:

```text
127.0.0.1:3000
```

Good:

```text
0.0.0.0:3000
```

Listening only on `127.0.0.1` restricts access to the local machine.

---

# Scenario 5 — Port Already in Use

Application:

```text
EADDRINUSE
```

Find the process:

```bash
sudo ss -tulpn
```

Example:

```text
3000

↓

node

↓

PID 4321
```

Now you know exactly which process owns the port.

---

# Scenario 6 — Firewall Blocking Traffic

Application is listening.

Still unreachable.

Inspect firewall rules:

```bash
sudo nft list ruleset
```

or

```bash
sudo iptables -L -n
```

Look for:

```text
drop

reject
```

on your application's port.

---

# Scenario 7 — Docker Container Can't Reach Another Container

Check IP:

```bash
docker inspect container1
```

Check routes:

```bash
docker exec container1 ip route
```

Test:

```bash
docker exec container1 ping container2
```

Inspect bridge:

```bash
ip link show docker0
```

Common causes:

- Wrong network
    
- Missing bridge
    
- Firewall
    
- Incorrect Docker network configuration
    

---

# Scenario 8 — Reverse Proxy Failure

Example architecture:

```text
Internet

↓

Nginx

↓

Express
```

User gets:

```text
502 Bad Gateway
```

Check:

```bash
ss -tuln
```

Is Express listening?

Next:

```bash
curl http://localhost:3000
```

If Express responds locally, inspect the Nginx configuration.

---

# Scenario 9 — Slow API

Measure latency:

```bash
ping api.example.com
```

Check routes:

```bash
traceroute api.example.com
```

Capture traffic:

```bash
sudo tcpdump port 443
```

Check the application itself:

- Slow database queries
    
- CPU usage
    
- Memory usage
    

Networking isn't always the bottleneck.

---

# Scenario 10 — HTTPS Doesn't Work

Check listening ports:

```bash
ss -tuln
```

Expect:

```text
443
```

Capture:

```bash
sudo tcpdump port 443
```

Verify TLS configuration:

```bash
openssl s_client -connect example.com:443
```

This helps diagnose certificate and TLS handshake issues.

If you only remember **10 networking commands**, make them these:

|---|---|

|`ip route`|Show routing table|

# Interview Problem

**Question:**

> Users cannot access your backend API. How would you troubleshoot it?

A strong answer:

1. Verify DNS resolution with `dig`.
    
2. Test connectivity with `ping` (if ICMP is permitted).
    
3. Inspect the route using `traceroute`.
    
4. Confirm the service is listening using `ss -tuln`.
    
5. Check firewall rules (`nftables` or `iptables`).
    
6. Capture traffic with `tcpdump` if necessary.
    
7. Review application logs for errors.
    

This demonstrates a structured, production-oriented approach.
