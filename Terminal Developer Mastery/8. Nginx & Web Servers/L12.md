# Lesson 12 — Load Balancing with Nginx

This lesson is about **scaling your backend**.

So far, your architecture has looked like this:

```text
Internet
    │
    ▼
  Nginx
    │
    ▼
Node.js
    │
    ▼

```

This works well for small applications.

But what happens when:

- 10,000 users visit simultaneously?
    
- Your CPU reaches 100%?
    
- Your Node.js process crashes?
    
- One server can't handle all requests?
    

The answer is **Load Balancing**.

# What is Load Balancing?

Instead of sending every request to one backend server...

```text
Users

↓

Nginx

↓

Node.js Server
```

...Nginx distributes requests across multiple servers.

```text
Users

↓

Nginx

├── Node 1
├── Node 2
└── Node 3
```

Every server shares the workload.

---

# Why Do We Need It?

Imagine one cashier in a supermarket.

```text
Customers

↓

Cashier
```

As customers increase:

- Long queues
    
- Slow service
    
- Frustrated customers
    

Now imagine three cashiers.

```text
Customers

↓

Cashier 1

Cashier 2

Cashier 3
```

Customers are served much faster.

Nginx acts like the manager deciding which cashier gets the next customer.

---

# Single Server Problem

```text
           1000 Requests
                 │
                 ▼
            Node.js Server
```

Problems:

- CPU overload
    
- Memory exhaustion
    
- Longer response times
    
- Single point of failure
    

---

# Multiple Servers

```text
           1000 Requests
                 │
                 ▼
               Nginx
      ┌──────────┼──────────┐
      ▼          ▼          ▼
   Node 1     Node 2     Node 3
```

Now each server handles roughly one-third of the requests (depending on the balancing algorithm).

---

# The `upstream` Block

Load balancing starts with an **upstream** block.

Example:

```nginx
upstream backend {

    server localhost:3001;

    server localhost:3002;

    server localhost:3003;

}
```

Instead of one backend:

```nginx
proxy_pass http://localhost:3000;
```

Use:

```nginx
proxy_pass http://backend;
```

Nginx chooses which server receives each request.

---

# Default Algorithm — Round Robin

If you don't specify an algorithm, Nginx uses **Round Robin**.

Requests:

```text
Request 1 → Server 1

Request 2 → Server 2

Request 3 → Server 3

Request 4 → Server 1

Request 5 → Server 2

Request 6 → Server 3
```

This evenly distributes traffic when servers have similar capacity.

---

# Visual Example

```text
Users

↓

Nginx

↓

1

↓

Node 1

↓

2

↓

Node 2

↓

3

↓

Node 3

↓

4

↓

Node 1
```

The cycle repeats.

---

# When Round Robin Works Best

Use it when:

- Servers have similar hardware
    
- Applications are stateless
    
- Traffic is evenly distributed
    

This is the most common starting point.

---

# Least Connections

Some requests finish quickly.

Others take much longer.

Instead of simply rotating servers...

Nginx can choose the backend with the **fewest active connections**.

Configuration:

```nginx
upstream backend {

    least_conn;

    server localhost:3001;

    server localhost:3002;

    server localhost:3003;

}
```

---

# Example

Current load:

```text
Server 1 → 25 connections

Server 2 → 8 connections

Server 3 → 17 connections
```

New request:

↓

Sent to:

```text
Server 2
```

because it has the fewest active connections.

---

# When to Use Least Connections

Ideal for:

- File uploads
    
- Report generation
    
- Image processing
    
- Long-running API requests
    

---

# IP Hash

Sometimes a user must always reach the same backend.

Example:

- Shopping cart
    
- In-memory sessions
    
- Game server
    

Configuration:

```nginx
upstream backend {

    ip_hash;

    server localhost:3001;

    server localhost:3002;

    server localhost:3003;

}
```

---

# How IP Hash Works

Client:

```text
203.0.113.10
```

↓

Always:

```text
Server 2
```

Another client:

```text
198.51.100.20
```

↓

Always:

```text
Server 1
```

This is called **sticky routing**.

---

# Why Sticky Sessions Matter

Suppose login sessions are stored only in memory.

Without sticky routing:

```text
Request 1

↓

Server 1

(Login stored)
```

Next request:

```text
↓

Server 3

(No login)

↓

User appears logged out
```

With IP hash:

```text
Every request

↓

Server 1
```

Session remains available.

> **Production Note:** Modern applications often store sessions in shared storage like Redis instead of relying on sticky routing. This allows any backend server to handle a user's request.

---

# Weighted Load Balancing

Not every server is equally powerful.

Suppose:

```text
Server 1

16 CPU cores
```

```text
Server 2

4 CPU cores
```

Server 1 should receive more traffic.

Configuration:

```nginx
upstream backend {

    server localhost:3001 weight=4;

    server localhost:3002 weight=1;

}
```

Meaning:

Out of five requests (on average):

```text
4

↓

Server 1

1

↓

Server 2
```

---

# Backup Server

Suppose one server is reserved for emergencies.

Configuration:

```nginx
upstream backend {

    server localhost:3001;

    server localhost:3002;

    server localhost:3003 backup;

}
```

Normally:

```text
3001

3002
```

Only.

If both fail:

↓

```text
3003
```

becomes active.

---

# Marking Servers Down

For maintenance:

```nginx
upstream backend {

    server localhost:3001;

    server localhost:3002 down;

}
```

Server 2 won't receive requests.

Useful during upgrades.

---

# Passive Health Checks

Open-source Nginx performs **passive** health checks.

If a backend repeatedly fails...

```text
Nginx

↓

Server

↓

Connection Failed

↓

Temporarily Avoid Server
```

This behavior is controlled with options like `max_fails` and `fail_timeout`.

Example:

```nginx
upstream backend {

    server localhost:3001 max_fails=3 fail_timeout=30s;

    server localhost:3002;
}
```

If Server 1 fails three connection attempts within 30 seconds, Nginx temporarily stops sending requests to it.

> **Note:** Active health checks (where Nginx periodically probes servers) are available in Nginx Plus, not in the open-source edition.

---

# Failure Example

Suppose:

```text
Node 2

↓

Crash
```

Nginx:

```text
Node 2

↓

Unavailable

↓

Route traffic

↓

Node 1

Node 3
```

Users may notice little or no disruption if the remaining servers can handle the load.

# High Availability (HA)

High Availability means:

> Keep the application running even when components fail.

Architecture:

```text
          Users
             │
             ▼
           Nginx
     ┌───────┼────────┐
     ▼       ▼        ▼
  Node 1  Node 2   Node 3
     │       │        │
     └────────┼────────┘
              ▼
          Shared Database
```

If one backend fails:

The others continue serving requests.

---

# Scaling Horizontally

Instead of buying a larger server...

```text
One Bigger Server
```

you add more servers:

```text
Node 1

Node 2

Node 3

Node 4

Node 5
```

This is **horizontal scaling**.

---

# Horizontal vs Vertical Scaling

|Vertical Scaling|Horizontal Scaling|
|---|---|
|Bigger CPU/RAM|More servers|
|Limited by hardware|Easier to expand|
|Simpler initially|Better long-term scalability|
|Single machine|Multiple machines|

Large internet services typically rely heavily on horizontal scaling.

# PM2 Cluster vs Nginx Load Balancing

Many Node.js developers ask:

> Why use PM2 Cluster if Nginx can load balance?

### PM2 Cluster

```text
One Machine

↓

PM2

↓

CPU Core 1

CPU Core 2

CPU Core 3

CPU Core 4
```

Uses all CPU cores on a **single server**.

---

### Nginx Load Balancing

```text
Nginx

↓

Server A

Server B

Server C
```

Distributes requests across **multiple servers**.

In production, it's common to use **both**:

```text
Internet

↓

Nginx

↓

Server A (PM2 Cluster)

↓

Server B (PM2 Cluster)

↓

Server C (PM2 Cluster)
```

# Common Problems

## Uneven Load

One server receives more traffic.

Possible causes:

- Incorrect weights
    
- Sticky sessions
    
- Long-running requests
    

---

## Session Loss

If sessions are stored only in application memory:

```text
Login

↓

Server 1

↓

Next Request

↓

Server 2

↓

Session Missing
```

Solution:

Use Redis or another shared session store.

---

## Database Bottleneck

Even with ten application servers:

```text
10 Servers

↓

One Database
```

The database may become the next performance bottleneck.

Scaling the application tier doesn't automatically scale the database.

---

# Best Practices

- Use `upstream` blocks instead of hardcoded backend addresses.
    
- Start with Round Robin unless you have a specific reason to choose another algorithm.
    
- Use `least_conn` for workloads with long-lived requests.
    
- Avoid relying on `ip_hash` when you can use a shared session store.
    
- Monitor backend health and remove unhealthy servers quickly.
    
- Combine Nginx load balancing with application process managers like PM2 for Node.js.
    

---

# Interview Questions

### 1. What is load balancing?

Load balancing distributes incoming requests across multiple backend servers to improve performance, scalability, and availability.

---

### 2. What is the default load-balancing algorithm in Nginx?

**Round Robin.**

---

### 3. When would you choose `least_conn` over Round Robin?

When requests vary significantly in duration, so sending new requests to the least busy server provides better distribution.

---

### 4. What does `ip_hash` do?

It consistently routes requests from the same client IP to the same backend server.

---

### 5. What is the difference between horizontal and vertical scaling?

- **Vertical scaling:** Increase the resources (CPU, RAM) of one server.
    
- **Horizontal scaling:** Add more servers and distribute traffic among them.

# Hands-on Practice

## Step 1: Run three Express servers

Create three simple Express apps listening on different ports:

- `3001`
    
- `3002`
    
- `3003`
    

Each should return a different message, such as:

```text
Hello from Server 1
```

```text
Hello from Server 2
```

```text
Hello from Server 3
```

---

## Step 2: Configure the upstream

```nginx
upstream express_backend {
    server localhost:3001;
    server localhost:3002;
    server localhost:3003;
}
```

---

## Step 3: Configure Nginx

```nginx
server {
    listen 80;
    server_name localhost;

    location / {
        proxy_pass http://express_backend;
    }
}
```

---

## Step 4: Test the configuration

```bash
sudo nginx -t
```

Reload Nginx:

```bash
sudo systemctl reload nginx
```

---

## Step 5: Verify load balancing

Run:

```bash
for i in {1..10}; do
    curl http://localhost
done
```

You should see responses alternating among the three servers (with the default Round Robin algorithm).

---

## Step 6: Simulate a failure

Stop one Express server, for example:

```bash
pm2 stop 1
```

or terminate the process manually.

Run the `curl` loop again and observe how requests continue to be served by the remaining backend servers.

---

# Key Takeaways

- Load balancing distributes requests across multiple backend servers.
    
- `upstream` groups define the pool of backend servers.
    
- Round Robin is the default balancing algorithm.
    
- `least_conn` is useful for uneven or long-running requests.
    
- `ip_hash` provides sticky routing but is not a replacement for shared session storage.
    
- Horizontal scaling is the standard approach for growing production systems.
    
- Combining Nginx with PM2 clusters is a common architecture for scalable Node.js deployments.
