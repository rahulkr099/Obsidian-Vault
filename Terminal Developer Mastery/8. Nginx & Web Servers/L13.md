# Why Performance Matters

Imagine your API receives:

```text
100 requests/second
```

Everything works fine.

A few months later:

```text
5,000 requests/second
```

Without optimization:

- CPU usage increases
    
- Memory usage increases
    
- Response times become slower
    
- Users experience delays
    

Good Nginx tuning can significantly improve throughput before you need additional servers.

---

# Performance Flow

Without optimization:

```text
Browser
   │
   ▼
 Nginx
   │
   ▼
Disk
```

Every request requires more work.

With optimization:

```text
Browser
   │
   ▼
 Nginx
 ├── Cache
 ├── Compression
 ├── Optimized I/O
 └── Worker Tuning
```

# Gzip Compression

Suppose your HTML file is:

```text
100 KB
```

With gzip:

```text
30 KB
```

The browser downloads much less data.

Benefits:

- Faster page loads
    
- Less bandwidth
    
- Reduced network latency
    

---

# Enable Gzip

```nginx
gzip on;
```

---

# Recommended Configuration

```nginx
gzip on;

gzip_comp_level 5;

gzip_min_length 1024;

gzip_vary on;

gzip_proxied any;

gzip_types
    text/plain
    text/css
    application/json
    application/javascript
    application/xml
    image/svg+xml;
```

---

## What These Directives Mean

### Enable compression

```nginx
gzip on;
```

Turns gzip on.

---

### Compression level

```nginx
gzip_comp_level 5;
```

Range:

```text
1 → Fastest

9 → Smallest files
```

Typical production value:

```text
5
```

Good balance between CPU usage and compression.

---

### Minimum size

```nginx
gzip_min_length 1024;
```

Files smaller than **1 KB** are not compressed because the overhead usually outweighs the benefit.

---

### Compress Only Useful Types

Compress:

- HTML
    
- CSS
    
- JavaScript
    
- JSON
    
- XML
    
- SVG
    

Avoid compressing:

- JPEG
    
- PNG
    
- MP4
    
- ZIP
    
- PDF
    

These formats are already compressed.

---

# Compression Example

Without gzip:

```text
HTML

100 KB

↓

Browser
```

With gzip:

```text
HTML

30 KB

↓

Browser
```

Network transfer becomes much faster.

# Brotli Compression

Modern browsers also support **Brotli**.

Compared to gzip:

|Gzip|Brotli|
|---|---|
|Older|Newer|
|Good compression|Better compression|
|Faster to compress|Slower to compress|
|Universal support|Supported by most modern browsers|

Brotli often produces **smaller responses** than gzip.

> **Note:** Brotli is not included in many default Nginx builds. It often requires installing an additional module or using a package that includes Brotli support.

# Browser Caching

Imagine downloading:

```text
logo.png
```

every time a page loads.

Wasteful.

Instead:

```text
Browser

↓

Download Once

↓

Store Locally

↓

Reuse
```

Much faster.

---

# Cache Static Files

```nginx
location ~* \.(css|js|png|jpg|jpeg|gif|svg|woff2?)$ {

    expires 30d;

    add_header Cache-Control "public";
}
```

Now browsers cache these files for **30 days**.

---

# Cache Versioning

Suppose:

```text
app.js
```

gets updated.

Browser still has the old version cached.

A better approach:

```text
app.94a2f.js
```

When the content changes, the filename changes too.

This is called **cache busting**.

React, Vite, Webpack, and other build tools do this automatically.

---

# Open File Cache

Nginx repeatedly checks files on disk.

Example:

```text
logo.png

style.css

script.js
```

Instead of checking disk metadata every time, Nginx can cache file information.

---

Configuration:

```nginx
open_file_cache max=1000 inactive=20s;

open_file_cache_valid 60s;

open_file_cache_min_uses 2;

open_file_cache_errors on;
```

Benefits:

- Fewer filesystem lookups
    
- Lower CPU usage
    
- Better performance for frequently accessed files
    

---

# sendfile

Normally:

```text
Disk

↓

Kernel

↓

Nginx

↓

Browser
```

Data passes through user space.

With:

```nginx
sendfile on;
```

Flow:

```text
Disk

↓

Kernel

↓

Browser
```

The kernel transfers the file directly to the network socket.

Benefits:

- Lower CPU usage
    
- Faster file transfers
    
- Fewer memory copies
    

---

# tcp_nopush

Used with `sendfile`.

Configuration:

```nginx
tcp_nopush on;
```

Nginx sends larger packets instead of many small ones.

This is efficient for large static files.

---

# tcp_nodelay

Configuration:

```nginx
tcp_nodelay on;
```

Sends small packets immediately.

Useful for:

- APIs
    
- Interactive applications
    
- Chat applications
    

---

# sendfile + TCP

Typical production setup:

```nginx
sendfile on;

tcp_nopush on;

tcp_nodelay on;
```

This combination works well for most workloads.

---

# Worker Processes

You learned earlier:

```nginx
worker_processes auto;
```

This creates one worker per CPU core.

Example:

```text
8 CPU Cores

↓

8 Workers
```

This is the recommended setting in most cases.

---

# Worker Connections

```nginx
events {

    worker_connections 4096;

}
```

Maximum theoretical connections:

```text
Workers × Worker Connections
```

Example:

```text
8 Workers

×

4096

=

32768 Connections
```

Actual concurrency also depends on operating system limits and workload.

---

# File Descriptors

Linux limits how many files and sockets a process can open.

Check the limit:

```bash
ulimit -n
```

Example:

```text
1024
```

For high-traffic servers:

```text
65535
```

is a common target after tuning the operating system.

---

# Worker File Limit

```nginx
worker_rlimit_nofile 65535;
```

Allows workers to use more file descriptors, provided the OS limit is also increased.

---

# Keep-Alive

Without keep-alive:

```text
Connect

↓

Request

↓

Disconnect
```

Every request repeats the connection setup.

---

With:

```nginx
keepalive_timeout 65;
```

Connections remain open briefly for additional requests.

Benefits:

- Lower latency
    
- Less CPU
    
- Fewer TCP handshakes

# Benchmarking

How do you know your configuration is better?

Measure it.

Popular tools:

- `wrk`
    
- `ab` (ApacheBench)
    
- `hey`
    
- `siege`
    

---

## ApacheBench

Example:

```bash
ab -n 1000 -c 100 http://localhost/
```

Meaning:

```text
1000 Requests

100 Concurrent Users
```

Useful for quick tests.

---

## wrk

```bash
wrk -t4 -c100 -d30s http://localhost
```

Meaning:

|Option|Meaning|
|---|---|
|`-t4`|4 threads|
|`-c100`|100 concurrent connections|
|`-d30s`|Run for 30 seconds|

`wrk` is generally preferred over `ab` for modern benchmarking.

# Production Example

```nginx
worker_processes auto;

worker_rlimit_nofile 65535;

events {
    worker_connections 4096;
}

http {

    sendfile on;

    tcp_nopush on;

    tcp_nodelay on;

    gzip on;

    gzip_comp_level 5;

    keepalive_timeout 65;

}
```

This provides a strong baseline for many production deployments.

# Common Mistakes

## Compressing Images

Bad:

```text
PNG

↓

Gzip
```

Little or no benefit.

May waste CPU.

---

## Compression Level Too High

```nginx
gzip_comp_level 9;
```

Very high CPU usage.

Usually unnecessary.

---

## No Browser Cache

Every refresh downloads:

```text
CSS

JavaScript

Images
```

again.

This wastes bandwidth and slows page loads.

---

## Too Few Worker Connections

```nginx
worker_connections 128;
```

High traffic may exhaust available connections.

---

## Ignoring Benchmark Results

Always:

1. Measure baseline performance.
    
2. Make one change.
    
3. Measure again.
    

Avoid changing many settings simultaneously without testing.

---

# Best Practices

- Enable `sendfile`.
    
- Enable gzip for text-based content.
    
- Use Brotli if your Nginx build supports it.
    
- Cache static assets aggressively with versioned filenames.
    
- Use `worker_processes auto`.
    
- Increase file descriptor limits for busy servers.
    
- Benchmark before and after tuning.
    
- Monitor logs and system resources continuously.

# Interview Questions

### 1. What does `sendfile` do?

It allows the operating system kernel to transfer files directly from disk to the network socket, reducing CPU overhead.

---

### 2. Why shouldn't JPEG and PNG files be compressed with gzip?

They are already compressed, so gzip provides little benefit while consuming additional CPU resources.

---

### 3. What is the purpose of `worker_processes auto;`?

It automatically creates one worker process per available CPU core.

---

### 4. What does `open_file_cache` improve?

It caches file metadata and descriptors, reducing repeated filesystem lookups for frequently accessed files.

---

### 5. Which benchmarking tools are commonly used with Nginx?

Common tools include:

- `wrk`
    
- `ab` (ApacheBench)
    
- `hey`
    
- `siege`

# Key Takeaways

- Gzip significantly reduces the size of text-based responses.
    
- Brotli can provide even better compression for supported clients.
    
- Browser caching reduces repeat downloads and improves user experience.
    
- `sendfile` enables efficient kernel-level file transfers.
    
- `worker_processes auto` and appropriate `worker_connections` improve concurrency.
    
- Benchmarking and monitoring are essential before and after performance tuning.
    
- Measure changes rather than assuming an optimization will improve performance.
