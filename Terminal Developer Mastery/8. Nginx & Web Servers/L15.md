# Production Architecture

A typical production deployment looks like this:

```text
                 Internet
                     │
                     ▼
              HTTPS (443)
                     │
                     ▼
                 Firewall
                     │
                     ▼
                  Nginx
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   React Build   Express API   Admin Panel
        │            │
        └────────────┘
              │
              ▼
        PostgreSQL/MongoDB
```

Nginx is the public entry point.

Everything else stays on private ports.

# Organizing Configuration

A clean directory structure helps as your infrastructure grows.

```text
/etc/nginx/

├── nginx.conf
├── mime.types
├── conf.d/
├── sites-available/
└── sites-enabled/
```

For multiple applications:

```text
sites-available/

api.example.com

blog.example.com

admin.example.com
```

Enable a site:

```bash
sudo ln -s /etc/nginx/sites-available/api.example.com \
/etc/nginx/sites-enabled/
```

Disable:

```bash
sudo rm /etc/nginx/sites-enabled/api.example.com
```

Always validate:

```bash
sudo nginx -t
```

Reload:

```bash
sudo systemctl reload nginx
```

# HTTPS (SSL/TLS)

Never expose login forms or APIs over plain HTTP.

HTTP:

```text
Browser

↓

Plain Text

↓

Server
```

HTTPS:

```text
Browser

↓

Encrypted

↓

Server
```

Benefits:

- Encryption
    
- Integrity
    
- Authentication
    
- Required for many modern browser features
    

---

# Redirect HTTP → HTTPS

```nginx
server {
    listen 80;
    server_name example.com www.example.com;

    return 301 https://$host$request_uri;
}
```

Every HTTP request is redirected to HTTPS.

---

# Example HTTPS Server

```nginx
server {

    listen 443 ssl http2;

    server_name example.com;

    ssl_certificate /etc/ssl/example/fullchain.pem;

    ssl_certificate_key /etc/ssl/example/private.key;

    location / {

        proxy_pass http://localhost:3000;

    }

}
```

> In production, many teams obtain certificates from a trusted Certificate Authority such as Let's Encrypt and renew them automatically.

# Security Headers

Security headers help browsers protect users.

Example:

```nginx
add_header X-Frame-Options "SAMEORIGIN" always;

add_header X-Content-Type-Options "nosniff" always;

add_header Referrer-Policy "strict-origin-when-cross-origin" always;

add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
```

These headers help reduce common web attacks and limit unnecessary browser capabilities.

---

## Content Security Policy (CSP)

A Content Security Policy restricts where browsers can load scripts, styles, images, and other resources from.

Example:

```nginx
add_header Content-Security-Policy "default-src 'self';" always;
```

> CSP should be tailored to your application. A policy that is too restrictive can break legitimate functionality.

# Hide Nginx Version

Default error pages may expose the server version.

Disable it:

```nginx
server_tokens off;
```

Instead of:

```text
nginx/1.28.0
```

users simply see:

```text
nginx
```

This reduces information disclosure.

---

# Restrict Request Size

Prevent excessively large uploads.

```nginx
client_max_body_size 20M;
```

Use the smallest value that meets your application's needs.

---

# Rate Limiting

Protect APIs from abuse.

Define a zone:

```nginx
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
```

Apply it:

```nginx
location /api/ {

    limit_req zone=api_limit burst=20;

    proxy_pass http://localhost:3000;
}
```

This limits clients to approximately 10 requests per second with a burst allowance.

---

# Restrict Sensitive Files

Never expose configuration files.

```nginx
location ~ /\. {

    deny all;

}
```

This blocks requests for hidden files such as:

```text
.env

.git

.htaccess
```

---

# Disable Directory Listing

Avoid exposing file lists.

Good:

```nginx
autoindex off;
```

Only enable directory listing when you intentionally want users to browse files.

---

# Log Rotation

Without rotation:

```text
access.log

↓

50 GB

↓

100 GB

↓

200 GB
```

Eventually, logs can consume all available disk space.

Most Linux distributions configure `logrotate` for Nginx automatically, but it's worth verifying.

Check:

```bash
ls /etc/logrotate.d/
```

Look for:

```text
nginx
```

# Back Up Configuration

Before major changes:

```bash
sudo cp /etc/nginx/nginx.conf \
/etc/nginx/nginx.conf.bak
```

Or back up an entire site configuration:

```bash
sudo cp /etc/nginx/sites-available/api.example.com \
/etc/nginx/sites-available/api.example.com.bak
```

Version-controlling configuration (for example, with Git) is even better for teams.

---

# Zero-Downtime Reload

After configuration changes:

```bash
sudo nginx -t
```

Then:

```bash
sudo systemctl reload nginx
```

Reload:

- Keeps existing connections alive
    
- Applies new configuration
    
- Avoids unnecessary downtime
    

Prefer `reload` over `restart` for configuration updates.

# Common Production Mistakes

## Forgetting to Test

Bad:

```text
Edit

↓

Reload
```

Good:

```text
Edit

↓

nginx -t

↓

Reload
```

---

## Restart Instead of Reload

Restart:

```bash
systemctl restart nginx
```

Drops active connections.

Reload:

```bash
systemctl reload nginx
```

Keeps serving existing clients.

---

## Running the Backend Publicly

Bad:

```text
Internet

↓

Node.js:3000
```

Better:

```text
Internet

↓

Nginx

↓

Node.js
```

Keep backend services bound to `localhost` or private network interfaces unless there is a specific need otherwise.

---

## Weak File Permissions

Avoid world-writable files.

Example:

```bash
chmod 644 file.conf
chmod 755 directory
```

Ensure ownership is appropriate for your system.

---

## No Monitoring

Without monitoring:

```text
Website down

↓

Nobody notices
```

With monitoring:

```text
Website down

↓

Alert

↓

Fix
```

# Production Deployment Checklist

## Before Deployment

- Code reviewed
    
- Tests passed
    
- Environment variables verified
    
- Backups created
    

---

## Nginx

- `nginx -t` passes
    
- HTTPS configured
    
- HTTP redirects to HTTPS
    
- Reverse proxy working
    
- Security headers configured
    
- Logs enabled
    
- Rate limiting configured where appropriate
    

---

## Backend

- Process manager (e.g., PM2, systemd, Gunicorn) running
    
- Health endpoint available
    
- Listening only on localhost/private interface
    
- Database connection verified
    

---

## After Deployment

- Website loads
    
- API responds
    
- SSL certificate valid
    
- Logs clean
    
- CPU and memory healthy
    
- Error rate acceptable

# Example Production Configuration

```nginx
worker_processes auto;

events {
    worker_connections 4096;
}

http {

    sendfile on;

    gzip on;

    keepalive_timeout 65;

    server_tokens off;

    server {

        listen 80;

        server_name example.com;

        return 301 https://$host$request_uri;
    }

    server {

        listen 443 ssl http2;

        server_name example.com;

        ssl_certificate /etc/ssl/example/fullchain.pem;

        ssl_certificate_key /etc/ssl/example/private.key;

        client_max_body_size 20M;

        location / {

            proxy_pass http://localhost:3000;

            proxy_set_header Host $host;

            proxy_set_header X-Real-IP $remote_addr;

            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}
```

This is a simplified example. A production configuration often includes additional TLS settings, logging, caching, and application-specific directives.

# Best Practices

- Keep Nginx configuration modular.
    
- Use HTTPS for all production traffic.
    
- Hide unnecessary server information.
    
- Configure security headers thoughtfully.
    
- Keep backend services private.
    
- Use `reload` instead of `restart` for configuration changes.
    
- Monitor logs and system resources continuously.
    
- Back up and version-control configuration files.
    
- Test changes in a staging environment before production whenever possible.

# Interview Questions

### 1. Why should you use `reload` instead of `restart`?

`reload` applies configuration changes while allowing existing connections to continue, minimizing user disruption.

---

### 2. Why should backend services listen on `localhost`?

It prevents direct public access. Nginx becomes the only public-facing service, providing a controlled entry point.

---

### 3. What does `server_tokens off;` do?

It hides the detailed Nginx version number from error pages and response headers, reducing information disclosure.

---

### 4. Why are security headers important?

They instruct browsers to enforce additional security policies, helping mitigate attacks such as clickjacking, MIME sniffing, and some forms of content injection.

---

### 5. What should you verify immediately after deployment?

- Application availability
    
- API functionality
    
- HTTPS and certificates
    
- Logs for errors
    
- Resource usage
    
- Health endpoints
