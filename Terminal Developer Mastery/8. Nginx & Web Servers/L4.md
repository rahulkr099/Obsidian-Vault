# The Main Configuration File

The heart of Nginx is:

```text
/etc/nginx/nginx.conf
```

Everything starts here.

Think of it like the **main()** function in a C/C++ program or the **app.js** file in an Express application.

```
nginx.conf
      │
      ├── Load modules
      ├── Global settings
      ├── Events
      ├── HTTP
      │      ├── Server
      │      │      ├── Location
      │      │      └── Location
      │      └── Server
      └── Other included files
```

---

# View the Configuration

Open it:

```bash
sudo nano /etc/nginx/nginx.conf
```

Or using Neovim:

```bash
sudo nvim /etc/nginx/nginx.conf
```

You'll see something similar to:

```nginx
user www-data;

worker_processes auto;

pid /run/nginx.pid;

events {

    worker_connections 1024;

}

http {

    include mime.types;

    default_type application/octet-stream;

}
```

Don't worry if everything looks confusing.

We'll understand every part.

---

# Configuration is Hierarchical

Nginx configuration looks like a tree.

```
Main Context

│

├── Events

│

└── HTTP

      │

      ├── Server

      │      │

      │      ├── Location

      │      └── Location

      │

      └── Server
```

Every child inherits settings from its parent unless overridden.

---

# What is a Context?

A **context** is a section enclosed by `{}` that groups related configuration directives.

Example:

```nginx
http {

}
```

Everything inside belongs to the HTTP context.

Another example:

```nginx
server {

}
```

A `server` block represents one website or virtual host.

---

# Main Context

The main context is everything **outside** any braces.

Example:

```nginx
user www-data;

worker_processes auto;

pid /run/nginx.pid;
```

These are global settings.

---

# Events Context

```nginx
events {

    worker_connections 1024;

}
```

This controls how Nginx handles connections.

Typical settings:

- Worker connections
    
- Event handling method
    

---

# HTTP Context

This is where most web server configuration lives.

Example:

```nginx
http {

}
```

Inside it, you'll define:

- Websites
    
- Reverse proxies
    
- Caching
    
- Compression
    
- Logging
    
- MIME types
    

---

# Server Context

Inside the HTTP context:

```nginx
http {

    server {

    }

}
```

Each `server` block usually represents a single website.

Example:

```text
example.com

↓

Server Block 1
```

```
blog.example.com

↓

Server Block 2
```

---

# Location Context

Inside a server:

```nginx
server {

    location / {

    }

}
```

A `location` block tells Nginx what to do for a specific URL or path.

Example:

```
/

↓

Homepage

/images/

↓

Image directory

/api/

↓

Backend API
```

We'll explore location matching in detail in Lesson 7.

---

# Context Hierarchy

```
Main

↓

HTTP

↓

Server

↓

Location
```

Settings flow from top to bottom.

Example:

```
HTTP

↓

Server

↓

Location
```

A setting defined in `http` is inherited by `server` and `location` unless overridden.

---

# What is a Directive?

A **directive** is a single configuration instruction.

Example:

```nginx
worker_processes auto;
```

This is one directive.

Another:

```nginx
listen 80;
```

Another:

```nginx
server_name example.com;
```

A directive always ends with a semicolon (`;`), unless it starts a block.

---

# Simple Directive

```nginx
client_max_body_size 20M;
```

Meaning:

Maximum upload size = 20 MB.

---

# Block Directive

Some directives open blocks:

```nginx
server {

}
```

Or:

```nginx
location / {

}
```

These contain additional directives inside them.

---

# Configuration Blocks

Imagine a website:

```text
example.com
```

Configuration:

```nginx
server {

    listen 80;

    server_name example.com;

    location / {

        root /var/www/html;

    }

}
```

Breakdown:

- `server` defines the website.
    
- `listen` defines the port.
    
- `server_name` defines the hostname.
    
- `location /` handles the root URL.
    
- `root` specifies the directory containing website files.
    

---

# Include Files

Large configurations become difficult to manage.

Instead of putting everything into one file, Nginx allows:

```nginx
include /etc/nginx/conf.d/*.conf;
```

This loads every `.conf` file in that directory.

---

# Why Use Include Files?

Instead of:

```
1000-line nginx.conf
```

You can organize:

```
nginx.conf

↓

proxy.conf

↓

gzip.conf

↓

security.conf

↓

cache.conf
```

Much cleaner.

---

# Example

Main file:

```nginx
http {

    include conf.d/*.conf;

}
```

Folder:

```
conf.d/

gzip.conf

proxy.conf

cache.conf
```

Each file contains related configuration.

---

# sites-available and sites-enabled

Ubuntu and Linux Mint organize websites using two directories.

```
sites-available/

↓

Contains every website configuration.
```

```
sites-enabled/

↓

Contains only enabled websites.
```

Enable a website:

```bash
sudo ln -s \
/etc/nginx/sites-available/myapp \
/etc/nginx/sites-enabled/
```

Disable:

```bash
sudo rm /etc/nginx/sites-enabled/myapp
```

No need to edit `nginx.conf`.

---

# Configuration Loading Order

When Nginx starts:

```
Read nginx.conf

↓

Read included files

↓

Read server blocks

↓

Read location blocks

↓

Ready to serve requests
```

If any configuration contains a syntax error, Nginx refuses to start or reload.

---

# Configuration Hierarchy Example

```nginx
http {

    client_max_body_size 10M;

    server {

        location /upload {

            client_max_body_size 100M;

        }

    }

}
```

Requests to `/upload` can upload up to **100 MB**, while other locations inherit the **10 MB** limit.

---

# Comments

Comments begin with `#`.

```nginx
# Reverse proxy

server {

}
```

Use comments to explain why a setting exists.

---

# Indentation

Good:

```nginx
server {

    location / {

        root /var/www/html;

    }

}
```

Bad:

```nginx
server{
location /{
root /var/www/html;
}
}
```

Indentation isn't required, but it makes configurations much easier to read.

---

# Always Test

Never edit and reload immediately.

Instead:

```bash
sudo nginx -t
```

If successful:

```text
syntax is ok

test is successful
```

Then reload:

```bash
sudo systemctl reload nginx
```

# Common Mistakes

## Missing Semicolon

Wrong:

```nginx
listen 80
```

Correct:

```nginx
listen 80;
```

---

## Wrong Nesting

Wrong:

```nginx
location / {

}

server {

}
```

A `server` block cannot be placed inside a `location` block.

Correct:

```nginx
server {

    location / {

    }

}
```

---

## Forgetting Reload

Editing the file doesn't change the running server.

After testing:

```bash
sudo systemctl reload nginx
```

---

# Production Best Practices

- Keep `nginx.conf` small.
    
- Use include files for modularity.
    
- One server block per website.
    
- Add comments for complex configurations.
    
- Use consistent indentation.
    
- Test with `nginx -t`.
    
- Reload instead of restarting whenever possible.
    
- Store reusable settings in `snippets/`.

# Interview Questions

### 1. What is the main Nginx configuration file?

`/etc/nginx/nginx.conf`

---

### 2. What is a context?

A context is a block enclosed by `{}` that groups related configuration directives, such as `http`, `server`, or `location`.

---

### 3. What is a directive?

A directive is a configuration instruction. Examples include `listen 80;` and `worker_processes auto;`.

---

### 4. What is the purpose of `include`?

It loads additional configuration files, making large Nginx configurations modular and easier to maintain.

---

### 5. Why are `sites-available` and `sites-enabled` used?

They allow you to keep all site configurations in one place while activating only the sites linked in `sites-enabled`, making it easy to enable or disable websites without deleting configuration files.

# Key Takeaways

- `nginx.conf` is the root of the Nginx configuration.
    
- Configuration is hierarchical: **Main → HTTP → Server → Location**.
    
- A **directive** is a single instruction ending with `;`.
    
- A **context** is a block enclosed in `{}` that contains related directives.
    
- `include` helps split configurations into manageable files.
    
- `sites-available` stores site configurations, while `sites-enabled` determines which sites are active.
    
- Always validate changes with `nginx -t` before using `systemctl reload nginx`.
