# 1. What is Observability?

In simple words:

> **Observability is the ability to understand what is happening inside a system by looking at the data it produces.**

Imagine your Node.js backend is running on a Linux server.

A user says:

> "The website is very slow."

You cannot physically see what is happening inside the server.

You need evidence.

For example:

```text
Application Logs
       +
CPU / Memory Metrics
       +
Database Metrics
       +
Request Traces
       ↓
Understand what is happening
```

That ability to understand the internal state of your application from its external outputs is **observability**.

---

# 2. Monitoring vs Observability

These terms are related, but they are not exactly the same.

## Monitoring

Monitoring generally answers:

> **"Is something wrong?"**

For example:

```text
CPU > 90%
Disk > 90%
Memory > 85%
API response time > 2 seconds
Server is DOWN
```

You can create an alert:

```text
🚨 CPU usage is above 90%
```

Monitoring tells you that something is wrong.

---

## Observability

Observability goes deeper.

It asks:

> **"Why is it wrong?"**

For example:

```text
CPU = 97%
       ↓
Node.js process = 92%
       ↓
/api/search receiving huge traffic
       ↓
MongoDB query taking 7 seconds
       ↓
Missing database index
```

Now you've found the **root cause**.

### Simple comparison

|Monitoring|Observability|
|---|---|
|Is something wrong?|Why is it wrong?|
|Predefined problems|Explore unknown problems|
|Alerts|Investigation|
|Metrics focused|Logs + Metrics + Traces|
|Health checking|Understanding system behavior|

A useful way to remember it:

```text
Monitoring
    ↓
Detect

Observability
    ↓
Understand
```

# 3. Why Do We Need Observability?

A local application might look like this:

```text
Browser
   ↓
React
   ↓
Express
   ↓
MongoDB
```

Everything is easy to inspect.

But production might look more like:

```text
                 ┌── React
                 │
Users ── CDN ── Nginx
                 │
                 ▼
            Load Balancer
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      API-1    API-2    API-3
        │        │        │
        └────────┼────────┘
                 ▼
              MongoDB
                 │
                 ▼
              Redis
```

Now problems become harder.

Suppose users report:

> "Login is taking 10 seconds."

Which component is responsible?

Could be:

```text
React
 ↓
Nginx
 ↓
Network
 ↓
Node.js
 ↓
Authentication middleware
 ↓
Redis
 ↓
MongoDB
 ↓
External OAuth API
```

Without observability, you're guessing.

With observability, you can investigate.

# 4. The Three Pillars of Observability

The traditional three pillars are:

```text
             Observability
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
     Logs      Metrics     Traces
```

Let's understand each.

---

# 5. Pillar 1 — Logs 📝

A **log** is a record of something that happened.

Example:

```text
2026-08-15 12:30:21 INFO User login successful userId=123
```

Another:

```text
2026-08-15 12:31:02 ERROR Database connection failed
```

Logs are useful for understanding **events**.

---

## Example Node.js log

```javascript
console.log("User logged in");
```

Better:

```javascript
logger.info({
  userId: user.id,
  requestId: req.id
}, "User logged in");
```

Even better in production:

```json
{
  "level": "info",
  "message": "User logged in",
  "userId": "123",
  "requestId": "abc-123",
  "timestamp": "2026-08-15T12:30:21Z"
}
```

This is called **structured logging**.

We'll learn this properly in Lesson 9.5.

---

# 6. Pillar 2 — Metrics 📊

A metric is a numerical measurement collected over time.

Examples:

```text
CPU usage       → 73%
Memory usage    → 61%
Requests/sec    → 240
Error rate      → 2.4%
Response time   → 320ms
Disk usage      → 78%
```

Metrics are excellent for understanding **system behavior and trends**.

For example:

```text
CPU

100% |             ███
 80% |         ███████
 60% |      ███████████
 40% |   █████████████
 20% |████████████████
     └──────────────────
       Time →
```

You might notice:

> CPU has been increasing continuously for the last 30 minutes.

That is valuable information.

---

# 7. Pillar 3 — Traces 🔗

A trace follows a request through different services.

Imagine this request:

```http
GET /api/orders/123
```

It might travel through:

```text
Browser
   ↓
Nginx
   ↓
Express API
   ↓
Auth middleware
   ↓
Order service
   ↓
MongoDB
   ↓
Redis
```

A trace lets you see how long each step took.

Example:

```text
GET /api/orders/123

Nginx                10ms
Express               5ms
Authentication       20ms
Order Service        15ms
MongoDB              850ms
Redis                  3ms
────────────────────────
Total                903ms
```

Now you immediately know:

> MongoDB is probably the bottleneck.

Without tracing, you might spend hours looking at the wrong component.

---

# 8. Logs vs Metrics vs Traces

Think of them like this:

### Logs

> **What happened?**

```text
Database connection failed.
```

### Metrics

> **How much / how often?**

```text
Database error rate = 8%
```

### Traces

> **Where did the request spend its time?**

```text
MongoDB query = 850ms
```

Together:

```text
Logs
"What happened?"

Metrics
"How often/how much?"

Traces
"Where did it happen?"
```

# 9. A Real Production Example

Imagine your MERN application receives complaints:

> "The website is very slow."

You open Grafana.

You see:

```text
CPU:       42%
Memory:    55%
Disk:      62%
Network:   Normal
Error rate: 1%
```

Nothing looks terrible.

Then you check:

```text
API latency
```

You find:

```text
GET /api/products
Average: 3.8 seconds
```

Now you investigate logs:

```text
Slow MongoDB query
collection=products
duration=3500ms
```

Then you investigate the database.

You discover:

```text
Query:
Product.find({ category: "laptop" })

No index on category
```

Root cause:

```text
Missing database index
        ↓
Slow MongoDB query
        ↓
Slow API
        ↓
Slow website
```

That's observability in action.

# 10. The Four Golden Signals ⭐

Google's SRE practices popularized four important signals for monitoring services.

They are:

```text
Latency
Traffic
Errors
Saturation
```

Remember:

> **LTES**

---

## 10.1 Latency

How long does something take?

Example:

```text
API response time = 240ms
```

But don't only look at averages.

Suppose:

```text
Average latency = 200ms
```

Looks good.

But:

```text
95th percentile = 1.5s
99th percentile = 5s
```

Some users are having a terrible experience.

That's why production systems often monitor:

```text
p50
p95
p99
```

---

# 11. Traffic

Traffic tells you how much demand your system is receiving.

For an API:

```text
Requests/sec = 500
```

For a website:

```text
Requests/minute = 30,000
```

For a database:

```text
Queries/sec = 2,000
```

Traffic helps answer:

> "How much work is the system receiving?"

---

# 12. Errors

Errors tell you how frequently requests are failing.

Example:

```text
Total requests = 10,000

Successful = 9,800
Failed     = 200

Error rate = 2%
```

You might monitor:

```text
HTTP 4xx
HTTP 5xx
Database errors
Timeouts
Connection errors
```

A sudden increase in `5xx` errors is usually something you want to investigate quickly.

---

# 13. Saturation

Saturation tells you how close a resource is to its limit.

Examples:

```text
CPU = 95%
Memory = 92%
Disk = 96%
Database connections = 98%
```

Think:

> **"How full is this resource?"**

For example:

```text
Database connection pool

Used: 98 / 100
```

The database isn't necessarily broken yet.

But you're very close to the limit.

That is saturation.

---

# 14. Golden Signals Example

For your backend:

```text
┌─────────────────────────────┐
│       Node.js API           │
├─────────────────────────────┤
│ Latency    → 240ms          │
│ Traffic    → 350 req/sec    │
│ Errors     → 0.8%           │
│ Saturation → CPU 68%        │
└─────────────────────────────┘
```

This gives you a quick picture of application health.

# 17. Observability vs Debugging

These are also different.

### Debugging

Usually happens after something goes wrong.

```text
Problem
   ↓
Investigate
   ↓
Find bug
   ↓
Fix
```

### Observability

Helps you understand the system continuously.

```text
Collect
   ↓
Observe
   ↓
Detect
   ↓
Investigate
   ↓
Fix
   ↓
Verify
```

Good observability makes debugging **much faster**.

---

# 18. Observability Is Not Just Tools

This is important.

Observability isn't:

> "Install Grafana and Prometheus."

Tools are only part of it.

Real observability requires:

```text
Good instrumentation
       +
Useful logs
       +
Useful metrics
       +
Useful traces
       +
Dashboards
       +
Alerts
       +
Good troubleshooting process
```

For example, an alert saying:

```text
🚨 Something is wrong
```

isn't very useful.

A better alert:

```text
🚨 Production API error rate > 5%

Service: user-api
Environment: production
Error rate: 8.4%
Duration: 10 minutes
Endpoint: POST /api/login
```

Now an engineer can act quickly.

# 🧠 Exercise

Imagine your production Node.js API has this situation:

```text
CPU:       95%
Memory:    72%
Disk:      48%
Requests:  800 req/sec
Errors:    7%
Latency:   4.2 seconds
```

Answer these questions yourself:

### 1. Which Golden Signal indicates increased demand?

### 2. Which Golden Signal indicates failed requests?

### 3. Which Golden Signal indicates resource pressure?

### 4. Which signal tells you users are waiting too long?

### 5. Would you immediately restart the server?

**Think before looking at the answers below.**

---

## ✅ Answers

### 1. Traffic

```text
800 requests/sec
```

indicates the amount of incoming work.

### 2. Errors

```text
7% error rate
```

is a major warning sign.

### 3. Saturation

```text
CPU = 95%
```

indicates resource pressure.

### 4. Latency

```text
4.2 seconds
```

is the request latency.

### 5. No — not immediately.

A restart might temporarily hide the problem.

Instead investigate:

```text
High CPU
   ↓
Which process?
   ↓
Which endpoint?
   ↓
Which operation?
   ↓
Application logs
   ↓
Database queries
   ↓
Root cause
```

**This is a very important production mindset:** don't blindly restart services before understanding the problem.
