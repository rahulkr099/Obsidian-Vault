# 1. What Is a Process?

A **program** is a file containing instructions.

A **process** is a running instance of a program.

For example:

```text
Node.js program
      ↓
node server.js
      ↓
Running process
```

Linux assigns the process an identifier:

```text
PID = Process ID
```

Example:

```text
node server.js
      ↓
PID 4821
```

---

# 2. Program vs Process

Suppose you have:

```bash
node server.js
```

The file:

```text
server.js
```

is the program/code.

When you execute:

```bash
node server.js
```

Linux creates a process.

So:

```text
Program
   ↓
Execution
   ↓
Process
   ↓
PID
```

You can have multiple processes running the same program.

For example:

```text
node server.js → PID 1201
node server.js → PID 1202
node server.js → PID 1203
```

---

# 3. Why Process Monitoring Matters

Imagine users report:

> "The API is very slow."

You check:

```bash
top
```

and discover:

```text
PID     CPU     COMMAND
4821    390%    node
```

Now you know:

> A Node.js process is consuming a large amount of CPU.

But that's only the beginning.

You need to know:

```text
Who started it?
What command started it?
Which application is it?
Who is its parent?
How long has it been running?
What state is it in?
```

That's where process-management tools become useful.

# 4. The PID

A PID uniquely identifies a running process.

Example:

```text
PID
4821
```

You can inspect it:

```bash
ps -p 4821
```

Or:

```bash
ps -p 4821 -f
```

The `-f` gives a more detailed format.

# 5. `ps` — Process Snapshot ⭐⭐⭐⭐⭐

One of the most important commands:

```bash
ps
```

It shows processes associated with your current terminal/session.

Try:

```bash
ps
```

You may see:

```text
PID TTY          TIME CMD
5312 pts/0    00:00:00 zsh
5410 pts/0    00:00:00 ps
```

This is a **snapshot**, unlike `top`, which continuously updates.


Important fields:

```text
USER
PID
%CPU
%MEM
STAT
START
TIME
COMMAND
```

# 11. Parent and Child Processes

Processes can create other processes.

For example:

```text
systemd
   ↓
nginx
   ├── worker
   ├── worker
   └── worker
```

Or:

```text
systemd
   ↓
Node.js
   ↓
worker process
```

The process that creates another process is the **parent**.

The created process is the **child**.

---

# 12. PPID

Suppose:

```text
PID   PPID
4821  1
```

That means:

```text
Process 4821
      ↓
Parent = PID 1
```

On modern Linux systems, PID 1 is normally the system's init system, commonly `systemd`.

---

# 13. Why PPID Matters

Imagine you find:

```text
node
PID 4821
```

You want to know:

> Who started this Node process?

Run:

```bash
ps -o pid,ppid,cmd -p 4821
```

Example:

```text
PID   PPID CMD
4821  1    node /opt/student-api/server.js
```

This suggests the process is directly managed under PID 1's process hierarchy.

If the parent is another process, that tells you something different.

# 14. `pgrep`

Instead of:

```bash
ps aux | grep node
```

you can use:

```bash
pgrep node
```

Example:

```text
4821
5100
```

This means two matching Node-related processes were found.

---

# 15. `pgrep -a`

Use:

```bash
pgrep -a node
```

Now you can see the command:

```text
4821 node /opt/student-api/server.js
5100 node worker.js
```

This is much more useful than only seeing PIDs.

---

# 16. `pgrep -f`

Sometimes you want to match the **full command line**:

```bash
pgrep -af "server.js"
```

This can help locate a specific application.

Example:

```text
4821 node /opt/student-api/server.js
```

Be careful with broad patterns, especially on production systems.

---

# 17. `pidof`

Another useful command:

```bash
pidof node
```

Example:

```text
4821 5100
```

It tells you the PIDs associated with the named executable.

Conceptually:

```text
pgrep
↓
Flexible process searching

pidof
↓
Find PIDs for a program
```

---

# 18. `pgrep` vs `pidof`

|Command|Purpose|
|---|---|
|`pgrep node`|Find processes matching name|
|`pgrep -a node`|Find + show command|
|`pgrep -f server.js`|Match full command|
|`pidof node`|Find PIDs for executable|

For daily Linux work:

```bash
pgrep -a node
```

is particularly useful.

# 22. Process States ⭐⭐⭐⭐⭐

Processes aren't always simply:

```text
running
```

Linux tracks different states.

You'll commonly see:

```text
R
S
D
T
Z
I
```

Let's understand them.

---

# 23. `R` — Running / Runnable

`R` means the process is:

```text
Running
```

or:

```text
Ready to run
```

Example:

```text
R
```

A process doing CPU-intensive work may frequently appear in this state.

---

# 24. `S` — Interruptible Sleep

`S` means the process is sleeping and waiting for an event.

This is completely normal.

For example:

```text
Node.js
waiting for network request
```

might spend much of its time sleeping.

So:

```text
S ≠ problem
```

---

# 25. `D` — Uninterruptible Sleep ⚠️

This is important.

`D` generally means the process is waiting for an operation that cannot currently be interrupted in the normal way, often related to I/O.

For example:

```text
Disk I/O
Network filesystem
Storage
```

A process stuck in `D` state can be a clue to serious I/O problems.

Example:

```text
node   D
```

combined with:

```text
iostat
high await
high I/O utilization
```

could indicate storage-related problems.

---

# 26. `T` — Stopped

`T` means the process is stopped, often due to job control or a signal.

For example:

```text
Ctrl + Z
```

can stop a foreground process.

You might see:

```text
T
```

in its state.

---

# 27. `Z` — Zombie Process ☠️

This is one of the most important concepts in this lesson.

A zombie is a process that has:

> **Finished execution but whose parent hasn't yet collected its exit status.**

The process is already dead.

But its process table entry remains temporarily.

---

# 28. How a Zombie Happens

Imagine:

```text
Parent
  │
  └── Child
```

The child finishes:

```text
Parent
  │
  └── Child → exits
```

But the parent hasn't called the appropriate wait operation.

So:

```text
Parent
  │
  └── Zombie
```

The zombie isn't actively running.

It is essentially waiting for the parent to acknowledge its termination.

---

# 29. How to Find Zombies

Try:

```bash
ps aux | awk '$8 ~ /^Z/'
```

Or:

```bash
ps -eo pid,ppid,state,cmd | grep '^.* Z '
```

The exact formatting can vary.

You can also use:

```bash
ps aux | grep '<defunct>'
```

You may see:

```text
user  5123  0.0  0.0  ...  Z  ... [worker] <defunct>
```

`<defunct>` is commonly associated with zombies.

---

# 30. Are Zombies Dangerous?

One zombie isn't necessarily a crisis.

But a growing number of zombies can indicate:

```text
Parent process bug
Poor child-process management
Broken worker architecture
```

Remember:

> A zombie is already dead.

You don't "kill" a zombie in the normal sense.

The parent needs to reap it.

---

# 31. How Do You Fix Zombies?

First identify the parent.

```bash
ps -o pid,ppid,state,cmd -p <PID>
```

Suppose:

```text
PID   PPID
5123  4800
```

Then:

```text
5123 → zombie
4800 → parent
```

Investigate the parent.

Usually the correct fix is:

```text
Fix/restart parent
```

rather than trying to kill the zombie itself.

---

# 32. Orphan Processes

An **orphan** is different from a zombie.

A process becomes orphaned when its parent exits while the child continues running.

Conceptually:

```text
Parent
  │
  └── Child
```

Parent dies:

```text
Parent ❌
  │
  └── Child
```

The child is then adopted/reparented by another process, traditionally PID 1 or another subreaper depending on the system.

So:

```text
Zombie
→ finished but not reaped

Orphan
→ still running but original parent disappeared
```

Very important distinction.

---

# 33. Process Signals ⭐⭐⭐⭐⭐

Linux controls processes using **signals**.

Common ones:

```text
SIGTERM
SIGKILL
SIGINT
SIGHUP
SIGSTOP
SIGCONT
```

You'll use these during troubleshooting.

---

# 34. `SIGTERM`

Signal:

```text
15
```

Usually:

```bash
kill -TERM <PID>
```

or simply:

```bash
kill <PID>
```

This requests that the process terminate gracefully.

This is generally the first signal you should try when you intentionally need to stop a process.

---

# 35. `SIGKILL`

Signal:

```text
9
```

Command:

```bash
kill -KILL <PID>
```

or:

```bash
kill -9 <PID>
```

This forcefully terminates the process.

The process cannot catch or handle `SIGKILL`.

Use it carefully.

---

# 36. Why `kill -9` Shouldn't Be Your First Move

A beginner often does:

```bash
kill -9 4821
```

immediately.

That's not ideal.

You may prevent the application from:

```text
Closing connections
Flushing data
Cleaning resources
Writing final logs
Gracefully shutting down
```

Better:

```text
SIGTERM
   ↓
Wait
   ↓
Check process
   ↓
SIGKILL only if necessary
```

---

# 37. `SIGINT`

Signal:

```text
2
```

Usually generated by:

```text
Ctrl + C
```

It means roughly:

> Interrupt this process.

For a terminal application:

```bash
node server.js
```

pressing:

```text
Ctrl + C
```

typically sends SIGINT.

---

# 38. `SIGHUP`

Signal:

```text
1
```

Historically associated with terminal hangups.

It can also be used by applications to mean:

> Reload configuration.

But behavior is application-specific.

Never assume `SIGHUP` automatically reloads every application.

---

# 39. `SIGSTOP` and `SIGCONT`

Stop a process:

```bash
kill -STOP <PID>
```

Continue it:

```bash
kill -CONT <PID>
```

These are useful for controlled process testing, but be cautious on production systems.

---

# 40. Graceful Shutdown

A well-designed Node.js application should handle shutdown signals.

For example:

```javascript
process.on("SIGTERM", async () => {
  console.log("SIGTERM received");

  await server.close();

  await mongoose.connection.close();

  process.exit(0);
});
```

The exact implementation should match your application's architecture.

The idea is:

```text
SIGTERM
   ↓
Stop accepting new work
   ↓
Finish active work
   ↓
Close DB connections
   ↓
Close server
   ↓
Exit
```

This is extremely important in production deployments.

A production application might eventually hit:





# 49. Don't Confuse Processes and Threads

A process can contain multiple threads.

Conceptually:

```text
Process
 ├── Thread
 ├── Thread
 ├── Thread
 └── Thread
```

Node.js has an event-driven architecture and can also use worker threads or child processes when needed.

You'll encounter threads more deeply when investigating advanced performance problems.

# 51. Process States in Practice

Here's a useful mental table:

|State|Meaning|Usually concerning?|
|---|---|---|
|`R`|Running/runnable|Not by itself|
|`S`|Interruptible sleep|Usually normal|
|`D`|Uninterruptible sleep|Investigate if persistent|
|`T`|Stopped|Depends|
|`Z`|Zombie|Investigate if accumulating|
|`I`|Idle kernel thread|Usually normal|

Don't panic when you see `S`.

Most normal server processes spend a lot of time sleeping while waiting for events.

# 56. Zombie Investigation

If you discover:

```text
Z
```

don't immediately panic.

First count them:

```bash
ps aux | awk '$8 ~ /^Z/ {count++} END {print count+0}'
```

Then inspect:

```bash
ps -eo pid,ppid,state,cmd | awk '$3=="Z"'
```

Identify the parent:

```text
Zombie PID
   ↓
PPID
   ↓
Parent process
```

Then investigate the parent.

# 57. Why Zombies Matter for Node.js

Node.js applications can create child processes using APIs such as:

```javascript
child_process
```

If child-process lifecycle management is implemented poorly, you can encounter zombie processes.

This becomes more important when your backend uses:

```text
Workers
Background jobs
FFmpeg
Image processing
Shell commands
Child processes
```

Always manage child processes carefully.

---

# 58. Process Monitoring Security

Be careful with:

```bash
ps aux
```

because command lines can sometimes expose sensitive arguments.

For example, a badly designed command might contain:

```text
--password=secret
```

which could become visible to other users with appropriate process visibility.

Better application design:

> **Don't put secrets directly into command-line arguments when safer mechanisms exist.**

This is another connection between observability and security.

# 60. Interview Questions ⭐

### Q1. What is a process?

> A process is a running instance of a program managed by the operating system. Each process normally has a unique process ID (PID).

---

### Q2. What is the difference between PID and PPID?

> PID identifies a process, while PPID identifies its parent process.

---

### Q3. What is a zombie process?

> A zombie is a process that has finished execution but whose parent has not yet collected its exit status. It remains as a process-table entry until it is reaped.

---

### Q4. Can you kill a zombie?

> Not in the normal sense. The zombie has already terminated. The parent process needs to reap it. If necessary, investigating or restarting the parent may resolve the issue.

---

### Q5. What is an orphan process?

> An orphan is a still-running child process whose original parent has exited. It is reparented to an appropriate process, commonly PID 1 or a subreaper.

---

### Q6. What's the difference between SIGTERM and SIGKILL?

> SIGTERM requests graceful termination and can be handled by the application. SIGKILL forcefully terminates the process and cannot be caught or handled.

---

### Q7. Why shouldn't `kill -9` always be used?

> Because it doesn't allow the application to perform graceful shutdown tasks such as closing connections, flushing data, or cleaning resources.

```text
# Inspect useful fields

# Process tree
pstree -p

# Monitor one process
top -p <PID>

# Open files/resources
lsof -p <PID>

# Process file descriptors
ls -l /proc/<PID>/fd

# Graceful termination
kill <PID>

# Force termination — use carefully
kill -9 <PID>
```

# 62. 🔥 Your Production Process Debugging Workflow

Memorize this workflow:

```text
             Something is wrong
                     │
                     ▼
              Identify process
                     │
                pgrep / ps
                     │
                     ▼
               Check resource
                     │
              top / htop / btop
                     │
                     ▼
               Check process
                     │
               PID + PPID + STAT
                     │
                     ▼
              Check process tree
                     │
                  pstree
                     │
                     ▼
               Check application
                     │
             journalctl / logs
                     │
                     ▼
               Check system
                     │
          vmstat / iostat / sar
                     │
                     ▼
                Root cause
                     │
                     ▼
            Take safe action
```

This is a much stronger approach than:

```text
Server slow
   ↓
kill -9 everything
```

### Question 3

### Question 4

Should you run:

```bash

```

?

## ✅ Answers

### 1

```text
5205
```

is a **zombie process**.

### 2

Its parent is:

```text
5200
```

because:

```text
PPID = 5200
```

### 3

No.

It's already terminated.

### 4

No.

The correct investigation is:

```text
5205 zombie
   ↓
parent = 5200
   ↓
investigate Node.js parent
   ↓
understand why child wasn't reaped
```

# 64. Another Challenge 🧠

You run:

```bash
ps aux --sort=-%cpu | head
```

and see:

```text
node  4821  385.0  12.5
```

Your server has:

```text
8 logical CPUs
```

Is `385% CPU` necessarily impossible?

### ❌ No.

A process can consume multiple CPU cores.

Approximately:

```text
385% ≈ 3.85 logical CPUs
```

So the process is using a substantial amount of the server's CPU capacity.
