# Lesson 9.11 — Disk Monitoring 💾🔍

**Module:** 9 — Observability  
**Lesson:** 9.11  
**Level:** Intermediate → Advanced

## 🎯 Goal

In this lesson, you'll learn how to monitor and troubleshoot Linux storage.

You'll learn:

- `df`
    
- `du`
    
- Filesystems
    
- Mount points
    
- Disk capacity
    
- Inodes
    
- Disk I/O
    
- `iostat`
    
- Large files
    
- Log files filling disks
    
- Docker storage
    
- Deleted-but-open files
    
- Read-only filesystems
    
- Disk-full incidents
    
- Storage troubleshooting
    

The most important idea is:

> **A disk problem is not always "the disk is full."**

You can have:

```text
Disk capacity problem
Inode problem
I/O performance problem
Filesystem problem
Application storage problem
```

Let's learn how to distinguish them.

---

# 1. Why Disk Monitoring Matters ⭐⭐⭐⭐⭐

Imagine your Node.js API suddenly starts returning:

```http
500 Internal Server Error
```

Your CPU:

```text
30%
```

Memory:

```text
55%
```

Network:

```text
Normal
```

Everything looks fine.

But:

```bash
df -h
```

shows:

```text
/dev/nvme0n1p2   100G   100G     0  100%
```

💥 The filesystem is full.

Your application may now fail to:

```text
Write logs
Create temporary files
Upload files
Create database files
Create sockets
Write caches
Create new files
```

This is why disk monitoring is critical.

---

# 2. Disk Monitoring Has Multiple Dimensions

Think of storage like this:

```text
                 Storage Health
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
   Capacity          Inodes          I/O
       │               │               │
     df/du          df -i          iostat
```

You need to understand all three.

---

# 3. Capacity

Capacity answers:

> **How much storage space is being used?**

Example:

```text
100 GB total
80 GB used
20 GB available
```

You investigate this with:

```bash
df -h
```

---

# 4. Inodes

Inodes answer:

> **How many files/directories can this filesystem still create?**

You can have:

```text
Disk space available
```

but:

```text
No inodes available
```

Then you may still be unable to create new files.

This is one of the most interesting Linux storage problems.

---

# 5. I/O Performance

I/O answers:

> **How quickly can the storage system handle reads and writes?**

For example:

```text
Disk capacity:
40%

But:

I/O latency:
300ms
```

Your disk isn't full.

But it may be **slow or overloaded**.

Use:

```bash
iostat -xz
```

---

# 6. The Three Questions

When troubleshooting storage, ask:

```text
1. Is the filesystem full?
        ↓
      df -h

2. Are we running out of inodes?
        ↓
      df -i

3. Is storage performance poor?
        ↓
      iostat
```

Then:

```text
Where is the space being used?
        ↓
      du
```

Memorize this.

---

# 7. `df` — Filesystem Usage ⭐⭐⭐⭐⭐

Start with:

```bash
df -h
```

Example:

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p2  100G   72G   28G  72% /
tmpfs           3.8G  100M  3.7G   3% /run
/dev/sdb1       500G  220G  280G  44% /data
```

This tells you:

```text
Filesystem
Total size
Used
Available
Percentage
Mount point
```

---

# 8. What Is a Filesystem?

A filesystem organizes data on a storage device.

Common Linux filesystems include:

```text
ext4
XFS
Btrfs
```

Your physical disk might be:

```text
/dev/nvme0n1
```

with a partition:

```text
/dev/nvme0n1p2
```

formatted with a filesystem and mounted at:

```text
/
```

Conceptually:

```text
Physical Disk
      ↓
Partition
      ↓
Filesystem
      ↓
Mount point
      ↓
Directory tree
```

---

# 9. What Is a Mount Point?

A mount point is where a filesystem becomes accessible inside the Linux directory tree.

For example:

```text
/              → root filesystem
/home          → user data
/var           → variable application/system data
/mnt/data      → additional storage
```

Example:

```text
/dev/sdb1 → /data
```

means:

> `/dev/sdb1` is mounted at `/data`.

---

# 10. Why Mount Points Matter

Suppose you have:

```text
/         → 100 GB
/data     → 500 GB
```

If `/data` is a separate filesystem:

```text
/data/myfile
```

uses the `/data` filesystem.

It doesn't consume the root filesystem's capacity.

This becomes important when troubleshooting:

```text
"/ is full"
```

while:

```text
/data has plenty of space
```

---

# 11. `df -h` vs `du -h`

This distinction is extremely important.

### `df`

```bash
df -h
```

Answers:

> How full is the filesystem?

### `du`

```bash
du -h
```

Answers:

> How much space are files/directories consuming?

So:

```text
df
 ↓
Filesystem perspective

du
 ↓
Directory/file perspective
```

---

# 12. `du`

Try:

```bash
du -sh ~
```

Example:

```text
id="m9w4k2"
8.5G    /home/rahul
```

Meaning:

> Your home directory is using approximately 8.5 GB.

---

# 13. Find Large Directories

A useful command:

```bash
sudo du -xh --max-depth=1 / 2>/dev/null
```

Example:

```text
/var       25G
/home      18G
/usr       12G
/opt        8G
```

Now you know where to investigate.

---

# 14. Sort Directory Sizes

You can combine `du` with `sort`:

```bash
sudo du -xh --max-depth=1 / 2>/dev/null | sort -h
```

Now the smallest directories appear first and the largest near the bottom.

For descending order:

```bash
sudo du -xh --max-depth=1 / 2>/dev/null | sort -hr
```

This is an excellent command to remember.

---

# 15. Find Large Files

Suppose:

```text
/var
```

is huge.

You can investigate:

```bash
sudo du -xh --max-depth=1 /var 2>/dev/null | sort -hr
```

Maybe:

```text
/var/log → 18G
/var/lib → 5G
```

Then:

```bash
sudo du -xh --max-depth=1 /var/log 2>/dev/null | sort -hr
```

You might discover:

```text
/var/log/my-api → 15G
```

Now you've found the likely cause.

---

# 16. `find` for Large Files

Another powerful command:

```bash
sudo find /var -type f -size +1G -ls
```

This searches for files larger than:

```text
1 GB
```

You can change it:

```bash
-size +500M
```

or:

```bash
-size +100M
```

Very useful during disk incidents.

---

# 17. Be Careful With `find /`

This:

```bash
sudo find / -type f -size +1G
```

can be expensive on a large server.

It may:

```text
Take time
Scan many filesystems
Produce lots of output
```

Start with the suspicious filesystem/directory:

```bash
sudo find /var -type f -size +1G -ls
```

Better targeted troubleshooting.

---

# 18. Inodes ⭐⭐⭐⭐⭐

Now let's discuss something beginners often miss.

Run:

```bash
df -i
```

Example:

```text
Filesystem       Inodes   IUsed   IFree IUse% Mounted on
/dev/nvme0n1p2   6.5M     6.5M       0  100% /
```

This means:

```text
Disk space may still exist
```

but:

```text
No free inodes
```

You may be unable to create new files.

---

# 19. What Is an Inode?

An inode stores filesystem metadata about a file.

Conceptually:

```text
File
 │
 ├── Metadata
 │    ├── owner
 │    ├── permissions
 │    ├── timestamps
 │    └── location information
 │
 └── Data blocks
```

The inode is not the file's actual content.

It contains information needed to manage the file.

---

# 20. Too Many Small Files

Inode exhaustion often happens because of **huge numbers of small files**.

Imagine:

```text
10 GB available
```

but a directory contains:

```text
10 million tiny files
```

You can run out of inodes before running out of disk space.

Examples:

```text
Temporary files
Cache files
Mail queues
Application-generated files
Session files
Container layers
```

---

# 21. Finding Directories With Many Files

Suppose:

```bash
df -i
```

shows:

```text
IUse% = 100%
```

Now you need to find directories containing enormous numbers of files.

For a targeted directory:

```bash
find /var -xdev -type f | wc -l
```

You can inspect suspicious subdirectories individually.

Be cautious with very large trees because scanning millions of files can itself be expensive.

---

# 22. Capacity vs Inodes

Remember:

### Problem A

```text
Disk:
100%
```

Solution:

```text
Find large files/directories
```

### Problem B

```text
Inodes:
100%
```

Solution:

```text
Find directories containing huge numbers of files
```

They are different problems.

# 23. Disk I/O

Now let's talk about performance.

Your filesystem could show:

```text
Use% = 40%
```

and still be slow.

Why?

Because:

```text
Storage capacity
      ≠
Storage performance
```

You need to investigate I/O.

```text

```

You learned this in Lesson 9.9.

# 25. Disk I/O Bottleneck Example

Suppose:

```text
Filesystem:
40% full

But:

await:
300ms

%util:
98%
```

Your problem isn't capacity.

Your problem is:

```text
Storage performance
```

Possible causes:

```text
Heavy database workload
Backup process
Large file operations
Slow underlying storage
High concurrent I/O
```

---

# 26. Read vs Write

Storage workload can be:

```text
Reads
Writes
```

For example:

```text
Reads:
500 MB/s

Writes:
20 MB/s
```

This suggests a read-heavy workload.

Or:

```text
Reads:
20 MB/s

Writes:
500 MB/s
```

This is write-heavy.

Your investigation should consider what your application normally does.

---

# 27. Database Storage

Databases can generate significant I/O.

For example:

```text
Node.js
   ↓
MongoDB
   ↓
Disk
```

A slow storage subsystem can cause:

```text
Database latency ↑
       ↓
API latency ↑
       ↓
Users experience slow requests
```

This is why disk monitoring is also application monitoring.

---

# 28. Logs Are a Common Disk Killer 🚨

Suppose your Node.js application produces:

```text
500 MB logs/day
```

After:

```text
30 days
```

that's roughly:

```text
15 GB
```

If you don't rotate/compress/delete logs:

```text
Disk usage
    ↑
    ↑
    ↑
100%
```

This connects directly to Lesson 9.4.

---

# 29. Check `/var/log`

Run:

```bash
sudo du -xh --max-depth=1 /var/log 2>/dev/null | sort -hr
```

You may find:

```text
/var/log/journal → 4G
/var/log/nginx   → 3G
/var/log/my-api  → 12G
```

Now you know where to investigate.

Don't blindly delete logs from a running production system.

Use your configured rotation/retention strategy.

# 31. Docker Images

Old images can accumulate:

```text
image:v1
image:v2
image:v3
image:v4
...
```

Each can consume storage.

During CI/CD, this can become a problem.

But:

> **Don't run aggressive Docker cleanup commands blindly on production servers.**

Unused images may be intentionally retained for rollback.

---

# 32. Docker Volumes

Volumes can contain:

```text
Database data
Uploaded files
Application state
```

Never blindly delete volumes.

For example:

```bash
docker system prune --volumes
```

can be dangerous because persistent data may be removed if it's considered unused.

Always inspect before cleanup.

---

# 33. Deleted Files Still Using Disk 🚨

Here's a fascinating Linux problem.

Suppose a process has:

```text
/var/log/app.log
```

open.

You delete the file:

```bash
rm /var/log/app.log
```

You might expect disk space to immediately return.

But the application still has the file open.

The filesystem can keep the underlying blocks allocated until the process closes the file descriptor.

---

# 34. Find Deleted-But-Open Files

Use:

```bash
sudo lsof +L1
```

You may see:

```text
node 4821 ... /var/log/app.log (deleted)
```

This means:

```text
File name → deleted
File data → still held by process
```

This can explain a confusing situation:

```text
du says:
not much space

df says:
disk still full
```

---

# 35. Why `df` and `du` Can Disagree

This is a classic troubleshooting situation.

Suppose:

```text
df -h
→ 95% used
```

but:

```text
du -sh /
→ much lower
```

One possible cause:

```text
Deleted-but-open files
```

Investigate:

```bash
sudo lsof +L1
```

This is an excellent production troubleshooting technique.

---

# 36. Read-Only Filesystem

Another possible problem:

```text
Filesystem mounted read-only
```

Your application may fail with errors like:

```text
EROFS
Read-only file system
```

Check mount information:

```bash
findmnt
```

or:

```bash
mount
```

You can investigate kernel logs:

```bash
journalctl -k
```

A filesystem becoming read-only can be a serious storage/filesystem issue.

---

# 37. Check Mounts

Run:

```bash
findmnt
```

You may see:

```text
TARGET   SOURCE          FSTYPE
/        /dev/nvme0n1p2  ext4
/home    /dev/nvme0n1p3  ext4
/data    /dev/sdb1       xfs
```

This gives you a clear view of:

```text
Mount point
Device
Filesystem type
```

---

# 38. Check Filesystem Type

You can use:

```bash
df -T
```

Example:

```text
Filesystem      Type  Size Used Avail Use%
/dev/nvme0n1p2  ext4  100G 72G   28G  72%
```

Now you know:

```text
Filesystem type = ext4
```

---

# 39. `lsblk`

Another extremely useful storage command:

```bash
lsblk
```

Example:

```text
NAME        SIZE TYPE MOUNTPOINTS
nvme0n1     500G disk
├─nvme0n1p1  1G part /boot/efi
└─nvme0n1p2 499G part /
sdb         1T   disk
└─sdb1      1T   part /data
```

This helps you understand the physical storage layout.

---

# 40. `lsblk -f`

Try:

```bash
lsblk -f
```

This adds:

```text
Filesystem
UUID
Mount point
```

Very useful when diagnosing storage configuration.

---

# 41. Disk Health vs Disk Usage

Another important distinction:

```text
Disk usage
```

asks:

> Is the filesystem full?

Whereas:

```text
Disk health
```

asks:

> Is the physical storage device healthy?

For physical disks, tools such as:

```text
smartctl
```

can be used when supported.

For example:

```bash
sudo smartctl -a /dev/sda
```

However, on cloud VMs, you often don't have direct access to the underlying physical device's SMART data.

---

# 42. Don't Run `fsck` Randomly

You may hear:

```bash
fsck
```

when talking about filesystem problems.

Important:

> **Do not casually run filesystem repair tools on a mounted production filesystem.**

Filesystem repair can be disruptive and should be performed according to the filesystem and operational procedure.

First gather evidence.

# 43. Disk Monitoring Workflow ⭐⭐⭐⭐⭐

When the application can't write data:

### Step 1

```bash
df -h
```

Ask:

```text
Is the filesystem full?
```

---

### Step 2

```bash
df -i
```

Ask:

```text
Are inodes exhausted?
```

---

### Step 3

If capacity is high:

```bash
sudo du -xh --max-depth=1 / 2>/dev/null | sort -hr
```

Ask:

```text
Where is the space?
```

---

### Step 4

Investigate suspicious directories:

```bash
sudo du -xh --max-depth=1 /var 2>/dev/null | sort -hr
```

---

### Step 5

Find huge files:

```bash
sudo find /var -type f -size +500M -ls
```

---

### Step 6

Check I/O:

```bash
iostat -xz 2
```

---

### Step 7

If `df` and `du` don't make sense:

```bash
sudo lsof +L1
```

---

### Step 8

Check mounts:

```bash
findmnt
```

This workflow covers a huge percentage of common Linux storage incidents.

# 51. Storage Retention Strategy

A production system should have a storage lifecycle.

For logs:

```text
Current logs
    ↓
Rotate
    ↓
Compress
    ↓
Retain
    ↓
Delete/archive
```

For backups:

```text
Recent backups
    ↓
Older backups
    ↓
Archive
    ↓
Delete according to policy
```

Without retention policies:

```text
Storage usage
      ↑
      ↑
      ↑
```

eventually becomes an incident.

---

# 52. Don't Just Delete Random Files

During a disk emergency, someone might say:

```bash
sudo rm -rf /var/log/*
```

🚨 Don't do this blindly.

You might:

```text
Destroy evidence
Delete important logs
Break applications
Remove files still required
Create security/compliance issues
```

First identify:

```text
What is consuming space?
Why?
Can it be safely rotated?
Can it be archived?
```

---

# 53. Emergency Disk Response

If a production filesystem is at:

```text
99–100%
```

your immediate priority is:

```text
1. Confirm the affected filesystem
2. Identify what is consuming space
3. Prevent further growth
4. Safely reclaim space
5. Restore application operation
6. Investigate root cause
7. Add prevention
```

Don't just delete random data.

# 54. Monitoring Thresholds

A reasonable starting point might be:

```text

→ Watch

Disk > 80%
→ Warning

Disk > 90%
→ High priority

Disk > 95%
→ Critical
```

But these are only starting points.

A server with predictable daily growth should use thresholds based on:

```text
Growth rate
Available capacity
Time to exhaustion
Application requirements
```

# 60. The Production Decision Tree ⭐⭐⭐⭐⭐

When an application can't write to disk:

```text
             Can't write data
                    │
                    ▼
                 df -h
```

# 62. 🧠 Challenge 2

You see:

```text
df -h
→ 30% used

df -i
→ 100% used
```

What's wrong?

### Answer:

You're experiencing **inode exhaustion**, probably due to a huge number of files.

Disk capacity still exists, but the filesystem has run out of inode entries.

# 65. Interview Questions ⭐

### Q1. What's the difference between `df` and `du`?

> `df` reports filesystem-level space usage, while `du` estimates the disk usage of files and directories.

---

### Q2. Can a filesystem run out of space even when `df -h` shows free space?

> Yes. It can run out of inodes, preventing new files from being created even though data blocks remain available.

---

### Q3. What causes inode exhaustion?

> Usually a very large number of files, especially many small files such as temporary files, caches, session files, or application-generated files.

---

### Q4. Why can `df` and `du` show different values?

> One possible reason is deleted files that are still open by running processes. The filesystem continues to hold their storage until those processes close the file descriptors.

---

### Q5. How do you investigate a full filesystem?

A good answer:

```text
df -h
   ↓
Identify full filesystem
   ↓
du
   ↓
Find large directories
   ↓
find
   ↓
Find large files
   ↓
df -i
   ↓
Check inode usage
   ↓
lsof +L1
   ↓
Check deleted-open files
```
