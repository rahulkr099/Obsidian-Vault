# Lesson 9.12 — Network Monitoring 🌐🔍

**Module:** 9 — Observability  
**Lesson:** 9.12  
**Level:** Intermediate → Advanced

## 🎯 Goal

This is the final lesson of **Part 3 — Monitoring**.

Today you'll learn how to investigate Linux network problems using:

```text
ss
ip
iftop
nload
tcpdump
```

You'll learn to answer:

- Is the network interface working?
    
- What IP addresses does the server have?
    
- Which ports are listening?
    
- Which processes are accepting connections?
    
- How many connections exist?
    
- Is traffic increasing?
    
- Is a particular connection causing problems?
    
- Is the problem DNS, TCP, Nginx, Node.js, or the network?
    
- How do you capture packets for deeper investigation?
    

---

# 1. Why Network Monitoring Matters ⭐⭐⭐⭐⭐

Imagine your MERN application looks like this:

```text
                    Internet
                       │
                       ▼
                    Nginx
                       │
                       ▼
                  Node.js API
                       │
                       ▼
                    MongoDB
```

Users report:

> "The website is not loading."

You check:

```text
CPU → 20%
RAM → 40%
Disk → 50%
```

Everything looks healthy.

The problem might be:

```text
DNS
   ↓
Network interface
   ↓
Firewall
   ↓
Port
   ↓
Nginx
   ↓
Node.js
   ↓
Database connection
```

Network observability helps you find **where the request is actually failing**.

---

# 2. Network Monitoring Has Layers

Think about troubleshooting from the bottom upward:

```text
┌──────────────────────────────┐
│ Application                  │
│ Node.js / Nginx              │
├──────────────────────────────┤
│ TCP / UDP                    │
├──────────────────────────────┤
│ IP                           │
├──────────────────────────────┤
│ Network Interface            │
├──────────────────────────────┤
│ Physical / Virtual Network   │
└──────────────────────────────┘
```

Different commands operate at different layers.

|Command|Main purpose|
|---|---|
|`ip`|Interfaces, IPs, routes|
|`ss`|TCP/UDP sockets and connections|
|`nload`|Network traffic overview|
|`iftop`|Traffic by connection|
|`tcpdump`|Packet-level investigation|

---

# 3. `ip` — Your Main Network Command ⭐⭐⭐⭐⭐

Modern Linux uses:

```bash
ip
```

instead of older tools such as:

```text
ifconfig
route
```

You should become comfortable with:

```bash
ip addr
ip link
ip route
```

---

# 4. `ip addr`

Run:

```bash
ip addr
```

or:

```bash
ip a
```

You'll see network interfaces.

Example:

```text
2: eth0:
    inet 192.168.1.20/24
    inet6 ...
```

Important information:

```text
Interface name
IPv4 address
IPv6 address
Subnet
Interface state
```

---

# 5. Understanding a Network Interface

An interface is essentially Linux's connection point to a network.

Common names include:

```text
eth0
ens33
enp3s0
wlan0
wlp2s0
lo
```

Modern Linux systems often use predictable interface names such as:

```text
enp3s0
wlp2s0
```

Your actual names will depend on your hardware/environment.

---

# 6. The `lo` Interface

You will usually see:

```text
lo
```

This is the **loopback interface**.

Its common address is:

```text
127.0.0.1
```

It represents:

> This machine talking to itself.

For example:

```text
Node.js → 127.0.0.1:3000
```

means the connection stays on the same machine.

---

# 7. `ip link`

Run:

```bash
ip link
```

This focuses on interface state.

Example:

```text
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP>
```

Important:

```text
UP
LOWER_UP
```

generally indicate the interface is operational at the relevant network/link layers.

---

# 8. Check One Interface

For example:

```bash
ip addr show eth0
```

If your interface is called something else:

```bash
ip addr show wlp2s0
```

Find your actual interface using:

```bash
ip link
```

first.

---

# 9. `ip route` ⭐⭐⭐⭐⭐

Run:

```bash
ip route
```

Example:

```text
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link
```

This tells you about routing.

The important line:

```text
default via 192.168.1.1
```

means:

> Traffic destined for networks without a more specific route goes through this gateway.

---

# 10. Why Routing Matters

Suppose:

```text
Internet
   ↓
Server
```

but the server has no valid default route.

The interface may be:

```text
UP
```

and the IP address may look correct.

But external communication can still fail.

So:

```text
ip addr
```

and:

```text
ip route
```

are both important.

---

# 11. Network Troubleshooting Basics

Start with:

```bash
ip addr
```

Then:

```bash
ip route
```

Then test connectivity.

For example:

```bash
ping -c 4 1.1.1.1
```

If that works, test DNS:

```bash
ping -c 4 google.com
```

This can help distinguish:

```text
Network connectivity
```

from:

```text
DNS resolution
```

Note: ICMP may be blocked, so a failed ping doesn't always prove the network is broken.

# 12. `ss` — Socket Statistics ⭐⭐⭐⭐⭐

Now we reach one of the most important commands:

```bash
ss
```

`ss` is used to inspect:

```text
TCP
UDP
Listening ports
Connections
Sockets
```

Try:

```bash
ss
```

---

# 13. Show Listening Ports

One of the commands you should memorize:

```bash
ss -lnt
```

Meaning:

```text
-l → listening
-n → numeric
-t → TCP
```

Example:

```text
State   Local Address:Port
LISTEN  0.0.0.0:80
LISTEN  0.0.0.0:443
LISTEN  127.0.0.1:3000
```

Now you can see:

```text
Nginx → 80
Nginx → 443
Node.js → 3000
```

---

# 14. Why `-n` Matters

Without:

```bash
-n
```

Linux may try to resolve addresses or service names.

For troubleshooting, numeric output is often faster and clearer.

So:

```bash
ss -lnt
```

is an excellent default.

---

# 15. Show Processes

Use:

```bash
sudo ss -lntp
```

The `p` means:

> Show process information.

Example:

```text
LISTEN 0 511 0.0.0.0:80  0.0.0.0:* users:(("nginx",pid=1200))
LISTEN 0 511 127.0.0.1:3000 users:(("node",pid=4821))
```

Now you can connect:

```text
Port
 ↓
Process
 ↓
PID
```

This is extremely useful.

---

# 16. Find Port 3000

Suppose your Node.js API should listen on:

```text
3000
```

Check:

```bash
sudo ss -lntp | grep :3000
```

If you get:

```text
LISTEN ... 127.0.0.1:3000 ... node
```

the application is listening.

If you get nothing:

```text
No listener
```

your Node.js service may not be running or may be listening on another port/address.

---

# 17. `0.0.0.0` vs `127.0.0.1` ⚠️

This is extremely important for backend development.

Suppose Node.js listens on:

```text
127.0.0.1:3000
```

It accepts connections only through the local machine's loopback interface.

Nginx on the same server can access it.

But external clients cannot directly connect to it through the server's network interface.

---

If it listens on:

```text
0.0.0.0:3000
```

it generally means:

> Listen on all IPv4 interfaces.

This makes the port potentially reachable externally, depending on firewall/security rules.

---

# 18. Typical Production Architecture

A safer common architecture is:

```text
Internet
   │
   ▼
Nginx :443
   │
   ▼
Node.js 127.0.0.1:3000
```

Instead of:

```text
Internet
   │
   ▼
Node.js :3000
```

Why?

Nginx can handle:

```text
TLS
Reverse proxy
Rate limiting
Headers
Static files
Connection handling
```

while Node.js remains behind it.

# 19. TCP Connections

Run:

```bash
ss -tn
```

You may see:

```text
State       Local Address       Peer Address
ESTAB       192.168.1.20:443   10.0.0.5:52142
ESTAB       192.168.1.20:443   10.0.0.6:52150
```

This shows active TCP connections.

---

# 20. TCP States

You'll encounter states such as:

```text
LISTEN
ESTABLISHED
TIME-WAIT
CLOSE-WAIT
SYN-SENT
SYN-RECV
FIN-WAIT-1
FIN-WAIT-2
```

The most important initially:

```text
LISTEN
ESTABLISHED
TIME-WAIT
CLOSE-WAIT
SYN-SENT
SYN-RECV
```

---

# 21. `LISTEN`

Means:

> A service is waiting for incoming connections.

Example:

```text
LISTEN :443
```

Nginx is waiting for HTTPS connections.

---

# 22. `ESTABLISHED`

Means:

> A TCP connection is currently established.

Example:

```text
Client
  │
  │ TCP
  ▼
Nginx
```

`ESTABLISHED` represents an active connection.

---

# 23. `TIME-WAIT`

This is often misunderstood.

You may see many:

```text
TIME-WAIT
```

connections.

This does **not automatically mean something is broken**.

TCP uses TIME-WAIT as part of connection cleanup and to prevent delayed packets from interfering with future connections.

A large number can become relevant under very high connection churn, but don't treat every TIME-WAIT socket as a problem.

---

# 24. `CLOSE-WAIT`

This one can be more interesting.

`CLOSE-WAIT` means the remote side has closed its connection, but the local application hasn't fully closed its side.

If you see a large and continuously growing number of:

```text
CLOSE-WAIT
```

it can indicate an application resource/connection handling problem.

For example:

```text
Node.js
   ↓
Connections aren't being closed correctly
   ↓
CLOSE-WAIT keeps growing
```

This is a valuable application-level clue.

---

# 25. Count Connections

You can use:

```bash
ss -tan | wc -l
```

This gives an approximate count of TCP socket entries.

For a more specific state:

```bash
ss -tan state established | wc -l
```

You can monitor trends rather than relying on one number.

---

# 26. Count Listening Ports

```bash
ss -lnt
```

If you want just the number of listening TCP sockets:

```bash
ss -lnt | tail -n +2 | wc -l
```

---

# 27. Find Connections to Port 443

```bash
sudo ss -tn sport = :443
```

This can help investigate HTTPS traffic.

Depending on `ss` syntax/version, you may also use:

```bash
sudo ss -tn '( sport = :443 )'
```

The exact filtering syntax can vary, so verify the output on your system.

---

# 28. Find Node.js Connections

If your Node app listens on 3000:

```bash
sudo ss -ntp | grep ':3000'
```

This can show:

```text
Client
   ↓
Node.js
   ↓
Connection
```

Now you can investigate whether the application has an unusual number of active connections.

---

# 29. UDP

TCP isn't everything.

To inspect UDP:

```bash
ss -lun
```

Meaning:

```text
-l → listening
-u → UDP
-n → numeric
```

Useful for services such as:

```text
DNS
DHCP
Some monitoring systems
Custom UDP services
```

# 30. `nload` — Traffic Overview

Now let's look at:

```bash
nload
```

Install if necessary:

```bash
sudo apt install nload
```

Run:

```bash
nload
```

You'll get a live traffic view.

Conceptually:

```text
Incoming
██████████████
5.2 Mbit/s

Outgoing
██████
1.1 Mbit/s
```

It helps answer:

> Is network traffic unusually high?

---

# 31. When `nload` Is Useful

Suppose your application suddenly becomes slow.

You check:

```text
CPU → normal
RAM → normal
Disk → normal
```

Then:

```bash
nload
```

shows:

```text
Incoming traffic
████████████████████
950 Mbps
```

on a 1 Gbps interface.

Now you have a strong clue:

> The network interface may be close to saturation.

---

# 32. `iftop` — Traffic by Connection

`nload` shows overall traffic.

`iftop` shows:

> **Who is generating the traffic?**

Install:

```bash
sudo apt install iftop
```

Run:

```bash
sudo iftop
```

You may see something like:

```text
10.0.0.5      => 192.168.1.20
10.0.0.6      => 192.168.1.20
192.168.1.20  => 10.0.0.7
```

with traffic rates.

---

# 33. `nload` vs `iftop`

|Tool|Answers|
|---|---|
|`nload`|How much traffic?|
|`iftop`|Who is generating traffic?|

Think:

```text
nload
 ↓
Overall network traffic

iftop
 ↓
Traffic by connection
```

---

# 34. `iftop` Requires Privileges

Usually:

```bash
sudo iftop
```

because packet/connection information requires appropriate privileges.

Choose the correct interface if needed.

For example:

```bash
sudo iftop -i eth0
```

or:

```bash
sudo iftop -i wlp2s0
```

---

# 35. `tcpdump` — Packet-Level Investigation 🔬

Now we reach the deepest tool:

```bash
tcpdump
```

This is a packet analyzer.

While:

```text
ss
```

shows sockets,

```text
iftop
```

shows traffic,

`tcpdump` lets you inspect actual packets.

---

# 36. Basic `tcpdump`

Run:

```bash
sudo tcpdump
```

You'll see packets such as:

```text
IP 192.168.1.10.52134 > 192.168.1.20.443
IP 192.168.1.20.443 > 192.168.1.10.52134
```

Press:

```text
Ctrl + C
```

to stop.

---

# 37. Don't Run `tcpdump` Blindly

A busy server can produce enormous amounts of packet output.

Instead, filter.

For example:

```bash
sudo tcpdump -i eth0 port 443
```

This captures traffic involving port 443.

---

# 38. Capture Traffic on Port 3000

For your Node.js API:

```bash
sudo tcpdump -i lo port 3000
```

if Node is listening on loopback.

You may see traffic like:

```text
127.0.0.1.52140 > 127.0.0.1.3000
127.0.0.1.3000 > 127.0.0.1.52140
```

This can prove whether packets are actually reaching the application.

---

# 39. Capture Only TCP

```bash
sudo tcpdump -i eth0 tcp
```

Only TCP packets are displayed.

---

# 40. Capture Only UDP

```bash
sudo tcpdump -i eth0 udp
```

Useful for investigating:

```text
DNS
DHCP
Custom UDP services
```

---

# 41. Capture DNS Traffic

DNS commonly uses port 53.

You can inspect:

```bash
sudo tcpdump -i any port 53
```

This can help investigate:

> Is the machine sending DNS queries?

> Are DNS responses returning?

---

# 42. Capture HTTP

For plain HTTP:

```bash
sudo tcpdump -i any port 80
```

For HTTPS:

```bash
sudo tcpdump -i any port 443
```

But remember:

> HTTPS payloads are encrypted.

You can see packet metadata, endpoints, timing, TCP behavior, etc., but not simply read the encrypted HTTP contents.

---

# 43. `-n` With `tcpdump`

Use:

```bash
sudo tcpdump -n
```

This prevents DNS/name resolution in the output.

For troubleshooting, this is often preferable because:

```text
IP addresses
+
ports
```

are immediately visible.

---

# 44. Capture a Limited Number of Packets

Instead of running indefinitely:

```bash
sudo tcpdump -c 20 -i any port 443
```

This captures approximately:

```text
20 packets
```

then exits.

Great for testing.

---

# 45. Save Packets to a File

You can capture:

```bash
sudo tcpdump -i any port 443 -w capture.pcap
```

Now the packet capture is saved as:

```text
capture.pcap
```

You can later inspect it using packet-analysis tools such as Wireshark.

This is extremely useful for serious network investigations.

---

# 46. Read a Capture

You can inspect a saved capture using:

```bash
tcpdump -r capture.pcap
```

This means:

```text
-r
↓
Read capture
```

You can also use:

```bash
tcpdump -nn -r capture.pcap
```

for numeric output.

---

# 47. TCP Handshake 🔗

A TCP connection starts with a three-way handshake:

```text
Client                 Server

  SYN  ───────────────►

       ◄──────────── SYN-ACK

  ACK  ───────────────►

        Connection
        established
```

These packets are:

```text
SYN
SYN-ACK
ACK
```

---

# 48. Why the TCP Handshake Matters

Suppose a client cannot connect to your Node.js API.

You capture:

```bash
sudo tcpdump -n -i any port 3000
```

You see:

```text
SYN
SYN
SYN
SYN
```

but no:

```text
SYN-ACK
```

That tells you something important:

> The connection attempt isn't receiving the expected response.

Possible causes include:

```text
Firewall
No service listening
Routing issue
Wrong IP
Network filtering
Application/service issue
```

You need further evidence to identify the exact cause.

---

# 49. Example: No Listener

Suppose:

```bash
ss -lntp | grep :3000
```

returns nothing.

Then:

```bash
tcpdump -n port 3000
```

shows incoming SYN packets.

This gives you:

```text
Client
 ↓
SYN
 ↓
Server
 ↓
No application listening
```

This is a much stronger diagnosis than simply saying:

> "Network is broken."

# 51. Real Incident 🚨

User reports:

> "My website is completely down."

Don't immediately restart Nginx.

Start with:

```bash
ss -lntp
```

You expect:

```text
:80
:443
```

Suppose:

```text
:80  → nginx
:443 → nginx
```

Good.

Now:

```bash
systemctl status nginx
```

Looks healthy.

Then:

```bash
curl -I http://127.0.0.1
```

returns:

```text
HTTP/1.1 200 OK
```

So Nginx works locally.

---

# 52. Continue the Investigation

Check the server's network:

```bash
ip addr
ip route
```

Everything looks correct.

Now:

```bash
sudo ss -tn
```

You see many connections.

Check:

```bash
nload
```

Network traffic looks normal.

Now the problem may be outside the server:

```text
DNS
Cloud firewall
Load balancer
CDN
External routing
```

This is why you should troubleshoot **layer by layer**.

# 53. Another Incident — Node.js Not Reachable

Suppose:

```text
Nginx
 ↓
502 Bad Gateway
```

Check:

```bash
ss -lntp | grep :3000
```

Nothing.

Then:

```bash
systemctl status student-api
```

shows:

```text
failed
```

Now you've found the problem:

```text

 ↓

 ↓

 ↓

```

This isn't fundamentally a network-interface problem.

It's an application/service problem.

# 54. Another Incident — Too Many Connections

Suppose your API becomes slow.

Run:

```bash
ss -tan | wc -l
```

and get:

```text
85000
```

You investigate states:

```bash
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c
```

You might discover:

```text
ESTAB       10000
TIME-WAIT   70000
CLOSE-WAIT   5000
```

Now you have clues.

Especially:

```text
CLOSE-WAIT
```

growing continuously could indicate connection cleanup problems.

But:

```text
TIME-WAIT
```

can naturally be high on busy systems.

Always interpret the numbers based on workload and trends.

# 62. Network Incident Workflow ⭐⭐⭐⭐⭐

When your API can't be reached:

### Step 1 — Interface

```bash
ip addr
ip link
```

Ask:

```text
Is the interface up?
Does it have the expected IP?
```

---

### Step 2 — Routing

```bash
ip route
```

Ask:

```text
Is there a valid route/default gateway?
```

---

### Step 3 — Listening ports

```bash
sudo ss -lntp
```

Ask:

```text
Is the expected service listening?
```

---

### Step 4 — Local application

```bash
curl -I http://127.0.0.1
```

or:

```bash
curl http://127.0.0.1:3000
```

Ask:

```text
Does the application work locally?
```

---

### Step 5 — Connections

```bash
ss -tn
```

Ask:

```text
Are connections arriving?
Are there unusual states?
```

---

### Step 6 — Traffic

```bash
nload
```

Ask:

```text
Is the interface receiving/sending traffic?
```

---

### Step 7 — Connection-level traffic

```bash
sudo iftop
```

Ask:

```text
Who is generating traffic?
```

---

### Step 8 — Packet-level evidence

```bash
sudo tcpdump -n -i any port 443
```

Ask:

```text
Are packets actually reaching the server?
```

---

### Step 9 — Application logs

```bash
journalctl -u nginx
journalctl -u student-api
```

Now correlate network behavior with application errors.

# 66. Security Warning ⚠️

Network monitoring tools can reveal sensitive information.

For example:

```bash
sudo ss -tnp
```

may show:

```text
IPs
Ports
Processes
Connections
```

And:

```bash
tcpdump
```

can capture potentially sensitive traffic metadata and, for unencrypted protocols, potentially sensitive contents.

So:

> **Packet captures should be treated as sensitive production data.**

Store them securely and don't share them publicly without reviewing their contents.

# 68. Interview Questions ⭐

### Q1. What is `ss` used for?

> `ss` displays socket information and is commonly used to inspect listening ports, TCP/UDP connections, socket states, and associated processes.

---

### Q2. How would you check whether a service is listening on port 3000?

```bash
sudo ss -lntp | grep :3000
```

---

### Q3. What is the difference between `ip addr` and `ip route`?

> `ip addr` shows network interfaces and their addresses, while `ip route` shows how the system routes packets to different networks.

---

### Q4. What is `tcpdump`?

> `tcpdump` is a command-line packet capture and analysis tool used to inspect network traffic at the packet level.

---

### Q5. What is the difference between `nload` and `iftop`?

> `nload` provides an overall view of incoming and outgoing interface traffic, while `iftop` shows traffic broken down by network connections/hosts.

---

### Q6. What does `CLOSE-WAIT` indicate?

> The remote side has closed its connection, but the local application hasn't fully closed its side. A continuously growing number can indicate an application connection-management problem.

---

### Q7. Does a high number of `TIME-WAIT` connections automatically indicate a problem?

> No. TIME-WAIT is a normal part of TCP connection termination. It becomes worth investigating when the volume is unusually high relative to workload or causes resource pressure.

# 70. 🧠 The Most Important Mental Model

When a network problem occurs, don't say:

> "The network is down."

Break it down:

```text
Is interface up?
       ↓
     ip link

Does server have correct IP?
       ↓
     ip addr

Does it have a route?
       ↓
     ip route

Is the service listening?
       ↓
     ss

Does the application work locally?
       ↓
     curl

Are packets arriving?
       ↓
     tcpdump

Is traffic excessive?
       ↓
     nload / iftop

Are connections behaving strangely?
       ↓
     ss
```

That's how a backend engineer approaches network incidents.
