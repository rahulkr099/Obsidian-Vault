# 1. What Are Metrics?

A **metric** is a numerical measurement that changes over time.

Examples:

```text
CPU usage       → 42%
Memory usage    → 61%
HTTP requests   → 1,240
Disk usage      → 73%
API latency     → 180 ms
Active users    → 52
```

Instead of:

```text
"Server feels slow"
```

we want:

```text
CPU = 92%
Memory = 87%
API latency = 1.8 seconds
```

Now we have measurable evidence.

---

# 2. Logs vs Metrics

You've already learned logs.

For example:

```text
2026-08-15 12:30:20 ERROR Database connection failed
```

A log tells you:

> **What happened?**

A metric tells you:

> **How much / how often / how long?**

Example:

```text
http_requests_total = 120430
```

This tells you how many requests have occurred.

---

# 3. Metrics vs Logs

|Logs|Metrics|
|---|---|
|Detailed events|Numerical measurements|
|High volume|Usually more compact|
|Great for investigation|Great for trends|
|"What happened?"|"How much/how often?"|
|Search individual events|Query time-series|
|Useful for errors|Useful for dashboards/alerts|

A production system needs both.

---

# 4. Metrics vs Traces

You already learned the three pillars:

```text
             Observability
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
     Logs       Metrics     Traces
       │          │          │
    Events     Numbers     Requests
```

For example:

### Logs

```text
Database connection timeout
```

### Metrics

```text
DB request latency = 2.4s
```

### Trace

```text
HTTP Request
    ↓
Auth middleware
    ↓
Controller
    ↓
Service
    ↓
MongoDB
       ↑
    2.1 sec
```

They complement each other.

# 5. What Is Prometheus? ⭐⭐⭐⭐⭐

Prometheus is an open-source monitoring and alerting system designed around **time-series metrics**.

Its basic job is:

```text
Collect metrics
      ↓
Store metrics
      ↓
Query metrics
      ↓
Evaluate rules
      ↓
Send alerts
```

Think of Prometheus as:

> **A database + scraper + query engine for metrics.**

---

# 6. Prometheus Architecture

The basic architecture looks like:

```text
                     ┌───────────────┐
                     │  Prometheus   │
                     │    Server     │
                     └───────┬───────┘
                             │
                         Scrape
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        Node Exporter    App Metrics    Other Exporter
              │              │              │
              ▼              ▼              ▼
           Linux          Node.js         Database
```

Prometheus periodically asks targets:

> "Give me your current metrics."

---

# 7. The Prometheus Pull Model ⭐⭐⭐⭐⭐

This is one of the most important concepts.

Prometheus usually uses a **pull model**.

```text
Prometheus
     │
     │ GET /metrics
     ▼
Target
     │
     │ metrics
     ▼
Prometheus
```

For example:

```text
Prometheus → http://server:9100/metrics
```

The target responds:

```text
cpu_usage...
memory_usage...
disk_usage...
```

Prometheus stores the results.

---

# 8. Pull vs Push

### Pull

```text
Prometheus
    ↓
GET /metrics
    ↓
Application
```

### Push

```text
Application
    ↓
Send metrics
    ↓
Monitoring server
```

Prometheus is primarily designed around:

> **Pulling metrics from targets.**

This makes service discovery and monitoring state easier to reason about in many environments.

# 11. Prometheus Data Model

Prometheus stores data as **time series**.

Think:

```text
Metric
 +
Labels
 +
Timestamp
 +
Value
```

Example:

```text
http_requests_total
```

with:

```text
method="GET"
status="200"
```

at:

```text
12:30:00
```

with:

```text
value = 120
```

---

# 12. Time-Series Data

Imagine CPU usage:

```text
Time        CPU
12:00       30%
12:01       35%
12:02       42%
12:03       67%
12:04       91%
```

This is a time series.

Prometheus continuously stores measurements like these.

So you can later ask:

> What was CPU usage during the last 6 hours?

# 13. Metric Name

A Prometheus metric might look like:

```text
http_requests_total
```

or:

```text
node_cpu_seconds_total
```

The name describes what is being measured.

Good metric names should be:

```text
Clear
Consistent
Meaningful
```

---

# 14. Labels ⭐⭐⭐⭐⭐

Labels make metrics much more powerful.

Example:

```text
http_requests_total{
  method="GET",
  status="200"
}
```

Another series could be:

```text
http_requests_total{
  method="POST",
  status="201"
}
```

Same metric:

```text
http_requests_total
```

Different labels:

```text
GET / 200
POST / 201
```

---

# 15. Think of Labels Like Database Columns

Imagine:

```text
http_requests_total
```

is like a database table.

Labels:

```text
method
status
route
```

are like dimensions.

For example:

```text
method   status   route
GET      200      /users
POST     201      /users
GET      404      /users/:id
```

This lets you slice your metrics in different ways.

---

# 16. Labels Are Powerful — But Dangerous

Don't create labels with unlimited values.

Bad:

```text
user_id="928374928374"
```

because potentially millions of users can produce millions of time series.

This is called:

> **High cardinality**

Instead:

```text
method="GET"
status="200"
route="/users/:id"
```

is much safer.

---

# 17. Cardinality

Suppose you have:

```text
100 routes
10 HTTP methods
5 status classes
```

You might have thousands of combinations.

That's manageable depending on your system.

But if you add:

```text
user_id
request_id
email
random UUID
```

the number of unique time series can explode.

So:

> **Never treat labels like arbitrary metadata storage.**

---

# 18. Prometheus Metric Types

Prometheus commonly uses four metric types:

```text
Counter
Gauge
Histogram
Summary
```

Let's understand each.

---

# 19. Counter ⭐⭐⭐⭐⭐

A counter represents a value that generally **only increases**.

Example:

```text
http_requests_total
```

Initially:

```text
100
```

Then:

```text
150
```

Then:

```text
230
```

It can reset when the application restarts.

Counters are ideal for:

```text
Requests
Errors
Jobs processed
Events
```

---

# 20. Gauge

A gauge represents a value that can go **up and down**.

Examples:

```text
memory_usage_bytes
active_connections
temperature
queue_length
```

For example:

```text
CPU:
40%
 ↓
70%
 ↓
30%
 ↓
85%
```

That's gauge-like behavior.

---

# 21. Counter vs Gauge

Remember:

```text
Counter
↓
Usually only increases

Gauge
↓
Can increase or decrease
```

Examples:

```text
requests_total → Counter
active_users   → Gauge
errors_total   → Counter
memory_usage   → Gauge
```

---

# 22. Histogram

Histograms are extremely important for backend engineers.

They measure distributions.

For example:

> How long do API requests take?

Instead of only:

```text
Average latency = 200ms
```

you can understand buckets:

```text
<100ms
<250ms
<500ms
<1s
<2s
```

This helps answer:

> How many requests are slow?

---

# 23. Why Average Latency Isn't Enough

Imagine:

```text
99 requests → 50ms
1 request   → 10 seconds
```

Average might hide the real user experience.

A histogram can show:

```text
Most requests → fast
Some requests → extremely slow
```

This is why latency histograms are widely used.

---

# 24. Summary

A summary also measures distributions, but it calculates quantiles on the client side.

You'll see concepts such as:

```text
p50
p90
p95
p99
```

For example:

```text
p50 = 100ms
p95 = 500ms
p99 = 1.5s
```

Meaning roughly:

```text
50% of observations ≤ 100ms
95% ≤ 500ms
99% ≤ 1.5s
```

The exact interpretation depends on the metric and query/window.

---

# 25. Histogram vs Summary

For now, remember:

|Type|Good for|
|---|---|
|Counter|Events that accumulate|
|Gauge|Current value|
|Histogram|Distributions/buckets|
|Summary|Quantiles/distributions|

In modern backend observability, histograms are particularly useful when you need to aggregate latency data across many instances.

# 30. Prometheus Configuration

The main configuration file is:

```text
prometheus.yml
```

A basic configuration looks conceptually like:

```yaml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]
```

Let's understand it.

---

# 31. `global`

Example:

```yaml
global:
  scrape_interval: 15s
```

This says:

> Scrape targets approximately every 15 seconds unless overridden.

So:

```text
Prometheus
   ↓ every 15 sec
Target
```

---

# 32. `scrape_configs`

This section defines what Prometheus should monitor.

Example:

```yaml
scrape_configs:
  - job_name: "prometheus"
```

We're creating a monitoring job called:

```text
prometheus
```

---

# 33. `targets`

Example:

```yaml
static_configs:
  - targets: ["localhost:9090"]
```

This tells Prometheus:

> Scrape metrics from `localhost:9090`.

The endpoint is usually:

```text
/metrics
```

So conceptually:

```text
http://localhost:9090/metrics
```

---

# 34. Prometheus's Own Metrics

If Prometheus is running:


```text

```


# 39. Your First PromQL Query ⭐⭐⭐⭐⭐

Prometheus has its own query language:

> **PromQL — Prometheus Query Language**

In the Prometheus web UI, try:

```promql
up
```

This is one of the most important beginner queries.

---

# 40. What Does `up` Mean?

The `up` metric indicates whether Prometheus successfully scraped a target.

Usually:

```text
up = 1
```

means:

> Target was successfully scraped.

And:

```text
up = 0
```

means:

> Scrape failed.

This simple metric is incredibly useful.

---

# 41. Query `up`

Try:

```promql
up
```

You may see something like:

```text
up{instance="localhost:9090",job="prometheus"} 1
```

Now you have:

```text
job
instance
value
```

---

# 42. What Is `job`?

A `job` identifies a group of targets performing the same role.

For example:

```text
job="node"
job="nginx"
job="api"
job="database"
```

Example:

```text
up{job="api"} 1
```

means:

> The API target was successfully scraped.

---

# 43. What Is `instance`?

`instance` typically identifies the target endpoint.

Example:

```text
instance="192.168.1.20:9100"
```

So:

```text
job="node"
instance="192.168.1.20:9100"
```

means:

> Node Exporter running at that endpoint.

# 52. Scrape Interval

Suppose:

```yaml

```

Prometheus approximately does:

```text
12:00:00 → scrape
12:00:15 → scrape
```

The right interval depends on:

```text

Metric volatility

```

Don't automatically use extremely short intervals.

# 53. Why Not Scrape Every Millisecond?

Because every scrape creates overhead:

```text
Network
CPU
Storage
Memory
```

If you have:

```text
1000 targets
```

and:

```text
100 metrics each
```

you can quickly generate substantial time-series data.

Monitoring itself must be designed efficiently.

# 54. Prometheus Storage

Prometheus stores time-series data locally by default.

Conceptually:

```text
Target
 ↓
Prometheus
 ↓
Local TSDB
```

TSDB means:

> Time Series Database.

Prometheus's local storage is optimized for this type of metric data.

For larger architectures, long-term storage integrations can be added later.

---

# 55. Prometheus Is Not Your Log System

Don't try to store:

```text

```

inside Prometheus.

Use:

```text
Prometheus → Metrics
Loki/ELK → Logs
```

For example:

```text
                Application
               /           \
              ▼             ▼
          Metrics          Logs
              │             │
              ▼             ▼
         Prometheus        Loki
              │             │
              └──────┬──────┘
                     ▼
                  Grafana
```

This is the direction we'll build toward.

# 58. PromQL Basics

PromQL is one of the most important skills in modern observability.

Start with:

```promql
up
```

Then:

```promql
up == 0
```

This finds targets that are down/unreachable from Prometheus's perspective.

# 59. Metric Selection

Suppose you have:

```text
http_requests_total
```

Query:

```promql
http_requests_total
```

Prometheus returns matching time series.

With labels:

```promql
http_requests_total{method="GET"}
```

Now you're selecting:

> Only GET requests.

---

# 60. Label Filtering

Example:

```promql
http_requests_total{status="500"}
```

This means:

> Select HTTP 500 request series.

Another:

```promql
http_requests_total{route="/api/users"}
```

This means:

> Select metrics for the `/api/users` route.

---

# 61. Multiple Label Filters

You can combine:

```promql
http_requests_total{
  method="GET",
  status="200"
}
```

Meaning:

```text
GET
+
200
```

---

# 62. Metric Arithmetic

PromQL supports calculations.

For example:

```promql
1 - up
```

This can conceptually turn:

```text
up = 1 → 0
up = 0 → 1
```

Useful when constructing expressions.

---

# 63. Rate ⭐⭐⭐⭐⭐

Counters continuously increase.

You usually don't want to know:

```text
Total requests since server started
```

You often want:

> How fast are requests arriving?

PromQL provides:

```promql
rate(http_requests_total[5m])
```

This estimates the per-second increase over the last 5 minutes.

---

# 64. Why `rate()` Matters

Suppose:

```text
http_requests_total
```

is:

```text
10,000
```

That number alone isn't very useful.

But:

```promql
rate(http_requests_total[5m])
```

might return:

```text
25
```

Meaning approximately:

> 25 requests/second over that recent window.

This is much more useful for monitoring traffic.

---

# 65. `increase()`

Another useful function:

```promql
increase(http_requests_total[1h])
```

This asks approximately:

> How many requests occurred during the last hour?

So:

```text
rate()
→ per-second rate

increase()
→ increase over a time window
```

---

# 66. `sum()`

Suppose you have:

```text
http_requests_total
```

with:

```text
method
route
status
```

You might have many series.

You can aggregate them:

```promql
sum(http_requests_total)
```

This gives a combined result across matching series.

---

# 67. `sum by()`

You can group by labels.

For example:

```promql
sum by (status) (
  rate(http_requests_total[5m])
)
```

This can show request rate by HTTP status.

Conceptually:

```text
200 → 120 req/s
201 → 20 req/s
404 → 5 req/s
500 → 3 req/s
```

This is extremely useful for backend monitoring.

---

# 68. HTTP Error Rate

Imagine:

```text
http_requests_total
```

with:

```text
status
```

You can eventually calculate:

```text
5xx requests
----------------
all requests
```

This produces an error ratio.

For example:

```text
0.02
```

means:

```text
2%
```

of requests in the selected window.

This is much better than simply saying:

> "The API has errors."

# 70. Configuration Validation

When modifying:

```text
prometheus.yml
```

be careful with YAML indentation.

For example:

```yaml

  - job_name: "node"
```

# 80. Production Warning ⚠️

Prometheus is powerful, but you can create problems with bad metric design.

Avoid:

```text
user_id
request_id
session_id
email
UUID
full URL with arbitrary query parameters
```

as labels.

Instead use bounded dimensions:

```text
method
status
route
environment
service
region
```

This is one of the most important Prometheus design rules.

# 81. Metric Naming

Prefer names that communicate:

```text
what
unit
type
```

Examples:

```text
http_requests_total
process_cpu_seconds_total
http_request_duration_seconds
```

Notice:

```text
_seconds
```

for duration.

Prometheus conventions generally prefer base units such as:

```text
seconds
bytes
```

rather than:

```text
milliseconds
megabytes
```

You can convert them when displaying.

---

# 82. Why Base Units Matter

Instead of:

```text
request_duration_ms
```

prefer:

```text
request_duration_seconds
```

Then:

```text
0.250 seconds
```

can be displayed as:

```text
250 ms
```

Grafana can handle the presentation.

The underlying metric stays consistent.

# 84. The Four Golden Signals 🚦

A very useful monitoring framework is the **Four Golden Signals**:

```text
Latency
Traffic
Errors
Saturation
```

### Latency

How long requests take.

### Traffic

How much demand the system receives.

### Errors

How many requests fail.

### Saturation

How close the system is to its limits.

For your Node.js backend:

```text
Traffic → requests/sec
Latency → API response time
Errors → 5xx rate
Saturation → CPU/memory/connections
```

Keep these in mind when we build Grafana dashboards.

# 88. Interview Questions ⭐

### Q1. What is Prometheus?

> Prometheus is an open-source monitoring and alerting system that collects and stores time-series metrics and provides PromQL for querying them.

---

### Q2. Does Prometheus use push or pull?

> Prometheus primarily uses a pull-based model where the Prometheus server periodically scrapes metrics from targets.

---

### Q3. What is an exporter?

> An exporter exposes metrics from a system or application in a format Prometheus can scrape.

---

### Q4. What is a time series?

> A time series is a sequence of timestamped metric values, usually identified by a metric name and set of labels.

---

### Q5. What are labels?

> Labels are key-value dimensions attached to metrics that allow different time series to be distinguished and queried.

---

### Q6. What is high cardinality?

> High cardinality occurs when a metric has a very large number of unique label combinations, potentially causing excessive memory and storage usage.

---

### Q7. Counter vs Gauge?

> A counter represents a cumulative value that generally increases, while a gauge represents a value that can increase or decrease.

---

### Q8. What is PromQL?

> PromQL is Prometheus's query language used to select, filter, aggregate, calculate, and analyze time-series metrics.

---

### Q9. What does `up` mean?

> `up` is a built-in Prometheus metric indicating whether a target was successfully scraped. `1` normally means success and `0` means the scrape failed.

# 89. 📋 PromQL Cheat Sheet

Start memorizing these:


```promql
up == 0
```

```promql
metric_name
```

Filter by label.

```promql

```

Calculate recent per-second rate.

```promql

```

Calculate increase over a time range.

```promql

```

Aggregate series.

```promql
sum by (label) (metric_name)
```

Aggregate while grouping by a label.
