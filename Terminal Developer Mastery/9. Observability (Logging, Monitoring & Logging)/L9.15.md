# 1. What Is Node Exporter? ⭐⭐⭐⭐⭐

Prometheus Node Exporter is a Prometheus exporter that exposes hardware and operating-system metrics from a machine.

Think of it like an adapter:

```text
Linux Server
     │
     │ system information
     ▼
Node Exporter
     │
     │ Prometheus metrics
     ▼
Prometheus
```

Node Exporter doesn't replace Prometheus.

It **exposes metrics for Prometheus to scrape**.

---

# 2. Why Do We Need Node Exporter?

Prometheus itself doesn't automatically know:

```text
CPU usage
RAM usage
Disk usage
Filesystem usage
Network traffic
System load
```

Node Exporter collects this information from Linux and exposes it.

For example:

```text
Linux
  │
  ├── CPU
  ├── RAM
  ├── Disk
  ├── Network
  └── Filesystem
        │
        ▼
  Node Exporter
        │
        ▼
  /metrics
        │
        ▼
  Prometheus
```

---

# 3. Node Exporter Architecture

Your final setup will look like:

```text
                 Linux Server
                      │
             ┌────────┴────────┐
             │                 │
           System          Applications
             │                 │
             ▼                 ▼
       Node Exporter       Node.js / Nginx
             │                 │
             │                 │
             ▼                 ▼
          /metrics          /metrics
             │                 │
             └────────┬────────┘
                      ▼
                  Prometheus
                      │
                      ▼
                   Grafana
```

This is the foundation of infrastructure monitoring.

# 4. Node Exporter Uses Port 9100

By default, Node Exporter commonly listens on:

```text
9100
```

So you'll eventually have:

```text
Prometheus → localhost:9090
Grafana    → localhost:3000
Node       → localhost:3000/your-app
Node Exporter → localhost:9100
```

Notice the potential port conflict:

```text
Grafana → 3000
Node.js → 3000
```

If both are on the same machine, configure one differently.

# 10. What Is `/metrics`?

Remember the Prometheus pull model:

```text
Prometheus
     │
     │ GET /metrics
     ▼
Node Exporter
     │
     │ metric data
     ▼
Prometheus
```

So:

```text
http://localhost:9100/metrics
```

is essentially the doorway through which Prometheus collects Linux metrics.

---

# 11. Don't Read the Entire `/metrics` Output

There may be thousands of lines.

Instead:

```bash
curl -s http://localhost:9100/metrics | head
```

Or search:

```bash
curl -s http://localhost:9100/metrics | grep node_cpu | head
```

This is much easier.

# 12. Run Node Exporter as a systemd Service ⭐⭐⭐⭐⭐

Running:

```bash
./node_exporter
```

is okay for testing.

But if the terminal closes:

```text
Node Exporter stops.
```

A production service should:

```text
Start automatically
Restart on failure
Run in background
Have controlled permissions
Be managed by systemd
```

So let's create a service.

---

# 13. Create a Dedicated User

Create a system user:

```bash
sudo useradd --no-create-home --shell /usr/sbin/nologin node_exporter
```

Why?

Security.

Instead of running the exporter as:

```text
root
```

we use:

```text
node_exporter
```

with limited privileges.

---

# 14. Install the Binary

Move the binary somewhere standard:

```bash
sudo cp node_exporter /usr/local/bin/node_exporter
```

Check:

```bash
which node_exporter
```

Expected:

```text
/usr/local/bin/node_exporter
```

---

# 15. Set Ownership

```bash
sudo chown node_exporter:node_exporter /usr/local/bin/node_exporter
```

Verify:

```bash
ls -l /usr/local/bin/node_exporter
```

---

# 16. Create systemd Service

Create:

```bash
sudo nano /etc/systemd/system/node_exporter.service
```

Add:

```ini
[Unit]
Description=Prometheus Node Exporter
Wants=network-online.target
After=network-online.target

[Service]
User=node_exporter
Group=node_exporter
Type=simple
ExecStart=/usr/local/bin/node_exporter

Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Save the file.

# 22. Connect Node Exporter to Prometheus ⭐⭐⭐⭐⭐

Now we need to tell Prometheus:

> "Please scrape Node Exporter."

Open your Prometheus configuration:

```bash
nano prometheus.yml
```

Add:

```yaml
scrape_configs:
  - job_name: "node"
    static_configs:
      - targets:
          - "localhost:9100"
```

Your configuration might now look similar to:

```yaml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets:
          - "localhost:9090"

  - job_name: "node"
    static_configs:
      - targets:
          - "localhost:9100"
```

# 27. CPU Metrics ⭐⭐⭐⭐⭐

Node Exporter exposes:

```text
node_cpu_seconds_total
```

This is a counter representing CPU time.

You'll usually see labels such as:

```text
cpu="0"
mode="user"
mode="system"
mode="idle"
mode="iowait"
```

For example:

```text
node_cpu_seconds_total{
  cpu="0",
  mode="idle"
}
```

---

# 28. Why CPU Metrics Are Counters

Imagine:

```text
CPU idle seconds:
1000
1005
1010
1015
```

The value continuously increases.

That's a counter.

We need:

```promql
rate(...)
```

to determine how quickly it is changing.

---

# 29. CPU Usage Query

A common CPU utilization query:

```promql
100 * (
  1 - avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  )
)
```

This gives approximate CPU utilization percentage.

Conceptually:

```text
Total CPU
   -
Idle CPU
   =
Used CPU
```

---

# 30. Per-CPU Usage

You can also inspect individual CPUs:

```promql
100 * (
  1 - rate(node_cpu_seconds_total{mode="idle"}[5m])
)
```

You might see:

```text
CPU 0 → 20%
CPU 1 → 30%
CPU 2 → 70%
CPU 3 → 40%
```

This can help identify uneven workload distribution.

---

# 31. Memory Metrics ⭐⭐⭐⭐⭐

Important Node Exporter memory metrics include:

```text
node_memory_MemTotal_bytes
node_memory_MemAvailable_bytes
```

You can calculate memory usage:

```promql
100 * (
  1 -
  node_memory_MemAvailable_bytes
  /
  node_memory_MemTotal_bytes
)
```

This gives approximate memory utilization.

---

# 32. Why `MemAvailable`?

A common beginner mistake is:

```text
Total memory - completely unused memory
```

and assuming that equals:

> memory available to applications.

Linux uses memory for:

```text
Caches
Buffers
Kernel structures
```

So `MemAvailable` is generally more useful for estimating how much memory is still available to applications.

# 34. Filesystem Metrics

Node Exporter exposes filesystem metrics such as:

```text
node_filesystem_size_bytes
node_filesystem_avail_bytes
node_filesystem_free_bytes
```

You can calculate filesystem usage:

```promql
100 * (
  1 -
  node_filesystem_avail_bytes
  /
  node_filesystem_size_bytes
)
```

But don't immediately put this query into production without filtering filesystems.

---

# 35. Why Filesystem Filtering Matters

Linux exposes many filesystems:

```text
/proc
/sys
/run
/dev
/tmp
/
```

Some are virtual filesystems.

You usually care about real filesystems such as:

```text
/ 
/home
/data
```

So dashboard queries should filter appropriately.

---

# 36. Example Filesystem Filter

A more useful query might include:

```promql
100 * (
  1 -
  node_filesystem_avail_bytes{
    fstype!~"tmpfs|overlay"
  }
  /
  node_filesystem_size_bytes{
    fstype!~"tmpfs|overlay"
  }
)
```

The exact filters depend on your environment.

The important lesson is:

> **Know what filesystem you're measuring.**

---

# 37. Disk I/O Metrics

Node Exporter also exposes disk I/O metrics such as:

```text
node_disk_read_bytes_total
node_disk_written_bytes_total
```

These are counters.

Use:

```promql
rate(node_disk_read_bytes_total[5m])
```

to estimate read throughput.

And:

```promql
rate(node_disk_written_bytes_total[5m])
```

for write throughput.

---

# 38. Disk I/O vs Disk Space

Don't confuse:

```text
Disk space
```

with:

```text
Disk I/O
```

### Disk space

```text
How much storage remains?
```

### Disk I/O

```text
How much data is being read/written?
```

A server can have:

```text
20% disk used
```

but:

```text
Very high disk I/O
```

Both metrics matter.

---

# 39. Network Metrics

Node Exporter exposes network counters such as:

```text
node_network_receive_bytes_total
node_network_transmit_bytes_total
```

Use:

```promql
rate(node_network_receive_bytes_total[5m])
```

for incoming traffic.

And:

```promql
rate(node_network_transmit_bytes_total[5m])
```

for outgoing traffic.

---

# 40. Filter Network Interfaces

Linux has interfaces such as:

```text
lo
eth0
enp3s0
wlan0
docker0
```

You may not want:

```text
lo
docker0
```

in your primary network dashboard.

For example:

```promql
rate(
  node_network_receive_bytes_total{
    device!="lo"
  }[5m]
)
```

You can add additional filters based on your environment.

---

# 41. Network Receive vs Transmit

Remember:

```text
receive
↓
data coming INTO server

transmit
↓
data going OUT of server
```

So:

```text
receive → incoming traffic
transmit → outgoing traffic
```

---

# 42. System Load

Node Exporter provides load-related metrics such as:

```text
node_load1
node_load5
node_load15
```

These correspond roughly to:

```text
1-minute load
5-minute load
15-minute load
```

You can query:

```promql
node_load1
```

---

# 43. Load Is Not CPU Percentage

This is very important.

If you see:

```text
load = 4
```

that does **not** mean:

```text
CPU = 4%
```

Load represents runnable/uninterruptible work over time, not direct CPU utilization percentage.

Interpret it relative to the number of CPU cores and workload.

---

# 44. Uptime

Node Exporter provides system time metrics such as:

```text
node_boot_time_seconds
```

You can use this to determine when the machine booted.

For example:

```promql
time() - node_boot_time_seconds
```

gives approximately:

> seconds since boot.

You can display this as a duration in Grafana.

# 55. Prometheus Scrape Interval

If:

```yaml
scrape_interval: 15s
```

and Node Exporter goes down immediately after a scrape, Prometheus may not notice instantly.

It may take another scrape.

So:

```text
Failure
   ↓
Next scrape
   ↓
Prometheus detects failure
   ↓
Alert evaluation
   ↓
Alertmanager
```

We'll build alerting in Part 5.

# 56. Node Exporter Security ⚠️

Node Exporter exposes information about the machine.

Therefore:

> Don't expose port `9100` publicly unless you have a strong reason and appropriate access controls.

Prefer:

```text
Prometheus
   │
   │ private network
   ▼
Node Exporter
```

rather than:

```text
Internet
   │
   ▼
Server:9100
```

If Prometheus and Node Exporter are on the same machine:

```text
127.0.0.1:9100
```

can be a good design when external access isn't needed.

---

# 57. Firewall Considerations

If Prometheus is on another server:

```text
Prometheus Server
       │
       │ TCP 9100
       ▼
Application Server
```

you need network access between them.

But don't simply open:

```text
9100
```

to the entire internet.

Instead allow only the monitoring server/network where appropriate.

---

# 58. Node Exporter and Containers

If you're monitoring a Linux host running Docker:

```text
Linux Host
   │
   ├── Docker
   │    ├── Node.js
   │    ├── MongoDB
   │    └── Nginx
   │
   └── Node Exporter
```

Node Exporter can provide host-level metrics.

Container-specific metrics may require additional monitoring approaches.

This distinction becomes important later when you build the Docker observability stack.

# 59. Common Troubleshooting Problem #1

Prometheus says:

```text
node → DOWN
```

First check:

```bash
sudo systemctl status node_exporter
```

---

# 60. Problem #2 — Port Not Listening

Run:

```bash
sudo ss -lntp | grep :9100
```

If nothing appears:

```text
Node Exporter isn't listening.
```

Check logs:

```bash
journalctl -u node_exporter -n 50
```

---

# 61. Problem #3 — Metrics Endpoint Fails

Run:

```bash
curl http://localhost:9100/metrics
```

If this fails:

```text
Prometheus cannot scrape it either.
```

Fix Node Exporter first.

---

# 62. Problem #4 — Wrong Target

Your Prometheus config might say:

```yaml
targets:
  - "localhost:9100"
```

But Node Exporter might actually be on:

```text
192.168.1.20:9100
```

if Prometheus is running on another machine.

Remember:

> `localhost` refers to the machine **running Prometheus**, not the machine you are monitoring.

This is a very common mistake.

---

# 63. Problem #5 — Firewall

Suppose:

```text
Node Exporter
  ↓
curl works locally
```

but:

```text
Prometheus
  ↓
can't scrape
```

Possible cause:

```text
Firewall
```

Check the network path and firewall rules.

Don't immediately assume Node Exporter is broken.

---

# 64. Problem #6 — Prometheus Configuration

If Prometheus won't restart:

```bash
sudo systemctl status prometheus
```

Then:

```bash
journalctl -u prometheus -n 50
```

Look for:

```text
YAML errors
Invalid configuration
Incorrect target
Permission issues
```

YAML indentation matters.

---

# 65. Verify Every Layer

When Node Exporter isn't working:

```text
1. Is the process running?
        ↓
systemctl status

2. Is port 9100 listening?
        ↓
ss

3. Does /metrics work?
        ↓
curl

4. Can Prometheus reach it?
        ↓
Prometheus Targets

5. Does up = 1?
        ↓
PromQL

6. Does Grafana show the data?
        ↓
Dashboard
```

This is exactly the troubleshooting mindset you've been building throughout Module 9.

# 72. Interview Questions ⭐⭐⭐⭐⭐

### Q1. What is Node Exporter?

> Node Exporter is a Prometheus exporter that exposes Linux system and hardware metrics in a Prometheus-compatible format.

---

### Q2. What port does Node Exporter normally use?

> Port 9100 by default.

---

### Q3. How does Prometheus collect Node Exporter metrics?

> Prometheus periodically scrapes Node Exporter's `/metrics` endpoint.

---

### Q4. Why should Node Exporter not normally be publicly exposed?

> It exposes system-level monitoring information and usually only needs to be accessible by the monitoring system.

---

### Q5. Why run Node Exporter as a systemd service?

> It allows automatic startup, process supervision, restart handling, centralized logging, and proper service management.

---

### Q6. What is `node_cpu_seconds_total`?

> It is a cumulative CPU time counter broken down by CPU and operating mode, such as idle, user, system, and iowait.

---

### Q7. Why use `rate()` on CPU metrics?

> CPU time is a counter. `rate()` calculates its recent change per second, allowing us to derive CPU utilization.

---

### Q8. What's the difference between disk usage and disk I/O?

> Disk usage measures how much storage capacity is occupied, while disk I/O measures how much data is being read or written.

# 74. 🔥 PromQL to Remember

### Target status

```promql
up{job="node"}
```

### CPU

```promql
100 * (
  1 - avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  )
)
```

### Memory

```promql
100 * (
  1 -
  node_memory_MemAvailable_bytes
  /
  node_memory_MemTotal_bytes
)
```

### Load

```promql
node_load1
```

### Network receive

```promql
rate(node_network_receive_bytes_total{device!="lo"}[5m])
```

### Network transmit

```promql
rate(node_network_transmit_bytes_total{device!="lo"}[5m])
```

### Disk read

```promql
rate(node_disk_read_bytes_total[5m])
```

```promql
rate(node_disk_written_bytes_total[5m])
```
