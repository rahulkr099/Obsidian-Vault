# 1. What Is Alertmanager?

Prometheus Alertmanager is the component that handles alerts generated by Prometheus.

Think of it like this:

```text
Prometheus
   ↓
Detects problem
   ↓
"CPU is high"
   ↓
Alertmanager
   ↓
Decides:
   ├── Who should receive it?
   ├── How should it be grouped?
   ├── Should it be suppressed?
   └── Where should it be sent?
```

So Alertmanager is basically the **alert traffic controller**.

# 2. Prometheus vs Alertmanager ⭐⭐⭐⭐⭐

This distinction is extremely important.

### Prometheus

Responsible for:

```text
Metrics
Scraping
Storage

Alert evaluation
```

### Alertmanager

Responsible for:

```text
Grouping
Deduplication
Routing
Silencing
Inhibition
Notifications
```

Think:

```text
Prometheus
"Something is wrong."

Alertmanager
"Okay. Who should I tell, how, and when?"
```

# 4. Why Not Let Prometheus Send Everything?

Imagine you have:

```text
100 servers
```

and:

```text
20 alerts
```

That's potentially:

```text
2000 alert situations
```

You need logic such as:

```text
Group related alerts
Remove duplicates
Route by team
Route by severity
Suppress dependent alerts
Temporarily silence alerts
```

That's Alertmanager's job.

# 12. Create systemd Service

Create:

```bash
sudo nano /etc/systemd/system/alertmanager.service
```

Add:

```ini
[Unit]
Description=Prometheus Alertmanager
Wants=network-online.target
After=network-online.target

[Service]
User=alertmanager
Group=alertmanager
Type=simple

ExecStart=/usr/local/bin/alertmanager \
  --config.file=/etc/alertmanager/alertmanager.yml \
  --storage.path=/var/lib/alertmanager

Restart=on-failure

[Install]
WantedBy=multi-user.target
```

# 16. Alertmanager Configuration

The main configuration is:

```text
/etc/alertmanager/alertmanager.yml
```

A simple configuration might look like:

```yaml
global:
  resolve_timeout: 5m

  receiver: default
```

---

# 17. `global`

Example:

```yaml
global:
  resolve_timeout: 5m
```

Global settings apply broadly.

`resolve_timeout` controls how long Alertmanager waits before considering an alert resolved when resolution information isn't otherwise received.

You don't need to memorize every global option.

The important idea:

```text
global
   ↓
Default Alertmanager behavior
```

---

# 18. `route` ⭐⭐⭐⭐⭐

This is one of the most important sections.

Example:

```yaml
route:
  receiver: default
```

It says:

> Send alerts matching this route to the `default` receiver.

Think of it as:

```text
Alert
  ↓
Routing rules
  ↓
Receiver
```

---

Examples:

```text

Slack
```

Conceptually:

```yaml
receivers:
  - name: email-team
```

The receiver contains the notification configuration.

# 22. Grouping ⭐⭐⭐⭐⭐

Imagine:

```text
Server 1 down
Server 2 down
Server 3 down
Server 4 down
```

If they all belong to:

```text
cluster=production
```

Alertmanager can group them.

Instead of:

```text
🚨 Server 1
🚨 Server 2
🚨 Server 3
🚨 Server 4
```

you can receive:

```text
🚨 Production cluster:
4 servers are down
```

Much cleaner.

---

# 23. `group_by`

Example:

```yaml
route:
  receiver: default
  group_by:
    - alertname
    - cluster
```

This means alerts can be grouped based on:

```text
alertname
cluster
```

So related alerts can arrive together.

---

# 24. Why Grouping Matters

Without grouping:

```text
100 alerts
```

might mean:

```text
100 notifications
```

With grouping:

```text
100 alerts
   ↓
5 meaningful notifications
```

This is one of the most important ways to reduce alert fatigue.

---

# 25. Deduplication

Suppose Prometheus sends the same alert repeatedly.

Alertmanager helps prevent you from receiving:

```text
🚨 API down
🚨 API down
🚨 API down
🚨 API down
```

as separate noisy notifications.

Instead, Alertmanager tracks alerts and handles repeated notifications according to its routing/grouping configuration.

---

# 26. Group Wait

A route can specify:

```yaml
group_wait: 30s
```

This means Alertmanager can wait briefly before sending the first notification for a new group.

Why?

Because more related alerts may arrive.

For example:

```text
Server 1 down
   ↓
Server 2 down
   ↓
Server 3 down
```

Instead of sending three separate notifications immediately, Alertmanager can collect them into a group.

---

# 27. Group Interval

Example:

```yaml
group_interval: 5m
```

This controls how often updates to an existing alert group are sent.

Think:

```text
Initial group
   ↓
Notification
   ↓
More alerts arrive
   ↓
Wait
   ↓
Update notification
```

---

# 28. Repeat Interval

Example:

```yaml
repeat_interval: 4h
```

This controls how often an alert group is re-notified if it remains active.

Without sensible repeat behavior, a long-running incident can become noisy.

---

# 29. Grouping Timeline

Imagine:

```text
12:00:00
Server 1 down

12:00:10
Server 2 down

12:00:20
Server 3 down
```

With:

```yaml
group_wait: 30s
```

Alertmanager can wait and send something like:

```text
12:00:30

🚨 3 servers down
```

That's much more useful.

---

# 30. Inhibition ⭐⭐⭐⭐⭐

This is another important Alertmanager feature.

Suppose:

```text
Database server DOWN
```

Then you might also get:

```text
API cannot connect to database
```

But the API failure is a downstream effect.

You don't necessarily want:

```text
🚨 Database DOWN
🚨 API DB connection failure
🚨 API errors
🚨 API latency
```

all at once.

---

# 31. What Is Inhibition?

Inhibition means:

> **Suppress certain alerts when another more important alert is already firing.**

For example:

```text
DatabaseDown
      ↓
Suppress
DatabaseConnectionErrors
```

This reduces noise.

---

# 32. Inhibition Example

Conceptually:

```yaml
inhibit_rules:
  - source_matchers:
      - alertname="DatabaseDown"

    target_matchers:
      - alertname="DatabaseConnectionFailure"

    equal:
      - environment
```

Meaning:

> If the database is down, suppress related database connection failure alerts for the same environment.

The exact matcher syntax depends on your Alertmanager version/configuration style.

---

# 33. Silencing ⭐⭐⭐⭐⭐

Sometimes an alert is expected.

Example:

```text
Scheduled maintenance
```

You know:

```text
Server will be offline
```

You don't want:

```text
🚨 Server Down
```

during that window.

You can create a **silence**.

---

# 34. What Is a Silence?

A silence says:

> Don't notify me about alerts matching these labels for this period.

For example:

```text
environment=staging
```

could be silenced during maintenance.

The alert can still exist internally.

You're just suppressing notifications.

---

# 35. Silence vs Inhibition

Important distinction:

### Silence

Manually says:

```text
Don't notify about this alert.
```

### Inhibition

Automatically says:

```text
Don't notify this dependent alert because a more important alert is active.
```

So:

```text
Silence → intentional suppression
Inhibition → dependency-based suppression
```

This is a good way to organize a larger project.

# 78. Interview Question ⭐⭐⭐⭐⭐

### "What's the difference between Prometheus and Alertmanager?"

Strong answer:

> Prometheus collects metrics, stores time-series data, evaluates PromQL and alerting rules, and determines when an alert condition is firing. Alertmanager receives those alerts and handles grouping, deduplication, routing, silencing, inhibition, and notifications such as email or Slack.

That's an excellent interview answer.

---

# 79. Interview Question

### "What is alert grouping?"

> Alert grouping combines related alerts into a single notification to reduce notification noise and make incidents easier to understand.

---

# 80. Interview Question

### "What is inhibition?"

> Inhibition suppresses lower-priority or dependent alerts when a higher-priority alert is already firing.

Example:

```text
DatabaseDown
    ↓
Suppress
DatabaseConnectionFailure
```

---

# 81. Interview Question

### "What is a silence?"

> A silence temporarily suppresses notifications for alerts matching specified labels, commonly during planned maintenance.

---

# 82. Interview Question

### "Why use labels in alerts?"

> Labels provide structured metadata that can be used to classify, group, filter, and route alerts.

Example:

```yaml
severity: critical
service: api
environment: production
```

---

# 83. Interview Question

### "What is alert fatigue?"

> Alert fatigue occurs when engineers receive too many noisy or low-value alerts, reducing their ability to recognize and respond to important incidents.

A strong engineer doesn't just create alerts.

They create:

> **High-signal alerts.**
