
Now comes one of the most important backend-engineering skills:

> **Finding out why a system is slow.**

A production problem rarely says:

```text

```

Instead, you'll see:

```text
API is slow
CPU is high
Memory is increasing
Requests are timing out

```

Your job is to move from:

```text

  ↓

  ↓

  ↓

  ↓

  ↓
FIX
  ↓

```

---

# 1. What Is a Performance Bottleneck?

A **bottleneck** is a component that limits the performance of the overall system.

Imagine:

```text
User
 ↓
Nginx
 ↓
Node.js
 ↓
MongoDB
```

Suppose:

```text
Nginx       → 5 ms
Node.js     → 20 ms
MongoDB     → 900 ms
```

The database is probably the bottleneck.

Your application cannot become much faster until the slow component is addressed.

---

# 2. The Bottleneck Principle

Think of a system as a pipeline:

```text
A → B → C → D
```

If:

```text
A = fast
B = fast
C = slow
D = fast
```

then:

```text
C
↓
Bottleneck
```

Improving A or D won't solve the main problem.

This sounds obvious, but it's a very common production debugging mistake.

---

# 3. Performance vs Availability

These are different problems.

### Availability

```text
Is the service working?
```

Example:

```text
API → DOWN
```

### Performance

```text
Is the service working fast enough?
```

Example:

```text
API → responding
Latency → 5 seconds
```

A service can be:

```text
UP + SLOW
```

and that's often just as important as:

```text
DOWN
```

---

# 4. User Experience Is the Final Signal

Imagine:

```text
CPU = 40%
Memory = 50%
Disk = 30%
```

Everything looks healthy.

But:

```text
API latency = 4 seconds
```

Users still experience:

> A slow application.

So don't assume:

```text
Infrastructure looks healthy
        ↓
Application must be healthy
```

That's false.

You need application-level observability too.

---

# 5. The Four Golden Signals ⭐⭐⭐⭐⭐

When investigating performance, remember:

```text
Latency
Traffic
Errors
Saturation
```

### Latency

How long requests take.

### Traffic

How much work the system is handling.

### Errors

How much work is failing.

### Saturation

How close a resource is to its capacity.

These four signals give you an excellent starting point.

---

# 6. First Rule of Performance Debugging

> **Don't guess. Measure.**

Bad approach:

```text
API slow
 ↓
Maybe MongoDB
 ↓
Restart MongoDB
```

Better:

```text
API slow
 ↓
Check latency
 ↓
Check error rate
 ↓
Check traffic
 ↓
Check CPU
 ↓
Check memory
 ↓
Check disk
 ↓
Check network
 ↓
Check database
 ↓
Find evidence
```

This is much more reliable.

# 7. Performance Investigation Workflow ⭐⭐⭐⭐⭐

Use this:

```text
1. Confirm the problem
       ↓
2. Measure impact
       ↓
3. Establish timeline
       ↓
4. Check recent changes
       ↓
5. Check golden signals
       ↓
6. Check system resources
       ↓
7. Check application
       ↓
8. Check dependencies
       ↓
9. Form hypothesis
       ↓
10. Test hypothesis
       ↓
11. Mitigate
       ↓
12. Verify
```

Memorize this workflow.

# 8. Step 1 — Confirm the Problem

Suppose someone says:

> "The website is slow."

Don't immediately start changing things.

First ask:

```text
Which endpoint?
Which users?
Which region?
When did it start?
How slow?
Is it always slow?
Is it intermittent?
```

You need to turn:

```text
"The website is slow."
```

into measurable information.

---

# 9. Step 2 — Measure Impact

Suppose you discover:

```text
Normal latency:
200 ms

Current latency:
2.5 seconds
```

Now you have evidence.

Maybe:

```text
p50 = 400ms
p95 = 2.5s
p99 = 5s
```

This is much more useful than:

```text
"Feels slow."
```

---

# 10. Percentiles Matter ⭐⭐⭐⭐⭐

Don't only look at average latency.

Consider:

```text
Requests:
100ms
110ms
120ms
130ms
5000ms
```

Average:

```text
≈ 1 second
```

But most requests were fast.

Percentiles give you a better picture.

---

# 11. p50

p50 means:

> 50% of requests are faster than this value.

It's approximately the median.

Example:

```text
p50 = 150ms
```

Half of requests are faster than 150ms.

---

# 12. p95

p95 means:

> 95% of requests are faster than this value.

Example:

```text
p95 = 800ms
```

This means roughly:

```text
95% → ≤ 800ms
5%  → > 800ms
```

This is often much more useful for user experience.

---

# 13. p99

p99 means:

> 99% of requests are faster than this value.

Example:

```text
p99 = 4 seconds
```

This reveals the slowest portion of traffic.

Useful for detecting:

```text
Rare slow requests
Database problems
GC pauses
Network issues
Lock contention
```

---

# 14. Average vs Percentiles

Use:

```text
Average
```

for broad understanding.

Use:

```text
p50
p95
p99
```

for latency analysis.

A production dashboard should ideally show:

```text
p50 latency
p95 latency
p99 latency
```

rather than only:

```text
average latency
```

Ask:

```text
When did the problem begin?
```

Suppose:

```text

10:17 → latency increases
```

That's strong evidence.

Timeline:

```text
10:00
Healthy
  ↓
10:15
Deployment
  ↓
10:17
Latency ↑
  ↓
10:20
Errors ↑
```

Now your deployment becomes a strong hypothesis.

A common production pattern is:

```text

      ↓

```

# 17. Step 4 — Check Traffic

Suppose API latency increases.

First check:

```text
Traffic
```

Maybe:

```text
Normal:
100 requests/sec

Current:
1000 requests/sec
```

Then the increased latency might be caused by traffic growth.

Architecture:

```text
Traffic ↑
   ↓
CPU ↑
   ↓
Queue ↑
   ↓
Latency ↑
```

This is very different from:

```text
Traffic normal
CPU normal
Latency ↑
```

---

# 18. Step 5 — Check Errors

Look at:

```text
HTTP 4xx
HTTP 5xx
Timeouts
Database errors
Connection failures
```

Suppose:

```text
Latency ↑
5xx ↑
```

That's more concerning than:

```text
Latency ↑
5xx normal
```

Because users may be experiencing both:

```text
Slow responses
+
Failed requests
```

---

# 19. Step 6 — Check CPU

Linux:

```bash
top
```

or:

```bash
htop
```

or:

```bash
btop
```

Prometheus:

```promql
100 * (
  1 - avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  )
)
```

Look for:

```text
CPU > 90%
```

But remember:

> High CPU is a signal, not a root cause.

---

# 20. CPU Bottleneck

A CPU bottleneck can look like:

```text
CPU ↑
Latency ↑
Queue ↑
Throughput ↓
```

Possible causes:

```text
Expensive algorithm
Infinite loop
High traffic
JSON processing
Encryption
Compression
Regex processing
CPU-heavy dependency
```

For Node.js specifically:

```text
CPU-heavy JavaScript
```

can block the event loop.

---

# 21. Node.js CPU Example

Imagine:

```javascript
for (let i = 0; i < 10000000000; i++) {
    // expensive work
}
```

The Node.js process may consume a CPU core heavily.

During that time:

```text
Request A
   ↓
Heavy computation
   ↓
Event loop blocked
   ↓
Request B waits
Request C waits
Request D waits
```

Now latency increases.

---

# 22. Event Loop Bottleneck

This is especially important for MERN developers.

Node.js uses an event-driven architecture.

Conceptually:

```text
Requests
   ↓
Event Loop
   ↓
JavaScript execution
```

If JavaScript performs long synchronous CPU work:

```text
Event Loop
    ↓
BLOCKED
```

Then unrelated requests can become slow.


Possible causes:


# 24. Memory Leak Pattern

A classic pattern:

```text

```

This is different from:

```text

70%
40%
75%
45%
70%
```

The second pattern may simply reflect workload.

# 28. Disk Bottleneck

Disk problems are often confused with disk capacity.

Two different questions:

### Capacity

```text
How much space remains?
```

### Performance

```text
How fast can we read/write?
```

---

# 29. Disk Capacity Problem

Check:

```bash
df -h
```

Example:

```text
Filesystem
/dev/nvme0n1p2
85% used
```

Then:

```bash
du -sh /*
```

or more targeted:

```bash
sudo du -xh /var | sort -h | tail
```

This helps locate large directories.

---

# 30. Disk I/O Bottleneck

A server may have:

```text
Disk = 30% full
```

but still be slow because disk I/O is overloaded.

Check:

```bash
iostat
```

or:

```bash
iostat -xz 1
```

Depending on your installed `sysstat` tools.

Look for:

```text
High utilization
High await
High I/O activity
```

---

# 31. What Does `await` Mean?

In storage performance tools, `await` broadly represents:

> The time an I/O operation spends waiting/being serviced.

High latency can indicate:

```text
Slow storage
Overloaded disk
Contention
```

Don't interpret one metric in isolation.


Possible hypothesis:

```text

```

Then investigate:

```text

```

# 33. Network Bottleneck

A network bottleneck can produce:

```text
Latency ↑
Timeouts ↑
Throughput ↓
Connections ↑
```

Check:

```bash
ss -s
```

and:

```bash
ss -tan
```

You can also use:

```bash
nload
```

and:

```bash

```

---

# 34. Network Latency vs Network Throughput

These are different.

### Latency

```text
How long does communication take?
```

### Throughput

```text
How much data can move per second?
```

You might have:

```text
Low traffic
High latency
```

or:

```text
High traffic
Low latency
```

Don't confuse them.

# 35. Test Connectivity

Basic:

```bash
ping example.com
```

But remember:

> Ping tests ICMP, not your application protocol.

For HTTP:

```bash
curl -I https://example.com
```

For more detailed timing:

```bash
curl -w "\nDNS: %{time_namelookup}\nConnect: %{time_connect}\nStart Transfer: %{time_starttransfer}\nTotal: %{time_total}\n" \
  -o /dev/null \
  -s https://example.com
```

This can help separate:

```text
DNS
Connection
Server response
Total time
```

---

# 36. Application Latency Breakdown

```text
Total = 2.0s
```

and:

```text

```

```text

```

# 38. Missing Database Index

Imagine:

```javascript
User.find({ email })
```

without an appropriate index.

MongoDB may need to inspect many documents.

Conceptually:

```text
1,000,000 documents
       ↓
Search through many documents
       ↓
Slow query
```

With an appropriate index:

```text
Index
 ↓
Find matching data
 ↓
Much faster
```

This is why database observability matters.

---

# 39. N+1 Query Problem

Suppose:

```text
Fetch 100 users
```

then:

```text
For each user:
    Fetch profile
```

You might accidentally create:

```text
1 query
+
100 queries
=
101 queries
```

This can dramatically increase latency.

Observability can reveal:

```text
Request latency ↑
DB query count ↑
```

# 40. Connection Pool Exhaustion

Suppose your Node.js application has:

```text
MongoDB connection pool
```

and all connections are busy.

New requests may wait.

Then:

```text
Connection pool full
      ↓
Requests wait
      ↓
Latency ↑
      ↓
Timeouts ↑
```

This is a classic backend bottleneck.

```text
 ↓

 ↓

```

If workers can't process jobs quickly enough:

```text

```

# 43. The USE Method

A useful performance-analysis technique is the **USE Method**:

```text
Utilization
Saturation
Errors
```

For each resource ask:

### Utilization

How busy is it?

### Saturation

Is work waiting because it's overloaded?

### Errors

Are failures occurring?

---

# 44. USE Method Example

For CPU:

```text
Utilization → 95%
Saturation  → high load
Errors      → none
```

Potential CPU bottleneck.

For disk:

```text
Utilization → 95%
Saturation  → high I/O wait
Errors      → none
```

Potential storage bottleneck.

---

# 45. RED Method

For services, another useful model is **RED**:

```text
Rate
Errors
Duration
```

### Rate

Requests per second.

### Errors

Failed requests.

### Duration

Request latency.

For your Node.js API:

```text
Rate      → 500 req/s
Errors    → 5%
Duration  → p95 800ms
```

This is an excellent application dashboard.

---

# 46. RED + USE

Together:

```text
Application:
RED

Infrastructure:
USE
```

So:

```text
API
├── Rate
├── Errors
└── Duration

Server
├── Utilization
├── Saturation
└── Errors
```

This gives you a strong troubleshooting framework.

# 49. Find the Root Cause

Further investigation reveals:

```text
A marketing campaign
```

caused a huge traffic spike.

Now:

```text
Traffic spike
   ↓
Node.js CPU saturation
   ↓
Request queue
   ↓

```

```text
Unexpected traffic increase
```

```text

```

These are related but not identical.


# 54. Timeout Chains

Imagine:

```text
Browser
 ↓ 30 sec timeout
Nginx
 ↓ 29 sec timeout
Node.js
 ↓ 28 sec timeout
MongoDB
 ↓ 27 sec timeout
```

A slow dependency can cause a chain of waiting.

This is why good systems use:

```text
Timeouts
Retries
Circuit breakers
Bulkheads
```

You'll encounter these concepts in advanced backend engineering.

---

# 55. Retry Storms

Be careful with retries.

Suppose a dependency becomes slow:

```text
Request
 ↓
Dependency timeout
 ↓
Retry
 ↓
Dependency timeout
 ↓
Retry
```

Now traffic to the already struggling dependency increases.

You get:

```text
Failure
 ↓
Retries
 ↓
More traffic
 ↓
More failure
 ↓
More retries
```

This can become a **retry storm**.


This connects your logging lessons with performance analysis.

```text
     ↓

     ↓
```

```text
     ↓
```


# 60. Performance Bottleneck: Concurrency

```text

```

# 61. File Descriptors

Linux services have limits on open file descriptors.

A process may need descriptors for:

```text
Sockets
Files
Database connections
Pipes
```

Too many open connections can cause problems.

Check:

```bash
ulimit -n
```

And inspect processes with tools such as:

```bash
lsof -p <PID>
```

if `lsof` is installed.

# 64. `vmstat` During an Incident

Run:

```bash

```

Watch:

```text

so
bi
bo

```

Useful signals include:

```text

so → swap out
bi → blocks in
bo → blocks out
wa → I/O wait
```

High `wa` can suggest storage-related waiting.


# 69. `sar`

# 70. Performance Investigation Table

|Signal|Possible Problem|
|---|---|
|CPU high|CPU-bound workload|
|Memory rising|Memory leak|
|Swap rising|Memory pressure|
|Disk full|Capacity issue|
|Disk I/O high|Storage bottleneck|
|Network traffic high|Traffic spike|
|Network latency high|Network/dependency issue|

# 71. Correlation Is Not Causation

Suppose:

```text
CPU ↑
Latency ↑
```

You cannot immediately say:

> CPU caused latency.

Maybe:

```text
Traffic ↑
   ↓
CPU ↑
   ↓
Latency ↑
```

In that case:

```text
Traffic
```

was the initial cause.

CPU was an intermediate effect.

Always investigate the chain.

# 76. Five Whys

A simple RCA technique:

### Problem:

```text

```

### Why 1?

```text
Database queries became slow.
```

### Why 2?

```text
Queries performed collection scans.
```

### Why 3?

```text
Required index was missing.
```

### Why 4?

```text
New query was introduced without an index.
```

### Why 5?

```text

```

```text

```

Not just:


# 79. Caching as a Bottleneck Solution

Suppose:

```text
Database
 ↓
1000 identical queries/sec
```

Caching could reduce:

```text
1000 queries
```

to:

```text
100 database queries
+
900 cache hits
```

But caching introduces complexity:

```text
Cache invalidation
Stale data
Memory usage
Cache stampede
```

So don't add caching blindly.

# 80. Rate Limiting as a Protection Mechanism

If traffic suddenly spikes:

```text
10,000 requests/sec
```

and your server can handle:

```text
2,000 requests/sec
```

without protection:

```text
System overload
```

Rate limiting can protect the service:

```text
Incoming traffic
      ↓
Rate limiter
      ↓
Allowed traffic
      ↓
Application
```

This doesn't fix the root cause, but it can prevent cascading failure.

# 89. Interview Question ⭐⭐⭐⭐⭐

### "How would you investigate a slow API?"

A strong answer:

> First I'd confirm the latency increase and determine which endpoints and users are affected. I'd check p50, p95 and p99 latency, request rate and error rate. Then I'd correlate the timing with recent deployments or configuration changes. I'd inspect CPU, memory, disk and network metrics, followed by database latency, connection pools and external dependencies. I'd use logs and application metrics to narrow down the slow component, form a hypothesis, test it, mitigate the issue, and then verify that latency has returned to normal.

That's a strong backend/SRE interview answer.

---

# 90. Interview Question

### "How do you know CPU is the bottleneck?"

Don't say:

> CPU is 90%, therefore CPU is the bottleneck.

Instead:

> I'd correlate CPU utilization with latency, throughput, load, process-level CPU usage and application behavior. If CPU saturation increases while latency rises and throughput becomes constrained, that provides stronger evidence of CPU being the bottleneck.

Much stronger answer.

# 92. Interview Question

### "What is the difference between RED and USE?"

> RED is primarily for services: Rate, Errors and Duration. USE is primarily for resources: Utilization, Saturation and Errors.

Memorize this.

```text
RED → Services
USE → Resources
```

---

# 93. Interview Question

### "Why is p95 latency useful?"

> p95 shows the latency experienced by the slower portion of requests and is more informative than average latency when a small percentage of requests are extremely slow.

# 94. Interview Question

### "What is a bottleneck?"

> A bottleneck is a component or resource that limits the performance or throughput of the overall system.
