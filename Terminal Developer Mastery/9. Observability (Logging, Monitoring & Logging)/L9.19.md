# Lesson 9.19 — Production Incident Debugging 🚨🔧

**Module:** 9 — Observability  
**Part:** 6 — Performance Analysis  
**Lesson:** 9.19  
**Level:** Intermediate → Advanced

## 🎯 Goal

This lesson brings together almost everything you've learned in Module 9:

```text
Logs
  +
Metrics
  +
Monitoring
  +
Alerts
  +
Performance analysis
  ↓
Production incident debugging
```

The goal isn't just to know commands.

The goal is to develop the mindset:

> **When production breaks, stay calm, collect evidence, reduce impact, find the cause, and verify recovery.**

---

# 1. What Is a Production Incident?

A production incident is an unexpected event that negatively affects your live system.

Examples:

```text
API unavailable
Database unavailable
High latency
High error rate
Server crash
Disk full
Memory exhaustion
Network failure
Security issue
Queue backlog
External service failure
```

For example:

```text
Users
  ↓
Nginx
  ↓
Node.js API
  ↓
MongoDB
```

If MongoDB becomes unavailable:

```text
MongoDB ❌
    ↓
Node.js requests fail
    ↓
5xx errors increase
    ↓
Users see errors
```

That's a production incident.

---

# 2. Incident vs Bug

A bug is:

> A defect in software.

An incident is:

> An operational event causing actual impact.

A bug may exist for months without causing an incident.

Example:

```text
Bug:
Incorrect edge-case validation
```

Incident:

```text
Production API returns 500
to thousands of users.
```

The bug may be the cause, but the incident is the operational event.

---

# 3. The Incident Lifecycle ⭐⭐⭐⭐⭐

A mature incident process looks like:

```text
Detection
   ↓
Triage
   ↓
Investigation
   ↓
Mitigation
   ↓
Recovery
   ↓
Verification
   ↓
Root Cause Analysis
   ↓
Postmortem
   ↓
Prevention
```

Memorize this flow.

---

# 4. Detection

An incident can be detected by:

```text
Alert
User report
Monitoring dashboard
Log anomaly
Health check
Support team
Engineer observation
```

Ideally:

```text
Monitoring
   ↓
Alert
   ↓
Engineer
```

rather than:

```text
Users
   ↓
"We can't use the application!"
```

Good observability helps you detect problems before users report them.

---

# 5. Example Alert

Suppose Alertmanager sends:

```text
🚨 CRITICAL

HighAPIErrorRate

Service: api
Environment: production

5xx error rate:
18%

Duration:
10 minutes
```

Don't immediately restart everything.

First:

> **Confirm the incident.**

---

# 6. Step 1 — Confirm the Incident

Check:

```text
Is the alert real?
Is it still happening?
Who is affected?
What functionality is affected?
```

Open your Grafana dashboard.

Look at:

```text
Traffic
Errors
Latency
CPU
Memory
Database
```

---

# 7. Step 2 — Determine Blast Radius

**Blast radius** means:

> How much of the system or how many users are affected?

Ask:

```text
Is one endpoint affected?
One service?
One server?
One region?
All users?
Only some users?
```

Example:

```text
GET /products       ✅
GET /users          ✅
POST /orders        ❌
POST /payments      ❌
```

This is very different from:

```text
Entire API unavailable
```

---

# 8. Severity

You need to determine how serious the incident is.

Example:

### Low

```text
Minor feature degraded
Few users affected
Workaround exists
```

### Medium

```text
Important functionality degraded
Many users affected
```

### Critical

```text
Core application unavailable
Large percentage of users affected
Revenue/security impact
No workaround
```

The exact naming differs between organizations.

---

# 9. Don't Focus on Blame

During an incident, avoid:

```text
"Who deployed this?"
"Who wrote this code?"
"Who caused this?"
```

Instead ask:

```text
"What happened?"
"What evidence do we have?"
"How do we reduce impact?"
```

Blame slows down incident response.

---

# 10. Step 3 — Establish a Timeline

This is one of the most powerful incident-debugging techniques.

Create:

```text
Time
Event
Evidence
```

Example:

|Time|Event|
|---|---|
|10:00|System healthy|
|10:12|Deployment started|
|10:15|Deployment completed|
|10:17|Latency increased|
|10:18|5xx increased|
|10:20|Alert fired|
|10:23|Investigation started|
|10:30|Rollback started|
|10:32|Errors decreasing|
|10:35|Service recovered|

Now you have a story.

---

# 11. Why Timeline Matters

Suppose:

```text
Deployment
   ↓
5 minutes later
   ↓
Errors increase
```

That's strong evidence.

Compare:

```text
Errors increase
   ↓
30 minutes later
   ↓
Deployment
```

The deployment is much less likely to be the original cause.

Timeline helps separate:

```text
Cause
```

from:

```text
Effect
```

---

# 12. Step 4 — Check Recent Changes

One of your first questions should be:

> **What changed recently?**

Check:

```text
Code deployment
Configuration
Environment variables
Database migration
Infrastructure
Dependencies
DNS
Certificates
Firewall
Feature flags
Traffic
```

A useful investigation command for Git-based deployment systems is to inspect recent commits:

```bash
git log --oneline --decorate -10
```

But don't assume the latest commit is automatically responsible.

You need evidence.

# 13. Step 5 — Check Application Health

For your Node.js backend, check:

```text
Health endpoint
Process status
Logs
Error rate
Latency
Request rate
```

For example:

```bash
curl -i http://localhost:5000/health
```

If behind Nginx:

```bash
curl -i http://localhost/health
```

You might see:

```text
HTTP/1.1 200 OK
```

or:

```text
HTTP/1.1 500 Internal Server Error
```

---

# 14. Health Check ≠ Full Health

Suppose:

```text
GET /health
```

returns:

```text
200 OK
```

but:

```text
POST /orders
```

returns:

```text
500
```

The server process is alive, but the application isn't fully healthy.

This is why health checks should be designed carefully.

---

# 15. Liveness vs Readiness

Two useful concepts:

### Liveness

> Is the application alive?

Example:

```text
Process running
```

### Readiness

> Is the application ready to serve traffic?

Example:

```text
Database connection available
Required dependencies healthy
Application initialized
```

You might have:

```text
Liveness  → 200
Readiness → 503
```

This can be very useful in orchestrated environments.



# 18. Step 7 — Check Logs

During an incident, don't just read random log lines.

Search for:

```text
ERROR
WARN
timeout
connection
refused
failed
exception
fatal
```

For example:

```bash
journalctl -u myapp --since "15 minutes ago"
```

Or:

```bash
journalctl -u nginx --since "15 minutes ago"
```

This gives you a focused time window.

---

# 19. Search Application Logs

If your app writes logs to a file:

```bash
grep -i "error" app.log
```

Recent errors:

```bash
tail -n 200 app.log | grep -i "error"
```

But structured JSON logs are even better because they can be queried by:

```text
timestamp
level
service
request_id
status
route
```

---

# 20. Correlation IDs ⭐⭐⭐⭐⭐

Suppose a request has:

```text
request_id=abc123
```

You can search:

```bash
grep "abc123" app.log
```

Now you might find:

```text
Request received
Database query started
Database timeout
Request failed
```

This is incredibly useful.

Instead of searching millions of log lines, you follow one request.

Now switch from logs to metrics.

Look at:

```text
Request rate
Error rate
Latency

```

> Is the problem isolated or systemic?

Suppose you see:


# 23. Another Example

Suppose:

```text
Traffic       ↑ 500%
CPU           ↑ 98%
Memory        ↑
Latency       ↑

```

Now the pattern is very different.

Likely:

```text

    ↓

    ↓
Slow responses
    ↓

```

# 24. Step 9 — Check Processes

Run:

```bash
ps aux --sort=-%cpu | head
```

and:

```bash

```

Or:

```bash

```

Look for:

```text

Zombie processes
```

# 25. Check Process Tree

Use:

```bash

```

You might discover:

```text

 └── node
      ├── worker
      ├── worker
      └── child process
```

This helps understand process relationships.

# 26. Step 10 — Check Network

Check listening services:

```bash
sudo ss -lntp
```

You might expect:

```text
:80
:443
:5000
:9100
```

If your Node.js app should listen on:

```text
5000
```

but nothing is listening:

```text
❌ Node.js isn't accepting connections.
```

---

# 27. Check Active Connections

```bash
ss -tan
```

Or:

```bash
ss -s
```

Look for:

```text
Established
TIME-WAIT
CLOSE-WAIT
Listening
```

Unexpected connection growth can indicate:

```text
Traffic spike
Connection leak
Slow clients
Dependency problems
```

---

# 28. `CLOSE_WAIT` Warning

Large numbers of:

```text
CLOSE_WAIT
```

can sometimes indicate that the application isn't properly closing sockets.

This can lead to resource exhaustion.

But again:

> Don't conclude "CLOSE_WAIT = bug" without investigating context.

# 29. Step 11 — Check Database

For a MERN backend:

```text
Node.js
   ↓
MongoDB
```

Check:

```text
Connection health
Query latency
Connections
CPU
Memory
Disk I/O
Slow queries
```

If your API is slow but:

```text
Node CPU = normal
Node memory = normal
```

database latency becomes an important suspect.

# 30. Database Connection Failure

Application logs might show:

```text
MongoServerSelectionError
```

or:

```text
connection timeout
```

Then:

```text
Node.js
   ↓
MongoDB
   X
```

Check whether MongoDB is:

```text
Running
Reachable
Accepting connections
```

# 31. Test Database Connectivity

From your server, test the database connection using the appropriate MongoDB client/tool for your environment.

The goal is to distinguish:

```text
Application problem
```

from:

```text
Database/network problem
```

For MongoDB deployments, you may also inspect database-specific metrics and logs.

---

# 32. Step 12 — Check External Dependencies

Your application might depend on:

```text
Payment API
Email provider
OAuth provider
AI API
Cloud storage
Maps API
```

Suppose:

```text
Payment API latency
500ms → 8s
```

Your application may become slow even though:

```text
CPU = 30%
Memory = 40%
```

This is why dependency observability is important.

---

# 33. Dependency Failure Pattern

```text
External API
     ↓
Slow
     ↓
Node.js waits
     ↓
Connections occupied
     ↓
Requests queue
     ↓
Latency increases
     ↓
Timeouts
```

A small external problem can become a large application problem.

---

# 34. Step 13 — Form a Hypothesis

At this point, don't just collect information forever.

Create a hypothesis.

Example:

> "The API latency increase is caused by MongoDB query latency after the latest deployment."

That's testable.

---

# 35. Good Hypothesis

A good hypothesis has:

```text
Cause
+
Evidence
+
Expected result
```

Example:

```text
Cause:
Missing database index

Evidence:
DB query latency increased

Expected result:
Adding the index should reduce query latency
```

---

# 36. Bad Hypothesis

```text
"Something is wrong with the server."
```

Too vague.

Or:

```text
"MongoDB is definitely broken."
```

No evidence.

Better:

```text
"MongoDB query latency increased from 30ms to 1.5s immediately after deployment, and API latency increased at the same time."
```

That's evidence-based.

---

# 37. Step 14 — Test the Hypothesis

Suppose:

```text
Hypothesis:
Latest deployment caused the problem.
```

Possible test:

```text
Rollback
```

If after rollback:

```text
Latency ↓
Errors ↓
```

then your hypothesis becomes much stronger.

---

# 38. But Be Careful With Tests

Never experiment recklessly in production.

Bad:

```text
Delete database index
Restart random services
Change kernel settings
Kill processes
```

without understanding the consequences.

Prefer:

```text
Safe observation
Controlled rollback
Known mitigation
Staging reproduction
```

---

# 39. Step 15 — Mitigate the Incident

Your first objective is:

> **Reduce user impact.**

Possible mitigations:

```text
Rollback deployment
Scale instances
Disable feature
Rate-limit traffic
Fail over
Restart unhealthy process
Increase capacity
Remove bad configuration
```

Choose the safest effective action.

---

# 40. Rollback Example

Suppose:

```text
v1 → healthy
v2 → errors
```

If you're confident:

```text
Rollback v2
```

Then:

```text
v1
 ↓
Errors decrease
 ↓
Latency normal
```

Now users are protected.

You can investigate v2 afterward.

---

# 41. Restart vs Rollback

Don't confuse them.

### Restart

```text
Process
 ↓
Stop
 ↓
Start
```

Useful for:

```text
Temporary process issue
Deadlock
Corrupted runtime state
Memory problem
```

### Rollback

```text
New version
 ↓
Old version
```

Useful when:

```text
Recent deployment introduced the issue.
```

A restart won't fix a bad release.

---

# 42. Step 16 — Verify Recovery

Never say:

> "I think it's fixed."

Measure it.

Check:

```text
Error rate
Latency
Traffic
CPU
Memory
Database
Alerts
Logs
```

Example:

```text
Before:

5xx = 20%
p95 = 4s

After:

5xx = 0.5%
p95 = 250ms
```

That's evidence of recovery.

---

# 43. Recovery Timeline

```text
Incident
  ↓
Mitigation
  ↓
Metrics improve
  ↓
Alerts resolve
  ↓
Logs normalize
  ↓
Users recover
```

Don't close the incident immediately after the first metric improves.

Watch for recurrence.

---

# 44. Step 17 — Keep Monitoring

Suppose you roll back.

For the next period, monitor:

```text
10–30 minutes
```

or whatever is appropriate for your service.

Watch:

```text
Errors
Latency
Traffic
CPU
Memory
Database
```

You want:

```text
Stable
```

not merely:

```text
Temporarily better
```

# 45. Incident Communication

During serious incidents, communication matters.

A simple update:

```text
10:20 — Incident identified
10:25 — API errors confirmed
10:30 — Latest deployment suspected
10:32 — Rollback started
10:35 — Error rate decreasing
10:40 — Service recovered
10:50 — Monitoring stable
```

This keeps everyone aligned.

---

# 46. Don't Over-Communicate Noise

Avoid sending:

```text
"Maybe database?"
"Could be network?"
"I think CPU?"
"Trying something."
```

Instead communicate:

```text
"Evidence currently points to MongoDB query latency.
We're validating this hypothesis."
```

Be concise and evidence-based.

# 47. Incident Commander

For larger incidents, one person may act as:

> **Incident Commander**

Their job is to coordinate the response.

They don't necessarily fix the bug themselves.

They focus on:

```text
Priorities
Communication
Delegation
Decision-making
Incident progress
```

---

# 48. Incident Roles

In mature teams, responsibilities can be separated:

```text
Incident Commander
        │
   ┌────┼────┐
   ▼    ▼    ▼
Investigator
Communicator
Operations
```

Small teams may have one person doing everything.

But as systems grow, separating responsibilities becomes valuable.

During the incident, record:

```text
Timestamp
Action
Result
Evidence
Decision
```

Example:

```text
10:25
Checked MongoDB latency.
```

# 50. Root Cause Analysis

After recovery, ask:

> Why did this happen?

Not:

> Who caused it?

A good RCA identifies:

```text
Technical cause
Contributing factors
Detection gaps
Process gaps
Prevention
```

---

# 51. Example RCA

### Incident

API latency increased to 4 seconds.

### Root cause

A newly deployed endpoint executed an unindexed MongoDB query.

### Contributing factor

Production dataset was much larger than staging.

### Detection gap

No database query latency alert existed.

### Prevention

```text
Add index
Add query performance testing
Add DB latency metrics
Add alert
Improve staging data volume
```

This is a strong postmortem.

---

# 52. Five Whys Example

### Why was the API slow?

MongoDB queries were slow.

### Why were queries slow?

The query scanned a large collection.

### Why?

There was no suitable index.

### Why?

The new endpoint was deployed without query-performance validation.

### Why?

The testing environment didn't represent production-scale data.

Root issue:

```text
Testing process
```

not merely:

```text
Missing index
```

---

# 53. Blameless Postmortem ⭐⭐⭐⭐⭐

A good engineering culture focuses on:

```text
Systems
Processes
Conditions
Failures
```

rather than:

```text
Person X made mistake Y.
```

Why?

Because people make mistakes.

Good systems should make dangerous mistakes:

```text
Harder to make
Easy to detect
Easy to recover from
```

---

# 54. What Goes Into a Postmortem?

A useful postmortem contains:

```text
1. Summary
2. Impact
3. Timeline
4. Detection
5. Root cause
6. Contributing factors
7. Mitigation
8. Resolution
9. What went well
10. What went poorly
11. Action items
```

---

# 55. Example Postmortem

## Summary

A production API experienced elevated latency for 18 minutes.

## Impact

```text
30% of requests exceeded 2 seconds.
5% returned 5xx responses.
```

## Root Cause

An unindexed database query was introduced in the latest deployment.

## Mitigation

Rolled back the deployment.

## Permanent Fix

Added the required database index and performance test.

---

# 56. Action Items

Bad:

```text
Improve database.
```

```text

```

Another:

```text
Add production-scale query performance test.
Owner: QA
Priority: Medium
```

Let's simulate a realistic outage.

```text
v2.4.0
```

# 62. Check Logs

Node.js logs show:


```text
Application
    ↓
MongoDB
    ↓
```

# 63. Check Database

Database metrics show:

# 64. Find the Query

Logs reveal:

```text
GET /api/orders
```

is executing a new query.

Suppose the query is:

```javascript
Order.find({
    userId,
    status
});
```

No appropriate compound index exists.

---

# 65. Immediate Mitigation

Because the issue started immediately after deployment:

```text
Rollback v2.4.0
```

After rollback:

```text
MongoDB latency ↓
API latency ↓
5xx ↓
```

Incident mitigated.

---

# 66. Permanent Fix

Now create the appropriate index based on actual query patterns.

For example, conceptually:

```javascript
db.orders.createIndex({
    userId: 1,
    status: 1
});
```

Then:

```text
Performance test
   ↓
Deploy
   ↓
Monitor
```

The exact index should be chosen based on your real query shape and MongoDB's query plans.

That's root-cause thinking.

# 70. The 10-Minute Incident Checklist

When something breaks, use:

```text
1. 🚨 What alert fired?
2. 👥 Who is affected?
3. 📈 What metrics changed?
4. 🕐 When did it start?
5. 🚀 What changed recently?
6. 📜 What do logs say?
7. 🖥️ Are resources saturated?
8. 🗄️ Are dependencies healthy?
9. 🔬 What is my hypothesis?
10. 🛠️ What is the safest mitigation?
```

Then:

```text
11. Verify recovery.
12. Document everything.
```

# 71. Don't Restart Everything

This is one of the most important lessons.

Bad:

```text
API slow
 ↓
Restart Nginx
 ↓
Restart Node
 ↓
Restart MongoDB
 ↓
Reboot server
```

Now you've destroyed valuable evidence.

Instead:

```text
Observe
 ↓
Collect evidence
 ↓
Identify suspect
 ↓
Mitigate carefully
```

Restart only when there's a reason.

# 72. Preserve Evidence

During an incident, useful evidence includes:

```text
Logs
Metrics
Deployment history
Configuration
Process state
Network state
Database metrics
Screenshots
Timeline
```

If you immediately restart everything, some evidence disappears.

This is especially important for difficult incidents.

# 73. Incident Severity and Response

A simple model:

```text
P1
Critical outage
Immediate response

P2
Major degradation
Urgent response

P3
Limited impact
Normal engineering response

P4
Minor issue
Backlog/investigation
```

Organizations may use different names.

The important idea is:

> **Response should match impact.**

# 74. When to Escalate

Escalate when:

```text
Impact is increasing
Root cause is unknown
Your permissions are insufficient
A critical dependency is involved
Security may be involved
You cannot safely mitigate
```

Asking for help is not failure.

In production engineering:

> **Fast escalation can reduce downtime.**

# 75. Incident Command Principle

During a serious incident:

```text
Stabilize first.
Understand second.
Optimize third.
```

For example:

```text
API is down
```

Don't start redesigning your entire architecture.

First:

```text
Restore service.
```

Then:

```text
Find root cause.
```

Then:

```text
Prevent recurrence.
```

# 77. The Scientific Method for Incidents

Incident debugging is surprisingly similar to science:

```text
Observe
 ↓
Question
 ↓
Hypothesis
 ↓
Prediction
 ↓
Test
 ↓
Evidence
 ↓
Conclusion
```

Example:

```text
Observation:
API latency increased.

Hypothesis:
Database query became slow.

Prediction:
Database latency should also increase.

Test:
Check database metrics.

Evidence:
DB latency increased from 30ms → 2s.

Conclusion:
Database is likely contributing to the incident.
```

This is much better than guessing.

# 78. Production Debugging Mindset ⭐⭐⭐⭐⭐

Always separate:

```text
Fact
```

from:

```text
Hypothesis
```

Example:

### Fact

```text
5xx increased from 1% to 15%.
```

### Hypothesis

```text
Database is causing the errors.
```

Don't present your hypothesis as fact until you've verified it.

This makes incident communication much clearer.

# 82. Interview Question ⭐⭐⭐⭐⭐

### "How would you debug a production API outage?"

Strong answer:

> First I'd confirm the alert and determine the blast radius. I'd check API health, request rate, error rate and latency, then correlate the incident timeline with recent deployments or configuration changes. I'd inspect application and Nginx logs, system resources, processes, network connections, database health and external dependencies. I'd form an evidence-based hypothesis, apply the safest mitigation such as rollback or failover, and verify recovery using metrics and logs. Afterward I'd perform root-cause analysis and create prevention actions.

---

# 83. Interview Question

### "What would you do first during a production incident?"

Good answer:

> First I would confirm the incident and assess its impact rather than immediately changing the system. I'd determine the affected services and users, inspect key metrics and logs, and establish when the problem started.

---

# 84. Interview Question

### "Why shouldn't you immediately restart the server?"

Because:

```text
You may:
Lose evidence
Hide the root cause
Cause additional downtime
Make debugging harder
```

Restarting can be a valid mitigation, but it should be an intentional decision.

---

# 85. Interview Question

### "What is a postmortem?"

> A postmortem is a structured review of an incident that documents its impact, timeline, root cause, response, and prevention actions so the organization can learn and reduce the chance of recurrence.

---

# 86. Interview Question

### "What is a blameless postmortem?"

> A blameless postmortem focuses on system conditions, processes and technical causes rather than blaming individuals for mistakes.

---

# 87. Interview Question

### "What is blast radius?"

> Blast radius describes the scope of impact from an incident, such as the number of affected users, services, regions or resources.

---

# 88. Interview Question

### "What is mitigation?"

> Mitigation is an action that reduces the impact of an incident, even if it doesn't permanently fix the root cause.

Example:

```text
Rollback
```

can mitigate an incident while the underlying bug is investigated later.

---

# 89. Interview Question

### "What is root cause?"

> The root cause is the underlying condition that led to the incident. A strong RCA also considers contributing factors and why existing detection or prevention mechanisms didn't stop the problem.
