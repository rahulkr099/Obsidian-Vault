# 1. What is a Linux Log?

A **log** is a record of something that happened on a system.

Linux continuously records events such as:

```text
User login
SSH connection
Service startup
Service failure
Kernel events
Authentication failures
Network events
Application errors
System warnings
```

For example:

```text
Aug 15 12:31:42 server sshd[1824]: Accepted password for rahul
```

This tells us:

```text
Date       → Aug 15
Time       → 12:31:42
Service    → sshd
Process ID → 1824
Event      → SSH login accepted
User       → rahul
```

Logs are essentially the **history of your server**.

---

# 2. Why Are Logs Important?

Imagine your Node.js application suddenly stops working.

A user tells you:

> "The website isn't working."

You could start randomly restarting things.

That's a bad approach.

Instead:

```text
User reports problem
       ↓
Check application
       ↓
Check service status
       ↓
Check logs
       ↓
Find error
       ↓
Understand cause
       ↓
Fix
```

Logs provide evidence.

---

# 3. Where Are Linux Logs Stored?

On most Linux systems, traditional log files are located under:

```bash
/var/log
```

Start by exploring it:

```bash
ls /var/log
```

For a more useful view:

```bash
ls -lah /var/log
```

You may see files and directories such as:

```text
alternatives.log
apt/
auth.log
boot.log
dpkg.log
kern.log
syslog
ufw/
```

The exact files depend on your Linux distribution and logging configuration.

---

# 4. Important `/var/log` Files

Here are some common ones you'll encounter on Debian/Ubuntu/Linux Mint systems.

|Log|Purpose|
|---|---|
|`/var/log/syslog`|General system activity|
|`/var/log/auth.log`|Authentication/login events|
|`/var/log/kern.log`|Kernel messages|
|`/var/log/dpkg.log`|Package management|
|`/var/log/apt/`|APT package operations|
|`/var/log/boot.log`|Boot-related information|
|`/var/log/ufw/`|UFW firewall logs|
|`/var/log/nginx/`|Nginx logs, if installed|

Your Linux Mint system may not have every file listed above, and modern systems also rely heavily on **systemd journal**, which we'll study in Lesson 9.3.

---

# 5. `ls` — Explore the Log Directory

Start with:

```bash
ls -lah /var/log
```

The `-l` gives detailed information.

The `-a` includes hidden entries.

The `-h` makes file sizes easier to read.

Example:

```text
-rw-r----- 1 syslog adm  25M Aug 15 12:30 syslog
-rw-r----- 1 syslog adm  12M Aug 15 12:20 auth.log
```

You can immediately see:

```text
permissions
owner
group
size
last modification
filename
```

---

# 6. Reading Logs with `cat`

For a small log:

```bash
cat /var/log/dpkg.log
```

But be careful.

Some logs can be **very large**.

Running:

```bash
cat /var/log/syslog
```

could dump thousands of lines into your terminal.

That's why interactive tools are usually better.

---

# 7. Reading Logs with `less`

Use:

```bash
less /var/log/syslog
```

This is one of the most useful commands for log analysis.

Inside `less`:

```text
↑ / ↓       Move
Space       Next page
b           Previous page
g           Beginning
G           End
/word       Search
n           Next match
N           Previous match
q           Quit
```

For example:

```text
/ERROR
```

searches for `ERROR`.

Then:

```text
n
```

moves to the next match.

---

# 8. `tail` — See the End of a Log

Very useful:

```bash
tail /var/log/syslog
```

By default, you get the last 10 lines.

You can request more:

```bash
tail -n 50 /var/log/syslog
```

Meaning:

> Show the last 50 lines.

---

# 9. `tail -f` — Follow a Log Live ⭐

This is extremely useful for backend development.

```bash
tail -f /var/log/syslog
```

Now the terminal waits for new log entries.

When something happens:

```text
new event
    ↓
log file changes
    ↓
terminal displays it
```

Stop with:

```text
Ctrl + C
```

This is useful when debugging a service while simultaneously performing an action.

---

# 10. Example: Watching Nginx Logs

If Nginx is installed:

```bash
sudo tail -f /var/log/nginx/access.log
```

Then open your website.

You might see:

```text
192.168.1.20 - - [15/Aug/2026:12:35:21 +0530] "GET / HTTP/1.1" 200 1842
```

You made a request.

Nginx recorded it.

---

# 11. `grep` — Search Logs 🔎

One of the most important skills in Linux troubleshooting is:

```bash
grep
```

For example:

```bash
grep "error" /var/log/syslog
```

This searches for lines containing `error`.

Case-insensitive:

```bash
grep -i "error" /var/log/syslog
```

This matches:

```text
error
Error
ERROR
```

---

# 12. Search for Multiple Things

You can search for terms such as:

```bash
grep -i "failed" /var/log/auth.log
```

or:

```bash
grep -i "warning" /var/log/syslog
```

or:

```bash
grep -i "connection" /var/log/syslog
```

This is extremely useful when troubleshooting.

---

# 13. Combine `grep` with `tail`

Suppose your application generates a huge log.

You can do:

```bash
tail -n 1000 /var/log/syslog | grep -i error
```

Meaning:

```text
Get last 1000 lines
       ↓
Search for errors
```

Another useful pattern:

```bash
tail -f /var/log/syslog | grep -i error
```

Now you see **new errors as they appear**.

This is a very useful debugging technique.

---

# 14. `grep -n`

The `-n` option displays line numbers.

```bash
grep -n "error" /var/log/syslog
```

Example:

```text
1842:Aug 15 12:40:01 server app[1234]: database error
1920:Aug 15 12:41:17 server app[1234]: connection error
```

Now you know exactly where the matching lines are.

---

# 15. `grep -E`

You can search for multiple patterns.

```bash
grep -Ei "error|failed|critical" /var/log/syslog
```

This means:

```text
error
OR
failed
OR
critical
```

Very useful during incident investigation.

---

# 16. Searching by Date

Suppose you're investigating today's problems.

You might search:

```bash
grep "Aug 15" /var/log/syslog
```

Or:

```bash
grep "Aug 15.*error" /var/log/syslog
```

The exact approach depends on the log format.

Later, `journalctl` will give us much better time-based filtering.

---

# 17. Understanding a Log Line

Consider:

```text
Aug 15 12:45:21 server nginx[2341]: 192.168.1.5 - "GET /api/users HTTP/1.1" 500
```

Break it down:

```text
Aug 15
   ↓
Date

12:45:21
   ↓
Time

server
   ↓
Hostname

nginx
   ↓
Service

[2341]
   ↓
Process ID

GET /api/users
   ↓
Request

500
   ↓
HTTP error
```

This is why understanding log structure matters.

# 18. Common Log Levels

Applications often use levels such as:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

Think of them as severity levels.

### DEBUG

Detailed information useful during development.

```text
DEBUG User object loaded
```

### INFO

Normal system activity.

```text
INFO Server started on port 3000
```

### WARN

Something unusual but not necessarily a failure.

```text
WARN Database connection pool is 80% full
```

### ERROR

Something failed.

```text
ERROR MongoDB connection failed
```

### FATAL

A serious error that may cause the application to stop.

```text
FATAL Unable to initialize database
```

We'll use these concepts when we build structured application logging.

# 19. Authentication Logs 🔐

One especially important log is:

```bash
/var/log/auth.log
```

It contains authentication-related events on systems that use this traditional log.

For example:

```bash
sudo grep -i "failed" /var/log/auth.log
```

You might find:

```text
Failed password for invalid user test
Failed password for root
```

This can indicate:

- Wrong passwords
    
- Automated login attempts
    
- Brute-force attempts
    
- Misconfigured services
    

Security monitoring will become much more important in **Module 10**.

---

# 20. Kernel Logs

Kernel-related information can traditionally be found in:

```bash
/var/log/kern.log
```

Depending on your system configuration, you can also inspect kernel messages with:

```bash
dmesg
```

For example:

```bash
dmesg | tail
```

Kernel logs can help investigate:

```text
Hardware problems
Drivers
USB devices
Memory issues
Network devices
Disk problems
```

Be aware that modern Linux systems increasingly expose this information through the systemd journal as well.

---

# 21. Package Management Logs

On Debian-based systems:

```bash
/var/log/dpkg.log
```

records package management operations.

For example, after installing a package:

```bash
sudo apt install nginx
```

package-related activity can be recorded in these logs.

You can inspect:

```bash
less /var/log/dpkg.log
```

APT also maintains logs under:

```bash
/var/log/apt/
```

Since you just completed the Nginx module, this is particularly useful.

# 24. Log Formats

Different applications produce different formats.

### Plain text

```text
Server started on port 3000
```

Simple, but difficult to process automatically.

### Traditional structured text

```text
2026-08-15 12:30:01 INFO Server started
```

Better.

### JSON

```json
{
  "timestamp": "2026-08-15T12:30:01Z",
  "level": "info",
  "message": "Server started",
  "service": "user-api"
}
```

Much easier for log aggregation systems to process.

We'll study structured JSON logging in **Lesson 9.5**.

---

# 25. Important Rule: Don't Log Everything

A beginner may think:

> "I'll log everything."

That's usually a mistake.

Too many logs create:

```text
Huge storage usage
       ↓
Higher costs
       ↓
Harder searching
       ↓
More noise
       ↓
Important errors get buried
```

Good observability means:

> **Collect useful information, not unlimited information.**

# 26. Production Example 🚨

Imagine your Node.js API suddenly returns:

```text
502 Bad Gateway
```

Users report:

> "The website is down."

You investigate.

### Step 1 — Check Nginx

```bash
sudo tail -n 50 /var/log/nginx/error.log
```

You find:

```text
connect() failed (111: Connection refused) while connecting to upstream
```

This tells you Nginx can't connect to Node.js.

---

### Step 2 — Check Node.js

Check whether the process is running:

```bash
ps aux | grep node
```

Suppose nothing useful appears.

Now you know:

```text
Nginx
  ↓
Cannot reach Node.js
  ↓
Node.js probably stopped
```

---

### Step 3 — Check application logs

Depending on how your Node.js application runs, inspect its logs.

If it's a systemd service:

```bash
sudo journalctl -u my-api
```

We'll learn this properly in **Lesson 9.3**.

Suppose you find:

```text
ERROR MongoServerSelectionError
ERROR Unable to connect to MongoDB
```

Now you've gone several levels deeper:

```text
502
 ↓
Nginx cannot reach API
 ↓
Node.js stopped
 ↓
MongoDB connection failed
 ↓
Root cause investigation
```

That's real-world troubleshooting.

# 🧠 Challenge

Imagine you find this in a log:

```text
Aug 15 13:15:22 server nginx[1821]: connect() failed (111: Connection refused) while connecting to upstream
Aug 15 13:15:22 server nginx[1821]: upstream server temporarily disabled
Aug 15 13:15:23 server nginx[1821]: 502 Bad Gateway
```

Answer these before looking below:

### Question 1

What component is reporting the problem?

### Question 2

What does `Connection refused` suggest?

### Question 3

What HTTP error is being returned?

### Question 4

What would you check next?

---

## ✅ Answers

### 1. Nginx

The process:

```text
nginx[1821]
```

is reporting the error.

### 2. The upstream isn't accepting the connection

Potential reasons include:

```text
Node.js stopped
Wrong port
Application crashed
Firewall/network problem
Incorrect Nginx configuration
```

### 3. HTTP 502

```text
502 Bad Gateway
```

usually means the proxy couldn't get a valid response from the upstream server.

### 4. Check the upstream application

For a Node.js backend, investigate:

```text
Is Node.js running?
Which port is it listening on?
Did the application crash?
Are there application errors?
Is MongoDB causing startup failure?
```

Useful commands could include:

```bash
ps aux | grep node
```

and:

```bash
ss -lntp
```

and, if running under systemd:

```bash
sudo journalctl -u my-api
```

# 🚀 Real Backend Engineer Mindset

When an incident occurs, don't just search randomly.

Build a chain:

```text
SYMPTOM
   ↓
Where did it happen?
   ↓
Which service?
   ↓
Which process?
   ↓
Which error?
   ↓
What happened immediately before it?
   ↓
What dependency failed?
   ↓
ROOT CAUSE
```

For example:

```text
502 Bad Gateway
       ↓
Nginx
       ↓
Connection refused
       ↓
Node.js unavailable
       ↓
Application crashed
       ↓
MongoDB connection failed
       ↓
Investigate MongoDB/network/configuration
```

This way of thinking will become one of your strongest backend troubleshooting skills.
