# 1. What is systemd?

Before learning `journalctl`, you need to understand **systemd**.

Modern Linux distributions commonly use systemd to manage system services.

For example:

```text
Linux
  │
  └── systemd
       ├── nginx
       ├── ssh
       ├── docker
       ├── mongodb
       └── your-node-api
```

systemd can:

- Start services
    
- Stop services
    
- Restart services
    
- Enable services at boot
    
- Track service status
    
- Manage dependencies
    
- Collect service output
    

For example:

```bash
systemctl status nginx
```

You may see:

```text
● nginx.service
   Loaded: loaded
   Active: active (running)
   Main PID: 1234
```

But what if you want to know:

> **Why did Nginx fail?**

That's where the journal becomes important.

---

# 2. What is the systemd Journal?

The **systemd journal** is a centralized logging system managed by `systemd-journald`.

Instead of having to search many individual files, you can use:

```bash
journalctl
```

Think of it as:

```text
Many system/service events
          ↓
   systemd-journald
          ↓
       journal
          ↓
     journalctl
          ↓
      You inspect
```

This is especially useful for services running under systemd.

---

# 3. `journalctl`

Start with:

```bash
journalctl
```

This displays journal entries.

You'll probably see a lot of information.

For example:

```text
Aug 15 12:10:01 laptop kernel: ...
Aug 15 12:10:02 laptop systemd[1]: Started ...
Aug 15 12:10:03 laptop NetworkManager: ...
Aug 15 12:10:05 laptop sshd: ...
```

You can think of the journal as a large searchable database of system events.

---

# 4. Don't Read Everything at Once

Running:

```bash
journalctl
```

may return thousands of entries.

Usually you want to **filter**.

Useful filters include:

```text
Service
Time
Priority
Boot
Process
User
```

We'll learn them one by one.

---

# 5. Read the Most Recent Journal Entries

A very useful option is:

```bash
journalctl -n
```

This displays recent entries.

For example:

```bash
journalctl -n 50
```

means:

> Show the last 50 journal entries.

This is similar to:

```bash
tail -n 50
```

for normal log files.

---

# 6. Follow the Journal Live

This is one of the most useful commands:

```bash
journalctl -f
```

`-f` means **follow**.

It behaves similarly to:

```bash
tail -f
```

You see new events as they happen.

For example:

```text
journalctl -f
```

Then start a service:

```bash
sudo systemctl restart nginx
```

You may immediately see journal entries related to that operation.

Stop following with:

```text
Ctrl + C
```

---

# 7. Service Logs with `-u` ⭐

This is probably the most important `journalctl` option for backend engineers.

Use:

```bash
journalctl -u nginx
```

`-u` means:

> Show logs for a particular systemd unit.

For example:

```bash
journalctl -u nginx
```

Or:

```bash
journalctl -u ssh
```

Or:

```bash
journalctl -u docker
```

If your Node.js application runs as a systemd service:

```bash
journalctl -u my-api
```

you can see its logs.

---

# 8. Combine `-u` and `-f`

This is extremely useful:

```bash
journalctl -u nginx -f
```

Meaning:

> Follow Nginx logs live.

For your backend:

```bash
journalctl -u my-api -f
```

Now imagine you're testing:

```http
POST /api/login
```

while watching the logs.

You can immediately see what your backend is doing.

---

# 9. Get the Last 100 Lines of a Service

Instead of:

```bash
journalctl -u nginx
```

use:

```bash
journalctl -u nginx -n 100
```

This gives you the last 100 entries.

Very useful during incidents.

---

# 10. Reverse Order with `-r`

Normally, logs are shown chronologically.

You can reverse them:

```bash
journalctl -r
```

Now the newest entries appear first.

For a service:

```bash
journalctl -u nginx -r
```

This is useful when you care about **what happened most recently**.

---

# 11. Filter by Time

This is extremely important in production.

Suppose a problem started around 12:30.

You can use:

```bash
journalctl --since "12:30"
```

Or:

```bash
journalctl --since "2026-08-15 12:30:00"
```

You can also specify an ending time:

```bash
journalctl \
  --since "2026-08-15 12:30:00" \
  --until "2026-08-15 12:40:00"
```

Now you're looking at a specific incident window.

---

# 12. Relative Time Filtering

You don't always need an exact date.

For example:

```bash
journalctl --since "1 hour ago"
```

Or:

```bash
journalctl --since "30 minutes ago"
```

Or:

```bash
journalctl --since today
```

Or:

```bash
journalctl --since yesterday
```

These are extremely convenient.

---

# 13. Service + Time

This combination is very powerful.

Suppose Nginx started failing in the last hour:

```bash
journalctl -u nginx --since "1 hour ago"
```

For your Node API:

```bash
journalctl -u my-api --since "30 minutes ago"
```

Now you're investigating only relevant information.

---

# 14. Filter by Priority 🚨

The journal supports different priorities.

Common levels:

```text
0 → emerg
1 → alert
2 → crit
3 → err
4 → warning
5 → notice
6 → info
7 → debug
```

The most commonly useful ones are:

```text
err
warning
info
debug
```

---

# 15. Show Errors

Use:

```bash
journalctl -p err
```

This means:

> Show error-level messages.

You can also check the current boot:

```bash
journalctl -p err -b
```

This is a very useful troubleshooting command.

---

# 16. Show Warnings and Errors

You can specify a range:

```bash
journalctl -p warning
```

This can include warning-level messages and more severe messages depending on the priority range behavior.

For a focused error investigation, `-p err` is usually clearer.

---

# 17. Boot Logs

The journal can tell you what happened during system boot.

Use:

```bash
journalctl -b
```

`-b` means:

> Current boot.

This is useful for investigating:

- Services failing during startup
    
- Driver problems
    
- Network startup problems
    
- Disk problems
    
- Boot-time errors
    

---

# 18. Previous Boot

You can inspect earlier boots.

First:

```bash
journalctl --list-boots
```

You might see something like:

```text
-2  abc123...  Fri 2026-08-14 09:10
-1  def456...  Fri 2026-08-14 21:30
 0  ghi789...  Sat 2026-08-15 08:15
```

The current boot is usually:

```text
0
```

The previous one:

```text
-1
```

You can inspect it:

```bash
journalctl -b -1
```

This is extremely useful if:

> "The server worked yesterday, but after reboot something broke."

---

# 19. Previous Boot Errors

Combine them:

```bash
journalctl -b -1 -p err
```

This asks:

> Show errors from the previous boot.

Very useful for diagnosing problems that occurred before a restart.

---

# 20. Kernel Logs

You can ask the journal to show kernel messages:

```bash
journalctl -k
```

This can help investigate:

```text
Kernel issues
Hardware events
Drivers
Network interfaces
Storage
Memory
USB devices
```

You can combine:

```bash
journalctl -k -b
```

Meaning:

> Kernel messages from the current boot.

---

# 21. Search Inside Journal Output

You can pipe journal output into `grep`.

For example:

```bash
journalctl -u nginx | grep -i error
```

Or:

```bash
journalctl -u my-api | grep -i database
```

Or:

```bash
journalctl -b | grep -i failed
```

This is a useful combination:

```text
journalctl
     ↓
Filter journal
     ↓
grep
     ↓
Find specific information
```

---

# 22. `journalctl` + `less`

You can also use:

```bash
journalctl -u nginx | less
```

Then use the normal `less` navigation:

```text
/word
n
N
g
G
q
```

This is useful for large outputs.

---

# 23. Show Logs Without Pager

Sometimes `journalctl` opens output in a pager.

You can use:

```bash
journalctl --no-pager
```

For example:

```bash
journalctl -u nginx --no-pager
```

This is particularly useful when piping output into other commands.

---

# 24. Important: `journalctl` Is Not the Same as `/var/log`

This distinction is important.

Traditional logging:

```text
/var/log/
   ├── syslog
   ├── auth.log
   ├── kern.log
   └── nginx/
```

Systemd journal:

```text
systemd-journald
       ↓
journalctl
```

Modern Linux systems often use **both**.

Some applications write directly to files.

Others write to stdout/stderr and let systemd collect the output.

For example:

```text
Node.js
  ↓
stdout/stderr
  ↓
systemd
  ↓
journal
  ↓
journalctl
```

This is one reason systemd logging is so convenient for backend services.

# 25. Running a Node.js API with systemd

Imagine your backend has a service:

```text
my-api.service
```

You could have:

```text
systemd
   ↓
Node.js
   ↓
Express API
```

When Node.js prints:

```javascript
console.log("Server started");
```

systemd can capture it.

Then:

```bash
journalctl -u my-api
```

can show:

```text
Server started
Database connected
Listening on port 3000
```

If the application crashes:

```text
MongoServerSelectionError
```

could also appear in the journal.

This is extremely useful for production Node.js applications.

# 26. A Real Incident 🔥

Let's simulate one.

Suppose your production API suddenly returns:

```text
502 Bad Gateway
```

You know Nginx is in front of Node.js.

### Step 1 — Check Nginx

```bash
sudo systemctl status nginx
```

Suppose:

```text
Active: active (running)
```

Nginx is alive.

---

### Step 2 — Check Node.js service

```bash
sudo systemctl status my-api
```

You discover:

```text
Active: failed
```

Now investigate.

---

### Step 3 — Read recent logs

```bash
journalctl -u my-api -n 100
```

You find:

```text
Error: listen EADDRINUSE: address already in use :::3000
```

Interesting.

Another process is already using port 3000.

---

### Step 4 — Verify

```bash
sudo ss -lntp | grep :3000
```

You discover another Node process is listening there.

Now you have a real chain:

```text
502 Bad Gateway
       ↓
Nginx healthy
       ↓
Node service failed
       ↓
journalctl
       ↓
EADDRINUSE
       ↓
Port 3000 already occupied
```

That's a proper investigation.

# 29. Production Debugging Workflow

When a systemd service fails, use this workflow:

```text
             Service problem
                    ↓
          systemctl status
                    ↓
             Is it running?
              ↙         ↘
            YES          NO
             ↓            ↓
       Check logs    journalctl -u
             ↓            ↓
        Investigate     Find error
             ↓            ↓
          Root cause ←────┘
                    ↓
                  Fix
                    ↓
                Restart
                    ↓
                 Verify
```

Useful commands:

```bash
systemctl status my-api
```

then:

```bash
journalctl -u my-api -n 100
```

then:

```bash
journalctl -u my-api -f
```

after fixing the issue.

# 30. Persistent Journals

There is an important concept:

> **What happens to logs after reboot?**

Depending on configuration, journal data may be stored persistently or only temporarily.

Check:

```bash
ls -lah /var/log/journal
```

If the directory exists, persistent journal storage may be configured.

You can also inspect the journal configuration:

```bash
cat /etc/systemd/journald.conf
```

Look for:

```text
Storage=
```

Possible values include:

```text
persistent
volatile
auto
none
```

### `persistent`

Store journal data on disk.

### `volatile`

Store journal data mainly in memory.

### `auto`

Use persistent storage if the journal directory exists; otherwise use volatile storage.

### `none`

Don't store journal data.

For production servers, persistent logs are generally valuable because you don't want a reboot to erase the evidence needed to investigate an incident.

# 31. Journal Disk Usage

Logs themselves consume disk space.

Check journal size:

```bash
journalctl --disk-usage
```

You might see:

```text
Archived and active journals take up 250.0M in the file system.
```

This is important because:

```text
Logs grow
   ↓
Disk usage increases
   ↓
Disk becomes full
   ↓
Applications may fail
```

Observability can ironically become a source of problems if logging is not managed properly.

We'll learn proper log retention and `logrotate` in **Lesson 9.4**.


This is where `journalctl` starts becoming a serious troubleshooting tool.

# 🔥 Important Mental Model

Don't think of `journalctl` as:

> "A command that shows logs."

Think of it as:

> **A query interface for your Linux system's event history.**

For example:

```text
"What happened?"
       ↓
journalctl

"What happened to nginx?"
       ↓
journalctl -u nginx

"What happened in the last hour?"
       ↓
journalctl --since "1 hour ago"

"What went wrong?"
       ↓
journalctl -p err

"What happened during the previous boot?"
       ↓
journalctl -b -1

"What is happening right now?"
       ↓
journalctl -f
```

That mindset will make Linux troubleshooting much easier.
