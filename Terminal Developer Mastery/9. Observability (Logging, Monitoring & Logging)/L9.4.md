# 1. Why Do We Need Log Management?

In the previous lessons, you learned how to read logs.

But there's a problem:

> **Logs keep growing.**

Imagine your backend writes:

```text
10 MB/day
```

That's:

```text
10 MB × 30 days = 300 MB/month
```

Now imagine a busy application:

```text
500 MB/day
```

That's:

```text
500 MB × 30 = 15 GB/month
```

Eventually:

```text
Logs
  ↓
Disk fills
  ↓
Disk reaches 100%
  ↓
Applications cannot write
  ↓
Database may fail
  ↓
Server can become unstable
```

So:

> **Logging without log management is dangerous.**

---

# 2. What is Log Rotation?

**Log rotation** means periodically replacing an old log with a new one.

Imagine:

```text
app.log
```

After rotation:

```text
app.log
app.log.1
```

After another rotation:

```text
app.log
app.log.1
app.log.2
```

After compression:

```text
app.log
app.log.1.gz
app.log.2.gz
```

The newest log remains:

```text
app.log
```

Older logs are moved aside.

---

# 3. Why Rotate Logs?

Without rotation:

```text
app.log
   ↓
100 MB
   ↓
500 MB
   ↓
2 GB
   ↓
10 GB
   ↓
💥 Disk full
```

With rotation:

```text
app.log
   ↓
rotate
   ↓
app.log.1.gz
   ↓
new app.log
```

This gives you:

- Controlled disk usage
    
- Historical logs
    
- Compression
    
- Automatic cleanup
    
- Easier troubleshooting
    

---

# 4. What is `logrotate`?

On many Linux systems, **`logrotate`** is used to automatically manage log files.

It can:

- Rotate logs
    
- Compress old logs
    
- Delete old logs
    
- Create new log files
    
- Run commands after rotation
    
- Keep a specific number of historical logs
    

Check whether it's installed:

```bash
logrotate --version
```

You may see something like:

```text
logrotate 3.x.x
```

---

# 5. Where is `logrotate` Configured?

The main configuration file is:

```bash
/etc/logrotate.conf
```

There is also a directory:

```bash
/etc/logrotate.d/
```

This directory is extremely important.

You can inspect it:

```bash
ls -lah /etc/logrotate.d/
```

You may find configurations for things like:

```text
nginx
apt
rsyslog
docker
```

depending on your system.

---

# 6. Main Configuration

Open:

```bash
sudo less /etc/logrotate.conf
```

You'll see configuration similar to:

```text
weekly
rotate 4
create
include /etc/logrotate.d
```

Let's understand these.

---

# 7. `weekly`

```text
weekly
```

means:

> Rotate logs weekly by default.

Other possibilities include:

```text
daily
weekly
monthly
```

For high-volume applications, daily or even more frequent rotation may be appropriate.

---

# 8. `rotate`

Example:

```text
rotate 4
```

means:

> Keep four old rotated logs.

For example:

```text
app.log
app.log.1
app.log.2
app.log.3
app.log.4
```

When another rotation happens, the oldest may be removed.

---

# 9. `compress`

Example:

```text
compress
```

means:

> Compress old log files.

You may end up with:

```text
app.log
app.log.1.gz
app.log.2.gz
app.log.3.gz
```

This can save significant disk space.

---

# 10. Why Compression Matters

Suppose:

```text
app.log.1 = 200 MB
```

A text log often compresses very well.

You might end up with something much smaller:

```text
app.log.1.gz = 25 MB
```

So instead of:

```text
200 MB × 10
```

you might only need a fraction of that storage.

This is especially useful for verbose application logs.

---

# 11. `delaycompress`

You may see:

```text
delaycompress
```

This means:

> Don't compress the most recently rotated log immediately; compress it during the next rotation.

Example:

```text
Current:
app.log
app.log.1
app.log.2.gz
```

After another rotation:

```text
app.log
app.log.1
app.log.2.gz
app.log.3.gz
```

The exact naming behavior depends on the rotation configuration, but the main idea is to delay compression of the newest rotated file.

---

# 12. `missingok`

Example:

```text
missingok
```

means:

> Don't produce an error if the log file doesn't exist.

Useful because some services may not create a log until they actually run.

---

# 13. `notifempty`

```text
notifempty
```

means:

> Don't rotate an empty log.

This avoids unnecessary rotations.

---

# 14. `create`

Example:

```text
create 0640 www-data adm
```

After rotation, `logrotate` creates a new log file with specified permissions and ownership.

For example:

```text
0640
```

means:

```text
Owner → read/write
Group → read
Others → no access
```

Log permissions matter because logs can contain sensitive information.

---

# 15. `copytruncate`

This option is particularly interesting for applications.

```text
copytruncate
```

means approximately:

```text
Copy current log
      ↓
Create rotated copy
      ↓
Truncate original
      ↓
Application continues writing
```

This can be useful when an application keeps the same file open and doesn't automatically reopen the log.

But it has a tradeoff: a small amount of data can potentially be lost during the copy/truncate operation.

For applications that support reopening log files, signaling/reopening the logger is often cleaner.

---

# 16. Example Logrotate Configuration

Imagine your Node.js API writes:

```text
/var/log/my-api/app.log
```

You could create:

```bash
sudo nano /etc/logrotate.d/my-api
```

with:

```text
/var/log/my-api/app.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 root adm
}
```

Let's break it down.

```text
daily
```

Rotate every day.

```text
rotate 14
```

Keep 14 rotations.

```text
compress
```

Compress old logs.

```text
delaycompress
```

Delay compression of the newest rotated log.

```text
missingok
```

Don't complain if the file doesn't exist.

```text
notifempty
```

Don't rotate an empty file.

```text
create 0640 root adm
```

Create the new log with controlled permissions.

---

# 17. Result

Before rotation:

```text
/var/log/my-api/
└── app.log
```

After rotation:

```text
/var/log/my-api/
├── app.log
├── app.log.1
└── app.log.2.gz
```

Eventually:

```text
app.log
app.log.1.gz
app.log.2.gz
...
app.log.14.gz
```

Then older logs are removed according to the policy.

---

# 18. `dateext`

Another useful option:

```text
dateext
```

Instead of:

```text
app.log.1
app.log.2
```

you may get date-based filenames such as:

```text
app.log-20260815
app.log-20260814.gz
```

This can make historical logs easier to identify.

---

# 19. Retention Policy

A production system should have a clear answer to:

> **How long do we keep logs?**

For example:

```text
Application logs
→ 14 days

Security logs
→ 90 days

Audit logs
→ 1 year
```

The correct period depends on:

- Application requirements
    
- Security requirements
    
- Compliance requirements
    
- Storage capacity
    
- Troubleshooting needs
    

Don't blindly keep logs forever.

---

# 20. Retention Is a Tradeoff

More retention:

```text
More history
    +
More storage
    -
Higher cost
```

Less retention:

```text
Less storage
    +
Lower cost
    -
Less historical information
```

Good production engineering finds the right balance.

---

# 21. Log Levels Affect Storage

Remember the levels:

```text
DEBUG
INFO
WARN
ERROR
```

If your production application writes massive amounts of:

```text
DEBUG
```

logs:

```text
DEBUG DEBUG DEBUG DEBUG DEBUG
DEBUG DEBUG DEBUG DEBUG DEBUG
DEBUG DEBUG DEBUG DEBUG DEBUG
```

your logs can grow very quickly.

Production applications commonly use a more controlled logging level.

For example:

```text
Production → INFO/WARN/ERROR
Development → DEBUG
```

The exact setup depends on the application.

---

# 22. Log Rotation ≠ Centralized Logging

These are different concepts.

### Log rotation

Controls:

```text
How much local disk space logs consume.
```

Example:

```text
logrotate
```

### Centralized logging

Moves/aggregates logs elsewhere.

Example:

```text
Application
   ↓
Log shipper
   ↓
Loki / Elasticsearch
   ↓
Search + dashboards
```

So:

```text
Rotation
   ↓
Local storage management

Centralization
   ↓
Centralized collection + analysis
```

We'll study centralized logging in Lesson 9.7.

# 23. Systemd Journal and Logrotate

This is an important distinction.

`logrotate` primarily manages **log files**.

For example:

```text
/var/log/nginx/access.log
```

The systemd journal has its own storage and retention mechanisms.

You can inspect journal storage with:

```bash
journalctl --disk-usage
```

So don't assume:

```text
logrotate
```

automatically manages all systemd journal data.

They are separate systems.

---

# 24. Journal Retention

Systemd journal configuration can be controlled through:

```text
/etc/systemd/journald.conf
```

For example, settings can control:

```text
SystemMaxUse
SystemKeepFree
MaxRetentionSec
RuntimeMaxUse
```

These determine how much disk space the journal can consume and how long entries may be retained.

After changing journald configuration, you typically restart/reload the service appropriately.

For example:

```bash
sudo systemctl restart systemd-journald
```

Be careful when changing system logging settings on production systems.

---

# 25. Check Your Journal Size

Run:

```bash
journalctl --disk-usage
```

Example:

```text
Archived and active journals take up 180.0M in the file system.
```

If it becomes very large, investigate your journal retention configuration rather than simply deleting files manually.

---

# 26. Don't Manually Delete Active Logs

Avoid doing things like:

```bash
sudo rm /var/log/syslog
```

on a running production system.

Why?

Because a process may already have the file open.

You can end up with confusing behavior.

Instead:

```text
Use logrotate
      or
Use the application's supported log handling
      or
Use journald's retention controls
```

Proper log management is safer than manually deleting files.

---

# 27. Testing `logrotate`

Before actually rotating logs, you can test the configuration.

A very useful command is:

```bash
sudo logrotate -d /etc/logrotate.conf
```

`-d` means debug mode.

It shows what `logrotate` **would do** without actually performing the rotation.

This is very useful when creating a new configuration.

---

# 28. Force a Rotation

For testing, you can force rotation:

```bash
sudo logrotate -f /etc/logrotate.conf
```

`-f` means:

> Force rotation.

⚠️ Don't casually use this on production logs.

Use it when you understand the configuration and intentionally want to test it.

---

# 29. Check Logrotate Configuration

You can inspect:

```bash
sudo less /etc/logrotate.conf
```

and:

```bash
ls -lah /etc/logrotate.d/
```

Then inspect a specific configuration:

```bash
sudo less /etc/logrotate.d/nginx
```

if it exists.

# 30. How Automatic Rotation Happens

You might wonder:

> "Who actually runs logrotate?"

On modern Linux systems, this can be triggered by a systemd timer.

Check:

```bash
systemctl status logrotate.timer
```

You may see something similar to:

```text
● logrotate.timer
   Loaded: loaded
   Active: active (waiting)
```

You can also inspect:

```bash
systemctl list-timers | grep logrotate
```

The exact scheduling mechanism can vary by distribution/version.

# 33. Security Considerations 🔐

Logs can contain sensitive information.

Never casually log:

```text
Passwords
Access tokens
Refresh tokens
API keys
Session cookies
Credit card data
Private secrets
```

Bad:

```json
{
  "email": "rahul@example.com",
  "password": "mypassword123"
}
```

Better:

```json
{
  "email": "rahul@example.com",
  "event": "login_failed"
}
```

Log management is therefore also part of **security engineering**.

You'll revisit this deeply in Module 10.

---

# 34. Permissions Matter

Suppose:

```text
/var/log/my-api/app.log
```

contains sensitive information.

Don't make it world-readable:

```text
-rw-r--r-- 
```

unless there is a good reason.

A more controlled permission might be:

```text
0640
```

meaning:

```text
Owner  → read/write
Group  → read
Others → none
```

Always think:

> Who actually needs to read this log?

# 37. Production Incident Example 🚨

Imagine your server suddenly reports:

```text
Disk usage: 98%
```

You investigate:

```bash
df -h
```

Then:

```bash
sudo du -sh /var/log/*
```

You discover:

```text
/var/log/my-api → 18G
```

Then:

```bash
sudo du -sh /var/log/my-api/*
```

You discover:

```text
app.log → 17G
```

Now the root cause is obvious:

```text
Excessive application logging
        ↓
No rotation
        ↓
app.log grows
        ↓
Disk fills
```

The fix isn't simply:

```bash
rm app.log
```

Instead:

```text
1. Investigate why it grew
2. Configure rotation
3. Set retention
4. Compress old logs
5. Reduce unnecessary logging
6. Monitor disk usage
```

This is much more production-safe.

# 🔥 Important Mental Model

Log management has four major responsibilities:

```text
             LOG MANAGEMENT
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
    Rotation   Retention   Compression
       │           │           │
       └───────────┼───────────┘
                   ▼
             Disk Protection
```

And production logging should follow:

```text
Generate useful logs
        ↓
Store safely
        ↓
Rotate
        ↓
Compress
        ↓
Retain for appropriate period
        ↓
Centralize when needed
        ↓
Monitor storage
```

## 🎯 What you should now be able to explain

If an interviewer asks:

> **"Why is log rotation important?"**

A strong answer is:

> Log rotation prevents application and system logs from growing indefinitely and consuming all available disk space. It periodically archives logs, optionally compresses older logs, and removes logs according to a retention policy. This keeps storage under control while preserving enough historical information for troubleshooting and auditing.

That's a practical production answer—not just a definition.
