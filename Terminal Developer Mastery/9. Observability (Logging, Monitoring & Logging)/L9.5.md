# 1. What Is Application Logging?

Application logging means your backend records important events while it is running.

For example:

```text
Server started
Database connected
User logged in
Order created
Payment failed
Database query failed
Request took too long
```

A Node.js application might start with:

```javascript
console.log("Server started");
```

Then:

```javascript
console.log("User logged in");
```

And:

```javascript
console.error("Database connection failed");
```

This works during development.

But production applications need much better logging.

---

# 2. Why `console.log()` Isn't Enough

Imagine your production server receives:

```text
10,000 requests/minute
```

And your logs look like:

```text
User logged in
User logged in
Request received
Database query
Request received
Error
User logged in
Request received
```

You have a problem.

You don't know:

- Which user?
    
- Which request?
    
- Which endpoint?
    
- Which server?
    
- Which environment?
    
- When exactly?
    
- How long did it take?
    
- What caused the error?
    

You need **context**.

Instead of:

```text
Error
```

you want something like:

```json
{
  "level": "error",
  "message": "Database query failed",
  "service": "student-api",
  "requestId": "req-8f31",
  "method": "GET",
  "path": "/api/students",
  "durationMs": 842,
  "error": "MongoServerSelectionError"
}
```

Now the log is useful.

---

# 3. What Makes a Good Production Log?

A useful application log generally contains:

```text
Timestamp
Log level
Message
Service
Environment
Request ID
Relevant context
Error information
```

For example:

```json
{
  "timestamp": "2026-08-15T13:20:10.421Z",
  "level": "info",
  "service": "student-api",
  "environment": "production",
  "requestId": "req-123",
  "message": "Student created"
}
```

This is called **structured logging**.

---

# 4. Structured Logging

Structured logging means logs are stored as structured data rather than random text.

### Unstructured

```text
Student Rahul created successfully
```

A human can understand it.

But machines have difficulty extracting information consistently.

### Structured

```json
{
  "event": "student_created",
  "studentId": "stu_123",
  "requestId": "req_456"
}
```

Now a logging platform can easily search:

```text
studentId = stu_123
```

or:

```text
event = student_created
```

This becomes extremely powerful when we introduce Loki/ELK later.

---

# 5. JSON Logging

JSON is commonly used for structured logs.

Example:

```json
{
  "level": "info",
  "message": "Server started",
  "port": 3000,
  "service": "student-api"
}
```

Another:

```json
{
  "level": "error",
  "message": "Database connection failed",
  "service": "student-api",
  "error": "MongoServerSelectionError"
}
```

Each log entry becomes a structured object.

---

# 6. Why JSON?

Imagine you have:

```text
10 million logs
```

You want to find:

> All database errors from the `student-api` service during the last hour.

Structured logs make this much easier.

You can filter:

```text
service = student-api
level = error
error contains database
time > 1 hour
```

This is one reason production systems prefer structured logging.

---

# 7. Log Levels

A logger normally provides several levels.

The common ones are:

```text
debug
info
warn
error
fatal
```

Let's understand them.

---

## DEBUG

Detailed information mainly useful while developing or troubleshooting.

```javascript
logger.debug("Starting database query");
```

Example:

```json
{
  "level": "debug",
  "message": "Starting database query",
  "collection": "students"
}
```

Don't blindly produce huge amounts of debug logs in production.

---

## INFO

Normal application events.

```javascript
logger.info("Server started");
```

Example:

```json
{
  "level": "info",
  "message": "Server started",
  "port": 3000
}
```

---

## WARN

Something unusual happened, but the application can continue.

```javascript
logger.warn("Database connection pool is nearly full");
```

Example:

```json
{
  "level": "warn",
  "message": "Database connection pool is nearly full",
  "usage": 92
}
```

---

## ERROR

Something failed.

```javascript
logger.error("Failed to create student");
```

Example:

```json
{
  "level": "error",
  "message": "Failed to create student",
  "error": "ValidationError"
}
```

---

## FATAL

A serious error that prevents the application from continuing normally.

```javascript
logger.fatal("Unable to initialize application");
```

Not every logging library uses `fatal`, but the concept is common.

---

# 8. Log Level Hierarchy

Think:

```text
DEBUG
  ↓
INFO
  ↓
WARN
  ↓
ERROR
  ↓
FATAL
```

As severity increases:

```text
DEBUG → detailed
INFO  → normal
WARN  → unusual
ERROR → failure
FATAL → critical failure
```

---

# 9. Don't Log Sensitive Data 🚨

This is extremely important.

Never log:

```text
Passwords
Access tokens
Refresh tokens
JWT secrets
API keys
Session cookies
Credit card information
Database passwords
Private encryption keys
```

Bad:

```javascript
console.log(req.body);
```

Why?

Suppose:

```json
{
  "email": "rahul@example.com",
  "password": "SuperSecret123"
}
```

Your password is now in the logs.

That is dangerous.

---

# 10. Bad Authentication Logging

Never do this:

```javascript
logger.info({
  email: req.body.email,
  password: req.body.password
}, "Login attempt");
```

Instead:

```javascript
logger.info({
  email: req.body.email
}, "Login attempt");
```

Even better, depending on your privacy/security requirements, avoid logging the full email address and use a safer identifier.

---

# 11. Request Logging

Every HTTP request is potentially useful to observe.

For example:

```http
GET /api/students
```

You might want:

```text
Method: GET
Path: /api/students
Status: 200
Duration: 45ms
Request ID: abc123
```

Structured:

```json
{
  "level": "info",
  "message": "HTTP request completed",
  "method": "GET",
  "path": "/api/students",
  "statusCode": 200,
  "durationMs": 45,
  "requestId": "abc123"
}
```

This is much more useful than:

```text
Request received
```

---

# 12. Request ID ⭐⭐⭐⭐⭐

A **request ID** uniquely identifies a request.

Imagine a user sends:

```http
POST /api/orders
```

You generate:

```text
requestId = req-7f8d92
```

Then every log related to that request contains:

```text
req-7f8d92
```

For example:

```text
Request received
      ↓
Authentication
      ↓
Order validation
      ↓
MongoDB query
      ↓
Order created
      ↓
Response sent
```

All logs:

```json
{"requestId":"req-7f8d92","message":"Request received"}
{"requestId":"req-7f8d92","message":"User authenticated"}
{"requestId":"req-7f8d92","message":"Creating order"}
{"requestId":"req-7f8d92","message":"Order created"}
```

Now you can search:

```text
requestId = req-7f8d92
```

and see the entire request flow.

---

# 13. Why Request IDs Are So Powerful

Imagine your server receives 1,000 requests simultaneously.

Without request IDs:

```text
Request started
Database query
Request started
User authenticated
Database query
Error
Request finished
```

Which event belongs to which request?

Very difficult.

With request IDs:

```text
req-A → Request started
req-B → Request started
req-A → Database query
req-B → User authenticated
req-A → Error
req-B → Request finished
```

Now the events are traceable.

---

# 14. Correlation ID

A **correlation ID** is similar to a request ID but can represent a broader operation across multiple services.

Imagine:

```text
Frontend
   ↓
API Gateway
   ↓
Student Service
   ↓
Notification Service
   ↓
Email Service
```

One user operation could have:

```text
correlationId = corr-789
```

Every service carries that ID.

```text
API Gateway
corr-789
   ↓
Student Service
corr-789
   ↓
Notification Service
corr-789
   ↓
Email Service
corr-789
```

Now you can investigate one business operation across multiple services.

---

# 15. Request ID vs Correlation ID

A simple way to remember:

### Request ID

Usually identifies:

> **One HTTP request.**

### Correlation ID

Can identify:

> **A larger operation across multiple requests/services.**

In a simple monolithic Express application, you may only need request IDs.

In distributed systems, correlation IDs become much more useful.

---

# 16. Generate a Request ID

You can use a package such as `uuid` or another unique ID generator.

For example:

```bash
npm install uuid
```

Then:

```javascript
import { v4 as uuidv4 } from "uuid";

const requestIdMiddleware = (req, res, next) => {
  req.requestId = req.headers["x-request-id"] || uuidv4();

  res.setHeader("x-request-id", req.requestId);

  next();
};

export default requestIdMiddleware;
```

Now each request gets an ID.

---

# 17. Why Accept an Existing Request ID?

Suppose another service calls your API:

```http
X-Request-ID: req-123
```

You don't necessarily want to generate:

```text
req-456
```

and lose the original context.

Instead:

```javascript
req.requestId =
  req.headers["x-request-id"] || uuidv4();
```

This means:

```text
Existing ID?
    ↓
Use it

No ID?
    ↓
Generate one
```

This becomes important when services communicate with each other.

---

# 18. Response Headers

Returning the ID to the client can also be useful:

```javascript
res.setHeader("x-request-id", req.requestId);
```

Then the browser/client can receive:

```http
X-Request-ID: req-123
```

If a user reports:

> "I got an error."

You can potentially ask for the request ID:

```text
Request ID: req-123
```

Then search your logs.

That's much better than:

> "Let me search through 100,000 logs."

---

# 19. Express Logging Middleware

A basic example:

```javascript
const requestLogger = (req, res, next) => {
  const start = Date.now();

  res.on("finish", () => {
    const durationMs = Date.now() - start;

    console.log({
      method: req.method,
      path: req.originalUrl,
      statusCode: res.statusCode,
      durationMs,
      requestId: req.requestId
    });
  });

  next();
};
```

This records the request after the response finishes.

---

# 20. Why Measure Duration?

Suppose you see:

```json
{
  "path": "/api/students",
  "statusCode": 200
}
```

That's useful.

But:

```json
{
  "path": "/api/students",
  "statusCode": 200,
  "durationMs": 1840
}
```

is much better.

You now know:

> The request took 1.84 seconds.

This becomes a metric later.

---

# 21. Logging Errors Properly

Bad:

```javascript
try {
  await createStudent();
} catch (error) {
  console.log(error);
}
```

Better:

```javascript
try {
  await createStudent();
} catch (error) {
  logger.error({
    error: error.message,
    stack: error.stack
  }, "Failed to create student");
}
```

Even better, include useful context:

```javascript
logger.error({
  requestId: req.requestId,
  userId: req.user?.id,
  error: error.message,
  stack: error.stack
}, "Failed to create student");
```

But only include identifiers that are safe and genuinely useful.

---

# 22. Don't Accidentally Leak Secrets in Errors

Be careful with:

```javascript
logger.error(error);
```

An error object can sometimes contain sensitive data depending on the library and context.

For production logging, deliberately choose what you record:

```javascript
logger.error({
  message: error.message,
  name: error.name,
  stack: error.stack
}, "Request failed");
```

You should still review stack traces and error metadata for sensitive values.

---

# 23. Build a Logger Instead of Scattered `console.log()`

Instead of:

```javascript
console.log("User created");
console.log("Database connected");
console.error("Something failed");
```

create a centralized logger.

Conceptually:

```text
src/
├── config/
├── controllers/
├── services/
├── repositories/
├── middleware/
├── utils/
└── logger/
    └── logger.js
```

Then everywhere:

```javascript
logger.info(...)
logger.warn(...)
logger.error(...)
```

This gives you consistent behavior.

# 27. Pino HTTP

With `pino-http`, you can add HTTP logging.

Conceptually:

```javascript
import pinoHttp from "pino-http";

app.use(
  pinoHttp({
    logger
  })
);
```

Now requests can automatically generate logs.

You can then use:

```javascript
req.log.info("User authenticated");
```

and:

```javascript
req.log.error(error, "Database failed");
```

This is much cleaner than manually calling a global logger everywhere.

---

# 28. Request IDs with Pino HTTP

Pino HTTP can also work with request IDs.

Conceptually:

```javascript
app.use(
  pinoHttp({
    logger,
    genReqId: (req) =>
      req.headers["x-request-id"] || crypto.randomUUID()
  })
);
```

Now each request receives an identifier.

Your logs can contain:

```text
req.id
```

This gives you a very useful pattern:

```text
HTTP request
      ↓
Request ID
      ↓
Logger
      ↓
Structured logs
```

# 29. Development vs Production Logging

You don't necessarily want the exact same output everywhere.

### Development

Human-readable logs are convenient:

```text
INFO Server started on port 3000
INFO Database connected
```

### Production

JSON is usually more useful:

```json
{
  "level": "info",
  "service": "student-api",
  "msg": "Database connected"
}
```

Why?

Because production logs may be consumed by:

```text
Loki
Elasticsearch
Datadog
CloudWatch
Grafana
```

Structured output is easier for these systems to process.

A useful production logger should distinguish:

```text

3xx → redirect
4xx → client problem
5xx → server problem
```

For example:

```json
{
  "method": "GET",
  "path": "/api/students",
  "statusCode": 200,
  "durationMs": 42
}
```

And:

```json
{
  "method": "POST",
  "path": "/api/students",
  "statusCode": 500,
  "durationMs": 1300,
  "requestId": "req-123"
}
```

This gives you useful incident information.

# 32. Health Check Logging

Suppose your application exposes:

```http
GET /health
```

It may be called frequently by monitoring systems.

If you log every health check:

```text
GET /health
GET /health
GET /health
GET /health
GET /health
```

your logs can become noisy.

You might choose to:

- Log health checks at a lower level
    
- Exclude them from application logs
    
- Sample them
    
- Track them primarily through metrics
    

This is a good example of:

> **Not everything needs to be a log.**

# 33. Application Logs vs Metrics

Suppose you want:

> Number of requests per second.

You could log every request:

```text
Request 1
Request 2
Request 3
...
Request 10000
```

But that's inefficient.

A metric is better:

```text
requests_total = 10000
```

This is an important observability principle:

```text
Events/details
    ↓
Logs

Numbers/trends
    ↓
Metrics
```

We'll explore metrics in later lessons.

# 34. Logging Database Operations

Be careful here.

Bad:

```javascript
logger.info({
  query,
  userData,
  password

```

Better:

```javascript
logger.debug({
  collection: "students",
```

You generally don't want to dump entire database documents into production logs.

# 39. Your Architecture + Logging

You already prefer:

```text
Controller
    ↓
Service
    ↓
Repository
```

That's a good place to apply logging carefully.

### Controller

Log request-level information:

```text
Request received
Request completed
```

### Service

Log important business operations:

```text
Student registration
Course enrollment
Payment processing
```

### Repository

Usually avoid excessive logs.

```text

```

Don't log every successful query unless you specifically need that level of detail.

# 40. Error Middleware

A centralized Express error handler is a great place to perform consistent error logging.

Conceptually:

```javascript
app.use((err, req, res, next) => {
  logger.error(
    {
      requestId: req.id,
      error: err.message,
      stack: err.stack
    },
    "Unhandled application error"
  );

  res.status(500).json({
    message: "Internal server error",
    requestId: req.id
  });
});
```

Notice something useful:

```text
requestId
```

is returned to the client.

Now the user can give you:

```text
Request ID: req-123
```

and you can search the logs.

---

# 41. Never Return Internal Errors Directly

Bad:

```javascript
res.status(500).json({
  error: err.stack
});
```

This may expose:

- File paths
    
- Internal implementation details
    
- Database information
    
- Library versions
    
- Sensitive information
    

Instead:

```javascript
res.status(500).json({
  message: "Internal server error",
  requestId: req.id
});
```

Log the technical details internally.

This is an important production security practice.

---

# 42. A Complete Example

A simplified Express application could look like:

```javascript
import express from "express";
import pino from "pino";
import pinoHttp from "pino-http";

const app = express();

const logger = pino({
  level: process.env.LOG_LEVEL || "info"
});

app.use(
  pinoHttp({
    logger,
    genReqId: (req) =>
      req.headers["x-request-id"] || crypto.randomUUID()
  })
);

app.get("/api/students", async (req, res) => {
  req.log.info(
    {
      requestId: req.id
    },
    "Fetching students"
  );

  res.json({
    students: []
  });
});

app.use((err, req, res, next) => {
  req.log.error(
    {
      err,
      requestId: req.id
    },
    "Unhandled application error"
  );

  res.status(500).json({
    message: "Internal server error",
    requestId: req.id
  });
});

app.listen(3000, () => {
  logger.info(
    {
      port: 3000
    },
    "Server started"
  );
});
```

This is only a learning example; a production implementation should also handle configuration, graceful shutdown, error serialization, and logger behavior carefully.

# 45. Add a Custom Request ID

A more useful configuration:

```javascript
import crypto from "node:crypto";
import pinoHttp from "pino-http";

app.use(
  pinoHttp({
    logger,
    genReqId: (req) => {
```

# 46. Return Request ID

You can expose it:

```javascript
app.use(
  pinoHttp({
    logger,
    genReqId: (req, res) => {
      const requestId =
        req.headers["x-request-id"] || crypto.randomUUID();

      res.setHeader("x-request-id", requestId);

      return requestId;
    }
  })
);
```

Then:

```bash
curl -i http://localhost:3000/api/students
```

You should be able to see:

```text
x-request-id: ...
```

Request:

```bash

```

Then inspect your logs.

You should have enough information to connect:

```text

     ↓

     ↓

     ↓

```

This is the beginning of proper production observability.

# 📌 Lesson 9.5 Summary

Remember these core concepts:

### Application logs

> Records important events inside your application.

### Structured logging

> Store logs as structured data instead of random strings.

### Log levels

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

### Request ID

> Identifies one request and helps connect all logs belonging to it.

### Correlation ID

> Connects a larger operation across multiple requests/services.

### Production rule

```text
Log useful information
        +
Add enough context
        +
Protect sensitive information
        +
Make logs machine-readable
```

And one of the most important backend habits:

> **When an error happens, don't just log `"Something went wrong"`. Log enough safe context to explain what happened, where it happened, and how you can find the complete request later.**
