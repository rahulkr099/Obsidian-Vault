# 1. The Golden Rule of Logging ⭐

A very useful rule is:

> **Log enough information to understand and investigate a problem, but not so much that logs become expensive, noisy, slow, or dangerous.**

Think of logging as a balance:

```text
Too little logging
       ↓
Can't debug

Too much logging
       ↓
Noise + cost + performance problems

Bad logging
       ↓
Security risks

Good logging
       ↓
Useful + searchable + safe
```

---

# 2. What Should You Log?

A production backend should generally log important events.

For example:

### Application lifecycle

```text
Server started
Server stopped
Database connected
Database disconnected
Configuration loaded
```

### HTTP requests

```text
Method
Path
Status code
Duration
Request ID
```

### Errors

```text
Error type
Error message
Stack trace
Request ID
Relevant context
```

### Authentication events

```text
Login success
Login failure
Logout
Account lockout
Suspicious authentication activity
```

### Important business events

```text
User registered
Course enrolled
Order created
Payment failed
Assignment submitted
```

---

# 3. What Should You NOT Log? 🚨

This is one of the most important topics in this lesson.

Never casually log:

```text
Passwords
Access tokens
Refresh tokens
JWT secrets
API keys
Database passwords
Session cookies
Encryption keys
Credit card information
```

Also be careful with:

```text
Personal information
Private messages
Full request bodies
Authentication headers
Database documents
```

---

# 4. The Most Dangerous Mistake

This is extremely common:

```javascript
console.log(req.body);
```

It looks harmless.

But imagine a login request:

```json
{
  "email": "rahul@example.com",
  "password": "SecretPassword123"
}
```

Now you've accidentally stored the password in:

```text
Application logs
Server logs
Centralized logging
Log backups
Monitoring systems
```

One innocent `console.log()` can create a serious security problem.

---

# 5. Never Log Authentication Headers

Don't do this:

```javascript
logger.info({
  headers: req.headers
});
```

Why?

Because headers can contain:

```text
Authorization
Cookie
Session information
API keys
Internal metadata
```

For example:

```http
Authorization: Bearer eyJhbGciOi...
```

You don't want that in your logs.

---

# 6. If You Need to Log a Sensitive Field

Sometimes you genuinely need some information for debugging.

Use **redaction**.

For example:

```text
Email:
rahul@example.com

Password:
[REDACTED]
```

Or:

```text
Authorization:
[REDACTED]
```

Never rely on developers remembering:

> "Don't log that field."

Build protection into your logging system.

---

# 7. Redaction

Redaction means replacing sensitive information with something safe.

For example:

```json
{
  "email": "rahul@example.com",
  "password": "[REDACTED]"
}
```

Or:

```json
{
  "authorization": "[REDACTED]"
}
```

Many logging libraries support redaction.

For example, with Pino:

```javascript
const logger = pino({
  redact: [
    "req.headers.authorization",
    "req.headers.cookie",
    "password",
    "accessToken",
    "refreshToken"
  ]
});
```

The exact paths depend on your application's log structure.

---

# 8. Log Levels Matter

You learned:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

Now let's learn how to use them properly.

---

## DEBUG

Use for detailed troubleshooting information.

Example:

```javascript
logger.debug({
  studentId,
  courseId
}, "Checking enrollment");
```

Useful during development.

But don't flood production with debug logs unless deliberately enabled.

---

# 9. INFO

Use for normal important events.

Good examples:

```javascript
logger.info("Application started");
```

```javascript
logger.info(
  { userId },
  "User registered"
);
```

```javascript
logger.info(
  { orderId },
  "Order created"
);
```

---

# 10. WARN

Use when something unexpected happened but the application can continue.

Examples:

```text
Database pool 80% utilized
Slow external API
Repeated login failures
Deprecated API used
Cache unavailable
```

Example:

```javascript
logger.warn({
  durationMs: 3500
}, "External service is responding slowly");
```

---

# 11. ERROR

Use when an operation failed.

Examples:

```text
Database query failed
Payment processing failed
External API failed
Unexpected application exception
```

Example:

```javascript
logger.error({
  err,
  requestId: req.id
}, "Database query failed");
```

---

# 12. Don't Abuse ERROR

A common beginner mistake is:

```javascript
logger.error("User entered wrong password");
```

That may not necessarily be a server error.

A failed login can be an expected application event.

Depending on your security requirements, something like:

```text
WARN login_failed
```

may be more appropriate.

Think about severity carefully.

---

# 13. Log Events, Not Every Line of Code

Bad logging:

```javascript
logger.info("Entered controller");
logger.info("Entered service");
logger.info("Entered repository");
logger.info("Running function");
logger.info("Returned from function");
logger.info("Exited function");
```

This creates noise.

Instead:

```javascript
logger.info(
  { studentId },
  "Student profile updated"
);
```

One useful event is better than five meaningless logs.

---

# 14. Avoid Log Noise

Imagine your application receives:

```text
1000 requests/second
```

And every request creates:

```text
Request received
Request authenticated
Controller started
Service started
Repository started
Query started
Query finished
Controller finished
Request finished
```

That's:

```text
9 × 1000
=
9000 logs/second
```

That's huge.

Your logging system becomes part of the problem.

---

# 15. Health Checks Are a Classic Example

Suppose Kubernetes, a load balancer, or a monitoring system calls:

```http
GET /health
```

every few seconds.

If you have:

```text
100 requests/sec
```

you could produce thousands of repetitive logs.

Instead, consider:

- Lowering their log level
    
- Excluding successful health checks
    
- Sampling them
    
- Using metrics instead
    

For example:

```text
GET /health → DEBUG
```

instead of:

```text
GET /health → INFO
```

---

# 16. Log Sampling

**Sampling** means intentionally logging only a subset of events.

Suppose:

```text
1,000,000 requests
```

You might not need a full detailed log for every successful request.

You could:

```text
100% errors
100% slow requests
10% successful requests
```

This dramatically reduces noise.

---

# 17. What Should Always Be Logged?

A useful rule:

```text
Errors
   ↓
Usually 100%

Slow requests
   ↓
Usually 100%

Security events
   ↓
Usually high coverage

Important business events
   ↓
High coverage

Normal successful requests
   ↓
Can be sampled
```

The exact policy depends on your system.

---

# 18. Slow Request Logging ⭐

One of the best logging techniques is to focus on slow requests.

Suppose your normal API response time is:

```text
50–200ms
```

But one request takes:

```text
4500ms
```

That's worth investigating.

You can create a rule:

```text
duration > 1000ms
       ↓
log as WARN
```

Example:

```javascript
if (durationMs > 1000) {
  logger.warn({
    method: req.method,
    path: req.originalUrl,
    durationMs,
    requestId: req.id
  }, "Slow request");
}
```

This is much more useful than logging every successful request at maximum detail.

---

# 19. Don't Log Huge Objects

Bad:

```javascript
logger.info({
  user
});
```

If `user` contains:

```text
profile
settings
permissions
history
preferences
metadata
```

you may generate enormous logs.

Instead:

```javascript
logger.info({
  userId: user.id
}, "User authenticated");
```

Log only what is useful.

---

# 20. Avoid Logging Entire Database Documents

Bad:

```javascript
const student = await Student.findById(id);

logger.info({
  student
});
```

The document may contain sensitive information.

Better:

```javascript
logger.info({
  studentId: student.id
}, "Student retrieved");
```

Use identifiers instead of entire objects.

---

# 21. Avoid Logging Request Bodies by Default

Bad:

```javascript
logger.info({
  body: req.body
});
```

Request bodies may contain:

```text
Passwords
Tokens
Private data
Large files
Personal information
```

Instead, explicitly choose safe fields:

```javascript
logger.info({
  email: req.body.email
}, "Registration request");
```

And even that should be considered carefully depending on privacy requirements.

---

# 22. Don't Log File Upload Contents

Suppose your API supports:

```http
POST /api/upload
```

Don't log the entire file or binary content.

Instead:

```json
{
  "event": "file_uploaded",
  "fileSize": 2048000,
  "mimeType": "image/jpeg"
}
```

Useful metadata without dumping the actual content.

---

# 23. Logging and Privacy

Production logs can contain personal information.

Think carefully before logging:

```text
Email
Phone number
Address
IP address
User profile
Location
Private messages
```

Ask:

> **Do I actually need this information to operate/debug the system?**

If not:

> Don't log it.

This principle is sometimes called **data minimization**.

---

# 24. Logging and Performance

Logging isn't free.

Every log may involve:

```text
Application code
       ↓
Object serialization
       ↓
String/JSON creation
       ↓
I/O
       ↓
Disk/network
       ↓
Log collector
```

At high traffic, this can become expensive.

---

# 25. Synchronous vs Asynchronous Logging

If logging blocks your application:

```text
Request
  ↓
Write log
  ↓
Wait
  ↓
Database
  ↓
Response
```

performance can suffer.

Modern logging libraries such as Pino are designed with high-performance logging in mind.

The general principle:

> **Logging should have as little impact on application performance as reasonably possible.**

---

# 26. Logging Errors Correctly

Bad:

```javascript
logger.error("Something failed");
```

What's missing?

```text
Which operation?
Which request?
Which user?
Which service?
What error?
What endpoint?
```

Better:

```javascript
logger.error({
  requestId: req.id,
  userId: req.user?.id,
  method: req.method,
  path: req.originalUrl,
  error: err.message
}, "Failed to create student");
```

Even better when appropriate:

```javascript
logger.error({
  err,
  requestId: req.id,
  userId: req.user?.id,
  method: req.method,
  path: req.originalUrl
}, "Failed to create student");
```

The logging library can serialize error information more consistently.

---

# 27. Don't Expose Internal Errors to Users

Internally:

```json
{
  "level": "error",
  "requestId": "req-123",
  "error": "MongoServerSelectionError",
  "stack": "..."
}
```

Externally:

```json
{
  "message": "Internal server error",
  "requestId": "req-123"
}
```

This is an excellent production pattern.

```text
Detailed information
       ↓
Internal logs

Safe information
       ↓
Client response
```

---

# 28. Request IDs Are Your Friend

Suppose the user receives:

```json
{
  "message": "Internal server error",
  "requestId": "req-98321"
}
```

You can search:

```text
requestId = req-98321
```

and find:

```text
Request received
Authentication passed
Database query started
Database query failed
Exception occurred
Response 500
```

This makes incident investigation much easier.

---

# 29. Correlation IDs in Distributed Systems

Imagine:

```text
API Gateway
     ↓
Student Service
     ↓
Payment Service
     ↓
Notification Service
```

One operation:

```text
correlationId = corr-123
```

Every service logs:

```text
API Gateway       corr-123
Student Service   corr-123
Payment Service   corr-123
Notification      corr-123
```

You can reconstruct the complete operation.

This becomes increasingly important when applications grow beyond a single Node.js service.

# 30. Production Log Format

A good production log might look like:

```json
{
  "timestamp": "2026-08-15T14:10:20.124Z",
  "level": "error",
  "service": "student-api",
  "environment": "production",
  "requestId": "req-123",
  "method": "POST",
  "path": "/api/students",
  "statusCode": 500,
  "durationMs": 820,
  "error": "MongoServerError",
  "message": "Failed to create student"
}
```

This is excellent because it answers:

```text
When?
What severity?
Which service?
Which environment?
Which request?
Which endpoint?
What status?
How long?
What error?
What happened?
```

---

# 31. Standardize Your Log Fields

Don't write:

```json
{
  "req": "abc"
}
```

in one place and:

```json
{
  "request_id": "abc"
}
```

somewhere else.

Pick a standard.

For example:

```text
requestId
service
environment
level
timestamp
```

Consistency makes searching and dashboards much easier.

---

# 32. Use Event Names

Instead of only:

```text
"User did something"
```

use clear event names:

```json
{
  "event": "user_registered"
}
```

Examples:

```text
user_registered
login_success
login_failed
course_enrolled
order_created
payment_failed
student_updated
database_connection_failed
```

This makes logs easier to search.

---

# 33. Don't Overuse Human-Friendly Messages

This:

```text
"Rahul created a student named Rahul Kumar"
```

is readable.

But structured fields are better:

```json
{
  "event": "student_created",
  "studentId": "stu-123",
  "userId": "user-456"
}
```

Now the logging platform can filter:

```text
event = student_created
```

or:

```text
userId = user-456
```

---

# 34. Environment Should Be Included

It's useful to know whether the event happened in:

```text
development
staging
production
```

For example:

```json
{
  "service": "student-api",
  "environment": "production",
  "level": "error"
}
```

Otherwise you may accidentally investigate a staging error while production is healthy.

---

# 35. Service Name Matters

Imagine you eventually have:

```text
student-api
auth-api
payment-api
notification-api
```

Every log should identify its service.

```json
{
  "service": "student-api"
}
```

This becomes essential for centralized logging.

---

# 36. Don't Log the Same Error Multiple Times

A common architecture problem:

```text
Repository
   ↓
logs error

Service
   ↓
logs same error

Controller
   ↓
logs same error

Global error middleware
   ↓
logs same error
```

One failure produces:

```text
4 identical error logs
```

This creates noise.

Instead, decide where errors should be logged.

For example:

```text
Low-level layer
   ↓
throw error

Global error handler
   ↓
log final error
```

Or log at the layer where meaningful context is first available—but avoid repeated logging of the same exception.

```text

    ↓
```

# 42. Common Logging Mistakes ❌

### Mistake 1

```javascript
console.log(req.body);
```

**Problem:** potentially exposes sensitive information.

---

### Mistake 2

```javascript
logger.info("Something happened");
```

**Problem:** no context.

---

### Mistake 3

```javascript
logger.error(error);
```

everywhere.

**Problem:** inconsistent and potentially duplicated.

---

### Mistake 4

Logging every function call.

**Problem:** huge noise.

---

### Mistake 5

Logging secrets.

**Problem:** serious security issue.

---

### Mistake 6

Logging huge objects.

**Problem:** storage and performance problems.

---

### Mistake 7

Using `ERROR` for everything.

**Problem:** alerts become meaningless.

---

### Mistake 8

No request ID.

**Problem:** difficult to trace a user's request.

---

### Mistake 9

No retention policy.

**Problem:** logs eventually consume disk.

---

### Mistake 10

No environment/service field.

**Problem:** difficult to identify where an event occurred.

# 43. Interview Question ⭐

### Question:

> Why shouldn't we log everything?

### Good answer:

Because excessive logging increases storage and processing costs, creates noisy logs that make troubleshooting harder, can reduce application performance, and increases the chance of accidentally exposing sensitive information. Production logging should capture useful events with appropriate severity and context while avoiding unnecessary or sensitive data.

---

# 44. Interview Question ⭐

### Question:

> Why are structured logs better than plain text logs?

### Answer:

Structured logs use consistent fields such as `timestamp`, `level`, `service`, `requestId`, and `statusCode`. This makes logs easier for machines and humans to search, filter, aggregate, analyze, and visualize in centralized logging systems.

---

# 45. Interview Question ⭐

### Question:

> What is a correlation ID?

### Answer:

A correlation ID is an identifier used to connect related operations across requests or services. It allows engineers to follow one business operation through multiple components of a distributed system.

---

# 46. Interview Question ⭐

### Question:

> What should you never log?

A good answer:

> Secrets and sensitive data such as passwords, authentication tokens, API keys, session cookies, private keys, payment information, and unnecessary personal data should not be logged. Sensitive fields should be omitted or explicitly redacted.
