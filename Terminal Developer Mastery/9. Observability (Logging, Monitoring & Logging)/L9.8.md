# 1. What Is Monitoring?

Monitoring means continuously observing the state and performance of a system.

For a Linux server, we might monitor:

```text
CPU
Memory
Disk
Network
Processes
Load
Uptime
Services
```

For example:

```text
CPU:       42%
Memory:    61%
Disk:      73%
Load:      1.42
Network:   25 Mbps
```

Monitoring answers:

> **"What is happening to my system?"**

---

# 2. Monitoring vs Observability

These terms are related but not identical.

### Monitoring

You watch known signals:

```text
CPU > 90%
Disk > 85%
Memory > 90%
```

Then:

```text
Alert 🚨
```

### Observability

You investigate the system using:

```text
Logs
Metrics
Traces
```

to understand **why** something happened.

Think:

```text
Monitoring
   ↓
Something is wrong

Observability
   ↓
Why is it wrong?
```

# 4. CPU Monitoring

CPU represents the processing work being performed by the system.

You might see:

```text
CPU Usage: 25%
```

or:

```text
CPU Usage: 95%
```

But remember:

> **High CPU isn't automatically a problem.**

A server intentionally doing heavy computation may correctly use 100% CPU.

The real question is:

> **Is the CPU usage high compared with the workload and expected baseline?**

---

# 5. CPU Example

Suppose your Node.js API normally has:

```text
CPU:
20–40%
```

Suddenly:

```text
CPU:
98%
```

for 20 minutes.

That's suspicious.

Possible causes:

```text
Infinite loop
CPU-heavy operation
Too many requests
Expensive database processing
Compression
Encryption
Malicious traffic
Memory pressure
```

You need more evidence before deciding the cause.

---

# 6. CPU Usage Isn't One Number

A CPU can spend time in different states.

You may encounter:

```text
user
system
idle
iowait
steal
```

### User

CPU time spent running user-space applications.

For example:

```text
Node.js
Python
Nginx
```

### System

CPU time spent inside the kernel.

For example:

```text
System calls
Networking
Filesystem operations
```

### Idle

CPU isn't doing useful work.

### I/O wait

CPU is waiting for I/O operations.

For example:

```text
Disk
Network
```

### Steal

Important mainly in virtualized environments.

It represents CPU time taken by the hypervisor/host from your virtual machine.

# 7. Memory Monitoring

RAM is another critical resource.

Check:

```bash
free -h
```

You might see:

```text
               total   used   free
Mem:            7.6G    4.2G   800M
Swap:           2.0G    200M   1.8G
```

Don't immediately think:

```text
free = low
```

means:

> "My server is almost out of memory."

Linux deliberately uses RAM for caching.

---

# 8. Linux Uses RAM for Cache

Suppose:

```text
Total RAM = 8 GB
```

You might see:

```text
Used = 6.5 GB
Free = 500 MB
```

That doesn't necessarily mean you're in trouble.

Linux may be using memory for:

```text
Filesystem cache
Buffers
Application memory
Kernel memory
```

Some of that memory can be reclaimed when applications need it.

That's why `free -h` is more useful than simply looking at the "free" column.

---

# 9. The `available` Memory Concept ⭐

Run:

```bash
free -h
```

Example:

```text
               total   used   free  shared  buff/cache  available
Mem:            7.6G   4.1G   500M    300M      3.0G       3.2G
```

The important number is often:

```text
available
```

It estimates how much memory can be given to applications without significant swapping.

So:

```text
free = 500 MB
available = 3.2 GB
```

does **not** mean:

> "Only 500 MB RAM remains."

---

# 10. Swap

Swap is disk space used when RAM pressure becomes high.

Conceptually:

```text
RAM
 ↓
Full
 ↓
Swap
 ↓
Disk
```

Disk is much slower than RAM.

So heavy swapping can cause:

```text
Slow application
High latency
Poor performance
```

Check:

```bash
free -h
```

Example:

```text
Swap:
2.0G total
1.8G used
```

That deserves investigation.

---

# 11. Memory Leak

A memory leak happens when an application continues consuming memory without properly releasing it.

Imagine:

```text
10:00 → 300 MB
11:00 → 500 MB
12:00 → 900 MB
13:00 → 1.5 GB
14:00 → 2.5 GB
```

Eventually:

```text
RAM exhausted
      ↓
Swap increases
      ↓
Application becomes slow
      ↓
OOM killer may terminate processes
```

This is why memory monitoring matters.

---

# 12. Disk Monitoring

There are two important questions:

### Question 1

How much disk space is available?

Use:

```bash
df -h
```

### Question 2

Which files/directories are consuming the space?

Use:

```bash
du -sh *
```

or:

```bash
sudo du -sh /var/* 2>/dev/null
```

These answer different questions.

# 13. Disk Usage Example

Suppose:

```bash

```

shows:

```text
Filesystem      Size  Used Avail Use%
/dev/nvme0n1p2  100G   92G    8G  92%
```

Your disk is:

```text
92% full
```

That's worth investigating.

Possible causes:

```text
Logs
Docker images
Database files
Backups
Uploaded files
Temporary files
Package caches
```

---

# 14. Disk Usage vs Disk I/O

These are different.

### Disk usage

How much storage capacity is occupied:

```text
92 GB / 100 GB
```

### Disk I/O

How actively the disk is reading/writing.

For example:

```text
Read:  300 MB/s
Write: 150 MB/s
```

A disk can have:

```text
20% capacity used
```

but still be experiencing:

```text
Heavy I/O
```

So:

```text
Capacity ≠ Performance
```

This distinction is extremely important.

# 17. What Is Load Average? ⭐⭐⭐⭐⭐

This is one of the most misunderstood Linux metrics.

Example:

```text
load average: 0.72, 0.81, 0.65
```

These represent approximately:

```text
1 minute
5 minutes
15 minutes
```

So:

```text
0.72 → last 1 minute
0.81 → last 5 minutes
0.65 → last 15 minutes
```

But:

> **Load average is NOT simply CPU percentage.**

This distinction is very important.

---

# 18. What Does Load Average Represent?

Load average roughly represents the amount of work that is:

```text
Runnable
or
waiting for certain resources
```

It can include tasks waiting for CPU and certain uninterruptible I/O states.

So high load can come from:

```text
CPU pressure
Disk I/O pressure
Other resource contention
```

---

# 19. Load Average Depends on CPU Count

Suppose you have:

```text
2 CPU cores
```

and:

```text
load = 2
```

That's approximately:

```text
2 units of work
2 CPU cores
```

The system may be fully utilized.

But:

```text
load = 2
```

on:

```text
8 CPU cores
```

is much less concerning.

Therefore:

> **Always interpret load average relative to the number of CPU cores.**

---

# 20. Find CPU Count

Run:

```bash
nproc
```

Example:

```text
8
```

Your system has 8 logical CPUs.

Then:

```bash
uptime
```

might show:

```text
load average: 3.5, 2.9, 2.4
```

On an 8-CPU system, that's not necessarily alarming.

---

# 21. Load Average Example

### Server A

```text
CPU cores: 2
Load: 4.0
```

Potentially concerning.

### Server B

```text

Load: 4.0
```

Much less concerning.

### Server C

```text
CPU cores: 16
Load: 4.0
```

Likely quite comfortable, assuming no other issue.

The raw number isn't enough.

# 22. CPU vs Load

Imagine:

```text
CPU = 20%
Load = 8
```

That might seem strange.

But it can happen when many processes are waiting on I/O rather than actively consuming CPU.

This is why:

```text
CPU
+
Load
+
I/O
```

should often be considered together.

# 26. Liveness vs Readiness

You'll encounter these terms in modern production systems.

### Liveness

Question:

> Is the application process alive?

Example:

```text
GET /health/live
```

Response:

```json
{
  "status": "alive"
}
```

### Readiness

Question:

> Is the application ready to serve real traffic?

Example:

```text
GET /health/ready
```

It might verify:

```text
Database connection
Required dependencies
Application initialization
```

Conceptually:

```text
Alive ≠ Ready
```

---

# 27. Example

Suppose Node.js is running:

```text
Node process → alive
```

But MongoDB is unavailable:

```text
MongoDB → unavailable
```

Then:

```text
Liveness → PASS
Readiness → FAIL
```

This distinction becomes especially important with containers and orchestration systems.

# 28. Monitoring Baselines ⭐⭐⭐⭐⭐

One of the most important ideas in monitoring is the **baseline**.

Suppose your server normally has:

```text
CPU: 20–40%
Memory: 50–65%
Load: 1–2
Disk: 40–60%
```

This is your normal behavior.

Then suddenly:

```text
CPU: 95%
Memory: 90%
Load: 8
```

You know something changed.

Without a baseline:

```text
CPU = 70%
```

doesn't tell you much.

Maybe 70% is normal.

Maybe it's extremely unusual.

---

# 29. Monitoring Trends

Don't only look at the current number.

Look at:

```text
Current
↓
Previous
↓
Trend
```

Example:

```text

10:00 → 45%
11:00 → 50%
12:00 → 55%
13:00 → 63%
14:00 → 71%
15:00 → 79%
```

That's much more interesting than:

```text

```

You may be seeing a memory leak.

---

# 30. Rate of Change Matters

Suppose disk usage is:

```text
Monday → 40%
Tuesday → 41%
Wednesday → 42%
Thursday → 43%
```

That's probably normal.

But:

```text
14:00 → 50%
14:30 → 65%
15:00 → 80%
15:30 → 95%
```

Something is happening.

Maybe:

```text
Runaway logs
Backup
Uploaded files

Temporary files
```

Monitoring trends helps detect this.

# 31. Monitoring Thresholds

You can define thresholds.

Example:

```text
CPU > 80%
Memory > 85%
Disk > 80%
Disk > 90% → critical
```

But don't blindly alert on every threshold.

For example:

```text
CPU > 80%
```

for:

```text
10 seconds
```

may be completely normal.

Better:

```text
CPU > 80%
for 10 minutes
```

might be more meaningful.

This reduces alert noise.

# 57. Interview Questions ⭐

### Q1. What is monitoring?

> Monitoring is the continuous collection and observation of system and application signals such as CPU, memory, disk, network, latency, and service health to detect abnormal behavior and operational problems.

---

### Q2. What is load average?

> Load average represents the average amount of work involving runnable or certain uninterruptible tasks over approximately 1, 5, and 15 minutes. It should be interpreted relative to the number of CPU cores and other resource conditions.

---

### Q3. What is the difference between `df` and `du`?

> `df` shows filesystem-level disk capacity and usage, while `du` helps identify which directories or files are consuming disk space.

---

### Q4. Why isn't low free memory necessarily a problem on Linux?

> Linux uses available RAM for filesystem caches and buffers. The `available` value is generally more useful than the raw `free` value for understanding how much memory applications can still use.

---

### Q5. Why monitor trends instead of only current values?

> A single value provides limited context. Trends reveal gradual changes such as memory leaks, increasing disk consumption, rising traffic, or deteriorating application performance.
