**Module:** 9 — Observability

## 🎯 Goal

```text

```

The important goal isn't memorizing commands.

> **Which tool should I use when something goes wrong?**

# 1. Your Linux Monitoring Toolkit

Think of these tools as different diagnostic instruments:

```text
                  Linux Server
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
     CPU/RAM         Disk I/O         History
       │               │                │
   top/htop/btop     iostat            sar
   vmstat/free
       │
       ▼
     System
      state
```

Each tool answers different questions.

|Tool|Main purpose|
|---|---|
|`top`|Live processes + CPU/RAM|
|`htop`|Interactive process monitoring|
|`btop`|Modern visual monitoring|
|`vmstat`|CPU, memory, processes, I/O|
|`iostat`|Disk/device performance|
|`free`|Memory + swap|
|`uptime`|Uptime + load average|
|`sar`|Historical system statistics|

# 2. Start With `uptime`

When you first SSH into a server:

```bash
uptime
```

Example:

```text
14:32:10 up 12 days, 4:31, 2 users, load average: 1.42, 1.18, 0.95
```

This immediately gives you:

```text
Current time
Uptime
Logged-in users
1-minute load
5-minute load
15-minute load
```

---

# 3. Why `uptime` Is Useful

Suppose a user says:

> "The server became slow."

You can quickly check:

```bash
uptime
```

Suppose you get:

```text
load average: 12.5, 10.2, 8.7
```

and:

```bash
nproc
```

returns:

```text
4
```

Now you have a reason to investigate.

But don't stop there.

`uptime` tells you:

> **Something might be wrong.**

It doesn't tell you:

> **Why.**

That's where the other tools come in.

---

# 4. `free` — Memory Investigation

Run:

```bash
free -h
```

Example:

```text
               total   used   free  shared  buff/cache  available
Mem:            7.6Gi   4.2Gi  600Mi  250Mi      2.8Gi       3.1Gi
Swap:           2.0Gi   100Mi  1.9Gi
```

Important values:

```text
total
used
free
buff/cache
available
swap
```

For practical diagnosis, pay special attention to:

```text
available
swap
```

---

# 5. Why `free -h` Uses `-h`

Without `-h`:

```bash
free
```

you might get:

```text
Mem: 7964380 4231240 ...
```

Not very friendly.

With:

```bash
free -h
```

you get:

```text
7.6Gi
4.2Gi
3.1Gi
```

`-h` means:

> Human-readable.

You'll use this option constantly.

---

# 6. Check Memory Continuously

You can use:

```bash
free -h -s 2
```

This refreshes approximately every 2 seconds.

Conceptually:

```text
free
 ↓
wait 2 sec
 ↓
free
 ↓
wait 2 sec
 ↓
free
```

This can help you observe changing memory usage.

Press:

```text
Ctrl + C
```

to stop.

# 7. `top` — Your First Major Monitoring Tool ⭐⭐⭐⭐⭐

Run:

```bash
top
```

You'll get a live process monitor.

It shows information about:

```text
Load
CPU
Memory
Processes
Process IDs
```

A typical screen contains something like:

```text
top - 14:40:01 up 12 days
Tasks: 200 total
%Cpu(s): 15.2 us, 4.1 sy, 80.0 id
MiB Mem : 7800 total
MiB Swap: 2048 total
```

Below that you'll see processes.

---

# 8. Understanding the Top Section

Let's break it down.

### Load

```text
load average:
1.2
1.0
0.8
```

These are approximately:

```text
1 minute
5 minutes
15 minutes
```

---

# 9. CPU Fields in `top`

You may see:

```text
%Cpu(s): 10.0 us, 2.0 sy, 0.0 ni, 87.0 id, 1.0 wa, ...
```

Important fields:

### `us`

User-space CPU usage.

### `sy`

Kernel/system CPU usage.

### `id`

Idle CPU.

### `wa`

I/O wait.

### `st`

Steal time in virtualized environments.

---

# 10. Why I/O Wait Matters

Suppose you see:

```text
us = 20%
sy = 5%
id = 10%
wa = 65%
```

You might think:

> "CPU is heavily used."

But a huge part of the time is actually:

```text
wa = 65%
```

The CPU is waiting for I/O.

This points you toward:

```text
Disk
Storage
Database I/O
Other I/O bottlenecks
```

rather than simply "CPU is too slow."

# 12. PID

PID means:

> **Process ID**

Example:

```text
PID
4821
```

You can later investigate it:

```bash
ps -p 4821 -f
```

or:

```bash
ls -l /proc/4821
```

---

# 13. `%CPU`

This tells you how much CPU the process is consuming.

Example:

```text
node      85.4
```

Maybe your Node.js process is doing heavy work.

But remember:

On multi-core systems, a process can show more than 100% CPU.

For example:

```text
node    350%
```

can mean it is consuming roughly 3.5 logical CPUs' worth of CPU time.

---

# 14. `%MEM`

This shows the process's share of physical memory.

Example:

```text
node    15.2
```

If you see:

```text
node    50.0
```

you should investigate what the process is doing.

---

# 15. Sorting in `top`

One of the most useful things you can do is sort processes.

Press:

```text
P
```

This sorts by CPU usage.

Then:

```text
M
```

sorts by memory usage.

So during an incident:

```text
CPU problem
   ↓
Press P

Memory problem
   ↓
Press M
```

Very useful.

---

# 16. Other Useful `top` Keys

Inside `top`:

```text
P → CPU
M → Memory
k → Kill process
r → Change priority
1 → Show individual CPU cores
q → Quit
```

You don't need to memorize everything.

Start with:

```text
P
M
1

```

---

# 17. Show Individual CPU Cores

Press:

```text
1
```

inside `top`.

You may see:

```text
%Cpu0
%Cpu1
%Cpu2
%Cpu3
```

This is useful when one CPU core is overloaded while the others are relatively idle.

For example:

```text
CPU0 → 99%
CPU1 → 15%
CPU2 → 18%
CPU3 → 20%
```

This can indicate a workload that isn't spreading well across cores.

# 19. Why `htop` Is Popular

`htop` is an interactive alternative to `top`.

It gives you:


Conceptually:

```text

```

# 20. `top` vs `htop`

|Feature|`top`|`htop`|
|---|---|---|
|Usually preinstalled|Yes|Often not|
|Interactive|Yes|Yes|
|Visual|Basic|Better|
|Process tree|Limited|Better|
|Beginner-friendly|Medium|High|
|Server environments|Excellent|Excellent|

A good Linux engineer should know both.

# 21. `htop` Process Tree

One very useful feature:

```text

```

Depending on version/configuration, this can toggle a tree view.

You might see:

```text

 ├── nginx
 ├── sshd
 └── node
      ├── node
      └── worker
```

This helps you understand parent/child relationships.

---

# 22. Killing a Process with `htop`

You can select a process and use:

```text
F9
```

to send a signal.

But:

> **Don't kill production processes blindly.**

First understand:

```text
What is it?
Who owns it?
Why is it running?
Will systemd restart it?
Will killing it cause downtime?
```

Observability comes before intervention.

# 26. `vmstat` — System-Wide Performance

Now we reach an extremely useful command:

```bash
vmstat
```

Run:

```bash
vmstat
```

You may see:

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs  us sy id wa
```

It gives a compact overview of:

```text
Processes
Memory
Swap
I/O
System activity
CPU
```

---

# 27. `vmstat` With an Interval

A more useful command:

```bash
vmstat 2
```

means:

> Display statistics every 2 seconds.

Stop:

```text
Ctrl + C
```

You can also limit the number of samples:

```bash
vmstat 2 5
```

Meaning:

```text
Every 2 seconds
5 reports
```

This is extremely useful for troubleshooting.

---

# 28. Important `vmstat` Columns

### `r`

Runnable processes waiting for CPU.

High values can indicate CPU pressure.

### `b`

Processes blocked, often waiting on I/O.

High values can point toward I/O pressure.

### `si`

Swap in.

### `so`

Swap out.

High swap activity can indicate memory pressure.

---

# 29. `vmstat` CPU Columns

You'll see:

```text
us
sy
id
wa
st
```

Similar to `top`.

Meaning:

```text
us → user CPU
sy → system CPU
id → idle
wa → I/O wait
st → steal
```

This makes `vmstat` useful for getting a compact system-level picture.

---

# 30. Example `vmstat` Investigation

Suppose:

```text
r   b   si   so   us  sy  id  wa
12  0    0    0   95   3   2   0
```

Interpretation:

```text
r = 12
```

Many tasks want CPU.

```text
us = 95
```

CPU heavily occupied by user processes.

```text
wa = 0
```

I/O wait isn't the main issue.

Likely:

> CPU pressure.

---

# 31. Another Example

```text
r   b   si   so   us  sy  id  wa
2   8   500  400   20   5  10  65
```

Now:

```text
si/so high
wa high
b high
```

This points toward:

```text
Memory pressure
+
I/O pressure
```

You would investigate:

```text
free -h
iostat
top
```

Install if needed:


# 33. What Does `iostat` Tell You?

It can show:

```text
CPU statistics
Device statistics
Read/write operations
Throughput
Utilization
Latency-related indicators
```

For example:

```text
Device
nvme0n1
```

You might see:

```text
r/s
w/s
rkB/s
wkB/s
await
%util
```

---

# 34. Important `iostat` Fields

### `r/s`

Reads per second.

### `w/s`

Writes per second.

### `rkB/s`

Read throughput.

### `wkB/s`

Write throughput.

### `await`

Average I/O request time.

### `%util`

Approximate device utilization.

---

# 35. `await`

Suppose:

```text
await = 2ms
```

That's very different from:

```text
await = 300ms
```

High latency can indicate:

```text
Storage contention
Slow disks
Heavy workload
Underlying infrastructure problems
```

Always interpret it with the device type and workload.

---

# 36. `%util`

If you see:

```text
%util = 95%
```

the device is very busy.

But don't treat one metric as absolute proof of a bottleneck.

Combine:

```text
%util
await
throughput
queue depth
application latency
```

and your workload characteristics.

---

# 37. Example Disk Incident

Users report:

> "API requests are taking 5 seconds."

You run:

```bash
iostat -xz 2
```

and find:

```text
await = 250ms
%util = 98%
```

Then:

```text
top
```

shows:

```text
wa = 70%
```

Now the evidence strongly suggests:

```text
Application latency
      ↓
Storage I/O pressure
      ↓
High I/O wait
```

That's a much stronger diagnosis than:

> "The server is slow."

# 38. `sar` — Historical Monitoring ⭐⭐⭐⭐⭐

Now one of the most important tools:

```bash
sar
```

`sar` is part of the `sysstat` package.

Install:

```bash
sudo apt install sysstat
```

Depending on your distribution, the service/configuration may also need to be enabled before historical collection begins.

---

# 39. Why `sar` Is Special

Most tools show:

> **What is happening right now?**

`sar` can show:

> **What happened earlier?**

That's incredibly useful.

Imagine:

```text
10:00 → server normal
11:00 → server normal
12:30 → users complain
13:00 → you investigate
```

The problem disappeared.

`top` now looks normal.

How do you investigate?

Historical metrics.

That's where `sar` helps.

---

# 40. CPU History

For CPU statistics:

```bash
sar -u
```

You may see:

```text
12:00:01  all  %user  %system  %iowait  %idle
12:10:01  all  20.0   5.0      2.0      73.0
12:20:01  all  25.0   6.0      3.0      66.0
```

Now you can see historical behavior.

---

# 41. Memory History

You can use:

```bash
sar -r
```

to examine memory-related statistics.

This can help identify:

```text
Memory pressure
Free memory trends
Paging
```

---

# 42. Network History

You can use:

```bash
sar -n DEV
```

to examine network interface activity.

This can help answer:

> Was network traffic unusually high at 14:00?

---

# 43. Load History

You can use:

```bash
sar -q
```

to examine run queue/load-related statistics.

This can help correlate:

```text
High load
+
High CPU
+
High I/O
```

over time.

---

# 44. Disk History

Depending on your `sysstat` version and configuration, commands such as:

```bash
sar -d
```

can show historical device activity.

This is useful for questions like:

> Did disk activity spike when the application became slow?

---

# 45. `sar` Is an Incident Investigation Tool

Imagine:

```text
User:
"The API was extremely slow at 2 PM."

You:
"Is it still slow?"

User:
"No."
```

Current monitoring:

```text

```

# 47. A Real Incident Workflow

Suppose:

> **Users report the API is slow.**

Don't randomly run commands.

Follow a method.

### Step 1 — Load

```bash

```

Ask:

```text

```

---

### Step 2 — CPU

```bash

```

```text

```

```text

```

---

### Step 3 — Memory

```bash

```

Ask:

```text

```

---

### Step 4 — System pressure

```bash

```

Ask:

```text
Is r high?

Is wa high?
```

---

### Step 5 — Disk

```bash

```




### Step 7 — Logs

Then:

```bash

```

Ask:

```text

```

This is observability in practice.

# 50. Create a Monitoring Function

Since you're becoming comfortable with the Linux terminal, create a small helper.

Add to your shell configuration:

```bash
healthcheck() {
    echo "===== UPTIME ====="
    uptime

    echo
    echo "===== MEMORY ====="
    free -h

    echo
    echo "===== DISK ====="
    df -h

    echo
    echo "===== FAILED SERVICES ====="
    systemctl --failed --no-pager
}
```

Reload your shell configuration, depending on your shell:

```bash
source ~/.zshrc
```

Then:

```bash
healthcheck
```

Now you have your own mini server health command.

# 52. Monitoring vs Diagnosis

A common beginner mistake is thinking:

> "I ran `top`, therefore I monitored the server."

Not exactly.

The real skill is:

```text
Tool
 ↓
Observation
 ↓
Interpretation
 ↓
Hypothesis
 ↓
Verification
```

Example:

```text
top
 ↓
Node.js uses 95% CPU
 ↓
Maybe application workload is high
 ↓
Check request rate
 ↓
Check logs
 ↓
Check recent deployment
 ↓
Find expensive endpoint
```

That's **diagnosis**.

---

# 53. Don't Make This Mistake

Suppose:

```text
CPU = 90%
```

You immediately:

```bash
kill -9 node_pid
```

❌ Bad idea.

You might hide the symptom while losing evidence.

Better:

```text
1. Observe
2. Identify process
3. Check logs
4. Check recent changes
5. Understand cause
6. Decide whether intervention is needed
```

Production debugging should preserve evidence whenever possible.

# 55. Interview Questions ⭐

### Q1. What is the difference between `top`, `htop`, and `btop`?

> They are interactive system monitoring tools. `top` is the traditional widely available tool, `htop` provides a more interactive and user-friendly interface, and `btop` provides a more modern visual dashboard.

---

### Q2. What does `vmstat` show?

> `vmstat` provides a compact view of process activity, memory, swap, I/O, system activity, and CPU utilization. It is useful for identifying resource pressure and performance bottlenecks.

---

### Q3. What is `iostat` used for?

> `iostat` is used to analyze CPU and storage I/O performance, including read/write activity, throughput, latency-related metrics such as `await`, and device utilization.

---

### Q4. Why is `sar` useful?

> `sar` collects and reports historical system activity. It is particularly useful when an incident has already ended and current tools no longer show the problem.

---

### Q5. What is I/O wait?

> I/O wait is CPU time during which the CPU is waiting for certain I/O operations to complete. High I/O wait can indicate storage or other I/O-related bottlenecks.

## 🔥 One rule to remember

> **Don't ask "Which monitoring command should I memorize?" Ask "What question am I trying to answer?"**

```text
"What's happening now?"
        ↓
top / htop / btop

"Is memory under pressure?"
        ↓
free / vmstat

"Is storage slow?"
        ↓
iostat

"Where is disk space going?"
        ↓
df / du

"What happened earlier?"
        ↓
sar

"What's the overall situation?"
        ↓
uptime + top + free + df
```

That mindset will make you much better at Linux troubleshooting than simply memorizing dozens of commands.
