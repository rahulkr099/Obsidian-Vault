# 🤔 Why Use JSON Files?

Until now, you've written JSON directly in the command:

```bash
curl \
-H "Content-Type: application/json" \
-d '{"name":"Rahul","age":21}' \
<https://httpbin.org/post>
```

This works well for small requests.

But imagine sending this:

```json
{
  "user": {
    "name": "Rahul",
    "email": "rahul@example.com",
    "address": {
      "city": "Bokaro",
      "state": "Jharkhand",
      "country": "India"
    },
    "skills": [
      "JavaScript",
      "Node.js",
      "MongoDB",
      "Docker",
      "Linux"
    ]
  }
}
```

Putting all of that inside your terminal quickly becomes difficult to read and edit.

---

# The Better Way

Create a file.

Example:

**user.json**

```json
{
  "name": "Rahul",
  "age": 21
}
```

Then:

```bash
curl \
-H "Content-Type: application/json" \
-d @user.json \
<https://httpbin.org/post>
```

Notice:

```bash
@user.json
```

means:

> Read the contents of `user.json` and send them as the request body.

---

# How `@` Works

Without `@`

```bash
-d '{"name":"Rahul"}'
```

The JSON is written directly.

With `@`

```bash
-d @user.json
```

`curl` opens the file, reads it, and sends its contents.

## Step 2

## Step 3

Write:

```json
{
  "name": "Rahul",
  "age": 21,
  "city": "Bokaro"
}
```

Save it.

---

## Step 4

Send it.

```bash
curl \
-H "Content-Type: application/json" \
-d @user.json \
<https://httpbin.org/post>
```

Response:

```json
{
  "json": {
    "name": "Rahul",
    "age": 21,
    "city": "Bokaro"
  }
}
```

Exactly the same as typing the JSON manually.

# Pretty Print

```bash
curl \
-H "Content-Type: application/json" \
-d @user.json \
<https://httpbin.org/post> | jq
```

Only show the JSON:

```bash
curl \
-H "Content-Type: application/json" \
-d @user.json \
<https://httpbin.org/post> | jq '.json'
```

# Why Professionals Prefer Files

Imagine you're testing a registration API.

Instead of:

```bash
curl \
-d '{"name":"Rahul","email":"rahul@example.com","password":"123456"}'
```

Create:

```
register.json
```

```json
{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "123456"
}
```

Now your command becomes:

```bash
curl \
-H "Content-Type: application/json" \
-d @register.json \
<http://localhost:3000/api/register>
```

Much cleaner.

---

# Reusing Request Bodies

Suppose you want to test different users.

Create:

```
users/
├── user1.json
├── user2.json
├── admin.json
└── guest.json
```

Then:

```bash
curl \
-H "Content-Type: application/json" \
-d @users/admin.json \
<http://localhost:3000/api/register>
```

or

```bash
curl \
-H "Content-Type: application/json" \
-d @users/guest.json \
<http://localhost:3000/api/register>
```

No need to rewrite commands.

# Real Backend Project Structure

A common testing directory might look like:

```
api-testing/
│
├── payloads/
│   ├── login.json
│   ├── register.json
│   ├── create-todo.json
│   ├── update-todo.json
│   └── profile.json
│
├── scripts/
│   ├── login.sh
│   ├── register.sh
│   └── create-todo.sh
│
└── responses/
```

This is similar to how Postman stores requests in collections.

# Common Mistakes

## ❌ Missing `@`

Wrong:

```bash
curl \
-d user.json
```

This sends:

```
user.json
```

as the request body.

---

Correct:

```bash
curl \
-d @user.json
```

---

## ❌ Wrong File Path

Wrong:

```bash
-d @users.json
```

when the file is actually:

```
payloads/users.json
```

Correct:

```bash
-d @payloads/users.json
```

---

## ❌ Invalid JSON

Example:

```json
{
"name":"Rahul",
}
```

Validate first:

```bash
jq . user.json
```

If it's valid, `jq` prints formatted JSON.

If not, it reports the error.

---

# Absolute vs Relative Paths

Suppose you're in:

```
/home/rahul/projects/api-testing
```

Relative path:

```bash
-d @payloads/login.json
```

Absolute path:

```bash
-d @/home/rahul/projects/api-testing/payloads/login.json
```

Relative paths are usually preferred because they're easier to share and use across systems.

# 💡 Pro Tips

### 1. Use meaningful file names

Instead of:

```
test.json
```

Prefer:

```
login.json
register.json
create-todo.json
update-profile.json
```

---

### 2. Keep payloads under version control

Store your `payloads/` directory in Git. This makes it easy to review changes and collaborate with teammates.

---

### 3. Pair payloads with shell scripts

Example:

```
api-testing/
├── payloads/
│   └── login.json
└── scripts/
    └── login.sh
```

**[login.sh](http://login.sh)**

```bash
#!/usr/bin/env bash

curl \
  -H "Content-Type: application/json" \
  -d @payloads/login.json \
  <http://localhost:3000/api/login> | jq
```

Now you can simply run:

```bash
./scripts/login.sh
```

This is a simple but powerful workflow used by many backend developers.
