# Why Debugging Matters

Every backend developer eventually sees errors like:

- ❌ `400 Bad Request`
- ❌ `401 Unauthorized`
- ❌ `403 Forbidden`
- ❌ `404 Not Found`
- ❌ `409 Conflict`
- ❌ `413 Payload Too Large`
- ❌ `415 Unsupported Media Type`
- ❌ `422 Unprocessable Entity`
- ❌ `500 Internal Server Error`

Instead of guessing, you'll learn how to find the exact cause.

# 1. The Golden Rule

When an API doesn't work, don't change random things.

Follow this order:

```
1. URL
2. HTTP Method
3. Headers
4. Request Body
5. Authentication
6. Server Logs
7. Response Body
```

Most bugs are found within these seven steps.

---

# 2. Verbose Mode (`v`)

The first tool every backend developer reaches for:

```bash
curl -v <https://httpbin.org/get>
```

Example output:

```
> GET /get HTTP/1.1
> Host: httpbin.org
> User-Agent: curl/8.5.0
> Accept: */*

< HTTP/1.1 200 OK
< Content-Type: application/json
< Content-Length: 305
```

---

## Understanding the Symbols

### `>`

Means:

```
Request sent by curl
```

Example:

```
> POST /users HTTP/1.1
> Content-Type: application/json
```

---

### `<`

Means:

```
Response from server
```

Example:

```
< HTTP/1.1 201 Created
< Content-Type: application/json
```

---

# 3. Silent Mode (`s`)

Hide progress meter:

```bash
curl -s <https://httpbin.org/get>
```

Useful for scripting.

Combine with `jq`:

```bash
curl -s <https://httpbin.org/get> | jq
```

---

# 4. Include Response Headers (`i`)

Normally:

```bash
curl <https://httpbin.org/get>
```

Shows only:

```json
{
  ...
}
```

Using:

```bash
curl -i <https://httpbin.org/get>
```

Shows:

```
HTTP/1.1 200 OK
Content-Type: application/json

{
 ...
}
```

Very useful for debugging.

---

# 5. Headers Only (`I`)

Need only metadata?

```bash
curl -I <https://httpbin.org/get>
```

Output:

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 305
```

No response body.

---

# 6. Save Response to a File

Instead of printing:

```bash
curl <https://httpbin.org/json>
```

Save it:

```bash
curl -o response.json <https://httpbin.org/json>
```

Open it:

```bash
cat response.json
```

Pretty-print:

```bash
jq . response.json
```

---

# 7. Save with Original Filename

```bash
curl -O <https://example.com/file.pdf>
```

Notice:

```
-o
```

You choose the filename.

```
-O
```

The server chooses the filename.

# 8. View HTTP Status Code

Sometimes you only care about the status.

```bash
curl \
-s \
-o /dev/null \
-w "%{http_code}\n" \
<https://httpbin.org/status/404>
```

Output:

```
404
```

Very useful in Bash scripts.

---

# 9. View Multiple Metrics

```bash
curl \
-o /dev/null \
-s \
-w "
Status: %{http_code}
Time: %{time_total}
Size: %{size_download}
IP: %{remote_ip}
\n" \
<https://httpbin.org/get>
```

Example:

```
Status: 200
Time: 0.184
Size: 305
IP: 52.6.xx.xx
```

# 10. Following Redirects

Some URLs redirect.

Example:

```bash
curl <http://github.com>
```

May return:

```
301 Moved Permanently
```

Automatically follow redirects:

```bash
curl -L <http://github.com>
```

# 11. Debugging JSON APIs

Suppose:

```bash
curl \
-H "Content-Type: application/json" \
-d '{"name":"Rahul"}' \
<http://localhost:3000/users>
```

Returns:

```
400 Bad Request
```

Checklist:

✅ Is JSON valid?

```bash
echo '{"name":"Rahul"}' | jq
```

---

✅ Is `Content-Type` correct?

```
application/json
```

---

✅ Is `express.json()` enabled?

---

✅ Is middleware before routes?

---

# 12. Debugging Authentication

Suppose:

```
401 Unauthorized
```

Check:

```bash
curl -v \
-H "Authorization: Bearer TOKEN" \
<http://localhost:3000/profile>
```

Questions:

- Is the token present?
- Is it expired?
- Is "Bearer" spelled correctly?
- Is there a space after `Bearer`?

Correct:

```
Authorization: Bearer eyJ...
```

Wrong:

```
Authorization:Bearer
```

---

# 13. Debugging File Uploads

If upload fails:

Check:

```bash
-F "photo=@image.jpg"
```

Not:

```bash
-d @image.jpg
```

Also verify:

```bash
ls image.jpg
```

Does the file exist?

# 14. Debugging Express

Suppose:

```jsx
app.post("/users",(req,res)=>{

```

Nothing appears.

Check:

### Middleware

```jsx
app.use(express.json());
```

---

### Route

Correct?

```
POST /users
```

Not:

```
GET /users
```

---

### Content-Type

Correct?

```
application/json
```

# 15. HTTP Status Codes

## 200 OK

Everything worked.

---

## 201 Created

A resource was successfully created.

Common after:

```
POST /users
```

---

## 204 No Content

Success.

No response body.

Usually after DELETE.

---

## 400 Bad Request

Client sent invalid data.

Examples:

- Invalid JSON
- Missing field
- Wrong format

---

## 401 Unauthorized

Authentication failed.

Missing or invalid token.

---

## 403 Forbidden

Authenticated.

But not allowed.

Example:

Normal user accessing admin endpoint.

---

## 404 Not Found

Wrong URL.

Example:

```
/api/user
```

instead of

```
/api/users
```

---

## 405 Method Not Allowed

Wrong HTTP method.

Example:

```
GET /login
```

when only:

```
POST /login
```

exists.

---

## 409 Conflict

The request conflicts with the current state of the server.

Example:

- Trying to register an email address that already exists.
- Creating a resource with a duplicate unique identifier.

---

## 413 Payload Too Large

The request body exceeds the server's configured limit.

Example:

- Uploading a 50 MB JSON payload when the limit is 10 MB.

---

## 415 Unsupported Media Type

Wrong `Content-Type`.

Example:

```
text/plain
```

instead of:

```
application/json
```

---

## 422 Unprocessable Entity

The request format is valid, but the data fails validation.

Example:

```json
{
  "email": "not-an-email",
  "age": -5
}
```

---

## 500 Internal Server Error

Server bug.

Usually your code crashed.

Look at:

```
Terminal logs
```

---

# 16. Reading Express Logs

Example:

```jsx
app.post("/users",(req,res)=>{

console.log(req.body);

console.log(req.headers);

});
```

Very useful.

# 17. Compare Good vs Bad Request

Good:

```bash
curl \
-H "Content-Type: application/json" \
-d '{"name":"Rahul"}' \
<http://localhost:3000/users>
```

---

Bad:

```bash
curl \
-H "Content-Type:text/plain" \
-d '{"name":"Rahul"}' \
<http://localhost:3000/users>
```

Notice the tiny header difference.

---

# 18. Trace the Entire Request

Verbose mode is good.

Tracing is even better.

```bash
curl --trace trace.log <https://httpbin.org/get>
```

Open:

```bash
cat trace.log
```

You'll see every byte sent and received.

For timestamps:

```bash
curl --trace-time --trace trace.log <https://httpbin.org/get>
```

This is especially helpful when diagnosing intermittent network or protocol issues.

# 19. A Professional Debugging Workflow

Whenever a request fails:

```
API fails
   │
   ▼
Check URL
   │
   ▼
Check Method
   │
   ▼
Check Headers
   │
   ▼
Check Body
   │
   ▼
Check Authentication
   │
   ▼
Check Server Logs
   │
   ▼
Read Response
   │
   ▼
Fix Problem
```

Don't skip steps.

# 💡 Pro Tips

### 1. My most-used debugging command

```bash
curl -v \
-H "Content-Type: application/json" \
-d '{"name":"Rahul"}' \
<http://localhost:3000/users>
```

It immediately shows what you sent and what the server returned.

---

### 2. Save error responses

When debugging large APIs:

```bash
curl \
-o error-response.json \
<http://localhost:3000/api/users>
```

Then inspect them with:

```bash
jq . error-response.json
```

---

### 3. Log only when needed

Temporary logs are useful:

```jsx
console.log(req.headers);
console.log(req.body);
```

But remove or replace them with proper logging before deploying to production to avoid exposing sensitive information.
