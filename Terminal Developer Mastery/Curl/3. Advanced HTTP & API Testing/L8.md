# 1. Why Caching Exists

Imagine an API returns:

```
GET /profile

↓

5 KB JSON
```

The user refreshes the page 100 times.

Without caching:

```
Browser

↓

100 Requests

↓

Server
```

The server performs the same work repeatedly.

---

With caching:

```
Browser

↓

Uses Cached Copy

↓

No New Download
```

Benefits:

- Faster pages
- Lower bandwidth usage
- Reduced server load
- Better user experience

---

# 3. Cache-Control Header

The most important caching header.

Example:

```
Cache-Control: max-age=3600
```

Meaning:

> Cache this response for **3600 seconds (1 hour).**

---

Inspect it:

```bash
curl -I <https://httpbin.org/cache>
```

Look for:

```
Cache-Control:
```

---

# 4. Common Cache-Control Directives

|Directive|Meaning|
|---|---|
|`max-age=3600`|Cache for 1 hour|
|`no-cache`|Revalidate before using|
|`no-store`|Never cache|
|`public`|Anyone may cache|
|`private`|Only the browser may cache|
|`must-revalidate`|Must verify after expiration|
|`immutable`|Content will not change|

---

# 5. public vs private

### Public

```
Cache-Control: public
```

Suitable for:

- CSS
- JavaScript
- Images
- Logos

---

### Private

```
Cache-Control: private
```

Suitable for:

- User profile
- Dashboard
- Account settings

Shared caches should not store these responses.

---

# 6. no-cache vs no-store

Many developers confuse these.

## no-cache

```
Cache-Control: no-cache
```

Meaning:

The response **may be stored**, but the client **must check with the server before reusing it**.

---

## no-store

```
Cache-Control: no-store
```

Meaning:

Never save the response anywhere.

Ideal for:

- Banking
- Password reset
- Sensitive medical data

---

# 7. Expires Header

Older caching mechanism.

```
Expires: Tue, 29 Jul 2026 12:00:00 GMT
```

Modern applications usually prefer:

```
Cache-Control
```

because it's more flexible.

---

# 8. What is an ETag?

An **ETag (Entity Tag)** uniquely identifies a specific version of a resource.

Example:

```
ETag: "abc123xyz"
```

Think of it as:

```
File Version

↓

Hash

↓

Unique ID
```

---

# 9. First Request

```
GET /profile
```

Server responds:

```
HTTP/1.1 200 OK

ETag: "abc123"

{
    ...
}
```

The browser stores:

- Response body
- ETag

---

# 10. Second Request

Instead of downloading again:

```
GET /profile

If-None-Match: "abc123"
```

The client asks:

> "Has this resource changed?"

---

# 11. Resource Unchanged

Server compares ETag.

If identical:

```
304 Not Modified
```

Response:

```
HTTP/1.1 304 Not Modified
```

No response body is sent.

The client uses its cached copy.

---

# 12. Resource Changed

Suppose the profile changed.

Server replies:

```
200 OK

ETag: "new456"

{
    updated data
}
```

The cache is updated.

---

# 13. Testing ETags

First request:

```bash
curl -I <https://httpbin.org/etag/test123>
```

Example:

```
ETag: test123
```

---

Second request:

```bash
curl \
-H 'If-None-Match: test123' \
<https://httpbin.org/etag/test123>
```

Expected:

```
304 Not Modified
```

# 14. Last-Modified Header

Instead of a version ID:

```
Last-Modified:

Tue, 29 Jul 2026 09:00:00 GMT
```

---

Client later asks:

```
If-Modified-Since:

Tue, 29 Jul 2026 09:00:00 GMT
```

# 16. Browser Cache vs API Cache

Websites:

```
HTML

↓

CSS

↓

JS

↓

Images
```

These are excellent caching candidates.

---

APIs:

Usually cache:

```
Countries

Categories

Products

Documentation
```

Avoid long caching for rapidly changing resources like:

- Live stock prices
- Chat messages
- Notifications

# 17. CDN Caching

```
User

↓

CDN

↓

Origin Server
```

If the CDN already has the response:

```
User

↓

CDN

↓

Response
```

The origin server is never contacted.

---

# 18. Common Cache Problems

### Stale Data

User:

```
Updated profile picture
```

Still sees:

```
Old profile picture
```

Usually caused by cache expiration or invalidation issues.

---

### Missing Cache-Control

Server:

```
200 OK
```

Without caching headers.

Browsers may make conservative caching decisions.

---

### Incorrect public/private

Never cache sensitive user information with:

```
Cache-Control: public
```

# 19. Debugging Caching

Inspect headers:

```bash

```

Look for:

- Cache-Control
- ETag
- Last-Modified
- Expires

---

Verbose mode:

```bash
curl -v URL
```

Useful for seeing request and response headers.

# 20. Express Example

Install:

```bash
npm install etag
```

Express already generates ETags by default unless disabled.

Custom headers:

```jsx
app.get("/users", (req, res) => {
    res.set("Cache-Control", "public, max-age=3600");

    res.json(users);
});
```

Private endpoint:

```jsx
app.get("/profile", (req, res) => {
    res.set("Cache-Control", "private, no-cache");

    res.json(profile);
});
```

# 22. 200 vs 304

|Response|Body Sent?|Network Usage|
|---|---|---|
|200 OK|✅ Yes|Higher|
|304 Not Modified|❌ No|Very low|

304 saves bandwidth because only headers are exchanged.

|Resource|Recommended Header|
|---|---|
|CSS / JS|`public, max-age=31536000, immutable`|
|Images|`public, max-age=31536000, immutable`|
|Product Catalog|`public, max-age=600`|

|Password Reset|`no-store`|

# 💡 Pro Tips

### 1. Use `Cache-Control` instead of `Expires`

Modern applications should rely primarily on:

```
Cache-Control
```

It's more flexible and easier to configure than absolute expiration dates.

---

### 2. Don't disable caching unnecessarily

Many APIs return static or infrequently changing data. Proper caching can significantly reduce latency and server load.

---

### 3. Choose cache policies based on the resource

- **Static assets:** Long-lived public caching.
- **User-specific data:** `private` with revalidation.
- **Sensitive information:** `no-store`.

Avoid using a single caching policy for every endpoint.
