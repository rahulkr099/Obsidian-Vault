# 1. Why Rate Limiting Exists

Imagine someone runs:

```
while true
do
    curl <https://api.example.com/users>
done
```

The server suddenly receives:

```
Millions of Requests

↓

CPU ↑

Memory ↑

Database ↑

↓

Server Crash
```

Rate limiting protects the API.

---

# 2. What Is Rate Limiting?

A server limits how many requests a client can make within a certain period.

Example:

```
100 requests

per

1 minute
```

If the limit is exceeded:

```
HTTP/1.1 429 Too Many Requests
```

---

# 3. HTTP 429

Example:

```
HTTP/1.1 429 Too Many Requests

Retry-After: 30
```

Meaning:

> Wait **30 seconds** before trying again.

---

# 4. Rate Limit Headers

Many APIs return headers like:

```
X-RateLimit-Limit: 100

X-RateLimit-Remaining: 37

X-RateLimit-Reset: 1753700000
```

Meaning:

|Header|Meaning|
|---|---|
|X-RateLimit-Limit|Maximum requests|
|X-RateLimit-Remaining|Requests left|
|X-RateLimit-Reset|When the limit resets|

Inspect them:

```bash
curl -I <https://api.github.com>
```

---

# 5. Retry-After

Server:

```
Retry-After: 60
```

Client:

```
Stop Requests

↓

Wait 60 Seconds

↓

Retry
```

Ignoring this header can lead to repeated failures.

---

# 6. Fixed Window Algorithm

Example:

```
Minute 1

100 Requests

↓

Blocked

↓

Minute 2

Counter Resets
```

Simple but can create traffic spikes at window boundaries.

---

# 7. Sliding Window Algorithm

Instead of resetting every minute:

```
Last 60 Seconds

↓

Count Requests

↓

Allow / Deny
```

Provides smoother traffic control.

---

# 8. Token Bucket

Imagine a bucket.

```
Bucket

● ● ● ● ●

5 Tokens
```

Each request consumes one token.

```
Request

↓

4 Tokens

↓

3 Tokens

↓

2 Tokens
```

Tokens are gradually refilled.

Benefits:

- Allows short bursts.
- Limits sustained abuse.

---

# 9. Leaky Bucket

Think of water dripping out steadily.

```
Requests

↓↓↓↓↓↓↓

Bucket

↓

Constant Output
```

This smooths traffic instead of sending bursts to the server.

---

# 10. Which Algorithm Is Most Common?

|Algorithm|Common Usage|
|---|---|
|Fixed Window|Small APIs|
|Sliding Window|Modern APIs|
|Token Bucket|Cloud services|
|Leaky Bucket|Networking|

# 12. Exponential Backoff

Don't retry immediately.

Bad:

```
429

↓

Retry Immediately

↓

429

↓

Retry Immediately
```

Good:

```
1 Second

↓

2 Seconds

↓

4 Seconds

↓

8 Seconds

↓

16 Seconds
```

This gives the server time to recover.

---

# 13. Bash Example

```bash
sleep 1

sleep 2

sleep 4

sleep 8
```

Simple exponential backoff.

---

# 14. curl Retries

```bash
curl \
--retry 5 \
--retry-delay 2 \
<https://example.com>
```

This retries after failures.

For more advanced behavior:

```bash
curl \
--retry 5 \
--retry-all-errors \
<https://example.com>
```

---

# 15. Idempotency

Some requests are safe to retry.

Examples:

```
GET /users
```

```
DELETE /todo/5
```

Running them multiple times usually has the same end result.

---

Some requests are **not** naturally safe:

```
POST /payments
```

Retrying blindly could create duplicate charges.

---

# 16. Idempotency Keys

Payment APIs often use:

```
Idempotency-Key:

abc123xyz
```

If the client retries:

```
Same Key

↓

Server Detects Duplicate

↓

Returns Previous Result
```

No duplicate payment is created.

# 20. Distinguish Retryable vs Non-Retryable Errors

|Status|Retry?|Reason|
|---|---|---|
|200|❌|Success|
|400|❌|Client request is invalid|
|401|❌|Authentication required or failed|
|403|❌|Permission issue|
|404|❌|Resource not found|
|408|✅|Request timed out|
|429|✅|Wait, then retry|
|500|✅|Temporary server error|
|502|✅|Bad gateway|
|503|✅|Service unavailable|
|504|✅|Gateway timeout|

# 22. Express Rate Limiting

Install:

```bash
npm install express-rate-limit
```

Example:

```jsx
import rateLimit from "express-rate-limit";

const limiter = rateLimit({
    windowMs: 60 * 1000,
    max: 100
});

app.use(limiter);
```

Meaning:

```
100 Requests

↓

1 Minute

↓

429
```

# 23. Retry Loop in Bash

```bash
MAX_RETRIES=5

for ((i=1; i<=MAX_RETRIES; i++)); do
    if curl --fail -s <https://example.com/api> > /dev/null; then
        echo "Success"
        exit 0
    fi

    echo "Retry $i..."

    sleep $((2 ** i))
done

echo "Failed after retries"

exit 1
```

This uses exponential backoff (`2, 4, 8, 16, 32` seconds).

# 💡 Pro Tips

### 1. Always respect `Retry-After`

If the server tells you:

```
Retry-After: 30
```

wait **30 seconds** before retrying. Ignoring it can worsen congestion or lead to temporary bans.

---

### 2. Retry only temporary failures

Good retry candidates:

- `408`
- `429`
- `500`
- `502`
- `503`
- `504`

Don't automatically retry errors like `400`, `401`, `403`, or `404`—those usually require fixing the request or credentials.

---

### 3. Make POST requests safe when needed

For operations like payment processing or order creation, support **idempotency keys** so retries don't accidentally create duplicate resources.
