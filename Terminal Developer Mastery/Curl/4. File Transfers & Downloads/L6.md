# 1. Why Authentication?

Many files are **not publicly accessible**.

Examples:

- Company backups
- Customer invoices
- Private GitHub releases
- CI/CD build artifacts
- Medical records
- Internal documentation

Instead of:

```
Anyone
    │
    ▼
Download
```

the flow becomes:

```
Authenticate
    │
    ▼
Authorized?
    │
 ┌──┴──┐
 │Yes  │No
 ▼     ▼
File   401
```

# 2. Authentication Methods

|Method|Common Usage|
|---|---|
|Bearer Token|REST APIs|
|Basic Auth|Legacy APIs, WebDAV|
|API Key|Cloud APIs|
|Cookies|Logged-in websites|
|Signed URL|Cloud storage|
|Client Certificate|Enterprise systems|

# 3. Bearer Token Authentication

Most modern APIs use JWT or OAuth access tokens.

Example:

```bash
curl \
-H "Authorization: Bearer $TOKEN" \
-O \
<https://api.example.com/files/report.pdf>
```

Request:

```
Authorization: Bearer eyJhbGciOi...
```

---

# 4. Download Protected Files

Example:

```bash
curl \
-H "Authorization: Bearer $TOKEN" \
-L \
-O \
<https://api.example.com/download/report.pdf>
```

Options:

- `L` → Follow redirects
- `O` → Keep original filename

---

# 5. Upload Protected Files

```bash
curl \
-T backup.tar.gz \
-H "Authorization: Bearer $TOKEN" \
<https://backup.example.com/uploads/backup.tar.gz>
```

---

# 6. Basic Authentication

Some servers still use username/password.

```bash
curl \
-u username:password \
-O \
URL
```

Equivalent header:

```
Authorization: Basic base64(username:password)
```

---

# 7. Prompt for Password Securely

Instead of exposing the password in your shell history:

```bash
curl \
-u username \
-O \
URL
```

`curl` prompts:

```
Enter host password:
```

This is safer for interactive use.

---

# 8. Authentication with Cookies

First, log in and save cookies:

```bash
curl \
-c cookies.txt \
-X POST \
-d "email=user@example.com&password=secret" \
<https://example.com/login>
```

Later, use the session:

```bash
curl \
-b cookies.txt \
-O \
<https://example.com/private/report.pdf>
```

---

# 9. API Keys

Some services use API keys in headers.

```bash
curl \
-H "X-API-Key: $API_KEY" \
-O \
URL
```

Others expect query parameters:

```bash
curl \
-O \
"<https://example.com/file.zip?api_key=$API_KEY>"
```

Prefer headers whenever the API supports them to reduce accidental exposure in logs.

---

# 10. Signed URLs

Cloud storage often provides temporary links.

Example:

```
<https://bucket.s3.amazonaws.com/file.zip>?
X-Amz-Algorithm=...
&X-Amz-Signature=...
```

No extra authentication header is needed.

Download:

```bash
curl -O "SIGNED_URL"
```

The signature in the URL authorizes access.

---

# 11. Upload Using a Signed URL

Cloud providers often allow uploads too.

```bash
curl \
-T backup.tar.gz \
"SIGNED_UPLOAD_URL"
```

No bearer token is required because authorization is built into the URL.

---

# 12. GitHub API Authentication

Download release metadata:

```bash
curl \
-H "Authorization: Bearer $GITHUB_TOKEN" \
-H "Accept: application/vnd.github+json" \
<https://api.github.com/repos/OWNER/REPO/releases/latest>
```

Many GitHub API endpoints require authentication to avoid low rate limits or access private resources.

---

# 13. Download From Private Artifact Servers

Example:

```bash
curl \
-H "Authorization: Bearer $TOKEN" \
-O \
<https://artifacts.example.com/builds/app.tar.gz>
```

Common in CI/CD systems.

# 14. Environment Variables

Avoid hardcoding secrets.

Bad:

```bash
TOKEN="my-secret-token"
```

Better:

```bash
export TOKEN="my-secret-token"
```

Then:

```bash
curl \
-H "Authorization: Bearer $TOKEN" \
URL
```

---

# 15. Use a `.env` File

Example:

```
TOKEN=your-token
API_URL=https://api.example.com
```

Load it:

```bash
source .env
```

Use:

```bash
curl \
-H "Authorization: Bearer $TOKEN" \
"$API_URL/files/report.pdf"
```

> **Security note:** Never commit `.env` files containing secrets to version control.

---

# 16. Common Authentication Errors

|Status|Meaning|
|---|---|
|401 Unauthorized|Missing or invalid credentials|
|403 Forbidden|Authenticated but not allowed|
|404 Not Found|Wrong endpoint (or intentionally hidden resource)|
|429 Too Many Requests|Rate limit exceeded|

---

# 17. Debug Authentication

Use verbose mode:

```bash
curl \
-v \
-H "Authorization: Bearer $TOKEN" \
URL
```

Inspect:

- Request headers
- Response headers
- HTTP status
- Redirects

Be careful not to share verbose logs publicly if they contain credentials.

---

# 18. Protect Secrets

Avoid:

```bash
curl \
-H "Authorization: Bearer my-secret-token"
```

Safer:

```bash
curl \
-H "Authorization: Bearer $TOKEN"
```

Even better for reusable scripts:

```bash
if [[ -z "$TOKEN" ]]; then
    echo "TOKEN is not set"
    exit 1
fi
```

---

# 19. Production Download Script

```bash
curl \
--fail \
-L \
-C - \
--retry 5 \
--retry-all-errors \
--connect-timeout 5 \
--max-time 600 \
-H "Authorization: Bearer $TOKEN" \
-O \
<https://downloads.example.com/app.tar.gz>
```

This combines:

- Authentication
- Resume support
- Retries
- Redirects
- Timeouts

---

# 20. Production Upload Script

```bash
curl \
--fail \
--retry 3 \
--retry-all-errors \
--connect-timeout 5 \
--max-time 1800 \
-T backup.tar.gz \
-H "Authorization: Bearer $TOKEN" \
<https://backup.example.com/uploads/backup.tar.gz>
```

# 22. Common Mistakes

### ❌ Hardcoding Tokens

```bash
TOKEN="abcdef12345"
```

Instead:

```bash
export TOKEN="abcdef12345"
```

or use a secrets manager in production.

---

### ❌ Committing Secrets

Never commit:

```
.env
```

Add to `.gitignore`:

```
.env
```

---

### ❌ Sharing Verbose Logs

`curl -v` can expose:

- Authorization headers
- Cookies
- Session IDs

Always review logs before sharing them.

# 💡 Pro Tips

### 1. Keep secrets out of your shell history

Instead of:

```bash
curl -H "Authorization: Bearer actual-secret-token" URL
```

Use environment variables:

```bash
export TOKEN="actual-secret-token"

curl \
-H "Authorization: Bearer $TOKEN" \
URL
```

---

### 2. Prefer headers over query parameters

This is generally more secure:

```
Authorization: Bearer <token>
```

than:

```
<https://example.com/file?token=>...
```

because URLs are more likely to appear in logs and browser history.

---

### 3. Treat signed URLs as temporary secrets

A signed URL grants access until it expires. Avoid posting it publicly or storing it longer than necessary.
