# 1. Sequential vs Parallel Downloads

Sequential:

```
Download File 1
        │
        ▼
Download File 2
        │
        ▼
Download File 3
        │
        ▼
Finished
```

Parallel:

```
File 1 ──┐
          │
File 2 ──┼──► Download Together
          │
File 3 ──┘
```

Multiple downloads happen at the same time.

---

# 2. Why Parallel Downloads?

Suppose you need to download:

- Ubuntu ISO
- Fedora ISO
- Debian ISO

Sequential:

```
10 min

+

10 min

+

10 min

=

30 min
```

Parallel:

```
10 min

All Together
```

Actual time depends on:

- Network bandwidth
- Server limits
- Disk speed

---

# 3. `-parallel`

Modern versions of `curl` support native parallel transfers.

Example:

```bash
curl \
--parallel \
-O <https://example.com/file1.zip> \
-O <https://example.com/file2.zip> \
-O <https://example.com/file3.zip>
```

All three downloads begin together.

---

# 4. Limit Parallel Jobs

Don't overload your system.

```bash
curl \
--parallel \
--parallel-max 4 \
-O URL1 \
-O URL2 \
-O URL3 \
-O URL4 \
-O URL5
```

At most:

```
4 Downloads

↓

Same Time
```

---

# 5. Parallel + Redirects

Combine with:

```bash
curl \
--parallel \
-L \
-O URL1 \
-O URL2
```

Useful for GitHub release assets.

---

# 6. Parallel + Resume

Large downloads:

```bash
curl \
--parallel \
-C - \
-L \
-O URL1 \
-O URL2
```

Interrupted downloads resume automatically.

---

# 7. Parallel + Retries

Reliable production command:

```bash
curl \
--parallel \
--retry 5 \
--retry-all-errors \
-L \
-O URL1 \
-O URL2
```

# 8. Download URLs from a File

Create:

```
urls.txt
```

Contents:

```
<https://example.com/file1.zip>
<https://example.com/file2.zip>
<https://example.com/file3.zip>
```

Loop:

```bash
while read -r url
do
    curl -LO "$url"
done < urls.txt
```

This is sequential.

---

# 9. Parallel Batch Download

```bash
cat urls.txt \
| xargs -n1 -P4 curl -LO
```

Explanation:

- `n1`

One URL per command.

- `P4`

Run four downloads simultaneously.

---

# 10. Why Use `xargs`?

Pipeline:

```
urls.txt

↓

xargs

↓

curl

↓

Downloads
```

Useful when:

- Hundreds of URLs
- Dynamic URL generation
- API-generated download lists


Downloads:

```

```

# 12. Retry Failed Downloads

Example loop:

```bash
while read -r url
do

    curl \
    --fail \
    --retry 5 \
    -LO "$url"

done < urls.txt
```

---

# 13. Log Successes and Failures

Example:

```bash
while read -r url
do

    if curl --fail -LO "$url"

    then
        echo "SUCCESS $url"
    else
        echo "FAILED $url"
    fi

done < urls.txt
```

# 24. Common Errors

### Too Many Parallel Downloads

```
100 Downloads
```

may overload:

- CPU
- Memory
- Internet connection
- Remote server

Choose a reasonable limit (for example, 4–8 parallel transfers) unless you know the environment can handle more.

---

### Ignoring Retry Logic

One failed download should not stop the entire batch unnecessarily.

Always consider:

```bash
--retry
```

---

### Missing Resume

For large files:

```bash
-C -
```

can save a significant amount of time.

---

# 25. Production Command

```bash
curl \
--parallel \
--parallel-max 4 \
--retry 5 \
--retry-all-errors \
--connect-timeout 5 \
--max-time 1800 \
--fail \
-L \
-C - \
-O URL1 \
-O URL2 \
-O URL3
```

Suitable for many production download workflows.

# 💡 Pro Tips

### 1. Prefer `-parallel` when available

If your `curl` version supports it, it's usually simpler than coordinating multiple background jobs manually.

```bash
curl --parallel -O URL1 -O URL2
```

Check your version:

```bash
curl --version
```

---

### 2. Use `xargs` for dynamic workloads

When URLs come from another command or a file:

```bash
cat urls.txt | xargs -n1 -P4 curl -LO
```

This scales well for large batches.

---

### 3. Combine resume, retry, and verification

For important downloads:

```
Download

↓

Resume (-C -)

↓

Retry (--retry)

↓

Verify (sha256sum)

↓

Use
```

Reliability comes from combining these features rather than relying on just one.
