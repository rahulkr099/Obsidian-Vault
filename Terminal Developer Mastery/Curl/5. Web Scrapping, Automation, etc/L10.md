# What is Cron?

**Cron** is a background service (daemon) that runs scheduled tasks automatically.

Instead of remembering to run a script every day:

```
You
 │
 ▼
Run monitor.sh
```

Cron does it for you:

```
Cron
 │
 ▼
Runs monitor.sh
 │
 ▼
Every hour
```

---

# Common Uses of Cron

Cron is commonly used for:

- Database backups
- Website monitoring
- API polling
- Sending reports
- Cleaning log files
- Synchronizing files
- Updating software
- Running maintenance scripts

---

# Check if Cron is Running

On many Linux distributions:

```bash
systemctl status cron
```

On some distributions (such as Fedora):

```bash
systemctl status crond
```

Start the service if needed:

```bash
sudo systemctl start cron
```

Enable it at boot:

```bash
sudo systemctl enable cron
```

Verify it's enabled:

```bash
systemctl is-enabled cron
```

Output:

```
enabled
```

# Cron Format

A cron entry has five time fields followed by the command:

```
* * * * * command
│ │ │ │ │
│ │ │ │ └── Day of week (0–7, where 0 and 7 are Sunday)
│ │ │ └──── Month (1–12)
│ │ └────── Day of month (1–31)
│ └──────── Hour (0–23)
└────────── Minute (0–59)
```

---

# Every Minute

```
* * * * * command
```

Runs once every minute.

---

# Every Hour

```
0 * * * * command
```

Runs at the beginning of every hour.

---

# Every Day at Midnight

```
0 0 * * * command
```

Runs daily at 12:00 AM.

---

# Every Day at 6:30 AM

```
30 6 * * * command
```

Runs every day at **06:30**.

---

# Every Monday

```
0 9 * * 1 command
```

Runs every Monday at **09:00**.

---

# Every 5 Minutes

```
*/5 * * * * command
```

Runs every five minutes.

---

# Every 15 Minutes

```
*/15 * * * * command
```

---

# Every Two Hours

```
0 */2 * * * command
```

Runs at:

```
00:00
02:00
04:00
06:00
...
```

# Schedule Your Monitor

Suppose you created:

```
/home/rahul/scripts/monitor.sh
```

Run every minute:

```
* * * * * /home/rahul/scripts/monitor.sh
```

---

# Redirect Output

Without redirection, cron may email command output (if mail is configured).

Save output to a log instead:

```
* * * * * /home/rahul/scripts/monitor.sh >> /home/rahul/monitor.log 2>&1
```

Explanation:

|Part|Meaning|
|---|---|
|`>>`|Append standard output|
|`2>&1`|Redirect standard error to the same destination|

---

# Use Absolute Paths

Avoid:

```bash
python monitor.py
```

Prefer:

```bash
/usr/bin/python3 /home/rahul/scripts/monitor.py
```

Likewise for shell scripts:

```
* * * * * /bin/bash /home/rahul/scripts/monitor.sh
```

Cron uses a minimal environment, so don't rely on your interactive shell's `PATH`.

---

# Environment Variables

You can define variables inside your crontab:

```
PATH=/usr/local/bin:/usr/bin:/bin

MAILTO=""
```

`MAILTO=""` disables cron email notifications for that crontab.

---

# Test Before Scheduling

Always verify manually:

```bash
./monitor.sh
```

Only schedule it after it works correctly.

---

# Log with Timestamps

Inside your script:

```bash
echo "$(date): Website checked" >> monitor.log
```

Sample log:

```
Mon Jul 27 18:00:01 IST 2026: Website checked
```

---

# Check Cron Logs

Depending on your Linux distribution:

Ubuntu/Debian:

```bash
grep CRON /var/log/syslog
```

Fedora/RHEL:

```bash
journalctl -u crond
```

These logs help diagnose scheduling issues.

# Example Monitoring Script

```bash
#!/bin/bash

URL="<https://example.com>"

STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$URL")

echo "$(date): $STATUS" >> /home/rahul/monitor.log
```

Cron entry:

```
*/5 * * * * /bin/bash /home/rahul/scripts/monitor.sh
```

---

# Schedule Multiple Jobs

```
# Every hour
0 * * * * /home/rahul/backup.sh

# Every 5 minutes
*/5 * * * * /home/rahul/monitor.sh

# Every night
0 2 * * * /home/rahul/cleanup.sh
```

Comments begin with `#`.

---

# Prevent Overlapping Jobs

If a job takes longer than its schedule interval, multiple copies may run simultaneously.

A common solution is `flock`:

```bash
flock -n /tmp/monitor.lock /bin/bash /home/rahul/scripts/monitor.sh
```

This ensures only one instance runs at a time.

# Common Mistakes

❌ Using relative paths.

Incorrect:

```bash
monitor.sh
```

Correct:

```bash
/home/rahul/scripts/monitor.sh
```

---

❌ Forgetting execute permissions.

```bash
chmod +x monitor.sh
```

---

❌ Assuming your shell environment is available.

Cron doesn't automatically load your aliases, shell functions, or custom `PATH`.

---

❌ Ignoring logs.

Always redirect output while testing:

```
>> monitor.log 2>&1
```

Logs are often the fastest way to identify problems.

---

# Cron vs Manual Execution

|Manual|Cron|
|---|---|
|Started by you|Started automatically|
|Interactive environment|Minimal environment|
|Immediate|Scheduled|
|Good for testing|Good for automation|

        ▼

        │
        ▼

This is a simplified version of how many scheduled maintenance and monitoring tasks work in production.

# Best Practices

- Test scripts manually before scheduling.
- Always use absolute paths.
- Redirect output to log files.
- Keep scheduled tasks small and focused.
- Prevent overlapping executions for long-running jobs.
- Review logs regularly.

# Key Takeaways

- Cron automates recurring tasks on Linux.
- `crontab -e` edits your personal schedule.
- Cron expressions define **when** a task runs.
- Use absolute paths and log output.
- `flock` can prevent duplicate executions.
- Cron is a fundamental tool for backend automation and system administration.

# 💡 Backend Engineer Tip

Modern Linux systems often use **systemd timers** as an alternative to cron. They offer advantages like dependency management, persistent timers (catching up on missed runs after reboot), and better integration with system logs.

For learning and for many automation tasks, **cron remains an essential skill** because it is simple, widely available, and commonly encountered on production servers. Once you're comfortable with cron, learning systemd timers becomes much easier.
