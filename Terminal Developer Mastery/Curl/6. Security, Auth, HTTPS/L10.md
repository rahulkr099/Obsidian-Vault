# What is a Secret?

A **secret** is any piece of information that must remain confidential.

Examples include:

- API Keys
- Database passwords
- JWT secrets
- OAuth Client Secrets
- SSH private keys
- TLS private keys
- Encryption keys
- Session secrets

If an attacker obtains these, they may gain unauthorized access to your systems.

---

# Common Secrets

|Secret|Example|
|---|---|
|API Key|`sk_live_xxxxx`|
|JWT Secret|`super_secret_key`|
|Database Password|`mypassword123`|
|SSH Private Key|`id_rsa`|
|Client Certificate Key|`client.key`|
|OAuth Client Secret|`GOCSPX-...`|

---

# The Biggest Mistake

Hardcoding secrets.

❌ Bad:

```jsx
const API_KEY = "sk_live_ABC123";
```

or

```bash
API_KEY="sk_live_ABC123"
```

Problems:

- Visible in Git.
- Visible to teammates.
- Difficult to rotate.
- Easy to leak.

---

# Use Environment Variables

Instead:

```bash
export API_KEY="sk_live_ABC123"
```

Use:

```bash
curl \
-H "X-API-Key: $API_KEY" \
<https://api.example.com/data>
```

Your script doesn't contain the actual secret.

---

# Reading Environment Variables

Bash:

```bash
echo "$API_KEY"
```

Node.js:

```jsx
const apiKey = process.env.API_KEY;
```

Python:

```python
import os

api_key = os.getenv("API_KEY")
```

---

# Using `.env`

A common development practice:

```
API_KEY=sk_live_ABC123
DATABASE_URL=postgres://...
JWT_SECRET=my_secret
```

Node.js often loads this with `dotenv`:

```jsx
import dotenv from "dotenv";

dotenv.config();

console.log(process.env.API_KEY);
```

---

# Never Commit `.env`

Always ignore it.

`.gitignore`

```
.env
.env.local
.env.production
```

If a `.env` file is pushed to a public repository, treat every secret inside it as compromised.

---

# What If You Already Committed a Secret?

Suppose you accidentally push:

```
API_KEY=sk_live_SECRET
```

Even if you delete the commit later, the secret may already have been copied.

The correct response is:

1. Revoke the key.
2. Generate a new one.
3. Update your applications.
4. Review logs for suspicious activity.

---

# Secret Rotation

Secrets should not live forever.

Workflow:

```
Old Secret
      │
Generate New Secret
      │
Update Applications
      │
Verify
      │
Delete Old Secret
```

Reasons:

- Routine security policy
- Employee departure
- Possible compromise
- Expiration

---

# Secret Managers

In production, organizations often use dedicated secret management systems.

Popular options include:

- HashiCorp Vault
- AWS Secrets Manager
- Azure Key Vault
- Google Secret Manager
- Kubernetes Secrets (with appropriate protections)

Instead of:

```
Application

↓

Hardcoded Secret
```

Use:

```
Application

↓

Secret Manager

↓

Retrieve Secret
```

# SSH Keys

Never share:

```
~/.ssh/id_rsa
```

This is your private key.

Safe to share:

```
~/.ssh/id_rsa.pub
```

Public keys are meant to be distributed.

---

# TLS Private Keys

Never expose:

```
server.key
```

or

```
client.key
```

These keys prove the identity of your server or client.

---

# File Permissions

Restrict access to sensitive files.

Example:

```bash
chmod 600 ~/.ssh/id_rsa
```

Meaning:

- Owner can read/write.
- Others have no access.

---

# Secure Bash Script

Instead of:

```bash
API_KEY="secret123"

curl \
-H "X-API-Key: $API_KEY" \
<https://api.example.com>
```

Use:

```bash
: "${API_KEY:?API_KEY is not set}"

curl \
-H "X-API-Key: $API_KEY" \
<https://api.example.com>
```

This exits with an error if `API_KEY` isn't defined.

---

# Prompting for Secrets

Instead of:

```bash
read PASSWORD
```

Use:

```bash
read -s PASSWORD
```

- `s` hides the input while typing.

---

# Temporary Environment Variables

One command only:

```bash
API_KEY="secret123" \
curl \
-H "X-API-Key: $API_KEY" \
<https://api.example.com>
```

A more reliable pattern is:

```bash
API_KEY="secret123" bash -c '
curl -H "X-API-Key: $API_KEY" <https://api.example.com>
'
```

The variable exists only for that command's environment.

---

# Logging Secrets

Avoid:

```bash
echo "$JWT_SECRET"
```

Avoid:

```bash
echo "$DATABASE_PASSWORD"
```

Logs often end up in:

- CI/CD systems
- Containers
- Monitoring tools
- Cloud logging platforms

Never print secrets unless absolutely necessary.

---

# Masking Secrets

Better:

```
sk_live_****************
```

or

```
**************
```

Many CI/CD systems automatically mask configured secrets.

---

# Secrets in GitHub

GitHub automatically scans public repositories for many common credential formats.

If it detects an exposed secret, it may notify the provider so the key can be revoked.

Don't rely on this—prevent leaks instead.

---

# Docker

Avoid:

```docker
ENV API_KEY=secret123
```

This bakes the secret into the image.

Prefer:

```bash
docker run \
-e API_KEY=secret123 \
my-app
```

or orchestrator-specific secret mechanisms.

---

# Kubernetes

Instead of embedding secrets in Deployments:

Use:

```
Kubernetes Secret
```

Then mount it as:

- Environment variables
- Files

Remember that Kubernetes Secrets are **not encrypted by default** in etcd unless encryption at rest is configured.

# Common Mistakes

❌ **Hardcoding secrets**

Never place secrets directly in source code.

---

❌ **Committing `.env`**

Treat committed secrets as compromised.

---

❌ **Printing secrets**

Avoid logging tokens, passwords, and keys.

---

❌ **Sharing private keys**

Only share public keys.

---

❌ **Using one secret forever**

Rotate secrets periodically.

---

# Best Practices

- Use environment variables for development.
- Use a secret manager in production.
- Ignore `.env` files in Git.
- Rotate secrets regularly.
- Revoke compromised credentials immediately.
- Protect private keys with restrictive file permissions.
- Never expose secrets in logs or screenshots.
- Give applications only the secrets they actually need.

# Real-World Backend Example

Suppose your Express backend uses:

- PostgreSQL
- JWT
- OpenAI API
- Redis

Instead of:

```jsx
const JWT_SECRET = "supersecret";
const OPENAI_API_KEY = "sk-live-...";
```

Use:

```jsx
const JWT_SECRET = process.env.JWT_SECRET;
const OPENAI_API_KEY = process.env.OPENAI_API_KEY;
const DATABASE_URL = process.env.DATABASE_URL;
const REDIS_URL = process.env.REDIS_URL;
```

For local development:

```
JWT_SECRET=...
OPENAI_API_KEY=...
DATABASE_URL=...
REDIS_URL=...
```

For production:

- Environment variables
- Container secrets
- Cloud secret manager
- Platform secret storage

# Secrets vs Configuration

|Configuration|Secret|
|---|---|
|App port|Database password|
|Log level|API key|
|Environment|JWT secret|
|Feature flags|Private key|

A useful rule:

> If exposing the value could compromise security, treat it as a secret.

---

# Key Takeaways

- Secrets include passwords, API keys, JWT secrets, and private keys.
- Never hardcode secrets into source code.
- Use environment variables for development.
- Use dedicated secret managers in production.
- Protect `.env` files and private keys.
- Rotate and revoke secrets when necessary.
- Never log sensitive values.

# 💡 Backend Engineer Tip

As you continue building Express.js applications, you'll likely end up with a `.env` file similar to this:

```
PORT=5000
NODE_ENV=development

DATABASE_URL=postgres://...

JWT_SECRET=...

ACCESS_TOKEN_SECRET=...
REFRESH_TOKEN_SECRET=...

OPENAI_API_KEY=...

REDIS_URL=...
```

Your application should read these values from `process.env` and **never** commit the `.env` file to Git. This approach makes it easy to use different secrets for development, staging, and production without changing your application code.
