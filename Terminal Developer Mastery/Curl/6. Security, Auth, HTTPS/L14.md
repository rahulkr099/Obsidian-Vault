# Principle of Least Privilege

Every user, service, and application should have **only the permissions it needs**.

Bad:

```
API Key

↓

Full Database Access
```

Better:

```
API Key

↓

Read Only
```

Examples:

- Read-only database users for reporting.
- Separate admin and user roles.
- Narrow OAuth scopes.
- Minimal IAM permissions in cloud platforms.

---

# Secure by Default

Bad application:

```
Everything Enabled
```

Good application:

```
Everything Disabled

↓

Enable Only What's Needed
```

Examples:

- Disable debug mode in production.
- Disable directory listing.
- Disable unused endpoints.
- Disable unused services.

---

# HTTPS Everywhere

Always prefer:

```
HTTPS
```

Never:

```
HTTP
```

Reasons:

- Encryption
- Integrity
- Authentication

Redirect HTTP traffic to HTTPS where appropriate.

---

# Keep Certificates Healthy

Monitor:

- Expiration dates
- Trusted CAs
- Certificate renewal
- Revocation status

Automate renewals whenever possible.

---

# Never Trust User Input

Every request should be considered untrusted.

Validate:

- Length
- Type
- Format
- Range
- Allowed values

Example:

```
Age

↓

18–120
```

instead of accepting any value.

---

# Authentication vs Authorization

Authentication:

```
Who are you?
```

Authorization:

```
What are you allowed to do?
```

Never assume that an authenticated user is automatically allowed to perform every action.

---

# Use Strong Authentication

Avoid:

```
password123
```

Prefer:

- Strong passwords
- Multi-factor authentication (MFA) where appropriate
- OAuth
- mTLS for service-to-service communication

---

# Store Passwords Securely

Never store:

```
password123
```

Instead:

```
bcrypt hash
```

or another modern password hashing algorithm such as Argon2.

Passwords should be **hashed**, not encrypted.

---

# Protect Secrets

Never expose:

- API Keys
- JWT Secrets
- Database passwords
- SSH private keys
- TLS private keys

Use:

- Environment variables
- Secret managers
- Restricted file permissions

---

# Rotate Credentials

Secrets should change periodically.

```
Old Secret

↓

New Secret

↓

Revoke Old Secret
```

Do the same for:

- API keys
- Certificates
- Passwords
- Tokens

---

# Log Carefully

Useful logs:

```
Login Success

Login Failure

Permission Denied

Server Error
```

Avoid logging:

- Passwords
- JWTs
- API Keys
- Session IDs
- Personal information unless necessary

---

# Handle Errors Safely

Bad:

```
Database Password:
root123
```

Better:

```
Internal Server Error
```

Keep detailed diagnostics in internal logs, not in user-facing error messages.

---

# Rate Limiting

Protect APIs from abuse.

Example:

```
100 Requests

↓

1 Minute
```

If exceeded:

```
429 Too Many Requests
```

---

# Use Timeouts

Don't let connections wait forever.

Example:

```bash
curl \
--connect-timeout 5 \
--max-time 30 \
<https://example.com>
```

Timeouts improve reliability and reduce resource exhaustion.

---

# Validate HTTPS Certificates

Don't ignore certificate errors.

Avoid:

```bash
curl -k
```

except for controlled local testing.

Always verify certificates in production.

---

# Verify Downloads

Always verify:

- SHA256
- SHA512
- Digital signatures (when available)

Don't trust a file solely because it downloaded successfully.

---

# Update Software

Keep updated:

- Operating system
- `curl`
- OpenSSL
- Node.js
- Dependencies
- Docker images

Security patches often fix known vulnerabilities.

---

# Principle of Fail Securely

If something goes wrong:

Bad:

```
Authentication Failed

↓

Allow Access
```

Good:

```
Authentication Failed

↓

Deny Access
```

When in doubt, fail safely.

# Bash Script Security

Always begin scripts with:

```bash
set -euo pipefail
```

Benefits:

- Exit on errors (`e`)
- Treat unset variables as errors (`u`)
- Catch pipeline failures (`pipefail`)

Always quote variables:

Good:

```bash
echo "$FILE"
```

Bad:

```bash
echo $FILE
```

---

# File Permissions

Sensitive files:

```bash
chmod 600 secret.key
```

Public files:

```bash
chmod 644 public.pem
```

Follow the principle of least privilege for file access.

# Real-World Backend Example

Imagine your Express.js backend.

Instead of:

```jsx
app.use(cors());
```

Use a more restrictive configuration:

```jsx
app.use(cors({
  origin: "<https://your-frontend.example>",
  credentials: true
}));
```

Instead of:

```jsx
const JWT_SECRET = "secret";
```

Use:

```jsx
const JWT_SECRET = process.env.JWT_SECRET;
```

Instead of:

```bash
curl -k <https://api.example.com>
```

Use:

```bash
curl <https://api.example.com>
```

These small improvements significantly strengthen your application's security.

# Top 15 Security Rules

1. Always use HTTPS.
2. Never hardcode secrets.
3. Use environment variables or a secret manager.
4. Validate all input.
5. Escape or sanitize output where appropriate.
6. Hash passwords with bcrypt or Argon2.
7. Rotate credentials regularly.
8. Verify downloads with checksums or signatures.
9. Avoid `curl -k` in production.
10. Use least privilege everywhere.
11. Log securely.
12. Keep software updated.
13. Apply rate limiting.
14. Test authentication and authorization separately.
15. Assume user input is untrusted.

# 💡 Backend Engineer Tip

You've built several Express.js projects already, so here's a practical security checklist you can apply before deploying any backend:

- Enable `helmet` to set common security headers.
- Restrict CORS to trusted origins instead of allowing all origins.
- Validate incoming requests with a schema validator (such as Joi or Zod).
- Hash passwords with `bcrypt` or `Argon2`—never store plaintext passwords.
- Store secrets in environment variables or a secret manager, not in source code.
- Use HTTPS in production and secure cookies when using session-based authentication.
- Apply rate limiting to authentication and other sensitive endpoints.
- Keep dependencies updated and regularly review them for known vulnerabilities.

Following this checklist consistently will prevent many of the most common backend security issues before they ever reach production.
