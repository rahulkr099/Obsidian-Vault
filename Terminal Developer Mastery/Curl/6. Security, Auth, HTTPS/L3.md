# What is Certificate Validation?

When you run:

```bash
curl <https://example.com>
```

`curl` does **much more** than send an HTTP request.

It first checks whether the server's certificate is trustworthy.

Simplified workflow:

```
Connect
   │
Receive Certificate
   │
Check Certificate Chain
   │
Check Expiration
   │
Check Hostname
   │
Check Trusted CA
   │
Secure Connection
```

If any step fails, `curl` refuses the connection.

---

# Validation Checklist

A certificate must pass **all** of these checks:

|Check|Purpose|
|---|---|
|Certificate exists|Server presented a certificate|
|Not expired|Certificate is still valid|
|Not before date|Certificate is already valid|
|Trusted issuer|Signed by a trusted CA|
|Valid chain|Complete certificate chain|
|Hostname matches|Certificate matches requested domain|
|Digital signature|Certificate hasn't been modified|

---

# Trusted Certificate Authorities

Your operating system includes a **CA trust store**.

Example:

```
Ubuntu
 │
 ├── Let's Encrypt
 ├── DigiCert
 ├── Google Trust Services
 ├── GlobalSign
 └── Sectigo
```

`curl` checks whether the server's certificate chains back to one of these trusted roots.

---

# Certificate Chain Review

```
Website Certificate
       │
Intermediate CA
       │
Root CA
       │
Trusted by OS
```

If the chain reaches a trusted Root CA, validation succeeds.

---

# Hostname Validation

Suppose you visit:

```
<https://github.com>
```

The certificate must include:

```
github.com
```

or an appropriate wildcard such as:

```
*.github.com
```

If the certificate is issued for:

```
example.com
```

the connection fails because the hostname doesn't match.

---

# Expiration Check

Certificates have two dates:

```
Not Before:
2026-01-01

Not After:
2027-01-01
```

If today's date is outside this range, validation fails.

---

# Self-Signed Certificates

Normally:

```
Website
   │
Signed by CA
```

A self-signed certificate looks like:

```
Website
   │
Signs Itself
```

Because no trusted CA vouched for it, browsers and `curl` reject it by default.

Self-signed certificates are common in:

- Local development
- Internal testing
- Home labs

They are generally **not appropriate for public production websites**.

---

# Typical Error

You may see:

```
curl: (60) SSL certificate problem:
self-signed certificate
```

This means the certificate could not be traced back to a trusted CA.

---

# Tell `curl` to Trust a Specific CA

If you have the CA certificate:

```bash
curl --cacert my-ca.crt <https://example.local>
```

- `-cacert` tells `curl` to use the specified CA certificate in addition to (or instead of, depending on the TLS backend) its default trust configuration.

This is commonly used for:

- Internal company CAs
- Development environments
- Private PKI

---

# Using a CA Directory

Instead of one certificate:

```bash
curl --capath /etc/ssl/certs <https://example.com>
```

- `-capath` points to a directory containing trusted CA certificates.

---

# Default CA Location

To see where your `curl` installation looks for CA certificates:

```bash
curl -V
```

Example output:

```
Features: SSL HTTPS-proxy IPv6

SSL: OpenSSL
```

Depending on your platform and TLS library, the default CA bundle or directory may vary.

---

# The Dangerous Option: `k`

```bash
curl -k <https://example.com>
```

or

```bash
curl --insecure <https://example.com>
```

This **disables certificate validation**.

`curl` no longer verifies:

- Trusted issuer
- Expiration
- Hostname
- Certificate chain

The encrypted connection still exists, but you lose authentication of the server.

---

# Why `k` Is Dangerous

Imagine an attacker intercepts your connection.

Without validation:

```
You
 │
Fake Server
 │
Attacker
```

Because validation is disabled, your client cannot distinguish the fake server from the real one.

This increases the risk of man-in-the-middle (MITM) attacks.

---

# When Is `k` Acceptable?

Reasonable uses include:

- Local development
- Temporary testing
- Lab environments

Avoid it for:

- Banking
- Production APIs
- Payment systems
- Authentication services
- Internet-facing applications

---

# Common Validation Errors

## 1. Expired Certificate

```
certificate has expired
```

Solution:

Renew the certificate.

---

## 2. Unknown CA

```
unable to get local issuer certificate
```

Solution:

- Install the correct CA certificate.
- Use `-cacert` if appropriate.
- Verify the certificate chain.

---

## 3. Hostname Mismatch

```
certificate does not match host
```

Example:

You visit:

```
api.example.com
```

Certificate:

```
example.org
```

Validation fails.

---

## 4. Self-Signed Certificate

```
self-signed certificate
```

Solution:

Trust the CA (or the self-signed certificate, if appropriate) instead of bypassing validation.

---

## 5. Incomplete Chain

The server forgets to send an intermediate certificate.

Result:

```
unable to verify the first certificate
```

The server administrator typically needs to configure the full certificate chain.

---

# Inspecting Problems with OpenSSL

Connect:

```bash
openssl s_client -connect example.com:443
```

This displays:

- Certificate chain
- Verification status
- TLS version
- Cipher suite

Look for:

```
Verify return code: 0 (ok)
```

If the return code isn't `0`, OpenSSL will usually indicate the reason.

---

# Using Verbose `curl`

```bash
curl -v <https://example.com>
```

Useful information includes:

- TLS version
- Certificate subject
- Certificate issuer
- Handshake progress
- Verification messages

---

# Certificate Validation Workflow

```
Client
   │
Connect
   │
Receive Certificate
   │
Verify Dates
   │
Verify Hostname
   │
Verify CA Chain
   │
Verification Successful?
   │
 ├── Yes → Secure Connection
 │
 └── No  → Abort
```

# Common Mistakes

❌ **Using `-k` in production.**

Always fix the underlying certificate problem instead.

---

❌ **Assuming encryption alone is enough.**

Encryption without certificate validation does not verify the server's identity.

---

❌ **Ignoring hostname mismatches.**

Even a valid certificate is rejected if it doesn't match the requested domain.

---

❌ **Forgetting intermediate certificates.**

A correctly configured server should send the full certificate chain.

---

# Best Practices

- Never use `-insecure` in production unless you fully understand and accept the risks.
- Keep your operating system's CA store updated.
- Renew certificates before expiration.
- Verify hostnames carefully.
- Use `-cacert` for trusted internal CAs instead of disabling verification.
- Investigate certificate errors instead of bypassing them.

---

# Key Takeaways

- Certificate validation is essential for secure HTTPS communication.
- `curl` checks expiration, hostname, trusted CAs, certificate chains, and digital signatures.
- Self-signed certificates are rejected unless explicitly trusted.
- `-cacert` allows you to trust a specific CA certificate.
- `-capath` uses a directory of trusted CA certificates.
- `-insecure` disables critical security checks and should be avoided in production.

## 💡 Backend Engineer Tip

Many internal company services use a **private Certificate Authority** instead of public CAs like Let's Encrypt. In those environments, the correct solution is usually to install or reference the organization's CA certificate (for example, with `--cacert`), **not** to use `curl -k`. Knowing this distinction is an important production skill for backend engineers.
