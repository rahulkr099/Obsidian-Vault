# What is an API Key?

An API key is a **unique secret string** issued by a service.

Example:

```
sk_live_8d92jKslFj2N8...
```

or

```
AIzaSyDk82...
```

It identifies **your application**, not necessarily an individual user.

---

# Why Use API Keys?

When you access a public API, the provider wants to know:

- Who is making requests?
- How many requests are being made?
- Which account should be billed?
- Should rate limits apply?

Instead of logging in every time, your application sends its API key.

---

# Authentication Flow

```
Application
      │
API Key
      │
────────────►
API Server
      │
Verify Key
      │
200 OK
```

---

# Header-Based API Keys

The most common method is sending the key in an HTTP header.

Example:

```
X-API-Key: sk_live_123456789
```

Request:

```bash
curl \
-H "X-API-Key: YOUR_API_KEY" \
<https://api.example.com/data>
```

---

# Authorization Header

Some APIs reuse the `Authorization` header.

Example:

```
Authorization: ApiKey YOUR_API_KEY
```

or

```
Authorization: Bearer YOUR_API_KEY
```

Always read the API documentation to know which format is expected.

---

# Query Parameter API Keys

Some APIs accept keys in the URL.

Example:

```
<https://api.example.com/weather?apikey=YOUR_KEY>
```

`curl`:

```bash
curl \
"<https://api.example.com/weather?apikey=YOUR_API_KEY>"
```

---

# Why Query Parameters Are Less Secure

URLs may be:

- Stored in browser history.
- Logged by web servers.
- Recorded by reverse proxies.
- Included in analytics tools.
- Shared accidentally.

Because of this, sending API keys in headers is generally preferred.

---

# Header vs Query Parameter

|Header|Query Parameter|
|---|---|
|More secure|Less secure|
|Hidden from URL|Visible in URL|
|Recommended|Use only if required|

---

# Example Request

```bash
API_KEY="abc123"

curl \
-H "X-API-Key: $API_KEY" \
<https://api.example.com/users>
```

---

# HTTP Response

Successful request:

```
HTTP/1.1 200 OK
```

Invalid key:

```
HTTP/1.1 401 Unauthorized
```

Some APIs may instead return:

```
HTTP/1.1 403 Forbidden
```

The exact status code depends on the API's design.

---

# Environment Variables

Avoid this:

```bash
API_KEY="sk_live_secret_key"
```

Better:

```bash
export API_KEY="sk_live_secret_key"
```

Then:

```bash
curl \
-H "X-API-Key: $API_KEY" \
<https://api.example.com/data>
```

---

# `.env` Files

Many applications store secrets in a `.env` file.

Example:

```
API_KEY=sk_live_secret_key
DATABASE_URL=...
JWT_SECRET=...
```

In Node.js, these values are commonly loaded with packages like `dotenv`.

**Never commit `.env` files to Git.**

---

# `.gitignore`

Always ignore secret files.

Example:

```
.env
.env.local
.env.production
```

This prevents accidentally pushing secrets to GitHub.

---

# API Key Rotation

Sometimes a key must be replaced because:

- It expired.
- It was leaked.
- It was accidentally committed.
- Company policy requires regular rotation.

Workflow:

```
Old Key
    │
Generate New Key
    │
Update Application
    │
Delete Old Key
```

---

# What if a Key Leaks?

Imagine someone pushes this to GitHub:

```
sk_live_ABC123SECRET
```

Anyone with that key may be able to use your API quota or incur charges.

If a key leaks:

1. Revoke it immediately.
2. Generate a new key.
3. Update your applications.
4. Review logs for suspicious activity.

---

# Rate Limiting

Many APIs associate rate limits with your API key.

Example:

```
100 requests/minute
```

Exceeding the limit may result in:

```
HTTP/1.1 429 Too Many Requests
```

---

# Reading Rate Limit Headers

Many APIs return headers such as:

```
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 950
X-RateLimit-Reset: 1785300000
```

You can inspect them with:

```bash
curl -I \
-H "X-API-Key: $API_KEY" \
<https://api.example.com/data>
```

---

# Verbose Debugging

```bash
curl \
-v \
-H "X-API-Key: $API_KEY" \
<https://api.example.com/data>
```

Useful for checking:

- Request headers
- Response headers
- Status code
- TLS details

Be careful not to share logs containing real API keys.

# Common Mistakes

❌ **Hardcoding API keys**

```jsx
const apiKey = "sk_live_secret";
```

Instead, use environment variables.

---

❌ **Committing secrets to Git**

If a secret reaches a public repository, assume it has been compromised.

---

❌ **Sharing screenshots**

Be sure API keys are hidden before sharing terminal output or screenshots.

---

❌ **Using query parameters unnecessarily**

Prefer headers whenever the API supports them.

---

❌ **Reusing the same key everywhere**

Use separate API keys for:

- Development
- Staging
- Production

This limits the impact if one environment is compromised.

---

# Best Practices

- Store API keys in environment variables or a secure secret manager.
- Never commit secrets to source control.
- Rotate keys regularly.
- Use HTTPS for every API request.
- Use the least-privileged key available.
- Monitor API usage for unexpected activity.
- Separate development and production credentials.

---

# Real-World Backend Example

Suppose your Express backend calls a weather service.

```bash
WEATHER_API_KEY="your_api_key"

curl \
-H "X-API-Key: $WEATHER_API_KEY" \
<https://weather.example.com/v1/current?city=Delhi>
```

Your backend:

1. Reads the key from an environment variable.
2. Sends it in the request header.
3. Receives the weather data.
4. Returns only the necessary information to your frontend.

The frontend **never sees the API key**.

---

# API Keys vs Bearer Tokens vs Basic Auth

|Feature|API Key|Bearer Token|Basic Auth|
|---|---|---|---|
|Represents|Application|User or session|Username & password|
|Expires|Sometimes|Usually|No|
|Revocable|Yes|Yes|Password change required|
|Sent Every Request|Yes|Yes|Yes|
|Common For|Public APIs|User login|Legacy/internal systems|

---

# Key Takeaways

- API keys identify an application making requests.
- Headers are generally safer than query parameters.
- Store keys securely using environment variables or secret managers.
- Never commit keys to Git repositories.
- Rotate compromised or outdated keys immediately.
- Protect every API request with HTTPS.

## 💡 Backend Engineer Tip

A common beginner mistake is calling third-party APIs (such as AI, payment, or email services) **directly from the frontend** using an API key. This exposes the key to anyone inspecting the application.

The recommended architecture is:

```
Frontend
    │
    ▼
Your Backend
    │
(API Key stored securely)
    ▼
Third-Party API
```

Your backend keeps the API key secret, makes the external request, and returns only the necessary data to the frontend. This pattern is standard practice in production backend systems.
