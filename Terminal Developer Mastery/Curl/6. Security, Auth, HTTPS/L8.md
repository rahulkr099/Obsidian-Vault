# What is a Cookie?

A **cookie** is a small piece of data stored by the browser.

The server sends it.

The browser stores it.

The browser automatically sends it back on future requests.

---

# Cookie Workflow

```
Client
   │
Request
   │
────────────►
Server
   │
Set-Cookie
   │
◄────────────
Browser stores cookie
   │
Future Request
Cookie:
sessionid=abc123
```

---

# What is a Session?

A session is **server-side storage**.

Instead of storing user information in the browser:

```
Browser

↓

Session ID
```

The server stores:

```
Session ID

↓

User Information
```

---

# Session Example

Suppose you log in.

The server creates:

```
Session ID

a8x92jd82
```

The server stores:

```
Session Table

a8x92jd82

↓

User ID: 42

Name: Rahul

Role: Admin
```

The browser only receives:

```
sessionid=a8x92jd82
```

---

# Login Flow

```
Login Request
       │
       ▼
Server
       │
Verify Username & Password
       │
Create Session
       │
Generate Session ID
       │
Set-Cookie
       ▼
Browser
```

---

# Set-Cookie Header

Example:

```
Set-Cookie: sessionid=abc123
```

The browser stores:

```
sessionid=abc123
```

---

# Future Requests

Every future request automatically includes:

```
Cookie: sessionid=abc123
```

Unlike JWTs, JavaScript doesn't usually need to manually add this header.

---

# Browser Workflow

```
User Logs In
      │
      ▼
Server
      │
Set-Cookie
      ▼
Browser Stores Cookie
      │
Every Request
      ▼
Cookie Sent Automatically
```

# Session Lookup

When the server receives:

```
Cookie: sessionid=abc123
```

It searches:

```
Session Store

abc123

↓

User ID

↓

Permissions

↓

Authenticated
```

---

# Cookie vs Session

These terms are often confused.

|Cookie|Session|
|---|---|
|Stored in browser|Stored on server|
|Small piece of data|User state|
|Sent with requests|Looked up using Session ID|

Think of it like this:

```
Cookie

↓

Contains Session ID

↓

Server Finds Session
```

---

# Cookie Attributes

Cookies can include additional properties.

Example:

```
Set-Cookie:
sessionid=abc123;
HttpOnly;
Secure;
SameSite=Lax
```

---

# HttpOnly

```
HttpOnly
```

Prevents JavaScript from reading the cookie using `document.cookie`.

Helps reduce the impact of many XSS attacks.

Recommended for authentication cookies.

---

# Secure

```
Secure
```

Cookie is sent **only over HTTPS**.

Never over plain HTTP.

Always enable this in production.

---

# SameSite

Controls whether cookies are sent with cross-site requests.

Values:

```
Strict
```

```
Lax
```

```
None
```

---

## SameSite=Strict

Most restrictive.

Cookies are **not** sent on cross-site requests.

Highest CSRF protection, but can affect user experience in some flows.

---

## SameSite=Lax

A balanced default.

Allows cookies for top-level navigation while protecting against many cross-site request forgery (CSRF) scenarios.

---

## SameSite=None

Cookies are sent with cross-site requests.

Must also include:

```
Secure
```

Otherwise, modern browsers reject the cookie.

Often required for third-party authentication flows or embedded content.

---

# Expiration

Temporary cookie:

```
Set-Cookie:
sessionid=abc123
```

Deleted when the browser session ends.

Persistent cookie:

```
Set-Cookie:
sessionid=abc123;
Max-Age=86400
```

or

```
Expires=Wed, 01 Jan 2027 00:00:00 GMT
```

Remains until it expires or is deleted.

# Using `curl`

Show headers:

```bash
curl -I <https://example.com>
```

Look for:

```
Set-Cookie:
```

---

# Save Cookies

```bash
curl \
-c cookies.txt \
<https://example.com>
```

- `c` (or `-cookie-jar`) saves received cookies.

Example file:

```
cookies.txt
```

---

# View Cookies

```bash
cat cookies.txt
```

You may see entries similar to:

```
example.com

sessionid

abc123
```

(The actual file uses the Netscape cookie file format.)

---

# Send Saved Cookies

```bash
curl \
-b cookies.txt \
<https://example.com/profile>
```

- `b` (or `-cookie`) loads cookies from a file and sends them with the request.

---

# Save and Reuse

Login:

```bash
curl \
-c cookies.txt \
-X POST \
-d "username=rahul&password=secret123" \
<https://example.com/login>
```

Then:

```bash
curl \
-b cookies.txt \
<https://example.com/dashboard>
```

Exactly like a browser.

---

# Cookies + Sessions

```
Login

↓

Server Creates Session

↓

Session ID

↓

Cookie

↓

Browser Stores Cookie

↓

Future Requests

↓

Server Finds Session
```

---

# Logout

Server:

Deletes session.

Browser:

Receives:

```
Set-Cookie:
sessionid=;
Max-Age=0
```

Cookie removed.

Session ends.

---

# Session Expiration

Sessions typically expire after inactivity.

Example:

```
30 minutes
```

or

```
24 hours
```

The exact timeout depends on the application's configuration.

---

# Session Storage

Sessions can be stored in:

- Memory (development)
- Redis
- Database
- Distributed cache

Large production systems commonly use Redis or another shared store so multiple application servers can access the same session data.

---

# Sessions vs JWT

|Sessions|JWT|
|---|---|
|Server stores state|Client stores token|
|Easy logout|Logout requires token invalidation strategy|
|Easy revocation|More complex revocation|
|Server memory/storage required|Stateless on server|
|Great for traditional web apps|Great for APIs & microservices|

# Common Mistakes

❌ **Storing sensitive data directly in cookies**

Store only a session identifier or carefully designed data. Avoid putting passwords or secrets into cookies.

---

❌ **Forgetting `HttpOnly`**

Authentication cookies should usually be inaccessible to JavaScript.

---

❌ **Not using `Secure`**

Authentication cookies should only travel over HTTPS in production.

---

❌ **Ignoring `SameSite`**

Choose an appropriate `SameSite` policy to reduce CSRF risk while supporting your application's flows.

---

❌ **Using in-memory sessions in production**

If your application runs on multiple servers or restarts, in-memory sessions can cause users to lose their sessions. Use a shared session store instead.

---

# Best Practices

- Use HTTPS for authenticated applications.
- Set `HttpOnly` on session cookies.
- Set `Secure` in production.
- Configure an appropriate `SameSite` value.
- Use a shared session store (such as Redis) for scalable applications.
- Expire inactive sessions.
- Destroy sessions on logout.

---

# Real-World Backend Example (Express.js)

A user logs into your Express application.

1. Express verifies the username and password.
2. A session is created and stored in Redis.
3. A random session ID is generated.
4. The response includes:

```
Set-Cookie:
sessionid=abc123;
HttpOnly;
Secure;
SameSite=Lax
```

On later requests:

```
Cookie:
sessionid=abc123
```

The backend retrieves the session from Redis and identifies the user without requiring them to log in again.

---

# Key Takeaways

- Cookies are stored in the browser.
- Sessions are stored on the server.
- Authentication cookies usually contain only a session ID.
- `Set-Cookie` creates cookies; the browser returns them in the `Cookie` header.
- `curl -c` saves cookies, and `curl -b` sends them.
- Use `HttpOnly`, `Secure`, and an appropriate `SameSite` setting for secure authentication cookies.

# 💡 Backend Engineer Tip

Since you've built Express.js backends before, you'll encounter both **JWT-based authentication** and **session-based authentication**.

A common guideline is:

- **Traditional web apps with server-rendered pages** → Sessions + Cookies
- **REST APIs consumed by React, mobile apps, or third-party clients** → JWT/Bearer Tokens
- **OAuth login (e.g., Google/GitHub)** → Often OAuth for identity, then your application establishes either a session cookie or issues its own JWT for subsequent requests.

Being comfortable with both approaches will help you work across a wide range of backend architectures.
