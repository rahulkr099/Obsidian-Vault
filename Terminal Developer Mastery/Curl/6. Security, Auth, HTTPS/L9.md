# What is mTLS?

mTLS stands for:

```
Mutual Transport Layer Security
```

Normal HTTPS:

```
Client

↓

Verifies Server
```

mTLS:

```
Client

⇅

Server

Both verify each other
```

Both parties present certificates.

Both parties prove their identity.

---

# TLS vs mTLS

## Normal HTTPS

```
Client
   │
TLS Handshake
   │
Verify Server Certificate
   ▼
Server
```

Only the **server** has a certificate.

---

## Mutual TLS

```
Client
   │
Client Certificate
   │
────────────►
Server
   │
Server Certificate
   │
◄────────────
Client
```

Now:

- Client trusts Server
- Server trusts Client

---

# Why Use mTLS?

Instead of asking:

```
Username

Password
```

or

```
Bearer Token
```

The server asks:

```
Show me your certificate.
```

Only clients with trusted certificates can connect.

# Certificates Used

### Server Certificate

Used by the server.

Example:

```
server.crt
```

---

### Client Certificate

Used by the client.

Example:

```
client.crt
```

---

### Client Private Key

Must remain secret.

Example:

```
client.key
```

---

### Certificate Authority

Signs both certificates.

Example:

```
company-ca.crt
```

---

# mTLS Handshake

```
Client
   │
Client Hello
   │
────────────►

Server
   │
Server Hello
Certificate
Certificate Request
   │
◄────────────

Client
   │
Client Certificate
Proof of Private Key
   │
────────────►

Server
   │
Verify Client Certificate
   │
Encrypted Session Begins
```

Notice the extra **Certificate Request** step.

---

# Using `curl`

Basic example:

```bash
curl \
--cert client.crt \
--key client.key \
<https://secure.example.com>
```

Meaning:

```
Client Certificate

+

Private Key
```

---

# Combined PEM File

Some systems provide:

```
client.pem
```

Containing both:

- Certificate
- Private Key

Then:

```bash
curl \
--cert client.pem \
<https://secure.example.com>
```

---

# Password-Protected Keys

If the private key is encrypted:

```bash
curl \
--cert client.crt \
--key client.key \
<https://secure.example.com>
```

`curl` may prompt you for the key's passphrase unless you provide it using supported options. Interactive prompting is generally safer than embedding secrets in scripts.

---

# Using a PKCS#12 File

Some organizations provide a `.p12` or `.pfx` file containing:

- Client certificate
- Private key
- Sometimes intermediate certificates

Example:

```bash
curl \
--cert client.p12:mypassword \
--cert-type P12 \
<https://secure.example.com>
```

---

# Certificate Validation

The server checks:

- Certificate signed by trusted CA?
- Certificate expired?
- Certificate revoked?
- Correct client?
- Valid signature?

If all checks pass:

```
HTTP/1.1 200 OK
```

---

# Failed Authentication

No certificate:

```
HTTP/1.1 403 Forbidden
```

or the TLS handshake may fail before any HTTP response is sent.

---

Invalid certificate:

```
TLS Handshake Failed
```

Connection rejected.

---

# mTLS Workflow

```
Client

↓

Present Client Certificate

↓

Server Verifies

↓

TLS Session Established

↓

HTTP Requests
```

Authentication happens during the TLS handshake.

---

# Certificate Revocation

Suppose an employee leaves.

Instead of changing passwords:

```
Revoke Certificate
```

The client certificate becomes invalid.

Future connections fail.

Revocation can be managed using mechanisms such as Certificate Revocation Lists (CRLs) or the Online Certificate Status Protocol (OCSP), depending on the environment.

# Common Errors

## Missing Certificate

```
handshake failure
```

Server expected a client certificate.

---

## Wrong Private Key

```
unable to use client certificate
```

The private key doesn't match the certificate.

---

## Expired Certificate

```
certificate expired
```

Renew the certificate.

---

## Unknown CA

```
unknown ca
```

The server doesn't trust the Certificate Authority that signed the client certificate.

---

## Revoked Certificate

```
certificate revoked
```

Access denied.

# Common Mistakes

❌ **Committing private keys to Git**

Never store:

```
client.key
```

in version control.

---

❌ **Sharing client certificates carelessly**

Treat client certificates and their private keys as sensitive credentials.

---

❌ **Using expired certificates**

Monitor and renew certificates before they expire.

---

❌ **Ignoring certificate revocation**

Revoke compromised certificates promptly.

---

❌ **Confusing server and client certificates**

Server certificates identify the server.

Client certificates identify the client.

---

# Best Practices

- Keep private keys secure.
- Protect private keys with strong passphrases where appropriate.
- Issue certificates from trusted CAs.
- Rotate certificates periodically.
- Revoke compromised certificates immediately.
- Monitor certificate expiration.
- Use mTLS only where strong mutual authentication is required.

# Real-World Backend Example

Imagine your company has an internal **Payment API**.

Architecture:

```
Order Service
      │
Client Certificate
      ▼
Payment Service
      │
Verify Certificate
      ▼
Process Payment
```

Before any payment request is accepted:

1. The Payment Service verifies the Order Service's client certificate.
2. Only trusted internal services can connect.
3. Unauthorized services are rejected before application logic runs.

This provides strong service-to-service authentication, even if the network is compromised.

# Key Takeaways

- mTLS requires **both** the client and server to authenticate with certificates.
- Client authentication happens during the TLS handshake.
- `curl` supports client certificates with `-cert` and `-key`.
- mTLS is widely used for secure service-to-service communication.
- Private keys must always be protected and never shared.
