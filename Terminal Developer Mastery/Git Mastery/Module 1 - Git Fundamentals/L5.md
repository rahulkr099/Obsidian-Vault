# Lesson 5 — Git File Lifecycle

This is one of the **most important lessons** in Git.

If you understand the Git file lifecycle, you'll understand **how Git thinks**.

Almost every Git command (`add`, `commit`, `restore`, `reset`, `diff`, etc.) is based on these file states.

# The Three Git Areas

Before learning file states, understand Git's three main areas.

```text
                Git Repository
             (Commit History)
                    ▲
                    │
             git commit
                    │
                    ▼
             Staging Area
                (Index)
                    ▲
                    │
               git add
                    │
                    ▼
            Working Directory
          (Your project files)
```

Think of them like this:

|Area|Purpose|
|---|---|
|Working Directory|Where you write and edit code|
|Staging Area|Where you prepare changes for the next commit|
|Repository|Where committed snapshots are stored|

Suppose you're building a Todo API.

```text
todo-api/
│
├── src/
│   ├── app.js
│   ├── routes.js
│   └── auth.js
│
├── package.json
└── README.md
```

You edit:

```text
src/auth.js
```

At this moment:

The file exists only in the **Working Directory**.

Git hasn't saved anything yet.

# The Four Main File States

A file can be in one of these states:

```text
Untracked
     │
git add
     ▼
Staged
     │
git commit
     ▼
Committed
     │
Edit file
     ▼
Modified
     │
git add
     ▼
Staged
```

Let's understand each one.

---

# 1. Untracked

Git has never seen this file before.

Example:

```bash
touch auth.js
```

Check status:

```bash
git status
```

Output:

```text
Untracked files:

auth.js
```

Git says:

> "I see this file, but I'm not tracking it."

---

# Example

Suppose you create:

```text
controllers/userController.js
```

Git knows it exists.

But it isn't part of project history.

---

# 2. Staged

You tell Git:

> "Include this file in the next commit."

Command:

```bash
git add auth.js
```

Now:

```bash
git status
```

Output:

```text
Changes to be committed:

new file: auth.js
```

Git has copied the current version into the **Staging Area**.

---

# Why Have a Staging Area?

Imagine you changed:

```text
auth.js
```

```text
user.js
```

```text
payment.js
```

You only want to save:

- auth
    
- user
    

Not payment.

The staging area lets you choose exactly what goes into the next commit.

---

# 3. Committed

Now save everything permanently.

```bash
git commit -m "Add authentication module"
```

Git creates a snapshot.

The file is now safely stored in the repository.

---

# 4. Modified

Suppose you edit:

```text
auth.js
```

Again.

Git notices.

```bash
git status
```

Output:

```text
Changes not staged for commit:

modified: auth.js
```

The committed version and the current version are different.

# The Complete Lifecycle

Let's build a small project.

---

## Step 1

Create a file.

```bash
touch app.js
```

Status:

```text
Untracked
```

---

## Step 2

Stage it.

```bash
git add app.js
```

Status:

```text
Staged
```

---

## Step 3

Commit it.

```bash
git commit -m "Create app.js"
```

Status:

```text
Working tree clean
```

---

## Step 4

Edit it.

```javascript
console.log("Hello");
```

Status:

```text
Modified
```

---

## Step 5

Stage again.

```bash
git add app.js
```

Status:

```text
Staged
```

---

## Step 6

Commit again.

```bash
git commit -m "Add hello message"
```

Done.

# Understanding `git status`

`git status` is the command you'll use most often.

Run:

```bash
git status
```

It tells you:

- Current branch
    
- Modified files
    
- Staged files
    
- Untracked files
    
- Merge status
    
- Rebase status
    

Example:

```text
On branch main

Changes to be committed:
    modified: app.js

Changes not staged:
    modified: auth.js

Untracked files:
    payment.js
```

From this, you immediately know:

- `app.js` → staged
    
- `auth.js` → modified
    
- `payment.js` → untracked
    

---

# Example from a Backend Project

Imagine:

```text
src/
├── auth.js
├── routes.js
├── payment.js
└── profile.js
```

Status:

```text
modified:

auth.js

routes.js

untracked:

payment.js

staged:

profile.js
```

This means:

- `profile.js` is ready to commit.
    
- `auth.js` and `routes.js` still need `git add`.
    
- `payment.js` hasn't been added to Git yet.

# Common Mistakes

## Mistake 1

Editing a file and forgetting:

```bash
git add
```

Result:

The changes won't be included in the next commit.

---

## Mistake 2

Thinking:

```bash
git commit
```

automatically stages files.

It doesn't.

You must stage changes first.

---

## Mistake 3

Not checking:

```bash
git status
```

Professional developers check `git status` frequently before adding, committing, switching branches, or pushing.

# Best Practices

- Run `git status` often.
    
- Commit small, focused changes.
    
- Stage only related files together.
    
- Avoid large commits that mix unrelated work.
    
- Review what you're about to commit before running `git commit`.

After each `git status`, try to identify the state of `app.js` before looking at the output.

# Mini Challenge

Create this backend project:

```text
backend-api/
├── src/
│   ├── app.js
│   ├── routes.js
│   └── auth.js
├── package.json
└── README.md
```

Then:

1. Initialize Git.
    
2. Create all the files.
    
3. Observe them as **Untracked**.
    
4. Stage only `README.md` and `package.json`.
    
5. Check `git status`.
    
6. Commit only those staged files.
    
7. Verify that the `src/` files are still untracked.
    

This exercise demonstrates one of Git's biggest strengths: **you decide exactly what becomes part of each commit.**
