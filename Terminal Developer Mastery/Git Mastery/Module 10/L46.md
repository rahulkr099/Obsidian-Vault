# Why Learn Git Internals?

Most developers know how to use Git:

```bash
git add .
git commit -m "Add authentication"
git push origin main
```

But very few know **what Git actually does**.

Understanding Git internals helps you:

- Debug strange Git issues
    
- Recover lost commits
    
- Understand merge conflicts better
    
- Use advanced Git commands confidently
    
- Perform well in backend engineering interviews
    

---

# Git Is a Content-Addressable Database

Many beginners think Git stores:

```text
Project

↓

Version 1

↓

Version 2

↓

Version 3
```

Not exactly.

Git actually stores **objects** in a database.

```text
Blob

Tree

Commit

Tag
```

Everything in Git is built from these four object types.

---

# Git Doesn't Think in Files

You think:

```text
app.js
```

Git thinks:

```text
Blob Object
```

You think:

```text
src/
```

Git thinks:

```text
Tree Object
```

You think:

```text
Version 1
```

Git thinks:

```text
Commit Object
```

# The Three Areas of Git

Git operates with **three main areas**.

```text
Working Directory

↓

Staging Area (Index)

↓

Repository (.git)
```

Understanding these three areas explains almost every Git command.

---

# 1. Working Directory

This is what you see in your editor.

Example:

```text
project/

│

├── app.js

├── package.json

└── README.md
```

When you edit:

```javascript
console.log("Hello");
```

You're changing the **Working Directory**.

Git has **not** saved anything yet.

---

# 2. Staging Area (Index)

When you run:

```bash
git add app.js
```

Git copies the current version of `app.js` into the **Staging Area**.

```text
Working Directory

↓

Staging Area
```

The staging area lets you choose **exactly what** will go into the next commit.

Think of it as a **shopping cart** before checkout.

---

# 3. Repository (`.git`)

When you run:

```bash
git commit -m "Update app"
```

Git stores the staged content permanently inside:

```text
.git/
```

This directory is the Git repository.

---

# Visual Overview

```text
Edit File

↓

Working Directory

↓

git add

↓

Staging Area

↓

git commit

↓

Repository
```

This flow is fundamental to Git.

---

# What Happens During `git add`?

Suppose:

```javascript
console.log("Hello");
```

You save the file.

Git sees:

```text
Modified
```

Run:

```bash
git add app.js
```

Git:

1. Reads the file.
    
2. Compresses its content.
    
3. Creates a **Blob object** (if that exact content doesn't already exist).
    
4. Records it in the staging area.
    

The file is **not yet part of a commit**.

---

# What Happens During `git commit`?

When you commit:

```bash
git commit -m "Initial commit"
```

Git:

- Creates a **Tree** representing the directory structure.
    
- Creates a **Commit** object.
    
- Stores:
    
    - author
        
    - timestamp
        
    - commit message
        
    - parent commit (if any)
        
    - tree reference
        
- Moves the current branch pointer to the new commit.
    

---

# The `.git` Directory

Create a repository:

```bash
git init
```

You'll see:

```text
project/
│
├── .git/
├── app.js
└── README.md
```

The `.git` directory contains **all Git metadata**.

Delete it:

```bash
rm -rf .git
```

Your files remain, but Git history disappears.

---

# The `objects` Directory

The most important folder:

```text
.git/objects/
```

It stores:

```text
Blob Objects

Tree Objects

Commit Objects

Tag Objects
```

Git compresses these objects to save space.

# Example Repository

Suppose:

```text
project/

README.md

app.js
```

After the first commit:

```text
Working Directory

↓

Blob (README)

Blob (app.js)

↓

Tree

↓

Commit
```

Git stores these objects in `.git/objects`.

---

# Blob Objects

A **Blob** stores the **contents of a file**.

Example:

```text
README.md
```

Content:

```text
Hello Git
```

Git creates:

```text
Blob
```

Important:

A blob **does not store the filename**.

It stores **only the file's contents**.

---

# Tree Objects

A **Tree** stores:

- filenames
    
- directories
    
- permissions
    
- references to blobs and other trees
    

Example:

```text
src/

│

├── app.js

├── auth.js

└── utils/
```

Git represents this as a tree object.

Think of a tree as Git's version of a directory.

---

# Commit Objects

A commit stores:

- Author
    
- Email
    
- Timestamp
    
- Commit message
    
- Parent commit
    
- Tree reference
    

Visual:

```text
Commit

↓

Tree

↓

Blob

Blob

Blob
```

The commit itself doesn't contain file contents—it points to a tree.

---

# Tag Objects

Annotated tags are also stored as Git objects.

They contain:

- Tag name
    
- Message
    
- Author
    
- Referenced object (usually a commit)
    

We'll revisit tags when discussing object types in more depth.

---

# Git Uses Snapshots, Not Diffs

A common misconception:

> Git stores only differences between versions.

In reality:

Git primarily stores **snapshots** of your project.

Imagine:

Commit 1:

```text
app.js
README.md
```

Commit 2:

Only `app.js` changes.

Git creates a new snapshot that reuses the unchanged `README.md` blob instead of copying it again.

This is efficient because identical content is stored only once.

---

# Why Git Is Fast

Git is fast because:

✅ Most operations use the local repository.

✅ Objects are compressed.

✅ Unchanged content is reused.

✅ History is stored efficiently.

Commands like:

```bash
git log
```

or

```bash
git diff
```

usually don't require an internet connection.

---

# Branches Are Lightweight

Many beginners think:

```text
Branch

↓

Copy Entire Repository
```

Wrong.

A Git branch is simply:

```text
Pointer

↓

Commit
```

Example:

```text
main

↓

Commit A
```

Create:

```bash
git checkout -b feature/login
```

Now:

```text
main ─────► Commit A

feature/login ─► Commit A
```

No files are duplicated.

This makes branch creation almost instantaneous.

---

# Why Git Rarely Duplicates Data

Suppose:

Commit 1:

```text
README.md
```

Commit 2:

README is unchanged.

Git reuses the same blob.

```text
Blob

▲

│

Commit1

Commit2
```

This content-addressable storage saves disk space.

# Common Misconceptions

❌ Git stores files by filename.

Reality:

Git stores file **contents** in blobs.

---

❌ Every commit duplicates the repository.

Reality:

Git reuses unchanged objects.

---

❌ Branches are expensive.

Reality:

Branches are lightweight pointers.

---

❌ `git add` creates a commit.

Reality:

It only stages changes.

---

# Best Practices

✅ Understand the Working Directory, Staging Area, and Repository.

✅ Stage only what belongs in the next commit.

✅ Remember that branches are cheap—create them freely.

✅ Don't manually edit files inside `.git` unless you fully understand the consequences.

# Interview Questions

### 1. What are the three areas of Git?

- Working Directory
    
- Staging Area (Index)
    
- Repository (`.git`)
    

---

### 2. What does `git add` do?

It stages changes by creating blob objects (if needed) and updating the index. It does **not** create a commit.

---

### 3. What is stored inside the `.git` directory?

Git metadata, object database, references, configuration, logs, hooks, the index, and more.

---

### 4. Does Git store complete copies of files in every commit?

Git stores snapshots of the project while reusing unchanged objects, so identical file contents are not duplicated.

---

### 5. Why are Git branches lightweight?

Because a branch is essentially a movable pointer to a commit, not a separate copy of the repository.

## 💡 Backend Engineer Tip

Understanding Git internals makes advanced commands like `reflog`, `reset`, `cherry-pick`, and `rebase` much less mysterious. Once you realize that Git is fundamentally a database of interconnected objects and lightweight pointers, many "magic" Git behaviors become logical and predictable.
