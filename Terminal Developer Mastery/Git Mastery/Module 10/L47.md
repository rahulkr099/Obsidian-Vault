# Lesson 47 — Git Objects (Blob, Tree, Commit & Tag)

> **Goal:** Understand the four Git object types—**Blob**, **Tree**, **Commit**, and **Tag**. By the end of this lesson, you'll know how Git stores your project internally and how to inspect these objects using Git's low-level commands.

---

# Everything in Git Is an Object

When you run:

```bash
git add .
git commit -m "Initial commit"
```

Git doesn't save "files" and "folders" in the way your operating system does.

Instead, it creates objects.

There are only **four object types**:

```text
Blob
Tree
Commit
Tag
```

Everything in Git history is built from these four building blocks.

---

# The Relationship Between Objects

A Git repository looks like this internally:

```text
Commit
   │
   ▼
 Tree
 ├──── Blob (README.md)
 ├──── Blob (package.json)
 └──── Tree (src)
          │
          ├── Blob (app.js)
          └── Blob (auth.js)
```

Think of it like a family tree:

- Commit points to a Tree.
    
- Tree points to Blobs and other Trees.
    
- Blob stores file content.
    

---

# Object 1 — Blob

**Blob = Binary Large Object**

A Blob stores:

- File contents
    
- Nothing else
    

It **does not store**:

- Filename
    
- Directory
    
- Permissions
    
- Creation date
    

Example:

```text
README.md
```

Content:

```text
Hello Git
```

Git stores:

```text
Blob

↓

Hello Git
```

Notice:

The filename is **not** part of the blob.

---

# Why Doesn't Git Store the Filename?

Imagine:

```text
README.md

↓

Rename

↓

README_NEW.md
```

Content stays exactly the same.

Git simply changes the Tree object.

The Blob remains unchanged.

This saves storage.

---

# Blob Example

File:

```javascript
console.log("Hello");
```

Git stores something conceptually like:

```text
Blob

↓

console.log("Hello");
```

The blob has no idea whether the file is called:

```text
app.js
```

or

```text
server.js
```

The content is what matters.

---

# Creating a Blob Manually

Git provides a plumbing command:

```bash
git hash-object app.js
```

Example output:

```text
3b18e8f...
```

This is the hash of the file's contents.

To actually store the object in Git:

```bash
git hash-object -w app.js
```

The `-w` flag means **write** the object into Git's object database.

---

# Inspecting a Blob

View the object type:

```bash
git cat-file -t <hash>
```

Output:

```text
blob
```

View the contents:

```bash
git cat-file -p <hash>
```

Output:

```javascript
console.log("Hello");
```

---

# Object 2 — Tree

A Tree represents a directory.

A Tree stores:

- Filenames
    
- Directory names
    
- Permissions
    
- References to blobs
    
- References to other trees
    

Example:

```text
project/

├── README.md
├── package.json
└── src/
    ├── app.js
    └── auth.js
```

Git creates:

```text
Tree

├── README → Blob
├── package → Blob
└── src → Tree
```

---

# Nested Trees

Directories become Trees.

```text
src/

└── controllers/

       └── auth.js
```

Internally:

```text
Tree (root)

↓

Tree (src)

↓

Tree (controllers)

↓

Blob (auth.js)
```

---

# Viewing a Tree

Find the current commit:

```bash
git rev-parse HEAD
```

Inspect it:

```bash
git cat-file -p HEAD
```

You'll see something similar to:

```text
tree 4e5c...
author Rahul
committer Rahul

Initial commit
```

Now inspect the tree:

```bash
git cat-file -p <tree_hash>
```

Example output:

```text
README.md
package.json
src
```

Each entry points to another object.

---

# Object 3 — Commit

The Commit object ties everything together.

It stores:

- Tree hash
    
- Parent commit
    
- Author
    
- Committer
    
- Timestamp
    
- Commit message
    

Diagram:

```text
Commit

↓

Tree

↓

Blobs
```

---

# Commit Example

Conceptually:

```text
Commit

Tree: 91ab...

Parent: 32bc...

Author: Rahul

Message:

"Add authentication"
```

The commit itself does **not** store your files.

It stores references to them.

---

# Commit Chain

Suppose:

```text
Commit A

↓

Commit B

↓

Commit C
```

Each commit stores:

```text
Parent

↓

Previous Commit
```

This creates Git's history.

---

# Visual Commit Graph

```text
Commit C

↓

Commit B

↓

Commit A
```

Every commit knows its parent.

This is why Git can show history with:

```bash
git log
```

---

# Inspecting a Commit

Current commit:

```bash
git rev-parse HEAD
```

View it:

```bash
git cat-file -p HEAD
```

Example:

```text
tree ...

parent ...

author ...

committer ...

message
```

---

# Object 4 — Tag

Annotated tags are objects too.

They store:

- Tag name
    
- Author
    
- Message
    
- Referenced object
    

Example:

```bash
git tag -a v1.0 -m "Production release"
```

Inspect:

```bash
git cat-file -p v1.0
```

You'll see:

```text
object ...

type commit

tag v1.0

tagger ...

Production release
```

---

# Lightweight Tags

Remember:

```bash
git tag v1.0
```

Lightweight tags are **not** separate tag objects.

They're just references that point directly to a commit.

---

# Object Relationships

Here's the complete picture:

```text
Tag

↓

Commit

↓

Tree

├── Blob

├── Blob

└── Tree

      ├── Blob

      └── Blob
```

Everything eventually points back to blobs.

---

# Object IDs (Hashes)

Every object has a unique ID.

Example:

```text
a94c1d4f3...
```

This ID is calculated from the object's contents.

If the contents change:

```text
Hello

↓

Hello World
```

The hash changes.

That means:

New content → New object.

---

# Why Hashes Matter

Hashes allow Git to:

- Detect corruption
    
- Avoid duplicate storage
    
- Identify objects uniquely
    
- Verify integrity
    

If even one character changes, the hash changes completely.

---

# Where Are Objects Stored?

Inside:

```text
.git/objects/
```

Example:

```text
.git/

└── objects/

      ├── 2a/

      ├── 7b/

      └── f9/
```

Git organizes objects into subdirectories based on the first two characters of their hash.

For example:

```text
Hash:

ab1234567890...
```

Stored as:

```text
.git/objects/ab/1234567890...
```

This improves filesystem performance.

---

# Real Backend Example

Project:

```text
expense-api/

├── server.js
├── routes/
├── controllers/
└── package.json
```

After commit:

```text
Commit

↓

Tree

├── package.json → Blob

├── server.js → Blob

└── controllers → Tree

        └── auth.js → Blob
```

No duplicate copies are created for unchanged files.

---

# Low-Level Commands Summary

Create a blob:

```bash
git hash-object -w app.js
```

Get object type:

```bash
git cat-file -t <hash>
```

Print object contents:

```bash
git cat-file -p <hash>
```

Current commit hash:

```bash
git rev-parse HEAD
```

List object IDs in the repository (reachable from refs):

```bash
git rev-list --objects --all
```

---

# Common Misconceptions

❌ Blob stores filenames.

Reality:

Blob stores only file contents.

---

❌ Commit stores file contents.

Reality:

Commit points to a tree.

---

❌ Trees store file data.

Reality:

Trees store names and references.

---

❌ Lightweight tags create tag objects.

Reality:

Only annotated tags create tag objects.

---

# Best Practices

✅ Understand the relationship:

```text
Commit

↓

Tree

↓

Blob
```

✅ Use plumbing commands on a practice repository.

✅ Avoid modifying `.git/objects` manually.

✅ Remember that hashes are based on object contents.

---

# Useful Commands Summary

|Command|Purpose|
|---|---|
|`git hash-object file`|Compute a file's hash|
|`git hash-object -w file`|Store a blob object|
|`git cat-file -t <hash>`|Show object type|
|`git cat-file -p <hash>`|Print object contents|
|`git rev-parse HEAD`|Show current commit hash|
|`git rev-list --objects --all`|List reachable objects|

# Interview Questions

### 1. What are the four Git object types?

- Blob
    
- Tree
    
- Commit
    
- Tag
    

---

### 2. What does a Blob store?

Only the file's contents—not its filename, path, or metadata.

---

### 3. What is the purpose of a Tree object?

It represents a directory and maps filenames to blobs or other trees, along with metadata like file modes.

---

### 4. What information does a Commit object contain?

A reference to a tree, parent commit(s), author, committer, timestamps, and the commit message.

---

### 5. What's the difference between annotated and lightweight tags internally?

Annotated tags are separate Git objects containing metadata, while lightweight tags are simply references that point directly to a commit.

## 💡 Backend Engineer Tip

You rarely use Git's plumbing commands in day-to-day development, but understanding them explains _why_ commands like `reset`, `checkout`, `rebase`, and `cherry-pick` work. When debugging complex Git issues or recovering history, this knowledge becomes incredibly valuable.
