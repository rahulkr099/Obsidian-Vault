# Lesson 48 — SHA Hashes, Object IDs & Git Integrity

> **Goal:** Understand how Git identifies every object using cryptographic hashes, why even a tiny change creates a completely different object ID, and how hashing makes Git fast, reliable, and resistant to corruption.

---

# Why Do Git Objects Have Strange IDs?

Suppose you create a commit:

```bash
git commit -m "Add authentication"
```

Git shows:

```text
commit 3d5b8e8a8b7d7c90f9a8d1f2c3b4a5d6e7f8g9h
```

Where did this long string come from?

It is a **cryptographic hash**.

Git uses it as the object's identity.

---

# What is a Hash?

A **hash function** converts any amount of data into a fixed-size value.

Example:

```text
Input

↓

Hello Git
```

Output:

```text
9f8a73d4...
```

The output is called:

- Hash
    
- Digest
    
- Object ID
    

These terms are often used interchangeably in Git discussions.

---

# Think of It Like a Fingerprint

Every object gets a unique fingerprint.

```text
README.md

↓

Hash A
```

```text
app.js

↓

Hash B
```

Even if two files have different names but **identical content**, they produce the **same hash**.

---

# One Character Changes Everything

Original file:

```text
Hello Git
```

Hash:

```text
7f3a91...
```

Change one letter:

```text
Hello GIT
```

New hash:

```text
d91b7e...
```

Even a tiny modification results in a completely different hash.

This property is called the **avalanche effect**.

---

# Why Is This Important?

Because Git can instantly tell:

```text
Same Content

↓

Same Hash
```

or

```text
Different Content

↓

Different Hash
```

This enables efficient storage and integrity checks.

---

# Content-Based Storage

Suppose you have:

```text
README.md
```

Content:

```text
Welcome
```

Later you create:

```text
COPY.md
```

with exactly the same content:

```text
Welcome
```

Git stores:

```text
One Blob

↓

Referenced Twice
```

The filename doesn't matter.

Only the content matters.

---

# Object IDs

Every Git object has an ID.

Example:

```text
Blob

↓

5b1c9f...
```

```text
Tree

↓

8d7fa2...
```

```text
Commit

↓

a61e92...
```

Git uses these IDs to connect objects together.

---

# What Is SHA?

Historically, Git used **SHA-1** to generate object IDs.

SHA stands for:

```text
Secure Hash Algorithm
```

SHA-1 produces a **160-bit hash**, typically displayed as 40 hexadecimal characters.

Example:

```text
5d41402abc4b2a76b9719d911017c592
```

(Shown here only as an example of hexadecimal text.)

---

# SHA-1 vs SHA-256

Modern Git also supports **SHA-256** repositories.

|SHA-1|SHA-256|
|---|---|
|160-bit|256-bit|
|40 hex characters|64 hex characters|
|Traditional Git default|Stronger modern option|

Most existing repositories still use SHA-1 for compatibility, while newer repositories can be initialized with SHA-256 support.

---

# Why Did Git Move Toward SHA-256?

Researchers demonstrated practical collision attacks against SHA-1.

Although Git included additional protections, the community introduced SHA-256 support to strengthen long-term security.

---

# What Is a Collision?

A collision means:

```text
Different Inputs

↓

Same Hash
```

For a strong hash function, collisions should be extraordinarily difficult to find.

Git depends on hashes uniquely identifying object contents.

---

# Git's Integrity Model

Imagine someone edits a stored object.

Original:

```text
Hello Git
```

Stored hash:

```text
ab123...
```

Someone changes the object:

```text
Hello Hacker
```

The content no longer matches the recorded hash.

Git detects this inconsistency.

---

# Hash Chain

A commit stores:

```text
Tree Hash
```

The tree stores:

```text
Blob Hashes
```

Diagram:

```text
Commit

↓

Tree

↓

Blob

↓

File Content
```

If one blob changes:

- Blob hash changes
    
- Tree hash changes
    
- Commit hash changes
    

The entire chain is affected.

---

# Why Commit Hashes Change

Suppose:

Commit:

```text
Add Login
```

Later you modify:

```text
app.js
```

Even if the commit message stays the same:

```text
Add Login
```

The commit receives a **new hash**, because it now references a different tree.

---

# Commit Identity

A commit hash depends on:

- Tree
    
- Parent commit(s)
    
- Author
    
- Committer
    
- Timestamp
    
- Commit message
    

Changing any of these produces a new commit ID.

---

# Example

Original:

```text
Author

↓

Rahul
```

Hash:

```text
A123
```

Change only the commit message:

```text
Fix Login
```

New hash:

```text
B456
```

The commit is a different object.

---

# Why Rebasing Changes Commit IDs

Rebase rewrites commits.

Example:

Before:

```text
A

↓

B

↓

C
```

After rebase:

```text
A

↓

B'

↓

C'
```

Even if the code is identical, the parent relationships change.

Therefore:

```text
New Commit Hashes
```

This is why rebasing rewrites history.

---

# Verifying Repository Integrity

Git provides:

```bash
git fsck
```

This checks:

- Missing objects
    
- Corrupted objects
    
- Broken references
    
- Repository consistency
    

Healthy repository:

```text
No Problems Found
```

If corruption exists:

Git reports the affected objects.

# Finding Object IDs

Current commit:

```bash
git rev-parse HEAD
```

Example output:

```text
8a5c9d...
```

Compute a file hash:

```bash
git hash-object app.js
```

View object type:

```bash

```

Print object contents:

```bash

```

# Real Backend Example

Repository:

```text
expense-api/

├── server.js
├── auth.js
└── package.json
```

Modify:

```text
auth.js
```

Git creates:

```text
New Blob

↓

New Tree

↓

New Commit
```

Only the changed path receives new objects.

Everything else is reused.

---

# Why Git Is Efficient

Imagine:

Repository:

```text
1000 Files
```

Only one file changes.

Git creates:

```text
1 New Blob

↓

Updated Tree(s)

↓

1 New Commit
```

The remaining unchanged blobs are reused.

This makes Git very space-efficient.

---

# Git Is Tamper-Evident

Because objects are identified by their contents:

```text
Modify Object

↓

Hash Changes

↓

References Break
```

Git can detect unexpected changes.

This is one reason Git is trusted for source code management.

---

# Common Misconceptions

❌ Hashes are random numbers.

Reality:

Hashes are deterministic. The same input always produces the same output.

---

❌ Renaming a file changes its blob hash.

Reality:

The blob stores only file contents. Renaming changes the tree, not the blob.

---

❌ Commit hashes only depend on code.

Reality:

Commit metadata (author, message, parent, timestamps, etc.) also contributes.

---

❌ Git compares every file byte-by-byte all the time.

Reality:

Git primarily uses object IDs to identify identical content efficiently.

---

# Best Practices

✅ Don't rely on abbreviated hashes when absolute uniqueness matters in scripts.

✅ Use commit hashes when discussing specific code versions.

✅ Run `git fsck` if you suspect repository corruption.

✅ Understand that rewriting history changes commit IDs.

# Interview Questions

### 1. What is a Git object ID?

A Git object ID is a cryptographic hash generated from an object's contents (and, for commits, associated metadata). It uniquely identifies that object.

---

### 2. Why does changing one character produce a different hash?

Because cryptographic hash functions have the avalanche effect, where even a tiny input change produces a dramatically different output.

---

### 3. Why do commit hashes change after a rebase?

Rebase rewrites commits by changing their parent relationships (and often timestamps), creating new commit objects with new hashes.

---

### 4. Does renaming a file create a new blob?

Not if the file contents stay the same. The blob is reused, while the tree object changes to reflect the new filename.

---

### 5. What does `git fsck` do?

It verifies the integrity and connectivity of the Git object database, reporting missing, corrupted, or unreachable objects.

## 💡 Backend Engineer Tip

Hashes are the foundation of Git's design. Once you understand that every object is identified by its content, many advanced Git behaviors—such as history rewriting, object reuse, deduplication, and repository verification—become much easier to reason about. This knowledge is especially useful when working with large backend codebases or debugging complex Git issues.
