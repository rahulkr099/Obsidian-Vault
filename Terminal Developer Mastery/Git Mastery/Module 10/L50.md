

# Part 10 — Git Internals & Advanced Concepts

# Lesson 50 — Git References (HEAD, Branches & Refs)

> **Goal:** Understand how Git keeps track of commits using references (refs). By the end of this lesson, you'll know what `HEAD` is, how branches work internally, why detached `HEAD` happens, and how Git moves branch pointers after every commit.

---

# What Are Git References?

Imagine Git had to remember commit hashes manually.

Example:

```text
8f2a3b91d0e5a6f7...
```

Typing long hashes every time would be impractical.

Instead, Git uses **references**, or **refs**.

A ref is simply a **human-readable name that points to an object**, usually a commit.

Examples:

```text
main
feature/login
v1.0
HEAD
```

---

# Why References Exist

Without refs:

```text
Checkout

↓

8a7b6c5d4e...
```

With refs:

```text
Checkout

↓

main
```

Much easier!

---

# Types of References

Git has several kinds of refs.

```text
HEAD

Branches

Tags

Remote Branches
```

Most of the time, these point to commits.

---

# The Most Important Reference: HEAD

`HEAD` tells Git:

> **"This is where I'm currently working."**

Think of it as your **current location**.

Example:

```text
main

↓

Commit C
```

`HEAD` points to:

```text
main
```

So internally:

```text
HEAD

↓

main

↓

Commit C
```

---

# Viewing HEAD

Run:

```bash
cat .git/HEAD
```

Typical output:

```text
ref: refs/heads/main
```

This means:

```text
HEAD

↓

refs/heads/main

↓

Latest Commit
```

HEAD usually points to a **branch**, not directly to a commit.

---

# Branches Are Just References

Many beginners think:

```text
Branch

↓

Copy of Repository
```

Wrong.

A branch is just:

```text
Pointer

↓

Commit
```

Example:

```text
main

↓

Commit A
```

---

# Creating a Branch

Suppose:

```text
Commit A
```

Run:

```bash
git checkout -b feature/login
```

Now:

```text
main ─────────► Commit A

feature/login ─► Commit A
```

Both branches point to the same commit.

No files are copied.

---

# Making a Commit

You're on:

```text
feature/login
```

Create a commit.

Git creates:

```text
Commit B
```

Then moves only:

```text
feature/login
```

Diagram:

```text
main ─────────► Commit A

feature/login ─► Commit B
```

The `main` branch stays where it was.

---

# HEAD Moves Too

Remember:

```text
HEAD

↓

feature/login
```

After the commit:

```text
HEAD

↓

feature/login

↓

Commit B
```

HEAD follows the current branch.

---

# Switching Branches

Run:

```bash
git checkout main
```

Now:

```text
HEAD

↓

main
```

The working directory changes to match the commit pointed to by `main`.

---

# Branch Movement

Suppose:

```text
main

↓

Commit A
```

Create:

```text
Commit B
```

Git updates:

```text
main

↓

Commit B
```

The branch pointer moves automatically.

Previous commits remain unchanged.

---

# Visual Example

Before commit:

```text
HEAD
 │
 ▼
main

↓

Commit A
```

After commit:

```text
HEAD
 │
 ▼
main

↓

Commit B

↓

Commit A
```

Notice:

The commit didn't move.

The **branch pointer** moved.

---

# Detached HEAD

One of the most confusing Git concepts.

Suppose:

```text
Commit A

↓

Commit B

↓

Commit C
```

Checkout:

```bash
git checkout <commit-hash>
```

Now:

```text
HEAD

↓

Commit B
```

HEAD points **directly to a commit**, not a branch.

This is called:

```text
Detached HEAD
```

---

# Detached HEAD Diagram

Normal:

```text
HEAD

↓

main

↓

Commit C
```

Detached:

```text
HEAD

↓

Commit B
```

No branch is attached.

---

# Is Detached HEAD Dangerous?

Not immediately.

You can:

- View old code
    
- Run tests
    
- Inspect history
    
- Build old releases
    

The danger is making commits and then forgetting to save them.

---

# Example

Checkout:

```bash
git checkout HEAD~2
```

Git says:

```text
You are in 'detached HEAD' state.
```

If you commit:

```bash
git commit -m "Experiment"
```

The commit exists.

But no branch points to it.

If you later switch branches without creating a reference, that commit can become difficult to find (though it is often recoverable via `git reflog` for some time).

---

# Recovering Detached HEAD Work

Create a branch:

```bash
git checkout -b experiment
```

Now:

```text
experiment

↓

New Commit
```

The work is safely referenced.

---

# Git References Directory

Inside:

```text
.git/
```

You'll find:

```text
refs/

├── heads/

├── tags/

└── remotes/
```

Each directory stores a different type of reference.

---

# Branch References

Example:

```text
.git/refs/heads/
```

Contains:

```text
main

feature/login

feature/payment
```

Each file stores the hash of the commit that the branch points to.

Example:

```bash
cat .git/refs/heads/main
```

Output:

```text
9ab37d...
```

---

# Tag References

Annotated or lightweight tags are stored under:

```text
.git/refs/tags/
```

Example:

```text
v1.0

v2.0
```

Each tag references an object (commonly a commit).

---

# Remote References

When you fetch from GitHub:

```bash
git fetch origin
```

Git updates:

```text
refs/remotes/origin/main
```

These are **remote-tracking branches**.

They record the last known state of the remote repository.

---

# HEAD vs Branch

HEAD:

```text
Current Location
```

Branch:

```text
Named Pointer
```

Usually:

```text
HEAD

↓

Branch

↓

Commit
```

---

# Symbolic References

HEAD is normally a **symbolic reference**.

Instead of containing a commit hash:

```text
9ab3...
```

it contains:

```text
ref: refs/heads/main
```

Git follows that reference to find the current commit.

---

# Real Backend Example

Repository:

```text
expense-api/
```

Current branch:

```text
main
```

HEAD:

```text
HEAD

↓

main

↓

Commit A
```

Create:

```bash
git checkout -b feature/auth
```

Now:

```text
HEAD

↓

feature/auth

↓

Commit A
```

Commit:

```text
Commit B
```

Result:

```text
main ─────────► Commit A

feature/auth ─► Commit B
```

---

# Why Branches Are Cheap

Branch creation:

```bash
git branch feature/report
```

Git creates:

```text
One Reference File
```

That's it.

No repository copy.

This is why creating branches is almost instantaneous.

---

# Common Misconceptions

❌ HEAD is a commit.

Reality:

Usually, HEAD points to a branch, which points to a commit.

---

❌ Branches contain commits.

Reality:

Branches are pointers to commits.

---

❌ Commits move.

Reality:

Commits are immutable. Branch pointers move.

---

❌ Detached HEAD means Git is broken.

Reality:

It's simply a state where HEAD points directly to a commit instead of a branch.

---

# Best Practices

✅ Create a branch before making experimental commits from a detached HEAD state.

✅ Use branch names instead of raw commit hashes whenever practical.

✅ Don't manually edit files in `.git/refs`.

✅ Understand that branch movement is simply pointer movement.

# Interview Questions

### 1. What is `HEAD` in Git?

`HEAD` is a reference that identifies your current working position. It usually points to the currently checked-out branch.

---

### 2. What is a Git branch internally?

A branch is a lightweight reference (pointer) to a commit.

---

### 3. What happens to a branch after a new commit?

Git creates a new commit and moves the current branch pointer to that new commit.

---

### 4. What is a detached `HEAD`?

A detached `HEAD` occurs when `HEAD` points directly to a commit instead of a branch, often after checking out a specific commit.

---

### 5. Why are Git branches considered lightweight?

Because creating a branch typically only creates a new reference pointing to an existing commit. It does not copy the repository.

## 💡 Backend Engineer Tip

Understanding **HEAD** and **references** is essential before learning advanced Git commands like `reset`, `rebase`, `reflog`, and `cherry-pick`. Most "mysterious" Git behavior becomes much easier to understand once you realize that Git is primarily moving lightweight pointers—not rewriting files or copying repositories.
