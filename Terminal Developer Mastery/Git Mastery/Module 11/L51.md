# What is GitHub Actions?

GitHub Actions is GitHub's built-in **automation platform**.

It automatically performs tasks whenever something happens in your repository.

For example:

- Someone pushes code
    
- Someone opens a Pull Request
    
- A release is created
    
- Every night at 2 AM
    
- Every Monday morning
    
- Every hour
    

Instead of doing repetitive work manually, GitHub Actions does it for you.

Think of it as:

> "If this event happens → automatically run these steps."

# CI and CD

You'll hear these terms constantly.

## CI (Continuous Integration)

Automatically verify new code.

Example:

```
Push code

↓

Run tests

↓

Build project

↓

Report success/failure
```

Purpose:

Catch bugs early.

---

## CD (Continuous Delivery / Deployment)

Automatically release software.

Example:

```
Push to main

↓

Build Docker image

↓

Deploy to production
```

# Basic Concepts

GitHub Actions has a few core components.

## Workflow

A workflow is the complete automation.

Example:

```
CI Pipeline
```

or

```
Deploy Backend
```

---

## Event (Trigger)

What starts the workflow?

Examples:

```
push

pull_request

release

schedule

workflow_dispatch
```

---

## Job

A workflow can contain multiple jobs.

Example:

```
Workflow

├── Test

├── Build

└── Deploy
```

Jobs can run:

- one after another
    
- or in parallel
    

---

## Step

Each job contains steps.

Example:

```
Job

↓

Checkout code

↓

Install Node

↓

Install packages

↓

Run tests

↓

Build
```

---

## Runner

A runner is the machine executing your workflow.

GitHub provides:

- Ubuntu
    
- Windows
    
- macOS
    

Example:

```
runs-on: ubuntu-latest
```

---

# Workflow File Location

GitHub looks for workflows here:

```
.github/
    workflows/
        ci.yml
```

Example:

```
project/

.github/

workflows/

ci.yml
```

This folder is special.

---

# Your First Workflow

Create:

```
.github/workflows/hello.yml
```

Contents:

```yaml
name: Hello Workflow

on:
  push:

jobs:
  hello:
    runs-on: ubuntu-latest

    steps:
      - name: Say Hello
        run: echo "Hello GitHub Actions!"
```

---

# Understanding It Line by Line

## Workflow name


---

## Trigger

```yaml

  push:
```

---

## Jobs

```yaml

```

---

## Job Name

```yaml

```

Internal identifier.

---

## Runner

```yaml

```

---

## Steps

```yaml

```

Sequence of commands.

---

# Workflow Execution

```bash

```

GitHub:

```

↓

↓

↓

↓
```

# A More Useful Example

```yaml
name: Show Repository Info

on:
  push:

jobs:
  info:
    runs-on: ubuntu-latest

    steps:
      - run: pwd
      - run: ls
      - run: whoami
      - run: date
```

This prints:

- current directory
    
- files
    
- current user
    
- system date

# Best Practices

- Keep workflows focused on one purpose.
    
- Use descriptive workflow names like `Backend CI` or `Deploy Production`.
    
- Test workflows on a feature branch before using them on `main`.
    
- Review workflow logs when something fails.
    
- Store secrets (API keys, tokens) in GitHub Secrets, not in workflow files.
    
- Prefer official actions (such as `actions/checkout`) when available.
    

---

# Common Mistakes

❌ Putting workflow files outside `.github/workflows/`

❌ Committing passwords or tokens in YAML

❌ Running unnecessary jobs on every push

❌ Ignoring failed workflow logs

❌ Creating one huge workflow instead of separating CI and deployment when appropriate
