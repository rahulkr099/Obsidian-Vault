# Module 11 — GitHub Features

# Lesson 52 — Protected Branches

> **Goal:** Learn how professional backend teams protect important branches (such as `main`) from accidental or unsafe changes using GitHub's branch protection rules.

---

# Why Protected Branches Exist

Imagine you're working on a production backend.

The `main` branch contains the code currently deployed to users.

A developer accidentally runs:

```bash
git push origin main
```

The code:

- hasn't been reviewed
    
- contains bugs
    
- breaks tests
    

Without branch protection:

```text
Push

↓

main updated

↓

Production deployment

↓

Users affected
```

A single mistake can cause downtime.

Protected branches help prevent this.

---

# What Is a Protected Branch?

A **protected branch** is a branch with rules that control who can push and how changes are made.

Instead of allowing anyone to push directly:

```text
Developer

↓

main
```

The workflow becomes:

```text
Developer

↓

Feature Branch

↓

Pull Request

↓

Code Review

↓

Tests Pass

↓

Merge into main
```

---

# Why Backend Teams Protect `main`

Professional teams want to ensure:

- Code is reviewed
    
- Tests pass
    
- CI succeeds
    
- History stays clean
    
- Accidental force pushes are blocked
    
- Important commits aren't deleted
    

---

# Common Protected Branches

Most repositories protect:

```text
main
```

Sometimes also:

```text
master
```

```text
develop
```

```text
release/*
```

```text
hotfix/*
```

Large companies may protect several long-lived branches.

---

# Typical Workflow

Instead of:

```bash
git add .
git commit -m "Add payment API"
git push origin main
```

Developers use:

```bash
git switch -c feature/payment-api

git add .
git commit -m "feat(payment): add payment API"

git push origin feature/payment-api
```

Then:

```text
Open Pull Request

↓

Review

↓

CI

↓

Merge
```

---

# What Can Branch Protection Enforce?

GitHub allows several rules.

---

## 1. Require Pull Requests

No direct pushes.

Instead:

```text
Feature Branch

↓

Pull Request

↓

Merge
```

This is the most common rule.

---

## 2. Require Code Reviews

Example:

```text
Pull Request

↓

2 approvals required

↓

Merge allowed
```

Benefits:

- Better code quality
    
- Knowledge sharing
    
- Fewer production bugs
    

---

## 3. Require Passing Status Checks

This connects directly with **GitHub Actions**.

Example:

```text
Push

↓

GitHub Actions

↓

Tests

↓

Lint

↓

Build

↓

Success

↓

Merge allowed
```

If tests fail:

```text
Merge blocked
```

---

## 4. Require Conversation Resolution

Suppose a reviewer comments:

> Please validate the email input.

Until that conversation is resolved:

```text
Merge

↓

Blocked
```

Every review comment should be addressed.

---

## 5. Require Up-to-Date Branches

Suppose:

```text
main

A

B

C
```

Your branch:

```text
A

B

Feature
```

Meanwhile someone merges:

```text
main

A

B

C

D
```

GitHub may require:

```text
Update branch

↓

Run tests again

↓

Merge
```

This ensures your code works with the latest changes.

---

## 6. Block Force Pushes

Normal push:

```bash
git push
```

Dangerous:

```bash
git push --force
```

Force pushing can rewrite history.

Protected branches usually reject it.

---

## 7. Prevent Branch Deletion

Without protection:

```bash
git push origin --delete main
```

could delete an important branch (if permissions allow).

Protection blocks this.

---

## 8. Restrict Who Can Push

Example:

```text
Intern

❌ Cannot push

Senior Developer

✅ Can push

CI Bot

✅ Can push
```

Useful in large organizations.

---

# How GitHub Branch Protection Works

```text
Developer Pushes

↓

Protected Branch Rules

↓

Checks Run

↓

Review Required

↓

Merge Allowed
```

If any rule fails:

```text
Merge blocked
```

# Setting Up Branch Protection

Repository owners or administrators can configure it.

Navigate to:

```text
Repository

↓

Settings

↓

Branches

↓

Branch Protection Rules
```

Create a rule for:

```text
main
```

Common settings include:

- Require a pull request before merging
    
- Require approvals
    
- Require status checks to pass
    
- Require conversation resolution
    
- Block force pushes
    
- Prevent deletion
    

---

# Recommended Rules for Small Teams

For a startup with 2–10 developers:

|Rule|Recommendation|
|---|---|
|Pull Requests|✅ Required|
|One Approval|✅ Yes|
|GitHub Actions|✅ Required|
|Force Push|❌ Block|
|Delete Branch|❌ Prevent|
|Conversation Resolution|✅ Enable|

---

# Recommended Rules for Large Teams

For larger engineering teams:

|Rule|Recommendation|
|---|---|
|Pull Requests|✅ Required|
|Two or More Approvals|✅ Yes|
|Passing CI Checks|✅ Required|
|Signed Commits (optional)|✅ Consider|
|Force Push|❌ Never|
|Branch Deletion|❌ Never|
|CODEOWNERS Reviews|✅ Enable|

All Green

---

# Benefits

Protected branches help you:

- Prevent accidental mistakes
    
- Improve code quality
    
- Catch bugs before merging
    
- Enforce team workflows
    
- Keep repository history clean
    
- Increase confidence in production releases
    

---

# Common Mistakes

❌ Allowing direct pushes to `main`

❌ Merging without reviews

❌ Ignoring failed CI checks

❌ Using `--force` on shared branches

❌ Giving everyone admin access

---

# Real Backend Example

Imagine you're working on an authentication API.

Developer A adds JWT authentication.

Developer B changes database models.

Without protection:

```text
Both push directly

↓

Conflict

↓

Broken application
```

With protection:

```text
Feature Branches

↓

Pull Requests

↓

CI

↓

Reviews

↓

Safe Merge
```

---

# Best Practices

- Protect `main` from day one.
    
- Use feature branches for all new work.
    
- Require at least one review, even in small teams.
    
- Make GitHub Actions checks mandatory before merging.
    
- Delete merged feature branches to keep the repository clean.
    
- Reserve admin permissions for a small number of trusted maintainers.
