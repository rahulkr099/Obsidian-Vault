# Lesson 53 — CODEOWNERS

> **Goal:** Learn how professional teams automatically assign the right reviewers to Pull Requests using the `CODEOWNERS` file.

# Why CODEOWNERS Exists

Imagine you're working in a backend team with 15 developers.

Your project looks like this:

```text
project/

├── backend/
├── frontend/
├── database/
├── docs/
├── infrastructure/
└── scripts/
```

Different developers specialize in different areas.

For example:

|Developer|Expertise|
|---|---|
|Alice|Backend|
|Bob|Frontend|
|Charlie|Database|
|David|DevOps|
|Emma|Documentation|

Now imagine someone changes:

```text
database/schema.sql
```

Who should review it?

Certainly not someone who only works on the frontend.

This is exactly what **CODEOWNERS** solves.

---

# What is CODEOWNERS?

A **CODEOWNERS** file tells GitHub:

> "When files in these locations change, automatically request reviews from these people or teams."

Instead of manually finding reviewers:

```text
Developer

↓

Open PR

↓

Wonder who should review...
```

GitHub automatically does it:

```text
Open PR

↓

GitHub reads CODEOWNERS

↓

Requests reviewers automatically
```

---

# Why Backend Teams Use CODEOWNERS

Large repositories contain many components:

```text
Backend

Frontend

Database

Infrastructure

Documentation

CI/CD

Docker

Tests
```

Each area has experts.

CODEOWNERS ensures:

- Correct reviewer
    
- Faster reviews
    
- Better quality
    
- Shared responsibility
    

---

# Where is CODEOWNERS Stored?

GitHub checks these locations (in order):

```text
.github/CODEOWNERS
```

or

```text
CODEOWNERS
```

or

```text
docs/CODEOWNERS
```

The most common location is:

```text
.github/CODEOWNERS
```

Example:

```text
project/

.github/
    CODEOWNERS
```

---

# Basic Syntax

A CODEOWNERS file contains:

```text
File Pattern    Owner
```

Example:

```text
*.md    @docs-team
```

Meaning:

> Every Markdown file is owned by `@docs-team`.

---

# Assign an Owner to Everything

```text
*   @backend-team
```

The `*` means:

All files.

---

# Specific Folder Ownership

Example:

```text
backend/   @backend-team
```

Whenever someone changes:

```text
backend/auth.js
```

GitHub requests:

```text
@backend-team
```

---

# Multiple Owners

You can assign more than one owner.

```text
backend/   @alice @bob
```

When backend files change:

```text
Review Request

↓

Alice

Bob
```

---

# Different Owners for Different Areas

Example:

```text
frontend/      @frontend-team
backend/       @backend-team
database/      @db-team
docs/          @docs-team
docker/        @devops-team
```

Now GitHub knows who should review each part of the project.

---

# File-Specific Ownership

Instead of an entire folder:

```text
Dockerfile    @devops-team
```

Only changes to:

```text
Dockerfile
```

trigger those reviewers.

---

# File Extension Patterns

Example:

```text
*.sql    @database-team
```

Every SQL file belongs to the database team.

Similarly:

```text
*.md     @docs-team
```

All documentation files are assigned to documentation maintainers.

---

# Order Matters

GitHub uses the **last matching rule**.

Example:

```text
*           @team

backend/    @backend-team
```

For:

```text
backend/auth.js
```

GitHub chooses:

```text
@backend-team
```

because it is the more specific rule that appears later.

# What Happens During a Pull Request?

Developer changes:

```text
backend/auth.js

database/users.sql
```

GitHub reads:

```text
backend/

database/
```

Automatically requests:

```text
@backend-team

@database-team
```

The developer doesn't need to remember who to tag.

---

# CODEOWNERS + Protected Branches

CODEOWNERS becomes even more powerful with branch protection.

Workflow:

```text
Feature Branch

↓

Pull Request

↓

GitHub Requests Code Owners

↓

Owners Review

↓

GitHub Actions Pass

↓

Merge Allowed
```

If required code owner reviews are enabled, the PR cannot be merged until an appropriate owner approves it.

---

# CODEOWNERS + GitHub Actions

A professional backend workflow often looks like:

```text
Developer Pushes

↓

Pull Request

↓

CODEOWNERS Review Request

↓

GitHub Actions

├── Tests

├── Build

├── Lint

└── Security Scan

↓

Approvals

↓

Merge
```

Automation handles both quality checks and reviewer assignment.

---

# Teams vs Individuals

Instead of assigning:

```text
@alice
```

Large organizations usually assign:

```text
@company/backend-team
```

Benefits:

- People can join or leave the team without changing the CODEOWNERS file.
    
- Responsibilities stay organized.
    
- Easier maintenance.

# Best Practices

- Store the file in `.github/CODEOWNERS`.
    
- Use teams instead of individual usernames whenever possible.
    
- Match repository structure with ownership.
    
- Keep ownership rules simple and easy to understand.
    
- Update CODEOWNERS whenever folders are renamed or responsibilities change.
    
- Combine CODEOWNERS with protected branches and required reviews for maximum benefit.
    

---

# Common Mistakes

❌ Forgetting to update CODEOWNERS after moving files

❌ Assigning reviewers who no longer work on the project

❌ Making one person the owner of everything

❌ Creating overly complicated matching rules

❌ Assuming CODEOWNERS replaces code reviews—it only helps assign reviewers

---

# CODEOWNERS vs Manual Review Requests

|Manual Review|CODEOWNERS|
|---|---|
|Developer chooses reviewers|GitHub assigns automatically|
|Easy to forget someone|Consistent every time|
|Slower for large teams|Scales well|
|Depends on memory|Based on repository rules|
