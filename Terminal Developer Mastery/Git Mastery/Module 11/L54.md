# Lesson 54 — Templates (Issue & Pull Request)

> **Goal:** Learn how professional repositories use **Issue Templates** and **Pull Request Templates** to make bug reports, feature requests, and code reviews consistent and efficient.

# Why Templates Matter

Imagine you're maintaining a popular backend project.

Every day, people open issues like:

**Issue #1**

```text
Login not working.
```

That's it.

No operating system.

No browser.

No logs.

No steps to reproduce.

You have to spend time asking for more details before you can even investigate.

Now compare that with:

```text
Bug Summary:
Login API returns HTTP 500.

Steps to Reproduce:
1. Login with valid credentials.
2. Submit the form.
3. Receive HTTP 500.

Expected Result:
User should receive a JWT token.

Actual Result:
Internal Server Error.

Environment:
Ubuntu 24.04
Node.js 22
Chrome 140
```

The second report is much easier to understand and fix.

That's the purpose of templates.

---

# What Are GitHub Templates?

Templates are pre-written forms that GitHub automatically fills in when someone creates:

- An Issue
    
- A Pull Request
    

Instead of writing from scratch:

```text
User

↓

Blank page
```

GitHub provides:

```text
User

↓

Structured form

↓

Submit
```

---

# Types of Templates

Professional repositories commonly use:

|Template|Purpose|
|---|---|
|Bug Report|Report a problem|
|Feature Request|Suggest a new feature|
|Documentation|Report documentation issues|
|Pull Request|Describe code changes|
|Security Report|Report vulnerabilities (usually handled privately)|

# Issue Templates

Issue templates help contributors provide the right information.

Example:

```text
Issue Title

Bug Description

Steps to Reproduce

Expected Behavior

Actual Behavior

Environment

Screenshots

Additional Notes
```

This saves time for both contributors and maintainers.

---

# Where Issue Templates Are Stored

Templates are usually stored here:

```text
.github/

issue_template/
```

Example:

```text
project/

.github/

issue_template/

bug_report.md

feature_request.md
```

GitHub automatically detects them.

# Pull Request Templates

Every Pull Request should answer the same basic questions.

Without a template:

```text
PR Title

"Update API"
```

No explanation.

No context.

Reviewers are left guessing.

With a template:

```text
Summary

Changes Made

Testing

Checklist
```

The review becomes much smoother.

---

# Where PR Templates Are Stored

The most common location is:

```text
.github/

pull_request_template.md
```

Example:

```text
project/

.github/

pull_request_template.md
```

---

# Example Pull Request Template

```markdown
# Summary

Describe your changes.

# Related Issue

Fixes #

# Testing

How did you test this?

# Checklist

- [ ] Tests pass
- [ ] Documentation updated
- [ ] No sensitive information committed
- [ ] Ready for review
```

Every new Pull Request starts with this content.

---

# Typical Backend Pull Request

```text
Testing

Tested using Postman and automated unit tests.

Checklist

✔ Tests pass

✔ Documentation updated

✔ No breaking changes
```

Now reviewers immediately understand the change.

# Issue Forms

GitHub also supports **Issue Forms**, which use YAML to create structured forms.

Example fields:

```text
Name

Email

Operating System

Node Version

Description

Logs
```

Advantages:

- Required fields
    
- Dropdowns
    
- Checkboxes
    
- Better consistency
    

For many modern repositories, Issue Forms are preferred over simple Markdown templates.

# Best Practices

### Keep Templates Short

People are more likely to complete concise templates.

Good:

```text
Summary

Testing

Checklist
```

Not:

```text
40 required questions
```

---

### Ask for Useful Information

Good examples:

- Steps to reproduce
    
- Expected behavior
    
- Actual behavior
    
- Environment
    
- Testing performed
    

Avoid unnecessary questions that don't help resolve the issue.

---

### Use Checklists

Example:

```markdown
- [ ] Tests pass
- [ ] Documentation updated
- [ ] No secrets committed
- [ ] Ready for review
```

Checklists help prevent common mistakes.

---

### Link Related Issues

Encourage contributors to reference issues.

Example:

```text
Fixes #123
```

When merged, GitHub can automatically close the linked issue.

---

# Common Mistakes

❌ Creating templates that are too long

❌ Asking irrelevant questions

❌ Forgetting to update templates as the project evolves

❌ Not including testing information in PR templates

❌ Expecting templates to replace code reviews—they only improve communication
