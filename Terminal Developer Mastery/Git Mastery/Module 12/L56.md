# Module 12 — Open Source

# Lesson 56 — Finding Open Source Projects

> **Goal:** Learn how to find high-quality open-source projects, evaluate whether they are healthy and welcoming, and choose projects that match your current skills and interests.

---

# Why Contribute to Open Source?

Open source is more than writing code.

It helps you:

- Improve your coding skills
    
- Learn from experienced developers
    
- Build a public portfolio
    
- Understand professional Git workflows
    
- Receive code reviews from real engineers
    
- Network with developers worldwide
    

For backend engineers, open-source contributions are excellent evidence of practical experience.

---

# What Makes a Good Project?

Not every repository is worth contributing to.

A healthy project usually has:

- Active maintainers
    
- Recent commits
    
- Open and closed issues
    
- Clear documentation
    
- A `README.md`
    
- A `CONTRIBUTING.md`
    
- A license
    
- Responsive code reviews
    

Example:

```text
Repository

├── README.md
├── CONTRIBUTING.md
├── LICENSE
├── package.json
├── src/
└── tests/
```

These are good signs that the project is maintained.

---

# Characteristics of a Healthy Repository

Ask yourself these questions:

|Question|Good Sign|
|---|---|
|Recent commits?|✅ Yes|
|Active Pull Requests?|✅ Yes|
|Issues being answered?|✅ Yes|
|Documentation available?|✅ Yes|
|Releases published?|✅ Yes|
|Automated tests?|✅ Yes|

If the answer is "No" to most of these, the project may be inactive.

# Choosing the Right Project

A common mistake is choosing a huge project immediately.

For example:

```text
Linux Kernel
```

or

```text
Kubernetes
```

These are incredible projects—but not ideal for a first contribution.

Instead, choose projects where you can understand the codebase within a few days.

# Read the README

Before writing any code, read:

```text
README.md
```

It usually explains:

- What the project does
    
- Installation steps
    
- Development setup
    
- Technologies used
    
- How to contribute
    

Never skip this step.

---

# Check CONTRIBUTING.md

A good repository usually contains:

```text
CONTRIBUTING.md
```

It explains:

- Coding standards
    
- Branch naming
    
- Commit message format
    
- Testing requirements
    
- Pull Request process
    

We'll study this file in the next lesson.

# Start Small

Your first contributions don't have to involve complex code.

Examples:

- Fix spelling mistakes
    
- Improve documentation
    
- Correct examples
    
- Add comments
    
- Improve error messages
    
- Add tests
    
- Fix small bugs
    

Small contributions still count.

---

# Learn from Existing Pull Requests

Open recent Pull Requests and observe:

- Commit messages
    
- Code style
    
- Review comments
    
- Requested changes
    
- Merge process
    

This is one of the best ways to learn professional development practices.


This is the standard workflow for open-source contributions.

# Red Flags

Be cautious if a repository has:

- No README
    
- No license
    
- No recent activity
    
- Hundreds of unanswered issues
    
- Broken installation instructions
    
- Failing CI for a long time
    
- Abandoned Pull Requests
    

These signs often indicate an unhealthy project.

---

# Best Practices

- Choose projects related to your learning goals.
    
- Read documentation before coding.
    
- Start with small issues.
    
- Follow the project's coding style.
    
- Test your changes before submitting.
    
- Be respectful when communicating with maintainers.
    

---

# Common Mistakes

❌ Choosing a project that is too large

❌ Skipping the README

❌ Ignoring CONTRIBUTING guidelines

❌ Starting multiple issues at once

❌ Making unrelated changes in one Pull Request

❌ Expecting your first PR to be merged immediately
