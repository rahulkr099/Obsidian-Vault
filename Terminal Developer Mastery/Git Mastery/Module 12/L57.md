# Module 12 — Open Source

# Lesson 57 — Reading `CONTRIBUTING.md`

> **Goal:** Learn how to read and follow a project's `CONTRIBUTING.md` file so you can contribute like a professional and significantly increase the chances of your Pull Requests being accepted.

---

# What is `CONTRIBUTING.md`?

`CONTRIBUTING.md` is a document that explains:

> **"This is how we expect people to contribute to this project."**

Think of it as the project's **rulebook**.

Without it:

```text
New Contributor

↓

Does things their own way

↓

Maintainer requests many changes

↓

PR delayed or rejected
```

With it:

```text
New Contributor

↓

Reads CONTRIBUTING.md

↓

Follows project rules

↓

PR matches expectations

↓

Faster review
```

---

# Why Every Contributor Should Read It

Many beginners make this mistake:

```text
Fork Repository

↓

Write Code

↓

Open PR
```

They never read the contribution guidelines.

This often leads to:

- Wrong branch
    
- Wrong commit messages
    
- Missing tests
    
- Incorrect formatting
    
- PR rejected
    

Professional developers **always read `CONTRIBUTING.md` first**.

---

# Where is It Located?

Most repositories place it in the root directory.

Example:

```text
project/

README.md

CONTRIBUTING.md

LICENSE

package.json

src/
```

Sometimes it's inside:

```text
.github/
```

---

# What Does It Usually Contain?

Most `CONTRIBUTING.md` files include:

- Project setup
    
- Development environment
    
- Branch strategy
    
- Coding style
    
- Testing instructions
    
- Commit message format
    
- Pull Request process
    
- Code review expectations
    

---

# 1. Development Setup

Example:

```text
Clone repository

↓

Install dependencies

↓

Configure environment

↓

Run application
```

For a Node.js project, you might see:

```bash
git clone https://github.com/example/project.git

cd project

npm install

npm run dev
```

Some projects may require:

- Docker
    
- PostgreSQL
    
- Redis
    
- MongoDB
    
- Environment variables
    

Follow the instructions exactly.

---

# 2. Branch Workflow

Many projects specify:

```text
main

↓

feature/login

feature/auth

bugfix/cache
```

Instead of working directly on:

```text
main
```

Always create a new branch if the guidelines require it.

Example:

```bash
git switch -c feature/improve-validation
```

---

# 3. Commit Message Rules

Some projects require:

```text
feat(auth): add JWT middleware
```

instead of:

```text
Updated auth
```

Many repositories use **Conventional Commits**, which you've already learned.

---

# 4. Coding Style

Projects often define coding standards.

Examples:

- ESLint
    
- Prettier
    
- Black (Python)
    
- gofmt (Go)
    
- rustfmt (Rust)
    

Example instruction:

```text
Run:

npm run lint

before submitting.
```

Ignoring formatting rules often causes CI failures.

---

# 5. Testing Requirements

Professional repositories expect contributors to test their changes.

Typical workflow:

```text
Write Code

↓

Run Tests

↓

Fix Failures

↓

Open PR
```

Node.js example:

```bash
npm test
```

Sometimes you'll also run:

```bash
npm run test:coverage
```

---

# 6. Pull Request Process

Many projects require:

```text
Fork

↓

Create Branch

↓

Commit

↓

Push

↓

Open PR

↓

Wait for Review
```

Some projects also require:

- Linking an issue
    
- Completing a PR template
    
- Updating documentation
    

---

# 7. Code Review Expectations

Maintainers may request changes.

Example:

```text
Reviewer:

Please rename this variable.
```

Good response:

```text
Update code

↓

Push new commit

↓

Reply politely
```

Avoid arguing unless you have a strong technical reason.

---

# 8. Communication Guidelines

Many projects include a Code of Conduct.

Expected behavior:

- Be respectful
    
- Be patient
    
- Assume good intentions
    
- Welcome new contributors
    

Professional communication is as important as good code.

# What Happens If You Ignore It?

Example:

```text
Project requires:

npm run lint
```

You don't run it.

GitHub Actions:

```text
Lint

↓

Failed
```

Your PR cannot be merged until you fix the issue.

# Before Opening a Pull Request

Use this checklist:

```text
□ Read README

□ Read CONTRIBUTING.md

□ Created feature branch

□ Followed coding style

□ Ran formatter

□ Ran tests

□ Updated documentation (if needed)

□ Used proper commit messages

□ Filled PR template

□ Linked related issue
```

# Best Practices

- Read `CONTRIBUTING.md` before writing code.
    
- Follow the project's branch naming rules.
    
- Use the required commit message format.
    
- Run all tests locally before pushing.
    
- Keep Pull Requests focused on one change.
    
- Ask questions politely if something is unclear.
    

---

# Common Mistakes

❌ Skipping the contribution guide

❌ Working directly on `main`

❌ Mixing multiple features in one PR

❌ Ignoring failed CI checks

❌ Not updating documentation when required

❌ Becoming defensive during code review

---

# CONTRIBUTING.md vs README.md

|README.md|CONTRIBUTING.md|
|---|---|
|Explains the project|Explains how to contribute|
|Installation|Development workflow|
|Features|Contribution rules|
|Usage|PR and review process|
|User-focused|Contributor-focused|

Both are important, but they serve different audiences.

# How This Fits Your Backend Journey

By now, you've learned:

- Git branching
    
- Pull Requests
    
- GitHub Actions
    
- Protected branches
    
- CODEOWNERS
    
- PR templates
    

`CONTRIBUTING.md` ties all of these together by explaining **how a specific project expects contributors to use them**.

Whether you're contributing to:

- an Express API,
    
- a Docker-based project,
    
- a CLI tool,
    
- or a Linux utility,
    

the first thing you should do is read the contribution guide.
