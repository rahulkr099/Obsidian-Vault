# Module 12 — Open Source

# Lesson 58 — Making Your First Contribution

> **Goal:** Learn the complete professional workflow for making your first open-source contribution—from selecting an issue to getting your Pull Request merged.

---

# The Big Picture

Contributing to open source isn't just writing code.

It's following a collaborative workflow.

Here's the complete process:

```text
Find Project

↓

Find Issue

↓

Read Documentation

↓

Fork Repository

↓

Clone Your Fork

↓

Create Branch

↓

Write Code

↓

Run Tests

↓

Commit Changes

↓

Push Branch

↓

Open Pull Request

↓

Address Review Feedback

↓

Merge 🎉
```

This is the same workflow used by professional backend engineers every day.

---

# Step 1 — Choose an Issue

Start with a small task.

Good examples:

- Improve an error message
    
- Fix a typo
    
- Add a missing test
    
- Update documentation
    
- Fix a small bug
    

Avoid issues like:

```text
Rewrite authentication system
```

or

```text
Refactor the whole API
```

For your first contribution, smaller is better.

---

# Step 2 — Read the Issue Carefully

Don't immediately start coding.

Understand:

- What is the problem?
    
- What is the expected behavior?
    
- Has someone already started working on it?
    
- Are there maintainer comments?
    

Example:

```text
Issue:
Validation error message is unclear.

Expected:
"Email is required"

Current:
"Validation failed"
```

Now you know exactly what to fix.

---

# Step 3 — Read the Documentation

Before writing code, read:

```text
README.md
```

Then:

```text
CONTRIBUTING.md
```

These files explain:

- Project setup
    
- Coding standards
    
- Testing
    
- Branch naming
    
- Pull Request process
    

---

# Step 4 — Fork the Repository

If you don't have write access:

```text
Original Repository

↓

Fork

↓

Your GitHub Account
```

Now you own a copy.

---

# Step 5 — Clone Your Fork

Clone your fork to your local machine.

```bash
git clone https://github.com/your-username/project.git

cd project
```

---

# Step 6 — Add the Original Repository

Your fork should know about the original project.

Check remotes:

```bash
git remote -v
```

Example:

```text
origin
https://github.com/your-username/project.git
```

Add the original repository:

```bash
git remote add upstream https://github.com/original/project.git
```

Now verify:

```bash
git remote -v
```

Output:

```text
origin

https://github.com/your-username/project.git

upstream

https://github.com/original/project.git
```

### Why `upstream`?

Later, you can sync your fork with the latest changes.

---

# Step 7 — Update Your Fork

Before creating a branch:

```bash
git fetch upstream

git switch main

git merge upstream/main
```

Your fork is now up to date.

---

# Step 8 — Create a Feature Branch

Never work directly on `main`.

Example:

```bash
git switch -c fix/email-validation
```

Good branch names:

```text
feature/add-cache

bugfix/login-error

docs/readme-update

test/auth-api
```

---

# Step 9 — Make Your Changes

Example:

Before:

```javascript
return "Validation failed";
```

After:

```javascript
return "Email is required";
```

Keep the change focused.

Don't fix unrelated problems in the same Pull Request.

---

# Step 10 — Run Tests

Professional developers always verify their work.

Example:

```bash
npm install

npm test
```

Also run:

```bash
npm run lint
```

If the project uses formatting:

```bash
npm run format
```

Fix every failing test before pushing.

---

# Step 11 — Review Your Changes

Check what changed:

```bash
git status
```

See the differences:

```bash
git diff
```

Read your own code one more time.

Ask yourself:

- Does this solve the issue?
    
- Did I accidentally change anything else?
    

---

# Step 12 — Commit Your Work

Stage files:

```bash
git add .
```

Create a professional commit:

```bash
git commit -m "fix(validation): improve email error message"
```

Avoid messages like:

```text
Updated

Fixed stuff

Changes
```

---

# Step 13 — Push Your Branch

```bash
git push origin fix/email-validation
```

GitHub now has your changes.

---

# Step 14 — Open a Pull Request

GitHub will usually show:

```text
Compare & Pull Request
```

Click it.

Fill in the PR template.

Example:

```text
Summary

Improved email validation error message.

Related Issue

Fixes #42

Testing

✔ npm test

✔ npm run lint
```

---

# Step 15 — GitHub Actions Runs

Your Pull Request automatically triggers CI.

Example:

```text
GitHub Actions

↓

Install Dependencies

↓

Run Tests

↓

Run Linter

↓

Build

↓

Success ✅
```

If something fails:

```text
Fix

↓

Commit

↓

Push

↓

CI Runs Again
```

---

# Step 16 — Code Review

A maintainer reviews your Pull Request.

Possible feedback:

```text
Please rename this variable.
```

or

```text
Could you add a test?
```

This is normal.

Almost every Pull Request receives review comments.

---

# Step 17 — Update Your Pull Request

Make the requested changes.

Then:

```bash
git add .

git commit -m "refactor: rename validation variable"

git push
```

The Pull Request updates automatically.

No need to create a new PR.

---

# Step 18 — Pull Request Gets Merged

After approval:

```text
Review Approved

↓

Merge

↓

Issue Closed

↓

Contribution Complete 🎉
```

Congratulations!

You are now an open-source contributor.

# Best Practices

- Work on one issue per Pull Request.
    
- Keep changes small and focused.
    
- Test before pushing.
    
- Write clear commit messages.
    
- Respond politely to review comments.
    
- Keep your branch updated with the latest `main` if needed.
    
- Thank maintainers for their feedback and time.
    

---

# Common Mistakes

❌ Working directly on `main`

❌ Forgetting to add the `upstream` remote

❌ Skipping tests

❌ Mixing unrelated fixes in one PR

❌ Ignoring CI failures

❌ Becoming discouraged if reviewers request changes

Remember: review comments are meant to improve the code, not criticize you.
