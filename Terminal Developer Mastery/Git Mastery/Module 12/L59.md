# Module 12 — Open Source

# Lesson 59 — Handling Review Feedback

> **Goal:** Learn how professional developers respond to code review feedback, update Pull Requests, communicate respectfully with maintainers, and improve code through collaboration.

---

# Why Code Reviews Matter

Many beginners think:

> "If someone requested changes, my code must be bad."

This is **not** how professional software teams work.

In fact, even senior engineers receive review feedback every day.

A Pull Request usually looks like this:

```text
Developer

↓

Open Pull Request

↓

Reviewer Reads Code

↓

Suggestions

↓

Developer Updates PR

↓

Approved

↓

Merged
```

Receiving feedback is a normal part of software development.

---

# What Happens During a Code Review?

A reviewer may check:

- Code correctness
    
- Readability
    
- Performance
    
- Security
    
- Testing
    
- Documentation
    
- Naming
    
- Architecture
    

Example comment:

```text
Could you rename this variable?
```

or

```text
Please handle the null case here.
```

or

```text
This query could be optimized.
```

None of these mean your contribution is rejected—they are opportunities to improve it.

---

# Types of Review Feedback

## 1. Style Feedback

Example:

```javascript
let x = user.name;
```

Reviewer:

```text
Please rename x to userName.
```

Improved version:

```javascript
let userName = user.name;
```

This improves readability.

---

## 2. Logic Feedback

Example:

```javascript
if (age > 18)
```

Reviewer:

```text
Should 18-year-olds also be allowed?
```

Corrected version:

```javascript
if (age >= 18)
```

---

## 3. Performance Feedback

Example:

```javascript
users.forEach(...)
```

Reviewer:

```text
Consider using a Map for faster lookups.
```

---

## 4. Security Feedback

Example:

```javascript
console.log(jwtSecret);
```

Reviewer:

```text
Never log secrets.
```

Security reviews are especially important for backend projects.

---

## 5. Testing Feedback

Reviewer:

```text
Could you add a unit test for this function?
```

Professional teams often require tests before merging.

---

## 6. Documentation Feedback

Reviewer:

```text
Please update the README.
```

If behavior changes, documentation should reflect it.

---

# Reading Feedback Carefully

Don't rush.

Read every comment carefully.

Bad approach:

```text
Reviewer comments

↓

Developer replies immediately

↓

Misunderstands request
```

Better approach:

```text
Reviewer comments

↓

Read everything

↓

Understand

↓

Implement

↓

Reply
```

---

# Responding Professionally

Good response:

```text
Thanks! I've updated the variable name.
```

Another example:

```text
Good catch. I've added the missing null check.
```

Or:

```text
I've added the requested unit test.
```

Short, polite, and clear.

---

# When You Disagree

Sometimes you may have a different technical opinion.

Bad response:

```text
You're wrong.
```

Professional response:

```text
I chose this approach because it avoids an additional database query.
What do you think about this alternative?
```

Explain your reasoning respectfully and be open to discussion.

---

# Updating Your Pull Request

Suppose a reviewer asks:

```text
Rename variable

↓

Add tests

↓

Update documentation
```

Make the changes locally.

Then:

```bash
git add .

git commit -m "refactor: address review comments"

git push
```

The existing Pull Request updates automatically.

No new PR is needed.

---

# Resolving Review Conversations

After making changes:

```text
Reviewer Comment

↓

Developer Updates Code

↓

Reply

↓

Conversation Resolved
```

Don't mark a conversation as resolved unless the requested change has actually been addressed.

---

# Example Review

Original code:

```javascript
const d = new Date();
```

Reviewer:

```text
Can you use a more descriptive variable name?
```

Updated code:

```javascript
const currentDate = new Date();
```

Reply:

```text
Done! Renamed it to currentDate.
```

---

# Example Backend Review

Suppose you're working on an authentication API.

Reviewer comments:

```text
JWT expiration should be configurable.
```

Instead of:

```javascript
expiresIn: "1h"
```

You update it:

```javascript
expiresIn: process.env.JWT_EXPIRES_IN
```

Commit:

```bash
git commit -m "refactor(auth): use configurable JWT expiration"
```

Push the changes and reply:

```text
Updated to use an environment variable. Thanks for pointing that out!
```

# GitHub Review Statuses

A reviewer can choose:

### Approve

```text
Looks good.

Approved.
```

---

### Comment

```text
Suggestion:

Could you simplify this function?
```

These comments may not block merging.

---

### Request Changes

```text
Please fix these issues before merging.
```

This means more work is needed before approval.

---

# Review Workflow

```text
Open PR

↓

GitHub Actions

↓

Reviewer

↓

Comments

↓

Developer Updates Code

↓

Push

↓

Reviewer Re-checks

↓

Approve

↓

Merge
```

---

# Large Pull Requests

Huge Pull Requests are difficult to review.

Bad example:

```text
Changed:

120 files

4,000 lines
```

Better example:

```text
Changed:

5 files

120 lines
```

Smaller Pull Requests are reviewed faster and with fewer mistakes.

---

# Responding to Multiple Comments

Suppose you receive:

```text
Rename variable

↓

Add test

↓

Fix formatting

↓

Update docs
```

Instead of making four separate commits, you can often address all related review comments together, then push once and reply to each comment explaining what changed.

---

# What If CI Fails?

Sometimes the reviewer approves your code, but GitHub Actions reports:

```text
Tests Failed
```

Workflow:

```text
Fix Tests

↓

Commit

↓

Push

↓

CI Runs Again

↓

Green

↓

Merge
```

Passing reviews alone is not enough if required checks are failing.

---

```text

↓

GitHub Actions

↓

Backend Reviewer

↓

DevOps Reviewer

↓

Comments

↓

Developer Updates PR

↓

CI Passes

↓

```

Multiple reviewers are common in production systems.

---

# Best Practices

- Read all review comments before making changes.
    
- Respond politely and professionally.
    
- Explain your reasoning when appropriate.
    
- Keep discussions focused on the code.
    
- Test every change before pushing.
    
- Thank reviewers for their feedback.
    

---

# Common Mistakes

❌ Taking review comments personally

❌ Ignoring reviewer suggestions

❌ Arguing without technical reasoning

❌ Marking conversations as resolved before fixing the issue

❌ Force-pushing shared history without understanding the impact

❌ Opening a new Pull Request instead of updating the existing one

---

# Review Feedback is Learning

Every review helps you improve.

Over time you'll learn:

- Better architecture
    
- Cleaner code
    
- Better naming
    
- Security practices
    
- Testing strategies
    
- Team conventions
    

Many experienced developers say that code reviews are one of the fastest ways to grow.
