# Module 13 — Git Recovery

# Lesson 65 — Recover After `git reset`

> **Goal:** Understand how `git reset` works, the differences between `--soft`, `--mixed`, and `--hard`, and how to recover from accidental resets using `git reflog`.

---

# Why This Matters

`git reset` is one of Git's most powerful—and most misunderstood—commands.

It can:

- Move branch pointers
    
- Uncommit changes
    
- Unstage files
    
- Discard changes
    
- Make commits appear "lost"
    

Used correctly, it's extremely useful.

Used carelessly, it can be scary.

The good news is that **most accidental resets can be recovered**.

---

# What Does `git reset` Do?

A Git repository has three important areas:

```text
Working Directory

↓

Staging Area (Index)

↓

Repository (Commits)
```

Different reset modes affect different areas.

---

# Example History

Suppose:

```text
A──B──C──D  main
```

Where:

- `D` is the latest commit.
    

You run:

```bash
git reset <target>
```

Git moves the branch pointer.

How much else changes depends on the reset mode.

---

# `git reset --soft`

This is the safest reset.

Command:

```bash
git reset --soft HEAD~1
```

Before:

```text
A──B──C──D
```

After:

```text
A──B──C
```

But:

```text
Changes from D

↓

Still Staged
```

Visual:

```text
Repository

Moved Back

↓

Staging Area

Still Contains Changes

↓

Working Directory

Unchanged
```

---

# When to Use `--soft`

Suppose your commit message is bad.

```text
Fix
```

Reset softly:

```bash
git reset --soft HEAD~1
```

Then recommit:

```bash
git commit -m "fix(auth): validate refresh token"
```

No work is lost.

---

# `git reset --mixed`

This is the **default** mode.

Command:

```bash
git reset HEAD~1
```

or

```bash
git reset --mixed HEAD~1
```

Before:

```text
A──B──C──D
```

After:

```text
A──B──C
```

Changes from `D` remain in your **working directory**, but they are **no longer staged**.

Visual:

```text
Repository

Moved Back

↓

Staging Area

Cleared

↓

Working Directory

Changes Preserved
```

---

# Example

Suppose:

```bash
git add .

git commit -m "Temporary change"
```

Oops.

Use:

```bash
git reset HEAD~1
```

Now:

```bash
git status
```

Output:

```text
Modified files

not staged
```

You can edit them before committing again.

---

# `git reset --hard`

This is the most dangerous mode.

Command:

```bash
git reset --hard HEAD~1
```

Before:

```text
A──B──C──D
```

After:

```text
A──B──C
```

Git also:

- Removes staged changes
    
- Removes working directory changes
    

Visual:

```text
Repository

Moved Back

↓

Staging Area

Deleted

↓

Working Directory

Deleted
```

Uncommitted work can be permanently lost.

---

# Comparison Table

|Mode|Branch Pointer|Staging Area|Working Directory|
|---|---|---|---|
|`--soft`|Moves|Keeps changes staged|Keeps changes|
|`--mixed`|Moves|Unstages changes|Keeps changes|
|`--hard`|Moves|Clears staging|Discards changes|

---

# Recover After `--hard`

Suppose:

```text
A──B──C──D
```

You accidentally run:

```bash
git reset --hard HEAD~1
```

Now:

```text
A──B──C
```

Don't panic.

Run:

```bash
git reflog
```

Example:

```text
HEAD@{0}: reset: moving to HEAD~1

HEAD@{1}: commit: Add JWT middleware
```

Commit:

```text
abc123
```

still exists.

---

# Recover the Lost Commit

Create a recovery branch:

```bash
git switch -c recovery abc123
```

Or move your branch back:

```bash
git reset --hard abc123
```

The commit is restored.

---

# Recover After `--mixed`

Suppose:

```bash
git reset HEAD~1
```

Nothing is lost.

Run:

```bash
git status
```

You'll see:

```text
Modified:

server.js
```

Simply stage and recommit:

```bash
git add .

git commit -m "Correct commit"
```

---

# Recover After `--soft`

Suppose:

```bash
git reset --soft HEAD~1
```

Run:

```bash
git status
```

Output:

```text
Changes to be committed
```

Everything is already staged.

Just recommit:

```bash
git commit -m "Better commit message"
```

---

# Real Backend Example

History:

```text
A Express Setup

B Login API

C JWT Middleware

D Refresh Tokens
```

You accidentally remove `D`:

```bash
git reset --hard HEAD~1
```

Recover:

```bash
git reflog
```

Find:

```text
HEAD@{1}

Refresh Tokens
```

Restore:

```bash
git switch -c recovery-refresh <hash>
```

Verify the code.

Merge or reset back if appropriate.

---

# Reset vs Restore vs Revert

|Command|Primary Purpose|
|---|---|
|`git reset`|Move branch pointer and optionally change staging/working directory|
|`git restore`|Recover or discard file changes|
|`git revert`|Undo changes by creating a new commit|

Choose the command based on what you want to accomplish.

---

# Safe Workflow Before Using `--hard`

Instead of immediately running:

```bash
git reset --hard
```

Follow this checklist:

```text
1. Run git status

↓

2. Verify changes

↓

3. Push important work (optional but recommended)

↓

4. Use reflog if recovery is needed
```

---

# Visual Overview

```text
git reset

│

├── --soft
│      Keeps staged changes
│
├── --mixed
│      Keeps working directory changes
│
└── --hard
       Discards working directory changes
```

---

# Best Practices

- Use `--soft` when changing commit history without losing staged work.
    
- Use `--mixed` for local cleanup before recommitting.
    
- Use `--hard` only when you're certain you no longer need your current uncommitted changes.
    
- Check `git status` before and after a reset.
    
- Learn `git reflog` before relying on `--hard`.
    

---

# Common Mistakes

❌ Running `git reset --hard` without understanding its effects

❌ Assuming `--mixed` deletes work

❌ Forgetting that `git reset` rewrites history

❌ Using `git reset` instead of `git revert` on a shared branch

❌ Panicking instead of checking `git reflog`

---

# Commands You'll Use Most

|Purpose|Command|
|---|---|
|Soft reset|`git reset --soft HEAD~1`|
|Mixed reset (default)|`git reset HEAD~1`|
|Hard reset|`git reset --hard HEAD~1`|
|View reflog|`git reflog`|
|Recover with branch|`git switch -c recovery <hash>`|
|Move branch back|`git reset --hard <hash>`|
