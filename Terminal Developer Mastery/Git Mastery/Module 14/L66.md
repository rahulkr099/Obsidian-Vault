# Module 13 — Git Recovery

# Lesson 66 — Fix Merge Conflicts

> **Goal:** Learn how merge conflicts happen, how to read conflict markers, resolve them safely, and complete merges or rebases without losing anyone's work.

---

# Why Merge Conflicts Happen

A merge conflict occurs when Git **cannot automatically decide** how to combine changes from two branches.

Git is smart—but it can't read intentions.

Imagine two developers editing the same line.

```text
main

A──B──C

         \
feature    D
```

Both modify the same code.

Git doesn't know which version is correct.

Instead of guessing, Git asks **you** to decide.

---

# A Simple Example

Suppose `server.js` contains:

```javascript
const PORT = 3000;
```

### On `main`

```javascript
const PORT = process.env.PORT || 3000;
```

### On `feature`

```javascript
const PORT = 8080;
```

Now merge:

```bash
git switch main

git merge feature
```

Git responds:

```text
Auto-merging server.js

CONFLICT (content): Merge conflict in server.js

Automatic merge failed.
```

---

# Git Stops the Merge

Your repository is now in a special state.

Run:

```bash
git status
```

Output:

```text
You have unmerged paths.

Fix conflicts and run:

git commit

or

git merge --abort
```

Git will not continue until every conflict is resolved.

---

# Conflict Markers

Open the conflicted file.

You may see:

```javascript
<<<<<<< HEAD
const PORT = process.env.PORT || 3000;
=======
const PORT = 8080;
>>>>>>> feature
```

These markers are added by Git.

---

# Understanding the Markers

```text
<<<<<<< HEAD
```

Current branch (`main`)

---

```text
=======
```

Separator

---

```text
>>>>>>> feature
```

Incoming branch

Visual:

```text
Current Version

↓

=======

↓

Incoming Version
```

---

# Resolving the Conflict

Suppose you want both ideas.

Final file:

```javascript
const PORT = process.env.PORT || 8080;
```

Remove:

- `<<<<<<<`
    
- `=======`
    
- `>>>>>>>`
    

Save the file.

Git no longer sees conflict markers.

---

# Tell Git the Conflict Is Resolved

Stage the resolved file:

```bash
git add server.js
```

Now:

```bash
git status
```

Git reports:

```text
All conflicts fixed.
```

Complete the merge:

```bash
git commit
```

Git creates a merge commit.

# Multiple Conflicts

Sometimes several files conflict.

Example:

```text
controllers/authController.js

routes/authRoutes.js

package.json
```

Resolve each one.

Stage each file:

```bash
git add controllers/authController.js

git add routes/authRoutes.js

git add package.json
```

Then:

```bash
git commit
```

---

# Backend Example

Suppose:

Developer A:

```javascript
app.use("/api/auth", authRoutes);
```

Developer B:

```javascript
app.use("/api/users", userRoutes);
```

Git produces:

```javascript
<<<<<<< HEAD
app.use("/api/auth", authRoutes);
=======
app.use("/api/users", userRoutes);
>>>>>>> feature
```

Correct resolution:

```javascript
app.use("/api/auth", authRoutes);
app.use("/api/users", userRoutes);
```

Both features remain.

---

# When One Side Should Win

Sometimes one version is clearly correct.

Keep current branch:

```javascript
const timeout = 5000;
```

Discard incoming version.

Or keep incoming version instead.

The important part is that **you make an intentional decision**.

---

# Merge Conflict During Rebase

Conflicts also happen while rebasing.

Example:

```bash
git rebase main
```

Git:

```text
CONFLICT (content):

authController.js
```

Resolve the file.

Stage it:

```bash
git add authController.js
```

Continue:

```bash
git rebase --continue
```

If another conflict appears, repeat the process.

---

# Abort a Merge

Suppose you realize:

> "I don't want to merge yet."

Run:

```bash
git merge --abort
```

Git restores the repository to the state before the merge started.

---

# Abort a Rebase

Similarly:

```bash
git rebase --abort
```

Everything returns to the pre-rebase state.

# Conflict Resolution Strategy

Whenever you see a conflict:

```text
Read Both Versions

↓

Understand Intent

↓

Choose Correct Code

↓

Remove Markers

↓

Run Tests

↓

Commit
```

Don't simply delete markers without understanding the code.

# Common Conflict Types

|Conflict|Example|
|---|---|
|Same line edited|Two developers change one variable|
|File deleted vs modified|One branch deletes, another edits|
|Rename conflict|Both rename the same file differently|
|Binary file conflict|Images or compiled files changed|
|Package file conflict|`package.json`, `package-lock.json`|

# Real Backend Scenario

Feature branch:

```text
Add JWT Refresh Tokens
```

Main branch:

```text
Refactor Authentication Middleware
```

Both modify:

```text
middleware/auth.js
```

Merge:

```bash
git merge feature/jwt-refresh
```

Conflict:

```javascript
<<<<<<< HEAD
verifyAccessToken();
=======
verifyRefreshToken();
>>>>>>> feature
```

Correct solution:

```javascript
verifyAccessToken();
verifyRefreshToken();
```

Run tests:

```bash
npm test
```

Commit:

```bash
git commit
```

# Best Practices

- Pull or fetch regularly to reduce conflicts.
    
- Keep feature branches small and short-lived.
    
- Read every conflict carefully.
    
- Test after resolving conflicts.
    
- Ask teammates if you're unsure which version is correct.
    
- Never leave conflict markers in committed code.
    

---

# Common Mistakes

❌ Committing files that still contain:

```text
<<<<<<<
=======
>>>>>>>
```

❌ Automatically choosing one version without understanding it

❌ Forgetting to stage resolved files

❌ Skipping tests after conflict resolution

❌ Ignoring `git status`
