# Module 13 — Git Recovery

# Lesson 69 — Git Garbage Collection (`git gc`)

> **Goal:** Understand how Git stores data internally, what `git gc` (Garbage Collection) does, how it affects repository size, and how it relates to recovering lost commits.

---

# Why Does Git Need Garbage Collection?

Every time you:

- Create a commit
    
- Modify a file
    
- Delete a branch
    
- Rebase
    
- Reset
    
- Stash
    

Git creates internal objects.

Over time, your repository accumulates:

- Old commits
    
- Dangling commits
    
- Unreachable objects
    
- Loose objects
    
- Temporary data
    

Without cleanup, repositories would become unnecessarily large.

That's where **Garbage Collection (GC)** comes in.

---

# Git Objects

Internally, Git stores everything as objects.

The four main object types are:

```text
Blob

↓

Tree

↓

Commit

↓

Tag
```

---

## Blob

Stores file contents.

Example:

```text
server.js
```

Every version of a file becomes a blob.

---

## Tree

Represents a directory.

Example:

```text
controllers/

routes/

middleware/
```

---

## Commit

Stores:

- Author
    
- Timestamp
    
- Parent commit
    
- Tree reference
    
- Commit message
    

Example:

```text
Commit

↓

Points to Tree

↓

Tree Points to Blobs
```

---

## Tag

Stores release information.

Example:

```text
v1.0.0
```

---

# Where Are Objects Stored?

Inside:

```text
.git/objects
```

Initially, objects are stored individually.

Example:

```text
.git/

objects/

ab/

cd/

ef/
```

These are called **loose objects**.

---

# What is `git gc`?

Run:

```bash
git gc
```

Git performs maintenance.

It may:

- Compress objects
    
- Combine loose objects into packfiles
    
- Remove expired temporary files
    
- Clean unreachable objects (subject to retention rules)
    
- Optimize repository performance
    

---

# Visual Workflow

Before:

```text
Loose Objects

↓

Thousands of Files

↓

Large Repository
```

After:

```text
Packfiles

↓

Compressed

↓

Smaller Repository
```

---

# Packfiles

Instead of storing thousands of tiny files:

```text
Blob

Blob

Blob

Blob
```

Git combines them:

```text
Packfile
```

Benefits:

- Faster cloning
    
- Faster fetching
    
- Less disk usage
    

---

# When Does Git Run GC?

Often, you don't need to run it manually.

Git automatically performs maintenance after enough repository activity.

Examples:

- Many commits
    
- Many branch operations
    
- Large numbers of loose objects
    

Modern versions of Git also run background maintenance automatically on many systems.

---

# What Are Unreachable Objects?

Suppose:

```text
A──B──C──D
```

You run:

```bash
git reset --hard HEAD~1
```

History becomes:

```text
A──B──C
```

Commit:

```text
D
```

still exists, but nothing references it.

It's now:

```text
Unreachable
```

---

# Why Recovery Works

Earlier lessons used:

```bash
git reflog
```

Recovery works because Git **doesn't immediately delete unreachable commits**.

Instead:

```text
Unreachable Commit

↓

Wait

↓

Eligible for Cleanup

↓

git gc

↓

Eventually Removed
```

This retention period is what gives you a chance to recover lost work.

---

# Inspect Repository Size

View object statistics:

```bash
git count-objects -v
```

Example:

```text
count: 142

size: 568

in-pack: 400

packs: 2
```

Meaning:

- Loose objects
    
- Packfile objects
    
- Number of packfiles
    

---

# Packing Objects

Run:

```bash
git gc
```

Then:

```bash
git count-objects -v
```

You'll usually notice:

```text
Loose Objects

↓

Much Lower

Packfiles

↓

Higher
```

Git compressed your repository.

---

# Aggressive Garbage Collection

Command:

```bash
git gc --aggressive
```

Git spends more time optimizing.

Possible benefits:

- Better compression
    
- Smaller repository
    

Trade-offs:

- Slower to run
    
- Usually unnecessary for everyday development
    

Reserve this for special situations, such as optimizing very large repositories.

---

# Pruning Unreachable Objects

Git can remove unreachable objects that have exceeded their retention period.

Example:

```bash
git prune
```

Normally, you should **avoid running `git prune` directly** unless you understand its consequences.

`git gc` coordinates pruning safely as part of its maintenance process.

---

# Backend Example

Imagine an Express project.

History:

```text
A

B

C

D
```

You accidentally remove:

```text
D
```

Recover:

```bash
git reflog
```

Success.

But weeks later:

```bash
git gc
```

After the retention period expires, unreachable commit `D` may no longer be recoverable.

This is why you should recover important work **as soon as you realize it's missing**.

# Repository Maintenance

Useful maintenance commands:

View repository health:

```bash
git fsck
```

View object counts:

```bash
git count-objects -v
```

Run garbage collection:

```bash
git gc
```

---

# `git gc` vs `git fsck`

|Command|Purpose|
|---|---|
|`git gc`|Optimize and clean the repository|
|`git fsck`|Verify repository integrity and find unreachable objects|

---

# What `git gc` Does NOT Do

It does **not**:

❌ Delete active branches

❌ Delete current commits

❌ Remove valid tags

❌ Remove reachable history

It only cleans objects that Git determines are no longer needed, following its retention policies.

---

# Real Production Scenario

A backend team works on a repository for several years.

Repository:

```text
20,000 commits

500 branches

Thousands of merged PRs
```

Without maintenance:

- More loose objects
    
- Slower operations
    
- Larger disk usage
    

Regular Git maintenance helps keep operations efficient.

# Best Practices

- Let Git perform automatic maintenance in most cases.
    
- Recover lost commits promptly using `git reflog`.
    
- Avoid manually deleting Git internals.
    
- Run `git fsck` if you suspect repository corruption.
    
- Understand that unreachable commits are not stored forever.
    

---

# Common Mistakes

❌ Assuming deleted commits are recoverable forever

❌ Running aggressive cleanup before checking `git reflog`

❌ Using `git prune` without understanding its effects

❌ Manually editing files inside `.git/objects`

❌ Confusing repository optimization with backup
