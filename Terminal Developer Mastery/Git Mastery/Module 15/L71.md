# Lesson 71 — Express API Repository

> **Goal:** Learn how to organize and manage a professional Express.js backend repository using Git. This lesson combines everything you've learned so far—Git, Linux, branching, commit history, and collaboration—into a realistic backend project.

---

# Why This Matters

In real companies, you rarely work on tiny repositories. Instead, you'll contribute to large backend applications with:

- REST APIs
    
- Authentication
    
- Databases
    
- Docker
    
- CI/CD
    
- Automated testing
    
- Multiple developers
    

Git should help keep the project organized, not create confusion.

```
url-shortener-api/
│
├── src/
│   ├── controllers/
│   ├── routes/
│   ├── middleware/
│   ├── services/
│   ├── repositories/
│   ├── models/
│   ├── config/
│   ├── utils/
│   └── app.js
│
├── tests/
│
├── docs/
│
├── scripts/
│
├── .github/
│   ├── workflows/
│   └── ISSUE_TEMPLATE/

├── docker-compose.yml
```

# Step 1 — Initialize Repository

```bash
mkdir url-shortener-api

cd url-shortener-api

git init
```

Verify:

```bash
git status
```

Output:

```
On branch main

No commits yet
```

---

# Step 2 — Create Initial Structure

```
mkdir src tests docs scripts

touch README.md

touch .gitignore

touch package.json
```

Commit:

```bash
git add .

git commit -m "chore: initialize backend project structure"
```

---

# Step 3 — Professional `.gitignore`

Example:

```
node_modules/

.env

coverage/

dist/

logs/

*.log

.vscode/

.DS_Store
```

Never commit:

- Dependencies
    
- Secrets
    
- Build files
    
- Temporary logs
    

---

# Step 4 — Add Express

```bash
npm init -y

npm install express
```

Notice:

```
package.json

package-lock.json
```

Git Status:

```
modified: package.json

new file: package-lock.json
```

Commit:

```bash
git add package.json package-lock.json

git commit -m "build: add Express dependency"
```

---

# Step 5 — First API

Create:

```
src/app.js
```

Example:

```javascript
const express = require("express");

const app = express();

app.get("/", (req, res) => {
    res.json({
        message: "API Running"
    });
});

app.listen(3000);
```

Commit:

```bash
git add src/

git commit -m "feat: create initial API endpoint"
```

# Step 6 — Branch for Features

Instead of working on `main`:

```
main
```

Create:

```bash
git switch -c feature/authentication
```

Now all authentication work happens here.

# Step 8 — Merge via Pull Request

Never merge directly into `main`.

Instead:

```

          │
          ▼
Pull Request
          │
          ▼
Code Review
          │
          ▼
```

# Step 9 — Bug Fixes

Bug discovered?

Create:

```bash

git pull

git switch -c bugfix/token-expiry
```

Fix:

```

```

Merge after review.

# Common Mistakes

### Working directly on `main`

Bad:

```
main
 ├── commit
 ├── commit
 ├── commit
```

Good:

```
main
 ├── feature/auth
 ├── feature/cache
 ├── feature/search
```

---

### Giant commits

Bad:

```
feat: completed everything
```

Good:

```
feat: create user model

feat: implement login API

feat: add JWT middleware

test: add login tests
```

---

### Committing secrets

Never commit:

```
.env

id_rsa

firebase.json

service-account.json
```

---

### Mixing unrelated changes

Bad:

```
feat: authentication + Docker + README + CI + caching
```

Good:

Each logical change gets its own commit.

# Real-World Example Workflow

```
Clone repository

↓

Create feature branch

↓

Write code

↓

Commit frequently

↓

Push branch

↓

Open Pull Request

↓

Code Review

↓

Address feedback

↓

Merge

↓

Delete feature branch
```

This workflow is common in professional backend teams.

---

# Best Practices

- Start every new feature from the latest `main`.
    
- Keep commits focused on one logical change.
    
- Write descriptive commit messages.
    
- Use feature branches for all work.
    
- Review your changes with `git diff` before committing.
    
- Never commit secrets or generated files.
    
- Keep documentation updated as the project evolves.

## Key Takeaways

- A well-organized repository is easier to maintain and collaborate on.
    
- Feature branches and small commits improve code reviews.
    
- Repository structure, documentation, and Git history are as important as the code itself.
