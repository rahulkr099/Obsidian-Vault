# Lesson 72 — Dockerized Backend

> **Goal:** Learn how Git and Docker work together in a professional backend project. By the end of this lesson, you'll be able to version-control a Dockerized Express API, collaborate on it, and keep your repository clean and reproducible.

---

# Why Docker + Git?

Imagine you push your Express API to GitHub.

Your teammate clones it.

Without Docker, they might face problems like:

- Different Node.js version
    
- Missing dependencies
    
- Different operating system
    
- Missing environment variables
    
- "Works on my machine" issues
    

Docker solves these problems by packaging your application and its environment together.

Git tracks the Docker configuration so everyone uses the same setup.

---

# Project Structure

A typical Dockerized backend project looks like this:

```text
url-shortener-api/
│
├── src/
│   ├── app.js
│   ├── routes/
│   ├── controllers/
│   └── ...
│
├── Dockerfile
├── docker-compose.yml
├── .dockerignore
├── .gitignore
├── package.json
├── package-lock.json
├── .env.example
├── README.md
└── .github/
```

---

# Step 1 — Create a Dockerfile

Create:

```text
Dockerfile
```

Example:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

EXPOSE 3000

CMD ["npm", "start"]
```

---

## Understanding Each Line

### Base image

```dockerfile
FROM node:22-alpine
```

Uses a lightweight Node.js image.

---

### Working directory

```dockerfile
WORKDIR /app
```

Everything happens inside `/app`.

---

### Copy dependency files

```dockerfile
COPY package*.json ./
```

Copies:

- package.json
    
- package-lock.json
    

before copying the source code.

Why?

Docker caches layers.

If only source code changes, dependencies don't need reinstalling.

This makes builds much faster.

---

### Install packages

```dockerfile
RUN npm install
```

Installs project dependencies.

---

### Copy project

```dockerfile
COPY . .
```

Copies remaining files.

---

### Expose port

```dockerfile
EXPOSE 3000
```

Documents that the container listens on port 3000.

---

### Start application

```dockerfile
CMD ["npm", "start"]
```

Runs:

```bash
npm start
```

---

# Step 2 — Create `.dockerignore`

Never copy unnecessary files into the image.

Example:

```text
node_modules

.git

.github

coverage

.env

*.log

dist
```

Benefits:

- Smaller images
    
- Faster builds
    
- Better security
    

---

# Step 3 — Update `.gitignore`

Your `.gitignore` should include:

```text
node_modules/

.env

coverage/

dist/

logs/

*.log
```

Notice:

We **do not ignore**:

- Dockerfile
    
- docker-compose.yml
    
- .dockerignore
    

These files should always be tracked.

---

# Step 4 — Create `docker-compose.yml`

Example:

```yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    env_file:
      - .env
```

Now the application starts with:

```bash
docker compose up
```

instead of remembering long Docker commands.

---

# Step 5 — Build the Image

```bash
docker build -t url-shortener-api .
```

Verify:

```bash
docker images
```

---

# Step 6 — Run the Container

```bash
docker run -p 3000:3000 url-shortener-api
```

Visit:

```text
http://localhost:3000
```

---

# Step 7 — Commit Docker Support

Check status:

```bash
git status
```

Example:

```text
new file: Dockerfile

new file: docker-compose.yml

new file: .dockerignore
```

Commit:

```bash
git add Dockerfile docker-compose.yml .dockerignore

git commit -m "build: dockerize Express application"
```

Notice the Conventional Commit type:

```text
build:
```

because build configuration changed.

# Professional Workflow

Instead of mixing Docker with unrelated work:

Bad:

```text
feat: authentication

+ Docker

+ README

+ CI

+ tests
```

Good:

```text
feat: implement authentication

build: add Docker support

docs: update Docker instructions

test: add Docker integration tests
```

Each commit has one purpose.

# Keeping Images Reproducible

A reproducible build means:

Every developer builds the same image.

This requires:

- Dockerfile committed
    
- package-lock.json committed
    
- Same base image
    
- Same build steps
    

Avoid using floating versions like:

```dockerfile
FROM node:latest
```

Instead:

```dockerfile
FROM node:22-alpine
```

or an even more specific version if required by your team.

---

# Environment Variables

Never commit:

```text
.env
```

Instead commit:

```text
.env.example
```

Example:

```env
PORT=3000

DATABASE_URL=

JWT_SECRET=
```

Each developer creates their own:

```text
.env
```

from:

```text
.env.example
```

# Common Mistakes

## Committing `.env`

Bad:

```text
.env
```

This may expose:

- Database passwords
    
- API keys
    
- JWT secrets
    

Always ignore it.

---

## Committing `node_modules`

Bad:

```text
node_modules/
```

Never commit installed dependencies.

---

## Ignoring Docker Files

Bad:

```text
Dockerfile
```

in `.gitignore`

Other developers won't be able to build the project.

---

## Using `latest`

Bad:

```dockerfile
FROM node:latest
```

Tomorrow, `latest` may point to a different version and unexpectedly break your application.

---

## Huge Docker Commits

Bad:

```text
build: Docker
```

after changing 50 unrelated files.

Keep Docker changes isolated.

# Best Practices

- Commit Docker configuration files.
    
- Never commit secrets.
    
- Use `.dockerignore` to reduce image size.
    
- Pin Docker base image versions.
    
- Keep Docker-related commits separate from feature work.
    
- Document how to build and run the project in `README.md`.
    
- Test that a fresh clone can be built successfully using only the repository contents.

## Key Takeaways

- Docker and Git complement each other: Docker standardizes the runtime, while Git tracks the configuration.
    
- Docker-related files are source code and should be version-controlled.
    
- Reproducible builds reduce onboarding time and eliminate "works on my machine" problems.
    
- A clean Git history and a well-structured Docker setup are hallmarks of professional backend engineering.
