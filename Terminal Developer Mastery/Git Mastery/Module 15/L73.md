# Lesson 73 — CI/CD with GitHub

> **Goal:** Learn how professional backend teams automatically build, test, and validate their code using GitHub Actions. By the end of this lesson, you'll create a basic CI pipeline that runs every time code is pushed or a Pull Request is opened.

# Why CI/CD?

Imagine a team of five backend developers.

Developer A pushes code.

Developer B pulls it.

Developer C accidentally breaks authentication.

Developer D forgets to run tests.

Developer E uses Node.js 22, while Developer A uses Node.js 20.

Without automation, bugs reach production quickly.

Continuous Integration (CI) solves this by automatically checking every change.

---

# What is CI?

**Continuous Integration (CI)** means:

> Every code change is automatically verified before it is merged.

Typical CI tasks:

- Install dependencies
    
- Run linting
    
- Run tests
    
- Build the project
    
- Check formatting
    
- Detect common errors
    

---

# What is CD?

**Continuous Delivery/Deployment (CD)** automates releasing software.

Examples:

```text
Push Code
      │
      ▼
Run Tests
      │
      ▼
Build Docker Image
      │
      ▼
Deploy to Server
```

In this lesson, we'll focus on **CI**.

# GitHub Actions Overview

GitHub Actions is GitHub's built-in automation system.

Workflow files are stored inside:

```text
.github/
└── workflows/
    └── ci.yml
```

Git tracks these files like any other source code.

---

# Basic CI Workflow

Create:

```text
.github/workflows/ci.yml
```

Example:

```yaml
name: Node.js CI

on:
  push:
    branches:
      - main
      - develop

  pull_request:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - run: npm ci

      - run: npm test
```

---

# Understanding the Workflow

## Workflow Name

```yaml
name: Node.js CI
```

This is the name shown in GitHub's Actions tab.

---

## Triggers

```yaml
on:
```

Defines when the workflow runs.

Example:

```yaml
push:
```

Runs after every push.

Example:

```yaml
pull_request:
```

Runs for every Pull Request.

Professional teams usually test both.

---

## Jobs

```yaml
jobs:
```

A workflow can contain multiple jobs.

Example:

```text
Lint

↓

Test

↓

Build

↓

Deploy
```

Jobs can run:

- Sequentially
    
- In parallel
    

---

## Runner

```yaml
runs-on: ubuntu-latest
```

GitHub creates a temporary Ubuntu virtual machine.

Your workflow runs there.

When finished:

The VM is destroyed.

---

## Checkout Repository

```yaml
- uses: actions/checkout@v4
```

Downloads your repository onto the runner.

Equivalent to:

```bash
git clone ...
```

---

## Install Node

```yaml
actions/setup-node
```

Installs Node.js.

Example:

```yaml
node-version: 22
```

Every workflow uses the same Node version.

---

## Install Dependencies

```yaml
npm ci
```

Notice:

Not

```bash
npm install
```

---

# Why `npm ci`?

`npm ci`

- Faster
    
- Uses package-lock.json
    
- Reproducible
    
- Designed for CI
    

Professional pipelines almost always use:

```bash
npm ci
```

```text

```

cannot be merged unless:

This prevents broken code from entering production.

# Common Mistakes

## Not Committing Workflow Files

Bad:

```text
ci.yml
```

exists locally but wasn't committed.

GitHub cannot run it.

---

## Using `npm install`

Prefer:

```bash
npm ci
```

for reproducible installs.

---

## Ignoring Failing Tests

Never merge because:

> "It passes on my machine."

CI is the source of truth.

---

## Not Pinning Node Version

Bad:

```yaml
node-version: latest
```

Good:

```yaml
node-version: 22
```

Everyone uses the same runtime.

---

## Huge Workflow Files

Avoid putting every task into one massive workflow.

Split by responsibility when the project grows.

# Best Practices

- Commit workflow files to the repository.
    
- Use `npm ci` instead of `npm install` in CI.
    
- Pin Node.js versions.
    
- Run linting before tests if possible.
    
- Keep workflows fast to encourage frequent commits.
    
- Require passing CI before merging into protected branches.
    
- Review workflow changes just like application code.

# Key Takeaways

- CI automatically verifies every code change.
    
- GitHub Actions is the standard CI solution for many GitHub-hosted backend projects.
    
- A good CI pipeline installs dependencies, lints code, runs tests, and builds the application.
    
- Protected branches combined with CI help maintain a stable and reliable codebase.
    
- Automated validation saves time, catches bugs early, and makes team collaboration more efficient.
