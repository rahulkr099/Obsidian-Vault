# Why Simulate Team Collaboration?

Most Git problems don't happen when working alone.

They happen when:

- Multiple developers edit the same files.
    
- Features are developed in parallel.
    
- Bugs need urgent fixes.
    
- Pull Requests overlap.
    
- Merge conflicts occur.
    

Professional Git usage is primarily about **working effectively with other developers**.

# Project Scenario

Imagine you're part of a five-person backend team building a **Task Management API**.

The team consists of:

|Developer|Responsibility|
|---|---|
|Alice|Authentication|
|Bob|Task CRUD|
|Charlie|Notifications|
|David|Docker & CI|
|You|User Profile API|

The repository already contains:

```text

│   ├── controllers/
│   ├── routes/
│   ├── middleware/
│   ├── services/
│   └── app.js
│
├── tests/
├── Dockerfile
├── package.json
└── README.md
```

# Step 1 — Clone the Repository

Everyone starts from the same repository.

```bash
git clone git@github.com:company/task-api.git

cd task-api
```

Always verify you're on the latest main branch.

```bash
git switch main

git pull origin main
```

Never start new work from an outdated branch.

---

# Step 2 — Create Your Feature Branch

You're implementing user profiles.

```bash
git switch -c feature/user-profile
```

Branch structure:

```text
main
 │
 ├── feature/authentication
 ├── feature/tasks
 ├── feature/notifications
 ├── feature/user-profile
 └── feature/docker
```

Each developer works independently.

---

# Step 3 — Make Small Commits

Instead of writing all the code at once, commit logical milestones.

### Commit 1

```text
feat: create profile controller
```

### Commit 2

```text
feat: add profile route
```

### Commit 3

```text
test: add profile API tests
```

### Commit 4

```text
docs: document profile endpoints
```

Small commits make reviews easier.

---

# Step 4 — Push Your Branch

```bash
git push -u origin feature/user-profile
```

The remote repository now contains your branch.

---

# Step 5 — Open a Pull Request

Instead of merging directly:

```text
feature/user-profile

        │

        ▼

   Pull Request
```

A Pull Request should include:

- What changed
    
- Why it changed
    
- Screenshots (if UI)
    
- Test results
    
- Related issue number
    

Example description:

```markdown
## Summary

Adds profile management API.

## Changes

- Profile controller
- Profile routes
- Validation middleware
- Unit tests

## Testing

- npm test
- Manual API testing

Closes #42
```

---

# Step 6 — Code Review

Your teammate reviews the Pull Request.

Comments might include:

```text
Use asyncHandler here.

Rename this variable.

Missing validation.

Add test coverage.

Simplify this query.
```

Professional developers expect feedback.

Code review improves the code—not just finds mistakes.

---

# Step 7 — Respond to Review

Instead of creating a new Pull Request:

Simply update the same branch.

Example:

```bash
git add .

git commit -m "refactor: address PR review comments"

git push
```

The Pull Request updates automatically.

---

# Step 8 — Another Developer Changes the Same File

While you're working:

Bob merges changes into:

```text
src/routes/profile.js
```

Now your branch is behind.

---

# Update Your Branch

Fetch the latest changes.

```bash
git fetch origin
```

Rebase onto the updated main branch.

```bash
git rebase origin/main
```

Or merge if your team's workflow prefers it.

```bash
git merge origin/main
```

---

# Step 9 — Resolve Merge Conflict

Suppose both developers edited:

```text
src/routes/profile.js
```

Git shows:

```text
<<<<<<< HEAD

Your code

=======

Bob's code

>>>>>>> origin/main
```

Resolve manually.

Final file:

```javascript
router.get("/profile", getProfile);

router.patch("/profile", updateProfile);

router.delete("/profile", deleteProfile);
```

Then continue.

```bash
git add src/routes/profile.js

git rebase --continue
```

---

# Step 10 — CI Runs Automatically

After pushing:

```text
Push

↓

GitHub Actions

↓

Lint

↓

Tests

↓

Build

↓

Success
```

If tests fail:

Fix them before requesting another review.

---

# Step 11 — Pull Request Approved

Reviewers approve.

```text
✔ Approved
```

Merge using the team's strategy.

Common choices:

- Squash and Merge
    
- Rebase and Merge
    
- Merge Commit
    

For feature branches, many teams prefer **Squash and Merge** to keep `main` clean.

---

# Step 12 — Delete the Branch

After merging:

```bash
git branch -d feature/user-profile
```

Delete the remote branch too.

```bash
git push origin --delete feature/user-profile
```

Keeping old branches around creates clutter.

# Hotfix Scenario

Production bug discovered.

Do **not** continue working on your feature branch.

Create a new branch from `main`.

```bash
git switch main

git pull

git switch -c hotfix/profile-auth
```

Fix the bug.

Commit:

```text
fix: prevent unauthorized profile access
```

Open a Pull Request immediately.

# Team Communication

Git works best with communication.

Examples:

```text
"I'm working on authentication routes."

"I'm modifying profile.js today."

"Please wait before changing user.service.js."

"I've rebased onto main."

"CI is currently failing."
```

Many merge conflicts are avoided simply by talking to teammates.

# Common Mistakes

## Working Directly on `main`

Bad:

```bash
git switch main
```

Writing new features directly here increases the risk of unstable code.

---

## Huge Pull Requests

Bad:

```text
150 files changed
```

Large PRs are difficult to review.

Aim for focused, manageable changes.

---

## Ignoring Review Comments

If reviewers request changes, address them thoughtfully.

Code review is collaborative, not adversarial.

---

## Forgetting to Sync with `main`

Always update your branch before requesting a final review.

---

## Leaving Old Branches

Delete merged branches to keep the repository organized.

# Best Practices

- Create one branch per feature or bug fix.
    
- Keep Pull Requests focused and easy to review.
    
- Commit frequently with meaningful messages.
    
- Sync your branch with `main` regularly.
    
- Resolve conflicts carefully and test afterward.
    
- Respond to review comments with follow-up commits.
    
- Delete merged branches.
    
- Communicate with teammates when working on shared areas of the codebase.

# Mini Project

Simulate a one-week sprint for a backend team.

1. Create a repository for a Task Management API.
    
2. Create four feature branches:
    
    - `feature/authentication`
        
    - `feature/tasks`
        
    - `feature/notifications`
        
    - `feature/user-profile`
        
3. Make at least three commits on each branch.
    
4. Merge the branches one by one into `main`.
    
5. Intentionally create and resolve one merge conflict.
    
6. Run your CI workflow after each merge.
    
7. Delete merged branches.
    
8. Review the final commit history with:
    

```bash
git log --oneline --graph --decorate --all
```

Your goal is to produce a clean, understandable Git history that resembles the work of a real backend team.

# Key Takeaways

- Git is fundamentally a collaboration tool, not just a version control system.
    
- Feature branches, Pull Requests, and code reviews are the foundation of professional team workflows.
    
- Small commits and focused Pull Requests make collaboration smoother.
    
- Regularly syncing with `main` reduces merge conflicts.
    
- Good communication is just as important as good Git commands when working on a team.
