# Phase 1 — Create Feature Branches

Each feature gets its own branch.

```bash
git switch main

git pull origin main
```

Create branches:

```bash
git switch -c feature/user-profile
```

```bash
git switch -c feature/task-labels
```

```bash
git switch -c feature/email-notifications
```

---

# Phase 2 — Develop Features

Example commit history:

```text
feat: create profile controller

feat: add profile routes

feat: implement task labels

feat: send notification emails

test: add notification tests

docs: update API documentation
```

Notice:

Each commit does **one logical thing**.

---

# Phase 3 — Push Branches

```bash
git push -u origin feature/user-profile
```

Repeat for every feature branch.

---

# Phase 4 — Open Pull Requests

Each Pull Request contains:

- Summary
    
- Related issue
    
- Testing performed
    
- Screenshots (if UI)
    
- Reviewer
    

Example:

```markdown

## Related Issue
```

- Code quality

- Tests
    
- Performance
    
- Security
    
- Documentation
    

Example feedback:

```text
Improve test coverage.
```

Update the branch.

# Phase 7 — Merge Features

```text

↓

↓
```

# Phase 8 — Create Release Branch

Many teams prepare a release branch.

```bash
git switch main

git pull

git switch -c release/v1.5.0
```

Purpose:

- Final testing
    
- Documentation updates
    
- Version changes
    
- Last-minute fixes
    

No new features should be added here.

---

# Phase 9 — Update Version

Example:

```json
{
  "version": "1.5.0"
}
```

Commit:


# Phase 10 — Final Testing

Before releasing:

Run:

```bash
npm test
```

Build:

```bash
npm run build
```

Docker:


Run locally:

```bash
docker run -p 3000:3000 task-api:v1.5.0
```

Verify:

- Authentication
    
- APIs
    
- Database
    
- Logging
    
- Environment variables

# Phase 11 — Tag the Release

Create an annotated tag:

```bash
git tag -a v1.5.0 -m "Release version 1.5.0"
```

Push the tag:

```bash
git push origin v1.5.0
```

This permanently marks the release commit.

# Phase 15 — Emergency Hotfix

A bug is discovered:

> Users cannot update their profiles.

Do **not** continue working on unrelated feature branches.

Start from the latest `main`:

```bash
git switch main

git pull

git switch -c hotfix/profile-update
```

Fix the issue.

Commit:

```text
fix: restore profile update endpoint
```

Run tests.

Open an expedited Pull Request.

Merge after review.

---

# Phase 16 — Patch Release

Create a patch version:

```text
v1.5.1
```

Tag it:

```bash
git tag -a v1.5.1 -m "Hotfix release"
```

Push:

```bash
git push origin v1.5.1
```

Deploy again.

# Common Mistakes

## Deploying Without Tests

Bad:

```text
Looks fine.

Deploy.
```

Always run automated tests before releasing.

---

## Skipping Tags

Without tags, it becomes difficult to identify exactly which commit is running in production.

---

## Mixing Features and Hotfixes

Keep emergency fixes separate from ongoing feature work.

---

## Large Release Commits

Release preparation should contain only release-related changes.

---

## Ignoring Monitoring

A successful deployment is only the beginning. Watch the application after release to catch issues early.

# Best Practices

- Keep `main` stable and protected.
    
- Merge only reviewed and tested Pull Requests.
    
- Use semantic versioning for releases.
    
- Create annotated Git tags for every production release.
    
- Maintain clear release notes.
    
- Automate builds, tests, and deployments.
    
- Monitor production after every deployment.
    
- Handle hotfixes in dedicated branches.
    
- Delete merged branches to keep the repository clean.
