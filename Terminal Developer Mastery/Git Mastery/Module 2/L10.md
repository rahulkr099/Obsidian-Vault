# Module 2 — Daily Git Workflow

# Lesson 10 — Undoing Mistakes (`git restore`, `git reset`, `git revert`)

Every developer makes mistakes.

You might:

- Delete the wrong file.
    
- Edit the wrong function.
    
- Stage the wrong files.
    
- Commit too early.
    
- Push a bug.
    
- Delete an important branch.
    

The good news?

**Git is designed to recover from mistakes.**

This lesson will teach you the **safe** ways to undo changes and explain **when** to use each command.

> **Important Rule**
> 
> Before using any undo command, always run:
> 
> ```bash
> git status
> ```
> 
> Know exactly what state your repository is in before changing anything.

---

# Lesson Goals

By the end of this lesson, you'll know how to:

- Undo file changes
    
- Unstage files
    
- Undo commits
    
- Revert commits safely
    
- Understand the difference between `restore`, `reset`, and `revert`
    
- Choose the correct command for each situation

# The Three Git Areas (Review)

Understanding undo commands is much easier if you remember Git's three areas.

```text
Working Directory
       │
    git add
       ▼
Staging Area
       │
 git commit
       ▼
Repository
```

Different commands affect different areas.

# Common Mistakes

Imagine this timeline:

```text
Edit file

↓

Oops

↓

Need to undo
```

Or:

```text
Stage file

↓

Oops

↓

Need to unstage
```

Or:

```text
Commit

↓

Oops

↓

Need to undo commit
```

Each situation has a different solution.

---

# Scenario 1 — Undo Changes in a File

Suppose:

```javascript
const PORT = 3000;
```

You accidentally change it to:

```javascript
const PORT = 9999;
```

You haven't staged it yet.

Restore the file:

```bash
git restore app.js
```

Result:

```javascript
const PORT = 3000;
```

Your local edits are discarded.

---

# What Does `git restore` Do?

It replaces the file in your **Working Directory** with the version from the last commit (or another specified source).

```text
Repository

↓

Restore

↓

Working Directory
```

---

# Restore Multiple Files

```bash
git restore app.js auth.js
```

---

# Restore Everything

```bash
git restore .
```

This restores all modified tracked files in the current directory.

⚠️ Be careful—your uncommitted changes will be lost.

---

# Scenario 2 — Unstage a File

Suppose:

```bash
git add app.js
```

Then you realize:

> "I didn't want to commit this yet."

Run:

```bash
git restore --staged app.js
```

Status changes from:

```text
Changes to be committed
```

to:

```text
Changes not staged for commit
```

The file is **still modified**, but it's no longer staged.

---

# Visualizing `git restore --staged`

```text
Working Directory

↓

Staging Area

↓

Repository
```

`git restore --staged` moves the file out of the staging area but leaves your edits intact.

---

# Scenario 3 — Restore and Unstage

Suppose you want to:

- Remove from staging
    
- Discard local changes
    

Use:

```bash
git restore --staged app.js
git restore app.js
```

Now the file matches the last commit.

---

# `git reset`

`git reset` is a more powerful command.

It can:

- Unstage files
    
- Move the branch pointer
    
- Remove commits (depending on the mode)
    

For beginners, the safest use is:

```bash
git reset HEAD app.js
```

This unstages `app.js` but keeps your edits.

Today, prefer:

```bash
git restore --staged app.js
```

It's clearer and less risky.

---

# `git reset --soft`

Imagine:

```text
Commit A

↓

Commit B

↓

Commit C
```

Run:

```bash
git reset --soft HEAD~1
```

Result:

```text
Commit A

↓

Commit B
```

- Commit C disappears from history.
    
- All its changes remain staged.
    

Useful when you want to rewrite the last commit.

---

# `git reset --mixed` (Default)

```bash
git reset HEAD~1
```

or

```bash
git reset --mixed HEAD~1
```

Result:

- Last commit removed.
    
- Changes remain in the Working Directory.
    
- Nothing is staged.
    

---

# `git reset --hard`

```bash
git reset --hard HEAD~1
```

This removes:

- The commit
    
- Staged changes
    
- Working directory changes
    

Everything goes back to the previous commit.

⚠️ This can permanently delete uncommitted work.

---

# Reset Comparison

|Command|Commit|Staging Area|Working Directory|
|---|---|---|---|
|`--soft`|Moves back|Keeps changes staged|Keeps changes|
|`--mixed`|Moves back|Unstages changes|Keeps changes|
|`--hard`|Moves back|Clears staging|Discards changes|

---

# Understanding `HEAD`

`HEAD` points to your current commit.

Example:

```text
Commit A

↓

Commit B

↓

Commit C ← HEAD
```

`HEAD~1`

means:

```text
Commit B
```

`HEAD~2`

means:

```text
Commit A
```

---

# Scenario 4 — Undo the Last Commit Safely

Suppose you committed:

```text
Fix login
```

But it introduced a bug.

Instead of deleting history, create a new commit that reverses it:

```bash
git revert HEAD
```

Git creates a new commit:

```text
Commit A

↓

Buggy Commit

↓

Revert Commit
```

History remains intact.

---

# Why `git revert`?

Imagine you've already pushed to GitHub.

Other developers have pulled your commit.

Deleting history with `git reset` can cause problems.

Instead:

```bash
git revert HEAD
```

creates a new commit that safely undoes the changes.

---

# `git reset` vs `git revert`

## `git reset`

Changes history.

Good for:

- Local commits
    
- Private branches
    

---

## `git revert`

Preserves history.

Good for:

- Shared repositories
    
- Production branches
    
- Team projects
    

---

# Backend Example

Suppose you deploy:

```text
Add payment API
```

Users report failures.

Don't do:

```bash
git reset --hard
```

Instead:

```bash
git revert HEAD
```

Now the payment feature is removed while the project history stays accurate.

---

# Which Command Should I Use?

|Situation|Command|
|---|---|
|Discard local edits|`git restore file`|
|Unstage a file|`git restore --staged file`|
|Remove last local commit but keep changes staged|`git reset --soft HEAD~1`|
|Remove last local commit and unstage changes|`git reset HEAD~1`|
|Delete everything (dangerous)|`git reset --hard HEAD~1`|
|Undo a pushed commit|`git revert HEAD`|

---

# Real Backend Workflow

Suppose:

```text
Commit

↓

Push

↓

Production Bug
```

Safe solution:

```bash
git revert HEAD

git push
```

Team members simply pull the new revert commit.

---

# Common Mistakes

## Mistake 1

Using:

```bash
git reset --hard
```

without understanding the consequences.

Always double-check before running it.

---

## Mistake 2

Using:

```bash
git reset
```

after pushing to GitHub.

This rewrites history and can disrupt your teammates.

---

## Mistake 3

Forgetting to check:

```bash
git status
```

before undoing changes.

---

# Best Practices

- Prefer `git restore` for files.
    
- Prefer `git revert` after pushing commits.
    
- Use `git reset` mainly for local, unpublished history.
    
- Avoid `git reset --hard` unless you're certain you don't need the changes.
    
- Check `git status` before and after undo operations.
    

---

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git restore file`|Discard local changes|
|`git restore --staged file`|Unstage a file|
|`git restore .`|Restore all tracked files|
|`git reset HEAD file`|Unstage a file (older syntax)|
|`git reset --soft HEAD~1`|Undo last commit, keep changes staged|
|`git reset HEAD~1`|Undo last commit, keep changes unstaged|
|`git reset --hard HEAD~1`|Delete last commit and changes|
|`git revert HEAD`|Create a new commit that undoes the last commit|

# Hands-on Lab

Create a practice repository:

```bash
mkdir undo-lab
cd undo-lab

git init

echo "# Demo" > README.md

git add README.md

git commit -m "Initial commit"

echo "New line" >> README.md

git status

git restore README.md

echo "Another line" >> README.md

git add README.md

git restore --staged README.md

git status
```

Then create another commit and experiment with:

```bash
git reset --soft HEAD~1

git status
```

Next, recommit the changes and try:

```bash
git revert HEAD
```

Observe how the commit history changes.

## Professional Tip

A good rule to remember is:

- **Not pushed yet?** → `git reset` is often appropriate.
    
- **Already pushed and shared?** → `git revert` is usually the safest choice.
    

Experienced backend engineers rely on this distinction to avoid disrupting teammates while still fixing mistakes quickly.
