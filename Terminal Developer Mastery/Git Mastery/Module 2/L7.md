# Module 2 — Daily Git Workflow

# Lesson 7 — Mastering `git add`

In the last lesson, you learned how to **read your repository** using `git status`.

Now you'll learn the command that moves changes from your **Working Directory** to the **Staging Area**:

```bash
git add
```

Many beginners think:

> "`git add` adds a file to the repository."

This is **not correct**.

`git add` **does not commit anything**.

It simply tells Git:

> "I want this version of these changes to be included in my next commit."

---

# Review the Git Workflow

```text
Working Directory
        │
   git add
        ▼
 Staging Area
        │
 git commit
        ▼
 Repository
```

Remember:

- `git add` → prepares changes
    
- `git commit` → saves changes

```bash
git add app.js
```

Status:

```text
Changes to be committed:

new file: app.js

Untracked:

auth.js
routes.js
README.md
```

Only `app.js` is staged.

```bash
git add auth.js routes.js
```

Now:

```text
Changes to be committed:

app.js

Untracked:

```

# Stage an Entire Directory

Suppose:

```text
src/

app.js
auth.js
routes.js
```

Stage everything inside `src`:

```bash
git add src/
```

Very common in backend projects.

---

# Stage Everything

```bash
git add .
```

This is one of the most frequently used commands.

Meaning:

> Stage all changes in the current directory and its subdirectories.

Example:

```text
backend/

src/
README.md
package.json
```

```bash
git add .
```

Everything becomes staged.

---

# Understanding `git add .`

It stages:

- New files
    
- Modified files
    
- Deleted files (inside the current directory)
    

Example:

```text
Before

Working Directory

↓

app.js modified

auth.js deleted

README.md new
```

↓

```bash
git add .
```

↓

```text
All ready for commit
```

---

# `git add -A`

Another useful command:

```bash
git add -A
```

Stages:

- New files
    
- Modified files
    
- Deleted files
    

Across the **entire repository**.

Many developers use:

```bash
git add -A
```

instead of:

```bash
git add .
```

because it's explicit and works consistently regardless of your current directory.

---

# Difference Between `git add .` and `git add -A`

Imagine:

```text
backend/

src/
config/
README.md
```

You're inside:

```text
backend/src
```

Now run:

```bash
git add .
```

It stages changes **only under `src/`**.

But:

```bash
git add -A
```

Stages changes from the **whole repository**, including `config/` and `README.md`.

> **Recommendation:** If you're at the project root, both often behave similarly. In large repositories, `git add -A` is a safer choice when you truly want every change.

---

# Stage Modified Files Only

```bash
git add -u
```

Stages:

- Modified files
    
- Deleted files
    

Does **not** stage new untracked files.

Example:

```text
Modified:

app.js

Deleted:

auth.js

New:

payment.js
```

After:

```bash
git add -u
```

Status:

```text
Staged:

app.js
auth.js

Still untracked:

payment.js
```

---

# Stage a Specific File Type

Stage all JavaScript files:

```bash
git add *.js
```

Stage Markdown files:

```bash
git add *.md
```

Useful for small projects.

---

# Stage Using Wildcards

Example:

```bash
git add src/controllers/*.js
```

Stages every JavaScript file inside the `controllers` directory.

---

# What Actually Happens?

Suppose:

```javascript
const PORT = 3000;
```

You run:

```bash
git add app.js
```

Git stores the **current snapshot** of the file in the **Staging Area**.

Now edit it again:

```javascript
const PORT = 5000;
```

Status:

```text
MM app.js
```

Meaning:

- First version is staged.
    
- Second version exists only in your working directory.
    

Git tracks both.

---

# Partial Staging

This is one of Git's most powerful features.

Imagine you changed:

- Login bug
    
- Authentication
    
- Database code
    

All inside one file.

You only want to commit the login fix.

Use:

```bash
git add -p
```

Git shows each change (called a **hunk**) separately:

```text
Stage this hunk?

y = yes
n = no
q = quit
```

You decide exactly which changes to stage.

Professional developers use this frequently.

---

# Interactive Add

```bash
git add -i
```

This opens an interactive menu where you can:

- Stage files
    
- Unstage files
    
- Review changes
    
- Stage patches
    

It's less common today, but useful to know.

---

# Verify Before Committing

Always run:

```bash
git status
```

Example:

```text
Changes to be committed:

modified: app.js

Changes not staged:

modified: auth.js
```

Now you know exactly what will be committed.

---

# Backend Example

Imagine you're working on an authentication API.

Changed files:

```text
src/auth.js
src/user.js
README.md
package-lock.json
```

You only want to commit the authentication feature.

```bash
git add src/auth.js
git add src/user.js
```

Commit:

```bash
git commit -m "Add JWT authentication"
```

`README.md` and `package-lock.json` stay out of this commit.

This creates a clean, focused commit history.

---

# Common Mistakes

## Mistake 1

Using:

```bash
git add .
```

without checking what changed.

Always review first:

```bash
git status
```

---

## Mistake 2

Forgetting to stage a modified file.

Result:

The commit doesn't include your latest changes.

---

## Mistake 3

Staging unrelated files together.

Bad example:

```text
JWT authentication

+
README update

+
CSS fixes

+
Docker changes
```

Keep commits focused on one logical change.

---

# Best Practices

- Check `git status` before and after `git add`.
    
- Stage only related changes together.
    
- Use `git add -p` to create clean commits.
    
- Prefer several small commits over one huge commit.
    
- Review what is staged before committing.

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git add file`|Stage one file|
|`git add file1 file2`|Stage multiple files|
|`git add .`|Stage everything in the current directory|
|`git add -A`|Stage all changes in the repository|
|`git add -u`|Stage modified and deleted files only|
|`git add *.js`|Stage all JavaScript files|
|`git add src/`|Stage an entire directory|
|`git add -p`|Partially stage changes|
|`git add -i`|Interactive staging|
