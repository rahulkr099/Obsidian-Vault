# Why Do We Merge?

Suppose you're building a backend API.

On `main`:

```text
Express Server
```

You create a new branch:

```text
feature/auth
```

After a few hours:

```text
JWT Authentication

↓

Login Endpoint

↓

Middleware
```

Now the feature is complete.

You want those changes in `main`.

That's called **merging**.

---

# Before Merge

Imagine this history:

```text
A

↓

B ← main
 \
  \
   C

↓

D ← feature/auth
```

`feature/auth` has two new commits.

`main` doesn't.

---

# Merge Command

First switch to the branch that should receive the changes.

Usually that's `main`.

```bash
git switch main
```

Then merge:

```bash
git merge feature/auth
```

Meaning:

> "Take everything from `feature/auth` and integrate it into `main`."

---

# Fast-Forward Merge

The simplest merge.

History:

```text
A

↓

B ← main
 \
  \
   C

↓

D ← feature/auth
```

Nothing has changed on `main`.

Git simply moves `main` forward.

Result:

```text
A

↓

B

↓

C

↓

D ← main
      ↑
feature/auth
```

No merge commit is created.

Git just advances the branch pointer.

---

Feature:


After merge:

```text

D
```

A perfectly straight history.

# Example

Create a branch:

```bash
git switch -c feature/login
```

Make some commits.

Return:

```bash
git switch main
```

Merge:

```bash
git merge feature/login
```

Git output:

```text
Updating 8f62aa0..4d9bc82

Fast-forward

src/auth.js

README.md
```

Git recognized that a simple pointer move was enough.

---

# Three-Way Merge

Now imagine something different.

Both branches changed.

```text
        C ← main
       /
A

↓

B
       \
        D

↓

E ← feature/auth
```

Both branches have unique commits.

Git cannot simply move a pointer.

It must combine both histories.

---

# Merge Result

```text
        C
       /
A

↓

B
       \
        D

↓

E
       \
        \
         M ← Merge Commit
```

Git creates a new commit.

This is called a **merge commit**.

---

# What Is a Merge Commit?

A merge commit has:

- Two parents
    
- One combined project snapshot
    

Unlike a normal commit:

```text
Commit

↓

One Parent
```

A merge commit:

```text
Merge Commit

↙        ↘

Parent 1  Parent 2
```

This records exactly where the two development histories came together.

---

# Git Decides Automatically

Git compares:

- Common ancestor
    
- Current branch
    
- Feature branch
    

Then calculates:

> "What changed?"

Most merges happen automatically.

# Viewing Merge History

Run:

```bash
git log --graph --oneline --decorate
```

Example:

```text
*   a9c74d2 Merge branch 'feature/auth'
|\
| * d8f41aa Add JWT middleware
| * 1a2bcde Add login route
* | 5d8b912 Add logging middleware
|/
* 8f62aa0 Initial commit
```

Notice the graph.

This is why `git log --graph` is so useful.

---

# Default Merge Message

Git usually creates:

```text
Merge branch 'feature/auth'
```

You can edit it.

Or specify one:

```bash
git merge feature/auth -m "Merge authentication feature"
```

---

# No Fast-Forward

Sometimes teams always want merge commits.

Even when unnecessary.

Use:

```bash
git merge --no-ff feature/auth
```

History:

Instead of:

```text
A

↓

B

↓

C

↓

D
```

You get:

```text
A

↓

B
 \
  \
   C

↓

D
 \
  \
   M
```

Why?

Because the merge commit records:

> "This entire feature was merged here."

Many companies prefer this for major features.

---

# Fast-Forward vs No Fast-Forward

Fast-forward:

```text
A

↓

B

↓

C

↓

D
```

Simple.

Linear.

---

No Fast-Forward:

```text
A

↓

B
 \
  \
   C

↓

D
 \
  \
   M
```

Shows feature boundaries.

---

# Delete the Feature Branch

After merging:

```bash
git branch -d feature/auth
```

The commits remain.

Only the branch pointer is removed.

# Common Mistakes

## Mistake 1

Trying to merge while on the wrong branch.

Bad:

```bash
git switch feature/auth

git merge main
```

Usually you want:

```bash
git switch main

git merge feature/auth
```

Always ask:

> **Which branch should receive the changes?**

---

## Mistake 2

Forgetting to pull the latest changes before merging.

A common workflow is:

```bash
git switch main
git pull
git merge feature/auth
```

This reduces surprises.

---

## Mistake 3

Keeping merged branches forever.

Delete them:

```bash
git branch -d feature/auth
```

---

# Best Practices

- Merge only completed, tested work.
    
- Merge into `main`, not the other way around (unless you have a specific workflow).
    
- Delete merged feature branches.
    
- Use descriptive feature branch names.
    
- Review changes before merging.

## Professional Tip

There are three major ways teams integrate code:

1. **Merge commits** (`git merge`) — preserves branch history.
    
2. **Rebasing** (`git rebase`) — creates a cleaner, linear history.
    
3. **Squash merging** — combines an entire feature branch into a single commit.
    

Understanding when to use each approach is a key skill for backend engineers.
