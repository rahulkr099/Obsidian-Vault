# Module 3 — Branching

# Lesson 14 — Merge Conflicts: Understanding and Resolving Them

Many beginners fear merge conflicts.

Professional developers?

They expect them.

A merge conflict **does not mean Git is broken**.

It simply means:

> **Git doesn't know which change is correct, so it's asking you to decide.**

Learning to resolve conflicts confidently is one of the most important Git skills for a backend engineer.

# What is a Merge Conflict?

Imagine two developers editing the same line.

Original:

```javascript
const PORT = 3000;
```

Developer A changes it to:

```javascript
const PORT = 5000;
```

Developer B changes it to:

```javascript
const PORT = process.env.PORT;
```

Now Git has a problem.

Which version should it keep?

Git cannot safely guess.

So it creates a **merge conflict**.

---

# When Do Conflicts Happen?

Conflicts commonly occur when:

- Two developers edit the same line.
    
- One developer deletes a file while another edits it.
    
- Two branches rename the same file differently.
    
- The same configuration file is modified in incompatible ways.
    

Examples:

- `package.json`
    
- `package-lock.json`
    
- `docker-compose.yml`
    
- `.env.example`
    
- `README.md`
    

These files often change frequently.

---

# A Conflict Example

Start with:

```javascript
function login() {
    return true;
}
```

### Branch: `feature/auth`

```javascript
function login() {
    return verifyJWT();
}
```

### Branch: `main`

```javascript
function login() {
    return validatePassword();
}
```

Now merge:

```bash
git switch main
git merge feature/auth
```

Git reports:

```text
Auto-merging auth.js
CONFLICT (content): Merge conflict in auth.js
Automatic merge failed; fix conflicts and then commit the result.
```

Git has stopped the merge and is waiting for you.

---

# Check the Repository Status

Run:

```bash
git status
```

Example:

```text
On branch main

You have unmerged paths.

Unmerged paths:

both modified: auth.js
```

Git clearly identifies the conflicting file.

---

# Open the File

Git inserts conflict markers:

```text
<<<<<<< HEAD
return validatePassword();
=======
return verifyJWT();
>>>>>>> feature/auth
```

Let's understand them.

---

# Understanding Conflict Markers

```text
<<<<<<< HEAD
```

This is the version from your current branch (`main`).

---

```text
=======
```

Separator.

---

```text
>>>>>>> feature/auth
```

This is the incoming version from the branch being merged.

---

# Visual Representation

```text
Current Branch

↓

<<<<<<< HEAD

Current Code

=======

Incoming Code

>>>>>>> feature/auth
```

Your job is to decide the final version.

---

# Resolve the Conflict

Maybe both changes are needed.

Edit the file:

```javascript
function login() {
    validatePassword();
    return verifyJWT();
}
```

Remove all conflict markers:

- `<<<<<<<`
    
- `=======`
    
- `>>>>>>>`
    

Save the file.

---

# Mark the Conflict as Resolved

After editing:

```bash
git add auth.js
```

This tells Git:

> "I've resolved the conflict."

Check:

```bash
git status
```

You should now see:

```text
All conflicts fixed but you are still merging.
```

---

# Finish the Merge

Commit:

```bash
git commit
```

Git opens your editor with a default message:

```text
Merge branch 'feature/auth'
```

Save and quit.

Merge complete.

---

# Abort a Merge

Suppose the merge becomes too messy.

You want to start over.

Run:

```bash
git merge --abort
```

Git returns the repository to the state before the merge started.

This only works if the merge is still in progress.

# Conflict Example: Deleted vs Modified

`main`:

Deletes:

```text
old-auth.js
```

`feature/auth`:

Edits:

```text
old-auth.js
```

Git reports:

```text
CONFLICT (modify/delete)
```

You decide:

- Keep the file
    
- Or remove it
    

Then:

```bash
git add old-auth.js
```

or

```bash
git rm old-auth.js
```

Complete the merge.

---

# Conflict Example: Rename

`main`

```text
auth.js → authentication.js
```

`feature/auth`

```text
auth.js → login.js
```

Git cannot decide the final filename.

You choose the correct name manually.

---

# Binary File Conflicts

Suppose two developers edit:

```text
logo.png
```

Git cannot merge images.

You'll choose one version or replace it with a new file.

---

# Real Backend Example

Suppose:

`main`

```javascript
app.use(express.json());
```

Feature branch:

```javascript
app.use(cookieParser());
```

Meanwhile another developer changes:

```javascript
app.use(express.urlencoded());
```

Git may ask you to combine them:

```javascript
app.use(express.json());
app.use(express.urlencoded());
app.use(cookieParser());
```

# Avoiding Conflicts

## Pull Frequently

Instead of working for two weeks:

```bash
git pull
```

every day.

This reduces divergence.

---

## Keep Branches Small

Better:

```text
Feature

↓

3 commits

↓

Merge
```

Than:

```text
Feature

↓

150 commits

↓

3 months

↓

Merge
```

---

## Communicate

If your teammate is rewriting:

```text
auth.js
```

Avoid making large unrelated edits to the same file without coordination.

---

## One Feature Per Branch

Avoid:

```text
Authentication

+

Payments

+

Docker

+

Tests
```

Keep branches focused.

---

# Common Mistakes

## Mistake 1

Deleting conflict markers incorrectly.

Bad:

```text
<<<<<<<
```

left inside the file.

Always remove every marker.

---

## Mistake 2

Running:

```bash
git add .
```

before checking the resolved file.

Review your changes first.

---

## Mistake 3

Panic.

Most conflicts affect only a few lines.

Read them carefully.

---

# Best Practices

- Read the conflict before editing.
    
- Understand both versions.
    
- Keep the correct code, not just one side automatically.
    
- Test the application after resolving conflicts.
    
- Commit immediately after a successful resolution.

# Professional Tips

### 1. Use a Merge Tool

Git can launch graphical merge tools:

```bash
git mergetool
```

Popular tools include:

- VS Code
    
- Meld
    
- KDiff3
    
- Beyond Compare
    

These provide side-by-side comparisons, making conflicts easier to resolve than editing markers manually.

---

### 2. Enable `rerere`

One of Git's lesser-known but powerful features is **reuse recorded resolution**.

```bash
git config --global rerere.enabled true
```

If you resolve the **same conflict again later**, Git can automatically reuse your previous resolution. This is especially useful in long-lived feature branches.

---

### 3. Never Rush a Conflict Resolution

A merge conflict is not just a Git problem—it can introduce application bugs if resolved incorrectly.

After resolving conflicts:

1. Run your tests.
    
2. Start the application.
    
3. Verify the affected feature works as expected.
    

For backend projects, this might mean:

```bash
npm test
```

or

```bash
npm run dev
```

and testing the affected API endpoints.
