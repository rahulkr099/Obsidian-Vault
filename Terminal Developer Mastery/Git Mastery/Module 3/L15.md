# Module 3 — Branching

# Lesson 15 — Mastering `git rebase`

Congratulations! You've reached one of the most advanced and valuable Git topics.

`git rebase` is often considered "advanced Git," but once you understand it, you'll see that it's simply another way to integrate changes.

Many companies use rebasing every day to keep their Git history clean and easy to read.

> **Key Idea**
> 
> **Merge preserves history.**
> 
> **Rebase rewrites history.**

Understanding **when to use each** is far more important than memorizing commands.

# The Problem

Imagine this history:

```text
        C
       /
A

↓

B
       \
        D

↓

E ← feature/auth
```

You want to integrate `feature/auth` into `main`.

There are two choices:

1. Merge
    
2. Rebase
    

---

# Option 1 — Merge

```bash
git switch main
git merge feature/auth
```

Result:

```text
        C
       /
A

↓

B
       \
        D

↓

E
       \
        \
         M
```

History is preserved exactly as it happened.

---

# Option 2 — Rebase

```bash
git switch feature/auth

git rebase main
```

Git says:

> "Pretend your feature branch started from the latest `main`."

Result:

```text
A

↓

B

↓

C

↓

D'

↓

E'
```

Notice:

`D` and `E` became:

```text
D'

E'
```

These are **new commits**.

Git replayed your work on top of `main`.

---

# Why the Apostrophe (`'`)?

Rebased commits are **new commits**.

Even if the code is identical, the:

- Commit hash
    
- Parent commit
    
- Timestamp (in some cases)
    

change.

Original:

```text
D

↓

E
```

Rebased:

```text
D'

↓

E'
```

Different hashes.

# Why Teams Like Rebase

Suppose 20 developers create feature branches.

Merge history:

```text
 \

  \

   M

  /

 /

 \

  \

   M

 /

```

After months:

The graph becomes complex.

Rebase produces:

```text
A

↓

B

↓

C

↓

D

↓

E

↓

F

↓

G
```

One straight line.

Much easier to read.

---

# Example

Create:

```bash
git switch -c feature/login
```

Make:

```text
Commit A

Commit B

Commit C
```

Meanwhile:

`main` receives:

```text
Commit X

Commit Y
```

Now:

```bash
git switch feature/login

git rebase main
```

Git moves:

```text
Commit A

Commit B

Commit C
```

on top of:

```text
Commit X

Commit Y
```

---

# Finish Integration

After rebasing:

```bash
git switch main

git merge feature/login
```

Since the history is now linear, Git usually performs a **fast-forward merge**.

---

# Merge vs Rebase

|Merge|Rebase|
|---|---|
|Preserves history|Rewrites history|
|Creates merge commits|Creates a linear history|
|Safer for shared branches|Better for local cleanup|
|Easier to understand collaboration|Easier to read long-term history|

---

# Interactive Rebase

One of Git's most powerful tools:

```bash
git rebase -i HEAD~3
```

Meaning:

> "Interactively edit the last 3 commits."

Git opens your editor:

```text
pick a1b2c3 Add login route
pick d4e5f6 Fix typo
pick 7g8h9i Add tests
```

Now you can change the commands.

---

# Interactive Commands

|Command|Meaning|
|---|---|
|`pick`|Keep commit|
|`reword`|Change commit message|
|`edit`|Stop and modify commit|
|`squash`|Combine with previous commit|
|`fixup`|Combine and discard message|
|`drop`|Remove commit|

---

# Squashing Commits

Suppose history:

```text
Add login API

↓

Fix typo

↓

Fix typo again

↓

Remove debug log
```

Not ideal.

Interactive rebase:

```text
pick Add login API

squash Fix typo

squash Fix typo again

squash Remove debug log
```

Result:

```text
Add login API
```

One clean commit.

This is extremely common before opening a pull request.

---

# Reword Commit Messages

Suppose:

```text
Update
```

Interactive rebase:

```text
reword Update
```

Git opens the editor.

Change to:

```text
Add JWT authentication middleware
```

Much better.

---

# Drop a Commit

Suppose you accidentally committed:

```text
Temporary debug logs
```

Interactive rebase:

```text
drop Temporary debug logs
```

The commit disappears from history.

Only do this for local, unpublished commits.

---

# Edit a Commit

Example:

```text
edit Add login API
```

Git pauses.

You modify files.

Then:

```bash
git add .

git commit --amend

git rebase --continue
```

Useful when you forgot to include a file in a commit.

---

# Rebase Conflicts

Rebase can also produce conflicts.

Git stops:

```text
Conflict

↓

Resolve

↓

git add

↓

git rebase --continue
```

If necessary:

```bash
git rebase --abort
```

returns to the original state.

---

# Golden Rule of Rebase

> **Never rebase commits that have already been shared with others.**

Why?

Because rebasing changes commit hashes.

Example:

You push:

```text
A

↓

B

↓

C
```

Your teammate pulls.

Then you rebase:

```text
A

↓

B'

↓

C'
```

Now the histories no longer match.

This creates confusion and extra work for everyone.

---

# Safe Situations for Rebase

✔ Before pushing

✔ On your own feature branch

✔ Cleaning up commits

✔ Updating a feature branch with the latest `main`

---

# Dangerous Situations

❌ Rebasing `main` after it's been pushed.

❌ Rebasing shared branches.

❌ Rebasing commits teammates already depend on.

---

# Backend Workflow

Morning:

```bash
git switch feature/payment
```

Work.

Commit.

Meanwhile:

`main` receives:

```text
Database migration

Logging

Bug fixes
```

Update your feature:

```bash
git fetch origin
git rebase origin/main
```

Resolve conflicts if any.

Continue development.

When ready:

```bash
git switch main

git merge feature/payment
```

Usually a fast-forward merge.

---

# Common Mistakes

## Mistake 1

Rebasing public history.

This forces teammates to reconcile rewritten commits.

---

## Mistake 2

Thinking rebase deletes commits.

It doesn't.

It recreates them with new parents.

---

## Mistake 3

Using rebase when merge is simpler.

Sometimes preserving the real development history is more valuable.

---

# Best Practices

- Rebase your own feature branches.
    
- Merge shared branches.
    
- Squash small "fix typo" commits before creating a pull request.
    
- Use interactive rebase to clean up history.
    
- Avoid rebasing published history.
    

---

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git rebase main`|Replay current branch onto `main`|
|`git rebase -i HEAD~3`|Interactive rebase|
|`git rebase --continue`|Continue after resolving conflicts|
|`git rebase --abort`|Cancel the rebase|
|`git commit --amend`|Modify the most recent commit|

# Professional Tips

## 1. Rebase Before Opening a Pull Request

A common workflow is:

```bash
git fetch origin
git rebase origin/main
```

This ensures your feature branch is based on the latest `main`, reducing merge conflicts during code review.

---

## 2. Squash "Noise" Commits

During development, it's normal to create commits like:

```text
Fix typo
Oops
Debug
Try again
```

Before sharing your work, use an interactive rebase to turn them into a few meaningful commits that clearly tell the story of the feature.

---

## 3. A Common Team Workflow

Many backend teams follow a pattern like this:

```text
Create feature branch
        ↓
Develop
        ↓
Commit frequently
        ↓
Rebase onto latest main
        ↓
Run tests
        ↓
Open Pull Request
        ↓
Merge into main
        ↓
Delete feature branch
```

This keeps both the codebase and the Git history organized.
