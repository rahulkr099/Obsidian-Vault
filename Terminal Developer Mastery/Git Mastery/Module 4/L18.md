# Module 4 — GitHub Essentials

# Lesson 18 — `git clone`, `git fetch`, and `git pull`

So far you've learned how to **push** your work to GitHub.

Now it's time to learn how to **download** work from GitHub.

This is something backend engineers do many times every day.

Whether you're joining a new project, updating your branch, or reviewing a teammate's work, you'll use one of these commands:

- `git clone`
    
- `git fetch`
    
- `git pull`
    

Although they seem similar, **they do very different things**.

- How to clone a repository

# The Big Picture

Imagine GitHub as the central server.

```text
        GitHub
           ▲
           │
     push  │  fetch/pull
           │
           ▼
     Your Computer
```

- **Push** → Upload your work
    
- **Fetch** → Download updates (without changing your work)
    
- **Pull** → Download updates and integrate them
    
- **Clone** → Download an entire repository for the first time
    

---

# `git clone`

Suppose your teammate created a project.

Repository:

```text
inventory-api
```

You don't have it yet.

Clone it:

```bash
git clone git@github.com:company/inventory-api.git
```

Git creates:

```text
inventory-api/

├── .git
├── src/
├── package.json
├── README.md
```

You now have:

- Entire commit history
    
- All branches (references)
    
- Repository configuration
    
- Remote named `origin`
    

---

# What Happens During Clone?

Git performs several steps automatically:

```text
Download repository

↓

Create directory

↓

Initialize Git

↓

Configure origin

↓

Checkout default branch
```

One command does all of this.

---

# Clone into a Different Folder

Normally:

```bash
git clone git@github.com:user/project.git
```

creates:

```text
project/
```

You can choose another name:

```bash
git clone git@github.com:user/project.git backend-api
```

Result:

```text
backend-api/
```

---

# Verify the Clone

After cloning:

```bash
cd inventory-api

git remote -v
```

Output:

```text
origin  git@github.com:company/inventory-api.git (fetch)
origin  git@github.com:company/inventory-api.git (push)
```

The remote is already configured.

---

# What is `git fetch`?

Suppose another developer pushes new commits.

Your local repository is now behind GitHub.

Run:

```bash
git fetch
```

Git downloads:

- New commits
    
- New branches
    
- New tags (as needed)
    

But it **does not** change your current branch.

---

# Visual Example

Before:

```text
Local:

main

↓

A

↓

B
```

GitHub:

```text
A

↓

B

↓

C
```

Run:

```bash
git fetch
```

Now:

```text
Local main

↓

A

↓

B

origin/main

↓

A

↓

B

↓

C
```

Notice:

Your working files **did not change**.

Only the remote-tracking branch (`origin/main`) was updated.

---

# Check What Changed

After fetching:

```bash
git log --oneline main..origin/main
```

Example:

```text
8c9f123 Add rate limiter
4a1de56 Improve logging
```

This shows commits that exist on the remote but not locally.

---

# Compare Branches

```bash
git diff main origin/main
```

You can inspect changes before applying them.

This is why many experienced developers prefer `fetch` first.

---

# What is `git pull`?

`git pull` is actually two commands combined:

```text
git fetch

+

git merge
```

When you run:

```bash
git pull
```

Git:

1. Downloads new commits.
    
2. Merges them into your current branch.
    

---

# Visual Example

Before:

```text
Local:

A

↓

B
```

GitHub:

```text
A

↓

B

↓

C
```

Run:

```bash
git pull
```

Result:

```text
A

↓

B

↓

C
```

Your local branch is now updated.

---

# Pull with Rebase

Some teams prefer:

```bash
git pull --rebase
```

Instead of:

```text
Fetch

↓

Merge
```

Git performs:

```text
Fetch

↓

Rebase
```

This creates a cleaner, more linear history.

We'll revisit this in advanced team workflows.

---

# Fetch vs Pull

|`git fetch`|`git pull`|
|---|---|
|Downloads changes|Downloads and integrates changes|
|Safe inspection|Immediate update|
|Doesn't modify working tree|Changes current branch|
|Good for reviewing|Good when you're ready to update|

---

# Which Should You Use?

Suppose you're working on a critical payment API.

Instead of immediately pulling:

```bash
git fetch
```

Inspect:

```bash
git log --oneline HEAD..origin/main
git diff HEAD origin/main
```

If everything looks good:

```bash
git merge origin/main
```

or

```bash
git rebase origin/main
```

This gives you more control.

---

# Fetch All Remotes

If you have multiple remotes:

```bash
git fetch --all
```

Git downloads updates from every configured remote.

---

# Fetch Pruned Branches

Sometimes remote branches are deleted.

Clean up stale remote-tracking branches:

```bash
git fetch --prune
```

This removes references like:

```text
origin/feature/old-feature
```

when they no longer exist on the server.

---

# Updating a Feature Branch

Suppose you're on:

```text
feature/payment
```

Latest changes exist on:

```text
origin/main
```

Workflow:

```bash
git fetch origin
git rebase origin/main
```

or:

```bash
git merge origin/main
```

Both are valid depending on your team's workflow.

---

# Common Backend Workflow

Start the day:

```bash
git switch main
git pull
```

Create a feature branch:

```bash
git switch -c feature/orders
```

Work.

Commit.

Push.

Before opening a Pull Request:

```bash
git fetch origin
git rebase origin/main
```

Resolve conflicts if needed.

Push updated branch.

---

# Common Mistakes

## Mistake 1

Running:

```bash
git pull
```

without checking for local changes.

If you have uncommitted work:

```bash
git status
```

first.

---

## Mistake 2

Thinking:

```bash
git fetch
```

updates your files.

It doesn't.

It only updates remote-tracking references.

---

## Mistake 3

Cloning repeatedly.

Clone a repository once.

After that:

```bash
git pull
```

or

```bash
git fetch
```

to stay updated.

# Useful Commands

View remotes:

```bash
git remote -v
```

Fetch:

```bash
git fetch
```

Fetch from one remote:

```bash
git fetch origin
```

Pull:

```bash
git pull
```

Pull with rebase:

```bash
git pull --rebase
```

Clone:

```bash
git clone <repository-url>
```

---

# Best Practices

- Clone only once.
    
- Run `git status` before pulling.
    
- Use `git fetch` when you want to inspect changes first.
    
- Keep your local `main` branch updated.
    
- Rebase feature branches onto the latest `main` when appropriate.
    

---

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git clone <url>`|Download a repository for the first time|
|`git fetch`|Download updates without modifying your branch|
|`git fetch --all`|Fetch from all remotes|
|`git fetch --prune`|Remove stale remote-tracking branches|
|`git pull`|Fetch and merge|
|`git pull --rebase`|Fetch and rebase|

# Professional Tips

## 1. Start Every Workday Like This

Many backend engineers begin with:

```bash
git switch main
git pull
git switch feature/current-task
git rebase main
```

This ensures your feature branch starts from the latest codebase.

---

## 2. Review Before Integrating

For important production branches, prefer:

```bash
git fetch
git log --oneline HEAD..origin/main
git diff HEAD origin/main
```

instead of immediately running `git pull`.

---

## 3. Remember the Mental Model

Think of these commands as three different actions:

```text
Clone
│
├── First time getting the repository
│
Fetch
│
├── Download updates safely
│
Pull
│
└── Download and apply updates
```

If you keep this distinction clear, you'll avoid many common Git synchronization mistakes.
