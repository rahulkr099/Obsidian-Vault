# What is a Pull Request?

A **Pull Request (PR)** is a request to merge one branch into another.

Example:

```text
feature/login

↓

Pull Request

↓

main
```

It says:

> "I've completed this feature. Please review it before merging."

A PR is **not** a Git command.

It's a **GitHub feature** built on top of Git.

---

# Why Not Push Directly to `main`?

Imagine a team of five backend engineers.

Without Pull Requests:

```text
Developer A

↓

Push to main

↓

Production
```

Anyone can accidentally:

- Break authentication
    
- Delete APIs
    
- Introduce bugs
    
- Leak secrets
    

---

Professional teams usually protect `main`.

Instead:

```text
Feature Branch

↓

Pull Request

↓

Review

↓

Approval

↓

Merge

↓

main
```

# Creating a Pull Request

On GitHub:

Choose:

```text

main
```

and

```text

```

Meaning:

> Merge **feature/jwt-auth** into **main**.

# Good PR Description

Example:

```text
## Summary

Adds JWT authentication.

## Changes

- Login endpoint
- JWT middleware
- Token validation
- Unit tests

## Testing

- npm test
- Manual API testing
```

A good description helps reviewers understand the context before reading code.

# Code Review

Your teammate opens the PR.

They review:

```text
Files Changed

↓

Comments

↓

Suggestions
```

Example:

```javascript
const token = req.headers.authorization;
```

Reviewer:

> Check for a missing Authorization header before accessing it.

---

# Review Comments

Comments can be:

### General

```text
Authentication looks good.
```

---

### Line-specific

```javascript
const user = await User.findById(id);
```

Comment:

> Handle the case where `user` is `null`.

These comments are attached directly to the relevant line of code.

---

# Responding to Feedback

Suppose the reviewer requests changes.

You fix the issue:

```bash
git add .
git commit -m "Handle missing authorization header"
git push
```

Notice:

You **do not** create a new Pull Request.

The existing PR automatically updates with the new commit.

# Merge Strategies

GitHub offers several merge options.

## 1. Create a Merge Commit

Equivalent to:

```bash
git merge
```

History:

```text
Feature

↓

Merge Commit

↓

main
```

Preserves branch history.

---

## 2. Squash and Merge

Suppose your feature has:

```text
Add login

↓

Fix typo

↓

Fix typo

↓

Remove debug

↓

Fix lint
```

GitHub combines them into:

```text
Add JWT authentication
```

One clean commit.

This is very popular for feature branches.

---

## 3. Rebase and Merge

Equivalent to:

```bash
git rebase
```

Creates a clean, linear history.

No merge commit.

---

# Which Merge Strategy Should You Choose?

|Strategy|Best For|
|---|---|
|Merge Commit|Preserve branch history|
|Squash Merge|Clean feature history|
|Rebase Merge|Linear commit history|

Many startups use **Squash and Merge** for feature branches.

---

# Branch Protection

Professional teams often protect `main`.

Rules might include:

- No direct pushes
    
- Pull Request required
    
- Passing CI required
    
- At least one approval
    
- No unresolved review comments
    

This greatly reduces accidental mistakes.

# Common Mistakes

## Mistake 1

Creating huge Pull Requests.

Bad:

```text
Authentication

Payments

Docker

Tests

Refactoring

Documentation

All in one PR
```

Instead:

One feature.

One Pull Request.

---

## Mistake 2

Ignoring review comments.

Reviews improve code quality.

Respond thoughtfully, even if you disagree.

---

## Mistake 3

Merging without reading CI failures.

Always check:

```text
✅ All checks passed
```

before merging.

---

## Mistake 4

Keeping Pull Requests open for weeks.

Large, stale PRs are difficult to review.

Aim for small, focused changes.

---

# Best Practices

- Keep PRs under ~300–500 changed lines when practical.
    
- Write descriptive titles.
    
- Explain **why** the change was made, not just **what** changed.
    
- Respond to reviewer comments promptly.
    
- Keep commits meaningful (or squash before merging if that's your team's convention).
    
- Delete feature branches after merging.
    

---

# Pull Request Checklist

Before opening a PR, ask yourself:

- ✅ Does the project build?
    
- ✅ Do all tests pass?
    
- ✅ Did I remove debug code?
    
- ✅ Is my branch up to date?
    
- ✅ Is the PR description clear?
    
- ✅ Does the feature work as expected?

# Professional Tips

## 1. Think of a PR as a Conversation

A Pull Request is not just code—it's where developers discuss design decisions, suggest improvements, and document the reasoning behind changes.

---

## 2. Review Your Own PR First

Before asking others to review:

- Read the "Files changed" tab.
    
- Look for accidental debug statements.
    
- Check formatting.
    
- Confirm only the intended files are included.
    

This catches many issues before anyone else sees them.

---

## 3. Small PRs Get Reviewed Faster

Compare these two scenarios:

**Good:**

```text
Add user avatar upload
```

(200 lines changed)

**Poor:**

```text
Authentication + Payments + Refactor + Docker + Docs
```

(5,000 lines changed)

Small, focused PRs are easier to understand, review, test, and merge.
