# What is a Fork?

A **fork** is your **own copy** of someone else's GitHub repository.

Example:

Original repository:

```text
open-source/backend-api
```

You click:

```text
Fork
```

GitHub creates:

```text
rahul/backend-api
```

Notice:

The repository now belongs to **you**, even though it started from someone else's code.

---

# Why Fork Instead of Directly Pushing?

Suppose the original repository belongs to a company.

```text
company/backend-api
```

You don't have write permission.

You cannot:

```bash
git push origin main
```

GitHub rejects it.

Instead:

```text
Fork

↓

Your Copy

↓

Push There

↓

Open Pull Request
```

# Fork vs Clone

Many beginners confuse these.

## Fork

Happens on GitHub.

Creates:

```text
GitHub Repository

↓

GitHub Repository
```

---

## Clone

Happens on your computer.

Creates:

```text
GitHub Repository

↓

Local Repository
```

---

# Together

Typical workflow:

```text
Original Repository

↓

Fork

↓

Your GitHub Repository

↓

Clone

↓

Local Computer
```

Both operations are required.

# Example

Original:

```text
expressjs/express
```

Fork:

```text
rahul/express
```

Clone:

```bash
git clone git@github.com:rahul/express.git
```

Now you can edit safely.

---

# The Two Remotes

After cloning your fork:

```bash
git remote -v
```

Initially:

```text
origin

↓

git@github.com:rahul/express.git
```

Only your fork exists.

---

# Add the Original Repository

Add another remote:

```bash
git remote add upstream git@github.com:expressjs/express.git
```

Now:

```bash
git remote -v
```

Output:

```text
origin    git@github.com:rahul/express.git
upstream  git@github.com:expressjs/express.git
```

---

# Understanding the Names

```text
origin

↓

Your Fork
```

```text
upstream

↓

Original Repository
```

This naming convention is used almost everywhere in open source.

---

# Why Do We Need `upstream`?

The original project continues to evolve.

New commits:

```text
expressjs/express

↓

100 new commits
```

Your fork becomes outdated.

You need to synchronize.

---

# Fetch Upstream Changes

```bash
git fetch upstream
```

Git downloads:

```text
upstream/main
```

without changing your work.

---

# Update Your Local `main`

Switch:

```bash
git switch main
```

Merge:

```bash
git merge upstream/main
```

Or rebase:

```bash
git rebase upstream/main
```

Now your local repository matches the latest upstream.

---

# Update Your Fork

Push:

```bash
git push origin main
```

Now:

```text
Local

↓

Origin

↓

Upstream
```

Everything is synchronized.

# Complete Contribution Workflow

## Step 1

Fork:

```text
company/backend-api
```

↓

```text
rahul/backend-api
```

---

## Step 2

Clone:

```bash
git clone git@github.com:rahul/backend-api.git
```

---

## Step 3

Add upstream:

```bash
git remote add upstream git@github.com:company/backend-api.git
```

---

## Step 4

Create a feature branch:

```bash
git switch -c fix/login-validation
```

Never work directly on `main`.

---

## Step 5

Develop.

Commit.

Example:

```bash
git add .
git commit -m "Fix login validation bug"
```

---

## Step 6

Push:

```bash
git push -u origin fix/login-validation
```

Notice:

Push to:

```text
origin
```

not

```text
upstream
```

---

## Step 7

Open Pull Request

GitHub displays:

```text
Compare & Pull Request
```

Select:

```text
Base Repository

↓

company/backend-api
```

Compare:

```text
fix/login-validation
```

---

## Step 8

Maintainers review.

Possible outcomes:

✅ Approved

❌ Changes requested

💬 Questions

You respond by making additional commits and pushing them to your fork. The Pull Request updates automatically.

---

# Never Push to Upstream

Good:

```bash
git push origin feature/api
```

Bad:

```bash
git push upstream main
```

Normally you won't even have permission.

Even if you do, company policies usually require Pull Requests instead of direct pushes.

---

# Sync Before New Work

Before creating a new feature:

```bash
git fetch upstream

git switch main

git merge upstream/main

git push origin main
```

Then:

```bash
git switch -c feature/new-task
```

Always start from an updated `main`.

# Common Mistakes

## Mistake 1

Working directly on:

```text
main
```

Instead:

```bash
git switch -c feature/issue-42
```

---

## Mistake 2

Never syncing with upstream.

Result:

Your Pull Request contains outdated code and unnecessary conflicts.

---

## Mistake 3

Pushing to upstream.

Always push to:

```text
origin
```

Your fork.

---

## Mistake 4

Making huge Pull Requests.

Instead of:

```text
Authentication

Payments

Docker

Tests

Refactoring
```

Submit one focused change.

---

# Best Practices

- Fork only once.
    
- Keep your fork synchronized with `upstream`.
    
- Create a new branch for every issue.
    
- Keep commits focused and descriptive.
    
- Read the project's contribution guidelines before starting.
    
- Reference the issue number in your PR if requested.

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git clone <fork-url>`|Clone your fork|
|`git remote add upstream <original-url>`|Add original repository|
|`git fetch upstream`|Download upstream updates|
|`git merge upstream/main`|Update local `main`|
|`git push origin main`|Sync your fork|
|`git push -u origin feature/x`|Push a feature branch|
|Open Pull Request|Submit changes to the original project|

# Professional Tips

## 1. Read `CONTRIBUTING.md` First

Most open-source repositories include:

```text
CONTRIBUTING.md
```

It often explains:

- Branch naming
    
- Commit message conventions
    
- Testing requirements
    
- Code style
    
- PR checklist
    

Following it greatly increases the chances that your contribution will be accepted.

---

## 2. Keep Pull Requests Small

Maintainers review many PRs every week.

A focused PR like:

```text
Fix JWT expiration validation
```

is much easier to review than a PR that changes multiple unrelated features.

---

## 3. Stay in Sync with Upstream

Before starting any new contribution, many experienced contributors run:

```bash
git fetch upstream
git switch main
git merge upstream/main
git push origin main
```

This ensures your next feature branch starts from the latest version of the project.
