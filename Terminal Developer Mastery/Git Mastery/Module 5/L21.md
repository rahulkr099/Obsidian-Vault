# What is a Git Tag?

A **tag** is a permanent label attached to a specific commit.

Example:

```text
A

↓

B

↓

C ← v1.0.0

↓

D

↓

E ← main
```

Even if `main` moves forward, `v1.0.0` always points to commit `C`.

---

# Why Use Tags?

Without tags:

```text
Commit:

9f3a2c1
```

Hard to remember.

With tags:

```text
v1.0.0
```

Much easier.

# Lightweight Tags

The simplest kind.

Create:

```bash
git tag v1.0.0
```

Git simply creates a pointer.

Think of it like a bookmark.

---

# Annotated Tags

Professional teams usually use **annotated tags**.

Create:

```bash
git tag -a v1.0.0 -m "First production release"
```

Annotated tags store:

- Tag name
    
- Author
    
- Date
    
- Message
    
- Referenced commit
    

They become part of your project's release history.

---

# List Tags

View all tags:

```bash
git tag
```

Example:

```text
v1.0.0
v1.1.0
v2.0.0
```

---

# Inspect a Tag

```bash
git show v1.0.0
```

Example:

```text
Tag: v1.0.0

Author: Rahul

Date: ...

Message:

First production release
```

You'll also see the commit the tag references.

---

# Tag a Specific Commit

Normally:

```bash
git tag v1.0.0
```

tags the latest commit.

You can tag an older commit:

```bash
git tag v1.0.0 4f29ab8
```

Where:

```text
4f29ab8
```

is the commit hash.

---

# Checkout a Tag

Suppose you need to inspect version 1.0.0.

```bash
git switch --detach v1.0.0
```

Git places you in a **detached HEAD** state.

You're viewing history exactly as it existed for that release.

---

# Detached HEAD

Visualize:

```text
A

↓

B ← v1.0.0

↓

C ← main
```

Checkout:

```text
v1.0.0
```

Now:

```text
HEAD

↓

B
```

You're **not** on a branch.

You're looking at a historical snapshot.

---

# Return to Main

```bash
git switch main
```

---

# Delete a Local Tag

```bash
git tag -d v1.0.0
```

Only the local tag is removed.

---

# Push Tags to GitHub

Pushing commits:

```bash
git push
```

does **not** push tags.

Push one tag:

```bash
git push origin v1.0.0
```

Push all tags:

```bash
git push origin --tags
```

---

# Delete Remote Tags

Delete locally:

```bash
git tag -d v1.0.0
```

Delete remotely:

```bash
git push origin --delete v1.0.0
```

---

# What is a GitHub Release?

A **GitHub Release** is built on top of a Git tag.

Example:

```text
Git Tag

↓

v1.0.0

↓

GitHub Release
```

A release can include:

- Release notes
    
- Downloadable source code
    
- Binary files
    
- Documentation links
    
- Changelog
    

---

# Example Release

```text
Version:

v1.2.0

Title:

Backend API 1.2

Release Notes:

• JWT Refresh Tokens
• Email Verification
• Performance Improvements
• Fixed Login Bug
```

Users immediately understand what's new.

---

# Semantic Versioning (SemVer)

Most backend projects follow:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.5.8
```

---

# PATCH Version

Example:

```text
1.0.0

↓

1.0.1
```

Use for:

- Bug fixes
    
- Documentation corrections
    
- Performance improvements
    

No breaking changes.

---

# MINOR Version

Example:

```text
1.0.0

↓

1.1.0
```

Use for:

- New features
    
- New endpoints
    
- Additional functionality
    

Existing APIs still work.

---

# MAJOR Version

Example:

```text
1.0.0

↓

2.0.0
```

Breaking changes.

Example:

```text
/users

↓

/api/users
```

Existing clients may need updates.

---

# SemVer Examples

|Version|Meaning|
|---|---|
|`1.0.0`|First stable release|
|`1.0.1`|Bug fix|
|`1.1.0`|New feature|
|`1.2.0`|Another feature|
|`2.0.0`|Breaking API change|
|`2.1.0`|New feature after breaking release|
|`2.1.1`|Bug fix|

# Common Mistakes

## Mistake 1

Using tags like:

```text
latest
```

Instead use:

```text
v1.4.0
```

Version numbers are much clearer.

---

## Mistake 2

Forgetting to push tags.

Remember:

```bash
git push
```

doesn't include tags.

---

## Mistake 3

Using lightweight tags for official releases.

Prefer:

```bash
git tag -a
```

for production releases.

---

## Mistake 4

Skipping release notes.

Future teammates (and your future self) will appreciate a clear changelog.

---

# Best Practices

- Use Semantic Versioning.
    
- Prefer annotated tags for releases.
    
- Write meaningful release notes.
    
- Tag only tested, deployable commits.
    
- Keep release names consistent (e.g., `v1.2.0`).

# Professional Tips

## 1. Never Tag Untested Code

A release tag should point to code that has passed:

- Unit tests
    
- Integration tests
    
- Code review
    
- CI checks
    

Treat a tag as a promise that this version is ready.

---

## 2. Automate Releases

Many production projects use GitHub Actions to automatically:

```text
Push Tag
      ↓
Create GitHub Release
      ↓
Run CI
      ↓
Build Docker Image
      ↓
Deploy
```

You'll learn this workflow in the GitHub Actions/CI-CD module.

---

## 3. Keep a Changelog

Many projects maintain a `CHANGELOG.md` like:

```text
## v2.0.0
- Added JWT authentication
- Added search API
- Added categories
- Improved validation

## v1.1.0
- Added pagination
- Fixed login validation
```

This makes it easy for users and teammates to understand what's changed between releases.
