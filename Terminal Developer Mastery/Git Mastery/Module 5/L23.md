# What Does `git push` Do?

Every commit you make is stored locally.

Example:

```text
Laptop

↓

A

↓

B

↓

C
```

GitHub still has:

```text
GitHub

↓

A

↓

B
```

Running:

```bash
git push
```

uploads commit **C**.

Result:

```text
Laptop                GitHub

A                     A
↓                     ↓
B                     B
↓                     ↓
C                     C
```

# What is an Upstream Branch?

Think of it as a default destination.

Without upstream:

Every push needs:

```bash
git push origin main
```

With upstream configured:

```bash
git push
```

Git already knows where to send the commits.

---

# Visualizing Upstream

```text
Local Branch

main

↓

origin/main
```

Git remembers:

> "When I push `main`, send it to `origin/main`."

```bash

```

Example:

```text

```

The part in brackets:

```text

```

shows the configured upstream.



# Pushing a New Branch

Create:

```bash

```

Commit your work.

Push:

```bash

```

Now GitHub contains:


# Why Use `-u`?

Without:

```bash
git push origin feature/profile
```

every push requires:

```bash
git push origin feature/profile
```

With:

```bash
git push -u origin feature/profile
```

future pushes become:

```bash
git push
```

Much easier.

# Push All Branches

Sometimes useful:

```bash

```

This pushes every local branch.

Use with care—it's uncommon in day-to-day work.

# Push Tags

Remember:

```bash
git push
```

does **not** push tags.

Push one tag:

```bash
git push origin v1.0.0
```

Push all:

```bash
git push origin --tags
```

# What Happens if Someone Else Pushes First?

Suppose GitHub now contains:

```text
A

↓

B

↓

C
```

Your local branch:

```text
A

↓

B

↓

D
```

You try:

```bash
git push
```

Git rejects it.

Error:

```text
! [rejected]
```

Why?

Git refuses to overwrite someone else's work.

---

# Fix the Rejection

Update first:

```bash
git pull
```

or

```bash
git fetch
git merge origin/main
```

Resolve any conflicts.

Then:

```bash
git push
```

---

# Force Push

Sometimes after a rebase:

```bash
git rebase main
```

Git history changes.

Normal push fails.

You might think:

```bash
git push --force
```

This works...

but it can overwrite teammates' commits.

---

# Why `--force` Can Be Dangerous

Imagine:

GitHub:

```text
A

↓

B

↓

C
```

Your rewritten history:

```text
A

↓

B'

↓

C'
```

A force push replaces the remote history.

If someone else built work on `C`, their history can be lost.

---

# The Safer Option

Instead of:

```bash
git push --force
```

use:

```bash
git push --force-with-lease
```

This command checks whether the remote branch has changed since your last fetch.

If it has, Git stops the push instead of overwriting newer work.

This is the recommended option after rebasing your own feature branch.

---

# When is Force Push Acceptable?

Usually:

✅ Your own feature branch.

Example:

```text
feature/payment
```

after:

```bash
git rebase
```

Avoid force-pushing:

- `main`
    
- `develop`
    
- Shared branches
    

unless your team has explicitly agreed on the workflow.

# Common Errors

## Error 1

```text
fatal: The current branch has no upstream branch
```

Fix:

```bash
git push -u origin main
```

or for a feature branch:

```bash
git push -u origin feature/profile
```

---

## Error 2

```text
Everything up-to-date
```

Nothing new to push.

Verify:

```bash
git status
```

---

## Error 3

```text
Permission denied (publickey)
```

SSH authentication failed.

Test:

```bash
ssh -T git@github.com
```

---

## Error 4

```text
non-fast-forward
```

Someone else updated the remote.

Pull or fetch the latest changes before pushing again.

---

# Best Practices

- Use `git push -u` the first time you push a branch.
    
- Push small, logical commits frequently.
    
- Never push secrets, API keys, or `.env` files.
    
- Prefer Pull Requests over pushing directly to `main`.
    
- Use `--force-with-lease` instead of `--force` when rewriting your own branch history.

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git push`|Push to the configured upstream|
|`git push origin main`|Push `main` to `origin`|
|`git push -u origin main`|First push and set upstream|
|`git push -u origin feature/login`|Push a new feature branch|
|`git branch -vv`|Show upstream configuration|
|`git branch -r`|List remote branches|
|`git push --all origin`|Push all branches|
|`git push origin --tags`|Push all tags|
|`git push --force-with-lease`|Safely force-push rewritten history|

# Professional Tips

### 1. Push Early, Push Often

Don't wait until you've written thousands of lines of code.

Frequent pushes:

- Back up your work.
    
- Make code reviews easier.
    
- Reduce the risk of losing changes.
    

---

### 2. Feature Branches First

A common professional rule is:

```text
Never develop directly on main.
```

Instead:

```text
main
   ↓
feature/auth
feature/orders
feature/payments
```

Each feature gets its own branch and Pull Request.

---

### 3. Be Careful with Force Pushes

If you need to update a rebased feature branch:

```bash
git push --force-with-lease
```

is almost always the safer choice.

If you're ever unsure whether a branch is shared, **avoid force-pushing** until you've confirmed your team's workflow.
