# The Big Picture

```text
             GitHub
                ▲
                │
       git push │ git fetch / git pull
                │
                ▼
        Your Local Repository
```

- **Push** → Upload your work
    
- **Fetch** → Download changes only
    
- **Pull** → Download **and** integrate changes
    

---

# What is `git fetch`?

`git fetch` downloads the latest information from the remote repository **without changing your current branch**.

Command:

```bash
git fetch
```

Think of it as:

> "Download everything, but don't touch my work yet."

---

# Example

GitHub:

```text
A
↓
B
↓
C
```

Your computer:

```text
A
↓
B
```

Run:

```bash
git fetch
```

Now Git knows:

```text
main

A
↓
B

origin/main

A
↓
B
↓
C
```

Notice:

Your local `main` branch is still at **B**.

Only `origin/main` has moved to **C**.

Your files do **not** change.

---

# What is `origin/main`?

Many beginners think:

```text
main
```

and

```text
origin/main
```

are the same.

They are not.

```text
main
```

Your local branch.

```text
origin/main
```

Git's local record of the remote branch.

After every fetch, Git updates:

```text
origin/main
```

---

# Inspect Remote Changes

After fetching:

```bash
git log --oneline HEAD..origin/main
```

Example:

```text
9fd3ab Add JWT refresh token
c74aa1 Improve logging
```

These commits exist remotely but not locally.

---

# Compare Changes

```bash
git diff HEAD origin/main
```

This lets you inspect incoming changes before applying them.

---

# What is `git pull`?

`git pull` is simply:

```text
git fetch

+

git merge
```

Command:

```bash
git pull
```

Git:

1. Downloads changes.
    
2. Immediately merges them into your current branch.
    

---

# Example

GitHub:

```text
A
↓
B
↓
C
```

Local:

```text
A
↓
B
```

Run:

```bash
git pull
```

Result:

```text
A
↓
B
↓
C
```

Your files are updated immediately.

---

## Fetch

```text
   │
```


# `git pull --rebase`

Instead of merging:

```bash
git pull --rebase
```

Git performs:

```text
Fetch

↓

Rebase

↓

Updated branch
```

This creates a cleaner, linear history.

Many teams configure Git to use this by default for feature branches.

---

# Fetch First, Merge Later

A professional workflow is:

```bash
git fetch
```

Inspect:

```bash
git log --oneline HEAD..origin/main
```

Review:

```bash
git diff HEAD origin/main
```

Then choose:

```bash
git merge origin/main
```

or

```bash
git rebase origin/main
```

This gives you complete control.

---

# Fetch All Remotes

If you have multiple remotes:

```bash
git fetch --all
```

Git fetches updates from every configured remote.

---

# Clean Up Deleted Branches

Suppose someone deletes:

```text
feature/old-auth
```

on GitHub.

Your local remote reference still exists.

Remove stale references:

```bash
git fetch --prune
```

---

# Updating Your Local `main`

A common workflow:

```bash
git switch main
git pull
```

Now:

```text
main
```

contains the latest code.

Then update your feature branch:

```bash
git switch feature/orders
git rebase main
```

or

```bash
git merge main
```

# Backend Team Workflow

Morning:

```bash
git switch main

```

Start feature:

```bash
git switch -c feature/payment
```

Work.

Commit.

Before opening the Pull Request:

```bash

```

Resolve conflicts if needed.

# Common Errors

## Error 1

Merge conflict during pull.

Example:

```bash
git pull
```

Git reports:

```text
CONFLICT (content)
```

Fix:

- Resolve conflicts.
    
- `git add`
    
- `git commit`
    

---

## Error 2

Uncommitted changes.

Example:

```text
Your local changes would be overwritten.
```

Fix:

```bash
git status
```

Then either:

Commit:

```bash
git add .
git commit -m "Save work"
```

or temporarily save your changes:

```bash
git stash
```

Then pull again.

---

## Error 3

Thinking `git fetch` updates your files.

It doesn't.

It only updates remote-tracking branches such as:

```text
origin/main
```

---

# Fetch vs Pull

|`git fetch`|`git pull`|
|---|---|
|Downloads changes|Downloads and integrates changes|
|Doesn't change your current branch|Updates your current branch|
|Safe for inspection|Immediate synchronization|
|Good before reviewing|Good when ready to update|

---

# Best Practices

- Run `git status` before pulling.
    
- Use `git fetch` when working on important features.
    
- Keep `main` updated regularly.
    
- Prefer reviewing incoming changes before merging.
    
- Use `git pull --rebase` if your team's workflow recommends it.
    

---

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git fetch`|Download remote changes only|
|`git fetch --all`|Fetch from every remote|
|`git fetch --prune`|Remove stale remote-tracking branches|
|`git pull`|Fetch + Merge|
|`git pull --rebase`|Fetch + Rebase|
|`git diff HEAD origin/main`|Compare local and remote|
|`git log HEAD..origin/main`|Show incoming commits|

# Professional Tips

## 1. Don't Blindly Run `git pull`

If you're working on a critical backend feature, prefer:

```bash
git fetch
git log --oneline HEAD..origin/main
git diff HEAD origin/main
```

This lets you understand what's about to change before modifying your branch.

---

## 2. Update `main` Before Starting New Work

A common daily routine:

```bash
git switch main
git pull
git switch -c feature/new-api
```

Starting from an up-to-date `main` reduces merge conflicts later.

---

## 3. Think of `git fetch` as "Check the Mail"

A useful mental model:

- **`git fetch`** → "Download the mail, but don't open it."
    
- **`git pull`** → "Download the mail and immediately put it into your current work."
    

This simple distinction helps you remember why `fetch` is the safer choice when you want to review changes first.
