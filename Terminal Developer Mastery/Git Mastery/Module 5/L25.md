# The Problem

Suppose you want to contribute to:

```text
github.com/company/backend-api
```

Can you simply do:

```bash
git push origin main
```

No.

Why?

Because you **don't have write permission**.

GitHub rejects your push.

---

# The Solution

Instead of pushing directly:

```text
Original Repository

↓

Fork

↓

Your Repository

↓

Clone

↓

Develop

↓

Push

↓

Pull Request

↓

Original Repository
```

This is the standard open-source workflow.

# What is a Fork?

A **Fork** creates **your own copy** of someone else's repository on GitHub.

Example:

Original:

```text
company/backend-api
```

After clicking **Fork**:

```text
rahul/backend-api
```

Notice:

The repository now belongs to **you**.

You have full write access to **your fork**.

---

# What is a Clone?

A **Clone** downloads a Git repository to your computer.

Command:

```bash
git clone git@github.com:rahul/backend-api.git
```

Result:

```text
Laptop

↓

backend-api/
```

Now you can edit the project locally.

---

# Fork vs Clone

|Fork|Clone|
|---|---|
|Happens on GitHub|Happens on your computer|
|Creates a new GitHub repository|Creates a local copy|
|Used when you don't own the repository|Used to work locally|
|Gives you your own remote repository|Gives you a working directory|

# The Two Important Remotes

After cloning your fork:

```bash
git remote -v
```

Initially:

```text
origin  git@github.com:rahul/backend-api.git
```

`origin` points to **your fork**.

---

# Adding the Original Repository

Add another remote:

```bash
git remote add upstream git@github.com:company/backend-api.git
```

Verify:

```bash
git remote -v
```

Output:

```text
origin    git@github.com:rahul/backend-api.git
upstream  git@github.com:company/backend-api.git
```

---

# Understanding `origin` and `upstream`

```text
origin
      ↓
Your Fork
```

```text
upstream
      ↓
Original Repository
```

Think of:

- **origin** → Your copy
    
- **upstream** → Official project
    

---

# Why Do We Need `upstream`?

The original project keeps changing.

Example:

```text
Original Repository

↓

100 new commits
```

Your fork becomes outdated.

You need to synchronize it.

---

# Fetch Updates from Upstream

```bash
git fetch upstream
```

Git downloads new commits from the original project.

---

# Update Your Local Main Branch

Switch:

```bash
git switch main
```

Merge:

```bash
git merge upstream/main
```

Or:

```bash
git rebase upstream/main
```

Now your local `main` is up to date.

---

# Update Your Fork

Push:

```bash
git push origin main
```

Now:

```text
Original Repository

↓

Your Fork

↓

Your Computer
```

All three are synchronized.

# Complete Contribution Workflow

## Step 1

Fork:

```text
company/backend-api
```

↓

```text
rahul/backend-api
```

---

## Step 2

Clone:

```bash
git clone git@github.com:rahul/backend-api.git
```

---

## Step 3

Configure upstream:

```bash
git remote add upstream git@github.com:company/backend-api.git
```

---

## Step 4

Create a feature branch:

```bash
git switch -c fix/login-validation
```

Never develop directly on `main`.

---

## Step 5

Write code.

Commit:

```bash
git add .
git commit -m "Fix login validation"
```

---

## Step 6

Push:

```bash
git push -u origin fix/login-validation
```

Notice:

Push to:

```text
origin
```

not

```text
upstream
```

---

## Step 7

Open a Pull Request.

GitHub automatically shows:

```text
Compare & Pull Request
```

Select:

Base:

```text
company/backend-api
```

Compare:

```text
fix/login-validation
```

---

## Step 8

Maintainers review.

Possible outcomes:

✅ Approved

❌ Changes requested

💬 Discussion

If changes are requested:

Fix the issue.

Commit.

Push again.

The Pull Request updates automatically.

# Common Mistakes

## Mistake 1

Working directly on:

```text
main
```

Always create a feature branch:

```bash
git switch -c feature/request-logging
```

---

## Mistake 2

Pushing to `upstream`

Bad:

```bash
git push upstream main
```

Usually this fails because you don't have permission.

Push to:

```bash
git push origin feature/request-logging
```

---

## Mistake 3

Never syncing with upstream

If you don't update regularly:

- Your fork becomes outdated.
    
- Merge conflicts become more likely.
    
- Your Pull Request may be harder to merge.
    

---

## Mistake 4

Huge Pull Requests

Avoid:

```text
Authentication

Payments

Docker

Refactoring

Documentation
```

all in one PR.

Keep each Pull Request focused on one change.

---

# Best Practices

- Fork a repository only once.
    
- Add `upstream` immediately after cloning.
    
- Sync your fork before starting new work.
    
- Create a new branch for each issue or feature.
    
- Write meaningful commit messages.
    
- Read the project's `CONTRIBUTING.md` file before contributing.
    

---

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git clone <fork-url>`|Clone your fork|
|`git remote add upstream <original-url>`|Add the official repository|
|`git fetch upstream`|Download upstream changes|
|`git merge upstream/main`|Update local `main`|
|`git push origin main`|Update your fork|
|`git switch -c feature/x`|Create a feature branch|
|`git push -u origin feature/x`|Push a feature branch|
|Open Pull Request|Submit changes to the original project|

# Professional Tips

### 1. Read `CONTRIBUTING.md` Before Coding

Most mature open-source projects include a `CONTRIBUTING.md` file that explains:

- Coding standards
    
- Branch naming
    
- Commit message format
    
- Testing requirements
    
- PR checklist
    

Following these guidelines increases the likelihood that your Pull Request will be accepted.

---

### 2. Sync Before Every New Feature

A good habit before starting work:

```bash
git fetch upstream
git switch main
git merge upstream/main
git push origin main
git switch -c feature/new-change
```

This keeps your branch based on the latest code and reduces merge conflicts.

---

### 3. Build Your GitHub Profile with Quality

Maintainers appreciate contributors who:

- Submit focused Pull Requests.
    
- Write clear commit messages.
    
- Respond politely to review comments.
    
- Keep discussions professional.
    
- Learn from feedback.
    

A handful of high-quality contributions is often more valuable than many low-quality ones.
