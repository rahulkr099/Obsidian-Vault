# What is a Pull Request?

A **Pull Request (PR)** is a request to merge changes from one branch into another.

Usually:

```
feature/login
        │
        ▼
main
```

You are saying:

> "I've finished my work. Please review it before merging."

Think of it as asking:

> "Can someone check my code before it becomes part of the project?"

---

# Why Pull Requests Exist

Without PRs:

```
Developer
      │
      ▼
main
```

Anyone could accidentally:

- break production
    
- introduce bugs
    
- reduce performance
    
- remove important code
    

PRs add a review step.

```
Developer
      │
      ▼
Pull Request
      │
 Review
      │
 Approval
      │
      ▼
Merge
```

# Creating a Feature Branch

Instead of coding directly on `main`:

```bash

```

Work normally.

```
Commit

Commit
```

Example:

```

Fix validation

Improve error handling
```

Push:

```bash
git push origin feature/login
```

Then open a PR on GitHub.

# Opening a Pull Request

GitHub usually detects your pushed branch.

It shows:

```
Compare & Pull Request
```

Click it.

You choose:

```
Base:

main

Compare:

feature/login
```

GitHub shows:

- commits
    
- changed files
    
- additions
    
- deletions

# Anatomy of a Pull Request

A PR contains:

```
Title

Description

Commits

Files Changed

Comments

Review Status

Checks

Merge Button
```

Everything about that feature lives here.

---

# Good PR Title

Bad:

```
Update
```

Bad:

```
Changes
```

Bad:

```
Fix
```

Good:

```
Add JWT authentication

Fix login validation

Improve caching layer

Add password reset endpoint
```

Be specific.

---

# Writing a Good PR Description

Poor:

```
Done.
```

Better:

```
## Summary

Added JWT authentication.

## Changes

- Login endpoint
- JWT generation
- Auth middleware
- Token verification

## Testing

- Login tested
- Invalid token tested
- Expired token tested
```

This saves reviewers time.

---

# Professional PR Template

Many teams use a template like:

```markdown
## Summary

What does this PR do?

---

## Changes

- Added ...
- Fixed ...
- Removed ...

---

## Why?

Explain the reason.

---

## Testing

How was it tested?

---

## Screenshots

(if UI)

---

## Checklist

- [x] Tests passed
- [x] Lint passed
- [x] Documentation updated
```

This ensures important details aren't forgotten.

---

# Keep PRs Small

Good:

```
Login Feature

15 files

250 lines
```

Bad:

```
Entire backend rewrite

380 files

18,000 lines
```

Small PRs are:

- easier to review
    
- easier to test
    
- easier to merge
    
- less likely to create conflicts
    

A common guideline is to keep each PR focused on **one logical change**.

# Commit Before Opening PR

Good history:

```
Add login endpoint

Add auth middleware

Fix JWT expiration

Update tests
```

Bad history:

```
asdf

test

again

last

last2

final

real-final
```

Clean commit history helps reviewers understand the progression of your work.

# Draft Pull Requests

Sometimes you're still working.

GitHub supports:

```
Draft Pull Request
```

Meaning:

> "Don't merge yet."

Useful when:

- work isn't finished
    
- you want early feedback
    
- CI testing is running
    
- you're discussing design decisions
    

---

# Review Process

Typical flow:

```
Developer

↓

Open PR

↓

CI Runs

↓

Reviewer Assigned

↓

Reviewer Comments

↓

Developer Fixes

↓

Reviewer Approves

↓

Merge
```

This review cycle improves both code quality and shared understanding.

---

# Responding to Review Comments

Reviewer:

> Variable name unclear.

Good response:

```
Renamed to userProfile.

Thanks!
```

Reviewer:

> Can this fail?

Good response:

```
Added null check.

Thanks for catching that.
```

Avoid defensive replies. Treat reviews as collaboration, not criticism.

---

# Updating a PR

Need to fix something?

Simply commit again:

```bash
git add .

git commit -m "Address review comments"

git push
```

The PR updates automatically.

No need to create a new PR.

# Merge Strategies

GitHub provides several merge options.

## 1. Create a Merge Commit

```
main

A---B---C

      \
       D---E
            \
             M
```

Preserves the exact branch history.

---

## 2. Squash and Merge

```
D

E

F
```

becomes

```
Single Commit
```

Result:

```
main

A---B---C---X
```

Great for keeping history clean.

---

## 3. Rebase and Merge

```
main

A-B-C

feature

D-E
```

becomes

```
A-B-C-D-E
```

Creates a linear history without an extra merge commit.

---

# Which Merge Strategy Should You Use?

|Strategy|Best For|
|---|---|
|Merge Commit|Preserve full branch history|
|Squash Merge|Small features, cleaner history|
|Rebase Merge|Linear project history|

Many teams prefer **Squash and Merge** for feature branches because it keeps `main` easier to read.

# Continuous Integration (CI)

Many repositories automatically run checks when a PR is opened.

Examples:

- Build project
    
- Run tests
    
- Check formatting
    
- Lint code
    
- Security scans
    

```
PR

↓

CI

↓

✅ Passed

or

❌ Failed
```

A failed check usually means the PR shouldn't be merged until the issue is fixed.

---

# Best Practices for Professional PRs

✅ One feature per PR

✅ Write a clear title

✅ Explain _why_, not just _what_

✅ Keep changes focused

✅ Test before opening

✅ Respond politely to reviews

✅ Update documentation if needed

✅ Ensure CI passes

---

# Common Mistakes

❌ Huge PRs with unrelated changes

❌ Vague titles like "Update"

❌ No description

❌ Mixing formatting changes with feature work

❌ Ignoring review comments

❌ Merging without testing

# Interview Questions

### 1. What is a Pull Request?

A Pull Request is a request to merge changes from one branch into another after review.

---

### 2. Why are Pull Requests important?

They enable code reviews, automated testing, discussion, and safer collaboration before code reaches the main branch.

---

### 3. What should a good PR include?

- Clear title
    
- Summary of changes
    
- Reason for the change
    
- Testing details
    
- Focused, well-scoped commits
    

---

### 4. What is the difference between a Draft PR and a regular PR?

A Draft PR signals that the work is not ready to merge but is open for feedback, while a regular PR is intended for review and eventual merging.

---

### 5. Why do teams prefer small Pull Requests?

Small PRs are easier to review, test, understand, and merge, reducing the chance of bugs and merge conflicts.
