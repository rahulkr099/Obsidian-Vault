# What is a Code Review?

A **code review** is the process of examining another developer's code before it is merged into the main branch.

Instead of immediately merging:

```text
Developer
    │
    ▼
Code Review
    │
    ▼
Approved
    │
    ▼
Merged
```

A teammate checks the code for:

- Correctness
    
- Readability
    
- Performance
    
- Security
    
- Maintainability
    
- Coding standards
    

The goal is **better software**, not criticizing the developer.

---

# Why Code Reviews Matter

Imagine you wrote this:

```python
def divide(a, b):
    return a / b
```

A reviewer notices:

> "What happens if `b` is `0`?"

Updated code:

```python
def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by zero")
    return a / b
```

One review prevented a production bug.

# What Reviewers Look For

## 1. Correctness

Does the code work as expected?

Example:

```javascript
const total = price * quantity;
```

Reviewer asks:

> "Can `quantity` ever be negative?"

---

## 2. Readability

Bad:

```javascript
let x = a + b;
```

Better:

```javascript
let totalPrice = itemPrice + tax;
```

Readable names reduce confusion.

---

## 3. Simplicity

Bad:

```javascript
if (isLoggedIn === true) {
    ...
}
```

Better:

```javascript
if (isLoggedIn) {
    ...
}
```

Simple code is easier to maintain.

---

## 4. Maintainability

Reviewer asks:

- Will future developers understand this?
    
- Is the logic easy to modify?
    
- Is there duplicate code?
    

Example:

Instead of:

```javascript
calculateTax1()
calculateTax2()
calculateTax3()
```

Create:

```javascript
calculateTax(type)
```

---

## 5. Performance

Example:

Bad:

```python
for user in users:
    if user.id == target:
        ...
```

Reviewer asks:

> "Should this use a dictionary for O(1) lookup?"

Performance reviews become important for large datasets.

---

## 6. Security

Reviewer checks:

- SQL Injection
    
- XSS
    
- Authentication
    
- Authorization
    
- Password handling
    
- Secret keys
    

Example:

Bad:

```javascript
const password = "admin123";
```

Better:

```javascript
process.env.DB_PASSWORD
```

Never hardcode secrets.

---

## 7. Error Handling

Bad:

```python
file = open("users.txt")
```

Better:

```python
try:
    with open("users.txt") as file:
        ...
except FileNotFoundError:
    ...
```

Reviewers ensure failures are handled safely.

---

## 8. Testing

Reviewer checks:

- Are tests included?
    
- Do they cover edge cases?
    
- Do all tests pass?
    

Example:

Feature:

```text
Password Reset
```

Tests should include:

- Valid email
    
- Invalid email
    
- Expired token
    
- Missing token

# Types of Review Comments

## Suggestion

> Consider using a helper function here.

Friendly and optional.

---

## Question

> Why did you choose recursion instead of iteration?

The reviewer wants to understand your reasoning.

---

## Issue

> This crashes if the array is empty.

A problem that should be fixed.

---

## Praise

> Nice use of middleware here.

Reviews aren't only about problems—they should also recognize good work.

---

# Good Review Comments

Good:

```text
Consider extracting this logic into a helper function for better reuse.
```

Good:

```text
Could this variable have a more descriptive name?
```

Good:

```text
What happens if the API returns null?
```

These comments explain the concern and encourage discussion.

---

# Poor Review Comments

Bad:

```text
Wrong.
```

Bad:

```text
Terrible code.
```

Bad:

```text
Rewrite everything.
```

These comments don't explain the problem or help improve the code.

---

# Review the Code, Not the Person

Bad:

```text
You don't understand JavaScript.
```

Good:

```text
This function could be simplified by using array.map().
```

Focus on the code, never the developer.

---

# Receiving Review Feedback

Don't take comments personally.

Instead of:

```text
Why are you criticizing my code?
```

Respond with:

```text
Good catch! I'll update it.
```

Or:

```text
Thanks. I hadn't considered that case.
```

Reviews are part of teamwork.

---

# When You Disagree

Sometimes you may have a different opinion.

Instead of arguing:

```text
You're wrong.
```

Say:

```text
I chose this approach because it avoids an extra database query. What do you think?
```

Professional discussions are based on technical reasoning.

---

# Responding to Review Comments

Example:

Reviewer:

```text
Can this return null?
```

Developer:

```text
Yes. Added a null check.
```

Reviewer:

```text
Variable name unclear.
```

Developer:

```text
Renamed to currentUser.
```

Keep replies short, polite, and solution-focused.

---

# Approving a Pull Request

After reviewing, you can:

```text
Approve
```

Meaning:

> Looks good to merge.

---

```text
Request Changes
```

Meaning:

> Fix these issues before merging.

---

```text
Comment
```

Meaning:

> Feedback only; approval isn't blocked.

---

# Review Checklist

Before approving, ask yourself:

### Does it work?

- Feature behaves correctly
    
- No obvious bugs
    

---

### Is it readable?

- Clear variable names
    
- Good function names
    
- Consistent formatting
    

---

### Is it secure?

- No secrets committed
    
- Proper input validation
    
- Correct authentication checks
    

---

### Is it tested?

- Tests added
    
- Existing tests pass
    

---

### Is it maintainable?

- No unnecessary complexity
    
- Reusable logic extracted where appropriate
    
- Minimal code duplication

# Backend Review Example

Suppose a teammate adds a login route.

```javascript
app.post("/login", async (req, res) => {
    const user = await User.findOne({
        email: req.body.email
    });

    if (user.password === req.body.password) {
        res.send("Logged in");
    }
});
```

Possible review comments:

✅ Passwords should be hashed.

✅ Compare passwords using `bcrypt.compare()`.

✅ Return proper HTTP status codes.

✅ Handle missing users.

✅ Validate request input.

✅ Avoid exposing internal errors.

A review like this greatly improves security and reliability.

# Common Code Review Mistakes

❌ Reviewing without understanding the feature

❌ Nitpicking every formatting detail when automated tools can handle it

❌ Leaving vague comments

❌ Ignoring tests

❌ Approving without reading the code

❌ Taking feedback personally

# Tools That Help Reviews

Many teams automate repetitive checks using tools like:

- **ESLint** – JavaScript linting
    
- **Prettier** – Code formatting

- **Ruff** – Python linting
    
- **GitHub Actions** – Run tests and CI
    
- **SonarQube** – Code quality and security analysis
    

Automation catches common issues so reviewers can focus on design and logic.

# Interview Questions

### 1. What is the purpose of a code review?

To improve code quality, catch bugs early, share knowledge, enforce coding standards, and ensure maintainable software before merging changes.

---

### 2. What should reviewers focus on?

- Correctness
    
- Readability
    
- Security
    
- Performance
    
- Error handling
    
- Testing
    
- Maintainability
    

---

### 3. How should you respond to review comments?

Professionally, respectfully, and with technical reasoning. Treat feedback as an opportunity to improve the code.

---

### 4. What's the difference between "Approve" and "Request Changes"?

- **Approve:** The PR is ready to merge.
    
- **Request Changes:** Important issues should be resolved before merging.
    

---

### 5. Why should review comments explain _why_?

Explaining the reasoning helps the author learn, encourages productive discussion, and makes feedback actionable.
