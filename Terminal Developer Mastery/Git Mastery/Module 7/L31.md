# What is Rebase?

`git rebase` is a Git command that **moves or reapplies commits onto a different base commit**.

Instead of creating a merge commit, rebase **rewrites history** to produce a cleaner, linear commit history.

Imagine this history:

```text
main

A ─── B ─── C

            \
feature       D ─── E
```

Here:

- `main` has commits `A → B → C`
    
- `feature` started from `C`
    

Now someone adds another commit to `main`:

```text
main

A ─── B ─── C ─── F

            \
feature       D ─── E
```

Your feature branch is now behind.

You have two options:

- Merge
    
- Rebase
    

---

# Option 1 — Merge

```bash
git checkout feature
git merge main
```

History becomes:

```text
A ─── B ─── C ─── F
            \      \
             D ─── E ─── M
```

`M` is a **merge commit**.

Nothing is rewritten.

---

# Option 2 — Rebase

```bash
git checkout feature
git rebase main
```

Git temporarily removes your commits:

```text
D

E
```

Moves to latest `main`:

```text
A ─── B ─── C ─── F
```

Then reapplies them:

```text
A ─── B ─── C ─── F ─── D' ─── E'
```

Notice:

```text
D'

E'
```

These are **new commits**, not the original ones.

Git copied the changes onto a new base.

---

# Why Use Rebase?

Benefits:

✅ Linear history

✅ Easier to read

✅ Cleaner commit graph

✅ Better for feature branches

Many teams prefer a history like:

```text
A ─ B ─ C ─ D ─ E ─ F
```

instead of:

```text
A ─ B ─ C ──────── M
      \         /
       D ─ E ──
```

---

# Merge vs Rebase

|Merge|Rebase|
|---|---|
|Creates merge commit|Rewrites commit history|
|Preserves original history|Creates a linear history|
|Safe for shared branches|Best for local branches|
|Doesn't change commit IDs|Creates new commit IDs|

---

# When Should You Use Rebase?

Use rebase when:

- Updating your feature branch with the latest `main`
    
- Cleaning your own commit history
    
- Preparing a Pull Request
    
- Working on a local branch that nobody else uses
    

Avoid rebasing branches that other people are actively using.

# Basic Rebase

Current history:

```text
main

A ─── B ─── C
```

Feature:

```text
A ─── B ─── D ─── E
```

Update `main`:

```text
git checkout main
git pull
```

Switch back:

```bash
git checkout feature
```

Rebase:

```bash
git rebase main
```

Done.

---

# Rebase Conflicts

Sometimes both branches modify the same code.

Git pauses:

```text
CONFLICT

app.js
```

Check status:

```bash
git status
```

Resolve conflict manually.

Then:

```bash
git add app.js
```

Continue:

```bash
git rebase --continue
```

If more conflicts appear:

Repeat.

---

# Abort a Rebase

If something goes wrong:

```bash
git rebase --abort
```

Git restores your branch to its original state before the rebase began.

---

# Skip a Commit

Rarely, you may want to skip the problematic commit:

```bash
git rebase --skip
```

Only use this if you're sure the skipped changes are unnecessary.

---

# Interactive Rebase

One of Git's most powerful features.

Command:

```bash
git rebase -i HEAD~4
```

Meaning:

> Interactively edit the last **4 commits**.

Git opens an editor:

```text
pick a1b2 Add login API
pick c3d4 Fix typo
pick e5f6 Update README
pick g7h8 Remove debug logs
```

Now you decide what to do with each commit.

---

# Interactive Rebase Commands

|Command|Meaning|
|---|---|
|`pick`|Keep commit|
|`reword`|Change commit message|
|`edit`|Stop and edit commit|
|`squash`|Combine with previous commit|
|`fixup`|Combine without keeping message|
|`drop`|Remove commit|

---

# Reword

Before:

```text
pick a1b2 Update
```

Change:

```text
reword a1b2 Update
```

Git asks for a better message.

Example:

```text
Add JWT authentication middleware
```

---

# Squash

Suppose history is:

```text
Add login API

Fix typo

Fix validation

Improve messages
```

Interactive rebase:

```text
pick Add login API
squash Fix typo
squash Fix validation
squash Improve messages
```

Result:

```text
Add login API
```

One clean commit replaces four small ones.

---

# Fixup

Example:

```text
Add JWT

Fix spelling
```

Use:

```text
pick Add JWT
fixup Fix spelling
```

Result:

```text
Add JWT
```

The second commit disappears without asking you to edit the commit message.

---

# Drop

Suppose one commit accidentally added debug code:

```text
Add login

Debug logging

Fix API
```

Interactive rebase:

```text
pick Add login
drop Debug logging
pick Fix API
```

The debug commit is removed from history.

---

# Edit

Suppose you forgot to include a file.

Interactive rebase:

```text
edit Add authentication
```

Git pauses.

Make your changes:

```bash
git add .
git commit --amend
git rebase --continue
```

Now the original commit includes the missing changes.

# Rewriting Public History

**Important Rule:**

❌ Don't rebase commits that have already been shared with teammates.

Example:

You push:

```text
A ─ B ─ C
```

Your teammate builds on top:

```text
A ─ B ─ C ─ D
```

If you rebase and rewrite `A-B-C`, your teammate's history no longer matches, causing unnecessary conflicts.

**Rule of thumb:**

- ✅ Rebase your own local branches.
    
- ❌ Avoid rebasing shared branches like `main` or branches others are using.
    

---

# Force Push After Rebase

Because rebase changes commit IDs, a normal push won't work.

You'll see:

```text
Rejected
```

Use:

```bash
git push --force-with-lease
```

Prefer:

```bash
git push --force-with-lease
```

instead of:

```bash
git push --force
```

`--force-with-lease` is safer because it refuses to overwrite work that others have pushed since your last fetch.

# Interview Questions

### 1. What is `git rebase`?

`git rebase` reapplies commits onto a new base commit, creating a cleaner, linear history by rewriting commit history.

---

### 2. What is the difference between merge and rebase?

- **Merge** combines histories and creates a merge commit.
    
- **Rebase** rewrites commits onto another branch, avoiding merge commits and producing a linear history.
    

---

### 3. What is Interactive Rebase?

Interactive Rebase (`git rebase -i`) lets you edit, reorder, combine, rename, or remove commits before sharing them.

---

### 4. Why shouldn't you rebase public branches?

Rebasing changes commit IDs, which can disrupt teammates who have based their work on the original commits.

---

### 5. What is the difference between `squash` and `fixup`?

- **Squash:** Combines commits and lets you edit the resulting commit message.
    
- **Fixup:** Combines commits while discarding the second commit's message.
