# Lesson 32 — Git Cherry-pick (Move Specific Commits)

> **Goal:** Learn how to copy individual commits from one branch to another using `git cherry-pick`. By the end of this lesson, you'll know when cherry-pick is useful, how it works, how to resolve conflicts, and when you should avoid it.

---

# What is Cherry-pick?

`git cherry-pick` copies **one or more specific commits** from one branch and applies them to another branch.

Unlike `merge` or `rebase`, it **does not bring the entire branch**—only the commits you choose.

Imagine this history:

```text
main

A ─── B ─── C
          \
feature     D ─── E ─── F
```

Suppose commit **E** contains an important bug fix.

Instead of merging the whole `feature` branch, you can copy only **E** into `main`.

Result:

```text
main

A ─── B ─── C ─── E'
```

Notice the `'`.

`E'` is a **new commit** with the same changes as `E`, but a different commit ID.

---

# Why Use Cherry-pick?

Cherry-pick is useful when you want:

- One bug fix
    
- One feature
    
- One documentation update
    
- One configuration change
    

without bringing unrelated work.

---

# Real-World Example

Imagine your feature branch contains:

```text
feature/auth

Add Login API

Add Registration API

Fix Password Validation

Refactor Database Layer

Improve README
```

Production only needs:

```text
Fix Password Validation
```

Cherry-pick copies only that fix.

---

# Basic Command

First, switch to the target branch:

```bash
git checkout main
```

Apply the commit:

```bash
git cherry-pick <commit-hash>
```

Example:

```bash
git cherry-pick a1b2c3d
```

Git creates a new commit on the current branch.

---

# Finding Commit Hashes

Use:

```bash
git log --oneline
```

Example:

```text
a1b2c3d Fix JWT validation

b2c3d4e Add Login API

c3d4e5f Update README
```

Copy the commit hash you want.

# Cherry-picking Multiple Commits

Apply multiple commits one by one:

```bash
git cherry-pick commit1 commit2 commit3
```

Example:

```bash
git cherry-pick a1b2 b2c3 c3d4
```

Git applies them in order.

---

# Cherry-picking a Range

Git can copy a range of commits.

Example:

```bash
git cherry-pick A^..D
```

Suppose:

```text
A

↓

B

↓

C

↓

D
```

This copies:

- A
    
- B
    
- C
    
- D
    

to the current branch.

---

# Cherry-picking Without Committing

Sometimes you want to inspect changes first.

Use:

```bash
git cherry-pick --no-commit <hash>
```

Git applies the changes to your working directory but **doesn't create a commit**.

You can:

```bash
git status
```

Review the changes, then commit manually:

```bash
git commit -m "Apply login validation fix"
```

---

# Cherry-pick Conflicts

Just like merge and rebase, conflicts can happen.

Example:

```text
main

app.js
```

Feature also changed:

```text
app.js
```

Git stops:

```text
CONFLICT

app.js
```

Resolve the conflict manually.

Then:

```bash
git add app.js
```

Continue:

```bash
git cherry-pick --continue
```

---

# Abort Cherry-pick

If something goes wrong:

```bash
git cherry-pick --abort
```

Git returns the branch to its previous state.

---

# Skip a Commit

If applying multiple commits and one fails:

```bash
git cherry-pick --skip
```

Git skips the problematic commit and continues with the next one.

---

# Cherry-pick vs Merge

## Merge

```text
main

A ─ B ─ C
     \
      D ─ E ─ F
```

After merge:

```text
A ─ B ─ C ─── M
     \       /
      D ─ E ─ F
```

Entire branch included.

---

## Cherry-pick

```text
A ─ B ─ C ─ E'
```

Only one commit copied.

---

# Cherry-pick vs Rebase

Rebase:

```text
Feature

D

E

F
```

becomes:

```text
Main

A

B

C

D'

E'

F'
```

Entire branch is moved.

Cherry-pick:

```text
Only:

E
```

becomes:

```text
Main

A

B

C

E'
```

Only one commit moves.

# Backporting Fixes

Imagine:

```text
main

Version 2.0
```

Old branch:

```text
release-1.5
```

A security bug is fixed in `main`.

Instead of merging all new features into `release-1.5`, cherry-pick only the security fix.

Example:

```bash
git checkout release-1.5
git cherry-pick ab12345
```

This is called **backporting**.

# Viewing Cherry-picked Commits

Use:

```bash
git log --oneline --graph
```

Example:

```text
a123 Add Login

b456 Fix JWT

c789 Improve Docs
```

The cherry-picked commit appears as a normal commit with a new hash.

---

# Duplicate Changes

Remember:

Cherry-pick **copies changes**, not commit IDs.

Original:

```text
Commit:

ABC123
```

Cherry-picked:

```text
Commit:

XYZ789
```

Same code.

Different commit.

---

# Common Mistakes

❌ Cherry-picking large feature commits

❌ Cherry-picking without understanding dependencies

❌ Forgetting to test after cherry-picking

❌ Cherry-picking the same commit multiple times

❌ Assuming commit hashes remain the same

---

# Best Practices

✅ Cherry-pick only small, self-contained commits

✅ Test after cherry-picking

✅ Keep commit messages meaningful

✅ Use it for bug fixes and hotfixes

✅ Resolve conflicts carefully

# Interview Questions

### 1. What is `git cherry-pick`?

`git cherry-pick` copies one or more specific commits from one branch and applies them to another branch.

---

### 2. How is cherry-pick different from merge?

- **Merge** combines the entire branch history.
    
- **Cherry-pick** copies only selected commits.
    

---

### 3. When should you use cherry-pick?

When you need to move a specific bug fix, hotfix, documentation update, or other isolated change without merging the entire branch.

---

### 4. Does cherry-pick preserve the original commit hash?

No. It creates a new commit with a different hash because it is a new commit in the target branch.

---

### 5. How do you continue after resolving a cherry-pick conflict?

```bash
git add .
git cherry-pick --continue
```

## 💡 Backend Engineer Tip

As a backend developer, you'll most commonly use **cherry-pick** for:

- 🚑 Emergency production hotfixes
    
- 🔒 Security patches
    
- 📦 Backporting fixes to older releases
    
- 📝 Moving small documentation changes
    
- 🧪 Applying isolated bug fixes between release branches
    

Avoid using cherry-pick to move large features—it works best for **small, independent commits**.
