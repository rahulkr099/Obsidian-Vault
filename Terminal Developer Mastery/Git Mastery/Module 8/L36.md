# What is a Git Tag?

A **Git tag** is a **permanent label** attached to a specific commit.

Unlike a branch, a tag **does not move**.

Think of a tag as placing a bookmark in a book.

```text
Book

Page 120

↓

Bookmark
```

No matter how much you keep reading, the bookmark stays on page 120.

Git tags work the same way.

---

# Why Use Tags?

Imagine your backend API reaches version **1.0**.

History:

```text
A ─ B ─ C ─ D ─ E
```

Commit **C** is your first stable release.

Create a tag:

```text
A ─ B ─ C(v1.0) ─ D ─ E
```

Months later, even after hundreds of commits, you can always return to **v1.0**.

---

# Real-World Uses of Tags

Tags are commonly used for:

- 🚀 Production releases
    
- 🏷️ Version numbers
    
- 📦 Software distributions
    
- 🔒 Stable milestones
    
- 🐛 Hotfix releases
    
- 📚 Important checkpoints
    

Examples:

```text
v1.0.0

v1.1.0

v2.0.0

v2.0.1
```

---

# Branches vs Tags

## Branch

A branch **moves** as you commit.

```text
A ─ B ─ C ─ D
              ↑
           main
```

After another commit:

```text
A ─ B ─ C ─ D ─ E
                  ↑
               main
```

---

## Tag

A tag stays fixed.

```text
A ─ B ─ C(v1.0) ─ D ─ E
```

Even after:

```text
A ─ B ─ C(v1.0) ─ D ─ E ─ F ─ G
```

`v1.0` still points to commit **C**.

---

# Lightweight Tags

A **lightweight tag** is the simplest type of tag.

It stores:

- Tag name
    
- Reference to a commit
    

Nothing else.

Think of it as a shortcut:

```text
v1.0

↓

Commit C
```

---

# Creating a Lightweight Tag

Tag the current commit:

```bash
git tag v1.0
```

Now:

```text
A ─ B ─ C(v1.0)
```

---

# Viewing Tags

List all tags:

```bash
git tag
```

Example:

```text
v1.0

v1.1

v2.0
```

---

# Tagging an Older Commit

Find commit hashes:

```bash
git log --oneline
```

Example:

```text
a1b2c3d Add Login

b2c3d4e Add JWT

c3d4e5f Initial Commit
```

Tag the login commit:

```bash
git tag v1.0 a1b2c3d
```

Now `v1.0` points to that commit instead of `HEAD`.

---

# Viewing Tag Details

Show the tagged commit:

```bash
git show v1.0
```

Output:

```text
commit a1b2c3d

Author: Rahul

Date: ...

Add Login API
```

For a lightweight tag, `git show` displays the commit directly because there is no extra tag metadata.

---

# Checking Out a Tag

Switch to a tag:

```bash
git checkout v1.0
```

Git moves to that exact commit.

---

# Detached HEAD

After checking out a tag:

```bash
git checkout v1.0
```

Git prints:

```text
You are in 'detached HEAD' state.
```

Why?

Because a tag isn't a branch.

Example:

```text
main

↓

A ─ B ─ C(v1.0) ─ D ─ E
```

Checking out `v1.0` places you here:

```text
A ─ B ─ C
          ↑
        HEAD
```

You're no longer on `main`.

---

# Should You Commit on a Tag?

Technically, yes.

```bash
git checkout v1.0
```

Then:

```bash
git commit -m "Temporary fix"
```

But this creates a commit in a **detached HEAD** state.

If you switch away without creating a branch, that commit can become difficult to find.

Instead:

```bash
git checkout -b hotfix-v1.0 v1.0
```

Now you're on a proper branch and can commit safely.

---

# Deleting a Tag

Delete a local tag:

```bash
git tag -d v1.0
```

Output:

```text
Deleted tag 'v1.0'
```

The commit remains; only the tag is removed.

---

# Renaming a Tag

Git doesn't provide a rename command.

Instead:

Delete:

```bash
git tag -d v1.0
```

Recreate:

```bash
git tag v1.0.0
```

# Listing Tags with a Pattern

Show only version 1 tags:

```bash
git tag -l "v1.*"
```

Output:

```text

```

Useful in repositories with many releases.

# Lightweight Tags vs Annotated Tags

|Lightweight Tag|Annotated Tag|
|---|---|
|Simple pointer|Full Git object|
|No author information|Stores author|
|No date|Stores creation date|
|No message|Supports tag message|
|Quick to create|Better for official releases|

In professional projects, annotated tags are usually preferred for releases.

---

# Tags and GitHub

Creating a tag locally **does not automatically send it to GitHub**.

Local repository:

```text
v1.0
```

Remote repository:

```text
No Tag
```

Push a specific tag:

```bash
git push origin v1.0
```

Push all tags:

```bash
git push origin --tags
```

We'll discuss this further in the lessons on GitHub Releases.

# Common Mistakes

❌ Thinking tags move like branches

❌ Forgetting to push tags to the remote

❌ Making commits directly in a detached HEAD state

❌ Using lightweight tags for major production releases when annotated tags would be more appropriate

---

# Best Practices

✅ Tag every production release.

✅ Use semantic version names.

Examples:

```text
v1.0.0

v1.2.3

v2.0.0
```

✅ Keep tag names consistent.

✅ Push tags after creating them.

✅ Use lightweight tags for quick local markers or temporary milestones.

# Interview Questions

### 1. What is a Git tag?

A Git tag is a permanent reference to a specific commit, typically used to mark releases or important milestones.

---

### 2. What is the difference between a branch and a tag?

- A **branch** moves forward as new commits are added.
    
- A **tag** always points to the same commit.
    

---

### 3. What is a lightweight tag?

A lightweight tag is a simple reference to a commit without additional metadata like author, date, or a tag message.

---

### 4. Does creating a tag automatically push it to GitHub?

No. Tags must be pushed explicitly:

```bash
git push origin v1.0
```

or:

```bash
git push origin --tags
```

---

### 5. What happens when you check out a tag?

Git places you in a **detached HEAD** state because tags are fixed references, not branches.

## 💡 Backend Engineer Tip

In professional backend projects, every deployment to production is usually associated with a Git tag. If production is running **`v2.4.1`**, anyone on the team can instantly check out that exact codebase, investigate bugs, or recreate the release. Tags provide a reliable snapshot of what was actually deployed.
