# Lesson 37 — Annotated Tags

> **Goal:** Learn how to create and use **annotated tags**, understand how they differ from lightweight tags, and see why almost every professional software project uses annotated tags for official releases.

# What is an Annotated Tag?

An **annotated tag** is a **full Git object** that stores metadata in addition to pointing to a commit.

Unlike a lightweight tag, it contains information such as:

- Tag name
    
- Target commit
    
- Tagger name
    
- Tagger email
    
- Creation date
    
- Tag message
    

Think of it as a signed release note attached to a commit.

```text
v1.0.0

↓

Commit

↓

Release Information
```

---

# Why Use Annotated Tags?

Imagine you're releasing version **2.0.0** of your backend API.

You don't just want to remember **which commit** it was.

You also want to know:

- Who created the release?
    
- When was it released?
    
- Why was it released?
    
- What changed?
    

Annotated tags answer these questions.

# Lightweight vs Annotated Tags

## Lightweight Tag

Stores only:

```text
v1.0

↓

Commit
```

---

## Annotated Tag

Stores:

```text
Tag Name

↓

Commit

↓

Author

↓

Date

↓

Message
```

Much richer information.

---

# Creating an Annotated Tag

Basic syntax:

```bash
git tag -a v1.0.0
```

Git opens your default editor.

Example message:

```text
Release version 1.0.0

Initial production release
```

Save and exit.

---

# Create Tag With Message

Instead of opening an editor:

```bash
git tag -a v1.0.0 -m "Initial production release"
```

This is the most common approach.

---

# Tagging an Older Commit

Find commit hashes:

```bash
git log --oneline
```

Example:

```text
8fa1234 Add JWT Authentication

4bc5678 Add Login API

1de9876 Initial Express Setup
```

Tag the authentication commit:

```bash
git tag -a v1.0.0 8fa1234 -m "First stable backend release"
```

---

# Viewing Tags

List tags:

```bash
git tag
```

Example:

```text
v1.0.0

v1.1.0

v2.0.0
```

---

# Inspecting an Annotated Tag

Use:

```bash
git show v1.0.0
```

Example output:

```text
tag v1.0.0

Tagger: Rahul Kumar

Date: ...

Initial production release

commit 8fa1234

Add JWT Authentication
```

Notice the extra information:

- Tagger
    
- Date
    
- Message
    

A lightweight tag doesn't include this metadata.

---

# Viewing Only the Tag Information

Instead of showing the commit:

```bash
git cat-file -p v1.0.0
```

Example:

```text
object 8fa1234

type commit

tag v1.0.0

tagger Rahul Kumar

Initial production release
```

This reveals the tag object itself.

---

# Updating a Tag

Tags are intended to be **immutable** (unchanging).

If you need to change one:

Delete it:

```bash
git tag -d v1.0.0
```

Create it again:

```bash
git tag -a v1.0.0 -m "Updated release message"
```

Avoid changing tags that have already been shared with others.

---

# Pushing Annotated Tags

Creating a tag locally:

```bash
git tag -a v1.0.0 -m "Release"
```

does **not** upload it to GitHub.

Push a specific tag:

```bash
git push origin v1.0.0
```

Push every tag:

```bash
git push origin --tags
```

---

# Deleting Remote Tags

Delete locally:

```bash
git tag -d v1.0.0
```

Delete from the remote:

```bash
git push origin --delete v1.0.0
```

or the older equivalent:

```bash
git push origin :refs/tags/v1.0.0
```

# Checking Out an Annotated Tag

Just like a lightweight tag:

```bash
git checkout v1.0.0
```

Git switches to that commit.

You'll still enter a **detached HEAD** state.

If you need to make changes:

```bash
git checkout -b hotfix-v1.0.0 v1.0.0
```

---

# Signing Tags (Advanced)

Professional projects often **cryptographically sign** release tags.

Example:

```bash
git tag -s v1.0.0 -m "Signed release"
```

This uses a GPG key to verify that the release was created by the expected maintainer.

We'll cover signing in a later security module.

# Lightweight vs Annotated Comparison

|Feature|Lightweight|Annotated|
|---|---|---|
|Points to commit|✅|✅|
|Stores author|❌|✅|
|Stores date|❌|✅|
|Stores message|❌|✅|
|Separate Git object|❌|✅|
|Best for official releases|❌|✅|

# Common Mistakes

❌ Using lightweight tags for official releases

❌ Forgetting to push tags to the remote

❌ Editing tags after teammates have already fetched them

❌ Writing vague tag messages like:

```text
Release
```

Instead, be descriptive:

```text
Initial production release with JWT authentication and user management
```

---

# Best Practices

✅ Use annotated tags for production releases.

✅ Write meaningful release messages.

✅ Use Semantic Versioning (coming in the next lesson).

✅ Push tags immediately after creating them.

✅ Never move or recreate public release tags unless absolutely necessary.

# Interview Questions

### 1. What is an annotated tag?

An annotated tag is a Git object that stores metadata such as the tagger, creation date, and a descriptive message in addition to referencing a commit.

---

### 2. How do annotated tags differ from lightweight tags?

Annotated tags include metadata and are separate Git objects, while lightweight tags are simple references to commits.

---

### 3. How do you create an annotated tag?

```bash
git tag -a v1.0.0 -m "Initial production release"
```

---

### 4. Why are annotated tags preferred for releases?

Because they preserve useful release metadata, making it easier to track who created the release, when it was created, and what it represents.

---

### 5. How do you push an annotated tag to GitHub?

```bash
git push origin v1.0.0
```

or push all tags:

```bash
git push origin --tags
```

## 💡 Backend Engineer Tip

In most professional backend teams, **every production deployment corresponds to an annotated Git tag**. If someone reports a bug in **`v2.3.1`**, the team can immediately check out that exact release, inspect the code that was deployed, compare it with newer versions, or create a hotfix branch from it. Annotated tags make release management predictable and traceable.
