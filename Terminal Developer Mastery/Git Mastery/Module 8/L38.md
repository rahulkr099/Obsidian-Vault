# What is a GitHub Release?

A **GitHub Release** is an official, published version of your software.

It is **built on top of a Git tag** and usually includes:

- Release version
    
- Release notes
    
- Downloadable source code
    
- Optional compiled binaries or assets
    
- Links to the tagged commit
    

Think of it this way:

```text
Git Commit
      ↓
Git Tag
      ↓
GitHub Release
```

A **tag** marks a commit.

A **release** explains what that version contains.

↓

```text

✓ MongoDB

```

Users immediately know:

- Which version to download
    
- What's new
    
- What changed

# Git Tag vs GitHub Release

|Git Tag|GitHub Release|
|---|---|
|Marks a commit|Publishes a version|
|Exists in Git|Exists on GitHub|
|No release notes|Rich release notes|
|Simple reference|Download page|
|Local + Remote|GitHub feature|

Think of it like this:

```text
Tag

↓

Bookmark
```

```text
Release

↓

Published Book Edition
```

# Creating a Release

Typical workflow:

1. Push your code
    

```bash
git push origin main
```

2. Create a tag
    

```bash
git tag -a v1.0.0 -m "Initial release"
```

3. Push the tag
    

```bash
git push origin v1.0.0
```

4. Open GitHub
    
5. Navigate to:
    

```text
Releases

↓

Draft New Release
```

6. Select:
    

```text
Tag

↓

v1.0.0
```

7. Write release notes.
    
8. Publish.
    

---

# Release Notes

Good release notes answer:

- What changed?
    
- Why?
    
- Are there breaking changes?
    
- Are there bug fixes?
    

Example:

```markdown
# v1.1.0

## Added

- User profile endpoints
- Password reset API

## Fixed

- JWT expiration bug

## Improved

- Better error messages
```

Professional teams often follow this structure.

# What is Semantic Versioning?

Semantic Versioning (SemVer) is a standard way to number software releases.

Format:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.5.3
```

Meaning:

```text
2

↓

Major
```

```text
5

↓

Minor
```

```text
3

↓

Patch
```

---

# MAJOR Version

Increase the **major** version when you make **breaking changes**.

Example:

```text
v1.0.0
```

↓

```text
v2.0.0
```

Breaking change:

```text
Old API

/api/login
```

becomes:

```text
/api/v2/login
```

Existing clients must update.

---

# MINOR Version

Increase the **minor** version when you add **new features** without breaking existing ones.

Example:

```text
v1.2.0
```

↓

```text
v1.3.0
```

Added:

```text
User Notifications
```

Existing APIs still work.

---

# PATCH Version

Increase the **patch** version for:

- Bug fixes
    
- Security fixes
    
- Performance improvements
    

Example:

```text
v1.3.1
```

↓

```text
v1.3.2
```

Example change:

```text
Fix JWT Validation Bug
```

No API changes.

# Automatic Release Notes

GitHub can generate release notes automatically by comparing:

```text
v1.2.0

↓

v1.3.0
```

It detects:

- Merged Pull Requests
    
- Contributors
    
- Commits
    

You can then edit the generated notes before publishing.

# Interview Questions

### 1. What is a GitHub Release?

A GitHub Release is a published version of your software built from a Git tag. It includes release notes, downloadable source code, and optional assets.

---

### 2. What is Semantic Versioning?

Semantic Versioning is a versioning scheme in the format:

```text
MAJOR.MINOR.PATCH
```

It communicates the impact of changes between releases.

---

### 3. When should you increase the MAJOR version?

When introducing **breaking changes** that require users or clients to modify how they use your software.

---

### 4. What is the difference between a Git tag and a GitHub Release?

A **Git tag** marks a specific commit, while a **GitHub Release** is a published package around that tag with release notes and downloadable assets.

---

### 5. What is a patch release?

A patch release increments the third number (for example, `v1.2.3` → `v1.2.4`) and is used for bug fixes, security fixes, or small improvements that don't break compatibility.

## 💡 Backend Engineer Tip

Most professional backend teams treat **Git tags**, **Semantic Versioning**, and **GitHub Releases** as a single release management system:

- **Git Tag** → Identifies the exact commit.
    
- **Semantic Version** → Communicates compatibility and change scope.
    
- **GitHub Release** → Documents the release and distributes it.
    

This combination makes deployments traceable, simplifies rollbacks, and helps teammates and users understand exactly what changed between versions.
