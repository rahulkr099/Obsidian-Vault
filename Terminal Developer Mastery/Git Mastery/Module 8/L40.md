# What is a Hotfix?

A **hotfix** is an **emergency change** made to fix a critical problem in production.

Unlike a normal feature release, a hotfix is:

- 🚑 Urgent
    
- 🎯 Small and focused
    
- ⚡ Released as quickly as possible
    
- 🧪 Still tested before deployment
    

Examples:

- Login is broken
    
- Payment API fails
    
- Security vulnerability
    
- Database migration bug
    
- Production crash
    

---

# Why Not Fix It on the Feature Branch?

Imagine your branches look like this:

```text
main

↓

v1.2.0 (Production)
```

```text
feature/payment

↓

50% Complete
```

Production bug:

```text
Users Cannot Login
```

You **don't** want to merge the unfinished payment feature just to fix login.

Instead, create a **hotfix branch**.

# Step 1 — Identify the Production Version

Suppose production is running:

```text
v1.2.0
```

Confirm using Git tags:

```bash
git tag
```

Output:

```text
v1.0.0

v1.1.0

v1.2.0
```

---

# Step 2 — Create a Hotfix Branch

Start from the production tag:

```bash
git checkout -b hotfix/login-fix v1.2.0
```

History:

```text
main

↓

v1.2.0

↓

hotfix/login-fix
```

You now have an isolated branch containing exactly what is running in production.

---

# Step 3 — Fix the Bug

Example:

Before:

```javascript
if (!token) {
    return res.status(401).json({ message: "Unauthorized" });
}
```

Bug:

The token validation incorrectly rejects valid tokens.

After fixing:

```javascript
if (!token || token.trim() === "") {
    return res.status(401).json({ message: "Unauthorized" });
}
```

Keep the fix focused.

Avoid unrelated refactoring.

---

# Step 4 — Commit the Fix

```bash
git add .
git commit -m "Fix JWT validation for empty tokens"
```

A good hotfix commit message clearly describes the problem being fixed.

---

# Step 5 — Test the Fix

Run:

```bash
npm test
```

Also verify manually:

```text
✓ Login

✓ Register

✓ Refresh Token

✓ Protected Routes
```

Even urgent fixes should be tested.

---

# Step 6 — Create a Hotfix Tag

Create a new patch version:

```bash
git tag -a v1.2.1 -m "Hotfix for JWT authentication"
```

Notice:

```text
v1.2.0

↓

v1.2.1
```

Patch version increased.

---

# Step 7 — Deploy

Push:

```bash
git push origin hotfix/login-fix
git push origin v1.2.1
```

Deploy:

```text
GitHub Actions

↓

Production
```

Verify:

```text
GET /health

↓

200 OK
```

---

# Step 8 — Merge Back

One common mistake:

Developer fixes production.

Forgets development.

Later:

```text
main

↓

Bug Fixed
```

Development:

```text
develop

↓

Still Buggy
```

Eventually:

The bug returns.

Always merge the hotfix back.

Example:

```bash
git checkout main
git merge hotfix/login-fix
```

Then:

```bash
git checkout develop
git merge hotfix/login-fix
```

This keeps all active branches in sync.

# Common Mistakes

❌ Fixing directly on `main` without a branch

❌ Mixing unrelated changes into the hotfix

❌ Forgetting to merge the hotfix back into development branches

❌ Forgetting to create a new release tag

❌ Skipping testing because "it's just a small fix"

---

# Best Practices

✅ Keep hotfixes small and focused.

✅ Increase only the patch version.

✅ Test before deployment.

✅ Create an annotated tag.

✅ Document the hotfix in release notes.

✅ Merge the fix back into all relevant long-lived branches.

# Hotfix vs Feature

|Feature|Hotfix|
|---|---|
|Adds functionality|Fixes production issues|
|Can take weeks|Usually hours or days|
|Normal release cycle|Emergency release|
|Minor or major version|Patch version|
|Larger scope|Minimal scope|

# Interview Questions

### 1. What is a hotfix?

A hotfix is a small, urgent change made to fix a critical issue in production without waiting for the next regular release.

---

### 2. From which branch or commit should a hotfix be created?

Typically from the **current production branch** or the **release tag** that represents the version running in production.

---

### 3. Which Semantic Version number usually changes for a hotfix?

The **patch** version.

Example:

```text
v1.2.0

↓

v1.2.1
```

---

### 4. Why should a hotfix be merged back into development branches?

To prevent the same bug from reappearing in future releases when ongoing development is merged.

---

### 5. Should hotfixes skip testing?

No. Although the process is faster, critical functionality should still be tested before deployment.

## 💡 Backend Engineer Tip

In professional backend engineering, **speed is important during incidents—but stability is even more important**. A good hotfix changes only what's necessary, is tested quickly but carefully, is tagged with a new patch version, and is merged back into all active development branches. This disciplined workflow helps prevent urgent fixes from becoming future regressions.
