# Lesson 41 — Feature Branch Workflow

> **Goal:** Learn the Feature Branch Workflow, one of the most widely used Git workflows in startups and backend teams. By the end of this lesson, you'll know how developers work on multiple features simultaneously without disrupting the stable codebase.

# What is a Feature Branch Workflow?

A **Feature Branch Workflow** means **every new feature, bug fix, or improvement is developed in its own Git branch** instead of directly on `main`.

Instead of this:

```text
main

↓

Developer A commits

↓

Developer B commits

↓

Developer C commits
```

Professional teams do this:

```text
main
 ├── feature/login
 ├── feature/payment
 ├── feature/profile
 └── feature/notifications
```

Each developer works independently.

---

# Why Use Feature Branches?

Imagine a team building an Expense Tracker API.

Three developers are working simultaneously.

Developer A:

```text
JWT Authentication
```

Developer B:

```text
Payment API
```

Developer C:

```text
Reports API
```

If everyone commits directly to `main`:

```text
main

↓

Authentication

↓

Half Payment Feature

↓

Broken Reports

↓

Bug Fix

↓

More Payment Code
```

`main` becomes unstable.

Feature branches solve this problem.

---

# The Basic Workflow

```text
main

↓

Create Feature Branch

↓

Write Code

↓

Commit Changes

↓

Push Branch

↓

Open Pull Request

↓

Code Review

↓

Merge into main

↓

Delete Branch
```

This is the foundation of modern collaborative development.

---

# Step 1 — Start from an Updated `main`

Always begin with the latest version of the main branch.

```bash
git checkout main
```

Pull the latest changes:

```bash
git pull origin main
```

This reduces future merge conflicts.

---

# Step 2 — Create a Feature Branch

Create a new branch for your work.

```bash
git checkout -b feature/payment-api
```

Now:

```text
main
     \
      feature/payment-api
```

You're isolated from everyone else's work.

---

# Branch Naming Conventions

Good names:

```text
feature/user-auth

feature/payment-api

feature/email-verification

feature/dashboard

feature/report-export
```

Poor names:

```text
new

temp

work

update

branch1
```

A branch name should describe **what you're building**.

---

# Step 3 — Develop the Feature

Commit regularly.

Example:

```bash
git add .
git commit -m "Create payment controller"
```

Later:

```bash
git commit -m "Add payment validation"
```

Later:

```bash
git commit -m "Write payment tests"
```

Small commits are easier to review and debug.

---

# Commit History

Example:

```text
feature/payment-api

↓

Create Controller

↓

Add Validation

↓

Write Tests

↓

Improve Error Handling
```

Instead of:

```text
One Huge Commit

↓

500 Files Changed
```

Small, logical commits are preferred.

---

# Step 4 — Push the Feature Branch

```bash
git push origin feature/payment-api
```

Now the branch exists on GitHub.

Teammates can:

- Review
    
- Test
    
- Collaborate
    

without affecting `main`.

---

# Step 5 — Open a Pull Request (PR)

```text
feature/payment-api

↓

Pull Request

↓

main
```

A PR is a request to merge your work into another branch.

It starts the review process.

---

# What Happens During Code Review?

Reviewers check:

- Correctness
    
- Readability
    
- Security
    
- Performance
    
- Coding standards
    
- Tests
    
- Documentation
    

They might comment:

```text
Consider validating amount > 0
```

or:

```text
Can this query be optimized?
```

Code review improves quality and shares knowledge across the team.

---

# Step 6 — Update Your Branch

While you're working, `main` continues to change.

Example:

```text
main

↓

New Login Feature

↓

Bug Fix
```

Update your branch:

```bash
git checkout main
git pull origin main
git checkout feature/payment-api
git merge main
```

Or, if your team prefers rebasing:

```bash
git rebase main
```

Always follow your team's agreed workflow.

---

# Step 7 — Merge the Feature

Once:

- PR approved
    
- CI passed
    
- Tests passed
    

Merge:

```text
feature/payment-api

↓

main
```

Many teams use **Squash Merge**.

Result:

```text
main

↓

Payment API
```

instead of many intermediate commits.

---

# Step 8 — Delete the Branch

After merging:

Delete locally:

```bash
git branch -d feature/payment-api
```

Delete remotely:

```bash
git push origin --delete feature/payment-api
```

This keeps the repository tidy.

# Advantages

✅ Isolates unfinished work

✅ Keeps `main` stable

✅ Easier code reviews

✅ Parallel development

✅ Better testing

✅ Easier rollback (by reverting a merge or specific commit)

---

# Disadvantages

⚠ Long-lived branches can drift from `main` and create merge conflicts.

⚠ Developers must regularly sync with `main`.

⚠ Large feature branches are harder to review.

---

# Keeping Branches Small

Instead of one giant branch:

```text
feature/new-dashboard
```

for three weeks,

split it into:

```text
feature/dashboard-layout

feature/dashboard-api

feature/dashboard-charts
```

Smaller branches mean:

- Faster reviews
    
- Fewer conflicts
    
- Easier testing

# Common Mistakes

❌ Developing directly on `main`

❌ Creating huge branches with hundreds of commits

❌ Never updating from `main`

❌ Mixing unrelated features in one branch

Example:

```text
Payment API

+

Dark Theme

+

Documentation
```

Each should have its own branch.

---

# Best Practices

✅ One feature per branch.

✅ Update your branch regularly.

✅ Keep commits small and meaningful.

✅ Open Pull Requests early for feedback.

✅ Delete merged branches.

# Useful Commands Summary

|Command|Purpose|
|---|---|
|`git checkout main`|Switch to `main`|
|`git pull origin main`|Update `main`|
|`git checkout -b feature/name`|Create a feature branch|
|`git add .`|Stage changes|
|`git commit -m "message"`|Commit changes|
|`git push origin feature/name`|Push the branch|
|`git merge main`|Bring the latest `main` changes into your branch|
|`git branch -d feature/name`|Delete the local branch|
|`git push origin --delete feature/name`|Delete the remote branch|

# Interview Questions

### 1. What is a Feature Branch Workflow?

It is a Git workflow where each feature, bug fix, or enhancement is developed in its own branch and merged into `main` only after review and testing.

---

### 2. Why shouldn't developers commit directly to `main`?

Because it can make the main branch unstable, introduce unfinished work, and bypass code review and automated checks.

---

### 3. When should a feature branch be deleted?

After it has been successfully merged into the target branch and is no longer needed.

---

### 4. Why should feature branches be kept small?

Smaller branches are easier to review, test, merge, and maintain. They also reduce the likelihood of merge conflicts.

---

### 5. What should you do if `main` changes while you're working?

Regularly update your feature branch by merging or rebasing the latest changes from `main`, following your team's workflow.

## 💡 Backend Engineer Tip

In many backend teams, a feature branch represents a **single unit of work**—often linked to a ticket in Jira, Linear, or GitHub Issues. Keeping branches focused and short-lived makes code reviews faster, CI pipelines quicker, and releases more predictable.
