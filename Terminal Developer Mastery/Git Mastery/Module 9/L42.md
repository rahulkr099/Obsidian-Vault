# What is Git Flow?

**Git Flow** is a branching strategy introduced by **Vincent Driessen** in 2010.

Instead of having only a `main` branch and short-lived feature branches, Git Flow introduces several long-lived branches with specific responsibilities.

The core idea is to separate:

- Development
    
- Releases
    
- Production
    
- Emergency fixes
    

---

# Git Flow Branches

A typical Git Flow repository contains:

```text
main
develop
feature/*
release/*
hotfix/*
```

Each branch has a specific purpose.

---

# The Overall Structure

```text
                    feature/login
                   /
main ─────────────┐
                  │
                  └──── develop ───── feature/payment
                          │
                          └──── feature/report

                  release/v1.2
                        │
                        ▼
                      main
                        ▲
                  hotfix/v1.2.1
```

---

# The `main` Branch

The `main` branch represents **production-ready code**.

Rules:

- Stable only
    
- Tagged releases only
    
- No direct development
    

Example:

```text
main

↓

v1.0.0

↓

v1.1.0

↓

v1.2.0
```

Every commit on `main` should be deployable.

---

# The `develop` Branch

The `develop` branch is where daily development happens.

Example:

```text
main

↓

Production
```

```text
develop

↓

Current Development
```

Features are merged into `develop`, **not directly into `main`**.

---

# Feature Branches

Every new feature starts from `develop`.

```bash
git checkout develop
git checkout -b feature/payment-api
```

Workflow:

```text
develop

↓

feature/payment-api

↓

Commits

↓

Merge

↓

develop
```

Notice:

The feature does **not** go to `main`.

---

# Release Branches

When enough features are complete:

Create a release branch.

```bash
git checkout develop
git checkout -b release/v1.3.0
```

Purpose:

- Final testing
    
- Documentation
    
- Version updates
    
- Bug fixes
    

No new features are added.

---

# Release Workflow

```text
develop

↓

release/v1.3.0

↓

Testing

↓

Bug Fixes

↓

main

↓

Tag v1.3.0
```

After release:

Merge back into `develop`.

This ensures release-specific fixes are not lost.

---

# Hotfix Branches

Suppose production has a critical bug.

Create:

```bash
git checkout main
git checkout -b hotfix/v1.3.1
```

Workflow:

```text
main

↓

hotfix/v1.3.1

↓

Fix

↓

main

↓

Tag v1.3.1
```

Then merge the hotfix into:

- `develop`
    
- Any active release branch (if applicable)

# Advantages

✅ Clear separation of production and development

✅ Easy release management

✅ Supports parallel feature development

✅ Excellent for scheduled releases

✅ Good support for maintenance versions

---

# Disadvantages

❌ Many branches

❌ More merging

❌ More complex

❌ Slower release process

❌ Can be excessive for small teams

---

# Git Flow vs Feature Branch Workflow

|Feature Branch Workflow|Git Flow|
|---|---|
|`main` + feature branches|Multiple long-lived branches|
|Simpler|More structured|
|Faster releases|Scheduled releases|
|Less merging|More merging|
|Popular in startups|Popular in larger or release-driven teams|

---

# Git Flow vs GitHub Flow

GitHub Flow:

```text
main

↓

feature

↓

PR

↓

main
```

Git Flow:

```text
main

↓

develop

↓

feature

↓

release

↓

main
```

GitHub Flow is simpler.

Git Flow is more structured.

---

# Where is Git Flow Used?

Git Flow works well when:

- Multiple versions must be maintained
    
- Releases follow a schedule (e.g., monthly or quarterly)
    
- QA teams test release branches
    
- Production fixes are carefully managed
    

Examples:

- Enterprise software
    
- Desktop applications
    
- Banking systems
    
- ERP software
    

---

# Where Git Flow is Less Suitable

Git Flow is often **not** the first choice when:

- Deploying many times per day
    
- Using Continuous Deployment
    
- Working in a very small team
    
- Building fast-moving startups
    

These teams often prefer GitHub Flow or Trunk-Based Development because they reduce branching complexity.

# Common Mistakes

❌ Creating features directly from `main`

Correct:

```text
develop

↓

feature
```

---

❌ Forgetting to merge release fixes back into `develop`

---

❌ Long-running feature branches that diverge significantly from `develop`

---

❌ Using Git Flow for very small projects where a simpler workflow would be easier to maintain

---

# Best Practices

✅ Keep `main` production-ready.

✅ Create features from `develop`.

✅ Create release branches only when preparing a release.

✅ Merge hotfixes back into both `main` and `develop`.

✅ Tag every production release.

# Useful Commands Summary

|Command|Purpose|
|---|---|
|`git checkout develop`|Switch to development branch|
|`git checkout -b feature/login`|Create feature branch|
|`git checkout -b release/v1.2`|Create release branch|
|`git checkout -b hotfix/v1.2.1 main`|Create hotfix branch|
|`git merge feature/login`|Merge feature into `develop`|
|`git tag -a v1.2.0 -m "Release"`|Tag a production release|

# Interview Questions

### 1. What is Git Flow?

Git Flow is a branching strategy that uses dedicated branches for development, features, releases, and hotfixes to organize software delivery.

---

### 2. What is the purpose of the `develop` branch?

It is the integration branch where completed feature branches are merged before preparing a release.

---

### 3. What is a release branch?

A temporary branch created from `develop` to stabilize a version through testing and bug fixes before merging into `main`.

---

### 4. From which branch should a hotfix be created?

From the current production branch, typically `main`.

---

### 5. Is Git Flow always the best workflow?

No. It is well suited to structured release processes but may be unnecessarily complex for teams that deploy continuously or frequently.

## 💡 Backend Engineer Tip

Git Flow is an excellent workflow to understand because it teaches disciplined release management. However, many modern backend teams—especially startups practicing Continuous Integration and Continuous Deployment (CI/CD)—prefer simpler workflows like **GitHub Flow** or **Trunk-Based Development** to reduce merge complexity and ship features faster. Knowing Git Flow helps you work effectively in enterprises and understand the evolution of modern Git practices.
