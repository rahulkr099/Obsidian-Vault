# What is Trunk-Based Development?

**Trunk-Based Development (TBD)** is a Git workflow where developers integrate their work into a **single shared branch** (called the **trunk**) **frequently**.

In Git, the trunk is usually:

```text
main
```

Unlike Git Flow, branches are:

- Very short-lived
    
- Small
    
- Merged quickly
    

Sometimes teams even commit directly to the trunk (with strict automation), though many still use very short-lived branches and Pull Requests.

---

# Why "Trunk"?

Historically, version control systems called the primary development line the **trunk**.

Git uses:

```text
main
```

So in Git:

```text
Trunk

=

main
```

---

# Core Principle

The biggest idea behind TBD is:

> **Integrate early and integrate often.**

Instead of waiting days or weeks:

```text
Developer

↓

1 Week

↓

Merge
```

Developers integrate:

```text
Developer

↓

Several Times Per Day

↓

Merge
```

Small changes reduce integration problems.

---

# Git Flow vs Trunk-Based Development

Git Flow:

```text
main

↓

develop

↓

feature

↓

release

↓

main
```

Lots of branches.

---

Trunk-Based Development:

```text
main

↓

Tiny Branch

↓

Merge

↓

Tiny Branch

↓

Merge
```

Much simpler.

---

# Why Use Trunk-Based Development?

Imagine 20 backend developers.

If everyone keeps feature branches open for two weeks:

```text
Developer A

↓

200 commits
```

Developer B:

```text
↓

180 commits
```

Developer C:

```text
↓

150 commits
```

Eventually:

```text
Huge Merge Conflicts
```

Instead:

```text
Small Merge

↓

Small Merge

↓

Small Merge
```

Much easier.

# Why Automated Tests Matter

Suppose everyone merges several times per day.

Without tests:

```text
main

↓

Broken
```

Everyone is blocked.

Instead:

```text
Tests

↓

Pass

↓

```

This keeps the trunk healthy.

---

# Keeping `main` Green

Teams often say:

> **Keep the trunk green.**

Meaning:

```text
All Tests Pass
```

at all times.

Never knowingly merge broken code.

# Feature Flags

One challenge:

Suppose a feature isn't finished.

How can it be merged?

Answer:

**Feature Flags**

Example:

```javascript
if (featureFlags.newDashboard) {
    showNewDashboard();
} else {
    showOldDashboard();
}
```

The code exists:

```text
Merged
```

But users don't see it yet.

---

# GitHub Flow vs Trunk-Based Development

|GitHub Flow|Trunk-Based Development|
|---|---|
|Short-lived branches|Very short-lived branches|
|Frequent merges|Very frequent merges|
|CI/CD friendly|CI/CD focused|
|PRs often reviewed before merge|PRs are usually small and merged quickly|
|Good for most startups|Common in high-velocity engineering teams|

---

# Git Flow vs Trunk-Based Development

|Git Flow|TBD|
|---|---|
|Many long-lived branches|One trunk|
|Release branches|Usually no release branches|
|Scheduled releases|Continuous releases|
|More merge complexity|Less merge complexity|

# Where is Trunk-Based Development Used?

TBD is common in organizations that emphasize:

- Continuous Integration
    
- Continuous Delivery
    
- Small incremental changes
    
- Strong automation
    

It is often associated with high-performing engineering teams and has been widely discussed in industry literature and engineering conferences.

---

# When is TBD Not a Good Fit?

TBD may be difficult if:

- Automated testing is weak.
    
- CI pipelines are unreliable.
    
- Developers frequently work offline for long periods.
    
- Large changes cannot be broken into smaller increments.
    

In these situations, teams often adopt a simpler feature branch workflow first and gradually move toward TBD.

---

# Common Mistakes

❌ Long-lived branches

```text

↓

3 Weeks
```

❌ Large Pull Requests

```text
2,000 Files Changed
```

❌ Merging without tests

❌ Waiting days before integrating

---

# Best Practices

✅ Merge at least once a day (many teams merge much more frequently).

✅ Keep Pull Requests small.

✅ Use feature flags for incomplete functionality.

✅ Maintain a reliable CI pipeline.

✅ Keep `main` deployable.

# Useful Commands Summary

|Command|Purpose|
|---|---|
|`git checkout -b feature/name`|Create a short-lived branch|
|`git add .`|Stage changes|
|`git commit -m "message"`|Commit small changes|
|`git push origin feature/name`|Push branch|
|`git merge feature/name`|Merge into `main`|
|`git branch -d feature/name`|Delete merged branch|

# Interview Questions

### 1. What is Trunk-Based Development?

A workflow where developers integrate small changes into a shared main branch frequently, typically using very short-lived branches or direct commits with strong automation.

---

### 2. Why are branches short-lived in TBD?

Short-lived branches reduce merge conflicts, simplify reviews, and encourage continuous integration.

---

### 3. Why are feature flags important in TBD?

They allow incomplete features to be merged safely while keeping them hidden from users until they're ready.

---

### 4. What infrastructure is essential for TBD?

Reliable Continuous Integration, automated testing, and often Continuous Deployment.

---

### 5. Can Trunk-Based Development work without automated tests?

It's possible, but it becomes much riskier because frequent integration depends on quickly detecting regressions.

## 💡 Backend Engineer Tip

Many modern backend teams don't adopt Trunk-Based Development overnight. They often start with **GitHub Flow**, build confidence in automated testing and CI/CD, and gradually shorten branch lifetimes. As engineering practices mature, the workflow naturally evolves toward Trunk-Based Development, enabling faster and safer releases.
