# Lesson 6 — Mastering `git status`

If there is **one Git command** you should memorize, it's this:

```bash
git status
```

Professional developers run `git status` constantly.

Before:

- `git add`
    
- `git commit`
    
- `git push`
    
- `git pull`
    
- `git merge`
    
- `git switch`
    
- `git restore`
    

they almost always check the repository status first.

> **Rule:** Never guess the state of your repository. Let `git status` tell you.

# What Does `git status` Do?

It answers these questions:

- Which branch am I on?
    
- Have I modified any files?
    
- Which files are staged?
    
- Which files are untracked?
    
- Is my working tree clean?
    
- Am I in the middle of a merge or rebase?
    
- Is my local branch ahead or behind the remote?
    

Think of it as a **health check** for your Git repository.

---

# Start with a New Repository

```bash
mkdir git-status-demo
cd git-status-demo

git init
```

Check the status:

```bash
git status
```

Output:

```text
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```

Let's break this down.

---

# Understanding the Output

## Line 1

```text
On branch main
```

This tells you:

- Current branch = `main`
    

Later you'll see:

```text
On branch feature/login
```

or

```text
On branch bugfix/auth`
```

---

## Line 2

```text
No commits yet
```

Meaning:

You haven't created your first commit.

Once you commit:

```bash
git commit -m "Initial commit"
```

This line disappears.

---

## Last Line

```text
nothing to commit
```

Meaning:

Git has no tracked changes waiting to be committed.

---

# Example 1 — Untracked Files

Create a file:

```bash
touch app.js
```

Now:

```bash
git status
```

Output:

```text
Untracked files:

    app.js

nothing added to commit
```

Meaning:

Git sees the file.

But isn't tracking it.

---

# Example 2 — Stage the File

```bash
git add app.js
```

Run:

```bash
git status
```

Output:

```text
Changes to be committed:

    new file: app.js
```

This means:

Git will include `app.js` in the next commit.

---

# Example 3 — Commit It

```bash
git commit -m "Add app.js"
```

Now:

```bash
git status
```

Output:

```text
nothing to commit, working tree clean
```

Perfect.

This is what you want before pushing code.

---

# What Does "Working Tree Clean" Mean?

It means:

- No modified files
    
- No staged files
    
- No untracked files
    

Everything matches the latest commit.

Example:

```text
Repository

↓

Working Directory

↓

Exactly the same
```

---

# Example 4 — Modify a File

Edit:

```javascript
console.log("Hello");
```

Run:

```bash
git status
```

Output:

```text
Changes not staged for commit:

    modified: app.js
```

Meaning:

Git found changes.

But you haven't staged them.

---

# Example 5 — Stage Again

```bash
git add app.js
```

Status:

```text
Changes to be committed:

    modified: app.js
```

Notice the difference:

Before:

```text
Changes not staged
```

After:

```text
Changes to be committed
```

# Multiple Files

Suppose:

```text
backend/

app.js
auth.js
payment.js
README.md
```

Status:

```text
Changes to be committed:

    modified: app.js

Changes not staged:

    modified: auth.js

Untracked files:

    payment.js
```

Interpretation:

|File|State|
|---|---|
|app.js|Staged|
|auth.js|Modified|
|payment.js|Untracked|
|README.md|Clean|

# Short Status

Instead of:

```bash
git status
```

Run:

```bash
git status --short
```

Example:

```text
M  app.js
 M auth.js
?? payment.js
```

This is the format experienced developers often use.

---

# Understanding Short Status

|Symbol|Meaning|
|---|---|
|`??`|Untracked|
|`M`|Modified|
|`A`|Added|
|`D`|Deleted|
|`R`|Renamed|
|`C`|Copied|

---

# Two-Column Status

Example:

```text
MM app.js
```

Git uses two columns.

```text
XY filename
```

Where:

- First column = Staging Area
    
- Second column = Working Directory
    

---

Example:

```text
M  app.js
```

Means:

- Staged modification
    
- No further edits
    

---

Example:

```text
 M app.js
```

Means:

- Not staged
    
- Working directory modified
    

---

Example:

```text
MM app.js
```

Means:

- Staged
    
- Modified again after staging
    

This is very common.

# Real Backend Example

Imagine:

You stage:


Then continue coding.

Now:

```text

```

Meaning:

Version A:

Already staged.

# Ignored Files

Suppose `.env` is ignored.

Status won't show:

```text
.env
```

Because Git ignores it.

# Show Ignored Files

```bash
git status --ignored
```

Useful when debugging `.gitignore`.

---

# Show Branch Information

```bash
git status -sb
```

Example:

```text
## main
 M app.js
?? auth.js
```

Very compact.

Professional developers love this option.

---

# Repository Before First Commit

Output:

```text
No commits yet
```

Repository After First Commit:

```text
nothing to commit
```

This small difference tells you exactly where you are.

---

# Common Status Messages

## Clean

```text
nothing to commit, working tree clean
```

Everything saved.

---

## Modified

```text
Changes not staged for commit
```

You edited files.

---

## Ready to Commit

```text
Changes to be committed
```

Files are staged.

---

## New Files

```text
Untracked files
```

Git hasn't started tracking them.

---

## Merge Conflict

Later you'll see:

```text
Unmerged paths
```

This means Git needs help resolving conflicts.

# Daily Backend Workflow

A professional backend engineer might do:

```bash
git status

# edit code

git status

git add src/auth.js

git status

git commit -m "Add JWT validation"

git status

git push
```

Notice how `git status` is used before every important step.

---

# Best Practices

✅ Run `git status` before committing.

✅ Run it before switching branches.

✅ Run it before pulling remote changes.

✅ Learn to read the short status output.

✅ Never commit without checking what's staged.

# Mini Project

Create a small backend project:

```text
inventory-api/
├── src/
│   ├── app.js
│   ├── routes.js
│   ├── controllers/
│   └── services/
├── package.json
├── README.md
└── .env
```

Tasks:

1. Initialize Git.
    
2. Create all files.
    
3. Stage only `README.md` and `package.json`.
    
4. Check `git status`.
    
5. Modify `README.md` again **after staging it**.
    
6. Run `git status --short` and identify the status code (you should see something like `MM README.md`).
    
7. Explain in your own words what each file's status means.
