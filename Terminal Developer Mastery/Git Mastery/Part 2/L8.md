# What is a Commit?

A **commit** is a **snapshot** of your project at a specific point in time.

Imagine you're building an Express backend.

Version 1:

```text
Login API
```

↓

Commit

↓

Version 2:

```text
JWT Authentication
```

↓

Commit

↓

Version 3:

```text
Password Reset
```

↓

Commit

↓

Version 4:

```text
User Profile API
```

Each commit saves the current state of your project.

---

# Git Timeline

```text
Commit A

↓

Commit B

↓

Commit C

↓

Commit D

↓

Commit E
```

Git stores these snapshots so you can always return to an earlier version if needed.

# Create a Practice Repository

```bash
mkdir commit-demo
cd commit-demo

git init
```

Create a file:

```bash
echo "# Backend API" > README.md
```

Stage it:

```bash
git add README.md
```

Commit it:

```bash
git commit -m "Initial commit"
```

Example output:

```text
[main (root-commit) a1b2c3d] Initial commit
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
```

---

# Breaking Down the Output

```text
[main
```

Current branch.

---

```text
(root-commit)
```

This is the very first commit.

Later commits won't show this.

---

```text
a1b2c3d
```

This is the **short commit hash**.

Every commit gets a unique identifier.

---

# Commit Hash

Example:

```text
9d3ab95
```

Full hash:

```text
9d3ab95e84b6cfcb68498b73c1f8fd673ea29f63
```

Git generates this automatically.

No two commits have the same hash.

---

# Think of the Commit Hash Like a Fingerprint

Every commit has a unique identity.

```text
Commit A

↓

f3ac2d1
```

↓

```text
Commit B

↓

91be8fd
```

↓

```text
Commit C

↓

7d84af2
```

Git uses these hashes to locate commits.

A commit stores:

- Project snapshot
    
- Commit message
    
- Author
    
- Email
    
- Date and time
    
- Parent commit
    
- Commit hash
    

Example:

```text
Commit

↓

Hash

↓

Author

↓

Timestamp

↓

Message

↓

Project Snapshot
```

# Writing Commit Messages

The message should explain **what changed**, not **how**.

Good:

```text
Add JWT authentication
```

Good:

```text
Fix login validation bug
```

Good:

```text
Implement password reset endpoint
```

Bad:

```text
Update
```

Bad:

```text
Changes
```

Bad:

```text
asdf
```

Bad:

```text
Fix
```

---

# Good vs Bad Examples

## Good

```text
Add user authentication middleware
```

You immediately know what happened.

---

## Bad

```text
Code update
```

What update?

Nobody knows.

---

# Professional Commit Style

Use the **imperative mood**.

Good:

```text
Add login API
```

Good:

```text
Fix JWT bug
```

Good:

```text
Remove unused middleware
```

Avoid:

```text
Added login API
```

Avoid:

```text
Fixed login
```

Git itself uses the imperative style because it reads naturally as an instruction:

> "If applied, this commit will **Add login API**."

# Multi-line Commit Messages

Sometimes a one-line message isn't enough.

Run:

```bash
git commit
```

Git opens Neovim (because you configured it in Lesson 3).

Example:

```text
Add JWT authentication

Implement middleware for token verification.

Protect profile endpoints.

Add unit tests.
```

The first line is the **subject**.

The remaining lines form the **body**.

---

# Commit Message Structure

```text
Subject (≤ 50 characters)

Blank line

Explanation
```

Example:

```text
Add JWT authentication

Protect private routes using Express middleware.

Return 401 for invalid or expired tokens.

Add tests for authorization failures.
```

This format becomes valuable when commits need extra context.

# The `-m` Option

Instead of opening an editor:

```bash
git commit -m "Add login API"
```

This is the most common way to create short commits.

---

# Commit All Tracked Files

Suppose you've modified only tracked files.

Instead of:

```bash
git add app.js

git commit -m "Fix bug"
```

You can use:

```bash
git commit -am "Fix bug"
```

The `-a` option automatically stages **modified and deleted tracked files** before committing.

⚠️ It **does not** include new untracked files.

Example:

```text
New file:

payment.js
```

`git commit -am` will **not** commit `payment.js`.

You still need:

```bash
git add payment.js
```

# Backend Example

Suppose you've completed JWT authentication.

Good commit:

```text
Add JWT authentication middleware
```

Next feature:

```text
Implement refresh token endpoint
```

Next bug:

```text
Fix password validation logic
```

Notice how each commit represents **one logical change**.

---

# Atomic Commits

Professional developers create **atomic commits**.

One commit = one idea.

Good:

```text
Commit 1

Add login endpoint
```

Commit 2:

```text
Fix login validation
```

Commit 3:

```text
Add login tests
```

Bad:

```text
JWT

README

Docker

CSS

Tests

API

Everything
```

One giant commit is difficult to review and debug.

---

# Verify Before Committing

Always check:

```bash
git status
```

Then:

```bash
git diff --cached
```

This shows exactly what is staged for the next commit.

Finally:

```bash
git commit -m "..."
```

This habit helps prevent accidental commits.

---

# Common Mistakes

## Mistake 1

Writing:

```text
Update
```

Too vague.

---

## Mistake 2

Committing unrelated work together.

Example:

- Authentication
    
- Docker
    
- README
    
- Database migration
    

Split them into separate commits.

---

## Mistake 3

Skipping `git status`.

You might commit files you didn't intend to include.

---

## Mistake 4

Using `git commit -am` for new files.

Remember:

`-a` ignores untracked files.

---

# Best Practices

- Commit frequently.
    
- Keep commits small.
    
- One logical change per commit.
    
- Write clear messages.
    
- Review staged changes before committing.
    
- Use the commit body for complex changes.

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git commit -m "Message"`|Create a commit|
|`git commit`|Open editor for a detailed message|
|`git commit -am "Message"`|Stage tracked changes and commit|
|`git log`|Show full history|
|`git log --oneline`|Compact history|
|`git diff --cached`|Show staged changes|
