# Module 2 — Daily Git Workflow

# Lesson 9 — Exploring History with `git log`, `git show`, and `git diff`

Writing commits is only half of Git.

The other half is **reading history**.

Professional backend engineers constantly ask questions like:

- Who changed this file?
    
- When was this bug introduced?
    
- What exactly changed?
    
- Which commit broke the API?
    
- How did this function look yesterday?
    

Git provides powerful tools to answer these questions.

# `git log`

The most basic history command:

```bash
git log
```

Example:

```text
commit 8d9f4e3...

Author: Rahul

Date: Fri Jul 31 10:20:30 2026

    Add Docker support

commit 4f2ab91...

Author: Rahul

Date: Thu Jul 30 18:45:02 2026

    Add JWT authentication
```

Newest commits appear first.

# Compact History

Most developers prefer:

```bash
git log --oneline
```

Example:

```text
8d9f4e3 Add Docker support

4f2ab91 Add JWT authentication

d67b4e1 Implement login API

5acb2fd Setup Express server

8f62aa0 Initial commit
```

Much easier to read.

---

# Beautiful Graph View

One of the most useful commands:

```bash
git log --oneline --graph --decorate
```

Example:

```text
* 8d9f4e3 (HEAD -> main) Add Docker support
* 4f2ab91 Add JWT authentication
* d67b4e1 Implement login API
* 5acb2fd Setup Express server
* 8f62aa0 Initial commit
```

Explanation:

- `*` → Commit
    
- `HEAD` → Your current position
    
- `main` → Current branch
    

This is the same command you aliased as:

```bash
git lg
```

in Lesson 3.

# What is a Diff?

A **diff** shows the difference between two versions.

Example:

Before:

```javascript
const PORT = 3000;
```

After:

```javascript
const PORT = 5000;
```

Git displays:

```diff
- const PORT = 3000;
+ const PORT = 5000;
```

Legend:

- `-` Removed
    
- `+` Added
    

---

# `git diff`

Suppose you modify:

```javascript
console.log("Hello");
```

to:

```javascript
console.log("Hello Git");
```

Before staging:

```bash
git diff
```

Output:

```diff
-console.log("Hello");
+console.log("Hello Git");
```

This compares:

**Working Directory** ↔ **Staging Area**

---

# `git diff --cached`

Suppose you run:

```bash
git add app.js
```

Now:

```bash
git diff
```

shows nothing because the working directory matches the staging area.

Instead:

```bash
git diff --cached
```

shows:

```diff
-console.log("Hello");
+console.log("Hello Git");
```

This compares:

**Staging Area** ↔ **Last Commit**

---

# Comparing Two Commits

Suppose:

```text
Commit A

↓

Commit B
```

Run:

```bash
git diff A B
```

Example:

```bash
git diff 5acb2fd d67b4e1
```

Git shows every change between those commits.

---

# Compare Two Branches

Later, when you learn branches:

```bash
git diff main feature/login
```

Git shows everything different between the two branches.

---

# Show Changes to One File

```bash
git diff app.js
```

Only displays differences for `app.js`.

Useful in large backend projects.


No code, just file names.

# Search Commit Messages

Search for commits mentioning "JWT":

```bash

```

Who changed `auth.js`?


Shows only commits affecting that file.

# Backend Example

Suppose:

```text
src/

auth.js

user.js

payment.js
```

Need to know when `auth.js` changed?

```bash
git log src/auth.js
```

Need to know what changed?

```bash
git show <commit_hash>
```

Need to compare two versions?

```bash
git diff hash1 hash2 -- src/auth.js
```

This is a common debugging workflow.

# Reading Diffs

Example:

```diff
@@

- app.listen(3000)

+ app.listen(5000)
```

Meaning:

Removed:

```javascript
app.listen(3000)
```

Added:

```javascript
app.listen(5000)
```

# Common Mistakes

## Mistake 1

Using:

```bash
git diff
```

after staging changes.

It shows nothing.

Use:

```bash
git diff --cached
```

instead.

---

## Mistake 2

Using the full 40-character commit hash.

Usually the first 7–10 characters are enough if they're unique.

---

## Mistake 3

Ignoring commit history.

Professional developers use `git log` frequently to understand how a project evolved.

---

# Professional Workflow

Before pushing:

```bash
git status

git diff --cached

git log --oneline -5

git push
```

This helps ensure:

- Correct files are staged.
    
- The changes look as expected.
    
- Your commit history is clean.
    

---

# Best Practices

- Use `git log --oneline` for everyday history.
    
- Use `git lg` if you've created the alias.
    
- Review staged changes with `git diff --cached`.
    
- Search history instead of guessing.
    
- Learn to read diffs—they are essential for code reviews.

# Cheat Sheet

|Command|Purpose|
|---|---|
|`git log`|Full history|
|`git log --oneline`|Compact history|
|`git log --graph --decorate --oneline`|Graph view|
|`git log -5`|Last 5 commits|
|`git show`|Latest commit details|
|`git show <hash>`|Specific commit|
|`git diff`|Working Directory vs Staging Area|
|`git diff --cached`|Staging Area vs Last Commit|
|`git diff hash1 hash2`|Compare commits|
|`git log --grep="text"`|Search commit messages|
|`git log file`|History of a file|

## Professional Tip

When debugging a production issue, experienced backend engineers often follow this sequence:

```bash
git log --oneline          # Find the relevant commit
git show <commit_hash>     # Inspect exactly what changed
git diff old_hash new_hash # Compare versions if needed
```

Learning these three commands well will make you much more effective at understanding and debugging code changes.
