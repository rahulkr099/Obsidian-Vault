# The Problem Without Branches

Imagine a backend team working on the same project.

```
Rahul
│
├── Login API
│
├── JWT
│
├── Payment API
│
├── Docker
│
└── Bug Fix
```

Everyone edits the same files.

Problems:

- Broken code
    
- Incomplete features
    
- Difficult debugging
    
- Constant conflicts
    

Without branches, teamwork becomes chaotic.

---

# The Solution

Each developer gets their **own branch**.

```
main
│
├── feature/login
│
├── feature/payment
│
├── feature/docker
│
└── bugfix/jwt
```

Each branch is isolated.

Developers work independently.

When ready:

→ Merge into `main`.

---

# What is a Branch?

A **branch** is simply an independent line of development.

Think of it like this:

```
main

↓

Initial Project
```

Now you create a branch:

```
main

↓

Initial Project
       \
        \
feature/login
```

Both branches start at the same commit.

Then they evolve independently.

---

# Git Branches Are Cheap

One common misconception:

> "Creating branches copies the project."

No.

Git **does not duplicate the repository**.

A branch is simply a **pointer to a commit**.

Example:

```
Commit A

↓

Commit B ← main
```

Create a branch:

```
Commit A

↓

Commit B ← main
          ↑
     feature/login
```

Nothing is copied.

Both branches point to the same commit.

---

# Branches Grow Independently

Suppose you add two commits.

```
Commit A

↓

Commit B

↓

Commit C

↓

Commit D ← feature/login
```

Meanwhile `main` stays here:

```
Commit A

↓

Commit B ← main
```

The feature branch has moved forward.

`main` remains stable.

Suppose users are using your API.

Stable version:


No.

# View Branches

Run:

```bash
git branch
```

Example:

```text
* main
```

The `*` means:

Current branch.

---

# Create a Branch

```bash
git branch feature/login
```

Now:

```bash
git branch
```

Output:

```text
feature/login

* main
```

Notice:

You're **still on `main`**.

Creating a branch does **not** switch to it.

---

# Switch Branches

Move to the new branch:

```bash
git switch feature/login
```

Output:

```text
Switched to branch 'feature/login'
```

Now:

```bash
git branch
```

Output:

```text
* feature/login

main
```

---

# Older Way

You'll often see:

```bash
git checkout feature/login
```

This still works.

Modern Git recommends:

```bash
git switch
```

because it's more focused and less confusing.

---

# Create and Switch

Instead of two commands:

```bash
git branch feature/payment

git switch feature/payment
```

Use:

```bash
git switch -c feature/payment
```

Equivalent older syntax:

```bash
git checkout -b feature/payment
```

---

# Branch Naming

Professional examples:

```
feature/login

feature/payment

feature/profile-api

bugfix/token-expiry

hotfix/security

docs/api

refactor/auth-service

test/login
```

Avoid:

```
branch1

test123

new

temp

rahul
```

Names should describe the work.

# Switching Back

```bash
git switch main
```

What happens?

Git restores your files to match `main`.

You're no longer looking at the login feature.

This surprises many beginners.

Remember:

> **Each branch has its own snapshot of the project.**

# Common Mistakes

## Mistake 1

Doing every feature directly on `main`.

Bad:

```
main

↓

Everything
```

Better:

```
main

↓

feature/auth

↓

Merge

↓

feature/payment

↓

Merge
```

---

## Mistake 2

Giving branches meaningless names.

Bad:

```
branch2
```

Good:

```
feature/user-profile
```

---

## Mistake 3

Forgetting which branch you're on.

Always check:

```bash
git status
```

or

```bash
git branch
```

---

# Best Practices

- Keep `main` stable.
    
- One feature per branch.
    
- Delete merged branches.
    
- Use descriptive names.
    
- Switch branches frequently instead of mixing unrelated work.
    

---

# Useful Commands

|Command|Purpose|
|---|---|
|`git branch`|List branches|
|`git branch name`|Create branch|
|`git switch name`|Switch branch|
|`git switch -c name`|Create and switch|
|`git checkout name`|Older way to switch|
|`git checkout -b name`|Older way to create and switch|

Create a repository:

```bash
mkdir branch-lab

git init

echo "# Inventory API" > README.md

git add README.md

git commit -m "Initial commit"
```

Practice branching:

```bash
git branch

git branch feature/login

git branch feature/payment

git branch bugfix/auth

git branch
```

Switch branches:

```bash
git switch feature/login

git branch

git switch main

git switch feature/payment

git switch main
```

Observe how the current branch (`*`) changes.

# Mini Project

Use your `notes-api` repository.

Create these branches:

```text
feature/auth

feature/notes

feature/search

bugfix/token-validation

docs/api
```

Tasks:

1. Create all five branches.
    
2. Switch to `feature/auth`.
    
3. Add a file named `auth.js`.
    
4. Commit the change.
    
5. Switch back to `main`.
    
6. Verify that `auth.js` is **not present** on `main`.
    
7. Switch back to `feature/auth`.
    
8. Confirm that `auth.js` reappears.
    

This exercise demonstrates one of the most important ideas in Git: **each branch has its own view of the project**.

## Professional Tip

Many backend engineers keep several branches active at the same time:

- `main` → Stable production code
    
- `develop` → Integration branch (in some workflows)
    
- `feature/*` → New features
    
- `bugfix/*` → Bug fixes
    
- `hotfix/*` → Emergency production fixes
