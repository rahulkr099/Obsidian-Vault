# The Problem: "It Works on My Machine"

Imagine you're building an Express application.

Project:

```
URL Shortener API
```

Your setup:

```
Node.js 22
MongoDB 8
Redis 8
Ubuntu
```

Everything works perfectly.

You push your code to GitHub.

Your teammate pulls it and gets:

```
npm install
```

Immediately:

```
❌ Dependency error

❌ MongoDB version mismatch

❌ Node version mismatch

❌ Redis missing

❌ Environment differences
```

You say:

> "But it works on my machine."

This became one of the biggest problems in software engineering.

---

# Traditional Solution

Everyone manually installs:

- Node.js
- npm
- MongoDB
- Redis
- Git
- Environment variables
- Configuration files

Every developer ends up with a slightly different environment.

Example:

|Developer|Node|MongoDB|Redis|
|---|---|---|---|
|Rahul|22|8.0|8|
|Alice|20|7.0|Not Installed|
|Bob|18|6.0|7|

The application behaves differently for each developer.

---

# Virtual Machines

One early solution was to give every developer a virtual machine.

```
Laptop
│
├── Host OS
│
└── Virtual Machine
    ├── Guest OS
    ├── Node
    ├── MongoDB
    ├── Redis
    └── App
```

This solved consistency, but introduced new problems.

---

# Problems with Virtual Machines

- Heavy (often several GB)
- Slow startup
- High RAM usage
- High CPU usage
- Duplicate operating systems
- Slow file sharing

Example:

A VM might require:

- 4 GB RAM
- 40 GB Disk
- 2 CPU cores

Just to run one backend.

---

# Containers

Containers take a different approach.

Instead of virtualizing **hardware**, they virtualize the **application environment**.

```
Host OS
│
├── Docker Engine
│
├── Express Container
├── MongoDB Container
├── Redis Container
└── Nginx Container
```

Notice:

There is **one operating system**, shared by all containers.

---

# Containers vs Virtual Machines

|Virtual Machine|Container|
|---|---|
|Includes full OS|Shares host kernel|
|Large (GBs)|Small (MBs)|
|Slow startup|Starts in seconds|
|Heavy RAM usage|Lightweight|
|Hardware virtualization|OS-level virtualization|
|Good isolation|Efficient isolation|

# What Is a Container?

A container is:

> **A running isolated process packaged with everything the application needs.**

It includes:

- Node.js
- Dependencies
- Application code
- Configuration
- Required libraries

But **not** a full operating system.

---

# What Is an Image?

Think of an image as a blueprint.

Example:

```
Node Image
```

contains:

```
Linux Filesystem
Node.js
npm
```

You **cannot** run an image directly.

You create a **container** from it.

---

# Image vs Container

Image:

```
Blueprint
```

Container:

```
Running application
```

Analogy:

|Image|Container|
|---|---|
|Recipe|Cooked meal|
|Blueprint|House|
|Class|Object|
|ISO file|Running operating system|

- Tiny one-off shell scripts

- GUI-heavy desktop applications (unless you have a specific need)

Docker is most valuable when consistency and reproducibility matter.

# Common Misconceptions

## ❌ Docker is a Virtual Machine

No.

Containers share the host kernel.

---

## ❌ Docker Replaces Linux

No.

Docker runs **on top of** Linux features (or a Linux VM on Windows/macOS).

---

## ❌ Containers Are Permanent

Containers are meant to be disposable.

Important data should live in **volumes**, which we'll cover later.

# Best Practices

- Treat containers as **ephemeral** (replaceable).
- Keep one primary responsibility per container.
- Don't store important data inside the container filesystem.
- Version your images using tags.

---

# Common Mistakes

### Installing Everything on the Host

Avoid relying on your local machine for project dependencies when a container can provide a reproducible environment.

---

### Thinking Containers Replace Backups

Containers are disposable.

Your **data** is not.

Use persistent storage (volumes) and backups.

---

### One Giant Container

Don't put:

- Express
- MongoDB
- Redis
- Nginx

all inside one container.

Prefer one service per container.

## 💡 Backend Engineer Insight

One of the biggest mindset shifts is this:

> **Don't configure machines. Configure applications.**

Instead of documenting dozens of setup steps in a `README`, you define the environment once in Docker. Anyone—whether it's a teammate, a CI pipeline, or a production server—can run the same image and get the same behavior.

In **Lesson 2**, we'll install Docker, explore its architecture (Docker Engine, CLI, daemon, registries), and learn how these components work together before running your first container.
