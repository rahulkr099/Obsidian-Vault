# Module 3 — Lesson 12: Debugging Docker Containers 🔍

> **"Writing Docker containers is a skill. Debugging Docker containers is what makes you a backend engineer."**

Every backend developer eventually sees errors like:

```
Container exited immediately
Connection refused
Cannot connect to MongoDB
Port already in use
Permission denied
```

The difference between a junior and a senior engineer is often **how quickly they can find the root cause**.

This lesson teaches a systematic debugging workflow.

---

- Debug failed containers
- Read Docker logs effectively
- Inspect running containers
- Debug networking issues
- Debug volumes and file permissions
- Troubleshoot Docker Compose
- Develop a production debugging workflow

# The Debugging Mindset

Never guess.

Follow this flow:

```
Problem

↓

Observe

↓

Collect Information

↓

Find Root Cause

↓

Fix

↓

Verify
```

Avoid randomly changing files hoping something works.

---

# The 7-Step Docker Debugging Workflow

```
1. Is the container running?

↓

2. Read logs

↓

3. Inspect container

↓

4. Check environment variables

↓

5. Check networking

↓

6. Check volumes/files

↓

7. Rebuild if needed
```

Memorize this sequence.

---

# Step 1 — Is the Container Running?

```bash
docker ps
```

Running containers:

```
CONTAINER ID

STATUS

Up 10 minutes
```

Stopped containers:

```bash
docker ps -a
```

Example:

```
Exited (1)
Exited (137)
Exited (0)
```

The exit code is your first clue.

---

# Common Exit Codes

|Exit Code|Meaning|
|---|---|
|0|Program finished normally|
|1|General application error|
|125|Docker couldn't start the container|
|126|Command exists but isn't executable|
|127|Command not found|
|130|Stopped with Ctrl+C|
|137|Killed (often SIGKILL or OOM)|
|143|Graceful termination (SIGTERM)|

---

# Step 2 — Read Logs

Most problems appear immediately.

```bash
docker logs my-app
```

Follow logs live:

```bash
docker logs -f my-app
```

Last 50 lines:

```bash
docker logs --tail 50 my-app
```

Include timestamps:

```bash
docker logs -t my-app
```

---

# Example

```
Error:

Cannot find module express
```

Cause:

```
Dependencies not installed
```

---

# Another Example

```
MongoNetworkError
```

Possible causes:

- MongoDB isn't running
- Wrong connection string
- Wrong hostname
- Firewall or network issue

---

# Step 3 — Inspect Container

```bash
docker inspect my-app
```

This shows:

- Environment variables
- Mounted volumes
- Networks
- Ports
- Restart policy
- IP address
- Image information

Useful when your container isn't behaving as expected.

---

# Step 4 — Enter the Container

```bash
docker exec -it my-app sh
```

Or:

```bash
docker exec -it my-app bash
```

Inside:

```bash
pwd
ls
env
cat package.json
```

Now you can verify what's actually inside the container.

---

# Check Running Processes

```bash
ps aux
```

Or:

```bash
top
```

Confirm your Node application is running.

---

# Check Files

```bash
ls -la
```

Suppose:

```
server.js
```

is missing.

Maybe:

```docker
COPY . .
```

didn't copy what you expected.

---

# Step 5 — Verify Environment Variables

Inside container:

```bash
env
```

Or:

```bash
printenv
```

Expected:

```
PORT=5000

NODE_ENV=production
```

Missing?

Maybe:

- `.env` wasn't loaded
- `docker compose` configuration is wrong
- Variable name is misspelled

---

# Step 6 — Debug Networking

List networks:

```bash
docker network ls
```

Inspect:

```bash
docker network inspect my-network
```

Shows:

- Connected containers
- IP addresses
- DNS names

---

# Test Connectivity

Inside backend:

```bash
docker exec -it backend sh
```

Try:

```bash
ping mongodb
```

If `ping` isn't available (common in minimal images), use:

```bash
getent hosts mongodb
```

or test the application directly.

If it fails:

- Wrong service name
- Different network
- MongoDB not running

---

# Wrong Connection String

Wrong:

```
mongodb://localhost:27017/app
```

Correct:

```
mongodb://mongodb:27017/app
```

Remember:

Inside Docker,

```
localhost

=

the current container
```

---

# Check Listening Ports

Inside:

```bash
ss -tulpn
```

Or:

```bash
netstat -tulpn
```

Verify your application is listening on the expected port.

---

# Step 7 — Debug Volumes

List:

```bash
docker volume ls
```

Inspect:

```bash
docker volume inspect mongo-data
```

Check mounted files:

```bash
ls /data/db
```

If files disappear:

- Wrong mount path
- Wrong volume
- Container recreated without a persistent volume

---

# Permission Problems

Example:

```
Permission denied
```

Check:

```bash
ls -l
```

See ownership:

```bash
id
```

Sometimes the application runs as a different user than the file owner.

---

# Debug Docker Compose

Running services:

```bash
docker compose ps
```

Logs:

```bash
docker compose logs
```

Backend only:

```bash
docker compose logs backend
```

Follow logs:

```bash
docker compose logs -f backend
```

---

# Validate Compose File

```bash
docker compose config
```

This shows the final configuration after:

- Variable substitution
- Merged configuration
- Defaults

Very useful for spotting mistakes.

---

# Rebuild Properly

Changed Dockerfile?

```bash
docker compose up --build
```

Need a clean rebuild?

```bash
docker compose build --no-cache
```

---

# Remove Old Containers

```bash
docker compose down
```

Or:

```bash
docker compose down -v
```

Only use `-v` if you're okay removing volumes too.

---

# Debug Image Contents

Start a shell instead of your application:

```bash
docker run -it --entrypoint sh my-app
```

Now inspect:

```bash
ls
cat package.json
```

Great for checking whether your image contains the expected files.

---

# Health Checks

View health:

```bash
docker inspect my-app
```

Look for:

```
State

↓

Health

↓

healthy
```

Possible states:

```
healthy

unhealthy

starting
```

---

# Restart Loops

Example:

```
Restarting (1)
Restarting (1)
Restarting (1)
```

Usually means:

- App crashes immediately
- Missing environment variable
- Database unavailable
- Invalid startup command

Start with the logs.

---

# Debugging Build Failures

Example:

```
npm ERR!
```

Possible causes:

- Wrong Node version
- Network issue
- Invalid `package.json`
- Dependency conflict

---

# Debugging "Port Already in Use"

Error:

```
Bind for 0.0.0.0:5000 failed
```

Check:

```bash
docker ps
```

Or on Linux:

```bash
ss -tulpn | grep 5000
```

Solution:

- Stop the existing process
- Or use another host port

Example:

```bash
docker run -p 5001:5000 my-app
```

---

# Debugging Slow Builds

Possible causes:

- Large build context
- Missing `.dockerignore`
- Poor layer ordering
- Disabled build cache

Check:

```bash
docker build .
```

Observe which steps rebuild.

---

# Debugging Slow Containers

Check resource usage:

```bash
docker stats
```

Example:

```
CPU

Memory

Network

Block I/O
```

Look for unusually high CPU or memory usage.

---

# Debugging Checklist

```
✓ Container running?

✓ Logs checked?

✓ Environment variables correct?

✓ Network working?

✓ Volume mounted?

✓ Files present?

✓ Ports exposed?

✓ Dockerfile correct?

✓ Compose file valid?

✓ Rebuilt image?
```

# Best Practices

### Read Logs First

Most issues are revealed there.

---

### Use `docker compose config`

Validate before debugging runtime issues.

---

### Keep Health Checks

They help identify unhealthy services.

---

### Build With Cache

Avoid unnecessary rebuilds.

---

### Use Clear Container Names

Makes debugging easier.

---

### Instrument Your Application

In addition to Docker logs, use structured application logging so failures are easier to diagnose.

# 🏆 Debugging Challenge

Your backend fails with:

```
Error: connect ECONNREFUSED 127.0.0.1:27017
```

Investigate using this checklist:

1. Is the MongoDB container running?
2. Does the backend use `mongodb://localhost:27017`? If so, change it to `mongodb://mongodb:27017`.
3. Is MongoDB on the same Docker network?
4. Can the backend resolve the hostname `mongodb`?
5. Are the environment variables correct?
6. Check backend logs after making the fix.

# 💡 Senior Backend Engineer Insight

When debugging Docker issues in production, experienced engineers rarely jump straight into the container. They typically follow this order:

```
Monitoring Alerts
        │
        ▼
Application Logs
        │
        ▼
Container Logs
        │
        ▼
Container Health
        │
        ▼
Network & Storage
        │
        ▼
Interactive Investigation
```

Having a repeatable troubleshooting process is more valuable than memorizing commands. It helps you solve unfamiliar problems quickly and consistently.
