# Module 3 — Lesson 5: Volumes & Persistent Storage 💾

> **"Containers are temporary. Data shouldn't be."**

One of the biggest surprises for new Docker users is that **containers are disposable**. If you delete a container, anything stored inside it is usually gone—unless you've stored that data outside the container.

This lesson teaches you how to keep your data safe.

---

# Why Storage Matters

Imagine you have a MongoDB container.

```
MongoDB Container
        │
        ▼
Database Files
```

You add thousands of users.

Then you run:

```bash
docker rm mongodb
```

Everything disappears.

Why?

Because the data lived **inside the container**.

---

# Container Filesystem

Every running container has its own writable layer.

```
Image (Read Only)

↓

Writable Container Layer
```

When the container is removed:

```
Writable Layer

❌ Deleted
```

This is why containers are considered **ephemeral**.

---

# The Problem

Suppose your Express app stores uploaded images.

```
uploads/
    cat.jpg
    dog.jpg
```

If these files live inside the container:

```
docker rm app
```

Everything is lost.

Not good.

---

# Docker Storage Options

Docker provides three main ways to store data.

```
Docker Storage

├── Volumes ⭐⭐⭐⭐⭐
├── Bind Mounts ⭐⭐⭐⭐⭐
└── tmpfs ⭐⭐⭐☆☆
```

Let's learn each.

---

# Option 1 — Docker Volumes

Volumes are managed by Docker.

```
Container

↓

Volume

↓

Host Disk
```

The volume exists **outside** the container.

---

# Create a Volume

```bash
docker volume create mydata
```

List volumes:

```bash
docker volume ls
```

Example:

```
DRIVER    VOLUME NAME

local     mydata
```

---

# Inspect a Volume

```bash
docker volume inspect mydata
```

You'll see:

- Mount point
- Driver
- Labels
- Metadata

---

# Using a Volume

Run an Ubuntu container.

```bash
docker run -it \
-v mydata:/data \
ubuntu:24.04
```

Inside:

```bash
cd /data

echo "Hello Docker" > hello.txt
```

Exit.

---

# Test Persistence

Run another container.

```bash
docker run -it \
-v mydata:/data \
ubuntu:24.04
```

Check:

```bash
cat /data/hello.txt
```

Output:

```
Hello Docker
```

Even though it's a different container, the data remains.

---

# Visual Explanation

```
Container A

↓

Volume

↑

Container B
```

Both containers share the same data.

---

# Anonymous Volumes

Docker can create a volume automatically.

```bash
docker run \
-v /data \
ubuntu
```

Docker creates a random volume name.

Usually, named volumes are easier to manage.

---

# Named Volumes

Preferred:

```bash
docker volume create mongo-data
```

Then:

```bash
docker run \
-v mongo-data:/data/db \
mongo
```

Easy to identify later.

---

# Option 2 — Bind Mounts

Instead of letting Docker manage storage, use a folder from your computer.

```
Host Folder

↓

Container Folder
```

---

# Example

Suppose your project:

```
project/

├── server.js

├── package.json
```

Run:

```bash
docker run -it \
-v $(pwd):/app \
node:22
```

Now:

```
Host project

⇄

Container /app
```

Changes happen instantly.

---

# Why Developers Love Bind Mounts

Edit code:

```
VS Code

↓

Save File

↓

Container immediately sees changes
```

No rebuild needed.

Perfect for development.

---

# Windows Example

PowerShell:

```powershell
docker run -v ${PWD}:/app node:22
```

---

# Linux Example

```bash
docker run -v $(pwd):/app node:22
```

---

# Bind Mount vs Volume

|Volume|Bind Mount|
|---|---|
|Managed by Docker|Managed by you|
|Best for databases|Best for source code|
|Portable|Host dependent|
|Safer|Easy to edit|

---

# Option 3 — tmpfs

Stores files only in RAM.

```
Memory

↓

Container
```

Nothing touches the disk.

---

# Example

```bash
docker run \
--tmpfs /temp \
ubuntu
```

Perfect for:

- Secrets
- Temporary cache
- Session files

---

# Where Docker Stores Volumes

Linux:

```
/var/lib/docker/volumes/
```

Usually don't edit these files manually.

Use Docker commands instead.

---

# Removing Volumes

Delete:

```bash
docker volume rm mydata
```

Remove unused volumes:

```bash
docker volume prune
```

Docker asks for confirmation.

---

# Mounting Multiple Volumes

Example:

```bash
docker run \
-v uploads:/uploads \
-v logs:/logs \
myapp
```

Different folders.

Different purposes.

---

# MongoDB Example

```bash
docker run -d \
--name mongodb \
-v mongo-data:/data/db \
-p 27017:27017 \
mongo
```

Now database survives container deletion.

---

# PostgreSQL Example

```bash
docker run -d \
--name postgres \
-v postgres-data:/var/lib/postgresql/data \
postgres
```

---

# MySQL Example

```bash
docker run -d \
--name mysql \
-v mysql-data:/var/lib/mysql \
mysql
```

---

# Express Upload Example

```
uploads/

↓

Docker Volume

↓

Persistent Images
```

Perfect for:

- PDFs
- Images
- Videos

# Backing Up a Volume

Create an archive.

```bash
docker run --rm \
-v mydata:/data \
-v $(pwd):/backup \
ubuntu \
tar czf /backup/mydata.tar.gz /data
```

Backup created:

```
mydata.tar.gz
```

---

# Restoring a Volume

Reverse the process.

```bash
docker run --rm \
-v mydata:/data \
-v $(pwd):/backup \
ubuntu \
tar xzf /backup/mydata.tar.gz -C /
```

# Storage Best Practices

### Use Volumes for Databases

```
MongoDB

PostgreSQL

Redis
```

Never store database files only inside a container.

---

### Use Bind Mounts During Development

```
Local Code

↓

Running Container
```

Fast feedback.

---

### Backup Important Volumes

Databases deserve regular backups.

---

### Remove Unused Volumes

Clean periodically.

```bash
docker volume prune
```

---

# Common Mistakes

### Storing Database Inside Container

```
Container

↓

Delete Container

↓

Database Gone
```

Always use a volume.

---

### Using Bind Mounts in Production

Prefer Docker-managed volumes for application data.

---

### Deleting Volumes Accidentally

Remember:

```bash
docker volume rm
```

permanently removes stored data.

---

# Development vs Production

Development:

```
Host Source Code

↓

Bind Mount

↓

Container
```

Production:

```
Database

↓

Named Volume

↓

Container
```

# 💡 Backend Engineer Insight

A simple rule used by experienced backend engineers:

- **Application code** → Bind Mount (during development)
- **Databases** → Named Volumes
- **Temporary files or secrets** → `tmpfs` (when appropriate)

If you follow this rule, you'll avoid one of the most common Docker mistakes: accidentally losing important data.
