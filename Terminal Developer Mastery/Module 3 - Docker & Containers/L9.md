# Module 3 — Lesson 9: Environment Variables & Secrets 🔐

> **"Never hardcode configuration. Configuration belongs outside your code."**

One of the biggest differences between beginner and production-ready applications is **how configuration is managed**.

A professional backend application should be able to run in:

- Development
- Testing
- Staging
- Production

**without changing a single line of code.**

The only thing that changes is the configuration.

# Why Environment Variables?

Suppose your Express app connects to MongoDB.

Bad:

```jsx
const DB_URL =
  "mongodb://admin:password123@localhost:27017/mydb";
```

Problems:

- Password inside code
- Can't change for production
- Difficult to maintain
- Security risk

---

# Better Approach

```jsx
const DB_URL = process.env.MONGODB_URI;
```

Now the code never changes.

Only the value changes.

# Dockerfile and ENV

Inside Dockerfile:

```docker
ENV NODE_ENV=production
```

Now every container gets:

```
NODE_ENV=production
```

unless overridden.

---

# Runtime Overrides Dockerfile

Dockerfile:

```docker
ENV PORT=5000
```

Run:

```bash
docker run -e PORT=7000 my-app
```

Result:

```
PORT=7000
```

Runtime values always win.

---

# Build Arguments (ARG)

Used **only while building**.

```docker
ARG NODE_VERSION=22
```

Example:

```docker
FROM node:${NODE_VERSION}
```

Build:

```bash
docker build \
  --build-arg NODE_VERSION=22 \
  -t my-app .
```

After the image is built:

```
ARG disappears.
```

---

# ARG vs ENV

|Feature|ARG|ENV|
|---|---|---|
|Available during build|✅|✅|
|Available at runtime|❌|✅|
|Override at runtime|❌|✅|

Remember:

```
ARG

↓

Build Only

ENV

↓

Running Container
```

# What Is a Secret?

Secrets include:

```
Database Password

JWT Secret

Stripe Secret Key

AWS Keys

OAuth Client Secret
```

These should never be committed to Git.

---

# Never Do This

```jsx
const JWT_SECRET = "super-secret-password";
```

Or:

```jsx
const API_KEY =
  "123456789";
```

Anyone with the code can see them.

---

# Correct Way

```jsx
const JWT_SECRET =
  process.env.JWT_SECRET;
```

# Best Practices

### Keep Secrets Outside Code

Always use:

```jsx
process.env
```

---

### Use Strong Secrets

Generate long, random values for production.

---

### Use Different Values Per Environment

Development ≠ Production.

---

### Never Commit `.env`

Always ignore it.

---

### Validate Required Variables

At application startup:

```jsx
if (!process.env.JWT_SECRET) {
  throw new Error("JWT_SECRET is required");
}
```

Fail fast instead of discovering the problem later.

---

# Common Mistakes

❌ Hardcoding passwords

```jsx
const password = "123456";
```

---

❌ Committing `.env`

Secrets become public.

---

❌ Using development secrets in production

Always separate environments.

---

❌ Assuming `ARG` is available at runtime

It isn't.

```bash

  -e PORT=5000 \
  -e NODE_ENV=production \
  my-app

# Use .env file

# Show environment variables
docker exec -it my-app env
```

```docker

ARG NODE_VERSION=22

ENV NODE_ENV=production

WORKDIR /app

COPY package*.json ./

RUN npm install --omit=dev

COPY . .

EXPOSE 5000

CMD ["node", "server.js"]
```

# 💡 Backend Engineer Insight

Professional backend teams usually don't access `process.env` throughout the entire codebase. Instead, they centralize configuration.

For example:

```
src/
├── config/
│   ├── env.js
│   ├── database.js
│   └── redis.js
├── controllers/
├── services/
└── server.js
```

`config/env.js`

```jsx
import dotenv from "dotenv";

dotenv.config();

export const config = {
  port: process.env.PORT || 5000,
  nodeEnv: process.env.NODE_ENV || "development",
  mongodbUri: process.env.MONGODB_URI,
  redisUrl: process.env.REDIS_URL,
  jwtSecret: process.env.JWT_SECRET,
};
```

The rest of the application imports `config` instead of reading `process.env` directly. This makes validation, testing, and maintenance much easier.
