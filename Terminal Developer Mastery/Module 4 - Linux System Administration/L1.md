# Why Permissions Matter

Imagine your backend stores:

- User passwords
- JWT secrets
- Environment variables
- Uploaded files
- Database backups

Should everyone on the server access them?

**Absolutely not.**

Permissions decide:

- Who can read
- Who can modify
- Who can execute

# Linux Security Model

Every file has **three things** attached to it.

```
Owner

Group

Others
```

And every category has three possible permissions:

```
Read (r)

Write (w)

Execute (x)
```

# Permission Meaning

### Read (r)

Can open the file.

Example:

```bash
cat notes.txt
```

---

### Write (w)

Can modify or delete the file (subject to directory permissions).

Example:

```bash
echo "Hello" >> notes.txt
```

---

### Execute (x)

Can execute the file as a program or script.

Example:

```bash
./app.sh
```

# Directory Permissions

Permissions work differently on directories.

Suppose:

```
drwxr-x---
```

### Read

Can list filenames.

```bash
ls folder
```

---

### Write

Can create, rename, or delete files (again, subject to ownership and directory rules).

---

### Execute

Can enter the directory.

```bash
cd folder
```

Without execute permission:

```bash
cd folder
```

fails.

This surprises many beginners.

# Changing Permissions — Symbolic Mode

General form:

```bash
chmod [who][+/-/=][permissions] file
```

Examples:

Add execute:

```bash
chmod +x script.sh
```

Remove write:

```bash
chmod -w notes.txt
```

Owner gets write:

```bash
chmod u+w notes.txt
```

Group gets execute:

```bash
chmod g+x app.sh
```

Others lose read:

```bash
chmod o-r secret.txt
```

Give everyone read:

```bash
chmod a+r file.txt
```

Where:

- `u` = user (owner)
- `g` = group
- `o` = others
- `a` = all

# Common Numeric Modes

## 755

```
Owner : rwx = 7

Group : r-x = 5

Others: r-x = 5
```

Command:

```bash
chmod 755 script.sh
```

Used for:

- Scripts
- Executables
- Directories

---

## 644

```
Owner : rw-

Group : r--

Others: r--
```

Command:

```bash
chmod 644 config.json
```

Used for:

- Most text files
- Source code
- Configuration files

---

## 600

```
Owner : rw-

Group : ---

Others: ---
```

Perfect for:

```
.env

SSH private keys

Secrets
```

---

## 700

```
Owner : rwx

Group : ---

Others: ---
```

Private scripts.

---

# The Dangerous One: 777

```bash
chmod 777 file
```

Means:

```
rwx

rwx

rwx
```

Everyone can:

- Read
- Write
- Execute

🚫 **Never use `777` as a quick fix.**

If something only works with `777`, there's usually an ownership or permission problem that should be solved properly.

---

# Changing Ownership

View ownership:

```bash
ls -l
```

Change owner:

```bash
sudo chown rahul file.txt
```

Change owner and group:

```bash
sudo chown rahul:developers file.txt
```

---

# Change Group

```bash
sudo chgrp developers project.txt
```

---

# Recursive Changes

Directories often contain many files.

```bash
sudo chown -R rahul:developers project/
```

Recursive permission change:

```bash
chmod -R 755 project/
```

⚠️ Be careful with recursive permission changes—they affect every file and subdirectory. Often you'll want different permissions for directories and files.

---

# Better Recursive Pattern

A common production approach is:

Directories:

```bash
find project -type d -exec chmod 755 {} \;
```

Files:

```bash
find project -type f -exec chmod 644 {} \;
```

This gives:

- Directories: executable so they can be entered
- Files: readable, but not executable by default

# Backend Example

Project:

```
backend/

├── .env

├── package.json

├── src/

└── uploads/
```

Recommended permissions:

|Item|Permission|
|---|---|

|`package.json`|644|
|`src/`|755|
|`uploads/`|755 (or more restrictive depending on your application)|

# SSH Keys

Private key:

```
~/.ssh/id_ed25519
```

Permission:

```bash
chmod 600 ~/.ssh/id_ed25519
```

Public key:

```bash
chmod 644 ~/.ssh/id_ed25519.pub
```

If private keys are too permissive, SSH may refuse to use them.

# Why Scripts Don't Run

Suppose:

```bash
./deploy.sh
```

Error:

```
Permission denied
```

Fix:

```bash
chmod +x deploy.sh
```

Now:

```bash
./deploy.sh
```

works.

---

# Diagnosing Permission Errors

When you see:

```
Permission denied
```

Ask yourself:

```
1. Who owns the file?

↓

2. What are the permissions?

↓

3. Which user am I?

↓

4. Is this a file or directory?

↓

5. Is execute permission required?
```

This process solves most permission-related issues.

# Permission Cheat Sheet

```
755 → rwxr-xr-x → Executables & Directories

644 → rw-r--r-- → Source Code

600 → rw------- → Secrets

700 → rwx------ → Private Scripts

777 → rwxrwxrwx → Avoid
```

Useful commands:

```bash
# View permissions
ls -l

# Add execute
chmod +x script.sh

# Set numeric permissions
chmod 755 script.sh
chmod 644 file.txt
chmod 600 .env

# Change owner
sudo chown user file

# Change owner and group
sudo chown user:group file

# Change group
sudo chgrp group file
```

# 💡 Senior Backend Engineer Insight

One of the biggest differences between beginners and experienced Linux engineers is how they respond to permission errors.

A beginner often tries:

```bash
chmod 777 somefile
```

An experienced engineer asks:

1. Who owns this file?
2. Which user is running the application?
3. Which permission is actually missing?
4. Can I fix this with proper ownership instead?

Following this approach keeps your systems secure while solving the underlying problem instead of masking it.
