# What is Cron?

Cron is the Linux scheduler.

It runs commands automatically based on a schedule.

Example:

```
Every Day
     │
     ▼
02:00 AM
     │
     ▼
Database Backup
```

No user interaction required.

---

# Cron Components

```
cron daemon
      │
      ▼
Reads crontab
      │
      ▼
Runs commands
      │
      ▼
Logs output
```

# Cron Format

A cron schedule has **five fields**:

```
* * * * * command
│ │ │ │ │
│ │ │ │ └── Day of Week (0-7)
│ │ │ └──── Month
│ │ └────── Day of Month
│ └──────── Hour
└────────── Minute
```

# Absolute Paths

Cron has a limited environment.

Bad:

```
0 * * * * backup.sh
```

Good:

```
0 * * * * /home/rahul/scripts/backup.sh
```

Always use absolute paths.

---

# Which Shell?

Default shell:

```
/bin/sh
```

If your script needs Bash features:

```bash
#!/bin/bash
```


# Example Backup Script

```bash
#!/bin/bash

mkdir -p /home/rahul/backups

cp database.db \
/home/rahul/backups/database-$(date +%F).db
```

Cron:

```
0 2 * * * /home/rahul/scripts/backup.sh
```

Runs every night at 2:00 AM.

---

# Logging Cron Output

Without redirection, output may be emailed to the user (if local mail is configured) or discarded.

Recommended:

```
0 2 * * * /home/rahul/scripts/backup.sh >> /var/log/backup.log 2>&1
```

Meaning:

```
stdout

↓

backup.log
```

```
stderr

↓

backup.log
```

Both outputs go to one file.

---

# Silence Output

```
0 2 * * * command > /dev/null 2>&1
```

Use only if you truly don't need logs.

# Environment Variables

Cron does **not** load your interactive shell configuration.

This may fail:

```
node server.js
```

Better:

```
/usr/bin/node /opt/backend/script.js
```

Find Node:

```bash
which node
```

# Common Backend Tasks

### Database Backup

```
0 2 * * * /opt/scripts/db-backup.sh
```

---

### Delete Old Logs

```
0 3 * * * find /var/log/app -type f -mtime +30 -delete
```

Deletes logs older than 30 days.

---

### SSL Renewal

Many systems use:

```
0 0 * * * certbot renew
```

(Some modern distributions use a `systemd` timer instead.)

---

### Health Check

```
*/5 * * * * curl -fs <http://localhost:5000/health>
```

The `-f` option causes `curl` to return a non-zero exit status on HTTP errors.

---

### Cache Cleanup

```
0 */6 * * * /opt/scripts/cache-clean.sh
```

Runs every six hours.

---

# Prevent Overlapping Jobs

Suppose a backup takes 20 minutes.

Don't schedule it every 10 minutes.

Better:

```
Backup

↓

Completes

↓

Next Backup
```

For stricter protection, use `flock`:

```
0 * * * * flock -n /tmp/backup.lock /opt/scripts/backup.sh
```

This prevents a second instance from starting if one is already running.

---

# Test Before Scheduling

Always test manually:

```bash
./backup.sh
```

If it fails manually, it will fail in cron too.

---

# Production Example

Suppose your project:

```
/opt/backend
```

Nightly backup:

```
0 1 * * * \
/opt/backend/scripts/backup.sh \
>> /var/log/backend-backup.log 2>&1
```

Morning cleanup:

```
30 5 * * * \
/opt/backend/scripts/cleanup.sh \
>> /var/log/backend-cleanup.log 2>&1
```

# Debugging Failed Cron Jobs

Suppose your job never runs.

Checklist:

```
Is cron running?
        │
        ▼
systemctl status cron
        │
        ▼
Executable?
(chmod +x)
        │
        ▼
Absolute paths?
        │
        ▼
Correct PATH?
        │
        ▼
Manual execution works?
        │
        ▼
Check logs
```

This sequence resolves most cron issues.

# Best Practices

### Always Use Absolute Paths

```bash
/usr/bin/node
```

instead of:

```bash
node
```

---

### Log Everything

Capture both standard output and errors:

```
>> logfile 2>&1
```

---

### Test Scripts Manually

Run them before scheduling.

---

### Avoid Overlapping Jobs

Use sensible intervals or `flock` for locking.

---

### Keep Jobs Small

Complex workflows are easier to maintain as standalone scripts called by cron.

# 💡 Senior Backend Engineer Insight

Experienced backend engineers treat automation as production code. A cron job isn't "finished" just because it runs once—it should be:

```
Write Script
      │
      ▼
Test Manually
      │
      ▼
Use Absolute Paths
      │
      ▼
Capture Logs
      │
      ▼
Schedule with Cron
      │
      ▼
Monitor First Execution
      │
      ▼
Review Logs Periodically
```

Many production incidents come from "invisible" scheduled jobs. Logging, testing, and monitoring make those jobs reliable and much easier to troubleshoot.
