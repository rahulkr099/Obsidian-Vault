# Linux Storage Architecture

```
Physical Disk (SSD/HDD)
        │
        ▼
Partition
        │
        ▼
Filesystem (ext4, xfs, btrfs...)
        │
        ▼
Mount Point
        │
        ▼
Files & Directories
```

Example:

```
SSD
│
├── Partition 1
│      │
│      ▼
│    ext4
│      │
│      ▼
│      /
│
└── Partition 2
       │
       ▼
      ext4
       │
       ▼
      /home
```

# Check Disk Usage

Most commonly used command:

```bash
df -h
```

Example:

```
Filesystem      Size Used Avail Use% Mounted on

/dev/sda2       100G  48G   47G  51% /

/dev/sda3       500G 120G  350G  26% /home
```

---

# Understanding df Output

|Column|Meaning|
|---|---|
|Filesystem|Disk or partition|
|Size|Total capacity|
|Used|Used space|
|Avail|Free space|
|Use%|Percentage used|
|Mounted on|Mount point|

---

# Human Readable Output

Always use:

```bash
df -h
```

instead of:

```bash
df
```

The `-h` flag displays KB/MB/GB instead of raw blocks.

---

# Check Specific Directory

```bash
df -h /home
```

or

```bash
df -h .
```

Current directory's filesystem.

---

# Directory Size

Another essential command:

```bash
du -sh .
```

Output:

```
1.8G .
```

Meaning:

Current directory uses **1.8 GB**.

---

# Compare Folder Sizes

```bash
du -sh *
```

Example:

```
5G uploads

300M logs

25M src

800K docs
```

Quickly identifies the largest directories.

---

# Sort by Size

```bash
du -sh * | sort -hr
```

Example:

```
5G uploads

2G backups

800M logs
```

A favorite command for diagnosing disk issues.

---

# Show One Level Deep

```bash
du -h --max-depth=1
```

Great for exploring project directories.

---

# Find Large Files

Example:

```bash
find . -type f -size +100M
```

Find files larger than 100 MB.

---

# Find Largest Files

```bash
find . -type f -exec ls -lh {} \; | sort -k5 -hr | head
```

Shows the biggest files in the current directory tree.

---

# List Block Devices

```bash
lsblk
```

Example:

```
NAME   SIZE TYPE MOUNTPOINT

sda    1T   disk

├─sda1 512M part /boot

├─sda2 100G part /

└─sda3 900G part /home
```

This gives an overview of your storage layout.

---

# Detailed Filesystem Information

```bash
lsblk -f
```

Example:

```
NAME FSTYPE LABEL UUID MOUNTPOINT
```

Shows:

- Filesystem type
- UUID
- Labels
- Mount points

---

# Identify Filesystem Type

```bash
df -T
```

Example:

```
Filesystem Type Size Used Mounted

/dev/sda2 ext4
```

---

# Common Filesystems

|Filesystem|Use|
|---|---|
|ext4|Default on Ubuntu/Mint|
|xfs|Common on enterprise servers|
|btrfs|Snapshots and advanced features|
|FAT32|USB drives|
|exFAT|Cross-platform storage|
|NTFS|Windows drives|

---

# Mount Points

Linux attaches filesystems to directories.

Example:

```
USB Drive

↓

/media/rahul/PENDRIVE
```

Everything becomes part of a single directory tree.

---

# View Mounted Filesystems

```bash
mount
```

or

```bash
findmnt
```

`findmnt` is often easier to read.

---

# Mount a Drive

Example:

```bash
sudo mount /dev/sdb1 /mnt/data
```

Now the drive appears under:

```
/mnt/data
```

---

# Unmount

```bash
sudo umount /mnt/data
```

or

```bash
sudo umount /dev/sdb1
```

**Note:** It's `umount`, not `unmount`.

---

# Check Open Files

If unmount fails:

```
target is busy
```

Find who is using it:

```bash
lsof /mnt/data
```

or

```bash
fuser -vm /mnt/data
```

---

# UUID

Instead of:

```
/dev/sdb1
```

Linux often mounts using:

```
UUID=4c5f...
```

View UUIDs:

```bash
blkid
```

UUIDs remain stable even if device names change.

---

# Automatic Mounting

Configuration file:

```
/etc/fstab
```

View:

```bash
cat /etc/fstab
```

Example:

```
UUID=xxxx / ext4 defaults 0 1
```

⚠️ Incorrect edits to `/etc/fstab` can prevent a system from booting. Always back it up before making changes.

---

# Disk Inodes

Sometimes disk space looks available, but you still can't create files.

Check inode usage:

```bash
df -i
```

Example:

```
Filesystem Inodes IUsed IFree IUse%

/dev/sda2 6553600 6549000 4600 99%
```

The disk has free bytes but almost no inodes left because it contains too many small files.

---

# Check Free Memory? No!

Many beginners confuse:

```bash
df
```

with

```bash
free
```

Remember:

```
df

↓

Disk Space
```

```
free

↓

RAM
```

---

# Real Backend Example

Project:

```
backend/

├── uploads
├── logs
├── backups
├── node_modules
└── src
```

Check sizes:

```bash
du -sh *
```

Output:

```
20G uploads

8G backups

2G logs

500M node_modules

25M src
```

Immediately obvious:

- uploads
- backups

are consuming the most space.

---

# Docker Storage

Docker images consume disk space.

Check:

```bash
docker system df
```

Clean unused objects:

```bash
docker system prune
```

Remove unused images, containers, and networks.

Be careful—read the prompt before confirming.

---

# Journal Logs

System logs can also grow.

Check:

```bash
journalctl --disk-usage
```

Reduce size:

```bash
sudo journalctl --vacuum-size=500M
```

---

# Finding Huge Log Files

```bash
find /var/log -type f -size +100M
```

---

# Backend Storage Best Practices

Store separately:

```
Application

Uploads

Logs

Backups
```

Don't mix everything into one directory.

---

# Storage Monitoring

Regularly monitor:

- Disk usage
- Inode usage
- Log growth
- Docker storage
- Backup size

Waiting until the disk reaches 100% often means downtime.

# Production Troubleshooting Scenario

## Problem

Your Express API suddenly stops working.

Logs show:

```
Error: ENOSPC

No space left on device
```

### Step 1

Check filesystem:

```bash
df -h
```

### Step 2

Locate large directories:

```bash
du -sh /var/* | sort -hr
```

### Step 3

Inspect logs:

```bash
du -sh /var/log/*
```

### Step 4

Inspect Docker:

```bash
docker system df
```

### Step 5

Inspect backups:

```bash
du -sh /opt/backups/*
```

Only after identifying the cause should you delete or archive data.

# Best Practices

### Use `df -h`

Human-readable disk usage.

---

### Use `du -sh`

Measure directory sizes.

---

### Monitor Log Growth

Large log files are a common cause of full disks.

---

### Use UUIDs

More reliable than `/dev/sdX` names.

---

### Clean Docker Periodically

Remove unused images and containers.

---

### Backup Before Major Changes

Especially before editing `/etc/fstab` or deleting large directories.

---

# Common Mistakes

❌ Deleting files without checking what they are.

---

❌ Editing `/etc/fstab` without a backup.

---

❌ Confusing RAM (`free`) with disk (`df`).

---

❌ Ignoring inode usage.

---

❌ Deleting active log files while applications are still writing to them.

# 💡 Senior Backend Engineer Insight

When a production server reports **"No space left on device,"** experienced engineers avoid deleting random files. They follow a structured investigation:

```
Application Error
       │
       ▼
df -h
(Check filesystem usage)
       │
       ▼
df -i
(Check inode usage)
       │
       ▼
du -sh /var/* | sort -hr
(Find large directories)
       │
       ▼
Check:
• Logs
• Docker
• Backups
• Uploads
       │
       ▼
Archive or clean safely
       │
       ▼
Verify free space
       │
       ▼
Confirm application recovery
```

This methodical approach minimizes the risk of deleting important data and helps restore services quickly.
