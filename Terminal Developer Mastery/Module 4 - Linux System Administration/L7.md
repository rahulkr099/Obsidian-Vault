# Module 4 — Lesson 7: Log Management 📜

> **"Professional backend engineers don't guess what went wrong—they read the logs."**

If your backend crashes at **2:00 AM**, the logs will tell you:

- What happened
- When it happened
- Which user triggered it
- Why it failed
- What failed first

Logs are one of the **most valuable debugging tools** in Linux.

# Why Logs Matter

Imagine your Express backend suddenly returns:

```
500 Internal Server Error
```

Without logs:

```

```

The logs turn mystery into evidence.

# The `/var/log` Directory

Most Linux logs live here.

```bash
cd /var/log

ls
```

Typical output:

```
alternatives.log

apt

auth.log

boot.log

dpkg.log

journal

kern.log

syslog
```

---

# Important Log Files

|File|Purpose|
|---|---|
|`/var/log/syslog`|General system events|
|`/var/log/auth.log`|Authentication & SSH|
|`/var/log/kern.log`|Kernel messages|
|`/var/log/dpkg.log`|Package installation history|
|`/var/log/boot.log`|Boot messages|
|`/var/log/journal/`|systemd journal storage|

> **Note:** Some distributions (such as Fedora/RHEL) primarily use the `systemd` journal instead of `syslog`.

---

# Viewing Small Logs

Use:

```bash
cat filename
```

Example:

```bash
cat /var/log/dpkg.log
```

Good for small files.

---

# Better Viewer: `less`

Large logs:

```bash
less /var/log/syslog
```

Navigation:

|Key|Action|
|---|---|
|↑ ↓|Scroll|
|Space|Next page|
|b|Previous page|
|/|Search|
|n|Next match|
|q|Quit|

`less` is one of the most-used tools for reading logs.

---

# View Beginning

```bash
head /var/log/syslog
```

Default:

```
First 10 lines
```

Custom:

```bash
head -30 /var/log/syslog
```

---

# View End

```bash
tail /var/log/syslog
```

Last 10 lines.

Custom:

```bash
tail -50 /var/log/syslog
```

---

# Live Monitoring

One of the most important commands:

```bash
tail -f /var/log/syslog
```

Now every new log entry appears instantly.

Press:

```
Ctrl + C
```

to stop following the file.

---

# Search Logs

Example:

```bash
grep ERROR server.log
```

Output:

```
ERROR MongoDB timeout
```

---

# Ignore Case

```bash
grep -i error server.log
```

Matches:

```
ERROR

Error

error
```

---

# Recursive Search

```bash
grep -R JWT /var/log
```

Searches through multiple files and directories.

---

# Count Matches

```bash
grep -c ERROR server.log
```

Output:

```
17
```

---

# Show Line Numbers

```bash
grep -n ERROR server.log
```

Example:

```
145: ERROR Database failed
```

---

# Combine with `tail`

```bash
tail -100 server.log | grep ERROR
```

Only search recent log entries.

---

# `journalctl`

With `systemd`, logs are stored in the **system journal**.

Show everything:

```bash
journalctl
```

---

# Latest Logs

```bash
journalctl -n 50
```

Last 50 log entries.

---

# Follow Live

```bash
journalctl -f
```

Similar to:

```bash
tail -f
```

---

# Current Boot

```bash
journalctl -b
```

Logs since the last reboot.

---

# Previous Boot

```bash
journalctl -b -1
```

Very useful after a failed reboot.

---

# Service Logs

Suppose your backend service is called:

```
backend
```

View logs:

```bash
journalctl -u backend
```

Recent logs:

```bash
journalctl -u backend -n 50
```

Live:

```bash
journalctl -u backend -f
```

---

# Filter by Time

Last hour:

```bash
journalctl --since "1 hour ago"
```

Today:

```bash
journalctl --since today
```

Specific time:

```bash
journalctl --since "2026-07-25 10:00"
```

Range:

```bash
journalctl \
--since "09:00" \
--until "10:00"
```

---

# Filter by Priority

Errors only:

```bash
journalctl -p err
```

Warnings:

```bash
journalctl -p warning
```

Critical:

```bash
journalctl -p crit
```

Priority levels:

|Level|Meaning|
|---|---|
|emerg|System unusable|
|alert|Immediate action required|
|crit|Critical condition|
|err|Error|
|warning|Warning|
|notice|Normal but significant|
|info|Informational|
|debug|Debugging|

# Log Levels

A common convention:

```
ERROR

WARN

INFO

DEBUG
```

Example:

```
INFO  User login

INFO  API started

WARN  Slow database

ERROR Connection failed
```

Structured levels make filtering much easier.

# Log Rotation

Logs grow continuously.

Linux rotates logs automatically.

Configuration:

```
/etc/logrotate.conf
```

Additional rules:

```
/etc/logrotate.d/
```

---

# Check Rotation

```bash
cat /etc/logrotate.conf
```

---

# Force Rotation (Testing)

```bash
sudo logrotate -f /etc/logrotate.conf
```

Useful when testing log rotation.

---

# Compressed Logs

Older logs often end with:

```
.gz
```

Read without extracting:

```bash
zless logfile.gz
```

Search:

```bash
zgrep ERROR logfile.gz
```

```

```
User reports error
       │
       ▼
systemctl status backend
       │
       ▼
journalctl -u backend -n 50
       │
       ▼
Read stack trace
       │
       ▼
Check environment variables
       │
       ▼
Fix configuration
       │
       ▼

       │
       ▼

# Best Practices

### Use `journalctl`

For services managed by `systemd`, it's the first place to look.

---

### Follow Logs Live

```bash
journalctl -u backend -f
```

or

```bash
tail -f logfile
```

while testing.

---

### Use Meaningful Log Levels

Don't log everything as an error.

---

### Rotate Logs

Prevent disks from filling due to ever-growing log files.

---

### Never Log Secrets

Avoid logging:

- Passwords
- JWT secrets
- API keys
- Database passwords
- OAuth tokens

---

❌ Using only `cat` for huge log files.

# 💡 Senior Backend Engineer Insight

Experienced Linux engineers rarely start debugging by restarting services. They first gather evidence from the logs.

A common troubleshooting workflow looks like this:

```
Problem Reported
       │
       ▼
systemctl status service
       │
       ▼
journalctl -u service -n 100
       │
       ▼
Identify the first error
       │
       ▼
Trace the root cause
       │
       ▼
Fix the issue
       │
       ▼
Restart service (if needed)
       │
       ▼
Monitor logs to verify the fix
```

Notice that **restarting is near the end**, not the beginning. Good engineers understand _why_ something failed before trying to recover it.
