# What is SSH?

SSH stands for **Secure Shell**.

It provides:

- Secure remote login
- Encrypted communication
- File transfer
- Remote command execution
- Secure tunneling

Instead of sitting in front of the server, you securely control it from your terminal.

# First SSH Connection

General syntax:

```bash
ssh username@server-ip
```

Example:

```bash
ssh rahul@192.168.1.50
```

You'll be prompted for:

- Password
- Host verification (first connection)

---

# First Connection Warning

Example:

```
The authenticity of host can't be established.

Are you sure you want to continue?
```

Answer:

```
yes
```

Linux stores the server's fingerprint in:

```
~/.ssh/known_hosts
```

This helps detect man-in-the-middle attacks.

---

# SSH Key Authentication

Instead of passwords, professionals use **SSH keys**.

Advantages:

- Stronger security
- Faster login
- Can disable password authentication
- Required by many cloud providers

---

# Public and Private Keys

```
Private Key
(id_ed25519)
      │
      │ Never Share
      ▼
Public Key
(id_ed25519.pub)
      │
      ▼
Copied to Server
```

---

# Generate SSH Keys

Recommended algorithm:

```bash
ssh-keygen -t ed25519 -C "rahul@example.com"
```

You'll be asked:

```
File location?

Passphrase?
```

Press Enter to use defaults, or choose a passphrase for extra security.

---

# Generated Files

```
~/.ssh/

id_ed25519

id_ed25519.pub
```

Meaning:

```
Private Key

Public Key
```

---

# Correct Permissions

Private key:

```bash
chmod 600 ~/.ssh/id_ed25519
```

Public key:

```bash
chmod 644 ~/.ssh/id_ed25519.pub
```

Directory:

```bash
chmod 700 ~/.ssh
```

---

# Copy Public Key to Server

Easy method:

```bash
ssh-copy-id username@server-ip
```

Example:

```bash
ssh-copy-id rahul@192.168.1.50
```

This appends your public key to:

```
~/.ssh/authorized_keys
```

---

# Manual Method

Display public key:

```bash
cat ~/.ssh/id_ed25519.pub
```

Copy the entire line.

On the server:

```bash
mkdir -p ~/.ssh

nano ~/.ssh/authorized_keys
```

Paste the key.

Permissions:

```bash
chmod 700 ~/.ssh

chmod 600 ~/.ssh/authorized_keys
```

---

# Login Using Key

```bash
ssh rahul@192.168.1.50
```

If configured correctly, no password is required (unless your private key has a passphrase).

---

# SSH Agent

Avoid typing the passphrase repeatedly.

Start agent:

```bash
eval "$(ssh-agent -s)"
```

Add key:

```bash
ssh-add ~/.ssh/id_ed25519
```

List loaded keys:

```bash
ssh-add -l
```

---

# SSH Configuration

Instead of:

```bash
ssh rahul@192.168.1.50
```

Create:

```
~/.ssh/config
```

Example:

```
Host backend
    HostName 192.168.1.50
    User rahul
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```

Now connect using:

```bash
ssh backend
```

This becomes invaluable when you manage multiple servers.

---

# Run Remote Commands

```bash
ssh backend uptime
```

Example output:

```
14:25 up 7 days
```

Another example:

```bash

```

# Copy Files with scp

Upload:

```bash
scp app.js backend:/home/rahul/
```

Download:

```bash
scp backend:/home/rahul/log.txt .
```

Recursive copy:

```bash
scp -r project backend:/opt/
```

---

# rsync

Preferred for deployments.

Example:

```bash
rsync -avz project/ backend:/opt/backend/
```

Options:

- `a` → archive
- `v` → verbose
- `z` → compress

Benefits:

- Copies only changed files
- Faster than repeated `scp`
- Preserves permissions and timestamps

---

# SSH Port Forwarding

Access a remote service locally.

Example:

```bash
ssh -L 8080:localhost:5000 backend
```

Now:

```
localhost:8080
```

connects to:

```
backend:5000
```

Useful for securely accessing databases or internal dashboards.

---


# SSH Configuration File

Server configuration:

```
/etc/ssh/sshd_config
```

Common settings:

```
PermitRootLogin no

PasswordAuthentication no

PubkeyAuthentication yes
```

After changes:

```bash
sudo systemctl restart ssh
```

---

# Production Hardening

A secure SSH server should:

- Disable root login
- Use SSH keys instead of passwords
- Disable password authentication after verifying key access
- Keep OpenSSH updated
- Restrict access with a firewall
- Use strong passphrases for private keys

---

# Verify Server Fingerprint

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Compare this fingerprint with the one shown during the first connection to verify you're connecting to the correct server.

# Common SSH Errors

## Permission Denied

```
Permission denied (publickey)
```

Check:

- Public key installed?
- Correct permissions?
- Correct username?
- Correct private key?

---

## Connection Refused

```
Connection refused
```

Check:

```bash
systemctl status ssh
```

Is the SSH service running?

---

## Connection Timed Out

Possible causes:

- Wrong IP
- Firewall
- Network issue
- Server offline

# Best Practices

### Use Ed25519 Keys

Prefer:

```bash
ssh-keygen -t ed25519
```

---

### Protect Your Private Key

Never share:

```
id_ed25519
```

Only share:

```
id_ed25519.pub
```

---

### Disable Root Login

```
PermitRootLogin no
```

---

### Prefer Key Authentication

After confirming keys work, disable password authentication if appropriate for your environment.

---

### Use SSH Config

Managing many servers becomes much easier with host aliases.

# Common Mistakes

❌ Copying the private key instead of the public key.

---

❌ Incorrect permissions on `~/.ssh` or `authorized_keys`.

---

❌ Disabling password authentication before confirming key-based login works.

---

❌ Editing `sshd_config` without restarting the SSH service.

---

❌ Forgetting to verify the server fingerprint on the first connection.

# 💡 Senior Backend Engineer Insight

SSH is more than a remote login tool—it's the backbone of Linux server administration.

A typical deployment session for an experienced backend engineer looks like this:

```
SSH into Server
        │
        ▼
git pull (or rsync deployment)
        │
        ▼
npm ci
        │
        ▼
Run database migrations (if any)
        │
        ▼
sudo systemctl restart backend
        │
        ▼
curl localhost:5000/health
        │
        ▼
journalctl -u backend -f
        │
        ▼
Confirm service is healthy
```

Notice that deployment isn't complete when the code is copied. It's only complete after the service is restarted, health checks pass, and the logs confirm the application is running correctly.
