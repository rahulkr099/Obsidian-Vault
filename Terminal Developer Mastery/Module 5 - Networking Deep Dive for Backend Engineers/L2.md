# What is TCP/IP?

TCP/IP is a **suite of networking protocols** that allows computers to communicate over networks.

Think of it as a set of agreed rules:

```
Computer A
     │
 TCP/IP Rules
     │
Computer B
```

Without these rules, devices wouldn't understand each other.

---

# The TCP/IP Model

The Internet is commonly described using four layers.

```
Application
      │
Transport
      │
Internet
      │
Network Access
```

Each layer has a specific responsibility.

---

# Layer 1 — Application

Protocols you use directly:

- HTTP
- HTTPS
- SSH
- DNS
- SMTP
- FTP
- WebSocket

Example:

```
Browser

↓

HTTP
```

---

# Layer 2 — Transport

Main protocols:

- TCP
- UDP

Responsible for:

- Reliable delivery (TCP)
- Fast delivery (UDP)
- Ports
- Segmentation

---

# Layer 3 — Internet

Responsible for:

- IP addressing
- Routing packets between networks

Protocols:

- IPv4
- IPv6
- ICMP

---

# Layer 4 — Network Access

Responsible for moving data over the physical network.

Examples:

- Ethernet
- Wi-Fi

---

# Encapsulation

Each layer wraps data before sending it.

```
HTTP Request
      │
TCP Segment
      │
IP Packet
      │
Ethernet Frame
      │
Network Cable / Wi-Fi
```

The receiving computer unwraps the layers in reverse order.

---

# TCP vs UDP

|Feature|TCP|UDP|
|---|---|---|
|Connection|Yes|No|
|Reliable|✅|❌|
|Ordered|✅|❌|
|Retransmission|✅|❌|
|Speed|Slower|Faster|
|Streaming|Less suitable|Better|
|File transfer|Excellent|Poor|

---

# When is TCP Used?

Most backend technologies rely on TCP:

- HTTP
- HTTPS
- SSH
- Git over HTTPS/SSH
- MongoDB
- PostgreSQL
- MySQL
- Redis (default)

Reliability is more important than raw speed.

---

# When is UDP Used?

UDP is useful when speed matters more than perfect delivery.

Examples:

- Live video
- Voice calls
- Online gaming
- DNS queries (most cases)

Losing a few packets is often acceptable.

# TCP Connection

TCP must establish a connection before exchanging data.

This is called the **Three-Way Handshake**.

---

# Step 1 — SYN

Client:

```
Client

SYN

↓

Server
```

Meaning:

> "I'd like to start a connection."

---

# Step 2 — SYN-ACK

Server:

```
Server

SYN + ACK

↓

Client
```

Meaning:

> "I received your request and I'm ready."

---

# Step 3 — ACK

Client:

```
Client

ACK

↓

Server
```

Meaning:

> "Great! Let's communicate."

---

# Three-Way Handshake Diagram

```
Client                         Server
   │                              │
   ├──────── SYN ───────────────► │
   │                              │
   │ ◄────── SYN + ACK ───────────┤
   │                              │
   ├──────── ACK ───────────────► │
   │                              │
   │======= Connection Ready =====│
```

Only after this does HTTP, HTTPS, SSH, or another application protocol send its data.

---

# Why Three Steps?

The handshake ensures:

- Both sides are reachable
- Initial sequence numbers are exchanged
- Both sides agree to communicate

---

# Sequence Numbers

TCP labels every byte with a sequence number.

Example:

```
Packet 1

Seq = 1000
```

Next packet:

```
Seq = 2000
```

The receiver uses these numbers to reconstruct data in order.

---

# Acknowledgments (ACK)

After receiving data:

```
ACK = 2000
```

Meaning:

> "I've received everything up to byte 1999. Send me byte 2000 next."

---

# Lost Packet

Suppose:

```
Packet 3
```

never arrives.

TCP detects the missing acknowledgment and retransmits it.

```
Packet 1 ✓

Packet 2 ✓

Packet 3 ✗

↓

Retransmit Packet 3
```

This is why TCP is reliable.

---

# Out-of-Order Packets

Packets may arrive like this:

```
1

3

2
```

TCP buffers them and delivers them to the application in the correct order:

```
1

2

3
```

---

# Flow Control

Imagine a fast sender and a slow receiver.

Without limits:

```
Fast Sender

↓↓↓↓↓↓↓↓

Slow Receiver
```

The receiver would be overwhelmed.

TCP uses a **receive window** to tell the sender how much data it can accept.

---

# Congestion Control

Sometimes the **network**, not the receiver, is overloaded.

```
Many Computers
        │
        ▼
     Router
        │
        ▼
     Internet
```

If too many packets are sent too quickly, routers begin dropping them.

TCP reduces its sending rate to relieve congestion.

---

# TCP Connection Termination

Closing a connection also requires coordination.

```
Client                    Server
   │                         │
   ├──────── FIN ──────────► │
   │                         │
   │ ◄──────── ACK ──────────┤
   │                         │
   │ ◄──────── FIN ──────────┤
   │                         │
   ├──────── ACK ──────────► │
```

This orderly shutdown helps ensure no data is lost.

---

# TIME_WAIT

After closing:

```
TIME_WAIT
```

The socket stays around briefly.

Purpose:

- Ensure delayed packets don't interfere with future connections.
- Confirm the final ACK isn't lost.

Seeing sockets in `TIME_WAIT` is usually normal.

---

# MTU (Maximum Transmission Unit)

Networks limit packet size.

Typical Ethernet MTU:

```
1500 bytes
```

If data exceeds the MTU:

```
Large Data

↓

Packet 1

Packet 2

Packet 3
```

The sender splits it into multiple packets.

---

# Fragmentation

Large packets may be fragmented.

Modern systems generally try to avoid IP fragmentation because it hurts performance.

Instead, they use **Path MTU Discovery** to learn the largest safe packet size.

---

# Check MTU

```bash
ip link
```

Example:

```
mtu 1500
```

---

# TCP States

Common states:

|State|Meaning|
|---|---|
|LISTEN|Waiting for connections|
|SYN_SENT|Client sent SYN|
|SYN_RECV|Server received SYN|
|ESTABLISHED|Connected|
|FIN_WAIT|Closing|
|CLOSE_WAIT|Waiting to close|
|TIME_WAIT|Recently closed|

View them:

```bash
ss -tan
```

---

# Observe TCP Connections

Start a local server:

```bash
python3 -m http.server 8080
```

Another terminal:

```bash
curl <http://localhost:8080>
```

Observe:

```bash
ss -tan
```

You'll likely see connections transition through states such as `ESTABLISHED` and then `TIME_WAIT`.

# Troubleshooting TCP Problems

## Connection Refused

```
ECONNREFUSED
```

Usually means:

- No service is listening on the destination port.

Check:

```bash
ss -tulpn
```

---

## Connection Timed Out

Possible causes:

- Firewall
- Network issue
- Wrong IP
- Server unreachable

---

## Too Many TIME_WAIT Connections

Usually not an error.

Investigate only if they are consuming significant resources.

# 💡 Senior Backend Engineer Insight

When you type:

```
<https://your-api.com/users>
```

many developers think:

```
Browser
   │
   ▼
Server
```

A backend engineer thinks:

```
Browser
    │
DNS Resolution
    │
TCP Three-Way Handshake
    │
TLS Handshake (HTTPS)
    │
HTTP Request
    │
Nginx Reverse Proxy
    │
Express Application
    │
Database Query
    │
HTTP Response
    │
TCP Connection Reuse or Close
```

Understanding these layers makes production issues much easier to diagnose because you can identify _which_ layer is failing instead of treating "the network" as a single black box.
