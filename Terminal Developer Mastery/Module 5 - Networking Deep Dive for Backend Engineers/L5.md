# What is REST?

REST stands for:

> **Representational State Transfer**

REST is **an architectural style**, not a protocol.

It defines guidelines for designing APIs that are:

- Simple
- Predictable
- Scalable
- Stateless

---

# REST Architecture

```
Frontend (React)
       │
 HTTP Request
       ▼
Express REST API
       │
 Business Logic
       │
MongoDB
       │
 HTTP Response
       ▼
Frontend
```

# Resource-Based Design

In REST, everything is a **resource**.

Examples:

```
Users

Products

Orders

Posts

Comments

Todos
```

Each resource gets its own endpoint.

---

# Good Endpoint Examples

```
/users

/products

/orders

/posts

/todos
```

---

# Bad Endpoint Examples

```
/getUsers

/createProduct

/deleteOrder

/updatePost
```

**Reason:** HTTP methods already describe the action.

---

# CRUD Operations

CRUD stands for:

|Operation|Meaning|
|---|---|
|Create|Add new data|
|Read|Retrieve data|
|Update|Modify data|
|Delete|Remove data|

---

# CRUD Mapping

|CRUD|HTTP Method|Example|
|---|---|---|
|Create|POST|`/users`|
|Read|GET|`/users`|
|Read One|GET|`/users/5`|
|Update|PUT/PATCH|`/users/5`|
|Delete|DELETE|`/users/5`|

---

# REST Endpoint Design

```
GET     /users
GET     /users/10

POST    /users

PUT     /users/10

PATCH   /users/10

DELETE  /users/10
```

Notice:

No verbs.

Only resources.

# HTTP Method Examples

## GET

Retrieve data.

```
GET /users
```

Response:

```json
[
  {
    "id":1,
    "name":"Rahul"
  }
]
```

---

## GET One

```
GET /users/10
```

---

## POST

Create user.

```
POST /users
```

Body:

```json
{
  "name":"Rahul",
  "email":"rahul@example.com"
}
```

---

Response:

```
201 Created
```

---

## PUT

Replace entire resource.

```
PUT /users/10
```

Body:

```json
{
  "name":"Rahul Kumar",
  "email":"rahul@example.com"
}
```

---

## PATCH

Partial update.

```
PATCH /users/10
```

Body:

```json
{
  "name":"Rahul Kumar"
}
```

---

## DELETE

```
DELETE /users/10
```

Response:

```
204 No Content
```

# API Versioning

Good:

```
/api/v1/users

/api/v2/users
```

Why?

Older clients continue working while newer versions evolve.

# Consistent API Responses

Recommended structure:

Success:

```json
{
    "success": true,
    "data": {}
}
```

Error:

```json
{
    "success": false,
    "message": "Something went wrong"
}
```

# HTTP Status Code Guide

|Action|Status|
|---|---|
|GET success|200|
|POST success|201|
|DELETE success|204|
|Validation failed|400|
|Unauthorized|401|
|Forbidden|403|
|Not found|404|
|Conflict|409|
|Server error|500|

---

## Client-Server

---

## Uniform Interface

# Best Practices

### Use Nouns for Resources

Good:

```
/users
```

Bad:

```
/getUsers
```

---

### Return Consistent Responses

Clients become easier to write and maintain when response formats are predictable.

---

### Use Correct Status Codes

Let the status code communicate the result before the response body does.

---

### Validate Input

Reject invalid requests before reaching your business logic or database.

---

### Keep URLs Predictable

A developer should be able to guess the endpoint structure without reading documentation.

---

# Common Mistakes

❌ Using verbs in endpoint names.

---

❌ Returning `200 OK` for resource creation instead of `201 Created`.

---

❌ Mixing response formats across endpoints.

---

❌ Ignoring pagination for large collections.

---

❌ Returning database errors directly to clients.

# 💡 Senior Backend Engineer Insight

REST is not just about using HTTP methods correctly—it's about creating APIs that are **predictable**.

When another developer sees:

```
GET    /api/v1/users
POST   /api/v1/users
PATCH  /api/v1/users/:id
DELETE /api/v1/users/:id
```

they can immediately understand how to use your API without reading extensive documentation.

The best REST APIs feel intuitive because they follow consistent conventions. That consistency becomes even more valuable as your application grows and multiple frontend, mobile, or third-party clients consume the same backend.
