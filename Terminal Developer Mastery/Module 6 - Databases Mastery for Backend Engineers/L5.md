# Why JOIN?

Without JOIN:

```
Users

Orders
```

Separate tables.

With JOIN:

```
Rahul

↓

Order 101

↓

$120.00
```

JOIN combines related data.

---

# INNER JOIN

Returns only matching rows.

```sql
SELECT
    users.name,
    orders.total
FROM users
INNER JOIN orders
ON users.id = orders.user_id;
```

Result:

```
Rahul   120.00

Rahul    80.00

Aman    250.00
```

Priya has no orders, so she isn't included.

---

# INNER JOIN Diagram

```
Users

● ● ●

Orders

● ●

↓

Only Matching Rows
```

---

# LEFT JOIN

Returns:

- All rows from left table
- Matching rows from right table

```sql
SELECT
    users.name,
    orders.total
FROM users
LEFT JOIN orders
ON users.id = orders.user_id;
```

Result:

```
Rahul   120.00

Rahul    80.00

Aman    250.00

Priya   NULL
```

---

# LEFT JOIN Diagram

```
Users

● ● ●

Orders

● ●

↓

All Users
```

---

# RIGHT JOIN

Opposite of LEFT JOIN.

```sql
SELECT *
FROM users
RIGHT JOIN orders
ON users.id = orders.user_id;
```

Less common because swapping table order with `LEFT JOIN` usually achieves the same result.

---

# FULL OUTER JOIN

Returns:

- All users
- All orders

Matched where possible.

```sql
SELECT *
FROM users
FULL OUTER JOIN orders
ON users.id = orders.user_id;
```

Useful for comparing datasets.

---

# CROSS JOIN

Every row with every row.

```sql
SELECT *
FROM users
CROSS JOIN products;
```

3 users × 10 products

↓

30 rows.

Use carefully.

---

# SELF JOIN

Join a table with itself.

Example:

Employees:

```
Employee

↓

Manager
```

```sql
SELECT
    e.name,
    m.name AS manager
FROM employees e
JOIN employees m
ON e.manager_id = m.id;
```

# Aggregate Functions

Aggregate functions summarize data.

---

# COUNT

Total rows:

```sql
SELECT COUNT(*)
FROM users;
```

Result:

```
3
```

---

# SUM

Total revenue:

```sql
SELECT SUM(total)
FROM orders;
```

Result:

```
450.00
```

---

# AVG

Average order value:

```sql
SELECT AVG(total)
FROM orders;
```

---

# MAX

Largest order:

```sql
SELECT MAX(total)
FROM orders;
```

---

# MIN

Smallest order:

```sql
SELECT MIN(total)
FROM orders;
```

---

# GROUP BY

Group rows before aggregation.

```sql
SELECT
    user_id,
    SUM(total)
FROM orders
GROUP BY user_id;
```

Result:

```
User 1

200.00

User 2

250.00
```

---

# GROUP BY Flow

```
Orders

↓

Group by User

↓

Sum
```

---

# HAVING

`WHERE`

↓

Filters rows.

`HAVING`

↓

Filters groups.

Example:

```sql
SELECT
    user_id,
    SUM(total)
FROM orders
GROUP BY user_id
HAVING SUM(total) > 150;
```

---

# WHERE vs HAVING

```sql
WHERE total > 100
```

Before grouping.

---

```sql
HAVING SUM(total) > 200
```

After grouping.

---

# Subqueries

A query inside another query.

Example:

Highest order:

```sql
SELECT *
FROM orders
WHERE total = (
    SELECT MAX(total)
    FROM orders
);
```

---

# IN Subquery

Users with orders:

```sql
SELECT *
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
);
```

---

# EXISTS

Checks whether rows exist.

```sql
SELECT *
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.user_id = u.id
);
```

Very useful in production.

---

# Common Table Expression (CTE)

Creates a temporary named result.

```sql
WITH totals AS (

    SELECT
        user_id,
        SUM(total) AS amount

    FROM orders

    GROUP BY user_id

)

SELECT *
FROM totals;
```

CTEs improve readability.

---

# Multiple CTEs

```sql
WITH

users_cte AS (

    SELECT *
    FROM users

),

orders_cte AS (

    SELECT *
    FROM orders

)

SELECT *
FROM users_cte;
```

Useful for complex queries.

---

# Window Functions

One of PostgreSQL's most powerful features.

Unlike `GROUP BY`, they do **not collapse rows**.

---

# ROW_NUMBER()

```sql
SELECT
    name,
    ROW_NUMBER() OVER (
        ORDER BY name
    )
FROM users;
```

Result:

```
1 Rahul

2 Aman

3 Priya
```

---

# RANK()

Ranking scores:

```sql
SELECT
    name,
    marks,
    RANK() OVER (
        ORDER BY marks DESC
    )
FROM students;
```

Equal scores receive the same rank, leaving gaps.

---

# DENSE_RANK()

Similar to `RANK()`.

No skipped rankings.

---

# Running Total

```sql
SELECT

    total,

    SUM(total) OVER (
        ORDER BY id
    )

FROM orders;
```

Result:

```
120

200

450
```

Excellent for dashboards.

---

# PARTITION BY

Separate rankings.

```sql
RANK() OVER (

PARTITION BY department

ORDER BY salary DESC

)
```

Ranks employees within each department.

---

# CASE

SQL's if-else.

```sql
SELECT

name,

CASE

WHEN age >= 18 THEN 'Adult'

ELSE 'Minor'

END

FROM users;
```

---

# COALESCE

Replace NULL.

```sql
SELECT

COALESCE(phone,'Not Available')

FROM users;
```

---

# NULLIF

Useful for avoiding division by zero.

```sql
SELECT

100 / NULLIF(value,0)
```

If `value` is zero, `NULLIF` returns `NULL`, preventing an error.

---

# Real Analytics Query

Revenue per user.

```sql
SELECT

u.name,

SUM(o.total)

FROM users u

JOIN orders o

ON u.id = o.user_id

GROUP BY u.name

ORDER BY SUM(o.total) DESC;
```

---

# Real Reporting Query

Top 5 customers.

```sql
SELECT

u.name,

SUM(o.total) AS revenue

FROM users u

JOIN orders o

ON u.id = o.user_id

GROUP BY u.name

ORDER BY revenue DESC

LIMIT 5;
```

---

# Query Execution Order

```
FROM

↓

JOIN

↓

WHERE

↓

GROUP BY

↓

HAVING

↓

SELECT

↓

ORDER BY

↓

LIMIT
```

Remember this.

# Best Practices

### Use Explicit JOINs

Prefer:

```sql
JOIN
```

instead of older comma-separated joins.

---

### Use Aliases

```sql
users u

orders o
```

Makes queries easier to read.

---

### Prefer CTEs

They improve readability for complex logic.

---

### Avoid Unnecessary Subqueries

Sometimes a JOIN is simpler and more efficient.

---

### Learn Window Functions

They're common in reporting, analytics, and interviews.

---

# Common Mistakes

❌ Forgetting the JOIN condition.

This can create an unintended Cartesian product.

---

❌ Using `HAVING` instead of `WHERE`.

---

❌ Grouping without understanding aggregation.

---

❌ Selecting columns that aren't grouped or aggregated.

# 💡 Senior Backend Engineer Insight

Most backend developers spend their time writing CRUD queries. Senior backend engineers spend much of their time writing **data retrieval and reporting queries** that answer business questions efficiently.

A common production flow looks like this:

```
Client Request
       │
       ▼
Express API
       │
       ▼
Repository / ORM
       │
       ▼
Complex SQL Query
       │
 ┌───────────────┐
 │ JOINs         │
 │ GROUP BY      │
 │ Aggregations  │
 │ Window Funcs  │
 │ CTEs          │
 └───────────────┘
       │
       ▼
PostgreSQL
       │
       ▼
JSON Response
```

Learning these SQL features has benefits beyond interviews:

- Build analytics dashboards.
- Generate business reports.
- Detect trends and anomalies.
- Optimize backend APIs by reducing application-side processing.
- Solve many problems with a **single SQL query** instead of multiple database calls.

Well-written SQL often replaces hundreds of lines of application code while being faster and easier for the database engine to optimize.
