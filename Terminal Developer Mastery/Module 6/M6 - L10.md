# What is Database Scaling?

Scaling means increasing your system's capacity to handle:

- More users
    
- More data
    
- More requests
    
- Higher availability
    

Without slowing down.

---

# The Growth Problem

```text
100 Users
    │
    ▼
1,000 Users
    │
    ▼
100,000 Users
    │
    ▼
10 Million Users
```

A single database server eventually becomes a bottleneck.

---

# Vertical Scaling (Scale Up)

Increase the power of a single machine.

```text
Database Server

8 GB RAM
↓

32 GB RAM
↓

64 GB RAM

More CPU

Faster SSD
```

---

## Advantages

- Simple
    
- No application changes
    
- Easy to manage
    

---

## Disadvantages

- Hardware limit
    
- Expensive
    
- Single point of failure
    

---

# Horizontal Scaling (Scale Out)

Instead of one powerful server:

```text
Database

↓

Server 1

Server 2

Server 3

Server 4
```

Multiple machines share the workload.

---

## Advantages

- Almost unlimited growth
    
- High availability
    
- Fault tolerance
    

---

## Disadvantages

- More complex
    
- Data distribution challenges
    
- Network overhead
    

---

# Which One First?

Most companies scale like this:

```text
Small Startup

↓

Vertical Scaling

↓

Read Replicas

↓

Caching

↓

Partitioning

↓

Sharding

↓

Global Distribution
```

Don't start with sharding on day one.

---

# Replication

Replication means copying data.

```text
Primary

↓

Secondary

↓

Secondary
```

All writes go to the primary.

Secondaries receive copies.

---

# Primary Database

Handles:

```text
INSERT

UPDATE

DELETE
```

Also serves reads when needed.

---

# Replica Database

Usually handles:

```text
SELECT
```

Only.

This reduces load on the primary.

---

# Read Replica Architecture

```text
               API

                 │

       ┌─────────┴─────────┐

       ▼                   ▼

 Primary DB          Read Replica

 Writes                 Reads
```

---

# Why Read Replicas?

Suppose:

```text
10,000

Read Requests

100

Write Requests
```

Reads dominate.

Replicas distribute the load.

---

# Replication Lag

Problem:

```text
Primary Updated

↓

Replica Not Updated Yet
```

Short delay.

A user might briefly read stale data.

---

# Eventual Consistency

Replica catches up later.

```text
Primary

↓

Replica

↓

Same Data
```

Eventually.

---

# Synchronous Replication

```text
Write

↓

Primary

↓

Replica

↓

Success
```

Safer.

Slightly slower.

---

# Asynchronous Replication

```text
Write

↓

Primary

↓

Success

↓

Replica Later
```

Faster.

Most common.

---

# Partitioning

Split one huge table.

Instead of:

```text
Orders

10 Billion Rows
```

Use:

```text
Orders_2024

Orders_2025

Orders_2026
```

---

# Benefits

Queries scan less data.

Maintenance becomes easier.

---

# PostgreSQL Partitioning

```sql
CREATE TABLE orders (

id BIGINT,

created_at DATE

)

PARTITION BY RANGE(created_at);
```

Example partitions:

```text
orders_2025

orders_2026
```

---

# Types of Partitioning

## Range

```text
January

↓

February

↓

March
```

Great for dates.

---

## List

```text
India

USA

Japan
```

Partition by country.

---

## Hash

```text
Hash(UserID)

↓

Partition
```

Even distribution.

---

# Sharding

Horizontal partitioning across servers.

Instead of:

```text
One Server

↓

10 TB
```

Use:

```text
Shard 1

Shard 2

Shard 3

Shard 4
```

---

# Example

Users:

```text
A–F

↓

Shard 1

G–M

↓

Shard 2

N–Z

↓

Shard 3
```

---

# Better Sharding

Use a hash.

```text
Hash(User ID)

↓

Shard
```

More balanced.

---

# Good Shard Key

Should:

- Distribute evenly
    
- Avoid hotspots
    
- Support common queries
    

Examples:

```text
user_id

tenant_id
```

---

# Bad Shard Key

Timestamp.

Why?

Every new row lands on one shard.

Hotspot.

---

# Sharding Architecture

```text
Application

↓

Router

↓

Shard 1

Shard 2

Shard 3
```

Router decides where data lives.

---

# Load Balancer

Distributes requests.

```text
Clients

↓

Load Balancer

↓

API 1

API 2

API 3
```

Databases benefit indirectly because traffic is spread across application servers.

---

# Connection Pooling

Opening a database connection is expensive.

Bad:

```text
Request

↓

Open Connection

↓

Query

↓

Close
```

Every request.

---

Better:

```text
Pool

↓

Reuse Connection
```

---

# Why Pooling?

Without pool:

```text
1000 Requests

↓

1000 Connections
```

With pool:

```text
1000 Requests

↓

20 Connections
```

Huge savings.

---

# Node.js Example

```javascript
const { Pool } = require("pg");

const pool = new Pool({

  max: 20

});
```

Twenty reusable connections.

---

# PgBouncer

Popular PostgreSQL connection pooler.

```text
Application

↓

PgBouncer

↓

PostgreSQL
```

Useful for thousands of concurrent connections.

---

# Caching Before Scaling

Don't scale the database first.

Ask:

```text
Can Redis cache this?
```

Often the answer is yes.

---

# CAP Theorem

Distributed systems can guarantee only **two** of these three properties simultaneously:

```text
C

Consistency

A

Availability

P

Partition Tolerance
```

---

# Consistency

Every client sees the latest committed data.

---

# Availability

Every request receives a response.

---

# Partition Tolerance

System continues working despite network failures between nodes.

---

# Real World

Network failures happen.

Therefore:

```text
Partition Tolerance

↓

Always Needed
```

Most distributed systems choose between stronger consistency and higher availability during a partition.

---

# CP Systems

Choose:

```text
Consistency

+

Partition Tolerance
```

May reject or delay some requests during network partitions.

---

# AP Systems

Choose:

```text
Availability

+

Partition Tolerance
```

May temporarily return stale data.

---

# Database Choices

|Database|Typical Design|
|---|---|
|PostgreSQL|Strong consistency|
|MongoDB Replica Sets|Tunable depending on read/write concerns|
|Redis|Tunable depending on persistence and replication configuration|

Real-world behavior depends on deployment and configuration.

# Best Practices

### Optimize First

Before scaling:

- Improve queries
    
- Add indexes
    
- Cache results
    

---

### Use Connection Pools

Never open one database connection per request.

---

### Cache Hot Data

Redis is usually cheaper than adding more database servers.

---

### Choose Good Shard Keys

Avoid hotspots.

---

### Monitor Everything

Scaling decisions should be driven by metrics.

---

# Common Mistakes

❌ Sharding too early.

---

❌ Ignoring replication lag.

---

❌ Not using connection pooling.

---

❌ Scaling before optimizing queries.

---

❌ Treating Redis as a permanent data store.

# 💡 Senior Backend Engineer Insight

Most successful backend systems don't jump straight to distributed databases. They evolve in stages.

```text
Stage 1
──────────────
Single Database
        │
        ▼
Stage 2
──────────────
Indexes
+
Connection Pool
+
Redis Cache
        │
        ▼
Stage 3
──────────────
Primary
+
Read Replicas
        │
        ▼
Stage 4
──────────────
Partitioning
+
Background Workers
        │
        ▼
Stage 5
──────────────
Sharding
+
Multi-Region Deployment
```

For **95% of startups**, the following combination is enough for a long time:

- Well-designed database schema
    
- Proper indexes
    
- Connection pooling
    
- Redis caching
    
- Read replicas
    
- Continuous monitoring
    

Sharding is powerful, but it introduces operational complexity. Most engineering teams postpone it until there is clear evidence that simpler scaling techniques are no longer sufficient.
