# Why Database Security Matters

Imagine your application stores:

```text
Users

↓

Passwords

↓

Payments

↓

Personal Information
```

If an attacker gains database access, they may:

- Read sensitive information
    
- Modify records
    
- Delete data
    
- Install malicious objects (depending on privileges)
    
- Demand ransom after encrypting or deleting data

# CIA Triad

Every security system aims to protect:

```text
Confidentiality

↓

Integrity

↓

Availability
```

---

## Confidentiality

Only authorized people can access data.

Example:

Only the account owner should view their bank balance.

---

## Integrity

Data cannot be changed without authorization.

Example:

An attacker cannot modify an order amount.

---

## Availability

Authorized users should access data when needed.

Example:

Backups and replication help maintain availability.

# Principle of Least Privilege

Give only the permissions required.

Bad:

```text

↓

Full Database Admin
```

Good:

```text

↓

UPDATE
```

Only where needed.

# SQL Injection

One of the most common database attacks.

Bad code:

```javascript
const query =
  "SELECT * FROM users WHERE email = '" + email + "'";
```

If input is:

```text
' OR 1=1 --
```

The query may return every user.

---

# Safe Queries

Always use parameterized queries.

```javascript
const result = await pool.query(
  "SELECT * FROM users WHERE email = $1",
  [email]
);
```

The database treats the input as data, not SQL.

---

# Prisma Example

```javascript
const user = await prisma.user.findUnique({
  where: {
    email
  }
});
```

ORMs help reduce injection risk when used correctly.

---

# Mongoose Example

```javascript
const user = await User.findOne({
  email
});
```

Still validate and sanitize input.

---

# NoSQL Injection

Unsafe:

```javascript
User.findOne(req.body);
```

If the attacker sends:

```json
{
  "email": {
    "$ne": null
  }
}
```

The query may behave unexpectedly.

Safer:

```javascript
User.findOne({
  email: req.body.email
});
```

Validate input types before querying.

---

# Input Validation

Never trust user input.

Use:

- Joi
    
- Zod
    
- express-validator
    

Example:

```javascript
const schema = Joi.object({
  email: Joi.string().email().required()
});
```

Validate before reaching the database.

---

# Password Storage

Never store:

```text
password123
```

Always store:

```text
Hashed Password
```

Recommended:

- bcrypt
    
- Argon2
    
- scrypt
    

---

# bcrypt Example

```javascript
const hashedPassword =
  await bcrypt.hash(password, 12);
```

Verification:

```javascript
await bcrypt.compare(password, hashedPassword);
```

Never decrypt passwords—they are verified by comparing hashes.

# Environment Variables

Never hardcode:

```javascript

```

Use:

```javascript

```

---

# Don't Commit Secrets

Never push:

```text

```

to Git.

Use:

```text
.gitignore
```

And rotate credentials if they're accidentally exposed.

---

# PostgreSQL Roles

Create a role:

```sql
CREATE ROLE app_user
LOGIN
PASSWORD 'strong_password';
```

Grant limited permissions:

```sql
GRANT SELECT, INSERT, UPDATE
ON users
TO app_user;
```

Avoid using superuser accounts in applications.

---

# MongoDB Roles

Create a user with limited permissions.

Example role:

```text
readWrite
```

Avoid administrative accounts for application connections.

---

```text

↓
```

# Best Practices

### Use Parameterized Queries

Never concatenate SQL strings with user input.

---

### Validate Every Input

Treat all user input as untrusted.

---

### Hash Passwords

Use:

- bcrypt
    
- Argon2
    

Never reversible encryption.

---

### Restrict Database Permissions

Applications should never connect as administrators.

---

### Rotate Secrets

Change credentials periodically and after suspected exposure.

---

### Enable Monitoring

Watch for:

- Failed logins
    
- Unusual query activity
    
- Permission changes
    

---

# Common Mistakes

❌ Hardcoding database passwords.

---

❌ Running applications as the database superuser.

---

❌ Logging passwords or JWTs.

---

❌ Skipping input validation because "the frontend validates it."

---

❌ Leaving databases exposed to the public internet.

# 💡 Senior Backend Engineer Insight

Database security isn't a single feature—it's the result of multiple layers working together.

```text
Internet
    │
    ▼
HTTPS
    │
    ▼
Authentication
    │
    ▼
Authorization
    │
    ▼
Input Validation
    │
    ▼
Parameterized Queries
    │
    ▼
Database
    │
    ▼
Encryption
    │
    ▼
Encrypted Backups
    │
    ▼
Monitoring & Auditing
```

A production-ready backend follows a **defense-in-depth** strategy:

- The **application** validates and authorizes requests.
    
- The **database** enforces constraints, permissions, and data integrity.
    
- The **infrastructure** protects secrets, network access, and backups.
    
- The **operations team** monitors logs, rotates credentials, and responds to incidents.
    

No single control is enough by itself, but together they significantly reduce risk.
