# Module 6 — Lesson 12: ORMs & Query Builders 🏗️

> **"An ORM makes database access easier. A backend engineer knows when to use the ORM—and when to bypass it."**

One of the biggest mistakes beginners make is believing:

> **"ORMs replace SQL."**

They don't.

ORMs generate SQL for you.

If you don't understand SQL, you'll eventually struggle to debug performance problems, optimize queries, or understand what the ORM is doing behind the scenes.

# What is an ORM?

ORM = **Object Relational Mapper**

It maps:

```text
JavaScript Objects

↓

SQL Tables
```

Instead of writing:

```sql
SELECT * FROM users;
```

You write:

```javascript
await prisma.user.findMany();
```

The ORM generates the SQL.

---

# Without ORM

```text
Application

↓

Raw SQL

↓

Database
```

---

# With ORM

```text
Application

↓

ORM

↓

SQL

↓

Database
```

---

# Why Use an ORM?

Advantages:

- Faster development
    
- Type safety
    
- Easier CRUD
    
- Migrations
    
- Relationships
    
- Reduced boilerplate
    

---

# Downsides

ORMs are **not magic**.

Possible issues:

- Slower complex queries
    
- Hidden SQL
    
- N+1 problems
    
- Difficult optimization
    
- Vendor lock-in

# ORM vs Query Builder

ORM:

```javascript
await prisma.user.findMany();
```

Query Builder:

```javascript
knex("users")
.select("*");
```

Raw SQL:

```sql
SELECT *
FROM users;
```

---

# What is a Query Builder?

Instead of generating SQL from models:

You build SQL programmatically.

```text
JavaScript

↓

SQL

↓

Database
```

More flexible than many ORMs.

# Repository Pattern

Don't let controllers access the database directly.

Good architecture:

```text
Controller

↓

Service

↓

Repository

↓

ORM

↓

Database
```

---

# Repository Example

```javascript
class UserRepository {

async findByEmail(email){

return prisma.user.findUnique({

where:{

email

}

});

}

}
```

Benefits:

- Easier testing
    
- Easier refactoring
    
- Database abstraction

# N+1 Problem

Bad:

```text
Load Users

↓

Loop

↓

Load Posts

↓

Loop

↓

Load Comments
```

Many unnecessary queries.

---

Better:

```text
Single Query

↓

JOIN

↓

Result
```

Or eager loading where appropriate.

---

# Lazy Loading

Load related data only when requested.

```text
User

↓

Posts (Later)
```

---

# Eager Loading

Load immediately.

```text
User

↓

Posts
```

One request.

---

# Choosing Lazy vs Eager

Use eager loading when related data is always needed.

Use lazy loading when it is rarely needed.

Avoid over-fetching.

Good candidates:

- Complex reports
    
- Window functions
    
- Recursive queries
    
- Bulk operations
    
- Database-specific features
    

Keep most CRUD in the ORM.

# 💡 Senior Backend Engineer Insight

Experienced backend engineers don't become attached to a single database library—they choose the right abstraction for the task.

```text
                  Service Layer
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   Prisma ORM      Raw SQL (pg)     Redis Client
        │               │               │
        └───────────────┼───────────────┘
                        ▼
                  PostgreSQL
```

A practical approach for production systems is:

- **Prisma or Drizzle** for everyday CRUD operations.
    
- **Raw SQL** for complex reports, bulk updates, and performance-critical queries.
    
- **Repository pattern** to isolate data access from business logic.
    
- **Migrations** to evolve the schema safely and consistently.
    

This gives you the productivity of an ORM without sacrificing the flexibility and performance of SQL when it matters.
