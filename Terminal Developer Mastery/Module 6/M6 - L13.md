# What is a Backup?

A backup is a copy of your data that can be restored later.

```text
Production Database
        │
        ▼
     Backup Copy
        │
        ▼
 Restore if Needed
```

---

# Backup Goals

A good backup strategy should protect against:

- Hardware failure
    
- Human error
    
- Software bugs
    
- Ransomware
    
- Cloud outages
    
- Natural disasters
    

---

# Types of Backups

There are three major types.

```text
Full Backup

Incremental Backup

Differential Backup
```

---

# Full Backup

Copies everything.

```text
Database

↓

Complete Copy
```

Advantages:

- Easy restore
    
- Simple
    

Disadvantages:

- Large storage
    
- Slow
    

---

# Incremental Backup

Only copies changes since the previous backup.

```text
Monday

Full Backup

↓

Tuesday

Changes

↓

Wednesday

Changes
```

Advantages:

- Small
    
- Fast
    

Disadvantages:

- Restore takes longer because multiple backups are needed.
    

---

# Differential Backup

Copies everything changed since the last **full** backup.

```text
Monday

Full

↓

Tuesday

Changes

↓

Wednesday

Tuesday + Wednesday Changes
```

Restore is usually faster than incremental backups.

---

# Backup Comparison

|Type|Size|Backup Speed|Restore Speed|
|---|---|---|---|
|Full|Large|Slow|Fast|
|Incremental|Small|Fast|Slow|
|Differential|Medium|Medium|Medium|

---

# Backup Schedule

Example:

```text
Sunday

Full Backup

↓

Monday–Saturday

Incremental Backups
```

Common production strategy.

---

# Hot Backup

Backup while database is running.

```text
Users Continue Working

↓

Backup Runs
```

Preferred for production.

---

# Cold Backup

Database is stopped.

```text
Shutdown

↓

Backup

↓

Restart
```

Simple but causes downtime.

---

# PostgreSQL Backups

Common tools:

- `pg_dump`
    
- `pg_dumpall`
    
- `pg_basebackup`
    

---

# pg_dump

Backup one database.

```bash
pg_dump mydb > backup.sql
```

Logical backup.

---

# Restore

```bash
psql mydb < backup.sql
```

---

# pg_dumpall

Backup every database.

```bash
pg_dumpall > full_backup.sql
```

---

# pg_basebackup

Creates a physical backup of the PostgreSQL cluster.

Useful for:

- Replication
    
- Disaster recovery
    
- Large production systems
    

---

# Write-Ahead Log (WAL)

One of PostgreSQL's most important features.

Every change is first written to the WAL.

```text
SQL Query

↓

WAL

↓

Database Files
```

Benefits:

- Crash recovery
    
- Replication
    
- Point-in-Time Recovery
    

---

# Point-in-Time Recovery (PITR)

Suppose:

```text
10:00 Backup

↓

10:30 Accident

↓

Delete Users

↓

11:00 Realize Mistake
```

With PITR:

Restore database to:

```text
10:29:59
```

Instead of losing an entire day's work.

---

# WAL Archiving

```text
Database

↓

WAL Files

↓

Archive Storage
```

Required for PITR.

---

# MongoDB Backup

Common tools:

- `mongodump`
    
- `mongorestore`
    

---

# mongodump

```bash
mongodump --db backend
```

Creates BSON backup files.

---

# mongorestore

```bash
mongorestore dump/
```

Restores the database.

---

# MongoDB Replica Sets

Backups are often taken from a secondary node.

Benefits:

- Less load on primary
    
- Reduced production impact
    

---

# Redis Recovery

Redis stores data primarily in memory.

Persistence options:

- RDB
    
- AOF
    

---

# RDB Recovery

```text
Snapshot

↓

Restart

↓

Restore Snapshot
```

---

# AOF Recovery

Replay every recorded command.

```text
SET

↓

INCR

↓

HSET

↓

Restore
```

Generally offers less data loss than RDB alone.

---

# Cloud Snapshots

Cloud providers commonly support:

```text
Database

↓

Snapshot

↓

Cloud Storage
```

Useful for managed databases.

---

# 3-2-1 Backup Rule

One of the best-known backup practices.

Keep:

```text
3 Copies

↓

2 Different Media

↓

1 Off-site Copy
```

Example:

- Production database
    
- Local backup
    
- Cloud backup
    

---

# Encryption

Always encrypt backups.

```text
Database

↓

Encrypted Backup

↓

Storage
```

If a backup is stolen, encryption helps protect the data.

---

# Backup Retention

Example policy:

```text
Daily

7 Days

Weekly

4 Weeks

Monthly

12 Months
```

Retention depends on business and regulatory needs.

---

# Backup Verification

Never assume backups work.

Always test:

```text
Backup

↓

Restore

↓

Verify Data
```

An untested backup is not a reliable backup.

---

# Disaster Recovery (DR)

Disaster Recovery is the plan for restoring service after a major failure.

Example:

```text
Database Failure

↓

Restore Backup

↓

Recover Service
```

---

# Recovery Time Objective (RTO)

Question:

```text
How quickly must the system be restored?
```

Example:

15 minutes.

---

# Recovery Point Objective (RPO)

Question:

```text
How much data loss is acceptable?
```

Example:

5 minutes.

---

# RTO vs RPO

```text
Failure

↓

Restore

↓

Running Again
```

RTO:

Time to recover.

RPO:

Maximum acceptable data loss.

---

# Example

Company requirements:

```text
RTO = 30 Minutes

RPO = 5 Minutes
```

Meaning:

- Restore within 30 minutes.
    
- Lose no more than 5 minutes of data.

# Multi-Region Disaster Recovery

```text
Primary Region

↓

Backup Region

↓

Restore if Needed
```

Protects against regional outages.

---

# Real MERN Example

Suppose your Todo application uses:

```text
PostgreSQL

↓

Redis

↓

Object Storage
```

Recovery order:

1. PostgreSQL
    
2. Redis cache rebuild
    
3. Restart application
    

Since Redis is a cache, it can often be repopulated from the primary database.

# Best Practices

### Automate Backups

Never rely on manual backups.

---

### Test Restores Regularly

A backup that can't be restored is effectively useless.

---

### Encrypt Backups

Protect sensitive information.

---

### Store Backups Off-site

Protect against local disasters.

---

### Monitor Backup Jobs

Alert immediately on failures.

---

### Document Recovery Procedures

Everyone on the team should know the recovery process.

---

# Common Mistakes

❌ Keeping backups on the same server as the database.

---

❌ Never testing restore procedures.

---

❌ Forgetting WAL archiving when PITR is required.

---

❌ Storing backups without encryption.

---

❌ No retention policy.

# Backup & Recovery Cheat Sheet

```text
Full Backup
→ Entire database

Incremental
→ Changes since last backup

Differential
→ Changes since last full backup

WAL
→ Crash recovery + PITR

PITR
→ Restore to a specific time

RTO
→ Recovery time target

RPO
→ Acceptable data loss

3-2-1 Rule
→ 3 copies
→ 2 media
→ 1 off-site

Always:
→ Encrypt
→ Automate
→ Test restores
```

# 💡 Senior Backend Engineer Insight

Professional teams don't measure success by **how quickly they can take a backup**—they measure it by **how confidently they can recover**.

A mature production environment follows a complete recovery lifecycle:

```text
Production Database
        │
        ▼
 Automated Backups
        │
        ▼
 Encrypted Storage
        │
        ▼
 Off-site Replication
        │
        ▼
 Regular Restore Testing
        │
        ▼
 Documented Disaster Recovery Plan
        │
        ▼
 Monitoring & Alerts
```

The key mindset is:

- **Backups prevent data loss.**
    
- **Recovery procedures reduce downtime.**
    
- **Restore testing proves your backups actually work.**
    

Many organizations discover backup problems only during an emergency. Practicing restores before an incident is what separates resilient engineering teams from unprepared ones.
