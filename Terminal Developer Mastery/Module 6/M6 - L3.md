# What is Database Design?

Database design is the process of organizing data so that it is:

- Easy to store
    
- Easy to retrieve
    
- Easy to update
    
- Consistent
    
- Scalable
    

Think of it as creating the blueprint before building a house.

---

# Step 1 — Identify Entities

An **entity** is a real-world object you want to store.

For an online store:

```text
E-commerce

├── User
├── Product
├── Order
├── Category
├── Payment
└── Review
```

Each becomes a table.

---

# Step 2 — Identify Attributes

Attributes describe an entity.

Example:

```text
User

├── id
├── name
├── email
├── phone
├── password
└── created_at
```

---

# Step 3 — Choose Primary Keys

Every table needs a unique identifier.

```text
Users

id
```

```text
Products

id
```

```text
Orders

id
```

Primary keys should:

- Be unique
    
- Never change
    
- Never be NULL
    

---

# Step 4 — Identify Relationships

Entities rarely exist alone.

Example:

```text
User

↓

Orders
```

One user can have many orders.

---

# Relationship Types

There are four main relationship types.

---

# 1. One-to-One (1:1)

Example:

```text
User
 │
 │
 ▼
Profile
```

One user has one profile.

Example tables:

```text
Users

id
name
email
```

```text
Profiles

id
user_id
bio
avatar
```

---

# 2. One-to-Many (1:N)

Most common relationship.

Example:

```text
User

↓

Orders
```

One user

↓

Many orders

Tables:

```text
Users

id
name
```

```text
Orders

id
user_id
total
```

---

# 3. Many-to-One (N:1)

Reverse of One-to-Many.

```text
Many Orders

↓

One User
```

---

# 4. Many-to-Many (M:N)

Example:

Students enroll in many courses.

Courses contain many students.

```text
Students

↔

Courses
```

Needs a junction table.

```text
Enrollments

student_id

course_id
```

---

# Cardinality

Cardinality describes **how many** records can be related.

```text
1 : 1

1 : N

N : 1

M : N
```

---

# ER Diagram

Entity Relationship Diagram.

Example:

```text
Users
-----
id
name
email
   │
   │ 1
   │
   │
   ▼
Orders
------
id
user_id
total
status
```

---

# E-commerce Example

```text
Users
   │
   │
   ▼
Orders
   │
   │
   ▼
Order_Items
   ▲
   │
Products
```

This is a common production design.

# Why Not Store Everything in One Table?

Bad:

```text
Order

User Name

User Email

Product Name

Product Price
```

Problems:

- Duplicate user data
    
- Duplicate product data
    
- Hard to update
    
- Wasted storage
    

---

# Normalization

Normalization reduces:

- Duplication
    
- Inconsistency
    
- Update problems
    

Goal:

Store each fact only once.

---

# First Normal Form (1NF)

Rules:

- Atomic values
    
- No repeating groups
    

Bad:

```text
Phone

9876543210,9999999999
```

Good:

```text
Phone

9876543210
```

or create a separate phone table if multiple numbers are required.

---

# Second Normal Form (2NF)

Requirements:

- Must satisfy 1NF
    
- Every non-key column depends on the whole primary key
    

This mainly matters when using composite primary keys.

---

# Third Normal Form (3NF)

Requirements:

- Must satisfy 2NF
    
- No transitive dependencies
    

Bad:

```text
Students

id

city

state
```

If state depends on city rather than the student, consider separating location data.

---

# Normalization Example

Bad:

```text
Orders

Order ID

User Name

User Email

Product Name

Price
```

Good:

```text
Users

Orders

Products

Order_Items
```

Each table has one responsibility.

---

# Denormalization

Sometimes duplication is intentional.

Example:

```text
Orders

total_price
```

Even though it can be calculated from order items.

Why?

Because recalculating every time can be expensive.

Trade-off:

```text
More Storage

↓

Faster Reads
```

---

# SQL vs MongoDB Design

## SQL

Normalize more aggressively.

```text
Users

↓

Orders

↓

Products
```

---

## MongoDB

Embedding is common when data naturally belongs together.

```json
{
  "_id": "...",
  "name": "Rahul",
  "addresses": [
    {
      "city": "Delhi"
    }
  ]
}
```

References are still useful for large or shared data.

---

# Choosing Embed vs Reference (MongoDB)

Embed when:

- Data belongs exclusively to the parent
    
- Data is usually read together
    
- Arrays stay reasonably small
    

Reference when:

- Data is shared
    
- Data grows without bound
    
- Documents could exceed MongoDB's document size limit
    

---

# Naming Conventions

Tables:

```text
users

orders

products
```

Columns:

```text
user_id

created_at

updated_at
```

Use consistent naming throughout the project.

---

# Data Types Matter

Bad:

```text
price

TEXT
```

Good:

```text
price

DECIMAL
```

Bad:

```text
age

VARCHAR
```

Good:

```text
age

INTEGER
```

# Constraints

Useful constraints include:

Primary Key:

```sql
PRIMARY KEY
```

Unique:

```sql
UNIQUE(email)
```

Not Null:

```sql
NOT NULL
```

Foreign Key:

```sql
FOREIGN KEY
```

Constraints help the database enforce correctness.

# Real Example — URL Shortener

Since you've built a URL shortener, here's a production-friendly relational design.

```text
Users
----------------
id
name
email
password_hash
created_at
```

```text
Short_URLs
----------------
id
user_id
short_code
original_url
expires_at
created_at
```

```text
Clicks
----------------
id
short_url_id
ip_address
user_agent
referrer
clicked_at
```

Relationship:

```text
Users
   │
   ▼
Short_URLs
   │
   ▼
Clicks
```

Benefits:

- Users own many short URLs.
    
- Each short URL has many click records.
    
- Analytics scale independently from URL storage.

# Common Design Mistakes

❌ One giant table.

---

❌ No primary key.

---

❌ Storing comma-separated values.

Example:

```text
skills

Java,Python,C++
```

Instead, use a separate table or collection as appropriate.

---

❌ Using incorrect data types.

---

❌ Missing foreign keys.

---

# Schema Evolution

Applications change over time.

Example:

Version 1:

```text
Users

id

name
```

Version 2:

```text
Users

id

name

phone
```

Database migrations allow schemas to evolve safely.

# Best Practices

### Model the Real World

Tables should represent real business concepts.

---

### Keep One Responsibility Per Table

Avoid mixing unrelated data.

---

### Use Constraints

Let the database help enforce data integrity.

---

### Normalize First

Denormalize only after identifying a performance need.

---

### Plan for Growth

Design with future features in mind, but avoid overengineering.

---

---

❌ Storing multiple values in one column.

---

❌ Forgetting relationships.

# 💡 Senior Backend Engineer Insight

Database design is about modeling **business rules**, not just storing data.

For example, an order in an e-commerce system isn't simply a list of products—it has:

- A customer
    
- One or more items
    
- A payment
    
- A shipping address
    
- A status history
    
- Timestamps
    
- Business constraints
    

A production architecture often looks like this:

```text
                React
                  │
                  ▼
             Express API
                  │
          Business Logic
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 PostgreSQL            Redis Cache
(Relational Data)      (Fast Access)
        │
        ▼
 Well-Normalized Schema
        │
        ▼
Indexes + Constraints + Transactions
```

Strong backend engineers spend significant time designing the data model **before** writing code. A solid schema makes application logic simpler, improves performance, and reduces bugs.
