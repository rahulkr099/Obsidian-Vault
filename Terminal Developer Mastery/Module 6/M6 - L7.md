# What is a Transaction?

A **transaction** is a group of database operations treated as **one logical unit of work**.

Either:

```text
Everything Succeeds
```

or

```text
Everything Fails
```

Never halfway.

---

# Real Example

Transfer:

```text
Rahul

↓

Transfer $500

↓

Aman
```

Operations:

```text
1. Deduct $500

2. Add $500

3. Save History
```

All three must succeed together.

---

# Without Transaction

```text
Deduct Money

✓

Power Failure

↓

Add Money

✗
```

Money disappears.

---

# With Transaction

```text
BEGIN

↓

Deduct

↓

Add

↓

History

↓

COMMIT
```

If anything fails:

```text
ROLLBACK
```

Everything returns to its original state.

---

# Transaction Lifecycle

```text
BEGIN
   │
   ▼
SQL Statements
   │
   ▼
Success?
   │
 ┌─┴─────┐
 │        │
Yes      No
 │        │
 ▼        ▼
COMMIT ROLLBACK
```

---

# BEGIN

Start transaction.

```sql
BEGIN;
```

Nothing is permanent yet.

---

# COMMIT

Save changes.

```sql
COMMIT;
```

Now changes become permanent.

---

# ROLLBACK

Undo everything.

```sql
ROLLBACK;
```

Database returns to its previous consistent state.

---

# Banking Example

Initial:

```text
Rahul

$1000

Aman

$500
```

Transfer:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

UPDATE accounts
SET balance = balance + 500
WHERE id = 2;

COMMIT;
```

Result:

```text
Rahul

$500

Aman

$1000
```

---

# Failure Example

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

-- Error occurs

ROLLBACK;
```

Final:

```text
Rahul

$1000
```

No money lost.

# ACID

Every serious relational database follows ACID principles.

```text
A

Atomicity

C

Consistency

I

Isolation

D

Durability
```

Let's understand each one.

---

# A — Atomicity

All or nothing.

Example:

```text
Withdraw

↓

Deposit

↓

History
```

If one fails:

Everything fails.

---

# Atomicity Visualization

```text
✓

✓

✗

↓

ROLLBACK
```

No partial updates.

---

# C — Consistency

Database rules must always remain valid.

Example:

```text
Balance

Cannot Become Negative
```

Constraint:

```sql
CHECK (balance >= 0)
```

Transactions should never leave the database in an invalid state.

---

# I — Isolation

Multiple users may use the database simultaneously.

Each transaction should behave correctly even when others are running.

---

# Example

Rahul buys:

```text
Laptop
```

At the same time:

Aman buys:

```text
Laptop
```

Without isolation:

Both may believe they bought the last item.

---

# D — Durability

After:

```sql
COMMIT;
```

Data survives:

- Power failure
    
- Server restart
    
- Crash
    

PostgreSQL uses the **Write-Ahead Log (WAL)** to help ensure durability.

---

# Isolation Problems

Without proper isolation, concurrent transactions can produce incorrect results.

Common problems:

- Dirty Read
    
- Non-Repeatable Read
    
- Phantom Read
    

---

# Dirty Read

Transaction A:

```text
Balance = $500
```

Not committed yet.

Transaction B:

Reads:

```text
$500
```

Then:

Transaction A rolls back.

The value never actually existed.

---

# Non-Repeatable Read

Transaction:

```text
Read Balance

↓

Another Transaction Updates

↓

Read Again
```

Different result.

---

# Phantom Read

Query:

```sql
SELECT *

FROM orders

WHERE total > 100;
```

Later:

Another transaction inserts:

```text
Order = $200
```

Running the same query again returns an extra row—a "phantom."

---

# Isolation Levels

PostgreSQL supports:

|Level|Prevents|
|---|---|
|Read Committed (default)|Dirty reads|
|Repeatable Read|Dirty + Non-repeatable reads|
|Serializable|Dirty + Non-repeatable + Phantom reads (by ensuring transactions behave as if executed one after another)|

Higher isolation often means more locking or retries.

---

# Read Committed

Default.

Every query sees only committed data.

Most web applications use this level successfully.

---

# Repeatable Read

If you read the same row twice:

Same value.

Even if another transaction commits changes in between.

---

# Serializable

Safest.

Database ensures the result is equivalent to transactions executing one at a time.

May require retrying transactions if serialization conflicts occur.

---

# Locks

Transactions lock data.

Purpose:

Prevent conflicting updates.

---

# Row Lock

Transaction:

```text
Update User 5
```

Another transaction waits.

Only that row is locked.

---

# Table Lock

Less common.

Entire table becomes unavailable for conflicting operations.

Usually avoided unless necessary.

---

# FOR UPDATE

Lock selected rows.

```sql
SELECT *

FROM accounts

WHERE id = 1

FOR UPDATE;
```

Prevents concurrent modifications until the transaction completes.

---

# Deadlock

Two transactions waiting for each other.

```text
Transaction A

Locks User

Needs Order

↓

Transaction B

Locks Order

Needs User
```

Neither can continue.

---

# PostgreSQL Deadlock Detection

Good news:

PostgreSQL detects deadlocks automatically.

One transaction is aborted.

The application should retry if appropriate.

---

# Avoid Deadlocks

Good practice:

Always lock resources in the same order.

Example:

```text
Users

↓

Orders

↓

Payments
```

Never change lock order randomly.

---

# Savepoints

Partial rollback.

```sql
BEGIN;

SAVEPOINT step1;
```

If needed:

```sql
ROLLBACK TO step1;
```

Useful in complex workflows.

---

# Transaction Example

Order placement.

```text
Create Order

↓

Reduce Inventory

↓

Payment

↓

Create Invoice

↓

COMMIT
```

Failure?

↓

Rollback.

---

# PostgreSQL Auto Commit

Normally:

```sql
INSERT ...

↓

Auto Commit
```

Each statement commits automatically unless you explicitly start a transaction.

---

# Node.js Example

Using the `pg` library:

```javascript
const client = await pool.connect();

try {
  await client.query("BEGIN");

  await client.query(
    "UPDATE accounts SET balance = balance - $1 WHERE id = $2",
    [500, 1]
  );

  await client.query(
    "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
    [500, 2]
  );

  await client.query("COMMIT");
} catch (err) {
  await client.query("ROLLBACK");
  throw err;
} finally {
  client.release();
}
```

This is the standard transaction pattern in Node.js.

---

# Prisma Transaction

```javascript
await prisma.$transaction([
  prisma.account.update({
    where: { id: 1 },
    data: {
      balance: {
        decrement: 500
      }
    }
  }),

  prisma.account.update({
    where: { id: 2 },
    data: {
      balance: {
        increment: 500
      }
    }
  })
]);
```

Prisma automatically commits if all operations succeed or rolls back if one fails.

---

# Mongoose Transaction

MongoDB also supports transactions (with replica sets).

```javascript
const session = await mongoose.startSession();

await session.withTransaction(async () => {
  // Multiple operations
});
```

# Best Practices

### Keep Transactions Short

Hold locks for the shortest possible time.

---

### Lock Only What You Need

Prefer row-level locks over table-level locks.

---

### Retry Serialization Failures

At higher isolation levels, applications should retry transactions that fail due to serialization conflicts.

---

### Always Handle Errors

Every transaction should have a rollback path.

---

### Commit Promptly

Don't leave transactions open longer than necessary.

---

# Common Mistakes

❌ Forgetting `ROLLBACK` after an error.

---

❌ Long-running transactions.

---

❌ Updating rows in inconsistent lock order.

---

❌ Using transactions for every simple `SELECT`.

---

❌ Ignoring transaction failures and retry requirements.

```sql

```

```text

C → Consistency

I → Isolation

D → Durability
```

```text
Read Committed
Repeatable Read
```

# 💡 Senior Backend Engineer Insight

Transactions are about protecting **business invariants**, not just grouping SQL statements.

Consider an order-processing system:

```text
Customer Places Order
         │
         ▼
Create Order Record
         │
         ▼
Reserve Inventory
         │
         ▼
Charge Payment
         │
         ▼
Create Shipment
         │
         ▼
Commit Transaction
```

If inventory reservation fails after payment is charged, your application must either:

- Roll back everything (when possible), or
    
- Use a carefully designed compensation workflow for distributed systems.
    

As systems grow into microservices, a single database transaction can no longer span every service. That's where patterns like the **Saga pattern** and **Outbox pattern** become important. Those topics build directly on the transaction concepts you've learned here.

For a single PostgreSQL-backed application, though, mastering transactions, locks, and ACID is one of the most valuable skills you can develop.
