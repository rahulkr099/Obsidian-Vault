# The Big Picture

Suppose you type:

```text
https://google.com
```

Your browser **doesn't know Google's IP address**.

It starts asking different DNS servers until it finds the answer.

The complete flow looks like this:

```text
Browser

↓

Browser Cache

↓

Operating System Cache

↓

Recursive DNS Resolver

↓

Root DNS Server

↓

TLD Server (.com)

↓

Authoritative DNS Server

↓

Google IP Address

↓

Browser connects to Google
```

---

# Step 1 — Browser Cache

Modern browsers cache DNS results.

Example:

Yesterday you visited:

```text
google.com
```

Today:

```text
google.com
```

Instead of asking DNS again:

```text
Browser

↓

Cache

↓

Google IP
```

The browser immediately uses the cached IP if it hasn't expired.

This makes websites load faster.

---

# Step 2 — Operating System Cache

If the browser doesn't have the answer, it asks the operating system.

Example:

```text
Chrome

↓

Linux DNS Cache
```

Linux may already know the answer.

If yes:

```text
Browser

↓

OS Cache

↓

IP Address
```

No Internet lookup is needed.

---

# Step 3 — Recursive DNS Resolver

If the OS cache doesn't know the answer, it contacts a **Recursive DNS Resolver**.

Usually this belongs to:

- Your ISP
    
- Google Public DNS (`8.8.8.8`)
    
- Cloudflare DNS (`1.1.1.1`)
    
- Quad9 (`9.9.9.9`)
    

Example:

```text
Laptop

↓

Recursive Resolver
```

Its job is simple:

> "Find the IP address for me."

---

# What Makes It "Recursive"?

Imagine asking a librarian:

> "Please find this book."

You don't search the shelves yourself.

The librarian does all the work.

A recursive resolver works the same way.

It asks multiple DNS servers until it gets the answer.

---

# Step 4 — Root DNS Server

If the recursive resolver doesn't already know the answer, it asks a **Root DNS Server**.

The root server **doesn't know Google's IP**.

Instead it replies:

> "I don't know the IP, but I know who manages `.com` domains."

Example:

```text
Resolver

↓

Root Server

↓

".com servers are over there."
```

---

# Root Servers

There are **13 logical root server identities**, named:

```text
A
B
C
...
M
```

Each logical root server is actually provided by many physical servers around the world using **Anycast**, making DNS fast and reliable.

They don't store every website.

They only know where to find top-level domain (TLD) servers.

---

# Step 5 — TLD Server

The resolver now contacts the **Top-Level Domain (TLD)** server.

For:

```text
google.com
```

It asks:

```text
.com
```

The TLD server replies:

> "I don't know Google's IP, but I know Google's authoritative DNS servers."

Example:

```text
Resolver

↓

.com Server

↓

Google Name Server
```

---

# What is a TLD?

Examples:

```text
.com

.org

.net

.edu

.gov

.in
```

Each TLD has its own DNS servers.

---

# Step 6 — Authoritative DNS Server

Now the resolver contacts Google's **Authoritative DNS Server**.

This server owns the DNS records.

Example:

```text
Resolver

↓

Google Authoritative Server
```

It finally replies:

```text
google.com

↓

142.250.xxx.xxx
```

This is the final answer.

---

# Step 7 — Cache the Answer

The recursive resolver stores the answer according to its **TTL (Time To Live)**.

Then it returns:

```text
IP Address
```

to your computer.

Your operating system also caches it.

Your browser may cache it too.

Now everyone has the answer for future requests.

---

# Step 8 — Connect to Google

Only now can networking continue.

```text
Browser

↓

TCP Connection

↓

TLS Handshake

↓

HTTPS Request

↓

Google Server
```

DNS resolution is complete.

# Recursive vs Iterative Queries

This is a very common interview question.

## Recursive Query

Your computer says:

> "Find the final answer for me."

The recursive resolver does all the work.

Example:

```text
Laptop

↓

Resolver

↓

Final IP
```

---

## Iterative Query

Now the resolver asks:

```text
Root Server
```

Root replies:

> "Ask the .com server."

Then:

```text
Resolver

↓

.com Server
```

The `.com` server replies:

> "Ask Google's authoritative server."

Finally:

```text
Resolver

↓

Authoritative Server

↓

Final IP
```

Each server gives the **best next direction**, not always the final answer.

---

# Recursive vs Iterative

|Recursive|Iterative|
|---|---|
|Client expects final answer|Server returns the best next step|
|Used between client and resolver|Used between DNS servers|
|Simpler for the client|Reduces work on individual DNS servers|

---

# Why Caching Is Important

Imagine one billion people visiting:

```text
google.com
```

Without caching:

```text
1 billion DNS lookups
```

every few minutes.

With caching:

```text
One lookup

↓

Millions of cached answers
```

Caching reduces:

- Latency
    
- Internet traffic
    
- DNS server load

# What Happens If DNS Fails?

Suppose:

```text
google.com
```

cannot be resolved.

Your browser shows an error such as:

```text
DNS_PROBE_FINISHED_NXDOMAIN
```

Even though:

- Google servers are working
    
- Your Internet connection exists
    

Without DNS, the browser doesn't know **where** to connect.

---

# Common DNS Errors

## NXDOMAIN

Means:

```text
Domain doesn't exist.
```

Example:

```text
gooogleeeee.com
```

---

## SERVFAIL

Means:

```text
DNS server failed.
```

---

## Timeout

The DNS server didn't respond before the request timed out.

---

## Wrong DNS Record

Example:

```text
api.example.com

↓

Old IP
```

Users reach the wrong server or no server at all.

## Query a domain

```bash

```

---

## Show only IP

```bash
dig +short google.com
```

---

## Find authoritative name servers

```bash
dig google.com NS
```

---

## Query a specific DNS server

```bash
dig @8.8.8.8 google.com
```

This asks Google's public DNS server directly.

---

## Query Cloudflare DNS

```bash
dig @1.1.1.1 google.com
```

Useful when comparing responses from different resolvers.

---

## Trace the DNS resolution path

```bash
dig +trace google.com
```

This command follows the resolution process from the root servers to the authoritative server, making it an excellent learning and debugging tool.

# Common Interview Questions

### 1. What is DNS resolution?

DNS resolution is the process of translating a domain name into an IP address so a client can connect to the correct server.

---

### 2. What is a recursive resolver?

A recursive resolver receives a DNS query from a client and performs all the necessary lookups to return the final answer.

---

### 3. What is an authoritative DNS server?

An authoritative DNS server stores the official DNS records for a domain and provides the definitive answer for those records.

---

### 4. What is the purpose of the root DNS servers?

Root DNS servers direct resolvers to the correct Top-Level Domain (TLD) servers.

---

### 5. Why is DNS caching important?

Caching speeds up DNS lookups, reduces latency, lowers network traffic, and decreases the load on DNS infrastructure.

---

### 6. What is the difference between recursive and iterative queries?

- **Recursive query:** The resolver is responsible for returning the final answer.
    
- **Iterative query:** Each DNS server returns the best next server to query until the authoritative server is reached.

# Key Takeaways

- DNS resolution starts with the **browser cache**, then the **OS cache**, before contacting a **recursive resolver**.
    
- **Root DNS servers** direct queries to the appropriate **TLD servers**.
    
- **TLD servers** point to the domain's **authoritative DNS servers**.
    
- The **authoritative server** provides the official DNS records.
    
- **Caching** makes DNS much faster and more scalable.
    
- `dig +trace` is one of the best commands for understanding and debugging DNS resolution.
