# Typical Production Architecture

Most production applications follow a similar architecture.

```text
                 Internet
                     │
                     ▼
               HTTPS (443)
                     │
                     ▼
                  Nginx
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
     React        Express      Django
  Static Files      API        Admin Panel
```

Nginx becomes the **single entry point**.

# Example 1 — Express.js

Suppose your Express server is running:

```text
localhost:3000
```

Basic Express app:

```javascript
const express = require("express");

const app = express();

app.get("/", (req, res) => {
    res.send("Hello from Express");
});

app.listen(3000);
```

---

## Nginx Configuration

```nginx
server {

    listen 80;

    server_name api.example.com;

    location / {

        proxy_pass http://localhost:3000;

    }

}
```

Flow:

```text
Browser

↓

api.example.com

↓

Nginx

↓

localhost:3000

↓

Express
```

# Example 2 — React + Express

This is one of the most common MERN deployments.

React build:

```text
/var/www/react
```

Express:

```text
localhost:3000
```

Configuration:

```nginx
server {

    listen 80;

    server_name example.com;

    root /var/www/react;

    index index.html;

    location / {

        try_files $uri /index.html;

    }

    location /api/ {

        proxy_pass http://localhost:3000;

    }

}
```

Requests:

```text
/

↓

React
```

Requests:

```text
/api/users

↓

Express
```

The frontend and backend share one domain.

---

# Why This Is Better

Instead of:

```text
Frontend

↓

example.com
```

and

```text
Backend

↓

api.example.com
```

you can simply use:

```text
example.com

↓

React

↓

/api

↓

Express
```

Benefits:

- No CORS issues
    
- Easier authentication with cookies
    
- Cleaner URLs
    
- Simpler deployment
    

This directly relates to issues you've encountered before with Vercel and Render deployments, where frontend and backend lived on different origins.

# Multiple Backend Services

Modern applications often have several services.

```text
Users

↓

Nginx

├── Auth Service
├── User Service
├── Payment Service
└── Notification Service
```

Example:

```nginx
location /auth/ {

    proxy_pass http://localhost:3001;

}

location /users/ {

    proxy_pass http://localhost:3002;

}

location /payments/ {

    proxy_pass http://localhost:3003;

}
```

Each URL goes to a different backend.

# SPA + API + Admin

A common architecture:

```text
Internet

↓

Nginx

├── React App
├── Admin Panel
└── Backend API
```

Configuration:

```nginx
server {

    listen 80;

    server_name example.com;

    root /var/www/react;

    location / {

        try_files $uri /index.html;

    }

    location /api/ {

        proxy_pass http://localhost:3000;

    }

    location /admin/ {

        proxy_pass http://localhost:4000;

    }

}
```

Everything works under one domain.

# Important Proxy Headers

A basic proxy works.

A **production proxy** forwards important headers.

Example:

```nginx
location / {

    proxy_pass http://localhost:3000;

    proxy_set_header Host $host;

    proxy_set_header X-Real-IP $remote_addr;

    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    proxy_set_header X-Forwarded-Proto $scheme;

}
```

These headers are extremely important.

---

## Host Header

```nginx
proxy_set_header Host $host;
```

Preserves:

```text
example.com
```

instead of:

```text
localhost
```

Your backend knows which domain the client requested.

---

## Client IP

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

Without this:

Backend sees:

```text
127.0.0.1
```

With it:

Backend sees:

```text
203.0.113.25
```

(the real client IP).

Useful for:

- Logging
    
- Security
    
- Rate limiting
    
- Analytics
    

---

## Forwarded IP Chain

```nginx
proxy_set_header X-Forwarded-For
$proxy_add_x_forwarded_for;
```

If requests pass through multiple proxies:

```text
Client

↓

Cloudflare

↓

Nginx

↓

Express
```

The backend receives the full chain of IPs.

---

## HTTPS Information

```nginx
proxy_set_header X-Forwarded-Proto $scheme;
```

Backend knows whether the original request used:

```text
http
```

or

```text
https
```

Many frameworks use this for secure redirects and cookie settings.

---

# WebSocket Support

Applications like:

- Chat apps
    
- Live dashboards
    
- Online games
    

need WebSockets.

Extra configuration:

```nginx
location /socket.io/ {

    proxy_pass http://localhost:3000;

    proxy_http_version 1.1;

    proxy_set_header Upgrade $http_upgrade;

    proxy_set_header Connection "upgrade";

}
```

Without these headers, WebSocket upgrades will fail.

# Common Errors

## 502 Bad Gateway

Meaning:

Nginx couldn't communicate with the backend.

Possible causes:

- Backend stopped
    
- Wrong port
    
- Firewall
    
- Backend crashed
    

---

## 504 Gateway Timeout

Meaning:

Backend took too long to respond.

Possible causes:

- Slow database
    
- Infinite loop
    
- Long-running request
    

---

## 404

Possible causes:

- Wrong `location`
    
- Incorrect `proxy_pass`
    
- Backend route doesn't exist
    

---

## CORS Problems

If:

```text
frontend.com
```

calls

```text
api.example.com
```

you need CORS.

If everything is served from:

```text
example.com
```

you often avoid many CORS complications entirely.

# Best Practices

- Serve static assets directly with Nginx.
    
- Proxy only dynamic requests.
    
- Forward proxy headers (`Host`, `X-Real-IP`, `X-Forwarded-*`).
    
- Keep backend services listening on localhost or private interfaces.
    
- Separate API routes from frontend routes.
    
- Monitor logs from both Nginx and your backend.

# Interview Questions

### 1. Why is Nginx placed in front of Express.js?

To provide HTTPS termination, static file serving, request routing, caching, compression, security features, and reverse proxy capabilities.

---

### 2. What does `proxy_set_header Host $host;` do?

It forwards the original `Host` header from the client so the backend knows which domain was requested.

---

### 3. Why is `X-Forwarded-For` important?

It preserves the client's IP address (and proxy chain) so the backend can perform accurate logging, analytics, and security checks.

---

### 4. Why can serving React and Express under one domain reduce CORS issues?

Because the browser treats requests as **same-origin**, avoiding many cross-origin restrictions.

---

### 5. What additional configuration is needed for WebSockets?

You typically need:

- `proxy_http_version 1.1`
    
- `proxy_set_header Upgrade $http_upgrade`
    
- `proxy_set_header Connection "upgrade"`
    

to allow the HTTP connection to upgrade to a WebSocket connection.

# Hands-on Practice

## Step 1: Start an Express server

```javascript
const express = require("express");

const app = express();

app.get("/api/hello", (req, res) => {
    res.json({
        message: "Hello from Express!"
    });
});

app.listen(3000);
```

---

## Step 2: Configure Nginx

```nginx
server {
    listen 80;
    server_name localhost;

    location /api/ {
        proxy_pass http://localhost:3000;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

---

## Step 3: Test the configuration

```bash
sudo nginx -t
```

---

## Step 4: Reload Nginx

```bash
sudo systemctl reload nginx
```

---

## Step 5: Test through Nginx

```bash
curl http://localhost/api/hello
```

Expected response:

```json
{
  "message": "Hello from Express!"
}
```

Notice that you're calling **Nginx**, but the response is coming from **Express**.

---

## Step 6: Inspect forwarded headers

Modify your Express route:

```javascript
app.get("/api/hello", (req, res) => {
    res.json({
        host: req.headers.host,
        forwardedFor: req.headers["x-forwarded-for"],
        protocol: req.headers["x-forwarded-proto"]
    });
});
```

Call the endpoint again and observe how Nginx passes information about the original client request.

# Key Takeaways

- Nginx can reverse proxy virtually any backend framework.
    
- A single Nginx instance can route requests to multiple backend services.
    
- `proxy_pass` forwards requests to backend applications.
    
- `proxy_set_header` ensures important client information reaches the backend.
    
- Hosting your frontend and backend under one domain simplifies deployment and often eliminates many CORS issues.
    
- WebSockets require additional proxy configuration to support protocol upgrades.
