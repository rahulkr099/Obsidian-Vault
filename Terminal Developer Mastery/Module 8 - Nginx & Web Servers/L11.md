Without optimization:

```text
Browser

↓

Nginx

↓

Backend

↓

Nginx

↓

```

Every request waits for the backend.

---

# What is Proxy Buffering?

Normally:

```text
Backend

↓

Small response

↓

Nginx

↓

Browser
```

Nginx can **buffer** the backend response before sending it to the client.

---

## Why Buffer?

Imagine:

Backend generates:

```text
100 MB response
```

Client internet:

```text
Very slow
```

Without buffering:

The backend stays busy until the slow client finishes downloading.

---

With buffering:

```text
Backend

↓

Nginx Memory

↓

Backend becomes free

↓

Slow client downloads from Nginx
```

The backend can immediately start serving new requests.

---

# Enable Buffering

Buffering is enabled by default.

Configuration:

```nginx
location / {

    proxy_pass http://localhost:3000;

    proxy_buffering on;

}
```

---

# Disable Buffering

Some applications need streaming.

Examples:

- Live logs
    
- Server-Sent Events (SSE)
    
- Streaming APIs
    

Configuration:

```nginx
proxy_buffering off;
```

Now data is sent immediately.

---

# Proxy Buffers

Configuration:

```nginx
proxy_buffers 8 16k;
```

Meaning:

```text
8 buffers

↓

16 KB each
```

Total buffer memory:

```text
128 KB
```

---

# Busy Buffers

```nginx
proxy_busy_buffers_size 32k;
```

Controls how much buffered data can be actively sent to clients while Nginx continues reading from the backend.

Usually, the default value is sufficient.

---

# Buffer Size

```nginx
proxy_buffer_size 8k;
```

Stores the **response headers** from the backend.

If your application sends unusually large headers (for example, many cookies), you may need to increase this.

---

# Timeouts

Production systems should never wait forever.

Nginx provides several timeout settings.

---

## Connect Timeout

```nginx
proxy_connect_timeout 5s;
```

Maximum time to establish a connection to the backend.

If the backend isn't reachable:

```text
5 seconds

↓

Fail
```

---

## Read Timeout

```nginx
proxy_read_timeout 60s;
```

Maximum time Nginx waits for the backend to send data.

Example:

```text
Backend

↓

Processing...

↓

No response

↓

60 seconds

↓

Timeout
```

Common symptom:

```text
504 Gateway Timeout
```

---

## Send Timeout

```nginx
proxy_send_timeout 60s;
```

Maximum time allowed for Nginx to send the request to the backend.

---

# Large File Uploads

By default, Nginx limits upload size.

Example error:

```text
413 Request Entity Too Large
```

Increase the limit:

```nginx
client_max_body_size 100M;
```

Now uploads up to **100 MB** are allowed.

Common values:

```text
10M

25M

50M

100M

500M
```

Choose a size that fits your application rather than simply making it as large as possible.

---

# Why This Matters

Suppose users upload videos.

Default:

```text
1 MB

↓

Upload fails
```

After configuration:

```text
100 MB

↓

Upload succeeds
```

---

# Keep-Alive Connections

Without keep-alive:

Every request creates a new TCP connection.

```text
Browser

↓

Connect

↓

Request

↓

Close

↓

Connect Again

↓

Request
```

This adds unnecessary overhead.

---

With keep-alive:

```text
One Connection

↓

Request

↓

Request

↓

Request

↓

Close
```

Much faster.

---

Configuration:

```nginx
keepalive_timeout 65;
```

Meaning:

Keep idle connections open for **65 seconds** before closing them.

---

# Backend Keep-Alive

For upstream servers:

```nginx
upstream backend {

    server localhost:3000;

    keepalive 32;

}
```

Meaning:

Maintain up to **32 idle connections** to the backend for reuse.

---

# What is an Upstream?

Instead of writing:

```nginx
proxy_pass http://localhost:3000;
```

Create a named backend:

```nginx
upstream backend {

    server localhost:3000;

}
```

Then:

```nginx
proxy_pass http://backend;
```

This becomes much more useful when multiple backend servers are added.

---

# Unix Sockets

Instead of TCP:

```text
localhost:3000
```

Some applications communicate using Unix domain sockets.

Example:

```text
/var/run/gunicorn.sock
```

Configuration:

```nginx
location / {

    proxy_pass http://unix:/var/run/gunicorn.sock;

}
```

---

# Why Use Unix Sockets?

Benefits:

- No TCP overhead on the same machine
    
- Slightly lower latency
    
- Efficient local communication
    

Common for:

- Django + Gunicorn
    
- PHP-FPM
    
- Some Node.js deployments
    

---

# Proxy HTTP Version

Default:

```nginx
proxy_http_version 1.0;
```

For modern applications:

```nginx
proxy_http_version 1.1;
```

Required for:

- WebSockets
    
- Connection reuse
    
- Persistent connections
    

---

# WebSocket Configuration

For applications like:

- Chat apps
    
- Live dashboards
    
- Notifications
    

Use:

```nginx
location /socket.io/ {

    proxy_pass http://localhost:3000;

    proxy_http_version 1.1;

    proxy_set_header Upgrade $http_upgrade;

    proxy_set_header Connection "upgrade";

}
```

Without these settings, the HTTP connection cannot upgrade to a WebSocket connection.

---

# Preserve Original Headers

A common production block:

```nginx
proxy_set_header Host $host;

proxy_set_header X-Real-IP $remote_addr;

proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

proxy_set_header X-Forwarded-Proto $scheme;
```

These help your backend:

- Know the original host
    
- Log the real client IP
    
- Detect HTTPS
    
- Support secure cookies and redirects
    

---

# Disable Request Buffering

Sometimes applications process uploads as they arrive.

Configuration:

```nginx
proxy_request_buffering off;
```

Useful for:

- Streaming uploads
    
- Video uploads
    
- Large file transfers
    

---

# Example Production Configuration

```nginx
upstream backend {
    server localhost:3000;
    keepalive 32;
}

server {

    listen 80;

    server_name api.example.com;

    client_max_body_size 50M;

    location / {

        proxy_pass http://backend;

        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;

    }

}
```

This configuration is suitable for many production APIs.

# Common Production Problems

## 502 Bad Gateway

Meaning:

Nginx cannot connect to the backend.

Possible causes:

- Backend stopped
    
- Wrong port
    
- Socket file missing
    
- Firewall
    
- Permission issue
    

---

## 504 Gateway Timeout

Meaning:

Backend is too slow.

Possible reasons:

- Slow database
    
- Long-running request
    
- Heavy computation
    

Possible solution:

```nginx
proxy_read_timeout 120s;
```

But increasing the timeout is only appropriate if long-running requests are expected. Otherwise, investigate why the backend is slow.

---

## 413 Request Entity Too Large

Cause:

Upload exceeds:

```nginx
client_max_body_size
```

Fix:

Increase the limit if appropriate.

---

## WebSocket Doesn't Connect

Usually caused by:

Missing:

```nginx
proxy_http_version 1.1;
```

or

```nginx
proxy_set_header Upgrade $http_upgrade;
```

# Best Practices

- Use **upstream** blocks instead of hardcoding backend addresses.
    
- Set appropriate timeout values rather than extremely large ones.
    
- Keep `client_max_body_size` as small as your application reasonably needs.
    
- Use HTTP/1.1 for modern proxying and WebSockets.
    
- Prefer Unix sockets for local communication when supported.
    
- Monitor logs after changing proxy settings to catch regressions early.

# Interview Questions

### 1. What is proxy buffering?

Proxy buffering allows Nginx to read the backend response into memory before sending it to the client, reducing the time backend servers remain occupied by slow clients.

---

### 2. What causes a `504 Gateway Timeout`?

It occurs when the backend fails to respond within the configured `proxy_read_timeout` period.

---

### 3. What does `client_max_body_size` control?

It defines the maximum size of the client request body that Nginx will accept, commonly affecting file uploads.

---

### 4. Why use an `upstream` block?

It creates a reusable named backend configuration and makes scaling to multiple backend servers much easier.

---

### 5. Why use Unix sockets instead of TCP?

For processes running on the same machine, Unix sockets can reduce networking overhead and offer slightly better performance.

# Hands-on Practice

## Step 1: Create an upstream

```nginx
upstream express_backend {
    server localhost:3000;
    keepalive 16;
}
```

---

## Step 2: Configure the proxy

```nginx
server {
    listen 80;
    server_name localhost;

    client_max_body_size 25M;

    location / {
        proxy_pass http://express_backend;

        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
        proxy_send_timeout 30s;
    }
}
```

---

## Step 3: Test the configuration

```bash
sudo nginx -t
```

---

## Step 4: Reload Nginx

```bash
sudo systemctl reload nginx
```

---

## Step 5: Verify

```bash
curl http://localhost
```

Then inspect the Nginx logs:

```bash
sudo tail -f /var/log/nginx/access.log
```

and, if something goes wrong:

```bash
sudo tail -f /var/log/nginx/error.log
```

```text

    Nginx
      │
      ▼
localhost:3000
      │
```

Nginx handles:

- HTTPS

# Key Takeaways

- Advanced proxy settings improve reliability and performance in production.
    
- Buffering allows backends to finish work quickly while Nginx serves slow clients.
    
- Timeouts prevent requests from hanging indefinitely.
    
- `client_max_body_size` controls upload limits.
    
- `upstream` blocks simplify configuration and prepare you for load balancing.
    
- Unix sockets are an efficient option for local backend communication.
    
- WebSockets require HTTP/1.1 and upgrade headers to function correctly.
