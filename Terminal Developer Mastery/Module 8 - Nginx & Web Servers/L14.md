# Why Logging Matters

Imagine a user says:

> "I can't log in."

Without logs:

```text

```

With logs:

```text

200
```

```text

```

# Types of Logs

Nginx mainly uses two logs:

```text
Access Log

Error Log
```

---

# Access Log

Every request is recorded.

Default location:

```text
/var/log/nginx/access.log
```

Example:

```text
192.168.1.20 - - [30/Jul/2026:11:22:14 +0530] "GET / HTTP/1.1" 200 612 "-" "Mozilla/5.0"
```

---

# Search Logs

Find all 404 errors:

```bash
grep ' 404 ' /var/log/nginx/access.log
```

Find API requests:

```bash
grep "/api/" /var/log/nginx/access.log
```

Find requests from a specific IP:

```bash

```

# Count Requests

Top requested URLs:

```bash
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -nr | head
```

Example output:

```text

410 /api/users

220 /login
```

# Error Log

Access logs record **every request**.

Error logs record **problems**.

Default:

```text
/var/log/nginx/error.log
```

---

Example:

```text
2026/07/30 11:25:02 [error] 1945#1945:
connect() failed (111: Connection refused)
while connecting to upstream
```

Meaning:

Nginx couldn't connect to the backend.

---

# Watch Error Logs

```bash
tail -f /var/log/nginx/error.log
```

---

# Error Log Levels

Configuration:

```nginx
error_log /var/log/nginx/error.log warn;
```

Common levels:

```text
debug

info

notice

warn

error

crit

alert

emerg
```

Production usually uses:

```text
warn
```

or

```text
error
```

Debug logging is helpful during troubleshooting but can generate a large amount of output.

# Custom Access Logs

Default logs are useful.

Custom logs are even better.

Example:

```nginx
log_format custom
'$remote_addr - $remote_user [$time_local] '
'"$request" $status '
'$body_bytes_sent '
'"$http_referer" '
'"$http_user_agent" '
'$request_time';
```

Enable it:

```nginx
access_log /var/log/nginx/access.log custom;
```

Now each entry includes:

```text
$request_time
```

which helps identify slow requests.

---

# Useful Log Variables

|Variable|Meaning|
|---|---|
|`$remote_addr`|Client IP|
|`$request`|HTTP request|
|`$status`|Status code|
|`$host`|Host header|
|`$uri`|Requested URI|
|`$request_time`|Total request time|
|`$upstream_response_time`|Backend response time|
|`$body_bytes_sent`|Response size|

# Request Tracing

Suppose a request takes:

```text
4.8 seconds
```

Where is the delay?

Use:

```nginx
$request_time
```

Example:

```text
0.002

0.031

4.821
```

You immediately know which requests are slow.

---

# Upstream Response Time

Log:

```nginx
$upstream_response_time
```

Example:

```text
0.010
```

or

```text
2.940
```

If:

```text
$request_time

≈

$upstream_response_time
```

the backend is likely responsible for the delay.

# Debugging 404 Errors

Problem:

```text
404 Not Found
```

Checklist:

- File exists?
    
- Correct `root`?
    
- Correct `alias`?
    
- Correct `location`?
    
- Typo in URL?
    

Test:

```bash
curl -I http://localhost/missing-file
```

---

# Debugging 403 Errors

Meaning:

```text
Forbidden
```

Possible causes:

- File permissions
    
- Directory permissions
    
- `deny all`
    
- Missing index file
    
- SELinux/AppArmor policies (on systems where they are enabled)
    

Check permissions:

```bash
ls -l
```

Check ownership:

```bash
stat index.html
```

---

# Debugging 500 Errors

If Nginx returns:

```text
500 Internal Server Error
```

Usually inspect:

- Backend logs
    
- Application code
    
- Framework logs
    

Nginx itself may simply be passing the backend's error response.

---

# Debugging 502 Bad Gateway

Most common backend deployment problem.

Example:

```text
502 Bad Gateway
```

Possible causes:

- Backend stopped
    
- Wrong port
    
- Firewall
    
- Wrong Unix socket
    
- Socket permission issues
    

Check:

```bash
ss -tulpn
```

Example:

```bash
ss -tulpn | grep 3000
```

Verify your backend is listening on the expected port.

---

# Debugging 504 Gateway Timeout

Meaning:

Backend didn't respond in time.

Possible causes:

- Slow SQL query
    
- Slow MongoDB query
    
- External API delay
    
- Infinite loop
    
- Heavy computation
    

Check:

```nginx
proxy_read_timeout
```

But remember: increasing the timeout may hide the symptom rather than solve the underlying performance problem.

# Reload vs Restart

Reload:

```bash
sudo systemctl reload nginx
```

- Applies configuration changes
    
- Existing connections continue
    

Restart:

```bash
sudo systemctl restart nginx
```

- Stops
    
- Starts again
    
- Existing connections are interrupted
    

Use **reload** whenever possible after configuration changes.

# Monitor Active Connections

Basic stub status module:

```nginx
location /nginx_status {
    stub_status;
    allow 127.0.0.1;
    deny all;
}
```

Reload:

```bash
sudo systemctl reload nginx
```

Check:

```bash
curl http://127.0.0.1/nginx_status
```

Example:

```text
Active connections: 12

server accepts handled requests

1000 1000 2500

Reading: 0

Writing: 2

Waiting: 10
```

Meaning:

- **Active connections**: Total open connections.
    
- **Reading**: Reading client requests.
    
- **Writing**: Sending responses.
    
- **Waiting**: Idle keep-alive connections.

# Real Troubleshooting Workflow

Suppose users report:

```text
Website returns 502.
```

Step 1:

```bash
systemctl status nginx
```

↓

Running?

---

Step 2:

```bash
ss -tulpn | grep 3000
```

↓

Backend running?

---

Step 3:

```bash
tail -f /var/log/nginx/error.log
```

↓

Connection refused?

---

Step 4:

```bash
curl http://localhost:3000
```

↓

Backend responding?

---

Step 5:

```bash
sudo nginx -t
```

↓

Configuration valid?

This systematic approach is much faster than changing random settings.

# Best Practices

- Check **error logs** before changing configuration.
    
- Run `nginx -t` before every reload.
    
- Use custom log formats to record request and upstream response times.
    
- Monitor both Nginx and backend logs together.
    
- Keep log rotation enabled to prevent logs from filling the disk.
    
- Troubleshoot methodically: verify configuration, service status, ports, and logs before making changes.

# Interview Questions

### 1. What's the difference between the access log and the error log?

- **Access log** records every HTTP request.
    
- **Error log** records warnings, errors, and operational problems.
    

---

### 2. How do you validate an Nginx configuration?

```bash
sudo nginx -t
```

---

### 3. What command shows the fully expanded Nginx configuration?

```bash
sudo nginx -T
```

---

### 4. How would you investigate a `502 Bad Gateway` error?

Check:

1. Whether the backend process is running.
    
2. Whether the backend is listening on the configured port or socket.
    
3. Nginx error logs.
    
4. The `proxy_pass` configuration.
    
5. Firewall or permission issues.
    

---

### 5. What is `$upstream_response_time` used for?

It records how long the backend took to respond, helping distinguish backend latency from other delays.

# Hands-on Practice

## Step 1: Watch access logs

```bash
sudo tail -f /var/log/nginx/access.log
```

Visit your site from a browser and observe new entries appear.

---

## Step 2: Watch error logs

```bash
sudo tail -f /var/log/nginx/error.log
```

---

## Step 3: Introduce a configuration error

Edit your Nginx configuration and intentionally misspell a directive, for example:

```nginx
servr_name localhost;
```

Then test:

```bash
sudo nginx -t
```

Observe how Nginx reports the syntax error.

Restore the correct directive before continuing.

---

## Step 4: Trigger a 404

```bash
curl -I http://localhost/file-that-does-not-exist
```

Then search for the request:

```bash
grep "404" /var/log/nginx/access.log
```

---

## Step 5: Simulate a 502

Stop your backend application:

```bash
pm2 stop all
```

or stop the process manually.

Then:

```bash
curl http://localhost/api/hello
```

Check:

```bash
tail -f /var/log/nginx/error.log
```

You should see an upstream connection error.

Restart your backend afterward.

---

## Step 6: Inspect live service logs

```bash
journalctl -fu nginx
```

Reload Nginx in another terminal:

```bash
sudo systemctl reload nginx
```

Watch the journal output in real time.

# Key Takeaways

- The **access log** records every request, while the **error log** records operational issues.
    
- `nginx -t` should be part of every configuration change.
    
- `$request_time` and `$upstream_response_time` are valuable for diagnosing slow requests.
    
- `journalctl`, `systemctl`, `ss`, and `curl` are essential tools alongside Nginx logs.
    
- Follow a structured troubleshooting process instead of guessing.
