# The Big Picture

When you start Nginx:

```bash
sudo systemctl start nginx
```

Linux does **not** create just one process.

Instead, Nginx creates several processes.

```
             Nginx
                │
         Master Process
          /     |      \
 Worker  Worker  Worker ...
```

Each process has a different responsibility.

---

# Why Multiple Processes?

Imagine a restaurant.

One chef cannot cook for 500 customers.

Instead:

- One manager supervises
    
- Many chefs prepare food
    

Nginx works the same way.

|Restaurant|Nginx|
|---|---|
|Manager|Master Process|
|Chef|Worker Process|
|Customers|Clients|

---

# Master Process

The **Master Process** is the boss.

Its job is **not** to serve websites.

Instead, it manages the workers.

Responsibilities:

- Read configuration
    
- Start worker processes
    
- Stop workers
    
- Restart workers
    
- Reload configuration
    
- Handle signals
    

Think of it as a supervisor.

```
            Master
          /    |    \
      Worker Worker Worker
```

The master rarely handles client requests.

---

# Worker Processes

Workers do the real work.

Every HTTP request goes to a worker.

Example:

```
Browser

↓

Worker Process

↓

Serve HTML
```

Or

```
Browser

↓

Worker

↓

Proxy to Node.js

↓

Return Response
```

Workers are responsible for:

- Accepting connections
    
- Reading requests
    
- Serving files
    
- Sending responses
    
- Reverse proxy
    
- Caching
    
- Compression
    

---

```

```

Notice:

- One master

# Why Multiple Workers?

Modern CPUs have multiple cores.

Example:

```
CPU

Core 1

Core 2

Core 3

Core 4
```

Nginx can run one worker per CPU core.

Example:

```
Master

↓

Worker 1 → Core 1

Worker 2 → Core 2

Worker 3 → Core 3

Worker 4 → Core 4
```

This allows requests to be processed in parallel.

---

# How Many Workers?

Inside `nginx.conf`:

```nginx
worker_processes auto;
```

`auto` means:

> Create one worker for each CPU core.

Example:

4 CPU cores

↓

4 workers

8 CPU cores

↓

8 workers

This is recommended for most systems.

---

# Worker Connections

Each worker can handle many client connections.

Configuration:

```nginx
events {
    worker_connections 1024;
}
```

This means:

One worker

↓

1024 simultaneous connections

If there are:

```
4 workers

×

1024 connections

=

4096 connections
```

Nginx can serve thousands of clients at the same time.

---

# Traditional Servers

Older servers worked differently.

One client

↓

One thread

```
Client 1 → Thread 1

Client 2 → Thread 2

Client 3 → Thread 3

Client 4 → Thread 4
```

Thousands of users required thousands of threads.

Problems:

- Huge memory usage
    
- Context switching
    
- Slower performance
    

Apache (traditional process/thread model) commonly used this approach.

---

# Nginx's Event-Driven Architecture

Nginx uses an **event loop**.

Instead of:

```
1 Client

↓

1 Thread
```

It uses:

```
One Worker

↓

Many Connections
```

Like this:

```
Worker

├── Client 1

├── Client 2

├── Client 3

├── Client 4

├── Client 5

└── Client 1000
```

One worker watches many connections.

---

# What is an Event?

An event is simply:

> "Something happened."

Examples:

- New client connected
    
- Data received
    
- File finished reading
    
- Response ready
    
- Connection closed
    

The worker reacts only when something happens.

---

# Imagine a Call Center

Old model:

Each customer gets one employee.

```
Customer 1 → Employee 1

Customer 2 → Employee 2

Customer 3 → Employee 3
```

Nginx model:

One employee monitors many phone calls.

When someone speaks:

↓

Respond.

When silent:

↓

Move to another call.

Very efficient.

---

# Non-Blocking I/O

This is a key idea behind Nginx.

Suppose reading a file takes 2 seconds.

Blocking server:

```
Read File...

(wait...)

(wait...)

(wait...)
```

Nothing else happens.

Nginx:

```
Start reading file

↓

Handle another client

↓

Handle another client

↓

File ready

↓

Send response
```

It doesn't waste time waiting.

---

# Event Loop

Simplified:

```
while (running)

↓

Wait for events

↓

Process event

↓

Back to waiting
```

Thousands of connections can be managed with a small number of workers.

---

# Request Processing

Let's request:

```
GET /
```

Flow:

```
Browser

↓

Master

↓

Worker accepts request

↓

Read request

↓

Find configuration

↓

Serve HTML

↓

Return response
```

The master doesn't process the request—it simply manages workers.

# Reverse Proxy Example

```
Browser

↓

Worker

↓

Node.js

↓

Worker

↓

Browser
```

The worker forwards the request to your backend and sends the backend's response back to the client.

# Static File Example

```

↓

↓

```

# Connection Lifecycle

```
Client Connects

↓

Worker Accepts

↓

Read Request

↓

Process Request

↓

Send Response

↓

Close Connection
```

Or, if Keep-Alive is enabled:

```
Keep Connection Open

↓

Wait for Next Request
```

---

# Keep-Alive

Without Keep-Alive:

```
Connect

↓

Request

↓

Disconnect
```

Repeated for every request.

With Keep-Alive:

```
Connect

↓

Request 1

↓

Request 2

↓

Request 3

↓

Disconnect
```

Reusing connections reduces latency and CPU overhead.

---

# Performance Model

Nginx is fast because it:

- Uses few processes
    
- Uses little memory
    
- Handles many connections per worker
    
- Uses non-blocking I/O
    
- Uses an event-driven architecture
    
- Minimizes context switching
    

---

# Worker Crash Scenario

Suppose a worker crashes.

```
Worker

↓

Crash
```

The master detects it.

```
Master

↓

Start New Worker
```

The service continues running without manual intervention.

---

# Reload Configuration

When you run:

```bash
sudo systemctl reload nginx
```

The sequence is:

```
Master

↓

Read New Configuration

↓

Start New Workers

↓

Old Workers Finish Requests

↓

Old Workers Exit
```

This enables **zero-downtime configuration reloads**.

# Interview Questions

### 1. What is the job of the master process?

The master process reads the configuration, starts and stops worker processes, reloads configuration, and manages the overall Nginx lifecycle. It does **not** handle client requests.

---

### 2. What do worker processes do?

Worker processes accept client connections, process HTTP requests, serve static files, proxy requests to backend applications, and send responses.

---

### 3. Why is Nginx considered event-driven?

Instead of creating one thread or process per connection, each worker monitors many connections and reacts only when events occur, allowing it to efficiently handle thousands of simultaneous clients.

---

### 4. What does `worker_processes auto;` mean?

It tells Nginx to automatically create one worker process for each available CPU core.

---

### 5. What does `worker_connections 1024;` mean?

Each worker can manage up to **1024 simultaneous connections** (subject to operating system limits such as available file descriptors).

---

### 6. Why is Nginx more memory-efficient than traditional thread-per-request servers?

Because it uses a small number of worker processes with an event-driven, non-blocking model instead of creating a separate thread or process for every client connection.

---

# Key Takeaways

- Nginx uses **one master process** and **multiple worker processes**.
    
- The **master process manages** Nginx; **workers handle** client requests.
    
- Workers use an **event-driven, non-blocking I/O model** to efficiently manage thousands of simultaneous connections.
    
- `worker_processes auto;` matches the number of workers to the CPU cores.
    
- `worker_connections` controls how many simultaneous connections each worker can handle.
    
- Reloading Nginx creates new workers with the updated configuration while allowing existing workers to finish their current requests, enabling zero-downtime configuration changes.
