# Connecting to Localhost

Welcome to the first practical lesson of SSH.

Today, you won't connect to a cloud server or VPS.

Instead, you'll connect to **your own computer**.

This is the safest place to learn because if something goes wrong, you aren't affecting a production server.

# What is Localhost?

Every computer can talk to **itself**.

This special address is called:

```
localhost
```

Think of it as calling your own phone number.

The call never leaves your phone.

Similarly:

```
ssh localhost
```

never leaves your computer.

---

# The Loopback Interface

Linux has a special network interface called the **loopback interface**.

Its job is to let programs communicate with the same machine.

Diagram:

```
Your Computer
     │
     ▼
Loopback Interface
     │
     ▼
Your Computer
```

No router.

No internet.

No Wi-Fi.

Everything stays inside your computer.

---

# Localhost vs 127.0.0.1

These two are almost always equivalent.

```
localhost
```

↓

maps to

```
127.0.0.1
```

Example:

```bash
ping localhost
```

and

```bash
ping 127.0.0.1
```

Both usually reach the same destination.

---

# What About My Hostname?

Every computer also has a hostname.

Find yours:

```bash
hostname
```

Example:

```
mint-laptop
```

If your hostname resolves correctly, this may also work:

```bash
ssh mint-laptop
```

However, **`localhost` is the most reliable choice** for local testing because it always refers to the current machine.

---

# Three Ways to Reach Your Own Machine

```
localhost
```

↓

```
127.0.0.1
```

↓

```
Your hostname
```

All may point to your computer, but they are resolved differently.

|Method|How it works|
|---|---|
|`localhost`|Special hostname mapped locally|
|`127.0.0.1`|IPv4 loopback IP address|
|`hostname`|Resolved through local name resolution or DNS|

---

# Does SSH Need an SSH Server?

Yes.

Remember Module 1:

```
SSH Client
     │
     ▼
SSH Server (sshd)
```

Even when connecting to yourself, the SSH client still needs an SSH server to accept the connection.

---

# Check if SSH Server is Running

Run:

```bash
systemctl status ssh
```

Possible result:

```
Active: active (running)
```

Great! You can continue.

If you see:

```
Unit ssh.service could not be found
```

or

```
inactive (dead)
```

don't worry—we'll install and configure the SSH server in **Lesson 2**.

---

# Your First SSH Connection

If your SSH server is running:

```bash
ssh localhost
```

The first time, you'll likely see:

```
The authenticity of host 'localhost' can't be established.
ED25519 key fingerprint is ...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Type:

```
yes
```

SSH stores the server's fingerprint in:

```
~/.ssh/known_hosts
```

---

# Authentication

Next, SSH will authenticate you.

Depending on your setup, it may ask for:

- Your account password
- Your SSH key passphrase
- Nothing at all (if key-based login is already configured)

Example:

```
rahul@localhost's password:
```

Remember: nothing appears while you type the password. This is normal.

---

# Welcome to the Remote Shell

After logging in successfully:

```
Last login: Wed Jul 29 17:45:22
rahul@mint:~$
```

It may look exactly like your normal terminal prompt.

That's because you're logged into **the same computer**, but through SSH.

---

# Verify You're Connected

Run these commands:

```bash
whoami
```

Shows the current user.

---

```bash
hostname
```

Shows the machine name.

---

```bash
pwd
```

Shows the current working directory.

---

```bash
uptime
```

Shows how long the system has been running.

---

# Exit the Session

When finished:

```bash
exit
```

or press:

```
Ctrl + D
```

You'll return to your original terminal.

---

# What Actually Happened?

Even though you stayed on the same machine:

```
Terminal
     │
     ▼
SSH Client
     │
     ▼
127.0.0.1:22
     │
     ▼
SSH Server
     │
     ▼
Remote Shell
```

This is the exact same process used when connecting to a VPS—only the destination changes.

# Why Backend Developers Practice with Localhost

Local SSH is perfect for:

- Testing SSH configurations
- Learning key authentication
- Practicing commands safely
- Troubleshooting without internet access
- Trying new SSH options before using production servers

Many developers test locally before changing server configurations.

---

# Common Problems

### Connection Refused

```
ssh: connect to host localhost port 22:
Connection refused
```

Cause:

- SSH server isn't running.

Solution:

```bash
sudo systemctl start ssh
```

---

### Permission Denied

```
Permission denied
```

Cause:

- Wrong username
- Wrong password
- Incorrect SSH key

---

### Host Key Warning

```
WARNING:
REMOTE HOST IDENTIFICATION HAS CHANGED!
```

Usually happens if the SSH server was reinstalled or its host keys changed.

We'll learn how to handle this safely in Lesson 4.

# Key Takeaways

- `localhost` is a special hostname that always refers to your own computer.
- `127.0.0.1` is the IPv4 loopback address.
- An SSH client still needs an SSH server (`sshd`), even for local connections.
- The first connection stores the server's fingerprint in `~/.ssh/known_hosts`.
- Practicing with `localhost` builds confidence before working with remote servers.
