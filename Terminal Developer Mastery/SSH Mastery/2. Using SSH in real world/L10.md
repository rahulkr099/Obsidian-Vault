# Mastering `~/.ssh/config`

This is one of the **highest ROI (Return on Investment)** SSH features you'll ever learn.

Almost every experienced backend engineer has an SSH configuration file.

Instead of typing this every day:

```bash
ssh -i ~/.ssh/company_key -p 2222 ubuntu@203.0.113.10
```

This saves time, reduces mistakes, and makes automation much cleaner.

# What is `~/.ssh/config`?

It's a configuration file that tells SSH:

> "Whenever I connect to this host, use these settings automatically."

Location:

```
~/.ssh/config
```

Think of it as your personal address book for SSH.

---

# Without SSH Config

Suppose you have a production server.

Every connection requires:

```bash
ssh \
-i ~/.ssh/company_key \
-p 2222 \
ubuntu@203.0.113.10
```

That's a lot to remember.

---

# With SSH Config

Create one configuration entry:

```
Host production
    HostName 203.0.113.10
    User ubuntu
    Port 2222
    IdentityFile ~/.ssh/company_key
```

Now connect with:

```bash
ssh production
```

That's it.

---

# Creating the File

Check whether it exists:

```bash
ls -l ~/.ssh/config
```

If it doesn't exist:

```bash
touch ~/.ssh/config
```

Set secure permissions:

```bash
chmod 600 ~/.ssh/config
```

Open it:

```bash
nvim ~/.ssh/config
```

or

```bash
nano ~/.ssh/config
```

---

# Understanding Each Field

Example:

```
Host production
    HostName 203.0.113.10
    User ubuntu
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```

Meaning:

|Field|Purpose|
|---|---|
|`Host`|Alias you type|
|`HostName`|Real hostname or IP|
|`User`|Login username|
|`Port`|SSH port|
|`IdentityFile`|Private key|

```
    User ubuntu
    IdentityFile ~/.ssh/staging_key

    User dev
    IdentityFile ~/.ssh/dev_key
```

Now:


```bash

```


# Global Settings

You can apply settings to every host.

Example:

```
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
```

Meaning:

Every SSH connection automatically:

- sends keep-alive packets every 60 seconds
- disconnects after 3 missed replies

---

# Combining Global and Host Settings

```
Host *
    ServerAliveInterval 60

Host production
    HostName 203.0.113.10
    User ubuntu
    IdentityFile ~/.ssh/prod_key

Host staging
    HostName 203.0.113.20
    User ubuntu
```

Global settings apply to all hosts unless a host-specific setting overrides them.

---

# Viewing the Effective Configuration

Suppose you're unsure what SSH will actually use.

Run:

```bash
ssh -G production
```

You'll see the fully resolved configuration, including defaults and values from your config file.

Search for a specific option:

```bash
ssh -G production | grep identityfile
```

# SSH Config with Remote Commands

Works exactly the same.

Instead of:

```bash
ssh ubuntu@203.0.113.10 uptime
```

You can write:

```bash
ssh production uptime
```

Or:

```bash
ssh production "pm2 status"
```

Or:

```bash
ssh production "docker ps"
```

This is one reason SSH config is so useful in scripts and daily work.

# Common Mistakes

## ❌ Wrong Permissions

If the file is world-readable:

```bash
chmod 600 ~/.ssh/config
```

SSH expects configuration files in `~/.ssh` to have restrictive permissions.

---

## ❌ Using Tabs

Prefer spaces for indentation:

```
Host production
    User ubuntu
```

Most examples and documentation use spaces, which avoids formatting inconsistencies.

---

## ❌ Duplicate Host Names

Bad:

```
Host production
...

Host production
...
```

Only one alias should represent one logical connection.

```
    ServerAliveCountMax 3

    User YOUR_USERNAME

```

```
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519
```

Then you can simply use:

```bash
ssh my-vps
```

# Key Takeaways

- `~/.ssh/config` stores reusable SSH connection settings.
- `Host` is your shortcut name.
- `HostName` is the real server address.
- You can save usernames, ports, identity files, and keep-alive settings.
- `ssh -G HOST` shows the final configuration SSH will use.

## Pro Tip ⭐

Many deployment scripts become much cleaner with SSH aliases. Compare:

Without config:

```bash
ssh -i ~/.ssh/company_key -p 2222 ubuntu@203.0.113.10 "pm2 restart backend"
```

With config:

```bash
ssh production "pm2 restart backend"
```

The second version is easier to read, less error-prone, and much easier to maintain—especially when used in shell scripts or CI/CD pipelines.
