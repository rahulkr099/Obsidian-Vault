# The Problem

Imagine you run these commands:

```bash
ssh production uptime
```

Then:

```bash
ssh production "pm2 status"
```

Then:

```bash
ssh production "docker ps"
```

Each command:

- Creates a TCP connection
- Performs SSH encryption negotiation
- Authenticates
- Opens a session

This repeated setup adds noticeable delay.

---

# Solution: Connection Multiplexing

SSH can reuse an existing connection.

Instead of:

```
Laptop
 │
 ├── SSH Connection #1
 ├── SSH Connection #2
 ├── SSH Connection #3
```

SSH uses:

```
Laptop
 │
 └── One Master Connection
        │
        ├── Command 1
        ├── Command 2
        └── Command 3
```

Much faster.

---

# Enable Multiplexing

In:

```
~/.ssh/config
```

Add:

```
Host *
    ControlMaster auto
    ControlPath ~/.ssh/control-%r@%h:%p
    ControlPersist 10m
```

---

# What These Mean

## `ControlMaster auto`

Automatically create a master SSH connection.

---

## `ControlPath`

Where SSH stores the socket used to reuse the connection.

Example:

```
~/.ssh/control-ubuntu@production:22
```

---

## `ControlPersist`

```
10m
```

Keep the master connection alive for **10 minutes** after the last session ends.

During those 10 minutes, future SSH commands connect almost instantly.

---

# How It Works

First connection:

```bash
ssh production
```

Time:

```
2 seconds
```

Disconnect.

Immediately run:

```bash
ssh production uptime
```

Time:

```
0.1 seconds
```

Because the existing master connection is reused.

---

# Checking if Multiplexing Works

Run:

```bash
ssh -v production
```

Look for output similar to:

```
Control socket connect
```

or

```
Multiplexing control connection
```

The exact wording varies by OpenSSH version, but messages mentioning a **control socket** or **multiplexing** indicate that connection sharing is being used.

# Running Commands in Parallel

Suppose you have:

```
production
staging
development
```

Instead of checking them one at a time:

```bash
ssh production uptime
```

```bash
ssh staging uptime
```

```bash
ssh development uptime
```

Use a loop:

```bash
for host in production staging development
do
    echo "== $host =="
    ssh "$host" uptime
done
```

# Useful Shell Aliases

Instead of typing:

```bash
ssh production
```

Create an alias.

In:

```
~/.zshrc
```

or

```
~/.bashrc
```

Add:

```bash
alias prod="ssh production"
```

Now:

```bash
prod
```

connects immediately.

---

Another example:

```bash
alias logs="ssh production 'pm2 logs backend'"
```

Now:

```bash
logs
```

opens your production logs.

# Using `scp` with SSH Config

Without config:

```bash
scp -i ~/.ssh/key file.txt ubuntu@203.0.113.10:/tmp
```

With config:

```bash
scp file.txt production:/tmp
```

Much cleaner.

Use:


# Measuring Connection Time

Use:

```bash
time ssh production exit
```

Example:

```
real    0m1.92s
```

With multiplexing enabled, the second connection is often significantly faster because it reuses the existing master connection.

# Cleaning Up Control Sockets

Sometimes you want to close the master connection immediately.

Use:

```bash
ssh -O exit production
```

Meaning:

> Close the master connection for the host named `production`.

Check:

```bash
ls ~/.ssh/control-*
```

to see existing control sockets.

---

# Common Mistakes

## ❌ Huge `ControlPersist`

Example:

```
24h
```

Leaving a master connection open for a full day may not match your organization's security expectations.

For most personal development setups, values like **5–15 minutes** are a practical balance.

---

## ❌ Forgetting SSH Config

Multiplexing depends on:

```
~/.ssh/config
```

Without those settings, every connection starts from scratch.

---

## ❌ Creating Too Many Aliases

Good:

```bash
prod
```

Bad:

```bash
p
```

Aliases should remain descriptive so they're easy to remember.

## Pro Tip ⭐

For your future Node.js backend work, a highly productive SSH configuration is:

```
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
    ControlMaster auto
    ControlPersist 10m
    ControlPath ~/.ssh/control-%r@%h:%p
```

This combination gives you:

- Stable connections
- Faster reconnects
- Less typing
- Better support for deployment scripts

Many experienced Linux and DevOps engineers use a setup very similar to this.
